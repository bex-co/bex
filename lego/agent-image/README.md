# Agent sandbox image

This image is ADR047's in-sandbox execution environment. It contains git, Node.js, Python 3.11 (Debian's `/usr/bin/python3`) and every line 3.8 to 3.15 (`python3.8` … `python3.15`, each with `pip` and `venv`; the session's own choice is `python3`, below), Go, JDK 17, Rust and Cargo through rustup, build tools, `uv`/`uvx`, `gitleaks`, `gh`, the AWS CLI, nvm, direnv, the pinned Claude Code, Codex, Gemini, Muse Code and DeepSeek Harness ACP adapters, the gateway-backed Git proxy path, and the bex session driver. The driver owns one ACP agent over stdio and exposes port `8787`:

- `GET /stream` — AI SDK v6 UI-message SSE. Provider `raw` chunks are retained as standard `data-acp` parts so plans, diffs, and terminals survive the AI SDK's UI conversion.
- `POST /turn` — accepted only with the gateway's signed, single-use driver grant; raw ACP launch is intentionally not exposed.

The cluster's `sandbox-agent-driver-ingress` Cilium policy admits port `8787` only from the `bex-ssh-gateway` workload identity. The process intentionally binds the pod interface; loopback-only binding would make the gateway path impossible.

## Build and configure

Build from the `lego/` context:

```sh
docker build -f agent-image/Dockerfile -t bex-agent-sandbox:dev .
```

## Agent-owned delivery (ADR090)

The agent delivers its own work; the driver never commits or pushes. During setup the driver checks out the session branch (cloning `BEX_AGENT_REPO_URL` when the workspace is empty) and writes repo-local `user.name`/`user.email`, `push.default=current` and the branch upstream, so a plain `git commit` and `git push` land on the bound branch. Repo hooks run for the agent as they would for a developer; only the driver's own setup and read-only Git calls are hardened.

Every session carries the bex platform overlay (`driver/src/overlay.ts`): where the agent runs, what it can use, and that the deliverable is a PR, ready for review unless a draft is asked for (w10/040), merged or marked ready only when the task or a person's message asks. It travels through ACP `systemPrompt` append when the adapter advertises `sessionCapabilities.systemPrompt` (claude-agent-acp), as Codex `developer_instructions` via `CODEX_CONFIG` for codex-acp, and otherwise as a first-prompt preamble that is never published to the stream. An `invalid_params` reply fails the turn with a named reason. Claude sessions also disable Claude Code's built-in git instructions and attribution.

Repo sessions register the `bex` stdio MCP server (`dist/mcp-bex.js`) on `session/new` and `session/load`. Its single tool, `open_or_update_draft_pr({title, body, draft?})`, posts to the gateway's `pull-request` verb at `BEX_AGENT_REPO_URL` + `/pull-request`; head, base and repository are fixed by that path, and the gateway authenticates the source Pod. It opens the pull request ready for review, as Devin does, and as a draft only with `draft: true`, which the overlay and the tool's description reserve for a task, message or repository instructions that ask for one (w10/040); `draft` is read only when the pull request is opened, and `draft_not_supported` refuses it on a repository whose plan has no drafts. Repo sessions also get `reply_on_pull_request({body})` (ADR047 D11), which posts one comment on the session's own pull request through the `pull-request/comment` verb on the same path; the PR number is fixed server-side and bex appends a footer naming the agent. Since w10/m538 they also get `mark_pull_request_ready({})` and `merge_pull_request({method?, commitTitle?, commitMessage?, auto?} | {disableAuto})`, which undraft and merge the session's own pull request through the `pull-request/ready` and `pull-request/merge` verbs, as Devin does when asked. The merge is pinned to the head bex last recorded for the pull request and uses the named method or the repository's first allowed one; branch protection decides, and GitHub's refusal comes back with its reason under a typed code (`merge_blocked`, `head_changed`, `merge_method_not_allowed`, `not_permitted`, `pull_request_draft`, `auto_merge_not_allowed`). Since w10/m577 `auto: true` arms GitHub auto-merge, pinned the same way, so GitHub merges the pull request once its required checks pass (`{merged: false, autoMerge: true}`), a base branch that requires a merge queue queues it with or without `auto` (`mergeQueue: true`), and `disableAuto: true` undoes either (`autoMergeDisabled: true`). An armed or queued answer also carries `next`, which tells the agent to end its turn without watching the checks and to report it armed or queued, not merged. The overlay and both tool descriptions say to use them only when the task or a person's message asks; asked to merge once the checks pass, the agent calls the tool with `auto: true` and ends its turn instead of watching the checks. After a merge, and only a merge, the tool marks the driver's pull request record merged at that head, so the post-turn check does not call merged work unpushed when GitHub deletes the branch. There is no GitHub token in the image. `gh` reads the session's repository and makes the writes the gateway admits through it instead (see below). Sessions that can still start children (`BEX_AGENT_SPAWN_URL`, ADR102 D9) also get `spawn_session`, `get_child_session`, `wait_child_sessions({childIds, timeoutSeconds?})`, `message_child_session({childId, prompt})` and `cancel_child_session({childId})`, which call the session's Pod-bound spawn URL with no credential; the parent is always the calling session and only its own descendants can be named.

When the agent ends its turn the driver reads Git state (dirty tree, local commits on neither the remote session branch nor its base branch, remote head, recorded PR). If work is undelivered it sends one follow-up prompt on the same ACP session, then re-reads the facts and writes them to the status file as `git{dirty,unpushedCommits,remoteHead,baseBranch,prRecorded,prUrl,prNumber}`.

The official `@agentclientprotocol/sdk` and AI SDK versions are exact pins in `driver/package.json`; each public ACP adapter is pinned and build-verified in the image Dockerfile. A provider CLI that ships as a native binary rather than an npm package (Muse Code's `muse`, ADR108) carries a `nativeBinary` pin in the profile manifest: the `native-binaries` stage downloads the artifact for the target architecture and refuses it unless its SHA-256 matches, and `install-profiles` checks the installed file again, that it is root-owned, and that `--version` reports the pinned version. A profile's `sessionConfig` is set with ACP `session/set_config_option` after every `session/new` and `session/load` (Muse: its own sandbox off, approvals settled natively), and its `model` is written to Muse's settings before the adapter starts, together with `run.workflow_trigger_mode: off`: a Muse workflow only reports after the turn has ended, so it would end the turn with its work undone (ADR108 D8). A profile's `nodeRuntime` names the Node that runs its executable (DeepSeek Harness needs Node 24, copied to `/opt/node24/bin/node` from a pinned image stage, while the agent's shell keeps the image's Node 22; ADR114): `install-profiles` checks it is root-owned and meets the package's `engines.node`, and the driver starts DeepSeek Harness on it from an empty launch directory with a `--patch` overlay that pins its OpenRouter model at the gateway. The driver probes `initialize.agentCapabilities` before calling optional `session/load`. For the pinned Codex adapter it also binds the OpenAI provider through ACP `providers/set` before `session/new`; `OPENAI_BASE_URL` alone can leave Codex on its built-in public origin. The binding carries only the session placeholder and the exact internal model-proxy URL. The driver negotiates Codex's typed session-failure extension and turns a terminal provider/transport record into the persisted failed verdict instead of accepting its `end_turn` wrapper as a false-green no-op.

## Baked tools and `gh` (w10/m513)

The Dockerfile pins each tool it adds beside the language toolchains, and its final-stage check fails the build unless each reports its pin: the Python lines below, `uv`/`uvx` `0.13.9` and `gh` `2.105.0` from their release tarballs checked by SHA-256 per architecture, and `gitleaks` `8.30.1` built from its module (pinned by its go.sum hash) with the image's Go toolchain, since the release binary's Go 1.24 standard library fails the Trivy CRITICAL gate. The check also runs `uv venv --python 3.12` with `UV_PYTHON_DOWNLOADS=never`. Other tool versions are a repository environment's setup step away: every session's GitHub baseline includes `release-assets.githubusercontent.com`, where GitHub release downloads (`uv python install`, tool tarballs) redirect.

In a repo session the driver serves a Unix socket beside its status file (`gh/api.sock`) and writes a gh config naming it (`http_unix_socket`). The agent's environment gets `GH_CONFIG_DIR`, `GH_REPO` (the session's repository: `origin` is the Git proxy, which gh cannot map), a placeholder `GH_TOKEN`, `GH_PROMPT_DISABLED=1` and no update checks. gh sends each call over the socket as plain HTTP; the driver forwards `api.github.com` calls to the gateway's `github-api` route at `BEX_AGENT_REPO_URL` + `/github-api/<path>` and refuses any other host. The gateway admits REST `GET`/`HEAD` on `/repos/<owner>/<repo>/…` and GraphQL queries that read that repository, a node by id, the rate limit or the schema, injects a read-only installation token of that one repository, and follows GitHub's log and archive redirects itself, without the token. So `gh run list`, `gh run view --log-failed`, `gh pr view <number>`, `gh pr checks <number>` and `gh api repos/{owner}/{repo}/…` work; a `gh pr` command without the number fails, since gh cannot find the current branch's pull request through `origin`, so the overlay names the number (w10/042). Since w10/m522 it also admits the writes ADR090 D4 lists on that repository, each with a token minted for that call that holds pull requests, issues and Actions write and no contents write: `gh pr comment`, review-thread replies, `gh pr review --comment`/`--request-changes`, `gh pr edit --add-label/--add-assignee/--add-reviewer`, `gh issue create/comment/edit/close`, `gh run rerun [--failed|--job]`, `gh run cancel` and, since w10/033, `gh workflow run <workflow> --ref <the session branch>`. It refuses `gh pr create`, `pr edit --title/--body/--base`, `pr ready` and `pr merge` (naming `mark_pull_request_ready` and `merge_pull_request`), `pr close`, `pr review --approve`, `gh workflow run` on any other ref (or with no `--ref`, which picks the default branch) and every code, ref or settings write with a message naming the `bex` tools. Sessions without a repository get no gh configuration, and neither does a session dispatched with `BEX_AGENT_GITHUB_CLI=0` (its workspace's admins turned `gh` off, w10/m524): it has no socket, no `GH_*` variables, and an earlier turn's gh config on a kept disk is removed. Since w10/m561 the same holds for a session whose own `agentConfig.githubCli`, whose automation or whose workspace's automations default turned `gh` off. Its overlay says who turned `gh` off (`BEX_AGENT_GITHUB_CLI_LEVEL`) and that pull requests stay with the `bex` tools, and the gateway refuses its route naming that level, which also covers a turn that started before the setting changed.

`gh` works the same way in the session's terminals (w10/027), as Devin's `gh` token is on the machine for every shell. Once the socket serves, the driver writes the agent's `GH_*` settings as shell exports to `gh/env.sh` beside its status file (mode 0600, uid 10001's, as the terminals are), and `bex-agent-tools.sh` sources that file in every shell it sets up. The web Shell and an SSH session start `/bin/sh`, which is dash and reads the script through `ENV`; `ssh … '<command>'` and Zed run `/bin/sh -lc`, a login shell that reads it through `/etc/profile`; and every bash reads it as below. So `gh run list` and `gh api repos/{owner}/{repo}` work in a terminal without arguments and reach the same gateway route, with the same admitted writes and the same refusals. A session without a repository, or with `gh` turned off, has no `gh/env.sh`, so its terminals have no `GH_*` and `gh` asks for `gh auth login`. The socket was already reachable from a terminal, which runs as the agent's uid, so the file adds no access.

## The session's Python (w4/m544)

A session runs the Python its repository asks for, chosen by Render's rules from the table a native build uses ([ADR047 § A session runs the Python its repository asks for](../../docs/ADR047-cloud-coding-agent-sessions.md#a-session-runs-the-python-its-repository-asks-for-amendment-w4m544-2026-11-20)): `PYTHON_VERSION`, then the root `.python-version`, then Render's default for when the session was created (`BEX_AGENT_SESSION_CREATED_AT`).

- **Baked lines.** Each `python-3.X` stage is the digest-pinned official image a native build of that bookworm line runs on (`lego/types/toolchains/python.go`; 3.8.20, 3.9.25, 3.10.22, 3.11.18, 3.12.16, 3.13.18, 3.14.10, 3.15.2: `PYTHON_VERSIONS`), the official builds, with GNU readline. `python-tree.sh` keeps only `python3.X`, `pip3.X`, `libpython3.X.so*`, `lib/python3.X` and `include/python3.X`, byte-compiles the library (the image ships no `.pyc`, and a session cannot write one beside the root-owned library) and strips the debug symbols the full image keeps. Each line is one linked layer, so a refreshed digest pulls and replaces that line alone; before stripping and bytecode the files are 17 MB (3.8) to 31 MB (3.15) compressed. `/usr/bin/python3` stays Debian's 3.11. The final-stage check fails the build unless each line reports its patch, imports `ssl`, `sqlite3`, `ctypes`, `readline` (GNU, not libedit), `ensurepip`, `venv` and the other compiled modules, runs `pip` and makes a venv (3.12's with its own `pip`). `TestAgentImageBakesTheTablesPythonLines` (`lego/backend/cmd/agent-toolchain`) fails when a stage, a patch or a copy drifts from the table. 3.7, whose official build is bullseye's and needs OpenSSL 1.1, is not baked and is refused by name in a session.
- **Selection.** `agent-toolchain` (`lego/backend/cmd/agent-toolchain`, at `/usr/local/bin/agent-toolchain`) resolves the choice; the check runs it in an empty directory and requires today's default to be a baked patch. After the checkout and before any setup step, the driver (`driver/src/python-select.ts`) points `python`, `python3`, `pip`, `pip3` and the line's `python3.X`/`pip3.X` in `/opt/bex-python/bin` at it. That directory, uid 10001's, is first on the image's `PATH` and on the one `bex-agent-tools.sh` restores in a login shell, so the agent, setup steps, the web Shell, SSH and Zed all run it; the check proves `sh -c`, `sh -ic`, `sh -lc`, `bash -c`, `bash -lc` and `bash -ic` see it. The first turn shows `setup: Python` with `==> Using Python <version> (from PYTHON_VERSION | .python-version)` or `(default)`; a snapshot build records it as its first step; a refused request fails setup `AGENT_SESSION_SETUP_FAILED` naming it.
- **Exact patches.** A `PYTHON_VERSION` patch the image lacks is fetched from the official image's top layers on Docker Hub (`driver/src/python-fetch.ts`, through `curl`, so the session's proxy applies) into `/opt/bex-python/<version>`, checked against each layer's digest; when that fails the line's baked patch runs and the step names the fallback and why.
- **uv.** No `UV_PYTHON*` variable is set, so uv's own settings decide: it finds the selected `python3.X` on `PATH`, and `python-preference = "only-managed"` still downloads uv's build.

## Devin's base-image runtimes (w10/024)

Devin's base image has JDK 17, Rust and Cargo through rustup, the AWS CLI, nvm and direnv ([Template library](https://docs.devin.ai/onboard-devin/environment/templates), read 2026-11-19), so this image has them too, each pinned and checked the same way:

- **JDK 17:** Eclipse Temurin `17.0.21` from the digest-pinned `eclipse-temurin:17.0.21_9-jdk-noble`, at `/opt/java/openjdk` (`JAVA_HOME`), without its `jmods`.
- **Rust:** rustup `1.29.3` (rustup-init checked by SHA-256 per architecture) with the `1.100.0` toolchain, minimal profile plus `clippy` and `rustfmt`, in the official rust image's layout: `RUSTUP_HOME=/usr/local/rustup`, `CARGO_HOME=/usr/local/cargo`, with `~/.rustup` and `~/.cargo` linked to them, so `. "$HOME/.cargo/env"` works.
- **AWS CLI:** `2.41.2`, AWS's installer checked by SHA-256 per architecture, in `/usr/local/aws-cli`.
- **nvm:** `0.41.0`, its three files from the release tag checked by SHA-256, in `NVM_DIR=/usr/local/nvm`.
- **direnv:** `2.38.2`, built from its module (pinned by its go.sum hash) with the image's Go toolchain, as `gitleaks` is.

uid 10001 owns the Rust and nvm homes, so a session installs the toolchain a `rust-toolchain.toml` names, a `rustup component` or the Node an `.nvmrc` names (`nvm install`), and cargo keeps its registry cache there. What they fetch is in the registry catalog of every session (ADR047 D5): `index.crates.io`, `static.rust-lang.org` and `nodejs.org`, plus the Gradle wrapper's and plugin portal's hosts for the JDK.

`/etc/profile.d/bex-agent-tools.sh` (`bex-agent-tools.sh`) sets up the shells. Interactive bash (a terminal's `bash`, Zed's terminal) reads it through `/etc/bash.bashrc`, and an interactive `sh` (the web Shell's and SSH's `/bin/sh`, dash) through `ENV` (a `PATH` fix and a repo session's `gh` settings, above). In an interactive bash, nvm loads as its installer sets it up, so `nvm alias default` applies, and the direnv hook loads an allowed `.envrc` at each prompt, as in Devin's shell. Login shells (`bash -l`, which Claude Code takes its shell snapshot in) read it through `/etc/profile`, and it puts the image's toolchains back on the `PATH` Debian's `/etc/profile` resets. Every other bash (a setup step, `bash -c`) reads it through `BASH_ENV`, so `nvm install 20` and `nvm use` work there directly, as in a Devin blueprint step: `nvm` loads on its first call, so a shell that never calls it pays nothing. The final-stage check runs as uid 10001 and fails the build unless every tool reports its pin, Java compiles and runs a class, cargo builds a crate offline, the homes are writable, nvm answers in all three kinds of shell, and a `gh/env.sh` beside `BEX_AGENT_STATUS_FILE` reaches `sh -ic`, `sh -lc`, `bash -c`, `bash -lc` and `bash -ic` while its absence leaves them without `GH_REPO`.

## Java tools on the full tier (w10/032)

A full-tier session reaches the internet only through the gateway's egress proxy, which bex-api names in `HTTPS_PROXY`. The JVM reads no such variable, and Maven's HTTP transport takes a proxy only from its settings, so bex-api also gives the proxy as JVM system properties in `BEX_AGENT_JAVA_PROXY_OPTIONS`: host, port, the session claim as user and password, `http.nonProxyHosts` (loopback and the gateway, as `NO_PROXY`), and an empty `jdk.http.auth.tunneling.disabledSchemes`, without which the JDK refuses Basic on a CONNECT.

- The JDK sends proxy credentials only through a `java.net.Authenticator`, which a plain `HttpURLConnection` or `java.net.http.HttpClient` does not install, so the driver serves a loopback relay for the sandbox's life (`driver/src/java-proxy.ts`, w10/038). It sends each CONNECT and plain-HTTP request on to the proxy with the session claim, and passes a tunnel's bytes untouched. The driver points its `BEX_AGENT_JAVA_PROXY_OPTIONS` at the relay (host and port only) before any tenant process runs, and writes the same value to `java/env.sh` beside `BEX_AGENT_STATUS_FILE` for terminals, so any JVM HTTP client that honours the standard proxy properties reaches the internet. A relay that fails to start, or an older image, leaves the gateway's properties.
- `bex-agent-tools.sh` reads `java/env.sh` and puts the properties in front of `JAVA_TOOL_OPTIONS` in every shell, once (replacing the gateway's there in a shell started before the relay), and the driver does the same for the agent's own process (`credentials.ts`). A value already there, such as a repository's own secret, stays after them, so its own properties win. Each JVM prints `Picked up JAVA_TOOL_OPTIONS`, as the JDK always does.
- `mavenrc` is `/etc/mavenrc`, which `bin/mvn` of every Maven 3 and 4, and an older wrapper's `mvnw`, sources before Java starts. It writes Maven global settings naming the proxy to `$TMPDIR/bex-maven-<uid>/settings.xml` on each run and passes them as `-gs` (`-is` on Maven 4, which renamed it), unless the command names its own. A repository's own user settings (`~/.m2/settings.xml`, or `-s` in `.mvn/maven.config`) merge over them, so its proxies, mirrors and servers win. They keep the HTTP blocker of Maven's stock global settings, which they stand in for.
- On `registries` and `custom` the variable is unset, so both do nothing: those tiers reach the Maven and Gradle hosts of the registry catalog directly.

The final-stage check proves the composition in every kind of shell, with and without the relay's `java/env.sh`, that the JVM takes the properties, and the settings `mavenrc` writes. The driver suite runs a JVM's `HttpURLConnection` and `java.net.http.HttpClient` through the relay where a JDK is installed.

## Credential and sandbox-lifetime contracts

`BEX_AGENT_REPO_URL` points at the gateway's Pod-bound Git smart-HTTP proxy. The gateway verifies the direct source Pod against immutable session/repository/branch labels, mints the repository-narrowed GitHub installation token internally, and injects it only on the TLS upstream hop. The sandbox never receives a raw token; receive-pack is parsed and rejected unless every update targets its exact `bex-agent/*` branch. The image contains no Git credential helper or credential cache.

Live turns are a second signed boundary. The driver receives only a derived Ed25519 public key and rejects `POST /turn` unless the gateway supplies a short-lived, session/action-bound, single-use grant after ticket redemption and fresh authorization. There is no raw `/acp` launcher route for same-Pod code to invoke.

The sandbox never holds a real model key. `BEX_AGENT_MODEL_API_KEY` is only the session-bound placeholder; the driver hands it to the ACP child under the adapter's native name next to the gateway model-proxy base URL, and the gateway swaps in the real key on its upstream hop (ADR062). There is therefore no credential scrub, Git-object scan or pre-snapshot hook. Nothing in the sandbox outlives it: there is no workspace snapshot or restore (ADR059 hibernation was retired on 2026-10-25). An idle session's sandbox is terminated after `BEX_AGENT_SANDBOX_IDLE_TTL` (2h), and the next message runs in a fresh sandbox that re-clones the session branch and is primed from the durable transcript (ADR047 D3).

## Warm Go dependency cache

The image carries a Go cache at `/opt/bex-go` (`GOMODCACHE=/opt/bex-go/mod`, `GOCACHE=/opt/bex-go/cache`) for sessions that build this repository, such as the scheduled `rt-*` routines (ADR105 § Until the AX42-1 arrives):

- `deploy.yml` writes `agent-image/go-deps.txt`, the third-party packages `go list -deps -test` finds over the four `lego/` modules in workspace mode. The Dockerfile's `go-deps` stage builds them, vets a throwaway package importing them to cache their vet facts, and drops the module zips. A build without the list, such as `scripts/dev-env.sh`'s, leaves the cache empty.
- The stage resolves the same workspace with the same Go as a session, at the same paths, so a session's build and vet with default flags reuse its entries: locally, `go build` over the four modules took 17 s instead of 29 s and `go vet` 10 s instead of 35 s, with nothing downloaded.
- Cached entries carry a far-future mtime, so Go neither trims them nor rewrites their mtime on use (which would copy each used file into the sandbox's writable layer).
- `/opt/bex-go` is a linked layer (`COPY --link`), independent of the layers above it, and the registry build cache serves its stage, so it changes, and a node pulls it again, only when the dependency list does. `AGENT_REBUILD` rebuilds the other layers on each deploy, so apt packages refresh. The Trivy gate and the SBOM skip `/opt/bex-go`: it is build input for sessions, not software the image runs.
- About 3.4 GB uncompressed (1.2 GB of modules, 2.2 GB of build output). A session that builds a different repository is unaffected; writes go to the session's own layer as before.

BEX_LIVE_VERIFY=1 BEX_VERIFY_AGENT_DRIVER=1 \
