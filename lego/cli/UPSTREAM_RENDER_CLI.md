# Upstream Render CLI pin

`bex` deliberately imports the upstream command package rather than copying or forking it.

- **Render release:** `v2.27.0`
- **Upstream commit:** `a764810a768202704e7206eb7b87a47211fcd98e`
- **Go module version:** `v1.1.3-0.20260909214233-a764810a7682`

The upstream repository's v2 tags are not valid Go-module major-version tags because its module path has no `/v2` suffix. Go therefore records the exact release commit as a pseudo-version in `go.mod`.

**Go toolchain:** v2.26.0 upgraded upstream to Go 1.27 (`85c8c2c`); v2.27.0 stays on Go 1.27, so `lego/cli/go.mod` and the shared `lego/go.work` remain at `go 1.27.0`. The three platform modules (`types`/`operator`/`backend`) and the shipped image stay on the 1.26 line (the Docker build has no workspace file). The CI jobs that build the workspace derive their Go version from `lego/cli/go.mod`, so they follow this bump automatically; `GOWORK=off` jobs (operator/backend/govulncheck) are unaffected. See [lego/AGENTS.md](../AGENTS.md).

## Updating the pin

1. Choose an upstream release and pin its exact commit with `go get github.com/render-oss/cli@<commit>` from this directory.
2. Update all three values above and review the upstream command/API changes. Confirm the upstream `cmd` package still exports `RootCmd` (Bex-native commands attach to it in `main.go`) and that no new upstream command collides with a Bex-native command name (`code`, `glm`, `muse`, `kimi`, `deepseek`, `upgrade`).
3. Check the update-check seams. `bex` intercepts the root `--version`/`-v` path in `main.go` (mirroring upstream's unexported `isRootVersionRequest` — re-diff that function on every pin bump) because upstream's handler compares against render-oss/cli releases behind the const `cfg.RepoURL`. A **second call site** in `pkg/tui/views/login.go` cannot be intercepted: once upstream releases something newer than this pin, `bex login`'s TUI shows a Render upgrade banner. Mitigation is bumping this pin promptly. (If upstream ever makes `RepoURL`/`InstallationInstructionsURL` vars, add the two `-X` repoints to `scripts/bex-cli-build.sh`; a PR proposing that was opened and then withdrawn by user decision 2026-08-15 — do not reopen without an explicit user decision.)
4. Re-diff the branding overlay (`lego/cli/internal/branding`). Confirm `cmd.CustomHelpTemplate` still contains `(eq .CommandPath "render")` (or update the string replace), `cliVersion` is still a cobra template func we can override, `docs` is still a root command we can retarget, and `SetupCommands` still late-adds commands so the HelpFunc **and UsageFunc** re-walks remain necessary (flag/arg errors call UsageFunc, not HelpFunc — do not hang branding on `SetFlagErrorFunc`, which upstream's `observeCobraValidationAndHelp` replaces without delegating). Spot-check `bex --help`, `bex workspace set --help`, datastore command/flag help (including `pg`/`kv` aliases), `bex blueprints validate --help` (`render.yaml` and `bex.yml` must stay intact), and error-path usage for a late-added command (`bex services update --bogus-xyz`, `bex logs --bogus-xyz`, `bex keyvalues create --bogus-xyz`, `bex workflows list --bogus-xyz` — stderr must not contain a bare `render ` command line). The workspace-set help override must match the bridge configuration precedence (`BEX_CLI_CONFIG_{DIR,PATH}` plus explicit `RENDER_CLI_CONFIG_{PATH,DIR}`; empty = unset); flag usage and single-quoted workspace command references must remain Bex-branded.
5. **Re-diff the wire transport, not only the help tree.** A pin bump can change how a command talks to bex behind an unchanged `--help` surface: the v2.24.0 bump (w2/m79) moved `ea sandboxes exec` from a single `POST /sandboxes/{id}/exec` to a connect-token handshake (`POST /sandboxes/{id}/runs/{operation}/token`, then a Bearer redeem at the returned `uri`), and two help-graded re-baselines (v2.26.0, v2.27.0) did not notice (w7/m147). On every bump: diff `pkg/sandbox/repo.go` (connect/exec/file handshakes), the operation paths in `pkg/client/client_gen.go` (`grep -n operationPath`), and the SSE structs in `pkg/sandbox/sse.go` (`execExitEvent`/`execErrorEvent` JSON tags) against `lego/cli/testdata/sandbox-exec-contract.json`; `go test -run PinnedSandboxExec .` drives the pinned client against that contract and fails on a transport change until the contract and bex-api move together (`lego/backend/internal/sandbox/connect_test.go` proves the server side of the same file).
6. Re-diff the telemetry sender seam (`pkg/analytics` + `internal/analyticsnotice`): the sender POSTs `CreateCliTelemetryEvent` to `<api-base>/cli-telemetry-events`, which bex-api implements (w5/m92) — confirm the endpoint path, the `CliTelemetryEventPOSTInput` field set (new fields must be accepted server-side; check `telemetryEventRequest`), the consent inputs (`RENDER_CLI_DISABLE_ANALYTICS`, `DO_NOT_TRACK`), and that the one-time notice marker path is `config.StateDir()/analytics/notice-shown`. In `bex` that is `$HOME/.bex/state` by default (`RENDER_CLI_CONFIG_DIR` mapped from `BEX_CLI_CONFIG_DIR` / `$HOME/.bex`, w8/018) — not `~/.render`. Record any schema delta in `docs/cli-compatibility-checklist.md`.
7. Run `bash scripts/bex-cli-validate.sh`, `cd lego/cli && go test ./...`, and the live device-flow check in `scripts/bex-cli-auth-e2e.sh` when Bex auth infrastructure is available.
8. Update `docs/cli-compatibility-checklist.md` with supported-version and compatibility evidence or an explicit Bex server-side limitation. **Re-diff `ea` subcommand names**, not only whether the group is present: `bex ea --help` must list the current `Use:` strings (`sandboxes`, `sandbox-groups`, `objects` at v2.27.0). A rename with no alias (`sandbox` → `sandboxes`) slipped through the v2.24.0, v2.26.0, and v2.27.0 re-baselines because they graded new commands and Bex-native collisions only (`w8/016`). Re-check the pin-conditional rows: `skills` non-TTY panic, `logs` unauthenticated panic, service-disks command/flag.

The CI validation compares this record to `go.mod`; an unnoticed dependency bump cannot pass the launcher test workflow.
