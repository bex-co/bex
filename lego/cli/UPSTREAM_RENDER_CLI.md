# Upstream Render CLI pin

`bex` deliberately imports the upstream command package rather than copying or forking it.

- **Render release:** `v2.38.0`
- **Upstream commit:** `09b7802aa379c92a087884412d88b2b3f8a75a9a`
- **Go module version:** `v1.1.3-0.20261120013850-09b7802aa379`

The upstream repository's v2 tags are not valid Go-module major-version tags because its module path has no `/v2` suffix. Go therefore records the exact release commit as a pseudo-version in `go.mod`.

**Go toolchain:** v2.26.0 upgraded upstream to Go 1.27 (`85c8c2c`); v2.29.0 required Go 1.27.2 and v2.32.0 moved upstream to Go 1.27.3 and v2.37.0 to Go 1.27.4 (v2.38.0 kept it), so `lego/cli/go.mod` and the shared `lego/go.work` are at `go 1.27.4`. The three platform modules (`types`/`operator`/`backend`) and the shipped image stay on the 1.26 line (the Docker build has no workspace file). The CI jobs that build the workspace derive their Go version from `lego/cli/go.mod`, so they follow this bump automatically; `GOWORK=off` jobs (operator/backend/govulncheck) are unaffected. See [lego/AGENTS.md](../AGENTS.md).

## Updating the pin

1. Choose an upstream release and pin its exact commit with `go get github.com/render-oss/cli@<commit>` from this directory.
2. Update all three values above and review the upstream command/API changes. Confirm the upstream `cmd` package still exports `RootCmd` (Bex-native commands attach to it in `main.go`) and that no new upstream command collides with a Bex-native command name (`code`, `glm`, `muse`, `kimi`, `deepseek`, `upgrade`, `edit`; `skills` is a deliberate replacement).
3. Check the update-check seams. `bex` intercepts the root `--version`/`-v` path in `main.go` (mirroring upstream's unexported `isRootVersionRequest` — re-diff that function on every pin bump) because upstream's handler compares against render-oss/cli releases behind the const `cfg.RepoURL`. A **second call site** in `pkg/tui/views/login.go` (the banner after `bex login`) is suppressed in `internal/bridge/transport.go`: the launcher's default-transport wrapper answers upstream's `cfg.RepoURL + "/releases/latest"` request with a local 404, so login never advertises a Render CLI release (`TestUpstreamReleaseCheckNeverAdvertisesRenderCLI`); `main.go` prints bex's own release hint in its place (`TestBexLoginReportsBexReleaseNotRenderCLI`). Re-check that the version client still uses `http.Get` and the same path on every pin bump. Since v2.38.0 the login banner is gone, and a **third call site** prints after any command: `internal/updatenotice`, started in `cmd.Execute`, once a day tells a person at a terminal, or an AI agent in one line, "Update available: v<pin> → v<latest>. To upgrade, see: https://render.com/docs/cli…". It reads a cache at `config.StateDir()/update-check.json` (`~/.bex/state/` by default, or a state directory shared with Render's own CLI through an explicit `RENDER_CLI_CONFIG_DIR`) and prints a cached newer release without any request, so the transport refusal alone does not stop it. `bridge.Apply` therefore always sets its off switch, `RENDER_CLI_DISABLE_UPDATE_NOTIFIER=1`, which `updatenotice.Start` reads before the cache or the network; the transport refusal stays the second guard for its lookup (`internal/updatenotice/release.go`, an `http.Client` with no transport of its own). `TestUpstreamUpdateNoticeNeverPrints` drives the binary as an agent with no cache, a fresh cache and a stale cache naming a newer release, and fails if any notice prints or the cache is written; `TestApplyAlwaysTurnsUpstreamsUpdateNoticeOff` pins the switch. On every pin bump re-check that `Start` still reads `cfg.UpdateNotifierDisabled()` first, and grep `cmd/` for any other caller of `updatenotice` or `cfg.RepoURL`. bex's own post-command hint (`internal/update`) is unaffected: it reads `BEX_NO_UPDATE_NOTIFIER`. (If upstream ever makes `RepoURL`/`InstallationInstructionsURL` vars, add the two `-X` repoints to `scripts/bex-cli-build.sh`; a PR proposing that was opened and then withdrawn by user decision 2026-08-15 — do not reopen without an explicit user decision.)
4. Re-diff the branding overlay (`lego/cli/internal/branding`). Confirm `cmd.CustomHelpTemplate` still contains `(eq .CommandPath "render")` and `{{if .Runnable}} [subcommand]` (or update the string replaces; the second keeps a bex-native group, which `usage.Guard` makes runnable so it can refuse an unknown word, at `<subcommand>`, and `TestBexNativeGroupsWithoutAWordAreUnchanged` fails when it no longer applies), `cliVersion` is still a cobra template func we can override, `docs` is still a root command we can retarget, and `SetupCommands` still late-adds commands so the HelpFunc **and UsageFunc** re-walks and the launcher's `cobra.OnInitialize` `branding.Refresh` remain necessary (shell completion serializes `Short` without calling either wrapper; Execute must still register those children before cobra runs initializers, w2/043) (flag/arg errors call UsageFunc, not HelpFunc — do not hang branding on `SetFlagErrorFunc`, which upstream's `observeCobraValidationAndHelp` replaces without delegating). Spot-check `bex __complete pg ""` (Bex descriptions), `bex --help`, `bex workspace set --help`, datastore command/flag help (including `pg`/`kv` aliases), `bex blueprints validate --help` (`render.yaml` and `bex.yml` must stay intact), and error-path usage for a late-added command (`bex services update --bogus-xyz`, `bex logs --bogus-xyz`, `bex keyvalues create --bogus-xyz`, `bex workflows list --bogus-xyz`, `bex sandboxes create --bogus-xyz`, `bex sandbox-groups images import --bogus-xyz`, `bex ea blueprints create --bogus-xyz` — stderr must not contain a bare `render ` command line). Grep the help of new commands for upstream state paths (`~/.render/state/`), `RENDER_CLI_CONFIG_DIR` advice and mid-line `| render ` examples (v2.35.0 `ea blueprints`, v2.34.0 `sandbox-groups images`). Also grep it for `render.com/docs` links: a served command's link needs its Bex page in `branding.helpDocsLinks` (v2.35.0 `ssh` and `ea blueprints`, w32/008), and `TestNoHelpLinksRenderDocs` walks every help page and fails on a new one. The workspace-set help override must match the bridge configuration precedence (`BEX_CLI_CONFIG_{DIR,PATH}` plus explicit `RENDER_CLI_CONFIG_{PATH,DIR}`; empty = unset); flag usage and single-quoted workspace command references must remain Bex-branded. Then re-check the run-time copy seam (`brandRuntimeOutput`, checklist below this list).
5. **Re-diff the wire transport, not only the help tree.** A pin bump can change how a command talks to bex behind an unchanged `--help` surface: the v2.24.0 bump (w2/m79) moved `ea sandboxes exec` (top-level `sandboxes exec` since v2.32.0) from a single `POST /sandboxes/{id}/exec` to a connect-token handshake (`POST /sandboxes/{id}/runs/{operation}/token`, then a Bearer redeem at the returned `uri`), and two help-graded re-baselines (v2.26.0, v2.27.0) did not notice (w7/m147). The v2.37.0 bump (w22/m444) stopped sending `{command}` with that mint, so the token takes the command its redeem names (`connect.requestBody` in the contract is empty). The v2.38.0 bump (w22/m604) added the sandbox-group environment commands and parses `POST /environments/{id}/resources` as a 201 with the environment: the `environment` section of `lego/cli/testdata/sandbox-groups-contract.json` records every request `sandbox-groups create --environment`, `environment set` (by id and by name) and `environment remove` send, `go test -run PinnedSandboxGroupEnvironment .` drives the pinned client against it, and `lego/backend/internal/sandbox/group_environment_cli_contract_test.go` replays it against bex-api. A 429 now prints the API's message (`too many requests: <message>`, `TestPinnedClientPrintsBexTooManyRequestsMessages`), so a bex 429 message must read well on its own and name no code. On every bump: diff `pkg/sandbox/repo.go` (connect/exec/file handshakes), the operation paths in `pkg/client/client_gen.go` (`grep -n operationPath`), and the SSE structs in `pkg/sandbox/sse.go` (`execExitEvent`/`execErrorEvent` JSON tags) against `lego/cli/testdata/sandbox-exec-contract.json`; `go test -run PinnedSandboxExec .` drives the pinned client against that contract and fails on a transport change until the contract and bex-api move together (`lego/backend/internal/sandbox/connect_test.go` proves the server side of the same file).
6. Re-diff the telemetry sender seam (`pkg/analytics` + `internal/analyticsnotice`): the sender POSTs `CreateCliTelemetryEvent` to `<api-base>/cli-telemetry-events`, which bex-api implements (w5/m92) — confirm the endpoint path, the `CliTelemetryEventPOSTInput` field set (new fields must be accepted server-side; check `telemetryEventRequest`), the consent inputs (`RENDER_CLI_DISABLE_ANALYTICS`, `DO_NOT_TRACK`), and that the one-time notice marker path is `config.StateDir()/analytics/notice-shown`. In `bex` that is `$HOME/.bex/state` by default (`RENDER_CLI_CONFIG_DIR` mapped from `BEX_CLI_CONFIG_DIR` / `$HOME/.bex`, w8/018) — not `~/.render`. Record any schema delta in `docs/cli-compatibility-checklist.md`. The Bex disclosure (`internal/disclosure`, ADR113 D5) stands on five more upstream facts; re-check each: upstream prints nothing when `notice-shown` exists (`analyticsnotice.ShowIfNeeded`); `notice` is still a child of the hidden `analytics` group, which `setupCommands` adds only after the API client is built; that group still carries the `render.analytics.notice.eligibility: ineligible` annotation; `analytics.New` still reads consent once, inside `setupCommands`, before Cobra's initializers run; and the send subprocess is still marked by `analytics.IsSendSubprocess`. `go test -run 'Disclos|Notice|Undisclosed|CIBypasses|FirstTerminal|Completion|Formula' .` fails when one of them moves.
7. Re-diff `pkg/skills` and `cmd/skills*.go`: the launcher replaces the `skills` tree (`internal/skills`, w8/m143) but calls upstream's installer helpers. Confirm `InstallSelectedSkills` still removes only the selected directories for a non-empty selection, and `TestCommandSurfaceMatchesUpstream` still passes for new flags. Separately, re-pin the skills pack when `render-oss/skills` changes: bump `packgen.UpstreamCommit`, run `hack/sync-skills.sh`, and review the diff and any failing patch.
8. Run `bash scripts/bex-cli-validate.sh`, `cd lego/cli && go test ./...`, and the live device-flow check in `scripts/bex-cli-auth-e2e.sh` when Bex auth infrastructure is available.
9. Update `docs/cli-compatibility-checklist.md` with supported-version and compatibility evidence or an explicit Bex server-side limitation. **Re-diff `ea` subcommand names**, not only whether the group is present: `bex ea --help` must list the current `Use:` strings (`blueprints`, `objects` at v2.35.0; `sandboxes`/`sandbox-groups` left `ea` for the root at v2.32.0 with no alias). A rename with no alias (`sandbox` → `sandboxes`) slipped through the v2.24.0, v2.26.0, and v2.27.0 re-baselines because they graded new commands and Bex-native collisions only (`w8/016`). Re-check the pin-conditional rows: `skills` non-TTY panic, `logs` unauthenticated panic, `restart <dpg-id>` Postgres HTTP-error swallowing (`bex restart dpg-00000000000000000000 --confirm -o json`), service-disks command/flag.

The CI validation compares this record to `go.mod`; an unnoticed dependency bump cannot pass the launcher test workflow.

Run-time command references (`render <command>` → `bex <command>`, w2/m263 D4=A) are branded by `branding.brandRuntimeOutput` (`internal/branding/runtime.go`), which wraps every command's `RunE` without touching its body. On every pin bump:

- Regenerate the run-time inventory with the grep in [docs/bex-cli.md § Compatibility and branding limits](../../docs/bex-cli.md#compatibility-and-branding-limits). Check that each hit is a returned error (rewritten for every command), printed by a command listed in `runtimeStdout`, or recorded there as a residual. When a new command prints a next step to stdout, add it to `runtimeStdout` with a test.
- Re-diff `pkg/blueprint/output.go` and `pkg/text/blueprint.go`. The next step must still be `meta.next` in JSON/YAML and the single line after the text `Next:` title. Re-diff `pkg/command/wrapper.go` `PrintData`: each format must still be written in one `Write`, and YAML through `yaml.v3` `Marshal` at indent 4.
- Confirm cobra still prints a `RunE` error with `err.Error()`, and that upstream classifies exit codes with `errors.As` (`cmd/execution.go`), which `brandedError.Unwrap` preserves.
- Re-diff the product-name phrases of `runtimeProse` against `cmd/logout.go` and `pkg/blueprint/output.go` (w2/073, w2/082). A reworded phrase stops matching without an error; `TestBexBinaryDeviceLoginRefreshAndLogoutStayInBexConfig`, `TestLogoutRevokeFailureNamesBex` and `TestBlueprintApproveNextStepNamesBex` fail when one does. Confirm the interactive `postgres create` wizard still draws its success screen (`pkg/tui/views/pgcreate.go`) through the command's stdout, which `wizardOutput` and `keepTerminal` wrap.
- Re-run the variable grep in the same section. A run-time message that names a variable the bridge fills (`RENDER_API_KEY`, `RENDER_OUTPUT`) needs its exact phrase in `branding.NameBexInputs` (w32/009). Confirm `setupRootCmdPersistentRun` still installs the root `PersistentPreRunE` during Execute and that it still prints the `RENDER_OUTPUT` error itself through `cmd.ErrOrStderr()`: `brandPreRunOutput` wraps that hook from `branding.Refresh`.
- Run `go test -run 'TestBlueprintNextStepsNameBex|TestWorkspaceCurrentWithoutWorkspaceNamesBex|TestLogoutNamesTheVariableTheUserSet|TestBadOutputVariableIsNamedAsSet' .` and `go test ./internal/branding/`.

The explicit `login` command's runtime prompt is branded through its Cobra stdout writer (`branding.brandLoginOutput`). Re-check that `views.NonInteractiveLogin` still writes the complete fixed prompt through one `command.Println` call, and run `TestBexLoginReportsBexReleaseNotRenderCLI` to preserve the device URL/code while changing only that prefix. The separate automatic `LoginView` used inside other interactive commands remains an upstream runtime-copy residual.
