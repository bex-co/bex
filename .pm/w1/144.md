# Roll every node onto the CVE-2026-98432-fixed kernel 6.8.0-149 once it reaches noble-security

Why: the 2026-11-02 roll moved the fleet only to 6.8.0-147, which does not fix CVE-2026-98432 (IPv4 TCP use-after-free), and unprivileged tenant code can reach the vulnerable path from inside the cluster.

## State (2026-11-04)

- Every node runs `6.8.0-147-generic` (rolled from `6.8.0-117` on 2026-11-02). The bake runs `apt-get full-upgrade` and fails unless the newest kernel equals `kernel_version` in `infra/packer/bex-worker.pkr.hcl`. Commits `0688d26b5`, `4aafb11a8` and `dbf144584` predate the 2026-11-04 rewrite and are cited as text only.
- Platform Go services build with `godebug multipathtcp=0` (`lego/go.work`, `lego/operator/go.mod`, `lego/backend/go.mod`), which closes the MPTCP listener the claimed exploit chain uses.
- [Ubuntu](https://ubuntu.com/security/CVE-2026-98432) lists noble `linux` as "Vulnerable, work in progress in 6.8.0-149.149". 149 has been in noble-proposed since 2026-10-26.

## Why it stays urgent

Verified 2026-11-04 on a linuxkit 7.0.12 test kernel. An unprivileged process (uid 65534, `CapEff: 0`, no-new-privileges) can `setsockopt(IP_OPTIONS)` record-route and `connect()`. The accepted child socket's `getsockopt(IP_OPTIONS)` returned `070b0c7f0000017f00000100`, so the SYN's options reached the vulnerable `ireq_opt` path. Any tenant workload can reach the bug from inside the cluster, and no network filter blocks that.

## Steps

1. When the Ubuntu page shows noble `linux` **Released**, set `kernel_version = "6.8.0-149"` in `infra/packer/bex-worker.pkr.hcl` and dispatch `snapshot.yml`.
2. Canary: patch `rollout.after` on `bex-tenant-0` only. Confirm a replacement node reports `6.8.0-149-generic` and goes Ready.
3. Bump `rolloutAfter` on every MachineDeployment and on the KubeadmControlPlane in `infra/clusterapi/overlays/hetzner-caph/cluster.yaml`. Keep tenant-0's canary timestamp. Patch the out-of-band sandbox pool live and record it in `sandbox-pool.yaml`.
4. After every platform node, unseal the rescheduled OpenBao member per [ADR015 § Node drain and rolling-maintenance unseal](../../docs/ADR015-openbao-backup-restore.md#node-drain-and-rolling-maintenance-unseal) (`scripts/bao-init.sh`). Otherwise the PDB stalls the drain.
5. tenant-lg (`cx43`) may hit fsn1 `resource_unavailable`. Delete the failed Machine to retry.
6. After the roll, consider removing `godebug multipathtcp=0`.

## Done when

Every node reports `6.8.0-149-generic`, all three OpenBao members are unsealed with three raft voters, and `app-cluster.yml` is green.
