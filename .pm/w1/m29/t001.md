## Objective

Design a component that reads a Postgres client's cleartext `SSLRequest` preamble (the pre-TLS-handshake byte sequence older/default-mode clients send) and extracts routing information so the request can still reach the correct CNPG cluster before Traefik's TCP/SNI layer takes over — the fix `docs/ADR009-postgresql-management.md:53` names but leaves unbuilt.

## Context

- `docs/ADR009-postgresql-management.md:53` — the existing gap description and named fix approach (`pg_sni_proxy`-style).
- Traefik's current TCP/SNI routing for external managed-Postgres (find the relevant `deploy/gitops/` chart/config — likely wherever the DB TCP routes are defined, per `BEX_DB_DOMAIN`).
- PG's wire protocol: a client that doesn't set `sslnegotiation=direct` sends a plaintext `SSLRequest` message first, expects an `S`/`N` response, *then* starts the TLS handshake (which is when SNI becomes visible) — this is why Traefik's SNI-based routing can't see it: SNI only exists once TLS actually starts, and by then the routing decision needs to already be made, or the proxy needs to speak enough of the preamble to extract a routing hint (e.g. from the initial connection's source port mapping, or a proxy protocol / startup-packet inspection approach — pg_sni_proxy specifically works around this by injecting a fake SNI based on config).

## Steps

1. Research `pg_sni_proxy` (or equivalent prior art) and how it solves the preamble-vs-SNI ordering problem.
2. Decide the routing-key mechanism this proxy will use to know which CNPG cluster a given connection targets, given SNI isn't available yet at the point routing must be decided (e.g. per-Database a distinct external port, or a proxy that terminates the preamble handshake itself and re-multiplexes to Traefik with proper SNI once TLS starts).
3. Document the chosen design and how it composes with the existing direct-TLS (SNI-based) path — both must keep working.
