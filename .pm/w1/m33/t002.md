## Objective

When `App.Spec.PreDeployCommand` is set, run it to completion against the new revision's image before the Deployment rolls forward; a non-zero exit fails the deploy and leaves the previous revision serving.

## Context

- `lego/operator/internal/controller/app_controller.go` reconciles Deployments from App CRs; deploy/revision generation tracking already exists (build Jobs are named `bld-<name>-gen-<generation>`, per root `CLAUDE.md`'s `BEX_BUILD_NAMESPACE` entry).
- This is real health-gating semantics, not a cosmetic field — the rollout must actually wait on this step, mirroring how the existing health-check gate blocks a revision from becoming ready (`docs/ADR004-deployment.md`).

## Steps

1. Before rolling the Deployment to the new revision's image, run `PreDeployCommand` as a Job (name convention `predeploy-<name>-gen-<generation>`) using the new image, with the App's runtime env vars available (migrations typically need DB connection env).
2. Block the rollout until the Job completes; on success proceed to the normal Deployment update; on failure, mark the deploy failed and do not touch the running Deployment (old revision keeps serving).
3. Handle timeouts (a hung migration shouldn't block forever — apply a bounded deadline, matching the existing build-Job timeout pattern if one exists).

## Files

- `lego/operator/internal/controller/app_controller.go`
- `lego/operator/internal/build/` (if the Job-dispatch helper is reusable)

## Acceptance criteria

- [ ] A successful `PreDeployCommand` gates the rollout, then the new revision serves.
- [ ] A failing `PreDeployCommand` fails the deploy; the old revision is untouched and keeps serving.
- [ ] Unset `PreDeployCommand` behaves exactly as today (no gating step, byte-identical).
- [ ] envtest coverage for both success and failure paths.

## Out of scope

- Surfacing status/logs on the deploy record (t003) — this task only needs the gating mechanism to work.
