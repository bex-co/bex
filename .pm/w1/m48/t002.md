## Objective

`internal/logs` reads that ask for `type=build` (alone or via all-types) merge deterministic, synthesized platform lines derived from the deploy rows overlapping the query window — so REST/GraphQL/MCP all return them through the one core verb with zero adapter work.

## Context

- `lego/backend/internal/logs/service.go` — QueryLogs/Logs route to Loki (`History`) or pod-log fallback; synthesis is an additive merge either way and must NOT change the `buildStoreUnavailable` (503) contract when Loki is absent and `type=build` history is requested — decide and pin whether a storeless `type=build` read returns synthesized lines alongside the named error or keeps the 503 (t001's design note; don't silently relabel an error as success, per the deploy-log-panel's honesty rules).
- Deploy rows come from the control-plane store (`internal/deploys` / `internal/store`); logs currently has no store dependency — inject a narrow source (function field, like `History`) rather than importing the feature package, mirroring `PodLogSource`.
- Deterministic ids (deploy id + phase) so history/tail dedupe holds.

## Steps

1. Add a `DeployPhaseSource`-style injected reader (deploy rows for an App within a window); nil ⇒ no synthesis (byte-identical today).
2. Synthesize entries per t001's mapping; merge + sort into windowed results, capped by `limit` like any other line.
3. Wire the source in `internal/api` composition when the control-plane store is configured.

## Files

- `lego/backend/internal/logs/service.go` (+ a small `progress.go` if cleaner)
- `lego/backend/internal/api/server.go` (wiring)

## Acceptance criteria

- [ ] `GET /v1/logs?type=build` over a deploy's window returns the synthesized lines interleaved with real build lines, identical via GraphQL `logs` and MCP `list_logs`.
- [ ] Storeless (`BEX_CP_DB_URI` unset) and Loki-less behavior is explicitly pinned by test — no accidental contract change.
