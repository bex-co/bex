# bex-api never exits on SIGTERM — it serves for the full grace period with a cancelled context

`lego/backend/cmd/api/main.go:77` installs controller-runtime's signal handler (`ctx := ctrl.SetupSignalHandler()`), which **catches** SIGTERM/SIGINT and cancels `ctx` — but main's last statement is `log.Fatal(httpSrv.ListenAndServe())` (line ~393), which never returns on a signal. So the first SIGTERM does not terminate the process. It:

1. cancels the context every background loop hangs off — the apps-rows→CR projector, the usage compaction loop, the audit retention sweep, the control-plane internal API — so they all stop; while
2. leaving the public HTTP server listening and answering.

In Kubernetes that is the whole `terminationGracePeriodSeconds` (default 30s) during which a **terminating pod still takes traffic with its control plane already shut down**, followed by a SIGKILL — so every rollout both drags and drops in-flight requests, and requests routed to the pod in that window can hit a cancelled store context. Discovered while writing `scripts/events-verify.sh` (w3/m7): stopping the host bex-api needed a SIGKILL backstop, which is what exposed it.

Fix shape: stop blocking on `ListenAndServe`; serve in a goroutine, `<-ctx.Done()`, then `httpSrv.Shutdown(timeoutCtx)` (and the same for the `BEX_CP_ADDR` server, which already has an `ErrServerClosed` check implying that was the intent). Small, but it touches the process lifecycle and deserves its own change plus a test that a SIGTERM'd binary exits — hence a note, not a drive-by fix inside an unrelated milestone.

Source: found by w3/m7's E2E (`scripts/events-verify.sh`), 2026-07-12.
