## Objective

The bulk patch has been unguarded since the quota landed (2026-08-17), so production may already hold over-quota maps. Count them before t001 makes them un-editable in surprising ways (a later in-quota edit to an over-quota map will be refused).

## Steps

1. With operator access, measure every service's env and file map (key count and `mapBytes`) through the secrets store or the projected Secrets. **Read only.**
2. Record the counts (not values) in the m147 README Evidence section: how many are over 500 entries or 512 KiB, and whether any projected Secret is near or over 1 MiB.
3. Decide how t001's refusal treats an already-over-quota map. Options: refuse only writes that grow it; allow shrinking writes, which is the recommended shape and matches "deleting frees room" in ADR066 #6; or refuse everything. Implement the chosen rule in t001's tests if it differs from t001's default.

## Acceptance criteria

- [x] The counts are recorded, or the sweep is recorded as not possible with the reason.
- [x] The rule for existing over-quota maps is decided and covered by a test (a shrinking write to an over-quota map succeeds, if that rule is chosen).

## Result (2026-09-15)

- **Sweep: not possible from this environment.** Measuring every service's maps needs read access to production OpenBao or `kubectl get secrets` on the app cluster. Neither is available to this worker: no production kubeconfig, and the QA user can reveal only its own workspace's values. The one known over-quota map is the milestone's own fixture, which was deleted at filing. So the count of pre-existing over-quota maps in other workspaces is **unknown**, and an operator with cluster access should run it before relying on "none".
- **Rule: grow refused, shrink allowed** (`patchWithinQuota`, `secrets/batch.go`). A patch whose resulting map is over quota is refused only if it adds entries or bytes. A delete, or an edit that doesn't grow the map, succeeds, which matches ADR066 #6's "deleting frees room". So a service that already has an over-quota map from before w1/m147 is never stuck: it can always get back under. Tests in `TestPatchEnvironmentOnAnAlreadyOverQuotaMap` (`secrets/batch_quota_test.go`) cover deleting an entry, a same-size edit, and adding an entry (refused, store unchanged). The dashboard mirrors the rule: saved opaque rows are never flagged.

## Out of scope

- Modifying any tenant's map.
