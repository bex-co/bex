## Objective

Keeping idle streams open changes what the capacity guards and security rules see. Settle each change explicitly.

## Context

- Caps: `lego/backend/internal/logs/service.go:174-181` (`MaxSSEConns`, `MaxSSEConnsPerSubject`, `MaxSSEConnsPerWorkspace`), enforced at `rest.go:218-256`; env defaults in `lego/backend/CLAUDE.md` (`…_SSE_CONNS`).
- No-producer rule (codex #3): `service.go:836-844`, plus `liveSubscribable` in `logsSubscribe` (`rest.go:139-`).
- Watchdog: `service.go:823-832` (`withRevalidation` → `revalidateTailTarget`).
- Edge: `api.bex.co` sits behind Cloudflare.

## Steps

1. Measure: with the per-subject cap at its production value, open N Logs tabs on idle services, and record the tab at which `log subscription capacity reached` appears. Decide whether that is acceptable (Render-like), or whether idle streams should count differently. Record the decision in `docs/ADR006-bex-api.md` or the logs ADR.
2. Confirm `type=predeploy` (and any other producer-less type) is still refused before a slot is taken, and add a test that distinguishes "no producer type" from "zero pods right now".
3. Confirm the watchdog cancels an idle stream on revocation and on App deletion (test with a fake checker and a deleted CR).
4. Measure the edge's idle-stream cutoff (an SSE fetch with the heartbeat disabled on `dev-1`, or from Cloudflare docs for the plan in use) and set the heartbeat interval with margin.

## Acceptance criteria

- [ ] The cap decision is recorded with the measured tab count.
- [x] Tests: the no-producer refusal still takes no slot; revocation and deletion end an idle stream.
- [x] The heartbeat interval is justified by a measured or documented edge limit.

## Progress (2026-09-15)

- **Cap decision: recorded, live measurement pending.** It is written up in `docs/ADR006-bex-api.md` § Request caps. The production caps are the code defaults (`cmd/api/config.go:535-537`; no override in `deploy/`): 100 global, 5 per subject and 20 per workspace. An idle tail holds a slot exactly as a running service's tail always did. A sixth concurrent tail for one subject gets `429 too many active log subscriptions`, and idle tails are not counted differently. The measured tab count on production is still to be recorded after deploy (open six SSE subscribes as the QA user and record which one gets the 429).
- **No-producer rule: `TestAppTailStillRefusesAQueryWithNoLiveProducer`.** `type=predeploy` returns `ErrBadRequest` immediately instead of parking. `liveSubscribable` still rejects it before `acquireSubscription` in `logsSubscribe`. "Zero pods right now" is the separate open-stream case covered by the t001 tests.
- **Watchdog: `TestIdleTailStillEndsOnRevocationAndDeletion`.** A zero-pod SSE tail ends on a fresh deny and on App deletion, and releases its slot.
- **Edge: documented, not measured.** Cloudflare's proxy read timeout, 100 s, is documented, and `api.bex.co` is Cloudflare-proxied. No `dev-1` exists to measure against, since the local cluster is down. `DefaultTailHeartbeatInterval` is therefore 25 s, a 4× margin.
