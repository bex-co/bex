# 092 — Changing a linked environment group redeploys a service whose auto-deploy is off; Render deploys only linked services with auto-deploy enabled

Why: owners turn auto-deploy off precisely so that nothing ships without them. Today any Render-shaped env-group write (a variable, a secret file, a link or unlink) opens a new release on every linked service anyway.

- **Severity:** major. A release the owner opted out of happens with no warning. The dashboard's own group editor asks for a save mode, but the REST verbs Render clients use never do.
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 14 (environment groups journey). Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`. Fixtures (created and deleted inside the run): web service `qa-20260914-env` (`srv-dak0bhogsm7s73f64hkg`, `examples/hello-go`, which answers `GET /` with `$MESSAGE`) linked to group `qa-20260914-eg-a` (`evg-dak0cqogsm7s73f64hm0`, `MESSAGE=from-group-a`).

The group's own page states the behavior unconditionally: "Linking or unlinking redeploys the affected service."

## Root cause

- **Hard-coded deploy mode.** Every Render-shaped group write passes `SaveMode: SaveModeDeploy`:
  - `SetEnvGroupVars` `lego/backend/internal/envgroups/service.go:884`
  - `SetEnvGroupVarInput` `:936-939`
  - `DeleteEnvGroupVar` `:960-962`
  - `SetEnvGroupFile` `:979-981`
  - `DeleteEnvGroupFile` `:1003`
  - `ApplyEnvGroup` `:1372`
- **The rollout ignores auto-deploy.** `patchEnvironmentAuthorized` then rolls **every** linked service (`lego/backend/internal/envgroups/patch.go:282-306` → `rollOne` → `rollLinkedService`, `service.go:1114-1119`).
- **Link paths roll too.** Link (`linkFetched`, `service.go:1082-1086`), unlink (`detachFetched`, `:1176-1180`) and create-with-services (`persistCreate`, `:659-665`) roll the service directly.
- **No check anywhere.** `grep -rni autodeploy lego/backend/internal/envgroups` (non-test) returns **0** hits.
- **Only callers who pass a mode escape.** The explicit save modes (PATCH `/v1/env-groups/{id}/contents`, GraphQL `saveMode` `graphql.go:298`, MCP `saveMode` `mcp.go:204`, the dashboard editor `env-group-editors.tsx:51`) let them choose `save_only`.

## Fix (~60m)

- **Target behavior (Render parity).** A Render-shaped group write, link, unlink or delete updates the group's Secret for every linked service, but opens a deploy only on linked services whose `autoDeploy` is `yes`. Others keep running their current release and pick up the new values on their next deploy. The explicit `saveMode` paths are a caller's deliberate choice and stay as they are.
- **Report it honestly.** Add the untouched services to the write result (e.g. `pendingServiceIDs`), and change the group page copy to "Linking or unlinking redeploys linked services that have auto-deploy on."
- **Blast radius:** the six hard-coded call sites above plus link, unlink and create-with-services. Decide `ApplyEnvGroup` (Blueprint sync) separately against Render's Blueprint semantics and record the decision.
- **Tests:** per verb, one auto-deploy-on service (rolls) and one auto-deploy-off service (no deploy row, Secret updated). The existing explicit-`saveMode` tests stay as the control.
- **Adjacent / unverified:**
  - The config-change deploy **rebuilt** (`build_started`). Whether it built the pinned commit or the branch head was not checked (same commit in this run; see `w1/m148` for Restart building the branch head). If it is the head, an auto-deploy-off service can ship unreviewed commits this way.
  - Unlink, link and secret-file writes were read in code, not probed with auto-deploy off.
- **Render:** "If you make changes to an environment group (including deleting it), Render kicks off a new deploy for every linked service that has autodeploys enabled." (`render.com/docs/configure-environment-variables`, fetched 2026-09-14).
- **Dedupe:** `docs/ADR018-render-parity.md` environment-groups row records the save modes but not this divergence. No board item covers it. Not fixed on `main` as of `88fa89ba7`.
