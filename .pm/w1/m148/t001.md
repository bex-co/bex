## Objective

One target for all five entry points: a restart rolls new instances of the release that is **live** now, meaning the same resolved commit (and, for an image-backed service, the same image), and never re-resolves the branch.

## Context

- `lego/backend/internal/apps/service.go:2935-2941` (`Restart` clears `BuildCommit`); `apps/rest.go:739`; MCP `restart_service` (`apps/mcp.go:704`: read the handler first).
- `lego/backend/internal/deploys/graphql.go:215-221` (`restartServer` → `Trigger(…, TriggerParams{})`); `deploys/service.go:552-561` (the resolver pins H when there is no `commitId`).
- The live release's commit: the live deploy row's `commit` (`LatestDeployCommit`, `deploys/service.go:58`, already used to carry commits onto `config_change` rows), or `spec.BuildCommit` as currently pinned.
- Dashboard: `manual-deploy-button.tsx:110-115`, `service-row-actions.tsx:34-51`.
- `restartedAt` is release identity (`lego/operator/internal/controller/release_identity.go:70,121`).

## Steps

1. Decide the mechanism and record it in the verb's doc comment and ADR004:
   - **(a)** restart = `Trigger` with `CommitID` set to the live release's resolved commit (rebuilds the same code);
   - **(b)** restart reuses the live image (rolls pods without a build), which would need a restart annotation outside release identity.

   Prefer (b) if it is contained; otherwise (a).
2. Make `apps.Service.Restart` and `restartServer` go through that one verb, so REST, GraphQL and MCP cannot differ.
3. Restart has no live release yet (the first deploy is still building): refuse with a clear 409 rather than deploying the head.
4. Dashboard: header and row **Restart** call the restart verb (`restartServer`), not a bare `triggerDeploy`.

- [ ] Controls unchanged: Deploy latest commit resolves H, push webhooks pin the pushed SHA, and a `config_change` rebuild keeps the running commit.
