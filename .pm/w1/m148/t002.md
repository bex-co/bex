## Objective

A deliberate pin is a first-class, durable action. The dashboard can make it, and it is not silently replaced by the next push.

## Context

- Backend: `Trigger` with `commitId` sets `spec.BuildCommit` (`lego/backend/internal/deploys/service.go:559-561`) and never touches `autoDeploy`. REST, GraphQL and MCP already accept `commitId` (`w2/done/m30`).
- Render: "Deploy a specific commit … Specify a commit by its SHA, or by selecting it from a list of recent commits. This disables automatic deploys for the service." (`render.com/docs/deploys`, 2026-09-14).
- Dashboard: `dashboard/src/features/services/components/manual-deploy-button.tsx` (menu items only: latest / clear cache / restart); `useTriggerDeploy` already takes options.
- Live evidence: m148 README § Evidence 2–3 (`autoDeploy: true` after a pin).

## Steps

1. Backend: a trigger carrying `commitId` also sets `autoDeploy = false` in the same patch, and the response and the service read reflect it. Record the Render-matching rule in ADR004.
2. Dashboard: add **Deploy a specific commit** to Manual Deploy (repo-backed services only). It opens a dialog with a SHA input, plus recent commits if the GitHub integration exposes them cheaply (otherwise SHA-only, noted). Say plainly that it turns auto-deploy off. Show a server refusal verbatim (an unknown SHA, for example).
3. Deploy detail and Settings show that auto-deploy is off because of a pin.

## Acceptance criteria

- [ ] The m148 DoD's pin and auto-deploy bullets pass live.
- [ ] An invalid SHA is refused with the server's message in the dialog.

## Out of scope

- Re-enabling auto-deploy automatically on a later "Deploy latest commit". Decide it in t004 (Render keeps it off until the user re-enables it).
