# 087 — A deploy waiting on the workspace build cap reads only "Queued" for its whole wait, though the operator has already written why

Why: a first deploy sat for 8¾ minutes showing nothing but "Queued" and `==> Build queued`. The platform knew the exact reason ("workspace has 2/2 concurrent builds active; waiting for a slot") and showed it on no surface, so the user cannot tell a capacity wait from a stuck deploy.

- **Severity:** minor. The deploy resolved on its own, but for the whole wait the product gives no reason it already has.
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 5, journeys 2/3. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`. Fixture `qa-20260914-sus` (`srv-dajsm18gsm7s73f647ng`, free web service, `examples/hello-go`, docker), deleted inside the run.

## What was observed (every probe was run)

1. The service was created at `10:23:01Z` (deploy `dep-dajsm18gsm7s73f647o0`, `trigger: create`). GraphQL polled every 10 s:

   ```text
   10:23:01 → 10:31:40   deploy.status = queued      service.phase = Building
   10:31:47              deploy.status = build_in_progress
   10:32:51              deploy.status = live        service.phase = Running
   ```

2. During the wait, two genuine builds were running in the same workspace (read-only):

   ```text
   eden-cms-v2       dep-dajskk0gsm7s73f647j0  build_in_progress since 10:20:58 (new_commit)
   beancount-cms-v2  dep-dajsmda6m8ac739r5ms0  build_in_progress since 10:24:28 (new_commit)
   ```

   `BEX_MAX_CONCURRENT_BUILDS` is `"2"` in `lego/operator/config/manager/manager.yaml:178-179`, so the workspace cap was full. This was a legitimate capacity wait, not a stuck deploy.

3. For all 8¾ minutes, the deploy page (`/services/<id>/deploys/<dep-id>`) showed: status **Queued** · timeline `Deploy created 3:23 AM → Queued 3:23 AM` · logs `03:23:01 AM ==> Build queued`. There was no reason, position or estimate. `deploys { failureReason }` stayed `""`.
4. Afterwards the timeline reads `Deploy created 3:23 AM → Deploy started 3:31 AM → Live 3:32 AM`, with nothing explaining the 8-minute gap.

## Root cause

- **The operator writes the reason:** `lego/operator/internal/controller/app_controller.go:796-797` sets phase `Building`, reason `BuildQueued`, message `"<noun> has <active>/<limit> concurrent builds active; waiting for a slot"`. The `noun` is `workspace` for the per-workspace cap and `cluster` for the cluster-wide one (`:1119-1122`). A scheduler wait uses `"waiting for build capacity: " + obs.Message` (`:937-938`).
- **The backend keeps the status but drops the message:** `observedDeployStatus` maps `BuildQueued` to deploy status `queued` (`lego/backend/internal/store/reconciler.go:868-885`). The message is surfaced only by `failureReasonFor` (`:1320-1323`), and only when a queued row **times out** ("the build never started: …"). The `deploys` table has no reason column for an open row.
- **The narration has one line for the whole wait:** `lego/backend/internal/logs/progress.go:84-90` emits `==> Build queued` at `CreatedAt`, and nothing more until `StartedAt`.

## Fix: target behavior

**While a deploy is `queued` because of `BuildQueued` or `RegistryCredsPending`, the build-log narration states the operator's current reason.** For example, `==> Waiting for a build slot: this workspace has 2/2 builds running`, re-emitted when the reason changes. The deploy page then shows that line under **Queued**.

- **Shape:** the progress follower already reads deploy state each tick (`progress.go`, w1/m48). It also needs the App's `Ready` condition message while the row is `queued`. Put the change in the one core verb, so REST `GET /v1/logs`, GraphQL `logs`, MCP log reads and the SSE tail stay identical. No new UI component is needed, since the deploy page already renders build narration.
- **`failureReason` stays terminal-only:** it must not be repurposed for a live wait.
- **Adjacent classes:**
  - **Workspace cap:** name it; the tenant's own builds are the reason.
  - **Cluster cap (`noun: cluster`):** use tenant-neutral copy ("waiting for platform build capacity"), and **do not** print `4/4`, which reveals other tenants' build activity.
  - **Scheduler wait (`:937-938`):** also tenant-neutral.
  - **`RegistryCredsPending`:** narrate it as "preparing registry credentials".
- **Tests:**
  - a queued row with each reason produces the matching line;
  - the reason changing emits a new line;
  - the cluster-cap line carries no counts;
  - the existing `==> Build queued` / `==> Building from …` lines are unchanged (control).
- **Estimate:** ~60m (backend progress line plus tests). Promote to a milestone if carrying the message needs a stored column.
