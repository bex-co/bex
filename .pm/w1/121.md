# Service environment variables never reach a buildpack (kpack) build, so `BP_*` settings are unconfigurable

Why: Paketo is configured through build-time `BP_*` variables (`BP_NODE_VERSION`, `BP_GO_TARGETS`, …). A tenant who sets them on the service sees no effect, which silently removes the documented way to steer the buildpack path.

**Source:** `w1/108` production validation, 2026-10-02. Fixture `qa-20261002-108-bp24` (deleted) was `qa-…-bp` plus `BP_NODE_VERSION=24.*` in its service `envVars`; kpack produced the identical Node 26 image, i.e. the variable never reached the build env.

- **Look at:** how `lego/operator/internal/build/kpack.go` authors the kpack `Image` (`spec.build.env`) versus how the native and Dockerfile paths pass build-time env (`internal/build/native.go`, `build.go`). Render exposes service env vars to the build; mirror that rather than inventing a separate build-env surface.
- **Security:** only non-secret values belong in a kpack `Image` spec; decide whether secret-backed env vars are excluded or mounted, consistent with the Dockerfile path's handling.
- **Done when** a buildpack build honors `BP_NODE_VERSION` set on the service (proved live), with an operator test asserting the projected build env.
