# 085 — The Key Value and Postgres Details cards print raw `status` and plan ids, so a suspended store reads "Suspended" in its header and "available" in its own Status row

Why: the detail page contradicts itself about whether a datastore is running, and the same two rows leak untranslated wire values into every locale.

- **Severity:** minor. It misleads, but the header badge beside it is correct.
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 2, journey 12. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, fixture `qa-20260914-kv` (`red-dajrprggsm7s73f6459g`, free), created, suspended, resumed and deleted inside the run.

## Repro (every step was run)

1. Create a Key Value store and wait for **Available**, then open `/keyvalue/<red-id>`. Details card: `Status` **available**, `Instance type` **free**. Header badge: **Available**.
2. Danger Zone → Suspend Key Value Instance → type `sudo suspend key value <name>` → confirm. Sampled every 5 s for 30 s, then once after a reload:

   ```text
   header badge : Suspended
   Status row   : available
   API          : {"data":{"keyValue":{"status":"available","suspended":"suspended"}}}
   ```

3. The same page with `?lang=zh`: the header badge reads **可用**, the row labels translate (`状态`, `实例类型`), but the values stay **available** and **free**.
4. A pre-existing Postgres, `/databases/dpg-d9nqg95cavls73fp8m20` (read-only): header **Available**; Details `Status` **available**, `Instance type` **basic-256mb**.
5. Resume: the header returns to **Available** and the API reads `not_suspended`, so the resume journey itself is fine.

## Root cause

- `dashboard/src/routes/keyvalue.$keyValueId.tsx:293-294` and `dashboard/src/routes/databases.$databaseId.tsx:363-364` pass `keyValue.status` / `database.status` and `.plan` straight into `MetadataList` as values.
- The header badge instead goes through `deriveStatus` (`dashboard/src/features/keyvalue/lib/status.ts:79-85`, `dashboard/src/features/databases/lib/status.ts:111-117`). That function returns `suspended` whenever the resource is suspended and reads its word from `STATUS_LABEL` (`features/keyvalue/lib/labels.ts:9-15`, and the databases equivalent). The wire `status` deliberately stays `available` while suspended (the backend reports readiness separately from suspension), so only the derived view is correct.
- Blast radius: `grep -rnE "value: [a-zA-Z]+\??\.(status|plan|phase)( \|\||\s*\?\?|,|\s*\})" dashboard/src --include='*.tsx'` finds **exactly these 4 rows** (2026-09-14). Service and static-site headers do not render such rows.

## Fix

- **Status row:** render the same derived label the badge uses, `t(STATUS_LABEL[deriveStatus(x).key])`, or drop the row as redundant with the badge (Render's datastore Info section does show a status; keep it, derived). A suspended store must read **Suspended** in both places.
- **Instance type row:** the catalog display name, from `useKeyValueInstanceTypes` / `useDatabaseInstanceTypes` (each maps `id → name`; they already feed `key-value-plan-section.tsx` / `database-plan-section.tsx`). Fall back to the id while the catalog loads or when the id is not in it.
- **Tests:** a route test per page asserting a suspended fixture renders the suspended label in the Details card, and a plan id renders its catalog name. The existing header-badge tests are the control.
- **Estimate:** ~40 min. Dashboard only; REST/GraphQL/MCP untouched.

## Unverified

- A **suspended Postgres** was not probed: only pre-existing databases were available, and suspending one is off-limits. The identical row code plus `deriveStatus` makes the same disagreement near-certain.
- `unavailable` / `creating` states in the Details card were not captured this run.
