## Objective

Pick the PromQL for Postgres and Key Value CPU and memory (and their limits), counting only the datastore's own container, and prove the series are retained.

## Context

- App metrics already query cAdvisor: `lego/backend/internal/metrics/source.go:259-317` (`container_cpu_usage_seconds_total` rate, `container_memory_working_set_bytes`).
- CNPG instance pods are `<cluster>-N`; Key Value runs as a StatefulSet (`<name>-0`) with a `redis_exporter` sidecar whose own CPU must not count (w4/181 raised its limit to 50m).
- Prometheus keep-lists live in `deploy/gitops/base/prometheus.yaml`; a dropped series would read as an empty chart (the m161 keep-list precedent).
- Limits come from the plan's tier catalog, as service `cpu-limit`/`memory-limit` do.
- Render's metric resource scope (pinned OpenAPI `resourceIdParam`): "server, cron job, postgres, or redis".

## Steps

1. Write the selectors (namespace + pod + container) for both kinds.
2. Run them against the local cluster and, read-only, against production Prometheus if reachable; otherwise note it for t005.
3. Decide Key Value `memory`: keep the existing `kv_memory` (redis_exporter `used_memory`) mapping unless Render evidence says instance memory.

## Acceptance criteria

- [ ] Queries return non-empty series for a running Postgres and Key Value, excluding sidecars; the Key Value memory decision is recorded.

## Out of scope

- `http-*`, `bandwidth` and `instance-count` for datastores (stay refused).
