# 093 — Render's `GET /notification-settings/overrides` (list a workspace's service notification overrides) returns bex's bare 404, and ADR018 doesn't record the gap

Why: a Render client that audits which services mute or force deploy mail gets an undocumented `404 page not found`. bex's parity row says notifications are ✅ on every surface, and names every other divergence but not this one.

- **Severity:** minor (Render REST parity; the per-service reads work).
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 15. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`; fixture web service `qa-20260914-pin` (`srv-dak0pg26m8ac739r60u0`), created and deleted inside the run.

## Repro (every request was run, from the signed-in dashboard page)

```text
GET /v1/notification-settings/overrides                                        → 404 "404 page not found"
GET /v1/notification-settings/overrides?ownerId=tea-d98210cbbpdc73dcrkvg      → 404 "404 page not found"
GET /v1/notification-settings/overrides/services/srv-dak0pg26m8ac739r60u0     → 200 {"notificationsToSend":"default","previewNotificationsEnabled":"default"}   (control)
GET /v1/notification-settings/owners/tea-d98210cbbpdc73dcrkvg                 → 404 "404 page not found"   (recorded divergence, below)
GET /v1/notification-settings                                                  → 200 {"deployStarted":false,"deploySucceeded":false,"deployFailed":true}          (bex member defaults)
```

## Contract

- **Render** (pinned spec `lego/backend/internal/api/openapi/render-public-api-1.json`): `list-notification-overrides`, `GET /notification-settings/overrides`.
  - Optional `ownerId`, `serviceId`, `cursor` and `limit` query parameters.
  - `200` returns an array of `notificationOverrideWithCursor`.
- **bex** registers only the per-service `GET`/`PATCH /v1/notification-settings/overrides/services/{id}` (`lego/backend/internal/apps/rest.go:1334-1341`) and member defaults `GET`/`PATCH /v1/notification-settings` (`lego/backend/internal/notifications/rest.go:44-47`).
- **Validator:** a route that exists only in Render's spec passes to bex's mux and gets its plain 404 (`lego/backend/internal/api/render_openapi.go:360-366`).

## Record

- **Covered divergence.** `docs/ADR018-render-parity.md` row 227 lists "workspace defaults remain per-member", which covers `…/owners/{ownerId}`.
- **Uncovered gap.** Neither that row nor `docs/render-artifacts/notify-on-fail.md` (which lists only the two per-service routes, `:21-22`) mentions the list operation.

## Fix (~30m)

- **Implement the list.** Serve `GET /v1/notification-settings/overrides` from the same authoritative `App.spec.notificationsToSend` the per-service route reads. Scope it to the caller's workspace (`ownerId` resolved like the other routes), filter by `serviceId`, and page with Render's `{notificationOverride, cursor}` envelope. It is a read-only projection.
- **Or record the divergence.** If it isn't implemented, add it to row 227 as an explicit divergence with the reason, and to `notify-on-fail.md`.
- **Tests:** a composed-server test through the strict Render validator. A service with `notificationsToSend: failure` appears; a `default` service appears with `default` (confirm against Render's response semantics); another workspace's services never appear.
- **Unverified:** whether Render lists services whose override is `default`, and whether the official Render CLI calls this operation.
- **Dedupe:** no board item mentions `notification-settings/overrides` as a list. `w3/done/m15` shipped only the per-service routes. Not fixed on `main` as of `86d262d35`.
