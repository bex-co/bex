## Objective

Give the claim start a chooser mode. In this mode the OAuth callback always sends the browser to the account chooser, which lists every installed account the authorizing GitHub user administers and marks each one connected or not for this workspace. It never binds automatically, and it never fails with `no_claimable_installation` just because the user has nothing installed yet.

## Context

- `lego/backend/internal/github/service.go`:
  - `StartClaim` (:394).
  - `claimFromCallback` (:438): 0 candidates return `errNoClaimableInstallation`, 1 binds, and more than 1 calls `offerClaimSelection`.
  - `GetClaimSelection` (:518), `SelectClaim` (:558), and the `ClaimCandidate` struct.
- `lego/backend/internal/github/rest.go:93`: the `GET /v1/git/callback` branch that redirects with `git_claim_selection`.
- `lego/backend/internal/github/graphql.go`: `claimGit`, `gitClaimSelection`, `selectGitClaim`.
- `lego/backend/internal/store/github.go`: the `github_connect_transactions` and `github_claim_selections` rows.
- REST and GraphQL clients of `claimGit` may rely on a single candidate binding automatically. Keep that behaviour when the new option is absent.
- MCP stays without connect and claim verbs (ADR078 §5).

## Steps

1. Add a start option to `claimGit` / `POST /v1/git/claim` (for example `chooser: true`) and record it on the transaction row; add a migration if the row needs a column.
2. In chooser mode, the callback persists a selection for 0, 1 or N proved candidates and redirects with `git_claim_selection`.
3. Add `connected` to each candidate returned by `GetClaimSelection`: true when the installation is already bound to the selection's workspace. `SelectClaim` on a connected candidate stays an idempotent success.
4. Keep every proof (signed state, single-use nonce, initiator match, fresh `can_manage`, the installation-admin proof) and the 5-minute selection TTL.
5. Expose the option and the field in REST and GraphQL under the same names, and regenerate the dashboard's GraphQL types.
