## Objective

A redirect that carries `setup_action` comes from GitHub's setup URL, not from an OAuth claim, so route it accordingly:

- `install` or `update` with `installation_id`: handled as today.
- `request`, meaning an org member asked the owners to install the App: a bounded `git_error=install_requested`.
- Any other `setup_action` with no `installation_id`: `invalid_installation`.

None of these may reach `claimFromCallback`.

## Context

- `lego/backend/internal/github/rest.go:131`: an empty `installation_id` selects the claim branch (ADR078 §3a step 2). `setup_action` is read nowhere in `lego/`.
- The risk: a requester who administers exactly one other installation would have that unrelated account bound silently. Anyone else would get the misleading `no_claimable_installation` message.
- GitHub's setup-URL docs document only `installation_id`; whether the request flow redirects at all is undocumented. Handle it defensively.
- Callback error copy lives in `dashboard/src/features/git/locales/*.ts` (`git.callbackError*`, 8 locales), mapped in `dashboard/src/features/git/components/connect-github-card.tsx`. The allowed codes are in `rest.go`'s `writeCallbackFailure`.

## Steps

1. In the callback, read `setup_action` before branching. Only its absence, together with `code` and `state`, selects the claim branch.
2. Add `install_requested` to the bounded callback codes, and consume the nonce as every other branch does.
3. Map the code in the dashboard to a message in all 8 git locales: "Your request to install the bex GitHub App was sent to the organization's owners. Once one approves it, connect again."
4. Log the `setup_action` value (never a token) so the first live occurrence is visible.
