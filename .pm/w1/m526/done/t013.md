## Objective

The agent new-session composer follows the workspace's GitHub connection set for as long as it is open, as the source picker does. This holds wherever the change is made: the callout's new tab, Settings in another tab, a teammate, or Settings before the composer mounted. A disconnected account's repos leave the composer's repository list. Once the last account is gone, reaching for a repository offers "Connect GitHub account" again.

## Context

- t010 walk 2 (2026-11-21, pin `820edf28d22d`), the agent composer row, in `bex-canary`. Connect through the callout passed. Then:
  1. With BlockEdenHQ connected and the composer open, BlockEdenHQ was disconnected from Settings in another tab. 30 s later the composer's repository list still listed BlockEdenHQ's 27 repos, and an in-app trip to Settings and back did not refresh them.
  2. With BlockEdenHQ connected, the account menu went to Settings in the same tab, Disconnect removed it, and the sidebar went back to Agents. The repo list was empty, since Settings evicts the cached repos, but the composer still read the cached `agentSessionCapabilities.github.connected = true`. So no callout appeared, and the person saw "No repositories yet. Connect a GitHub account, …" with no way to connect from there (DoD 1).
- Cause: `dashboard/src/features/agent-sessions/components/new-session-composer.tsx` ran `useOnGitConnectionsChange` and `useRefetchOnFocus` only inside `GitHubEmptyCallout`. The callout is mounted only while GitHub is missing, so nothing watched the set once an account was connected. `useAgentSessionCapabilities` is `cache-first`, so a remounted composer reads the readiness it cached before the disconnect.
- The server's readiness (`agentsessions.Service.Capabilities`, `GitHub.GetConnection`) is "the workspace has a GitHub connection", the same fact as `gitConnections` being non-empty.
- The source picker already hosts the watcher for its whole life (`service-source-picker.tsx`, t006).

## Steps

1. In `NewSessionComposer`, read the polled connection set (`useGitConnections`). Refetch repos whenever the set changes (`useOnGitConnectionsChange(refetchRepos, { poll: false })`), and refetch the set itself when the tab regains focus.
2. Re-read readiness when the cached `capabilities.github.connected` disagrees with the loaded connection set. This covers a change made while the composer was closed.
3. Drop the callout's own watcher, which the composer's now covers.
4. Tests in `new-session-composer.test.tsx`:
   - one account disconnected elsewhere refetches the repos only; the last one also re-reads readiness;
   - a cached readiness that disagrees with the set is re-read on mount, and one that agrees is not;
   - focus re-reads the connection set.

## Outcome (2026-11-21)

`NewSessionComposer` reads the polled connection set (`useGitConnections`) for as long as it is open. A change to the set refetches the repos (`useOnGitConnectionsChange(refetchRepos, { poll: false })`), and a regained focus re-reads the set at once. A cached `capabilities.github.connected` that disagrees with the loaded set is read again, which brings the callout back after the last account goes, also when that happened while the composer was closed. `GitHubEmptyCallout` lost its own watcher, which the composer's now covers.

Four tests cover it. One account disconnected elsewhere refetches the repos only, and the last one also re-reads readiness. A cached readiness that disagrees with the set is re-read on mount. One that agrees is not re-read. Focus re-reads the set. The first, second and fourth failed with the fix reverted; the third guards against an extra read and passes either way.

`yarn lint` passes. The full `yarn test` run passed all 807 files and 9749 tests. Its one unhandled rejection came from `sso-buttons.test.tsx`, which reaches the local `dashboard/.env` Kratos URL on `:8099`, the same unrelated local error t012 recorded.
