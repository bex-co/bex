## Objective

Everything that describes the deploy lifecycle and `maxShutdownDelaySeconds` matches what the operator now does, and matches Render's order: traffic switches, a drain follows, then `SIGTERM`, then the shutdown delay, then `SIGKILL`. Otherwise the difference is recorded as a divergence.

## Steps

1. **API and dashboard descriptions.** REST, GraphQL and MCP descriptions of `maxShutdownDelaySeconds`, and the dashboard hint "Wait 1–300 seconds after SIGTERM before force-stopping the process (default 30)", still hold. The value reads back as the user set it, not as the widened grace period.
2. **ADR004.** Correct `docs/ADR004-app-deployment.md:223`. "Zero-downtime by construction" needs the drain as well as readiness gating; name the drain length and why.
3. **ADR018.** Add or extend a row in `docs/ADR018-render-parity.md` for zero-downtime deploys. Render waits 60 s after switching traffic before `SIGTERM`; record bex's drain length as a deliberate divergence if it is shorter.

## Acceptance criteria

- [ ] REST, GraphQL and MCP `maxShutdownDelaySeconds` read back unchanged, and their descriptions are accurate.
- [ ] ADR004 and ADR018 describe the drain and any divergence from Render's 60 s.
