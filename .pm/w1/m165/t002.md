## Objective

Render's MCP server now registers a `list_events` tool that bex has never decided about. Decide it: either bex exposes an equivalent MCP tool over the events feed it already owns, or the gap is a recorded deliberate divergence in `docs/ADR018-render-parity.md`. Produce the decision with its rationale; t003 lands it. This is a surface decision, not a feature build — the data already exists on two other surfaces.

## Context

- Live failure of the `render-mcp` job, every scheduled run since 2026-08-24:

  ```
  $ scripts/render-mcp-drift.sh
  ##[error]upstream ref=main added=[list_events] removed=[none]
  ```

- `list_events` appears in none of `docs/ADR018-render-parity.md`, `lego/backend/internal/api/mcp_parity.go`, or `lego/backend/internal/api/openapi/render-mcp-tools.json`.
- Current pin: 22 tools, `pin.capturedAt` `2026-08-18`, `source.commit` `89c1f01b45270303d3b596b275ba0aaca39c2972` (`2026-08-17`), ref `main` — deliberately `main` rather than the `v0.3.0` release, per the pin's own recorded note.
- The drift script compares **tool names and argument names only** — descriptions and annotations are excluded as editorial. So the decision has to name the arguments, not just the tool.
- bex already exposes the substance on two surfaces:
  - the three-source durable events feed with Render-shaped filters — `w3/m7`, `w3/m16`, `w3/m19`, extended by `w7/m66` (`build_started`/`build_ended`, `pre_deploy_*`, `job_run_ended`, `branch_deleted`)
  - owner-scoped `GET /v1/events/{eventId}` hydration across deploy, audit and typed-fact sources — `w8/m24`
- `mcp_parity.go` already carries per-tool acknowledgment strings (e.g. the `create_static_site` entry explaining `publishPath`), so an "acknowledge" outcome has an established home and shape.
- ADR018's Service events feed row records the feed as done with deliberate REST divergences; a `list_events` decision belongs on or beside that row.

## Steps

1. Capture what upstream's `list_events` actually takes and returns: run `scripts/render-mcp-capture.py --ref main` (or read the built server's own `tools/list`) and record the tool's argument names verbatim.
2. Compare against bex's existing events reads — the feed's filter vocabulary and `GET /v1/events/{eventId}` — and note which upstream arguments bex can already answer and which it cannot.
3. Check Render's own product behavior for the tool so the decision is made against what it does, not against its name alone.
4. Recommend one outcome, with the reason written out:
   - **implement** — bex adds an MCP tool over the existing feed, arguments matching upstream's names, semantics matching bex's REST/GraphQL reads; or
   - **acknowledge** — the gap is deliberate, with the rationale and an ADR018 row, in the shape `mcp_parity.go` already uses.
5. If the arguments reveal a surface bex genuinely lacks (rather than lacks a tool for), say so and scope it as follow-up rather than widening this milestone.
