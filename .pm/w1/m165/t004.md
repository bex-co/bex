## Objective

Both halves of this workflow failed for five weeks while carrying almost no instruction. `render-schema` printed a path and the word "inconsistent"; `render-mcp` printed `added=[list_events]` with no statement of what a reader should do about it. Now that both jobs can run, make a red run self-describing: which check failed, what it found, and the action that clears it. The point is that the next genuine drift is acted on in a day rather than read past for five weeks.

## Context

- The two failure messages as they stand today:
  - `Render webhook vocabulary fixture is internally inconsistent: docs/render-artifacts/fixtures/render-webhook-vocabulary-2026-08-17.json`
  - `upstream ref=main added=[list_events] removed=[none]`
- Neither says whether the reader should refresh a pin, implement a tool, acknowledge a divergence, or repair a fixture — the four real outcomes.
- The repo already has the reference text for the MCP path: `scripts/render-mcp-drift.sh`'s header explains the check-never-update rule, and the pin's `note` records the regeneration command. That guidance exists in the files but not in the failure output.
- `lego/backend/internal/api/mcp_parity_test.go` and the `conformanceAllowlist` workflow comments in `.github/workflows/backend-test.yml` (the "Pin-update workflow" block, lines 118–127) are the established shape for writing a keep-or-fix decision procedure next to the check that enforces it.
- Issue [#74](https://github.com/bex-co/bex/issues/74) is the consumer: `ci-red-streak.yml` reports a standing red with the first failing commit, and a legible message is what makes that report actionable.
- Deliberately **not** in scope: making this workflow a required check. `ci-red-streak.yml`'s own header records why (binding production releases to a drift check means any flake there stops shipping).

## Steps

1. For `render-mcp`: on drift, print the added/removed tool names **and** the decision procedure — refresh the pin when upstream moved deliberately, implement the tool, or add the `mcp_parity.go` acknowledgment — with the exact regeneration command.
2. For `render-schema`: on a fixture or schema fault, print which assertion failed, which file it read, and whether the expected action is repairing the fixture or re-reviewing the pin.
3. Keep both scripts check-never-update: no path may mutate a pin or fixture as a side effect of the check.
4. Prove each message by forcing each failure: mutate a pin copy (add and remove a tool) and corrupt a fixture copy, and capture the output.
5. Trigger the workflow with `workflow_dispatch` and confirm both jobs pass on the real tree.

## Files

- `scripts/render-mcp-drift.sh`
- `scripts/render-schema-drift.sh`
- `.github/workflows/render-schema-drift.yml` (only if job-level output/summary wiring is needed)

## Acceptance criteria

- [ ] A forced MCP drift names the added/removed tools and states the three possible actions with the regeneration command; captured output is recorded in the milestone README.
- [ ] A forced `render-schema` fault names the failing assertion, the file, and the expected action; captured output recorded.
- [ ] Neither script writes to a pin or fixture on any path (verified by running both against a read-only checkout or by inspection).
- [ ] A `workflow_dispatch` run has both jobs green.

## Out of scope

- Making the workflow a required/gating check — explicitly rejected, see `ci-red-streak.yml`'s header.
- Changing the weekly schedule or the runner pool (`.pm/DO_NOT_DO.md` `#CI-RUNNERS`, `#RUNNER-HOSTS`).
- Acting on any drift the repaired checks report.
