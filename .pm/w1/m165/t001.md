## Objective

The `render-schema` job of the `Render schema drift` workflow has never compared Render's published schemas against bex's reviewed pins, because `scripts/render-schema-drift.sh` exits 1 on a self-check of one of its own fixtures long before it fetches anything upstream. Find out what "internally inconsistent" means for that file, decide whether the fixture is wrong or the check that reads it is wrong, fix that one, and get the job to the point where it actually performs the comparison it exists for.

## Context

- Live failure, most recent scheduled run (2026-09-27T09:16Z) and every run back to 2026-08-24:

  ```
  $ scripts/render-schema-drift.sh
  Render webhook vocabulary fixture is internally inconsistent: \
    /home/docker/actions-runner/_work/bex/bex/docs/render-artifacts/fixtures/render-webhook-vocabulary-2026-08-17.json
  ##[error]Process completed with exit code 1.
  ```

- The workflow runs two independent jobs; this task owns `render-schema` only. `render-mcp` fails for a genuine reason and is t002/t003's subject.
- `.github/workflows/render-schema-drift.yml` — `schedule: "17 6 * * 1"` (weekly, Monday), plus `workflow_dispatch`, on `[self-hosted, Linux, ARM64, bex-ci]`.
- The fixture sits under `docs/render-artifacts/fixtures/`, whose practice is to redact ids/emails; the drift script is a check-never-update script by design (the header of its MCP sibling states the rule).
- Issue [#74](https://github.com/bex-co/bex/issues/74) names this job as never having passed in the runs inspected, and cites `d82cc98cd` as the precedent: a `yq` expression that returned one line per document and so could never compare equal, failing regardless of the manifest. Check for that shape first.

## Steps

1. Run `scripts/render-schema-drift.sh` locally and find the exact assertion that emits "internally inconsistent" — which two views of the fixture it compares, and why they cannot agree.
2. Decide, and write down in the milestone README's `## Root cause`, which side is at fault: the fixture's recorded vocabulary, or the consistency check's reading of it. Prefer the reading being wrong only if the fixture is verifiably faithful to the capture it names.
3. Fix that one side. Do not relax or delete the consistency check to get past it — if the check is genuinely redundant, say so explicitly in the README rather than quietly dropping an assertion.
4. Re-run the script and confirm it proceeds to the upstream comparison and reports a real verdict (pass, or a named drift).
5. If it now reports genuine REST-schema drift, record the drift in the milestone README and file it as follow-up work — do not absorb a parity change into this task.
