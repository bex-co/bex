# Blueprints refuse a database and a service with the same name; Render's mattermost example uses one

Why: Render's own `render-examples/mattermost` (commit `51a1d9ae…`, now `lego/backend/internal/apps/testdata/render-mattermost/render.yaml`) declares database `mattermost` and web service `mattermost`, and bex refuses the whole file before planning: `duplicate name "mattermost" — every service and database name in a render.yaml must be unique` (`registerUniqueName`, `lego/backend/internal/apps/deploy.go:1925-1931`). Render accepts it, so an unchanged Render example cannot import.

- Found by w1/m175's fixture test (`TestRenderExampleBlueprintsCopyTheirGeneratedPasswords`), which asserts this refusal and checks mattermost's copies on a renamed variant.
- First check what Render actually namespaces by: kind (services vs databases vs Key Value) or type. `fromService`, `fromDatabase` and the plan's `(kind, name)` keys already carry the kind, so a per-kind name set may be enough; confirm nothing else (resource names derived from the Blueprint name, plan IDs, sync detach matching, `appsByName`) assumes one shared namespace.
- Done when the unchanged mattermost file parses and plans, a same-kind duplicate is still refused by name, and the fixture test drops its rename.

**Triage 2026-10-15 (`/loopx w1`): blocked on evidence only Render can give.** The premise "Render accepts it" is inferred from the example and is unverified. Render's Blueprint spec says the opposite for the file: "Provide a unique name for each resource in your Blueprint file" (services and databases alike; no per-kind wording), which is exactly what bex enforces. But Render keeps the example current (`render.yaml` last edited 2025-01-17, "Update database plan"), so it may still be accepted. Deciding needs Render's own answer: `POST /v1/blueprints/validate` (or a dashboard Blueprint preview) on the unchanged mattermost file, which needs a Render account or `RENDER_API_KEY` (the same gate as `w10/002`). If Render accepts it, implement per-kind uniqueness as described above; if it refuses, delete this note and drop the rename from the fixture test.

**Answered 2026-10-15 by Render itself** (Render CLI v2.21.0 against `api.render.com`, `render blueprints validate`): the unchanged mattermost file is `valid` (plan: database `mattermost` and services `mattermost-minio`, `mattermost`); ghost and wordpress are valid too. Probes: a database and a service sharing a name, a Key Value and a service, and a database and a Key Value are all valid; two services (web and worker) sharing a name are refused ("service name dup of type worker is used more than once"), as are two databases ("database name "dup" is already used by databases[0]"). So Render's rule is unique within a kind (services, Key Value, databases), not across the file. Implement per-kind uniqueness as above.
