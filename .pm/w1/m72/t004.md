## Objective

Make it impossible for a harness's logs to grow without bound, and reclaim what has already accumulated.

## Context

- `.pm/w5/dev-5/logs` is **3.9 GB** — the single largest thing in the repo working tree (`.pm` totals 4.8 GB, and `w5` alone is 4.0 GB of it). The files are per-service port-forward logs: `pf-kratos.log`, `pf-hydra.log`, `pf-loki.log`, `pf-mailpit.log`, `pf-bex-db.log`, `pf-kratos-admin.log`, plus `bex-api.log`.
- `bin/` adds ~100 MB per workstream (a compiled `bex-api`, and a `render` binary in `w9`) — ~800 MB across the ten. Untracked, but worth a `clean` verb.
- Already gitignored per `dev-N/.gitignore` (`.kubeconfig`, `.pids/`, `logs/`, `bin/`), confirmed by `git ls-files`. This is a disk and hygiene problem, not a repo-bloat problem.
- A port-forward that reconnects in a tight loop is the likely cause of 3.9 GB — worth a look while here, since truncation would hide it.

## Steps

1. Truncate or rotate each log on `up`, so a long-lived environment cannot accumulate indefinitely.
2. Add a `clean` verb that removes `logs/` and `bin/` for a given N, refusing to run while that environment is up.
3. Reclaim the existing 3.9 GB.
4. Note in `dev-N/README.md` that logs are truncated per `up`, so nobody is surprised by a lost tail.
5. If the runaway log turns out to be a reconnect loop, file it as an inbox note rather than fixing it here.

## Files

- `scripts/dev-env.sh`
- `.pm/w*/dev-*/README.md`

## Acceptance criteria

- [ ] Logs are bounded across repeated `up` runs; demonstrated, not assumed.
- [ ] `clean` reclaims `logs/` and `bin/` and refuses while the environment is up.
- [ ] The existing 3.9 GB is reclaimed and `du -sh .pm` recorded before and after.

## Out of scope

- Shipping a log-rotation daemon; truncate-on-up is sufficient for a dev harness.
