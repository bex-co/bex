# 095 — A linked environment group's secret file silently replaces the service's own secret file of the same name, the reverse of the env-var rule, and the Environment page marks nothing

Why: a service's explicitly set secret file (a certificate, a credentials JSON) is swapped at runtime for a shared group's file the moment the group is linked. The API and dashboard keep showing the service's own file, while bex's rule for env vars on the same page is the opposite (the service always wins).

- **Severity:** major. Silent runtime substitution of a credential file, invisible on every surface.
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 22. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`. Fixtures were created and deleted inside the run:
  - web service `qa-20260914-sfc` (`srv-dak2o5i6m8ac739r62j0`), `examples/hello-python` with Docker Command `python -m http.server $PORT --directory /etc/secrets`, so it serves its own mounted files;
  - env group `qa-20260914-sfg` (`evg-dak2ocggsm7s73f64j9g`);
  - both deleted 17:22:08Z (`DELETE` → `204`, then `GET` → `404`).

## Root cause

- **Order of the file sources.** The service's own `<name>-files` Secret joins `spec.filesFromSecrets` by `addString` when its first file is saved (`lego/backend/internal/secrets/files.go:224-228`), so on a created-with-files service it is **first**. A linked group's `<evg>-files` Secret is appended at link time (`lego/backend/internal/envgroups/service.go:1084`), so it comes **later**.
- **Projection.** `secretFileMounts` projects `filesFromSecrets` in list order into one `/etc/secrets` volume, with no duplicate-path guard (`lego/operator/internal/controller/app_controller.go:3894-3925`). The later source's `qa.txt` is what the pod sees.
- **The env-var contrast.** `envFromSources` deliberately puts the service's own Secret **last** so "a service's own variable overrides a linked group's — matching Render" (`app_controller.go:3847-3878`). Files got no equivalent ordering.
- **Display.** `EnvGroupItem` computes `overridden` from `group.envVarKeys` only and renders `group.secretFileNames` without any check (`dashboard/src/features/services/components/env-groups-panel.tsx:188-189`, `:236`).

## Fix (~45m)

- **Target:** a service's own secret file always wins over a linked group's file of the same name, the same rule as env vars. `secretFileMounts` places the service's own files Secret (`<name>-files`, or the pending annotation) **last**, whatever its position in `filesFromSecrets`.
- **Group vs group:** between groups keep last-linked wins, consistent with `w1/091`, and document it.
- **Display:** mark a linked group's file as overridden when the service defines the same name (reuse `services.envGroupKeyOverridden`-style copy). Mark a group-vs-group shadow once `w1/091` exposes link order.
- **Record** the file precedence in `docs/ADR013-secrets.md` and the environment-groups row of `docs/ADR018-render-parity.md`. Render's docs state precedence only for env vars ("that value always takes precedence over any linked environment groups") and are silent on files.
- **Tests:**
  - operator: a projection-order test where the service files Secret is last with groups linked before and after the first service file;
  - dashboard: the panel marks a shadowed group file;
  - live: repeat the repro, expecting `from-service`.
- **Adjacent classes:** a service created **without** files that links a group and adds a file later is already service-last today (same `addString`), so the fix must be order-independent. Removing the service's file must fall back to the group's. Restart and redeploy must not reshuffle.
- **Unverified:** the kubelet's behavior for duplicate paths across projected sources beyond "later wins" as observed; group-vs-group file collisions; behavior after unlink.
- **Dedupe:** `w1/091` covers env-var collisions between two groups and only names files as unverified. `w6/done/067` covers the env-var service-override marker. No item covers service-vs-group secret files. Not fixed on `main` as of `2ff4d69a2`.
