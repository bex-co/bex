# 100 — An environment group that is already over the secret-map quota refuses every batch save, including deletes that would bring it back under

Why: `w1/m147` aligned the **service** batch patch on "a map already over quota can shrink but not grow" (`patchWithinQuota`, `lego/backend/internal/secrets/batch.go`), matching ADR066 #6's "deleting frees room". The environment-group batch patch still checks the resulting map unconditionally. So a group over 500 entries or 512 KiB per map rejects a patch that only deletes entries: the result is still over quota, so the patch is refused, and the group can't be brought back under through `PatchEnvironment`.

- **Severity:** minor. Env-group writes have been quota-checked since the round-11 fix (`cacde0622`, 2026-08-17), so a group can only be over quota if it was filled before then or through a path outside `envgroups`. The per-key `DeleteEnvGroupVar` / `DeleteEnvGroupFile` deletes are unaffected, so a workaround exists.
- **Found:** code triage during `w1/m147` t006, 2026-09-15. Reasoned from code; not probed live. No over-quota group is known to exist.

## Where

- `lego/backend/internal/envgroups/patch.go:186-189`: `secrets.ValidateEnvMapQuota(env)` / `secrets.ValidateFilesMapQuota(files)` run on the patched copies with no comparison against the pre-patch maps.
- The rule to reuse: `patchWithinQuota(before, after, within)` in `lego/backend/internal/secrets/batch.go`, which refuses only when the result is over quota **and** has more entries or bytes than before.

## Fix

- Export the helper from `secrets` (for example `ValidatePatchQuota(before, after, within)`).
- Call it at `envgroups/patch.go:186-189` with `oldEnv`/`env` and `oldFiles`/`files`.
- Extend `envgroups/quota_guard_test.go` with a pair of tests on a group seeded over quota: a delete succeeds, and an add is refused.
- Keep the refusal sentence unchanged, so the `w1/m147` adapter table still holds.
