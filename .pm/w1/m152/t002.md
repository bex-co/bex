## Objective

When a deploy is canceled and a prior successful release exists, the operator keeps or restores that release's image **and** configuration snapshot. A canceled `config_change` therefore rolls no pod and changes nothing a request can observe.

## Context

- `settleCanceledRelease` → `dispatchRuntime(ctx, app, app.Status.Image, port)` renders the **current** spec (`lego/operator/internal/controller/app_controller.go:621-648`).
- `Cancel` stamps `AnnotationCanceledReleaseGeneration` (`lego/backend/internal/deploys/service.go:716-723`).
- Live: the cancel at 15:28:47Z was followed by a new instance at 15:28:51Z serving the canceled value (m152 README § Evidence).

## Steps

1. **Settle from the last release.** In the canceled branch, dispatch from the last successful release's recorded identity (t001 snapshot) instead of the current spec. If the running Deployment already matches that identity, don't touch it.
2. **Leave the saved spec alone.** The canceled change stays saved; a later deploy ships it. Don't revert user intent, only what runs.
3. **Re-run the DoD probe.** Run m152 DoD bullets 1–2 live, twice.

## Acceptance criteria

- [ ] m152 DoD bullet 1 passes live: no instance is created after the cancel, and `curl` keeps serving the old value for 5 minutes.
- [ ] m152 DoD bullet 2 passes live: the value stays saved, and the next manual deploy ships it.

## Progress (2026-09-28, `/loopx w1`) — code shipped `1353244f1`, live acceptance pending deploy

The canceled branch now calls `settleConfigSnapshotTo(successfulReleaseGeneration(app))`
before dispatching the prior image, so image and configuration revert together; the saved
spec is left alone. The projection was re-keyed on `status.configSnapshotGeneration` alone
(t001 required it to equal `releaseGeneration`, which made an earlier generation
unreachable). A target with any source copy missing leaves the projection unchanged.

Unit tests in `release_config_snapshot_test.go`, mutation-checked. Both acceptance criteria
are live production checks, so this task stays open until `1353244f1` is deployed and DoD
bullets 1–2 are probed.

### Follow-up shipped `6383cf40e` — the first fix still rolled a pod

An envtest reproducing the filed defect end to end (serve generation 1; save, which
rewrites `<name>-env` and bumps `spec.restartedAt`; cancel before generation 2 reaches
the Deployment) failed on `1353244f1`: the template gained a new
`app.bex.co/restarted-at` annotation. Secrets are not the only thing a `config_change`
alters — restartedAt, start command, health-check path and plan all reach the template —
so re-projecting the saved spec still rolled a pod, just with the old values.

Every normal pass now records the template it applied as
`<name>-podtemplate-r<generation>`, and a pass settling a cancel over a served release
applies that record verbatim. When the Deployment already holds it, nothing is written and
nothing rolls. The envtest now passes and is mutation-checked.
