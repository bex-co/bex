## Objective

Every successful release records the exact runtime configuration it ran with: env values, secret files, linked group values and spec fields in release identity. That lets a cancel, or a restart of an old pod, bring back that release exactly instead of whatever the mutable Secrets now hold.

## Context

- Service env and files live in one mutable `<name>-env` / `<name>-files` Secret, rewritten in place on save (`lego/backend/internal/secrets/service.go:714-717`). Group Secrets `<evg>-env` / `<evg>-files` are likewise shared and rewritten (`lego/backend/internal/envgroups/service.go:653-657`).
- Release identity already hashes `envFromSecret`, `envFromSecrets`, `filesFromSecrets`, `restartedAt` and the commands (`lego/operator/internal/controller/release_identity.go`). It names the Secrets, not their contents.
- m152 README § Root cause and § Adjacent classes (old-release pods restarting read new values).

## Steps

1. **Design.** Choose the snapshot shape, e.g. immutable per-release Secret copies (`<name>-env-<release>`) referenced by the Deployment template, or a content digest in release identity plus a retained copy. Record the choice and the retention/GC policy in `docs/ADR004-app-deployment.md` (or ADR013).
2. **Snapshot at release time.** Operator or backend writes the snapshot when a release is dispatched, and the pod template references the snapshot, not the mutable Secret.
3. **Garbage-collect** snapshots beyond the releases rollback can reach. Keep the rollback window consistent with `w2/m10`.

## Files

## Acceptance criteria

- [ ] A running release's pods keep reading their release's values after a later save, including a pod that crash-restarts.
- [ ] The design, retention policy and secret-size budget are recorded in the ADR.
