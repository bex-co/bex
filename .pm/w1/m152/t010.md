## Objective

Prove the t002 snapshot-restore fix against a second config class — `healthCheckPath` (pod-template probe config, not the mutable env Secret) — whose canceled rollout demonstrably wedged a service in `Deploying` with a never-ready pod. After the fix, canceling a health-gated rollout must restore the last successful release's full pod template (old image AND no probe) and settle the phase to `Running`.

## Context

### The observation (production, 2026-09-17, `/qa-find-bugs` w4-targeted run)

Free web service `qa-20260917-p7-web` (`srv-dam2aih2dbts73fi25tg`), first deploy live. Setting **Health Check Path** to `/qa-bogus-health` (404s on the app) opened a `config_change` deploy whose new pod logged `listening` but never became ready — correct Render-parity gating (startupProbe budget 900s, `deployment_projection.go:131`). Canceling that stuck deploy at ~10:43:15 produced:

- a NEW pod (`[0fol6]`, 10:43:25) running the OLD image **with the canceled probe still projected** (revert re-dispatches old image against current spec — this milestone's exact mechanism, `app_controller.go:639-652`), never becoming ready;
- the service phase stuck at `Deploying` with zero in-flight work (deploys read `Canceled` over `Live`), still stuck 8+ minutes after the cancel at last observation — predicted to self-heal only at the 15-minute `progressDeadlineSeconds` via `settleFailedRollout` → `settlePriorRelease` (`app_controller.go:2849-2852,4541-4546`), unobserved this run;
- the pre-cancel old pod (`[4l5q5]`, probe-free) keeps serving 200 throughout, so the `Deploying` phase contradicts a healthy serving state;
- the never-ready revert pod has no deploy row — the same "pod rollout without a deploy row" violation the milestone DoD's third bullet already names.

The canceled change (bogus probe) demonstrably reached the running pods' template — the env-var case from filing day, in a second config class.

### Fix shape (already decided by t001/t002)

No new design: the release snapshot must capture the pod-template probe configuration (`healthCheckPath`, and the TCP-vs-HTTP mode it implies) alongside env/start/image, and the cancel path must restore the snapshot's template rather than re-projecting current spec. This task is the live proof, not the implementation.

### Acceptance

On a throwaway free web service with a live first deploy:

1. Set Health Check Path to a path that 404s; wait for the `config_change` deploy to sit `update_in_progress` with its new pod `listening` but unready.
2. Cancel the deploy.
3. Within 2 minutes of the cancel (not 15): service phase reads `Running`; exactly one pod exists and it serves traffic; no pod carries the canceled probe (prove by the rollout completing — a probe-carrying pod could never become ready);
4. The saved Health Check Path still reads `/qa-bogus-health` (saved-but-not-deployed, per the t003 truth surfaces); a later deploy ships it and gates honestly.
5. Delete the fixture.
