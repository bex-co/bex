## Objective

Confirm REST, GraphQL, MCP and the dashboard report the corrected phase consistently, and compare against Render's behavior for a service that never served.

## Files

- `docs/ADR018-render-parity.md`
- `.pm/w1/m160/README.md`

## Acceptance criteria

- [ ] The comparison is in the m160 README, and any divergence is recorded in ADR018.

## Out of scope

- Changes to Render-shaped response fields.

## Result (2026-09-28, `/loopx w1`)

Done. `phase` is not a Render field — Render's nearest equivalents are the deploy's
`status` and the service's `suspended` — so there is no Render behaviour to diverge from,
and no ADR018 row to add. It is an already-documented bex extension
(`apps/render.go:111-116`, "bex-native superset (ignored by Render clients)").

REST, GraphQL and MCP all serialize the same `renderService` from the one
`AppView.Phase`, and the dashboard reads the GraphQL field, so a corrected phase is
corrected on every surface at once and cannot drift without changing that field. Table
and the `omitempty` note are in the milestone README.
