## Objective

Enumerate every piece of correctness-relevant state bex-api holds in process memory, decide for each whether it must become shared/durable under two replicas or is acceptably per-replica, and write that contract down so t002–t004 implement against it.

## Context

- `.pm/FUTURE-MAYBE.md` names three: the deploy-hook rate limiter (`lego/backend/internal/deploys/deployhook.go:190` — token bucket), the outbound-webhook failure-notice suppression (`lego/backend/internal/webhooks/worker.go:160` — `emittedAt` map), and the outbound-webhook delivery worker itself (`worker.go:55` — two replicas double-deliver every event).
- bex-api runs two replicas in prod (w1/m52).

## Steps

1. Grep bex-api for in-memory maps/counters/timers that survive across a request but not across replicas.
2. Classify each: must-be-shared (affects externally-observable once-ness or rate), acceptably-per-replica (best-effort, idempotent, or bounded), or already-durable.
3. Record the inventory as a short table and confirm t002–t004 scope against it.

## Files

- `lego/backend/internal/webhooks/worker.go`

## Completion (2026-07-30) — the multi-replica contract

Swept bex-api for state that survives a request but not a replica
(`KeyedRateLimiter`, `sync.Mutex`/`sync.Map`, `TTLCache`). Inventory:

| Bucket | Location | Class | Reason |
| --- | --- | --- | --- |
| Outbound-webhook delivery (dispatch fan-out + send) | `webhooks/worker.go` (`dispatch`/`send`) | **must-be-shared** | two replicas each insert a delivery row per event (fresh ids ⇒ dup rows) and each POST the same due rows ⇒ double-delivery, externally observable |
| Failure-notice suppression (`emailedAt` map) | `webhooks/worker.go:165` | **must-be-shared** | a restart re-emails and the 2nd replica double-emails the "webhook failing/disabled" notice |
| Deploy-hook rate limiter | `deploys/deployhook.go` (`DeployHookRateLimiter`) | **acceptably-per-replica** | credential-gated endpoint whose action (trigger redeploy) is newest-wins idempotent; a 2× ceiling at two replicas is a bounded over-provision, not an abuse escalation. Same posture as the two limiters below ⇒ document, don't distribute (t004) |
| Main API limiter (`BEX_RATE_LIMIT`) | `api/ratelimit.go` | per-replica (out of m58 scope) | pre-existing accepted precedent; not one of the three named buckets |
| Device-flow limiter (`BEX_DEVICE_RATE_LIMIT`) | `cliauth/ratelimit.go` | per-replica (out of m58 scope) | same coarse-abuse-guard posture |
| Auth / tenancy / authz / apikey TTL caches | `api/auth.go`, `api/tenancy.go`, `authz`, `apikeys` | acceptably-per-replica | bounded-stale read caches; no once-ness or rate impact |
| Billing meter-event emitter | `billing`/`store` | already-durable | durable `emitted_at` outbox (ADR040), not in-memory |

**Contract for t002–t004:** the two webhook buckets move to the control-plane
Postgres store; the deploy-hook limiter stays per-replica with the reason
documented. No correctness-critical bucket is dropped — the two out-of-scope
limiters and the TTL caches are best-effort by design, and billing is already
durable.
