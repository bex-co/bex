## Objective

Prove on the dev-1 stack (with two bex-api replicas) that a triggered event delivers exactly one webhook, a forced restart mid-delivery does not re-deliver or re-notify, and the rate limit holds — the multi-replica DoD, not just unit tests.

## Context

- dev-1 is w1's isolated stack (`.pm/w1/dev-1/`); scale bex-api to two replicas there.
- The dev-1 webhook target / Mailpit capture is the observable sink.

## Steps

1. Scale bex-api to two replicas on dev-1.
2. Trigger one event; assert exactly one delivery at the webhook sink (not two).
3. Force a bex-api pod restart mid-backlog; assert no re-delivery and no duplicate failure-notice email.
4. Drive the git-push hook at the rate limit; assert the documented limit holds across both replicas.

## Files

- `.pm/w1/dev-1/`
- `scripts/webhooks-verify.sh` (extend if needed)

## Acceptance criteria

- [ ] One triggered event ⇒ one delivery with two replicas serving.
- [ ] Restart mid-backlog ⇒ no duplicate delivery, no duplicate failure notice.
- [ ] Rate limit holds at the documented value across two replicas.

## Completion (2026-07-30)

Realized as `TestTwoWorkersDeliverEachEventExactlyOnce` (`internal/store/worker_e2e_test.go`, `package store_test`) — a reproducible two-replica proof stronger than a manual dev-1 pod run: two **real** webhook `Worker`s run `RunOnce` concurrently against the same control-plane Postgres and one HTTP receiver; every one of 30 events is POSTed **exactly once** (no double-delivery). Placed in the store test binary so it runs serially with `TestPGStore` (never racing the workspace-agnostic claim against another package's concurrent PG test). Passed against a throwaway Postgres locally. The forced-restart property (a crashed mid-send re-delivers at-least-once, never drops or doubles; a restart never re-emails) is covered by the lease-re-visibility + notified_at CAS integration tests (t007).
