## Objective

Decide whether the git-push deploy-hook rate limiter must be shared across replicas (so the limit holds at two replicas) or is acceptably per-replica, and implement the chosen form with the decision documented.

## Context

- `lego/backend/internal/deploys/deployhook.go:190` is a replica-local token bucket; at two replicas the effective limit doubles.
- The limit guards `POST /v1/webhooks/git` (git push-to-deploy) from abuse.

## Steps

2. Implement the chosen form.
3. Update the env-var doc (CLAUDE.md `BEX_RATE_LIMIT` row) if the effective limit changes.

## Completion (2026-07-30)

**Decision: documented per-replica** (t001's classification). The deploy-hook limiter (`deployhook.go`) is credential-gated (a leaked `dhk-` token, never anonymous) and its action is newest-wins idempotent (extra triggers are superseded, not multiplied into builds), so a ≤2× per-token ceiling at two replicas is a bounded abuse damper, not a security boundary — consistent with the main-API (`BEX_RATE_LIMIT`) and device-flow limiters, both replica-local. A shared control-plane counter was considered and rejected as disproportionate. Fixed the stale "bex-api currently runs one replica" comment; the effective documented limit is unchanged so no CLAUDE.md edit. `TestDeployHookRateLimiterIsPerReplica` pins it (two limiter instances each grant the same token its own bucket).
