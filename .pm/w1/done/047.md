# 047 — The dashboard has no role-awareness, so tightened verbs render as controls that always fail

> **PROMOTED → `w9/m84`** (2026-08-17, `/pm-brainstorm` "what to do for w9"): materialized as the "Role-aware dashboard controls: disable-with-reason instead of always-fail" milestone. This note is retained for history and moved to `done/`.

From `w1/m68` t008 (Render parity). Not a security gap — the server is authoritative and refuses correctly. A UX gap, surfaced by m68 moving four verbs from `can_operate` to `can_create`.

## What is true today

- A **contributor** now gets 403 on: set pre-deploy command, set cron `command`, create a one-off job, deploy with `imageUrl`/`commitId`, and set Postgres statement-logging parameters.
- The dashboard renders those controls unconditionally. `dashboard/src/features/services/components/build-deploy-section.tsx` shows the pre-deploy command field to everyone; a `grep` for any client-side capability check (`canCreate`, `can_create`) finds **nothing** in `dashboard/src` outside a GraphQL document and a test comment.
- So the affected member sees an editable field, fills it in, saves, and gets an error toast. The refusal is correct and legible; discovering it by failing is not.

## Why it isn't m68's job

The dashboard has no capability plumbing to hook into — this is "introduce viewer-role-awareness to the dashboard", a cross-cutting feature (resolve the caller's role, expose it through the GraphQL surface the dashboard already queries, thread a `capabilities` context through the feature components), not a patch to one section. Building it inside a security-remediation milestone would have been scope creep, and building a one-off check just for the pre-deploy field would be the wrong shape.

## When to do it

Promote when the dashboard next gets substantial attention, or the first time a real workspace has non-admin members (today most workspaces are single-member admin, so the gap is latent). Pair it with:

- the same treatment for the other already-existing role boundaries the dashboard also ignores (`can_view_sensitive` on connection strings/env values, `can_manage_billing` on the billing surface, `can_manage` on members) — m68 did not create this class, it just added members to it;
- a decision on the pattern: hide vs. disable-with-reason. Disable-with-reason is better here — a hidden control makes the role model invisible, while "your role cannot change what this service runs" teaches it.
