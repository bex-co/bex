# bex-api's error response shape (`{"error": "string"}`) breaks every Render-spec client's error messages

`w9/m2`'s Render CLI walk found bex-api's error writer (`lego/backend/internal/core/http.go:63,66`, `WriteJSON(w, code, map[string]string{"error": err.Error()})`) emits `{"error": "<message>"}` on every 4xx/5xx, system-wide. Render's real contract (the CLI's generated `Error` type, `cli/pkg/client/types_gen.go:2120`) is a flat `{"id": "...", "message": "..."}` body. Because `{"error": "..."}` is still valid JSON, Go's `encoding/json` silently decodes it into a zero-value `Error{}` instead of erroring — so the CLI's error decoder (`cli/pkg/client/client.go`) never even reaches its raw-body fallback, and reports the generic `"unknown error"` for **every** bex-api error the CLI hits, discarding whatever real message bex-api sent. Confirmed via a logging proxy: the CLI printed `Error: unknown error` for a request bex-api actually rejected with a specific, useful message (`{"error":"bad request: unknown maxmemoryPolicy \"allkeys_lru\" ..."}`).

This is the single highest-impact, lowest-effort fix the whole CLI-compat exercise turned up: one response-writer shape change (`core.WriteJSON` error path → `{"id": ..., "message": ...}`) fixes error legibility for every current and future Render-spec client (this CLI, any SDK, custom agents), not just one command. Likely sub-hour; check whether the frontend dashboard or any other in-repo caller relies on the `{"error": ...}` shape before changing it wholesale (probably not, since the dashboard parses GraphQL errors separately).

Evidence + full repro harness: `docs/cli-compatibility-checklist.md` (root cause RC1).

Source: `w9/m2` (Render CLI compatibility), 2026-07-15.
