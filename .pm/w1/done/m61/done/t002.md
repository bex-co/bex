## Objective

`sandbox_tenant_keys` (migration 0054) has no FK to `tenants`, so a deleted workspace's OpenSandbox tenant key row survives forever and still resolves via `WorkspaceForSandboxKey` (`internal/store/sandboxtenants.go:78-93`) — a live credential row for a dead tenant. Add the FK with `ON DELETE CASCADE` and clear existing orphans.

## Context

- Table: `api_key text PRIMARY KEY, workspace_id text NOT NULL UNIQUE` — `workspace_id` should reference `tenants(id) ON DELETE CASCADE` like every other workspace-keyed table (cf. migration 0051).
- Prod may already hold orphaned rows (every workspace deleted since w3/m32 shipped); the up migration must delete them before adding the constraint or it fails validation.
- Next free migration number verified 2026-07-31: **0056**.

## Steps

1. `0056_sandbox_tenant_keys_fk.up.sql`: `DELETE FROM sandbox_tenant_keys WHERE workspace_id NOT IN (SELECT id FROM tenants);` then `ALTER TABLE sandbox_tenant_keys ADD CONSTRAINT sandbox_tenant_keys_workspace_fk FOREIGN KEY (workspace_id) REFERENCES tenants (id) ON DELETE CASCADE;`
2. `0056_sandbox_tenant_keys_fk.down.sql`: drop the constraint.
3. Store test (gated on `BEX_TEST_DB_URI`, runs for real in CI): mint a key, delete the tenant, assert `WorkspaceForSandboxKey` returns `ErrNotFound`.

## Out of scope

- Stopping the running sandboxes themselves (t003).
- Revoking the key at the OpenSandbox server side (the key is only honored via bex-api's tenant-lookup callback, which reads this table — the cascade is the revocation).
