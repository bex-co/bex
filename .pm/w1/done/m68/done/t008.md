## Objective

Check that this milestone's authorization and billing changes are consistent across every surface they reach — REST, GraphQL, MCP, and the dashboard — and compare the new role boundaries against render.com's own model, recording any deliberate divergence in the parity ledger rather than letting it drift silently.

## Context

t001, t002, and t004 change **authorization outcomes** on verbs tenants call: a contributor who could previously set a pre-deploy command, a cron command, a one-off job command, a deploy `imageUrl`/`commitId`, or Postgres logging parameters now receives 403; a recovery without a bound payment method now receives 402. Each change lands in a shared service method, so the surfaces should stay identical by construction — this task verifies that rather than assuming it.

The dashboard question is the substantive one: a contributor-role user who now gets 403 should not be shown a control that always fails. Check what the affected UI does with the refusal.

## Steps

1. For each corrected verb, confirm the refusal is identical in shape across REST (`params`/error dialect), GraphQL (`extensions`), and MCP (error text) — the shared `core.CodedError` mapping should give this for free.
2. Compare against Render's documented role model: does Render let its CONTRIBUTOR-equivalent role set a pre-deploy command, trigger a deploy with an image, or create a one-off job? Record the answer with a dated citation.
3. Update `docs/ADR018-render-parity.md` if bex now diverges deliberately — a stricter bex role boundary is a defensible divergence, but it must be a recorded one.
4. Check the dashboard's behavior for a contributor on the affected controls; if a control is now guaranteed to fail for that role, file the UI follow-up (do not build it here).
5. Update `docs/ADR024-members.md`'s role description if the contributor role's meaning has materially narrowed.
