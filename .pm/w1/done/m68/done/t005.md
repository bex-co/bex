## Objective

Close round-5 Finding 10 (medium): scheduled KeyValue backups write a full RDB plus a gzip copy plus an optional `age` copy into an `EmptyDir` with no `SizeLimit`, in containers with no ephemeral-storage requests or limits. A tenant controls both dataset size and compressibility, so a large instance can put a shared node under disk pressure and evict unrelated workloads.

## Context

- `lego/operator/internal/controller/keyvalue_backup.go:244-248` — `EmptyDir: &corev1.EmptyDirVolumeSource{}`, no `SizeLimit`. The containers use `guaranteedResources("50m", "128Mi")`, which sets CPU and memory only.
- `lego/operator/internal/controller/database_exports.go:270-284` — the sibling that already does this correctly, with a 20 GiB work-volume limit. Copy that pattern rather than inventing one.
- `deploy/gitops/base/tenant-quotas.yaml:12-45` — the per-tenant `ResourceQuota` does not bound ephemeral storage either, so there is no second layer catching this.
- Bounds that already exist and limit the blast radius: paid-plan-only, a 15-minute `activeDeadlineSeconds`, and `ForbidConcurrent` per instance (so the concern is aggregate concurrency across instances, not one runaway job).

## Steps

1. Derive the `SizeLimit` from the largest KeyValue plan's dataset size plus headroom for the simultaneous representations the pipeline holds (RDB + `.gz` + optionally `.gz.age`) — the multiplier is the part worth writing down in a comment, because it is what a future plan-size change has to revisit.
2. Set the `SizeLimit` on the backup `EmptyDir` and add ephemeral-storage requests and limits to every container in the Job (including the `age` stage, `keyValueBackupAgeImage`).
3. Confirm the failure mode is the one intended: exceeding the volume limit should fail that Job (evicting the backup pod only), not the Valkey instance and not a neighbor.
4. Consider adding `ephemeral-storage` to the tenant `ResourceQuota` as the second layer; if it would break existing workloads, note it for `w1/046.md` rather than shipping it blind.

## Acceptance criteria

- [ ] Generated backup Jobs carry a bounded `EmptyDir` with a documented derivation for the number.

- [ ] A backup that exceeds the bound fails within its own Job; the Valkey pod and co-scheduled pods are unaffected.
