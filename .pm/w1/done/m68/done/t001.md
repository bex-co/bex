## Objective

Close round-5 Finding 2 (high): four verbs still authorize on `core.RelCanOperate` while selecting the code a workload runs. A workspace **contributor** — a role meant for lifecycle operations, not code — can persist a shell command or swap an image and get arbitrary execution with the service's secrets and network identity. Upgrade exactly the parameter-bearing paths to `core.RelCanCreate`, leaving parameter-free lifecycle intact.

## Context

The previous round already fixed this class **partially**, which is why the remaining sites are easy to misread as intentional. `apps/service.go:2854` carries the precedent comment:

> `SECURITY (codex #1): build/start commands are attacker-chosen code the service executes with its runtime identity, so this is create-like, not lifecycle — gate on can_create (developer and up), not can_operate.`

That reasoning was applied to `SetCommands`, `SetSource`, `SetSourceAndRegistryCredential`, `agentsessions.Create`, and `agentsessions.Steer`. It was not applied to:

- `lego/backend/internal/apps/service.go:2833` — `SetPreDeployCommand`; the command runs to completion against the new revision's image with the service's env/secret projections (`lego/operator/internal/predeploy/predeploy.go:140-153`).
- `lego/backend/internal/apps/service.go:3028` — `SetCronJob`; takes `schedule` **and** `command`. Only the command is create-like — a schedule-only change is genuinely lifecycle and must stay available to contributors. Both args are `*string`, so the distinction is already expressible.
- `lego/backend/internal/jobs/service.go:174` — `Create`; runs a caller-supplied `startCommand` in the service's current image.
- `lego/backend/internal/deploys/service.go:400` — `Trigger`; `p.ImageURL` / `p.CommitID` select new executable content. A **bare** trigger (no params) is a redeploy of the already-approved artifact and must remain `can_operate` — this is the one site needing a conditional relation, not a blanket upgrade.

Role ladder (`deploy/gitops/authz/model.fga:67-71`): `can_operate: contributor or developer or admin`; `can_create: developer or admin`. Contributors hold `can_operate` and `can_view_logs`, not `can_create` or `can_view_sensitive`.

`lego/backend/internal/api/roleladder_test.go:319-332` is the policy table — `*deploys.Service.Trigger` is currently pinned there as `RelCanOperate`, so that pin has to move with the code (and express the conditional case honestly).

## Steps

1. `SetPreDeployCommand` and `jobs.Service.Create` → `core.RelCanCreate`, each with a one-line SECURITY comment citing this finding, matching the `codex #1` precedent's shape.
2. `SetCronJob` → authorize `RelCanCreate` when `command != nil`, `RelCanOperate` when only `schedule` is supplied. Prefer resolving the relation once before the fetch over two fetch paths.
3. `deploys.Service.Trigger` → `RelCanCreate` when `p.ImageURL != ""` or `p.CommitID != ""`, else `RelCanOperate`. Leave `triggerFetched` and the deploy-hook path untouched — the hook is a separate authentication boundary already minted behind `can_view_sensitive`.
4. Update `representativeVerbRelations` so each corrected method is pinned, and record the two conditional verbs in a way the table can express (a second entry or an explicit comment — do not silently drop them from the policy table).
5. Re-read the sibling setters in `apps/service.go` once more for any fifth instance of the class; if one exists, fix it here rather than filing it.

- [ ] A contributor is refused on: set pre-deploy command, set cron **command**, create a one-off job, trigger with `imageUrl`, trigger with `commitId`.
- [ ] A contributor still succeeds on: a bare deploy trigger, and a cron **schedule-only** update.
- [ ] A developer and an admin succeed on all of the above.
- [ ] Refusals are identical across REST, GraphQL, and MCP (they share the service method, so assert at least one non-REST surface to prove it).
- [ ] `representativeVerbRelations` pins every corrected method, and the conditional relations are legible in the table rather than absent.
