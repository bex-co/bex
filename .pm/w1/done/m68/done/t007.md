> **Status 2026-08-10:** bex-api now warns loudly on every start where `BEX_OAUTH_RESOURCE` is set and the flag is off, and ADR012 §7 carries the 4-step activation procedure. **Remaining: steps 1–4** — confirm the LIVE Hydra records for the CLI + mobile clients carry `bex.co/platform-client`, re-stamp if not, then flip to `"1"`. Not done blind: the reverse order refuses the official CLI's logins.

## Objective

Close round-5 Finding 1 (high) by performing the activation `w1/m67/t001` deliberately deferred. The audience-discipline mechanism is built, tested, and shipped **off**; until it is on, a human token minted for any self-registered (DCR) OAuth client that the victim consents to carries that user's full workspace authority across REST, GraphQL, and MCP.

## Context

- `lego/backend/internal/api/auth.go:409-418` — the empty-`aud` rejection for human subjects is conditional on `a.requireAudience`. Machine (`client_credentials`) tokens keep the exception unconditionally by design. A failed platform-client lookup fails closed (503), never a silent downgrade.
- `lego/operator/config/api/deployment.yaml:117-119` — ships `BEX_OAUTH_REQUIRE_AUDIENCE: "0"`, with the activation order spelled out in the surrounding comment.
- `scripts/auth-bootstrap-client.sh:166` and `:195` — **verified 2026-08-10:** both the Render CLI client and the bex-mobile client already carry `"metadata":{"bex.co/platform-client":true}` in their registration bodies. So the script is correct as written; what is unproven is whether the **live** Hydra records carry the marker (they predate the script change).
- `deploy/gitops/base/values/hydra.values.yaml:63-68` — dynamic client registration is enabled, which is what makes the exception reachable by an arbitrary third party.
- Activation order matters and is one-directional: flipping the flag before the live clients carry the marker refuses the official CLI's device-flow logins, which legitimately request no audience.

## Steps

1. Inspect the live Hydra client records for the CLI and mobile clients and confirm whether `bex.co/platform-client` is present. Do not assume the script has been re-run since it gained the marker.
2. If absent, re-run `scripts/auth-bootstrap-client.sh` against production and re-confirm.
3. Only then set `BEX_OAUTH_REQUIRE_AUDIENCE: "1"` in `lego/operator/config/api/deployment.yaml` and deploy.
4. Verify after rollout: the official `render` CLI can still log in via device flow; bex-mobile can still authenticate; a token with the canonical `BEX_OAUTH_RESOURCE` audience succeeds; an audience-less human token from an unmarked client is refused.
5. Update `docs/ADR012-auth.md` §7 to record that activation happened, and consider making the rule secure-by-default (derive from `BEX_OAUTH_RESOURCE` being set) so a future environment cannot ship it off — propose it here even if the change lands later.
