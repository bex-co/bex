## Objective

Close round-5 Finding 7 (medium): a contributor can set `log_statement=all` on a managed Postgres and then read the resulting SQL text — including literal passwords, tokens, and personal data — through the log API. `ExecuteQuery` and the top-query/process views correctly reserve that data for `can_view_sensitive`; a parameter write under `can_operate` manufactures the same disclosure by another route.

## Context

- `lego/backend/internal/postgres/service.go:778-790` — `normalizeParameterOverrides` drops exactly one key, `shared_preload_libraries` (because the operator always sets it). Every other key, including the whole `log_*` family, passes through verbatim.
- `lego/backend/internal/postgres/service.go:800` — `UpdatePostgres` fetches with `core.RelCanOperate`; `SetParameterOverrides` (`insights.go:371`) is a thin wrapper over it, so both reach the write with contributor rights.
- `lego/operator/internal/controller/database_controller.go:336-353` — the operator copies `spec.parameters` into the CNPG cluster's `postgresql.parameters`.
- `deploy/gitops/authz/model.fga:67-71` — `can_view_logs` includes contributor; `can_view_sensitive` does not. That asymmetry is the whole finding.
- `lego/backend/internal/postgres/insights_test.go:81-93` already asserts `log_statement=all` survives normalization — so the fix must update that expectation deliberately, not accidentally.

Same authorization class as t001 (a `can_operate` write that yields something the ladder reserves for a stronger relation), which is why it follows it — apply a consistent rationale and comment style.

## Steps

1. Decide the gate shape and record why in a comment. An allowlist of known-safe performance parameters is the strongest form but risks refusing legitimate tuning; classifying the confidentiality-affecting keys (`log_statement`, `log_min_error_statement`, `log_min_duration_statement`, `log_duration`, and any sibling that emits statement text) and requiring `can_view_sensitive` for those is the narrower change. Prefer the narrower one unless the safe set proves small and enumerable.
2. Enforce at the service boundary so REST, GraphQL, and MCP inherit it; do not enforce in the operator (a CR written directly is a different trust boundary, already covered by ADR043 namespace isolation).
3. Update `insights_test.go:81-93` to assert the new refusal, and add the positive case that a safe tuning parameter still round-trips.
4. Check whether KeyValue has an equivalent parameter-override surface with the same shape; if it does, fix it here.

## Acceptance criteria

- [ ] A contributor cannot enable statement or error-statement logging through `SetParameterOverrides` or the general Postgres update.
- [ ] A developer/admin can (or the parameter is refused for everyone — whichever the chosen shape decides, asserted explicitly rather than left implicit).
- [ ] Safe performance parameters remain writable by the roles that could write them before.
- [ ] The existing test that pinned the vulnerable behavior is updated to pin the fix.

## Out of scope

- Redacting database log message content generally — a larger change, and the disclosure is closed at the source here.
- Auditing the full PostgreSQL GUC surface for other confidentiality-affecting settings beyond the logging family; note anything found for `w1/046.md`.
