## Objective

With GraphQL emitting `srv-` ids, the dashboard's service URLs become `/services/srv-…` automatically (navigation builds from the returned `id`) — sweep everything downstream for id≠name assumptions so the flip lands clean, and verify the m45 `/web/{srv-id}` alias deep-links are now id-consistent end to end.

## Context

- URL builders already pass `service.id` (`resource-table.tsx:108`, `service-detail-header.tsx`, `services.new.tsx` post-create navigate, `manual-deploy-button.tsx`) — these inherit the new id.
- Places to check for id-as-name assumptions: the detail header's "Service ID:" display (becomes the srv- id — Render's own display; the name stays as the heading/slug), the slug row, SSH command hints (`ssh <service>@…`? — the gateway addresses instances by Render-compatible instance ids derived from srv-, docs/ADR035-ssh.md), the logs SSE `service=` param (REST side accepts both shapes via the same seam — verify), search/filtering that matches on id, and anything string-comparing `id === name`.
- `services.new.tsx:662` navigates with `result.id` — confirm the create mutation returns the srv- id post-t001.
- The stale-URL case: a user's bookmarked `/services/whoami/logs` still resolves (t003's fallback) but in-app navigation should never mint name URLs anymore.

## Steps
