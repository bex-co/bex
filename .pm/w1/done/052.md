# 052 — Build-Job name derivation forks between backend and operator above 63 chars

From the 2026-08-19 architecture survey ([Bex Refactor Ledger](https://claude.ai/code/artifact/5ceae798-6df1-4f3c-94b6-6b1126f640c2) §0). The backend's `buildJobName` (`lego/backend/internal/deploys/service.go:196-203`) truncates `bld-<name>-gen-<generation>` with a **plain slice** `n[:63]`, while the operator's `JobName` (`lego/operator/internal/build/build.go:1031-1041`) truncates via the **hash-suffixed** `stableKubernetesName` (`build.go:1047-1056`). The backend comment at `deploys/service.go:191-195` says "mirrors … exactly … keep the two in sync by hand" — it doesn't: any App whose derived name exceeds 63 chars gets two different Job names, so deploy **Cancel** and built-image lookup (`deploys/service.go:634,645`) target a Job the operator never created.

**Fix.** Make the backend derive the name identically to the operator (the operator creates the Job, so its algorithm is authoritative). Preferred: move the hash-truncating derivation into `lego/types` (both modules already import it) and call it from both sides; acceptable minimum: replicate the algorithm in the backend with golden-vector tests pinning both modules to identical outputs (a shared test can't import across the module boundary, so pin against fixed vectors).

**Also check while there:** the pre-deploy pair — `lego/operator/internal/predeploy/predeploy.go:129-134` uses a plain slice; verify the backend's predeploy log reads (`type=predeploy`) derive the same name for long App names, and align if forked.

**Acceptance:** a regression test with an App name long enough that `bld-<name>-gen-<n>` exceeds 63 chars, asserting the backend-computed and operator-computed Job names are equal (via shared helper or golden vectors); Cancel path exercised in an existing test with the long name.
