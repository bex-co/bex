# Bare-name resource ids block the Render CLI's client-side resource-type routing — needs a design decision, not a quick fix

`w9/m2`'s Render CLI walk found that `restart`/`ssh`/`psql`/`kv-cli`/`pgcli` (any `render-oss/cli` command that infers a resource's type from its id's prefix, `cli/pkg/resource/service.go`) fail on **every** bex resource id: `Error: failed to restart resource: unknown resource type`. Root cause is architectural, not a bug — `docs/ADR020-identifiers.md` §Known deviations deliberately uses the user-chosen name as the id for managed datastores (Postgres/KeyValue), and Services follow the same unminted-id pattern (`a.Name = req.Name`, `lego/backend/internal/apps/service.go`). Render's real ids all carry a type prefix (`srv-`, `dpg-`, `red-`, …); bex's carry none, so the CLI has nothing to switch on.

This is bigger than a sub-hour fix and reopens a settled ADR — **do not just implement something**, size and design it properly (or explicitly decide it's not worth reversing ADR020 for CLI compatibility alone) before promoting to a milestone. Options worth weighing: mint real typed ids after all (reverses ADR020, likely a larger migration than it looks given every REST/GraphQL/MCP caller and the dashboard currently key off the bare name); or accept the CLI's `restart`/`ssh`/`psql`/`kv-cli`/`pgcli` stay permanently `✖` against bex as a documented, deliberate divergence.

Evidence + full repro harness: `docs/cli-compatibility-checklist.md` (root cause RC5).

Source: `w9/m2` (Render CLI compatibility), 2026-07-15.
