## Objective

Close the user-visible gap: the untiered legacy apps (bare CRs created before the control plane — prod's `beancount-cms` is the known case) get a tier via the new plan verb, and the payoff is proven live — pods carry requests==limits and the metrics page's Percentage tab shows 0–100 charts with a "Limit …" label where it said "No limit configured — percentage is undefined".

## Context

- **Store-managed apps need nothing here** — `normalizeTier` already defaults empty→`free` and the projector already writes `spec.tier` (`reconciler.go:184,211`). The gap is exactly the apps with no row.
- Fix mechanism: the t003 plan-change verb (CR-patch path) — no migration/backfill machinery needed. Survey untiered apps first (`kubectl get apps.app.bex.co -A -o custom-columns=NAME:.metadata.name,TIER:.spec.tier`).
- Tier choice for `beancount-cms`: pick by its observed usage (w3/m4.5 showed ~420MiB working set — `free`/`starter` at 512Mi is tight; `standard` 2Gi is the safe call). Setting it rolls the pod once.
- Verification: after the roll, `kubectl get pod -o yaml` shows requests==limits; the prod (or tunnel-dev) metrics page shows Percentage charts + "Limit …" label; the `*_LIMIT` metrics need no changes (they read pod-spec limits).
- Docs: `docs/control-plane.md` §Tiers table becomes a pointer to `lego/types/tiers/tiers.yaml` (keep the prose, drop the duplicated numbers); `docs/observability.md`'s no-limit deviation note now applies only to untiered bare-CR apps. Prettier after.

## Steps

2. Verify live: pod limits present; metrics page Percentage tab + limit label rendering real values.
