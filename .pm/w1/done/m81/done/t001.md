## Objective

Make the dashboard's "Add a custom domain" dialog show the server's error when
`addCustomDomain` is rejected, instead of silently sitting open. Today a
server-side rejection is completely invisible to the user.

## Context

- Confirmed in the 2026-08-19 QA walk. Repro: a service → Settings → Custom
  Domains → "Add Custom Domain" → enter `*.example.com` → "Add Domain".
- The domain passes the dialog's client-side regex, so the mutation fires. The
  API correctly rejects it: `POST https://api.bex.co/graphql` (operation
  `AddCustomDomain`) returns HTTP 200 with
  `errors: [{ message: "bad request: wildcard hostnames are not allowed: \"*.example.com\"" }]`.
- The dialog stays open with the button re-enabled and **no toast, no inline
  error** — the user cannot tell it failed or why. (Screenshot:
  `.playwright-mcp/domain-wildcard-no-error.png`.)
- Root cause: the dialog's mutation handler only renders its own client-side
  validation state; it does not read/surface the GraphQL `errors[]` array on the
  `addCustomDomain` response/rejection.
- Contrast — the webhook create form already does this right: a userinfo URL is
  rejected with an inline "Enter an absolute HTTPS URL without embedded
  credentials" plus a summary alert. Mirror that pattern here.
- This must cover **all** server rejections of `addCustomDomain`, not just
  wildcards: apex/PSL-rejected hostnames, a domain already claimed by another
  workspace, etc. — all currently fail silently.

## Steps

1. Find the custom-domain add dialog component under `dashboard/src` (search for
   `addCustomDomain` / "Add a custom domain" / the `AddCustomDomain` operation).
2. Capture the mutation error (Apollo `onError` / caught rejection / `errors[]`)
   and render it — inline under the Name field and/or a dialog-level alert, and
   keep the dialog open with the button re-enabled so the user can correct and
   retry. Reuse the webhook form's error-display pattern/component for
   consistency.
3. Strip any redundant server-error prefix for readability if the webhook form
   does (e.g. `bad request: `), matching that precedent.
4. Verify on dev-1 (or against the running API) that a wildcard and a second
   distinct rejection both now surface a visible message.

## Files

- `dashboard/src/**` — the custom-domain add dialog component and any shared
  form-error primitive it should reuse (the one the webhook create form uses).

## Acceptance criteria

- [ ] Submitting `*.example.com` shows the API's rejection message to the user
      (inline or toast); the dialog stays open for correction.
- [ ] A second, non-wildcard server rejection of `addCustomDomain` also surfaces
      a visible message (proves the fix reads `errors[]` generically, not a
      wildcard special-case).
- [ ] A valid domain still succeeds and closes the dialog / shows DNS records as
      before (no regression to the happy path).

## Out of scope

- Adding new server-side domain validation rules (the API already rejects
  correctly; this task is purely about surfacing the existing error).
- The other three QA findings (separate tasks t002–t004).
