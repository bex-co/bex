## Objective

Make an environment-variable change that rolls a new revision discoverable where
a customer looks for it — the service's Deploys list — matching Render, or
explicitly confirm and document that bex intentionally surfaces it only on
Events.

## Context

- Observed in the 2026-08-19 QA walk: saving an env var on a service bumped the
  revision `rev-1 → rev-2` and rolled new pods, and it appears on the **Events**
  timeline as "Environment configuration changed" — but the **Deploys** tab
  still showed only "1 deploy" (the original), with no entry for the
  env-triggered rollout.
- On Render, a configuration change that triggers a new deploy produces a deploy
  record with a trigger reason. bex's rollout happened (revision advanced) but
  left no deploy row.
- Decide the correct behavior first, then implement:
  - If an env change **should** create a deploy record (Render parity), find why
    the rollout doesn't produce one the Deploys reader returns, and fix the
    producer/reader so it appears with an accurate trigger label.
  - If bex deliberately models env changes as config events (not deploys), that
    is a Render-parity divergence — record it in `docs/ADR018-render-parity.md`
    and confirm the Events surfacing is the intended, sufficient answer.
- Check consistency across REST/GraphQL/MCP deploy-list reads, not just the UI
  (the dashboard reads the same core deploy list).

## Steps

1. Reproduce: edit an env var on a service, watch revision advance, then load
   the Deploys tab and the REST/GraphQL deploy list.
2. Determine the intended model (Render behavior vs bex's deploy/event split in
   `internal/apps` / deploys feature). Cite the evidence.
3. Implement the chosen resolution: either surface the env-triggered rollout in
   the deploy list (all surfaces) with a correct trigger, or document the
   intentional divergence in ADR018 and leave Events as the surface.

## Files

- `lego/backend/internal/**` (deploys/apps feature) if the deploy list should
  include the rollout; and/or `dashboard/src/**` for the Deploys view.
- `docs/ADR018-render-parity.md` if the outcome is a documented divergence.

## Acceptance criteria

- [ ] After an env-var save that rolls a revision, the rollout is discoverable in
      the Deploys list (matching Render) **or** ADR018 records the intentional
      Events-only divergence with rationale.
- [ ] Whatever the outcome, REST, GraphQL, MCP, and the dashboard agree (no
      surface shows it where another hides it inconsistently).

## Out of scope

- Redesigning the Events/Deploys consolidation (that shipped in w1/m47); this is
  only about the missing env-triggered rollout entry.
