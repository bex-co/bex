## Objective

Stop the free-tier create and scaling surfaces from letting a customer build and
submit a request the plan cannot honor. Give immediate client-side feedback
against the plan's limits, consistent with how the API enforces them.

## Context

- Observed in the 2026-08-19 QA walk:
  - **New Postgres** on the Free plan (advertised "256 MB RAM, 0.1 CPU, 1 GB")
    accepts a **9999 GB** disk size and enables "Create database" with no
    client-side validation.
  - The **web-service Scaling** control offers a manual-instances slider up to
    **100** with no plan-based cap shown, even on a Free service (Free is
    single-instance).
- Not confirmed whether the server rejects these (the QA walk deliberately did
  not submit, to avoid provisioning). First establish the server's actual
  limits, then make the client agree so the user never assembles a silently
  invalid request — and if the server rejection path is reached, ensure its
  error surfaces (same class as t001).
- Plan limits live in the shared plan/tier catalog (`lego/types/tiers/tiers.yaml`
  and the pricing/plan surfaces); the dashboard should derive caps from the
  selected plan rather than hard-code them.

## Steps

1. Determine the real per-plan caps the API enforces for Postgres disk size and
   service instance count (free vs paid) from the tier catalog / service-layer
   validation.
2. In the New Postgres dialog, bound/validate the disk-size field against the
   selected instance type (min/max, and disable/annotate Create when out of
   range) rather than accepting arbitrary values.
3. In the Scaling control, cap the manual-instances max (and/or annotate) to what
   the selected plan allows, so a Free service can't request 100 instances in the
   UI.
4. Confirm the API's own rejection (if a request still reaches it) is surfaced,
   not swallowed (align with t001's error-surfacing pattern).

## Files

- `dashboard/src/**` — New Postgres create dialog and the service Scaling
  component; the plan/tier catalog accessor they should read caps from.

## Acceptance criteria

- [ ] The Free Postgres create form rejects/blocks an out-of-range disk size
      (e.g. 9999 GB) before submit, driven by the selected plan's real limit.
- [ ] The Scaling control does not offer more instances than the selected plan
      permits (or clearly warns and blocks submit).
- [ ] Caps are derived from the plan/tier catalog, not hard-coded, so they track
      the server's limits.

## Out of scope

- Changing the actual plan limits or pricing; this is UI validation parity with
  existing server enforcement.
