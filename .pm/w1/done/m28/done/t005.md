## Objective

Make `deploy.yml`'s `build-and-deploy` job depend on the new test workflows passing — since this repo pushes directly to `main` (per the `/ship` workflow, no PR gate), the enforcement point has to be inside the triggered workflow run itself, not branch-protection required-checks (which only bind PR merges, not direct pushes).

## Context

- `deploy.yml` currently has one job, `build-and-deploy`, triggered on `push: branches: [main]` with `paths: ["lego/**", "dashboard/**", "deploy/gitops/**", ...]`.
- GitHub Actions can't `needs:` a job in a *different* workflow file directly — either (a) fold the test jobs into `deploy.yml` itself as prerequisite jobs `build-and-deploy` depends on via `needs:`, or (b) use `workflow_call` to invoke the test workflows as reusable workflows from within `deploy.yml` and gate on their result. Pick whichever keeps the existing per-module workflow files most usable standalone (e.g. for a PR that doesn't push to main) — likely (b), calling the already-built t001-t003 workflows as reusable jobs.

## Steps

1. Convert `go-test-backend.yml`/`go-test-operator.yml`/`dashboard-test.yml` to `workflow_call`-triggered reusable workflows (in addition to keeping their own `push`/`pull_request` triggers, if GitHub Actions syntax allows both — check current Actions support).
2. In `deploy.yml`, add jobs that call each relevant reusable workflow (path-filtered the same way `build-and-deploy` already is per component), and make `build-and-deploy` `needs:` them.
3. Confirm a test failure in any called workflow blocks `build-and-deploy` from running.

## Files

- `.github/workflows/deploy.yml`
- `.github/workflows/go-test-backend.yml`, `go-test-operator.yml`, `dashboard-test.yml`

## Acceptance criteria

- [ ] `build-and-deploy` does not run (or fails before building/pushing) when a gated test workflow fails.

## Out of scope

- Branch protection rules (moot given direct-push-to-main is this repo's actual practice).
