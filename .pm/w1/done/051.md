# 051 — The second MCP fold: the per-field `update_*` / `rename_*` tools

> **Promoted and completed 2026-08-18 as `w1/m74`** (see `done/m74/`). The three questions below were answered from REST's own shape rather than by fresh judgement: fold what `PATCH` carries, keep what has its own route. 12 tools retired, **187 → 175**. The note is kept as the record of what prompted it.

`w1/m71` folded the 34-tool `set_*` grammar into five patch-shaped `update_*` tools and took the MCP surface from 213 to 187. It deliberately stopped at the `set_` prefix. What is left behind is the **same per-field grammar wearing a different prefix**, and it is now the largest remaining source of one-tool-per-field on the agent surface.

## The candidates (measured at 187 tools)

| resource | per-field tools that could fold | fold target |
| --- | --- | --- |
| service | `update_service_plan` (has `dryRun`), `scale_service`, `update_idle_timeout`, `update_publish_path`, `update_static_routes`, `update_static_headers`, `update_cron_job` | `update_service` |
| postgres | `update_postgres_plan` (`dryRun`), `update_postgres_version`, `update_postgres_disk_autoscaling`, `rename_postgres` | `update_postgres` (its `PostgresPatch` already carries every one of these fields) |
| key value | `update_key_value_plan` (`dryRun`), `rename_key_value` | `update_key_value` (same — `KeyValuePatch` already carries them) |
| project / environment | `rename_project`, `rename_environment` | `update_project` / `update_environment`, which already take `name` |

That is roughly **15 tools for ~4 fold targets that already exist**, so the reduction is about the same size as m71's without needing a single new tool.

## Why m71 did not do it

Scope: the milestone's definition of done was written around the `set_*` family and its DoD quantified the delta ("roughly 28"). Folding twice as much under that heading would have made the milestone's own acceptance unverifiable. `w1/m71/t008` records it as out of scope.

## What makes this one harder than m71

Not the mechanics — the mechanics are identical — but three real questions:

1. **`dryRun` semantics.** Three of the candidates carry `dryRun`, and the patch tools already accept it for datastores. On `update_service` there is no dry run today, and REST's `patchService` previews **only** a plan change (`f.plan == ""` ⇒ plain read). Folding `update_service_plan` means deciding what `dryRun` means for a multi-field service patch, which is a contract decision, not a rename.
2. **Plan changes are billing events.** `SetPlan` runs payment/billing gates the other setters do not. Making a plan change one optional argument among twenty makes it easier for an agent to change a plan while meaning to change something else. Worth an explicit deliberation, possibly a distinct required confirmation.
3. **`update_cron_job` is a name upstream once shipped.** m70's pin classifies it `Extension` today because upstream REMOVED its placeholder in #89 — but bex's description advertises "Render ships a non-functional stub for this tool; bex makes it real". Retiring the name loses that positioning; keeping it costs a tool. A decision, not an oversight.

## Also worth folding into that pass

- **Allowlist spelling across surfaces.** m71 standardized MCP on `ipAllowList` (entries) + `ipAllowListCidrs` (strings). GraphQL still spells the same pair `entries`/`cidrs` on the datastores and `ipAllowListEntries`/`ipAllowList` on environments. REST is Render-shaped and must not move, but the two bex-owned surfaces disagreeing with each other is drift bex chose, not drift Render imposed.
- **The four surviving `set_*` upserts** (`set_env_var`, `set_secret_file`, `set_env_group_var`, `set_env_group_secret_file`) are correctly standalone (merge-one-key, paired with `delete_*`), but their names now read as leftovers of a grammar that no longer exists. A `put_env_var`-style rename would say what they do; it is cosmetic and should ride a pass that is already touching the ledger.

## Sizing

One milestone, roughly m71's shape: a grammar task that answers the three questions above, two fold tasks, a ledger/deprecation task, parity, simplify, tests, closeout. The guard (`TestMCPParityInventory`) and the deprecation-ledger precedent (`docs/render-artifacts/mcp-setter-fold-2026-08-18.md`) both already exist, so the supporting machinery is free this time.
