## Objective

Stop bex-api from serving traffic for the entire termination grace period after a SIGTERM — today `ctrl.SetupSignalHandler()` cancels the context every background loop hangs off, but `main`'s last statement blocks on `log.Fatal(httpSrv.ListenAndServe())`, which never returns on a signal.

## Context

- `lego/backend/cmd/api/main.go:77` installs the signal handler; the blocking `ListenAndServe()` call is around line 393 (per `.pm/w1/019.md`'s original finding — re-locate exactly, line numbers may have shifted).
- Two servers need this fix: the public HTTP server, and the `BEX_CP_ADDR` internal control-plane API server (which already has an `ErrServerClosed` check — a hint that graceful shutdown was intended there but never wired to actually call `Shutdown`).
- Discovered while writing `scripts/events-verify.sh` (`w3/m7`) — stopping the host bex-api needed a SIGKILL backstop.

## Steps

1. Change `main.go` to run `httpSrv.ListenAndServe()` in a goroutine (logging/handling `http.ErrServerClosed` as expected, not fatal).
2. After starting the goroutine, `<-ctx.Done()`, then call `httpSrv.Shutdown(timeoutCtx)` with a reasonable timeout.
3. Apply the same pattern to the `BEX_CP_ADDR` server if it isn't already fully wired.
4. Confirm all background loops (projector, usage compaction, audit retention sweep) still stop cleanly on the same signal — don't regress their existing shutdown behavior while fixing the HTTP server.

## Files

- `lego/backend/cmd/api/main.go`

## Acceptance criteria

- [x] `ListenAndServe`/internal-API server no longer blocks `main` past a SIGTERM.
- [x] Existing background-loop shutdown behavior is unchanged.

## Result

Added `serveUntilShutdown(ctx, *http.Server) error` in `lego/backend/cmd/api/main.go`: runs `ListenAndServe` in a goroutine, `select`s on the serve error vs `ctx.Done()`, and on cancel calls `srv.Shutdown` with a 10s bounded timeout. Both servers use it — the public API server (was the blocking `log.Fatal(httpSrv.ListenAndServe())`) and the `BEX_CP_ADDR` internal server (was a goroutine with an `ErrServerClosed` check but no `Shutdown`). The background loops (projector, usage compaction, audit sweep) still stop on the same cancelled `ctx` — unchanged. Grace-period duration (`terminationGracePeriodSeconds`) untouched, per scope.

## Out of scope

- Changing the grace-period duration itself (`terminationGracePeriodSeconds` in the Deployment spec) — this task fixes the process's own responsiveness to the signal, not the k8s-side timeout.
