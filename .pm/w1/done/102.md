# 102 — A WebSocket on which only the client sends messages does not keep a free web service awake

> **Promoted 2026-09-15 → `w1/m161`** by user decision during the w1 triage. The milestone carries the fix, its tests and its live verification.

Why: Render counts "WebSocket messages from existing connections" as inbound traffic that keeps a free web service from spinning down. `w1/m151` reads bex's WebSocket activity from the `websocketegress` Traefik plugin, whose `bex_websocket_egress_bytes_total{app_id}` counter measures **server→client** frame bytes only. A connection where the client sends messages but the service never replies (a telemetry sink, for example), with no new HTTP requests, therefore reads as idle, and the service sleeps after its window.

- **Severity:** minor. Most WebSocket apps send server→client frames (replies, pings, pushes), and any HTTP request also counts.
- **Found:** `w1/m151` t002, 2026-09-14, from the plugin source. Not probed live.

## Where

- `deploy/gitops/charts/traefik-plugins/websocketegress/websocketegress.go`: counts writes on the hijacked connection (egress) only.
- `lego/operator/internal/controller/activity.go` `activityQueries`: reads that counter.

## Fix

- Count client→server frame bytes in the plugin as a second counter (for example `bex_websocket_ingress_bytes_total{app_id}`), keep it in the Prometheus `metric_relabel_configs` allowlist (`deploy/gitops/base/prometheus.yaml`), and add it to `activityQueries`.
- Or record the divergence as permanent in ADR018 if reading client frames is not worth the plugin change.
