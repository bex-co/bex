## Objective

Reduce how often the direct meter is actually absent (mitigation — t002 is the fix that makes absence non-fatal): stop the DaemonSet from rolling on every image pin when the meter binary didn't change, and verify its scheduling covers every node tenant pods can land on.

## Context

- The DS (`bex-system/bex-egress-meter`, Argo-managed from `deploy/gitops/`, tracking-id `bex-operator:apps/DaemonSet`) hit template generation **67 in 45h** — it rolls with the shared bex-operator image pin on every deploy, opening an `up` gap each time. Its counters are node-persistent (pinned BPF map + `/var/lib/bex-egress-meter` checkpoint), so the roll's damage is purely the scrape gap — which today blanks 12h of chart.
- Scheduling reality (prod 2026-07-18): DESIRED=1 of 8 nodes — CP + platform nodes are tainted and the DS carries **no tolerations**; only untainted tenant nodes qualify. Verify against ADR022's placement model whether tenant pods can ever run on platform nodes (if they can't, tolerations are unnecessary; if they can, the meter must follow). One cordoned tenant node left a single instance whose eviction produced the observed ~12h absence.
- Options for the roll churn (pick with evidence, don't over-build): a separately-pinned meter image tag that only moves when `cmd/egress-meter`/its packages change; or accept rolls (counters survive; post-t002 the gap no longer blanks charts) and only document it. The second may genuinely be enough — decide against the t006 verification bar.
- ⚠️ This is GitOps-side (`deploy/gitops/`) + possibly `deploy.yml` pin logic — platform infra, not operator code (ADR001 split).

## Steps

1. Read the DS manifest + pin flow; confirm what exactly bumps the template each deploy.
2. Decide roll-avoidance vs roll-acceptance; implement the chosen minimal change (if any) and record the decision in the t001 ADR section.
3. Verify scheduling coverage against ADR022 (tenant-pod placement); add tolerations only if tenant pods can land on tainted pools.
