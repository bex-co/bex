## Objective

Stop the Outbound Bandwidth panel from masking failures: distinguish real data, a genuinely empty window ("No data in range"), and a degraded source (new state naming the source), and never render a GraphQL error as the empty state.

## Context

- Today `network-metrics-card.tsx:262-271` renders the bandwidth series through `SvgLineChart`, whose empty branch prints "No data in range" (`svg-line-chart.tsx:68`) — which is exactly what a hard error produced before t002, and what a degraded-but-served series must NOT silently look like after it.
- Consume t003's per-source health field: degraded ⇒ render the chart WITH an annotation (badge/tooltip: which source, i18n'd copy like "bandwidth may be undercounted — direct egress meter was offline for part of this window"); genuine error (network/503) ⇒ the existing `MetricUnavailable` state.
- Add the field to the hand-authored `dashboard/src/graphql/definitions.ts` documents (the m49 pattern) + `metrics.graphql`.
- All new strings via `useTranslations` with `metrics.*` keys in `features/metrics/locales/{en,zh}.ts`.

## Steps

1. Extend the Metrics/MonthToDateBandwidth documents + types with the health field.
2. Add the degraded annotation to the bandwidth `MetricSection` (chart still renders); keep "No data in range" only for a healthy-but-empty series.
3. Route query errors to `MetricUnavailable`, not the empty state.
4. Component tests: three states render distinctly; error ≠ empty.
