## Objective

Expose the workspace's seat usage — `used` (accepted members + outstanding invites, the same formula `store.CanAddMember` already enforces) and `limit` (from `store.LimitsFor(plan).MaxMembers`; 0 = unlimited) — as a read on the members surface, mirroring Render's `owner.usage.users { used, limit }` (docs/render-artifacts/team-members.graphql:13-18). Today the cap is invisible until an invite is refused with a `PlanLimitError`.

## Context

- `lego/backend/internal/members/service.go` — `List`/`ListInvites` verbs; add a `SeatUsage` (or extend the members list view) computed off the existing counts.
- `lego/backend/internal/store/plans.go:72-98` — `LimitsFor`, `CanAddMember` (count formula: members + outstanding invites).
- Reads `CountTenantMembers` live in `internal/store/workspaces.go`; outstanding-invite count in `internal/store/members.go`.
- Gate like `List` (`RelCanView`) — seat usage is not sensitive; every role sees the seat bar on Render.

## Steps

1. Add a `SeatUsage{Used, Limit}` view to `members.Service` (one Core computation; do not duplicate the count formula — reuse the store predicates).
2. Surface it on REST (`GET /v1/workspaces/{id}/members` envelope or a sibling read — pick the least-invasive Render-consistent shape), GraphQL (e.g. `workspaceSeatUsage(workspaceId)` or a field alongside `workspaceMembers`), and MCP (extend `list_workspace_members`' return).
3. `limit` semantics: unlimited plans return the same shape Render does for unlimited (verify against the artifact; do not invent a sentinel that breaks Render clients).
