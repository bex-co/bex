## Objective

Add a `ResendInvite` Core verb — re-send the invite email for an existing pending invite and refresh its `expires_at` — so an admin whose invitee lost the mail doesn't have to revoke + re-invite (today's only path, and one that churns the invite id).

## Context

- `lego/backend/internal/members/service.go` — sibling of `RevokeInvite` (`service.go:387-398`); same `RelCanManage` gate, same pending-only lookup.
- `lego/backend/internal/members/email.go:34-60` — `sendInvite` is reusable as-is.
- `lego/backend/internal/store/members.go` — needs an `UpdateInviteExpiry`-style touch (reset to `now()+InviteTTL`); keep the token stable (t004 depends on the emailed link staying valid).
- Delivery stays best-effort (log, don't surface) per docs/ADR024-members.md — but the verb itself must 404 on an unknown/accepted/expired-and-purged invite id.

## Steps

1. `Service.ResendInvite(ctx, workspaceID, inviteID)` — admin-gated; refresh expiry; re-send email; return the updated InviteView.
2. REST `POST /v1/workspaces/{id}/invites/{inviteId}/resend`; GraphQL `resendWorkspaceInvite(workspaceId, inviteId)`; MCP `resend_workspace_invite`.
3. Dashboard: a Resend action on the pending-invite row (`team-panel.tsx:158-196`), admin-gated like Revoke, success toast with the refreshed expiry.

## Acceptance criteria

- [ ] Resend on a pending invite delivers a second email (Mailpit on dev-N) and pushes `expires_at` forward; the invite id and token are unchanged.
- [ ] Resend on an accepted or unknown invite id is a clean 404 across all three surfaces.
- [ ] Non-admin callers get 403.

## Out of scope

- Rate-limiting resends (no cap exists on first-sends either; revisit only if abused).
