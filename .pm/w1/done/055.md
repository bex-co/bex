# 055 — KeyValue project/env setters bypass the patch path Postgres uses

From the 2026-08-19 architecture survey ([Bex Refactor Ledger](https://claude.ai/code/artifact/5ceae798-6df1-4f3c-94b6-6b1126f640c2) §0). The same three verbs on the twin datastores use different write mechanics: `lego/backend/internal/postgres/service.go:1076,1094,1113` (`SetProjectID` / `SetEnvironmentIPAllowList` / `SetEnvironmentID`) route through `patchDatabase`/`patchDatabaseObj`, while `lego/backend/internal/keyvalue/service.go:501,522,540` do a raw fetch → mutate → `resourcemeta.Touch` → `Client.Update`. A full `Update` carries different conflict/overwrite semantics than a patch (last-writer-wins over the whole object vs a targeted merge), so the same operation behaves differently depending on which datastore it targets.

**Fix.** Route the three KeyValue setters through the same patch-shaped helper the Postgres side uses (add the `patchKeyValue` equivalent if it doesn't exist), so conflict semantics match. Don't attempt the broader `datastore[T]` consolidation here — this note only stops the drift at the three verbs that have already diverged.

**Acceptance:** the KeyValue setters issue a patch (assert via the fake client's recorded action type or equivalent), and a regression test covers at least one setter's concurrent-modification behavior matching the Postgres twin; `go test ./...` green from `lego/backend/`.
