# 097 — Blueprint preview shows every fetch failure as "Blueprint file not found" with raw backend text; a wrong branch or missing repo reads only "github: unexpected status 404"

Why: the review step is where a Blueprint author finds out they typed the wrong branch, repo or path. Today it answers with an internal error string or a bare status code, under a title that is wrong for half the cases, so they can't tell what to fix.

## Root cause

- **The backend passes internal error text through.** `PreviewBlueprint` turns any `discoverBlueprintFile` error into `BlueprintPreview{Error: err.Error()}`, stripping only a `bad request: ` prefix (`lego/backend/internal/apps/blueprint.go:557-562`). The wire carries internal text and no reason.
- **Missing file.** `GetFileContents` formats `github: file %q not found at ref %q: %w` (`lego/backend/internal/github/client.go:860`). The ref is the commit SHA `discoverBlueprintFile` pinned up front (`blueprint.go:272`).
- **Wrong branch or missing repo.**
  - `resolveBlueprintCommit` returns the commit lookup's error unwrapped (`github/service.go:1053-1065`).
  - `GetCommit` returns a bare `&APIError{Status}` for any non-200 (`client.go:589-590`).
  - `APIError.Error()` is only `github: unexpected status %d`; it is deliberately body-free per `w6/005` (`client.go:189-195`).
- **Path rules.** The `approvedBlueprintPath` refusals (`blueprint.go:304-317`) land in the same `Error`. So do implicit discovery with neither file (the canonical fetch error, `:293-294`) and `ErrBlueprintFilenameAmbiguous` (`:288`).
- **Dashboard.** `dashboard/src/routes/blueprints.new.tsx:243-253` renders every `!preview.found` under `blueprints.previewNotFoundTitle` ("Blueprint file not found", `features/blueprints/locales/en.ts:121-124`). The body is `preview.error ||` the friendly `previewNotFoundBody` ("Blueprint file {path} not found on {branch} branch.", `:125-129`). That fallback can never render, because this path always sets `Error`.

## Fix (~45m)

- **Target behavior.** The preview carries a coded `reason`, and the dashboard picks both title and body from it. No raw error text, `github:` prefix or commit SHA reaches the UI. The reasons:
  - `file_not_found` (with path and branch)
  - `branch_not_found`
  - `repo_not_found_or_no_access`
  - `access_denied` (401/403)
  - `rate_limited` (429, retryable)
  - `invalid_path` (bad extension, or not a clean relative path)
  - `ambiguous_filename` (both `render.yaml` and `bex.yml`)
  - `unavailable` (other upstream status or transport failure, retryable)
- **Backend.** Classify in `PreviewBlueprint` with `errors.As(*github.APIError)` plus the path-rule and ambiguity sentinels, and add `reason` to `BlueprintPreview` on REST, GraphQL and MCP `preview_blueprint` together. Keep `error` for API clients, but make it human-readable.
- **Dashboard.** Map `reason` to title and body. Show `invalid_path` beside the path field rather than as "not found", and offer Retry only for retryable reasons.
- **Tests.** A backend table test per reason with a fake fetcher, and a dashboard test per reason's title and body.
- **Adjacent classes.**
  - GitHub answers `404` for a private repo the installation can't see, so a missing repo and a repo with no access can't be told apart. Keep them one combined reason ("Repository not found, or bex's GitHub app can't access it"). Splitting them would turn the preview into a private-repo existence oracle.
  - The existing-Blueprint sync view and the auto-sync worker (`blueprint_auto_sync_worker.go`) hit the same fetch errors. They should reuse the classifier.

  - The existing-Blueprint sync view was not probed, and Render's own copy for these cases was not checked.
