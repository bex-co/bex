# Resolve the four ServicePatch surface divergences deliberately

Filed by `w1/m78` t004 (Render parity), 2026-08-19. The m78 refactor made the REST/MCP service-update op table single-sourced (`apps/settings.go`) and turned four previously-invisible divergences into explicit, commented fill-site gaps. They are preserved byte-identically today; each now needs a deliberate resolution — extend the missing surface, or record the asymmetry as intended in `docs/ADR018-render-parity.md`:

1. `repo` / `image` / `imageOwnerId` — REST `PATCH /v1/services/{id}` accepts them; MCP `update_service` does not. Render's PATCH accepts image updates, so MCP is the short surface.
2. `notificationsToSend` — MCP-only in the patch table; REST has only the separate `/notification-settings` route. Check Render's actual PATCH field set before extending.
3. `autoscaling` — MCP-only in the patch table; REST has only `PUT …/autoscaling`. Render likewise uses the dedicated endpoint — the MCP extra may be the divergence to document rather than the REST gap to fill.
4. Maintenance-before-plan-on-free-downgrade reorder — REST-only (`ServicePatch.MaintenanceBeforeFreeDowngrade`). If it's a correctness ordering (avoid a paid-feature validation refusing the downgrade), MCP multi-field updates want it too.

Each is sub-hour once decided; the cross-surface equivalence test in `apps/settings_test.go` and the order/completeness guards will enforce whatever is chosen.
