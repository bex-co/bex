# Edge canaries confirm before opening an incident and name the failure they saw

Why: one ~40-second failure at 2026-10-16 21:40Z opened #97 and #98, which were still open on a healthy edge seven hours later, and both bodies prescribe a fix the probe output contradicts.

**Evidence (run `38970933970`, verified 2026-10-17).**

- #98 is titled "onbex.co fallback TLS is invalid or expiring" and says to rotate the certificate. But `scripts/onbex-default-tls-verify.sh` prints a specific error for each certificate check, and none fired: the `openssl s_client` handshake, SAN and 30-day checks passed. Only the final `curl` timed out ("Operation timed out after 20002 milliseconds with 0 bytes received").
- #97 says `ssh.bex.co:22` "wrote its SSH banner but did not send SSH_MSG_KEXINIT" and blames PROXY protocol. The probe actually failed earlier, with `read server identification: … i/o timeout`: no banner arrived.
- Same run, same minute: the Web Shell probe (`wss://ssh.bex.co/shell`, same LB IP `49.12.20.236`) passed at 21:41:34, and tenant-view and request-logs passed. At 04:27Z both edges answered normally (404 for `notfound.onbex.co`, banner `SSH-2.0-bex`).
- Each verdict rests on one sample. Recovery waits for the next scheduled run (`37 */6 * * *`), and GitHub started it 3+ hours late; the 00:37Z slot had still not run at 04:54Z.
- **Cause unknown.** It could be the runner (Docker Desktop on the shared Mac; the 03:33Z deploy also failed with "runner lost communication") or the edge (a single LB target stalling). Production metrics were not available to this session.

**Change.**

- Retry a failed probe twice, about 30 seconds apart, before declaring an edge down. This matches the workflow's stated bar: catch breakages that would go "unnoticed for weeks", not 40-second blips.
- Classify the failure and put the class in the issue title and body: connect timeout, no banner, banner but no KEXINIT, TLS trust, SAN, expiry, HTTP status/timeout. Give only the remedy that fits that class.
- Record `curl -w` connect/appconnect/starttransfer timings, and which sibling probes in the same run passed, so the next occurrence can be attributed to runner or edge.

**Files:** `.github/workflows/ssh-edge-liveness.yml`, `scripts/ssh-kexinit-probe.sh` (and the Go probe test it runs), `scripts/onbex-default-tls-verify.sh`, `scripts/shell-ws-probe.sh`.

**Constraints:** runners stay `[self-hosted, Linux, ARM64, bex-production]` (#CI-RUNNERS, #RUNNER-HOSTS); `bash scripts/github-actions-validate.sh` stays green. `scripts/onbex-default-tls-secret.test.sh` and the probe unit tests must pass.

**Done when:** each probe's issue text matches what failed (shown by forcing each class locally, for example an unroutable address, a self-signed host and a closed port); a single transient failure no longer opens an issue; a sustained one still does.

**Done 2026-10-17.** `scripts/edge-probe.sh` runs each edge probe up to three times, 30s apart, before an edge counts as down, and records the failure class the last attempt saw. `.github/workflows/ssh-edge-liveness.yml` uses it for the SSH, fallback-TLS and Web Shell probes. Issue titles name the class, and the remedy is class-specific: the PROXY-protocol advice only for a banner without KEXINIT, certificate rotation only for the certificate's own failures (`certificate_failure`), reachability checks otherwise. `scripts/edge-probe.test.sh` (wired into `scripts.yml`) pins the classes on the 2026-10-16 run's real outputs, a cleared transient opening nothing, and a sustained failure failing.
