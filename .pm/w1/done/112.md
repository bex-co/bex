## Transferred scope and evidence

## Objective

Make the DoD's second bullet true. Every sandbox charge row shows its owning agent session's repo and branch, or `plan · image` when there is no such session, so rows can be told apart. Found by the live re-probe on 2026-09-26 (`/qa-find-bugs` pass 219, recorded in the milestone README). All 14 sandbox rows in `usage(ownerId: "tea-d98210cbbpdc73dcrkvg") { estimatedCost { resources } }` and on `/billing` → Charges read `starter sandbox (deleted)`. That includes `271ec9ce-a32b-4128-bb43-02a9e57b01b6` at $78.61, which is indistinguishable from thirteen $0.00–$0.12 rows. That meets "never a bare UUID" to the letter and misses its point.

## Context

- `lego/backend/internal/usage/service.go:377-396`: when neither a live name nor a retained record exists, a sandbox falls back to `tier + " sandbox"`. That is the only label these rows get.
- `lego/backend/internal/store/resource_names.go:137` `SandboxUsageMetadata` labels only from `agent_sessions` / `agent_session_dispatches` rows with `repo <> ''`. A repo-less session (the `w3/m79` real-model repo-less path) or a sandbox created outside a session never gets one. The same filter applies to migration `0121`'s backfill.
- `sandbox_meter_states` (`store/migrations/0061_sandbox_compute_meter.up.sql:14-23`) records `phase`, `tier` and weight, and **no image**. So the `plan · image` form that t001 step 2 and t002 step 3 asked for cannot be produced from what is stored today. The Decisions section records the SQL-join choice but not this dropped fallback.

## Steps

1. Record the image while the sandbox is alive. Either add `image` to `sandbox_meter_states`, written by the meter where `tier` is written, or write a `plan · image` label into `resource_display_names` at sandbox create. The second shape follows the existing retained-name design and keeps the label after the sandbox is reaped. Pick one and say why in the README's Decisions.
2. In `resolveServiceNames`, fall back to `plan · image` and only then to `<tier> sandbox`. Keep the session repo/branch label first.
3. For a repo-less session, prefer a session-derived label that identifies it (for example the session id or its title, if one exists) over `plan · image`, if that is more useful. Record the choice.
4. Pre-fix sandboxes stay as they are: the image is unrecoverable for already-reaped ones. Note that in the Backfill decision.
5. Tests: a session-less sandbox resolves to `plan · image`; a repo-less session's sandbox resolves to the chosen label; two sandboxes with the same tier and different images get different labels.

## Acceptance criteria

- [ ] On production, a fresh sandbox created without a repo and then terminated shows `plan · image` (or the recorded repo-less label) on `/billing` → Charges and in `usage { estimatedCost { resources { serviceName } } }`. REST and MCP carry the same `serviceName`.
- [ ] Sandbox rows are distinguishable. No two sandboxes with different images share a label.

## Out of scope

- Renaming the pre-fix `starter sandbox` rows, whose images were never recorded.

## Triage 2026-09-28 (`/loopx w1`) — decision made, feasibility proven, live acceptance is post-deploy

**Step 1's decision: option (b), a retained display name at create.** Not option (a)
(`image` column on `sandbox_meter_states`). Reasons:

- It reuses the mechanism `resolveServiceNames` **already reads first**:
  `retained[key]` from `resource_display_names` (`usage/service.go:371`). A row written
  at create needs no new fallback branch and no migration.
- It survives reaping by design, which is the whole problem — the label must outlive
  the sandbox.
- Option (a) would record the image but still require a new join and a new fallback,
  and `sandbox_meter_states` is a metering table, not a labelling one.

**Insertion point, verified.** `Meter` already carries `Store MeterStore`
(`sandbox/meter.go`) and `Service.Create` already calls `s.Meter.Observe(ctx, raw)`
immediately after resolving the image — `raw.Image.URI`, falling back to
`tmpl.Image` (`sandbox/service.go:505-525`). So plan and image are both in hand at the
one call that already has store access. `MeterStore` needs the
`RecordResourceDisplayNames` verb `usage` already uses.

**Feasibility proven live on production.** A session-less sandbox — exactly the case
this note targets — creates fine and its response carries the image:

```
POST /v1/sandboxes {"ownerId":"tea-…","plan":"starter"}  -> 201
  id     sbx-dat20rbncejs739qiv9g
  plan   starter
  image  docker.io/library/alpine:3@sha256:28bd5fe8b56d1bd048e5babf5b10710ebe0bae67db86916198a6eec434943f8b
POST /v1/sandboxes/sbx-…/terminate                       -> 204   (fixture removed; none remain)
```

So the intended label for that shape would be `starter · alpine:3` (the digest wants
trimming to stay readable). Note `DELETE /v1/sandboxes/{id}` is **405** — termination
is `POST …/terminate`, worth knowing for any future probe.

**Step 3's repo-less-session half is a second, separate gap.** `SandboxUsageMetadata`
labels only from `agent_sessions` / `agent_session_dispatches` rows with `repo <> ''`
(`store/resource_names.go:141-155`), so a repo-less session gets nothing even though a
session exists and could name itself. That is a SQL change in the same query, not part
of the create-time label.

**Why this is parked rather than shipped now: its acceptance criterion cannot pass
until the fix is deployed.** The label is written *at sandbox create*, so no sandbox
that already exists — including any fixture created now — can ever acquire one. The
DoD ("a fresh sandbox created without a repo and then terminated shows `plan · image`
on /billing → Charges and in `usage { estimatedCost { resources { serviceName } } }`,
with REST and MCP carrying the same `serviceName`") is therefore a strictly post-deploy
check. Shipping the code and immediately re-probing would re-diagnose the old build,
which is the exact trap `w4/111` recorded.

**To clear:** implement the two halves above, ship, wait for a deploy, then create one
session-less sandbox and one repo-less-session sandbox, terminate both, and read
`/billing` → Charges plus the `usage` query. Parent `w2/m96` keeps its rename, purge and
live-acceptance obligations; completing this note satisfies only its cross-workstream
dependency.

## Implemented 2026-09-29 (`/loopx w1`, `de9ac4d1c`) — live acceptance next

- **Step 1 (option b):** `Meter.Label` retains `plan · image` in `resource_display_names` at create, from `Service.Create` right after `Meter.Observe`. The label is keyed by the same public id the usage rows carry. The image is shortened, with no digest and no implicit `docker.io/library/`, so `starter · alpine:3`; the tag stays, so two images never share a label.
- **Step 2:** no new fallback branch was needed, because `resolveServiceNames` already reads the retained name before `<tier> sandbox`.
- **Step 3:** a repo-less session is labelled `agent session <session id>`. It is unique and findable in the session list, which `plan · image` would not be. `SandboxUsageMetadata` no longer filters `repo <> ''`, and a session's repo/branch label still wins over the retained one.
- **Step 4:** sandboxes from before this keep `<tier> sandbox`; their images were never stored. Migration `0121`'s historical backfill is unchanged.
- **Step 5 tests:** `TestSandboxChargeLabel` (shape; different images give different labels), `TestMeterLabelRetainsPlanAndImageAtCreate`, `TestCreateRetainsTheChargeLabel` (fails with the create call removed) and `TestSandboxUsageMetadataPG` (a repo-less session gives `agent session ags-3`; fails on the old query). Run against a real Postgres (`BEX_TEST_DB_URI`), full backend suite and lint green.

The live check needs a pin that includes `de9ac4d1c`: create a session-less sandbox, terminate it, and read `usage { estimatedCost { resources { serviceName } } }` and REST `/v1/usage`.
