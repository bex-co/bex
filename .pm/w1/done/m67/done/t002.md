## Objective

Close Finding 1 (resource-exhaustion, CWE-400): authentication wraps the rate limiter (`auth(rl(handler))`), and the only general limiter is keyed by **resolved identity** — so it cannot protect the work of resolving an identity. There is no negative cache (`introspectUpstream` returns on `!active` without a `Put`) and singleflight only coalesces *identical* tokens, so every unique invalid bearer or session credential costs exactly one upstream Hydra introspection or Kratos whoami. An anonymous client can amplify cheap requests into the shared identity services that every tenant's control plane depends on.

## Context

- `lego/backend/internal/api/server.go:905-916` — `rl := s.rateLimitMiddleware()`, then `mux.Handle("/v1/", auth(rl(rest)))` (and `/graphql`, `/mcp`).
- `lego/backend/internal/api/auth.go:230-250` (introspect + singleflight + cache) and `:349-365` (whoami) — the two upstream calls.
- Existing, proven building blocks to reuse — do not invent a new limiter: `webhookRateLimitMiddleware` and `deployHookLookupRateLimitMiddleware` (`server.go:945-965`) are already IP-keyed and mount outside the auth gate, and `BEX_TRUSTED_PROXY_CIDRS` already resolves the real client IP behind Traefik (`docs/ADR006-bex-api.md` §Rate limits).
- `hasSessionCredential` (`auth.go:220-228`) already avoids Kratos round trips for unrelated cookies — the same "don't pay upstream for junk" instinct, applied one level up.
- Report: report.md Finding 1.

## Steps

1. Mount an outer IP-keyed admission limiter around the auth gate for `/v1/`, `/graphql`, `/mcp`, with its own env knobs (`BEX_AUTH_RATE_LIMIT` / `_BURST` following the existing naming and `0` ⇒ disabled), trusted-proxy aware like its siblings.
2. Bound credential size before allocation/upstream I/O: refuse absurd `Authorization`/`X-Session-Token` values with a 401 without calling Hydra/Kratos.
3. Bound concurrent authentication work (a semaphore around upstream introspection/whoami) so a burst that passes the limiter still cannot saturate the identity services.
4. Keep the inner identity-keyed limiter exactly as is — this is admission control in front of it, not a replacement — and keep successful-auth latency unchanged.
5. Consider a small bounded negative cache **in addition to** the above (never instead of it); only if it does not weaken revocation semantics, which the positive cache already handles carefully via `revocationEpoch`.
