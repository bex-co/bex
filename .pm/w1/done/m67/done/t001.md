## Objective

Close Finding 6 (token-validation, CWE-345): the shared auth gate accepts an active Hydra token whose introspection omits `aud` or `iss`, even when `BEX_OAUTH_RESOURCE`/`BEX_OAUTH_ISSUER` are configured to pin both. The exception exists for API-key client-credentials tokens (which carry no audience), but it is written as a blanket "empty claim ⇒ accept" rule, so a dynamically registered client's consented **human** token can be replayed against bex without any bex resource binding. Hydra runs with DCR enabled, so a third party can register a client; only the consent screen stands in the way.

## Context

- `lego/backend/internal/api/auth.go:290-303` — `if a.resource != "" && len(out.Aud) > 0 && !slices.Contains(...)` and the mirror `out.Iss != ""` check.
- `lego/backend/internal/api/auth.go:305-312` — the gate already computes `human := out.Sub != "" && out.Sub != out.ClientID`, i.e. the token class is **already known** at the decision point.
- `deploy/gitops/base/values/hydra.values.yaml:63-68` — `dynamic_client_registration.enabled: true`; unknown clients are not auto-consented (`isTrusted` in `dashboard/src/common/server-fn/hydra-consent.ts`), so exploitation needs a human to approve.
- `lego/backend/internal/api/server.go:914-916` — the resulting Identity feeds REST, GraphQL, and MCP.
- `docs/ADR012-auth.md` §7 — the discovery/audience contract.
- Report: report.md Finding 6.

## Steps

1. Split the policy by token class: human authorization/device tokens must present the exact configured issuer **and** contain the configured resource in `aud`; client-credentials tokens keep the documented empty-audience exception.
2. Prefer an authoritative check over inference where cheap — the API-key store already knows which `client_id`s are bex-minted keys; use it to justify the exception rather than relying on `sub == client_id` alone.
3. Make the issuer check unconditional for both classes when configured (an empty `iss` from a configured verifier is a failure, not a pass).
4. Verify the dashboard's Kratos-session path and the official Render CLI device flow are unaffected (they are not Hydra-audience-bearing in the same way) before changing acceptance.

## Acceptance criteria

- [ ] An active human token with empty `aud` is **rejected** when `OAuthResource` is configured — test fails before the fix.
- [ ] An API-key client-credentials token with empty `aud` still authorizes (no regression for existing keys), and only because it is positively identified as that class.
- [ ] An empty or mismatched `iss` is rejected when an issuer is configured.
- [ ] With neither configured, behavior is byte-identical to today (local dev unaffected).
- [ ] Backend suite green; MCP/agent OAuth flow re-verified end to end (`docs/ADR025-connect-an-agent.md` recipe).

## Out of scope

- Requiring Hydra to mint the bex audience for every client (a deployment change worth doing, but the gate must not depend on it).
