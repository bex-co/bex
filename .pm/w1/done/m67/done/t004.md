## Objective

Close Finding 2 (resource-exhaustion, CWE-400): endpoint creation has no count ceiling anywhere — not in the service, not in the store, not in the schema — and the dispatch worker expands every event across every matching enabled endpoint into one in-memory batch and one pgx insert. The 200-event read bound bounds the left factor only; a workspace admin can grow the right factor persistently and then impose large allocations and database batches on a worker shared by every tenant.

## Context

- `lego/backend/internal/store/webhooks.go:72-92` — `CreateWebhookEndpoint`: plain INSERT, no count check.
- `lego/backend/internal/store/webhooks.go:185-203` — the global enabled-endpoint load the worker fans out over.
- `lego/backend/internal/webhooks/worker.go:318-350` — the nested `for rows { for byTenant[...] }` batch build + `EnqueueWebhookDeliveries`.
- `lego/backend/internal/store/migrations/0025_webhooks.up.sql:3-13` — endpoint schema (no constraint to hang a quota on).
- Precedent for a plan-aware cap enforced at the persistence boundary: the members seat cap (`store.ErrInvitePlanLimit`, `w1/m44`) — same shape, reuse the pattern and the error-mapping style.
- Report: report.md Finding 2.

## Steps

1. Enforce a per-workspace endpoint cap transactionally in the store (count + insert in one transaction, so two concurrent creates cannot both pass), with a typed store error mapped to a clear tenant-facing refusal.
2. Add a platform ceiling as well, so the sum across workspaces is bounded even if a per-workspace cap is generous.
3. Bound the dispatch pass: cap deliveries per transaction and page the endpoint scan, so one tick's allocation is bounded regardless of endpoint count; interleave rather than materializing everything.
4. Surface the cap in the error message and, if cheap, in the endpoints list response (Render-style limit/usage), so the dashboard can show it.
