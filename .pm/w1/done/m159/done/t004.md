## Objective

Check the three surfaces this milestone touches against Render's equivalents and against bex's own REST/GraphQL/MCP values, and record any divergence.

## Files

- `docs/ADR018-render-parity.md`
- `.pm/w1/m159/README.md`

## Acceptance criteria

- [ ] The status and plan shown on a datastore page match what REST, GraphQL and MCP report for the same resource.
- [ ] Any divergence from Render is recorded in ADR018; the comparison is in the m159 README.

## Out of scope

- Changing Render-shaped response fields.

## Result (2026-09-28, `/loopx w1`)

Done. All three API surfaces verified live on throwaway fixture `qa-20260928-kv`
(`red-dat0lijncejs739qiuvg`, created → suspended → read → deleted): `status`,
`suspended` and `plan` identical across REST, GraphQL and MCP. The milestone
README's `## Render parity (t004)` section carries the table, and it **corrects**
the 2026-09-15 write-up, which had concluded that a suspended store legitimately
reports `status: "available"` and that nothing on the wire should change —
Render's pinned `databaseStatus` enum contains `suspended`, and `b465b6100`
fixed the wire accordingly. No ADR018 divergence to record.
