## Objective

Close Finding 7 (authorization-state, CWE-863): membership rows are mutated before OpenFGA and tuple failures are not durably retried. A failed grant makes the next `ChangeRole` return early (the row already equals the target, so the tuple repair is skipped); revocation errors are discarded for role changes and removals; invite redemption for an existing member grants the new role without revoking the old. Because the model ORs roles, stale elevated tuples retain privilege indefinitely.

## Context

- `lego/backend/internal/members/service.go:512-588` — `ChangeRole`/`Remove`: `if m.Role == role { return ... }` early-return skips tuple repair; `revokeRole` discards errors.
- `lego/backend/internal/store/members.go:315-327` — DB role update.
- `lego/backend/internal/api/tenancy.go:195-212` — invite redemption upsert path.
- `deploy/gitops/authz/model.fga:61-75` — `can_create: developer or admin`, `can_manage: admin` (OR semantics ⇒ a stale higher tuple still authorizes).
- Report: report.md Finding 7.

## Steps

1. Reconcile OpenFGA to **exactly one** expected role per member: write the target tuple and delete every other role tuple for that subject/workspace (don't rely on the DB row already matching).
2. Surface and retry revocation errors instead of discarding them; make a retry repair tuple state even when the membership row already equals the requested role (drop or bypass the `m.Role == role` early return for the reconcile path).
3. On invite redemption for an existing member, revoke the prior role before/atomically-with granting the new one.
4. Persist membership change + an authorization outbox record in one DB transaction and drive a reconcile/repair loop from it so a transient OpenFGA failure converges.
