## Objective

Stop the invite verb from silently changing an existing member's role. Inviting
an email that already belongs to an active member of the workspace must be
refused with a clear "already a member" error (Render's behavior) instead of
creating a pending invite that later auto-redeems and overwrites their role.
Add a defense-in-depth guard so the redeem path can never downgrade/overwrite an
existing member even if a stale pending invite exists.

## Context

- **Root cause (confirmed live 2026-08-19):**
  - `lego/backend/internal/members/service.go` `Invite(...)` authorizes
    `can_manage`, validates role + email, checks the seat cap, then calls
    `store.CreateInvite` — it **never checks whether `email` is already an
    active member**.
  - `lego/backend/internal/api/tenancy.go` `acceptInvites(...)` runs on the auth
    gate for every request carrying an email → `store.AcceptInvitesForEmail(email, subject)`
    (`lego/backend/internal/store/*.go`) → `redeemInvite(...)`, whose write is:

    ```sql
    INSERT INTO tenant_members (tenant_id, subject, role) VALUES ($1,$2,$3)
    ON CONFLICT (tenant_id, subject) DO UPDATE SET role = EXCLUDED.role
    ```

    For a subject already a member, `DO UPDATE SET role = EXCLUDED.role`
    overwrites their role with the invited one and marks the invite accepted.
  - Net effect: re-inviting `puncsky@gmail.com` (an Admin) as Developer silently
    demoted them on their next request; no pending invite remained afterward.
- Render rejects re-inviting an existing member ("already a member"); mirror that.
- Membership is keyed by `subject` (identity id); the email lives on the
  identity. The members view already resolves member email via the `Identities`
  interface (`members/service.go`), so "is this email already a member" is
  resolvable — decide the cleanest lookup (resolve members' emails and compare,
  or a store-level `MemberByEmail`). A new coded error (e.g.
  `MEMBER_ALREADY_EXISTS` / `core.ErrConflict`-class) should be returned so all
  three surfaces render it identically.

## Steps

1. In `members.Invite`, after email canonicalization and before `CreateInvite`,
   refuse when the email already belongs to an active member of the workspace,
   returning a coded "already a member" error (name it; keep the message
   Render-aligned). Preserve existing behavior for genuinely new invitees.
2. Harden `store.redeemInvite`: do not silently overwrite an existing member's
   role — the invite-time check is primary, but the redeem path must not
   downgrade an existing member if a stale/racing pending invite is redeemed
   (e.g. `ON CONFLICT … DO NOTHING`, or skip the role write when a membership
   already exists — choose the option that keeps a genuinely-new join correct
   and is covered by t005's tests).
3. Confirm the seat-cap accounting still holds (a refused invite must not consume
   or leak a seat).

## Files

- `lego/backend/internal/members/service.go` (Invite guard)
- `lego/backend/internal/store/*.go` (`redeemInvite` / `AcceptInvitesForEmail`,
  optional `MemberByEmail`)
- possibly `lego/backend/internal/core` (a new coded error)

## Acceptance criteria

- [ ] Inviting an email that is already an active member returns the coded
      "already a member" error; the member's role is unchanged.
- [ ] Redeeming a pending invite for a subject who is already a member does not
      change their role (defense-in-depth), while a genuinely new invitee still
      joins with the invited role.
- [ ] Seat usage is unaffected by a refused invite.

## Out of scope

- The dashboard-side email validation + error surfacing (t002).
- Reworking the accept-on-login mechanism beyond the no-overwrite guard.
