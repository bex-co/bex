## Objective

Decide — with the user — whether bex keeps the mint-once signing-secret contract (secret shown exactly once at creation, the api-key precedent) or matches Render's dashboard, which reveals the secret any time in Settings (masked, Show + Copy). Implement the decided treatment on the Settings tab and record the outcome.

## Context

- Today every read verb deliberately omits the secret column (`webhookEndpointColumns`, `lego/backend/internal/webhooks/store/webhooks.go:64`); only Create returns it (service.go:171-175, documented at graphql.go:39-40 and rest.go:34-40 as the api-key mint-once precedent from w3/m11).
- The secret is stored **plaintext** (Standard-Webhooks HMAC signing requires it — the delivery worker fetches it, store/webhooks.go:464), so a reveal verb needs **zero migration**; mint-once is a policy choice, not a schema constraint. Mint-once narrows the exposure surface (no read path can leak it) but is weaker parity: Render's Settings shows `whsec_…` masked with Show secret/Copy ("A token used to sign and verify request payloads.").
- **Default recommendation: keep mint-once for this milestone.** Record the divergence in `docs/render-artifacts/webhooks-ui.md` and ADR018's webhook row. If the user opts into parity instead: add an authz-gated reveal (RelCanManage, same relation as Update) as a deliberate mutation/POST verb (not on the plain GET read path), audit-log each reveal, and mirror it on REST/GraphQL consistently — MCP omission is acceptable (Render's MCP has no webhook tools at all).

## Steps

1. Put the choice to the user with the trade-off above (one question, two options, recommendation first).
2. If **keep mint-once**: Settings shows a static "Signing secret — shown once at creation" note (i18n'd); update the artifact + ADR018 divergence note. Done.
3. If **reveal**: backend verb (service + store read-with-secret + GraphQL/REST exposure + audit event), dashboard masked field with Show/Copy, tests for the authz gate and audit row.
