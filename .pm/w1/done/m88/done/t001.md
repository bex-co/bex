## Objective

Render attaches a disk at create through `serviceDetails.<type>.disk`. bex has no such field, and because Render-matched routes decode strictly, a Render-shaped create carrying it returns **400 unknown field "disk"** rather than being ignored. Today the only way to get a disk at create is a Blueprint.

## Context

- `createServiceRequest`/`serviceDetailsReq` have no disk field (`lego/backend/internal/apps/rest.go:174`, `:221-253`).
- The only producer of `CreateRequest.Disk` is the Blueprint compiler (`deploy.go:1976`) — the plumbing below REST already exists, including `validateCreateDisk`.
- Strict decode: `lego/backend/internal/api/render_openapi.go:316` → `lego/backend/internal/core/http.go:60-90`.
- ADR082 D6/D7 never recorded this as deliberate, so right now it reads as a bug to anyone porting from Render.

## Steps

1. Decide: implement `serviceDetails.<type>.disk` on create, or declare the refusal deliberate.
2. If implementing, reuse `validateCreateDisk` so create and add-disk cannot drift on eligibility, tier, replica and mount-path rules.
3. Either way, write the outcome into ADR082 D6 — the point is that the behavior stops being accidental.

## Files

- `lego/backend/internal/apps/rest.go`, `lego/backend/internal/apps/service.go`, `docs/ADR082-persistent-disks.md`

## Acceptance criteria

- [ ] a Render-shaped create with `serviceDetails.disk` either attaches the disk or fails with a named, documented error — not "unknown field"
- [ ] the decision appears in ADR082

## Out of scope

- Changing the Blueprint path, which already works.
