## Objective

Render's `POST /disks/{diskId}/snapshots/restore` returns **200 with the disk object**; bex returns **202 with no body**. Render documents `list-snapshots` as 201; bex returns 200. No bex surface returns the disk from a restore — GraphQL returns `Boolean`, MCP `{restoring:true}`.

## Context

- `lego/backend/internal/apps/disk_snapshots.go:189` (restore), `:186` (list).
- The 202 is argued in a code comment (`:146-149`) — a restore is asynchronous, which is a real justification — but it appears in neither ADR082 nor `docs/render-artifacts/disks.md`, so it is an undocumented divergence rather than a decided one.
- The OpenAPI middleware validates **requests only**, so nothing catches response drift. Worth considering a response-shape guard while here.

## Steps

1. Decide per route: match Render's shape, or keep bex's and record why.
2. If keeping 202, say so in ADR082 with the async rationale, and make GraphQL/MCP agree on whatever the answer is.
3. Consider a test that pins response shapes for the Render-intersecting disk routes.
