## Objective

Replace parity-by-comment with parity-by-registry: a declaration site where each MCP tool states whether it is `Parity1to1` with Render's official server, a `Superset` of a Render tool (same name, extra args), or a bex `Extension` (no Render counterpart).

## Context

- Working precedent in this repo: `lego/backend/internal/id` — a `Kind` registry plus a guard test that fails when an id-bearing resource is added without registering its kind (`docs/ADR020-identifiers.md`, and the repo rule requiring every id to be minted through it).
- 213 `mcp.AddTool` call sites across 24 packages; `internal/apps` alone holds 58.
- The registry must be reachable from a test without starting a server, and must not require every feature package to import the API root (features never import the root — `internal/api/server.go:18` documents the no-cycle rule).

## Steps

1. Define the class enum and a registration seam that sits next to `mcp.AddTool` — a thin wrapper or a per-package manifest, whichever avoids a feature→root import.
2. Decide and document the `Superset` rule: same tool name as Render, additional optional arguments allowed, no removed or renamed Render argument.
3. Wire the registry so a test can enumerate every registered tool with its class and its argument names.
4. Leave the 213 existing call sites unclassified for now — t004's guard makes that state fail, and t003 fixes it.

## Files

- `lego/backend/internal/api/` (registry + class type)
- one representative feature package wired end to end as the pattern (`internal/jobs` is the smallest, 4 tools)

## Acceptance criteria

- [ ] A test can list every registered MCP tool with `{name, class, argNames}`.
- [ ] No feature package imports the API root.
- [ ] The `Superset` rule is written down where the class is defined, not only in a milestone doc.

## Out of scope

- Classifying the other 209 tools (t003).
