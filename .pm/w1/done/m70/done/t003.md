## Objective

Assign a parity class to every one of the 213 registered MCP tools, checked against t001's pin rather than against the existing comments — and produce the inventory that decides m71's scope.

## Context

- Per-package tool counts at HEAD: `apps` 58, `postgres` 28, `envgroups` 17, `agentsessions` 14, `environments` 11, `secrets` 10, `members` 10, `keyvalue` 9, `projects` 8, `deploys` 7, `webhooks` 6, `registrycreds` 5, `sandbox` 4, `jobs` 4, `sshkeys` 3, `apikeys` 3, `billing` 3, then 2 or fewer each across `metrics`, `workspaces`, `logs`, `github`, `events`, `notifications`, `usage`.
- Existing comments are a starting hypothesis, NOT the answer — they carry stale manual check dates and are inconsistent (86 tools self-declare `"bex extension"` per tool; `secrets`/`envgroups`/`jobs` declare it once at the file header and never per tool, so 31 more are extensions without saying so individually).
- Known hypothesis to verify, not assume: the whole `set_*` family (34 tools) is an invented bex grammar — `internal/apps/mcp.go:88` states "Render's official MCP has no update tools for any of them", and ADR018 repeats it in four rows.
- `agentsessions` (14) and `sandbox` (4) are pillar-5 bex products with no Render counterpart at all.

## Steps

1. Diff bex's registered tool names against the pin to get the three raw buckets: in both, bex-only, Render-only.
2. For every tool in both, compare argument names to separate `Parity1to1` from `Superset`.
3. Classify every bex-only tool as `Extension`.
4. Record any **Render-only** tool (present upstream, absent in bex) as a parity gap — that is an ADR018 row, not a blocker for this milestone.
5. Write the per-class counts and the full table into the milestone's evidence, and correct any file-header or per-tool comment that the pin contradicts.
