## Objective

Install CNPG's supported Barman Cloud plugin and materialize the ObjectStore resources needed by tenant databases and bex-db without exposing credentials.

## Context

- CNPG 1.30 defers removal of in-tree Barman support to 1.31, making the current release the migration window.
- Official migration guidance requires the plugin, ObjectStore resources, Cluster plugin configuration, external cluster updates, and plugin-method ScheduledBackups.
- Existing S3 credentials remain out of band in Kubernetes Secrets.

## Steps

1. Pin and deploy a plugin version compatible with CNPG and the upgraded Kubernetes cluster.
2. Create tenant and bex-db ObjectStore resources that preserve current destination, retention, endpoint, and credential references.
3. Add GitOps validation for plugin readiness, ObjectStore references, and secret-key names without decoding secret data.

- deploy/gitops/base/

## Acceptance criteria

- [x] The Barman Cloud plugin is declared through GitOps and reports Ready.
- [x] Tenant and platform ObjectStore resources resolve their existing destinations and credential references.
- [x] Validation fails on a missing plugin/ObjectStore or mismatched reference without reading secret values.

## Out of scope

- Deleting in-tree backup fields before successful migration and restore drills.

## Completion evidence

- GitOps pins the official Barman Cloud plugin `v0.13.0` manifest by SHA-256, and production runs `ghcr.io/cloudnative-pg/plugin-barman-cloud:v0.13.0` at 1/1 Ready on the platform pool. Its client and server cert-manager Certificates both report Ready.
- Production has exactly the staged `bex-system/bex-db` and `default/bex-tenant-postgres` ObjectStores. They preserve `s3://bex-tfstate/bex-db` with 7-day retention and `s3://bex-tfstate/postgres` with 30-day retention, the Wasabi endpoint, and the existing Secret/key references.
- The tenant namespace received the credential Secret out of band. Verification inspected only Secret names and key names (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`), never decoded values; no Secret object renders from GitOps.
- `scripts/gitops-validate.sh` fails closed if the vendored manifest hash, plugin image/CRD/certificates, placement, ObjectStore destinations, retention, or Secret/key references drift, and it rejects any rendered Secret. Argo CD reports both plugin applications Synced/Healthy at `87a949bf`.
