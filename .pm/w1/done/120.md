# A buildpack Node service built with the default engine range crash-loops on `libatomic.so.1`

Why: `builder: buildpack` is bex's zero-command Paketo path, and its most common input — a Node app whose `engines.node` is an open range such as `>=20` — builds green and then never starts.

**Source:** `w1/108` production validation, 2026-10-02 (fixture `qa-20261002-108-bp`, deleted). `examples/hello-node` built through kpack with the new builder (`170ab193…`): detect, build and export succeeded, and the image ran on `run-jammy-base` (amd64 `7e12e68b…`). The container crash-looped with `error while loading shared libraries: libatomic.so.1`.

- **Not caused by the 108 bump.** `>=20` resolves to Node 26 (26.10.0 now; the old builder's node-engine would have chosen 26.5.1). Both Node 26 linux-x64 binaries link `libatomic.so.1`, and neither the old (`20cc5001…`) nor the new (`33c1e0d7…`) `run-jammy-base` ships it. Node 24.21.0 does not need it.
- **Options:** (a) a run image that includes libatomic (e.g. `run-jammy-full`, or a bex-extended run image); (b) default `BP_NODE_VERSION` to the newest LTS when the app's range is open; (c) both. Check what Render's native Node runtime does for an open range before choosing, and keep parity.
- **Related:** `w1/121` — service `envVars` such as `BP_NODE_VERSION` do not reach the kpack build today, so a tenant cannot work around this themselves.
- **Done when** a `builder: buildpack` build of `examples/hello-node` serves `200` on production, with a regression check.
