## Objective

Make the backend derive the build-Job name identically to the operator so deploy Cancel and built-image lookup address the Job the operator actually created. Today the backend's `buildJobName` truncates `bld-<name>-gen-<generation>` with a plain slice `n[:63]` while the operator truncates with a hash-suffixed `stableKubernetesName`; above 63 chars the two names differ and the backend targets a Job that never exists.

## Context

- Backend: `lego/backend/internal/deploys/service.go:196-203` (`buildJobName`, plain slice); lookups at `deploys/service.go:634,645`. Its comment claims it "mirrors … exactly" the operator — it doesn't.
- Operator (authoritative — it creates the Job): `lego/operator/internal/build/build.go:1031-1041` (`JobName`) via `stableKubernetesName` (`build.go:1047-1056`).
- The modules cannot import each other; both import `lego/types`.
- Same class nearby: `lego/operator/internal/predeploy/predeploy.go:129-134` uses a plain slice — check whether the backend's predeploy log reads (`type=predeploy` in the logs feature) derive the same name for long App names.

## Steps

1. Preferred: add the hash-truncating name derivation to `lego/types` (e.g. a small `k8sname` helper or a function beside the existing shared contract) and call it from both `build.JobName` and the backend's `buildJobName`. Fallback if a types change is too invasive: replicate the operator algorithm in the backend and pin both with golden vectors.
2. Add a regression test with an App name long enough that `bld-<name>-gen-<n>` exceeds 63 chars asserting the two derivations agree (shared-helper call sites, or identical golden-vector outputs in each module's tests).
3. Audit the predeploy naming pair; align the same way if forked.
4. New Go files carry the Apache-2.0 header from `lego/operator/hack/boilerplate.go.txt`.
