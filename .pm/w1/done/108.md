**CNB runtime crash is not caused by the bump; no revert.** `hello-node` declares `engines.node: ">=20"`, so node-engine picks the newest line. The new builder (8.8.0) picks 26.10.0. The old builder `5799343c…` bundles node-engine 8.5.1, whose newest dependency is 26.5.1. `objdump -p` on the nodejs.org `linux-x64` tarballs that both buildpack.toml files point to shows that **both** 26.5.1 and 26.10.0 have `NEEDED libatomic.so.1`, while 24.21.0 does not. A layer listing of **both** the old run image (`run-jammy-base@sha256:20cc5001…`) and the new one (`33c1e0d7…`) for amd64 shows no `libatomic`. The old pins would therefore have produced the same crash. `cnb-builder`, `cnb-stack-build` and `cnb-stack-run` built and exported correctly, so they are accepted. Separate follow-ups, not in scope here:

- (a) Paketo Node 25+/26 on `run-jammy-base` lacks `libatomic1`. The likely fix is a fuller run image or a default `BP_NODE_VERSION`.
- (b) Service `envVars` (here `BP_NODE_VERSION`) did not reach the kpack `Image.spec.build.env`. The App spec carried no literal env, so `buildEnv()` forwarded nothing. As a result, `BP_*` cannot currently be set through the REST API.
- (c) No production App uses `builder: buildpack` today.

The build-stack digest `01fb3e25…` (amd64 manifest `9f47e1f3…`) is inside the kpack-composed builder. It could not be read directly without kpack RBAC. The successful ClusterStack reconcile, plus the run-image half of the same stack resolving to the new digest, is the evidence for it.
