# 056 — MCP drops typed error codes on 130 of 175 tools

From the 2026-08-19 architecture survey ([Bex Refactor Ledger](https://claude.ai/code/artifact/5ceae798-6df1-4f3c-94b6-6b1126f640c2) §0). `core.MCPError` reaches only 6 of 24 MCP adapters — envgroups (17 call sites), agentsessions (16), webhooks (8), sandbox (4), apps (3), secrets (1) — and **zero** uses in `postgres/mcp.go` (23 tools), `keyvalue/mcp.go` (6), `members/mcp.go` (10), `deploys/mcp.go` (7), registrycreds, projects, environments, jobs. So a coded error that REST returns in `params` (`core/http.go:265`) and GraphQL in `extensions` (`core/errors.go:209`) — `PLAN_LIMIT`, `PAYMENT_REQUIRED`, `AGENT_SESSION_LIVE_LIMIT`, … — is silently flattened to plain text for most agent-facing tools, which is exactly the surface agents parse programmatically.

**Fix.** Wrap once at the shared tool-registration seam (the place all 24 adapters register their handlers) so every tool's returned error is mapped through the coded-error → MCP-error translation, instead of relying on per-handler discipline. Make the wrapper idempotent so the 6 adapters already calling `core.MCPError` don't double-wrap; then the per-handler calls can be dropped opportunistically (not required here).

**Constraints:** tool count and schemas must not change — `TestMCPParityInventory` (w1/m70) and the m70/m71 classification guard must stay green; this is an error-shape fix, not a surface change.

**Acceptance:** a regression test driving a coded error through a previously-uncovered adapter's tool (e.g. a postgres tool hitting `PAYMENT_REQUIRED` or a quota code) and asserting the code survives in the MCP error payload; existing MCPError-using adapters keep byte-identical output; `go test ./...` green from `lego/backend/`.
