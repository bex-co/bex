## Objective

Audit that the Events feed is consistent across all three API surfaces (REST, GraphQL, MCP) and matches Render's documented behavior.

## Context

This is a standing closing task for milestones that touch REST/GraphQL/MCP/UI surfaces. See [docs/ADR018-render-parity.md](../../../docs/ADR018-render-parity.md) for the parity ledger.

Render's events are documented at:
- OpenAPI spec (if public)
- Dashboard behavior (captured in t001)
- Official MCP server (if any expose events)

## Steps

1. Compare REST `GET /v1/services/{id}/events` response against GraphQL `serviceEvents` query:
   - Same fields? (id, timestamp, type, details, cursor)
   - Same event types? (deploy_started, deploy_ended, config_changed, etc.)
   - Same pagination semantics? (cursor-based, limit, defaults)
   - Same error shapes? (e.g., both 400 on invalid date range)
2. Compare GraphQL against MCP (from t002):
   - Tool name and arguments match the pattern of other list tools
   - Same event schema returned
3. Compare all three against Render's documented contract (OpenAPI, docs)
   - Any fields Render shows that bex omits?
   - Any fields bex shows that Render doesn't? (if so, mark as a documented bex extension)
4. Check ADR018's events row — update it if this milestone added new coverage
5. Verify `TestEventSurfaceParity` passes (the existing test that pins REST=GraphQL consistency)

- `lego/backend/internal/events/rest.go`

## Acceptance criteria

- [ ] REST, GraphQL, and MCP return identical event schemas
- [ ] All three surfaces accept the same query parameters (serviceId, type, startTime, endTime, cursor, limit)
- [ ] Pagination semantics are consistent across surfaces
- [ ] Error messages are consistent (no naked errors in one surface)
- [ ] TestEventSurfaceParity passes
- [ ] ADR018 events row is accurate (✅ fully implemented or ◐ if any gaps remain)

## Out of scope

- Implementing fields beyond what Render exposes (those are non-goals)
- CLI compatibility (separate work in docs/cli-compatibility-checklist.md)
