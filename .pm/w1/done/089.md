# 089 — `GET /v1/webhooks/event-types` always answers `400 invalid path parameter "webhookId"`: the strict Render validator reads `event-types` as a webhook id

Why: bex registers, authz-classifies and documents a REST route for the webhook event vocabulary that no client can ever reach. It is the only one of 183 REST routes shadowed this way, and nothing guards against the next one.

**Absorbed 2026-09-15 into [w2/m100](../../w2/m100/README.md)** — tracked there; this note is closed.

- **Severity:** minor. The dashboard reads the vocabulary over GraphQL `webhookEventTypes` (`dashboard/src/features/webhooks/api/webhooks.graphql:40-42`), and MCP returns it in `list_webhook_endpoints` (`lego/backend/internal/webhooks/mcp.go:94`). REST is the one surface whose route never answers.
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 13 (outbound webhooks journey). Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`.

## Root cause

- **The route exists.** `lego/backend/internal/webhooks/rest.go:250-254` registers `GET /v1/webhooks/event-types`. Its comment says it is "what the dashboard's event-type picker lists", which is untrue: the picker uses GraphQL.
- **The validator claims it.** `renderRequestValidator.ServeHTTP` (`lego/backend/internal/api/render_openapi.go:360-409`) passes a request through only when bex's mux has **no** pattern for it. This route has one, so the validator asks the pinned Render spec (`internal/api/openapi/render-public-api-1.json`) for a route. `FindRoute` matches Render's `GET /webhooks/{webhookId}` (`retrieve-webhook`), and `event-types` fails `webhookId`'s id pattern, giving a `400` before bex's handler runs.
- **Why tests miss it.**
  - `TestRenderRouteIntersectionInventory` (`render_openapi_test.go:183-223`) walks only Render templates against bex's mux, never bex literal paths against Render templates.
  - `TestRenderRequestValidatorPassThroughBoundaries` (`:428-457`) uses a synthetic mux.
  - `crossworkspace_rest_test.go:151` and `scope_matrix_ops.go:620` classify the route as if it were reachable.

## Blast radius (exhaustive)

- **Only this route.** A segment-wise comparison ran over every `Handle`/`HandleFunc` pattern under `lego/backend/internal` (183 routes, non-test) against the pinned spec's 208 operations. It counted a route as shadowed when a same-method Render path matched with a `{param}` where bex has a literal and Render has no exact literal operation for that path. Result: **1**, `GET /v1/webhooks/event-types` ⇐ Render `GET /webhooks/{webhookId}`.

## Fix (~45m)

- **Pass bex-native literal routes through.** In `ServeHTTP`, skip Render validation when the matched bex mux pattern has a literal segment where the matched Render template has a parameter. That request is routed to a bex-native handler, not the Render operation. Keep validation for every real intersection (`TestRenderRouteIntersectionInventory`'s list stays unchanged).
- **Fix the comment** at `rest.go:250-251`: GraphQL serves the picker; REST is for API clients.
- **Tests:**
  - a composed-server test: `GET /v1/webhooks/event-types` → `200` with `EventTypes`, while `GET /v1/webhooks/whk-<20 chars>` still runs Render validation, and a malformed id still gets `400`;
  - a reverse inventory guard: every registered bex route checked against the pinned spec fails on any new shadowing.
- **Adjacent classes:** malformed webhook ids keep the `400`, well-formed unknown ids keep the canonical `404`, and nothing changes for Render-shaped routes.
- **Unverified:** whether any external client ever called this route; no dashboard, CLI or doc references it (`grep -rn "webhooks/event-types"` finds only the registration, the scope matrix and the cross-workspace test).
- **Render:** Render has no event-types route; this is a bex extension. Not fixed on `main` as of `fcb1ef507`.
