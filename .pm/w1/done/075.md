# Extract a shared `ConfirmDialog` for the dashboard's 27 hand-rolled AlertDialogs

Why: 27 dashboard files each re-spell the same confirm-dialog JSX (header title + description, cancel + destructive confirm footer). Any change to the shape — a pending spinner on confirm, a consistent destructive variant, an aria fix — currently has to land 27 times or land inconsistently.

Found during w1/m86's simplify pass. The disk tab (`features/services/components/disk-section.tsx`) added the 28th and 29th copies. It was deliberately NOT locally abstracted: a one-file helper would have made that file diverge from the house idiom rather than converge with it. The fix belongs at the shared level or not at all.

- Count: `grep -rl AlertDialogCancel src/features/ src/common/ | wc -l` → 27 files. Heaviest: `cron-runs-section.tsx` (5), `session-detail-header.tsx` (5), `webhook-deliveries-card.tsx` (3), `active-sessions-panel.tsx` (3), `service-environment-editor.tsx` (3), `secret-file-row.tsx` (3).
- Existing partial precedents to fold in, not duplicate: `common/components/revoke-icon-button.tsx` (the icon-button flavor) and `common/components/protected-confirmation-dialog.tsx` (the server-issued confirm-phrase flavor). A new `ConfirmDialog` should be the plain flavor those two are specializations of.
- Two trigger shapes must both be supported, since both are in live use: an uncontrolled `AlertDialogTrigger` wrapping a button, and a controlled `open`/`onOpenChange` pair driven by a list selection (`disk-section.tsx`'s snapshot restore is the latter).
- Sizing: > 1h across more than one task if the 27 call sites are actually migrated, so promote to a milestone rather than doing it inline. Migration is mechanical but each site needs its test re-checked for the queried role/name.
