# Render's per-service Authentication setting: require sign-in through the customer's identity provider

Why: Render's dashboard lets a paid web service require authentication for every request, through an OAuth app the customer registers with their identity provider, and bex has nothing like it; found by the w1/m645 dashboard ledger, with no changelog entry yet.

- **Found:** w1/m645's first full read of Render's public dashboard bundle (2026-11-26). Row: `UpdateServerAuthConfig` in [dashboard-operations.md](../../docs/render-artifacts/dashboard-operations.md#services).
- **Render (bundle, not gated by a flag):** service Settings has an **Authentication** section, "Enforce authentication for requests to this service.", disabled with "Authentication is only available for paid instances." on a free instance.
  - Fields: an enable switch, **Client ID** ("From your identity provider's app credentials."), a client secret shown as Configured / Not configured ("(leave blank to keep current value)"), and a list of routes "that bypass authentication", each a method (or `ALL`) and a path pattern.
  - `mutation UpdateServerAuthConfig($id, $authConfig: AuthConfigInput!)` answers `authConfig { enabled clientId clientSecretSet skipAuthRoutes { method pathPattern } }` and a `deploy { id }`: saving deploys the service. The form asks for confirmation before it saves.
  - Not in Render's public OpenAPI pin or on render.com/docs as of 2026-11-26: read the docs again before building, since the protocol (OIDC discovery, issuer field, cookie scope) is not visible in the bundle.
- **bex:** no service-level authentication at the edge. The nearest is the inbound IP allowlist (ADR018 § Custom domains).
- **Done when:** Render's docs for the feature are captured, and the work is filed as a milestone (edge auth in front of the service, REST/GraphQL/MCP, Settings UI, paid-plan gate), or the user signs off a divergence in ADR018 and the ledger row moves to that.

**Done 2026-11-26: the feature sits behind a Render frontend flag, and no docs exist to capture.** The note's "not gated by a flag" was wrong. The Settings section renders only when `oauth_proxy` is on, and so does the new web service form's Authentication block. `oauth_proxy` is a hook of Render's `frontendFlag` chunk, which reads `allFrontendFlags`. Render's server answers that query for the signed-in user, workspace and organization, and the dashboard reads a flag the answer leaves out as off. As of 2026-11-26, render.com/docs and the changelog have nothing on the feature: the docs index's nearest pages are Private Services, Inbound IP Rules and Managed OIDC, and Managed OIDC covers tokens a service sends out, not visitors signing in. The public API pin has nothing on it either. The ledger treats a flagged feature as `flagged` until its gate goes, as it does `postgres-parameter-overrides`, so this closes without a milestone. Two changes make the ledger hold that:

- `UpdateServerAuthConfig` is now `flagged` on `oauth_proxy` in [dashboard-operations.md](../../../docs/render-artifacts/dashboard-operations.md#frontend-flags).
- `scripts/lib/render_dashboard_ops.py` reads the frontend-flag chunk as well. w1/m645's parser read only the `featureflags` chunk, so it missed all 29 frontend flags. Each one now has a row, and `scripts/render-dashboard-ops.test.sh` covers the second mechanism.

When `oauth_proxy` leaves the bundle, the weekly `render-dashboard-ops` job fails and names this note. Then read Render's docs and file the build from the findings above, or sign a divergence off in ADR018. More of the bundle, for that build:

- **Copy:**
  - The switch is headed "Require Authentication: When enabled, all requests must be authenticated. Unauthenticated requests will be directed to sign in."
  - The public routes are headed "Public routes: Define path patterns that bypass authentication. Your server must do its own authorization checks for these routes." The "path patterns" link goes to Render's redirects and rewrites rule syntax.
  - A route is "All methods" (`ALL`, sent as `null`) or one HTTP method, plus a path. A missing leading `/` is added. A comma is refused ("Cannot contain a comma"), and the placeholder is `/webhooks/slack/:provider`.
- **Confirm dialogs (the typed confirm is `sudo auth <enable|disable|update|lock> <service name>`):**
  - "Enable Authentication": "Users will be required to sign in before reaching this service."
  - "Disable Authentication": "Authentication will be disabled. The service will become publicly accessible."
  - "Update Authentication Settings".
  - Enabling with an empty Client ID or Client Secret shows "Enable maintenance mode": "The service will be unreachable until both are provided."
  - Enabling on a service in maintenance mode shows "Enable authentication and disable maintenance mode". This is why the mutation also answers `maintenanceMode { enabled uri }`.
- **Plan:** a free instance shows "Authentication is only available for paid instances." with an Upgrade button to the service's plan page. The section is offered on web services only. `createServer` carries `authConfig` only for a paid plan.
