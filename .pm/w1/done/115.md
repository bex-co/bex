# Make usage-coverage diagnostics expose missing evidence

Why: the current diagnostic excludes streams with no health rows and cannot identify absent hours, undermining diagnosis of coverage pinned at the month boundary.

**Estimate:** 45m. **Status:** done 2026-09-29. User-approved brainstorm item 4, 2026-09-28.

## Scope and acceptance

- Create a reusable workspace-scoped, read-only query such as `scripts/usage-coverage-diagnose.sql`; align expected intervals with `CurrentUsageCoverage`, `aggregateUsageCoverage` and `evaluateStreamCoverage` in `lego/backend/internal/store/usage.go`.
- Enumerate expected hours within the requested period and each stream's expected lifetime, joining with the correct workspace/resource identity; report first missing and first unhealthy evidence separately.
- Demonstrate with small local fixtures that zero-health-row streams appear, a missing first hour is detected despite later healthy rows, and healthy/closed streams respect their bounds.
- Replace the flawed query in [w4/m139/t002](../../w4/blocked/m139/t002.md) with the verified query or invocation and link the reusable artifact. Do not overwrite original production observations.
- Distinguish missing health evidence from missing billable usage. No production query execution, collector repair, billing change or claim of resolving the production incident is part of this note.

## Source and goal

The source task's `LEFT JOIN` is null-rejected by `WHERE h.window_start >= ...`; its minimum non-healthy recorded timestamp cannot detect an absent interval. This supports trustworthy usage reporting under ADR008. Only diagnostic preparation is extracted; production attribution and any repair remain owned by w4/m139/t002, whose current access blocker is unchanged.

## Done (2026-09-29, `/loopx w1`)

[`scripts/usage-coverage-diagnose.sql`](../../../scripts/usage-coverage-diagnose.sql) is a read-only psql script (`BEGIN READ ONLY`, `-v ws=… [-v now=…]`). It mirrors `CurrentUsageCoverage`, `evaluateStreamCoverage` and `aggregateUsageCoverage` hour by hour:
- It uses the same in-scope rule and the same expected range per stream, `[max(hour(expected_from), month start), min(last closed hour, hour(expected_through)))`, in UTC.
- It reports every in-scope stream with `expected_hours`, `health_rows`, `first_missing_health`, `first_unhealthy` (a period-wide scan, as the Go health pass does), `observed_through` and a verdict.
- It reports billable `usage_hours` and `first_missing_usage` separately.

It was validated against a throwaway `postgres:16-alpine` with **every real migration applied**, loaded with [`scripts/usage-coverage-diagnose.fixtures.sql`](../../../scripts/usage-coverage-diagnose.fixtures.sql):
- A zero-health-row stream appears (`srv-zero`, behind at 00Z).
- A missing first hour is detected despite five later healthy rows (`srv-gap`, behind at 00Z). The old query could see neither of these.
- A degraded hour after an earlier gap is reported alongside the gap (`srv-late`: missing at 01Z, unhealthy at 03Z).
- A closed stream respects its bound (`srv-closed`, complete through 03Z).
- A healthy stream is complete, with its usage reported separately (`srv-ok`: 6 usage hours; every other stream shows usage missing independently of health).
- Another workspace's stream is excluded.

The default `now` and the missing-`ws` usage message were also exercised. w4/m139/t002's flawed inline query is replaced by this invocation; its production observations and its production-read gate are unchanged. No production query was run.
