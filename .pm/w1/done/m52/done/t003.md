## Objective

A transient network blip (a roll window, an LB hiccup) must not strand the dashboard in a persistent error state. Today `loadRouteResource` dehydrates `{state: "error"}` into the page and no child ever re-runs it — the `/project/$projectId` page showed "Couldn't load resources" until a manual reload even though the API had recovered seconds later.

## Context

- `dashboard/src/common/lib/document-head/index.ts` `loadRouteResource` (the route-loader wrapper used by the project/service/database/keyvalue/webhook shells) — the dehydrated error is the strand.
- Apollo client factory: `dashboard/src/common/apollo/`. Loaders use `fetchPolicy: "network-only"`.
- Reads are safe to retry; **do not blanket-auto-retry mutations** — they are not idempotent in general. The existing mutation error toasts stay; users retry writes explicitly.
- The incident's move-error toasts were real transport failures of `setProjectServices` calls mid-roll — with t001's drain those stop failing at the source; this task only makes *reads* self-heal.

## Steps

1. Add a retry link (network/transport errors only, ~2 attempts with short backoff, queries only) to the Apollo client chain — applies to both the SSR and browser clients.
2. On client hydration, when a route's dehydrated loader result is `state: "error"`, re-run the loader once (e.g. `router.invalidate()` from a small shared hook mounted by the resource shells, the same pattern as `useNotFoundRedirect`).
3. Unit-test both: retry link retries transport errors and not GraphQL errors; hydration re-run fires exactly once on error state and not on ready/not-found.

## Files

- `dashboard/src/common/apollo/`
- `dashboard/src/common/lib/document-head/index.ts`
- `dashboard/src/common/hooks/` (new `use-loader-error-retry` or similar, mounted beside `useNotFoundRedirect` in the resource shells, e.g. `routes/project.$projectId.tsx`)

## Acceptance criteria

- [ ] With bex-api briefly unreachable during SSR, the hydrated page self-recovers to data without a manual reload.
- [ ] GraphQL-level errors (forbidden, bad request) are NOT retried and still render the error state immediately.
- [ ] Mutations are not auto-retried anywhere.

## Out of scope

- Optimistic-UI / offline queueing for mutations.
- Server-side drain and readiness (t001/t002).

## Outcome (2026-07-18)

Shipped: (1) `RetryLink` (queries only; transport failures + 5xx/429; never mutations, never GraphQL errors, never 4xx) in front of both the SSR and browser HTTP links; (2) `useLoaderErrorRetry` mounted in all seven resource shells beside `useNotFoundRedirect` — on a dehydrated `state:"error"` it re-runs the loaders ONCE via a same-location replace navigation, and on the error→ready transition runs one more to recompute the head.

Two upstream quirks found live and worked around: `router.invalidate()` re-runs loaders but never recomputes `match.meta` (stale error `<title>` survives recovery), and even a navigation's meta is computed at commit from the loaderData available then — hence the second navigate.

Evidence (dev-1, live browser through a TCP proxy with a 5s outage): mid-outage navigation ⇒ "Couldn't load resources" + "Something went wrong" title at t=13.9s ⇒ hands-off recovery to full data + correct title at t=15.2s, ~0.5s after the API returned. No reload, no user action.
