## Objective

A failed pre-deploy command always closes its deploy with a reason like "pre-deploy command exited with code 3 — see the pre-deploy logs". It carries the timeout wording only when the command really exceeded its window.

## Context

- `lego/backend/internal/store/reconciler.go:1310-1339` (`failureReasonFor`: requires `c.ObservedGeneration == app.Generation`, else `timedOutDeployReason`) and `:1341-1346` (the timeout text).
- `lego/operator/internal/controller/app_controller.go:4262` (`setNotReadyCondition` stamps `obj.GetGeneration()`). Nothing under `lego/operator/internal/predeploy/` reads a container exit code, so today's message is the Job condition text (`BackoffLimitExceeded: Job has reached the specified backoff limit`).
- Precedent: `w6/done/m123` made failed **build** reasons human (no Kubernetes internals).
- Live evidence: m149 README § Evidence 2 and 4 (two identical failures, two different wrong reasons).

## Steps

1. **Reproduce the timeout-text case deterministically** in a store/reconciler test (the row closes before the matching Ready condition is observed). Fix the ordering so a `PreDeployFailed` row never takes the timeout fallback.
2. **Operator:** when the pre-deploy Job fails, read the pod's terminated container state and record the exit code (and signal, if any) in `status.preDeploy.message`. Keep the timeout-exceeded case distinct.
3. **Store:** map it to the human reason. Don't expose `BackoffLimitExceeded`.

- [ ] Tests cover: an immediate non-zero exit, a real timeout (keeps the timeout text with its window), a superseded/canceled pre-deploy (not a command failure), and build and rollout timeout wording unchanged (controls).
