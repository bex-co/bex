## Objective

Close Finding 7 (improper-certificate-validation, CWE-295): production workflows fetch `/etc/kubernetes/admin.conf` over SSH with `StrictHostKeyChecking=accept-new`, and none of them supplies the helper's already-implemented `BEX_SSH_KNOWN_HOSTS_FILE` pin — so a first-seen control-plane host key is trusted on faith, and the subsequent `cluster-info` check authenticates only against the CA embedded in that same unverified kubeconfig. The fix is mostly wiring: the seam exists, no caller uses it.

## Context

- `scripts/fetch-app-kubeconfig.sh:23-50` — optional `BEX_SSH_KNOWN_HOSTS_FILE` → `UserKnownHostsFile`, but `StrictHostKeyChecking=accept-new` is hardcoded.
- `scripts/verify-substrate.sh:38-39` — same optional seam, same gap.
- `.github/workflows/app-cluster.yml:45-52`, `.github/workflows/deploy.yml:471-489` and `:502-515` — the production callers; later steps write cloud/deploy Secrets with the fetched kubeconfig.
- Repo rule: `.env.example` mirrors `.env` variable names, and `scripts/gh-secrets.sh` pushes `.env` into Actions secrets.
- Report: report.md Finding 7.

## Steps

1. Make the helper fail closed when a known-hosts file is supplied: `StrictHostKeyChecking=yes` in that branch, `accept-new` only in the unpinned (local/dev) branch, with the choice logged.
2. Add a `BEX_SSH_KNOWN_HOSTS` secret path: workflows materialize the secret to a temp file and export `BEX_SSH_KNOWN_HOSTS_FILE` when it is non-empty, so activation is a secret away and the unpinned path stays byte-identical until then.
3. Mirror the new name in `.env.example` (name + comment, never a value) so `scripts/gh-secrets.sh` carries it.
4. Document the one-time capture (`ssh-keyscan` against a known-good control plane, verified out of band) in the relevant runbook/ADR next to the existing SSH-credential trust chain (`docs/ADR019-infra-credentials.md`).
5. Apply the same treatment to `scripts/verify-substrate.sh` so the two SSH entry points cannot drift.

## Acceptance criteria

- [ ] With a known-hosts file supplied that lacks/mismatches the host key, the helper exits non-zero **before** `admin.conf` is read (verified with a local sshd-less negative test or an explicit dry-run assertion).
- [ ] With no known-hosts input, behavior is byte-identical to today (no CI breakage before the secret exists).
- [ ] `.env.example` carries the new variable name; workflows wire it conditionally.
- [ ] The capture procedure is written down where the credential trust chain lives.

## Out of scope

- Provisioning the actual host key into GitHub Actions secrets (operator action — call it out in the milestone closeout as the activation step, like ADR035's production gates).
- Pinning the Kubernetes CA fingerprint independently (worth a follow-up note; the host-key pin is the load-bearing half).
