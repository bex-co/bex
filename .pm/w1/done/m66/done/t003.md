## Objective

Close Finding 8 (token-validation, CWE-345): `missingPKCE()` tests only that `code_challenge` is present and never reads `code_challenge_method`, so a `plain` or method-omitted authorization-code request reaches consent acceptance. The function's own doc comment states the intended invariant ("require a code_challenge (S256)"), so this is implementation-versus-intent drift, not a design choice — and Hydra runs with Dynamic Client Registration enabled (`deploy/gitops/base/values/hydra.values.yaml:63-68`), so confidential DCR clients are reachable.

## Context

- `dashboard/src/common/server-fn/hydra-consent.ts:110-124` — `missingPKCE`; `:219-230` (GET/headless path) and `:325-339` (POST/human-decision path) are the two call sites.
- The RFC 8628 device path (`/oauth2/device/verify`) must stay exempt — it has no redirect and no verifier.
- `docs/ADR012-auth.md` §7/§8a — the OAuth surface this gate protects.
- Report: report.md Finding 8.

## Steps

1. Rewrite the guard to parse the authorization request once and reject unless: the request is the device exception, **or** `response_type` has no `code`, **or** (`code_challenge` non-empty **and** `code_challenge_method` is exactly `S256`).
2. Reject duplicated `code_challenge`/`code_challenge_method` parameters and mixed-case/malformed method values explicitly.
3. Keep one shared implementation for both entry points (the report's preventive control) and keep the refusal message accurate.
