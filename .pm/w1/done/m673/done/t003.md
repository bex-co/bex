## Objective

Serve Render's operation on bex-api's GraphQL with Render's names, so the dashboard can call it as Render's does.

## Context

- Render: `isDeployableImage(externalImageReference: ExternalImageReferenceInput!): { deployable failureCode failureReason }`, input `{ imageUrl, registryCredentialId }`; the type names come from t001.
- Schema snapshot: `lego/backend/internal/api/testdata/schema.graphql`. Scope tables: `lego/backend/internal/api/scope_matrix_ops.go` (`OpClassRead`) and `key_permission_ops.go` (`core.KeyWorkspaceRegistry`, as `GQL Query.registryCredentials`).
- Workspace resolution: a credential belongs to one workspace. With a credential, the check runs in that workspace, and the caller must be able to read the credential (`registryCredential(id)`'s rule). Without one, the check runs in the caller's current workspace. The per-workspace limit from t002 then applies.

## Steps

1. Add the input type, result type and code enum to the GraphQL schema with Render's names, and resolve the field through t002's check.
2. A credential id the caller cannot read answers the same not-found error `registryCredential(id)` answers. It does not answer a `failureCode`, so ids cannot be probed.
3. Register the operation in both scope tables, and regenerate the schema snapshot.
4. Real-DB tests: a member and an API key with `KeyWorkspaceRegistry` get an answer; a key without it and a member of another workspace using that workspace's credential are refused; each code reaches the GraphQL answer.
