## Objective

See every definition-of-done item work end to end, first on dev-1, then on production once a pin carries the milestone.

## Steps

1. On dev-1 (`bash scripts/dev-env.sh 1 up`, bex-api built from the tree), in the create form and in a disposable image service's Settings, walk these cases:
   - a public image (`docker.io/library/nginx:latest`);
   - a missing tag;
   - a malformed URL;
   - an image published only for the other architecture;
   - a private image with no credential, with a wrong credential and with its right credential.
   Note each message, icon and button state.
2. Compare each pending frame with its ready state at 1440 and 390 px, and check that no page scrolls sideways at 390 px.
3. Over GraphQL, as an API key with and without `KeyWorkspaceRegistry`, check the answers and the refusal. Point a URL at a loopback or metadata host and check that it answers `invalid_input_url` without a dial.
4. On production, after a `chore(deploy): pin platform images to <sha>` carrying the milestone: sign in as the QA user with `bash scripts/qa-login.sh` and repeat steps 1 and 2 in `bex-canary` with disposable services, then delete them and sign out. Name only bex's fixture workspaces in the record.

**The window.** Nothing scrolls sideways at either width (`scrollWidth` equals `clientWidth`). At 1440 px the window never scrolls, and Settings, both the page and the dialog, does not scroll the window at 390 px.

At 390 px the create form does let the window scroll, by 717–857 px, in pending and ready frames alike, once a source shows the rest of the form. The cause is not this milestone. The form's Generate button has a label with `sr-only @md:not-sr-only`. That label is absolutely positioned, and the page scroller around it is static, so nothing inside the scroller contains it. This is the leak w1/m657 found, and `83a2ff4630` fixes it by adding `relative` to `PAGE_SCROLL_CLASS`, which the create page uses. Pin `6ba91ca5b72f` does not carry that commit yet. Adding `relative` to the live scroller took the window's scroll to 0, and `scrollTo(0, 1e6)` left `scrollY` at 0, both while the check was held and after it answered.
