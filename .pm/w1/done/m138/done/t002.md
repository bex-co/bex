## Objective

Stop the Events feed from re-deriving the deploy status client-side. With t001 the backend now says exactly which failure kind occurred and why; the route should render that, so `build_failed` / `pre_deploy_failed` badge correctly and the failure reason appears beside the `Deploy ended` line.

## Context

- `dashboard/src/routes/services.$serviceId.events.tsx:224-250` — the `status` derivation hand-maps `details.deployStatus` (`succeeded` → `live`, `failed` → `update_failed`); `deploy_started` handling (`update_in_progress` unless finished) is correct and stays.
- `dashboard/src/features/services/api/events.graphql` — the `ServiceEvents` query's `details` selection; add the two new fields. Regenerate types (`dashboard/CLAUDE.md` codegen).
- The Deploy detail page already renders `failureReason` (`dashboard/src/features/deploys/components/deploy-detail-page.tsx`) — reuse its presentation/copy rather than inventing a second one.

## Steps

1. Select the new fields in `events.graphql`; run codegen.
2. For `deploy_ended`, take the badge status from the backend's extra status field (fall back to the old mapping only when the field is absent, e.g. older events); pass `failureReason` into `EventSummary` (or the row) and render it with the same component/copy the Deploy page uses. Add `en` and `zh` strings if new copy is needed.
3. Update `services.$serviceId.events` tests: a `build_failed` event badges `build_failed` and shows the reason; a succeeded event shows none.
