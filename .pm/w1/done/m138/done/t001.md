## Objective

Give the `deploy_ended` event enough detail that a consumer can badge the deploy the way the Deploy page does and show why it failed. Today `events.Details` carries only Render's lossy 3-value `deployStatus` (`store.RenderDeployStatus` collapses `build_failed`, `pre_deploy_failed`, `update_failed` to `failed`), so `failureReason` and the specific failure kind never reach the events adapters.

## Context

- `lego/backend/internal/events/service.go:437-444` — `Details` struct; `:710-711` fills `DeployStatus` / `PreDeployStatus` from the deploys row (`r`).
- `lego/backend/internal/store/store.go:176-189` — `RenderDeployStatus`; `:263-269` — the deploy row's `FailureReason`.
- Adapters: `lego/backend/internal/events/rest.go:75-76` (JSON tags, `preDeployStatus` is the precedent for a bex extra), `graphql.go:56-60`, `mcp.go`.
- Render's `deploy_ended.details.deployStatus` enum is `succeeded | failed | canceled`; it must not change.

## Steps

1. Add `FailureReason string` and a bex-extra field carrying the deploy object's own status (`live | build_failed | pre_deploy_failed | update_failed | canceled | …`; pick a name consistent with `preDeployStatus`'s style and document it in the struct comment) to `Details`; fill both at `:710-711` from the deploys row.
2. Expose both on REST (`omitempty`, comment "bex extra"), GraphQL (add to the `ServiceEventDetails` type in the schema + field map), and MCP (same JSON shape as REST).
3. Extend `lego/backend/internal/events/service_test.go` / `vocabulary_test.go`: a `build_failed` deploy row yields `deployStatus: failed`, the extra status `build_failed`, and the row's `failureReason`; a live deploy yields empty extras.

## Files

- `lego/backend/internal/events/service.go`, `rest.go`, `graphql.go`, `mcp.go`
- backend GraphQL schema (the `ServiceEventDetails` type)
- `lego/backend/internal/events/service_test.go`

## Acceptance criteria

- [ ] `GET /v1/services/{id}/events` for a `deploy_ended` of a build-failed deploy returns `deployStatus: "failed"` plus the extra status and `failureReason`; a succeeded deploy returns neither extra.
- [ ] GraphQL `serviceEvents { details { … } }` and the MCP events tool return the same two fields with the same values.
- [ ] Render's `deployStatus` enum is unchanged (`TestRenderConformance` / events vocabulary tests stay green).

## Out of scope

- Dashboard rendering (t002, t003).
- Adding the fields to `deploy_started` (Render's `deploy_started` intentionally has no terminal status).
