## Objective

When the model proxy is refused a credential because the workspace has no key, tell bex-api — so the session terminalizes on the spot with `ModelAuthFailureReason` instead of returning a bare 403 and letting the agent CLI retry its way into a raw JSON-RPC error.

## Context

- `lego/backend/internal/sshgateway/modelproxy/modelproxy.go:162-171` is the gap: any `ErrForbidden` from `mintWithRetry` becomes `http.Error(w, "forbidden", 403)` with no report.
- Forty lines below, the vendor-rejection path does the right thing (`modelproxy.go:200-210`): on an upstream 401/403 it calls `b.reportAuthFailure(verified)` with the comment "Report it so bex-api terminalizes the session in seconds (w5/m80 t003) rather than the agent CLI riding its full retry/backoff (~3min observed)." The missing-key case has the same consequence and needs the same treatment.
- `reportAuthFailure` (`modelproxy.go:226-236`) is already detached, time-bounded (`authFailureReportTimeout`, 5s) and best-effort — it only logs on failure, so calling it on a second path adds no new failure mode.
- Calling it here is **safe**: `ModelAuthFailer.Fail` independently re-resolves the session and re-checks `currentSandboxCaller` (`lego/backend/internal/agentsession/model.go:350-362`), so a stale or cross sandbox cannot use this to terminalize a live session — it 403s at bex-api, harmlessly. Do not weaken that check.
- `mintWithRetry` (`modelproxy.go:256-271`) retries on `ErrForbidden` for `mintModelRetryAttempts`. A missing key is **not** transient, so the new sentinel should also skip the retry loop rather than burn its attempts — this is where the ~13 mint-denied log lines over ~5s came from in `dev-1`.
- Observed today (`ags-da9674i9086hnle27720`): `phase = failed`, `failure_reason = "Internal error: Failed to authenticate. API Error: 403 forbidden\n (code -32603)"` — the ACP adapter's own error text, surfaced verbatim to the tenant.

## Steps

1. In `mintWithRetry`, treat the t001 sentinel as terminal: return immediately instead of retrying (a missing key will not appear mid-turn).
2. In the `mintWithRetry` error branch, when the error is the t001 sentinel, call `b.reportAuthFailure(verified)` before writing the response.
3. Keep the response to the sandbox a 403 — the sandbox learns nothing new, and the driver's existing handling is unchanged. Only bex-api's bookkeeping changes.
4. Pick the metrics label deliberately: the existing `b.Metrics.Authentication("rejected_target")` is about a target mismatch and now under-describes this case. Add a distinct label (mirroring `vendor_auth_rejected`) so the two refusals stay separable in metrics.
5. Confirm the whole path against `dev-1` per `.pm/w1/dev-1/README.md`: delete the key at `tenants/data/default/agent-sessions/<ws>/model-key`, start a repo-less session, and read `failure_reason` from the `agent_sessions` row.

## Acceptance criteria

- [ ] A mint refused for a missing key reports the auth failure exactly once and the session lands `failed` with `ModelAuthFailureReason`.
- [ ] It is **not** retried by `mintWithRetry` — one refusal, not `mintModelRetryAttempts`.
- [ ] A mint refused for an authorization reason (stale/cross sandbox, session not found) still returns 403 and reports **nothing**.
- [ ] The two refusals carry different `Metrics.Authentication` labels.
- [ ] Verified live in `dev-1` with the key removed: `failure_reason` is the actionable string, and the ~13 `mint denied` log lines collapse to one.

## Out of scope

- Preventing the session from starting at all when `capabilities.modelKeyReady` is false — that is `w4/m89` t004.
- Any change to the vendor-rejection path (`modelproxy.go:200-210`), which already works.
- Changing the wording of `ModelAuthFailureReason`; t003 decides whether it still reads correctly for this cause.
