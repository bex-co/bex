## Objective

Ship drain-guard the same way the activator ships: one image with an extra entrypoint, its own ServiceAccount, and a Deployment on the platform pool. It is added through `config/prod`, not `config/default`, for two reasons. Production CAPI manages its own cluster, while the local mock keeps CAPI in `kind-bex-mgmt`. And `config/prod` has no namespace transformer, so the `bex-capi` Role keeps its namespace beside the rest of drain-guard's manifests.

## Context

- Pattern: `lego/Dockerfile` build and copy lines, `lego/operator/config/activator/`, `lego/operator/config/default/kustomization.yaml`, `scripts/image-pin-validate.sh`.
- Prod CAPI namespace is `bex-capi`. The guarded pool is `nodepool=bex-tenant-0` (`infra/clusterapi/overlays/hetzner-caph/cluster.yaml:379-435`).

## Steps

1. Add the `drain-guard` build and copy lines to `lego/Dockerfile`.
2. Add `lego/operator/config/drain-guard/`: ServiceAccount, ClusterRole + binding, the `bex-capi` Role + RoleBinding, and the Deployment. The Deployment runs 1 replica on the platform pool, sets its flags, and uses the restricted security context. List it in `config/prod`.
3. (Merged into step 2.)
4. Register the new Deployment wherever the validators expect every operator-image consumer.

## Files

- `lego/Dockerfile`, `lego/operator/config/drain-guard/*`, `lego/operator/config/prod/kustomization.yaml`
- `scripts/image-pin-validate.sh`

## Acceptance criteria

- [x] `kubectl kustomize lego/operator/config/prod` renders drain-guard, and the GitOps and image-pin validators pass.
- [x] The operator's `config/rbac/role.yaml` is unchanged.

## Out of scope

- Leader election or more replicas. A single replica is enough: CAPI waits for the hook, so a restarting guard only delays a drain.
