# Prod nodes can't pull from Zot out of the box — bake the pull path into the node template

**Found live 2026-07-12** backfilling `beancount-cms`/`eden-cms-v2` to build-from-git on prod: **no git-built image had ever been pullable on prod**. Builds pushed to Zot fine, but every deploy died in `ImagePullBackOff`. Three stacked causes, two fixed where they belong, one hand-applied and still owed a durable home:

1. **Node DNS + plain-HTTP registry** (hand-applied to `bex-tenant-0-b5swk-hnb78` only): kubelet resolves `zot.bex-registry.svc` via **host** DNS (fails) and containerd requires TLS by default. Fix per node: `/etc/hosts` entry for the zot ClusterIP + `/etc/containerd/certs.d/zot.bex-registry.svc:5000/hosts.toml` (`server = "http://…"`, `skip_verify = true`) + `config_path = "/etc/containerd/certs.d"` in `config.toml` + containerd restart. **This must move into the CAPH machine template / cloud-init (`infra/`)** — the cluster-autoscaler mints fresh tenant nodes (max 3) that today would fail every pull. (Also consider a stable NodePort or node-local resolution instead of the /etc/hosts hack.)
2. **NetworkPolicy blocked node-originated pulls** (fixed in `deploy/gitops/base/network-policies.yaml`, pending ship): kubelet pulls arrive from the **node** identity, and under Cilium a k8s `ipBlock` can never match node traffic — added the additive `CiliumNetworkPolicy allow-node-image-pulls` (`fromEntities: host, remote-node`) in `bex-registry`; also applied live (unmanaged by Argo, so it sticks meanwhile).
**Related prod-DB drift fixed live 2026-07-13:** `tenant_invites` was owned by `postgres` while every sibling table is owned by the `bex` app role — every authenticated call spammed `permission denied for table tenant_invites` and invite redemption (w4/m12) was silently broken on prod. Fixed with `ALTER TABLE tenant_invites OWNER TO bex`. Open question: how the table got created as `postgres` (hand-run migration?) — worth a migration-ownership guard.

3. **Zot's 10Gi volume was 99% full** (fixed live): a runaway rebuild loop on the since-deleted `eden-cms-v2-git` app pushed **44+ generations** (~9.7Gi) until blob PUTs 500'd. Deleted all its manifests, restarted zot (startup GC) → 2.5Gi used. **Two residual questions:** what kept bumping that App's generation to 51 (spec-churn loop — reconciler? clone-secret refresh?), and Zot needs retention/GC policy + volume-usage alerting so the registry can't silently fill again.
