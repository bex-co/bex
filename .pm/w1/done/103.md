# 103 — A background worker whose newest release is waiting on or failed a pre-deploy step cannot be suspended, resumed or scaled

> **Promoted 2026-09-15 → `w1/m158`** by user decision during `/loop-worker w1`. The milestone carries the fix, its tests and its live verification.

Why: `w1/m156` lets web and private services keep converging replicas and routing while a newer release's pre-deploy step is pending, running or failed. Workers were left out, because they have no Service or Ingress and never auto-hibernate. But a worker's replica count also follows suspend, resume and manual scale, and those still wait behind the gate's halt. So a paid worker whose latest pre-deploy failed keeps running after Suspend, and stays at 0 after Resume, until the owner ships a new release.

- **Severity:** moderate. Explicit user actions on a paid service are silently ignored, but only while a newer release is held.
- **Found:** `w1/m156` t002, 2026-09-15, traced from the code. Not probed live.

## Where

- `lego/operator/internal/controller/app_controller.go`: `holdUnpassedRelease` returns `held=false` for a worker, so `reconcileKubernetes` still returns on the pre-deploy gate's halt before the Deployment write and `reconcileWorkerStatus`.
- The same freeze for a release still waiting for its image (a queued, running or failed build) affects every type and is `w1/104`.

## Fix

- Give workers the replica half of `convergeServingRuntime`: a scale-only patch of the existing Deployment, then the worker's parked or running status, with no Service or Ingress. Keep the pod template on the prior release.
- Add worker cases to `wake_over_failed_release_test.go`: suspend and resume over a failed pre-deploy verdict, and a manual scale while the step runs.
