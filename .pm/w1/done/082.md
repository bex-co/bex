# Intermittent `ERR_CONNECTION_CLOSED` on api.bex.co mutations

Observed 2026-08-19 (dashboard QA walk, round 2). Several `POST https://api.bex.co/graphql`
**mutations** intermittently failed in the browser with `net::ERR_CONNECTION_CLOSED`,
then succeeded on retry — seen on the workspace member `inviteWorkspaceMember` and
`changeWorkspaceMemberRole` paths (the reads on the same pages were fine).

Why it matters: mutations are **not** auto-retried by the dashboard's Apollo retry
link (only idempotent queries are), so a dropped mutation connection just makes the
action appear to "do nothing" — no toast, no change. This masked the invite-error
toast during testing and would confuse a real user.

Needs characterization before it's actionable — is bex-api closing keep-alive
connections early, an edge/Cloudflare idle-timeout on POST, or a pod roll mid-request?
Reproduce, check bex-api access/error logs + Traefik/edge timeouts around a failing
request id, and decide whether it's a server bug or acceptable transient (and whether
write-safe retry/idempotency-key handling is warranted). Not obviously >1h until
characterized; promote to a milestone if it turns out to be a real server-side defect.
