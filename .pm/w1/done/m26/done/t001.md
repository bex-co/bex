## Objective

Replace the hand-applied, single-node `/etc/hosts` + containerd `hosts.toml` hack with a durable fix baked into the CAPH machine template/cloud-init, so every tenant node the cluster-autoscaler mints (up to 3, per `w1/m3`/`w1/m20`) can pull from Zot on first boot with zero manual steps.

## Context

- Currently only `bex-tenant-0-b5swk-hnb78` has the hand-applied fix: `/etc/hosts` entry for the Zot ClusterIP, `/etc/containerd/certs.d/zot.bex-registry.svc:5000/hosts.toml` (`server = "http://…"`, `skip_verify = true`), `config_path = "/etc/containerd/certs.d"` in `config.toml`, plus a containerd restart.
- Root cause: kubelet resolves `zot.bex-registry.svc` via **host** DNS (fails — that ClusterIP is only resolvable in-cluster), and containerd requires TLS by default against a plain-HTTP internal registry.
- Consider a stable NodePort or node-local DNS resolution as a cleaner alternative to the `/etc/hosts` hack (evaluate both, pick one).
- CAPH overlay lives in `infra/clusterapi/overlays/hetzner-caph/`; machine template / cloud-init config is likely a `KubeadmConfigTemplate` or similar CAPI resource there.

## Steps

1. Decide: node-local DNS resolution vs. a stable NodePort for Zot — pick whichever is more durable against future registry moves.
2. Encode the chosen fix (DNS record or NodePort + containerd `hosts.toml`/`config.toml` config) into the CAPH machine template/cloud-init so it applies on every node boot.
3. Confirm the one hand-patched node's config matches what the template will now produce (no drift between the manual fix and the templated one).

## Files

- `infra/clusterapi/overlays/hetzner-caph/`

## Acceptance criteria

- [ ] A node provisioned from the updated template pulls from Zot with no manual steps (verified in t007).
- [ ] The fix is idempotent across reboots/re-provisions.
