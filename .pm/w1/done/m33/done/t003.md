## Objective

Make a failed pre-deploy step distinguishable from a failed health check on the deploy record, with access to its logs.

## Context

- Deploy history/status lives in `lego/backend/internal/apps` (deploy trigger/history verbs, `w2/done/m11`).
- Logs access follows the existing pattern in `lego/backend/internal/logs` (pod logs / Loki-backed history per `docs/ADR010-observability.md`).

## Steps

1. Add a `preDeployStatus` (pending/running/succeeded/failed) field to the deploy record, distinct from the overall deploy status and from health-check failure.
2. Make the pre-deploy Job's logs retrievable the same way build-Job logs already are (if that pattern exists) or via the standard pod-logs path.
3. Update the deploy-status state machine so a pre-deploy failure short-circuits before any health-check attempt (there's nothing to health-check if the migration failed).

## Files

- `lego/backend/internal/apps/*.go` (deploy record + status)
- `lego/backend/internal/logs/` (if a new log-source wiring is needed)

## Acceptance criteria

- [ ] A failed pre-deploy step is visibly distinct from a failed health check in the deploy record.
- [ ] Pre-deploy step logs are retrievable through the existing logs surface.

## Out of scope

- REST/GraphQL/MCP/bex.yml field wiring for `preDeployCommand` itself (t004).
