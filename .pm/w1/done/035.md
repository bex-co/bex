# Bandwidth/egress router matcher misses Traefik's websecure sibling — HTTPS bytes uncounted

Found 2026-07-18 by w1/m50/t006's month-to-date sanity check. `core.TraefikRouterNamesForIngress` (`lego/backend/internal/core/traefik.go:103`) constructs `<ns>-<ingress>-<host>-<path>@kubernetes` — which matches Traefik's plaintext-HTTP router (for apps in ns `default` the label starts `default-…`, a namespace prefix, not an entrypoint) — but Traefik ALSO mints an entrypoint-prefixed sibling `websecure-<same>@kubernetes` for the TLS entrypoint, and that router carries essentially all real user traffic (HTTPS). Every consumer of the matcher therefore counts only plaintext bytes (mostly the 80→443 redirects):

- the Outbound Bandwidth chart + `monthToDateBandwidth` (verified: the API's 83.1 MB for beancount-cms-v2's July equals the `default-…` router's Prometheus increase (83.4 MiB) almost exactly, while `websecure-…` series sum to hundreds of MB–GB over the same window — treat the raw websecure sum cautiously: router-counter flap/resets inflate `increase()`, the exact hazard ADR023's billing gate guards against);
- the http egress source's health product (resets/process terms scoped to the same matcher);
- **the usage rollup's egress_bytes meter** — billing undercounts HTTPS egress to near-zero even when its health gate passes (compounds `w1/034`).

Fix sketch (milestone-sized, touches billing semantics so it needs the ADR023 care): include the entrypoint-prefixed siblings in the matcher (`^((websecure|web)-)?(names…)$` — confirm the exact entrypoint prefixes from the prod Traefik config) or resolve real router labels via Prometheus label discovery scoped to the constructed suffix; re-verify against a served request over HTTPS; decide whether historical usage rows need a correction note (they undercounted, never overcounted — consistent with "never invent bytes"). Related: `w1/034` (egress rollup hours skipped), `docs/render-artifacts/webhooks-ui.md`-style evidence capture recommended.
