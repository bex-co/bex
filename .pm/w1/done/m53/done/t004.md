## Objective

Login-time workspace-invite redemption matches the Kratos identity's `traits.email` against the
pending invite, and the backend code does **not** check that the email is verified. If the Kratos
identity schema lets a user set/edit their email without verification, an attacker sets their email
to a victim's invited address, logs in, and is auto-granted the invited role — potentially admin — in
the target workspace. Confirm the Kratos side enforces verification, or escalate.

## Context

- `lego/backend/internal/api/auth.go:396` — `whoami` reads `traits.email`.
- `lego/backend/internal/api/tenancy.go:175-197` — `acceptInvites` → `AcceptInvitesForEmail(email, subject)`;
  the invite is redeemed on email match. No verified-status check here.
- The backend does the right thing **given** a verified email; the entire risk lives in Kratos
  config, which is not in this repo (chart/values live in `deploy/gitops`).
- Related: `docs/ADR024-members.md` documents invite-accept-on-login.

## Steps

1. Inspect the Kratos identity schema + config in the gitops tree (and prod, if needed): is
   `verification.enabled` on, and can `traits.email` be changed pre-verification? Determine whether
   `whoami` can ever return an unverified/attacker-chosen email for an authenticated session.
2. If verification IS enforced: add a defensive check anyway (filter `acceptInvites` on the verified
   address list, or assert `whoami` returns only verified addresses) and document the dependency in
   `docs/ADR024-members.md` so it can't silently regress.
3. If verification is NOT enforced: escalate — this is up to workspace/account takeover. File a
   hardening task (block redemption on unverified email) and note the interim exposure.
