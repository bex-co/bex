## Objective

While a newer release has no image (build queued, running, waiting on a credential, or failed), a cron job's pass must still reach `reconcileCronJob` for the prior release so `spec.suspend`, `spec.schedule` and the command are written, without advancing the pod template to the unbuilt release.

## Context

- `lego/operator/internal/controller/app_controller.go:597-600` — `Reconcile` returns on `resolveDeployImage`'s halt before the runtime dispatch at `:2079` (`reconcileCronJob`).
- `holdPendingArtifact` (`:5019`) returns `held=false` for cron jobs because `scalableRuntime` (`:4954`) excludes them; `:3545` is where `cj.Spec.Suspend` is projected.
- `w1/done/m158` did the analogous extension for workers (only replicas move); the cron analogue is: only suspend/schedule/command move, image stays on the prior release.
- `servingPriorRelease` is the existing 'is there a prior image' probe.

## Steps

1. Add a cron branch to `holdPendingArtifact` (or a sibling `holdPendingCronArtifact`) that, when a prior release serves, calls `reconcileCronJob` with the prior image and returns held.
2. Keep the phase rules: a Building phase stays Building; a failed build's verdict is not erased by the held pass.
3. Envtest: a cron App with `suspended: true` set while its newest release has no image gets `spec.suspend=true` on the CronJob within one pass, and the CronJob's image is the prior release's.

## Files

- `lego/operator/internal/controller/app_controller.go`
- `lego/operator/internal/controller/app_controller_test.go` (or the cron envtest file)

## Acceptance criteria

- [ ] Suspend, resume and a schedule edit converge on the CronJob while the newest release has no image.
- [ ] The CronJob never carries the unbuilt release's image.
