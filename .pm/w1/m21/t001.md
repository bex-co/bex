## Objective

Introduce a `static_site` service type: the spec recognizes it, and the build pipeline produces a static bundle published to an object-store/CDN origin instead of an image → Deployment. This is the mechanism foundation; serving/edge rules are t002.

## Context

- Compute service types today (web/worker/cron from m15) reconcile to Deployments; static sites must **not** — they build → object storage (the CDN origin).
- Build-from-git already exists in-cluster (w1/m5, BuildKit Jobs); the static build reuses that build trigger but a different output sink.
- Backup/object storage precedent: the CNPG `barmanObjectStore` S3 pattern (`BEX_DB_BACKUP_*`) — an S3-compatible bucket is already in the platform.

## Steps

1. Add a `static_site` service type + `spec.publishPath` (and any static-only build fields) to the `App`/service spec in `lego/types/`.
2. Wire the operator to run the build for a static site and upload `publishPath` output to an object-store bucket (the CDN origin), keyed by app + revision.
3. Skip Deployment/Service creation for static sites; record the served origin/URL in status.

## Files

- `lego/types/…` (service type + publishPath)
- `lego/operator/internal/controller/…` (static build → object-store path)

## Acceptance criteria

- [ ] A `static_site` App builds and its `publishPath` output lands in the object store; no Deployment is created.
- [ ] `make test` green; deepcopy/CRD regenerated.

## Out of scope

- Serving, redirects/rewrites, custom headers (t002); API/UI (t003/t004).
