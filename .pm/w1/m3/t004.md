## Objective

Expose the same stable-id rename behavior to every first-party surface so the REST/CLI fix does not create a new GraphQL, MCP, or dashboard capability gap.

## Context

- GraphQL currently exposes plan-only `updateDatabasePlan`; MCP similarly has plan/lifecycle tools but no Postgres rename verb.
- The dashboard routes database detail pages by `database.id` and renders `database.name`; that is the desired stable-URL/mutable-heading split once ids and names diverge.
- `docs/ADR006-bex-api.md` requires one core with thin adapters and equivalent semantics/error shapes.

## Steps

1. Add a GraphQL database rename/update mutation over the same core method, including dry-run if the surface's update convention supports it.
2. Add/update the MCP Postgres tool with stable-id + new-name inputs and the same validation/errors; avoid a second rename implementation.
3. Add a dashboard name editor in the database settings/detail experience using the GraphQL mutation, with pending/error/success states and query-cache refresh.
4. Keep `/databases/<databaseId>` and all project/environment links on the same id before and after rename; only human-facing labels/headings change.
5. Regenerate/update dashboard GraphQL definitions, operations, tests, and translations.

## Acceptance criteria

- [ ] REST, GraphQL, and MCP invoke the same rename core and return the same unchanged id/new name pair.
- [ ] The dashboard can rename a database and remains on the same detail URL while every visible resource name refreshes.
- [ ] A failed rename leaves the old name/UI/cache intact and shows an actionable error.
- [ ] Project and Environment resource tables continue linking by stable id and display the renamed value.

## Out of scope

- A general-purpose datastore settings redesign or KeyValue rename UI.
