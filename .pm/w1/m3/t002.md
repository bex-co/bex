## Objective

Make the immutable Database CR identity the id used by every Postgres operation and stable reference, while the mutable display name is used only where a human-facing name belongs.

## Context

- `pgView` currently sets both `ID` and `Name` from `d.Name`; `CreatePostgres` and `Recover` create the CR under the requested display name.
- Projects and Environments persist/return `PostgresView.ID`; recovery sources, audit targets, exports, metrics, users, connection Secrets, CNPG children, routes, and backups contain Database identities in different places.
- Once Kubernetes names are opaque, two workspaces can legitimately choose the same display name. A single workspace must still reject ambiguous duplicates.
- The official CLI resolves a human name from a list, then sends the returned opaque id to item routes; bex item routes must therefore resolve by stable id, not by the mutable name.

## Steps

1. Change create and recovery paths to mint `dpg-…` metadata names and store the request name in `spec.name`; preserve owner/project/environment labels.
2. Make `PostgresView.ID` and all item lookups use immutable identity, while `PostgresView.Name` uses the effective display-name helper.
3. Enforce normalized display-name uniqueness inside the owning workspace on create, recovery, and rename; allow the same display name in different workspaces without weakening authz.
4. Audit every Postgres consumer (projects/environments, recovery, users, exports, query/metrics, lifecycle, connection info, audit targets, purge) and keep stable references keyed to id. Rename misleading `name` parameters/interfaces to `id` where that prevents future conflation.
5. Preserve the operator boundary: operator mechanisms continue to key CNPG children, Secrets, services, SNI routes, backup paths, and Jobs from immutable CR metadata, never from mutable display name.

## Acceptance criteria

- [ ] A newly created/recovered Postgres returns `id: dpg-…` and the requested `name`, and its Database CR is named by that same stable id.
- [ ] Two workspaces may use the same display name; a duplicate inside one workspace is rejected deterministically.
- [ ] Get/lifecycle/query/recovery/project/environment operations continue to work after the display name changes because they hold/use the stable id.
- [ ] Cross-workspace access by a known `dpg-…` id remains forbidden, and audit targets remain stable across rename.
- [ ] Operator-owned data-plane object names and connection/backup identities depend only on immutable CR identity.

## Out of scope

- Renaming the PostgreSQL database/schema/user inside CNPG or changing connection endpoints; this feature renames the Render resource, not its physical data-plane identities.
