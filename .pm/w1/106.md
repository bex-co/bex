# 106 — A cancel over a never-served release stamps a `releaseGeneration` that never succeeded

Why: `successfulReleaseGeneration` falls back to `status.image` + `observedGeneration` when `status.activeRevision` is empty, so a first release that never served can be recorded as the last successful one — the same never-served confusion `w1/m160` removed from the failure and cancel phases, on the field bex-api closes deploy rows from.

- **Severity:** minor. It needs a first release that never served (a crash-loop) followed by a cancel; the deploy row's own status still comes from the Build condition.
- **Found:** `w1/m160` t003 blast radius, 2026-09-15. Traced from code, not probed.

## Where

- `lego/operator/internal/controller/release_identity.go`, `successfulReleaseGeneration`: after the `rev-` prefix parse, `if app.Status.Image != "" && app.Status.ObservedGeneration > 0 { return app.Status.ObservedGeneration }`.
- Its caller is `prepareAppReleaseDecision`'s canceled branch: `app.Status.ReleaseGeneration = successfulReleaseGeneration(app)`.
- The consumer is `lego/backend/internal/store/reconciler.go`, which compares `app.Status.ReleaseGeneration` against the open deploy's generation.

## Why it was left out of `w1/m160`

The fallback is also the legacy path for Apps that predate `status.activeRevision`; removing it could change which generation those Apps report as successful. That needs backend evidence (what the deploy reconciler does when `releaseGeneration` is 0 for a legacy App), which is a milestone of its own rather than a line change inside a fix milestone.

## Fix

Decide what a never-served release should report — most likely 0, with the legacy case handled explicitly — and pin it with a store-reconciler test that closes the deploy row correctly in both shapes.
