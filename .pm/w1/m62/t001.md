## Objective

Pin down the exact wire shape Render returns when a workspace without payment information tries to create a paid instance type, so bex's refusal (ADR046 §4) matches Render's dialect instead of inventing one. bex-api's Render compatibility is evidence-based (`docs/render-artifacts/` convention): capture first, implement against the capture.

## Context

- ADR046 §4 commits to `402 Payment Required` in Render's REST error dialect (`{"message": …}`) but flags the exact status/message as needs-capture.
- Render prompts for a card at paid instance-type selection (dashboard) — the REST behavior for a card-less `POST /v1/services` with `plan: starter` is what bex must mirror.
- Existing captures live in `docs/render-artifacts/` (e.g. `owners-api.md`, `notify-on-fail.md`, `pricing.md`) — follow their dated-evidence format.
- The homebrew `render` CLI is authed against api.bex.co, not render.com — a real capture needs a render.com workspace **without** payment info (a fresh free account).

## Steps

1. On a card-less render.com workspace, attempt a paid create via REST (`POST /v1/services` with a paid `plan`) and via the dashboard; record status code, body, and headers (redact tokens).
2. Repeat for a paid Postgres/Key Value create if the account allows.
3. If a genuine capture is impossible (no card-less Render workspace available), document the best-evidenced shape from Render's OpenAPI spec + dashboard behavior and record the uncertainty explicitly.
4. Write `docs/render-artifacts/paid-create-without-card.md` with the dated evidence; note any divergence bex will accept in `docs/ADR046-payment-onboarding-and-paid-gating.md` §4.

## Files
