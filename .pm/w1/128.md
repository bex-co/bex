# Prod never narrows the kubelet CSR approver to the node network: its values file is unwired, and its CIDR is wrong

Why: `deploy/gitops/base/kubelet-csr-approver.yaml` (and ADR072 finding 5's remediation) say "the prod overlay narrows this further to the Hetzner private network (overlays/prod/values/kubelet-csr-approver.values.yaml)", but no kustomization or Application references that file (`git grep` finds no reference), so prod runs the base values with no `providerIpPrefixes` at all. Found by w1/127's review, 2026-10-15.

- **Do not wire the file as it stands.** It says `providerIpPrefixes: [10.0.0.0/16]`, which is the Terraform bootstrap network (`infra/terraform/variables.tf:63`). The app cluster's nodes live on `10.10.0.0/16` (`infra/clusterapi/overlays/hetzner-caph/cluster.yaml:1105-1110`; the LB's private address is `10.10.0.7`). With the wrong prefix the approver would deny every prod kubelet-serving CSR, and as serving certs rotate, `kubectl exec`/`logs`/`port-forward` and metrics-server's kubelet TLS would fail cluster-wide.
- The always-on check (every SAN IP must be one of the Node's own addresses) already blocks a forged SAN, so this is defense in depth, not an open hole. Check whether nodes' InternalIPs are all inside `10.10.0.0/16` (plus whether public IPs appear in kubelet SANs) before choosing the prefix.
- Shape: patch the prod `kubelet-csr-approver` Application's values with the correct prefix (not a dead side file), extend the w1/127 approver guard in `scripts/gitops-validate.sh` so prod's prefix must be the CAPH node CIDR, delete or fix the side file, and correct the base comment.
- Done when prod's rendered approver carries the node CIDR, the guard pins it, and after the deploy new kubelet-serving CSRs are still approved on production (needs a production read of CSR status).
