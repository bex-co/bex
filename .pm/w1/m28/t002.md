## Objective

Add a CI workflow that runs `cd lego/operator && make test` (envtest + unit; auto-runs manifests/generate/fmt/vet first per `CLAUDE.md`) on every PR and push touching `lego/operator/**` or `lego/types/**` — today the operator module has no CI workflow at all.

## Context

- `CLAUDE.md`: "`make test` — unit + envtest; auto-runs manifests/generate/fmt/vet first. First run downloads envtest binaries to `bin/`."
- envtest needs `setup-envtest` (kubebuilder's tool) to fetch the etcd/kube-apiserver binaries in CI — this is a well-established pattern (`kubebuilder`'s own CI does this); use `actions/setup-go` + the Makefile's existing envtest bootstrap (check `lego/operator/Makefile` for how it invokes `setup-envtest` locally and replicate that in CI, don't hand-roll a separate mechanism).
- Types module (`lego/types/`) has no independent CI — since the operator imports it and `make test`'s codegen reads CRD/deepcopy markers from `../types`, gating on operator-path changes plus types-path changes is sufficient; don't create a third redundant workflow for `lego/types/` alone.

## Steps

1. Create a new workflow file that checks out, sets up Go, and runs `make test` in `lego/operator/`.
2. Trigger on `pull_request`/`push` to `main` with `paths: ["lego/operator/**", "lego/types/**", ...]`.
3. Confirm it runs green against current `main` (first run will be slower — envtest binary download).

## Files

- new `.github/workflows/go-test-operator.yml`

## Acceptance criteria

- [ ] Workflow runs `make test` in `lego/operator/` and passes against current `main`.

## Out of scope

- `make test-e2e` (kind cluster) — CLAUDE.md itself flags this as "slow, CI territory" but explicitly not something to run casually; out of scope for this milestone, a candidate for a future, separate workflow if ever wanted.
