## Steps

1. Verify the deploy gate and record the pin sha.
2. At each starting point in the matrix, in a test workspace:
   1. Connect an already-installed account through the single action: the chooser shows it, you choose it, and its repos appear in place with no reload. A half-filled form keeps its input.
   2. Check that the chooser marks the already-connected accounts and disappears after the choice.
   3. Disconnect that account: only its repos disappear.
   4. Connect the same account again: it completes with no GitHub Configure dead end.
3. Once, at any starting point: run the first-install path with BlockEdenHQ.
4. Once: switch to a non-default workspace, connect there, and confirm the binding lands in that workspace (`GET /v1/git/connections?ownerId=…`).
5. Check that opening the Credentials menu leaves focus off Disconnect, and that the agent composer's settings link lands on the GitHub card.
6. After each workspace's walk, compare REST `GET /v1/git/connections` and GraphQL `gitConnections` with what the UI shows.
7. The non-owner install request (t003): walk it if a GitHub account that is a non-owner org member is available; otherwise record "not walked live; covered by tests".
8. Restore the end state:
   - the `bex` workspace connected to `bex-co`, `puncsky` and `BlockEdenHQ` (its state at filing), unless the user says otherwise;
   - record the final bindings of all three workspaces.
9. For any failed cell, either fix it in this milestone (`/pm add-task w1/m526 …`, before Closeout) or file a follow-up through `/pm`. Re-walk the cell after the fix reaches production.

### Failures and gates

1. **The agent composer offers no connect action in a workspace without GitHub (FAIL; fixed in t012).**
   - In `bex-canary` with nothing connected, "Add repository or session" → Repositories shows only the text "No repositories — connect GitHub in workspace settings first.". That text has no action, and it names a page that has no GitHub card.
   - The callout with "Connect GitHub account" and "GitHub settings" renders only when `githubMissing && Boolean(repo)` (`new-session-composer.tsx`). A repo can only be picked from the connected installations' list, which is empty here. So the composer's connect entry and its settings link (DoD 1 and DoD 6) are unreachable live, and the tests passed only because they mock repos alongside a not-connected capability.
   - Re-walk this row once the pin carries t012.
2. **The first-install path (BlockEdenHQ) is gated on the user.**
   - Uninstalling the App from BlockEdenHQ (`github.com/organizations/BlockEdenHQ/settings/installations/183918549`) opens GitHub's **Confirm access** sudo-mode page. It asks for GitHub Mobile, a passkey, an authenticator code or an emailed code, which only the user can give.
   - Before the uninstall was attempted, no service in `bex`, `bex-canary` or `tian-personal` deployed from a `BlockEdenHQ` repo (`GET /v1/services`). Production database access was not available in this checkout (no `.env`), so other users' workspaces were not checked.
   - Nothing was uninstalled.
3. **GitHub's re-authorize prompt (observation, not a defect).** After about ten OAuth round trips in an hour, GitHub showed "This application has made an unusually high number of requests to access your account. Please reauthorize the application to continue." Authorize then continued to the chooser normally. A real user connecting a few accounts will not meet it.
