# Service environment variables never reach a buildpack (kpack) build, so `BP_*` settings are unconfigurable

Why: Paketo is configured through build-time `BP_*` variables (`BP_NODE_VERSION`, `BP_GO_TARGETS`, …). A tenant who sets them on the service sees no effect, which silently removes the documented way to steer the buildpack path.

**Source:** `w1/108` production validation, 2026-10-02. Fixture `qa-20261002-108-bp24` (deleted) was `qa-…-bp` plus `BP_NODE_VERSION=24.*` in its service `envVars`; kpack produced the identical Node 26 image, i.e. the variable never reached the build env.

- **Look at:** how `lego/operator/internal/build/kpack.go` authors the kpack `Image` (`spec.build.env`) versus how the native and Dockerfile paths pass build-time env (`internal/build/native.go`, `build.go`). Render exposes service env vars to the build; mirror that rather than inventing a separate build-env surface.
- **Security:** only non-secret values belong in a kpack `Image` spec; decide whether secret-backed env vars are excluded or mounted, consistent with the Dockerfile path's handling.
- **Done when** a buildpack build honors `BP_NODE_VERSION` set on the service (proved live), with an operator test asserting the projected build env.

## Triage + implementation 2026-10-02 — BLOCKED on deploy + live verify

**Verdict: Work; implemented; parked on the live half of the DoD.**

- **Premise confirmed.** `buildEnv()` (`internal/controller/app_controller.go`) fed the kpack `Image` only `BP_*`/`BPE_*` entries from literal `spec.env`. Values saved through the API do not live there: they live in the service's own Secret (`spec.envFromSecret`) and the linked group Secrets (`spec.envFromSecrets`). The native path merges those Secrets into a BuildKit secret mount (`projectNativeBuildEnv`). The kpack path never read them, so `BP_NODE_VERSION=24.*` was dropped.
- **Render behaviour.** Render exposes service env vars to the build. Docker builds get them as build args ("Render injects your service's environment variables as build args with the same keys and values", render.com/docs/docker-secrets). bex's Dockerfile path passes no service env at all. That is a separate parity gap, not filed here.
- **The secret boundary is kpack's, not a choice.** kpack v0.18.0 rejects `valueFrom.secretKeyRef` in Image/Build env: `pkg/apis/build/v1alpha2/build_validation.go` `validateBuildEnvSecretKeyRefs` returns "secretKeyRef is not supported for build environment variables". A Secret-backed value can only reach kpack as a plaintext `spec.build.env` value. Only Paketo's own configuration surface (`BP_*` build, `BPE_*` launch) is projected, and every other service variable stays out of the CR.
- **Change.** `projectBuildpackBuildEnv` reads the same ordered Secret sources as the native build. The shared `readBuildEnvSources` keeps the native path's checks: an absent group is optional, a missing own Secret fails, a protected operator Secret is refused, and it reads the saved sources, not the served snapshot. It keeps `BP_`/`BPE_` keys with precedence groups < own Secret < literals, sorted, and hands them to `KpackImage`. `desiredAppReleaseIdentity` now counts `envFromSecret`/`envFromSecrets` as artifact identity for buildpack services too, as it already did for native ones. Value edits already bump `restartedAt` (`backend/internal/secrets/service.go`), which mints a new revision and a new kpack `Image`.
- **Tests.** `internal/controller/buildpack_env_test.go`:
  - `TestProjectBuildpackBuildEnvCarriesServiceBPKeysOnly` checks precedence. It also builds the kpack `Image` and asserts `spec.build.env` carries `BP_NODE_VERSION=24.*`, while `DATABASE_URL` and the group token appear nowhere in the CR.
  - `TestProjectBuildpackBuildEnvSourceContract` covers the source contract.
  - `TestBuildpackEnvSourcesAreArtifactIdentity` failed against the old identity code and passes now.
- **Remaining gate (DoD "proved live").** Deploy this change, then build a `builder: buildpack` `examples/hello-node` service with `BP_NODE_VERSION=24.*` in its service `envVars`. The kpack `Image.spec.build.env` must carry it, and the build log must show node-engine selecting 24.x. Because of **120**, it then also serves 200, since Node 24 does not need libatomic.
