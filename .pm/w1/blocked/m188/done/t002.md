## Objective

为确认受影响且上游暂缺修复的旧版本提供可重复、可追溯的同版本安全补丁镜像，优先完成实际在用版本。

## Context

- 每次租户构建临时 apt 升级的旧做法仍不采用；补丁在平台镜像发布时完成。
- 修复范围为本项 Brotli 风险，系统库和运行时自带库分别验证。

## Steps

1. 沿用现有镜像发布、签名与 SBOM 方式，按 t001 的结论制作固定来源、固定补丁的镜像配方；需要时回移到相同运行时版本。
2. 在现有 self-hosted runner 与 CI/production 池边界内发布；不新增主机或更改已接受的凭据隔离约束。
3. 记录构建输入、补丁来源、镜像身份与逐架构验证结果，建立持续构建、扫描及失败后保留原已验证 pin 的机制。

## Files

- deploy/native-base/（复用最新 main 的统一供应流程，含系统/Node 补丁配方与来源记录）
- .github/workflows/native-base-image.yml（原有发布流程，增加安全与逐架构验收、签名和不取消运行中编译的排队）
- .github/workflows/cnb-run-image.yml（现有发布模式参考）

## Acceptance criteria

- [x] 需要修补的镜像有可复验补丁依据，版本查询仍符合用户选择；平台只切换经验证的不可变镜像。
- [x] 系统库和运行时自带库的修复证据完整；不能以改标签、换 digest 或忽略 CVE 冒充修复。
- [x] 覆盖生产 amd64 和仓库支持的 arm64 路径；无法同版本安全修补的情况逐项给出具体证据。

## Out of scope

不建设通用运行时发行版产品；不顺带承诺修复旧运行时全部历史漏洞，不静默升级语言大版本。
