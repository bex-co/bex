## Objective

A push to a `checksPass` service's branch records a pending (service, commit) instead of deploying; check events deploy it when all checks pass and drop it on any failure; a newer push supersedes an older pending commit.

## Context

- Push handling and auto-deploy decisions: `lego/backend/internal/apps/webhook.go`, `lego/backend/internal/apps/deploy.go` (`AutoDeployTrigger`, :355).
- Migrations live under `lego/backend/internal/store/` (numbered SQL).

## Steps

1. Add the pending table/migration keyed by service and commit.
2. On `check_suite` completed events (and a list-check-runs read for the head commit) evaluate per t001: all `success`/`neutral`/`skipped` → deploy with trigger reason; any failure → drop and record why; zero checks → no deploy.
3. Ignore events for commits that are not the branch's latest pending one.

## Files

- `lego/backend/internal/apps/webhook.go`
- `lego/backend/internal/apps/deploy.go`
- `lego/backend/internal/store/` (migration)

## Acceptance criteria

- [x] Unit/integration tests: pass → one deploy of that commit; fail → no deploy; newer push → only the newest deploys; zero checks → no deploy; duplicate webhook deliveries → one deploy.

## Outcome

Done 2026-10-17, no migration. A push that passes the service's filters records the commit in the App annotation `app.bex.co/checks-pending-commit`; a newer push overwrites it. Checks are read at once (a commit already checked elsewhere deploys on push) and on every completed `check_suite`; the suite's branch isn't matched. All-pass claims the commit with an optimistic-lock patch, retried on unrelated conflicts, so it deploys exactly once. Billing is checked before the claim, and the record is restored if the deploy call fails. A failed check keeps it awaiting; branch delete and switching away forget it. The body must be a completed suite with a valid head SHA, so other signed bodies replayed under the header do nothing.
