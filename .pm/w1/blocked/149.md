# Cursor Origin as a Git provider: build it, or sign it off beside GitLab and Bitbucket

Why: Render's dashboard now connects "Cursor Origin" as a Git provider, and bex has no disposition for it; GitLab and Bitbucket Git providers are user-rejected non-goals, but that decision does not name this one.

- **Found:** w1/m645's dashboard ledger (2026-11-26), rows `cursorOriginConnect`, `cursorOriginConfirm`, `cursorOriginConfirmUrl`, `cursorOriginDisconnect`, `cursorOriginInstallUrl` and `cursorOriginInstallations` in [dashboard-operations.md](../../../docs/render-artifacts/dashboard-operations.md#git-and-registry-credentials).
- **Render (bundle, no flag):** Account Settings' Git providers list has **Connect Cursor Origin**: "Connect to a Cursor workspace where Render is already installed. If it isn't installed yet, a Cursor admin can install it." A callback page says "Connected to Cursor Origin", and the analytics event is "Git Provider Connected" with `git_provider: cursor_origin`. Disconnecting removes each installation.
- **bex:** Git connections are GitHub only, and workspace-owned ([ADR078](../../../docs/ADR078-github-workspace-connections.md), `.pm/DO_NOT_DO.md` #GIT-WORKSPACE-OWNED). `.pm/DO_NOT_DO.md` rejects GitLab and Bitbucket Git-provider integration by user decision (2026-07-13).
- **Needs the user:** build Cursor Origin as a Git provider (a workspace-owned connection, as GitHub's), or record it as a non-goal with the GitLab and Bitbucket lines.
- **Done when:** the decision is recorded, as a filed milestone or as a DO_NOT_DO line plus an ADR018 `—` note on the Git connections row, and the six ledger rows point at it.

**Parked 2026-11-26: the feature is flagged, but Render documents it, so the decision is still the user's.** The note's "no flag" was wrong. In Render's dashboard bundle, every way to reach Cursor Origin reads the frontend flag `cursor_origin`, which Render's server answers per user, workspace and organization through `allFrontendFlags`. The `providers` chunk's Git provider list adds Cursor Origin only when the flag is on. That list feeds Account Settings' Git Deployment Credentials, its Add credential menu and the connect dialog. The connect-repo panel's provider row and its `cursorOriginInstallations` query (skipped when the flag is off) read the same flag. The ledger row is `cursor_origin` in [dashboard-operations.md](../../../docs/render-artifacts/dashboard-operations.md#frontend-flags).

w1/148 closed because its feature had no docs. That does not hold here. On 2026-11-26 [render.com/docs/git-provider](https://render.com/docs/git-provider) listed "Cursor Origin (beta)" beside GitHub, GitLab and Bitbucket, so the flag is a staged rollout of a documented beta, as `artifact_reuse` was for Build Sources. The changelog has no entry. The six `cursorOrigin*` operations therefore stay `gap` on this note. Render's docs say:

- "Cursor Origin and its Render integration are currently in beta." "A Cursor workspace _admin_ must install the Render app before other members can connect."
- Under Git Deployment Credentials, Add credential → Cursor Origin offers **Connect** (Render is already installed in the Cursor workspace) or **Install on Cursor** (for a Cursor admin, when it is not).
- "Sign-in with Cursor Origin is not supported." Pull request previews work with every supported provider.
- On a repository Cursor Origin mirrors from GitHub, automatic deploys and pull request previews are unavailable. Connecting the original GitHub repository is the way around it.

Building it is more than code:

- Render is an app that Cursor workspaces install. Cursor's docs ([cursor.com/docs/origin](https://cursor.com/docs/origin)) describe private Origin Apps built on its Public API, and say nothing about listing an app for other workspaces to install. bex would need an app registered with Cursor, an account and credentials only the user can obtain.
- Render binds the connection to a user, as a Git Deployment Credential. A bex build would be workspace-owned, as GitHub's is (`.pm/DO_NOT_DO.md` #GIT-WORKSPACE-OWNED).
- Render's public API pin already carries `cursor_origin_receipt_expired` and `cursor_origin_receipt_invalid`. `lego/backend/internal/api/render_error_codes_test.go` lists both as not applicable because bex offers no Cursor Origin integration. A build would emit them.

More of the bundle, for that build:

- The connect dialog is headed "Connect Cursor Origin": "Connect to a Cursor workspace where Render is already installed. If it isn't installed yet, a Cursor admin can install it." Its buttons are **Install on Cursor** (`cursorOriginInstallUrl`) and **Connect** (`cursorOriginConfirmUrl`). Each opens Cursor in a popup.
- The callback page exchanges Cursor's `installation_receipt` (`cursorOriginConnect`) or `confirmation_receipt` (`cursorOriginConfirm`). It shows "Connecting your Cursor Origin workspace…" and then "Connected to {namespace} on Cursor Origin". An expired receipt shows "That took too long": "Cursor's receipt is only valid for five minutes, and this one expired before the connection completed. Please try again." The analytics event is "Git Provider Connected" with `git_provider: cursor_origin`.
- An installation carries `installationId`, `manageUrl`, `namespaceId`, `namespaceSlug`, `status` (active or suspended), `scopes` and `createdAt`. Configure opens the active installation's `manageUrl` on Cursor. A suspended one reads "This Cursor Origin connection is suspended. A Cursor admin can reactivate it in Cursor Origin." Disconnect calls `cursorOriginDisconnect` for each installation.

The gate: the user decides, through `/unblock w1`. One option is to build Cursor Origin as a workspace-owned Git provider, which needs a bex app registered on Cursor Origin. The other is to sign it off as a non-goal beside GitLab and Bitbucket, with a `.pm/DO_NOT_DO.md` line and a `—` note on ADR018's Git connections row. Either way, the six ledger rows then point at the outcome.
