## Objective

Store avatar images. Expose upload and reset for the user and, admin-only, for the workspace, in Render's own operations (a monogram is an uploaded image, t001). Give `User` and the workspace an avatar field the dashboard can render (Render has no organization avatar, t001).

> **Amended 2026-11-26 (t001's capture):** one storage path, an uploaded image or none; no monogram column; no "confirm" step (the PUT is the upload).

## Context

- Object storage: [ADR112](../../../../../docs/ADR112-object-storage.md). Uploads are presigned, as Render's `avatarPresignedUpload` is, and type and size are checked against t001's limits server-side too.
- New operations need rows in `lego/backend/internal/api/scope_matrix_ops.go` and `key_permission_ops.go`; changes are audit-logged where ADR018's audit-log row says Render logs them.
- CSP: `dashboard/server/security-headers.ts` (`img-src`) gains the avatar bucket's origin and `https://en.gravatar.com`.
- A deleted user or workspace deletes its avatar object.

## Steps

1. Schema and storage (migration for the avatar reference and monogram choice).
2. Mutations: presigned upload, confirm, set monogram, reset; workspace variants admin-only.
3. Read fields: the uploaded image URL, or the monogram, or nothing (the client applies the Gravatar default as Render's does).
4. CSP update with its tests.

## Outcome (2026-11-26)

- GraphQL: Render's `avatarPresignedUpload(avatarOwnerId, avatarType: AvatarType!, avatarSizeBytes: Int!) { url verb }` (a query, classed a write in the scope matrix; key permission `workspace.settings.manage`) and `deleteAvatar(avatarOwnerId, avatarType): Boolean!`, in `lego/backend/internal/avatars`. An account's avatar is its own (another id reads as no such user; an API key is refused, `AVATAR_PERSON_REQUIRED`); a workspace's is its Admins' (`can_manage`, audited by the authorize funnel). `avatarDownload { url }` (`PresignedDownload`) on `User`, `Workspace`, `WorkspaceMember`, `OrganizationMember`, `OrganizationWorkspace` and `EventUser` (`gqlutil.AvatarDownloadField`): every such field of one document reads in a single store query (`core.AvatarBatch`, graphql-go thunks).
- **Deviation from the task text: the image is kept in Postgres, not object storage** (migration 0348, `avatars` and `avatar_uploads`). A stored avatar is a 128 × 128 JPEG of a few kilobytes; a row goes with its workspace by `ON DELETE CASCADE` and with its account in `CleanupAccountSubject`, works the same on dev-N, CI and production, and needs no new credential, bucket, bucket CORS rule or second CSP origin. The upload URL is bex-api's own `PUT /v1/avatar-uploads/<token>` (256-bit, single-use, 10 minutes, only its SHA-256 stored, exactly `avatarSizeBytes` of a PNG or JPEG up to 1 MiB and 4096 px a side, typed by its bytes); the image is `GET /v1/avatars/<128-bit key>` (immutable cache, `nosniff`, `default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: cross-origin`). Both are outside the gate behind the client-address limiter, in `alwaysPublicInventory` and `internal/api/AGENTS.md`.
- CSP (`dashboard/server/security-headers.ts`): `img-src` gains the API origin and `https://en.gravatar.com` (which answers 404 rather than redirecting); `connect-src` already had the API origin.
- Tests: `store/avatars_pg_test.go`, `api/avatars_e2e_test.go` (real Postgres and OpenFGA), `avatars/service_test.go`.
