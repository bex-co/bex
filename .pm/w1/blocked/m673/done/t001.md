## Done (2026-11-26)

Recorded in [new-service-wizard.md § The image check](../../../../../docs/render-artifacts/new-service-wizard.md#the-image-check-isdeployableimage): the operation and its types (`ExternalImageReferenceInput`, `IsDeployableImageResult`, `UndeployableImageFailureCode`, from Apollo's `possibleTypes` map), the two call sites, every message, the 800 ms debounce, the icons, and the button and credential rules. The status mapping table (registry answer × credential → code) is in the same section.

The four questions:

- **The credential select** is disabled while the image is a deployable public image with no credential chosen (`disabled: deployable && !credential` at both call sites).
- **On success the Update Image dialog** shows "This is a public image that can be accessed without credentials." or "We were able to authorize access to this image with the selected credential.". The create form's inline connect form shows no success sentence: it keeps its helper line "Deploy an image from a Docker registry" and a check mark.
- **`failureReason` is never shown** once the path parses: the client maps the code, and a failure with no code reads "An error occurred.". The README's "failureReason is the fallback" was corrected there.
- **Create.** The bundle cannot say whether `createServer` refuses an undeployable image. Both forms gate on the check, and bex's create keeps its reference rules only.

Also settled: bex's docs page on images has no platform or size section, so bex's two messages carry no link. Render also filters the credential list by the image's registry, which [w4/735](../../../../w4/735.md) already tracks.
