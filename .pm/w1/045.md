# 045 — Custom domains are served before DNS ownership is proven (scan F4)

From the 2026-08-10 codex-security scan (`codex-security-bex-qmBeaW`, revision `855b0ce7`), Finding 4 — medium, confirmed against source in the same-day triage. **Milestone-sized; kept as a note deliberately** (same treatment as `008`/autoscaling before m20) because it is a product feature, not a patch — promote it when it is scheduled.

## What is true today

- `lego/backend/internal/apps/domains.go:434-490` (`addOne`) persists a host claim after only: `AuthorizeApp(can_operate)`, canonicalization, `reservedHost`, and `hostClaimedElsewhere` (first-come uniqueness). There is no DNS challenge bound to workspace + app + hostname.
- `lego/backend/internal/apps/domains.go:203-233` — `VerificationStatus` is derived from **cert-manager having issued a TLS secret**, i.e. issuance is treated as ownership proof.
- `lego/operator/internal/controller/app_controller.go:1658-1684` — every effective host becomes both a TLS entry and an Ingress `Host` rule; pending certificate state does not stop HTTP routing.

## Why it is narrower than "hostname hijack"

HTTP-01 issuance requires the victim's DNS to already point at the bex edge, so the live scenarios are **dangling-DNS takeover** (victim's record still points at bex after they leave) and **squatting/denial** (attacker claims a hostname first, blocking the rightful tenant, whose claim then hits `errDomainInUse`).

## What the fix looks like

- A pending, **non-serving** claim state: no Ingress rule and no Certificate until verified.
- A random DNS TXT challenge bound to (workspace, app, hostname), revalidated before any reassignment; apex + wildcard handled with DNS-based proof.
- Centralized domain state transitions so verified ownership is the only input to ingress projection.
- Render parity: Render requires DNS verification for custom domains — compare and match the surface (`docs/ADR005-custom-domain.md`, `docs/ADR018-render-parity.md`).
