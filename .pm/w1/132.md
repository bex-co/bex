# A canceled release over nothing served leaves its pods running

Why: canceling a first release that had already started rolling (an image service, or a repo service whose build finished) marks the service Canceled but leaves its Deployment at full replicas, so a failing pod keeps restarting after the cancel. This is the cancel-side sibling of the restart loop w1/m179 closed for the progress-deadline verdict.

**Evidence (2026-10-17, found by the w1/m179 review).**

- `lego/operator/internal/controller/app_controller.go`, `settleCanceledRelease`: the `releaseHasServed` branch dispatches the served release. The other branch sets `PhaseCanceled` and Ready `BuildCanceled`, writes status, and never touches the Deployment. Reconcile returns there (`if releaseDecision.canceled`, ~:630), so no later pass in that state scales it either.
- Also reachable from w1/m179's stop: stopped first release → a new deploy rolls release 2 (replicas back to configured) → cancel → Canceled, with release 2's pods still running.
- The activator's stopped guard (`cmd/activator/main.go`, Phase Failed with empty `activeRevision`) doesn't cover Canceled, so a free service in that state is also woken by requests.

**Render:** a canceled deploy stops; with no earlier live deploy nothing runs (the Cancel dialog promises "the last successful deploy remains live", and there is none).

**Shape:** in the never-served cancel branch, scale an existing Deployment to 0 (keep template, Service and Ingress), and extend the activator guard to Canceled. Add a lifecycle-fixture test (image first release rolling → cancel → replicas 0, phase Canceled; a later deploy rolls) and an activator case. About 45m. Check first whether `w1/m164` / `w5/m114` already pinned the current behavior on purpose.
