## Objective

Expose what t002 stopped weaponizing: per-source egress health (`http` / `websocket` / `direct`) as a field on the bandwidth responses, so clients can annotate degraded windows instead of guessing.

## Context

- Sources and their health terms already exist (`egressquery.App` specs + `Health`); t002 computes health per source anyway — this task returns it instead of discarding it.
- Shape suggestion: `sources: [{source: "direct", healthy: false}]` (or a `degradedSources: [String]` minimal form) on the GraphQL `metrics(BANDWIDTH)` result and `monthToDateBandwidth`; REST/MCP mirror per the one-core-three-adapters rule. Render has no counterpart field (its chart is unannotated) — this is a bex extension; name it so it can't collide with future Render fields.
- Dashboard consumption is t004; keep this task backend-only with generated-schema/type updates for the dashboard hand-authored the way m49 did (`dashboard/src/graphql/definitions.ts`) only if t004 needs it immediately — otherwise leave definitions.ts to t004.

## Steps

1. Extend the core bandwidth verb's return with per-source health; thread through REST/GraphQL/MCP fragments identically.
2. Backfill the GraphQL schema + REST JSON shape docs (ADR006 field tables if present).
3. Unit test: degraded direct source ⇒ series present AND `sources` marks direct unhealthy.
