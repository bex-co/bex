# The image field uses Render's words: "Image URL", "Please supply the full name of the image." and the Git-repository hint

Why: Render parity in wording. w1/m673 t006 found three places where bex's image field still speaks differently from Render's two image forms.

Render's image forms, read 2026-11-26 from its public dashboard bundle ([new-service-wizard.md § The image check](../../docs/render-artifacts/new-service-wizard.md#the-image-check-isdeployableimage)):

- The field's label is **Image URL**, and the Update Image dialog's heading reads "The image URL for your external image.". bex labels it "Docker Image" (`services.createImageLabel`).
- A path Render's client cannot parse reads "Please supply the full name of the image.", and no check is sent. bex shows one of its own three messages from w4/406 instead (`services.createImageMalformed`, `createImageTooLong`, `createImagePrivateHost`, `dashboard/src/common/lib/utils/docker-image.ts`). They are more specific than Render's, so choosing between them is part of the work.
- In the Update Image dialog, a failing URL that looks like a GitHub or GitLab repository (`^(git@)?git(hub|lab).com(/|:)`) reads "Invalid image URL – did you mean to deploy a Git repository instead?". In bex, `github.com/acme/app` passes the syntax check and the registry check answers `does_not_exist`.

End state: the label and the Git-repository hint match Render in all eight locales, and the unparseable-path message is Render's sentence or a recorded ADR018 divergence. `dashboard/src/features/services/components/__tests__/image-check-field.test.tsx` covers each one.
