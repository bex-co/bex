> **Status 2026-08-10:** manifest value + `gitops-validate.sh` guard are done and green. **Remaining: deploy.** The setting takes effect on the next bex-api rollout; verify two external clients get distinct failure buckets afterwards.

## Objective

Close round-5 Finding 8 (medium, and effectively a live regression against `w1/m67`): the pre-auth failure limiter m67/t002 shipped four commits ago is deployed without proxy topology, so every external request resolves to the Traefik pod IP and the entire internet shares **one** 60/min failure bucket. Any anonymous client can drain it and make legitimate uncached bearer/session authentication return 429.

## Context

- `lego/backend/cmd/api/main.go:846` parses `BEX_TRUSTED_PROXY_CIDRS`; empty is valid and means "trust no proxy".
- `lego/backend/internal/core/clientip.go:76-81` — with an empty trusted set, `ClientIP` returns the immediate peer and forwarding headers are ignored. Behind Traefik the peer is always the proxy.
- `lego/backend/internal/api/authadmission.go:108-113` — a depleted bucket refuses **before** the upstream Hydra/Kratos call, which is the property that makes the limiter valuable and also the property that makes a shared bucket an outage.
- `lego/operator/config/api/ingress.yaml:8-24` — public traffic reaches the API through Traefik.
- Verified 2026-08-10: the variable appears in `.env.example:360` (empty) and nowhere in `lego/operator/config/api/deployment.yaml`, `deploy/gitops/`, or `infra/`. It is unset in `.env`. So the control is inert in production and the failure mode above is the current behavior.

This is deployed-configuration work, not application work — the mechanism is correct and tested (`internal/api/ratelimit_test.go:182`).

## Steps

1. Determine the actual Traefik pod CIDR on the production cluster (the pod network the ingress controller runs in — not the node CIDR, unless Traefik runs host-network there; check before assuming).
2. Set `BEX_TRUSTED_PROXY_CIDRS` in `lego/operator/config/api/deployment.yaml` with a comment explaining that the value must track the CNI pod CIDR and that a wrong value is worse than none (it would let a spoofed `X-Forwarded-For` choose the bucket key).
3. Mirror the variable name into `.env.example` if its comment needs updating to reflect that production sets it.
4. Verify against the deployed API that two distinct external clients land in distinct buckets — the cheapest proof is that a flood from one source no longer sheds a second source's first request.
5. Consider whether an empty trusted-proxy set behind the public ingress should fail readiness. Recommend rather than implement if it would block local/dev runs; record the recommendation in the milestone outcome either way.

## Acceptance criteria

- [ ] The deployed API resolves per-client IPs from `X-Forwarded-For` when the peer is Traefik, and ignores the header from any other peer.
- [ ] A sustained invalid-credential flood from one external source does not 429 a different external source.
- [ ] The chosen CIDR is documented next to the value, including how to re-derive it if the CNI or ingress placement changes.
