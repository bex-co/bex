## Definition of done

- A workspace **contributor** is refused (403) on every verb that selects the code a workload runs — pre-deploy command, cron command, one-off job command, and a deploy trigger carrying `imageUrl` or `commitId` — across REST, GraphQL, and MCP, while a **parameter-free redeploy** and a **schedule-only** cron change remain available to them. Each corrected method is pinned in `representativeVerbRelations`.
- A contributor cannot turn on PostgreSQL statement/error logging; the sensitive-literal disclosure path that `can_view_sensitive` gates is not reachable through a `can_operate` parameter write.
- Two distinct external client IPs arriving through Traefik resolve to **distinct** pre-auth failure buckets in the deployed configuration; a flood from one source no longer 429s unrelated logins.
- `Recover` refuses a paid plan without a bound payment method and refuses during a billing-mutation lock, matching `CreatePostgres`/`SetPlan`.
- Generated KeyValue backup Jobs carry a bounded `EmptyDir` and explicit ephemeral-storage requests/limits; an oversized backup fails inside its own Job without evicting neighbors.
- Every production workflow that reads `admin.conf` over SSH — **including `openbao-restore-drill.yml`** — supplies the host-key pin, and `BEX_SSH_KNOWN_HOSTS` is captured so the control is live rather than inert.
- An audience-less **human** token from an unmarked dynamically-registered OAuth client is rejected in the deployed configuration, while the official Render CLI's device flow and bex-mobile continue to authenticate.

## Outcome (2026-08-10) — code complete, activations pending

**F2 — the executable-selection class (t001).** Four verbs still reached the "run attacker-chosen code with the service's secrets" sink on `can_operate`: `SetPreDeployCommand`, `SetCronJob(command)`, `jobs.Create(startCommand)`, and `deploys.Trigger(imageUrl|commitId)`. The two that are conditional now resolve their relation from the request before the single fetch, so a **bare** redeploy and a **schedule-only** cron change stay contributor capabilities — the distinction that makes this a boundary rather than a blanket tightening. The real deliverable is `internal/api/m68_executable_selection_test.go`, which enumerates the **class** and states where it ends (content from outside the approved source is in; selecting among content already inside it — `SetRootDir`, `SetDockerfilePath` — is not, and both were examined and deliberately left). A class member missing from that table now fails a test, which is what did not happen when `codex #1` fixed five of nine.

**F7 — statement logging (t002).** `normalizeParameterOverrides` dropped exactly one key, so a contributor could set `log_statement=all` and then read the SQL literals through `can_view_logs`. The logging family now needs `can_create` — chosen over `can_view_sensitive` deliberately: identical roles (developer or admin), but `can_create` is a **write** relation, so the change stays in the service events feed instead of vanishing into an unrecorded allowed read. Gate is on presence, not delta, because the map is a full replacement and the delta reading would need a second authorization pass this codebase forbids.

**F5 — recovery (t004).** `Recover` reached `Client.Create` with neither billing gate. Both added, plus the plan/version validation it also lacked — but only for **caller-supplied** values, since re-validating an inherited plan would refuse to recover an instance whose plan has left the catalog. A sweep of every `Client.Create` confirmed recovery was the only gap: the Blueprint paths already gate via `requireStackPaymentMethod`.

**F10 — backup storage (t005).** The `EmptyDir` bound is derived per instance (`2 × allocated storage + 1 GiB`) rather than as one constant, so a starter instance cannot claim a standard instance's ceiling and a disk-autoscaled instance still gets a budget for the storage it actually has. The `2×` comes from reading the pipeline: peak is at `gzip`, where source and target coexist — the three representations never do, because each stage deletes as it goes.

**F8/F3/F1 — the three that need an operator.** Each shipped everything that can live in the repo, and each is **inert until someone acts**:

- **F8 (t003):** `BEX_TRUSTED_PROXY_CIDRS: 10.244.0.0/16` is now in the API deployment, derived from the CAPI cluster's pod CIDR and held to it by a new `gitops-validate.sh` check (proven to fail when the value is absent). It takes effect **on the next deploy**. The value trusts the whole pod CIDR and therefore leans on ADR043's default-deny keeping tenant pods off bex-api — written into the manifest comment, because that coupling is the thing a future reader must not silently break.
- **F3 (t006):** `openbao-restore-drill.yml` — the fetcher m66 missed, and the one that then handles the unseal keys — now wires the pin, and `github-actions-validate.sh` **derives** the fetcher list from the tree so a new one is caught the day it is added (verified: reverting the workflow makes it name that exact file). **`BEX_SSH_KNOWN_HOSTS` is still uncaptured**, so all three workflows remain on trust-on-first-use. Capture needs SSH from a trusted position plus an out-of-band fingerprint check — deliberately not automated, because capturing whatever answers would pin an attacker's key just as happily as the real one.
- **F1 (t007):** the flag stays `"0"`. Flipping it before the **live** Hydra records carry `bex.co/platform-client` refuses the official CLI's device-flow logins, and those records predate the script change that adds the marker — so this needed a check I could not run from here. What did ship: bex-api now **logs a warning on every start** where a resource is configured and the flag is off, so the inert state stops being silent (the same treatment `ssh-hostkey.sh` gives its fallback), and ADR012 §7 carries the exact 4-step activation procedure.

**Found on the way: a security fix that had been inert since the day before.** `make test` regenerated `app.bex.co_databases.yaml` with a `spec.deletedUsers` field. That field was added to the types on 2026-08-09 by the previous remediation commit **without regenerating the CRD** — so the API server was pruning it, and the fix it belonged to (a Postgres login role deleted through the API must actually be dropped) never worked in production. CI could not catch this because `make test` regenerates before testing, repairing the tree in the runner and staying green. `operator-test.yml` now fails on any uncommitted codegen. Same shape as F1/F3: shipped, believed done, inert.
