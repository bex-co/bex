## Objective

Close round-5 Finding 5 (medium): `Recover` provisions a new managed Postgres on a caller-selected or inherited plan without calling `RequirePaymentMethod` or `RequireBillingMutation`, while the ordinary create and plan-change paths enforce both for the identical resource cost. A developer can provision paid capacity in a workspace whose billing state should refuse it.

## Context

- `lego/backend/internal/postgres/recovery.go:173-241` — `Recover` authorizes `RelCanCreate` on the **source**, resolves `plan` (from `req.Plan`, falling back to the source's), builds the new `Database`, and calls `s.Client.Create` with no financial check in between.
- `lego/backend/internal/postgres/service.go:521-532` — `CreatePostgres` is the reference: `core.PaidPlan(req.Plan)` ⇒ `RequirePaymentMethod`, then `RequireBillingMutation` unconditionally, both **after** the dry-run return so a preview costs nothing.
- `lego/backend/internal/postgres/service.go:633-666` — `SetPlan` applies the same pair on plan change.
- Gates are only active when `BEX_REQUIRE_PAYMENT_METHOD=1` (ADR046), so this is a policy hole rather than a live loss today — but it is exactly the class ADR046 exists to make uniform.

## Steps

1. Insert both gates in `Recover` **after** the plan is finally resolved and validated and **before** `s.Client.Create`, mirroring the create path's order and its `core.PaidPlan` condition.
2. Use the source's tenant id (already read into `tenantID`), consistent with the labels the new CR receives.
3. Sweep the other create-like datastore paths for the same omission — KeyValue create/recover, and any Blueprint-driven provisioning path that bypasses `CreatePostgres`. Fix any found here; this is the second time a create-like path has been discovered without the shared invariant.
4. If a shared guard helper would make the invariant hard to omit next time, prefer introducing it over a third copy of the two calls.

## Files

- `lego/backend/internal/postgres/recovery.go`

## Acceptance criteria

- [ ] Recovery onto a paid plan is refused with `PAYMENT_REQUIRED` when no payment method is bound.
- [ ] Recovery is refused during a billing-mutation lock, on any plan.
- [ ] A permitted recovery still creates the intended plan/version and the same `Recovery` spec as before.
- [ ] The gate ordering matches `CreatePostgres` (no gate charged for a request that fails validation).

## Out of scope

- Changing what `PaidPlan` classifies, or the gate semantics themselves.
- Quota/cleanup policy for recovered instances.
