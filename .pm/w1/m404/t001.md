## Objective

Confirm on production that a long-running `bex agent` command loses its login once the 15-minute access token expires, and whether a second concurrent `bex` process makes it worse, before changing code.

## Context

- Upstream `render-oss/cli` `pkg/client/client.go`: `NewDefaultClient` → `maybeRefreshAPIToken` refreshes only at construction; on a non-timeout refresh failure it clears the refresh token and writes its own (possibly stale) config.
- `lego/cli/internal/agent/api.go` `defaultAPI()` keeps `raw.RequestEditors` (a static bearer) for the whole run.
- Hydra: `access_token: 15m`, `rotation_grace_period: 60s` (`deploy/gitops/base/values/hydra.values.yaml`).

## Steps

1. Sign in as the QA user with `bash scripts/qa-login.sh` and a CLI device login (never read `.env`/`muse.env`; never print tokens).
2. Start a session whose turn runs past 15 minutes (or `bex agent wait --timeout 25m` on one kept busy) with `--follow`; note the time and the CLI config's `expires_at` (that field only).
3. In a second terminal run `bex agent list` every few minutes.
4. Record the first error text and its time relative to `expires_at`, and whether the second terminal ever fails.
5. Log out and revoke the session (`bash scripts/qa-login.sh --logout <jar>`); delete the QA session.
