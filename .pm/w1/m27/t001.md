## Objective

Give `bex-db` (bex-api's control-plane CNPG Postgres cluster) a real backup configuration — it currently has none at all, per the standing `# TODO(task 007): add spec.backup.barmanObjectStore -> Wasabi for off-cluster backups + PITR.` comment in its manifest.

## Context

- `deploy/gitops/charts/bex-postgres/cluster.yaml` — single-instance CNPG `Cluster` named `bex-db` in `bex-system`, holds every workspace/member/audit/usage/API-key row (`docs/ADR003-control-plane.md`).
- Existing pattern to mirror: `etcd-backup`/`openbao-backup`'s `<name>-s3` Secret + Hetzner Object Storage target (`deploy/gitops/charts/etcd-backup/cronjob.yaml`'s `S3_ENDPOINT`/`S3_BUCKET` env vars from a `secretRef`).
- CNPG's own `spec.backup.barmanObjectStore` is the *native* mechanism (unlike etcd/OpenBao's shell-script CronJobs) — same idea Render-managed tenant Postgres already uses (`docs/ADR009-postgresql-management.md`, driven by the operator's `BEX_DB_BACKUP_*` env vars for tenant `Database` CRs). `bex-db` is a static GitOps chart, not operator-reconciled, so its config goes directly in `cluster.yaml`.

## Steps

1. Add `spec.backup.barmanObjectStore` to `cluster.yaml`: endpoint/bucket pointing at the same Hetzner Object Storage account etcd-backup/openbao-backup use, under its own prefix (e.g. `s3://bex-tfstate/bex-db` or a dedicated bucket — match whatever convention `BEX_DB_BACKUP_DESTINATION` already uses for tenant Postgres).
2. Reference a new `bex-db-backup-s3` Secret (created out-of-band in t002) for credentials.
3. Enable a scheduled backup (CNPG's `ScheduledBackup` resource or `spec.backup.retentionPolicy`) plus continuous WAL archiving for PITR.
