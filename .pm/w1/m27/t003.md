## Objective

Prove `bex-db`'s backup is actually restorable — recover to a new CNPG cluster from the real backup taken in t002, and confirm real control-plane data survives.

## Context

- Mechanism: CNPG's `bootstrap.recovery` from a `barmanObjectStore` source — the exact recovery path `docs/ADR009-postgresql-management.md` already documents and bex-api's `recover` verb already exercises for tenant-managed Postgres. This task proves the same mechanism works for bex's own control-plane database.
- Pick a known, identifiable row (e.g. a specific workspace name or audit-log entry) to verify post-restore, not just "the cluster came up."

## Steps

1. Create a new CNPG `Cluster` with `spec.bootstrap.recovery` pointing at the backup from t002 (a throwaway cluster, not `bex-db` itself — don't touch the live one).
2. Wait for recovery to complete; connect and query for the known row picked beforehand.
3. Tear down the throwaway recovery cluster once verified.
4. Record the drill (date, what was recovered, how long it took) — feeds into t007's ADR.

## Files

- none (a throwaway CNPG `Cluster` manifest applied ad hoc, not committed)

## Acceptance criteria

- [ ] A real recovered cluster contains the pre-chosen known row, byte-for-byte correct.
- [ ] Drill notes captured for t007.

## Out of scope

- Automating this as a recurring drill — a one-time proof is this milestone's bar; recurrence cadence is t007's recommendation, not built here.
