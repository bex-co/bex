# `BUN_VERSION=latest` builds the newest Bun at every deploy, as on Render

Why: Render's `latest` "Uses the most recent stable release of Bun for every deploy" ([bun-version](https://render.com/docs/bun-version)), but bex maps it to the newest reviewed line's pin, so a service that asks for `latest` builds an older Bun (1.4.4) than one with only a lockfile (Render's dated default 1.4.5).

- **Found:** `/pm-brainstorm one render aspect for w1` (2026-11-25), item 4, re-checked by an independent verifier the same day.
- **bex today:**
  - `bunRequest` (`lego/operator/internal/build/nativeversion.go:636-650`, the case at 641-642) maps `latest` to the 1.4 line, `oven/bun:1.4@sha256:1d22548f…` (`native.go:243`), which is 1.4.4.
  - `exactRequest` → `toolchains.ExactVersion("latest", …)` returns "", so `resolveNativeBunExact` (`nativeresolve.go:483-501`) returns before any lookup. Only `canary`, the floating tag, is resolved live.
  - On 2026-11-25 `oven/bun:latest` = `1.4` = 1.4.5 (`sha256:3aa040e5…`, pushed 2026-11-19), and a lockfile-only service created since 2026-11-20 gets 1.4.5 (`bunDefaults` 511-520, `datedBunDefault` 529-544).
  - Nothing records this as a divergence: w8/315 and w8/371 say "`latest` … unchanged", w8/m71 t001 designed "`latest`: onto the newest line" when the reviewed patch was the newest release, and ADR018 and ADR060 are silent.
- **Not fixed by a pin bump:** [m635](m635/README.md) moves the 1.4 pin to 1.4.5, which hides this until Bun 1.4.6; the gap reopens with every Bun release.
- **Change:**
  - Resolve `latest` live like `canary`: read the `oven/bun:latest` digest at build (`bunRepo` is already in `exactRepos`) and pin the `FROM` by it.
  - Narrate it canary-style with the digest (`==> Using Bun latest (oven/bun:latest@sha256:…)`); the per-instance StartLines Bun line (w32/093) says the same. Reading the release number from the OCI label `org.opencontainers.image.version` would mean extending `registry.ReadImageRuntimeMetadata`, the `ExactImageResolver` interface and its fakes (~1.5–2h), so it stays out of this note.
  - An unreachable registry keeps the reviewed pin with a `Could not look up …` line.
  - Add `latest` to `supportedLines`; the refusal text already tells users to "set … latest".
- **Done when:**
  - `TestResolveNativeBun` (`nativeversion_test.go:749`) and the dated-default table row at :1017 expect the live lookup for `latest`;
  - a fake-resolver test pins the observed digest, and the unreachable case narrates the fallback;
  - `cd lego/operator && go test ./internal/build/...` passes;
  - on production a disposable QA service with `BUN_VERSION=latest` logs the `oven/bun:latest` digest, and `bun --version` in its shell equals the newest Bun release; the service is deleted afterwards.
