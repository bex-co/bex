## Objective

Close the SIGTERM-vs-endpoint-removal race on bex-api rolls. w1/m30's in-process graceful shutdown already drains **in-flight** requests; the remaining window is Traefik/kube-proxy still routing **new** requests to a terminating pod for a few seconds after SIGTERM. The image is a single static binary (no shell), so a `preStop: exec sleep` is unavailable — do the drain in-process: on SIGTERM, flip readiness to failing while continuing to serve for a drain window, then shut down.

## Context

- m30 shipped the SIGTERM graceful-shutdown helper used by both servers (`lego/backend/cmd/api/main.go`, `lego/backend/cmd/ssh-gateway/main.go`) — extend it, don't fork it.
- `lego/operator/config/api/deployment.yaml` points **both** liveness and readiness at `GET /healthz`. Flipping `/healthz` to 503 on SIGTERM would trip liveness too — split out a `/readyz` for readiness first; liveness stays `/healthz`.
- Drain window must exceed readiness `periodSeconds` (10s) + endpoint propagation; ~10–15s is the usual choice. Must stay under `terminationGracePeriodSeconds` (default 30s) minus the m30 in-flight drain budget.
- Rollout strategy: base Deployment has no explicit `strategy`; the 06:54 incident events show an old pod deleted while the replacement was still `FailedScheduling` (anti-affinity, 3 platform nodes). Set explicit `RollingUpdate` `maxUnavailable: 0` / `maxSurge: 1` + `minReadySeconds` so a ready surge pod always precedes a kill. PDB `minAvailable: 1` already exists (`lego/operator/config/prod/api-pdb.yaml`, w1/m38).
- `deploy.yml` rolls via `kubectl rollout restart` on the mutable `:latest` tag — no workflow change expected.

## Steps

1. Add `/readyz` to bex-api (always 200 until SIGTERM) and switch the readiness probe to it; keep `/healthz` for liveness.
2. Extend the m30 shutdown helper: on SIGTERM, mark not-ready, keep serving for the drain window, then run the existing in-flight drain + `Shutdown`.
3. Add `strategy: {rollingUpdate: {maxUnavailable: 0, maxSurge: 1}}` + `minReadySeconds` to `config/api/deployment.yaml`; sanity-check the anti-affinity/3-node interplay (surge pod must always have a schedulable node).
4. Apply the same drain-window extension to ssh-gateway (shares the helper) if it falls out naturally; otherwise note it as follow-up.
5. Verify on dev-1 or the mock cluster: `kubectl rollout restart` under a continuous `curl` loop → zero non-2xx.

## Acceptance criteria

- [ ] On SIGTERM, `/readyz` returns 503 while regular requests keep succeeding through the drain window; process exits cleanly afterward.
- [ ] A `kubectl rollout restart deploy/bex-api` under a continuous request loop (≥5 rps) completes with zero failed requests on a 2-replica cluster.
- [ ] Explicit rollout strategy + `minReadySeconds` in the manifest; no old pod is killed before its replacement is Ready.
