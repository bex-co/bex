## Objective

A freshly rolled dashboard pod must not serve the "Something went wrong · bex Dashboard" SSR error page (inbox `036`, observed twice on 2026-07-18 after the m50 and m51 rolls), and a recovered page must not keep the stale error `<title>` on the tab. Root cause per 036's hypothesis + the manifest: the readiness probe is `GET /` — which renders fine even when the pod cannot reach api.bex.co yet — so Kubernetes hands traffic to a pod whose SSR data fetches fail.

## Context

- `dashboard/deploy/deployment.yaml`: single replica, readiness + liveness both probe `/`; default rollout strategy for replicas=1 is already surge-then-kill, so the readiness gate is the whole handover decision — it just measures the wrong thing.
- 036 names three candidate fixes: a readiness gate on upstream (bex-api) reachability, an SSR retry, or letting the client error boundary recover without serving the error page. Reproduce first (controlled roll, read the actual SSR error from pod logs), then decide — the decision and evidence go in this task's notes.
- Stale `<title>`: the head/error-title logic is in `dashboard/src/common/lib/document-head/` (`stateTitle`, `titleHead`) + the root error component (`src/common/root-route/`); fix whichever path leaves the error title behind after the client recovers, independent of the main fix chosen.
- SSR reaches bex-api via `VITE_SSR_API_URL` (in-cluster Service DNS); also drain the Node server on SIGTERM (same pattern as t001 — the dashboard pod currently gets no drain at all) if the reproduce shows kills mid-request.

## Steps

1. Reproduce: controlled `kubectl rollout restart deploy/dashboard` while curling full-page loads; capture the SSR error from the new pod's logs.
2. Decide readiness-gate vs SSR-retry vs client-boundary-recovery from the evidence; implement (readiness gate = a `/healthz` server route that checks bex-api reachability, probed by readiness; liveness stays `/`).
3. Fix the stale error `<title>` regardless of the main fix.
4. Re-run the controlled roll: no error page served, title correct.

## Files

- `dashboard/deploy/deployment.yaml`
