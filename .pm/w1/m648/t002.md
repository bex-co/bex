## Objective

Store avatar images in platform object storage. Expose upload, monogram and reset for the user and, admin-only, for the workspace. Give `User` and the workspace (and `Organization`, if t001 shows Render has one) an avatar field the dashboard can render.

## Context

- Object storage: [ADR112](../../../docs/ADR112-object-storage.md). Uploads are presigned, as Render's `avatarPresignedUpload` is, and type and size are checked against t001's limits server-side too.
- New operations need rows in `lego/backend/internal/api/scope_matrix_ops.go` and `key_permission_ops.go`; changes are audit-logged where ADR018's audit-log row says Render logs them.
- CSP: `dashboard/server/security-headers.ts` (`img-src`) gains the avatar bucket's origin and `https://en.gravatar.com`.
- A deleted user or workspace deletes its avatar object.

## Steps

1. Schema and storage (migration for the avatar reference and monogram choice).
2. Mutations: presigned upload, confirm, set monogram, reset; workspace variants admin-only.
3. Read fields: the uploaded image URL, or the monogram, or nothing (the client applies the Gravatar default as Render's does).
4. CSP update with its tests.

## Files

- `lego/backend/internal/` (users/workspaces packages, a migration), `dashboard/server/security-headers.ts`

## Acceptance criteria

- [ ] Real-DB tests cover an upload round trip, a refused type and size, a non-admin refused on the workspace, and deletion with the owner.

## Out of scope

- A REST or MCP avatar surface (Render has none).
