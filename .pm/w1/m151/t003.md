## Objective

The activity rule holds in every state an eligible App can be in, and the paths that behave correctly today keep doing so.

## Context

- The idle clock is referenced 13 times in `lego` (non-test), with two writers: `app_controller.go:2411` and `cmd/activator/main.go:179`.
- Readers: `lastActiveTime` (`:1892`), `shouldAutoHibernate` (`:1942`), `idleRequeueAfter` (`:1954`).
- Adjacent states:
  - routing hold (`parkKubernetes`, `:2158-2181`, `w6/m94`);
  - activator routing while no pod is ready (`ingressBackend`, `:2340-2347`);
  - maintenance mode (`TestMaintenanceModePrecedesAutoHibernate`);
  - explicit `idleTTLSeconds`;
  - suspend/resume;
  - paid/private/worker/cron/static (never sleep).

## Steps

1. **Map every state.** For each state above, state and test what the activity rule does:
   - activity during the routing hold must not cause a flap;
   - a wake request still stamps;
   - maintenance still wins;
   - a manual suspend is never overridden by activity.
2. **Rollouts.** Decide and record whether a completed rollout restamps `last-active`. At filing time the config-change deploy that finished at 13:12:58Z did not; the first hibernate was timed from the first deploy at 13:10:47Z.
3. **Events.** After the fix, a `service_hibernated`/`service_woken` pair means real idleness. Confirm the push-notification exclusion (`lego/backend/internal/notifications/push_worker.go:663-669`, `w6/m47`) still applies.
4. **Regression tests.** Keep the existing `TestShouldAutoHibernate` cases (`idle_test.go:162-255`) passing unchanged, as the controls.
