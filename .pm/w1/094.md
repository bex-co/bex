# 094 — A suspended web service answers every visitor with Traefik's raw `503 no available server` (text/plain), not a bex "service suspended" response

Why: to anyone hitting a suspended service (a browser, an uptime monitor, a webhook sender) a deliberate suspend looks exactly like a platform outage. `w6/m94` already treated this text as a defect on the wake path, and `w3/m46` gave suspended static sites a real response.

- **Severity:** minor (UX/API honesty; the certificate and URL promise holds).
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 18. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`. Fixture: free web service `qa-20260914-sus` (`srv-dak1nd8gsm7s73f64ip0`, `examples/hello-go`), created and deleted inside the run (`DELETE` 16:10:41Z → `204`, then `GET` → `404`; URL `404` at 16:11:04).

Pass 13 saw the same body from the other side: a webhook delivery to a suspended receiver recorded `HTTP 503`, `responseBody "no available server"`.

## Root cause

- **Routing.** A suspended compute service keeps its Ingress and certificate but scales to 0 (`parkKubernetes`, `lego/operator/internal/controller/app_controller.go:2153-2181`). `ingressBackend` routes to the maintenance alias only in maintenance mode, and to the activator only when auto-hibernating or when the App is sleep-eligible, which a suspended App is not (`:2317-2347`; `autoSleepEligible` requires `!Spec.Suspended`, `:1935-1938`). The public route therefore keeps pointing at the App's own endpoint-less Service, and Traefik answers with its built-in text.
- **Not bex text.** `grep -rn "no available server" lego/ deploy/ infra/` finds nothing, the same check `w6/done/m94/done/t001.md:17` recorded.
- **Siblings already solved it.** Suspended static sites serve the static-server's 404 over the managed cert (`app_controller.go:3140-3150`, `w3/m46`). Sleeping free services get the activator's content-negotiated 503 interstitial (`lego/operator/cmd/activator/main.go:198-210`).

## Fix (~45m)

- **Route to a bex response.** Point a suspended web service's Ingress at the activator (or maintenance) alias that already serves content-negotiated pages. Answer with `503` + `Retry-After` and a bex "This service is suspended" body: HTML for browsers, `{"error":"service suspended"}` for JSON/API clients, and **no** wake side-effect (the activator must not scale a suspended App; mirror the maintenance branch, `main.go:151-156`).
- **Keep the promises.** URL and certificate stay the same. Resume restores the App's own backend (`ingressBackend` order: maintenance → suspended → sleep → own Service).
- **Tests:** an operator test that a suspended web App's Ingress backend is the suspended responder; an activator test that the suspended response negotiates HTML/JSON and never patches replicas or `last-active`; the static-site and wake paths as controls.
- **Adjacent classes:** private services, workers and cron jobs have no public host, so there's no change there. Maintenance mode keeps precedence.
- **Unverified:** what Render serves for a suspended web service. Its docs pages fetched this run don't say, so record Render's actual response in `docs/ADR018-render-parity.md` (Suspend/Resume row) when implementing, rather than assuming.
- **Dedupe:** `w6/done/m94` covers the wake/hibernate route only, and `w3/done/m46` covers suspended static sites. `.pm/DO_NOT_DO.md` has no suspend entry, and ADR018's Suspend/Resume row records no suspended-response decision. Not fixed on `main` as of `013dbdefc`.
