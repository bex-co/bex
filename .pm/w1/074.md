# secret_cache_test flakes ~50% on a loaded machine — leftover Apps starve the restricted manager

Why: it is a CI gate (`operator-test.yml` → `deploy.yml`), so an intermittent
failure intermittently blocks every deploy, and it is the pin protecting the
production incident where a cluster-wide Secret informer stopped all
controllers from starting.

Observed 2026-08-23 while working w1/m85. **Pre-existing on `main`** — reproduced
on a clean worktree at `869aaaf3` with none of the disk work applied: 2 of 3
full-suite runs failed, while the spec passes every time in isolation
(`--ginkgo.focus="Namespace-scoped Secret cache"`).

## It is a hang, not slowness

`internal/controller/secret_cache_test.go:224` waits 10s for its App to reach
`Hibernated`. Raising the deadline to 60s does **not** help — the reconcile
never happens, so the timeout is a symptom, not the cause. (That experiment was
reverted; do not "fix" this by raising the timeout.)

## Root cause

The spec starts a real manager as a deliberately **restricted user** (cluster
access for CRs/workloads, Secrets only in `default`). That manager watches Apps
cluster-wide, so it also reconciles every App **left behind in `default` by
earlier specs** — `predeploy-app`, `predeploy-fail-app`, and others. Those
reconciles fail on permissions the restricted role does not grant:

```
ERROR Reconciler error {"App": {"name":"predeploy-app"}, "error":
  "reclaim build artifacts: list ServiceAccounts: serviceaccounts is forbidden:
   User \"secret-cache-…\" cannot list resource \"serviceaccounts\" … in \"default\""}
ERROR controller-runtime.cache.UnhandledError Failed to watch {"type": "*v1.ReplicaSet",
  "error": "replicasets.apps is forbidden: … at the cluster scope"}
```

controller-runtime retries them with backoff on a single reconcile worker, so
the spec's own App is starved and never converges inside the deadline. Whether
it fails therefore depends on how many Apps earlier specs happen to have left in
`default` and on ginkgo's random spec order — which is exactly the ~50% shape,
and it gets worse as the suite grows.

## Fix options (pick deliberately — each trades something)

1. **Isolate the spec's namespace** and scope the manager's cache to it. Removes
   the cross-spec coupling entirely and keeps the RBAC restriction exactly as
   strict. Most faithful, most work.
2. **Grant the restricted role `serviceaccounts` + `replicasets`.** One-line-ish,
   and it does not weaken the Secret restriction the spec exists to pin — but it
   does make the role less minimal than the incident's role was.
3. **Have other specs clean up their Apps.** Fixes this symptom, leaves the
   suite one leaked App away from the same starvation next time.

Option 1 is the one that stops this recurring; 2 is the cheap unblock.
