## Objective

Prove the gate end to end on a real repository.

## Context

- Needs an App installation that has granted `checks: read` (production App update by its owner, or a dev App).

## Steps

1. Create a `checksPass` service on a repo with a GitHub Actions workflow.
2. Push a commit whose check passes → it deploys; push one whose check fails → no deploy; push two quickly → only the newest deploys.
3. Delete the fixture.

## Gate (2026-10-17)

This needs the production GitHub App to hold **Checks: Read-only** and subscribe to **Check suite**. Only the App owner can grant that (GitHub → Settings → Developer settings → GitHub Apps → bex → Permissions & events), and the bex-co installation then approves it. Until then the service refuses `checksPass` by name, which was itself verified by tests. After the grant: on a QA-owned free service from a repo with a GitHub Actions workflow, select After CI Checks Pass, then check that a push whose workflow passes deploys, a failing one doesn't (until a passing re-run), and two quick pushes deploy only the newest. Delete the fixture.

## Gate check (2026-10-17)

`gh api /apps/bex-co` and `gh api /orgs/bex-co/installations`: the App and installation `90623475` (updated 2026-10-15) hold `checks: write`, but `check_suite` is not among the App's events. That subscription is the only missing piece. bex refuses `checksPass` until the installation's events include `check_suite` (`github/service.go` `ChecksPermitted`).
