## Objective

Render's three filter-discovery paths answer with Render's shape from the same verbs GraphQL `metricsFilters` and `metricsPathFilterSuggestions` already use, so a REST client can discover which instances, status codes, hosts and paths to filter by.

## Context

- **Render spec** (`api/openapi/render-public-api-1.json`):
  - `/metrics/filters/application` ("List queryable instance values"): `startTime`, `endTime`, `resolutionSeconds`, `resource`, `service`.
  - `/metrics/filters/http` ("List queryable status codes and host values"): adds `host` and `statusCode`. Its response items carry `filter` with enum `host, statusCode` plus `values`.
  - `/metrics/filters/path` ("List queryable paths"): adds `path`.
- **Existing GraphQL verbs:** `metricsFilters` (`metrics/graphql.go:345`, input fields `start`, `end`, `type`, `outputFilters`, `ownerId`, `filters`) and `metricsPathFilterSuggestions` (`:362`).
- **Live at filing:** all three paths were bare `404`.

## Steps

1. Register the three routes and map Render's query parameters onto the existing verbs. Do not add a new query path.
2. Render the documented response shapes, and confirm them against the spec's schemas.
3. **Adjacent classes.** A store-dependent filter answers `503` when Loki is unwired, never `[]`. Scope everything to the caller's workspace, as `w3/done/m18/t004` decided.
4. Probe live (m155 DoD bullet 4): `filters/http` lists `statusCode` values that include `200` and `404` after mixed traffic.
