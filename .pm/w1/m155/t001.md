## Objective

`GET /v1/metrics/http-requests?…&aggregateBy=statusCode` returns one series per status code, like GraphQL `aggregateBy:["STATUS_CODE"]` already does. `aggregateBy=host` is refused with a coded `400` that says why, never silently answered with the ungrouped series.

## Context

- **Parser.** `lego/backend/internal/metrics/rest.go:172-190` reads `GroupBy: v.Get("groupBy")` (`:185`) and never `aggregateBy`.
- **Validator.** It enum-checks `aggregateBy` (`bogus` → `400 invalid query parameter "aggregateBy"`) and refuses `groupBy` as non-Render (`api/render_openapi.go:386-388`).
- **Existing mappings to reuse.**
  - MCP: `applyHTTPRequestAggregate` (`metrics/mcp.go:124-135`) maps `statusCode` to `"status"` and refuses `host` with a coded message.
  - GraphQL: `aggregateBy` mapping at `graphql.go:427-441`.
- **Docs.** `docs/ADR010-observability.md:188` still documents `groupBy`.
- **Live evidence.** m155 README § Evidence, 19:56:37Z.

## Steps

1. **Parse `aggregateBy` on REST** through the same mapping MCP uses. Share one helper rather than a third copy.
2. **Name the label from Render.** Confirm Render's REST label name for the status breakdown (spec plus a capture, if available) and emit that name, even though GraphQL relabels to `code`.
3. **Drop `groupBy`.** Remove the unreachable `groupBy` read, or keep it only if some non-validated caller path still needs it. Update ADR010:188.
4. **Probe live** (m155 DoD bullets 1–2).
