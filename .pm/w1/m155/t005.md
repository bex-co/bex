## Objective

An agent calling `get_metrics` with Render's documented metric types (`cpu_usage`, `memory_usage`, `http_request_count`, `bandwidth_usage`, `active_connections`, plus the names that already coincide) gets series instead of `bad request: unknown metric`.

## Context

- **Render's vocabulary.** `render-oss/render-mcp-server` `pkg/metrics/tools.go:138-141` accepts `cpu_usage, memory_usage, http_request_count, active_connections, instance_count, http_latency, cpu_limit, cpu_target, memory_limit, memory_target, bandwidth_usage`.
- **bex today.** `metrics/mcp.go:41` documents bex ids (`cpu|memory|instance_count|http_requests|http_latency|bandwidth|cpu_target|memory_target`). Names go straight to `Metrics`, which rejects unknown ids (`service.go:447`).
- **Why no test failed.** The parity pin counts `get_metrics` as a Superset on argument names only (`api/mcp_parity_test.go:269`).
- **Live at filing:** `metricTypes:["cpu_usage"]` returned `isError "bad request: unknown metric \"cpu_usage\""`, while `["cpu"]` and `["cpu_limit"]` returned series.
- **Datastore case.** `active_connections` targets a Postgres resource on Render; bex serves it through `get_datastore_metrics` (`db_connections`).

## Steps

1. Map Render's names to bex ids at the MCP boundary; the existing bex names keep working as legacy aliases (the `w2/m91` alias policy). Keep each result series' `metric` label deterministic, and record which name it carries.
2. Decide `active_connections` on `get_metrics`: route it to the datastore verb for a `dpg-`/`red-` resource, or refuse clearly.
3. Update the `metricTypes` jsonschema description, and extend the parity pin so an enum-value regression fails.
4. Probe live (m155 DoD bullet 6).
