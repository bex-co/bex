## Objective

GraphQL `Deploy` answers every fact the Notices need that bex keeps or can keep: whether the deploy cleared the build cache, the Blueprint and sync that opened it, and whether a move to a free plan opened it (if t001 found that bex opens such a deploy).

## Context

- `deploys.clear_cache` is stored since w4/413 (`lego/backend/internal/store/migrations/0165_deploy_clear_cache.up.sql`) and only the events feed reads it.
- A Blueprint sync opens deploys with `trigger: blueprint` (`store.TriggerBlueprintSync`, `lego/backend/internal/store/store.go:348`; `lego/backend/internal/deploys/blueprint_sync_trigger_test.go`), but the row keeps no sync id. Syncs are `store.BlueprintSync` (`lego/backend/internal/store/blueprints.go:73`).
- `Deploy` GraphQL type: `lego/backend/internal/deploys/graphql.go`; schema snapshot `lego/backend/internal/api/testdata/schema.graphql`.
- Mint any new id only through `lego/backend/internal/id`; new migrations take the next free number on `origin/main`.

## Steps

1. Add a nullable column for the Blueprint sync on `deploys` (and the Blueprint, if the sync does not already name it), written where a sync opens a deploy, with its down migration.
2. Serve `clearCache`, the Blueprint id and sync id, and, if t001 settled it, the free-plan fact on GraphQL `Deploy`, each absent (null) when it does not apply. Never infer one from another fact.
3. Leave REST and MCP deploy objects as they are unless t001 found the field in Render's pinned contract.
4. Regenerate the dashboard's GraphQL types and the schema snapshot.

## Files
