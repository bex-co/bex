# 091 — Two linked environment groups define the same key: the service runs the most recently linked group's value, but its Environment page marks neither group's key as shadowed

Why: when two shared groups collide, the page gives no hint which value the service runs. bex's rule (last linked wins) is also recorded nowhere and differs from Render's current behavior (most recently created wins), so an owner reading either the page or Render's docs predicts the wrong value.

- **Severity:** minor (display truth plus an undocumented rule). Render itself "does not guarantee" group-vs-group precedence.
- **Found:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-09-14 pass 14 (environment groups journey). Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`. Fixtures were created and deleted inside the run:
  - web service `qa-20260914-env` (`srv-dak0bhogsm7s73f64hkg`, `examples/hello-go`, which answers `GET /` with `$MESSAGE`, else `OK`);
  - group `qa-20260914-eg-a` (`evg-dak0cqogsm7s73f64hm0`, `MESSAGE=from-group-a`, created 14:36:27.9Z);
  - group `qa-20260914-eg-b` (`evg-dak0crogsm7s73f64hn0`, `MESSAGE=from-group-b`, created 14:36:31.6Z).

## Root cause

- **Runtime.** Linking appends the group's Secret to `spec.envFromSecrets` (`addString`, `lego/backend/internal/envgroups/service.go:1083`, `:1896-1901`). The operator emits groups in that order, then the service's own Secret (`envFromSources`, `lego/operator/internal/controller/app_controller.go:3847-3878`). Kubernetes lets the last `envFrom` source win, so the service's own variables beat every group, and the **most recently linked** group beats earlier ones.
- **Display.** `EnvGroupItem` marks a group key as overridden only when the **service** defines it (`dashboard/src/features/services/components/env-groups-panel.tsx:185-190`, `w6/done/067`). It never compares linked groups with each other. `linked` is the workspace group list filtered by link (`:68-70`), so it carries no link order.

## Fix (~50m)

- **Name the rule.** Keep "last linked wins" (changing it would silently flip running services) and record it as a deliberate divergence in `docs/ADR018-render-parity.md` (environment groups row) and `docs/ADR013-secrets.md`.
- **Show it.** Expose each linked group's position in `spec.envFromSecrets` to the panel (e.g. a `linkOrder` or ordered `linkedEnvGroups` on the service read), render linked groups in precedence order, and mark a key as shadowed by the later group that defines it. That is the same strike-through affordance and a new tooltip, e.g. "Overridden by `<group>`, linked later".
- **Tests:** a panel test with two groups sharing a key (the earlier-linked one is marked) plus the existing service-override case as the control.
- **Adjacent classes:** service-vs-group stays as `w6/067` made it; secret files with the same name in two groups follow the same last-linked rule and need the same marker (`FilesFromSecrets`, `service.go:1084`).
- **Unverified:** secret-file collisions across groups were not exercised. REST, GraphQL and MCP reads were not compared for link order.
- **Render:** "If a service defines an environment variable in its individual settings, that value always takes precedence … Render _does not guarantee_ its precedence behavior when multiple linked environment groups define the same environment variable. Currently, Render uses the value from the _most recently created_ environment group." (`render.com/docs/configure-environment-variables`, fetched 2026-09-14).
- **Dedupe:** `w6/done/067` covers service-vs-group only. Not fixed on `main` as of `88fa89ba7`.
