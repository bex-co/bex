# Close the four remaining service-disk REST divergences from the w1/m86 parity audit

Why: each one is a place where a Render-shaped client gets a different answer from bex than from Render, and none of them is currently recorded in ADR082 as deliberate — so they read as bugs to anyone comparing the two, and they were invisible until audited.

The audit's other five findings were fixed in w1/m86 (missing `common.cancel` key, disk absent from `serviceDetails`, `kind` rejected on `get-disk-capacity`, Disk tab offered on cron jobs, no confirmation phrase on restore). These four remain:

1. **No API surface can attach a disk at create time.** `createServiceRequest`/`serviceDetailsReq` (`lego/backend/internal/apps/rest.go:174`, `:221-253`) have no disk field; the only producer of `CreateRequest.Disk` is the Blueprint compiler (`deploy.go:1976`). Render's equivalent is `serviceDetails.<type>.disk` on `POST /v1/services`. Worse than absent: Render-matched routes decode strictly (`api/render_openapi.go:316` → `core/http.go:60-90`), so a Render-shaped create carrying `serviceDetails.disk` returns **400 unknown field "disk"** rather than being ignored. Either implement it or record the refusal in ADR082 D6.

2. **Restore's REST response diverges from the pinned contract.** Render's `POST /disks/{diskId}/snapshots/restore` returns **200 with the disk object**; bex returns 202 with no body (`apps/disk_snapshots.go:189`). GraphQL returns `Boolean`, MCP `{restoring:true}` — no surface returns the disk. Render's `list-snapshots` is documented 201, bex returns 200 (`:186`). The 202 is argued in a code comment (`:146-149`) but appears in neither ADR082 nor `docs/render-artifacts/disks.md`. The OpenAPI middleware validates requests only, so nothing catches response drift — consider whether a response-shape guard is worth adding while here.

3. **`GET /v1/disks` ignores most of Render's documented filters and mis-types one.** Render documents `serviceId` (an **array**), `diskId`, `name`, `createdBefore/After`, `updatedBefore/After`, `ownerId`, `cursor`, `limit`. bex reads only `q.Get("serviceId")` (`apps/disks.go:363-364`), so a repeated `serviceId` silently uses the first, and the `diskId`/`name`/time-window filters pass the OpenAPI gate (they are in the spec) and are then **silently ignored**, returning unfiltered results. The Key Value list already implements this same filter family — follow it.

4. **`sizeGB` default 10 is unreachable over REST.** Render's `add-disk` body requires `sizeGB` and the validator enforces it, so omitting it 400s on REST while GraphQL/MCP/Blueprint all default to 10 (`disks.go:289-291`, `:494`, `:563`). Faithful to Render, but the "default 10" contract then holds on only three of four surfaces. Decide: implement the default on REST too, or state in ADR082 D6 that REST deliberately requires it.

Also worth folding in while in this code: **Render's own used-bytes route is `/v1/metrics/disk-usage`** (with `resource=srv-…`, no `kind` at all); bex mounts `/v1/metrics/disk` (`metrics/rest.go:50`), so the Render-documented route for exactly this series 404s. And `validateDisk` runs before the one-disk conflict check (`disks.go`), so a second disk on a free-tier service reports the tier 400 rather than the more specific `DISK_LIMIT` — shared across surfaces, so not a parity break, but the less useful of the two errors.

Sizing: > 1h across more than one task (each item touches REST plus its tests, and two need an ADR amendment). Promote to a milestone rather than doing inline.
