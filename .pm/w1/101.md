# 101 — A build failure (or cancel) after a first release that never served reads Running

Why: `w6/m124` settles a failed build over a prior release to Running, and `w6/m52` does the same for a canceled release. Both decide "a prior release exists" with `app.Status.Image != ""`. But `status.image` can be set by a first release that never served. For example, a first release that crash-looped until `settleFailedRollout` marked it Failed leaves `status.image` behind with `status.activeRevision` empty. If the next deploy's build then fails or is canceled, the service reads **Running** with Ready `True/PriorReleaseServing`, and bex-api reports it healthy, while nothing is serving.

- **Severity:** minor. It needs a first release that never served, followed by a failed or canceled build. The deploy row still closes correctly (`build_failed` / `canceled` come from the Build condition and the release generation, not the phase).
- **Found:** code review during `w1/m149` t005 (simplify), 2026-09-14. Reasoned from code; not probed live. `w1/m149` uses `status.activeRevision` for the same decision on pre-deploy failures.

## Where

- `lego/operator/internal/controller/app_controller.go`, in `fail`: `if app.Status.Image != "" { r.settleFailureOverPriorRelease(...) }` (build failures, around `:4294`).
- `app_controller.go` around `:633`: the canceled-release path's `if app.Status.Image != ""`.
- The rule that already holds: `settleFailedRollout` and (since `w1/m149`) `failPreDeploy` key on `status.activeRevision`, which `markRunning` sets only once a release has actually served.

## Fix

- Switch both checks to `app.Status.ActiveRevision != ""`, or to one shared `releaseHasServed(app)` predicate used by all four paths.
- Extend `failed_build_prior_release_phase_test.go` and `canceled_release_phase_test.go` with a case where `status.image` is set and `status.activeRevision` is empty, expecting `Failed` / the first-release terminal.
- Keep the existing Running and Hibernated cases green.
