## Objective

Turn m70's classification into an explicit, reviewable mapping: which `Extension` tools fold into which `update_*` tool, which stay standalone, and which are untouchable.

## Context

- m70/t003's inventory is the input. Do not re-derive parity from comments.
- Hypothesis to confirm against the inventory, not assume: all 34 `set_*` are `Extension`. 14 self-declare `"bex extension"`; the rest are unlabelled but sit in packages whose file headers declare the whole fragment an extension (`internal/secrets/mcp.go`, `internal/envgroups/mcp.go`) or are covered by `internal/apps/mcp.go:88`.

- Not every setter should fold. A setter whose argument shape is genuinely unlike a field patch (`set_environment_acl`, `set_postgres_parameter_overrides`, allowlist replacements) may read better standalone. Decide deliberately and record why.

## Steps

1. Table every `Extension` setter: resource, field, argument shape, proposed fold target.
2. Mark the ones that should stay standalone, with a one-line reason each.
3. Confirm each fold target's `update_*` tool exists; note the ones that must be created.
4. Define the semantics of an omitted argument in `update_*` — absent means unchanged, not cleared — and check it matches the REST `PATCH` behaviour the same Service method already implements.
5. Get the mapping reviewed before writing code; this is the decision, the rest is mechanical.
