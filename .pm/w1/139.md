# Registry retention must never delete a live release's image

Why: Zot keeps only the 5 most recently pushed images per repository, so a run of builds that never reached live evicted the image the live release runs on; the next reschedule hit ImagePullBackOff and took the site down.

Filed 2026-10-24.

- Incident: `beancount-cms-v2`'s live release (deploy `dep-dbcc94159…`, image `gen-1368@sha256:a2de0964…`, 2026-10-21) was pruned after ~10 newer images were pushed by deploys that then ended `update_failed`. The w5/174 node roll (2026-10-24 06:30 UTC) moved its pod to a node without the cached image: `ImagePullBackOff` for hours, Traefik `no available server` on beancount.io.
- `lego/operator/internal/registry/zotconfig.go`: `defaultRetentionCount = 5` (`mostRecentlyPushedCount`). Fix: pin every live (and rollback-eligible) release image — e.g. a `keepTags` pattern the operator stamps on live artifacts, or retag the live image under a protected tag on promotion — and add a regression test that retention cannot select it.
- Also roll back eligibility: Render keeps rollback targets; bex's Rollback relies on `ResolvedImage` that retention may already have deleted.
