## Objective

Apply `w6/m124`'s invariant to pre-deploy failures. When a release is already live and serving, a failed pre-deploy step leaves the service phase `Running` and only the deploy row reads `pre_deploy_failed`. A first-ever release that fails pre-deploy still reads `Failed`.

## Context

- `lego/operator/internal/controller/app_controller.go`:
  - `:4516-4524`: `failPreDeploy` → `r.fail(ctx, app, "PreDeployFailed", err)`;
  - `:4327`: `r.fail` sets `PhaseFailed`;
  - `:4323` / `:4342`: `settleFailedBuildOverPriorRelease`, used only for build failures;
  - `:4502-4514`: the pending/running branch sets `PhaseDeploying`.
- Live evidence: m149 README § Evidence 2 (phase `Failed` while the URL returned 200; the Failed → Deploying → Failed flap).
- The first-release control is recorded in `w4/done/m103/done/t002.md`.

## Steps

1. In `failPreDeploy`, when a prior release is live, settle the service phase exactly as `settleFailedBuildOverPriorRelease` does. Keep `status.preDeploy` and the not-ready reason for the deploy row.
2. While pre-deploy is pending or running over a live release, do not report `Failed` or a phase that contradicts what is serving.
3. First-ever release: unchanged (`Failed`).

- [ ] The m149 DoD's "stays Running" and "no false Failed" bullets pass live.
- [ ] Envtest covers: pre-deploy failure over a live release → phase `Running`, deploy `pre_deploy_failed`; first release → `Failed`; build failure over a prior release unchanged (control).
