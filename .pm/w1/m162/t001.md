## Objective

Record, with dated evidence, what Render does when Root Directory is set: the whole repository is cloned, build and start commands run from the root directory, files outside it remain reachable, and by default only changes under the root directory (plus build-filter paths) trigger a build. This is the contract t002/t003 implement and t005 documents.

## Context

- Render docs: render.com/docs/monorepo-support (Root Directory, Build Filters) and the Root Directory setting on the service settings page.
- bex today: `lego/operator/internal/build/build.go:850` sets the BuildKit context to `<source>/<rootDir>`; `lego/operator/internal/build/kpack.go:108` sets kpack `source.subPath` to rootDir. Neither leaves the rest of the repo reachable.
- `docs/ADR004-app-deployment.md:186,284` describe the current scoping as the feature; `docs/ADR018-render-parity.md:69` marks Root Directory ✅ on that basis.
- Working-tree scaffold `examples/shared-package-monorepo/` (npm workspaces `apps/*` + `packages/*`; `@shared-package-monorepo/api` depends on `@shared-package-monorepo/shared`) is the failing shape.

## Steps

1. Read the two Render docs pages; capture the exact sentences about clone scope, working directory and trigger scoping.
2. Write `docs/render-artifacts/root-directory-monorepo.md` with the quotes, the date, and a one-paragraph statement of the contract bex must meet.
3. Note the trigger-scoping rule explicitly: a shared-package change outside rootDir needs a build filter on Render too, so bex's webhook scoping (ADR004:284) is already parity.
