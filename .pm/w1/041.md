# Hash workspace-invite tokens at rest (deferred from w1/m53/t005 L6)

`tenant_invites.token` is stored in plaintext (`store/members.go` `AcceptInviteByToken`
does `WHERE token = $1`). A DB-read compromise yields live invite tokens.

Deferred from w1/m53 (not fixed) because:

- **Well mitigated already:** 128-bit `crypto/rand` entropy (`members/service.go`
  `newToken`), 7-day TTL, single-use (transactional `redeemInvite` sets
  `accepted_at`), and the token is **never** returned in any REST/GraphQL/MCP
  response — so DB read is the only exposure vector.
- **Conflicts with resend semantics:** `ResendInvite` documents "id and token
  unchanged so the original link stays live." A `sha256(token)`-at-rest scheme
  can't reproduce the plaintext for a resend, so resend would have to mint a NEW
  token and invalidate the old emailed link — a behavior change to a live,
  prod-verified feature (w1/m44).
- **Migration + backfill risk** on a working invite flow.

Do (when picked up):

1. Add `token_hash` column; write `sha256(token)` on create, look up by hash on
   accept; keep the plaintext only long enough to email it.
2. Decide resend: mint-a-new-token (old link dies) is the clean choice — update
   `docs/ADR024-members.md`'s "original link stays live" note accordingly.
3. Backfill: hash existing rows, or let them expire under the 7-day TTL and only
   hash new invites.
