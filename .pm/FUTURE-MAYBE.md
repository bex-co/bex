# FUTURE / MAYBE — deferred ideas, revisit when the trigger is met

Not anti-goals (those live in [DO_NOT_DO.md](DO_NOT_DO.md)) and not committed roadmap (that's the `wN/mN` milestones). These are ideas that are **correct in principle but premature now** — each has a concrete **trigger** that should bring it back onto the board. When running `/pm-brainstorm` or `/pm`, don't schedule these unless their trigger is met; when a trigger _is_ met, promote the item to a real milestone/task.

## Deferred

- **Per-workspace sandbox control-plane credentials (w3/007 residual).** The shared `opensandbox-server`, controller, and ssh-gateway identities are RoleBound into every provisioned `<ws>-sandbox`; Kubernetes confines each binding to one namespace, but the permissions aggregate on the shared ServiceAccount. Compromise of one trusted control-plane component can therefore reach every provisioned workspace sandbox namespace even though normal request authorization and network isolation remain intact. Candidate shapes are upstream per-request impersonation, an audience-bound namespace token broker, or per-workspace identities without one deployment per tenant. The full attacker model and completion proof are retained in [`w3/done/007.md`](w3/done/007.md). **Trigger: sandbox leaves early access, a compliance tenant-containment requirement lands, or upstream exposes a usable namespace-scoped identity hook.**

- **Content-aware sandbox egress controls for approved writable APIs (w3/008 residual).** FQDN/SNI allowlists prove destination confinement, not DLP: a sandbox can still upload data to an attacker-controlled account on an approved writable service such as GitHub or an LLM API. Credential brokering shipped in w3/m37–m40, but account/action/content constraints would require provider-aware brokers or an authenticated outbound proxy with explicit privacy and TLS costs. The full design questions and completion evidence are retained in [`w3/done/008.md`](w3/done/008.md). **Trigger: bex plans to make an enterprise DLP claim, or a tenant requires preventive controls over approved writable destinations.**

- **Availability-alert delivery + CPU-throttle visibility (w2/028 findings, 2026-08-23).** The 2026-08-20 eden-cms-v2 restart loop (liveness-killed 33×/16h at its 500m CPU limit) proved two gaps: (a) `server_failed` notifications deliver over push channels only, so a tenant with no device/webpush subscription gets **zero** availability alerts — email covers deploy events only; a fix needs a `server_failed` email channel WITH flap-digesting (the app recorded 1399 failed/available pairs — naive email would spam); (b) the dashboard never shows "you are pinned at your CPU limit" next to the restart count, so tenants can't self-diagnose throttle-driven restarts. Tier-aware liveness timing was weighed and rejected (the loop was correct behavior for an oversubscribed app; the tenant's plan upgrade to 1CPU/2Gi ended it). **Trigger: a second throttle-driven restart loop, or a tenant asking why they weren't alerted.**

- **Render-shaped Managed OIDC for AI/cloud providers.** Render ships Managed OIDC (Anthropic, OpenAI, AWS GA): a deployed service receives short-lived OIDC tokens and authenticates to those providers without stored long-lived API keys (dashboard/product surface, absent from the public OpenAPI). bex's deliberate alternative today: agent sessions keep BYO keys in OpenBao and inject them only through the mandatory SSH-gateway model proxy ([ADR062](../docs/ADR062-sandbox-credential-vault.md) / [ADR064](../docs/ADR064-security-review-round10.md)); platform auth OIDC (Hydra) is a different layer. ADR018 records the row as ✖ with that alternative noted — parity is documented, not silently claimed. From `w2/025` (w2/m79 re-baseline, 2026-08-19); deferred by user direction 2026-08-23. Building it is a real product milestone (an in-platform IdP for tenant workloads + per-provider exchange + SDK/dashboard surface). **Trigger: a tenant asks for key-less AI/cloud auth from services, or Render parity pressure makes the ✖ row material.**

- **Micro-abstraction residuals from w1 simplify passes (m49/m51).** Five small extract-when-reused items from `w1/done/033.md` (the m49 webhook-pages `/simplify` pass + one m51 addition), each audited 2026-07-19 with its trigger unfired; the two siblings that did fire already landed (`sudo-command-field.tsx` via w5/024, `formatDateLong` via `bcb28f73`). (a) **Shared field block** (Label + helper + Input, the `space-y-2` pattern in the webhook create page + Settings card) — **trigger: a third webhook form appears.** (b) **Detail-shell data-sharing convention** — m49's `/webhook/$webhookId` shell shares its query result via React context while the services/projects shells let each child re-fire and lean on Apollo dedup; **trigger: the next new detail shell arrives — pick one convention then.** (c) **Backend-served event grouping (keys only)** — serve `{type, groupKey}` with labels still translated dashboard-side; **trigger: the webhook event vocabulary outgrows the dashboard catalog's 17 keys.** (d) **`sameSet()` / `triState()` extraction to `@/common/lib/`** — each single-use (`webhook-settings-card`, `event-picker`); **trigger: a second hierarchical picker or set-dirty form appears.** (e) **Shared `egressquery` per-source health helper** — `metrics/source.go`'s interactive best-effort check and `usage.queryEgressSources`' skip/defer gate share the same iterate-specs/run-`Health()`/branch-transport-vs-unhealthy shape; **trigger: either loop next changes.**

- **Datastore availability/health/completion webhook events (durable operator status-event channel).** `w3/m26` shipped the exact current Render datastore event vocabulary but honestly omitted availability/health/completion transitions: "the operator has no control-plane event channel" — bex's webhook worker reads only the deploys+audit_events composition, so operator-observed status transitions (Postgres unavailable/available, backup completed) have no durable source to project from. Building that channel is real architecture (an operator→control-plane event write path), premature on webhook demand alone. Filed by `/pm-brainstorm` round 21, 2026-07-15 (closeout-residual sweep over `w3/done/m26`). **Trigger: a second feature needs durable operator status transitions (status history, uptime reporting), or a tenant asks for datastore health webhooks.**

- **kpack/CNB private base-image auth.** `w6/m34` shipped `registryCredentialId` build-time auth for Docker-runtime builds only, matching Render exactly — Render's field is Docker-runtime-only, so this is explicitly NOT a parity gap (`w6/done/m34/done/t002.md`: "note the divergence if kpack private bases ever matter"). Extending the credential to kpack's builder/run-image pulls is correct in principle, unmotivated today. Filed by `/pm-brainstorm` round 21, 2026-07-15. **Trigger: a tenant needs private CNB base/run images.**

- **Off-provider/cross-region backup replica.** Every backup copy — `etcd-snapshots/`, `openbao-snapshots/`, `bex-db/`, `postgres/`, `auth-dbs/`, `keyvalue/` — lives in **one** Wasabi region (`s3.eu-central-2`, bucket `bex-tfstate`); a regional object-storage loss or account lockout destroys all restore paths at once, invalidating every drilled runbook in `docs/ADR031-platform-data-backup.md`. Surfaced during the m19 rebuild's failure-domain review 2026-07-11; refreshed by the 2026-07-31 persistent-store backup audit (`w7/015`, retired to this entry 2026-08-07 — explicitly lower priority than the since-landed w7/m67/m68). Shapes evaluated there: (a) bucket-level replication to a second region/provider (Wasabi replication or a second bucket + `aws s3 sync` sweep CronJob) — the likely pick, one mechanism covers all prefixes with no per-job changes; (b) dual-write from each backup job (more moving parts); (c) a second Barman ObjectStore for the CNPG stores (doubles WAL traffic). Needs a provider/cost decision. **Trigger: first paying tenant, or any compliance conversation.**

- **Payment collection & dunning (Phase 3 of the billing half — the money-movement remainder).** The billing half's trigger ("a hosted bex offering becomes roadmap-worthy") **fired 2026-07-19** (user request to integrate Metronome); its first two phases were promoted to real milestones **`w7/m47`** (shadow export — sealed `usage_hourly` → Metronome `/v1/ingest`, env-gated, byte-identical when off) and **`w7/m48`** (billing surface — per-customer contracts + real invoices/cost over REST/GraphQL/MCP + dashboard) — placed in w7 for capacity per user direction (`docs/ADR040`'s home is still w8's metering lineage). Design: `docs/ADR040-billing-metronome.md` (Metronome is the rating/invoicing engine; `tiers.yaml`'s "prices are Metronome's" pointer now realized as rate cards). What **remains deferred** is Phase 3 only: wiring Metronome → Stripe (or a Metronome payment connector) for actual charging + dunning, which needs a payment-provider decision, payment-method-capture UX, and PCI scope. Superadmin/comped tenants are already handled without collection (ADR040 §7: `billing_excluded`, or a 100% credit + non-collectible contract). **Trigger: a payment provider is chosen AND the first paying tenant exists** — then materialize a Phase 3 milestone starting from ADR040 §8 + `.pm/w6/RESEARCH-workspaces.md` finding 6 (Render's flat-subscription + inactivity-waiver model).

- **Build-artifact caching/reuse for repo-backed `deploy_only`.** `w2/done/m30/done/t003.md` deferred it explicitly: "Building real build-artifact caching/reuse to make `deploy_only` genuinely true for repo-backed services — a materially bigger feature… starts from this task's honest-rejection baseline." Real parity substance (Render caches builds by default; faster rebuilds would also cut build-minutes usage), and BuildKit's registry cache export/import is the natural mechanism given the ephemeral-worker pipeline (`docs/ADR034-scalable-build-pipeline.md`) — but the why-now is weak while builds work and nobody is blocked. Filed by `/pm-brainstorm` round 17, 2026-07-15. **Trigger: build times become a user complaint, or real `deploy_only` demand appears for repo-backed services.**

- **Registry in-cluster TLS (Zot HTTP-only residual, ADR022 §225–227).** In-cluster Zot speaks HTTP (`registry.insecure=true` on build push), so build-push credentials cross the cluster network in plaintext — accepted inside the trusted cluster network and the reason Zot stays ClusterIP-only. Largely mitigated: Cilium WireGuard node-to-node encryption (w1/m19) covers the cross-node pod path, leaving only same-node pod↔Zot traffic, where the kernel is the trust boundary anyway. Defense-in-depth, weak why-now. Filed `w7/008` 2026-07-19; retired to this entry 2026-08-07. **Trigger: Zot is exposed beyond ClusterIP, a compliance/audit requirement lands, or WireGuard node encryption is ever disabled.**

- **ssh-gateway DB role RLS defense-in-depth (codex-security #23).** `w7/m56`'s scoped `bex_ssh_gateway` Postgres role deliberately grants table-wide access to `ssh_sessions`/`shell_ticket_nonces`; row-scoping lives in application SQL. Residual: a *stolen* gateway DB credential could rewrite any tenant's SSH-session audit row or delete cross-replica ticket claims. Fix shape when triggered: `ENABLE ROW LEVEL SECURITY` + a gateway-role policy scoping rows to gateway-originated sessions, revoke unrestricted `UPDATE`/`DELETE`. Filed `w7/017` 2026-08-01; retired to this entry 2026-08-07. **Trigger: a compliance/audit requirement lands, or the stolen-gateway-credential threat model rises.**

- **Operator day-to-day `jobs.create` narrowing (codex-security #6).** `operator-daytoday-rbac.yaml` granted the day-to-day ClusterRole `[create, delete]` on `batch/jobs` cluster-wide (kept intentionally by w7/m37 for `kubectl create job --from=cronjob/...` maintenance); a Job creator can name any namespace ServiceAccount and harvest its token — and author any pod template. **RESOLVED 2026-08-15** by codex-security round-9 #2 (escalated to high; the standing trigger fired): `jobs:create` removed from the routine ClusterRole entirely — manual one-shot CronJob triggers are break-glass (admin kubeconfig) per docs/ADR011/ADR015/ADR037, `scripts/operator-kubeconfig.sh` now smoke-tests that Job creation is denied, and `jobs:delete` alone stays for stuck-run cleanup. Resolution recorded in docs/ADR063-security-review-round9.md.

- **`onbex.co` PSL / tenant cookie isolation (codex-security #12, owner-waived 2026-07-30).** `onbex.co` is absent from the Public Suffix List (unlike `onrender.com`), so a `Domain=onbex.co` cookie set by tenant A's JS reaches sibling tenant B (cookie tossing / session fixation between tenant apps; real-Chrome-proven). Control-plane sessions already moved to `*.bex.co`. Waived because PSL eligibility needs ~2,000–3,000 distinct users vs. bex's ~17 (`docs/drills/2026-07-29-static-site-trust-baseline.md`). Closure path: (a) submit `onbex.co` to the PSL at eligibility, or (b) move tenant apps beneath a per-tenant suffix (e.g. `<tenant>.apps.onbex.co` with a PSL entry for `apps.onbex.co`). Filed `w7/021`; retired to this entry 2026-08-07 — this entry IS the track-to-closure record. **Trigger: distinct-user count approaches the PSL eligibility threshold (~2k).**

- **microVM runtime tier for tenant workloads (Kata / gVisor `RuntimeClass`).** The isolation ladder's next rung after w7's namespace tier ([DO_NOT_DO.md](DO_NOT_DO.md) §vcluster: "namespace (default) → microVM (Kata/Firecracker/gVisor, hard)"). Kernel-sharing is w7's accepted residual risk: NetworkPolicy + Pod Security baseline bound the blast radius, but a kernel exploit still crosses tenants on the same node. Deferred 2026-07-09 (w7 creation) because it's hard — node images must ship the runtime, CAPH node provisioning changes, and per-pod overhead fights bex's dense bin-pack economics — and the pre-GA threat model doesn't demand it. **Trigger: public GA / open signup with untrusted tenants** — revisit as an operator `RuntimeClass` knob per App or per plan tier.

- **OpenBao auto-unseal.** `w1/done/m38/done/t003.md` deferred auto-unseal as "a separate design decision, not this milestone" without filing it anywhere — recorded here by `/pm-brainstorm` round 16, 2026-07-15. Manual Shamir unseal is real toil: every platform-node roll or OpenBao pod restart needs an operator with `.env` keys. OpenBao now runs as a healthy 3-member raft across the three platform nodes, but each restarted pod still needs an operator unseal. Design is non-trivial on Hetzner (no native KMS): candidates are a cloud-KMS auto-unseal (external dependency + credential), transit auto-unseal via a second small bao, or accepting scripted unseal with the existing GH-secrets custody (`docs/ADR013-secrets.md`, `docs/ADR037-openbao-rekey-runbook.md`). Correct in principle, premature while rolls are rare and rehearsed (`w1/m38` drill). **Trigger: a second manual unseal is needed within any single month.**

- **Workspace ownership transfer.** A workspace is pinned to its creator (`tenants.owner_identity_id`; onboarding's personal-tenant resolution is owner-keyed — docs/ADR024-members.md § Invites): members can hold `admin`, but nobody can *transfer* the workspace to another member. Render exposes no public transfer API either (it's a support-ticket flow there), so this is not a parity gap — it becomes relevant when a living account needs to hand its personal-workspace binding to another identity. Design touches onboarding's owner-keyed upsert, the one-personal-workspace invariant, and FGA — not a quick verb. Filed by the Team Members investigation (w4/m33 creation), 2026-07-16. **Account-deletion offboarding is now promoted separately as `w2/m84`: it deletes sole-member workspaces, refuses to abandon other members without another admin, and detaches the deleted identity from a surviving shared workspace; it deliberately does not invent a general transfer verb. Remaining trigger: an explicit transfer request from a living account, or multi-workspace tenancy work reopening the owner-keyed onboarding path.**

- **Intermittent `ERR_CONNECTION_CLOSED` on api.bex.co mutations (w1/071, 2026-08-19).** During a dashboard QA walk, several `POST /graphql` **mutations** (`inviteWorkspaceMember`, `changeWorkspaceMemberRole`) intermittently failed in the browser with `net::ERR_CONNECTION_CLOSED`, then succeeded on retry; reads on the same pages were fine.
