## Objective

When the release that is serving can no longer start (its image cannot be pulled and no pod of it is ready), the service must not read `Running` with "the previously deployed release keeps serving". There is no previous release here: the failing one is the served one.

## Context

- `settleFailedRolloutMessage` (`lego/operator/internal/controller/app_controller.go`): for a release that has served and has no newer release over it, it calls `settleFailureOverPriorRelease`, which stamps `Running` (or `Hibernated`) and `Ready=True PriorReleaseServing`. That is right when an earlier release still serves and wrong when the failing Deployment is the served release itself with no ready pod.
- Why it is its own task: the phase a settled release reports is read by the wake and hibernate paths, the failed-rollout hold, `rolloutPending` (a phase other than `Running` reads as a rollout in progress and would flap `Failed`/`Deploying` each pass) and bex-api's deploy bookkeeping. The change has to be made against a pod that really cannot pull, on a cluster.
- w8/263 is the same question for a crash or an out-of-memory kill of the live release, and should settle on the same shape.

## Files

- `lego/operator/internal/controller/app_controller.go`, `release_config_snapshot.go`
- `lego/backend/internal/apps/` (the service view), `dashboard/` (the status badge)

## Acceptance criteria

- [ ] A Free service whose live build is gone, woken by a request: the service reads failed (not `Running`), with the missing-build sentence, on REST, GraphQL, MCP and the dashboard, and it does not flap between phases.
- [ ] A service with two instances where one cannot pull and one serves still reads `Running`.
- [ ] Once the image can be pulled again (a redeploy), the service reads `Running` without manual steps.
