## Objective

Before accepting a rollback to a cluster-registry image, ask the registry whether the manifest exists. Refuse a missing one with 409 and a sentence that names the build and what to do instead. The same check decides `deployActions` and the dashboard's row action. An external image is not ours to keep and stays as it is.

## Context

- `lego/backend/internal/deploys/actioncaps.go:40-45` (`RollbackEligible`), `:94-103` (`restorableRollbackTarget`, the static-site precedent, w4/m197).
- REST `POST /v1/services/{id}/rollback`, GraphQL `rollbackService`, MCP `rollback_deploy`; dashboard `dashboard/src/features/deploys/lib/deploy-status.ts:47-48`.

## Files

- `lego/backend/internal/deploys/`
- `dashboard/src/features/deploys/`

## Acceptance criteria

- [ ] A rollback to a deploy whose build is gone answers 409 on REST, GraphQL and MCP and adds no deploy row.
- [ ] `deployActions` reports the row as not rollback-able with the reason, and the dashboard offers Rollback only on rows whose build is stored.
- [ ] A rollback to a stored build and to an external image behave as before.
