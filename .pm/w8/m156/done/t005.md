## Objective

A wake, a restart or a reschedule of the live release has no open deploy row, so a pull failure there is silent: the events show nothing, the service reads `Running` and the activator answers `service not ready`. Write `image_pull_failed` with its alert, and do not show the service as running.

## Done 2026-11-11 (the event; the status moved to t010)

- **What the operator already says.** When the release that is serving cannot pull its image, the operator settles "the previously deployed release keeps serving" on `Ready` and records the real verdict on the release-scoped `Rollout` condition (`settleFailedRolloutMessage`). With a deploy open, bex-api reads that through the deploy row. With none open (a wake, a restart, a reschedule), nothing read it.
- **Now.** `servedReleasePullFailure` (`lego/backend/internal/store/reconciler.go`) writes an `image_pull_failed` fact when no deploy is open and the `Rollout` condition is an image pull failure for the generation whose image is recorded as serving. One fact per time the condition turns, however many passes see it. A newer release that failed over the served one is not touched: its generation differs, and its deploy row already recorded its own fact. The fact feeds the Events timeline and the Image Pull Failed email like the deploy-bound one.
- **Tests:** `served_release_pull_failure_test.go`.
- **Not verified on a cluster.** The path was read, not run: whether a woken Free service reaches this settle, and with which condition, needs a pod that cannot pull. That check is in t009.
- **Split off:** "the service is not shown as Running" is t010. It changes how the operator settles a served release, which this session could not exercise on any cluster.
