## Objective

Before accepting a rollback to a cluster-registry image, ask the registry whether the manifest exists. Refuse a missing one with 409 and a sentence that names the build and what to do instead. The same check decides `deployActions` and the dashboard's row action. An external image is not ours to keep and stays as it is.

## Acceptance criteria

- [x] A rollback to a deploy whose build is gone answers 409 on REST, GraphQL and MCP and adds no deploy row.
- [x] `deployActions` reports the row as not rollback-able with the reason, and the dashboard offers Rollback only on rows whose build is stored.
- [x] A rollback to a stored build and to an external image behave as before.

## Done 2026-11-11

- **Who asks the registry.** The operator, with the App's own credential it already holds. bex-api gets no registry credential. The operator reads the repository's tags and each tag's digest when a release settles and every ten minutes after, and publishes the digests as `App.status.storedImages` (`refreshStoredImages`, `lego/operator/internal/controller/live_tag.go`; `Creds.StoredDigestsFor`, `lego/operator/internal/registry/digest.go`).
- **Why not derive it.** What retention kept is not computable from deploy history: the `live-` window and the pushed window are counted separately, and cache and signature tags share the second.
- **The refusal.** `deploys.BuildStored` joins the shared rollback predicate. The verb answers 409: "the build of deploy "dep-…" (ws/web:gen-1@sha256:…) is no longer stored — only a service's recent builds are kept. Deploy its commit again instead", and adds no row. `deployActions` does not count such a deploy as a target.
- **Nothing is refused on a guess.** No listing yet, an external image, another repository's build, a deploy with no image or recorded by tag alone, a deploy made after the listing was read, and the build that is serving all count as stored.
- **Found by review and fixed before commit.** A registry error on one tag was treated like a removed tag, so a partial listing could be published and pullable builds refused for ten minutes; now only a 404 leaves a tag out and any other failure fails the reading. A listing without the serving build (an empty one included) is rejected. The listing records the generation it was read at, so a stale one never judges a newer build. A listing is dropped when the service stops running its own builds. One reading is bounded to 20 seconds and 64 tags, and a failed one is retried after two minutes, not every pass.
- **Dashboard.** GraphQL `Deploy.buildAvailable` (a bex extension; REST's deploy object is unchanged). The deploy detail page and the Deploys tab read it per row; the Events feed has no per-deploy build state, so it reads an id→availability map of the newest 100 deploys. Rollback is hidden where the build is gone.
- **A stale listing** (a build removed since the last reading) still lets a rollback through, which then fails at the pull as before; t004 makes that failure read as what it is.
