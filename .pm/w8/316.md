# A Blueprint whose services reference each other's URLs builds one of them twice, and its first live build lacks the reference

Why: Render's own `render-examples/ai-hedge-fund-on-render` Blueprint wires a FastAPI service and a static Vite frontend to each other: the API's `FRONTEND_URL` is the site's `RENDER_EXTERNAL_URL`, and the site's build-time `VITE_API_URL` is the API's. The template's comments promise each side "the correct slug even when Render appends a suffix". On bex the site's first deploy builds and goes live without `VITE_API_URL`, and a second `blueprint_sync` deploy, opened 0.4 s later, rebuilds it with the value. So a new import spends two full builds on the site, and for about five minutes serves a frontend whose API base URL is unset. w8/306 kept "exactly one redeploy" for a reference cycle (`TestMutualHostReferencesStillResolve`), but ADR018 records no signed-off divergence for it.

**Severity:** minor (the import converges; the first live build of the cycle's back-edge service is wrong for one build's duration, and the build is spent twice). **Attribution:** server (bex-api Blueprint apply). **Estimate:** ~2h. **Source:** `/qa-find-bugs-cli` w8 loop sweep `96ed`, 2026-11-13 UTC, released `bex v0.6.0` (Render CLI v2.36.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `1c4d721bc8dc`.

The end state was right: the API's `/` answered 200, the site's bundle carried `https://ai-hedge-fund-api-74eh.onbex.co` twice, and `FRONTEND_URL` read `https://ai-hedge-fund-web-74eh.onbex.co`. Every fixture was deleted (GET 404), and the Blueprint's project was reclaimed.

## Root cause

- `lego/backend/internal/apps/deploy.go:1250-1283` (`referencedFirst`) orders a create after the siblings it references, but "a reference cycle's back edges still take the second pass". Here the site was written first, without `VITE_API_URL`.
- `applyStackServices` (`deploy.go:1137-1191`) writes each service whole, through `applyStackService` → `Create`, which mints the control-plane row and its slug and applies the App CR in one step (`service.go:2750-2781`, `a.Spec.Subdomain = row.Slug`). The operator dispatches the first build as soon as the CR lands.
- `patchDeferredStackServices` (`deploy.go:1288`) then re-applies the site with the resolved reference. That bumps its generation and opens a second deploy, which waits behind the first build (w8/m119).

A slug is the bare name or gains a random suffix on a conflict (w8/306), so it can't be predicted, but it is known once the row exists, before any CR is applied.

## Fix

Split the create pass for services this apply creates: first create every service's control-plane row, which mints its slug and first deploy id; then resolve every host reference, cycle edges included, against the minted slugs; then apply each App CR once, with its complete env. A service that already exists resolves as today. Keep `patchDeferredStackServices` only as the fallback for a reference the row pass cannot resolve, and update `TestMutualHostReferencesStillResolve` to expect one deploy per service. An alternative with the same effect is to apply a back-edge service's CR with its first build held until the reference pass releases it.

## Blast radius

Every Blueprint with mutually referencing services (`fromService` with `host`, `hostport`, `port` or an `envVarKey` of `RENDER_EXTERNAL_URL`/`RENDER_EXTERNAL_HOSTNAME`), on its first apply only. A re-sync resolves against existing services in any order. A static site or any build that bakes the value in is wrong for its first live window; a runtime reader is wrong until the second deploy rolls.

## Regression checks

- Unit: a two-service cycle on first apply records two creates and no redeploy, and each service's first applied spec carries its reference.
- Live after the backend deploy: `render-examples/ai-hedge-fund-on-render` gives the static site one deploy (trigger `other`) whose bundle carries the API URL, and the API one deploy.
