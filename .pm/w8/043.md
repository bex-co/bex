# 043 — `logs --end <t>` drops the line stamped exactly `t` on the log-store path (Loki's exclusive `end`)

Why: the pinned CLI documents `--end` as "Filter logs at or before the specified end time", bex's MCP schema calls `endTime` "RFC3339 upper time bound (inclusive)", and the pod-log path keeps `t == end`. The store path silently excludes it, so "show me everything up to this line", with the line's own timestamp pasted as `--end`, hides that line.

Severity: minor. Attribution: server (`lego/backend/internal/logs/loki.go`).

## Repro (2026-10-03, `/qa-find-bugs-cli` w8 loop sweep 7)

Production, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Fixture: free image web service `srv-db0eg0nfq78s73et1ec0` (`qa-20261003-176a3d-lg`), 150 numbered requests `/seq-176a3d-001…150`, deleted afterwards (`GET` 404).

```text
$ bex logs -r <srv> --type request --start <T0> --limit 100 --direction forward --path /seq-176a3d-075 -o json
  → timestamp 2026-10-03T11:34:28.922023387Z   (line #75)
$ bex logs -r <srv> --type request --start <T0> --end 2026-10-03T11:34:28.922023387Z --limit 100 --direction forward -o json
  → last line is seq-176a3d-074        (expected …-075 included)
$ … --start 2026-10-03T11:34:28.922023387Z --direction forward  → first line seq-176a3d-075   (start inclusive ✓)
$ … --start <t75> --end <t75>  → 400 "startTime must be before endTime"   (an inclusive [t, t] window is refused)
controls ✓: ordering by --direction, --limit, --path, --status-code, --method, comma-OR --text all correct on the same data
```

## Mechanism

- `loki.go:280-292` `lokiRange` documents "the `[start, end]` window" but passes `q.End` straight to Loki's `query_range` (`loki.go:64`), whose `end` is **exclusive**. The label-values call at `loki.go:226` does the same.
- The pod-log/in-process filter is inclusive (`service.go:469-476`, which drops only `t.After(q.End)`), so the two sources disagree.
- `render.go:186-201` (`pageCursors`) already accounts for Loki's exclusive end on the **paging cursors** (`retreatBefore(oldest)` = oldest − 1 ns). That stays correct if `end` becomes inclusive, because the cursor already sits strictly before the boundary group.
- `core.ValidateQueryRange` (`core/pagination.go:94-99`) refuses `start == end`, which is a valid inclusive single-instant window.

## Fix

- In `lokiRange`, when `q.End` is caller-supplied (non-zero), send `end + 1ns` to Loki (both `query_range` and label-values), so the store path is inclusive like the pod path. Leave the defaulted `end = now` as is.
- Allow `start == end` in `ValidateQueryRange`, refusing only `start > end`. Check that the Render CLI and the dashboard do not depend on the refusal.
- Add a test with a log line exactly at `end` on both the Loki and pod paths. Re-run the existing paging tests to prove that backward/forward pages still neither repeat nor skip a line.
