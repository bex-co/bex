# A failed adopt plan tells the caller to send a `confirm` phrase that Render's create and approve cannot carry

Why: when a Blueprint created with `--existing-resources adopt` names a resource another Blueprint manages, the plan fails with the notice `service "api" is managed by blueprint exs-…; retry with confirm="takeover blueprint exs-…" to transfer ownership to this blueprint`. Render's create (`POST /v1/blueprints`), plan and approve have no `confirm` field, and the pinned CLI has no flag for it, so the advice cannot be followed from the surface that printed it.

**Severity:** minor (a correct refusal with unusable advice; the same class as the advice w8/m153 removed from create). **Attribution:** server. **Estimate:** ~40m. **Source:** found while implementing w8/m153 (2026-11-11); recorded in ADR049 § "A Blueprint is its id" as the known gap.

## Evidence

- `TestM153_AnAdoptModeSecondCreateNeverTakesAManagedResource` (`lego/backend/internal/apps/blueprint_per_source_test.go`) logs the notice above for a second adopt-mode create of a file whose service the first Blueprint manages. The plan's outcome is `failed`, and approving it is refused.
- The text comes from `blueprintOwnershipError` (`lego/backend/internal/apps/blueprint_ownership.go:217`), which every surface shares. It is right for the surfaces that take the phrase: the one-step create and `syncBlueprint` (REST, GraphQL, MCP).
- `RenderCreateBlueprintRequest` and the approval body (`blueprint_onboarding.go`) have no `confirm`.

## Fix

1. Give a planned sync's notice its own ending when the conflict is reported by a plan: say what can be done from there. For example: `service "api" is managed by Blueprint exs-… ("name"). Create this Blueprint with existingResources create_new to get its own copy, or remove the service from that Blueprint and sync it so it releases the service.`
2. Keep the phrase wording where `confirm` is accepted.
3. Decide separately whether Render's approve should accept a takeover at all; Render documents "Do not manage a particular resource with more than one Blueprint" and no transfer between Blueprints, so the parity-sufficient answer is no.

## Acceptance

- A failed adopt plan's notice names the resource and its managing Blueprint and mentions no `confirm` phrase; REST, GraphQL and MCP print the same text.
- The one-step create's and sync's `BLUEPRINT_RESOURCE_CONFLICT` still carry the phrase in `params.confirm`.
- A unit test pins both wordings.

## Unverified

- What Render prints when an adopt-mode Blueprint names a resource another Blueprint manages was not exercised on a Render account.

## Dedupe

No `.pm` item covers this notice. w4/m125 (done) introduced the shared wording; w2/m256 t014 (done) removed a surface-specific verb from the connection message, which w8/m153 has now retired.
