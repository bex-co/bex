# 036 — BLOCKER: since `cae30d1e0`, every deploy of a web service with env vars fails with "unknown namespace for the cache"

> **Duplicate of `w4/171`** (filed concurrently by QA pass 257). Fix and close there. This note only adds the blast-radius controls below: a cron with env vars → live, a cron without env → live, a web service without env → gets an instance. Only Deployment-backed services with config sources fail.

Why: production cannot create or roll out any Deployment-backed service that has environment variables (and presumably secret files or linked env groups). The first deploy never starts a pod (the phase goes `Failed` and the URL answers 404), and every later image deploy, config change or restart fails in seconds. Deploys that were already running keep serving, but none of them can be changed.

Live, 2026-09-28 ~17:14Z, production `cae30d1e0` (deployed about 16:50Z), `bex v0.2.1`, human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` post-deploy smoke test (sweep 90). Fixtures (all deleted): web `srv-data0unvlo4s73e5gd20` (`--env-var HTTP_PORT=3000`), crons with and without env vars, and a web service without env vars.

```text
$ bex services create --type web_service --image …/http-https-echo:35 --plan free --env-var HTTP_PORT=3000
  → create deploy update_failed after 252 s; instances []; phase Failed; site 404
$ bex deploys create <srv> --image …:34 --wait   → exit 1 in 11 s
$ bex services update <srv> --health-check-path … → config_change update_failed in 11 s
failureReason (every row):
  snapshot tea-daif693dqjvc73e7as3g-qa-20260928-36ed78-sm-env for generation N:
  unable to get: tea-daif693dqjvc73e7as3g/tea-daif693dqjvc73e7as3g-qa-20260928-36ed78-sm-env-rN
  because of unknown namespace for the cache

controls: cron + env var → live;  cron without env → live;  web without env → gets an instance
```

## Mechanism

- `cae30d1e0` (w1/m152 t001) added `ensureReleaseConfigSnapshot` → `copyConfigSecret` (`lego/operator/internal/controller/release_config_snapshot.go:~160-200`). It reads (and checks for) `<source>` and `<source>-r<gen>` Secrets with the reconciler's **cached** client.
- The manager's Secret informer is deliberately restricted to a single namespace (`NamespacedSecretCacheOptions`, `secret_cache.go:41-49`), and the ClusterRole cannot list Secrets cluster-wide. Apps live in per-workspace `tea-…` namespaces, so every cached Secret `Get` there fails with `unknown namespace for the cache`. The same file already records that datastore Secret reads must use the **uncached** client for exactly this reason.

## Fix (urgent)

1. Immediately: roll back `cae30d1e0`, or gate the snapshot step off in production, so deploys work again.
2. Proper fix: route `copyConfigSecret`'s reads and writes through an uncached client scoped by the existing namespaced Role (the pattern of `KeyValueReconciler.SecretClient`), or add the tenant namespace to the Secret cache only if the RBAC allows it. Add an envtest or integration test that runs the snapshot step against an App in a namespace **other** than the manager's cache namespace. The unit tests evidently used a fake client that does not enforce cache scoping.
3. After the fix: re-run this repro. A free web service with `--env-var` goes live, and an image deploy plus a config change both go live with `<name>-env-rN` snapshots present.

## Unverified

- Secret-file-only and env-group-linked services (presumed affected: same `releaseConfigSources`).
- Whether existing services' routine restarts or rescheduled pods fail too (not tested on pre-existing resources, by rule). A pod rescheduled without a rollout keeps the old template, so it is presumably unaffected.

Estimate: rollback ~10m; fix ~1h. **Severity: blocker.**
