# `bex services create --runtime docker` silently drops `--start-command` and `--build-command`

Why: the create exits 0 and prints the new service, so the caller believes the Docker Command was set. The service then starts with the Dockerfile's `CMD`. A migration or a wrapper command passed this way never runs, and nothing says so.

**Severity:** minor. **Attribution:** upstream Render CLI (the request never carries the command; the bex API stores a Docker Command when it is sent). **Estimate:** ~20m to record it, plus the upstream patch. **Source:** `/qa-find-bugs-cli` w8 loop sweep `cc62`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0, `24ac2d60fdb2`), `https://api.bex.co/v1/`, production pin `7ca0227aa477`, workspace `bex-canary`, QA human device login. The code is the same at the HEAD pin (v2.36.0, `4fd34231b637`).

## Evidence

```text
$ bex services create --name qa-20261111-cc62-dcmd --type web_service --repo https://github.com/bex-co/bex --branch main \
    --runtime docker --root-directory examples/hello-node --plan free \
    --start-command '/bin/sh -c "echo DC-MARK-1 && echo DC-MARK-2 && exec node main.js"' -o json --confirm
exit 0
  "envSpecificDetails": { "dockerCommand": "", "dockerContext": ".", "dockerfilePath": "./Dockerfile" }
```

- The deploy went live and `bex logs -r <srv> --type app` showed only the Dockerfile `CMD`'s line (`hello-node listening on 10000`). Neither marker appeared.
- Control over REST on the same service: `PATCH /v1/services/<srv>` with `serviceDetails.envSpecificDetails.dockerCommand` set to the same string answered 200 and read it back. After `bex deploys create <srv> --wait` the app log showed `DC-MARK-1`, `DC-MARK-2`, then the listen line. So the server stores and runs a Docker Command; only the CLI create does not send it.

## Root cause

`buildRuntimeEnvSpecificDetails` (pinned `pkg/service/create.go:289-310`) handles the Docker runtime first: with no registry credential it returns `nil`, and with one it sends `DockerDetailsPOST{RegistryCredentialId}` only. `buildCommand` and `startCommand` are never read on that branch, although `DockerDetailsPOST` has a `dockerCommand` field (`pkg/client/types_gen.go:2164-2171`). No validation refuses the flags either.

The update path does refuse them: `buildDockerUpdateEnvSpecificDetails` (`pkg/service/update.go:413-422`) returns `--build-command and --start-command are only supported for native runtimes`. So the same flag is an error on `services update` and a silent no-op on `services create`.

## Expected

One of the two, consistently on create and update:

- `--start-command` on a Docker web service, private service or worker is sent as `dockerCommand` (Render's [Docker Command](https://render.com/docs/docker) setting; a cron already sends its command on every runtime), or
- create refuses the flag with the update path's message.

`--build-command` has no Docker meaning ("you can't customize the command that Render uses to build your image") and should be refused on create as it is on update.

## Fix

- Upstream: map `--start-command` to `DockerDetailsPOST.DockerCommand` on the Docker branch of `buildRuntimeEnvSpecificDetails` and refuse `--build-command` there. Prepare it as `260-upstream.patch` with a `create_test.go` case beside "web service with docker runtime maps registry credential to docker details" (`:196`).
- bex: no launcher workaround and no request rewrite (DO_NOT_DO). Add the caveat to `docs/cli-compatibility-checklist.md` on the `services create` rows `--build-command` and `--start-command` (`:229-230`): on `--runtime docker` the pinned client drops both; set the Docker Command with a Blueprint's `dockerCommand`, the dashboard or the API.

## Acceptance

- The checklist rows state the limitation and the workaround.
- With the upstream patch, `services create --runtime docker --start-command X` reads back `dockerCommand: X` against bex and the command's output appears in the app log; `--build-command` is refused before any request.
- After the patch is adopted: the same journey with the released `bex`.
