# Every deploy gives the sandbox lifecycle server a new image digest and so restarts it, even when nothing in it changed

Why: `opensandbox-server` is one `Recreate` replica, so a restart is a window in which every sandbox call in every workspace answers `503 SANDBOX_RUNTIME_UNAVAILABLE` (a bare `500` before w8/248). w8/248 removed the two scripted restarts a deploy made; the third remains, because the deploy pins a different server digest every time.

**Severity:** minor (one short, named, retryable outage per deploy; sandboxes themselves keep running). **Attribution:** infrastructure (build). **Estimate:** ~60m. **Source:** found while working w8/248, 2026-11-11.

## Evidence

- `git log -- deploy/opensandbox/kustomization.yaml`: the last six `chore(deploy): pin platform images …` commits (2026-11-10 01:21 UTC to 2026-11-11 05:21 UTC) each changed the `opensandbox-server` digest. None of them had a change under `deploy/opensandbox/server.Dockerfile` or `deploy/opensandbox/requirements.lock`.
- `.github/workflows/deploy.yml` `build_opensandbox` builds `deploy/opensandbox/server.Dockerfile` with no layer cache on every run. The Dockerfile's first `RUN` is `apt-get update && apt-get install --only-upgrade …` against a moving Debian mirror, and nothing sets `SOURCE_DATE_EPOCH`, so layer contents and timestamps differ from build to build.
- Argo CD syncs the new digest, the Deployment's pod template changes, and `strategy: Recreate` (`deploy/opensandbox/server-in-cluster.yaml:83`) stops the old pod before it starts the new one. The store is a ReadWriteOnce PVC (`opensandbox-store`), which is why it is `Recreate` and cannot simply be a rolling update or a second replica.

## Fix

Pick one, in this order of preference:

1. **Pin only when the inputs changed.** Key the server image by a hash of its build inputs (`server.Dockerfile`, `requirements.lock`, the base-image digest and a dated "security refresh" stamp). If an image with that key already exists in the registry, the deploy reuses its digest and the pin is unchanged. A weekly refresh stamp keeps Debian security upgrades flowing. `scripts/lib/image-digest-exists.sh` already answers "does this tag exist".
2. **Make the build reproducible.** `SOURCE_DATE_EPOCH` plus BuildKit `rewrite-timestamp=true`, and replace `apt-get update` with a dated `snapshot.debian.org` source, so the same inputs produce the same digest.

The controller image (`build_opensandbox_controller`) and the agent sandbox image have the same shape and may deserve the same treatment; check their digest history first. Restarting the controller does not take the sandbox API down.

## Acceptance

- Two consecutive production deploys with no change under `deploy/opensandbox/` pin the same `opensandbox-server` digest, and the server pod's age spans both.
- A 5-second poll of `GET /v1/sandboxes` across such a deploy shows only 200.
- A change to `requirements.lock` still produces a new digest and one restart.

## Dedupe

w8/248 (the named 503, the read repeats, the two scripted restarts). No other `.pm` item covers the server image's digest churn; `build-toolchain-freshness` (w7) watches toolchain pins, not image reproducibility.
