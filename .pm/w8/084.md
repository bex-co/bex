# Postgres restart reports success when the API refuses it

Why: CLI automation treats a refused database restart as successful, so an operator receives a positive result even though no restart was requested.

**Status:** todo. **Worker:** worker8. **Severity:** major. **Attribution:** upstream Render CLI. **Estimate:** 55m. Sub-hour correction with behavioral verification; no Bex fork or server response change.

## Reproduction and evidence

Functional CLI QA, 2026-10-11 UTC, production `https://api.bex.co/v1/`, isolated human OAuth, workspace `bex-canary` / `tea-daif693dqjvc73e7as3g`. Released Bex v0.3.2 and actual unmodified Render v2.27.0, commit `a764810a768202704e7206eb7b87a47211fcd98e`; Bex source HEAD `4abcd7d8ff23fc06ec917b7b8a70c004d3ca56c8`. Deployed backend/operator revision was not observed. Render production was not contacted.

```sh
bex restart dpg-00000000000000000000 --confirm -o json
```

The synthetic ID is nonexistent: its detail API returns 404, and native `postgres get` exits 1 with `No Postgres database with ID 'dpg-00000000000000000000'`. Restart instead exits **0**, with empty stderr and this JSON string on stdout:

```json
"dpg-00000000000000000000 restarted successfully"
```

A fresh process reproduces in both binaries. Actual native request captures show **POST `/v1/postgres/dpg-00000000000000000000/restart` → HTTP 404**, body:

```json
{
  "code": "NOT_FOUND",
  "error": "not found",
  "id": "not_found",
  "message": "not found",
  "params": null
}
```

Bex exits 0 in 0.518s; Render exits 0 in 0.347s. These are actual process durations, separate from the initial direct Bex reproduction (0.385s). The service sibling control, `restart srv-00000000000000000000 --confirm -o json`, receives the same named 404 but exits **1**, empty stdout, `Error: failed to restart resource: received response code 404 (NOT_FOUND): not found`. Bex takes 0.518s; Render 0.442s. [Full native requests, responses and streams](evidence/084/native-wire.json).

The transparent forwarder admitted only those two exact synthetic POST paths, with no request body, and forwarded to fixed `api.bex.co`. It changed authority only; copied private config host was replaced because stored host takes precedence. Safe headers were captured; Authorization/cookies were never journaled. The first body journal treated gzip bytes as text; that non-lossless body capture was excluded and all four synthetic controls were repeated in fresh native processes. The durable capture preserves raw body bytes as base64 and decodes gzip solely for the readable journal, while forwarding the original response bytes and headers unchanged. Four native children/config copies and the Go process group were cleaned up. [Forwarder source](evidence/084/forwarder.go.txt). The first compile attempt never listened or executed a client; its unused variable was corrected before capture.

## Root cause and affected callers

The pin's producer/consumer chain is:

- `cmd/restart.go:37–47` runs `views.RestartResource` for noninteractive output. The interactive confirmation view uses the same operation.
- `pkg/tui/views/restartview.go:60–65` emits the success string whenever the resource operation returns nil. `pkg/resource/service.go:223–229` dispatches `dpg-` IDs to Postgres restart.
- [`pkg/postgres/repo.go:90–96`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/postgres/repo.go#L90) calls raw generated **`RestartPostgres`**, which returns `*http.Response` (`pkg/client/client_gen.go:6298`). It then passes that raw object to `client.ErrorFromResponse`.
- [`pkg/client/client.go:104–168`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/client/client.go#L104) inspects the decoded wrapper's `HTTPResponse` and `Body` fields. A raw `http.Response` has no `HTTPResponse` field, so `firstNonNilErrorField` returns nil without checking status. The command therefore reports success for an HTTP failure.
- The generated **`RestartPostgresWithResponse`** (`client_gen.go:54800–54806`) already parses through `ParseRestartPostgresResponse:71096–71106`, reads/closes the body, and provides those fields. The service sibling `pkg/service/repo.go:151–162` uses its corresponding `WithResponse` method and rejects the captured 404 correctly.

An actual-pin [loopback probe](evidence/084/response-probe.go.txt), [module](evidence/084/response-probe-go.mod.txt), [checksums](evidence/084/response-probe-go.sum.txt) and [eight results](evidence/084/response-probe.json) exercise the existing Postgres repository, generated decoded method plus shared error helper, and service repository against the same responses. Postgres loses 400/404/409/429/500/503; the decoded control and service sibling reject each. Both successful 200 and upstream-declared 202 remain successes. **Only 404 was reproduced live**; the other statuses are local consumer evidence, with a deliberately constant error body. This probe does not implement the proposed fix.

A production-package search for a raw generated method followed by `ErrorFromResponse` found only this Postgres restart call in the tested pin. Its other CRUD/suspend/resume paths use decoded methods. Root noninteractive restart and the interactive restart view share it; the interactive preconfirmation lookup can separately stop a nonexistent ID, but a subsequent refusal is still lost. Live interactive and text/YAML output paths were not exercised. Key Value restart stays client-unsupported; cron and App restart rules are separate.

## Proposed work and acceptance

1. **Upstream correction (15m):** use `RestartPostgresWithResponse` in the existing Postgres repository, then retain the shared error helper and normal transport-error propagation. Keep the request unchanged and preserve 200/202 acceptance. Prepare the patch locally; external submission, pin adoption and release need separate authorization.
2. **Behavioral regression coverage (20m):** repository and root command tests must fail on the current code: a 404 produces a nonzero exit, no success stdout, and the named not-found diagnostic. Exercise 400/409/429/500/503 locally, a network failure, and successful 200/202. Check JSON/text/YAML failure paths and the shared interactive operation without requiring a production outage.
3. **Caller/contract review (10m):** preserve the service sibling, current-pin Postgres suspend/resume/delete, typed-ID dispatch and unsupported families. Ensure the decoded method consumes/closes the response body. REST/GraphQL/MCP/dashboard need no failure-status rewrite for this client defect. Bex's live server correctly returns 404; changing it to force a transport error would hide the client cause.
4. **Closeout (10m):** after separately authorized upstream adoption, repeat the synthetic failure and an owned Free restart with SQL server-start-time and data controls; update the compatibility ledger with the shipped result.

Open/blocked/done board and Bex history searches found no matching raw-response Postgres restart item. w8/done/040 is the server's cron refusal; w8/done/023 is the deleting-App write guard; w4/done/m137 is datastore restart status. Those do not repair this client error consumer. [Upstream review](evidence/084/upstream-review.json): the GitHub issue query returned no match, and [later upstream repository source](https://github.com/render-oss/cli/blob/c4d106cfdaf8eec6d23475155e43f4baeeed2013/pkg/postgres/repo.go#L85) plus its [error helper](https://github.com/render-oss/cli/blob/c4d106cfdaf8eec6d23475155e43f4baeeed2013/pkg/client/client.go#L129) retain this mismatch. That is source review, not a later-version native test; search coverage is not exhaustive. Later main also changes suspend/resume consumers, so re-audit them before any future pin adoption rather than asserting those later paths are currently shipped defects.
