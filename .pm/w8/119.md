# Env-group tombstones accumulate forever and every scan still reads them

Why: every deleted environment group leaves a permanent `{"tombstoned":"1"}` fence at its workspace meta path (`plantDeletedMetaFence`), so each workspace's group scan — list, environment membership, name and quota checks — grows with every group it ever deleted. w8/m113 made the scan concurrent (about 8× faster), which removes the timeout, but the cost is still linear in deleted groups and unbounded.

Follow-ups from the m113 review, smallest first:

1. **One read per workspace-listed id.** An id from the workspace's own LIST is read at the legacy tenant first (a miss for deleted and post-m80 groups) and then at the workspace. Reading the workspace path first for those ids halves the scan. Before doing it, confirm the MigratePaths window (legacy full meta and workspace copy both present) keeps legacy authoritative or identical.
2. **Age tombstones out.** Record `deletedAt` on the fence, and remove fences older than a grace period that outlives any in-flight create (ids are freshly minted). The removal can be lazy during a scan or a sweep.
3. **A process-wide OpenBao read budget.** The limit of 8 is per scan, and a create runs two scans, so many simultaneous scans multiply the load.

Evidence: [m113 profile](m113/done/t001.md).

**Superseded by [w8/m114](m114/README.md) (2026-10-18):** m114 moves env-group metadata into the control-plane store, so the scan, the fences and the per-scan fan-out all go away. Do not implement these items separately; m114's closeout (t012) retires this note to `done/`.
