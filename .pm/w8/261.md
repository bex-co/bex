# Rolling back to the deploy that is already live is accepted: 201, a restarted instance and a redundant deploy

Why: w4/051 made every surface refuse a rollback to the release that is already running, and w4/110 made `deployActions` stop offering it. In production neither holds any more. A fresh service with one live deploy is told rollback is allowed, and the call restarts its instance and adds a second deploy row for the same image. A script or agent that binds to the capability, or a user who clicks Rollback on the live deploy's detail page, restarts a healthy service for nothing.

**Severity:** minor (no wrong artifact is ever selected; the cost is a needless restart and a misleading deploy history). **Attribution:** server (backend deploys). **Estimate:** ~60m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `65de`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `7ca0227aa477`, workspace `bex-canary`, QA human device login. The pinned CLI has no rollback command, so the calls are REST `POST /v1/services/{id}/rollback` and GraphQL `deployActions` with the CLI's token; the fixtures and deploys were made with `bex`.

## Evidence

All four cases answer `201` with `trigger: rollback`. The contract is `409 conflict: deploy "…" is already live — nothing to roll back to`.

**1. Fresh image service, its only deploy.**

```text
$ bex services create --name qa-20261111-65de-rbc --type web_service --image docker.io/traefik/whoami:v1.10.1 --plan free -o json --confirm
first deploy dep-…oj30  live 11:50:53Z

POST /v1/services/<srv>/rollback {"deployId":"dep-…oj30"}        (11:51:26Z)
→ 201 {"id":"dep-…ojb0","status":"created","trigger":"rollback",
       "image":{"ref":"docker.io/traefik/whoami@sha256:6956a30c…"}}
```

- The rollback deploy went `live` at 11:52:10Z and the first deploy turned `deactivated`.
- `bex services instances <srv>` then listed one instance created 11:51:28Z: the running instance was replaced.
- `bex deploys list <srv>` shows two rows, `rollback` and `other`, for the same digest.

**2. The capability projection.** On a second fresh image service, GraphQL `deployActions(serviceId)` answered `rollback … precondition: "no_eligible_rollback_target"` while the first deploy was in progress, and this once it was live and still the only deploy:

```json
{ "action": "rollback", "outcome": "allowed", "precondition": null, "reason": null }
```

**3. Git-backed service.** A free native Node service with four standard deploys (`bex deploys create <srv> --wait`). Rollback to the live fourth one → `201`, image `…-qa-20261111-65de-tools:gen-4@sha256:ffaba5fa…`.

**4. Live deploy made with an image tag override.** After `bex deploys create <srv> --image docker.io/traefik/whoami:v1.10.4 --wait` went live, a rollback to that deploy → `201`. The instance id changed (`…-e6obfq…` → `…-rb72oi…`), the pod name in whoami's `Hostname` changed, and the new deploy ran the same digest `sha256:1699d99c…`.

**Controls that do answer 409.**

- The live deploy is itself a rollback deploy.
- The live deploy came from an override given by digest: `bex deploys create <srv> --image docker.io/traefik/whoami@sha256:43a68d10… --wait`.

So the guard fires only when the reference string the service holds is already the digest reference.

## Root cause

`RollbackActionable` (`lego/backend/internal/deploys/actioncaps.go:71-88`) decides "already what is running" by comparing reference strings:

- `:79`, with a release selection: `d.ResolvedImage != selected.Image`.
- `:87`, without one: `d.ResolvedImage != a.Spec.Image`.

`d.ResolvedImage` is backfilled from the App's `Status.Image` when the deploy closes live (`lego/backend/internal/store/reconciler.go:963-974`). That is the reference the operator ran, pinned by digest: `docker.io/traefik/whoami@sha256:…` for an external image, `<repo>:gen-4@sha256:…` for a build. The other side is the caller's spelling:

- `a.Spec.Image` is the saved setting, `docker.io/traefik/whoami:v1.10.1` (case 1).
- An override's selection stores the string the caller sent (`deploys/service.go:877`), a tag in case 4 and a digest in the second control.
- A rollback's selection is written from a `ResolvedImage`, which is why the first control matches.

The verb (`service.go:1183`) and the projection (`actioncaps.go:185-188`) share the predicate, so both are wrong together.

`TestRollbackRefusesCurrentLiveNoOp` (`cancel_rollback_test.go:392-405`) passes because the fake closes the deploy with `"web:v1"`, the same string as `sampleApp`'s `Spec.Image` (`service_test.go:61`). No test uses a digest-pinned `ResolvedImage`.

## Fix

1. Decide the no-op by release identity, not by reference spelling. A live deploy `d` is not a rollback target when its generation is the one the App serves and no newer generation is requested (`AnnotationReleaseGeneration <= d.Generation`). With a selection, `d.Generation == selected.Generation` is enough. Where an image comparison is still wanted, compare digests (`d.ImageSHA` against `Status.ImageDigest.Digest`).
2. Keep the recovery arm: after a newer release failed, the still-live deploy stays a valid target (`TestRollbackToLiveDeployRecoversDriftedImage`).
3. Give the tests production-shaped values: a tag in `Spec.Image` with a digest-pinned `ResolvedImage`, a repo-backed App with `gen-N@sha256:…`, and an override by tag.

## Acceptance

- A fresh service with one live deploy: `deployActions` reports rollback with `no_eligible_rollback_target`, and `POST …/rollback` to that deploy answers 409. No deploy row is added and the instance id is unchanged.
- A git-backed service with two live-in-turn deploys: rollback to the live one → 409; rollback to the previous one → 201.
- A live deploy made with `--image <tag>` → 409.
- After a newer deploy fails, rollback to the still-live deploy → 201.
- REST, GraphQL `rollbackService`, MCP `rollback_deploy` and the dashboard deploy detail page agree.

## Unverified

- What `Spec.Image` holds for a repo-backed service was not read from the cluster. Case 3's 201 shows it is not the `gen-N@sha256` reference.
- When the guard stopped firing. w4/110 recorded 409 on every target of a fresh image service on 2026-09-21.
- Whether the redundant rollout drops requests on a single-instance service. Not measured.

## Dedupe

w4/051 (done) added the guard and w4/110 (done) the projection precondition; this is both regressing. w8/128 (done) is the wording of rollback refusals. ADR018's Rollback row states the guard as current behavior ("an already-selected live release is refused with 409").

## Shipped 2026-11-11 (w8 drain); the live replay waits for the next production deploy

- **Fix.** `RollbackActionable` (`lego/backend/internal/deploys/actioncaps.go`) decides "already what is running" by release, not by how the image is spelled.
  - With a selected runtime (an override or an earlier rollback), the live deploy of the selection's generation is the one running.
  - Without one, the live deploy is a target only as a recovery: a newer release generation was requested and is not live, or the saved image moved off the one this deploy was created from. A deploy row records the saved image it was created from (`deploys.image`), so the comparison is spelling against the same spelling; a repository service has an empty one on both sides.
- **Tests** (`rollback_live_noop_test.go`) use production's shapes: a tag saved with a digest run, a repository service with `gen-N@sha256` builds, and a tag override. All three fail on the old predicate. They also assert `deployActions` reports `no_eligible_rollback_target` for the fresh service and keeps offering rollback while a previous build exists, and that both recovery arms stay.
- **Surfaces.** REST, GraphQL `rollbackService` and MCP `rollback_deploy` call the one verb. The dashboard never offered rollback on the live deploy (`isRollbackableDeployStatus` is `deactivated` only), so it needed no change.
- **Answer to "Unverified".** A repository service's `spec.image` is empty (`deploys/service.go` clears it for a repository source), which is why case 3 never matched.
- **Left as it was.** A deploy row from before rows recorded their release (generation 0) keeps the old comparison of references. After a newer release was canceled rather than failed, the live deploy is still accepted as a target (the requested generation stays above it); that arm is unchanged here and is filed as w8/271.
