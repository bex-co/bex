# A renamed service keeps its old name: a create or rename to it is refused "already in use", and `?name=<old name>` lists the renamed service

Why: Render's rule is that "All of a workspace's services must have unique names" (render.com/docs/projects; create-service: "Must be unique within the workspace"), which is a rule about the names services have now. In bex, a service renamed from `x` to `y` still blocks `x` for every other service, and Render's own `name` list filter still finds it under `x`, so the workspace cannot reuse a name that no service shows.

- Severity: minor. A user renames `api` to `api-old`, then cannot create a new `api` and is told the name is in use, while `bex services` lists no `api`.
- Versions: `bex v0.8.0` (Render CLI v2.36.0), `main` `06a28e115`; production pin not read.
- Context: 2026-11-21 05:02–05:16 UTC, `https://api.bex.co`, workspace `bex-canary`, human device-login token, `/qa-find-bugs-cli w8` routine sweep r19-00bb.

## Repro

Fixtures `srv-dc0ib8d26tvc739p1680` (free Python web) and `srv-dc0idft26tvc739p16a0` (free static), both deleted.

```text
$ bex services create --name qa-20261121-00bb-a --type web_service … --plan free -o json --confirm
  → srv-dc0ib8d26tvc739p1680, slug qa-20261121-00bb-a, url https://qa-20261121-00bb-a.onbex.co
$ bex services update srv-dc0ib8d26tvc739p1680 --name qa-20261121-00bb-a2 -o json --confirm
  → exit 0; name qa-20261121-00bb-a2; slug and url unchanged (as on Render)
$ bex services -o json                   → no service named qa-20261121-00bb-a
POST /v1/services?dryRun=true {"type":"static_site","name":"qa-20261121-00bb-a",…}
  → 409 {"code":"CONFLICT","message":"name \"qa-20261121-00bb-a\" is already in use"}
PATCH /v1/services/srv-dc0idft26tvc739p16a0 {"name":"qa-20261121-00bb-a"}
  → 409 {"code":"CONFLICT","message":"name \"qa-20261121-00bb-a\" is already in use"}
GET /v1/services?name=qa-20261121-00bb-a&ownerId=<tea>
  → 200 [ {"service":{"id":"srv-dc0ib8d26tvc739p1680","name":"qa-20261121-00bb-a2",…},"cursor":"qa-20261121-00bb-a"} ]
```

After `srv-dc0ib8d26tvc739p1680` was deleted, the same dry run answered 200. The name is held only while the renamed service lives.

## Root cause

- `lego/backend/internal/store/store.go:2560` `serviceNameTaken` matches `a.name = $3 OR a.display_name = $3`. `apps.name` is the immutable creation name (w8/m47 t001 chose "every displayed and creation-time name"). Create (`:1343`) and rename (`:2448`) both use it.
- The creation name is also the `(tenant_id, name)` unique key and the App CR's object name (`core.CRName`, `core/base.go:2094`), so a newcomer cannot simply take `x` as its own resource name.
- `lego/backend/internal/apps/rest.go:947`: the list `name` filter matches `a.Name` (creation) as well as `renderServiceName(a)` (shown).
- ADR018's "Address a service by name" row records that "Render's own rename-uniqueness behavior is unverified; bex applies its create rule".

## Fix

- Make uniqueness and the `name` filter use the shown name, `COALESCE(NULLIF(display_name,''), name)`, only.
- When a create asks for a name that is only another service's hidden creation name, mint a suffixed resource name for the newcomer and label it with the typed name. The free-form-name path already does this (`serviceNameLabel` + `labelNewService`, `apps/service.go:2290`).
- Allow a rename to such a name.
- By-name resolution already prefers the shown name (w8/m47 t002), so `x` then targets the newcomer.
- Check the Blueprint plan's by-name matching (`workspaceSnapshot`) and the dashboard's name-availability check against the new rule.
- Amend ADR018's row.
- Before building, confirm on Render that renaming frees the old name: rename a throwaway service in a Render account the user controls, then create one under the old name. If Render refuses, record that in ADR018 instead and close this.
