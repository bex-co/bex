# 023 — `bex deploys create` on a just-deleted service returns 500 instead of 404

Why: every by-id read answers a deleting service with a clean 404 (the w3/m81 contract), but the deploy trigger lets a terminating App through and fails with `500 internal error`. That breaks the Render-compatible error dialect clients branch on, and it is the kind of 500 that pages someone.

Live, 2026-09-26, production `726042a28`, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 14. Reproduced 3/3 on fresh free image web services (`srv-darnsiod0qnc73d79sog`, `srv-darnv40d0qnc73d79ss0`, `srv-darnvf0d0qnc73d79svg`, all deleted):

```text
$ bex services delete <srv> --confirm            # exit 0
$ bex deploys create <srv> --confirm             # within ~2 s
Error: received response code 500: internal error
$ bex deploys list <srv>                         # same moment
Error: unexpected response: 404 Not Found
# ~3 s later, and for a never-existent id:
$ bex deploys create <srv> --confirm
Error: received response code 404: not found
```

Siblings in the same window answer 404: `services instances`, `restart`, `logs`, `deploys list`.

## Mechanism

- `lego/backend/internal/core/base.go:1150-1164` `NotFoundIfDeleting`: "Read verbs call it after Authorize*; WRITE verbs deliberately do not". That exemption exists so teardown (delete) can still authorize the CR (`keyvalue/service.go:294-295`).
- `lego/backend/internal/deploys/service.go` guards `List` (`:316`) and `Get` (`:358`), but `Trigger` (`:438`) goes `AuthorizeApp` → `triggerFetched` (`:574`) with a CR whose `DeletionTimestamp` is set. Some step then fails as an unclassified error and is written as 500. The candidates are `EnsurePullSecret`/`EnsureCloneSecret` writing into a namespace under teardown (`:585-598`), the `patchApp` generation bump, or `Store.CreateDeploy` against an app row already removed. The exact step is **unverified** (no server log access this run).

## Fix

Refuse non-teardown **mutations** of a deleting App up front with the same answer reads give. In `Trigger`, `Restart`, `Rollback` and `Cancel`, and the deploy-hook path (`deployhook.go:381`, which calls `triggerFetched` directly), call `core.NotFoundIfDeleting(a)` right after authorization. Delete stays exempt. Check the other App write verbs (`apps` update/scale/suspend, `jobs create`) for the same shape and apply the same guard where a deleting App reaches a side effect.

## Acceptance

- [ ] `bex services delete <srv>` then an immediate `bex deploys create <srv>` → `404 not found` (never 500), and no deploy row, secret or CR patch is written for the deleting App.
- [ ] The same result for `bex restart <srv>` and the deploy hook.
- [ ] A backend test drives `Trigger` against an App with `DeletionTimestamp` set and fails on the old code. Deleting a service still works (teardown not blocked).
