# A service deployed from a public non-GitHub repository (GitLab, Codeberg, …) gets deploys with no commit: commit resolution is GitHub-only

Why: Render deploys any public Git repository by URL and shows each deploy's commit (SHA and message). bex accepts a public GitLab URL and builds and serves it, but the deploy has no `commit`. bex-api resolves commits only through the GitHub API. Without a commit, the deploy history can't say what is running, a deploy can't be pinned to the SHA that was checked, and rollback targets are unnamed. This is not the GitLab _integration_ that `.pm/DO_NOT_DO.md` rejects (connect, repo listing, private deploy, push-to-deploy). Public repo URLs need no provider connection.

Severity: **minor** (the service works; deploy metadata is missing and the build is unpinned). Attribution: server (bex-api commit resolver). Estimate: ~45m. Source: `/qa-find-bugs-cli` loop sweep 6a81, 2026-10-27 02:41–02:44 UTC. Context: HEAD-built bex `34bcceed6` with pinned Render CLI v2.27.0 `a764810a7682`; platform pin `b4726243e74f`; `https://api.bex.co/v1/`; workspace `bex-canary`; human device login.

## Evidence

```text

ref: refs/heads/main  HEAD  → 87e8c32b8918a836c09475e0f668ea7c436d3758
$ bex services create --type static_site --name qa-…-gl --repo https://gitlab.com/pages/plain-html --publish-directory public -o json --confirm
exit 0 → srv-dbg0ul4d3d3c73caqavg (repo https://gitlab.com/pages/plain-html, branch main); live in ~17 s; GET / → "Plain HTML site using GitLab Pages"
GET /v1/services/srv-dbg0ul4d3d3c73caqavg/deploys?limit=1 →
  {"id":"dep-dbg0ul4d3d3c73caqb00","status":"live","trigger":"other","bexTrigger":"create","createdAt":…,"finishedAt":…}
  # no "commit" (a GitHub-backed deploy carries {"commit":{"id":<sha>,"message":…}}), and no "startedAt"
```

The fixture was deleted by ID (`GET` 404).

## Root cause

- `apps.resolveDeployCommit` (`lego/backend/internal/apps/commit.go:52`) and `deploys.resolveCommit` (`lego/backend/internal/deploys/service.go:881`) call `Commits.ResolveCommit`, which is GitHub's `commitSource` (`lego/backend/internal/github/service.go:1308`).
- `resolveCommit` returns "no commit" unless `core.CanonicalRepo(repoURL)` starts with `github.com/` (`service.go` ~`:1346`). Public repos resolve only through GitHub's REST `GetCommit` (`resolvePublicCommit`, `:1384`). So every other host deploys without commit metadata ("omitted, not faked", w9/001).

## Fix

- Add a host-agnostic fallback for public HTTPS repos: resolve `ref` to a SHA with the Git smart-HTTP protocol, as `git ls-remote <repo> refs/heads/<ref>` does (anonymous, bounded timeout, the same miss/TTL cache and no-existence-oracle rule as `resolvePublicCommit`).
- That gives the SHA. For the message, either leave it empty (Render shows it, so prefer filling it) or have the operator report the checked-out commit's subject from the clone step into the deploy row.
- Pin the build to the resolved SHA exactly as for GitHub public repos.
- Keep GitHub on its current API path (it also supplies the message and author time).

## Blast radius

- Every service whose repo URL is on a non-GitHub host: GitLab, Codeberg, self-hosted Gitea/GitLab, Bitbucket public repos.
- The deploy list and detail (REST/GraphQL/MCP, CLI `deploys list`, dashboard), `RENDER_GIT_COMMIT` if it reads the same record, rollback/deploy-by-commit selection, and auto-deploy comparisons. Auto-deploy on push for those hosts remains out of scope (DO_NOT_DO).

## Regression checks

- Unit: a `gitlab.com` public URL resolves `main` to the `ls-remote` SHA; an unknown ref or a private repo is a miss (no existence oracle); the GitHub path is unchanged.
- Live: recreate the fixture above. The first deploy carries `commit.id = 87e8c32b8918…` (or the then-current HEAD), and `RENDER_GIT_COMMIT` matches on a web service. Delete by ID with a 404 proof.

## Outcome — 2026-10-28

**Work → blocked on API deployment and hosted acceptance.** The source premise held. `github.Service.resolveCommit` now routes non-GitHub public HTTPS URLs to anonymous smart-HTTP discovery before the GitHub-App configuration guard; the connected and anonymous GitHub API paths retain their message/author metadata behavior.

- `internal/github/public_git.go` reads the exact repository path's upload-pack advertisement, resolving branches, HEAD, lightweight/peeled annotated tags, and full advertised SHA-1/SHA-256 IDs. It never invents an unadvertised SHA. Branch names win over same-named tags. There is no Git subprocess, provider integration, credential helper, or object fetch.
- The shared `10s` success / `2m` miss cache and singleflight apply. Requests have a `5s` budget, a `1 MiB` response cap, a 16,384-packet cap and at most three HTTPS redirects. Every hop rejects userinfo/non-public dial targets; the production client uses `netutil.SafeDialContext`, no ambient proxy, and no credentials/cookies. All lookup failures stay indistinguishable misses.
- Create and Trigger regression tests prove SHA-only results persist on the deploy row, appear as the Render commit object, and pin `App.Spec.BuildCommit`. The existing clone verifies that exact SHA and stamps the OCI revision label used for `RENDER_GIT_COMMIT`, independent of Git host.
- Focused GitHub/apps/deploys suites, GitHub race tests, workspace lint/dead-code checks, and independent parser/transport review pass. The required real-dependency backend ship gate runs before push. No operator or transport adapter change is needed.
- Anonymous `git ls-remote` and an overlay test of the **production helper with `Service{}` (GitHub disabled)** both returned `87e8c32b8918a836c09475e0f668ea7c436d3758` for `https://gitlab.com/pages/plain-html` main. Final helper main lookup took 388 ms; an unknown ref returned empty/false/nil in 290 ms. HEAD, qualified main and advertised full SHA also matched. Overlay temporary files were removed; this run created no production fixture.

**Scope choice:** message and author time remain empty for generic Git hosts, as permitted by this note: ref advertisements contain neither. Huge/malformed/shallow advertisements and unadvertised historical SHAs remain safe misses; an explicit requested deploy SHA still follows the existing direct build pin when metadata resolution misses. GitHub keeps its richer metadata. See [ADR004](../../../docs/ADR004-app-deployment.md#deploy-commit-provenance-w9001-public-repo-fallbacks-w4m108-t004--w8209).

**Gate:** the release pipeline must deploy bex-api, then QA must recreate the GitLab static fixture and a web fixture, verify current advertised `commit.id`, matching runtime `RENDER_GIT_COMMIT`, an explicit-SHA deploy, and unknown/private-ref miss behavior without regressing GitHub. Delete each fixture by ID and retain 404 proofs. Hosted checks remain unverified, so this note is parked rather than done. The original `startedAt` question is unchanged and is not claimed by this fix.
