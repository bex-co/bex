# A free image web service that listens only on 127.0.0.1 went `live` 7 minutes into its first deploy with no ready instance, where Render keeps scanning and times the deploy out

Why: w8/388's live check on 2026-11-22 saw a deploy report success while nothing served. A user would read `==> Your service is live 🎉` and `live` on a service whose URL answers 503. Render fails such a deploy at its budget (w8/391's `==> Timed Out`).

- Severity: major if it reproduces. The deploy status, the event, the log and notifications all say it succeeded, and nothing serves.
- Seen once, on production pin `de0ed1cbfe7f`, in `bex-canary`. Fixture `qa-20261122-w8388-localhost` (`srv-dc18g7rgedlc73cp63q0`, deploy `dep-dc18g7rgedlc73cp63qg`) is deleted. It was a free `docker.io/library/busybox:1.36` image web service created at 06:13:51 UTC with `POST /v1/services` (`plan: free`, no `healthCheckPath`), `dockerCommand` `sh -c 'mkdir -p /tmp/w && httpd -f -p 127.0.0.1:$PORT -h /tmp/w & wait'`.
  - The build log narrated the localhost scan correctly (w8/388, w8/389): five pairs, then the timeout pair at 06:19:21.
  - REST `stallReason` at 06:18:38 was the open-port check's wait with `hint_image_default_port` ("Nothing accepted a TCP connection on port 10000, the default because the image declares no TCP ports. …"), and the row read `update_in_progress`.
  - At 06:21:15.34 (7 min 24 s) the deploy closed `live`. The `deploy_ended` event says `succeeded`, and the log reads `==> Your service is live 🎉`.
  - `GET /v1/services/<srv>/instances` at 06:22:49 listed one instance, created 06:13:53, so the pod was never replaced. `https://qa-20261122-w8388-localhost.onbex.co/` answered 503 `{"error":"service not ready","retryAfter":5}`, which is the activator's answer for an App with no ready instance (`writeWakeResponse`, `lego/operator/cmd/activator/main.go:378-386`). - Not yet known: what passed. The startup check is the helper's `open-port` exec (`healthProbeOpenPortHandler`, `lego/operator/internal/controller/health_probe.go:70`). It dials the pod's global address (`healthprobe.PodAddrs`), never loopback (`lego/operator/internal/healthprobe/openport.go:77`), so the check alone should not pass on a 127.0.0.1 listener. Read the operator log for App `qa-20261122-w8388-localhost` around 06:21:15 UTC, if it has been kept. That needs `HCLOUD_TOKEN` for `scripts/fetch-app-kubeconfig.sh`, which this checkout's `.env` does not carry. Otherwise reproduce it, live or on the mock cluster, and read the pod's conditions, the Deployment's status and the App's status at the moment it closes.
- Also seen: after discovery's 90 s window, the image service's stall names only the closed default port and drops the localhost finding that discovery wrote (`http_port_localhost_only`). ## Fix

Find what marked the deploy live. A release whose instance never became ready must stay in progress until its budget, then fail as w8/391 closes it. Keep the localhost finding in the stall text past discovery, so the failure reason at the budget names it too.

## Investigated 2026-11-22: the localhost stall shipped (`37b642e1fc`), the trigger not found

- **What marks a web service live.** The operator writes `Running` for a web service only in `reportKubernetesRunning`, once the Deployment reports the instance available (`deploymentRolloutReady`) and the pod list agrees (`deploymentPodsReady`). `reportRolloutProgress` also records the release active when every current-revision pod is Ready (`currentRevisionFullyReady`), which bex-api reads as live through `RolloutSettling`. Both need Kubernetes to report the instance Ready. The pod has no readiness gate, and nothing in bex writes pod or Deployment status, so the kubelet reported this pod Ready at least once. The 503 at 06:22:49 says it was not Ready again 94 s later: `service not ready` needs an active revision and no ready instance, and the route sits on the activator only while `readyReplicas` is 0.
- **What the check sees.** The startup and readiness probes are `health-probe open-port` (`healthProbeOpenPortHandler`). It lists the pod's LISTEN sockets, here 10000 on 127.0.0.1, and dials the pod address on each, which a loopback-only listener refuses. A free web image pod runs one container, and no bex sidecar listens in it. So the check should not pass, and nothing in the operator turns a failing check into `Running`.
- **Two reruns on the same pin `de0ed1cbfe7f` did not reproduce it.**
  - `qa-20261122-w8394-localhost` (`srv-dc1a1abgedlc73cp640g`), the note's fixture alone, created 07:58:33 UTC. It was `update_in_progress` at 10 minutes and `update_failed` at 08:13:36 (15 min 3 s, `timedOutSeconds` 900). Its one instance was never replaced, and the URL gave the first-deploy response throughout. Its node's reader gave no localhost finding.
  - w8/388's timeline replayed: `qa-20261122-w8394-lh2` (`srv-dc1a743gedlc73cp642g`, created 08:10:57), whose discovery named the localhost listener as w8/388's did, beside a `nc -lk -p $PORT` sibling deleted at +4:54 and a second sibling created at +5:14. The second sibling went live at 08:17:52, as w8/388's did 28 s before its localhost fixture. lh2 stayed `update_in_progress` and read `update_failed` at 08:25:59 (15 min 2 s).
  - All four fixtures were deleted by ID, each `GET` 404. The QA session was logged out (whoami 401).
- **Not available: the logs.** The trigger needs the operator log and the pod's node's kubelet journal around 06:21:15 UTC. `scripts/fetch-app-kubeconfig.sh` stops at `HCLOUD_TOKEN is required`, and this checkout's `.env` has none. Both reruns ended before production rolled to pin `89642635b9ce` (dispatched deploy `45001198444`, operator rolled 08:32–08:35 UTC), so both ran on `de0ed1cbfe7f`. That roll restarted the operator, so its log from 06:21 survives only where the platform ships it to Loki. The kubelet journal stays on the node. Look there for a kubelet or containerd restart near 06:21: a kubelet that regenerates a running container's status before its probe workers exist can report it started and Ready. Look also for an operator restart.
- **Shipped: the localhost finding past discovery (`37b642e1fc`).** Round 2 showed it live. Discovery's stall named the listener on localhost four times, but the failure reason at the budget read "… Nothing accepted a TCP connection on port 10000, the default because the image declares no TCP ports. The server must bind host 0.0.0.0 on the port in PORT (10000). If the service does not need to receive traffic on any port, create a background worker instead. No port answered HTTP during startup discovery." `detectLocalhostAfterDiscovery` (`lego/operator/internal/controller/port_detect.go`) now reads the node's reader once a scan interval for a web image service whose discovery fell back, and replays the verdict between scans. When only loopback listens, `rolloutStallDiagnosis` words the stall as "…: a TCP connect to any open port on the instance. … No open port was detected on 0.0.0.0, but ports are open on localhost (10000): the server must bind host 0.0.0.0 on the port in PORT (10000). No port answered HTTP during startup discovery." It drops the background-worker hint, because the process serves. The verdict at the budget scans afresh, so its "never succeeded within the rollout window" reason ends the same way. bex-api reads the stall as `PortScanLocalhostOnly`. A node without a reader keeps the image's port hint.
