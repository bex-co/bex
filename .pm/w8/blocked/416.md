# A web service whose `PORT` is set but whose process listens on another port never goes live, where Render detects the bound port and uses it

Why: Render's port-binding doc says that a server bound to a port other than `PORT` is "usually" detected and used. Its port-scan failure happens only when no open port at all is found. bex detects the bound port only while `PORT` is unset. Once a user sets `PORT`, a process on another port stalls for the full 15-minute rollout window and fails. The stall text says "the image declares no other TCP port", although bex's listener reader can see the port the process opened.

Severity: **minor** (the deploy fails where Render's would go live; the previous release keeps serving). Attribution: operator, `lego/operator/internal/controller/port_detect.go` and `web_image_http.go`. Estimate: ~50m. Source: routine `cli-qa` sweep r35, 2026-11-23 03:23–03:50 UTC, bex v0.9.0 (Render CLI v2.36.0, pin `4fd34231b637`), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login.

## Render's contract

[render.com/docs/web-services § Port binding](https://render.com/docs/web-services#port-binding) (`curl https://render.com/docs/web-services.md`, lines 141–145):

> The default value of `PORT` is `10000` for all Render web services. You can override this value by setting the environment variable …
>
> If you bind your HTTP server to a different port, Render is _usually_ able to detect and use it. If Render fails to detect a bound port, your web service's deploy fails …

[render.com/docs/troubleshooting-deploys § Port scan timeout reached](https://render.com/docs/troubleshooting-deploys) defines the failure as "Render failed to detect at least one open port on your service's host before its scan timed out".

Neither page makes detection depend on whether `PORT` is the default or a value the user set. A process with one HTTP listener on `0.0.0.0` is therefore detected and served either way. The "Binding to multiple ports" section asks a service with several listeners to put its public server on `PORT`. That is the case where `PORT` should decide.

## Evidence (bex, live)

Fixture `qa-20261123-5355-port` (`srv-dc1r6a53vdpc73b0i7a0`), a free `busybox:1.36` web service in `bex-canary`, created through REST, because the pinned CLI refuses `--start-command` on image services. Its `dockerCommand` listens on `0.0.0.0:${LISTEN:-$PORT}` and serves a page that names the port. Times are UTC.

1. No `PORT` set: live, and the page reads `listen=10000 PORT=10000`.
2. `PUT /v1/services/<id>/env-vars/PORT {"value":"8080"}`, then `bex deploys create <id> --confirm`: live in under 40 s, and the page reads `listen=8080 PORT=8080`. The `PORT` override works.
3. `PUT …/env-vars/LISTEN {"value":"9090"}` (so the process listens on 9090 while `PORT=8080`), then `bex deploys create` → `dep-dc1r75l3vdpc73b0i7i0` at 03:31:34.
   - The app log shows `qa5355 listening on 9090 (PORT=8080)` at 03:31:41.
   - The deploy stays `update_in_progress`. Its `stallReason` from 03:32 on: "… a TCP connect to port 8080. … Nothing accepted a TCP connection on port 8080, set by the service's PORT environment variable; the image declares no other TCP port. Bind the server to 0.0.0.0 on port 8080, or change the service's port to the one it listens on. …"
   - The deploy log (`bex logs -r <id> --type build`) has only `==> Deploy queued` and `==> Deploying image docker.io/library/busybox:1.36`, with no scan line, because a port is open.
   - The URL kept answering 200 from the previous release (`listen=8080`) throughout, which matches Render's zero-downtime rule.
   - At 03:46:37, 15 minutes in, the deploy closed `update_failed` with the same text as its `failureReason` ("… never succeeded within the rollout window …"). The deploy log ends `==> Timed Out` and `==> Common ways to troubleshoot your deploy: …`. The URL still served the 8080 release.
4. Control: `DELETE …/env-vars/PORT` (so `LISTEN=9090` and no `PORT`), then `bex deploys create`. The deploy was live 33 s later, with the deploy log reading `==> Detected HTTP on port 9090; serving it`. The page reads `listen=9090 PORT=10000`. The same process on the same port is detected when `PORT` is unset and never when it is set.

The fixture was deleted by ID afterwards and answered 404.

## Root cause

- `explicitServingPort` (`port_detect.go:92-95`) counts `app.Status.EnvPort > 0` as an explicit port. `detectBoundPort` returns before reading the pod's listeners whenever it is true (`port_detect.go:213`). `detectedServingPort` also clears any detection then (`:100-104`).
- The image HTTP discovery has the same gate: `app.Status.EnvPort == 0` (`web_image_http.go:52`).
- `App.servingPort` puts `Status.EnvPort` ahead of any detected port (`lego/types/v1alpha1/image_network.go`).
- So with a user `PORT`, nothing ever looks at the port the process opened. The stall then falls to `hintNoOtherPort` (`lego/types/v1alpha1/deploy_reasons.go:267`), which speaks only of the image's declared ports.

## Fix

- When a web service's `PORT` (or explicit port) has no listener after `portDetectGrace`, run the same listener read `detectBoundPort` runs today. If exactly one HTTP listener on `0.0.0.0` answers, route, probe and serve on it, as for an unset `PORT`. Keep the process's environment as the user set it: `PORT` stays 8080, as w8/267 keeps `PORT=10000` for a detected port.
- When `PORT` has a listener, `PORT` wins over any other listener, as today. That is Render's multiple-ports rule.
- With several HTTP listeners and none on `PORT`, name them in the stall as the unset-`PORT` path already does. The stall text should never claim no other port when the reader saw one. Name the listener the reader found.
- Apply it to both paths: configured-port services (`detectBoundPort`) and web image services (`web_image_http.go`). Private services follow w8/m504's rules, so check whether the same gate applies there, and list it in the change.
- Update ADR018's `PORT` row ("With a `PORT` the service sets, the process's bound port never differs from the routed port") and ADR004's port precedence to match.

## Acceptance

In `bex-canary` on a free `busybox:1.36` web service with the `dockerCommand` above:

- `PORT=8080`, `LISTEN=9090`, then `bex deploys create` → the deploy goes `live` within about a minute, and `GET https://<name>.onbex.co/` serves `listen=9090 PORT=8080`. The process environment still has `PORT=8080`.
- `PORT=8080` and no `LISTEN` → live on 8080, as today.
- `PORT=8080`, with the process listening on both 8080 and 9090 → served on 8080.
- Only a loopback listener (`127.0.0.1:9090`) with `PORT=8080` → still fails at the rollout budget, with w8/388's localhost wording.

## Triage 2026-11-23 (`/loopx w8`): Render routes only to `PORT`, so the narration and the stall were wrong, not the routing

The Unverified step above found Render's behavior. It is not what this note inferred.

- **Render's staff say a set `PORT` turns detection off.** community.render.com/t/15678 (2023-09-27, read from the Wayback copy, because community.render.com redirects to render.discourse.group, which does not resolve): "By default, the platform will try and detect that port, but if you want to disable the port detector and specify the port to use with the public proxy, you can set the `PORT` env var." /t/363 (2021-01-27): "You can tell Render which port to use by defining the PORT environment variable". That answer fixed a Hasura image Render had routed to 9691 instead of 8080.
- **Render's deploy log scans that port alone.** /t/21740 (2024-05-12) logs `==> Continuing to scan for open port 5000 (from PORT environment variable)...` four times, 63 s apart. htdio-stg/deploy-templates#1 (2025-02-17) has five such lines for port 80, then `==> Port scan timeout reached, failed to detect open port 80 from PORT environment variable. Bind your service to port 80 or update the PORT environment variable to the correct port.` Neither log has a docs line.
- **The doc line this note cited is the unset case.** "If you bind your HTTP server to a different port, Render is _usually_ able to detect and use it" (render.com/docs/web-services.md, line 143). bex has matched it since w8/177.
- **Verdict: work, rescoped.**
  - bex's routing with `PORT` set (`explicitServingPort`, `web_image_http.go:52`) is already Render's, so the Fix and the first Acceptance line here are void.
  - What did differ was the narration. bex's deploy log said nothing for the whole 15 minutes, where Render names the port.
  - The stall's advice was wrong too. It told an image service "the image declares no other TCP port … change the service's port", although `PORT` overrides the service's port, and it said nothing at all on a native service.
  - That is the point this note's Unverified section kept as the smaller fix.
