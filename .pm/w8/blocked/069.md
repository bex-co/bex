# 069 — A native build's "==> Using <runtime> <line>" narration is sometimes missing from the build log

Why: the narration is the user's only record of which toolchain line was picked and why, so dropping it hides the very signal w8/m51 added. Severity: minor (observability). Attribution: native build log capture.

## Evidence (2026-10-08, production, released `bex v0.3.2`, bex-canary fixtures from `examples/runtime-version`)

- Python fixture `srv-db3vqqm2bdqc73aphs20`. The **first** build (queued 20:30:34Z, building from `8e10e70`) used `python:3.12-bookworm`, and `python --version` printed `Python 3.12.15`. But `bex logs --type build --text "Using Python"` returns nothing, and a type-less search finds nothing either. The `==>` lines are only `Build queued` and `Building from …`.
- The redeploy of the same service (`dep-db3vssm2bdqc73aphs3g`) logged `2026-10-08 20:35:13 ==> Using Python 3.12 (from .python-version)`.
- The Node fixture `srv-db3vqqogu8gc73cl1310`'s first build logged `==> Using Node 22 (from .nvmrc)` at 20:31:50, before `Building from` (20:31:55).

## Mechanism (to confirm)

`lego/operator/cmd/native-resolve/main.go:55` prints the single narration line to stdout of a short-lived build step (`internal/build/nativeresolve.go`, `NativeResolveBinary`). The line exists only in that container's output. If build-log capture attaches after a fast container has exited (a first build, with a cold image pull of the bex image, is a plausible case), its one line can be lost. Check how the build-log collector reads init/step containers and whether it can miss output from a completed container. Make the narration durable, for example by emitting it from a step whose logs are always collected, or by having the collector read completed containers' logs.

## Acceptance

- The narration appears in the build log of every native build, the first included. Cover this with a test that runs a native build whose resolve step exits before the collector attaches.

## Reproduction attempt (2026-10-08, w8 /loopx) — not reproduced

Three native Python fixtures were created concurrently from `examples/runtime-version/python` (`qa-20261008-rv069-1..3`, bex-canary, deleted afterwards). For each **first** build, the kubelet log of the build pod's `resolve-native-runtime` container and the Loki-served `bex logs --type build --text "Using Python"` both show `==> Using Python 3.12 (from .python-version)`. So 0 of 3 dropped. The Alloy log-shipper showed no warnings around the original 20:31Z window.

**Lead:** `rv069-1`'s build Job was created about a minute after its siblings. If the original build's first pod was replaced or deleted before Alloy's file tailer read it, the kubelet removes its log files with the pod and the line is gone. Build pods tail files (w6/m123), which survives a *late* attach but not pod deletion. That is unconfirmed: the original build pod was garbage-collected with its service before it could be inspected.

**BLOCKED on a recurrence with evidence:** the next occurrence must be captured with the build Job's events and pod list (`kubectl -n bex-build get events --field-selector involvedObject.kind=Job`, and pods by `app.bex.co/build`) *before* the service is deleted. Until then there is no defect to fix that the code inspection supports.
