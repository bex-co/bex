# 097 — Literal alert/emergency severities become unknown and disappear from CLI level filters

Why: an application can log an explicit supported severity yet its most urgent records are classified as unknown and omitted from the CLI's level filters.

**Severity:** minor. **Attribution:** log-shipper producer normalization. **Estimate:** 55m. Follow-up to [done/031](../done/031.md), with a distinct producer gap; its working query aliases remain in place. User-requested continuous `$qa-find-bugs-cli`, w8, sweep174, 2026-10-12 UTC / 2026-10-11 America/Los_Angeles. Filing only; no fix or ship.

Published Bex v0.3.2 and unmodified Render v2.27.0 at a764810a768202704e7206eb7b87a47211fcd98e target `https://api.bex.co/v1/` with the isolated QA human OAuth grant in `bex-canary` (`tea-daif693dqjvc73e7as3g`). Source HEAD aeeba21e7cd5a56a0f59d5a0ffe7d17fa457aff0; deployed API/operator/collector revisions unknown. Commands use non-TTY JSON output.

## Reproduction

A fresh owned Free Node web service prints the [harmless programme](../evidence/097/program.js.txt). Representative lines:

```text
{"level":"alert","message":"QA174_dc1b01 JSON_ALERT"}
{"level":"emergency","message":"QA174_dc1b01 JSON_EMERGENCY"}
{"severity":"ALERT","message":"QA174_dc1b01 JSON_SEVERITY_ALERT"}
{"severity":"EMERGENCY","message":"QA174_dc1b01 JSON_SEVERITY_EMERGENCY"}
level=alert msg=QA174_dc1b01_FMT_alert
severity=EMERGENCY msg=QA174_dc1b01_FMT_EMERGENCY
```

```sh
bex logs --resources <OWNED_SERVICE_ID> --type app --text <OWN_MARKER> --limit 100 --confirm -o json
bex logs --resources <OWNED_SERVICE_ID> --type app --text <OWN_MARKER> --level alert --limit 100 --confirm -o json
bex logs --resources <OWNED_SERVICE_ID> --type app --text <OWN_MARKER> --level emergency --limit 100 --confirm -o json
```

Repeat with unmodified same-pin Render explicitly configured against Bex, in isolated copied config. The recorded fixture is deleted; create a fresh owned fixture before replaying.

**Actual:** both unfiltered clients return all 13 exact messages. The six lines above carry `level:unknown`. `--level alert` and `--level emergency` each exit0 with only the ordinary `error` and `critical` controls; neither includes a literal alert/emergency record. Bex alert/emergency queries take 3.006s/3.066s; Render takes 3.006s/3.099s, with empty stderr. `error`/`critical` filters and an error-containing union miss the same six IDs.

**Expected:** normalize the two explicit valid severity names to the existing error bucket, so the current `storedLevels` alias mapping can return them. Preserve all message bytes. This follows the pinned CLI's accepted vocabulary and the existing server's alert/emergency→error mapping, rather than introducing a new severity model.

## Root cause and blast radius

[Source excerpts](../evidence/097/source.txt) and [caller census](../evidence/097/callers-contract.json):

- `deploy/gitops/base/log-shipper.yaml:332` lowercases explicit JSON/logfmt severity but maps only error/err/fatal/panic/critical/crit into error. Literal `alert` and `emergency` fall through to unknown. Case folding already works; uppercase inputs also fall through.
- The sibling platform normalization at `:505` omits the same aliases. JSON behavior is confirmed in the locally rendered source pipeline only; production platform streams were not queried.
- `lego/backend/internal/logs/loki.go:566–591 storedLevels` already maps requested alert/emergency to error plus the literal name. Its two production callers are Loki query construction (`:440`) and the Postgres fallback filter (`service.go:631`). The query mapper cannot recover a record stored as unknown without also returning unrelated unknown messages.
- The pinned `cmd/logs.go:63–64` explicitly accepts alert and emergency. `pkg/tui/views/logloader.go:155–173` copies those values into `ListLogsParams`; `pkg/logs/repo.go:30–40` decodes the API result. Both native clients behave faithfully; the launcher needs no workaround.
- `scripts/test_log_shipper.py:211–223` exercises many aliases but omits these two enum names. The PostgreSQL severity normalizer uses its own engine vocabulary; the minimal correction targets the two generic App/platform templates.
