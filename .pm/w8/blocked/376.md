# A re-plan of an unchanged Blueprint with an `envVarGroups` entry never reads `no_changes`: the env group always plans as an update of `envVars` and `name`, and approving it writes nothing

Why: `bex ea blueprints plan` on a Blueprint nobody changed should read `no_changes`, as it does for Blueprints without env groups. With an env group it reads `planned` forever, and the CLI tells the user to approve a change that does not exist. 12 of the 181 `render-examples` root files declare `envVarGroups`, among them `full-stack-fastapi-template`, `mastodon`, `forem` and `saleor`.

- Severity: minor. The final state is right; the plan is noise that never goes away.
- Attribution: server (bex-api Blueprint plan).
- Source: the w8/375 live check, 2026-11-21 13:08–13:16 UTC, `bex v0.9.0`, workspace `bex-canary`, production pin `cce6c749f6ff`.

## Evidence

`examples/blueprint-refs/render.yaml` (`5a3f6680d3`) declares one env group, two free web services and a static site.

1. `bex ea blueprints create --repo https://github.com/bex-co/bex --path examples/blueprint-refs/render.yaml --auto-sync=false` was followed by approve. That created `exs-dc0pfogn82tc73dukq00`, env group `evg-dc0pfqon82tc73dukq4g` and three services. Every service went live with one deploy.
2. `bex ea blueprints plan exs-dc0pfogn82tc73dukq00 -o json` read `planningOutcome: planned`. Every service was a `noop`, but the env group was an `update` with `changedFields` `[envVars, name]`.
3. Approving that plan (`exe-dc0pgt8n82tc73dukqfg`, `success`) wrote nothing. The group's `updatedAt` stayed `2026-11-21T13:09:00.417917Z`, and no service got a new deploy or event.
4. A second re-plan read the same `update`, with `[envVars, name]` again.

Every fixture was then deleted by ID, and each answered 404.

## Root cause

- `lego/backend/internal/apps/blueprint_state_plan.go:425-433`: an existing env group is always `BlueprintPlanUpdate`, and `blueprintDeclaredFieldChanges` lists every declared field. The comment's reason is "Group values are write-only". But the server can read them. `ApplyEnvGroup` (`lego/backend/internal/envgroups/service.go:1614`) reads them and is already idempotent:
  - a literal is written only when it is absent or differs;
  - a `generateValue` key is written only when absent;
  - no writes means no Secret write and no roll.
- `name` is never a change, because the group was matched by that name.
- The `EnvGroupApplier` seam (`lego/backend/internal/apps/deploy.go:178`) exposes only `GroupIDsByName` to the plan, so the plan cannot ask.
- ADR049 (lines 150 and 166) records "existing environment groups keep their separate conservative update plan". ADR018 has no row signing that off as a divergence.

## Fix

- Add a seam method that answers whether `ApplyEnvGroup` would write. Both must share one diff of literals and generates, so the plan and the apply cannot drift. The method returns no values, only "writes owed".
- In the plan, an existing group is a `noop` when nothing is owed and `planEnvGroupMove` plans no move. Otherwise it is an `update` whose `changedFields` name `envVars` only when vars are owed, plus `environment` for a move. Drop `name`.
- Update `blueprint_plan_moves_test.go:269-289` and `blueprint_empty_environment_test.go:133`, which pin the old always-update answer.
- Add tests:
  - an unchanged group plans `noop`;
  - a changed literal, a new literal and a missing generate each plan `update envVars`;
  - a group `sync: false` entry (ignored, w8/293) stays a `noop`.
- Amend ADR049's two sentences.

## Acceptance

- **Production check, after the pin carries the fix:** re-run w8/375's live check in `bex-canary`. The first re-plan after approve must read `no_changes`. As a control, change `GROUP_MARKER` on the group through the API: the next re-plan must read `update` with `envVars`. Delete every fixture by ID and confirm each 404.

## Shipped, waiting for production (2026-11-21)

- `00b6fea8b5` shipped the fix. `ApplyEnvGroup`'s diff is now `blueprintVarWrites` (`lego/backend/internal/envgroups/service.go`), and `envgroups.GroupWritesOwed` asks the same diff whether a write is owed, returning no values. It is a function wired as `apps.Service.EnvGroupWritesOwed` (`lego/backend/internal/api/server.go`), like `GroupPlacements`, rather than an `EnvGroupApplier` method, so the verb sweeps do not count it as a transport verb.
- The plan (`planEnvGroupVars` in `lego/backend/internal/apps/blueprint_state_plan.go`) makes an existing group a `noop` when nothing is owed and no move is planned. Otherwise it is an `update` listing `envVars` only when a variable is owed, plus `environment` for a move. `name` is never listed.
- A caller without `can_view_sensitive`, or an API key not granted env-group values, is refused by a non-auditing probe, so a viewer's validate cannot tell whether a guessed value matches. Such a caller gets `update envVars` with a message saying the plan cannot read the values.
- REST, GraphQL and MCP all serialize the one shared `BlueprintPlanAction`, so they change together. The dashboard's plan row dropped its "Group values are write-only, so every declared variable is re-applied" note in all eight locales, because the note is no longer true.
- ADR049 (D5 twice) and ADR018 (two Blueprint rows) were amended.
- Tests:
  - `blueprint_env_group_plan_test.go`: an unchanged group plans `noop`, and a group `sync: false` entry stays `noop`. A changed literal, a new literal, an empty literal and a missing generate each plan `update envVars`, then `noop` after the apply. A value edited through the API plans `update`, and an edited generated value does not. A viewer gets the message.
  - `writes_owed_test.go`: the answer agrees with `ApplyEnvGroup`, writes nothing, and refuses a viewer and an ungranted key.
  - The moves and empty-environment tests were updated.
- Checks: reverting the plan change fails five tests, and dropping the sensitive probe fails both refusal tests. The backend real-DB suite passed in `scripts/ship-gates.sh`, and so did the dashboard's `yarn lint` and `yarn test`.
