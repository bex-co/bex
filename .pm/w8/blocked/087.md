# Clearing a datastore project filter leaves its active scope in place

Why: A user who clears a project filter in the datastore connection picker still sees No Results, even though a fresh CLI process shows the workspace datastore.

**Status:** blocked. **Worker:** worker8. **Severity:** minor. **Attribution:** upstream Render CLI command callbacks, shared by Bex. **Estimate:** 55m to prepare the upstream correction, behavioral checks and caller review. External submission, adoption and release are separate follow-ups.

For each command in a fresh process:

2. Press `f` for Filter by Project, then Enter on the owned project. The chooser inventory contains exactly that one project. Its genuinely empty environment correctly produces No Results.

4. **Actual:** the picker still says No Results and omits the same owned datastore. **Expected:** clear the active scope and restore that datastore's workspace row. psql/pgcli also retain the old project header; kv-cli's selection callback does not set a project header, so row restoration is the decisive common symptom.
5. Dismiss with Ctrl+C. The isolated config's `project_filter` and `project_name` are empty. Start the same command again: the owned datastore row returns immediately.

All six clear attempts reproduce across the two clients and three commands, in 3.340–3.455s including deliberate dismissal. All six fresh-process controls show the owned row in 0.737–0.763s. ## Cause and shared callers

The unchanged pin's producer, `pkg/tui/views/projectfilter.go:35–41`, runs `config.ClearProjectFilter()` and invokes the handler with `nil`. The saved config really clears, as the native readbacks confirm. `pkg/tui/flows/options.go:58–68` passes that handler through without resetting its command input.

Three command consumers reuse a pointer and update it only for a non-nil project:

- [`cmd/psql.go:59–65`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/cmd/psql.go#L59): retains Project and EnvironmentIDs on the nil callback.
- [`cmd/pgcli.go:48–54`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/cmd/pgcli.go#L48): same retained PSQLInput.
- [`cmd/kvcli.go:47–52`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/cmd/kvcli.go#L47): retains EnvironmentIDs; its existing non-nil branch does not assign Project.

`NewPSQLView` (`pkg/tui/views/psql.go:103–118`) and `NewRedisCLIView` (`rediscli.go:43–58`) consult saved defaults only when EnvironmentIDs is nil. The retained nonempty array therefore wins over the newly cleared config. Their list consumers (`postgreslist.go:63–85`, `keyvaluelist.go:61–80`) still place that array in ListPostgresParams/ListKeyValueParams and call their list services. Bex's REST list producers are `lego/backend/internal/postgres/rest.go:189` and `internal/keyvalue/rest.go:234–240`; the same scope correctly returns the project's empty list, while each unfiltered fresh control returns the owned row. This is consumer state loss, with no observed malformed server response or request refusal.

The complete six-command/flow callback census also finds services (`cmd/service.go:247–259`), logs (`pkg/tui/flows/log.go:94–101`) and SSH (`cmd/ssh.go:119–129`). Those construct fresh inputs on nil and are source-reviewed controls, not separately live-tested clear operations. The two list-view Init paths choose the resource table while the ID is empty (`psql.go:249–254`, `rediscli.go:167–172`), which explains why this reproduction needs no child connection.

[Later upstream source review](../evidence/087/upstream-review.json) at `c4d106cfdaf8eec6d23475155e43f4baeeed2013` finds all three command files and projectfilter.go byte-identical to the tested pin. This is source evidence only; no later release/main executable was run, and no upstream issue-absence claim is made.
