# A deploy that waited behind a failed one can read `queued` through its whole build: three times its row skipped `build_in_progress`, and its `build_started` and `build_ended` events were stamped in the same second, after the build

Why: a deploy row is how the CLI (`bex deploys list`), the API, the dashboard and the Events timeline say what a deploy is doing. Render's deploy statuses go `queued` → `build_in_progress` → `update_in_progress` → `live`, and bex's own rule is to report `build_in_progress` once a build pod is running (`lego/backend/internal/store/reconciler.go:1646-1664`). Three times in this sweep, a deploy that had waited behind a failed one built for 50 to 60 seconds while its row read `queued`. The row then jumped to `update_in_progress` 53 to 63 s after `Build successful`. Its `build_started` and `build_ended` events were written together at that moment, so the Events timeline records a zero-length build that started after it had finished. The build log, streaming at the same time, said the opposite.

**Severity:** minor (status and event timestamps are wrong for a minute or two; the deploy itself proceeds). **Attribution:** platform (operator status or backend sampling; the mechanism was not located). **Estimate:** ~2h, most of it reading the operator's log for the deploys below. **Source:** `/qa-find-bugs-cli` w8 loop sweep `81af`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `3d66946c9e16`, workspace `bex-canary`, QA human device login.

## Evidence

Free native Rust web services from `bex-co/bex` (`--root-directory examples/runtime-version/python`). The build command prints a few variables (about 50 s of build). The start command prints them and then sleeps, so every deploy failed its 15-minute rollout window (`update_failed`, no open port). Each "waiting" deploy was created with `bex deploys create <srv>` while the one ahead was rolling out. Rows were read with `bex deploys list` every 3 to 8 s, the build log with `bex logs --type build`, and events with `GET /v1/services/<id>/events`. Times are UTC.

- For the fifth, a live read of the build log during the gap showed `==> Waiting for platform build capacity` (09:32:43). - Control, same sweep: a deploy waiting behind a failed build (`dep-dbqnm0iibtfs738vkuvg`, Python service) read `build_in_progress` from 08:41:51, the second its build started. Four first deploys created together at 08:10 also showed `build_in_progress` while they built.
- Not a finding here: the 75 to 144 s between the failure and the next build pod. In the one case read live it was a capacity hold, and other QA sessions were building in the same cluster.

## Expected

- While a deploy's build pod is running, its row reads `build_in_progress`, within one backend sampling period (30 s, `defaultResyncPeriod`, `lego/backend/internal/store/reconciler.go:83`) of the pod starting.
- `build_started` carries the time the build started and `build_ended` the time it ended, as w6/035 promised. A build that ran for 50 s does not read as zero seconds.
- Render's deploy object uses the same statuses: `build_in_progress` while it builds, with `build_started`/`build_ended` events around the build ([Deploys](https://render.com/docs/deploys), API `Deploy.status`).

## Root cause

Not located; a code read found no timer that produces these gaps. What the code says:

- The row stays `queued` while the operator's `status.releaseGeneration` is below the row's generation and the row holds the overlap slot (`reconciler.go:1922-1924`). With the generations equal, it reads `build_in_progress` only for `phase=Building` with Ready reason `Building` observed for the current generation (`:1646-1664`, `readyReasonForGeneration` `:2248-2256`). Any other `Building` reason reads `queued`.
- The operator writes `Building` on the pass that sees the build pod placed on a node (`lego/operator/internal/controller/app_controller.go:1311-1313`, `podsPlaced` in `lego/operator/internal/build/build.go:1054-1065`). While the build runs it requeues every 5 s (`buildObserveRequeue`). A release held for capacity requeues every 30 s (`app_controller.go:1156-1160`) and is otherwise woken by `wakeHeldBuilds` (`build_hold.go:164-189`), whose send is non-blocking and drops the wake when the channel is full.
- `build_started` and `started_at` are the backend's own clock at the row's first non-queued transition. `buildStartedAt` returns `time.Now()` when a row leaves `queued` for any in-progress status (`lego/backend/internal/store/reconciler.go:1318-1320`), and `TransitionDeploy` stamps `clock_timestamp()` (`store.go:3087`). The operator's recorded build window (`observedStart`) is used only when a row closes straight from `queued` (`reconciler.go:1321-1324`). So a row that goes from `queued` straight to `update_in_progress` stamps both build events at once.
- So in the three bad cases, no pass of the backend's 30 s loop saw the App with `releaseGeneration` at the waiting deploy and reason `Building` for 100 to 114 s after the pod started. The likely reasons, untested: the operator's 5 s requeues were not served (a Reconcile error loses `RequeueAfter` for the per-item backoff, or both production workers, `BEX_APP_RECONCILE_WORKERS=2`, were busy), or its status writes failed.

## Fix

1. Read the operator's log and the App's condition history for the three deploys above (Ready `lastTransitionTime`, `status.releaseStart.startedAt`, "Reconciler error" lines, `workqueue_queue_duration_seconds{name="app"}` around 08:32–08:35 and 08:54–08:56 UTC on 2026-11-12) and name where the minute went.
2. Whatever the cause, make the dispatch pass write `Building` in the same status update that records the pod placed. The backend can also take a Kick from the operator's status change, as deploy verbs do since w8/270.
3. When a row leaves `queued` for a status past the build, take `build_started` (and `started_at`) from the operator's recorded build window, as the queued-to-terminal close already does (`observedStart`, `reconciler.go:1321-1324`; the build Job's `startTime`, read by `jobRunWindow`, `lego/operator/internal/build/build.go:775`), not from the observation.

## Acceptance

- The case above, replayed three times on production: the waiting deploy reads `build_in_progress` within 35 s of its build pod's first log line, and `build_started` is within 35 s of that line and before `build_ended`.
- The capacity-hold case still reads `queued` until the pod is placed, with `==> Waiting for platform build capacity` in the live log.

## Unverified

- Whether the first three waits were capacity holds.
- Whether it happens without a failed deploy ahead (only that shape was run).
- Docker and image-backed services.

## Dedupe

- w4/535 (blocked) is the opposite timestamp error: `build_started` stamped at the row's creation, minutes early.
- w4/361 (done) was a queued row stuck forever with nothing running.
- w8/270 (done) closed the waiting penalty after a live or canceled deploy and recorded ordinary dispatch time as not filed. This item is the row and the events, not the dispatch.
- w8/m119 and m120 (done) are the overlap slot's ownership, not its reporting.

## Fix 3 shipped, parked on the operator's logs (2026-11-12, `/loopx w8`)

- **Fix 3, shipped.** A row first seen past its build (straight from `queued` to `update_in_progress` or `pre_deploy_in_progress`) now takes `build_started` and `started_at` from the operator's recorded build window (`status.buildRun`), and every `build_ended` takes the window's finish when there is one, instead of the pass that noticed (`buildLifecycleFacts`, `recordedBuildWindow`, `lego/backend/internal/store/reconciler.go`; `TransitionDeploy` lets that evidence outrank its clock on a dispatch-observing phase). The third evidence row would now read `build_started` 08:54:16 and `build_ended` 08:55:10, not both 08:56:10. A row seen leaving the queue into `build_in_progress` keeps the observation's clock. Test: `TestBuildFactsForARowFirstSeenPastItsBuild`.
- **Fixes 1 and 2, open.** Why the row read `queued` for 100–114 s while the build pod ran is still unlocated, and the code read found no timer that explains it; it needs the production operator's log and the App's condition history for the three deploys and the `app` workqueue metrics around 08:32–08:35 and 08:54–08:56 UTC on 2026-11-12. **Gate:** cluster access to production (the user's), or a reproduction on the mock cluster (down until this host's inotify limits are raised: `sudo sysctl -w fs.inotify.max_user_instances=512 fs.inotify.max_user_watches=524288`).
