# A restore of a freshly created paid Postgres instance is still `creating` after 15 minutes

Why: `POST /v1/postgres/{id}/recovery` on a new `0.1c-256mb` instance answered 200 with a new instance id, and that instance never left `creating` in the 15 minutes it was watched. A restore of an empty database should take about as long as a create (two minutes here). Either it is stuck, or it is slow in a way nothing explains to the user.

**Severity:** unknown until reproduced (one observation; the restore may have completed later). **Attribution:** infrastructure/runtime (recovery bootstrap) or server (status). **Estimate:** ~45m to reproduce and read the cluster. **Source:** found while closing w8/m155, 2026-11-11 UTC, production pin `f609163ada8e`, workspace `bex-canary`, QA human device login.

## Evidence

```text
19:05:48  bex pg create --name qa-w8m155-src --plan 0.1c-256mb        → dpg-dbqbp37pvbns739s7pe0
19:07:56  status available (2 min 8 s); one table with one row written
19:08:09  POST /v1/postgres/<src>/recovery-info                         → earliestRecoveryTime = latestRecoveryTime = 2026-11-11T19:07:59Z
19:08:10  POST /v1/postgres/<src>/recovery {"restoreName":"qa-w8m155-restored","restoreTime":"2026-11-11T19:07:59Z"}
                                                                        → 200, id dpg-dbqbq6npvbns739s7pog
19:08:10 – 19:23:45  bex pg get <restored>                              → status creating, every 10 s (90 polls)
19:23:46  both instances deleted (204)
```

An earlier attempt at 18:52 asked for a time ten seconds before `earliestRecoveryTime` and is not evidence of anything.

## Not checked

- Whether the restored instance would have become available later, and what its events or `failureReason` said: it was deleted at the end of the time box.
- The cluster side (the recovery Job, the CloudNativePG Cluster's phase, the WAL archive at that moment). No cluster access from here.
- Whether restoring to exactly `latestRecoveryTime`, seconds after the first base backup, is the trigger. A target a few minutes inside the window may behave differently.

## Fix

Reproduce with a source that has existed for ten minutes and a target well inside its window, then with the shape above. If the second hangs: either the target equals the end of the archived WAL and recovery waits for a segment that is never archived on an idle database, or the status never leaves `creating` on a recovery failure. Report the cause in the instance's status in product terms either way.

## Acceptance

- A restore of a just-created paid instance to its latest recoverable time reaches `available`, or is refused at once with a sentence that says what to wait for.
- A restore that cannot finish leaves `creating` for a failure state with a reason.

## Dedupe

No `.pm` item covers a restore that does not finish. w8/m155 recorded the observation in its closeout.

## Triage 2026-11-12 (`/loopx w8`): cause reproduced off-cluster; parked on a cluster

**Likely cause, reproduced with plain PostgreSQL 17 (Docker, no CNPG).** PostgreSQL's `recovery_target_time` stops only at a commit, abort or restore-point record later than the target. On a database idle since its last commit, no such record exists after any later target, so recovery replays to the end of the archive and stops with `FATAL: recovery ended before configured recovery target was reached` (PostgreSQL 13 and later). Repro: base backup, one commit, target 3 s after it, `pg_switch_wal()`, restore with that target: `consistent recovery state reached` … `FATAL: recovery ended before configured recovery target was reached`. A CNPG instance doing that crash-loops, so the Database never leaves `creating`.

**Why the evidence above hits it.** `latestRecoveryTime` is the source's `lastSuccessfulBackupTime` (`lego/backend/internal/postgres/recovery.go`, `recoveryWindow`), the end of the first base backup, which here came after the one write. `Recover` accepts any target in [earliest, now] (`recovery.go`), and the operator passes it to CNPG as `recoveryTarget.targetTime` (`lego/operator/internal/controller/database_controller.go`). Any restore of an idle source to a time after its last transaction fails the same way, not only a fresh one.

**Fix direction (to verify on a cluster):** make every accepted target reachable: write a restore point on the source when the restore is requested (`pg_create_restore_point` + `pg_switch_wal()` as the instance's superuser, so the archive holds a record later than any target up to now), or restore to the end of the archive when the target is at or after the source's last commit. Separately, a recovery that cannot finish must leave `creating` for a failure state with a reason (acceptance line 2), and `latestRecoveryTime` reading the last base backup's end rather than "now" may itself be a Render-parity question (Render's window runs to the present).

**Gate:** verifying either fix needs CloudNativePG with an object store: the local CAPD mock cluster (down until this host's inotify limits are raised: `sudo sysctl -w fs.inotify.max_user_instances=512 fs.inotify.max_user_watches=524288`), or approval to create two paid Postgres instances in `bex-canary` for a production repro (QA rules forbid paid fixtures without it).
