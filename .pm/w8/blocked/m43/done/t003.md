## Objective

The database page's High Availability section (`dashboard/src/routes/databases.$databaseId.tsx:267-281`) shows the control disabled with the plan requirement on unsupported plans. The plan picker blocks a downgrade under HA with the same message the API returns.

## Acceptance criteria

- [ ] Component tests cover free (disabled + reason), supported (enabled), and downgrade-under-HA (blocked).

## Outcome (2026-09-26) — done

- The dashboard has no HA enable control: `ha-panel.tsx` only shows status and failover, and no create/update form sends `enableHighAvailability`. So "disable the control" came down to: the HA panel says "High availability requires a plan with at least 1 CPU…" instead of "not enabled" when the current plan cannot offer it.
- The plan picker (`database-plan-section.tsx`) blocks Save with the API's message when an HA database selects a plan without HA. Cancel still resets.
- Source is the backend predicate via the new `DatabaseInstanceType.supportsHighAvailability` GraphQL field (offline codegen, feature hunk only). The dashboard never re-derives it from `cpu`.
- Tests: `ha-panel.test.tsx` (unsupported plan → requirement, supported → neutral), `database-plan-section.test.tsx` (downgrade under HA blocked; no HA → any plan).
