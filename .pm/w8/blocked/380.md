# A service addressed by its slug or display name lists its events with that string as `serviceId`, and gives each static route and header a different id than its `srv-` path does

Why: bex-api resolves `/v1/services/{id}` by `srv-` id, then display name, then slug (`core/base.go:1446`, w4/m19 + w8/367), and `bex deploys list <name>` relies on it. Two readers then echo the raw path string where the canonical service id belongs, so one route has up to three ids, an id read under one path form 404s under another, and an event's `serviceId` is a name that `GET /v1/events/{id}` itself never returns.

- Severity: minor. Render clients that always send `srv-` ids are unaffected. A REST or MCP caller that addresses a service by name gets ids that do not round-trip, and the ids change when the service is renamed.
- Versions: bex CLI v0.9.0 release binary. Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md` (`4fd34231b637`). The production pin is unknown, and the code is unchanged on main `a6015f5d9a`.
- Context: 2026-11-21 19:00–19:10 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`). Routine `cli-qa`, run r28, nonce `21f9`. Fixtures (deleted, 404 confirmed): free nginx image web service A `srv-dc0ukja5r8pc73e30e20` (slug `qa-20261121-21f9-a`, later renamed `qa-20261121-21f9-a3`) and static site B `srv-dc0ukju0ri4c73c3vsn0` (slug `qa-20261121-21f9-b`, later named `QA-20261121-21F9-A3`) from `gitlab.com/pages/plain-html` with two routes and one header.
- Attribution: server, `lego/backend/internal/apps` (static rules) and `lego/backend/internal/events`.

Under the same three path forms, the deploy list's `serviceId`, the instance ids and the service `id` all read `srv-dc0ukja5r8pc73e30e20`, so only these two readers diverge.

## Root cause

- `apps/render.go:933` `withRuleIDs` derives a rule id from `serviceID` + content + ordinal, as ADR018's routes row says ("derived from its service"). Every caller passes the request's path value instead of the service id: `apps/rest.go:1497/1526/1529/1556/1571/1588/1603`, and the edit lookups `routeIndex`/`headerIndex` at `apps/static_rules.go:56/61` pass the `name` argument.
- `events/service.go:1172` builds each event with `view(r, service)`, where `service` is the caller's string. The resolved `appID := a.Labels[store.LabelAppID]` sits a few lines above. REST (`events/rest.go:578`), GraphQL `events` (`events/graphql.go:387`) and MCP `list_events`/`list_service_events` (`events/mcp.go:137/157`) all share it.

## Fix

- Derive rule ids from the resolved service id (`AppView.ID` / `a.Labels[core.LabelAppID]`) everywhere. `ListRoutes`/`ListHeaders` (`apps/service.go:6659/6695`) return only views, so they also return the id or the `AppView`. `routeIndex`/`headerIndex` take `a`'s id instead of `name`. Then the `srv-` path's ids, the only ones a Render client sees, are unchanged.
- `events/service.go:1172`: `view(r, appID)`.

## Acceptance

- In `bex-canary`, on a free static site with one route and one header: list routes and headers under the `srv-` id, the slug and the display name. Each rule's id must be the same under all three, PATCH and DELETE by that id must work under any form, and the ids must not change after a rename.
- On any free service, `GET /v1/services/<slug>/events` and GraphQL/MCP list events by name answer `serviceId` = the `srv-` id, equal to `GET /v1/events/{id}`.
- Regression tests: an apps REST test that lists, patches and deletes a route by id across the `srv-`/name path forms, and an events test that lists by name and asserts `serviceId`.

- Selectors: `services update` resolves names with spaces, unicode (`qa-21f9-ünï-测试`), commas (`qa,21f9,comma`), a leading dash after `--`, a name shaped like a nonexistent `srv-` id (the 404 falls through to the name search), and padded names (trimmed). A name equal to another service's id resolves to the id, as upstream's `resolveServiceIDFromNameOrID` does. A case variant is a different name. Names are workspace-unique (409), as `render.com/docs/projects` says. The same environment name in two projects: `kv list --environment production` refuses "multiple environments found … across projects", and `--project <name>` disambiguates. Project names are exact and case-sensitive, and a duplicate is 409.
- REST `name` filters on services, projects and environments are exact and case-sensitive, with no substring or prefix match, and comma and repeated values are ORed. Render documents only "Filter by name", and the pinned CLI matches exactly on the client side for services and relies on the server for projects and environments. No divergence is observable.
- Custom-domain ids were not covered: attaching a domain was out of scope.

## Fix (2026-11-21, `/loopx w8`, commit `880dda5d82`)

- Target: Render's by-path verbs take only `srv-` ids, and the pinned CLI resolves names on the client (`resolveServiceIDFromNameOrID`). bex's name addressing is a recorded native addition (ADR018 "Address a service by name (bex extension)"), so it stays. Every form now resolves once in `core.Base.AuthorizeApp`, and each reader derives from the App it returns, never from the path string. A REST middleware that rewrote `{id}` would have resolved and audited each request twice, so the readers were fixed instead.
- Events: `events.Service.List` builds each event with the App's id (`view(r, appID)`), which REST, GraphQL `serviceEvents` and MCP `list_events`/`list_service_events` share.
- Static rules: `ListRoutes`/`ListHeaders` also return `publicID(a)`. The REST list, PUT, add, patch and the `routeIndex`/`headerIndex` lookups derive rule ids from it or from `AppView.ID`, so the `srv-` path's ids are unchanged. GraphQL and MCP carry no rule ids.
- Sweep of every reader of the path value:
  - Metrics: `Metrics` and `MetricsFilters` echoed `resource=<name>` as the `resource` label, derived instance ids from it, and offered both as RESOURCE/INSTANCE filter values. So a canonical instance filter under a name matched nothing. Both now canonicalize `q.App` after authorization.
  - Deploys: a trigger, restart or rollback's deploy-started email named the path string. It now names `core.AppPublicName`, as a push, the deferred restart and the close-time email do. w8/128's refusal text still names the caller's selector.
  - Cron runs: the `CRON_*` conflicts' `serviceId` detail is the id.
  - Already canonical: deploys, instances, custom domains (`server.id`), disks, env vars and secret files (keyed through `scopeAuthorized`), and logs (`appLogResource`).
  - Left as is: legacy one-off jobs, keyed by `service_name` from before the w4/m116 create gate, are listed under whichever string addresses them. Creation is gone, and the rows are read-only history.
- Tests (each failed with its fix reverted):
  - `apps` `TestStaticRuleIDsAgreeAcrossServiceForms` lists, puts, adds, patches and deletes routes and headers across the `srv-` id, slug and display-name paths. `TestStaticRuleIDsSurviveARename` covers a rename.
  - `events` `TestListByNameAnswersTheServiceID`.
  - `metrics` `TestMetricsByNameAnswerTheServiceID`.
  - `deploys` `TestTriggerNotifiesDeployStartedOffRequestPath` and `TestRestartStartedNotificationNamesTheService`, and `api` `TestEventSurfaceParity`, now expect the id or the public name.
- ADR018: the by-name row and the static-rules row record the rule.
- Left: the production acceptance above, once the pin carries `880dda5d82`. Two free static sites in `bex-canary`: read routes, headers and events under the id, slug and display name. Each must report the `srv-` id and the same rule ids, and PATCH/DELETE by an id read under one form must work under another. Delete the fixtures by id and confirm the 404s.
