## Reproduction and observed behavior

Both `bex pgcli --help` and unmodified `render pgcli --help` exit 0 and include the following example, differing only in executable branding:

```text
# Pass through pgcli arguments
bex pgcli pg-abc123 -- --csv -q
```

Replace the example selector with a real, available, run-owned free Postgres. This hunt created `qa-20261008-651b37-pg-help` / `dpg-db45eahgovas7388mfeg`, Postgres 17, database/user `qa_help_651b37`; it was available before the probes and has since been deleted. On an equivalent fresh fixture, run:

```sh
BEX_HOST=https://api.bex.co/v1/ BEX_WORKSPACE=<qa-workspace-id> \
  BEX_CLI_CONFIG_PATH=<isolated-human-config> \
  bex pgcli <owned-available-postgres-id> -- --csv -q

RENDER_HOST=https://api.bex.co/v1/ RENDER_WORKSPACE=<same-qa-workspace-id> \
  RENDER_CLI_CONFIG_PATH=<separate-equivalent-human-config> \
  render pgcli <same-owned-available-postgres-id> -- --csv -q
```

**Expected:** the advertised passthrough arguments are accepted by pgcli, allowing a database session. **Actual:** both clients launch pgcli, which emits:

```text
Usage: pgcli [OPTIONS] [DBNAME] [USERNAME]
Try 'pgcli --help' for help.

Error: No such option '--csv'. Did you mean '--dsn'?
```

Both display `An error occurred while running pgcli`; neither reaches the SQL prompt or sends the query. The bounded Bex probe was interrupted after 18.700s (parent exit 0 after Ctrl-C); the Render probe was terminated after 20.734s (parent exit -15). These are harness interruption outcomes, **not** claims about child exit propagation or a new TUI hang defect. One earlier helper launch failed before executing Bex; it is excluded from the product evidence.

Independent fresh processes, without database access, establish the failing boundary: `pgcli --csv -q` exits **2**, has empty stdout and the complete stderr above; `pgcli -q` also exits **2**, with the same usage/help lines followed by `Error: No such option '-q'.`. Both flags are absent from real `pgcli --help`.

The same available database succeeds through Bex with valid pgcli arguments:

```sh
bex pgcli <same-owned-available-postgres-id> -- \
  --single-connection --pgclirc <run-owned-profile> \
  --prompt 'qa-pgcli> ' --less-chatty
```

The PTY executes `SELECT 'qa-pgcli-help-651b37' AS marker, current_database() AS db, current_user AS usr, split_part(current_setting('server_version'), '.', 1) AS major;`, observes the ordered row `qa-pgcli-help-651b37 | qa_help_651b37 | qa_help_651b37 | 17` and `SELECT 1`, then quits with rollback of pgcli's read transaction. Bex exits **0 in 3.913s**, without timeout; its temporary CA file is removed. Earlier independent real-pgcli ID/name controls on another owned free Postgres also passed. Thus this finding concerns the example, with a healthy actual SQL connection as the control.

## Producer, consumer and proposed fix

The pinned [upstream `cmd/pgcli.go`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/cmd/pgcli.go), inspected in the exact local module cache, defines the incorrect `Example` literal at **lines 26–30**. Its `RunE` **lines 73–75** deliberately stores everything after `--` in `PSQLInput.Args`. The shared [upstream `pkg/tui/views/psql.go`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/tui/views/psql.go) resolves the Postgres selector at **190**, checks its public-IP allowance at **195–205**, fetches connection-info at **208**, appends those arguments unchanged at **213–215**, then executes the selected tool at **218**. The installed pgcli 4.6.0 Click option declarations are in its package `pgcli/main.py`; `--csv` and `-q` are unsupported, independently confirmed by the real parser.

Prepare an upstream change replacing this pgcli-specific example with a tested valid option such as `--single-connection`. Keep the generic passthrough unchanged. `psql --csv -q` is valid and its sibling example should remain. This is one upstream help producer consumed by Render and Bex; the shared execution boundary serves two tools (`psql`, `pgcli`). No REST, GraphQL, MCP, UI, operator or Bex trust workaround is needed. Bex receives an accepted upstream correction through a separately reviewed future pin/release, rather than a local fork.
