# Blueprint plans call an existing environment group a create when its name is padded

Why: A valid declaration should identify the existing group consistently, so the change plan agrees with the parser and apply path about which resource will be updated.

## Cause, consumers and scoped correction

[Numbered producer/consumer excerpts](../evidence/094/source.txt):

- `apps/deploy.go:2136–2144` trims group names in `parseEnvGroup`; create (`envgroups/service.go:509`) and apply (`1516`) use that same existing rule. `applyStackEnvGroups` (`apps/deploy.go:842`) passes the trimmed parsed name to `ApplyEnvGroup`, which finds an existing same-workspace group by that name (`envgroups/service.go:1520`). Apply is source-traced, not performed here.
- `apps/blueprint_ir.go:257–265` copies the untrimmed source `name` into `BlueprintResourceIR.Name`. `PlanBlueprintIR:272–310` uses that value as resource identity.
- `apps/blueprint_state_plan.go:141` looks up the raw name in the canonical `GroupIDsByName` map. Padded names miss the existing group, so the planner emits a create without its ID. Exact names reach the intentional conservative update branch at `223–228`.
- `blueprintValidationPlanFromIR` (`apps/blueprint.go:1888–1889`) separately copies **parsed** group names into `plan.envGroups`, explaining why one response reports the normalized group yet plans a differently spelled new group.
- Pinned `pkg/client/blueprints/blueprints_gen.go:250–273` defines only the summary fields, explaining the narrower native output. Dashboard `blueprint-plan-summary.tsx:66–85,117–147` consumes the action operation/name/ID; its browser rendering was not exercised here.

[Twelve actual compiler/parser/planner observations](../evidence/094/parser-planner.json), [virtual probe](../evidence/094/probe_test.go.txt), [input](../evidence/094/probe-input.json), [overlay](../evidence/094/probe-overlay.json), [complete passing output](../evidence/094/probe.log.txt), isolate this mechanism in unchanged current source under Go1.27.0. All declarations parse to the canonical name; nine padded IR names produce false creates and three exact names produce updates. This is a diagnostic probe, not a fixed build or full suite.

Align the **environment-group IR identity** with the existing trim rule at the single resource-construction seam. Successful lookup must retain the existing group ID and conservative update semantics, without reading its values or introducing a new naming restriction.

## Outcome (2026-10-12) — fix shipped, blocked on hosted acceptance

- **Fix:** `blueprintResourceFromMap` (`lego/backend/internal/apps/blueprint_ir.go`) keys an `env_var_group` IR resource on its trimmed name, the rule `parseEnvGroup` and `ApplyEnvGroup` already apply. Planning, the resource inventory, error locations and duplicate detection (`"  g"` beside `"g"` is the same duplicate the parser already refuses) now agree on one identity; a whitespace-only name keeps its parser error, and other resource kinds are unchanged. Consumer review covered `PlanBlueprintIR`/`blueprint_state_plan.go`, inventory, detach/ownership and error-path lookups.
- **Tests:** `TestBlueprintPaddedEnvGroupNamePlansTheExistingGroup` (`blueprint_envgroup_name_test.go`) validates leading, trailing and U+00A0/U+2003 padding in root, `ungrouped` and project/environment declarations: each plans `update` of `evg-shared` under the canonical name; absent groups still plan a canonical `create`, interior spaces are kept, whitespace-only stays invalid. The nine padded cases fail on the original IR; backend `go test ./...` passes.
- **Noted, not changed:** services, Postgres and Key Value names are also trimmed by the parser but not in the IR (`deploy.go` `fieldsByResource` lookups); the finding scopes those to their own contracts.
- **Blocked:** full-server validation against a fresh owned empty group (padded and exact, three locations) needs the fix deployed to production, then cleanup.
