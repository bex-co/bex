# A web service listening only on 127.0.0.1, or on ports that answer no HTTP, gets the plain `No open ports detected` scan line, where Render names the case it found

Why: w8/385 (2026-11-21) made the deploy log narrate Render's port scan with its plain wording. Render words two cases differently, and bex's 127.0.0.1 QA fixtures hit the first of them every sweep.

- Severity: minor. The plain line and the stall text still point at host `0.0.0.0` and `PORT`; Render's own lines name the cause.
- Render, from deploy logs quoted in GitHub issues (no Render doc prints them; community.render.com no longer resolves):
  - Listener only on localhost (kibetrns/TakeAwayTest#4, 2024-09-30): `==> No open ports detected on 0.0.0.0, continuing to scan...`, then `Port scan timeout reached, no open ports detected on 0.0.0.0. Detected open ports on localhost -- did you mean to bind one of these to 0.0.0.0?`
  - Open ports that answer no HTTP (tacheometry/steam-hour-farmer#10, 2024-08-29): `==> No open HTTP ports detected on 0.0.0.0, continuing to scan...`, then `==> Port scan timeout reached, no open HTTP ports detected. If you don't need to receive public HTTP traffic, create a private service instead.`
  - Both are from 2024. Re-check that Render still prints them, from a newer public log, before shipping.
- bex today: the scan lines come from `logs.portScanLines` (`lego/backend/internal/logs/progress.go`). The control plane times the scan from the stall (`appv1alpha1.PortScanOf`, `lego/types/v1alpha1/deploy_port_scan.go`). The operator's no-open-port hint (`noOpenPortMessage`, `lego/operator/internal/controller/port_detect.go`) and the image HTTP discovery (`web_image_http.go`) do not say whether a loopback or a non-HTTP listener was seen. The node listener reader (w6/m530) reads `/proc/<pid>/net/tcp{,6}`, which lists loopback sockets too.

## Fix

1. Operator: when the scan finds no port on the pod address but the listener reader shows a loopback listener, use a new hint code that says so (Render's "did you mean to bind one of these to 0.0.0.0?"). When it finds open ports and none answers HTTP on a web service, use a code that says that. Add both templates to `deploy_reasons.go` and the dashboard locales.
2. `PortScanOf` returns which case was found, the row records it, and `portScanLines` writes Render's matching scan and timeout lines.

## Acceptance

- Unit tests for both hints, both classifications and both line sets.
- Live in `bex-canary`, on a free `busybox:1.36` web service with `httpd -f -p 127.0.0.1:$PORT`: `bex logs --type build` shows `==> No open ports detected on 0.0.0.0, continuing to scan...` within about 2 minutes. Delete the fixture by ID and confirm the 404.

Estimate: ~1h.

## Shipped 2026-11-21 (`4844d0b169`), live check owed

- **The reader.** The node's listener reader answers a pod's loopback-only ports apart from its reachable ones (`listeners.Answer.Loopback`, JSON `loopback`, omitted when empty). A reader from before this change reads as none. A node without a reader is swept and keeps the plain wording.
- **The operator.** The bound-port scan (`scanForBoundPort`) writes `hint_no_open_port_localhost` when nothing is reachable but something listens on loopback. It writes `hint_no_open_http_port` when open ports answer no HTTP; Phoenix's epmd case gets this one now. HTTP discovery (`selectWebImageHTTP`) writes `http_port_localhost_only` and `http_port_none_http` in the same cases. All four have templates in `deploy_reasons.go` and wording in all eight dashboard locales.
- **The scan.** `PortScanOf` returns `PortScanLocalhostOnly` or `PortScanNoHTTPPort`. A listener that accepts discovery's connection and stays silent reads as no HTTP when the reader listed it and no other port answers. Discovery waiting on a lower silent port while a higher one answers HTTP keeps `http_port_not_answering`, which ends the scan as before. `SetDeployStallReason` records a running scan's first finding and its moment in `port_scan_found`/`port_scan_found_at` (migration 0326), from the same clock reading as `port_scan_since` when the scan starts with a finding, and never changes it.
- **The lines.** `portScanLines` words each line, and the timeout line, for what the scan had found by that line's moment. Lines before the finding keep the plain text, so a line a tail already sent never rewords. The no-HTTP lines carry no docs line. w8/389 changes only the cadence loop; each wording is one `portScanWording` value.
- **Tests:** `TestPortScanOfTheOperatorsStalls`, `TestPortScanFindings`, `TestReadKeepsOnlyListenersOffLoopback`, `TestClientReadsTheHandler`, `TestClientReadsAnAnswerWithoutLoopback`, `TestDetectBoundPortNamesALocalhostOnlyListener`, `TestDetectBoundPortNeverAdoptsAListenerThatDoesNotAnswerHTTP`, `TestWebImageHTTPDiscoveryNamesWhatItFound`, `TestPortScanLinesNameWhatTheScanFound`, `TestPortScanTailWordsTheLinesAfterTheFinding`, the real-DB `TestPGStallReasonRecordsThePortScansFinding`, and the dashboard's zh wording test. I mutated each branch, the wording lookup, the moment check, the reader's loopback split and the shared clock reading, and each mutant failed its test.
- **w8/385's live check:** its fixture, which listens on `127.0.0.1:$PORT`, reads the localhost wording once the pin carries this commit. A fixture that listens nowhere (`dockerCommand` `sleep 3600`) still reads the plain line.
- **Owed:** the production check in Acceptance once the pin carries `4844d0b169`. The expected line is now `==> No open ports detected on 0.0.0.0, continuing to scan...`, followed once by the docs line.
