## Objective

Resolve the requested Python/Node version from the service's env and checked-out source with Render's precedence, and select the matching pinned line.

## Context

- Env vars reach the operator as the build env (the native build already decodes them in-image, `native.go` env loader). The resolver needs them at Dockerfile-generation time.
- Version files live in the checked-out source (`/source/<rootDir>`). Decide whether resolution runs in the clone container (it can read files and emit the chosen line) or in the operator from a fetched file. Prefer the clone step, which already classifies tenant failures.
- Python: `PYTHON_VERSION` → `.python-version` → default. Node: `NODE_VERSION` → `.node-version` → `.nvmrc` → `package.json` `engines.node` → default.

## Steps

1. Implement the resolvers per the t001 policy (semver ranges and `lts` for Node).
2. Thread the chosen line into `nativeDockerfile`'s `FROM`.
3. Read version files relative to the service's root directory, the same way Render reads them from the repo root used for the build.

## Files

- `lego/operator/internal/build/native.go` (+ new resolver file), `build.go` (clone step if used)

## Acceptance criteria

- [ ] Unit tests cover each precedence level and the fallbacks for both runtimes, including a bounded `engines` range and `lts`.

## Out of scope

- Other runtimes (t004).

## Outcome (2026-10-05)

`ResolveNativeVersion` (`internal/build/nativeversion.go`) covers Python (`PYTHON_VERSION` → `.python-version`) and Node (`NODE_VERSION` → `.node-version` → `.nvmrc` → `engines.node`, with semver ranges via Masterminds/semver against each line's exact pinned version, `lts`/`lts/<codename>`/`latest` aliases). Resolution runs in-cluster as the `resolve-native-runtime` init container (bex's own image, `/native-resolve`, after the preparer). It reads files from the service's root directory read-only, accepts regular files only, and rewrites the generated Dockerfile's FROM.
