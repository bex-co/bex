# A Blueprint whose repo is on GitLab or Bitbucket has its render.yaml and commit read from github.com under the same owner/repo

Why: `blueprintRepoToken` (`lego/backend/internal/github/service.go:1562`) takes owner/repo from `ownerRepo`, which drops the host (`service.go:1491`). `resolveBlueprintCommit` (`service.go:1591`) and the content fetch (`service.go:1618`) then call the GitHub API with that pair. So a Blueprint repo `https://gitlab.com/<owner>/<repo>` pins a commit and reads `render.yaml` from `github.com/<owner>/<repo>`: a different repository, possibly another party's, or a 404 that names the wrong host. Render reads a Blueprint from the repo it was given.

- **Source:** follow-up from the w8/343 worker (`c5f5e4915`, `7954674a1`), 2026-11-20. Found by code reading while fixing non-GitHub repo validation; **not reproduced live**.
- **Severity:** major if reproduced. A Blueprint sync applies a configuration from a repository the user never named.
- **Fix direction:**
  - Make the Blueprint fetch host-aware. A github.com repo keeps today's path.
  - A public GitLab or Bitbucket repo fetches over public git transport: `resolvePublicGitCommit`, which already exists for github.com fallbacks, plus a raw read of `render.yaml` at that commit.
  - Any other host, or a private one that can't be reached, answers a 400 that names the host. It never falls through to github.com.
  - Check what Render supports for GitLab and Bitbucket Blueprints before choosing between "fetch" and "refuse". Its docs cover GitLab and Bitbucket repos for Blueprints.
- **Done when:**
  - A unit test shows a gitlab.com Blueprint URL never calls the GitHub client with its owner/repo.
  - A live dry run of a Blueprint pointing at a public GitLab repo either reads that repo's `render.yaml` at its pinned commit or is refused with the host named.
  - A github.com control is unchanged.
- **Blast radius:** every caller of `blueprintRepoToken` (`service.go:1592`, `1618`), and any other `ownerRepo` user that then calls the GitHub API. Grep them in the same change.
- **Estimate:** ~1h.

## Reproduced 2026-11-20 (`/loopx w8`), production pin before `c5f5e4915`

`POST https://api.bex.co/v1/blueprints/preview` in `bex-canary` as the QA human (a dry run: preview writes nothing). GitLab's `render-examples/elasticsearch` has `HEAD` → `master` at `1bdf6f5d…` and no `main`. GitHub's repository of the same name has `main` at `2c1495cc…`, whose `render.yaml` carries an extra `autoDeploy: false` line.

| Body `repo`, `branch` | bex answer |
| --- | --- |
| `https://gitlab.com/render-examples/elasticsearch`, `main` | `found`, `commitId` `2c1495cc…`, GitHub's manifest |
| `https://gitlab.com/render-examples/elasticsearch`, `master` | `found`, `commitId` `2c1495cc…` (GitHub redirects its renamed `master`) |
| `https://github.com/render-examples/elasticsearch`, `main` (control) | `found`, `commitId` `2c1495cc…` |

Render reads Blueprints from GitHub, GitLab and Bitbucket, with public repositories needing no connected account ([deploy-to-render](https://render.com/docs/deploy-to-render): "Paste your GitHub/GitLab/Bitbucket repo URL", "Public repos are supported out of the box"; Render's own `gitlab.com/render-examples` group has a Blueprint in `elasticsearch`). So the parity choice is to fetch from gitlab.com and bitbucket.org and refuse every other host by name.

## Fix shipped 2026-11-20 (`/loopx w8`), live check owed

- `ce33010c1`: `resolveBlueprintCommit` and `fetchBlueprintFileAtCommit` check `onGitHub` first. A `gitlab.com` or `bitbucket.org` repository pins its branch (`refs/heads/<branch>` only, as GitHub's `/branches/{branch}`) from its own public advertisement, read fresh with no cache, and classified by `publicGitRefused` (now shared with `ValidateRepo`). It then reads the file from the host's raw endpoint at that commit, following no redirect (`github/public_blueprint.go`). It never calls the GitHub client or mints a token.
- Any other host, and an SSH, `http://`, userinfo or non-default-port URL of those two, is refused before any read with coded `BLUEPRINT_HOST_UNSUPPORTED`, whose message names the host. A preview shows it as `repo_not_found_or_no_access` with that message, and a create answers 400.
- Tests (`github/public_blueprint_test.go`): GitLab (plain URL, `.git`, subgroup) and Bitbucket read from their own host, with the GitHub client never called even when the workspace's GitHub connection has the same owner. The classification test covers a missing repository, a private one, non-Git, a missing branch, a tag that is not a branch, an outage, 429, raw 404, the sign-in redirect, an oversized file and raw 503. Nine unsupported URLs are refused by name with no request, and a github.com control is unchanged. With the dispatch reverted, every host case fails.
- Real hosts, through the production client from this host: gitlab `render-examples/elasticsearch@master` → `1bdf6f5d` and its own `render.yaml`; `@main` → branch not found; a missing file → 404; missing GitLab and Bitbucket repos → not found; `bitbucket.org/tutorials/markdowndemo@master` → `5b6c39df` and its README; codeberg → refused by name.
- Known gaps: the dashboard's copy for `repo_not_found_or_no_access`, `access_denied` and `unavailable` still names GitHub, which is wrong wording for a GitLab or Bitbucket repository. A Blueprint on an unsupported host with no branch, and a host that does not answer, still answers `repo and branch are required` before the host refusal (`blueprintBranch`). Private GitLab and Bitbucket repositories wait on those providers' Git connections (ADR018, ◐).
- Next, once production's pin carries `ce33010c1`: in `bex-canary`, preview `https://gitlab.com/render-examples/elasticsearch` with `master` (want `commitId` `1bdf6f5d…` and GitLab's manifest, without the `autoDeploy: false` line), with `main` (want `branch_not_found`), and with no branch (want `master`). Then preview `https://codeberg.org/forgejo/forgejo` with `forgejo` (want the host refusal naming `codeberg.org`), and the github.com control with `main` (want `2c1495cc…`). Create nothing.
