## Root cause and proposed fix

[Source excerpts, caller census and targeted history](source.txt), checkout dc1043a16d9c94f1450b6ab07aa7c1b1b0769aa1:

1. `NewLokiSource`, loki.go:59–95, requests 1,000 raw candidates whenever any text term exists. The text prefilter was removed by c7567af44, `fix(logs): match Loki history text locally`, to preserve Unicode semantics.
2. For raw mode, loki.go:90–92 deletes nonmatching candidates inside fetch. `scanLokiWindow`, loki.go:184–237, invokes raw-page coverage handling only for display mode. It receives zero filtered matches, advances to the entire slice boundary and treats that slice as covered, even when Loki returned a full raw page. Older matches inside the slice are skipped.
3. `queryLogPage`, render.go:138–190, receives neither matches nor a ScanIncompleteError. `pageCursors`, render.go:211–220, consequently reports hasMore: false. REST logsQuery:113–118 returns that completed empty envelope. The pinned repo returns JSON200 unchanged and nonInteractiveLogs writes its log array; both clients correctly display the server's false result.
4. Display mode keeps raw candidates until displayScanPage computes actual coverage from raw timestamps, then matches. The same stored fixture therefore succeeds. This is not ingestion loss or query syntax failure.

Route every local text search through raw-candidate coverage before applying its original raw/display matcher. Share the scanner rather than fork it. Preserve inclusive caller end versus exclusive Loki end exactly once for all locally paged modes, far-timestamp group re-reads, both directions, deduplication, limits and the 18s budget. If the budget expires before covering history, return the actual scanned edge as an incomplete page. Do not rewrite the CLI request or restore unsafe Unicode regexp filtering.

**Blast radius:** one production NewLokiSource construction; four Service.History uses (plain ReadLogs plus filtered App, Postgres and Key Value paths); three queryLogPage adapters (REST, GraphQL, MCP), with the CLI using REST and the dashboard consuming GraphQL. Any effective raw text term, including ASCII, can trigger this at saturation. App backward history is live-confirmed; forward behavior is locally reproduced. Saturated managed-data, GraphQL/MCP/dashboard, instance filtering and live-tail parity remain unexercised live. The earlier nonsaturated KV/PG checks still pass. Live subscriptions and pod fallback do not use this Loki paging fetch; preserve their contracts without asserting this failure there.
