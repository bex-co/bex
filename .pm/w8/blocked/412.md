# A native build canceled a few seconds in logs `==> Downloading cache...` after its `==> Deploy canceled`, so the canceled log no longer ends on the cancel line

Why: cli-qa routine run 37 (sweep r34, 2026-11-23, production pin `19fdb46f1758`, bex v0.9.0) canceled a native build about 3 s in.

- **Seen once.** Deploy `dep-dc1okqhfdpsc73e0hkcg` of the bex-canary fixture `qa-20261123-r34-node` (`render-examples/express-hello-world`, since deleted) logged `==> Deploy canceled` at 00:35:58.568 UTC, then `==> Downloading cache...` at 00:36:01.022.
- **Where the line comes from:** the build pod's cache restore, which w9/126 added. The canceled build Job's pod seems to keep running for a few seconds after the cancel. That mechanism is unverified.
- **What it contradicts:** w8/297's Definition of done says a canceled build's log ends with `==> Deploy canceled`, and `docs/render-artifacts/live-deploy-following.md` lists that as the canceled build's last line.
- Severity: minor. The deploy's state is right; the log reads as if the build went on after the cancel.
- Attribution: operator (the deploy-build cancel in `lego/operator/internal/controller/`), or backend (the build-log read in `lego/backend/internal/logs/`, if it should stop at the cancel).
- Dedupe: w8/297 (done) fixed the cancel verdict. No item covers lines after the close.

## Fix

Find whether the pod keeps running, and whether that matters beyond the log: for example, a cache upload after cancel, or compute billed. Then fix one of two ways:
- the cancel stops the build pod before any further step runs, for example by deleting the Job with foreground propagation, or by killing the step process; or
- the build log stops at the deploy's close line, so a late line is never shown under a closed deploy.

Prefer the first, if the pod's extra work is real. Check that Render's canceled-build log also ends at its cancel line (`docs/render-artifacts/live-deploy-following.md`).

## Mechanism and fix, 2026-11-23 (`/loopx w8`)

- **Mechanism, verified.** The cancel deletes the build Job: bex-api with foreground propagation, then the operator's canceled passes (`StopRevision`). The kubelet then stops the running phase with SIGTERM. It starts no later phase. Every build phase is a `sh -c` script running as its container's PID 1, and none trapped TERM. Linux delivers an outside signal to PID 1 only when it handles that signal, so the phase ran on until the SIGKILL at the end of the pod's default 30 s grace period. A Docker probe with the cache phase's own `amazon/aws-cli:2.22.35` image reproduced it: after `docker stop -t 8`, a `sh -c` script printed `==> Downloading cache...` 3 s later and died only at the SIGKILL (exit 137).
- **The work was real.** For up to 30 s after a cancel, the running phase kept going. That was cache-restore's S3 download in this case. In others it was BuildKit's tenant build steps, the skopeo push, or cache-save's upload.
- **Fix (`2d3aec114f`).**
  - Every shell phase opens with `trap 'exit 143' TERM`, so the shell takes the signal and never starts another command.
  - `bex_run` runs the classified command (the clone's fetch, BuildKit's solve) in the background and waits on it, so those phases end at the signal. The kernel then kills the rest of the container.
  - The pod's grace period is 1 s, so any other command in flight (aws or skopeo transfers, which print nothing) is killed at the kubelet's 2 s floor.
- **Probes with the fix.** As PID 1, a stopped `bex_run` phase ends in 0.14 s with nothing after it, in both `busybox:1.37.0` and `moby/buildkit:v0.30.0`. The aws-cli image's trapped shell exits 143 as its current command returns, without the next `echo`.
- **Tests.** `TestS3CacheRestoreStoppedWhileListingSaysAndFetchesNothing` stops a cache-restore while its store listing is in flight. It exits 143 with no `==> Downloading cache...` and no fetch. `TestAClassifiedPhaseEndsAtTheStopSignal` and `TestABuildPodStopsWhenItIsDeleted` cover the other two parts. Each test fails with its part of the fix reverted. The operator suite (`make test`) and lint pass.
- **What is left.** A line a phase writes between the cancel's stamp and the kubelet's signal, a fraction of a second, still sorts after `==> Deploy canceled`. If the live check shows one, file the read-side ordering (the verdict after the build's last line, as the live tail already holds it) as its own item.
- **Render.** This run read no Render log of a canceled build. `docs/render-artifacts/live-deploy-following.md` lists `==> Deploy canceled` as a canceled build's last line, and the fix keeps that true.
