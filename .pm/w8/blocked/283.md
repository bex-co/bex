# A deploy started while a restart settles records a false "Instance failed" outage and the restart as canceled, though the restarted instance serves throughout

Why: `server_failed` is a Critical event: it sends the "Service unavailable" push, alert emails and webhooks. Restarting a service and deploying it shortly after is ordinary, and on bex that pair reports a one-to-two-minute outage that never happened, then lists the restart as "Canceled — Superseded" in the deploy history although its instance took every request.

**Severity:** major (a false Critical availability alert; the deploy history contradicts what served). **Attribution:** server (bex-api reconciler: availability sampling and the superseded-row verdict), with the operator's revision bookkeeping for restarts as the suspected input. **Estimate:** ~90m (diagnose on a cluster, fix both verdicts, tests; promote if it splits). **Source:** `/qa-find-bugs-cli` w8 loop sweep `53bf`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `10acf5314735`, workspace `bex-canary`, QA human device login.

## Evidence

## Expected

- No `server_failed` while the service's instance answers. Render, [Troubleshooting deploys](https://render.com/docs/troubleshooting-deploys): "An `Instance Failed` event occurs when your service's application exits unexpectedly, or when Render restarts it after repeated health check failures." Queuing a deploy is neither.
- The restart's row ends `live` (then `deactivated` when the deploy goes live), as w4/405 settled for any release whose pods served before a newer one superseded it: "Only a release that never served closes `canceled`."

## Root cause (traced in code; the App's status during the window was not read)

- The superseded verdict, `supersededDeployStatus` (`lego/backend/internal/store/reconciler.go:1869-1909`): a row whose generation is below the adopted release generation is `live` only when `servesGeneration` finds that generation in `status.activeRevision` (`:1861-1864`); otherwise it is `canceled`, and the comment names "one a Restart … ended" as a release that never settled. A restart reuses its release's revision (`releaseRevision`, `lego/operator/internal/controller/release_identity.go:768-770`, from the release generation), so a restart row's own generation is probably never what `activeRevision` names, and every superseded restart row closes `canceled` whether or not its pods served.
- The false outage, `observedServiceStateFor` (`reconciler.go:2258-2350`): the unhealthy branches are `servingRevisionDown` (`:2241-2246`, phase `Building` with a current-generation `Serving=False`/`ServingRevisionUnavailable`) and the `Ready=False` branch, which an open deploy suppresses unless the reason is a concrete container failure. `observeServingRevision` (`lego/operator/internal/controller/serving_condition.go:31-65`) counts only non-deleting Ready pods labelled with `status.activeRevision`. Which branch fired, and what `activeRevision` and the restarted pod's revision label were at 07:40:26, needs the App CR from the cluster; the two-pass debounce means the condition read unhealthy at about 07:39:56 and 07:40:26.

## Fix

1. On a cluster, replay the sequence and record the App's `status.activeRevision`, `releaseGeneration`, phase, and `Ready`/`Serving` conditions every 5 s; name the branch.
2. A restart's pods that are Ready serve the release: `Serving` must count them, and the superseded verdict must treat a restart row whose pods became Ready as served (`live`, then `deactivated`).
3. A deploy waiting behind a restart is rollout progress, never an availability failure.
4. Tests for both verdicts with the restart-then-deploy order, and the restart-alone and deploy-alone controls unchanged.

## Acceptance

- `bex restart <srv>`, then `bex deploys create <srv> --wait` 30 s later, URL polled every 2 s: every poll 200, no `server_failed`/`server_available` pair in `GET /v1/services/<srv>/events`, and the restart's row ends `live` then `deactivated`.
- The same with the deploy 5 s after the restart (before the restarted instance is Ready): the row may end `canceled` only if its pods never became Ready.
- A real crash during that window still records `server_failed`.

## Unverified

- The operator-side state at 07:40:26 (no cluster access from this sweep); the two code paths above are where the verdicts are made, not a confirmed mechanism.
- Whether an image-backed or multi-instance service shows the same.
- Whether the alert email and push were actually sent for the fixture (the QA workspace's notification settings were not read).

## Dedupe

`rg -il restart .pm | xargs rg -il "server_failed|failed its health check" | xargs rg -il "supersed|queued behind"`: no match. w4/405 (done) fixed the superseded verdict for releases that served before their `activeRevision` stamp; restarts were not part of its probe. w1/m185 (done) added `servingRevisionDown`. w8/265 (open) is a user cancel near readiness, not a supersede. w8/m158 (on main since 2026-11-12 06:45, not in pin `10acf5314735`) changes `recordObservations` only for process exits; it does not touch these verdicts.
