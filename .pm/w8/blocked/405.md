# A Blueprint image service with `autoDeployTrigger: commit` or `checksPass` (or `autoDeploy: true`) fails validation, where Render's spec says the field "has no effect" for a prebuilt image

Why: Render accepts and ignores an enabled auto-deploy trigger on a prebuilt-image service, so a Render-valid `render.yaml` is refused on bex. ADR049 (line 209) chose to refuse it (w4/m99) before the parity rule of 2026-10-17, and ADR018 records no user sign-off for that divergence.

- Severity: minor. The whole file is refused at validate, plan and apply, so a migrating user must edit a Render-valid Blueprint before bex takes it. Nothing is created wrongly.
- Seen: routine `cli-qa`, 2026-11-22 18:30 UTC, bex CLI v0.9.0 (Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md`), `https://api.bex.co/v1/`, QA human device-flow login, workspace `bex-canary`. This was `blueprints validate` only, so nothing was created.
- Repro: `bex blueprints validate render.yaml -o json` (exit 1) with:

  ```yaml
  services:
    - type: web
      name: qa-20261122-r31-w
      runtime: image
      plan: free
      image:
        url: docker.io/library/nginx:1.27
      autoDeployTrigger: checksPass
  ```

  ```json
  {
    "errors": [
      {
        "error": "prebuilt image services cannot declare autoDeployTrigger; remove it or deploy from repo instead",
        "path": "services[0].autoDeployTrigger"
      }
    ],
    "valid": false
  }
  ```

  The same file with `autoDeployTrigger: commit`, or with `autoDeploy: true`, is refused the same way. `autoDeployTrigger: off` and `autoDeploy: false` pass. The refusal comes from bex's own rule, not from the schema, which is byte-identical to Render's and accepts the field on a server service.

- Render, from [render.com/docs/blueprint-spec](https://render.com/docs/blueprint-spec) § `autoDeployTrigger` (read 2026-11-22): "This field has no effect for services that [deploy a prebuilt Docker image](/docs/deploying-an-image.md)." The same section says that `commit` is "Equivalent to the deprecated setting `autoDeploy: true`".
- bex: `prebuiltImageSourceFields` (`lego/backend/internal/apps/blueprint_compiler.go:438-439`) lists `autoDeploy` and `autoDeployTrigger`, and `blueprintPrebuiltImageProblems` (`:465`, the trigger branch at `:504`) refuses any enabled value. ADR049:209 describes this as "neutral-value compatibility".

## Fix

- In the Blueprint compiler, accept `autoDeployTrigger: commit|checksPass` and `autoDeploy: true` on a prebuilt-image service and give them no effect: no repo watch and no deploy on any push. An invalid enum keeps its schema error. Do the same in Blueprint plan and sync, so a re-sync of the same file plans `no_changes`.
- Leave the direct REST, GraphQL and MCP create and PATCH refusals (w4/418) alone unless Render's REST answer for an image service with `autoDeploy: "yes"` is measured. They are a separate surface, and Render's docs say nothing about them.
- Readback (unverified): Render's stored `autoDeploy` for such a service is not known. Keep bex's neutral readback (`autoDeploy: "no"`, `autoDeployTrigger: "off"`) unless a Render answer shows otherwise, and say so in ADR049.
- Amend ADR049:209 to say the enabled values are accepted and ignored, citing the Render line above. Update the ADR018 Blueprint row.

## Acceptance

- [ ] The repro file validates with exit 0 for `checksPass`, `commit` and `autoDeploy: true`, and its plan creates the service.
- [x] Controls: `autoDeployTrigger: bogus` is still refused by the schema. `buildCommand`, `repo` and `dockerfilePath` beside `image` are still refused, because Render's docs do not say those have no effect.
- [x] A test applies such a Blueprint and proves the image service has no auto-deploy and that a re-plan of the same file reads `no_changes`.

Estimate: ~45m.

## Shipped 2026-11-22 (`764d2efc78`), live check owed

- **Render, re-read 2026-11-22** ([blueprint-spec](https://render.com/docs/blueprint-spec) § `autoDeployTrigger`): "This field has no effect for services that deploy a prebuilt Docker image." `commit` is "Equivalent to the deprecated setting `autoDeploy: true`", and "If you include both, `autoDeployTrigger` takes precedence." The page says nothing that makes `repo`, `buildCommand` or `dockerfilePath` no-ops beside `image`.
- **The fix.** `prebuiltImageSourceFields` keeps `autoDeploy` as a create-only entry, for w4/418's direct create refusal, and drops `autoDeployTrigger`, so `blueprintPrebuiltImageProblems` no longer refuses either spelling. `parseService` drops `autoDeploy` and `checksPass` on an entry with an image, so validate, plan, sync and apply all take the file and the service keeps the image default: `spec.autoDeploy` false, no trigger, read back as `autoDeploy: "no"` and `autoDeployTrigger: "off"`. Every validate surface goes through the same compiler and parse: REST `POST /v1/blueprints/validate` (what `bex blueprints validate` posts), GraphQL `validateBlueprint` and MCP `validate_bex_yml`.
- **Left as they were:** direct REST, GraphQL and MCP create and PATCH still refuse enabled Auto-Deploy on an image service (w4/418), because Render's answer there is not measured. Readback stays neutral, because Render's stored value for such a service is not known. ADR049 and the ADR018 Blueprint row say both.
- **Tests:** `TestValidateBlueprintImageAutoDeployOnEverySurface` runs this note's repro on REST, GraphQL and MCP. `checksPass`, `commit` and `autoDeploy: true` are valid. `autoDeployTrigger: bogus`, `buildCommand`, `repo` and `dockerfilePath` beside `image` are refused at their paths. `TestDeployStackImageAutoDeployHasNoEffect` plans a create for each of the five spellings, applies it with Auto-Deploy off, and re-plans under every spelling as a no-op. `TestBlueprintChecksPassTrigger` checks that the parse drops the trigger. With the fix reverted, all three fail. With only the parse change reverted, the plan test fails on create's `cannot declare autoDeploy`. Two fixtures that used `checksPass` beside an image as their invalid file now use `buildCommand`.
- **Owed:** the production check in Acceptance once the pin carries `764d2efc78`. In `bex-canary`, `bex blueprints validate render.yaml -o json` must exit 0 and print `"valid": true` with no errors for this note's repro file with `autoDeployTrigger: commit`, again with `checksPass` and with `autoDeploy: true`. `autoDeployTrigger: bogus` must still exit 1 with an error at `services[0].autoDeployTrigger`. Render's validate prints no warning for this case, so there is no wording to compare. The check is validate-only and creates nothing.
