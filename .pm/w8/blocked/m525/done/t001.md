## Objective

Carry a second patch on the log-shipper's Alloy (`deploy/log-shipper/`) that adds an opt-in argument to `stage.limit` (name chosen here, for example `by_entry_timestamp = true`). When it is set, each by-label bucket admits a line by the line's own timestamp, not by `time.Now()`, with the rule in the milestone's definition of done item 2.

## Context

- Upstream `shouldThrottle` calls `rl.Allow()` on an `x/time/rate` limiter (`internal/component/loki/process/stages/limit.go:109` at `091a20eb3eb5`, the `ALLOY_COMMIT` in `deploy/log-shipper/Dockerfile`). That limiter refills by wall clock at batch time.
- The entry's timestamp at `stage.limit` is the CRI write time of the record's first chunk (`stage.cri`, plus the carried `cri-first-chunk-timestamp.patch`). That is the same stamp the kubelet serves the tail.
- Rule: `step(t) = floor(t.UnixNano() / (1e9 / rate))`. A new bucket starts with `burst` tokens at its first line's step. A line at a later step adds `step - last` tokens, capped at `burst`, and moves `last`. A line at or before `last` adds none. Admit when tokens ≥ 1, spending one.
- `sandbox_pods` uses `stage.limit` too (20/s, 400). It must keep upstream behavior, which is why the argument is opt-in.

## Steps

1. Write `deploy/log-shipper/patches/limit-entry-timestamp.patch` with the argument, the bucket, and a Go test driven by the shared table from t002 (copy it into the patch's testdata, or read it from a path the Dockerfile copies in).
2. Apply it in the Dockerfile after the CRI patch, and extend the build's `go test` run to cover the limit stage.
3. Keep `max_distinct_labels`, the drop counters and `drop = true` as they are.
