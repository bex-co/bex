# Since w8/399, a nested `package.json` asking for Node older than 14 fails a Python, Ruby, Go, Rust or Elixir build, which may break existing services on their next deploy

Why: w8/399 (`0170f10098`, parked) made bex find `engines.node` in a `package.json` below the service's Root Directory, and the Node companion of every other runtime (`resolveNativeCompanion`) reads the same file. The 399 worker notes that "a nested `package.json` asking for Node <14 now fails a non-Node build too". Before 399, only a root `package.json` could do that. A Python service whose repo carries an old `docs/package.json` or `legacy-frontend/package.json` with `"engines": {"node": "12.x"}` will deploy today, and will fail once 399 rolls.

- Severity: minor to major, depending on how many existing repos have such a file. It turns a passing build into a failing one with no change by the user.
- Attribution: operator, `lego/operator/internal/build/nativeresolve.go` / `nativeversion.go` (w8/399's search) and `resolveNativeCompanion`.
- Dedupe: w8/398 (Node before 14 still refused) and w8/399 (the search) are the parents. No item covers the companion case.

## Fix

Match Render. If Render ignores `engines.node` for non-Node runtimes, or falls back to its default with a warning, the companion must not fail the build on a nested file (and, if the evidence says so, on a root one either). Keep a primary Node service's refusal as w8/398 set it. Record the rule in ADR060 and ADR018, citing only the user's own decisions as user decisions.

## Render's behavior (researched 2026-11-22)

- **Render reads `engines.node` for a non-Node service.**
  - A Render engineer wrote that "The Node version can be set in the same way using the Python Runtime, as it can using the Node runtime" (community.render.com thread 15676, 2023-09-27, read through web.archive.org).
  - Two public Python build logs name a root `package.json`: `==> Requesting Node.js version >=18.0.0` / `==> Using Node.js version 24.1.0 via /opt/render/project/src/package.json` after a Poetry build (Von-Base-Enterprises/core-nexus#17, 2025-06-08), and `==> Requesting Node.js version 24.x` / `==> Using Node.js version 24.13.1 via /opt/render/project/src/package.json` after a pip build (officechbusinessservices-creator/E-BOT#2, 2026-02-19). In both, Render printed the Node lines after the build command had already failed.
- **Render installs Node releases bex refuses.** A Node service logged `==> Using Node version 12.18.3 via environment variable NODE_VERSION` and then built and started (community.render.com thread 15142, 2023-09-07). [render.com/docs/node-version](https://render.com/docs/node-version) (read 2026-11-22) names no minimum and says nothing about an unsupported or invalid request. render.com/docs/native-runtimes lists `node` and `npm` in every native runtime.
- **Not found:** a published log of what Render does with a release that does not exist.

So on Render a Python service with `docs/package.json` asking for `12.x` builds, on Node 12. bex cannot install Node before 14, and the evidence on failures is thin, so the option that never fails is the dated default with a warning. A primary Node service keeps w8/398's refusal.

## Fix (2026-11-22, `bed044a25c`)

- `resolveNativeCompanion` (`lego/operator/internal/build/nativecommon.go`): when another runtime's Node request is one bex refuses as tenant input (`UnsupportedVersionError`), from any signal, the companion resolves again with no Node signal. It takes the dated default (w8/370), and the log reads `==> Using Node.js version 24.22.1 (default)`, the docs line, then `==> docs/package.json engines.node "12.x" is not a supported Node version; supported Node lines are 14, 16, 18, 20, 22, 24, 26, and any other Node release from 14 on installs (such as 25.8.1); using the default Node.js version instead`. A release with no image (`.nvmrc` `99.99.99`) falls back the same way. An unreadable registry is still a platform error. A Node service and a static site still refuse.
- Tests (`nativenodepackage_test.go`): `TestNodeCompanionFallsBackOnARequestBexCannotInstall` covers a nested `docs/package.json` `12.x`, a root `package.json` `<14`, `NODE_VERSION=12.22.12` and `.nvmrc` `99.99.99`, for Python, Ruby, Go, Rust and Elixir, on the common base and the official images. Each case also checks that a Node service refuses the same input, and the warning quotes that refusal. `TestNodeCompanionRegistryErrorStillFails` keeps the platform error. With the fallback disabled, the first test fails. w8/m77's `TestResolveNativeBuildAddsJSToolsToNonNodeRuntimes` asserted that `NODE_VERSION=12` fails a non-Node build; it now asserts the default Node and the warning, and ADR060's m77 bullet says so. w8/370's, w8/371's, w8/372's, w8/398's and w8/399's tests pass unchanged, and so do `make test` and `make lint`.
- Recorded in ADR060 D7 ("Another runtime's Node never fails its build") and ADR018.
- Open (follow-up): installing Node releases before 14, which Render does (thread 15142).
