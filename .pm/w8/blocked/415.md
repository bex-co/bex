# A refused region names bex's internal placement `fsn1`, and `fsn1` itself is accepted on a service create, where Render refuses anything outside its five regions

Why: since user decision D7 (w8/218) and w9/105, no public surface reads `fsn1` back: an omitted region reads `frankfurt`, and a Render region reads itself back. The create-time refusal still tells customers "bex runs every resource in fsn1", and a service create still accepts `fsn1`, a value the pinned Render CLI, Render's API enum, Blueprints and bex's own Postgres and Key Value REST all refuse.

Severity: **minor** (wording, and one accepted value Render refuses; the single-region placement itself is the signed-off D1 policy, w8/152, ADR049 D7, and is not in question). Attribution: server, `lego/backend/internal/resourcemeta/metadata.go`. Estimate: ~30m. Source: routine `cli-qa` sweep r35, 2026-11-23 03:23–03:50 UTC, bex v0.9.0 (Render CLI v2.36.0, pin `4fd34231b637`), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login.

## Render's contract

- Render's region enum is `frankfurt`, `ohio`, `oregon`, `singapore`, `virginia` (pinned client `pkg/types/region.go`, and Render's OpenAPI `region`). [render.com/docs/regions](https://render.com/docs/regions) lists the same five.
- The pinned CLI's own refusal is `region must be one of: frankfurt, ohio, oregon, singapore, virginia` (`ParseRegion`, `pkg/types/region.go:35-43`). bex's comment on `CheckRequestedRegion` says it is "worded like the pinned Render CLI's own check".

## Evidence (bex, live)

Dry-run creates (`?dryRun=true`, nothing was created) in `bex-canary`, one free resource per call:

| Surface                                | Region sent                                                  | Answer                                                                                                                                       |
| -------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/services` (web and static)   | the 5 Render regions                                         | 200, `serviceDetails.region` reads the region sent, URL `https://<name>.onbex.co`                                                            |
| `POST /v1/services` (web and static)   | none                                                         | 200, reads `frankfurt`                                                                                                                       |
| `POST /v1/services` (web and static)   | `fsn1`                                                       | **200, reads `frankfurt`**                                                                                                                   |
| `POST /v1/services` (web and static)   | `mars`, `Oregon`, `" oregon"`, `us-west-2`                   | 400 `{"error":"bad request: region must be one of: frankfurt, ohio, oregon, singapore, virginia; bex runs every resource in fsn1","id":"bad_request",…}` |
| `POST /v1/postgres`, `/v1/key-value`   | the 5 Render regions, none                                   | 200, `region` reads the region sent, or `frankfurt`                                                                                          |
| `POST /v1/postgres`, `/v1/key-value`   | `fsn1`, `mars`, `Oregon`, `" oregon"`, `us-west-2`           | 400 `{"error":"invalid request body at /region","id":"bad_request",…}`                                                                       |

The CLI journey matches: `bex services create --type web_service --image docker.io/library/busybox:1.36 --plan free --region ohio` created `srv-dc1r6cl3vdpc73b0i7c0`, which read back `region: ohio` and `https://qa-20261123-5355-envn.onbex.co`. A REST create with `region: singapore` (`srv-dc1r6a53vdpc73b0i7a0`) read back `singapore`. Both were deleted by ID and answered 404 afterwards. `--region mars` is refused by the pinned client before any request.

## Root cause

`Config.CheckRequestedRegion` (`lego/backend/internal/resourcemeta/metadata.go:185-196`) accepts `region == c.PlatformRegion()` and appends `"; bex runs every resource in %s"` with the platform region. Both date from w8/152 (2026-10-29), when every resource still read back `fsn1`, so a client had to be able to resubmit it. D7, decided the same day, moved every readback to `frankfurt`, and w9/105 made a created resource read back its own Render region. Nothing reads `fsn1` any more: the dashboard and `lego/cli` contain no `fsn1`.

Postgres and Key Value REST refuse `fsn1` and every non-enum value first in the composed server's pinned OpenAPI validator (`safeRenderValidationMessage`, `lego/backend/internal/api/render_openapi.go:1219-1238`). A service's `serviceDetails` is a `oneOf` the validator does not check field by field, so services reach `CheckRequestedRegion`. GraphQL `createService`/`createDatabase`/`createKeyValue` and the MCP create tools call `CheckRequestedRegion` directly, so they accept `fsn1` on every resource type (from the code; not exercised live).

## Fix

- `CheckRequestedRegion` accepts `""` and the five Render regions only, and refuses everything else with exactly `region must be one of: frankfurt, ohio, oregon, singapore, virginia`, as `core.ErrBadRequest`. Drop the platform clause and the placement suffix.
- Keep `StampRegion` and `ResourceRegion` unchanged.
- Update the tables that pin `fsn1` as accepted: `resourcemeta/metadata_test.go`, `apps/blueprint_region_test.go` (REST/GraphQL/MCP service create), `postgres/region_test.go` and `keyvalue/region_test.go`. Add `fsn1` to each refused row.
- Amend ADR049 D7's paragraph ("Any Render region … is accepted") so that it no longer says `BEX_REGION` itself is accepted.

## Acceptance

In `bex-canary`, with dry runs only:

- `POST /v1/services?dryRun=true` with `serviceDetails.region: "fsn1"` → 400 whose message is `region must be one of: frankfurt, ohio, oregon, singapore, virginia` (with or without bex's `bad request: ` prefix), and no `fsn1` anywhere in the body. `mars` gets the same answer.
- The same body with `oregon` → 200 reading `oregon`; with no region → 200 reading `frankfurt`.
- GraphQL `createService(… region: "fsn1")` and MCP `create_web_service` with `region: "fsn1"` refuse with the same message.
- `POST /v1/postgres?dryRun=true` and `/v1/key-value?dryRun=true` with `fsn1` still 400.

## Unverified

- Render's own API body for a non-enum region was not captured, since the pinned CLI refuses it client-side. So the target wording is the pinned client's, not Render's server's.
- The GraphQL and MCP acceptance of `fsn1` comes from the code.

## Dedupe

`rg -i "bex runs every resource|fsn1" .pm` finds only w8/152 (done, which introduced the message), w8/218 (done, D7) and w9/105 (done). No open item covers the message or the `fsn1` acceptance. The single-region placement is D1 (2026-10-29), recorded in ADR049 D7 and ADR018, so it is not filed.

## Fix (shipped `814be34c12` 2026-11-23 by `/loopx w8`)

- **The rule.** `resourcemeta.CheckRequestedRegion` (`lego/backend/internal/resourcemeta/metadata.go`) accepts an omitted region and Render's five, and refuses everything else, `fsn1` included, with `resourcemeta.UnknownRegionError()`: `bad request: region must be one of: frankfurt, ohio, oregon, singapore, virginia`, the pinned CLI's `ParseRegion` wording with no placement clause. It no longer reads the platform config, so it is a package function. Services (REST, GraphQL, MCP), Postgres and Key Value (GraphQL, MCP) and build sources call it.
- **Postgres and Key Value REST.** The pinned OpenAPI gate refused a non-enum top-level `region` with only `invalid request body at /region`. It now answers the same shared message (`renderRequestValidator`, `lego/backend/internal/api/render_openapi.go`).
- **Unchanged.** Placement, `StampRegion` and `ResourceRegion`, so stored rows read as before (only Render regions were ever stamped). Blueprints already refused `fsn1` through the pinned schema enum at the resource's path. Nothing inside bex sends `fsn1` on input: the dashboard sends no region on create, and `lego/cli`, the operator and migrations carry none. Sandbox groups have their own region rule (ADR042) and were not touched.
- **Docs.** ADR018's Create-service row and ADR049 D7 no longer say `BEX_REGION`'s own spelling is accepted. `docs/render-artifacts/cli-services-create-update.md`'s `--region` row was stale (readback `fsn1`) and now says what is served.
- **Tests.** `TestCheckRequestedRegionSpeaksOnlyRendersVocabulary` pins the exact error for `fsn1`, `" fsn1 "`, `mars`, `Vietnam`, `Oregon`, `" oregon"`, `us-west-2` and `local-capd`. `fsn1` moved to the refused rows of `TestCreateServiceRegionPolicyAcrossSurfaces`, `TestCreatePostgresRegionPolicyAcrossSurfaces` and `TestCreateKeyValueRegionPolicyAcrossSurfaces` (REST, GraphQL, MCP each), which also check that no refusal names `fsn1`. `TestCreateRegionPolicyThroughComposedServer` pins the exact body for `fsn1`, `mars` and `Vietnam` on `/v1/services`, `/v1/postgres` and `/v1/key-value` through the pinned validator. A Blueprint service with `region: fsn1` is a located schema refusal. Restoring the old rule and dropping the gate override fails the resourcemeta, Postgres, Key Value and composed-server tests with this note's live answers (201 for a service with `fsn1`, `invalid request body at /region` on the datastores). The backend real-DB suite (ship gates), `go vet` and golangci-lint pass.
