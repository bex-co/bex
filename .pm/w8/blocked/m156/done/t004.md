## Objective

When a cluster-registry image cannot be pulled because its manifest is gone, say so in `failureReason` and in the `image_pull_failed` event in product terms. Do not print the containerd error or `zot.bex-registry.svc`.

## Context

- The failure today reads `image pull is failing: zot.bex-registry.svc:5000/…: Back-off pulling image … failed to resolve image: … not found`.

## Files

- `lego/operator/internal/controller/` (image pull failure diagnosis)
- `lego/backend/internal/store/reconciler.go`

## Acceptance criteria

- [x] No `failureReason` or event message contains `zot.bex-registry.svc`; a missing build reads as a missing build, with the next step.
- [x] A pull failure of an external image keeps naming that image.

## Done 2026-11-11

- `platformPullFailure` (`lego/operator/internal/controller/image_network.go`) writes the stall text for a pull failure of an image in the platform's own registry, at both places the operator diagnoses one (the rollout's stuck pod and the early permanent-failure check).
  - A missing manifest reads: "image pull is failing: the build this release runs on (ws-1/web:gen-8) is no longer stored, so its image cannot be pulled. Only a service's recent builds are kept. Deploy the commit again to build it."
  - Any other failure of a build reads: "…the platform could not pull this release's build (ws-1/web:gen-8). The pull is retried."
  - Neither prints the registry's host, the digest or the container runtime's error. The terminal form swaps the usual prefix ("image pull failed: …").
- An external image keeps naming itself and the registry's answer, unchanged.
- bex-api adds nothing of its own: `failureReason` is the operator's text, and the `image_pull_failed` event carries the image through `PublicImageRef`.
