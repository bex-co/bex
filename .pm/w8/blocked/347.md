# A service create or update carrying both `autoDeploy` and `autoDeployTrigger` is accepted and silently drops `autoDeploy`, where Render says you can't set both

Why: Render's API refuses this request ("You can't set both `autoDeploy` and `autoDeployTrigger` in the same request.", pinned OpenAPI `components.schemas.autoDeploy.description`). bex answers 200 and applies only the trigger, so a client sending `autoDeploy: "no"` next to `autoDeployTrigger: "commit"` is told it worked and still has auto-deploy on.

- Severity: minor. It needs a client that sends both fields, and the pinned CLI never does (`pkg/service/create.go:87` and `update.go:50` send only `autoDeploy`). But the request succeeds while the setting it asked for is ignored.
- Versions: bex CLI v0.7.0 (Render CLI pin `v1.1.3-0.20261106232710-4fd34231b637`); checkout `2b90885cf`; deployed revision not read.
- Context: 2026-11-20 08:44–08:50 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), QA human device-flow token, REST with the CLI's User-Agent; routine `cli-qa`, sweep a380.

## Repro

Fixture `qa-20261120-a380-rb` (`srv-dc00d6l29hjs73bcfvc0`), a free Node web service from `https://github.com/render-examples/express-hello-world`. It was deleted afterwards (GET → 404).

| Request | Answer | Read back (`GET /v1/services/{id}`) |
| --- | --- | --- |
| `PATCH /v1/services/{id}` `{"autoDeployTrigger":"off"}` | 200 | `autoDeploy: "no"`, `autoDeployTrigger: "off"` |
| `PATCH` `{"autoDeploy":"yes"}` | 200 | `yes`, `commit` |
| `PATCH` `{"autoDeploy":"no","autoDeployTrigger":"commit"}` | **200** | **`yes`, `commit`**: `autoDeploy: "no"` is dropped |
| `POST /v1/services` with `"autoDeploy":"no","autoDeployTrigger":"commit"` and `"dryRun":true` (free Node web service) | **200**, the planned service reads `autoDeploy: "yes"`, `autoDeployTrigger: "commit"` | no service created (workspace list checked) |
| `PATCH` `{"autoDeployTrigger":"sometimes"}` / `"Commit"`, `{"autoDeploy":"maybe"}` | 400 `{"error":"invalid request body at /autoDeployTrigger","id":"bad_request",…}` | unchanged |

Expected, from Render's contract: a request carrying both fields is a 400 (`id: "bad_request"`) and changes nothing.

## Root cause

`parseAutoDeploy` (`lego/backend/internal/apps/rest.go:843`) returns the trigger whenever one is set and reads `autoDeploy` only otherwise. Both REST call sites, create (`rest.go:743`) and PATCH (`rest.go:1137`), carry the comment "autoDeployTrigger … wins over the legacy autoDeploy enum when both are sent (w5/m53, w1/m181)". w5/m53 t001 chose that as "Render's documented precedence" before 2026-11-02. The OpenAPI pinned on 2026-11-02 (`4d4f37c84`, w2/m251) carries the opposite rule, and nobody re-checked w5/m53's choice against it.

## Fix

- In `parseAutoDeploy`, refuse a request whose `autoDeploy` and `autoDeployTrigger` are both non-empty with `core.ErrBadRequest` and a message that quotes Render's rule, for example `autoDeploy and autoDeployTrigger can't both be set; use autoDeployTrigger`. Validate before any write, so nothing changes. This covers both REST call sites, including `dryRun`.
- Rewrite both call-site comments and record the change in ADR018's Auto-Deploy row (citing the pinned OpenAPI sentence), superseding w5/m53's precedence note.
- Blast radius, check only: GraphQL `updateService` (`graphql.go:791`) and MCP `update_service` (`mcp.go:900`) take both fields with the same trigger-wins rule. A Blueprint (`deploy.go:3378`) does too. Change each one only if its own Render contract says the same thing: Render's MCP tool schema for MCP, and Render's Blueprint spec for `render.yaml`. GraphQL is bex's own surface, so follow REST there. Record what you find for each.

## Acceptance

- `PATCH /v1/services/{id}` `{"autoDeploy":"no","autoDeployTrigger":"commit"}` answers 400 `bad_request` naming both fields, and the service reads back what it held before.
- `POST /v1/services` with both fields (and with `dryRun`) answers the same 400, and creates no service.
- Controls still pass: either field alone on create and PATCH, `bex services update <srv> --auto-deploy=false` (reads back `no`/`off`), `bex services create … --auto-deploy`, and `services create --from` clone.
- A unit test covers the refusal and both single-field paths.

## Covered in the same sweep, no finding

- Rollback over REST (the pinned CLI has no rollback command). It answers 201 with `trigger: rollback` and the target's commit, goes live in 22 s, and serves the target's commit. It shares PATCH's op table, so it follows REST too. bex's MCP create tools take only `autoDeploy`.
