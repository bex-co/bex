# The Node bundled into a Python, Ruby, Go or Rust build is 24.22.3, while a Node or static service created since 2026-10-21 gets Render's dated default 24.22.1

Why: cli-qa routine run 22 (sweep r20, 2026-11-21 07:45Z, production pin `f797f525f5df`) logged `==> Using Node 24.22.3 (default)` in the Python, Ruby, Go and Rust builds. The static site's build logged `==> Using Node 24.22.1 (default)`. Render's dated Node default table (render.com/docs/node-version) covers "your service", and does not say whether it also applies to the Node bundled with other runtimes.

- Severity: minor, and unverified against Render. It only matters to builds that call Node outside a Node service.
- Cause: `resolveNativeCompanion` (`lego/operator/internal/build/nativecommon.go:185`) calls `ResolveNativeVersion` with a zero creation time. So `defaultExact` (`lego/operator/internal/build/nativeversion.go:195`) never applies the `renderNodeDefault20261021` entry (`nativeversion.go:261`). The bundled Node therefore takes the Node 24 line's current patch (`native.go:203`), which w6/m291 refreshed to 24.22.3 on 2026-11-16.

## Fix

First settle the target with a read-only Render measurement: `node --version` in a Python service's build on Render, if a public build log or example shows it.

- If Render reports 24.22.1 (the dated default), resolve the bundled Node with the service's creation date, and add a unit test.
- If Render reports the line's latest patch, record that in ADR018 and close the note.

## Acceptance

- A Python service created in `bex-canary` after the fix logs the same bundled Node version Render uses for an equivalent service. Use a free fixture, and delete it by ID afterwards.
- A unit test pins the chosen rule.

Estimate: ~30m.

## Target settled from Render, fix shipped 2026-11-21 (`2878c4a8f`)

Render's bundled Node takes the same dated default as a Node service created on the same date. Its documentation does not say so, but its staff and its build logs do:

- A Render engineer (community.render.com thread 15676, 2023) wrote that Node is set in the Python runtime "in the same way" as in the Node runtime. The log line links render.com/docs/node-version.
- Every published non-Node log names an exact default from that page's dated table, never the line's newest patch. Services with different creation dates get different defaults at the same time:
  - A Go build on 2023-09-28 (GitHub linweiyuan/go-chatgpt-api#266) logged `14.17.0 (default)`.
  - A long-running Rails app's Ruby build on 2024-08-16 (thread 24131) logged the same 14.17.0. New services then got 20.15.1.
  - A uvicorn service on 2024-01-19 (assafelovic/gpt-researcher#89) logged `20.10.0 (default)`, though 20.11.0 had been out since 2024-01-09.
  - A Python 3.11 service on 2024-09-01 (rdavydov/Twitch-Channel-Points-Miner-v2#592) logged `20.15.1 (default)`, though 20.17.0 had been out since 2024-08-21.

The fix: `resolveNativeCompanion` now takes the creation time, and `ResolveNativeBuildExact` passes it for the Node companion. `TestNodeCompanionDefaultFollowsTheServiceCreationDate` covers Python, Ruby, Go, Rust and Elixir, on the common base and on the official images. A service created since 2026-10-21 gets `node:24.22.1-bookworm` and the log line `==> Using Node 24.22.1 (default)`. An older or unknown-age service keeps the reviewed 24.22.3. The test fails with the fix reverted. `make test` and the operator lint pass. The evidence is in ADR060 (§ Companion Node default) and ADR018.

A static site's Gemfile Ruby still resolves with no creation date. No Render log shows which Ruby a static site gets.

**Parked** until production runs the fix. The live check comes next: in `bex-canary`, create a free native Python web service from `render-examples/flask-hello-world` with no Node signal and build command `pip install -r requirements.txt && node -v`. Its log should read `==> Using Node 24.22.1 (default)` and `v24.22.1`. Then delete the service by ID, confirm the 404, and close.
