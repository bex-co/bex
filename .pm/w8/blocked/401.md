# A Node release before 14, such as `NODE_VERSION=12.18.3`, is refused at version selection, where Render installs it and builds

Why: w8/398 (`5cb35808e7`) made every Node release from 14 on install from its own digest-pinned official image, but kept releases before 14 refused (`.pm/w8/done/398.md` residual). w8/400 (`bed044a25c`) found that Render installs them. A Node service logged `==> Using Node version 12.18.3 via environment variable NODE_VERSION`, then built and started (community.render.com thread 15142, 2023-09-07, recorded in `.pm/w8/blocked/400.md` line 33). Since w8/400, the companion Node of a non-Node service falls back to the dated default with a warning, but a Node service or a static site that asks for 12 still fails.

- Severity: minor. Releases before 14 are long out of support, but a repo pinned to one deploys on Render and not on bex.
- Attribution: operator, `lego/operator/internal/build/nativeversion.go` / `nativecommon.go` (the floor w8/398 kept).
- Dedupe: w8/398 and w8/400 list this only as an open follow-up. No item covers it.

## Render

- Thread 15142 (above).
- [render.com/docs/node-version](https://render.com/docs/node-version): the documented resolution (node-version-alias) has no floor.

Re-check both, and find Render's lowest installable release if any source states one.

## Fix

Install Node releases before 14 from their official digest-pinned images, the way w8/398 installs 14 and later, as far back as the official images exist. Check whether those old images still run on bex's common base (glibc, architecture), as w8/372 checked for old Bun. If one can't run there, fail with a clear, named reason. Once a primary Node service can install the requested release, w8/400's companion fallback should use it too, rather than fall back. Update ADR060 and ADR018, citing only the user's own decisions as user decisions.

## Acceptance

- Unit tests: `NODE_VERSION=12.18.3` resolves to that release's pinned image for a Node service, a static site and a non-Node service's companion.
- Live in `bex-canary`: a free Node web service from a small public `render-examples` repo with `NODE_VERSION=12.18.3` logs Render's version line, and `node -v` prints `v12.18.3` at runtime, if the app runs on Node 12. If it doesn't, a build command `node -v && exit 0` with a minimal start is enough. Delete it by ID and confirm the 404.

Estimate: ~1h.

## Render's behavior (re-checked 2026-11-22)

- Thread 15142 (2023-09-07; read through its 2023-09-26 web.archive.org copy): `==> Build successful 🎉`, `==> Deploying...`, `==> Using Node version 12.18.3 via environment variable NODE_VERSION`, then the start failed with `Error: Cannot find module 'express'` thrown from `internal/modules/cjs/loader.js:968`, Node 12's own loader. So Render installed and ran 12.18.3.
- [render.com/docs/node-version](https://render.com/docs/node-version), read again 2026-11-22: `node-version-alias` resolves every request, and the page names no minimum and says nothing about unsupported or end-of-life releases. No source found states Render's lowest installable release.

## Fix (2026-11-22, `cfb888fdab`)

- **Selection** (`lego/operator/internal/build/nativeversion.go`, `native.go`): `nodeRequest` no longer refuses a fully qualified version before 14; the resolve phase installs it or refuses it by name. The lines before 14 join the odd lines in `nodeReleasedLines` at their final releases (0.10.48, 0.12.18, 4.9.1, 5.12.0, 6.17.1, 7.10.1, 8.17.0, 9.11.2, 10.24.1, 11.15.0, 12.22.12, 13.14.0, from nodejs.org/dist/index.json). Before 4.0 a line is its 0.x minor (`nodeLine`). So `12` and `12.x` give 12.22.12, `<14` 13.14.0, `>=8 <11` 10.24.1, `0.12` 0.12.18, and `lts/argon` … `lts/erbium` their line's final release. A partial version a final misses (`12.18`) lists the line's tags.
- **Images** (`nativeresolve.go`): a release before 14 comes from bookworm or bullseye, else `-buster`, `-stretch` or `-wheezy` (`nodeLegacyVariants`). Docker Hub, read 2026-11-22, has official images back to 0.8.28, and no release has only a jessie one. Of nodejs.org's 539 releases before 14, 268 have a Debian image a build can pull: bullseye 12.22.5–12.22.12, buster, stretch 4.8.4–12.5.0, and wheezy 0.10.45–8.2.0. 64 have only an image in Docker's retired v1 manifest format (0.8.28, 0.10.36–0.10.44, 0.12.0–0.12.13, 4.0.0–4.4.4, 5.0.0–5.11.0, 6.0.0–6.2.1). Docker Hub serves those whatever `Accept` asks for, and buildx 0.35 refuses `node:6.0.0-wheezy` with `support Docker Image manifest version 2, schema 1 has been removed`. The other 207 have no Debian-variant image.
- **Refusals by name:** `ResolveTag` (`dockerhub.go`) reports a v1-only tag as `errV1Manifest`, and the build fails at version selection with `NODE_VERSION=6.0.0 cannot be installed: Node 6.0.0's only official image, node:6.0.0-wheezy, is in Docker's retired v1 image format, which the builder cannot pull; …`. A release no image carries fails with `NODE_VERSION=0.8.6 cannot be installed: no official image node:0.8.6-bookworm (or its bullseye, buster, stretch or wheezy variant) exists; …`. Messages for releases from 14 on are unchanged.
- **On the common base** (`nativecommon.go`): the guard that checks a copied tree's Debian suite now reads stretch's `VERSION="9 (stretch)"`, because Debian 9.9 in `node:6.17.1-stretch` has no `VERSION_CODENAME`. It also reads wheezy's `/etc/os-release`, wheezy's only copy, and still refuses a tree from another suite. pnpm 10 needs Node 18.12, so every earlier release gets the standalone pnpm (`nativepnpm.go`). The legacy node-gyp Python patch stays on lines 14 and 16.
- **Does it run there?**
  - The amd64 node binary is the same nodejs.org build in every variant (12.18.3's is byte-identical in buster and stretch). Read with `readelf`, 12.x needs at most `GLIBC_2.17`, `GLIBCXX_3.4.18` and `CXXABI_1.3.5`. 8.x and 10.x need `GLIBC_2.9`, 4.x and 6.x `GLIBC_2.4`, and 0.10 and 0.12 `GLIBC_2.3.3`. Each links only libc, libm, libdl, librt, libpthread, libgcc_s and libstdc++, against the common base's glibc 2.36.
  - Builds run on linux/amd64, and every pullable image has an amd64 manifest. The wheezy images are amd64 only, so the arm64 mock cluster cannot build 0.10.45–8.2.0.
  - BuildKit pulled `node:0.10.45-wheezy`, `4.4.5-wheezy`, `5.12.0-wheezy`, `6.2.2-wheezy` and `12.18.3-buster` for amd64. The guard's shell accepted the real wheezy, early-stretch and jessie `os-release` files in Bookworm's dash.
  - On this arm64 host, `TestNativeImageRunsAnOptedInNodeBefore14` (opt-in, real registry, official-image path) built and ran 12.18.3 (buster), 10.15.3 (stretch) and 6.17.1 (early stretch). Each build printed its node, its npm (6.14.6, 6.4.1, 3.10.10), Yarn 1.22.22 and pnpm 10.34.9, and `npm install ms@2.1.3` worked. Each image then started on the same release.
  - Under QEMU's x86-64 user-mode emulation on this host, 19 amd64 trees were each copied over `/usr/local` of the amd64 common base's own root filesystem (`bex-cnb-run@sha256:49dbbd72…`, glibc 2.36), as `applyNativeCommonBase` does: 0.10.45, 0.10.48, 0.12.18, 4.4.5, 4.9.1, 5.12.0, 6.2.2, 6.17.1, 7.0.0, 7.10.1, 8.0.0, 8.17.0, 9.11.2, 10.24.1, 11.15.0, 12.5.0, 12.18.3, 12.22.12 and 13.14.0. Each printed its version. 18 served an HTTP, zlib and crypto probe, and 17 ran `npm install ms@2.1.3` from the registry. 12.5.0 aborted in libuv's start-up (`uv__close_nocheckstdio: Assertion fd > -1`), an emulator fault, since its arm64 build serves natively on Bookworm. 9.11.2's npm 5.6.0 failed the install with its own `Cannot read property 'length' of undefined`.
- **The companion:** the same resolver serves a Node service, a static site and another runtime's Node companion. So a stray `docs/package.json` with `12.x` now builds a Python service on Node 12.22.12, as on Render. w8/400's fallback is left for what no build can install: a line with no release, a release or range with no image, or a v1-only image.
- **Tests** (`nativenodelegacy_test.go`):
  - selection, and parity with `maxSatisfying` over an index fixture for 16 requests and three signals;
  - install on and off the common base from buster, bullseye, stretch and wheezy, with the guard and the standalone pnpm;
  - the guard run in `sh` against stretch, early-stretch and wheezy files, and two mislabeled ones;
  - the companion for all five runtimes, and the static site;
  - the v1 and no-image refusals with the Dockerfile untouched;
  - `ResolveTag`'s v1 detection, and the pnpm rule.
- **Mutation-checked:** restoring the floor, dropping the legacy variants, the guard change, the v1 refusal, the pnpm rule, the old LTS codenames, the old released lines, the resolver's v1 check or the 0.x line rule each fails its tests.
- **Older tests:** they asserted the floor, and now use requests that still refuse. w8/398's `12.22.12` and `<14` refusals became `27` and `<0.10`. w8/399's `<14` file refusal became `>=27`. w8/m77's `NODE_VERSION=12` fallback became `27`. w8/400's fallback cases became `>=27`, `~21.6.5`, `0.8.6`, a v1-only `6.0.0` and `99.99.99`. The rest of w8/370's, w8/371's, w8/372's, w8/398's, w8/399's and w8/400's tests pass unchanged, and so do `make test` and `make lint`.
- Recorded in ADR060 D7 ("Node releases before 14") and ADR018. The w8/398 and w8/400 bullets now point to it.
- **Effect on w8/400's parked live check:** on a pin carrying `cfb888fdab`, its `hack4impact-uiuc/communityconnect-labs` fixture (`frontend/package.json` `"node": "12.x"`) builds on Node 12.22.12 via `frontend/package.json`. It no longer gets the default with a warning, and its deploy should still go live.
