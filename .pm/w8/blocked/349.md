# `bex workspace set <unknown tea- id>` fails with "unexpected response: 403 Forbidden", where Render's retrieve-workspace answers 404

Why: Render documents `GET /v1/owners/{ownerId}` with errors `401, 404, 406, 410, 429, 500, 503` and no 403 (`docs/render-artifacts/owners-api.md`; the pinned CLI's fake Render API answers an unknown owner with 404, `internal/fakes/renderapi/server.go:522-531`). bex answers 403 `FORBIDDEN` for a workspace id that does not exist and for one the caller is not in. So the pinned CLI's `workspace set` prints a different status than on Render.

- Severity: minor. The exit status is non-zero either way, and bex leaks nothing: the unknown id and the foreign id get the same answer. The divergence is only the status code and the CLI line.
- Versions: bex CLI v0.7.0 (Render CLI pin `4fd34231b637`); production pin `12716d1d7097`.
- Context: 2026-11-20 09:46 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, no `BEX_WORKSPACE`. Routine `cli-qa` run `rt9-4ca8`.

## Repro

```text
$ bex workspace set tea-zzzzzzzzzzzzzzzzzzzz -o json      → rc 1 in 0.3 s, stderr "Error: unexpected response: 403 Forbidden"
GET /v1/owners/tea-zzzzzzzzzzzzzzzzzzzz                    → 403 {"code":"FORBIDDEN","error":"forbidden","id":"forbidden","message":"forbidden","params":null}
GET /v1/owners/usr-zzzzzzzzzzzzzzzzzzzz                    → 403 (same body)
```

The pinned client prints `unexpected response: <status>` for any non-200 (`pkg/owner/repo.go:46-57`), so on Render the same command reads `unexpected response: 404 Not Found`. The config is left unchanged in both cases (verified: `workspace: ""`).

## Fix

On REST `GET /v1/owners/{ownerId}`, answer 404 `not_found` for an id that is unknown or names a workspace the caller is not a member of. Both cases must keep one answer, so membership is never revealed.

Decide, and record in ADR006 next to the line 20 rule, whether the `X-Bex-Workspace` header keeps its 403. That rule covers a header-named workspace, not this path read. Keep GraphQL and MCP consistent with whatever is chosen. If 403 is kept on purpose instead, record the divergence in ADR018.

## Acceptance

- `bex workspace set tea-zzzzzzzzzzzzzzzzzzzz` exits 1 with `unexpected response: 404 Not Found`.
- A foreign workspace id gets the identical 404.
- The QA workspace id still sets.
- A backend test covers the unknown and non-member cases.

Render's spec lists 404 and no 403 for both retrieve-workspace and list-workspace-members (`lego/backend/internal/api/openapi/render-public-api-1.json`), so a workspace the caller is not in must get 404 too: an id that names no workspace and one the caller is not in now get one identical 404 `NOT_FOUND` (`workspace not found`).

- Surfaces: REST `GET /v1/owners/{ownerId}`, `/members`, `/limits`; GraphQL `workspace(id)`, `workspaceLimits(ownerId)` (`workspaces.Service.authorizeWorkspaceRead`).
- Kept 403: a member's 2FA or Google-login refusal and a narrowed token's insufficient scope, so neither depends on whether the workspace exists. Workspace selectors keep ADR006's 403 as well: `ownerId`, MCP `workspaceId` (which `get_workspace_limits` takes) and `X-Bex-Workspace`, a bex extension read only on name-addressed service paths. ADR006, ADR072's named exemptions and `owners-api.md` record this.
