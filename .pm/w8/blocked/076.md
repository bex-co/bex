Why: an 86-character description is refused by ordinary CLI updates and can strand cloning of an otherwise valid static site configured through the API.

**Status:** blocked. **Worker:** worker8. **Estimate:** 45m for a focused upstream patch and regression preparation; upstream acceptance, pin refresh and release are later prerequisites. **Severity:** minor. **Attribution:** upstream Render CLI, reproduced in published Bex and unmodified Render at the same pin. No product fix or external submission in this hunt.

## Reproduction and results

Create a fresh disposable Free static site through `services create`, then run this update against its returned ID:

```sh
qa_description="$(python3 -c 'print("雪" * 86, end="")')"
bex services update "$OWN_STATIC_ID" --ip-allow-list "cidr=0.0.0.0/0,description=$qa_description" --confirm -o json
```

The description has 86 Unicode code points and 258 UTF-8 bytes. Bex exits 1 in 0.096s with empty stdout and an error ending `description exceeds 255 characters`. Unmodified Render exits 1 in 0.033s with the same complete error. The saved service, including its prior description, remains unchanged. Exact expanded commands and full errors are in the artifact.

Both clients exercised all six cases below against the same owned source, with API readback after every command:

| Description | Code points / UTF-8 bytes | Both clients |
| --- | --- | --- |
| `x` repeated 255 times | 255 / 255 | Exit 0; exact description preserved |
| `雪` repeated 85 times | 85 / 255 | Exit 0; exact description preserved |
| `雪` repeated 86 times | 86 / 258 | Exit 1; saved service unchanged |
| `雪` repeated 255 times | 255 / 765 | Exit 1; saved service unchanged |
| `x` repeated 256 times | 256 / 256 | Exit 1; correct over-limit control |
| `QA,office=入口,description=kept` | 29 / 33 | Exit 0; commas, equals and Unicode preserved |

The literal description supplied to the first command is shorter than its advertised character limit. The refusal threshold instead follows its UTF-8 encoding. This is a character-counting defect, not a malformed CIDR or a punctuation parser failure.

For the clone case, an explicitly labeled **API-only diagnostic setup** sent `PATCH /v1/services/<own-source-id>` with `{"serviceDetails":{"ipAllowList":[{"cidrBlock":"0.0.0.0/0","description":"<86 copies of 雪>"}]}}`. It returned HTTP 200; a subsequent GET preserved all 86 code points exactly. The actual expanded body and complete response are durable evidence. This API setup is not a native CLI success claim.

Then, with no description flag supplied:

```sh
bex services create --from "$OWN_STATIC_NAME" --name "$FRESH_QA_NAME" --confirm -o json
```

Bex and unmodified Render both exit 1 with empty stdout and the same description-length error, in 2.081s and 2.413s respectively. Their exact fresh names remain absent from the subsequent service list. Restoring the source description to 85 copies through the same own-resource API setup makes ordinary cloning succeed in both clients: Bex clone `srv-db4ejvj93q6c73at02sg` and Render clone `srv-db4ek0b93q6c73at02ug`. Both reached Live, served their own HTML URLs with HTTP 200, and retained all 85 code points. Thus the failure also affects inherited configuration.

The offline probe invokes the actual pinned parser, rather than an imitation: ASCII 255 passes / 256 fails; `雪` 85 passes / 86, 255 and 256 fail; 63 emoji pass / 64 fail; punctuation control passes. A 64-emoji label is 64 code points but 256 bytes. With the two captured REST source bodies, the actual `ServiceFromAPI` → normalize/validate → request builder constructs the 85-character clone request and refuses the 86-character one. No network was used by this probe.

Live mutation wire was not intercepted for native CLI commands. The local validation boundary is proven by source and the actual offline builder; no claim of a captured zero-POST trace is made. API-only diagnostics include their exact method/path/body/status/response.

## Diagnosis and proposed fix

Pinned `pkg/types/ipallowlist.go:40–42` defines the limit as 255, tests `len(description)`, and reports characters. Go's string length counts bytes. `ParseIPAllowListEntry` is the common producer/validator and returns the complete description unchanged for accepted inputs.

Clone consumption is explicit: static details are read in `pkg/service/clone.go:202–207`; `formatIPAllowListEntries` at 309–317 encodes the description into the composite input; `applyIPAllowListDefaults` at 301–307 inherits it. `cmd/servicecreate.go:139–147` merges source configuration and validates it before constructing the request at 158–163. A valid description from the REST source therefore trips the same byte guard without any user-supplied description flag.

Prepare an upstream change in the one shared parser to count Unicode code points with `utf8.RuneCountInString(description)` for the stated 255-character limit. Keep ASCII behavior, CIDR parsing/normalization, punctuation preservation and the 256-code-point refusal. Do not truncate descriptions, strip them from Bex reads or fork/vend the CLI. If upstream establishes an intentional byte-based contract instead, document that constraint and correct the diagnostic to bytes; this hunt found no such declared API limit. The pinned `cidrBlockAndDescription.description` schema is a string with no `maxLength`.

Bex's producer is already faithful: `lego/backend/internal/apps/render.go:472–485` emits structured entries within `serviceDetails`; `apps/service.go:4581–4597` persists description metadata; `core/cidr.go` `ValidateAllowList` validates CIDRs and explicitly leaves descriptions as free text. The API acceptance above confirms that behavior for this owned static fixture. No server correction is proposed. REST/GraphQL/MCP/UI description semantics should stay unchanged.

## Shared consumers and acceptance

There are six direct production validator call sites in the pin's `pkg/types/{service,keyvalue,postgres}/{create,update}.go`, plus the loop in shared `ParseIPAllowList`. Five production callers feed that list parser: the service create helper, Key Value create/update and Postgres create/update. The service helper is consumed twice in create (web/static) and twice in update (web/static). Existing per-type applicability refusals remain in place. One production `ServiceFromAPI` caller supplies service cloning; both web and static descriptions can enter that path. Other resource types and the interactive paths were inspected in source only.

Acceptance for the upstream patch:

- Real shared-parser checks: 255 ASCII or Unicode code points pass; 256 fail; 64 emoji pass. Descriptions round-trip exactly, including commas, equals and IPv6 controls.
- Use the actual create/update validators and builders for all six command families above; include a static-source clone with the 86-character fixture. Preserve invalid CIDR and unsupported-resource-type guards.
- After upstream acceptance and a released Bex pin refresh, replay the native static update and ordinary clone above. The 86- and 255-character cases exit 0 and read back exact descriptions; a 256-character refusal exits 1 without changing saved metadata. Both successful clones reach Live and serve HTTP 200. A checkout-only test is insufficient for distribution closeout.
- Verify description producers still return exact Unicode in REST and the existing GraphQL/MCP/UI readers; only REST was live-probed here.

## Outcome (2026-10-09) — blocked on external submission

Prepared [`076-upstream.patch`](076-upstream.patch). The shared `ParseIPAllowListEntry` (`pkg/types/ipallowlist.go`) now counts with `utf8.RuneCountInString`, so the advertised limit of 255 _characters_ holds. The limit, CIDR parsing and normalization, punctuation handling and exact round-trip are unchanged. Because it is the single validator behind all six create/update families and the clone merge, one change covers every caller.

New upstream test `TestParseIPAllowListEntryDescriptionLength` covers:

- ASCII: 255 characters pass, 256 fail
- `雪`: 255 characters pass, 256 fail
- 64 emoji pass
- a description with commas, `=` and Unicode passes

The 255-`雪` and 64-emoji cases fail against the unmodified byte check. Every `pkg/...` suite passes, and `go vet` is clean. The base blob `d2346e9` is identical at the pin and at upstream main `c4d106cf` (2026-10-09).

The clone path was covered through the shared parser rather than a separate `ServiceFromAPI` case. The 86-character live replay runs after release.

Gate: the user must authorize external submission to render-oss/cli after a fresh dedupe. Upstream acceptance then needs a Bex pin refresh and a CLI release. No fork, per DO_NOT_DO.
