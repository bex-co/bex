## Objective

Render's sandbox build create now says its `name` "Can't start with `sbb-`, the prefix reserved for build IDs." `validateImageName` accepts such a name, so a later `buildName` lookup could collide with a build ID. Refuse it.

## Context

- `lego/backend/internal/sandbox/images.go:381-388` (`validateImageName`): 1–255 characters, no surrounding spaces, no control characters.
- Sandbox create resolves `buildId` (an `sbb-` ID) or `buildName` (`sandbox/rest.go:61-64`).

## Steps

1. Refuse a name with the prefix `sbb-` (case as Render's pattern, `^sbb-`) with the existing `CodeSandboxImageInvalid` 400 and a message naming the reserved prefix.
2. Keep names that merely contain `sbb-`.

## Files

- `lego/backend/internal/sandbox/images.go` and its test

## Acceptance criteria

- [x] `sbb-x` gives 400 naming the prefix.
- [x] `my-sbb-image` is accepted.
- [x] Run `go test ./internal/sandbox/...`.

## Out of scope

- Renaming existing builds whose names already start with `sbb-`. Count them first and record the number in the closeout.

## Done (2026-11-16)

- `validateImageName` refuses a name starting with `sbb-` (case as Render's text, `ids.SandboxBuild`'s prefix) with 400 `SANDBOX_IMAGE_INVALID`. The message is `name can't start with "sbb-", the prefix reserved for build IDs`. Render's 400 documents only a message, no code. REST, GraphQL and MCP import through the one `ImportImage` verb.
- `my-sbb-image`, `sbb`, `sbbx-image` and `SBB-image` are still accepted (`TestAnImageNameMayNotStartWithTheBuildIDPrefix`). The real-DB import table also refuses `sbb-anything`.
- The count of existing builds whose names start with `sbb-` needs production data, so t008 makes it.
