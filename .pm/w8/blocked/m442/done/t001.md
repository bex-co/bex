## Objective

Render's 2026-11-16 spec adds the query parameter `build` (an array of build IDs, "such as a service build or a sandbox image build") to `/logs`, `/logs/subscribe` and `/logs/values`, and the value `build` to the log label names. bex refuses the parameter with 400. Accept it, filter on it, and label build lines with their build ID.

## Context

- **Production today (pin `7aaa8700befa`):**
  - `GET /v1/logs?…&build=<id>` → 400 `unsupported query parameter "build" for list-logs` (the strict Render request gate).
  - `/logs/values?label=build` → 400 `label must be one of instance|host|statusCode|method|level|type`.
- `lego/backend/internal/logs/` (`service.go` `LogTypeBuild = "build"`, `loki.go` build streams `type="build"`, w7/m28 and w8/m159). Sandbox image builds are `sbb-` (`internal/id/id.go:134-136`).
- The parameter's schema is an array, like `resource` and `instance`: repeated query values, OR within the filter, AND with the others.

## Steps

1. Decide the ID a service build's lines carry: the deploy's build, `dep-`, or a new build ID. Record it in ADR018 as bex's choice (unverified against Render).
2. Accept `build` on all three routes once the pin includes it (t004), and route it the way `--instance` and the other structured filters are routed (history, tail and values).
3. Emit a `build` label on build lines and sandbox image-build lines.
4. Answer an unknown build with an empty page, not 404, as other filters do.

## Done (2026-11-16)

- `GET /v1/logs`, `/logs/subscribe` and `/logs/values` take `build` (REST `parseLogParams`), and so do GraphQL `logs`/`logLabelValues` and MCP `list_logs`/`list_log_label_values`. Every surface goes through `LogQuery.Build` (`internal/logs/build_filter.go`).
- **The build ID choice (step 1):** a service build's ID is its deploy's `dep-` id. pipeline_minutes_exhausted's `buildId` already carries it (w9/m345), and so does a deploy's platform-line instance. It is recorded in ADR018 (round 8 and the Build logs row) as bex's choice until Render's value is observed.
- **Labels.** A build Job's pod line carries the deploy that ran its generation (`buildIndex`, from the deploy rows; a shared generation goes to the row that built). A platform line carries its own deploy (`progressEntry`). The live build tail labels each attached pod's lines. A kpack pod and a pre-deploy step carry none. bex's sandbox image builds write no log lines, so no line carries an `sbb-` build.
- **Filter.** OR within, AND with the rest. Only build lines carry a build, so the filter narrows a read to `type=build`. Beside types that read none, history and values answer empty and a live tail answers 400. The store selector gets a positive `pod=~"^(<jobs>)-[^-]+$"` matcher, and an unknown build gets a matcher that selects no pod, so the answer is an empty page. A datastore refuses the filter as it refuses `type`. A filter whose deploy rows cannot be read answers the error.
- **Deviation:** `/logs/values?label=build` does not list build IDs. Render's live spec kept `list-logs-values`' `label` enum at `instance|host|statusCode|method|level|type`, so `label=build` stays Render's 400 (`TestRenderRequestValidatorAdmitsTheLogsBuildFilter`). The values route takes `build` as a filter instead. The README's definition of done is amended to match.
- Tests: `internal/logs/build_filter_test.go`. `go test ./internal/logs/` passes.
