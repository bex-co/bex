## Reproduction and observable failure

A fresh explicit Free PostgreSQL18, custom harmless database/user names, no replicas or pooler, is created through native Bex0. Both clients connect normally to actual18.6. Bex selects the recorded ID; Render resolves the unique owned name. Each executes the unchanged command below with isolated QA credentials/configuration and supported psql passthrough flags:

```sh
bex psql "$OWN_PG_ID" --command 'CREATE EXTENSION IF NOT EXISTS pg_duckdb;' --confirm -o json -- -X -q -t -A -v ON_ERROR_STOP=1
render psql "$OWN_PG_NAME" --command 'CREATE EXTENSION IF NOT EXISTS pg_duckdb;' --confirm -o json -- -X -q -t -A -v ON_ERROR_STOP=1
```

Both exit1 with empty stdout and PostgreSQL's extension-not-available error. Its hint says the extension needs installation on the server. Four identical before/after catalogs contain no pg_duckdb entry. No serving filesystem inspection is claimed. The command succeeds only when a usable extension package and required managed configuration are provided; [Render's documented extension list](https://render.com/docs/postgresql-extensions) includes pg_duckdb for PostgreSQL16 and later.

Two normal native aggregate controls independently create five own rows, including café:李 and a negative integer amount, then return exact grouped count/totals: café:李2/1500, north2/1975, west1/0. Python independently derives the expected totals. Entire transactions roll back; catalogs show own schema absence, preserved vector0.8.6, pg_stat_statements1.12 and plpgsql1.0, with hstore still available/uninstalled. This isolates a missing capability from a general SQL/connectivity failure. Native wire was not intercepted; complete native commands/stdout/stderr/exit and API-only lifecycle diagnostics are retained separately.
