# A Bun service created since 2026-11-20 with only a lockfile builds on Bun 1.4.4, but Render's default for it is 1.4.5

Why: Render's Bun default is dated by service creation, like Node's, Python's and Ruby's, and moved to 1.4.5 for services created on or after 2026-11-20. bex has no dated Bun defaults: a lockfile-only service always gets the 1.4 line's reviewed patch, so a new Bun app runs a different Bun than on Render.

- Severity: minor. The app builds and serves, but on the previous patch.
- Versions: bex CLI v0.9.0 release binary; Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md`; production pin `f797f525f5df` (the fixture built at 09:05 UTC, before the `cce6c749f6ff` roll). The code is unchanged on main `61bf9154e0`.
- Context: 2026-11-21 08:59–09:09 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY. Routine `cli-qa`, run r23, nonce `8555`.

## Render

[render.com/docs/bun-version](https://render.com/docs/bun-version), read 2026-11-21. It lists `BUN_VERSION`, then `.bun-version`, in descending precedence. Including "a `bun.lock` or `bun.lockb` file in your service's root directory" opts a service into Bun on the default version. Its dated defaults table ("Service Creation Date | Default Bun Version"):

| Created | Default |
| --- | --- |
| `2026-11-20` and later | `1.4.5` |
| `2026-10-22` to `2026-11-20` | `1.4.4` |
| `2026-10-12` to `2026-10-22` | `1.4.3` |
| `2026-09-09` to `2026-10-12` | `1.4.2` |
| `2026-07-16` to `2026-09-09` | `1.3.14` |
| `2025-12-08` to `2026-07-16` | `1.3.4` |
| `2025-08-18` to `2025-12-08` | `1.2.20` |
| Before `2025-08-18` | `1.1.0` |

[render.com/docs/language-support](https://render.com/docs/language-support) also gives Bun `1.4.5`. Bun 1.4.5 was released 2026-11-19 (`gh api repos/oven-sh/bun/releases`: `bun-v1.4.5 2026-11-19T08:47:28Z`).

The repo has `bun.lock` and no `BUN_VERSION` or `.bun-version`. The service `srv-dc0lqqt26tvc739p1dn0` was created `2026-11-21T08:59:23Z`. Build log:

2026-11-21 09:06:18  QA_BUILD_BUN 1.4.4

## Cause

- `lego/operator/internal/build/native.go:238` `nativeBun` pins the 1.4 line at `1.4.4` (`oven/bun:1.4@sha256:1d22548f…`, the same digest as `oven/bun:1.4.4`).
- `lego/operator/internal/build/nativeversion.go:380` `ResolveNativeBun` takes no creation time. For a lockfile signal, `exactRequest` finds no requested version, so `Exact` stays empty and the build uses the line's reviewed patch. `exactDefaults` (`nativeversion.go:265`) has steps for Node, Elixir, Ruby and Python but none for Bun.
- The caller, `resolveNativeBunExact` (`nativeresolve.go:453`), is reached from `ResolveNativeBuildExact`, which already has `created` (`nativeresolve.go:65`). That is the same path w8/370 used to date the companion Node.
- w8/198 kept Bun on Render's default by bumping the line's patch (1.4.3 → 1.4.4). That moves every existing service. Render keeps 1.4.4 for services created from 2026-10-22 to 2026-11-20.

## Fix

- Give Bun dated default steps, as w9/138 did for Ruby (`61bf9154e0`): at least `{2026-10-22, 1.4.4}` and `{2026-11-20, 1.4.5}`, plus earlier rows where a line exists.
- Pass `created` into `ResolveNativeBun`. When the signal is only a lockfile, set `Exact` to the dated default when it differs from the line's patch, so `pinExactVersion` swaps in `oven/bun:1.4.5` pinned by digest. If the tag is missing or the registry is unreachable, the existing fallback keeps the reviewed patch and says so.
- Name the exact version in the log line (`==> Using Bun 1.4.5 (default, from bun.lock)` or equivalent), not only `1.4`.
- `BUN_VERSION`, `.bun-version`, `latest` and `canary` are unchanged.
- A service created before 2026-10-22 has no Render-matching row unless its line exists. Rows outside the reviewed lines (1.1.0, 1.2.20) depend on w8/372.

## Fix (2026-11-21, `cc2f43c6d`)

- `bunDefaults` (`lego/operator/internal/build/nativeversion.go`) holds Render's whole dated table from [render.com/docs/bun-version](https://render.com/docs/bun-version), read again on 2026-11-21. Every row from 2025-08-18 on (1.2.20, 1.3.4, 1.3.14, 1.4.2, 1.4.3, 1.4.4 and 1.4.5) falls on a reviewed line. Every one of those tags exists as `oven/bun:<version>` (Docker Hub tag API 200).
- `ResolveNativeBun` now takes the creation time, and `ResolveNativeBuildExact` passes it. When the only signal is a lockfile, `datedBunDefault` moves the choice onto that release's line and sets `Exact` when the release differs from the line's reviewed patch, so `pinExactVersion` copies `oven/bun:1.4.5` pinned by digest. A missing tag or an unreachable registry keeps the reviewed patch and says so.
- A service of unknown age keeps the 1.4 line's reviewed patch. So does one created before 2025-08-18, whose Render default (1.1.0) is on no reviewed line yet (w8/372).
- `BUN_VERSION`, `.bun-version`, `latest` and `canary` are unchanged.
- The Bun log line now names the exact release: `==> Using Bun 1.4.5 (from bun.lock)`, and `==> Using Bun 1.3.14 (from BUN_VERSION=1.3)` for a line request.
- Tests: `TestResolveNativeBunDatedDefault` covers both sides of the 2026-11-20 step, each earlier row, the pre-2025-08-18 fallback, unknown age, an explicit `BUN_VERSION=1.4.4`, a `.bun-version` line, `latest` and `canary`. `TestResolveNativeBuildPinsTheDatedDefaultBun` covers the pinned `oven/bun:1.4.5`, its log line, the `COPY`, and the missing-tag fallback. Both fail with the fix disabled. `make test` and `make lint` pass.
- ADR060's runtime table Bun row and ADR018 name the dated defaults.
