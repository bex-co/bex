# A Node version on an odd line (`.nvmrc` `25.8.1`) fails the build as "not a supported Node version", and a range that reaches one (`>=20 <22`) builds on 20.20.2 where Render installs 21.7.3

Why: Render resolves every Node version signal through `node-version-alias`, which picks the newest Node release of any line that matches (`semver.maxSatisfying` over all of nodejs.org's releases). bex knows only the even lines 14–26. An app pinned to Node 15, 17, 19, 21, 23 or 25 builds on Render and fails at version selection on bex, and a range that reaches an odd line silently builds on the even line below it. bex's own ADR060 already says Render "builds on any released version" of Node.

- Severity: major. A Render-valid service cannot build at all when its version file names an odd line. The silent downgrade from a range is minor on its own.
- Versions: bex CLI v0.9.0 release binary, pinned Render CLI v2.36.0 (`4fd34231b637`), production pin `89642635b9ce`. The code is unchanged on main `554bbb0799`.
- Context: 2026-11-22 11:38–11:43 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY. Routine `cli-qa`, run r30, nonce `7c3e`.

## Render

- [render.com/docs/node-version](https://render.com/docs/node-version), read 2026-11-22. It lists, "in descending order of precedence", `NODE_VERSION`, `.node-version`, `.nvmrc` and `package.json` `engines`. It also says:
  - "You can specify either a semantic version number (such as `18.18.0`) or an alias (such as `lts`)."
  - "Render uses the `node-version-alias` module to resolve version aliases and semver ranges."
  - The page names no supported-line list and no minimum.
- `node-version-alias` (`src/main.js`) passes any value that is not an alias to `normalize-node-version`. That module (`src/main.js:6-9`) loads every release with `all-node-versions` and returns `semver.maxSatisfying(versions, versionRange)`. So:
  - `25.8.1` resolves to 25.8.1;
  - `25` and `v25` resolve to 25.9.0;
  - `>=20 <22` resolves to 21.7.3, and `>=24 <26` to 25.9.0.
- Each of these releases is in `nodejs.org/dist/index.json`: 21.7.3 (2024-04-10), 23.11.1, 25.8.1 (2026-03-10) and 25.9.0 (2026-03-31). Docker Hub has `node:21-bookworm` and `node:25-bookworm` (both tags answer 200).

## Root cause

- **The line table holds only even lines.** `lego/operator/internal/build/native.go:201-209` reviews 14, 16, 18, 20, 22, 24 and 26.
- **A plain version must name a line.** `nodeRequest` (`lego/operator/internal/build/nativeversion.go:780-799`) maps a plain version to its major (`:793-796`) and fails when `r.t.find(major)` has no line. `fromFile` and `fromEnv` then return `UnsupportedVersionError`.
- **A range picks from the lines, not from releases.** `highestSatisfying` (`:806-826`) checks only each line's pinned version, newest line first, so `>=20 <22` stops at 20.20.2. w8/307's `excludedNodeRange` and `pinRangeRelease` move a range only within the chosen line.
- w8/173 added lines for "every major … that Render's documented ranges and default tables reach", and those are all even. w8/372 and w8/373 fixed the same refusal for Bun and Elixir by installing any release no line carries.

## Fix

- **Resolve the request the way `node-version-alias` does.** For a plain version, partial version or range, take the newest release in nodejs.org's index that satisfies it. ADR060's freshness check already reads that index. Aliases (`lts`, `lts/<codename>`, `node`, `latest`) keep their current mapping.
- **Build that release:**
  - If a reviewed line carries its major, use the line, as an exact version through w8/175's path when the patch differs.
  - Otherwise, either add reviewed odd lines (19, 21, 23 and 25 have official `-bookworm` images) or install the exact release from its official image or tarball, as w8/372 does for Bun. Pick the cheaper option and record it in ADR060 D7.
- **Refuse only what nodejs.org does not have,** with the existing named error (for example `99.99.99`).
- **Narrate the version installed:** `==> Using Node.js version 21.7.3 via environment variable NODE_VERSION`.
- **Same resolver everywhere:** the Node companion of Python, Ruby, Go, Rust and Elixir services, and static sites. Count those callers in the fix.

## Fix (2026-11-22, `5cb35808e7`)

- Cause confirmed on main `bef828ae3b`: `nodeRequest` mapped a plain version to its major and refused it with no reviewed line, and `highestSatisfying` matched ranges against the even lines' pins only.
- Render's target, read again 2026-11-22: [render.com/docs/node-version](https://render.com/docs/node-version) says "Render uses the `node-version-alias` module to resolve version aliases and semver ranges", and names no line list or minimum. nodejs.org/dist/index.json (fetched 2026-11-22) gives each odd line's final release: 15.14.0, 17.9.1, 19.9.0, 21.7.3, 23.11.1 and 25.9.0. Its newest stable release is 26.13.1, and `27.0.0-alpha` builds are prereleases, which `maxSatisfying` skips.
- Choice recorded in ADR060 D7: no reviewed odd lines. Every odd line is past its end of life, so a line would only pin a frozen release. Each release installs from its own official image instead, as w8/372 does for Bun. Docker Hub (checked 2026-11-22) has `node:25.8.1-bookworm`, `25.9.0-bookworm`, `21.7.3-bookworm`, `21.6.2-bookworm` and `23.11.1-bookworm`. 19.9.0 and 17.9.1 have no `-bookworm` image (their `-bullseye` answers 200), and 15.14.0 has neither (its `-buster` answers 200). `99.99.99-bookworm` answers 404.
- Now (`lego/operator/internal/build`):
  - A fully qualified version from Node 14 on that no reviewed line carries is installed as itself (`nativeNodeAnyRelease`).
  - Partial versions and ranges resolve against the reviewed pins and the odd lines' finals (`nodeOddLines`, `rangeLines`): `v25` → 25.9.0, `>=20 <22` → 21.7.3, `>=24 <26` → 25.9.0. `>=20` (26.13.1), `^22` (22.23.5) and `>=20 <23` (22) are unchanged.
  - When an odd final misses the request (`25.8`, `~21.6.0`), the resolve phase lists that line's tags and takes the newest release inside it, bookworm first.
  - `pinNodeRelease` pins `node:<release>-bookworm` by digest, or the `-bullseye`/`-buster` image through w8/309's donor path. Node 15 and 17 get the standalone pnpm.
  - A release with no image fails at version selection by name: `NODE_VERSION=99.99.99 is not a Node release: no official image node:99.99.99-bookworm (or its bullseye or buster variant) exists; …`. A range no release meets fails with `… matches no Node release …`. An unreadable registry is a platform error. Versions before 14 are refused as before.
  - The log reads `==> Using Node.js version 25.8.1 via /opt/render/project/src/.nvmrc`.
- Callers: the primary Node service and the static site (`ResolveNativeBuildExact` → `pinNativePrimary`), and the Node companion of Python, Ruby, Go, Rust and Elixir (`resolveNativeCompanion`). The companion now pins before the legacy-pnpm decision on the common base too, so an exact 18.x before 18.12 companion there also gets the standalone pnpm.
- Tests (`nativenoderelease_test.go`):
  - `TestNodeBuildInstallsTheReleaseNodeVersionAliasResolves` checks 17 requests against `maxSatisfying` over an index fixture, through `NODE_VERSION`, `.nvmrc` and `engines.node`.
  - Selection table and refusals; the odd-line table invariants.
  - Install on and off the common base, including the bullseye and buster donors with the legacy pnpm, the companion for all five runtimes, and the static site.
  - Refusal by name with the Dockerfile untouched, and the registry-down platform error.
- Mutation-checked: dropping the odd lines, the exact-release branch, the strict pin, the 15/17 pnpm, or the companion pin each fails its tests. `make test` and `make lint` pass. ADR060 (Node row, D7 amendment) and ADR018 record it.
- Residual, not fixed: an OR range whose highest line matches only an older release while a lower line's newest matches (`^20 || ~22.11.0`) still takes the lower line. This is the existing two-pass `highestSatisfying`. A single pass would trust `lineHasRelease`'s probe of patch numbers that may not exist. Node 15 and 17 get no legacy node-gyp Python patch, which is unmeasured for their npm.
