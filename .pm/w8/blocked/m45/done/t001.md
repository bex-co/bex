## Objective

Pick the mechanism and record it in this milestone and in the ADR that owns workspace targeting (ADR043/ADR006):
- (a) the launcher sends the selected workspace as an explicit bex header that the server honors only for name resolution (a bex-native, documented addition, like `X-Bex-CLI-Version` in `lego/cli/internal/bridge/transport.go`), or
- (b) server-only: names resolve only when unambiguous across the caller's workspaces, otherwise 409, or
- both.

Weigh upstream-contract purity (the skill forbids teaching the launcher workarounds for server gaps) against correctness for single-name-many-workspace users.

## Acceptance criteria

- [ ] The decision is recorded with its trade-offs, and the user signs off if it adds a launcher header.

## Outcome (2026-09-26) — done (decision recorded; the launcher half awaits sign-off)

**Decision: both, landed in two steps.**

- **(b) server refusal: shipped now.** It needs no contract change and removes the silent wrong-target mutation by itself. It holds for every client: the pinned CLI, raw REST, GraphQL and MCP.
- **(a) launcher header: proposed, not built.** It needs the user's sign-off (this task's criterion, and the skill rule against teaching the launcher around server gaps). Shape: the launcher sends the selected workspace (`BEX_WORKSPACE` / `bex workspace set`) as a documented bex header, like `X-Bex-CLI-Version` (`lego/cli/internal/bridge/transport.go`). The server treats it as the named workspace for **name resolution only**, so `bex restart web` with A selected resolves A's `web` instead of 409. Trade-off: an upstream-contract addition the pinned client never sends vs. convenience for users with the same name in several workspaces. Without it, those users get a 409 with the ids, which is safe but less convenient.
