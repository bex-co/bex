# Runtime port detection never runs: every App carries `spec.port: 10000`, and `detectBoundPort` treats any `spec.port` as an explicit port (root cause of w4/393)

Why: Render's web-service docs say "If you bind your HTTP server to a different port, Render is usually able to detect and use it". w8/177 shipped that detection, and w4/393 made scan failures visible. On production, though, a native web service that binds its own port still waits on 10000 for the full 15 minutes, and its failure reason never mentions detection. Render's own `render-examples/hapi-quick-start` (hard-coded port 3000) answers 200 at `https://hapijs.onrender.com/` but never goes live on bex.

Severity: **major** (an official Render quick start never serves; the only workaround is to set `PORT` to a port the user has to discover). Attribution: platform runtime (operator) plus the API's create default. Estimate: ~50m. Source: `/qa-find-bugs-cli` loop sweep d580, 2026-10-26 (07:51–08:20 UTC). Context: HEAD-built bex `bb8ea5ac3` with pinned Render CLI v2.27.0 `a764810a7682`; platform pin `2331a3dad`, which contains w8/177 `090634e6c` and w4/393 `4c36bd37f`; `https://api.bex.co/v1/`; workspace `bex-canary`; human device login.

Port 3000 is first in `commonHTTPPorts`. A scan that ran would have appended "The process is listening on port 3000…". A scan that failed would have appended w4/393's "Port detection could not reach the instance…". Neither appears in the stall or failure text, so `detectBoundPort` returned before scanning. The fixture was deleted by ID afterwards (`services delete` 0 → `GET` 404).

## Root cause

- `lego/operator/internal/controller/port_detect.go:83` (line numbers at HEAD `bb8ea5ac3`) returns `""` when `app.Spec.Port > 0`. `detectedServingPort` (`:69`) applies the same test, so a detection could never be applied either.
- Every real App has `spec.port > 0`:
  - `normalizeCreateDefaults` (`lego/backend/internal/apps/service.go:3244`) writes `port = appv1alpha1.DefaultPort` (10000) when the request omits one. It is stored at `:3067`.
  - The CRD declares `+kubebuilder:default=10000` (`lego/types/v1alpha1/app_types.go:626`), so the API server defaults even a hand-applied CR.
- `port_detect_test.go` builds in-memory Apps with `Port: 0`, a state that never exists in the cluster, and its "an explicit port" case uses 3000. Nothing exercises a defaulted 10000.
- This is not one of w4/393's three candidate causes (NetworkPolicy resync, Cilium, pod eligibility). The scan never starts.

## Fix

- Render has no service `port` field; only `PORT` overrides detection there. So treat `spec.port == appv1alpha1.DefaultPort` as "not configured" in both guards (`detectBoundPort` and `detectedServingPort`). Keep these as overrides: any other explicit `spec.port`, `status.envPort` (a `PORT` variable), and image ports.
- Detection only runs while 10000 itself fails its check, so a process that does bind 10000 is never touched.
- Pre-w8/168 Apps that stored the old CRD default 3000 keep it (they already serve there).
- Tests:
  - an App with `Port: DefaultPort` and one other answering port gets `status.detectedPort` after two scans, and the stall/failure text names it;
  - `Port: 10000` plus `PORT=10000` and `Port: 8080` stay undetected;
  - the old `Port: 0` cases keep passing.
- Update ADR018 rows 104 and "PORT env var" and the w8/177 note: detection now applies to the default port.

## Blast radius

- Every web service created without `--port`/`PORT`: all native runtimes, and Git-built Docker web services that don't qualify for image ports.
- Image web services with a declared port use w4/m243's image-port path, which this guard doesn't affect.
- Private services and workers are excluded by the type check, unchanged.
- REST/GraphQL/MCP already project `port`/`openPorts` from `App.ServingPort`, so they report the detected port with no API change. The dashboard has no change.

## Acceptance (live, after the operator deploys)

- Recreate the hapi fixture above (Render's commands, no `PORT`). Within ~2 minutes of the container starting, the deploy goes `live`, and `GET /` returns `Hello, world!`.
- The deploy/stall text names port 3000. `GET /v1/services/{id}` reports `serviceDetails.port: 3000` (or `openPorts` 3000).
- Control: a service with `--env-var PORT=10000` whose process binds 3000 still fails on 10000.
- Re-run w4/393's two fixtures (nginx, `python -u -m http.server 8000`) and close w4/393 with them.
- Delete fixtures by ID with 404 proofs.

## Unverified

- Whether the scan then reaches the pod. The NetworkPolicy/Cilium path from w4/393 is still untested on production, because the guard always stopped the scan before it started. If it can't reach the pod, the w4/393 text appears instead of a detection, and w4/393's diagnosis resumes from there.

## Dedupe

- `rg -i 'detectBoundPort|Spec.Port > 0|port detection' .pm`: w8/177 (done; shipped the guard) and w4/393 (blocked; same symptom, cause unknown, cluster access requested). This note supplies that root cause. w4/393 is cross-linked and keeps its live acceptance.
- No open item names the default-port guard. Not in `.pm/DO_NOT_DO.md`, and no ADR018 divergence. The fix isn't on main: HEAD `bb8ea5ac3` still has the guard.

## Corroboration (live `/qa-find-bugs w4` loop run 8a59, 2026-10-27 UTC, pin `b4726243e74f`)

Still reproduces on the newer pin, which carries the w4/393 diagnostics (`4c36bd37f`). A Free image web service `ghcr.io/stefanprodan/podinfo:6.7.0` (`srv-dbg26k5n83uc738uua00`, no port, no `PORT`; the image's OCI config declares **no** `ExposedPorts` and podinfo listens on 9898) stayed `update_in_progress` for the full window and ended `update_failed` at 15 min. Neither detection sentence appeared in the stall or failure text (no "The process is listening on port N", no "Port detection could not reach the instance…"), consistent with the early return. The URL answered the first-deploy 503 throughout. The fixture was deleted (`GET` → 404).

Adjacent copy defect seen in the same failure: `failureReason` says "Nothing accepted a TCP connection on port 10000, **the primary port selected from the image's declared TCP ports (10000)**", but the image declares no ports; 10000 is the platform default fallback. When `ExposedPorts` is empty the sentence should say so, e.g. "port 10000, the default because the image declares no ports", so the user isn't told their image declared 10000.
