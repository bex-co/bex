# A redeploy whose health-check path never answers fails at 18 minutes with "so the rollout is waiting", and its new instance keeps running after the failure

Why: Render gives a failing health check 15 minutes, then cancels the deploy and keeps only the existing instances. On bex a path that never answers (as opposed to one that returns 500) misses the operator's 15-minute verdict: the row is closed 3 minutes later by bex-api's fallback gate, the failure reads as if the rollout were still waiting, and the failed release's instance stays up next to the live one.

- Severity: major. The old release keeps serving throughout (good), but the deploy outcome is late, its reason contradicts its status, and an instance of a release that failed keeps running, which on a paid plan is a second billed instance.
- Versions: bex CLI v0.7.0 (Render CLI pin `4fd34231b637`); production `https://api.bex.co/v1/` on 2026-11-20 13:13–13:37 UTC; deployed revision not read.
- Context: routine `cli-qa` run `rt13-5f51`, QA human device-flow login, isolated config, workspace `bex-canary`. Two free image web services from `docker.io/library/python:3.12-alpine` with a `dockerCommand` that serves `GET /ok` → 200, `GET /bad` → 500 and `GET /hang` → never answers (sleeps 3600 s), and prints its `RENDER_INSTANCE_ID` on `/`. Both run-owned and deleted afterwards.

## Repro

```text
# both services live, then a healthy health check:
bex services update <srv> --health-check-path /ok                 → rc 0
bex deploys create <srv> --wait --confirm -o json                 → rc 0 in 41 s, live (both services)

# A (control): a path that answers 500
bex services update <srvA> --health-check-path /bad; bex deploys create <srvA> --confirm   (13:16:09)
  → update_failed at 13:31:13 (15 min 3 s), failureReason "… startup health check never succeeded within the rollout window, so the deploy failed: GET /bad on port 10000 …"
  → the URL served the old instance throughout; afterwards `bex services instances` lists only the old instance

# B: a path that never answers
bex services update <srvB> --health-check-path /hang; bex deploys create <srvB> --confirm  (13:16:09)
  → stays update_in_progress past 15 min; `bex services instances` shows a NEW instance created at 13:31:19 (the 15-minute mark)
  → update_failed at 13:34:11 (18 min 2 s), failureReason "the container is running but its startup health check has not succeeded, so the rollout is waiting: GET /hang on port 10000. Check that the path returns a 2xx or 3xx status on the service's own port."
  → the deploy_ended event carries the same waiting wording
  → the URL served the old instance throughout (every 20 s poll, 13:16–13:37)
  → at 13:36:52, 2 min 41 s after the failure, `bex services instances` still lists the old instance AND the 13:31:19 instance; `numInstances` is 1
```

Clearing the path restores normal deploys: `bex services update <srvA> --health-check-path ""` then `bex deploys create <srvA> --wait --confirm` → live in 34 s.

## What the code says

- `lego/backend/internal/store/reconciler.go:99-123`: bex-api's `defaultDeployGateTimeout` is 18 minutes, a fallback that is meant to fire only when the operator has not reported `ProgressDeadlineExceeded` at 15 minutes. B's 18 min 2 s close is that fallback, so the operator never settled B's rollout.
- `reconciler.go:1213-1236`: on that close the reason comes from `currentFailureReason(cur)` (the App's current Ready message, still the in-flight stall text) before the `TerminalStallText` restatement that w8/219 added, so the waiting wording survives into `failureReason` and the `deploy_ended` event.
- `lego/operator/internal/controller/app_controller.go:4142-4200` (`progressDeadlineExceeded`, `scaledUpPastDeadline`) only settles on Kubernetes' `Progressing=False ProgressDeadlineExceeded`. The new instance at the 15-minute mark suggests the pod was replaced then: a startup-probe kill, a w7/m81 liveness restart, or the deadline handling itself. The replacement would reset or suppress the Deployment's progress deadline, and the operator then never reaches its own verdict. **Unverified:** the production kubeconfig was not available to this run (`scripts/fetch-app-kubeconfig.sh` needs `HCLOUD_TOKEN`), so the Deployment's conditions and the probe spec were not read.

## Fix

1. Reproduce on the local cluster (`scripts/mock-cluster.sh`) with a readiness/startup path that never answers. Read the Deployment's `Progressing` condition, the pod events and the probe spec at the 15-minute mark to find what created the second pod and why no `ProgressDeadlineExceeded` verdict reached `settleFailedRollout`.
2. Make the operator fail a never-answering health check at the same 15-minute budget as an answering one, and tear the failed release's instances down as it does for the 500 case. A probe timeout must count against the budget exactly like a non-2xx answer.
3. In bex-api's fallback close, restate the in-flight stall text with `TerminalStallText` on every `update_failed` path, including `currentFailureReason`, so no failed row or `deploy_ended` event says "so the rollout is waiting".

## Acceptance

- On a free fixture whose health path never answers, a redeploy ends `update_failed` 15 minutes (± 30 s) after it started, with a `failureReason` containing "never succeeded within the rollout window, so the deploy failed" and no "so the rollout is waiting".
- Within 60 s of the failure, `bex services instances <srv>` lists only the live release's instance, and the URL served that instance throughout.
- The 500-path control still fails at 15 minutes with the same wording, and clearing the path still deploys live.
- Operator and backend tests cover a probe that times out and the fallback close's wording.

## Worker findings (2026-11-20, `/loopx w8`)

- **Not deterministic.** Six replays on the same production pin (`12716d1d7097`) in `bex-canary` all settled at 15 minutes: two runs of two never-answering fixtures (the r13 threaded server, `/hang`) plus a `/bad` control, deployed together, once with no traffic and once polling each URL every 5 s. Every deploy ended `update_failed` 15m03s–15m14s after it started, with "never succeeded within the rollout window, so the deploy failed: GET /hang on port 10000 …". With traffic, only the live instance was listed within 10 s, `phase` read Running and the URL kept answering. With no traffic, the services parked after the verdict. All fixtures deleted (GET 404).
- **A timed-out check is not special to the operator.** `health-probe check` exits 1 for a timeout and for a non-2xx answer alike, and the kubelet counts both against the startup budget. The operator reads neither probe output nor events. Its only network contact with the pod is the port scan, and the r13 server is threaded, so port 10000 stayed open.
- **What B's evidence fits:** the settle at the deadline put the served template back, which scaled the failed release's pod away. Its verdict write was then lost: `updateStatusRetrying` logs and returns, and the settle reported success. The next pass found no verdict, a Deployment on the served release and a ready old pod, so it chose `actRoll` and rolled the failed release again. That gave a new pod (13:31:19), a fresh 15-minute Kubernetes clock, the in-flight stall on Ready, and bex-api's 18-minute gate. Production runs two App workers, and A and B hit their deadlines in the same second. Unverified on the cluster: no production kubeconfig (`HCLOUD_TOKEN` absent), and the local cluster cannot boot (inotify 128).
- **Fixed in `5c9b1f99d`.** The operator stores the verdict before it restores the served template. If that write fails, the settle returns the error and leaves the Deployment on its `ProgressDeadlineExceeded`, so the next pass settles again (`TestRolloutDeadlineStoresItsVerdictBeforeRestoringTheServedRelease`, which fails on the old order). bex-api's gate close restates the current Ready diagnosis with `TerminalStallText` (`TestGateCloseOfAnUnsettledProbeStallReadsAsFailed`; the image-pull case in `02e630b86`). The operator `make test` and the real-DB backend suite pass.

Then delete the fixtures and close. The race itself cannot be replayed on demand (0 of 6); the unit test covers it.
