# The default Postgres user cannot `CREATE USER`, which Render's credentials page implies it can

Why: Render's credentials page says "Users created directly with the `CREATE USER` command are _not_ managed by Render", which only makes sense if the statement works for the database's user. On bex it answers `permission denied to create role`. w8/m155 gave the default users `CREATEDB` and deliberately left `CREATEROLE` out, because it is not safe on every PostgreSQL version bex serves. Someone has to decide the rule.

**Severity:** minor (parity; the dashboard and API still add credentials and users). **Attribution:** infrastructure (the operator's CloudNativePG role projection) plus a decision. **Estimate:** ~60m once decided. **Source:** found while working w8/m155 t001, 2026-11-11.

## Evidence

- Production, `bex-canary`, free PostgreSQL 18 (sweep `833c`, 2026-11-11): `bex psql <db> -c "create user qa_u with password '…'"` → `ERROR: permission denied to create role` / `DETAIL: Only roles with the CREATEROLE attribute may create roles.`
- The same refusal on a kind cluster with CloudNativePG 1.30.1 after `createdb: true` was added to the owner's managed role (the w8/m155 spike).
- render.com/docs/postgresql-credentials (read 2026-11-11): "Users created directly with the `CREATE USER` command are _not_ managed by Render.", "not built-in PostgreSQL roles or users created via `CREATE USER`." No Render page lists the default user's role attributes.

## Why it was not simply granted

- **PostgreSQL 16 and later:** a non-superuser with `CREATEROLE` administers only the roles it created, and can grant membership only in roles it holds `ADMIN OPTION` on. It cannot alter `postgres`, `streaming_replica` or `cnpg_metrics_exporter`, and cannot grant itself a predefined role. Granting it there looks safe.
- **PostgreSQL 13, 14 and 15** (all offered by bex and by Render): a role with `CREATEROLE` can alter any non-superuser role and grant membership in any of them, the predefined ones included. It can therefore make itself a member of `pg_execute_server_program`, `pg_read_server_files` and `pg_write_server_files`, and run programs or read files in the database pod with `COPY … PROGRAM`. That pod holds the instance's server certificate keys, the replication client certificate and whatever the backup plugin mounts. It can also reset the password of `streaming_replica`. Today a tenant cannot run anything in that pod.

## Fix (needs a decision)

1. **Grant on 16 and later only.** `createrole: true` on the owner and each default credential when the cluster runs PostgreSQL 16 or later. The projection must key on the major the cluster actually runs (`status.currentVersion`), not the requested one, so an upgrade in flight is not granted early; an upgrade from 15 gains it afterwards. Record the 13–15 difference in ADR018 with the user's sign-off.
2. **Grant everywhere, after hardening 13–15.** Needs a way to stop a `CREATEROLE` role granting itself the predefined server-file and program roles there. PostgreSQL has no setting for that; an event trigger cannot catch `GRANT` of a role. Likely not achievable.
3. **Keep refusing, and record it.** A signed-off divergence in ADR018: users are added through bex (`POST /postgres/{id}/credentials`, `…/users`, the dashboard), never by SQL.

Whichever is chosen: a SQL-created user is not shown by bex's user list (as on Render), can sign in through both URLs, and is outside credential rotation. Confirm what Render's default user really has (`\du` on a Render database) before deciding; that was not possible from here.

## Acceptance

- ADR009's role table and ADR018's Postgres row state the decided rule, with the user's sign-off if it differs by version.
- If granted: `CREATE USER` succeeds on a database of an allowed major, `GRANT pg_execute_server_program TO <self>` fails, an existing database gains the attribute without a restart, and an operator test covers each major.

## Dedupe

w8/m155 (CREATEDB) recorded this as its open question. No other `.pm` item covers `CREATEROLE`.

## Verdict 2026-11-11 (w8 drain): blocked — option 1 does not work under CloudNativePG, so nothing shipped

Option 1 (grant `CREATEROLE` on PostgreSQL 16 and later) was implemented, reviewed and then withdrawn before it was committed. It would have given the default user a statement that works once and then traps it.

- **What happens.** On PostgreSQL 16 and later, `CREATE ROLE` by a non-superuser adds a `pg_auth_members` row making the creator an `ADMIN`-only member of the new role. That row is the creator's whole authority over the role. CloudNativePG's role sync reads every membership row of a managed role with no `admin_option` filter and runs `REVOKE <role> FROM <member>` for each one not in `inRoles` (`internal/management/controller/roles/postgres.go`, `List` and `UpdateMembership`, at v1.30.1, the version `deploy/gitops/base/cnpg-operator.yaml` pins). bex's owner is a managed role with `inRoles: [pg_monitor]`.
- **Reproduced on `postgres:16-alpine`** with the default user's projected attributes and the sync's own statement:
  - before the sync, the owner alters the role it created;
  - `pg_auth_members` holds `app_ro | owner | grantor postgres | admin t | inherit f | set f`, and the sync's query returns `{pg_monitor,app_ro}`;
  - after `REVOKE "app_ro" FROM "owner"`: `ALTER ROLE app_ro PASSWORD …` → `permission denied to alter role`; `DROP ROLE app_ro` → `permission denied to drop role`; `GRANT app_ro TO other` → `permission denied to grant role`. Only a superuser can remove the role, and a tenant has none;
  - once the owner has granted the role to another role, the `REVOKE` fails with `dependent privileges exist`. The sync runs a role's grants and revokes in one transaction, so that role's membership changes fail from then on.
- **Upstream:** [cloudnative-pg#11448](https://github.com/cloudnative-pg/cloudnative-pg/issues/11448), "Automatic role grant of `CREATEROLE` is revoked with managed roles", open and untriaged since 2026-09-07 against 1.30.0.
- **Not run:** the revocation on a live CloudNativePG cluster. The PostgreSQL side was run; the operator side is from its source and the upstream report.

**What is needed, from whom.** One of:

1. **Upstream fixes #11448** and bex moves its pin. Then option 1 is about 40 lines: `managedRoles(…, createRole bool)` sets `createrole: true` on the owner and each `OwnerPrivileges` credential (not on a retired login), gated by `status.currentVersion >= 16` so an upgrade in flight is not granted early, with one operator test per major.
2. **The user approves carrying a patched CloudNativePG instance manager** (filter `ADMIN`-only rows out of the membership diff) until upstream lands it.
3. **The user signs off the divergence** (option 3 above): `CREATE USER` stays refused on every version, recorded in ADR018.

PostgreSQL 13–15 need the user's sign-off under every option: `CREATEROLE` there lets a tenant run programs in its database pod.

ADR009 § role attributes and ADR018's Postgres row now state this as an open divergence that is not signed off.
