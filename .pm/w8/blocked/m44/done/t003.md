## Objective

Keep `imageUrl`/`imgURL` scoped to one deploy, preserve the saved service image through success or failure, and record the Render evidence and cross-surface decision. A subsequent ordinary/configuration deploy must use saved settings.

## Acceptance criteria

- [x] The decision is recorded with Render evidence.
- [x] With the chosen behavior, the sweep-13 step 2 sequence (fail an image deploy, then clear the pre-deploy command) behaves as decided, and a backend test pins it.

## Historical blocker (2026-09-26; resolved 2026-10-02)

**Render evidence could not be established here.** `render.com/docs/deploy-hooks` says only "If you _don't_ provide this parameter, Render uses whichever tag or digest you've specified in the service's settings". That reads as `imgURL` being a per-deploy override that leaves settings alone, but it says nothing about success vs. failure. The API reference's `imageUrl` field ("host, repository, and image name all must match the currently configured image") is silent too. A direct check needs a Render account: deploy a nonexistent tag via `imageUrl`, then read `image.imagePath` and trigger a config change.

**Restoring the row alone is unsafe** (investigated): `SetAppImage(lastLive)` makes the projector move `spec.image` back under the failed release's generation. `markRunning` then stamps `ActiveRevision = rev-N` for a release that never served, and after a pre-deploy failure the gate re-stamps its terminal verdict and never rolls. A correct "restore" must open a rollback-style release (a new deploy row, like `Rollback`), not just write the row.

Options for the user: (a) keep the requested image (today: reads already show `imagePath` = the failed tag, and the next deploy uses it) and record that as the decision; (b) auto-open a rollback release to the last live image when an `imageUrl` deploy fails; (c) stop writing the row for `imageUrl` at all (Render's settings-unchanged reading), which needs a projector exception for `spec.image`.

## Decision and implementation (2026-10-02)

The user accepted leaving saved settings unchanged. [Render's image webhook documentation](https://render.com/docs/deploying-an-image#deploy-via-webhook) explicitly says future deploys use the saved tag/digest. Applying that persistence rule to REST/GraphQL/MCP is the documented bex consistency decision; the REST field reference itself is silent about persistence.

`triggerFetched` now selects an image-only `ReleaseConfig` for the newly serialized release instead of writing the saved row or `spec.image`. Each deploy row records its caller's override. Existing operator release selection, projection and generation expiry do the rest; ordinary/configuration deploys return to the saved image. No restoration of a failed release's row occurs.

Backend tests cover successful/failed override completion followed by a normal deploy and projection preservation. The operator test checks current saved commands/env plus the selected image, then expiry for a subsequent release. The concurrent tests include the actual Restart method and deploy-hook HTTP handler. An overlay mutation replacing the selection with `spec.image` fails the regression tests. Production failure → config-change verification remains in t007, after ship.
