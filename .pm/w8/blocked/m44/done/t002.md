## Objective

In `settleFailedRollout` (`lego/operator/internal/controller/app_controller.go:2845-2852`), consult `stuckPodMessage` (and the quota message) before `settleFailureOverPriorRelease`, and carry its reason/message into the deploy fact. The prior release keeps serving, but the failed deploy row says why. Consider failing fast on a persistent `ErrImagePull`, as t001 does.

## Acceptance criteria

- [ ] A failed-over-prior-release rollout whose new pods are `ImagePullBackOff` closes with `image pull is failing: …`, not the generic health-gate line (`store/reconciler.go:1446-1455`).
- [ ] CrashLoopBackOff and quota-blocked rollouts over a prior release get their specific reasons too (same fix).

## Wider than image pull (2026-09-26, `/qa-find-bugs-cli` sweep 39)

The same branch drops **w4/m112's health-check diagnosis** too, so t002 should keep any `stuckPodMessage` result, not only the image-pull branch. Live, production `726042a28`, free repo web service `srv-das5q20d0qnc73d7a2q0` (express-hello-world, first release live, deleted afterwards):

- `app_controller.go:2849-2852`: `releaseHasServed` → `settleFailureOverPriorRelease(…, "the latest rollout failed")` returns before `stuckPodMessage`. m112's "a failed deploy inherits the probe diagnosis" therefore holds only for first releases.
- The ~4 minutes with no `stallReason` on a still-open deploy (after the 900 s progress deadline, before settle) is an unverified cause. Check whether the projector clears the stall once `ProgressDeadlineExceeded` is set but before the row goes terminal. Keeping the last diagnosis until terminal would be the honest shape.
- Acceptance addition: the same health-check repro ends `update_failed` with the `GET /qa-nope on port 3000` diagnosis as its failure reason, and `stallReason` never disappears while the deploy is still open.

## Outcome (2026-09-26) — done

- `settleFailedRollout` now computes the diagnosis (`stuckPodMessage` → quota → `ProgressDeadlineExceeded`) before branching. Over a served release it writes the new `ConditionRollout` (False, diagnosis reason/message, stamped with the release generation, `lego/types/v1alpha1/app_types.go`) in the same status write, and the PriorReleaseServing Ready message reads `the latest rollout failed: <diagnosis>; …`. Image pull, crash loop, container config, **health check (sweep 39)** and quota all flow through.
- Backend (`store/reconciler.go`): `recordedRolloutFailure` closes the matching row `update_failed` as soon as the verdict exists, not at the health-gate timeout, with the diagnosis as `failureReason` (plus `EventReasonImagePullBackoff` for pulls). That closes the ~4 min window where the row sat open with no `stallReason`: the row goes terminal on the same pass the operator settles.
- Timing: the over-prior-release path still settles at Kubernetes' ProgressDeadlineExceeded (`rolloutBudgetSeconds` 900s), about 15 min instead of about 18, now with the right reason. No early fail-fast was added on this path, because the prior release serves throughout and a pull that recovers still rolls out.
- Tests: `TestRolloutDeadlineOverPriorReleaseKeepsTheDiagnosis` (image pull; nothing diagnosed), `store.TestRolloutFailureOverServingReleaseClosesNowWithItsDiagnosis`, `TestRolloutVerdictForAnotherReleaseIsIgnored`.
