# A failed native build's closing log lines double the `==> ` marker (`==> ==> Installing Bundler …`)

Why: cli-qa routine run 22 (sweep r20, 2026-11-21 07:45Z, production pin `f797f525f5df`, bex v0.9.0) built a free Ruby service from `render-examples/sidekiq`. The build failed, and its build log ended with `==> ==> Installing Bundler 2.5.23 (from Gemfile.lock)` under `==> Build failed: build failed in the build command step:`. Render prints each narration line with a single `==> `.

- Severity: minor. It is narration polish, but it shows on every failed native build whose log tail holds bex's own `==> ` lines.
- Cause: `buildFailureMessage` (`lego/operator/internal/controller/build_failure.go:81`) puts the raw log tail into the failure reason. That tail already holds bex's own `==> ` lines. `terminalLines` (`lego/backend/internal/logs/progress.go:474`) then prefixes `"==> "` to each line of the reason.
- Dedupe: no `.pm` item matches. w4/457, which fixed the order of these lines, still holds.

## Fix

Strip an existing `==> ` prefix before adding one in `terminalLines`, or keep the tail's own markers and skip the prefix for lines that already have one. Check every caller that renders a failure reason: the deploy log stream, `bex logs` and the dashboard deploy page.

## Acceptance

- No terminal failure line starts with `==> ==> `.
- `TestTerminalLinesAppendFailureReason` covers a reason line that already starts with `==> `.
- A live failed native build in `bex-canary` shows each closing line with a single marker. Use a free fixture, and delete it by ID afterwards.

Estimate: ~20m.

## Status (2026-11-21, loopx w8): fixed in `cce6c749f`; the live check waits for the pin
