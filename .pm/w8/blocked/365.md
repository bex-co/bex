# A Blueprint mapping with two or more unknown keys gets one error at the mapping, naming the keys in random order, where a single unknown key is reported at the key itself

Why: Render's Validate Blueprint gives each error a `path` that is "the path to the field with the error (e.g., `services[0].plan`)" with that field's line and column (api-docs.render.com/reference/validate-blueprint, read 2026-11-21). bex does that for one unknown key (w4/632), but a second typo in the same service turns both into one error at the service's `- type:` line, and running the same file twice can name the keys in a different order.

- Severity: minor. Validation still fails with exit 1, and both names are in the message. Only the position, the path and the stability of the message are wrong.
- Versions: bex CLI v0.8.0 (released 2026-11-21 01:31 UTC; Render CLI pin `4fd34231b637`, v2.36.0). Also seen with v0.7.0. Production pin: not read. The code is unchanged on main (`git log -S 'len(additional.Properties) == 1'` finds only `a4587f033`).
- Context: 2026-11-21 04:20–04:30 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY. Routine `cli-qa`, nonce `c7e2`. Validation only: no resource was created.

## Repro

`unknown.yaml`:

```yaml
services:
  - type: web
    name: qa-20261120-c7e2-web
    runtime: node
    plan: free
    repo: https://github.com/render-examples/express-hello-world
    buildCommand: yarn
    startCommand: node app.js
    bogusField: 1
    healthCheck: /healthz
topLevelBogus: true
```

```text
$ bex blueprints validate unknown.yaml -o json        → rc 1, stderr empty
{"errors":[
  {"column":5,"line":2,"path":"services[0]",
   "error":"at '/services/0': additional properties 'bogusField', 'healthCheck' not allowed"},
  {"column":1,"line":11,"path":"topLevelBogus",
   "error":"at '': additional properties 'topLevelBogus' not allowed"}],
 "valid":false}
```

- The second entry is right: a lone unknown key gets its own path and its key's position.
- The first points at `- type: web` (line 2, column 5), not at `bogusField` (line 9, column 5) or `healthCheck` (line 10, column 5), and its path is the service, not a field.
- Six runs of the same file gave `'bogusField', 'healthCheck'` four times and `'healthCheck', 'bogusField'` twice. `-o yaml` and the TTY text (`services[0] (line 2, column 5): …`) inherit both problems.

## Root cause

- `appendBlueprintSchemaProblems` (`lego/backend/internal/apps/blueprint_compiler.go:1443-1465`) moves the path onto the key and uses `source.keyLocations` only when `len(additional.Properties) == 1` (`:1445`). With two or more keys it keeps the mapping's pointer and location and passes the validator's message through as it is.
- The validator builds `kind.AdditionalProperties.Properties` while ranging over the instance object, a Go map (`github.com/santhosh-tekuri/jsonschema/v6@v6.0.3/validator.go:241`, appended at `:266`, reported at `:278`). So the order of the names changes from run to run. `sortBlueprintSourceProblems` (`:1769`) sorts whole problems, not the names inside one message.

## Fix

In `appendBlueprintSchemaProblems`, when an `AdditionalProperties` error names N > 1 keys, append N problems, one per key. Each gets the path `<parent>/<key>`, the key's `keyLocations` position, and the message for one key (`at '<parent>': additional properties '<key>' not allowed`), the same message the single-key case gives today. The existing sort then orders them deterministically. The shared compiler serves REST validate, preview and apply, GraphQL `validateBlueprint`/`blueprintPreview`, MCP `validate_bex_yml`/`preview_blueprint` and the dashboard's error list, so this one change covers all of them. Check that the anyOf branch selection (`selectBlueprintAnyOfCause`, w4/m102) still picks the same branch: it counts leaves, and splitting happens only when the problems are appended, after the branch is chosen.

- A single unknown key (the `colour` row of `blueprint_yaml_location_test.go:79`) is unchanged.
- A backend table test covers 2 and 3 unknown keys in one service, unknown keys in a nested mapping (`envVars[0]`), and repeated runs comparing equal.
- Unverified: whether Render's own validator sorts errors by line or by path. bex sorts by path, so a file with `runtime`, `plan` and `region` errors on lines 4, 5 and 6 lists them as plan, region, runtime. That is kept as it is.

## Verdict

- 2026-11-21 triage: the premise held at main `702b45cd5`. `appendBlueprintSchemaProblems` used the key's path and position only when `len(additional.Properties) == 1`, and it is the only `AdditionalProperties` handler in `lego/`.
- Verdict: work.
- Fixed in `93ad73e8a`:
  - An `additionalProperties` error with N keys becomes N problems. Each has the path `<parent>/<key>`, the key's line and column, and the one-key message the lone case already gave (`at '/services/0': additional properties 'bogusField' not allowed`). The path sort then orders them the same way on every run.
  - The anyOf branch choice (w4/m102) is unchanged, because the split happens only when the chosen leaf is appended.
  - REST validate, GraphQL `validateBlueprint`, MCP `validate_bex_yml`, preview and the dashboard's error list all read this one compiler, and the dashboard renders each entry as it comes (`blueprint-error-list.tsx`). No dashboard change was needed.
  - Tests: `TestBlueprintUnknownPropertiesPointAtEachKey` (two and three keys in a service, two in `envVars[0]`, a root key beside them, 20 repeated runs comparing equal) and `TestValidateBlueprintReportsEachUnknownKeyOnEverySurface` (this note's file over REST, GraphQL and MCP). Both fail with the fix reverted. `TestBlueprintUnknownPropertyPointsAtItsKey` (the `colour` row) passes unchanged.
  - Checks: `go test ./internal/apps/` and the ship gates' real-DB backend suite pass.
  - Order: within one mapping the keys follow the path sort, which is alphabetical, as this note's Acceptance keeps it. In this note's file that is also their source order.
