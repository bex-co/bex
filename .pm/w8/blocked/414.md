# `/v1/metrics/bandwidth-sources` answers no points for traffic in the current hour, stamps its hourly points at the end of each hour (in the future for the current one), and starts the hours at `startTime`

Why: Render's `bandwidth-sources` "returns hourly data points" (pinned `render-public-api-1.json`; its example stamps whole UTC hours, `1709856000`, `1709859600`). w8/190's own acceptance says its `total` agrees with `/v1/metrics/bandwidth` summed per hour. On bex, a window that ends now answers `values: []` for every source while `/v1/metrics/bandwidth` shows the bytes, and a window ending later shows the bytes on a point stamped in the future.

- Severity: minor. It is a REST-only Render route. A client charting egress by source reads nothing for the current hour, and a timestamp that has not happened yet for the hour that just ended.
- Versions: `bex v0.9.0` (Render CLI v2.36.0, pin `4fd34231b637`), `main` `8693058e00`. Production pin `19fdb46f1758`; `lego/backend/internal/metrics` is identical on it and on `main`.
- Context: 2026-11-23 02:02–02:15 UTC, `https://api.bex.co/v1/`, workspace `bex-canary`, human device-login token, `/qa-find-bugs-cli w8` routine sweep met1122. The CLI has no metrics command, so these are REST GETs with the CLI's token.

## Repro

Free web service `srv-dc1ptf9fdpsc73e0hln0` (since deleted), created 02:02:37, served 186 paced GETs from 02:03:24 to 02:05:54. Timestamps are decoded from the epoch seconds the route returns.

at 02:14:31  same with startTime=01:00:00Z, and with startTime=01:30:00Z, endTime=now → every source "values": []

## Root cause

`bandwidthSources` (`lego/backend/internal/metrics/bandwidth_sources.go:104`) sets `q.Resolution = time.Hour` and passes the caller's `startTime`/`endTime` straight to `Service.Metrics`. That issues a Prometheus `query_range` with `step=3600` from `start`:

- The step grid starts at `start`, not at a UTC hour: 01:30, 02:30 for a 01:30 start, and now−1h, now for the default window.
- Each point is `increase(…[3600s])` evaluated at its own timestamp, so it holds the hour that ends there. The current hour's bytes only appear at the next grid point after now, which needs `endTime` past it and gets a future timestamp.
- A window ending now has no grid point after the traffic, so it answers nothing for it. For a service created this hour, that is every point, because no point from before the service existed is returned (w8/m124's incarnation scoping; the per-minute read of the same window starts at 02:03).
- Hours after now read 0 through the `or vector(0)` fallback (w8/413).

`bandwidthSourcesFor` (`bandwidth_sources.go:130`) copies each point's timestamp unchanged.

## Fix

Build the hourly buckets in the handler:

- Floor `startTime` to its UTC hour and bound `endTime` at now.
- Stamp each bucket with the start of its hour, as Render's example does.
- Include the in-progress hour, bounded at now.
- Read each bucket's bytes as the increase over `[hour, min(hour+1h, now)]`. Either evaluate at the bucket's end and shift the stamp back one hour, or read the current partial hour with its own instant query.
- Never return a timestamp after now or a bucket before the service existed.

The per-minute `/v1/metrics/bandwidth` is out of scope here. It follows the same end-stamped convention as every other bex metrics series, and Render's convention for those is not recorded.

## Blast radius

One REST route. GraphQL and MCP have no per-source hourly read; GraphQL `monthToDateBandwidth` reads month totals through its own path. w8/413's clamp changes the same source, so land the two together: with the clamp alone, a future-ended window would also lose the current hour.

## Acceptance

- Unit tests in `lego/backend/internal/metrics`. Given a fake source:
  - A window 00:00–02:11 with bytes at 02:03–02:06 returns buckets stamped 00:00, 01:00 and 02:00 (or only 02:00 for a service created at 02:02). The 02:00 bucket holds the bytes.
  - A window ending at 06:00 returns nothing stamped after now.
  - Every timestamp is a whole UTC hour.
- Live, after deploy, in `bex-canary` on a fresh free web service with a few dozen paced requests: `GET /v1/metrics/bandwidth-sources?resource=<srv>&startTime=<this hour's start>&endTime=<now>` returns one `total` point, stamped on this hour, whose value × 1 MiB is within 5% of the `/v1/metrics/bandwidth` sum over the same window. No source has a timestamp after the request time. Delete the fixture by ID and confirm a 404.

## Fix (shipped `611fe6d163` and `ecf69e5400` 2026-11-23 by `/loopx w8`)

- **Render's shape.** The pinned spec (`render-public-api-1.json`, `get-bandwidth-sources`, and the same text in the pinned CLI's `pkg/client/client_gen.go`) "returns hourly data points" and stamps its example on whole UTC hours, `1709856000` (2024-03-08 00:00Z) and `1709859600` (01:00Z). A first point at midnight is a start stamp, so each point is stamped with the start of its hour.
- **Whole hours, read so far.** `bandwidthSources` (`lego/backend/internal/metrics/bandwidth_sources.go`) reads the UTC hours the window touches: from the first one's start to the last one's end, and no later than now (`hourlyRead`). It uses the finest step that divides an hour within the per-series point budget: one minute for up to about seven days, four minutes at the default 720-hour cap. `bandwidthSourcesFor` adds each step's bytes to the hour the step began in, and stamps that hour's start. The hour in progress reads up to now. Nothing is stamped after now, and an hour from before the service existed has no point (w8/m124). The total is the same sum `/v1/metrics/bandwidth` gives over the same window.
- **Cap.** `BEX_MAX_QUERY_HOURS` and the start/end order are checked on the window as requested, before it widens to whole hours, so "the last 30 days" taken off the hour is still served. `Service.Metrics` is now the cap check plus `metricsInWindow`, and the handler names the `metrics.Metrics` audit verb that these reads recorded before (`ecf69e5400`, after w21/093's frame sweep refused the method-value chain). The datastore refusal reads the requested window.
- **Surfaces.** REST is the only one. GraphQL and MCP have no per-source hourly read, and the dashboard has no bandwidth-sources view.
- **Tests.** These four tests cover the change, and five mutations each make them fail: end-stamping, an hourly step, no floor on the start, the cap on the widened window, and no bound at now.
  - `TestBandwidthSourcesStampsWholeHoursFromTheirStart` replays the repro at 02:11:06 with bytes sent at 02:03–02:06. A window from 00:00 returns 00:00, 01:00 and 02:00, with the bytes on 02:00. A service created at 02:02:37 returns only 02:00. A start at 01:30 returns 01:00 and 02:00. A window ending at 06:00 returns nothing after now. No window returns 01:00 and 02:00. A window wholly ahead returns `[]`. Every timestamp is a whole UTC hour.
  - `TestBandwidthSourcesTotalMatchesTheBandwidthSum`.
  - `TestBandwidthSourcesCapAppliesToTheRequestedWindow`.
  - `TestHourlyReadSpansTheWholeHoursUpToNow`.
  - The backend real-DB suite (ship gates), lint and dead-code analysis pass.
