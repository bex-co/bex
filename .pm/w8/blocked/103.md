# 103 — CLI trims a local file path and silently uploads its neighbor

Why: a quoted configuration-file path can select different bytes than the file the user supplied, while service creation reports success.

**Severity:** minor functional configuration bug. **Ownership:** upstream Render CLI, shared by the Bex launcher. **Estimate:** 45m to prepare one parser/resolver repair and meaningful regressions; external acceptance, Bex pin refresh and release are separate prerequisites. **Status:** todo. Source: continuous `$qa-find-bugs-cli` w8 sweep225, ADR008 reliable hosting and ADR018 unchanged CLI contract. No product implementation, external filing or ship by QA.

## Reproduction

Create harmless local files named `neighbor.txt` and `neighbor.txt ` (the latter ends in one space), containing NEIGHBOR_A and INTENDED_SPACE_B respectively. Supply the second path as one literal argv value:

```sh
bex services create --name <FRESH_QA_NAME> --type web_service --image nginx:1 \
  --plan free --region frankfurt --secret-file "qa-note.txt:$FIXTURE_DIR/neighbor.txt " \
  --confirm -o json
```

The trailing space is inside the quoted argument. Both published Bex 0.3.2 and unmodified Render 2.27.0 at pin a764810a768202704e7206eb7b87a47211fcd98e read neighbor.txt, quietly POST NEIGHBOR_A under secretFiles[0].content, and exit0 against the local fixture responder. Paths ending in tab and newline do the same. An existing standalone.txt followed by space fails as missing when the trimmed neighbor is absent, and sends no POST. Plain and interior-space controls preserve the intended contents.

[Complete six-case resolver and twelve-command native receipts](evidence/103/README.md). Native requests are captured at a local POST-only responder with a dummy key and a fake create response, rather than a production service. Six commands send wrong bytes successfully, two falsely report a missing file, and four controls pass. Fake IDs are never production targets or resource-ledger entries. No hosted apply or runtime claim is made.

## Diagnosis and fix

- Pin pkg/types/service/secretfile.go:14–27 cuts NAME:LOCAL_PATH, then trims both sides. Trimming localPath at 20 changes the filesystem name after the shell has preserved the quoted argument.
- pkg/service/secretfiles.go:28–45 reparses the flag and calls os.ReadFile on that changed path; its content is used verbatim. pkg/service/create.go:50–54 and 96 attach the resolved files to the create request.
- pkg/types/service/servicecreate.go:249–253 validates through the same parser, while NormalizeServiceCreateCLIInput:214–237 leaves the SecretFiles array unchanged. cmd/servicecreate.go:150–163 builds and submits the request. One production resolver caller and one validation caller share this parser; enumerate their tests/aliases before changing it.

Prepare an upstream change that preserves the exact local-path bytes and reads the literal supplied file, with proper empty-path/delimiter errors. Retain target-name normalization and interior-space/colon-path behavior. Update the existing whitespace-normalization test so it distinguishes target-name formatting from a literal filesystem path. If upstream keeps an explicit normalization syntax, it must refuse the ambiguous input rather than silently read a different existing file. Do not strip files from requests, compensate on the server, or fork the CLI.

Current official upstream main `28b233e29812a911c7c0f30594c419cf10714fca` still trims the local path in [its parser](https://github.com/render-oss/cli/blob/28b233e29812a911c7c0f30594c419cf10714fca/pkg/types/service/secretfile.go#L19). This is a source check, not execution of that main revision. Three targeted read-only upstream issue searches returned zero matches; no exhaustive census or external submission is claimed.
