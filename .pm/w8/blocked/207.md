# A request whose upload takes longer than 60 s is cut off with 502: the tenant edge runs Traefik v3's default 60 s `readTimeout`, so the app receives a truncated body

Why: a web service that accepts uploads (files, videos, backups) over a slow link fails once the client needs more than 60 seconds to send the request. The edge closes the request body at exactly 60.0 s, the app sees a short read, and the client gets `502 Bad Gateway`. Responses that take long are fine (a 420 s response completed), so this is specific to the request-reading phase. Render's first-party docs state no request-duration or upload limit. Community reports put Render's request timeout at 100 minutes, but that was not confirmed from first-party docs here. Either way, a silent 60 s cap on request bodies is not a documented Render limit.

Severity: **major** (large uploads from ordinary connections fail with 502, and the app processes a truncated body; nothing says why). Attribution: infrastructure (tenant edge Traefik entrypoint config). Estimate: ~45m plus a security decision on the slow-client trade-off (see Fix). Source: `/qa-find-bugs-cli` loop sweep 7980, 2026-10-26 (21:10–21:56 UTC). Context: HEAD-built bex `4a5574f27` with pinned Render CLI v2.27.0 `a764810a7682`; platform pin `b4726243e74f`; `https://api.bex.co/v1/`; workspace `bex-canary`; human device login. `*.onbex.co` service hosts resolve to the Hetzner LB (`49.12.20.236`), not Cloudflare, so Cloudflare's 100 s proxy limit is not involved.

## Root cause

- `deploy/gitops/overlays/prod/values/traefik.values.yaml` configures the `web` and `websecure` entrypoints (ports, NodePorts, `proxyProtocol`) but no `transport.respondingTimeouts`.
- Traefik v3 (production pins v3.7.5) defaults `entryPoints.<name>.transport.respondingTimeouts.readTimeout` to **60 s**, the maximum time to read an entire request including its body. `writeTimeout` defaults to 0 and `idleTimeout` to 180 s, which is why long responses are unaffected.

## Fix

- Set `transport.respondingTimeouts.readTimeout` on `web` and `websecure` in the prod (and local) Traefik values to a Render-compatible bound. The recommended value is **6000 s (100 minutes)**, the commonly cited Render request limit. Use `0` (unbounded) only if the security review prefers it.
- Trade-off to sign off: `readTimeout` is also the edge's only defence against slow-header/slow-body clients holding connections open (slowloris). The tenant edge has no per-IP connection or in-flight limits today (`rg -i 'inFlightConn|inFlightReq|rateLimit' deploy/gitops` finds none), only PROXY-protocol client identity. So record in ADR022 whether a longer bound is acceptable alone or needs an `inFlightConn` per-client cap alongside it. Traefik exposes no separate header-read timeout.
- Add a guard to `scripts/gitops-validate.sh` (or the edge validator) so the value can't silently fall back to the 60 s default.
- Record the limit in ADR018 (a new "Request duration / upload timeout" row) with the measured behavior.

## Blast radius

- Every web service and static site behind the `web`/`websecure` entrypoints, including custom domains. Static sites rarely receive bodies, though.
- The dashboard and bex-api share the edge only if they route through these entrypoints. Check `api.bex.co`'s own route before raising the value (its Go server keeps its own `ReadTimeout`, w4/m140).
- Downloads, SSE, WebSockets and long responses are unaffected (write side).

## Regression checks

- Live after GitOps syncs Traefik: the 10 KB/s upload of 1.33 MB (~130 s) to a body-reading fixture returns 200 with `got=1333337 of 1333337`. A fast upload is still 200. A client that sends headers and then stalls past the new bound is closed.
- Delete fixtures by ID with 404 proofs.

## Unverified

- Render's actual limit. The first-party docs export (`render.com/docs/llms-full.txt`, 2026-10-26) states none; "100 minutes" comes from community reports.
- Whether the Hetzner LB adds its own idle limit for silent connections. One early `?wait=150s` and one `?wait=330s` request hung until the client gave up (no response at all) right after the fixture went live. Every later repeat, alone and alongside the slow upload, succeeded, so this was not reproducible and is not part of this item.

## Loopx outcome — 2026-10-28

**Implemented; BLOCKED on GitOps sync and hosted acceptance.** Both HTTP entrypoints explicitly use `readTimeout: 6000s` in base/local values, inherited by production. The rendered Helm guard checks web/websecure for both base and prod, so a chart/value override cannot silently restore the 60s default. ADR022 records the finite-budget slow-client trade-off without introducing an unmeasured per-IP concurrency cap; no optional policy decision holds this parity fix. ADR018 records the precise remaining measurement limit. Render's [first-party comparison now documents 100-minute HTTP responses](https://render.com/docs/render-vs-vercel-comparison#long-running-requests-and-jobs); the exact upload-phase split remains unmeasured. API/dashboard share the edge, and bex-api retains its separate 10s header/30s body limits.
