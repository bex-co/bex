# A static site answers a failed `If-Match` with 412 and an identity `Range` with 206, where Render's edge ignores both and sends 200

Why: w8/361's read-only measurement of Render (`sveltekit-static`, 2026-11-21) found that Render's static-site edge ignores `If-Match` on a `GET`. A `"stale"` tag got `200`, with and without br, and so did either form of the matching tag on identity. Render also ignores `Range: bytes=0-9` on a compressible file's identity body, with or without `If-Range`, and answers `200`. A PNG gets `206` on both.

Bex instead answers a failed `If-Match` with `412` (w4/272) and an identity `Range` without `If-Range` with `206`. ADR018 has no signed-off difference for either, so under the parity rule each needs a fix or a recorded sign-off.

- Severity: minor. Clients that rely on these headers get different statuses than on Render. That can break, or rescue, a resumed download or a conditional fetch.
- Evidence: `.pm/w8/blocked/361.md`, "Seen, not judged here", from 25 read-only Render requests.
- Context: filed by the `/loopx w8` orchestrator from the w8/361 worker's report. 361's tag-direction fix (`870ffe3f9`) is parked on the next pin.

## Fix

First re-measure on 2–3 public Render static sites, read-only, a handful of requests. Check whether this is Render's own edge or Cloudflare in front of it, and whether it varies by file type: compressible versus binary, and HTML versus assets.

Then choose:

- **Mirror Render:** ignore `If-Match` on a static `GET`, and ignore `Range` on a compressible identity body while still honoring it on binary files. Keep `If-None-Match` and the w8/360 404 behavior intact.
- **Or keep bex's stricter answers:** record them as differences in ADR018 and raise them through `/unblock w8` for the user's sign-off. Then park the item with that gate.

The code is in `lego/operator/internal/staticserver/`. Build on 358, 359, 360 and 361.

## Acceptance

On a free `bex-canary` static site, after the fix is live:

- `If-Match: "stale"` and `Range: bytes=0-9` on a compressible file and on a PNG answer with the statuses Render gives;
- the ETag and 304 behavior from 358–361 is unchanged.

Then delete the fixture by ID and confirm a 404.

## Outcome

- 2026-11-21 triage: the premise held at main `d0fe17f39`. `serveObject` passed `If-Match` and `Range` straight to `http.ServeContent`, so a stale `If-Match` got `412` (w4/272, chosen from RFC 9110, not from Render) and an identity or gzip `Range` got `206`.
- Render re-measured on 2026-11-21 with about 50 read-only requests to `sveltekit-static`, `mentorship-guide`, `buzz-docs`, `breadcrumbs-wiki`, `wc3v`, `black-widow-site` and `whatseasonisitinhorizon`:
  - Every answer came from Cloudflare in front of Render's origin (`server: cloudflare`, mostly `cf-cache-status: HIT`). These are Cloudflare's rules, which is what a Render customer gets.
  - `If-Match: "stale"` got `200` and the file on HTML, CSS, JS and PNG, with br, gzip and no `Accept-Encoding`.
  - A PNG takes `Range: bytes=0-9` in every coding: `206`, with `Accept-Ranges: bytes`.
  - A compressible file's identity and gzip bodies answer a `Range` with `200`, the whole body and no `Accept-Ranges`.
  - Its br body takes a `Range` up to 2,641 bytes (twelve files, `206` of the br bytes). From 4,573 bytes up (eight files) it answers `200` with the whole br body and no `Content-Length`. HTML and assets behave alike; only size and coding matter.
- Verdict: mirror Render. It is the parity default, and no sign-off is needed.
- Fixed in `16a6b71c8`:
  - `edgeRequest` drops `If-Match` before `http.ServeContent` on every file. On a body `encodeBody` reports unranged, it also drops `Range`: a compressible file's identity and gzip bodies, and a br body over `maxRangedBrotliBytes` (4 KiB, inside the unmeasured gap).
  - `fileResponseWriter` drops `Accept-Ranges` on those bodies, as Render sends none. Every 200 keeps its exact `Content-Length`.
  - `If-None-Match`, every 304 (strong tag, w8/361) and the `404.html` miss (w8/360) are unchanged.
  - Tests: `TestRangesAndIfMatchFollowRendersEdge` (small and large br, gzip, identity, PNG; GET and HEAD; `If-Range`, stale and current `If-Match`, an unsatisfiable range) and `TestIfMatchNeverHidesIfNoneMatch`. Seven tests fail with `edgeRequest` and the `Accept-Ranges` drop removed, and the large-br cases fail with the 4 KiB bound removed.
  - Checks: `make test` and `make lint` pass. ADR029 § `If-Match` and ranges and the ADR018 static-site row record the rule.
- **Seen, not judged here:** `mentorship-guide`'s `favicon.ico` (15,086 bytes, `image/vnd.microsoft.icon`) went to a br client identity, with a strong tag and a 206 for a range. bex counts `.ico` as compressible. That is one request only.
- Parked: production's pin `820edf28d22d` predates the fix. Once the pin carries `16a6b71c8`, sign in as the QA user and, in `bex-canary`, create a free static site. Its build should write an `index.html` over 1 KiB, a JS file whose br body is over 4 KiB (random hex text, about 16 KiB), a small CSS file and a PNG. Then check:
  - `If-Match: "stale"` gets `200` and the body on each file, with `br`, `gzip` and no header.
  - `Range: bytes=0-9` gets `206` on the PNG in every coding and on the small CSS with `br`. It gets `200` with the whole body and no `Accept-Ranges` on the large JS with `br`, and on every compressible file with `gzip` or no header.
  - `If-None-Match` with the strong tag still gets `304`, and a miss still gets the `404.html` page.
  - Delete the fixture by ID, confirm a 404, and close. w8/361's parked check can run on the same fixture.
