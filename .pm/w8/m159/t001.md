## Objective

`GET /v1/logs` (and GraphQL `logs`, MCP `list_logs`) with `type` listing `build` beside `app` and/or `request` answers 200 with every requested type's lines in one time-ordered page, instead of `400 log type "build" must be requested on its own`. Render documents `type` as an array that includes `build`, with no restriction; the pinned CLI sends `--type request,build` as `type=request&type=build`.

## Context

- `lego/backend/internal/logs/service.go:335-361` `LogQuery.validate` refuses build or predeploy beside another type.
- `lego/backend/internal/logs/loki.go:520-546` `lokiTypeMatcher`: app and request by `container` (`container=~"app|"`), build by `type="build"`. One stream selector cannot union them, which is why w6/m131 made the refusal permanent; `TestBuildTypeIsNeverCombined` (`loki_test.go:179-197`) pins it and must change with this task.
- Pagination: `queryLogPage` reads `Limit+1` (`probe`) to set `hasMore`/`nextStartTime`/`nextEndTime`. Two store reads must be merged by timestamp and cut at the limit so the cursor stays correct in both directions.
- Deploy-scoped reads (`q.Deploy`, `service.go:364`) and the synthesized progress lines for `type=build` (`progress.go`) must keep working when build is one of several types.

## Steps

1. Split a mixed query into the store reads it needs (app/request selector, build selector), run both with the same window, direction, filters and `Limit+1`, merge by timestamp (stable on ties), and cut to the limit.
2. Add the progress lines when `build` is among the types, as for `type=build` alone.
3. Keep `predeploy` refused beside other types unless folding it in is trivial with the same merge (it is not a Render type); say which in the README.
4. Replace `TestBuildTypeIsNeverCombined` with tests of the merged result.
