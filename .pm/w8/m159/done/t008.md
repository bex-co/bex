## Objective

A live tail that follows a build prints every line the build writes, as it writes it: the clone, the runtime and version lines, the build command and its output, the error of a failing command, then the upload. Today it prints only bex's own `==>` narration and the push container's lines. This holds for `bex logs --tail --type build`, the type-less `bex logs --tail` and the interactive `bex deploys create`. The fix is the attach rule in bex-api's build tail, not the CLI.

### Mechanism (traced)

- **The build steps are init containers.** The build pod runs `clone`, the native preparer and version resolver, and `buildkit` as init containers. The pusher is its only regular container (`lego/operator/internal/build/build.go:1410-1436`).
- **Kubernetes reports such a pod as `Pending` until the pusher starts.** Its Init Containers page says: "A Pod that is initializing is in the `Pending` state but should have a condition `Initialized` set to false."
- **`awaitBuildPod` attaches only to a `Running` pod.** It counts a `Running` pod as active and treats a `Pending` one as "waiting" (`lego/backend/internal/logs/service.go:2017-2022`), so the tail keeps polling every 2 s through the whole build.
- **It returns when the pusher starts.** It returns `runningContainers` = the pusher (`:2032-2033`). `followBuild` then records every init container as already over, `before := terminatedContainers(pod)` (`:1887`), and never attaches them.
- **The w6/m123 phase watcher (`:1917-1959`) cannot cover this.** It only starts after `awaitBuildPod` returns, which is when the pod turns `Running`, and by then nothing is left to attach.
- **The same gate serves every live build tail:**
  - `followBuilds` (the CLI's WebSocket tail, `:1298`);
  - the type-less and mixed tail through `followPodsAndBuilds` (`:1303`);
  - the dashboard's SSE `followBuildLogs` (`:1300`). The dashboard's deploy page also polls windowed history every 5 s while the deploy is open (`dashboard/src/features/deploys/hooks/use-deploy-logs.ts:181-182`), which masks the gap there; that was not checked live.
- **The tests never model a real build pod.**
  - `buildPodFor` (`logs_test.go:107-121`) builds a pod in phase `Running` with one regular container running.
  - `TestBuildTailAttachesAPhaseThatFinishedBetweenPolls` (`build_phase_attach_test.go:29`) sets container states with no pod phase.
  - No test has a `Pending` pod whose init container runs.
- **This predates m159.** The gate dates from `b0b5508b3` (2026-07-17). Before m159 a tail opened during a build hit it the same way; m159's definition of done is the first check that watches a build from its start.

### Expected (Render)

- [Subscribe to new logs](https://api-docs.render.com/reference/subscribe-logs): "Logs are streamed in real-time as they are generated."
- The [CLI reference](https://render.com/docs/cli-reference) says `render deploys create` will "Trigger a service deploy and stream logs in real time".
- A build's lines are generated while it runs, so the tail carries the build command's output as it is written.

## Steps

1. **Attach while the pod is still `Pending`.** In `awaitBuildPod`, treat a pod as attachable when any of its containers runs, init or regular, whatever the pod's phase. A `Pending` pod with no running container is still "waiting", as now.
2. **Don't drop phases that ended after the tail opened.**
   - In `followBuild`, `before` should hold only the containers that terminated before the tail's `Since`, read from `State.Terminated.FinishedAt`. Today it holds every container terminated at attach.
   - A phase that ran and ended between two polls after the tail opened (a fast `clone`) is then read from `Since`, through the existing `sent` de-duplication on `followBuilds`.
   - A tail opened mid-build still skips the phases that finished before it opened, as Render's "as they are generated" implies.
3. **Tests**, with a build pod that goes through its real lifecycle:
   - `Pending` with `clone` running, then `Pending` with `buildkit` running, then `Running` with the pusher, then `Succeeded`;
   - and a variant where `buildkit` fails, so the pod goes `Pending` → `Failed` with no regular container ever running.
   - The WebSocket build tail, the type-less tail and the SSE build tail emit every phase's lines in order, including the failing command's output. Change `buildPodFor`, or add a lifecycle helper beside it, so no test models a build pod as `Running` from its first line.

## Acceptance criteria

- [x] The type-less `bex logs --tail` and the interactive `bex deploys create` show the same build lines.

## Outcome

Done 2026-11-12 (`/loopx w8`), shipped; the production replay is t007's.

- **Step 1.** `awaitBuildPod` (`lego/backend/internal/logs/service.go`) attaches to a build pod as soon as any of its containers runs, init or regular, whatever the pod's phase; a `Pending` or `Running` pod with nothing running is still "waiting". It used to count only a `Running` pod, which a build pod becomes when its push starts.
- **Step 2.** `followBuild` treats as already over only the phases that ended before the tail's lower bound (`terminatedBefore`, from `State.Terminated.FinishedAt`); a phase that ended after it, between two polls, is attached and read from that bound. A tail with no lower bound (the dashboard's SSE build tail) reads every phase.
- **Step 3.** `TestBuildTailFollowsABuildPodThroughItsLifecycle` drives a WebSocket build tail, and a type-less WebSocket tail, through `Pending` (clone running) → `Pending` (BuildKit running) → `Running` (push) and, in a second case, → `Failed` with no regular container ever running: every phase's lines arrive in order, the failing command's error included. It fails on the previous code (the tail reads nothing after the clone's pod turns to BuildKit). `TestBuildTailSkipsOnlyPhasesThatEndedBeforeItOpened` covers acceptance 4. `TestBuildTailAttachesAPhaseThatFinishedBetweenPolls` now pins the bound and the order. `buildPodFor` is unchanged; the lifecycle helper sits in the new test.
- **Order (review).** Phases are attached in the pod's own order, the ended ones read to their end before a running one starts (`phasesToAttach`), so a phase read late never prints after the one that followed it; a skipped phase counts toward "every phase attached", so the watcher stops as soon as nothing is left.
- **Not done:** a build pod that goes `Pending` → `Failed` between two polls (a clone that fails within about a second) is still never attached, so such a tail shows only the `==> Build failed` narration; acceptance 3's build-command failure runs long enough to be attached.
- ADR010's live-tail section records the attach rule.
