## Objective

`GET /v1/logs/subscribe` with `build` among its types streams build lines as builds run, for as long as the subscription is open. A subscription opened when no build runs stays open on keepalives and streams the next build; it never closes with `4000 no running build is available to follow`, and it never replays an earlier deploy's lines. Mixed with `app`/`request`, the tail streams all of them.

## Context

- `lego/backend/internal/logs/service.go:1188-1190`: build has its own tail only as the sole type (`followBuildLogs`); every other tail is `followPods` plus the request poll.
- `ErrBuildNotRunning` (`service.go:74`) is the terminal outcome today; `docs/render-artifacts/live-deploy-following.md:44` records it as a deliberate "named terminal" answer. The dashboard deploy page's build tail reopens a terminated subscription every 5 s while the deploy builds (same doc, § Fixes); keep that page working.
- Live sweep `53bf`: a `--tail --type build` opened at 07:22:15 printed three lines of the deploy that went live at 07:18:10, then closed 8 s before the next deploy began; the CLI exited 1.
- The CLI reconnects on drops (pinned `pkg/logs/tail.go`), and treats close code 4000 as final.

## Steps

1. Give the build producer a watch on the service's build pods: attach when one starts, detach when it ends, keep waiting. Only lines at or after the subscription's start time (or the caller's `startTime`) are sent.
2. Run it beside `followPods` when the types include build and something else.
3. Keep the synthesized progress lines for builds that start while subscribed.
4. Check the per-process SSE/WebSocket slot accounting still bounds a tail that now waits.
