# Postgres reads omit the Render-required `suspenders` and `role` fields

Why: Render's `postgres`/`postgresDetail` schemas require `suspenders` and `role`, and bex already knows both values (it emits the sibling `suspended` enum, and every listed database is a primary) — omitting them makes the pinned CLI render `"suspenders": null` and breaks strict consumers of a required-field contract, the same class w4/014 fixed for services and w6/m109 fixed for `ipAllowList`/`readReplicas` before explicitly flagging this pair as the remaining unowned gap (`.pm/w6/done/m109/README.md:68`).

Seen in the `/qa-find-bugs-cli` loop sweep 512, 2026-10-19, production, `bex-canary`, human device-login QA identity, HEAD-build `bex` plus raw REST with the same credential (read-only against a pre-existing database; nothing mutated):

- `bex postgres get dpg-… -o json` → `"suspenders": null`, `"role": ""` (the pinned client's struct defaults showing through).
- Raw `GET /v1/postgres/{id}` → the payload has **no `suspenders` and no `role` key at all** (24 keys; diffed against the vendored Render schema at `lego/backend/internal/api/openapi/render-public-api-1.json`: `postgresDetail.required` ∌ payload = `project`, `role`, `suspenders`; `project` is a separately allowlisted shape divergence and is **not** part of this note).
- Services do not have this gap: `lego/backend/internal/apps/service.go:1180` `suspenders()` returns `["user"]`/`[]`, pinned by `TestSuspendersPresentOnAllThreeSurfaces` (w4/014). Key Value correctly has no `suspenders` — Render's `keyValue`/`redis` schemas don't define one.

Root cause: `PostgresView` (`lego/backend/internal/postgres/service.go`, `Suspended` at line 134, filled at :521 from `core.SuspendedEnum(d.Spec.Suspended)`) has no `Suspenders` or `Role` field, so REST omits both keys, GraphQL exposes only `suspended` (`graphql.go:53`), and MCP inherits the same view. The omission is currently recorded as fixture allowlist entries (`conformance_allowlist_test.go:79,81,91,93`) under "omitted unknown metadata" — but neither field is unknown: `suspenders` derives from the same `d.Spec.Suspended` bool already read at :521 using the service rule (bex's only suspend path is user-driven, so `["user"]` while suspended, `[]` otherwise), and `role` is Render's `databaseRole` enum (`primary`|`replica`) — every `PostgresView` this endpoint returns is a primary (replicas are nested `ReadReplicaView`s, a different shape).

Fix: add `Suspenders []string` (always serialized, nil-coalesced like `ReadReplicas`/`IPAllowList` per w6/m109) and `Role string` (`"primary"`) to `PostgresView`/`pgView`, expose `suspenders`/`role` on the GraphQL Postgres type, let MCP inherit, and drop the four `role`/`suspenders` entries from the `list-postgres`/`retrieve-postgres` conformance allowlists (the guard test fails stale entries, which proves the drop). Do not touch the `project` entry.

Acceptance:

- `bex postgres get <id> -o json` and raw `GET /v1/postgres/{id}` carry `"suspenders": []` and `"role": "primary"` for a running database; no `null`.
- A suspended owned Postgres reads `"suspenders": ["user"]` on REST, GraphQL, and MCP alike (mirror of the w4/014 service test, extended to Postgres).
- `list-postgres` rows carry both fields too; the conformance guard passes with the four entries removed.
- Key Value payloads are unchanged (no `suspenders` — Render's schema has none there).

Severity: minor (required-field parity; tolerant clients unaffected today). Estimate: ~40m.
