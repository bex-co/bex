# A new Elixir service with no `ERLANG_VERSION` builds on Erlang/OTP 28.5.0.8; Render's default since 2025-06-12 is exactly 28.0.2

Why: Render documents an exact default Erlang/OTP next to its exact default Elixir. bex now gives a new service Render's exact Elixir (1.18.4, `w6/m291`), but the OTP under it is whatever the `elixir:1.18` image was built with, a newer 28.x than the one Render installs. That is the w8/198 and w4/620 class (Render's exact default, not the line's newest patch), for Erlang.

**Severity:** minor (the same OTP major, so most apps behave the same; an app or dependency sensitive to the OTP patch, such as a NIF or a known OTP regression, runs on a different release than on Render). **Attribution:** build (operator native version resolution). **Source:** `/qa-find-bugs-cli` sweep `af3b`, 2026-11-16, production pin `48bc2a0fedda`, bex CLI v0.7.0, workspace bex-canary.

## Render

[render.com/docs/elixir-erlang-versions](https://render.com/docs/elixir-erlang-versions) (read 2026-11-16) gives these defaults for services created 2025-06-12 and later:

| Runtime | Default (exact) | Minimum |
| --- | --- | --- |
| Elixir | `1.18.4` | `1.12.0` |
| Erlang/OTP | `28.0.2` | `24.3.4` |

Both are set with `ELIXIR_VERSION` and `ERLANG_VERSION`. The page says "Your Elixir version must be compatible with your Erlang/OTP version!"

## bex (production, 2026-11-16 14:23–14:26 UTC)

```sh
bex services create --name qa-20261116-af3b-ex2 --type web_service \
  --repo https://github.com/render-examples/phoenix_hello --branch master --runtime elixir \
  --build-command 'elixir --version; erl -noshell -eval '\''{ok,V}=file:read_file(filename:join([code:root_dir(),"releases",erlang:system_info(otp_release),"OTP_VERSION"])), io:format("QA_OTP_FULL ~s~n",[V]), halt().'\''' \
  --start-command 'sleep 900' --plan free --confirm -o json
bex logs -r <srv-id> --type build --limit 100 -o text
```

There is no `ELIXIR_VERSION`, `ERLANG_VERSION` or `.tool-versions`, so this is a default build. The build log:

```text
==> Using Elixir 1.18.4 (default)
Erlang/OTP 28 [erts-16.4.0.7] [source] [64-bit] [smp:4:4] [ds:4:4:10] [async-threads:1] [jit:ns]
Elixir 1.18.4 (compiled with Erlang/OTP 28)
QA_OTP_FULL 28.5.0.8
==> Build successful 🎉
```

- The target is OTP `28.0.2`; the log shows `28.5.0.8`.
- The `Using …` line names no Erlang, so the log doesn't show which OTP was chosen either.
- `w8/197` (2026-10-23) saw the same thing then (`28.5.0.6`) and called the default a match because the major agreed. Exact defaults have been the board's rule since `w8/198`.

## Cause (code read at `48bc2a0fedda`)

- `exactDefaults` (`lego/operator/internal/build/nativeversion.go:218-232`) has `nativeElixirRuntime: {{renderElixirDefault20250612, "1.18.4"}}` and no Erlang step.
- `resolver.elixir` (`nativeversion.go:807-832`) sets `choice.erlang` only from an `ERLANG_VERSION` finer than a major. With none, the build takes the Elixir line image's own OTP (`elixir:1.18@sha256:1638…`, `toolchain-freshness.json` `native-elixir`), which is the newest 28.x it was built on.
- The exact-OTP path already exists: an `ERLANG_VERSION` such as `28.0.2` builds on the official `erlang` image of that release with hexpm's Elixir on top, both digest-pinned (`w8/197`, `nativeerlang.go`).

## Fix

- When no `ERLANG_VERSION` is set and the service was created on or after 2025-06-12, set `choice.erlang = "28.0.2"`, as if `ERLANG_VERSION=28.0.2` were set, through the `w8/197` path. A dated `exactDefaults` step for the OTP is the natural shape, beside the Elixir one.
- Pin both the `erlang:28.0.2` image and hexpm's Elixir 1.18.4 build for OTP 28 by digest.
- Name the OTP in the default line, for example `Using Elixir 1.18.4 on Erlang/OTP 28.0.2 (default)`, so the log says what was installed.
- **Keep:**
  - An explicit `ELIXIR_VERSION` without an `ERLANG_VERSION` stays as it is. The page gives no rule for which OTP a non-default Elixir gets, so that is unverified.
  - Services created before 2025-06-12 also stay as they are. Render's page doesn't state their OTP default.
  - The creation-date gate keeps a running service's toolchain from moving under an operator upgrade (the `pythonCreationCutoff` pattern).
- No REST, GraphQL, MCP or dashboard change.

## Regression checks

- **Production:** the command above on a fresh fixture gives `QA_OTP_FULL 28.0.2` with `Elixir 1.18.4`. `ERLANG_VERSION=28.3` still gives an OTP 28.3.x (`w8/197`). `ELIXIR_VERSION=1.19.5` alone still builds.
- **Unit:** `cd lego/operator && make test` (`internal/build` resolver and exact-image tests).

## Unverified

- Which OTP Render installs when only `ELIXIR_VERSION` is set to a non-default line.
- Whether hexpm publishes Elixir 1.18.4 for OTP 28 on both architectures. `w8/197`'s path builds from hexpm's per-OTP-major builds, so it most likely does.
- **Observed, not filed:** the companion Node on this Elixir build logged `==> Using Node 24.22.3 (default)`, while a Node service created now gets Render's dated default 24.22.1.
  - Cause: `resolveNativeCompanion` (`nativecommon.go`) calls `ResolveNativeVersion`, which passes a zero creation time, so `defaultExact` returns nothing.
  - Render's docs say only that every native runtime includes `node`, not which version, so whether the companion should follow the 24.22.1 default is unverified.

## Dedupe

- `rg -i '28\.0\.2' .pm docs` finds nothing. `rg -i 'default (erlang|otp)' .pm docs` finds only ADR018's exact-Erlang row (`w8/197`).
- `w8/197` (done) covers an explicit minor or patch `ERLANG_VERSION` and states "Default builds are unaffected".
- `w6/m291` (pin `e3a57b1c398f`) made the Elixir default exact, but not the OTP.

**Estimate:** ~45m.
