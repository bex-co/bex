# 030 — Postgres logs are ~85% CloudNativePG operator chatter, and PostgreSQL's own lines arrive wrapped in CNPG's JSON envelope

Why: `bex logs -r <dpg-…>` (and the dashboard Postgres Logs tab) is where a user looks for slow queries, auth failures and checkpoint trouble. Today, 64 of the first 75 lines of a new database are CNPG instance-manager internals ("Starting EventSource", "Defaulting for Cluster", lease acquisition, "OS distribution is not supported"). The 11 real PostgreSQL lines are one-line JSON blobs with the message buried at `record.message`. The shipper comment assumes the opposite.

Live, 2026-09-27, production `726042a28`, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 44. Fixture: free Postgres `dpg-das9498d0qnc73d7a3q0` (deleted). Key Value control `red-das9490d0qnc73d7a3p0` shows clean Valkey server lines.

```text
$ bex logs -r dpg-… --limit 100 --direction forward -o text      # 75 lines, classified by the JSON "logger"/"msg":
11 instance-manager "Starting EventSource"      7 "Starting Controller"      7 "Starting workers"
 6 "Refreshed configuration file"               5 cluster-resource "Defaulting for Cluster"
 3 "Starting webserver" · 3 "Installed configuration file" · 2 "Triggered a managed role reconciliation" · 1 "OS distribution is not supported" …
11 logger=postgres msg=record   ← the only PostgreSQL output, e.g.
   {"level":"info","ts":"…","logger":"postgres","msg":"record","logging_pod":"dpg-…-1","record":{"log_time":"…","error_severity":"LOG","message":"ending log output to stderr",…}}
```

Lines also expose platform internals, such as the lease lock `tea-daif693dqjvc73e7as3g/dpg-…` and the instance-manager controller names.

## Mechanism

- `deploy/gitops/base/log-shipper.yaml:346-399` (`type=postgres`) keeps the `postgres` container on the premise "CNPG pods include an instance-manager sidecar. PostgreSQL's own stdout is the public datastore log source". In CNPG the `postgres` container's PID 1 **is** the instance manager. It logs its own JSON and re-emits PostgreSQL's csvlog as `{"logger":"postgres","msg":"record","record":{…}}`, so everything is shipped verbatim.
- The direct-pod fallback (`lego/backend/internal/datastorelogs/logs.go` `readPod`/`parseLine`, via `logs/service.go:597-600` and `postgres/logs.go:69`) reads the same container stream with the same result.

## Fix

In the shipper's `type=postgres` pipeline (and the same rule in `datastorelogs.parseLine` for the fallback):

1. `stage.json` on the line. **Drop** entries whose `logger` is not `postgres`. CNPG operational noise belongs to platform observability, not the tenant.
2. For `logger=postgres, msg=record`, rewrite the line to PostgreSQL's own shape, `<log_time> [<process_id>] <error_severity>:  <message>` (plus `DETAIL`/`HINT` when present), and map `error_severity` to the `level` label (`LOG/INFO→info`, `WARNING→warning`, `ERROR/FATAL/PANIC→error`).
3. Keep the existing `type`/`resource`/`instance` labels.
