## Objective

Decide the shape of the durable signal emitted when the disk-usage sample is persistently unavailable: a Warning Event, a status condition, or both; and the debounce (N consecutive failures) that separates a real outage from benign first-reconcile noise (no PVC yet, cluster still provisioning). Write the decision into the task/PR description before implementing.

## Context

- `lego/operator/internal/controller/database_autoscale.go:176-179` — sample errors are logged at Info and swallowed; the success path emits a `DiskAutoscaled` Event and appends `status.diskResizeHistory`; persist failures go through `r.dbFail(..., "DiskAutoscalingFailed", ...)`.
- Failure modes to cover: Prometheus unreachable, kubelet PVC series missing, `^<name>-[0-9]+$` selector matching nothing.
- Where to persist the consecutive-failure counter: annotation (the `lastResize` cooldown precedent) vs in-memory (lost on manager restart — probably fine for a debounce, but decide explicitly).

## Steps

1. Enumerate the failure modes and pick signal + debounce + counter storage.
2. Check CNPG/kubebuilder conventions for Warning Events vs conditions on the Database CR.
3. Record the design (a short paragraph) for t002 to implement.
