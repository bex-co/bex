# A web service that binds no port fails with "Port detection could not reach the instance", not Render's "no open ports detected"

Why: a web service whose process opens no port on `0.0.0.0` is a common first-deploy mistake (a worker created as a web service, a server bound to `127.0.0.1`). Render names it and says what to do. bex waits the same 15 minutes and then says its own port detection could not reach the instance, which reads as a platform fault and tells the user nothing to change.

**Severity:** minor (failure-path wording; the deploy fails at the right time and the previous release keeps serving). **Attribution:** infrastructure/runtime (operator stall diagnosis). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `cc62`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `7ca0227aa477`, workspace `bex-canary`, QA human device login.

## Evidence

Two free native Node web services from `https://github.com/bex-co/bex` (`--root-directory examples/static-site`), no health check path, no `PORT` variable.

**1. Nothing listens.**

```text
$ bex services create --name qa-20261111-cc62-noport --type web_service --repo https://github.com/bex-co/bex --branch main \
    --runtime node --root-directory examples/static-site --plan free --build-command true --start-command "sleep 3600" \
    --auto-deploy=false -o json --confirm
```

- Build ended 10:02:40Z. The deploy stayed `update_in_progress` and closed `update_failed` at 10:18:10Z (15.5 min, Render's start-command limit).
- `bex logs -r <srv> --type app` is empty for the whole wait. `--type build` gains one line at the end.
- `failureReason` on the deploy, the `deploy_ended` event and that log line (`==> Deploy failed: …`) all read:

```text
the container is running but its startup health check never succeeded within the rollout window, so the deploy failed:
a TCP connect to port 10000. Check that the path returns a 2xx or 3xx status on the service's own port — an unset Health
Check Path falls back to a TCP connect, which only asks whether the process is listening. Port detection could not reach
the instance, so a process listening on another port cannot be detected yet.
```

**2. The process listens on `127.0.0.1` only** (`http.createServer(…).listen(process.env.PORT, '127.0.0.1')`, app log `QA LISTEN 127.0.0.1:3000`). Ninety seconds into the rollout the `deploy_started` event's `stallReason` is the same text with "has not succeeded, so the rollout is waiting" and the same last sentence.

**Control.** The same service with a server on `0.0.0.0:3000` went `live` in 3.5 min and answered 200, so the scan does reach the instance and finds a listener when there is one.

## Expected

Render, [Troubleshooting deploys § Port scan timeout reached](https://render.com/docs/troubleshooting-deploys): "Render failed to detect at least one open port on your service's host before its scan timed out", with the causes "bind your host and port" (host `0.0.0.0`) and starting to listen too late. The log line Render prints (quoted in w6/m148 and w8/177): `Port scan timeout reached, no open ports detected. Bind your service to at least one port. If you don't need to receive traffic on any port, create a background worker instead.`

On bex the message for both cases should say that no open port was found on the instance's address, that the server must bind `0.0.0.0` on `PORT` (10000 unless set), and that a service with no port belongs in a background worker. It should not say port detection failed when the instance was reachable.

## Root cause

- `detectBoundPort` (`lego/operator/internal/controller/port_detect.go:108-160`) appends the "could not reach the instance" sentence whenever `scanBoundPort` returns an error (`:120-127`, added by w4/393 so that a failed scan is not silent).
- `scanBoundPort` (`:175-199`) tries `portscan.LikelyHTTPPorts` first. `portscan.scan` (`lego/operator/internal/portscan/portscan.go:127-174`) returns `ErrUnreachable` when no port is open **and no port refused the connection** (`:170-172`).
- The observed text proves the scan returned an error with nothing listening. So on production a closed port on a tenant pod does not refuse the operator's connect, and "no listener" always takes the `ErrUnreachable` (or deadline) branch. The scanner's own comment expects this ("even when closed ports drop probes instead of refusing them", `:53-55`). Which of the two errors it was is not visible from the tenant side.
- The `case 0` branch (`port_detect.go:137-138`), which a refusing pod would reach, adds no text at all, so even there nothing says "no open ports".
- The sentence before it, "Check that the path returns a 2xx or 3xx status", is written for every probe kind (`app_controller.go:6265-6266`), including a TCP probe that has no path.

## Fix

1. In `detectBoundPort`, when the scan finds no open port, with or without an error, append a no-open-port sentence in Render's terms: no open port was detected on the instance; bind `0.0.0.0` on `PORT`; a service that takes no traffic should be a background worker. Keep the operator's `port detection scan failed` log line for the error case.
2. Keep "could not reach the instance" only for a scan that cannot be explained by a missing listener. If closed ports never refuse on production, that distinction does not exist there, and the sentence should go; a cluster check decides (see Unverified).
3. For a TCP probe, drop "Check that the path returns a 2xx or 3xx status" and say that nothing accepts connections on the port.
4. The image-web path has the same sentence in flight (`web_image_http.go:191`, "Port detection could not reach the instance; retrying the HTTP scan"). Give it the same treatment, and check `private_ports.go:233`.

## Acceptance

- A free native web service with start command `sleep 3600` ends `update_failed` with a `failureReason` that says no open port was detected and names `0.0.0.0`, `PORT` and the background-worker alternative. It does not say port detection could not reach the instance.
- A server bound to `127.0.0.1:$PORT` gets the same in-flight `stallReason` and final `failureReason`.
- A server on `0.0.0.0:3000` still goes live with "The process is listening on port 3000, which the service now uses."
- A health check path that answers 500 keeps today's path-specific text.
- `TestDetectBoundPort*` covers: nothing open with refusals, nothing open without refusals, and a scan error with a port already found.

## Unverified

- Why a closed port on a tenant pod does not refuse the operator's connect (network policy drop, or the pod sandbox). It needs `kubectl` on the cluster. If it is a policy drop, the full 65k sweep can never finish inside `portDetectTimeout` and only the twelve likely ports are ever scanned in practice; a service on, say, port 7000 would then not be detected. Not tested in this sweep.
- Render's in-progress narration (`No open ports detected, continuing to scan...`) is quoted from community threads in w8/177, not from Render's docs.

## Shipped 2026-11-11 (w8 drain); the live check waits for the next production deploy

- **No open port.** `detectBoundPort` (`lego/operator/internal/controller/port_detect.go`) now ends the stall text with: "No open port was detected on the instance: the server must bind host 0.0.0.0 on the port in PORT (10000). If the service does not need to receive traffic on any port, create a background worker instead." It says so whether the scan came back empty or unreachable. The evidence above shows both are one case on production (a closed port drops the connect), so "Port detection could not reach the instance" is gone from the product; the operator's log keeps the scan's own error.
- **A TCP check has no path.** For a TCP probe the stall text no longer says "Check that the path returns a 2xx or 3xx status". It says no Health Check Path is set and the connect only asks whether the process is listening. An HTTP check keeps the path sentence.
- **The two siblings.** An image-backed web service in its scan window reads "No port answers HTTP yet; continuing to scan while the container starts" for both cases (`web_image_http.go`), and a private service reads "No open port was detected on the instance: the server must bind host 0.0.0.0 on the service's port (N)" (`private_ports.go`).
- **Test:** `TestDetectBoundPortNamesAnInstanceWithNoOpenPort` covers an empty and an unreachable scan.
