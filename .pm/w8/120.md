# Logs query with a future start and open end returns 500

Why: a user typo or clock-skewed script asking for logs from the future gets an opaque 500 (and an internal-error log) instead of the 400/empty result every sibling window gets.

Found by `/qa-find-bugs-cli` sweep 104, 2026-10-18, against `https://api.bex.co/v1/` with the pinned-CLI HEAD build; repro ×3 on two resources (Postgres `dpg-db9r654flioc739mcpbg`, service `srv-daif6dsmg29s73d1umvg`):

```text
bex logs --resources <id> --start 2030-01-01T00:00:00Z --limit 3
→ exit 1: Error: error listing logs: received response code 500: internal error
```

Same 500 with `--direction forward`. Controls in the same sweep: explicit inverted range (`--start 2026-10-18 --end 2026-10-17`) → honest 400 `startTime must be before or equal to endTime`; future start **with** a future end → 200 empty; past window, now window, relative `5m` → 200.

Mechanism: `core.ValidateInclusiveQueryRange` (`lego/backend/internal/core/pagination.go:169`) treats a zero end as open, and `checkWindowCap` (same file, :184) substitutes `end = now()` only for the cap check — a future start passes both. `lokiRange` (`lego/backend/internal/logs/loki.go:362`) then also defaults `end = now`, producing start > end, Loki's `query_range` rejects it, and the error surfaces as 500. The explicit-inverted 400 proves the intended verdict; the implicitly-inverted case (open end defaulted to now) just never gets compared.

Fix sketch (pick one, keep all surfaces identical): validate the effective window after defaulting the open end to now in `CheckInclusiveQueryWindow`/`CheckQueryWindow` (400, consistent with the explicit case), or clamp in `lokiRange` and return an empty page. Check the shared-helper callers for the same latent shape: metrics (`lego/backend/internal/metrics/service.go:395` uses `core.CheckQueryWindow`) and events. Add a unit case to `lego/backend/internal/core/pagination_test.go` (future start, zero end) and a logs-level case beside `loki_bounds_test.go`.

Second symptom, same defaulting (sweep 106, fresh service with known app lines): `--end 2030-01-01T00:00:00Z` with **no** start returns 200 with zero lines, because `lokiRange` defaults the start to `end − lokiLookback` (7 days, `loki.go:45`), i.e. a window entirely in 2030. The same lines return with no window. A caller-supplied end should not drag the default start years into the future — clamp the defaulted end to now (or the defaulted start to the earlier of end−lookback and now−lookback) as part of the same fix.

Acceptance: the repro above returns 400 (or a documented 200 empty) on REST/GraphQL/MCP alike — never 500; a future end alone still returns the lines up to now; existing window tests stay green.
