# `POST`/`PATCH /registrycredentials` are unreachable: the Render-schema validator and the bex handler demand contradictory bodies

Why: registry credentials are how private-image services get pull access, and the REST create/update surface for them accepts **no** body at all in production — the documented bex dialect is refused by the request validator, and the validator's dialect is refused by the handler. GraphQL works, so the dashboard path lives, but any REST client (including the pinned CLI lineage and Render-shaped automation) cannot create or rename a registry credential.

Seen in the `/qa-find-bugs-cli` loop sweep 676, 2026-10-19, production, `bex-canary` (probes create nothing until the GraphQL control; that fixture was deleted and list-verified empty on both surfaces):

- Bex dialect `POST /v1/registrycredentials {"name","host":"ghcr.io","username","authToken"}` (the shape `createCredentialRequest` decodes, `lego/backend/internal/registrycreds/rest.go:71`) → `400 invalid request body at /registry`. Adding fields one by one walks the refusal through `/registry` → `/ownerId` → `/username` → `/authToken`: the gate is the pinned Render OpenAPI schema, whose `create-registry-credential` requires `name, registry, username, authToken, ownerId` and knows no `host`.
- Render dialect `{"name","registry":"DOCKER","ownerId","username","authToken"}` → bare `400 {"error":"bad request"}`: it passes the schema gate, then the handler's strict JSON decoding (`core.WithStrictJSONDecoding`, applied in `renderRequestValidator.ServeHTTP`) rejects the unknown `registry` field, and the handler collapses that decode error to `core.ErrBadRequest` (`registrycreds/rest.go:131`).
- `PATCH /v1/registrycredentials/{id} {"name":…}` → the same `invalid request body at /registry` (Render's `update-registry-credential` schema requires all four fields); no REST body can rename a credential either.
- Unaffected, verified live: `GET /registrycredentials`, `GET /registrycredentials/{id}`, `DELETE` (204). Control via GraphQL `createRegistryCredential(name, host, username, authToken)` → 201-equivalent with `rgc-…` id, secret never echoed; deleted afterwards.

Root cause: the validator's deliberate-divergence wiring was never extended to this resource. `registrycreds/rest.go:27-36` documents the intentional generalization from Render's `registry` enum to an arbitrary `host`, but `applyRenderCompatibility` (`lego/backend/internal/api/render_openapi.go:317`) has no entry for `create-registry-credential`/`update-registry-credential` in `renderRequiredCompatibility`, `renderBodyPropertyExtensions`, or any sibling map — the three one-concession-per-line maps every other divergent operation uses. The composed stack is therefore unsatisfiable: schema-required `registry` vs strict-decoder-unknown `registry`. The pieces are each tested only in isolation — the package's `rest_test.go` drives the mux without the validator, and `TestRegistryCredentialWorkspaceQueryPassesRenderValidator` exercises GET/PATCH/DELETE against a stub handler, never POST through the real handler.

Fix (~45m): teach the contract the same divergence the handler already documents. For `create-registry-credential`: drop `registry` from required (or remove it from the validated property set) and add `host` via `renderBodyPropertyExtensions` so bex's body validates; for `update-registry-credential`: drop all four Render-required fields (bex PATCH is per-field partial, `registrycreds/rest.go:82`) and admit `host`/`expiresAt` as the handler does. Keep `registry` itself refused — bex's wire deliberately has no such field; a caller sending it should keep getting a refusal, just one that names the actual problem (the strict decoder already produces it once the schema stops demanding the field). Add a composed-stack test beside `TestRegistryCredentialWorkspaceQueryPassesRenderValidator`: real mux + validator, POST the bex body → 201 and the secret absent from the response; PATCH a rename → 200. Audit the remaining `create-*`/`update-*` operations for the same schema-vs-handler field drift while the maps are open (the class, not just this instance).

Acceptance:

- Live after deploy: `POST /v1/registrycredentials` with the bex body returns 201, the credential lists on REST and GraphQL, and no response ever carries the secret.
- `PATCH` with a single field (e.g. `{"name": …}`) returns 200 with the rename read back.
- A body carrying `registry` is refused with a message that names the unknown/unsupported field, never required-field whack-a-mole ending in a bare `bad request`.
- GraphQL/MCP create/update behavior byte-unchanged.

Severity: moderate — a whole REST resource verb pair is dead, with a working GraphQL sibling that masks it from the dashboard. Estimate: ~45m.
