# A Rust service does not get Render's `ROCKET_PORT`, so a Rocket app listens on its own default port

Why: Render sets `ROCKET_PORT=10000` at runtime on every Rust service, so a Rocket app listens on the service's port with no configuration. bex does not set it. A Rocket app that relies on it listens on Rocket's own default (8000).

**Severity:** minor. **Attribution:** infrastructure/runtime (operator). **Estimate:** ~60m. **Source:** `/qa-find-bugs-cli` sweep `965c` via w8/256, 2026-11-11.

## Why it was not set with the others (w8/256)

Render's value is its default port. On bex the port a service is routed on can differ (a configured port, or a `PORT` variable), and a fixed `ROCKET_PORT=10000` in the image would then move a Rocket app off the port the platform routes to, including one that works today through `Rocket.toml`. The value has to follow the serving port, and the service's own `ROCKET_PORT` has to win, whether it is a plain or a secret-backed variable.

## Fix

Inject it from the operator the way `WEB_CONCURRENCY` is (`lego/operator/internal/controller/web_concurrency.go`): for a native Rust service whose own variables and linked groups do not set `ROCKET_PORT` (`configuredEnv`), add `ROCKET_PORT=<serving port>` to the container. Runtime only; the build does not get it.

## Acceptance

- A Rust service with no `ROCKET_PORT` of its own has `ROCKET_PORT` equal to `PORT` at runtime and not in its build.
- With its own `ROCKET_PORT`, plain or from an environment group, that value reaches the process.
- No other runtime gets the variable.

## Unverified

- Whether Render's `ROCKET_PORT` follows a `PORT` the service sets, or stays 10000.
