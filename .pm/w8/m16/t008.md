## Objective

Add the `parameterOverrides` field Render's `postgresPATCHInput` documents to bex's `PostgresPatch`, delegating to the existing PUT-subresource path — so a Render-SDK client sending `PATCH {parameterOverrides:{…}}` stops having its overrides silently ignored.

## Context

- `PostgresPatch` (`lego/backend/internal/postgres/service.go:579`) has no `parameterOverrides`; the dedicated `PUT /v1/postgres/{id}/parameter-overrides` seam (`rest.go:358-374`) is the implementation to delegate to — keep it as the single write path.
- The divergence is documented as deliberate in `docs/ADR018-render-parity.md:88` (bex prefers the dedicated subresource); this task retires the *silent-ignore* half while keeping the subresource: accepted inline, applied via the same seam. Update the ADR018 note accordingly.
- "Accepted but silently dropped" is the exact class w6/m35 exists to kill — same rationale here.
- Cross-surface: GraphQL/MCP already have explicit override verbs; only the REST PATCH body gains the field (matching Render's REST shape). Record that asymmetry-with-reason in the parity task (t004).

## Steps

1. Add the field to `PostgresPatch` + the PATCH handler, delegating to the override-set verb (same validation, same audit event).
2. Test: PATCH with inline overrides applies them; PATCH without the field leaves overrides untouched.
3. Update `docs/ADR018-render-parity.md:88`'s note.
