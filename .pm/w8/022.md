# 022 — Deploying a specific image (`deploys create --image`, deploy hook `?imgURL=`) is always canceled: the projector reverts `spec.image`

Why: for an image-backed service, "deploy this tag" is the main release verb, and CI usually drives it through the deploy hook or `deploys create --image … --wait`. On production every such deploy ends `canceled`: `--wait` exits 1, the service keeps reporting the old image, and the new image's pre-deploy command has already run.

Live, 2026-09-23, production, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 7. Fixture: free web service `qa-20260923-2246e7-web` (`srv-dapqrmjbdpcs73f5efu0`, image `docker.io/mendhak/http-https-echo:34`, since deleted).

```text
$ bex deploys create srv-dapqrmjbdpcs73f5efu0 --image docker.io/mendhak/http-https-echo:35 --wait --confirm -o json
Waiting for deploy dep-dapqsdbbdpcs73f5eg3g to complete...
{ "id": "dep-dapqsdbbdpcs73f5eg3g", "status": "canceled", "image": {"ref": "docker.io/mendhak/http-https-echo:35"}, "trigger": "api", … }
exit 1 after 31 s
```

- Reproduced 3/3: `dep-dapqsdbbdpcs73f5eg3g`, `dep-dapqsoh4dm7c7390qa70`, and `dep-dapqteh4dm7c7390qa90`. The last one ran with the pre-deploy command cleared, so the pre-deploy step is not the cause. No newer deploy superseded any of them.
- For each attempt, the deploy's build log is `==> Deploy queued`, then the pre-deploy output (`pre`, printed **twice** when a pre-deploy command was set), then `==> Deploy canceled`, about 25–40 s later. The app logs show **two** fresh pods start about 10 s apart for each attempt (for example `10:47:39`/`10:47:47` and `10:49:44`/`10:49:56`). That is a roll to the new generation followed by a re-roll.
- Afterwards, the service's `imagePath` still reads `…:34`.
- Control: `bex services update <srv> --image …:35` (the row-writing path) makes the service report `:35`. It opened **no** deploy row and started no new pod, so which image was then serving is **unverified**. The echo image does not expose its tag, and SSH is denied on free instances.

## Mechanism

- `lego/backend/internal/deploys/service.go:641-645` (`triggerFetched`) applies `imageUrl` **only to the App CR** (`a.Spec.Image = p.ImageURL` inside `patchApp`), then opens the deploy row with that image (`:657`).
- For store-managed Apps, `spec.image` is **row-owned**: the control-plane projector writes the row's image onto the CR (`store.go:1847` `SetAppImage`: "The projector carries it onto spec.image"). `Rollback` knows this and writes the row first (`service.go:912-918`: "Row-first: the projector owns spec.image for store-managed Apps"). So does the repo-backed branch of `triggerFetched` itself (`:604-614`, `SetAppImage(ctx, appID, "")`). The `imageUrl` branch never calls `SetAppImage`. The projector restores the old image, the generation moves past the deploy's `releaseGeneration`, and the reconciler closes the row `canceled`.
- `TestTriggerImageURLAcceptsImageBacked` (`service_test.go:697-710`) asserts only the CR's `spec.image` against a fake store, so it cannot see the revert.

## Fix

In `triggerFetched`, when `p.ImageURL != ""` on an image-backed service, call `s.Store.SetAppImage(ctx, appID, p.ImageURL)` **before** the CR patch, the same row-first order `Rollback` uses. Keep the CR assignment so the patch and the projection agree. Refusals already happen earlier in `validateTrigger`, so a refused trigger still writes nothing.

**Blast radius:** every caller of `triggerFetched` with an image: REST `POST /v1/services/{id}/deploys` (`rest.go:255`), GraphQL `deployService(imageUrl:)` (`graphql.go:211`), MCP `deploy` (`mcp.go:187`), and the unauthenticated deploy hook `?imgURL=` (`deployhook.go:381`). Parameter-free triggers, restarts, commit pins and rollbacks are unaffected (no image argument, or already row-first). Separately, check why `services update --image` opened no deploy row while its value changed. It may be correct if the CR already carried that image; record the answer.
