# 020 — `bex logs --type build --tail` exits 0 with no reason when no build pod exists yet (or anymore)

Why: from the CLI, a build tail started while a deploy is still `queued` (or after the build pod finishes but before the row closes) prints one or two `==>` lines and exits 0 within a second. There is no stream and no explanation, so it looks like the build is over. The SSE path already tells its clients why. The WebSocket path the Render CLI uses drops the reason.

Live, 2026-09-23, production, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 6. Fixture: static site `qa-20260923-7346b2-site` (`srv-dapq3irbdpcs73f5efm0`, since deleted).

```text
# deploy dep-dapq3irbdpcs73f5efmg in `queued` ("Build queued" 09:54:19 … "Building from" 09:55:15)
$ bex logs -r srv-dapq3irbdpcs73f5efm0 --type build --tail -o text      # exit 0, 1 s
2026-09-23 09:54:19  ==> Build queued
2026-09-23 09:54:19  ==> Preparing registry credentials

# control: same command while the next deploy was `created`/pod pending → waited and streamed 16 build lines over 146 s
# after the pod finished, row still build_in_progress → exit 0 in 1-2 s, 2 lines, no reason
```

## Mechanism

- `lego/backend/internal/logs/service.go:1250-1252` `awaitBuildPod` returns `ErrBuildNotRunning` when no build pod is Pending or Running. That includes a deploy row that is still `queued` before the build Job exists: the registry-credentials wait and the workspace/cluster build-slot caps. w2/m99 recorded this as its "Known limitation" and invited this follow-up (`.pm/w2/blocked/m99/README.md` §Known limitation).
- `lego/backend/internal/logs/rest.go:424-431` (SSE/NDJSON) writes the named refusal as a final `event: error` or line. `rest.go:350-353` (WebSocket) writes a final frame **only** for `ErrLogsUnavailable`/`ErrLogStoreUnavailable`. Every other `followErr`, including `ErrBuildNotRunning`, just closes the socket.
- The pinned consumer (`render-oss/cli` `pkg/logs/repo.go` `TailLogs`) decodes every WS message as a `Log` and ends the stream on any read error without reading close reasons. So the CLI exits 0, and even the `{"error": …}` frame the unavailable branch sends decodes to an empty log line.

## Fix

1. **Park while the deploy is open.** In `awaitBuildPod`, treat "no pod, but the deploy row for this build is non-terminal (`created`/`queued`/pre-Job `build_in_progress`)" as waiting, not terminal. The progress follower already re-reads the row (`prog`) and narrates the wait each tick. `ErrBuildNotRunning` stays the answer when the row is terminal or absent.
2. **Make the terminal reason visible to the pinned CLI.** On the WebSocket path, send any named terminal refusal (`ErrBuildNotRunning`, unavailable) as one final **Log-shaped** frame: the `==>` progress-line shape the stream already uses, with `type=build`, stating the reason. Do this instead of the current `{"error"}` object, which the CLI decodes to a blank line. Then close normally.

## Acceptance

- [ ] While a deploy sits `queued` before its Job exists, `bex logs -r <srv> --type build --tail` stays open, prints the m99 wait narration, and then streams the build once the pod runs.
- [ ] With no open deploy, the same command prints a final `==> no running build is available to follow` line and exits. The line's wording matches the SSE `event: error` text.
- [ ] A backend test drives the WebSocket handler for both cases. The SSE tests (`logs_test.go:799-808`) stay green.

## Unverified

- Whether exit 0 at stream end is the right code for "nothing to follow". That is the pinned client's behavior and not bex's to change.
- The pre-Job wait on the workspace-cap path. Only the registry-credentials wait was observed live.

Dedupe: `w2/m99` (blocked) owns wait narration and explicitly left tail parking out. No open item covers the WebSocket path dropping the refusal. ADR010 §"The SSE live tail" documents the terminal event for SSE only.
