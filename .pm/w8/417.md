# bex-api's two replicas each keep their own rate-limit buckets, so a caller's effective REST budget is up to twice Render's

Why: w8/410 (`696783e94e`, done) gave the Render-compatible REST surface Render's per-endpoint budgets, for example 400 GETs a minute and 30 writes a minute. But production runs bex-api with two replicas (`lego/operator/config/prod/kustomization.yaml`). The per-caller token buckets and the log-subscription caps live in process memory, and nothing in front of the replicas pins a client to one. So a caller can get up to twice each budget (`.pm/w8/done/410.md` line 79, ADR006 line 764).

- Severity: minor (parity). A script tuned on bex can exceed Render's limits, or see `RateLimit-Remaining` that doesn't fall as it would on Render, because consecutive requests read different buckets (`.pm/w8/done/410.md` lines 94–107).
- Parity: Render's rate limits are per user ([api-docs.render.com/reference/rate-limiting](https://api-docs.render.com/reference/rate-limiting)). ADR006 notes the per-replica split, but ADR018 records no user sign-off, so under AGENTS.md it is open parity work.
- Attribution: server (bex-api's limiter, `lego/backend/internal/…` rate-limit middleware).

## Fix

Share the buckets across replicas, so each caller has one budget per Render row. Options to weigh:
- a shared store bex-api already depends on, such as Postgres with an atomic upsert, or the platform's Valkey if there is one;
- consistent-hash routing of each caller to one replica at the edge;
- dividing each budget by the replica count, with its error bars.

Keep the limiter fail-open, or fail-closed as the current one does, on a store outage, and record the choice. Keep internal callers unthrottled (w8/410). Include the log-subscription caps. Update ADR006's note, and record the outcome in ADR018, citing only the user's own decisions as user decisions.

## Acceptance

- A test with two limiter instances sharing the store: 400 GETs across both in a minute succeed, and the 401st is refused, with `RateLimit-Remaining` consistent across instances.
- Live in `bex-canary`: two GETs within 150 ms read 399 then 398, whichever replica each reaches. No 429 is provoked.
