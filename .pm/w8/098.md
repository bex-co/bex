# Blueprint validation accepts Key Value envVarKey refs that resolve to an empty key

Why: A manifest author gets a clean validation plan for an environment reference that Bex cannot materialize into a valid Pod configuration; refusing it before apply keeps core hosting configuration dependable (ADR008/ADR049/ADR018).

**Current status:** todo — 10m remaining acceptance. Source fix and primary production native gate pass; remaining original checks are required before closeout.

**Severity:** minor. **Estimate:** 10m remaining for public error guidance; original 55m guard work is shipped. **Attribution:** backend Blueprint reference validation/resolution. **Context:** 2026-10-12, human OAuth in bex-canary (`tea-daif693dqjvc73e7as3g`), production `https://api.bex.co/v1/`, non-TTY JSON output. Bex v0.3.2; unmodified Render v2.27.0 at pin `a764810a768202704e7206eb7b87a47211fcd98e`; source HEAD `a5ad5cda47f3b346a95f000021910a5bc33d88f3`; deployed revision unknown. Filing only, uncommitted.

## Reproduction and expected behavior

Run in an isolated QA config and explicitly selected workspace:

```sh
bex blueprints validate kv-env-key-complete.yaml --confirm -o json
render blueprints validate kv-env-key-complete.yaml --confirm -o json
```

Point both binaries at Bex, using equivalent human OAuth authentication. The [complete document](evidence/098/kv-env-key-complete.yaml) declares a Free Key Value source with `ipAllowList: []` and a Free image web consumer. The consumer has `key: QA_TARGET` and `fromService: {type: keyvalue, name: qa175-94d0fe-source, envVarKey: QA_UNDECLARED}`. [The redis alias](evidence/098/redis-env-key-complete.yaml) behaves identically. QA_UNDECLARED names no source variable.

**Actual:** all four native checks return `valid:true`, empty stderr and exit0. Actual compiled parsing accepts both shapes, classifies one Key Value reference, and its apply resolver returns `SecretKeyRef.Key: ""` without an error. The real Kubernetes key-validation helper rejects that empty key. The operator copies the same key into the Pod environment.

**Expected:** refuse a Key Value envVarKey-only reference with a located error explaining the required property. Keep the existing HTTP 200 validation envelope with `valid:false`, errors on stdout and native exit1. This target follows Bex's actual property-only Key Value resolver. Exact rejection of this document on Render production is unmeasured; the generic reviewed schema alone does not forbid the combination.

## Mechanism and shared callers

[Producer and consumer source](evidence/098/source.txt), [caller census](evidence/098/callers.json):

- `lego/backend/internal/apps/deploy.go:2620–2655`, validateKeyedEnv: the EnvVarKey branch runs before the Key Value property-required branch. A nonempty key with no property passes.
- `deploy.go:2040–2043`, classifyRefs: either Key Value alias is deferred to kvRefs, bypassing ordinary same-file env lookup and its missing-key refusal.
- `deploy.go:2692–2712`, resolveKeyValueRef: `kvPropertyKey[ref.Property]` has no lookup-success guard. An empty property yields an empty key while the function returns nil error. The only production caller is resolveServiceRefs at 1017; that prelude has one caller in applyStackServices at 932.

The exercised utility check supports this consumer requirement; full Pod admission was not invoked.
- Four shared parse callers cover validation (blueprint.go:661), disconnected-Blueprint grouping reclamation (1607), apply preparation (deploy.go:1687) and generated-manifest self-check (blueprint_generate.go:240). REST, GraphQL and MCP validation all call ValidateBlueprint. The same parser guard should serve every transport and dashboard feedback.

## Proposed fix and acceptance

In validateKeyedEnv, validate the Key Value reference shape before allowing an ordinary service envVarKey copy: reject envVarKey on a Key Value target and require a recognized property. Add a defensive map-lookup/shape check to resolveKeyValueRef so malformed input cannot return an empty selector. Preserve existing supported properties and both aliases; do not fork the CLI or rewrite its requests. Include the caller/transport census and behavior tests in this sub-hour fix.

- [ ] Both native clients against Bex return valid:false/exit1 for each bad alias, with a located env reference error; rejection happens before any apply writes.
- [ ] Host/port/connectionString and ordinary App-copy controls still pass. Missing property, hostport, both-fields and missing-App-key controls retain their correct refusals.
- [ ] Actual resolver tests require nonempty mapped keys for every accepted property, including password; malformed direct resolver input returns an error. Keep legacy redis behavior aligned with keyvalue.
- [ ] Verify the four parser callers and REST/GraphQL/MCP/dashboard feedback use the same semantics. Add meaningful nested, forward and existing-target controls where this shared rule applies; record any remaining live coverage gaps.
