# A deploy that lands after the operator adopts the waiting deploy, but before bex-api records the deploy ahead as live, still cancels the waiting deploy

Why: w8/396 closed the window that opens after bex-api records the deploy ahead as `live`. One window is left before that, where the waiting deploy is still closed `canceled` although the operator runs it, and the new deploy then waits for its whole publish. Render's Wait would leave it running.

- **Where.** `adoptWaitingDeploy` (`lego/backend/internal/store/store.go`, w8/396) frees the pending slot only when no other deploy is recorded executing. The partial unique indexes allow one executing row and one waiting row per app (`0080_deploy_overlap_queue.up.sql`).
  - Deploy A serves, and the operator adopts B from the pending slot at once. Then a deploy C can land before the reconciler's next pass closes A's row `live`.
  - While A's row is still open, B cannot leave the slot. So `cancelPendingDeploys` closes B `Superseded by` C (`newDeploy`), and C waits behind A's row (202).
  - The operator still holds B's release (`releaseInFlight`) and runs it to the end. C is adopted only after B serves.
- **Not seen live yet.** In the w8/392 and w8/396 runs, C was sent after A read `live`, so it always hit the later window. This one comes from the code. A git push or a configuration save can land here, since neither waits for A to read `live`.
- **Fix direction.** Close the gap before the App write, without making the trigger record A's verdict itself (`recordDeploy` and `recordLifecycleFacts` own that). One option: when the App reports a waiting row adopted while an older row still reads executing, kick the reconciler and wait a few seconds for that row to close, as `rollout.AwaitAdoption` waits for an adoption. Then open the row as w8/396 does. Keep Override's cancel-and-start.

## Acceptance

- A backend test, real DB. A served, B pending, the App reporting B adopted, and A's row still open. A new deploy leaves B running and waits behind it once A's row closes. B is never `canceled`.
- Live in `bex-canary`, if a timing can be found: trigger C while A still reads `update_in_progress` after it served. Otherwise unit and real-DB tests alone, with the reason recorded.
