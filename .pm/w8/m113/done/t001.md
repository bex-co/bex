## Outcome (2026-10-18)

Done. Read-only timings against production with a QA browser session, mirroring each request the pinned CLI's `services` command makes (pkg/service: list all services, list projects, then each project's environments, then the same again for datastores):
- `GET /v1/services?ownerId=<bex>&limit=100&includePreviews=true`: 0.47 s for **5 services**; the next cursor page is 0.53 s and empty.
- `GET /v1/projects`: 0.33 s, 3 projects.
- `GET /v1/environments?projectId=…` for each project: **14.96 / 13.47 / 11.85 s**, each returning `[]`.
- `GET /v1/env-groups?ownerId=<bex>`: **14–16 s for 1 live group**. The same list takes 1.9 s on bex-canary and 0.5–1.0 s on tian-personal, and a single group read takes 0.31 s.
- The other member lists are fast: Postgres 0.74 s, Key Value 0.90 s, a single project 0.76 s.

The slow segment is therefore not the services list. `environments.List` always runs the workspace-wide `membersByEnvironment` scans, and their env-group membership read (`listScopedMeta`) reads every listed group id's metadata sequentially. A deleted group's id stays listed behind its resurrection fence (`plantDeletedMetaFence`). A controlled experiment on bex-canary (five owned groups created and deleted) put each extra tombstone at roughly 50 ms, which implies about 260 listed ids in bex. The CLI pays the scan once per project and again for datastores: 3 × ~14 s × 2 ≈ 84 s, plus the remaining calls, matches the 110–125 s repro.
