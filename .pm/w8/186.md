# Every REST env-var write (`PUT /env-vars`, `PUT`/`DELETE /env-vars/{key}`) immediately redeploys the service; Render's API saves the change and deploys nothing until the caller triggers a deploy

Why: [Render's API reference](https://api-docs.render.com/reference/update-env-vars-for-service) for `PUT /services/{serviceId}/env-vars` says: "Changes will **not** be deployed automatically. Instead you must call the deploy API to have changes pushed out to your service, irrespective of the `autoDeploy` option set on the service." Render's deploy-behavior choice ("Save, rebuild, and deploy" / "Save and deploy" / "Save only", [changelog 2024-09-11](https://render.com/changelog/specify-deploy-behavior-when-modifying-environment-variables)) exists only in the dashboard. Bex rolls the service on every REST env-var write. A script or agent that sets five variables one at a time therefore causes five production rollouts, each with a partial configuration, where on Render it would stage all five and deploy once. A change meant to wait for a planned deploy goes live immediately. ADR018's env-vars row records "legacy item/replace writes still roll immediately for compatibility" without a user sign-off.

**Severity:** major (unrequested production rollouts with intermediate configurations, against Render's documented API contract). **Attribution:** server (secrets write path). **Estimate:** 1h30m. **Source:** `/qa-find-bugs-cli` sweep 1320, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1320--env-var-writes-redeploy)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`. Free image web service created with the pinned CLI (`traefik/whoami:v1.10.3`, `--env-var PORT=80 --env-var QA_A=one`, `srv-dbcs1o4ttgas739mhso0`, deleted 204 → 404). After its first deploy went live, one deploy existed. Each write below created a new deploy within the same second, with event `env_vars_changed` followed by `deploy_started` (`trigger.envUpdated: true`, deploy trigger `service_updated`):

| Write | Response | New deploy |
| --- | --- | --- |
| `PUT /v1/services/<id>/env-vars` with `[{"key":"PORT","value":"80"},{"key":"QA_A","value":"two"}]` | 200 | `dep-dbcs20kttgas739mhsp0` (07:53:38Z) |
| `PUT /v1/services/<id>/env-vars/QA_B` with `{"value":"three"}` | 200 | `dep-dbcs26nt16hs73ajmbvg` (07:54:02Z) |
| `DELETE /v1/services/<id>/env-vars/QA_B` | 204 | `dep-dbcs2f7t16hs73ajmc0g` (07:54:36Z) |

## Expected

The three REST verbs (and Render's secret-file `PUT` and `DELETE` verbs, which follow the same rule) store the change and deploy nothing. The next deploy (`POST /v1/services/{id}/deploys`, `bex deploys create`, or an auto-deploy) uses the stored values. The service keeps running its current release until then, as with bex's own `save_only` mode. A restart keeps the running configuration, per [render.com/docs/deploys](https://render.com/docs/deploys): "if you've recently updated your service's environment variables but haven't redeployed since then, restarting does _not_ incorporate those changes". Check bex's restart against that too.

## Root cause

`lego/backend/internal/secrets/service.go:1081–1089` `materializeEnv` projects the Secret and calls `bumpRestart` (stamps `spec.restartedAt`), so the pods roll on the next reconcile. `SetEnvVars` (`:480`), `SetEnvVar` (`:560–598`) and `DeleteEnvVar` (`:607–636`) all call it. The comment at `:1093–1095` says: "The older single-item verbs keep calling materializeEnv and retain their immediate-roll behavior." Secret-file item writes do the same (`secrets/files.go:697`, "materializeFiles layers the legacy immediate rollout"). The batch path (`secrets/batch.go`, `SaveModeOnly`) already implements the no-rollout behavior.

## Fix

Route the Render-shaped REST verbs through the batch path with `save_only` semantics:

- `PUT /env-vars`;
- `PUT` and `DELETE /env-vars/{key}`;
- the secret-file `PUT`, item `PUT` and item `DELETE`.

Each projects the configuration for the next release without `bumpRestart`. Keep the explicit `deploy` and `rebuild` modes for surfaces that ask for them: GraphQL, MCP `update_environment` and the dashboard's three-button save. Make sure the service's "pending configuration" state is visible, as it already is for `save_only` (w4/m239's pending-deploy signal), so an owner can see that the stored values differ from the running release. Update ADR018's env-vars and secret-files rows and ADR013.

## Blast radius

REST env-var and secret-file writes for every service type. Callers that relied on the immediate roll, such as bex's own CLI-free scripts and the dashboard if it calls REST rather than GraphQL, must trigger a deploy explicitly. Check `dashboard/` and any internal callers before switching. Env-group content writes are a separate contract: Render redeploys linked auto-deploy services on dashboard group edits; settle the API group-edit behavior against a capture.

## Acceptance

- Unit: each REST verb stores the values and leaves `spec.restartedAt` and the active release unchanged. A subsequent deploy runs with the new values.
- Live after deploy: repeat the table. No new deploy appears after any write, `GET /env-vars` shows the stored values, and `bex deploys create` then rolls once with them. Delete by ID with a 404 proof.

## Dedupe

`git grep -i 'roll immediately|immediate-roll|legacy item' .pm`: no open item. w4/m239 (done) made env-group link, unlink and delete wait for the next deploy on Auto-Deploy-off services; it did not change service env-var writes.
