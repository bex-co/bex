# Lift the three signed-off edge-compression differences once Traefik can

Why: w8/m83 ships gzip-only Traefik `compress` with three ADR018 differences from Render the user signed off on 2026-10-31 — `no-transform` responses are compressed, a strong `ETag` stays strong on the gzip body, and Brotli is off because Traefik v3.7.5's Brotli writer encodes ≥ 1 KiB `206` bodies. Each lifts as soon as upstream allows it.

Severity: **minor** (performance/HTTP-semantics edge cases; content is exact). Attribution: platform edge (Traefik). Estimate: ~30m per lift once an upstream release exists; tracking only until then. Filed 2026-10-31 from w8/m83.

## What would lift each

- **Brotli:** a Traefik release whose Brotli writer skips partial (`206`/`Content-Range`) responses, as its gzip writer does → add `br` first in `edgeCompressionMiddlewares` (`lego/operator/internal/controller/edge_compression.go`); the `large range untouched` row of `TestEdgeCompressionOnTheDeployedTraefik` must still pass.
- **no-transform / strong ETag:** a `compress` option for either, or a traefik/yaegi composed writer that keeps `http.Flusher` so the saved `bexCompressGuard` design ([attempt](m83/evidence/edge-compression-attempt/README.md)) no longer buffers streams.

## How to check

On each Traefik bump, rerun `BEX_TRAEFIK_INTEGRATION=1 go test ./internal/controller -run TestEdgeCompressionOnTheDeployedTraefik` with `br` enabled, and read the release notes for `compress` options. Opening upstream issues/PRs needs the user's authorization (external publication).
