## Objective

Make acknowledgment mean that eligible automatic Blueprint work is durable, while preserving the existing signed-delivery replay protection and App behavior.

## Context

- Parent milestone: [w8/m38 — Resource-independent Blueprint auto-sync](README.md), user-approved on 2026-09-08.
- Current auto-sync is an unpersisted goroutine launched around the webhook response; a process exit can lose the work.
- store/gitwebhook.go and apps/webhook.go already implement signed-body replay claims. Blueprint intent must compose with those claims rather than bypass them or duplicate App redeploys.

## Steps

1. Persist the minimum workspace/Blueprint/generation/source/delivery identity needed to execute or diagnose the accepted run, using existing store transaction patterns.
2. Enforce one logical intent per verified delivery and Blueprint; bind identity to the existing authenticated replay key rather than a freely replaceable header alone.
3. Make durable acceptance part of successful acknowledgment. Handle enqueue failure without acknowledging lost work or repeating App mutations on a retry.
4. Add appropriate indexes and bounded admission/retention behavior; do not persist credentials or unnecessary webhook/source bodies.

## Acceptance criteria

- [ ] Killing the process immediately after a successful acknowledgment leaves a discoverable pending intent.
- [ ] Duplicate delivery, including across replicas/restarts, creates one logical Blueprint intent.
- [ ] Enqueue failure is not acknowledged as accepted work; existing App mutations do not repeat because Blueprint persistence failed.
- [ ] Invalid signatures, foreign scope, and no-target deliveries allocate no Blueprint intent.
- [ ] Stored acceptance data excludes tokens and unnecessary secret-bearing payloads.

## Out of scope

- Exactly-once guarantees for arbitrary external apply effects.
- Replacing the existing Git webhook replay mechanism or adding an external queue service.
