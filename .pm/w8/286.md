# A build whose image upload hits a registry error prints skopeo's raw retry lines to the tenant's build log, naming the cluster-internal registry host and its in-cluster IP

Why: bex keeps platform internals out of what a tenant reads. A build that fails for an infrastructure reason gets guidance instead of its output tail, because that tail "names registry endpoints and platform components" (`lego/operator/internal/controller/build_failure.go:87-89`). w4/m236 removed `zot.bex-registry.svc:5000` from deploy rows and events, and w6/m123 and w6/084 removed the build Job's text and the scheduler's verdict. The build log stream was not covered. When an upload retries, the tenant reads skopeo's own log lines, with the registry's cluster DNS name, its in-cluster address and port, a blob digest, and `level=warning` / `level=fatal`, followed by a silent rerun of the whole build.

**Severity:** minor (information exposure of cluster-internal names and addresses; no credential is printed, and the build recovered on its own). **Attribution:** platform build plane (operator build Job push phase). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `81af`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `3d66946c9e16`, workspace `bex-canary`, QA human device login.

## Evidence

A free native Rust web service (`qa-20261112-81af-env-rust`, `bex-co/bex`, root directory `examples/runtime-version/python`, a build command that prints a few variables). Deploy `dep-dbqo7hq6krac73d83hag`, read afterwards with `bex logs -r <srv> --type build --start 2026-11-12T09:31:00Z --direction forward -o text`. Times are UTC. Nothing tells the reader that the first attempt failed or why the build starts over. The deploy went on to `update_in_progress`; its `failureReason` was never set. The same service's earlier builds in this sweep (four of them) printed no registry lines, so the text appears only when an upload retries or fails.

## Expected

- No build log line contains a cluster-internal host (`*.svc`, `*.cluster.local`), an in-cluster address, or a raw tool log record. This is the rule w4/m236 set for deploy and event surfaces, and the rule `build_failure.go` already applies to a failed build's message.
- A retried or failed upload reads in product terms, in Render's `==>` voice. For example: `==> Uploading build failed: the build registry could not be reached; retrying` after each failed attempt, and before a Job rerun `==> Retrying the build (attempt 2 of 2): the image upload failed`.
- Render documents no wording for this. The claim rests on bex's own rule, not on a Render string.

## Root cause

- A native build's push phase runs `skopeo "$@" >/dev/null || exit $?` (`nativePushNarration`, `lego/operator/internal/build/build.go:251-255`). stdout is dropped, and stderr reaches the build log as is. The comment says so on purpose: "its errors still reach the log on stderr".
- A Dockerfile build's push phase is a bare `skopeo` command with no wrapper (`build.go:1359-1371`), so its stdout transcript and its stderr both reach the log (not run in this sweep).
- skopeo's `--retry-times 3` (`build.go:1365`) logs each retry as a `level=warning` record. The final `level=fatal` exits non-zero, and the Job's `backoffLimit` (2 attempts, `buildPodFailurePolicy`, `build.go:1770-1803`) reruns the whole pod.
- The deploy-level message is already safe. Two failed attempts end as `BackoffLimitExceeded` → `FaultInfra` (`lego/types/v1alpha1/jobnames.go:103-114`), whose message carries guidance instead of the tail (`build_failure.go:83-90`). Only the live log stream leaks.
- The cache phases (`cacheBestEffort`, `cacheRestoreBestEffort`, `cachePurgeBestEffort`, `build.go:1505-1519`) pass skopeo's stderr through the same way. No cache line appeared in this sweep's builds, so whether those containers' logs reach the tenant was not established.

## Fix

1. Wrap every skopeo invocation in a build Job (native push, Dockerfile push, cache restore, save and purge) so its stderr goes to the operator's log, or into a file the phase reads, and never to the tenant stream. Print one product line per failed attempt instead, with no host, address or digest. Keep the raw text available to operators (the container's own log in the build namespace, or a `logf` line from `failureDetail`).
2. Before a Job's second attempt starts its build, say so in the log, so a tenant does not read the same build twice without explanation.
3. Add a test on the push-phase scripts: given a skopeo stderr naming `zot.bex-registry.svc:5000` and an address, the tenant-visible output contains neither.
4. Amend the w4/m236 rule where it is recorded (ADR028's lineage or ADR018's build-logs row) to name the build log as a covered surface.

## Acceptance

- A native build whose first upload attempt is refused (on the mock cluster, scale the registry to zero for ten seconds during the push) prints no `zot.`, `.svc`, IP address, `level=` or `msg=` text in `bex logs --type build`, and prints the product line instead.
- The same for a Dockerfile build.
- A clean build's log is unchanged.

## Unverified

- The Dockerfile push phase's output on production; the code says it is unwrapped.
- Whether the cache phases' stderr reaches the tenant stream.
- Why the registry refused connections for at least 11 s (09:35:02–09:35:13). A registry restart for a new service's credential is the leading candidate (w4/m347); this sweep cannot see the cluster.

## Dedupe

- w4/m236 (done) took the internal registry host out of deploy `image.ref` and event `details.image`. The build log was not in its scope.
- w4/582 (done) moved native builds' `Build successful` after the push, and sent skopeo's per-blob transcript to `/dev/null`, leaving stderr in the log.
- w6/m123 and w6/084 (done) cover the build Job's text and the scheduler's verdict.
- w4/m347 (todo) is the registry restart itself, and what it does to in-flight pushes. It is not about what a tenant reads.
- Searched `.pm` for `zot.bex-registry.svc` with "build log", and for `pinging container registry` and `level=warning msg`: no other item.

## Cleanup

The service was deleted; `GET /v1/services/<id>` answers 404.
