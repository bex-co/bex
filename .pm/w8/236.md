# pg_duckdb segfaults Postgres in a database that also has TimescaleDB

Why: on PG 16/17/18, Render offers both `pg_duckdb` and `timescaledb` and documents no restriction on using them together. In a bex database where both exist, any query DuckDB executes against a Postgres table segfaults the backend, and Postgres restarts the whole instance. That is a customer-triggerable outage of their own database, and it diverges from what Render's docs promise. w8/234 found it and recorded it in [ADR092](../../docs/ADR092-postgres-extension-supply.md) as a known upstream limitation. This note owns the fix.

- **Root cause:** pg_duckdb v1.1.1 `PostgresTableReader::InitUnsafe` (`src/scan/postgres_table_reader.cpp:66`) calls `standard_planner()` directly and skips `planner_hook`, which is where TimescaleDB 2.31 initialises its per-query hash table. TimescaleDB's relation hooks still fire, and `ts_classify_relation` dereferences the uninitialised state. This is [duckdb/pg_duckdb#845](https://github.com/duckdb/pg_duckdb/issues/845), open since 2025-06. #846 was proposed and did not resolve it, and a community fork carries a patch (lnicho/pg_duckdb#1).
- **Reproduce:** published PG16 arm64 operand `ghcr.io/bex-co/bex-operator@sha256:61599a12d43d2f0109c57465610f9b9638ef47a3dfdb284034b455363514b4db`. Preload `timescaledb,pg_duckdb`, then `CREATE EXTENSION timescaledb; CREATE EXTENSION pg_duckdb; CREATE TABLE t AS SELECT generate_series(1,1000) v; SET duckdb.force_execution = true; SELECT sum(v) FROM t;` → SIGSEGV. The gdb backtrace runs `ts_classify_relation` ← `standard_planner` ← `pgduckdb::PostgresTableReader::InitUnsafe`.
- **Options:** (a) adopt an upstream pg_duckdb release that plans through `planner()` once #845 is fixed, or (b) build pg_duckdb in `deploy/pg-operand/Dockerfile` from the reviewed v1.1.1 source with that one-line change, reusing upstream's `libduckdb.so`. (b) changes the image's supply chain (a from-source build on the amd64-emulated runners) and likely exceeds an hour; promote it if taken. Either option should make `check.sh` run the forced DuckDB scans back in `appdb` next to TimescaleDB and drop the separate `duckdb_scans` database, then remove the ADR092 limitation.
- **Do not:** refuse `CREATE EXTENSION` for the combination as the fix. Render allows both, and a refusal is a new divergence that needs ADR018 sign-off.
