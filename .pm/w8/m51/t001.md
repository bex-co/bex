## Objective

Write down which toolchain lines bex offers per native runtime and exactly how a requested version maps onto one, so the rest of the milestone implements a recorded decision rather than an improvisation.

## Context

- `lego/operator/internal/build/native.go:78-85` — today's single pin per runtime.
- `docs/ADR060-*.md` D7 + `lego/operator/internal/build/toolchain-freshness.json` — reviewed digest inventory and weekly freshness workflow.
- Render docs: render.com/docs/python-version, /node-version (precedence in the milestone README); read the Go, Ruby, Rust and Elixir pages for their mechanisms (e.g. `go.mod` `go`/`toolchain`, `.ruby-version`/`Gemfile` `ruby`, `rust-toolchain(.toml)`, `.tool-versions`).

## Steps

1. Pick the supported lines per runtime (for example, Python 3.10–3.14, Node 20/22/24/26, Go the two latest minors, and so on). Weigh freshness-review cost against coverage.
2. Define resolution. Map a fully-qualified request (`3.11.9`) onto its minor line, not the exact patch. State that divergence from Render explicitly. Node semver ranges resolve to the highest supported line satisfying the range. `lts` resolves to the current LTS line. Anything outside the set is a named build failure, never a fallback.
3. Record the decision in ADR060 (D7 addendum) and ADR018 (native runtime row), including the patch-level divergence.
