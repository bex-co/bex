# 054 — Blueprint refusal messages ignore the registry's recorded reason: `postgresMajorVersion: "10"`–`"12"` says "uses an unsupported Render Blueprint value", and a cron's `preDeployCommand` says "is not available on bex"

Why: the value is valid Render (`"10"`–`"18"`); bex just doesn't provision below 13. The Blueprint error blames the author's Render syntax and gives no next step. The create API for the same request says exactly what to do, and the capability registry already stores the right reason.

Severity: minor. Attribution: server (`lego/backend/internal/apps/blueprint_compiler.go`).

## Evidence (2026-10-05, `/qa-find-bugs-cli` w8 loop, sweep 14)

Production pin `8f58b933d`, `bex v0.2.1` (pin Render CLI v2.27.0), workspace `bex-canary`, human device login. Validate only (no fixtures).

```text
$ cat db10.yaml
databases:
  - name: qa-bp14-db
    plan: free
    postgresMajorVersion: "10"          # same for "11" and "12"
$ bex blueprints validate db10.yaml -o json
{"valid":false,"errors":[{"path":"databases[0].postgresMajorVersion","error":"postgresMajorVersion uses an unsupported Render Blueprint value", …}]}   # exit 1
$ bex postgres create --name qa-r14-pg12 --plan free --version 12 --confirm -o json     # control: API path, nothing created
Error: received response code 400 (POSTGRES_VERSION_UNKNOWN): PostgreSQL version "12" is not supported; choose one of 13|14|15|16|17|18
```

`"13"` validates clean. Every other unsupported enum value probed gets a tailored message: `region: oregon` → `per-resource region placement is not available on bex`; `previews.generation: automatic` → `preview environments are not available on bex`. Only `postgresMajorVersion` reaches the generic fallback.

Sweep 15, same pattern on the field-level path: a `type: cron` with `preDeployCommand: echo hi` → `services[0].preDeployCommand: preDeployCommand is not available on bex`. That is misleading, since bex runs pre-deploy commands for web, private and worker services. The registry's reason for this exact pointer is `cron jobs do not run the App pre-deploy phase, so accepting this command would silently ignore it`. The static-site `preDeployCommand` pointer has the same shape.

## Mechanism

- `lego/backend/internal/apps/schema/capabilities.json` `enumValues["#/definitions/database/properties/postgresMajorVersion/enum"]` marks `"10"`/`"11"`/`"12"` `unsupported` with `reason: "bex supports PostgreSQL 13 through 18; lower upstream versions cannot be provisioned"`.
- `lego/backend/internal/apps/blueprint_compiler.go:220-223` reports the refusal through `blueprintUnsupportedEnumMessage(field, enumPointer)` (`:665-677`), which has cases for plans, `autoDeployTrigger` and the workflow enums only. `postgresMajorVersion` falls to `fmt.Sprintf("%s uses an unsupported Render Blueprint value", field)` and the registry `reason` is never consulted.

- Field-level twin: `blueprint_compiler.go:647-663` `blueprintUnsupportedCapabilityMessage` falls back to `"%s is not available on bex"` for every pointer without a hand-written case, including `#/definitions/cronService/properties/preDeployCommand` and `#/definitions/staticService/properties/preDeployCommand`.

## Fix

Add a `postgresMajorVersion` case producing the API's wording, `PostgreSQL version "12" is not supported on bex; choose one of 13|14|15|16|17|18`. Derive the list from the same source the API uses (`POSTGRES_VERSION_UNKNOWN`), not a hand-copied literal, so the two can't drift. Make **both** generic fallbacks (field and enum) use the registry entry's `reason` when one exists, so a newly classified pointer is explained by default. Optionally name the offending value too. Pass the value through, since `blueprintEncodedValue(child)` is already computed at the call site.
