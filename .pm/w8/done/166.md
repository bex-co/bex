# `POST /v1/blueprints` answers 400 after it has already created the Blueprint, leaving an auto-syncing connection the caller never learns about

Why: when a new Blueprint's first apply fails (for example on w8/165's `rootDir: ./`), the create endpoint returns the apply error as a 400 with no Blueprint in the body. The Blueprint row, its failed sync and its `autoSync: true` are already committed. An API, MCP or automation client reasonably reads 400 as "nothing was created", so it does not delete anything. It is left with a hidden connection that re-syncs that repository on every push, and a retry of the same create collides with or silently revives it (w8/m37 revive).

**Severity:** minor (orphaned, auto-syncing resource behind an error response). **Attribution:** server (Blueprint create response contract). **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1283, 2026-10-21 ([evidence](evidence/cli-sweep1283/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `a3f66521f93d`, bex-canary.

1. `POST /v1/blueprints {"name":"qa-20261021-a71be8-vsort","ownerId":"tea-daif693dqjvc73e7as3g","repo":"https://github.com/Davender-1565/VisualSort","branch":"main"}` → `400 {"error":"service \"visual-sort\": bad request: rootDirectory must be a relative path with no '..' components","id":"bad_request",…}`. There is no `id` in the body.
2. `GET /v1/blueprints?ownerId=…` lists `blp-dbca9be03oos73cqinu0` "qa-20261021-a71be8-vsort", `status: error`, `autoSync: true`, `lastSync: 2026-10-21T11:40:29Z`. Its sync `bsr-dbca9be03oos73cqinug` has `state: error` and the same message.
3. It was deleted by ID (204, then GET 404).

## Expected

Pick one contract and apply it to REST, GraphQL `createBlueprint` and MCP:

1. **Created-with-error (Render's dashboard model, recommended):** a Blueprint whose initial sync fails still exists. Return `201` with the Blueprint (`status: error`, the failed sync's message, `resources: []`), so the client has the ID to fix, re-sync or delete it. Optionally create it with `autoSync: false` until the first successful sync.
2. **Atomic:** run every apply-time validation before admission (the validate endpoint already reports this error), and on an apply failure roll back the row so that 400 truly means "nothing exists".

The validate endpoint reports the rootDir error, while create's pre-admission checks (`compileStack`, billing, `blueprintActionPlan`) miss it. That gap is how a known-bad manifest reaches admission.

## Root cause

`lego/backend/internal/apps/blueprint.go:1141–1194`: `AdmitBlueprintCreate` persists the Blueprint (`AutoSync: true`) and a running sync. `deployParsedStack` then fails, and `completeAdmittedSync` (`:1206–1226`) records the error and returns `applyErr`. `CreateBlueprint` propagates it as the HTTP error, dropping the admitted `b`.

## Fix

For option 1, when `applyErr` is a tenant-input error, return `toBlueprintView(updated)` with the sync error attached and a `201`. Keep 5xx for platform failures, and keep the row in that case too, because its sync history explains the failure. For option 2, add the per-resource create validation used by `blueprints/validate` to the pre-admission checks. Either way, document the contract in ADR049.

## Acceptance

- Handler tests: a manifest whose apply fails returns either 201 with `status: error` and a non-empty sync error (option 1) or 400 with no row left behind (option 2). REST, GraphQL and MCP agree.
- Live after deploy: repeat step 1. The response either carries the Blueprint ID, or `GET /v1/blueprints` shows no new row. Clean up by ID with a 404 proof.
