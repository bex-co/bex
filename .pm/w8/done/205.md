# A multi-port Docker web service publishes its lowest declared port, not its HTTP port: Render's RabbitMQ template goes `live` on epmd (4369) and its URL answers 502, where Render exposes the HTTP management port

Why: Render's [RabbitMQ guide](https://render.com/docs/deploy-rabbitmq) for `render-examples/rabbitmq` sets no `PORT`. It says: "Render automatically discovers all available ports on your RabbitMQ service and only exposes the HTTP management port outside your private Render network … the RabbitMQ management interface will be available on your .onrender.com URL". Since w4/m243, bex picks a Docker web service's public port from the image's `EXPOSE` set with ADR089's private-service rule: explicit port, else 3000, else the **lowest** declared port. ADR089 L108 itself says this is "a Bex policy, not a claim about Render's algorithm". For an image whose lowest port is not HTTP, the TCP health check passes, the deploy reports `live`, and every public request returns 502.

Severity: **major** (an official Render template deploys "successfully" but its URL never works, and nothing tells the user why). Attribution: platform runtime (operator image-port selection for web services). Estimate: **> 1h** (HTTP-aware selection, tests, docs, live check); promote to a milestone if it splits. Source: `/qa-find-bugs-cli` loop sweep 5dba, 2026-10-26 (10:42–10:55 UTC). Context: HEAD-built bex `b4726243e` with pinned Render CLI v2.27.0 `a764810a7682`; `https://api.bex.co/v1/`; workspace `bex-canary`; human device login.

4369 is Erlang's epmd, a binary protocol, so the edge's HTTP request to it fails. The fixture was deleted by ID (`GET` 404). This was a free plan without Render's disk, which affects only persistence.

## Root cause

- `lego/operator/internal/controller/image_network.go:140` takes `primary := ports[0]` (the sorted declared TCP ports), overridden only by a declared 3000 (`imagePortPreferred`, `:49`) or a configured port/`PORT`.
- That is ADR089 § Port slice decisions rule 3 (`docs/ADR089-render-container-compatibility.md:108`, `:192–196`). It was designed for private services (ClickHouse: 8123/9000/9009), and w4/m243 (ADR089 L179) applied it unchanged to web services.
- Web services also skip runtime detection when image ports exist (`port_detect.go`, `HasImagePorts()`), so nothing corrects the choice.
- The TCP startup check passes on any accepting port, so a non-HTTP primary looks healthy.

## Fix

For a **web** service in an image-port mode (`web-image-v1`) with no explicit port and no `PORT`, choose the public port the way Render describes: the port that speaks HTTP.

- When the first release's container is running, probe each declared TCP port (and, if none answer, the listening set from `portscan`) with a bounded HTTP/1.1 request (`GET / HTTP/1.1`, `Host: <platform host>`, ~1 s). Choose the lowest port that returns a parseable HTTP status line (any status code).
- Keep the current rule (3000 if declared, else lowest) as the fallback when no port answers HTTP, and keep private services on ADR089's rule unchanged.
- Record the choice in `status.imageNetwork.primaryPort`, as today, so reads, `openPorts`, addresses and Blueprint references follow it (ADR089 D4). The other declared ports stay private, as on Render.
- Decide once per image digest, consistent with ADR089 L109 ("Do not silently select another port because the primary became unhealthy"). A later release with the same digest reuses the decision.
- Name the chosen port in the deploy log ("Detected HTTP on port 15672; serving it"), and when no port speaks HTTP say so in the stall text.
- Docs: amend ADR089 rule 3 for web services, ADR018 row 104 (Open ports), and the w4/m243 note.

## Blast radius

- New Git-built Docker and prebuilt-image **web** services whose image declares several TCP ports with a non-HTTP port lowest: RabbitMQ (4369), Elixir/Erlang releases with epmd, images with metrics or admin ports below the app port.
- Single-port images and images declaring 3000 are unaffected. Private services are unchanged.
- Existing web services keep their recorded primary unless redeployed with a new digest. Decide whether to re-evaluate on the next deploy and note it in the milestone.
- REST/GraphQL/MCP `port`/`openPorts`, the dashboard Connect panel and `RENDER_*` URLs read the recorded primary, so there are no API changes.

## Regression checks

- Unit tests for the selection:
  - {4369 TCP-only, 5672 TCP-only, 15672 HTTP} → 15672;
  - {80 HTTP, 443 TLS} → 80;
  - {8080 HTTP} → 8080;
  - none HTTP → lowest (unchanged);
  - declared 3000 HTTP → 3000;
  - explicit port or `PORT` → unchanged;
  - private service → unchanged.
- Live: recreate the RabbitMQ fixture above with no `PORT`. It goes live with `serviceDetails.port 15672`, `/` returns 200, and the deploy log names 15672. A single-port nginx image still serves on 80. Delete fixtures by ID with 404 proofs.

## Unverified

- Render's exact algorithm (whether it prefers HTTP, the lowest HTTP port, or something else); the guide states only the outcome for this image.
- Whether 15691/15692 (Prometheus, HTTP) start before 15672 in practice. The rule "lowest HTTP port" picks 15672 either way.
