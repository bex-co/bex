2026-10-16: implemented.

**The change.** Primary Ruby images carry Render's Bundler settings before the build RUN:

- `BUNDLE_DEPLOYMENT=true`;
- `BUNDLE_PATH=/opt/render/project/.gems`;
- `BUNDLE_BIN=/opt/render/project/.gems/bin`, with that bin directory first on `PATH`.

They apply to the build, pre-deploy and runtime, and a service's own value wins in each phase.

**Why the path settings too.** Review showed that deployment mode alone installs into the app's `vendor/bundle`. That would leak gems into a root-publishing static site or a Jekyll build, and break bare `puma`/`rails` commands. So Render's gem directory and binstubs come along.

**Gate.** `TestNativeRubyImageBundlerDeployment` runs real Bundler 2.6.9 on Ruby 3.4:

- a matched lock installs outside the source tree and serves rake 13.3.1 through `bundle exec` and a bare `rake` binstub (the image's own is 13.2.1), with the lock unchanged;
- a stale lock fails ("frozen"), and so does a missing lock;
- a service's `BUNDLE_DEPLOYMENT=false` or `BUNDLE_FROZEN=false` re-resolves a stale lock;
- a service's own `BUNDLE_PATH` is honoured.

**Other checks.**

- Placement is verified on every Ruby line and for an explicit Ruby static build.
- Fail-before: without the default, the stale and missing cases built.
- The Rails gate (114) and the m85/JS-tool Ruby gates still pass; the Rails fixture now locks at build because it commits no lock.

**Not covered.**

- Bundler on Ruby 3.3 (2.5) and 4.0 (4.x) is not executed.
- Pre-deploy and Secret-file overrides share the image-ENV mechanism and are not separately executed.

The behaviour change (a current Gemfile.lock is required) is recorded in ADR060.
