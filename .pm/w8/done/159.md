# Render's official Django example cannot build on bex because bex sets no `RENDER` variable, and would run with `DEBUG=True` if it did build

Why: ADR018:137 decided that bex injects no `RENDER_*` defaults ("a deliberate divergence … since they name a competitor's platform"). Render's own Django example and guide detect production with `DEBUG = 'RENDER' not in os.environ` and add `RENDER_EXTERNAL_HOSTNAME` to `ALLOWED_HOSTS`. On bex that makes `DEBUG` true, so `STATIC_ROOT` is never set and `collectstatic` fails the build. If the build were changed to pass, the site would run in Django debug mode, with an `ALLOWED_HOSTS` that rejects its own public host. The decision has a concrete cost: Render's flagship Python quickstart does not build, and the obvious workaround ships debug mode to the internet. This note asks for the decision to be revisited with that evidence. It is not a silent re-file.

**Severity:** major (Render's official Django example fails; the failure mode leans toward exposing debug pages). **Attribution:** platform runtime policy (ADR018:137). **Decision needed:** yes. **Estimate:** 30–60m once decided. **Source:** `/qa-find-bugs-cli` sweep 1274, 2026-10-21 ([evidence](../evidence/cli-sweep1274/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `9cace6b6e25d`, workspace `tian-personal`. The Blueprint is `https://github.com/render-examples/django`, and its `mysite/settings.py` contains:

```python
DEBUG = 'RENDER' not in os.environ
ALLOWED_HOSTS = []
RENDER_EXTERNAL_HOSTNAME = os.environ.get('RENDER_EXTERNAL_HOSTNAME')
if RENDER_EXTERNAL_HOSTNAME:
    ALLOWED_HOSTS.append(RENDER_EXTERNAL_HOSTNAME)
```

`STATIC_ROOT` is assigned only under `if not DEBUG:`. With `PYTHON_VERSION=3.12.11` set (an unrelated psycopg2 pin issue), the build's `python manage.py collectstatic --no-input` failed:

```
django.core.exceptions.ImproperlyConfigured: You're using the staticfiles app without having set the STATIC_ROOT setting to a filesystem path.
```

Setting `RENDER=true` and `RENDER_EXTERNAL_HOSTNAME=mysite.onbex.co` by hand cleared it. With migrations moved to pre-deploy ([w8/158](../158.md)), the service went `live`: `/` 200, `/admin/login/` 200, unknown path a production 404 (not a debug page). Resources were deleted (204 → 404).

## Expected

Render's [default environment variables](https://render.com/docs/environment-variables) include `RENDER` ("always `true`. Your code can check this value to detect whether it's running on Render"), `RENDER_EXTERNAL_HOSTNAME`, `RENDER_EXTERNAL_URL`, `RENDER_SERVICE_ID`/`NAME`/`TYPE`, `RENDER_GIT_*`, `IS_PULL_REQUEST` and others; most are available at both build and runtime. Render's Django quickstart is written against them.

## Root cause

`lego/operator/internal/controller/app_controller.go:5056–5076` `appEnv` injects only `PORT`, and the native build bundle carries only the user's variables. ADR018:137 records this: "bex does not inject `RENDER_*` equivalents — a deliberate divergence, not an omission, since they name a competitor's platform."

## Fix (decision first)

1. **Inject Render's documented defaults** at build and runtime, at the lowest precedence so any user value wins: `RENDER=true`, `RENDER_EXTERNAL_HOSTNAME`/`RENDER_EXTERNAL_URL` (web and static only, otherwise empty), `RENDER_SERVICE_ID`, `RENDER_SERVICE_NAME`, `RENDER_SERVICE_TYPE`, `RENDER_GIT_BRANCH`/`RENDER_GIT_COMMIT`/`RENDER_GIT_REPO_SLUG` (Git-backed), `RENDER_INSTANCE_ID`, `IS_PULL_REQUEST=false`. `PORT` stays reserved. This is the same compatibility bex already gives Render's API, CLI, `render.yaml` filename and `Rndr-Id` header (w8/m125). Pair it with w8/155 (Blueprint references to the same names).
2. **Inject bex-named equivalents only** (`BEX=true`, `BEX_EXTERNAL_HOSTNAME`, …). This keeps the naming decision, but Render apps stay broken.
3. **Keep the decision**, and add a Blueprint plan warning when a repository's code is likely to depend on `RENDER` (out of reach for the compiler). Record in ADR018 that Render's official Django example does not build.

Option 1 is recommended. The naming objection already gave way for `render.yaml`, `Rndr-Id` and the Render CLI protocol, and only option 1 makes Render's own quickstarts run.

## Acceptance

- One decision recorded in ADR018:137.
- For option 1: operator tests show the defaults in the runtime env and the native/Dockerfile build env, and a user-set `RENDER_EXTERNAL_HOSTNAME` overrides the injected one. Live: `render-examples/django` (with `PYTHON_VERSION` set and migrations handled per w8/158) builds and serves `/` 200 without the manual `RENDER` variables. A request with a foreign `Host` gets Django's production 400, not a debug page. Delete the fixtures by ID with 404 proofs.

## Blast radius

Every App's runtime env and every native/Dockerfile build env (precedence lowest). Container env size grows by about 12 variables. Clones and exports must not persist the injected values as user variables.

## Dedupe

ADR018:137 (the decision itself; not modified by this note), w8/155 (`fromService.envVarKey: RENDER_*` references in Blueprints, a sibling), w8/m125 (`Rndr-Id`, a precedent for adopting Render's names). No item records that Render's official Django example fails.
