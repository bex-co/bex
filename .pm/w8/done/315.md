# `BUN_VERSION=1.3.0` builds and runs on Bun 1.3.14: bex maps an exact Bun version onto its reviewed line, where Render installs the exact version

Why: Render's [Bun version](https://render.com/docs/bun-version) page (read 2026-11-13) says a semantic version such as `1.4.4` "uses the exact Bun version specified for every deploy", and recommends it for most services. Render's own `render-examples/elysiajs-hello-world` Blueprint pins `BUN_VERSION: 1.3.0`. bex maps any `BUN_VERSION` or `.bun-version` version onto its major.minor line and installs that line's reviewed patch, so the service builds and runs on a different Bun than its owner pinned, and the build log reads `Using Bun 1.3`. w8/175 closed the same gap for `PYTHON_VERSION`, `NODE_VERSION`, Ruby and Elixir through the exact-image path; the Bun companion was left on line resolution.

**Severity:** minor (patch differs within the pinned line; a user who pins a patch to reproduce a known-good build gets another). **Attribution:** platform build (native version selection). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `f1a6`, 2026-11-13 UTC, released `bex v0.6.0` (Render CLI v2.36.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `1c4d721bc8dc`.

## Evidence

`bex ea blueprints create --repo https://github.com/render-examples/elysiajs-hello-world` then `bex ea blueprints approve`. The free web service `elysiajs-hello-world-qcpv` went live and served `Hello Elysia`. Its build log:

```text
==> Using Node 24 (default)
==> Using Bun 1.3 (from BUN_VERSION=1.3.0)
==> Running build command 'bun install'...
bun install v1.3.14 (0d9b296a)
```

Docker Hub has `oven/bun:1.3.0` (amd64 and arm64, `sha256:00cccad6e9c6…`), as it has `1.2.20` and `1.1.0`, Render's older dated defaults. The service and Blueprint were deleted (GET 404, URL 404).

## Root cause

- `lego/operator/internal/build/nativeversion.go:320-333` (`resolver.bunRequest`): a plain version with a dot maps to `minorLine`, so `1.3.0` becomes line `1.3`.
- `ResolveNativeBun` (`:236-239`) sets `NativeChoice.Exact` only for the floating `canary` tag (`resolver.choice`, `:379-384`). `exactRequest` (`:763`), which sets `Exact` for the primary runtimes, reads `nativeToolchains[runtime]` and is never applied to Bun (`nativeBun` is its own toolchain).
- `resolveNativeBunExact` (`nativeresolve.go:461-471`) already pins any `Exact` through `pinExactVersion`, and `bunRepo` (`oven/bun`) is already in `exactRepos` (`dockerhub.go:79`). `exactImage` maps `oven/bun:1.3@…` to `oven/bun:1.3.0`.

## Fix

Set `Exact` in `ResolveNativeBun` for a fully qualified `BUN_VERSION` or `.bun-version` (optionally `v` or `bun-v` prefixed) inside the chosen line that differs from the line's reviewed patch, sharing `exactRequest`'s rule by passing it the toolchain rather than the runtime name. `pinExactVersion` then installs the exact image by digest, the log reads `Using Bun 1.3.0 (from BUN_VERSION=1.3.0)`, and a missing tag or unreachable registry keeps the reviewed patch with a log line, as for the other runtimes. A lockfile-only opt-in, `latest`, a line (`1.3`) and `canary` are unchanged.

## Blast radius

Every native build that opts into Bun with an exact version (Bun is a companion on any native runtime, w8/m71). The runtime image carries the same Bun, so the fix applies to build and runtime alike. No API or dashboard change.

## Regression checks

- Unit: `BUN_VERSION=1.3.0` and `.bun-version` `1.3.0` resolve to `Exact` `1.3.0`; `BUN_VERSION=1.4.4` (the reviewed patch), `1.3`, `latest`, `canary` and a bare `bun.lock` keep today's choice.
- Live after the operator deploy: `render-examples/elysiajs-hello-world` logs `Using Bun 1.3.0` and `bun install v1.3.0`, and serves `Hello Elysia`.

## Resolution

**DONE 2026-11-13.**

- **Exact Bun:** `ResolveNativeBun` (`lego/operator/internal/build/nativeversion.go`) now sets `Exact` for a fully qualified `BUN_VERSION` or `.bun-version` (also `v` or `bun-v` prefixed) inside the chosen line that differs from its reviewed patch, through the same `exactRequest` rule the primary runtimes use (it now takes the toolchain). `resolveNativeBunExact` pins it through `pinExactVersion`: `oven/bun:1.3.0` by digest, narrated `Using Bun 1.3.0 (from BUN_VERSION=1.3.0)`. A missing tag or unreachable registry keeps the reviewed patch and says so. A line (`1.3`), a range, `latest`, `canary` and a lockfile-only opt-in are unchanged; the extra digest note stays canary's.
- **Tests:** `TestResolveNativeBun` gains an `exact` column (Render's elysiajs `1.3.0`, `bun-v1.3.0`, `.bun-version` `v1.2.21`, the reviewed patch, a line, a range, `latest`, `canary`, lockfiles). `TestResolveNativeBuildPinsAnExactBun` covers the pinned image, its narration and the `COPY`, and the missing-tag fallback. `TestNativeImageRunsAnOptedInBun` now expects Bun 1.3.4 at build and runtime, and `cmd/native-resolve`'s `TestRunNarratesAnOptedInBun` the `Using Bun 1.3.4` narration.
- **Real image:** the resolved Dockerfiles for `BUN_VERSION=1.3.4` on a node and a python base were built with BuildKit on this host and printed `bun runtime=1.3.4 built=1.3.4 requested=1.3.4` for both.
- **Docs:** ADR060's Bun companion paragraph records the exact install.
- **Production check after the operator rolls:** `render-examples/elysiajs-hello-world` logs `Using Bun 1.3.0` and `bun install v1.3.0`, and serves `Hello Elysia`.
