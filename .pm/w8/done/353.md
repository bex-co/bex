# A restart pulls the running release's image with the registry credential of a later failed deploy, so a service whose image switch failed cannot restart

Why: a restart is supposed to rerun the release that is serving (Render's Restart keeps the running configuration, w4/m433), but bex pulls that release's image with whatever registry credential the service's settings name now. One failed image switch with a bad or foreign credential then makes every restart of the healthy old release fail, and leaves the running instance one reschedule away from an outage.

- Severity: major. The failed deploy correctly leaves the old release serving, but its recovery verb (Restart) is broken until the user clears the credential, and anything that re-pulls the served image (a restart, an eviction or node drain, a wake on a node without the image cached) uses the wrong credential.
- Versions: production `https://api.bex.co/v1/` on 2026-11-20 15:14–15:25 UTC; bex CLI v0.7.0 (Render CLI pin `4fd34231b637`, v2.36.0); deployed revision not read.
- Context: routine `cli-qa` run `r14-f377`, QA human device-flow token, workspace `bex-canary`, `-o json`/`-o text`, non-TTY with `--confirm`. Fixtures (run-owned, deleted afterwards): fake Docker Hub credential `rgc-dc067g4d1ruc73b8crt0` (username `qa-fake-user`, a made-up token), free image web services `srv-dc067pkd1ruc73b8crug` and `srv-dc06aqkd1ruc73b8cs3g`.

## Repro (second fixture, never had a credential before)

  → dep-dc06aqkd1ruc73b8cs40 live in 46 s; https://qa-20261120-f377-img2.onbex.co/ → 200

bex deploys create <srv> --wait --confirm -o json

  → events: server_restarted, deploy_started, image_pull_failed (imageURL = the nginx digest), deploy_ended failed

The first fixture (`srv-dc067pkd1ruc73b8crug`) shows the same: served nginx with no credential, failed switch to the private image with the fake credential, restart `dep-dc069dcd1ruc73b8cs20` update_failed with the same Docker Hub 401 on the served digest. Public nginx needs no credential, so Docker Hub only refuses it because the fake credential was sent.

## Cause (traced; the operator pod path is read, not stepped through)

- A deploy trigger materializes the service's saved credential into its pull Secret and sets `spec.externalRegistryPullSecret` (`lego/backend/internal/deploys/service.go:944-999`). The Secret's name is one per App, `<app>-registry-pull` (`lego/types/v1alpha1/secretnames.go:48`), so it is not tied to a release.
- Restart selects the served release's record (`restartSelectedRelease` → `targetReleaseConfig`, `lego/backend/internal/deploys/rollback_config.go:46-85` and `:183`): image, port, shutdown delay and pre-deploy command. The release record (`ReleaseRecordSpec`, `lego/types/v1alpha1/releasesnapshots.go:101`) carries env, commands and replicas but no registry credential or pull Secret.
- The operator attaches `app.Spec.ExternalRegistryPullSecret` to every pod it builds, whatever release it is (`lego/operator/internal/controller/app_controller.go:2436-2451`). So the restarted served release pulls with the failed deploy's credential. The control matches: clearing the saved binding made the restart pass.

## Fix

Make the registry credential part of the release, as the image is:

1. Record the release's credential binding (the credential id, or "none") in its release record when it goes live, next to the image.
2. Give each release its own pull Secret content: a per-generation Secret name, or keep the served release's Secret untouched until the new release is live. Materialize the new credential under a new name at trigger time, and garbage-collect it with the release.
3. Restart and rollback select the target release's binding through `ReleaseConfigReference`, and the operator uses it for that release's pods instead of `spec.externalRegistryPullSecret`. A release recorded before this change keeps today's behavior.

If this turns out to be more than about an hour across backend, types and operator, promote it to a milestone.

Blast radius to check: rollback to an older deploy that used a different credential or none (same selection path, `targetReleaseConfig` with `restart=false`), Dockerfile builds whose `FROM` uses a credential (`registryCredentialApplies`), build-source carriers (`withLinkedSourcePullSecret`), the wake of a hibernated free service on a node without the image cached, and a credential whose token is rotated while a release serves (on Render a new pull would use the new token; keep that, since it is the same credential).

## Acceptance

In `bex-canary` with the CLI: create a free nginx image service with no credential and wait for live; `services update --image <nonexistent private docker.io image> --registry-credential <fake rgc->`; `deploys create --wait` fails and the URL keeps 200; then `bex restart <srv> --confirm` reaches live within about a minute with the served nginx digest, and the URL stays 200 throughout. Then the same with `POST /v1/services/<srv>/rollback` to the first deploy. A backend test pins that the restart's release config carries the served release's binding, and an operator test pins that a restarted served release's pods name the served release's pull Secret, not the spec's.

- Unverified: whether a saved-only `services update --registry-credential` (with no failed deploy in between) also breaks the restart; whether an eviction or wake of the served pod hits the same 401 (not forced on production); Render's own behavior was not probed (no Render account), the expectation comes from Render's documented Restart and bex's own w4/m433 reading of it.
- Dedupe: `rg -i 'restart' .pm | rg -i 'credential|pull secret|registry-pull'` finds nothing; w4/m301 (credentials apply only to services that select them), w4/599 and w8/m156 (served image retention) are about other things. `git log -S ExternalRegistryPullSecret --since=2026-11-10 -- lego` shows no fix in flight.
- Estimate: ~1h (backend selection + types + operator pod path + tests); promote if larger.

The fix is more than an hour across the types, the backend and the operator. Each credential needs its own per-App Secret, because one shared Secret lets a later trigger rewrite what the serving release pulls with. The release's binding has to reach Restart and rollback, which may be readable from the adopted spec records have held since w8/m121. The operator's pod, step Job and image-read paths need to use that binding. Tests are needed in both suites, and the production replay waits on a pin.
