## Objective

Make list and by-ID behavior agree after disconnect, and prevent ordinary get/update/sync calls from reactivating a disconnected record.

## Context

- Parent milestone: [w8/m37 — Blueprint lifecycle consistency](../README.md), user-approved on 2026-09-08.
- store.GetBlueprint and GetBlueprintByRepo currently read disconnected rows; ListBlueprints excludes them.
- SyncBlueprint can retrieve the old row and prepareSyncManifest upserts it back to syncing. The explicit CreateBlueprint path also uses UpsertBlueprint and must be treated deliberately.

## Steps

1. Reproduce disconnect followed by get, history read, update, and sync on the same ID across the shared core.
2. Separate active-resource lookup from any internal historical lookup; ordinary reads/mutations of a disconnected ID return the shared not-found behavior.
3. Keep re-establishment confined to explicit creation, with a fresh execution generation so an old queued job cannot regain authority.
4. Retain workspace ownership checks and safe foreign-ID behavior before any returned data or side effect.

## Acceptance criteria

- [ ] A disconnected Blueprint is absent from list and ordinary by-ID reads on REST, GraphQL, and MCP.
- [ ] Update and Sync using the old disconnected ID cause zero mutations and cannot restore active status.
- [ ] Any explicit creation over an existing source is deliberate, tested, and cannot revive old execution authority.
- [ ] Foreign/missing IDs remain safely scoped; deployed resources are retained.

## Out of scope

- Deleting deployed resources or exposing a new reconnect API.
- Purging retained internal history solely to make tenant reads absent.
