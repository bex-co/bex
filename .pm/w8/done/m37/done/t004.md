## Objective

Recover the lifecycle record after an API process dies so a Blueprint cannot remain running/syncing forever.

## Context

- Parent milestone: [w8/m37 — Blueprint lifecycle consistency](../README.md), user-approved on 2026-09-08.
- Only CreateBlueprint/runSync currently transition blueprint_syncs; no background recovery path settles abandoned running rows.
- w5/m85 is a reference for bounded, persisted recovery of interrupted work, not a reason to couple Blueprint execution to agent-session code.

## Steps

1. Define and persist the execution heartbeat/deadline needed to distinguish live ownership from an abandoned run.
2. Wire bounded, indexed recovery into the existing backend worker lifecycle; use independent cleanup contexts and per-tick limits.
3. After the deadline, mark an abandoned attempt as interrupted/error with a useful retry instruction, while preserving disconnected state and current generation.
4. Require an explicit new sync to retry a partially applied stack; recheck current authorization, billing, ownership, and source conditions.
5. Account for old/new replicas during rollout and existing stranded rows without marking a demonstrably live run abandoned.

## Acceptance criteria

- [ ] Simulated process loss after admission and during apply reaches an error state after the documented bound.
- [ ] A live healthy run is not falsely abandoned; recovery work is bounded per tick.
- [ ] Disconnected rows and newer execution generations cannot be overwritten by recovery.
- [ ] Retry requires a new valid attempt; ambiguous partial application is never automatically replayed or marked successful.
- [ ] Real-Postgres restart/concurrency evidence covers rollout and recovery failure paths.

## Out of scope

- Automatic replay of partially applied work without a separate idempotency proof.
- Sandbox recovery or a new external queue service.
