# Renaming a Blueprint-managed env group makes the next sync create a second group with the declared name, and link the services to both

Why: a dashboard rename is an ordinary edit of a Blueprint-managed resource ("You _can_ still make changes to a Blueprint-managed resource via other mechanisms", [infrastructure-as-code](https://render.com/docs/infrastructure-as-code)), but on bex the next sync forgets the group it created, mints a copy, and leaves both linked.

- Severity: minor to major, depending on Render's behavior. With both groups linked and the same keys in each, the newer copy's values win (the newest linked group wins on Render and bex alike). The renamed original then looks live, but any edit of it changes nothing at runtime.
- Source: the w8/381 worker checked the lead from routine `cli-qa` run 29 (2026-11-21, nonce `bf3e`; filed under w8/381's "Lead, not filed"). The finding comes from code on main `3b11c4b878`, not from a live run.
- Attribution: server, `lego/backend/internal/envgroups` and the Blueprint plan.

## What the code does

- `RenameEnvGroup` (`envgroups/service.go:819`) changes only the display name. The id, contents and links stay.
- Blueprint env groups are matched by name alone. The plan looks the declared name up in `GroupIDsByName` (`apps/blueprint_state_plan.go:99`, `:174-176`), and the apply uses `findGroupByName` (`ApplyEnvGroup`, `envgroups/service.go:1625`). After a rename both miss, so the plan shows `create` and the apply mints a new group with the declared name.
- `fromGroup` then links the service to the new group (`LinkEnvGroup`, `envgroups/service.go:1767-1782`, by name). Nothing unlinks the renamed one, so the service carries both.
- Env groups have no Blueprint claim. `store.BlueprintClaimKind` covers service, database, key_value and build_source only (`store/blueprint_resource_claims.go:33-38`), so nothing records that the renamed group was this Blueprint's.

## What Render does (not established)

- The [Blueprint spec](https://render.com/docs/blueprint-spec) says resources are named in the file ("If you add the name of an existing service to your Blueprint file, Render attempts to apply the Blueprint's configuration to that existing service"). It says nothing about a resource renamed outside the file, for env groups or services.
- First step: find out, from a Render workspace or Render support documentation. The candidates are: Render renames the group back on the next sync (it tracks the resource by id), or Render also creates a second group (name matching, as bex does).
- If Render tracks by id: give env groups a Blueprint claim keyed by id, so a sync matches the claimed group whatever its current name and renames it back. Check whether services renamed in the dashboard have the same gap, since service claims are keyed by name too (`BlueprintResourceKey{Kind, Name}`).
- If Render also creates a copy: record the parity in ADR018 and close.

## Render's behavior (researched 2026-11-21)

Nothing settles a resource renamed outside the file:

- Docs: "if any such changes conflict with Blueprint-defined configuration, the next Blueprint sync _overwrites_ them" and "If you delete a Blueprint-managed resource, Render recreates it the next time you sync" ([infrastructure-as-code](https://render.com/docs/infrastructure-as-code), also in `render.com/docs/llms-full.txt`). Nothing on renames, except read replicas.
- Pinned OpenAPI: `GET /blueprints/{blueprintId}` lists `resources[]` with `id`, `name` and `type`, `environment_group` included. `POST /blueprints/validate` takes no Blueprint id, so it can only match a workspace's resources by name.
- Community (archived copies; the forum's new host does not resolve): threads 5131 (2022) and 18289 (2024) describe name matching when a Blueprint is first created or first syncs ("Matching the names/types of the services will be detected when the Blueprint first syncs"). No staff answer about a rename.
- GitHub: several pull requests assert that Render matches by name, but they are agent-written assumptions, and none records a sync after a dashboard rename. One (`ericsaupe/scavenger-hunt#325`) ran the validate endpoint, which has no Blueprint context.

## Decision and fix (commit `f30ee69c89`)

No evidence settles it, so bex takes the behavior that never leaves a service linked to two copies, which also follows Render's overwrite rule: track the applied group by id and rename it back on sync.

- `blueprint_env_group_claims` (migration 0323): each sync records the groups it applied by id under their declared names. Not exclusive (two Blueprints may still share a group), replaced whole each sync, dropped on disconnect and with a deleted group.
- Plan: a renamed claimed group plans `update` with `changedFields: [name]` on its id; its variables and environment compare against that group. Apply: the sync renames it back (`envgroups.GroupRename`) before `ApplyEnvGroup`, so the services keep one link.
- A declared name another group has taken meanwhile is refused in the plan and the sync, naming both group ids. A deleted claimed group is recreated under its declared name.
- `resources[]` keeps listing the claimed group by id while it is renamed.
- Services: no change. Their file name matches `immutableName`, which a rename leaves alone, and the label is kept.
- Claims start at each Blueprint's first sync after the deploy. A group renamed before then is still matched by name.
- Recorded in ADR049 § Env groups renamed outside the file and the ADR018 Blueprint row.

Tests:

- `apps` `TestASyncRenamesItsEnvGroupBackInsteadOfMintingACopy`: plan `update name` on the original id, `resources[]` lists it, approve leaves one group named back and one link, re-plan `no_changes`.
- `apps` `TestASyncRefusesWhenItsEnvGroupsNameWasTakenMeanwhile`, `TestASyncRecreatesADeletedEnvGroupOnce`, `TestASyncAfterAServiceRenameKeepsTheService`.
- `store` `TestPGBlueprintEnvGroupClaims` (real Postgres): non-exclusive, replaced whole, same workspace only, cascades on group delete, released on disconnect.
