## Objective

Refresh the pinned upstream schema (`lego/backend/internal/apps/schema/render.yaml.json`, SHA-256 pinned in `blueprint_schema.go`, retrieved 2026-08-02) against the current `https://render.com/schema/render.yaml.json` (now also on SchemaStore), classify any newly appeared fields/enum values in `capabilities.json` (fail-closed `unsupported` by default per ADR049 D2), and verify the ADR049 "scheduled drift report" actually runs on a cadence — create it if it doesn't exist.

## Context

- Registry loader fails startup on any unclassified field, so a re-pin forces classification of everything new — that is the point.
- Known upstream additions since the ADR049 design window: `projects`/`ungrouped` (Oct 2025, already classified), validate API (Jan 2026, already implemented). Check for anything newer.
- ADR049's costs section promises "a scheduled drift report makes lag explicit, never auto-updates production" — confirm whether any CI workflow implements this.

## Steps

1. Fetch the current upstream schema; diff against the pinned copy.
2. If changed: update the pinned file + SHA-256 in `blueprint_schema.go`, classify every new field/enum in `capabilities.json` (default `unsupported` with a real reason), and run the backend tests (registry validator).
3. Locate the drift check (`.github/workflows/`); if absent, add a scheduled workflow that fetches the upstream schema, compares digests, and fails/notifies on drift without changing production.
4. Note the new retrieval date + digest in `docs/ADR049-render-yaml-parity.md`.
