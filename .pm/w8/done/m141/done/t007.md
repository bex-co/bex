## Fix — 2026-10-29 (hosted re-check still pending deploy)

- **Cause.** `httpport.Probe` gave each declared port a 1 s exchange budget, probed all of them concurrently and kept the lowest port that answered. A port that accepted the connection but had not sent a status line within 1 s counted the same as a port that is not HTTP. RabbitMQ's management listener (15672) renders `index.html` on its cold first `GET /`; on a Free instance's small CPU share that can exceed 1 s. Prometheus (15692) returns a tiny 404 at once, so the first scan committed 15692 permanently for the digest. Run 2 was fast enough and chose 15672.
- **Fix (retry plus a larger budget).**
  - `httpport.Probe` now returns `Result{Port, Unanswered}`. It tries ports lowest first, and the per-port budget is now 3 s, still inside the 10 s scan bound. Each port is classified three ways:
    - refused, closed, reset, oversized or non-HTTP replies are definitely not HTTP;
    - a parseable HTTP/1.x status line, of any code including 401, is HTTP;
    - an accepted connection that is still silent at its deadline, or a port the scan bound never reached, is unknown.
  - `Unanswered` is the lowest unknown port below the chosen one.
  - `selectWebImageHTTP` does not commit a higher HTTP port while a lower port is unanswered and the container is still inside the 90 s discovery window. It reports `Port N accepted a connection but has not answered HTTP yet; continuing to scan…` and retries on the next 15 s scan. The first, timed-out request also warms the listener. After the window, the lowest port that answered wins. If none answered, the recorded fallback applies as before. The scan stays bounded.
  - Everything else is unchanged: binary and TLS listeners are never promoted, noEXPOSE runtime discovery still works, decisions are still reused per digest, and the `Detected HTTP on port N` narration is the same.
- **Regression tests.**
  - `internal/httpport`: `TestProbeReportsASlowFirstAnswerOnTheLowerPortAsUnanswered`. A lower port's first answer is slower than the budget and a higher port returns a fast 404. The cold scan reports the lower port as unanswered, and the warm retry selects it. The non-HTTP table now also requires that definite non-HTTP answers, including close-without-reply, are never reported as unanswered.
  - `internal/controller`: `TestWebHTTPWaitsForASlowLowerListenerBeforeCommittingAHigherOne`. A cold scan inside the window waits instead of committing the higher port, and the next scan commits the lower one. After the window, a permanently silent lower port no longer blocks the HTTP choice. Reverting the controller gate reproduces the hosted failure exactly: `Detected HTTP on port <higher>`.
- **Risk.** An image with a lower listener that accepts connections and stays silent on `GET /` delays its HTTP choice until the end of the 90 s window. That is the bounded worst case, and the window and fallback are unchanged. RabbitMQ's lower listeners are expected to reject `GET /` at once: epmd 4369 closes on an invalid packet size, AMQP 5672 replies with its protocol header and closes, and the TLS ports are unbound by default. The hosted re-check confirms this.
- **Still open:** the hosted re-check on the deployed pin. Run several RabbitMQ no-PORT fixtures, each expected to report `Detected HTTP on port 15672`, plus nginx 80 and the noEXPOSE control. Delete the fixtures by ID with 404 proofs.
