# A deploy trigger with `deployMode: deploy_only` plus `imageUrl` or `clearCache` is accepted, where Render's contract says `deploy_only` cannot be combined with either

Why: Render's Trigger deploy refuses `deploy_only` alongside `commitId`, `imageUrl` or `clearCache`, so a client that sends one of those mixes on Render gets a 400 it can correct. On bex the same request quietly opens a deploy, and the caller never learns that the mix is invalid on Render.

- Severity: minor. Nothing breaks, but a request Render refuses opens a deploy on bex.
- Versions: bex CLI v0.9.0 release binary. Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md` (v2.36.0, `4fd34231b637`). Production pin `cce6c749f6ff`. The code is unchanged on main `436def3144`.
- Context: 2026-11-21 14:14–14:22 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`). Routine `cli-qa`, run r26, nonce `fc60`. Fixtures were the free image web service `srv-dc0qa6t2n01c73bc1iog` (`docker.io/library/nginx:1.27.0-alpine`) and the free native Python service `srv-dc0qa552n01c73bc1img` (`render-examples/flask-hello-world`). This run created and deleted both, and a 404 confirmed each delete.
- Attribution: server (`lego/backend/internal/deploys`). The pinned CLI never sends `deployMode`, so only REST, GraphQL `triggerDeploy` and MCP `trigger_deploy` callers reach this.

## Render

The pinned OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`, `POST /services/{serviceId}/deploys`) and [api-docs.render.com/reference/create-deploy](https://api-docs.render.com/reference/create-deploy) (read 2026-11-21) say:

- `deployMode`: "`deployMode` cannot be combined with `buildId`. `deploy_only` cannot be combined with `commitId`, `imageUrl`, or `clearCache`."
- `imageUrl`: "Cannot be combined with `buildId`, `commitId`, or `deployMode: deploy_only`."
- `commitId`: "Cannot be combined with `buildId`, `imageUrl`, or `deployMode: deploy_only`."

## Repro (REST, production)

```sh

# HTTP 201 {"id":"dep-dc0qeh0n82tc73dukttg","serviceId":"srv-dc0qa6t2n01c73bc1iog","status":"created","trigger":"api","bexTrigger":"api","image":{"ref":"docker.io/library/nginx:1.27.1-alpine"},…}  → went live on 1.27.1

# HTTP 201 {"id":"dep-dc0qi3t2n01c73bc1jh0",…,"status":"created","image":{"ref":"docker.io/library/nginx:1.27.0-alpine"},…}
```

Controls on the same pin, all correct:

- `{"deployMode":"deploy_only","commitId":"facfc73"}` on the Git service → 400 (deploy_only is refused for any repo-backed service).
- `{"commitId":…,"imageUrl":…}` on the image service → 400 "commitId is not supported for image-backed services".
- `{"deployMode":"bogus"}` → 400 "invalid request body at /deployMode".
- `{"clearCache":"bogus"}` → 400.
- `bex deploys create --commit facfc73 --image …` fails in the client before sending anything ("only one of commit or image may be specified").

## Mechanism

`validateTrigger` (`lego/backend/internal/deploys/service.go:737`) checks `buildId` against the other fields (`:750`). For `deploy_only` it refuses only a repo-backed service (`:761`), and it never checks `deploy_only` against `imageUrl` or `clearCache`. On an image-backed service, both mixes fall through to the normal trigger. The image mix deploys the new tag. The cache mix redeploys the configured image, and its `clear` has no effect, since an image service has no build. `service_test.go:757-761` asserts only that `deploy_only` alone is fine on an image service.

## Fix

In `validateTrigger`, after the `buildId` block, refuse `p.DeployMode == "deploy_only"` combined with `p.ImageURL != ""`, `p.CommitID != ""` or `p.ClearCache == "clear"`: `core.ErrBadRequest` with Render's wording, `deployMode "deploy_only" cannot be combined with commitId, imageUrl, or clearCache`. Before refusing on `clearCache`, check whether REST, GraphQL or MCP fills in a default `do_not_clear` when the caller sends none. If one does, refuse only an explicit `clear`, or only a field the caller actually sent, so a bare `deploy_only` never breaks. Keep the existing repo-backed refusal: FUTURE-MAYBE records repo-backed `deploy_only` as deferred, not this item. Restarts never set `DeployMode`, so they are unaffected. The deferred replay at `restart_wait.go:221` replays an already-validated request.

## Blast radius

`validateTrigger` serves REST `POST /v1/services/{id}/deploys` (`rest.go:266`), GraphQL `triggerDeploy` (`graphql.go:257`), MCP `trigger_deploy` (`mcp.go:197`) and the deploy hook, which never sets `deployMode`. No dashboard caller sends `deployMode` (`dashboard/src/features/services/hooks/use-trigger-deploy.ts` only passes it through). Update ADR018's "Trigger a deploy" row (`docs/ADR018-render-parity.md:158`), which says only that `deploy_only` is "accepted image-backed".

## Acceptance

- In REST, GraphQL and MCP, `deploy_only` with `imageUrl`, with `clearCache: "clear"` and with `commitId` each answer 400 on an image-backed service and open no deploy row.
- `deploy_only` alone on an image-backed service still answers 201 and redeploys the configured image.
- Unit tests in `lego/backend/internal/deploys` cover each mix and the bare control.

## Unverified

- Render's exact status and wording for these mixes was not observed (no Render account). The contract text above is the oracle.
