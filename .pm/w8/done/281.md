# On a service whose port was detected earlier, the "no open port" stall text tells the user to bind "the port in PORT (3000)" while the process's PORT is 10000

Why: since w8/267 a detected port is routed to and probed, but `PORT` stays 10000, as on Render. The no-open-port text from w8/259 still prints the probed port as the value of `PORT`. On a service that once listened on a detected port, a later deploy whose server binds no reachable port is told "the server must bind host 0.0.0.0 on the port in PORT (3000)". The process reads `PORT=10000`, so the sentence names a value the user cannot find in their environment.

**Severity:** minor (wrong number in a hint; following either reading gets the service live). **Attribution:** platform runtime (operator stall text). **Estimate:** ~20m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `7794`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `10acf5314735` (rolled 06:42–06:43 UTC), workspace `bex-canary`, QA human device login.

## Evidence

One free native Node service (`qa-20261112-7794-np`), auto-deploy off. Times are UTC.

```text

       06:33:25  log  QA-BOOT PORT=10000 listening 3000
       06:33:55  deploy live;  curl → ok envport=10000 local=3000
       GraphQL service: port 3000, configuredPort 3000, openPorts [3000]

06:45  start: print PORT, then a server on 127.0.0.1:$PORT                (pin 10acf5314735)
       06:53:07  log  QA-BOOT PORT=10000 bind 127.0.0.1
       06:54:15  deploy stallReason:
         "the container is running but its startup health check has not succeeded, so the rollout is
          waiting: a TCP connect to port 3000. No Health Check Path is set, so the check is a TCP
          connect, which only asks whether the process is listening on that port. No open port was
          detected on the instance: the server must bind host 0.0.0.0 on the port in PORT (3000). If
          the service does not need to receive traffic on any port, create a background worker instead."
```

The same service's first deploy (`sleep 3600`, no port ever detected) read "the port in PORT (10000)", which is right.

## Expected

The number in "the port in PORT (N)" is the `PORT` the process receives: 10000 here. Render: "Bind your server to `0.0.0.0` and the port specified by the `PORT` environment variable, which defaults to `10000`" ([Troubleshooting your deploy](https://render.com/docs/troubleshooting-deploys)).

When the probed port came from detection, the text can also name it, for example: "the server must bind host 0.0.0.0 on the port in PORT (10000); it listened on port 3000 before."

## Root cause

- `noOpenPortMessage(port)` prints the port it is given as `PORT` (`lego/operator/internal/controller/port_detect.go:199-201`). Its caller passes the serving port, which is `status.detectedPort` (3000) while that is set.
- `processPort` (`port_detect.go:100-105`) already computes what the process receives: the default when the serving port was detected. `crashHintPort` (`:110-115`) was added by w8/267 for the crash-loop text, but the no-open-port text was not changed with it.
- `status.detectedPort` is sticky (w8/267 left its fix 2 undone), so every later deploy of such a service gets the wrong number until a scan finds a new listener.

## Fix

1. Build the sentence from `processPort(app, port)`. When the serving port was detected, add the detected port as a second clause, as in Expected.
2. Check the Docker variant (`app_controller.go:6101-6103`), which prints `PORT (%d)` from the same argument.
3. A test: an App with `status.detectedPort: 3000` and no `PORT` variable gets "the port in PORT (10000)".

## Acceptance

- The case above: the stall text names `PORT (10000)` and mentions port 3000 as where the server listened before.
- A service with no detected port keeps today's text.
- A service with `PORT=3000` saved keeps "the port in PORT (3000)".

## Unverified
