# 218 — `services create --from <id>` without `--region` is refused with "region must be one of"

Why: cloning a service from the CLI should work without restating the source's region, as the pinned Render client's `--from` flow expects; today it fails before any other validation.

Found 2026-10-29 by the `/loopx w8` m131 live check (production pin `479bd3fe243b`, bex-canary, released Bex v0.3.3): `bex services create --from <owned free web id> --pre-deploy-command …` without `--region` exited 1 with `region must be one of: …` before reaching the pre-deploy check; adding `--region oregon` reached it. Not yet reproduced in isolation or traced: confirm what region value the pinned client sends for `--from` (empty vs the source's), what the source service reports, and whether bex should default an empty region to the source's (or Render's default) as Render does. Then fix server-side; no CLI fork.

Acceptance: `bex services create --from <id> --name <new> --confirm -o json` (no `--region`) creates the clone in the source's region on both released Bex and the pinned Render client; an explicit invalid region is still refused by name.

## Trace — 2026-10-29 (`/loopx w8`)

The refusal is **client-side** in the pinned Render CLI, before any request: `services create --from` copies the source's `serviceDetails.region` into the new request (`pkg/service/clone.go:140–189`, `withDefaultAlias` at :272), then parses it against Render's region enum (`pkg/types/region.go`: frankfurt, ohio, oregon, singapore, virginia). bex reports every service's region as `BEX_REGION` (`fsn1`, e.g. `GET /v1/services/srv-daif6dsmg29s73d1umvg` → `region: fsn1`), which is not in that enum, so `region must be one of: …` follows unless `--region` overrides it. Key Value creation also refuses `"region":"fsn1"` although its readback reports `fsn1` (m136 check).

**Decision needed (user):** w8/152's D1 (2026-10-29) says inputs normalize to `BEX_REGION` and readback shows `BEX_REGION`. Clone parity needs readback to be a Render region value instead, e.g. report `frankfurt` (Falkenstein is in Germany) on the Render-shaped REST/MCP surfaces while keeping `fsn1` internally — or accept that `--from` needs `--region` (a divergence ADR018 would record). Which should the Render-shaped readback be?
