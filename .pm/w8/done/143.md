# Web services receive caller-forged `True-Client-IP` / `CF-Connecting-IP`, the client-IP headers Render tells apps to trust

Why: on Render every public web service sits behind Cloudflare, which overwrites `CF-Connecting-IP` and `True-Client-IP` with the real client address. Render's own guidance points apps at those headers for rate limiting, allowlists and audit logs, because the caller cannot control them. On Bex the same app receives whatever the caller sent. Bex's edge only rewrites `X-Forwarded-For`/`X-Real-IP`, so a migrated app's IP-based rate limit or audit trail is trivially spoofable.

**Severity:** major (security-relevant parity gap for migrated apps). **Attribution:** infrastructure (Traefik edge). **Estimate:** 60m. **Source:** `/qa-find-bugs-cli` sweep 1241, 2026-10-20 ([evidence](evidence/cli-sweep1241/README.md)).

## Reproduction

Production, deployed pin `94533d795067`, workspace `bex-canary`. A free web service was created with `bex services create --type web_service --image docker.io/ealen/echo-server:0.9.2 --plan free -o json --confirm` (it echoes request headers) and later deleted (GET 404).

`curl https://<slug>.onbex.co/cf -H 'CF-Connecting-IP: 203.0.113.66' -H 'True-Client-IP: 203.0.113.77' -H 'X-Client-IP: 203.0.113.88' -H 'CF-IPCountry: KP' -H 'X-Forwarded-For: 1.2.3.4'`. Headers the container received (client IPv4 redacted):

```json
{
  "cf-connecting-ip": "203.0.113.66",
  "cf-ipcountry": "KP",
  "true-client-ip": "203.0.113.77",
  "x-client-ip": "203.0.113.88",
  "x-forwarded-for": "<client-ip>",
  "x-real-ip": "<client-ip>",
  "x-forwarded-proto": "https",
  "x-forwarded-server": "traefik-796944c7d6-nhg24"
}
```

The control is correct: a forged `X-Forwarded-For`, `X-Real-IP`, `X-Forwarded-Proto` or `X-Forwarded-Host` is replaced with the real values. That is stricter than Render, which appends to `X-Forwarded-For`. A plain request carries no `True-Client-IP` or `CF-Connecting-IP` at all.

## Expected (Render)

- Render's [PocketBase guide](https://render.com/articles/host-pocketbase-on-render) recommends `CF-Connecting-IP` because Cloudflare “overwrites whatever the caller sent”. A Render staff answer on the [community forum](https://community.render.com/t/ip-whitelisting/13292) points to `True-Client-IP` for the same anti-spoofing purpose, and [a forum header dump from a Render web service](https://community.render.com/t/accessing-client-ips-in-a-node-express-app/36282) shows both on every request.
- The Bex target: an app never receives a caller-supplied value in these headers. `True-Client-IP` (and `CF-Connecting-IP`, unless the TCP peer is a genuine Cloudflare edge for a tenant's orange-cloud custom domain) is either the address Traefik already uses for `X-Real-IP`, or absent.

## Root cause

The tenant entrypoints (`deploy/gitops/base/values/traefik.values.yaml:54–57`; prod overlay `deploy/gitops/overlays/prod/values/traefik.values.yaml:51–67`, PROXY protocol trusted only from the LB at `10.10.0.7/32`) let Traefik rewrite only its own `X-Forwarded-*`/`X-Real-IP` set. No entrypoint or App middleware touches other client-identity headers. The per-App middleware chain (redirect, IP allow, environment allow; `app_controller.go:3634–3700`) carries no header sanitizer. `core/proxiedhosts.go:30–45` already records that Bex deliberately does not trust `CF-Connecting-IP` for its own allowlist decisions; the edge still hands that header to tenants unfiltered.

## Fix

Add one platform-owned request-header sanitizer to the `web`/`websecure` entrypoints (`entryPoints.<name>.http.middlewares`) so it covers every App, static site and custom domain.

- **Minimum:** a `headers` middleware with `customRequestHeaders` set to `""` for `True-Client-IP`, `CF-Connecting-IP`, `X-Client-IP` and `CF-IPCountry`, which removes caller values.
- **Preferred, if cheap with the existing local-plugin mechanism** (`deploy/gitops/charts/traefik-plugins/`): set `True-Client-IP` to the post-PROXY-protocol client address, and keep `CF-*` only when the peer is inside the Cloudflare ranges Bex already pins in `core/proxiedhosts.go`.
- Optionally drop `X-Forwarded-Server`, which exposes the Traefik pod name to tenants.
- Record the header contract in ADR018/ADR022.

## Acceptance

- Live after GitOps sync, on a fresh free echo service (deleted by ID with a 404 proof): the forged-header curl above shows no caller value for `true-client-ip`, `cf-connecting-ip`, `x-client-ip` or `cf-ipcountry` (absent, or equal to the real client address). The `X-Forwarded-*`/`X-Real-IP` controls are unchanged; a static site and a custom-domain host behave the same.
- `scripts/gitops-validate.sh` passes, and rendering the chart shows the entrypoint middleware.

## Unverified

- A tenant custom domain behind the tenant's own Cloudflare proxy was not exercised; the preferred variant must keep its genuine `CF-Connecting-IP`.
- Render's exact header set was taken from Render's articles and forum captures, not from a live Render request in this sweep.

## Dedupe

`rg -i 'true-client-ip|cf-connecting-ip|x-forwarded-server'` (excluding evidence) matches only `core/proxiedhosts.go`'s allowlist-trust comment and ADR018's inbound-IP row (Cloudflare-proxied allowlist warning). Neither covers headers forwarded to tenant processes. No open or done item.
