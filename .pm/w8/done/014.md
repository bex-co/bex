# `webhooks.Verify` omits the Standard Webhooks timestamp-tolerance check it advertises

Why: `lego/backend/internal/webhooks/signing.go` documents `Verify` as the reference implementation a real webhook consumer would write ("the ~5 lines Verify below spells out"), but it checks only the HMAC and never bounds the timestamp — so the code bex publishes as the consumer recipe is missing the freshness half the Standard Webhooks spec requires, and anyone who copies it accepts captured deliveries forever.

Source: `~/.local/state/bex-security-integration/20260915T200437Z/scan/report.md` finding 2 (CWE-294), **re-triaged and downgraded** — see below.

## Downgraded from the scan's "medium"

The scan framed this as replayable webhook authentication in bex. It is not: `Verify` has **zero production callers**. bex is the webhook *sender*, never a receiver. The only references are `lego/backend/internal/store/worker_e2e_test.go:156`, `lego/backend/internal/webhooks/service_test.go:256`, and `signing_test.go`. There is no bex endpoint to replay against.

What remains is real but smaller: this is exported, documented reference code, and it silently diverges from the spec it names.

## The gap

`signing.go:87-99` parses `timestamp`, folds it into the expected HMAC via `Sign`, and compares — nothing ever bounds `ts` against the receiver's clock:

```go
func Verify(secret, msgID, timestamp string, body []byte, signatureHeader string) bool {
	ts, err := strconv.ParseInt(timestamp, 10, 64)
	if err != nil {
		return false
	}
	want := Sign(secret, msgID, time.Unix(ts, 0), body)
	...
}
```

The Standard Webhooks spec (`signing.go:30-41` cites it, and Render's outbound webhooks follow it) mandates a tolerance window — 5 minutes is the reference value — precisely to stop indefinite replay. Every reference library ships it; ours doesn't.

## Shape of the fix

- Reject timestamps outside ±5 minutes of `time.Now()` inside `Verify`, in both directions (a far-future timestamp is as wrong as a stale one).
- Keep the existing constant-time signature comparison and the malformed-timestamp rejection unchanged.
- Existing tests in `signing_test.go` pin fixed epochs (`1614265330`, `1750000000`) and will start failing — thread an injectable clock or build fresh timestamps rather than widening the window to keep them green.
- New tests: correctly-signed delivery older than the window fails; fresh correctly-signed delivery passes; far-future timestamp fails.
- Note the window in the `Verify` doc comment so the recipe stays self-describing.
