# `bex skills install` installs Render's agent skills: 22 `render-*` skills that tell the user's coding agent to run `render deploys create`, connect `mcp.render.com` and open `dashboard.render.com`

Why: on Render, `render skills install` gives an AI coding tool skills that operate the platform the user is on. On bex, the help text is rebranded ("Install Bex agent skills to AI coding tools…", `lego/cli/internal/branding/branding.go:170`). But the command clones the hard-coded `https://github.com/render-oss/skills.git` (upstream `pkg/skills/installer.go:21`) and writes Render's skills unchanged into `~/.claude/skills` and `~/.agents/skills`. An agent that follows them leaves bex:

- it runs `render login`/`render deploys create` (which talk to `api.render.com` unless the `render` binary happens to be absent);
- it adds `https://mcp.render.com/mcp` with a Render API key instead of bex's `https://api.bex.co/mcp` (ADR025);
- it sends the user to `dashboard.render.com`.

ADR008 makes bex AI-native, so this is the first thing an agent-first user runs, and the help promises bex skills.

Severity: **major** (the AI-native onboarding path actively points the user's agent at a different platform and account; nothing errors, so the user can't tell). Attribution: CLI (`lego/cli` launcher over upstream `pkg/skills`) plus content (no bex skills pack exists). Estimate: ~3h (pack + launcher override). Source: `/qa-find-bugs-cli` loop sweep 3093, 2026-10-28 10:45 UTC. Context: HEAD-built bex `fe5947541` with pinned Render CLI v2.27.0 `a764810a7682`; sandboxed `HOME` (nothing written to a real home directory).

## Prior decision

[w8/m29 t004](done/m29/done/t004.md) and `docs/bex-cli.md` § "Identity, storage and copy that branding deliberately leaves alone" list "`~/.render/skills.yaml` + `render-oss/skills` for `bex skills`" as an accepted **branding** residual. That was judged as copy. The effect is functional: the installed content operates the wrong platform. ADR018 has no row for it and no user sign-off, so per AGENTS.md ("a divergence stands only when ADR018 records it with the user's sign-off") it is open to reconsideration. If the user prefers to keep it, record it in ADR018 instead and change the `--help` copy so it no longer promises bex skills.

## Proposed fix

- Publish a bex skills pack (e.g. `bex-co/skills`, or embed it in the CLI binary so the pack is pinned to the CLI release). Derive it from `render-oss/skills` (check its license) with `render` → `bex`, `mcp.render.com` → `api.bex.co/mcp` (ADR025), `dashboard.render.com` → `dashboard.bex.co`, `onrender.com` → `onbex.co`. Drop skills for bex non-goals (workflows, sandboxes) or reduce them to "not available on bex".
- In `lego/cli`, override the installer source (repo URL / embedded FS) and move the state file to the bex config dir (`$BEX_CLI_CONFIG_DIR/skills.yaml`). Handle a pre-existing `~/.render/skills.yaml` so `bex skills update`/`remove` don't touch a real Render CLI install's state, which they currently share.
- Name the skills `bex-*` so they coexist with a user's genuine Render skills.
- Update `docs/bex-cli.md` (remove the residual line), `docs/cli-compatibility-checklist.md:295` and `UPSTREAM_RENDER_CLI.md` (re-diff `pkg/skills` on each pin).

## Acceptance

- In a sandboxed `HOME`, `bex skills install --confirm -o json` installs only bex skills. `grep -rli 'render.com\|mcp.render.com\|`render ' ` over the installed dirs finds nothing user-directing (attribution/license lines allowed), and the MCP skill points at `https://api.bex.co/mcp`.
- `bex skills install` in a `HOME` that already holds `render-*` skills and `~/.render/skills.yaml` leaves both untouched.
- An agent following the installed CLI skill can log in and deploy with `bex` against `api.bex.co`. Spot-check one deploy with a fixture, then delete it by ID with a 404 proof.
