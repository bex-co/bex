# Tenant apps cannot reach SMTP on 25/465, while free apps can use 587; neither rule matches Render or is documented for tenants

Why: Render blocks outbound 25, 465 and 587 only for free instances; paid services can send mail on any of them. On Bex every tenant service, free or paid, silently times out on 25 and 465 because the Hetzner network blocks them by default, while 587 is open to free and paid alike. ADR012 records the block, but only as a platform-operator note for Kratos's courier. A tenant whose app uses implicit-TLS SMTP (`smtps://…:465`, the default in many mailer guides) sees sends hang and time out with no Bex guidance.

**Severity:** minor (workaround: 587 or 2525 with STARTTLS; failure is a timeout in the app's own logs). **Attribution:** infrastructure (provider egress policy) and docs. **Estimate:** 30m to document; more if Hetzner unblocking or a policy is chosen. **Source:** `/qa-find-bugs-cli` sweep 1256, 2026-10-20 ([evidence](evidence/cli-sweep1256/README.md)). **Decision needed (user):** keep the provider block and document it for tenants, or request Hetzner's 25/465 unblock for the tenant pool. Separately, decide whether free services should be refused 587 as on Render (anti-abuse) or stay more generous.

## Reproduction

Production, deployed pin `94533d795067`, workspace `bex-canary`. A free image service (`python:3.12-alpine`, Docker Command running a probe app) was created over REST because the pinned CLI refuses `--start-command` for image runtimes, then deleted (GET 404). From inside the container it only opens a TCP connection and reads the greeting line; no SMTP command and no mail are sent. Two runs gave identical results:

| Destination | Result |
| --- | --- |
| `smtp.gmail.com:25` | fails after 6.0 s (`OSError` network unreachable / timeout) |
| `aspmx.l.google.com:25` | fails after 6.0 s |
| `smtp.gmail.com:465` | fails after 6.0 s |
| `smtp.gmail.com:587` | connected in 0.03 s, greeting `220 smtp.gmail.com ESMTP …` |
| `www.google.com:443` (control) | connected in 0.02 s |

Paid tenant services run on the same tenant-pool nodes and share their egress addresses (ADR018 “Service outbound IPs”, the node ExternalIPs), so the 25/465 block applies to them too. That part is inferred: no paid fixture was created.

## Expected (Render)

[render.com/docs/free](https://render.com/docs/free): “Free web services can't send outbound network traffic on ports `25`, `465`, or `587`.” The restriction is listed only among free-instance limitations, so paid instances may use them.

## Where it lives

- `docs/ADR012-auth.md:255`: “Hetzner blocks outbound implicit-TLS SMTP … `25` and `465` time out; `587` and `2525` are open”. Platform-only.
- No tenant-facing record: ADR018 has no egress-port row, and `rg -i '465|port 25|smtp'` over ADR018/ADR022/ADR043 and DO_NOT_DO finds nothing.

## Fix options

1. **Document (minimum):** add an ADR018 row and the tenant docs and dashboard copy explaining that outbound 25/465 are unavailable on every plan and to use 587/2525 with STARTTLS. Note the divergence from Render paid plans.
2. **Unblock for the tenant pool:** request Hetzner's SMTP unblock for the tenant-pool servers. That restores Render's paid behaviour and needs abuse controls (for example a free-plan egress NetworkPolicy denying 25/465/587, which also gives free-tier parity).

## Dedupe

ADR012 covers the platform courier only. No `.pm` item covers tenant SMTP egress.
