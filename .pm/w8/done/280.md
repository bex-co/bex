# A deploy of a commit SHA that is not in the repository is accepted and fails in its build; Render's deploy hook answers 404

Why: Render's deploy hook refuses a `ref` its linked repository does not have with `404 Not Found` and starts nothing. bex answers `200 {"deploy":{"id":…}}`, opens a deploy, queues a build, and the build fails 40–55 s later with git's raw `fatal: remote error: upload-pack: not our ref <sha>`. The user who mistyped a SHA in a CI script gets a success, then a failed deploy (and its failure notification), and the build log says it was building `@main`. `bex deploys create --commit <unknown sha>` does the same through REST.

**Severity:** minor (nothing that serves traffic changes; the previous deploy keeps serving). **Attribution:** server (deploy trigger, commit resolution). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `53bf`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pins `e7a56b07e0d7` (CLI case, 06:37) and `10acf5314735` rolling (hook case, 06:40; the deploy code is the same at both), workspace `bex-canary`, QA human device login.

## Expected

Render, [Deploy hooks](https://render.com/docs/deploy-hooks), "On failure", `404 Not Found`: "The commit SHA specified in the `ref` query parameter was not found in the service's linked repository." (The `400` row covers "a `ref` parameter was provided for a service that doesn't deploy from a Git repository", which bex already refuses, w8/141.) [Deploying a specific commit](https://render.com/docs/deploy-a-commit): "you can provide either a full or short commit SHA."

So for the hook: `404` with a sentence naming the `ref`, no deploy row, no build, no notification. For REST `POST /v1/services/{id}/deploys` with `commitId`, Render's [reference](https://api-docs.render.com/reference/create-deploy) lists `404 Unable to find the requested resource.` but does not tie it to `commitId`; answering the same `404` keeps the two doors to one deploy consistent (see Unverified).

## Root cause

- `deploys.Service.Trigger` resolves the requested commit only for provenance and opens the deploy whatever the answer: `commit := s.resolveCommit(ctx, a, p.CommitID)` (`lego/backend/internal/deploys/service.go:843`; `resolveCommit` at `:982-1005` returns an empty `CommitInfo` on any miss). Before that it checks only the ref's syntax (`store.ValidGitRef`, `:746`).
- The resolver cannot say "no such commit": the installation path turns GitHub's `422` (no such ref) into a plain miss with `404` (`lego/backend/internal/github/service.go:1363-1367`), and the anonymous GitHub path collapses every failure into a miss (`:1400-1413`), on purpose, so a lookup never distinguishes a private repository from a missing one.
- `spec.buildCommit` then carries the bad SHA to the clone phase, whose `git fetch origin "$REF"` fails; that line is the build's only error.
- The build log's `==> Building from …@main` comes from `lego/backend/internal/logs/progress.go:282-291`: with no resolved commit on the row it prints the branch, although the deploy asked for a SHA.
- The hook passes `ref` straight into the same `Trigger` (`lego/backend/internal/deploys/deployhook.go:376-389`) and always answers `200` on success.

## Fix

1. Give the resolver a third answer, "this repository has no such commit", returned only when the host proves it: GitHub's `422` on the installation path, and on the anonymous path a `422` (GitHub answers `422` only for a repository it shows publicly; a private or missing repository is `404`, which stays a miss, so no existence oracle is added). Rate limits, timeouts and other hosts stay "unknown" and the deploy opens as today.
2. In `Trigger`, when a caller-supplied `CommitID` (not a restart, not a rollback) gets that answer, refuse before any write: `core.ErrNotFound`-class `404` with a coded body, e.g. `COMMIT_NOT_FOUND`, "commit `<ref>` was not found in `<repo>`". The hook's message names `ref` (`inHookVocabulary`); REST, GraphQL `triggerDeploy` and MCP `trigger_deploy` share the refusal.
3. In `progress.go`, a deploy row whose commit did not resolve but which asked for one prints the requested ref, not the branch.

## Acceptance

- `POST …/deploy-hooks?key=<key>&ref=0123456789abcdef0123456789abcdef01234567` on a Public Git URL service → `404`, body names the ref, no new deploy in `bex deploys list <srv>`.
- `bex deploys create <srv> --commit 0123456789abcdef0123456789abcdef01234567 -o json --confirm` → exit 1 with that message, no new deploy.
- Unchanged: a real full SHA and a real 7-character SHA deploy (both doors), a deploy with no commit builds the branch head, and a deploy still opens when GitHub cannot be reached (unit test with the resolver erroring).
- The same on a GitHub App–connected private repository (installation path).

## Unverified

- Render's REST `commitId` answer for an unknown SHA (only the hook's is documented).
- Whether Render counts a SHA from another branch of the same repository as "found"; bex builds it today (the clone fetches the SHA directly). Keep that.
- Repositories on hosts other than GitHub: their smart-HTTP advertisement lists refs, not every commit, so they cannot prove absence; they stay best-effort.
