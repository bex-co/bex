# A Render region is silently normalized on create but refused in every Blueprint, so 75 of 100 real Render exports fail on `region` alone

Why: bex has two opposite policies for the same input. `bex services create --region oregon` succeeds and places the service in `fsn1` without a word. A Blueprint with `region: oregon` is refused, because "accepting-then-ignoring placement intent would be a lossy approximation". Render's Blueprint export writes `region` on every service and database, so the path a Render customer is most likely to try first is the one that fails. That happens to three out of four real exports, one error per resource (48 errors for one file), with nothing else wrong.

**Severity:** major (blocks most Render Blueprint imports). **Attribution:** server policy (ADR049 D7 against the ADR018 create normalization). **Decision needed:** yes, see Fix. **Estimate:** 60m once decided. **Source:** `/qa-find-bugs-cli` sweep 1267, 2026-10-20 ([evidence](evidence/cli-sweep1267/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, deployed pin `9cace6b6e25d`, workspace `bex-canary`, human device-login grant, HEAD-built pinned CLI.

1. Corpus: GitHub code search for `Exported from Render` in files named `render.yaml` returned 100 distinct files. Each begins with Render's export header (`# Exported from Render on <date>`). Each was run through `bex blueprints validate <file> -o json`, read-only.
2. Results: 4 valid and 96 invalid. 89 files have at least one `per-resource region placement is not available on bex` error at `services[N].region`, `databases[N].region` or `projects[N].environments[N].{services,databases}[N].region`. **75 files fail on `region` alone.** The regions are the ones Render's exporter writes: `oregon` (63 occurrences), `virginia` (33), `singapore` (27) and `frankfurt` (19). The remaining failures are documented refusals (previews, names that are not DNS labels per ADR020/ADR049) or files the author broke by hand (tabs, invalid enums).
3. The same intent through create: `bex services create --name qa-20261020-<nonce>-region --type web_service --plan free --image docker.io/ealen/echo-server:0.9.2 --region oregon -o json --confirm` → exit 0 in 4.6 s, `serviceDetails.region: "fsn1"`, empty stderr. The fixture `srv-dbbvf71v5vjs73b9h9gg` was deleted (204, then GET 404).
4. A minimal Blueprint with `region: frankfurt` (the Render region nearest `fsn1`) is refused with the same error, so no spelling of `region` validates.

## Expected

Pick one policy and apply it on every surface. Render's own export always carries `region`, and Render's validate response has no warnings channel (`ValidateBlueprintResponse {valid, errors, plan}` at the pin). So "refuse" means a migrating user must delete every `region:` line by hand, and nothing tells them to.

## Root cause

- Create: `lego/backend/internal/apps/rest.go:248–251` says that bex "intentionally normalizes" the CLI's `serviceDetails.region` to the configured placement. ADR018:81 records "accepted and then normalized to truthful `BEX_REGION` (`fsn1` in production)". Postgres and Key Value create do the same: they accept the region "as a placement hint" and keep `BEX_REGION` authoritative (`postgres/service.go:281–284`, `keyvalue/service.go:172`).
- Blueprint: every `region` entry in `lego/backend/internal/apps/schema/capabilities.json` is `unsupported`, with the reason "accepting-then-ignoring placement intent would be a lossy approximation (ADR049 D7)". ADR049:175 says the same thing in prose. w8/054 kept the message text ("per-resource region placement is not available on bex") without a remedy.

## Fix (decision first)

1. **Normalize in Blueprints too (recommended).** This matches create. Validate, plan, sync and apply accept any Render `region` and place the resource in `BEX_REGION`. The plan and the dashboard import preview state the placement once ("Render region `oregon` → bex runs every resource in `fsn1`"). Because the pinned CLI cannot show warnings, `bex blueprints validate` would simply pass. Flip the five `region` registry entries to a translated handler, and update ADR049 D7 and ADR018.
2. **Refuse everywhere.** Create with a `region` other than `BEX_REGION` returns 400, matching Blueprints. Make the Blueprint message actionable ("remove `region`; bex runs every resource in `fsn1`") and report it once per file rather than once per resource.

Either way, the Blueprint and create answers for the same region must match.

## Acceptance

- One policy, written once (registry plus ADR049/ADR018), with REST/GraphQL/MCP create, Blueprint validate/sync/apply and the dashboard import all agreeing. A test table covers `oregon`, `frankfurt`, absent `region`, and an invalid region (`Vietnam`, still refused by the schema enum).
- For option 1: 75 of the corpus files validate unchanged. For option 2: create `--region oregon` returns 400 with the same wording the Blueprint gives.
- Live after deploy: re-run the corpus and the create probe. Delete any fixture by ID with a 404 proof.

## Addendum — the pinned CLI's clone needs `--region` because bex reports `fsn1` (sweep 1296, 2026-10-21)

The single-region policy also breaks a CLI journey. Every service reads back `serviceDetails.region: "fsn1"`, which is not in Render's region enum. `bex services create --from <srv-id> --name <n>` (no `--region`) fails locally with `Error: region must be one of: frankfurt, ohio, oregon, singapore, virginia`, because the pinned CLI re-validates the source's region. With `--region frankfurt` the clone succeeds and is placed in `fsn1` anyway. `docs/cli-compatibility-checklist.md` lists this as partial but still names the value `local-capd`, which is stale; production reports `fsn1`. Whichever region policy is chosen, consider reporting a Render-enum region on reads (for example `frankfurt`, the nearest), or document `--region` as required for clones. Evidence: [cli-sweep1296](evidence/cli-sweep1296/README.md).

## Done — 2026-10-29

Implemented user decision D1 (one region policy on every surface).

**What changed**

- **Blueprints.** The four `…/properties/region` registry entries (server, cron, database, redisServer) and the five `#/definitions/region/enum` values in `lego/backend/internal/apps/schema/capabilities.json` are now `translated`. Before, they were `unsupported`. Validate, plan, sync and apply accept any Render region on services, cron jobs, Postgres and Key Value, at the top level and under `projects[].environments[]`, and place each resource in `BEX_REGION`. The "per-resource region placement is not available on bex" message is gone (`blueprint_compiler.go`). So are the `parseDatabase` region refusal and the unused `bexDatabase.Region` field (`deploy.go`). A value outside Render's enum (`Vietnam`, `fsn1`) is still refused by the pinned schema, located at its path.
- **Create.** `resourcemeta.Config.CheckRequestedRegion` is the one rule: a Render region or `BEX_REGION` is accepted and never persisted, and anything else is a 400 (`region must be one of: frankfurt, ohio, oregon, singapore, virginia; bex runs every resource in fsn1`). Services enforce it in `apps.Service.Create` through the new `CreateRequest.Region`, which REST `serviceDetails.region`, GraphQL `createService(region:)` and MCP `create_web_service`/`create_cron_job` `region` all fill. Postgres and Key Value enforce it in `CreatePostgres`/`CreateKeyValue`. GraphQL `createDatabase`/`createKeyValue` and MCP `create_postgres`/`create_key_value` gained `region`. The REST composed server additionally refuses non-enum values through the pinned OpenAPI validator.
- **MCP parity.** The four create tools now accept upstream's `region`, so they move from `Divergent` to `Superset` (inventory 10 / 9 / 2 / 170). `mcpAcceptedDivergences` drops their entries, and `TestMCPParityGitCreateToolsBreakOnlyOnRegion` becomes `TestMCPParityCreateToolsAcceptRegion`.
- **Docs.** ADR049 D7 is amended with the corpus-guard divergence list. ADR018 is amended: the MCP inventory, the Create-service row, the Blueprint row and the registry-reason note. ADR006's capability-registry row is updated too. All cite D1, 2026-10-29.

**Tests**

- `apps/blueprint_region_test.go` covers four things:
  - every Render region, plus an absent region, compiles and parses with zero problems on all seven resource positions; `Vietnam`, `mars` and `fsn1` are refused at their exact paths;
  - a Render-export-shaped Blueprint (header `# Exported from Render on …`, `region: oregon/virginia/frankfurt/singapore` on services, the keyvalue and the database) validates and plans with no errors on the service, REST, GraphQL and MCP;
  - apply reads every service back in `fsn1`;
  - REST/GraphQL/MCP service create accepts `oregon`/`frankfurt`/`virginia`/absent/`fsn1` and reads back `fsn1`, and refuses `Vietnam`/`us-east-1` with the shared message.
- `postgres/region_test.go` and `keyvalue/region_test.go` give the same create table on REST/GraphQL/MCP, with readback.
- `api/region_policy_test.go` runs through the composed server with the pinned OpenAPI validator: services, Postgres and Key Value with `oregon`/`virginia` return 201 and GET `region: fsn1`; `Vietnam` returns 400.
