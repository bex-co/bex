# Canceling a deploy during its build can record a false `server_failed` and `server_available` on an instance that kept serving

Why: `server_failed` is a Critical event. It sends the "Service unavailable" push, alert emails and webhooks. On Render, canceling a deploy leaves the running instance alone and records only the canceled deploy. On bex, a cancel while the new release is still building sometimes also records `server_failed` (`"unhealthy": "The instance failed its health check"`) 2–11 s later, then `server_available` 4–23 s after that. In this sweep that happened on 3 of 6 cancels. The instance was the same one throughout, and its URL answered 200 throughout.

**Severity:** major (a false Critical alert on every notification channel, for something the user did on purpose). **Attribution:** server (bex-api service-state projection), on a settled platform. **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `9d4e`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `33e1b1e6117c`.

## Root cause

`observedServiceStateFor` (`lego/backend/internal/store/reconciler.go:2340`) turns the App's status into the service's availability, and `server_failed` / `server_available` are written when that availability changes (`reconciler.go:532`).

- **The phase during a build:** while a service that has already served builds a new release, the operator keeps the App in phase `Building`. Its `Ready` condition is False with reason `Building` or `BuildQueued` (`setPhaseWith(…, PhaseBuilding, …)`, `lego/operator/internal/controller/app_controller.go:1165`, `:1261`, `:6801`). `Serving` stays True for the current generation, because the served release's pod is ready. `servingRevisionDown` (`:2323`) needs `Serving` False to report a real outage during a build.
- **The shortcut that misses it:** the "a served release is still serving" shortcut, `reconciler.go:2374`, applies only to phases `Deploying` and `Running`. So a `Building` App falls through to the later checks.
- **What used to save it:** during the build, `if hasOpenDeploy && !concreteContainerFailure(...) { break }` (`:2403`) keeps it healthy. Only the open deploy row stands between a healthy building service and the fallback.
- **The cancel removes that:** `deploys.Service.Cancel` (`lego/backend/internal/deploys/service.go:1059`) closes the row at once, as the `deploy_ended canceled` event at the cancel's second shows. The operator moves the phase off `Building` only in its settle pass (`settleCanceledRelease`, `app_controller.go:803`, which dispatches the served release: `Deploying`, then `Running`). The phase samples above put that 6–25 s after the cancel.
- **The fallback in that window:** `:2411` sees an active revision and a `Ready` reason that is neither a park reason nor `RolloutSettling`. It reports `unhealthy` with `readiness_failed`, which is `server_failed`. The pass after the settle reports healthy again, which is `server_available`.
- **Why only some runs:** whether a projector pass lands inside the window decides whether the pair is written.

## Fix

- **Widen the shortcut:** add `PhaseBuilding` to the shortcut at `reconciler.go:2374`. A building service whose `Serving` condition is True for the current generation is healthy, whether or not a deploy row is open. The real outage while building (w1/m185) keeps its path through `servingRevisionDown`, which needs `Serving` False.
- **Unit tests (`observedServiceStateFor`):**
  - phase `Building`, `Ready` False (`Building`), `Serving` True for the current generation, an active revision, and **no** open deploy: healthy, with no reason code.
  - the same with `Serving` False (`ServingRevisionUnavailable`): unhealthy `readiness_failed`, unchanged.
  - the same with `BuildQueued`.
- **Integration test, if the store's event tests reach it:** a cancel that closes the row while the App still reads `Building` writes no `server_failed`.

## Blast radius

- **Who:** every service type with a served release whose build can be canceled: web, private and background services, and any static site or cron job that reports phase `Building` while it builds.
- **Suspend while building:** it closes the row `canceled` too, before the operator parks the App. The same window may write the same false pair; with this fix it does not. Not exercised.
- **Not affected:** a deploy superseded by a newer one keeps a deploy row open, so it never reaches the fallback. A first deploy has no active revision, so it never reaches it either.
- **Downstream of the event:** the push (`DeliveryEventServerFailed`, Critical, `lego/backend/internal/notifications/push_worker.go:393`), alert emails, `server_failed` webhooks, and the service's recorded availability history.

## Regression checks

## Fix (shipped 2026-11-12, `/loopx w8`)

- **The shortcut covers `Building`:** `observedServiceStateFor` (`lego/backend/internal/store/reconciler.go`) now counts a service in phase `Building` as healthy, alongside `Deploying` and `Running`, when its `Serving` condition is True for the current generation. A build over a release that still serves is healthy whether a deploy row is open or not, so a cancel that closes the row before the operator leaves `Building` writes nothing. A build over a release with no ready pod (`Serving` False, `ServingRevisionUnavailable`, w1/m185) is still an outage.
- **Test:** `TestObservedServiceStateBuildWithNoOpenDeploy` (`serving_down_test.go`) uses reasons `Building` and `BuildQueued`, with the live revision serving and no open deploy: healthy, no reason code. With no ready pod: `unhealthy` / `readiness_failed`. Without the fix, the first case reads `unhealthy` / `readiness_failed`, the production observation.
- **Review** (`/simplify`): no test pinned the old behaviour, and nothing the change now records is false.
  - **Applied:** the phase check moved into `servingRevisionUp`, beside `servingRevisionDown`. The comment now says why the open-deploy guard cannot cover a cancel. The tests gained four checks: a healthy observation with a deploy open; Serving's transition time as the edge; no facts written in the cancel's window; and a stale-generation `Serving` that is still an outage.
  - **Noted, unchanged:** a build that starts healthy now records Serving's transition time as the service's healthy time. `Deploying` already did this.
- **Still owed on production:** the regression check above. Six mid-build cancels, with no `server_failed` and no `server_available`.
