# A first deploy whose start command exits 0 ends with `deploy_ended` `reason: {}`, though the same crash with exit 1 reads `failure.earlyExit` + `nonZeroExit`

Why: an app that exits "successfully" right after start is the case Render's `earlyExit` field exists for ("the application exited early. Services besides cron jobs should not exit unless receiving a `SIGTERM` signal from Render"), and it is a common start-command mistake (a script that backgrounds the server and returns). bex records the cause for every non-zero exit and none for status 0, so a Render client, a webhook consumer or the dashboard reading `reason.failure` sees a failed deploy with no cause.

- Severity: minor. The deploy fails at the right time (≈35 s) and its `failureReason` string says "(last exit code 0)"; only the structured reason is empty.
- Versions: bex CLI v0.9.0 release binary. Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md` (`4fd34231b637`). Production pin unknown; the code is unchanged on main `cd0e6bae6a`.
- Context: 2026-11-21 21:25–21:27 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`). Routine `cli-qa`, run r29, nonce `6070`. The pinned CLI refuses `--start-command` off native runtimes ("only supported for native runtimes"), so the fixtures were created with `POST /v1/services` (`runtime: image`, `plan: free`, `dockerCommand`), then read through the CLI and REST.
- Attribution: operator records nothing for a status-0 exit; bex-api then has nothing to map.

## Root cause

- `lego/operator/internal/controller/app_controller.go:4414` (`recordRolloutExit`): `if t != nil && (t.ExitCode != 0 || t.Reason == containerReasonOOMKilled)`. A status-0 termination never reaches `rolloutFailureFor`, so `status.rolloutFailure` stays nil for the release (the type documents `ExitCode` as "the app container's last non-zero exit code", `lego/types/v1alpha1/app_types.go:1810`).
- `lego/backend/internal/store/reconciler.go:1256` `deployCloseEnd` then returns `DeployEnd{}`, and `lego/backend/internal/events/service.go:799` `failureFromEnd` returns nil when `ExitCode == nil && !OOMKilled && TimedOutSeconds == 0`, so `reason` is `{}`.
- Within bex the two event paths already disagree: `server_failed` maps a status-0 exit of a live instance to `earlyExit: true` (w8/m158, `store/reconciler.go:1693`), while `deploy_ended` sets `earlyExit` for every non-timeout crash including non-zero ones (w8/m146) and drops status 0.

## Fix

- Operator: record a startup termination with status 0 too, e.g. `RolloutFailureStatus.ExitCode = &0` (and fix the field's doc comment), or a new `EarlyExit bool` field if a zero `ExitCode` would confuse another reader (`recordedRolloutFailure`, `store/reconciler.go:1264`, reads the same record).
- bex-api `failureFromEnd`: an exit with status 0 gives `{"earlyExit": true, "evicted": false}` with no `nonZeroExit`; a non-zero exit keeps today's `nonZeroExit` + `earlyExit` (w8/m146's live-checked shape).
- One caller each: `recordRolloutExit` is called once (`app_controller.go:4332`), `failureFromEnd` once (`events/service.go:767`). REST, GraphQL `reason { failure { earlyExit … } }` and MCP share the events service, so no shape change.

## Fixed (2026-11-21, `6010194604`), live check owed

Render's shape, from the pinned schema (`lego/backend/internal/api/openapi/render-public-api-1.json`, `GET /events/{eventId}`, Deploy Ended `reason.failure`, which references the Cron Job Run Ended `reason` object): `nonZeroExit` is "If present, the application exited with the specified non-zero status", `earlyExit` is "If true, the application exited early. Services besides cron jobs should not exit unless receiving a `SIGTERM` signal from Render", and `evicted` is required. A start command that exits 0 is therefore `{"failure": {"earlyExit": true, "evicted": false}}`.

- Operator: `recordRolloutExit` records a status-0 termination on `status.rolloutFailure` too (`ExitCode: 0`); a non-zero exit or an OOM kill in any pod of the release still wins. The `ExitCode` doc and the CRD say so.
- bex-api: the deploys table refused exit 0 (`CHECK (end_exit_code <> 0)`, migration 0176), so migration 0324 drops that check. `failureFromEnd` sends `nonZeroExit` only for a non-zero status; a deadline close with a clean exit on record reads `timedOutSeconds` alone. REST, GraphQL (`reason { failure { … } }`) and MCP `list_events` share the mapping. The dashboard timeline shows the deploy's `failureReason` sentence, not the structured reason, so it is unchanged; that sentence is w8/386.
- Tests: `TestStartupCleanExitRecordsExitZero` (operator), the `startup clean exit` and `deadline with a clean exit on record` cases of `TestDeployAndBuildEndedCarryRendersReason` (events) and the clean-exit leg of `TestPGDeployEndReasonReachesEventReads` (real DB). Each failed with its part of the fix reverted: no record, `nonZeroExit: 0`, and the check-constraint violation.
- Owed: the production check in Acceptance, once the pin carries `6010194604`.
