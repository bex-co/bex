# Blueprints that use YAML anchors and aliases are refused, although Render resolves them and real Render Blueprints depend on them

Why: YAML anchors (`&name`) and aliases (`*name`) are standard YAML, and teams use them to share one `envVars` block across services. RooCode's Roomote ships a maintained Render Blueprint that uses them; its header says Render "consumes this file directly". Bex refuses every alias with "YAML aliases are not supported in Blueprints", so such a repository cannot be imported at all. The refusal was a safety measure against alias amplification. The compiler's walk budgets now bound amplification directly, so the blanket refusal is no longer needed.

**Severity:** minor (2 of 218 Render-schema-valid real files; a full import blocker for those projects). **Attribution:** server (Blueprint YAML front end). **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1270, 2026-10-21 ([evidence](evidence/cli-sweep1270/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, deployed pin `9cace6b6e25d`, workspace `bex-canary`, HEAD-built pinned CLI. The manifest passes Render's pinned Blueprint schema with 0 errors once its aliases are resolved:

```yaml
services:
  - type: web
    name: qa-20261021-a1
    runtime: image
    image: { url: docker.io/ealen/echo-server:0.9.2 }
    plan: free
    envVars: &shared
      - key: LOG_LEVEL
        value: info
  - type: web
    name: qa-20261021-a2
    runtime: image
    image: { url: docker.io/ealen/echo-server:0.9.2 }
    plan: free
    envVars: *shared
```

`bex blueprints validate alias.yaml -o json` → exit 1, `{"errors":[{"column":14,"line":17,"path":"services[1].envVars","error":"YAML aliases are not supported in Blueprints"}],"valid":false}`.

Corpus (sweep 1270): `RooCodeInc/Roomote` (`render.yaml`: `envVars: &roomote-app-env` reused as `*roomote-app-env` by two more services) and `lemma-work/lemma-platform` (`envVars: &backend_env` / `*backend_env`). Both headers describe the file as the one Render reads ("Render consumes this file directly: the 'Deploy to Render' button and Render's Blueprint sync both read `render.yaml`"; "Render reads this file from the repository root"). Roomote's comments also describe Render's alias semantics ("This anchored env block is duplicated per app service"; "Render cannot extend the shared env-var sequence alias with one controller-only secret").

## Expected

Aliases resolve to their anchored node, as in any YAML 1.2 parser, and the Blueprint validates, plans and applies exactly as if the block were written out. Render's Blueprint reference does not mention anchors either way, so the evidence is the two maintained Render deploy files above. Errors inside an aliased block should point at the anchor's source location (or the alias site), with a stable line and column.

## Root cause

`lego/backend/internal/apps/blueprint_compiler.go:954–955` returns `BLUEPRINT_YAML_ALIAS` for every `yaml.AliasNode`. The comment at `:830–838` records why: "aliases are already rejected". It also records that the compiler now has structural walk budgets that bound "the amplified in-memory shape" (`blueprintMaxNodes` 100 000, `blueprintMaxDepth` 100, checked during the walk before each allocation) on top of the 512 KiB byte cap. The alias refusal dates from the first strict compiler (`3c8faf888`) and has no parity decision in ADR049.

## Fix

In `yamlNodeToBlueprintValue`, follow `node.Alias` and walk the anchored node, counting every materialized node against the same walk budget. An alias bomb then fails on the existing budget error instead of on the alias itself. Keep merge keys (`<<:`) out of scope unless the same walk handles them; Roomote notes that Render cannot merge sequences anyway. Locations: map paths under an alias to the anchor's line and column. Document the change in ADR049.

## Acceptance

- Compiler tests: the manifest above compiles to two services with identical `envVars`. A classic billion-laughs document fails on the node budget with the existing budget message, not on an alias. Aliases inside `envVarGroups` and `databases` work the same way. An error inside an anchored block reports a line and column inside that block.
- Both corpus files validate past the alias stage; their other refusals (for example region, w8/152) are unchanged.
- Live after deploy: validate the manifest above → `valid: true`.

## Dedupe

`rg -i 'yaml alias|BLUEPRINT_YAML_ALIAS|anchor' .pm docs`: no item. The refusal comes from the original compiler commit, and the budget comment treats it as already settled.
