# Key Value `connection-info` advertises the external URL about a minute before it accepts connections

Why: right after a user first allows an IP on a Key Value store, `bex kv-cli`, the dashboard Connect panel and any client given the advertised `rediss://` URL fail with a cryptic `SSL_connect failed: unexpected eof`. bex should publish the external URL only once it works.

**Severity:** minor (transient, about 60 s, retry succeeds). **Attribution:** operator/runtime + server. **Estimate:** ~60m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `a6b6`, 2026-11-08.

## Evidence

- Checkout build `bex vqa-460c283a6` (HEAD `460c283a6`), Render CLI v2.35.0 `24ac2d60fdb2`. API `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human OAuth (workspace owner's CLI login). Deployed revision unknown.
- Fresh free store `red-dbo455r40q1c73bmudng` (`qa-20261108-a6b6-kv3`), `available` at 09:37:02Z:

  ```text
  09:37:07.395  bex keyvalues update <id> --ip-allow-list "cidr=<qa-ip>/32,description=qa" -o json --confirm   → exit 0
  09:37:10–09:38:05  GET /v1/key-value/<id>/connection-info → externalConnectionString "rediss://default:<redacted>@<id>.kv.bex.co:6379" (present from the first poll)
                     valkey-cli --sni <id>.kv.bex.co -u <that URL> PING → "Could not connect to Valkey at <id>.kv.bex.co:6379: SSL_connect failed: unexpected eof while reading" (7 consecutive tries, 5 s apart)
  ```

  The first store of the sweep (`red-dbo3vik0r0ts73a72t60`) showed the same thing through `bex kv-cli <name>` in a PTY: 4× `SSL_connect failed: unexpected eof` right after enabling, then `PING → PONG`, `SET/GET` round-trip about a minute later.
- Render: the external URL is shown only once an allowlist entry exists ([Key Value docs](https://render.com/docs/key-value): "External URL isn't shown? You first need to add at least one IP range…"). Bex already matches that. Render's live Key Value timing was not measured.

**Re-verified on production pin `2d453686f` (sweep `9f56`):** fresh free store `red-dbo7q3atc71s73ac9t90`, enabled 13:46:27.6Z. The external URL was advertised from 13:46:34Z, PINGs got `SSL_connect failed: unexpected eof` 10 times, and the first `PONG` came at 13:47:40Z (about 66 s).

## Root cause

`lego/operator/internal/controller/keyvalue_controller.go:1093-1094` sets `Status.ExternalHost` as soon as `intent.public` is true. `lego/backend/internal/keyvalue/service.go:1321-1322` publishes `externalConnectionString` (and `cliCommand` with `--sni`, `:1346`) whenever `Spec.Public && Status.ExternalHost != ""`. The TLS listener opens later: per ADR021 §"Enable", cert-manager issues the certificate, the kubelet projects the Secret, and the operator retries `CONFIG SET tls-port 6380` every 5 s until the files exist. Until then the SNI proxy forwards to a closed port and the client sees EOF.

## Fix

Have the operator record when the TLS listener is confirmed open (for example `Status.ExternalReady` / a `TLSListenerReady` condition set after the successful `CONFIG SET tls-port`, cleared on disable). Gate `externalConnectionString` / the `--sni` `cliCommand` on it on REST, GraphQL `cliCommand`, the legacy `/redis` alias and MCP, and show "External access is being enabled…" in the dashboard Connect panel meanwhile. Older stores with a static listener count as ready when their pod is ready.

## Acceptance

- Fresh free store, enable allowlist, poll `connection-info` every 2 s: from the first response that contains `externalConnectionString`, `valkey-cli … PING` answers `PONG` on every try.
- Disable → external URL disappears; re-enable of a store with an issued certificate reports ready within seconds.
- `bex kv-cli <name>` right after enable reconnects successfully or prints the internal-only command, never an EOF loop.

## Dedupe

`rg -i "SSL_connect|unexpected eof|externalHost"` over `.pm` and `docs`: w8/m134 (private newborn stores, done) introduced the lazy listener. No item covers the advertise-before-ready window.

## Done — 2026-11-10

Connection info now gates the external URL on the listener, not on `externalHost`: `KeyValueConnectionInfo` (`lego/backend/internal/keyvalue/service.go`) drops the `rediss://` URL, and with it the `--sni` CLI command, until `status.tlsListener` is true. The operator sets that only after `CONFIG SET tls-port` succeeds on a runtime-switch store, or from the pod template on an older one. REST, the `/redis` alias, GraphQL and MCP share the function. The dashboard Connect panel says "External access is being enabled…" for a public store without the URL, instead of "Not public". Tests: `TestConnectionInfoWaitsForTheTLSListener`, and a dashboard panel case. ADR021 records it.
