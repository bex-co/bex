# With no `package.json` at the repo root, a Node build ignores the `engines.node` of the one in a subdirectory and builds on the default, where Render uses the first `package.json` it finds in a subdirectory

Why: Render's Node version page says that "If there isn't a `package.json` file in your repo's root directory, Render uses the first `package.json` file it finds in a subdirectory." bex reads `engines.node` only from `package.json` at the service's root. A monorepo deployed without a Root Directory (with `cd backend && npm install` as its build command, for example) gets Render's default Node on bex and the version its `engines` names on Render.

- Severity: minor. The service builds and runs, but on a different Node major than Render would pick, and nothing in the log says why.
- Versions: bex CLI v0.9.0 release binary, pinned Render CLI v2.36.0 (`4fd34231b637`), production pin `89642635b9ce`. The code is unchanged on main `554bbb0799`.
- Context: 2026-11-22 11:48–11:52 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY. Routine `cli-qa`, run r30, nonce `7c3e`.

## Render

[render.com/docs/node-version](https://render.com/docs/node-version), read 2026-11-22. Under the `package.json` `engines` method: "If there isn't a `package.json` file in your repo's root directory, Render uses the first `package.json` file it finds in a subdirectory." The same page says that an unbounded range such as `>=20` "always resolves to the latest release of Node.js". It does not say in what order subdirectories are searched.

## Repro (bex, production)

`render-examples/docs-api-agent-template@5f73445` has no root `package.json`. Both `backend/package.json` and `frontend/package.json` declare `"engines": {"node": ">=22.0.0"}`, and the repo has no `.node-version` or `.nvmrc`. Whichever file Render finds first, it resolves `>=22.0.0` to the newest release, 26.13.1 today.

```sh
bex services create --name qa-20261122-7c3e-nested --type web_service --plan free \
  --repo https://github.com/render-examples/docs-api-agent-template --branch main --runtime node \
  --build-command 'echo QA_BUILD_NODE $(node -v) && ls' \
  --start-command 'echo QA_RT_NODE $(node -v); node -e "require(\"http\").createServer((q,r)=>r.end(\"QA_RT \"+process.version)).listen(process.env.PORT||10000)"' \
  --confirm -o json </dev/null
bex logs -r <srv> --type build --limit 1000 --direction forward -o text
```

The service was `srv-dc1dd2rbki1s73dg3vgg`. It went live on the default:


## Root cause

- `packageEnginesNode` (`lego/operator/internal/build/nativeversion.go:1201-1216`) reads `readFile("package.json")` only. `readFile` is rooted at the service's root directory (`BEX_NATIVE_SOURCE_DIR`, `lego/operator/cmd/native-resolve/main.go:26`), and when that file is missing the function returns "".
- It has two callers: `fromPackageEngines` (`:850-860`, the signal) and `nodeRequestText` (`:1176-1190`, the narration and range request).

## Fix

- **Fall back the way Render does:** when the root has no `package.json`, use the first `package.json` found in a subdirectory.
  - Search breadth-first, in lexical order, skipping `node_modules` and dot-directories, with a small depth bound. Render's order is undocumented, so record the choice in ADR060 D7.
  - Use the same file for the signal, the `==> Requesting Node.js version …` line, and the source path in `Using Node.js version … via <path>`.
- **Keep the precedence:** a root `.node-version` or `.nvmrc` still wins over the fallback, and a root `package.json` with no `engines` still means "no signal" (Render says only that a missing file triggers the search).
- **Scope:**
  - Primary Node services and the Node companion of the other runtimes (`resolveNativeCompanion`) read through this function. Check whether Node-based static sites do too (`nativeRuntime`, `native.go:294`), and count every caller in the fix.
  - A service with a Root Directory searches below that directory. Render's monorepo page says commands and files are relative to it.

## Regression checks

- **Unit:**
  - A tree with only `backend/package.json` (`engines.node: ">=22.0.0"`) resolves to the newest line, with source `backend/package.json`.
  - With a root `package.json` that has no `engines`, the default stays.
  - A root `.nvmrc` still wins over the fallback.
  - `node_modules/x/package.json` is never chosen.
- **Production:** repeat the fixture above in `bex-canary`. The log names `26.13.1 via /opt/render/project/src/backend/package.json` (or `frontend/`, per the recorded order), and the app prints `QA_RT_NODE v26.13.1`. Delete the fixture and confirm 404.

## Fix (2026-11-22, `0170f10098`)

- Render's rule, read again 2026-11-22:
  - [render.com/docs/node-version](https://render.com/docs/node-version), under the `engines` method: "If there isn't a `package.json` file in your repo's root directory, Render uses the first `package.json` file it finds in a subdirectory." The same page puts `.node-version` and `.nvmrc` in "the root of your repo", with no fallback.
  - [render.com/docs/monorepo-support](https://render.com/docs/monorepo-support): "Render runs commands and interacts with files relative to your service's root directory", and "Files outside your service's root directory are not available to the service at build time or at runtime." So "the repo's root" is the service's Root Directory when one is set.
  - The build command's `cd` plays no part. Render's log names the version before `==> Running build command` (docs/render-artifacts/native-version-narration.md), so it cannot see where the command goes.
- So the gap was the search alone. bex already read every version file relative to the Root Directory (`BEX_NATIVE_SOURCE_DIR` is `boundedSourceDir(o.RootDir)`, `nativeresolve.go`).
- Now (`lego/operator/internal/build`):
  - `nodePackageJSON` (`nativeresolve.go`) picks the `package.json` that counts. It is the root's whenever the root has an entry by that name. Otherwise it is the first regular one below the root. The search is breadth-first, with each directory's entries in lexical order, at most three levels and 1,000 directories down. It skips `node_modules` and dot-directories and never follows a symlink.
  - The resolve phase computes it once and passes it to the primary and to `resolveNativeCompanion`. A Node service, a static site (`nativeRuntime` is Node) and the Node companion of Python, Ruby, Go, Rust and Elixir therefore read the same file.
  - The file's path travels in the choice's Source (`backend/package.json engines.node`). That one value drives the signal, the `==> Requesting Node.js version …` line (`nodeRequestText`), the log path (`==> Using Node.js version 26.13.1 via /opt/render/project/src/backend/package.json`) and the refusal (`backend/package.json engines.node "<14" is not a supported Node version`).
  - Precedence is unchanged: `NODE_VERSION`, then the root's `.node-version` and `.nvmrc`, then `engines.node`. A root `package.json` without `engines` is still no signal. So is a first nested one without `engines`, because Render names only a missing root file as the trigger.
- Tests: `nativenodepackage_test.go`.
  - The search: none, the root, one subdirectory, lexical order among siblings, shallowest first, the depth bound, `node_modules`, dot-directories, a file link, a `package.json` directory, and a directory link out of the checkout.
  - End to end through `ResolveNativeBuildExact`: this repo's layout gives 26.13.1 via `backend/package.json` with the request line, and a Python service's Node companion reads `web/package.json`. A root `.nvmrc` wins, a root `package.json` without `engines` keeps the default, and so do a first nested one without `engines` and a `node_modules` one.
  - The refusal names the file.
- Mutation-checked: without the search, with the old narration key, or with `node_modules` searched, the new tests fail. w8/398's, w8/370's, w8/371's and w8/372's tests pass unchanged. `make test` and `make lint` pass.
- Recorded in ADR060 D7 (the Node rows and the "A `package.json` in a subdirectory" rule) and ADR018.
- Residual: a Python, Ruby, Go, Rust or Elixir repo whose first nested `package.json` asks for a Node bex refuses (before 14) now fails at version selection, as one at its root already did. Render's order between two differing subdirectories is still unverified.
