# On Python, Ruby, Elixir, Go and Rust native services the app never gets SIGTERM when a script starts it, and an app with no SIGTERM handler ignores it; both run until SIGKILL

Why: Render's [deploy sequence](https://render.com/docs/deploys) says: "After 60 seconds, Render sends a `SIGTERM` signal to your app's process on the _original_ instance". If the process has not exited when the shutdown delay ends (`maxShutdownDelaySeconds`, default 30, 1–300), Render sends `SIGKILL`. [ADR018](../../docs/ADR018-render-parity.md) records the same contract, and [w8/m88](done/m88/README.md) made it hold for native Node images. There the start command runs under bex's `native-init`, which forwards the signal and then signals whatever the command left running.

Every other native runtime still starts with `ENTRYPOINT []`, and its CMD `/bin/bash -c <start command>` runs as PID 1. m88's launch audit ([t003](done/m88/done/t003.md)) left "other primary runtimes and companions → unchanged `ENTRYPOINT []`" untested. Linux delivers a signal from outside the container to the namespace's PID 1 only when that process has a handler for it ([pid_namespaces(7)](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)). Two common start-command shapes therefore break:

- **A script that runs the app without `exec`** (`./start.sh`, `bin/web`). bash stays PID 1, has no SIGTERM handler, and drops the signal. The app never receives SIGTERM, so its shutdown code never runs. It keeps running through the whole delay and is then SIGKILLed.
- **An app launched directly with no SIGTERM handler.** bash execs the app, so the app is PID 1 and the signal is dropped. This covers Python's default, Flask's `app.run()` and a plain worker loop. The app runs the full delay instead of exiting on SIGTERM. Render's PID 1 for native services is undocumented, so parity for this shape is inferred. The cause and the fix are the same as for the script shape.

**Severity:** major. On five of the six native runtimes, the shutdown contract that `maxShutdownDelaySeconds` configures never reaches a script-launched app. On a web service the 60 s drain still lets most in-flight requests finish, so the visible loss is the app's own shutdown work (closing connections, flushing, deregistering). A background worker has no drain. There, the in-progress job is SIGKILLed without the warm-shutdown signal that job frameworks use to stop fetching and requeue; this is inferred, because workers are paid and no worker was run. **Attribution:** platform build (native image entrypoint). **Estimate:** ~60m (the condition, per-runtime placement tests, a generated-image process test for both shapes). **Source:** `/qa-find-bugs-cli` w8 loop sweep `6aa7`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login. The Python runs (14:51–15:12 UTC) ran on production pin `ca7fbbe606c8`, rolled by workflow_dispatch and pinned at 14:41:54. The Node control ran on `f018ce9455c8` (deploys 2–3) and during that roll (deploy 4). Nothing between the two pins, or on main since, touches `native-init` or the native entrypoint.

## Root cause

- `lego/operator/internal/build/nativeinit.go:48-50`: `nativeServingInit` is `!o.StaticSite && o.NativeResolverImage != "" && nativeRuntime(o) == nativeNodeRuntime`. For any other runtime, `nativeEntrypoint` (`:55-61`) writes `ENTRYPOINT []`, and neither the native-init context (`build.go:1193`) nor its staging (`nativeresolve.go:409`) is added.
- `lego/operator/internal/build/native.go:493-495`: the CMD is `NativeStartArgv` = `/bin/bash -c <command>`. bash execs a lone or final simple command, and nothing else stands between it and PID 1.
- `lego/operator/cmd/native-init/main.go:104-145` already solves both shapes. As PID 1 it forwards SIGTERM to the child. A non-PID-1 bash, or a handler-less app, then dies of it. Once the child has exited, native-init sends the signal to everything left behind with `kill(-1)` and waits within the pod's grace period, which is the script case.
- The native runtimes: `nativeToolchains` (`native.go:93` on) keys `node`, `python`, `ruby`, `elixir`, `go` and `rust`. Only `node` gets native-init.

## Fix

- **Start every native serving image under native-init:** drop the `nativeRuntime(o) == nativeNodeRuntime` clause from `nativeServingInit`.
  - The binary is static (`CGO_ENABLED=0`, `lego/Dockerfile:56-58`), so it runs on every toolchain base (Debian python, ruby, elixir, golang and rust images).
  - The resolve phase that stages it already runs for every native build.
- **Keep:**
  - Static sites stay excluded.
  - Docker and prebuilt images keep their own ENTRYPOINT (Docker semantics; Render's Docker runtime leaves the image's ENTRYPOINT in charge).
  - Explicit cron `Command` and pre-deploy overrides still bypass the ENTRYPOINT, as m88 t003 recorded.
  - Exit status passes through unchanged: the command's own, or 128 + the signal.
- **Update m88's disposition and ADR060's w8/m88 note** to say native-init covers every native runtime.

## Blast radius

- **Covered:** every Python, Ruby, Elixir, Go and Rust native web service, private service, background worker, and cron job without an explicit Command (it uses the image CMD).
- **When it takes effect:** existing releases keep their image's ENTRYPOINT until their next build.
- **Not changed:** Node (already covered), Docker and prebuilt images, static sites, managed data.
- **API surfaces:** no REST, GraphQL, MCP, Blueprint or dashboard change.

## Regression checks

- Per-runtime placement tests: an `ENTRYPOINT ["/native-init"]` and the `bex-init` context for every line of every runtime. Extend m88's Node 22/24/26 check.

  - a `start.sh` that runs the app without `exec` must log `SIGTERM` and exit within the grace period;

## Shipped 2026-11-12 (`/loopx w8`); the production check waits for the deploy that carries it

- **Fix:** `nativeServingInit` (`lego/operator/internal/build/nativeinit.go`) drops its Node-only clause. Every native service image whose build has the resolve phase now ends with `COPY --link --from=bex-init /native-init /` and `ENTRYPOINT ["/native-init"]` in front of its exact CMD, with the `bex-init` buildctl context and the resolver's staging. Static sites, Docker and image sources, and cron and pre-deploy runs with an explicit `command` are unchanged. A service picks it up on its next build.
- **Tests:**
  - `TestNativeServiceStartsUnderNativeInit`: 27 subtests, every line of every runtime selected through its own version signal (`nativeLineSignal`, shared with `nativebases_test.go`). Each checks that the line resolved and that the image ends with native-init in front of the CMD. It fails on the Node-only rule (Go first).
  - `TestNativePythonServiceStopsOnSIGTERM` (BuildKit integration, `BEX_BUILDKIT_INTEGRATION=1`, run locally): a `start.sh` that runs the app without `exec`, and a handler-less app launched directly, each stop on `docker stop -t 20` in under a second. Neither exits 137, the handler logs `SIGTERM`, and neither bash nor the app is PID 1. On the Node-only rule both took 20.2 s, to SIGKILL.
- **Review** (`/simplify`, three reviewers): no blocking finding; every toolchain base is Debian with `/bin/bash`, and native-init is static. Elixir's `epmd` is re-parented to native-init and gets the signal after the BEAM exits. Shared the version-signal and container helpers, updated the Node-only comments (`build.go`, `cmd/native-init`, `lego/Dockerfile`, ADR013) and recorded in ADR060 that the wait for leftover processes now applies to every runtime.
- **Docs:** ADR060 § Graceful shutdown (w8/290 paragraph), ADR013.
- **Still owed on production:** runs 1 and 2 again on a Python service built after the deploy. The script-launched app logs `SIGTERM` about 60 s after the switch, and the handler-less app's last line comes at that SIGTERM, not 60 s + the delay. Run 3's Node results stay the same.
