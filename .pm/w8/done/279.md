# A Blueprint that gives a service both a disk and autoscaling is refused with the cluster's validation text

Why: Render's Blueprint spec does not allow `scaling` on a service with an attached disk, and bex refuses the file, which is right. But the error reads `spec: Invalid value: "object": a service with spec.disk cannot use autoscaling`. That is the App resource's admission rule, with its `spec.` field names, passed through as the Blueprint error. Every other disk rule in a Blueprint answers in product terms, and the REST path has its own sentence for this exact case.

**Severity:** minor (the refusal is correct; only the wording leaks). **Attribution:** server (backend Blueprint compiler). **Estimate:** ~20m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `699a`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `8330744bd643`, workspace `bex-canary`, QA human device login.

## Evidence

```text
$ cat render.yaml
services:
  - type: web
    name: qa-bp-web
    runtime: node
    plan: 1c-2g
    buildCommand: npm install
    startCommand: npm start
    scaling:
      minInstances: 1
      maxInstances: 2
      targetCPUPercent: 60
    disk:
      name: data
      mountPath: /var/data
      sizeGB: 1

$ bex blueprints validate render.yaml -o json        # exit 1
{"errors":[{"path":"services[0].scaling",
  "error":"spec: Invalid value: \"object\": a service with spec.disk cannot use autoscaling"}],"valid":false}
```

The neighbouring disk rules, from the same run:

```text
disk + numInstances: 2   → service "qa-bp-web": a service with a disk cannot run more than one instance (currently 2)
mountPath: data          → service "qa-bp-web": mountPath must be an absolute path
mountPath: /etc/secrets  → service "qa-bp-web": mountPath "/etc/secrets" is reserved by the platform; mount a subdirectory of it instead
disk on the free plan    → service "qa-bp-web": disks require a paid instance type
```

The same sweep validated 99 other Blueprint files (valid and invalid per Render's spec). No other message carried cluster wording.

## Expected

`services[0].scaling: service "qa-bp-web": a service with a disk cannot use autoscaling`, in the form of its neighbours, with no `spec:`, `Invalid value` or `spec.disk`.

## Root cause

- The sentence is the CRD's validation rule message (`lego/types/v1alpha1/app_types.go:447`).
- The REST disk path checks the combination itself and says "a service with a disk cannot use autoscaling; turn autoscaling off first" (`lego/backend/internal/apps/disks.go:329-331`).
- A Blueprint reaches admission through the dry-run create (`lego/backend/internal/apps/blueprint_preview_creates.go`) without that check having run, so the rule's own text comes back. Where the Blueprint path skips the check was not traced.

## Fix

1. Check disk plus autoscaling in the Blueprint compiler and report it with the product sentence at `services[n].scaling`.
2. Go through the other CRD rule messages in `app_types.go` and confirm each one a Blueprint can reach has a compiler check in front of it, so an admission message is never the user's first answer.

## Acceptance

- The file above answers `services[0].scaling: service "qa-bp-web": a service with a disk cannot use autoscaling` and exits 1.
- A test fails if a Blueprint validation error contains `Invalid value:` or `spec.`.
- Unchanged: the other disk refusals keep their text.

## Unverified

- Render's own wording for this refusal.

## Shipped 2026-11-12 (`/loopx w8`); the CLI replay waits for the next production deploy

- **Create.** `validateCreateDisk` now knows whether the same entry turns autoscaling on, so a `disk` beside `scaling` answers `services[0].scaling: service "qa-bp-web": a service with a disk cannot use autoscaling` on validate and sync (`TestBlueprintDiskWithScalingIsRefusedInProductWords`). The disk rules (paid plan, one instance, no autoscaling) share one sentence each across REST and Blueprints (`disks.go`).
- **Sync onto an existing service.** `ApplyBlueprintServiceSpec` judges the service the sync leaves: a disk added to a service that autoscales or runs two instances, or `scaling`, `numInstances: 2` or `plan: free` added to one with a disk, is refused before any write at the field that breaks the rule, as a 400 naming the service (it would otherwise reach admission, or, for a conflict, answer 500). Each rule is judged on its own, so a legacy disk with no recorded plan does not excuse a new autoscaling range. When the scaling range is the live service's, the sentence adds "declare numInstances in the file to turn autoscaling off".
- **A changed type** reads "a service's type cannot be changed after it is created; delete the service and create it again to change its type", not the App rule.
- **Guard (Fix 2).** `TestBlueprintIsNeverAnsweredWithAnAdmissionRule` reads every `XValidation` rule on the App (and fails if one is written in a form it cannot parse) and requires each to name either a manifest the compiler refuses for that rule, in product words, or the check that stands in front of it. A new App rule fails it until it is covered.
