# A web service switched to a prebuilt image keeps its configured port 10000, where an image-created one serves on its image's exposed port

Why: since w8/m461 a switched service reads and runs as an image-created service in every other field. The port is the one difference. An image that ignores `$PORT` (nginx listens on 80) still fails its first deploy after a switch, although the same image created as a new service serves.

**Severity:** minor (an image that honours `$PORT` works; one that does not fails its health check). **Attribution:** server (`portMode` is stamped at create only). **Source:** w8/m461 t004, 2026-11-17, `TestSwitchedServiceReadsAsAnImageCreatedOne` (`lego/backend/internal/apps/native_image_switch_test.go`), which diffs a switched read against an image-created one.

## Evidence

- An image-created web service gets `spec.portMode: web-image-v1` at create (`configureNewImageCompatibility`, `lego/backend/internal/apps/service.go`, w4/m243). It serves on the port its image exposes and reads `openPorts: []` until one is detected, with no `port`.
- A native web service has no port mode, so it keeps its configured `port: 10000`. A switch to an image (`sourceFields.applyTo`) leaves that alone. The switched read has `port: 10000` and `openPorts: [{port: 10000, protocol: TCP}]`.
- `appv1alpha1.AppSpec.UsesWebImagePorts` (`lego/types/v1alpha1/image_network.go`) says "Only services stamped at create carry the mode, so existing web services keep their configured-port behavior."

## To decide and do

- Render's docs say a Docker web service is served on the port it binds, and w4/m243 followed that for new image services. Check whether a source switch on Render keeps the earlier port. If that can't be measured, follow the image-created behaviour (Render parity first).
- If a switch should adopt image ports: on a switch to a prebuilt image, a web or private service whose port is the default and not explicitly configured takes `web-image-v1` / `image-v1`, as create would. An explicit port selects the configured variant. A switch back to a native build returns the service to its configured port. Do this in the one source writer, so REST, GraphQL, MCP and a Blueprint sync agree.

## Testable end state

`TestSwitchedServiceReadsAsAnImageCreatedOne` passes with the port fields no longer excluded. On production, a native Node service switched to `docker.io/library/nginx:1.27-alpine` and deployed answers 200 on its URL.

**Promoted 2026-11-19 to [w8/m504](../m504/README.md)** by `/loopx w8`. The web half is already served by bound-port detection: a switched web service keeps no port mode, so `detectBoundPort` adopts nginx's 80, as production showed for the same configured-port state in [w8/177](177.md). The private half is real: no detector covers a configured-port private service. Stamping the mode in the source writer would re-project the still-serving native release on a save-only switch, because the operator reads `HasImagePorts()` from the saved spec and `PortMode` is release identity.
