# A service's inbound IP list reads back changed when it allows all: a lone `0.0.0.0/0` returns two rules, descriptions are dropped, and the default is not Render's `0.0.0.0/0` "everywhere"

Why: Render reads back the rules a user wrote, and its default rule is one entry, `0.0.0.0/0` with the description `everywhere`. On bex a user who saves `0.0.0.0/0` "office VPN fallback" reads back `[{0.0.0.0/0,""},{::/0,""}]`; a tool that diffs desired against actual rules (Terraform, a Blueprint export) sees a change it did not make on every read. w8/m157 recorded the difference as not signed off (README § "The read default differs from Render in shape") and filed no follow-up; this is it.

**Severity:** minor (access is right; the stored rules and their descriptions are not what was written). **Attribution:** server (`core.ServiceAllowListToSpec` / `core.ServiceAllowList`). **Estimate:** ~45m. **Source:** `/loopx w8` replay of w8/m157 t008, 2026-11-12 UTC, production pin `3d66946c9e16`, workspace `bex-canary`, QA human device login; also seen by `/qa-find-bugs-cli` sweep `7794` on pin `e7a56b07e0d7`.

## Evidence

```text
$ bex services update <srv> --ip-allow-list "cidr=0.0.0.0/0,description=everywhere" --ip-allow-list "cidr=::/0,description=everywhere-v6" -o json --confirm
GET /v1/services/<srv>  serviceDetails.ipAllowList → [{"cidrBlock":"0.0.0.0/0","description":""},{"cidrBlock":"::/0","description":""}]
GraphQL service { ipAllowListEntries } and MCP get_service: the same.

sweep 7794: --ip-allow-list cidr=0.0.0.0/0,description=everywhere → reads back the same two-entry pair, descriptions empty.
An untouched new web service or static site reads the same pair.
```

A rule list that restricts (for example `203.0.113.0/24` "doc-range") reads back as written, description included.

## Expected

Render: a new service has the single rule `0.0.0.0/0`, description `everywhere`; a written list reads back as written. (Render's Terraform provider, quoted in w8/m157's README, sends and compares the list verbatim.)

## Root cause

`lego/backend/internal/core/cidr.go:247-256` `ServiceAllowListToSpec`: a set that does not restrict (only `0.0.0.0/0` and/or `::/0`) is saved as no rule, so what was written, and its descriptions, is discarded; `ServiceAllowList` (`:266-275`) reads "no rule" as `UnrestrictedAllowList()`, the two-range pair. The reason given in the code, that a stored lone `0.0.0.0/0` "would refuse every IPv6 source", does not apply today: service hosts publish no AAAA record (`dig AAAA <svc>.onbex.co` is empty), so no client reaches a service over IPv6.

## Fix

1. Save a non-restricting list as written (entries and descriptions), and keep the operator from projecting a middleware for it: the operator already decides by the stored ranges, so make a stored list that contains `0.0.0.0/0` or `::/0` project no middleware (check `lego/operator` where `spec.ipAllowList` becomes the Traefik middleware, and `RestrictsInbound`).
2. Read "no rule" (an untouched service) as Render's default, `[{"cidrBlock":"0.0.0.0/0","description":"everywhere"}]`, on REST, GraphQL, MCP and the Blueprint export; keep `[]` for blocked.
3. The dashboard's "Allow all traffic" button writes that default.
4. Update ADR018's inbound IP row: the shape difference is closed.

## Acceptance

- Writing `0.0.0.0/0` "everywhere" reads back exactly that on REST, GraphQL and MCP, and the service answers 200.
- A new service reads `[{"cidrBlock":"0.0.0.0/0","description":"everywhere"}]` and answers 200.
- `[]` still blocks; a restricting list still restricts; an omitted field still changes nothing (w8/m157's tests).
- A Blueprint export of an untouched service followed by a re-apply plans no change.

## Unverified

- Whether Render admits IPv6 sources under a lone `0.0.0.0/0` (moot until bex has IPv6 ingress; file it then).

Any other list, one that restricts nothing included (`0.0.0.0/0` "office VPN fallback"), is saved and read back as written, descriptions included. The dashboard's **Allow all traffic** writes the default.
- **Operator unchanged (Fix 1 narrowed).** A stored list like `0.0.0.0/0` "office VPN fallback" projects a middleware that admits every IPv4 source and no IPv6 one. No service host publishes an AAAA record, so nothing is refused today; the IPv6 decision is filed as w8/285.

The flat CIDR form (GraphQL `ipAllowList`/`cidrs`, MCP `ipAllowListCidrs`) reads `["0.0.0.0/0"]` and cannot carry a description, so writing it back, alone or beside the entries read with it, is the default rule.
- **Blueprint.** An untouched service still exports no `ipAllowList`, and an export of a service with a described allow-all rule carries it; both re-apply unchanged (`TestBlueprintExportOfAnOpenServiceReappliesUnchanged`).
