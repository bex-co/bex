## Closed — 2026-11-19 (loopx session)

- **Render's contract.** [render.com/docs/native-runtimes](https://render.com/docs/native-runtimes) lists `zip` and `unzip` with the marker its legend defines as "Available both during builds and at runtime", on Debian 12 "bookworm", and names no version (read 2026-11-19). bex supplies Debian 12's `zip` 3.0-13+deb12u1 beside `unzip` 6.0-28+deb12u1 (t001). Which version Render ships is unverified, and no Render-hosted comparison was run.
- **Build and runtime.** bex's build and runtime share one image, so `zip` is available in both phases, as Render lists it. The original program needs it in both: its server reports the zip version at start and creates an archive per request (t006), and the maintained runtime check fails when zip is removed after the build (t005).
- **zip's contract.** Info-ZIP's `zip(1)` manual describes the `-0` to `-9` levels, `-X`, `-Z bzip2`, `-y`, `-r`, `-D`, `-j`, `-x`, `-@`, stdin as `-`, streaming to stdout, `-u`, `-d`, `-z`, `-T`, `-MM` and the exit statuses 12, 16, 18 and 3 (its DIAGNOSTICS section). The maintained checks run each of these (t005).
- **ADR060.** The D7 m107 row records the packages, the behaviors accepted, the exit statuses and the limits: no encryption, split archives or Zip64 workloads, and no exact Render version. It adopts with the next native rebuild on the current image, as every D7 tool does.
- **No surface change.** zip arrives through the image every native build already uses. REST, GraphQL, MCP, Blueprint and the dashboard keep their schemas, fields and error shapes, and no selector, toggle or launcher change was added.

  - Each create used the frozen original build and start commands from `testdata/native-utilities/original-cases.json`, with no installer line. They differ only in the per-client marker (`QA434_03af_bex` / `_render`).
  - Each kept the public source `git-fixtures/basic@6ecf0ef`, no environment variables (Render's default Node for a new service) and `--auto-deploy=false`.
