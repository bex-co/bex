## Objective

Render t001's listener on every store whose proxy forwards the TLS port, and expose it on the stable Service, so `kv-sni-proxy` can dial `<id>.<ns>.svc.cluster.local:<refusal port>`.

## Context

- The proxy's TLS env, port and certificate mount are rendered when `intent.tlsForwarded()` (`lego/operator/internal/controller/keyvalue_internal_proxy.go:119`). The stable Service's ports are set at `keyvalue_controller.go:812`, and it selects the proxy once it is ready (`keyvalue_controller.go:806`).
- **Held templates (w6/m517).** A proxy's pod template moves only at the store's own change, unless `kvInternalProxyRollRevision` is bumped, which rolls every store's proxy once and closes its held clients after the drain (`keyvalue_internal_proxy.go:195`). `TestKeyValueInternalProxyRenderingIsPinned` makes the change decide.
  - Recommended: **no bump.** The author's rule reserves a bump for a security fix or a held template that can no longer work, and ADR021 § 10 says Render breaks a store's connections at the customer's change, not at a platform ship. A store created after the deploy gets the listener at once. An existing store gets it at its next own change, and until then t003's dial fails and the client reads today's EOF (README DoD 5). Record the choice and its reason in the pin test's comment and in ADR021 (t004).
- The new port must be one Valkey never listens on (Valkey uses 6379 and 6380), so a stable Service that still selects Valkey directly refuses the dial too.
- Network: tenant namespaces admit `bex-system` on every port (`allow-datastore-control-ingress`, `lego/backend/internal/store/namespaces.go:1136`). Check that the store's own `-internal-proxy-environment-ingress` policy (`keyvalue_internal_network.go:73`) need not list the port for `kv-sni-proxy` traffic, and on a legacy shared apps namespace too. Say what you found in the task record.

## Steps

1. Add a named constant for the refusal port (for example `6381`) where both the controller and `cmd/kv-sni-proxy` can read it (`internal/sniproxy` is already imported by both).
2. When `intent.tlsForwarded()`: add the env var, a container port named for the refusal, and a stable Service port with the same target. Service changes roll nothing.
3. Update the rendering pin and record the roll decision.
4. Tests: the rendered Deployment and Service carry the port only when the TLS port is forwarded. An envtest store whose proxy template is held keeps it, while its Service still gains the port.

## Record (2026-11-22)

- `controller.KeyValueAllowListRefusalPort` is `6381`, named `ip-refusal`. It lives in the controller, not `internal/sniproxy`: an edit to `sniproxy` changes both SNI proxy binaries and so rolls `pg-sni-proxy` too (`TestACRDFieldEditLeavesBothProxiesByteIdentical`, ADR021 § 10). `kv-sni-proxy` keeps its own `allowListRefusalPort`, and `TestTheRefusalPortIsTheOperatorsPort` (a test-only import) holds the two equal.
- When `intent.tlsForwarded()`, the proxy gets `BEX_KV_ALLOWLIST_REFUSAL_ADDR=:6381` and the container port. While `intent.public`, the stable Service gets port `6381`. The `-backend` Service does not, since the refusal dials nothing.
- **Roll decision: no bump.** The inputs digest is unchanged; only the two TLS fixtures' template pins moved, and the decision is recorded in `TestKeyValueInternalProxyRenderingIsPinned`'s comment. A held proxy keeps today's drop until the store's own change, and a store created after the deploy has the listener at once.
- **Network.** `kv-sni-proxy` reaches `6381` exactly where it reaches `6380`. In a tenant namespace, `allow-datastore-control-ingress` admits `bex-system` on every port (`lego/backend/internal/store/namespaces.go`, peer-scoped). The store's `-internal-proxy-environment-ingress` admits only environment clients and need not list the port, since NetworkPolicies are additive. The shared `default` namespace has no `allow-datastore-control-ingress`, so the only policy selecting a proxy pod there is the operator's own; `kv-sni-proxy` reaches neither `6380` nor `6381` on it, which this milestone leaves unchanged. Read from the code: the production kubeconfig fetch needs `HCLOUD_TOKEN`, which this checkout's `.env` does not carry.
- Tests: `TestKeyValueInternalProxyAnswersAllowListRefusalsWithTheTLSPort` (the port and env only with the TLS port, never on `-backend`, on the stable Service only while public, never one Valkey listens on), the envtest spec "keeps a public store's template without the allow-list refusal, while its Service gains the port", and the updated port counts in `TestKeyValuePublicFrontDoor`, `TestKeyValueInternalProxyCutoverPreservesServerAndRouting` and `TestKeyValueInternalAuthKeepsTheProxyRoute`.
