# An Update Source during a release in flight rolls that release on the previous image

Why: a source update saved while a release builds or rolls out must wait behind that release (Render's Update Source contract), not roll it on the previous image.

Filed as `w8/124` from the w8/m119 code review on 2026-10-19 and renumbered to 127 the same day. Its note was overwritten in the shared tree by the `qa-login.sh` note that also took the number 124 and was committed in `69e925197`. `f2b59f784`, `w8/126` and ADR060 refer to this item as `w8/124`.

`sourceUpdatePending` was decided before `releaseInFlight` in `prepareAppReleaseDecision`. A source update saved mid-build or mid-pre-deploy therefore took the `sourcePending` path, and the release in flight rolled the prior image (`status.image`) under its new revision.

**Done (2026-10-19, `f2b59f784`):** in `prepareAppReleaseDecision`, a pending source update now yields to a release in flight whose source is already fixed (`releaseInFlight` and `releaseSourceFixed`: its build has started, or its artifact is built and it is rolling out). That release keeps its pinned identity, so it resolves and rolls its own artifact, and the saved source waits for a deploy behind it.

Two cases were filed as w8/126, now w8/m121: a build not yet dispatched, and a repo-to-image switch. In both the saved spec still decided. With no release in flight the pending source still holds the serving image, as before.

`TestSourceUpdateDuringAReleaseInFlightKeepsItsOwnArtifact` covers a release building and then rolling out. It fails before the change and passes after. Not reproduced live: the window is one build long and needs an Update Source saved inside it.
