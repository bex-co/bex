# A static site's `.ico` gets the ETag and Range rules of a text file, where Render's edge treats it as a binary that Cloudflare compresses: weak tag on br and gzip, strong on identity, and a 206 of the identity bytes in every coding

Why: w8/361 and w8/362 copied Render's rules for the types Render's origin compresses (HTML, CSS, JS, SVG, XML). `.ico` is on bex's compressible list too, but on Render it behaves the other way round, so after those fixes ship every favicon's validator and Range answers differ from Render's.

- Severity: minor. A favicon still loads and revalidates. A client that resumes a download or compares tag strength sees bex differ from Render, and after 361 ships the identity and br tags will be the opposite of Render's.
- Versions: production pin `820edf28d22d` (before 361 and 362); main `bcf51d886` carries `870ffe3f9` (361) and `16a6b71c8` (362). CLI `bex-cli/v0.7.0` (Render CLI v2.36.0).
- Context: routine `cli-qa` run r18-7abd, 2026-11-21 01:28–01:40 UTC, `bex-canary`, human device-login token. About 60 read-only requests to Render sites.

## Render (read-only, 2026-11-21)

Sites: `wc3v`, `whatseasonisitinhorizon`, `mentorship-guide` and `breadcrumbs-wiki` (`.onrender.com`), all `server: cloudflare` with `rndr-id`. The pattern held on all four. On the first two it held for every check below; on the other two the tag checks were run.

| request on `/favicon.ico` (`image/vnd.microsoft.icon`, 15–34 KB) | Render |
| --- | --- |
| `Accept-Encoding: br` or `br, gzip` | `200`, `content-encoding: br`, `etag: W/"…"`, no `Content-Length` |
| `Accept-Encoding: gzip` | `200`, `content-encoding: gzip`, `etag: W/"…"` |
| no `Accept-Encoding`, `identity` or `HEAD` | `200`, `etag: "…"` (strong), `content-length`, `accept-ranges: bytes` |
| `Range: bytes=0-9` with br, gzip or none | `206`, `content-range: bytes 0-9/<identity size>`, strong tag, no `Content-Encoding` |
| `If-None-Match` with either form, any coding | `304` with the strong tag |

On the same sites, origin-compressed types run the opposite way, which is the rule w8/361 adopted:

- `/` is strong with br and weak with no header (`wc3v`, `whatseasonisitinhorizon`).
- `.svg` (`mg-book.svg`, `safari-pinned-tab.svg`, `undraw_docusaurus_tree.svg`) and `sitemap.xml` are strong with br, sending `content-length` and `accept-ranges`, and weak with no header.

So Render's origin serves `.ico` as identity, like a PNG, and the Cloudflare edge compresses it on the fly for br and gzip clients. Cloudflare weakens the tag when it does that, and it serves a Range from the identity object.

w8/362's note saw `mentorship-guide`'s `.ico` sent identity to a br client, once. In this run it came back br with a weak tag on every one of six br requests, so that single observation was not the steady state.

## bex

Production (pin `820edf28d22d`), free static site `srv-dc0f923cd0vs73c88e90` serving a 15,004-byte `favicon.ico` (now deleted):

- br: `200`, `content-encoding: br`, `etag: W/"…"` (14 bytes). gzip: the same in 55 bytes. Both match Render.
- `Accept-Encoding: identity` and `HEAD`: strong tag with `content-length`. These match Render.
- A `GET` with no `Accept-Encoding`: `etag: W/"…"` and no `content-length`, because of the gzip-decoding proxy hop. Render sends the strong tag.
- `Range: bytes=0-9` with br: `206 content-range: bytes 0-9/14`, the br bytes. With gzip: `0-9/55`. Render sends the identity bytes `0-9/15406` in both.
- `If-None-Match`: `304` with the weak tag. Render sends the strong one.

On main, the code (`lego/operator/internal/staticserver/`) makes it diverge further:

- `encoding.go:136` lists `image/x-icon` and `image/vnd.microsoft.icon` (with `image/bmp`, `font/ttf`, `font/otf` and `application/vnd.ms-fontobject`) in `compressibleType`.
- `encodeBody` (`encoding.go:230`) then gives `.ico` the w8/361 rule: strong with br, weak with gzip, identity and no header. That is the opposite of Render on both.
- It gives `.ico` the w8/362 Range rule too (`edgeRequest`, `staticserver.go:598`): a br body up to 4 KiB answers a Range from the br bytes, and gzip or identity answers `200` with the whole body and no `Accept-Ranges`. Render answers `206` of the identity bytes in every coding.

## Fix

Split `compressibleType` in two:

- **Origin-compressed:** text, JS, JSON, XML and SVG. Keep 361 and 362 unchanged for these.
- **Edge-compressed:** `.ico` (measured). For these:
  - Encode br or gzip only when the request has no `Range`.
  - Weaken the tag on every encoded body. Keep identity, `HEAD` and the no-header `GET` strong, which may need the gzip-decoding hop to restore the strong tag or skip edge-compressed types.
  - Answer a Range from the identity bytes with `206` and the strong tag in every coding, and send `Accept-Ranges: bytes` on identity.
  - Send the strong tag on every `304`, as now.

Before moving `image/bmp`, `font/ttf`, `font/otf` and `application/vnd.ms-fontobject`, measure 1–2 public Render static sites, read-only, for one file of each. Put each in the class Render shows, and leave any type with no Render sample where it is, with a comment. Record the two classes in ADR029 § ETag direction and § `If-Match` and ranges, and in the ADR018 static-site row. Add tests next to `TestETagStrengthFollowsRender` and `TestRangesAndIfMatchFollowRendersEdge` covering an `.ico` in br, gzip, identity and no header, with and without `Range`.

## Acceptance

Once production carries the fix, create a free `bex-canary` static site whose build writes a 15 KB `favicon.ico` and an `index.html` (for example `printf '\000\000\001\000' > out/favicon.ico && head -c 15000 /dev/zero >> out/favicon.ico`). Then check:

- `curl -sI -H 'Accept-Encoding: br' …/favicon.ico` gives `content-encoding: br` with `etag: W/"…"`, and gzip gives the same.
- `curl -sI …/favicon.ico` and a `GET` with no header give the strong tag with `content-length` and `accept-ranges: bytes`.
- `Range: bytes=0-9` gives `206 content-range: bytes 0-9/15004` with the strong tag and no `Content-Encoding`, for br, gzip and no header.
- `If-None-Match` with either form gives `304` with the strong tag.
- `/` still follows 361 and 362: strong with br, weak with no header.

Delete the fixture by ID and confirm a 404.

## Unverified

## Outcome

- 2026-11-21 triage: the premise held at main `ba70d788d`. `compressibleType` (`encoding.go:126`) put the icon types with text, so `encodeBody` gave `.ico` w8/361's tag rule and `edgeRequest` w8/362's Range rule.
- Render measured read-only on 2026-11-21, about 200 requests to 13 sites (`vue`, `pdfjs`, `angular`, `gatsby`, `jekyll`, `sveltekit-static`, `webfpvsimulator`, `runny-ai`, `rust-wasm-calc.app` and the four above). For each file: br, gzip, no header, `HEAD`, and `Range: bytes=0-9` with br and with no header.
  - **Edge compressed**, like `.ico`: only `image/vnd.microsoft.icon`, now on six sites (`vue` 4,286 bytes and `pdfjs` 32,988 bytes added).
  - **Origin compressed**, like text (strong on br, weak elsewhere, no Range on identity): `font/ttf` (two `.ttf` files on `angular`, and an `.otf` on `runny-ai` that Render also labels `font/ttf`), `application/vnd.ms-fontobject` (`.eot`) and `application/wasm` (three sites), plus JSON, XML and text.
  - **Never compressed** (one strong tag, 206 in every coding): `font/woff` (two files), `application/pdf` (1 MB), PNG (two sites), and `binary/octet-stream`.
  - No 206 carried `Accept-Ranges`, on any of those types.
  - No sample was found for `image/bmp`, `application/yaml` or the `x-font` types.
- Verdict: work. The split is by content type, and the icon types are the class.
- Fixed in `1d9af0ece`:
  - `compressionOf` puts a type in `uncompressed`, `originCompressed` or `edgeCompressed`. 361 and 362 hold unchanged for origin types. `bmp`, `yaml` and `x-font` stay origin compressed, with a comment.
  - An edge-compressed file weakens its tag on br and gzip only. A request with a `Range` gets identity, so the 206 carries the identity bytes and the strong tag in every coding. Every 304 keeps the strong tag.
  - The header-less `GET`: Traefik's forwarder is Go's `http.Transport`, which asks the static server for gzip and decodes the answer. A new `staticSite` instance of the edge plugin, last on every static site's route (`<app>-static-site`), sets `X-Bex-No-Accept-Encoding: 1` when the client sent no `Accept-Encoding`, and drops a caller's own. An icon then goes identity with `Content-Length` and `Accept-Ranges`. Text ignores the marker and keeps reaching that client through the decode, as on Render. The external-rewrite proxy drops the marker, and `scripts/gitops-validate.sh` keeps its two copies equal.
  - No 206 carries `Accept-Ranges` now, as on Render.
  - The plugin ConfigMap is now `bex-client-ip-headers-plugin-9dg4gd6h78`, so Traefik restarts on the new code.
  - Tests: `TestIconTagsFollowRendersEdgeCompression`, `TestIconRangesGetTheIdentityBytes`, `TestCompressionOf`, `TestNoAcceptEncodingMarkerLeavesTextToTheEdgesDecoder`, the plugin's `TestStaticSiteMarksNoAcceptEncoding` (compiled and under Yaegi v0.16.1), the operator's `TestStaticSiteMarkerMiddlewareIsStaticSiteOnly`, and the opt-in `TestStaticSiteOnTheDeployedTraefik`. That last one runs the real static server behind the pinned Traefik with the plugin interpreted. It passes, and with the marker left out of the chain it fails with the production symptom: a weak tag and no `Content-Length`. The icon tests fail with the icon types moved back to the origin class, and the marker cases fail with the marker check removed.
  - Checks: `make test` and `make lint` pass. ADR029 § Edge-compressed types and the ADR018 static-site row record it.
- **Seen, not judged here:** Render sends `font/ttf` for an `.otf` file (`runny-ai`'s `MaterialIcons-Regular.otf`, one sample), and bex sends `font/otf`.
- Parked: production's pin `f797f525f5df` predates the fix. Once the pin carries `1d9af0ece`, run this note's Acceptance in `bex-canary` and close it. Traefik takes the plugin from `main` through Argo, so it is live before the operator writes the middleware.
