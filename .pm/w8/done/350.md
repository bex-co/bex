# A native cron job's own command and the pre-deploy command miss a secret file the image was not built with, until the next build

Why: Render puts every secret file in a native service's root directory "at runtime", with no condition (render.com/docs/configure-environment-variables). Since w8/348, `native-init` links the mounted files at every start, but these two workloads start without it, so after a deploy that does not build they still see only the names the image was built with.

- Severity: minor. It affects a cron job with its own command, and a paid service's pre-deploy command, after an environment-group link, a file added to a linked group or a "Save and deploy" that adds a file. The file is at `/etc/secrets/<name>` throughout, and the next build puts it in the root.
- Found by: the w8/348 worker, 2026-11-20, from the code. Not reproduced on production.

## Where

- The cron container replaces the image's entrypoint when the cron has a command: `container.Command = shellCommand(command)` in `cronPodSpec` (`lego/operator/internal/controller/app_controller.go`, the `default:` branch). Only a cron linked to a native build source passes the command as `Args` to the entrypoint (`launchNativeArgs`, w2/m262).
- The pre-deploy Job runs `preDeployArgv`, which for a native image is `/bin/sh -c <command>` as the container's `Command` (`app_controller.go`, `preDeployArgv`, w8/172).
- Both use the release's image and mount `/etc/secrets`, so they get the image's build-time links (`nativeSecretFileLinks`, `lego/operator/internal/build/native.go`) and nothing else.

## Options

- Run both through the image's entrypoint (`Args` instead of `Command`), as `launchNativeArgs` does. A native image's entrypoint is `native-init` or `[]` since w8/m61. Check images from before w8/m61, whose toolchain entrypoint would then receive the arguments, and whether rewriting the CronJob template on the operator upgrade is safe.
- Or give the `/bin/sh -c` script the same link step as a prefix, for native images only.

## Acceptance

- A native cron job with its own command, linked to a group with a secret file after its last build, reads `./<name>` on its next triggered run with no build in between. After an unlink the name is gone from the root.
- The same for a paid service's pre-deploy command on the link deploy.
- Regression tests in the operator suite. Docker and image services keep `/etc/secrets` only.

## Fixed (2026-11-20, `/loopx w8`)

- Both workloads now start under the image's entrypoint, as the service's start command does (`runsNativeEntrypoint`, `lego/operator/internal/controller/deployment_projection.go`). A native cron job's own command is the container's `args`, `/bin/bash -c <command>`: the shape of the image's CMD, which a cron linked to a native build source already used (w2/m262). The pre-deploy command and the initial deploy hook are `/bin/sh -c <command>` as `args` (`preDeployLaunch`). `native-init` then links the files mounted for that run (w8/348). Docker, prebuilt and buildpack images keep the command in place of their program. So does a release with no start command, which no native build has (a rollback across a runtime change).
- The pre-deploy command takes the launch the release's instances will have (`selectedLaunch`); the hook takes the live instance's (`containerLaunch`). A cron release reads its own command's launch back from its record (`commandLaunch`), so a Restart or rollback across a runtime change runs a Docker image as a Docker image.
- The two questions above. An image built before w8/m61 still has its toolchain's entrypoint, which then receives the arguments, as it already did for that image's start command and for a no-build rerun (`servedBuildRerunLaunch`): Node's `docker-entrypoint.sh` runs them, and the Python, Ruby, Go, Rust and Elixir images set none. Both shells are absolute paths, so an empty `PATH` still starts them (w8/m61). Rewriting the CronJob template on the operator upgrade is safe: it reaches the next run only, never a run in flight. A Restart or rollback of a release recorded before this change keeps that release's shell launch, and a pre-deploy Job already created is never rewritten (`EnsureOwnedJob` adopts it).
- Tests: `native_entrypoint_launch_test.go` (the cron launch per builder; the record round trip, both runtime-change rollbacks included; the hook), `TestPreDeployLaunch`, `TestJobPassesArgsToTheImageEntrypoint`, the literal-runtime test running the native cron's and the pre-deploy's argv, and the envtest `native_entrypoint_launch_envtest_test.go` (a native service's pre-deploy Job and a native cron's CronJob on a real API server: no `command`, the arguments, `/etc/secrets` mounted). With `runsNativeEntrypoint` back to the old rule they all fail; without `commandLaunch` the record cases fail.
- Container check: `native-init` built from this tree as the entrypoint of a `golang:1.27.2` image whose build step linked `own.txt gone.txt`, with `/etc/secrets` mounted read-only holding `own.txt grp.txt`. Passed as arguments (the new launch), both `/bin/bash -c` and `/bin/sh -c` read `./grp.txt` and find `./gone.txt` removed. With `--entrypoint` (the old launch) `./grp.txt` is missing and the run exits 1. An exit status passes through.
- Not checked on production: a cron job and a pre-deploy command need a paid plan, and QA fixtures are free only. The service side of the same linking is w8/348's production check.
- ADR013 and ADR018's secret-files row record it.
