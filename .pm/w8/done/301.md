# A deploy a Blueprint sync starts reads `trigger: other`, not Render's `blueprint_sync`: the row is written with a bare `"blueprint"` that the REST mapping never learned

Why: Render's deploy `trigger` is a closed enum (`api`, `blueprint_sync`, `deploy_hook`, `deployed_by_render`, `manual`, `other`, `new_commit`, `rollback`, `service_resumed`, `service_updated`; w8/058), and `blueprint_sync` is its value for a deploy a Blueprint sync started. bex knows the cause and stores it as `bexTrigger: "blueprint"`, but REST maps it to `other`. A client that sorts deploys by cause therefore cannot tell a sync's rollout from any unexplained one:

- the pinned CLI's `bex deploys list`;
- a Render-generated SDK;
- the Terraform provider.

**Severity:** minor (the deploy is correct; only its stated cause is wrong). **Attribution:** server (bex-api deploy trigger mapping). **Estimate:** ~30m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `7788`, 2026-11-13 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `8acf1d116941`.

## Evidence

1. **Create:** the unmodified Render template `render-examples/fastify-hello-world` was planned and approved with `bex ea blueprints create --repo https://github.com/render-examples/fastify-hello-world --name qa-20261113-7788-fst --auto-sync=false -o json` and `bex ea blueprints approve <exs-…> --confirm -o json`. The free service `fastify-hello-world-example-xb2h` (`srv-dbr8leshd5js73aueqag`) went live at 04:02:29 UTC.
2. **Drift:** `bex services update <srv> --start-command "echo drift-7788 && node app.js" --health-check-path / -o json --confirm` exited 0 and saved without deploying.
3. **Plan:** `bex ea blueprints plan <exs-…> -o json --confirm` planned one `update` with `changedFields: [startCommand]`. `healthCheckPath`, which the file does not declare, was correctly left out. This matches Render's documented behavior: "if any such changes conflict with Blueprint-defined configuration, the next Blueprint sync overwrites them".
4. **Approve:** `bex ea blueprints approve <exs-…> --confirm -o json` restored `startCommand: node app.js`, kept `healthCheckPath: /`, and opened a deploy.

`GET /v1/services/srv-dbr8leshd5js73aueqag/deploys`:

```text
dep-dbr8nrshd5js73aueqqg  created  trigger=other  bexTrigger=blueprint   ← the sync's rollout
dep-dbr8leshd5js73aueqb0  live     trigger=other  bexTrigger=create
```

`bex deploys list <srv> -o json` shows the same `trigger: other`. The service and the Blueprint were deleted afterwards.

## Root cause

- **The write:** `lego/backend/internal/apps/deploy.go:4196-4210` (`recordBlueprintRedeploy`) writes the row with the literal trigger `"blueprint"`.
- **Not a constant:** the value is not one of the `store.Trigger*` constants (`lego/backend/internal/store/store.go:283-313`) and not in `store.AllTriggers` (`:317`). So the w8/058 conformance test, which seeds every `AllTriggers` entry, never sees it.
- **The mapping:** `lego/backend/internal/deploys/rest.go:321` (`renderTrigger`) passes through only the values it lists, so `"blueprint"` falls to the default, `other`.

## Fix

- **Name it:** add `store.TriggerBlueprintSync = "blueprint_sync"` (or keep the stored `"blueprint"` and name it as a constant), use it in `recordBlueprintRedeploy`, and add it to `AllTriggers`.
- **Map it:** have `renderTrigger` map it to `blueprint_sync`, and keep `bexTrigger` as is.
- **First deploys:** decide, and record in ADR018's deploy row, the trigger of a Blueprint-created service's first deploy. It reads `other` / `bexTrigger: create` today, and Render most likely reports `blueprint_sync` for it too, though no capture shows it (w8/296 Unverified).
- **Dashboard and events:** check whether the dashboard's deploy list labels a sync's rollout, and whether the events feed's `deploy_started` trigger flags have anything to set (today they are all `false` for it).

## Blast radius

- **Deploys affected:** every deploy a Blueprint sync, approval or auto-sync opens on an existing service.
- **Surfaces:** REST `GET /v1/services/{id}/deploys` and `/{deployId}`, the pinned CLI's `deploys list`, and MCP if it shares `toRenderDeploy`.
- **Unchanged:** GraphQL's bex vocabulary.

## Regression checks

- **Go test:** `renderTrigger(store.TriggerBlueprintSync)` returns `blueprint_sync`. The conformance suite seeds the new constant through `AllTriggers`, and `recordBlueprintRedeploy` writes it.
- **Production:** the 7788 steps. The sync's deploy reads `trigger: blueprint_sync`.

## Dedupe

- w8/058 (done) mapped `create` and `config_change` and listed `blueprint_sync` in Render's enum, but bex's Blueprint redeploy value was outside its constant set.
- w8/296 (done) noted the first-deploy question as unverified.
- No `.pm` item covers the sync's rollout trigger.

## Resolution

**DONE 2026-11-13.** `store.TriggerBlueprintSync` names the stored `"blueprint"` (kept, so earlier rows read the same) and joins `AllTriggers`. `recordBlueprintRedeploy` writes it, and `renderTrigger` maps it to `blueprint_sync`, so REST, MCP and the pinned CLI's `deploys list` report a sync's rollout as Render does. `bexTrigger` and GraphQL keep `blueprint`, which the dashboard already labels. ADR018's deploy row records the mapping. First deploys are unchanged: a Blueprint-created service's first deploy is a `create` and reads `other`, as every first deploy does; what Render reports for it stays unverified. The events feed is unchanged: Render's `deploy_started` trigger has no Blueprint flag. Production check after the next roll: the 7788 steps' sync deploy reads `trigger: blueprint_sync`.
