## Closed — 2026-11-16 (loopx session)

Maintained real-image checks, run by every `native-common-image.yml` utility cohort (`TestNativeUtilityGeneratedImages`) on the published digest:

- **Archive and supplier.** The original m91 program decodes its PostgreSQL 15 custom archive with `pg_restore`. It runs at build and again at runtime with the network off, and passes the exact source, archive and three-row hashes. A genuine PostgreSQL 18 archive restores its exact rows. `psql` and `pg_dump` report 18.x, which also proves their `libpq` closure loads. A malformed archive fails. The supplier-removed control (official Node image) fails on `pg_restore`.
- **Families.** Families runs exercise the shared neighbors on the same digest: Node, Python, Ruby, Elixir and Go/Rust primaries, companions, native-init, static, `env`/`PATH`/root and cache. Run 43883107194 covers `5d6b8139`; run 43900534897 covers `4b809600`.
- **Unit tests** cover the recipe boundaries: common-base pinning, exact-environment refusal, primary order before companions, and no tenant `apt-get`.

Live client-server checks ran on production rather than in the cohort, because the cohort has no PostgreSQL server. The fixture was a Free PostgreSQL 18.6 in bex-canary plus a Free Node 24 service (t006). At build and on three runtime requests, the service ran four steps against the server:

1. `psql` created a table and inserted three Unicode, quote and comma rows.
2. `pg_dump --format=custom --inserts` dumped it (`Dumped from 18.6`, `by 18.7`).
3. `pg_restore --file=-` returned the exact INSERT rows.
4. `pg_restore --dbname` loaded them back into the server, and `psql` read them back exactly.

**Bounds:**

- No maintained check runs against a live server.
- Servers older than 18 are not exercised live.
- ARM64 is out of scope (D3).
- Cache stability rests on the digest-pinned base: an image change is a reviewed pin change, re-qualified by families.
