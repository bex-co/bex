# A static site serves `.js` as `text/javascript; charset=utf-8`, `.xml` as `text/xml; charset=utf-8` and `.webmanifest` as `application/manifest+json`, where Render serves `application/javascript`, `application/xml` and `binary/octet-stream`

Why: the `Content-Type` of three common static-site file kinds differs from Render's:

- every JavaScript bundle;
- every `sitemap.xml`, `rss.xml` and `atom.xml`, which Docusaurus, Astro and VuePress all emit;
- every PWA `site.webmanifest`.

Anything that compares responses, asserts on a type, or keys a cache or CDN rule on one sees bex differ from the Render site it moved from. w8/323 noted the JavaScript and XML difference and left it out of its change ("both work in every browser"), but no follow-up was filed. Render parity is the top rule, and a divergence stands only when ADR018 records it with the user's sign-off.

**Severity:** minor. Browsers accept either JavaScript type for scripts and modules, and feed readers and crawlers accept either XML type. A manifest is fetched without a type check. **Attribution:** server (static-server; the uploader's type guess). **Estimate:** ~30m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `a1a1`, 2026-11-14 UTC, released `bex v0.6.0`, `https://api.bex.co/v1/`, workspace `bex-canary`, production pin `706a389d5924` (after the 06:52 UTC roll that carries w8/317–325).

## Render's behavior (black-box GETs, 2026-11-14 ~07:10 UTC)

Public Render static sites, each answer carrying `rndr-id`:

| File | Sites | `content-type` |
| --- | --- | --- |
| `.js` | `sveltekit-static.onrender.com` (`_app/immutable/**/*.js`, 6 files), `buzz-docs.onrender.com` (`_astro/page.*.js`, w8/323) | `application/javascript` (no charset) |
| `.xml` | `mentorship-guide.onrender.com/sitemap.xml`, `/blog/rss.xml`, `/blog/atom.xml`; `breadcrumbs-wiki.onrender.com/sitemap.xml`, `/blog/rss.xml`; `buzz-docs.onrender.com/sitemap-index.xml`, `/sitemap-0.xml`; `wc3v.onrender.com/sitemap.xml` | `application/xml` (no charset) |
| `.webmanifest` | `mentorship-guide.onrender.com/site.webmanifest`, `wc3v.onrender.com/site.webmanifest` | `binary/octet-stream` |

With `Accept-Encoding: br, gzip`, Render sends the `.js` and `.xml` files `content-encoding: br` and the `.webmanifest` uncompressed (`vary: Accept-Encoding` only).

The same probes match bex on every other kind captured: `.css`, `.html`, `.md` and `.txt` are `text/…; charset=utf-8` (w8/323); `.json` is `application/json`; `.svg` is `image/svg+xml`; `.ico` is `image/vnd.microsoft.icon`; and `.png`, `.gif` and `.webp` carry their image types.

## bex (fixtures `qa-20261114-a1a1-svk`, `qa-20261114-a1a1-mime`)

- **The same template:** a fresh import of `render-examples/sveltekit-static` serves every `_app/immutable/**/*.js` as `text/javascript; charset=utf-8`, where Render's copy of the template serves `application/javascript`.
- **One file per extension:** the static site `srv-dbs0fu7nl79c73bm6ajg` builds from `octocat/Spoon-Knife` with a build command that writes a one-byte file per extension (`printf x > out/f.$e`), publish path `out`. It answers:
  - `.js`, `.mjs` and `.cjs` → `text/javascript; charset=utf-8`;
  - `.xml` → `text/xml; charset=utf-8`;
  - `.webmanifest` → `application/manifest+json`.

  Every other extension above matches Render. Both fixtures were deleted afterwards (GET `/v1/services/{id}` → 404).

## Root cause

- **Upload:** the publish Job's upload container runs `aws s3 sync` (`lego/operator/internal/publish/publish.go:494`) in `amazon/aws-cli:2.22.35` (`:52`). That CLI bundles Python 3.12 (`libpython3.12.so.1.0`) and the image has no `/etc/mime.types`. Python 3.12's built-in table stores `.js`/`.mjs` as `text/javascript`, `.xml` as `text/xml` and `.webmanifest` as `application/manifest+json`.
- **Charset:** `S3Origin.Get` (`lego/operator/internal/staticserver/s3origin.go:119`) passes the stored type through `declareUTF8Text` (`:132`, w8/323), which adds `charset=utf-8` to any valid-UTF-8 `text/*`.
- **Served type:** `contentType` (`lego/operator/internal/staticserver/staticserver.go:1126`) prefers the origin's type over every table. `staticExtensionTypes` maps `.cjs` to `text/javascript; charset=utf-8` itself (`:1147`).

## Fix (target behavior)

- In `contentType`, serve Render's captured types by extension, ahead of the origin's guess:
  - `.js` → `application/javascript`;
  - `.xml` → `application/xml`;
  - `.webmanifest` → `binary/octet-stream`.

  `.mjs` and `.cjs` were not captured on Render. Give them `.js`'s `application/javascript`, and record that as an uncaptured choice. A saved `Content-Type` header rule still wins (w4/272).
- **Check the dependants of the new types:**
  - Brotli/gzip: `compressibleType` (`encoding.go:108`) already counts `application/javascript` and `application/xml` and does not count `binary/octet-stream`, so `.js`/`.xml` stay compressed and a manifest goes out uncompressed, as on Render.
  - The ETag: `contentETag` (`staticserver.go:737`) computes from `contentType(reqPath, …)`, so it follows the new type.
  - `nosniff` still allows `application/javascript` as a script type.
- Leave every other extension's type unchanged. Fonts, `.map`, `.wasm`, `.avif` and media were not captured on Render, and bex's current types are the IANA ones.
- **Docs:** record the captured table in ADR029 next to the w8/323 charset note, and update ADR018's static-site row.

## Blast radius

- Every static site, which all share the static-server.
  - The 404.html page (`staticserver.go:453`) and rewrite targets resolve their type through `contentType` too.
  - Objects that were already published change type on the next fetch after the roll. Nothing needs republishing.
- Web services are unaffected; they serve their own types.
- Callers of `contentType`: `staticserver.go:453`, `:520`, `:737`.
