## Objective

Wrap the blueprint sync's project/environment grouping loop in one control-plane-store transaction so a mid-loop failure (store error, ACL write error, context cancellation) rolls back every grouping row from that sync instead of persisting a partial set.

## Context

- Round-7 triage (`w1/049` #5): the grouping loop writes row-by-row with no transaction; the action plan runs first but omits groupings.
- Store: `lego/backend/internal/store/blueprints.go` + the projects/environments store files; service loop in `lego/backend/internal/apps/blueprint.go` (`runSync`/apply path).
- OpenFGA tuple writes can't join a Postgres tx — order so tuples are written after commit, and compensate (delete tuples) on post-commit failure, or write tuples idempotently keyed so a retry heals; pick the simpler shape consistent with existing store patterns.

## Steps

1. Trace the grouping apply loop; identify every write (rows + ACL tuples).
2. Move row writes into one tx; define the tuple-write ordering/compensation.
3. Injected-failure test: fail after N groupings ⇒ zero rows persisted.

## Files

- `lego/backend/internal/apps/blueprint.go`
- `lego/backend/internal/store/` (blueprints/projects/environments)

## Acceptance criteria

- [ ] Mid-loop failure leaves no grouping rows from that sync (integration test, real Postgres).
- [ ] Successful sync behavior unchanged.
