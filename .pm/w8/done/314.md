# A sandbox create from an image still importing answers `400 SANDBOX_IMAGE_NOT_READY` by id or `404 build_not_found` by name, and a connect-token mint on an ended sandbox answers `409 SANDBOX_ENDED`, where Render's contract answers `409 build_not_succeeded` and `409 sandbox_not_running`

Why: Render's pinned OpenAPI (`render-public-api-1.json`) documents a create from a build that has not succeeded as `409 build_not_succeeded`, both by `buildId` and when "no build with the specified name has succeeded". It documents both connect-token mints on a terminated or errored sandbox as `409 sandbox_not_running`. The Render SDK branches on those exact pairs, so on bex a create racing an image import raises the wrong exception. ADR018 grades the `buildId`/`buildName` row "✅ Matches Render" while recording the bex code. This is the same class as w8/312 (done), on the operations it did not cover.

**Severity:** minor (status and machine-readable code; the messages are right and the CLI prints the same sentence after the fix). **Attribution:** server (bex-api sandbox service). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `daae`, 2026-11-13 UTC, released `bex v0.6.0` (Render CLI v2.36.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `1c4d721bc8dc`.

## Evidence

Fixtures: group `sbg-dbrm5old9ioc73ds1aqg`, image `sbb-dbrmardgh3vs73b14mlg` (`bex sandbox-groups images import docker.io/library/node:22 --name qa-daae-node`, status `running` during the probes), and sandbox `sbx-dbrm6cdd9ioc73ds1b60`, stopped with `bex sandboxes stop` at 19:27:33 UTC.

| Request | bex answers | Render's pinned contract |
| --- | --- | --- |
| `bex sandboxes create --group <sbg> --image sbb-dbrmardgh3vs73b14mlg` (REST `POST /v1/sandboxes` `{"buildId": …}`) | `400 {"code":"SANDBOX_IMAGE_NOT_READY","message":"image sbb-… is running; a sandbox can start from it once it has succeeded",…}` | `409 build_not_succeeded`: "The specified build has not succeeded" |

The consumer that breaks is the Render Python SDK 1.8.0 (package `render`, required by `render-sdk==1.8.0`):

- `render/experimental/sandbox/api.py:320-335` (`_handle_image_api_error`, used by `create sandbox` at `:406`) raises `ImageNotReadyError` only for `409` with `build_not_succeeded` (`_IMAGE_NOT_SUCCEEDED_CODE`, `:144`), and `ImageNotFoundError` for `404 build_not_found`. On bex, a create from an importing image raises a generic client error by id, and `ImageNotFoundError` by name, so retry-until-ready code keyed on `ImageNotReadyError` gives up.
- `render/public_api/models/error_code.py` lists `BUILD_NOT_SUCCEEDED` and `SANDBOX_NOT_RUNNING` as typed constants; neither of bex's codes is in it.

The pinned CLI's `explainConflict` (v2.36.0 `pkg/sandbox/repo.go`) keys on the 409 status and then GETs the sandbox, so its output does not depend on the code and is unchanged by the fix. bex's own deploy path already answers Render's pair for build sources (`POST /v1/services/{id}/deploys` `buildId`: `build_not_found` 404, `build_not_succeeded` 409; ADR018 Build Sources row). `sandbox_not_running` has been in the pin since `8efafd90f` (2026-09-11), before w3/m318 chose `SANDBOX_ENDED`.

The rest of the sweep's sandbox walk passed. `create --wait` returned `running` in 6.2 s. Omitted plan and idle timeout read `1c-2g` and `900`. Exec exit codes 7, 0, 127 and 137 came through, with stdout and stderr split. File and directory copies round-tripped byte for byte, including a relative path under `/home/render`. A 300 s idle timeout suspended the sandbox within about 6 minutes, and the next exec resumed it in 4.1 s with `$HOME` kept and `/tmp` cleared (the recorded divergence). A repeat stop succeeded (exit 0). `snapshots create|list|get` and `create --from` were refused by name (`SANDBOX_SNAPSHOTS_UNSUPPORTED`). Execution records carry `stoppedAt` and `exitCode`.

## Root cause

- `lego/backend/internal/sandbox/images.go:722-726`: a build that has not succeeded is `core.NewBadRequestError(CodeSandboxImageNotReady, …)` (`CodeSandboxImageNotReady = "SANDBOX_IMAGE_NOT_READY"`, `:73`).
- `images.go:711-717`: by name, only `NewestSucceededSandboxBuild` (`lego/backend/internal/store/sandbox_builds.go:200`) is asked. Its `ErrNotFound` becomes `build_not_found` whether or not the group has a pending, running or failed build of that name.
- `lego/backend/internal/sandbox/records.go:50,66`: `sandboxEndedError` answers `CodeSandboxEnded = "SANDBOX_ENDED"`. Callers: the run mint (`exec.go:215` through `endedConflict`, `records.go:173`, and `exec.go:231`), the file mint (`file_connect.go:138`, `:147`), and suspend/resume (`service.go:1632`, bex verbs with no Render REST counterpart in the pin).

## Fix

1. `images.go`: answer a not-succeeded build with `core.NewConflictError("build_not_succeeded", …)` (409), keeping the message and `params`. Export it beside `CodeBuildNotFound`.
2. By name: when no succeeded build matches, ask whether any build of that name exists in the group, through a small store query (newest build of the name, any status). If one does, answer `409 build_not_succeeded` naming its status; if none does, keep `404 build_not_found`.
3. `records.go`: rename the code to Render's `sandbox_not_running`, keeping the "was terminated at …" / "errored" messages and `params`. Suspend and resume share the helper and take the same code, so one ended-sandbox code serves every verb.
4. Update the ADR018 rows (`buildId`/`buildName`, the terminated-sandbox row at `:516`), `docs/cli-compatibility-checklist.md:207`, and the tests that pin the old codes (`images_test.go:327`, `records_test.go:142,196`).

No dashboard or mobile code reads `SANDBOX_IMAGE_NOT_READY` or `SANDBOX_ENDED`. GraphQL and MCP share the service, so they change together.

## Blast radius

- Create from an image: REST, GraphQL `createSandbox(buildId, buildName)`, MCP `spawn_sandbox`.
- Ended sandbox: both connect-token mints (REST, which the CLI's `exec` and `copy` and the SDK's exec and file calls use), plus bex's suspend/resume.
- Out of scope and already right: `404 build_not_found` for an unknown id or another group's build, and `409 image_in_use` on build delete. An import the registry cannot serve answers `400 SANDBOX_IMAGE_UNAVAILABLE`, where Render documents a 400 with no code; the extra code is harmless. Snapshot codes wait on snapshots shipping (w8/312's follow-up note).

## Regression checks

- `POST /v1/sandboxes` with the `buildId` of a `pending` or `running` import answers `409 build_not_succeeded`; with a `failed` one too.
- `buildName` whose only builds are pending, running or failed answers `409 build_not_succeeded`. An unknown name still answers `404 build_not_found`, and a name with a succeeded build still starts the sandbox.
- Both connect-token mints on a terminated sandbox answer `409 sandbox_not_running` with "was terminated at <time>"; on an errored one, "errored". The pinned CLI still prints `Error: sandbox … was terminated at …`.
- Live, with the Render SDK: a create from an importing image raises `ImageNotReadyError`.

## Dedupe

w8/312 (done) fixed create's timeout, plan and name codes and the build list's `status`; it did not touch image or ended-sandbox refusals. w3/m318 (blocked) introduced `SANDBOX_ENDED` and graded it against the CLI's sentence, not the pinned code. w22/004 (blocked) covers list paging only.

## Resolution

**DONE 2026-11-13.**

- **Image refusals:** a create from a build that has not succeeded answers Render's `409 build_not_succeeded` (`CodeBuildNotSucceeded`, `lego/backend/internal/sandbox/images.go`), message and `params` kept. By name, when no succeeded build matches, the existing `SandboxBuilds` list (newest first) decides: a name with builds answers `409 build_not_succeeded` naming the newest one's status, and only a name no build has answers `404 build_not_found`.
- **Ended sandbox:** the shared refusal is Render's `sandbox_not_running` (`CodeSandboxNotRunning`, `records.go`), for both connect-token mints and bex's suspend and resume. Messages ("was terminated at …", "errored") are unchanged, so the pinned CLI prints the same sentence.
- **Surfaces:** REST, GraphQL `createSandbox` and MCP `spawn_sandbox` share the service.
- **Tests:** `TestImageReadsAndCreateRefusals` covers by-id 409, by-name 409 while the name's only build is importing, and an unknown name's 404. `TestTerminatedSandboxStaysReadable` and `TestErroredSandboxRefusesConnectTokens` pin the new code. All three ran against real Postgres.
- **Docs:** ADR018's terminated-sandbox and `buildId`/`buildName` rows and the CLI checklist record the codes.
- **Production check after the next roll:** `bex sandboxes create --image <importing sbb->` and REST `buildName` of an importing image answer `409 build_not_succeeded`; `bex sandboxes exec` on a stopped sandbox answers `409 sandbox_not_running` and still prints "was terminated at …".
