# A deploy that lands after the operator adopts the waiting deploy, but before bex-api records the deploy ahead as live, still cancels the waiting deploy

Why: w8/396 closed the window that opens after bex-api records the deploy ahead as `live`. One window is left before that, where the waiting deploy is still closed `canceled` although the operator runs it, and the new deploy then waits for its whole publish. Render's Wait would leave it running.

- **Where.** `adoptWaitingDeploy` (`lego/backend/internal/store/store.go`, w8/396) frees the pending slot only when no other deploy is recorded executing. The partial unique indexes allow one executing row and one waiting row per app (`0080_deploy_overlap_queue.up.sql`).
  - Deploy A serves, and the operator adopts B from the pending slot at once. Then a deploy C can land before the reconciler's next pass closes A's row `live`.
  - While A's row is still open, B cannot leave the slot. So `cancelPendingDeploys` closes B `Superseded by` C (`newDeploy`), and C waits behind A's row (202).
  - The operator still holds B's release (`releaseInFlight`) and runs it to the end. C is adopted only after B serves.
- **Not seen live yet.** In the w8/392 and w8/396 runs, C was sent after A read `live`, so it always hit the later window. This one comes from the code. A git push or a configuration save can land here, since neither waits for A to read `live`.
- **Fix direction.** Close the gap before the App write, without making the trigger record A's verdict itself (`recordDeploy` and `recordLifecycleFacts` own that). One option: when the App reports a waiting row adopted while an older row still reads executing, kick the reconciler and wait a few seconds for that row to close, as `rollout.AwaitAdoption` waits for an adoption. Then open the row as w8/396 does. Keep Override's cancel-and-start.

## Acceptance

- A backend test, real DB. A served, B pending, the App reporting B adopted, and A's row still open. A new deploy leaves B running and waits behind it once A's row closes. B is never `canceled`.
- Live in `bex-canary`, if a timing can be found: trigger C while A still reads `update_in_progress` after it served. Otherwise unit and real-DB tests alone, with the reason recorded.

Estimate: ~1h.

## Shipped 2026-11-22 (`2019ee694a`)

- **The rule.** Where every writer opens its deploy row, after its App write, a row opened under the App's adopted release (`store.WithAdoptedRelease`) waits while that release has reached a waiting row and an older row it has passed still reads executing. It kicks the reconciler (`PGStore.KickReconciler` → `Reconciler.Kick`, wired in `cmd/api`) and re-reads every 100 ms until the pass records the older row, at most 5 s (`DeployAheadRecordWait`; a git host's webhook waits about 10 s). It never records A's verdict itself and never refuses the deploy. Then w8/396's `adoptWaitingDeploy` frees B's slot and C answers 202 `queued` behind B. Override does not wait.
- **Where.** `awaitDeployAheadRecorded` (`lego/backend/internal/store/store.go`) runs at the start of `createDeploy`, `EnsureCheckedDeploy`, `CreateRollbackDeploy` and `CreateDeferredDeploy`, so it covers the trigger verbs, Rollback and Restart, the row-level waits, a configuration save, a git push, a checked push, a Blueprint sync and the build-source fan-out. The note suggested the wait before the App write. After it, the release the writer reads is the one its own write saw, so no adoption can slip in between the check and the write. An environment "Save and deploy" behind a deploy in flight (`deferServedBuildDeploy`, `lego/backend/internal/secrets/batch.go`) had no adopted release and now passes one.
- **Tests.** Real DB:
  - `TestPGDeployWaitsForThePassThatRecordsTheDeployAhead` and `TestPGDeferredDeployWaitsForThePassThatRecordsTheDeployAhead` cover a deploy C and a deferred Restart. A kick runs the reconciler's own `recordDeploy` of A from an App that serves A and has adopted B. A closes `live`, B stays in progress and is never canceled, and C waits in the pending slot.
  - `TestRESTTriggerWaitsForThePassThatRecordsTheDeployAhead` drives C through the REST handler. C answers 202.
  - `TestPGOverrideDeployDoesNotWaitForTheDeployAhead` is the Override control. `TestPGWaitingDeployAdoptionNeedsAFreeSlot` now also checks the bound.
  - A unit test checks that the environment save passes the adopted release.
  - Each test fails with its part of the fix removed. Without the wait, B closes `canceled` `Superseded by` C, as in production.
- **No live check: no reliable timing exists.** The window runs from the operator adopting B to the reconciler's next pass. For a client, A reads `update_in_progress` the whole time. In w8/396's run the served content changed about 2 s after A read `live`. So nothing a client can see marks the adoption, and a C sent "after A served, before A reads `live`" can't be told apart from one that lands before the adoption. That case correctly replaces B, which never ran. The real-DB tests are the evidence. w8/396's parked A/B/C check exercises the neighbouring window once the pin carries `fab9600c58`.
