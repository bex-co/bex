# A failing instance keeps receiving traffic for ~30 s after its health check starts failing; Render stops routing to it after 15 s

Why: [Render's health-check docs](https://render.com/docs/health-checks) say: "If a running service instance fails consecutive health checks for 15 seconds, Render temporarily stops routing traffic to it". Checks run "every few seconds" with a 5 s deadline, and a restart follows at 60 s. Bex's readiness probe runs every 10 s with Kubernetes' default 3 failures, so a broken instance stays in rotation about twice as long. On a multi-instance or autoscaled service, users get errors from the failing instance for an extra ~15 s where Render would already have shifted them to healthy peers. ADR018's health-checks row and the comment at `deployment_projection.go:86–94` record "one deliberate divergence" (cost of probing tenant paths) without a user sign-off.

**Severity:** minor. **Attribution:** platform runtime (readiness probe timing). **Estimate:** 30m. **Source:** `/qa-find-bugs-cli` sweep 1324, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1324--health-check-rotation)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `21652364739c`, `bex-canary`. Free image web service (`python:3.12-alpine`), `healthCheckPath: /health`, whose `/health` turns to 500 after `GET /fail` (`srv-dbctc5rpgbls73dcpb40`, deleted 204 → 404). After `GET /fail` at t+0, polling `GET /` once per second:

| Time | Edge |
| --- | --- |
| t+1 s … t+33 s | 200 from the failing instance |
| ≈ t+29 s | `server_failed` event (09:24:26Z) |
| t+34 s | client TLS handshake timeout (single occurrence) |
| t+58 s | 503 `{"error":"service not ready"}` (activator readiness hold) |
| t+109 s | 200 from the restarted instance (`server_available` 09:25:45Z) |

The restart roughly tracks Render's 60 s window (the liveness threshold) plus restart and boot time. Removal took about 30 s rather than 15 s.

## Expected

The instance leaves rotation after 15 s of consecutive failed checks: a 5 s period × 3 failures, with the existing 5 s timeout. The restart stays at 60 s (period 5 s × 12 failures, or the current derived constant at the new period).

## Root cause

`lego/operator/internal/controller/deployment_projection.go:86–106,318–321`: `healthCheckPeriodSeconds = 10` is set on the startup and liveness probes, while the readiness probe takes Kubernetes' default period (10 s) and failure threshold (3). That is 30 s.

## Fix

Give the readiness probe `PeriodSeconds: 5`, `FailureThreshold: 3`. Re-derive the liveness threshold so the restart stays at 60 s, and keep the startup budget at Render's 15 minutes. The probe cost argument in the comment does not hold against parity: Render itself checks "every few seconds". Update the comment and ADR018's health-checks row.

## Blast radius

Every web and private service with a health check (HTTP or TCP). An app whose health path is slow (more than 5 s) is already failing under the 5 s timeout, so it is unchanged. Probe traffic to tenant paths doubles.

## Acceptance

- Envtest: the readiness probe is 5 s × 3, and the liveness window is still 60 s.
- Live after deploy: repeat the table. Traffic stops reaching the failing instance within about 15–20 s of `/fail`. Delete by ID with a 404 proof.
