# Turning on PgBouncer for a public Postgres leaves its external pool host serving a certificate without its own name

Why: the pooled external URL bex hands out (`dpg-…-pool.db.bex.co`) must verify like the primary URL does. After `--connection-pool pgbouncer` on an existing database, PgBouncer keeps serving the pre-change certificate, which names only the primary host. Any client that verifies the hostname (`sslmode=verify-full`, `sslrootcert=system`, the drivers Render's docs recommend) cannot connect through the pool. A database restart does not fix it.

**Severity:** major (the pooled external connection string fails for verifying clients indefinitely; the same mechanism likely leaves poolers on the old certificate after every renewal). **Attribution:** operator (pooler TLS reload). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `88c4`, 2026-11-10, released `bex v0.5.0` (Render CLI v2.35.0), production pin `4630a48a7`.

## Root cause

- `lego/operator/internal/controller/database_public_tls.go:57-60` states that "the pooler's client-facing certificate IS the cluster's serverTLSSecret, so the pooler's public SNI name must be (and is) on the certificate". Enabling the pooler changes the name set, so cert-manager re-issues `<db>-public-tls` (`:80-84` budget note). The `cnpg.io/reload` label (`:91-94`) hot-reloads **PostgreSQL** only. The PgBouncer pods created by `reconcilePooler` (`database_controller.go:1329-1360`, `poolerSpec`) started on the old Secret contents and never reload them, so they serve the old certificate until they are recreated (here: by toggling the pooler off and on).
- **Inferred, not observed:** a routine renewal (cert-manager renews well before the 90-day expiry) has the same effect. The poolers keep the previous certificate until it expires, and then every TLS client of the pool fails.

## Fix

Roll the Pooler's pods whenever the served certificate changes. In `reconcilePooler`, stamp the Pooler `spec.template.metadata.annotations` with the public TLS Secret's certificate serial (or its `resourceVersion`/hash), so CNPG rolls PgBouncer when it changes. Keep `poolerAdoptsDatastorePriority`'s template handling intact; it currently deletes `template`. Alternatively order the Pooler only after the Certificate covering its name is Ready. Both are needed for the enable-on-existing case and the renewal case.

## Acceptance

- envtest: a public Database whose `<db>-public-tls` Secret changes serial → the Pooler template annotation changes. An unrelated reconcile does not change it.
- Live: on a fresh public `0.1c-256mb` database, `bex pg update <id> --connection-pool pgbouncer`, then within 2 minutes `psql "<externalConnectionPoolString>"` with `PGSSLROOTCERT=system` returns a row, and `openssl s_client -starttls postgres -servername <id>-pool.db.bex.co` shows the same serial as the primary host.
- Read replicas: confirm the replica SNI hosts (CNPG instances, reloaded via `cnpg.io/reload`) present the re-issued certificate after a replica is added. Not exercised in this sweep.

## Done — 2026-11-10

`reconcilePooler` (`lego/operator/internal/controller/database_controller.go`) stamps the Pooler's Pod template with `app.bex.co/served-certificate`. Its value is a sha256 digest of the `tls.crt` in the Cluster's `spec.certificates.serverTLSSecret`, the certificate PgBouncer serves (`database_pooler_tls.go`). CNPG then rolls PgBouncer when the certificate changes, whether a re-issue on pooler enable or a renewal, and never on an unrelated reconcile. An existing Pooler that the priority rule leaves alone keeps its live template, with only the annotation added. A private database, which serves CNPG's own certificate, gets no annotation. The reconcile runs again after a re-issue through the public-TLS pending requeue (30 s), and after a renewal through CNPG's Cluster status update, since the Cluster is owned. `TestPoolerRollsWhenItsServedCertificateChanges` covers: no stamp while private, a stable digest across reconciles, and a new digest after a re-issue. ADR009 records the rule. Live re-check (enable the pooler on a public database; the pooled `verify-full` psql returns a row within 2 minutes) after the 19:00 UTC deploy, with w8/m149's closeout. The read-replica SNI check stays as noted: CNPG instances reload through `cnpg.io/reload`.
