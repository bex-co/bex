# A Blueprint database with no `ipAllowList` is private on bex, but Render documents it as open to all IPs

Why: Render's Blueprint reference says an omitted Postgres `ipAllowList` means "Render allows all IPs for a new database (all connections require valid credentials)". Projects rely on that to run migrations or admin scripts from outside with the External Database URL. Bex creates the same database private (`ipAllowList: []`, `public: false`). The imported app then crash-loops on missing tables, and the owner's documented recovery path (`psql`/migrate from outside) is refused until they discover and edit the allow list. Bex's REST create already follows Render's public default (w2/038), so only the Blueprint path differs.

**Severity:** major (a real Render Blueprint's documented setup flow fails on import). **Attribution:** server (Blueprint datastore create default). **Decision note:** ADR009:238/261 call the private Blueprint default "Bex-native" but do not weigh it against Render's documented Blueprint default; confirm before implementing. **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1273, 2026-10-21 ([evidence](evidence/cli-sweep1273/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, deployed pin `9cace6b6e25d`, workspace `tian-personal` (bex-canary's single free Postgres slot is held), human device-login grant, HEAD-built pinned CLI.

1. Connect the real Blueprint `D-Atharv/feature-flag-service` (`POST /v1/blueprints`, branch `main`). It declares `databases: [{name: ffs-postgres, plan: free, postgresMajorVersion: "16"}]` with no `ipAllowList`, a free Key Value with `ipAllowList: []`, and a free Docker web service whose `DATABASE_URL`/`REDIS_ADDR` come from `fromDatabase`/`fromService … connectionString`. Its `scripts/render-migrate.sh` runs migrations from outside against "Render dashboard -> ffs-postgres -> Connect -> External Database URL", because "the free web service plan rejects preDeployCommand".
2. `GET /v1/postgres/dpg-dbc61165u6js73eso46g` → `ipAllowList: []`, `public: false`.
3. The service crash-loops: `load api keys: … relation "api_keys" does not exist`. The project expects the operator to migrate from outside.
4. `bex psql dpg-dbc61165u6js73eso46g -c 'select 1'` → `Error: IP address (<client-ip>) not in allow list for ffs-postgres`.
5. Recovery on bex required `bex pg update … --ip-allow-list cidr=<v4>/32 --ip-allow-list cidr=<v6>/128 --confirm`. After that the two goose `Up` sections applied through `bex psql -c`, and a manual `bex deploys create … --wait` went `live`. `/readyz` reported Postgres and Key Value ready. So the rest of the Blueprint works; only the access default blocked it.

All four resources were deleted (Blueprint 204 → 404; service, Postgres and Key Value 204 → 404).

## Expected

[Render Blueprint reference, Postgres `ipAllowList`](https://render.com/docs/blueprint-spec): omitted → "Render allows all IPs for a new database (all connections require valid credentials)". `ipAllowList: []` → "block all external connections". Key Value differs: Render requires the field, and an explicit `[]` is private, which bex already honors.

Target: a Blueprint-created Postgres with no `ipAllowList` is public with an unrestricted rule, as REST create already does (ADR009:233). Together with [w8/140](blocked/140.md) (`0.0.0.0/0` must admit IPv6), that means `0.0.0.0/0` plus `::/0`. Blueprint export then round-trips the public intent, which it already emits for a public database with no rules (ADR009:238). A later sync that omits the field keeps preserving the saved list (w2/m166, unchanged).

## Root cause

Blueprint database creation keeps the native private default when `ipAllowList` is absent. ADR009:238 ("omission keeps the Bex-native private default") and :261 ("Blueprint creates remain private when `ipAllowList` is omitted") record that choice. The REST adapter's Render default (w2/038, ADR009:233) runs only on `POST /v1/postgres`. The Blueprint compiler/apply path that maps `databases[]` to `CreatePostgresRequest` leaves `Public` false when the key is absent. Locate it from `blueprint_plan.go`/`deploy.go`'s database create mapping.

## Fix

In the Blueprint database create mapping only, treat an absent `ipAllowList` as Render's public default: `public: true` with no restricting rules (or explicit `0.0.0.0/0` and `::/0`, matching the REST default's representation). Leave explicit `[]`, nonempty lists and sync-time omission semantics unchanged. Plan and preview should state "external access: all IPs (credentials required)" for such a database. Native GraphQL/MCP/dashboard creates keep their private default. Update ADR009:238/261 and ADR049.

## Acceptance

- Plan/apply test: a Blueprint database with no `ipAllowList` is created `public: true` and unrestricted. `[]` stays private, and a CIDR list is restricted and public. A second sync omitting the field changes nothing (w2/m166 control).
- Export/re-import round-trips the database's access unchanged.
- Live after deploy, on a fresh free fixture in a workspace with capacity: Blueprint-create a database with no `ipAllowList`, and `bex psql <id> -c 'select 1'` succeeds from outside over IPv4 and over IPv6 (after w8/140). Delete it by ID with a 404 proof.

## Blast radius

The Blueprint Postgres create path, plus its plan/preview text and export. Key Value is unchanged, because Render requires its `ipAllowList`. REST, GraphQL, MCP and dashboard creates are unchanged.

## Dedupe

ADR009:233 (REST default, w2/038), :238 and :261 (Blueprint/native private default, w2/m166). w8/140 (IPv6 under `0.0.0.0/0`, fixed and awaiting release) and w9/m164 (dual-stack trap) are related but separate. No item compares the Blueprint default with Render's documented Blueprint default.
