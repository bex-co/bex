## Objective

Make each authorization decision already selected by the audit policy explain which relation and verified OAuth delegation facts governed it, without turning audit storage into a token or free-form metadata sink.

## Context

- `lego/backend/internal/core/audit.go` builds fixed-shape `AuditEvent` values at the `core.Base` interception point.
- `lego/backend/internal/store/audit.go` persists `audit_events`; migrations currently end at `0087`.
- `lego/backend/internal/audit/` projects the same store rows through Render-shaped REST and Bex GraphQL reads consumed by `dashboard/src/features/audit/`.
- Existing volume policy records allowed and denied writes plus denied reads; this milestone enriches those selected decisions rather than logging every successful read.

## Steps

1. Extend the fixed audit event/row schema with the required relation and nullable, bounded OAuth client id, accepted audience, and canonical scope set; add the next reversible Postgres migration and indexes only where query evidence requires them.
2. Populate the fields exclusively from `core.Identity` and the server-selected relation at the shared emit seam; session, machine, system, and pre-migration rows remain valid with absent OAuth provenance.
3. Thread the fields through the audit store and neutral service projection, then expose them as additive Bex metadata on existing REST/GraphQL audit reads without changing Render event/status semantics.
4. Render a concise delegation summary in the existing dashboard Audit Log detail/row affordance, with safe fallbacks for old and non-OAuth rows.

## Acceptance criteria

- [ ] A recorded third-party OAuth decision returns subject, client id, accepted audience, canonical capabilities, required relation, and outcome over the existing audit read surfaces.
- [ ] Session, machine-key, system, and pre-migration events remain readable with explicit absent provenance.
- [ ] Database constraints and application normalization bound every new field and reject non-canonical capability values.
- [ ] No bearer token, refresh token, authorization code, raw introspection body, request body, or caller-supplied free-form metadata can enter the audit row.
- [ ] The migration round-trips against real Postgres and existing audit pagination/retention behavior stays intact.

## Out of scope

- Logging every successful read.
- Storing token hashes or reconstructable credentials.
- A new standalone OAuth-audit API.
