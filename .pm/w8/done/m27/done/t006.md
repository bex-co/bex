## Objective

Verify that Bex's OAuth extension preserves Render-compatible resource behavior and that every Bex surface expresses the same capability denial, audit provenance, and platform-client compatibility contract.

## Context

- Render does not expose Bex's third-party OAuth/MCP provider contract, so granular scopes are an additive security extension rather than a claim of upstream feature equivalence.
- Bex resource verbs still promise matching semantics across REST, GraphQL, MCP, dashboard, and the official CLI launcher.
- `docs/ADR018-render-parity.md` is the authoritative place to name supported behavior and deliberate divergence.

## Steps

1. Exercise representative read, write, and sensitive operations through REST, GraphQL, and MCP with the same scoped identities and compare error codes/parameters.
2. Verify dashboard session behavior and the unmodified official CLI launcher remain unchanged while third-party OAuth callers are narrowed.
3. Check audit REST compatibility for additive fields and GraphQL/dashboard consumption, avoiding a fabricated claim that Render supports Bex OAuth scopes.
4. Update the parity ledger and CLI compatibility checklist with evidence or file a concrete follow-up before closeout for any real drift.
