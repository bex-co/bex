## Objective

Preserve the server-verified OAuth client, platform marker, accepted audience, and canonical capability set from Hydra introspection through the request context without retaining the bearer token.

## Context

- `lego/backend/internal/api/auth.go` already decodes Hydra's `client_id`, `aud`, and space-separated `scope`, but `core.Identity` retains only the client id and human/machine class.
- `lego/backend/internal/core/identity.go` is the context contract consumed by every feature's shared `core.Base`.
- Positive introspection results are cached; a cached identity must carry the same normalized grant facts as the cache miss that produced it.

## Steps

1. Extend `core.Identity` with immutable OAuth provenance sufficient for authorization: canonical deduplicated capability scopes, the accepted API audience, and whether the client was verified as platform-marked.
2. Normalize Hydra's scope and audience values at introspection, bound their cardinality/length, reject malformed or ambiguous values, and retain only the closed capability vocabulary plus the compatibility scope needed by the gate.
3. Resolve the platform-client marker once on the cache-miss path when the human-token policy needs it, fail closed on lookup errors, and carry the verified result into the cached identity.
4. Keep Kratos-session and machine-key identity construction explicit so neither can accidentally acquire a human-delegation grant from empty/default fields.

## Acceptance criteria

- [ ] Two semantically equivalent Hydra scope strings produce one sorted, deduplicated capability representation.
- [ ] The identity records only the audience Bex actually accepted, not arbitrary token audiences.
- [ ] Cache hits and cache misses authorize from identical provenance.
- [ ] No raw access token, refresh token, authorization code, or unbounded introspection field reaches `core.Identity`, a log, or an audit row.
- [ ] Session and machine-token identity fixtures remain distinguishable from third-party human OAuth tokens.

## Out of scope

- Changing Hydra's token format or issuing custom JWT claims.
- Persisting live access tokens or introspection responses.
