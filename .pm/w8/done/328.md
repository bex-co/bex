# A new Python uv project with no `UV_VERSION` builds with uv 0.12.10; Render's default for services created since 2026-11-03 is uv 0.13.7

Why: Render picks a Python uv project's default uv by the service's creation date, as it does the interpreter. Its [uv version page](https://render.com/docs/uv-version) gives:

| Service created | Default uv |
| --- | --- |
| 2026-11-03 and later | 0.13.7 |
| 2026-10-12 to 2026-11-03 | 0.12.24 |
| 2026-09-09 to 2026-10-12 | 0.12.10 |

bex has one constant, `0.12.10`, for every service whatever its age. So a uv project created today builds with a uv two releases older than Render's, and lock-format or resolver behavior that differs between them shows up only on bex.

**Severity:** minor (a parity drift in a default tool version; an explicit `UV_VERSION` is honored exactly). **Attribution:** operator (native Python build resolution). **Estimate:** ~30m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `5cf7`, 2026-11-14 UTC, released `bex v0.6.0`, `https://api.bex.co/v1/`, workspace `bex-canary`, production pin `706a389d5924`.

## Evidence

- **Render**, [render.com/docs/uv-version](https://render.com/docs/uv-version), fetched 2026-11-14:
  - the current default is "**`0.13.7`**";
  - "set your service's `UV_VERSION` environment variable to any version number that's compatible with your Python version";
  - the history table above, whose oldest rows are "`2026-02-11` to `2026-09-09`" → `0.10.2` and "Before `2025-06-12`" → `0.7.12`.

  PyPI has both later releases: `uv 0.12.24` and `uv 0.13.7`, the latter uploaded 2026-11-03T02:41Z.
- **bex**, on a service created 2026-11-14:
  - a free `render-examples/descope-render` import (sweep `c19f`, 00:42 UTC; `uv.lock`, no `UV_VERSION`) logged `==> Using uv 0.12.10 (from uv.lock)`;
  - the same production pin answers today.
- **Siblings, already filed:** the same sweep confirmed, on fresh free services created 2026-11-14T09:23Z with no version signal:
  - `==> Using Ruby 3.4.4 (default)` and `ruby 3.4.4 (2025-05-14 revision a38531fd3f)`;
  - `==> Using Python 3.14.8 (default)` and `Python 3.14.8`.

  Render's defaults for services created since 2026-11-03 are 3.4.12 and 3.14.10. That drift is **`w4/620`** (open), which this note does not duplicate.
- **Already matching:** Render's other current defaults, Node `24.22.1` (since 2026-10-21), Bun `1.4.4` (since 2026-10-22), Elixir `1.18.4` and Poetry `2.1.3`, equal bex's reviewed defaults.

## Root cause

- **The default:** `defaultUVVersion = "0.12.10"` (`lego/operator/internal/build/nativeversion.go:340`, w8/m81, 2026-10-16) was Render's default when w8/m81 shipped.
- **No creation date:** `ResolveNativeUV` (`:352`) takes no creation time. Every uv project without `UV_VERSION` gets that one constant (`:358`), so Render's 2026-10-12 and 2026-11-03 moves were never mirrored.
- **The call site:** `ResolveNativeBuildExact` (`nativeresolve.go:114`) has `created` in hand but does not pass it.

## Fix (target behavior)

Give uv a creation-date default, in the pattern `pythonCreationCutoff` and `rubyDefaultCutoff` use (`nativeversion.go:142`, `:158`):

- **The cutoff:** a service created at or after a new cutoff `T` (the time this change ships) defaults to `0.13.7`. One created earlier keeps `0.12.10`, so a running service's toolchain never moves under an operator upgrade.
  - Services created on bex between 2026-11-03 and `T` keep 0.12.10, where Render would give them 0.13.7.
  - Record that window as the known residual, as `w4/620` does for the interpreters.
- **The plumbing:** pass `created` from `ResolveNativeBuildExact` into `ResolveNativeUV`. A zero `created` (unknown) keeps the legacy default.
- **Unchanged:** an explicit `UV_VERSION` is still installed exactly, and the `uv.lock` opt-in is the same. The install step (`nativePythonToolInstall`, `pip install uv==<version>`) needs no change, since any PyPI release installs.
- **Messages:** keep the error text that names an example release pointing at the current default.
- **Docs:** ADR060's uv paragraph (§ "uv in native Python uv projects (w8/m81)") gains the creation-date table.

Do this together with `w4/620` if one worker takes both; they share the cutoff pattern and the date.

## Blast radius

- **Who:** only native Python services whose root directory has a `uv.lock`, across web, private, worker and cron types and their pre-deploy commands.
- **Unaffected:** services without `uv.lock`, and Poetry.
- **Callers:** one, `ResolveNativeBuildExact`. `cmd/native-resolve` reaches it through that function with the App's creation time.

## Regression checks

- **Unit:** `ResolveNativeUV` with `uv.lock` and no `UV_VERSION`:
  - created zero or before `T` → `0.12.10`;
  - created at or after `T` → `0.13.7`;
  - `UV_VERSION=0.11.0` → `0.11.0` at any age;
  - no `uv.lock` → not added.
- **Production, after the operator rolls:** import `render-examples/descope-render` fresh (free). Its build log should read `==> Using uv 0.13.7 (from uv.lock)`, and `/health` should answer 200. Delete the fixture.
