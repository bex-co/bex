## Closed — 2026-11-19 (loopx session)

- **Render's contract.** [render.com/docs/native-runtimes](https://render.com/docs/native-runtimes) lists `gettext` with the marker its legend defines as "Available both during builds and at runtime", on Debian 12 "bookworm". It names no version and lists no `locales` package (read 2026-11-19). bex supplies Debian 12's `gettext` and `gettext-base` `0.21-12` (t001). Which version Render ships is unverified, and no Render-hosted comparison was run.
- **Django's requirement.** Django's `compilemessages` asks for "GNU gettext tools 0.19 or newer" (its own error text, which the original build printed before this repair). 0.21 meets it, and the original build compiles its catalog on production (t006).
- **Build and runtime, as Render lists them.** The packages are on the one image that build, pre-deploy and runtime run (t002), so a runtime `msgfmt` works too; the original program recompiles its catalog on every request.
- **ADR060.** The D7 m96 row records the packages, the behaviors accepted, the locale limit (only `C.UTF-8`; no other system locale is claimed) and that authored environment values stay effective. It adopts with the next native rebuild on the current image, as every D7 tool does.
- **No surface change.** gettext arrives through the image every native build already uses. REST, GraphQL, MCP, Blueprint and the dashboard keep their schemas, fields and error shapes, and no selector, toggle or launcher change was added.
- **Two-client replay on production** (details in t006): published bex v0.7.0 and the unmodified Render CLI at the lego/cli pin (`render-oss/cli` `4fd34231b637`) each created one Free Python service in bex-canary with the frozen original build and start commands from `testdata/native-utilities/original-cases.json`, no installer line, the public source `git-fixtures/basic@6ecf0ef`, `PYTHON_VERSION=3.13` and `--auto-deploy=false`.
