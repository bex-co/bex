# `bex sandboxes exec` is cut off at 3 min 30 s, whether or not the command is printing

Why: on Render a sandbox command runs as long as it needs (sandboxes live up to 30 days), but on bex every exec stream dies 210 s after it starts. A test suite, `npm install` or build in a sandbox fails with an HTTP/2 `INTERNAL_ERROR`, and its execution record shows no exit code.

**Severity:** major (any sandbox command longer than 3½ minutes fails; the error names no cause). **Attribution:** server (bex-api sandbox connect stream). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `54a1`, 2026-11-10, released `bex v0.5.0` (Render CLI v2.35.0 `24ac2d60fdb2`), production pin `1672bb379`.

## Evidence

Workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human OAuth (the workspace owner's CLI login), non-TTY. Sandbox `sbx-dbpcrpppjd2c73f0qrjg` (`--plan 4c-8g`, created and stopped by this run). Three execs were started together at 08:07:48Z:

$ bex sandboxes exec sbx-… -- sh -c 'sleep 120; echo s120-done; exit 4'    → exit 4, 121 s, "s120-done"

  tick1 … tick10, then

The earlier exec in sandbox `sbx-dbpcre9pjd2c73f0qrdg` failed the same way at 210.74 s (07:55:52 → 07:59:22Z). The command was printing every 20 s, so this is a total-duration cap, not an idle timeout.

## Root cause

- `lego/backend/internal/sandbox/idle.go:150-153` `allowLongResume` sets the connection's write deadline to **now + `LongResumeWait` (3 min, `:76`) + 30 s = 210 s**, so a wake-on-exec can wait out a resume past bex-api's 30 s `WriteTimeout` (`cmd/api/main.go:1658`).
- `connect.go` `ConnectStreamHandler` calls it before `StreamExec` (`exec.go:274-302`). Nothing lifts the deadline once the gateway accepts and output starts flowing, so the first write after 210 s fails and the edge resets the HTTP/2 stream. Introduced by `be753e48d` (w2/m278, 2026-11-07). Before that the handler set no deadline at all, so the 30 s server `WriteTimeout` presumably applied. That earlier state was not verified live.
- The long-lived log tail already does the right thing: `internal/logs/rest.go:462-465` clears the write deadline (`SetWriteDeadline(time.Time{})`) for its stream.

## Fix

1. In `StreamExec`, once the gateway has accepted (`stream.start()`), clear the write deadline (`http.NewResponseController(w).SetWriteDeadline(time.Time{})`) or replace it with a rolling per-write deadline. Bound the exec instead by the gateway's `SessionTimeout` (4 h, `sshgateway/sandboxsse/sandboxsse.go:125`) and the sandbox's own lifetime. Apply the same check to the file connect routes (`file_connect.go:243-249` already resets its deadlines after the transfer).
2. Close orphaned execution records. When bex-api restarts mid-stream, the deferred `stopExecution` never runs, so the record stays open (`exe-dbpcul1pjd2c73f0qrtg`). Reconcile open records on startup, or when listing, against the gateway or the sandbox state.
3. Investigate the 40 s "no exit event" ending (`exe-dbpd0kjb7ovs73djkn5g`). It is unexplained: no rollout was running and the sandbox stayed `running`. Find the request in bex-api/gateway logs around 08:06:18Z.

## Acceptance

- Unit: a fake gateway streaming one chunk every 20 s for 5 minutes. The handler delivers every chunk and the exit event (fails on today's code at 210 s).
- Live: `bex sandboxes exec <sbx> -- sh -c 'for i in $(seq 15); do sleep 20; echo t$i; done; exit 6'` prints `t1`…`t15` and exits 6 after about 300 s. `sh -c 'sleep 300; exit 3'` exits 3. Both execution records carry `stoppedAt` and `exitCode`.
- Render: Render documents no exec duration limit; the sandbox `timeoutSeconds` (up to 30 days) bounds it.

## Dedupe

`rg -i 'long.running exec|allowLongResume|exec.*(cut|write timeout)' .pm docs`: no item. w2/m278 (done, wake-on-exec) introduced the deadline. w32/m298 (done, execution history) introduced the records. w7/m147 re-graded `sandboxes exec` with short commands only.
