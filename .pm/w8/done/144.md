# A new service shows the logs of a deleted service that had the same name

Why: App log reads select Loki streams by the App's name, so deleting a service and creating another with the same name hands the newcomer its predecessor's application and request history. That history includes paths, client IPs and SIGTERM lines from a workload the user deleted. On Render, logs belong to the service ID, and a new service never shows another service's lines.

**Severity:** major (a deleted service's data resurfaces and a new service's history is misleading; same workspace only). **Attribution:** server (logs read path). **Estimate:** 60m. **Source:** `/qa-find-bugs-cli` sweep 1244, 2026-10-20 ([evidence](evidence/cli-sweep1244/README.md)).

## Reproduction

HEAD checkout CLI `94533d795` against pinned Render CLI v2.27.0, production `https://api.bex.co/v1/`, deployed pin `94533d795067`, workspace `bex-canary`, human device-login grant. Free `docker.io/ealen/echo-server:0.9.2` services, all deleted at the end (GET 404).

1. `bex services create --name qa-20261020-4fc180-reuse --type web_service --image docker.io/ealen/echo-server:0.9.2 --plan free -o json --confirm` → `srv-dbbibk9q56vc73bn8dig` (this was already the second incarnation of the name; the first, `srv-dbbibd9q56vc73bn8dgg`, had been deleted 2 s earlier and recreation succeeded immediately).
2. `curl https://qa-20261020-4fc180-reuse.onbex.co/zze9427a-secret-path` → 200. `bex logs -r srv-dbbibk9q56vc73bn8dig --text zze9427a -o json` shows 3 marker lines.
3. `bex services delete srv-dbbibk9q56vc73bn8dig --confirm` → GET 404. 30 s later, the same `bex services create --name qa-20261020-4fc180-reuse …` → `srv-dbbict9q56vc73bn8dkg`, `createdAt 2026-10-20T08:29:41Z`.
4. `bex logs -r srv-dbbict9q56vc73bn8dkg --text zze9427a -o json` → exit 0, **3 marker lines** from the deleted service. `bex logs -r srv-dbbict9q56vc73bn8dkg --type request --path /zze9427a-secret-path -o json` → 1 request line.
5. `GET /v1/logs?ownerId=…&resource=srv-dbbict9q56vc73bn8dkg&startTime=2026-10-20T08:20:00Z` → 200 with 14 entries, **13 of them timestamped before the service existed**. They come from both earlier incarnations: instance `…stl5fms7`'s `Listening on port 3000.` and `Received SIGTERM signal…`, instance `…nev126fq`'s app lines, and four request lines. The deploy list and events for the new id are correctly scoped (one deploy, two events).

## Expected

Logs are owned by the service ID, as on Render, where a deleted service's logs go with it. A read for `srv-B` never returns lines emitted by `srv-A`, whatever the names, including lines from `srv-A`'s pods that are still terminating after `srv-B` exists. Instance and status-code discovery and Loki-backed request metrics follow the same rule.

## Root cause

`lego/backend/internal/logs/service.go:573–582` (`QueryLogs`) authorizes the requested `srv-…` id and then sets `q.App = app.Name`, the App CR's name, which is derived from the service name. `lokiSelectorFor` (`lego/backend/internal/logs/loki.go:445–454`) selects `{namespace=<ws>, app=<name>}` with no identity label and no lower bound at the App's creation. Every incarnation of a name in a workspace shares that stream. The same name-keyed resolution is at `service.go:547` (the initial tail lines), `:824` (`LogLabelValues`, i.e. instance and status discovery), `:961` (`followLogs`, the `--tail` stream) and `lego/backend/internal/metrics/lokisource.go:125` (host/path request metrics from Loki). Postgres and Key Value are not affected: they select by immutable id (`database=dpg-…`, `keyvalue=red-…`, `loki.go:448–451`).

## Fix

Scope App log reads to the current incarnation.

- **Exact, preferred:** ship the runtime pod's existing `bex.co/app-id` label (ADR004: every runtime pod carries it) as a Loki stream label in `deploy/gitops/base/log-shipper.yaml`, and select on `app_id=<srv-id>` alongside `app`. For request lines, attribute through the Ingress/Service the operator names for that App.
- **Fallback for streams shipped before the label existed:** clamp every App read's start to the App CR's `creationTimestamp` (and the matching start of Loki metric windows).
- Apply the same scoping at all five call sites above. Keep the namespace and app equality matchers (the tenant guard in `loki.go:438–444`).

## Blast radius

REST `/v1/logs`, `/v1/logs/subscribe` and label values; GraphQL `logs`/`logLabelValues`; MCP `list_logs`; the dashboard Logs tab and deploy-log views (these share `QueryLogs`/`followLogs`); the CLI `logs` (history and `--tail`); and Loki-backed `http_requests`/`http_latency` with host/path filters. Prometheus-backed CPU and memory selectors in `metrics/service.go:852/923/1124/1347` were not checked live and are worth reviewing in the same change.

## Acceptance

- Unit: two Apps with the same name in one namespace, A deleted before B was created, plus A's terminating pod logging after B exists. Every read path for B returns only B's lines, and the fix fails before / passes after.
- Live after deploy: repeat steps 1–5 on fresh fixtures. The new service's `--text <marker>`, `--path` and unfiltered history before its own first deploy are empty, and its instance discovery lists only its own instances. Delete the fixtures with 404 proofs.

## Metrics leak too (sweep 1245)

A third pair of incarnations was used (`srv-dbbihfecbnls73997fb0` deleted, then `srv-dbbihopq56vc73bn8du0` created at `08:40:04Z` with the same name). For the new id, `GET /v1/metrics/{cpu,memory,instance-count,http-requests}?resource=<new id>` (last 25 minutes, 60 s resolution) returns points timestamped `08:40:00–08:40:01Z`, before the service existed. CPU and memory include a second series whose `instance` is `srv-dbbihopq56vc73bn8du0-qjnaj8crbhnslsbcpm6s`: the deleted predecessor's pod, presented as an instance of the new service because public instance ids are derived from the pod name (ADR035) under the new service's id. So the Prometheus selectors at `metrics/service.go:852/923/1124/1347` share the name-keyed scope, and their fix belongs with this item.

Configuration does not leak. The recreated service starts with no env vars or secret files (the predecessor had `QA_INHERIT` and `qa1245.txt`; the process sees nothing), no custom domains (the predecessor had one) and default notification settings (the predecessor's override was `none`).
