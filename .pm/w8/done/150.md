# A Docker service's `dockerContext` resolves from the repo root, so Render's own monorepo export (`rootDir` + `dockerContext: .`) fails to build

Why: Render resolves `dockerContext` (like `dockerfilePath`) inside the service's root directory. Render's Blueprint export for a monorepo Docker service writes `rootDir: backend`, `dockerContext: .`, `dockerfilePath: ./Dockerfile`. Bex reads that `.` as the repository root, while it reads `./Dockerfile` inside `backend/`. The Dockerfile then runs against the wrong context, and every `COPY` of a file in `backend/` fails. A team moving a working Render monorepo to bex gets a failed first build with `"/requirements.txt": not found`, and the only workaround is to rewrite the path into a form that breaks the same file on Render.

**Severity:** major (Render-exported or Render-documented monorepo Docker services fail to build on import). **Attribution:** server (API and Blueprint write/read paths) plus operator build context. **Estimate:** 90m. **Source:** `/qa-find-bugs-cli` sweep 1266, 2026-10-20 ([evidence](evidence/cli-sweep1266/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, deployed pin `9cace6b6e25d`, workspace `bex-canary`, human device-login grant. Public repo `render-examples/twingate-example`: `example-pserv/` holds a two-line nginx `Dockerfile` (`FROM nginx:alpine` … `COPY index.html …`) and its `index.html`. The repo root has no `index.html`. The pinned CLI has no `dockerContext` flag, so the field was sent through the same REST create that the CLI uses.

1. `POST /v1/services` with `rootDir: "example-pserv"`, `serviceDetails.runtime: "docker"`, `envSpecificDetails: {"dockerContext": ".", "dockerfilePath": "./Dockerfile"}` (`qa-20261020-a18296-dctx`, `srv-dbbu8m65u6js73eso1pg`) → 201. Read back: `rootDir: example-pserv`, `dockerContext: "."`.
2. The first deploy ended `build_failed` after 78 s. `bex logs -r <id> --type build`: `[internal] load build definition from ./Dockerfile` → `transferring dockerfile: 115B` (it found `example-pserv/Dockerfile`), then `transferring context: 2B`, then `COPY index.html …` → `ERROR: failed to calculate checksum … "/index.html": not found`. `failureReason` carries the same line.
3. Control, same body without `dockerContext` (`qa-20261020-e89060-dctl`, `srv-dbbuctu5u6js73eso1s0`): `COPY index.html` → `DONE`, image built. (Its container then hit the recorded `nginx:alpine` `chown` posture from sweep 454, which is unrelated.) The only difference between the two builds is the context directory.
4. The control's read-back shows the second half of the problem: with `dockerContext` unset, `GET /v1/services/{id}` reports `dockerContext: "example-pserv"`, the repo-root path. Render reports `.` (its schema default; the pinned CLI's own fake Render API also defaults it to `.`). Exporting or cloning that service carries `rootDir: example-pserv` plus `dockerContext: example-pserv`, which Render resolves to `example-pserv/example-pserv`.

Both fixtures were deleted by ID (204, then GET 404).

## Expected

Render's semantics, from three independent sources:

- Render's pinned Blueprint schema (`lego/backend/internal/apps/schema/render.yaml.json`, `buildSourceGit`): `dockerContext` is "The Docker build-context directory, relative to rootDir. Defaults to rootDir, or the repository root if rootDir is unset." `dockerfilePath` is "relative to rootDir".
- [Render's monorepo guide](https://render.com/docs/monorepo-support): "All of the following settings operate relative to the root directory: Build command, Start command, Pre-deploy command, Publish directory, Dockerfile path, Docker build context directory."
- Render's own Blueprint export of a live service ([`aliyevaladddin/AladdinAI/render.yaml`](https://github.com/aliyevaladddin/AladdinAI/blob/main/render.yaml), header `# Exported from Render on 2026-05-31…`): `rootDir: backend`, `dockerContext: .`, `dockerfilePath: ./Dockerfile`. `backend/Dockerfile` runs `COPY requirements.txt .`, and `requirements.txt` exists only in `backend/`. A user report in [`AjayMaan13/FinSight/render.yaml`](https://github.com/AjayMaan13/FinSight/blob/main/render.yaml) says the opposite spelling (`rootDir: ml-service` plus `dockerContext: ml-service`) "doubled the path (ml-service/ml-service), which Render's builder couldn't resolve".

The older `serverService`/`cronService` descriptions in the same schema still say "relative to the repo root" for both fields. Bex already disregards that wording for `dockerfilePath`, so it cannot be the reason to keep it for `dockerContext`.

Target: the wire value of `dockerContext` is relative to `rootDir`, default `.`. The build context is `<repo>/<rootDir>/<dockerContext>`. Reads, exports and clones report the rootDir-relative value (`.` when unset). A service without `rootDir` behaves exactly as today. `..` stays refused.

## Root cause

- `lego/types/v1alpha1/app_types.go:474–481` defines `spec.dockerContext` as "relative to the repository root and resolved independently of RootDir". `lego/operator/internal/build/build.go:986–998` implements that: `dockerfileDir` comes from `RootDir`, but `contextDir = boundedSourceDir(o.DockerContext)` drops `RootDir`. `sourcePathChecks` (`build.go:1443–1458`) checks the same repo-root path.
- The premise came from `w8/m19/t004` ("Render semantics: `dockerContext` defaults to repo root, resolved independently of `rootDir`"), taken from the older field description. No live Render comparison backed it.
- Write paths copy the wire value into the spec unchanged: REST create (`lego/backend/internal/apps/rest.go:459–497` → `service.go:2912, 2958`, validated at `:3028`), MCP `create_web_service`/`create_cron_job` (`mcp.go:197, 255, 275, 312, 339, 365`). Their tool descriptions call `dockerContext` "relative to the repository root" while the same tools call `dockerfilePath` "relative to rootDir" (`mcp.go:196, 311`), and the Blueprint plan (`blueprint_plan.go:236`).
- Read paths report the repo-root form: `render.go:584` emits `cmp.Or(a.DockerContext, a.RootDir)`, and `blueprint_generate.go:393–394` exports `spec.DockerContext` verbatim beside `rootDir`.

## Fix

Pick one representation and translate at a single seam. Either is acceptable if reads and builds agree:

1. **Store rootDir-relative (recommended).** `spec.dockerContext` means "relative to `spec.rootDir`". The operator builds from `boundedSourceDir(path.Join(RootDir, DockerContext))`, and `sourcePathChecks` checks the same path. API, MCP and Blueprint writes store the wire value as sent. `render.go` reports `cmp.Or(a.DockerContext, ".")` for Docker builds, and the Blueprint export emits the stored value. A `rootDir` change then carries the context with it, as Render's guide describes. This needs a one-time conversion of existing Apps that have both fields (for example the pre-existing `hello-go`: `rootDir: examples/hello-go`, `dockerContext: examples/hello-go`). Strip the `rootDir` prefix (`examples/hello-go` → `.`) so each build is byte-identical before and after. List any App whose stored context lies outside its `rootDir` instead of rewriting it.
2. **Keep repo-root storage and translate at the boundary.** Writes store `path.Join(rootDir, wire)`; reads and exports report the path relative to `rootDir`. No CR conversion is needed, but a later `rootDir` PATCH must re-base the stored context, or it silently keeps pointing at the old directory.

Update the CRD comment, the MCP tool descriptions, ADR006's create-mapping paragraph and ADR049's `dockerContext` capability note to say "relative to the root directory".

## Acceptance

- Build unit tests: `{RootDir: "backend", DockerContext: "."}` and `{RootDir: "backend"}` both give the context `/source/backend`. `{RootDir: "", DockerContext: "app"}` gives `/source/app` (unchanged). The Dockerfile path is unchanged in every case.
- API tests: REST create with `rootDir: backend` + `dockerContext: "."` reads back `dockerContext: "."`; with no `dockerContext`, it reads back `"."`, not `"backend"`. The same holds through MCP and the Blueprint plan.
- The Blueprint export of such a service round-trips through `bex blueprints validate` and re-imports to an identical spec. AladdinAI's exported shape (`rootDir` + `dockerContext: .` + `dockerfilePath: ./Dockerfile`) compiles to the same build paths Render uses.
- Conversion test: an App stored as `rootDir: examples/hello-go`, `dockerContext: examples/hello-go` yields the identical BuildKit `--local context=` argument before and after.
- Live after deploy: repeat steps 1–3 on fresh free fixtures. Step 1's shape now builds (`COPY index.html` → `DONE`), and the control reads back `dockerContext: "."`. Delete both by ID with 404 proofs.

## Blast radius

One shared field across REST create, MCP (two tools), the Blueprint plan/apply/export, the operator build Job and its source-path preflight, and the REST/GraphQL/MCP read projection (`render.go`). Docker builds only: native and buildpack builds already refuse `dockerContext` (w5/090). Services without `rootDir` are unaffected. GraphQL `createService` does not take the field (w5/m117). The dashboard neither shows nor edits it. Existing Apps with both fields need the conversion described in Fix option 1, including bex's own `hello-go` example service.
