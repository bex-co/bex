# A new Ruby service with no version signal builds on Ruby 3.4.11; Render's default for services created since 2025-06-12 is exactly 3.4.4

Why: Render's [Ruby version](https://render.com/docs/ruby-version) page fixes the default for new services at `3.4.4` (services created on or after 2025-06-12; older services have dated defaults from 2.6.8 to 3.3.6). bex resolves "no signal" to its 3.4 line's reviewed patch, 3.4.11, so an app that relies on the platform default runs a different Ruby than on Render. w8/174 already matched Render's dated default for Python (3.14.8) and the defaults for Node (24.22.1) and Elixir (1.18.4) match. Ruby is the only runtime whose default patch differs.

Severity: minor (default runtime patch differs; same minor line). Source: `/qa-find-bugs-cli` loop sweep c7e2, 2026-10-23 UTC, bex v0.3.3, pin Render CLI v2.27.0 `a764810a7682`, platform pin `fa8ac5bba24a`, `https://api.bex.co/v1/`, `bex-canary`, human device login.

## Root cause

`lego/operator/internal/build/native.go:121-127`: `nativeRubyRuntime` `defaultLine: "3.4"`, whose line entry is `{line: "3.4", version: "3.4.11", image: "ruby:3.4-bookworm@sha256:80259ba8…"}`. The default resolves to the line's reviewed patch. Unlike w8/174's Python handling, no creation-date default table exists for Ruby.

## Fix

Mirror w8/174: a dated default table for Ruby (2025-06-12 and later → `3.4.4`, plus Render's earlier dated defaults where bex supports the line), resolved through w8/175's exact-tag path (`ruby:3.4.4-bookworm`, pinned by digest at resolve time, with the reviewed line patch as the logged fallback). The `Using Ruby …` line names the exact version. Existing services keep what they build on now unless their creation date maps to a different default (decide with ADR060 whether to apply the table to services created before this change, as w8/174 did). Update ADR060 and ADR018:84.

## Blast radius

Native Ruby builds with no Gemfile.lock `RUBY VERSION`, `.ruby-version`, `.tool-versions` or `Gemfile` `ruby` signal, in every workspace. Explicit signals and `RUBY_VERSION` are unaffected.

## Acceptance

- Unit: no signal, created now → `3.4.4` via the exact-tag image; with a `.ruby-version` of `3.4` → the line's reviewed pin (unchanged).
- Live after the operator deploy: the repro above logs `Using Ruby 3.4.4 (default)` and `ruby 3.4.4`. Delete by ID with a 404 proof.

## Addendum — Bun's default patch also differs (sweep 9f3b, source-level)

Render's [language-support](https://render.com/docs/language-support) page (read 2026-10-23) lists the native defaults: Node `24.22.1`, Bun `1.4.4`, Python `3.14.8`, Ruby `3.4.4`, Go and Rust latest stable, Elixir `1.18.4`. bex matches Node, Python (w8/174), Elixir, Go and Rust. Besides Ruby, Bun differs: `lego/operator/internal/build/native.go:140-144` `nativeBun` `defaultLine: "1.4"` → `{line: "1.4", version: "1.4.3", …}`, so a Bun-opted service (a `bun.lock`/`bun.lockb` with no `BUN_VERSION`/`.bun-version`) gets 1.4.3 where Render installs 1.4.4. Not reproduced live (no fixture repo with a bare Bun lockfile). Fix it with the same dated-default mechanism and add a unit case.
