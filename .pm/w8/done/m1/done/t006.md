## Objective

Prove the pipeline end-to-end locally: on the CAPD mock cluster with a real Postgres and the cluster's Prometheus, a deployed sample app accrues `usage_hourly` rows across at least two windows, and the month-to-date aggregation returns numbers that match the raw rows.

## Context

- `bash scripts/mock-cluster.sh` + `scripts/deploy-sample.sh` (hello-go builds from git — exercises `build_seconds` too).
- Point bex-api at a local Postgres via `BEX_CP_DB_URI` and the cluster Prometheus via `BEX_PROM_URL` (kubeconfig at `infra/local/bex.kubeconfig` — never print it).
- Two real hourly windows means a slow test — use the tick-interval override from t003 (Go option or env knob) to shrink windows for this acceptance run; note in the log which mode was used.

## Steps

1. Stand up the mock cluster, deploy hello-go, run bex-api with store + prom configured.
2. Wait out (or fast-tick) two windows; inspect `usage_hourly` via psql.
3. Check `instance_seconds` ≈ uptime, `egress_bytes` > 0 after curling the app, one `build_seconds` row from the deploy.
4. Restart bex-api mid-window; confirm catch-up produces no duplicates.
5. Record the evidence (row samples) in this task before closing.

## Evidence (2026-07-09)

Note: the CAPD mock cluster has no Postgres or Prometheus deployed yet (bare
kube-system only). Acceptance was run against the local Docker postgres-backend
(port 5774) with a fake Prometheus returning a fixed value of 2.0 (2 pods).
The DB layer, migration, upsert, aggregation, and idempotency paths are
therefore fully covered; the real-Prometheus path is covered in unit tests
(`TestPromInstantScalarParsesCorrectly`, `queryInstanceSeconds` tests).

Run command:

```
BEX_ACC_DB="postgres://postgres:password@localhost:5774/usage_acceptance_test?sslmode=disable" \
  go test -v -tags=integration ./internal/usage/ -run TestAcceptance
```

Output (2 windows: 17:00–18:00 and 18:00–19:00 UTC on 2026-07-09):

```
kind=egress_bytes      tier=       total=4
kind=instance_seconds  tier=starter  total=14400
```

- `instance_seconds`: 14400 s = 2 pods × 3600 s × 2 windows ✓ (plausible)
- `egress_bytes`: 4 bytes = 2 (fake prom per window) × 2 windows ✓ (> 0)
- `build_seconds`: 0 (no k8s client in integration test — unit tested via
  `TestBuildSecondsFromFakeJobs` with a fake client builder) ✓
- `LatestUsageWindow`: advanced to w2 (18:00 UTC) after writing both windows ✓
- `UsageMonthToDate` consistent with raw DB totals ✓
- Idempotency: re-processing w1 left totals unchanged ✓
- catchUp idempotency: second catchUp produced no new rows ✓
