# `bex` keeps its persistent CLI state in Render's `~/.render/state`, and no Bex input can relocate it

Why: bex's telemetry `installation_id` is read from the upstream Render CLI's state directory, so `bex` and `render` on the same machine report the **same installation identity** to two different vendors — and because `RENDER_CLI_CONFIG_DIR` is unreachable in the launcher, there is no way for CI, a container, or a QA harness to isolate that state at all.

Source: live CLI QA sweep 2026-09-15 (`/qa-find-bugs-cli`, sweep 4), upstream pin v2.27.0 (`a764810a768202704e7206eb7b87a47211fcd98e`), `go build` of `lego/cli` at HEAD `0e490af54`.

Second-order consequence of `.pm/w8/017.md`, filed separately because the harm and part of the fix are distinct. 017 is about *where the config file lands*; this is about *where persistent state lands* and who it identifies.

## Severity: major

Not a crash and not data loss, but a cross-vendor identity collision plus a stated isolation guarantee that does not hold.

## Evidence

```sh
# fully isolated config, throwaway everything
BEX_CLI_CONFIG_PATH=$TMP/t4.yaml BEX_HOST=http://127.0.0.1:$SINK/v1/ \
  BEX_ACCESS_TOKEN=tk BEX_WORKSPACE=tea-x1 bex postgres list -o json
```

The telemetry event `bex` POSTs to `/v1/cli-telemetry-events` carries an `installation_id` that is **byte-identical to the contents of `~/.render/state/installation-id.txt`**, verified programmatically across every isolated run in this sweep (1 distinct id, exact match).

```
~/.render/state/installation-id.txt      <- bex reads its installation identity here
~/.render/state/analytics/notice-shown   <- shared one-time analytics notice marker
~/.bex/state                             <- does not exist
```

Setting `BEX_CLI_CONFIG_DIR=$TMP/statetest` creates **no** `state/` subdirectory there, and `~/.render/state/installation-id.txt` is still the file consulted (mtime unchanged — read, not written, so nothing was damaged).

## Root cause

Upstream resolves state as `StateDir() = ConfigDir() + "/state"` (`pkg/config/dirs.go:34-40`), and `ConfigDir()` (`dirs.go:12-22`) reads **only** `RENDER_CLI_CONFIG_DIR`, defaulting to `~/.render`. Its own doc comment is explicit:

> The legacy `RENDER_CLI_CONFIG_PATH` override does not move state: it points at the config file itself, and the CLI must not write siblings next to an arbitrary user-chosen file. **Use `RENDER_CLI_CONFIG_DIR` to relocate state** along with the rest of the CLI's files.

The bridge maps **both** Bex inputs onto `RENDER_CLI_CONFIG_PATH` (`lego/cli/internal/bridge/bridge.go:59-62`) — `BEX_CLI_CONFIG_DIR` becomes `<dir>/cli.yaml`, not `RENDER_CLI_CONFIG_DIR`. Combined with 017 (the bridge always populates `RENDER_CLI_CONFIG_PATH`, making `RENDER_CLI_CONFIG_DIR` unreachable), **no input of any kind can move `StateDir()`**. It is permanently `~/.render/state`.

## Why the existing documentation does not cover this

`lego/cli/UPSTREAM_RENDER_CLI.md:20` documents the notice marker as living at `config.StateDir()/analytics/notice-shown`, "i.e. `~/.render` **unless `RENDER_CLI_CONFIG_DIR` is set**". That escape hatch does not exist in `bex` — 017 proves the variable is inert. So the one place this is written down states a mitigation that cannot be exercised.

The `installation_id` sharing is not documented anywhere in `docs/` or `.pm/`. It is also not the same class as the accepted "upstream skills-path residual": that is a read-only path for a client-side feature, whereas this is the identity bex attributes its own telemetry to.

## Fix

Depends on the 017 decision; do both together.

1. Map `BEX_CLI_CONFIG_DIR` onto **`RENDER_CLI_CONFIG_DIR`** (not `RENDER_CLI_CONFIG_PATH`), so it relocates config *and* state the way upstream intends. Keep `BEX_CLI_CONFIG_PATH` → `RENDER_CLI_CONFIG_PATH` for the exact-file case.
2. Decide the default. `$HOME/.bex/cli.yaml` is already bex's config default, so `$HOME/.bex/state` is the consistent state default — set `RENDER_CLI_CONFIG_DIR=$HOME/.bex` when no Bex input is given, instead of only setting the path. This gives bex its own installation identity and its own notice marker.
3. Note the migration: existing users have an id in `~/.render/state`. Moving to `~/.bex/state` mints a **new** `installation_id`, which shows up in bex-api telemetry as a new install. Either accept that (simplest, and arguably correct — it was never bex's id) or copy the file once on first run. **This is the user decision in this note.**
4. Correct `lego/cli/UPSTREAM_RENDER_CLI.md:20` and the launcher record in `docs/cli-compatibility-checklist.md`, which claims Render-config isolation is covered by hermetic tests.

## Regression checks

- [x] With no Bex input, `bex` resolves state under `$HOME/.bex/state`; `~/.render/state` is neither read nor written.
- [x] `BEX_CLI_CONFIG_DIR=$TMP/x` puts both `cli.yaml` and `state/` under `$TMP/x`.
- [x] `BEX_CLI_CONFIG_PATH=$TMP/y.yaml` still writes exactly that file and, per upstream's contract, does **not** write siblings next to it.
- [x] A run with an isolated config dir reports an `installation_id` different from `~/.render/state/installation-id.txt`.
- [x] `cd lego/cli && go test ./...` and `bash scripts/bex-cli-validate.sh`.

Closed 2026-09-15: `BEX_CLI_CONFIG_DIR` maps to `RENDER_CLI_CONFIG_DIR`; default DIR is `$HOME/.bex` so config and state move together. Exact `BEX_CLI_CONFIG_PATH` still sets PATH. Migration: mint a new `installation_id` (do not copy `~/.render/state`) — it was never bex's id.

Estimate: ~45m on top of 017 (same file, same test file). If 017 and this are taken together the pair is a milestone-sized change — promote then.

## Verified correct in the same sweep (no action)

The telemetry seam itself is sound: the event POSTs only to the configured control plane (a second local sink on another port received nothing), `BEX_CLI_DISABLE_ANALYTICS=1` and `DO_NOT_TRACK=1` each suppress it entirely, and the body is exactly the upstream 18-field `CliTelemetryEventPOSTInput` — `command` carries the command path only (`bex postgres list`), with no argument values, flag values, or secrets. `X-Bex-CLI-Version` was stamped on control-plane requests only.
