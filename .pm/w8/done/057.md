# 057 — Postgres REST wire drift: `plan` answers Blueprint spelling `basic-256mb` (Render's API enum is `basic_256mb`), and create refuses Render's `parameterOverrides` with a bare `bad request body`

Why: two small breaks of the pinned Render REST contract on `/v1/postgres`. A Render client that sends `plan: basic_256mb` reads back `basic-256mb`, a value outside the response enum. A Render-valid create body with `parameterOverrides` is refused with no field named, while `/v1/services` names the unknown field.

Severity: minor. Attribution: server (`lego/backend/internal/postgres`).

## Evidence (2026-10-05, `/qa-find-bugs-cli` w8 loop, sweep 18)

Production pin `8f58b933d`, workspace `bex-canary`, human device login. REST `dryRun` creates sent with the CLI's own token (read privately from the isolated config), User-Agent `render-cli/2.27.0`. Nothing created.

```text
POST /v1/postgres {"name":"qa-r18-pg","plan":"basic_256mb","ownerId":"tea-…","version":"16","dryRun":true}
→ 200  … "plan":"basic-256mb" …                                    # sent underscore, answered hyphen

POST /v1/postgres {… "plan":"free", "parameterOverrides":{"work_mem":"64MB"}, "dryRun":true}
→ 400  {"error":"bad request body","id":"bad_request","message":"bad request body"}

POST /v1/postgres {… "version":"19" …}  → 400 "invalid request body at /version"
POST /v1/postgres {… "version":"12" …}  → 400 (POSTGRES_VERSION_UNKNOWN) "… choose one of 13|14|15|16|17|18"   # control: named
POST /v1/services {… unknown field …}    → 400 "request body contains unknown field \"…\""                    # control: names the field
```

Pinned Render contract (`lego/backend/internal/api/openapi/render-public-api-1.json`):

- `postgres.plan` / `postgresDetail.plan` → `postgresPOSTInput.properties.plan`, whose enum spells `basic_256mb`, `basic_1gb`, `basic_4gb`. Render's **Blueprint** schema (`internal/apps/schema/render.yaml.json` `postgresPlan`) spells them `basic-256mb`/`basic-1gb`/`basic-4gb`. Render uses different spellings on the two surfaces, and bex answers REST with the Blueprint one.
- `postgresPOSTInput.properties.parameterOverrides` = `{"type":"object","additionalProperties":{"type":"string"}}`, a valid create field.

`docs/cli-compatibility-checklist.md:141` claims "bex's own tier names round-trip". That holds for input (underscore accepted) but not for the response spelling.

## Mechanism

- `lego/backend/internal/postgres/service.go:489` builds the view with `Plan: d.Spec.Plan`, the bex tier id (`basic-256mb`, `tiers.go`). No mapping to Render's REST enum happens on output.
- `lego/backend/internal/postgres/rest.go:186-198` decodes create into `CreatePostgresRequest` (+`public`), which has no `ParameterOverrides`. PATCH (`:449`) has one. Strict decoding fails, and `decodeOr400` (`:136-142`) flattens every decode error to `bad request body`, dropping the field name. `version` enum failures come from the OpenAPI validator (`invalid request body at /version`) before the handler's named `POSTGRES_VERSION_UNKNOWN`.

## Fix

- REST (and the CLI-facing) Postgres view: render `plan` in Render's REST spelling (`basic_256mb` …). Keep accepting both on input. Leave GraphQL/MCP/Blueprint on bex's id, or document the choice per surface in ADR018.
- Create: accept `parameterOverrides` (thread it to the same `SetParameterOverrides` validation PATCH uses), or refuse it with a named code. Either way, make `decodeOr400` keep the decoder's message (`unknown field "x"`, type errors) like `/v1/services` does.
- Optional: let `version` reach the handler so `"19"` gets the same `POSTGRES_VERSION_UNKNOWN` sentence as `"12"`.

## Acceptance

- [ ] `dryRun` create with `plan: basic_256mb` → `plan: "basic_256mb"` in the response, and `bex postgres get` on a basic database shows `basic_256mb`.
- [ ] `dryRun` create with `parameterOverrides: {"work_mem":"64MB"}` → 200 with the overrides echoed (or a named 400 naming `parameterOverrides`). A body with an unknown field names it.
