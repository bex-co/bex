# A nonexistent Docker Hub image burns the full 15-minute rollout budget instead of the 90-second pull-failure settle

Why: bex has an early settle for permanent image-pull failures (90-second grace, then fail — w8/m44) precisely so a missing image doesn't hide behind the 15-minute rollout deadline, but its permanence classifier substring-matches registry answers and Docker Hub's actual answer for a nonexistent repository matches none of them, so the most common registry's most common pull error rides the entire budget as a bare `update_in_progress`.

Seen in the `/qa-find-bugs-cli` loop sweep 532, 2026-10-19, production, `bex-canary`, HEAD-build CLI:

- `bex services create --image docker.io/library/qa532-no-such-image-zzz:latest --plan free` → created; deploy stayed `update_in_progress` from 10:00:56Z to 10:16:02Z (**15m06s**), then settled `update_failed` / phase `Failed`, first release correctly stopped at zero.
- The Events feed knew immediately (10:00:56Z): `image_pull_failed` plus `stallReason: "image pull is failing: Back-off pulling image \"docker.io/library/qa532-no-such-image-zzz:latest\": ErrImagePull: failed to pull and unpack image …: failed to resolve image: pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed"`, and the terminal `failureReason` carries the same text — diagnosis quality is fine; only the timing is wrong.
- The classifier it evaded: `predeploy.PermanentPullFailure` (`lego/operator/internal/predeploy/predeploy.go:286-304`), shared by rollout pods via `permanentRolloutPullFailure` (`app_controller.go:3286-3288,3479-3501`). After the 90s `imagePullGrace` it requires the lowercased waiting message to contain one of `code = notfound`, `manifest unknown`, `manifest_unknown`, `: not found`, `404 not found`, `unauthorized`, `authentication required`. Docker Hub's answer contains **none** of those ("pull access denied", "repository does not exist", "insufficient_scope") — although the function's own comment states the intent: "Missing-image and denied-auth answers wait through imagePullGrace" and then fail.

Fix: teach the classifier Docker Hub's missing/denied vocabulary, minimally `pull access denied`, `insufficient_scope`, and `repository does not exist` (all three appear in the one real answer above; adding the set keeps any single-substring drift from reopening the hole). These answers are permanent for a given image+credential pair mid-rollout: a fixed credential or tag arrives via a new deploy, exactly the reasoning already encoded for the existing substrings. Keep network/backoff wording excluded. Pin the captured real-world message (above, verbatim) as a table vector next to the existing classifier tests, for both callers (pre-deploy Job and rollout pod).

Acceptance:

- Fresh owned free service with `--image docker.io/library/<nonexistent>:latest`: deploy settles `update_failed` within ~3 minutes of pod creation (90s grace + settle), with the same named `failureReason`; first release still stops at zero; events unchanged.
- A transient pull error (network wording) still does **not** settle early — existing classifier tests keep passing, plus the new Docker Hub vectors.
- Pre-deploy Job image failures with the same registry answer settle on the same early path.

Severity: minor-major (no wrong state, but a first-deploy user with a typo'd image tag waits 15 minutes for a verdict bex knew in 90 seconds). Estimate: ~25m.


**Done (2026-10-19, `5ae176831`, live after deploy `d98d07f62`):** `PermanentPullFailure`, shared by pre-deploy Jobs and rollout pods, now also treats Docker Hub's "pull access denied", "repository does not exist" and "insufficient_scope" as permanent. Network and backoff wording still waits out the deadline. The production message, verbatim, is pinned in the classifier table and the rollout-settle table, and both fail on the old classifier.

Live on production: a fresh owned Free service with `docker.io/library/qa-w8-131-no-such-image-zzz:latest` settled `update_failed` 105 seconds after create, where it used to take 15m06s. Its reason was `image pull is failing: … Back-off pulling image …`. The fixture was deleted by ID, 404.
