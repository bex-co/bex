# Production CI runner's Docker cannot apply memory or CPU limits

Why: on the `bex-production` self-hosted runner, any container started with `--memory` or `--cpus` is refused at start, so a job that relies on Docker resource limits fails or silently runs without them.

Found by the w8/m114 preservation audit's credential-free probe on 2026-10-18 ([run 39173043198](https://github.com/bex-co/bex/actions/runs/39173043198), step "Probe local Docker limits"):

- `docker info`: cgroup driver `cgroupfs`, cgroup v2, and memory, CPU CFS and pids limits all reported as supported.
- `docker create` + `docker start` with `--memory 512m` or `--cpus 1` fails: `runc create failed: unable to apply cgroup configuration: cannot enter cgroupv2 "/sys/fs/cgroup/docker" with domain controllers -- it is in threaded mode`.
- With no limit, or with `--pids-limit 128` only, the container starts.

The m114 audit worked around it by restoring without those limits (`48db5a42f`, now removed with the audit). Fix the runner host instead: the `docker` cgroup must be a domain cgroup, not threaded, with the memory and cpu controllers delegated (check `/sys/fs/cgroup/docker/cgroup.type` and the parent's `cgroup.subtree_control`, or switch dockerd to the systemd cgroup driver). Then verify that a `--memory 512m --cpus 1` container starts on a `bex-production` job.

**Blocked 2026-10-18 (loopx w8): the fix is prepared, and applying it needs the user.** The runners are Docker-in-Docker containers from `bex-co/block-eden-mono` `projects/github-runner/`. They run on the operator's Mac under Docker Desktop (`.pm/DO_NOT_DO.md` #RUNNER-HOSTS). Fixing them means changing that repo and rebuilding the shared runner fleet, which is outside this repo and outside the pre-approved local dev environments.

Diagnosis, from a read-only check of `github-runner-runner-bex-production-1`:

- The container's root cgroup is a `domain` with 9 processes and an empty `cgroup.subtree_control`. Docker uses the `cgroupfs` driver on cgroup v2.
- Under cgroup v2's no-internal-process rule, a cgroup that holds processes cannot delegate domain controllers to its children. So dockerd's `docker` child cgroup has no memory or cpu controllers, and runc reports it as threaded.
- `dind-entrypoint.sh` starts `dockerd` without docker:dind's cgroup v2 nesting step.

Reproduced and fixed on this Docker Desktop kernel. Two throwaway privileged containers ran the same runner image (`myusername/github-actions-runner:latest`) with the entrypoint overridden, so no runner registered:

- **Unpatched:** a plain container and `--pids-limit 128` start. `--memory 512m`, `--cpus 1`, and both together fail with `runc create failed: unable to start container process: unable to apply c[group configuration]`.
- **With the nesting step:** all five start.

The patch is in [`122-upstream.patch`](122-upstream.patch), against block-eden-mono `HEAD`, and applies cleanly with `git apply`:

- `dind-entrypoint.sh`: before dockerd starts, move the root cgroup's processes into an `init` child and enable every controller in `cgroup.subtree_control`.
- `runner-config.test.sh`: asserts that step runs before `dockerd`. It passes with the patch and fails against the unpatched entrypoint.

What the user needs to do:

1. Apply the patch in block-eden-mono and commit it.
2. After checking for active jobs, rebuild and restart both pools: `docker compose up -d --build runner-bex-production runner-bex-ci`, from the runbook `docs/runbooks/runner-pool-relabel.md`.
3. Confirm that a `--memory 512m --cpus 1` container starts in a `bex-production` job, for example the probe step w8/m114's audit used.

**Done (2026-10-18):** the cgroup v2 nesting shipped in bex-co/block-eden-mono as `8abb38b0d5`. Its refinements, the quiet process move and a test that pins the nesting before dockerd, followed as `d62abafdde`, which supersedes the parked `122-upstream.patch`. All 10 runners were rebuilt and replaced one idle runner at a time, with no job interrupted, and all are online on the new image. Inside an idle bex-production runner, the job user's nested Docker now delegates every controller (`cgroup.subtree_control: cpuset cpu io memory hugetlb pids rdma`). A container started with `--memory 512m --cpus 1 --pids-limit 128` ran with `memory.max=536870912`, `cpu.max=100000 100000` and `pids.max=128`.
