# A bandwidth read whose `endTime` is after now answers zero-valued buckets for minutes that have not happened and marks every egress source degraded

Why: w4/644 set the rule that no metrics read returns a point after the request time, but it fixed only the resource source (cpu, memory, instance count). `/v1/metrics/bandwidth` still runs its range and its source-health check up to a future `endTime`, so a client asking for "the next 15 minutes" of a window reads a flat zero tail and a `degraded_sources=http,websocket,direct` warning that is false.

- Severity: minor. The bytes in the past part of the window are right. The tail and the label are wrong, and the dashboard's "Partial data" annotation reads the same label (ADR023).
- Versions: `bex v0.9.0` (Render CLI v2.36.0, pin `4fd34231b637`), `main` `8693058e00`. Production pin `19fdb46f1758`; `lego/backend/internal/metrics` and `egressquery` are identical on it and on `main`.
- Context: 2026-11-23 02:02–02:15 UTC, `https://api.bex.co/v1/`, workspace `bex-canary`, human device-login token, `/qa-find-bugs-cli w8` routine sweep met1122 (metrics API). The CLI has no metrics command, so the probes are REST GETs with the CLI's token.

## Repro

Free web service `srv-dc1ptf9fdpsc73e0hln0` (image `nginx:1.27-alpine`, since deleted), created 02:02:37. 186 paced GETs ran from 02:03:24 to 02:05:54. At 02:11:06:

```text
GET /v1/metrics/bandwidth?resource=<srv>&startTime=2026-11-23T02:04:00Z&endTime=2026-11-23T02:10:06Z   (end 1 min ago)
→ 200, 1 series, labels [resource], 7 points 02:04…02:10, sum 99083 bytes

→ 200, 1 series, labels [degraded_sources=http,websocket,direct, resource], 23 points 02:04…02:26, sum 99083 bytes
  the 15 points from 02:12 to 02:26 are all {"value": 0}
```

The same future window on the other metrics stops at now and carries no extra label: `http-requests`, `http-latency` (last point 02:06, the last minute with traffic), and `memory` and `instance-count` (last point 02:11). It reproduced on three reads (`endTime` 02:10 at 02:07, 02:30 at 02:08, and 02:26 at 02:11). Every read whose end was not in the future had no `degraded_sources` label.

## Root cause

`NewPrometheusRequestSource` (`lego/backend/internal/metrics/source.go:86`) passes `req.End` unchanged to both steps:

- the health check, `egressquery.Instant(…, egressquery.Health(spec, seconds), req.End)` (`source.go:102`). It is evaluated at a future instant, over a range that is mostly in the future, so every source's health product reads below 1.
- the range query, `promQueryRange(…, req.Start, req.End, …)` (`source.go:115`). The chart query ends in `or vector(0)` (`egressquery.IncreaseOrZero`, `egressquery/query.go:340`), so Prometheus answers 0 at every step up to `end`.

The resource source has clamped since w4/644: `end := earlierTime(req.End, time.Now())` (`source.go:207`). The request source never got that clamp. `http_requests` and `http_latency` show no future points only because their queries have no zero fallback.

## Fix

At the top of the request source's closure, bound the end at now, as the resource source does: `end := earlierTime(req.End, time.Now())`. Return no series when `end` is before `req.Start`. Use `end` for the health range (`seconds`), the health instant and the range query. Every other request metric is unchanged, because their points already stop at now.

Land it together with w8/414. With the clamp alone, `/v1/metrics/bandwidth-sources` over a window ending in the future would lose the current hour, which today shows up only as a future-stamped point.

## Blast radius

Every bandwidth read goes through this source: REST `/v1/metrics/bandwidth` and `/v1/metrics/bandwidth-sources`, GraphQL `metrics` (`BANDWIDTH`) and MCP `get_metrics` (`bandwidth_usage`). Only REST was exercised; GraphQL and MCP are inferred from the shared `Service.Metrics` path. The billing rollup reads `egressquery` directly over closed windows (`usage/service.go`), so it is not affected.

## Fix (shipped `a0d1503967` 2026-11-23 by `/loopx w8`)

- **One bound for every Prometheus read.** `promQueryRange` (`lego/backend/internal/metrics/source.go`) is the transport under every Prometheus-backed metrics source. It now bounds the range end at now (`untilNow`), and a window wholly in the future queries nothing. The request source bounds its bandwidth health check, the range and the instant, with the same end. The resource and activity sources' own w4/644 clamps are gone, since the transport covers them.
- **The same gap elsewhere, closed by the same bound.** cpu and memory limits, disk usage, Key Value memory and connections, datastore cpu and memory, Postgres connections and replication lag: their instant selectors carried the last sample up to five minutes past now. The Prometheus `http_requests` and `http_latency` fallback: an increase or rate window reaches back from a step after now. The Loki reads (request metrics, lock waits) need nothing, because `count_over_time` answers no point for an empty bucket.
- **Surfaces.** REST `/v1/metrics/*`, GraphQL `metrics` and MCP `get_metrics` all read these sources through `Service.MetricsWithQuantiles` and `DatastoreMetrics`.
- **Render.** The pinned spec (`render-public-api-1.json`, `endTimeParam`) says only "Defaults to `now()`". A time that has not happened has no data, and w4/644 set the rule that no metrics read returns a point for one.
- **Tests.** `TestBandwidthWindowEndingAfterNowReadsUpToNow` drives the request source with `End = now + 15m` against a fake Prometheus that answers past now as the real one does: health 0 and `or vector(0)` zeros. The `query_range` end and every health instant are at most now, there is no `degraded_sources` label and no point after now, and a window wholly ahead makes no query. `TestPrometheusSourcesEndAtNow` covers ten sources. Both fail with the bound removed. The backend real-DB suite (ship gates), lint and dead-code analysis pass.
- **w8/414.** With the bound, `/v1/metrics/bandwidth-sources` over a window ending after now no longer shows the current hour's bytes on a future-stamped point. Until w8/414 builds the hourly buckets, it reads as a window ending now already does: no point for the current hour.
