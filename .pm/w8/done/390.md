# A git push, a configuration roll, a Blueprint sync or a build-source fan-out still replaces a deploy the operator has not adopted yet, where Render's default Wait lets it finish

Why: w8/387 made bex-api's deploy verbs (REST, GraphQL and MCP trigger, the deploy hook, a build-source carrier's build, "Save, rebuild, and deploy") wait at the row level behind a deploy whose release the operator has not adopted yet. The other release writers still write the App directly. The operator pins a release only once it has adopted it (`releaseInFlight`, `lego/operator/internal/controller/release_identity.go`), so a direct write landing in that window (about 1 to 2 s after the deploy opens) replaces the deploy, which closes `canceled` ("Superseded by …") and never runs.

- Severity: minor. The window is short, but two pushes in quick succession, or a push right after a manual deploy, hit it.
- Writers: the push webhook (`redeployFetched`, `lego/backend/internal/apps/service.go`, which patches the App and then `CreateDeploy`s outside the deploys trigger lock), configuration saves that roll a release, Blueprint sync, and the build-source fan-out (`triggerFetched` with `p.build`, `lego/backend/internal/deploys/build_sources.go`).
- Parity: Render's Wait, "Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy" ([render.com/docs/deploys](https://render.com/docs/deploys)). ADR018's "List / get deploy objects" row records this as still open (w8/387).
- Related, unverified live: the operator never pins a direct static publish (`pinnableSourceRelease` returns false for `directStaticPublish`), so a newer deploy, from any writer, replaces one already adopted. Check that on a no-build static site, and fix it here too if it holds.

## Fix

Route each direct writer through the same rule as the deploy verbs. Behind a deploy whose generation is ahead of `status.releaseGeneration`, open a deferred `queued` row (`CreateDeferredDeploy`, with the commit the push named) that the deferred-deploy worker runs once the deploy ahead has ended. Otherwise, write through as today. Keep Override's cancel-and-start.

## Acceptance

- Tests: a push right after a `201` trigger, before adoption, leaves the trigger's deploy running to `live`, then the push's deploy runs with its own commit. A second push while the first push's deploy waits replaces only that deploy.
- ADR018: drop the "Still open" sentence from the w8/387 paragraph.

Estimate: ~2h.

## Shipped 2026-11-21 (`93e61e60ea`), live check owed

- **Premise held.** Each writer named above wrote its release to the App with no check of the deploy ahead, so in the second or two before the operator adopted that deploy, the write replaced it.
- **Fix.** One rule for every writer, `rollout.DeployAheadUnadopted` (`lego/backend/internal/rollout/adoption.go`), which w8/387's check in `deploys` now calls.
  - A git push waits at the row level like a trigger. `deploys.Service.DeferNewCommit` is wired into `apps.Service.DeferNewCommit` and called first in `redeployFetched`. It opens a `queued` `new_commit` deploy carrying the pushed commit, and the deferred-deploy worker runs it through `triggerFetched` once the deploy ahead has ended. Only waiting deploys replace each other.
  - A build-source fan-out waits the same way, carrying `DeferredRequest.BuildID`. A fan-out that completes a linked service's first deploy (`firstBuild`), which waits for that very build, ships at once.
  - A checksPass commit whose checks passed stays pending in `dispatchCheckedCommit`. The 15 s recovery poll dispatches it once the deploy ahead is adopted.
  - A configuration save that rolls a release (`Tracker.Patch` and `PatchLocked`, staged writes included) and a Blueprint sync (`patchChangedStackService`) wait for the adoption, then write through and pend behind the operator's pin (`rollout.AwaitAdoption`). They cannot wait at the row level: a held spec change would be what the operator renders the deploy ahead from when it adopts it. The wait is bounded at 15 s, after which the write goes through as before. A service's first release (nothing adopted yet, and the first release reads the saved settings) and Override never wait.
  - An environment "Save and deploy" already waited at the row level behind any deploy (w4/667).
- **Tests:** `TestPushBehindAnUnadoptedDeployWaitsAndRunsItsCommit` (a push after a `201` leaves that deploy running to `live`, then runs with its own commit, and a second push replaces only the first push's waiting deploy), `TestPushBehindAnAdoptedDeployWritesThrough`, `TestFanoutBehindAnUnadoptedDeployShipsItsBuildOnceThatEnds`, `TestAPushThatWaitsLeavesTheAppAlone`, `TestACheckedPushBehindAnUnadoptedDeployStaysPending`, `TestABlueprintSyncWaitsForTheDeployAheadToBeAdopted`, `TestARollingWriteWaitsForTheDeployAheadToBeAdopted` (Patch and PatchLocked), `TestARollingWriteDoesNotWaitWhereNothingCanBeReplaced`, `TestAWriteThatRollsNothingDoesNotWait` and `TestAStagedRollingWriteWaitsOnTheLiveApp`. Ten mutants, each reverting one part of the fix, all fail their test. A git push is covered by these tests only, because a live check needs a repository bex controls.
- **Docs.** ADR018's Trigger, List / get deploy objects and Overlapping Deploy Policy rows are amended, and the "Still open" sentence is replaced.
- **Static publish.** The premise holds from the code: `pinnableSourceRelease` returns false for `directStaticPublish`, so `releaseInFlight` never holds an adopted no-build publish. That is an operator change to the publish Job's view, filed as [w8/392](../blocked/392.md).
- **Owed:** the production check in the gate once the pin carries `93e61e60ea`.
