# 037 — `bex logout` on one machine signs the user out of every CLI session

Why: logging out a laptop (or a CI job, or an agent sandbox) silently kills the same user's CLI sessions everywhere else, which then fail with a misleading "your token is expired". Render's logout revokes only the presented token.

Severity: major. Attribution: server (`lego/backend/internal/cliauth`).

## Repro (2026-10-03, `/qa-find-bugs-cli` sweep 1 of the w8 loop)

Production `https://api.bex.co/v1/`, released `bex v0.2.1` (pin v2.27.0 `a764810a7682`), deployed revision unknown, human device login as the QA user, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY. Two isolated config dirs, A and B, each with its own successful `bex login`.

```text
07:22:53  after B's login:   A whoami → ok    B whoami → ok
07:23:09                      A → ok           B → ok
07:23:12  BEX_CLI_CONFIG_DIR=<B> BEX_CLI_CONFIG_PATH=<B>/cli.yaml bex logout -o text
          → "Successfully logged out of Render."
07:23:21  A: bex whoami -o json → exit 1  "Error: your token is expired; run `render login` to get a new one"
07:23:29 … 07:23:54  A still fails on every poll
```

A's stored `expires_at` was still ~7 days away, so the CLI never attempted a refresh. The same thing happened earlier in the sweep with no local logout at all: A's session died 32 minutes after login. A concurrent QA run using the same account had most likely run `bex logout`.

## Mechanism

- Upstream `cmd/logout.go` calls `oauth.RevokeToken(ctx, apiCfg.Key)`, which sends **this config's** access token to `POST /v1/oauth/revoke`. It then tells the user to revoke "your CLI token" at `settings#cli-tokens`. Render manages CLI tokens one by one.
- `lego/backend/internal/cliauth/service.go:194-238` (`revoke`): for the CLI/mobile public client it sends `DELETE /admin/oauth2/auth/sessions/consent?subject=<sub>&client=<cli client>` (l.209-216). Deleting the consent session revokes **every** access and refresh token Hydra issued to that client for that subject. That means all of the user's devices. `invalidate` then evicts only the presenting token from the local cache.
- `w4/done/m27/done/t004.md` specified "revokes the caller's access + refresh chain/consent". It verified that a second **user** is unaffected, but never tested a second **device** of the same user. Its out-of-scope line ("Global sign out every device") shows that a global sign-out was not intended.

## Fix

- Revoke only the presented grant. Use Hydra's public RFC 7009 revocation (`POST <hydra-public>/oauth2/revoke`, `token=<presented access token>`, `client_id=<CLI public client>`, auth method `none`). Fosite revokes by request ID, so the access token and the refresh chain rotated from the same device grant die together. Other device grants, which have different request IDs, survive. Keep the `invalidate` cache eviction and the cross-replica revocation marker for the revoked token only.
- Keep the consent-session wipe only for an explicit "sign out everywhere" action, such as the dashboard's connected-apps revoke (w4/m18). It is not part of `bex logout`.
- Mobile shares `isPlatformHumanClient`, so apply the same per-grant rule to `MobileClientID`.

- [ ] Controls: a second user is unaffected (m27 control). The machine API-key self-revocation branch is unchanged. Dashboard connected-apps revoke still kills all of that client's tokens.
- [ ] Backend test: `revoke` calls the per-token revocation, never `sessions/consent`, for the CLI and mobile clients.

## Unverified

- That production Hydra's fosite revocation removes the whole rotated refresh chain for one grant when given its access token. If it does not, revoke by the refresh token instead. That would need a bex-side lookup, because upstream sends only the access token.
- Whether the cross-replica positive-cache marker (`BumpOAuthRevocation`, subject+client granularity) would also evict other devices' cached tokens. If it is subject+client, it needs a per-token key.

## Closure (2026-10-03)

Fixed: `cliauth.revoke` (`lego/backend/internal/cliauth/service.go`) now revokes only the presented token at Hydra's public RFC 7009 `POST /oauth2/revoke` (`client_id` = the CLI or mobile client, auth `none`) and never calls `sessions/consent`; the unused admin URL was dropped from `cliauth.New`. Both unverified points are settled. (1) Against `oryd/hydra:v26.2.0`, the production image, run locally in memory mode with two auth-code grants for one subject: grant A rotated once, then revoking A's new access token gave HTTP 200, A access inactive, and A refresh `invalid_grant`. Grant B's access stayed active and its refresh still rotated. (2) The subject+client revocation marker is only a cache-eviction epoch. Other devices' cached tokens re-introspect as active, which the server-level test `TestRenderCLILogoutImmediatelyInvalidatesCachedAccessToken` now asserts with an `other-device` token. New tests: `TestLogoutRevokesOnlyThePresentedGrant` (CLI and mobile) and `TestLogoutHydraRefusalFailsClosed`. ADR012 logout text was updated. Backend `go test ./...` and backend lint are clean. The production two-config `bex logout` re-check follows the deploy of this commit.
