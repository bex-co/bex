# Audit every Render-gated create/update body against its bex handler

Why: w8/135 found that a whole REST verb pair was unreachable because the pinned Render request schema and the bex handler's strict decoder demanded contradictory bodies, and nothing tested the two composed. The same drift can hide on any other Render-shaped operation whose bex handler deliberately diverges.

Filed from w8/135's fix on 2026-10-19. `applyRenderCompatibility` (`lego/backend/internal/api/render_openapi.go`) widens the contract only where a concession is listed in `renderRequiredCompatibility` / `renderBodyPropertyExtensions`. For any other `create-*` / `update-*` (and other body-bearing) operation, a field Render requires that the bex handler does not decode, or a field bex needs that Render does not declare, makes the strict stack refuse every bex body. The package tests drive handlers without the validator, so the conflict surfaces only on production.

Do:

- For each body-bearing operation bex registers behind the Render validator, send the bex handler's minimal valid body through `newRenderRequestValidator` + the real handler (as `TestRegistryCredentialRESTWritesPassTheRenderValidator` does) and record which reach the handler.
- Ideally land one table-driven composed test covering them, so a future concession gap fails CI.
- File each conflict found as its own fix, or fix it here if small.

Acceptance: a composed test enumerates the Render-gated create/update operations bex serves and proves a bex-dialect body reaches each handler; any conflict found is fixed or filed.

Estimate: ~1h (likely a milestone if several conflicts turn up).

**Done (2026-10-19):** bex serves 25 Render operations with a JSON request body. `TestRenderGatedBexBodiesReachTheirHandlers` (`lego/backend/internal/api/render_gated_bodies_test.go`) sends a minimal bex-dialect body for each through the real server: the pinned Render request validator, then the handler's strict decoder. It asserts that neither a schema refusal nor an "unknown field" comes back.

Audit result: no other contradiction. All 25 reach their handlers. The one apparent miss, `create-service`'s Render-required `image.ownerId`, is a field the handler decodes and the official CLI always sends (empty), so a body satisfying both exists.

Run against the contract from before w8/135 (`410b9ae7b^`), the test fails exactly create-registry-credential and update-registry-credential, so it guards the class in CI. Test-only change; nothing to verify live.
