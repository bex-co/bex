# A prebuilt-image deploy reports the linux/amd64 platform-manifest digest as `image.sha`, not the tag's index digest; a service created by digest reports a different digest than its own `image.ref` (w4/m243 regressed w8/m122)

Why: w8/m122 made each prebuilt-image deploy report the digest it ran as `image.sha`, specified as the tag's **index** digest. That is what the registry's `Docker-Content-Digest`, `docker buildx imagetools inspect` and the kubelet report, and what a user pins with `image@sha256:…`. Since w4/m243 pins image web services by digest, bex reports the **platform manifest** digest instead. So the value matches nothing the user sees. For a service created by digest, the deploy's `image.ref` (`…@sha256:006b…`) and `image.sha` (`sha256:bcfc…`) disagree within one object.

Severity: **minor** (wrong digest value; nothing fails, but a user or tool verifying "which image is running" gets a mismatch). Attribution: platform runtime (operator image pinning feeding m122's digest record). Estimate: ~40m. Source: `/qa-find-bugs-cli` loop sweep 1c70, 2026-10-27 00:39–00:45 UTC (running w8/m122/t007). Context: HEAD-built bex `1c521b261` with pinned Render CLI v2.27.0 `a764810a7682`; platform pin `b4726243e74f`; `https://api.bex.co/v1/`; workspace `bex-canary`; human device login.

## Root cause

- `registry.ReadImageConfig` follows an image index to its linux/amd64 child and returns the child's digest as `ImageConfig.Digest` (`lego/operator/internal/registry/image_config.go:287–294`, return at `:80`).
- `resolveImageNetwork` pins the release image to `prefix + "@" + metadata.Digest` (`lego/operator/internal/controller/image_network.go:159`), so `status.image` carries the platform digest.
- `recordImageDigest` treats a digest-pinned `status.image` as its own evidence (`image_digest.go`, rule 1 in ADR004 § Deploy image digest). bex-api then reports that platform digest as `image.sha`.
- m122's design and its evidence (`.pm/w8/blocked/m122/evidence/README.md:22`: "The kubelet reports the tag's **index** digest, not the platform manifest") predate m243's pinning.

## Fix

- Keep the digest the user-facing reference resolves to (the index digest for a multi-arch tag; the manifest digest for a single-arch tag; the user's own digest for a by-digest create) and report that as `image.sha`. Two options:
  1. **Recommended:** have `ReadImageConfig` return both the top-level digest of the requested reference (the `Docker-Content-Digest` of the first fetch) and the platform digest. Pin the release image to the top-level digest, since the kubelet resolves the platform itself as before m243. That also makes rule 1 report the right value.
  2. Keep pinning by platform digest, but record the top-level digest separately in `status.imageNetwork` and let `recordImageDigest` prefer it.
- Make the image-config cache key and the m243/t008 "read once per release" work use the same top-level digest.
- Update ADR004 § Deploy image digest to say which digest is reported for multi-arch tags.

## Blast radius

- Every prebuilt-image web service created since w4/m243 (`web-image-v1` / `web-image-configured-v1`), and private image-port services if they share the pin path.
- Git-built Docker services report their own build digest (single manifest), so they're unaffected.
- REST `image.sha`, GraphQL `Deploy.imageSha`, MCP `get_deploy`/`list_deploys`, the CLI `SHA:` line and the dashboard all read the same record.
