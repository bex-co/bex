# `bex keyvalues update --ip-allow-list` on a Persistence Off store fails with 400 `KEY_VALUE_RESTART_CONFIRMATION_REQUIRED`: enabling external access restarts (and empties) the store on bex, where Render changes the allowlist without a restart

Why: Render changes a Key Value's IP allowlist without restarting it (ADR018's Key Value row: "Render documents no restart for allowlist changes", [render.com/docs/key-value](https://render.com/docs/key-value)). On bex, the first time a store gets external access its pod template gains the TLS listener and the store restarts. For a Persistence Off store, which Render's own CLI offers (`--persistence-mode off`), that deletes every key. Bex therefore refuses the change unless the body carries a bex-only `confirm` phrase. The pinned CLI has no way to send it, so a valid upstream `bex keyvalues update --ip-allow-list …` can never succeed on such a store. A Render-shaped REST PATCH is refused the same way. ADR018 lists the restart as a divergence with no user sign-off.

**Severity:** minor (affects Persistence Off stores only; the workaround is to switch persistence on, enable access, then switch it off, or to accept the data loss through the dashboard or a non-CLI client). **Attribution:** platform runtime (Key Value pod template) plus the server gate that guards it. **Estimate:** 1h30m. **Source:** `/qa-find-bugs-cli` sweep 1313, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1313--key-value-allowlist)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`, human device-login grant, HEAD-built pinned CLI. The fixture was deleted afterwards (404).

1. `bex keyvalues create --name qa-20261022-804e66-kvacl --plan free --confirm -o json` → `red-dbcpn37t87js73873b9g`, `ipAllowList: []`, `public: false`, `persistenceMode: journal_snapshot`.
2. `bex keyvalues update red-dbcpn37t87js73873b9g --persistence-mode off --confirm` → exit 0; the store is `available` with `persistenceMode: off`.
3. `bex keyvalues update red-dbcpn37t87js73873b9g --ip-allow-list 'cidr=203.0.113.0/24,description=qa1313-docnet' --confirm` → **exit 1**: `Error: received response code 400 (KEY_VALUE_RESTART_CONFIRMATION_REQUIRED): turning on external access for "qa-20261022-804e66-kvacl" restarts it, and with persistence off that deletes every key; retry with confirm="sudo clear key value qa-20261022-804e66-kvacl"`. The allowlist stays `[]`.
4. `PATCH /v1/key-value/<id> {"ipAllowList":[{"cidrBlock":"203.0.113.0/24","description":"qa1313-docnet"}]}` (Render's body) → the same 400.

## Expected

Setting or replacing the allowlist applies without restarting the store or touching its data, whatever its persistence mode. Steps 3 and 4 succeed, and the store keeps serving existing connections and keys.

## Root cause

- `lego/operator/internal/controller/keyvalue_controller.go:696–702,742`: `tlsListener: public || (listening && kvDomain != "" && !kv.Spec.Suspended)`. A store that has never been public runs without `--tls-port`. The first enable adds it (`:900–902`), which changes the StatefulSet template and restarts the pod. w4/m233 already keeps the listener once it has run, so later toggles do not restart.
- `lego/backend/internal/keyvalue/service.go:940–962` (`externalAccessRestarts`, `requireRestartConfirmation`) turns that restart into the confirmation gate for Persistence Off stores.

## Fix

Start every store with the TLS listener from creation whenever `BEX_KV_DOMAIN` is set: `tlsListener: kvDomain != "" && !kv.Spec.Suspended`. External access then stays gated only by `public`, at the Service TLS port and the kv-sni-proxy route (as the struct comment already describes), and turning it on never changes the pod template. `externalAccessRestarts` becomes false for every such store, so the confirmation gate disappears for them.

Existing stores that never listened would restart once when the listener is added. Do not roll them for it: add the listener on their next natural restart (plan, persistence or version change, or resume). Keep the gate only for a legacy store that still lacks it, until then.

Update ADR021 §3 and ADR018's Key Value row.

## Blast radius

New Key Value stores on every surface (REST, GraphQL, MCP, dashboard, CLI, Blueprints with `ipAllowList`). The listener is internal until `public`; the certificate is already provisioned per store (`reconcileKeyValueTLS`). Existing listening stores are unchanged.

## Acceptance

- Envtest: a new store's template has `--tls-port` before it is public; flipping `public` does not change the template hash.
- Live after deploy: repeat steps 1–3. Step 3 exits 0, and a key written over the internal address before step 3 is still present after it. Delete by ID with a 404 proof.

## Dedupe

`git grep -i 'RESTART_CONFIRMATION|tls listener|allowlist.*restart' .pm`: w4/m233 (done) made later toggles restart-free and added the gate. No open item covers the first enable.

**Done 2026-10-22:** `keyValueIsNew` (operator): a store with no StatefulSet (confirmed uncached) and a configured issuer starts with the TLS listener, so its first external access restarts nothing; the backend gate already keys off `status.tlsListener`. Pre-existing stores are not rolled; they gain the listener at their first enable. ADR021/ADR018 amended. Live steps 1–3 after deploy (create a NEW store).
