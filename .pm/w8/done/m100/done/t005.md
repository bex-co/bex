## Closed — 2026-11-19 (loopx session)

Every `native-common-image.yml` utility cohort (`TestNativeUtilityGeneratedImages`) runs these real-image checks on the image it publishes:

- **The original program** (already maintained). `python313-original` runs the frozen m100 build on the Python 3.13 primary through `original-cases.py`: the before proof, the original `swig -python qa_swig.i`, the `gcc -shared -fPIC $(python3-config --includes)` compile and the `build` step, which the frozen `valid_after` checks. Three HTTP requests on a `--network none` runtime then import the extension again and pass the frozen oracle.
- **New SWIG checks** in `utility-check.py`, at the `node-compute` build and network-off runtime and at the `node-static` build. They replace the two older SWIG lines, which they cover.
  - m100's own interface through its original argv, outside the original program. `swig -swiglib` must answer `/usr/share/swig4.0` with no `SWIG_LIB` set, and the generated wrapper and proxy must be the exact bytes production generated (`a5594a40…`, `25875c83…`). The compiled module's results must equal weighted sums computed independently in Python and the exact `Crème brûlée & 李`.
  - The packaged library: `typemaps.i` `OUTPUT` arguments return `[0, 3, 2]` for 17/5 and `[0, -3, -2]` for -17/5 (C truncation, where Python's `divmod` gives -4 and 3), an `exception.i` `SWIG_exception` raises `ValueError` with its message, and `carrays.i` arrays reach C (sum 43).
  - The data tree is what supplies them: under an authored `SWIG_LIB` pointing elsewhere, the same interface exits 1 unable to find `swig.swg` and `typemaps.i`.
  - C++: `-c++` with `std_string.i`, compiled by `g++`, carries `crème brûlée & 李 two words` through `std::string` and changes only the ASCII letters.
  - Include paths and outputs: `%include "custom.i"` fails with a named error and no wrapper until `-Iinc` names the authored directory; `-o gen/…` and `-outdir inc` place the wrapper and the proxy there, and the module imports.
  - Exit statuses: 1 with `Syntax error in input(1).` and neither wrapper nor proxy written; 1 for an unknown option.
- **New omission control.** `missing-swig` removes only the `/usr/bin/swig` link. It proves `command -v swig` fails while `swig4.0` still answers 4.1.0, `python/python.swg` remains in its library and `gcc` runs. The original m100 build must then fail with `swig: command not found` after its ready line, the sweep 421 failure.
- **How this was checked before shipping.** The host is arm64 and the adopted image is amd64-only, so the generated-image gate cannot run here. Two local replicas installed Debian's `swig`/`swig4.0` `4.1.0-0.2` (with `python3-dev`) on the stock `node:24-bookworm` and `python:3.13-bookworm` images:
  - the new block passed offline as uid 1000 and as root, and generated the same wrapper and proxy bytes production did on amd64;
  - each of 14 source mutations failed the assertion it targets: swapped weights, ASCII-only Unicode, `-builtin` (other wrapper bytes), a wrong library path, no `OUTPUT` typemap, no `%exception`, Python's division, `SWIG_LIB` at the packaged library, C++ wrapped as C, every letter upper-cased, no `-Iinc`, no `-outdir`, a valid "bad" interface and a known option;
  - two image mutations failed too: deleting `python/typemaps.i` failed the library interface, and deleting `python/std_string.i` failed the C++ one. On stock `node:24-bookworm` the block fails at its first `swig`;
  - the original m100 build and its three network-off runtime requests passed through `original-cases.py` on the Python replica, and on stock `python:3.13-bookworm` the build failed with `swig: command not found`;
  - after the exact `missing-swig` command, the original build printed `QA_SWIG_BEFORE` with `swig_path` null and failed with `swig: command not found`. Variants that also deleted `swig4.0` or the library stopped in the removal layer before its ready line.
  - The push of this change re-runs the amd64 utility cohort through `native-common-image.yml`; that run is the amd64 proof.
