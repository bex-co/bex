# The first request to a sleeping free web service fails with an immediate 503 (`{"error":"service not ready"}`) where Render holds it through the spin-up and serves it; webhooks, bots and API clients lose that request

Why: Render delays the first request to a spun-down free web service until it is back up. Its dashboard notice for free instances reads "Your free instance will spin down with inactivity, which can delay requests by 50 seconds or more", and [render.com/docs/free](https://render.com/docs/free) says "Render displays a loading page to connecting browsers while a service is spinning up". So a browser sees a loading page, and any other client waits and is then served. Bex's activator wakes the service but answers the triggering request at once:

- a non-browser client gets `503 {"error":"service not ready","retryAfter":5}`;
- a browser gets a polling page, which matches Render's loading page and is not in scope here.

A webhook delivery (GitHub does not retry failed deliveries automatically), a chat-bot callback, an API client or a `curl` script therefore fails on the first contact after idle. ADR007 records this as "a deliberate agent/API reliability divergence" ("Render instead holds a non-browser request through the cold start"). There is no user sign-off, and ADR018 does not list it, so under ADR008 § Render parity first it is an open gap.

**Severity:** major (every free web service's first request after 15 idle minutes fails for non-browser clients; free is where hobby bots and webhooks live). **Attribution:** platform edge (activator). **Estimate:** 3h. **Source:** `/qa-find-bugs-cli` sweep 1309, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1309--cold-start)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`. Owned free image web service (`python:3.12-alpine`, `dockerCommand: python -m http.server 10000`, `srv-dbcocsou12fs73e9aid0`):

1. Live at 03:44:19Z; one warm `GET /` → 200 at 03:44:30Z. After that only API reads, no traffic to its URL.
2. `service_hibernated` at 04:00:19Z (15 m 49 s idle, consistent with Render's 15-minute window).
3. `GET /` with `User-Agent: curl/8.7.1`, `Accept: */*` → **503 in 0.65 s**, `Retry-After: 5`, body `{"error":"service not ready","retryAfter":5}`.
4. Retries at +1 s and +6 s → 503; at +12 s → 200. The service was ready about 12 s after the wake, well within the time Render would have held the request.

The fixture was deleted (204 → 404). The same 503 was seen on the pre-existing `hello-go` in sweep 1300 (one read-only GET).

## Expected

For a client that does not accept `text/html` (API clients, webhooks, `curl`, bots), the request that wakes the service, and any such request arriving while it wakes, is held until an instance is ready. It is then forwarded with its method, headers and body, and the response is the app's own. Render's notice allows "50 seconds or more" and its docs say spin-up "takes about one minute". A browser (`Accept: text/html`) keeps bex's loading/polling page, as on Render. A request still unserved at the bound gets a gateway timeout, as a slow app would.

## Root cause

`lego/operator/cmd/activator/main.go:202,213` call `writeWakeResponse` (`:252–262`) right after `wakeApp` (`:219`) patches the Deployment to one replica. That always returns 503: HTML (polling page) when `text/html` is acceptable, otherwise JSON. The activator never forwards a request to the app. The Ingress stays on the activator until the operator swaps it back to the app Service (`internal/controller/app_controller.go:2814–2840` `ingressRoutesToActivator`). ADR007:75 describes the response negotiation as the chosen design.

## Fix

1. On the wake path, for a request that does not accept `text/html`, hold it instead of answering. Wake as today, then wait for a ready endpoint of the App's Service, using an endpoints/EndpointSlice watch or a short poll. Reverse-proxy the original request to it (`httputil.ReverseProxy` to the App's ClusterIP Service on its serving port), streaming the body. Bound the hold at about 90 s (Render's "about one minute" spin-up, "50 seconds or more"). Past the bound, answer `504`/`503` as now. Coalesce concurrent holds per App so N waiting requests trigger one wake.
2. Keep the existing immediate answers where Render also does not hold: suspended, maintenance, a failed first release, and the first deploy in progress (ADR007 precedence). The w6/m94 readiness hold on an awake but unhealthy service needs its own Render comparison; do not change it silently.
3. WebSocket upgrades are held and proxied the same way (Render counts WebSocket traffic as activity).
4. Request-body limits: stream rather than buffer, so a large upload waits on the TCP connection rather than in activator memory.
5. Update ADR007 (§ wake contract) and add an ADR018 row, removing the "deliberate divergence" sentence.

## Blast radius

Free web services with auto-sleep (every free web service by default since w6/m116), on all clients. The activator also fronts readiness holds and suspended/first-deploy answers; only the wake branch changes. Static sites do not sleep. Paid services never route to the activator for wake. The browser polling page stays; it matches Render's loading page.

## Acceptance

- Unit/integration: a held request to a waking App is forwarded once an endpoint is ready, preserving method, body and headers. Concurrent holds share one wake. A hold past 60 s answers the bounded error. Suspended, maintenance and first-deploy answers are unchanged.
- Live after deploy: repeat the reproduction. The first `curl` after `service_hibernated` returns 200 with the app's body after the spin-up delay. A `POST` with a body is delivered to the app (echo server). Delete by ID with a 404 proof.

## Dedupe

`git grep -i 'cold start|holds? .{0,30}request|wake.{0,40}503' .pm`: open items w4/m164 (idle accounting) and w1/124 (stuck Deploying never hibernates) are about when a service sleeps, not how its wake request is answered. No open item covers holding the request.

**Done 2026-10-22:** `cmd/activator/hold.go` — non-browser requests that trigger or join a wake of a Hibernated App are held (≤90 s, 256 total/64 per App, one poller per App) and reverse-proxied to the App's Service; 504 at the bound; browsers, awake-unready and every earlier-precedence state unchanged. New hosting-regime NetworkPolicy `allow-activator-ingress` (activator pods only). Tests `hold_test.go` (+ -race), store policy test; ADR007/ADR018/ADR043 amended. Live repro (including a POST echo) after deploy; the policy reaches existing namespaces on the next reconcile.
