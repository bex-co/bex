## Objective

Confirm the newly visible refused lines agree across every surface that exposes request logs, and that the recorded behavior matches Render's documented contract.

## Context

- Oracle: Render's [inbound IP rules](https://render.com/docs/inbound-ip-rules) — blocked requests still appear in HTTP request logs. One Core log query backs REST, GraphQL, and MCP ([ADR010](../../../../../docs/ADR010-observability.md)); the dashboard reads the same store.
- Discovery contract (w6/m131): offered filter values must be matchable. After t001, `statusCode` discovery must offer `403` only when refused lines actually exist for that service.

## Steps

1. On a dev stack with the fixed shipper: generate an allowlist 403 + a 200 on one owned service; read both back identically via REST (`GET /v1/logs`), GraphQL `logs`, MCP `list_logs`, and the pinned-CLI-shaped filters (`statusCode=403`, `4xx`, `path`).
2. Check `/v1/logs/values?label=statusCode` offers `403` post-fix and the dashboard Filters popover can match it.
3. Record any remaining divergence in [ADR018](../../../../../docs/ADR018-render-parity.md) / [ADR010](../../../../../docs/ADR010-observability.md) if the docs' wording over- or under-claims.

## Files

- `docs/ADR010-observability.md`, `docs/ADR018-render-parity.md` (only if wording needs correction)

## Acceptance criteria

- [x] All four readers return the same refused line set for the same query.
- [x] Discovery and filters agree (offered ⇒ matchable).

## Out of scope

- Dashboard UI changes beyond confirming the existing popover works.
