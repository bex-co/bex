# A Docker build does not find its secret files in the build-context root, as on Render

Why: Render gives a Dockerfile build its secret files twice: as BuildKit build secrets, and as files in the root of the build context ("Render also copies your secret files into the root of your Docker build context"). bex gives the build secrets only (w1/m178), so a Dockerfile that reads an uploaded `.npmrc` or `.env` from its context with `COPY` builds on Render and fails, or builds without the file, on bex.

**Severity:** minor (parity; a Dockerfile written for the mount form already works). **Attribution:** infrastructure (operator build plane). **Estimate:** ~50m. **Source:** found while working w8/m154 t003 (2026-11-11); Render's page read the same day.

## Evidence

- render.com/docs/docker-secrets: "Render also copies your secret files into the root of your Docker build context." and "If your Dockerfile copies the full build context (for example, with `COPY . .`), your image contains your secret files." It tells authors to list the names in `.dockerignore` to keep them out of the image, and adds: "Secret mounts continue to work for files in `.dockerignore`."
- `lego/operator/internal/build/dockerinputs.go`: `dockerBuildInputsScript` copies the files into a private EmptyDir and `dockerBuildInputsEnv` passes each as `--secret id=<render id>,src=…/files/<name>`. Nothing is written into the context directory BuildKit reads.
- Not reproduced on a cluster: read from the code.

## Fix

1. For a Dockerfile build with secret files, write each file into the root of the build context before `buildctl` runs (the context is the service's `dockerContext`, else its `rootDir`). A repository file of the same name: decide and record (Render does not say; the secret file winning matches w8/m154's rule for native services).
2. Keep the build secrets as they are.
3. This puts secret bytes where `COPY . .` bakes them into the image, exactly as on Render. Record that in ADR013 with Render's `.dockerignore` advice, and say it in the dashboard's secret-files help for Docker services. If the user would rather keep bex stricter than Render here, that is a signed-off difference for ADR018, not a default.

## Acceptance

- A Dockerfile with `COPY .npmrc /root/.npmrc` builds when `.npmrc` exists only as a secret file.
- With the name in `.dockerignore`, the image does not contain the file and `RUN --mount=type=secret,id=_npmrc` still reads it.
- A Dockerfile build without secret files is unchanged; native builds are unchanged.
- An operator test pins the context copy and the `.dockerignore` case.

## Unverified

- Render's behavior was read from its documentation, not run on a Render account.

## Dedupe

w1/m178 (done) added the build secrets and did not copy into the context. w8/m154 covers native runtimes at runtime only. No other `.pm` item mentions the build-context root.

## Shipped 2026-11-11 (w8 drain); the live check waits for the next production deploy

- **Operator.** A Dockerfile build with secret files gets one more init container, `context-files`, between the clone and BuildKit (`dockerContextFilesStep`, `lego/operator/internal/build/dockerinputs.go`). It copies each secret file into the root of the Docker build context (`dockerContext` when set, else the root directory). It is restricted like the clone, and BuildKit keeps its read-only source mount. The build secrets are unchanged: they are read from the private snapshot, so a name in `.dockerignore` still mounts.
- **The repository cannot steer the copy.** The step enters the context directory and writes relative to it, so no path is resolved twice. The directory it entered must lie inside the checkout; a link out of it, or a missing directory, fails the build as the tenant's error. A link or file of the secret's name is replaced, never followed; a real directory of that name is kept. (Review found that the first version, which rebuilt the path from `pwd -P`, lost a trailing newline of a directory name and could then follow a sibling link out of the checkout; a test pins it.)
- **Dashboard.** The secret file dialog of a Docker-runtime service says the file is also copied into the build context root and should be listed in `.dockerignore` unless the image is meant to contain it, as Render's page does.
- **Docs.** ADR013 § secret files and ADR018's secret-files row.
- **Checked here:** operator tests for the Job shape and the script (`dockercontext_test.go`), and two real `docker buildx` builds of the acceptance cases: `COPY .npmrc` builds from a context that got the file from the copy, and with `.npmrc` in `.dockerignore` the image lacks it while `RUN --mount=type=secret,id=_npmrc` still reads it.
- **Still owed:** the first acceptance line on production (a Docker-runtime service whose Dockerfile has `COPY .npmrc`, with `.npmrc` uploaded only as a secret file). It needs the deploy that carries this change.
