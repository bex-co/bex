# A build failure's reason loses its verdict: the kubelet keeps only the head of each build phase's termination message, and bex writes the tail

Why: a build phase writes the last 4096 bytes of its output to `/dev/termination-log`, and the operator reads the failing step and its reason from the end of that message (`nativeCommandFailure`, `buildkitFailureSummary`, `failureTail`). The kubelet, however, caps all of a pod's termination messages at 12 KiB, divides that evenly among every container in the spec (init containers included), and keeps the head of each message (`pkg/kubelet/status/status_manager.go` `normalizeStatus`: `bytesPerStatus = MaxPodTerminationMessageLogLength / containers`; `Message = Message[:bytesPerStatus]`; `MaxPodTerminationMessageLogLength = 1024 * 12`). A native static build pod has 4 containers (3072 bytes each) and a native service build 5 (2457 bytes each), so the end of a 4096-byte message, which holds BuildKit's verdict, is cut off. The reason then falls back to "build failed in the build environment step" and quotes BuildKit's raw transcript, bex's internal build script included.

**Severity:** major (a failed build's reason misnames the step and shows bex's recipe instead of the user's error, on any build whose transcript tail runs long). **Attribution:** platform build (termination message size vs. the kubelet's per-container share). **Source:** w8/291's production check, `/loopx w8` / QA sweep 7ab8, 2026-11-12, pin `33e1b1e6117c`, released `bex v0.5.0`, workspace `bex-canary`.

## Evidence

Free native static site `qa-20261112-7ab8-static` (`srv-dbr104qqljrc73co79l0`, `render-examples/express-hello-world`, build `mkdir -p out && echo 'v1-7ab8' > out/index.html`). After it went live, `bex services update <srv> --publish-directory nope --confirm -o json`, then `bex deploys create <srv> --wait -o json --confirm`: exit 1 in 74 s, `build_failed`, and the site kept serving `v1-7ab8`.

- **The build log holds (w8/291):** `==> Publish directory nope does not exist!` at 19:18:42, with no `Uploading build...` and no `Build successful`.
- **The failure reason does not:**

```text
build failed in the build environment step:
#27 0.861 (Use `node --trace-deprecation ...` to show where the warning was created)
…
#27 2.571 ==> Publish directory nope does not exist!
#27 ERROR: process "/bin/bash -c . /opt/bex/load-env\n/bin/bash /opt/bex/install-deps || exit\nbex_publish_dir='nope'\nbex_publish_check() { … }\ntrap bex_publish_check EXIT\nmkdir -p out && echo 'v1-7ab8' > out/index.html" did not complete successfully: exit c
```

The message ends at `exit c`: the kubelet kept 3072 of the 4096 bytes, so BuildKit's summary block and its closing `error: failed to solve: process … exit code: 86` were gone, and `nativeCommandFailure` found no verdict to map. The same transcript, built locally with the pinned BuildKit and read whole, maps to `publish directory` / `Publish directory nope does not exist!`.

## Fix (shipped 2026-11-12, `/loopx w8`)

- `captureFailureTail` (`lego/operator/internal/build/build.go`) gives every build phase `BEX_MESSAGE_BYTES` = min(4096, 12 KiB ÷ the pod's container count), and `classifyPrelude` writes that many bytes of the output's tail, so the kubelet keeps the message whole and its end (the verdict) survives.
- Every phase run through `classifyPrelude` now writes its own message, not only the native BuildKit phase. The clone and a Dockerfile build's BuildKit phase used to leave it to the kubelet's log fallback (up to 2 KiB), whose end the kubelet also cut once the pod had more than six containers (a native build with the build cache and signing has eight, 1536 bytes each).
- **Test:** `TestBuildPhaseMessageFitsThePodsShare` checks every container's budget, with the resolve phase (five containers, 2457 bytes each, as in production). It feeds a long publish-failure transcript through the phase, cuts the message as the kubelet does, and still gets the `publish directory` step with Render's sentence. With the budget ignored the message is 4096 bytes against a 3072-byte share. `TestBuildCacheAddsOnlyWhatItClaimsToAdd` treats the budget as a cache seam (the cache phases change the count).
- **Review** (`/simplify`, three reviewers): build Jobs are create-only, so existing Jobs and BuildKit's cache keys are unaffected. Publish, pre-deploy and runtime messages are short or written by the kubelet itself, so they need no budget.
- **Blast radius:** every build pod (native, Dockerfile, buildpack, static), every phase's termination message. A smaller tail means the reason quotes less output; the verdict is what it now keeps.
- **Still owed on production:** the 7ab8 steps after the deploy that carries this. The deploy closes `build_failed` with "build failed in the publish directory step: Publish directory nope does not exist!", and a build command failing with `exit 3` still reads "build failed in the build command step: … exited with code 3".
