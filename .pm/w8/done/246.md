# Postgres HA and read-replica refusals name the internal plan id and a Kubernetes CPU quantity, not the plan the user typed

Why: a CLI user who asked for `--plan 0.1c-256mb` is told `plan "basic-256mb" has 100m CPU`: a plan name they never typed, a spelling that is neither the REST enum's (`basic_256mb`) nor the CLI's, and a CPU unit Render never shows.

**Severity:** minor (copy; status codes and error codes are right). **Attribution:** server (bex-api Postgres validation). **Estimate:** ~20m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `88c4`, 2026-11-10, released `bex v0.5.0`, production pin `4630a48a7`.

## Evidence

```text
$ bex pg create --name qa-20261110-88c4-pg --plan 0.1c-256mb --read-replica qa-20261110-88c4-rr --version 17 -o json --confirm
Error: received response code 400 (POSTGRES_READ_REPLICA_PLAN_UNSUPPORTED): read replicas require a Postgres plan with at least 0.5 CPU;
       plan "basic-256mb" has 100m CPU; remove read replicas before selecting this plan                                      (nothing created)
$ bex pg update dpg-dbpdmmij0hgs73eavo20 --high-availability -o json --confirm            (database on 0.1c-256mb)
Error: received response code 400 (POSTGRES_HA_PLAN_UNSUPPORTED): high availability requires a Postgres plan with at least 1 CPU; plan "basic-256mb" has 100m CPU
```

The thresholds are right: Render requires 0.5 CPU for replicas and 1 CPU for HA (ADR018 row 189).

## Root cause

- `lego/backend/internal/postgres/tiers.go:137` formats `tier.ID` (the canonical internal id, `basic-256mb`) and `tier.CPU` (a Kubernetes quantity, `100m`).
- `lego/backend/internal/postgres/admission.go:86` does the same for replicas. Its remedy, "remove read replicas before selecting this plan", fits a plan change on a database that has replicas, not a create that asks for one.

## Fix

Name the plan as the request spelled it. Fall back to the spec-based id (`0.1c-256mb`) when the request named no plan (an existing database). Print CPU as Render does (`0.1 CPU`). Keep the `params` object, but put the requested plan in it. On create, say "choose a plan with at least 0.5 CPU (for example 0.5c-1g) to add read replicas". REST, GraphQL, MCP and Blueprint share these helpers.

## Acceptance

- Unit: `--plan 0.1c-256mb` with a replica → the message names `0.1c-256mb` and `0.1 CPU`. `basic_256mb` → names `basic_256mb`. HA enable on an existing `basic-256mb` database → names its spec-based id.
- Live: the two commands above print the corrected text and still exit 1 with the same codes.

## Dedupe

`rg -n 'POSTGRES_HA_PLAN_UNSUPPORTED|READ_REPLICA_PLAN_UNSUPPORTED' .pm`: w8/m50 and w8/m43 introduced the checks; no item covers the wording.

## Done — 2026-11-10

The HA refusal (`lego/backend/internal/postgres/tiers.go`, `checkHighAvailabilityPlanNamed`) and the read-replica refusal (`admission.go`) now name the plan as the request spelled it. When the request named no plan, as with HA enabled on an existing database, they use its spec-based id (`tiers.PostgresSpecID`). CPU is printed as Render shows it (`0.1 CPU`, from the Kubernetes quantity). `params.plan` and `params.cpu` carry the same values. The replica remedy fits the request: adding replicas reads "choose a plan with at least 0.5 CPU (for example 0.5c-1g) to add read replicas", and moving a database that has replicas keeps "remove read replicas before selecting this plan". Codes are unchanged. `TestPlanRefusalsNameThePlanAsTyped` covers `0.1c-256mb` and `basic_256mb` on create, a plan change with replicas, HA on create, and HA enable on an existing `basic-256mb` (named `0.1c-256mb`), with neither `100m` nor `"basic-256mb"` in any message. `TestPostgresSpecID` covers the catalog helper. REST, GraphQL, MCP and Blueprint share these checks.
