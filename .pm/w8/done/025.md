# 025 — Kubernetes' "unable to retrieve container logs for containerd://…" placeholder is served as the tenant's own app log line

Why: when a container is gone (evicted, or garbage-collected after a cron run), `bex logs` shows lines like `unable to retrieve container logs for containerd://4336b7cbe…`, typed `app` at `level: unknown`, as if the tenant's process printed them. They are Kubernetes' own error text, and they carry an internal containerd id. Users debugging a crashed run read platform noise as their own output, and the real cause (the container was removed) is never said plainly.

Live, 2026-09-26, production `726042a28`, `bex v0.2.1` (pin v2.27.0), workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 32. Fixture: free busybox cron `srv-das1da0d0qnc73d7a0v0` that wrote past its 1 GiB ephemeral-storage limit and was evicted (deleted afterwards):

```text
$ bex logs -r srv-das1da0d0qnc73d7a0v0 --limit 40 -o json
{"timestamp":"2026-09-26T19:05:33.351680017Z",
 "labels":[{"name":"type","value":"app"},{"name":"resource","value":"srv-das1…"},{"name":"instance","value":"srv-das1…-fhps0gn0…"},{"name":"container","value":"app"},{"name":"level","value":"unknown"}],
 "message":"unable to retrieve container logs for containerd://4336b7cbe…"}
{"timestamp":"2026-09-26T19:05:33.754231323Z", … same message …}
```

The run's real output (`CPUMAX=…`, `WROTE-1x500MB`) sits alongside these lines.

## Mechanism

- `lego/backend/internal/logs/podlogs.go:34-41` (`NewPodLogSource`) and `:56-66` (`NewPodLogStream`) read the pod-log subresource with `Timestamps: true`, so every genuine line starts with an RFC3339Nano timestamp.
- When the container's log file no longer exists, the kubelet answers **200** with a single untimestamped body line, `unable to retrieve container logs for containerd://<id>`. bex parses that like any line and gives it a read-time timestamp, `type: app` and `level: unknown`. It can repeat once per read.
- `w6/done/m111` §"Look-alike symptoms" recorded the same symptom ("six of the nine captured `type: app` lines are Kubernetes' own error text"), noted as a pipeline-classification question, but did not file it.

## Fix

In the pod-log line parser used by both functions, treat a line **without** the RFC3339 timestamp prefix that matches the kubelet placeholder (`unable to retrieve container logs for `) as a platform signal, not app output. Either drop it, or replace it with one platform-typed line such as `==> logs for this instance are no longer available (container removed)`, deduplicated per instance. Never emit the containerd id.

## Acceptance

- [ ] On an evicted or exited-and-collected instance, `bex logs -r <srv>` never returns a `type: app` line containing `unable to retrieve container logs` or a `containerd://` id.
- [ ] Parser test: an untimestamped placeholder body is dropped or re-typed, and a genuine timestamped app line containing the same words is kept.

## Outcome (2026-09-27) — done

`parseContainerLogLine` (`lego/backend/internal/logs/service.go`), shared by the pod-log query read and the live follow, recognizes the kubelet's untimestamped `unable to retrieve container logs for …` body (every genuine line carries the `Timestamps: true` prefix). It becomes one platform line: `==> logs for this instance are no longer available: its container was removed`, with `container: platform` (the synthesized-line label) and no containerd id. A tenant's own timestamped line with the same words is untouched. Kubelet sends one such body per read, so there's one line per instance read and nothing to dedupe. Test: `TestKubeletLogsGonePlaceholderIsAPlatformLine`. Loki history comes from the shipper reading container files, not the kubelet API, so it doesn't carry this placeholder. That wasn't re-probed live.
