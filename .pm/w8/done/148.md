# Tenant requests carry no `Rndr-Id`, and request logs have no `requestID` to correlate with app logs

Why: Render's logging guide tells developers to read the per-request `Rndr-Id` header (sent both to the service and back to the client), log it, and search for it to see a request's whole history. The same value appears as `requestID` in Render's HTTP request logs. On Bex the header never arrives and request logs carry no ID, so a migrated app's request correlation silently logs nothing and support conversations have no shared request ID.

**Severity:** minor (missing documented tracing aid; no data loss). **Attribution:** infrastructure (edge) plus logs. **Estimate:** about 90 minutes across edge, shipper and logs read path; promote to a milestone if the edge piece needs a plugin. **Source:** `/qa-find-bugs-cli` sweeps 1241 and 1254, 2026-10-20 ([evidence](evidence/cli-sweep1254/README.md)).

## Observed

- Headers received by a free echo-server web service (sweep 1241): `host`, `user-agent`, `accept-encoding`, `x-forwarded-for`, `x-forwarded-host`, `x-forwarded-port`, `x-forwarded-proto`, `x-forwarded-server`, `x-real-ip`. There is no `rndr-id` and no other request ID. Response headers to the client: `Content-Type`, `Content-Length`, `Date`, `Etag`, `Connection`, also with no request ID.
- `bex logs -r <service> --type request -o json` entries carry labels `type`, `resource`, `method`, `statusCode` and a raw Traefik JSON `message`, but no request ID field or label (sweep 1228 sample).

## Expected (Render)

[render.com/docs/logging](https://render.com/docs/logging): “In each HTTP request log entry, the value of the `requestID` field uniquely identifies the associated request. Render includes this same value in the `Rndr-Id` HTTP header — both in the request to your web service and in the response to the requesting client … In your web service's code, you can extract this value from the header and include it in every log you generate for a given request. If you do, you can search for this ID in the log explorer to view the corresponding request's chronological log history.”

## Where it would live

- Edge: no tenant entrypoint or App middleware mints a request ID today (`deploy/gitops/base/values/traefik.values.yaml` entrypoints; the per-App chain at `lego/operator/internal/controller/app_controller.go:3634–3700`). Traefik v3 has no built-in request-ID middleware. The `clientipheaders` local plugin that w8/m123 is adding (`deploy/gitops/charts/traefik-plugins/clientipheaders/`) is the natural place to also set `Rndr-Id` on the request and response when absent, and overwrite any client-supplied value.
- Access log: keep the header in Traefik's access-log `fields.headers` allowlist so the shipper can parse it.
- Logs read: expose it on request entries as `requestID` (REST label/field, GraphQL, MCP and dashboard), and let `--text <id>` find the app lines that echo it.

## Acceptance

- Live: a request to a fresh free service gets an `Rndr-Id` response header. The app receives the same value in `rndr-id`, and a client-supplied `Rndr-Id` is replaced. `bex logs -r <id> --type request -o json` shows that value as `requestID`, and `bex logs -r <id> --text <value>` returns the request line plus any app line that logged it. Static sites behave the same.
