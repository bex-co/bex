# 058 — Deploy `trigger` answers `create` and `config_change`, values outside Render's enum, and the conformance test only seeds `api`, so it can't catch them

Why: `trigger` is a closed enum in the pinned Render schema. Any strictly generated Render client (OpenAPI SDKs, the Terraform provider) rejects or mis-decodes a deploy whose trigger is `create`, and that is every service's first deploy, plus every settings-driven redeploy (`config_change`). The divergence is not allowlisted or documented, and `TestRenderConformance` cannot see it.

Severity: minor. Attribution: server (`lego/backend/internal/deploys`, `lego/backend/internal/store`).

## Evidence (2026-10-05, `/qa-find-bugs-cli` w8 loop, sweep 19)

Production pin `8f58b933d`, workspace `bex-canary`, human device login. Read-only: the live `GET /v1/services/{id}/deploys` responses for the workspace's pre-existing services, validated with `jsonschema` 4.23 against `deployList` in the pinned `render-public-api-1.json`. The probe used the CLI's own token, read privately, and printed only schema paths, never instance values.

```text
GET /services/{web|cron}/deploys   $[*].deploy.trigger  value "create" not in enum      (every service checked)
```

Earlier in this loop (sweeps 7–8, 2026-10-04): `bex deploys list` showed `"trigger":"config_change"` on the deploy a `services update --build-command` / `--root-directory` opened.

Render's enum (`components.schemas.deploy.properties.trigger`): `api`, `blueprint_sync`, `deploy_hook`, `deployed_by_render`, `manual`, `other`, `new_commit`, `rollback`, `service_resumed`, `service_updated`.

The same validator found every other surveyed family conformant (`/owners`, `/users`, `/postgres`, `/key-value`, `/projects`, `/env-groups`). Service `rootDir`/`serviceDetails` gaps are already allowlisted in `internal/api/conformance_allowlist_test.go` (ADR018 §Resource metadata contract), so they are not part of this note.

## Mechanism

- `lego/backend/internal/store/store.go:222-235` defines the trigger vocabulary, including `TriggerCreate = "create"` and `TriggerConfigChange = "config_change"` (w6/m51). `internal/deploys/rest.go:66` puts it straight into Render's `trigger` field, with the comment "bex extra".
- `internal/api/conformance_test.go:187` (`conformDeploy`) seeds only `store.TriggerAPI`, and `conformance_allowlist_test.go` has no deploy entry. The conformance suite is blind to the other spellings.
- Docs drift: `docs/ADR018-render-parity.md:130` still says config changes "never" open a deploy-history row. w6/m51 made them `config_change` deploys.

## Fix

- Map onto Render's enum on the REST wire: `config_change` → `service_updated` (Render's meaning). For `create`, decide `new_commit` for repo-backed, `api` for image-backed, or `other`, and record the choice. Expose bex's finer value in an extension field (for example `bexTrigger`) if the dashboard or events feed needs it. GraphQL/MCP may keep bex's vocabulary, as documented in ADR018.
- Make `conformDeploy` table-driven over every `store.Trigger*` constant, so a new trigger value fails conformance until it maps or is allowlisted.
- Correct ADR018 row 130.

## Acceptance

- [ ] `GET /v1/services/{id}/deploys` for a freshly created service and after a settings-driven redeploy: every `trigger` is a member of Render's enum. `bex deploys list -o json` shows the mapped values.
- [ ] `TestRenderConformance` fails if any `store.Trigger*` constant serializes outside the enum.
- [ ] Controls: `api`, `deploy_hook`, `rollback` and `new_commit` are unchanged. The dashboard Deploys/Events views still distinguish a settings save from a manual deploy.

## Dedupe

`rg -i 'trigger.{0,30}(enum|create|config_change)' .pm docs` found the w6/m51 introduction of `config_change` and the ADR018 row. Neither discusses Render's enum. No allowlist entry exists.

Estimate: ~40m.

Done 2026-10-05 (loopx):
- **Mapping.** The REST and MCP deploy shape (`toRenderDeploy`) maps `trigger` onto Render's closed enum via `renderTrigger`: `config_change` → `service_updated`, `create` → `other` (no exact Render value, and `new_commit`/`api` would claim a cause bex can't vouch for), and `api`/`deploy_hook`/`rollback`/`new_commit` unchanged. Unknown values also map to `other`.
- **Extension field.** bex's precise value is kept in the new `bexTrigger` field. GraphQL, which the dashboard reads, keeps bex's vocabulary, so the Deploys/Events views still tell a settings save apart from a manual deploy.
- **Conformance.** `store.AllTriggers` lists every value. `TestRenderConformance` seeds one deploy per entry in list-deploys, and a pass-through mutation of the mapping fails it with the enum error. `TestAllTriggersListsEveryTriggerConst` parses `store.go`, so a new `Trigger*` constant must join the list.
- **Docs.** ADR018's "never a deploy-history row" paragraph is marked superseded with the mapping.
- **Checks.** Backend suite and `make lint` are green. Not live-replayed.
