## Reproduction

The [port-worker document](../evidence/096/port-worker.yaml) declares `qa173-4b9e73-source` as `type:web`, then references it with:

```yaml
key: QA_TARGET
fromService:
  name: qa173-4b9e73-source
  type: worker
  property: port
```

```sh
bex blueprints validate port-worker.yaml --confirm -o json
```

**Actual:** Bex exit0 in 0.556s; unmodified same-pin Render against Bex exit0 in 0.521s. Both print `valid:true` with the two-service plan and no stderr. The actual unchanged parser retains `reference_type:worker`, records the target as `web_service` and resolves `QA_TARGET` to `3000`.

The [copy-worker document](../evidence/096/copy-worker.yaml) uses `envVarKey:QA_SOURCE` instead of `property:port`; the same mismatch is accepted and resolves to `source-173`. Repeat each with reference types `cron` or `pserv`: the declared target remains web, and all mismatches pass. The reverse [worker-target copy](../evidence/096/copy-worker-target-misdeclared-web-plan-control.yaml) also passes while retaining reference type web and actual target background_worker.

**Expected:** a provided reference type must describe the target's declared service kind. Return the existing HTTP 200 validation envelope with `valid:false`, an error locating `fromService.type`, expected/actual kinds, and native exit1. This expected mismatch rule is an **inference** from the required field and its documented meaning, supported by the [reviewed schema](../evidence/096/reviewed-schema.json) and [official Blueprint reference documentation](https://render.com/docs/blueprint-spec#referencing-service-properties). Render-production rejection of this exact input has not been measured.

## Root cause and shared callers

[Source](../evidence/096/source.txt) and [caller census](../evidence/096/callers.json):

- `lego/backend/internal/apps/deploy.go:1853–1920` registers target names, known values and ports but retains no declared service-kind index.
- `stackIndex.classifyRefs:2031–2077` uses `FromService.Type` only to select the Key Value branch. For every other accepted type, name lookup and actual target addressability decide the result, without comparing the supplied type with the declared target.
- `resolveRef:2715–2743` resolves `envVarKey` from known values and `port` from the port map, ignoring the submitted non-Key Value type. The decoder demonstrably retains it, so normalization is not the cause.
- `classifyRefs` and `resolveRef` each have one production caller. `parseCompiledStack` has four: validation (`blueprint.go:661`), plan (`blueprint.go:1607`), apply preparation (`deploy.go:1687`) and generated-manifest self-check (`blueprint_generate.go:240`). A shared parser guard covers these producers; the CLI consumer needs no change.
- Host/hostport classification goes through the same name index but stores deferred `hostRef` values without type. Outside-file host validation (`blueprint_ownership.go:653 unknownServiceReferences`) currently checks existence. These are source-inspected neighbors, not live-proven mismatches in this finding.

## Proposed fix

Carry the canonical declared Render service kind alongside the existing name/value/port indexes, and compare it with a non-Key Value reference's provided type before classifying any same-file reference. Reuse the compiler's accepted aliases; a static site's Render declaration is `type:web` even though its internal App subtype is static_site. Do not turn this into a new enum or broaden supported reference properties.

Report the mismatch at the reference field through existing located Blueprint errors. Keep actual target addressability, Key Value/database routing, sibling order and correctly typed worker/cron value copies unchanged. Census outside-file host type handling and retain a clear limitation if it remains separate work; do not advertise that untested route as fixed.

REST, GraphQL and MCP validation/plan/apply consume the shared parser; the dashboard should display its located error. Verify existing transport mappings and compare the typed-reference semantics with Render documentation and any feasible authoritative behavior before landing the guard. No CLI fork or request rewrite.
