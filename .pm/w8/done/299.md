# A Blueprint's `fromDatabase` variables are missing from the service's env vars, and a write to one answers 200, lists the new value and is ignored by the process

Why: when a Blueprint gives a service a variable from a database (`fromDatabase`) or a Key Value (`fromService` with `type: keyvalue` and a `property`), bex stores it on the App as a Secret reference. Every env-var read skips references:

- REST `GET /v1/services/{id}/env-vars`;
- the GraphQL `envVarKeys` the Environment tab uses;
- MCP.

So the service's `DATABASE_URL`, `POSTGRES_PASSWORD` and the like are invisible, though the process has them.

The write guard w4/m120 added for Blueprint literals skips references too. A `PUT` of such a key therefore answers 200, the list shows the new value, and every deploy still runs the reference: the shadowing that guard's own comment warns about ("the API reports 200, the Environment tab shows the new value, and the process keeps the old one, forever").

Render stores these as ordinary service variables. Its Blueprint spec says (§ Setting environment variables > Referencing service properties, read verbatim 2026-11-13): "These environment variables update to match the current value of the referenced property on each Blueprint sync. They do _not_ update immediately whenever that property changes." A stored value is a variable that "belong[s] directly to the service", which Render's list endpoint returns (`GET /services/{serviceId}/env-vars`: "This endpoint only returns environment variables that belong directly to the service"). A write changes it until the next sync.

**Severity:** major.

- **Silently ignored write:** a user or API client who sets the database URL is told it worked, sees the new value, and the app keeps the old one.
- **Invisible values:** the Environment tab and `GET /env-vars` hide connection settings the process uses, in 67 of the 171 `render-examples` templates that declare services (fetched 2026-11-13).

**Attribution:** server (bex-api env-var reads and write guard). **Estimate:** ~2h. **Source:** `/qa-find-bugs-cli` w8 loop sweep `3b03`, 2026-11-13 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `08c3c3fc3f0e`.

## Root cause

- **How references are stored:** `lego/backend/internal/apps/deploy.go:3485-3512` (`resolveDatabaseRef`) and `:3515-3540` (`resolveKeyValueRef`) turn `fromDatabase` and Key Value `fromService` entries into `spec.Env` items with `ValueFrom.SecretKeyRef`. That is deliberate ("Credentials remain indirect so rotation never writes plaintext into an App"), and since w5/m265 a sync re-points them, as Render documents.
- **Reads skip them:** `lego/backend/internal/secrets/service.go:258-271` (`manifestEnv`) returns only `spec.Env` items without `ValueFrom`: "ValueFrom entries are skipped … and have no representation in an env-var view". `mergeManifestEnv` (`:283`), and through it every read (`ListEnvVars`, `ListEnvVarsPage`, `GetEnvVar`, `EnvVarKeys`, `EnvVarValue`; w4/m120 t001), never sees a reference.
- **The write guard skips them:** `secrets/service.go:509-537` (`refuseManifestKeys`) takes its owned keys from the same `manifestEnv`, so `SetEnvVars`, `SetEnvVar` and `DeleteEnvVar` (`:552`, `:639`, `:682`) do not refuse a referenced key. The write lands in the store and is projected through `envFrom`, which the manifest's `env` entry beats, as the guard's comment explains.

## Fix

Treat a referenced key like a Blueprint literal: listed, flagged, and owned by the Blueprint.

- **Reads:** list every `spec.Env` reference on all env-var reads, flagged `managedBy: blueprint` as m120's literals are.
  - Its value is the referenced property's current value, read from the Secret it names. The datastore credential Secrets bex-api already reads for connection info qualify; the read needs the same authorization as reading the service's other variables.
  - Never expose the Secret's name or key.
- **Writes:** make `refuseManifestKeys` own referenced keys too, so `SetEnvVar` / `SetEnvVars` / `DeleteEnvVar` answer `ENV_VAR_MANIFEST_MANAGED` with the same advice.
  - Render lets the write stand until the next sync, so the stricter refusal goes through the same ADR018 record as m120's.
  - If that record says Render's semantics should win instead, the write must reach the process; a 200 that changes nothing is the one outcome to remove.
- **Dashboard:** the Environment tab shows the referenced variables read-only, as it does manifest literals.

## Blast radius

- **Reference kinds:** every Blueprint service with `fromDatabase` (any property) or `fromService` to a Key Value with a property, on every Blueprint path (create, sync, auto-sync, `blueprints/deploy`).
- **Surfaces:** REST env-var reads and writes, GraphQL `envVars`/`envVarKeys`/`envVar`, MCP env tools, and the dashboard Environment tab.
- **Unchanged:** literals (m120), seeded `sync: false`/`generateValue` values (store-owned) and `fromService` `envVarKey` copies.

## Resolution 2026-11-13 (`/loopx w8`)

**Done.** Shipped by the backend commit that carries this record. A Blueprint's references are listed and owned like its literals, as w4/m120 records for Render's Blueprint-managed variables ("likewise read-only in its dashboard", ADR018).

- **Reads** (`lego/backend/internal/secrets/service.go`):
  - `manifestEnv` now reports each `spec.Env` `SecretKeyRef` alongside the literals.
  - `resolveManifestRefs` reads the value from the Secret the reference names, in the App's own namespace, once per Secret per read. That is the value a container started now gets.
  - A missing Secret or key reads `""`, since the process cannot start with it either. Any other Secret read error answers the store's "could not be read" error.
  - REST list/get, GraphQL `envVars`/`envVar` and MCP show the value, flagged `managedBy: blueprint`. The manifest still wins a collision with a store value that landed before this fix (the 3b03 bogus `PGRST_DB_URI`).
- **Keys-only reads read no Secret:** `envVarKeys`, a GraphQL `envVars` page that selects no `value` (the Environment tab's query), and `ListEnvVarNames`, the Blueprint generator's seam, which promises that no value is read.
- **Writes:** `refuseManifestKeys` takes its keys from the same `manifestEnv`, so `SetEnvVar`, `SetEnvVars`, `DeleteEnvVar` and `PatchEnvironment` (a rename away from such a key included) answer 409 `ENV_VAR_MANIFEST_MANAGED`.
- **Dashboard:** no change. The Environment tab already renders `managedBy` rows read-only (`service-environment-editor.tsx:324`).
- **Docs:** ADR013 § Two writers, one read, and the ADR018 env-vars row.

**Tests:**

- **New:** `TestManifestReferencesAreListedWithTheirSecretsValues` and `TestKeysOnlyReadsDoNotReadReferencedSecrets` (`manifest_refs_test.go`).
  - The first covers the two references into one Secret, the literal, a missing Secret, and the pre-fix store collision.
  - The second fails every Secret read, then checks that the keys-only paths still answer and the value list fails with `ErrSecretsStoreFailed`.
- **Extended:** `TestManifestKeyWritesAreRefused` now runs every write verb for a literal and a reference.
- **Mutation check:** with references dropped from `manifestEnv`, all three tests fail.

**Production check owed after the next roll:** repeat the 3b03 steps on `render-examples/postgrest`.

- `GET …/env-vars` lists `PGRST_DB_URI` and `PGRST_DB_ANON_ROLE`, flagged `managedBy: blueprint`.
- `PUT …/env-vars/PGRST_DB_URI` answers 409 `ENV_VAR_MANIFEST_MANAGED`.
- A deploy still connects.
