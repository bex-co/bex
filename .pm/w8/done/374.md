# `bex logs --start 30d` with no `--end` is refused as "query range exceeds 720 hours", so a 30-day read fails on every plan

Why: 30 days is Render's longest log retention and a preset in Render's own log explorer, and Render's List logs contract documents no range limit at all. In bex, the natural "everything you keep" read, `bex logs -r <id> --start 30d`, fails with a 400 on every plan: the CLI computes `now - 720h`, and by the time bex-api checks the window its own clock has moved on by the request's latency.

- Severity: minor. `--start 719h` works, and so does an explicit `--end`. But the documented relative form for a full retention window always fails, and so does any start past the cap, even though ADR010 says a start before the retention floor is clamped, not refused.
- Versions: bex CLI v0.9.0 release binary; Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md` (v2.36.0, `4fd34231b637`); production pin `cce6c749f6ff`. The code is unchanged on main `0778f210dd`.
- Context: 2026-11-21 11:57–12:03 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`, Scale plan, so its own floor is 30 days), non-TTY. Routine `cli-qa`, run r24, nonce `656830`. Fixture: free image web service `srv-dc0ocld2n01c73bc1ab0` (`nginx:1.27-alpine`), created and deleted by this run (404 confirmed).

## Render

- [api-docs.render.com/reference/list-logs](https://api-docs.render.com/reference/list-logs), read 2026-11-21. `startTime`: "Epoch/Unix timestamp of start of time range to return. Defaults to `now() - 1 hour`." `endTime`: "Epoch/Unix timestamp of end of time range to return. Defaults to `now()`." It documents no maximum range, no retention error and no too-long-range error. Its only 400 codes are `multiple_regions` and `too_many_resources`.
- The pinned client's `--start` takes relative forms (`pkg/command/time.go` `parseRelativeTime`: `^(\d+)([smhd])$`, computed as `now - N` on the client) and sends no `endTime` unless `--end` is given.
- ADR010 § retention: "A start before the floor is clamped, not refused … a `startTime` 20 days back on Hobby reads the last seven days." The same sentence then carves out "a start more than `BEX_MAX_QUERY_HOURS`, 720 hours by default, back is still a 400", which is what makes `30d` fail. ADR018 lists the 720 h window only as a deployment companion cap in the rate-limits row. It records no signed-off logs divergence.

## Repro (bex, production)

```sh
bex logs -r <srv-id> --start 30d   --limit 2 -o json   # exit 1: Error: error listing logs: received response code 400: bad request: query range exceeds 720 hours
bex logs -r <srv-id> --start 720h  --limit 2 -o json   # exit 1, same 400
bex logs -r <srv-id> --start 719h  --limit 2 -o json   # exit 0, 2 lines
bex logs -r <srv-id> --start 29d   --limit 2 -o json   # exit 0, 2 lines
bex logs -r <srv-id> --start "$(date -u -d '-720 hours +5 seconds' +%FT%TZ)" --limit 2 -o json   # exit 0, 2 lines
bex logs -r <srv-id> --start 400d  --limit 3 -o json   # exit 1, same 400
bex logs -r <srv-id> --start 2025-01-01T00:00:00Z --limit 3 -o json --direction forward   # exit 1, same 400 (1.64 s)
bex logs -r <srv-id> --start 2025-01-01T00:00:00Z --end 2025-01-02T00:00:00Z --limit 3 -o json   # exit 0, empty (a window wholly before the floor)
```

The fixture was minutes old, so its App floor (`core.AppNotBefore`, w8/m124) would have clamped every one of these reads to a few minutes of lines.

## Mechanism

- `lego/backend/internal/logs/rest.go:77-92` `renderWindow`: it runs before any floor is applied. With no `endTime` it measures the window as `now - q.Since` through `core.CheckInclusiveQueryWindow(s.MaxQueryHours, …)`, `lego/backend/internal/core/pagination.go:240-258` (`checkWindowCap`: `end.Sub(start) > maxHours*time.Hour` → 400 `query range exceeds %d hours`).
- The client's `now - 720h` arrives at the server's later `now`, so the span is 720 h plus the latency, and the read is refused.
- The retention floor (`floorAt`, `service.go:634`, `core.LogFloor`) and the App floor (`service.go:748`) only reach `lokiRange` (`loki.go:389-402`, `start = later(start, later(q.notBefore, q.retentionFloor))`) after this check has already refused the read.
- `TestLogQueryCapMeasuresTheWindowUpToNow` (`future_window_test.go:136-153`) asserts that a 31-day start is refused. That rule came from w8/123's fix ("A start older than the cap is still refused") and was restated by w9/m389 t006. Neither recorded a Render basis for it.

## Fix

- In `renderWindow`, clamp instead of refusing. When `q.Since` lies more than `MaxQueryHours` before the window's effective end (`earlier(q.End, now)`), set `q.Since` to that end minus `MaxQueryHours` and read on.
- This keeps the Loki query bounded at 720 h, exactly as the cap does today. Loki keeps 720 h (ADR010), and every plan's floor is at most 30 days, so no line is lost.
- An inverted window stays a 400 (`startTime must be before or equal to endTime`). A window that has not begun stays an empty page. A window wholly before the floor stays an empty last page with `hasMore: false`.
- Page cursors (`nextStartTime`/`nextEndTime`) must name the clamped window.
- Update ADR010's retention sentence and the ADR018 logs row: a start of any age is clamped to what is kept, as Render documents no range error. Replace the 31-day case of `TestLogQueryCapMeasuresTheWindowUpToNow` with clamp assertions.

## Blast radius

`renderWindow` serves every log read: REST `GET /v1/logs` and `GET /v1/logs/values`, GraphQL `logs`/`logLabelValues` (`graphql.go`) and MCP `list_logs`/`list_log_label_values` (`mcp.go`), for services, Postgres and Key Value alike. `logsSubscribe` never window-checks (w6/m111). Leave metrics (`metrics/service.go:430`) and events alone: they share `BEX_MAX_QUERY_HOURS`, but ADR018's events row records "Explicit wider ranges still fail" as deliberate. If either one turns out to differ from Render, file it as its own item. The dashboard's `30d` preset sends an explicit `endTime` (`dashboard/src/features/metrics/lib/range.ts:225` `resolveRange`), so it lands exactly on 720 h and passes today. It must keep passing.

## Acceptance

- `bex logs -r <id> --start 30d --limit 2 -o json`, and the same with `720h`, `400d` and `2025-01-01T00:00:00Z`, exit 0 with the newest lines the plan keeps, on a fixture older than a few minutes and on a fresh one. The same holds through REST, GraphQL `logs` and MCP `list_logs`.
- On a Hobby workspace, `--start 30d` reads the last seven days. With `--direction forward`, the first line is at or after the floor.
- `--start 2026-11-21T11:55:00Z --end 2026-11-21T11:50:00Z` stays a 400. `--start 2027-01-01T00:00:00Z` stays an empty page with exit 0. `--start 719h` and a dashboard `30d` read are unchanged.
- Unit tests in `lego/backend/internal/logs` cover a past-cap start with no end, a past-cap start with an explicit end, and the cursor of the clamped window.
