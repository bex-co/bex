# For about 10 s after a service delete, its deploy hook, logs and metrics still answer 200 while every other read of it is already 404

Why: w3/m81's contract says that once a service's deletion is accepted every by-id read answers 404. Three read families skip `core.NotFoundIfDeleting`, so for the teardown window they keep serving the deleted service's data, and the deploy-hook read even hands out a hook URL for it.

- Severity: minor. Same caller and workspace only, and the window is short (about 8–12 s), but a script that deletes and then reads gets two different answers to "does this service exist?".
- Versions: `bex v0.8.0` (Render CLI v2.36.0), `main` `06a28e115`; production pin not read.
- Context: 2026-11-21 05:13–05:15 UTC, `https://api.bex.co`, workspace `bex-canary`, human device-login token, `/qa-find-bugs-cli w8` routine sweep r19-00bb.

## Repro

Free static site `srv-dc0idft26tvc739p16a0` (deleted). A poller ran every 4 s, statuses only, while `bex services delete <srv> --confirm` ran at 05:14:21:

```text
05:14:21 svc=200 /deploys=200 /env-vars=200 /events=200 /deploy-hook=200 logs=200 metrics/bandwidth=200
05:14:25 svc=404 /deploys=404 /env-vars=404 /events=404 /deploy-hook=200 logs=200 metrics/bandwidth=200
05:14:29 svc=404 /deploys=404 /env-vars=404 /events=404 /deploy-hook=200 logs=200 metrics/bandwidth=200
05:14:33 svc=404 /deploys=404 /env-vars=404 /events=404 /deploy-hook=404 logs=404 metrics/bandwidth=404
```

The paths were `GET /v1/services/<srv>`, `…/deploys`, `…/env-vars`, `…/events`, `…/deploy-hook`, `GET /v1/logs?ownerId=<tea>&resource=<srv>&startTime=…&endTime=…` and `GET /v1/metrics/bandwidth?resource=<srv>&…`.

On a free web service, `srv-dc0ib8d26tvc739p1680` (deleted), a sweep a few seconds after `services delete` saw the same split:

- `…/deploy-hook` answered 200 `{"url":"https://api.bex.co/v1/deploy-hooks?key=<redacted>"}`.
- `GET /v1/logs` answered 200 `{"hasMore":true,"logs":[…request log lines…]}`.
- `GET /v1/logs/values?label=instance` answered 200 with three instance ids.
- `GET /v1/metrics/cpu` answered 200 with samples.
- `bex logs -r <srv> --limit 5 -o json` exited 0 and printed the lines.
- At the same moment, the service, deploys, deploy-by-id, events, env vars, secret files, instances, custom domains, headers, routes and jobs reads, `POST …/restart`, and `bex deploys list`, `services instances`, `restart` and `deploys create` all answered 404 or exited 1 with 404.

40 s later, every read of both services answered 404.

## Root cause

All of these reads authorize through `core.Base.AuthorizeApp`, which returns the App CR while its finalizer holds it, and none of them calls `core.NotFoundIfDeleting` (`core/base.go:1813`) afterwards. The service, deploys and env-var reads do call it.

- `lego/backend/internal/deploys/deployhook.go:131`: `GetDeployHook`. It also writes a token for a service that never had a hook, through `writeDeployHookToken`. `RegenerateDeployHook` (`:163`) has the same gap.
- `lego/backend/internal/logs/service.go:715`: the per-resource authorization behind `GET /v1/logs` and `/v1/logs/values`.
- Metrics: `lego/backend/internal/metrics/service.go:496` and `:1377`, `metrics/datastore.go:368` (the service branch; the Postgres and Key Value branches at `:325` and `:342` already check), and `metrics/retention.go:111`.

## Fix

- Call `core.NotFoundIfDeleting(a)` right after `AuthorizeApp` in each read above, matching `apps.Get` and `deploys.List`.
- Alternatively, add an `AuthorizeLiveApp` helper that does both, and switch the by-id read verbs to it.
- Keep it off the delete path itself and off the log-tail termination logic (w1/m146: deleting a service ends the tail).
- Audit the other `AuthorizeApp(` callers (81 non-test call sites) for by-id reads of the same kind, and list any deliberate exemption in the note's closing line.

## Acceptance

- A backend test holds an App with a finalizer and a `DeletionTimestamp`. `GetDeployHook`, `RegenerateDeployHook`, a logs query, a log-values query and a metrics query for it each return `core.ErrNotFound`, and no deploy-hook token row is written. The same calls on a live App are unchanged.
- Live in `bex-canary`, after the fix is deployed: the poller above on a fresh free static site shows deploy-hook, logs and metrics turning 404 in the same round as the service read. Delete the fixture by ID and confirm a 404.

Dedupe: w3/m81 (the contract, services/routes/headers/deploys), w8/m35 (Postgres and Key Value), w8/023 (deploy trigger 500) and w4/473 (build sources) each fixed other families. No item names deploy hooks, logs or metrics in the deleting window. Estimate: about 45 minutes.

## Worked 2026-11-21 (`/loopx w8`)

Verdict: work. The premise held on `main` `ef26ddb39`: `GetDeployHook`, `RegenerateDeployHook`, the logs owner check and the metrics reads called `AuthorizeApp` with no deletion check, and the datastore branches of logs, metrics retention, the project views and Blueprint generation had none either.

Fixed in `21dc909fa` at the seam rather than per verb: `core.Base.AuthorizeApp` answers `ErrNotFound` for a deleting App once the caller is authorized, so every service verb (reads, writes, no-op writes, a repeated `DELETE`) agrees the moment the delete returns, and `AuthorizeLiveApp` is gone. Postgres and Key Value tenant verbs take `fetchLiveDatabase` / `fetchLiveKeyValue`, the writable console and a repeated delete included; logs, metrics and Blueprint generation refuse a deleting datastore; an env group cannot be created around a deleting service. Env groups and webhook endpoints delete their row, so they have no window. Deliberate exemptions: the project and environment placement fan-outs (`SetProjectID`, `ClearProjectID`, `SetEnvironment*`, `ClearEnvironmentID`) still reach a departing datastore to clear its labels; an open log tail still ends at its watchdog when the CR is gone (w1/m146); `events.Get` by event id still serves an event of a deleted service, best effort.

Regression tests (each fails on `ef26ddb39`): `core` `TestAuthorizeAppHidesADeletingService` and `TestAuthorizeAppRefusesBeforeHidingADeletingService`, `deploys` `TestDeletingServiceHasNoDeployHook` (no token written), `logs` `TestDeletingResourcesHaveNoLogs`, `metrics` `TestDeletingResourcesHaveNoMetrics`, `apps` `TestDeletingServiceIsAbsentToEveryWrite`, `postgres` / `keyvalue` `…IsAbsentToEveryWrite`, `envgroups` `TestADeletingServiceCannotJoinAGroup`.

Next: once production's pin carries `21dc909fa`, run the note's 4-second poller in `bex-canary` on a fresh free static site (service, deploys, env-vars, events, deploy-hook, logs, metrics/bandwidth) across `bex services delete <srv> --confirm`, check every path turns 404 in the same round, then delete the fixture by id, confirm a 404, and close.
