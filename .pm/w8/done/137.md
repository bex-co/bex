# Static-site single-rule REST operations are missing: `POST`/`DELETE …/headers`, `POST`/`PATCH`/`DELETE …/routes` answer 405/404

Why: Render's pinned OpenAPI defines per-rule operations for static-site edge rules (`add-headers`, `delete-header`, `add-route`, `patch-route`, `delete-route`), but bex serves only the bulk `GET`/`PUT` pair — a REST client following Render's API reference cannot add or remove one header/route rule without rewriting the whole set, and gets a bare 405/404 with no hint that the `PUT` replace-all spelling exists.

Seen in the `/qa-find-bugs-cli` loop sweep 801, 2026-10-20, production, `bex-canary` (disposable static site `qa801-static`, since deleted and verified 404):

- `POST /v1/services/{id}/headers {"path","name","value"}` → `405 {"error":"method not allowed",…}`. Render: `add-headers` (201).
- `POST /v1/services/{id}/routes {"type":"redirect","source","destination"}` → 405. Render: `add-route` (201).
- `DELETE /v1/services/{id}/headers/{headerId}` → bare `404 {"error":"not found"}` (no route pattern at all, so not even the coded `NOT_FOUND` envelope). Render: `delete-header` (204).
- `PATCH /v1/services/{id}/routes/{routeId} {"priority":0}` → bare 404. Render: `patch-route` (priority update).
- `DELETE /v1/services/{id}/routes/{routeId}` → bare 404. Render: `delete-route` (204).
- Working control, same fixture: `PUT …/headers` and `PUT …/routes` (replace-all) → 200 with minted `hdr-…`/`rte-…` ids and `priority`; `GET` list returns the `{header|route, cursor}` envelopes; `PUT []` clears.

Root cause: only two handlers per resource are registered — `lego/backend/internal/apps/rest.go:1279-1282` wires `GET`/`PUT` for `routes` and `headers` and nothing else. [ADR029](../../../../docs/ADR029-static-sites.md) documents the edge-rule surface as "`GET`/`PUT /v1/services/{id}/routes` and `.../headers` (bulk replace, Render-compatible)" — the bulk pair is genuinely Render-shaped, but the five single-rule operations in the pinned OpenAPI were never registered, and no ADR018 row or gap-backlog entry records their absence (the Static site row claims REST ✅). The pinned CLI exposes no header/route commands, so only direct REST clients hit this — which is why the CLI loop missed it until a REST-first sweep.

Fix (~1h): register the five operations on the same verbs the bulk `PUT` already funnels into (`SetRoutes`/`SetHeaders` in `lego/backend/internal/apps/service.go`): `POST` appends one validated rule and returns Render's 201 shape; `DELETE` removes by rule id (named 404 for an unknown id, not the bare mux 404); `PATCH …/routes/{id}` reorders priority with the same shift semantics Render documents. Mind the response-shape asymmetry Render itself carries (POST headers answers `{"headers": {…}}`, POST routes answers the bare route) — mirror the pinned schema, and check GraphQL/MCP stay bulk-only deliberately (Render's own MCP ships these as stubs; bex's `update_static_routes`/`update_static_headers` already cover the capability) so the three surfaces stay consistent by capability even where wire verbs differ. Add REST tests beside the existing routes/headers tests covering add → list → delete and a priority patch.

Acceptance:

- Live after deploy: `POST …/headers` → 201 and the rule lists; `DELETE …/headers/{id}` → 204 and the rule is gone; unknown rule id → coded 404 naming the rule.
- `POST …/routes` → 201; `PATCH …/routes/{id}` changes priority read-back order; `DELETE …/routes/{id}` → 204.
- Bulk `GET`/`PUT` behavior byte-unchanged; GraphQL/MCP unchanged.
- ADR029's edge-rule bullet updated to name the single-rule operations.

Severity: minor — capability exists via bulk replace on every surface; only Render-shaped per-rule REST calls fail. Estimate: ~1h.
