# 021 — Every 404 says "app not found", even for a missing deploy, project or job

Why: `core.ErrNotFound`'s text is the literal `"app not found"`, and REST writes `err.Error()` as the message. So a missing *deploy* on a real service reads as if the service were missing, and wrapped errors read `app not found: project: not found`. Users look for the wrong thing.

Live, 2026-09-23, production, `bex v0.2.1`, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 7.

```text
$ bex deploys cancel srv-daif6dsmg29s73d1umvg dep-doesnotexist0000000 --confirm   # the service exists
Error: failed to cancel deploy: received response code 404: app not found
$ bex jobs list srv-doesnotexist00000000
Error: received response code 404: app not found
$ bex environments prj-doesnotexist0000000
Error: received response code 404: app not found: project: not found
```

Controls that name their resource correctly: sandboxes (`404 (SANDBOX_NOT_FOUND): sandbox not found`), and Key Value/Postgres by-id lookups, which the pinned client resolves itself (`No Key Value with ID '…'`).

## Mechanism

- `lego/backend/internal/core/errors.go:39`: `ErrNotFound = errors.New("app not found")`. It dates from when Apps were the only resource and is now returned by 31+ non-test call sites across deploys, jobs, projects, environments and more.
- `core/http.go:302-305` `WriteErr` uses `err.Error()` as both `error` and `message`. `store/projects.go:66,77,215` wrap it as `project: %w`, which gives the doubled text.

## Fix

1. Change the sentinel text to the neutral `"not found"`. The `id: "not_found"` and the status code are unchanged.
2. Where the resource is known, wrap it so the message names it (`deploy not found`, `project not found`, `job not found`). Put the wrap at the verb boundary and avoid double-prefixing, as the sandbox package already does.

**Blast radius:** the dashboard's not-found detection is `/\bnot[ -]?found\b/i` (`dashboard/src/common/lib/document-head/index.ts:137`), so it still matches. Update the string-pinned tests: `core/http_helpers_test.go:137`, `dashboard/src/features/metrics/hooks/__tests__/use-metrics.test.ts:231`, and the comments in `gqlutil.go:182` and `use-not-found-redirect.ts:12`. GraphQL and MCP carry the same text, so check that all three surfaces agree afterwards.

## Acceptance

- [ ] A missing service still 404s with `id: not_found`, and dashboard dead-id redirects still work (existing tests).

## Outcome (2026-09-25)

- `core.ErrNotFound`'s text is now the neutral `"not found"` (`id: "not_found"` and the 404 unchanged). New `core.NotFound(resource)` names the resource (`"deploy not found"`) while staying `errors.Is(err, core.ErrNotFound)`, so REST, GraphQL and MCP carry the same text and status mapping is untouched.
- `store.MapError` turns the store's `"<entity>: not found"` into `core.NotFound(entity)` — one change covering every store-backed miss (`project not found`, `deploy not found`, …) and removing the doubled `app not found: project: not found`; irregular shapes fall back to the neutral sentinel.
- `deploys` returns `core.NotFound("deploy")` for all five missing-deploy paths (Get, Cancel, Rollback).
- A missing **service** now reads `not found` (the generic App resolvers in `core/base.go` stay neutral), which the acceptance allows.
- Updated: `core/http_helpers_test.go` pin, `gqlutil.go` comment, dashboard `use-not-found-redirect.ts` comment and three test fixtures (the dashboard matcher `/\bnot[ -]?found\b/i` is unchanged and still matches).

Tests: `store/maperror_test.go` (fails on the old code: `app not found: project: not found`), and the deploys unknown-deploy test now asserts `deploy not found`. Full backend suite and the affected dashboard tests pass. Not verified live against production (needs this commit deployed).
