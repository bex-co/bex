Why: a service switched from a prebuilt image to Git still reports an image runtime, so the supported CLI clone command cannot inherit its configuration without an extra runtime override.

**Status:** done. **Worker:** worker8. **Severity:** major. **Attribution:** backend runtime projection after a source change. **Estimate:** 55m for the projection correction, transition checks and shared caller review.

## Producer, consumer and correction

- `apps/service.go:4213–4265` resolves the repo change and clears the image. `sourceFields.applyTo` at :4203–4208 changes only repo, image, branch and registry credential; the image-born service keeps `spec.runtime="image"` / `builder="auto"`.
- `effectiveRuntime` at `apps/service.go:990–1006` returns any explicit runtime before examining source. Thus the retained image runtime wins even with a Git repo and no image. `view` :1098 uses it; `renderServiceDetails` at `apps/render.go:435–438` emits it as both `runtime` and `env`.
- Exact-pin `pkg/service/clone.go:94–125` extracts source defaults. `applySourceDefaults` :230–244 inherits the Git repo; `applyRuntimeDefaults` :246–252 deliberately does not inherit an image runtime when there is no image. `pkg/service/create.go:54–56` then refuses the missing runtime. The client correctly handles valid source metadata; changing its guard would mask the backend mismatch.
- Make the shared runtime projection source-aware for this transition: when repo is present, image absent, explicit runtime is the retained `image` value and builder is empty/auto/dockerfile, derive `docker` as the existing default Git builder does. Keep genuine image-only reads as `image`, explicit native Git runtimes unchanged, and the existing static/buildpack exceptions. Avoid resetting native build/start configuration or creating a release as a side effect of a read/source save.

The exact local producer path `resolveSourcePatch → applySourceChange → view → toRenderService` reproduces the wrong image runtime for **four** image-born kinds: web, private, worker and cron. Controls preserve derived Docker, explicit Go and genuine image runtimes. ## Outcome (2026-10-12) — fix shipped, blocked on hosted acceptance

- **Fix:** `staleImageRuntime` (`lego/backend/internal/apps/build_strategy.go`) names a runtime `image` left behind once a Git repo replaced the image. The shared source fold (`sourceFields.applyTo`, so the save and its preflight probe) clears it, and `effectiveRuntime`, `buildStrategy` and the Dockerfile-path check ignore it on records saved earlier. A Git source on the default/auto builder therefore reads `docker` on AppView (REST/GraphQL/MCP), Render `serviceDetails.runtime`/`env` and Blueprint export. Genuine image services, branch-only saves and explicit native runtimes keep theirs. The save stays untracked (no deploy row or release); the operator already built such records with the default builder.
- **Tests:** `TestImageToGitSourceSaveReadsDockerRuntime` (`source_runtime_test.go`) creates image-born web/private/worker/cron services through the real create path, saves a Git repo through `ApplyServicePatch`, and asserts the view and Render details read `docker` and the spec strategy is the Dockerfile build. - **Blocked:** the native journey (both clients: image source → Git save → same-type clone without `--runtime` exits 0, reaches Live and serves) and cleanup need the fix deployed to production.
