# Per-service notification-override `GET`/`PATCH` omit the schema-required `serviceId`

Why: Render's pinned schema requires `serviceId` on the single-override object (`retrieve-service-notification-overrides` / `patch-service-notification-overrides`, `required: [serviceId, previewNotificationsEnabled, notificationsToSend]`), but bex's single-object response carries only the two settings fields — a strict Render-shaped client validating the response, or correlating a PATCH result with its service without re-reading the URL, gets an object that fails its own contract. The workspace list on the same surface includes `serviceId` per row, so the two bex answers disagree with each other too.

Seen in the `/qa-find-bugs-cli` loop sweep 806, 2026-10-20, production, `bex-canary` (disposable free web service, since deleted and verified 404; override reset to `default` before deletion):

- `GET /v1/notification-settings/overrides/services/{id}` → `200 {"notificationsToSend":"default","previewNotificationsEnabled":"default"}` — no `serviceId`.
- `PATCH … {"notificationsToSend":"failure"}` → 200 with the same two-field shape (value applied correctly; reset to `default` also 200).
- `GET /v1/notification-settings/overrides?ownerId=…` → rows are `{"override":{"type":"service","serviceId":"srv-…",…},"cursor":…}` — `serviceId` present there.
- Bogus enum control: `PATCH {"notificationsToSend":"bogus806"}` → 400 `invalid request body at /notificationsToSend`.

Root cause: `notificationOverrideResponse` (`lego/backend/internal/apps/rest.go:1448`) has only the two settings fields, and both the single `GET` (rest.go:1530) and `PATCH` (rest.go:1537) return `toNotificationOverride(app)`, which never sets an id. The list path builds the separate `notificationOverrideItem` (rest.go:1471) that does carry `ServiceID` — the single-object struct was simply never given the field when the pair was registered (`registerNotificationOverrideRoutes`, w3/m15; the list followed in w2/m100). ADR018's Notifications row claims the exact Render `GET`/`PATCH` paths with no recorded divergence on response shape.

Fix (~20m): add `ServiceID string \`json:"serviceId"\`` to `notificationOverrideResponse` and set it from `app.ID` in `toNotificationOverride`. That one change covers both single-object verbs; the list item already matches. Add/extend a REST test asserting the three required fields on GET and PATCH responses beside the existing override tests.

Acceptance:

- Live after deploy: `GET` and `PATCH /v1/notification-settings/overrides/services/{id}` return `serviceId` equal to the path id alongside the two settings fields.
- List response byte-unchanged; GraphQL `setNotificationsToSend` and MCP `update_service(notificationsToSend:)` unchanged.

Severity: minor — settings values read/write correctly; only the required identity field is absent. Estimate: ~20m.
