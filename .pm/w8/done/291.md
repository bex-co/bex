# A native static site whose publish directory is missing logs `==> Build successful 🎉`, then `==> Build failed` 47 s later

Why: a static site's publish directory is checked only after the build image has been pushed. So a typo in the Publish Directory (or a build that writes elsewhere) produces a build log that first says the build succeeded and then that it failed. On Render a missing publish directory is the build's own failure, reported as `Publish directory <dir> does not exist!` (the wording users quote in Render community threads, e.g. "Publish directory dadjokes/build does not exist", "Publish directory ng-build does not exist"), and the build does not report success first.

**Severity:** minor (contradictory narration on the deploy page and in `bex logs`; the deploy does close `build_failed` with a correct reason, and the previous release keeps serving). **Attribution:** platform build (native static image vs. the publish Job's extract step). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `abd1`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `ca7fbbe606c8`.

## Root cause

- `lego/operator/internal/build/build.go:270-280`: `nativePushNarration`, the push phase of every native build, prints `==> Uploading build...`, `==> Uploaded in Ns` and then `==> Build successful 🎉` unconditionally once the image is pushed.
- `lego/operator/internal/build/native.go:347-351`: for a static site the generated Dockerfile ends after the build `RUN`; nothing in the build checks `StaticPublishPath`, although `Options.StaticPublishPath` (`build.go:478-481`) is known at that point.
- `lego/operator/internal/publish/publish.go:569-571`: the publish Job's `extract` init container tests `$PUBLISH_PATH` in the built image afterwards and fails with `the publish directory "…" does not exist in the built image` (user-source exit), which w21/049 closes `build_failed`. That Job runs after the push, here 47 s later.
- A Dockerfile-built static site is not affected the same way: its push phase (`dockerfilePush`) prints no verdict.

## Fix

Fail the build itself when the publish directory is missing, before the upload, with Render's sentence, so the build log ends `==> Publish directory <dir> does not exist!` and the row closes `build_failed` with that reason, and never prints `Build successful`.

- **Preferred:** for `o.StaticSite` native builds whose publish path is not the root, end the generated Dockerfile with a check after the build `RUN` (the path passed as a build arg or env, never interpolated into the shell) that prints `==> Publish directory <dir> does not exist!` and exits with the code the build classifier maps to a user build failure. Map that line to the row's `failureReason` the way the build-command failure is (w4/m324). Keep the publish Job's check as the backstop.
- **Alternative (narration only):** for static sites, move `==> Build successful 🎉` out of `nativePushNarration` and emit it once the extract has found the directory. This removes the contradiction but keeps the 47 s gap and bex's sentence.
- `publishesRoot(o.StaticPublishPath)` (`nativestaticdeps.go:132`) already tells the root apart.

## Blast radius

- Every native static site (any runtime, the Node default included) whose Publish Directory is missing after the build: a typo, a build that writes `dist` while the site says `build`, an empty build command.
- Not changed: Dockerfile-built static sites (their check stays in the publish Job), web/private/worker services, and a first publish's existing `build_failed` close (w21/049).

## Regression checks

- A generated-Dockerfile test: a static native build with `StaticPublishPath: "out"` carries the check after the build `RUN`, a root publish path does not, and a service build does not.
- Production: the abd1 steps. The failing deploy's build log ends `==> Publish directory nope does not exist!` with no `Build successful`, the row closes `build_failed` with that reason within the build, and the site keeps serving. A correct publish directory still logs `Build successful 🎉` and goes live.

## Shipped 2026-11-12 (`/loopx w8`); the production check waits for the deploy that carries it

- **Fix (the preferred option):** a native static site's build step (`nativeDockerfile`) now starts with a prefix (`nativePublishCheckStep`, `lego/operator/internal/build/nativestaticdeps.go`). It holds the publish path as one single-quoted word, plus an EXIT trap that runs after the authored command. When the command succeeded and the directory is missing from the image's working directory (`nativeWorkdir`, where the publish Job's extract looks), the trap prints `==> Publish directory <dir> does not exist!` and exits 86. A failing command keeps its own status, and a root or unset publish path gets no check.
- **Log and reason:**
  - The build-log filter drops BuildKit's exit-code verdict after that line, so the log ends with Render's line. The upload and `Build successful 🎉` never run.
  - `nativeCommandFailure` names the step `publish directory`, with Render's sentence as the tail, but only when the check's line is in the transcript. A command that itself exits 86 stays a `build command` failure named as one.
  - The deploy closes `build_failed` with "build failed in the publish directory step: Publish directory <dir> does not exist!".
  - The publish Job's extract stays the backstop: a command that replaces the EXIT trap or execs skips the check.
- **Tests** (`nativepublishcheck_test.go`):
  - the check's placement, and none for a root path, an unset path or a service;
  - the real script under bash: the directory left, left elsewhere, a failing command, a clean `exit 0` without it, and a path with a space and a quote;
  - the BuildKit log and the failure reason;
  - a static command failing with 3 or 86 is a build command failure.

  The log test fails without the filter's suppression, and the exit-86 case fails without the line gate. Operator `make test` passed.
- **Review** (`/simplify`, three reviewers): shared constants for the exit, the sentence and the working directory; awk extracts the exit code once; a `printedQuote` helper; the line gate (a lone exit 86 used to leak bex's script into the reason). The BuildKit cache misses once per static site after the rollout, and again only when its publish path changes.
- **Docs:** ADR029 § Publish.
- **Still owed on production:** the abd1 steps. A saved Publish Directory `nope`, then a deploy: the build log ends `==> Publish directory nope does not exist!` with no `Uploading build...` or `Build successful`, the row closes `build_failed` with that reason, and the site keeps serving. A correct directory still logs `Build successful 🎉` and goes live.
