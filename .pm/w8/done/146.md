# A recreated static site serves the deleted site's cached pages until its second deploy

Why: the static server's object cache is keyed by `<workspace>/<site name>/rev-N/<path>` and assumes a revision prefix is never reused. Revision numbers restart at `rev-1` when a site is deleted and recreated under the same name. Visitors to the new site's URL then keep getting the deleted site's pages, for every path that was requested while the old site was live, even after the new deploy reports `live`. A user who deletes a site to take content down and recreates it still has that content served publicly.

**Severity:** major (wrong and possibly withdrawn content served publicly while the deploy reads live). **Attribution:** platform runtime (static server). **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1248, 2026-10-20 ([evidence](evidence/cli-sweep1248/README.md)).

## Reproduction

HEAD checkout CLI `94533d795` against pinned Render CLI v2.27.0, production `https://api.bex.co/v1/`, deployed pin `94533d795067`, workspace `bex-canary`, human device-login grant. Public repositories, no-build publish.

1. `bex services create --name qa-20261020-4fc46e-stat --type static_site --repo https://github.com/mdn/beginner-html-site --branch main --publish-directory . -o json --confirm` → `srv-dbbiur9q56vc73bn8ebg`, live in 22 s. `GET https://qa-20261020-4fc46e-stat.onbex.co/` → 200, body sha256 `e999a69c…`, which is that repository's `index.html`.
2. `bex services delete srv-dbbiur9q56vc73bn8ebg --confirm` → GET 404. The URL answers 404 `404 page not found`.
3. Recreate the name from the other repository: `… --repo https://github.com/mdn/beginner-html-site-styled …`. The name is refused with `409 … already in use` for about 100 s while the deleted site is torn down (recorded in the evidence), then → `srv-dbbivuucbnls73997fs0`, whose first deploy `dep-dbbivuucbnls73997fsg` is `live` (commit `6c7a360ddb`) in 13 s.
4. `GET /` and `GET /index.html` → 200, sha256 **`e999a69c…` (the deleted site's page)**, `ETag "6ZmmnMpGv4mR6dOv2XsOrw"`, `Cache-Control: public, max-age=0, must-revalidate`. The new repository's `index.html` is `5d04139b…`. A cache-busting query (`/?cb=…`) changes nothing. Paths never requested on the old site come from the new publication (`/styles/style.css` 200; the old site's `/Firefox-icon.png` and `/CONTRIBUTING.md` 404), so the bucket was cleaned and only the cache is stale.
5. The stale page was still served more than 6 minutes after the new deploy went live. `bex deploys create srv-dbbivuucbnls73997fs0 --wait` (now `rev-2`) → `GET /` serves `5d04139b…`.

All fixtures were deleted (GET 404); the ledger shows no survivor.

## Expected

A new site serves only its own publication, as on Render, where each service is a distinct ID with a fresh CDN namespace. The first `live` deploy's content is what the URL returns.

## Root cause

- `lego/operator/internal/staticserver/cache.go:21–24` documents the invariant: “Keys are `<appID>/<revision>/<path>` — a revision prefix is immutable, so an entry is never stale and needs no TTL (a new deploy is a new revision => a new key).”
- `staticserver.go:142–151` (`Site.keyFor`) builds the cache key from `Site.Prefix`, which is `app.Status.StaticPrefix` = `<ws>/<app name>/rev-N/`. `resolver.go:93–96` sets `AppID: app.Name` and `Revision: app.Status.ActiveRevision`.
- ADR029:26 restates the assumption: “The static-server's in-memory cache is keyed by revision prefix, so it is never stale and is never purged.”
- Neither key component is unique per incarnation. The release generation restarts at 1 for a new App CR with the same name, a reset the operator already knows about for built images (`pinBuiltImage`'s comment, `app_controller.go:1455–1458`: “The per-release gen-N tag RESETS on delete+recreate of the same App name”). Static publications never got the equivalent guard, so a cached object from the deleted site's `rev-1` answers the new site's `rev-1` requests indefinitely (no TTL; only budget eviction or a static-server restart clears it).

## Fix

Make the cache key incarnation-unique without changing object-store paths. Have the resolver carry the App's UID, or its `app.bex.co/app-id` srv id, in `Site`, and prefix every cache key with it (including the brotli variant keys from `encoding.go`'s `brotliVariantKey`). Keep `Prefix`/`StaticPrefix` as the storage key. Optionally also evict a site's cache entries when its App disappears from the resolver.

## Acceptance

- Unit (`staticserver`): two `Site`s with the same `Prefix` but different identities never share a cache entry. A request for the second never returns the first's cached body or ETag, including the br variant. The existing invariant tests stay green.
- Live after deploy: repeat steps 1–4 on fresh free fixtures (with a request to `/` while the first is live). The recreated site's first live deploy serves its own `index.html`. Delete the fixtures with 404 proofs.

## Blast radius

Every static-site cache entry: plain and brotli variants, negative (404) entries (`staticserver.go:492` caches misses, so an old 404 can also mask a new file), and every host that resolves to the site. Rollback copies a retained publication into a new revision (ADR029/w4/m197), so it gets a new key and is unaffected. Web services are not involved. The same name-keyed class is w8/144 (logs and metrics), but this one is a separate component and fix.

## Dedupe

`rg -i 'incarnation|recreat|same name'` combined with static/cache across `.pm` and `docs` (excluding evidence) found no item. Sweep 363 (`static-revision-cache`) covered revision changes within one App, not recreation.

## Status — DONE (2026-10-28; was BLOCKED 2026-10-20 on deployment, hosted acceptance below)

Implemented and unit-tested: `Site.Incarnation` (the App UID, set by the resolver) prefixes every cache key, covering objects, cached misses and Brotli variants (`Site.cacheKey`), while origin keys are unchanged. `TestRecreatedSiteNeverServesItsPredecessorsCache` fails on the pre-fix code and passes after. ADR029 records it. The live acceptance needs the deployed release: the release pipeline deploys the static-server; QA repeats steps 1–4 on fresh free fixtures (a request to `/` while the first is live) and the recreated site's first live deploy serves its own `index.html`; delete the fixtures with 404 proofs.
