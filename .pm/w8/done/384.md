# A first image deploy with nothing listening tells the user to "check that the path returns a 2xx or 3xx status", though the service has no Health Check Path

Why: w8/259 (2026-11-11) removed the path sentence from a TCP-check stall because there is no path to check. w4/m350 (`5d053738a3`, 2026-11-14) then gave a first web image release an exec `open-port` check instead of the TCP probe, and that probe falls through to the "other check" wording, so the path advice is back for exactly the services that listen nowhere or only on 127.0.0.1.

- Severity: minor. The deploy still fails at the 15-minute budget, and the same stall text goes on to name port 10000, host `0.0.0.0` and the background-worker alternative; the first sentence points the user at a setting that does not exist.
- Versions: bex CLI v0.9.0 release binary. Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md` (`4fd34231b637`). Production pin unknown; the code is unchanged on main `cd0e6bae6a`. The same text was recorded on 2026-11-19 in w5/m356's live check (`qa-20261119-m356-lo`) without being called out.
- Context: 2026-11-21 21:22–21:32 UTC, `https://api.bex.co/v1/`, QA human device-flow login, workspace `bex-canary`. Routine `cli-qa`, run r29, nonce `6070`. Fixtures created with `POST /v1/services` (`runtime: image`, `plan: free`, `dockerCommand`, no `healthCheckPath`), because the pinned CLI refuses `--start-command` off native runtimes. Both deleted, 404 confirmed.
- Attribution: operator stall wording (`lego/operator/internal/controller`), surfaced through the deploy's `stallReason`/`failureReason` on REST, GraphQL, MCP and the dashboard.

## Repro

`docker.io/library/busybox:1.36` web services, read with `GET /v1/services/{id}/deploys?limit=1`:

- `srv-dc10n0e0ri4c73c4017g`, `sh -c '… httpd -f -p 127.0.0.1:$PORT -h /tmp/w & wait'`
- `srv-dc10n260ri4c73c4019g`, `sh -c '… sleep 2147483 & wait'`

From about 3 minutes after the deploy started (`update_in_progress`), both read:

```text
the container is running but its startup health check has not succeeded, so the rollout is waiting: the configured health check. Check that the path returns a 2xx or 3xx status on the service's own port. Nothing accepted a TCP connection on port 10000, the default because the image declares no TCP ports. The server must bind host 0.0.0.0 on the port in PORT (10000). If the service does not need to receive traffic on any port, create a background worker instead. No port answered HTTP during startup discovery.
```

w5/m356 recorded the failed form, "… never succeeded within the rollout window, so the deploy failed: the configured health check. Check that the path …", with the same tail. A native service with no path gets the TCP sentence instead ("No Health Check Path is set, so the check is a TCP connect, which only asks whether the process is listening on that port", w8/259's 2026-11-12 replay).

## Root cause

- `lego/operator/internal/controller/health_probe.go:70` `healthProbeOpenPortHandler` is the startup/readiness probe of a first web image release still discovering its HTTP port (w4/m350): an exec of `/bex-health/health-probe open-port`.
- `lego/operator/internal/controller/app_controller.go:6986` `probeStallText`: `probeGET` (`:7072`) recognises only `HTTPGet` and the helper's `check` exec, and `tcp` only a `TCPSocket` probe, so the `open-port` exec takes `OtherProbeStallReason`, whose templates end with `probeStallPathTail` (`lego/types/v1alpha1/deploy_reasons.go:148-150`, `:185-189`: "Any other check keeps the path advice its sentence has always ended on").

## Fix

- In `probeStallText`, recognise `healthProbeChecksOpenPort(probe.Exec)` (`health_probe.go:135`) and word it as Render's default check: "…: a TCP connect to any port the instance listens on. No Health Check Path is set, so the check only asks whether the process is listening on a port." Add `probe_open_port_{waiting,failed}{,_restarted}` codes with templates in `deploy_reasons.go`, the terminal swap in `terminalStallMessage` unchanged, and the dashboard's deploy-reason strings in every locale under `dashboard/src/features/deploys/locales/` (w4/591, w5/m356 word reasons by code).
- Keep the "other" wording for a genuinely unknown probe (gRPC). Blast radius: `probeStallText` has one production caller (`app_controller.go:6978`); every web image service on its first release with no Health Check Path, on every workspace.

## Acceptance

- Regression tests: a `probe_stall_reason_test.go` case for the `open-port` exec (waiting, failed, restarted), `TestDeployReasonsRoundTrip` for the new codes, and the dashboard locale test. Revert and watch them fail.

## Fixed (2026-11-21, `a9d7e9f639`), live check owed

Render's port-scan guidance ([Troubleshooting deploys § Port scan timeout reached](https://render.com/docs/troubleshooting-deploys), quoted in [w8/259](../done/259.md)) asks for "at least one open port on your service's host", and its default health check is "TCP socket probes to one of your service's open ports" (`health_probe.go`'s `healthProbeOpenPortHandler`). Neither has a path.

- Operator: `probeStallText` (`app_controller.go`) recognises the `open-port` exec (`healthProbeChecksOpenPort`) before the GET and TCP cases. It words the check as "…: a TCP connect to any open port on the instance. No Health Check Path is set, so the check is a TCP connect, which only asks whether the process is listening on at least one port." The port hints (port 10000, host `0.0.0.0`, the background worker, no HTTP discovered) still follow in `{hint}`.
- Types: the codes `probe_open_port_{waiting,failed}{,_restarted}` (`lego/types/v1alpha1/deploy_reasons.go`). The failed half is the shared `ProbeStallWaiting`→`ProbeStallFailed` swap, so `terminalStallMessage` and bex-api's `TerminalStallText` restate it alike.
- Unchanged: a gRPC or other unknown check keeps "the configured health check" with the path sentence, a GET keeps the path sentence, and a native TCP probe keeps w8/259's sentence.
- Surfaces: the deploy's `stallReason`/`failureReason`, the `deploy_ended` event and MCP carry the English. GraphQL's `deployReason` parses it as the new code, and the dashboard words it in all eight locales.
- Tests: the two `any open port` cases of `TestProbeStallMessageParsesAsItsTemplate` (startup, and readiness restarted by liveness; waiting and failed, with and without a hint) failed with the operator branch disabled, reading "Check that the path …". `TestDeployReasonsRoundTrip` and `TestDashboardWordsEveryDeployReason` take every template, the new codes included. The dashboard's "words a stall of the any-open-port check without the path advice" failed with the en and zh entries removed.
- Owed: the production check in Acceptance, once the pin carries `a9d7e9f639`.
