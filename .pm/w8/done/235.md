# A static site with a missing publish directory emits `build_ended: failed` but its deploy never closes

Why: w4/493 and w4/505 (both done 2026-11-05) made a missing publish directory a user build failure. The deploy should close `build_failed` with a plain reason, and `build_ended` should report `failed` only once that outcome is known. On production the second half happens but the first does not. `build_ended` reports `failed` (with an empty `reason`) about 40 s in, yet the deploy itself stays `update_in_progress` with no `finishedAt`, no `failureReason` and no `deploy_ended`. It had not closed 24 minutes later, and the build log never shows a failure line. A user, `bex deploys create --wait` and any CI gate see a deploy that never finishes and never says why. On Render the deploy ends as a failed build, and the log names the missing directory.

Severity: **major** (a deploy hangs indefinitely on a common user mistake, and the w4/493 reason never reaches any surface). Attribution: operator/store deploy outcome for static publishes (`withholdBuildEndedWhilePublishing` in `store/reconciler.go` and the `BuildFailedUserError` path from `48633d332`). Not traced in the cluster. Estimate: ~60m. Source: `/qa-find-bugs-cli` loop sweep 3093, 2026-11-06 00:58–01:22 UTC, pin `92ff0029334d` (contains `48633d332` w4/493 and `712f3f695` w4/505), workspace `bex-canary`.

## Expected

Within seconds of the failed publish, the deploy reads `build_failed`, with `finishedAt` set and the w4/493 plain reason (`the publish directory "does-not-exist" does not exist in the repository at "<sha>"`). One `deploy_ended` is emitted with `deployStatus: failed`, and `build_ended`'s `reason` carries `buildFailed {id}` (Render's shape, as w8/m146 adopted). The build log ends with the same reason.

**DONE 2026-11-05** (`/loopx w8`): already fixed by `b78173c37` (w4/515), which landed while this run was shipping the same fix. The root cause was the deploy transition table. `build_failed` had no edge from `update_in_progress`, where a static site's publish runs, so the store refused the close and the row stayed open forever. `build_ended`, which is derived from the observed status, still said `failed`. `b78173c37` adds that edge, and it also stops lifecycle facts from minting a terminal `build_ended` for a transition the row cannot make. This run reproduced the same failure independently (the row stayed `update_in_progress` with an empty reason before the edge existed) and confirmed that the closed row is what produces `failureReason`/`finishedAt`, `deploy_ended`, `build_ended`'s `buildFailed {id}` (`events.deployEndReason`) and the build log's closing failure line (`logs.terminalLines`). Hosted re-check is pending the next deploy.
