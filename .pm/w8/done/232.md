# `POST /v1/build-sources` answers 500 `internal error` but creates the build source anyway

Why: Render's `CreateBuildSource` returns `201` with the new build source. bex instead returns `500 {"error":"internal error"}` for every valid create, git or image, yet the resource exists right afterwards and lists, reads, renames and deletes normally. A client sees a hard failure, so it either gives up on a resource that exists or retries and makes duplicates. Three creates in this sweep left three build sources.

Severity: **major** (the whole create path of a new public API fails on every call, and the failure is not even honest about whether anything was created). Attribution: backend `lego/backend/internal/apps/build_sources.go:151` `CreateBuildSource`. The likely cause is the final `s.GetBuildSource(ctx, id)` read-back running before the new App is readable; not traced. Estimate: ~45m. Source: `/qa-find-bugs-cli` loop sweep 3093, 2026-11-03 17:06–17:09 UTC, pin `ac4d469bafaf` (w2/m254 t003 `c3dae1674` live), workspace `bex-canary`.

GET /v1/build-sources?ownerId=…  (seconds later) → all three exist:
  srv-dbl199b67o7c7382uge0 qa-20261103-3093-bs   created 17:06:46Z

GET /v1/build-sources/{id} → 200;  PATCH {name} → 200 renamed;  GET /v1/services/{id} → 404 (not a service, as intended)

## Fix

Make create return what it created. Either:

- build the `201` body from the request and the minted id instead of re-reading; or
- wait for or retry the read-back (or read from the store row `s.create` just wrote), and map a not-yet-readable result to the created view rather than an internal error.

Add a backend test that drives `CreateBuildSource` through the real create path and asserts a `201` with the minted `id`. Check whether the same read-back pattern exists in other new create paths.

## Acceptance

Also noticed, not filed: build-source ids use the `srv-` prefix. Check Render's id prefix for build sources and ADR020 before calling that a divergence.
