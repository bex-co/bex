# A far-future log endTime with no startTime still returns 500 (or times out)

Why: done w8/120 promised "never 500; a future end alone still returns the lines up to now". A user or script passing a generous `--end` (an end-of-year bound, or a clock-skewed host) instead gets an opaque 500 or a 503 timeout for a window that can only ever hold the last seven days.

Found by the `/qa-find-bugs-cli` solo loop, run 2 sweep r1, 2026-10-19 ~03:20 UTC, against `https://api.bex.co/v1/` (platform pin `f3871ba9fd44`, which includes the w8/120 fix `456090929`). Pinned-CLI HEAD build `v0.3.3+e572e7977`, workspace `bex-canary`, human device login. Fixture: an owned Free native web service `srv-dbaolj8u2drc73bm0qcg` with recent app lines. Each case was run against the same fixture in fresh CLI processes, and the 2030 case twice:

```text
bex logs -r <srv-id> --end 2030-01-01T00:00:00Z --limit 3 -o json
→ exit 1: Error: error listing logs: received response code 500: internal error   (also --direction forward, --type request)
bex logs -r <srv-id> --end <now+24d … now+40d> --limit 3        → 500 internal error
bex logs -r <srv-id> --end <now+20d … now+23d> --limit 3        → 503 (QUERY_TIMEOUT): log search timed out
bex logs -r <srv-id> --end <now+1h | now+6d | now+8d> --limit 3 → 200, 3 lines   (the w8/120 behavior)
bex logs -r <srv-id> --start <now-1d> --end <now+40d> --limit 3 → 400 query range exceeds 720 hours
bex logs -r <srv-id> --start 2030-01-01T00:00:00Z --limit 3     → 200 empty   (w8/120 fixed)
```

Mechanism: `lokiRange` (`lego/backend/internal/logs/loki.go:370-380`) now defaults an omitted start to `earlier(end, now) − lokiLookback` (7 days), but it still returns the caller's far-future `end` as the query's upper bound. `checkWindowCap` (`lego/backend/internal/core/pagination.go:184-186`) returns early when `start` is zero, so the defaulted window is never capped.

- Once `end − (now − 7d)` passes 720h, Loki refuses the query (its own max query length) and the error surfaces as a 500. An explicit start hits the backend's honest 400 instead.
- Just under the cap, the backward scan walks roughly three empty future weeks and spends the 18s budget, giving a 503 `QUERY_TIMEOUT`.

Fix sketch: no line can be stamped after now, so clamp the history query's effective upper bound to `earlier(q.End, now)` in `lokiRange`. Keep `lokiEndParam`'s inclusive +1ns only when the caller's End is itself at or before now, and keep the page cursors on the clamped bound.

- Then `--end 2030` with no start reads `now−7d..now` and returns the latest lines, matching the +1h/+6d/+8d behavior that already works.
- Decide whether the explicit `--start now−1d --end now+40d` case should cap on the effective (clamped) window and return that day's lines, rather than the current 400; record the rule in ADR010.

Check the same defaulting in the label-values source and the Postgres/Key Value log reads that share `lokiRange`. Also check metrics, which uses `core.CheckQueryWindow` (`metrics/service.go`), for a far-future end with an omitted start.

Acceptance:

- `bex logs -r <id> --end 2030-01-01T00:00:00Z --limit 3 -o json` exits 0 with the latest lines, on REST, GraphQL and MCP alike, in both directions and for `--type request`.
- An end 20–40 days ahead behaves the same, with no 500 or 503.
- Existing w8/120, w8/043 (inclusive end) and window-cap tests stay green; add unit cases for a far-future end with a zero start beside `loki_bounds_test.go` and `core/pagination_test.go`.

Severity: minor. Estimate: ~45m.

**Done (2026-10-19):**

- **Window clamp.** `lokiRange` ends the window it sends Loki at the earlier of the caller's `endTime` and now plus a 10-minute clock grace (`lokiFutureGrace`, Loki's creation grace for nodes whose clocks run ahead). An `endTime` inside the grace stays the caller's own inclusive end, with w8/043's +1ns. A clamped end stays exclusive. So `--end 2030` with no start reads the last seven days, backward and forward, for every log type and every resource the logs service serves. That covers REST, GraphQL and MCP, which share one `checkWindow`, and label discovery.
- **Query-hours cap.** `checkWindow` measures `BEX_MAX_QUERY_HOURS` on the window up to now. An explicit start one day ago with an end 40 days ahead now reads that day instead of returning a 400. A start older than the cap is still refused, and a window that has not begun stays an empty page.
- **Metrics.** Untouched. A far-future end there with no start reads an empty future window, not an error.
- **Tests.** `TestLogsUpToAFarFutureEndQueryLokiOnlyUpToNow` (both directions) and `TestLogQueryCapMeasuresTheWindowUpToNow` fail before and pass after. `TestLokiRange` gains fixed-clock far-future and clock-skew cases. The existing w8/120, w8/043 and window-cap tests stay green.
- **Docs.** The rule is recorded in ADR010.
- **Follow-up.** The review also found that omitted-start cursors default to one hour while the read looks back seven days, which predates this change; it is filed as w8/125.
