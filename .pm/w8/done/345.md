# A short commit SHA deploy of a GitLab or Bitbucket service fails at clone with "couldn't find remote ref", and an unknown SHA opens a deploy instead of a 404

Why: Render takes "either a full or short commit SHA" in a deploy hook's `ref` ([deploy-a-commit](https://render.com/docs/deploy-a-commit)), and bex already expands one for a github.com repo (w8/280). On a public GitLab or Bitbucket repo, the same 7-character SHA of a real commit fails the build with `fatal: couldn't find remote ref d832d0d`, and its log says `Building from …@master`. GitLab CI hands its jobs such a SHA as `$CI_COMMIT_SHORT_SHA`. Also, a SHA the repo doesn't have opens a deploy that records the bogus SHA as its commit, where GitHub answers `404 commit_not_found`.

- Severity: major. A documented way to deploy a commit can't work for these hosts, and the error says the commit is missing when it exists. The previous release keeps serving.
- Versions: bex CLI v0.7.0 (Render CLI pin `v1.1.3-0.20261106232710-4fd34231b637`); production pin `98e053468f52` for every case (no roll between 02:44 and 03:10 UTC); checkout `869f38253`.
- Context: 2026-11-20 02:44–03:10 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), QA human device-flow login, `-o json`, no TTY; routine `cli-qa` run `rt6-7a3d` (services from public GitLab and Bitbucket repos).

## Root cause

- `lego/backend/internal/github/service.go:1378`: `resolveCommit` sends every repo not on github.com to `resolvePublicGitCommit` (`github/public_git.go:75-86`). That reads only the smart-HTTP advertisement, which lists ref tips. A full 40- or 64-hex SHA it doesn't list is echoed back as requested (w8/209, `core.ValidCommitSHA`, `core/giturl.go:118`). An abbreviated SHA is a plain miss.
- `lego/backend/internal/deploys/service.go:1090-1116` `lookupCommit` turns the miss into an empty commit, and `:1009-1013` writes the raw `d832d0d` into `spec.BuildCommit`.
- The clone step runs `git fetch -q --depth 1 origin -- "$REF"` (`lego/operator/internal/build/build.go:1891`). upload-pack takes ref names and full object names, never a prefix, so git answers `couldn't find remote ref d832d0d`.
- For github.com, `resolvePublicCommit` (`github/service.go:1455`) asks GitHub's commits API, which accepts a prefix. It returns the full SHA, the message and the time, so the build pins the full SHA. That is why the control works.
- Unknown SHA: w8/280 gave GitHub `store.ErrCommitNotFound` (`noSuchCommit`, `service.go:1418`), which `triggerFetched` (`deploys/service.go:877`) turns into `404 commit_not_found` before any write. Its Unverified said other hosts "cannot prove absence". The advertisement can't, but the GitLab and Bitbucket commit APIs above can.
- The log line is `logs/progress.go:366-379`. With no commit on the row, it prints `pc.branch`, the service's branch at read time, not at deploy time. After a later `services update --branch adr/yaml-pr`, the 03:01 short-SHA deploy that had read `@master` read `@adr/yaml-pr`.

## Fix

- In the `!onGitHub` branch, for a gitlab.com or bitbucket.org repo, ask that host's anonymous commit API when the advertisement can't resolve the ref and the ref is hex (an abbreviated SHA, or a full one it doesn't list). `parsePublicBlueprintSource` (`github/public_blueprint.go:71`, w8/344) already addresses both hosts.
  - GitLab: `GET https://gitlab.com/api/v4/projects/<url-escaped path>/repository/commits/<ref>`.
  - Bitbucket: `GET https://api.bitbucket.org/2.0/repositories/<workspace>/<repo>/commit/<ref>`.
  - Use the SSRF-safe `anonymousGitClient` (`public_git.go:256`), with no redirects, a bounded body and the 5 s budget.
- A 200 returns `CommitInfo{Hash, Message, AuthorAt}` from `id`/`message`/`committed_date` or `hash`/`message`/`date`. The build then pins the full SHA, and the row carries the message and time as the GitHub control's does.
- GitLab's `404 Commit Not Found`, or Bitbucket's 404 `error.message` `Commit not found`, is `store.ErrCommitNotFound`. Cache it with `publicCommitNotFoundTTL` (30 s), so the trigger answers `404 commit_not_found` and opens nothing.
- `404 Project Not Found`, a missing repository, 401, 403, 429, 5xx and timeouts stay a miss, so today's behavior and the no-existence-oracle rule hold: a private repo reads like a missing one, as the advertisement already does.
- A full SHA that the API can't answer for (an outage) is still recorded as requested (w8/209).
- Other hosts are unchanged. Expanding a prefix in the clone step itself for any host (a treeless fetch, then `git rev-parse`) is a separate follow-up, not part of this.
- Optional, same change: the build log prints the requested ref when the row has no commit, as w8/280's Fix 3 said and left undone.

## Unverified

- Render documents short SHAs only for the deploy hook. The REST `commitId` says "The SHA of a specific Git commit" (pinned CLI `pkg/client/types_gen.go:5317`). The CLI case follows bex's own GitHub behavior.
- How Render answers an ambiguous prefix, and how GitLab and Bitbucket do (neither was probed).
- Whether Render shows a commit message for a public-URL service. Today a GitLab or Bitbucket deploy carries `commit.id` with no `message` or `createdAt` (ADR004 § Deploy commit provenance, w8/209's scope choice). This fix fills them only when it calls the host API. Filling them on every deploy would spend those hosts' anonymous API quota on each one. That is a separate decision, not part of this.
- Those hosts' anonymous rate limits were not measured. Bitbucket's is low, so cache the answers the way the GitHub anonymous path does.
