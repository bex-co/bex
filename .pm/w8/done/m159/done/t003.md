## Objective

A logs read or tail with no `type` returns every type, build included, as `LogQuery.wants` already says it should. The interactive `bex deploys create` then shows the build it started: its pinned flow (`pkg/tui/flows/log.go:54-60`) tails the service from now with no type. The dashboard's service Logs tab asks for `app` and `request` explicitly, so it keeps showing what Render's service explorer shows.

## Context

- `lego/backend/internal/logs/loki.go:520-546` `lokiTypeMatcher`, `len(q.Types) == 0` branch: app and request only ("Build is deliberately NOT in this union", w6/m131).
- Evidence for the default: Render's deploy page is its log explorer scoped to the deploy, with an **All logs** default that includes build lines (`docs/render-artifacts/live-deploy-following.md:56`). Render's [Logging](https://render.com/docs/logging) page says only that request logs "appear alongside application logs" in the service explorer. No Render page states the API default (recorded in the README's Unverified).
- The dashboard Logs tab reads through GraphQL `logs` (`dashboard/src/features/logs/api/logs.graphql`), whose `type` is a single string ("the shape the dashboard has always sent", `:13`); its all-types view sends no type. It needs a way to ask for app and request together: a list argument (`types: [String!]`), or a value such as `app,request` that `NormalizeTypes` splits. Check the mobile app's log screen the same way.
- The Hobby plan narrows the type-less union to app (`noRequest`, w8/m138): keep build in it.

## Steps

1. Make the type-less union app + request + build, on the read and the tail.
2. Give GraphQL `logs` a way to request app and request together, and make the dashboard Logs tab (and any other UI that means "service logs") use it for its all-types view; leave the deploy page as it is.
3. Re-run the interactive `bex deploys create` check of the README's definition of done 4.
