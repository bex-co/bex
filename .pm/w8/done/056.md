# 056 — REST create skips the per-type setting gates that update and Blueprints enforce (cron, worker, private service and static site all accept settings that don't apply to them)

Why: bex's rule is "nothing accepted is ignored". `PATCH` refuses a health-check path on `cron_job`/`background_worker` (`health check path is not applicable to a …`), and the operator never probes those types. But create stores the path, reads it back as if it applied, and Blueprint validate passes it.

Severity: minor. Attribution: server (`lego/backend/internal/apps`).

## Evidence (2026-10-05, `/qa-find-bugs-cli` w8 loop, sweep 15)

Production pin `8f58b933d`, workspace `bex-canary`, human device login. Nothing created: dry-runs and validate only.

The bypass is REST, GraphQL, MCP and Blueprint.

## Mechanism

- `lego/backend/internal/apps/service.go:2670` (`specFromCreate`) runs `normalizeHealthCheckPath(req.HealthCheckPath)` with no type check. `validateTypeSpecificCreate` (`:2819-2853`) gates schedule, hosts and static fields, but not the health path.
- The Blueprint adapter forwards `HealthCheckPath` for every service type (`deploy.go:2230`). `capabilities.json` marks `serverService.healthCheckPath` `translated` for all server types, worker included.
- `lego/operator/internal/controller/deployment_projection.go:262` (`if !p.worker`) attaches probes only to non-worker types, so the stored path never does anything.

- `service.go:2728,2766` validates and stores `req.IPAllowList` for every type. The type rule exists only in the Blueprint adapter (`deploy.go:2281`). Pre-deploy on cron is refused only in the update check (`settings_check.go` `checkPreDeployCommand`), and the renderSubdomainPolicy type rule likewise lives only in its update check, so create reaches a later, unrelated refusal.

## Fix

Move every per-type applicability rule into `validateTypeSpecificCreate`, sharing one predicate per setting with the update checks, so create, update and Blueprint cannot drift: `healthCheckPath` (web/private only; static sites too, which update currently allows), `preDeployCommand` (not cron/static), `ipAllowList` (web/static only), `renderSubdomainPolicy` (web/static only, with the type reason checked before the custom-domain reason). For health checks specifically: call call `checkHealthCheckPath`'s type check (or a shared `healthCheckPathApplies(type)`) from `validateTypeSpecificCreate`, so REST/GraphQL/MCP create and Blueprint apply/validate refuse it. For Blueprints, report it located at `services[n].healthCheckPath`.

Render comparison: Render's schema allows `healthCheckPath` on any `serverService` (web/pserv/worker) and documents health checks for web services only. Refusing matches bex's own update rule and its "fail closed rather than silently ignore" registry policy (see the cron `preDeployCommand` refusal reason in `capabilities.json`). If parity-by-ignoring is preferred instead, the update path must stop refusing. Either way the two must agree.

## Acceptance

- [ ] REST `POST /v1/services` (`dryRun` and real) for a `cron_job` with `preDeployCommand` / `ipAllowList` → 400 naming the type, matching the update/Blueprint wording; `renderSubdomainPolicy` → the type reason, not the custom-domain reason.
- [ ] REST `POST /v1/services` (`dryRun` and real) for `cron_job`/`background_worker` with `healthCheckPath` → 400 `health check path is not applicable to a cron_job` (or `background_worker`).
- [ ] `bex blueprints validate` of a `worker`/`cron` with `healthCheckPath` → exit 1 at `services[0].healthCheckPath`.
- [ ] Controls: web and private services keep accepting it on create and update. Existing workers/crons with a stored path are not broken (the path stays readable or is cleared, as decided).

## Dedupe

`rg -i 'health ?check.{0,40}(worker|cron).{0,40}create' .pm` found nothing. ADR018 row "Health checks" says "Rejected for `cron_job`/`background_worker`", which holds for update only.

Estimate: ~1h (4 settings × shared predicate across create/update/Blueprint + matrix test). If it grows past that, promote to a milestone.

Done 2026-10-05 (loopx):
- **Shared rules.** One applicability predicate and one refusal per setting now live in `settings_check.go`: `healthCheckPathApplies`, `preDeployCommandApplies`, and `errSubdomainPolicyNotApplicable`/`errIPAllowListNotApplicable` for the publicly routable types. The update checks use them, and `validateTypeSpecificCreate` checks them first. It therefore covers REST, GraphQL and MCP create (dry run and real) and Blueprint validate/apply (via `specFromCreate`).
- **Create.** It refuses exactly what update refuses, with the update wording. `renderSubdomainPolicy` gets the type reason, not the custom-domain guard.
- **ipAllowList on update.** Update now refuses a non-empty list on a type with no ingress, through `checkIPAllowList`, which `SetIPAllowList` and the PATCH preflight share. A clear stays allowed so a legacy stored list can be removed. The enforcement is a Traefik middleware on the Ingress, and the dashboard already offers it only for web/static.
- **Kept as today's update rule.** A static site's `healthCheckPath` is still accepted, since update allows it. Existing workers and crons with a stored path are untouched and readable. Generate Blueprint already omits these fields for those types.
- **Tests.** The create matrix (10 refusals naming the type, 7 controls), the cron `renderSubdomainPolicy` reason, update refusing a cron `ipAllowList` but allowing a clear, and a Blueprint worker `healthCheckPath` located at `services[0].healthCheckPath`. Backend suite and `make lint` are green. Not live-replayed.
