`w9/m2`'s KeyValue CLI-compat fix (this session, `lego/backend/internal/keyvalue/rest.go`) found and fixed a real bug the earlier "RC3 fixed"/"RC4 fixed" claims missed: every single-item KeyValue REST response (create/get/update/suspend/resume) sent bex's internal flat shape (`ownerId` as a bare string, `maxmemoryPolicy`/`persistenceMode` top-level) instead of Render's real contract, which nests `owner: {id,name,type}` and `options: {maxmemoryPolicy,persistenceMode}` (`cli/pkg/client/types_gen.go`'s `KeyValueDetail`). Because a JSON shape mismatch decodes silently to zero values rather than erroring, every `keyvalues` CLI command still exited 0 and looked like it worked while quietly showing an empty `ownerId` and omitting `maxmemoryPolicy`/`persistenceMode` from its output entirely.

Postgres's generated `PostgresDetail` type (`cli/pkg/client/types_gen.go`) has the identical `Owner Owner \`json:"owner"\`` nested field — bex-api's `internal/postgres/rest.go` almost certainly has the identical bug (flat `ownerId`), unverified but highly likely given both packages were built from the same template and both had the identical RC3/RC4-class bugs already. Fix pattern to mirror exactly: `lego/backend/internal/keyvalue/rest.go`'s new `renderKeyValue`/`keyValueOwner`/`toRenderKeyValue` (a REST-boundary-only wire-shaping layer — the CRD/GraphQL/MCP types stay untouched, only the REST JSON response wraps). Verify field-by-field (id/name isn't enough — the earlier keyvalue "fixed" claim only checked those and missed this) before calling it done.

Evidence + full repro harness: `docs/cli-compatibility-checklist.md` (root cause RC14, formerly drafted as RC11 before merging with a parallel session's RC11–RC13).

Source: `w9/m2` (Render CLI compatibility), 2026-07-15.
