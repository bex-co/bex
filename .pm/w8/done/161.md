# `bex blueprints validate` refuses a `fromService.envVarKey` copy of a `sync: false` variable, which Render's own AEO-analytics example uses

Why: a common Render pattern is to prompt once for a secret on one service (`sync: false`) and let sibling services copy it (`fromService: {name: web, envVarKey: API_KEY}`). Render's official `render-examples/AEO-analytics` does exactly that for its cron job. Bex validation drops every unanswered `sync: false` key from the copyable set, so the copy is refused as "no such plainly-defined variable". Validation (the CLI, CI checks, the dashboard's first validate) fails before the user has a chance to answer the prompt.

**Severity:** minor (validate-time refusal of a Render-valid Blueprint; the create path with answered prompts is expected to resolve, not live-verified). **Attribution:** server (Blueprint reference resolution). **Estimate:** 40m. **Source:** `/qa-find-bugs-cli` sweep 1276, 2026-10-21 ([evidence](../evidence/cli-sweep1276/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `9cace6b6e25d`, HEAD-built pinned CLI.

```yaml
services:
  - type: web
    name: qa-20261021-src
    runtime: image
    image: { url: docker.io/ealen/echo-server:0.9.2 }
    plan: free
    envVars:
      - key: SHARED_TOKEN
        sync: false
  - type: web
    name: qa-20261021-dst
    runtime: image
    image: { url: docker.io/ealen/echo-server:0.9.2 }
    plan: free
    envVars:
      - key: SHARED_TOKEN
        fromService: { type: web, name: qa-20261021-src, envVarKey: SHARED_TOKEN }
```

`bex blueprints validate syncref.yaml -o json` → exit 1, `services[1].envVars[0]` line 16: `fromService.envVarKey references env "SHARED_TOKEN" on service "qa-20261021-src", which has no such plainly-defined variable`. The same file nested under `projects[].environments[]` fails the same way. `render-examples/AEO-analytics/render.yaml` (`aeo-analytics-cron` copies `RENDER_API_KEY` and `RENDER_WORKFLOW_SLUG` from `aeo-analytics-web`, where both are `sync: false`) gets the same refusal.

## Expected

Render's Blueprint reference: `envVarKey` copies "the value of an environment variable from another service". The source being a prompted secret does not prevent it, as Render's own example shows. Validation should accept the reference and treat the value as "provided at creation". At create the copy takes the answered value, or an empty string if the prompt was left blank, as Render's prompt flow allows.

## Root cause

`lego/backend/internal/apps/deploy.go` `knownServiceEnv` (`:2501–2550`) deletes every `promptKeys` entry (`sync: false`) from `known` unless it was answered (`seedLiterals`). `resolveRef` (`:3170–3190`) then refuses the copy. Its own comment says the target may be "a plain literal or sync:false var", so the validate path contradicts the documented intent.

## Fix

Mark unanswered prompt keys as deferred-known, just as `generated` keys are deferred until the apply mints them (w1/m175). `resolveRef` then accepts them at validate/plan time and emits a plan note ("copies the value you enter for `SHARED_TOKEN`"). At create the copy takes the answered value; an unanswered prompt copies `""`, matching Render's blank-prompt behavior.

## Acceptance

- Compiler tests: the manifest above validates, flat and nested. With `envVarValues: {SHARED_TOKEN: x}` the consumer's `spec.Env` has `x`; without it, `""`. A reference to a key that is not declared at all still fails with the current message.
- Live after deploy: `bex blueprints validate` on the manifest above and on `render-examples/AEO-analytics/render.yaml` no longer reports the `plainly-defined` error for the `sync: false` copies.

## Dedupe

w8/155 is the same error path, but its case is Render default variables (`RENDER_EXTERNAL_URL`), not `sync: false` sources; the two fix different branches of `resolveRef`. w1/m175 covers deferred `generateValue` copies. No item covers prompted sources.
