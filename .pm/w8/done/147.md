# Bex sends no `RateLimit-*` headers, which Render now specifies on every response; ADR018's “parity-by-absence” is stale

Why: Render's current API reference and the OpenAPI document Bex itself validates against (`render-public-api-1.json`, pinned 2026-09-11) say that responses carry `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset`, and that 429s carry them alongside `Retry-After`. Bex sends only `Retry-After`, on 429. API clients that pace themselves on the remaining quota get no signal and only learn about the limit by being refused. ADR018 still records this as verified parity.

**Severity:** minor. **Attribution:** server (API middleware) and docs. **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1252, 2026-10-20 ([evidence](evidence/cli-sweep1252/README.md)).

## Observed

- `GET https://api.bex.co/v1/services?limit=1&ownerId=<bex-canary>` with the CLI's User-Agent → 200. Headers: `Content-Type`, `content-security-policy`, `strict-transport-security`, `x-content-type-options`, `x-frame-options`, `vary`, plus Cloudflare's own. No `RateLimit-*` header.
- `lego/backend/internal/api/ratelimit.go:95–106` sets only `Retry-After` and only on the refused path (`writeTooManyRequests`, `:143`). The successful path calls `next.ServeHTTP` with no header. The deploy-hook limiter (`deploys/deployhook.go:356`) has the same shape.

## Expected (Render)

- [api-docs.render.com/reference/rate-limiting](https://api-docs.render.com/reference/rate-limiting), read 2026-10-20: “Three rate limit headers are returned with every request: `Ratelimit-Limit` … `Ratelimit-Remaining` … `Ratelimit-Reset`”, with per-endpoint budgets (for example 400 GETs/min, 30 writes/min, 30 log reads/min).
- Pinned spec `lego/backend/internal/api/openapi/render-public-api-1.json`, `components.responses.429RateLimit`: headers `Retry-After`, `RateLimit-Limit`, `RateLimit-Remaining` (“Always `0` for this response”) and `RateLimit-Reset` (“Seconds until the current rate limit window resets”). Its description adds: “Rate-limited endpoints also return `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` on successful responses so clients can track their remaining quota.”
- The pinned CLI's generated client binds these headers on 429s (`pkg/client/client_gen.go:57156–57175`).

## Root cause

w7/m34 (2026-07-15) concluded “parity-by-absence” from an older spec copy (`testdata/render-openapi.json`, no 429 objects) and a docs paraphrase. ADR018's “Rate limits” row and `docs/render-artifacts/rate-limit-headers.md` still say “Render sends no `RateLimit-*` headers”, which the 2026-09-11 pin and the live reference contradict.

## Fix

In the shared limiter, emit `RateLimit-Limit` (the bucket's per-window allowance), `RateLimit-Remaining` (whole tokens left after this request's reservation) and `RateLimit-Reset` (seconds until the bucket is full again) on every response it admits. On a 429, send the same three headers alongside `Retry-After`, with Remaining `0`. Do the same in the deploy-hook limiter. Correct ADR018's row and the rate-limit artifact. Keep the existing budgets; Render's per-endpoint numbers are not adopted by this item.

## Acceptance

- Unit: an admitted request carries all three headers with Remaining decreasing across calls; a refused request carries `Retry-After` plus Remaining `0`. GraphQL and MCP responses behind the same middleware match.
- Live after deploy: `curl -sD- https://api.bex.co/v1/services?limit=1 -H 'Authorization: Bearer <token>'` shows the three headers.

## Dedupe

w7/done/m34 is the earlier capture this note supersedes (it was correct for its older spec copy). No open item covers `RateLimit-*` headers.
