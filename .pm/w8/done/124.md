# qa-login.sh --login-challenge fails when the seeded session needs no refresh

Why: the CLI QA loops approve `bex login` device requests with `scripts/qa-login.sh --login-challenge … --cookie-jar <session jar>`. On a second login in the same Kratos session, the helper exits with an error instead of approving, so a long loop has to work around it by hand each time it re-authenticates.

Seen in the `/qa-find-bugs-cli` solo loop, 2026-10-19 ~03:58 UTC, against production:

- The first device login of the run worked through the helper. With a seconds-old seeded session, Kratos answered the challenge-bound `GET /self-service/login/browser?login_challenge=…` (JSON) with a `200` refresh flow (`1010003`), and the helper submitted the password.
- A later device login on the same session (about 45 minutes after its last authentication) failed:

  ```text
  error: OAuth login did not reach the device success page (HTTP 400; endpoint Kratos /self-service/login/browser; query keys: login_challenge, return_to)
  ```

  The same JSON request answers `400 {"id":"session_already_available","reason":"A valid session was detected and thus login is not possible. Did you forget to set ?refresh=true?"}`. The helper only handles the JSON `null` body (`scripts/qa-login.sh:446-449`) and the refresh flow, so it gives up.
- Workaround that worked: pass a copy of the jar with the `ory_kratos_session` line removed (Hydra's CSRF cookie kept). Kratos then shows a normal password flow, the helper completes it, and `bex login` succeeds. This mints an extra Kratos session that also has to be revoked.

The product already handles this: the dashboard's `dashboard/src/common/hooks/use-ory-flow.ts:281-292` answers `session_already_available` plus a challenge by sending the browser straight back to Kratos with no form.

Fix: make the helper do the same. On a `400` whose JSON `id` is `session_already_available` while a login challenge is set, re-issue the bootstrap as a browser-shaped request (no `Accept: application/json`) and follow its redirect through `complete_device_login`, exactly as the JSON-`null` branch already does. It is unverified that Kratos's browser answer is the provider redirect in this case; confirm that first.

Acceptance:

- Approve two `bex login` device requests, about an hour apart, with the same seeded jar. Both reach the device success page without stripping the session cookie, and no extra Kratos session is minted.
- The existing first-login and refresh-flow paths are unchanged.

Estimate: ~20m (tooling only; no product change).
