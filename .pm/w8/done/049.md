# 049 — Postgres and Key Value accept another resource's ID as their name (`srv-…`, `dpg-…`), which services refuse since w8/034

Why: w8/034 reserved resource-ID lookalike names for service display names (`DISPLAY_NAME_RESOURCE_ID_RESERVED`), but the two datastore families still accept them on rename (and create). An ID-shaped name makes a selector ambiguous between "this ID" and "the thing named this".

Severity: minor. Attribution: server (`lego/backend/internal/postgres`, `lego/backend/internal/keyvalue`).

## Evidence (2026-10-04, `/qa-find-bugs-cli` w8 loop, sweep 2)

Production, `bex v0.2.1`, workspace `bex-canary`. Fixture: free Postgres `qa-20261004-3d35c5-pg` (`dpg-db1eb9ga8tcs73b1a0o0`, deleted).

```text
$ bex postgres update dpg-db1eb9ga8tcs73b1a0o0 --name srv-db1e4vnhb1uc73ebifi0 --confirm -o json   # another live resource's ID
exit 0 → name "srv-db1e4vnhb1uc73ebifi0"
$ bex postgres update dpg-db1eb9ga8tcs73b1a0o0 --name dpg-zzzzzzzzzzzzzzzzzzzz --confirm -o json
exit 0 → name "dpg-zzzzzzzzzzzzzzzzzzzz"
$ bex postgres get dpg-zzzzzzzzzzzzzzzzzzzz -o json      # resolves by name to dpg-db1eb9ga8tcs73b1a0o0
```

Controls in the same run: control characters, 300 characters and blank names are refused with `400 … at most 30 characters …`, and a normal rename succeeds.

## Mechanism

- `lego/backend/internal/postgres/service.go:293` `validateDatabaseName` and `lego/backend/internal/keyvalue/service.go:215` `validateKeyValueName` check only `ValidDatabaseName`, a DNS-label shape of at most 30 characters, which every `xxx-<20 lowercase alnum>` ID satisfies.
- The reserved-shape check lives only in the service rename path: `lego/backend/internal/apps/service.go:4463` (`ids.LooksLikeResourceID`, `lego/backend/internal/id/id.go:235`).
- The Blueprint datastore path (`lego/backend/internal/apps/deploy.go:2414`) has the same gap.

## Fix

Call `ids.LooksLikeResourceID` from `validateDatabaseName` and `validateKeyValueName`, on both create and update, and in the Blueprint database/keyValue parse. Return a named 400 reusing `DISPLAY_NAME_RESOURCE_ID_RESERVED` (or a datastore sibling code). Existing datastores with such names keep working; only new writes are refused. Check whether the Postgres name doubles as a physical identifier anywhere (CR name, `databaseName` default) before reusing the service code verbatim.

## Acceptance

- [ ] `bex postgres update <dpg> --name srv-<20>` and `bex keyvalues update <red> --name dpg-<20>` exit 1 with the named 400. The same applies to `postgres create --name red-<20>` / `keyvalues create --name srv-<20>` and a Blueprint `databases[].name: dpg-<20>`.
- [ ] Controls: an ordinary rename/create still succeeds. GraphQL/MCP rename paths return the same refusal.

## Dedupe

`rg -i 'LooksLikeResourceID|RESOURCE_ID_RESERVED' .pm` matches only w8/034, which scoped the fix to services.

Estimate: ~35m.

Done 2026-10-04 (loopx). `validateDatabaseName` and `validateKeyValueName` now refuse an ID-shaped name (`id.LooksLikeResourceID`) with a coded 400, `NAME_RESOURCE_ID_RESERVED` (`core.NameResourceIDReservedError`). Those two validators cover create, rename (REST/GraphQL/MCP) and Postgres recovery. Blueprint `parseDatabase` and `parseKeyValue` refuse the same shape with the same code. A sibling code is used rather than `DISPLAY_NAME_…`, because the field is `name`. The Postgres `name` is display-only: the CR name is a minted `dpg-` id and `databaseName` is separate. Existing ID-shaped datastores keep working, but a rename or a Blueprint re-sync that keeps such a name is now refused. Tests cover both validators (ID shapes refused, near-misses accepted), a create per kind, and both Blueprint parsers. The backend suite and `make lint` are green. Not live-replayed.
