## Objective

Make the collector's correctness contract explicit before refactoring it: zero is a valid measured quantity, source failure is not zero, and each App meter advances only through a contiguous sequence of successfully persisted windows.

## Context

- `lego/backend/internal/usage/service.go` currently returns plain `int64` from App meter queries, logs failures as zero, persists only positive egress/build values, and uses only the `instance_seconds` latest row for App catch-up.
- `usage_hourly` is already keyed independently by meter kind, so no schema change is needed.
- `w8/001` needs provable coverage before it can choose or enforce caps.

## Steps

1. Specify success versus failure at the query and persistence seams.
2. Specify per-meter cursor behavior, the existing 48-hour bound, and healthy-meter independence.
3. Map the contract to concrete tests before implementation.

## Acceptance criteria

- [ ] The implementation contract distinguishes a successful zero from an unavailable source.
- [ ] Each meter's cursor advances only after its row persists and stops at the first failed window.
- [ ] A failure in one meter does not prevent other meters from advancing.

## Out of scope

- Cap values, emails, suspension/build blocking, or expanding HTTP-response egress into full outbound accounting.
