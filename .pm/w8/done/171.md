# `RENDER_CPU_COUNT` is rounded up to a whole number (free and starter both report `1`), where Render reports the plan's CPU, e.g. `"0.5"`

Why: w5/m148 injects Render's default variables, and `RENDER_CPU_COUNT` is computed as `max(1, ceil(plan CPUs))`. Render documents the value as "The service's CPU count, based on its compute plan", with the example `"0.5"` or `"2"`. A starter service (`0.5c-512mb`) therefore reads `1` on bex and `0.5` on Render, and a free service reads `1` where its plan gives it a fraction of a core. Apps that size worker pools or thread counts from this variable over-provision on bex's small plans.

**Severity:** minor. **Attribution:** platform runtime (`renderenv.PlanCPUCount`). **Estimate:** 20m. **Source:** `/qa-find-bugs-cli` sweep 1290, 2026-10-21 ([evidence](evidence/cli-sweep1290/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `4b6687b5bc18`, bex-canary. A free `python:3.12-alpine` web service printed its environment (`srv-dbccs7159hnc73e5ho6g`, deleted 204 → 404): `RENDER_CPU_COUNT=1`, `RENDER_WEB_CONCURRENCY=1`, `WEB_CONCURRENCY=1`, and `os.cpu_count()=4` (the node's). The rest of the set was correct: `RENDER=true`, `RENDER_SERVICE_ID`, `RENDER_SERVICE_NAME`, `RENDER_SERVICE_TYPE=web`, `RENDER_EXTERNAL_HOSTNAME`/`URL`, and `RENDER_DISCOVERY_SERVICE` (`<name>-discovery`, which resolves to the pod IP). `RENDER_INSTANCE_ID` is the raw pod name, already w4/386.

## Expected

[Render default environment variables](https://render.com/docs/environment-variables): `RENDER_CPU_COUNT` is "The service's CPU count, based on its compute plan", with examples `"0.5"` and `"2"`. Target: emit the plan's CPU as a decimal string (`0.5` for starter/`0.5c-512mb`, `1` for standard/`1c-2g`, `2` for `2c-4g`, and the free plan's actual share). Keep `RENDER_WEB_CONCURRENCY`/`WEB_CONCURRENCY` as Render's recommended integer, which is where rounding belongs.

## Root cause

`lego/types/renderenv/renderenv.go:109–118`: `PlanCPUCount` returns `max(1, int(q.Value()))`, and `Value()` rounds 500m up to 1. The same integer feeds both `RENDER_CPU_COUNT` and the web concurrency (`:145–171`). The comment's "like Render's smallest plans" contradicts Render's documented `"0.5"` example.

## Fix

Split the two values. `RENDER_CPU_COUNT` = the plan's CPU quantity formatted as a decimal string (trim trailing zeros: `0.5`, `1`, `2`). Concurrency keeps `max(1, ceil(cpu))`, or Render's recommendation if a formula is documented. Update the renderenv tests and the ADR018 row from w5/m148.

## Acceptance

- Unit table: free → its fraction; `0.5c-512mb` → `0.5`; `1c-2g` → `1`; `2c-4g` → `2`. Concurrency stays an integer ≥ 1.
- Live after deploy: the probe above prints the decimal value for a free service, and for a starter service if a paid fixture is ever authorized. Delete by ID with a 404 proof.

## Dedupe

w5/m148 (introduced the variables), w4/386 (`RENDER_INSTANCE_ID` format). No item covers the CPU count's format.

**Done 2026-10-21:** `renderenv.PlanCPUs` formats the tier's CPU quantity (`0.5`, `1`, `2`); web concurrency keeps `PlanCPUCount`'s rounded-up integer; `TestPlanCPUsIsTheDecimalPlanQuantity`; ADR018 updated. Changing the variable's value rolls pods of services on fractional plans on the next release. Live acceptance after deploy.
