# `POST /blueprints` answers every fetch failure with a bare 500, hiding its own classified reason

Why: connecting a Blueprint is the front door of the git-connected flow, and its most common failures — typo'd repo, wrong branch, missing manifest, bad path, GitHub-app access missing — all currently read as `{"error":"internal error"}` in production, even though the codebase already classifies each one into a stable reason code with a user-safe sentence one function away. The dashboard preview shows the real reason; the create that follows it says "internal error".

Seen in the `/qa-find-bugs-cli` loop sweep 574, 2026-10-19, production, `bex-canary` (no fixture: every probe is refused/fails before admission; the registry still holds only the pre-existing `bex` blueprint):

- `POST /v1/blueprints` → `500 {"error":"internal error","id":"internal_error"}` for **all** of: repo `not-a-url`, `ftp://…`, nonexistent GitHub repo, nonexistent branch (`qa574-nope-branch`), missing file (`nope/render.yaml`), wrong extension (`render.txt`), path escape (`../render.yaml`), ssh-form repo, and the would-be-conflict input (dies at fetch first — `bex-co/bex@main` has no root `render.yaml`).
- The same inputs through `POST /v1/blueprints/preview` → `200 {found:false, reason, error}` with precise coded reasons: `invalid_path` ("repo URL … is not an owner/repo URL", "Blueprint path must be a .yaml or .yml file", "… clean repository-relative path"), `repo_not_found_or_no_access`, `branch_not_found`, `file_not_found`. Same backend, same classifier, same afternoon.
- Inputs that never reach the fetch behave correctly: missing repo/branch → named 400; synthetic `ownerId` → 403.

Root cause: `CreateBlueprint` returns the sync-history adapter as its HTTP error. `blueprintFetchFailure` (`lego/backend/internal/apps/blueprint.go:439`) formats `"<reason>: <sentence>"` as a **plain `fmt.Errorf` with no sentinel** — by design for `blueprint_syncs.error_message` (w2/m97 t003; the three `failSync` call sites at :1398/:1408/:1412 are correct). Its fourth call site, `CreateBlueprint` at `:1085`, returns that error up to `core.WriteErr`, which finds no `ErrBadRequest`/`ErrUnavailable`/coded error, classifies it unclassified-500, and deliberately suppresses the text (`core/http.go:310-316`). So the classified, user-safe message is built and then thrown away. w2/m97's README even records that "CreateBlueprint's initial fetch … route[s] through the same blueprintFetchFailure" — the sharing is intentional for the *classification*; the HTTP status mapping was never added for the create surface.

Fix (~30m): give the create path a reason→error mapping instead of reusing the history-string adapter as the HTTP error. Keep `failSync` call sites untouched. Suggested mapping, mirroring the reasons' own semantics: `invalid_path`, `ambiguous_filename`, `branch_not_found`, `file_not_found`, `repo_not_found_or_no_access`, `access_denied` → 400 (the caller's repo/branch/path/access state; a `core.CodedError` carrying the reason as `code` keeps it machine-keyable); `rate_limited`, `unavailable` → `core.ErrUnavailable` (503). Preserve the human sentence either way — it is already built from caller inputs only (no upstream vocabulary, no SHA, per the classifier's contract). Add handler/service tests beside the existing preview fetch-failure tests: create with a nonexistent repo and with an invalid path must not be 500 and must carry the reason; a rate-limited fake must be 503.

Acceptance:

- `POST /blueprints` with the probe set above returns the classified reason + sentence at a 4xx/503 status as mapped — never bare `internal error` for a fetch-classified failure.
- Preview and sync-history behavior byte-unchanged (same reason strings in `error_message`).
- A successful create path (fetch OK) is unaffected; the already-connected 409 keeps its shape.

Severity: moderate-minor — no wrong state (fetch precedes admission; nothing was created by any probe), but the primary Blueprint-connect failure surface is undiagnosable from the API today. Estimate: ~30m.

**Done (2026-10-19, `ca30db3a3`, live after pin `ca30db3a3646`):** live on production: `POST /blueprints` with a nonexistent repo → `400` with `code: "repo_not_found_or_no_access"` and its sentence; with a missing manifest path on a real repo → `400` `code: "file_not_found"` naming the path and branch. The blueprint list still holds only the pre-existing `bex` blueprint; nothing was created by the probes.
