# A Node release with no image in its line's Debian variant (16.13.2 has `-bullseye`, not `-bookworm`) falls back to the line's patch, and a companion Node ignores exact versions and ranges

Why: w8/175 (exact versions) and w8/307 (ranges) pin a Node release only through the official image of the line's own variant, `node:<release>-bookworm` for Node 16, 18 and 20. Docker Hub has bookworm images only for Node 16.20.x and 18.16+. So an older pin or range keeps the line's patch, and the build log says so:

- `NODE_VERSION=16.13.2`;
- `~16.13.0`, as in `render-examples/strapiconf2022-workshop-strapi`.

Render installs those releases. Docker Hub does have `node:16.13.2-bullseye`, and line 14 already builds on bullseye.

Separately, a Python or Ruby service whose build adds Node as a companion (`resolveNativeCompanion`) takes the line's patch whatever its `NODE_VERSION` asks. Companions skip `pinNativePrimary` while `nativeCommonBase` is empty.

**Severity:** minor (the build log already names the substitution since w8/307). **Attribution:** platform build (native version selection). **Estimate:** ~2–4h, plus a decision. **Source:** the /simplify review of w8/307, 2026-11-13, with live Docker Hub tag listings.

## Options

1. **Fall back to another variant.** When the line's variant has no image of the release, fall back to the newest older Debian variant that has one (bookworm, then bullseye). This changes the base OS of that one build (glibc, system libraries), which the build log should name.
2. **Build the release from source.** Install it on the line's own variant from the nodejs.org source tarball, using the backport path `commonNodeBuildStage` already has (checksum through `NodeSourceDigest`). It is slower but keeps the base OS.
3. **Companion Node.** Route its choice through `pinExactVersion`, so exact versions and ranges apply to it as to a primary.

## Dedupe

- w8/175 and w8/307 (done) cover the primary only, and only images of the line's variant.
- No `.pm` item covers a missing variant or companion versions.

## Resolution

**DONE 2026-11-13: option 3. Options 1 and 2 moved to w8/309.**

- **Companion Node:** a Node companion (Python, Ruby, Go, Rust and Elixir services) now goes through `pinExactVersion` (`lego/operator/internal/build/nativecommon.go`). It takes an exact version or a range like a primary does. `TestNodeCompanionTakesTheExactRelease` fails without it.
- **Option 1, the bullseye fallback, was implemented and then withdrawn after review:**
  - Debian 11 LTS ended on 2026-08-31, and Render builds on a current base.
  - Releases older than bookworm's include Node 18.0–18.11, where bex's pnpm 10 (which needs 18.12 or newer) would fail builds that succeed today.
  - The companion's node-gyp patch (`prepare-node14-tools.py`) has been verified only on the reviewed npm.
- **Option 2 was rejected:** the backport stage compiles Node from source, which is too slow for routine builds.
- **What w8/309 covers:** copying the release's Node onto the line's bookworm image, with the pnpm and node-gyp handling those releases need. Until then, such a release keeps the reviewed patch and the log names it.
- **Docs:** ADR060 D7 records it.
- **Production check after the next roll:** a Python service with `NODE_VERSION=18.17.1` logs Node 18.17.1 for its companion.

**Production check passed 2026-11-13 (sweep `3fce`, pin `1c4d721bc`).** A free Python web service from `render-examples/flask-hello-world` with `NODE_VERSION=18.17.1` logged `==> Using Node 18.17.1 (from NODE_VERSION=18.17.1)` beside `Using Python 3.14.8 (default)`. Its build command's `node -v` printed `v18.17.1`, and the service went live. Deleted (GET 404).
