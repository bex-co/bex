# A Blueprint with `dockerContext: ./` is refused ("must not contain an empty path segment"), so two of Render's one-click templates cannot be imported

Why: bex refuses any `dockerContext` that ends in `/`. `./`, `backend/` and `./backend/` all fail with `dockerContext must not contain an empty path segment (// or a trailing /)`, while `.`, `./backend` and `/` pass. Render's schema types `dockerContext` as a plain string ("The Docker build-context directory, relative to rootDir. Defaults to rootDir"). Two Render templates that their READMEs present as "pre-configured for one-click deployment to Render using the included `render.yaml`" write `dockerContext: ./`:

- `render-examples/RAG-chatbot-template`
- `render-examples/web-research-agent-template`

On bex both fail validation and planning. The same spelling of the same directory is already accepted for `rootDir` (w8/165 normalizes `./`, `server/` and `a//b`) and for `staticPublishPath` (a template's `./build/` validates). `dockerContext` alone is checked as typed.

**Severity:** minor. Hand-editing the file works around it, and the error names the rule. But it blocks importing those Render templates unchanged, and `./` is the most common way to write "the root". **Attribution:** server (bex-api path rule). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `f75b`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `ca7fbbe606c8`.

## Evidence

Corpus: the root `render.yaml` of every non-archived `render-examples` repository (229 repos, 174 with a Blueprint, fetched 2026-11-12). Each file was checked with `bex blueprints validate <file> -o json`: 151 passed and 23 failed. Two of the failures are this rule and nothing else:

```text
RAG-chatbot-template        services[0] (line 7), services[1] (line 71): dockerContext must not contain an empty path segment (// or a trailing /)
web-research-agent-template services[0] (line 9), services[1] (line 37): same
```

Both files declare `runtime: docker`, `dockerfilePath: ./backend/Dockerfile` (or `./frontend/Dockerfile`) and `dockerContext: ./`.

A minimal file isolates the rule (`type: web`, `runtime: docker`, `plan: free`, `repo: https://github.com/render-examples/express-hello-world`, `dockerfilePath: ./Dockerfile`, only `dockerContext` varied). Each run was `bex blueprints validate f.yaml -o json`:

| `dockerContext` | `valid` | exit |
| --------------- | ------- | ---- |
| `./`            | false   | 1    |
| `./backend/`    | false   | 1    |
| `backend/`      | false   | 1    |
| `/backend/`     | false   | 1    |
| `.`             | true    | 0    |
| `./backend`     | true    | 0    |
| `/`             | true    | 0    |

The customer journey: `bex ea blueprints create --repo https://github.com/render-examples/RAG-chatbot-template --name qa-20261112-f75b-ctx --auto-sync=false -o json` exited 1 in 1.6 s.

- **Result:** `planningOutcome: "failed"`, sync `state: "error"`.
- **Notices:** two with `severity: "error"` and the message above.
- **Locator:** each notice points at the service entry (`projects[0].environments[0].services[0]`, line 7, column 13), not at the `dockerContext` line (line 13).
- **Cleanup:** no resource was created. Blueprint `exs-dbqugisdhgcs73ao03r0` was deleted (204, then 404).

## Root cause

- `lego/backend/internal/store/api.go:697-719`: `RootDirProblem` refuses an empty path segment, so any value ending in `/` is refused.
- `lego/backend/internal/store/api.go:728-743`: `NormalizeRootDir` maps `./`, `server/` and `a//b` to one stored form (w8/165).
  - Create normalizes `rootDir` with it before the check (`apps/service.go:2118`), and so does the Blueprint compiler (`apps/deploy.go:3000`).
- `dockerContext` is never normalized:
  - **Blueprint:** `apps/deploy.go:3003` passes `repoRootRelative(a.DockerContext)` unchanged.
  - **Create:** `apps/service.go:3438` calls `checkDockerContextPath`.
  - **Update:** `apps/settings_check.go:255-256` calls `checkDockerContext`.
  - All three reach `apps/docker_context.go:119-124` (`checkDockerContextPath`), which applies `RootDirProblem` to the raw value.
- `dashboard/src/features/services/lib/build-settings-validation.ts:21-41` mirrors this. `relativePathError` judges "the Dockerfile Path and the Docker Build Context … as typed", so the Settings row refuses `./` too.
- The rule has been in place since w8/m128 moved `dockerContext` onto `checkDockerContextPath` (2026-10-20). w21/045 only gave the refusal its current sentence.

## Fix

Normalize `dockerContext` the way `rootDir` already is, then apply the path rule to the normalized value. `./`, `.` and the empty string all mean "rootDir itself", and `backend/` means `backend`.

- **Normalize first:** in `checkDockerContextPath`'s callers, run the value through `store.NormalizeRootDir`, after `repoRootRelative` on the Blueprint path. That covers the Blueprint compiler (`deploy.go:3003`), create (`service.go` create request) and update (`settings_check.go:checkDockerContext`).
  - `storedDockerContext(rootDir, "")` already stores the default.
  - `..`, absolute, backslash and control-character values stay refused by `RootDirProblem` exactly as today.
- **Dashboard:** judge Docker Build Context after the same normalization (`rootDirError`'s shape) and keep the Go and TS vectors pinned together.
- **Locator:** while there, put the Blueprint refusal on `…services[N].dockerContext` with that line, as `routes[N].destination` and other per-field refusals are, not on the service entry.
- **`dockerfilePath`:** leave it as is. It names a file, so a trailing `/` is a real error.

## Blast radius

- **Write surfaces:** every surface that writes `dockerContext` on a Dockerfile-built service or build source:
  - Blueprint validate, preview, create and sync, through REST multipart, GraphQL and MCP;
  - `POST /v1/services`;
  - `PATCH /v1/services/{id}`;
  - the dashboard forms that use `build-settings-validation.ts`.
- **CLI:** the pinned CLI has no `dockerContext` flag, so only `blueprints validate` and `ea blueprints` reach it from the CLI.
- **Unchanged:** stored values. `wireDockerContext` keeps reporting `.` for the default.

## Regression checks

- **Go table test:** `checkDockerContextPath` (or its callers) accepts `./`, `backend/`, `./backend/` and `a//b`, storing `""`, `backend`, `backend` and `a/b` relative to `rootDir`. It still refuses `../x`, `a/../b`, a backslash and a control character with today's sentences.
- **Blueprint validate:** valid for the two templates' files and for the minimal `./` file. An invalid context is located at the `dockerContext` key's line.
- **Dashboard vectors:** the TS tests mirror the same vectors.
- **Corpus guard:** `TestRenderExamplesCorpus` (opt-in, `BEX_RENDER_EXAMPLES_DIR`) run over a current `scripts/render-examples-corpus.sh` fetch. Both templates pass. This rule is not in its excuse lists, so the guard would have caught the refusal had it been run since these templates appeared.
- **Production:** the f75b table, where every row validates except a `..` control. Also `bex ea blueprints create --repo https://github.com/render-examples/RAG-chatbot-template --auto-sync=false` plans with no error notice; delete the Blueprint without approving it.

## Unverified

- Render's own answer to `./` was not observed directly; there is no Render account here. The evidence is the two templates Render publishes for one-click deploy and the schema's untyped string. Render's prose docs give no `dockerContext` example.

## Dedupe

- w8/150 (done) and w8/m128 (done): `dockerContext` is relative to `rootDir`; they changed its meaning, not its spelling.
- w8/165 (done): normalized `rootDir` only.
- w21/045 (done): named the rule's sentence.
- w8/215 (done): an earlier template corpus run (2026-10-28), whose tally does not list this refusal.
- No `.pm` item covers a trailing `/` on `dockerContext`.
