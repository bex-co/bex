# The PG 16/17/18 operand gate crashes Postgres after every extension is created

Why: `pg-operand-image` has been red on main since it was added (2026-10-31), so no per-major operand image (ADR092) can qualify, and m92/t008 cannot finish even once upstream unblocks the ordinary-owner restore.

- **Evidence:** run 42019084199 (`4bff00118`, 2026-11-05). After `acde09993` made `deploy/pg-operand/check.sh` create `timescaledb` before `pg_duckdb` (the `time_bucket` clash, duckdb/pg_duckdb#934, now a `WARNING`), jobs 16/17/18 create all eight extensions (`timescaledb`, the four PostGIS ones, `pg_partman`, `pg_ivm`, `pg_duckdb`) and the next statement fails with `server closed the connection unexpectedly … the server terminated abnormally` (exit 2). PG 13/14/15 get past it and stop, as intended, at the fatal ordinary-owner restore check (m92/t008, upstream-blocked).
- **Look at:** the server log inside the check container for 16–18 (`check.sh` keeps it under the data dir; print it on failure), whether the crash is `pg_duckdb` initialising with TimescaleDB loaded, a `shared_preload_libraries` ordering issue, or memory under amd64 emulation on the ARM64 build runners (the bex-build pool now has 12 CPUs / 24 GB, previously 4 / 8). Reproduce locally with the pushed digest: `docker run --platform linux/amd64 … deploy/pg-operand/check.sh <major> <allowlist>`.
- **Expected:** PG 16/17/18 reach the same ordinary-owner restore gate as 13/14/15; any extension combination that cannot coexist is either fixed in the image or recorded as a customer-facing limitation in ADR092.
- **Customer note:** on PG 16+ a customer who creates `pg_duckdb` before `timescaledb` hits the same `time_bucket` error; document it (ADR092 / ADR018) or make the image tolerate either order.
- **Do not:** make the ordinary-owner restore check non-fatal or drop the workflow's push trigger to get main green; both waive m92/t008's acceptance gate (`.pm/DO_NOT_DO.md`) and need a user decision.

**DONE 2026-11-06** (`/loopx w8`): the crash was not memory, emulation or preload order. Reproduced on the published PG16 arm64 digest (`sha256:61599a12…`) under the gate's 256m cgroup: the segfault hits the forced DuckDB scan `SELECT sum(v) FROM duck_values`, after the PostGIS/pg_ivm checks pass. Bisect: pg_duckdb alone, TimescaleDB preloaded but not created, and the Free memory/thread limits all pass; it only crashes with **both extensions created in one database**. gdb: `ts_classify_relation` ← `standard_planner` ← `pgduckdb::PostgresTableReader::InitUnsafe`, i.e. upstream [duckdb/pg_duckdb#845](https://github.com/duckdb/pg_duckdb/issues/845) (open since 2025-06).

- `deploy/pg-operand/check.sh` runs DuckDB execution (the forced scan, the non-role refusal and the two concurrent scans) in its own `duckdb_scans` database without TimescaleDB. Locally, PG16 now passes everything up to the ordinary-owner restore gate and fails there, exactly as 13–15 do. That gate stays fatal. PG 17/18 use the same pg_duckdb/TimescaleDB pairing; their confirmation is the next `pg-operand-image` run.
- `TestApplicationDatabaseExtensionsOnCNPG` (operator, live-cluster only) had the same pairing. It now runs its DuckDB step before TimescaleDB exists and drops pg_duckdb afterwards.
- ADR092 D3 now records the customer-facing limitation and the creation-order effect (pg_duckdb first makes TimescaleDB's install fail on `time_bucket`, duckdb/pg_duckdb#934).
- The fix itself (an upstream release, or a patched pg_duckdb in the image) is filed as w8/236.
