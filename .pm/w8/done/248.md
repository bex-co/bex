# Sandbox list and get answer `500 internal error` for minutes while a production deploy rolls out

Why: during the 2026-11-11 05:21 UTC deploy, `bex sandboxes list` and `GET /v1/sandboxes/{id}` failed with a bare `500 internal error` in every workspace for at least three minutes, while services and sandbox groups kept answering. A scheduled deploy should not take the sandbox API down, and when the sandbox runtime really is unreachable the answer should say so and be retryable.

**Severity:** major (a core sandbox read is unavailable on every deploy that restarts the runtime; the error names nothing). **Attribution:** server + infrastructure; the infrastructure half is unverified. **Estimate:** ~60m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `5e80`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, QA human device login.

## Evidence

## Analysis

- **Error mapping (verified in code):** `lego/backend/internal/sandbox/service.go:1305-1308` returns `s.Client.List`'s error as is, and `client.go:131-160,217-235` returns the transport error or `opensandbox list: status N` unwrapped. Neither is a `core` error, so REST answers `500 internal_error`. `core.ErrSandboxesUnavailable` (`core/errors.go:109`, a 503) is used only when the runtime is not configured. `Get` follows the same path (`client.go:200-211`).
- **Why the runtime was unreachable (unverified, no cluster access):** `deploy/opensandbox/server-in-cluster.yaml:82-84` runs `opensandbox-server` as `replicas: 1` with `strategy: Recreate`, so every rollout of it has a window with no server. The 200/500 alternation for about a minute after recovery suggests the server restarted more than once or was not ready when it started receiving traffic. Confirm with the pod's events and bex-api's logs for 05:21–05:26 UTC.
- **Not checked:** create, exec and stop during the window (no sandbox was running), GraphQL and MCP (same service methods, so presumably the same), whether running sandboxes survived (none existed).

## Fix

1. Map an unreachable or 5xx OpenSandbox answer on list/get/create/stop/exec to a named, retryable error: `503` with `Retry-After` and a code such as `SANDBOX_RUNTIME_UNAVAILABLE`, message "the sandbox runtime is restarting; retry in a few seconds". Keep 404/409 mappings as they are. Same on GraphQL (`extensions.code`) and MCP.
2. Close the rollout gap, after confirming the cause: a readiness-gated rolling update or a second replica for `opensandbox-server` if it can run two, or else a deploy step that waits for readiness before the pipeline reports success, plus bex-api retrying an idempotent read once or twice within the request deadline.
3. Add a sandbox-list probe to the post-deploy checks so a deploy that leaves the route failing is caught.

## Acceptance

- With `opensandbox-server` scaled to zero on a dev cluster, `bex sandboxes list` prints the named 503, not `500: internal error`; scaled back, it answers within seconds.
- During a production deploy that restarts `opensandbox-server`, a 5-second poll of `GET /v1/sandboxes` shows no 500, and either no failure at all or only the named 503 for a window recorded in the note.
- A unit test drives `Service.List`/`Get` against a refusing and a 502-answering runtime and asserts the 503 code.

## Dedupe

No `.pm` item covers sandbox routes failing during a deploy. w32/006 (done) made list read rules concurrently; w3/m318 (done) keeps terminated sandboxes readable; neither touches runtime unavailability.
