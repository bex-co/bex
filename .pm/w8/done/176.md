# `bex logs --text 'GET*200'` and every `/regex/` search return nothing: Render's log filters accept `*` wildcards and RE2 regex, bex's `text` is literal-only and no filter takes regex

Why: Render's pinned API documents every log filter (`text`, `path`, `host`, `method`, `statusCode`, `level`) with "[Wildcards and regex](https://render.com/docs/logging#wildcards-and-regular-expressions) are supported". Its docs give `foo*bar`, `/foo.*bar/`, `status_code:/4../` and `method:/(GET|POST)/` as examples. On bex a wildcard or regex `--text` search, and a regex in any structured filter, is matched as literal characters. It returns an empty result with exit 0, so a script or agent concludes "no such log lines" when the lines exist. ADR010:196 records "text is literal" as a divergence without a user sign-off. ADR018's logs row says "`*` wildcards honored", which is not true for `text`.

**Severity:** minor (silent empty results for documented queries; workaround: several literal `--text` values, which are ORed). **Attribution:** server (log query translation). **Estimate:** 1h30m. **Source:** `/qa-find-bugs-cli` sweep 1310, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1310--log-search-wildcards-and-regex)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`, HEAD-built pinned CLI. Owned free service `srv-dbcocsou12fs73e9aid0` (the sweep 1309 sleep fixture) (`python -m http.server 10000`) whose app log holds exactly one access line, `10.244.36.215 - - [22/Oct/2026 03:44:30] "GET / HTTP/1.1" 200 -`, and whose request log holds one `GET /`. Counts of matching entries from `bex logs -r <id> --limit 50 -o json`:

| Filter | Render semantics | bex |
| --- | --- | --- |
| `--type app --text 'HTTP/1.1'` | literal | 1 |
| `--type app --text 'GET*200'` | wildcard: GET … 200 | **0** |
| `--type app --text '*GET*200*'` / `'GET*'` | wildcard | **0** / **0** |
| `--type app --text '/GET.*200/'` | RE2 | **0** |
| `--type app --text '/GET/'` | RE2 | **0** |
| `--type app --text '/HTTP\/1\.[0-9]/'` | RE2 | **0** |
| `--type request --path '/*'` / `'*'` | wildcard | 1 / 1 |
| `--type request --path '/^\/$/'` | RE2 | **0** |

Every row exits 0 with no output for the zero cases.

## Expected

Each filter value is one of three forms:

- A value enclosed in `/…/` is an RE2 regular expression.
- A value containing `*` is a wildcard pattern, where `*` matches any run of characters.
- Anything else is a literal.

For `text`, Render's example `foo*bar` "returns logs containing foo followed by bar", so text patterns match anywhere in the message (unanchored, as today's literal substring search is). Several values stay ORed within a filter, and filters stay ANDed. An invalid regex is a 400 that names the filter and value, never a silent empty result.

## Root cause

- `lego/backend/internal/logs/service.go:526–536` `matchesText`: `strings.Contains(strings.ToLower(message), term)`. There is no wildcard or regex handling for `text` (`Search`, `service.go:271`, documented as "case-insensitive literal substrings").
- `lego/backend/internal/logs/loki.go:553–583` `labelMatcher`/`labelValuePattern`: values are `regexp.QuoteMeta`'d with only `*` restored, so `/…/` is matched literally. The comment calls the regex gap "a documented divergence (docs/ADR010-observability.md § Log filters)".
- The path/host line filters and the pod-log (live) path reuse `labelValuePattern` (the comment says Loki and pod-log filters share it), so live tail and history behave the same.

## Fix

1. Parse each filter value once into one of literal, wildcard or RE2. Go's `regexp` is RE2, so `/…/` compiles directly. Bound pattern length and refuse compile errors as `400 LOG_FILTER_INVALID` naming the filter.
2. `text`: matching stays unanchored, so a wildcard becomes `.*`-joined quoted parts searched anywhere, and RE2 is used as written. Keep today's case-insensitive literal behavior for plain values; for wildcards and regex, follow Render's case semantics once captured, and say which in ADR010.
3. Structured filters (labels and the path/host line filters): a `/…/` value is used as the regex itself. Loki's `=~` is fully anchored, so pass it through with `.*` padding only if Render's filter matching is unanchored. Capture one Render request (`status_code:/4../`) to settle that.
4. GraphQL `logs(text:)`, MCP `list_logs`/`query_logs` and the dashboard search share `LogQuery`, so they inherit the change. Update the MCP `jsonschema` descriptions (`logs/mcp.go:47–53`, today "* wildcards supported"), ADR010 § Log filters and ADR018's logs row.

## Blast radius

One query type (`LogQuery`) behind REST `GET /v1/logs` and `GET /v1/logs/subscribe`, GraphQL, MCP and the dashboard. History (Loki) and live tail (pod logs plus the request-log poll) are both affected. Literal searches are unchanged unless they contain `*` or are wrapped in `/…/`; those values change meaning, as on Render.

## Acceptance

- Unit: the table above, run through `LogQuery` for both the Loki and pod-log paths, gives 1 for every wildcard and regex row that should match. A bad regex (`/(/`) answers a named 400.
- Live after deploy: repeat the table on an owned fixture with `bex logs`, including `--tail` with `--text '/GET.*200/'`. Delete by ID with a 404 proof.

## Related, not in scope

ADR018's same row also lists "the request-log message is the raw JSON access line, not a rendered summary". Render's docs example `/responseTimeMS=\d{3}\d+/` shows Render's request-log message is a rendered `key=value` summary. Bex's is Traefik's full JSON, including internal names such as `KubernetesServiceName: bex-activator-<ws>-<name>`, `entryPointName` and `OriginStatus`. That divergence also has no sign-off; filing it needs a captured Render request-log line to state the target format.
