# 063 — Env-group linking and service secret files drift from Render's REST contract: link answers 204 with no body, `serviceLinks` holds bare ID strings, and bulk `PUT /services/{id}/secret-files` is 405

Why: three Render operations a migrating client or SDK uses behave differently on bex, and none is documented as a divergence or allowlisted:

- `link-service-to-env-group` (`POST /env-groups/{envGroupId}/services/{serviceId}`) is specified as 200 with the updated `envGroup`. bex answers 204 with no body, so a client that reads the result gets nothing.
- `envGroup.serviceLinks` items are specified as objects `{id, name, type}` (`serviceTypeShort`). bex returns bare service-ID strings, so a generated client fails to decode any group that has a link.
- `update-secret-files-for-service` (`PUT /services/{serviceId}/secret-files`, replace-all) is in Render's API. bex has no route, so it answers 405 `method not allowed`.

Severity: minor. Attribution: server (`lego/backend/internal/envgroups`, `lego/backend/internal/secrets`).

## Evidence (2026-10-06, `/qa-find-bugs-cli` w8 loop, sweep 44)

Production (pin containing `0903a31b6`), workspace `bex-canary`, human device login, REST with the CLI's token (read privately), User-Agent `render-cli/2.27.0`. Fixtures created and deleted three times over: free image web service plus environment group (the last pair was `srv-db25sj7pn68c73ec58d0` / its group; all deleted, ledger balanced). The probe validated responses with `jsonschema` 4.23 against the pinned `render-public-api-1.json` and printed no secret values.

```text
POST /v1/env-groups/{evg}/services/{srv}       → 204, empty body          # Render: 200 envGroup
GET  /v1/env-groups/{evg}                       → serviceLinks: ["srv-db25sj7pn68c73ec58d0"]
     schema envGroup: $.serviceLinks[*] type (string, want object {id,name,type})
POST link again                                  → 204 (idempotent; control)
POST link srv-zzzz… (nonexistent)               → 404 (control)
DELETE /v1/env-groups/{evg}/services/{srv} ×2   → 204, 204 (idempotent; control)

PUT  /v1/services/{srv}/secret-files/qa.txt {"content":"hello-qa"} → 200, validates as secretFile (control)
GET  /v1/services/{srv}/secret-files/qa.txt                         → 200, content round-trips (control)
PUT  /v1/services/{srv}/secret-files [{a.txt},{b.txt}]              → 405 {"error":"method not allowed",…}   # Render: update-secret-files-for-service
PUT  …/secret-files/..%2Fetc%2Fpasswd → 400 invalid secret file name; 300-char name → 400 (controls)
```

The `envVars[*].value` gap in the same `envGroup` validation is the documented reveal-only masking (ADR018 env-groups row), so it is not part of this note.

## Mechanism

- `lego/backend/internal/envgroups/rest.go:176` mounts the link as `core.HandleNoBody(http.StatusNoContent, …)`. `lego/backend/internal/envgroups/service.go:188` declares `ServiceLinks []string` (`json:"serviceLinks"`), serialized as-is on REST.
- `lego/backend/internal/secrets/rest.go:119-140` mounts `GET` list, `GET`/`PUT`/`DELETE` by name. There is no `PUT …/secret-files` collection route. Env vars do have Render's collection `PUT` (ADR018 env-vars row), so the two siblings differ.
- `internal/api/conformance_allowlist_test.go` has no entries for these operations, and the conformance fixture seeds no linked group, so the drift is unseen. Sweep 25's `envGroup` check passed only because that group had no links.

## Fix

- Link: return 200 with the updated group, in the same shape as `GET /v1/env-groups/{id}`.
- REST `serviceLinks`: serialize `{id, name, type}` (Render's short type: `web_service`, `private_service`, `background_worker`, `cron_job`, `static_site`) by resolving each linked App. Keep GraphQL/MCP shapes as documented. Include the stale-link prune from w6/m108.
- Add `PUT /v1/services/{id}/secret-files` (replace-all) on the same write path and quota as the per-file PUT (w1/m147 caps), returning `[secretFileWithCursor]` with the documented names-only list divergence. Alternatively, record it as a deliberate gap in ADR018 if replace-all is unwanted.
- Conformance: seed a group with one linked service, and cover the link response and the bulk secret-file PUT.

## Acceptance

- [ ] `POST /v1/env-groups/{id}/services/{srv}` → 200 with a body validating as `envGroup` (except the documented value masking), and `serviceLinks[0]` is `{id, name, type}`.
- [ ] `GET /v1/env-groups/{id}` with a linked service validates `serviceLinks` against Render's item schema.
- [ ] `PUT /v1/services/{id}/secret-files` with two files → 200 and replaces the set (a prior third file is gone). A file over the quota is refused with the w1/m147 message.
- [ ] Controls: idempotent re-link/unlink, nonexistent-service 404, per-file PUT/GET/DELETE, name validation, and dashboard link/unlink are unchanged.

Estimate: ~55m.

**Closed 2026-10-07 (w8 /loopx):** fixed. Two of the three drifts were real at triage:

- **Link response.** `POST /v1/env-groups/{id}/services/{serviceId}` now answers 200 with the committed `envGroup`, validated against the pinned spec in `TestEnvGroups_DeletingAServiceUnlinksIt`.
- **Bulk secret files.** `PUT /v1/services/{id}/secret-files` is the new `SetSecretFiles`. It has the same name validation, aggregate quota, CAS write and materialize path as the per-file PUT, and refuses a duplicated name. It is covered by `TestSetSecretFilesReplacesTheWholeSet`, the quota guard, the cross-workspace matrix, the scope matrix (Write, like the per-file PUT), and a conformance subtest proving the seeded files are replaced.
- **`serviceLinks` shape.** Already fixed before triage by `e3c1669a9` (w5/092). Render's `serviceTypeShort` is `web`/`pserv`/`worker`/`cron`/`static`, not the `web_service` spelling this note suggested, and bex already emits it.

The ADR018 env-group and secret-file rows are updated, and the bulk secret-file omission row is removed.
