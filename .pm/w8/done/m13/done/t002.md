## Objective

`databases`/`keyValues` queries accept the same cursor/limit args the paged REST path uses (matching how `services`' GraphQL handles paging — mirror that treatment, whatever it is, rather than inventing a new one).

## Files

- `lego/backend/internal/postgres/graphql.go`, `lego/backend/internal/keyvalue/graphql.go`

## Acceptance criteria

- [x] GraphQL paging matches REST semantics (shared-verb test).

## Done

`databases(cursor, limit)` and `keyValues(cursor, limit)` now use the same `core.StablePage` boundaries as REST while retaining their existing plain-list GraphQL result types. Omitted args return the complete list, so the dashboard's existing queries remain byte-for-byte unchanged. `TestPostgresListPaginationAcrossRESTAndGraphQL` and `TestKeyValueListPaginationAcrossRESTAndGraphQL` compare first/next/unknown-cursor behavior across adapters.
