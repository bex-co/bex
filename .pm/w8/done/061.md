# 061 — Render's `/metrics/{memory,cpu,…}` answers a bare `404 not found` for a live Key Value or Postgres, though Render scopes them to datastores and bex already has Key Value memory

Why: Render's metrics `resource` covers "server, cron job, postgres, or redis". A Render client (or the Render CLI/MCP) asking for a Key Value's memory gets the same `404 not found` it would get for an ID that doesn't exist, so it can't tell "unsupported" from "wrong ID". bex already serves Key Value memory (`kv_memory`, redis_exporter) through its native `DatastoreMetrics` verb. w1/m155 fixed this same bare-404 shape for `disk-usage` and `active-connections` by routing on the ID prefix, but not for `cpu`/`memory`.

Severity: minor. Attribution: server (`lego/backend/internal/metrics`).

## Evidence (2026-10-05, `/qa-find-bugs-cli` w8 loop, sweep 38)

Pinned Render contract: `components.parameters.resourceIdParam` = "IDs of resources (server, cron job, postgres, or redis) to filter by".

## Mechanism

`lego/backend/internal/metrics/rest.go:64-90` mounts `metricPaths` (`cpu`, `memory`, …, `:38-39`) on `metricQuery`, which resolves only App (service) resources. A `red-`/`dpg-` ID therefore fails resolution as "not found". Only `disk-usage` and `active-connections` route through `datastoreMetricQuery` with `datastoreKindFor` (`:96-108`, w1/m155). Key Value memory exists as `kv_memory` in `DatastoreMetrics` (ADR018 "Extended metrics" row, w5/011).

## Fix

In `metricQuery` (or ahead of it), branch on `datastoreKindFor(resource)` for non-service prefixes:

- `memory` + `red-` → serve `kv_memory` in Render's time-series shape (unit bytes).
- `cpu`/`memory` + `dpg-`, and `cpu`/`*-limit`/`instance-count` + `red-` → serve the series if bex has it (CNPG/Valkey pod container metrics are in the same Prometheus). Otherwise return a coded refusal naming what isn't served (as `bandwidth-sources` does with a 501), never a bare `not found`.
- Record the per-metric datastore coverage in ADR018's "Extended metrics" row.
