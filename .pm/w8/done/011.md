# 011 — Render's spec-based compute plan names: adopt as aliases or keep the divergence?

Why: the w8/m33 CLI re-baseline (pin v2.24.0 → v2.26.0) surfaced that Render CLI v2.25.0's `--plan` help text and interactive picker now advertise Render's new **spec-based compute plan names** — Postgres `0.1c-256mb`, `0.5c-1g`, `1c-2g` … `128c-1024g` (`pkg/client/postgres/plans_gen.go`), and Key Value `1g` etc. The legacy names (`basic_256mb`, `pro_*`, `accelerated_*`) remain valid input.

- The CLI's advertised list is **documentation-only, not validation** — `pkg/postgres/options.go` passes any `--plan` value straight through to the API. So a user who copies a suggested `2c-8g` from `render postgres create --help` sends it to bex.
- bex validates `--plan` against its **own** tier catalog (`internal/postgres` `tiers.Postgres.IDs()` → "plan must be one of …"), so a spec-based name is a named 400 (`core.ErrBadRequest`). bex's own plan names still round-trip; this is not a wire regression, it is a **pricing-catalog divergence** (bex has its own price sheet, [ADR030](../../docs/ADR030-pricing.md)/m7 — 30% off Render's compute).
- Recorded as an Intended divergence in `docs/cli-compatibility-checklist.md` and in the ADR018 round-3 note (2026-09-07); this note owns the open **product/pricing decision** so it is not silently accepted.

Decision needed: (a) keep the divergence (bex publishes its own plan taxonomy, spec-based names 400 — status quo), or (b) accept Render's spec-based names as **input aliases** onto the nearest bex tier for copy-paste ergonomics (a tier-catalog alias table + tests; no price-sheet change). Same question for the Key Value `1g`-style names. Sub-hour to size; a pricing call, not a code chore, so filed as an inbox note.
