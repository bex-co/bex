# A no-build static site's publish in flight is replaced by the next deploy, even once the operator has adopted it, where Render's default Wait lets it finish

Why: w8/390 checked the operator side it named as unverified. `releaseInFlight` (`lego/operator/internal/controller/release_identity.go`) holds a release only while `pinnableRelease` is true, and `pinnableSourceRelease` returns false for `directStaticPublish`, a repo-backed static site with no build command, Dockerfile, runtime or builder. Its publish Job clones the repo and uploads the publish directory (`reconcileStaticSite`, `app_controller.go`). So while it publishes, a newer release from any writer (a trigger, a git push, a configuration save, a Blueprint sync) is adopted at once, and the publish in flight closes "Superseded by …". The exclusion dates from ADR060 §D1a (w2/m72, "no build Job to protect"). w4/635 later pinned prebuilt images through their rollout, and w4/661 pinned selected releases, but static publishes were never pinned.

- Severity: minor. A no-build publish is short (a clone and an upload), so two deploys within its window are needed to hit it.
- Parity: Render's Wait, "Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy" ([render.com/docs/deploys](https://render.com/docs/deploys)). ADR018's "List / get deploy objects" row names this as still open (w8/390).
- Not yet seen live: the premise holds from the code above. Check it first on a free no-build static site in `bex-canary`. Trigger a deploy, wait about 5 s for the operator to adopt it, and trigger a second. The first should still reach `live`.

## Fix

Pin a direct static publish once the operator has adopted it, as `pinnableSourceRelease` pins a source build. The publish Job must render from the release's adopted view (`heldReleaseView`), with its commit, publish path and routes, not from the newer saved spec. The newer release then waits in the pending slot until the publish serves or fails. Keep Override's cancel-and-start, and keep w8/m460's hold, which keeps a static site's IP allow-list following the App while a publish runs.

## Acceptance

- Envtest: a direct static publish adopted and in flight, then a newer release written to the App. The first publishes and serves its own commit, and the newer one publishes after it.
- Live in `bex-canary`: two deploys of a free no-build static site, the second about 5 s after the first, both reach `live` in order. Delete the fixture by ID and confirm the 404.
- ADR018: drop the "Still open" sentence from the w8/390 paragraph.

Estimate: ~2h.

## Shipped 2026-11-22 (`e737de6976`), live check owed

- **The pin.** `pinnableSourceRelease` (`lego/operator/internal/controller/release_identity.go`) no longer leaves out `directStaticPublish`. So `releaseInFlight` holds a no-build publish while it clones (`Building`) and uploads (`Deploying`) until it serves, fails or has its own deploy canceled, as it holds a build. Its adoption records the release's spec (`recordAdoptedRelease`), so the pinned passes run on `heldReleaseView`: the publish Job clones the release's own commit and publishes its own directory, and the newer deploy waits in the pending slot. bex-api needed no change, since behind an adopted deploy a trigger already writes through and pends. Override's `app.bex.co/overlapping-deploy-policy=override` label still replaces the publish at once. A cancel's survivor that is a no-build publish now runs to completion as a build does (`survivorInFlight`).
- **w8/m460's hold is kept.** A saved change during the publish now pins it on its view as it pins a built static site, and `holdPendingStaticArtifact` still keeps the served revision's IP allow-list following the App. The m460 envtests pass unchanged.
- **Tests.** `TestDirectStaticPublishInFlightWaitsForTheNewerDeploy` covers cloning and uploading over a served release, a first release, and the controls (served, failed, own deploy canceled, suspended, Override). The envtest "finishes a publish in flight on its own commit before a newer deploy publishes" adopts a deploy of commit A and starts its clone. A deploy of commit B with another publish directory then waits, and no second publish Job exists. A publish Job lost mid-flight is recreated with commit A and the first directory, and commit B publishes from its own directory once A serves. "replaces the publish in flight at once under the Override policy" is the control. With the exclusion restored, both tests fail. Without the adoption record, the recreated Job clones commit B. The whole operator suite (`make test`) and `make lint` pass.
- **ADR018** (List / get deploy objects) replaces the "Still open" sentence with the pin, and ADR060 §D1a records it.
- **Owed:** the production check in Acceptance once the pin carries `e737de6976`. Make a free no-build static site in `bex-canary`, trigger a deploy, and trigger a second about 5 s after the first reads `build_in_progress`. Both must reach `live` in order, with the first never `canceled`. Then delete the fixture by ID and confirm the 404.

## Live check passed and closed 2026-11-22 on pin `89642635b9ce`

- **The gate.** Production pinned `89642635b9ce` at 08:32 UTC (`ab7cf746b3`), and `git merge-base --is-ancestor e737de6976 89642635b9ce` holds. No roll followed before the check.

- **The pair.** REST trigger A `dep-dc1b95r88nrc738n1lfg` (201) read `build_in_progress` 3.6 s later. Trigger B followed 6.1 s after that and answered 202 with an empty body, as Render's does; its row `dep-dc1b98b88nrc738n1lgg` read `queued`. A went `update_in_progress`, then `live` (finished 09:23:54.56 UTC), and was never `canceled`. B started 4.2 s after A finished, read `build_in_progress` and `update_in_progress`, and went `live` at 09:24:14.24. A turned `deactivated` only then. The events show A's `deploy_ended` `succeeded` with an empty reason, then B's `build_started`.
- **A burst too.** A first attempt had a script bug: it re-triggered on every empty 202, so eleven triggers landed during A's publish. A still went live and was never canceled. Each waiting deploy was replaced by the next one (`deploy_ended` reason `newDeploy`), as Render's Wait goes "directly to the most recently triggered deploy".
- **Seen on the way, filed as w8/396.** A deploy was waiting behind A. A trigger landed 0.7 s or 1.4 s after A served, and closed the waiting deploy `canceled` before it logged a build. The new deploy then sat in `==> Build queued` for 23 s and 26 s, where a deploy from idle starts in about 4 s.
- **Cleanup.** The fixture was deleted by ID (204). A `GET` of it then answered 404, and no `qa-392` service is left in the workspace. The QA session was logged out (the API refused its cookie with 401), and the jar was removed.
