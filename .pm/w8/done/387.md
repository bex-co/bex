# Two back-to-back deploy triggers cancel the first deploy ("Superseded by …") before it starts, where Render's default Wait policy lets the first finish

Why: the w8/378 live check (2026-11-21 ~22:10 UTC, production pin `ad799a7cf32b`, bex v0.9.0, free nginx image service in `bex-canary`) fired two plain triggers back to back, with no `imageUrl`, through both the CLI and MCP. The first answered `201` with a deploy, and the second `202` queued. About 2 s later, the first closed `canceled` with `Superseded by <the second>`, never started, and the queued one went live (`.pm/w8/done/378.md` line 83).

- Severity: minor to major. A user who triggers twice gets one deploy, not two, and the deploy the first `201` named never runs, so anything waiting on that ID sees a cancel. Under Render's Wait policy, the first deploy finishes, then the newest pending one runs.
- Attribution: server. The deferred-deploy worker and the trigger path (`lego/backend/internal/deploys`), and the operator's adoption point.
- Parity: ADR018's "Trigger a deploy" row (from w4/635) records "a deploy a newer trigger reaches before it was adopted never started and is still replaced". ADR018 records no user sign-off for that, so under AGENTS.md ("A divergence stands only when ADR018 records it with the user's sign-off") it is open parity work.

## Render

[render.com/docs/deploys](https://render.com/docs/deploys), Overlapping Deploy Policy, **Wait**: "Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy". That is the default for workspaces created on or after 2025-07-14, so every bex workspace. On Render a triggered deploy is in progress from the moment it is created. A `201` deploy is the in-progress one; only later triggers wait, and only the newest of those runs.

## Fix

Under Wait, a deploy answered `201` is never superseded by a later trigger, whether or not the operator has adopted it yet. It runs to its own end, then the newest queued deploy runs. Only queued deploys (the `202` ones) replace each other. Check the same rule for Restart, Rollback and image-override triggers, which share the deferred path (w5/m284, w4/652). Keep Override's behavior as it is. Amend ADR018's row and w4/635's sentence.

## Acceptance

- A unit or real-DB test: a trigger answered `201`, then a second one answered `202` before adoption. The first runs and ends `live`, the second runs after it, and a third trigger while the second is queued replaces only the second.
- Live in `bex-canary`, on a free nginx image service: two back-to-back `bex deploys create` both reach `live`, in order. Delete the fixture by ID and confirm the 404.

## Shipped 2026-11-21 (`d99a0bf99f`), live check owed

- **Premise held.** `triggerFetched` held a plain trigger only behind an image override or a selected release in flight, and wrote any other trigger to the App at once. The operator pins a release only once it has adopted it (`releaseInFlight`), so a release written before then replaced it, and the reconciler closed its row through `supersededCancelReason`.
- **Fix.** A deploy behind one whose release generation is ahead of the App's `status.releaseGeneration` (`deployAheadUnadopted`, `lego/backend/internal/deploys/restart_wait.go`) now waits at the row level, as w4/652's Rollback does. It answers `202` (the hook's bare `202`) with a `queued` deploy that changes no App, and the deferred-deploy worker runs it once the deploy ahead has ended. Only queued deploys replace each other. Behind an adopted deploy, a plain trigger still writes through behind the operator's pin, as w4/635's live check showed. This covers REST, GraphQL and MCP triggers, the deploy hook, a build-source carrier's build, and "Save, rebuild, and deploy". Restart, Rollback and image overrides already waited behind any deploy in flight, adopted or not. Override keeps its cancel-and-start (`appWaitsForActiveDeploy`). No operator change: the second release waits in the queue until the first one's row ends.
- **Found on the way.** A waiting "Save, rebuild, and deploy" (trigger `config_change`) ran as an environment "Save and deploy" on the served build (`runDeferredDeploy`). With no `DeployServedBuild` wired, it closed "could not run". It now carries `DeferredRequest.Rebuild` and runs as a rebuild.
- **Tests:** `TestBackToBackTriggersBothRunUnderWait` (REST `201` then `202`, no App change, then live then live, in order), `TestThirdTriggerReplacesOnlyTheWaitingDeploy` (Restart, Rollback and Rebuild wait behind a deploy not adopted yet, and a third trigger replaces only the waiting deploy while the first runs to `live`), and `TestWaitingRebuildRunsAsARebuild`. Each one fails with the fix reverted. `imageServiceRollingOut` now marks its deploy as adopted, so `TestPlainDeployWaitsOnlyBehindASelectedRelease` still covers the write-through path. The backend `deploys`, `store`, `secrets`, `api`, `apps` and `events` packages pass against real Postgres and OpenFGA, and `make lint` passes.
- **Docs.** ADR018's Trigger, Restart, List / get deploy objects and Overlapping Deploy Policy rows are amended, and so is w4/635's sentence. Follow-up [w8/390](../blocked/390.md) covers git pushes, configuration rolls, Blueprint syncs and build-source fan-outs, which write the App directly and still replace an unadopted deploy.
- **Owed:** the production check in Acceptance once the pin carries `d99a0bf99f`. A third trigger while the second is queued must replace only the second.
