## Objective

When a blueprint apply creates or adopts a service/Postgres/KeyValue, record the owning blueprint id on the resource — pick the storage that fits existing patterns (a control-plane store column on the resource rows, or a `bex.co/blueprint` label/annotation on the CRs alongside the existing identity labels in `core/base.go`) — and stamp existing blueprint-managed resources on their next sync (lazy backfill, no migration job). Disconnect clears the marker.

## Context

- Adoption path: `applyCreateWithFields` (`lego/backend/internal/apps/deploy.go`, existing-App fetch by name) and the datastore equivalents; sync entry `runSync` (`blueprint.go`).
- Store row already links blueprint→resources for `resources[]` display — check whether `store/blueprints.go`'s existing resource resolution can be the single source instead of a new marker; prefer one mechanism.
- Marker must survive non-blueprint edits (a dashboard PATCH must not strip it).

## Steps

1. Decide storage (column vs label) after reading the existing `resources[]` resolver; record the decision in this task on completion.
2. Stamp on create + adopt inside the apply transaction; clear on disconnect.
3. Surface the owning blueprint id in the resource detail read paths (needed by t002's error and the dashboard).

## Files

- `lego/backend/internal/apps/{deploy.go,blueprint.go}`
- `lego/backend/internal/store/` (or `lego/types/` + operator-ignored label if label route)

## Acceptance criteria

- [ ] Create/adopt stamps; disconnect clears; dashboard PATCH preserves.
- [ ] Next sync lazily stamps pre-existing managed resources.
