# 041 — `blueprints validate` on a zero-byte file answers a bare `400 bad request` instead of a validation result

Why: an empty `render.yaml`, for example one created by `touch` or truncated by a bad merge, gets an error with no reason, while a file holding a single newline gets the actionable `valid:false` "Blueprint must contain one YAML document". The validator should not depend on whether the file has one byte.

Severity: minor. Attribution: server (`lego/backend/internal/apps/rest.go`).

## Repro (2026-10-03, `/qa-find-bugs-cli` w8 loop sweep 4)

Production, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. No resources created.

```text
$ : > empty.yaml;  bex blueprints validate empty.yaml -o json
Error: validation request failed with status 400: {"error":"bad request","id":"bad_request","message":"bad request"}      exit 1
$ printf '\n' > ws.yaml;  bex blueprints validate ws.yaml -o json
{"errors":[{"error":"Blueprint must contain one YAML document","path":""}],"valid":false}                                   exit 1
$ printf '# just a comment\n' > c.yaml   → same valid:false result as ws.yaml
```

## Mechanism

- `decodeBlueprintValidationRequest` (`rest.go` ~l.1591-1593) returns `core.ErrBadRequest` when the multipart `file` part is empty (`len(content) == 0`). The JSON branch has the same check at ~l.1567 (`body.BexYAML == ""`).
- The route handler (`rest.go:1309-1318`) then maps **every** non-size decode error to a bare `core.ErrBadRequest`. That also drops the reasons the decoder already computed, such as `ownerId is required` and `unsupported content type "…"`.

## Fix

- Let empty content reach `CompileBlueprintIR`, so a zero-byte file returns the same 200 `valid:false` "Blueprint must contain one YAML document" result (with location `path:""`) as a whitespace-only file. Keep a truly absent `file` part as a 400.
- In the handler, pass the decoder's message through (`fmt.Errorf("%w: %s", core.ErrBadRequest, err)`) instead of a bare `ErrBadRequest`, so a missing `ownerId` or file part says so.
- GraphQL/MCP validate entry points: check that they treat an empty manifest the same way.

## Acceptance

- [ ] `bex blueprints validate <zero-byte file> -o json` prints `valid:false` with the one-document error and exits 1. The JSON body path behaves the same.
- [ ] A multipart request without `ownerId` or `file` returns a 400 that names the missing field.
- [ ] Controls: the whitespace-only, comment-only, broken-YAML and oversize (413) cases are unchanged.

## Closure (2026-10-03)

Fixed. `decodeBlueprintValidationRequest` (`lego/backend/internal/apps/rest.go`) lets a zero-byte multipart file, or an empty JSON `bexYaml`, reach `CompileBlueprintIR`. The result is the same 200 `valid:false` `BLUEPRINT_YAML_EMPTY` "Blueprint must contain one YAML document" as a newline- or comment-only file. A truly absent part still answers 400, now named: `file is required` / `bexYaml is required`. The route handler passes the decoder's reason through (`bad request: ownerId is required`, `unsupported content type "text/plain"`) instead of a bare `bad request`. GraphQL `validateBlueprint` and MCP `validate_bex_yml` already handed the manifest straight to `ValidateBlueprint`, so they needed no change. `TestValidateBlueprintEmptyManifestAndNamedRefusals` covers empty/newline/comment manifests on JSON and multipart plus the four named refusals. `TestRESTValidateBlueprintRenderCLIMultipartRequiresOwnerAndFile` encoded the old empty-file 400; it became `…RequiresOwner`. The size-boundary (413) and invalid-YAML tests are unchanged and pass. Backend `go test ./...` and lint are clean.
