# Runtime versions Render installs are refused at build time: Node 20/18/16/14, Python 3.7–3.9 and Ruby 3.2 (Render's own Rails examples) fail "not a supported version"

Why: a native build accepts only bex's reviewed version lines (Node 22/24/26, Python 3.10–3.14, Ruby 3.3/3.4/4.0, Elixir 1.17–1.19) and fails anything else by name. Render installs these older versions. It resolves any Node release or semver range, and its own default for services created before November 2023 is still Node 14.17.0. It supports any Python from 3.7.3. Real Render apps pinned to an older version therefore build on Render and fail on bex. That includes Render's own `rails-7`, `rails-6` and `sidekiq` examples (Ruby 3.2.0) and 80% of the `NODE_VERSION` pins in real `render.yaml` files. ADR018 row 84 lists "an unsupported version fails the build by name" as a divergence without a user sign-off (ADR060 D7 addendum), so under ADR008 § Render parity first it is a gap, not a decision.

**Severity:** major (blocks import of a large share of real Render Node apps; workaround is editing the app's version pin, which may not build on the newer runtime). **Attribution:** platform build (native runtime version selection). **Estimate:** 3h. **Source:** `/qa-find-bugs-cli` sweep 1307, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1307--runtime-versions)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`, human device-login grant, HEAD-built pinned CLI. Each fixture was deleted afterwards (204 → 404).

```text
$ bex services create --type web_service --runtime node --plan free \
    --repo https://github.com/render-examples/express-hello-world \
    --build-command yarn --start-command 'node app.js' --env-var NODE_VERSION=20 …
→ build_failed in 86 s: "build failed in the runtime version selection step:
  NODE_VERSION=20 is not a supported Node version; supported Node lines are 22, 24, 26"

$ bex services create --type web_service --runtime python --plan free \
    --repo https://github.com/render-examples/fastapi … --env-var PYTHON_VERSION=3.9.18
→ build_failed in 116 s: "PYTHON_VERSION=3.9.18 is not a supported Python version;
  supported Python lines are 3.10, 3.11, 3.12, 3.13, 3.14"
```

Real-world reach, from the Render corpora (sweeps 1267/1270/1276, ~700 `render.yaml` files):

- `NODE_VERSION`: 63 of 79 pins are refused: `20` (17), `~16.13.0` (5), `18` (4), `18.17.0` (4), `18.17.1` (4), `16` (4), `14` (4), `20.18.0` (3), and others.
- `PYTHON_VERSION`: 9 of 84 are refused: `3.9.x` (7), `3.8.10`, `3.1` (a typo).
- `ELIXIR_VERSION`: 1 of 1 (`1.20.4`).
- Ruby comes from `.ruby-version` or the Gemfile, which the corpus does not include. Render's own `render-examples/rails-7` and `rails-6` (`.ruby-version` `ruby-3.2.0`) and `sidekiq` (Gemfile `ruby '3.2.0'`) are refused by the same rule. `.nvmrc`, `.node-version`, `engines.node` and `.python-version` pins in repositories are refused the same way and are not counted here.

## Expected

The version signals Render honors select a toolchain Render would install:

- **Node:** [render.com/docs/node-version](https://render.com/docs/node-version) resolves `NODE_VERSION`, `.node-version`, `.nvmrc` and `engines.node` through `node-version-alias`, ranges included. Its default table still assigns 14.17.0 and the 20.x releases to older services.
- **Python:** [render.com/docs/python-version](https://render.com/docs/python-version) supports "any version from 3.7.3 onward".
- **Ruby and Elixir:** [render.com/docs/ruby-version](https://render.com/docs/ruby-version) and [render.com/docs/elixir-erlang-versions](https://render.com/docs/elixir-erlang-versions) list the supported ranges (read and quote them when fixing).

The parity-sufficient choice keeps D7's model (reviewed, digest-pinned lines) and adds a reviewed line for every major (Node) or minor (Python, Ruby, Elixir) that Render's documented ranges and default tables reach. At minimum that is:

- Node 14, 16, 18 and 20.
- Python 3.7, 3.8 and 3.9.
- Ruby 3.0, 3.1 and 3.2, plus 2.7 if Render's page lists it.
- Elixir 1.20.

A request outside Render's own supported range keeps today's named refusal. A request inside it never does. Exact patches are w8/175.

## Root cause

- `lego/operator/internal/build/native.go:87–131` (`nativeToolchains`, `nativeBun`) is the whole set of reviewed lines.
- `lego/operator/internal/build/nativeversion.go:74` `ResolveNativeVersion` maps a signal onto those lines. `:252` returns `UnsupportedVersionError` ("is not a supported … version; supported … lines are …") for anything else. That error is tenant-classified, so the build fails at "runtime version selection".
- `docs/ADR060-build-worker-reliability-and-performance.md` § D7 addendum records the refusal as intended. ADR018 row 84 lists it as a divergence with no user sign-off.

## Fix

1. Add a `nativeLine` per missing line with the official image digest (`node:20-bookworm`, `node:18-bookworm`, `node:16-bookworm` or `-bullseye`, `node:14-bullseye`, `python:3.9-bookworm`, `python:3.8-bookworm`, `python:3.7-bullseye`, `ruby:3.2-bookworm`, `ruby:3.1-bookworm`, `ruby:3.0-bullseye`, `elixir:1.20`), reviewed under D7 like the existing lines.
2. Check what each line needs from bex's companions:
   - the env loader;
   - `native-init`;
   - Bun, uv and Poetry installs;
   - FFmpeg, Hugo and the JS tools added to non-Node runtimes;
   - the `NODE_ENV`/`RAILS_ENV`/Bundler defaults.

   A bullseye or buster base may need its own companion builds. Where one cannot run on an old line, say so in the build log rather than refusing the version.
3. Range resolution (`engines.node: ">=16 <21"`, `~16.13.0`, Gemfile `~> 3.2`) picks the highest reviewed line that satisfies the range. It refuses only when nothing in Render's range does.
4. Amend ADR060 D7 addendum and ADR018 row 84 so that the refusal applies only to versions Render itself does not support.

## Blast radius

Every native runtime service (web, private, worker, cron) and static site with a version signal, on every surface (REST, GraphQL, MCP, dashboard, Blueprints), because the decision happens in the build. Services that build today are unaffected; new lines are only chosen by signals that are refused today. The default line is unaffected (w8/174).

## Acceptance

- Unit: `ResolveNativeVersion` maps `NODE_VERSION=20`, `.nvmrc` `18`, `engines.node: "~16.13.0"`, `PYTHON_VERSION=3.9.18`, `.ruby-version` `ruby-3.2.0` and `ELIXIR_VERSION=1.20.4` to a line. `NODE_VERSION=8` and `PYTHON_VERSION=3.6.15` (outside Render's ranges) still refuse by name.
- Live after deploy:
  - `express-hello-world` with `NODE_VERSION=20` and `fastapi` with `PYTHON_VERSION=3.9.18` go live and report those major/minor versions at runtime.
  - `render-examples/rails-7`, on a free plan with its migration step removed (w8/158), builds on Ruby 3.2.
  - Delete fixtures by ID with 404 proofs.

`git grep -i 'unsupported version|not a supported .* version|nvmrc.*18|PYTHON_VERSION=3\.9'` over `.pm`: no open item. w8/m51 introduced the lines and the refusal; w8/m91's open design is about native tools (psql, jq, …), not versions.
