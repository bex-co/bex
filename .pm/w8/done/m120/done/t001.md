## Objective

Choose where a release's own runtime settings and configuration snapshot are captured when it is adopted, and how a release held through rollout is rendered and recorded from them.

## Context

- `prepareAppReleaseDecision` adopts a release (`release_identity.go`); `releaseInFlight` holds it through rollout (w8/m119).
- `applyServingDeployment` projects from `app.Spec`.
- `recordReleasePodTemplate` writes `ReleaseRecordName(app, gen)` from `selectedRuntimeApp(app)`, which is the saved spec unless a Rollback or Restart selection applies.
- `ensureSavedReleaseConfigSnapshot` copies env and file Secrets after pre-deploy, so a value saved during the build lands in the earlier release.
- Selected releases already render from a record (`release_config_selection.go`, `projectRuntimeApp`), so the held release can likely reuse that path.

## Steps

1. Decide what is captured at adoption: the `ReleaseRecordSpec` fields and the config snapshot. Decide where it is stored: the release record written early, or a status field.
2. Decide how a held release whose spec moved on renders through its own record, and how that interacts with the cancel survivor (m117), suspend (w5/m114), pre-deploy holds and hibernation.
3. Write the decision and the exact sequence into t002 and t003.

## Acceptance criteria

- [x] Decision with rationale; t002 and t003 updated.

## Out of scope

- Prebuilt-image Apps, which never pin

## Outcome (2026-10-19)

**Decision: capture at adoption and render held releases from their own record, reusing the selected-release path.**

1. **At adoption** (the pass whose decision has `releaseChanged` for a pinnable source release, which is not a Rollback or Restart selection), the spec is the adopted release's own:
   - copy its configuration Secrets to their generation snapshots (`copyConfigSecret`, copy-once);
   - write its release record with the record spec fields (`releaseRecordSpec`) and no template yet.

   Do **not** flip `status.configSnapshotGeneration` then. A prior release still serving re-projects through that generation's snapshot names, so flipping early would roll it onto the newer values. That is why the snapshot step sits after pre-deploy. The deploy-stage `ensureSavedReleaseConfigSnapshot` then finds the snapshots already present (copy-once), keeps the adoption values, and flips the generation as today.
2. **While held.** `heldRelease` means the release is `releaseInFlight` or `survivorInFlight` (m117) and the saved spec has since moved to another release. In that state, `selectedRuntimeApp` / `selectedRuntime` read the held release's own record and `projectRuntimeApp` it, as for a Rollback. Its Deployment therefore renders with its own start command, command, health path, replicas (an operational scale still wins), env literals and source names.
3. **Its record.** `recordReleasePodTemplate` keeps the adoption record's `settingsFingerprint` and `savedReplicas` for a held release, rather than stamping the newer saved spec's.
4. **Fallbacks.** A held release adopted before this shipped has no record and keeps today's projection. A selected release (Rollback/Restart), a cancel over a served release, prebuilt images and suspended apps are unchanged.

**Known gap:** `preDeployCommand` is not a record field. A held release's pre-deploy step still runs the saved command, which t003 documents. Render's rollback contract also does not restore it.

**Sequence for "A held, B saved":**

| Moment | What happens |
| --- | --- |
| A adopted | A's record and snapshots are written with A's values |
| B saved | B is pending; A stays held |
| A's build resolves | The Deployment is projected from A's record: A's command and A's env snapshot. The record is rewritten with the template and keeps A's fingerprint |
| A serves | `rev-2`; A is live |
| B adopted | B's record and snapshots are written with B's values |
| B serves | B is live and A is deactivated |

Afterwards, Rollback to A or a Restart of A selects A's own values, and `undeployedChanges` compares the saved B against A's real record.
