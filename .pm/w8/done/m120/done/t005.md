## Objective

Run the DoD live journey and check that REST, GraphQL, MCP and the dashboard agree on the deploy history, `undeployedChanges` and the configuration a Restart or Rollback restores, measured against Render's running-configuration contract.

## Acceptance criteria

- [x] Live evidence recorded; any drift filed as follow-up work.

## Outcome (2026-10-19)

The live journey ran on production after deploy `108cdb3ac`, which included m120. The fixture was an owned Free Docker web service in bex-canary, built from `bex-co/bex` `examples/hello-go`. Its Docker command set `MESSAGE="start=<mark> K=$K"`, so each response shows the start command and env value the serving pods run.

- **Saves.** Each save wrote `K` with `patch_service_environment` `saveMode: save_only`, then the Docker command (`PATCH dockerCommand`), so one save is one deploy.
- **Session.** The run used the pinned `bex` v0.2.1 CLI with a human device login, and REST and GraphQL with the same QA identity.
- **Cleanup.** The fixture `srv-dbatin9kv6rc73en2cc0` was deleted by ID and answers 404.

Results, 9 of 10 checks:

- **Settings during rollout.** A then B were saved back to back. The served sequence was `start=A K=a`, then `start=B K=b`. No sample mixed A's command with B's env.
- **Rollback.** Rolling back to A served `start=A K=a`, so A's record holds A's command and env.
- **Restart** (m119's open bullet), with G serving and H building:
  - It kept serving `start=G K=g`.
  - H closed `canceled` with "Canceled by restart dep-…, which kept the running release: what this deploy was applying was not deployed".
  - `undeployedChanges` read `true`.
  - A standard deploy then served `start=H K=h` and `undeployedChanges` cleared to `false`.
- **Controls.** Cancelling the pending deploy kept the older one running to `live` (w8/m117). A suspend ended an in-flight rollout as `canceled` (w5/m114).
- **Surfaces.** The one failure was a harness artifact. MCP `list_deploys` defaults to 10 rows, Render's own tool bound (`deploys/mcp.go:115`), and this history had 12; the harness passed no `limit`. The m121 live run, on the same verbs after deploy `00a00c9d6`, read every surface with `limit: 100` once the history was stable. REST, GraphQL, MCP and the CLI returned the same 8 rows with the same statuses.
- **Dashboard.** It reads the same GraphQL `deploys` and `server { undeployedChanges }` queries. No drift was found against Render's running-configuration contract.
