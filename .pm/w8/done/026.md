# 026 — `blueprints validate` gaps: the 10 MiB limit is unreachable (2 MiB global cap wins), and a `fromService` host reference to a nonexistent service validates as `valid`

Why: validate is the gate authors and CI use before applying a Blueprint. (A) It refuses Blueprints between 2 and 10 MiB that the handler, its code comment and ADR049 all promise to accept (Render's limit). (B) It reports `valid: true` for a `fromService … property: host` pointing at a service that exists nowhere, a failure that only shows up at apply.

Live, 2026-09-26, production `726042a28`, `bex v0.2.1` (pin v2.27.0), workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 33. No resources created.

```text
# (A) 2,308,900-byte render.yaml (20,000 minimal services)
$ bex blueprints validate big.yaml -o json
Error: validation request failed with status 413: {"error":"request body exceeds 2097152 bytes","id":"payload_too_large",…}

# (B) same file, one env var, property varied
fromService: { type: pserv, name: qa33-nope-anywhere, property: port }      → error: references unknown service … (declare it under services:)
fromService: { type: pserv, name: qa33-nope-anywhere, property: hostport }  → same error
fromService: { type: pserv, name: qa33-nope-anywhere, property: host }      → "valid": true
```

## Mechanism

- **(A)** `lego/backend/internal/apps/rest.go:1473-1478` sets `maxBlueprintValidationFileBytes = 10 << 20` ("Render permits a Blueprint file of up to 10 MiB") and wraps the body at 11 MiB (`:1511`). But the router mounts `withBodyLimit(s.MaxBodyBytes)` (`api/server.go:1147`, `api/ratelimit.go:164-186`) on every route **first**, with `BEX_MAX_BODY_BYTES` defaulting to `2097152` (`cmd/api/config.go:550`). That fully buffers and rejects anything above 2 MiB before the handler runs, so the 10 MiB path is dead.
- **(B)** `lego/backend/internal/apps/deploy.go:1999-2003`: `allowExistingServiceHost` deliberately lets `property: host` reference a service **outside the file** (an existing workspace service), skipping the same-file existence check that `port`/`hostport` get. Validate's workspace-reference pass (`blueprint.go` → `validateWorkspaceReferences`, added by w4/118 for `fromDatabase` and `fromService`→Key Value) does not cover this service-host form, so nothing checks that the workspace actually has the service until apply resolves the slug.

## Fix

- **(A)** Give the validate route (and the Blueprint create/sync routes that accept the same file, if any) a per-route body limit of `maxBlueprintValidationBodyBytes` in place of the global 2 MiB. Keep the global default everywhere else.
- **(B)** Extend `validateWorkspaceReferences` to resolve every out-of-file `fromService` host target against the workspace. If absent, return a located error naming it ("fromService references unknown service 'x' in this workspace"), matching the w4/118 wording for databases and Key Value.

## Acceptance

- [ ] A 3 MiB and a 9.9 MiB syntactically valid Blueprint reach the validator (a validation result, not 413). A 10.5 MiB one gets the handler's own 10 MiB refusal.
- [ ] `property: host` to a service in neither the file nor the workspace → `valid: false` with the unknown-service error and a location. To an existing workspace service → still valid.

## Outcome (2026-09-27) — done

- **(A)** `api.Server.restBodyLimit` mounts the REST router with the global `BEX_MAX_BODY_BYTES` cap everywhere except `POST /v1/blueprints/validate`, which gets `apps.MaxBlueprintValidationBodyBytes` (11 MiB). A disabled global cap stays disabled. The validate handler now bounds both its JSON and multipart paths, and answers an oversized file (or envelope) with its own `413 "Blueprint file exceeds the 10 MiB validation limit"` instead of a generic 400. Tests: `api.TestRESTBodyLimitWidensOnlyBlueprintValidation` (3 MiB and 9.9 MiB reach the handler; 11 MiB+1 and other routes over 2 MiB get 413) and `apps.TestValidateBlueprintSizeRefusalIsItsOwn413` (multipart + JSON).
- **(B)** `validateWorkspaceReferences` resolves every out-of-file `fromService … property: host` target with the same `GetApp` lookup apply uses. A target that exists nowhere is `valid: false` with `service "x": fromService references unknown service "y" (declare it under services: or create it in this workspace first)`, located at the referencing `envVars[i]`. An existing workspace service still validates. Test: `apps.TestValidateBlueprintChecksOutOfFileServiceHosts`.
- Left as is: `POST /v1/blueprints/deploy` (inline `bexYaml` apply) keeps the global 2 MiB cap. The acceptance names validate only, and Render's 10 MiB applies to the synced file, which the Git-backed flows fetch server-side rather than post.

## Live re-verification (2026-09-27, `/qa-find-bugs-cli` sweep 51)

(B) **holds** on production `4a0422577` (deploy run `36306816215`, live 2026-09-27 12:09Z), `bex v0.2.1`, human device login, workspace `bex-canary`, fixtures deleted: an out-of-file `fromService … property: host` target gets `valid: false`, located at `services[0].envVars[0]` line 8 col 9. (A) **only partly**: a 3,004,900-byte Blueprint now reaches the validator (no 413), but it is refused with `Blueprint manifests are limited to 512 KiB` (`BLUEPRINT_YAML_TOO_LARGE`, `apps/blueprint_compiler.go:631,678`, a deliberate pre-decode amplification guard). The node budget (`blueprintMaxNodes = 100_000`) would also stop a real 10 MiB file. So the effective validate limit is **512 KiB**, not the 10 MiB this note and the handler's 413 text claim. The follow-up is `w8/032`: align the stated limit with the enforced one.

## Limit correction — 2026-10-02, w8/m48

The earlier 10 MiB acceptance statement confused the upload transport with the compiler budget. The effective manifest cap remains **512 KiB**, enforced before YAML decoding to bound amplification. m48 aligns REST validate's file/envelope refusal with the same named limit; it does not expand compiler budgets. The original (B) reference-validation fix is unaffected. Render's current [API documentation](https://api-docs.render.com/reference/validate-blueprint) describes a **10 MB total multipart request** bound, so bex's smaller decoded-manifest cap is an explicit divergence. The historical runs above remain unchanged as evidence of the mismatch that prompted this correction.
