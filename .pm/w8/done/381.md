# After a Blueprint is disconnected, its services' `render.yaml` env vars stay locked forever: every edit, delete and bulk replace answers 409 `ENV_VAR_MANIFEST_MANAGED` "edit the manifest and sync the blueprint", and reads still say `managedBy: blueprint`

Why: Render's disconnect "stops automatic resource syncing … It does not _delete_ any services or other resources that were managed by the blueprint" ([disconnect-blueprint](https://api-docs.render.com/reference/disconnect-blueprint)), so the services become ordinary ones. On bex, a variable the manifest declared with `value` or `fromService` can then never be changed or removed: no Blueprint is left to edit or sync, and the refusal points at one anyway.

- Severity: major. A customer who disconnects a Blueprint to manage a service by hand cannot change, rotate or delete those variables by any route (REST, CLI, dashboard, MCP share the guard). The only way out is to delete the service.
- Versions: bex CLI v0.9.0 release binary (Render CLI v2.36.0, pin per `lego/cli/UPSTREAM_RENDER_CLI.md`). Production pin `7e481dece7`. The code is unchanged on main `ba2564eca5`: no commit since the pin touches `secrets/` or the disconnect path.
- Context: 2026-11-21 19:45–19:58 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`). Routine `cli-qa`, nonce `bf3e`. Fixtures (all deleted, 404 confirmed): Blueprint `exs-dc0v9sm0ri4c73c3vth0` from `examples/blueprint-refs/render.yaml` with services `srv-dc0v9ue0ri4c73c3vtng` (app), `srv-dc0v9um0ri4c73c3vtpg` (peer) and `srv-dc0v9ue0ri4c73c3vtm0` (site), plus env group `evg-dc0v9u60ri4c73c3vtl0`.
- Attribution: server, `lego/backend/internal/apps` (disconnect) and `lego/backend/internal/secrets` (the guard).

The 409 body, verbatim: `{"code":"ENV_VAR_MANIFEST_MANAGED","error":"PEER_MARKER is declared in this service's render.yaml manifest, which owns its value — edit the manifest and sync the blueprint, or declare the variable with `sync: false` so the dashboard owns it instead","id":"conflict",…,"params":{"keys":["PEER_MARKER"]}}`.

`GET /v1/services/<app>/env-vars` after the disconnect lists `PEER_MARKER peer-marker-ok managedBy=blueprint` and `SITE_HOST blueprint-refs-site-panv.onbex.co managedBy=blueprint`, and `GET …/env-vars/PEER_MARKER` on the peer answers `"managedBy":"blueprint"`. The pinned CLI has no env-var edit verb for an existing service, so REST is the only route a CLI user has. The dashboard's Environment tab renders the same `managedBy` as read-only (w4/m120 t003).

## Root cause

- **The guard ignores the Blueprint's existence.** `refuseManifestKeys` (`lego/backend/internal/secrets/service.go:626`) refuses any key in `manifestEnv(a)` (`:282`). That function reads `a.Spec.Env` and treats every literal as declared unless the `bex.co/blueprint-env` annotation (`core/base.go:276-284`, `secrets/retained.go:55`) says otherwise. `SecretKeyRef` entries (`:297`) are always owned. The same map drives `managedBy` on every read (`:595`, `:955`, `:990`, `:1419`).
- **Disconnect leaves both in place.** `DisconnectBlueprint` (`lego/backend/internal/apps/blueprint.go:2156`) releases the claims and calls `clearBlueprintOwnership` (`apps/blueprint_ownership.go:560`). That only deletes the `core.LabelBlueprint` label (`:571-582`). It leaves `spec.Env` and the `bex.co/blueprint-env` annotation as the last sync stamped them (`stampBlueprintEnv`, `:323-336`), so every literal still reads as declared.
- **The mechanism for the fix already exists.** w21/m421 handles a variable a sync stopped declaring as a _retained_ literal: listed as ordinary, editable, and moved into the mutable store inside the write that names it (`secrets/retained.go:30-52`, `dropMovedRetained`). Disconnect never puts the service's literals in that state.

## Fix

1. **Disconnect makes every literal retained.** In `clearBlueprintOwnership`, for each App, patch the annotation `bex.co/blueprint-env` to the empty string (tracked, nothing declared) together with removing the label. `manifestEnv` then returns no literals, `managedBy` is empty, and the first write to each one moves it into the store through the existing w21/m421 path. The running process keeps its values until that write, as on Render.
2. **References.** A `fromDatabase` or Key Value reference is a `SecretKeyRef` on `spec.Env` and stays owned under step 1. On disconnect, resolve each into a store value (the value a container started now would get, `resolveManifestRefs`, `:309`) and drop it from `spec.Env` in the same App patch. Alternatively, teach `manifestEnv` that an App without `core.LabelBlueprint` owns no references, and make a write to one move it. Pick one and record it in ADR049 § Blueprint disconnect.
3. **Already-disconnected services.** Apps that carry `spec.Env` literals but no `core.LabelBlueprint` and no live Blueprint claim exist on production today. Either run a one-time backfill that stamps the empty annotation, or have `manifestEnv` read the missing label as "nothing declared". The second needs no migration and also covers step 2.
4. **Neighbors to check.** A sync that stops declaring a whole service (the w4/m125 `detach` action) and a takeover by another Blueprint must leave the same state. Count every caller of `clearBlueprintOwnership` and of the claim release.

## Fix (2026-11-21, `/loopx w8`, commit `6e75724eba`)

- Target, Render's [disconnect](https://api-docs.render.com/reference/disconnect-blueprint): "Disconnecting a Blueprint stops automatic resource syncing via the associated `render.yaml` file. It does not _delete_ any services or other resources that were managed by the blueprint." Render also says "You _can_ still make changes to a Blueprint-managed resource via other mechanisms … However, if any such changes conflict with Blueprint-defined configuration, the next Blueprint sync overwrites them" ([infrastructure-as-code](https://render.com/docs/infrastructure-as-code)). After a disconnect no sync is left to overwrite them, so the resources are ordinary ones.
- Every place a sync records ownership, checked:
  - On the App: `bex.co/blueprint-id`, `bex.co/blueprint-env`, and the `fromService` port records `app.bex.co/service-refs` and `app.bex.co/has-service-refs`. `ServiceRefPropagator` (20 s tick) would put back a port variable the owner had moved or deleted.
  - In Postgres: the claims, already released.
  - No Blueprint lock: env-group links (no guard), group variables (the mutable store), secret files (not declarable), static routes and headers, disks, custom domains (claims per App, not per Blueprint) and spec settings. Only the env verbs read the manifest.
- `DELETE /v1/blueprints/{id}`, GraphQL and MCP disconnect run the one `DisconnectBlueprint`. There is no separate delete path.
- `releaseBlueprintMarkers` (`apps/blueprint_ownership.go`) handles disconnect (`clearBlueprintOwnership`) and a sync that stops declaring a service (`clearBlueprintMarkers`, w4/m125). It drops the label, sets `bex.co/blueprint-env` to `""` and drops the port records, in one App patch. Every variable the last sync wrote is then retained (w21/m421): listed with no `managedBy`, and moved into the store by the write that names it.
- References (step 2): `retainedEnv` and `manifestEnv` treat an undeclared `SecretKeyRef` like a literal. Reads and the moving writes resolve it from its Secret (`resolveManifestRefs`, which now reads only the Secrets the given maps name). The write stores that value, or its own, and `dropSpecEnvNames` removes the reference. Resolving every reference at disconnect was rejected: it meant a store write per variable outside the App patch, or plaintext credentials in the App. As a consequence, a reference a connected sync stops declaring is retained too.
- Already-disconnected services (step 3): `declaredBlueprintEnv` reads an App that carries the record but no label as declaring nothing. No migration is needed. An App with no record keeps every variable declared: synced before w21/m421, or applied through `POST /v1/blueprints/deploy`, which has no Blueprint.
- Recorded in ADR049 § Blueprint disconnect.
- Tests:
  - `apps` `TestADisconnectedBlueprintsVariablesAreOrdinary`: create a Blueprint; edit, delete and bulk replace are refused while connected and succeed after the disconnect, with no `managedBy`.
  - `apps` `TestAServiceASyncStopsDeclaringHasOrdinaryVariables` (the w4/m125 path).
  - `apps` `TestADisconnectDropsTheServicesReferenceRecords`.
  - `secrets` `TestADisconnectedServicesVariablesAreOrdinary`: a literal and two `fromDatabase` references, both release shapes, set, delete, bulk replace and a rename that keeps the Secret's value.
  - `secrets` `TestAConnectedServicesReferencesFollowItsManifest`.
  - Each failed with the fix reverted, and the rename case failed without the reference resolution. The w21/m421 tests pass unchanged, except that their connected fixture now carries the label a connected service has.
- The env-group rename lead is real in code and filed as [w8/382](../blocked/382.md).
- Left: the production check, once the pin carries `6e75724eba`.
