## Closed — 2026-11-19 (loopx session)

- **Render's contract.** [render.com/docs/native-runtimes](https://render.com/docs/native-runtimes) lists `python3-dev`, `python3-pip` and `python3-setuptools` with the marker its legend defines as "Available both during builds and at runtime", on Debian 12 "bookworm", and names no versions (read 2026-11-19). It says nothing about which Python a Node service uses, PEP 668, `--user` installs or virtualenvs. bex supplies Debian 12's packages (t001–t003); which versions Render ships is unverified, and no Render-hosted comparison was run.
- **Build and runtime.** Build, pre-deploy and runtime share one image, so all three are present in every phase, as Render lists them (t004). The maintained checks reinstall the built wheel offline and run the embedded interpreter at the network-off runtime (t007), and both production services called the wheel and the extension on every request (t008).
- **Stated behavior, not a promise beyond Debian's.** Debian's `EXTERNALLY-MANAGED` marker stays, so a system or `--user` pip install is refused with `externally-managed-environment`, as on any Debian 12 host; `--target`, `python3 -m venv` and `--break-system-packages` work (t002). Render's page is silent on this, so it is recorded as observed behavior, not a divergence.
- **ADR060.** The D7 m103 row records the packages, the behaviors accepted, the exit statuses and the limits: system Python 3.11.2 only, no package index or build isolation, and a Python primary keeping its own pip, headers and manifest setuptools. It adopts with the next native rebuild on the current image, as every D7 tool does.
- **No surface change.** The tools arrive through the image every native build already uses. REST, GraphQL, MCP, Blueprint and the dashboard keep their schemas, fields and error shapes, and no selector, toggle or launcher change was added.
