## Closed — 2026-11-19 (loopx session)

Audited on main. The chain is the one w8/m94 to m102 traced, and no commit between production's pins `dff52c596d13` and `c81d2d447bd8` touches `deploy/native-base`, `deploy/native-common`, `native.go`, `nativeresolve.go`, `nativebases.go` or `nativecommon.go`.

- **One recipe chain.** `nativeDockerfile` (`native.go`) has one caller, the native build Job's preparer, and `cmd/native-resolve` ends with `applyNativeCommonBase` (`nativebases.go`). So every native web service, private service, worker, cron job and static-site build starts from the common image, whatever the primary (Node, Python, Ruby, Elixir, Go, Rust) and its companions.
- **Where each Python comes from.** `applyNativeCommonBase` re-copies only `/usr/local` from the selected primary, then sets the primary's environment, `PATH` included. Debian's interpreter and the three packages live in `/usr/bin`, `/usr/lib/python3*` and `/usr/include/python3.11`, so they survive every primary.
  - Node, Ruby, Elixir, Go and Rust primaries ship no `/usr/local/bin/python3`, so `python3` is Debian's 3.11.2 with these tools; sweep 424's Node 24 build is this case.
  - A Python primary puts its own `/usr/local/bin/python3` first on `PATH`. Its pip comes from the pinned official image and its setuptools, wheel and packaging from the offline manifest (ADR060 D7, below the table), and `check-primary-python.py` runs metadata, wheel, target and C-extension checks against its own headers on every families run. `/usr/bin/python3` keeps Debian's tools beside it. Nothing replaces a working primary interpreter.
  - A project's own virtualenv or `PYTHONPATH` still wins over both: bex sets no `PIP_*`, `PYTHONPATH` or `PYTHONHOME` (the image's only configured variable is `PATH`).
- **Phases.** Build, pre-deploy and runtime run one image: the pre-deploy Job runs the image the build produced. So the three packages are present at runtime too, as Render lists them. A static site's image is only its publish Job's extract source, so it has them at build only, and it publishes what its build wrote.
- **Cache and writes.** The base is digest-pinned, and tenant source and environment changes do not touch its layers. pip writes only to a named target or a virtualenv; Debian's site-packages refuse it (PEP 668). The checks passed as uid 1000 and as root on the replica (t007).
- **Exclusions.** Dockerfile, prebuilt-image and buildpack services never enter this recipe. A static site with no build command builds no native image.
- **Neighbors kept.** Node, npm, the other tools of the common image, native-init and the companion and package-manager steps are unchanged. m103 changes no product code.
- **Exercised versus source-only.**
  - Production (t008): build and runtime, Node 24 with Debian's Python 3.11.2, both CLIs, on `4b809600…`.
  - Maintained cohort: the frozen m103 program at the Node compute build and its network-off runtime (`node-compute`, through `original-cases.py`); the new packaging checks at that build and runtime and at the static build; and the three omission controls on the Node primary (t007).
  - Families runs on the same digest: the Python primaries' own packaging and headers, the other primaries, companions, native-init and static.
  - Not executed: a hosted pre-deploy run (Free refuses `preDeployCommand`, as Render does), ARM64 on production (D3) and trixie (the common image is bookworm only, as Render's runtimes are).
