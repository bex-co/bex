# A new Python service with no version signal builds on Python 3.13.16; Render's default for services created since 2026-10-12 is 3.14.8

Why: Render picks a Python service's default version by the service's creation date, and every service created since 2026-02-11 defaults to a 3.14 release. Bex's default line is 3.13 for every service. A Render app without a `PYTHON_VERSION` or `.python-version` therefore runs a different minor version on bex. That can change dependency resolution (wheel availability), language behavior and the version an app reports. ADR018 row 84 and ADR060 ("Python's default stays 3.13 although Render's creation-date default is now 3.14") record this without a user sign-off.

**Severity:** minor. **Attribution:** platform build (native default line). **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1307, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1307--runtime-versions)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`. `bex services create --type web_service --runtime python --plan free --repo https://github.com/render-examples/fastapi --build-command 'pip install -r requirements.txt' --start-command 'echo QAVER $(python --version 2>&1) && uvicorn main:app --host 0.0.0.0 --port $PORT'`, with no version signal. The service was created at 2026-10-22T03:34:44Z (`srv-dbco8l0u12fs73e9ai4g`). It went live in 221 s and logged `QAVER Python 3.13.16`. It was deleted (204 → 404). Sweep 1300's `mcp-server-python` showed the same thing (`/usr/local/lib/python3.13`).

## Expected

[render.com/docs/python-version](https://render.com/docs/python-version) default table:

| Service creation date | Render default |
| --- | --- |
| 2026-10-12 and later | 3.14.8 |
| 2026-02-11 to 2026-10-12 | 3.14.3 |
| 2025-06-12 to 2026-02-11 | 3.13.4 |
| earlier | 3.11.x |

A service created now builds on the 3.14 line (3.14.8 today, which is exactly bex's pinned 3.14 patch).

## Root cause

`lego/operator/internal/build/native.go:105`: `nativePythonRuntime: {label: "Python", defaultLine: "3.13", …}`. `ResolveNativeVersion` (`nativeversion.go:74`) falls back to `defaultLine` when there is no signal, regardless of the service's creation date. ADR060 D7 addendum: "No signal keeps the default … Python's default stays 3.13".

## Fix

Choose the default line from the App's creation timestamp, as Render does. Services created after this change get 3.14. Existing services keep 3.13, so an operator upgrade never moves a running service's toolchain; Render's creation-date table has the same effect. This is the WEB_CONCURRENCY cutoff pattern (w5/m147, `web_concurrency.go`). If bex wants Render's exact table instead (3.14 for every service created since 2026-02-11), get that decision in ADR018. Otherwise keep the cutoff and record the residual (existing pre-change services on 3.13) with sign-off. Narrate `==> Using Python 3.14 (default)` in the build log as today. Do the same check for Node: Render's table assigns 22.x to services created 2025-06-12 to 2026-04-21, while bex's Node default is 24 for every service. Apply the same creation-date rule if Node is in scope.

## Blast radius

Native Python web, private, worker and cron services, and Python-built static sites, with no version signal. One constant plus a creation-time input to `ResolveNativeVersion`. Existing services are unchanged under the cutoff.

## Acceptance

- Unit: no signal plus creation after the cutoff gives the 3.14 line; before it, 3.13. Any explicit signal still wins.
- Live after deploy: a new `render-examples/fastapi` service logs `Python 3.14.8`. A service created before the release keeps 3.13 on a manual redeploy. Delete by ID with 404 proofs.
