## Objective

When the pre-deploy Job's pod is waiting on `ImagePullBackOff`/`ErrImagePull`, fail the pre-deploy gate promptly (bounded retries, not the full 10-minute deadline) with `image pull is failing: <kubelet message>`. Share the wording with the rollout path (`stuckPodMessage`).

## Context

- `lego/operator/internal/predeploy/predeploy.go:224-257` (`FailureMessage`, `terminatedContainer`), `:71` (`predeployTimeout`).
- `failure_message_test.go:100` currently asserts the generic message for `ImagePullBackOff`. Invert it.

## Acceptance criteria

- [ ] A pre-deploy run with an unpullable image closes `pre_deploy_failed` within about 2 minutes, with the image-pull line.
- [ ] A slow but pulling image is not failed early (a control test with a transient `ContainerCreating`).

## Outcome (2026-09-26) — done

- `predeploy.PullFailure` (`lego/operator/internal/predeploy/predeploy.go`): the Job's pod has waited on `ErrImagePull`/`ImagePullBackOff` longer than `imagePullGrace` (90s from pod creation) → `image pull is failing: <kubelet message>; the pre-deploy command never ran`. `ContainerCreating` (a slow pull) and pods inside the grace window are never failed.
- `reconcilePreDeploy`'s pending branch checks it on every 5s requeue. It deletes the Job first (so a pull that succeeds later can never run the migration after the verdict; a failed delete retries), then records the verdict through `failPreDeploy`. The backend already closes the row from `status.preDeploy`. Expected close: ~95s after the pod starts, down from 611s.
- `FailureMessage` names the pull too when a failed Job's pod is stuck on it (deadline or not). The old `failure_message_test.go` "waiting" case now uses `ContainerCreating`.
- Tests: `TestFailureMessageNamesAFailingImagePull`, `TestPullFailureAfterGrace` (grace, slow pull, running, another Job's pod), `controller.TestPreDeployFailsFastOnAnUnpullableImage` (inside grace keeps running; past grace fails and deletes the Job).
