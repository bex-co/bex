# A client of a private Key Value's external URL still gets a bare TLS EOF, where Render presumably answers "AUTH failed: Client IP address is not in the allowlist."

Why: since w9/134 a private store's connection info hands out a `rediss://` URL over its reserved host, as Render's does. A client that uses it reads `SSL_connect failed: unexpected eof`, not the allow-list refusal that w8/m562 gives a refused source on a public store. The customer cannot tell a blocked store from an outage.

Severity: **minor** (parity; the message misleads, nothing is lost). Filed by `/loopx w8` from w8/m562 t006 (Render parity), 2026-11-22.

## What bex does

- A private store (created with `ipAllowList: []`, or cleared with `--clear-ip-allow-list`) has `status.reservedExternalHost` and no `status.externalHost` (w9/134, `4eda96b34f`).
- `kv-sni-proxy` routes only `spec.public` stores with a matching `status.externalHost` (`kvRouter.set`, `lego/operator/cmd/kv-sni-proxy/main.go`). A ClientHello for a private store's host resolves `unrouted` and is closed after the ClientHello, as an unknown name is.
- w8/m562's refusal path cannot answer it. That path ends TLS in the store's `kv-internal-proxy` with the store's `<id>-kv-tls` certificate, and a private store has no Certificate, by design, so it spends none of the Let's Encrypt budget (ADR021 § 3, w4/m357).

## What Render does (to verify)

- Render documents the refusal for "a disallowed IP address" (render.com/docs/key-value § Enabling external connections, read 2026-11-22). With an empty allow list every address is disallowed, so Render presumably answers the same refusal on its external URL.
- Not captured from Render. Verify first. Render routes its external Key Value endpoint by username on a regional host, so its TLS certificate exists whether or not any address is allowed.

## Possible fix

- Answer a private store's reserved host under the `*.kv.bex.co` wildcard once w4/m357 t002 lands (gated). `kv-sni-proxy` would then end TLS for refusals itself, for private and public stores alike, without per-store certificates.
- Or issue each private store's certificate anyway, which spends the per-domain budget w4/m357 is protecting.

## Acceptance

On a free Key Value in `bex-canary` created with `ipAllowList: []`, `valkey-cli --tls --sni <id>.kv.bex.co -h <id>.kv.bex.co -p 6379 PING` prints `(error) Client IP address is not in the allowlist.`, provided Render's capture shows the same. An unknown name is still dropped before TLS.

## Closed (2026-11-22): not a divergence

- **Render, checked.** render.com/docs/key-value (read 2026-11-22) says "By default, newly created Key Value instances are _not_ reachable at their external URL" (§ Enabling external connections), and `--clear-ip-allow-list` is how "to completely disable external access". Its dashboard shows no external URL for such a store: "External URL isn't shown? You first need to add at least one IP range to your instance's access control list. To continue blocking all external connections, you can add the dummy IP range `0.0.0.0/32`." The Terraform provider's `ip_allow_list` reads "If no IP addresses are provided, only connections via the private network will be allowed."
- **The refusal is for a list that refuses.** Render documents `AUTH failed: Client IP address is not in the allowlist.` for "a disallowed IP address". Its own way to publish a URL that refuses every source is the dummy `0.0.0.0/32` entry. No capture, staff answer or public report shows that refusal for an empty list. The one community thread with that title (`community.render.com` t/18092, early 2024, known only from search snippets because its forum host no longer resolves) is about a `0.0.0.0` entry whose `/0` the dashboard did not save, which is a non-empty list that refuses.
- **bex already matches both cases.** A private store is unreachable on its reserved host, and its dashboard shows the "add an inbound IP rule under Networking" note in place of the strings (w9/134, ADR021 §2). A `0.0.0.0/32` list makes the store public (`len(req.IPAllowList) > 0`, `lego/backend/internal/keyvalue/rest.go:372`), so w8/m562's refusal answers it once the pin carries `0eb545da0a`.
- No code changed. ADR021's note on private stores now cites this evidence.
