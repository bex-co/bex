# Log filters `task`, `taskRun`, and `sandbox` are accepted but silently ignored

Why: a caller who asks for one task run's logs and receives the service's entire log page has been silently widened — the exact failure mode the logs core promises never happens ("Every filter here is honored; a filter bex cannot honor is refused … never silently dropped", `lego/backend/internal/logs/service.go:243-246`; "never a silently widened query", `rest.go:507-512`).

Seen in the `/qa-find-bugs-cli` loop sweep 568, 2026-10-19, production, `bex-canary`, HEAD-build CLI, owned fixture `qa568-logs` (`srv-dbb6gavo17is73furrq0`, since deleted):

- REST `GET /v1/logs?ownerId=<ws>&resource=<svc>&limit=100` → 17 rows. Adding `&task=tsk-bogus568`, `&taskRun=run-bogus568`, or `&sandbox=sbx-bogus568` → the same 17 rows each. The control shows filtering itself works: `&host=bogus.example.com` → 0 rows, `&instance=instance-bogus568` → 0 rows.
- CLI parity: `bex logs -r <svc> --task-id tsk-bogus568` and `--task-run-id …` print the full unfiltered page (17/17). The pinned client is not the gap: `pkg/tui/views/logloader.go:170-171` maps the flags onto `ListLogsParams.Task/TaskRun` (form names `task`/`taskRun`), so they reach the server.
- Misspellings are handled correctly by contrast: `taskId=`/`taskRunId=`/`surpriseParam=` → `400 unsupported query parameter … for list-logs`. Only the three *declared* names slip through: the Render OpenAPI gate admits every parameter the pinned operation declares, but `parseLogParams` (`lego/backend/internal/logs/rest.go:513`) never reads `task`/`taskRun`/`sandbox`, and `LogQuery` has no fields for them — so they vanish between the gate and the parser.

Root shape: the strict-query gate derives the allowed set from the pinned OpenAPI (`buildAllowedQueryNames`), which includes Render's workflow/sandbox log filters; the handler's parser implements only the ADR010 § Log filters subset. Nothing downstream can match on task labels today (no shipped stream carries `task`/`taskRun`/`sandbox` labels; Workflows are a recorded non-goal, ADR018 "Render Workflows" omission row). GraphQL/MCP are already honest — their schemas expose no such arguments.

Fix (pick the honest arm, ≤1h either way):

- **Preferred:** thread the three filters through `parseLogParams` → `LogQuery` → the store/label matching the other structured filters use, so a bogus value returns an empty page today and real workflow/sandbox streams work if labels ever ship. The live tail cannot honor store labels: add them to `tailSupports()`' refusal set so `/logs/subscribe` refuses by name instead of streaming unfiltered (`/logs`, `/logs/values`, `/logs/subscribe` all share `parseLogParams`).
- **Acceptable alternative:** refuse the three parameters by name on the logs routes as unsupported (consistent with the Workflows non-goal) — but then the refusal must fire on all three routes and be recorded in ADR010's filter table / ADR018, not left as an invisible parser omission.

Either way, add a regression test at the parser/route level pinning that a declared-but-unimplemented filter can never widen: bogus `task`/`taskRun`/`sandbox` must not return the unfiltered set. (A generic guard — every OpenAPI-declared `list-logs` query name is either parsed into `LogQuery` or named in an unsupported set — would close the class.)

Acceptance:

- On an owned fixture with known log rows: `bex logs -r <svc> --task-id tsk-bogus` and `--task-run-id …` return zero rows (or the named unsupported refusal), never the full page; same for REST `task`/`taskRun`/`sandbox`.
- Unfiltered and supported-filter reads (host/instance/method/path/statusCode/level/text) are byte-unchanged.
- `/logs/subscribe` with a task filter refuses before streaming (or honors it); `/logs/values` agrees with `/logs`.

Severity: minor (no wrong mutation; a debugging user is misled about which logs they are looking at, and an agent filtering by task run silently reads everything). Estimate: ~45m.

**Done (2026-10-19, `f8008fcb3`, live after pin `ca30db3a3646`):** the three filters are refused by name on the logs routes. Live on production: `GET /logs?…&task=tsk-bogus738` (and `taskRun`, `sandbox`) → `400 log filter "task" is not supported: bex runs no Render Workflows or sandboxes, so no log belongs to one`; `/logs/values?label=level&task=…` refuses identically; `bex logs --task-id tsk-bogus738` surfaces the same 400 instead of the unfiltered page. The `/logs/subscribe` arm was not re-probed live (websocket); the refusal fires in the shared `parseLogParams` the subscribe route also uses.
