# A service create or Blueprint with an out-of-range `numInstances` is refused as "replicas must be 0-100", naming bex's internal field and a range Render's contract does not have

Why: `bex services create --num-instances -1` (or `101`) tells a Render user about a `replicas` field they never sent, with a lower bound of 0. Bex's own `/scale` names `numInstances must be 1-100`, and the pinned contract says `minimum: 1`.

- Severity: minor. The request is refused correctly, but the message names the wrong field and range.
- Versions: production pin `820edf28d22d`, main `bcf51d886`, CLI `bex-cli/v0.7.0` (Render CLI v2.36.0, which sends the flag value as `serviceDetails.numInstances` with no client check).
- Context: routine `cli-qa` run r18-7abd, 2026-11-21 01:33–01:36 UTC, `bex-canary`, human device-login token, `-o json`, non-TTY. Every refusal below created nothing: a REST name lookup returned `[]`.

## Repro

```text
$ bex services create --name qa-…-ni --type web_service --image docker.io/library/nginx:1.27-alpine \
    --plan free --num-instances=-1 -o json --confirm </dev/null
Error: received response code 400: bad request: replicas must be 0-100      (exit 1; same for 101)

POST /v1/services?dryRun=true  serviceDetails.numInstances: -1  → 400 {"id":"bad_request","message":"bad request: replicas must be 0-100"}
POST /v1/services?dryRun=true  serviceDetails.numInstances: 0   → 200, reads back numInstances 1
POST /v1/services/<id>/scale   {"numInstances": -1 | 0 | 101}   → 400 "bad request: numInstances must be 1-100"

bex blueprints validate render.yaml -o json   (web, plan starter)
  numInstances: -1 / 0 → "at '/services/0/numInstances': minimum: got -1, want 1"   (pinned schema)
  numInstances: 101    → "service \"qa-bp-ni\": replicas must be 0-100"
```

## Cause

`lego/backend/internal/apps/service.go:3838` (`normalizeCreateDefaults`) checks `req.Replicas < 0 || req.Replicas > store.MaxReplicas` and formats `replicas must be 0-%d`. Two things make that wrong for Render-shaped callers:

- 0 means "unset, default 1" because `CreateRequest.Replicas` is a plain `int32`. That is why the range reads 0-100.
- `replicas` is the name in GraphQL `createService(replicas:)` (`graphql.go:822`), the one caller for whom the message is right. REST create (`apps/rest.go:270`/`:674`, `serviceDetails.numInstances`) and Blueprint apply and validate pass the same message through. `Scale` (`service.go:4929`) already says `numInstances must be 1-%d`.

The pinned OpenAPI (`render-public-api-1.json`, `webServiceDetailsPOST.numInstances`) is `{"type":"integer","minimum":1}`, and the pinned Blueprint schema refuses 0 and below (`minimum: got 0, want 1`).

## Fix

In the REST adapter, validate `serviceDetails.numInstances` before it becomes `Replicas`, and do the same in Blueprint validation and apply. Use Scale's wording: `numInstances must be 1-100`. Two ways to do it:

- Pass the caller's field name into `normalizeCreateDefaults`.
- Check in each Render-shaped caller and leave the shared check as the GraphQL backstop.

Whether REST should refuse an explicit `numInstances: 0` to match `minimum: 1` needs presence detection (`*int32` or a raw-key check). Render's actual answer to 0 is unmeasured, so take it only if it falls out of the change. Otherwise note it as a follow-up and do not let it gate the wording fix.

## Blast radius

- Callers of `normalizeCreateDefaults` to check: REST create and dry-run, the Blueprint plan and apply paths, MCP create (`apps/mcp.go:337` maps `Replicas`), and GraphQL. GraphQL keeps `replicas` because that is its argument name.
- Update `create_normalization_test.go:364`/`:370`, which assert the old text.

## Acceptance

- `bex services create … --num-instances=-1` and `=101` exit 1 with a message naming `numInstances` and `1-100`, and create nothing.
- A Blueprint with `numInstances: 101` fails validation with the same wording at `services[0].numInstances`.
- `--num-instances=1` still creates and reads back `numInstances: 1`.
- GraphQL `createService(replicas: -1)` still says `replicas`.
- `cd lego/backend && go test ./internal/apps/...` passes.

## Dedupe

- `rg 'replicas must be' .pm docs` finds nothing.
- The free-plan `--num-instances 2` refusal ("free plan is limited to 1 instance(s)") was checked clean on 2026-11-17 and is a different path.
- `PATCH serviceDetails.numInstances` answering 400 "unknown field" matches the pinned contract: `webServiceDetailsPATCH` has no `numInstances`, and the pinned CLI hides and refuses `--num-instances` on update.

Estimate: ~30m.

## Outcome

- 2026-11-21 triage: the premise held at main `8e6dc9a06`. `normalizeCreateDefaults` (`service.go:3838`) said `replicas must be 0-100` for every create, and REST, GraphQL and MCP took an explicit 0 as "default 1".
- Render's contract, read 2026-11-21:
  - The pinned OpenAPI gives `numInstances` `minimum: 1` ("Defaults to 1") on all three `*DetailsPOST` schemas. The pinned Blueprint schema has `minimum: 1` too. The scale body has no minimum in the spec, and bex's 1-100 there stands.
  - render.com/docs/scaling caps a paid plan of up to 8 CPU / 32 GB at 100 instances (larger plans 5, free 1). Every bex plan is in the first class: `pro-ultra` is 8 CPU / 32 GB.
  - Render's own wording for an out-of-range count is unmeasured.
  - The pinned CLI sends `numInstances` only when `--num-instances` is given (`*int`, omitempty, and clone skips 0). Render's Terraform provider sends 1 in every recorded create. Refusing an explicit 0 breaks no known client.
- Verdict: work.
- Fixed in `8a90e166b`:
  - `validateInstanceCount(field, n)` is the one 1-100 rule. `Scale` uses it.
  - REST create reads `serviceDetails.numInstances` as optional. -1, 0 and 101 answer 400 `numInstances must be 1-100`, dry run included, and create nothing. Only an omitted count defaults to 1.
  - GraphQL `createService(replicas:)` and MCP `create_web_service(replicas:)` check their own argument and say `replicas must be 1-100`, explicit 0 included. Both are bex extensions (ADR006) and keep their names.
  - Create's backstop now says `numInstances`, which is what a Blueprint reaches. Validate locates it at `services[i].numInstances`. Apply refuses it for a new service and for one the file already manages.
  - Tests: `instance_count_bounds_test.go` (REST with dry run, GraphQL, MCP, Blueprint validate and apply). Each fails with the fix reverted. `create_normalization_test.go` asserts the new text.
  - ADR018's manual-scale row records the bounds.
  - Checks: `go test ./internal/apps/ ./internal/api/ ./internal/events/`, golangci-lint on `internal/apps`, and the ship gates' real-DB backend suite pass. No operator code changed.
- Parked: production's pin `f797f525f5df` predates the fix. Once the pin carries `8a90e166b`, run the Acceptance in `bex-canary`, adding `--num-instances=0`, GraphQL `replicas: 0` and MCP `create_web_service(replicas: 101)`. Delete the `=1` fixture, then close.
