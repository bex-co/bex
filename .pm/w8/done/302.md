# A Blueprint re-sync writes a nameless env var onto a service that declares the `PORT` it serves, and Kubernetes then refuses the service's pod template

Why: every Blueprint sync plans, then applies, one parsed stack. That covers a manual sync, an approval, an auto-sync, a Blueprint create over existing services, and `deployStack`.

- **Shared array.** The plan's target spec shares its `Env` array with that stack (`specFromCreate` assigns `req.Env`).
- **In-place delete.** For an existing service, `dropServedPortEnv` (`lego/backend/internal/apps/blueprint_generate.go:851`, w4/411) removes a literal `PORT` that restates the served port with `slices.DeleteFunc`, which compacts the array in place and zeroes its tail.
- **The apply reads it shifted.** It then merges a variable with no name into `spec.env`.
- **Kubernetes refuses it.** The operator copies `spec.env` into the container (`appEnv`), and Kubernetes refuses a pod template whose env has an empty name. So the service's Deployment can no longer change.

The apply's own drop (`updateStackService`) does the same to the request that a forward `fromService` host reference re-applies in its second pass.

**Who hits it:** any service whose Blueprint declares a literal `PORT` equal to the port it serves, from its second sync on. That includes every file Generate Blueprint writes for a service on a non-default port, since the exporter spells that port as `PORT` (w4/411). Live since `6e9eb5809` (2026-10-25).

**Severity:** major (a service stops taking deploys after a routine sync). **Attribution:** server (bex-api Blueprint apply), with the operator passing the value through. **Source:** found in the /simplify efficiency review of the w8/300 fix (2026-11-13), then reproduced with a unit test. Not yet observed live.

## Evidence

`DeployStack` twice with this file:

```yaml
services:
  - name: web
    type: web
    runtime: docker
    repo: https://github.com/bex/stack
    envVars:
      - { key: PORT, value: "10000" }
      - { key: APP_ENV, value: prod }
```

After the second apply, `spec.env` reads `PORT=10000, APP_ENV=prod, ""=""`. Adding a host reference to a service the same sync creates gives `PORT, APP_ENV, "", API_HOST`. The App CRD's `name` has no `minLength`, so the API server stores it.

## Fix

- **Root cause:** `specFromCreate` (`lego/backend/internal/apps/service.go`) gives the spec a copy of the request's env (`slices.Clone(req.Env)`) instead of the request's own array. So no in-place edit of a spec it built reaches a later read of the request: not `dropServedPortEnv` in the plan or the apply, and not the latent `storeEnvKeys` delete in `updateStackService`.
- **Healing a service an earlier sync damaged:**
  - the operator skips a nameless variable in the runtime (`appEnv`) and native build (`buildEnv`) env, as `buildEnvRefs` already did, so the next reconcile rolls again;
  - the next sync drops it (`mergeBlueprintEnv`) and plans that as an `envVars` change;
  - env reads (`manifestEnv`) no longer list it.

## Regression checks

- `TestReSyncOfAServedPortWritesNoNamelessVariable`: the same file twice, and a re-sync adding a forward host reference. Both failed before the fix.
- `TestSyncDropsANamelessVariableAnEarlierSyncWrote`, `TestANamelessManifestVariableIsNotListed`, and the operator's `TestANamelessVariableReachesNoContainer`. Each fails with its guard removed.
- **Production, after the next roll:** generate a Blueprint from a free web service whose app listens on a non-default `PORT`, create a Blueprint from that file, sync it twice, and check that `GET /v1/services/<id>/env-vars` lists no blank key and that a later deploy goes live.

## Unverified

Whether any production service already carries a nameless variable. Such a service has a Deployment that cannot update; the operator change heals it on the first reconcile after the roll.
