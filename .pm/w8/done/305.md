# A Key Value's connection info answers 409 "credentials are still converging" through every restart, though its credentials never change

Why: `GET /v1/key-value/{id}/connection-info` is the read behind:

- `bex kv-cli`;
- the dashboard's Connect panel;
- GraphQL and MCP connection reads;
- any script that copies the URL.

Render returns it as plain data. On bex it answers `409 {"message":"conflict: key value credentials are still converging"}` for the whole restart that a persistence change or a resume causes, about 20 s each time on a free store. Nothing about the credentials changes: a Key Value's password is immutable (w2/m61, "user-driven password rotation remains deliberately unsupported"). So the refusal and its message are both wrong, and a `bex kv-cli` started in that window fails with a message that suggests a credential problem.

**Severity:** minor (transient; connections themselves are unaffected beyond the restart). **Attribution:** server (bex-api Key Value connection info). **Estimate:** ~30m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `b7c4`, 2026-11-13 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `4c3c68e6b05b`.

## Evidence

Fixture: free Key Value `qa-20261113-b7c4-kv` (`red-dbrcal0v8soc73b22ppg`), created with `--persistence-mode off` and an allow-list, deleted afterwards (GET 404). Each status and connection-info read was polled every 4–5 s:

```text
# bex keyvalues update <kv> --persistence-mode snapshot --confirm
08:10:51 config_restart  HTTP 200
08:10:56 config_restart  HTTP 409  conflict: key value credentials are still converging
08:11:01–08:11:10 the same three more times
08:11:15 available       HTTP 200

# bex keyvalues suspend → every read during the suspension: suspended, HTTP 200

# bex keyvalues resume
08:12:40 config_restart  HTTP 200
08:12:45–08:13:00 config_restart  HTTP 409  conflict: key value credentials are still converging (4 reads)
08:13:06 available       HTTP 200
```

The first persistence change (`off` → `journal_snapshot`) showed the same window.

The rest of the journey passed. With `off` → `journal_snapshot` the marker key was gone afterwards, as Render documents for a change to or from Off. With `journal_snapshot` → `snapshot` the marker survived. `options.persistenceMode` read back each new mode, and PING answered once `available`.

## Root cause

`lego/backend/internal/keyvalue/service.go:1322-1325` (`KeyValueConnectionInfo`) refuses when `kv.Status.Phase != KVPhaseReady`, as well as when `status.credentialRevision` is empty or differs from the Secret's password. w2/m61 (c754afc72) added both conditions. The revision alone carries the guarantee it wanted: the operator sets `status.credentialRevision` only once the rollout and its pods are Ready on that revision, or the store is suspended (`keyvalue_controller.go:1183-1185`). Any restart moves the phase off Ready, so the extra condition refuses every restart, where the recorded revision still matches the unchanged password.

## Fix

- **Drop the phase condition.** Keep `credentialRevision == ""` (first provisioning) and a revision mismatch as the refusals.
- **Unchanged:** first provisioning still answers 409 until the first Ready, and any future credential change is still refused until its pod uses it.
- **Test:** a store in `config_restart` (phase not Ready, matching revision) returns its connection info; an empty or mismatched revision still answers 409.

## Blast radius

- **Surfaces:** REST `connection-info`, GraphQL and MCP connection reads, `bex kv-cli`, and the dashboard Connect panel, through the shared `KeyValueConnectionInfo`.
- **Windows:** every restart: persistence changes, resume, plan changes, and failover-style restarts.

## Dedupe

- w2/m61 (done) introduced the guard.
- w8/237 (done) gated only the external URL on the TLS listener.
- No `.pm` item covers the restart window.

## Resolution

**DONE 2026-11-13.** `KeyValueConnectionInfo` refuses only when `status.credentialRevision` is empty or differs from the Secret's password, no longer when the phase is not Ready. `TestConnectionInfoGatesImmutableCredentialRevision` now also covers a restarting store (phase `Provisioning`, matching revision), which is served, and fails when the phase condition is restored. The mismatch and first-provisioning refusals are unchanged. ADR021's step 4 records it. Production check after the next roll: on a free Key Value, `connection-info` polled through a persistence change and a resume answers 200 throughout.

**Production check passed 2026-11-13 (sweep `41e2`, pin `5de3d5bcc`).** On the template's free Key Value (`red-dbrdvc0k58is73aunq10`), `--persistence-mode snapshot` read `config_restart` for about 11 s, and `connection-info` answered 200 at every read (10:13:58–10:14:09). Deleted (GET 404).
