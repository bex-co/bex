# Every REST operation shares one 500-a-minute bucket and reports `RateLimit-Limit: 500`, where Render's rate-limiting reference gives per-endpoint budgets (400 GETs, 30 writes and 30 log reads a minute, 20 service creates an hour, 10 deploys a minute per service)

Why: the `RateLimit-*` headers exist so scripts can pace themselves, and bex reports a budget Render does not have. ADR006 and ADR018 call bex's 500 a minute "Render's documented API rate limit", but the page they cite no longer says that, so the parity row rests on a stale reading.

**Severity:** minor (parity: the headers are present and truthful about bex's own limiter, but the budget differs from Render's). **Attribution:** server (bex-api shared limiter). **Estimate:** ~2h. **Source:** routine `cli-qa` sweep r33, 2026-11-22 21:50–22:10 UTC, released `bex v0.9.0` (Render CLI pin `4fd34231b637`), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login. The run was read-only: about 150 requests at human pace, no flood and no 429 provoked.

## Evidence

- **bex, live.** Five back-to-back `GET /v1/services?ownerId=<bex-canary>&limit=1` calls, a `HEAD`, a GraphQL `{ __typename }` and every refusal in the sweep (400, 404 and 405) all carry `RateLimit-Limit: 500`, `RateLimit-Remaining: 498` or `499` and `RateLimit-Reset: 1`. A `POST` refusal reads the same as a `GET`.
- **Render.** [api-docs.render.com/reference/rate-limiting](https://api-docs.render.com/reference/rate-limiting), read 2026-11-22: "Rate limits are shared for a set of endpoints … All but one of these rate limits apply for your user except for deploys which is per service." The table:

  | Endpoints | Budget |
  | --- | --- |
  | `POST /v1/services` | 20 an hour |
  | `PATCH /v1/services`, `POST …/deploy`, `POST …/resume`, `POST …/suspend`, deploy hooks | 10 a minute per service |
  | `POST /v1/customdomain`, `POST /v1/customdomain/verify` | 50 an hour |
  | `POST /v1/jobs` | 100 a minute |
  | `GET /v1/logs`, `/logs/subscribe`, `/logs/values` | 30 a minute |
  | all other `POST`/`PATCH`/`DELETE` | 30 a minute |
  | all other `GET` | 400 a minute |

  The page's example shows `Ratelimit-Limit: 100`, `Ratelimit-Remaining: 99` and `Ratelimit-Reset: 45` on `curl -I https://api.render.com/v1/owners`. The figure 500 does not appear anywhere on the page.
- **bex's records.** `docs/ADR006-bex-api.md:679` says "Render's documented API rate limit is **500 requests per minute per API key** (source: api-docs.render.com/reference/rate-limiting …)". ADR018's "Rate limits" row (`docs/ADR018-render-parity.md:369`) says "Render: 500 req/min per API key … same 500/min default". w8/147 (done) added the headers and wrote "Render's per-endpoint numbers are not adopted by this item". No item has picked them up since.

## Root cause

`lego/backend/cmd/api/config.go:827` sets `BEX_RATE_LIMIT` to 500 a minute, with the burst defaulting to the rate. `api.NewRateLimiter` (`lego/backend/internal/api/ratelimit.go:72`) charges every request it does not classify to the caller's bucket and the workspace bucket (`generalBuckets`, `:128`). `core.SetRateLimitHeaders` (`lego/backend/internal/core/ratelimit.go:153`) reports the tighter of the two. Only sandbox operations are classified (`rl.Operations.RequestBuckets`, `ratelimit.go:97`). w22/m443 adopted Render's per-operation sandbox table that way (ADR018:619).

## Fix

1. Classify the Render-contract REST operations into Render's seven rows through the same `Operations` hook the sandbox table uses. Each row gets its own per-user bucket (a user's API keys and session share it, as on the sandbox rows). The deploy row is keyed per service and also covers bex's deploy-hook limiter (10 a minute per service). The headers then report the row's bucket, so `RateLimit-Limit` reads 400 on a GET and 30 on a write.
2. MCP tools that map one-to-one to a classified operation count against the same row, as the sandbox rows do. GraphQL is the dashboard's transport, so it stays on the general bucket. Record that in ADR018 as a looser variant and file stricter handling separately if it is wanted.
3. Correct ADR006 § Rate limits and the ADR018 "Rate limits" row to quote the current table, and keep `BEX_RATE_LIMIT` as the GraphQL and unclassified budget.

## Blast radius

- Every REST and MCP caller. A script that creates more than 20 services an hour through `POST /v1/services` starts receiving 429s with `Retry-After`. Blueprint applies create services internally, not through that route, so they are not affected.
- The QA routines' REST probes stay well inside 400 GETs a minute. Teammate harnesses that create services in bulk through REST (`scripts/`) need checking.

## Regression checks

- REST `GET /v1/services?limit=1` reports `RateLimit-Limit: 400`, and the 401st GET within a minute answers 429 with `Retry-After`.
- A rejected `POST /v1/env-groups` reports `RateLimit-Limit: 30`, and `GET /v1/logs` reports 30.
- 21 `POST /v1/services` refusals within an hour: the 21st answers 429, in a unit test with a fake clock, never against production.
- `POST /v1/services/{id}/deploys` counts per service: two services each get 10.
- Sandbox rows and GraphQL keep their current budgets.

## Resolution (2026-11-22, `/loopx w8`)

Shipped in `696783e94e`. Parked for the production read below.

- **REST.** A request bex's mux routes to an operation of the pinned Render spec spends that operation's row (`lego/backend/internal/api/render_ratelimit.go`), after the sandbox table, which still decides first. `RateLimit-Limit` reports the row: 400 on a GET (a HEAD counts as a GET), 30 on a write (a PUT counts as one, though Render's page names only POST, PATCH and DELETE) and on a log read, 20 on `POST /v1/services`, 50 on a custom-domain create or verify, 100 on a job create, and 10 on the deploy row. A refused request counts, because the limiter runs before validation. A user's API keys share their rows through the key's recorded creator (`core.RateLimitUser`, now shared with the sandbox rows). The deploy row is keyed by the `{serviceId}` path value. A 10,000-a-minute workspace bound stays as bex's abuse bound.
- **MCP.** The 28 Render tools bex serves spend the row of the REST request `render-mcp-server` makes for each, because its tools call Render's public API with the caller's key (one call, one token). They give the request's general token back. `trigger_deploy` spends its service's deploy row. A refusal is a tool error coded `rate_limited`. bex-only tools keep the general budget. `TestEveryRenderMCPToolHasARow` holds the table against the pin.
- **GraphQL, and the dashboard on REST.** Both keep `BEX_RATE_LIMIT` (500 a minute, now cited as bex's own figure). GraphQL mirrors Render's dashboard operations, not its public API, and Render's page names no limit for it. A Kratos session on REST is the dashboard's browser, so its calls keep the general budget too: the log tail (`dashboard/src/features/logs/hooks/use-live-logs.ts`, `GET /v1/logs/subscribe`), the webhook edit (`PATCH /v1/webhooks/{id}`), the delivery's event read and the audit CSV export.
- **Internal callers are not throttled, unchanged.** The `:8091` listener (the SSH gateway's, Kratos's, the object gateway's and the operator-run verbs) has no limiter. The operator never calls bex-api, and the reconciler runs in process. The webhook intakes sit outside the gate on `BEX_WEBHOOK_RATE_LIMIT`, and `/healthz` is unmetered.
- **Deploy hooks.** A hook call now spends its service's deploy-row bucket after the lookup, the bucket the REST and MCP deploys spend. The per-token bucket before the lookup moves to Render's ten a minute, burst ten (it was six, burst two).
- **Headers.** `RateLimit-Reset` stays in seconds. Render's page calls it a UTC epoch time, but its own example reads `45`, and the pinned spec's `429RateLimit` says "Seconds until the current rate limit window resets".
- **Tests.** `lego/backend/internal/api/render_ratelimit_test.go` covers each row's header, 20 creates an hour across one user's keys (the 21st answers 429 with `Retry-After: 180` on a fake clock, and one more passes three minutes later), the per-service deploy row across update, deploy, suspend and resume, a hook sharing its service's row, a session keeping 500, the MCP rows, the sandbox table asked first, the rows being off without the limiter, and both tables against their pins. Each was mutation-checked: removing the REST rows, the hook's share, the MCP middleware, the session exemption, the hourly window, the per-service key or the sandbox-first order fails its test.
- **Docs.** ADR006 § Rate limits now quotes the current table. ADR006's deploy-hook paragraph, ADR018's Rate limits and Secret deploy hook rows, `docs/render-artifacts/rate-limit-headers.md` and the backend env table are amended to match.

### What the stricter budgets mean for QA routines

- **Service creates are the tightest budget: 20 an hour per user,** whether they come through REST, `bex services create` or an MCP create tool.
  - The `cli-qa` sweeps are read-only or create a handful of fixtures, and `deploy-canary` creates one a week.
  - `scripts/cli-services-parity-verify.sh` creates about ten services per run, and `scripts/samples-lifecycle.sh` several. Two back-to-back runs as one user inside an hour can reach the cap.
  - Past the cap, each create answers 429 with `Retry-After: 180`. A routine should pace its creates, or retry on `Retry-After`, rather than fail.
  - A Blueprint apply creates its services internally, so it does not spend this budget.
- **Deploys:** 10 a minute per service, across deploy, update, suspend, resume and the hook.
- **Log reads:** 30 a minute per user. `bex logs` polled more often than every two seconds gets 429s.
- **Other calls:** GETs at 400 a minute and other writes at 30 a minute leave ordinary probes far inside their budgets.
- **Replicas:** bex-api runs two replicas and each counts alone, so the effective ceilings are up to twice these figures.

"Remaining falling by one" is reworded as unit-tested, because two live requests cannot show it:

- **Why a pair reads 399 twice.** The read row holds 400 tokens and refills one every 150 ms. `NewRenderRateLimits` gives each row its own figure as its burst (`lego/backend/internal/api/render_ratelimit.go`). `RateLimit-Remaining` is the whole number of tokens left (`core.SetRateLimitHeaders`). A GET on a full bucket leaves 399. A second GET 150 ms or more later finds the bucket full again and also reads 399. So two requests a few hundred milliseconds apart read what the read above saw three seconds apart.
- **Why a faster pair is not a check either.** Only a second GET within 150 ms that reaches the same replica reads 398. Each of bex-api's two replicas counts alone, and nothing in front of them pins a client to one. A 399/399 pair would prove nothing, so it was not sent.
- **The unit tests.** `TestRenderRowsReportTheirOwnBudgets` (`lego/backend/internal/api/render_ratelimit_test.go`) runs on a fixed clock. `GET /v1/services?limit=1` reads `RateLimit-Limit: 400` with Remaining 399, then a `HEAD` on the same row reads 398. `TestRateLimiterSendsRenderRateLimitHeaders` (`ratelimit_test.go`) reads Remaining 2, 1 and 0, then a 429 with 0. `TestSetRateLimitHeadersReportsTheTightestBucket` (`internal/core`) checks that the headers report the tightest of the buckets a request spends, with Remaining as whole tokens. All three passed on `27a27e53e8`, re-run on 2026-11-23 with the rest of the `RateLimit` tests in `internal/api` and `internal/core`.
