# A refused `bex sandboxes copy` upload over about 512 KB often stalls for two minutes and then answers `503 sandbox file gateway unavailable`, in place of its prompt `409` or `404`

Why: an upload onto an existing directory, or into a missing parent, must be refused at once with the gateway's own answer (`409 sandbox destination exists or is not a supported file target`, or `404 file_not_found`). For a small body that is what happens. For a body over about 512 KB the transfer usually hangs. bex-api waits out its two-minute bound on the gateway's response headers, then answers `503 sandbox file gateway unavailable`. The CLI user waits two minutes, then reads an outage message for what was a plain mistake. The Render SDK's 45 s read timeout gives up first and raises a timeout, not `SandboxFileNotFoundError`. Re-running `copy ./project sbx-…:/home/render/project` is the everyday way to hit it.

**Severity:** major (a refusal on a common path becomes a two-minute stall and a wrong status; successful transfers are unaffected). **Attribution:** server (ssh-gateway sandbox file transfer and its pods/exec stdin stream; bex-api only reports the stall). **Estimate:** ~1h. **Source:** `/qa-find-bugs-cli` w8 loop sweep `daae`, 2026-11-13 UTC, released `bex v0.6.0` (Render CLI v2.36.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `1c4d721bc8dc`.

## Evidence

Fixture: sandbox `sbx-dbrm5q5d9ioc73ds1arg` (group `sbg-dbrm5old9ioc73ds1aqg`, plan `1c-2g`, running). `/home/render/dir1` already existed. Every attempt below is a fresh `bex sandboxes copy <local> <sbx>:<path>` process with a 15 s client timeout, run one after another. Each `N/M` cell is the attempts that stalled out of the attempts run; the rest were answered in 0.9–3.8 s. A control request to an unknown `*.onbex.co` host answered 404 in about 0.2 s throughout, so the host network was clean.

| Upload | Refusal | Stalled |
| --- | --- | --- |
| directory with one 64 KB file onto existing `/home/render/dir1` | 409 | 0/4 |
| directory, 512 KB | 409 | 1/4 |
| directory, 1 MB | 409 | 3/4 |
| directory, 3 MB (one 3 MB file, an empty file, a nested file) | 409 | 4/4, and 4/6 in an earlier run |
| the same 3 MB directory into missing `/nonexistent-dir/d` | 404 | 1/4 |
| a single 3 MB file onto the existing directory | 409 | 3/4 |
| a single 3 MB file into a missing parent | 404 | 3/4 (0/2 in an earlier pair) |

Allowed to run, a stalled attempt ended after 121.3 s with `Error: received response code 503: sandbox file gateway unavailable` (exit 1). Its execution record (`GET /v1/sandboxes/{id}/execs`) runs from 19:21:55.02 to 19:23:54.92, two minutes. The destination was never changed and no `.bex-copy-*` staging directory was left. A 64 KB refusal, or the same uploads to a free path (3 MB file, 3 MB file by relative path, the nested directory), finish in 1.5–2.8 s. Downloads round-trip byte for byte (sha256 matched).

## Root cause

What is traced:

- The 503 is bex-api's reverse-proxy `ErrorHandler` (`lego/backend/internal/sandbox/file_connect.go:281-283`). It fires because the gateway sent no response headers within `sshgateway.NewUpstreamClient(2 * time.Minute)` (`lego/backend/cmd/api/main.go:1427`). That line's comment assumes the gateway answers "a file transfer's [headers] once it is written, so 2m never cuts either short". A stalled refusal breaks that assumption.
- The gateway's `upload` (`lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go:357`) starts the staging exec with the request body piped into its stdin (`:446`). `stageScript` (`:312-333`) checks the destination first and exits 73 (exists, `:316`/`:318`) or 66 (missing parent, `cd_parent` `:302`) **before reading any stdin**. After the exec, `upload` closes the body (`:450`) and waits for the copy goroutine (`:451`).

The probable stall, not yet observed on the cluster: the gateway keeps writing the upload into an exec stream whose process has exited and will never read it. `KubeExecutor.Execute` (`lego/backend/internal/sshgateway/exec.go:187-215`) uses client-go's SPDY executor. Its stdin copy goroutine stops making progress once the kubelet stops draining that stream, after about the size of its pipe and socket buffers. `StreamWithContext` then waits in its deferred `conn.Close()` (client-go v0.37.1 `tools/remotecommand/spdy.go:151`): resetting each stream needs the connection's frame writer, which the stuck stdin write holds. That explains the size threshold (64 KB never, 1 MB usually) and why a request-context cancel alone did not end it before bex-api's bound did. Gateway logs or a goroutine dump during a stall would confirm the exact blocking line. The existing tests cannot show it: `gatewaytest.FakeExecutor.Execute` (`lego/backend/internal/sshgateway/gatewaytest/fakes.go:171`) discards stdin.

## Fix

1. Refuse before streaming. In `upload`, run the destination checks (`cd_parent`, then the kind-specific tests the stage script makes today) as a stdin-less exec first, and map exit 66/73 through `executionError` as now. Only an accepted destination starts the staging exec with the body. This costs one short exec per upload.
2. Make the staging script safe against a destination that changes between the check and the stage. On its own late refusal it reads stdin to EOF (`cat >/dev/null`, bounded by the existing `MaxTransferBytes` reader and the five-minute deadline) before `exit 73`/`exit 66`. A late refusal is then slow but correct, never a stall.
3. Correct the `main.go:1424-1427` comment. Optionally, have bex-api answer a header timeout on a file transfer as `504` with a message that names the timeout, rather than "gateway unavailable".

## Blast radius

- Every upload refusal the stage script makes before reading stdin: an existing directory or symlink destination (directory kind), a destination that is a directory or symlink (file kind), a missing or unreadable parent, a relative path with no `$HOME`. That covers the CLI's `sandboxes copy`, the Render SDK's `copy_to`/upload, and the agent-attachment dispatch, which shares this gateway (`agentsessions/attachments_dispatch.go:52`, platform uploads to a fresh path, so normally unaffected).
- Downloads are unaffected: their script takes no stdin.
- Each stall holds one gateway exec stream and one bex-api request for two minutes. A goroutine still blocked after bex-api gives up would count against the gateway's channel limits, but that is not proven.

## Regression checks

- A fake executor that models a remote which exits without reading stdin and stops accepting it after 64 KB: a 3 MB directory onto an existing directory and a 3 MB file into a missing parent both answer 409/404 within a second, and no goroutine stays blocked.
- Live, with the pinned CLI on a running sandbox: 10 of 10 uploads of a 3 MB directory onto an existing directory answer `409` in under 5 s. 10 of 10 uploads of a 3 MB file into a missing parent answer `404 file_not_found` in under 5 s. A 3 MB directory to a free path still publishes byte-identically.
- An interrupted upload (client killed mid-body) still publishes nothing and leaves no staging directory, as w7/m150 t005 recorded.

## Dedupe

w7/m150 t005 verified "existing directory destination `409`" and "missing source or parent `404`" live on 2026-10-03, on dev-7 (runc, not gVisor), with payloads its record does not size. No open item covers a stalled refusal. w5/131 (done) covered the gateway's error text, not timing.

## Resolution

**DONE 2026-11-13.**

- **Refuse before streaming:** `upload` (`lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go`) now runs `checkScript`, a stdin-less exec of the destination checks, before it reads any of the body. A refused destination answers `409` or `404 file_not_found` at once, whatever the upload's size, and never reaches the staging exec.
- **A late refusal drains:** `stageScript` reads the rest of stdin before it exits on any refusal (EXIT traps), so a destination that changed after the check is refused slowly but correctly, never with a stall. The draining is bounded by the gateway's `MaxTransferBytes` reader and the five-minute deadline.
- **One destination rule:** the check, stage and publish scripts share one `destination_free` shell function.
- **Tests:**
  - `TestARefusedDestinationAnswersBeforeTheUploadStreams`: a stage exec that never ends models the stall; 3 MB uploads onto an existing directory and into a missing parent answer within the bound and never stage.
  - `TestARefusingStageDrainsTheUpload` runs the real script with `/bin/sh`: every refusal reads all 3 MB of stdin, including a `tar` that fails midway (as on a full sandbox disk). Without the drain it read 98,304 bytes, the same buffer threshold as the production stall.
  - `TestCheckRefusesTheStagesDestinations` pins the check's exit codes (existing directory or symlink 73, missing parent 66, a free path or a regular file to replace 0).
  - Each test fails with its half of the fix removed. The cleanup trap drains before it removes the stage, so a failed `rm` can't skip the drain.
- **Considered, not done:** the stage could print a ready byte after its checks and the gateway hold the body until it arrives, saving the extra exec on a successful upload. That depends on the container runtime's exit-while-stdin-open behavior and needs a live test first.
- **Not changed:** bex-api still answers a gateway header timeout as `503 sandbox file gateway unavailable` (the filing's optional 504); with the stall gone, only a real gateway fault reaches it. The `main.go` comment now says why two minutes never cuts a transfer short.
- **Production check after the next roll:** 10 of 10 uploads of a 3 MB directory onto an existing directory answer `409`, and 10 of 10 uploads of a 3 MB file into a missing parent answer `404 file_not_found`, each in under 5 s. A 3 MB directory to a free path still round-trips byte for byte.

**Production check passed 2026-11-13 (`/qa-find-bugs-cli` sweep `bc16`, 23:18 UTC, pin `3e30e291e`, released `bex v0.6.0`).** On a running sandbox in a QA-owned group:

- 10 of 10 `bex sandboxes copy` uploads of a 3 MB directory onto an existing `/tmp/exist` answered `409 … destination exists` in 0.9–1.9 s.
- 10 of 10 uploads of a 3 MB file into a missing parent answered `404 … destination parent does not exist` in 1.2–1.5 s.
- A 3 MB directory to a free path uploaded in 2.1 s and downloaded with identical sha256s.

The group was deleted afterwards.
