# A request still in flight when a new instance goes live is cut after ~40 s with 502: bex drains the old instance 10 s before `SIGTERM`, Render waits 60 s

Why: [Render's zero-downtime deploy docs](https://render.com/docs/deploys) say the old instance keeps serving after the switch: "After 60 seconds, Render sends a `SIGTERM` signal to your app's process on the _original_ instance", then waits the shutdown delay (default 30 s) before `SIGKILL`. A request that started on the old instance therefore has 60 s (plus whatever the app does with `SIGTERM`) to finish. Bex's old pod sleeps 10 s in `preStop` and then gets `SIGTERM`. An app that does not handle it, which includes any process running as PID 1 (PID 1 ignores `SIGTERM` by default), is killed at the end of the grace period, 10 + 30 s after the switch. Streaming LLM responses, long uploads and long-polling requests that Render carries across a deploy fail on bex. ADR018's graceful-shutdown row records "the drain is 10 s, not Render's 60 s" as a deliberate divergence without a user sign-off.

**Severity:** major (every deploy, config change and restart cuts long in-flight requests; streaming AI responses commonly run 30–120 s). **Attribution:** platform runtime (pod termination). **Estimate:** 1h. **Source:** `/qa-find-bugs-cli` sweep 1311, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1311--in-flight-drain)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`. Free image web service (`python:3.12-alpine`, `dockerCommand: python -c '<ThreadingHTTPServer on $PORT; GET /slow sleeps 70 s>'`, `maxShutdownDelaySeconds: 30` default, `srv-dbcp8cgu12fs73e9aj9g`, deleted 204 → 404):

1. Control: `GET /slow` with no deploy → **200 after 70.7 s**, so the edge does not time out a 70 s request.
2. `GET /slow` at 04:44:10Z. One second later, `PUT /v1/services/<id>/env-vars/QA_ROLL` (rolls a new pod; `env_vars_changed` and `deploy_started` at 04:44:11Z, `deploy_ended` at 04:44:34Z). The in-flight request answered **502 Bad Gateway after 62.2 s** (≈ 04:45:11Z), about 37 s after the new pod went live: the old pod's 10 s `preStop` plus the 30 s grace, then `SIGKILL`. A following `GET /` was served by the new pod (`…-78986fd4r2q8l`).

With a 40 s request (sweeps 1311a/b) the request survived only because it finished inside that window.

On Render's timeline the request ends at about +70 s, before the `SIGTERM` at switch + 60 s (≈ +83 s), so it completes.

## Expected

After the new instance is live and receiving traffic, the old instance keeps serving its in-flight requests (and accepts no new ones) for 60 s before `SIGTERM`. Then it gets the service's shutdown delay before `SIGKILL`. Total grace is 60 s + `maxShutdownDelaySeconds`.

## Root cause

The pod spec gives web and private pods `lifecycle.preStop.sleep: 10` and `terminationGracePeriodSeconds: 10 + maxShutdownDelaySeconds` (ADR018 graceful-shutdown row: "bex's web and private pods get a native `preStop.sleep` of 10 s, and their grace period is 10 s plus the delay (default 30)", w1/m154). In code: `lego/operator/internal/controller/deployment_projection.go:429–435` `const drainSeconds int64 = 10`, applied by `drainSecondsFor` (`:441–445`) and `applyDrain` (`:457–468`), which sets `PreStop.Sleep` and `TerminationGracePeriodSeconds = terminationGracePeriodSeconds(shutdownDelay, drain)`. The divergence is justified there as "without stretching every rollout and scale-in by a minute".

## Fix

Set `drainSeconds` to 60 for web and private services (`preStop.sleep: 60`, grace `60 + maxShutdownDelaySeconds`). Leave workers and disk-attached services (`Recreate`) unchanged; Render's docs exempt disk services from zero-downtime. A rollout's own completion does not wait for the old pod's termination, so only resource overlap and scale-in latency grow. Check:

- free-plan capacity, since an old pod lingers 50 s longer;
- autoscaling scale-in;
- the static-server and edge-cache sidecars' drains, which should follow the same 60 s.

Update ADR018's row and ADR004 to remove the divergence.

## Blast radius

Every web and private service rollout: deploys, env and secret changes that roll, restarts and scale-in. No API shape changes; `maxShutdownDelaySeconds` keeps meaning "after `SIGTERM`".

## Acceptance

- Envtest: a web App's pod has `preStop.sleep` 60 and grace 60 + delay; a worker is unchanged.
- Live after deploy: repeat step 2. The 70 s request completes with 200, served by the old pod, while new requests reach the new pod. Delete by ID with a 404 proof.
