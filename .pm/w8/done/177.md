# A native web service whose process listens on a port other than `PORT` never goes live (Render's own `fastapi-uv` example: uvicorn on 8000), because bex never detects the bound port; the image declared-port case is w4/388

Why: [Render's web-service docs](https://render.com/docs/web-services#port-binding) say: "If you bind your HTTP server to a different port, Render is _usually_ able to detect and use it". Render scans the running container for an HTTP listener on `0.0.0.0` instead of insisting on `PORT`. Bex routes and health-checks only the configured port (10000 by default since w8/168). A web service that binds anything else stalls on "a TCP connect to port 10000" and fails at the 15-minute start limit. This hits the most basic "deploy an existing image" case, a stock `nginx` image, and Render's own official `render-examples/fastapi-uv`. ADR018 row 104 lists "(2) no web-service detection" as deliberate, but ADR089:116 only scopes it "out of scope for this first phase", and no user sign-off is recorded. Under ADR008 § Render parity first it is an open gap.

**Scope (2026-10-22):** [w4/388](../w4/388.md), filed independently from the dashboard loop, owns the **image declared-port** half: a stock image such as nginx with `EXPOSE 80`. Its root cause is `resolveImageNetwork`/`UsesImagePorts` (private services only), and its target is to read public image configs anonymously. This item keeps the **runtime-detection** half, for native builds and other listeners that declare nothing: fix steps 2–3 below. The nginx reproduction stays as evidence for both.

**Severity:** major (a stock image or an official Render example never serves; the workaround of setting `PORT` to the bound port requires knowing the cause, and the stall reason never names the port the process actually bound). **Attribution:** platform runtime (operator port selection). **Estimate:** 4h. **Source:** `/qa-find-bugs-cli` sweep 1308, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1308--port-detection)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`, human device-login grant, HEAD-built pinned CLI. Both fixtures were deleted afterwards (204 → 404).

1. `bex services create --type web_service --image docker.io/library/nginx:1.27-alpine --plan free` (`srv-dbcohr7t87js73873av0`). It reads back `port: 10000` and `openPorts: [{port: 10000, protocol: TCP}]`. The image declares `EXPOSE 80`, and nginx listens on 80. After 52 s the deploy was `update_in_progress` with stall reason "the container is running but its startup health check has not succeeded, so the rollout is waiting: a TCP connect to port 10000. …".
2. `bex services create --type web_service --runtime python --plan free --repo https://github.com/render-examples/fastapi-uv --build-command ./install.sh --start-command ./run.sh` (Render's official example, as published; `run.sh` is `uv run -- uvicorn --host 0.0.0.0 main:app`, with no `--port`) (`srv-dbcoct7t87js73873ang`). The app log shows `Uvicorn running on http://0.0.0.0:8000`, and the deploy stalls with the same reason. `GET /` answers the first-deploy 503 ("This service's first deploy is in progress").

Reach in the Render corpora (~700 `render.yaml`, 959 web services): 5 hardcode a non-10000 port without `PORT` (`--port 8000` ×4, `--port 80` ×1, including Render's `descope-render` template). Implicit tool defaults (uvicorn 8000, `flask run` 5000, Streamlit 8501) and every Docker or image web service whose port comes from its Dockerfile are invisible to a `render.yaml` scan. The nginx case shows the image class is real.

## Expected

Render's behavior: a web service is reachable when its process binds `PORT`. Otherwise Render detects the port it does bind on `0.0.0.0` and routes there. Render's deploy log narrates the scan: `==> No open ports detected, continuing to scan...` repeats until a listener appears, and `==> Port scan timeout reached, no open ports detected.` fails the deploy (quoted in Render community threads, for example [35373](https://community.render.com/t/no-open-ports-detected-continuing-to-scan/35373) and [22983](https://community.render.com/t/port-scan-timeout-reached-no-open-ports-detected/22983)). The success line's exact wording is not captured. A process bound only to `127.0.0.1` is not detected, and the deploy fails with a message saying so. On bex:

- **Image and Docker web services with no configured port and no `PORT` variable** route to the image's single declared TCP port (`EXPOSE`). D3's verified image-metadata read already does this for private services (w6/m148). With several declared ports, use the existing primary-selection rule.
- **Any web service** whose health check on the configured port fails while the container listens on exactly one other TCP port on a wildcard address adopts that port for routing and the health check, records it as the serving port (`status.envPort`-style), reports it in `serviceDetails.port`/`openPorts`, and narrates the detected port in the deploy log (Render's wording to be captured). A listener on loopback only, or several candidate ports, keeps today's wait and gets a stall reason naming what was found ("listening only on 127.0.0.1:8000"; "listening on 8000 and 9000; set PORT to choose").
- An explicitly configured `PORT` or port keeps winning (w5/m149), so this never moves a service that binds what it was told to.

## Root cause

- `lego/types/v1alpha1/app_types.go` `DefaultPort = 10000` applies whenever `spec.port` is unset, and the operator's `envPort` (`operator/internal/controller/env_port.go:41–56`) only consults the service's own `PORT`.
- Web services never take the D3 image-port path. ADR018 row 104: "(2) no web-service detection: a web service reports its configured port", and ADR089:116 defers "undeclared-port discovery … and changing the public web-service ingress selection contract".
- Readiness is a TCP or HTTP probe on that one port (`deployment_projection.go`), so a process on another port can never pass it.

## Fix

1. **Declared-port step: tracked by [w4/388](../w4/388.md), not here.** For context: for a web service with no explicit port or `PORT`, run D3's digest-verified metadata read for the serving image and use its sole declared TCP port. This applies to prebuilt `image:` services too, which D3 currently skips; extend the read to them. Report it through the same `openPorts`/`port` projection private services use.
2. **Runtime detection step (covers native and undeclared listeners):** while a web rollout waits on its startup probe, list the pod's listening TCP sockets. A small sidecar in the pod's network namespace can read `/proc/net/tcp` and `/proc/net/tcp6` without exec into the tenant container; the `edge-cache` sidecar (w5/m151) is the precedent. If exactly one wildcard listener exists that is not the probed port, adopt it as above and re-roll on it. Render does this once per deploy; bex should too, with the result persisted for the release.
3. Update ADR018 row 104 and ADR089 § Port slice decisions so that web-service detection is a shipped parity behavior. Record what remains (UDP, loopback-only listeners) with sign-off, or ship it.

## Blast radius

Every web service with no explicit port or `PORT`: native, Docker and image sources, on REST, GraphQL, MCP, dashboard and Blueprints, because the selection happens in the operator. Services that already bind `PORT` or 10000 are unaffected; detection runs only when the configured port is not being listened on. Private services keep D3. Static sites are unaffected.

## Acceptance

- Unit/envtest: an App with no port whose image declares only `80` projects port 80 for Service, Ingress and probe. A pod reporting a single 8000 listener after a failed 10000 probe adopts 8000. A loopback-only listener and a two-listener pod keep waiting, with the named stall reasons.
- Live after deploy: both fixtures above go `live`. `GET /` returns the nginx welcome page and the FastAPI JSON. Their deploy logs name the detected port. Delete by ID with 404 proofs.
