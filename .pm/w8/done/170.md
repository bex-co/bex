# An unusable `PORT` value (`abc`, `0`, `70000`) is accepted and shown, but the process silently receives `PORT=3000`

Why: w5/m149 made `PORT` an ordinary variable, as on Render, and the operator "ignores unusable values". The write still succeeds and the Environment list shows `PORT=abc`, but the container gets `PORT=3000` and is health-checked on 3000, with no event or warning. The service quietly runs on a value the user never set, which is the stored-and-ignored state w2/m95 originally set out to remove. Render passes `PORT` through like any variable, so a bad value fails visibly there instead of being replaced.

**Severity:** minor. **Attribution:** server (env write validation) plus operator (silent substitution). **Estimate:** 30m. **Source:** `/qa-find-bugs-cli` sweep 1289, 2026-10-21 ([evidence](evidence/cli-sweep1289/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `4b6687b5bc18`, bex-canary. Four free `ealen/echo-server` web services were created via REST with `envVars: [{key: PORT, value: <v>}]`. 90 s later each was probed with `GET /?echo_env_body=PORT`, which prints the process's `PORT`:

| `PORT` written | Create | `serviceDetails.port` | Process sees | Deploy |
| --- | --- | --- | --- | --- |
| `abc` | 201 | 3000 | `"3000"` | live |
| `0` | 201 | 3000 | `"3000"` | live |
| `70000` | 201 | 3000 | `"3000"` | live |
| `80` (control) | 201 | 80 | `"80"` | live |

`GET /v1/services/{id}/env-vars` for the `abc` service lists `PORT = abc`. Its events are only `deploy_started` and `deploy_ended`, with no warning. All four fixtures were deleted (204 → 404).

## Expected

What a user sees and what the process gets should match. Preferred: refuse an unusable `PORT` at write time on every surface (REST service and env-group env vars, GraphQL, MCP, create, Blueprint, dashboard editor), with a coded 400: "PORT must be an integer from 1 to 65535". A group-provided `PORT` is validated the same way when the group is saved. Alternative: pass the literal through (Render's behavior) and let the deploy fail on its health check with the existing stall text.

## Root cause

w5/m149 (`65e0b19b5`): `env_port.go` resolves the effective `PORT` and drops values it cannot use, so the operator injects `DefaultPort`. The write paths removed the reserved-key refusal but added no value check in its place.

## Fix

Add `core.CheckPortValue(key, value)` and apply it wherever `core.ValidEnvKey` runs for `PORT`: service env, env groups, create, the Blueprint compiler and the dashboard editors (inline message). Keep the operator's ignore rule only as a backstop for values stored before the check, and emit a service event when it ignores one.

## Acceptance

- Tests: `PORT=abc|0|70000|-1|""` → 400 with the coded message on every surface; `PORT=80|8080|65535` accepted.
- Live after deploy: the `abc` row above returns 400, and nothing is created. Clean up any fixture by ID with a 404 proof.

## Dedupe

w5/m149 (PORT settable; its closeout says unusable values are ignored), w8/169 (the create response's port), w8/168 (the default port). No item covers validating the value.

**Done 2026-10-21:** `core.CheckEnvValue` now rejects a non-integer/out-of-range/reserved `PORT` (`ENVIRONMENT_VARIABLE_PORT_INVALID`) for every funnel (service/group env writes, create, environment patch) and Blueprint literals (`deploy.go`); tests in core and apps. Not done: dashboard inline message (the API error shows as the save error) and the operator event when it ignores a legacy stored value (log only). Live acceptance after deploy.
