# 027 — `services create` accepts invalid env var names (`1BAD`, `BAD KEY`, `BAD-DASH`), and they become permanent: reported as Blueprint-managed, and no update or delete can remove them

Why: every later env write refuses these names (`invalid environment variable name`), but create stores them. They then show up as `managedBy: blueprint` on a service that has no Blueprint. `DELETE` tells the user to edit a `render.yaml` that doesn't exist, and a bulk replace answers `200 []` while the var stays. The only way out is deleting the service.

Live, 2026-09-26, production `726042a28`, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 35. Fixtures: free busybox crons (all deleted).

```text
$ bex services create --type cron_job … --env-var "1BAD=x"          → exit 0 (same for "BAD KEY=x", "BAD-DASH=x")
$ bex services create --type cron_job … --env-var PORT=9            → 400 ENVIRONMENT_VARIABLE_RESERVED   (control: create does check names, but only for the reserved one)

GET    /v1/services/<srv>/env-vars          → 200 [{"envVar":{"key":"1BAD","value":"x","revision":"evr1_AAAAAAAAAAA","managedBy":"blueprint"}}]
PUT    /v1/services/<srv>/env-vars/1BAD     → 400 invalid environment variable name "1BAD"
DELETE /v1/services/<srv>/env-vars/1BAD     → 409 ENV_VAR_MANIFEST_MANAGED "1BAD is declared in this service's render.yaml manifest … edit the manifest and sync the blueprint"
PUT    /v1/services/<srv>/env-vars  []      → 200 []   … then GET still lists "BAD KEY"

# the process does receive them (cron running `env | od -c`)
QA_OK=z \n 1BAD=x \n BAD KEY=y \n
```

Controls (correct): values with `=`, spaces, UTF-8, quotes, empty and `$HOME` all reach the process literally. `KUBERNETES_SERVICE_HOST`, `PATH` and `RENDER` are stored in the normal store (no `managedBy`) and are editable.

## Mechanism

- `lego/backend/internal/apps/rest.go:535` → `render.go:39-45` `toEnvVars` copies names unchecked. `Service.Create` runs only `checkReservedSpecEnv` (`apps/service.go:1978-1988`, which checks PORT), never `core.ValidEnvKey`/`core.CheckEnvKey` (`core/config.go:62,127`).
- `takeCreateEnvLiterals` (`apps/service.go:2006-2027`) moves valid literals into the mutable store but deliberately **leaves invalid names on `spec.Env`** "rather than newly failing a create that works today".
- `w4/m120` then treats every literal left on `spec.Env` as manifest-owned (`secrets/service.go` `mergeManifestEnv`/`managedBy`, `refuseManifestKeys` → `ENV_VAR_MANIFEST_MANAGED`). The store verbs validate the key first (`CheckEnvKey`, `secrets/service.go:456,506,588`), so PUT is refused, DELETE hits the manifest guard, and the bulk replace rewrites only the store.
- The Blueprint path has the same gap: `blueprints validate` on `envVars: [{key: 1BAD}, {key: "BAD KEY"}]` → `"valid": true` (`apps/deploy.go:2334` checks only `IsReservedEnvKey`).

## Fix

1. Create: run `core.CheckEnvKey` on every literal `spec.Env` name, next to `checkReservedSpecEnv`, and refuse with the existing `invalid environment variable name "…"` 400. Do the same in the Blueprint service and env-group parsers (`deploy.go:2096,2334`), located like the other validate errors (w8/019).
2. Drop the invalid-name carve-out from `takeCreateEnvLiterals`. With (1) it becomes unreachable for new creates.
3. Existing rows: a pre-existing invalid-name `spec.Env` entry on an App **without** a Blueprint owner must be deletable. Either `managedBy` requires an actual Blueprint owner, or DELETE on such a key strips it from `spec.Env`. The bulk replace must never report `200 []` while a key remains.

## Acceptance

- [ ] `bex services create … --env-var "1BAD=x"` (and `BAD KEY`, `BAD-DASH`) → exit 1 with `invalid environment variable name`, nothing created. GraphQL/MCP create refuse the same way.
- [ ] `blueprints validate` flags each invalid key with its location. Valid keys and the value-edge controls above are unchanged.
- [ ] On a service created before the fix with an invalid key and no Blueprint: DELETE removes it (or it is reported without `managedBy: blueprint`), and a bulk `PUT []` leaves the list empty.

## Outcome (2026-09-27) — done

1. **Create** (`apps.checkReservedSpecEnv`, run on every create surface: REST, GraphQL, MCP) refuses a `spec.Env` name outside `core.ValidEnvKey` with the env verbs' own `400 invalid environment variable name "…"`, before anything is written. `takeCreateEnvLiterals` lost its invalid-name carve-out.
2. **Blueprints**: the service and env-group parsers refuse invalid keys (`<svc> envVars["1BAD"]: invalid environment variable name …`), located by `blueprints validate`. Env-group parse errors are now located resource errors like service/database ones.
3. **Existing debris**: an invalid-name `spec.Env` literal is listed without `managedBy` (no Blueprint can declare it any more). `DELETE …/env-vars/<key>` strips it from `spec.Env` (404 once gone), and a whole-set `PUT` clears such debris, so `PUT []` never answers `[]` while one is still listed.
4. **Production audit** (read-only `kubectl --context hetzner-prod`): 12 Apps, **0** invalid-name env entries, so nothing to clean up live.

Tests: `apps.TestCreateRefusesInvalidEnvVarNames` (`1BAD`, `BAD KEY`, `BAD-DASH`; nothing created or seeded), `TestCreationTimeEnvVarsLeaveReferencesOnTheSpec` (the old carve-out test, rewritten), `TestValidateBlueprintRefusesInvalidEnvVarNames`, and `secrets.TestInvalidNameDebrisIsListedAndRemovable` (mutation: removing the PUT cleanup fails it). Backend suite + lint are green; the only failures are the stateful git-webhook replay tests on a reused local DB, which is unrelated.
