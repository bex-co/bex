# `NODE_VERSION=lts` (and `.nvmrc` `lts/*`) builds on Node 24 although Node 26 has been LTS since 2026-10-28, and `lts/lithium` fails the build

Why: `lts` means the newest LTS release. Render accepts it as an alias, and the Node.js release index has listed 26.x as LTS ("Lithium") since 26.13.0 on 2026-10-28. bex hardcodes the LTS line as 24 and knows no `lithium` codename, so a service asking for "the current LTS" builds on the previous one, and one asking for `lts/lithium` cannot build at all.

**Severity:** major for `lts/lithium`, whose build fails at version selection, so the service never deploys. Minor for `lts` and `lts/*`, which build, but on the previous LTS line. **Attribution:** build (operator native version resolution). **Source:** `/qa-find-bugs-cli` sweep `4006`, 2026-11-16, production pin `e3a57b1c398f`, bex CLI v0.7.0, workspace bex-canary.

## Render

- [render.com/docs/node-version](https://render.com/docs/node-version) (read 2026-11-16): a version can be a semver number "or aliases (e.g. `lts`)". The order of precedence is `NODE_VERSION`, `.node-version`, `.nvmrc`, then `package.json` `engines`. The default for services created on or after 2026-10-21 is 24.22.1.
- **Node.js release index** (`https://nodejs.org/dist/index.json`, read 2026-11-16):
  - The first 26.x release marked LTS is `v26.13.0` (`lts: "Lithium"`, 2026-10-28).
  - The newest LTS is `v26.13.1` (Lithium, 2026-11-10).
  - The newest 24.x is `v24.22.3` (2026-11-10).
- **Unverified:** which release a Render build actually installs for `lts`, since this host has no Render account. The target follows the alias's meaning in nvm, n and fnm, and the release index.

## bex (production, 2026-11-16 13:50–13:59 UTC)

Four free web services were created with the released CLI from the same repo and commit (`render-examples/express-hello-world@039c347`, which has no version file and no `engines`):

```sh
bex services create --name <name> --type web_service \
  --repo https://github.com/render-examples/express-hello-world --branch main \
  --runtime node --build-command yarn --start-command 'node app.js' --plan free \
  [--env-var NODE_VERSION=<value>] --confirm -o json
bex logs -r <srv-id> --type build --limit 100 -o text
```

| `NODE_VERSION` | Build log | Result | Target |
| --- | --- | --- | --- |
| (unset) | `==> Using Node 24.22.1 (default)` | live, `GET /` 200 | 24.22.1 ✓ |
| `lts` | `==> Using Node 24.22.3 (from NODE_VERSION=lts)` | live | **26.13.1** |
| `lts/lithium` | `==> NODE_VERSION=lts/lithium is not a supported Node version; supported Node lines are 14, 16, 18, 20, 22, 24, 26`, then `==> Build failed: build failed in the runtime version selection step:` | `build_failed`, `GET /` 503 | **26.13.1** |
| `26` | `==> Using Node 26.13.1 (from NODE_VERSION=26)` | live, `GET /` 200 | 26.13.1 ✓ |

The 26 line is installed and builds (the last row), and the refusal itself lists 26 as supported. Only the alias mapping is stale.

## Cause (code read at `ae4e53083`)

- `lego/operator/internal/build/nativeversion.go`:
  - `:592`, `nodeLTSCodenames`, maps `fermium`…`krypton` to 14…24, with no `lithium`.
  - `:594-595` reads `// nodeLTSLine is the current active LTS line (24 until 26 enters LTS).` and `const nodeLTSLine = "24"`.
  - `nodeRequest` (`:602-618`) returns `nodeLTSLine` for `lts` and `lts/*`, and the map's line for `lts/<codename>`; an unknown codename returns `ok=false`.
- Every Node source goes through `nodeRequest`: `NODE_VERSION`, `.node-version`, `.nvmrc` (`:274`) and `package.json` `engines.node` (`fromPackageEngines`, `:669-678`). So the same staleness hits an `.nvmrc` holding `lts/*`, a common file, and an `engines.node` of `lts/*`.
- `nativeversion_test.go:80` pins `.nvmrc` `lts/*` to `"24"`, so the test enforces the stale answer.
- `docs/ADR060-build-worker-reliability-and-performance.md:335` documents `jod`=22 and `krypton`=24 as the full alias set.

## Fix

- Add `"lithium": "26"` to `nodeLTSCodenames`.
- Make `lts` and `lts/*` follow Node's schedule instead of a constant that someone has to remember to edit, for example a dated table like the default-version tables in the same file (`renderNodeDefault20261021`): `{2026-10-28 → "26"}` after `{… → "24"}`, evaluated at build time. The alias names the current LTS when the build runs, and that rule is unverified against Render's builder.
- Update `nativeversion_test.go:80` (and add cases for `lts`, `lts/lithium` and an `engines.node` of `lts/*`) and the ADR060 §335 line.
- No REST, GraphQL, MCP or dashboard surface changes. The resolved version shows up only in the build log and the runtime.

## Outcome (2026-11-16)

**Done.** `nodeLTSCodenames` and the `nodeLTSLine` constant are replaced by one dated table, `nodeLTS` (`lego/operator/internal/build/nativeversion.go`): every reviewed Node line with its codename and first-LTS date from `nodejs.org/dist/index.json` (14.15.0 Fermium 2020-10-27 … 26.13.0 Lithium 2026-10-28). `lts` and `lts/*` name the newest line whose LTS has begun when the build runs, so they give 26 now and will move on a future line's date with no edit. `lts/<codename>` looks the codename up in the same table, so `lithium` gives 26.

- **Schedule guard:** `TestNodeLTSCoversTheReviewedLines` fails a reviewed Node line without an entry, an entry naming no reviewed line, or dates out of order. Node's `schedule.json` already plans v27's LTS for 2027-10-20 with no codename yet, so an entry may leave the codename empty until Node names it.
- **Tests:** `TestResolveNativeVersion` now covers `NODE_VERSION=lts`, `.nvmrc` `lts/*` and `engines.node` `lts/*` → 26, `lts/lithium` → 26 and `lts/Krypton` → 24. `TestResolveNativeVersionRefusesUnsupportedByName` covers `lts/notacodename`, and `TestNodeLTSLineFollowsTheSchedule` covers the 2026-10-28 boundary. Against the old resolver the four 26 cases fail. `make test` passes.
- **Docs:** ADR060's Node-aliases bullet now describes the dated rule.
