# A Key Value instance can be moved to a smaller plan, including paid back to Free, which Render does not allow

Why: Render's Key Value docs say "It is not currently possible to downgrade a Key Value instance." bex accepts any plan change, so `bex kv update --plan free` on a paid store restarts it onto the smaller size with no check on what it holds. The behavior differs from Render with no recorded sign-off, and a downgrade below the data's size is a silent data-loss path.

**Severity:** minor (parity; possible data loss on a real store). **Attribution:** server. **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `45ef`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary` (Scale), QA human device login.

## Evidence

Run-owned free Key Value `red-dbpvqfik10fs73dvo5gg` (deleted with the sweep). The upgrade was not intended: `--plan 10g` was sent expecting a refusal, was accepted, and was reverted 17 seconds later.

```text
05:37:55  $ bex kv update red-dbpvqfik10fs73dvo5gg --plan 10g -o json --confirm
          { "data": { "plan": "pro_plus", "status": "config_restart", … } }                  exit 0
05:38:12  $ bex kv update red-dbpvqfik10fs73dvo5gg --plan free -o json --confirm
          { "data": { "plan": "free", "status": "config_restart", … } }                      exit 0
05:39:2x  $ bex kv get red-dbpvqfik10fs73dvo5gg -o json     → "plan": "free", "status": "available"
```

## Expected

Render (render.com/docs/key-value § Changing compute plans, read 2026-11-11): "You can upgrade your Key Value instance to a larger compute plan." and "It is not currently possible to downgrade a Key Value instance." The page documents `render kv update --plan` and the Update Key Value API for upgrades. What status and body Render's API answers for a downgrade is not documented.

## Root cause

`lego/backend/internal/keyvalue/service.go` validates a plan change only for existence, the paused-plan rule, billing and the one-free-instance limit (`:1082-1083`, `:1191-1210`; `SetPlan` at `:959-1004` for GraphQL/MCP). Nothing compares the target with the current plan. ADR021 (line 135) describes a downgrade as changing compute while keeping the disk, and records no comparison with Render.

## Fix

Parity-sufficient choice: refuse a plan change to a smaller compute plan (lower memory than the current plan in `tiers.Valkey`), including paid to `free`, with a named 400, for example `KEY_VALUE_PLAN_DOWNGRADE_UNSUPPORTED: a Key Value instance cannot move to a smaller plan; create a new instance and migrate`. Apply it in the shared patch path so REST `PATCH /v1/key-value/{id}`, GraphQL `updateKeyValuePlan`, MCP `update_key_value` and a Blueprint sync that lowers `plan` agree, and disable smaller plans in the dashboard's plan picker. Re-sending the current plan stays a no-op. Update ADR021 and the ADR018 Key Value row. Keeping the downgrade instead needs the user's sign-off recorded in ADR018, plus a guard for data larger than the target plan.

## Acceptance

- `bex kv update <paid store> --plan free` and `--plan <smaller paid plan>` exit non-zero with the named code; the store's plan and status are unchanged and it is not restarted.
- An upgrade and a same-plan update still succeed.
- GraphQL, MCP and Blueprint sync refuse the same change; a unit test covers each direction.

## Unverified

- What happens to data when a store is downgraded below its used memory (the fixture was empty, and creating paid fixtures on purpose is out of scope for the hunt).
- Render's exact refusal for a downgrade request.
- Whether Render refuses a lower `plan` in a Blueprint sync or ignores it.

## Dedupe

No `.pm` item mentions a Key Value downgrade. The services `planDowngradeError` (autoscaling) and Postgres storage expand-only rules are separate.

## Outcome (2026-11-11)

**DONE.** Fix `7492fe4ae` (+ test `b69011a9c`): `keyvalue.ErrPlanDowngrade` refuses a change to a plan with less memory, on REST, GraphQL, MCP, their dry runs, and a Blueprint's plan and sync; the dashboard's plan picker disables smaller plans; ADR021 and ADR018 record it. Replayed on production after deploy run 43038763852 pinned `f609163ada8e` (14:43 UTC), released `bex v0.5.0`, workspace `bex-canary`, run-owned store `red-dbqbhh03u30c73cf94ag` (deleted):

```text
bex kv update <id> --plan starter   (from free)       → exit 0, config_restart, then available on starter
bex kv update <id> --plan free                         → exit 1: 400 (KEY_VALUE_PLAN_DOWNGRADE_UNSUPPORTED): a Key Value instance cannot move
                                                         to a smaller plan (Starter to Free); create a new instance on the smaller plan and move the data to it
                                                         plan starter, status available: unchanged, not restarted
bex kv update <id> --plan starter   (same plan)        → exit 0, status stays available
bex kv update <id> --plan standard, then --plan starter → the upgrade is accepted; the smaller paid plan is refused with the same code (Standard to Starter)
GraphQL updateKeyValuePlan(plan: "free")               → errors[0].extensions.code = KEY_VALUE_PLAN_DOWNGRADE_UNSUPPORTED
bex blueprints validate (keyvalue qa-w8n249, plan: starter while the store is standard) → valid: false, the same sentence; plan: pro → valid
```

MCP and a Blueprint sync were not replayed live; they call the same check (`plan_downgrade_test.go`, `blueprint_kv_plan_downgrade_test.go`). What Render answers for a downgrade request is still undocumented.
