# A `sync: false` variable inside an env group makes bex refuse the whole Blueprint; Render ignores that one variable, so three Render templates fail on bex, including a one-click gallery template

Why: Render's Blueprint spec says, under "Prompting for secret values": "You can't apply `sync: false` to environment variables defined in an environment group. If you do this, Render ignores the environment variable." The Blueprint still applies; only that key is skipped. bex refuses the file instead. `blueprints validate` answers `valid: false` with exit 1, and `ea blueprints create` / plan fails with `env group "<name>" envVars["<KEY>"]: sync:false is not allowed inside an env group`.

ADR049 files this as "a refusal Render makes too", and `TestRenderExamplesCorpus` excuses it as `// Render forbids it too (blueprint-spec)`. The spec forbids writing it, but it does not say Render refuses the file. It says Render ignores the variable.

Three Render templates use the form:

- `render-examples/ravendr`: its `render.yaml` came from the commit "gallery-ready Blueprint for one-click template deploy" (2026-07-11), and its README has a Deploy to Render link.
- `render-examples/forem`: Deploy to Render button.
- `render-examples/git-scm.com`

**Severity:** minor. Removing the line works around it, and the error names the key. But it blocks importing those templates unchanged, and the refusal is filed as parity although Render's documented behavior differs. **Attribution:** server (bex-api Blueprint compiler). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `f75b`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `ca7fbbe606c8`.

## Evidence

**Corpus run.** `bex blueprints validate <file> -o json` was run over the 174 root `render.yaml` files in `render-examples`, fetched 2026-11-12. Three files fail on this rule and nothing else:

```text
forem        envVarGroups[0].envVars[15] (line 154): env group "rails" envVars["SENDGRID_API_KEY"]: sync:false is not allowed inside an env group
git-scm.com  envVarGroups[0].envVars[1]  (line 55):  env group "git-scm-shared" envVars["GITHUB_API_TOKEN"]: …
ravendr      envVarGroups[0].envVars[0]  (line 21):  env group "ravendr-shared" envVars["YOU_API_KEY"]: …
```

**Minimal file.** One env group with `API_KEY` and `MODE: prod`, linked by `fromGroup` from a free Node web service. Only `API_KEY`'s entry was varied:

| `API_KEY` entry | `valid` | exit |
| --------------- | ------- | ---- |
| `sync: false`   | false   | 1    |
| `sync: true`    | true    | 0    |
| `value: x`      | true    | 0    |

**Customer journey.** `bex ea blueprints create --repo https://github.com/render-examples/ravendr --name qa-20261112-f75b-envgrp --auto-sync=false -o json` exited 1 in 1.7 s:

- `planningOutcome: "failed"` and sync `state: "error"`;
- one notice, with `severity: "error"`, at `envVarGroups[0].envVars[0]`, line 21;
- `meta.next` said "fix the errors above".

No resource was created. Blueprint `exs-dbqugi4dhgcs73ao03pg` was deleted (204, then 404).

**Render's documentation** (`render.com/docs/blueprint-spec`, fetched 2026-11-12):

- "Environment groups": "You can't define an environment variable with `sync: false` in an environment group."
- "Prompting for secret values": "You can't apply `sync: false` to environment variables defined in an environment group." and "If you do this, Render ignores the environment variable."

Render's published schema (`render.com/schema/render.yaml.json`) types an env group's `envVars` items as `envVarFromKeyValue`, which includes `sync`. The schema accepts the form.

## Root cause

- `lego/backend/internal/apps/deploy.go:2708-2753` (`parseEnvGroup`): the `case e.Sync != nil && !*e.Sync` arm (`:2734-2735`) returns a refusal. Its doc comment says the entry "is rejected with a clear per-entry error rather than silently dropped".
- `deploy.go:2310-2314`: that refusal becomes a resource problem, so validate, preview, create, plan and every sync fail the whole file.
- `docs/ADR049-render-yaml-parity.md:412` classifies it as "a refusal Render makes too".
- `lego/backend/internal/apps/blueprint_render_examples_corpus_test.go:37` excuses it in `deliberateBlueprintDivergences`.

## Fix

Do what Render documents: accept the file and skip that variable.

- **`parseEnvGroup`:** a `sync: false` entry is not added to `literals` or `generates`, whether or not it carries a `value`. Return it in a new `ignored []string` (key plus entry index) instead of an error.
- **Validate:** `valid: true` when nothing else is wrong. Render's `ValidateBlueprintResponse` has no warnings field, so validate says nothing more.
- **Plan (`ea blueprints create` / `plan`, sync, preview):** add one `BlueprintNotice` per ignored key with `severity: "warning"`, located at the entry's path and line. Use a bex-owned sentence such as `env group "ravendr-shared" envVars["YOU_API_KEY"]: sync: false is ignored in an environment group; add this value to the group after the Blueprint is applied`. `BlueprintNotice` already models Render's "planning error or warning" (`blueprint_onboarding.go:83-90`).
  - The variable is not added to `requiredManualEnvVars`; Render prompts only for service-level `sync: false` keys.
- **Group contents:** the group is created, or synced, without the key. A later sync must not delete a value the user added to the group by hand for that key. Treat the ignored key the way an omitted key is treated today.
- **Docs and corpus guard:**
  - ADR049: move the item from "a refusal Render makes too" to the accepted inputs, citing the quote above.
  - Remove its entry from `deliberateBlueprintDivergences`, so the corpus guard proves forem, git-scm.com and ravendr validate.
  - Record the change in ADR018's Blueprint row.

## Blast radius

- **Surfaces:** every Blueprint entry point that parses env groups:
  - REST multipart validate, preview, `POST /v1/blueprints`, syncs and `blueprints/deploy`;
  - GraphQL;
  - MCP `validate_bex_yml`;
  - auto-sync on push.
- **Unchanged:** service-level `sync: false` (seeded once, prompted via `requiredManualEnvVars`), and the group refusals of `fromService`, `fromDatabase` and `fromGroup`. For a group, Render documents those as "can't reference values from your services, or from other environment groups", not as ignored.

## Regression checks

- **Go test, parsing:** a group with `{key: A, sync: false}`, `{key: B, sync: false, value: v}` and `{key: C, value: c}` parses with literals `{C: c}`, no error, and both A and B reported as ignored at their indexes.
- **Go test, validate and plan:** the f75b minimal file validates. Its plan creates the group with `MODE` only and carries one `warning` notice located at line 4.
- **Corpus:** `TestRenderExamplesCorpus` with this sweep's corpus. forem, git-scm.com and ravendr no longer fail on this rule.
- **Production:**
  - `bex blueprints validate` on the ravendr file exits 0.
  - `bex ea blueprints create --repo https://github.com/render-examples/ravendr --auto-sync=false -o json` plans with a warning notice and no error. Delete the Blueprint without approving it; the template's services are not free.

## Shipped 2026-11-12 (`/loopx w8`); the production check waits for the deploy that carries it

- **Fix:** `parseEnvGroup` (`lego/backend/internal/apps/deploy.go`) skips a group's `sync: false` entry, with or without a value, and records it as a notice located at the entry. A `generateValue` entry keeps its generation, as a service's parse orders the two. The group is created or synced without the key, and since `ApplyEnvGroup` keeps keys a Blueprint omits, a value the user adds to the group by hand survives later syncs. The key is not prompted for.
- **Validate:** `valid: true` when nothing else is wrong; validate says nothing more, since Render's response has no warnings.
- **Plan:** `ea blueprints create` / `plan` and sync planning carry one `warning` notice per ignored key, located at the entry's path and line. The sentence is `env group "<name>" envVars["<KEY>"]: sync: false is ignored in an environment group; add this value to the group after the Blueprint is applied`.
- **Tests:**
  - `TestParseEnvGroupIgnoresSyncFalse`: `sync: false` with and without a value is ignored at its index, `generateValue` wins, and a literal is kept.
  - `TestBlueprintPlanWarnsAboutAnIgnoredGroupSecret`: the plan succeeds with one warning at `envVarGroups[0].envVars[0]` (line 5) and no prompted key.
  - The w8/100 location test now expects a valid manifest with that warning.
  - The corpus guard no longer excuses the refusal.
- **Review** (`/simplify`, three reviewers):
  - Warnings are located through `blueprintResourceValidationErrors`, as the refusal was. A shared `blueprintNotice` builds the notices. The lookup is skipped for groups with nothing ignored.
  - Not changed: a failed plan reports only its errors, not these warnings.
  - Not changed: `currentStateCopyProblems` still copies a group's literal past a later group's hand-added value, as it does for any key added in the dashboard.
- **Docs:** ADR049 § Corpus guard (the item moved out of "a refusal Render makes too"), ADR018's Blueprint row.
