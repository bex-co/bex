# Render's free-plan "migrate in the build command" recipe cannot work on bex: the build gets no `fromDatabase` variable and cannot reach the database

Why: on a free instance Render has no pre-deploy step, so its own guides tell users to run migrations at the end of the build command against the internal `DATABASE_URL`. Render's official Django example (`render-examples/django`) does exactly that. On bex the build sees no `DATABASE_URL` at all, because `fromDatabase` values are dropped from the build environment. And the build pod's network policy could not reach the database anyway. Every Render app that follows this recipe fails its first build on bex. The bex-native fix, a pre-deploy command (which bex allows on free plans), works but is never suggested.

**Severity:** major (Render's documented free-plan setup for Django and Rails fails on import). **Attribution:** platform runtime (operator build env + build network boundary). **Decision note:** the build boundary is a deliberate security posture (ADR022:239, `bex-build` default-deny). See Fix for the options. **Estimate:** 60–150m depending on the option. **Source:** `/qa-find-bugs-cli` sweep 1274, 2026-10-21 ([evidence](evidence/cli-sweep1274/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `9cace6b6e25d`, workspace `tian-personal`, human device-login grant.

1. Connect `https://github.com/render-examples/django` as a Blueprint. It defines a free Postgres `mysitedb` and a free Python web service `mysite` with `buildCommand: ./build.sh` (`pip install …; collectstatic; python manage.py migrate`) and `DATABASE_URL` from `fromDatabase: {name: mysitedb, property: connectionString}`.
2. Two unrelated blockers had to be cleared first: the repo's `psycopg2-binary==2.9.9` cannot load on Python 3.13 (on Render's current 3.14 default too), so `PYTHON_VERSION=3.12.11` was set; and the `RENDER` variable is missing ([w8/159](done/159.md)). With both set, the build reached `migrate` and failed: `django.db.utils.OperationalError: connection to server at "localhost" (::1), port 5432 failed: Connection refused`. The app's `dj_database_url.config(default=…localhost…)` fell back because `DATABASE_URL` was absent from the build environment.
3. Bex-native workaround: PATCH `buildCommand` to `pip install -r requirements.txt && python manage.py collectstatic --no-input` and `preDeployCommand` to `python manage.py migrate`. The next deploy went `live` in 5 m 32 s. `GET /` 200, `/admin/login/` 200 with its static assets, unknown path 404.

All resources were deleted (Blueprint, service, Postgres: 204 → 404).

## Expected

Render: [Deploy a Rails 6 or 7 App](https://render.com/docs/deploy-rails-6-7) says "If you're running on the Free instance type, you can include a database migration step in your build command", where `DATABASE_URL` is the internal database URL. [Deploy a Django App](https://docs.render.com/deploy-django) and the official `render-examples/django` repo run `python manage.py migrate` in `build.sh`. [Docker builds](https://render.com/docs/docker) say "Render automatically translates those values [environment variables] to Docker build arguments". Render's build therefore has the service's variables, `fromDatabase` connection strings included, and can reach its own workspace's database over the private network.

## Root cause

1. **Build env:** `lego/operator/internal/build/native.go:210–220` `BuildLiterals` skips every `EnvVar` with `ValueFrom` set, and `fromDatabase`/`fromService` references are exactly those (`SecretKeyRef` to the datastore's connection Secret; `app_controller.go` `appEnv`). The native bundle (`native.go:417`), the Dockerfile literals (`build.go:1040`) and `projectNativeBuildEnv` (`app_controller.go:1636`) all go through it.
2. **Build network:** builds run in `bex-build` under `default-deny` plus `allow-required-egress` (`deploy/gitops/base/build-boundary.yaml:91–142`). The only egress allowed is DNS, the in-cluster registry, and public `0.0.0.0/0` **minus every private range** on TCP 22/80/443. Tenant Services and datastores (private ranges, port 5432/6379) are unreachable by design.

## Fix (decision first)

1. **Make Render's recipe work.** Project `fromDatabase`/`fromService` values into the build bundle, the same secret-mount path the env bundle already uses, never as literals in the Job spec. Add a scoped egress rule from a build pod to its own workspace's datastore endpoints only (match on the build pod's workspace label against the datastore's namespace/labels and port). Pre-deploy already runs co-located in the App namespace (ADR043 D8), so the security delta is limited to "tenant build code can reach tenant-owned datastores". It needs a written threat review (ADR022 addendum).
2. **Keep the boundary, make the failure actionable.** Leave builds isolated. When a build command fails with a database-connection error, or when a Blueprint's `buildCommand` contains a known migration verb (`migrate`, `db:migrate`, `alembic upgrade`, `prisma migrate deploy`) and the service has `fromDatabase` variables, add a plan-time warning and a build-failure hint: "builds cannot reach your database on bex; move migrations to the pre-deploy command (available on every plan)". Record the divergence in ADR018 (Pre-Deploy row) and ADR060.

Option 2 is cheaper and keeps the security boundary. Option 1 is the parity answer. Either way, the free-plan pre-deploy availability is the bex advantage to advertise.

## Acceptance

- Option 1: an operator test shows `DATABASE_URL` from `fromDatabase` present in the native and Dockerfile build env through a secret mount (never in the Job spec). A live `render-examples/django` deploy (with `PYTHON_VERSION` and w8/159 resolved) migrates in the build and goes `live`. A build cannot reach another workspace's database (negative control).
- Option 2: Blueprint validate/plan on `render-examples/django` shows the warning at the service's `buildCommand` line, and the build failure carries the hint. ADR018 records the divergence.
- Fixtures are deleted by ID with 404 proofs.

## Blast radius

Native and Dockerfile builds (kpack cannot take secret refs: w1/121), Blueprint plan text, the build-failure classifier, and `build-boundary.yaml`. Runtime and pre-deploy are unchanged.

## Dedupe

w1/121 (service env never reached kpack builds; literals only, secret refs impossible in kpack) and w1/m152 (a migration reads the previous release's config) touch build env but not `fromDatabase` values or build→database reachability. ADR022:239 records the build boundary's existence, not the Render migration recipe it breaks. No open item.
