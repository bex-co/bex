# A semver range in `NODE_VERSION` (`~16.13.0`) builds on the line's pinned 16.20.2, outside the range, where Render installs the newest release the range allows

Why: Render resolves `NODE_VERSION`, `.node-version`, `.nvmrc` and `engines.node` through `node-version-alias`, ranges included (render.com/docs/node-version, quoted in w8/173). So `~16.13.0` (>=16.13.0 <16.14.0) gets a 16.13.x release. bex maps the range to its Node 16 line and builds on that line's reviewed patch, 16.20.2, a release the range excludes. Its build log names only the line:

```text
==> Using Node 16 (from NODE_VERSION=~16.13.0)
```

w8/175 made a fully qualified version (`18.18.0`) build on that exact release. A range was left on the line's patch, even when the range excludes it. The same applies to Python, Ruby and Elixir ranges in version files (`~> 3.2` in a Gemfile, for example).

**Severity:** minor. The app usually runs fine on a newer patch, but the owner pinned a range for a reason, and nothing reports the substitution. **Attribution:** platform build (native version selection). **Estimate:** ~2–3h. **Source:** `/qa-find-bugs-cli` w8 loop sweep `2388`, 2026-11-13 UTC, released `bex v0.5.0`, `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `5de3d5bcce8e`.

## Root cause

- **The range picks only a line.** `lego/operator/internal/build/nativeversion.go:478-495` (`highestSatisfying`) resolves the range to a line, and its comment records the choice: "A range the pinned patch misses but another release of the line meets (`~16.13.0` against 16.20.2) still selects that line: the pinned patch stands in for the requested one, as it does for a plain version (w8/173)".
- **Only a plain version gets an exact release.** `exactRequest` (`:704-731`) takes only a fully qualified version: "a range, an alias or a lockfile keeps resolving to the line's reviewed patch".
- **The narration names only the line**, so the substitution is not visible.

## Fix

- **Resolve a range to a release.** When the range excludes the line's pinned patch, resolve it to the newest official release within the line that satisfies it, and build on that exact image through w8/175's path (`Exact`, digest-pinned at resolve time).
  - **Where the version list comes from:** a published index such as Node's `dist/index.json` (Python and Ruby have equivalents), or the registry's tag list. Not version-number probing: 16.13 stops at .2.
  - **When none can be found:** keep the line's patch with a log line saying so, as w8/175 does for a missing tag.
- **A range that includes the pin keeps it**, so `>=16`, `^16` and `16.x` change nothing.
- **Narration names the version:** `==> Using Node 16.13.2 (from NODE_VERSION=~16.13.0)`, as Render's log names the version it installed.
- **Docs:** ADR018's runtime row and ADR060 D7 record ranges next to exact versions.

## Regression checks

## Resolution

**DONE 2026-11-13, for Node.**

- **Recording the range:** `excludedNodeRange` (`lego/operator/internal/build/nativeversion.go`) records a Node semver range when the line's reviewed pin does not satisfy it. A partial version (`18.17`) counts as a range too, as node-version-alias reads it. It reads the range from `NODE_VERSION`, `.node-version`, `.nvmrc` or `package.json` `engines.node`.
- **Pinning a release:** in the resolve phase, `pinRangeRelease` (`nativeresolve.go`) lists the line's official tags through the existing Docker Hub resolver. It takes the newest release of the line's image variant that satisfies the range, and `pinExactVersion` then pins it like any exact version. The log names it: `==> Using Node 18.17.1 (from NODE_VERSION=~18.17.0)`.
- **When no release exists:** the reviewed patch stays, with a line naming it. That is this template's case: Node 16.13 has no bookworm image. The line reads `No official node:16.x-bookworm image satisfies ~16.13.0; using the reviewed Node 16 image (16.20.2)`.
- **Unchanged:** a range the pin satisfies consults nothing.
- **Tests:** `TestNodeRangePinsTheNewestOfficialReleaseInside` covers the env, `.nvmrc` and `engines` sources, and `TestNodeRangeWithoutAnOfficialReleaseSaysSo` covers the fallback. `TestNodeRangeListingFailureSaysSo` covers a failed listing, and the fixture's newer `-bookworm-slim` and `-alpine` tags are skipped. Each test fails when the range step is removed. Follow-up w8/308 covers a release with no image in the line's variant (16.13 has `-bullseye` but no `-bookworm`), and Node as a companion runtime.
- **Docs:** ADR060 D7 and ADR018's runtime row record it.
- **Scope:** Python has no ranges on Render, which requires a fully qualified version, and a Ruby `~>` range normally includes its line's pin, so neither is changed.
- **Production check after the next roll:** re-import the 2388 template; the API build log carries the "No official … satisfies ~16.13.0" line.
