# 029 — Binary secret files are silently corrupted in transit (upstream CLI + JSON-string contract); document it and say how to ship a binary file

Why: `bex services create … --secret-file keystore.p12:./keystore.p12` exits 0, and the service later fails TLS/keystore loading with no hint why. The file reaching `/etc/secrets/` is not the one on disk. Nothing in the docs warns that secret files must be text.

Live, 2026-09-27, production `726042a28`, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 41. Fixture: free busybox cron `srv-das78u0d0qnc73d7a3b0` (deleted) printing `sha256sum /etc/secrets/*`:

```text
local  big.txt (404,000 bytes, text)   sha256 e7c00957e85e23c4…   → container e7c00957e85e23c4…  ✔
local  bin.dat (1,024 random bytes)    sha256 414865cdf5e820bf…   → container 8dec9f779b5b53c7…  ✘ (silently different)
```

## Mechanism (upstream client + wire contract, not the bex server)

- The pinned CLI reads the file and sends `Content: string(data)` (`render-oss/cli` `pkg/service/secretfiles.go:34-42`). `encoding/json` replaces every invalid UTF-8 byte with U+FFFD, so binary content is altered before it leaves the machine.
- The Render API's secret-file `content` is a JSON string on every surface (REST/GraphQL/MCP), so no client can send raw bytes. The same happens with the unmodified `render` binary against Render. bex stores and mounts exactly what it received.

## Fix (docs; ~20m)

1. `docs/cli-compatibility-checklist.md`: add the secret-file `--secret-file` binary limitation to the upstream/Real-gaps list (pin-conditional).
2. `docs/bex-cli.md` and the dashboard secret-file help: "secret files must be UTF-8 text. For a binary file (keystore, `.p12`, DER cert), store it base64-encoded and decode at start, e.g. `base64 -d /etc/secrets/keystore.b64 > /tmp/keystore.p12`."
3. Optional, same PR if cheap: the dashboard secret-file upload refuses a non-UTF-8 file with that message instead of saving a mangled one. It reads the file client-side, so it can tell.

## Acceptance

- [ ] Checklist and CLI guide carry the limitation plus the base64 recipe. The dashboard either refuses binary uploads with the message or shows the same hint.
- [ ] No server change: text files (including a 404 KB one) keep round-tripping byte-identically, as they do today.

## Unverified

## Outcome (2026-09-27) — done

- `docs/bex-cli.md` has a new "Secret files must be UTF-8 text" section: why a binary `--secret-file` is altered in transit (pinned client `string(data)` + JSON-string contract), and a portable base64 recipe (`base64 < keystore.p12 > keystore.b64`, then `base64 -d /etc/secrets/keystore.b64 > /tmp/keystore.p12` at start).
- `docs/cli-compatibility-checklist.md` Real-gaps list: upstream/wire-contract entry, pin-conditional.
- Dashboard (`service-environment-editor.tsx`): uploads decode with `TextDecoder("utf-8", { fatal: true })` instead of `file.text()`, which silently swapped invalid bytes for U+FFFD. A binary file is skipped with the upload error, whose en/zh text now names UTF-8 and carries the base64 hint. Test: the upload case in `service-environment-editor.test.tsx` (text staged; a `.p12` with invalid bytes refused with the hint). `yarn test` (446 files), `tsc`, lint: green.
- No server change: text content round-trips exactly as before.
