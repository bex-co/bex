## Closed — 2026-11-16 (loopx session)

The adopted common base (w8/m91 t007/t008) is the supplier. `deploy/native-base/install.sh` installs Debian's `pandoc` with its normal closure, and the signed SPDX of the production image `sha256:5d6b8139…` (and of its successor `4b809600…`) lists `pandoc` and `pandoc-data` `2.17.1.1-2~deb12u1`. That is Debian 12's package, the base Render names for its native runtimes. `/usr/bin/pandoc` is on the default `PATH` before source and authored commands at build, pre-deploy and runtime. Its library closure is `libffi8`, `libgmp10`, `liblua5.3-0`, `libyaml-0-2` and `zlib1g`, all distribution packages under `/usr`; its data is `/usr/share/pandoc/data`. The common image's `toolchain-freshness.json` entry and ADR060 D7 inventory it. A changed package is a new image digest, so a reviewed pin change, re-qualified by a families run.

- **Review of the finding's candidates.** The official 3.12.1 static tarballs were neither executed nor adopted. The user's 2026-10-29 decision put every utility on the one Bookworm image as distribution packages, and Debian's build links Lua dynamically, which avoids the static release's C Lua-module limit that the finding noted. Render names Debian 12 as its base but no Pandoc version, so the version is not asserted to match Render's.
- **Observable behavior.** At build, the frozen original command converts the exact UTF-8 Markdown document to the expected HTML. At runtime, it converts it again on three requests with the network off. Both run in the `node-compute` case of the maintained utility cohort, which passed on `5d6b8139` (families run 43883107194) and `4b809600` (families run 43900534897). Both native clients reproduced it on production (t006).
