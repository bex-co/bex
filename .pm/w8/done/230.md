# A web service whose name contains `--` deploys `live` but its URL answers 503 `no-server` forever

Why: `POST /v1/services` accepts a name with consecutive hyphens and reports `slug` and `serviceDetails.url` with that name (`https://qa-20261102--3093dh.onbex.co`). The deploy closes `live` and an instance exists, but the public URL never reaches the app. Every request gets the activator's not-ready answer: `503`, `retry-after: 5`, `x-render-routing: no-server`, plus `{"error":"service not ready","retryAfter":5}` for API clients or the HTML wake page for browsers. A user sees a green deploy and a dead site. Render either serves such a service at its URL or names it differently; it never reports live and then serves nothing.

Severity: **major** (the service is unreachable with no error anywhere; a name like `my--app` or a generated `prefix--suffix` is enough). Attribution: operator route/activator for hostnames with `--` (`lego/operator/cmd/activator/main.go:364`, `app_controller.go` ingress backend). Not traced inside the cluster. Estimate: ~60m. Source: `/qa-find-bugs-cli` loop sweep 3093, 2026-11-02 08:24–08:30 UTC, pin `0688d26b5daa`, workspace `bex-canary`.

## Expected

Either the service serves at the URL it reports, or create normalizes the slug the way Render does (and reports that URL). It must never reach `live` while its URL is unroutable. A deploy that cannot be routed should fail with a reason.

## Narrowing — 2026-11-02 18:3x UTC (same sweep, pin `6ea2804bcb3d`)

Only the resource-name path keeps `--`. A name that is not a valid resource name is slugified, and the slugifier collapses `--`. Those services serve at once:

```text
name "QA--3093 Mixed"      → slug qa-3093-mixed                 → live, 200
name "QA 3093 Space Name"  → slug qa-3093-space-name            → live, 200
name "qa-3093-trail-"      → slug qa-3093-trail                 → live, 200
name "qa-3093-" + 60×"x"   → slug qa-3093-xxxxxxxxxxxxxxx-1e0fbd → live, 200
name "qa-20261102--3093dh" → slug qa-20261102--3093dh (kept)    → live, 503 no-server
```

So the fix can start at create. Treat a lowercase name containing `--` like any other non-resource name: slugify, collapsing the run, and keep the original as `name`/`displayName`. Still find out why a `--` host is unroutable, because existing Apps may already carry one. All four fixtures were deleted by ID (`GET` 404).

**DONE 2026-11-04** (`/loopx w8`): create and Blueprint no longer keep a name with a run of hyphens as its resource name. `slugKeepsName` (`lego/backend/internal/apps/blueprint_names.go`) gates both `serviceNameLabel` and `blueprintResourceSlug`, so `qa-20261102--3093dh` becomes the resource `qa-20261102-3093dh`, labeled with the name as typed. This is the same mapping the narrowing above showed serving 200 for `QA--3093 Mixed`. The legacy Blueprint mapping is unchanged, so an older service is still found. Tests: `TestCreateCollapsesAHyphenRunAndKeepsTheTypedName` plus new slug-table rows.

Routing root cause, still not explained: production Traefik access logs only show `qa-20261104--3093dh.onbex.co` (2026-11-04 22:59Z, after cleanup) matching the `bex-platform-host-fallback` Ingress. The operator's backend choice (`ingressBackend`, `serving := dep.Status.ReadyReplicas > 0`) and the activator lookup do not depend on the name's shape, and Traefik logged no error for a `--` Ingress. A read-only check on 2026-11-04 found no App in production with `--` in its name, and new ones can no longer be created through the API or Blueprints. So the live trace is not filed as separate work; reopen it only if a `--` App appears.

The same change also maps a typed `--` name in `NameAvailable`, so it answers for the name Create makes. A Blueprint sync finds an existing unlabelled `my--app` under `my-app` through `aliasLegacyResourceNames` instead of creating a duplicate.
