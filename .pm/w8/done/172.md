# The pre-deploy command still runs through bex's own `/bin/sh -c`: w8/164 fixed the Docker Command but not pre-deploy, so `sh -c <cmd>` silently runs nothing and shell-less images cannot pre-deploy

Why: w8/164 made a Docker Command run the way Render runs it, and ADR004:341 now says `shellCommand` applies to "every Docker Command, pre-deploy and cron command". The pre-deploy Job never adopted it. It still hardcodes `/bin/sh -c <command>`. The same command string therefore means one thing as a service's Docker Command and another as its pre-deploy command, in the same image. On a pre-deploy, the unquoted `sh -c <cmd>` form (Render's documented multi-command form, which w8/164 found in real Blueprints) runs the inner shell with only the first word as its script. That step then reports success without doing its work. For a migration, that means a deploy that goes live on an unmigrated schema.

**Severity:** minor (narrow trigger: no Docker/image `preDeployCommand` in the 601-file corpus uses `sh -c`, and shell-less images with pre-deploy steps are uncommon; but the failure mode is a silent success, not an error). **Attribution:** platform runtime (operator pre-deploy Job). **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1304, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1304--pre-deploy-launch)).

## Expected

A pre-deploy command on a Docker or image service is launched with the same rule as its Docker Command (`shellCommand`, as ADR004:341 states):

- `sh -c <rest>` runs the shell with the rest as its one script, so A prints `QA-PREDEPLOY-SHC-1304`.
- A plain command is exec'd directly, so B's `/whoami --help` runs on a shell-less image.
- Anything with shell syntax keeps `/bin/sh -c`.

Native and buildpack services keep their current shell launch, as their start commands do (`shellRunsStartCommand`).

When the pre-deploy program cannot start at all (`StartError`, exit 128), the failure names the program, as the start path does ("the startup program "/bin/sh" does not exist in this image"). It should not point at logs that cannot exist.

Render's own pre-deploy launch semantics are not captured (`docs/render-artifacts/docker-command.md` measures only the Docker Command; Render documents pre-deploy as paid-only and says nothing about a shell). The target here is bex's internal consistency and its own ADR004 statement, not a new Render measurement.

## Root cause

- `lego/operator/internal/predeploy/predeploy.go:136–148`: `Job` builds the container with `Command: []string{"/bin/sh", "-c", o.Command}` for every service. The doc comment still says "running `/bin/sh -c <Command>`".
- `lego/operator/internal/controller/app_controller.go:6118–6135` (`reconcilePreDeploy`) passes the raw string as `predeploy.Options.Command`. It never consults `shellCommand` (`controller/shell_command.go:117–135`) or `shellRunsStartCommand` (`deployment_projection.go:234–246`), which the Deployment (`deployment_projection.go:279–281`) and cron (`cronPodSpec`, `app_controller.go:4948–4952`) both use since `7866fb3ee`.
- `predeploy.go:247–267` `FailureMessage` has no `StartError` branch, so a program that never started reports "exited with code 128; check the pre-deploy logs". Its own comment says "Image failures name the cause instead of pointing to logs for a command that never started".

## Fix

1. Move the launch decision to the caller. `predeploy.Options` carries an argv (`Command []string`) instead of a string. `reconcilePreDeploy` passes `shellCommand(command)` when `shellRunsStartCommand(app, image, launch)` is true, and `[]string{"/bin/sh", "-c", command}` otherwise (native/buildpack, unchanged; w8/m61's absolute-shell rule still holds). This keeps `predeploy` free of a controller import.
2. In `FailureMessage`, map a terminated `StartError` to the start path's wording (reuse the `startExecFailure` parsing near `app_controller.go:5477–5520`): name the program and say it never ran.
3. Docs:
   - ADR004:268/281 and the pre-deploy row (ADR018:88) should describe the shared rule.
   - ADR018 row 84's "Docker Command launch (w6/077) … bex runs `sh -c <command>`" is stale since w8/164.
   - `docs/render-artifacts/docker-command.md:27–43` ("The operator runs the Docker Command as `sh -c <command>` … bex's `sh -c` is kept … Existing services must keep `sh -c`") should state the w8/164 rule and the remaining divergence.
   - The comments at `app_controller.go:5512` and `predeploy.go:25,107,136` also need the update.
4. Release recognition: if pre-deploy argv is compared when matching release records (as `release_config_selection.go:408` does for the start command), accept both the old `/bin/sh -c <command>` form and the new one.

## Blast radius

One builder (`predeploy.Job`), one caller (`reconcilePreDeploy`). Affects every Docker/image web, private and worker service with a pre-deploy command. Commands that need a shell are unchanged, as are plain commands on images that have `/bin/sh`, apart from argv shape. Only the `sh -c <rest>` form and shell-less images change behavior. Native/buildpack pre-deploys are untouched. Cron runs already use `shellCommand` (`cronPodSpec`). One-off jobs are refused on bex (`backend/internal/jobs/service.go:187`), so they have no launch path to fix. The operator's other hardcoded shells (`publish/publish.go`, `build/build.go:1428`) run platform-owned scripts, not tenant commands.

## Acceptance

- Unit: `predeploy.Job` uses the argv it is given. The controller test asserts a Docker/image App with `/bin/sh -c echo x` gets `["/bin/sh","-c","echo x"]` and `/whoami --help` gets `["/whoami","--help"]`, while a native App keeps `["/bin/sh","-c",cmd]`. `FailureMessage` turns a `StartError` pod into the named-program message.
- Live after deploy: repeat A (the marker appears in the pre-deploy logs) and B (the pre-deploy succeeds and the service goes live). An existing pre-deploy using `&&` still runs. Delete fixtures by ID with 404 proofs.
