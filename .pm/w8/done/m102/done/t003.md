## Closed — 2026-11-19 (loopx session)

- **Render's contract.** [render.com/docs/native-runtimes](https://render.com/docs/native-runtimes) lists `pigz` with the marker its legend defines as "Available during builds only", on Debian 12 "bookworm", and names no version (read 2026-11-19). bex supplies Debian 12's `pigz` 2.6-1 (t001). Which version Render ships is unverified, and no Render-hosted comparison was run.
- **Build only, with one stated difference.** bex's build and runtime share one image, so `pigz` is also on the runtime image. Nothing depends on that: the accepted runtime behavior is serving the bytes the build wrote, which the maintained check does with no pigz on `PATH` (t005). Render's narrower contract is the one documented to tenants, and no runtime availability is promised.
- **pigz's contract.** The [pigz documentation](https://zlib.net/pigz/) describes gzip-compatible output, zlib and pthread dependencies, `-p` threads, `-b` block size, `-i` independent blocks, `-z` zlib, `-K` ZIP, `-11` zopfli and the `PIGZ` variable. The maintained checks run each of these (t005).
- **ADR060.** The D7 m102 row records the packages, the behaviors accepted, the exit statuses and the limits: no compression-speed or parallel-scaling guarantee, and pigz present but not needed at runtime. It adopts with the next native rebuild on the current image, as every D7 tool does.
- **No surface change.** pigz arrives through the image every native build already uses. REST, GraphQL, MCP, Blueprint and the dashboard keep their schemas, fields and error shapes, and no selector, toggle or launcher change was added.

  - Each create used the frozen original build and start commands from `testdata/native-utilities/original-cases.json`, with no installer line. They differ only in the per-client marker (`QA423_5494_bex` / `_render`).
