## Closed — 2026-11-19 (loopx session)

Every `native-common-image.yml` utility cohort (`TestNativeUtilityGeneratedImages`) runs these real-image checks on the image it publishes:

- **The original asset app** (already maintained). `node-compute` runs the frozen m98 program on the Node 24 primary through `original-cases.py`. At build, the original `jq -e -c` filter writes the exact manifest and the original `rsync -a --delete --exclude='*.tmp'` copies the three published files byte for byte, dropping the own draft and the own stale output. Three HTTP requests on a `--network none` runtime repeat both, and the frozen oracle checks each.
- **Already maintained in `utility-check.py`:** an rsync copy of Unicode and space-named binary files with an exclude and stale-file removal, a malformed-JSON jq failure and a missing-source rsync failure.
- **New jq and rsync checks** in `utility-check.py`, at the `node-compute` build and network-off runtime and at the `node-static` build:
  - m98's own manifest and asset tree through the original jq and rsync argv, outside the original program, compared with a manifest and file map computed independently in Python;
  - jq: `-r` raw paths, `@sh` quoting that `shlex` splits back into the space-containing names, an Oniguruma `\p{L}` class matching only the Unicode name with `sub` rewriting it, `--arg`/`--argjson` values passed as data, `@base64` and `@base64d` against Python's encoding, `--slurp`, and the exit statuses (`-e` gives 1 on `null` and `false`, a compile error 3, `error()` 5 with its message);
  - rsync: `-a` keeps a `0750` mode, exact modification times, a symlink and an empty directory; `--delete` removes a stale directory but keeps an excluded file until `--delete-excluded`; a `--dry-run --itemize-changes` lists nothing when in sync and exactly `>f.st...... data.txt` after a change, without writing it; a source without its trailing slash copies the directory itself.
- **Sharper omission controls.** `missing-jq` now also proves `libjq.so.1` and `libonig.so.5` remain and `command -v jq` fails, so the original build fails at its jq step on the missing program alone; `missing-rsync` clears the shell's command cache and proves jq remains. Both must still reach the original command after their ready line.
- **How this was checked before shipping.** The host is arm64 and the adopted image is amd64-only, so the generated-image gate cannot run here. On Debian 12 arm64 with the identical `jq`/`libjq1` `1.6-2.1+deb12u3`, `libonig5` `6.9.8-1` and `rsync` `3.5.0+ds1-0+deb12u1` (and the same rsync libraries) from Debian's archive:
  - the new block passed on `python:3.13-bookworm` as uid 1000 and as root, with no network;
  - each of 16 mutations failed the assertion it targets (for example no `select`, no `--exclude`, no `--delete`, `-c` for `-r`, `join` for `@sh`, `.+` for `\p{L}+`, `-r` for `-a`, no `--dry-run`, no `--delete-excluded`, and `tree/` for `tree`);
  - on `node:24-bookworm`, the original m98 build and its three network-off runtime requests passed through `original-cases.py`;
  - after the exact new `missing-jq` command, the original build printed `QA_ASSET_BEFORE` and failed with `jq: command not found`; after `missing-rsync`, it printed `QA_ASSET_JQ` and failed with `rsync: command not found`. A `missing-jq` variant that also deleted `libjq.so.1` stopped in the removal layer before its ready line.
  - The push of this change re-runs the amd64 utility cohort through `native-common-image.yml`; that run is the amd64 proof.
