# Blueprint `fromService.envVarKey` cannot reference Render's default variables (`RENDER_EXTERNAL_URL`, `RENDER_EXTERNAL_HOSTNAME`, …), a documented Render pattern used by 1 in 23 real Blueprints

Why: the most common way a Render Blueprint gives a frontend its backend's public URL is `fromService: {name: api, type: web, envVarKey: RENDER_EXTERNAL_URL}`. Render's Blueprint reference documents referencing default variables, with a `RENDER_EXTERNAL_HOSTNAME` example. Bex refuses the reference because it never injects `RENDER_*` variables (a deliberate ADR018 choice). So the whole Blueprint fails validation, although bex knows the target's public URL and hostname exactly.

**Severity:** major (blocks real multi-service Blueprints; 26 of 601 sampled files use the pattern). **Attribution:** server (Blueprint reference resolution). **Estimate:** 90m. **Source:** `/qa-find-bugs-cli` sweep 1270, 2026-10-21 ([evidence](../evidence/cli-sweep1270/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, deployed pin `9cace6b6e25d`, workspace `bex-canary`, human device-login grant, HEAD-built pinned CLI. The manifest is two free image web services. It passes Render's pinned Blueprint schema with 0 errors.

```yaml
services:
  - type: web
    name: qa-20261021-api
    runtime: image
    image: { url: docker.io/ealen/echo-server:0.9.2 }
    plan: free
  - type: web
    name: qa-20261021-front
    runtime: image
    image: { url: docker.io/ealen/echo-server:0.9.2 }
    plan: free
    envVars:
      - key: BACKEND_URL
        fromService: { type: web, name: qa-20261021-api, envVarKey: RENDER_EXTERNAL_URL }
      - key: APP_HOST
        fromService: { type: web, name: qa-20261021-front, envVarKey: RENDER_EXTERNAL_HOSTNAME }
```

`bex blueprints validate default-ref.yaml -o json` → exit 1:

```json
{"errors":[{"column":9,"line":15,"path":"services[1].envVars[0]","error":"service \"qa-20261021-front\": envVars[\"BACKEND_URL\"]: fromService.envVarKey references env \"RENDER_EXTERNAL_URL\" on service \"qa-20261021-api\", which has no such plainly-defined variable"}],"valid":false}
```

Corpus: 601 distinct public `render.yaml` files from GitHub code search. 26 of them use `envVarKey: RENDER_*`: `RENDER_EXTERNAL_URL` 33 times, `RENDER_EXTERNAL_HOSTNAME` 12, `RENDER_SERVICE_NAME` 2, `RENDER_GIT_COMMIT` 2 (Render excludes this one) and `RENDER_INTERNAL_HOSTNAME` once. Of the 218 files that pass Render's own pinned schema, three are refused only for this. One of them, `linzhi-524/linjian-peek-public`, says it moved from `hostport` to the server's public `RENDER_EXTERNAL_URL` on purpose.

## Expected

[Render's Blueprint reference](https://render.com/docs/blueprint-spec): "A service can self-reference most default environment variables, depending on its service type and deploy method". It excludes `RENDER_CPU_COUNT`, `RENDER_GIT_COMMIT`, `RENDER_INSTANCE_ID`, `RENDER_WEB_CONCURRENCY` and `WEB_CONCURRENCY`. Its example copies `RENDER_EXTERNAL_HOSTNAME` to `APP_HOST`. The real files use the same lookup against another service in the file. [Render's default variables](https://render.com/docs/environment-variables) define `RENDER_EXTERNAL_URL`/`RENDER_EXTERNAL_HOSTNAME` as the web service's or static site's public URL and hostname, empty for other types.

Target: a `fromService.envVarKey` naming a referenceable Render default resolves to the truthful bex value. Without injecting any `RENDER_*` variable into containers (ADR018 stands), the consumer gets its own key with:

- `RENDER_EXTERNAL_URL` → the target's public URL (`https://<slug>.onbex.co`)
- `RENDER_EXTERNAL_HOSTNAME` → its hostname
- `RENDER_SERVICE_NAME` → its name
- `RENDER_SERVICE_ID` → its ID
- `RENDER_SERVICE_TYPE` → `web|pserv|worker|cron|static`
- `RENDER_GIT_BRANCH` and `RENDER_GIT_REPO_SLUG` for Git-backed targets
- `RENDER_DISCOVERY_SERVICE` only if ADR041's discovery host exists, otherwise refuse

The excluded names keep a refusal that says Render also excludes them. A target with no public URL (private service, worker) gets `""`, as Render documents.

## Root cause

`lego/backend/internal/apps/deploy.go:3186` resolves `fromService.envVarKey` only against the target's plainly-defined `spec.Env` entries. The post-apply copy check (`deploy.go:1487`, "no such plainly-defined variable in its current links") has the same rule. Render's default variables are not in `spec.Env`, because `appEnv` injects only `PORT` (`lego/operator/internal/controller/app_controller.go:5056–5076`; ADR018:137 "bex does not inject `RENDER_*` equivalents"). No other path resolves them.

## Fix

Add a resolver table for the referenceable defaults, keyed by Render's names, that computes values from the target App (slug/host via `EffectiveHosts`, ID, name, type, branch/repo). Consult it in the `fromService.envVarKey` path before the plain-env lookup, on both the validate/plan path and the apply/copy path, so a later slug or host change re-seeds the copy like any other `envVarKey` copy. Keep the five excluded names refused with a Render-matching sentence. Record the table in ADR049 (references) and cross-link it from ADR018's `RENDER_*` row, which stays a "not injected" divergence.

## Acceptance

- Compiler and plan tests: the manifest above validates. Its plan shows `BACKEND_URL` = the API's `https://<slug>.onbex.co`, and `APP_HOST` = the front service's own hostname (self-reference). `RENDER_GIT_COMMIT` and `RENDER_INSTANCE_ID` are refused with the exclusion sentence. A private-service target's `RENDER_EXTERNAL_URL` resolves to `""`.
- Apply/copy test: the consumer's Environment shows the resolved value, and recreating the target with a different slug re-seeds it.
- REST/GraphQL/MCP validate and the dashboard import return the same result.
- Live after deploy: validate the manifest, then sync it as a Blueprint on owned free fixtures. `GET /cf` on the front service shows `BACKEND_URL` equal to the API's URL. Delete everything by ID with 404 proofs. Re-run the three corpus files: no `plainly-defined` refusal remains.

## Blast radius

Blueprint compile, plan, apply and the post-apply copy reconciler. The REST/GraphQL/MCP env-var APIs have no `fromService`, so they are unaffected. The container environment is unchanged: still only `PORT` plus user variables.
