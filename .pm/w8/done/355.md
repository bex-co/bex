# A registry-credential create with no `ownerId` succeeds in the caller's default workspace, where Render refuses it

Why: Render's create-registry-credential requires `ownerId`. The pinned public spec (`lego/backend/internal/api/openapi/render-public-api-1.json`, `POST /registrycredentials`) lists `required: [name, registry, username, authToken, ownerId]`. bex answers 200 instead, and stores the credential in whichever workspace is the caller's default. A client that forgets the field gets a credential in a workspace it did not name, and nothing says so. Sibling creates already refuse: webhooks answer 400 `WEBHOOK_OWNER_REQUIRED` (`lego/backend/internal/webhooks/rest.go:192`), and projects answer 400 "name and ownerId are required" (`lego/backend/internal/projects/rest.go:173`).

- Severity: minor. It needs a client that omits a required field, and the pinned CLI has no registry-credential command. But the write lands silently in another workspace.
- Versions: production `https://api.bex.co/v1/` on pin `12716d1d7097`, 2026-11-20.
- Context: routine `cli-qa` run `r14-f377`, QA human device-flow token. A probe without `ownerId` meant for `bex-canary` created its credential in the QA user's default workspace `bex`. The worker deleted it there, and a GET confirmed the 404.

## Repro

```text
POST /v1/registrycredentials {"name":"qa-<nonce>-rc","registry":"DOCKER","username":"qa-fake","authToken":"<fake>"}
  → 200 {"id":"rgc-…","ownerId":"<caller's default tea- id>",…}   (Render: 400, ownerId is required)
```

## Cause

The REST handler passes `req.OwnerID` through unchecked (`lego/backend/internal/registrycreds/rest.go:164-185`). `Service.Create` then calls `core.WithWorkspace(ctx, "")` (`service.go:226`), and an empty id falls back to the caller's default workspace.

## Fix

Refuse a REST create whose `ownerId` is empty with 400 before any write, naming the field, in the same shape as the webhooks refusal. Check whether GraphQL `createRegistryCredential` and the MCP tool share the default. The dashboard always sends the selected workspace (w4/443), so its path is unaffected, but confirm it.

Sweep: list every other REST create whose pinned schema requires `ownerId` (services, postgres, key-value, env-groups, blueprints and the like), find the ones that still default silently, and fix them the same way or record why not.

## Acceptance

- `POST /v1/registrycredentials` without `ownerId` → 400 naming `ownerId`, and nothing is created: the caller's workspaces list no new credential.
- With `ownerId` set to a member workspace → 200, as today.
- The sweep's findings are recorded in this note, with each sibling fixed or justified.

## Dedupe

- No board item covers an omitted `ownerId` on create.
- w4/128 (done) kept "omitted `ownerId` = default workspace" for the by-id GraphQL routes on purpose. w8/m149 (done) made unfiltered lists span all of the caller's workspaces.
- Neither covers a create, where Render requires the field.

## Progress

- 2026-11-20: fixed in `3f47e1381`, at the Render request gate (`lego/backend/internal/api/render_openapi.go`). `renderRequiredCompatibility` no longer relaxes `ownerId` on any create but the webhook's, and every body that requires `ownerId` re-declares it with `minLength: 1`. An absent or blank `ownerId` answers 400 `OWNER_REQUIRED` (`ownerId is required`, `params.field: ownerId`) before any handler runs. `TestRenderCreatesRequireANamedOwner` and `TestRegistryCredentialCreateWithoutOwnerWritesNothing` pin it, and both fail on the old gate. ADR006's "deliberate deviation" is retired, and ADR018 (Create service row) and `docs/render-artifacts/openapi-request-validation.md` record the rule.
- Sweep, every create whose pinned body requires `ownerId`, before the fix (probed through `newRenderRequestValidator` with each handler stubbed, then traced into the handler):
  - `services`, `postgres`, `key-value` (and the `/redis` alias), `env-groups`, `registrycredentials`: the gate relaxed `ownerId`, so an absent or blank one reached the handler and landed in the caller's default workspace. Fixed.
  - `build-sources`, `sandboxes`, `sandbox-groups`: the gate refused an absent one, but `"ownerId":""` passed and defaulted (`CreateBuildSource` and the sandbox creates call `core.WithWorkspace(ctx, "")`). A generated Render client sends `""` when the caller never set it. Fixed by `minLength: 1`.
  - `projects`: the gate refused an absent one and the handler refused `""`. It now answers `OWNER_REQUIRED` either way.
  - `webhooks`: the handler already refused both as 400 `WEBHOOK_OWNER_REQUIRED`, so its relaxation stays and its named code is unchanged.
  - `dedicated-ips`, `workflows`: bex serves no create (ADR018 operation omissions), so nothing defaults.
- Not changed, with the reason:
  - GraphQL `createRegistryCredential` and the other GraphQL creates keep "omitted `ownerId` = default workspace". Render has no GraphQL, and ADR006 and ADR018 document that rule. The dashboard always sends the selected workspace (`dashboard/src/features/registry-credentials/hooks/use-create-registry-credential.ts`, `ownerId: currentWorkspaceId`), and it creates only through GraphQL, so it is unaffected.
  - MCP `create_registry_credential` is a bex extension (Render's MCP has no registry-credential tool). Like every MCP create it uses the call's `workspaceId`, else the default. Render's MCP creates take no owner argument either.
  - The pinned Render CLI refuses to run without a workspace (`config.WorkspaceID` returns `ErrNoWorkspace`) and always sends `ownerId`.
- Parked: production's pin `11b1e8f85f06` (rolled 15:24 UTC) predates the fix.
