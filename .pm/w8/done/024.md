# 024 — `bex logs --tail` with several resources silently follows only the first one

Why: `bex logs -r A,B --tail` looks like it is watching both services, but every line from B (and any later resource) is silently dropped. Someone tailing an app and its worker during an incident sees only half the picture, with no hint that anything is missing. The history query over the same resources returns both.

Live, 2026-09-26, production `726042a28`, `bex v0.2.1` (pin v2.27.0), human device login, workspace `bex-canary`. Found by the `/qa-find-bugs-cli` sweep 23. Fixtures: free web services A `srv-darsnigd0qnc73d79vrg` and B `srv-darsniod0qnc73d79vt0` (deleted):

```text
$ bex logs -r A,B --tail -o text      # 40 s, one request to each service's /<marker>-A and /<marker>-B
→ A's marker ×2, B's marker ×0, no error, exit on timeout
$ bex logs -r B,A --tail -o text      # order reversed
→ B's marker ×2, A's marker ×0
$ bex logs -r A,B --text <marker> --limit 50 -o json      # history, same pair
→ both A and B lines (3 each)
```

## Mechanism

- `lego/backend/internal/logs/rest.go:145` in `logsSubscribe`: `q.App = resources[0] // subscribe follows a single App`. The remaining resources are parsed and then discarded, with no error.
- The history handler just above loops over every resource and merges them (`rest.go:114-127`), so the two paths disagree on the same query shape.
- The pinned client sends `resource` as a list for subscribe too (`render-oss/cli` `pkg/client/types_gen.go:4158-4159`, `SubscribeLogsParams.Resource`, "Filter logs by their resource"), so a multi-resource tail is a supported request, not a client quirk.

## Fix

Pick one and record it:

1. **Fan-in (Render-shaped):** authorize every resource, acquire a subscription slot per resource (or count the whole subscription against the caller's/workspace's shares by resource count), follow each with the existing single-App follower, and merge frames onto the one WebSocket/SSE stream in arrival order. The WS and SSE writers already emit Render log objects carrying `resource` labels.
2. **Honest refusal (quick):** if `len(resources) > 1`, answer `400` before upgrading: "live tail follows one resource; pass a single --resources id". This beats silently dropping the rest.

Option 1 is the parity fix. Option 2 is an acceptable interim step that removes the silent loss.

## Acceptance

- [ ] `bex logs -r A,B --tail` either shows both services' new lines (option 1) or exits non-zero with the named one-resource message (option 2). It never streams only A.
- [ ] Backend test: a subscribe with two resources on the WebSocket and SSE paths fails on the old code.
- [ ] If option 1: per-resource authorization is enforced (a resource the caller cannot read is refused, not merged), and subscription-slot accounting covers every followed resource.

## Outcome (2026-09-27) — done (option 1, fan-in)

- `logsSubscribe` (`lego/backend/internal/logs/rest.go`) builds one query per requested resource. Each goes through `acquireSubscription` before the stream opens, which authorizes it (`can_view_logs`) and counts a slot against the process/caller/workspace shares, so an unreadable or unknown resource refuses the whole request with its status (404/403/429) and nothing streams.
- `followAll` runs the existing single-resource follower per resource and serializes frames and keepalives onto the one WS/SSE/NDJSON writer. The first follower to fail ends the tail with that refusal, and a client disconnect ends all of them quietly. One resource behaves exactly as before.
- Tests: `TestSubscribeFollowsEveryRequestedResource` (SSE + NDJSON × both orders, and the WebSocket path; fails with only the first resource followed) and `TestSubscribeRefusesWhenAnyResourceIsUnknown`. `go test -race` + lint green. ADR010's live-tail paragraph records it.
- Datastore + service mixes: the datastore follower still refuses live tails (`… live log subscription is not supported`), so a mix ends with that refusal. Unchanged behavior, now explicit.
