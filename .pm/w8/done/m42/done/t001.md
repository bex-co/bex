## Objective

Find out why vitest on `bex-ci` sometimes cannot start a forks worker (`[vitest-pool]: Failed to start forks worker … Timeout waiting for worker to respond`, run `35836680656`, where all 439 files passed but the run still exits 1) and why a run can go silent for 53 minutes (run `35696069432`, last output 07:20:47, canceled 08:13:18). Then fix the cause.

## Context

- `dashboard/vitest.config.ts`: `environment: "jsdom"`, `testTimeout: 10000`. No `pool`, `maxWorkers`, or `poolOptions` is set, so vitest uses the default forks pool sized to the host's CPU count.
- `.github/workflows/dashboard-test.yml:63` runs `yarn typecheck && yarn lint && yarn test` on the shared `bex-ci` ARM64 pool. The job has no `timeout-minutes`.
- Run durations: setup 247 s and environment 158 s out of a 318 s run. Worker startup is a large share of the time.

## Steps

1. Pull the failing logs for both runs. Check whether the host's CPU count as vitest sees it matches the runner's actual allocation (container cgroup vs host `nproc`).
2. Reproduce locally under CPU contention (for example `taskset`, or `stress-ng` beside `yarn test`) until the worker-start timeout or the hang appears.
3. Fix the cause: size the pool to the real allocation or pick an appropriate pool, and find whatever test or handle keeps the process alive during the hang.
4. Add a job `timeout-minutes` so a hang fails in minutes rather than holding a run for most of an hour.

## Outcome (2026-09-25)

**Root cause (both symptoms): host CPU oversubscription on the shared runner VM, not job sizing.**

- The fleet is 7 `bex-ci` + 3 `bex-production` runner containers on one Docker Desktop VM with **15 CPUs**; each container has a **4-CPU** cgroup quota (`cpu.max 400000 100000`), i.e. 40 CPUs of quota on 15. Inside a runner, `nproc` reports 15 but Node 22.23 `os.availableParallelism()` reports 4, so vitest's default is 3 forks — the job does not oversubscribe its own quota. The overload is host-wide.
- Every qualifying push runs each test gate **twice** at once: `backend-test`/`operator-test`/`dashboard-test`/`opensandbox-controller-test` trigger on `push: main` and are also `workflow_call`ed by `deploy.yml` for the same SHA.
- Evidence of starvation in the hang run `35696069432`: `yarn typecheck && yarn lint` alone took **20 min** (06:58:22 → 07:18:45); a 2-minute gap between two files at 07:24:38 → 07:26:48.
- **Worker-start timeout** (run `35836680656`): vitest 4.1.10 hardcodes `START_TIMEOUT = 60s` for a forks worker to answer (`cli-api.*.js:2794`). With `isolate: true` every one of the 439 files spawns a fresh worker, so each file is one more chance to miss it on a starved host; the run passed 439/439 and still exited 1.
- **53-minute hang**: at 07:26:24 vitest logged `[vitest-pool]: Timeout terminating forks worker for … create-context.test.ts`; two more files finished, then silence until cancellation at 08:13:18 (211 of ~439 files done). Consistent with a worker process that could not be reaped on the starved host; unbounded because the job had no `timeout-minutes` (default 360).

**What was measured and rejected** (local, 3 workers): forks 140 s vs threads 138 s uncontended — spawn cost is not the lever; per-file `setupFiles` (~216 ms) + jsdom (~240 ms) are. `--no-isolate` fails 304 tests (the suite relies on per-file `vi.mock`/module isolation). Full suite under 2× CPU oversubscription: 657 s, 440/440 passed, no worker-start error — the Mac is less starved than a 4-CPU-quota runner on the 15-CPU VM, so the failure did not reproduce locally.

**Fix in this repo:** `timeout-minutes: 30` on the dashboard job (slowest of the last 40 successful runs: 23 min), so a hang fails in 30 min instead of holding the deploy gate. No retries, skips, or `testTimeout` changes.

**Remaining cause (not in this repo — needs a user decision):** reduce host oversubscription — fewer concurrent runners (runner source `bex-co/block-eden-mono` `projects/github-runner/`, within `DO_NOT_DO.md` #RUNNER-HOSTS: same single host), and/or stop running every gate twice per push (drop the `push: main` triggers from the four gate workflows — but that loses the per-commit verdict for deploy runs cancelled while queued behind `bex-production-deploy`).
