# 038 — `BEX_WORKSPACE=<name>` is documented but every list/get answers "you are not allowed to take this action"

Why: `docs/bex-cli.md:58` promises "Active workspace id or name", but a name breaks almost every command with a misleading permission error. CI users following the doc will conclude their account lacks access.

Severity: minor. Attribution: Bex launcher plus docs, not upstream (Render documents no `RENDER_WORKSPACE`; upstream treats the value as an ID).

## Repro (2026-10-03, `/qa-find-bugs-cli` w8 loop sweep 1)

Production, released `bex v0.2.1` and HEAD `f68385c4f` build (same result), human device login, isolated config.

```text
BEX_WORKSPACE=bex-canary bex services -o json          → exit 1  Error: you are not allowed to take this action
BEX_WORKSPACE=bex-canary bex pg get <owned-pg-name>    → exit 1  same
BEX_WORKSPACE=bex-canary bex workspace current -o json → exit 1  Error: failed to list owners: unexpected response: 403 Forbidden
BEX_WORKSPACE=bex-canary bex blueprints validate x.yaml → exit 1  validation request failed with status 403: {"error":"forbidden",…}
BEX_WORKSPACE=no-such-ws  (any of the above)            → the same 403, indistinguishable
control: BEX_WORKSPACE=tea-daif693dqjvc73e7as3g          → all succeed
control: bex workspace set bex-canary                    → resolves and stores the id ("Workspace set to: bex-canary (tea-…)")
```

Wire: `GET /v1/owners/bex-canary` → `403 {"error":"forbidden","id":"forbidden","message":"forbidden"}`, and `GET /v1/services?ownerId=bex-canary` → the same 403.

## Mechanism

- `lego/cli/internal/bridge/bridge.go:67` copies `BEX_WORKSPACE` verbatim into `RENDER_WORKSPACE`. Upstream `pkg/config/config.go:122-124` returns that env value as the workspace **ID** for every command (`ownerId=` query, `owners/{id}`, Blueprint validate owner).
- Only the bex-native `X-Bex-Workspace` header path (`lego/backend/internal/api/cli_workspace.go`, `cliWorkspaceID`) resolves names, and only for `/v1/services/{name}/…` paths. That is why `deploys list <service-name>` worked in the same environment.

## Fix (pick one, then align docs)

- **Preferred:** in `bridge.apply`, when `BEX_WORKSPACE` is not a `tea-` id, resolve it once against `GET /v1/owners` with the same credential. An exact name match maps to the id. No match gives `no workspace named "<x>"` (the `workspace set` wording). More than one match gives `several workspaces are named "<x>"; use the id` (the server's `WORKSPACE_NAME_AMBIGUOUS` wording). Set `RENDER_WORKSPACE` to the id. Do this only when `RENDER_WORKSPACE` is unset, so the escape hatch is preserved.
- **Minimal:** change `docs/bex-cli.md:58` to "Active workspace **id**" and recommend `bex workspace set <name>` for names.
- Either way, keep the `X-Bex-Workspace` header carrying the resolved id, so the w8/m45 server path sees one canonical value.

## Acceptance

- [ ] `BEX_WORKSPACE=<unique name> bex services -o json`, `pg list`, `workspace current` and `blueprints validate` behave exactly like the id. An unknown name exits 1 naming the workspace, not "not allowed". (Or the docs say id-only and the troubleshooting text names the symptom.)
- [ ] `RENDER_WORKSPACE` set explicitly still wins untouched. An id value makes no extra request.

## Dedupe

`rg BEX_WORKSPACE .pm` shows only id-valued usage. The `w8/m45` README shows `BEX_WORKSPACE=bex-canary` in a transcript, but that evidence predates a name-vs-id check. No item covers name values.

Estimate: ~40m (launcher resolve and tests) or ~10m (docs only).

## Closure (2026-10-03)

Fixed with the preferred option. `bridge.ResolveWorkspaceName` (`lego/cli/internal/bridge/workspace.go`, called from `main.go` after `InstallControlPlaneHeaders`) resolves a non-`tea-` `BEX_WORKSPACE` once through upstream's own authenticated client (`owner.Repo.ListOwners`, `name` filter plus an exact match) and sets `RENDER_WORKSPACE` to the id. The `X-Bex-Workspace` header therefore carries the id too. An unknown name exits 1 with `no workspace named "<x>"`; a duplicate exits 1 listing the ids. An id costs no request, an explicit `RENDER_WORKSPACE` is never resolved, and with no usable login the value passes through to upstream's usual login error. Evidence: table test `TestResolveWorkspaceName`, plus the built binary run against a stub API. Name → `owners?name=bex-canary` then `ownerId=tea-…` on services/postgres/key-value/projects/workflows; id → no owners call; unknown/duplicate → exit 1 with the messages above; explicit `RENDER_WORKSPACE` → untouched. `docs/bex-cli.md` documents the behavior. `cd lego/cli && go test ./...` and CLI lint are clean. Not done: a live production check, because the local CLI login had expired and re-login needs an interactive browser. Users get the fix in the next `bex-cli/v*` release (`/release`).
