# A Restart of an image service that has never gone live deploys its saved image and reports "restarted successfully", where a repo-backed service with no live deploy is refused 409

Why: Render defines a restart as a new instance with "the exact same Git commit and configuration as the running instance", and bex refuses a repo-backed restart with nothing live for that reason. An image service with nothing live instead deploys whatever image is saved, so a save-only image change goes live through a Restart and the CLI says the service was restarted.

- Severity: major. The CLI and REST report a restart, but a different, never-deployed image goes live, and a saved change skips the manual deploy that Render and bex both require for it.
- Versions: bex CLI v0.9.0 release binary. Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md` (`4fd34231b637`). Production pin `7e481dece7ac`. The code is unchanged on main `278403b4ea`.
- Context: 2026-11-21 15:41–15:48 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY `-o text`. Routine `cli-qa`, run r27, nonce `1d7f`. Fixtures: free image web service `srv-dc0rnfi5r8pc73e307h0` and free native Python service `srv-dc0roou0ri4c73c3vgg0` (control), both deleted (404 confirmed).
- Attribution: server (`lego/backend/internal/deploys`). Every Restart surface shares `deploys.Service.Restart`: REST `POST /v1/services/{id}/restart`, GraphQL `restartServer`, MCP `restart_service`, and the dashboard's Restart service and services-list Restart.

## Render

- [render.com/docs/deploys § Restarting a service](https://render.com/docs/deploys#restarting-a-service) (read 2026-11-21): "the new instance always uses the exact same Git commit and configuration as the running instance at the time of the restart". The Manual Deploy table: Restart "Deploys the same commit that's currently deployed for the service".
- [render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image): image-backed services "must be deployed manually". A saved image URL waits for a deploy (bex matches: `services update --image` opens no deploy).
- Render documents no restart for a service with nothing running. bex's own repo-backed rule (`service.go:709-730`, "has no running release to restart, so it is refused rather than silently deploying the branch head") is the parity-consistent reading, and ADR018's Restart row promises that a saved but undeployed setting waits through a Restart (w4/m433, w32/058).

A live control passed on the same run: `bex restart` of a live free image service brought up a new instance (new `RENDER_INSTANCE_ID`, process start time reset) 25 s later on the same image.

## Root cause

- `lego/backend/internal/deploys/service.go:692-707` `restartNow`: `restartSelectedRelease` returns nil when nothing serves (`rollback_config.go:285-289` `restartSelectable` needs a serving deploy with a resolved image). The fallback then checks for a live deploy only `if a.Spec.Repo != ""` (`liveCommit`, `:716-736`). An image service skips the check and reaches `triggerFetched(…, store.TriggerRestart)` with no pinned artifact, which deploys the saved `spec.image` and saved configuration.
- `restart_wait.go:113-129` `deferRestart` returns `deferred=false` when there is no live deploy, and its comment says "the service has never been live, which Restart's own refusal covers". That refusal exists only for repo-backed services. So an image service restarted while its first deploy is still in flight also starts a second deploy of the saved image at once (inferred from the code, not run live).
- History: w1/m148 (`7e45c9ce14`, 2026-10) made Restart "redeploy an image-backed service's image" and refuse repo-backed services with no live deploy. w5/m107 later made Restart run the retained live image, but left the image path's fallback in place. w1/m179's DoD amendment ("a restart is a deploy for an image service") recorded that behavior without a parity decision, and ADR018 has no sign-off for it.

## Fix

- In `restartNow`, refuse every service with no live deploy before the trigger, whatever its source: `409` `conflict: service "<selector>" has no live deploy to restart; deploy it first`, the same error the repo path returns now. Keep `liveCommit` for picking the commit. Nothing is mutated, no deploy row opens, and no `server_restarted` event fires.
- That makes `deferRestart`'s comment true: a never-live image service restarted during its first deploy is refused too, not deployed twice.
- Neighbors stay as they are: a suspended service is still `409 … is suspended` (validated first), a cron job is still `400`, an unknown id is still `404`, and a live image service still restarts its retained release.
- The dashboard's Restart dialog says "restarts on the commit or image it is running now". Check whether it offers Restart for a never-live image service, and if it does, show the same refusal reason the way it does for repo services.

## Blast radius

One verb, `deploys.Service.Restart`, behind four surfaces (REST, GraphQL `restartServer`, MCP `restart_service`, dashboard). Affected types: image-backed web, private and worker services, and any service with an empty `spec.repo` (for example a build-source-linked one). Static sites and repo-backed services already refuse. `platform_rebuild.go:162` calls `liveCommit` on its own path and is unaffected.

## Acceptance

- In `bex-canary`, create a free image web service on a missing tag (first deploy `update_failed`). `bex restart <srv> --confirm` exits 1 with the 409 "has no live deploy to restart; deploy it first". `deploys list` shows only the first deploy, and events show no `server_restarted`.
- After `bex services update <srv> --image docker.io/library/nginx:1.27.0-alpine`, `bex restart` is still refused, and the URL keeps answering its unavailable response until `bex deploys create` deploys the saved image.
- Controls: a live free image service's `bex restart` still answers "restarted successfully" with a new instance on the same image. The repo-backed no-live 409 and the suspended 409 are unchanged.
- Tests in `lego/backend/internal/deploys` cover image no-live (idle and with the first deploy in flight) → 409 with no deploy row, plus the live-image control. GraphQL and MCP restart tests cover the same refusal.
- ADR018's Restart row says a service with nothing live is refused on every source type. w1/m179's amendment is corrected in that row.

## Fix (2026-11-21, `/loopx w8`, commit `39e6a2f1c9`)

- Triage: the premise held on main `83af88283e`. `restartNow` (`lego/backend/internal/deploys/service.go`) called `liveCommit` only `if a.Spec.Repo != ""`, and `TestRestartImageBackedKeepsItsImage` pinned the bug ("needs no prior live deploy").
- Render: the pinned `restart-service` operation (`lego/backend/internal/api/openapi/render-public-api-1.json`) lists 200, 400, 401, 403, 404, 406, 410, 429, 500 and 503, and no status for a service with nothing deployed (nor 409, which the suspended refusal already answers). [render.com/docs/deploys](https://render.com/docs/deploys#restarting-a-service) (read 2026-11-21) says a restart "Deploys the same commit that's currently deployed" and does not say what happens with nothing deployed. So the status is bex's existing repo-backed refusal, now on every source type: `409` `conflict: service "<id>" has no live deploy to restart; deploy it first`.
- Code: `restartNow` asks `liveCommit` for every service before the fallback trigger, and pins the commit only for a repo-backed one. A live image service still restarts its retained release (`restartSelectedRelease`), and a legacy live row with no resolved image keeps the image fallback. `deferRestart`'s comment ("never been live, which Restart's own refusal covers") is now true for image services as well.
- Surfaces: REST `/restart` and MCP `restart_service` reach the verb through `apps.Service.RestartDeploy` (`internal/api/server.go`), GraphQL `restartServer` calls it directly, and the dashboard's two Restart actions call `restartServer` and toast the server's refusal (`use-trigger-deploy.ts`), as they do for a repo service. No dashboard change was needed.
- Tests: `TestRestartImageBackedWithoutALiveDeployIsRefused` (first deploy failed, in flight on the Wait-policy store, canceled, with a saved image change) asserts the 409 on the verb and on `restartServer`, an unchanged App and no new deploy row. It failed with the fix reverted. `TestRestartImageBackedKeepsItsImage` is now the legacy live control, and `apps` `TestRestartRunsTheWiredDeployVerb` asserts REST 409 and the MCP tool error relay the refusal. The real-DB `api`, `apps`, `deploys`, `events` and `webhooks` suites passed.
- Siblings: Rollback refuses a target that never went live for every source (`service.go` "never went live — nothing to roll back to"). Suspend, Resume and Scale carry no `spec.repo` gate. `platform_rebuild.go` filters to repo services and calls `liveCommit`. `rollout.ServedArtifact` deploys the saved image of a never-live image service, but it serves "Save and deploy", a deploy and not a restart. No sibling shares the bug, and none was filed.
- ADR018's Restart row has a "Nothing live (w8/379)" clause that corrects w1/m179's amendment.
- Left: the production acceptance above, once the pin carries `39e6a2f1c9`.

## Second fix (2026-11-21, `/loopx w8`, commit `1ca652656c`)

- `deploys.Service.Restart` authorizes under `core.WithDeferredAllowedWriteAudit` and records `core.AuditVerbDeploysRestart` through `RecordAppConfigChanged` once the restart is accepted, whether it runs now or is queued behind a deploy in flight. The deferred-deploy worker's later run of a queued restart records no second row. A denial is still recorded at authorization. The store-less `apps.Restart` does the same with `core.AuditVerbAppsRestart` and authorizes once.
- Tests: `TestRestartRecordsServerRestartedOnlyWhenAccepted` (deploys: refused for an image service and a repo service with nothing live, a cron job and a suspended service, no row; accepted now, one row on `service:srv-1`; queued, one row, still one after it runs) and `TestStorelessRestartRecordsServerRestartedOnlyWhenItRuns` (apps). Both failed with the fix reverted. `api`, `apps`, `audit`, `core`, `deploys`, `events` and `webhooks` passed, and `make lint` reported 0 issues.
- ADR018's Restart row ("Trigger identity") says when `server_restarted` fires.
