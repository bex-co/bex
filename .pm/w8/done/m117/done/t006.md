## Fix for the 2026-10-28 replay — 2026-10-29 (`/loopx w8`)

The replay used a saved-image service (`python:3.12-alpine`). The shipped fix only named a survivor for repo-backed services, and a saved-image release is never pinned: B's request replaced A's release at once, so canceling B settled below both and A closed "Canceled along with B".

- `deploys.cancelSurvivor` now names the older deploy for a saved-image service too, on the same terms (neither deploy selected an image of its own; the pending one brought only a trigger). `CancelRelease` leaves `spec.buildCommit` alone for an image service.
- Operator: `survivorInFlight` holds for a saved-image survivor until it serves, and `redispatchSurvivor` makes it the release in flight again under its own generation, so A's row is adopted and reaches its own terminal state.
- Reconciler: `awaitingSurvivor` keeps the survivor's row open (within its gate timeout) while the reported release is still the canceled one, instead of closing it as superseded.
- Tests: envtest "a new image service's first deploy rolls out and serves after its duplicate is canceled" (fails without the operator change) and "…names no survivor still settles below both releases"; `TestASavedImageSurvivorsRowWaitsForItsRelease` (fails without the reconciler guard); `TestCancelOfThePendingDeployLeavesTheOlderOneRunning` now expects the image survivor and still refuses one behind an `--image` deploy.
- Limit: the redispatch rolls the saved spec. A settings edit saved between A and B without its own deploy would ride with A; repo-backed services keep their recorded per-release view.
