## Objective

Pin down exactly why canceling the newer of two open deploys strands the older row, and choose the smallest fix that makes the surviving open deploy dispatch again.

## Context

- Live repro (sweeps 52–53, 2026-10-18): create service (deploy A open) → `deploys create` (deploy B) → `deploys cancel B` → A stuck in `created` (sweep 52, ~9.5m) / `queued` with untouched `updatedAt` (sweep 53, 13m+); same-shape control builds in ~80s. Third repro sweep 61 same day: A `dep-dba9hijc1vqc73a2072g` queued, `updatedAt` frozen at cancel time (10:00:52Z) for 5m+.
- `lego/backend/internal/deploys/service.go:898` `Cancel` → `store.CancelRelease(ctx, client, app, d.Generation, …)` then CAS `CloseDeploy`.
- `lego/backend/internal/store/release_cancel.go:63` `CancelRelease`: stamps `AnnotationCanceledReleaseGeneration` = canceled row's generation; operator `settleCanceledRelease` settles the App (last served or `PhaseCanceled`) and rewinds the release generation.
- `lego/backend/internal/store/reconciler.go:1478` `supersededDeployStatus`: generations are monotonic — a row whose generation no longer matches the CR's release can never be adopted; the queued-ahead `OverlapPending` carve-out (line 1514) covers a row ahead of the reported release, not a row behind a canceled newer release. Suspected mechanism: B's generation superseded A's at trigger time, B's cancel settles/rewinds the operator release, and nothing re-dispatches A — it waits for the gate-timeout fallback (~35m, `reconciler.go:90` area) and closes without ever building.
- Questions to answer: what is `status.releaseGeneration` vs A's/B's generations at each step; does `settleCanceledRelease` rewind below A's generation or to B's; is A `OverlapPending`; which component is responsible for re-adopting A (operator release decision vs store reconciler); is the right fix in Cancel (don't stamp/settle when an older open row remains), in the operator's canceled branch (fall back to the older pending release), or in the reconciler (close A promptly and surface a fresh dispatch)?

Done 2026-10-18 (loopx w8): the mechanism. Deploy B is created `queued`/`overlap_pending` behind A (`store.prepareDeployCreate`, `lego/backend/internal/store/store.go:2088`). The operator pins A, which is `PhaseBuilding` (its build is queued or waiting on the registry credential), and holds B in `PendingReleaseGeneration` (ADR060 §D1a). Cancel(B) stamps `canceled-release-generation=B`, so `canceledReleaseIsLatest` is true and the canceled branch of `prepareAppReleaseDecision` (`lego/operator/internal/controller/release_identity.go:400`) rewinds `status.releaseGeneration` to the last served generation (0 for a new service). That abandons A's build, `settleCanceledRelease` (`app_controller.go:706`) reports `PhaseCanceled`, and A's row matches no live evidence in `supersededDeployStatus` (`lego/backend/internal/store/reconciler.go:1500`), so it stays open until the gate timeout. Fix locus: both sides. bex-api knows which deploy rows are open, so it names the release the cancel leaves running. The operator keeps that release pinned. The store reconciler closes any older row the cancel settled below.
