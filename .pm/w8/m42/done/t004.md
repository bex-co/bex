## Objective

The existing detector for a persistently red workflow (`scripts/ci-red-streak.sh`, `.github/workflows/ci-red-streak.yml`, issue #73) did not report the stalled `deploy (bex via Argo)` workflow, which has now failed 5 times in a row. Its open issue listed only `test (mobile)`. Make it see streaks in every workflow, however busy `main` is.

## Root cause (reproduced 2026-09-23, sweep 6)

- `scripts/ci-red-streak.sh:48` runs `gh run list --branch main --limit "$LIMIT"`. That is the newest N runs **across all workflows**. `:28` documents `BEX_CI_RUN_LIMIT` as "runs to fetch per workflow", and the workflow sets it to `100` (`ci-red-streak.yml:36`).
- On this repo, 100 runs span about 5.7 hours. The window before the 2026-09-22T13:28Z scheduled run covered 07:44–13:28Z. Inside it, deploy.yml had **1 failure and 14 supersession cancellations**. Cancellations are skipped, so the streak read as 1. The failures at 00:48, 05:49 and 06:42 were outside the window.
- Replaying that exact window (`gh run list --branch main --limit 100 --created "<2026-09-22T13:28:00Z"` into `BEX_CI_RUNS_JSON`) reproduces the issue text: only `test (mobile)`. Replaying deploy.yml's own history (`gh run list --workflow deploy.yml --branch main --limit 100`) gives `deploy (bex via Argo) — 5 consecutive failures. Last good: 8f07882f6. First failure: ee9652171 (2026-09-22T00:48)`. The streak logic is correct; the input window is wrong.
- The sibling `scripts/ci-schedule-drift.sh:145` (w3/042) already fetches per workflow (`gh run list --workflow "$1" …`). Use the same shape here.

## Steps

1. Enumerate active workflows (`gh workflow list --json id,name,state`) and fetch `--limit $LIMIT` runs per workflow on `main` (push/schedule events). Merge them into the array the existing jq already consumes, so the self-test seam (`BEX_CI_RUNS_JSON`) is unchanged.
2. Add a self-test fixture shaped like this incident: a workflow whose failures are separated by many cancelled runs and by runs of other workflows. It must be reported.
3. Run it read-only against the live repo and confirm deploy.yml is reported while the stall lasts. If the stall is over, use the recorded fixture instead.
