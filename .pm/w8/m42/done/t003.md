## Objective

Run `35709320846` failed the `opensandbox-controller` gate on `[FAIL] Pool scale When reconciling a resource [BeforeEach] should successfully scale out pool buffer size`, with `Timed out after 10.393s` at `.opensandbox-upstream/kubernetes/internal/controller/pool_controller_test.go:91` (35 passed / 1 failed). The job also printed many `tar: … Cannot open: File exists` lines while restoring the Go module cache, which may or may not be related. Explain the timeout and fix it where bex owns the cause.

## Context

- `.github/workflows/opensandbox-controller-test.yml` checks out the pinned upstream into `.opensandbox-upstream/` and runs `make test` (envtest) on `bex-ci`.
- The test code is upstream. A fix there is a bex patch or an upstream report, not an in-place edit of a checkout. Bex owns the runner environment, the cache step, and the pin.

## Steps

1. Read `pool_controller_test.go` around line 91 and find what the BeforeEach `Eventually` waits for (envtest API server start, a controller cache sync, a pod status update).
2. Check whether envtest's control plane or the Go cache restore is competing for CPU and disk with other jobs on the same host. Check whether the `File exists` restore means two jobs are unpacking into one shared module cache concurrently.
3. Fix the cause that bex owns (for example a job-private `GOMODCACHE` or cache key, or envtest asset placement). If the race is in upstream code, carry a minimal patch in the existing bex patch mechanism and file the upstream report.

## Outcome (2026-09-25)

**Root cause: envtest's own control plane stalled under host load; the controller was fine.** In run `35709320846` the Pool controller issued the pool pod `Create` at 09:36:40; the envtest kube-apiserver answered at 09:37:21 with `Failed to create pool pod: Timeout: request did not complete within requested timeout - context deadline exceeded` — 41 s for one write, against the BeforeEach's 10 s `Eventually`. The upstream test and controller did nothing wrong, and there is only one envtest package in the suite (`internal/controller`), so the job did not contend with itself. etcd fsync is ruled out: controller-runtime v0.21 envtest already passes `--unsafe-no-fsync` (`pkg/internal/testing/controlplane/etcd.go:179`). What remains is host-wide CPU/disk starvation on the shared runner VM.

**The `tar … Cannot open: File exists` lines — answered: not concurrent jobs.** `~/go/pkg/mod` persists inside each self-hosted runner container and Go writes module files read-only; setup-go's remote cache restore re-extracted 82,241 files over identical copies (09:26:42 → 09:29:58, 3 min 16 s of disk I/O on the shared host) and then saved the cache again in the post step. Backend and operator gates already disable it for exactly this reason (`docs/runbooks/runner-pool-relabel.md`); this gate was missed.

**Fix (bex-owned):** `cache: false` on this workflow's setup-go. No upstream patch is warranted — the timeout is the apiserver's, not a controller race. The 10 consecutive `bex-ci` runs acceptance item is verified by the milestone closeout (t007) via deploy.yml gate history, not by dispatching ten extra CI runs onto the already-oversubscribed pool.
