# A Free web service can roll back to any earlier deploy; Render limits Free to the two most recent previous deploys

Why: Render lists rollbacks among what a Free web service supports, with one limit: "only to the two most recent previous deploys". bex has no depth rule at all. The other Free limits Render documents (pre-deploy command, private network, SMTP ports, scaling, maintenance mode) are already enforced, so this one is an unrecorded divergence.

**Severity:** minor (bex is more permissive; nothing breaks). **Attribution:** server (backend deploys) and dashboard. **Estimate:** ~60m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `65de`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `7ca0227aa477`, workspace `bex-canary`, QA human device login. The pinned CLI has no rollback command; the rollback is REST with the CLI's token.

## Evidence

A free image service with four deploys, each live in turn:

```text
$ bex services create --name qa-20261111-65de-rb --type web_service --image docker.io/traefik/whoami:v1.10.1 --plan free -o json --confirm
$ bex deploys create <srv> --image docker.io/traefik/whoami:v1.10.2 --wait     # then v1.10.3, v1.10.4

D4 dep-…22o0  live         api    …:v1.10.4
D3 dep-…oi80  deactivated  api    …:v1.10.3
D2 dep-…oi1g  deactivated  api    …:v1.10.2
D1 dep-…21kg  deactivated  other  …:v1.10.1

POST /v1/services/<srv>/rollback {"deployId":"dep-…21kg"}      (D1, the third previous deploy)
→ 201 {"trigger":"rollback","image":{"ref":"docker.io/traefik/whoami@sha256:6956a30c…"}}
```

The rollback deploy went `live` 96 s later on v1.10.1's digest.

What already matches Render, on a git-backed free Node service with a `MARK` variable changed before each deploy: a rollback to the deploy made with `MARK=2` took 50 s with no build, the service answered `mark=2`, the saved variable still read `4`, and `autoDeploy` was unchanged.

## Expected

- [Free instances](https://render.com/docs/free), Free web services, supported features: "Rollbacks (only to the two most recent previous deploys)". The same page: "Upgrading your workspace plan does _not_ remove limitations on Free instances."
- [Rollbacks](https://render.com/docs/rollbacks): "Render retains a fixed number of recent build artifacts for each service, based on your workspace plan." "You can only roll back to a particular deploy if its build artifact is still available."

On a `free` web service, a rollback target must be one of the two most recent deploys that reached live before the current one. An older target is refused with a message that names the Free limit, and no surface offers it.

## Root cause

- `Rollback` (`lego/backend/internal/deploys/service.go:1136`) accepts any deploy id that passes `RollbackEligible` (`actioncaps.go:40`: status `live` or `deactivated`, and an image). Neither looks at the plan or at how far back the target is.
- `ActionCapabilities` scans the newest 20 rows (`eligibilityScanLimit`, `actioncaps.go:110`) and the dashboard offers Rollback on every `deactivated` row (`dashboard/src/features/deploys/lib/deploy-status.ts:47-48`).
- ADR018's Rollback row (`docs/ADR018-render-parity.md:125`) records no Free limit, and w1/m152 t009 left "Build-artifact retention limits on rollback eligibility (Render's per-plan build retention)" out of scope.

## Fix

1. In the shared predicate, for a web service on `plan: free`, accept only the two most recent earlier deploys that reached live. Refuse older ones with a 409 that says a Free web service can roll back to its two most recent previous deploys.
2. Use the same rule in `ActionCapabilities`, GraphQL `rollbackService`, MCP `rollback_deploy` and the dashboard's row action.
3. Record the rule in ADR018's Rollback row.

## Acceptance

- Free service with deploys D1–D4, D4 live: rollback to D3 and to D2 → 201; rollback to D1 → 409 naming the Free limit.
- The dashboard shows Rollback on D3 and D2 only.
- A paid service with the same history can still roll back to D1.
- A static site keeps its own retained-publication rule (w4/m197).

## Unverified

- How Render counts "previous deploys" when the history holds failed, canceled or rollback deploys. The reading above (deploys that reached live) follows bex's own eligibility rule.
- The paid side of the same sentence. The registry keeps the ten newest `live-` tags per repository (`lego/operator/internal/registry/zotconfig.go:57`, w1/m183), while the verb accepts any deploy id and the projection scans 20. A rollback to a built deploy outside the registry's window fails at image pull, and the window turned out to be two previous builds, not ten: filed as w8/266.

## Dedupe

w8/m131 (pre-deploy), w8/m130 (private network) and w8/m127 (SMTP) enforce the other Free limits from the same page. w1/m152 and w5/m107 define what a rollback restores. w1/m183 keeps recent rollback images in the registry. None limits rollback depth. w8/261 is the rollback no-op guard, filed from the same sweep.
