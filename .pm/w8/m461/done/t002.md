## Objective

After `services update --image <ref>` on a native-runtime service, with no command in the same save, the next deploy runs the image's own entrypoint. Today the native Start Command (`node app.js`) becomes the image's `/bin/sh -c` override and the deploy fails with `the startup program "node" does not exist in this image`. A command saved in the same PATCH or later still runs as the Docker Command (w4/m202).

## Context

- `lego/backend/internal/apps/service.go:5163-5175` (`sourceFields.applyTo`) and `resolveSourcePatch` (`:5181`) carry no command change.
- `lego/operator/internal/controller/deployment_projection.go:321` (`shellRunsStartCommand`) runs `spec.StartCommand` for an image source. The native Start Command and the Docker Command share that one field, so the operator cannot tell them apart.
- w4/418: an image service refuses a non-empty build command on update. The switch must not leave one behind either.
- ADR004's w4/m202 paragraph ("A prebuilt image runs its Docker Command whatever build settings it retains") needs a sentence on what a switch does to the native commands.

## Steps

1. Pick the behavior. The default is to clear `buildCommand` and `startCommand` on a native → image switch unless the same PATCH sets a command; a cron's native command follows the same rule. Keep `runtime`, `builder` and `rootDir` for the switch back. Keeping the native commands in a separate retained field so a switch back restores them is the alternative, if it costs no CRD churn. Record the choice in ADR004.
2. Apply it in the one source-switch writer, so REST, GraphQL (dashboard Settings → Source) and MCP `update_service` agree. A same-PATCH command or `dockerCommand` still wins.
3. A Dockerfile (`runtime: docker`) service's `dockerCommand` is already a Docker Command. Decide whether it carries over, and say which in ADR004.

## Acceptance criteria

- [ ] Native Node → `docker.io/jmalloc/echo-server:v0.3.7` with no command: the next deploy is `live` and the URL answers echo-server's body.
- [ ] Native → image with `--start-command '<cmd>'` in the same update: `<cmd>` runs, as w4/m202 requires.
- [x] The switched service holds no build command. A later `--build-command` is refused as on any image service (w4/418).
- [x] ADR004 states what a switch does to the native commands and what a switch back restores.

## Out of scope

## Result (2026-11-17)

Chosen behavior (the task's default, recorded in ADR004 § w8/m461): the one source writer (`sourceFields.applyTo` → `settleSourceSwitch`, `apps/build_strategy.go`) drops, on a switch from a build to a prebuilt image, the build command and a start command the build baked into its image (native, buildpack, a native cron's, a native build source's, and a linked cron's `command`; `checkSourcePatch` reads the carrier, `linksNativeBuildSource`). A Dockerfile build's start command is already its Docker Command and carries over, as does a Docker or image build source's `dockerCommand` (w3/069), as does a cron's explicit `command` override and an image → image switch's command. A command in the same PATCH is written after the source and runs (w4/m202). The dropped commands are not kept: a switch back needs its start command again (the alternative needed a new retained field). The Blueprint switch (w8/m70) applies the same rule to a service that builds itself; a sync does not read a linked service's carrier, so it keeps a linked command. The operator needs no change: `TestPrebuiltImageCommandAfterNativeSourceSwitch` already projects no command for an image with a retained native runtime and no command. Acceptance 1 and 2 are live checks, replayed in t007.
