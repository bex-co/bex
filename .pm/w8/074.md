# Return the declared 201 status for service secret-file upserts

Why: a successful file write returns HTTP 200, so the pinned generated client's typed success result is absent even though the server has applied the change.

**Minor, REST status mapping; estimate 35m.** Filed through /pm from functional CLI QA sweep 36, 2026-10-09 UTC. The native upload/deploy/runtime journey passes; the failing boundary is an API-only write response and its actual pinned decoder. Product code was not edited or shipped.

## Root, correction and acceptance

- `lego/backend/internal/secrets/rest.go:142`: the individual file PUT is registered with `core.HandleJSON(http.StatusOK, ...)`, then returns `SetSecretFile` at 149. This is a route-specific status choice, not a storage or launcher failure.
- Pinned `pkg/client/client_gen.go:49733–49738` defines `AddOrUpdateSecretFileResponse.JSON201`; `ParseAddOrUpdateSecretFileResponse` at 80673–80693 fills it only at status 201. Actual status 200 leaves the typed success field nil with no parse error.
- Change this one service-file upsert route to 201 and preserve the full declared body, including empty contents under [073](073.md). Do not modify the upstream decoder or globally change every PUT route.
- Neighbor contracts: service-file collection replacement is 200; item GET is 200; DELETE is 204. Environment-group file PUT separately declares 200 with an `envGroup` body, so copying the service's 201 rule there would be incorrect. MCP/GraphQL have no HTTP-201 analogue; their existing domain writes need no status change.

- [ ] A nonempty upsert on a disposable CLI-created service returns HTTP 201 with the same name/content, and the actual pinned parser populates `JSON201`. A fresh independent process reproduces the result.
- [ ] Empty-file upsert also returns 201 with `content: ""` and a populated typed result, coordinating with 073's body correction. Verify both adding a filename and updating an existing one.
- [ ] Test the composed REST route and actual generated decoder together; preserve normal 400/404 failure results, collection PUT 200, GET 200 and DELETE 204. Keep GraphQL/MCP writes on their existing shared service logic.
- [ ] Re-run the supported native create → bounded deploy wait → mounted-file checksum/HTTP runtime → exact-ID delete journey. API-only tests must remain labeled separately from native CLI coverage.
