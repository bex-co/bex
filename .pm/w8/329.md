# The activator now ends a waking request with 502 when the woken app takes over 100 seconds to answer; Render allows HTTP responses up to 100 minutes

Why: `0348c50c6` (w21/m394 t012, security finding R25-02, on main 2026-11-14 12:04 UTC, not yet deployed) gave the activator's proxy a `ResponseHeaderTimeout` of 100 s. Its comment reads "Render's 100-second HTTP request timeout".

Render documents the opposite magnitude: "Render web services allow HTTP responses to take up to 100 minutes" ([render.com/docs/render-vs-vercel-comparison](https://render.com/docs/render-vs-vercel-comparison), § "Long-running requests and jobs", fetched 2026-11-14). bex already matches that on every other path:

- w8/207 gives the tenant entrypoints a 6000 s (100 min) read budget;
- sweep `77c3` on 2026-11-14 measured an awake free service answering after 130 s and after 400 s with 200.

Once this ships, the request that wakes a free service gets the 100 s cut-off: the one the activator holds through the cold start and then proxies. If that app takes over 100 s to send its headers, a report, export or AI call that Render would serve becomes the activator's 502.

**Severity:** minor (only the waking request of a free service, and only past 100 s), but it is a parity regression in flight. **Attribution:** activator (`lego/operator/cmd/activator`). **Estimate:** ~15m. **Source:** `/qa-find-bugs-cli` w8 loop, 2026-11-14 12:15 UTC, while reviewing changes due in the next roll; production pin `706a389d5924` does not yet carry it.

## Root cause

- **The constant:** `proxyResponseHeaderTimeout = 100 * time.Second` (`lego/operator/cmd/activator/hold.go:58-60`), used as the proxy transport's `ResponseHeaderTimeout` (`:174`).
- **Where the number came from:** the security finding's validator prototype ("a `ResponseHeaderTimeout` of about 100 s", `.pm/w21/m394/done/t012.md:18`). That figure was taken as Render's request timeout, though Render's documented limit is 100 minutes.
- **What R25-02 needed:** its harm was hold slots pinned through the proxied exchange. The same commit already fixes that by releasing the slot once the wake wait succeeds. The header timeout only bounds a silent exchange's goroutine and connection, which a 100-minute bound also does.

## Fix (target behavior)

- **The value:** set `proxyResponseHeaderTimeout` to Render's 100 minutes (`100 * time.Minute`, the same 6000 s as w8/207's read budget), and correct its comment.
- **Kept:** the slot release before proxying, the 502 for a silent app, and the R25-11 maintenance fallback.
- **A guard:** a test pinning the value to 100 minutes, beside `TestUnansweringAppEndsAtTheResponseHeaderTimeout`, which compares only against the constant itself.

## Regression checks

- **Unit:** the transport's `ResponseHeaderTimeout` is `100 * time.Minute`. The 200 ms override still ends an unanswered exchange as 502, and the slot is still released after the wake.
- **Production, after the activator rolls:**
  1. Create a free `traefik/whoami` web service.
  2. Let it hibernate, or wait for the 15-minute idle window.
  3. `curl https://<svc>.onbex.co/?wait=130s` with a plain client, which is held through the wake.

  The answer should be 200 after about 130 s plus the wake, not 502. Delete the fixture afterwards.

## Dedupe

- **Searched:** `.pm` and `docs` for `ResponseHeaderTimeout`, `100-second` and `Render's 100`.
- **Hits:** only `w21/m394` t012 (done), which introduced the value. ADR018's request-duration row (w8/207) records Render's 100 minutes. No open item covers it.
