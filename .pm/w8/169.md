# A service created with a `PORT` env var reports `port: 3000` / `openPorts: [3000]` in its create response, then its real port on the next read

Why: since w5/m149 a service's own `PORT` variable selects its serving port, and the operator records it as `status.envPort`. The create response is projected before the operator has run, so it reports the platform default instead. The pinned CLI prints that create JSON, so a user who runs `bex services create … --env-var PORT=8085 -o json` is told the service listens on 3000, and Render's required `openPorts` says the same. The next `GET` (a second later) is correct, so scripts that act on the create response see a different service than the one that exists.

**Severity:** minor. **Attribution:** server (create view projection). **Estimate:** 30m. **Source:** `/qa-find-bugs-cli` sweep 1288, 2026-10-21 ([evidence](evidence/cli-sweep1288/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `4b6687b5bc18`, bex-canary, HEAD-built pinned CLI.

| Create | Create response | Immediate `GET /v1/services/{id}` |
| --- | --- | --- |
| `bex services create --type web_service --plan free --image docker.io/ealen/echo-server:0.9.2 --env-var PORT=8085 -o json --confirm` | `serviceDetails.port: 3000`, `openPorts: [{port: 3000, protocol: TCP}]` | `port: 8085`, `openPorts: [{8085/TCP}]` |
| REST `POST /v1/services` with `envVars: [{key: PORT, value: "8086"}]` | `port: 3000`, `openPorts: [3000]` | `port: 8086` |
| `--image redis:7-alpine --env-var PORT=6379` | `port: 3000` | `port: 6379`, `openPorts: [6379]`; the service went live on 6379 |

All fixtures were deleted (204 → 404).

## Expected

The create response describes the service as it will run: `port` and `openPorts` reflect the effective `PORT` from the create body (literal `envVars` and `--env-var`). A `PORT` that can only come from a linked env group may stay `3000` until the operator resolves it, since the create request cannot know it yet. Render's create response carries `openPorts` too, and it should not contradict the service's real listener.

## Root cause

w5/m149 (`65e0b19b5`): `App.ServingPort()` prefers `status.envPort`, which the operator writes after it resolves `PORT` in Kubernetes precedence (`env_port.go`). The create path builds its view from the freshly written App, which has no status yet, so `ServingPort()` falls back to `spec.port` or `DefaultPort` (3000).

## Fix

In the create (and env-update) response projection, compute a provisional effective port from the request's literal env using the same `env_port.go` resolver (literal `PORT`, ignoring unusable values). Use it for `port`/`openPorts` until `status.envPort` exists. Alternatively, copy the literal `PORT` into `spec.port` at create when no explicit port is given. Either way, add a create-response test next to m149's acceptance tests.

## Acceptance

- Handler test: a create with literal `PORT=8085` returns `port: 8085` and `openPorts: [{8085, TCP}]`. A create without `PORT` returns the default. A group-provided `PORT` is documented as resolving on the next read.
- Live after deploy: the CLI row above prints 8085 in the create JSON. Delete by ID with a 404 proof.

## Dedupe

w5/m149 (PORT settable; its tests cover reads after reconcile, not the create response). w8/168 (the default port value itself). No other item.
