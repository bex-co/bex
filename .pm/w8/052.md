# 052 — A failed native build reports bex's internal env-decoding wrapper instead of the user's build command and exit code

Why: when a native-runtime build command fails, the failure summary (`==> Build failed: …`, also stored as the deploy's failure reason) is a wall of bex's own shell plumbing. The user's command appears only at the very end, and `exit code: 3` only after it. Render names the command (`==> Running build command '<cmd>'…`) and the failure. `buildFailureMessage`'s own contract says the message must carry "never internals".

Severity: minor (UX; exposes how build env vars are transported, not any secret value). Attribution: operator (`lego/operator/internal/build`, `lego/operator/internal/controller/build_failure.go`).

## Evidence (2026-10-04, `/qa-find-bugs-cli` w8 loop, sweep 7)

Production (`c2febccdd` on main; deployed revision not observed), `bex v0.2.1` (pin Render CLI v2.27.0), workspace `bex-canary`, human device login. Fixture: free web service `qa-20261004-445879-node` (`srv-db1gn479mgqs73896rp0`, deleted). Public repo `https://github.com/bex-co/bex`, root `examples/hello-node`, `--runtime node`.

```text
$ bex services create --type web_service --name qa-20261004-445879-node --repo https://github.com/bex-co/bex --branch main \
    --root-directory examples/hello-node --runtime node --build-command "npm install" --start-command "node main.js" \
    --plan free --env-var MESSAGE=qa7-445879 --auto-deploy=false --confirm -o json
→ live in 123 s; curl → "qa7-445879"                                   # control: native build works
$ bex services update srv-db1gn479mgqs73896rp0 --build-command "echo qa7-build-445879; exit 3" --confirm -o json
$ bex deploys create srv-db1gn479mgqs73896rp0 --wait --confirm -o json
→ exit 1 after 95 s, status build_failed; the previous release keeps serving (200)
$ bex logs -r srv-db1gn479mgqs73896rp0 --type build --start … -o json | jq -r '.message'   # final lines
==> Build failed: build failed in the docker build step:
==> 0.098 qa7-build-445879
==> ------
==> error: failed to solve: process "/bin/bash -c : bex-native-env-rev=1\nwhile IFS= read -r record; do\n  [ -n \"$record\" ] || continue\n  key=${record%%=*}\n  encoded=${record#*=}\n  # The sentinel keeps command substitution from stripping value newlines.\n  value=\"$(printf '%s' \"$encoded\" | base64 -d 2>/dev/null && printf '.')\" || exit 1\n  export \"$key=${value%.}\"\ndone < /run/secrets/render-env\necho qa7-build-445879; exit 3" did not complete successfully: exit code: 3
```

The raw BuildKit lines above it (`#10 [stage-0 4/4] RUN --mount=type=secret,id=render-env,… ["/bin/bash","-c",": bex-native-env-rev=1\nwhile IFS= read …`, `#10 ERROR: process …`) repeat the same script three more times. The same shape is visible in the w4/m163 finding's static-site evidence (`bex-native-env-rev=none`), where it was incidental and not filed.

## Mechanism

- `lego/operator/internal/build/native.go:158-185` `nativeDockerfile` builds a single `RUN … ["/bin/bash","-c", <buildScript>]`. `buildScript` is the env-decoding loop with the user's `BuildCommand` appended, so BuildKit's process string is wrapper plus command.
- `lego/operator/internal/controller/build_failure.go:81-112` `buildFailureMessage` quotes `obs.Tail` (the failing container's captured output) verbatim for tenant faults, so BuildKit's `failed to solve: process "<script>" did not complete successfully: exit code: N` becomes the tenant-facing reason. The function comment requires "never internals".
- Unverified but likely: the same string is the deploy row's failure reason (operator status → `store.TransitionDeploy` `failureReason`), which the dashboard deploy page shows.

## Fix

- Keep the user's command as the only thing BuildKit names. For example, write the decoding loop to a helper in an earlier Dockerfile step (a `COPY --chmod=0755 <<'EOF' /opt/bex/load-env` heredoc, which the `dockerfile:1.7` syntax already allows) and run `RUN --mount=… ["/bin/bash","-c",". /opt/bex/load-env && <BuildCommand>"]`. The `bex-native-env-rev` cache key can move into the helper so cache invalidation (`docs/drills/2026-09-08-native-env-cache.md`) is unchanged. Apply the same treatment to static-site builds and the secret-file mounts (w4/m163).
- In `buildFailureMessage`, for native builds, rewrite BuildKit's `process "…" did not complete successfully: exit code: N` into `build command '<BuildCommand>' exited with code N`, keeping the captured user output above it.
- Optionally narrate `==> Running build command '<cmd>'…` before the RUN step, matching Render's canonical line (`docs/render-artifacts/live-deploy-following.md`).

## Acceptance

- [ ] A native build whose command is `echo marker; exit 3` ends with a summary that names the command and `exit code 3` (or `exited with code 3`), shows `marker`, and contains none of `bex-native-env-rev`, `/run/secrets/render-env`, `base64 -d`, `while IFS= read`.
- [ ] Controls: a passing native build still sees every env var, including values with newlines and `=` (the sentinel case), and secret files at `/etc/secrets/<name>` (w4/m163). Changing an env value still busts the build cache. Dockerfile-runtime failures are unchanged.
- [ ] Operator unit test on `buildFailureMessage` and on the generated Dockerfile.
