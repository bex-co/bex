# 066 — Upstream `psql -c` launches with an empty database target when IP discovery fails

Why: selecting a private Postgres must never send SQL to libpq's local or environment defaults; the imported CLI skips its IP check during an ipify failure and passes an empty external URL to the child.

Severity: major (wrong-target SQL risk; no wrong-database query observed). Attribution: **upstream Render CLI**, not a demonstrated Bex server or launcher regression. Estimate: ~50m to prepare the upstream guard and focused regression patch; upstream acceptance, dependency refresh and distribution are separate prerequisites. Source: `/qa-find-bugs-cli` w8 loop, 2026-10-07, offline sweep 11. Goal: dependable Postgres CLI sessions (ADR008 / ADR009). Filing only; no implementation, external issue submission, commit or release.

## Producer, consumer and ownership

- **Producer is deliberate:** `lego/backend/internal/postgres/service.go:799–866` serves private internal connection metadata and assigns the external string only when `Status.ExternalHost` exists. `service.go:223` keeps the required string key present. `rest.go:248` exposes that result. `TestPrivatePostgresInternalAndPSQLHostsAgree` and `TestConnectionInfoPrivateDatabaseOmitsServerCA` explicitly cover the private shape. Render's pinned `postgresConnectionInfo` schema requires a string, without a nonempty constraint; this response does not establish a schema violation.
- **Pinned consumer:** `pkg/tui/views/psql.go:58–69` checks the allowlist only when `getUserIP` succeeds; `:235–244` returns `ok=false` on an ipify transport/read error. `:70–84` then reads connection-info and constructs `exec.CommandContext` from the unchecked external string. `pkg/postgres/repo.go:79–92` decodes the successful response without a target guard.
- **Shared interactive consumer:** `pkg/tui/views/psql.go:182–218` repeats the same unchecked handoff in `loadDataPSQL`. It is used by `NewPSQLView`; its two command callers are `cmd/psql.go:51` and `cmd/pgcli.go:40`. `cmd/psql.go:103` is the sole noninteractive caller. Interactive psql/pgcli handoffs were reproduced through bounded PTYs as recorded above.
- **Bex trust setup preserves this upstream behavior:** `lego/cli/internal/pgtrust/pgtrust.go:177–180` treats an absent private CA as a no-op. Changing the server's legitimate internal metadata, inventing an external endpoint or substituting the internal URL would not repair the consumer correctly.

The expected refusal follows the selected-resource contract. Render documents that external access can be disabled while internal access remains available; disabling access does not authorize a different database target. [Render connection/access documentation](https://render.com/docs/postgresql-creating-connecting). PostgreSQL documents that empty/unset connection parameters use environment and built-in defaults. Passing this empty target can therefore redirect SQL to a separately configured reachable database; that consequence is an inference from the verified child argv and documented libpq behavior, not an observed wrong-database execution. [PostgreSQL libpq connection defaults](https://www.postgresql.org/docs/current/libpq-connect.html), [psql connection parameters](https://www.postgresql.org/docs/current/app-psql.html).

Read-only inspection of the published [Render v2.28.0 consumer](https://raw.githubusercontent.com/render-oss/cli/v2.28.0/pkg/tui/views/psql.go) on 2026-10-07 shows the same missing guard; it was not executed and does not replace the v2.27.0 oracle. A plain bump to that version is not a demonstrated fix. A later read of the [public upstream issue index](https://github.com/render-oss/cli/issues) showed eleven open titles, none matching this symptom. Filtered/closed searches and the API index remained inaccessible, so full upstream issue dedupe remains required before submission; no upstream issue was created.

## Proposed work and acceptance

Two bounded work units fit this inbox note: **upstream guard and focused regression patch (~30m)**, then a **separate shared-consumer verification task (~20m)** covering noninteractive psql, interactive psql and pgcli. Adoption, full repository pin-refresh checks and distribution wait on an available upstream fix and are outside this preparation estimate.

Prepare a focused **upstream** patch at `render-oss/cli/pkg/tui/views/psql.go`: after successful connection-info decoding, reject an empty/whitespace external target before constructing either child command, with an actionable external-access-unavailable message naming the selected resource but exposing no credentials. Preserve upstream IP-discovery fallback for usable targets. Add behavioral regression coverage in upstream `pkg/tui/views/psql_test.go` for both command constructors. Do not fork the dependency, mutate generated client code, add a Bex request rewrite or weaken TLS. Coordinate adoption through the repository's documented pin-refresh workflow once an upstream fix is available; no speculative version is named here.

- Re-run the exact command above with healthy and failed IP discovery: the private/empty-target case exits nonzero and never invokes the stub; JSON/text output remains truthful. Include whitespace and missing-key decode neighbors.
- Both shared interactive paths reject unusable external targets before launching `psql` or `pgcli`; verify with bounded PTYs and owned stubs. A documented non-TTY guard is not sufficient acceptance.
- Public nonempty target controls, passthrough arguments, ordinary IP refusal, child exit propagation and Bex CA provision/removal still work. Keep 401/403/404/503 responses as errors with no child, no existence leaks and no connection-string output.
- Preserve the REST/GraphQL connection-info private shape and internal use. MCP has no new connection-info surface to invent. No dashboard or operator change is proposed.
