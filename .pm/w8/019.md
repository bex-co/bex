# 019 — `blueprints validate` stops at the first semantic error, drops its line/column, and leaks an inner `bad request:`

Why: ADR049 promises that validation "reports every independently actionable error it can safely discover", each with "source line/column when known". Past the schema stage, bex reports one error per round trip with no location, so an author fixes a Blueprint one failed validate at a time.

Live, 2026-09-23, production `api.bex.co`, released `bex v0.2.1` (pin v2.27.0), human device-login auth, workspace `bex-canary`, `-o json`. Found by the `/qa-find-bugs-cli` sweep 5.

```text
$ cat two.yaml                       # two independent errors, same kind
services:
  - type: worker
    name: qa5-wrk
    runtime: image
    image: { url: docker.io/library/busybox:1.36 }
    plan: free                       # line 7
  - type: worker
    name: qa5-wrk2
    runtime: image
    image: { url: docker.io/library/busybox:1.36 }
    plan: free                       # line 13
$ bex blueprints validate two.yaml -o json      # exit 1
{ "errors": [ { "error": "service \"qa5-wrk\": bad request: a background_worker requires a paid plan; plan must be one of starter|standard|pro|pro_plus|pro_max|pro_ultra",
                "path": "services[0].plan" } ],
  "valid": false }
```

- Only `qa5-wrk` is reported. `qa5-wrk2` has the same independent error and appears only after the first one is fixed.
- The entry has no `line`/`column`, although the IR knows exactly where `plan` is.
- `bad request:` shows up in the middle of the message.

A second shape: a web service with `envVars: [{key: PORT}]` plus a free worker in the same file returns only the `PORT` reserved-variable error. Control: schema-stage problems **are** aggregated with locations. A file with an unknown `bogusField` and an invalid `plan` returns both errors, with `line`/`column`/`path`.

## Mechanism

- `lego/backend/internal/apps/blueprint.go:638-640` returns the compiler's `problems` all together, with locations. After that, `parseCompiledStack` (`:642`), `resolveBlueprintRegistryCredentials` (`:644`) and `validateBlueprintServices` (`:647`) each return a single `error`, and `:691-698` wraps it into a one-entry `Errors` list.
- `lego/backend/internal/apps/deploy.go:1308-1319` `validateBlueprintServices` returns on the first failing service (`return fmt.Errorf("service %q: %w", …)`).
- `blueprint.go:1733` `blueprintValidationError` sets `Line` only when the message text contains `line N` (`yamlLineRE`, `:1729`). It guesses `Path` by substring-matching resource and field names. It never reads `BlueprintField.Location` (`blueprint_ir.go:42-46`), which holds the exact line/column.
- `blueprint.go:694-697` strips `bad request: ` only as a **prefix**. The service wrap puts it after `service "…": `, so it reaches the user.

## Fix

1. Make `validateBlueprintServices` (and the per-resource parts of `parseCompiledStack`, where a resource's error does not invalidate later ones) collect one error per resource instead of returning the first. Keep fail-fast where a later check depends on an earlier result.
2. Carry the failing field's key with each error and fill `Line`/`Column` from `ir.Resources[i].Fields[key].Location`, falling back to the resource's own location. Replace the substring path guess where the field is known.
3. Strip the `core.ErrBadRequest` sentinel text wherever it appears (or build the message without it) so no validation entry contains `bad request:`.

**Blast radius:** `blueprintValidationFor` backs REST `POST /v1/blueprints/validate` (`rest.go:1280`), GraphQL `validateBlueprint`/`previewBlueprint` (`graphql.go:1193,1230`), MCP validate/preview (`mcp.go:1010,1018`), and the dashboard's create review and pre-sync dialog through `PreviewBlueprint` (`blueprint.go:784`). All of them gain the extra entries. The apply path (`DeployStack`) is out of scope and keeps its own fail-closed preflight.

## Acceptance

- [ ] `bex blueprints validate two.yaml -o json` returns **two** entries (`services[0].plan`, `services[1].plan`) with `line` 7 and 13 respectively, a column on each, and neither message containing `bad request:`. Exit 1.
- [ ] A PORT-plus-free-worker file returns both errors.
- [ ] Controls: the schema-stage aggregate (`bogusField` + bad `plan`) is unchanged, and a valid file still returns `valid: true` with its plan.

## More evidence (sweep 8, 2026-09-23): the other two validation stages behave the same way

```text
# a.yaml: a web service in projects/environments with envVars fromDatabase {name: qa8-db-missing} + fromGroup: qa8-group-missing
$ bex blueprints validate a.yaml -o json          # exit 1
{ "errors": [ { "error": "fromDatabase references unknown database \"qa8-db-missing\" in this workspace" } ], "valid": false }
# → no path, line or column at all, although the IR knows the envVars entry's location

# b.yaml: duplicate service name "dup" + a cron with schedule "61 * * * *"
$ bex blueprints validate b.yaml -o json          # exit 1
{ "errors": [ { "column": 5, "line": 7, "path": "services[1]", "error": "duplicate name \"dup\" for service (first declared at #/services/0)" } ], "valid": false }
# → the invalid cron schedule is never reported: a compiler-stage problem ends validation before the semantic stage runs
```

- `blueprint_ownership.go:555-577` `validateWorkspaceReferences` also returns a single entry built by `blueprintValidationError(ir, msg)`, so it gets the same message-text path guess (no match here) and no location. Include it in fix steps 1–2.
- The compiler-then-semantic ordering (`blueprint.go:638-641`) is correct for problems that make the IR unusable. A duplicate name elsewhere in the file does not make an unrelated service's `schedule` unvalidatable. When the IR is still well-formed, consider running the semantic stage per resource on resources the compiler did not flag. That judgment belongs to whoever implements this; the ADR049 sentence "every independently actionable error it can safely discover" is the bar.
- `fromGroup` to a missing group is deliberately not checked at validate (`blueprint.go:658-663` comment: the check needs `can_view_sensitive`). This is not part of this note.
- Extra acceptance: `a.yaml` gets `path`/`line` for its `fromDatabase` entry, and `b.yaml` reports the schedule error beside the duplicate name (or the note records why that cannot safely be done).
