# A request that arrives while a sleeping free service is already waking gets an immediate 503 tagged `no-server`: it is neither held through the cold start nor tagged `hibernate-pending-wake`

Why: Render holds a non-browser request to a spun-down free service until it is up, then serves the app's response; a browser gets the loading page tagged `X-Render-Routing: hibernate-pending-wake` (`docs/render-artifacts/wake-interstitial.md`, w8/178). bex does this only for the request that **finds** the App `Hibernated`. Once that first request starts the wake, the phase is no longer `Hibernated`, and the activator treats any further request during the cold start as an awake-but-unready App: an immediate 503 tagged `no-server`. A webhook or API client that retries during a wake someone else started is told "no server exists", and its request is dropped.

Severity: **minor** (the window is the ~30–60 s cold start; the first request is handled correctly). Attribution: operator (`lego/operator/cmd/activator`). Estimate: ~45m. Source: `/qa-find-bugs-cli` loop sweep 3093, 2026-10-29 03:37 UTC, during the w8/213 hosted acceptance. Context: platform pin `c9ccd73df050`; `https://api.bex.co/v1/`; workspace `bex-canary`.

## Evidence

```text
qa-20261029-3093-route2 (srv-dbhbkr2pmogc73fr0bgg, python:3.12-alpine http.server, Free), phase Hibernated at 03:37:07Z
1) curl -H 'Accept: text/html' https://…/        → 503 · retry-after: 5 · x-render-routing: hibernate-pending-wake   (starts the wake; correct)
2) ~1 s later: curl -H 'Accept: application/json' https://…/
                                                 → 503 · retry-after: 5 · x-render-routing: no-server   (immediately; not held)
3) 30 s later: curl -I https://…/                → 200, untagged
```

Render's captured behavior for (2) is a request held through the cold start that returns the application's 200 (`wake-interstitial.md` § API-client capture). The fixture was deleted by ID (`GET` 404).

## Root cause

`lego/operator/cmd/activator/main.go` (~`:243`): `routing := routingNoServer; if app.Status.Phase == PhaseHibernated { routing = routingWake }`. The hold decision `hold.holding(app, key)` (`hold.go` ~`:183`) is true while `Phase == Hibernated` **or** while this process's own `waking[key]` entry is live, but the routing tag consults only the phase. Either:

- the second request reached a different activator replica, whose `waking` map has no entry (the map is per process), so it was neither held nor tagged as a wake; or
- the HTML first request does not `markWaking`, because only holdable (non-HTML) requests do.

In both cases, the phase read from the informer cache has already moved past `Hibernated`.

## Fix

- Treat "a wake is in flight" as a shared fact rather than per-process memory. For example, derive it from the App: `spec` has replicas 1 after the wake patch while `status` has no ready endpoint, or the `app.bex.co/last-active` stamp is recent and no endpoint is ready. Use that predicate for **both** the hold decision and the routing tag (`hibernate-pending-wake`).
- Mark the wake in flight from the HTML path too, so a JSON request after a browser's request is held.
- A regression test: a wake started by an HTML request, followed by a JSON request (on a fresh activator instance, to model a second replica), yields a held request served with the app's response; an HTML follow-up gets the wake page tagged `hibernate-pending-wake`, never `no-server`.

## Acceptance (live)

- Hibernated Free fixture: an `Accept: text/html` request, then within 2 s an `Accept: application/json` request. The JSON request is held and returns the app's 200 (or, past the hold bound, the bounded error tagged `hibernate-pending-wake`). No response during the wake is tagged `no-server`. Repeat with JSON first, then HTML. Delete the fixture by ID with a 404 proof.

## Dedupe

- w8/178 (done) implemented the hold for the first non-browser request; its tests cover "concurrent holds share one wake" within one process. w8/213 (done) added the tags and deliberately tags an *awake* unready App `no-server`. Neither covers a request that arrives after another request already started the wake, or one that lands on another replica.
