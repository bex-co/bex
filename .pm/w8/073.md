# Preserve empty secret-file content in item and replace-all responses

Why: a valid zero-byte file returns an incomplete API object, so consumers cannot rely on the declared `content` field or distinguish the item response from a names-only listing.

**Minor, server serialization; estimate 55m.** Filed through /pm from functional CLI QA sweeps 33 and 36, 2026-10-09 UTC. The native CLI upload, deployment and mounted bytes pass; this is an API response contract finding, not a demonstrated CLI read-command failure. Product code was not edited or shipped.

## Reproduction and contract

Published Bex v0.3.2, Render pin v2.27.0 / `a764810a768202704e7206eb7b87a47211fcd98e`, module `v1.1.3-0.20260909214233-a764810a7682`. Production `https://api.bex.co`, isolated human QA grant, workspace `tea-daif693dqjvc73e7as3g`. Source HEAD `4e8fbac848c57a24f4d6d6a93ee512bb3b40f9fe`; actual deployed revision unobserved. [Complete sanitized create, API, log and runtime evidence](evidence/073/repro.json).

Two fresh native CLI creates uploaded an empty file and a generated nonempty UTF-8 control to disposable free image web services. The second was `qa-20261009-bb245a-empty` / `srv-db4bvtgec12s73fjue4g`; its create exits 0 in 0.951s. Use the supported journey:

```sh
bex services create --name qa-YYYYMMDD-NONCE-empty \
  --type web_service --runtime image \
  --image docker.io/mendhak/http-https-echo:35 --env-var HTTP_PORT=3000 \
  --secret-file qa-empty.txt:<EMPTY_FILE> \
  --secret-file qa-text.txt:<GENERATED_QA_TEXT_FILE> \
  --pre-deploy-command 'sha256sum /etc/secrets/qa-empty.txt /etc/secrets/qa-text.txt' \
  --health-check-path / --region frankfurt --plan free --auto-deploy=false \
  --max-shutdown-delay 11 --confirm -o json
```

The following are **API-only diagnoses** using the same grant/workspace and the actual CLI User-Agent, not invented CLI subcommands. Each GET ran in a fresh process.

```text
GET /v1/services/{owned-id}/secret-files/qa-empty.txt
200 {"name":"qa-empty.txt"}                       # content is absent

GET /v1/services/{owned-id}/secret-files/qa-text.txt
200 {"name":"qa-text.txt","content":"qa-bb245a\n"} # valid control

GET /v1/services/{owned-id}/secret-files/qa-missing.txt
404 {"code":"NOT_FOUND","error":"secret file not found","id":"not_found",
     "message":"secret file not found","params":null}

PUT /v1/services/{owned-id}/secret-files
[{"name":"qa-empty.txt","content":""},{"name":"qa-text.txt","content":"qa-bb245a\n"}]
200 [{"secretFile":{"name":"qa-empty.txt"},"cursor":"qa-empty.txt"},
     {"secretFile":{"name":"qa-text.txt","content":"qa-bb245a\n"},"cursor":"qa-text.txt"}]
```

Single-file empty PUT also omits `content`, and the following fresh GET repeats the omission. Its separate wrong status is [074](074.md); do not claim that its actual HTTP 200 is the declared success response.

The pinned `secretFile` schema in `lego/backend/internal/api/openapi/render-public-api-1.json` requires both `name` and `content` as strings. `retrieve-secret-file` declares it at HTTP 200; `update-secret-files-for-service` declares an array of `secretFileWithCursor`, whose nested file uses that schema. The required-property check fails only on the empty item's `content`. The declared list divergence is limited to `list-secret-files-for-service` (`conformance_allowlist_test.go:108–111`); it does not cover these item or replace-all responses.

## Root and affected consumers

- `lego/backend/internal/secrets/files.go:47–54`: `SecretFileView.Content` is `string` with `json:"content,omitempty"`, shared by names-only lists and content-bearing results. `GetSecretFile` at 95–113 finds the existing entry and correctly returns its empty string; JSON serialization then removes the field. `SetSecretFile` at 160 and `SetSecretFiles` at 202–206 return the same view.
- `secrets/rest.go:128–140,149`: bulk replacement wraps those views with `toSecretFileList`; individual GET/PUT return them directly. Three REST operations expose content-bearing results. The collection GET intentionally omits contents.
- Callers: `GetSecretFile` has three production consumers (REST, MCP, `SecretFileContent`); `SetSecretFile` has three (REST, MCP, GraphQL mutation); `SetSecretFiles` has one (REST). MCP item tools are `get_secret_file` and `set_secret_file` at `secrets/mcp.go:180–190`. Check their serialized output separately; it was not exercised live.
- GraphQL goes through `SecretFileContent` (`files.go:665–670`) into explicit string resolvers (`apps/graphql.go:839–845`). The actual GraphQL control returns `secretFile: {"name":"qa-empty.txt","content":""}` correctly.
- The actual same-pin generated GET decoder (`pkg/client/client_gen.go:80557`) accepts an omitted string as Go's zero value; [decoder control](evidence/074/probe-result.txt) confirms this. No native CLI secret-file reader exists. This report claims the declared wire-shape violation, not a Go decoder error or data loss.

## Correction and acceptance

Use a presence-aware response representation for item and replacement results that emits `content: ""`; keep metadata lists distinct. Do not globally remove `omitempty` from a shared list DTO or change input omission semantics. Coordinate the single-file result with 074's HTTP 201 correction.

- [ ] On a fresh CLI-created free fixture, individual GET of an existing empty file returns HTTP 200 with `{"name":"qa-empty.txt","content":""}`; nonempty bytes are unchanged and a missing filename remains 404.
- [ ] Replace-all PUT containing empty and nonempty files returns HTTP 200 with `content` present for both nested files and conforms to its pinned response schema. The mounted checksums and actual HTTP runtime still pass after a native `deploys create <id> --wait --confirm -o json`.
- [ ] The individual PUT response body preserves the empty string; its success status and generated decoder are tested under 074.
- [ ] Collection GET and metadata-only GraphQL/MCP lists keep their current names-only behavior. MCP item results preserve explicit empty content; GraphQL's already-passing content read remains unchanged. Cover actual adapter serialization, not just domain string equality.
- [ ] Inspect the independently declared `envgroups.SecretFileView` and callers before choosing a shared change. Its empty-item read is a source lead, not live coverage here; group write responses have different documented masking/response semantics and are outside this finding's confirmed fix scope.

## Implementation (2026-10-09) — live verification pending

Shipped the server fix. `SecretFileView.content` no longer has `omitempty`, so the item GET/PUT, replace-all PUT and MCP `get_secret_file`/`set_secret_file` emit `content: ""`. Lists now use a distinct names-only `SecretFileName` (REST collection GET, GraphQL `secretFiles`, MCP `list_secret_files`), so contents still cannot leak into a list by construction. Input decoding is unchanged.

Regressions: `TestREST_EmptySecretFileKeepsContent` checks exact bodies for item PUT/GET, replace-all with empty plus nonempty files, the names-only list and a missing file → 404. `TestMCP_SecretFiles` checks raw `content: ""` and a names-only list. Both fail with `omitempty` restored.

`envgroups.SecretFileView` was inspected and left unchanged. Its item GET carries the same `omitempty` (a source lead, not live-confirmed), and its PUT deliberately masks content, so it falls outside this note's scope.

Remaining: a live production check after deploy (fresh fixture, empty item GET, replace-all body). This note closes once that check passes.
