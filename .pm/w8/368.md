# A mistyped subcommand of `bex agent`, `bex code` or `bex s3 keys` prints help and exits 0, where `bex s3` and the docs say a usage error exits 2

Why: `docs/bex-cli.md` gives `bex agent` exit `2` for a usage error (its exit-code table) and says `bex s3` follows `bex agent` here, refusing "an unknown action" with `2`. But `bex agent wiat ags-…` in a CI step prints the group's help on stdout and exits 0, so a typo looks like success. `bex s3 frob` already exits 2, and so do `bex s3 cors frob` and `bex s3 lifecycle frob`. bex owns these commands, so they should behave the same way.

- Severity: minor. Nothing is mutated. The cost is silent false success in scripts and CI, which is where `bex agent` is meant to run.
- Versions: bex CLI v0.9.0 release binary (Render CLI pin `4fd34231b637`, v2.36.0). The launcher code is unchanged on main at `1c93effaf`. Production pin: not relevant, since this is launcher-only.
- Context: 2026-11-21 07:05 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY, stdin `/dev/null`. Routine `cli-qa`, nonce `0436b6`. No resource was created.

`bex agent show ags-d0000000000000000000` (there is no `show`) exits 0 with help, while `bex agent get` with the same id exits 1 with the API's refusal.

## Root cause

- cobra v1.10.2's `legacyArgs` (`args.go:28`) refuses an unknown word only on the **root** command (`!cmd.HasParent()`).
- A nested group with no `Args` validator takes the word as an argument. If the group has no `RunE`, `execute` returns `flag.ErrHelp` (`command.go:955`), which `ExecuteC` turns into printed help and a nil error, so the exit is 0. If the group has a `RunE`, that runs and ignores the word.
- `bex s3` avoids this with an explicit `Args`: `s3.go:126` (`usageError`, exit 2), and `subcommandArgs` (`internal/s3/config.go:184`) on `cors` and `lifecycle`.
- These groups have no such validator:
  - `internal/agent/agent.go:126`, the root (`agent`/`agents`), with no `Args` and no `RunE`;
  - `internal/agent/config.go:115` (`secrets`) and `:230` (`skills`);
  - `internal/agent/automations.go:122` (`automations`);
  - `internal/code/code.go:66` (`code`) and `:81` (`keys`), which have a `RunE` that prints status;
  - `internal/s3/tools.go:159` (`s3 keys`).

## Fix

- Give every bex-native group an `Args` validator. With no argument, it keeps today's behavior: help, or `bex code`'s status, with exit 0. A word that is not a subcommand gets `unknown command %q for %q` plus cobra's suggestions (`c.SuggestionsFor`, so `wiat` suggests `wait`) and exit 2 through `command.NewExitError(exitUsage, …)`, in the way `bex s3` does it.
- Simplest: one shared helper applied to each group above. Alternative: a walk at launcher setup that sets it on every bex-native command that has subcommands and no `Args`, so a new group cannot regress.
- Leave the imported Render groups alone: `workspace`, `services`, `deploys`, `sandboxes` and others exit 0 on an unknown word in the pinned upstream CLI too. That is upstream behavior and the launcher must not fork it.

## Sibling: cobra's own argument checks exit 1

The same docs promise exit 2 for a wrong command line, but cobra's built-in validators return a plain error, so the launcher exits 1:

- `bex agent env frob` (`cobra.NoArgs`, `internal/agent/config.go:402`) exits 1 with `unknown command "frob" for "bex agent env"`.
- `bex s3 mb` and `bex s3 mb a b c` (`cobra.ExactArgs`) exit 1 with `accepts 1 arg(s), received 0` (or `3`). The s3 docs say "A command line that is wrong exits `2`".
- bex's own validators already exit 2: `bex agent get a b c` and `bex agent wait` with no session both do.

`grep -rnE 'cobra\.(NoArgs|ExactArgs|MinimumNArgs|MaximumNArgs|RangeArgs)'` finds 31 call sites across `internal/{agent,s3,code,skills,upgrade}`. Fold them into the same fix: wrap every bex-native command's `Args` so its error becomes `command.NewExitError(exitUsage, err)`.

## Acceptance

- `bex agent wiat ags-x`, `bex agents frob`, `bex agent secrets frob`, `bex agent skills frob`, `bex agent automations frob`, `bex code frob`, `bex code keys frob` and `bex s3 keys frob` each exit 2, with nothing on stdout and `unknown command "<word>" for "bex …"` on stderr. `wiat` also gets a "Did you mean this? wait" line.
- Bare `bex agent`, `bex agent secrets`, `bex s3 keys` and `bex code` still exit 0, with the same output as today.
- A test walks every bex-native command that has subcommands, passes a bogus word, and asserts exit 2 with empty stdout. It fails when a new group lacks the validator.
- `bex agent env frob`, `bex s3 mb` and `bex s3 mb a b c` exit 2 with their current messages.
- `bex workspace frob` is unchanged: it exits 0, as upstream does.
