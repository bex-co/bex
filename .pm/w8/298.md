# A busy Postgres refuses every new connection and reads `config_restart`: under CPU load its pod fails readiness and drops out of the `-rw` Service, though Postgres keeps running

Why: while a small Postgres is CPU-saturated, bex takes it off the network. New connections fail through the external endpoint (`SSL SYSCALL error`) and inside the workspace (`Connection refused` on the `-rw` Service), and the database reads `config_restart`. Postgres itself never restarts, and the queries already running finish normally. Access returns about 10 s after the load ends.

- **One heavy query is enough:** a report, a migration or an index build makes the database unreachable for new connections for as long as the query runs.
- **It can feed on itself:** an app that reconnects and re-runs its startup queries can keep the database flapping. PostgREST did this for about 6 minutes right after its template was imported.

A Postgres server accepts new connections while busy: they are slow, not refused. Render reports `config_restart` for a configuration change, not for load. Render's free and Basic-256MB instances have the same 0.1 CPU as bex's (`free`, `basic-256mb`: `cpu: 100m` in `lego/types/tiers/tiers.yaml`), so the load in the repro below is ordinary for them.

**Severity:** major. A paid `basic-256mb` database is affected the same way, and the outage covers every new connection: app restarts, pool refills and `bex psql`. It also misreports the database as restarting. **Attribution:** platform runtime (CloudNativePG readiness → Service endpoints), plus bex-api's status mapping. **Estimate:** ~2h (probe settings per plan, status mapping, a load test). **Source:** `/qa-find-bugs-cli` w8 loop sweep `7c15`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `33e1b1e6117c`.

## Evidence

**Clean reproduction.** A free PostgreSQL 18 database was created with `bex postgres create --name qa-20261112-7c15-pg --plan free --ip-allow-list cidr=0.0.0.0/0,description=qa -o json --confirm` (`dpg-dbr2r1a585js73afgl40`, deleted afterwards).

A prober recorded `GET /v1/postgres/<id>` `.status` and ran `bex psql <id> --command 'select 1' -o json` through the external endpoint every 9–10 s:

- **Idle baseline:** 21:22–21:36 UTC, 84 samples, all `available`, every `select 1` answered (2.6–8.3 s including the client's container start).
- **Load:** at 21:37:13 three `bex psql <id> --command "set statement_timeout='100s'; select count(*) from generate_series(1,400000000)" -o json` ran in parallel. All three ran their full 100 s and ended with `canceling statement due to statement timeout` at 21:38:56, so their sessions were served throughout.

```text
21:37:08  available       select 1 OK
21:37:17  available       OK          (load started 21:37:13)
21:37:38  available       OK
21:37:48  config_restart  psql: error: connection to server at "dpg-dbr2r1a585js73afgl40.db.bex.co" (<ip>), port 5432 failed: SSL SYSCALL error
…         config_restart  the same error at 21:37:57, 38:06, 38:15, 38:23, 38:32, 38:41, 38:50 (8 of 8)
21:38:59  config_restart  OK          (load ended 21:38:56)
21:39:09  available       OK, and every sample to 21:43:36
```

The database's logs show a single start, at creation. Nothing restarted.

**Where it was found.** The Render template `render-examples/postgrest` was planned and approved with `bex ea blueprints create … --auto-sync=false` and `bex ea blueprints approve` (sweep 7c15, deleted afterwards). It creates a free database with `ipAllowList: 0.0.0.0/0` and a free Docker web service running PostgREST, whose anonymous role is the database user.

- **Timeline:** the database was created at 21:02:47 and logged one start at 21:04:09. The service went live at 21:07:50, and PostgREST started its schema-cache queries.
- **Status samples:** `config_restart` 21:08:10, `available` 21:10:01, `config_restart` 21:11:21, `available` 21:13:11, `config_restart` 21:13:20, then `available` from 21:14:49.
- **PostgREST's view:** it logged `connection to server at "dpg-…-rw.<workspace>" (<ip>), port 5432 failed: Connection refused` with backoff (8, 16, 32 s) until 21:14:49. Then it connected, and its schema cache took 9.2–9.4 s.

## Root cause

Code-verified:

- `lego/operator/internal/controller/database_controller.go:1890`: the Database's readiness comes from CloudNativePG's `status.readyInstances`.
- `lego/backend/internal/core/datastore_status.go:45-55` and `lego/backend/internal/postgres/service.go:529-548` (`dbStatus`): a database that has served before and is not Ready reads `config_restart`.

Inferred (no cluster access here):

- The operator sets no `probes` on the CloudNativePG `Cluster`; nothing under `lego/operator/internal` writes `spec.probes`, so the default readiness probe applies.
- On a 100m-CPU instance whose CPU the backends saturate, the readiness check times out. After its failure threshold (about 30 s; the first failed sample came 35 s into the load), the instance Pod turns NotReady.
- The `-rw` Service then has no ready endpoint. In-workspace clients get `Connection refused`, the external SNI proxy cannot reach a backend (`SSL SYSCALL error` after TLS), and `readyInstances` drops to 0.

Still to confirm on a cluster: the Pod's Ready condition and the probe's events during the load.

## Fix

- **Keep a busy single-instance database reachable.** On the CloudNativePG `Cluster`, set readiness probe tolerance from the plan's CPU (`spec.probes.readiness` timeout and failure threshold), so a saturated 100m or 500m instance is not marked NotReady by load alone.
  - High availability needs a plan of at least 1 CPU (w2/m171), so the lenient settings never slow a failover.
  - Alternatively, make the readiness check one that load cannot time out, if the pinned CloudNativePG offers such a probe type.
- **Report load as `available`.** A database whose Postgres is running and whose readiness failed without a spec change, restart or upgrade should not read `config_restart`.
  - Keep `config_restart` for real restarts: a spec generation the cluster has not served, or a restarting Pod.
  - Check the datastore outage facts too (`postgres_unavailable` / `postgres_available`), so a load spike does not send notifications for a restart that never happened.
- **Key Value:** check the same probe-to-endpoint path for Valkey on its 100m plans.

## Blast radius

- **Every Postgres on a small plan:** `free` and `basic-256mb` at 100m, `basic-1gb` at 500m under heavier load.
  - Every connection path depends on the `-rw` Service: in-workspace apps, the external endpoint, `bex psql`/`pgcli`, the dashboard's SQL console and exports that open new sessions.
- **Status and events:** the status and possibly the outage events and webhooks are wrong during the load.
- **Not checked:** larger plans, HA clusters and read replicas.

## Regression checks

- **Operator test:** the generated `Cluster` carries the plan's readiness settings.
- **bex-api test:** a database with `readyInstances: 0`, a current generation and no restart or upgrade reads `available`, or the chosen state, not `config_restart`.
- **Production:** the 7c15 reproduction. Three parallel `generate_series` counts for 100 s on a free database leave every `select 1` sample answered and the status `available`. The PostgREST template serves `/` within its schema-cache time after going live.

## Unverified

- **The probe chain:** the Pod's NotReady and probe timeouts were not observed directly (no cluster access). The external error was `SSL SYSCALL error`, the internal one `Connection refused`, and both stopped as soon as the load did.
- **Render under the same load:** not measured; there is no Render account here. The parity claim rests on ordinary Postgres behavior and Render's meaning of `config_restart`.
