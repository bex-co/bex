## Objective

On a Hobby workspace, an untyped or `type=all` log read must contain no request lines, as t005 intended: "an all-types query silently loses its request lines". This applies to REST `/v1/logs`, GraphQL, MCP, the CLI and the dashboard's default **All logs** view. Today it returns them, so the Pro gate on HTTP request logs is bypassed by simply omitting `type`.

## Context

- Live, `/qa-find-bugs w4` loop run n5b3, 2026-10-24 (pin `ba5ad0e65498`, `bex-canary` **Hobby**). Owned Free fixture `qa-20261024-n5b3-node` (`srv-dbe8ciqei42s73atadc0`), deleted afterwards.
  - `GET /v1/logs?ownerId=tea-daif693dqjvc73e7as3g&resource=srv-dbe8ciqei42s73atadc0&startTime=2026-10-24T10:15:00Z&endTime=2026-10-24T10:45:00Z&limit=100` (no `type`) → `200` with **83 lines labelled `type=request`** (raw Traefik access-log JSON: `ClientAddr`, `RequestPath`, `KubernetesServiceName`, `TLSCipher`, …) and 5 `type=app`.
  - The dashboard `/services/<id>/logs` default **All logs** renders those same request lines (`GET 503 {"ClientAddr":…}`).
  - Control: `…&type=request` → `400 "type: HTTP request logs require the Pro plan or higher; this workspace is on Hobby"`; `type=app` → `200`.
- Root cause: `requireRequestLogsPlan` (`lego/backend/internal/logs/service.go:467-477`) sets `q.noRequest = true` for an all-types query, and `LogQuery.wants` (`:400-408`) honors it. But `lokiTypeMatcher` (`lego/backend/internal/logs/loki.go:502-511`) returns the app+request union `container=~"<app>|"` whenever `len(q.Types) == 0`, **before** consulting `wants()`. So the store read never sees the flag. The pod-log and live-tail paths use `wants()` and are unaffected (unverified live).
- Callers of `requireRequestLogsPlan`: `service.go:626` (tail), `:664`, `:907` and `:1007`. List every history query that reaches `lokiTypeMatcher` with empty `Types`, including label-values / filter discovery, which may still offer request-only values such as `statusCode`/`method`/`path` on Hobby.

## Steps

1. In `lokiTypeMatcher`, branch on `q.noRequest` before the empty-types union, and emit the app-only matcher. Better: route the empty-types case through `wants()` so every flag applies.
2. Check the sibling readers that build their own selector: log label values / filters, the request-count metrics read (Metrics host/path filters are a different, unplanned gate; leave them), and log export/download if present.
3. Dashboard: on Hobby, **All logs** shows app lines only. t011's plan notice covers the explicit Request option.

## Acceptance criteria

- [x] Hobby: an untyped `/v1/logs` read returns zero `type=request` lines while app lines still return. GraphQL and MCP likewise. The dashboard All logs view shows no request lines.
- [x] Pro: an untyped read keeps the app+request union, byte-for-byte unchanged.
- [x] A test with a Hobby plan stub asserts the LogQL selector excludes request lines for an empty-types query. It fails against the current matcher.
