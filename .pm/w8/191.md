# List endpoints called without `limit` return the whole list in an unsorted order instead of Render's default page of 20, so a cursor taken from that page continues a different order; and unfiltered `GET /notification-settings/overrides` returns one workspace instead of all of the caller's

Why: Render's pinned list parameters page by default (`limitParam` defaults to 20; results continue by `cursor`), so a client that sends no `limit` gets 20 items and follows `cursor`. Bex's shared `core.StablePage` deliberately returns the complete, unsorted list whenever neither `cursor` nor `limit` is sent ("preserving pre-pagination clients' complete-list response and ordering"). A sorted order applies only once a page is requested. A Render client that sends no `limit` and then follows the last item's `cursor` (because it received 20 or more) continues in a different order, so it can duplicate or skip items. ADR018's env-vars row records "omitted REST page params keep bex's prior full-list behavior instead of Render's default" without a user sign-off.

Separately, Render documents `GET /notification-settings/overrides` with no filter as returning "all notification overrides for all workspaces the user belongs to". Bex scopes it to the caller's default workspace (ADR018's notifications row, "Scope divergence", also unsigned).

**Severity:** minor (API contract; the pinned CLI pages explicitly). **Attribution:** server (`core.StablePage` and its 14 list callers; notification-overrides scoping). **Estimate:** 1h30m. **Source:** `/qa-find-bugs-cli` sweep 1326, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1326--list-defaults-and-override-scope)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `21652364739c`, read-only. The caller belongs to three workspaces (`tea-d98210cbbpdc73dcrkvg`, `tea-da2isimlm39c739m4ofg`, `tea-daif693dqjvc73e7as3g`).

- `GET /v1/notification-settings/overrides` (no filters), fully paged → **6** overrides, all from `tea-d98210…`. Per-workspace (`?ownerId=` each) → 6 + 1 + 8 = 15. The unfiltered result covers none of the other two workspaces' 9.
- `GET /v1/notification-settings/overrides?ownerId=tea-daif693dqjvc73e7as3g` with no `limit` → all 8, in order `…f6l0m0, …d1umvg, …90q930, …f5eeug, …90q91g, …9j12i0, …9j12cg, …eq4fr0`. The same request with `&cursor=<first item's cursor>` → **`[]`**, although seven items follow it in the order just returned. Paging with `limit=3` walks a different (sorted) order and covers all 8 exactly once.
- `GET /v1/services?ownerId=…` with no `limit` → all 8 services, not sorted by ID (same helper).

## Expected

- With no `limit`, list routes return Render's default page size (20) in the same stable order that cursor continuation uses. A cursor from any page, including a default-size first page, continues that order without duplicates or gaps.
- Unfiltered `GET /notification-settings/overrides` spans every workspace the caller belongs to and is paged across them. `ownerId` narrows it to one workspace, as today.

## Root cause

- `lego/backend/internal/core/pagination.go:426–432` `StablePage(items, after, limit, requested, …)`: when `requested` is false (no `cursor` or `limit` in the query), items are returned unchanged. That covers 14 callers, including `apps/rest.go` (×4: services list, notification overrides, …), `postgres/rest.go`, `keyvalue/rest.go`, `projects/rest.go`, `registrycreds/rest.go`, `envgroups/service.go` and `apps/disks.go`.
- `lego/backend/internal/apps/rest.go:1632–1660`: the overrides list calls `s.List(ctx, q.Get("ownerId"))`, and an empty `ownerId` resolves to the caller's own workspace only.

## Fix

1. Make REST list routes apply Render's default `limit` (20) when it is omitted, and always sort by the cursor key, so unpaged and paged reads share one order. GraphQL and MCP callers that want the complete list keep passing their own limit. Audit internal callers (dashboard, CLI launcher, MCP) that relied on the full unpaged list.
2. Make the unfiltered overrides list iterate every workspace the caller is a member of, merged in one stable order. Keep `ownerId` and `serviceId` filters as today.
3. Add a conformance check that a request with no `limit` returns at most 20 items, and that continuing with its cursor yields no duplicates. Update ADR018's env-vars and notifications rows.

## Blast radius

Every REST list route that uses `StablePage`: services, Postgres, Key Value, projects, env groups, registry credentials, disks, notification overrides and others. Clients that read "everything" without paging will now get 20 at a time, as from Render. The notification-overrides change is read-only.

## Acceptance

- Unit: the no-`limit` response is ≤ 20 items and sorted; its last cursor continues without a duplicate; the unfiltered overrides list includes all member workspaces.
- Live after deploy: repeat the reproduction. Unfiltered overrides show 15. The no-`limit` canary list is in the same order as the `limit=3` walk, and a cursor from its first item returns the next seven.
