# Create dry-runs preview a service/Postgres/Key Value past the plan's count cap

Why: a Hobby workspace that already has its 1 Key Value (or 1 Postgres, or 25 services) gets a dry-run preview for another one, but the real create is refused by the namespace ResourceQuota. Dry run is still not a full validation step for plan caps (the remainder of w8/045).

- The caps exist only as ResourceQuota `count/*` keys (`lego/backend/internal/store/namespaces.go` `quotaForPlan`, `QuotaCapsForPlan` in `plans.go`). They are enforced at admission on the real CR create and translated by `core.QuotaCapError` (`postgres/service.go`, `keyvalue/service.go` CreateX; apps through `writeNewApp`). Every dry-run path returns before any CR create.
- Options: (a) a server-side dry-run CR create (`client.DryRunAll`). It treats a missing `<ws>` namespace as zero usage, but it needs live proof that ResourceQuota admission evaluates dry-run requests on our cluster version and that no webhook has side effects. (b) Count the workspace's CRs against `QuotaCapsForPlan`, read-only, which is the same source the "3/5 services" display uses (`workspaces.Service.ResourceLimits`).
- Tests: a Hobby workspace with 1 existing Key Value gets the same refusal from dry-run and real create, and the dry run writes nothing. The same holds for Postgres and the 26th service.
