# Renaming a Blueprint-managed env group makes the next sync create a second group with the declared name, and link the services to both

Why: a dashboard rename is an ordinary edit of a Blueprint-managed resource ("You _can_ still make changes to a Blueprint-managed resource via other mechanisms", [infrastructure-as-code](https://render.com/docs/infrastructure-as-code)), but on bex the next sync forgets the group it created, mints a copy, and leaves both linked.

- Severity: minor to major, depending on Render's behavior. With both groups linked and the same keys in each, the newer copy's values win (the newest linked group wins on Render and bex alike). The renamed original then looks live, but any edit of it changes nothing at runtime.
- Source: the w8/381 worker checked the lead from routine `cli-qa` run 29 (2026-11-21, nonce `bf3e`; filed under w8/381's "Lead, not filed"). The finding comes from code on main `3b11c4b878`, not from a live run.
- Attribution: server, `lego/backend/internal/envgroups` and the Blueprint plan.

## What the code does

- `RenameEnvGroup` (`envgroups/service.go:819`) changes only the display name. The id, contents and links stay.
- Blueprint env groups are matched by name alone. The plan looks the declared name up in `GroupIDsByName` (`apps/blueprint_state_plan.go:99`, `:174-176`), and the apply uses `findGroupByName` (`ApplyEnvGroup`, `envgroups/service.go:1625`). After a rename both miss, so the plan shows `create` and the apply mints a new group with the declared name.
- `fromGroup` then links the service to the new group (`LinkEnvGroup`, `envgroups/service.go:1767-1782`, by name). Nothing unlinks the renamed one, so the service carries both.
- Env groups have no Blueprint claim. `store.BlueprintClaimKind` covers service, database, key_value and build_source only (`store/blueprint_resource_claims.go:33-38`), so nothing records that the renamed group was this Blueprint's.

## What Render does (not established)

- The [Blueprint spec](https://render.com/docs/blueprint-spec) says resources are named in the file ("If you add the name of an existing service to your Blueprint file, Render attempts to apply the Blueprint's configuration to that existing service"). It says nothing about a resource renamed outside the file, for env groups or services.
- First step: find out, from a Render workspace or Render support documentation. The candidates are: Render renames the group back on the next sync (it tracks the resource by id), or Render also creates a second group (name matching, as bex does).
- If Render tracks by id: give env groups a Blueprint claim keyed by id, so a sync matches the claimed group whatever its current name and renames it back. Check whether services renamed in the dashboard have the same gap, since service claims are keyed by name too (`BlueprintResourceKey{Kind, Name}`).
- If Render also creates a copy: record the parity in ADR018 and close.
