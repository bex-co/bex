# A native build's log shows the build command's stderr and stdout out of order: every stderr line of a burst comes before the stdout lines printed between them

Why: a failing build's error lines (compilers and package managers write them to stderr) appear above the stdout lines that came before them, so the log no longer reads the way the command ran. A line printed without a final newline is also glued onto a later line from the other stream.

- **Found by:** `/qa-find-bugs-cli w8` routine run `cli-qa`, sweep r15-a065, 2026-11-20 18:16–18:45 UTC. bex CLI v0.7.0 (Render CLI v2.36.0 pin), QA human device login, workspace `bex-canary`, `-o text`/`json`.
- **Fixture:** free native Python web service `qa-20261120-a065-env` (`srv-dc08tu5i534c73chvb4g`, `render-examples/flask-hello-world@facfc73`, deleted, `GET` 404). Each case set the build command with `bex services update <srv> --build-command '…' --confirm`, then ran `bex deploys create <srv> --wait --confirm`. The log was read with `bex logs -r <srv> --type build --direction forward --start <createdAt> --end <finishedAt> -o json`.
- **Evidence (production), deploy `dep-dc093ili534c73chvbjg`, `build_failed`, `--wait` exit 1:** the build command was
  `for i in 1 2 3 4 5 6 7 8; do echo qa-out-$i; echo qa-err-$i >&2; done; …; printf qa-partial-out; …; echo qa-err-final >&2; exit 4`.
  The shell wrote `qa-out-1, qa-err-1, qa-out-2, qa-err-2, …`. The build log reads:

  ```text
  18:31:50.927054849Z qa-err-1
  …                   qa-err-2 … qa-err-8   (all stamped 18:31:50.9271)
  18:31:51.005342793Z qa-out-1
  …                   qa-out-2 … qa-out-8   (all stamped 18:31:51.0053–.0060)
  18:31:51.006034007Z qa-partial-out/bin/bash: line 2: sleep: command not found
  18:31:51.006048233Z qa-err-final
  18:31:51.006055396Z error: build command '…' exited with code 4
  ```

  The two streams arrive as separate batches about 78 ms apart, so all eight stderr lines precede all eight stdout lines. The earlier run `dep-dc091v5i534c73chvbeg` showed the same shape: `echo qa-fail-stderr-last >&2; printf "qa-no-newline-tail"` became the single line `qa-no-newline-tailqa-fail-stderr-last`, with the stdout tail first although it was written last. (The `sleep: command not found` came from a `PATH=qa` override set by the same sweep, not from the image.) Both streams carry identical labels (`resource`, `build`, `type: build`), so a reader cannot re-sort them. Lines from one stream keep their order: 40 and 25 numbered stdout lines read back complete and in order, forward and backward.

- **Cause (code, partly inferred):** the build command runs as a BuildKit `RUN` step. `nativeDockerfile` builds it as `shellJSON(nativeEnvLoaderPrefix + installStep + nativePublishCheckStep(o) + o.BuildCommand)` (`lego/operator/internal/build/native.go:446`, prefix at :422), so the command's stdout and stderr stay two file descriptors. BuildKit carries a step's output as per-stream `VertexLog` records (stream 1 and 2) and prints them in the order each stream's chunk reaches the progress writer, not in write order. `bex_run` (`build.go:154-157`) then merges buildctl's own output, and `nativeLogDisplay` (`build.go:213`) shows it as given. Unverified: the exact BuildKit v0.30.0 function that batches each stream (`util/progress/logs/logs.go` is the likely seat).
- **Fix:** make the build command's stderr share its stdout before the command runs, for example `exec 2>&1` as the first line of the RUN (in `nativeEnvLoaderPrefix` or ahead of `o.BuildCommand`). One file descriptor then carries both streams in write order, and a newline-less tail joins the next output the way a terminal shows it. Check that the failure summary (`buildkitFailureSummary`, the `==> Build failed:` block) still names the last lines and the exit code, and that `nativeEnvLoaderPrefix`'s test fixtures (`nativecommon_gorust_test.go:277`, `nativequalification_init_test.go:567`, `nativestaticdeps_test.go:226`) follow the new prefix. The RUN text changes, so every native build misses its build-command layer cache once. Leave Dockerfile builds alone: they are the tenant's own `RUN` steps, and Render builds them with BuildKit too.
- **Render:** how Render orders a mixed stdout/stderr burst in a build log was not observed. Write order is what a terminal, CI logs and `2>&1` all show, and it is the only order a reader can follow.
- **Acceptance (production, `bex-canary`, a free native fixture deleted afterwards with a 404):** with the build command above, `bex logs -r <srv> --type build --direction forward` shows `qa-out-1, qa-err-1, …, qa-out-8, qa-err-8` in that order, then `qa-partial-out` joined only with the output written after it, then `qa-err-final`, the `exited with code 4` line and the `==> Build failed:` summary. A unit test asserts the RUN merges stderr into stdout before the build command.
- **Dedupe:** `rg -i 'interleav|stderr.*order|stdout and stderr' .pm docs` finds only w4/m200 (app pod-log readers keep stdout and stderr records whole) and the deploy page's type interleaving (w9/m1). Neither covers the order of a build step's two streams. Not in `DO_NOT_DO.md` or ADR018.
- **Estimate:** ~30–45m, minor.
