# After a canceled deploy, rolling back to the deploy that is still live is accepted and restarts the instance

Why: w8/261 made a rollback to the already-live deploy answer 409. One state still gets through. When a newer deploy was requested and then canceled, the live deploy keeps running, yet a rollback to it is accepted: the instance is replaced and a redundant deploy row is added. The service was never off that release, so there is nothing to recover.

**Severity:** minor (a needless restart; no wrong artifact). **Attribution:** server (backend deploys). **Estimate:** ~45m. **Source:** review of the w8/261 fix, 2026-11-11. Read from the code; not run.

## Evidence

- `RollbackActionable` (`lego/backend/internal/deploys/actioncaps.go`) treats the live deploy as a recovery target when the requested release generation (`app.bex.co/release-generation`) is above the deploy's own. A cancel never rewinds that annotation (`lego/backend/internal/store/release_cancel.go:96-118`), so it stays above the live deploy for good.
- A canceled rollback or image override also leaves its release selection in the spec with the canceled generation. The live deploy's generation differs from it, so the selection arm accepts the live deploy as well.
- The cancel already records which release it leaves running (`AnnotationSurvivingReleaseGeneration`, read by `awaitingSurvivor` in `lego/backend/internal/store/reconciler.go`).

## Fix

In `RollbackActionable`, a live deploy whose generation is the survivor of the latest canceled request is what is running: not a target. Keep the recovery for a release that failed rather than was canceled. Check first what the saved settings hold after a cancel: if the canceled release's saved image or settings stay in the spec, a rollback to the live deploy does change what the next restart runs, and the refusal would be wrong.

## Acceptance

- A service with one live deploy; start a second deploy and cancel it; `POST …/rollback` to the live deploy answers 409 and adds no row, and `deployActions` reports `no_eligible_rollback_target`.
- After a second deploy that failed, the same call still answers 201.

## Unverified

- Not run on a cluster or in a test; the two arms were read.
- Render's answer for the same call after a canceled deploy.

## Dedupe

w8/261 (the same refusal for a service nothing newer was requested on). w8/265 is the cancel race itself, not this.

## Triage note 2026-11-11 (w8 drain): read further, not changed

Left open. The narrow rule ("the newest requested release was canceled, so the live deploy is what runs") is not safe on the App's annotations alone:

- **A survivor.** When the canceled deploy was only waiting behind another one, an older release is still in flight (`AnnotationSurvivingReleaseGeneration`). A rollback to the live deploy then supersedes it and must stay allowed.
- **A failed release underneath.** Live release 5, release 6 failed, release 7 requested and canceled. Rolling back to 5 was a recovery before 7 was requested (a wake or resume can start the newest template, the failed one: `restoreServedTemplate`'s comment), and whether it still is depends on which template the Deployment holds after the cancel. The annotations do not say; the deploy rows between the live one and the canceled one do.
- **A canceled image change.** The saved image stays the canceled one, so the image-drift arm accepts the live deploy as well. Refusing there is right only if a canceled release is never started again by a wake or a resume.

So the fix belongs in the verb, with the service's deploy rows at hand (every row newer than the live one is canceled, and no survivor is above it), and it needs the operator's behaviour after a cancel confirmed on a cluster first.
