# A REST deploy trigger that lands in the queue answers 201 Created with the queued row, where Render answers 202 Queued, as bex's own deploy hook already does

Why: Render's Trigger deploy separates "your deploy started" (201 with the deploy) from "your deploy is waiting behind the one in progress" (202 Queued, no body). The pinned Render CLI is written for that split: on a 202 it finds the queued deploy itself. bex answers every accepted trigger 201, so a client that branches on the status code cannot tell a queued deploy from a started one. bex's deploy hook already makes this split (w4/635).

- Severity: minor. The pinned CLI works either way, because it reads a 201's body and polls after a 202. Only status-code-aware API clients see the difference.
- Versions: bex CLI v0.9.0 release binary. Render CLI pin per `lego/cli/UPSTREAM_RENDER_CLI.md` (v2.36.0, `4fd34231b637`). Production pin `cce6c749f6ff`. The code is unchanged on main `436def3144`.
- Context: 2026-11-21 14:21 (CLI) and 14:28 (REST) UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`). Routine `cli-qa`, run r26, nonce `fc60`. Fixtures were the free native Python service `srv-dc0qa552n01c73bc1img` and the free image web service `srv-dc0qko52n01c73bc1k1g` (`nginx:1.27.0-alpine`). This run created and deleted both, and a 404 confirmed each delete.
- Attribution: server (`lego/backend/internal/deploys/rest.go`).

## Render

- In the pinned OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`), `POST /services/{serviceId}/deploys` documents `201` with the deploy schema and `202` `{"description": "Queued"}`, with no content. [api-docs.render.com/reference/create-deploy](https://api-docs.render.com/reference/create-deploy) says the same (read 2026-11-21).
- The pinned CLI handles exactly that. `pkg/deploy/repo.go:59` returns `resp.JSON201`, which is nil on a 202. `pkg/tui/views/deploycreate.go` `CreateDeploy` then calls `WaitForDeployCreate`, which lists the service's deploys with `status=queued`, `limit=1` until one appears.
- Render's deploy-hook docs say 200 "The deploy starts immediately" and 202 "The deploy will start after an in-progress deploy". bex's hook already follows them (`lego/backend/internal/deploys/deployhook.go:399-406`, w4/635).

Through the CLI, the second of two back-to-back `bex deploys create srv-dc0qa552n01c73bc1img --commit <sha> -o json --confirm` printed `"status": "queued"` straight from the 201 body. It then went live after the first, as Render's Wait policy says, so the queueing itself is right. Only the status code differs.

## Mechanism

The REST trigger handler (`lego/backend/internal/deploys/rest.go:266-292`) always ends with `core.WriteJSON(w, http.StatusCreated, toRenderDeploy(d))` (`:291`), whatever `d.Status` is. The hook handler checks `d.Status == store.DeployQueued` and answers `http.StatusAccepted` instead.

## Fix

In the REST trigger handler, when `d.Status == store.DeployQueued`, answer `202 Accepted` with no body, as Render's contract has no 202 schema and as the hook does. Keep `201` plus the deploy for a trigger that starts at once. Leave Rollback (`rest.go:318`) as it is unless Render's Rollback contract also documents a 202. Check that before changing it.

If a bex-owned caller needs the queued row's id, it reads `GET …/deploys?status=queued&limit=1`, as the pinned CLI does. GraphQL `triggerDeploy` and MCP `trigger_deploy` have no status code and keep returning the deploy.

## Blast radius

- `scripts/events-verify.sh:273,280` expects 201 from triggers fired while the service is idle, which are not queued, so it is unaffected. Re-run it, or read it, to confirm.
- No dashboard, mobile or CLI-launcher code calls this REST route. The dashboard uses GraphQL.
- The w2/m251 OpenAPI drift check (`lego/backend/internal/api/render_openapi.go`) already lists 202 for this operation.
- Update ADR018's "Trigger a deploy" row (`docs/ADR018-render-parity.md:158`) to say a queued trigger answers 202, as the hook does.

## Acceptance

- On a free image service with a deploy in progress, a second REST `POST …/deploys` answers `202` with an empty body. `GET …/deploys?status=queued&limit=1` lists that row, and it goes live after the first.
- An idle trigger still answers `201` with the deploy.
- `bex deploys create <srv> -o json --confirm`, run twice back to back, prints the queued deploy for the second call. That proves the pinned CLI's `WaitForDeployCreate` path works against bex.
- A unit test in `lego/backend/internal/deploys` covers both status codes.

## Unverified

- Whether Render's 202 carries any body. Its schema has none, so an empty body is the safe match.
