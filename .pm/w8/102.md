# 102 — Blueprint environment copies use a literal shadowed by a reference

Why: a Blueprint should copy the source service's effective variable, or reject a value it cannot resolve, instead of silently writing a different value to the consumer.

**Severity:** major (silent configuration mismatch in the current apply path; no production outage or data loss claimed). **Ownership:** shared server Blueprint environment classification. **Estimate:** 55m. **Status:** todo. Source: functional `$qa-find-bugs-cli` w8 sweeps198/204, 2026-10-13 UTC; [ADR049](../../docs/ADR049-render-yaml-parity.md) and ADR008 reliable hosting.

**Evidence boundary:** both native clients accept the problematic files against production. The value mismatch is proven through actual current public ValidateBlueprint/DeployStack and persisted App specs in a fake Kubernetes client. Hosted apply and pod values were not exercised; no pinned CLI apply command exists or is claimed. Current source c5a0eb9dd15f6b417bf586fdf26510706497b032; deployed API/operator/Kubernetes revisions unknown. This schedules a researched source bug with live admission evidence, not an observed production runtime incident.

## Current-source apply proof and root cause

Six actual ValidateBlueprint -> DeployStack diagnostics use a private virtual overlay. Each creates three App specs in a fake client and reads their actual persisted env arrays. Four reproduce different source/copy values; two controls agree. These assertions expect the current bug. Four existing env-classification/apply/type tests also pass; no full backend suite or future-fixed test is claimed. [Actual apply diagnostic](evidence/102/apply-results.json).

- `deploy.go:2451–2470` classifies references separately from literals. A literal adds VALUE to se.known; a same-key reference does not invalidate that entry. This is independent of entry order.
- `:1920` publishes that stale literal in idx.serviceKnownEnv before pass2. `:1945` classifies each service's references; `:2104–2108` appends a resolved reference after all plain env entries. It does not reconcile the known index with what the source will actually receive.
- `resolveRef:2774–2788` reads the stale map and treats VALUE as plainly defined, returning the losing literal to consumer. Its own comment excludes values that are themselves references or generated.
- `service.go:2311–2317` deliberately preserves manifest-owned env on the Blueprint App spec, unlike ordinary service creation. The actual public apply therefore persists the conflicting caller array and a different consumer literal; empty create seed maps are expected.
- `operator/app_controller.go:4741–4763`, consumed by deployment_projection.go:222, preserves that App env order. The reviewed [Kubernetes kubelet source](https://github.com/kubernetes/kubernetes/blob/v1.35.0/pkg/kubelet/kubelet_pods.go#L781-L899) overwrites each map entry while visiting container.Env, so the later reference value is effective. This runtime consequence is inferred from those source paths; no hosted pod observation is claimed.

[Source excerpts](evidence/102/source.txt), [primary contract review and limits](evidence/102/primary-contract-review.json). [Render's service-reference contract](https://render.com/docs/blueprint-spec#referencing-service-properties) describes envVarKey copies on sync; it does not establish precedence for duplicate entries in one envVars array. This finding requires consistency with Bex's existing accepted apply behavior, without inventing a Render duplicate-key rule.

## Scoped correction and acceptance

Before publishing a service's known-literal index, exclude a key whose effective value is supplied by a deferred reference. Track these keys across the complete classification, so a literal encountered later cannot restore a shadowed value. With Bex's existing plain-value-only resolver, the problematic consumer must receive the same honest refusal as the pure-reference chain, before any write. Do not merely update the index after classifying one service: consumer-first declarations would still read stale data. Preserve current duplicate-literal behavior and the caller's accepted reference-only configuration; do not introduce a global duplicate-key ban, change precedence, or expand reference-chain/generated-value support as this fix.

- The four bad-copy files in both clients return exit1/valid:false with a diagnostic at the consumer COPY_VALUE entry. Existing pure-chain refusals remain. A current-service regression should assert the refusal and zero fake App writes through public DeployStack; it must fail before the fix.
- Literal-only duplicates and unique-key controls retain valid:true and actual matching source/copy values. Cover both mixed entry orders, consumer-first declarations and the empty literal explicitly.
- Audit collisions with other deferred fromService/fromDatabase forms in the same classifier, plus seed/generate branches for follow-up, without reading dynamic values or expanding this item beyond known-index truthfulness. All five App kinds share service environment parsing; Key Value references take a separate resolver branch. Those sibling collision behaviors are untested, not passing claims.
- The parser has four production callers: compile/deploy (deploy.go:1696), shared validation (blueprint.go:661), disconnect grouping reclamation (:1607) and generated-manifest checking (blueprint_generate.go:240). Preserve existing callers and the w8/099 known-group correction. Shared validation/preview serves REST/GraphQL/MCP and dashboard review. Only native REST validation is live-tested here; other surfaces and hosted apply require acceptance checks.
- Run meaningful focused backend checks and review the small correction. No client fork, operator behavior, schema/envelope, pricing or new hosting feature is required.
