# Persistent Blueprint sync replaces an explicit service repo and branch

**Severity: major. Owner: backend Blueprint source context.** A valid provided-manifest sync declares one Git source but prepares and persists the containing Blueprint's different repository/branch. The accepted deployment then builds that other repository and fails. [Native/API/source/cleanup evidence](evidence/cli-sweep322/README.md).

## Expected and actual

[Render's Blueprint repo and branch contract](https://render.com/docs/blueprint-spec#repo) makes the containing source a default: a service can explicitly choose its own repo and branch. The retained manifest names Express/serve-static@master while the Blueprint is nodejs/node@main. Native validation succeeds through published Bex, unchanged Render pin and a fresh checkout build. One API-only provided sync returns200, leaves the authored YAML stored, but service readback becomes Node/main and the first new deployment uses Node's commit and ends build_failed. A separate native-created inline control builds/serves the exact Express commit/package/literals without recovery. Existing healthy image serving during the failed build is correct availability behavior, not this bug.

## Producer and consumer trace

- Pinned cmd/blueprintvalidate.go and pkg/client multipart validation send the authored document; no CLI apply exists. The API-only request is POST /v1/blueprints/OWN_ID/sync with ownerId and bexYaml. apps/rest.go:1421–1429, apps/graphql.go and apps/mcp.go adapt the shared SyncBlueprint method; the CLI is not rewriting source.
- apps/blueprint.go:1322–1360 recognizes provided YAML without consuming or claiming a Git file commit. prepareSyncManifest:1280–1299 compiles it with DeployRequest{Repo:b.Repo, Branch:b.Branch}. CreateBlueprint:1089–1090 and PreviewBlueprint:1021 feed the same containing context; the stored/fetched fallback at1463 also compiles through that shape.
- apps/deploy.go:1864–1874 turns those values into blueprintParseOverrides. parseService:2539–2551 first reads a.Repo/a.Branch, then unconditionally replaces both when the overrides are nonempty and image is absent. That behavior is deliberate for a direct deployment target, proven by maintained TestDeployStackRepoOverrideWins at deploy_test.go:251–261. A containing Blueprint default is incorrectly sent through that same force-override path.
- prepareSyncManifest stages the unmodified manifest, so stored YAML and the prepared request disagree. The corrected m70 managed-source fold then faithfully applies the wrong prepared tuple. persistBlueprintIntent at deploy.go:3454 writes it through SetAppSource; the app/controller/build projection consumes that repo/ref to clone/build. The wrong Git metadata and deployment commit establish the effect; this is not m70 retaining an old image or m66 losing a canonical write.

## Proposed correction and shared scope

Represent containing Blueprint source defaults separately from deliberate direct-deploy overrides in the shared compile/parse context. For persistent source context, preserve explicit per-service repo and branch; fill only the applicable omitted fields. Preserve the explicit direct-deploy override contract and existing image-source behavior. Do not globally reverse parse priority, rewrite YAML text after validation, repair metadata after side effects, or add a CLI workaround.

Census compile/parse callers in blueprint.go:661 (validation),1021 (preview),1090 (Git-backed create),1281 (sync preparation),1463 (stored/fallback),1663 (manifest analysis), blueprint_generate.go:240 (export validation), and deploy.go:698,1857,1864–1874. Fetched/stored/provided sync, create, preview and auto-sync/webhook paths must use the proper context, with coherent planning and application. Preserve exact stored YAML, source presence, m70's coupled source/strategy fold, retained rollback images, admission fencing and reviewed-file provenance. Check service commit binding when its repo differs from the Blueprint source; do not label a parent commit as belonging to another repo.

Four real preparation subcases fail and four controls pass without a product edit. Add maintained failing-first tests through the actual context/prepare/apply and canonical writer, rather than only checking a private helper. Root and nested declarations, explicit repo-only/branch-only/both, omitted same-source defaults, image sources, direct-deploy overrides and reviewed-file pins need coverage. Other resource families and transport adapters share parsing and are source-traced, not live-proven.
