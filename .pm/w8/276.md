# Twenty-two Postgres extensions on Render's supported list are refused with "permission denied" for the database user, and `pg_repack` is not installed

Why: Render lists about sixty extensions that "are available for all databases running PostgreSQL 13 or later" and says to enable any of them with `CREATE EXTENSION`. On a bex database the default user can create the 21 that PostgreSQL marks trusted, and finds `vector` and `pg_stat_statements` preinstalled. Twenty-two more are in the image but answer "permission denied to create extension … Must be superuser", so a migration that runs `CREATE EXTENSION earthdistance`, `dblink`, `moddatetime` or `bloom` fails. ADR092 plans an owner allowlist, but it is closed to the six extensions that are missing from the image, and its Context says only those six fail. The 22 are not in any milestone.

**Severity:** major (a documented `CREATE EXTENSION` fails for a third of Render's list; nothing else breaks). **Attribution:** platform (Postgres operand image and extension allowlist, ADR092). **Estimate:** ~2h on top of ADR092's adoption (w8/m92), milestone-sized with it. **Source:** `/qa-find-bugs-cli` w8 loop sweep `05f7`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `8330744bd643`, workspace `bex-canary`, QA human device login.

## Evidence

A free PostgreSQL 18 database, default user (`rolsuper` false, `rolcreatedb` true).

```text
$ bex pg create --name qa-20261111-05f7-pg --plan free -o json --confirm        # version 18, available in 90 s
$ bex psql <dpg> -c "create extension dblink;"
Error: exit status 1: ERROR:  permission denied to create extension "dblink"
HINT:  Must be superuser to create this extension.
```

Every name on Render's list was tried in one session with `CREATE EXTENSION IF NOT EXISTS`:

| Result | Extensions |
| --- | --- |
| Created (23) | `plpgsql`, `vector`, `pg_stat_statements` (all three already present), `btree_gin`, `btree_gist`, `citext`, `cube`, `dict_int`, `fuzzystrmatch`, `hstore`, `intarray`, `isn`, `lo`, `ltree`, `pgcrypto`, `pg_trgm`, `seg`, `tablefunc`, `tcn`, `tsm_system_rows`, `tsm_system_time`, `unaccent`, `uuid-ossp` |
| `42501` permission denied (22) | `amcheck`, `autoinc`, `bloom`, `dblink`, `dict_xsyn`, `earthdistance`, `file_fdw`, `insert_username`, `intagg`, `moddatetime`, `pageinspect`, `pg_buffercache`, `pg_freespacemap`, `pg_prewarm`, `pg_surgery`, `pg_visibility`, `pgaudit`, `pgrowlocks`, `pgstattuple`, `refint`, `sslinfo`, `xml2` |
| `0A000` not available, already tracked (9) | `postgis`, `postgis_raster`, `postgis_topology`, `postgis_tiger_geocoder` (w8/m92), `pg_partman` (m104), `pg_duckdb` (m109), `pg_ivm` (m110), `pg_similarity` (m111), `timescaledb` (m112) |
| `0A000` not available, not tracked (1) | `pg_repack` |
| `0A000`, not expected on 18 (3) | `adminpack` and `old_snapshot` (removed from PostgreSQL 17), `wal2json` (an output plugin, not created with `CREATE EXTENSION`) |

`pg_available_extensions` lists all 22 refused names with `trusted = false`.

Matching Render on the same database: `max_connections` is 100; an external connection with `sslmode=disable` is refused and `require` gets TLS 1.3; the Free plan refuses connection pooling, high availability, a larger disk and disk autoscaling by name, has no point-in-time recovery, and expires 30 days after creation.

## Expected

Render, [Postgres extensions](https://render.com/docs/postgresql-extensions):

- "Except where noted, these extensions are available for all databases running PostgreSQL 13 or later:" followed by the table the names above come from.
- "To enable any supported extension, run the CREATE EXTENSION command like so:"
- `pg_repack`: "PostgreSQL 16 or later." and "Requires installing the `pg_repack` client on your local machine."

So on bex the database user can `CREATE EXTENSION` each of the 22 on every major where Render lists it, and `pg_repack` on 16 and later.

## Root cause

1. PostgreSQL lets a database owner create an extension only when its control file says `trusted`. The 22 are contrib modules that ship untrusted, and the bex database user is not a superuser by design.
2. `vector` works because the operator installs it into every application database through the CNPG Database child (w8/m84, ADR009 § pgvector). Nothing does the same for the others, and ADR092 D2 rules out more preinstalls.
3. ADR092 D3 defines the owner allowlist as a closed list: "Only the reviewed names in D1's table". D1's table holds the six extensions missing from the image. The ADR adds that untrusted ones such as `file_fdw` and `dblink` "fail as before", and its Context says "Six of them fail on bex today", which undercounts by these 22 and `pg_repack`.
4. ADR092 is accepted but not adopted: no operand image is pinned in production, so today nothing admits an untrusted extension.

## Fix

1. Amend ADR092: D1's table and D3's allowlist cover every name on Render's list for each major, not only the six. Record each of the 22 with the majors where Render offers it.
2. Review each before admitting it. Creating the extension must give the owner nothing beyond what PostgreSQL's own grants allow:
   - `file_fdw` stays useless without `pg_read_server_files`, and `dblink` without a password still needs a superuser.
   - The inspection modules (`pageinspect`, `pg_surgery`, `amcheck`, `pg_buffercache`, `pg_freespacemap`, `pg_visibility`, `pgstattuple`, `pgrowlocks`, `pg_prewarm`) keep their default execute grants. Decide per module whether the owner gets them.
   - `pgaudit` needs `shared_preload_libraries`; project it the way D3 item 4 does for TimescaleDB.
3. Add `pg_repack` to the operand image on 16 and later, with the client-version note Render gives.
4. Extend D3's test (item 5): the owner creates each listed extension on each major, is still not a superuser afterwards, and a name outside the list still fails.
5. Until the image is adopted, record the 22 and `pg_repack` in ADR018 as an open gap, next to the six.

## Acceptance

- On a new database of each major 13 to 18, the default user runs `CREATE EXTENSION` for each of the 22 that Render lists for that major, and each succeeds.
- `CREATE EXTENSION cube; CREATE EXTENSION earthdistance; SELECT earth_distance(ll_to_earth(0,0), ll_to_earth(0,1));` returns a distance.
- `CREATE EXTENSION moddatetime;` and a `moddatetime` trigger updates a timestamp column.
- `CREATE EXTENSION pg_repack;` succeeds on 16 and later.
- The user is still not a superuser, and an extension outside Render's list is still refused.
- A logical export and restore of a database using these extensions works.

## Unverified

- Render's side is from its docs; no Render database was run. The docs do not say which user runs the command or how a non-superuser is allowed to.
- Only PostgreSQL 18 on the Free plan was run. Majors 13 to 17 and paid plans use the same role model and the same contrib set, so the same refusals are expected; `adminpack` and `old_snapshot` exist only below 17 and were not tried there.
- What a Render user can do with the inspection modules after creating them.
- Whether `wal2json` is present as an output plugin. Using it needs a replication slot, which was not tried.

## Dedupe

w8/m84 (done) preinstalls `vector`. w8/m92, m104, m109, m110, m111 and m112 (blocked on ADR092's image) cover PostGIS, pg_partman, pg_duckdb, pg_ivm, pg_similarity and TimescaleDB. w8/234 (done) and w8/236 (blocked) are faults inside that image. None names the untrusted contrib extensions or `pg_repack`.
