# A workspace-level environment group cannot be linked to a service that belongs to a project environment (409 `ENV_GROUP_SERVICE_ENVIRONMENT_MISMATCH`); Render allows linking it to any service

Why: Render's docs say: "If an environment group _doesn't_ belong to a particular project environment, you can link it to _any_ service in your team—including services that _do_ belong to an environment" ([configure-environment-variables § Scoping a group to a single environment](https://render.com/docs/configure-environment-variables#scoping-a-group-to-a-single-environment)). Only an environment-scoped group is restricted to its environment. Bex requires exact scope equality for every group, so the standard "shared secrets for staging and production" setup is refused. `bex blueprints validate` accepts the Blueprint form of the same setup, and apply then runs into the same refusal. ADR018's environment-groups row records this as "Scope divergence (w4/m143) … Expanding workspace-group reach needs a separate product decision", with no user sign-off. ADR008 § Render parity first says parity is never parked on an optional decision.

**Severity:** minor (an explicit refusal with a workaround: duplicate the group per environment, then keep the copies in sync). **Attribution:** server (env-group link validation). **Estimate:** 1h30m. **Source:** `/qa-find-bugs-cli` sweep 1312, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1312--env-group-scope)).

## Expected

- A group with no environment links to any service in its workspace, in or out of an environment.
- A group scoped to an environment links only to services in that environment, as today.
- Moving a group into an environment while it is linked outside that environment stays refused (`validateLinkedServiceEnvironments`), because Render's scoping rule forbids that end state.

## Root cause

`lego/backend/internal/envgroups/service.go:1278–1291` `validateGroupServiceEnvironment` returns `nil` only when `labels[core.LabelEnvironment] == groupEnvironment`. A workspace group (`""`) therefore matches only services with no environment. It is called on link (`service.go:1053,1060`), on initial links at group create (`initial_links.go:151`) and from the service-side link path (`service.go:536`). Blueprint apply links through `EnvGroups.LinkEnvGroup` (`apps/deploy.go:1069`), so it hits the same check.

## Fix

In `validateGroupServiceEnvironment`, accept `groupEnvironment == ""` for any service. Keep the equality rule for an environment-scoped group. Leave `validateLinkedServiceEnvironments` (scope changes) as is: scoping a group into an environment still requires every linked service to be in it. Check readers that assume equality, such as the dashboard's group picker (w4/m143) and any env-group list filtered by environment, so that a workspace group is offered to environment services. Update ADR018's environment-groups row to remove the scope divergence.

## Blast radius

Env-group link on REST, GraphQL, MCP, the dashboard and Blueprint apply. Only the workspace-group-to-environment-service case changes from refused to allowed. Environment-scoped groups are unchanged.
