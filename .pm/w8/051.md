# 051 — `blueprints validate` reports only one dangling `fromDatabase`/`fromService` reference, and which one changes from run to run

Why: ADR049 promises validation "reports every independently actionable error it can safely discover". w8/019 delivered that for the compiler and per-service stages, but the workspace-reference stage still returns its first failure. Because it iterates a Go map, the same file names a different missing reference on different runs, so an author fixes them one validate at a time and can't trust the answer.

Severity: minor. Attribution: server (`lego/backend/internal/apps`). Residual of `w8/019` (its "More evidence" section asked for `validateWorkspaceReferences` to join fix steps 1–2; the outcome added only the location).

## Evidence (2026-10-04, `/qa-find-bugs-cli` w8 loop, sweep 4)

Production (`17acbebc5` on main; deployed revision not observed), `bex v0.2.1` (pin Render CLI v2.27.0), workspace `bex-canary`, human device login. No fixtures (validate only).

```yaml
# two-db.yaml — three independent dangling references across two services
services:
  - type: web
    name: qa-bp4-web
    runtime: image
    image: { url: docker.io/mendhak/http-https-echo:35 }
    plan: free
    envVars:
      - key: A_URL
        fromDatabase: { name: qa-bp4-missing-a, property: connectionString }
      - key: B_URL
        fromDatabase: { name: qa-bp4-missing-b, property: connectionString }
  - type: web
    name: qa-bp4-web2
    runtime: image
    image: { url: docker.io/mendhak/http-https-echo:35 }
    plan: free
    envVars:
      - key: C_URL
        fromDatabase: { name: qa-bp4-missing-c, property: host }
```

```text
$ for i in $(seq 8); do bex blueprints validate two-db.yaml -o json | jq -r '.errors[0]|"\(.path) \(.error)"'; done | sort | uniq -c
   7 services[0].envVars[0] fromDatabase references unknown database "qa-bp4-missing-a" in this workspace
   1 services[1].envVars[0] fromDatabase references unknown database "qa-bp4-missing-c" in this workspace
```

Every run exits 1 with exactly **one** entry. The same applies when a dangling `fromDatabase` and a dangling `fromService` (`type: keyvalue`) sit in one file: only the database is reported. With the database reference removed, the Key Value one appears (`services[0].envVars[0]`, line 9).

## Mechanism

- `lego/backend/internal/apps/blueprint_ownership.go:555-578` `validateWorkspaceReferences` calls `resolveExistingBlueprintReferences` once and turns its single `error` into a one-entry list. The out-of-file `fromService … host` loop (`:579-598`) also `return`s on its first miss.
- `lego/backend/internal/apps/deploy.go:1054` `resolveExistingBlueprintReferences` → `resolveUndeclaredDatabases` (`:1104-1130`) and `resolveUndeclaredKeyValues` (`:1146-1168`) each `for name := range needed` over a `map[string]bool` and return on the first unknown/ambiguous name. Map iteration order is randomized, so the reported name varies.
- The apply path shares the resolver (`deploy.go:708`), so a failed `DeployStack`/sync also names an arbitrary one of several missing references.

## Fix

- Make the two resolvers collect every unknown/ambiguous name (and pooler-required refusal) instead of returning on the first. Sort the names so any single-error caller is deterministic. Return them as `blueprintResourceErrors` (the w8/019 aggregate type, whose `Error()`/`Unwrap()` keep apply's single-message behavior).
- In `validateWorkspaceReferences`, map each entry to its referencing `envVars[i]` pointer (`blueprintReferencePointer`), one located error per **reference**: two services referencing the same missing database each get their own entry. Let the host-ref loop collect too.
- Keep the cluster-read-failure fallback (`return nil`) unchanged.
