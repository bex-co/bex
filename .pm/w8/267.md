# After detecting the port a web service listens on, bex restarts the instance with `PORT` set to that port; Render leaves `PORT` at 10000, so an app that also uses `$PORT` crash-loops and never goes live

Why: Render's rule is that `PORT` is 10000 unless the user sets it, and that a server bound to some other port is "usually" detected and used. Detection there changes where traffic goes and nothing the app can see. On bex the detected port is also written into the process's environment: the instance that was found listening is replaced by one started with `PORT=<detected port>`. An app with a fixed public port and an internal listener on `$PORT` runs on its first start and then collides with itself on the second. The crash hint tells the user "the process must listen on $PORT (8080)", a value the platform chose.

**Severity:** minor (a narrow app shape never goes live; every detected-port service sees a `PORT` Render does not give it). **Attribution:** platform runtime (operator environment projection). **Estimate:** ~90m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `d230`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `f609163ada8e`, workspace `bex-canary`, QA human device login.

## Evidence

Two free native Node services, auto-deploy off, no `PORT` variable saved. Times are UTC.

**1. A fixed public port in front of a listener on `$PORT`.** The start command opens an HTTP server on `0.0.0.0:8080` that forwards each request to a second server on `127.0.0.1:$PORT`.

```text

    --runtime node --root-directory examples/runtime-version/node --plan free --build-command "echo build" \
    --start-command 'node -e "<server on 0.0.0.0:8080 forwarding to a server on 127.0.0.1:$PORT>"' --auto-deploy=false --confirm

17:59:18.6  instance …8hqja  QA-BOOT PORT=10000 upstream 127.0.0.1:10000 public 0.0.0.0:8080      (no error)
18:00:16    a second instance …u26mj is created
18:00:23.7  instance …u26mj  QA-BOOT PORT=8080 upstream 127.0.0.1:8080 public 0.0.0.0:8080
18:00:23.8  Error: listen EADDRINUSE: address already in use 0.0.0.0:8080

```

- GraphQL `service`: `port: 8080`, `configuredPort: 8080`, `openPorts: [8080]`, `phase: Deploying`.
- The deploy's `stallReason`: "container exited shortly after start and is restarting repeatedly (last exit code 1) — check the service logs for the crash output. If the crash is a port bind: the process must listen on $PORT (8080)."
- The URL answers 503 "This service's first deploy is in progress."
- The deploy closed `update_failed` at 18:15:41, 16 minutes after its build ended, with the same text as its `failureReason`. The service never served a request.

**2. The plain case, and what stays behind.** An HTTP server on a hard-coded `0.0.0.0:8080`:

```text
17:52:26.6  instance …dqus4  QA-BOOT PORT=10000 listening 8080
17:53:40.0  instance …3rh0n  QA-BOOT PORT=8080 listening 8080
17:54:22    deploy live;  curl → ok envport=8080 local=8080
```

- The process is started twice. This deploy took 3 min 18 s; the deploys before and after it on the same service took 2 min 20 s and 2 min 10 s.
- The start command was then changed to listen on `process.env.PORT`, the documented way, and deployed. The service answered `ok envport=8080 local=8080`: `PORT` stays 8080.

Matching Render in the same sweep: with `PORT=3000` saved the process reads 3000 and is served on 3000; a server on a hard-coded port is detected and served.

## Expected

Render, [Web services](https://render.com/docs/web-services):

- "The default value of `PORT` is `10000` for all Render web services. You can override this value by setting the environment variable for your service in the Render Dashboard."
- "If you bind your HTTP server to a different port, Render is _usually_ able to detect and use it."

So on bex:

- `PORT` is the user's value when they set one, and 10000 otherwise. Detection never changes it.
- Detection changes the port bex routes to and health-checks. The service in case 1 goes live and answers through 8080, with its internal listener on 10000.

## Root cause

1. `appEnv` appends `PORT=<port>` last, where `port` is the serving port (`lego/operator/internal/controller/app_controller.go:5661-5691`; callers `deployment_projection.go:285`, `app_controller.go:5507`, `:6948`). Its comment states the rule: "the port the process reads always equals the port the platform routes to". That was written for a user-set `PORT` (w5/m149), where it restates the user's own value.
2. Detection (w8/177, w8/202) records `status.detectedPort`, and `ServingPort()` returns it when neither a `PORT` variable nor an explicit port is set (`lego/types/v1alpha1/image_network.go:211-224`). The same projection therefore injects the detected port as `PORT`.
3. `PORT`, the container port and the probes are part of the pod template, so adopting a port replaces the instance. The process that was found listening is stopped and started again with a different environment.
4. `status.detectedPort` is cleared only by an explicit port or a `PORT` variable (`detectedServingPort`, `lego/operator/internal/controller/port_detect.go:76-85`). It survives later deploys, so `PORT` keeps the detected value after the app is fixed.
5. `crashLoopMessage` prints "the process must listen on $PORT (%d)" with the serving port (`app_controller.go:6080-6094`), whether the user or the detector chose it.

## Fix

1. Separate the two values. The port bex routes to and probes stays `ServingPort()`. The `PORT` the container receives is the user's `PORT` if set, else an explicit `spec.port`, else `DefaultPort`. A detected port is never written to it.
2. When a later scan finds the listener on the default port, clear `status.detectedPort`.
3. `crashLoopMessage`: when the serving port came from detection, leave out the "must listen on $PORT" sentence.
4. ADR018's `PORT` row says "The process's bound port never differs from the routed port". Keep that for a user-set `PORT` and state the detection case: routed to the detected port, `PORT` unchanged.

Not in this item: adopting a port without replacing the instance. The probe port is in the pod template, so that needs a different health-check path.

## Acceptance

- The service in case 1 goes live. Its URL answers through 8080, and the response shows the upstream on `PORT=10000`.
- A service listening on a hard-coded 8080 with no `PORT` variable: the process reads `PORT=10000`, the URL is served, and `serviceDetails.port` and `openPorts` read 8080.
- The same service changed to listen on `$PORT` and deployed: it listens on 10000 and the port reads back 10000.
- Unchanged: with `PORT=3000` saved, the process reads 3000 and is served on 3000.
- Test: for an App with `status.detectedPort: 8080` and no `PORT` variable, `appEnv` yields `PORT=10000` while the Service, Ingress and probes use 8080.

## Unverified

- Render's side is from its docs; no Render service was run. The docs do not say in so many words that `PORT` stays 10000 after detection. They give 10000 as the default "for all Render web services" and describe detection as something Render does with traffic.
- The first instance in case 1 was never requested: no route points at an instance before its port is adopted. Its log shows the boot line and no error.
- Whether any setting makes the app in case 1 serve on bex. From the code, none does: a saved `PORT` counts as explicit (`explicitServingPort`, `port_detect.go:69-71`), so bex then probes that port and never scans, and the public server on 8080 is not the one on `$PORT`. This was not run.
- Image-backed services with an undeclared listener (w8/205's path) were not run.
