# A native build's log stops after 2 MiB of build-command output, and loses output written faster than 200 KiB/s: BuildKit's default step-log limits clip it, where Render caps no build log

Why: a successful native build that prints more than 2 MiB keeps nothing after that point, not even the later commands' output (`pip install`'s "Successfully installed …"), and a fast burst loses its middle. The log then shows BuildKit's `[output clipped, log limit 2MiB reached]`. Render caps only application-generated lines on running instances (6,000 a minute, render.com/docs/logging), and ADR010 § Per-instance line cap says build logs "stay uncapped".

- **Found by:** `/qa-find-bugs-cli w8` routine run, sweep 617d, 2026-11-19 20:16–20:37 UTC. Production pin `1c63b6fe0a34` (rolled by 19:55 UTC). bex CLI v0.7.0 (Render CLI v2.36.0 pin), QA human device login, workspace `bex-canary`, `-o json`/`text`.
- **Fixture:** free native Python web service `qa-20261119-617d-py` (`srv-dbvl8vp0rfcc73dnr3s0`, `render-examples/flask-hello-world@main`, deleted, `GET` 404). Each case set `--build-command` with `bex services update … --confirm`, then ran `bex deploys create <srv> --confirm`. Lines were counted by paging `GET /v1/logs?type=build` (`limit=100`, forward, `hasMore`/`nextStartTime`), and checked with `bex logs -r <srv> --type build --text '<marker>'`.
- **Evidence (production):**

  | Case | Build command output | Kept in the build log | Log line at the cut |
  | --- | --- | --- | --- |
  | A, `dep-dbvlibb9f6kc73d4acrg`, live | 20,000 lines (`BLD617 seq=N`, about 330 KB) in about 1 s, then `pip install -r requirements.txt` | `seq` 1–12,700 (all stamped 20:18:02), then pip's lines | `[output clipped, log limit 200KiB/s reached]` |
  | B, `dep-dbvlq1r9f6kc73d4adt0`, live | 52,500 lines of 65 bytes (3.4 MB) at about 97 KB/s for 35 s, then `echo BLDEND617C`, then `pip install` | `seq` 1–32,264 only. No `seq` 32,265–52,500, no `BLDEND617C`, no `Successfully installed`; then `==> Build successful 🎉` | `[output clipped, log limit 2MiB reached]` at 20:35:18 |
  | C, `dep-dbvll939f6kc73d4ad0g`, `build_failed` | as B, then `echo BLDERR617 … >&2; exit 1` | `seq` 1–32,264 and 48,469–52,500 (the failure replays about the last 256 KiB at 20:24:51), plus the error lines | `[output clipped, log limit 2MiB reached]` at 20:24:37 |

  A failing build still shows its last lines, so the error survives. A successful one keeps nothing after the first 2 MiB of its build step, and a burst over 200 KiB in the step's first seconds loses lines in any outcome.

- **Cause (code):** the native build runs the build command as a BuildKit `RUN` step inside the build pod's `buildkit` container (`lego/operator/internal/build/build.go`, `buildkit := corev1.Container{…}` at about :1430, image `moby/buildkit:v0.30.0`, :71). Its env (`build.go:1379-1388`) sets only `BUILDKITD_FLAGS` and `BEX_BUILD_COMMAND`, so buildkitd keeps BuildKit's defaults: `defaultMaxLogSize = 2 * 1024 * 1024` and `defaultMaxLogSpeed = 200 * 1024` per step, overridable by `BUILDKIT_STEP_LOG_MAX_SIZE` and `BUILDKIT_STEP_LOG_MAX_SPEED` (`-1` disables), in `util/progress/logs/logs.go:22-23,62-83` at v0.30.0. `checkLimit` allows `ceil(seconds since the step started) × 200 KiB`, capped at 2 MiB, and drops the rest after one clip message (:126). `nativeLogDisplay` (`build.go:185-260`) then shows the transcript it is given. No bex setting names either variable (`rg STEP_LOG_MAX` finds nothing).
- **Fix:** set `BUILDKIT_STEP_LOG_MAX_SIZE=-1` and `BUILDKIT_STEP_LOG_MAX_SPEED=-1` on the `buildkit` container of native builds (static sites included), so the build command's whole output reaches the build log as it is printed. The platform's guard against a runaway build log stays Loki's per-stream limits (3 MB/s, 15 MB burst, ADR010) and the build timeout. Check that those make Alloy back off, not drop, at that rate. Dockerfile builds share the container: Render's Docker build log behavior was not observed, so either keep their defaults with a comment, or lift them too and record it in ADR018. Record the build-log row in ADR018 and ADR010.
- **Blast radius:** every native build and static-site build command (one container spec, `build.go`). Pre-deploy commands run as Jobs, not BuildKit, so they are not affected. Application, request and datastore logs are unaffected.
- **Regression checks:** a unit test that the native build Job's `buildkit` container carries both variables with `-1`, failing on today's spec. On production after the fix, cases A and B on a fresh free fixture keep every `seq` line, `BLDEND617C` and pip's `Successfully installed`, and no `output clipped` line appears. A build printing a few lines reads as before.
- **Unverified:** Render's limit on Dockerfile build output. That raising the limits keeps Loki under its per-stream limit for a pathological build (a build printing at more than 3 MB/s).
- **Dedupe:** `rg -i 'output clipped|STEP_LOG_MAX|log limit 200'` over `.pm` and `docs` finds nothing, and `git log -S STEP_LOG_MAX` is empty. w3/m506 caps application lines only and says build logs are uncapped.
- **Estimate:** ~45m.
