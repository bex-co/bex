# Noninteractive psql silently drops warnings on successful SQL

Why: a SQL command can succeed while PostgreSQL reports a meaningful warning; the CLI captures that diagnostic and then discards it, so automation sees only the command result.

**Status:** todo. **Worker:** worker8. **Severity:** minor. **Attribution:** upstream Render CLI. **Estimate:** 55m (30m upstream patch preparation, 25m command/formatter regression verification). ## Root cause and bounded correction

Pinned `pkg/tui/views/psql.go:45–95`, `ExecutePSQLNonInteractive`, runs the real child command with separate stdout/stderr buffers (`:82–84`). Its nonzero-exit branch includes stderr in the error (`:86–93`), but its successful return (`:95`) retains only stdout in `PSQLResult.Output`. The helper has **one production direct caller**, `cmd/psql.go:103`; that command prints the result at `:108`. `PSQLResult` (`views/psql.go:41–43`) exposes only `output`, and `pkg/text/psql.go:5` renders that field. [Caller and neighbor census](evidence/079/caller-census.json).

Prepare the fix **upstream**: give the helper an explicit diagnostic writer from `cmd.ErrOrStderr()` and forward the captured successful child stderr byte-for-byte. Preserve the existing stdout-only result schema, JSON/YAML parseability, text result, and nonzero-error behavior; do not append warnings to structured stdout or classify a warning as failed SQL. Keep stderr separate from the connection argument and avoid credential-bearing command traces. Bex should adopt the upstream correction through its pin, with no fork, vendor patch or launcher output repair. REST/GraphQL/MCP/dashboard need no contract change.

The affected production path is noninteractive `psql`, across JSON/YAML/text and any successful child that writes diagnostics. `pgcli` uses a separate interactive-only command and does not call this helper. Interactive psql's Bubble Tea execution, PG trust preparation, and error-output behavior are neighbors to preserve; they are not certified by this warning-only reproduction.

The [offline actual-helper reproduction](evidence/079/offline-probe.go.txt), [dependencies](evidence/079/go.mod.txt), [checksums](evidence/079/go.sum.txt), and [results plus independently executed child controls](evidence/079/offline-results.json) make the boundary reproducible without a database. The imported helper is unchanged; only HTTP transport and the child executable are controlled. Dummy metadata and a fake connection argument never reach a real network or SQL client. Four cases establish:

- Exit 0, stdout plus warning stderr: stdout survives, warning disappears.
- Exit 0, notice stderr only: empty result, notice disappears.
- Exit 0, stdout only: existing result preserved.
- Exit 3, error stderr: existing error contains the diagnostic.

Live WARNING was tested. Live NOTICE, interactive execution and real `pgcli` diagnostics remain untested; NOTICE is only an offline controlled-child observation.
