# A service created from a public non-GitHub repo with no branch builds `main`, not the repo's default branch, and a missing non-GitHub repo is accepted

Why: Render's `servicePOST.branch` says "If omitted, uses the repository's default branch", and bex already does that for github.com (w8/m76) and refuses an inaccessible github.com repo at create (w4/105). A GitLab or Bitbucket URL gets neither, so a repo whose default branch is `master` is created on `main` and its first build fails, and a typo'd URL is accepted and fails at clone.

- Severity: minor
- Versions: bex CLI v0.7.0 (Render CLI pin `v1.1.3-0.20261106232710-4fd34231b637`); production pin `98e053468f52`; checkout `72a37bf21`
- Context: 2026-11-20 01:10–01:30 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), QA human device-flow login; routine `cli-qa` (validation and error paths)

## Repro

All REST calls use `?dryRun=true`, which runs every create check and writes nothing (`apps/service.go:2367-2373`). Body (only `repo` varies):

```json
{
  "type": "web_service",
  "name": "qa-20261120-v5-dry",
  "ownerId": "tea-daif693dqjvc73e7as3g",
  "repo": "<repo>",
  "serviceDetails": {
    "plan": "free",
    "runtime": "node",
    "envSpecificDetails": { "buildCommand": "true", "startCommand": "true" }
  }
}
```

| `repo` | Repo's real HEAD (`git ls-remote --symref <repo>.git HEAD`) | bex answer |
| --- | --- | --- |
| `https://gitlab.com/gitlab-org/gitlab-foss` | `refs/heads/master` | 200, `"branch":"main"` |
| `https://gitlab.com/qa-v5-nosuch/nosuch-x9` | does not exist | 200, `"branch":"main"` |
| `https://bitbucket.org/qa-v5-nosuch/nosuch-x9` | does not exist | 200 |
| `https://example.com/a/b` | not a Git host | 200 |
| `https://github.com/octocat/qa-v5-no-such-repo-x9` (control) | does not exist | 400 `repository is not accessible through this workspace's GitHub connections or as public Git; …` |

The CLI sends the same body (`bex services create --type web_service --repo <repo> --runtime node --build-command true --start-command true --plan free --confirm`), so without `dryRun` each 200 row becomes a 201 and a service. Consequence, inferred from the same mechanism: when a branch is missing from the repo, the deploy fails fast with `couldn't find remote ref main`, as seen in an earlier static-site repo-switch sweep (78ec, 2026-11-17). A missing repo fails at clone with git's credential prompt error, which is the misleading message w4/105 removed for github.com.

## Root cause

- `lego/backend/internal/github/service.go:1154-1157`: `ValidateRepo` returns `""`, meaning no opinion, for any URL `githubOwnerRepo` does not parse as github.com.
- `lego/backend/internal/apps/service.go:2424-2433` therefore leaves `appv1alpha1.DefaultBranch` (`"main"`, `lego/types/v1alpha1/app_types.go:455`) for an omitted branch, and checks nothing.
- bex already reads public smart-HTTP advertisements for these hosts (w8/209): `github/public_git.go` `publicGitAdvertisementURL`, `parsePublicGitAdvertisement` (it returns the `symref=HEAD:` target as `head`), `oversizedPublicGitHead`, and the SSRF-safe `anonymousPublicGitClient`.

## Fix

- For a non-github.com https repo, `ValidateRepo` reads the public advertisement once, through the same client, cache and singleflight.
- A readable advertisement returns its `HEAD` symref branch (`refs/heads/X` becomes `X`) as `defaultBranch`.
- An answer that is not a Git advertisement (401, 403, 404, a non-Git content type) is a 400 with the same coded wording as the GitHub refusal: not accessible as public Git.
- A transport failure or 5xx keeps today's behavior and the w4/528 classification: no silent refusal on an outage. Decide whether it is a 503 or no opinion, and test it.
- Blueprint and Public-Git branch resolution (`blueprintBranch`, w4/532) should share the helper, so a GitLab Blueprint with no branch gets its default branch too. Check that path, and change it only if it has the same gap.

## Acceptance

- REST `POST /v1/services?dryRun=true` with `https://gitlab.com/gitlab-org/gitlab-foss` and no branch answers `"branch":"master"`.
- `https://gitlab.com/pages/plain-html` still answers `"branch":"main"`.
- `https://gitlab.com/qa-v5-nosuch/nosuch-x9` and `https://bitbucket.org/qa-v5-nosuch/nosuch-x9` answer 400 and create nothing.
- An explicit `branch` is kept as sent.
- github.com behavior is unchanged.
- Unit tests use a fake advertisement server: HEAD symref, missing repo, a non-Git 200, and a 5xx.
- The same checks hold for GraphQL `createService` and MCP `create_service`, which share `apps.Service.Create`.

## Unverified

- No Render account was used. Render's handling of a missing GitLab repo is inferred from `branch`'s documented default (Render must read the repo to choose it). A Render community report says a create for a repo Render cannot access answers 400 (GitHub, not GitLab).
- No real service was created from these URLs in this run.
- Bitbucket's default-branch advertisement was not read live.
