# CLI scope selectors cannot resolve accepted ID-shaped project and environment names

Why: An accepted project or environment name can become unusable in the CLI's documented ID-or-name flags, interrupting otherwise valid datastore journeys.

**Status:** todo. **Worker:** worker8. **Severity:** minor. **Attribution:** upstream Render CLI resolver. **Estimate:** 55m (35m narrow upstream correction, 20m shared-caller and native acceptance checks; upstream merge/release waiting time excluded). Source: functional CLI sweep150, 2026-10-11. Goal: dependable hosting discovery and selectors under ADR008 / ADR018. Filing only; no product implementation or external submission.

## Wire and root cause

[Complete diagnostic requests and responses](evidence/093/wire.json) retain methods, paths/query strings, statuses, relevant headers and response bodies. Native traffic was not intercepted. These are same-authority diagnostic replays, supported by the pinned request builder:

- `GET /v1/projects?ownerId=tea-daif693dqjvc73e7as3g&name=prj-00000000000000093206&limit=100` returns 200 and the exact owned project in its cursor envelope.
- `GET /v1/environments?name=evm-00000000000000093206&projectId=prj-db60hghtodic73duutjg&limit=100` returns 200 and the exact owned environment.
- Detail GETs using either **name string as an ID** return 404. These ID endpoints behave correctly.
- [Rename/readback captures](evidence/093/renames.json) prove accepted stored names, rather than an assumed naming contract.

Pinned upstream producer/consumer chain, with [numbered source excerpts](evidence/093/source.txt):

1. `pkg/validate/id.go:14–16,37–43` classifies every `prj-` / `evm-` plus 20 lowercase alphanumeric characters as an ID.
2. [`pkg/resolve/resolve.go:315–334`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/resolve/resolve.go#L315) sends recognized project strings to `GetProject` and immediately returns its error. The existing scoped `ListProjectsByName` path is never reached.
3. The same file at `225–287` sends recognized environment strings to `GetEnvironment` and immediately returns its error. The existing scoped exact-name list, uniqueness check and project/workspace validation are never reached.
4. `pkg/project/repo.go:84–94` / `pkg/environment/repo.go:22–32` discard response status information into plain `unexpected response: 404 Not Found` errors when `JSON200` is absent.
5. KV list calls `ResolveScopeInActiveWorkspace` at `cmd/kvlist.go:101`; PG list does the same at `pkg/postgres/service.go:222`. Both therefore fail before listing datastores.

Bex's project create/rename (`lego/backend/internal/projects/service.go:417,508–517`) and environment-name validation (`lego/backend/internal/environments/service.go:1157–1164`, shared by create/update) trim and require a nonempty name; they accept these names. Scoped name filtering is correct. This is not a proposed server detail-endpoint name alias or launcher request rewrite.

[Current upstream main](https://github.com/render-oss/cli/blob/main/pkg/resolve/resolve.go) was also read on 2026-10-11; both relevant ID branches still return immediately on getter errors. The [snapshot and observation metadata](evidence/093/upstream-main.json) are preserved; its commit SHA is unobserved and it was not executed. Tested behavior remains tied to the exact pin.

Follow-up sweep151 provides [baseline ambiguity/scope controls](evidence/093/ambiguity-controls.json): both native clients correctly reject a shared environment name across two own empty projects, accept explicit project or actual environment IDs, and reject inconsistent project/environment pairs (24 checks). After renaming one own environment, three fresh Bex checks correctly resolve the now-unique names. One additional Bex read hit a TLS handshake timeout during workspace retrieval, before a selector response; it is excluded, and four remaining Render recovery reads were unexecuted. The subsequent exact workspace diagnostic succeeds. These are controls on the unchanged resolver, not proof of a repaired build. [Both projects/environments were cleaned](evidence/093/ambiguity-cleanup.json).

## Repair and shared impact

Prepare a narrow upstream correction in the two getters and resolver branches, then consume it through the normal dependency pin once available. Preserve the currently accepted names. No Bex fork, vendoring, request rewrite, new naming restriction, or name reinterpretation in server by-ID endpoints.

- Expose a status-aware 404 sentinel from each affected getter, preserving its existing useful error detail. Fall through from the corresponding ID branch to the existing scoped exact-name path **only** on that getter's 404. Keep successful real-ID precedence.
- Preserve transport errors, 401/403/429/5xx errors and malformed/missing successful bodies as errors; do not fall back on every error or parse error text. `client.ErrorFromResponse` (`pkg/client/client.go:104–132`) does **not** return a typed `ErrorWithCode` for 404, so `errors.As` against that struct is not an existing solution. Avoid changing all global error consumers.
- Keep name uniqueness, active-workspace filtering, and project/environment consistency checks in their existing shared paths.

[Exact production caller census](evidence/093/callers.json): seven `GetProject` call sites and four `GetEnvironment` call sites. Review all 11 when adding status preservation; direct-ID inventory, resource display and datastore create/update paths must retain their semantics. The two failing list consumers and shared KV/PG resource resolvers are enumerated separately. Create/get/update/delete/suspend/resume impact is source-traced, not executed live. Workspace-name classification is a sibling lead, not a confirmed finding here.
