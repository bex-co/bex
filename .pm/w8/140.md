# Render's “allow any IP” datastore rule `0.0.0.0/0` locks out every IPv6-capable client

Why: Render documents `0.0.0.0/0` as the rule that “allows access from any IP address”, and Render Blueprints and the CLI use it as the open-access spelling. On Bex a Postgres or Key Value saved with exactly that rule refuses every IPv6 source. Dual-stack clients connect over IPv6 first, so `bex psql`, `psql` and `redis-cli` by hostname all fail with a bare TLS EOF.

**Severity:** major. **Attribution:** server (datastore SNI front doors). **Estimate:** 50m. **Source:** `/qa-find-bugs-cli` sweeps 1230 and 1232, 2026-10-20 ([1230](evidence/cli-sweep1230/README.md), [1232](evidence/cli-sweep1232/README.md)). **Parent cause:** [w9/m164](../w9/blocked/m164/README.md), the dual-stack allow-list trap, which is blocked on the AAAA decision. This note is the decision-independent piece. It applies whether or not the datastore wildcards keep publishing AAAA.

## Reproduction

- **Context:** production `https://api.bex.co/v1/`, deployed pin `94533d795067`. HEAD checkout CLI at `94533d795` against pinned Render CLI v2.27.0 (`a764810a7682`). Human device-login grant. Workspace `tian-personal` (`tea-da2isimlm39c739m4ofg`), chosen because `bex-canary`'s single Postgres and Key Value slots were held by other fixtures. The client is dual-stack: public IPv4 plus native IPv6.
- **Postgres (sweep 1230):** `bex pg create --confirm --name qa-20261020-9286a3-pg --plan free …` created `dpg-dbbg9e19a20c7385raa0` (PG 18.6). `bex psql <id> -c 'select …'` returned rows. Then:
  1. `bex pg update <id> --ip-allow-list cidr=0.0.0.0/0,description=everywhere --confirm -o json` → exit 0. Readback `ipAllowList: [{"cidrBlock":"0.0.0.0/0","description":"everywhere"}]`.
  2. `bex psql <id> -c 'select 42' -o text` failed for the full 180 s polling window, exit 1: `Error: exit status 2: psql: error: connection to server at "dpg-dbbg9e19a20c7385raa0.db.bex.co" (2a01:4f8:c01e:3d1f::1), port 5432 failed: SSL error: unexpected eof while reading`.
  3. A private probe with the same credentials (password never printed) forced each address. `hostaddr=49.12.20.236` → `t|42`. `hostaddr=2a01:4f8:c01e:3d1f::1` → `SSL error: unexpected eof while reading`. A plain `host=<db host>` connection picks IPv6 and fails the same way.
- **Key Value (sweep 1232):** `bex kv create --name qa-20261020-e09404-kv --plan free --ip-allow-list cidr=0.0.0.0/0,description=everywhere --confirm -o json` created `red-dbbge4h9a20c7385rahg`, available in 56 s. With TLS, SNI and private credentials, `redis-cli -h 49.12.20.236 PING` → `PONG`. `-h 2a01:4f8:c01e:3d1f::1` → `SSL_connect failed: unexpected eof while reading`. `-h <kv host>` → the same EOF.
- **Why the pinned CLI does not catch it:** its pre-check (`pkg/tui/views/psql.go:57–67`, `getUserIP` at `:235–247`) compares the IPv4 that `api.ipify.org` reports with the list, passes, and then hands libpq a hostname that resolves to AAAA as well as A.
- **Controls:** the CLI's own IPv4 gate refuses `cidr=203.0.113.0/24` and `--clear-ip-allow-list` locally (`IP address (<v4>) not in allow list for …`). An HTTP web service with `--ip-allow-list cidr=0.0.0.0/0` (sweep 1231) answers 200 over both `curl -4` and `curl -6`. App hostnames publish no AAAA, so web services are unaffected.
- **Cleanup:** both fixtures were deleted with `bex pg delete` / `bex kv delete --confirm`. GETs return 404, and the workspace's pre-existing service is untouched.

## Expected

[Render Postgres docs](https://render.com/docs/postgresql-creating-connecting): “The default block is `0.0.0.0/0`, which allows access from any IP address.” Render's datastore endpoints are IPv4-only, so on Render that rule admits every client. Bex already treats IPv6 as an extension: its own create default stores `0.0.0.0/0` and `::/0` (`core/cidr.go:209–216`, `postgres/rest.go:228`, `blueprint_generate.go:708`; ADR032 calls the `::/0` twin “a deliberate bex extension … seeding only `0.0.0.0/0` would have silently cut them off”). A user, Blueprint (`ipAllowList: - source: 0.0.0.0/0`), Terraform config or CLI flag that writes Render's single rule gets exactly that cut-off.

## Root cause

`lego/operator/internal/sniproxy/allowlist.go:34–49` (`ParseAllowList`) parses each rule literally, and `AllowedBy` (`:55–64`) tests `prefix.Contains(source.Unmap())`. An IPv6 source is never inside `0.0.0.0/0`. Both front doors call it: `cmd/pg-sni-proxy/main.go:248` and `cmd/kv-sni-proxy/main.go:148`. A refused source gets no route, so the proxy closes after the ClientHello. Clients see a bare TLS EOF and do not fall back to the A record.

## Fix

In `ParseAllowList`, for both the resource layer and the environment layer, a rule whose masked prefix is exactly `0.0.0.0/0` also admits `::/0`. The saved rule and every readback (REST, GraphQL, MCP, dashboard, Blueprint export) stay as authored; this is an enforcement-time equivalence only. Narrower IPv4 rules are not widened; that case stays with w9/m164's decision. Do not change the anti-enumeration behavior of refused sources. Note the equivalence in ADR009, ADR021 and ADR032.

## Blast radius

- Two production callers (the PG and KV SNI proxies) and both layers in each: the resource `ipAllowList` and `environmentIPAllowList`.
- Every write path that can store a lone `0.0.0.0/0` benefits without change: REST create/PATCH, GraphQL, MCP, dashboard, Blueprint create/sync, and the CLI `--ip-allow-list` flags.
- App HTTP ingress is out of scope (no AAAA on `*.onbex.co`, verified live).

## Acceptance

- `sniproxy` unit tests: an IPv6 source is admitted by `[0.0.0.0/0]` in each layer and refused by `[203.0.113.0/24]` and by `[]` (public:false semantics are unchanged). The AND of the two layers still holds.
- Live after deploy, on a fresh free Postgres and Key Value (deleted by ID with a 404 proof), from a dual-stack client: with exactly `cidr=0.0.0.0/0`, `bex psql <id> -c 'select 1'` returns the row by hostname, and `redis-cli --tls -h <kv host> PING` returns `PONG`. Forced-IPv6 probes succeed. With `cidr=203.0.113.0/24` both families are still refused, and readback still shows only `0.0.0.0/0`.

## Unverified

- The environment-layer variant (an environment whose own rules are exactly `0.0.0.0/0`) was not exercised live; it follows from the same `ParseAllowList` call.
- Whether Render itself returns a named refusal rather than an EOF for blocked sources was not observed. Legibility is w9/m164's (b′) work.

## Dedupe

w9/m164 (open, blocked) covers the narrow-rule trap: a caller's IPv4 `/32` with no IPv6 twin. Its tables and DoD do not mention `0.0.0.0/0` or Render's “any IP” meaning; this note is cross-referenced there. w2/038 and w2/m166 added the `::/0` twin to Bex's own defaults only. `git log -S'AllowedBy' -- lego/operator/internal/sniproxy` shows no change for this case, so this is not deploy lag.

## Status — BLOCKED (2026-10-20)

Implemented and unit-tested (source fixed: `sniproxy.ParseAllowList` treats a rule that masks to `0.0.0.0/0` as `0.0.0.0/0` + `::/0` in both layers (enforcement-only; readbacks unchanged; narrower IPv4 rules not widened); `TestRenderAnyIPRuleAdmitsIPv6`; ADR009/021/032). The live acceptance needs the deployed release: release pipeline deploys `pg-sni-proxy`/`kv-sni-proxy`; QA runs the live acceptance from a dual-stack client: a fresh free Postgres and Key Value with exactly `cidr=0.0.0.0/0` answer `bex psql <id> -c 'select 1'` and `redis-cli --tls -h <kv host> PING` by hostname and over forced IPv6; with `203.0.113.0/24` both families are refused; readback still shows only `0.0.0.0/0`; delete both by ID with 404 proofs.
