# Sandbox plans below `2c-4g` run with 2 CPUs and about 4 GiB, and a sandbox can fill its node's memory

Why: a sandbox's plan is its size on Render (`1c-2g` = 1 CPU / 2 GB) and bex bills it by that size, but on production a `starter` (0.5 CPU / 512 MiB) or `1c-2g` sandbox gets 2 CPUs and holds 3.5 GiB. Customers get what they did not pay for, and nothing stops one sandbox from exhausting a shared node.

**Severity:** major (plan limits not enforced: tenant isolation on shared sandbox nodes, and billing weight ≠ resources used). **Attribution:** infrastructure/runtime (OpenSandbox pod resources or the gVisor runtime). bex-api sends the right limits. **Estimate:** ~60m (diagnosis on the cluster + fix + live check). **Source:** `/qa-find-bugs-cli` w8 loop sweep `54a1`, 2026-11-10, released `bex v0.5.0` (Render CLI v2.35.0), production pin `1672bb379`.

## Evidence

Workspace `bex-canary`, human OAuth (the workspace owner's CLI login; the user authorized paid fixtures). Every sandbox was created with `bex sandboxes create --plan <p> --wait --confirm -o json` and stopped afterwards (404).

The in-guest figures (2 CPU / 4 GiB, and 4 CPU / about 7.6 GiB) look like whole-node sizes (a 2 vCPU / 4 GB and a 4 vCPU / 8 GB node), not plan sizes.

## Analysis

- bex-api is correct. `internal/sandbox/models.go:67-75` `planResources` maps `starter` → 500m/512Mi and `1c-2g` → 1/2Gi. `service.go:800-801` puts the plan size on the template. `client.go:167-176` sends `resourceLimits {cpu, memory}` with `resourceRequests` at a quarter (`meter.go:102-119`). The compute meter weight is computed from the same plan size (`service.go:882-887`), so billing assumes the plan.
- **Cause unverified (needs cluster access):** either the OpenSandbox server/controller does not carry `resourceLimits` onto the sandbox pod (`deploy/opensandbox/batchsandbox-template.yaml` has no resources), or gVisor (`runsc`, RuntimeClass `gvisor`) sizes the sandbox from the node and the pod cgroup limit is absent. The `starter` box holding 3.5 GiB without a kill argues that no 512 Mi limit exists on the host either.
- w2/m263 t003 ("plans size the container as named") left its live acceptance box unchecked (`.pm/w2/done/m263/done/t003.md:16`). No in-guest check was ever made.
- Secondary: when a sandbox exceeds its memory, the whole sandbox dies into `errored` instead of the guest OOM-killing the process, and the exec returns gVisor RPC text rather than a named error.

## Fix

1. On the cluster: `kubectl -n <ws>-sandbox get pod -l <opensandbox id label> -o jsonpath='{.spec.containers[*].resources}'` for a fresh `--plan 1c-2g` sandbox, plus its node's capacity. Record the answer here.
2. Make the pod carry the plan's limits (OpenSandbox server request mapping or a controller patch under `deploy/opensandbox/patches/`). Make gVisor size the sandbox from the container limits: runsc reads the pod cgroup when it exists at sandbox creation, so set pod-level limits, or the `dev.gvisor.*` annotations if needed. The guest then sees its plan.
3. With limits in place, exceeding memory should OOM-kill the offending process inside the guest (exit 137 to the exec) and keep the sandbox running. If gVisor cannot do that, return a named error (`SANDBOX_OUT_OF_MEMORY`) instead of urpc text.

## Acceptance

- Live, per plan `starter`, `1c-2g`, `2c-4g`: `bex sandboxes exec <id> -- sh -c 'cat /sys/fs/cgroup/memory/memory.limit_in_bytes; cat /sys/fs/cgroup/cpu/cpu.cfs_quota_us; nproc'` reports the plan's size (`536870912`/`50000`, `2147483648`/`100000`, `4294967296`/`200000`).
- Writing 1 GiB to `/dev/shm` in a `starter` sandbox fails (`dd` error or exit 137), and the sandbox stays usable or ends with a named error.
- Two parallel CPU loops in a `1c-2g` sandbox take about twice as long as one.

## Dedupe

`rg -i 'sandbox.*(cgroup|memory limit|plan size|1c-2g)' .pm docs`: only w2/m263 (done; its live check was never run). No open item. Render reference: `--plan 1c-2g|2c-4g|4c-8g|8c-16g` names the sandbox's compute size (pinned CLI help).
