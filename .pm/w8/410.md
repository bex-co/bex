# Every REST operation shares one 500-a-minute bucket and reports `RateLimit-Limit: 500`, where Render's rate-limiting reference gives per-endpoint budgets (400 GETs, 30 writes and 30 log reads a minute, 20 service creates an hour, 10 deploys a minute per service)

Why: the `RateLimit-*` headers exist so scripts can pace themselves, and bex reports a budget Render does not have. ADR006 and ADR018 call bex's 500 a minute "Render's documented API rate limit", but the page they cite no longer says that, so the parity row rests on a stale reading.

**Severity:** minor (parity: the headers are present and truthful about bex's own limiter, but the budget differs from Render's). **Attribution:** server (bex-api shared limiter). **Estimate:** ~2h. **Source:** routine `cli-qa` sweep r33, 2026-11-22 21:50–22:10 UTC, released `bex v0.9.0` (Render CLI pin `4fd34231b637`), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login. The run was read-only: about 150 requests at human pace, no flood and no 429 provoked.

## Evidence

- **bex, live.** Five back-to-back `GET /v1/services?ownerId=<bex-canary>&limit=1` calls, a `HEAD`, a GraphQL `{ __typename }` and every refusal in the sweep (400, 404 and 405) all carry `RateLimit-Limit: 500`, `RateLimit-Remaining: 498` or `499` and `RateLimit-Reset: 1`. A `POST` refusal reads the same as a `GET`.
- **Render.** [api-docs.render.com/reference/rate-limiting](https://api-docs.render.com/reference/rate-limiting), read 2026-11-22: "Rate limits are shared for a set of endpoints … All but one of these rate limits apply for your user except for deploys which is per service." The table:

  | Endpoints | Budget |
  | --- | --- |
  | `POST /v1/services` | 20 an hour |
  | `PATCH /v1/services`, `POST …/deploy`, `POST …/resume`, `POST …/suspend`, deploy hooks | 10 a minute per service |
  | `POST /v1/customdomain`, `POST /v1/customdomain/verify` | 50 an hour |
  | `POST /v1/jobs` | 100 a minute |
  | `GET /v1/logs`, `/logs/subscribe`, `/logs/values` | 30 a minute |
  | all other `POST`/`PATCH`/`DELETE` | 30 a minute |
  | all other `GET` | 400 a minute |

  The page's example shows `Ratelimit-Limit: 100`, `Ratelimit-Remaining: 99` and `Ratelimit-Reset: 45` on `curl -I https://api.render.com/v1/owners`. The figure 500 does not appear anywhere on the page.
- **bex's records.** `docs/ADR006-bex-api.md:679` says "Render's documented API rate limit is **500 requests per minute per API key** (source: api-docs.render.com/reference/rate-limiting …)". ADR018's "Rate limits" row (`docs/ADR018-render-parity.md:369`) says "Render: 500 req/min per API key … same 500/min default". w8/147 (done) added the headers and wrote "Render's per-endpoint numbers are not adopted by this item". No item has picked them up since.

## Root cause

`lego/backend/cmd/api/config.go:827` sets `BEX_RATE_LIMIT` to 500 a minute, with the burst defaulting to the rate. `api.NewRateLimiter` (`lego/backend/internal/api/ratelimit.go:72`) charges every request it does not classify to the caller's bucket and the workspace bucket (`generalBuckets`, `:128`). `core.SetRateLimitHeaders` (`lego/backend/internal/core/ratelimit.go:153`) reports the tighter of the two. Only sandbox operations are classified (`rl.Operations.RequestBuckets`, `ratelimit.go:97`). w22/m443 adopted Render's per-operation sandbox table that way (ADR018:619).

## Fix

1. Classify the Render-contract REST operations into Render's seven rows through the same `Operations` hook the sandbox table uses. Each row gets its own per-user bucket (a user's API keys and session share it, as on the sandbox rows). The deploy row is keyed per service and also covers bex's deploy-hook limiter (10 a minute per service). The headers then report the row's bucket, so `RateLimit-Limit` reads 400 on a GET and 30 on a write.
2. MCP tools that map one-to-one to a classified operation count against the same row, as the sandbox rows do. GraphQL is the dashboard's transport, so it stays on the general bucket. Record that in ADR018 as a looser variant and file stricter handling separately if it is wanted.
3. Correct ADR006 § Rate limits and the ADR018 "Rate limits" row to quote the current table, and keep `BEX_RATE_LIMIT` as the GraphQL and unclassified budget.

## Blast radius

- Every REST and MCP caller. A script that creates more than 20 services an hour through `POST /v1/services` starts receiving 429s with `Retry-After`. Blueprint applies create services internally, not through that route, so they are not affected.
- The QA routines' REST probes stay well inside 400 GETs a minute. Teammate harnesses that create services in bulk through REST (`scripts/`) need checking.

## Regression checks

- REST `GET /v1/services?limit=1` reports `RateLimit-Limit: 400`, and the 401st GET within a minute answers 429 with `Retry-After`.
- A rejected `POST /v1/env-groups` reports `RateLimit-Limit: 30`, and `GET /v1/logs` reports 30.
- 21 `POST /v1/services` refusals within an hour: the 21st answers 429, in a unit test with a fake clock, never against production.
- `POST /v1/services/{id}/deploys` counts per service: two services each get 10.
- Sandbox rows and GraphQL keep their current budgets.

## Unverified

Render's live headers were not observed (bex has no Render account, see w10/002). Whether Render counts a refused request against its budget, and whether its MCP server shares these rows, are taken from the page's wording only.
