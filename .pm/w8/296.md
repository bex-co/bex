# A Blueprint service with a `generateValue` or `sync: false` variable starts life with a canceled deploy: its seeded values are written after the service exists, which opens a second deploy that supersedes the first

Why: when a Blueprint creates a service, bex writes the service with its literal variables, which opens its first deploy. Only then does bex seed the file's `generateValue` and `sync: false` values into the env store (`SeedEnvVars`). That write is a tracked config change, so it opens a second deploy (`trigger: service_updated`, event `envUpdated: true`), and the first is canceled "Superseded by dep-…".

- **What the user sees:** every such service starts its history with a canceled deploy and an `env_vars_changed` event no one made.
- **Notifications:** a `deploy_ended` with `canceled` fires on the very first deploy.
- **Wasted build:** when the first build has already started, it runs twice. w8/m129 saw this as a side note on the Django template: "the Blueprint create opened two deploys and built twice".

On Render, both kinds of value exist when the resources are created:

- `sync: false` values are prompted for "during the initial Blueprint creation flow" (blueprint-spec, "Prompting for secret values").
- `generateValue` is generated by Render for the new service.

So a new service's history starts with one deploy. 118 of the 171 `render-examples` templates that declare services have at least one service-level `generateValue` or `sync: false` entry (fetched 2026-11-12).

**Severity:** minor. The final state is correct and the second deploy carries the values. The cost is a misleading first deploy, a spurious event and notification, and, when the first build has started, a second build against the platform's four-build cap. **Attribution:** server (bex-api Blueprint apply). **Estimate:** ~60m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `281e`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `33e1b1e6117c`.

## Evidence

Three unmodified Render templates were each planned and approved with `bex ea blueprints create --repo https://github.com/render-examples/<repo> --name qa-20261112-281e-<t> --auto-sync=false -o json`, then `bex ea blueprints approve <exs-…> --confirm -o json`, between 19:43:11 and 19:43:30 UTC. Each Blueprint creates one free Node or Python web service:

| template | env entries | deploys (`bex deploys list <srv> -o json`, newest first) | events |
| --- | --- | --- | --- |
| `elysiajs-hello-world` | literal `BUN_VERSION` | `dep-dbr1dk2585js73afghr0` live, `trigger: other` | `deploy_started`, `build_*`, `deploy_ended` |
| `tanstack-start` | literal `HOST` | `dep-dbr1dni585js73afghu0` live, `trigger: other` | same |
| `mcp-server-python` | `MCP_API_TOKEN` `generateValue: true`, literal `PORT` | `dep-dbr1doqqljrc73co7a80` `service_updated`; `dep-dbr1doiqljrc73co7a7g` canceled, `trigger: other` | see below |

The `mcp-server-python` service's events (`GET /v1/services/srv-dbr1doiqljrc73co7a70/events`, actor fields omitted):

```text
19:43:30  deploy_started  dep-dbr1doiqljrc73co7a7g  trigger {firstBuild: true,  envUpdated: false}
19:43:31  env_vars_changed  {}
19:43:31  deploy_started  dep-dbr1doqqljrc73co7a80  trigger {firstBuild: false, envUpdated: true}
19:43:40  deploy_ended    dep-dbr1doiqljrc73co7a7g  canceled, cancelReason "Superseded by dep-dbr1doqqljrc73co7a80"
19:44:40  build_started   dep-dbr1doqqljrc73co7a80
```

`GET /v1/services/srv-dbr1doiqljrc73co7a70/env-vars` lists `MCP_API_TOKEN` and `PORT` (values not read). The two literal-only services have one deploy each and no `env_vars_changed`. Here the first deploy was canceled while still queued, so it never built.

The second deploy then failed because the template itself is broken. Its unpinned `mcp` resolves to 2.3.0, and since mcp 2.x `from mcp.server.fastmcp import FastMCP` raises `ModuleNotFoundError`. Render would fail the same way. That failure is not part of this note.

## Root cause

- `lego/backend/internal/apps/deploy.go:1153-1156`: `applyStackService` writes the new App with only its literal env.
- `deploy.go:1188-1197`: "Seed sync:false/generateValue vars (seed-once) now that the service exists" calls `s.EnvSeeder.SeedEnvVars` for every created or existing service with `seedLiterals` or `seedGenerates`.
- `lego/backend/internal/secrets/service.go:727-792` (`SeedEnvVars`): writes the env store, then `materializeEnv`. As w4/m148's verification traced, that is `rollApp` → `Rollout.Patch` with `TriggerConfigChange`, a tracked rollout that supersedes the first deploy.
- w4/m148 already moved env-group links into the first App write (`initialEnvGroups`, `WithInitialEnvGroups`) for this reason. Its verification left the seed path as "a tracked rollout instead of the gated untracked group patch; no new seed-plus-group terminal lifecycle is claimed".
- Ordinary create already puts its env into the first write: `writeNewApp` (`apps/service.go:3115-3140`) runs `PrepareCreateSecrets` with `seed.env` (`takeCreateEnvLiterals`, `:2309-2313`), so the first pod sees the values and no second rollout happens.

## Fix

For a service the apply creates (`created` at `deploy.go:1153`), give the first write its seeds, so the first deploy carries them and nothing rolls afterwards:

- **Before `applyStackService` creates the service:**
  - add `seedLiterals` to the create request's env;
  - mint each `seedGenerates` key with `core.GenerateValue` and add it the same way;
  - `takeCreateEnvLiterals` then moves them into `seed.env`, and `PrepareCreateSecrets` stores them in the same mutable env store `SeedEnvVars` writes. Seed-once semantics hold for a new service, which has no prior values.
- **Skip `SeedEnvVars` for that service.** Keep it for services that already existed, where seed-once must not overwrite a live value and a real change still deploys.
- **Generated copies:** check the step after it. `generatedCopies` / `EnvCopier.CopyEnvVars` copies generated values into `fromService … envVarKey` consumers and may roll a newly created consumer the same way. If it does, resolve copies for created consumers into their first write too.
- **Pin it in tests:** a Blueprint apply that creates a service with one `generateValue` and one `sync: false` (approved value) records exactly one deploy (`TriggerCreate`) and no `env_vars_changed`. Its first release's env holds both keys, and a re-apply stays a no-op.

## Blast radius

- **Surfaces:** every path into `deployParsedStack` for a created service:
  - `ea blueprints approve` and its dashboard and GraphQL twins;
  - the first sync of a Blueprint;
  - auto-sync adding a service;
  - `POST /v1/blueprints/deploy`;
  - MCP `deploy` / `create_blueprint` / `sync_blueprint`.
- **Service types:** all five, since `SeedEnvVars` does not branch on type.
- **Unchanged:** services that already exist; a later sync that seeds a newly added key still deploys.
- **Corpus:** 118 of 171 Render templates with services are affected; the list comes from the `render-examples` corpus.

## Regression checks

- **Go:** the test above. Seed-once tests (`TestSeedEnvVarsSeedsOnce`, `TestSeedEnvVarsAllPresentIsNoOp`) stay green, and `TestBlueprintFiveFieldEndToEnd` still serves all five env forms.
- **Production:**
  - Approve a plan of `render-examples/mcp-server-python`. `bex deploys list <srv> -o json` shows one deploy, with no `canceled` row and no `env_vars_changed` event, and `MCP_API_TOKEN` is present.
  - The literal-only control (`elysiajs-hello-world`) is unchanged.
  - Delete the services, then the Blueprints.

## Unverified

- **The `sync: false` path:** not exercised live. That is a `sync: false` value supplied at `approve`, through `--manual-env-vars-file`. It goes through the same `SeedEnvVars` call (`seedLiterals`).
- **The duplicate build:** not reproduced here, because the first deploy was canceled while queued. w8/m129 recorded it on the Django template.
- **Render's deploy row:** what trigger Render records for a Blueprint-created service's first deploy. Render's enum has `blueprint_sync`, but bex maps a first deploy to `other` (w8/058), and no Render capture shows which one Render uses.
