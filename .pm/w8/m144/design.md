# Bounded service filesystems — implementation decision, 2026-10-29

The 2026-10-29 parity decision selects requested-size billing and a real writable bound. It does not require another pricing decision. This implementation uses a bounded ext4 filesystem inside the existing LUKS mapping, with the current 10 GiB provider minimum. It introduces no cloud resource and no tenant capability.

## Checked premise and rejected shortcut

- `lego/operator/internal/controller/disk.go` mounts the PVC directly and raises a request without any filesystem limit. A physical 10 GiB claim already satisfies a 1→5 GiB PVC request, so the existing resizer never has to run for that grow.
- Pinned CSI v2.22.0, revision `2d814c4f36351a6f1652f80657cb3ddd18d51a0b`: `internal/driver/controller.go` returns physical `volume.SizeBytes()` on create/expand; `internal/driver/node.go` ignores the requested capacity when invoking node resize; `internal/volumes/resize.go` uses the full-device `mount.ResizeFs.Resize`. A fixed `fsFormatOptions` or mount flag cannot make all three paths honor per-claim changing logical capacity. `mount-utils` prepends `fsFormatOptions` before the device; ext4's positional block-count argument is after the device.
- A project quota initially appears sufficient: real LUKS/ext4 enforces 1 GiB, grows online to 5 GiB and survives remount. It is **rejected** because capless root outside a pod user namespace can clear `PROJINHERIT`, create a project-0 directory and write outside the quota. The retained probe drops **all** capabilities for the escape. Current `render-v1` production pods are user-namespaced (w6/m151 done); `strict-v1`/`image-v1` remain host-user pods, so quota alone cannot meet every-policy parity. The exact current Render capabilities omit SYS_ADMIN; BuildKit's list must not be confused with it.
- Tenant namespaces enforce baseline Pod Security; adding a privileged/SYS_ADMIN quota helper in the tenant namespace would weaken that established boundary. The existing trusted CSI node already owns the decrypted device, so it is the appropriate place to format and grow the filesystem.

## Concrete owned implementation

`deploy/hcloud-csi/bounded-ext4.patch` applies to that exact reviewed upstream revision. `deploy/hcloud-csi/Dockerfile` fetches a checksum-locked source archive, applies the patch, runs upstream Go tests, and replaces only the driver binary in the digest-pinned original image. Existing cryptsetup/e2fsprogs and compatibility entrypoints are retained. `.github/workflows/hcloud-csi-image.yml` runs a real disposable encrypted-filesystem regression before publishing/signing a multiarch derivative. The existing Helm chart supports independent controller/node image name/tag overrides, including digest in name with an empty tag; hosting the derivative uses existing CI/GHCR and is not blocked on an optional preference or an upstream release.

- The new StorageClass opts into `boundedFilesystem: ext4-v1`. New CSI handles carry an opaque `bounded-ext4-v1:` prefix and provider labels retain the mode. The prefix makes a missing node capacity Secret fail closed during NodeExpand instead of falling back to full-device resize.
- Create/expand responses report requested logical bytes, allowing 1→5 GiB to run the node step inside the unchanged 10 GiB provider volume. ListVolumes reports unknown capacity (CSI's permitted zero value) for these volumes rather than misrepresenting physical provider capacity; authoritative create/expand responses and node filesystem stats retain actual semantics.
- The existing per-disk LUKS Secret also carries nonsecret current mode/logical bytes for node publish/expand. The operator derives this high-water value only from an admitted PVC request: it publishes initial capacity after successful PVC creation, retains the current admitted request before a grow, and raises the bound only after successful expansion admission. A refused quota/class grow cannot authorize larger capacity on a later remount, even when the expansion helper mutated its local object or status records the desired size. The passphrase remains unchanged; a missing encryption key is refused rather than silently provisioning plaintext. No controller/provisioner receives a new passphrase Secret reference.
- The trusted node uses explicit ext4 block counts on initial format and resize after opening/resizing the LUKS mapping. Existing filesystems are inspected; a shrink or a different format is refused without reformatting. LUKS header overhead bounds the top end to available mapping bytes. Legacy non-opt-in CSI volumes retain their original paths.

## Verified local evidence

- `evidence/upstream-linux-arm64-tests.txt`: patched driver, volume and provider-service regression suites pass on Linux/arm64, including create/expand below the provider floor, unchanged non-opt-in list behavior, current/missing/stale node Secret behavior and no provider side effect on invalid capacity.
- `evidence/patched-kernel-test.txt`: the **actual patched volume code** on a disposable arm64 Linux 7.2.9 loop/LUKS1/ext4 volume returns ENOSPC at 1,003,487,232 payload bytes for a 1 GiB filesystem (filesystem metadata consumes the rest), grows online to 5 GiB, preserves data through closing/reopening LUKS and remount, completes a file-level tar/gzip snapshot/restore, refuses shrink, and detects the old full-device resize as a mutation control. The container's exact own mapping/loop device are removed by test cleanup.
- `evidence/rejected-project-quota-proof.txt` retains the failed alternative's observed quota escape; it is not a product mechanism.
- Focused operator disk Secret tests pass: high-water grow, stale reconciliation idempotency, passphrase preservation, uncached tenant Secret access and fail-closed missing-key behavior.

## Remaining worker acceptance

1. Finish the derivative image build on both supported architectures, publish and review the signed digest, then pin both controller and node to it using the existing chart. New bounded StorageClass activation must follow readiness of **all** node/controller driver pods; the old controller rejects new opaque handles, but the old node publisher ignores sizing fields. All old node pods must fully terminate before class activation, not merely coexist with Ready replacements.
2. Enable the bounded class for every workspace's subsequent service-disk creates in the same milestone; no allowlist is planned. Keep the legacy class for immutable existing claims and managed datastores.
3. Inventory existing service disks via read-only metadata/usage before migration. A small existing filesystem needs an explicit offline shrink/rebind to the bounded handle/class with data preserved; do not reformat or shrink a mounted filesystem. If actual used data exceeds the requested capacity, preserve it and name that concrete per-disk gate rather than deleting data to satisfy a limit. No such inventory result has yet been assumed.
4. Run the original real Hetzner/LUKS fixture acceptance: 1 GiB hard-full, 1→5 GiB online grow, retained hashes, remount, operator snapshot/restore (not merely local tar), real kubelet used-byte metrics, unchanged requested-size meter, every authoring/readback surface, owned-fixture cleanup and unchanged quota/baseline. Production credentials or a permitted fixture may become a real gate only after checking them.

Local prototype proof is not a claim that production disks are capped. No production driver, existing disk or active StorageClass setting has been changed at this checkpoint.

## Admission-order regression review — 2026-10-29

Simplify review found that publishing App desired size before PVC expansion could let a remount bypass a quota/class refusal inside the provider’s 10 GiB floor. The node Secret now takes an explicit admitted capacity argument, independently of App spec/status. Regressions exercise refused quota patches (including the mutated in-memory PVC), non-expandable classes, accepted 1→5 GiB growth, repeated remount reconciliation with desired status still at 5 GiB, and create refusal publishing no capacity.

The post-admission Secret write can briefly lag the PVC patch. The CSI node reports this temporary stale bound as `Unavailable`, so kubelet retries online growth after convergence. `FailedPrecondition` is inappropriate here: Kubernetes v1.36.1 `pkg/volume/util/operationexecutor/node_expander.go` treats it as an in-use expansion failure that should not be retried on the node. The node regression verifies stale-bound refusal and successful retry with the converged admitted bound.
