## Objective

Reproduce the README finding where the pod and Cilium can be inspected (dev-8 on the local cluster if it runs sandboxes with Cilium FQDN policies, else production read-only), confirm where `REFUSED` comes from, and pick fix A, B or C.

## Steps

1. Create an allow-list sandbox, run the README repro, and confirm the three search-suffixed queries are refused by the DNS proxy (Hubble or `cilium monitor`), not by kube-dns.
2. Try A on one pod: does a `dnsConfig` in `deploy/opensandbox/batchsandbox-template.yaml` reach the sandbox pod's `/etc/resolv.conf`?
3. If A does not carry through, size B (policy + admission CEL + `gitops-validate.sh`) and C (find the Cilium config owner).
4. Record the choice and the evidence in the milestone README.

## Acceptance criteria

- [x] The source of `REFUSED` is observed, not inferred. (Same resolver, same query: `NXDOMAIN` in an allow-all sandbox, `REFUSED` in an allow-list one; no Hubble read, this host has no cluster credentials.)
- [x] One mechanism is chosen with a recorded reason; the others are noted as rejected or follow-ups. (A; see the milestone README § Mechanism chosen.)
