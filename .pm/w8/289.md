# Saving a setting after a failed build replaces the live instance of a web service, and after a canceled deploy it starts the canceled deploy's start command

Why: Render's [Update Service](https://api-docs.render.com/reference/update-service) "will not be deployed automatically", and since w8/m135 bex says the same: a save through `PATCH /v1/services/{id}` (the pinned CLI's `bex services update`) leaves "the running instance unchanged" ([ADR018](../../docs/ADR018-render-parity.md) § Settings saves through the API save only). That holds on a healthy service. Once its latest build has failed, it does not. The next save rolls the live instance with no deploy row and no event other than `commands_changed`. In the runs below this cost a request, twice raised a Critical `server_failed` "The instance failed its health check" event for a service that answered throughout (once with no `server_available` after it), and once started the start command of a deploy that had been canceled. The user's usual next step after a failed build is to fix the build command with exactly such a save.

**Severity:** major (an unrequested restart of the serving instance, a false Critical event that sends the "Service unavailable" push, emails and webhooks, and a canceled deploy's settings run in production). **Attribution:** platform runtime (operator release selection). **Estimate:** ~90m (the guard, an envtest per service type, the canceled-deploy variant). **Source:** `/qa-find-bugs-cli` w8 loop sweep `11ae`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login. Production pin `f018ce9455c8` (rolled 13:17:23–13:17:59 UTC) for run 0, and `9a5b95e96210` (rolled 12:17–12:18) for runs 1–4. The roll between them changed only events and edge-cache code.

## Expected

A save made through the API never changes the serving instance, whatever the last deploy's outcome. The saved fields wait for the next deploy, and `undeployedChanges` reads true. A canceled deploy's settings and build never run unless a later deploy selects them.

## Root cause

Traced in code; the canceled-deploy step (3) is inferred, not traced.

- **The failed release keeps its generation.**
  - `status.releaseGeneration` moves to the failed deploy's generation when that deploy is adopted (`lego/operator/internal/controller/release_identity.go:532`), and nothing moves it back after the build fails.
  - The serving pod's template label `labelRevision` is `releaseRevision(app)` (`deployment_projection.go:215`, `release_identity.go:768`), i.e. `rev-<failed generation>`, while `status.activeRevision` still names the serving release.
- **Right after the failure, the hold applies.** That pass reaches `buildFromSource`, which stops at the recorded build failure. `holdPendingArtifact` then keeps replicas and routing current but leaves the pod template alone (`app_controller.go:1030`, `:1100`, `:7338`).
- **A save-only PATCH skips that hold.**
  - Every PATCH row except the plan saves with `rollout.WithSaveOnly` (`lego/backend/internal/apps/settings.go:780-784`). That stamps `app.bex.co/pending-source-generation` (`lego/backend/internal/rollout/rollout.go:180-188`).
  - With that stamp newer than the release stamp, `sourceUpdatePending` is true (`release_identity.go:707-714`), and the decision is `sourcePending` (`:483-497`).
  - `reusableArtifactImage` then returns an image directly (`:686-690`), so `buildFromSource` and its hold never run.
  - The release planner has no build-failure input (`release_plan.go:174-197`). It sees a newer release over a template that served and rolls it (`applyServingDeployment`, `app_controller.go:2765`). The new template carries `rev-<failed generation>`, and that label is the new ReplicaSet.
- **The fix exists for static sites only.** `app_controller.go:966-975` (w32/003) says exactly this: "A static site whose latest build failed still names that failed release generation. Dispatching the serving image would publish it again under the failed generation's revision …". It holds only when `app.Spec.Type == TypeStaticSite`. Web, private and worker services, and cron jobs, take the path above.
- **Canceled deploy (inferred).** `reusableArtifactImage` prefers `app.ActiveReleaseConfig()` (`release_identity.go:686-688`). A deploy canceled after its instance started rolling (run 3: build done, stalled on its port check) appears to leave its own release config recorded as active, and the roll above picks it up. Read the App's status after such a cancel to confirm.

## Fix

1. Hold a failed release for every service type, not only static sites. Widen the guard at `app_controller.go:971` so that `decision.sourcePending && releaseHasServed(app) && terminalBuildFailureRecorded(app) && releaseRevision(app) != app.Status.ActiveRevision` sends any type to `holdPendingArtifact`, which already routes static sites, cron jobs and scalable services to their own holds. The sturdier alternative is a build-failure input to `planRelease` so that no path can roll a failed generation. Either way, the template must stay byte-identical until a deploy.
2. On cancel, clear or revert the active release config so that it names the serving release, not the canceled one (confirm the inference above first).
3. Tests: envtests modelled on `static_failed_build_hold_envtest_test.go:186-197` for a web service, a worker and a private service. Failed build, then a save-only build-command change: the Deployment template is unchanged and `activeRevision` stays the serving revision. Add the same with a `preDeployCommand` set (the planner's gate path), and one with a canceled deploy before the failure.

## Blast radius

- **Rolls the same way after a failed build** (inferred from the path): every save that writes the pending-source marker. That is every PATCH row except the plan (build/start command, health check path, pre-deploy command, shutdown delay, root directory, Dockerfile path) and an Update Source (repo, branch, image).
- **Pre-deploy command set:** the roll first runs the failed generation's pre-deploy step against the serving image.
- **Free service asleep:** the save is held while it sleeps, and the roll happens when it next wakes.
- **Not affected** (they write no pending marker, so the normal hold applies): scaling, autoscaling, domains and env-only saves. A later save of another field then puts the failed generation's env copies live.
- Every workspace; REST, MCP and the CLI. The dashboard's GraphQL settings saves deploy explicitly, so they are not affected.

## Acceptance

- Runs 0 and 1 on production: no new instance after the save. The URL answers from the same pod until the next deploy. The only event is `commands_changed`; there is no `server_failed`.
- Run 3 on production: the save starts nothing. `GET …/instances` lists one instance.
- The next deploy after such a save builds and goes live as usual (the w32/003 recovery path, for a web service).
