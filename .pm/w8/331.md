# A manager flag added to the operator manifest reaches production before the image that defines it, so the new manager pods exit until the next image pin

Why: Argo syncs `lego/operator/config` from `main` straight away, but the operator image only moves when a deploy job writes a pin. A commit that adds a command-line flag to `config/manager/manager.yaml` together with the code that defines it therefore runs the new flag on the old binary. The old binary's `flag.Parse()` rejects the unknown flag and exits, so every new manager pod crash-loops until the next pin. Today's instance is `f114fdd9f` (w21/m421 t001), and the CPU-limit raise it carries does not take effect in that window either.

**Severity:** minor (no outage: `maxUnavailable: 0` keeps the old pod serving, but the rollout is stuck and the fix it carries is held back). **Attribution:** deploy ordering. **Unverified:** the pod state itself. This host has no production access (`~/.ssh/bex` is absent), so nothing below was read from the cluster. **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop, 2026-11-16 09:15 UTC, read from `main` while reviewing the next roll.

## Mechanism (code read at `c39a0a7b4`)

- Argo's `bex-operator` Application tracks `targetRevision: main` with `automated: {prune: true, selfHeal: true}` (`deploy/gitops/base/bex.yaml:25`, `:33-36`). The prod overlay points it at `lego/operator/config/prod` (`deploy/gitops/overlays/prod/kustomization.yaml:79-83`). That overlay only adds env vars to the manager, so its `args` come from `config/manager/manager.yaml`.
- The image is pinned separately, by digest, in the same Application: `controller=ghcr.io/bex-co/bex-operator@sha256:8792…` (`bex.yaml:29`). It is written by `chore(deploy): pin platform images …` commits.
- `f114fdd9f` (08:59:13 UTC) added `--pprof-bind-address=127.0.0.1:6060` to the manager's args, and the flag's definition in `cmd/manager/main.go`.
- The last pin is `d3e0b99e4` (06:42:16 UTC, `3c6654df6`), and no pin has landed since. At `3c6654df6`, `parseManagerConfig` defines no `pprof-bind-address` flag and calls `flag.Parse()` with the default `ExitOnError`. A binary built there exits with `flag provided but not defined: -pprof-bind-address`.
- The Deployment rolls with 1 replica, `maxUnavailable: 0` and `maxSurge: 1` (`config/manager/manager.yaml:30-35`; the prod overlay's `replicas: 2` patches are for `bex-objectgw` and `bex-api`). So the surge pod crash-loops, the old pod keeps the old spec (500m CPU), and the rollout waits until the next pin brings a binary that knows the flag.
- The same ordering applies to any Deployment whose manifest comes from `main` while its image comes from a pin: bex-api (`config/api/deployment.yaml`), the activator, and the static server. A strategy that does allow unavailability would make the same commit an outage.

## Fix (target behavior)

A manifest on `main` never passes an argument that the pinned image does not define. Either:

- **Guard (recommended):** `scripts/gitops-validate.sh` (or `ship-gates.sh`) refuses a commit whose operator, bex-api or activator manifest passes a `--flag` that the source at the currently pinned commit does not define. Take the pinned commit from the `pin platform images to <sha>` digest's source commit, or from the pin commit's subject, and grep `flag.*Var(.*"<name>"`. A new flag then ships in two steps: the code first, and the manifest argument once a pin carries it.
- **Or tolerate it:** the binaries parse with `flag.ContinueOnError` and log an unknown flag instead of exiting. That is weaker, because a misspelled flag would then pass silently.

Then record the rule in `lego/operator/AGENTS.md`, next to the codegen and manifest notes.

## Acceptance

- The guard fails on a fixture that adds a flag to `manager.yaml` without a pinned image defining it, and passes once the pinned commit defines it.
- On production, after the next pin, the manager Deployment is fully rolled out (`1/1` updated, 0 restarts), and `kubectl -n bex-system logs` on a new manager pod shows no `flag provided but not defined`. The w21/m421 t001 walk covers this.
