# 039 — A health-check-stalled first deploy fails with the generic "progress deadline" reason or the probe diagnosis, depending on a 900-second race

Why: w4/m112 made stalled rollouts name the failing probe. On a first release the terminal `failureReason` still drops that diagnosis when kubelet restarts the container a few seconds before the deploy settles. The user is left with "rollout did not become healthy" after 15 minutes.

Severity: minor. Attribution: operator (`lego/operator/internal/controller`).

## Evidence (2026-10-03, `/qa-find-bugs-cli` w8 loop sweep 1)

Production, `bex v0.2.1`, workspace `bex-canary`. Fixture: free image web service `srv-db0ab12tm2ss7389qo50`, created as `docker.io/traefik/whoami:v1.10` with `WHOAMI_PORT_NUMBER=10000`. The process listens on 10000, but bex's probe targets `$PORT` 3000, so the startup TCP probe can never pass. Fixture deleted, `GET` 404.

| deploy | rollout started | container (re)starts (app logs) | settled | `failureReason` |
| --- | --- | --- | --- | --- |
| `dep-db0ab12tm2ss7389qo5g` (create) | 06:49:40 | 06:49:46, **07:04:53** | **07:04:57** | `rollout did not become healthy within the progress deadline` |
| `dep-db0ajivfq78s73et1bug` (api) | 07:08:02 | 07:08:00, **07:23:07** | **07:23:01** | `the container is running but its startup health check has not succeeded …: a TCP connect to port 3000. …` |

While each deploy was open, `GET /v1/services/{id}/deploys/{dep}` carried the correct `stallReason`, a TCP connect to port 3000. The same reason reached the `deploy_ended` event only for the second deploy.

## Mechanism

- `deployment_projection.go:131,136,405`: the Deployment's `progressDeadlineSeconds` is `rolloutBudgetSeconds` (900), counted from rollout start. The startupProbe budget is also 900 s (`failureThreshold = 900 / period`), counted from **container** start. When the container starts a few seconds after the rollout, kubelet kills and restarts it a few seconds **before** `ProgressDeadlineExceeded` lands.
- `settleFailedRollout` (`app_controller.go` ~l.2991-3001) recomputes `stuckPodMessage` at settle time. `probeStallMessage` then skips the freshly restarted container, because `probeHadTimeToFail` (l.4759) needs `period + timeout` since `StartedAt`. It returns "", and the generic message is recorded. On a crash-loop-free restart nothing is Waiting, so the CrashLoopBackOff branch does not fire either.
- The diagnosis already exists on the App's Ready condition (reason `HealthCheckFailing`) from the previous reconcile. Settle throws it away.

## Fix

- In `settleFailedRollout`, when `stuckPodMessage` returns "", fall back to the App's current Ready condition when its reason is one of the stall diagnoses (`HealthCheckFailing`, `CrashLoopBackOff`, `ImagePullBackOff`, `InvalidImageName`, `CreateContainerConfigError`). This is "keep the last diagnosis until terminal", the shape `w8/m44` t002's addendum asked for over a prior release.
- Also treat a restarted container (`RestartCount > 0` with `LastTerminationState.Terminated`) as a stall in `probeStallMessage`, even inside the `probeHadTimeToFail` window.
- Optionally give the startupProbe budget a margin past the progress deadline (for example 900 s + 2 periods), so kubelet's kill never precedes settle.
