# A trigger in the seconds after a deploy serves cancels the deploy waiting behind it, which the operator has already started, and then waits about 25 s for it

Why: w8/392's live check saw this twice. The waiting deploy reads `canceled` although its publish most likely runs. The deploy that replaced it reads `Build queued` for about 25 s, where Render, under its Wait policy, runs the waiting deploy and then the new one.

- **Seen.** On pin `89642635b9ce` in `bex-canary`, on a free no-build static site (`bex-co/bex`, `examples/static-site`, publish path `.`), three REST triggers:
  - Deploy A started publishing. B followed 6 s later and answered 202 `queued`.
  - A went `live`, finishing at 09:25:14.79 UTC. Trigger C came 1.4 s later and answered **201**.
  - B closed `canceled` with `deploy_ended` reason `newDeploy` → C. Its log has `==> Deploy queued` and `==> Deploy canceled` and no build line.
  - C logged `==> Build queued` at 09:25:16.18, but `==> Building from …` only at 09:25:42.45, 26 s later.
  - An earlier run gave the same result: a trigger 0.7 s after a serve canceled the waiting deploy, and the new deploy started 23 s after its create.
  - The controls: a deploy from idle starts building about 4 s after its trigger. A deploy waiting behind one in flight starts about 4 s after that one finishes.
- **Likely cause** (from the code; not yet confirmed on the cluster).
  - When A serves, the operator adopts B at once from the pending slot. Since `e737de6976`, `releaseInFlight` (`lego/operator/internal/controller/release_identity.go`) then holds B's adopted publish, as it holds any build.
  - bex-api still marks B as the waiting slot (`deploys.overlap_pending`). The reconciler clears that flag only when it sees the adoption (`TransitionDeploy`, `lego/backend/internal/store/store.go`, "Free the pending slot"), a few seconds later.
  - Within that window, `prepareDeployCreate` (`store.go`) does two things. Its `cancelPendingDeploys` closes B as superseded. Its `appWaitsForActiveDeploy` counts only rows `NOT overlap_pending`, so it finds nothing in flight and creates C as `created` (201).
  - The operator then runs B's publish to the end, so C is adopted only after B serves. That fits C's 26 s wait, about one full publish.
  - The same window looks open for any release the operator pins (source builds since w8/m119, prebuilt images since w4/635, selected releases since w4/661). Only the static case has been measured.
- **Render.** "Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy" ([render.com/docs/deploys](https://render.com/docs/deploys)). Once the deploy ahead ends, the waiting deploy is the one in progress, so a trigger after that waits behind it.
- **Fix direction.** Under the app lock, treat a waiting row whose generation the App's `status.releaseGeneration` has reached as adopted: clear its flag instead of canceling it, so the new trigger answers 202 `queued` behind it. The trigger already reads the App (`rollout.DeployAheadUnadopted`, `lego/backend/internal/rollout/adoption.go`). Keep Override's cancel-and-start.
- **Confirm first.** Use two commits or two publish directories so the served content shows whether B's publish ran. Or read the operator log or the App's `status.releaseGeneration` during the window.

## Acceptance

- A backend test, real DB: a waiting row whose generation the App status has adopted. A new trigger answers 202 `queued`, and the adopted row is not canceled. A waiting row that has not been adopted is still replaced (`newDeploy`).
- Live in `bex-canary` on a free no-build static site. Trigger A, then B about 5 s after A reads `build_in_progress`, then C within about 1 s of A reading `live`. A, B and C all reach `live` in order, and B is never `canceled`. Delete the fixture by ID and confirm the 404.
