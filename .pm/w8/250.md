# The one-step Blueprint create accepts a name another approved Blueprint already has

Why: Render keeps Blueprint names unique among approved Blueprints in a workspace. bex enforces that on Render's create (`POST /v1/blueprints` with `source`) and at approval, but not on its one-step create (GraphQL `createBlueprint`, the earlier REST body, the dashboard's connect flow). Since w8/m153 the dashboard can make several Blueprints from one file, and each defaults to the repository's name, so two copies end up with the same name and are told apart only by their suffix.

**Severity:** minor (parity; confusing lists, no data at risk). **Attribution:** server and dashboard. **Estimate:** ~45m. **Source:** found while implementing w8/m153 (2026-11-11); recorded in ADR049 § "A Blueprint is its id" as the known gap.

## Evidence

- `lego/backend/internal/apps/blueprint_onboarding.go` `CreatePlannedBlueprint` calls `plans.BlueprintNameTaken` and answers `409 BLUEPRINT_NAME_TAKEN`; `ApproveBlueprint` and the planned-sync approval check it again.
- `lego/backend/internal/apps/blueprint.go` `CreateBlueprint` has no such check: `req.Name` defaults to `repoName(req.Repo)` and is stored as given.
- `TestM153_NoCreateSurfaceAnswersAConnectionConflict` (`blueprint_per_source_test.go`) creates five Blueprints from one file; nothing stops two one-step creates from sharing a name.
- ADR049 § "Onboarding" records the rule: "Names — unique among approved Blueprints in the workspace, ignoring case (`409 BLUEPRINT_NAME_TAKEN`)".

## Fix

1. In `CreateBlueprint`, after the retry lookup, refuse a name another live approved Blueprint has with the same `BLUEPRINT_NAME_TAKEN` conflict. Pass the retry target's id as `exceptID`: a retried create must not be refused by the row its own failed attempt left.
2. Dashboard `/blueprints/new`: when the preview reports `matchedResources` (a copy is being made), prefill a name that is free, for example `<repo>-<suffix>`, and show `BLUEPRINT_NAME_TAKEN` next to the name field instead of as a toast.
3. Existing duplicates stay as they are; the rule applies to new creates and renames.

## Acceptance

- A one-step create with a name an approved Blueprint has answers `409 BLUEPRINT_NAME_TAKEN` on REST and GraphQL and creates nothing.
- Repeating a create whose apply failed is not refused by its own row.
- The dashboard's second create of a tracked repo proposes a free name; `yarn lint` and `yarn test` pass.

## Unverified

- Render's rule is taken from ADR049 and the store's comment ("Render: unique among approved Blueprints"), which w2/m256 checked; it was not re-checked on render.com for this note.

## Dedupe

No `.pm` item covers Blueprint name uniqueness on the one-step create. w2/m256 (done) added the rule to Render's create and approval.
