# Since w8/399, a nested `package.json` asking for Node older than 14 fails a Python, Ruby, Go, Rust or Elixir build, which may break existing services on their next deploy

Why: w8/399 (`0170f10098`, parked) made bex find `engines.node` in a `package.json` below the service's Root Directory, and the Node companion of every other runtime (`resolveNativeCompanion`) reads the same file. The 399 worker notes that "a nested `package.json` asking for Node <14 now fails a non-Node build too". Before 399, only a root `package.json` could do that. A Python service whose repo carries an old `docs/package.json` or `legacy-frontend/package.json` with `"engines": {"node": "12.x"}` will deploy today, and will fail once 399 rolls.

- Severity: minor to major, depending on how many existing repos have such a file. It turns a passing build into a failing one with no change by the user.
- Attribution: operator, `lego/operator/internal/build/nativeresolve.go` / `nativeversion.go` (w8/399's search) and `resolveNativeCompanion`.
- Dedupe: w8/398 (Node before 14 still refused) and w8/399 (the search) are the parents. No item covers the companion case.

## Render

Find out what Render does for a non-Node service's Node, from Render docs, Render staff answers, or public build logs, as w8/370 did:
- Does it read `engines.node` at all for a Python, Ruby, Go, Rust or Elixir service, and from which `package.json`?
- What happens when that version is unsupported or very old: fail, warn and fall back, or ignore?

Cite the evidence here.

## Fix

Match Render. If Render ignores `engines.node` for non-Node runtimes, or falls back to its default with a warning, the companion must not fail the build on a nested file (and, if the evidence says so, on a root one either). Keep a primary Node service's refusal as w8/398 set it. Record the rule in ADR060 and ADR018, citing only the user's own decisions as user decisions.

## Acceptance

- A unit test: a Python service with `docs/package.json` `engines.node` `12.x` resolves the way Render's evidence says, and never fails just because of that file unless Render fails too.
- Live in `bex-canary` once the pin carries the fix: a free Python web service from a public repo with such a nested file (or `render-examples/flask-hello-world` with a `rootDir` pointing at a subdirectory that has one, if no public repo fits) builds as Render would. Delete it by ID and confirm the 404.
