# A deploy waiting behind another one starts 50 to 60 seconds after that one finishes or is canceled; Render starts it at once

Why: Under Render's Wait policy a waiting deploy runs as soon as the deploy in progress finishes, and canceling the deploy in progress "immediately kicks off the waiting deploy". bex follows the policy: one deploy at a time, and an intermediate deploy is skipped. But the waiting deploy stays `queued` for most of a minute after its slot is free, because nothing wakes the operator when the release ahead settles. Static sites had the same stall and got a 1-second requeue in w4/m163. Web services did not.

**Severity:** minor (every overlapping deploy takes up to a minute longer; nothing fails). **Attribution:** operator (reconcile wake-up), with the backend's deploy sampling adding to it. **Estimate:** ~90m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `bcc7`, 2026-11-11 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `f609163ada8e`, workspace `bex-canary`, QA human device login.

## Evidence

A free git-backed Node service (`qa-20261111-bcc7-up`). Each deploy was triggered with `bex deploys create <srv>` after saving a new start command. Times are UTC, read from the deploy rows.

```text
Case 1: the deploy ahead goes live
19:21:31.2  deploy A created        19:21:41.1  A build started
19:21:43.5  deploy B → queued
19:21:45.9  deploy C → queued; B → canceled
19:23:23.6  A live
19:24:22.5  C build started          58.9 s after A went live
19:25:52.6  C live

Case 2: the deploy ahead is canceled
19:26:17.5  deploy D created        19:26:41.2  D build started
19:26:47.0  deploy E → queued
19:26:51.1  $ bex deploys cancel <srv> <D>  → "successfully canceled"; D canceled 19:26:51.4
19:27:41.0  E build started          49.6 s after the cancel
19:29:52.5  E live
```

- On the same service with nothing ahead, a build started 10 s (A), 24 s (D), 21 s and 16 s (two later deploys) after its trigger.
- From trigger to live, A took 112 s. From the moment its slot was free, C took 149 s and E took 181 s.

Matching Render in the same run: B was skipped when C arrived, only one build ran at a time, the URL kept answering throughout, and the service ended on C's start command.

## Expected

Render, [Deploys](https://render.com/docs/deploys):

- "Only one deploy can run at a time per service."
- Wait: "Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy:"
- "If you cancel an in-progress deploy while another deploy is waiting, Render immediately kicks off the waiting deploy."

On bex, a waiting deploy's build is dispatched within a few seconds of the deploy ahead going live, failing or being canceled.

## Root cause

1. The backend patches the App with the new release generation when the deploy is triggered and opens its row `queued` (`openRelease`, `lego/backend/internal/deploys/service.go:265-304`; `prepareDeployCreate`, `lego/backend/internal/store/store.go:2684-2712`). No backend worker starts it later. The operator does.
2. The operator holds the newer generation while the current release is in flight (`releaseInFlight`, `lego/operator/internal/controller/release_identity.go:383-397`) and adopts it on the next reconcile pass after that (`:512-536`).
3. Nothing schedules that next pass.
   - The pass that records the release as serving writes status only, and the App watch ignores an update that changes neither the generation, the deletion timestamp nor the finalizers (`lego/operator/internal/controller/event_predicates.go:34-43`).
   - That pass returns `runningRequeue`: the idle-hibernation timer for a Free web service, otherwise 30 s (`lego/operator/internal/controller/app_controller.go:3383-3407`, `childHealthRequeue` `:82`).
   - So adoption waits for an unrelated event. On a Free service the likely one is the old instance exiting when its 60 s drain ends (`drainSeconds`, `lego/operator/internal/controller/deployment_projection.go:493`), which fits the 59 s in case 1.
4. Static sites had this stall. Their publish path requeues after 1 s when `pendingReleaseOwed(app)` (`app_controller.go:4662-4667`, w4/m163). That function has no other caller (`release_identity.go:737-742`).
5. Cancel: `CancelRelease` stamps an annotation and deletes the build Job (`lego/backend/internal/store/release_cancel.go:70`, `:193`). An annotation does not change the generation, so the operator notices on its 5 s build-observe requeue. The rest of the 50 s was not located (see Unverified).
6. The deploy row's `started_at` and its `live` status are stamped by the backend's store reconciler, which runs every 30 s (`defaultResyncPeriod`, `lego/backend/internal/store/reconciler.go:83`). API writes kick an early pass (`Kick`, `:458-466`), but nothing in `lego/backend/internal/deploys` calls it, so a trigger or a cancel is followed at the next 30 s pass.

## Fix

1. Every service type that runs pods: when the current release settles (serving, failed or canceled) and `pendingReleaseOwed(app)`, requeue after 1 s, as the static path does. Only the web path was read; check the worker, private-service and cron paths for the same gap.
2. Cancel: make the cancel wake the operator at once, and find where the remaining time in case 2 goes. Compare `status.releaseStart` of the adopted generation with the build Job's creation time and the Ready condition's `BuildQueued` message.
3. Backend: kick the store reconciler after a deploy trigger and after a cancel, so the rows follow within a second.

## Acceptance

- Case 1 replayed: C's `startedAt` is at most 15 s after A's `finishedAt`.
- Case 2 replayed: E's `startedAt` is at most 15 s after D's `finishedAt`.
- Operator test: an App whose `status.pendingReleaseGeneration` is ahead of `status.releaseGeneration` gets a `RequeueAfter` of at most 1 s from the pass that marks the current release Running.
- Unchanged: an intermediate deploy is canceled when a newer one arrives, and only one build runs at a time.

## Unverified

- Where the 50 s in case 2 goes. From the code, adoption follows the cancel within 5 s. Candidates for the rest: the 30 s build-admission hold while the canceled Job still counts (`app_controller.go:1238-1249`), the canceled build pod holding its node resources until it exits, and the 30 s sampling in root cause 6.
- The timestamps are the backend's samples and can be up to 30 s late, so the true start of C's and E's builds may be earlier than shown. The trigger-to-live comparison (149 s and 181 s against 112 s) has the same sampling on both ends.
- Which event woke the operator in case 1. The old instance's exit is inferred from the timing.
- Paid services, where the steady-state requeue is 30 s, were not run.
- Each case was run once.
- Render's own latency was not measured; its side is from the docs.

## Shipped 2026-11-11 (w8 drain): fixes 1 and 3; the cancel case and the live check remain

- **Fix 1 (operator).** The pass that settles a release now comes straight back when a deploy is waiting in the pending slot: after one second, for a release that serves (web, private, worker), one that failed, and a static site as before (`owedReleaseRequeue`, `lego/operator/internal/controller/app_controller.go`). Without it nothing scheduled the adoption, and the waiting deploy started at the next unrelated event.
- **Fix 3 (backend).** A deploy verb kicks the store reconciler after it opens or cancels a release (`deploys.Service.Kick`, wired to the reconciler's `Kick`), so the row's started time and status follow within a second instead of at the next 30-second resync.
- **Fix 2 not done.** Where the rest of the cancel case's 50 seconds goes was not located (see Unverified above), and making a cancel wake the operator at once needs the operator's handling of the cancel stamp read on a cluster. The kick shortens the backend's share of it.
- **Tests:** `TestTheSettlingPassComesStraightBackForAWaitingDeploy` (the acceptance's operator test), `TestDeployVerbsKickTheStoreReconciler`.
