# A web service with no instance able to serve answers 503, often as Traefik's raw "no available server"; Render documents 502 Bad Gateway for a service whose only instance fails its health checks or that never had a successful deploy

Why: Render's troubleshooting page lists two causes of `502 Bad Gateway` that bex meets every day: "Your service has never had a successful deploy" and "Your service's only instance is failing repeated health checks". bex answers both with `503`. When the only instance of an awake service fails its health check, the 503 is Traefik's own `no available server` in plain text, with no `X-Render-Routing` tag, so it reads like an edge fault rather than the app being unhealthy. ADR007 records bex's first-deploy and failed-first-release answers as "a documented choice, not a parity claim" because "no Render documentation describes it". The troubleshooting page does.

**Severity:** minor (status code and wording; nothing else changes). **Attribution:** platform edge (activator, Traefik routing). **Estimate:** ~90m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `7794`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pins `e7a56b07e0d7` (cases 1 and 3) and `10acf5314735` (case 2, rolled 06:42–06:43 UTC), workspace `bex-canary`, QA human device login.

## Evidence

Free services. `traefik/whoami` answers its `/health` path with whatever status a `POST /health` sets, so the only instance can be made to fail its health check on demand. Times are UTC.

**1. An awake service whose only instance fails its health check** (`qa-20261112-7794-ip`, health check path `/health`, awake and serving for minutes):

```text
06:23:30  POST /health  500            → readiness fails
06:23:42 – 06:25:39  every request: 503  (118 polls), then 200 after the instance is restarted

$ curl -sD - https://qa-20261112-7794-ip.onbex.co/      (same for Accept: text/html, application/json, */*)
HTTP/2 503
content-type: text/plain; charset=utf-8
x-content-type-options: nosniff
content-length: 20

no available server
```

**2. The same, within two minutes of a wake** (06:55–06:57): requests are held, then answered by the activator:

```text
HTTP/2 503
cache-control: no-store
content-type: application/json
retry-after: 5
x-render-routing: no-server

{"error":"service not ready","retryAfter":5}
```

**3. A service whose first deploy failed** (`qa-20261112-7794-np`, start command `sleep 3600`, deploy `update_failed` at 06:20:38):

```text
HTTP/2 503
content-type: text/plain; charset=utf-8
x-content-type-options: nosniff
x-render-routing: no-server
content-length: 20

service unavailable
```

Not run in this sweep: the suspended and maintenance answers. ADR007 records both as 503, which is where Render's page puts them.

## Expected

Render, [Troubleshooting your deploy](https://render.com/docs/troubleshooting-deploys), "502 Bad Gateway": "Your service isn't able to handle a request. Common causes include:" — "Your service has never had a successful deploy", "Your service's only instance is failing repeated health checks", and a server not bound to `0.0.0.0` and `PORT`. Under "503 Service Unavailable" the page lists only a suspended service, a Free service spinning up ("Render displays a loading page while your service starts"), and maintenance mode.

So on bex:

- An awake service with no ready instance answers `502` from bex's own edge response, tagged `X-Render-Routing: no-server`, never Traefik's raw text.
- A service whose first deploy failed or was canceled answers `502`.
- A Free service spinning up, a suspended one and one in maintenance keep `503`.
- A first deploy still in progress: Render's page does not separate it from "never had a successful deploy". Decide between keeping bex's `503` first-deploy page (ADR007 w4/m235) and `502`, and record the choice in ADR007 with this quote.

## Root cause

1. An awake service's route points at its own Kubernetes Service. When its only pod turns unready, the Service has no endpoints and Traefik answers `503 no available server` itself. The activator's readiness hold (w6/m94) only sees requests while the route points at the activator, which is for about two minutes after a wake (case 2).
2. The activator answers a failed or canceled first release with `http.Error(w, "service unavailable", http.StatusServiceUnavailable)` (`lego/operator/cmd/activator/main.go:206-213`, w1/m179, w1/132).
3. ADR007's "First deploy in progress (w4/m235)" says no Render documentation describes these answers, and its routing-tag table lists "An awake App failing its health check (the readiness hold)" as an activator answer. Case 1 never reaches the activator.

## Fix

1. Send an awake web service's unready state to bex's edge: either a Traefik error-page middleware on the service route that maps a no-endpoint 503 to the activator's answer, or a failover service that points at the activator when the Service has no ready endpoint. The answer is `502`, `X-Render-Routing: no-server`, content-negotiated like the other activator answers.
2. A failed or canceled first release answers `502`.
3. Amend ADR007: quote Render's 502 causes, update the routing-tag table, and record the first-deploy-in-progress decision.

## Acceptance

- Case 1 replayed: every request while the only instance is unready answers `502`, tagged `X-Render-Routing: no-server`, with no `no available server` text.
- Case 2 replayed: the same `502`.
- Case 3 replayed: `502`.
- Unchanged: suspended, maintenance and spin-up answers keep `503`.

- A static site whose publish failed.
