# Render's environment-membership API is missing (`POST`/`DELETE /v1/environments/{id}/resources` → 404), and `DELETE` of a non-empty environment succeeds and silently detaches its services where Render's API answers 409

Why: Render's pinned OpenAPI has `POST /environments/{environmentId}/resources` and `DELETE /environments/{environmentId}/resources` (`environmentResourcesPOSTInput: {resourceIds: […]}` — "The ID of an env group, a service, a Postgres database, or a Redis instance"). They are how a Render API client, an agent or IaC tooling moves resources into or out of an environment. Render's `DELETE /environments/{id}` "Requires the environment to be empty", and `DELETE /projects/{id}` requires empty project environments; otherwise both return 409 ([delete-environment](https://api-docs.render.com/reference/delete-environment), [delete-project](https://api-docs.render.com/reference/delete-project)). Bex differs on both counts:

- It serves neither resources route, and exposes bex-only full-replacement routes instead (`PUT /v1/environments/{id}/service-links`, `…/database-links`, `…/keyvalue-links`, `…/env-group-links`).
- It deletes a non-empty environment with 204 and detaches its members.

A Render client cannot manage environment membership at all, and one that relies on the 409 as a safety check deletes environments it meant to keep. ADR032 calls these "explicit differences, not full Render lifecycle parity", with no user sign-off.

**Severity:** minor (API contract; membership can still be set at create time, through the dashboard, or through bex's own routes). **Attribution:** server (`environments` REST adapter). **Estimate:** 2h. **Source:** `/qa-find-bugs-cli` sweep 1323, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1323--environment-api)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `21652364739c`, `bex-canary`. Fixtures were deleted afterwards (service 204 → 404; project and both environments → 404).

1. `POST /v1/projects {…,"environments":[{"name":"staging"}]}` → 201 (`prj-dbcsvebpgbls73dcparg`, `evm-dbcsvebpgbls73dcpas0`). A free static site with no environment is created through `bex services create` (`srv-dbcsvej4qics739psb1g`).
2. `POST /v1/environments/evm-dbcsvebpgbls73dcpas0/resources {"resourceIds":["srv-dbcsvej4qics739psb1g"]}` → **404** `{"error":"not found"}`. The service's `environmentId` stays `null`.
3. `POST /v1/environments {"name":"prod2","projectId":"prj-dbcsvebpgbls73dcparg"}` → 201 (`evm-dbcsvjrpgbls73dcpaug`). The bex route `PUT /v1/environments/evm-dbcsvjrpgbls73dcpaug/service-links {"serviceIds":["srv-…"]}` → 200, and the service's `environmentId` is now that environment.
4. `DELETE /v1/environments/evm-dbcsvjrpgbls73dcpaug` → **204**. The service survives with `environmentId: null`, still in the project.

## Expected

- `POST /v1/environments/{id}/resources {resourceIds}` adds the listed resources (services, Postgres, Key Value, env groups) to the environment, and `DELETE /v1/environments/{id}/resources` with the same body removes them. Responses, refusals and cross-project and cross-workspace checks follow Render's spec. The existing project-join, IP-rule and env-group scope rules apply, as bex's link routes already enforce.
- `DELETE /v1/environments/{id}` on an environment with any member answers **409**, and `DELETE /v1/projects/{id}` with any non-empty environment answers 409, as in Render's API. Render's dashboard deletes contained services on project or environment deletion. The bex dashboard may keep its own confirmed flow, but the REST contract must be Render's.
- Bex's `*-links` routes can stay as bex extensions.

## Root cause

`lego/backend/internal/environments/rest.go:188–237` registers `GET`, `PATCH` and `DELETE /v1/environments/{id}`, the four `PUT …-links` routes and `PATCH …/acl`, but no `…/resources` route. `DELETE` cleans up members and deletes the row (ADR032:27, "Deleting an environment detaches its Postgres and Key Value members … Deleting a project leaves its surviving datastores unassigned"). ADR032:35 records the difference.

## Fix

1. Add `POST` and `DELETE /v1/environments/{id}/resources`. Resolve each ID's kind by prefix (`srv-`, `crn-`, `dpg-`, `red-`, `evg-`) and call the existing per-kind membership service as an add or remove (not a full replacement), all-or-nothing per request.
2. Make REST `DELETE /v1/environments/{id}` and `DELETE /v1/projects/{id}` answer 409 when members exist (Render's error shape). Keep detach-and-delete available to the dashboard and GraphQL through an explicit flag if bex wants it, and record that in ADR032.
3. Add both routes and the 409 to `TestRenderConformance`, then update ADR032 and ADR018's projects row.

## Blast radius

REST environments and projects routes only. GraphQL, MCP and the dashboard keep their flows unless they call REST delete. Callers relying on today's detach-on-delete through REST must empty the environment first.

## Acceptance

- Conformance: the resources routes validate against the pinned spec. A non-empty environment or project delete answers 409.
- Live after deploy: step 2 adds the service (its `environmentId` set), and a `DELETE …/resources` removes it. Step 4 answers 409 while the service is a member. Delete fixtures by ID with 404 proofs.

## Dedupe

`git grep -i 'environments/{id}/resources|preserve-and-detach|add-resources' .pm`: no open item. w4/m214 and w2/m37 shaped today's membership and delete behavior.
