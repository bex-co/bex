# A Blueprint plan never shows a reference variable it will add or change: `fromDatabase`, Key Value and `fromService` host entries are left out of a service's `changedFields`, though the approval applies them

Why: a planned sync is what a user reviews before `bex ea blueprints approve`. For an existing service, bex's plan diffs the file's literal env vars but not its references:

- `fromDatabase` (any property);
- `fromService` to a Key Value with a property;
- `fromService` `host`/`port`/`hostport`.

The approval resolves those references and writes them into the service, then deploys it. So a change of `DATABASE_URL` from nothing (or from another database) to a new database is applied without ever being listed.

ADR049 records the contract (§ w9/094): "On Render a Blueprint applies every change its file declares, and its plan lists each one."

**Severity:** minor. The service's other changes still plan an `update`, so the deploy itself is not hidden. When a reference is the only change, the plan reads `no_changes`, which needs a test (see Unverified). **Attribution:** server (bex-api Blueprint plan). **Estimate:** ~60m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `8f32`, 2026-11-13 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `8acf1d116941`.

## Root cause

- **The plan's target spec has no references.** `lego/backend/internal/apps/blueprint_state_plan.go:210`: the plan reads the service's target spec with `blueprintReadSpec(ctx, withCurrentTier(svc.req, …))`, then probes each declared path, `envVars` included, with `probeBlueprintServiceSpec` (`:236-251`).
- **References are kept apart.** `svc.req.Env` holds only the file's literals. References live in `svc.databaseRefs`, `svc.kvRefs` and `svc.hostRefs`, classified in `deploy.go:2598` (`classifyRefs`).
- **Only the apply resolves them.** `deploy.go:1301-1329` (`resolveServiceRefs`) appends them to `svc.req.Env` from `applyStackServices` (`:1181`), before `applyStackService` writes the service through the same `envVars` applier (`blueprint_plan.go:328-330`, `mergeBlueprintEnv`).
- **The plan never calls it.** So its `envVars` probe compares literals only.
- **Precedent:** the plan already handles one unresolvable case. A copy of a sibling's generated value is named `envVars` with a message (`blueprint_state_plan.go:253-259`, w1/m175). References get no such treatment.

## Fix

Plan references the way the apply writes them.

- **For an existing service,** resolve its references against the plan's view of the datastores, then run the `envVars` probe with them:
  - an existing database or Key Value resolves to its Secret reference, as `resolveDatabaseRef` / `resolveKeyValueRef` do;
  - one the same plan creates resolves to the name its `create` action carries;
  - a `fromService` host target resolves to its planned slug, as the apply's deferred pass does.
- **Reporting:**
  - a reference that adds a key, or points an existing key at another target, names `envVars`;
  - one that leaves a key unchanged names nothing, so an unchanged re-plan stays `no_changes`.
- **If resolution is not possible** without the write: name `envVars` with a message listing the referenced keys, as generated copies do, rather than leaving the change out.

## Blast radius

- **Plan surfaces:** every plan or preview of a sync that adds or retargets a reference on an existing service:
  - `ea blueprints create` (first plan over adopted resources) / `plan` / `update --branch|--path`;
  - REST `POST /v1/blueprints/{id}/syncs` and preview;
  - GraphQL `changedFields`;
  - MCP plan tools;
  - the dashboard's sync review.
- **Unchanged:** the apply, and plans of new services (`create` lists no fields).

## Regression checks

- **Go test:** a plan of an existing service whose file adds `fromDatabase` to an existing database names `envVars`. So do one whose file adds it to a database created in the same plan, and one that retargets an existing reference. An identical re-plan is `no_changes`.
- **Production:** the 8f32 steps. The `update --branch sessionStore` plan's service action lists `envVars` with the other three paths. Do not approve; delete the service and the Blueprint.

## Unverified

- **A reference-only change:** whether a file whose only change is a new reference plans `no_changes`. It follows from the code above (the probe sees no change, and the action becomes `noop`), but no branch with only that change exists in `render-examples` to run it live. If so, a later approval or auto-sync would apply a change that was planned as none.
- **Render's plan format:** how Render's plan names an env reference change, whether `envVars` or per key. Not observed.
