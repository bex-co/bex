# An Elixir 1.12–1.16 service, or a supported Elixir on another OTP major (1.18.4 on OTP 27.3), fails the build, where Render installs any compatible pair from Elixir 1.12.0 and Erlang 24.3.4

Why: Render sets Elixir and Erlang/OTP independently with `ELIXIR_VERSION` and `ERLANG_VERSION`. Its minimums are Elixir `1.12.0` and Erlang `24.3.4`, and its only rule is that the pair must be compatible. bex keeps one image per Elixir line, with one OTP major per line, and only for 1.17–1.20. So Phoenix apps pinned to Elixir 1.14–1.16, or to Elixir 1.17/1.18 on OTP 26 or 27, build on Render but fail version selection on bex.

- Severity: major. Render-valid services cannot build at all. Elixir 1.15/1.16 and OTP 26/27 pins are common in existing Phoenix apps.
- Versions: bex CLI v0.9.0 release binary; production pin `f797f525f5df`. The code is unchanged on main `61bf9154e0`.
- Context: 2026-11-21 09:01–09:06 UTC, `https://api.bex.co/v1/`, QA human device-flow login, isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY. Routine `cli-qa`, run r23, nonce `8555`.

## Render and upstream

- [render.com/docs/elixir-erlang-versions](https://render.com/docs/elixir-erlang-versions), read 2026-11-21: "You can specify different Elixir and Erlang/OTP versions by setting the following environment variables", namely `ELIXIR_VERSION` and `ERLANG_VERSION`. Also: "Your Elixir version must be compatible with your Erlang/OTP version!" (otherwise "your service's builds will fail").
- [render.com/docs/language-support](https://render.com/docs/language-support), "Minimum supported language versions": "Render services cannot use versions of certain languages earlier than those listed below". The rows are Elixir `1.12.0` and Erlang `24.3.4`.
- Elixir's [compatibility table](https://hexdocs.pm/elixir/compatibility-and-deprecations.html): 1.12 supports OTP 22–24; 1.15 and 1.16 support 24–26; 1.17 and 1.18 support 25–27; 1.19 supports 26–28. Elixir 1.18.4 also runs on 28, which is Render's own default pair, 1.18.4 on 28.0.2.
- Published images exist for each pair, for example `hexpm/elixir:1.16.3-erlang-26.0.2-debian-bookworm-20261104`, `1.18.4-erlang-27.3.4.16-debian-bookworm-20260824` and `1.12.3-erlang-24.3.4-debian-bookworm-20260610` (Docker Hub tag search, 2026-11-21).

Expected: `Elixir 1.16.3 (compiled with Erlang/OTP 26)` and `Elixir 1.18.4` on `Erlang/OTP 27`, each building. Both fixtures were deleted by ID (GET 404).

The control in the same run is Render's own documented pair, `ELIXIR_VERSION=1.19.5` with `ERLANG_VERSION=28.3`, on `srv-dc0lqpl2b0us73dobsig`. It logged `==> Using Elixir 1.19.5 on Erlang/OTP 28.3.3`, built `phoenix_hello` with `./build.sh`, and served 200. So the exact-OTP path (w8/197) works inside a line's own OTP major.

## Cause

- `lego/operator/internal/build/native.go:183` gives the Elixir lines as `1.17` (OTP 27), `1.18` (28), `1.19` (28) and `1.20` (29), one OTP each.
- `resolver.elixir` (`nativeversion.go:907`) maps `ELIXIR_VERSION` with `minorLine`, so 1.12–1.16 have no line and are refused through `unsupported`. It then refuses any `ERLANG_VERSION` whose major differs from `line.otp` (`nativeversion.go:924`).
- ADR060's runtime table records the same rule: "`ERLANG_VERSION` must match the chosen line's OTP major".
- The hexpm combination lookup that w8/197 added (`nativecommon_erlang.go:103-127`, `hexpm/elixir:<elixir>-erlang-<otp>-debian-…`) already resolves an exact Elixir on an exact OTP. It is consulted only after the line check passes.

## Fix

- Accept any Elixir from 1.12.0, and any `ERLANG_VERSION` from 24.3.4 that Elixir's compatibility table allows for the requested Elixir minor. Build such pairs on the digest-pinned hexpm image of that combination, through the existing exact-combination lookup.
- With only `ELIXIR_VERSION` outside a line, pick the newest OTP that minor supports, with the newest bookworm/trixie image that carries both.
- Keep refusing, by name, a pair Elixir marks incompatible, such as 1.16 on OTP 27 or 1.12 on 25. That is Render's "builds will fail".
- Keep refusing versions below Render's minimums, for example `ELIXIR_VERSION=1.11.4`.
- Cache keys already include the toolchain (ADR060 "Kept only for the toolchain that built them"), so a NIF built on another OTP is never restored.
- Amend ADR060's Elixir row.
