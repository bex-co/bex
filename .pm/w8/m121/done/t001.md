## Objective

Choose how release N's build reads N's own inputs once the saved spec has moved on, and write it into this task's outcome.

## Context

- `buildFromSource` (`app_controller.go:936`) reads `effectiveDeployRef(app.Spec)` and `effectiveBuilder(app.Spec)`, plus build command, root dir, Dockerfile path and build env, from the saved spec.
- `artifactIdentityInput` (`release_identity.go:144`) already lists exactly the build inputs. Its hash is `status.releaseArtifactFingerprint`, which gives a self-check.
- `pinnableSourceRelease` and `reusableArtifactImage` read `spec.image`. After a repo-to-image switch they skip the build and roll the prebuilt image, or `status.image` while a source update is pending.
- m120's `recordAdoptedRelease` already writes N's release record at adoption. That is a natural home for its inputs.

## Steps

1. Compare two options. (a) Store N's artifact inputs at adoption and overlay them on a held N's build and image selection. (b) Settle N as superseded and close its row canceled with a named reason. Weigh Render fidelity: Render builds a deploy's own commit.
2. Decide how a Dockerfile build's env build args and a native build's env bundle are sourced for a held N: live Secrets, or the adoption snapshots.
3. Decide what a held N adopted before this ships does, since it has no stored inputs.

## Outcome (2026-10-19)

**Option (a): a held release runs as it was adopted.** Render builds a deploy's own commit and lets Update Source wait for the next deploy. Superseding N would cancel a deploy the user asked for, so (b) is rejected.

1. **Capture.** `recordAdoptedRelease` already writes N's release record on the adoption pass. It also stores N's whole adopted `AppSpec` as JSON under an operator-internal data key. Record writes merge that key instead of replacing it, so the later `recordReleasePodTemplate` keeps it.
2. **View.** A held release's view is the saved spec with every field that `appv1alpha1.AppSpecIdentityClasses` (`lego/types/v1alpha1/app_identity.go:49`) does not class `IdentityOperational` copied from the adopted spec. Its artifact and release inputs are N's. Operational fields still follow the saved spec: replicas, suspend, autoscaling, domains and the clone Secret. `Disk` keeps the saved size and N's mount. Self-check: the view's release identity must equal `status.releaseFingerprint`. A view that fails it is ignored.
3. **Decision.** The record is loaded only on in-flight passes (Building or Deploying). `prepareAppReleaseDecision` evaluates `releaseInFlight` and `pinnableSourceRelease` on the view, so a repo-to-image switch still pins repo-backed N. In the `sourcePending` branch a captured release counts as source-fixed. w8/124's `releaseSourceFixed` stays as the legacy rule for releases adopted before this ships.
4. **The pass runs on the view.** When the decision pins a release that has a view, `app.Spec` becomes the view for the rest of that pass, in memory only. Build (`buildFromSource`, `effectiveDeployRef`), image selection (`reusableArtifactImage`), pre-deploy (its command, the m120 gap), runtime projection and record stamps all read N's inputs. The only non-status App writes are the finalizer and deletion paths, and they run before the decision. An envtest asserts the stored spec is untouched after held passes.
5. **Build and pre-deploy env.** `inFlightRelease` reads the live configuration Secrets. For a viewed release it reads N's adoption snapshots (m120 copied them at adoption), so a Dockerfile build's args, a native env bundle and a pre-deploy step see N's values, not the newer saved ones.
6. **Legacy.** A release adopted before this ships has no stored spec and keeps today's behavior (w8/124 and m120).
