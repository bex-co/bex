# Requests reach the app without Render's `X-Request-Start`, so APM request-queue time and queue-time autoscalers (Judoscale, New Relic, AppSignal) read nothing

Why: Render stamps every request with `X-Request-Start: <microseconds since epoch>` at its edge. New Relic, AppSignal, Scout and Judoscale read it to report request-queue time, and Judoscale autoscales on it. On bex the header never arrives, so those agents report no queue time and Judoscale-style autoscaling never fires, with no error anywhere.

Severity: minor (observability/autoscaling integrations silently degraded). Source: `/qa-find-bugs-cli` loop sweep 7d1f, 2026-10-23 UTC, bex v0.3.3, pin Render CLI v2.27.0 `a764810a7682`, `https://api.bex.co/v1/`, `bex-canary`, human device login.

## Evidence

Owned fixture `srv-dbde69vsf6rc738q75j0` (`qa-20261022-7d1f-hdr`, free web, `docker.io/ealen/echo-server:0.9.2`, `PORT=80`; deleted by ID afterwards). The headers the app received for `curl -s https://qa-20261022-7d1f-hdr.onbex.co/h` (client IPs redacted):

```text
accept = */*
accept-encoding = gzip
host = qa-20261022-7d1f-hdr.onbex.co
rndr-id = 486cb6cb-9d42-46d9-b356-2ccb0d2be2bd
true-client-ip = <ip>
user-agent = curl/8.7.1
x-forwarded-for = <ip>
x-forwarded-host = qa-20261022-7d1f-hdr.onbex.co
x-forwarded-port = 443
x-forwarded-proto = https
x-forwarded-server = traefik-6f466bbc9b-79rck
x-real-ip = <ip>
```

Render (`https://httpbin.onrender.com/headers`, a public httpbin on Render, 2026-10-23):

```text
"rndr-id": "637182a2-eef7-4e84",
"true-client-ip": "<ip>",
"x-forwarded-proto": "https",
"x-request-start": "1792729981006921"
```

`1792729981006921` is microseconds since the Unix epoch. The local clock read `1792729981056908` µs right after the response, about 50 ms later. A Judoscale bug about this header's precision on Render ([judoscale-node#123](https://github.com/judoscale/judoscale-node/issues/123)) confirms Render sends it to Docker web services.

## Root cause

The tenant edge plugin `deploy/gitops/charts/traefik-plugins/clientipheaders/clientipheaders.go:86-112` (`sanitizer.ServeHTTP`) already rewrites `Rndr-Id` on every tenant request (w8/m125). Nothing sets `X-Request-Start`, and Traefik has no built-in option for it ([traefik#5063](https://github.com/traefik/traefik/issues/5063)).

## Fix

In `sanitizer.ServeHTTP`: delete any client-supplied `X-Request-Start` (forgeable, as `Rndr-Id` is today), then set `X-Request-Start` to `strconv.FormatInt(time.Now().UnixMicro(), 10)`, Render's format (bare microseconds, no `t=` prefix). Add plugin tests (format and magnitude, a forged value replaced). Record the header in ADR018 beside `Rndr-Id`.

## Blast radius

Every tenant request through the `web`/`websecure` entrypoints (web services, static sites, custom domains; the plugin's existing scope). Platform hosts are unaffected. Apps that ignore the header see no change. The activator wake path must keep the original timestamp, so queue time includes the spin-up, as on Render. Verify the header is set before the activator hop.

## Acceptance

- Plugin unit tests pass. A forged `X-Request-Start: 1` from the client is replaced.
- Live after GitOps syncs Traefik: a fresh owned free echo-server service receives a 16-digit `x-request-start` within ±2 s of the request time. Delete by ID with a 404 proof.

## Dedupe

Searched `.pm` open and done, `docs/` and `deploy/` for `x-request-start`/request queue: none. w8/m123 (client-identity headers) and w8/m125 (`Rndr-Id`) own the same plugin but not this header. The `x-forwarded-server` pod name and the edge-added `accept-encoding: gzip` seen above are not filed (cosmetic).
