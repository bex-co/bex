# `PYTHON_VERSION=3.15.2` fails the build ("not a supported Python version"), though Python 3.15 was released on 2026-10-09 and Render takes "any released version from 3.7.3 onward"

Why: Render's Python contract is open-ended: any released version from 3.7.3 on, with only unreleased versions left to Docker. bex's native Python lines stop at 3.14, because they were set in `w8/m51` (2026-10-05), four days before Python 3.15.0. The toolchain refresh since (`w6/m291`) renewed the digests of existing lines but adds no new ones. A service that asks for a current Python release therefore cannot deploy at all.

**Severity:** major (a released version Render builds fails at version selection, so the service never deploys). **Attribution:** build (operator native toolchain lines). **Source:** `/qa-find-bugs-cli` sweep `0596`, 2026-11-16, production pin `bf2ab888d7dc`, bex CLI v0.7.0, workspace bex-canary.

## Render

[render.com/docs/python-version](https://render.com/docs/python-version) (read 2026-11-16), § Setting Your Python Version:

- `PYTHON_VERSION`: "You can specify any released version from `3.7.3` onward." and "You _must_ specify a fully qualified version (e.g., `3.13.5`) if you use this method."
- `.python-version`: "You _can_ omit the patch version (e.g., `3.13`) if you use this method." and "If you omit it, Render uses the latest corresponding patch version."
- "Render doesn't support unreleased Python versions natively, but you can use them via Render's Docker support."
- **Python 3.15** (endoflife.date, read 2026-11-16) was released 2026-10-09; the latest patch is `3.15.2` (2026-10-25). The official `python:3.15.2-bookworm`, `3.15-bookworm` and `-slim`/`-trixie` images are on Docker Hub (tagged 2026-11-12).
- **Unverified:** a Render build on 3.15.2 itself (this host has no Render account). The target follows the documented contract, and 3.15.2 is a released version.

## bex (production, 2026-11-16 15:21–15:25 UTC)

```sh
bex services create --name <name> --type web_service \
  --repo https://github.com/render-examples/flask-hello-world --branch main --runtime python \
  --build-command 'pip install -r requirements.txt; python --version' --start-command 'gunicorn app:app' \
  --plan free --env-var PYTHON_VERSION=<v> --confirm -o json
bex logs -r <srv-id> --type build --limit 100 -o text
```

| `PYTHON_VERSION` | Build log | Result |
| --- | --- | --- |
| `3.15.2` | `==> PYTHON_VERSION=3.15.2 is not a supported Python version; supported Python lines are 3.7, 3.8, 3.9, 3.10, 3.11, 3.12, 3.13, 3.14`, then `==> Build failed: build failed in the runtime version selection step:` | `build_failed`, about 40 s after the build started |
| `3.14.10` (control) | `==> Using Python 3.14.10 (from PYTHON_VERSION=3.14.10)`, then `Python 3.14.10` | live |

A `.python-version` of `3.15` takes the same path, since version selection is shared, but it was not run.

## Cause (code read at `bf2ab888d7dc`)

- `lego/operator/internal/build/native.go:118-126`: `nativePythonRuntime`'s `lines` end with `{line: "3.14", version: "3.14.10", image: "python:3.14-bookworm@sha256:3fe8…"}`. There is no `3.15` entry.
- Version selection refuses a request outside the reviewed lines, by name, with the list of lines (the message above). That is the right shape for a version that doesn't exist, but 3.15 does.
- `toolchain-freshness.json` tracks one entry per line (`native-python-3-14`, `:330`), so a new upstream line never appears in the freshness review.
- **The other runtimes are not affected today:**
  - Node's newest line, 26, is there (27 exists only as an alpha).
  - Bun's newest line, 1.4, is there; 1.4.4 is Bun's newest release.
  - Ruby, Elixir and Go were not checked against their upstream releases.

## Fix

- Add `{line: "3.15", version: "3.15.2", image: "python:3.15-bookworm@sha256:<digest>"}` to `nativePythonRuntime` and a `native-python-3-15` entry to `toolchain-freshness.json`. Pin the digest in the same review as the existing lines.
- Add `3.15.2` to the modern-Python fixture (`testdata/native-modern-python/check_tool_test.py`), and run the native-common qualification for the new line if production builds through the common base (`w8/m91`).
- **Default:** the no-signal default stays 3.14.10 (Render's default for services created since 2026-11-03), so only an explicit 3.15 request moves.
- **Keep it from recurring:** have the toolchain freshness review list upstream lines that are released but missing (Python's and Node's release indexes are machine-readable), so the next release, such as Python 3.16 in October 2027, is caught when it ships, not by a customer's failed build.
- No REST, GraphQL, MCP or dashboard change.

## Regression checks

- **Production:** the command above with `PYTHON_VERSION=3.15.2` gives `Using Python 3.15.2 (from PYTHON_VERSION=3.15.2)`, then `Python 3.15.2`, and goes live. `.python-version` `3.15` gives 3.15.2. `3.14.10` and no signal (3.14.10, default) are unchanged. `PYTHON_VERSION=3.16.0`, which is unreleased, is still refused by name.
- **Unit:** `cd lego/operator && make test` (`internal/build` line tables and the freshness test).

## Dedupe

- `git grep -iE 'python.{0,20}3\.15|3\.15\.[0-9]'` over `.pm`, `docs` and `internal/build` finds nothing. The lines came from `w8/m51` (`4a1dabce8`, 2026-10-05).
- `w6/m291` (toolchain refresh, pin `e3a57b1c398f`) renewed the existing lines' digests only.
- `w8/332` (Node `lts`) is the same class of a release the line tables did not follow, for an alias rather than a line.

**Estimate:** ~1h (the line, its digest review and the native-common qualification).
