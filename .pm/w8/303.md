# A Blueprint whose service takes a static site's `host` is refused whole, though Render's own `movie-context-provider` template deploys with it

Why: `render-examples/movie-context-provider` is an official Render template. Its README says it is "designed to be deployed to Render with zero configuration" through its `render.yaml`. Its web service takes the address of its static widget site:

```yaml
- key: MOVIE_POSTER_WIDGET_URL
  fromService:
    name: movie-mcp-widget # type: web, runtime: static
    type: web
    property: host
```

bex refuses the whole file at plan time. Nothing is created, so the template cannot be imported at all.

**Severity:** major for the templates that use it: 2 of the 172 `render-examples` root files (w8/292's corpus re-run). **Attribution:** server (bex-api Blueprint parser). **Estimate:** ~1h. **Source:** `/qa-find-bugs-cli` w8 loop sweep `4d5c`, 2026-11-13 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `4c3c68e6b05b`.

## Evidence

`bex ea blueprints create --repo https://github.com/render-examples/movie-context-provider --name qa-20261113-4d5c-mcp --auto-sync=false -o json` exited 1 with `planningOutcome: "failed"` (`exs-dbra5u0v8soc73b22kig`, deleted afterwards; it created nothing):

```json
{
  "line": 34,
  "column": 9,
  "path": "services[0].envVars[7]",
  "severity": "error",
  "message": "service \"movie-mcp-server-yqvt\": envVars[\"MOVIE_POSTER_WIDGET_URL\"] fromService host references \"movie-mcp-widget-yqvt\" which has no network address (only web/private services are addressable)"
}
```

**How Render resolves it.** The template's code shows what it expects to receive. `backend/src/utils/config.ts` (`buildRenderUrl`) turns the value into the widget's public URL:

- a full URL is used as is;
- a hostname gets `https://`;
- a bare label ("my-app") also gets `.onrender.com`. Its comment reads: "Handles Render.com shortcuts (e.g., "my-app" -> "https://my-app.onrender.com")".

So on Render the reference resolves to the static site's public address, either its subdomain label or its full hostname. Which of the two is not observed (no Render account): the code accepts both.

## Root cause

- `lego/backend/internal/apps/deploy.go:2648` (`classifyRef`) refuses `host`, `port` and `hostport` to any declared sibling missing from `idx.addressableServices`, which holds web and private services only. w8/081 added the guard from Render's spec text, which defines the three properties for web and private services, to stop a `port` of `0` or `<slug>:0` on a worker, cron job or static site.
- That reasoning holds for `port`/`hostport` (a static site has no port) and for workers and cron jobs (no address at all). It does not hold for a static site's `host`: the site has a public hostname, and Render's template relies on it.
- `hostReferenceProblems` (`blueprint_ownership.go:716`) applies the same rule to an existing workspace App the file does not declare.

## Fix

Render parity overrides w8/081's reading for this one case (AGENTS.md: amend the earlier decision):

- **Accept** `fromService` `property: host` naming a static site, declared or existing.
- **Resolve** it at apply to the site's public hostname, `RENDER_EXTERNAL_HOSTNAME` (`<slug>.onbex.co`, via the platform-variable path `renderenv.Value`). The template then builds `https://<slug>.onbex.co`. The bare label would make it build an `onrender.com` URL, so the full hostname is the choice that keeps Render's template working on bex.
  - A site with its platform subdomain disabled has no such hostname, so the variable is left out, as a port-carrying reference with no port is (ADR089 D4).
  - The free-plan private-address refusal (`serviceRefFreePlan`) does not apply: this is a public hostname.
- **Unchanged:** `port` and `hostport` on a static site, and all three properties on a worker or cron job, stay refused.
- **Docs:** ADR041 D1 and ADR049 record the static-site `host`, and the w8/081 record gets a pointer.

## Regression checks

- **Go test:**
  - `host` on a declared static site parses, validates, and resolves at apply to `<slug>.<base domain>`;
  - so does `host` on an existing static App the file does not declare;
  - `port`/`hostport` on a static site, and `host` on a worker or cron job, are still refused;
  - `TestBlueprintAddressRefsRequireAnAddressableTarget` moves its static × `host` case into the accepted set.
- **Production:** the 4d5c steps plan and approve (the template is all free: web, static site, Key Value, Postgres, with five `sync: false` keys given marker values). The web service's `MOVIE_POSTER_WIDGET_URL` reads the widget's `<slug>.onbex.co`, and the service goes live. The same walk also serves the owed w8/301 and w8/302 production checks: the template's `PORT: 3000` exercises w8/302 on a re-sync.

## Dedupe

- w8/081 (done) introduced the refusal; this amends it for static × `host` only.
- w8/292 (done) counted the two corpus files as a known class, taking Render's documentation at its word.
- No open `.pm` item covers it.
