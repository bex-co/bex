# A crawler's `GET /robots.txt` wakes a sleeping free web service and gets a 503; Render answers it with a "disallow all" robots file without spinning the service up

Why: [Render's free-instance docs](https://render.com/docs/free) say that while a free web service is spun down, "incoming requests to the path `/robots.txt` automatically receive a standard 'disallow all' response", and "these requests do _not_ reach your service or trigger a spin-up". On bex the request goes down the normal wake path. The crawler gets `503 {"error":"service not ready"}`, which crawlers treat as a temporary error and retry, and the service wakes. Every crawler visit therefore keeps a hobby service cycling awake: it spends compute and gets the service crawled once awake. ADR018's health-paths note lists "no `robots.txt` exception in bex" among the deliberate differences, with no user sign-off.

**Severity:** minor. **Attribution:** platform edge (activator). **Estimate:** 45m. **Source:** `/qa-find-bugs-cli` sweep 1317, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1317--robotstxt-while-asleep)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`. Free image web service (`python:3.12-alpine`, `python -m http.server 10000`, `srv-dbcqnlvt87js73873bo0`), deleted afterwards (204 → 404):

1. Live at 06:23:33Z; one warm `GET /` at 06:23:45Z; then no traffic.
2. `service_hibernated` at 06:39:33Z.
3. `GET /robots.txt` with `User-Agent: Googlebot/2.1 (+http://www.google.com/bot.html)` → **503** in 0.69 s, `Content-Type: application/json`, body `{"error":"service not ready","retryAfter":5}`.
4. `service_woken` at 06:40:09Z.

## Expected

While the service is spun down (hibernated by auto-sleep), `GET` or `HEAD /robots.txt` answers 200 `text/plain` with a disallow-all file (`User-agent: *` / `Disallow: /`). It does not scale the workload, update last-active or write a wake event. Once the service is awake, `/robots.txt` reaches the app as any path does (w4/m162).

## Root cause

`lego/operator/cmd/activator/main.go:203–213`: after the maintenance, suspended, failed-first-release, first-deploy and static branches, every remaining request runs `wakeApp` (`:219`, which writes last-active and patches replicas to 1) and then `writeWakeResponse`. There is no path exception.

## Fix

Before the wake coalescing, if the App is auto-hibernated (spun down, not suspended or in maintenance, which already answer earlier) and the request is `GET` or `HEAD` for exactly `/robots.txt` (no query handling beyond the path), write the disallow-all body with `Cache-Control: no-store` and return. Do not call `wakeApp`. Keep custom domains included: the exception is per host-routed App, so it applies on every host of a sleeping service. Update ADR007 (§ wake) and the ADR018 note.

## Blast radius

Activator wake path for free web services that auto-sleep. Paid services never sleep. Static sites do not route through the wake path. An awake service's own `/robots.txt` is unchanged.

## Acceptance

- Unit: a hibernated App's `GET /robots.txt` → 200 disallow-all with no replica patch and no last-active write. `/robots.txt?x=1` follows the same rule. `/robots.txt` on an awake App reaches the app, and other paths still wake.
- Live after deploy: repeat steps 1–3. Step 3 returns 200 disallow-all, and no `service_woken` follows within 60 s. Delete by ID with a 404 proof.

## Dedupe

`git grep -i 'robots' .pm`: w4/m162 (blocked; health paths) cites Render's `/robots.txt` exception but did not add it. No open item does.
