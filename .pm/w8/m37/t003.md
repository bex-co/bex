## Objective

Ensure acknowledged disconnect ends Blueprint management and cannot be undone by a sync that was admitted earlier.

## Context

- Parent milestone: [w8/m37 — Blueprint lifecycle consistency](README.md), user-approved on 2026-09-08.
- DisconnectBlueprint currently stamps status, reclaims empty groupings, and clears ownership independently of runSync.
- w8/m20 and m23 own the existing cleanup behavior: deployed services/datastores remain; only empty owned groupings and ownership markers are reclaimable.

## Steps

1. Use the same persisted execution boundary for disconnect and sync admission; return a clear busy conflict while an apply still has authority.
2. Invalidate stale or queued execution generations before acknowledging disconnect, and guard all late completion/ownership-stamp paths.
3. Coordinate ownership clearing and safe grouping reclamation with the disconnected state; retain observable retry obligations when required cleanup fails.
4. Exercise a worker paused before apply/completion, then a disconnect and late resume, proving the worker cannot restore management.

## Acceptance criteria

- [ ] After disconnect succeeds, no earlier run can set active/syncing status, restamp ownership, or start another apply step.
- [ ] An active apply produces the documented busy conflict; the caller can retry after it settles.
- [ ] Cleanup never deletes deployed services/datastores or externally referenced/populated groupings.
- [ ] Failed cleanup is observable and recoverable; success is not inferred from a discarded error.
- [ ] Concurrent explicit re-creation cannot give old workers authority over the new generation.

## Out of scope

- Force-canceling remote work without a fence proving it can no longer mutate.
- Resource sync-delete or broad grouping garbage collection.
