## Objective

Admit at most one active apply per Blueprint and update run/Blueprint state coherently, instead of allowing independent replicas to overwrite each other's lifecycle.

## Context

- Parent milestone: [w8/m37 — Blueprint lifecycle consistency](README.md), user-approved on 2026-09-08.
- CreateBlueprint/runSync independently write the Blueprint status and sync row with no admission lease or generation check.
- A process-local mutex cannot coordinate the production bex-api replicas. The store already supplies transactions and bounded worker patterns.

## Steps

1. Add the minimal persisted admission/owner/generation state and required migration/indexes, with IDs minted only through internal/id.
2. Unify create-initial, manual, and automatic run admission; require durable acceptance before apply and a documented busy conflict for competing synchronous calls.
3. Guard apply boundaries and completion by the accepted execution generation; avoid holding a database transaction open across Git or Kubernetes network work.
4. Commit terminal run state and the applicable Blueprint status together; a stale completion cannot overwrite a newer run or a disconnected row.

## Acceptance criteria

- [ ] Two independent API instances cannot interleave apply operations for one Blueprint; unrelated Blueprints remain independent.
- [ ] Admission/persistence failure causes zero workload mutations.
- [ ] A paused old worker cannot complete or apply new steps after losing execution authority.
- [ ] Run and Blueprint terminal state commit coherently, with no success response on failed persistence.
- [ ] Busy outcomes have one coded error through all adapters.

## Out of scope

- A general-purpose orchestration engine or changes to the operator/backend import boundary.
- Exactly-once claims for arbitrary external side effects.
