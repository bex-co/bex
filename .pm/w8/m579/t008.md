## Objective

Verify on production (`https://api.bex.co`) in `bex-canary` once the deployed platform pin carries t001–t003 that two rapid `GET` requests within 150 ms read `RateLimit-Remaining: 399` then `398`, whichever `bex-api` replica serves each request, without provoking a 429.

## Context

- Check that production's newest `chore(deploy): pin platform images to <sha>` commit on `origin/main` is a descendant of the code commits from t001–t003 (`git merge-base --is-ancestor <commit> <sha>`). If production does not carry them yet, park the milestone in `.pm/w8/blocked/m579/` with ``pin must carry `<sha>` `` so `/loopx w8` resumes automatically once the roll lands.
- Sign in with `bash scripts/qa-login.sh` using an isolated `bex` CLI config, and log out both the CLI config and any Kratos jar before deleting them.
- Workspace `bex-canary` only. Do not flood production and do not provoke a 429.

## Steps

1. Confirm production's pin carries t001–t003 and record the pin SHA.
2. Authenticate to `bex-canary` as the QA user (API key or device-login bearer, not a Kratos session, so the Render REST rows apply).
3. Send two back-to-back `GET /v1/services?ownerId=<bex-canary>&limit=1` requests within 150 ms on separate TCP connections (so Traefik can route them across both replicas), and inspect `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` on both responses. Repeat a small handful of pairs (e.g. 5 pairs, spaced ≥ 2 s apart so the bucket refills to 400 between pairs) to make hitting both replicas overwhelmingly likely while staying far below any 429.
4. Confirm every pair reads `RateLimit-Limit: 400` and `RateLimit-Remaining: 399` then `398` (never `399` twice within 150 ms), and no 429 occurs.
5. Also run one read-only control (`GraphQL { __typename }`) confirming `RateLimit-Limit: 500`.
6. Log out the isolated CLI and any Kratos jar, delete temporary auth files, and record the pin and observations in `.pm/w8/m579/README.md` under the public-board rules.
