# On a Hobby workspace, an unfiltered `bex logs -r <id>` still returns HTTP request lines; only an explicit `--type request` is refused (w8/m138 gate incomplete)

Why: w8/m138 made HTTP request logs a Pro-and-higher feature, as on Render. `requireRequestLogsPlan` refuses `type=request` and is meant to make an all-types query "silently lose its request lines". In production the all-types query, which is the default `bex logs -r <id>`, dashboard and MCP call, still returns request entries on a Hobby workspace. The gate is bypassed by the most common read.

Severity: minor (plan gate incomplete; no data exposure beyond the tenant's own logs). Source: `/qa-find-bugs-cli` loop sweep q9r2, 2026-10-24 UTC, bex v0.3.3, pin Render CLI v2.27.0 `a764810a7682`, platform pin `ba5ad0e65498` (includes `a836d2d0d`, w8/m138), `https://api.bex.co/v1/`, `bex-canary` (Hobby), human device login.

## Evidence

Owned free web service `srv-dbe7n3aei42s73atad3g` (`qa-20261024-q9r2-rl`, `traefik/whoami`, deleted by ID afterwards), three `GET /rl-q9r2` requests, then after 30 s:

```text
$ bex logs -r srv-dbe7n3aei42s73atad3g --type request --limit 5 -o json
Error: error listing logs: received response code 400: bad request: type: HTTP request logs require the Pro plan or higher; this workspace is on Hobby
$ bex logs -r srv-dbe7n3aei42s73atad3g --limit 20 -o json        → entries by label type: {"request": 3, "app": 1}
$ bex logs -r srv-dbe7n3aei42s73atad3g --type build --limit 3 -o text → build lines (control)
```

## Root cause

`lego/backend/internal/logs/loki.go:503-511` (`lokiTypeMatcher`): when `q.Types` is empty it returns the app+request union (`container=~"app|"`) before consulting `q.wants`, so the `noRequest` flag set by `requireRequestLogsPlan` (`internal/logs/service.go:467-476`) is never applied. `wants()` honors `noRequest` (`service.go:400-403`), but the empty-types fast path bypasses it. Other empty-types paths (the pod-log/live-tail path, `liveSubscribable`, per-line filters) may share the shortcut and need the same check.

## Fix

In `lokiTypeMatcher`, return the app-only matcher (`container="app"`) when `q.noRequest` is set and `q.Types` is empty. Audit every `len(q.Types) == 0` shortcut in `internal/logs` (Loki query, live tail, pod-log fallback, GraphQL/MCP adapters) so `noRequest` drops request lines everywhere. Add a test: Hobby plan + empty types → no request entries; Pro → request entries present.

## Acceptance

- Unit/integration: a Hobby-plan all-types query returns no `type=request` entries on the Loki path and the live tail. Pro returns them. Explicit `type=request` on Hobby is still the 400.
- Live after the backend deploy: the repro's unfiltered `bex logs -r <id>` on `bex-canary` shows app lines only. Delete the fixture by ID with a 404 proof.

Defect in w8/m138 t005 (blocked, awaiting closeout). Its DoD checks only the explicit `--type request` refusal. Not filed elsewhere.
