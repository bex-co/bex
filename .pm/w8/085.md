# Interactive datastore errors omit their underlying detail

Why: A failed native datastore session returns to a generic error panel even though its error object contains the process failure detail.

**Status:** todo. **Worker:** worker8. **Severity:** minor. **Attribution:** upstream Render CLI. **Estimate:** 50m. Correct the shared error view upstream and adopt through the normal pin workflow; no Bex fork or server change.

## Reproduction and evidence

Functional CLI QA, 2026-10-11 UTC, production `https://api.bex.co/v1/`, isolated human OAuth in `bex-canary` / `tea-daif693dqjvc73e7as3g`. Released Bex v0.3.2 and unmodified Render v2.27.0 at `a764810a768202704e7206eb7b87a47211fcd98e`; Bex source HEAD `84c2e4bfe114fba4459d86421de18269ba6a6d4c`. Backend/operator revision unobserved. Both clients targeted Bex.

Fresh owned Free Key Value `red-db5n4789n5bc73aqij2g`, `qa-20261011-069d45-kvexit`, reached `available` with `noeviction` and `journal_snapshot`. Native creation exited 0 in 0.555s. After setting the unique harmless nonnumeric value:

```sh
bex kv-cli red-db5n4789n5bc73aqij2g -- --raw SET qa106:069d45 QA106_069d45_not_a_number
bex kv-cli red-db5n4789n5bc73aqij2g -- --raw -e INCR qa106:069d45
```

The real `redis-cli -e` prints `ERR value is not an integer or out of range` and fails. The CLI resumes its interactive screen with a bordered panel containing only **An error occurred while running kv-cli**, followed by blank detail. The underlying process error, `exit status 1`, is absent. Bex and Render reproduce in separate native processes, 1.818s and 1.314s respectively including deliberate Ctrl+C dismissal. Both then exit 0; this interactive dismissal is **not** filed as incorrect child-status propagation. The Redis diagnostic was printed earlier in the terminal, so this finding does not claim it was never emitted. Standard streams share the PTY; native HTTP requests were not intercepted. [Full commands and terminal results](evidence/085/native.json).

GET before and after each failed INCR returned the exact original value. SET returned OK; PING returned PONG. No value loss or runtime failure was observed.

## Root cause and shared callers

- The pin's `pkg/tui/views/rediscli.go:78–83` wraps the process failure in `UserFacingError{Title: ..., Err: err}`, leaving `Message` empty.
- `pkg/tui/exec.go:34–72` passes the child failure through that wrapper and emits `ErrorMsg`. `pkg/tui/stack.go:182–198` pushes `NewErrorModel` and remains interactive for dismissal.
- [`pkg/tui/error.go:52–78`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/tui/error.go#L52) reads only `Title` and `Message` for a matched `UserFacingError`. It has no fallback for empty Message with a nonnil Err. In contrast, `UserFacingError.Error()` at `pkg/tui/stack.go:22–33` already returns that underlying error string.
- Exactly **two Err-valued constructors** exist in the tested source: this Redis wrapper and `pkg/tui/views/psql.go:138–145`, shared by interactive psql and pgcli. Those Postgres paths were not tested live here. SSH includes the underlying error in an explicit Message; missing-executable diagnostics also supply Message. Noninteractive psql uses a separate buffered result/error path. [Caller census](evidence/085/caller-census.json).

An [actual imported view probe](evidence/085/view-probe.go.txt), [module](evidence/085/view-probe-go.mod.txt), [checksums](evidence/085/view-probe-go.sum.txt) and [five results](evidence/085/view-probe.json) confirm that Title+Err loses detail, while an explicit Message and an ordinary unwrapped error display it. A title-only control remains valid. A fifth case uses the real ExitError from an ordinary local `/usr/bin/false` child and confirms that its `exit status 1` string is also absent from the panel. The probe calls the existing imported view; it implements no fix. [Exact later upstream commit review](evidence/085/upstream-review.json) finds the same Message-only consumer at `c4d106cfdaf8eec6d23475155e43f4baeeed2013`; this is source review, not a claim about the latest release or a later native test.

## Proposed work and acceptance

1. **Shared view correction (10m):** upstream, preserve explicit Message and Title; when Message is empty and Err is nonnil, display Err.Error(). Keep title-only errors and unwrapped errors working. This fallback exposes the process error already in the object; it does not recover Redis/SQL text from child stderr or change interactive exit behavior.
2. **Behavioral coverage (20m):** render the actual view with a child ExitError, wrapped UserFacingError, explicit Message plus a different Err, ordinary errors and title-only errors. Prove the current failing branch becomes visible and explicit Message retains precedence. Recheck both datastore wrappers, SSH and missing-executable messages.
3. **Contract and adoption review (10m):** prepare upstream correction and assess the exact adopted pin. Keep native child passthrough, TTY guards, ordinary successful sessions and the noninteractive psql result path unchanged. REST/GraphQL/MCP/dashboard require no contract change. External submission and pin/release work need separate authorization.
4. **Closeout (10m):** after adoption, repeat the failing INCR and GET/PING controls through both clients with an owned Free fixture; verify the panel contains its underlying process error.

Board searches across open, blocked and done items for ErrorModel, the wrapper names, blank error detail and interactive datastore errors found no matching item. w8/blocked/079 covers successful noninteractive psql stderr loss; w8/blocked/066 covers an empty connection handoff; w8/done/015 covers a selector panic. None changes this shared panel consumer. No forced network/auth failure or foreign resource was used for this ordinary command-error reproduction.
