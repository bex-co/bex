# A second database in a Postgres instance is outside logical exports and Insights, and no surface names it

Why: since w8/m155 the default user can `CREATE DATABASE`, as on Render. The instance's physical backups, point-in-time recovery, storage metering and suspend/resume are cluster-wide and cover the new database. Two things are not, and one is unchecked: a logical export dumps the primary database only; REST, GraphQL, MCP and the dashboard show one `databaseName`; and whether Insights' top queries include statements run in another database has not been checked. A user who keeps real data in a second database may believe an export contains it.

**Severity:** minor (a new capability's edges; no data is lost, an export is incomplete without saying so). **Attribution:** server (bex-api) and operator. **Estimate:** ~60m to decide and say it; more to cover every database. **Source:** found while working w8/m155 t003, 2026-11-11.

## Evidence (read from the code; not yet run on a cluster)

- `lego/operator/internal/controller/database_exports.go:88-89`: the export Job runs one `pg_dump` into `/work/${EXPORT_DIRECTORY}/${PGDATABASE}`, and `PGDATABASE` is the primary database from the connection Secret.
- `lego/operator/internal/controller/database_controller.go:602-604`: `pg_stat_statements` is created once, at bootstrap (`postInitSQL`). Its counters are cluster-wide, but the view is read through the primary database's connection; whether `top-queries` filters by database, and so hides statements run elsewhere, was not checked. `pg_stat_activity` is cluster-wide. pgvector is installed per application database (ADR009, w8/m84), so a database the user creates does not have it until they run `CREATE EXTENSION`.
- The API's `databaseName` and every connection string name the primary database. Render tells users to "substitute your new database's name as the final component"; bex's connection strings can be edited the same way.
- Render (render.com/docs/postgresql-creating-connecting, read 2026-11-11) says nothing about what its logical exports or its dashboard cover for additional databases.

## Fix

1. Say it where the user looks: the export dialog and `POST …/export` description ("exports the primary database `<name>`"), and the docs page for databases.
2. Decide whether an export should cover every database in the instance (`pg_dumpall`-style, or one dump per database). Check what Render's export contains for an instance with two databases before choosing; that needs a Render account.
3. Insights: check what `top-queries` and the size views report for a second database, then either cover it or say that they read the primary one.

## Acceptance

- The export surface names the database it exports, on REST, GraphQL, MCP and the dashboard.
- ADR009 states what a second database is and is not covered by, compared with Render where Render documents it.

## Dedupe

w8/m155 lists these under "What a second database is not covered by". No other `.pm` item covers additional databases.
