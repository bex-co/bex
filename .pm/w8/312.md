# A refused sandbox create answers bex's own codes, `SANDBOX_TIMEOUT_INVALID` and `SANDBOX_PLAN_INVALID`, or none for a name over 64 characters, where Render's contract names `invalid_timeout_seconds`, `invalid_sandbox_plan` and `invalid_sandbox_name`

Why: Render's pinned OpenAPI (`render-public-api-1.json`, re-pinned 2026-11-13 by w3/m367) lists the codes `POST /v1/sandboxes` answers with a 400. `name` over 64 characters or starting `sbx-` gets `invalid_sandbox_name`, an unsupported plan `invalid_sandbox_plan`, and a nonzero `timeoutSeconds` outside 60–2592000 `invalid_timeout_seconds`. The `errorCode` schema exists "so generated clients get typed constants", so a client branching on Render's code never matches bex's. ADR018 grades both rows ✅ and calls each bex code "Render's `invalid_…`", but the wire carries a different string. Only the `sbx-` case already matches. The builds list has the same gap for its `status` filter.

**Severity:** minor (machine-readable error codes; the refusals and messages are right). **Attribution:** server (bex-api sandbox service and REST OpenAPI gate). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `c7aa`, 2026-11-13 UTC, released `bex v0.6.0` (Render CLI v2.36.0), `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `1c4d721bc8dc`.

## Evidence

Every probe was refused, so none created a sandbox (a `sandboxes list --all` afterwards showed nothing created after 18:15 UTC).

| Request | bex answers | Render's pinned contract |
| --- | --- | --- |
| `bex sandboxes create --name <65 × q> --timeout 600` (REST `POST /v1/sandboxes` `{"name":"<65 chars>"}`) | `400 {"error":"invalid request body at /name","id":"bad_request",…}`, no `code` | `400 invalid_sandbox_name` |
| same, GraphQL `createSandbox(name: <65 chars>)` | `invalid_sandbox_name` | — |
| `bex sandboxes create --name sbx-qa` | `400 invalid_sandbox_name` ✓ | `invalid_sandbox_name` |
| `bex sandboxes create --timeout 59`, `--timeout 2592001`; REST `{"timeoutSeconds":30}`; GraphQL `timeoutSeconds: 30` | `400 SANDBOX_TIMEOUT_INVALID` on all three surfaces | `invalid_timeout_seconds` |
| `bex sandboxes create --plan 3c-6g`; REST and GraphQL the same | `400 SANDBOX_PLAN_INVALID` on all three surfaces | `invalid_sandbox_plan` |
| REST `GET /v1/sandbox-groups/<sbg>/builds?status=bogus` | `400 {"error":"status must be one of pending\|running\|succeeded\|failed",…}`, no `code` | `invalid_status` |

The pinned spec's `create-sandbox` 400 description says: "`invalid_sandbox_name`: `name` exceeds 64 characters or starts with `sbx-`", "`invalid_sandbox_plan`: The plan is not supported. The error message lists accepted plans", and "`invalid_timeout_seconds`: A nonzero `timeoutSeconds` is outside the range of 60 to the workspace's maximum, which defaults to 2592000 (30 days)". Render's own CLI test fake at the pin applies the same rule: `internal/fakes/renderapi/sandboxsnapshots.go` `invalidSandboxName` is `RuneCount > 64 || HasPrefix "sbx-"`, answered with `invalid_sandbox_name`. Its `cmd/sandboxcreate_test.go` expects `400 (invalid_sandbox_name)`. `list-sandbox-builds` documents `invalid_status`, `invalid_cursor`, `invalid_limit` and `invalid_sandbox_group_id`. All three codes have been in the vocabulary since the first pin (`4d4f37c84`, 2026-11-02).

The rest of the v2.36.0 sandbox walk passed on the same pin: `--name` (64 characters, Unicode, `list --name` exact match), omitted timeout 86400, `--timeout 0`, `--timeout 2592000`, the client-side `--idle-timeout` and negative-timeout checks, `sandbox-groups create`/`delete` (the preview is read-only, the confirmed delete terminated all six sandboxes and the group reads 404), and every `sandbox-groups credentials` verb refused by name with `SANDBOX_CREDENTIALS_UNSUPPORTED`.

## Root cause

- `lego/backend/internal/sandbox/lifetime.go:69`: `resolveTimeout` refuses with the literal code `"SANDBOX_TIMEOUT_INVALID"`.
- `lego/backend/internal/sandbox/service.go:425-426`: `invalidPlan` (commented "Render's invalid_sandbox_plan refusal") uses `"SANDBOX_PLAN_INVALID"`.
- The name and status cases never reach the service, which has the right code (`validateSandboxName`, `service.go:414`, `CodeInvalidSandboxName`; `ListImages`, `images.go:62`/`:664`, `CodeInvalidBuildStatus = "invalid_status"`). GraphQL and MCP therefore answer them correctly. On REST the OpenAPI gate refuses first: the pinned schema has `name.maxLength: 64` and an enum on the builds `status` parameter. The gate attaches a code only through `renderValidationErrorCodes` (`lego/backend/internal/api/render_openapi.go:910`), which is keyed by bare field name. Its comment (`:909`) says each name there "is unique to its operation in the pin", which `name` and `status` are not. `renderValidationCode(err)` (`:916`, called at `:763`) never sees the operation, although `route.Operation.OperationID` is in scope at the call site.

## Fix

1. Answer Render's codes from the service, so REST, GraphQL and MCP agree. Use `invalid_timeout_seconds` in `resolveTimeout` and `invalid_sandbox_plan` in `invalidPlan`, as exported constants beside `CodeInvalidSandboxName`, and keep the messages and `params`.
2. Make the gate's code map operation-aware: pass `compatOperationID(route.Operation.OperationID)` into `renderValidationCode`. Look up `(operation, field)` first, then the existing unique-name entries. Add `create-sandbox`/`name` → `invalid_sandbox_name` and `list-sandbox-builds`/`status` → `invalid_status`. For the name, answer the service's own message ("sandbox name must be at most 64 characters and must not start with \"sbx-\"") so REST matches GraphQL word for word. Alternatively, the gate can step aside for that one maxLength so `validateSandboxName` runs.
3. Amend the ADR018 sandbox `plan` and `timeoutSeconds` rows, ADR014 § Lifetime bound (`:131`), `docs/render-artifacts/ea-sandbox.md:50` and `docs/cli-compatibility-checklist.md:204-205` to the Render codes.

No dashboard or mobile code reads `SANDBOX_TIMEOUT_INVALID` or `SANDBOX_PLAN_INVALID`. They appear only in the two producers, their tests (`sandbox/service_test.go`, `lifetime_test.go`, `cli_flags_test.go:180`, `api/sandbox_create_flags_gate_test.go:85`) and the docs above. Since the pinned CLI only prints the code, no client logic changes.

## Blast radius

- Two producers (sandbox create's timeout and plan) on three surfaces.
- Two gate-only refusals on REST: create's `name`, and the builds list's `status`.
- Out of scope: the builds list's `limit` (codeless 400, Render's `invalid_limit`) and malformed `cursor` (200 `[]`, Render's 400 `invalid_cursor`). These belong to the repo-wide pagination decision in w22/004, which is blocked, so they are recorded there instead. The `sandbox_group_limit_reached`, `default_sandbox_group_not_deletable` and `invalid_sandbox_group_id` codes already match.

## Regression checks

- REST `POST /v1/sandboxes` with a 65-character name answers `400 invalid_sandbox_name` with the service's message. A 64-character name and a 64-rune non-ASCII name are still accepted.
- REST, GraphQL and MCP creates with `timeoutSeconds` 30, 59, 2592001 and -1 answer `invalid_timeout_seconds`. Creates with 0, 60 and 2592000 are accepted.
- An unknown plan answers `invalid_sandbox_plan` on all three surfaces, and the message still lists the plans.
- REST `GET /v1/sandbox-groups/{id}/builds?status=bogus` answers `400 invalid_status`.
- A malformed `sandboxGroupId` still answers `invalid_sandbox_group_id`, and `update-sandbox-group`'s `concurrencyLimit` still answers `SANDBOX_GROUP_LIMIT_INVALID`, so the existing unique-name entries are unchanged.
- No other operation's `name` or `status` refusal gains a code.

## Dedupe

None of the open w8 items covers sandbox error codes. w22/004 (blocked) covers list paging (`invalid_limit`, `invalid_cursor`, `invalid_owner_id`) and is cross-referenced above. w3/m303 graded `SANDBOX_TIMEOUT_INVALID` as the expected answer, but did not compare it with the pinned vocabulary.
