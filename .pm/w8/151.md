# `PATCH /v1/services/{id}` refuses Render's `envSpecificDetails.dockerContext` as an unknown field

Why: Render's update schema lets a caller change a Docker service's build context in place (`dockerDetailsPATCH.dockerContext`). Bex accepts the field at create time but refuses it on update with a 400. A service whose context is wrong cannot be repaired through the API, MCP or the dashboard. The user has to delete and recreate it, which changes its ID and URL and loses its deploy history.

**Severity:** minor. **Attribution:** server (REST patch decoder; no update surface anywhere). **Estimate:** 40m. **Source:** `/qa-find-bugs-cli` sweep 1266, 2026-10-20 ([evidence](evidence/cli-sweep1266/README.md)).

## Reproduction

Production `https://api.bex.co/v1/`, deployed pin `9cace6b6e25d`, workspace `bex-canary`. Owned free Docker web service `srv-dbbu8m65u6js73eso1pg` (`rootDir: example-pserv`, `dockerContext: "."`, created in the same sweep for [150](150.md); since deleted with a 404 proof).

`PATCH /v1/services/srv-dbbu8m65u6js73eso1pg` with `{"serviceDetails":{"envSpecificDetails":{"dockerContext":"example-pserv"}}}` →

```json
400 {"error":"bad request: request body contains unknown field \"dockerContext\"","id":"bad_request","message":"bad request: request body contains unknown field \"dockerContext\""}
```

Nothing was saved. The sibling fields `dockerfilePath` and `dockerCommand` are accepted in the same object.

## Expected

The pinned Render schema (`lego/backend/internal/api/openapi/render-public-api-1.json`) defines `dockerDetailsPATCH` as `{dockerCommand, dockerContext, dockerfilePath, registryCredentialId}`. A PATCH with `dockerContext` should store it, under the same validation as create (relative path, no `..`, Docker builds only, using the same refusal wording as `SetDockerfilePath` otherwise). It should read back unchanged and apply on the next deploy, with the rootDir-relative meaning fixed in [150](150.md).

## Root cause

`lego/backend/internal/apps/rest.go:873–897`: the PATCH handler decodes `envSpecificDetails` into a struct holding only `buildCommand`, `startCommand`, `dockerCommand`, `dockerfilePath` and `registryCredentialId`, under the strict decoder, so `dockerContext` is an unknown field. Below the transport there is no setter either. `dockerfilePath` has a full update path: `Service.SetDockerfilePath` (`service.go:4095`) with `checkDockerfilePath` (`settings_check.go:137`), GraphQL `setDockerfilePath` (`graphql.go:1649`) and MCP `update_service.dockerfilePath` (`mcp.go:101`). `dockerContext` has none on any surface. `service.go:580–582` still says the build settings are read-only except `RootDir`.

## Fix

Add `DockerContext *string` to the PATCH `envSpecific` struct and a `SetDockerContext` op to the shared patch table, modeled on `SetDockerfilePath`. Reuse create's validation (`service.go:3028`) and `checkDockerfilePath`'s Docker-build-only refusal. An empty string clears the field, which restores the default context. Mirror the existing `dockerfilePath` setters: MCP `update_service.dockerContext` and GraphQL `setDockerContext`. Audit and event verbs follow `AuditVerbSetDockerfilePath`/`dockerfile_path_changed`. Record the change in ADR006 and in ADR018's docker-settings row.

## Acceptance

- REST handler test: PATCH `dockerContext` on a Docker service → 200 and read back. On a native or prebuilt-image service → 400 with `SetDockerfilePath`'s wording. `"../x"` → 400 with create's wording. `dryRun` reports it and writes nothing.
- The same op is reachable from every surface that already updates `dockerfilePath`.
- Live after deploy: on a fresh free Docker fixture, PATCH `dockerContext` → 200, and the next deploy builds from the new context. Delete it by ID with a 404 proof.

## Blast radius

One field on the shared patch table. REST, plus whichever MCP and GraphQL setters mirror `dockerfilePath`. Create, read and Blueprint paths are covered by [150](150.md).

## Dedupe

`rg -i 'dockerContext' .pm`: no open item, and no done item covers updating it. w4/369 named unknown `envSpecificDetails` keys in the 400 (the error wording above comes from it), but did not add the field.
