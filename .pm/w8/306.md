# A Blueprint service whose file takes a forward `fromService` reference starts life with a canceled deploy: the reference pass opens a second, `blueprint_sync` deploy that supersedes the first

Why: when one Blueprint apply creates a service that takes a sibling's address declared later in the file (`fromService` `host`/`port`/`hostport`, or a copied platform variable), bex writes the service first without that reference. That write opens its first deploy. The second pass then adds the reference (`patchDeferredStackServices`), and that re-apply opens another deploy, which supersedes the first. Every such service therefore starts its history with:

- a canceled deploy, "Superseded by dep-…", and a `deploy_ended` with `canceled`;
- a first real deploy labelled `blueprint_sync` (REST) / `blueprint` (bex) instead of the create's;
- a second build, whenever the first build had already started before the cancel.

This is w8/296's symptom from another cause: w8/296 fixed the seeding of `sync: false` / `generateValue` values, which opened a `service_updated` deploy. On Render a Blueprint's new service has one first deploy. Render resolves the references among the resources it creates before that deploy.

**Severity:** minor (the service ends up correct; history, notifications and possibly one build are wrong). **Attribution:** server (bex-api Blueprint apply). **Estimate:** ~1–2h. **Source:** `/qa-find-bugs-cli` w8 loop sweep `41e2`, 2026-11-13 UTC, released `bex v0.5.0`, `https://api.bex.co/v1/`, workspace `bex-canary`, QA human device login, production pin `5de3d5bcce8e`.

## Evidence

`render-examples/movie-context-provider`: its web service `movie-mcp-server` takes `MOVIE_POSTER_WIDGET_URL` from `fromService: {name: movie-mcp-widget, type: web, property: host}`. That widget is a static site declared after it. `bex ea blueprints create … --auto-sync=false` and `approve` (`exs-dbrdv8ok58is73aunpsg`, deleted afterwards):

```text
web srv-dbrdvc8k58is73aunq2g
  dep-…aunq30  canceled  trigger other / bexTrigger create          created 10:00:17.24  finished 10:00:19.32  "Superseded by dep-dbrdvc8k58is73aunq50"
  dep-…aunq50  (built)   trigger blueprint_sync / bexTrigger blueprint  created 10:00:17.77
widget srv-dbrdvc8k58is73aunq40 (no references)
  dep-…aunq4g  live      trigger other
```

Here the first deploy was canceled 2 s in, before its build started, so nothing was built twice. A larger file, or a slower build queue, leaves more time for that first build to start. (The web build itself then failed: the template's `NODE_ENV=production` makes `npm ci` drop TypeScript. That is the template's problem, unrelated to this item.)

## Root cause

- `lego/backend/internal/apps/deploy.go:1181-1192` (`applyStackServices`): `resolveServiceRefs` returns the forward references, and the service is written without them, opening its create deploy.
- `deploy.go:1239-1260` (`patchDeferredStackServices`): re-applies the service with the references and `referencePass` set.
- `deploy.go:3972` and `:4016-4024` (`updateStackService`): `referencePass` only suppresses the per-setting change records. The spec still changed, so the release generation is bumped and `recordBlueprintRedeploy` writes a second deploy row. The first deploy is then closed as superseded.

## Fix

A service the same apply created takes its references into its first deploy instead of opening another one. Two options:

1. **Resolve before writing.** A sibling's slug is minted at create (ADR041 D3). Mint it, or pre-compute it, for every service the apply will create before the first write. Then a forward `host` reference resolves in the first pass, and only port-carrying references to an image-port private service remain deferred (their port is unknown until a build).
2. **Fold into the first release.** When the reference pass re-applies a service this apply created, update its spec without a new deploy row and without bumping the release generation, so the create deploy, still queued or building, rolls the final spec. This needs care: a build that already started must pick up the new spec, or be rebuilt under the same deploy row.

Prefer 1 for `host`; keep the deferred pass for the port-unknown case, and make it fold (2) or accept the second deploy only there.

## Blast radius

Every Blueprint (create or sync) that creates a service referencing a sibling declared later in the file. Render templates commonly declare the referencing service first: in the w8/292 corpus, 2 of 172 files take a static site's host, and more take a web or private service's host or port. Surfaces: deploy history (REST, CLI, dashboard), the events feed and notifications.

## Regression checks

- **Go test:** a `DeployStack` creating `web` (referencing `api` declared after it) records exactly one deploy row for `web`, with the create's trigger. Its env holds the reference.
- **Production:** the 41e2 import. The web service's deploy history starts with one deploy.
