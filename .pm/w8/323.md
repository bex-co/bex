# A static site serves `.html`, `.css`, `.md` and `.csv` with no charset (`text/html`, `text/markdown`), where Render declares `charset=utf-8` on every text type it serves

Why: Render's static sites send `charset=utf-8` on their text types:

- `text/html; charset=utf-8`
- `text/css; charset=utf-8`
- `text/markdown; charset=utf-8`
- `text/plain; charset=utf-8`

bex declares UTF-8 only on `text/plain` (w4/335), and only for valid UTF-8 bodies, so `.html`, `.css`, `.md` and `.csv` arrive with no charset. A browser decodes a charset-less `text/*` response it cannot sniff as windows-1252. UTF-8 Markdown, CSV or plain-text-like files viewed directly then show mojibake, which is what w4/335 fixed for `.txt` alone. CSS without a `@charset` falls back to the referring page's encoding. w4/335 deliberately stopped at `text/plain` because "Render's primary header documentation … does not establish Render's default charset". These captures now do.

**Severity:** minor. HTML usually carries `<meta charset>`; the visible damage is non-ASCII `.md`/`.csv`/`.css` content. **Attribution:** server (static-server or publish MIME). **Estimate:** ~30m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `3506`, 2026-11-14 02:55 UTC, released `bex v0.6.0`, `https://api.bex.co/v1/`, workspace `bex-canary`, production pin `ac206b76841b`.

## bex (fixture `qa-20261114-3506-ct`, `srv-dbrspg1rr8ts738m9p70`)

/x.md         200  content-type: text/markdown
/t.csv        200  content-type: text/csv

## Root cause

- The publish Job uploads with `aws s3 sync`'s guessed MIME types (`lego/operator/internal/publish/publish.go`, per w4/335's trace), which carry no charset.
- `S3Origin` (`lego/operator/internal/staticserver/s3origin.go:114-120`) adds `charset=utf-8` only through `utf8PlainText` (`:123-140`), which returns early for every media type but `text/plain`.
- `contentType` (`staticserver.go`, the table w4/581 extended) supplies types by extension without a charset for `.html`, `.css`, `.md` and `.csv`.

## Fix (target behavior)

- Widen w4/335's normalization from `text/plain` to every `text/*` media type that names no charset: at least `text/html`, `text/css` and `text/markdown`, which Render captures show, and `text/csv`, by the same rule.
  - Declare `charset=utf-8` when the unencoded body is valid UTF-8.
  - An explicit charset (stored or from a header rule), invalid UTF-8 and every non-`text/*` type stay as they are.
- Apply it once before caching, as w4/335 does, so encoded variants (br/gzip) inherit the declared type.
- Leave non-text types alone. Render's `application/javascript` and `application/xml` differ from bex's `text/javascript` and `text/xml`, but both work in every browser; they are not part of this change.
- Record the captured types in ADR029 and extend w4/335's note.

## Blast radius

- Every static site, which all share the static-server.
- The normalization is one function on `S3Origin`'s fetch path, used by direct files, the `404.html` page and rewrite targets.
- Tests: `s3origin_charset_test.go` pins today's text-plain-only behavior and needs `text/html`, `text/css`, `text/markdown` and `text/csv` cases. A header rule setting `Content-Type` still wins (w5/182 retypes the ETag).

## Acceptance

- Tests for valid-UTF-8 `.html`, `.css`, `.md` and `.csv`:
  - each serves `text/<type>; charset=utf-8`;
  - a Latin-1 `.csv` keeps its bare type;
  - a `Content-Type` rule still overrides;
  - brotli and gzip variants carry the same type.
- Live, after the static-server rolls: a fresh fixture's `/index.html`, `/styles.css`, `/x.md` and `/t.csv` answer `charset=utf-8`. Delete the fixture.
