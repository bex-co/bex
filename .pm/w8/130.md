# An SSH-form repo URL is accepted at create but every build dies on SSH host-key verification

Why: create validation explicitly advertises `https/ssh/git` repo URLs, and the operator's own submodule code states the intended rule — GitHub SSH URLs go over HTTPS "the same rule the App's own repo URL follows" — but neither tenant clone phase actually applies that rewrite to the parent repo, so the most natural repo string a user can paste (`git@github.com:owner/repo.git`, the form GitHub's own clone button offers) accepts cleanly and then fails every build with a misleading host-key error.

Seen in the `/qa-find-bugs-cli` loop sweep 529, 2026-10-19, production, `bex-canary`, HEAD-build CLI:

- `bex services create --repo git@github.com:bex-co/bex.git --runtime go --plan free …` → exit `0`, service created; the deploy resolves the branch head (`Building from git@github.com:bex-co/bex.git@218dffc`) and then `build_failed` within seconds of the clone starting:
  `failureReason: "build failed in the clone step:\nHost key verification failed.\nfatal: Could not read from remote repository…"`
- The same repo over `https://github.com/bex-co/bex` creates and builds normally (this loop's earlier sweeps).

Root cause: the two parent-clone phases fetch `$REPO` verbatim with no transport normalization — the build plane at `lego/operator/internal/build/build.go:1493-1499` (`buildCloneContainer`: `git remote add origin "$REPO"` then `git "$@" fetch`), and the static publish plane at `lego/operator/internal/publish/publish.go:585-587` (same shape). The submodule phase both share *does* normalize: `lego/operator/internal/execution/gitsubmodule.go:41-42` prepends `-c protocol.allow=never -c protocol.https.allow=always -c url.https://github.com/.insteadOf=git@github.com: -c url.https://github.com/.insteadOf=ssh://git@github.com/`, and its header (:25-27) asserts that is "the same rule the App's own repo URL follows" — it doesn't. Create-side admission accepts the SSH forms deliberately: `store.ValidRepo` (`lego/backend/internal/store/api.go:640-659`, SCP form and `ssh://` both pass) behind the `repo must be an https/ssh/git URL` message (`apps/service.go:3007`, `store/api.go:405`), so accepted-but-unbuildable is a contract contradiction, not user error. The build image has no SSH host trust or keys for arbitrary hosts, so the SSH transport can never succeed as wired; for GitHub it also bypasses the host-bound `GIT_AUTH_TOKEN` credential helper (`execution/gitcredential.go`), meaning a *private* GitHub repo given in SSH form fails even when bex holds a valid installation token for it.

Fix (follow the codebase's own stated rule): apply the submodule phase's transport set to both parent fetches, ideally as one shared `execution` constant next to `GitHubCredentialHelper` (the w1/m80 one-guarded-definition pattern) spliced into both planes' git options, so `git@github.com:`/`ssh://git@github.com/` fetch over HTTPS and the credential helper applies. Decide and name the non-GitHub SSH/`git://` remainder in the same change: with the protocol pin they fail as transport-refused instead of host-key noise; if they are meant to stay unsupported, refuse them at create with a message that says so (today's message promises them). Keep `$REPO` an environment lookup, never spliced into script text.

Blast radius: every repo-backed create/update path that reaches the build plane (REST/GraphQL/MCP/CLI create, blueprint apply) and the static direct-publish plane; webhook/blueprint syncs of an already-accepted SSH-form repo fail the same way every time. HTTPS repos are unaffected by the rewrite rules.

Acceptance:

- On a fresh owned fixture, `bex services create --repo git@github.com:bex-co/bex.git …` (public repo) reaches `live` (or at minimum clones successfully and fails only on later tenant build steps), and its build log shows the fetch going over HTTPS; `ssh://git@github.com/bex-co/bex.git` behaves the same.
- A static site whose repo is given in SSH form publishes through the direct-clone plane the same way.
- A non-GitHub SSH or `git://` repo either builds or refuses at create with a message naming the supported forms — never `Host key verification failed` from a doomed build.
- HTTPS create/build behavior is byte-unchanged; a unit test pins both clone containers' git options to the shared transport set (fails before the fix for the parent fetch).

Severity: major for anyone pasting GitHub's SSH clone URL (create succeeds, every deploy fails with a misleading reason); no data loss. Estimate: ~40m.
