# Key Value REST refuses the hyphenated enum spellings its handler, MCP schema, and ADR021 all say are accepted

Why: bex deliberately accepts both separator forms for the Key Value enums (`maxmemoryPolicy`, `persistenceMode`) — the handler normalizes them through one shared check "so create and update can never accept different values", the MCP tool schema advertises "underscore or hyphen forms both accepted", and ADR021 states all surfaces normalize "identically to create". On REST the pinned-schema validator only admits the underscore forms, so the hyphenated spellings the rest of the platform accepts (and that bex's own pre-w9 wire used) die at the gate on create and PATCH alike — one value, three surfaces, two answers.

Seen in the `/qa-find-bugs-cli` loop sweep 864, 2026-10-20, production, `bex-canary` (all fixtures deleted and verified 404):

- REST `POST /key-value {"maxmemoryPolicy":"allkeys-lru"}` → 400 `invalid request body at /maxmemoryPolicy`; `{"maxmemoryPolicy":"allkeys_lru"}` → 201.
- REST `PATCH /key-value/{id} {"maxmemoryPolicy":"allkeys-lru"}` → same 400; `allkeys_lru` → 200 (and a same-value hyphen PATCH on a `noeviction` store read as invalid too — the refusal is the spelling, not the change).
- REST `PATCH {"persistenceMode":"journal-snapshot"}` → 400 `invalid request body at /persistenceMode`; `journal_snapshot` → 200.
- GraphQL control: `createKeyValue(maxmemoryPolicy: "allkeys-lru")` → 200, read back normalized as `allkeys_lru` (fixture deleted via GraphQL, verified 404).

Root cause: the enum gate and the enum handler disagree about the accepted vocabulary. The handler's one shared check (`lego/backend/internal/keyvalue/service.go:213` `maxmemoryPolicyKnown`, `:222` `persistenceModeKnown`) runs `renderToCRD` (underscore→hyphen) before the membership test, with the design comment at `service.go:201-209`: Render's wire is underscore, the CRD is hyphen, "accepting a bare hyphenated value (bex's pre-w9 behavior) keeps working too". But REST traffic first passes the Render-schema validator (`lego/backend/internal/api/render_openapi.go`), whose pinned enums admit only the underscore spellings, and there is no compatibility-map entry widening these two fields to the handler's vocabulary — the w8/136 audit class (schema-vs-handler drift), in the stricter direction. GraphQL/MCP never pass that validator, so they honor the documented both-forms rule and REST alone breaks it.

Fix (~30m): widen the two REST enums at the validator the same way other bex-vocabulary fields are widened — add the hyphenated spellings to the accepted set for `maxmemoryPolicy`/`persistenceMode` on the Key Value create and PATCH operations via the existing compatibility maps in `render_openapi.go` (or an equivalent enum-extension entry), keeping the underscore forms canonical on every response. The handler already normalizes, so no service change is needed. Add a validator-level test beside the composed-stack tests from w8/136: REST create with `allkeys-lru` → 201 read back as `allkeys_lru`; REST PATCH `journal-snapshot` → 200. Check the sibling enum `plan` and the Postgres `connectionPool` alias handling for the same separator asymmetry while the maps are open.

Acceptance:

- Live after deploy: REST `POST /key-value` with `maxmemoryPolicy: "allkeys-lru"` returns 201 and reads back `allkeys_lru`; REST PATCH with `persistenceMode: "journal-snapshot"` returns 200.
- Underscore forms byte-unchanged everywhere; GraphQL/MCP behavior unchanged.
- A genuinely unknown policy (`bogus864`-class) still refuses by name on every surface.

Severity: minor — the canonical Render spellings work everywhere; only bex's own legacy/hyphen dialect is refused on one surface. Estimate: ~30m.
