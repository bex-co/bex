# 065 — Postgres CA preparation blocks `psql <id> --help` and `pgcli <id> --help` on a connection-info 503

Why: a user asking for help needs no database connection. The pending launcher trust feature prepares the session before Cobra handles help, so a still-provisioning database replaces the requested help with a TLS refusal. Keep the useful trust preparation on actual sessions while preserving Render's help contract before releasing it.

Severity: minor. Attribution: Bex launcher. Estimate: ~40m. Source: `/qa-find-bugs-cli` w8 loop, 2026-10-07, offline sweep 2. Goal: the imported Render CLI contract and usable Postgres hosting journeys (ADR009, `docs/bex-cli.md`). No implementation or commit by this filing.

## Reproduction

Use the private checkout-build recipe in [064.md](064.md#re-run-the-decisive-offline-case-without-network-or-real-credentials), with the fixture transport answering connection-info as the complete 503 response below. Use a typed workspace ID so the independent w8/064 name resolver never runs.

```text
BEX_WORKSPACE=tea-12345678901234567890 bex psql dpg-12345678901234567890 --help
BEX_WORKSPACE=tea-12345678901234567890 bex psql --help dpg-12345678901234567890
BEX_WORKSPACE=tea-12345678901234567890 bex pgcli dpg-12345678901234567890 --help
BEX_WORKSPACE=tea-12345678901234567890 bex psql dpg-12345678901234567890 -h
```

All four exit 1 and print no stdout. The first case's complete product stderr is:

```text
bex: cannot open a psql session to Postgres "dpg-12345678901234567890": the database's TLS server CA is not available yet (fixture: external endpoint is not provisioned).
A public bex Postgres pins sslmode=verify-full, so the session cannot open until its server CA exists. Retry once the database reports available; if it persists, the database's external endpoint is not provisioned
```

`pgcli` has the identical message with the tool name changed. Repeated fresh-process cases took 0.046–0.049s after warming the build (the initial psql case took 3.249s). Both tools were reproduced again, including help before the selector and the `-h` alias. Each failure first sends:

```http
GET /v1/postgres/dpg-12345678901234567890/connection-info
Authorization: Bearer <fixture-only dummy credential>

HTTP/1.1 503 fixture
Content-Type: application/json

{"id":"database_unavailable","message":"fixture: external endpoint is not provisioned"}
```

This is the complete fixture response, **not a production capture**. The transport separately logged the request; its `QA FIXTURE REQUEST ...` instrumentation is not product stderr. The decisive transport change from 064's recipe is:

```go
return &http.Response{
    StatusCode: http.StatusServiceUnavailable,
    Status: "503 fixture",
    Header: http.Header{"Content-Type": []string{"application/json"}},
    Body: io.NopCloser(strings.NewReader(`{"id":"database_unavailable","message":"fixture: external endpoint is not provisioned"}`)),
    Request: r,
}, nil
```

Run the probes with `PGSSLROOTCERT` absent in that process; preserve any personal `root.crt`. If the machine already has one, use the injectable `pgtrust.Options.Home` in a private test harness to model a machine without it, rather than modifying personal state or `HOME`.

## Render and valid controls

The unmodified **same-pin Render command package** with the same dummy auth and workspace exits 0, prints its ordinary psql/pgcli help and sends **zero requests** for `psql <id> --help`, `psql --help <id>` and `pgcli <id> --help`. The installed Bex v0.2.1 also exits 0 with ordinary Bex help on all three (no request). Checkout `bex psql --help` with no selector exits 0 with help and no request, because its trust preparer finds no target.

The neighboring real-session control is correctly refused by the same checkout build and fixture:

```text
bex psql dpg-12345678901234567890 -c 'SELECT 1' -o text
→ exit 1, the same actionable unavailable-CA message, one connection-info request
```

That refusal must survive the fix. It proves that bypassing preparation globally would remove a deliberate safety/error behavior; it is not evidence of a working SQL connection. Existing pure `pgtrust` tests prove CA-file provision/removal and explicit/implicit user trust precedence; actual successful child execution was not re-run in this network-restricted hunt.

Offline sweep 4 preserved three parsing neighbors in separate fresh processes: `psql -c '--help' <id> -o text`, `psql <id> --help=false -c "SELECT '--help' AS marker" -o text`, and `psql <id> -c 'SELECT 1' -o text -- --help`. Each made the same connection-info request and received the same exit-1 unavailable-CA refusal, rather than displaying CLI help. This observes the current preparer's behavior; parsing/child execution after a successful preparation remains unverified.

## Mechanism and exact fix

- `lego/cli/main.go:75-78` invokes `provisionPostgresTrust` and exits on its error before `cmd.Execute` (`:91`). `provisionPostgresTrust` (`:125-142`) uses `RootCmd.Find` to choose the tool, but does not check whether Cobra would display help rather than run it.
- `lego/cli/internal/pgtrust/pgtrust.go:147-162` extracts the database positional argument through `DatabaseArg`, checks existing user trust, then fetches the CA. It never distinguishes a help invocation with a selector. `fetch.go:37,58-59` turns the connection-info 503 into `ErrCAUnavailable`; `pgtrust.go:164-170` returns the refusal that main treats as fatal.
- Consumer/framework: pinned Cobra v1.10.2 `command.go:921-935` parses flags, tests the help bool, then returns `flag.ErrHelp` **before pre-run or RunE**. Pinned upstream `cmd/psql.go` / `cmd/pgcli.go` therefore do no API work for these help forms, as the fresh-process controls confirm. A psql/pgcli database selector does not change that rule.
- Producer neighbor: `lego/backend/internal/postgres/service.go:912` returns unavailable when the public database's server CA is not provisioned; missing external endpoints can also be unavailable. This normal convergence state must not be required for help. The synthetic message is not asserted to be a byte-identical production response.
- Fix the launcher preparation boundary so a **Cobra help invocation** goes directly to help with exit 0 and no CA fetch or temporary file. Preserve `--help=false`, literal `--help` inside a SQL/flag value, and arguments after `--` as upstream parses them; a raw substring scan is insufficient. Do not weaken `sslmode=verify-full`, rewrite connection strings or modify upstream commands.
- Shared boundary: exhaustive production-symbol search finds one `pgtrust.Provision` caller (`main.go:135`) and one `NewFetcher` construction (`:139`), reaching **two tools**, `psql` and `pgcli` (`pgtrust.go:52-53`). Review and test both, their flag placement and passthrough forms. No Postgres/Key Value REST, GraphQL, MCP, UI or server serialization change is needed; Key Value does not use this preparer.
- Adjacent classes retain their existing actual-session contract: a 503 still gives the clear unavailable-CA refusal; no login, not found, forbidden and transport failures defer to upstream; explicit `PGSSLROOTCERT` and existing user trust still win. Help needs no authorization or resource existence check, so skipping those reads does not disclose a resource.
