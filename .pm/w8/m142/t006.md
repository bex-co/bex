## Fix — 2026-10-29

**Production check (pin `03043c7df363`):** removing `PORT` from an echo-server web service (the image declares no ports; 8080 → PORT removed → deploy) gave 6–9 `502 Bad Gateway` among `200`s over about 17 s, reproduced 3×. Moves between two set ports gave zero `502`s. A cluster watch showed that during the window the CR-named Service, the one the Ingress routes to, was **not** pinned to a revision and still mapped 8080→8080. Its endpoints held the old pod and the ready candidate listening on 10000, so a share of requests hit a closed port. The slug Service was correctly pinned. Secondary: the first template of the new release still carried `PORT=8080` and was replaced about 1 s later.

**Cause.** Removing `PORT` starts the web image's HTTP port discovery. While it runs, every reconcile halts in `reportDeploymentStarting` (`web_image_http.go`), which ran before the CR-named `applyClusterIPService` (`app_controller.go`). That Service therefore never received the serving-revision pin from `privateServiceProjection` (`image_network.go`). The slug Service converges earlier in `convergeSharedChildren`, which is why it was pinned. The stale template came from `envPort`: it read `PORT` through the served release's config snapshot, because this release's own snapshot is taken later in the same pass, just before the template is written.

**Fix (operator).**

- `reconcileKubernetesRuntime` now applies the CR-named Service right after the Deployment write and before `reportDeploymentStarting` can halt the pass (workers excluded). Both Services pin the serving revision with its serving port for the whole discovery window, then switch together at promotion (`promoteImageNetwork`).
- `portRuntimeApp` → `savedReleasePortRuntime`: an image-port service whose new release is not snapshotted yet reads the saved sources (`inFlightRelease`), which this pass snapshots before writing the template. Configured-port (native) services keep the served projection, because their routing follows this port directly.
- Regression: envtest `Removing PORT while HTTP discovery runs (w8/m142)` (`image_port_recovery_envtest_test.go`). It saves `PORT=8080` in the service's env Secret, serves, deletes `PORT` and deploys. On every pass that writes the new release's template, it asserts `PORT=10000`, `EnvPort` 0, discovery pending, and a CR-named Service pinned to `rev-1` with only 8080→8080. After detection it asserts the Service moves to 10000 and is unpinned at completion. Before the fix it failed first on `PORT=8080` in the new template, then, with only that fixed, on the unpinned selector.
- Local verification: `make test` (operator) passes, except `cmd/activator` `TestConcurrentHeldRequestsShareOneWake`, an untouched timing test that failed once under full-suite load and passes 5/5 alone. `make lint` gives 0 issues in all four modules.

## Fix 2 — 2026-10-29

**Production re-check after Fix 1 (pin `69f0b17d1fad`):** echo-server with `PORT=8080`, then `PORT` removed and a deploy, polled every 0.25 s. Of 1523 requests, 38 returned `503`, all in one contiguous block of about 9.6 s. No `502`s remained. A read-only cluster watch showed the cause. At promotion, the new release's Ready candidate pod (ReplicaSet `5d794959df`) was killed. Choosing the port had rewritten its template from the discovery-time HTTP readiness probe on `/` to the final TCP probe, so the Deployment created a new ReplicaSet (`8598966c68`) with a new pod. The routed Services had already moved to the new revision, which now had no Ready pod. The serving release's pod kept running, unrouted, until it terminated.

**Cause.** `promotePortChangeEarly` (`image_network.go`) moved both Services as soon as `currentRevisionFullyReady` found a Ready pod carrying the new release's revision label. Choosing the HTTP port rewrites the release's template once (`appContainer` in `deployment_projection.go` probes `GET /` only while `webImageHTTPSelectionPending`), and that pass promoted on the discovery pod. The pod's labels still match the release, but the Deployment controller drains it as soon as the final template's ReplicaSet exists. Because its `minReadySeconds` hold (150 s during discovery) had not elapsed, it was not yet available. The Deployment controller removes such pods first, while the serving release's available pod is kept.

**Fix (operator).**

- Early promotion now requires a Ready, non-terminating pod of the **template this pass wrote**, not just of the release (`templatePodReady`, `image_network.go`). It finds the Deployment's ReplicaSet whose template, minus `pod-template-hash`, equals that template (the Deployment controller's own match), and counts Ready pods with that hash. Until that ReplicaSet exists, nothing is Ready. `reportKubernetesRunning` passes the written template rather than the cached re-read, which can predate the write.
- Until the final template has a Ready pod, both Services stay pinned to the serving release on its serving port. The `portChangeHoldSeconds` hold then keeps the old pod serving while routing moves (w4/428), and the public route keeps the replaced primary as an alias (w4/430). The Fix 1 behaviours are unchanged: the Services stay pinned while discovery runs, and the first template carries no stale `PORT`. Detected-port narration, per-digest reuse, rollback recovery and the final status-gated `promoteImageNetwork` are also untouched.
- The discovery-time HTTP probe is kept on purpose. It stops a binary listener passing TCP readiness and draining the serving release before discovery finishes. Gating promotion on the written template covers every same-release template rewrite, including a detected port that differs from the first guess.
- **Regression, envtest** `Promoting after HTTP port discovery (w8/m142)` (`image_port_recovery_envtest_test.go`). It serves `PORT=8080` from a simulated Ready pod (ReplicaSet + pod, as the Deployment controller and kubelet would write them). It then deletes `PORT` and deploys, and makes the discovery template's pod Ready. Next it marks the port detected, which rewrites the template to TCP on 10000. The test asserts the Service still pins `rev-1`. After draining the discovery pod and adding a not-yet-Ready final pod, it asserts that the Service selects a Ready pod. Once the final pod is Ready, it asserts that routing moves to the new release with 10000. **Before the fix** it failed at the first post-detection pass: the selector held `app.bex.co/revision: rev-2` while the only Ready `rev-2` pod belonged to the replaced template.
- **Regression, unit** `TestPortChangeRoutesOnlyToTheWrittenTemplate`: a Ready pod of a replaced template of the same release no longer moves routing. `TestPortChangeRoutesEarlyWhileTheOldPodsAreHeld` keeps the w4/428 case: a Ready pod of the written template still routes early.
- Local verification: `make test` (operator, including envtest) passes twice; `make lint` gives 0 issues in all four modules plus dead-code analysis.
