# 223 — A rollout refused by the workspace's memory quota sits "in progress" with no reason

Why: when a deploy cannot start its new pod because the workspace's resource quota is exhausted, the deploy shows `update_in_progress` for many minutes with no stall reason, so the user cannot tell that deleting or downsizing another service would unblock it (Render's equivalent states the capacity problem).

Found 2026-10-29 by the `/loopx w8` m117 re-check (production pin `2ac6fd95402e`, bex-canary): a Free image service's deploy stayed `update_in_progress` ~11 min with the URL serving the previous pod; `tenant-quota` was 5888Mi of 6Gi used (mostly another run's half-rolled QA fixtures), so the ReplicaSet's surge pod was refused (`FailedCreate … exceeded quota`), not left Pending/unschedulable. The existing unschedulable diagnosis ("the instance starts as soon as capacity frees up") does not cover a quota refusal, and the row carried no stall reason. It went live as soon as another service was deleted.

Fix: detect the ReplicaSet `FailedCreate` quota refusal during a rollout and surface it as the row's stall reason (and a terminal reason if the gate times out), naming the quota and what is using it where safe; regression test with a quota-refused surge. Acceptance: a deploy blocked by tenant quota shows that cause on the deploy row and dashboard within a minute, and goes live once capacity frees.

## Done — 2026-10-29

Root cause: the quota diagnosis already existed (`rolloutQuotaBlockMessage`, reason `RolloutBlockedByQuota`, which bex-api's `stallDiagnosis` already projects onto the open row), but it read the verdict from the first ReplicaSet carrying the release's revision label and gave up when that one had pods. A release can roll its template more than once (image-port discovery swaps its probe; the incident's echo-server ran in image-ports mode), so the replaced template's ReplicaSet — same revision, one serving pod — was found first and the surge ReplicaSet's `FailedCreate … exceeded quota` was never read. A ReplicaSet that had created some pods but not the rest was skipped the same way.

Fix (`lego/operator/internal/controller/app_controller.go`): the verdict is read from the newest ReplicaSet of the current release (the Deployment controller's `deployment.kubernetes.io/revision` order), whether or not it already has pods; `stuckPodMessage` still runs first and owns any pod that exists. The message names only the workspace's own quota numbers, never the pod, the quota object, or what uses it: "the workspace's resource quota is full (memory: 5888Mi of 6Gi in use, the new instance needs 512Mi): the new instance starts as soon as capacity frees up — to free it, delete, suspend or downsize another service, or upgrade the plan." The in-flight/terminal pair `QuotaStallWaiting`/`QuotaStallFailed` is in `lego/types/v1alpha1/stall_message.go`, so both the operator's `terminalStallMessage` and bex-api's `TerminalStallText` close a timed-out row with "…: the rollout window ended before capacity freed up, so the deploy failed; deploy again once there is room — …". `lastStallDiagnosis` now keeps the quota diagnosis as a settle fallback. Going live once capacity frees is unchanged: the ReplicaSet controller clears the condition on its next successful create and the 5 s rollout requeue rewrites Ready.

Tests: `rollout_quota_test.go` — the w8/223 shape (an earlier same-revision template serving, the surge refused by the memory quota), a rolling update over an old release, a partly created ReplicaSet, a stale verdict on a replaced template, no-leak checks, both halves of the wording, and `reportRolloutProgress` stamping the reason; `stall_message_test.go` covers the new pair; backend `parked_rollout_reason_test.go` closes a quota stall with its terminal wording.

Production re-check (read-only, `hetzner-prod`, 2026-10-29): the fix is not deployed yet, and filling a workspace's 6Gi memory quota with fixtures would also block other runs in the shared QA workspace, so no quota was filled. Of 154 bex-managed ReplicaSets in 107 Deployment/revision groups, 22 groups have more than one ReplicaSet for the same release, and in 11 of them the list order puts an older template first — each would have hidden a quota refusal under the old lookup. No ReplicaSet currently has a `ReplicaFailure` condition. Live acceptance (a quota-refused deploy shows the reason on its row within a minute) is for the next re-check after the operator image carrying this fix rolls out.
