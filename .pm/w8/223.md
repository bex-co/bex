# 223 — A rollout refused by the workspace's memory quota sits "in progress" with no reason

Why: when a deploy cannot start its new pod because the workspace's resource quota is exhausted, the deploy shows `update_in_progress` for many minutes with no stall reason, so the user cannot tell that deleting or downsizing another service would unblock it (Render's equivalent states the capacity problem).

Found 2026-10-29 by the `/loopx w8` m117 re-check (production pin `2ac6fd95402e`, bex-canary): a Free image service's deploy stayed `update_in_progress` ~11 min with the URL serving the previous pod; `tenant-quota` was 5888Mi of 6Gi used (mostly another run's half-rolled QA fixtures), so the ReplicaSet's surge pod was refused (`FailedCreate … exceeded quota`), not left Pending/unschedulable. The existing unschedulable diagnosis ("the instance starts as soon as capacity frees up") does not cover a quota refusal, and the row carried no stall reason. It went live as soon as another service was deleted.

Fix: detect the ReplicaSet `FailedCreate` quota refusal during a rollout and surface it as the row's stall reason (and a terminal reason if the gate times out), naming the quota and what is using it where safe; regression test with a quota-refused surge. Acceptance: a deploy blocked by tenant quota shows that cause on the deploy row and dashboard within a minute, and goes live once capacity frees.
