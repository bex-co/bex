# A native service's environment-group secret file is missing from its root directory after the link deploy, until the next build

Why: Render puts every secret file in a native service's root directory as well as `/etc/secrets` ("For non-Docker services, the file is _also_ available in your service's root directory", render.com/docs/configure-environment-variables), and linking a group "kicks off a new deploy". On bex the link, and a file added to a linked group, roll the service on its old image with no build, so the group's file is at `/etc/secrets/<name>` only. An app that reads `./<name>` starts without it. ADR013 § "Secret files in the service root, native runtimes" says this cannot happen: "Every deploy of a native service builds".

- Severity: major. The file is missing silently, as in w8/m154, and nothing tells the user to rebuild. The next build fixes it.
- Versions: bex CLI v0.7.0 (Render CLI pin `4fd34231b637`); production pin `12716d1d7097`; checkout `8178a5da7`.
- Context: 2026-11-20 09:45–10:03 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), QA human device-flow login, `-o json`, no TTY. Routine `cli-qa` run `rt9-4ca8`.

## Repro

1. Create a free native Python web service with one secret file of its own:
   `bex services create --name qa-20261120-4ca8-sf --type web_service --repo https://github.com/render-examples/flask-hello-world --runtime python --plan free --region oregon --build-command 'pip install -r requirements.txt' --start-command 'mkdir -p /tmp/w && ln -sfn /etc/secrets /tmp/w/etc && ln -sfn "$PWD" /tmp/w/root && echo QA-START eg=$QA_EG_KEY svc=$QA_SVC && exec python3 -m http.server $PORT --directory /tmp/w' --secret-file qa-sf.txt:sf1.txt --env-var QA_SVC=svc-1 --confirm -o json`
   This created `srv-dc01dk18bccs73evql3g`. `GET /etc/qa-sf.txt` and `GET /root/qa-sf.txt` both serve the marker, so the service's own file works.
2. `POST /v1/env-groups` creates `evg-dc01ekp8bccs73evql60` with `QA_EG_KEY=grp-1` and a secret file `qa-grp.txt`. Link it with `POST /v1/env-groups/evg-dc01ekp8bccs73evql60/services/srv-dc01dk18bccs73evql3g` (200).
3. The link opens deploy `dep-dc01i2p8bccs73evqldg` (`trigger: service_updated`, `bexTrigger: config_change`). Its whole log is:

   ```text
   09:55:23  ==> Deploy queued
   09:55:23  ==> Deploying image …/tea-daif693dqjvc73e7as3g-qa-20261120-4ca8-sf:gen-2@sha256:7c2b396d…
   09:55:56  ==> Your service is live 🎉
   ```

   No build ran: `gen-2` is the image of the 09:51 deploy. The process sees `QA_EG_KEY=grp-1` (`QA-START eg=grp-1 svc=svc-1`). Then:

   ```text
   GET /etc/qa-grp.txt   200 qa-rt9-4ca8-grp-v1
   GET /root/qa-grp.txt  404            ← missing from /opt/render/project/src
   ```

4. `PUT /v1/env-groups/<group>/secret-files/qa-grp2.txt` on the linked group rolls the service the same way (`dep-dc01j118bccs73evqlf0`, `config_change`, live in 14 s). `/etc/qa-grp2.txt` is 200 and `/root/qa-grp2.txt` is 404.
5. Control: `bex deploys create <srv> --confirm` builds (`dep-dc01j6kd1ruc73b8cgog`). After it, `/root/qa-grp.txt` and `/root/qa-grp2.txt` both serve their markers.
6. Unlinking (`DELETE /v1/env-groups/<group>/services/<srv>`, 204) also rolls with no build. `/etc/qa-grp.txt` is gone, but the root keeps `qa-grp.txt` as a dangling link (404 through the server; `ls` would still list it).

## Root cause (partly traced)

- The root copies are links that the native Dockerfile makes at build time (`nativeSecretFileLinks`, `lego/operator/internal/build/native.go:486`). The name list is `Options.NativeFiles`, which is the merged projection's keys (`lego/operator/internal/controller/app_controller.go:1357`). So a release only has the links its image was built with.
- A group link puts the group's files Secret into `spec.filesFromSecrets` (`lego/backend/internal/envgroups/service.go:1270`). That list is part of the native artifact identity (`lego/operator/internal/controller/release_identity.go:197-200`). Yet on production the link deploy reused the old image. Next step: find why the identity did not change, or why the changed identity still reused `gen-2`. The candidates are the release-config snapshot path (`release_config_selection.go:120`, `historicalSourceName`) and the auto-deploy staging from w4/m239.
- A file added to a group that is already linked changes no ref at all, so it can never produce a new artifact under the current identity.

## Fix

A release of a native service must have a root link for every secret file name it mounts and no link for a name it does not. Two ways to get there:

- Build whenever the set of mounted file names differs from the names the image was built with. This covers a link, an unlink, and a group or service file being added or removed.
- Or make the links independent of the image.

ADR013 rejected per-file `subPath` mounts and start-time links (w8/m154 t001). Pick an approach, record it there, and correct ADR013's "Every deploy of a native service builds" sentence.

## Blast radius

These may skip the build in the same way. Check each one:

- the env-group patch modes `deploy` versus `rebuild` (`PATCH /v1/env-groups/{id}/contents`);
- the service environment patch's `deploy` mode with an added or removed service secret file;
- a Blueprint sync that links a group;
- cron jobs, workers, private services and the pre-deploy Job (same image).

Docker and image services are unaffected: Render gives them `/etc/secrets` only.

## Acceptance

- Repeat steps 1–4 on production. `/root/qa-grp.txt` and `/root/qa-grp2.txt` serve their markers right after each roll, with no manual deploy.
- After an unlink, the name is gone from both paths.
- Regression tests cover link, unlink and group-file add for a native App.
- The control (a build) and a service's own secret file keep working.
