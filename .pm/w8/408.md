# A Key Value client connecting from an address outside the IP allow list gets a bare TLS EOF, where Render answers "AUTH failed: Client IP address is not in the allowlist."

Why: Render tells a client the allow list blocked it. On bex the same client gets `SSL_connect failed: unexpected eof while reading`, the same error as an outage, a wrong host or a TLS problem, so customers debug the wrong thing. bex's own Key Value skill pack promises Render's message (`lego/cli/internal/skills/pack/skills/bex-keyvalue/references/troubleshooting.md:3`), and clients never see it.

Severity: **minor** (parity; the error misleads and nothing else is lost). Attribution: infrastructure/runtime (`kv-sni-proxy`). Estimate: ~2h across proxy routing, a refusal listener with the store's certificate, and tests. That is over an hour, so promote it to a milestone at triage. Source: routine `cli-qa` sweep r32, 2026-11-22 20:28–20:50 UTC. Context: `https://api.bex.co/v1/`, workspace `bex-canary`, human device login, bex v0.9.0 (`compatible with Render CLI v2.36.0`), deployed revision not observed.

## Render's contract

[render.com/docs/key-value § Enabling external connections](https://render.com/docs/key-value#enabling-external-connections) (`curl https://render.com/docs/key-value.md`, lines 340–344):

> If you attempt to connect from a disallowed IP address, your client will display an error like the following:
>
> `AUTH failed: Client IP address is not in the allowlist.`

`redis-cli`/`valkey-cli` print `AUTH failed: %s` with the server's error string when their opening `AUTH` is refused. So Render completes the TLS handshake and answers the command with that error. The exact wire bytes are inferred from the client's format string and were not captured from Render.

## Evidence (bex, live)

The fixture was a free Key Value `qa-20261122-15ea-kv` (`red-dc1l4lm0usec73d5iumg`) in `bex-canary`. It was created with `bex kv create --plan free --ip-allow-list "cidr=10.0.0.0/8,description=private" --confirm -o json`, so the external endpoint exists but admits no internet address. Its connection info read `externalCertificate: publiclyTrusted`. It was deleted by ID afterwards, and the 404s were confirmed on REST, GraphQL and the CLI. The test host is outside `10.0.0.0/8`.

```text
$ bex kv-cli red-dc1l4lm0usec73d5iumg -- PING        # in a PTY; valkey-cli 8 on PATH
Could not connect to Valkey at red-dc1l4lm0usec73d5iumg.kv.bex.co:6379: SSL_connect failed: unexpected eof while reading
┌────────────────────────────────────────┐
│ An error occurred while running kv-cli │
└────────────────────────────────────────┘
```

`kv-cli` runs the connection info's `cliCommand` (`REDISCLI_AUTH=<redacted> valkey-cli --user <id> -h <id>.kv.bex.co --sni <id>.kv.bex.co -p 6379 --tls`, built by the pinned client at `pkg/tui/views/rediscli.go:118-164`). It has no client-side allow-list check, unlike `psql`. So the server's answer is all the user sees.

## Root cause

`kv-sni-proxy` passes TLS through: Valkey terminates it on 6380 with the store's certificate, and `kv-internal-proxy` passes it through too. See `lego/operator/cmd/kv-sni-proxy/main.go:17-19`, `cmd/kv-internal-proxy/main.go:17-21` and ADR021:108. A source the allow list refuses is handled exactly like an unknown hostname:

- `kvRouter.resolve` returns `false` when `!route.Allow.Admits(source)` (`cmd/kv-sni-proxy/main.go:163-165`).
- `handleConn` then logs `no allowed route` and closes the connection after reading only the ClientHello (`main.go:351-354`).

The client never gets a ServerHello, so all it can report is an EOF.

## Fix

A refused source on a **known** store's hostname completes a TLS handshake under that store's certificate. Every command it sends then gets the RESP error `-Client IP address is not in the allowlist.`, and the connection closes. An unknown hostname is still dropped as today.

- **Recommended:** route refused sources to a refusal listener on the store's own `kv-internal-proxy` (`internal/controller/keyvalue_internal_proxy.go:121` already wires its TLS port).
  - The listener mounts the store's Certificate Secret, which is in the same tenant namespace, so tenant private keys never leave it.
  - It holds no upstream connection.
  - `kvRoute` gains the refusal backend, and `resolve` returns it in place of `false` for a known name whose layers refuse the source.
- **Alternative:** once w4/m357 t002's gated `*.kv.bex.co` wildcard lands, `kv-sni-proxy` could terminate refused clients itself.
- Keep refused handshakes under the existing handshake and per-network caps (w21/070). Do not count them toward the route's connection capacity. Count them as a rejection in the proxy's metrics.
- The skill-pack troubleshooting page already describes the target, so it needs no change.

## Acceptance

In `bex-canary`, on a free Key Value created with `--ip-allow-list "cidr=10.0.0.0/8,description=private"`, from a host outside `10.0.0.0/8`:

- `bex kv-cli <id> -- PING` in a PTY prints `AUTH failed: Client IP address is not in the allowlist.`
- `valkey-cli --tls --sni <id>.kv.bex.co -h <id>.kv.bex.co -p 6379 PING` with no password prints `(error) Client IP address is not in the allowlist.`
- Controls:
  - An unknown hostname (`nope.kv.bex.co`) is still dropped before TLS.
  - An admitted source on a dev-N stack still reads `NOAUTH` without the password and `PONG` with it.
  - A store with external access cleared (`--clear-ip-allow-list`) is unchanged: its connection info has an empty `externalConnectionString`, matching Render's "External URL isn't shown" (key-value.md:387-389).
- Operator tests cover the refused-source route and the refusal listener.

## Unverified

- **Postgres:** `pg-sni-proxy` drops refused sources the same way (`cmd/pg-sni-proxy/main.go:295-297`). A direct `psql` from outside the list reads `SSL error: unexpected eof while reading`. Render's Postgres docs document no client-side message, so this note does not cover Postgres. `bex psql` refuses first on the client with the pinned client's own `IP address (<ip>) not in allow list for <name>` (`pkg/tui/views/psql.go:66`), identical to Render's CLI.
- **What Render sends to a client that never authenticates:** not captured.

## Dedupe

There is no board item on the refused-source error. w8/140 (IPv6 under `0.0.0.0/0`), w8/181 and w4/m233 (allow-list restarts), w4/625 (an empty list drops the handshake) and w21/070 (proxy caps) are neighbours, not duplicates. ADR018 and ADR021 record no divergence for this message.
