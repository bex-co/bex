# Blueprint create from a public GitHub repo fails "Could not reach GitHub" whenever one of its several unretried GitHub API reads fails

Why: in a workspace with no GitHub connection, `bex ea blueprints create` (and the dashboard's New Blueprint) cannot read a public `render.yaml` for as long as bex-api's anonymous GitHub API calls fail from bex's own network. GitHub's API was intermittently failing that day, even to outside clients, while git transport kept working. bex makes several sequential API reads with no retry and no git fallback, so any one failure blocks the customer, who cannot see or fix it.

**Severity:** major (Blueprint creation impossible throughout the window; nothing is created, and the 503 says to retry). **Attribution:** infrastructure/runtime (bex-api → api.github.com from production), with a server-side mitigation. **Estimate:** ~60m (diagnosis from production logs + fallback). **Source:** `/qa-find-bugs-cli` w8 loop sweeps `18cb` and `8c72`, 2026-11-08.

## Evidence

Checkout build `bex vqa-460c283a6`, Render CLI v2.35.0 `24ac2d60fdb2`, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`, **no GitHub connection**, per w4/528), human OAuth (workspace owner's CLI login), production pin `19dfc2982`.

After every attempt, `GET /v1/blueprints?ownerId=…` listed only the pre-existing `exs-dbk3isgrv49s73eq43lg`, so nothing was created.

**Recovery (sweep `4d90`):** at 11:53:14Z the same create returned `planned` in 1.52 s. The full walk then passed: `approve` → `success`, child `hello-node-wbby` served 200, re-`plan` → `no_changes`, `update --auto-sync=false/--name` applied, and an unknown `--branch` gave 400 `branch_not_found`. Everything was deleted afterwards. The failure window on bex was therefore at least 10:44–11:26Z and ended by 11:53Z.

Controls from the QA host, same window: `https://api.github.com/repos/bex-co/bex/contents/examples/hello-node/render.yaml?ref=main` → 200 (10:45Z), `raw.githubusercontent.com/…/render.yaml` → 200, `codeload.github.com/bex-co/bex/tar.gz/refs/heads/main` → 200 (27.8 MB). A static-site build on production cloned `https://github.com/bex-co/bex@2d45368` at 11:21:32Z, so git transport from the builders worked while the API reads failed. In the same window bex's builders received non-asset bodies for GitHub release downloads (w8/m148).

**Correction (sweep `bf43`, 13:07–13:08Z, pin `2d453686f`):** GitHub's API also failed for outside clients. From the QA host, `GET https://api.github.com/repos/bex-co/bex/contents/examples/hello-node/render.yaml?ref=main` returned **500** once (13:07:08Z, 0.8 s), and one HTTP/2 stream was reset (`CANCEL`), followed by 200s. githubstatus.com reported "All Systems Operational" throughout. bex's create failed twice in that minute (503 at about 13:06Z and 11.45 s at about 13:07Z), then succeeded at 13:08:36Z in 0.91 s. The earlier "while GitHub serves everyone else" overstated it. Part of today's failure is genuine, intermittent upstream API error, which bex maps correctly to 503. The bex-side defect is fragility: one create makes several sequential GitHub API reads (`ResolveBlueprintCommit`, then `FetchBlueprintFileAtCommit`, `blueprint.go:360-370`) with no retry for idempotent 5xx/reset and no fallback to git transport, which kept working on the builders throughout.

## Analysis

- `lego/backend/internal/apps/blueprint.go:421-437` (`classifyBlueprintFetchError`) maps 404 to file-not-found, 401/403 to access-denied and 429 to "GitHub is rate-limiting bex". Branch resolution maps the coded `GITHUB_RATE_LIMITED` from w4/528 to the rate-limit reason too (`:2370-2378`). The answer was the generic "Could not reach GitHub", so the failures were **5xx or transport errors/timeouts**, not a classified rate limit. The 13–30 s durations fit timeouts (`github/client.go:123`, 30 s per request).
- **Cause unverified:** the HTTP status and error of bex-api's GitHub calls are not observable from outside. Possibilities: degraded routing from bex's egress to `api.github.com`, GitHub blocking that egress range, or an unclassified anonymous rate-limit form.

## Fix

1. Diagnose from production bex-api logs for 09:45–11:30Z: status, latency and error of each GitHub call on the Blueprint paths (`ResolveBlueprintCommit`, `FetchBlueprintFileAtCommit`, `ValidateRepo`). Record the result here.
2. Retry each idempotent GitHub GET once or twice on 5xx or a stream reset, with a short jittered backoff that stays inside w5/m286's 28 s request budget. Then, for a public repo, when the API read still fails with 5xx/transport/timeout, fall back to git smart-HTTP. Resolve the ref with `ls-remote`, which w8/209 already implements for non-GitHub hosts in `github.Service.resolveCommit`. Read the file at that commit through a bounded shallow fetch, with the same no-existence-oracle rule and size limit. Keep the existing reasons when both paths fail.
3. Optionally (the follow-up w4/528 left unfiled): authenticate public-repo reads with a platform GitHub App installation token so they stop sharing GitHub's anonymous 60 requests/hour per egress IP.

## Acceptance

- Unit: API transport error / 502 / timeout for a public repo → the file is read through the git fallback and create succeeds. Private-repo and 404 behavior unchanged.
- Live: `bex ea blueprints create` on the public example succeeds. A forced API failure in dev shows the fallback is used and logged.
