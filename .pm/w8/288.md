# `bex logs --tail` first replays the instance's whole log since it started; Render's tail streams only new lines

Why: Render's CLI documents `--tail` as "Stream new logs", and its API's subscribe as "Logs are streamed in real-time as they are generated." On bex, a tail opened with no `--start` first prints everything the running instance has logged since its container started, then the new lines. On a service that has run for days that is the whole retained container log, delivered before the first new line, and a reader cannot tell where "now" begins. bex's own build tail already starts at the moment the subscription opens (w8/m159).

**Severity:** minor (no line is lost and the new lines do arrive; the tail opens with a burst of old ones). **Attribution:** server (bex-api live tail, `logs` service). **Estimate:** ~45m. **Source:** `/qa-find-bugs-cli` w8 loop sweep `c3d4`, 2026-11-12 UTC, released `bex v0.5.0` (Render CLI v2.35.0), `https://api.bex.co/v1/`, production pin `3d66946c9e16`, workspace `bex-canary`, QA human device login; first seen on the w8/m147 replay the same morning.

## Evidence

Free native Node web service `qa-20261112-c3d4-tail` (`srv-dbqpllpn6kgc738372h0`) whose start command logs `c3d4-seq <n> <ISO time>` every 3 s; container started 10:57:57 UTC, live at 10:58:42.

```text
# tail opened 11:02:01, no --start
$ timeout 25 bex logs -r srv-dbqpllpn6kgc738372h0 --tail -o text
2026-11-12 10:57:57  c3d4-seq 1 2026-11-12T10:57:57.228Z      ← the container's first line
…                                                             ← 82 lines from before the tail opened
2026-11-12 11:02:01  c3d4-seq 82 …
…                                                             ← then 8 new lines
exit 124 (timeout), 90 c3d4-seq lines in all

# control: the same tail with --start set to the moment it opens
$ timeout 20 bex logs -r srv-dbqpllpn6kgc738372h0 --tail --start 2026-11-12T11:02:33Z -o text
2026-11-12 11:02:33  c3d4-seq 93 …                            ← 7 lines, all new
```

The datastore tails do the same. On the w8/m147 replay, a free Key Value tail opened at about 10:24:19 began with 17 lines from 10:23:33 on (the store's creation), and a free Postgres tail opened at about 10:31:11 began with 12 lines from 10:23:51 on.

The pinned client sends no `startTime` on a tail unless `--start` is given: `LogLoader.TailLogs` builds `ListLogsParams` with `StartTime` only from the flag (`pkg/tui/views/logloader.go:162-183`), and `LogRepo.TailLogs` subscribes with those params (`pkg/logs/tail.go`, `pkg/logs/repo.go:41-43`).

## Expected

- A tail with no `startTime` streams what is generated from the moment it opens: no line older than the subscription, as Render documents for `--tail` ("Stream new logs") and for `GET /v1/logs/subscribe` ("Logs are streamed in real-time as they are generated").
- A tail with `startTime` keeps today's meaning, the lower bound of the window (the dashboard sends one on every connect, w6/m111), and a reconnect's `Last-Event-ID` still resumes after what was delivered (w6/m93).
- Render's exact behavior for a subscribe without `startTime` was not observed (no Render account); the claim rests on its documentation.

## Root cause

- `rest.go` (subscribe handler, around `:150-170`) passes a query with a zero `Since` when the request has no `startTime` and no `Last-Event-ID`.
- The pod producer follows each container from `q.Since` (`service.go:1610`, `streamContainerLogs`), and `NewPodLogStream` sets the kubelet's `SinceTime` only when `since` is non-zero (`podlogs.go:58-63`): zero means "from the beginning" (`service.go:147`), so the kubelet replays the container's whole log.
- The request-line producer starts its cursor at the same zero and floors it at one minute ago (`pollRequestLogs`, `service.go:1725-1745`), so it also replays up to a minute of request lines.
- `followBuilds` already sets `q.Since = time.Now()` for a zero `Since` (`service.go:1341-1343`), the Render reading; the pod and request producers were never given it.

## Fix

1. When a live subscription carries no `startTime` (and no `Last-Event-ID` to resume from), start it at the moment it opens: set `q.Since = time.Now()` once in `FollowLogs` (or the subscribe handler), before the producers start, so pods, datastores, request lines and builds share one rule. Leave history queries alone.
2. Check the finished-cron-run case (`service.go:1575`, "a Succeeded cron run replays once"): with the new rule, a tail opened between runs shows the next run, not the last one. That is Render's "new logs" reading; record it in ADR010 and update the tests that pinned the replay.
3. ADR018's "Application logs (query + live tail)" row: a tail starts at the moment it opens unless `startTime` is given.

## Acceptance

- `bex logs -r <srv> --tail -o text` on a service that has logged for a few minutes prints no line older than the moment it was started; new lines arrive as today.
- The same for a Key Value and a Postgres tail.
- `--tail --start <t>` still starts at `t`; the dashboard's Logs tab (which sends `startTime`) and an EventSource reconnect are unchanged.

## Unverified

- Render's behavior for a subscribe with no `startTime` (documentation only).
- Whether any bex surface relies on the replay (the dashboard sends `startTime`; the interactive `bex deploys create` stream sends `StartTime: now`, w8/m159).
