# The docs tell users of the released bex v0.7.0 to set `BEX_API_KEY`, which v0.7.0 ignores: the CLI says "run `bex login`" without sending the key

Why: `8227312bc` (w7/m426) added `BEX_API_KEY` to the launcher at 12:59 UTC on 2026-11-16, after bex CLI v0.7.0 was released (10:26 UTC). Its docs say the variable "needs a `bex` newer than v0.6.0", and v0.7.0 is newer than v0.6.0. Someone on the latest release who follows the CI recipe (`BEX_API_KEY=<key> bex services -o json`) gets a login error, with nothing to say the release lacks the variable.

**Severity:** minor (docs only; the workarounds the same paragraph names, `BEX_ACCESS_TOKEN=<key>` and `RENDER_API_KEY=<key>`, work on v0.7.0). **Attribution:** docs, for the released launcher. **Source:** `/qa-find-bugs-cli` sweep `9c1d`, 2026-11-16, released bex CLI v0.7.0 (`bex-cli/v0.7.0` is `81d60a943`; `git merge-base --is-ancestor 8227312bc bex-cli/v0.7.0` is false).

## Evidence (production, 2026-11-16 15:00 UTC)

The run used an empty config (no stored login), the released `bex` v0.7.0, `BEX_HOST=https://api.bex.co/v1/`, `BEX_WORKSPACE=<tea-id>`, and one variable at a time set to a placeholder that is not a real key:

| Variable set | Result |
| --- | --- |
| none | `Error: run \`bex login\` to authenticate`, exit 1, 0.0 s |
| `BEX_API_KEY=bex_qaprobe_notarealsecret` | `Error: run \`bex login\` to authenticate`, exit 1, 0.0 s: ignored, nothing sent |
| `BEX_ACCESS_TOKEN=bex_qaprobe_notarealsecret` | `Error: your token is expired; run \`bex login\` to get a new one`, exit 1, 0.9 s: sent as the bearer, refused with 401 |
| `RENDER_API_KEY=bex_qaprobe_notarealsecret` | as above, 0.6 s |

With a real key, the two variables that are sent would authenticate, since bex-api accepts a key as a bearer from pin `48bc2a0fedda` on. `BEX_API_KEY` would still be ignored.

## The wording

- `docs/bex-cli.md:106`: "**Released binaries.** `BEX_API_KEY` needs a `bex` newer than v0.6.0: the released binary gains it at the next CLI release. With a binary released before that, `BEX_ACCESS_TOKEN=<key>` (or `RENDER_API_KEY=<key>`) does the same thing…"
- `lego/cli/README.md:70`: "The released binary gains `BEX_API_KEY` at the next CLI release (after v0.6.0); with an older binary, `BEX_ACCESS_TOKEN=<key>` (or `RENDER_API_KEY=<key>`) does the same thing…"
- `docs/bex-cli.md:87-100` (§ CI and automation) shows `BEX_API_KEY=<key> bex services -o json` and a GitHub Actions `env:` block with `BEX_API_KEY` as the way to do it, with no version caveat next to the recipe.

## Fix

- Say "newer than v0.7.0" and "(after v0.7.0)" in both places. Put the one-line fallback (`BEX_ACCESS_TOKEN=<key>` on v0.7.0 and older) next to the recipe in § CI and automation, not only in the caveat below it.
- Once a release containing `8227312bc` is out, replace the caveat with the version that has it (for example, "since v0.8.0").
- A doc that names "the next release" can go stale on the day it is written, as here. An alternative is to state the commit (`8227312bc`) and let `/release cli` rewrite the sentence; the `/release` skill's checklist could grep for "next CLI release".
- No code change.
