# 220 — Toggling environment isolation briefly cuts a Key Value off from its own environment

Why: Render says same-environment traffic keeps working through an isolation change; bex replaces the Key Value's internal proxy on every toggle, so its own services lose it for a few seconds.

Found 2026-10-29 by the `/loopx w8` m136 live check (production, Scale workspace `bex`): after enabling isolation the production-environment probe got one `TCPFAIL` (+23 s), and after disabling it both probes failed at +14 s with a TLS timeout at +45 s, while the Valkey pod itself never restarted. The cluster showed the Key Value's `-internal` proxy Deployment roll to a new ReplicaSet each time. Likely cause: `lego/operator/internal/controller/keyvalue_internal_proxy.go:~79` puts `keyValueInternalProxyPodLabels(kv)` — including `labelNetworkIsolation` — into the one-replica Deployment's pod template, so the toggle changes the template; the Valkey StatefulSet already has a "never roll the template" guarantee (`TestKeyValueIsolationToggleNeverRollsTheTemplate`). Fix: keep the isolation label off the proxy's pod template (select it by namespace/policy instead, or relabel pods in place), or make the rollout surge-before-terminate; add the same no-roll regression for the proxy. Acceptance: an isolation toggle leaves the proxy's ReplicaSet unchanged and a same-environment probe never fails.

Also seen (minor, unverified): `POST /v1/key-value` with `"region":"fsn1"` is refused `invalid request body at /region` although responses report `region: "fsn1"`.
