# A caller's `X-Forwarded-For` is dropped at the edge, where Render keeps it and appends the client, so an app behind its own proxy or CDN never sees the end user's address

Why: on Render a web service fronted by the customer's own proxy (a Vercel or Netlify rewrite, Fastly, an nginx tier) still gets the end user in `X-Forwarded-For`, because Render keeps the incoming list and appends the client after it; on bex the app only ever sees the proxy's address, so IP rate limits, geo lookups and audit logs collapse onto one address after a move from Render.

Severity: **minor** (parity; it loses data only for apps behind a proxy of their own). Attribution: platform edge (Traefik entrypoint forwarded-header trust). Estimate: ~1h (edge config plus the plugin overwrite below; promote if the bex-api audit grows). Source: `/qa-find-bugs-cli` cli-qa routine sweep 251abe, 2026-11-22 14:17 UTC. Context: `https://api.bex.co/v1/`, workspace `bex-canary`, human device login, bex v0.9.0 (`compatible with Render CLI v2.36.0`), deployed revision not observed.

## Evidence

The bex fixture was a free image web service `qa-20261122-251abe-echo` (`srv-dc1finj88nrc738n1q20`, `docker.io/ealen/echo-server:0.9.2`, made with `bex services create --type web_service --image … --plan free --env-var PORT=8080 -o json --confirm`), deleted by ID after the sweep. The Render oracle is the public Render web service `httpbin.onrender.com` (`server: cloudflare`, `x-render-origin-server: uvicorn`), read with two GETs. The client address is redacted as `<client-ip>`.

```text
$ curl https://<host>/headers -H 'X-Forwarded-For: 198.51.100.7' -H 'True-Client-IP: 203.0.113.77' \
    -H 'X-Request-Start: 1' -H 'Rndr-Id: forged-id'

# Render (httpbin.onrender.com), what the app received
x-forwarded-for: 198.51.100.7,<client-ip>, 104.23.243.132, 10.25.100.135
true-client-ip:  <client-ip>
x-request-start: 1795357106957145
rndr-id:         395e8f4b-4a91-4763
# Render with no X-Forwarded-For sent
x-forwarded-for: <client-ip>, 172.69.134.200, 10.25.100.135

# bex (qa-20261122-251abe-echo.onbex.co), what the app received (same request)
x-forwarded-for: <client-ip>
x-real-ip:       <client-ip>
true-client-ip:  <client-ip>
x-request-start: 1795357070132080
rndr-id:         476a4574-5bf3-d4ae
```

So Render keeps the caller's entries and appends the client, then its Cloudflare and internal hops. bex replaces the whole list with the TCP peer. The other headers agree: a forged `True-Client-IP`, `X-Request-Start` and `Rndr-Id` are replaced on both (w8/m123, w8/196, w8/m125), and a forged `X-Forwarded-Proto: http` reads `https` on bex.

Render's own record agrees with the capture: its feature request "Send the correct X_FORWARDED_FOR" ([feedback.render.com](https://feedback.render.com/features/p/send-the-correct-xforwardedfor), marked complete 2021-05-28) has a staff answer "we set the first IP in the list to the real client IP", and a 2024 comment there reads "Render does not clear or reset any passed-in X-Forwarded-For header (it only appends to it)". Render's docs do not document the header.

## Root cause

The tenant entrypoints `web` and `websecure` (`deploy/gitops/overlays/prod/values/traefik.values.yaml:47–66`, base `deploy/gitops/base/values/traefik.values.yaml`) set `proxyProtocol.trustedIPs` but no `forwardedHeaders`. So Traefik's forwarded-headers handler treats every client as untrusted and deletes all incoming `X-Forwarded-*` before the entrypoint middlewares run. The proxy then writes the peer alone. ADR022 § client identity headers (line 178) records "`X-Forwarded-For`/`X-Real-IP` keep Traefik's behavior: … a forged value is replaced", but ADR018 records no signed-off divergence, so parity wins.

## Fix

- Keep the caller's `X-Forwarded-For` and append the real client after it, as Render does. One way: `forwardedHeaders.insecure: true` on `web`/`websecure` (base and prod), so the list survives and the proxy appends the peer.
- Then make the existing entrypoint plugin `deploy/gitops/charts/traefik-plugins/clientipheaders/clientipheaders.go` overwrite every other forwarded header that the trust change would let a caller set: `X-Forwarded-Proto` (from the TLS state), `X-Forwarded-Host`, `X-Forwarded-Port`, `X-Forwarded-Prefix`, `X-Forwarded-Server` and `X-Real-IP` (the post-PROXY peer). Today's results for those must not change. Read its line 206 comment first: it relies on the entrypoint setting `X-Forwarded-Proto`.
- If Traefik offers a narrower switch that keeps only `X-Forwarded-For`, prefer it.
- Record the contract in ADR022 and the ADR018 inbound-IP row.

## Blast radius

- Inbound IP rules match the TCP source (the middleware sets no `ipStrategy`, ADR018 inbound-IP row), so they are unaffected. Prove it with a forged `X-Forwarded-For` against a restricted service.
- bex-api `lego/backend/internal/core/clientip.go` walks `X-Forwarded-For` from the right past trusted proxies, so a longer list must still give the same client. Re-check its callers `api/ratelimit.go`, `api/security.go`, `cliauth/ratelimit.go`, `sshgateway/webshell/websocket.go` and `sshgateway/agentattach/agentattach.go`.
- The activator (`lego/operator/cmd/activator/hold.go:132`) and the static edge cache (`lego/operator/internal/edgecache/edgecache.go:390–409`) copy the inbound list, so they pass it on. Check that a woken service and a static site behave the same.

## Acceptance

- Live, after GitOps syncs Traefik, on a fresh free echo web service in `bex-canary` (deleted by ID, with a 404 proof): a request sending `X-Forwarded-For: 198.51.100.7` reaches the app as `198.51.100.7, <client-ip>`, and one sending none as `<client-ip>`.
- Forged `X-Forwarded-Proto: http`, `X-Forwarded-Host`, `X-Real-IP`, `True-Client-IP`, `X-Request-Start` and `Rndr-Id` still reach the app with the real values.
- A forged `X-Forwarded-For` does not pass a Scale-workspace inbound IP rule.
- `scripts/gitops-validate.sh` and `scripts/edge-proxyprotocol-validate.sh` pass. `clientipheaders` unit tests cover each overwrite.

## Unverified

- Render's hop list after the client (`<cloudflare-edge>, 10.x`) is not something bex can or needs to match. Only the caller's entries and the client's position matter.
- Whether Render merges repeated `X-Forwarded-For` header lines was not checked.
