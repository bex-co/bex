# A source update before a release's build starts still rolls the previous image as that release

Why: w8/124 covered a release whose build had started or whose artifact was built. Two narrower cases still record a revision for code that never ran.

Found by the w8/124 review on 2026-10-19 by reading code; not reproduced live. In each case, the saved spec makes the decision instead of the release in flight:

1. **The build has not started yet.** Release N's build is queued at the build cap, waiting on a registry credential, or its pod is still pending (`status.buildRun` not started for N) when an Update Source is saved. Pinning N would make `buildFromSource` read the saved repo/branch (`effectiveDeployRef(app.Spec)`) and store that build under N's fingerprint. Not pinning, as today, takes the `sourcePending` path. There `reusableArtifactImage` returns `status.image`, so N rolls N−1's image as `rev-N`.
2. **The source moves from a repo to a prebuilt image.** That Update Source arrives while repo-backed N is in flight. `pinnableSourceRelease` reads the saved spec (`spec.image` set), so `releaseInFlight` is false and the same `sourcePending` path applies.

Fix direction:

- Record the release's own source at dispatch (repo, branch, commit, image-vs-repo), so pinnability and the build both read status, not the saved spec.
- Or settle N as superseded when its own source can no longer be carried. Its row then closes canceled, and the saved source waits for the next deploy.

Tests: a pending source saved while N's build is queued and while N is mid-repo-to-image switch; assert N never rolls N−1's image as `rev-N`.
