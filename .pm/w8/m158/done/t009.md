## Objective

Each outage records exactly one `server_failed`, and the next `server_available` closes it.

- When a process exit of the serving release started the outage, the one event is the exit's, with its cause and instance. This holds whether bex-api sees the exit or the readiness loss first.
- Any other outage, including a health-check failure that begins after an earlier crash already recovered, records the sampled `unhealthy` event.

## Context

- **Found:** QA loop round 176 replaying t008 (this milestone's DoD), 2026-11-12 07:32–07:48 UTC, pin `3d66946c9e16`, which carries t001–t007. See the README's round 176 probe.
- **Fixture:** Free web service `qa-20261112-r176-crash` (`srv-dbqmmsiibtfs738vknt0`), image `docker.io/library/node:22-alpine`, Health Check Path `/health`. Its `node -e` server exits on `/exit3` and `/exit0`, allocates memory on `/oom`, and answers 500 on `/health` after `/sick`. It was deleted afterwards (DELETE 204, then GET 404).

### Defect 1 — DoD 1: a 10 s crash records two `server_failed`

- **Probe:** `curl /exit3` at 07:33:48 → 502. The service read 503 at 07:33:52 and 07:33:55, and 200 from 07:33:59.
- **Events:** `GET …/events?type=server_failed` returns two events, both stamped 07:33:49:
  - `{"instanceID":"tea-…-r176-crash-6cdcf48bcf-h7vz4","reason":{"evicted":false,"nonZeroExit":3}}`, with key `fact:exit:…:h7vz4:1`;
  - `{"reason":{"evicted":false,"unhealthy":"The instance failed its health check"}}`, with key `fact:observed:…:failed:1794468841754168313`. The key's stamp is the pass at **07:34:01**.
  - Then `server_available` at 07:34:03.
  - The dashboard shows two "Instance failed" rows: "The instance's process exited with status 3 and was restarted" and "A running instance failed its health check."
- **Mechanism (partly traced):**
  - **The suppression is order-dependent.** The sampled outage is dropped only when an exit-caused `server_failed` is **already committed** at or after the outage time minus 3 minutes (`lego/backend/internal/store/event_facts.go:434-444`; `instanceExitSinceSQL` and `instanceExitOutageWindow` at `:613-624`).
  - Within one pass the reconciler inserts exits before the observed state (`reconciler.go:529-533`), so the order is right only when the exit is already in `status.instanceExits` on the pass that confirms the outage.
  - **The exit reaches status late.** The operator reads only `LastTerminationState.Terminated` with `RestartCount > 0` (`lego/operator/internal/controller/instance_exits.go:116-135`), which exists only once the kubelet has restarted the container.
  - The not-ready pass (`reportRolloutProgress`, `app_controller.go:3751-3755`) usually runs before that, so it writes `Ready=False` with no exit.
  - Here the outage was confirmed on the 07:34:01 pass, and the exit fact was inserted on a later one.
  - **Not traced:** which write or watch delay held the exit back for 12 s although the container had restarted by 07:33:59: the operator's reconcile trigger, the status write, or bex-api's List snapshot.
- **Controls:**
  - The OOM kill (07:35:15, down about 40 s) and `exit(0)` (07:36:54, down about 45 s) each recorded exactly one `server_failed`, with the exit's cause.
  - In both, the longer kubelet back-off meant the exit was in status before the outage was confirmed.

### Defect 2 — DoD 3: a later health-check outage within 3 minutes is swallowed

- **Probe:** `curl /sick` at 07:38:07 made `/health` answer 500. The service read 503 from 07:38:20 through the last poll at 07:40:21, and had recovered by itself before 07:41:12 (presumably a liveness restart; the user restart came later, at 07:41:21).
- **Events:**
  - No `server_failed` was recorded for that outage.
  - `server_available` was recorded at **07:41:12**, directly after the previous `server_available` (07:37:41) with no failure between.
  - The dashboard shows "Service recovered" twice in a row.
- **Mechanism:** the window compares only times.
  - The outage's `server_failed` is dated at its Ready transition, about 07:38:10.
  - `instanceExitSinceSQL` found exit facts at 07:35:20 (`oom_killed`) and 07:36:55 (`early_exit`) in `[07:35:10, …]`, so the outage was skipped.
  - Both exits' outages had already closed, with `server_available` at 07:36:10 and 07:37:41.
  - The checkpoint still moved to `unhealthy`, so the recovery wrote an unpaired `server_available`. That is the shape w4/m230 and w4/350 removed.
- **Control:** `curl /sick` at 07:42:47, more than 3 minutes after the last exit (07:36:55), recorded `server_failed {"reason":{"unhealthy":"The instance failed its health check"}}` at 07:43:07 and `server_available` at 07:45:48. DoD 3 holds when no exit is in the window.

## Steps

1. **Make the attribution order-independent:** whichever fact arrives second resolves to one event.
   - Recommended: the operator records an exit from the app container's current `State.Terminated` too, so the exit is in status on the same write that drops `Ready`.
     - Today only `LastTerminationState` with `RestartCount > 0` is read.
     - Its key must stay stable across the restart, so a resync replays one fact: the instance plus the restart count the exit will carry.
   - And/or: bex-api holds an outage's confirmation for one pass while the observation shows the serving release's app container restarting or terminated.
   - Do not delete a recorded and delivered `server_failed` after the fact: webhooks, push and alert emails have already gone out.
2. **Narrow the window to the outage the exit started.** An exit explains a sampled outage only when:
   - its `FinishedAt` is within the readiness slack plus the confirmation debounce of the outage's start (its Ready transition), not anywhere in the 3 minutes before;
   - and no `server_available` was recorded between that exit and the outage's start.
   - Otherwise the sampled outage records its own `server_failed`.
3. **Tests** (store reconciler and `event_facts` tests, plus operator `withInstanceExits`):
   - outage confirmed before the exit is in status → exactly one `server_failed`, the exit's;
   - exit already in status → one, as today;
   - an `oom_killed` exit closed by `server_available`, then a health-check outage 90 s later → the outage records `unhealthy` and its recovery pairs with it;
   - a crash loop keeps its `afterUnready` behavior, with one event for the first exit.
