# `ERLANG_VERSION=28.3` builds on whatever OTP the Elixir image carries (28.5.0.6), while the build log says it was honored; Render installs the requested Erlang/OTP

Why: Render's [Elixir and Erlang/OTP versions](https://render.com/docs/elixir-erlang-versions) page lets a service pin both `ELIXIR_VERSION` (example `1.19.5`) and `ERLANG_VERSION` (example `28.3`). bex checks only that `ERLANG_VERSION`'s **major** matches the Elixir line, then builds on the official `elixir:<version>` image, whose OTP is whatever that image was built with. A service pinned to OTP 28.3 for a known-good runtime silently runs 28.5.0.6, and the build log claims `from ELIXIR_VERSION=1.19.5, ERLANG_VERSION=28.3`. w8/175 made exact patches work for Python/Node/Ruby/Elixir but not Erlang.

Severity: minor (a silently different runtime than requested). Source: `/qa-find-bugs-cli` loop sweep a5c0, 2026-10-23 UTC, bex v0.3.3, pin Render CLI v2.27.0 `a764810a7682`, platform pin `fa8ac5bba24a`, `https://api.bex.co/v1/`, `bex-canary`, human device login.

## Root cause

`lego/operator/internal/build/nativeversion.go:574-594` (`resolver.elixir`) compares only `ERLANG_VERSION`'s major with the line's `otp` and appends it to `choice.Source` for the log line. The image remains the Elixir image chosen by `ELIXIR_VERSION` (w8/175 exact-tag pinning), regardless of the requested OTP minor/patch.

## Fix

When `ERLANG_VERSION` is more specific than a major and differs from the chosen image's `OTP_VERSION`, build on an image that carries both versions. Prefer hexpm's published Elixir/Erlang combinations (`hexpm/elixir:<elixir>-erlang-<otp>-debian-bookworm-<date>`), resolved and pinned by digest at build time like w8/175. If no combination exists, fail by name, as for an unsupported version, so nothing claims an Erlang it does not run. The `Using …` log line names the OTP actually installed. ADR060 § Elixir and ADR018:84.

## Blast radius

Elixir native builds with a minor- or patch-level `ERLANG_VERSION` (and `.tool-versions` `erlang` entries if the resolver reads them). Major-only `ERLANG_VERSION=28` keeps today's behavior. Default builds are unaffected.

## Fix — 2026-10-29

**Production reproduction (before the fix), pin `03043c7df363`:** `render-examples/phoenix_hello` with `ELIXIR_VERSION=1.19.5` and `ERLANG_VERSION=28.3` built and ran on OTP 28.5.0.6. The log said `Using Elixir 1.19.5 (from ELIXIR_VERSION=1.19.5, ERLANG_VERSION=28.3)`.

**Change (operator, `lego/operator/internal/build`):**

- `resolver.elixir` still checks that `ERLANG_VERSION` matches the line's OTP major, and now also rejects a malformed value by name (`ERLANG_VERSION=28.x is not an Erlang/OTP release`). A minor or patch release (`28.3`, `28.3.1`, `OTP-28.5.0.6`) is carried as `NativeChoice.erlang`. A major alone (`28`) keeps the line image and makes no registry call, as before.
- The resolve phase builds on two images instead of the official elixir image (`pinErlangVersion`, `nativeerlang.go`), so the OTP is the requested one:
  - The base is the official `erlang` image of the newest matching OTP release, by its four-part tag (`erlang:28.3.3.0`). Only the four-part tag names a single release; `28.3` and `28.3.3` follow newer patches. This image is the official elixir image's own base, so the Debian buildpack-deps toolchain (gcc, make, git, curl), `rebar3` and the `/usr/local` layout are unchanged.
  - Elixir's tree (`/usr/local/lib/elixir`, plus the `elixir`/`elixirc`/`iex`/`mix` links and the official image's `LANG`/`ELIXIR_VERSION`) is copied from hexpm's build of the same Elixir on the same OTP (`hexpm/elixir:1.19.5-erlang-28.3.3-debian-trixie-20260824`).
  - Both images are digest-pinned at resolve time. The hexpm base image itself is not used: it has no compiler or git, which was the BLOCKED record's prerequisite (3).
- hexpm tags are listed through the Hub API tag search (`DockerHubResolver.ListTags`, prerequisite (1)). The registry's own `/tags/list` took 20–30 s per page, or returned 504, when seeking into hexpm/elixir. Digests come from the registry as before (prerequisite (2)). The reviewed-repository allowlist gains only `erlang` and `hexpm/elixir`.
- The log names the OTP installed: `==> Using Elixir 1.19.5 on Erlang/OTP 28.3.3 (from ELIXIR_VERSION=1.19.5, ERLANG_VERSION=28.3)`.
- No combination: the build fails as a tenant error, `ERLANG_VERSION=28.9 is not available with Elixir 1.19.5: no published image carries Elixir 1.19.5 on Erlang/OTP 28.9; set ERLANG_VERSION to another OTP 28 release (or 28 for the line's own) or choose another ELIXIR_VERSION`. A registry failure fails the build as a platform error. Neither falls back to another OTP.
- **Boundary/admission:** no gitops change is needed. `bex-build`'s `allow-required-egress` already allows public TCP 443, which covers `hub.docker.com`, `auth.docker.io` and `registry-1.docker.io`. BuildKit already pulls arbitrary public bases for tenant Dockerfiles. Pod admission checks the built tenant image in Zot, not build bases.
- Docs: ADR060 D7 addendum (Elixir row, plus an "Exact Erlang/OTP" paragraph under the resolution rules) and ADR018:84.
