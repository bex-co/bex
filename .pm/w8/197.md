# `ERLANG_VERSION=28.3` builds on whatever OTP the Elixir image carries (28.5.0.6), while the build log says it was honored; Render installs the requested Erlang/OTP

Why: Render's [Elixir and Erlang/OTP versions](https://render.com/docs/elixir-erlang-versions) page lets a service pin both `ELIXIR_VERSION` (example `1.19.5`) and `ERLANG_VERSION` (example `28.3`). bex checks only that `ERLANG_VERSION`'s **major** matches the Elixir line, then builds on the official `elixir:<version>` image, whose OTP is whatever that image was built with. A service pinned to OTP 28.3 for a known-good runtime silently runs 28.5.0.6, and the build log claims `from ELIXIR_VERSION=1.19.5, ERLANG_VERSION=28.3`. w8/175 made exact patches work for Python/Node/Ruby/Elixir but not Erlang.

Severity: minor (a silently different runtime than requested). Source: `/qa-find-bugs-cli` loop sweep a5c0, 2026-10-23 UTC, bex v0.3.3, pin Render CLI v2.27.0 `a764810a7682`, platform pin `fa8ac5bba24a`, `https://api.bex.co/v1/`, `bex-canary`, human device login.

## Evidence

Owned fixture `srv-dbdhd408dkas73a0v6e0` (`qa-20261023-a5c0-phx`, free web, Render's own `render-examples/phoenix_hello` with the [deploy-phoenix](https://render.com/docs/deploy-phoenix) build/start commands and a throwaway `SECRET_KEY_BASE`; deleted by ID afterwards). That image's config (`skopeo inspect --config docker://docker.io/library/elixir@sha256:d170fadf…`, linux/amd64): `OTP_VERSION=28.5.0.6`, `ELIXIR_VERSION=v1.19.5`.

## Root cause

`lego/operator/internal/build/nativeversion.go:574-594` (`resolver.elixir`) compares only `ERLANG_VERSION`'s major with the line's `otp` and appends it to `choice.Source` for the log line. The image remains the Elixir image chosen by `ELIXIR_VERSION` (w8/175 exact-tag pinning), regardless of the requested OTP minor/patch.

## Fix

When `ERLANG_VERSION` is more specific than a major and differs from the chosen image's `OTP_VERSION`, build on an image that carries both versions. Prefer hexpm's published Elixir/Erlang combinations (`hexpm/elixir:<elixir>-erlang-<otp>-debian-bookworm-<date>`), resolved and pinned by digest at build time like w8/175. If no combination exists, fail by name, as for an unsupported version, so nothing claims an Erlang it does not run. The `Using …` log line names the OTP actually installed. ADR060 § Elixir and ADR018:84.

## Blast radius

Elixir native builds with a minor- or patch-level `ERLANG_VERSION` (and `.tool-versions` `erlang` entries if the resolver reads them). Major-only `ERLANG_VERSION=28` keeps today's behavior. Default builds are unaffected.

## Acceptance

- Unit: `ELIXIR_VERSION=1.19.5`, `ERLANG_VERSION=28.3` resolves to an image whose OTP is 28.3. `ERLANG_VERSION=28` keeps the line image. A non-existent combination fails by name.
- Live after the operator deploy: the phoenix_hello fixture with both variables builds on OTP 28.3 (image config or `erl -eval` in the build), serves 200, and the build log names it. Delete by ID with a 404 proof.
