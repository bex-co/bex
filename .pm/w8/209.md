# A service deployed from a public non-GitHub repository (GitLab, Codeberg, …) gets deploys with no commit: commit resolution is GitHub-only

Why: Render deploys any public Git repository by URL and shows each deploy's commit (SHA and message). bex accepts a public GitLab URL and builds and serves it, but the deploy has no `commit`. bex-api resolves commits only through the GitHub API. Without a commit, the deploy history can't say what is running, a deploy can't be pinned to the SHA that was checked, and rollback targets are unnamed. This is not the GitLab _integration_ that `.pm/DO_NOT_DO.md` rejects (connect, repo listing, private deploy, push-to-deploy). Public repo URLs need no provider connection.

Severity: **minor** (the service works; deploy metadata is missing and the build is unpinned). Attribution: server (bex-api commit resolver). Estimate: ~45m. Source: `/qa-find-bugs-cli` loop sweep 6a81, 2026-10-27 02:41–02:44 UTC. Context: HEAD-built bex `34bcceed6` with pinned Render CLI v2.27.0 `a764810a7682`; platform pin `b4726243e74f`; `https://api.bex.co/v1/`; workspace `bex-canary`; human device login.

## Evidence

```text
$ git ls-remote --symref https://gitlab.com/pages/plain-html.git HEAD
ref: refs/heads/main  HEAD  → 87e8c32b8918a836c09475e0f668ea7c436d3758
$ bex services create --type static_site --name qa-…-gl --repo https://gitlab.com/pages/plain-html --publish-directory public -o json --confirm
exit 0 → srv-dbg0ul4d3d3c73caqavg (repo https://gitlab.com/pages/plain-html, branch main); live in ~17 s; GET / → "Plain HTML site using GitLab Pages"
GET /v1/services/srv-dbg0ul4d3d3c73caqavg/deploys?limit=1 →
  {"id":"dep-dbg0ul4d3d3c73caqb00","status":"live","trigger":"other","bexTrigger":"create","createdAt":…,"finishedAt":…}
  # no "commit" (a GitHub-backed deploy carries {"commit":{"id":<sha>,"message":…}}), and no "startedAt"
```

The fixture was deleted by ID (`GET` 404).

## Root cause

- `apps.resolveDeployCommit` (`lego/backend/internal/apps/commit.go:52`) and `deploys.resolveCommit` (`lego/backend/internal/deploys/service.go:881`) call `Commits.ResolveCommit`, which is GitHub's `commitSource` (`lego/backend/internal/github/service.go:1308`).
- `resolveCommit` returns "no commit" unless `core.CanonicalRepo(repoURL)` starts with `github.com/` (`service.go` ~`:1346`). Public repos resolve only through GitHub's REST `GetCommit` (`resolvePublicCommit`, `:1384`). So every other host deploys without commit metadata ("omitted, not faked", w9/001).

## Fix

- Add a host-agnostic fallback for public HTTPS repos: resolve `ref` to a SHA with the Git smart-HTTP protocol, as `git ls-remote <repo> refs/heads/<ref>` does (anonymous, bounded timeout, the same miss/TTL cache and no-existence-oracle rule as `resolvePublicCommit`).
- That gives the SHA. For the message, either leave it empty (Render shows it, so prefer filling it) or have the operator report the checked-out commit's subject from the clone step into the deploy row.
- Pin the build to the resolved SHA exactly as for GitHub public repos.
- Keep GitHub on its current API path (it also supplies the message and author time).

## Blast radius

- Every service whose repo URL is on a non-GitHub host: GitLab, Codeberg, self-hosted Gitea/GitLab, Bitbucket public repos.
- The deploy list and detail (REST/GraphQL/MCP, CLI `deploys list`, dashboard), `RENDER_GIT_COMMIT` if it reads the same record, rollback/deploy-by-commit selection, and auto-deploy comparisons. Auto-deploy on push for those hosts remains out of scope (DO_NOT_DO).

## Fix — 2026-10-29

**Root cause of the hosted failure.** `resolvePublicGitCommit` only returns SHAs the upload-pack advertisement lists. An explicit historical SHA (here `180e352…`, not a branch or tag tip) is never advertised, so the lookup missed. `deploys.resolveCommit` then wrote the raw `commitId` into `App.Spec.BuildCommit` (the clone still fetched and verified it) but opened the deploy row with an empty `CommitInfo`. The log narration (`logs/progress.go`) falls back to the branch when the row has no commit, which produced `Building from …@main`.

**Change** (`lego/backend/internal/github/public_git.go`): on a non-GitHub HTTPS repo, an explicit full SHA (40 or 64 hex) now resolves to its advertised peeled tag target when there is one, else to the lowercased SHA itself, even when the advertisement lacks it or the lookup misses. That SHA is already the build pin: the clone fetches exactly it and fails the deploy unless `git rev-parse HEAD` equals `EXPECTED_COMMIT`. So a `live` deploy proves the recorded commit, and an unknown SHA still fails at fetch, as the hosted run showed. Echoing the caller's own SHA reveals nothing about the repository, so the no-existence-oracle rule holds. The cache lookup moved into `lookupPublicGitCommit`, so a cached miss gets the same fallback. Unchanged: abbreviated SHAs (`180e352`) and unknown branches stay misses, and github.com keeps its API path, where an unknown SHA still records no commit. Message and author time stay empty on generic hosts. ADR004 § Deploy commit provenance is amended.

**Tests:** `TestPublicGitExplicitFullSHAIsRecordedAsRequested` covers the hosted case through `DeployCommitSource().ResolveCommit` on `gitlab.com/pages/plain-html`, in two cases: SHA not advertised, and lookup 404. Each is checked across two calls, so the cached miss is covered. Short SHA, unknown branch, github.com with the App disabled, and non-HTTPS stay misses. `TestPublicGitCommitAdvertisedRefs` now expects an unadvertised full SHA (SHA-1, and uppercase SHA-256) to resolve to itself and `180e352` to miss.

3. Run `--commit deadbeefdeadbeefdeadbeefdeadbeefdeadbeef`. Expect `update_failed` with the `could not fetch` reason. The row may now carry `commit.id = deadbeef…`; that is the requested commit, and the deploy fails.
4. Web fixture (python, start command echoing `RENDER_GIT_COMMIT`): after an explicit-SHA deploy, the runtime `RENDER_GIT_COMMIT` must equal the deploy's `commit.id`.
5. Private or missing repo: create from a non-existent `https://gitlab.com/<random>/<random>`. A branch deploy records no commit, as before.
6. GitHub control: `render-examples/vue-hello-world --commit cc017255…` still carries its message and `createdAt`.
7. Delete every fixture by ID (204) and keep the `GET` 404 proofs.

The original `startedAt` question and Render's short-SHA behavior remain unverified and are not claimed here.
