# Removing `PORT` from an image web service never takes effect: the next deploy or rollback reuses the cached network built for the old `PORT` (a rollback to the port-80 release waits on 9999 and fails; a fresh deploy stays on 9090) — w4/m243 t007 live check fails

Why: Render's rollback restores a previous deploy's artifact and brings it up. The usual recovery from a bad configuration deploy is: undo the change, roll back to the last good deploy, see it go live. w4/m243 t007 (deployed in `f4f12981e`) made image-port services keep serving through a failing port change, and that part works. But the rollback afterwards probes the failed candidate's port, so it never becomes healthy and ends `update_failed`. The service stays on the old pod, but every later deploy or rollback repeats the failure. t007's own live acceptance ("a rollback after a failure goes `live`") therefore fails on production.

Severity: **major** (the standard recovery path for a bad deploy is broken for image-port web services; the user is told the health check on a port they removed is failing). Attribution: platform runtime (operator image-port selection on rollback). Estimate: ~1h. Source: `/qa-find-bugs-cli` loop sweep 25, 2026-10-27 10:13–10:49 UTC, running w4/m243/t006's t007 live replay on pin `f4f12981e455`. Context: HEAD-built bex with pinned Render CLI v2.27.0 `a764810a7682`; `https://api.bex.co/v1/`; workspace `bex-canary`; human device login.

## Root cause (verified in code, reproduced live)

`resolveImageNetwork` (`lego/operator/internal/controller/image_network.go` ~`:106–111` at `f4f12981e`) reuses the cached `status.imageNetwork` when

```go
(cached.Image == image || cached.Source == image && cached.Revision == releaseRevision(app)) &&
(!configured || cached.PrimaryPort == configuredPrimary)
```

With `PORT` removed, `configured` is false, so **any** cached network is accepted, including one whose `PrimaryPort` was chosen from the now-deleted `PORT` (9999, or 9090 below). A rollback and a fresh deploy run the same digest-pinned image (`cached.Image == image`), so they hit the cache and keep the stale port. The platform then injects that port into the container as `PORT`, which makes the stale value self-sustaining for apps that honor `PORT`.

**Second reproduction (sweep 26, 11:13–11:17 UTC, same pin), fresh deploy without a rollback:**

```text
ealen/echo-server:0.9.2 with PORT=8080 → live, serviceDetails.port 8080
PUT PORT=9090 → bex deploys create --wait → succeeded, port 9090   (t007's 8080 → 9090: passes)
DELETE env-vars/PORT → 204; GET env-vars → []
bex deploys create --wait → dep-dbg8fa6q7drs739qkpi0 live, serviceDetails.port 9090, openPorts [9090]
GET /?echo_env_body=PORT → "9090"        # the container is still given PORT=9090 with no PORT configured
```

Expected after removing `PORT`: the image-port default (the image's declared port, `80` for echo-server) or Render's `PORT` default, never the removed value.

## Fix (target behavior)

- A rollback to a release that served on port N probes, routes and serves on N, using that release's recorded serving network or the current configuration (no `PORT` here). Never use a failed candidate's port.
- When `PORT` is removed, the next resolution clears `status.envPort`, so a fresh deploy also returns to the image's declared port.
- Fix the cache test: only reuse a cached network for an unconfigured resolution if that network was itself resolved unconfigured. Record `configuredPrimary` (or a `configured` flag) on `ImageNetworkStatus`, and treat a mismatch either way as a miss.
- Envtest:
  - serve on 80 → fail on 9999 → delete `PORT` → rollback → the Deployment's probe and the Service target 80, and the rollback goes live;
  - the same sequence with a fresh deploy instead of a rollback;
  - controls: an explicit `PORT` change that succeeds still moves to the new port (t007's 8080 → 9090 case).

## Blast radius

- Image-port web services (`web-image-v1`/`web-image-configured-v1`) after any failed port change: rollback, manual redeploy and env-group "Save and deploy".
- Git-built Docker web services in image-port mode likely share the path.
- Configured-port services (native, m182 named-port) are probably unaffected; verify.

## Regression checks
