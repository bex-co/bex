## Objective

Decide, against Render, what a Restart does to a deploy that is building when it arrives, and make sure the result is never a silently dropped saved change.

## Context

- Finding repro 4: Restart at 00:22:39 closed H (`dep-dbam4oe804hs73aaedmg`, building) `canceled` with an empty `failureReason`. The service then ran an older configuration while the saved spec was H's, and no deploy was pending.
- The restart release (generation 10) passes H's generation (9), so `reconciler.go:1529` cancels H; the operator abandons H's build.
- w4/m201 DoD: Restart "leaving saved V2 pending" — the saved configuration remains for the next deploy.
- Finding repro 5 shows the cancel without any overlap: one in-flight config deploy (X) is canceled as "Superseded by" the Restart; the service keeps the old release; `undeployedChanges` is `true` on GraphQL; the CLI shows nothing. Restart is "a special form of manual deploy" on Render, and ADR018 claims Render's Wait policy for overlapping triggers, under which the in-flight deploy would finish first.
- A Restart refused before any live deploy (`409 … has no live deploy to restart`) is correct and must stay.

## Steps

1. Establish Render's behavior for Restart while a deploy is in progress (docs, API reference, or an approved Render account observation). Record it in ADR018's Restart row.
2. Either make Restart wait behind the in-flight deploy (Wait policy; it then restarts whatever is running when it executes), or keep Override and say so: close the canceled row with a `failureReason` naming the restart ("Canceled by a restart; your saved changes were not deployed", not "Superseded"), and surface `undeployedChanges` wherever the deploy list is read.
3. Add tests for the chosen behavior.
