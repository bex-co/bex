## Objective

Decide how the run-to-completion pin and served-revision tracking change, so an executing release that rolls out is recorded as served, and write the chosen mechanism into t002/t003.

## Context

- Finding: [finding.md](finding.md) (three live repros plus Restart repro, CR timelines).
- `lego/operator/internal/controller/release_identity.go:370` `buildRunning` pins only while `status.phase == Building`. `prepareAppReleaseDecision` (`:400`, coalescing branch `:437`, adoption `:457`) adopts the pending generation on the first reconcile after the build resolves, while the pinned release's Deployment is still rolling out.
- `app_controller.go:2506` applies the pinned release's Deployment; `markRunning` (`:3043`, reached via `reportKubernetesRunning` `:2963`/`:2987`) is the only writer of `status.activeRevision` and runs only for the current release.
- `lego/backend/internal/store/reconciler.go:1529`, `supersededDeployStatus`: `releaseGeneration > open.Generation` closes the row canceled. The comment at `:1520-1528` assumes the executing row was already observed live.
- Render: Wait policy (default for new workspaces) lets the in-progress deploy finish, then proceeds to the most recent one (<https://render.com/docs/deploys>).
- Precedent from w8/m117 (`84f83ab08`, blocked awaiting deploy): `survivorInFlight` (`release_identity.go:520`) already keeps a cancel's surviving release pinned through build **and rollout** until `successfulReleaseGeneration` reaches it. Option A below is the same "until it serves" condition applied to the ordinary latest-pending slot. Reuse it rather than adding a parallel mechanism, and keep m117's six envtests green.

## Steps

1. Compare option A (keep the pending slot pinned until the pinned release is Running at its revision or its rollout settles failed; only then adopt) with option B (adopt immediately and build in parallel, but stamp `activeRevision`/a served-generation fact when the pinned Deployment revision completes; the backend closes the row live from it). Weigh latency (A delays the next build by one rollout), Render's Wait semantics, failure handling (pinned rollout fails or exceeds its progress deadline), hibernation/zero-replica Free services, and canceled-release interplay (m117, w5/m114).
2. Check the effect on `successfulReleaseGeneration`/`releaseHasServed` (`release_identity.go:544`, `:475`), which decide what a cancel or failed rollout restores.
3. Record the decision, and the exact status sequence the backend will observe, in t002 and t003.

## Outcome (2026-10-19)

**Chosen: option A (Render's Wait policy).** The release in flight stays pinned through its rollout, and the newer release is adopted only once it serves or settles. Option B would have adopted the newer release immediately. That needs a new "rolling" status, so the backend could hold off canceling a row whose pods are still coming up, and a stamp for the Deployment revision completing. Both are new state where A needs none. A adds one rollout of latency before the next build, which is what Render's documented default does.

Facts that decided it:

- Pinned and newer releases render the same template in both options. The Deployment is always projected from the current spec. Native and buildpack builds bake the start command into the image, so an in-flight release keeps its own command either way. A Docker build's command already came from the spec during the pinned rollout before this fix.
- Every path that ends a rollout leaves phase `Deploying`, so the pin cannot strand the pending slot:
  - `markRunning` writes `Running` with `activeRevision`;
  - `settleFailedRollout` writes `Failed`, or `Running` over the prior release, with a durable `ConditionRollout` at the release generation;
  - a parked app writes `Hibernated`;
  - static publish and cron reconciliation stamp `activeRevision`.
- `successfulReleaseGeneration` / `releaseHasServed` read `activeRevision`, which now names the release that actually served, so cancel and failed-rollout restores pick the right one.

The CR sequence for "A executing, B pending", now:

1. A is Building, and B coalesces into the pending slot.
2. A's build resolves. A runs its pre-deploy step and rolls out in `Deploying`, with B still pending.
3. A's pods are ready. `markRunning` writes `Running` and `activeRevision=rev-A`; the backend sees Ready at A's generation, so **A is live and the prior row deactivated**.
4. The next reconcile adopts B: `releaseGeneration=B`, `Building`, with `activeRevision` still `rev-A` for B's whole build. A backend pass that missed step 3 closes A live from that record.
5. B serves (`rev-B`): **B is live and A is deactivated**.

**m117 coordination.** The cancel paths (`survivorInFlight`, `latestRequestCanceled`) run before the pin and are unchanged, and m117's six envtests pass. The pin also releases when the in-flight release's own deploy is canceled (the cancel stamp names its generation), so Cancel of the executing deploy still ends it.
