# `GET /v1/env-groups/{id}` returns env vars without values (and secret files without contents), and the service secret-file list omits `content`, although Render's pinned schema requires both

Why: Render's pinned `envGroup` schema (`render-public-api-1.json`) requires `envVars: envVar[]`, where `envVar` requires `key` and `value`, and `secretFiles: secretFile[]`, where `secretFile` requires `name` and `content`. `GET /services/{id}/secret-files` returns `secretFileWithCursor[]` with the same required `content`. Bex's env-group responses send `{key}` only, and its secret-file list sends `{name}` only. A Render client that reads a group to sync, diff or export it receives schema-invalid objects and silently sees every value as missing. That covers scripts, agents and IaC tooling written against Render's API. Bex is also inconsistent with itself: `GET /services/{id}/env-vars` does return values. ADR018's env/secret-files rows record "list is names-only" and the conformance allowlist calls it "intentionally redacted", with no user sign-off; the env-group read is not conformance-checked at all.

**Severity:** minor (API contract; the values are reachable per key). **Attribution:** server (REST env-group and secret-file read projections). **Estimate:** 1h30m. **Source:** `/qa-find-bugs-cli` sweep 1314, 2026-10-22 ([evidence](evidence/cli-sweep1300/README.md#sweep-1314--env-group-and-secret-file-reads)).

## Reproduction

Production `https://api.bex.co/v1/`, pin `efdd8e2ff06b`, `bex-canary`, human device-login grant. All fixtures were deleted afterwards (204 → 404).

| Request | bex response | Render schema |
| --- | --- | --- |
| `POST /v1/env-groups {…,"envVars":[{"key":"QA_EVG","value":"qa1314-group-value"}]}` | 201, `envVars: [{"key":"QA_EVG"}]` | `envVar` requires `value` |
| `GET /v1/env-groups/<evg>` | 200, `envVars: [{"key":"QA_EVG"}]` | same |
| `GET /v1/env-groups/<evg>/env-vars/QA_EVG` | 200, `{"key":"QA_EVG","value":"qa1314-group-value"}` | — |
| `GET /v1/services/<srv>/secret-files`, after `bex services create … --secret-file qa1314.txt:<path>` | 200, `[{"secretFile":{"name":"qa1314.txt"},"cursor":"qa1314.txt"}]` | `secretFile` requires `content` |
| `GET /v1/services/<srv>/secret-files/qa1314.txt` | 200, with `content` | — |
| `GET /v1/services/<srv>/env-vars` | 200, every `envVar` with `value` | matches |

## Expected

The env-group create, read and update responses carry each variable's `value` and each secret file's `content`. The service secret-file list carries `content` for each file, as Render's schema requires and as bex's own service env-var list already does. Authorization stays as it is today for value reads. If a caller lacks the sensitive-read capability that the per-key read requires, the whole read is refused with that read's 403, never a silently masked body. Generated values that have not been materialized follow Render's shape for `generateValue` groups (check the capture).

## Root cause

- `lego/backend/internal/envgroups/service.go:98–140`: `EnvVarView` ("value is empty in list/get responses (fetched per key)") and `SecretFileView` (`content,omitempty`, "names-first discipline") are the metadata views used for group create, read and update. The value is filled only on the single-variable and single-file reads.
- The service secret-file list uses a names-only type. `lego/backend/internal/api/conformance_allowlist_test.go:105–113` allowlists `secretFile/content: property "content" is missing` as intentionally redacted.
- `lego/backend/internal/api/conformance_test.go` validates `get-env-vars-for-service` and `list-secret-files-for-service` but has no `retrieve-env-group` check, so the group omission is untested.

## Fix

1. Have the REST env-group create, read and update and the service secret-file list fill `value` and `content` from the same store the per-key reads use, behind the same sensitive-read authorization, and refuse the whole read with that read's 403 when the caller lacks it.
2. Remove the `list-secret-files-for-service` allowlist entry and add `retrieve-env-group` (and the create and update responses) to `TestRenderConformance`.
3. GraphQL, MCP and the dashboard may keep their reveal-on-demand UX. That is presentation, not the Render REST contract. Update the ADR018 rows.

## Blast radius

REST `/v1/env-groups` (create, retrieve, update and the list if it embeds variables) and `/v1/services/{id}/secret-files`. Audit logging of sensitive reads applies to these responses as it does to the per-key reads. Response size grows by the values.

## Acceptance

- Conformance: `retrieve-env-group` and `list-secret-files-for-service` validate against the pinned schema with no allowlist entry. A caller without sensitive-read access gets 403, not a masked 200.
- Live after deploy: repeat the table. Every row returns `value` or `content`. Delete fixtures by ID with 404 proofs.

## Dedupe

`git grep -i 'names-only|names-first|intentionally redacted' .pm`: no open item. w9/m5 and w4/326 shaped today's names-first reads.
