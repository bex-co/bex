## Objective

A scheduled run whose session waits for the pool is visibly queued, not dropped. A run whose session could not start for a platform cause is told apart from a broken template.

## Context

- `decideAutomationRun` (`lego/backend/internal/agentsessions/automation_scheduler.go`) settles a run `started` as soon as the session create is accepted. The sandbox wait happens after that, in the session.
- The overlap rule (D6) skips a tick while the previous run's session is `StateWorking`. A waiting session stays working, so the next tick is `skipped_overlap`, as Devin's queued runs are.
- Run activity is shown by `AgentAutomationRuns` (REST, GraphQL, MCP) and by the dashboard automation page.

## Steps

1. Carry the session's waiting state, and its start-failure cause, into the run's activity view on REST, GraphQL and MCP.
2. Dashboard automation page: a waiting run reads "waiting for a sandbox machine". A run whose session failed at start for a platform cause says so, apart from `failed_create`.
3. Confirm, with a test, that a platform start failure does not count toward the `repeated_failures` auto-pause (ADR101 D7).
