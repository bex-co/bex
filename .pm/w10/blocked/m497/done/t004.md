## Objective

A client reading a session sees that it is waiting for a sandbox machine, since when and why. A failed start reads with its named cause, and every surface uses the same fields and words.

## Context

- The session view, its failure reason and its code come from `lego/backend/internal/agentsessions/models.go`, `rest.go`, `graphql.go` and `mcp.go`. The dashboard keys the upgrade callout on `failureReasonCode === SANDBOX_CAPACITY_LIMIT` (`dashboard/src/features/agent-sessions/lib/mapper.ts`). The CLI reads `failureCode` (`lego/cli/internal/agent/render.go`).

## Steps

1. Add the fields t001 defined, for example `waitingFor: "sandbox_capacity"` with `waitingSince`, plus the start-failure cause, to the session view. Expose them on REST, GraphQL and MCP from one source, with shared descriptions.
2. Keep the waiting session in its starting state (`StateWorking`), so clients keep polling and automations count it as working.
3. Write the failure reason per cause in plain words. Name what happened and what the user can do: wait, try again, or contact support for a runtime cause.
4. Regenerate the GraphQL schema and the dashboard's generated types.

## Files

- `lego/backend/internal/agentsessions/` (models, rest, graphql, mcp), the GraphQL schema, the dashboard's generated GraphQL types under `dashboard/src/graphql/`

## Acceptance criteria

- [ ] REST, GraphQL and MCP return the same waiting and cause fields for one session, checked by a test across all three.
- [ ] `SANDBOX_CAPACITY_LIMIT` responses are unchanged.
