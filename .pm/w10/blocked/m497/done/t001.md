## Objective

Settle how bex-api learns why a sandbox pod did not run, which causes it waits on and for how long, and what each surface shows. Record the result in the ADRs before any code.

## Context

- Today a pod-ready timeout (`errPodReadyTimeout`, `lego/backend/internal/sandbox/client.go`) becomes `SANDBOX_CAPACITY_LIMIT` when the plan's limits are exhausted. Otherwise it becomes `SANDBOX_START_FAILED` with "sandbox did not start (platform issue)" (`podReadyTimeoutError`, `service.go`; ADR047 § "Capacity only when it is capacity (w9/074)").
- The OpenSandbox server waits up to `sandbox_create_timeout_seconds = 300` (`deploy/opensandbox/sandbox-cluster.toml`) and deletes the sandbox when the wait ends. Its 504 says only `Last state: Pending`.
- A dispatch has a 15-minute ceiling (`dispatchTimeout`, `agentsessions/service.go`). Recovery abandons a dispatch whose `agent_session_dispatches.next_check_at` has passed (`dispatch_recovery.go`, `store/agentdispatch.go`).
- bex-api cannot read pods in `<ws>-sandbox` namespaces. The per-tenant RoleBindings there are for the operator, the OpenSandbox server and controller, and the ssh-gateway (`deploy/gitops/base/tenant-namespace-clusterroles.yaml`; the NamespaceReconciler binds them).
- Devin's behavior is in the milestone README (waiting for capacity, never failed for it).
- w1/m405 owns the transient-fault retry. Agree the boundary with its design, which covers the same `bootSandbox` call site.

## Steps

1. Choose the cause source. Option one is a read-only `pods` get/list grant for bex-api in `<ws>-sandbox` namespaces. It is bound per tenant like `bex-tenant-ssh-gateway`, and the admission and `scripts/gitops-validate.sh` guards are extended. Option two is to read the pod while the create waits. Option three is to read the pod's state through OpenSandbox's own GET. Pick the least privilege that can see the `PodScheduled` condition and the container waiting reasons. Write down why, with the ADR028 security lineage in mind.
2. Define the cause vocabulary (e.g. `pool_full`, `image_pull`, `runtime`, `quota`, `unknown`) and the words for each cause. Keep `SANDBOX_START_FAILED` as the failure code. Choose whether the cause is a new field or part of the reason.
3. Define the wait.
   - Wait only for `pool_full`.
   - Set the bound. Measure it against the routines' turn lengths, and keep it under the turn ceiling.
   - Set the backoff between creates, and how the dispatch keeps itself alive across the 15-minute ceiling and recovery (a heartbeat on `next_check_at`, a waiting state on the session row).
   - Define what Cancel, Delete and Archive do during a wait.
4. Define the surfaces: the waiting field on the session view (REST, GraphQL, MCP), what the dashboard and `bex agent` show, and the automation run activity.
5. Amend:
   - ADR047 § "Capacity only when it is capacity".
   - ADR042 § Sandbox groups ("A create the pool cannot place still waits for the pod and then answers `503 SANDBOX_START_FAILED`").
   - ADR018: add a row with the Devin basis.
