## Objective

When a sandbox create's pod-ready wait ends, bex-api knows why the pod was not running, from the pod itself, using the source t001 chose.

## Context

- The production evidence is in the milestone README. The pods were `PodScheduled=False`, `Unschedulable`, with memory requests at 99.9% of the node's allocatable.
- Sandbox pods carry the session binding labels and the dispatch turn (`agentsession.BindingLabels`, `CreateAgentSessionSandbox`), and a base sandbox carries `bex.co/sandbox-id`. Either can find the pod.
- `podReadyTimeoutError` and `capacityExhausted` live in `lego/backend/internal/sandbox/service.go`.

## Steps

1. Add the RBAC t001 chose: a ClusterRole in `deploy/gitops/base/tenant-namespace-clusterroles.yaml`, its per-tenant binding in the NamespaceReconciler, and guards in `scripts/gitops-validate.sh` and the namespace admission policy. Or add the alternative t001 chose instead.
2. Add a reader that maps a pod to a cause:
   - `PodScheduled=False` with `Insufficient cpu` or `Insufficient memory` → `pool_full`.
   - Waiting `ErrImagePull` or `ImagePullBackOff` → `image_pull`.
   - A `FailedCreatePodSandBox` or missing runtime handler → `runtime`.
   - A quota refusal → `quota`.
   - Anything else → `unknown`.
3. Call it before the server deletes the pod. That means while the create waits, or at the timeout if the pod is still readable. Carry the cause on the start-failure error: `SANDBOX_START_FAILED` with a cause detail, and the plan-limit `SANDBOX_CAPACITY_LIMIT` unchanged.
4. The reader degrades to `unknown`, never to an error, when the read is refused or times out.
