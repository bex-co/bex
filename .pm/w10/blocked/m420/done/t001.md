## Objective

A cron job has no long-running instance and no health check, so it has no availability. Make the control-plane projection record no availability conclusion for a `cron_job` App, so `server_failed`, `server_hardware_failure` and `server_available` can never be produced for one, whatever its `Ready` condition says.

## Context

- `observedServiceStateFor` (`lego/backend/internal/store/reconciler.go:2458`) derives `Availability` from the `Ready` condition for every App type. A cron in `Deploying` (Ready=False `Deploying`) or after a step failure (`CronRunFailed`, `CronRunCancelFailed`) with `ActiveRevision` set and no open deploy reads `unhealthy` with `readiness_failed`.
- `guardServiceObservation` → `debounceUnhealthy` only needs two consecutive unhealthy passes; a trigger/cancel kicks several.
- Edges become facts in `lego/backend/internal/store/event_facts.go` (~`:1097`, `failureFactType`); `classifyAlertEmail` (`lego/backend/internal/notifications/alert_email_worker.go:243`) mails `server_failed`; push (`push_worker.go:822`) and webhooks (`webhooks/service.go:253`) fan it out too.
- `appv1alpha1.TypeCronJob = "cron_job"` (`lego/types/v1alpha1/app_types.go:457`). Phase transitions (suspend/resume facts) must keep working for cron jobs — only availability is removed.
- Check `instanceExitFacts` too: a cron has no Deployment, so `status.instanceExits` should stay empty; assert it rather than assume it.

## Steps

1. In `observedServiceStateFor`, for `app.Spec.Type == appv1alpha1.TypeCronJob`, return the observation with phase/suspension filled and availability cleared (`clearAvailability`) — not `suppressAvailability`, so no debounce/confirm pass is armed.
2. Make sure a cron's checkpoint that already holds `unhealthy` from before the fix cannot later emit a stray `server_available` (a cleared observation must keep the previous availability without an edge — confirm with `RecordObservedServiceState`'s handling of `AvailabilityObserved=false`).
3. Confirm `instanceExitFacts` yields nothing for a cron App; skip it explicitly for `TypeCronJob` if it could.
4. Tests in `lego/backend/internal/store`: a cron App Ready=False `Deploying` across three passes records no `server_failed`; same for `CronRunFailed`; a web service in the same state still records one (the guard is type-scoped).
