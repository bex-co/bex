## Objective

`spec.runAt` (trigger) and `spec.cancelRun` (cancel) are run requests, not releases. A generation change made only of them must leave a settled cron's `status.phase` and `Ready` condition as they were, so the dashboard does not show `Deploying` on every Trigger Run and no consumer reads it as a rollout.

## Context

- `reconcileCronJob` (`lego/operator/internal/controller/app_controller.go:5212`) calls `setPhase(ctx, app, PhaseDeploying, "Deploying", …)` whenever `Status.ObservedGeneration != Generation`; every trigger/cancel bumps the generation. `setPhase` writes Ready=False (`:7033`).
- w5/074 already keeps the 1-minute history poll from flapping through `Deploying`; this extends the same steady-state gate to run requests.
- The manual-run path is `ensureManualRun` / `cancelRequestedCronRun` / `preemptOtherCronRuns` (`:5375`–`:5395`) and `cron_manual_intent.go`; w4/m300 t010's start hold (`manualRunStartHold`) requeues there and must keep working.
- A step failure in that path (`stepFailure{reason: "CronRunFailed"|"CronRunCancelFailed"}` → `failStep` → `fail`) writes Ready=False as well; decide whether a run-request failure should mark the cron's release failed. Render keeps the cron job live and reports the run, so prefer keeping phase/Ready and surfacing the error on the run or as a retry.

## Steps

1. Determine "only run-request fields changed": compare the release-relevant spec against what the status records (e.g. `Status.Image`, the recorded release pod template / `releaseRevision`), or record the last release generation separately; pick the smallest reliable signal.
2. Skip `setPhase(PhaseDeploying)` when the cron is settled and only run-request fields changed; still advance `ObservedGeneration` at the end of the pass.
3. Keep a real change (image, command, schedule, env, plan) going through `Deploying`.
4. Tests (envtest or unit): trigger and cancel on a settled cron never write phase `Deploying` or Ready=False; a schedule change still does; t010's hold test still passes.
