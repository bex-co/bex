### Settle-before-delete probe 2026-11-12

Stripe **test mode**, every object prefixed `bex-probe-settle-1794538714`. A Customer with a Subscription on a metered Price, 3,000,000 units of usage sent as meter events, then bex's settle calls in order:

1. **Preview.** `POST /v1/invoices/create_preview` for the Subscription: `amount_due` 300¢, as expected.
2. **Anchor reset.** `POST /v1/subscriptions/{id}` with `billing_cycle_anchor=now`, `proration_behavior=always_invoice`, `payment_behavior=default_incomplete` created one **open** invoice for the shortened period (`billing_reason=subscription_update`, `attempt_count` 0). Stripe made no automatic charge.
3. **One charge.** A single off-session `POST /v1/invoices/{id}/pay` succeeded; the invoice went `paid`.
4. **Decline.** With a declining card, the pay was declined and left the invoice **open** with its `hosted_invoice_url`. A retry re-found it in the Subscription's `status=open` invoices, so the retry pays that invoice instead of resetting the anchor again.
5. **Prepaid.** A card from `tok_mastercard_prepaid` reports `card.funding=prepaid`, and `card.fingerprint` is present, so the t015 refusal and fingerprint dedupe have what they read.
6. **Summary lag.** The meter event summaries took **55 s and 62 s** (two runs) to reflect the 3,000,000 units. That is longer than the old 60 s `DefaultSettleWait`, and longer than any request can wait inside bex-api's 30 s HTTP write timeout.
7. **past_due window.** After the reset the Subscription is `past_due` straight away (documented Stripe behavior for `default_incomplete`) until bex pays the open invoice.

**Fixed as a result (2026-11-12):**

- An API request's settle now waits at most 20 s (`DefaultSettleWait`, never past the request's deadline) and answers the retryable `BILLING_SETTLING`. The dashboard's workspace and account deletion flows show "Finalizing final usage…" and retry every 15 s for up to 3 minutes, then show the retry message. The account-deletion worker's teardown is bound by no request and waits up to 150 s.
- Before the reset, the settle stamps `billing_lifecycles.settling_until` (10 minutes ahead), and a `subscription_past_due` observed before it opens no grace period. A declined settle charge's `invoice.payment_failed`, like any real failed invoice, still does (`settle.go` file comment).

## Before widening: backfill BYO key flags (found in t012, 2026-11-05)

- Route decisions read `agent_environments.model_key_set_at`, which only the t012 write path sets.
- A key an operator put into OpenBao by hand earlier (`agent-sessions/<ws>/model-key`) has no flag. Once the route widens, that workspace would silently switch from its own key to the billed platform model.
- **Automated.** bex-api runs a one-shot reconcile at startup, in the background (`agentsessions.BackfillModelKeyFlags`). It lists `agent-sessions/` in OpenBao and sets `model_key_set_at` for every workspace whose `model-key` secret holds a key and has no flag. It never clears a flag.
- **Verify after the deploy, before removing the allowlist.** Check the bex-api startup log line `agent model key flag backfill: workspaces=… keys=… flags_set=… failed=…`. Expect `failed=0`. Expect `keys` to match the hand-provisioned keys you know of. A restart retries any failure.

## Rollout gate decisions 2026-11-12 (user decisions)

- **(2) OpenRouter key limit: dropped.** The user decided the platform key gets no credit limit: the OpenRouter account balance is the cap ("所有的额度都是它的"). The key's own `limit` is `null`, so the old `PlatformModelCreditHigh` (80% of the key limit) could never fire. It is replaced by a balance alert: bex-api reads `GET https://openrouter.ai/api/v1/credits` every 10 minutes and exports `bex_agent_platform_model_credit_balance_usd` (`total_credits − total_usage`); `PlatformModelCreditLow` warns below $25 for 10m and `PlatformModelCreditCritical` pages below $5 (ADR091 D5).
- **(3) Stripe Radar custom rules: dropped as a gate, now an optional follow-up.** Why: the prepaid-card refusal and the card fingerprint dedupe are enforced in bex code since t015, and Stripe's default Radar risk blocking already applies to every charge. Custom rules would only add a second layer. They stay documented in the [runbook](../../../../docs/runbooks/stripe-billing-setup.md#radar-rules-for-card-binding-adr091-d105) for whenever abuse data calls for them.
- **(4) Terms: published.** The user delegated the wording to the agent. **Agent model usage terms** are live at the public route `/legal/agent-models` (en + zh, no sign-in, effective 2026-11-12) and linked as "Terms" from Settings → Agents and Billing → Agent model (ADR091 D8, D10.7).
- **(5) Test-mode e2e check: satisfied** by the t014 threshold probe and the settle-before-delete probe above (approach delegated by the user: "你自己决定").
- **Remaining before widening:**
  - **User action: top up the OpenRouter account.** Its balance was ≈ $8 on 2026-11-12 (`total_credits` 260, `total_usage` ≈ 251.87), already under the $25 warning line, and widening to every workspace would drain it fast.
