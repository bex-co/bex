## Objective

The SSR render and the client hydrate with the same language for every formatted time, so a zh cold load shows Chinese dates on first paint with no React #418 hydration error, and w6/m107's SSR clock fix still holds.

## Context

- w6/m107 (done; the SSR clock fix) and w21/054 (blocked: a missing `i18nextLng` cookie with localStorage `zh` causes #418 and an English flash) share the language-source risk.
- The language source the SSR i18n already uses (cookie / `?lang=`) is the one the formatters must read.

## Steps

1. Read the formatter language from the same source SSR i18n uses; never from `navigator`.
2. Cold-load a deploy page with `?lang=zh` and with the zh cookie in a production build and check the console.

## Files

- the dashboard's i18n/SSR wiring (`dashboard/src/` root route and i18n setup)

## Acceptance criteria

- [ ] A production-build cold load in zh logs no hydration error and paints Chinese dates; en unchanged. Record in § Findings whether w21/054's separate case is affected, without claiming it fixed.

## Progress (2026-11-14)

Step 1 is done in code: every formatter reads `i18n.language` from `useTranslations()`, the same i18next instance the SSR pass renders with and `use-language-hydration-sync` keeps aligned on the client; nothing reads `navigator`. Every absolute time also still renders only after hydration (`LocalTime`, `useLocalDateTime`/`useLocalDate`, the deploy header's `hydrated` guard, the range trigger's `useIsHydrated`, tooltips on hover, log rows on the client), so SSR markup carries no formatted time to mismatch. w21/054 (a missing `i18nextLng` cookie with localStorage `zh`) is not affected: it is about which language i18next starts with, which this change does not touch, so it is not claimed fixed.

**Blocked on the release gate:** step 2, the production-build cold load in zh and en with the console checked, runs against production after the batched deploy carries this milestone (DoD 1-3); no user action.
