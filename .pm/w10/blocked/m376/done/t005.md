## Objective

A dashboard test (or lint rule) fails when code outside the formatter module formats a date with a hard-coded `"en-US"`, a locale-less date-fns pattern or `toLocale*String(undefined)`, so the English-in-zh gap cannot return through a new call site.

## Context

- `dashboard/src/common/lib/format/` is the one sanctioned place; `yarn lint` runs eslint, typecheck and knip (dashboard AGENTS.md).

## Steps

1. Add an eslint `no-restricted-syntax` rule or a source-scan test with an allowlist of the formatter module.
2. Fix any call site it finds.

## Files

- `dashboard/eslint.config.*` or a test under `dashboard/src/common/lib/format/`

## Acceptance criteria

- [x] The rule fails on a deliberate `Intl.DateTimeFormat("en-US")` outside the module and passes on the tree.

## Result (2026-11-14)

`dashboard/eslint.config.js` adds a block for `src/**` outside `src/common/lib/format` and tests: `no-restricted-imports` of `date-fns` (only the format module may use it), and `no-restricted-syntax` for `toLocaleDateString()`/`toLocaleTimeString()` with no locale, any `toLocale*String(undefined …)` or `("default" …)`, `new Date(…).toLocaleString()` and `date.toLocaleString()` with no locale, and `new Intl.DateTimeFormat` with a literal locale. A number's `toLocaleString()` is not matched (checked with a probe file). It found the call sites t001 fixed, plus four zone-math uses of `Intl.DateTimeFormat("en"/"en-US")` that format nothing for display (`agent-automations/lib/schedule.ts`, `notifications/lib/push-policy.ts`), annotated with an `eslint-disable-next-line` and the reason.
