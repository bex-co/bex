# 027 — `gh` works for the agent but not in the session's web shell or SSH terminal

Why: a person who opens a session's terminal (the web Shell, `ssh`, Zed) and runs `gh run list` gets "gh auth login", because only the agent's process environment carries the `GH_*` settings the driver sets (w10/m513), while Devin's `gh` token is on the machine for every shell. Found by the w10/m513 Devin comparison (t007). Severity: minor (Devin parity). Surface: `lego/agent-image/driver/src/github-cli.ts`, the sandbox's login shell.

## Current state (2026-11-19)

The driver writes gh's config to `<status dir>/gh/config.yml` and passes `GH_CONFIG_DIR`, `GH_TOKEN` (a placeholder), `GH_REPO` and `GH_PROMPT_DISABLED` to the agent through `agentEnvironment`. A terminal started through the gateway exec path does not inherit them.

## End state

In a repo session, `gh run list` and `gh api repos/{owner}/{repo}` work from the web Shell and an SSH session without arguments (for example through a profile script or `/etc/gh` defaults the driver writes), and a repo-less session's terminal still has no `gh` configuration.

## Work record (2026-11-20)

- **Reference.** Devin's machine "can carry a GitHub CLI (`gh`) token" ([Security profiles](https://docs.devin.ai/product-guides/security-profiles), read 2026-11-20): it is on the machine, so every shell there has it.
- **Cause.** Besides the agent-only `GH_*` variables, the web Shell and an SSH session run `/bin/sh` through pods/exec (`webshell/websocket.go`, `nativessh/session.go`), which is dash in the image, and an interactive dash read no startup file at all: `bex-agent-tools.sh` reached only bash and login shells.
- **Fix** (`a23aff7d7`). The driver writes the agent's `GH_*` settings as quoted exports to `gh/env.sh` beside its status file (mode 0600) once the socket serves, after removing a kept disk's earlier one (`lego/agent-image/driver/src/github-cli.ts`). `bex-agent-tools.sh` sources it, and the image sets `ENV` to that script, so the web Shell's and SSH's interactive `/bin/sh` reads it; `ssh … '<cmd>'` and Zed's `/bin/sh -lc` read it through `/etc/profile`, and bash as before. A repo-less session, or a turn with `gh` off, removes the `gh` directory, so its terminals have no `GH_*`. The Dockerfile's final check fails the build unless the file reaches `sh -ic`, `sh -lc`, `bash -c`, `bash -lc` and `bash -ic` and its absence leaves them without `GH_REPO`. ADR047 D2, ADR090 D4 and `lego/agent-image/README.md` say so.
- **Tests.** `github-cli.test.ts` "a repo session's terminals get the agent's gh settings, and gh in them reaches the gateway route": with a quote in the status path, `sh -ic` (through `ENV`) and `bash -c` (through `BASH_ENV`) have exactly the agent's `GH_*`, a real `gh api repos/{owner}/{repo}` in `sh -ic` reaches the fake route with no token, and after `removeGitHubCliConfig` both have none. Restoring the old profile script fails it, and so does dropping the file write. The driver suite passes (273, 3 skipped).
- **Verified in the built image (arm64).** The image builds with its new check. With the driver's own `startGitHubCliProxy` in front of a fake `github-api` route, an interactive `/bin/sh` on a pty (the web Shell's exec) answered `gh run list` and `gh api repos/{owner}/{repo} --jq .full_name` (`acme/widgets`), as did `/bin/sh -lc` (SSH with a command); after `removeGitHubCliConfig` the same shell had no `GH_*` and `gh run list` asked for `gh auth login`. Production's sandbox Pods run the image in container `sandbox` as the image's user, with no `ENV` or `BEX_AGENT_STATUS_FILE` of their own (read-only `kubectl get pod`, 2026-11-20).

**Status: blocked (2026-11-20).** The gate clears by itself: a production pin that carries `a23aff7d7`. A session's sandbox runs the image of its dispatch, so its sessions must start after the pin. The check, with one short session at a time (the sandbox node is near capacity):

1. As the QA user (`scripts/qa-login.sh`), start a session in `tian-personal` on a repository its GitHub installation reaches. Once it runs, open its web Shell and run `gh run list` and `gh api repos/{owner}/{repo} --jq .full_name` with no arguments: both answer for the session's repository. If the QA account has an SSH key, `ssh <session id>@<the ssh gateway> 'gh api repos/{owner}/{repo} --jq .full_name'` answers the same.
2. Delete it, start a session with no repository, and in its web Shell `env | grep -c '^GH_'` prints `0`.
3. Delete it, log out, record it here and move this note to `done/`.

No user decision is needed.
