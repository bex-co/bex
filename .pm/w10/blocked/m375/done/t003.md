## Objective

For a repo whose `pushDeliveryMethod` is `unavailable`, the Blueprint preview says future file changes need a Manual Sync or a connected repo instead of promising automatic sync, a new Blueprint is created with `autoSync: false`, and an explicit `autoSync: true` on REST, GraphQL or MCP gets the same 400 as the service's `autoDeploy`.

## Result (2026-11-14)

Shipped for the Blueprint itself. `CreateBlueprint` and the deploy-time auto-registration (`upsertBlueprint`) store `autoSync: false` for a repo whose `pushDeliveryMethod` is `unavailable` (the upsert inserts it `paused`; a create's first sync settles `paused` through `CompleteBlueprintSync`). `UpdateBlueprint` refuses turning auto-sync on for such a repo with `400 autoSync needs a connected Git provider: … Sync the Blueprint manually, or connect the repo through the GitHub app`, which REST `PATCH /v1/blueprints/{id}`, GraphQL and MCP all reach. The Blueprint preview (REST and GraphQL `blueprintPreview`) answers `autoSync` for a not-yet-created Blueprint, in the reviewed workspace, and the dashboard's review shows `blueprints.previewManualSyncNote` (en, zh) when it is `false`. Only an install that rejects the shared manual webhook key can have such repos, so no other install asks GitHub. Render creates no Blueprint from a public Git URL, so there is no Render behavior to diverge from (ADR026 § 8). A new Blueprint service's own `autoDeploy` is t002's question. Tests: `TestBlueprintOnAnUnreachableRepoIsCreatedWithoutAutoSync` (preview, create, update; covered and manual-webhook controls) and the `blueprints-new` review-note cases.
