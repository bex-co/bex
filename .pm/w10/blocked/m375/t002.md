## Objective

When `pushDeliveryMethod` is `unavailable`, a create without `autoDeploy` stores it off (`autoDeploy: "no"`, `autoDeployTrigger: "off"`), and a create or update with `autoDeploy: "yes"` (REST `POST`/`PATCH /v1/services`, GraphQL `setAutoDeploy`, MCP `update_service`) is refused with 400 naming the reason and the way out, like the prebuilt-image refusal (w4/418). `unknown`, `manual_webhook` and `github_app` keep today's default; existing services keep their stored value.

## Context

- Evidence and fix shape: [w4/622](../../w4/done/622.md) (round 248).
- Create default `lego/backend/internal/apps/service.go:3580-3588` (also reached by Blueprint applies); `setAutoDeployFetched` `:5246`, `:5264`, `:5270-5273`; `lego/backend/internal/apps/settings.go:388`; refusal precedent `errPrebuiltImageField` `lego/backend/internal/apps/blueprint_compiler.go:401`.
- `pushDeliveryMethod` `lego/backend/internal/apps/pushdelivery.go:130-175` (`PushDeliveryUnavailable` `:56`).
- Build-source-linked services are not repo pushes and stay as they are.

## Steps

1. Consult `pushDeliveryMethod` on both write paths; store off by default and refuse an explicit `yes` with a named error, e.g. "auto-deploy needs a connected Git provider: bex doesn't receive this repo's pushes. Connect it through the GitHub app, or deploy with the Deploy Hook".
2. If t001 captured a different Render answer (for example a silent store-off), match its shape; the stored value is off either way.

## Blocked (2026-11-14)

**Needs the user's decision; the change is a divergence from what Render shows.** ADR026 § 8 records that Render shows Auto-Deploy as on for a public-Git-URL service (community report; bex deliberately kept the same default and discloses `pushDeliveryMethod` instead, "a disclosure ahead of Render, not a divergence"). Storing it off and refusing an explicit `yes` follows Render's docs rule but departs from Render's observed stored value, so under the root AGENTS.md rule it stands only with the user's sign-off in ADR018.

The implementation was written and tested on 2026-11-14, then withheld; re-apply it once the user signs off:

- `apps/pushdelivery.go`: `withholdUnreachableAutoDeploy(ctx, tenantID, requested *bool, spec)` stores `AutoDeploy=false, AutoDeployTrigger=""` for a new service whose `pushDeliveryMethod` is `unavailable` (not build-source-linked) and returns `errAutoDeployUnreachable("autoDeploy")` for an explicit `yes`; `checkAutoDeployTurnOn(ctx, a, enabled)` refuses turning it on from off (a stored-on service may re-send `yes`, so the official CLI's round-trips keep working).
- Call sites: `create()` right after the build-source link; `setAutoDeployFetched` after the prebuilt-image refusal; the `AutoDeploy` row's `check` in `settings.go`; `applyStackService` for a new Blueprint service (requested `nil`, so a file's `autoDeploy: true` is stored off, not refused).
- Tests: REST create (unavailable → `no`; `github_app`, `manual_webhook`, prebuilt image controls), explicit `yes` → 400, REST PATCH / GraphQL `setAutoDeploy` / MCP `update_service` refusals storing nothing, a stored-on re-send allowed, `unknown` keeps the default.
- t004's create form then needs a pre-create answer for a typed repo: a `repoPushDelivery(repo, ownerId)` GraphQL query (`RelCanCreate` in the named workspace, sending the selected workspace) and a debounced hook were written on 2026-11-14 and withheld with it.

Options for the user: (a) sign off the divergence (honest default off and 400, as above); (b) keep Render's observed behavior (status quo, with the hint and the banner's manual variant), and close t002/t004 as not wanted; (c) capture Render's API answer first (needs a Render API key, w10/002).
