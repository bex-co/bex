## Objective

When a push matches a service or Blueprint by id but its URL is not the stored one, bex updates the stored `repo` to the payload's canonical URL. Every read surface then shows the repository's current name, and a later rename back cannot collide with an unrelated new repository under the old name.

## Context

- `core.CanonicalRepo` (`lego/backend/internal/core/giturl.go:34`) is the canonical form both sides compare.
- The `apps` row is the source of truth; the projector carries `repo` to the App CR. Writing the CR directly would be reverted.
- A rename back to the old name and a new repository created under the old name are the reasons the id, not the URL, must win.
- GitHub also sends a `repository` event with `renamed` and `transferred` actions to Apps subscribed to it. bex handles only `push` today (`webhook.go:494`). Subscribing needs a change in the GitHub App's settings, which is optional here: the push carries what this task needs.

## Steps

1. In the id-matched path, compare the payload's canonical URL with the stored one; when they differ, update the `apps` or `blueprints` row through the store.
2. Record it once per change: an audit row with the system actor, naming the old and new URL.
3. Make the update idempotent across redeliveries and concurrent pushes.

## Files

- `lego/backend/internal/apps/webhook.go`, `lego/backend/internal/store/` (repo update), `lego/backend/internal/audit/` if a new verb is needed

## Acceptance criteria

- [ ] After an id-matched push from `owner/new-name`, REST `GET /v1/services/{id}` reads `https://github.com/owner/new-name`, and so do GraphQL and MCP.
- [ ] A Blueprint's `repo` moves the same way.
- [ ] A redelivery of the same push records no second audit row.

## Out of scope

- Handling the `repository` event (an optional follow-up if the App subscription is added).
