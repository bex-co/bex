## Objective

`BlueprintStatusBadge` is reused for two different backend vocabularies — `Blueprint.Status` (`created|paused|in_sync|syncing|error`) and `BlueprintSync.State` (`created|running|success|error`) — but its `variantMap`/`labelMap` were only ever built for the first one. Extend it so every real value from both vocabularies renders with an intentional styled variant instead of falling through to the raw-value fallback.

## Context

- `dashboard/src/features/blueprints/components/blueprint-status-badge.tsx`: `variantMap`/`labelMap` cover exactly `active, in_sync, syncing, error, paused`. `dashboard/src/routes/blueprints.$blueprintId.tsx:437` passes `run.state` (a `BlueprintSync.State` value — `lego/backend/internal/store/blueprints.go:60-63`: `created, running, success, error`) into the same component used for the Blueprint's own top-level status.
- `success` and `running` (and `created`, if a sync row is ever listed while still queued) aren't in either map, so they fall through to `variantMap[status] ?? "secondary"` and, worse, `labelMap[status] ?? t("blueprints.statusUnknown", {status})` — and `blueprints.statusUnknown`'s message is literally `"{status}"` (`dashboard/src/features/blueprints/locales/en.ts:349-352`), i.e. the raw backend string rendered verbatim and unstyled next to a properly capitalized, colored "Error" badge for the same column.
- Repro: blueprint `blp-d9nqg95cavls73fp8m10`'s Sync History — every successful row's State cell shows plain lowercase "success" text while the one failed row shows a red "Error" pill.
- Note `active` in the current `variantMap`/`labelMap` doesn't correspond to any constant in `lego/backend/internal/store/blueprints.go`'s `BlueprintStatus*`/`BlueprintSyncState*` lists (which use `in_sync`, not `active`) — leave it as-is (may be a legacy/other-caller value) but don't assume it's dead without checking other callers of `BlueprintStatusBadge`.

## Steps

1. Grep all callers of `BlueprintStatusBadge` to confirm the full set of status/state values it's ever handed (both `Blueprint.status` and `BlueprintSync.state` call sites).
2. Add `success` and `running` (and `created`, for completeness with the sync-state vocabulary) to `variantMap` and `labelMap`, with locale-driven labels — e.g. `success` → a positive/default-toned variant and a "Success" (or "Synced", matching whatever the codebase's existing convention is for a completed-successfully state elsewhere) label; `running` → the same "syncing" treatment (secondary + a "Running"/"In progress" label) since they're semantically the same as `syncing`.
3. Add the new locale keys to `dashboard/src/features/blueprints/locales/en.ts` and `zh.ts`, following the existing `blueprints.status*` naming pattern.
4. Confirm `error` (shared between both vocabularies) still maps identically — no regression there.
