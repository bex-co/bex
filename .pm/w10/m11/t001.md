## Objective

Stop the `/billing` Charges card from flashing a false, then-contradicted claim about whether its total is an estimate or a real Stripe invoice amount.

## Context

- `dashboard/src/features/usage/components/charges-card.tsx` — `ChargesCard` computes `const invoiced = invoicedUsd == null ? null : usd(invoicedUsd);` and then, unconditionally, `{invoiced == null ? t("usage.chargesDescriptionEstimate") : t("usage.chargesDescriptionInvoiced")}` in the `CardDescription` (around line 228-232). This does not consult the `loading` prop at all.
- The component already has a `loading` prop and uses it correctly for the row skeletons a few lines below (`loading && categories.length === 0 ? <Skeleton/> : ...`), so the same signal is available for the description — it's just not wired to it.
- Repro (live, 2026-08-21/22): on `/billing`, the initial paint shows "Accrued so far this period, priced from the bex rate sheet. An estimate, not an invoice." (`usage.chargesDescriptionEstimate`); once `invoicedUsd` resolves a moment later it swaps to "Accrued so far this period. The total is the amount Stripe will invoice." (`usage.chargesDescriptionInvoiced`). Both are real, distinct strings (`dashboard/src/features/usage/locales/en.ts:258-266`, `zh.ts` mirror) — the bug is committing to the "estimate, not an invoice" claim while `invoicedUsd` is merely *not yet loaded*, indistinguishable in the current code from "this workspace genuinely has no Stripe pricing."
- Caller: find where `ChargesCard` is rendered (likely `dashboard/src/routes/billing.tsx` or a `features/usage` billing page component) to confirm what `loading` is actually threaded from — the same query that resolves `invoicedUsd`.

## Steps

1. Read `charges-card.tsx` in full and find the `ChargesCard`'s caller to see the exact `loading`/`invoicedUsd` data-fetch relationship (are they from the same query, or could `loading` go false while `invoicedUsd` is still genuinely pending from a second request?).
2. Change the `CardDescription` so that while the data determining `invoicedUsd` is still in flight, it renders a neutral/loading state (e.g. a `Skeleton` matching the row skeletons' pattern, or simply nothing) rather than either `chargesDescriptionEstimate` or `chargesDescriptionInvoiced`. Only commit to one of the two real strings once the fetch has actually settled.
3. Confirm the two message strings themselves stay accurate for their real, resolved meaning (estimate-only workspace vs Stripe-priced workspace) — no copy change needed there, only the loading-state gating.
