## Objective

Every REST list operation t001 found returning the full set answers 20 items and a cursor when neither `cursor` nor `limit` is given, with the same clamp (100, or 1000 for audit logs) when `limit` is given.

## Context

- t001's table; `core.StablePage`, `core.PageParams`, `core.PageLimit` in `lego/backend/internal/core/pagination.go`.
- Render's cursor envelope is already served on paged requests (w8/m13 for datastores, w2/m43 for GraphQL lists).

## Steps

1. Make REST callers page unconditionally (a REST-side helper that always pages, so a future REST list cannot opt back into the full set); leave GraphQL's `gqlutil.Page` alone.
2. Flip the sandbox test and any other test that pinned the full-set default.

## Files

- the REST list handlers from t001 (`lego/backend/internal/*/rest.go`), `lego/backend/internal/core/pagination.go`

## Acceptance criteria

- [ ] Each changed list returns 20 and a cursor unpaged in its own test; `limit=100` still returns up to 100.
