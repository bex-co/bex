# 013 — An agent session's unpushed commits and working tree vanish when its next turn starts on a fresh sandbox

Why: an agent that could not push (or was stopped before it did) loses every change it made, silently, so the user pays for a run that delivers nothing and cannot even inspect what was done. Severity: major (lost work). Surface: cloud agent sessions (ADR047), sandbox lifecycle.

## Evidence (production, workspace `bex`, 2026-11-17/18)

- `ags-dbu0pfdikg6s738lam7g` (muse) made 3 local commits (`479416bef`, `585f7a3ff`, `89e9c6ca3`) whose push was refused (see [014](014.md)). A follow-up message hours later found the repository re-cloned at `origin/main`; `git cat-file -t` on all three: `fatal: Not a valid object name`.
- `ags-dbu0pfmc1l2s739d3n3g` (claude): the same, commit `aab904120` gone after the follow-up turn ("the sandbox re-cloned the repository at 10:25:59 UTC").
- `ags-dbutgej906ns73ff3kb0` (muse, `beancount-rt-flaky-test-fixer` automation): a verified fix was in the working tree, uncommitted, when the turn failed ([016](016.md)). The next message found `git status` clean: "the lazy-chart fix and ledger edit are gone".
- The transcript (`bex agent logs`) records tool commands but not file contents, and `bex agent files` lists nothing, so the work cannot be recovered from the session either.

## Gap against existing work

- w22/done/m413 keeps the disk of a turn the user **Stops**.
- w10/done/m15 closes an idle sandbox after 2h and keeps the conversation.

Neither covers a turn that ended, or failed, with unpushed work: the next turn starts on a new clone and nothing says the work is gone.

## Direction

Before a sandbox is closed or replaced, push the session's unpushed commits and an uncommitted-diff snapshot to a recovery ref (e.g. `refs/bex-agent/<session>/recovery`), or retain the disk as m413 does; tell the agent and the user in the next turn what was restored or lost. At minimum, surface "N unpushed commits were discarded" on the session.
