# 035 — `gh` can be turned off only for the whole workspace, while a Devin security profile also binds to the automations default, one automation or one session

Why: an admin who wants `gh` for interactive sessions but not for a scheduled automation (or the reverse) has only the workspace switch w10/m524 added, while Devin's profiles bind at five levels and "the most specific binding wins". Found by the w10/m524 Devin comparison (t008), 2026-11-19. Severity: minor (Devin parity, stricter variant). Surface: the agent environment, automations (`agentConfig`), session create.

## Reference

Devin security profiles bind at the enterprise default, organization default, automations default, an automation and a session; "the most specific binding wins, unless a mandatory profile higher up locks things down", and the automations default overrides "the organization default for those sessions". A profile can "remove the GitHub CLI token" ([Security profiles](https://docs.devin.ai/product-guides/security-profiles), read 2026-11-19).

## Current state (2026-11-19)

`agent_environments.github_cli_disabled` (w10/m524) is the only control. The mints read it per workspace (`Minter.githubCLIAllowed`, `lego/backend/internal/agentsession/mint.go`), and `driverEnv` sets `BEX_AGENT_GITHUB_CLI=0` from it (`lego/backend/internal/agentsessions/service.go`). Nothing on an automation's template or a session's `agentConfig` can turn `gh` off for that automation or session alone.

## End state

An automation's template and a session create can turn `gh` off for those sessions (for example `agentConfig.githubCli: false`, on REST, GraphQL, MCP, `bex agent run`/`bex agent automations` and the dashboard composer and automation form), and the workspace setting can be made mandatory so no automation or session turns `gh` back on. The mints and `driverEnv` resolve the most specific binding, the route's refusal names the level that turned it off, and a test covers each level's precedence.
