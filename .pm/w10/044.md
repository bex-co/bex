# Only a workspace admin selects an agent session's or an automation's `gh` binding, as Devin gates every security-profile selection

Why: w10/m561 lets a member turn `gh` off for their own session or automation, while Devin's "Members without the permission can't enumerate, select, or change profiles" gates even an opt-out behind "Manage security profiles".

- **Today (w10/m561).** `agentConfig.githubCli: false` on a session create and on an automation template is never refused (`refuseGitHubCLIOn`, `lego/backend/internal/agentsessions/githubcli.go`). Only `true` needs `can_manage`. ADR047 D2's w10/m561 amendment records this as a divergence: an off only removes access.
- **Devin** ([Security profiles](https://docs.devin.ai/product-guides/security-profiles), re-read 2026-11-22). Selecting a profile at any level needs "Manage security profiles", held by org admins by default. A member's session takes whatever chain applies.
- **The stricter variant.** A member's `githubCli: false` is refused too, with `AGENT_SESSION_GITHUB_CLI_LOCKED` / `AGENT_AUTOMATION_GITHUB_CLI_LOCKED` and `reason: admin_required`, and the composer and automation form show the control disabled for members. It may be a workspace option rather than the default, since an off cannot loosen anything.
- **Decide first.** Whether bex follows Devin here at all. A member who wants no `gh` in their own session can already ask the agent not to use it, so the variant trades a member's convenience for an admin's control.
- **Done when.** The chosen rule is enforced on REST, GraphQL, MCP, the CLI and the dashboard, ADR047 D2 drops or keeps the divergence line, and a test pins a member's off on each surface.
