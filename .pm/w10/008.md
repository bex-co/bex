# Sandbox pod-ready timeout: wrong user message, and the informer-staleness root cause

Why: the 2026-10-29/30 incident failed every agent session as "sandbox capacity reached". The real cause was opensandbox-server's informer cache never showing the BatchSandbox as Ready. It was mitigated in `e60b99f25` (informer off), but the root cause and the misleading message remain.

- `lego/backend/internal/sandbox/service.go` `sandboxCapacityError`: any POD_READY_TIMEOUT is reported as a capacity/plan limit with an "Upgrade plan" call to action. Distinguish the cases: ask OpenSandbox or the BatchSandbox for the Pod's actual state (Ready vs Pending/unschedulable), and only claim capacity when it is quota/unschedulable.
- Root-cause the stale informer (it started after the 2026-10-28/29 rebuilds, e.g. `092e9b57e` controller Go 1.26). Reproduce in dev with `informer_enabled = true` and check whether tenant-namespace watches deliver updates. Re-enable the informer only with a fix.
- Consider a bex-side safety net: if the session's sandbox Pod is Ready but create hasn't returned after N seconds, adopt the sandbox anyway.
