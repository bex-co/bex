## Objective

A datastore plan change's audit row carries the typed `PlanFrom`/`PlanTo` pair, exactly like an app plan change already does — closing the audit-detail asymmetry across the three siblings.

## Context

- Apps: `lego/backend/internal/core/audit.go:260-261` (`RecordPlanChanged`) sets `ev.PlanFrom`/`ev.PlanTo`.
- Datastores: `RecordDatabaseEffect`/`RecordKeyValueEffect` (same file, ~`:320-357`) build the event without the plan pair — the fields land NULL for `plan_changed` rows.
- The effect helpers are generic (also used for plain updates at `postgres/service.go:688`, `keyvalue/service.go:644`); the plan pair applies only to the plan-changed call sites (`postgres/service.go:570`, `keyvalue/service.go:542`), where `from` is already in scope. Either thread an optional plan pair into the helper or add dedicated plan-changed recorders mirroring apps' `RecordPlanChanged` — pick whichever reads simpler against the existing helper shape.

## Steps

1. Extend the recording path so the plan-changed call sites pass `from`/`to`; leave the generic-update call sites unchanged (no plan pair).
2. Run backend `go test ./...`; eyeball a recorded row (unit-level) to confirm the pair persists through `recordAudit`.

## Files

- `lego/backend/internal/core/audit.go`
- `lego/backend/internal/postgres/service.go`
- `lego/backend/internal/keyvalue/service.go`

## Acceptance criteria

- [ ] A postgres and a keyvalue plan change each produce an audit row with `PlanFrom`/`PlanTo` set to the real pair.
- [ ] Generic datastore updates still record no plan pair.
- [ ] Apps' behavior is unchanged.

## Out of scope

- Surfacing the pair anywhere new in REST/GraphQL responses beyond where apps' pair already appears (parity check owns spotting drift there).
