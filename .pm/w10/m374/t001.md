## Objective

An unfiltered `http_latency` read (REST `GET /v1/metrics/http-latency`, GraphQL `metrics(name: http_latency)`, MCP `get_metrics`, the dashboard chart) goes to the request-log store like the request count, so a minute containing a wake has a p99 within about 1 s of that request's `responseTimeMS`, and a minute with a single request has a point. It falls back to the Prometheus histogram only when Loki errors, as the count does.

## Context

- Evidence and the Traefik root cause: [w4/605](../../w4/done/605.md) (**major**, round 189: w4/559's DoD 2 failing live after its fix).
- `promQueryFor` in `lego/backend/internal/metrics/source.go:474-503` reads `rate(traefik_router_request_duration_seconds_bucket…)`; Traefik v3.7.17 router series are created on the first request and so never count it in `rate()`.
- `requestMetric`'s branch at `lego/backend/internal/metrics/service.go:1130` sends only the count to Loki; the `quantile_over_time(… | unwrap latency_ns …)` builder already exists (`lokisource.go:136-143`) and answers the wakes on a `host=` read.

## Steps

1. Admit `MetricHTTPLatency` to the Loki branch of `requestMetric` for unfiltered reads, with the existing Prometheus fallback on a Loki error.
2. Keep the `/p1` path count, the host filter, `aggregateBy=host` and a static site's Response Times unchanged (w4/m113).
