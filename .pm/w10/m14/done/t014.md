## Objective

Charge the card as soon as a workspace's agent-model spend reaches its trust tier's threshold ($10 at T0, rising to $25, $50, $250, none at T4), so non-payment exposure is bounded by the threshold rather than the month.

## Context

- ADR091 D10.2–D10.3 (amended 2026-11-02), D3 real-time meter (t004), D10.1 tiers (t005).
- Today usage reaches Stripe only through meter events after the 48h seal; there are no thresholds, off-cycle invoices or off-session PaymentIntents (`lego/backend/internal/billing/`). Pinned API: stripe-go v86, `2026-08-26.dahlia`.

## Steps

1. **Probe first** in Stripe test mode: set `billing_thresholds.usage_gte` on a meter-backed subscription item and confirm a threshold invoice is created and paid when the meter crosses it, and that the cycle invoice bills only the remainder. Record the result in this task.
2. If it works: set the agent-model item's `usage_gte` to the tier threshold in µUSD on subscription create and on every tier change (t005 signal); remove it at T4.
3. If it does not: bex creates the threshold invoice itself (`InvoiceItems` + `Invoices.New` + pay, idempotency key `bex-threshold-{workspace}-{seq}`) and stops reporting the already-invoiced amount to the meter.
4. A failed threshold charge enters the existing ADR040 §7 dunning path, drops the workspace to T0, and the mint refuses new platform-model requests with `BILLING_BALANCE_DUE` until a charge succeeds (no grace period for model spend).
5. Record monthly agent-model bad debt vs revenue so the D10 prepaid trigger (> 2%) can be checked.

## Files

- `lego/backend/internal/billing/`
- `pricing.yaml`, `lego/backend/internal/pricing/`

## Acceptance criteria

- [x] The probe result (item threshold works on meter prices, or the fallback was used) is written in this task.
- [ ] Stripe test mode: a T0 workspace crossing $10 gets exactly one threshold invoice, paid automatically; the cycle invoice bills only the remainder; replaying the same usage events does not double-bill.
- [x] Test: a tier change updates the item threshold ($10 → $25), and T4 removes it.
- [x] A failed charge marks the workspace past-due through the existing dunning state, drops it to T0, and the next mint is refused with `BILLING_BALANCE_DUE`; a later successful charge lifts the refusal.

## Out of scope

- Prepaid credits (rejected in ADR091).

**Conclusions:**

1. Item-level `billing_thresholds.usage_gte` works on a meter-backed price on `2026-08-26.dahlia`, in both billing modes, set at creation or by update, and it can be removed. The fallback (a bex-issued invoice) is not needed and was not built.
2. Stripe evaluated the threshold 15 to 28 minutes after the usage (it looks like a periodic batch). The threshold invoice is a draft that auto-finalizes and charges one hour later. So from the crossing to the charge is about 2.5 hours: up to ~65 minutes of bex export (D3), 15 to 28 minutes of evaluation, and 1 hour of draft. The D5 spend cap covers that window. A follow-up could finalize `subscription_threshold` drafts on `invoice.created` to save the hour.
3. Exactly one threshold invoice was issued per crossing. The cycle invoice excludes usage already invoiced, and a replayed meter event is rejected by its identifier, so nothing is billed twice.

## Implementation notes (2026-11-05)

- **Threshold.** `billing.AgentModelThresholds` reads the tier and `TierThresholdMicroUSD`. `StripeClient.SyncAgentModelThreshold` compares Stripe's current item value with the tier's and writes only when they differ (it removes the threshold at T4). The threshold is set at item creation (`EnsureContract`, the workspace-creation contract, and `syncContractItems` adding the item), when an existing Subscription is first synced in a process, on `Trust.OnTierChanged`, and in a sweep every `BEX_STRIPE_RECONCILE_INTERVAL` (default 5m). A held meter has no catalog Price, so it never gets a threshold. When two items rate the agent-model meter, the item on the catalog Price is used, and the duplicate is logged and counted (`operation="agent_model_item",result="duplicate"`).
- **Sweep state (review fix).** There is no clock window. Each `billing_trust` row records the value last applied to Stripe (`threshold_synced_microusd`), the trust version it was computed from (`threshold_synced_version`, the row's `updated_at`), and when it was computed (`threshold_synced_at`), with per-workspace backoff (`threshold_attempts`, `threshold_next_attempt_at`; 1 minute doubling to 1 hour). A workspace is due when it was never applied, when its trust record changed since, or when its payment lock expired after the value was computed. Each sync holds a per-workspace advisory lock and records the version it read. A webhook that commits during a sync therefore leaves the workspace due rather than skipped. When the recorded value already equals the tier's, Stripe is not called. One failing workspace backs off alone. The pass runs under a session advisory lock (`store.RunExclusive`), so only one bex-api replica calls Stripe. A threshold failure inside `syncContractItems` never blocks usage export: it is logged, counted and retried at the next contract sync. Workspaces with a trust record are also retried by the sweep. Ops edits to `billing_trust` must set `updated_at = now()`.
- **Threshold invoices are finalized at once (review fix).** On `invoice.created` with `billing_reason=subscription_threshold` and `status=draft`, bex-api calls `FinalizeInvoice` with `auto_advance=true` (idempotency key `bex-finalize-threshold-{invoice}`). An invoice that is already finalized is a no-op: bex-api re-reads it after a refused finalize. This removes Stripe's one-hour draft window. The live timing is not yet re-probed (open acceptance item).
- **Failed charge.** The mint refuses the platform route with `BILLING_BALANCE_DUE` (429, refusal header `billing-balance-due`, Anthropic-shaped `rate_limit_error`, session `failureReasonCode`). The refusal holds while any failed invoice of the workspace is open (`billing_trust_failed_invoices`), or while any unpaid write-off exists. Decision: a failed invoice is closed by `invoice.paid` (including $0), or by `invoice.voided`. A settlement that arrives before its failure leaves a tombstone, so the late failure cannot reopen it. `invoice.marked_uncollectible` does **not** close it: the invoice is still owed, so model spend stays refused until it is paid. The write-off clause also covers an invoice that ops marks uncollectible without a prior failure event. The T0 lock keeps t005's rule: only the newest failed invoice's payment settles it. The 20-second mint spend cache can delay the refusal, and its lift, by up to that TTL.
- **Bad debt (review fix).** `invoice.marked_uncollectible` records a row in `billing_agent_model_writeoffs` (migration 0197). The row holds the invoice's agent-model lines net of their discounts (re-read from Stripe), the written-off share `net × amount_remaining / total`, and the usage month (the first agent-model line's period start, else the invoice's `period_start`). The row has no FK, so it outlives the workspace. A later `invoice.paid` deletes it in its own statement, which works even after the workspace is gone. Revenue comes from `billing_agent_model_revenue_months`. Each sweep raises the current month's snapshot to the live `usage_hourly` + `usage_monthly` sum (`GREATEST`, using the new partial index `usage_hourly(kind, window_start) WHERE resource_kind='agent_session'`). It also raises the closed month's snapshot until an hour into the new month. So a workspace deleted mid-month (its usage rows cascade) keeps its revenue counted, up to the last sweep before deletion. **Where to read the D10 prepaid trigger:** the Prometheus gauges `bex_billing_agent_model_month_revenue_microusd{month="current"|"previous"}` and `bex_billing_agent_model_month_written_off_microusd{…}` on bex-api's internal `/metrics`, which every replica reads from the snapshot each pass, or `store.AgentModelBadDebtForMonth`. Trigger: written-off > 2% of revenue for the same usage month. Write-offs land one to two months after their usage month, so read the "previous" gauge, or query older months.
- **Retention.** Write-off rows are kept 7 years as a debt record, then purged by the billing worker's daily retention pass (`PurgeAgentModelWriteOffs`). That pass runs only while `BEX_STRIPE_DUNNING_ENABLED` is on. ADR086 records this in a dated amendment.
- **Webhook events.** `invoice.voided`, `invoice.marked_uncollectible` and `invoice.created` are now in `WEBHOOK_EVENTS`: 16 events. Add them to an existing endpoint with `--add-missing-webhook-events`.
