# 015 — Agent sessions fail with `SANDBOX_START_FAILED` when several start within a minute or two

Why: an automation fleet or a burst of user sessions loses runs to an error that names no cause and is never retried, so scheduled routines silently skip their slot. Severity: moderate (reliability under load). Surface: agent sandbox scheduling.

## Evidence (production, workspace `bex`, 2026-11-17)

- 10 sessions created within ~1 minute (`bex agent run`, agents muse and claude, repos bex and beancount-io): 3 failed at turn 1 with `SANDBOX_START_FAILED: sandbox did not start (platform issue)` — `ags-dbu0pg6c1l2s739d3n7g`, `ags-dbu0pg5ikg6s738lambg`, `ags-dbu0pgec1l2s739d3n90`.
- Re-run with 90 s between starts: 3 of 5 failed the same way — `ags-dbu2lrcj705s738i85c0`, `ags-dbu2mhohdavc73bdbhk0`, `ags-dbu2n8kj705s738i865g`. Two later starts 2 minutes apart both succeeded.
- 17 scheduled automations were also running in the workspace at the time.

## Gap against existing work

w9/done/074 introduced `SANDBOX_START_FAILED` for non-capacity start failures; it does not cover failures under concurrent starts, and the session shows no underlying reason.

## Direction

Record the underlying cause on the session (node pressure, image pull, gVisor gate, quota) and retry a start that failed for a transient reason before failing the turn; for automation runs, retry or reschedule rather than drop the slot.
