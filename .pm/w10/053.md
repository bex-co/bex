# 053 — Merging a stacked pull request now goes to GitHub's synchronous merge, which does not support stacks, where Devin's merge lands the pull request and every open one below it

Why: a takeover session, or one given a `number` (w10/041), asked to merge a person's stacked pull request now gets the synchronous merge. GitHub says that merge "does not support stacked pull requests", so the pull request does not land with its stack. Devin's merge button lands the whole stack. Filed by w10/048, 2026-11-23. Severity: minor (Devin parity; it reaches only stacked pull requests, and a session's own pull request is never stacked). Surface: `lego/backend/internal/github/merge.go` (`MergePullRequest`), `lego/backend/internal/agentsession/pullrequest_merge.go` (`PullRequester.Merge`), ADR090 D3.

## Reference

- [Devin Review](https://docs.devin.ai/work-with-devin/devin-review), read 2026-11-23: "Stacked PRs merge through GitHub's atomic stack merge: merging a PR also merges every open PR below it in the stack", and "The merge button shows exactly how many PRs the action will land".
- [Pulls](https://docs.github.com/en/rest/pulls/pulls), read 2026-11-23:
  - `PUT …/pulls/{n}/merge` "does not support stacked pull requests or merging with a merge queue".
  - `PUT …/pulls/{n}/merge-async` "is the required API for merging stacked pull requests", and "For a stacked pull request, the operation includes all open downstack pull requests". It takes `merge_action` (`default`, `direct_merge`, `merge_queue`), `merge_method` (direct merges only) and `sha`. It answers 202 with a UUID to poll (`GET …/merge-async/{uuid}`: `pending`, `merged`, `enqueued`, `failed`), or 200 when the pull request is already merged or queued.
- [Stacked pull requests APIs](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests-apis-and-webhooks), read 2026-11-23: "A stack cannot be merged with the legacy synchronous merge endpoints or mutations". A stack merge is atomic.

## What w10/048 left

`PullRequestMergeState` reports `Stacked` and `StackBase`. With `auto`, a stacked pull request arms its stack (`includeStack`). These still reach `MergePullRequest`, the synchronous merge:

- a plain merge of a stacked pull request;
- an arm GitHub refuses with "is in clean status" because the whole stack is ready now.

On a stack whose base requires a merge queue, the arm's method is ignored by the queue, and a plain call does not queue the stack.

## End state

A merge now of a stacked pull request lands it with every open pull request below it through `merge-async`, pinned to the head as today (`sha`), with the method rule of the stack's base. The same holds for the `auto` fallback when the stack is ready now. A stack whose base requires a merge queue is queued (`merge_action: default`). The verb polls the result within the request, under a stated bound, and maps `failed` to GitHub's words under today's codes. ADR090 D3 decides what an answer still `pending` at the bound says. The answer says how many pull requests landed, as Devin's button does. Tests cover the request body, each poll result, and a pull request in no stack left on today's synchronous merge.
