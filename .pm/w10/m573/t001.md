## Objective

Decide how a provider filter is stored, written, read and rolled out beside w10/m568's two modes, and amend the ADRs, so t002–t005 implement one written design. Record the decisions in the milestone README under `## Design record (t001)`.

## Context

- m568's storage (`docs/ADR047-cloud-coding-agent-sessions.md` D7 amendments; `lego/backend/internal/store/migrations/0330_agent_environment_model_allowlist.up.sql`): `disabled_models` are the models an admin turned off, and `known_models` is the catalog the last narrowing write saw (NULL allows all). The allowlist is `known_models − disabled_models`. `leftOn` (`lego/backend/internal/agentsessions/environment.go`) reads it, and a row with `known_models` NULL or `disabled_models` empty reads as the opt-out, which keeps a previous-release write readable.
- Devin, re-read 2026-11-22:
  - [Devin Desktop admin controls](https://docs.devin.ai/desktop/controls): "Filter by specific models or by provider (one filter type at a time)".
  - [List Models](https://docs.devin.ai/desktop/accounts/api-reference/list-models): `allowed_model_tags` "including provider tags such as `provider-anthropic`"; `allowed_model_uids` "Empty when the team allows models by tag only"; "A model is allowed when its UID is listed or it carries a listed tag".
- The catalog's provider is a model id's prefix before `/` (`deepseek`, `anthropic` today). `BEX_AGENT_PLATFORM_MODELS` refuses a malformed entry at startup (`lego/backend/AGENTS.md`).
- The previous release during the rollout is m568's code, or the code before it if both ship in one deploy. Neither knows the new column.

## Steps

1. **Storage.** For example a nullable `agent_environments.enabled_providers text[]`.
   - Decide what a provider write also stores in `disabled_models` and `known_models`, so a previous-release Pod offers the same set under the same catalog.
   - Decide how the new code tells a provider filter from a later previous-release `enabledModels` write that left the column in place. For example, it reads the provider filter only while the stored `disabled_models` and `known_models` are still the ones that filter wrote.
2. **The write.**
   - `enabledProviders` replaces the filter with a by-provider one. `enabledModels` replaces it with a by-model one (m568's modes). Both in one write are refused.
   - Choose the refusal code and params: an unknown provider (with the catalog's providers listed), both fields at once, off the route.
   - Decide what `[]` means: refused, or only the catalog default.
   - Decide how a provider filter returns to "allow all". For example, `enabledModels` naming every catalog model, as in m568, or every provider listed. Note whether listing every provider still leaves a new provider's model off, which is Devin's reading.
   - `defaultModel` must be in the offered set after the write, as today.
3. **The read.**
   - Name the fields on REST, GraphQL and MCP: the filter in force (for example `enabledProviders: [String!]`, null or `[]` when filtering by model) and the catalog's providers (for example `providers: [String!]!`, in catalog order).
   - `enabledModels` stays the effective list. `newModels` is `[]` under a provider filter.
   - GraphQL cannot carry an explicit null. Follow the `resetAutomationsGithubCli` pattern if a reset flag is needed.
4. **Amend the ADRs.**
   - ADR047 D7: the amendment, plus the `Scope.` line at :305.
   - ADR090 § Model pin ("A workspace narrows the catalog").
   - The ADR018 agent-model row: drop the w10/037 divergence and cite Devin's pages above.
