## Objective

Walk the whole `bex login` browser flow end to end and make it read as one streamlined experience: signed-out bounce → login → device confirm → (trusted-client consent skip) → device success, with consistent shell chrome, working theme + language across every step, and no dead ends. Fix small papercuts found on the walk; file anything larger as follow-up notes.

## Context

- Flow: CLI opens `/auth/device?device_challenge=…&user_code=…`; signed-out visitors bounce through `/auth/login` with `next` preserving code+challenge; after confirm, Hydra's redirect continues through login/consent routes; trusted clients (`OAUTH_TRUSTED_CLIENTS`) skip the consent screen; landing page is `/auth/device/success`.
- Drive it against the dev-10 stack (`bash .pm/w10/dev-10/up.sh`, Hydra + Kratos in `dev-10-auth`) with Playwright MCP; screenshots to `.playwright-mcp/` with bare filenames.
- Check specifically: the confirm page's code matches what the CLI printed; Cancel is a sane exit; back-button behavior; both themes; zh locale renders (await `ensureLanguage`); document titles per step; the success page's "return to your terminal" guidance.

## Steps

1. Bring up dev-10; start a real device flow (`bex login` pointed at dev-10, or curl Hydra's device endpoint to mint a challenge/code pair).
2. Walk the flow signed-out and signed-in; screenshot each step in light + dark and en + zh.
3. Fix small inconsistencies (spacing, copy, focus order, missing title) in place; note anything > sub-hour as `w10/NNN` inbox notes.

## Resolution

Deviated from the planned dev-10 k8s stack: stood up an isolated dashboard dev server (non-standard port 5199, per the workstream's port-collision rule) against `scripts/local-bex.mjs`'s existing Kratos/Hydra stub instead — sufficient because `handleDeviceVerification`'s GET only needs a session + non-empty user_code/device_challenge to render the confirm view (Hydra pairing is only reached on POST), so the confirm/expired/success pages can be exercised without a live device_challenge minted by a real CLI. Verified: light + dark themes and en/zh locales on the confirm page (`.playwright-mcp/device-confirm-light.png`, `device-confirm-dark.png`, `device-confirm-final.png`); the success page in en + zh (`device-success-final.png`, `device-success-zh-check.png`); the no-challenge GET still 302-redirects to Hydra's verify endpoint (signed-out/redirect leg unaffected); `/auth/device/success` renders correctly and independently of the confirm page (the regression this task's dev-loop surfaced and t001 fixed). No deferred findings — the flow was already consistent after t001/t002, so no follow-up inbox note was needed.
