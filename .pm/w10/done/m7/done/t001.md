## Objective

Replace the hand-rolled inline-HTML confirm page (`deviceConfirmationPage` in `hydra-device.ts`) with a real routed React page rendered inside `AuthPageShell`, so the signed-in confirm step at `/auth/device?device_challenge=…&user_code=…` looks and behaves like the rest of the auth workflow (consent page, device-success page) — theme-aware, i18n'd, same chrome — while byte-preserving the security semantics: the grant never pairs on a GET, and pairing requires the same-origin, session-bound POST to `/auth/device` (codex-security #9).

## Context

- `dashboard/src/routes/auth.device.tsx` — server-only route: GET `handleDeviceVerification`, POST `handleDeviceConfirm`; signed-out visitors bounce through login with code+challenge preserved in `next`.
- `dashboard/src/common/server-fn/hydra-device.ts:200-249` — `deviceConfirmationPage()` returns raw HTML with a fixed dark `<style>` block; this is what drifts from the rest of the workflow.
- Pattern to follow: `dashboard/src/features/auth/pages/consent-page/index.tsx` (AuthPageShell + Card + Buttons, `getRouteApi` search params) and `dashboard/src/routes/auth.device.success.tsx` + `device-success-page/index.tsx` (a sibling device-flow React page already on the shell).
- The confirm can stay a plain `<form method="POST" action="/auth/device">` with hidden `user_code` + `device_challenge` inputs — no JS required to submit, so the POST handler and its origin/session checks need no change. Both values already appear in the GET URL, so rendering them via a React route's search params leaks nothing new.
- Suggested shape: a `/auth/device/confirm` (or component-on-the-same-route) React page; the GET handler, in the signed-in-confirm case, redirects/renders into it instead of returning `deviceConfirmationPage(...)`. Keep the signed-out bounce and the Hydra-redirect continuation paths in the server handler exactly as they are.
- Every string through `useTranslations()` with new `auth.deviceConfirm*` keys in `features/auth/locales/{en,zh}.ts` (write "bex CLI", not "Render CLI" — t002 sweeps the pre-existing keys).

## Steps

1. Add the confirm React page (AuthPageShell + Card: heading, explanation, the user code in a monospace code box, "Only authorize this if you started the request" hint, Authorize submit button + Cancel link) with en/zh locale entries.
2. Route it (new child route or component on `/auth/device`) with `user_code`/`device_challenge` validated as search params; add a `translatedTitleHead` document title.
3. Point `handleDeviceVerification`'s signed-in-confirm branch at the new page; delete `deviceConfirmationPage()` and `htmlEscape` if now unused.
4. Verify the POST path is untouched: same-origin check, session check, pairing only on POST.
5. `yarn typecheck && yarn lint && yarn test` — fix fallout in `hydra-device`/`hydra-consent` server-fn tests that assert the old HTML body.

## Resolution

Built as a layout + index route split, not a single route file — `getRouteApi("/auth/device")`-style single-file rendering breaks the sibling `/auth/device/success` route (Hydra's fixed `redirect_uri`, `deploy/gitops/*/values/hydra.values.yaml`), which depends on the parent's default `<Outlet/>`. Found live via a dev-server probe (curl + Playwright) after the first attempt silently served a blank 200 for both `/auth/device` and `/auth/device/success`. Final shape: `auth.device.tsx` is a header-only layout (no `component`, no `server.handlers`); `auth.device.index.tsx` owns `server.handlers` (GET/POST — the route tree's exact-path slot for `/auth/device` goes to whichever sibling's `fullPath` ends in `/`), `validateSearch`, `loader`, and `component: DeviceConfirmPage`. `device-confirm-page/index.tsx` mirrors `consent-page/index.tsx`'s AuthPageShell + Card + hidden-form pattern. `deviceConfirmationPage`/`htmlEscape` deleted from `hydra-device.ts`; `handleDeviceVerification` now returns `Response | DeviceView`. Verified live (dev server + Playwright screenshots in `.playwright-mcp/device-confirm-final.png`, `device-success-final.png`): confirm page renders in AuthPageShell chrome in both themes, `/auth/device/success` unaffected, GET-without-challenge still 302s to Hydra, POST still pairs/fails-closed correctly.
