# `agentsession`'s signed-POST replay tests flake under the full real-DB ship gate

Why: two `/loopx w8` workers' ship-gate runs on 2026-11-22 each failed once in `lego/backend/internal/agentsession/http_transport_test.go`, a package neither of them touched. A flaky gate costs every workstream a re-run, sometimes longer, and trains workers to push past red.

- **Seen.**
  - The w8/406 worker (~20:00 UTC): `TestSignedPostReportsAReplayBexAPIRefusesAsSeenUnavailable` (line 233) failed once in a non-DB run, then passed 20 of 20 runs alone.
  - The w8/410 worker (~23:20 UTC): `TestSignedPostReplaysADeadPooledConnectionOnANewOne` (line 135) failed once in the full ship gate. It then passed 30 runs alone and 8 package runs, and the gate's re-run was green.
  - Main's CI has been green throughout, so this shows up under the heavier, more parallel local gate.
- **Likely shape** (unconfirmed): both tests exercise a dead pooled connection and its replay. A timing or port-reuse race under load, such as a server closing before the client's pool sees it or an ephemeral port reused, would fit. Neither run kept the failure output.
- **Severity:** minor (test reliability). **Attribution:** test, `lego/backend/internal/agentsession`. Filed from w8 for the package's owners; w8 is not working in this package.

## Fix

Reproduce it under load, for example with `go test -race -count=200 -run 'TestSignedPost' ./internal/agentsession/` alongside a busy package, or under the ship gate's parallelism. Capture the failure, then make the tests deterministic. That might mean an explicit connection-close signal or a fixed listener lifetime instead of timing. Don't add a retry around a flaky assertion.

## Acceptance

- The two tests pass 500 of 500 runs under `-race` with the ship gate's parallelism.
- The failure mode found is named in this note, with the fix.

Estimate: ~45m.

## Outcome (2026-11-23)

Done. The failure mode is a race between the pooled connection's return and the next request's dial. The tests now wait for the transport's own signal that the connection is pooled. No retry was added.

- **Failure mode.** Both tests assume that once the first `Check` returns, its connection is already in the transport's idle pool. Go 1.27 breaks that. Its `json.Decoder` makes a first read of 64 bytes. The email verb's answer here is 65 bytes: a 64-byte JSON object and the encoder's trailing newline. So `postSignedMint` decodes the value and closes the body one byte before EOF. Go 1.27's transport then drains that byte on the connection's read loop. It pools the connection only after `Check` has returned. The second request finds an empty pool, so it waits for an idle connection and dials one at the same time. Under load the dial can win. The "pooled" request then runs on a new connection, so its reset is not replayed (`cause=reset (new connection); giving up`). That is `bex-api saw 2 requests` in the replay-refused test, and `want it answered by the retry` in the dead-pooled-connection test. Go 1.26's decoder reads 512 bytes, gets all 65 plus EOF, and the pool return is synchronous. So the race needs the 1.27 toolchain. `lego/go.work` pins 1.27.4, so `cd lego/backend && go test ./...` uses it. The ship gate and CI run `GOWORK=off` on go1.26.5, and there 6,400 + 28,800 stressed runs of the old and new tests never failed. A gate whose suite ran under the workspace toolchain would hit the race.
- **Captured.** I reproduced it at 16 concurrent `-race` test binaries with `GOMAXPROCS=2` under `taskpolicy -b`. Baseline: 2 of 9,600 runs of the six `TestSignedPost*` tests failed on go1.27.4, both in the two tests above; an earlier pass failed 6 of 16 binaries. The `httptrace` timeline of a failure shows request 1's `PutIdleConn` after `check 1 returned`, and request 2 with `GotConn reused=false`. In a separate pass on the same harness, request 1's connection was pooled after `Check` returned in 2,409 of 3,200 runs and before it in 791.
- **Fix** (`lego/backend/internal/agentsession/http_transport_test.go`, test-only). `poolReturn` returns a context with a `PutIdleConn` trace hook and a `waitPooled(n)` that blocks, with a 10 s bound, until the transport says the warm-up connections are back in the pool. The four tests that need a pooled connection wait on it before their next request: the two above, `…WhenEveryPooledOneIsDead` (two connections) and `…DoesNotReplayATimeout`. The timeout test had the same race behind its `cause=timeout (reused connection` assertion. It also now warms up on a 5 s client sharing the transport, where it used to warm up inside the 200 ms budget. And it waits for the timed-out request to reach the server before counting requests.
- **Verified.**
  - The same stress harness with the fix passes 28,800 of 28,800 on go1.27.4 and 28,800 of 28,800 on go1.26.5.
  - Run under that load, `go test -race -count=500 -run TestSignedPost ./internal/agentsession/` passes on both toolchains (`GOWORK=off` and workspace).
  - `make lint` is clean.
- **Residual.** net/http can still decline to pool a connection when a goroutine stalls more than 50 ms at one point (`wroteRequest`, and 1.27's post-close drain). It never happened in these runs. If it does, `waitPooled` now names it ("never went back to the transport's idle pool") instead of failing on a misleading assertion.
