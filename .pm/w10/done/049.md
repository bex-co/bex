# 049 — `ssh ags-…@ssh.bex.co` into a session whose sandbox closed is refused with a banner, while SSH into a sleeping Devin session wakes it

Why: since w10/043 a member who runs a session's copied `ssh` command after its sandbox closed is told how to start it again and has to come back, while Devin's SSH "into a session whose machine has gone to sleep now wakes the machine and completes the request instead of showing 'not running'". Found by w10/043's Devin check, 2026-11-23. Severity: minor (Devin parity; the dashboard's Connect menu already starts the sandbox, ADR054 D8, and the CLI's is w6/169). Likely more than an hour across several tasks: promote it.

## Reference

[Devin release notes](https://docs.devin.ai/release-notes/2026), 2026-09-25, read 2026-11-23: "Sleeping Sessions Wake on Preview or SSH Traffic. Opening a preview URL or SSHing into a session whose machine has gone to sleep now wakes the machine and completes the request instead of showing 'not running'."

## Where

- `lego/backend/internal/agentsessions/ssh.go` (`ResolveSSHSession`, `errNoSandboxToOpen`) refuses a `completed`/`failed` session with no sandbox with `AGENT_SESSION_NOT_ATTACHABLE`; `lego/backend/internal/sshgateway/nativessh/server.go` (`toldRefusal`) prints its message.
- The gateway cannot start anything itself: its database role reads `agent_sessions` only (ADR054 D7). Starting a sandbox is `Service.Resume` in bex-api (`can_operate` plus a fresh `can_create`, billing and live-sandbox admission). A wake needs a signed gateway-to-bex-api verb beside `TwoFactorClient` and `KeyGrantClient` that runs `Resume` as the key's owner.
- The start takes longer than the 10 s handshake deadline, so the login has to wait somewhere other than inside it. One shape: admit the login with the session's id as its sticky target, then hold the first channel open while it waits for `resuming` to settle (the start's own ceiling), writing progress to the channel's stderr, as the dashboard's Connect menu shows the start. The resolver keeps refusing canceled and archived sessions with their banner.

## End state

- `ssh ags-…@ssh.bex.co` into a closed, unarchived session that the caller may operate and resume starts its sandbox, says so while it starts, and opens the shell once it is up. A caller who may view but not resume the session (a contributor without `can_create`, or a workspace that admission refuses) keeps the w10/043 banner, with the refusal's reason when admission refused.
- ADR054 D7 and D8 record the new verb and what it lets a gateway credential do. A security review covers it as the earlier gateway verbs were.
- Gateway tests cover the wake, the refusals and the start that ends without a sandbox. The production check opens a closed session in `tian-personal` with plain `ssh` and deletes the session afterwards.

## Promoted (2026-11-23)

Promoted to [w10/m597](../m597/README.md) by `/loopx w10`. The premise holds at `9fdf7e0a11`: `SSHResolver.ResolveSSHSession` still refuses a closed session with `errNoSandboxToOpen` (`lego/backend/internal/agentsessions/ssh.go:76-78`), and the gateway's only bex-api verbs ask questions (two-factor, key grant). The wake needs a new signed verb running `Service.Resume`, a held login past the 10 s handshake, the closed session's SSH surfaces, three ADRs and a security review, tests and a production check: more than one sitting.
