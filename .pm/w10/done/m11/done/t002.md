## Objective

Stop discarding the real Go error when a blueprint sync fails — store it on the `blueprint_syncs` row so later work (t003, t004) can surface it.

## Context

- `lego/backend/internal/store/blueprints.go`: `BlueprintSync` struct (~line 48) has no message/detail field — `ID, BlueprintID, CommitID, State, StartedAt, CompletedAt, CreatedAt`. `UpdateBlueprintSync(ctx, id, state string, completedAt *time.Time)` (~line 229) only ever writes `state`+`completedAt`.
- `lego/backend/internal/apps/blueprint.go` has **two** call sites that run a sync and know the exact failure but throw it away:
  - `SyncBlueprint`/its manifest-apply path (~line 438-461): `_, applyErr := s.deployParsedStack(...)`, then `if applyErr != nil { finalStatus = ...; syncState = store.BlueprintSyncStateError }`, then `_, _ = s.Blueprints.UpdateBlueprintSync(ctx, run.ID, syncState, &completedAt)` — `applyErr.Error()` is available right there and is not passed through.
  - `runSync` (~line 591-676): same pattern, `stack, applyErr = s.deployParsedStack(...)` / `s.deployStack(...)`, same discarded-error `UpdateBlueprintSync` call.
- Repro: blueprint `blp-d9nqg95cavls73fp8m10` (discourse_docker)'s Sync History has an "Error" row with commit `—` and zero other detail — consistent with there being no error data captured anywhere to show, even in the database.
- Migrations live in `lego/backend/internal/store/migrations/`; the latest pair is `0094_git_connections_tenant_fk.{up,down}.sql` — next is `0095`.

## Steps

1. Add migration `0095_blueprint_sync_error_message.up.sql` / `.down.sql`: `ALTER TABLE blueprint_syncs ADD COLUMN error_message text;` (nullable, no default — most rows are `success`/`running`/`created` and have none).
2. Add `ErrorMessage *string \`json:"errorMessage,omitempty"\`` to the `BlueprintSync` struct in `blueprints.go`.
3. Change `UpdateBlueprintSync`'s signature to accept an optional error message (e.g. `UpdateBlueprintSync(ctx context.Context, id, state string, completedAt *time.Time, errorMessage *string)`) and update its SQL to write the new column.
4. Update both call sites in `blueprint.go` to pass `applyErr.Error()` (as a `*string`, nil on success) through to `UpdateBlueprintSync`. Keep the message reasonably bounded (truncate very long errors — check whether an existing truncation helper exists in the codebase before writing a new one) so a pathological error string can't bloat the row.
5. Update the `BlueprintSyncService` interface in `blueprint.go` (~line 52, `UpdateBlueprintSync(ctx context.Context, id, state string, completedAt *time.Time) (store.BlueprintSync, error)`) to match the new signature, and any mock/fake implementations used by existing tests.

- [ ] A sync that fails (`applyErr != nil`) writes a non-empty `error_message` to its `blueprint_syncs` row; a sync that succeeds writes `NULL`.
- [ ] Migration applies cleanly up and down.
- [ ] `cd lego/backend && go test ./...` green, including a new/updated test asserting the persisted error message on an induced sync failure.
- [ ] `make lint` (from `lego/operator/`) green.
