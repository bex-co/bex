# 014 — An agent session cannot push a branch created from an older commit: the GitHub App lacks the `workflows` permission

Why: any session that starts from a commit whose `.github/workflows/` differs from the default branch's (a pinned commit, an older branch, a slow run while main moves) cannot deliver at all, and an agent that legitimately has to change a workflow never can. Severity: major for those sessions. Surface: agent sandbox Git proxy / GitHub App permissions (ADR047 delivery).

## Evidence (production, 2026-11-17/18)

Four sessions pinned to `35a5a52ec` (`ags-dbu0pfdikg6s738lam7g`, `ags-dbu0pfmc1l2s739d3n3g`, `ags-dbu2nv0hdavc73bdbhp0`, `ags-dbu3k5pc204s73bi71l0`) all failed `git push origin HEAD:bex-agent/<session>` with:

```
! [remote rejected] ... (refusing to allow a GitHub App to create or update workflow `.github/workflows/backend-test.yml` without `workflows` permission)
```

One agent pushed the bare pinned commit, carrying none of its own changes, and got the same refusal. Main had changed `backend-test.yml` (+22) and `scripts.yml` (+4) after the pin, so creating the branch reads as a workflow update. `open_or_update_draft_pr` then returns `branch_not_pushed`.

## Direction

Grant the App `workflows: write` scoped to `bex-agent/*` branches, or have the proxy create the branch from the default branch's tip and push the session's commits on top (rejecting only a commit that itself edits a workflow, with a message that says so). Report the refusal to the agent in plain words instead of the raw remote error.

## Outcome (2026-11-18, `/loopx w10`)

Done. The second direction (create the branch from the default branch's tip and put the session's commits on top) cannot work without rewriting the session's commits, so the fix takes the first direction, which matches Devin. Devin's GitHub App holds Workflows read and write ([docs.devin.ai/integrations/gh](https://docs.devin.ai/integrations/gh)).

- **Reproduced on GitHub** with the production App `bex-co`: a token with `contents:write` + `metadata:read` (today's session token) pushing `35a5a52ec` to a new `bex-agent/w10-014-probe` got the exact refusal above. The same push with `workflows:write` added was accepted. The probe branch was deleted. The App already holds `workflows: write`, and all five installations had granted it, so no GitHub settings change is needed.
- **Fix:** `MintSessionInstallationToken` and the takeover `FastForwardBranch` now request `contents:write` + `workflows:write` (`lego/backend/internal/github/client.go` `mintRepositoryWriteToken`). An installation that has not granted Workflows answers 422, and the mint then retries with contents alone, so a self-hosted App made from the older manifest keeps working.
- **Plain words:** when GitHub still refuses a workflow change, the Git proxy adds `remote: bex: …` side-band lines before GitHub's refusal (`relayReceivePackReport` in `lego/backend/internal/sshgateway/agentcred/agentcred.go`). They say why the push failed, give `git fetch origin HEAD && git merge FETCH_HEAD` for a branch that started from an older commit, and say a real workflow edit needs the owner to approve the permission.
- **Tests:** `TestMintSessionInstallationTokenFallsBackWithoutWorkflows`, `TestFastForwardBranch`, `TestRelayReceivePackReport*`, and `TestGitPushPrintsTheWorkflowRefusalExplanation`, which runs a real `git push` through the proxy against GitHub's recorded refusal bytes. Each one fails with its fix reverted.
- **Docs:** ADR047 D2 (amendment w10/014), ADR026 (manifest + trust boundary), ADR078, ADR094.
- Production gets the fix with the next deploy that carries this commit. Sessions minted before then keep the contents-only token until their next mint (every Git request mints).
