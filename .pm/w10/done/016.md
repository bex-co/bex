# 016 — A turn is killed after 30 minutes without agent output even while a tool command is still running

Why: a long but healthy check (the beancount-io dashboard `yarn test` takes ~30 min) ends the turn as failed, and with [013](done/013.md) everything not yet pushed is lost. Severity: major in combination with 013. Surface: agent runtime (ACP turn watchdog).

## Evidence (production, 2026-11-18)

`ags-dbutgej906ns73ff3kb0` (`beancount-rt-flaky-test-fixer`): the agent reproduced the bug, verified a fix 20/20, started the full dashboard suite before committing, and the turn failed with `ACP turn made no progress for 1800000ms`. The fix was lost. Worked around by a prompt rule in the beancount-io automations ("commit and push before any long suite; run it in the background with progress"); the re-run `ags-dbuuuus9rejs73fsjhlg` delivered beancount-io#216.

## Direction

Count a running tool command's output (or a periodic heartbeat from a live child process) as progress, and raise or make configurable the idle limit for automation templates; before failing a turn on the watchdog, snapshot unpushed work (013).

## Closed 2026-11-18 (`/loopx w10`): done

- **Triage (main at `d89526196`).** The snapshot clause shipped with w10/m491 (`0d7e8fc8b`, a failed turn keeps its undelivered work). The rest held. The transcript of turn 1 in production (read-only) shows the mechanism. At 17:38:33 muse started the full `yarn test` with `yield_time_ms: 300000`. Its `bash_input` calls came back `execution_state: background_running`, and the tool calls ended with them ("the final output is delivered to you automatically … wakes you even after you end the turn"). After 17:44:50 there was no ACP update and the prompt stayed open, so the idle clock, which paused only for an open tool call (`turn-bound.ts`), ran out at 18:15 while the suite was still burning CPU in muse's process tree.
- **Fix.** The driver samples the CPU time of its own descendants every minute from `/proc` (`lego/agent-image/driver/src/activity.ts`; gVisor writes the same `stat` fields). A minute in which the agent's tree used at least 5% of one CPU holds the idle clock (`TurnBound.activity`), for at most `BEX_AGENT_TOOL_CALL_TIMEOUT` (2h) past the agent's last update, as an open tool call does. A command waiting on the network or a lock uses no CPU, so a hung turn still fails at 30 minutes. ADR047 records it ("Amended 2026-11-18 (w10/016)").
- **Not taken.** Counting the command's output: the driver cannot read the agent's pipes, and this run piped the suite into `tail -25`, so it had no output to count. Raising the idle limit, or making it configurable per automation: the case that reached it no longer does, and a longer limit would only delay the hang guard.
- **Proof.** `test/turn-bound.test.ts` "a turn waiting on a busy background command outlives the idle bound" runs a real driver turn on Linux whose fixture agent waits on a CPU-bound child with no update. It fails on the old code with `ACP turn made no progress for 500ms` and passes with the fix (checked in `node:22-bookworm`). Its sibling shows that an idle child still fails at the bound. There are unit tests for the `/proc` parsing, the tree walk and the 2h hold. Production takes the fix with the next deploy that carries the agent image.
