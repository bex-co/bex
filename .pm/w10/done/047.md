# 047 — A session's surfaces do not show that auto-merge is armed on its pull request, or who armed it, as Devin's merge bar does

Why: after a session arms auto-merge (`merge_pull_request` with `auto: true`, w10/m577), its REST, GraphQL, MCP and dashboard reads say only `prState: open` until GitHub merges it, so a person cannot tell from bex that the pull request will merge itself, while Devin Review's "merge bar shows the current auto-merge status, including who enabled it". Found by the w10/m577 Devin comparison (t006), 2026-11-22. Severity: minor (Devin parity). Surface: `lego/backend/internal/agentsessions` (session read, PR-state poller), the dashboard session view.

## Reference

[Devin Review](https://docs.devin.ai/work-with-devin/devin-review), read 2026-11-22: "Enable or disable GitHub auto-merge from the merge button dropdown." "The merge bar shows the current auto-merge status, including who enabled it."

## Current state (2026-11-22, w10/m577)

The merge verb answers the sandbox `{merged: false, autoMerge: true}` or `{mergeQueue: true}` and records nothing on the session (`lego/backend/internal/agentsession/pullrequest_merge.go`, `Merge`). The PR-state poller (`lego/backend/internal/agentsessions/pr_state.go`) reads only open, closed and merged. GitHub's PullRequest has `autoMergeRequest { enabledAt enabledBy { login } mergeMethod }` and `isInMergeQueue`.

## End state

A session whose pull request has auto-merge armed or is in a merge queue shows it on REST, GraphQL and MCP (for example `prAutoMerge: {enabledBy, enabledAt, method}` or `prMergeQueued: true`) and on the dashboard's session view beside the PR state, kept current by the merge verb's answer and the PR-state poller, and cleared on a disarm or a merge. Tests cover the arm, the disarm, a person arming it on GitHub, and the merge.

## Done (2026-11-23)

A session's REST, GraphQL and MCP reads carry `prAutoMerge {method, enabledBy, enabledAt}` (GitHub's `autoMergeRequest`, absent when none is armed) and `prMergeQueued` (`isInMergeQueue`) beside `prState`; the dashboard's session header shows an "Auto-merge" or "In merge queue" badge beside the state, whose tooltip names who armed it, the method and when. Migration 0340 stores them (`pr_auto_merge` jsonb, `pr_merge_queued`). The merge verb records them at once on every session of the workspace that recorded the pull request: a pull request already armed or queued from the state it read, and an arm, a queue or a disarm from GitHub's read back (or, when that read fails, from its answer). The PR-state poller reads them with each read of an open pull request (one GraphQL read by node id), so a person arming or disarming it on GitHub shows within five minutes in its first week. A merged or closed read or delivery, or another pull request on the session, clears them. Tests: `TestPullRequestMergeAutoArmsAutoMergeAtTheRecordedHead` (the arm, a person's arm, a failed read back), `TestPullRequestMergeJoinsTheMergeQueue`, `TestPullRequestMergeDisableAutoUndoesTheArm` (the disarm), `TestPRStatesReadAutoMergeOfAnOpenPullRequest` (a person arming it on GitHub, the queue, a disarm, a merged one not asked), `TestPGAgentSessionPRMergeMarks` (real Postgres: workspaces, repeats, merge and close clear them), `TestEverySurfaceServesThePullRequestAutoMerge` (REST, GraphQL, MCP), and the dashboard header and mapper tests. ADR094 D7, ADR090 D3 and ADR047 amended. The `pull_request` webhook still forwards only state actions (`auto_merge_enabled`, `enqueued` and the rest are left to the poller, since production records no `pull_request` delivery).
