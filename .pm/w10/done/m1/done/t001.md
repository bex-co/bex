## Objective

Pin the exact controller-runtime informer and RBAC interaction that prevents the
manager from starting, then choose a Secret-watch design that preserves KeyValue
owner-event behavior without widening Secret access beyond the apps namespace.

## Context

- `lego/operator/internal/controller/keyvalue_controller.go` registers
  `Owns(&corev1.Secret{})`, which currently requests a cluster-wide Secret informer.
- `lego/operator/internal/controller/rbac_test.go` deliberately asserts that the
  manager ClusterRole cannot read Secrets cluster-wide.
- Production repeatedly logged `secrets is forbidden`, timed out every controller
  cache, and exited before reconciling `beancount-cms-v2`.

## Steps

1. Reproduce the manager cache-sync failure with the production-equivalent
   ClusterRole plus namespace-scoped apps Role.
2. Trace which KeyValue-owned Secret events must enqueue reconciliation and how
   the manager's namespace/cache configuration affects the informer.
3. Select and document a controller-runtime watch construction scoped to the apps
   namespace that does not require cluster-wide Secret list/watch.
4. Confirm the design retains the existing least-privilege RBAC assertions.

## Acceptance criteria

- [ ] The failure is reproducible and tied to a specific informer/watch path.
- [ ] The chosen design names how Secret events remain namespace-scoped and why no ClusterRole expansion is required.
- [ ] App, Database, and KeyValue controller startup behavior is included in the risk analysis.

## Out of scope

- Granting the operator cluster-wide Secret read access.
- Changing tenant-facing KeyValue or service APIs.
