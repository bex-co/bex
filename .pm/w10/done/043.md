# 043 — SSH into an agent session whose turn ended answers a bare `Permission denied (publickey)`, as if the key were wrong

Why: a member who copied a session's `ssh ags-…@ssh.bex.co` command and runs it after the turn ended gets the same refusal as an unregistered key, with no hint that the session only needs a message to run again, so they debug their key instead. Found by w10/032's live check, 2026-11-22. Severity: minor (Devin parity). Surface: `lego/backend/internal/agentsessions/ssh.go` (`ResolveSSHSession`, `liveSandboxPhase`), `lego/backend/internal/sshgateway/nativessh/server.go` (the public-key callback, `loginRefusal`).

## Evidence (production, pin `eaaa61506165`, 2026-11-22)

Repo-less session `ags-dc1kvrjr121s73eu0gcg` in `tian-personal`: once its first turn ended (`phase: completed`), `ssh` with the account's registered key printed only `Permission denied (publickey)`, while the sandbox Pod was still Running. After a steer started a new turn (`phase: running`), the same command opened a shell at once. The resolver authorizes `can_view_sensitive` first, then refuses `AGENT_SESSION_NOT_ATTACHABLE` for a phase outside `liveSandboxPhase` (`ssh.go:64-79`). The gateway sends a banner only for the login-requirement refusals `loginRefusal` knows (two-factor, Google sign-in), so this one reaches the client as a plain key rejection. The dashboard hides the SSH command while `sshAddress` is absent, so the CLI and a copied command are where this shows.

## End state

- An authorized member's SSH login into a session with no live sandbox gets an auth banner that says the session is not running and how to start it again (send it a message, then connect), in the same way the two-factor refusal's banner does. Check how Devin presents a sleeping session's machine before writing the wording, and cite it here.
- Someone who cannot view the session, or names a session that does not exist, still gets the bare refusal: the banner is sent only after authorization passes, so it never reveals that a session exists.
- A gateway test covers both cases.

## Outcome (2026-11-23)

Triage: work. Since w6/m564 (`e0754f8c23`) a finished session's sandbox opens while it is up, so the reported repro (completed, Pod still Running) now connects; but once the sandbox closes 5 minutes after the turn (w6/m563), and while it starts, or for a canceled or archived session, the resolver still refused `AGENT_SESSION_NOT_ATTACHABLE` and the gateway sent only the login-requirement banners (`server.go` `loginRefusal`).

Devin: "Opening a preview URL or SSHing into a session whose machine has gone to sleep now wakes the machine and completes the request instead of showing 'not running'" ([release notes](https://docs.devin.ai/release-notes/2026), 2026-09-25, read 2026-11-23). So the banner says "not running" as Devin did before that, and the wake itself is filed as w10/049.

- `agentsessions/ssh.go` `errNoSandboxToOpen` says what is wrong and what brings the sandbox back, per phase: closed ("is not running, and its sandbox has closed. To start it again, send the session a message, or choose Connect > Start the sandbox on its page in the dashboard. Then connect again"), starting, canceled, archived. `core.CodeAgentSessionNotAttachable` names the code.
- `nativessh/server.go` `toldRefusal` sends it as `bex: <message>.` in the auth banner for an `ags-` login, counted as `authentications_total{result="rejected_no_sandbox"}`. The resolver refuses that way only after `can_view_sensitive` passed (cached and fresh). A key enrolled by an API key is told only when its grant covers sandbox execution.
- Tests: `nativessh/sessionrefusal_test.go` runs the gateway over the real `agentsessions.SSHResolver`. A member gets the banner for a closed session and connects once the sandbox is up. Another member's session, a session that does not exist and one whose row is gone all get the bare refusal (`rejected_target`). A key without sandbox execution is not told. `TestSSHRefusalSaysWhatBringsTheSandboxBack` covers each phase's wording. Reverting the gateway branch or the key-grant check fails them.
- ADR035 § Fail-closed behavior and ADR054 D8 Limits record it. No production check was asked for. The banner path is the one the two-factor refusal uses in production.
