# 032 — Maven and Gradle reach nothing on a `full`-tier session, because the JVM ignores `HTTPS_PROXY`

Why: since w10/024 every session has JDK 17, but a `full`-tier session's only route out is the gateway egress proxy, which bex announces only through `HTTPS_PROXY`/`HTTP_PROXY`, and Java reads neither, so `mvn` and `./gradlew` cannot download a dependency or the Gradle wrapper there, while Devin's base image builds Java projects out of the box. Found by w10/024's worker (its "Not done here"), 2026-11-19. Severity: minor (Devin parity). Surface: `lego/backend/internal/agentsessions/service.go` (`withNetworkEnv`), the driver's run env, `lego/agent-image/`.

## Current state (2026-11-19, `aef913d70`)

- A full-tier sandbox resolves only the gateway's name, and its traffic leaves through the egress proxy ([ADR047 § full tier amendment w10/m19](../../../docs/ADR047-cloud-coding-agent-sessions.md)). `withNetworkEnv` sets `HTTPS_PROXY`/`HTTP_PROXY` in both spellings and `NO_PROXY` (`service.go:2014`) to `http://<ns>:<session>@bex-ssh-gateway.bex-system.svc.cluster.local:8085`, the userinfo being the base64url session claim sent as `Proxy-Authorization: Basic` (`agentsession/egress.go:58`).
- The JVM takes a proxy only from system properties (`https.proxyHost`, `https.proxyPort`, `http.nonProxyHosts`). Maven reads `<proxies>` in `~/.m2/settings.xml`, and Gradle reads `systemProp.https.proxy*` from `gradle.properties`. The JDK also refuses Basic authentication on a CONNECT tunnel unless `jdk.http.auth.tunneling.disabledSchemes` is cleared, so the session claim must get through as well.
- On `registries` and `custom` the catalog's Maven and Gradle hosts (`repo.maven.apache.org`, `services.gradle.org`, `plugins.gradle.org`, `plugins-artifacts.gradle.org`; `sessionegress/policy.go`) are reached directly, so those tiers are not affected.

## End state

- On a `full`-tier session, `mvn -q dependency:resolve` on a small project with one Maven Central dependency and `./gradlew help` (the wrapper downloads Gradle from `services.gradle.org`) both succeed through the egress proxy with the session claim. A model-provider host is still refused through it, and the gateway and loopback (`NO_PROXY`) stay direct.
- Nothing changes on `registries` or `custom`, and a repository's own `MAVEN_OPTS`, `JAVA_TOOL_OPTIONS`, `settings.xml` or `gradle.properties` still applies (added to, never replaced).
- The overlay's network line and ADR047's full-tier amendment say how Java tools reach the proxy.

## Work record (2026-11-20)

- **Reproduced.** With only the existing env (`HTTPS_PROXY`/`NO_PROXY`) in front of the real egress `Broker` (fake Pod binding and grant) on an internal Docker network, `curl` through the proxy answered 200 while `mvn -q dependency:resolve` (`NoPluginFoundForPrefixException`) and `./gradlew help` (the wrapper's `HttpsURLConnection`) both failed.
- **Fix** (`35b3880c9`).
  - bex-api's `withNetworkEnv` also sets `BEX_AGENT_JAVA_PROXY_OPTIONS` on full-tier sandboxes (`lego/backend/internal/agentsessions/service.go`, `javaProxyOptions`): `http`/`https` `proxyHost`, `proxyPort`, the claim as `proxyUser`/`proxyPassword`, `http.nonProxyHosts` (the JDK's loopback default plus `NO_PROXY`'s gateway hosts) and an empty `jdk.http.auth.tunneling.disabledSchemes`. A `BEX_` name, so no workspace secret can replace it.
  - `bex-agent-tools.sh` puts them in front of `JAVA_TOOL_OPTIONS` in every shell, once, and the driver does the same for the agent's own process (`credentials.ts`, `javaProxyEnvironment`). A value already there (a `JAVA_TOOL_OPTIONS` secret) stays after them, so its own properties win.
  - `lego/agent-image/mavenrc` is `/etc/mavenrc`, which `bin/mvn` of Maven 3 and 4 and the older jar-based `mvnw` source. It writes global settings naming the proxy, plus the HTTP blocker of Maven's stock global settings they replace, to `$TMPDIR/bex-maven-<uid>/settings.xml` on each run and passes `-gs` (`-is` on Maven 4), unless the command or `MAVEN_ARGS` names its own. User settings (`~/.m2/settings.xml`, `-s` in `.mvn/maven.config`) merge over them.
  - The egress proxy reads the claim from a CONNECT's `Authorization` when `Proxy-Authorization` is absent (`egressproxy.go`, `proxyAuthorization`). Maven 3.9.9's Apache HttpClient 4.5 sent its cached proxy Basic scheme as `Authorization` on about 50 parallel CONNECTs and gave up on the 407s. A plain-HTTP request's `Authorization` is the origin's and is never read.
  - The overlay's network line, ADR047's full-tier amendment (2026-11-20) and `lego/agent-image/README.md` say how Java tools reach the proxy.
- **Tests.**
  - Go: `TestCreateEgressFollowsTheWorkspaceTier` (the exact properties on `full`, none on `registries`/`custom`), `TestJavaProxyOptionsFollowTheProxyURLAndNoProxy`, and `TestAConnectMayCarryTheClaimAsAuthorization` (admitted, a sibling session's claim refused with 403, plain HTTP still 407). That last test fails with the fallback removed.
  - Driver: the overlay test, and "the agent's JVMs get a full-tier session's proxy before their own options".
  - The Dockerfile's final check covers the composition in `sh -ic`, `sh -lc`, `bash -c`, `bash -lc`, `bash -ic` and nested shells, a value of its own kept after, none without the variable, the JVM taking the properties, and the settings `mavenrc` writes and skips. Run in the local `bex-agent-sandbox:w10-027` image with the new files, it passes, and it fails with the old hook or an empty `mavenrc`.
  - Backend packages, the driver suite (274 pass, 3 skipped) and `make lint` all pass.
- **Verified locally.** The same Docker setup, in the agent image, as uid 10001:
  - `mvn -q dependency:resolve` succeeded on Maven 3.9.9, on Maven 4.0.0-rc-7 (with no `-gs` deprecation warning), and through a 3.1.1 jar `mvnw` that downloads Maven 3.8.8 itself. So did `./gradlew help` (8.12, downloaded from `services.gradle.org` through GitHub's release assets) and a Gradle dependency resolution in the daemon.
  - `api.anthropic.com` and `api.openai.com` were refused with 403 through the proxy. The gateway and loopback stayed direct.

  - A JVM HTTP client that installs no `java.net.Authenticator` still gets 407. That is filed as w10/038.
