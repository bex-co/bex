## Objective

Decide and implement the audit semantics for an idempotent datastore `SetPlan` (requested plan == current plan). Today both datastore services fall through to the generic update effect, so the audit log labels the call `UpdatePostgres`/`UpdateKeyValue` — a verb the caller never invoked. Either record the plan-set intent with a truthful verb or record nothing (matching how other no-op writes behave); apply the same decision to postgres and keyvalue identically.

## Context

- `lego/backend/internal/postgres/service.go:569-573` — `if from != plan { RecordDatabaseEffect(..., DatabasePlanChanged) } else { RecordDatabaseEffect(..., DatabaseUpdated) }`.
- `lego/backend/internal/keyvalue/service.go:541-545` — same shape with `KeyValuePlanChanged`/`KeyValueUpdated`.
- Verb mapping lives in `lego/backend/internal/core/audit.go` (`databaseAuditVerbs`/`keyValueAuditVerbs`); the mislabel is cosmetic for webhooks (`Update*` verbs are not in `verbEvents`) but wrong on the audit read surface.
- Check how apps' no-op writes behave (e.g. suspend-on-suspended, `RecordPlanChanged` call sites) and match that precedent when deciding record-vs-skip.

## Steps

1. Survey the existing no-op-write audit precedents in `core/audit.go` and the apps service; write the one-line decision (record plan verb vs skip) into the code comment at both call sites.
2. Implement the decided branch in both `SetPlan` implementations; keep postgres and keyvalue byte-symmetric.
3. Run backend `go test ./...`.

## Files

- `lego/backend/internal/postgres/service.go`

## Acceptance criteria

- [ ] A same-plan `SetPlan` no longer produces an `UpdatePostgres`/`UpdateKeyValue` audit row.
- [ ] Postgres and keyvalue behave identically; the decision rationale is recorded at the call sites.
- [ ] A real plan change still records `plan_changed` exactly as before.
