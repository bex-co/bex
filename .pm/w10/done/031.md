# 031 — The mobile app's session composer cannot choose the sandbox template

Why: since w10/m519 a session's sandbox template (its CPU and memory) is chosen in the dashboard composer, the CLI and the API, and the capabilities read lists the templates with the workspace default, but the phone composer still starts every session on the workspace default, so a person on the phone cannot start a session on `agent-4c-8g` for a repository that runs out of memory on `agent`. Found by the w10/m519 Devin comparison (t007), where the machine is picked under Configuration → Virtual environment when a session starts ([Outposts](https://docs.devin.ai/cloud/outposts/overview), read 2026-11-19). Severity: minor (parity across bex's own surfaces). Surface: `mobile/src/features/agent-sessions/composer/session-composer-screen.tsx`, `mobile/src/features/agent-sessions/api/agent-sessions.graphql`.

## Current state (2026-11-19)

The mobile composer's capabilities query (`MobileAgentSessionCapabilities`) reads no `templates` or `defaultTemplate`, and its create sends no `agentConfig.template`, so the session runs on the workspace default. The capabilities read already returns `defaultTemplate` and `templates { name cpu memoryGb }` (w10/m519). Companion of w10/029 (the same composer's model control).

## End state

The phone composer shows the template the session will run on (the workspace default, with its CPU and memory) and lets the person pick another of the listed templates; the session starts on it (`agentConfig.template`). Nothing in the app names a template or a size: both come from the capabilities read.

## Done (2026-11-20)

The phone composer's capabilities query reads `defaultTemplate` and `templates { name cpu memoryGb }`, and a sandbox pill joins the repo, agent and model pills (`mobile/src/features/agent-sessions/composer/session-composer-screen.tsx`, logic in `compose.ts` `templateControl`/`templateLabel`, sharing `sentChoice` with the model pill). The pill shows the template the session will run on with its CPU and memory, numbers formatted in the app's language ("agent · 2 CPU, 4 GB"). With more than one template it opens a picker listing each template with its size and the workspace default marked, and the create names `agentConfig.template` only when another template is picked. A workspace with one template shows it with no chevron, a read with none shows no pill, and a pick the refreshed read no longer lists falls back to the default and is not sent. Every name and size comes from the read. The template persists across agent switches, as the dashboard composer's does. The scope-policy allowlist admits the five fields, and the three new strings are in all eight languages, worded as the dashboard words them.

Checked on production as the QA user in `tian-personal`, without starting a session: the mobile `MobileAgentSessionCapabilities` document returns `defaultTemplate: agent` and `templates` `agent` (2 CPU, 4 GB) and `agent-4c-8g` (4 CPU, 8 GB), so the picker shape applies. The mobile `MobileCreateAgentSession` document naming `agentConfig.template: agent-8c-16g` is refused with `AGENT_SESSION_INPUT_INVALID` on `agentConfig.template`, listing both templates, and no session was created. A session starting on a picked template through the same `createAgentSession` input was verified by w10/m519 (`ags-dc004fpbgjqs73fpsp00`). Not exercised on a device. Mobile `yarn test` (415 unit tests), `bundle:ios` and `bundle:android` pass.
