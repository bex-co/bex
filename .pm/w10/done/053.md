# 053 — Merging a stacked pull request now goes to GitHub's synchronous merge, which does not support stacks, where Devin's merge lands the pull request and every open one below it

Why: a takeover session, or one given a `number` (w10/041), asked to merge a person's stacked pull request now gets the synchronous merge. GitHub says that merge "does not support stacked pull requests", so the pull request does not land with its stack. Devin's merge button lands the whole stack. Filed by w10/048, 2026-11-23. Severity: minor (Devin parity; it reaches only stacked pull requests, and a session's own pull request is never stacked). Surface: `lego/backend/internal/github/merge.go` (`MergePullRequest`), `lego/backend/internal/agentsession/pullrequest_merge.go` (`PullRequester.Merge`), ADR090 D3.

## Reference

- [Devin Review](https://docs.devin.ai/work-with-devin/devin-review), read 2026-11-23: "Stacked PRs merge through GitHub's atomic stack merge: merging a PR also merges every open PR below it in the stack", and "The merge button shows exactly how many PRs the action will land".
- [Pulls](https://docs.github.com/en/rest/pulls/pulls), read 2026-11-23:
  - `PUT …/pulls/{n}/merge` "does not support stacked pull requests or merging with a merge queue".
  - `PUT …/pulls/{n}/merge-async` "is the required API for merging stacked pull requests", and "For a stacked pull request, the operation includes all open downstack pull requests". It takes `merge_action` (`default`, `direct_merge`, `merge_queue`), `merge_method` (direct merges only) and `sha`. It answers 202 with a UUID to poll (`GET …/merge-async/{uuid}`: `pending`, `merged`, `enqueued`, `failed`), or 200 when the pull request is already merged or queued.
- [Stacked pull requests APIs](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests-apis-and-webhooks), read 2026-11-23: "A stack cannot be merged with the legacy synchronous merge endpoints or mutations". A stack merge is atomic.

## What w10/048 left

`PullRequestMergeState` reports `Stacked` and `StackBase`. With `auto`, a stacked pull request arms its stack (`includeStack`). These still reach `MergePullRequest`, the synchronous merge:

- a plain merge of a stacked pull request;
- an arm GitHub refuses with "is in clean status" because the whole stack is ready now.

On a stack whose base requires a merge queue, the arm's method is ignored by the queue, and a plain call does not queue the stack.

## End state

A merge now of a stacked pull request lands it with every open pull request below it through `merge-async`, pinned to the head as today (`sha`), with the method rule of the stack's base. The same holds for the `auto` fallback when the stack is ready now. A stack whose base requires a merge queue is queued (`merge_action: default`). The verb polls the result within the request, under a stated bound, and maps `failed` to GitHub's words under today's codes. ADR090 D3 decides what an answer still `pending` at the bound says. The answer says how many pull requests landed, as Devin's button does. Tests cover the request body, each poll result, and a pull request in no stack left on today's synchronous merge.

## Outcome — done 2026-11-23

- **Shipped:** a pull request the merge-state read finds in a GitHub stack, merged without `auto` or after GitHub refuses an `auto` arm because the stack is ready now ("is in clean status"), goes to `PUT …/pulls/{n}/merge-async` (`github.Client.MergePullRequestAsync`, `agentsession.PullRequester.mergeStack`). The body is `sha` (the pin), `merge_method` (the stack base's method rule), the commit text and `merge_action: default`, so GitHub merges directly or queues the stack where its base requires a merge queue. No `bypass_rules`.
- **The wait:** a `202` is polled at `GET …/merge-async/{uuid}` once a second for at most 15 s (`github.AsyncMergeWait`), inside the 30 s write timeout of bex-api's `:8091` listener. A failed read is tried again until the bound. A `409` (a merge already pending) is waited for at the pinned head and is `head_changed` at another.
- **The answers:** `merged` → `{merged: true, sha, method, stack: true, pullRequestCount}`, recording `prState: merged`. `enqueued` → `{mergeQueue: true, stack: true, pullRequestCount}`, recording `prMergeQueued`. `failed` (a `400`, or a later result) → GitHub's words under `merge_blocked`, `head_changed` ("Head branch was modified") or `merge_method_not_allowed`. Still `pending` at the bound → `{merged: false, mergePending: true, method, stack: true}`, with nothing recorded. The driver's `next` says it has not merged yet, not to use `gh pr merge`, and to call the tool again with the same arguments to read the result (ADR090 D3, w10/053 amendment).
- **How many:** the state read adds `stackEntry { position }` and `stack { entries(first: 100) { nodes { position pullRequest { state } } } }`. `pullRequestCount` is the pull request plus every `OPEN` one below it. It is omitted when a position below is unread. It also rides a fresh stack arm (w10/048).
- **Unchanged:** a pull request in no stack, a plain merge whose state read fails, an `auto` arm, a pull request already queued, and `disableAuto` (`TestPullRequestMergeLandsAStackedPullRequestWithItsStack`'s last case).
- **Tests:** `github.TestMergePullRequestAsyncLandsTheStackAndWaitsForItsResult` and `TestMergePullRequestAsyncRefusals` (request body, the 200/202/400/409/403/404/422 answers, each poll result, a failed read, the bound, a cancelled request), `TestPullRequestMergeStateReadsWhatGhReads` (the count), `agentsession.TestPullRequestMergeLandsAStackedPullRequestWithItsStack` and the updated `TestPullRequestMergeAutoArmsTheStackOfAStackedPullRequest`, plus `TestPullRequestMergeResponseWellFormed`. The driver tests are `merge_pull_request relays a stack merged now, or still landing, with how many pull requests it lands` and the stack queue in `…relays a stack's auto-merge, its queue and its undo`. With the routing reverted, both agentsession stack tests fail.
- **Not walked live:** no QA-owned repository holds a GitHub stack, so the call is tested against the REST description's `merge-async` contract (its request examples, four result shapes and 200/202/400/409 examples, read 2026-11-23). The extended state query ran read-only against GitHub's live schema on `github/gh-stack#576` (position 3 of a stack on `main`, entries with `MERGED` states).
