## Objective

Review the new verb and the held login as the key-grant and two-factor verbs were reviewed ([ADR118](../../../../../docs/ADR118-security-review-scoped-api-keys.md) and the chain listed in `docs/AGENTS.md`), and fix what it finds.

## Context

- The new power: before this, `BEX_SANDBOX_EXEC_SECRET` let a gateway only ask bex-api questions. Now it can make bex-api start a sandbox, billed to a workspace, as any subject the request names. Weigh that against what the gateway already holds (`pods/exec` in every `<ws>-sandbox` namespace, ADR054 D7) and against what binding the request to a registered key fingerprint buys.
- Pre-auth reach: the wake must run only after signature verification, the key re-read and the login requirements, never from `PublicKeyCallback`'s key query.
- Resource use: a held login keeps a connection and a limiter slot for up to the start's ceiling; repeated logins must not start more than one sandbox or bypass the live-sandbox cap.
- Rolling deploy and replay: nonce, timestamp skew, an old bex-api.
