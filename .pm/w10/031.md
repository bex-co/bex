# 031 — The mobile app's session composer cannot choose the sandbox template

Why: since w10/m519 a session's sandbox template (its CPU and memory) is chosen in the dashboard composer, the CLI and the API, and the capabilities read lists the templates with the workspace default, but the phone composer still starts every session on the workspace default, so a person on the phone cannot start a session on `agent-4c-8g` for a repository that runs out of memory on `agent`. Found by the w10/m519 Devin comparison (t007), where the machine is picked under Configuration → Virtual environment when a session starts ([Outposts](https://docs.devin.ai/cloud/outposts/overview), read 2026-11-19). Severity: minor (parity across bex's own surfaces). Surface: `mobile/src/features/agent-sessions/composer/session-composer-screen.tsx`, `mobile/src/features/agent-sessions/api/agent-sessions.graphql`.

## Current state (2026-11-19)

The mobile composer's capabilities query (`MobileAgentSessionCapabilities`) reads no `templates` or `defaultTemplate`, and its create sends no `agentConfig.template`, so the session runs on the workspace default. The capabilities read already returns `defaultTemplate` and `templates { name cpu memoryGb }` (w10/m519). Companion of w10/029 (the same composer's model control).

## End state

The phone composer shows the template the session will run on (the workspace default, with its CPU and memory) and lets the person pick another of the listed templates; the session starts on it (`agentConfig.template`). Nothing in the app names a template or a size: both come from the capabilities read.
