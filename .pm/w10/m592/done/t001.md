## Objective

Settle the contract the other tasks build on, choosing the option that matches Devin's two modes. "Allow all models" and "Allowlist specific models" are a setting of their own in [Devin CLI Team Settings](https://docs.devin.ai/cli/enterprise/team-settings), and its allowlist is stored UIDs and tags ([List Models](https://docs.devin.ai/desktop/accounts/api-reference/list-models): "A model is allowed when its UID is listed or it carries a listed tag"). Record the contract in the milestone README's design record, and amend ADR047 D7 ("No explicit mode"), ADR090 § Model pin ("A workspace narrows the catalog") and the ADR018 agent-model row.

## Context

- Today the mode follows the list. `modelOfferPatch` (`lego/backend/internal/agentsessions/environment.go:636`) stores `known_models` NULL when an `enabledModels` write leaves no model off. `leftOn` (`:971`) reads `known_models` NULL or `disabled_models` empty as "allow all".
- `providerFilter` (`:1034`) puts a filter by provider in force only while `disabled_models` is exactly what its write derived. A filter listing every provider stays a filter.
- Production (pin `ac882b5f557f`, 2026-11-23): 3 rows, none narrowed, 0 with `known_models` set, 0 filtered by provider. Every Pod runs m568 and m573, whose all-on write stores `known_models` NULL.
- The REST PATCH decodes strictly (`rest.go:113`): an unknown field is a 400.

## Steps

1. **Name and shape.** Proposal: `allowAllModels: Boolean!` on the read and `allowAllModels: Boolean` on the write (REST, GraphQL, MCP). Say what the read is off the platform route and on the workspace's own key, where there is no catalog to narrow: `enabledProviders` is null there.
2. **Storage.** Proposal: no migration. "Allow all" is `known_models` NULL with no filter by provider. An allowlist is `known_models` set, which may now have `disabled_models` `{}`, once `leftOn`'s pre-m568 clause (`len(env.DisabledModels) == 0`) is retired. Check that against the m568 rollout read rule and `ConvertLegacyModelLists`, and weigh it against a new column.
3. **The writes.**
   - `allowAllModels: true` returns to "allow all" from a list or a filter. Decide whether naming `enabledModels` or `enabledProviders` with it is refused, and with which code and `field`.
   - `allowAllModels: false` alone keeps the models on now as the allowlist; under a filter by provider, decide whether it keeps the filter.
   - With `enabledModels` it stores that allowlist even when it lists every catalog model.
   - **A write naming only `enabledModels`.** Choose between m568's rule (every model on returns to "allow all") and keeping the mode in force (Devin edits the list without changing the mode). Weigh API and MCP clients written against m568's descriptions. Do the same for `enabledProviders` alone.
   - Both modes are refused off the route and on the workspace's own key, as `enabledModels` is.
4. **The CLI.** `--models all` turns the mode on. Decide whether `--models ID,…` sends the mode off (an explicit allowlist, as Devin's mode reads) or keeps m568's rule, and what an older bex-api's strict 400 on the new field looks like to that user.
5. **The dashboard.** Proposal: a third filter option, "All models", beside "By model" and "By provider". Say what "By model" starts with when chosen from "All models" (every model on, as an allowlist), and what the model rows show under "All models".
6. **The rollout.** A previous-release Pod reads a row the new code writes, and the new code reads a row that Pod writes. Show both agree while the catalog is unchanged, and that the deploy must add no catalog model.
7. Write the design record and amend the three ADRs.
