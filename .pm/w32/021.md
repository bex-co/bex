# A sandbox command's non-ASCII output is corrupted: a UTF-8 character split across two output chunks arrives as U+FFFD

Why: Render says to "write each chunk as received to preserve the original output". On bex, any command printing more than ~64 KB of Chinese, Japanese, emoji or accented text through `bex sandboxes exec` (or the SDK, or MCP `sandbox_exec`) loses characters at chunk boundaries. Nothing reports it: the exit code is 0 and the text just differs.

- **Seen:** `/qa-find-bugs-cli` loop sweep 97a6, 2026-11-13 ~04:00–04:10 UTC, `bex-canary` (`tea-daif693dqjvc73e7as3g`), release `bex` v0.5.0 (Render CLI v2.35.0 pin), human device login, `https://api.bex.co/v1/`, production pin `8acf1d116941`, sandbox `sbx-dbr8m2ishdos73f2f6j0` (since terminated).
  - The file was written in the sandbox with `bash -c "yes 中文日志输出 | head -n N > ~/zhN.txt"`, then read with `bex sandboxes exec <sbx> -- cat zhN.txt > local`. The expected size and sha256 come from `wc -c` and `sha256sum` run inside the sandbox.

    ```text
    N=2000   expected 38000 B  b770367157b85b5c   got 38000 B  b770367157b85b5c  U+FFFD 0
    N=5000   expected 95000 B  0b71d2cbfa676593   got 95006 B  96bf1fa740a61d79  U+FFFD 3
    N=20000  expected 380000 B 888a698db4e5d9c2   got 380036 B 15299ab9108aee14  U+FFFD 18
    exec -- bash -c 'yes 日本語テキスト | head -n 200000'    4.4 MB: 4410488 B received, 1748 lines with U+FFFD
    exec -- bash -c "yes 'é🙂x' | head -n 300000"           2.4 MB: 2405120 B received, 731 lines with U+FFFD
    ```

  - Each damaged boundary turns one 3-byte character into three U+FFFD (+6 bytes). A pipe writing many small chunks (`yes | head`) is damaged throughout. A single `cat` write is damaged about every 64 KB.
  - Controls: the same 9.5 KB and 38 KB texts arrived intact on stdout and on stderr. `bex sandboxes copy <sbx>:zh.txt ./` (tar) is byte-identical. NUL bytes pass through.
- **Contract:** render.com/docs/sandboxes-executing (fetched 2026-11-13): "Output arrives in chunks that can contain part of a line or multiple lines. Write each chunk as received to preserve the original output." The pinned CLI does exactly that: `pkg/sandbox/sse.go` decodes each `output` event's `data` (a JSON string) and `cmd/sandboxexec.go:65-68` prints it unchanged.
- **Cause (traced at `f4e7accbc`; line numbers rechecked at `3eb906ebd`):**
  - The gateway hands each stdout/stderr write it gets from `pods/exec` to `sseStream.Write` (`lego/backend/internal/sshgateway/sandboxsse/sandboxsse.go:371-374`).
  - That function emits `outputEvent{Data: string(p)}`, and `emit` (`:321-334`) calls `json.Marshal`. `encoding/json` replaces invalid UTF-8 with U+FFFD, and the first and second halves of a character split at the write boundary are each invalid on their own.
  - bex-api passes the SSE through unchanged (`sandbox/exec.go:350`), so every consumer sees the replaced bytes.
- **Fix:**
  1. Give `sseStream` a carry buffer. Emit only up to the last complete UTF-8 sequence of each write, and hold back a trailing incomplete sequence (at most 3 bytes, only when its lead byte announces more bytes; `utf8.FullRune`). Prepend the held bytes to the next write.
  2. When `Execute` returns, flush each stream's remainder before the `exit` event, so no output is lost. A remainder that is still incomplete then is invalid in the original output, and is replaced as today.
  3. Keep stdout and stderr carries separate. Bytes that are invalid in the original output still become U+FFFD: a JSON string cannot carry them on Render's wire either.
- **Blast radius:** one writer serves every exec surface.
  - REST stream exec and the connect-token run path (CLI, Render SDK).
  - MCP `sandbox_exec` (`ExecBuffered` → `bufferExec`, `sandbox/exec.go:448-477`), which concatenates the already-replaced `data` strings. GraphQL has no exec.
  - Agent-session reads through `sessionExec` (`sandbox/service.go:1311-1317`): `ReadSessionStatus` and **`ReadSessionTranscript`**, which harvests up to 16 MiB of `session.jsonl`. Non-ASCII model output in a stored transcript is presumably damaged the same way. That is traced, not exercised, and the JSON lines still parse, so nothing fails.
  - The web shell sends binary frames (`webshell/websocket.go:402`) and service log tails send whole lines, so neither is affected.
- **Acceptance:** in `bex-canary`, write `yes 中文日志输出 | head -n 20000 > ~/zh.txt`, then `bex sandboxes exec <sbx> -- cat zh.txt > out`. `out` matches the in-sandbox `sha256sum ~/zh.txt` (380000 B, no U+FFFD), and so does `bex sandboxes exec <sbx> -- bash -c 'yes 日本語テキスト | head -n 200000'`. A gateway unit test splits every multi-byte character at every offset across two writes and asserts the concatenated `data` equals the input, with stdout and stderr interleaved.
- **Unverified:** Render's own chunking (whether its server splits only at character boundaries). Its docs promise the chunks "preserve the original output", which a split character in a JSON string cannot.
- **Dedupe:** no board item covers it (`rg 'U\+FFFD|replacement char|utf-?8'` over `.pm` matches only unrelated input-validation and static-asset items). The writer dates from the original exec gateway (`c789aae44`, w3/m33) and is unchanged since.
- Major (silent output corruption). ~1h.
