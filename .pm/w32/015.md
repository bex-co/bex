# `bex sandboxes list` returns the oldest sandbox first; bex's own parity contract says newest first

Why: ADR104 D2 records Render's sandbox list as newest first. On production bex lists oldest first, so `list --limit` and the first page show the stale end of a workspace's history.

- **Seen:** `/qa-find-bugs-cli` loop sweep 865a, 2026-11-12, `bex-canary`, release `bex` v0.5.0. `bex sandboxes list --all -o json` returned 24 sandboxes in ascending `createdAt`: `sbx-dbpugr7bq3ic73c0acm0` (2026-11-11T04:00:44Z) first, and the sweep's own `sbx-dbqmm42ibtfs738vknn0` (2026-11-12T07:30:24Z) last.
- **Contract:** ADR104 D2's exec row: "list is newest first, excludes `terminated` unless filtered in, and caps `limit` at 100". The pinned OpenAPI `list-sandboxes` description does not state an order. Execution history (w32/m298) is already newest first.
- **Cause (traced at `02c656c19`):** `lego/backend/internal/sandbox/service.go:1294` `Service.List` returns OpenSandbox's order unchanged. No sort exists in `service.go`, `rest.go`, `graphql.go` or `mcp.go`, so REST, GraphQL and MCP all inherit ascending creation order. Paging (`cursor`/`limit`, w22/001) slices that order.
- **Fix:**
  1. Re-confirm Render's order on render.com/docs/sandboxes-cli-reference and the SDK `list` docstring.
  2. If it is newest first, sort by `createdAt` descending with `id` as tiebreak in `Service.List`, before filtering and paging, so cursors stay stable.
  3. Test that a page of 2 over 3 sandboxes returns the two newest, and the cursor continues to the oldest.
- **Acceptance:** `bex sandboxes list --all -o json` in `bex-canary` lists the most recent `createdAt` first. REST, GraphQL and MCP agree.
- **Unverified:** Render's order is taken from ADR104 D2 (sources fetched 2026-11-08), not from the pinned OpenAPI.
- ~45m.
