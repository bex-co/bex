# A rolling `settings_change` that has to rebuild a private GitHub repo clones with the last trigger's expired token, so its build fails at checkout

Why: bex-api mints a fresh GitHub installation token (it lives 1h) at every deploy trigger (ADR026 § Accepted limitation), but a `settings_change` rollout never re-mints it. When the release has no built image to reuse (its newest commit's build failed), the operator rebuilds with a token that expired hours or days ago, and the service gets a `build_failed` deploy that has nothing to do with its code. On Render, a settings change that redeploys builds like any other deploy.

- **Seen:** w32/044's production run, 2026-11-19, pin `1c63b6fe0a34`. `/api migrate-container-policy --all --apply` rolled a legacy `builder: auto` service on a private GitHub repo that serves its prior release (its newest commit's push build failed on 2026-11-16). The migration's `settings_change` deploy was created at 19:57:40Z, its build ran 19:57:41–45Z, and it ended `build_failed` with `build failed in the source checkout step: remote: Invalid username or token. Password authentication is not supported for Git operations.` The service's `<app>-clone` Secret was last written at 2026-11-16T00:00:39Z, by that push deploy (`managedFields`, `api`), three days earlier. The service still serves its prior release, on its old policy.
- **Not seen when an image exists:** w32/040's two legacy `builder: auto` services on private repos rolled by the same migration on 2026-11-19 08:35Z went `live` in 40–100 s with no new build run. Their commit's image was reused, so no checkout ran. The defect needs a release whose commit has no built image.
- **Where:**
  - Every deploy trigger re-mints first: `deploys.Service` (`lego/backend/internal/deploys/service.go:929-941`, "Refresh the private-repo clone credential BEFORE the generation bump"), the push redeploy (`lego/backend/internal/apps/service.go:4357`), Blueprint sync (`lego/backend/internal/apps/deploy.go:4267`).
  - `MigrateContainerPolicy`'s rolling write (`lego/backend/internal/apps/container_policy_migration.go:95-108`, `rollouts().PatchLocked` with `TriggerSettingsChange`) does not.
  - Likely the same: `patchFetched` (`lego/backend/internal/apps/service.go:6111-6125`), the shared rolling `settings_change` write behind a dashboard Settings save that changes the release (build or start command, root directory, plan, …). `rollout.Tracker` (`lego/backend/internal/rollout/rollout.go`) mints nothing either. Confirm with a dashboard save on a service whose last build failed.
- **End state:** every write that opens a `settings_change` deploy on a repo-backed service re-mints the clone token before the generation bump, as a deploy trigger does; a mint failure fails the write loudly, as the trigger does. A backend test opens a `settings_change` on a private-repo service through the migration and through a Settings save and finds a token minted at the write. On production, a migration or Settings save of a private-repo service whose last build failed builds past checkout.
- **Estimate:** ~1h.

## Shipped (2026-11-19) — parked for the production walk

- **Triage:** the premise held. The only clone-token mints were the deploy triggers (`deploys/service.go:929-941`), the push redeploy, Blueprint sync, create, checks-pass and the control-plane reconciler. `rollout.Tracker.Patch` and `PatchLocked` minted nothing, and every rolling write outside the deploy verbs goes through them: `patchFetched` (`settings_change`), `MigrateContainerPolicy` (`settings_change`), the environment and env-group writes and service-reference propagation (`config_change`).
- **Code:** `a4a82cf6e`. `rollout.Tracker` gets a `CloneSecrets` mint (`CloneCredential`). When a write rolls a release that may build, `refresh` mints before the patch that bumps the generation and names the Secret in that patch. A release may build when the App is repo-backed and its release does not rerun the served build (`SelectReleaseImage` for this generation). A mint failure fails the write before anything is patched or recorded. A locked write mints once across its retries, and again only if the retry found another repo. A save-only write (REST `PATCH`, MCP `update_service`), a write held on a suspended service, an environment "Save and deploy" that reruns the served build, an operational write and an image-backed service mint nothing. `apps.Service.rollouts()` and the Tracker that secrets and env groups share (`api/server.go`) both use the deploy triggers' bridge (`ReconcilerCloneSecreter`, which gained `EnsureAppCloneSecret`). The fix also covers `config_change` releases with no live build to rerun, because they share the seam and build the same way.
- **Tests:** `rollout`:
  - `TestARollingWriteMintsTheCloneCredentialBeforeItsPatch` (Patch and PatchLocked: one mint, before any patch, and the Secret is named in the rolling patch);
  - `TestAWriteThatBuildsNothingMintsNoCloneCredential` (operational, save only, suspended, image-backed, rerun of the served build);
  - `TestACloneCredentialMintFailureFailsTheWrite`;
  - `TestALockedWriteMintsOnceAcrossARetry`.

  `apps`: `TestARollingSettingsChangeRefreshesTheCloneSecret` (the migration of a private-repo native service, and a `SetCommands` save, each mint a fresh token at the write, beside one `settings_change` row) and `TestAContainerPolicyMigrationFailsWhenTheCloneTokenCannotBeMinted` (the policy row is restored and no deploy is opened). `api`: `TestEnvironmentWritesMintTheDeployTriggersCloneCredential`. Each of six mutations failed its tests: no refresh, a mint on a rerun, Patch minting after its patch, a mint on every retry, the apps Tracker unwired, the server wiring removed. golangci-lint passes on `rollout`, `apps` and `api`, and the ship gate's real-DB backend suite passed.
- **Docs:** ADR026 § bex-api and its accepted limitation say every write that rolls a release which may build mints, as a trigger does.
