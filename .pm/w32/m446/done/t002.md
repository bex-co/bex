## Objective

Prove, and keep, that `ensureGranted` serves an existing admin when its `Check` errors. Two fixes on main since this task was filed do most of the work: a `Check` that fails on a reused connection is replayed, and a write of a tuple that already exists is a no-op. What remains is the test that pins the path, and a decision on whether an extra `Check` retry is still worth it.

## Context

- `lego/backend/internal/api/tenancy.go` `ensureGranted`: `if allowed, err := checker.Check(...); err == nil && allowed { return false, nil }` falls through to `GrantWorkspaceAdmin` for an error as well as for `false`.
- **w21/099 (`ef7e65cd3`, 2026-11-16):** `authz.writeTuple` now sends `on_duplicate: "ignore"` (and deletes `on_missing: "ignore"`), so the grant write of an admin tuple that already exists succeeds. `ensureGranted` then returns `granted = true`, and `personalTenant` re-reads `TenantForOwner` and serves the tenant. The old failure, a refused duplicate write answered as `503 tenant onboarding unavailable`, is gone once this is deployed. Its tests (`openfga_idempotent_e2e_test.go`) cover the writer, not this `Check`-error path.
- **w4/695 (`a77d36c92`, 2026-11-16):** `checkUpstream` sends through `core.DoJSONRead`, so net/http replays a `Check` that fails on a reused connection. `IdleConnTimeout` is now 30 s.
- Neither commit is in production pin `938c5cb36b49` (2026-11-16 23:07 UTC). Check with `git merge-base --is-ancestor <sha> <deployed sha>` before any live step.
- After both fixes, a `503` still comes back when OpenFGA cannot answer either the `Check` or the write. That is the intended fail-closed path.

## Steps

1. Add a test with a checker whose `Check` errors and a granter whose write of an existing tuple succeeds. The request must be served, with no `503` and no revoke.
2. Keep the w5/m372 re-read and revoke ordering in `personalTenant` intact. With `granted = true` after a no-op write, the re-read still runs, and a binding that ended must still be revoked.
3. Decide whether `ensureGranted` needs its own `Check` retry on top of the transport replay. Record the answer from t001's production logs: add one only if they show `Check` errors other than reused-connection resets.

## Result (2026-11-17, `/loopx w32`)

- **Step 1:** `TestEnsureTenantServesAnAdminWhoseCheckErrors` (fake granter) and `TestOnboardingServesAnAdminWhoseCheckErrorsE2E` (real Postgres and OpenFGA). In both, a Check that errors is followed by the grant, the person is served and nothing is revoked. With `ef7e65cd3`'s `on_duplicate` removed, the e2e test fails with the production answer: `workspace admin grant failed (authorization service): POST …/write returned 400`.
- **Step 2:** the w5/m372 tests pass unchanged (`TestEnsureTenantTakesBackAGrantThatOutlivedTheBinding`, `members_owner_pg_test.go`, `members_leave_e2e_test.go`). A no-op grant still reports `granted`, so the re-read and revoke still run.
- **Both fail:** `TestEnsureTenantCheckAndGrantBothFailingFailsClosed`. A person with no recently resolved workspace gets `503 tenant onboarding unavailable: workspace admin grant failed (authorization service)`.
- **Step 3 decision: no Check retry of its own.** Production shows no Check error other than a reset reused connection. No onboarding 503 happened in the 11.7 h after pin `ef7e65cd3f46` (t001), and w4/695's closure counted 0 Check resets in 10.5 h after its fix. The transport resends a reset Check, and with the Check answered no write is sent (`TestOnboardingSendsNoWriteWhenAResetCheckIsResent`: 3 checks, 0 writes; without the resend, 1 write). Any other Check error is followed by the grant, a no-op for an existing tuple. A Check error is now logged (`tenancy: admin check of … failed, so the grant is written again`), so a future class shows up in the logs.
