## Objective

Make the onboarding failure observable, and use it to name which call in `EnsureTenant` fails on production while a workspace is creating or deploying services.

## Context

- `lego/backend/internal/api/auth.go:395-404` answers `503 tenant onboarding unavailable` for any uncoded `EnsureTenant` error and drops the error.
- Candidates, all in `internal/api/tenancy.go`:
  - the per-request tombstone read (`AccountDeletionTombstoned`, `internal/store/accounts.go:69`);
  - `TenantForOwner` (`internal/store/workspaces.go:89`);
  - `ensureGranted` (`:383-397`): `Check`, then a write of an admin tuple that already exists.
- Reproduction from sweep 134: create a free image web service in a QA workspace and poll `GET /v1/services/{id}/deploys` once a second through its first deploy and one image deploy. That gave 4 failures in about 190 calls, and 0 in about 320 calls with nothing in flight.

## Steps

1. Log the wrapped error with the request id and the identity's method at `auth.go`'s onboarding branch, without the token or email.
2. Wrap each `EnsureTenant` step's error with which step failed (tombstone, owner read, check, grant write, re-read).
3. After the change is deployed, run the reproduction on production and read the bex-api log lines for the 503s. Record which step failed and with what error class (Postgres, OpenFGA status and body, deadline), and whether the OpenFGA log shows refused duplicate writes at those times.

## Files

- `lego/backend/internal/api/auth.go`
- `lego/backend/internal/api/tenancy.go`

## Acceptance criteria

- [ ] A forced store or OpenFGA error in `EnsureTenant` produces one bex-api log line naming the step and the cause, and no secret.
- [ ] The production reproduction's 503s are attributed to a named step and error class, recorded in this task.

## Out of scope

- Changing what the caller is answered; that is t002 and t003.
