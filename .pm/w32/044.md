# `migrate-container-policy --all` refuses every service whose last release failed, and would start a service canceled before its first release

Why: such services keep the strict policy on every run, so their next good deploy still runs without Render's measured capabilities; and the one service `--all` would move with nothing running gets started by the migration's own rollout, which its owner never asked for.

- **Seen:** w32/040's production run, 2026-11-19, pin `7af50a28168d`. `/api migrate-container-policy --all` (run it in the `bex-api` pod; its lines name the services, which this public board does not) refused four services with `conflict: a change is still being applied; migrate once it settles`, and none had a deploy in flight:
  - a native service whose only deploy, a `create`, ended `build_failed` on 2026-08-17: phase `Failed`, generation 1, no `status.observedGeneration` (the case w32/043 records);
  - an image service whose only deploy ended `update_failed` (`RolloutBlockedByQuota`) on 2026-10-17: phase `Failed`, generation 1, no `status.observedGeneration`;
  - an image service whose latest deploy ended `update_failed` (`ProgressDeadlineExceeded`) on 2026-10-17: phase `Failed`, generation 3, no `status.observedGeneration`;
  - a legacy `builder: auto` service that is `Running` on its prior release, whose newest `new_commit` build failed on 2026-11-16 in the source checkout: generation 730, `status.observedGeneration` 729, while its `Ready` condition already carries `observedGeneration: 730`.
- **Also seen:** the plan would have moved an image service whose only deploy was canceled before a release became available (phase `Canceled`, its Deployment scaled to zero, `app_controller.go:990-1007`). A `settings_change` rollout is a release, and the next release scales it back up, so the migration would start an image its owner stopped. w32/040 left it on its old policy and ran the per-service command for the other five.
- **Where:** `containerPolicyMigratable` (`lego/backend/internal/apps/container_policy_migration.go`) refuses whenever `Generation != Status.ObservedGeneration`. The operator's `AppReconciler.fail` (`lego/operator/internal/controller/app_controller.go:7282`) sets phase `Failed` and the conditions' `observedGeneration`, but never `status.observedGeneration`; a build that fails under a serving release likewise leaves it one behind.
- **End state:** `--all` moves every service that is not suspended and has no deploy in flight. One that runs nothing (`Failed` with no release served, `Canceled`) gets `render-v1` persisted for its next deploy with no rollout; one serving a prior release after a failed build or rollout rolls once as today. Backend tests cover each of the five shapes above. On production, `--all` then refuses only suspended services, and no service changes phase because it was migrated.
- **Related:** w32/043 is the first shape alone, reported by w32/m462's `--all-native` run. Landing this note lands w32/043 too.
