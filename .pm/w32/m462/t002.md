## Objective

Prove that a native runtime App with `containerPolicy: render-v1` gets the same pod security as a `render-v1` Docker App on every path that runs its image, and that the Passenger image bex builds starts under that security context. The existing integration test passed while production failed because it ran with Docker's default capabilities.

## Context

- `appSecCtx` and `appHostUsers` (`lego/operator/internal/controller/container_policy.go:65-90`) key on the policy, not the runtime. They cover the Deployment, the CronJob and the one-off cron run. Pre-deploy Jobs go through `lego/operator/internal/predeploy/predeploy.go`, and an initial deploy hook through the same package.
- The workload admission policy (`deploy/gitops/base/operator-workload-admission.yaml:91-107`) maps a policy to its capability list and seccomp profile. Confirm it admits a native App's workloads with `render-v1` and has no runtime condition.
- `render-v1` pods run `hostUsers: false` (`BEX_RENDER_V1_USER_NAMESPACES=*`, w6/m151). A native image is bex-built (`bex-init`, `/opt/render/project`, root-owned layers). Check that nothing in the native start path breaks under an idmapped rootfs.
- `TestNativeRubyImagePassengerPort` (`lego/operator/internal/build/nativeruntimeenv_test.go:392`, opt-in `BEX_BUILDKIT_INTEGRATION=1`) builds the Passenger fixture and runs it through `runServing(t, tag, name, url, args...)` (`:548`), with Docker's default capabilities.
- `render-v1`'s seccomp profile is generated by `scripts/seccomp-render-v1/generate.sh` and installed by `deploy/gitops/base/seccomp-profiles.yaml`.

## Steps

1. Add operator tests: a native App (a runtime such as `ruby`, no image, no Dockerfile) with `render-v1` projects the six capabilities from `appv1alpha1.ContainerPolicyCapabilities`, the Localhost profile and `hostUsers: false` on the Deployment, the CronJob, the manual run and the pre-deploy Job. The same App with `""` projects none.
2. Run the Passenger fixture under the pod's real security context: `--cap-drop ALL`, `--cap-add` for each `render-v1` capability (read from `ContainerPolicyCapabilities`, not a literal list), `--security-opt no-new-privileges`, and the `render-v1` seccomp profile when the test can generate it. It must serve on 10000 by default and on 9000 with `PASSENGER_PORT=9000`.
3. Add a strict case (`--cap-drop ALL` with nothing added) that asserts the watchdog fails to start. It documents why the policy is needed and fails if a later Passenger stops needing `SETGID`.
4. Run the opt-in suite locally (`BEX_BUILDKIT_INTEGRATION=1`). Docker runs on this host; where Go is not installed, run the suite through a Go container.

- [ ] The operator tests show the `render-v1` projection for a native App on all four paths.

## Out of scope
