## Objective

Existing native runtime services in every workspace can be moved onto `render-v1` through the existing operator-run migration. A bulk mode lets one operator run cover all of them, so parity reaches services created before this milestone.

## Context

- `MigrateContainerPolicy` (`lego/backend/internal/apps/container_policy_migration.go:53`) plans or applies one service. Applied, it persists the row, then rolls the service once as a tracked `settings_change` deploy under the App's optimistic lock. A refusal found under the lock restores the row. `containerPolicyMigratable` (`:135`) refuses what the creation default would not have given `render-v1`, so t001's predicate admits native services here too.
- It is run inside the bex-api pod: `kubectl -n bex-system exec deploy/bex-api -- /api migrate-container-policy srv-… [--apply]` (`lego/backend/cmd/api/migrate_policy.go`). It prints JSON.
- ADR089 § Privilege slice decisions item 6: "Moving an existing service is an explicit operator-run migration of one service". A bulk run is still that explicit operator-run step. t004 amends the wording.

## Steps

1. Confirm `containerPolicyMigratable` admits a native service after t001, and still refuses a static site.
2. Add a bulk mode, for example `migrate-container-policy --all-native [--apply]`. It lists every App in its own workspace namespace that runs a native runtime, judging linked services by their build source, and whose policy is not `render-v1`. It plans each one, and with `--apply` applies them one at a time. It prints one JSON line per service and a summary: migrated, no-op, and refused with the reason (suspended, deploy in flight, change pending, no control-plane row). One refusal does not stop the run.
3. Test the parser, the selection (native in, Docker and static sites out, already-`render-v1` a no-op), and a run where one service is refused and the rest migrate.
4. Count the existing Docker or image services still on `strict-v1` or `image-v1` (read-only, through the plan output or the Apps). If there are any, file their bulk migration as its own inbox note with `/pm add w32`. That widens the same Render-parity gap, but it is not this milestone's scope.
