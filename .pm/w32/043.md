# A native service whose only deploy failed at build can never be moved onto `render-v1`: the migration reads it as a change still being applied

Why: `migrate-container-policy` refuses such a service on every run, so it keeps the strict policy, and its next good deploy runs without Render's measured capabilities (a Passenger app on it still could not start).

- **Seen:** w32/m462 t008, 2026-11-19, production pin `7af50a28168d`. `/api migrate-container-policy --all-native` (plan, then `--apply`) refused one native service in a customer workspace with `conflict: a change is still being applied; migrate once it settles`. Its only deploy is `create` → `build_failed` on 2026-08-17. Its App reads phase `Failed`, `Ready=False/BuildFailedUserError`, `metadata.generation` 1 and no `status.observedGeneration`, three months later. Nothing is in flight, so it never settles. The plan's own output names it (run it in the `bex-api` pod; this public board does not carry customer service ids).
- **Where:** `containerPolicyMigratable` (`lego/backend/internal/apps/container_policy_migration.go:249`) refuses whenever `Generation != Status.ObservedGeneration`. Not traced yet: why the operator never stamped `observedGeneration` on an App whose first build failed (its build-failure path likely returns before the status write that sets it).
- **End state:** the migration moves such a service, without a rollout when nothing runs (there is no release to roll), or the operator stamps `observedGeneration` when it closes a failed first build. A backend test covers a Failed App at generation 1 with no observed generation. On production, `--all-native` refuses no service with `a change is still being applied` while none of them has a deploy in flight.
- **Not this:** a suspended service is refused with `resume the service before migrating it`, by design.
