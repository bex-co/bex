# Measure Render's native runtime process identity: does a native service run as root?

Why: w32/m462 gave native runtime services `render-v1`, Render's capability set measured on a Docker image (ADR089 § Privilege slice decisions), because Passenger Standalone's watchdog needs `SETGID` when it runs as root. Whether Render runs native services as root at all is unmeasured, and the answer decides whether bex's native identity matches Render's.

Gate: **a Render account** (a shell on a Render native Ruby service). This checkout has no Render credential. Render's docs do not say (render.com/docs/native-runtimes, /docs/troubleshooting-deploys and /docs/ssh, checked 2026-11-17).

## Steps

1. On Render, create a free native Ruby web service (any repo; start command `ruby -run -e httpd . -p $PORT`) and open its shell (dashboard Shell or `ssh`).
2. Record `id`, `grep Cap /proc/self/status`, `grep NoNewPrivs /proc/self/status`, `cat /proc/self/uid_map` and `ls -ln /opt/render/project/src | head`.
3. Do the same on a native Node or Python service, to show whether the identity is per runtime.
4. Record the result in [ADR089](../../docs/ADR089-render-container-compatibility.md) § Privilege slice decisions item 6 and in `docs/render-artifacts/container-privileges.md`.

## Then

- **Render runs native services as root** (bex's identity today, uid 0): nothing changes. Close this note with the evidence.
- **Render runs them as a non-root user:** bex running native services as that user is a stricter variant, a separate decision for the user (on Render, Passenger then never calls `initgroups`). File it as its own item; `render-v1` stays parity-sufficient either way.
