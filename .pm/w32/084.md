# A deploy's log carries none of its new instance's output, where Render's shows it between `==> Deploying...` and the verdict

Why: Render parity in the deploy log, on the surface a user reads first when a deploy fails. Render's deploy log shows the traceback that made a start command exit, right above `==> Exited with status 1`. bex's shows the verdict alone, and the user has to open the service's logs to find the cause.

- **Severity / estimate:** major, likely more than 1h: it joins app lines to a deploy's build stream. Promote when picked up if it is.
- **Seen:** w32/m560 t009, 2026-11-22. bex's `type=build` read carries the build pod's output and the platform lines only. The release's own instance writes `type=app` lines, which `bex logs -r <srv> --type build` and the dashboard's deploy log (build leg) never show.
- **Render reference (public issue logs):**
  - rkendel1/freq#187 (2026-07-14): a Python traceback, then `==> Exited with status 1`.
  - darthjee/ward#109 (2026-11-14): `==> Deploying...`, the `WEB_CONCURRENCY` line, the app's own output, then `==> Exited with status 1`.
  - DerekSopok/EMS-Kahoot#3: `==> Running 'npm start'`, then npm's output, then `==> Exited with status 1`.
- **Open questions:**
  - Which log `type` Render gives those lines in its API. The CLI's `--type build` read may carry them as `app`.
  - Whether Render stops copying them once the deploy goes live.
  - Whether every instance's output is copied, or only the first instance's.
- **Likely shape:** the deploy's own release pods (revision `rev-<generation>`), from `rollout_started_at` to `finished_at`. Read them in a deploy-scoped build read (`LogQuery.Deploy`), and in the live tail while the row is in its rollout.
- **Done when:** a failed native deploy's `bex logs -r <srv> --type build` shows the start command's own error output between `==> Running '<command>'` and `==> Exited with status N`, as it does on REST, GraphQL, MCP and the dashboard's deploy page.
