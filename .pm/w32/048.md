# A native service's saved start command is reported deployed by an env-group link or an environment "Save and deploy", but the new instance runs the old one

Why: the link deploy goes `live` and `undeployedChanges` turns false, yet the process still runs the previous start command, because the native image bakes the command into its CMD and the release reruns that image without overriding it. The change stays hidden until some later deploy happens to rebuild.

- **Severity / estimate:** major (a `live` deploy and the API both say the saved start command is running, and it is not), ~1h.
- **Seen:** `/qa-find-bugs-cli w32` routine, run `8185`, 2026-11-19 23:15–23:34 UTC. Production pin `98e053468f52`: `bex-api` and `bex-controller-manager` run `bex-operator@sha256:1ec4a7c2d561…`, read with `kubectl` on the control plane at 23:12Z. Released `bex` v0.7.0 (`bex-0.7.0-linux-arm64.tar.gz`, sha256 `dfff0702…`, checksum verified), isolated `BEX_CLI_CONFIG_DIR`, human device login as the QA user, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`). The project and env group were made through REST with the same OAuth token, because the pinned CLI has no command for either.

- **Control:** `bex deploys create srv-dbvo6d43j89c738afvkg --wait --confirm` (23:31:23Z, `api`) rebuilt the service, exit 0 in 140 s. At 23:33:29 its instance printed `QA8185 run2 QA_MARK=m8185-0c1c3296 QA_GRP=[g8185-f438650d]`. So the saved command and the env group are both fine. Only the release that reruns the served build drops the command.
- **Root cause:**
  - The link opens a configuration-only release: `envgroups.Service.rollLinkedService` → `selectServedBuild` (`lego/backend/internal/envgroups/service.go:1157-1188`) → `rollout.Tracker.SelectServedBuild` → `SelectReleaseImage` (`lego/backend/internal/rollout/served_image.go:94-107,125-127`). That writes an image-only `spec.releaseConfig` (`SourceGeneration` 0) for the serving build, and its generation passes the pending save, so `undeployedChanges` clears.
  - The operator renders that release from the saved spec, because `runtimeRecord` returns nil for `SourceGeneration == 0` (`lego/operator/internal/controller/release_config_selection.go:327-330`), so the launch is `launchUnknown`.
  - `shellRunsStartCommand` then answers false for the `native` and `buildpack` builders (`lego/operator/internal/controller/deployment_projection.go:326-338`), and `appContainer` sets neither `Command` nor `Args` (`:371-378`).
  - A native image bakes the start command at build time, `CMD ["/bin/bash","-c",<startCommand>]` (`lego/operator/internal/build/native.go:469`), so the rerun image starts the command it was built with.
- **Fix (target):** a release that reruns an existing native or buildpack artifact runs the release's own `startCommand`.
  - Recommended: when the artifact's baked command differs from the release's (or always, for a selected served build), project `Args = nativeStartArgs(startCommand)` onto the native entrypoint. That is the same projection `launchNativeArgs` already uses for build-source images.
  - Alternative: `SelectServedBuild` declines to rerun the served build, and builds, when a pending save changed the start command.
  - Either way, the deploy that goes `live` runs the saved command, `undeployedChanges` stays truthful, and a later Restart or rollback of that release runs the command its record names.
  - Do not change the pod template of native releases that are already running: re-templating every native App on an operator upgrade would roll the whole fleet, the concern `release_identity.go:194-198` names.
- **Blast radius:** the two `SelectServedBuild` callers:
  - env groups: an owner link (REST, GraphQL `linkEnvGroup`, MCP `link_env_group`, the dashboard, create with `serviceIds`), plus value writes and unlinks on Auto-Deploy-on services;
  - the service's own environment "Save and deploy" (`lego/backend/internal/secrets/batch.go:494-500`: REST batch `deploy` mode, GraphQL, MCP and the dashboard Environment page).

  Affected types are native-runtime and buildpack web services, private services and background workers. Not affected: Docker and prebuilt-image services, whose start command is projected as the container command; static sites, which rebuild; and a cron job's `cronCommand`, which is not baked into the image (unverified).
- **Regression checks:** the repro above passes when step 3's deploy starts `run2` with no build, and `undeployedChanges` reads false only then. Run the same steps with the service's own env "Save and deploy". Controls: a Docker service's saved start command through a link; a native service with no pending save, whose link still reruns the served build with no `==> Building from` line (w4/708); and a Restart after the fixed link deploy keeps `run2`.
- **Unverified:**
  - Render's behavior is not observed directly. That a "Save and deploy" there runs a saved start command over the existing build is inferred from its deploy log's `==> Running '<start command>'` step, which runs after the build.
  - The env-var "Save and deploy" path, Restart or rollback of the bad release, and the buildpack builder were read from the code, not exercised.
  - Pending native build-time fields (build command, root directory, runtime) are not rebuilt by a "Save and deploy" either. That matches Render's "existing build", but `undeployedChanges` clears for them too.
- **Dedupe:**
  - w4/708 (done; introduced the served-build rerun for group writes) and w4/m180 (the env "Save and deploy" rerun) never consider a pending start-command save.
  - w8/m135 (save only) and w8/289 (a save after a failed build) cover other halves.
  - `rg -i 'start command|startCommand'` over open `.pm` items finds nothing on this, and `.pm/DO_NOT_DO.md` has no entry. Not deploy lag: there are no commits to `rollout/`, `envgroups/`, `deployment_projection.go` or `release_config_selection.go` after `98e053468f52`.
- **Cleanup:** the run's service, the unexpected second service `qa-20261119-8185-neg` (a key that starts with a digit is valid by `core.EnvKeyRule`, so the create succeeded), the env group and the project were deleted by ID. Every by-ID read and URL answers 404.
