# A second image pull failure of the same live release records no `image_pull_failed`, because the Rollout condition's transition time never moves

Why: a live service whose image cannot be pulled on a wake, restart or reschedule gets one Image Pull Failed event and email for its release, ever. If the pull recovers (a registry blip) and fails again weeks later, the timeline, the webhook and the email stay silent while the service cannot start. Render reports each failure.

- **Found:** w32/036's blast-radius check, 2026-11-17, by reading the code (not reproduced on a cluster).
- **Cause:** `servedReleasePullFailure` (`lego/backend/internal/store/reconciler.go`) keys the fact `release:<srv>:<generation>:image_pull_failed:<Rollout LastTransitionTime>`, to record "one event per time the release stops being able to pull". The operator only ever writes `Rollout` with status False (`lego/operator/internal/controller/app_controller.go`, `settleFailedRolloutMessage`, `failBeforeDispatch`, the static publish verdict) and removes it only for a static site's publish verdict (`clearPublishVerdict`). `meta.SetStatusCondition` keeps `LastTransitionTime` when the status does not change, so after an App's first failed rollout the transition time never moves again: every later pull failure of the same served generation has the same key, and the store's `ON CONFLICT (source_key) DO NOTHING` drops it. The key test (`TestServedReleasePullFailureIsRecordedOncePerIncident`, "a later incident") moves the transition time by hand, which the operator never does.
- **Also seen:** after the release recovers, the stale verdict (served generation, `ImagePullBackOff`) stays on the App, so every later pass still matches it.
- **Related:** w8/m156 (blocked) t010 changes how the operator settles a served release that cannot pull and t009 is its live check. Check what t010 shipped before choosing a fix here. w32/036 fixed the date of this fact (observation time), not its key.
- **Fix direction:** give each incident its own identity on the operator side, for example a verdict cleared (or a recovery recorded) when the served release's instances are Ready again, or a per-incident timestamp in status, and key the fact by it.
- **Done when:** a reconciler test in which the same served generation fails to pull, recovers, and fails again (as the operator would write it, transition time unchanged) records two `image_pull_failed` facts, and fails today. If the operator changes, an envtest pins the recovery write.
- Minor, ~1h; may grow to a milestone if the operator change touches m156's settle path.
