# Passenger Standalone never starts on a native Ruby service: its watchdog needs `CAP_SETGID`, which native runtimes do not get

Why: Render sets `PASSENGER_ENGINE=builtin` and `PASSENGER_PORT=10000` so that `bundle exec passenger start` serves a Ruby app with no configuration. On bex that start command crash-loops on every native Ruby service, on any port, so a Passenger app moved from Render never deploys. It also blocks w32/m424's DoD 1.

Severity: **major**. Every Passenger Standalone app fails, with no workaround short of switching servers. Attribution: the container policy of native runtimes. They run as root under the strict policy (drop `ALL`, add nothing), while `render-v1`, Render's measured capability set, applies only to Docker and image services. Estimate: more than 1 h across several tasks, so promote it. Source: w32/m424 t007's production walk, 2026-11-17, pin `6984548a30f8`, `bex-canary`.

## Evidence

- **Production.** The fixture `qa-20261117-m424-passenger` (`srv-dbu2uuhc204s73bi6v8g`, deleted afterwards) was a free native Ruby 3.4.12 web service. Its build command wrote a `Gemfile` with `passenger` 6.1.0 and `rack` 3.1.8 and a `config.ru`, then ran `bundle lock`, `bundle install` and `passenger-config install-standalone-runtime --auto`. Its start command was `bundle exec passenger start`.
  - The build passed, and `PASSENGER_ENGINE=builtin` and `PASSENGER_PORT=10000` reached the build and the pod.
  - The container then printed `Could not start the server engine: Daemon 'PassengerAgent watchdog' failed to start.` and exited 1.
  - The deploy closed `update_failed`: "container exited shortly after start and is restarting repeatedly (last exit code 1)".
  - The pod ran as uid 0 with `CapEff: 0000000000000000` (`capabilities.drop: [ALL]`, RuntimeDefault seccomp), and the App's `containerPolicy` was empty.
- **Local repro** on `ruby:3.4` with the same Gemfile, Passenger's environment variables and start command:
  - Docker's default capabilities: `200` on 10000.
  - `--cap-drop ALL`: exit 1. Passenger's log reads `ERROR: Unable to lower Passenger watchdog's privilege to that of user 'root' and group 'root': cannot set supplementary groups: Operation not permitted (errno=1)`.
  - `--cap-drop ALL --cap-add SETGID`, with Docker's default seccomp: `200` on 10000.
- **Cause.** Passenger Standalone always starts the watchdog with `--no-user-switching --default-user <current user>` (`standalone/start_command/builtin_engine.rb:103-131` in passenger 6.1.0). Running as euid 0 with a user set, the watchdog's `lowerPrivilege()` calls `initgroups`, `setgid` and `setuid` (`src/agent/Watchdog/WatchdogMain.cpp:981-1011`), even when the target is root itself. `setgroups` needs `CAP_SETGID`.
- **bex's side.** `runsContainerPolicy` (`lego/backend/internal/apps/service.go:2930-2936`) gives the widened policy to Docker and image services only. `ContainerPolicyCapabilities` (`lego/types/v1alpha1/container_policy.go:35-44`) adds nothing for strict. [ADR089](../../docs/ADR089-render-container-compatibility.md)'s policy table says "Static sites and native runtimes are out of scope" for `render-v1`, whose measured Render set includes `SETGID`.

## Fix

- **Check Render first.** In a Render shell on a native Ruby service, read `id` and `grep Cap /proc/self/status`. A native service that runs as root with Render's measured set reaches `initgroups` and succeeds. One that runs as a non-root user never calls it. The answer decides between the two routes below. Record it in ADR089.
- **Parity route (preferred if Render's native services run as root).** Give native runtime services `render-v1` the way Docker and image services get it: the creation default, and the operator-run migration for existing services (`container_policy_migration.go`). Cover web, private, worker and cron services, and their pre-deploy and one-off jobs. Amend ADR089's scope row and ADR018. A narrower `SETGID`-only policy for native runtimes is the fallback if widening needs the user's sign-off. ADR089 says not to widen the allowlist silently.
- **Tests:**
  - The policy projection for a native service.
  - The migration of an existing native App.
  - An opt-in buildkit integration test in `lego/operator/internal/build/nativeruntimeenv_test.go`, beside `TestNativeRubyImagePassengerPort`, that runs the image with the pod's real security context (`--cap-drop ALL` plus the policy's adds). The existing test runs with Docker's default capabilities, which is why it passed while production fails.

## Acceptance (production, after the deploy)

- A free native Ruby web service that runs `bundle exec passenger start` and configures no port goes `live` on its first rollout, listens on 10000 and answers `200`. With its own `PASSENGER_PORT=9000`, it listens on 9000, goes `live` and answers `200`. That is w32/m424's DoD 1. Rerun it there and close w32/m424.
- The w32/m424 Gunicorn and `GEM_PATH` checks still hold.
