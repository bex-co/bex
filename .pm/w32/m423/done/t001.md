## Objective

Linking an environment group to a repo-backed service whose Auto-Deploy is off deploys it now, as Render documents, instead of holding the link until the owner's next deploy. Unlink and group delete keep today's hold for such a service.

## Context

- `lego/backend/internal/envgroups/service.go`: `autoDeployGated` (`:1180`) returns true for a build source and for `a.Spec.Repo != "" && !a.Spec.AutoDeploy`; `rollLinked` (`:1201`) then only stages the change with `rollout.StageGroupLink` (`lego/backend/internal/rollout/grouplinks.go:106`), else rolls refs + `spec.restartedAt` in one recorded rollout (`rollLinkedService`, `store.TriggerConfigChange`).
- Callers: create with `serviceIds` (`service.go:670`, which reports held services as `pendingServiceIds`, `:500`), `linkFetched` (`:1114`, shared by REST/GraphQL/MCP `LinkService` `:1060` and the Blueprint seam `LinkEnvGroup` `:1613`), unlink (`:1323`).
- Image-backed services are never held today (the Repo guard), so only repo-backed Auto-Deploy-off services change.
- Render: "That's it! Render kicks off a new deploy of your service to incorporate the values from the linked environment group." (render.com/docs/configure-environment-variables § Linking a group to a service, read 2026-11-16). Modifying or deleting a group deploys only services with autodeploys enabled (§ Modifying a group). The API reference for link, unlink and delete says nothing about deploys.

## Steps

1. Give `rollLinked` (or its callers) the link/unlink distinction: a link takes the rolled path for a repo-backed Auto-Deploy-off service; an unlink keeps `StageGroupLink`; group delete keeps its held path.
2. Keep build sources held (w2/m254: Render gives a build source the group at build time) and keep a suspended service's link staged as w4/m234 stages its saves; verify the suspended case today and keep it unchanged.
3. Keep the Blueprint seam's behavior unchanged (Render documents nothing for a sync-made link) and record that choice in t003.
4. Confirm a link already staged in `app.bex.co/pending-env-group-links` before this change is still folded by the next release (`FoldStagedGroupLinks`), so no migration is needed.
5. Create with `serviceIds` no longer lists a freshly linked service in `pendingServiceIds`.

**Done 2026-11-17:** `envgroups.rollLinked` takes a `groupLinkWrite`. An owner's link (`LinkService`, so REST, GraphQL, MCP and the dashboard, and a create with `serviceIds`) deploys every service whatever its Auto-Deploy setting: the refs and `spec.restartedAt` move in one recorded `config_change` rollout. A build source still stages (w2/m254). A suspended service goes through the same rollout, which the tracker holds (w4/m234). The create now names that service in `pendingServiceIds` for every service type, as `EnvironmentPatchResult` does; before, only a gated suspended service was named. A Blueprint sync's link (`LinkEnvGroup`), an unlink and a group delete keep the gate. The rolled write also drops any change still staged for that group (`rollout.DropStagedGroupLink`): without that, relinking a group after a staged unlink released the unlink over the link and dropped the group. A link staged before this change is still folded by `PrepareGroupRefsForRelease` at the next release, so no migration is needed. `cd lego/backend && go test` of envgroups, rollout, apps, deploys, environments, secrets and cmd/api passed; the full real-DB suite runs in the ship gate.
