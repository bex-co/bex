# `bex logs --type build --instance <id>` returns empty for every synthetic deploy progress line's own emitted `instance` ID

Why: `progressEntry` (`lego/backend/internal/logs/progress.go:389`) sets `LabelInstance` to the deploy ID (`dep-…`), which `setLogEntryResource` (`lego/backend/internal/logs/service.go:2756`) projects to a public `srv-<id>-<hash>` instance ID on every read, but `translateInstanceFilter` (`service.go:2704-2741`) builds its reverse-lookup candidates only from live App pods and Loki's `pod` label values — never deploy IDs — so filtering by any synthetic progress line's emitted `instance` ID resolves to `noSuchInstance` and returns zero lines.

- **Severity / estimate:** **minor**, ~30m. Any CLI user (or dashboard Log Explorer "Filter by instance" action) who copies the `instance` value from a `bex logs --type build -o json` progress line and passes it back to `--instance` gets an empty result (and a negated `instance != <id>` filter fails to exclude that deploy's progress lines).
- **Versions:** released `bex` v0.9.0 (`bex-0.9.0-linux-arm64.tar.gz`, compatible with Render CLI `v2.36.0`, upstream pin `4fd34231b637`); repo checkout synced to `b0a4384d44` (`lego/cli` pinned to Render CLI `v2.37.0`, `11ef59f330dedec290f8d71d89b8f7379bbbed09`); `translateInstanceFilter` and `synthesizeProgress` are unchanged on `main` through `b0a4384d44`.
- **Context:** routine `cli-qa` sweep `8b71`, 2026-11-23 22:48–22:55 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login (`bex login`), non-TTY `-o json`.

## Attribution and root cause

- **Attribution:** server (`lego/backend/internal/logs/`). The pinned Render CLI passes `--instance` verbatim as the `instance` query parameter on `GET /v1/logs`.
- **Root cause:**
  - `progressEntry` (`lego/backend/internal/logs/progress.go:383-394`) tags synthetic platform lines with `LabelInstance: deployID` (`dep-…`).
  - `labelHistory` → `setLogEntryResource` (`lego/backend/internal/logs/service.go:2755-2757`) projects every non-empty `LabelInstance` through `projectLogInstance(resource, pod)` → `srv-<id>-<hash>` (for `dep-dc2c3mmdfl0s73a7f6u0`, `srv-dc2c3mmdfl0s73a7f6tg-69h2smk0vnmv9b1jcsmu`).
  - `QueryLogs` (`service.go:1057`) calls `translateInstanceFilter(ctx, resource, appNS, &q, candidatesFromPods(pods))` before `queryHistory`.
  - `translateInstanceFilter` (`service.go:2704-2741`) gathers reverse-lookup candidates only from `live` (App pods) and `s.LabelValues(ctx, namespace, LabelInstance, part)` (Loki's `pod` label values from BuildKit/App pods). Synthetic progress lines are never stored in Loki, so deploy IDs (`d.ID`) are never in `cands`.
  - `ids.ResolveInstanceSelectors` therefore returns `[]`, `:2737` sets `q.Instance = []string{noSuchInstance}`, and `synthesizeProgress` (`progress.go:1196`, `if !q.keepPod(d.ID)`) drops every deploy's progress lines. For a negated filter (`q.negates(LabelInstance)`), `noSuchInstance` matches nothing, so excluding that projected instance ID fails to exclude the deploy's progress lines.

## Fix

- In `lego/backend/internal/logs/service.go` (`translateInstanceFilter`, `:2704-2741`, and its callers `QueryLogs:1057` and `followLogs:1581`):
  - When `q.wants(LogTypeBuild)` and `s.DeployProgress != nil`, fetch the service's deploy rows (`s.DeployProgress(ctx, resourceID, q.End)`) and add each deploy ID (`ids.InstanceCandidate{Name: d.ID}`) to `cands` (deduplicated via `seen`) before calling `ids.ResolveInstanceSelectors`. (Best-effort: ignore a `DeployProgress` error just as `LabelValues` errors are skipped at `:2720`.)
  - Check whether `LogLabelValues` (`service.go:1358-1431`) for `label == LabelInstance` with `q.wants(LogTypeBuild)` should stay Loki-backed or also include in-window deploy IDs; keep it consistent and document the choice in tests.
- **Surfaces (REST/GraphQL/MCP/UI):** REST `GET /v1/logs`, GraphQL `logs` (single-resource and project views), MCP `list_logs`, and live tails (`GET /v1/logs/subscribe`) all share `translateInstanceFilter`, so the single fix repairs every surface.

## Blast radius

- Callers of `translateInstanceFilter`: `QueryLogs` (`service.go:1057`), `queryDatastoreLogs` (`:1205`, `DeployProgress` not applicable / `wants(build)` false), `followLogs` (`:1581`), `followDatastore` (`:2008`).
- In `followLogs` (`:1581`) with `type=build`, resolving a deploy's projected `instance` ID also fixes `bex logs --type build --instance <projected-deploy-id> --tail` (`progressFollower` calls `q.keepPod(d.ID)`). Verify `followPodsAndBuilds` (`:1948`) stays accurate when `q.Instance` resolves to a deploy ID vs an App pod.
