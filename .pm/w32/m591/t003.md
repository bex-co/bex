## Objective

Move a failed deploy's single `==> Exited with status N` and troubleshooting pair from `d.FinishedAt` to `d.FirstExitAt` (with `*d.FirstExitCode`) when the deploy settled `update_failed` with a recorded non-OOM first exit, keeping Render's ANSI forms, ordering the pair after run 1's own output and before run 2, and confirming the live build/deploy tail delivers it cleanly without premature emission.

## Context

- `progressLines`, `rolloutLines`, `closingLines`, `rendersVerdict` and `progressFollower.emitRow` live in `lego/backend/internal/logs/progress.go`.
- `rendersVerdict` (`progress.go:925`) currently returns `==> Exited with status N` (`renderlog.PlatformFailure`) for `d.Status == "update_failed"` when `!d.TimedOut && d.ExitCode != nil && !d.OOMKilled`, and `closingLines` (`:902`) appends `styled(renderlog.PlatformStep, troubleshootLine)` at `d.FinishedAt`.
- **Whole-second timestamp subtlety:** kubelet stamps `Terminated.FinishedAt` in whole seconds, while the app container's stdout/stderr in Loki carries nanosecond timestamps within that same second (and a legacy image's `rolloutLines` stamps `AppStartedAt[0]` in whole seconds too, held by `rolloutLineStep` after `RolloutStartedAt`). Look at `hookMoments` (`progress.go:778-791`) for how whole-second end timestamps are held at the close of their second (`finishedAt.Add(time.Second - time.Nanosecond)`), and check what happens if run 2 starts in the next second (or even the same second!) or if `d.FinishedAt` is earlier than the end of that second:
  - Clamp the verdict timestamp so it is never after `d.FinishedAt`, never before `d.RolloutStartedAt` / run 1's narrated `Running` line, and when a second run's `AppStartedAt[1]` is recorded and strictly after `FirstExitAt` (e.g. next second), stays before `AppStartedAt[1]`'s timestamp (note: `FirstExitAt + 999_999_999ns` is already `< FirstExitAt + 1s`, so if run 2 starts in a later second it sorts strictly between run 1's output and run 2!). Check the edge case where run 1 exits and run 2 starts in the exact same whole second (on a legacy `InstanceAnnounces: false` image, run 2's `Running` line would need to sort after the exit pair or the exit pair sits right after run 1's start).
- **No premature emission & no double verdict:**
  - Emit the first-exit pair ONLY when `d.Status == "update_failed"` (and `!d.FinishedAt.IsZero()`, `!d.TimedOut`, `!d.OOMKilled`, `!d.FirstExitAt.IsZero()`, `d.FirstExitCode != nil`, and `!d.FirstExitAt.After(d.FinishedAt)`).
  - While the deploy is `update_in_progress`, do NOT emit it (a later run might still succeed and go `live`).
  - When the first-exit pair IS emitted, `closingLines` must add nothing at `d.FinishedAt` — neither a second `Exited` pair NOR a fallback to `terminalLines` (`==> Deploy failed: ...`)!
  - When `FirstExitAt` is zero (legacy rows, or an `update_failed` deploy where no first exit was recorded), keep today's `closingLines` pair at `d.FinishedAt` using `d.ExitCode`.
  - When a deploy fails with `TimedOut`, `OOMKilled`, `build_failed`, `pre_deploy_failed`, or `canceled`, or succeeds (`live`/`deactivated`), keep today's behavior unchanged.
- **Live tail (`progressFollower.emitRow`, `progress.go:1241`):**
  - Check `holdClosing`: when `holdClosing` is true (draining a build pod), any line earned by closing must stay held until `emitRow(..., false, emit)`. Today `holdClosing` checks `!at.Before(d.FinishedAt)`, which will NOT catch a verdict line stamped at `FirstExitAt < d.FinishedAt`! Ensure `holdClosing` still holds closing verdicts if needed (or tag/filter closing entries cleanly), and verify that when the deploy settles `update_failed`, `progressFollower` emits the pair once on `--type build --tail` and type-less `--tail`.

## Steps

1. Update `progressLines` and `closingLines` (and `rendersVerdict` as needed) in `lego/backend/internal/logs/progress.go` to emit the `==> Exited with status N` (`renderlog.PlatformFailure`) + `troubleshootLine` (`renderlog.PlatformStep`) pair at the clamped first-exit timestamp for qualifying `update_failed` deploys, emitting nothing at `d.FinishedAt`.
2. Update `progressFollower.emitRow` if `holdClosing` could leak the first-exit verdict while a build pod is still draining, and verify WebSocket/SSE tail delivery once the deploy settles `update_failed`.
3. Check whether `deployWindowEnd` (GraphQL/dashboard) or any other log-window helper assumes the verdict is at `d.FinishedAt`; verify the pair falls within `[d.CreatedAt, d.FinishedAt]`.
4. Write comprehensive unit tests in `lego/backend/internal/logs/progress_test.go` (and live-tail tests).
