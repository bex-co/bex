# After a failed Blueprint plan is fixed and re-planned with no changes, `bex ea blueprints approve` still says the newest sync "failed planning … fix the Blueprint file and re-plan"

Why: the refusal tells a user to do the thing they just did, so a fixed Blueprint looks broken. A plan that finds no changes leaves no record, so approve keeps answering for the stale failed plan.

- Severity: minor. Nothing is applied either way, which is right because there is nothing to approve. The code and the advice are wrong.
- Versions: released `bex` v0.9.0, upstream pin v2.36.0 `4fd34231b637`. Production pin `cce6c749f6ff`, live digest `sha256:e14f8ee4…`. No change to these lines since the pin; the code below is from `main` `7b9140a6a`.
- Context: cli-qa routine run `0cd3ca`, 2026-11-21 15:25–15:28 UTC, `https://api.bex.co`, workspace `bex-canary`, human device login, `-o json`, non-TTY.

## Repro

This starts on an owned, approved Blueprint (`exs-dc0rcsgn82tc73dukv40`, from `https://github.com/render-examples/go-web-server`, since deleted).

```sh
bex ea blueprints update exs-… --path nope.yaml -o json --confirm
# exit 1: path saved, planningOutcome "failed", sync exe-dc0rfqt2n01c73bc1lpg state "error" ("Blueprint file \"nope.yaml\" not found on branch \"master\".")
bex ea blueprints update exs-… --branch master --path render.yaml -o json --confirm
# exit 0: planningOutcome "no_changes", sync null
bex ea blueprints plan exs-… -o json --confirm
# exit 0: planningOutcome "no_changes", sync null; meta.next "No changes to approve. … If you previously planned changes that are still waiting for approval, running \"bex ea blueprints approve exs-…\" now will approve that earlier plan. …"
bex ea blueprints approve exs-… -o json --confirm
# exit 1: Error: received response code 409 (BLUEPRINT_SYNC_PLANNING_FAILED): the newest sync exe-dc0rfqt2n01c73bc1lpg failed planning and cannot be approved; fix the Blueprint file and re-plan
```

The approve over REST:

```text
POST /v1/blueprints/exs-dc0rcsgn82tc73dukv40/approve  {}
→ 409 {"code":"BLUEPRINT_SYNC_PLANNING_FAILED","error":"the newest sync exe-dc0rfqt2n01c73bc1lpg failed planning and cannot be approved; fix the Blueprint file and re-plan","id":"conflict","message":"…","params":{"syncId":"exe-dc0rfqt2n01c73bc1lpg"}}
```

`GET /v1/blueprints/{id}/syncs` lists only the failed plan and the first applied sync. The two `no_changes` plans that came after the failure left nothing.

## Cause

- A `no_changes` plan writes no sync row. `planBlueprintSync` (`lego/backend/internal/apps/blueprint_onboarding.go:319-334`) calls `SettleNoChangesPlan` (`lego/backend/internal/store/blueprint_plans.go:172-194`), which supersedes only a waiting `created` plan and updates a Blueprint that is still `created`.
- `ApproveBlueprint` reads `LatestBlueprintPlan` (`blueprint_plans.go:159-163`), which is the failed plan here. The plan has no actions, so it takes the branch at `blueprint_onboarding.go:537-539` and answers `BLUEPRINT_SYNC_PLANNING_FAILED` with "fix the Blueprint file and re-plan".
- ADR049 § Blueprint onboarding states the two approve refusals, but not this order of events.

## Fix

- Record that the newest planning attempt found no changes. One way is a `blueprints.no_changes_planned_at` column that `SettleNoChangesPlan` stamps, written through a new migration.
- When the newest planning attempt is older than that stamp, `ApproveBlueprint` answers `409 BLUEPRINT_NOTHING_TO_APPROVE` with something like "the newest plan of this Blueprint found no changes; there is nothing to approve". `params.syncId` is left out, because no sync is pending.
- An implementer may choose another record, provided the syncs list does not gain rows Render would not list. Render's `createBlueprintSync` answers `sync: null` for `no_changes`.
- Unchanged: a newest plan that failed, with no later plan, keeps today's `BLUEPRINT_SYNC_PLANNING_FAILED`. The `BLUEPRINT_PLAN_CHANGED` binding (w5/m384 t001) also stays as it is.
- Surfaces: REST approve, GraphQL `approveBlueprint` and MCP `approve_blueprint` share `ApproveBlueprint`.
- Docs: add the case to ADR049's approve bullet.

## Acceptance

- A test runs failed plan → `no_changes` plan → approve and gets `409 BLUEPRINT_NOTHING_TO_APPROVE` with the no-changes wording. Failed plan → approve still answers `BLUEPRINT_SYNC_PLANNING_FAILED`. Planned → `no_changes` → approve still answers `BLUEPRINT_NOTHING_TO_APPROVE` for the superseded plan. Run it on the real-DB store if the fix touches SQL.
- On production after the pin carries it, the Repro's last command prints `409 (BLUEPRINT_NOTHING_TO_APPROVE)` with the no-changes sentence. Delete the Blueprint by ID and check `GET` answers 404.
