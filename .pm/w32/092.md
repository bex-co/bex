# The CLI's live build tail carries a pre-deploy step's own output, as Render's deploy log does

Why: Render parity in the live deploy log. Render's `render logs --tail` of a deploy shows the pre-deploy command's output between `==> Starting pre-deploy: <command>` and the step's verdict. bex's WebSocket build tail sends w32/m572's narration lines but none of the command's output, so a user following a failing migration live sees the verdict with nothing before it.

- **Severity / estimate:** minor, likely more than 1h: the tail must follow a pod in another namespace, between two builds. Promote when picked up if it is.
- **Seen:** w32/m572 t006, 2026-11-22. `followBuilds` (`lego/backend/internal/logs/service.go`) streams only build pods (`BuildPods`, which selects on the `app.bex.co/build` label in `BEX_BUILD_NAMESPACE`). The pre-deploy Job's pod runs in the App's own namespace (ADR043 D8), and only `collectPreDeployLogs` reads it, for a `type=predeploy` history read. The history read of `type=build` carries the output through Alloy (w5/m100), so `bex logs --type build` and the dashboard's deploy page show it; the live `--tail` does not.
- **Render reference:** Unwrenchable/ATOMIC-FIZZ-CAPS-VAULT-77-WASTELAND-GPS#82 and dukens11-create/Flupflap#206 show the output between the step's lines in the deploy log; Render's subscription is a filter over what is generated (w8/m159).
- **Done when:** a live `bex logs -r <srv> --type build --tail` of a deploy with a pre-deploy step reads `==> Starting pre-deploy: <command>`, `==> Running '<command>'` on a native runtime, the command's output, then the step's verdict, each line once, with the same ids as the history read. A tail test covers it.
