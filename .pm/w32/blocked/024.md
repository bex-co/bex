# Downloading a sandbox path that is or passes through a symlink is refused as "sandbox destination exists or is not a supported file target"

Why: a path in a sandbox often runs through a symlink. Examples are a virtualenv's `lib64 -> lib`, `node_modules/.bin/*`, Alpine's `/etc/ssl/certs/*` and a merged-`/usr` image's `/lib -> usr/lib`. On bex, `bex sandboxes copy <sbx>:<such a path> ./x` is refused with `409`. The message talks about a "destination" that "exists", which is wrong for a download source. Nothing in Render's sandbox docs says a symlinked source is refused. The tenant is root in its own sandbox and can already `exec -- cat` the same file, so refusing the download protects nothing.

- **Seen:** `/qa-find-bugs-cli` loop sweep 23, 2026-11-14 ~13:23 UTC, `bex-canary` (`tea-daif693dqjvc73e7as3g`), release `bex` v0.5.0 (Render CLI v2.35.0 pin), human device login, production pin `c99e7815ebec`, sandbox `sbx-dbs5u6dv5sfs73boaipg` (since terminated). In the sandbox: `dl/top.txt`, `dl/rel-link -> top.txt`, `dl/dirlink -> sub`, `dl/sub/s.txt`, plus an uploaded `venv/lib64 -> lib`.

  ```text
  $ bex sandboxes copy <sbx>:dl/rel-link ./a                  # the path is a symlink to a file
  Error: received response code 409: sandbox destination exists or is not a supported file target
  $ bex sandboxes copy <sbx>:dl/dirlink ./b                   # a symlink to a directory
  Error: received response code 409: sandbox destination exists or is not a supported file target
  $ bex sandboxes copy <sbx>:dl/dirlink/s.txt ./c             # a file under a symlinked directory
  Error: received response code 409: sandbox destination exists or is not a supported file target
  $ bex sandboxes copy <sbx>:venv/lib64/python3.12 ./d        # a directory under venv/lib64 -> lib
  Error: received response code 409: sandbox destination exists or is not a supported file target
  $ bex sandboxes copy <sbx>:dl ./dl                          # control: the parent directory downloads, links kept
  Downloaded <sbx>:dl to ./dl
  ```

  The same `409` answers a single-request probe over HTTP/1.1 and HTTP/2, so the cause is not the transport.

- **Cause (traced at `9b11f48d7`):** `downloadScript` (`lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go:493-505`) runs `cd_parent` (`:290-306`). It enters the parent with `cd -P` and exits 73 when the physical path differs, which is the "symlinked ancestor" rule. It then exits 73 when the name itself is a symlink (`:496`). `executionError` maps 73 to `409 "sandbox destination exists or is not a supported file target"` (`:267-268`), the upload message. w32/m380 t004 kept the rule on purpose ("following a link there would move the transfer to a path nobody authorized"). That reasoning is about where an upload lands. A download only reads inside the caller's own sandbox, where the caller is root.
- **Fix:**
  1. For a download, resolve the source as the sandbox's filesystem does: follow symlinks in the parent and in the name. Run `cd` without `-P` and drop the physical-path check for downloads only, then archive or `cat` the resolved target. A symlink to a directory downloads that directory's tree.
  2. Keep the upload rule, which is where its rationale applies, but give it an accurate message. Name the case ("sandbox path passes through a symlink") instead of "destination exists".
  3. Record the download behavior in `docs/render-artifacts/ea-sandbox.md` ("existing symlink ancestors are refused") and in ADR018's sandbox file-transfer row.
- **Acceptance:** in `bex-canary` with the release CLI:
  - Each of the four downloads above succeeds.
  - `./a` holds `top.txt`'s content.
  - `./b/s.txt` exists.
  - The control download keeps `dl`'s own links.
  - An upload through a symlinked ancestor still fails, with the new message.
  - A gateway test covers a symlinked name and a symlinked ancestor for a download.
- **Unverified:**
  - Render's own answer for a symlinked download source. Its docs neither allow nor refuse it. The fix follows ordinary filesystem semantics, which the tenant already has through exec.
  - Whether the upload rule should also follow links. It is left in place here.
- **Dedupe:** `rg -i 'symlink ancestor|destination-path rule' .pm docs`. That finds w32/m380 t004, which kept the rule without separating downloads, and `ea-sandbox.md`. No open item covers download sources.
- Minor. ~45m.

## Shipped 2026-11-14 (`/loopx w32`), parked on the production deploy

- **Shipped:** `451080aea`: `downloadScript` resolves its source as the sandbox's filesystem does (`cd_parent "$1" follow`), so a link to a file sends the file, a link to a directory archives its tree, and a path through `lib64 -> lib` reads through it; a dangling link is `404 file_not_found`. An upload keeps the rule, and its symlinked ancestor now answers `409 sandbox upload path passes through a symlink` (exit 74). `follow` is an argument, so no image or sandbox env can turn it on for an upload. Tests: `TestADownloadFollowsSymlinks`, `TestShellRejectsExistingSymlinkAncestorsAndTargets` (with `follow=1` in the env), `TestASymlinkedUploadAncestorAnswersItsCause`. Docs, ADR018 (a new 🚧 row) and the CLI contract say so.
- **Gate:** production deploys are batched: `deploy.yml` deploys a push, or the hourly schedule once the pin is 6 h old. No user decision is needed. Once `git merge-base --is-ancestor 451080aea <pinned sha>` holds, a worker runs the acceptance walk above with the released CLI in `bex-canary`.
