## Objective

For a release whose instance writes `==> Running '<command>'` itself (t003's record), `rolloutLines` writes no `Running` line of its own. The instance's line is then the only one, in the service's log and on every deploy view that interleaves app lines. A release on an older image keeps the narrated line, so no deploy loses the line it shows today.

## Context

- `rolloutLines` (`lego/backend/internal/logs/progress.go:584`) writes the line at each recorded app-container start, as a `type=build` platform line.
- The dashboard's deploy page (`dashboard/src/features/deploys/hooks/use-deploy-logs.ts`) and the CLI's type-less deploy tail read the service's `type=app` lines over the deploy's window. They would show both copies, which have different ids.
- In tretta's capture, Render's line carries `instance`, `level` and a UUID id like the app's own output, and the platform lines carry neither (README § Render's line). Dropping the narrated copy for new images therefore takes the start command's `Running` line out of `bex logs --type build`, and puts it in the instance's stream, where Render's capture puts it. What Render's own `type=build` read returns stays with w32/085: record the choice in ADR018 so that w32/085's capture can confirm or reverse it.
- w32/m560's t008 walk expects `==> Running 'node main.js'` in `bex logs -r <srv> --type build`. If that walk is still open when this ships, add a dated line to its task saying that a release built after this milestone shows the line in the type-less read instead.
- The pre-deploy step's line follows t001's choice: when native-init stays quiet in the step's pod, `preDeployLines` keeps its copy unchanged.

## Steps

1. Pass t003's record into `rolloutLines` and skip the `Running` line when it is set. Keep the `Deploying...` and `WEB_CONCURRENCY` lines.
2. If t001 made the pre-deploy step announce, make `preDeployLines` skip its `Running` line on the same record, and check what that costs the CLI's live tail (w32/092).
3. Check that the deploy page shows the instance's line inside the deploy's window. The narrated line sat at the kubelet's whole-second start; the instance's comes a moment later. Check the line also falls inside the window of a deploy that failed.
4. Run `cd lego/backend && go test ./...` against the real-database deps, `make lint`, and `yarn lint` and `yarn test` in `dashboard/` if the hook changes.

## Done (2026-11-22)

`rolloutLines` (`lego/backend/internal/logs/progress.go`) writes no `Running` line for a release whose instance writes it, and keeps `Deploying...` and the `WEB_CONCURRENCY` line. A rollback to an older image keeps the narrated line. `preDeployLines` is unchanged: native-init stays quiet in the step's pod. The deploy page's window needed no change. Its window runs from `createdAt` to `finishedAt` (plus 7 ms for a live close), and the instance writes the line at its container's start, before readiness or a failed rollout's settling. The choice for `type=build` reads is recorded in the README and ADR018. The dated line for w32/m560's walk is in [its t008](../../m560/t008.md). Tests: `TestRolloutLinesFollowRendersLogByServiceTypeAndOutcome` (announcing web, private and worker releases, a restart, a timeout, a running rollout, a rollback to an older and to a newer image), `TestADeploysAppAndBuildViewShowsOneRunningLinePerStart` (one `Running` line per start, the instance's or the narration's), and `TestRolloutRunningLineReadsEachDeploysOwnRecord` through the composition root.
