# Capture Render's rollout lines for the deploys no public log shows: a worker, a private service, a prebuilt image, a rollback and a pre-deploy command

Why: w32/m560 had to assume what Render's deploy log says for these deploys. A capture settles each assumption, or turns it into a parity fix.

- **Severity / estimate:** minor, ~45m with a Render account: five free or cheap deploys and their logs.
- **Seen:** w32/m560, 2026-11-22. Thirty public Render logs fix the rollout lines for built web services, native and Docker, and none shows the cases below. bex's choice for each is recorded in `docs/render-artifacts/live-deploy-following.md` § The rollout and in ADR018 § Logs, Build logs.
- **What to capture on Render:**
  - **A background worker and a private service, both native.** bex assumes they read like a web service: `==> Deploying...`, then the `WEB_CONCURRENCY` line (private only, since Render gives a worker no default), then `==> Running '<command>'`, with no port scan.
  - **A prebuilt image** (Deploy an existing image). bex keeps `==> Deploying image <image>`, then the `WEB_CONCURRENCY` line. Qxad/openlist-for-PaaS#2 shows `==> Starting service...` before that line, but it may be a restart.
  - **A rollback, and a "Save and deploy" that reuses the build.** bex keeps `==> Deploying image <image>` and `==> Rolling out the current release`.
  - **A service with a pre-deploy command.** Where does its output sit against `==> Deploying...`? bex prints `==> Deploying...` after it, because the template is written once the step passes.
  - **The log `type` of each rollout line** in Render's API (`GET /v1/logs?type=build` against `type=app`), and whether Render's deploy log copies the instance's output (w32/084).
- **Gate:** a Render account. No Render credential exists in this checkout (checked for w32/039 on 2026-11-17). Like w32/039, this needs a `RENDER_API_KEY` in `.env`, or the user pastes the logs.
- **Done when:** each case's Render log is recorded in ADR018 § Logs, Build logs. Any line bex writes differently is fixed, or filed as its own item.

## Parked 2026-11-22 (`/loopx w32`): public logs settle the pre-deploy lines and part of the log types; the rest needs a Render account

**Credential check.** This checkout's `.env` sets no `RENDER_API_KEY` and no other `RENDER`-named variable, and holds no `rnd_`-shaped value (checked by name only). Nothing Render-related is in the environment, and `~/.render` and `~/.config/render` do not exist. Sibling checkouts were not read.

**Search.** About 1,900 GitHub issue and PR bodies that quote `Your service is live`, `Setting WEB_CONCURRENCY`, `Exited with status`, `Starting pre-deploy` or `Pre-deploy has`, plus code files that hold answers of Render's log API. What they settle is recorded in ADR018 § Logs, Build logs ("Render's logs for the cases w32/085 captures").

- **A pre-deploy command: settled, and bex differs.** Render's log reads `==> Starting pre-deploy: <command>` about 4 s after `==> Build successful 🎉`, with no `==> Deploying...` before it. Then `==> Running '<command>'` on a native runtime, the command's output, and `==> Pre-deploy complete!`, or `==> Pre-deploy has failed`, `==> Exited with status N` and the troubleshooting line (Unwrenchable/ATOMIC-FIZZ-CAPS-VAULT-77-WASTELAND-GPS#82, dukens11-create/Flupflap#206, stranske/learning-management-system#191, BerriAI/litellm#9549, ganjasan/mapsurvey#72 and #73). bex's `==> Deploying...` after the step agrees. bex writes neither opening nor closing line and closes a failure with `==> Pre-deploy failed: <reason>`: filed as [w32/087](../done/087.md). Still open: what follows `==> Pre-deploy complete!`. ganjasan/mapsurvey#73 quotes only selected lines of a passing step.
- **The log `type`: partly settled.** Two captures of Render's log API label every line of a native web service's deploy `type: app`. They are ivanseibel/tretta `docs/work/reports/assets/T014-public/04b-render-logs.json` (2026-10-18, 60 records) and Egoka/Altera `docs/multica/snapshots/2026-09-15-infrastructure-access/infrastructure.json` (2026-09-14, read through Render's MCP `list_logs`). That covers the build's lines with `resource` and `level` labels, and the platform's `==> Deploying...`, `WEB_CONCURRENCY` line, live line and URL block with `resource` alone. Neither file says which `type` filter its query used, so neither shows what a `type=build` read returns. bex labels its narration `type=build`, `instance=<dep-…>`.
- **`==> Running '<command>'` is the instance's own line: settled, and bex differs.** In tretta's capture it carries the `instance` and `level` labels and a UUID id, like the app's output. It appears at every start of the instance, free spin-ups with no deploy included (16:09, 17:17 and 19:02 that day). bex writes it only inside a deploy's `type=build` narration: filed as [w32/088](../done/088.md).
- **ANSI colour codes: settled, and bex differs.** Render's API messages colour the `==>` marker and bold the text (tretta; kush252/Sentry-AI `investigation_data.jsonl`). bex's are plain: filed as [w32/089](../089.md).
- **A background worker: two 2025 logs, not today's shape.** eurotax/dex-scanner#2 (2025-10-08; the repository's `render.yaml` then declared `type: worker`, `runtime: node`) reads `==> Deploying...` 2.9 s after the build and `==> Your service is live 🎉` 10.0 s after that. The worker's first output follows the live line, with no port scan, no URL block and no `Running` line. Sherbivs/SensaiOS#2 (2025-10-23, a Discord bot) reads `==> Deploying...`, `==> Your service is live 🎉`, then `==> Running 'npm start'`, which repeats after each crash. bex writes a worker's `Running` line before its live line. Both logs predate Render's `WEB_CONCURRENCY` default (2025-12-08).
- **Not in any public log:** a private service's deploy, a prebuilt image's deploy, a rollback, and a "Save and deploy" that reuses the build. Qxad/openlist-for-PaaS#2's `==> Starting service...` stays unexplained: its author tried both a prebuilt image and a repository.

5. Over one deploy's window, `GET /v1/logs?type=build`, `?type=app` and no `type`: which lines each read returns and with which labels, and whether the `type=build` read carries the instance's output (w32/084).
6. If the user has a domain to spare: a free web service with a root custom domain, to confirm that its URL block's `+ 2 more domains` counts the `www` redirect and the `onrender.com` subdomain (w32/m567's inference).

**Gate:** access to a Render account, from the user. Either a Render API key in `.env` as `RENDER_API_KEY` (the key w32/039 and w10/002 also wait on), or the user runs the probes above on their own Render account and pastes the logs.
