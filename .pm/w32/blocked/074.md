# After `ea blueprints update --path`, bex's approve refuses the plan still waiting with `409 BLUEPRINT_SOURCE_CHANGED`; the pinned Render CLI says Render's approve still applies it

Why: Render parity is the top product rule. The pinned CLI tells users that updating a Blueprint does not change a sync waiting for approval, so approve still applies the plan made from the previous path or branch, and bex refuses it instead.

- **Severity / estimate:** minor, parity, ~1h.
- **Contract (pinned `render-oss/cli` `v1.1.3-0.20261106232710-4fd34231b637`, `pkg/blueprint/output.go`):** `NewUpdateOut` (`:93-99`): "Updating does not change a sync that is waiting for approval, so approve could still apply a sync planned from the previous branch or path." Its user-facing text, printed when the update's re-plan saved no sync: "If you previously planned changes that are still waiting for approval, approving now could apply that earlier plan." The CLI's `Update` (`pkg/blueprint/service.go`) reports a plan request that errors as a `failed` outcome with no sync, so this text prints whenever the re-plan request itself fails. A bare `PATCH /v1/blueprints/{id}` followed by `approve` is the same case. Render's public API docs do not describe approve (read 2026-11-21).
- **bex today (found by w32/073's worker, 2026-11-21, main at `5adb4f3cf`):** a plan waits for approval, then `UpdateBlueprint` changes the path, then `ApproveBlueprint` answers `409 BLUEPRINT_SOURCE_CHANGED` "blueprint path no longer matches the reviewed source; refresh the preview and confirm again". Approval reuses the manual-sync reviewed-source pin (w8/m41): `runSync` calls `matchReviewedBlueprintSource(b, reviewed)` (`lego/backend/internal/apps/blueprint.go:1841`), which compares the plan's path with the Blueprint's current one, then fetches at `b.Path` (`:1845`). After a branch change the approve goes through, but the apply compiles the file with the Blueprint's new branch (`deployReq.Branch: b.Branch`, `:1961`; `prepareSyncManifest` takes `b`). So services that plan creates would follow the new branch, not the one it was planned from. A plan row stores `plan_path` but no branch (`blueprint_syncs`).
- **Fix direction:** approving a planned sync applies that plan's own source: its commit, its path and the branch it was planned from (a `plan_branch` column, falling back to the Blueprint's branch for older rows). The Blueprint keeps the settings the update saved. A manual sync with a reviewed pin keeps refusing drift as it does now. A failed re-plan that saved its sync stays the newest, and approve refuses it, as w32/073 pins.
- **Tests:** plan, then `PATCH` the path, then approve, applies the plan from the old path. Plan, then `PATCH` the branch, then approve, applies the plan with its own branch. Plan, then `update --path`, then a plan request that fails (`failingAppLists`), then approve, applies the earlier plan. On fake and real Postgres. Extend `lego/backend/internal/apps/blueprint_approve_waiting_plan_test.go`.

## Acceptance

- The three sequences above apply the waiting plan, and the reviewed-pin manual sync still answers `BLUEPRINT_SOURCE_CHANGED` after a path change.
- ADR049's approve bullet and ADR018's Blueprint onboarding row state the behavior, replacing the w32/073 residual.
- A live walk in `bex-canary` with the released `bex` once the pin carries the fix: an approved Blueprint whose plan waits, then a `PATCH` of its path to a second Blueprint file, then `approve`, applies the first plan. Delete the fixtures.

## Triage and fix (2026-11-21, `/loopx w32`) — parked for the production check

Verdict: work. On main at `2921589cf`, `ApproveBlueprint` sent the plan's path as a reviewed-source pin, and `runSync`'s `matchReviewedBlueprintSource` compared it with the Blueprint's current path (`409 BLUEPRINT_SOURCE_CHANGED`). The apply compiled with `b.Branch` (`prepareSyncManifest`, `deployReq.Branch`), and a plan row stored no branch. The pinned CLI's `NewUpdateOut` (`pkg/blueprint/output.go`, re-read at the pin) and `Update` (`pkg/blueprint/service.go`, a plan request that errors is a `failed` outcome with no sync) are the contract. Render's public API docs still describe no approve.

Fixed in `077de962c`:

- A planning attempt records its branch beside its path (`blueprint_syncs.plan_branch`, migration 0321). Approval applies the plan from its own source: it reads the plan's path at the plan's commit and compiles with the plan's branch, whatever an update saved since. A plan recorded before the migration takes the Blueprint's branch. The Blueprint keeps the path and branch the update saved, which the next plan reads.
- A manual sync pinned to a previewed commit still refuses a path or repo that changed (`BLUEPRINT_SOURCE_CHANGED`, w8/m41). A failed re-plan that saved its `error` sync stays the newest, and approve refuses it (w32/073). REST, GraphQL `approveBlueprint` and MCP `approve_blueprint` share `ApproveBlueprint`.
- Tests (`lego/backend/internal/apps/blueprint_approve_waiting_plan_test.go`, with a fetcher that serves each branch tip and a file per commit and path). A path `PATCH`, a branch `PATCH`, and a path `PATCH` followed by a plan request that fails outright (`failingAppLists`) each apply the waiting plan, reading only the plan's own `<commit>:<path>`. The created service builds the plan's branch, and the Blueprint keeps the update's settings. The path test also checks that a pinned manual sync still answers `BLUEPRINT_SOURCE_CHANGED`. A plan with no recorded branch applies with the Blueprint's. The path and branch together run on real Postgres, and `TestPlannedBlueprintSyncsPG` round-trips `plan_branch` and `NULL`. Mutations caught: dropping the plan's source override fails the three sequences (two with the old `409`, the branch one building `release`); dropping the fallback fails the no-branch test; writing no `plan_branch` fails both PG tests. The full real-DB backend gate passed.
- Docs: ADR049 § Blueprint onboarding's approve bullet and ADR018's Blueprint onboarding row, replacing the w32/073 residual.
