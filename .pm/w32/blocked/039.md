# Measure Render's native runtime process identity: does a native service run as root?

Why: w32/m462 gave native runtime services `render-v1`, Render's capability set measured on a Docker image (ADR089 § Privilege slice decisions), because Passenger Standalone's watchdog needs `SETGID` when it runs as root. Whether Render runs native services as root at all is unmeasured, and the answer decides whether bex's native identity matches Render's.

Gate: **access to a Render account**. Either a Render API key in `.env` as `RENDER_API_KEY` (the same key w10/002 waits on; a worker then creates the probe services with `POST /v1/services` and reads their logs with `GET /v1/logs`), or the user deploys the probe below from their own Render dashboard and pastes the log lines. Render's docs do not say which user runs a native service (render.com/docs/native-runtimes, /docs/troubleshooting-deploys and /docs/ssh, checked 2026-11-17).

## Public evidence — 2026-11-17

Every public source points to a non-root `render` user. None of them measures the start command's uid, `CapEff`, `NoNewPrivs` or `uid_map` on today's Render, so they do not settle the question:

- **`whoami` returns `render`.** A feedback.render.com request, dated 2023-05-08 ("Add current user to shell context in SSH sessions"), says: "when I SSH into a Render instance, the whoami command returns just render". It does not name the runtime. Render's SSH session runs as the service's running user (render.com/docs/ssh § Docker-specific configuration). A Docker image with no `USER` would therefore answer `root`, so this was most likely a native service.
- **`apt` fails with a permission error.** A community.render.com thread from 2022-08-23 (topic 5325, read through the Wayback Machine because the forum's new host does not resolve) shows `apt` on a native Python service failing with `Could not open lock file /var/lib/dpkg/lock-frontend - open (13: Permission denied) … are you root?`. Render staff replied: "You won't be able to install system-wide packages on our native environments." A root process that holds `DAC_OVERRIDE` (in Render's measured set) would not get `EACCES` there. The thread does not say whether this was the build or the start command.
- **Render's docs suggest a `render` user with gid 1000.** Render forbids mounting a disk at `/home/render` (render.com/docs/disks § Disallowed mount paths). A Docker service must put its application user in group `1000` to read secret files (render.com/docs/docker-secrets).

## Steps

1. On Render, create a **free** native Ruby web service from any repo. Free web services have no shell (render.com/docs/ssh, compatible service types), so the probe runs in the commands and prints to the logs.
   - Build command: `id; bundle install || true`.
   - Start command: `id; grep -E '^(Cap|NoNewPrivs|Seccomp)' /proc/self/status; cat /proc/self/uid_map; ls -ln /opt/render/project/src | head; exec ruby -run -e httpd . -p $PORT`.
   - A paid web service, private service or worker can instead run the same commands in its shell.
2. Record the build's and the start command's `id`, plus the start command's `Cap*`, `NoNewPrivs`, `Seccomp`, `uid_map` and the source tree's owners.
3. Do the same on a native Node service (`exec node -e "require('http').createServer((q,s)=>s.end('ok')).listen(process.env.PORT)"`) and on a Python service (`exec python -m http.server $PORT`). This shows whether the identity is per runtime. Delete the services afterwards.
4. Record the result in [ADR089](../../../docs/ADR089-render-container-compatibility.md) § Privilege slice decisions item 6 and in `docs/render-artifacts/container-privileges.md`.

## Then

- **Render runs native services as root** (bex's identity today, uid 0): nothing changes. Close this note with the evidence.
- **Render runs them as a non-root user** (what the public evidence suggests): running bex's native services as that user is a stricter variant. It is a separate decision for the user (on Render, Passenger then never calls `initgroups`). File it as its own item; `render-v1` stays parity-sufficient either way.
