## Objective

Choose how bex-api learns that a command it started is still running after the client's stream ended, and record the choice in ADR014 D4. Render's rule: a sandbox is idle only when no command or file transfer is in progress, a disconnect does not stop a command, and background processes left by a finished command do not count.

## Context

- Today the only signal is the open stream: `holdActive` (`lego/backend/internal/sandbox/idle.go:206-240`) is released when `StreamExec`'s copy returns (`exec.go:319-352`), and `stopExecution` closes the history record then.
- Commands run under `pods/exec` without a TTY through the wrapper in `exec.go:101-122`, and survive a cut stream.
- The idle sweeper (`idle.go:485` `suspendIfIdle`) decides on `sandbox_activity.last_activity_at` only.

## Steps

1. Compare at least these options:
   - **(a) In-sandbox command registry.** The exec wrapper records each command's top-level PID (and later its exit code) under a bex-owned path, e.g. `/run/bex-exec/<execution-id>`. To do that, the wrapper runs the user's shell as a child and waits for it instead of `exec`ing it, keeping signal and exit-code passthrough. Before claiming a pause, the sweeper asks the sandbox whether any registered command is still alive.
   - **(b) A detached drain.** bex-api keeps reading the gateway stream after the client leaves, holding activity and recording the exit code. Account for the gateway session slots it holds, the 4 h session cap and bex-api restarts.
   - **(c)** Any OpenSandbox `execd` facility that tracks commands, if it exists at the pinned version.
2. Pick one, or a combination, that survives client disconnects, the 4 h gateway cap and bex-api/ssh-gateway restarts, and that ignores background processes of finished commands.
3. Say what the execution history reports for a command whose end bex could not observe, for example a sandbox that ended while it ran.
4. Record the decision, and what happens to sandboxes created before the change, in ADR014 D4.

## Done — 2026-11-14

Decision: (a), an in-sandbox command registry, recorded in ADR014 D4 ("Commands that outlive their stream").

- (b), a detached drain, covers only the disconnect: the 4 h cap and a restart of bex-api or ssh-gateway still cut the stream, and the drain holds a gateway slot for the rest of the command. (c) does not apply: bex runs commands through the gateway's own `pods/exec`, not `execd`.
- The wrapper keeps `bash -c` in `$HOME`, the `/bin/sh` fallback, the exit code and the stdout/stderr split. It runs the command as a foreground child so the command keeps SIGINT and SIGQUIT. `TestARegisteredCommandRunsAsBeforeAndRecordsItsExit` and `TestARegisteredCommandKeepsSIGINT` check this, and the m348 tests still pass. All of them also pass in the `bash:5.3` base image (BusyBox `sh`, bash 5.3).
- What the history reports when bex cannot learn a command's end: a paused or ended sandbox is not probed, so its open records end at their last refresh with no exit code, as before. A registry that cannot be read keeps the sandbox up for at most an hour.
- Older sandboxes: the wrapper travels in each exec's argv, so every command started after the deploy is registered.
