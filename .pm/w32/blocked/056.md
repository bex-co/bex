# With the released `bex` CLI, an image service switched from a native runtime cannot switch back to Git

Why: since w32/052, `bex services update <id> --repo … --branch …` on such a service answers `400 native runtime node requires buildCommand and startCommand`, and the pinned Render CLI refuses to send the commands with the switch. A CLI user has no route back to Git; only the dashboard, REST, GraphQL and MCP have one.

- **Severity / estimate:** minor, ~1h. The switch between a build and a prebuilt image is a bex extension (ADR018's Runtime row: Render's docs do not say whether a service can switch).
- **Seen:** w32/052's production walk, 2026-11-20, pin `3e53abbe3bc3`, `bex-canary`, released `bex` v0.7.0 (Render CLI v2.36.0). Record: `.pm/w32/done/052.md`, § Gate walk, step 4.
  - A native `node` web service switched to `docker.io/library/nginx:alpine` with `bex services update <id> --image …` reads `runtime: image`, with no build or start command (w8/m461 drops them).
  - `bex services update <id> --repo https://github.com/bex-co/bex --branch main` exits 1 with `received response code 400: bad request: native runtime node requires buildCommand and startCommand` (w32/052's refusal, as designed).
  - `bex services update <id> --repo … --branch main --build-command A --start-command B` exits 1 with `--build-command and --start-command are only supported for native runtimes`, before any request. The pinned client reads the current runtime (`image`) and calls `buildImageUpdateEnvSpecificDetails` (`render-oss/cli` `pkg/service/update.go:393-396`). It also refuses `--runtime` on update (`servicetypes.ErrRuntimeUpdateNotSupported`, `update.go:21-22`).
  - The same switch through REST `PATCH` (`repo`, `branch` and `serviceDetails.envSpecificDetails.{buildCommand,startCommand}`) and through GraphQL `setRepo` with both commands each saved, and each deploy went `live` with `200`.
  - Before w32/052, the CLI switched back in two updates: `--repo` saved with empty commands and `runtime: node`, and then `--build-command` and `--start-command` were accepted.
- **Cause:** the switch to an image drops the native commands but keeps the runtime, builder and root directory for a switch back (ADR004, the w8/m461 paragraph). The switch back then has to carry the commands, and the pinned client cannot send them to a service that reads as an image.
- **Options (pick the one that keeps every surface consistent):**
  1. Keep the native build and start commands that the switch to an image drops, somewhere the image service does not run them (not `spec.startCommand`, which w8/m461 shows is the Docker Command). Restore them on a switch back that sends none. `--repo` alone then saves a service that builds, and a switch back that sends commands still overrides them.
  2. Have the bex launcher (`lego/cli`) send one `PATCH` with the repo and the commands when the service reads `image` and `--repo` comes with `--build-command` / `--start-command`. This diverges from the pinned client's own validation, so prefer option 1.
- **Check Render first:** whether Render's API or CLI lets an image-backed service become Git-backed at all. If it does not, record that in ADR018's Runtime row, and still keep the bex extension usable from the CLI.

## Acceptance

- With the released CLI, an image service switched from native switches back to Git with `bex services update <id> --repo … --branch …` (option 1), and its next `bex deploys create --wait` goes `live`. A switch back with no kept commands and none sent still answers create's 400.
- Backend tests cover the switch out and back on REST, GraphQL and MCP. The w32/052 refusal tests still pass.
- ADR004's w32/052 paragraph and ADR018's Runtime row describe the CLI route.

## Shipped (2026-11-21) — parked for the production walk

- **Render first:** Render's API changes a service's backing repo or image, and since 2026-05-11 so does its dashboard: Settings → Build → Source → Edit opens an Update Source dialog, and for a Git repo it asks to confirm the runtime, build command and start command ([changelog](https://render.com/changelog/change-your-services-backing-repo-or-image-in-the-render-dashboard), read 2026-11-21). [deploying-an-image](https://render.com/docs/deploying-an-image) still says nothing about switching. Render's own CLI has no route either: it refuses `--runtime` on every update (`ErrRuntimeUpdateNotSupported`: "use the API directly, or create a new service") and `--build-command` / `--start-command` on a service whose runtime reads `image`. Render's answer to a repo-only `PATCH` of an image service was not observed (no Render credential). Keeping the runtime and commands across the switch stays a bex extension, so the CLI route is option 1, on the server; option 2 (a launcher-side `PATCH`) would teach the launcher a workaround around the pinned client's own validation.
- **Triage:** the premise held on `64fb726f3`. `settleSourceSwitch` dropped the native commands on the switch to an image (w8/m461) and kept nothing, and `checkNativeCommandsKept` refused the switch back without them (w32/052).
- **Code:** `92931a92f` (bex-api only).
  - The source writer (`sourceFields.applyTo`, shared by REST `PATCH`, GraphQL `setImage` / `setRepo` and MCP `update_service`) keeps what a switch to an image drops from a build of the service's own (`keepSwitchBackCommands`): a native build's build and start commands, a buildpack build's start command, a native cron's command. They live in the App annotations `app.bex.co/switch-back-build-command` and `app.bex.co/switch-back-start-command`, which only bex-api reads: `spec.startCommand` is the image's Docker Command.
  - A switch back to the repo writes them back before any command the same update sends, which wins. The kept start command replaces a Docker Command saved on the image.
  - A change of image keeps them. A switch back, a link to a build source and a Blueprint sync that moves the service off the image forget them. A switch from a Dockerfile build or a build source link keeps nothing. A switch back with nothing kept and none sent still gets create's 400.
- **Tests:**
  - `lego/cli/switched_image_switch_back_contract_test.go` drives the pinned client against the switched service's read (`testdata/switched-image-clone-source.json`) and records its request for `--repo … --branch main` in `testdata/switched-image-switch-back-request.json`: `repo` and `branch` only. It also pins the client's refusal of both commands and of `--runtime`, so a pin bump that starts sending them fails there.
  - `TestSwitchingBackToANativeRepoRestoresItsCommands` replays that body on REST, and the same switch through GraphQL `setRepo` and MCP `update_service`, on a web, private, worker and cron service; each builds with its kept commands and keeps nothing afterwards. Commands sent with the switch back win on every surface.
  - `TestKeptCommandsFollowTheImageService` (an image change keeps them, a Docker Command gives way, clearing one in the switch back is refused), `TestSwitchingBackWithNothingKeptNeedsItsCommands` (w32/052's refusal on every surface, then the save with both commands), `TestLinkingABuildSourceForgetsKeptCommands`, `TestBlueprintSyncOffTheImageForgetsKeptCommands`, and the kept column of `TestSourceSwitchToImageAcrossCallersTypesAndSources` (every source kind, type and caller). The w32/052 clear tests pass unchanged.
  - Each part was reverted in turn (no restore, no keep, Docker Command kept, link keeps, Blueprint keeps, image change forgets), and each made at least one of these fail. The backend real-DB suite (ship gate), the `lego/cli` suite, and golangci-lint on both modules pass.
