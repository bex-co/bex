# `bex sandboxes cp <sbx>:. ./sandbox-home`, the CLI's own help example, is refused: the home directory itself is not an accepted path

Why: the pinned CLI's `sandboxes copy --help` lists `bex sandboxes cp sbx-abc123:. ./sandbox-home` as an example. It also says "A relative sandbox path resolves inside the sandbox's home directory", so `.` is the home directory. On bex that example fails with a message that calls `.` unclean, and there is no other path that downloads the whole home directory.

- **Seen:** `/qa-find-bugs-cli` loop sweep 6c54, 2026-11-13 ~13:51 UTC, `bex-canary` (`tea-daif693dqjvc73e7as3g`), release `bex` v0.5.0 (Render CLI v2.35.0 pin), human device login, `https://api.bex.co/v1/`, production pin `5de3d5bcce8e`, sandbox `sbx-dbrh980k58is73auo4s0` (since terminated).

  ```text
  $ bex sandboxes cp sbx-dbrh980k58is73auo4s0:. ./sandbox-home
  Error: received response code 400: bad request: sandbox path must be a clean non-root path (absolute, or relative to the home directory without '..'), at most 4096 bytes and 64 levels, without control characters
  (exit 1, 0.31 s; nothing written locally)
  $ bex sandboxes copy sbx-dbrh980k58is73auo4s0:up-plain ./x      # control: a directory under home
  Downloaded sbx-dbrh980k58is73auo4s0:up-plain to ./x
  ```

  Rechecked on pin `1c4d721bc8dc` (2026-11-13 16:45 UTC, `sbx-dbrjt7tgh3vs73b14cmg`): the same `400`.

- **Contract:**
  - The pinned client sends `path=.` unchanged. The help example is in `cmd/sandboxcopy.go:79` at pin `4fd34231b637`; bex's help prints it with the `bex` name.
  - The Render SDK resolves a relative remote path "under the sandbox's home directory … as scp does" (SDK v1.8.0 `copy_to`, quoted in w32/m299), after `posixpath.normpath`, which leaves `.` as `.`.
- **Cause (traced at `ae142a062`):**
  - `sandboxfiles.ValidatePath` (`lego/backend/internal/sandboxfiles/ticket.go:142-151`) refuses `value == "."` next to `""`, `/` and `..`.
  - The mint route checks it through `validateFileConnectPath` (`lego/backend/internal/sandbox/file_connect.go:98-103`), so the refusal comes before any ticket exists.
  - w32/m299 made relative paths resolve under home, but never decided `.` itself. Its tests cover `.` only as the parent of a named entry.
- **Fix:**
  1. Accept `.` in `ValidatePath`, meaning the home directory. The download script already handles it: `cd_parent "."` enters the physically resolved `$HOME`, and `tar -cf - -C . .` archives it.
  2. An upload to `.` names an existing directory, so it keeps the existing refusal for any existing directory destination (`stageScript` exit 73 → 409 "sandbox destination exists"). That is consistent with the no-merge rule, not a new one.
  3. Update `bexServerPolicy.paths` in `lego/cli/testdata/sandbox-file-contract.json` and the paths paragraph of `docs/render-artifacts/ea-sandbox.md`.
- **Acceptance:** in `bex-canary`, `bex sandboxes cp <sbx>:. ./sandbox-home` downloads the home directory, so a file written with `exec -- bash -c 'echo hi > ~/f'` reads `hi` locally. `bex sandboxes copy ./d <sbx>:.` is refused as an existing destination. `..`, `/` and `../x` are still refused. A `ticket_test.go` row and a `shell_test.go` run of the real download script cover `.`.
- **Note:** until w32/m380 ships, a home directory that contains any symlink or hard link (a virtualenv or `node_modules`, for example) still fails to download for that reason. The walk should use a home without links, or follow m380.
- **Dedupe:** no board item covers it. `rg` for `sandbox-home` and for a home-directory `.` path over `.pm` matches only w32/m299's tests, where `.` is the parent of a named entry.
- Minor. ~30m.
