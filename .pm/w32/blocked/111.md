# `bex restart <dpg-id>` (and `POST /v1/postgres/{id}/restart`, GraphQL `restartDatabase`, MCP `restart_postgres`) returns `202` ("restarted successfully") on a suspended Postgres database instead of `409 Conflict`

Why: A suspended Postgres database has its CNPG cluster hibernated with zero running pods; reporting `"restarted successfully"` while mutating `spec.restartedAt`, stamping `cnpg.io/restartedAt` onto the hibernated cluster, and recording a `postgres_restarted` effect misleads CLI/API/MCP/dashboard callers and diverges from suspended-service restarts (`409 Conflict`) and suspended-Postgres exports (`409 Conflict`).

- **Attribution:** server
- **Root cause:**
  - `lego/backend/internal/postgres/lifecycle.go:76-90` (`Service.Restart`): calls `fetchLiveDatabase`, then immediately runs `s.patchDatabaseObj` to write `d.Spec.RestartedAt = s.Now().UTC().Format(time.RFC3339)` and calls `s.RecordDatabaseEffect(ctx, d, core.DatabaseRestarted)` without checking `d.Spec.Suspended` (or `s.RequireBillingMutation`).
  - Operator side (`lego/operator/internal/controller/database_controller.go:1971-1983`, `setLifecycleAnnotations`): unconditionally stamps `cnpg.io/restartedAt` alongside `cnpg.io/hibernation: on` on the hibernated CNPG Cluster when `db.Spec.RestartedAt != ""`.
  - Sibling `Service.Failover` (`lego/backend/internal/postgres/lifecycle.go:97-113`): also omits `if d.Spec.Suspended` (and fetches `d` twice via `fetchLiveDatabase` at `:102` and `patchDatabase` at `:109`).
  - Sibling `Service.ActionCapabilities` (`lego/backend/internal/postgres/actioncaps.go:71`): emits `core.DecideAction(core.ActionRestart, operate, "")` with an empty precondition even when `d.Spec.Suspended == true` (compare `deploys/actioncaps.go:255` and `apps/actioncaps.go:105`, which report `core.PrecondSuspended`).
  - Sibling `Service.setSuspended` (`lego/backend/internal/postgres/lifecycle.go:65-67`): returns `pgView(d)` instead of `s.view(d)` on the idempotent no-op branch, dropping `Region` and `DashboardURL` on GraphQL `suspendDatabase`/`resumeDatabase` and MCP `suspend_postgres`/`resume_postgres`.
  - Pinned consumer: `github.com/render-oss/cli` `cmd/restart.go:45` → `pkg/tui/views/restartview.go:60` → `pkg/postgres/repo.go:90-97` calls `POST /v1/postgres/{id}/restart` via `RestartPostgres` (raw `*http.Response`) instead of `RestartPostgresWithResponse`, so `client.ErrorFromResponse` (`pkg/client/client.go:176-186`) returns `nil` for every HTTP error status (`401`/`403`/`404`/`409`/`500`) — `bex restart <dpg-id>` silently swallows `409` and exits `0` at pinned Render CLI `v2.38.0` (upstream defect graded in `w32/113` and `docs/cli-compatibility-checklist.md`), whereas raw REST `POST /v1/postgres/{id}/restart`, GraphQL `restartDatabase`, and MCP `restart_postgres` surface the server's `409 Conflict`.
- **Fix:**
  1. In `lego/backend/internal/postgres/lifecycle.go`:
     - In `Service.Restart` (`:76-90`): after `fetchLiveDatabase`, return `fmt.Errorf("%w: Postgres %q is suspended; resume it before restarting", core.ErrConflict, name)` when `d.Spec.Suspended` is true (before `patchDatabaseObj` and `RecordDatabaseEffect`), and check `s.RequireBillingMutation(ctx, d.Labels[core.LabelTenant])` consistent with `deploys.Service.restart` (`deploys/service.go:715`) and `postgres.Service.setSuspended` resume (`lifecycle.go:60`).
     - In `Service.Failover` (`:97-113`): reject `d.Spec.Suspended` with `core.ErrConflict` (`Postgres %q is suspended; resume it before failing over`) before patching, and reuse the already-fetched `d` via `s.patchDatabaseObj` instead of calling `s.patchDatabase` a second time.
     - In `Service.setSuspended` (`:65-67`): return `s.view(d)` instead of `pgView(d)` so idempotent GraphQL/MCP suspend/resume keeps `Region` and `DashboardURL`.
  2. In `lego/backend/internal/postgres/actioncaps.go:71`: compute `ActionRestart`'s precondition from `d.Spec.Suspended` (`core.PrecondSuspended`) and `BillingPreconditionFor` (matching `deploys/actioncaps.go:255-259` and `apps/actioncaps.go:105`), and verify `actioncaps_test.go` and dashboard/mobile consumers remain consistent.
