# A static site published without a build command reports a missing branch as `update_failed` (after `update_in_progress`); a repo build reports the same mistake as `build_failed`

Why: Render clones a static site's repo as the first step of its build, so a typo'd branch fails the build. On bex, a static site with no build command reports the clone as a rollout instead, so the deploy status says the source was fine and the update failed. A CLI user's `--wait` still exits 1, but anything that reads the status gets the wrong step: scripts, webhooks, the dashboard's "Build failed" filter. The same mistake on a web service already reads `build_failed`.

- **Seen:** `/qa-find-bugs-cli` sweep 37 (nonce b97f), 2026-11-15 06:47–06:51 UTC, release `bex` v0.6.0 (Render CLI v2.36.0 pin), production pin `89ac87445bec`, `bex-canary`, human device login. Both fixtures are deleted.

  ```text
  # static site, no build command (direct publish, w9/010), branch that does not exist
  $ bex services create --name qa-20261115-b97f-branch --type static_site --repo https://github.com/bex-co/bex \
      --branch no-such-branch-b97f --root-directory examples/static-site --publish-directory . -o json   → srv-dbslb8moou4c73fdrg00
  deploys list: created → update_in_progress (06:48:37) → update_failed (06:48:48)
  build log: ==> Building from https://github.com/bex-co/bex@no-such-branch-b97f
             ==> Deploy failed: clone: could not fetch "no-such-branch-b97f" from this service's repository — check that the branch
                 or commit exists and that bex still has access to the repo (exit 128)

  # control: Docker web service, same repo and branch
  $ bex services create --name qa-20261115-b97f-webbr --type web_service --repo https://github.com/bex-co/bex \
      --branch no-such-branch-b97f --root-directory examples/hello-go --runtime docker --plan free -o json   → srv-dbslbqldergc73ccgi40
  deploys list: created → queued → build_failed (06:50:29)
  build log: ==> Build failed: build failed in the source checkout step:  ==> fatal: couldn't find remote ref no-such-branch-b97f
  ```

- **Cause (traced at `fe5a7dcd4`, the deployed pin's code; line numbers refreshed at `48c93ceed`):**
  - A direct static publish (`directStaticPublish`, `lego/operator/internal/controller/app_controller.go:1734`) never builds. `publishStaticRevision` sets `PhaseDeploying` "Publishing" (`:4740`, `:4798`), which bex-api reads as `update_in_progress` (`backend/internal/store/reconciler.go` phase switch). The clone runs inside the publish Job.
  - When the Job fails, `failureMessage` → `failedContainerDetail` (`lego/operator/internal/publish/publish.go`) marks `UserError` only for exit `userSourceExit` (66). That code is used for a missing publish directory (w4/493), which closes `build_failed`.
  - The clone step exits 128 for a ref that does not exist, so the failure goes through `failPublish` (`app_controller.go`, "publication is a rollout of the static release, not a build", w4/m155) and the row closes `update_failed`.
  - A repo build classifies the same git exit as a tenant build failure (w7/m82), hence `build_failed` for the web service.
- **Fix:**
  1. On the direct-publish path, the clone step's tenant-source failures exit `userSourceExit`, so the row closes `build_failed` as a missing publish directory does. Those are an unknown branch or commit, and a repository bex cannot read. Platform faults stay as they are: upload, store and credential relocation.
  2. While a direct publish clones and stages, report `build_in_progress` (`PhaseBuilding` with a build-running reason), not `update_in_progress`. Render's static deploy is one build step from clone to "Your site is live". Keep `update_*` for the upload, or drop it if Render has no such phase for static sites; check Render's static deploy statuses.
- **Acceptance (production, release CLI, `bex-canary`):**
  - The static command above reads `build_in_progress` while it runs and ends `build_failed`, with the same clone message.
  - The Docker control is unchanged (`build_failed`).
  - A good direct-publish static site still goes `live`, and a missing publish directory still ends `build_failed` (w4/493).
  - An operator test covers a clone-mode publish with exit 128 for a missing ref.
- **Unverified:** Render's exact status sequence for a static site with no build command whose branch is missing. Render's docs put the clone in the build ("==> Cloning from …" is the build log's first line), but this run did not observe Render itself. Also unverified: whether any other publish-step exit should count as the tenant's.
- **Dedupe:**
  - `rg -n -i 'direct (static )?publish|clone.*update_failed' .pm` finds no open item.
  - w4/493 (done) did this for the missing publish directory, w4/m155 (done) made publication a rollout, and w7/m82 (done) attributes clone exit 128 to the tenant on the build plane.
  - Not deploy lag: unchanged on `origin/main`.
- Minor (wrong status vocabulary on a common mistake; the message is right). ~45m.

## Shipped (2026-11-15, `21728df75`)

- **Fix 1:** the direct publish's clone script exits `userSourceExit` (66) when `git fetch` fails, for the parent and for a submodule, so the deploy closes `build_failed` with the clone's own sentence (no `clone:` prefix, no exit code). A clone killed or failing elsewhere (checkout, staging copy) and every upload or store fault stay rollout failures.
- **Fix 2:** `publish.Ensure` places an in-flight direct publish: waiting until a pod is on a node, cloning until a pod's clone step exits 0, then publishing. The operator reports `BuildQueued`, `Building` and then `Deploying`/`Publishing`, which bex-api reads as `queued`, `build_in_progress` and `update_in_progress`. `update_*` is kept for the upload, as for a built site's publish. Render's API documents the same eleven statuses for every service type and does not say which a static site visits ([deploys](https://render.com/docs/deploys): "As soon as a build succeeds, we deploy it"). An extract (built site) and a rollback publish are unchanged. Recorded in [ADR029](../../../docs/ADR029-static-sites.md).
- **Tests:** `TestDirectPublishOfAnUnfetchableRefIsAUserSourceError` runs the real clone script against a local repository: a missing branch, a missing commit and an unreadable repository each exit 66. With the fix reverted they exit 128. `TestDirectPublishReportsItsCloneStep` covers the three in-flight phases. The envtest "a direct static publish (w32/028)" walks a first publish through `BuildQueued` → `Building` → `Publishing` → Running, and then a replacement on a missing branch to a `BuildFailedUserError` Build verdict while the served release keeps serving. It fails with the phase change reverted. `make test` passes.
