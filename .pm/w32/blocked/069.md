# `bex ea blueprints create` saves `autoSync: true` for a repo whose pushes bex never receives; the same Blueprint then refuses `--auto-sync=true`

Why: a Blueprint created with the pinned CLI from a public repository reads `autoSync: true` and `in_sync`, so its owner expects pushes to sync it, but bex never receives those pushes and nothing ever syncs. w10/m375 t003 fixed this for the dashboard's create, the preview and the deploy-time upsert, but not for the Render-shaped create the CLI, REST, GraphQL `createPlannedBlueprint` and MCP `create_blueprint` use.

- Severity: major. Nothing is lost, but the Blueprint says it will follow pushes and it never will. The preview of the same repository says `autoSync: false`, and turning auto-sync on later is refused for this repo.
- Versions: released `bex` v0.9.0 (`bex-0.9.0-linux-arm64`, sha256 `714f4e1a…` as in the release's `checksums.txt`), upstream pin v2.36.0 `4fd34231b637`. Production gitops pin `cce6c749f6ff`. The live `bex-api` digest read on the control plane is `sha256:e14f8ee4…`, the pin's own. The only change to these files since that pin is `667d4f7dc` (disk shutdown delay), which does not touch this path. The code below is from `main` `7b9140a6a`.
- Context: cli-qa routine run `0cd3ca`, 2026-11-21 15:19–15:32 UTC, `https://api.bex.co`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login, `-o json`, non-TTY.

## Repro

`render-examples/go-web-server` is public, its default branch is `master`, and its `render.yaml` declares one free Go web service with no `repo` or `branch`. The workspace's GitHub App does not cover it.

```sh
bex ea blueprints create --repo https://github.com/render-examples/go-web-server --name qa-<nonce>-bp -o json --confirm
# exit 0: blueprint exs-…, "branch": "master", "autoSync": true, "status": "created", planningOutcome "planned" (create service go-rima)
bex ea blueprints approve exs-… -o json --confirm
# exit 0: sync state "success"; service srv-… "go-rima" built master@589deed and served 200 at https://go-rima.onbex.co
curl -s -H "Authorization: Bearer <token>" https://api.bex.co/v1/blueprints/exs-…
# 200 … "autoSync":true, … "status":"in_sync"
bex ea blueprints update exs-… --auto-sync=false -o json --confirm   # exit 0, "status": "paused"
bex ea blueprints update exs-… --auto-sync=true -o json --confirm
# exit 1: Error: received response code 400: bad request: autoSync needs a connected Git provider: bex doesn't receive this repo's pushes. Sync the Blueprint manually, or connect the repo through the GitHub app
```

The same body over REST, which is what the pinned client sends (`pkg/blueprint/service.go` `buildCreateRequest` always sets `autoSync`, `true` unless `--auto-sync=false`):

```text
POST /v1/blueprints
{"ownerId":"tea-daif693dqjvc73e7as3g","name":"qa-20261121-0cd3ca-wiret","source":{"repo":"https://github.com/render-examples/go-web-server","path":"render.yaml"},"autoSync":true,"existingResources":"create_new"}
→ 201, blueprint {"branch":"master","autoSync":true,"status":"created"}, planningOutcome "planned", notices []
```

With `autoSync` left out (MCP `create_blueprint` without it) the answer is the same, `autoSync: true`. The control is the dashboard's own review of the same repository, GraphQL `blueprintPreview(repo: "https://github.com/render-examples/go-web-server", existingResources: "create_new")`. It answers `{"autoSync":false,"branch":"master","found":true}`, and the dashboard's create stores `autoSync: false`. All fixtures were deleted: both REST Blueprints, the CLI Blueprint and `srv-dc0rd3gn82tc73dukv70` each answer `GET` 404. The workspace's four baseline resources are unchanged.

## Cause

`CreatePlannedBlueprint` (`lego/backend/internal/apps/blueprint_onboarding.go:220-223`) sets `autoSync := true` and takes the request's value when one is sent. It never asks `repoPushesUnreachable` (`pushdelivery.go:189`). The other paths all ask it:

- the legacy `CreateBlueprint` (`blueprint.go:1471`);
- the preview (`blueprint.go:1252`);
- the deploy-time upsert (`blueprint.go:2280`);
- `UpdateBlueprint`'s refusal (`blueprint.go:2096`, `errAutoSyncUnreachable`).

w10/m375 t003 added those checks on 2026-11-14 and named only `CreateBlueprint` and the upsert. `TestBlueprintOnAnUnreachableRepoIsCreatedWithoutAutoSync` (`blueprint_autosync_reach_test.go:31`) covers the preview, the legacy create and update, but not the planned create.

## Fix

- In `CreatePlannedBlueprint`, when `s.repoPushesUnreachable(ctx, tenantID, req.Source.Repo)` is true, store `autoSync: false`, so approval settles the Blueprint `paused` as the legacy create's does.
- When the request sent `autoSync: true`, also answer a `warning` notice in the create's `notices`, worded like `errAutoSyncUnreachable`. For example: "auto-sync is off: bex doesn't receive this repository's pushes. Sync the Blueprint manually, or connect the repo through the GitHub app". The pinned CLI prints notices (`pkg/text/blueprint.go` `writePlanningResult`).
- Do not answer 400. Refusing an explicit `true`, as update does, would fail the CLI's default `ea blueprints create --repo <public url>`, which always sends `true`. That stricter variant is a separate decision.
- Surfaces: REST `POST /v1/blueprints` with `source`, GraphQL `createPlannedBlueprint` and MCP `create_blueprint` all reach `CreatePlannedBlueprint`, so one change covers them. The dashboard uses the legacy `createBlueprint`, which is already right.

## Acceptance

- A unit test next to `TestBlueprintOnAnUnreachableRepoIsCreatedWithoutAutoSync` covers `CreatePlannedBlueprint`. An unreachable repo with `autoSync` omitted, and with `true`, is stored `false`. The `true` case carries the warning notice, and approval settles `paused`. A covered repo still stores `true` with no notice. The test fails with the check removed.
- On production after the pin carries the fix, the Repro's create reads `"autoSync": false` with the warning notice, and the Blueprint reads `paused` after approval. Delete everything by ID and check each `GET` answers 404.
- `docs/ADR049-render-yaml-parity.md` § Blueprint onboarding states the rule for the Render-shaped create, citing w10/m375 t003.
