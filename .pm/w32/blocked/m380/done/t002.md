## Objective

`bex sandboxes copy <sbx>:dir ./dir` succeeds when `dir` holds symlinks or hard links. Today any one of them fails the download.

The pinned client's `extractTar` already expects these entries:

- it restores `tar.TypeSymlink` inside an `os.Root`, which refuses any later write that escapes through a link;
- it restores `tar.TypeLink` entries, because "The sandbox's tar emits these for multiply-linked files";
- it skips devices and FIFOs.

## Context

- `download` (`lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go:509`) relays the sandbox's `tar -cf - -C "$name" .` (`downloadScript`, `:492-505`) through `copyArchive` (`:550`). That function refuses both link types (`:691-693`).
- BusyBox tar writes hard-link targets relative to the archive root (`./top.txt`). Its entry order is the directory's read order, so a link can come before or after its target's data.

## Steps

1. Use t001's rules on this path: pass symlinks through with their targets unchanged, and drop special entries.
2. Pass a hard link through when its cleaned `Linkname` names a regular file already emitted. Rewrite the link name to the same cleaned form as entry names.
3. If BusyBox can emit a hard link whose target has not been emitted yet, send the file's content as a regular entry instead of refusing. Test for that case.

## Done — 2026-11-14

- The download path uses the same `copyArchive` rule (one rule, both directions).
- `testdata/busybox-links.tar` is BusyBox v1.37.0's `tar -cf - -C dl .` of `top.txt`, `hard.txt` (a second link), `sub/inner.txt` and `sub/hard-inner.txt`, `rel-link`, `abs-link -> /etc/hostname`, `dirlink -> sub`, `dangling`, and a FIFO with two names. `TestABusyBoxTreeOfLinksDownloadsWithItsLinks` serves it through the real download handler and pins the gateway's output as `lego/cli/testdata/sandbox-download-links.tar`. `lego/cli` `TestPinnedSandboxDownloadRestoresLinks` has the pinned client's `Download` extract that file: every symlink reads back its target, both hard-link pairs are one inode, and neither FIFO name exists.
- Step 3: BusyBox archives the first name it reads for an inode with its data and each later name as a hard link to it, so a link never comes before its target (the fixture's `./top.txt -> ./hard.txt` follows `./hard.txt`). Nothing to fall back on. A hard link to a skipped FIFO (`./pipe -> ./pipe-hard`) is skipped; the pinned client would otherwise fail its `os.Root.Link`. BusyBox also writes a second name for a symlink as a hard link to it (`./rel-link-2 -> ./rel-link`), which the gateway sends as a copy of the symlink. A socket is skipped under both its names (`socket ignored`), so no hard link to one appears.
