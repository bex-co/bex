# An environment "Save and deploy" or an env-group deploy clears a saved build command, branch or root directory from `undeployedChanges`, though it reruns the serving build

Why: after an environment "Save and deploy" (or a deploy an environment group's write opens), the dashboard and GraphQL say a repo-backed web, private or worker service has no undeployed changes, while a build setting saved earlier and never built waits for the next deploy, the gap w32/058 closed for Restart and rollback.

- **Severity / estimate:** minor, ~1h.
- **Seen:** w32/058's worker, 2026-11-21, on `main` at `18667982a`, by reading the code. Not checked on production.
- **Cause:**
  - bex-api's environment "Save and deploy" (`lego/backend/internal/secrets/batch.go`, `selectServedBuild`) and every env-group write that deploys (`internal/envgroups/service.go`) call `rollout.Tracker.SelectServedBuild` (`internal/rollout/served_image.go`). For a source-built service that selects the serving release's image with no `sourceGeneration` (`SelectReleaseImage`), so the release reruns the serving build with the new environment instead of building.
  - The operator records that release like a standard one (`recordAdoptedRelease`, `release_config_snapshot.go`, skips only a selection with a `sourceGeneration`). `writeRuntimeConfigRecord` stamps its settings and build settings fingerprints from the saved spec, pending build command included. `servingConfigurationDiffers` then reads the pending build setting as deployed.
  - w32/058 made a Restart's or rollback's record copy its target's `BuildSettingsFingerprint` and name it in `SettingsFingerprint` (`selectedSettingsFingerprint`). This release kind has no target record to copy from, only the serving release whose image it reruns.
- **Expected:** Render's environment-variable page separates saving only, deploying the existing build with the saved variables, and rebuilding before the deploy ([render.com/docs/configure-environment-variables](https://render.com/docs/configure-environment-variables#setting-environment-variables), as ADR004 § Saved settings records). A deploy of the existing build runs none of a build setting saved since it was built, which applies at the next build. So a saved build setting the serving build was not made from reads `true` (`saved`) until a deploy builds it. "Save, rebuild, and deploy" builds and is not affected.
- **Fix direction:** when the operator adopts an image-only selection that reruns the serving build of a repo-backed service (`ref.Image` is the image the serving release's record runs), carry that record's `BuildSettingsFingerprint` and stamp `selectedSettingsFingerprint` with it, as `ensureSelectedReleaseConfig` does for a Restart. An image override of a prebuilt image is not this case (`image_override`). A serving record without build settings keeps today's comparison.
- **Acceptance:** with a native web service, `bex services update <id> --build-command '…'` (save only), then **Save and deploy** of one variable on the dashboard's Environment page: after the deploy is live with no build, GraphQL `undeployedChanges` / `undeployedChangesReason` read `true` / `saved`, and the next `bex deploys create <id> --wait` clears them. The same holds for an env-group link that deploys. Controls: the same steps with no pending save read `false`, and "Save, rebuild, and deploy" builds the saved command and reads `false`.
- **Dedupe:** w32/058 covers Restart and rollback (selections with a `sourceGeneration`). w32/048 made this release kind run the saved start command, which a rerun of the serving build can apply; a build setting it cannot. `rg -i 'served build|save and deploy' .pm` finds no open item on its build settings.

## Shipped (2026-11-21, `603158fca`)

- **Verdict:** work. The premise held on `main` at `a284f23fb`: `recordAdoptedRelease` wrote the rerun's record with the saved spec's settings and build settings fingerprints, and `servingConfigurationDiffers` read a pending build command as deployed. A unit repro and an envtest reproduced it.
- **Fix (`603158fca`):**
  - A rerun of the serving build (`servedBuildRerun`: an image-only selection with no `sourceGeneration` on a repo-backed service) copies the serving release's `BuildSettingsFingerprint` when that release's record runs the selected image (`rerunBuildSettings`). Its `SettingsFingerprint` names that build with the rerun's own settings (`selectedSettingsFingerprint`), as a Restart's does since w32/058. Both `recordAdoptedRelease` and every later `recordReleasePodTemplate` write carry it, and a rerun of a rerun keeps the first build's.
  - `buildSettingsFingerprint` no longer counts the start command and environment a native build also bakes in (`build-v1`). The rerun runs the saved start command (w32/048), variables, groups and secret files, and the settings fingerprint names those. Without this, the copy alone would have read a first variable, a group link or a saved start command as undeployed after every rerun of a native service.
  - `recordedSettingsMatch` also accepts the saved settings named on their own build, which is what an identical Restart or rerun records.
  - A serving record without build settings, with w32/058's artifact form of them (no production record has it: no pin carried `ef26ddb39`), or running another image keeps the saved comparison. So on production, only a service whose serving build was recorded by the new operator reads the fix: the walk below needs a fixture created after the pin.
- **Tests:**
  - `TestARerunOfTheServedBuildKeepsSavedBuildSettingsUndeployed` covers a native and a Dockerfile service. With nothing saved, a saved start command, a first variable or a group link the rerun reads `false`; with a saved build command, branch or root directory, or a group link and a saved build command, `true` / `saved`. The served build command put back reads `false`, through a rerun of the rerun too. Three served-record controls keep the saved comparison.
  - The envtest "An environment Save and deploy keeps a saved build setting undeployed (w32/060)" runs a native service: a first-variable Save and deploy (`false`), a saved build command then a Save and deploy (`true` / `saved`) and a group link (`true` / `saved`), the command put back (`false`), a saved start command then a Save and deploy (`false`), and a deploy that builds the saved command (`false`). No rerun dispatches a build.
  - Without the copy, 10 unit cases and the envtest fail. With the start command and environment kept in the build settings, 4 unit cases and the envtest fail. Without the new match, w32/058's identical cases fail. The operator suite (`make test`, the controller package 729 s) and `make lint` pass.
- **Docs:** ADR004 § Settings saves wait for a deploy, ADR013's rerun bullet and ADR018's env-var row.
- **Not changed:** `undeployedChangesApplying` during the rerun's rollout still reads `true` when a build setting is pending, since `inFlightCarriesSavedConfiguration` compares only the recorded fields. It is transient and reads `false` once the rerun serves.

  6. Put the build command back with `bex services update`. Pass: `false` / `""`.
  7. Save the step 3 command again and run `bex deploys create <id> --wait --confirm`. Pass: the build log echoes `w32060`, and the service reads `false` / `""`.
  8. Save another build command, then Save, rebuild, and deploy one variable (`saveMode: "rebuild"`). Pass: the build runs it, and the service reads `false` / `""`.
