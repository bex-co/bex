## Objective

Build a reproducible harness that installs the unmodified `render-oss/sdk` Python and TypeScript v1.8.0 releases and points them at a bex API base, and record which REST routes and wire formats the SDKs' sandbox clients use.

## Context

- Python: `Render(token=..., base_url=...)`, default `https://api.render.com` (`python/render/render.py:40`); sandbox client under `python/render/experimental/sandbox/` (`api.py`, `client.py`, `files.py`, `_tar.py`, `_wait.py`)
- SDK v1.8.0 changelog: sandbox names, `delete_group`, `set_default_group`, new error classes
- DO_NOT_DO: Render's own clients are clients to verify, never forked or vendored; gaps become bex-api work
- No artifacts in git (AGENTS.md): pin by version and sha256 in markdown, install at run time

## Steps

1. Write `scripts/render-sdk-compat.sh` (or a small test program under `lego/backend/...` testdata if it fits the existing CLI contract pattern) that installs pinned v1.8.0 into a scratch venv / node project and runs a scenario against `BEX_API_URL` with an API key from the environment.
2. Read the SDK source and list each sandbox method with its HTTP route, body and response shape, including file upload/download (tar streaming?) and exec streaming.
3. Diff that list against bex's served sandbox routes and `lego/cli/testdata/sandbox-exec-contract.json`.

## Files

- scripts/render-sdk-compat.sh
- docs/cli-compatibility-checklist.md (new SDK section skeleton)

## Acceptance criteria

- [ ] The harness runs both SDKs against a dev-N or production bex-api with only env configuration
- [ ] Every SDK sandbox method is mapped to its route and wire shape
