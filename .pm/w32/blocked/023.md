# A directory with more than 10,000 entries cannot be copied into or out of a sandbox; the download fails mid-stream without naming the cause

Why: Render documents no entry-count limit for sandbox file transfers. bex caps a directory archive at 10,000 entries in both directions, and real project trees routinely exceed that: a JavaScript project's `node_modules`, a Python `site-packages`, a `.git` directory. `bex sandboxes copy ./app <sbx>:app` is refused, and `bex sandboxes copy <sbx>:app ./app` streams part of the tree before it fails with a transport error that names no cause.

- **Seen:** `/qa-find-bugs-cli` loop sweep 23 (post-deploy walk), 2026-11-14 ~13:18–13:22 UTC, `bex-canary` (`tea-daif693dqjvc73e7as3g`), release `bex` v0.5.0 (Render CLI v2.35.0 pin), human device login, `https://api.bex.co/v1/`, production pin `c99e7815ebec`, sandbox `sbx-dbs5u6dv5sfs73boaipg` (since terminated).

  ```text
  # upload: 10,050 empty files, refused before anything is written (the cause is named)
  $ bex sandboxes copy ./many <sbx>:many
  Error: received response code 400: invalid or unsupported sandbox archive: too many entries      (exit 1, 8.4 s)

  # download: 10,050 empty files made in the sandbox with `seq 1 10050 | xargs touch`
  $ bex sandboxes copy <sbx>:big ./big
  Error: read archive: stream error: stream ID 3; INTERNAL_ERROR; received from peer                (exit 1, 2.6 s)
  ```

  One download ticket per request, minted as the pinned client does, fetched once with curl (token and URI query not printed):

  ```text
  GET <uri> --compressed (HTTP/1.1) → 200 Content-Type: application/x-tar, Content-Encoding: gzip; 69,632 B, then "transfer closed with outstanding read data remaining" (curl 18)
  GET <uri> --compressed (HTTP/2)   → 200 Content-Encoding: gzip; 69,632 B, then an HTTP/2 stream error (curl 92)
  GET <uri>              (HTTP/1.1) → 200 Content-Type: application/x-tar, Transfer-Encoding: chunked; 4,196,354 B, curl exit 0
  GET <uri>              (HTTP/2)   → 200 Content-Type: application/x-tar; 4,196,354 B, curl exit 0
  ```

  The last two bodies hold 8,196 of the tree's 10,051 entries and no end-of-archive marker. Python's `tarfile` reads all 8,196 without an error. A client that does not ask for gzip therefore gets a success-shaped, silently truncated archive. The pinned client is not exposed to that half: it asks for gzip and also checks the end-of-archive marker (`pkg/sandbox/files.go`, `terminatedReader`).

- **Render's contract:** render.com/docs/sandboxes-files and render.com/docs/sandboxes-limits (read 2026-11-14) state no file-count or entry-count limit, and no upload size limit. The only documented transfer bound is the SDKs' client-side download cap: "The SDK enforces a default file size limit of 256 MB", which "applies to the entire tar archive". The TypeScript SDK then "throws `SandboxDownloadTooLargeError` without returning a partial result". The rate limit is 1,000 upload or download requests per minute.
- **Cause (traced at `9b11f48d7`):**
  - `files.MaxArchiveEntries = 10_000` (`lego/backend/internal/sandboxfiles/ticket.go:39`). `copyArchive` (`lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go:712`) vets every directory archive in both directions and fails at entry 10,001 (`:727-729`).
  - An upload is vetted before anything is published, so it answers `400` with the cause.
  - A download streams through a buffering `gzip.Writer` (`:545-551`). By entry 10,001 the gateway has already sent compressed bytes, so it cannot answer the cause (`:575-579`) and aborts with `http.ErrAbortHandler` (`:585`). The CLI only sees the transport error.
  - The bound dates from the first copy path (w7/m150, whose README says "the original contract did not actually name numeric limits"). It is a bex choice, not Render's, and ADR018 has no row for it.
  - The silent truncation for a non-gzip client is not traced. The gateway always answers `Content-Encoding: gzip`, and an identity client sees an un-encoded body, so the edge decodes it. That decoded stream ends cleanly when the origin aborts.
- **Fix:**
  1. Remove the entry cap in both directions, as on Render. The 256 MiB wire and decoded bounds (`MaxTransferBytes`) stay. They already bound the gateway's per-archive bookkeeping (`seen` and `symlinks` in `copyArchive`), because every entry costs at least one 512-byte header. If a separate bound is still wanted for the maps, derive it from the byte bound so it never trips first.
  2. Update `docs/render-artifacts/ea-sandbox.md` (the "10,000 archive entries" bound), the `sandboxes copy` row in `docs/cli-compatibility-checklist.md`, `bexServerPolicy.maxArchiveEntries` in `lego/cli/testdata/sandbox-file-contract.json`, and ADR018's sandbox file-transfer row.
  3. Remaining bounds can still fail mid-stream: 256 MiB, five minutes, or a sandbox-side `tar` error. Make sure no client can read those as a complete archive. One option is `Cache-Control: no-transform` on the download, so the edge passes the gzip body through unchanged. Check the effect live with a non-gzip client and record it.
- **Acceptance:** in `bex-canary` with the release CLI:
  - Make 25,000 empty files with `seq 1 25000 | xargs touch`. `bex sandboxes copy <sbx>:big ./big` downloads them all, and `bex sandboxes copy ./big <sbx>:big2` uploads them, so `ls ~/big2 | wc -l` reads 25000.
  - A download cut by a remaining bound still fails in the CLI, and a non-gzip curl of the same ticket does not exit 0 with a partial archive.
  - `TestArchiveEntryPolicyAndBudgets` no longer refuses 10,001 entries, and a test pins the byte bound as the only archive-size limit.
- **Unverified:**
  - The edge mechanism behind the silent truncation (step 3 above).
  - Whether Render itself has an undocumented server-side entry or byte limit.
  - The byte cap on uploads is also undocumented on Render. It is left in place here because it guards gateway memory and time, and Render's SDK applies 256 MB to downloads.
- **Dedupe:** `rg -i 'MaxArchiveEntries|too many entries|10,000 (archive )?entries' .pm docs`. That finds w7/m150 (where the bound was set), w32/m380 t001 and t003 (which kept it, and expected an over-limit download to name its cause before streaming), and `ea-sandbox.md`. No open item covers it.
- Major. ~1h.

## Shipped 2026-11-14 (`/loopx w32`), parked on the production deploy

- **Shipped:** `d95b5130a`: `copyArchive` has no entry cap in either direction. Its index keys each name by a 128-bit maphash digest (about 60 B per entry), so the 256 MiB byte bound bounds it too; kept symlink targets are copied out of the PAX block and capped at 8 MiB. A download says `Cache-Control: no-store, no-transform`. Tests: `TestManyLinksAndSkippedEntriesAreCopied` (25,000 entries of every kind), `TestTheByteBoundIsAnArchivesOnlySizeLimit` (the stream runs to exactly 256 MiB, past 524k entries), `TestAHardLinkToASymlinkPastTheKeptTargetsIsRefused`. Docs, ADR018 (a new 🚧 row) and the CLI contract drop the cap.
- **Found during the fix:** `api.bex.co` sits behind Cloudflare (`server: cloudflare`, 2026-11-14), and bex-api asks the gateway for gzip and passes it through, so the edge that decoded the gzip for a non-gzip client was Cloudflare. Its docs say it can serve an origin's gzip "to visitors uncompressed" and that `no-transform` stops it altering the body (developers.cloudflare.com/speed/optimization/content/compression/, rules/compression-rules/, read 2026-11-14). They do not state the no-gzip-visitor case, so the walk's non-gzip curl settles it.
- **Follow-up filed:** [w32/025](025.md), a gateway-wide budget for archive indexes, which the `/simplify` review raised.
- **Gate:** production deploys are batched: `deploy.yml` deploys a push, or the hourly schedule once the pin is 6 h old. No user decision is needed. Once `git merge-base --is-ancestor d95b5130a <pinned sha>` holds, a worker runs the acceptance walk above with the released CLI in `bex-canary`.
