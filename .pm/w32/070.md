# `bex ea blueprints create` with no `--branch` answers a missing repository with an uncoded 400 in service-create wording; with `--branch` it is `repo_not_found_or_no_access`

Why: the same mistyped or private repository gets two different refusals depending on whether `--branch` was passed. Only one of them carries the Blueprint fetch `code` that scripts and the dashboard's review key on, so the create path disagrees with bex's own preview.

- Severity: minor. The create is refused either way and writes nothing. The wording and the missing `code` are what differ.
- Versions: released `bex` v0.9.0, upstream pin v2.36.0 `4fd34231b637`. Production pin `cce6c749f6ff`, live digest `sha256:e14f8ee4…`. No change to these lines since the pin; the code below is from `main` `7b9140a6a`.
- Context: cli-qa routine run `0cd3ca`, 2026-11-21 15:21–15:27 UTC, `https://api.bex.co`, workspace `bex-canary`, human device login, `-o json`, non-TTY. No Blueprint row was written by any case (list checked after each).

Every other create refusal in the same run is coded: `file_not_found` for no `render.yaml`, `file_not_found` for a bad `--path`, `branch_not_found`, and `BLUEPRINT_NAME_TAKEN`.

## Cause

With no `source.branch`, `CreatePlannedBlueprint` (`lego/backend/internal/apps/blueprint_onboarding.go:201-210`) asks `s.blueprintBranch` for the default branch. Any error other than `errBlueprintBranchRequired` is returned as it comes from `GitHub.ValidateRepo` (`blueprint.go:2722-2724`), the service create's uncoded `ErrBadRequest`. The legacy `CreateBlueprint` does the same at `blueprint.go:1389-1391`. The preview maps the same error through `blueprintBranchRefusal` (`blueprint.go:2739`), and a create with a branch goes through `blueprintCreateFetchError` (`blueprint.go:433`). Neither create maps it. w8/346 coded only the unsupported-host case (`RefuseBlueprintHost`).

## Fix

- In both creates, pass a failed default-branch lookup through `blueprintBranchRefusal(err, repo)`. When it classifies the error, answer the error `blueprintCreateFetchError` would give for that reason: `core.NewBadRequestError(reason, message, nil)`, or `core.NewUnavailableError` when `RetryableBlueprintFetch(reason)` holds (`rate_limited`, `unavailable`). One shared helper is enough.
- Leave `errBlueprintBranchRequired` falling back to `main`, as it does today.
- Surfaces: REST `POST /v1/blueprints` (both bodies), GraphQL `createPlannedBlueprint` and `createBlueprint`, and MCP `create_blueprint` reach the two creates. The preview is already right.

## Acceptance

- A unit test (beside `blueprint_host_wording_test.go`) shows a missing github.com repository and a missing gitlab.com repository, created with no branch, answer `400 repo_not_found_or_no_access` with the same message the preview gives, on both creates. A rate-limited lookup answers `503 rate_limited`. With a branch the answers are unchanged.
- On production after the pin carries it, the table's no-branch rows print `received response code 400 (repo_not_found_or_no_access): …`, the same text as the rows with `--branch`.
