# Switching a service's `--repo` or `--image` retroactively rewrites every historical deploy's `==> Building from <repo>@<sha>` build log line and its log ID

Why: `buildProgressLines` (`lego/backend/internal/logs/progress.go:422,438-479`) borrows `repo` and `branch` from the service's **current** `App.Spec` (`newProgressContext` at `:274-288`) instead of reading each deploy's own source, so updating a service's `--repo` (or switching it to a prebuilt `--image`) rewrites the `==> Building from …` line — and alters the deterministic `logID` — of every earlier deploy in history.

- **Severity / estimate:** **minor**, likely >1h (promote if so — needs a `deploys` migration + store/reconciler write + `DeployProgress` wiring + fallback for pre-migration rows). Switching a service's repository makes historical deploy logs claim past commits were built from the new repository (e.g. `https://github.com/expressjs/serve-static@a52d442`, a commit from `bex-co/bex` that does not exist in `serve-static`), and switching a Git service to a prebuilt image (`spec.Repo == ""`) turns every past Git build's `==> Build queued` / `==> Building from …` into `==> Deploy queued` / `==> Rolling out the current release`.
- **Versions:** released `bex` v0.9.0 (`bex-0.9.0-linux-arm64.tar.gz`, compatible with Render CLI `v2.36.0`, upstream pin `4fd34231b637`); repo checkout synced to `b0a4384d44` (`lego/cli` pinned to Render CLI `v2.37.0`, `11ef59f330dedec290f8d71d89b8f7379bbbed09`); `newProgressContext` and `buildProgressLines` are unchanged on `main` through `b0a4384d44`.
- **Context:** routine `cli-qa` sweep `8b71`, 2026-11-23 22:44–22:55 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login (`bex login`), non-TTY `-o json` / `-o text`.

## Attribution and root cause

- **Attribution:** server (`lego/backend/internal/store/`, `lego/backend/internal/deploys/`, `lego/backend/internal/logs/`).
- **Root cause:**
  - `store.Deploy` (`lego/backend/internal/store/store.go:396-455`) records per-deploy `Image`, `Commit`, `DetectedHTTPPort` (explicitly documented at `progress.go:65` as *"saved on this deploy, never borrowed from the current App"*), `LiveURLs`, `Rollout`, and `PreDeployRun`, but does **not** record the deploy's `Repo` or `Branch`.
  - `newProgressContext` (`lego/backend/internal/logs/progress.go:274-288`) copies `app.Spec.Repo` and `app.Spec.Branch` from the current `App` CR, and `buildProgressLines` (`progress.go:422,438-479`) uses `pc.repo` and `pc.branch` for **every** deploy row — including historical rows created before a `--repo`, `--branch`, or `--image` source switch.
  - Because `logID` hashes `(instance, timestamp, message)`, rewriting the message also mutates the historical log entry's `id`.

## Fix

- Record the deploy's `repo` and `branch` on the `deploys` row when a Git-backed deploy is created (new SQL migration adding nullable/empty-default `repo` and `branch` columns to `deploys`, wired through `store.Deploy`, deploy creation in `internal/deploys/`, and `DeployProgress` in `lego/backend/internal/api/server.go:1017-1050`).
- In `buildProgressLines` (`lego/backend/internal/logs/progress.go:421-480`): prefer `d.Repo` / `d.Branch` when recorded on the deploy row, falling back to `pc.repo` / `pc.branch` only for pre-migration rows where `d.Repo == ""` (while never rewriting a `d.Built == true` row with `d.Repo != ""` into `==> Deploy queued` / `==> Rolling out the current release` after the service switches to a prebuilt image).
- **Surfaces (REST/GraphQL/MCP/UI):** All log surfaces read `buildProgressLines`, so fixing `DeployProgress` + `buildProgressLines` keeps CLI, REST, GraphQL, MCP, and dashboard deploy logs immutable and consistent.

## Blast radius

- Touches `lego/backend/migrations/` (new highest-numbered migration), `lego/backend/internal/store/` (`Deploy` struct + SQL/memory queries), `lego/backend/internal/deploys/` (record `app.Spec.Repo`/`app.Spec.Branch` on deploy creation), `lego/backend/internal/api/server.go` (`DeployProgress` adapter), and `lego/backend/internal/logs/progress.go`.
- Preserve `store.Deploy`'s existing REST/GraphQL/MCP deploy DTOs (no extra unrequested public fields on `GET /v1/services/{id}/deploys`).
