# The sandbox test fake `fakeMeterStore` appends without a lock, so `-race` flags `TestParallelResumesNeverExceedTheLimit`

Why: `go test -race ./internal/sandbox/` fails on a data race in a test fake, not in product code. That hides real races (w32/059's handler race was found this way) behind a known failure.

- **Severity / estimate:** minor, test-only, ~20m.
- **Seen:** 2026-11-20, while w32/059's worker ran the sandbox package with `-race` against the CI-pinned deps. Neither CI nor `scripts/ship-gates.sh` runs `-race`, so no gate fails today.
- **Where:** `lego/backend/internal/sandbox/meter_test.go:121`. `fakeMeterStore.ObserveSandboxMeter` does `f.observations = append(f.observations, obs)` with no lock. `RecordResourceDisplayNames` (`:108`) and `TerminateMissingSandboxMeters` (`:125`) also write shared fields unguarded. The parallel resumes in `TestParallelResumesNeverExceedTheLimit` (`groups_test.go:569`) call into the fake concurrently.
- **Fix:** add a `sync.Mutex` to `fakeMeterStore`. Lock it in every method that reads or writes its fields, and in any test that reads `observations` while workers may still run.

## Acceptance

- `go test -race -count=20 ./internal/sandbox/` reports no data race against the CI-pinned deps (`scripts/backend-test-deps.sh`).
- No product code changes.
