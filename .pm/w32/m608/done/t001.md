## Objective

Add `repo` and `branch` columns to the `deploys` table and populate them when each Git-backed deploy row is created or promoted, so every deploy keeps its own source provenance independently of later `apps` source switches (`SetAppSource`).

## Context

- `store.Deploy` (`lego/backend/internal/store/store.go:396-480`) already stores per-deploy `Image`, `Commit`, `DetectedHTTPPort`, `LiveURLs`, `Rollout`, and `PreDeployRun`, with internal-only fields tagged `json:"-"` so public deploy DTOs stay unchanged.
- `deployColumns` and `scanDeploy` live at `lego/backend/internal/store/store.go:3667-3700`. The fake store is in `lego/backend/internal/store/fake_test.go`.
- Highest migration on `origin/main` as of promotion is `0341_build_source_deploy_scope`; re-check `origin/main` before numbering (likely `0342_deploy_source.{up,down}.sql`).
- Deploy creation and promotion paths in `lego/backend/internal/store/`:
  - `CreateApp` (`store.go:1436`) — has `a.Repo` and `a.Branch` in scope.
  - `insertDeploy` (`store.go:2867-2880`, used by `CreateDeploy`, `CreateRestartDeploy`, and `EnsureCheckedDeploy`) — runs in a transaction that already locks the `apps` row (`lockApp` via `prepareDeployCreate`), where `apps.repo` and `apps.branch` are stored (`SetAppSource` updates `apps` before opening a deploy).
  - `CreateDeferredDeploy` (`store.go:3057-3098`) and `promoteDeferredDeploy` (`store.go:3104-3130`) — a deferred deploy opens its real release when promoted, so `promoteDeferredDeploy` must record the source active for that promoted release.
  - `CreateRollbackDeploy` (`store.go:3421-3447`) — restores a built/previous image (`image` is set, no build runs); verify it does not claim an image-only deploy built from repo, or handle cleanly alongside `d.Image != ""` / `d.Built`.
  - `CreateAwaitingBuildDeploy` (`build_fanout.go:74-90`) and `promoteAwaitingBuildDeploy` (`build_fanout.go:235-274`) — linked services deploy a build source's artifact (`apps.repo` is NULL on linked services); carrier build rows go through `CreateDeploy`.
- Edge case to check carefully: an explicit image-override deploy (`POST /v1/services/{id}/deploys` with `imageUrl` on a repo-backed service, `deploys/service.go:1077-1084`) passes a non-empty `image` while `apps.repo` is non-empty. Decide clearly whether `deploys.repo`/`deploys.branch` should be empty when `d.Image != ""` (so an image-override deploy is explicitly not a repo build) or populated only when `d.Image == ""`, and verify how `CreateRestartDeploy` / config-change reuse deploys (`d.Image` set vs empty) behave.

## Steps

1. Re-check the highest migration number on `origin/main` (`ls lego/backend/internal/store/migrations/`). Add the next migration pair (`0342_deploy_source.up.sql` and `.down.sql`):
   - `ALTER TABLE deploys ADD COLUMN IF NOT EXISTS repo TEXT NOT NULL DEFAULT '';`
   - `ALTER TABLE deploys ADD COLUMN IF NOT EXISTS branch TEXT NOT NULL DEFAULT '';`
   - Comment citing `w32/m608` and explaining that empty strings on pre-migration rows fall back to the App's current source.
2. Add `Repo string \`json:"-"\`` and `Branch string \`json:"-"\`` to `store.Deploy`, and include `repo, branch` in `deployColumns` and `scanDeploy`.
3. Populate `repo` and `branch` on deploy creation/promotion in `PGStore` (`CreateApp`, `insertDeploy`, `promoteDeferredDeploy`, `promoteAwaitingBuildDeploy`, and check `CreateRollbackDeploy`/`CreateDeferredDeploy`/`CreateAwaitingBuildDeploy`) and mirror the behavior in `fake_test.go` (`memStore`). Confirm that `SetAppSource` updates `apps.repo`/`apps.branch` before every source-switch deploy is opened, so reading the locked `apps` row (when `d.Image == ""`) captures the exact source for that deploy — or pass it explicitly if any caller writes the App CR before `apps`.
4. Verify no public REST/GraphQL/MCP deploy DTO gains new fields (`json:"-"`).
5. Add unit and real-Postgres tests (`lego/backend/internal/store/`) proving:
   - Initial (`CreateApp`), `CreateDeploy`, `EnsureCheckedDeploy`, and promoted deferred deploys record `repo` and `branch`.
   - Calling `SetAppSource` to switch repo, switch branch, or switch to a prebuilt image does not mutate earlier deploy rows, and the next deploy records the new source (or empty for prebuilt image).
   - An image-override deploy on a repo-backed service records empty `repo`/`branch` (or matches the chosen invariant cleanly).
   - Pre-migration rows with empty `repo`/`branch` scan cleanly.
