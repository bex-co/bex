# `bex services update` with both `--repo` and `--image` silently discards `--repo` and switches the service to `--image` instead of returning `400`

Why: `repo` and `image` are mutually exclusive service sources across create, Blueprints, and build-sources; silently letting `image` clobber `repo` on `PATCH /v1/services/{id}` (and MCP `update_service`) turns a conflicting CLI/API command into an unintended source-kind switch with exit `0`.

### `bex services update <svc> --repo <url> --image <img-ref>` accepts both sources and silently switches to `--image`

- **Severity:** major
- **Versions:** released `bex v0.9.0` (`bex-0.9.0-linux-arm64.tar.gz`, sha256 `714f4e1a…`, pinned Render CLI `v2.36.0`) and checkout build of `lego/cli` at `96a3ab81e5` (Render CLI `v2.37.0`, commit `11ef59f330de`); production pin `f46c44d9ddb1` (`eb52a59622`)
- **Context:** 2026-11-24 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login (`scripts/qa-login.sh --login-challenge`), non-TTY `-o json --confirm`
- **Repro:**

  ```bash
  SVC=$(BEX_WORKSPACE=tea-daif693dqjvc73e7as3g bex services create \
    --name qa-20261124-ba2d-repro --type web_service --runtime docker \
    --repo https://github.com/bex-co/bex --branch main --root-directory examples/hello-go \
    --plan free --auto-deploy=false --confirm -o json | jq -r '.id')

  # Pass mutually exclusive --repo and --image together (reproduces on both v0.9.0 and HEAD v2.37.0)
  BEX_WORKSPACE=tea-daif693dqjvc73e7as3g bex services update "$SVC" \
    --repo https://github.com/render-examples/go-web-server \
    --image docker.io/library/nginx:1.27-alpine \
    --confirm -o json
  ```

- **Expected / actual:**
  - **Expected:** Matching `POST /v1/services` (`validateCreateSource` in `lego/backend/internal/apps/service.go:3794-3800` → `errPrebuiltImageField("repo")`: `"a service cannot declare both image and repo; remove repo or deploy from repo instead"`), Blueprint validation (`blueprint_compiler.go:459-461`), `build-sources` (`build_sources.go:611`), and the pinned CLI's own `services create` (`pkg/types/service/servicecreate.go:94`: `"cannot specify both --repo and --image"`), `PATCH /v1/services/{id}` (and `ApplyServicePatch` / `SetSourceAndRegistryCredential`) refuses a request that supplies both `repo` and `image` with `HTTP 400` and leaves the service untouched.
  - **Actual:**
    - On released `bex v0.9.0` (`srv-dc2h7nha05ic738s5m9g` and `srv-dc2h941npn2c73ckvfp0`) and checkout `bex` at `96a3ab81e5` (`srv-dc2h941npn2c73ckvfp0`), `bex services update` exited `0` (`HTTP 200`), silently discarded `--repo https://github.com/render-examples/go-web-server`, cleared the service's Git repo, and switched the service to the prebuilt image:
      `{"id":"srv-dc2h941npn2c73ckvfp0","repo":null,"branch":null,"imagePath":"docker.io/library/nginx:1.27-alpine","runtime":"image"}`.
- **Wire evidence:**
  - Pinned CLI (`pkg/service/update.go:30-49`, `pkg/types/service/serviceupdate.go:98-121`) sends `PATCH /v1/services/{id}` with `{"repo":"https://github.com/render-examples/go-web-server","image":{"imagePath":"docker.io/library/nginx:1.27-alpine","ownerId":""}}`.
  - Server returned `HTTP 200 OK` with `"repo":null,"branch":null,"imagePath":"docker.io/library/nginx:1.27-alpine","serviceDetails":{"runtime":"image",…}`.
- **Runtime evidence:** Disposable fixtures `srv-dc2h7nha05ic738s5m9g` and `srv-dc2h941npn2c73ckvfp0` were created in `bex-canary` and deleted after reproduction (`HTTP 404` verified on `GET /v1/services/srv-dc2h941npn2c73ckvfp0`).
- **Attribution:** server
- **Root cause:**
  - `lego/backend/internal/apps/service.go:5580-5610` (`resolveSourcePatch`): handles `if patch.Repo != nil` (`next.repo = ...; next.image = ""`) and then `if patch.Image != nil` (`next.image = ...; next.repo = ""`) sequentially with no mutual-exclusion check when both `patch.Repo != nil` and `patch.Image != nil` are supplied. Because `patch.Image` runs second, it silently overwrites `next.repo = ""` and switches the service to the prebuilt image.
  - Pinned consumer: `github.com/render-oss/cli@v1.1.3-0.20261117005113-11ef59f330de` `pkg/types/service/serviceupdate.go:98-121` does not check `s.Repo != nil && s.Image != nil` client-side (unlike `servicecreate.go:94`), and `pkg/service/update.go:30-49` serializes both fields into `UpdateServiceJSONRequestBody`.
- **Fix:**
  - At the start of `resolveSourcePatch` (`lego/backend/internal/apps/service.go:5580-5595`), reject `patch.Repo != nil && patch.Image != nil` with `errPrebuiltImageField("repo")` (`400 bad request: a service cannot declare both image and repo; remove repo or deploy from repo instead`) before mutating `next` or running any side effects.
  - This automatically covers `ApplyServicePatch`, `ApplyServicePatchDryRun` (`PATCH /v1/services/{id}` and MCP `update_service`), `SetSourceAndRegistryCredential`, and `build_sources.go:637`, across all service types (`web_service`, `private_service`, `background_worker`, `cron_job`, `static_site`).
