# A static site's rollback clears a saved, undeployed setting from `undeployedChanges`, though the setting still waits for the next deploy

Why: after a rollback, the dashboard and GraphQL say a static site has no undeployed changes. Its saved build command, root directory or publish directory still differs from what is served, and goes live at the next deploy without warning.

- **Severity / estimate:** minor, ~1h.
- **Seen:** w32/049's production walk, 2026-11-20, pin `3e53abbe3bc3`, `bex-canary`. Record: `.pm/w32/done/049.md`, Walk step 4, "Static rollback (w4/m197)".
  - A save of a second build command (writing `PUB2`) read `undeployedChanges: true` / `saved` while the site still served `PUB`.
  - REST `POST /v1/services/S/rollback` went `live` with no build and re-served `PUB`.
  - Afterwards `undeployedChanges` read `false`, although the saved build command was never deployed.
- **Known cause (from w32/049's note, "Known limit, unchanged"):** the rolled-back release's settings are not recorded, so the operator's static settings fingerprint takes the saved settings as served. w32/049 fixed the same gap for Restart (`releaseSettingsFingerprint` kept on restart, `8ab2633c8`). w32/053 added `servedSettingsFingerprint` for failed deploys (`51d66ef96`). Rollback has neither.
- **First check Render:** establish whether Render's dashboard still reports pending changes after a rollback of a static site. Render's rollback redeploys an earlier build and keeps service settings as they are. Cite the source. If Render matches bex today, close this as already met with that evidence.
- **Also check web services:** whether a web service rollback has the same gap (`restartSelectedRelease` / `openSelectedRelease` paths in `lego/backend/internal/rollout/`, w32/049's record), so one fix covers both.

## Acceptance

- After a static rollback with a pending save, GraphQL `undeployedChanges` / `undeployedChangesReason` read `true` / `saved`, and the next deploy clears them.
- An operator or backend test covers rollback with and without a pending save.
- If the fix touches it, ADR018's Rollback row states the behavior.
- The production walk runs once the pin carries the fix and w32/053's `51d66ef96`.

## Shipped (2026-11-21) — parked for the production walk

- **Render first:** Render's rollback "reuses certain configuration details from the target deploy … Other settings use the service's _current_ configuration", and "Rolling back does not overwrite any of your service's current configuration settings … When you next trigger a _standard_ deploy, Render uses the service's current configuration as usual" ([render.com/docs/rollbacks](https://render.com/docs/rollbacks), read 2026-11-21). The page names no banner or other indicator of pending settings, and `undeployedChanges` is a bex extension (w32/053's "Unverified"), so there is no Render reading for bex to match. Render's contract is what the flag reports: the saved settings go live at the next deploy. So the flag must read `true` while they differ from what the rollback serves. Not "already met".
- **Triage:** the premise held on `2e02b0303`. A static rollback's `prepareAppReleaseDecision` recorded the saved settings as the release's own (`status.releaseSettingsFingerprint`), and its publication then recorded them as served (`recordStaticRevision`). So `staticSaveWaits` compared the saved settings with themselves. w32/049's walk had in fact no save pending at the rollback: `PUB2` had been deployed (`gen-6`), and the rollback to the first deploy re-served `PUB`. The fix covers both shapes: a save pending at the rollback, and saved settings newer than the target's.
- **Code:** `e6685c42c` (operator only).
  - Each static publication record (`<app>-static-r<generation>`) also keeps the settings fingerprint its publication was released with (key `settings`, `writeStaticPublicationRecord`). A record written before the fix gains the served settings (`status.servedSettingsFingerprint`) when the next publish replaces its publication. A backfill still replaces nothing.
  - When the operator adopts a rollback to another publication, `decideRelease` reads the target's record (`carryRestoredPublicationSettings`: the generation its prefix's `rev-N` names, controlled by this App, same prefix). The release carries those settings, and the restored publication serves them.
  - A record without settings falls back to the settings serving at the request, so a save that was waiting keeps waiting. A Restart keeps w32/049's served settings, and the reason stays `saved` (a static selection has no `sourceGeneration`).
- **Web services (the note's "Also check"):** a separate gap, filed as w32/058, so this fix does not cover it. A Restart or rollback's runtime record stamps the saved settings fingerprint (`writeRuntimeConfigRecord`). So a saved build command, branch or root directory reads as deployed once the selected release serves. The target's fingerprint also covers the plan and disk, which Render's rollback keeps current, so the static fix does not carry over.
