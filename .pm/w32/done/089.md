Why: Render parity in what `GET /v1/logs` and the CLI print. Render's messages colour the `==>` marker (blue for a step, green for a success) and bold the text, so `render logs` shows coloured deploy steps in a terminal. bex returns the same words as plain text.

- **Severity / estimate:** minor, ~1h: the codes go into each line bex writes itself, and the dashboard already renders ANSI (`dashboard/src/features/logs/lib/ansi.ts`).

Triage at `df7d823c75` confirmed the premise: every `==>` line bex writes is plain (`lego/backend/internal/logs/progress.go`, the build pod's awk and shell in `lego/operator/internal/build/`, `announce` in `lego/operator/cmd/native-init/main.go:126`). It also settled which of Render's readers get the codes. tretta's file is `render logs -o json` output (Go's `MarshalIndent` order and `>` escape, records joined with no separator), so the API's messages carry them and so do `-o json` and `-o yaml`. The pinned Render CLI keeps SGR codes on a terminal or a pipe and drops `ESC ( B` (`SanitizeTerminal`). Render's MCP `list_logs` returns the API's response untouched (`render-mcp-server` `pkg/logs/tools.go` at `4f14414479`). Sentry-AI and Ishan2036924/upmyrank-poc add a red platform form (`Exited with status 1`, the port-scan timeout, `Timed Out`).
