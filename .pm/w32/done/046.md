# A redeploy of an unchanged commit never runs a native build command: the build step comes from the layer cache, so a static site rebuilt for new CMS content keeps serving the old build

Why: Render runs the build command on every deploy ("With each deploy, Render proceeds through the following commands for your service", render.com/docs/deploys), and its deploy hooks exist to rebuild a site "when content changes" in a headless CMS (render.com/docs/deploy-hooks). On bex since pin `4b2cebd0bd03`, a native service or static site redeployed at the same commit with the same environment reuses its last build: the deploy goes `live` and nothing new is built.

- **Severity:** major. The deploy reads successful and the site serves stale content, with no error. It hits every workspace since w9/m492 turned the S3 layer cache on everywhere (`BEX_BUILD_CACHE=s3`, `lego/operator/config/prod/kustomization.yaml:51`, live from pin `4b2cebd0bd03`, 2026-11-19 09:13Z). Before that, the cache was off in production after the 2026-10-26 trial rollback (`e1cf5817e`).
- **Attribution:** operator, native build recipe. Not the CLI: the pinned client sends a valid `POST /v1/services/{id}/deploys`, and bex accepts it and builds.
- **Source:** `/qa-find-bugs-cli` sweep 257, 2026-11-19 19:39–19:51Z, released `bex` v0.7.0 (Render CLI v2.36.0), isolated config, human device login, `bex-canary` (`tea-daif693dqjvc73e7as3g`), production pin `c624a4f217ff`. The native recipe has not changed since `4b2cebd0bd03`.
- **Estimate:** ~1h.

## Cause

- `nativeDockerfile` (`lego/operator/internal/build/native.go:410-441`) runs the build command in one `RUN` step. Its BuildKit cache key covers the toolchain layers, `COPY . .` (the root directory's files), the env loader and `ARG RENDER_GIT_COMMIT`. The loader carries `: bex-native-env-rev=<NativeEnvRevision>` (`:416`), so a changed environment or secret file reruns the step (w7/m87). Nothing in the key changes from one release to the next, so the same commit and environment give a `CACHED` step once a layer cache is imported.
- w9/m492 imports that cache on every build (`s3cache.go`, `cache-restore`). `build.go:211-212` then prints `==> Reusing the cached result…` in place of the command's output (w4/582).
- ADR060 D3's w9/m493 drill records it as expected ("3, same source | the build step `CACHED`", `docs/ADR060-build-worker-reliability-and-performance.md:277`). w9/m492 t005 counted it as the native speed-up ("`==> Reusing the cached result…`, no pip line"). w9/m493 t004 had to change an env var to make build 2 run. No ADR018 row records this as a divergence or has the user's sign-off.

## Fix

- Make the build command's step specific to the release: write the release's build revision (`Options.Revision`, `gen-<release generation>` from `releaseBuildRevision`) into the loader beside the env revision, e.g. `: bex-native-release=gen-12`. Every release then runs the command, as on Render. A retry of the same release keeps its key.
- What the cache is for stays the same. The toolchain and tool layers before the step still come from the layer cache, and the command still reads w9/m493's `$XDG_CACHE_HOME` and w9/m494's dependency directories. That is Render's model: the build cache makes the command fast, and the command still runs.
- Dockerfile builds keep BuildKit's own layer semantics. w9/m492 cites render.com/docs/docker for Docker layer caching. kpack builds and image-backed deploys are unaffected.
- Docs:
  - Amend the ADR060 D3 m493 drill row 3 and the D3 text: a same-source release runs the command, and only a retry reuses it.
  - Add to ADR018's `Trigger a deploy` row: every deploy runs a native build command, as Render's.
  - Update the cached-step sentence in `docs/render-artifacts/live-deploy-following.md`, which then applies to a retried release only.
- Tests (`native_test.go`, beside `TestNativeDockerfileEnvRevisionBustsCacheKey`):
  - Two Options that differ only in `Revision` produce different build-command steps.
  - The same `Revision` produces a byte-identical Dockerfile.
  - Literal env values still stay out of the Dockerfile.
  - With the release line removed, the first assertion fails.

## Blast radius

Every native build goes through `nativeDockerfile`: the Node, Python, Ruby, Go, Rust and Elixir web services, private services, background workers and cron jobs, static sites, and Build Source carriers (`BuildOnly`).

The triggers that reach a same-commit release are:

- the dashboard's Manual Deploy → Deploy latest commit with no new push
- deploy hooks (with or without `ref`)
- REST `POST /v1/services/{id}/deploys`, GraphQL `triggerDeploy` and MCP `trigger_deploy`, with or without the same `commitId`
- `POST /v1/build-sources/{id}/builds`

A restart does not build, and a rollback runs its target's recorded image, so neither is affected. The exception is a static site rollback with no stored image: it rebuilds the target commit (ADR018 `Rollback` row, "Known limits"). Render serves the retained artifact there and runs no build, so that rebuild running the command again is no closer to Render than reusing it; leave it as it is. Clear build cache & deploy already ran the command, because a clear release imports no layer cache (w9/m493 t004, build 3).
