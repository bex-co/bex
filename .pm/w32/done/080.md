# An image hosted on `registry.k8s.io` never deploys: the operator refuses the registry's manifest redirect and fails the deploy as "the registry refused to read the image (HTTP 307)"

Why: `registry.k8s.io` answers every manifest read with a `307` to Google Artifact Registry. bex's image metadata reader refuses any manifest redirect, so every image from a registry that bex itself lists as trusted fails in about a second, and the message tells the user to check an image URL and tag that are correct. Render pulls a public image from any registry (the premise of w5/171 and w8/167).

- **Severity / estimate:** major, ~45m. A core journey (deploy a public prebuilt image) cannot succeed for this registry. The message misleads the user.
- **Versions:** released `bex` v0.9.0 (Render CLI v2.36.0). Production pin `de0ed1cbfe7f`: bex-system pods on `sha256:7bbf4b673110…`, read on the control plane.
- **Context:** routine `cli-qa`, 2026-11-22 ~05:25 UTC, `https://api.bex.co/v1/`, workspace `bex-canary`, human device login, non-TTY text and JSON output.
- **Repro:**
  - `bex services create --name qa-20261122-1ad8-none --type web_service --image registry.k8s.io/pause:3.9 --plan free --confirm -o json` exits 0 with `srv-dc17pj6s4hfc739j5md0`.
  - `bex deploys list srv-dc17pj6s4hfc739j5md0 -o json` shows `dep-dc17pj6s4hfc739j5mdg` as `update_failed`, created 05:25:32.48 and finished 05:25:33.25, with no `startedAt`.
  - `bex logs -r srv-dc17pj6s4hfc739j5md0 --type build -o text`:

    ```text
    2026-11-22 05:25:32  ==> Deploy queued
    2026-11-22 05:25:33  ==> Deploy failed: the registry refused to read the image registry.k8s.io/pause:3.9 (HTTP 307). Check the image URL and tag
    ```

  - The fixture was deleted by ID right after.

- **Wire evidence (anonymous, no credential involved):**
  - `GET https://registry.k8s.io/v2/pause/manifests/3.9` with the index and manifest-list `Accept` types answers `307`, `Location: https://us-west2-docker.pkg.dev/v2/k8s-artifacts-prod/images/pause/manifests/3.9?rid=…`.
  - The same `GET` on that `Location` answers `200` with `application/vnd.docker.distribution.manifest.list.v2+json` and `Docker-Content-Digest: sha256:7031c1b283388d2c2e09b57badb803c05ebed362dc88d84b480cc47f72a21097`.
  - `registry.k8s.io/echoserver:1.10` gets the same `307`. Every image on this registry is affected.
- **Attribution:** infrastructure/runtime (operator). The CLI request and bex-api's create are correct. `registry.k8s.io` passes bex-api's registry policy, and it is even on the restricted fallback list (`trustedImageRegistry`, `lego/backend/internal/store/image.go:173`).
- **Root cause:** `readImageConfigDocument` (`lego/operator/internal/registry/image_config.go:378`) sets `CheckRedirect` to `http.ErrUseLastResponse` for manifest reads, so the `307` reaches `statusFailure` (`:125`) as a `RefusedError{Status: 307}`. `imageRefusalError` (`lego/operator/internal/controller/image_network.go:840`) then words it as `DeployReasonImageRead`. w8/201 (`1da018e63`) taught config **blob** reads to follow up to 3 https redirects without the `Authorization` header (`blobRedirectPolicy`, `:349`). It kept manifest reads refusing redirects "so the credential and the trust anchor stay on the registry" (`:165`). For a read with no credential, refusing protects nothing. The kubelet follows the same redirect when it pulls the image, and the digest it pulls by is verified either way. bex's own sandbox image import already follows manifest redirects (`lego/backend/internal/sandbox/import_bounds_test.go:154`).
- **Fix:**
  - Let manifest reads in `readImageConfigDocument` follow redirects under `blobRedirectPolicy`'s rules: https only, at most `maxBlobRedirects` hops, and `Authorization` dropped on every hop. The shared dialer's address refusals still apply.
  - Keep the first verified response's digest as the pinned digest, as now.
  - A `401` that arrives after a redirect must not trade the registry's bearer for the redirect target's realm. Refuse it with the existing refusal wording, or exchange only against the original registry's challenge.
  - Decide in the change whether a credentialed read follows too (credential dropped) or keeps refusing. Write down the reason next to `:165`.
- **Blast radius:** `ReadImageConfig`, `ReadImageRevision`, `ReadImageRuntimeMetadata` and `ImageFileSHA256` all read through `readImageConfigDocument`. Their callers are `registry_read_gate.go:200` and `image_network.go:277`, for every image-backed service type (web, private, worker, cron). `livetag.go` and `copy.go` also refuse redirects. They talk to bex's own Zot, which does not redirect, so they stay as they are.
- **Regression checks:**
  - A unit test with a fake registry whose manifest endpoint answers `307` to a second https host serving the manifest. The read returns that manifest's digest and config. Reverting the fix makes it fail with `RefusedError{307}`.
  - Keep refusal tests for an `http` redirect, for more than 3 hops, and for a redirect to a refused address.
  - Live: `bex services create --type web_service --plan free --image registry.k8s.io/echoserver:1.10 --env-var PORT=8080` reaches `live`, and its URL answers `200`. `docker.io/library/nginx:1.27-alpine` and `ghcr.io/…` controls stay `live`. Delete the fixtures by ID and confirm the 404s.
- **Unverified:**
  - No Render account was used. That Render deploys `registry.k8s.io/pause:3.9` is inferred from its any-registry pull, which w5/171 and w8/167 also rely on.
  - Other registries that redirect manifest reads were not surveyed.
- **Dedupe:** `rg` over `.pm` and `docs` for `registry.k8s.io`, `HTTP 307`, `status 307`, `manifest redirect` and `refuse.*redirect` found only w8/200 and w8/201 (blob redirects, done) and w5/171 and w8/167 (registry allowlist, done). Nothing open covers manifest redirects. `git log -S "Manifest redirects are"` returns only `1da018e63`. This is not deploy lag.

## Fixed in `031ee9c245`, parked on its deploy (2026-11-22)

- **Re-checked on main before the fix:** `image_config.go:378` still refused every manifest redirect, and nothing in the registry package had changed since pin `de0ed1cbfe7f`. An anonymous `GET https://registry.k8s.io/v2/pause/manifests/3.9` answered `307` to `us-west2-docker.pkg.dev`, which answered `200` with the manifest list `sha256:7031c1b2…`. The config blob takes one more `307`, to `cdn.registry.k8s.io`. Render documents "You can deploy public images from any registry Render can reach" (render.com/docs/deploying-an-image).
- **Fix:** manifest reads follow redirects under the policy blob reads already used, now named `redirectPolicy`: https only, at most 3 hops, `Authorization` dropped on every hop, and the shared dialer's address guard on every hop. Credentialed reads follow too, with the credential dropped. The reason is written next to `ReadImageConfig`: the credential never leaves the named registry, and the pinned digest is the sha256 of the bytes read, which the kubelet verifies. A `401` from a redirect target is refused as it stands and never exchanged at the target's realm. The token request still refuses redirects. A hop the policy refuses (plaintext, more than 3 hops) is now a definitive `RefusedError` with the redirect's status. Before, it was a transient error the deploy waited out for its whole rollout budget.
- **Tests** (`image_config_test.go`):
  - A registry whose manifests `307` to a mirror on another https host (anonymous, Bearer, Basic-credentialed, and a manifest-list index) returns the mirror manifest's digest and config, and no `Authorization` reaches the mirror. Reverting the fix fails these with `status 307`.
  - The refusal tests cover a plaintext redirect, a redirect loop, and the mirror's own Bearer challenge, anonymous and credentialed. Removing the `!redirected` guard fails both challenge cases on the token exchange.
  - A redirect to `169.254.169.254` through the real shared transport is refused by its dial guard.
  - `make test` passes (controller envtest 635 s), and golangci-lint on the package is clean.
- **Next (the resumed worker):** once production's pin carries `031ee9c245`, run the live check in `bex-canary`:
  - `bex services create --name qa-<date>-<id> --type web_service --plan free --image registry.k8s.io/echoserver:1.10 --env-var PORT=8080 --confirm -o json` reaches `live`, and its `onbex.co` URL answers `200`.
  - The controls stay `live`: `docker.io/library/nginx:1.27-alpine`, plus one `ghcr.io/…` public image.
  - Delete every fixture by ID, confirm each `404`, then close.
  - `pause:3.9` listens on no port, so it is not a live fixture.
