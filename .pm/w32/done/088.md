# A native service's own log writes `==> Running '<start command>'` each time its instance starts, as Render's does, not only inside a deploy's rollout

Why: Render parity in a service's application log. On Render the instance itself writes `==> Running '<start command>'` whenever it starts the command: at a deploy, after a crash, and when a free instance spins up after idling. A bex service's application log shows none of these, so a spin-up or a restart has no marker in it.

- **Severity / estimate:** minor, ~1h: one line at each start of a native image's start command, in the instance's own stream.
- **Seen:** w32/085's search of public Render logs, 2026-11-22. bex writes the line only as a platform line of a deploy's `type=build` narration, at the starts the operator recorded while the rollout ran (`rolloutLines`, `runningLineFormat`, `lego/backend/internal/logs/progress.go`; at most ten, none after `finished_at`, w32/m560). The app stream (`type=app`, `bex logs -r <srv>`, the service's Logs page) carries no such line.
- **Render reference:**
  - ivanseibel/tretta, `docs/work/reports/assets/T014-public/04b-render-logs.json` at `b0f216c985`: 60 records of Render's log API for a free native Node web service on 2026-10-18. `==> Running 'pnpm --filter @tretta/server start'` comes at 16:09:33.80, 17:17:23.28 and 19:02:34.09, when no deploy ran (the service's deploys, in the same report's `08b-render-deploys.json`, are at 19:09 that day and on 10-16 and 10-17), each after the previous run ended with `Command failed with signal "SIGTERM"`: free spin-ups. It comes again at 19:10:21.13, inside the deploy. Every `Running` record carries the `instance` label (`srv-…-<suffix>`), the `level` label and a UUID id, as the app's own output does. The platform's lines (`==> Deploying...`, the `WEB_CONCURRENCY` line, the live line and the URL block) carry only `resource` and `type`, with ids of another shape.
  - DerekSopok/EMS-Kahoot#3 and Sherbivs/SensaiOS#2: the line again after each exit of the command.
  - Bubba898/luchadores-web#5 (2026-02-01, native Bun): each start writes `==> Using Bun version 1.3.4 (default)` and its docs line before `==> Running 'yarn start'`. Check whether Node, Python and Ruby instances write their version line at start too (tretta's spin-ups show none for Node).
- **Likely shape:** native-init, which already runs the configured start command in the container, writes `==> Running '<command>'` to the container's stdout before it executes the command, quoted as configured (`$PORT` unexpanded). The line then reaches every app read and tail with the pod's own labels. The deploy narration's `rolloutLines` then reads it from the app stream instead of writing its own copy, or drops its copy where the deploy log already interleaves the app lines (the dashboard's deploy page, w32/084), so no reader sees it twice. Settle that against w32/085's open question on which `type` Render gives these lines.
- **Done when:** a free native web service that spins down and is woken by a request shows `==> Running '<start command>'` in `bex logs -r <srv>` at the start of the woken instance, with the instance's own labels, on REST, the subscribe stream, GraphQL, MCP and the service's Logs page. A restart after a crash shows it again. A Dockerfile or prebuilt-image service shows none. A deploy's log shows the line once per start, not twice.

**Promoted to [w32/m575](../m575/README.md), 2026-11-22** (`/loopx w32`). Triage at `81bfb51e07` confirmed the premise: native-init writes nothing to stdout (`lego/operator/cmd/native-init/main.go:68`), and the only `==> Running '<command>'` lines bex writes are the deploy narration's `type=build` platform lines (`rolloutLines`, `preDeployLines`, `lego/backend/internal/logs/progress.go:584`, `:513`). A re-read of tretta's capture confirmed that Render's line carries `instance`, `level: info` and a UUID id at 16:09:33.80, 17:17:23.28, 19:02:34.09 and 19:10:21.13, while the platform's lines carry neither. The note's own scope check is more than an hour across several tasks:

- native-init is copied into each image at build (`nativeEntrypoint`, `lego/operator/internal/build/nativeinit.go`), so an image built before the change never writes the line. The narration must keep its copy for those releases and drop it for the new ones, which needs an operator record of which image a release runs and its projection onto the deploy row.
- The dashboard's deploy page and the CLI's type-less deploy tail interleave the service's app lines with the narration, so both copies would show.
- A pre-deploy step, a cron run and a one-off run go through native-init too, and Render's line for a cron or one-off run is not yet observed.

So the milestone takes native-init's line, a per-release record, the narration's choice between the two copies, the docs and a production walk with a free spin-up: about 7h over ten tasks.
