# `bex services update <free-web> --maintenance-mode-uri <url>` (and Blueprints/REST/GraphQL/MCP) persists a custom `maintenanceMode.uri` and emits `maintenance_mode_uri_updated` events on free web services and non-web services

Why: Maintenance Mode (including its custom maintenance page URL) is a paid web-service feature that the dashboard disables on free plans and hides on non-web types, yet `validateMaintenanceEligibility` ignores non-empty `uri` whenever `enabled` is `false`, allowing free web services and non-web services to persist paid-only maintenance URIs, emit bogus `maintenance_mode_uri_updated` events/webhooks, and propagate the URI via `bex services create --from`.

Supplying a non-empty `maintenanceMode.uri` on a free web service or any non-web service (`static_site`, `private_service`, `background_worker`, `cron_job`) should be refused with `HTTP 400` (`maintenanceMode requires a paid web service plan` / `maintenanceMode is available only for web services`) before any CR patch or `maintenance_mode_uri_updated` event/webhook.

- **Attribution:** server
- **Root cause:**
  - `lego/backend/internal/apps/service.go:974-985` (`validateMaintenanceEligibility`):
    ```go
    func validateMaintenanceEligibility(serviceType, tier string, mode *MaintenanceModeView) error {
        if mode == nil || !mode.Enabled {
            return nil
        }
        ...
    ```
    When `w9/068` relaxed presence checking so `services create --from <free-web>` could echo the inert default `{enabled: false, uri: ""}`, it short-circuited on `!mode.Enabled` alone without checking `strings.TrimSpace(mode.URI) == ""` (and `TestEnablingMaintenanceModeOnFreePlanStillRefused` in `lego/backend/internal/apps/cron_docker_command_test.go:358-384` only tested `URI: ""`).
  - As a result, `validateMaintenanceEligibility` admits any non-empty `uri` with `enabled: false` across every write path: `validateTypeSpecificCreate` (`service.go:3664`), `validateMaintenanceMode` (`service.go:988`, called by `checkMaintenanceMode` at `settings_check.go:596`, `validateNewSpecMaintenanceMode` at `service.go:1030`, and Blueprint sync at `deploy.go:4085`).
  - Pinned consumer: `github.com/render-oss/cli@v1.1.3-0.20261117005113-11ef59f330de` `pkg/service/update.go:161-171` reads `beforeDetails.MaintenanceMode`, merges `--maintenance-mode-uri`, and sends `PATCH /v1/services/{id}`; `pkg/service/clone.go:162-165` echoes `details.MaintenanceMode` on `services create --from`.
- **Fix:**
  1. In `lego/backend/internal/apps/service.go:974-985` (`validateMaintenanceEligibility`): treat `{enabled: false, uri: ""}` (trimmed) as the only inert value — change the early return from `if mode == nil || !mode.Enabled` to `if mode == nil || (!mode.Enabled && strings.TrimSpace(mode.URI) == "")`, so any write with `enabled: true` OR a non-empty `uri` enforces both `serviceType == appv1alpha1.TypeWebService` and paid `tier`.
  2. In `lego/backend/internal/apps/settings_check.go:594-609` (`checkMaintenanceMode`): preserve safe no-op echo / downgrade compatibility for a paid service that previously stored a custom URI, disabled maintenance mode, and downgraded to `free` — if `current := maintenanceModeView(a.Spec.MaintenanceMode); current == in`, return `in, nil` without mutating or emitting events (and clearing `{enabled: false, uri: ""}` remains accepted by rule 1). Note: verify protected-environment ordering (`requireUnprotected` only triggers when `in.Enabled != current.Enabled`, so `current == in` has no toggle to guard).
  3. Confirm `manifestPlanAndMaintenance` (`lego/backend/internal/apps/deploy.go:3458-3475`) still upgrades omitted-plan Blueprint web services declaring `maintenanceMode` to `starter` while refusing explicit `plan: free` or non-web `type:` with non-empty `uri`.
