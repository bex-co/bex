# 116 — A stale `BEX_WORKSPACE` name breaks workspace-independent commands (`skills`, `code`/launchers, `edit`, `docs`, `analytics notice`/`send`, `workflows dev`/`init`/`--local`, and `s3` with explicit env keys)

Why: `docs/bex-cli.md` promises that "Only a command that reads the active workspace resolves it", and `docs/bex-cli.md` promises that `bex s3` with `BEX_S3_ACCESS_KEY_ID` + `BEX_S3_SECRET_ACCESS_KEY` "needs no sign-in, no workspace and no `bex-api`". Because `workspaceIndependent` in `lego/cli/main.go:290-293` was never updated as new Bex-native and local upstream commands landed after `w8/064`, a renamed, deleted, or typoed `BEX_WORKSPACE` name exits `1` before local commands run, breaks `bex analytics notice` (used by installers), and forces every detached `bex analytics send` child process to make an extra synchronous `GET /v1/owners?name=` API call on every CLI invocation whenever `BEX_WORKSPACE` holds a workspace name.

Severity: minor. Attribution: Bex launcher. Estimate: ~45m. Source: `/qa-find-bugs-cli` routine `cli-qa` sweep `5217`, 2026-11-24. Goal: `docs/bex-cli.md` § Configuration (`BEX_WORKSPACE`), § Object storage (`bex s3`), and `w8/064`'s contract that only active-workspace consumers resolve `BEX_WORKSPACE`. No dependencies and no product fix implemented by this filing.

## Root cause

`lego/cli/main.go:83-90` registers a `cobra.OnInitialize` callback that calls `bridge.ResolveWorkspaceName(workspaceUse(cmd.RootCmd, os.Args[1:]))`. `workspaceIndependent` (`lego/cli/main.go:290-293`) lists only the ten paths added in `w8/064` plus `upgrade`:

```go
var workspaceIndependent = []string{
	"workspaces", "workspace set", "whoami", "login", "logout", "help",
	"completion", cobra.ShellCompRequestCmd, cobra.ShellCompNoDescRequestCmd, "upgrade",
}
```

Everything not in `workspaceIndependent`, not a help-only group (`usage.HelpOnly`), not carrying a non-empty `--workspace` flag, and not passing a typed resource ID as its first positional argument falls through to `bridge.WorkspaceRequired` (`lego/cli/main.go:320-346`), which issues `GET /v1/owners?name=<BEX_WORKSPACE>&limit=100` (`lego/cli/internal/bridge/workspace.go:44-103`) and exits `1` on 0 or >1 matches.

Specifically missed workspace-independent commands:

1. `skills` (`skills list`, `install`, `update`, `remove` — `lego/cli/internal/skills/skills.go`), which operates only on local agent skill directories and never reads `config.WorkspaceID()`.
2. `code` (`code`, `code keys`, `code keys set`, `code keys unset`) and every coding-agent launcher in `code.Catalog()` (`glm`, `muse`, `kimi`, `deepseek` — `lego/cli/internal/code/code.go:33-120`), all purely local.
3. `edit` (`lego/cli/internal/desktop/desktop.go:94-123`) and its path shorthand `bex <path>` (`desktop.Shorthand` at `lego/cli/main.go:69`): even for `bex edit ags-<id>`, `fetchSSHAddress` (`lego/cli/internal/desktop/session.go:73-88`) calls `GET /v1/agent-sessions/{id}` directly without `config.WorkspaceID()`.
4. `docs` (upstream `cmd/docs.go:9-17`), which opens docs in a browser and never reads the workspace.
5. `analytics notice` (`cmd/analyticsnotice.go:19-39`) and `analytics send` (`cmd/analyticssend.go:9-26`): neither reads the workspace, and `analytics send` is re-executed as a detached child process by every telemetry-emitting command, so omitting it also adds a wasted `GET /v1/owners?name=` call to every command when `BEX_WORKSPACE` is a valid workspace name.
6. `workflows init` (`cmd/workflowinit.go`), `workflows dev` (`cmd/workflow.go:42-75`), and workflow commands invoked with `--local` (`workflows tasks list --local`, `workflows runs list/start/details/cancel --local`, and top-level/workflow shortcut `--local` flags in `cmd/task.go:48`, `cmd/run.go:20`, `cmd/workflowshortcuts.go:12`), which target the local workflow dev server on `localhost:8120` rather than Bex's API.
7. `s3` S3-protocol commands (`ls`, `cp`, `mv`, `rm`, `sync`, `mb`, `rb`, `presign`, `cors`, `lifecycle`, `env`, and `info s3://...`) when both `BEX_S3_ACCESS_KEY_ID` and `BEX_S3_SECRET_ACCESS_KEY` are non-empty (`lego/cli/internal/s3/session.go:58-59,247-252`, `docs/bex-cli.md:448`). Note that `s3 keys`, `s3 public`, and `s3 info <bucket>` (without `s3://`) call `d.owner()` (`lego/cli/internal/s3/tools.go:194,241,303,381,451`) and still require the active workspace.

## Fix plan

1. Update `workspaceIndependent` and `workspaceUse` in `lego/cli/main.go:290-346`:
   - Add `"skills"`, `"code"`, every provider name from `code.Catalog()` (`glm`, `muse`, `kimi`, `deepseek`), `"edit"`, `"docs"`, `"analytics notice"`, `"analytics send"`, `"workflows init"`, and `"workflows dev"` to `workspaceIndependent` (or compute provider names from `code.Catalog()` so a new provider cannot drift).
   - For workflow commands (`path == "workflows"` or `strings.HasPrefix(path, "workflows ")`), when `target.Flags().Lookup("local")` has value `"true"`, return `bridge.WorkspaceUnused`. Keep `ea objects --local` workspace-required because upstream uses `config.WorkspaceID()` in its local object path.
   - For `s3` commands that go through `d.session()` (all `s3` subcommands except `s3 keys`, `s3 public`, and `s3 info` on a bare bucket name without `s3://`), when both `BEX_S3_ACCESS_KEY_ID` and `BEX_S3_SECRET_ACCESS_KEY` are non-empty, return `bridge.WorkspaceUnused`.
2. Extend `TestStaleWorkspaceNameBlocksOnlyConsumers` in `lego/cli/main_test.go` to cover all newly exempted commands (including asserting zero `/v1/owners?name=` lookups for both stale and valid `BEX_WORKSPACE` names, and preserving `WorkspaceRequired` for `ea objects list --local`, `s3 keys list`, `s3 public`, `workspace current`, and `services`).
3. Update the `BEX_WORKSPACE` row in `docs/bex-cli.md:60` so the documented list of workspace-independent commands matches the implementation.
4. Verify with `cd lego/cli && go test ./...` and `make lint`, plus a live check against `https://api.bex.co/v1/` with `BEX_WORKSPACE=stale-nonexistent-ws-...` confirming `skills list`, `code keys`, `analytics notice`, `workflows tasks list --local`, and `BEX_S3_ACCESS_KEY_ID=... BEX_S3_SECRET_ACCESS_KEY=... bex s3 env` no longer fail on the stale workspace name while `services` and `workspace current` still refuse.

## Resolution (2026-11-24)

- Updated `workspaceIndependent` and `workspaceUse` in `lego/cli/main.go` to exempt `skills`, `code`, provider launchers from `code.Catalog()`, `edit` (and `bex <path>`), `docs`, `analytics notice`, `analytics send`, `workflows init`, `workflows dev`, `workflows … --local`, and S3-protocol `s3` commands when both `BEX_S3_ACCESS_KEY_ID` and `BEX_S3_SECRET_ACCESS_KEY` are non-empty (`s3.UsesEnvCredentials` in `lego/cli/internal/s3/session.go`).
- Added `usage.MarkHelpOnly` (`lego/cli/internal/usage/usage.go`) and marked `s3`, `s3 cors`, and `s3 lifecycle` help-only groups so they also skip workspace resolution without S3 env keys.
- Preserved workspace resolution for `ea objects … --local`, remote `workflows`, `s3` without both env keys, `s3 keys`, `s3 public`, `s3 info <bucket>`, `s3 info s3://<bucket>`, `services`, and `workspace current`.
- Updated the `BEX_WORKSPACE` row in `docs/bex-cli.md`.
- Extended `TestStaleWorkspaceNameBlocksOnlyConsumers` in `lego/cli/main_test.go` (including a detached `analytics send` zero-lookup regression check) and added `TestUsesEnvCredentials` in `lego/cli/internal/s3/s3_test.go`; verified the regression test fails when `lego/cli/main.go` is reverted.
- Verified with `CI=true go test ./...` in `lego/cli`, `make lint` across all four Go modules, `bash scripts/bex-cli-validate.sh`, and a read-only live check against `https://api.bex.co/v1/` (isolated human device login, `BEX_WORKSPACE=stale-nonexistent-ws-w32-116`, zero resources created, session logged out and revoked afterwards).
