# `BEX_WORKSPACE` / `RENDER_WORKSPACE` breaks `bex services create|update|delete` and `bex ssh <srv-id>` whenever `~/.bex/cli.yaml` saves a different workspace — upstream CLI defect, grade and document it

Why: `docs/bex-cli.md` documents `BEX_WORKSPACE` as the per-command active workspace override (and `workspace current`, `services`, `postgres`, `keyvalues`, `logs`, `sandboxes`, `sandbox-groups`, `ea objects`, `s3`, and `agent` all honor it), yet every `bex services create`, `services create --from`, `services update`, `services delete`, and `bex ssh <srv-id>` invocation fails client-side whenever `~/.bex/cli.yaml` holds a different saved workspace. `docs/cli-compatibility-checklist.md` currently grades `services create`/`update`/`delete` and `ssh` `[x]` with no upstream caveat, and `docs/bex-cli.md` does not warn users or scripts about the `cli.yaml` conflict.

### `validate.WorkspaceMatches` ignores `RENDER_WORKSPACE` (`BEX_WORKSPACE`), breaking `services create|update|delete` and `ssh <srv-id>` when `cli.yaml` holds another workspace

- **Severity:** major (upstream CLI defect; docs/ledger grading + pin-bump re-check in bex)
- **Versions:** checkout build of `lego/cli` at `aa6c4ec3f7` (pinned Render CLI `v2.38.0`, `github.com/render-oss/cli@v1.1.3-0.20261120013850-09b7802aa379`); unmodified upstream `render` built from the exact same pin `09b7802aa379`; installed `/home/tp/.local/bin/bex` `v0.3.3` (Render CLI `v2.27.0`); production pin `7b046987bcd8` (`4b533337ab`)

- **Expected / actual:**
  - **Expected:** Setting `BEX_WORKSPACE` (or `RENDER_WORKSPACE`) overrides the active workspace in `cli.yaml` consistently across all commands, so `services create`, `services create --from`, `services update`, `services delete`, and `ssh <srv-id>` target `tea-daif693dqjvc73e7as3g` (`bex-canary`) just like `workspace current`, `services`, `deploys list`, `services instances`, `jobs list`, `logs`, `postgres`, `keyvalues`, `sandboxes`, `sandbox-groups`, `ea objects`, `s3`, and `agent`.
  - **Actual:** Every `services create|update|delete` invocation above exited `1` with `Error: resource in workspace does not match the workspace in the current workspace context tea-d98210cbbpdc73dcrkvg. Unmodified `render` (`v2.38.0`) and installed `bex v0.3.3` (`v2.27.0`) reproduced identically.
- **Wire evidence:**
  - `services create` fails client-side in `pkg/service/repo.go:83` before sending `POST /v1/services`.
  - `services delete <id>` / `services update <id>` call `GET /v1/services/srv-dbkq3hdhhjfs73eiahe0` → `200` with `"ownerId": "tea-daif693dqjvc73e7as3g"`, then fail client-side in `validate.WorkspaceMatches`.
  - `ssh srv-dbkq3hdhhjfs73eiahe0` calls `GET /v1/services/srv-dbkq3hdhhjfs73eiahe0` → `200`, fails `validate.WorkspaceMatches`, swallows the error at `pkg/tui/views/ssh.go:113-116`, and falls back to `GET /v1/services?name=srv-dbkq3hdhhjfs73eiahe0&ownerId=tea-daif693dqjvc73e7as3g` → `200 []`, printing `No service found with name or ID 'srv-dbkq3hdhhjfs73eiahe0'`.

- **Attribution:** upstream (`render-oss/cli`), not bex server or launcher. Do **not** fork the CLI or add a server/launcher workaround.
- **Root cause:**
  - Pinned upstream `github.com/render-oss/cli@v1.1.3-0.20261120013850-09b7802aa379` `pkg/config/config.go:120-133` (`config.WorkspaceID()`) reads `os.Getenv("RENDER_WORKSPACE")` first and falls back to `cli.yaml`'s `cfg.Workspace`.
  - `pkg/validate/workspace.go:11-18` (`validate.WorkspaceMatches(workspaceID)`) instead calls `cfg, err := config.Load()` directly and compares `cfg.Workspace != "" && cfg.Workspace != workspaceID`, ignoring `RENDER_WORKSPACE` completely.
  - All four call sites in `pkg/service/repo.go` hit it: `DeployService` (line 62), `CreateService` (line 83), `GetService` (line 144), and `resolveServiceIDFromNameOrID` (line 189).
  - Upstream itself noted the problem in `pkg/keyvalue/repo.go:84-88` ("Unlike the service repo, this method does not call validate.WorkspaceMatches on data.OwnerId"), but left `pkg/validate/workspace.go` and `pkg/service/repo.go` broken.
