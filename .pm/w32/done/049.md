# A static site's Restart rebuilds the live commit with the saved settings, so a save that was never deployed goes live, or fails, through a "restart"

Why: Render's restart "always uses the exact same Git commit and configuration as the running instance", and bex's own web-service Restart keeps the running release, but a static site's Restart runs the saved build command, root directory and publish directory. It publishes changes the owner only saved, and `undeployedChanges` then reads false.

- **Severity / estimate:** major (a Restart changes what the site serves, or fails on a setting the live site does not use, while the CLI reports `restarted successfully`), ~1h.
- **Seen:** `/qa-find-bugs-cli w32` routine, run `128f`, 2026-11-20 00:19–00:58 UTC. Production pin `98e053468f52` (`bex-api` and `bex-controller-manager` run `bex-operator@sha256:1ec4a7c2d561…`, read with `kubectl` at 00:17Z). Released `bex` v0.7.0 (`bex-0.7.0-linux-arm64.tar.gz`, checksum verified), isolated `BEX_CLI_CONFIG_DIR`, human device login as the QA user, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), `-o json`/`text` non-TTY.
- **Repro** (`<…>` = placeholders):
  1. `bex services create --name qa-…-sta --type static_site --repo https://github.com/bex-co/bex --branch main --root-directory examples/static-site --build-command 'mkdir -p dist/sub && cp index.html dist/ && echo QA128F-PUB > dist/marker.txt && …' --publish-directory dist -o json` created `srv-dbvp43150n7c739ba0ig`. Its first deploy `dep-dbvp43150n7c739ba0j0` (commit `35252fd`) went `live`, and `/marker.txt` served `QA128F-PUB`. The operator recorded its publication (`…-128f-sta-static-r1`).
  2. Saved a bad root directory: `bex services update <srv> --root-directory examples/nope-128f -o json` (save only, exit 0).
  3. 00:49:28Z: `bex restart <srv> --confirm -o json` printed `"<srv> restarted successfully"`, exit 0. It opened `dep-dbvpi643j89c738ag4m0` (REST `trigger: other`), which **built** `35252fd` with the saved root directory and closed `build_failed`: `==> Build failed: build failed in the source checkout step:` / `the root directory "examples/nope-128f" does not exist in the repository at "35252fd77feed…"`. The site kept serving `QA128F-PUB`.
  4. Saved a good root directory and a second build command: `bex services update <srv> --root-directory examples/static-site --build-command '… echo QA128F-PUB2 > dist/marker.txt …' -o json`. GraphQL `service(id:) { undeployedChanges undeployedChangesReason }` read `true` / `"saved"`.

- **Expected / actual:**
  - Expected: a Restart re-serves what is live, the running release's publication, with no build. The saved settings wait for the next deploy, and `undeployedChanges` keeps reporting them. This is the contract the ADR018 Restart row records ("Running artifact and configuration (w5/m107)") and the dashboard's static Restart dialog promises ("`{name}` is published again from the commit it is serving now. Commits pushed since are not deployed.").
  - Actual: the Restart is a full rebuild of the live commit with today's saved build command, root directory and publish directory. It publishes a pending save (step 5) or fails on one the live site does not use (step 3).
- **Control (same run):** an image web service `srv-dbvp5fs3j89c738ag3i0` with a pending save (health check path cleared, `undeployedChanges: true`, `saved`). `bex restart` opened `dep-dbvplv43j89c738ag4pg`, live in 25 s with no build. The Deployment's readiness probe still checks `--path /health`, and `undeployedChanges` stays `true` (`historical_release`). Only the static path diverges.
- **Root cause:**
  - `restartSelectedRelease` (`lego/backend/internal/deploys/rollback_config.go:181-184`) returns `nil, nil` for every `static_site`.
  - So `restartNow` (`lego/backend/internal/deploys/service.go:695-709`) falls through to the legacy fallback: `triggerFetched` with `TriggerParams{restart: true, CommitID: <live commit>}` and `store.TriggerRestart`. That is a commit-pinned build from the saved spec, and it advances the release past the pending save, so `undeployedChanges` clears.
  - Rollback already does the right thing for the same type. Since w4/m197 (`c9666f01d`), `Rollback` selects the target's retained publication through `staticReleaseSelection` (`service.go:1356-1366`, `rollback_config.go:97-114`; record `appv1alpha1.StaticPublicationRecordName`), "so the saved publish directory, root directory and build command are irrelevant to it and stay as saved". The operator's restore branch copies that prefix with no build (`fetch` publish Job). Restart never got the same branch. w5/m107's closeout lists "static republish uses current build settings" as a known limit, and the ADR018 Restart row does not mention static sites.
- **Fix (target):**
  - For a `static_site`, `restartSelectedRelease` selects the serving deploy (`servingDeploy`, which must not require a `ResolvedImage`: a direct no-build publish has none). It takes that deploy's retained publication with `staticReleaseSelection` and opens the row through `openSelectedRelease` as a `restart` (bex trigger `restart`, REST `other`, `server_restarted`). The deferred-restart worker (`restartNow`) takes the same path.
  - Result: no build, the live publication is re-served, saved settings stay saved, and `undeployedChanges` keeps reporting them.
  - When the serving release has no retained publication (published before w4/m197, or expired), keep today's commit-pinned republish and log it, like the web-service legacy fallback ("Limits" in the ADR018 Restart row).
  - Update the ADR018 Restart row (static sites), the w5/m107 limit and ADR029. The dashboard dialog copy stays true.
- **Blast radius:** every Restart caller goes through `deploys.Service.Restart`: REST `POST /v1/services/{id}/restart`, GraphQL `restartServer`, MCP `restart_service`, the dashboard Manual Deploy → Restart service and the services-list Restart, plus the deferred restart that runs after a deploy in flight (w5/m284). Affected: static sites, both built (build command) and direct (no build); for a direct site a pending root or publish directory applies the same way. Not affected: web, private and worker services (selected release, the control above); cron jobs (refused, w8/040).
- **Regression checks:** steps 1–5 above pass when step 3's restart goes `live` serving `QA128F-PUB` with no `==> Building from` line, and step 5's restart serves `QA128F-PUB` with `undeployedChanges` still `true` / `saved`. A following `bex deploys create <srv> --wait` then publishes `QA128F-PUB2`. Controls: a web-service restart (unchanged); a static rollback (w4/m197, unchanged); a static site whose serving release has no publication record (legacy fallback, logged).
- **Unverified:**
  - Render's restart of a static site was not observed: there is no Render account (w32/039). The target follows Render's documented restart contract, which names only cron jobs as unsupported, and bex's own static Restart copy.
  - The direct (no-build) static mode and the deferred restart were read from the code, not exercised.
  - `spec.buildCommit` stays pinned to `35252fd` after the restart; whether a later "Deploy latest commit" clears it was not checked.
- **Dedupe:**
  - w4/m141 (static rollback no-op; wrote the static Restart copy) and w4/m197 (static rollback from the retained publication) cover rollback only.
  - w5/m107 and w4/m433 (Restart keeps the running configuration) exclude static sites, and w32/046 discusses only the rollback rebuild.
  - `rg -i 'restart' .pm` over open items finds nothing on static sites, and `.pm/DO_NOT_DO.md` has no entry.
  - Not deploy lag: no commit to `deploys/rollback_config.go` or `restartNow` since `b946df6ae` (w4/m433, 2026-11-16), which the pin carries.
- **Cleanup:** the static site (with its REST-added routes and headers), the image web service, a free Key Value and two bad-source static sites from the same run were deleted by ID. Every by-ID REST read answers `404`, and both `onbex.co` hosts answer `404`.

## Shipped (2026-11-20) — parked for the production walk

- **Triage:** the premise held on `72a37bf21`. `restartSelectedRelease` returned `nil, nil` for every `static_site`, so `restartNow` fell back to the commit-pinned rebuild from the saved spec. The note's fix alone was not enough for its `undeployedChanges` check: the operator's static saved-change status (`staticSaveWaits`) needs the pending-save marker, which any restart stamp consumes, and adopting a release rewrote `status.releaseSettingsFingerprint` to the saved spec's. A backend-only fix would still have cleared `undeployedChanges`.
- **Code:** `8ab2633c8`.
  - bex-api (`lego/backend/internal/deploys/rollback_config.go`): `staticRestartSelection` selects the serving release (`servingDeploy`) and its retained publication (`retainedStaticPublication`) as `spec.releaseConfig.staticPrefix`, and the row opens through `openSelectedRelease` as a restart. The deferred restart takes the same path through `restartNow`. For a static release whose row is not yet projected Live, `servingDeploy` needs no image (a direct publish has none) and uses the status image as provenance only. A serving release with no record keeps the commit-pinned republish and logs `static restart rebuilds the live commit with the saved settings`.
  - Operator (`lego/operator/internal/controller`): `restoresServedPublication` keeps the served settings fingerprint when a release restores the very prefix serving now (`prepareAppReleaseDecision`). `staticSaveWaits` also reads an adopted restore (`restoredPublicationAdopted`), so the save keeps reading `true` / `saved` until a deploy publishes it. A rollback to another publication records the saved settings as before.
  - The operator's restore branch (`staticRestoreSelection`, the `fetch` publish Job) already handled any release that carries a `staticPrefix`, so the restart needed no publish change.
- **Tests:**
