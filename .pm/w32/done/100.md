# Render CLI operations outside the pinned OpenAPI spec (`ea blueprints`, `sandbox-groups`, `ea objects`) bypass `w8/411`'s error-code filter and still print bex-internal codes (`NOT_FOUND`, `SANDBOX_GROUP_NOT_FOUND`, `REGION_NOT_OFFERED`)

Why: `w8/411` (`446e40ddb0`) strips non-Render error codes from Render REST operations so the pinned Render CLI prints `received response code 404: <message>` instead of `received response code 404 (NOT_FOUND): <message>`, matching Render's `errorCode` vocabulary. Because `withRenderErrorCodes` recognizes Render operations only through `render-public-api-1.json`, nine Render CLI operations not yet published in that spec bypass the filter and still emit bex's upper-case internal codes on REST and in CLI stderr.

- **Severity / estimate:** minor, ~45m. Status codes and messages are right; the error line's parenthesised code leaks bex-internal identifiers and disagrees with sibling commands in the same group (`ea blueprints update` vs `plan`/`approve`, `sandbox-groups delete` vs `default set`).
- **Versions:** released `bex` v0.9.0 (`bex-0.9.0-linux-arm64.tar.gz`, compatible with Render CLI `v2.36.0`, upstream pin `4fd34231b637`); repo checkout at `2e0a5339c3` (`lego/cli` pinned to Render CLI `v2.37.0`, `11ef59f330dedec290f8d71d89b8f7379bbbed09`); production platform pin `ac882b5f557f` (`87ea4b0ee5`). `withRenderErrorCodes` is unchanged through `2e0a5339c3`.
- **Context:** routine `cli-qa`, 2026-11-23 17:05–17:18 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login (`bex login`), non-TTY `-o json`. ## Attribution and root cause

- **Attribution:** server (`lego/backend/internal/api`). The pinned Render CLI's error decoder (`github.com/render-oss/cli`, `pkg/client/client.go` `ErrorFromResponse`) prints `(<code >)` whenever the server returns a non-empty `code` field, and `bex` does not alter it.
- **Root cause:** `withRenderErrorCodes` (`lego/backend/internal/api/render_openapi.go:1068-1082`) decides whether to filter a REST error's `code` solely via `contract.renderOperation(pattern, r)` (`:1033`), which matches only operations listed in the embedded `lego/backend/internal/api/openapi/render-public-api-1.json` (165 paths, 264 operations). Render's public OpenAPI spec omits nine Render CLI operations that bex serves:
  1. `POST /v1/blueprints` (`lego/backend/internal/apps/rest.go:1688`)
  2. `POST /v1/blueprints/{id}/syncs` (`lego/backend/internal/apps/rest.go:1700`)
  3. `POST /v1/blueprints/{id}/approve` (`lego/backend/internal/apps/rest.go:1712`)
  4. `DELETE /v1/sandbox-groups/{sandboxGroupId}` (`lego/backend/internal/sandbox/groups.go:696`)
  5. `POST /v1/sandbox-groups/{sandboxGroupId}/set-default` (`lego/backend/internal/sandbox/groups.go:703`)
  6. `GET /v1/objects/{ownerId}/{region}` (`lego/backend/internal/api/objects_render.go:81`)
  7. `PUT /v1/objects/{ownerId}/{region}/{key...}` (`lego/backend/internal/api/objects_render.go:101`)
  8. `GET /v1/objects/{ownerId}/{region}/{key...}` (`lego/backend/internal/api/objects_render.go:119`)
  9. `DELETE /v1/objects/{ownerId}/{region}/{key...}` (`lego/backend/internal/api/objects_render.go:135`)
- For all nine, `onRender` stays `false`, so `core.WriteErr` emits every bex-internal upper-case code (`NOT_FOUND`, `FORBIDDEN`, `SANDBOX_GROUP_NOT_FOUND`, `BLUEPRINT_NOTHING_TO_APPROVE`, `BLUEPRINT_SYNC_PLANNING_FAILED`, `BLUEPRINT_PLAN_CHANGED`, `BLUEPRINT_NAME_TAKEN`, `BLUEPRINT_MANUAL_ENV_VAR_UNKNOWN`, `BLUEPRINT_MANUAL_ENV_VARS_MISSING`, `REGION_NOT_OFFERED`, `OBJECT_NOT_FOUND`, `OBJECT_KEY_INVALID`, `OBJECT_TOO_LARGE`, `OBJECT_STORAGE_QUOTA`, `OBJECT_REQUESTS_LIMITED`, `SIZE_BYTES_REQUIRED`, `INVALID_CURSOR`).

## Fix

- Extend `withRenderErrorCodes` (`lego/backend/internal/api/render_openapi.go:1068`) with an explicit set of Render CLI REST patterns served outside the pinned OpenAPI spec (the nine patterns above) so `onRender` is true for them too, keeping bex-native REST routes (`/v1/s3/...`, `/v1/agent-sessions/...`, `/v1/git/...`, `/v1/blueprints/{deploy,generate,preview}`), GraphQL `extensions.code`, and MCP `CODE:` prefixes untouched.
- **Preserve Render's own lower-case codes on those routes:**
  - `default_sandbox_group_not_deletable` (on `DELETE /v1/sandbox-groups/{sandboxGroupId}`) and `invalid_sandbox_group_id` / `invalid_cursor` / `invalid_limit` / `invalid_owner_id` / `insufficient_token_scope` are already in `contract.errorCodes` (from `render-public-api-1.json`).
  - Check `POST /v1/blueprints`'s `BlueprintPreviewReason` codes (`lego/backend/internal/apps/blueprint.go:639-659`, e.g., `repo_not_found_or_no_access` which the CLI receives on an inaccessible repo): either keep Render's documented EA lower-case codes in a narrow companion allow-set for `withRenderErrorCodes` or confirm against the pinned CLI whether the client branches on them; never drop a code the pinned CLI switches on.
  - Note `objects_render.go:212` currently emits upper-case `INVALID_CURSOR` rather than Render's lower-case `invalid_cursor` (which IS in `contract.errorCodes`); align or let the filter drop the upper-case code consistently.
- Update `docs/ADR006-bex-api.md` (`Render's REST operations answer Render's codes only`) to note that Render CLI operations outside the pinned spec follow the same filter.
