## Objective

Check that every surface that reads a deploy's log shows the same three lines:

- REST `GET /v1/logs?type=build` and `GET /v1/logs/subscribe`;
- the GraphQL logs query;
- MCP `list_logs`;
- the dashboard's deploy page log pane;
- `bex logs`.

They all read one synthesis in `logs.Service`. Compare each with Render's logs in the milestone README.

## Follow-ups to file with `/pm add w32` (each with its evidence)

- **The primary URL block under Render's live line.** Render follows `==> Your service is live 🎉` with `==> `, a `///` rule, `==> Available at your primary URL https://<service>.onrender.com` and another rule (lelewithheart/Pixel-Breach#10 and 20 more logs found by that phrase). bex writes none of it.
- **The new instance's output in the deploy log.** Render's deploy log carries it between `Deploying...` and the verdict, such as rkendel1/freq#187's traceback before `Exited with status 1`. bex's `type=build` carries none of it.
- **Any unknown from the milestone README that is still open:** a worker's, private service's, prebuilt image's or pre-deploy deploy log, or Render's log `type` for these lines.

## Acceptance criteria

- [x] Every surface is checked and agrees, or each drift is filed as its own item.

## Production walk (2026-11-23)

These are t008's fixtures (§ Walk), read with the CLI's device-login token over three surfaces: REST `GET /v1/logs` (with `ownerId`, `resource`, `type`, the deploy's window and `direction=forward`), GraphQL `logs` with the deploy page's own variables (`resource`, `type`, the deploy's window, and `deployId` on the build leg), and MCP `list_logs` at `https://api.bex.co/mcp`.

- **Node, `type=build`, over the rollout window.** All three returned the same 11 lines with the same ids and the same nanosecond stamps as the CLI: `Build successful`, `Deploying...`, the `WEB_CONCURRENCY=1` line, the live line and the URL block. On `type=app`, all three returned the same `==> Running 'node main.js'` (05:58:00.862770811Z, id `…d03d9a08`) with the pod as `instance`.
- **Dockerfile.** On `type=build`, all three returned the same 12 lines and ids, `Deploying...` and the `WEB_CONCURRENCY` line included. On `type=app`, none carries a platform line.
- **Static site.** On `type=build`, all three returned the same three lines.
- **The subscribe stream.** The CLI's `--tail` (the WebSocket `GET /v1/logs/subscribe`) carried `Deploying...` and the `WEB_CONCURRENCY` line as they were recorded, on the `--type build` tail and the type-less tail alike. The type-less tail also carried `Running 'node main.js'` (t008 § Walk).
- **The dashboard's deploy log pane.** Checked through its own document (`dashboard/src/features/logs/api/logs.graphql` `Logs`, the GraphQL reads above) and its merge, not rendered: this host has no Playwright browser. `useDeployLogs` merges the build, pre-deploy and app legs with a stable sort. `toLogLines` reverses each newest-first page first, so lines that share one stamp keep the API's order (the Dockerfile service's port line and live line). The Node legs merge into Render's order, with `Running` once: `Deploying...`, `WEB_CONCURRENCY=1`, `Running 'node main.js'`, the app's line, then the live line.
- **Against Render's logs** (milestone README: DerekSopok/EMS-Kahoot#3 and frayel/devagent#62 native, darthjee/ward#109 and Collective-Intelligence-Labs/omnichain-payments-evm#46 Dockerfile):
  - Render writes `Deploying...` 0.1 s to 34 s after the build's last line. bex wrote it 6.2 s and 3 s after.
  - The `WEB_CONCURRENCY` line comes right after, in both.
  - `Running` appears on the native runtime only. Render writes it 9 s to 12 s after `Deploying...`, and bex wrote it 12.5 s after.
  - Render's log `type` for these lines stays open in [w32/085](../../../blocked/085.md).

No surface drifts, so no new item is filed. One gap sits outside this milestone: a no-build static site's log has no `==> Uploading build...` line. [w32/081](../../081.md) records that Render's narration of a no-build site is not observed.
