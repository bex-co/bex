# Every build of a service with a secret file fails with "a platform error … contact support": the build Job's new projected volume is denied by `bex-build-job-shape`

Why: since the 2026-11-14 22:44 UTC deploy, a repo-backed service that has a secret file cannot deploy at all. Its build fails within seconds and tells the customer to contact support. This regresses w4/m163, verified on production 2026-10-29, which made build commands read secret files at `/etc/secrets/<name>` as on Render. Render documents secret files for builds: "For non-Docker services, … available … during builds", and Docker builds get them as build secrets.

- **Seen:** `/qa-find-bugs-cli` sweep 27 (nonce a308), 2026-11-15 02:19–02:27 UTC, release `bex` v0.6.0 (Render CLI v2.36.0 pin), `https://api.bex.co/v1/`, production pin `2d9bbae6bb8d`, `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login. - **Cause (traced at `f05cc9694`, the same code as the deployed pin):**
  - `deploy/gitops/base/operator-workload-admission.yaml:658-660`, policy `bex-build-job-shape`, binds every Job created in `bex-build`. It admits only `(has(v.emptyDir) || has(v.secret))` volumes. Its own header says it is fail-closed on purpose: "a legitimate template change (new volume type …) must update this policy in the same commit".
  - w4/m363 (`4e6c15481`, 2026-11-14) replaced the build's secret-files volume `secretVolume(secretFilesVolume, o.NativeFilesSecret)` with `projectedSecretsVolume(secretFilesVolume, o.NativeFilesSecrets)` (`lego/operator/internal/build/build.go:1369-1370`, helper `:1210`). It packs the merged files into several Secrets so none passes Kubernetes' limit. The policy was not changed.
  - The Job create is therefore denied. The operator masks the admission denial as `platform_error` with a reference (`controller/platform_refusal.go`, w9/090), and the deploy ends `build_failed` before any pod exists.
  - Not caught by tests: the envtest that runs the real build Job against `bex-build-job-shape` (`controller/container_policy_admission_test.go:615-634`, w21/m409) builds its Job with no secret files, no runtime env Secret and the default builder, so the projected volume never reaches the policy.
- **Blast radius:** every Job `build.BuildJob` writes with `NativeFilesSecrets` set, which is any secret file in scope for the release: the service's own or a linked environment group's (`secretFileSources`). That covers:
  - native builds (web, private, worker, cron, static with a build path);
  - Dockerfile builds, which receive the same volume for build secrets (`build.go:1369-1373`, `dockerinputs.go:162`);
  - build-source services.
  - Not affected: image-backed services (no build), and a direct static publish (no build command, a publish Job). w4/m363's own live fixture is an image service, so its t008 replay would not see this.
- **Fix:**
  1. Admit a projected volume of non-crown Secrets in `bex-build-job-shape`, for example `has(v.emptyDir) || has(v.secret) || (has(v.projected) && v.projected.sources.all(s, has(s.secret) && !(s.secret.name in variables.crownSecrets)))`. Update the policy's message and the header comment.
  2. Make the envtest create the build Job with every volume `build.BuildJob` can add: `NativeFilesSecrets` (two shards), `RuntimeEnvSecret`, the native builder and a Dockerfile build. Assert the operator's own author passes and a crown Secret inside a projected volume is still denied. If `scripts/gitops-validate.sh` pins the policy text, update its guard.
  3. Optionally, a CI check that renders every `BuildJob` option combination and evaluates the policy, so the next volume type fails CI, not production.

**Done (2026-11-15, `ca40b50cc`):** `bex-build-job-shape` now admits a projected volume whose every source is a non-crown Secret. A crown Secret, a ServiceAccount token or a downward-API source in a projection is still denied.
