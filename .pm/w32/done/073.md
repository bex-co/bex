# After a no-changes or unsaved failed plan, bex's Blueprint approve refuses or supersedes an earlier waiting plan; the pinned Render CLI says Render's approve still applies it

Why: Render parity is the top product rule. The pinned CLI tells users that an earlier plan still waiting for approval stays the one `approve` applies, and bex behaves differently.

- **Severity / estimate:** minor, parity, ~1h.
- **Contract (pinned `render-oss/cli` `v1.1.3-0.20261106232710-4fd34231b637`, `pkg/blueprint/output.go`):**
  - `replanNoChangesNext` (`:105-111`): "A plan with no changes is not saved, so an older planned sync can still be the newest one, and approve would apply it." The user-facing text: "If you previously planned changes that are still waiting for approval, running `render ea blueprints approve <id>` now will approve that earlier plan."
  - `NewPlanOut` (`:70-81`) and `NewUpdateOut` (`:87-101`) cover a failed plan that saves no sync: "approve could still apply it". A failed plan that saves a sync is the newest one instead, and approve refuses it.
- **bex today (from w32/071's worker, 2026-11-21, `f3068e934`):** after a newer no-changes or failed plan, bex either refuses the approve or marks the earlier waiting plan superseded. w32/071 made a later no-changes plan answer `409 (BLUEPRINT_NOTHING_TO_APPROVE)`, also after a superseded or applied plan.
- **Unverified:**
  - Which exact sequences differ. Walk each one against bex, starting from a plan waiting for approval:
    1. a no-changes re-plan
    2. a failed re-plan with no saved sync
    3. a failed re-plan with a saved sync
    4. an `update --path` with a failing re-plan
  - Render's live answer for each. There is no Render account (w10/002), so the pinned CLI's text and Render's public API docs are the evidence.
- **Fix direction:** a no-changes plan, and a failed plan that saves no sync, leave the earlier waiting plan as the newest, and `approve` applies it. Keep w32/071's 409 for the case where nothing is waiting. Record any divergence that stays in ADR018 with the user's sign-off, per the parity rule.

## Acceptance

- Backend tests pin each of the four sequences to the behavior the pinned CLI's text describes.
- If bex changes, ADR018's Blueprint approve row states the behavior.
- A live walk in `bex-canary` with the released `bex` runs once the pin carries the fix: plan with changes, re-plan with no changes, approve applies the first plan. Fixtures deleted.

## Triage and fix (2026-11-21, `/loopx w32`) — parked for the production check

Evidence: the pinned CLI's `pkg/blueprint/output.go`, `pkg/blueprint/service.go` (`Update` reports a plan request that errors as `failed` with no sync) and the generated client's approve doc ("Approve the newest Sync in the `created` state…"). Render's public API (`api-docs.render.com/openapi/render-public-api-1.json`, read 2026-11-21) documents no plan or approve operation, and render.com/docs/infrastructure-as-code says nothing about them. bex on main before the fix, each sequence starting from a plan waiting for approval:

1. **A no-changes re-plan: diverged.** `SettleNoChangesPlan` marked the waiting plan `superseded` (w2/m256 t014, no ADR018 sign-off), so approve answered `409 BLUEPRINT_NOTHING_TO_APPROVE`. Render's approve applies the waiting plan.
2. **A failed re-plan with no saved sync: already matched.** Every `failed` outcome bex answers carries the `error` sync it saved (`recordFailedPlan` is the only source of `failed`). So the CLI reaches this branch only when the plan request itself fails, and that request saves nothing. The waiting plan stays the newest, and approve applies it.
3. **A failed re-plan with a saved sync: already matched.** The `error` sync is the newest, and approve refuses it with `409 BLUEPRINT_SYNC_PLANNING_FAILED`, naming that sync.
4. **`update --path` with a failing re-plan: already matched.** The re-plan saves its `error` sync, which approve refuses as in 3. A related divergence came out of this walk and is filed as w32/074: when nothing new is saved after a path `PATCH`, approve refuses the waiting plan with `409 BLUEPRINT_SOURCE_CHANGED`, and after a branch `PATCH` the apply compiles that plan with the new branch.

Fixed in `9f908886f`. `SettleNoChangesPlan` no longer touches waiting plans. It still stamps `no_changes_planned_at` (w32/071) and still takes a `created` Blueprint to `in_sync` or `paused`. A waiting plan older than the stamp is the newest sync, and approve applies it. Admitting a planned row now clears the stamp in the claim's `UPDATE`, so a second approve names the applied sync rather than "the newest plan … found no changes". REST, GraphQL `approveBlueprint` and MCP `approve_blueprint` share `ApproveBlueprint`.

- Tests (`lego/backend/internal/apps/blueprint_approve_waiting_plan_test.go`): one test per sequence on the fake store, a `created` Blueprint's first plan approved after a no-changes re-plan, and sequence 1 on real Postgres. `TestNoChangesPlanSupersedesAWaitingPlan` is replaced, and `TestBlueprintPlanConnectionAndNoChangesPG` now expects the waiting plan kept. Before the fix, both sequence-1 tests failed. With the supersede restored on Postgres, the store and apps PG tests fail. With the stamp left in place at approval, the second approve fails. The full real-DB backend gate passed.
- Docs: ADR049 § Blueprint onboarding's approve and no-changes bullets, and ADR018's Blueprint onboarding row, which also names w32/074 as open.
- Deviation: the dashboard shows a waiting plan only while the Blueprint is `created`. After a no-changes re-plan a `created` Blueprint reads `in_sync`, so its waiting first plan can be approved from the CLI, REST, GraphQL and MCP but is not shown on the Blueprint page. A waiting re-plan of an approved Blueprint was already in that position.
- Follow-up w32/075: Render deletes a planned sync not approved within 24 hours, and bex never expires one. That matters more now that a no-changes re-plan no longer clears it.

**Next, once the pin carries `9f908886f`:** in `bex-canary`, with the released `bex` and a human device login (`scripts/qa-login.sh --login-challenge`), create and approve a Blueprint from `https://github.com/render-examples/go-web-server` (one free web service). Delete that service by ID, then run `ea blueprints plan`, which must answer `planned` with `create` of the service. Run a manual sync (`POST /v1/blueprints/{id}/sync`) that re-creates the service, then `ea blueprints plan` again, which must answer `no_changes`. `ea blueprints approve` must then print the first plan's sync id as approved, not a 409. Delete the Blueprint and its service by ID, check that each `GET` answers 404, and close.
