# `bex ssh --help` and `bex ea blueprints --help` link Render's docs instead of Bex's

Why: the help tells a Bex user to add their SSH key to their **Bex** account, then links Render's instructions for doing that in Render's dashboard. Bex publishes its own SSH and Blueprints pages, and w7/045 already ruled that supported help must not send users to `render.com/docs`.

- **Severity:** minor (docs destination in help; no request or exit status changes)
- **Versions:** bex v0.5.0 (latest release `bex-cli/v0.5.0` = `f43a4ffa1`, linux-arm64 tarball verified with `checksums.txt`). HEAD `3a12969ed` has the same `lego/cli` (only `testdata/sandbox-file-contract.json` differs), so this is not deploy lag. Upstream pin Render CLI v2.35.0 (`24ac2d60`). Deployed revision: n/a (client-side help).
- **Context:** 2026-11-09 `/qa-find-bugs-cli w32` loop sweep, offline (the QA sign-in is still refused: `qa-login.sh` → `error: login failed — no session established`, see w32/m284). Isolated `BEX_CLI_CONFIG_PATH`, `BEX_HOST=https://api.bex.co/v1/`, `RENDER_*`/`BEX_*` unset, non-TTY.
- **Repro:** `bex ssh --help` and `bex ea blueprints --help`.
- **Expected:** links to the Bex pages for the same topics. Both pages are live (HTTP 200): `https://bex.co/docs/platform/ssh#register-a-public-key` ("SSH and web shell | Documentation | bex.co") and `https://bex.co/docs/platform/blueprints` ("Manage Blueprints | Documentation | bex.co").
- **Actual:** exit 0, and:
  - `bex ssh --help`: `SSH uses your local SSH keys. Add the public key to your Bex account before you connect. See https://render.com/docs/ssh#ssh-setup.` (`your Render` is rewritten to `your Bex`, the URL is not, so the sentence is now self-contradictory.)
  - `bex ea blueprints --help`: `Manage your Bex infrastructure as code with Blueprints. … Learn more: https://render.com/docs/infrastructure-as-code`
- **Attribution:** Bex launcher (help branding overlay).
- **Root cause:** both strings arrived with the v2.35.0 pin bump (w2/m256, `cc2043ca8`, 2026-11-05). Upstream `cmd/ssh.go:33` (absent at v2.29.0, the v0.4.0 pin) and `cmd/blueprints.go:33` (`ea blueprints` is new in v2.35.0). `branding.RewriteText` deliberately never rewrites hostnames, so a `render.com/docs` link in help needs a narrow per-command override. Only `jobs create` has one (`lego/cli/internal/branding/branding.go:148-155`, w7/045). The pin-bump runbook (`lego/cli/UPSTREAM_RENDER_CLI.md` step 4) lists the strings to grep new help for (`~/.render/state/`, `RENDER_CLI_CONFIG_DIR`, `| render `) but not `render.com/docs`, so neither bump caught these.
- **Fix:** in `brandTree`, beside the `jobs create` override, replace the two URLs in `c.Long` for root-level `ssh` and `ea blueprints` only:
  - `https://render.com/docs/ssh#ssh-setup` → `https://bex.co/docs/platform/ssh#register-a-public-key`
  - `https://render.com/docs/infrastructure-as-code` → `https://bex.co/docs/platform/blueprints`

  Keep the no-global-hostname-rewrite rule. Add `render.com/docs` to the step-4 grep list in `UPSTREAM_RENDER_CLI.md`. Update the w7/045 sentence in `docs/bex-cli.md` § Compatibility and branding limits ("the one help page that cited `render.com/docs`…") to list all three overrides. No REST/GraphQL/MCP/UI surface is involved.
- **Blast radius:** a sweep of all 134 v0.5.0 help pages found no other `render.com/docs` link. Remaining `render.com`/`RENDER_*` hits are non-goal families (`workflows dev` `RENDER_USE_LOCAL_DEV`/`RENDER_LOCAL_DEV_URL`, `ea objects` `RENDER_REGION`) and the intended `workspace set` `RENDER_CLI_CONFIG_*` precedence text. The `workflows init` run-time "Visit our docs … render.com/docs/workflows" line is inside a non-goal command and has no Bex page; leave it.
- **Regression checks:** in `TestBexNestedHelp` (`lego/cli/main_test.go:969`), add cases `ssh` (want `bex.co/docs/platform/ssh`, absent `render.com/docs`) and `ea blueprints` (want `bex.co/docs/platform/blueprints`, absent `render.com/docs`). Better still, add a tree walk asserting no supported command's help contains `render.com/docs`, with an explicit allowlist for the non-goal `workflows`/`ea objects` families, so the next pin bump fails CI instead of a QA sweep finding it. Then `cd lego/cli && go test ./...`, and spot-check `bex ssh --help`, `bex ea blueprints --help`, and that `bex jobs create --help` stays clean.
- **Unverified:** whether `bex ssh` run-time errors (e.g. no registered key) also cite Render docs. That needs an authenticated session and an owned service, both blocked this sweep.
- **Dedupe:** w7/done/045 (the `jobs create` link only) and w2/done/044. The m256 pin-bump tasks never audited help links. Nothing open on any workstream's board mentions these URLs. Not in `DO_NOT_DO.md`, the `docs/bex-cli.md` residual list, or the checklist non-goals (`ssh` and `ea blueprints` are supported).
- **Estimate:** 25m

## Done (2026-11-11, `/loopx w32`)

- **Fixed:** `branding.helpDocsLinks` (`lego/cli/internal/branding/branding.go`) maps the two links to their Bex pages, and `brandTree` applies each to its own command's `Long` only: `ssh` → `https://bex.co/docs/platform/ssh#register-a-public-key`, `ea blueprints` → `https://bex.co/docs/platform/blueprints`. Hostnames are still never rewritten globally.
- **Tests:** two `TestBexNestedHelp` cases, and `TestNoHelpLinksRenderDocs`, which walks every help page of the built launcher (141 at the v2.36.0 pin; the provider launchers are skipped because they hand `--help` to Claude Code) and fails on any `render.com/docs` link. With the `ssh` entry disabled both tests fail. `go test ./...` and golangci-lint v2.15.0 pass for `lego/cli`.
- **Docs:** the pin-bump runbook (`lego/cli/UPSTREAM_RENDER_CLI.md` step 4) now says to grep new help for `render.com/docs`, and `docs/bex-cli.md` lists all three per-command overrides.
- **Still unverified:** whether `bex ssh` run-time errors cite Render's docs (needs a signed-in session). The fix reaches users with the next `bex-cli` release.
