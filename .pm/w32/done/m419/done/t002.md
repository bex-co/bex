## Objective

Prove that t001 covers every operational setting on an App whose newest image release was refused, not only the two observed live (service IP allow-list and suspend).

## Context

- Every setting converged by `dispatchRuntime` → `reconcileKubernetes` was skipped while the refused image stopped the pass at `app_controller.go:777`.
- The workspace and environment rule fan-outs write every App in scope (w9/m388, w4/m28), so one refused App ignored a workspace-wide rule.

## Steps

1. For an App with a served release and a refused candidate, check each row in envtest. Check it on production where it is cheap and free.
   - service IP allow-list restrict / reopen
   - environment-layer rules (`spec.environmentIPAllowList`)
   - workspace-layer rules (`spec.workspaceIPAllowList`)
   - suspend / resume
   - free-tier auto-sleep and wake
   - custom domain add / remove (hosts)
   - `numInstances`, autoscaling
   - maintenance mode
   - edge-cache profile middleware
   - an image-port private service
2. Repeat the allow-list and suspend rows for each refusal reason: 404 (`DeployReasonImageNotFound`), 401/403 (`ImagePullFailed`), other (`ImageMetadataUnavailable`).
3. Repeat them for a bad tag saved with `services update --image` and then deployed, as well as for a per-deploy `--image` override.
4. Record the matrix in the milestone README. A row that turns out unreachable on this path gets its evidence.
