# `undeployedChangesReason` goes stale after a save races the main reconciler: `false` with `saved`, or `true` with an empty reason

Why: REST, GraphQL and MCP promise the reason is empty while `undeployedChanges` is false, and the dashboard picks its hint from it (`image_override` gets its own wording), but after a save that lands while the main reconciler writes status, the reason keeps the value from before the save, with nothing to repair it until the next spec change.

- **Severity / estimate:** minor, ~40m.
- **Seen:** w32/053's production walk, 2026-11-21 01:41–01:54 UTC, pin `820edf28d22d` (`bex-operator@sha256:ca059b406934…`), workspace `bex-canary`, released `bex` v0.7.0 as the QA user. Read through GraphQL `service(id:) { undeployedChanges undeployedChangesReason }`, REST, and the App CR on the control plane. Both fixtures are deleted.
  - Native Node web service `srv-dc0f8uvob2ts7390kang`: a bad branch was saved and its deploy failed, which read `true` / `saved` (correct). At 01:48:48Z `bex services update <id> --branch main` put the live branch back. From 01:48:50Z until the fixture was deleted at 01:54:40Z, it read **`undeployedChanges: false`, `undeployedChangesReason: "saved"`**. The CR's status had no `undeployedChanges` and had `undeployedChangesReason: saved` at 01:49:45Z.
  - Static site `srv-dc0f8orcd0vs73c88e70`: during a later build (`dep-dc0fddjcd0vs73c88fmg`, `build_in_progress`), `--root-directory examples/nope-…` was saved at 01:41:19Z, and the read at 01:41:30Z was **`true` with reason `""`**. The clear 4 s later then read `false` / `""`, so how long the empty reason would have lasted was not measured.
- **Root cause** (`lego/operator/internal/controller`, HEAD `f797f525f`):
  - The `app-config-status` controller owns all three fields (`recordUndeployedChanges`, `saved_configuration.go:195-205`). When a save bumps the App, it patches them while the main reconciler may already hold an older copy of the App.
  - The main reconciler's status write then conflicts. Its retry keeps only two of the three fields from the fresh object: `updateStatusRetrying` (`app_controller.go:7319-7320`) and `setNotReadyCondition` (`:7366-7367`) copy `UndeployedChanges` and `UndeployedChangesApplying`, not `UndeployedChangesReason`. w4/414 (`baa01aa8f`) added the reason after those copies were written. So the write puts the reason back to its value from before the save, next to the fresh flag.
  - Nothing repairs it. `savedConfigurationPredicate.Update` (`saved_configuration.go:54`) wakes the controller only on a generation, `ActiveRevision`, `Phase`, snapshot-generation or annotation change, not on a status-only reason change. The web path requeues after a minute only while it is `different`, has release config sources or carries a saved-config revision annotation (`:119-120`), none of which held here. The static path never requeues. So a `false` flag with a stale reason stays until the next save or deploy.
- **Fix:** have both retries keep `UndeployedChangesReason` from the fresh object, as they already keep the other two fields. One shared helper for those fields would let a later field not be missed again. Add a unit test that simulates the race: the main reconciler holds `true` / `saved`, the fresh object holds `false` / `""`, and after the retry the stored status must read `false` / `""`. Add the reverse case too (`false` / `""` held, `true` / `saved` fresh).
- **Regression checks:** with the fix reverted, the new test fails. On production, a web service whose saved bad branch failed to deploy reads `false` / `""` within seconds of putting `main` back and still a minute later. A static site's root-directory save during a build reads `true` / `saved`.
- **Blast radius:** every App type. The flag itself stays correct, so the dashboard banner shows and hides correctly. What a reader gets wrong is the reason: a stale `image_override` would pick the override hint for a real saved change (`dashboard/src/features/services/lib/status.ts:396`), and API clients see a reason next to `false`.
- **Dedupe:** `rg` of `.pm` for `undeployedChangesReason` / `UndeployedChangesReason`. w4/414 introduced the field, w4/456 is the early-`ActiveRevision` transient, and w21/051's side observation is a `true` / `saved` flag with no reason mismatch. None of them covers a reason that disagrees with its flag.
