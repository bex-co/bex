# The docs say a CLI sandbox upload keeps hard links, but the released CLI's upload stores each hard-linked name as a separate file

Why: ADR018 and the sandbox reference promise that `bex sandboxes copy` keeps hard links in both directions. The upload half is not true for the CLI, so a user who relies on it gets duplicated files (and, for a hard-link-heavy tree, a larger upload) without being told.

- **Seen:** `/qa-find-bugs-cli` sweep 158, 2026-11-16 15:48 UTC, released `bex` v0.7.0 (Render CLI v2.36.0 pin), pin `bf2ab888d7dc`, QA human device login, `bex-canary`, sandbox `sbx-dbtibd1adajs73bactu0` (since stopped):
  - locally `up/f.txt` and `up/hl` share one inode (link count 2) and `up/sl -> f.txt`;
  - `bex sandboxes cp ./up <sbx>:/tmp/up` and `bex sandboxes cp ./up <sbx>:up2` both exit 0;
  - in the sandbox `sl -> f.txt` is kept, but `f.txt` and `hl` have link count 1 and different inodes (4/5 on the `/tmp` tmpfs, 58/59 under the 9p home);
  - the sandbox filesystem supports hard links (a manual `ln` there works), and the download direction keeps them: `bex sandboxes cp <sbx>:. ./home` brought a sandbox hard-link pair down as one inode with link count 2.
- **Cause:** the pinned Render CLI's upload archiver (`github.com/render-oss/cli` `pkg/sandbox/files.go`, the walk around `tar.FileInfoHeader`) writes every regular file as its own entry and never emits a `TypeLink` header. bex's gateway keeps the hard-link entries an archive carries (w32/m380), but this client never sends any. Render's CLI ships the same archiver, and Render's docs promise only symlinks ("Symlinks are preserved, and sockets, FIFOs, and other special files are skipped"), so this is upstream client behavior and parity holds; no code change.
- **Already known on the board, not in the docs:** w32/m380's walk recorded that "the local hard-link pair arrived as two files, as expected" ([m380](done/m380/README.md)). The user-facing docs never picked that up:
  - `docs/ADR018-render-parity.md`, row "Links in a copied directory (CLI `sandboxes copy`, SDK `copy_to`/`copy_from`)": "keeps … its hard links to a file earlier in the same archive, in both directions", "verified on production … with the release CLI";
  - `docs/render-artifacts/ea-sandbox.md`, the **Links (w32/m380)** paragraphs: the same claim, with no exception for the CLI's upload.
- **Fix (docs only):** in both places say that the CLI's upload stores each name of a hard-linked file as a separate file (the pinned client's archiver writes regular entries only), that downloads and any archive that carries link entries keep them, and cite the pinned client's archiver. Leave the symlink and special-file wording as it is.
- **Acceptance:** both docs state the CLI-upload exception; `bash scripts/docs-links-validate.sh` exits 0; `npx prettier@3.4.2 --check` is clean for the touched files.
- **Unverified:** whether the Render Python and TypeScript SDK uploads emit hard-link entries (m380 notes Python's `tarfile` records a second name for an archived inode as a link), so the SDK half of the row may hold.
- **Same sweep, with the release (no action):** w32/022 (`bex sandboxes cp <sbx>:. ./home` copies the home directory, its symlinked directory kept), w32/024 (a download through a symlinked source path, file and directory) and symlink preservation in both directions all hold on v0.7.0.
- **Dedupe:** `git grep -n -i 'hard.?link' origin/main -- .pm` finds only w32/m380 (done, where this is recorded as expected), w32/022, w32/023 and w32/025 (done or unrelated), and w7/m150. No open item covers the doc wording.
- Minor, docs only, ~15m.

**Done 2026-11-17 (docs only):** ADR018's "Links in a copied directory" row, `ea-sandbox.md`'s **Links (w32/m380)** paragraph and the `sandboxes copy` row of `cli-compatibility-checklist.md` (a third place with the same claim) now say a download keeps the sandbox's hard links and an upload keeps them only in an archive the caller built, while `bex sandboxes copy` and the Python SDK's `copy_to` store each name as a separate file. The **Unverified** point is settled from the released packages: `render` 1.8.0 (which `render-sdk` 1.8.0 aliases) `render/experimental/sandbox/_tar.py` `_entry` turns `gettarinfo`'s link entries into regular files ("Store each name as its own regular file instead"), and its `files.py` `extract_tar` restores a downloaded link with `os.link`; `@renderinc/sdk` 1.8.0 has no directory archiver, and its `upload` sends the caller's bytes (`application/x-tar` or `application/gzip`) as they are. The pinned client's `writeTar` (`render-oss/cli@v1.1.3-0.20261106232710-4fd34231b637` `pkg/sandbox/files.go`) calls `tar.FileInfoHeader`, which never writes `TypeLink`.
