## Objective

Drive create, get, list (status and name filters), exec, file upload/download, wait, terminate, snapshots and groups, and the error classes in both SDKs against bex, and grade each in a new SDK section of the compatibility checklist.

## Context

- Grades use the checklist legend (`[x]` works, `[~]` partial, `[-]` non-goal with reason)
- Groups are an approved non-goal (w7/m150); snapshots are w32/m285

## Steps

1. Run the scenario on a dev-N stack with sandbox routes mounted, then on production.
2. For every failure, record attribution: bex-api gap, SDK behavior, or documented non-goal.
3. Write the grades.

- docs/cli-compatibility-checklist.md

## Acceptance criteria

- [x] Each sandbox method of both SDKs has a grade with evidence
- [x] Each failure is attributed

## Result — 2026-11-17 (done)

- `scripts/render-sdk-compat.sh` now walks every v1.8.0 sandbox method of both SDKs, the Python async client and the generated execution, image-list and credential calls. It creates disposable deny-all sandboxes, a disposable group and an imported image, and removes them all. `SDK_COMPAT_SUSPEND=1` also waits out an idle suspension and resumes.
- It ran on production as the QA user in `bex-canary` with a device-login token from released `bex` v0.7.0. The last run passed all 64 steps (35 Python, 29 TypeScript), and the suspend step passed in an earlier run. One earlier run hit two client-side 5 s TLS handshake timeouts, which did not recur.
- Grades and attribution: `docs/cli-compatibility-checklist.md` § Render SDK. No step failed because of bex.
