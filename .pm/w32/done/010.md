# `bex agent … --follow` exits 1 and prints no result when its last transcript read hits one transient error

Why: a CI job that runs `bex agent run --follow` fails, with no session JSON on stdout, although the session succeeded and the CLI had already read that. The trigger is one 429, gateway 5xx or dropped connection on a single request. A pipeline that retries the step starts a second paid session unless it passed `--idempotency-key`.

- **Severity:** minor (rare trigger, but a false failure in exactly the unattended use `--follow` is for)
- **Versions:** bex v0.5.0 (release) and a checkout build of HEAD `57498b14b` (Render CLI pin v2.36.0). Same result on both. Deployed revision: n/a (client-side; `bex agent` is Bex-native code, not upstream).
- **Context:** 2026-11-11 `/qa-find-bugs-cli w32` loop sweep, offline (the QA sign-in is still refused, see w32/m284). No production request: a loopback stub of the agent-session routes, shaped after `lego/cli/testdata/agent-cli-contract.json`, with a placeholder `BEX_ACCESS_TOKEN` and `BEX_WORKSPACE`. Non-TTY.
- **Repro:** the stub answers the session read `state: succeeded`, and answers the transcript normally until the read that follows that session read, which gets one `503` (or `429` with `Retry-After: 1`).
  1. `bex agent run --follow -o json "stub task"`
  2. `bex agent logs <ags-id> --follow -o text`
- **Expected:** the read is retried, as `docs/bex-cli.md:168` promises for a wait ("survives up to five consecutive transient failures (a 429, a gateway 5xx or a dropped connection), waiting at least as long as a `Retry-After` asks"). The command then prints the session and exits by its state: 0 here.
- **Actual:** no retry, exit 1 after 2 s.
  1. stdout is empty. stderr: `Started ags-d0stub0000000000000a`, the transcript, then `Error: read transcript of agent session ags-d0stub0000000000000a: 503 STUB_TRANSIENT: stub transient failure`.
  2. stdout has the transcript. stderr: the same error (`429 STUB_TRANSIENT` in the 429 case).
- **Wire evidence (case 1, in order):**

  ```text
  POST /v1/agent-sessions?ownerId=tea-d0stub0000000000000a                             -> 201
  GET  /v1/agent-sessions/ags-d0stub0000000000000a/transcript?limit=1000               -> 200 (1 part)
  GET  /v1/agent-sessions/ags-d0stub0000000000000a/transcript?afterSeq=1&limit=1000    -> 200 (empty)
  GET  /v1/agent-sessions/ags-d0stub0000000000000a/transcript?afterSeq=1&limit=1000    -> 200 (empty)
  GET  /v1/agent-sessions/ags-d0stub0000000000000a                                     -> 200 state=succeeded
  GET  /v1/agent-sessions/ags-d0stub0000000000000a/transcript?afterSeq=1&limit=1000    -> 503
  ```

- **Controls:** with every read answering 200 the same commands exit 0, and case 1 prints the session JSON. With the `503` moved one read earlier (the quiet poll, before the session read) the command also exits 0, so the tolerance works everywhere but on the last pass.
- **Attribution:** Bex launcher (`lego/cli/internal/agent`).
- **Root cause:** `follow` reads the transcript once more after the session settles, for parts that land with the state change, and returns that read's error as it is: `lego/cli/internal/agent/watch.go:221-225`. Every other read in the loop goes through `poll.tolerate` (`watch.go:199-207`, `:211-217`). The settled session it has just read (`s`, `raw`) is dropped, so `await` and `report` never print it, and held partial rows are never flushed. `run --follow`, `send --follow` and `logs --follow` share this function. `--wait` and `bex agent wait` do not read the transcript and are not affected.
- **Fix:** make the last pass as tolerant as the rest.
  1. Retry the final `drain` on a transient error (`transient(err)`), sleeping through the same `poller` so `Retry-After` is honored, up to `transientLimit` tries.
  2. If it still fails, or fails with a non-transient error, do not lose the result: flush what was held, warn on stderr that the end of the transcript could not be read, and return the settled session so the command prints it and exits by its state. The state is already known and is what `--follow` promises to exit by.
  3. Keep `--timeout` and Ctrl-C behavior: a deadline or interrupt during the retries ends them, and the settled session is still returned (as line 223 already does when `ctx` has ended).

  No REST/GraphQL/MCP/UI surface is involved.

- **Blast radius:** one function, three callers through `await` and `logsCommand` (`lego/cli/internal/agent/agent.go:773-797`, `:680-687`). JSON output on stdout is unchanged when nothing fails.
- **Regression checks:** beside `TestFollowWaitsForCompleteCopiesAndExitsByState` (`lego/cli/internal/agent/agent_test.go:691`):
  - a `503` on the read after the settled session read, then 200 → exit by state, session printed, the transcript read retried once;
  - a `429` with `Retry-After` there → the retry waits at least that long;
  - that read failing `transientLimit` times → the session is still printed, exit by state, one warning on stderr;
  - `run --follow -o json` under the first case → stdout is exactly the session JSON.

  Then `cd lego/cli && go test ./...`.

- **Unverified:** how often production answers a 429 or 5xx on that read; no live session was run. Seen in the code but not exercised: successful session reads reset the failure counter (`watch.go:104-106`), so a transcript route that keeps failing while session reads succeed is tolerated without limit until the session settles, and then fails here.
- **Dedupe:** nothing in `.pm/` (open or done) mentions the final transcript pass. w9/m177 (blocked on the CLI release) shipped `bex agent`; its tests cover transient reads for `wait` (`TestWaitSurvivesTransientReadsButNotMissingSessions`) and a quiet follow, not this read. Not in `DO_NOT_DO.md`.
- **Estimate:** 40m

## Done (2026-11-11, `/loopx w32`)

- **Fixed:** `follow` now makes its last transcript read through `drainTail` (`lego/cli/internal/agent/watch.go`), which retries a transient failure through the follow's own `poller`: up to `transientLimit` tries, sleeping at least `pollFirst` or the `Retry-After`. An error that remains (an outage, or a refusal, which is not retried) no longer replaces the result. Held partial rows are flushed, the settled session is returned with the error in `waitResult.tailErr`, and `run`/`send --follow` and `logs --follow` print one warning on stderr: "the end of the transcript may be missing: … `bex agent logs <id>` prints the whole transcript." The command then prints the session and exits by its state. A `--timeout` or Ctrl-C during the retries ends them and still returns the settled session.
- **Tests** (`lego/cli/internal/agent/agent_test.go`; the fake API can now land rows with the state change and fail the reads after it):
  - `TestFollowKeepsTheResultWhenTheLastTranscriptReadFails`: a 503 is retried and the tail prints; a 429 waits out its `Retry-After`; an outage of `transientLimit`+1 reads and a 403 each cost only the tail, with one warning and the partial row shown; every case exits by the session's state.
  - `TestRunFollowKeepsJSONStdoutClean`, now three cases: `run --follow -o json` prints the session JSON on stdout when every read answers, when the last one is retried and when it is given up.
  - `TestFollowReturnsTheSettledSessionWhenStoppedWhileRetryingTheLastRead`.
  - With the retry removed, or with the old "return the error" path restored, these fail. `go test ./...` and golangci-lint v2.15.0 pass for `lego/cli`.
- **Docs:** `docs/bex-cli.md` § `bex agent`, the Waiting rule.
- **Still unverified:** no live session was followed (QA sign-in, w32/m284). Not changed: while a session is still working, a transcript route that keeps failing is tolerated as long as session reads succeed, as before. The fix reaches users with the next `bex-cli` release.
