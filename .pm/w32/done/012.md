# `BEX_WORKSPACE` set to a workspace name that starts with `tea-` is never resolved

Why: `docs/bex-cli.md:58` says `BEX_WORKSPACE` takes a workspace id or name. A workspace whose slug or display name starts with `tea-` (for example `tea-house`) is taken for an id, sent as `ownerId=tea-house`, and every command fails with the "not allowed" answer that name resolution (w8/038) was added to remove.

- **Severity:** minor (only names that begin with `tea-`; the id and `bex workspace set` still work)
- **Versions:** bex v0.5.0 (release) and a checkout build of HEAD `6e893bfb8` (Render CLI pin v2.36.0). Same result on both. Deployed revision: n/a (client-side).
- **Context:** 2026-11-11 `/qa-find-bugs-cli w32` loop sweep, offline (the QA sign-in is still refused, see w32/m284). No production request: a loopback stub that answers `GET /v1/owners?name=` with one workspace for the names it knows and refuses any `ownerId` that is not that workspace's id, with a placeholder `BEX_ACCESS_TOKEN`. Non-TTY, `-o json`.
- **Repro:** the stub knows the names `acme` and `tea-house`, both for workspace `tea-d0stub0000000000000a`.
  1. `BEX_WORKSPACE=tea-house bex services -o json`
  2. `BEX_WORKSPACE=tea-house bex agent list -o json`
  3. `BEX_WORKSPACE=acme bex services -o json` (control)
- **Expected:** as in the control: one `GET /v1/owners?name=tea-house`, then the command runs with `ownerId=tea-d0stub0000000000000a`.
- **Actual:**

  ```text
  $ BEX_WORKSPACE=tea-house bex services -o json        → exit 1
  Error: you are not allowed to take this action
    GET /v1/services?ownerId=tea-house&includePreviews=false&limit=100 -> 403   (no /owners lookup)

  $ BEX_WORKSPACE=tea-house bex agent list -o json      → exit 1
  Error: list agent sessions: 403 not allowed
    GET /v1/agent-sessions?limit=20&ownerId=tea-house -> 403

  $ BEX_WORKSPACE=acme bex services -o json             → exit 0, []
    GET /v1/owners?name=acme&limit=100 -> 200
    GET /v1/services?ownerId=tea-d0stub0000000000000a&includePreviews=false&limit=100 -> 200
  ```

- **Attribution:** Bex launcher (`lego/cli/internal/bridge`).
- **Root cause:** `resolveWorkspaceName` skips the lookup for any value with the `tea-` prefix: `strings.HasPrefix(name, workspaceIDPrefix)` (`lego/cli/internal/bridge/workspace.go:75`). A workspace id is `tea-` plus a 20-character xid, and the rest of the system checks that shape:
  - the server treats a value as a workspace id only when it is well formed (`ids.KindOf`, `lego/backend/internal/id/id.go:266`; used for the same header in `lego/backend/internal/api/cli_workspace.go:58`);
  - the launcher's own `typedResourceID` is `^[a-z]{3}-[0-9a-z]{20}$` (`lego/cli/main.go:299`).

  Such names exist: a workspace slug is any DNS label (`validWorkspaceName`, `lego/backend/internal/workspaces/service.go:52`) and the display name is freeform (w3/m246).

- **Fix:** treat the value as an id only when it has the id's shape (`^tea-[0-9a-z]{20}$`, the pattern `typedResourceID` uses); resolve anything else as a name. A name that is itself id-shaped keeps meaning the id, as on the server, where a lookup matches an id before a name. Update the sentence in `docs/bex-cli.md:58` only if its wording needs it; the behavior it describes becomes true. No REST/GraphQL/MCP/UI surface is involved.
- **Blast radius:** one condition. Every command that reads the active workspace goes through it (`ResolveWorkspaceName`, called from `lego/cli/main.go:80`). A real id still costs no request. `RENDER_WORKSPACE` set by the user stays untouched.
- **Regression checks:** in `TestResolveWorkspaceName` (`lego/cli/internal/bridge/workspace_test.go:12`):
  - `tea-house` with one listed owner → the owner's id, one lookup;
  - `tea-house` with no listed owner → `no workspace named "tea-house"`;
  - a 24-character well-formed id → unchanged, no lookup (already covered).

  Then `cd lego/cli && go test ./...`.

- **Unverified:** production's exact answer to `ownerId=tea-house`; the stub's 403 follows the bridge's own comment ("a name used to fail everywhere with a misleading 'not allowed'", `workspace.go:27-28`). No workspace with such a name was created.
- **Dedupe:** w8/done/038 added the resolution "when `BEX_WORKSPACE` is not a `tea-` id" and w8/done/064 and 078 refined when it runs; none considers a name with that prefix. Nothing open covers it. Not in `DO_NOT_DO.md`.
- **Estimate:** 20m

## Done (2026-11-11, `/loopx w32`)

- **Fixed:** `resolveWorkspaceName` (`lego/cli/internal/bridge/workspace.go`) takes a value for an id only when it matches `^tea-[0-9a-v]{20}$`; anything else, including a name that starts with `tea-`, is looked up as a name. The alphabet is the xid's base32-hex (`0-9a-v`), which is what the server checks before it reads a value as an id (`wellFormed`, `lego/backend/internal/id/id.go:172`), not the looser `[0-9a-z]` of `typedResourceID` that this note suggested: with the server's own rule the launcher and the server agree on every value. A well-formed id still costs no request, and a `RENDER_WORKSPACE` the user set is still untouched.
- **Tests:** four cases in `TestResolveWorkspaceName` (`tea-house` found, `tea-house` unknown, a 20-character tail outside the xid alphabet, an id with one character too many), and `TestStaleWorkspaceNameBlocksOnlyConsumers` now runs the built binary with `BEX_WORKSPACE=tea-house`: one `GET /v1/owners?name=tea-house`, then the resolved id as `ownerId`. With the old prefix-only rule all five fail. `go test ./...` and golangci-lint v2.15.0 pass for `lego/cli`.
- **Docs:** `docs/bex-cli.md`, the `BEX_WORKSPACE` row.
- **Seen, left alone:** two backend tests that are not run in CI spawn the binary with a short fake id in `BEX_WORKSPACE` (`tea-clilive` in `lego/backend/internal/api/cli_binary_live_test.go:49`, `tea-a` from `lego/cli/testdata/sandbox-file-contract.json` in `lego/backend/internal/sandbox/file_roundtrip_test.go:306`). Each spawn now makes one name lookup, which their harness refuses, so the value passes through as before and they still pass. No script or doc passes a short `tea-…` value through `BEX_WORKSPACE`.
- **Still unverified:** production's answer to `ownerId=tea-house`, and a real workspace with such a name (QA sign-in, w32/m284). The fix reaches users with the next `bex-cli` release.
