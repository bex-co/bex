# A single file uploaded to a sandbox with `Content-Encoding: gzip` is refused with 415, where Render's contract gunzips it

Why: Render's file-transfer contract applies `Content-Encoding: gzip` to both upload types. A raw HTTP client that compresses a single file, as Render's reference allows, gets `415 raw uploads do not accept Content-Encoding` on bex.

- **Seen:** w32/041's worker, 2026-11-19, reading Render's contract:
  - `connect-sandbox-files` (the pinned `lego/backend/internal/api/openapi/render-public-api-1.json` and api-docs.render.com, read 2026-11-19): "Use `application/octet-stream` for a single file or `application/x-tar` for a directory archive. For gzip compression, also set `Content-Encoding: gzip`."
  - render-oss/cli `pkg/sandbox/repo.go`: "a single file travels as octet-stream and a directory as an x-tar archive, with Content-Encoding: gzip carrying wire compression independently of either". Its `UploadFile`: "Pass contentEncoding "gzip" to declare a gzip-compressed body, which the server gunzips before handling".
  - `render` 1.8.0 `render/experimental/sandbox/api_sync.py`: "with Content-Encoding carrying wire compression separately".
- **bex today:** `(*Server).upload` in `lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go` refuses every `Content-Encoding` but `identity` on `application/octet-stream`. The CLI and both SDKs send a single file raw, so only a raw HTTP caller hits this.
- **Fix:**
  - Gunzip a gzip-encoded single file the way the archive path does: bound it by the 256 MiB decoded limit, and publish only after the gzip trailer's CRC and length check pass.
  - `Content-Length` then counts compressed bytes, so the stage's byte-count check (`stageScript`'s `wc -c` against `$size`) needs the decoded count. For example, the gateway counts what it sends and compares that with the count the stage reports.
  - The trailer proves the body is complete, so admit a gzip file sent chunked. A nonempty raw body sent with no encoding keeps its `411`.
- **End state:**
  - Gateway tests cover the cases:
    - A gzip file is stored with its decoded bytes.
    - A truncated gzip, a corrupt checksum and an over-bound decoded size answer `400`/`413` and publish nothing.
    - A raw file is unchanged.
  - Then flip ADR018's "Upload content types and encodings" row from 🚧 to ✅, and update `docs/render-artifacts/ea-sandbox.md` § Bounded file transfers and the upload refusal message in `errUploadContentType`.
- Estimate ~1h; minor (no Render client sends it).

## Done (2026-11-19)

- **The change:** `(*Server).upload` in `lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go` accepts `Content-Encoding: gzip` on `application/octet-stream`, as on `application/x-tar`.
  - It gunzips the file within the 256 MiB decoded bound and publishes it only once the gzip trailer's CRC-32 and length check out. A gzipped file may be sent chunked. A plain nonempty file sent chunked keeps its `411`.
  - A truncated or corrupt stream answers `400 invalid gzip upload: …`, and one that decodes past the bound answers `413`. Neither publishes anything. Any other encoding answers `415` for either type.
  - The byte-count check moved from `stageScript` to `publishScript`: the gateway passes the count it sent, after decoding, as `$6`, and a stage that holds another count exits 65 and is removed.
  - `errUploadContentType` now says gzip applies to either type.
- **Tests:**
  - `TestAGzippedFileIsStoredDecoded` covers a file sent with a length and chunked. `TestABadGzippedFileIsRefusedAndNotPublished` covers a truncated trailer, a corrupt checksum, a wrong length, a body that is not gzip, an empty body and an oversized decode. `TestAnUploadInAnotherEncodingIsRefused` and `TestPublishRefusesAFileItsStageDoesNotHoldWhole` cover the rest.
  - `TestAGzippedFileUploadIsStoredDecoded` (`internal/sandbox/file_roundtrip_test.go`) sends the file through bex-api's connect route to the gateway, which runs the real scripts.
  - Three mutations each fail their tests: refusing a gzipped file again, dropping the publish-time count check, and not classifying a bad gzip stream.
  - The existing raw-file tests pass unchanged.
- **Docs:** ADR018's "Upload content types and encodings" row is ✅. `ea-sandbox.md` § Bounded file transfers and the checklist's SDK `upload` row say the same.
- **Not verified live:** no Render client sends a gzipped single file, and this checkout has no Render account to compare against (w32/039).
