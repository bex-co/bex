# `bex s3` tells a throttled `ls`, `info`, `mb`, `cors` or `lifecycle` to "run with a lower --concurrency", a flag those commands refuse

Why: the busy message is the one instruction a throttled user gets, and on most `bex s3` commands following it fails with `unknown flag: --concurrency`, so the advice should name a flag only where the command has it.

- Severity: minor. Nothing is lost; the hint sends the user to a flag the command does not have.
- Versions: released `bex` v0.9.0 (`bex-0.9.0-linux-arm64`, checked against the release's `checksums.txt`). `lego/cli/internal/s3/client.go:233` is unchanged at `main` `3fb0e140d`. Upstream pin v2.36.0 `4fd34231b637`; production pin `cce6c749f6ff`.
- Context: cli-qa routine run `36da`, 2026-11-21 14:40Z. Reproduced against a local stub on `127.0.0.1` (`BEX_S3_ENDPOINT`, `BEX_S3_ACCESS_KEY_ID`/`BEX_S3_SECRET_ACCESS_KEY` set to dummy values) that answers every request `503` with the gateway's own listing-cap body: `<Error><Code>SlowDown</Code><Message>Too many listings from this workspace; Wasabi counts what a listing reads, so they are capped. Retry shortly.</Message>…`. bex's gateway sends that body for a sixth listing in a second (`lego/backend/internal/s3gw/handlers_list.go:71`). It also sends `SlowDown` when a key or workspace is over its request rate (`gateway.go:198`) and when too many transfers are in flight (`handlers_object.go:134`). Not reproduced live: `bex-canary` refuses listings until 2026-12-01 (they count as egress, ADR112 D3), and driving the shared gateway into its cap would load other tenants.

## Repro

```sh
bex s3 ls s3://<bucket>            # after the SDK's retries, exit 1:
# Error: bex object storage is busy (SlowDown: Too many listings from this workspace; Wasabi counts what a listing reads, so they are capped. Retry shortly. (request …)); wait a moment, or run with a lower --concurrency
bex s3 ls s3://<bucket> --concurrency 1
# Error: unknown flag: --concurrency   (exit 1 on v0.9.0; exit 2 since fd970dce7)
```

`bex s3 ls` (buckets or objects), `info`, `mb`, `cors get`, and `lifecycle get` printed the same `--concurrency` advice against the stub, and a `503 ServiceUnavailable` gets it too (`info`: `ServiceUnavailable: Service Unavailable`). Only `cp`, `mv`, `rm`, `sync` and `rb` register the flag (`concurrencyFlag` at `cp.go:101`, `rm.go:97`, `sync.go:281`, `buckets.go:127`). `presign`, `cors set`/`delete` and `lifecycle set`/`delete` reach the same message through `run.fail` and have no such flag either (`public` goes through bex-api, not this path).

## Cause

`explain` (`lego/cli/internal/s3/client.go:193-235`) words every `SlowDown` and `ServiceUnavailable` fault the same way, `…; wait a moment, or run with a lower --concurrency`. It does not know which command failed. `run.fail` (`s3.go:208-216`) is its only caller. Every command reaches it through `deps.open`, which has the `*cobra.Command`.

## Fix

- In `deps.open`, record on `run` whether `c.Flags().Lookup("concurrency")` exists. Pass it to `explain`, which appends `or run with a lower --concurrency` only when it does. Otherwise the message ends `; wait a moment and run it again`.
- Keep the code and message in the parentheses unchanged. They are the gateway's words and name the limit that was hit.
- Docs: `docs/bex-cli.md` § `bex s3` "Flags, output and exit codes" does not quote the message; nothing to change there.

## Acceptance

- A unit test in `lego/cli/internal/s3` drives `ls`, `info s3://bucket/key`, `mb`, `cors get` and `lifecycle get` against an `httptest` server answering `503 SlowDown`. Each exits 1, and its message names `SlowDown` and the server's message, and does not contain `--concurrency`. `cp`, `rm`, `sync` and `rb` still end `or run with a lower --concurrency`. With the fix reverted, the first group fails.
- `cd lego/cli && go test ./...` passes.
- Reaches users with the next `bex-cli` release after v0.9.0. No live walk is needed: the gateway's `SlowDown` bodies are unchanged, and `handlers_list.go:71` is the producer of the text above.

## Dedupe

No board item or commit names the hint (`rg -- "lower --concurrency" .pm`, `git log -S"lower --concurrency"`: only `ed1452f75`, which added it). w8/368 (`fd970dce7`, after v0.9.0) made the unknown flag exit 2 and leaves the hint unchanged. Estimate: ~20m.

## Done

2026-11-21: `deps.open` records on the command's `run` whether it has a `--concurrency` flag (`c.Flags().Lookup("concurrency")`), and `run.fail` passes that to `explain` (`lego/cli/internal/s3/client.go`). A `SlowDown` or `ServiceUnavailable` that outlasts the retries keeps the gateway's code, message and request id in the parentheses. The message ends `or run with a lower --concurrency` only on `cp`, `mv`, `rm`, `sync` and `rb`, and `; wait a moment and run it again` everywhere else. `TestABusyServerSuggestsConcurrencyOnlyWhereTheCommandTakesIt` drives 17 commands against the fake S3 endpoint answering every request `503 SlowDown` with the listing-cap body: `ls` (buckets and objects), `info s3://bucket/key`, `mb`, and `cors` and `lifecycle` `get`, `set` and `delete`, then `cp` up and down, `mv`, `rm` single and `--recursive`, `sync` and `rb`. Each exits 1 after at least five attempts, names the code and message, and has the right ending. With the old `explain` restored, the ten commands with no such flag fail. With the flag lookup forced false, the seven that have it fail. `cd lego/cli && go test ./...` and golangci-lint pass. Deviations from the note: a HEAD answer has no body, so `info s3://bucket/key` and a download's first request name `ServiceUnavailable` and the request id, not `SlowDown` and its message. The test rig gets a zero retry backoff through a new `deps.backoff` (nil is the SDK's exponential backoff), so a fault that every attempt meets fails in milliseconds and not up to 15 s. No live walk, as the note says. Reaches users with the next `bex-cli` release after v0.9.0.
