# The TypeScript SDK can upload a sandbox file as `application/gzip`, and bex's gateway refuses it with 415

Why: Render's released TypeScript SDK offers `application/gzip` as an upload content type. If Render accepts it, a script written against Render fails on bex with `415 unsupported upload Content-Type`, and no checklist row or ADR018 row says so.

- **Seen:** w32/035's worker, 2026-11-17, reading the released Render TypeScript SDK v1.8.0: its `SandboxUploadContentType` includes `application/gzip`.
- **bex today:** `lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go`, `(*Server).upload`, admits `application/octet-stream` (raw, no `Content-Encoding`) and `application/x-tar` (with `Content-Encoding` empty, `identity` or `gzip`). Every other media type gets `415 unsupported upload Content-Type`, so a gzip upload is always refused.
- **Unchecked:** what Render does with an `application/gzip` upload. It might store the bytes as one file, unpack a gzipped tar into a directory, or refuse the request. `docs/cli-compatibility-checklist.md` and the ADR018 sandbox file-transfer rows do not grade this content type.
- **Fix:** settle Render's behavior from its API reference, the SDK source (what the SDK sends with that type, and the path it targets), or a live call. Then make bex do the same, or record the divergence in ADR018 with the reason. Add a gateway test for the chosen behavior, and grade the row in the checklist and ADR018.

**Done 2026-11-19:** Render's behavior is settled from its contract. bex keeps refusing `application/gzip`, and the refusal now names the documented forms.

- **Render documents two upload types.**
  - The `connect-sandbox-files` reference (pinned OpenAPI and api-docs.render.com) says: "Use `application/octet-stream` for a single file or `application/x-tar` for a directory archive. For gzip compression, also set `Content-Encoding: gzip`."
  - render.com/docs/sandboxes-sdk-typescript lists `contentType` as "`application/octet-stream` (default) or `application/x-tar`" (read 2026-11-19).
- **`application/gzip` is a leftover.** It is still in `SandboxUploadContentType` in `@renderinc/sdk` v1.8.0, v1.9.0 and on render-oss/sdk main. It dates from Render's earlier format:
  - render-oss/cli #532 (2026-07-29) uploaded a gzipped directory archive as `application/gzip`.
  - #589 (2026-08-07) moved uploads to `x-tar` with `Content-Encoding: gzip`.
  - #590 (2026-08-17) moved downloads, as the client half of Render's api #34092.
  - The TypeScript type arrived in render-oss/sdk #262 (2026-08-18) and has not changed since.
  - Render's clients now say it "is a payload type the server no longer sends" (render-oss/cli `pkg/sandbox/files_test.go`). Neither the CLI nor either SDK sends it.
- **Live behavior is unmeasured.** No Render account exists here (w32/039's gate). Guessing either earlier meaning, unpacking as a directory or storing as a file, could silently put files where Render does not. The documented refusal fails loudly instead.
- **The change:**
  - `errUploadContentType` answers `415` for any other type, `application/gzip` included. It names `application/octet-stream`, and `application/x-tar` with `Content-Encoding: gzip`, before any sandbox command runs.
  - `TestAnUploadInAnotherContentTypeIsRefusedWithTheDocumentedForms` covers the case. A mutation that accepts `application/gzip` as a gzipped archive fails it.
  - ADR018 has a new "Upload content types and encodings" row. `ea-sandbox.md` and the checklist's SDK `upload` row say the same.
- **Follow-up w32/045:** Render's contract also gunzips a single file sent with `Content-Encoding: gzip`, and bex refuses it with 415.
