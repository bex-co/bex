## Objective

The t008 walk on production (2026-11-17) saw three filesystem captures of the same running sandbox end `failed` with `error: "the sandbox's filesystem could not be committed"`, which is the substrate's `Failed` state (`settleSnapshot`, `lego/backend/internal/sandbox/snapshots.go:791`). All three came between 06:55 and 07:00 UTC, after a production deploy rolled bex-api at 06:53: 3 of the 9 captures in that window failed. The 3 captures before it and the 18 after it (12 in the walk from 07:00:45, 6 in the SDK runs) all reached `available`. Render documents no such window: a capture of a running sandbox reaches `available`. Find the substrate's reason, and make a capture requested during or just after a platform deploy reach `available`.

## Context

- **Failed captures**, all of `sbx-dbtvi9teg69s73cfbvfg` in `bex-canary` (`tea-daif693dqjvc73e7as3g`), all deleted since:
  - `snp-dbtvkpjvsrns73ebrk00`, requested through MCP at 06:55:34 UTC;
  - `snp-dbtvli0mlqgs73cq4dl0`, requested through MCP at 06:57:11; it failed within 5 s;
  - `snp-dbtvmvrvsrns73ebrl10`, requested through REST at 07:00:16.
- **The deploy:** run 44031784852 (`21762a1df1fb`) wrote pin `2806a07b8` at 06:48:15, and its `roll bex onto the freshly-pushed image` step ran from 06:53:01 to 06:53:44. The pin also changed the opensandbox-controller digest (`6a1a8b05…` → `fd0307d5…`, `deploy/gitops/base/values/opensandbox-controller.values.yaml`). Argo then rolls the controller that runs the commit Jobs.
- **Not the surface:** MCP, REST and the CLI each also captured successfully in the same session. Plain back-to-back captures, a capture right after a delete, and a capture right after a TTL expiry all succeeded outside the window.
- **Where the reason is:** bex-api logs `sandbox snapshots: capture of <snp> failed: <reason>: <message>` for each failure (`snapshots.go:793`). The substrate's own record is gone: the sweep deletes a settled capture's `SandboxSnapshot` with its commit Jobs (`cleanCapture`). The logs need production cluster read (`scripts/fetch-app-kubeconfig.sh`, Loki), which this host does not have (§ Blocked — 2026-11-17).

## Steps

1. Read the three log lines and the controller's rollout and pod start times around 06:48–07:01 UTC. Decide between three causes: a controller roll, a bex-api roll, or something else.
2. Fix the cause where it lives, with a regression test on the bex-api side when the fix is there. Two possible fixes:
   - deploy.yml reuses the controller image when its inputs are unchanged, as it already does for the OpenSandbox server (`OpenSandbox server — reuse the image built from the same inputs`);
   - bex-api retries a capture whose substrate failure is transient, instead of failing the snapshot.
3. Check it on production: run captures back to back in `bex-canary` across a deploy's `roll bex onto the freshly-pushed image` step and the following controller sync, and confirm every one reaches `available`.
4. Change the `[~]` grades of the two checklist rows to `[x]`, and the 🚧 on ADR018's capture row.

## Cause — 2026-11-17 (`/loopx w32`, production cluster read)

- **The three log lines** (bex-api `bex-api-674b7f4477-g4slw`, also in Loki):
  - `06:55:34 sandbox snapshots: capture of snp-dbtvkpjvsrns73ebrk00 failed: snapshot_runtime_create_failed: Failed to create Kubernetes SandboxSnapshot osb-snap-f4cd7b65…: ('Connection aborted.', RemoteDisconnected('Remote end closed connection without response'))`
  - `06:57:13 … snp-dbtvli0mlqgs73cq4dl0 failed: snapshot_runtime_create_failed: … osb-snap-ff48ece1…: ('Connection aborted.', RemoteDisconnected(…))`
  - `07:00:16 … snp-dbtvmvrvsrns73ebrl10 failed: snapshot_runtime_create_failed: … osb-snap-4128d5e8…: ('Connection aborted.', RemoteDisconnected(…))`
- **Where it fails.** The OpenSandbox server (`opensandbox-server-5cb6bb94dc-xqb2f`, PyPI 0.2.2, up since 05:30) answers the capture 202, then creates the `SandboxSnapshot` object in the background (`opensandbox_server/services/k8s/snapshot_runtime.py:99`, `create_namespaced_custom_object`). That POST went out on a pooled keep-alive connection to the API server, which the remote end closed without answering. urllib3 retries reads on such a connection but never a POST, so the server marked the capture Failed within 20 ms. Nothing was created: deleting each failed capture logged `Kubernetes SandboxSnapshot … already absent`. None of the three API servers logged anything at those instants.
- **Not the deploy.** The OpenSandbox controller's new pod started at 06:52:00 and bex-api's two pods at 06:53:05 and 06:53:19, and the captures at 06:52:38 and 06:53:23 succeeded across both rolls. The controller is not on the failing path at all: the object it would reconcile was never created. The OpenSandbox server did not restart. The same error also failed sandbox creates, which have nothing to do with captures. Loki holds five of them between 2026-11-16 05:00 and 2026-11-17 05:35 (`Error creating sandbox: ('Connection aborted.', RemoteDisconnected(…))`, OpenSandbox 500 `KUBERNETES::API_ERROR`). They include the agent-session failures ADR105 records at 05:00:05 and 06:30:04 on 2026-11-16 and one at 05:35:02 on 2026-11-17 (`agent-session dispatch: sandbox create failed`), which w1/m405's retry covers. The window was coincidence: 4 of the server's 54 creates since 05:30 (24 sandboxes, 30 captures) hit a dropped connection.
- **Fix (bex-api).** `settleSnapshot` (`lego/backend/internal/sandbox/snapshots.go`) no longer fails a capture whose server reason is `snapshot_runtime_create_failed`. `recapture` requests a new capture of the same sandbox, records it as the snapshot's capture, and deletes the failed record. It allows up to three requests per snapshot: column `capture_attempts`, migration 0286, `TakeSandboxSnapshotCaptureAttempt`. A sandbox no longer running (409/404) fails the snapshot. A request the server does not answer leaves the failed capture, and the next sweep tries again within the same bound. Every other failure reason still fails at once. The retry is safe because the server never created the object, so nothing froze or committed the sandbox.
- **Not fixed here:** the server's own client. A patched OpenSandbox server that retries its creates would also cover sandbox creates. Those are w1/m405's, which retries a transient create in bex-api.

## Production check — 2026-11-17 (`/loopx w32`, verified)

- **The fix is on production.** Pin `5bcfe8939f5b` (`5e0fb5ad8`) carries `b2a7b83e5`. Both bex-api pods ran its image `bex-operator@sha256:fc8cbbbe…` from 09:45:48 and 09:46:06 UTC. Migration 0286 is applied: `sandbox_snapshots.capture_attempts` exists (`smallint`, default 1). A second pin reached bex-api during the check: `19103ba12f70` (`63fdff100`, image `dd7d2543…`), which also carries the fix. Argo rolled it out from 10:10:15 (ReplicaSet `7ff77d9dbf`). Then deploy run 44058637106's roll step restarted bex-api at 10:13:20–10:13:48 (ReplicaSet `744c58cd79`).
- **Captures.** One running sandbox in `bex-canary` (`sbx-dbu273gvchns73divjcg`, `--idle-timeout 0`) was captured 16 times, one about every 2 min 47 s, from 09:51:16 to 10:33:27 UTC. Each capture was `bex sandboxes snapshots create <id> --kind filesystem --name t009-f7ccef-<n> --wait`, run as the QA user with the released `bex` v0.7.0, whose `checksums.txt` matched.
  - All 16 reached `available` in 14–21 s, each 6,809,002–6,809,004 B.
  - Each snapshot was deleted once it settled, and the sandbox was stopped at the end. Afterwards the workspace lists no snapshots and no sandboxes.
- **The server lost the create under 5 of the 16, and each was requested again.** These were captures 2, 5, 9, 12 and 15, at 09:54:03, 10:02:24, 10:13:32, 10:21:51 and 10:30:20. Each time the OpenSandbox server logged `Failed to create Kubernetes SandboxSnapshot … RemoteDisconnected`. Within 2 s, bex-api logged `capture of <snp> failed: snapshot_runtime_create_failed` and then `requested again as <capture> (attempt 2 of 3)`, and that snapshot reached `available`.
  - These lines were read from the pods' own logs and Loki for 09:45–10:40.
  - Those are the only `snapshot_runtime_create_failed` lines bex-api logged after the deploy. The server logged no failed sandbox create in that time.
  - Capture 9 crossed that restart: a pod of the outgoing ReplicaSet `7ff77d9dbf` requested it again at 10:13:33, and it reached `available`.
- **A pattern worth knowing, not a gate.** The lost creates came every 8–11 minutes. That is 5 of 16 here, against 4 of 54 earlier on 2026-11-17, which suggests the server's pooled API connection goes stale on a timer. bex-api absorbs it for captures, and w1/m405 retries sandbox creates. A server-side retry would remove it at the source (§ Cause, "Not fixed here").
- **Regraded:** the two checklist rows are `[x]`, ADR018's capture row is ✅, and ADR104 D4 records the check.
