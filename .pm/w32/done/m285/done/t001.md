## Objective

Amend ADR104 D4 (and ADR014/ADR042 where they describe the mechanism) with the snapshot design: a filesystem snapshot is an OCI image committed from a running sandbox's rootfs (the D5 mechanism w2/m278 uses for suspend), stored per sandbox group with Render's lifecycle, and `--kind runtime` (Render's default) answers a named 400 recorded as a temporary difference until w2/m322 (user decision D1=A, 2026-11-11).

## Context

- Render (render.com/docs/sandboxes-snapshots): kinds `runtime` (default; memory+CPU state) and `filesystem`; capture needs a running sandbox and does not terminate it; status `creating`/`available`/`failed`; 30-day default expiry, custom expiry at capture; names 1–64 chars, not starting `snp-`, case-sensitive, latest available wins on reuse; restore creates a new sandbox, inherits plan/policy/timeouts, env not preserved; delete refused while creating; capture rate limit 10/min
- ADR042 D5: rootfs commit to OCI + pod recreate; commit Jobs run in `opensandbox-snapshot` namespace (w3/m42 patch)
- w2/m278 closed on D1=A (2026-11-11): memory and process checkpointing is funded as w2/m322, so the runtime kind is planned, not declined (ADR018 § Sandbox create flags, `idleTimeoutSeconds` row)
- IDs: `snp-` minted via `lego/backend/internal/id` (`id.New`)
- Render snapshots are scoped to a sandbox group. bex serves groups since w22/m311, so snapshots are scoped to the source sandbox's group (unblock record, 2026-11-16)
- ADR104 D4 § Security of the capture path and § Billing hook, and D11's storage bounds, are requirements of this design

## Steps

1. Read w2/m278's final mechanism and reuse it.
2. Specify storage (registry repository per workspace), metadata (Postgres table), expiry and purge, quotas/rate limit, and billing (whether stored snapshots are metered; follow Render's pricing page).
3. Record the runtime-kind refusal in ADR018 as a temporary difference that w2/m322 closes.
4. Remove the `[-]` 'non-goal at this pin' grade rationale in the checklist in favor of the target.
