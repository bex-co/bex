# After a static site's deploy fails, `undeployedChanges` is inverted: the save that never went live reads deployed, and reverting it to what is live reads saved

Why: a static site whose deploy failed tells its owner there is nothing left to deploy while it still serves the old release, and after they put the setting back it asks them to deploy a change that does not exist; a web service given the same steps reads truthfully.

- **Severity / estimate:** minor, ~1h.
- **Seen:** `/qa-find-bugs-cli w32` routine, run `4aa5`, 2026-11-20 02:39–02:58 UTC. Production pin `98e053468f52` (`c8c774658`; running images not read, the control plane did not answer `fetch-app-kubeconfig.sh`). Released `bex` v0.7.0 (Render CLI v2.36.0, checksum verified), isolated `BEX_CLI_CONFIG_PATH`, human device login as the QA user, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY. `undeployedChanges` read with the same OAuth token through REST `GET /v1/services/{id}` (the field is omitted when false) and GraphQL `service(id:) { undeployedChanges undeployedChangesReason }`; both agreed.
- **Repro** (owned static site `qa-20261120-4aa5-static`, `srv-dbvqvqs3j89c738ag6k0`, deleted after the run; `bex-co/bex` `main`, root `examples/static-site`, a build command that writes a marker into `out2/index.html`, publish `out2`):
  1. `bex deploys create <id> --wait --confirm` → `live` (`dep-dbvrat43j89c738ag73g`), the site serves marker `QA4AA5-S2`. **A:** `undeployedChanges` false.
  2. `bex services update <id> --branch qa-no-such-branch-4aa5 -o json` → exit 0. **B:** `true`, `saved`. Correct.
  3. `bex deploys create <id> --wait --confirm` → exit 1, `Build failed for deploy dep-dbvrcm950n7c739ba6bg` (`fatal: couldn't find remote ref qa-no-such-branch-4aa5`). The site still serves `QA4AA5-S2` from `main`. **C:** `undeployedChanges` **false**, still false 20 s later, though the saved branch has never been served.
  4. `bex services update <id> --branch main -o json` → exit 0. **D:** **`true`, `saved`**, still 30 s later, though every saved setting now equals the live release's.
  - Control without the failed deploy: step 2 then step 4 (branch set and reverted) reads `false`, as w8/339 made it.
  - Control on a web service (`srv-dbvqu1k3j89c738ag6i0`, native node): after two failed deploys, saved commands that differ from the live release read `true`; reverting every setting to the live release's reads `false`.
  - Same with a failing build command on the same site (02:56–02:58): `--build-command 'echo QA4AA5 fail; exit 3'` read `true`; its deploy `dep-dbvrdjk3j89c738ag79g` failed (`build command … exited with code 3`) and the site kept serving `QA4AA5-S2`, yet the flag read **false**; putting the live build command back read **`true`, `saved`**, still 20 s later.
- **Expected:** `undeployedChanges` compares the saved settings with the release that is serving, so C reads `true` / `saved` (the bad branch is still waiting for a deploy that works) and D reads `false`, as the web-service path already does.
- **Root cause** (`lego/operator/internal/controller`):
  - A static site's flag is `staged || staticSaveWaits(app)` (`saved_configuration.go:101`). `staticSaveWaits` (`:138-146`) returns false unless `sourceUpdatePending(app)` (`release_identity.go:835`), and otherwise compares `releaseSettingsFingerprint(app.Spec)` with `status.releaseSettingsFingerprint`.
  - That fingerprint is written when a release is **dispatched**, not when it serves (`prepareAppReleaseDecision`, `release_identity.go:637-643`; also `redispatchSurvivor`, `:758`). w8/339 added it to net out a set-and-clear. A dispatch that then fails overwrites it with the failed release's settings.
  - Any deploy request consumes the pending marker (`sourceUpdatePending` is `release < pending`), whether or not the release served. So after the failed deploy (C) the check returns false at once, and after the revert (D) it compares the live settings with the failed release's fingerprint, which differs.
  - The web path compares the saved spec with the serving release's own record (`servingConfigurationDiffers`, `saved_configuration.go:245`), so a failed release cannot move it.
- **Fix:** keep the settings fingerprint of the publication that is **serving**: write it where a static revision becomes the served one (`recordStaticRevision`, `app_controller.go:4987`, for a publication that actually published; a Restart that re-serves the retained publication keeps it, w32/049), and leave the dispatch-time field for the in-flight release only. `staticSaveWaits` then compares the saved spec with the served fingerprint whenever a requested release failed or was canceled (`requestedReleaseFailed`, `saved_configuration.go:211`, already knows a failed request) as well as while a save is pending. A release from an older operator with no served fingerprint keeps today's comparison.
- **Blast radius:** static sites only. Every setting the fingerprint covers is affected the same way: branch, repo, build command, root and publish directory. A build that fails (bad branch, failing build command, missing publish directory) and a canceled build are the two ways a dispatched static release never serves; the canceled one is inferred from the code, not run. The dashboard's "saved changes aren't live yet" banner and Deploy button read this flag (REST, GraphQL and MCP `get_service` all read `status.undeployedChanges`).
- **Regression checks:** the repro's C reads `true` / `saved` and D reads `false`; the same with a failing build command instead of a bad branch. Controls: w8/339's root-directory and publish-directory set-and-clear (during a first build and a later one) still read `false`; a publish-directory save that stays saved still reads `saved` until a deploy publishes it (w8/m460 site A); w32/049's Restart after a pending save still reads `saved`.
- **Unverified:** a canceled static build was not run. `undeployedChanges` is a bex extension; Render's dashboard shows no equivalent API field to compare against.
- **Dedupe:** `rg` of `.pm` for `ReleaseSettingsFingerprint`, `staticSaveWaits` and `undeployedChanges` with failed deploys: w8/339 (set-and-clear, fixed by this fingerprint, verified without a failed deploy), w8/m460 (first-build saves), w32/049 (static Restart), w21/041 (`undeployedChangesApplying` on a sleeping service). None covers a failed or canceled static release. The one commit since the pin on these files, `8ab2633c8` (w32/049), keeps the served fingerprint only for a Restart that re-serves the live publication; every other dispatch still overwrites it on HEAD, so this is not deploy lag. The line numbers above are HEAD's.
