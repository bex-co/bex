# The backend sandbox test `TestATransferIsRecordedAndStoppedWithoutAnExitCode` races the handler's deferred stop, and fails the real-DB ship gate on unrelated pushes

Why: a flaky test in the real-DB backend suite stops `scripts/ship-gates.sh` for a push that never touched sandboxes. Each flake costs a worker a rebase and a second full gate run.

- **Severity / estimate:** minor (test-only race, no product defect known), ~30m.
- **Seen:** 2026-11-20, w32/057's park commit. The first `scripts/ship-gates.sh` run failed in the untouched `lego/backend/internal/sandbox` package. The same push passed after a rebase and a rerun.
- **Where:** the test is `lego/backend/internal/sandbox/executions_test.go:328`. The handler stops the execution in a deferred call, `defer s.stopExecution(ctx, claims.Workspace, claims.ExecutionID, nil)` at `lego/backend/internal/sandbox/file_connect.go:246`.
- **Suspected cause (from w32/057's worker, unverified):** the deferred stop can land after the `204` has reached the test. A test that reads the execution record right after the response can then see it still running.
- **Fix:**
  1. Confirm the race with `go test -race -count=50 -run TestATransferIsRecordedAndStoppedWithoutAnExitCode ./internal/sandbox/` against the CI-pinned deps (`scripts/backend-test-deps.sh`).
  2. Make the test wait for the recorded stop (poll with a bounded deadline) instead of reading once.
  3. If a client can also observe the window, finish the stop before the response is written, and test that order instead.

## Acceptance

- The test passes 50 consecutive runs with `-race` against the real deps.
- If the handler changed, a test pins that the execution is stopped before the response.

## Outcome (2026-11-21)

- **Confirmed** against the CI-pinned deps: `go test -race -count=200 -run 'TestATransferIsRecordedAndStoppedWithoutAnExitCode$' ./internal/sandbox/` failed 5 of 200 runs (4 of 200 without `-race`). With the proxy's `FlushInterval: -1` set to `0` as an experiment it failed 0 of 500 runs. The cause was the proxy, not the test. `httputil.ReverseProxy.copyResponse` arms `time.AfterFunc(-1, delayedFlush)` once the gateway's headers arrive, and when that goroutine wins it flushes the 204 to the client before `ServeHTTP` returns, so before the deferred `stopExecution`. A download with a declared length always reached the client whole first, because each write is flushed.
- **A client could see it.** A history read right after an upload's 204 or a download's last byte could still find the transfer running, although an exec stream's record already stops before its response ends. So the handler changed (fix step 3): `transferEnd` (`lego/backend/internal/sandbox/file_connect.go`), called from the proxy's `ModifyResponse`, ends the record at once for a response with no body. For a response with a body, it ends the record when the body's last declared byte, its EOF or its error is read from the gateway, before the proxy writes it on. The request's end still closes a transfer that got no response, through the same once-only end (`transferRecord`).
- **Tests:** `TestATransferIsStoppedBeforeItsResponseEnds` (`executions_test.go`) holds the store's stop open and checks, for an upload and for a download, that the response has not ended while the stop is still being written. With the old handler restored, its download case failed 20 of 20 runs and its upload case 3 of 20. With the fix, the note's test passed 500 consecutive `-race` runs and the new test 50, `internal/sandbox` passed without `-race`, and golangci-lint reported 0 issues.
- **Unrelated, seen under `-race` only:** `TestParallelResumesNeverExceedTheLimit` reports a data race in the test fake `fakeMeterStore.ObserveSandboxMeter` (`meter_test.go`, an append without a lock under concurrent resumes). CI and the ship gate run without `-race`.
