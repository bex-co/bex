# A Phoenix release on a free web service never serves: port detection adopts epmd's 4369 before Phoenix binds `PORT`

Why: Render's own `render-examples/phoenix_hello`, deployed with Render's documented commands, goes `live` on bex and then answers every request with `502`. Render routes it on `PORT` (Render "forwards inbound traffic to only one HTTP port per web service", render.com/docs/web-services, read 2026-11-17).

Severity: **major**. An official Render quick start never serves, and the only workaround is setting `PORT` yourself. Attribution: operator port detection (w8/177, w8/202). Estimate: ~1h. Source: w32/m425's production capture, 2026-11-17, on pin `55c120858af0` in `bex-canary`.

## Evidence

- Fixture `qa-20261117-m425-ex` (`srv-dbu1q3ec1l2s739d46tg`, free web service, native Elixir, `render-examples/phoenix_hello@master`, build `./build.sh`, start `_build/prod/rel/phoenix_hello/bin/server`, a throwaway `SECRET_KEY_BASE`, no `PORT`). The probe's prefixes from `examples/default-env-probe` ran first. The fixture was deleted afterwards.
- The release starts Erlang distribution (`RELEASE_DISTRIBUTION=name`, and the release script's own default `sname` does the same), so `epmd` listens on 4369 and the distribution listener on a random port (40639) seconds after the container starts. On the 0.1-CPU free plan, Phoenix logged `Running PhoenixHelloWeb.Endpoint with Bandit 1.10.1 at :::10000` only about a minute after the container started.
- Meanwhile the operator's scan (`scanForBoundPort`, `lego/operator/internal/controller/port_detect.go:160-195`) saw one open port other than 10000 in two scans 15 s apart, after the 20 s grace (`portDetectGrace`, `:57`), and adopted it: App `status.detectedPort: 4369`, and `GET /v1/services/{id}` read `serviceDetails.port: 4369`, `openPorts: [4369, 40639]`. Adopting the port replaced the instance (the probe port is in the pod template). The new pod passed its TCP check on epmd, the deploy closed `live`, and `https://qa-20261117-m425-ex.onbex.co/` answered `502` from then on, while Phoenix served on 10000 inside the pod.
- The scan treats any TCP listener as the service. Detection only runs while the configured port fails its check, so a slow boot that opens a non-HTTP listener first is enough. No Elixir live fixture had served since w8/202 (2026-10-28) made detection apply to the default port: w8/333 (2026-11-16) used `sleep 900`.

## Fix

- Adopt a detected port only when it answers HTTP, as Render routes one HTTP port. The `internal/httpport` probe already does this for web image services (`web_image_http.go`, "Detected HTTP on port {port}"). A listener that does not answer HTTP stays out of `others`, so a lone epmd or distribution port is never adopted and the scan keeps waiting for `PORT`.
- Optionally, also drop a detected port once the configured port answers, so a service that adopted the wrong port recovers on its next deploy.
- Tests: two scans that find only 4369 (a TCP listener that never answers HTTP) adopt nothing; an HTTP listener on 3000 is still adopted (the w8/202 hapi case); a scan that finds 10000 open returns as today.

## Acceptance (production, after the operator deploys)

- `render-examples/phoenix_hello` on a free web service with Render's commands and no `PORT` goes `live` on 10000 and `GET /` answers `200`; `serviceDetails.port` reads 10000.
- The w8/202 control still holds: a Node process listening only on 3000 goes live on 3000 (`examples/default-env-probe`, `exec perl serve.pl 3000`).

## Dedupe

`rg -i 'epmd|4369' .pm docs` finds no open item. w8/205 (done) fixed the same symptom for Docker and image web services, whose declared ports go through HTTP selection ([ADR089](../../../docs/ADR089-render-container-compatibility.md) step 3: "An early successful TCP check on epmd must not promote a non-HTTP listener"). The native path's bound-port scan (w8/177, w8/202, w8/267, all done) never got that rule; this note gives it the same one.

## Worked 2026-11-17 (code; the live check waits for a deploy)

- **Verdict:** work. The premise held: `scanForBoundPort` counted every TCP listener the scan found, so a lone epmd seen in two scans became `status.detectedPort`. Render's scanner counts HTTP listeners only: its deploy log reads "No open HTTP ports detected on 0.0.0.0, continuing to scan..." (community.render.com, read 2026-11-17).
- **Fix:** the scan's ports other than the configured one go through `httpport.Answering`, a new sibling of `Probe` that returns every candidate answering a bounded `GET /` with an HTTP/1.x status line. Only those count as the process's listeners. With none, the stall carries the no-open-port hint and the scan keeps waiting for `PORT`, as Render does. The two-scan agreement and the several-listeners hint are unchanged; a non-HTTP port beside an HTTP one is no longer named.
- **Recovery step not taken:** no production App had a `status.detectedPort` (0 of 28, read 2026-11-17), so no service is stuck on a wrong port and the optional "drop a detected port" change was not needed.
- **Tests** (`lego/operator`): `TestDetectBoundPortNeverAdoptsAListenerThatDoesNotAnswerHTTP` (epmd alone, then epmd with a silent distribution listener: two scans adopt nothing and say no open port; with 10000 open the scan stands down), `TestDetectBoundPortAdoptsALoneListener` and `TestDetectBoundPortWithoutAPersistedDefault` (a real HTTP listener is still adopted, the w8/202 case), `TestStallHintsAndQueuedCausesAreTemplated` (the hints on real listeners), and `TestAnsweringKeepsEveryHTTPListenerAndNothingElse` in `internal/httpport`. With the filter removed, the first three fail.
