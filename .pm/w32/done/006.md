# List makes one Cilium read per allow-list sandbox

Why: a workspace with N allow-list sandboxes pays N Kubernetes GETs on every `list` (REST, GraphQL, MCP, CLI `ea sandboxes list`).

- `Service.List` (`lego/backend/internal/sandbox/service.go:1220`) calls `withRules` (`service.go:798`) per sandbox, and each call is a `SandboxManager.Rules` GET of that sandbox's `sandbox-egress-…` CiliumNetworkPolicy.
- Fix: add one namespace-wide list by the `bex-sandbox-egress` managed-by label (`lego/backend/internal/sessionegress/sandbox.go`) that returns rules by sandbox id, and fill them in one pass, as `withNames` (`service.go:1238`) does for names. Keep the ownership check per object.
- Test: a list of several allow-list sandboxes makes exactly one Kubernetes list call, and returns the same rules as before.
- ~40m. From `/pm-brainstorm more for w32`, 2026-11-09, item 4.

**Done 2026-11-09 (`/loopx w32`), with a deliberate deviation from the proposed fix.** bex-api's ServiceAccount may only `get`/`create`/`update`/`delete` CiliumNetworkPolicies in sandbox namespaces (`deploy/gitops/base/bex-api-namespace-rbac.yaml:45-46`), with no `list`. Widening that production RBAC to save read latency is not worth it. Instead `Service.List` reads each allow-list sandbox's policy concurrently, at most 8 at a time (`errgroup`, `maxConcurrentRuleReads`), so a list costs about one Kubernetes round trip rather than one per sandbox. A failed read still fails the list. `TestListReadsAllowListRulesConcurrently` passes only when the reads overlap (verified failing with the limit forced to 1), and covers the failure path. `go test -race` is clean.
