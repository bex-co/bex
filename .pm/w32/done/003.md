# Static site wedges after a failed build: next deploy stays "Build queued", ipAllowList changes never apply

Why: one failed static-site build freezes the site. The fix-forward deploy never runs, and operational changes (here: inbound IP rules) silently don't take effect while the API reports them saved. A user who mistypes a build command can't recover without deleting the site.

- **Severity:** major. The user's normal recovery path (fix the build command, then redeploy) does not work.
- **Versions:** `bex` v0.3.3 (installed release, `~/.local/bin/bex`, upstream Render CLI v2.27.0); production deployed revision unknown (checkout HEAD `2f7106a24`).
- **Context:** 2026-11-04, https://api.bex.co/v1/, workspace bex-canary (`tea-daif693dqjvc73e7as3g`), human OAuth session, non-TTY `-o json`.

## Attribution: server (operator). Root cause: partly traced

- `lego/operator/internal/controller/app_controller.go:1051` `terminalBuildFailureRecorded(app)` halts every pass after a recorded build failure. The comment above it says a tenant deploy advances the release generation so the gate reopens. On production the fix-forward deploy did **not** leave "Build queued", so either the generation the CLI deploy bumps is not the one this gate compares, or the static path never re-enters `buildFromSource`. **Unverified which**; needs a reproduction in envtest or dev-N with operator logs.
- `app_controller.go:6920` `holdPendingArtifact`: its doc comment says it returns held=false for a static site. So while a static site's newest build is failed or pending, nothing converges for the serving release: the Ingress/Traefik `Middleware` (`spec.ipAllowList.sourceRange`) isn't reconciled. Web, private and cron services do keep converging (w1/m157, cron hold). Other static operational fields that live on the Ingress (custom domains, suspend routing, headers via static-server?) are probably frozen the same way; **unverified**.

## Fix

1. Make a static site with a serving prior revision keep converging its routing (Ingress, allow-list Middleware, suspend responder, hosts/TLS) while a newer build is failed or pending, as `holdPendingArtifact` does for Deployments. In practice: a static branch that runs `reconcileStaticIngress`/middleware convergence against `Status.ActiveRevision` without publishing.
2. Find why the next deploy after a failed static build stays "Build queued", and make it dispatch. Then add an envtest: failed static build, new deploy, Job is created and the deploy goes live.
3. Regression check for (1): failed latest build, then add an allow-list, then the excluded client gets 403, and clearing it gives 200. The control is a healthy static site (already works).

## Outcome (2026-11-04, loopx w32)

Reproduced both halves in envtest (`lego/operator/internal/controller/static_failed_build_hold_envtest_test.go`, the CLI sequence at CR level: built site live → failing deploy → allow-list add/clear/re-add → save-only build-command fix → deploy). Both assertions failed before the fix.

1. **Routing froze:** confirmed as traced. Every pass after the failure halted at `buildFromSource`'s `terminalBuildFailureRecorded` gate, and `holdPendingArtifact` returned held=false for static sites. Fix: `holdPendingStaticArtifact` converges the served site's routing (`convergeStaticRouting`, extracted from `reconcileStaticSite`: IP allow-list Middleware, WebSocket meter, host Ingress, suspended responder) while a newer build is pending or failed, without writing status. Suspended static passes keep their old dispatch path.
2. **Fix-forward deploy stuck at "Build queued":** the REST `services update --build-command` is save-only (`rollout.WithSaveOnly`), so it stamps `pending-source-generation`. That source-pending pass dispatched the serving image through `reconcileStaticSite`, whose revision is `releaseRevision` = the **failed** release generation (`rev-2` ≠ active `rev-1`). It published the old image again under `rev-2` and set phase `Deploying`, and `releaseInFlight` then pinned the release, so the deploy coalesced into the pending slot behind a publish that was never owed. Fix: in `resolveDeployImage`, a source-pending static site whose release revision is not the active one holds its routing instead of publishing. Why the live rename control recovered was not established: a rename is not a release-rolling change, so it stamps no pending source.

Verified: the new envtest passes, as do the full `lego/operator` suite (`go test ./...` with envtest 1.37) and `go vet`. Live CLI acceptance on bex-canary needs this operator deployed; re-run the acceptance steps above after deploy.
