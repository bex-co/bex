## Objective

The docs say what shipped: native runtime services run `render-v1`. They give the parity basis, and they name the one open question (Render's native process identity) as a filed follow-up.

## Context

- [ADR089](../../../../../docs/ADR089-render-container-compatibility.md), D2's policy table (`render-v1` row): "Static sites and native runtimes are out of scope". § Privilege slice decisions item 6 (scope and lifecycle) says "New Docker/image/Dockerfile services (not static sites, not native runtimes)" and "explicit operator-run migration of one service".
- Basis: § Privilege slice decisions item 1 (never stricter on a measured axis), and D2's "**Superseded 2026-10-20:** under Render parity first the allowlist widens to Render's measured set".
- [ADR022](../../../../../docs/ADR022-tenant-isolation.md):185 lists `render-v1` for "New Docker/image/Dockerfile services".
- [ADR018](../../../../../docs/ADR018-render-parity.md): find the row that covers native runtimes or container privileges, and add the dated fix (w32/m462).
- Render's docs do not say whether native services run as root (render.com/docs/native-runtimes, /docs/troubleshooting-deploys and /docs/ssh, checked 2026-11-17).

## Steps

1. Amend ADR089's table row and item 6: native runtime services get `render-v1` from creation (w32/m462, with the date), and the migration has a bulk mode for them. Add the Passenger evidence and the basis in a short dated update, and keep the history.
2. Amend ADR022:185 and the `runsContainerPolicy` wording that ADRs quote.
3. Add the ADR018 note.
4. File a follow-up with `/pm add w32`: in a Render shell on a native Ruby service, record `id` and `grep Cap /proc/self/status`, and in ADR089 whether Render runs native services as root. If it does not, the stricter variant (bex running native services as a non-root user) is a separate decision. Its gate is a Render account.
5. `npx prettier@3.4.2 --write` on the touched docs; `bash scripts/docs-links-validate.sh`.
