# Historical `type=build` log reads (`bex logs`, REST, GraphQL, MCP) ignore positive `level`, `statusCode`, `method`, `host`, and `path` filters on synthetic deploy progress lines

Why: `synthesizeProgress` (`lego/backend/internal/logs/progress.go:1179-1216`) merges synthetic `type=build` deploy progress lines (`==> Build queued`, `==> Building from …`, `==> Your service is live 🎉`, primary URL block) whenever `q.Types` contains `build`, and `q.keep(e)` (`lego/backend/internal/logs/service.go:939-957`) never checks `q.Level` (because `compileLevelFilter` does not run in `QueryLogs`) or request filters (`StatusCode`, `Method`, `Host`, `Path`), so filtering by `--level` or any HTTP request filter returns synthetic build narration that does not match the filter.

- **Severity / estimate:** **major**, ~45m. Every `bex logs -r <id> --type build --level <lvl>` or `--status-code` / `--method` / `--path` / `--host` query — and every combined `--type build --type app --level <lvl>` or `--type build --type request --status-code <code>` query — floods the filtered result (even with `hasMore: true`) with unrelated synthetic `==>` build/deploy progress lines that carry no `level`, `statusCode`, `method`, `host`, or `path` labels, disagreeing with Loki's real build streams, unfiltered queries, and the live tail.
- **Versions:** released `bex` v0.9.0 (`bex-0.9.0-linux-arm64.tar.gz`, compatible with Render CLI `v2.36.0`, upstream pin `4fd34231b637`); repo checkout synced to `b0a4384d44` (`lego/cli` pinned to Render CLI `v2.37.0`, `11ef59f330dedec290f8d71d89b8f7379bbbed09`); deployed production revision unknown (predated `f78c393011`; `synthesizeProgress` and `LogQuery.keep` are unchanged on `main` through `b0a4384d44`).

## Expected / actual

- **Expected:** Consistent with Loki's build stream selectors (`lokiSelectorFor` at `lego/backend/internal/logs/loki.go:506,514,518` and `lokiRequestFieldStages` at `:605-614`) and `followPodsAndBuilds` (`service.go:1942-1950`), synthetic `type=build` progress and hook lines carry no `level`, `statusCode`, `method`, `host`, or `path` labels and therefore never match a **positive** (non-negated) filter on any of those five labels. Every single-type `type=build` query with a positive `level` or request filter returns `[]`, and a mixed `type=build,app` / `type=build,request` query returns only the matching app/request lines with zero synthetic build lines. Negated filters (`q.negates(label)` on GraphQL/dashboard saved views, such as `level != error` or `statusCode != 200`) still keep synthetic build lines, matching Loki's `!=` behavior on unlabeled build streams.
- **Actual:** `synthesizeProgress` merges all in-window deploy progress and hook lines into every `type=build` historical read regardless of positive `level`, `statusCode`, `method`, `host`, or `path` filters across CLI, REST, GraphQL, and MCP.

## Attribution and root cause

- **Attribution:** server (`lego/backend/internal/logs/`). The pinned Render CLI passes `--type`, `--level`, `--status-code`, `--method`, `--host`, and `--path` directly as query parameters to `GET /v1/logs` and renders the returned entries verbatim.
- **Root cause:**
  1. `synthesizeProgress` (`lego/backend/internal/logs/progress.go:1179-1216`) checks only `if s.DeployProgress == nil || !slices.Contains(q.Types, LogTypeBuild)` (`:1180`) before iterating deploy rows and emitting `progressLines(d, rowPC)` and `hookLines(d, pc.hook)` filtered through `q.keep(e)` (`:1206`).
  2. `LogQuery.keep` (`lego/backend/internal/logs/service.go:939-957`) checks only `q.levelFilter`, `q.matchesText`, and time bounds. In `QueryLogs` (`service.go:1003-1084`), `compileLevelFilter()` is **never** called for App queries (it runs only in `queryDatastoreLogs:1194`, `followLogs:1557`, and `followDatastore:1996`), so `q.levelFilter` is always `nil`, and `keep` has no check for `StatusCode`, `Method`, `Host`, or `Path`.
  3. Because `narrowToBuilds()` (`build_filter.go:124-133`) rewrites `q.Types = ["build"]` when `q.Build` is set, build-filtered queries with a positive `level` or request filter hit the same leak.

## Fix

- In `lego/backend/internal/logs/progress.go` (`synthesizeProgress`, `:1179-1182`):
  - Add a small helper on `LogQuery` (e.g. `excludesProgressLines()` or `hasPositiveNonBuildFilter()`) that returns `true` when any of `LabelLevel` (`len(q.Level) > 0`), `LabelStatusCode` (`len(q.StatusCode) > 0`), `LabelMethod` (`len(q.Method) > 0`), `LabelHost` (`len(q.Host) > 0`), or `LabelPath` (`len(q.Path) > 0`) is non-empty **and** `!q.negates(label)`.
  - Return `entries` immediately in `synthesizeProgress` when that helper is `true`.
  - Keep negated filters (`q.negates(label) == true`, e.g. `level != error`, `statusCode != 200` from GraphQL `filterDocument` / dashboard saved searches) eligible for progress synthesis, matching Loki's `!=` evaluation on unlabeled build streams (`loki.go:502,607,610`).
- **Surfaces (REST/GraphQL/MCP/UI):** All four historical read surfaces (CLI/REST `GET /v1/logs`, GraphQL `logs` including project-scoped views, MCP `list_logs`, and dashboard Log Explorer) share `Service.QueryLogs` → `queryHistory` → `synthesizeProgress`, so the single core fix repairs every surface consistently.
