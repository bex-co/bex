# A setting saved while a deploy waits on a throttled or failing image registry does not reach the serving release until the registry answers

Why: on Render, IP rules and suspension act on a service at once, even while a deploy is in progress. A served image service whose newest deploy waits out a Docker Hub rate limit (429), a 5xx or a network error ignores an IP allow-list, a suspend or a workspace rule for as long as the wait lasts.

- **Found by:** w32/m419's Render parity task, 2026-11-16, from the code; not reproduced live.
- **Where:** `Reconcile` in `lego/operator/internal/controller/app_controller.go`, the image-port branch. `imageRegistryWait` (`image_network.go`) returns the wait's requeue before `failBeforeDispatch` or `dispatchRuntime` runs. The registry read gate's `registryBusyError` returns the same way. Each retry backs off from 30 s to 5 minutes and repeats until the registry answers, and Docker Hub's anonymous limit can last hours.
- **Shape of the fix:** over a served release, hold the serving release while the read waits, as w32/m419 does for a refused read: call `holdPendingArtifact` with the wait's requeue as its `buildHalt`, and keep the Deploying phase and the wait's stall message (`ImageRegistryRateLimited` / `ImageRegistryUnavailable`). Do not record a Rollout verdict: the deploy is still open and must still go live once the registry answers.
- **Done when:** an envtest App with a served release, whose newest deploy's registry read answers 429, projects a changed IP allow-list Middleware and parks on suspend while the deploy stays Deploying with its rate-limit stall message. Once the registry answers 200, the deploy goes live.
- **Estimate:** ~1h. Minor: the wait ends by itself, unlike w32/m419's refusal.

## Shipped and closed — 2026-11-16 (`/loopx w32`)

- **Fix:** over a served release, `imageRegistryWait` now hands the pass to `holdRegistryWait` instead of returning. That runs the m419 hold (`holdServingRelease`, the body of `holdPendingArtifact`) as an open pass. Shared children, the Ingress with its middlewares, and the replicas converge, as on any non-poll held pass. The phase stays Deploying with the wait's stall message, and a parked pass scales and routes without settling Hibernated. No Rollout verdict is written, so the release still rolls once the registry answers. The pass returns the wait's requeue, not the hold's, so the registry is read no sooner than before. A hold error is logged rather than retried at once.
- **Deviation from the shape above:** the wait's requeue is not passed as `buildHalt`. A non-zero `buildHalt` makes the hold a build's poll, which skips the middleware rewrite when the route already matches, so an allow-list edit would not project. The hold takes an explicit `open` flag instead.
- **Also fixed:** a read the gate turns away (`registryBusyError`) used to restamp the generic `ImageRegistryUnavailable` wait. A save's pass usually lands inside the host's breaker window, so a rate-limited deploy's stall flipped to the generic message. It now keeps `ImageRegistryRateLimited` and its message.
- **Acceptance:** `refused_image_hold_envtest_test.go`, "when the registry delays the deploy instead (w32/031)". A served `whoami` web service's per-deploy tag answers 429 (Retry-After 120), or fails as a request. In both cases the restricted allow-list's `-ip-allow` Middleware is projected and chained, then removed on reopen. A suspend gives 0 replicas and hosts on the suspended responder, and a resume brings them back. Throughout, the App reads Deploying with the wait's current-generation stall reason and message, no verdict, rev-1 active and the served template. The second read returns the wait's requeue (2 min for the 429, 1 min backoff for the failed request). Once the registry answers 200, the deploy goes live as its own revision. A first release whose read answers 503 stays on its plain wait with nothing dispatched.
- **Mutations, each caught:**
  - without the hold, the Middleware is never projected;
  - returning the hold's requeue gives 30 s, not 120 s;
  - a non-open hold parks Hibernated;
  - without the busy fix, the 429 stall reads `ImageRegistryUnavailable`.
- **Test refactor:** m419's table now shares the settings walk (`settings`) with this one. Its 10 specs keep their assertions and pass.
- **Docs:** ADR004 § A release without an image does not freeze the serving one either. ADR018's Suspend / Resume row, the failed-build hold paragraph, and the Inbound IP allowlist row.
- **No production walk:** the acceptance is the envtest above. A live 429 from Docker Hub cannot be produced on demand.
- **Left as is:** the host breaker opens for its own window (30 s doubling), not for the registry's Retry-After. So a save's pass after that window can read again before Retry-After ends, as before this change.
