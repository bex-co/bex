# A deploy's log carries none of its new instance's output, where Render's shows it between `==> Deploying...` and the verdict

Why: Render parity in the deploy log, on the surface a user reads first when a deploy fails. Render's deploy log shows the traceback that made a start command exit, right above `==> Exited with status 1`. bex's shows the verdict alone, and the user has to open the service's logs to find the cause.

- **Severity / estimate:** major, likely more than 1h: it joins app lines to a deploy's build stream. Promote when picked up if it is.
- **Seen:** w32/m560 t009, 2026-11-22. bex's `type=build` read carries the build pod's output and the platform lines only. The release's own instance writes `type=app` lines, which `bex logs -r <srv> --type build` and the dashboard's deploy log (build leg) never show.
- **Render reference (public issue logs):**
  - rkendel1/freq#187 (2026-07-14): a Python traceback, then `==> Exited with status 1`.
  - darthjee/ward#109 (2026-11-14): `==> Deploying...`, the `WEB_CONCURRENCY` line, the app's own output, then `==> Exited with status 1`.
  - DerekSopok/EMS-Kahoot#3: `==> Running 'npm start'`, then npm's output, then `==> Exited with status 1`.
- **Open questions:**
  - Which log `type` Render gives those lines in its API. The CLI's `--type build` read may carry them as `app`.
  - Whether Render stops copying them once the deploy goes live.
  - Whether every instance's output is copied, or only the first instance's.
- **Likely shape:** the deploy's own release pods (revision `rev-<generation>`), from `rollout_started_at` to `finished_at`. Read them in a deploy-scoped build read (`LogQuery.Deploy`), and in the live tail while the row is in its rollout.
- **Done when:** a failed native deploy's `bex logs -r <srv> --type build` shows the start command's own error output between `==> Running '<command>'` and `==> Exited with status N`, as it does on REST, GraphQL, MCP and the dashboard's deploy page.

## Closed 2026-11-22: the deploy log already carries the new instance's output, and the open log-type question stays with w32/085

`/loopx w32` triaged this note on main `59c7ca5527` and found its premise does not hold on the deploy log itself. What is left is the open question the note names first, which w32/085 already owns.

- **Render's deploy log is its log explorer cut to the deploy's window.** An authenticated walk of dashboard.render.com on 2026-07-17 found the deploy page is Render's general log explorer scoped to the deploy's absolute window (`?r=start~end`). Its default is **All logs**, and it offers **All logs / Application logs / Build logs** (`docs/render-artifacts/live-deploy-following.md` § 2026-07-17 production incident). A Render staff reply from 2021 says the same: a deploy page shows logs "up until a point in time shortly after the deploy finished" (community.render.com thread 756, read through the Wayback Machine). The instance's output in the logs this note cites is the service's own output, and that window takes it in. In rkendel1/freq#187, darthjee/ward#109 and DerekSopok/EMS-Kahoot#3 it sits between `==> Deploying...` (or `==> Running '<command>'`) and `==> Exited with status 1`.
- **bex's deploy page reads the same way.** `useDeployLogs` (`dashboard/src/features/deploys/hooks/use-deploy-logs.ts`) reads three legs and interleaves them by time: the deploy's build lines and its pre-deploy lines, both scoped to the deploy, and the service's app lines over the deploy's window. It polls every 5 s while the deploy runs. Its tests "interleaves build/predeploy/app lines chronologically, not grouped by type" and "scopes the build and predeploy legs to the deploy, not the app leg" passed (19 of 19, `vitest run src/features/deploys/hooks/__tests__/use-deploy-logs.test.ts`, 2026-11-22). Under All logs, a failed native deploy's page therefore shows the start command's traceback between `==> Running '<command>'` and `==> Exited with status 1`, as Render's does. On both products the Build logs filter hides it. w32/m560 t009's code check read only the pane's build leg.
- **The CLI's deploy stream carries it too.** The pinned Render CLI streams a deploy by tailing the whole service (render-oss/cli `cmd/deploycreate.go`). bex's tail with no type follows the App's pods and its builds together (`followPodsAndBuilds`, `lego/backend/internal/logs/service.go`). `bex logs -r <srv> --type app,build` reads both in one interleaved history (`storeReads`, w8/m159).
- **Only `type=build` lacks it, and Render's type for these lines is unmeasured.** The note's done-when asks `--type build` (and REST, GraphQL and MCP `type=build`) to return the instance's output, which would file app output under the `build` type. Render's logs API has only `app`, `request` and `build` (api-docs.render.com/reference/list-logs, CLI `--type`), and its explorer buckets application lines apart from build lines. No public log shows which type Render gives an instance's output, or its `==>` lines. w32/085's last bullet captures exactly that with a Render account ("whether Render's deploy log copies the instance's output (w32/084)"). If Render's `type=build` read carries the output, w32/085's done-when files the fix. That fix is a milestone, not a note: the app streams carry `pod`, not the revision, so the operator must record the release's pods, and the deploy-scoped build read and its live tail must read them from `rollout_started_at` to `finished_at`.
- **Filed from this triage:** [w32/086](../086.md). Render writes `==> Exited with status N` and the troubleshooting line after each run of a start command that exits. bex writes them once, at the deploy's close.
