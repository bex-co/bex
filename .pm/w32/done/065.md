# After a deployed image service switches back to a native build, its first deploy probes the image's detected port, fails once and re-rolls

Why: the switch back from an image is a supported route since w32/056, and its first deploy starts a pod that can never pass its startup probe, which costs about 50 s and a spurious restart before the service goes live.

- **Severity / estimate:** minor, ~45m. The deploy goes `live`; it is slower and logs a failed probe and a second start.
- **Seen:** w32/056's production walk, 2026-11-21, pin `cce6c749f6ff`, `bex-canary`, released `bex` v0.9.0. Record: `.pm/w32/done/056.md`, § Gate walk, the image-deployed variant.
  - A native `node` web service from `examples/default-env-probe` (process on the default `PORT` 10000) was switched to `docker.io/library/nginx:alpine` and deployed. That deploy went `live` serving nginx on 80 (`GET /` → `Welcome to nginx!`).
  - `bex services update <id> --repo https://github.com/bex-co/bex --branch main`, then `bex deploys create <id> --wait --confirm`. The build succeeded at 10:09:58Z. The first pod printed `default-env-probe listening on 10000` at 10:10:26Z, and the cluster logged `Startup probe failed: dial tcp <pod>:80: connect: connection refused` and killed it. A second pod started at 10:11:18Z, and the deploy logged `==> Detected HTTP on port 10000; serving it` and went `live` at 10:11:30Z, 92 s after the build. The App then read `status.detectedPort: 10000` and `runtimePorts` `[10000]`.
  - The same service's earlier switch back, made before the image had ever served, went `live` 41 s after its build with one start and no `Detected HTTP` line.
- **Cause (not traced to a line):** the deploy's `Detected HTTP on port 10000; serving it` is the web image HTTP discovery (`lego/operator/internal/controller/web_image_http.go:176`, w4/615), which runs for a web service stamped with a web-image port mode (`AppSpec.UsesWebImagePorts`, `lego/types/v1alpha1/image_network.go:212`), built images included. The candidate's first pod was probed on 80, the nginx release's HTTP port, until discovery chose 10000 and re-projected the probes, which rolled a second pod. Two places can carry the old port to the native candidate: the serving release's image network (`ActiveImageNetwork`, `image_network.go:224`) as its provisional primary, or `status.detectedPort`, which only an explicit port clears (`detectedServingPort`, `port_detect.go:97`). The fixture was deleted before either was read; reproduce first.
- **Check Render first:** whether Render remembers a detected port across deploys or scans each deploy afresh ([web services docs](https://render.com/docs/web-services), port binding). Likely fix: a release whose source kind changes (image to build or back) starts with no port carried from the other kind, so the first native pod is probed on its default port.

## Acceptance

- A web service that went live on an image's detected port, switched back to a native build and deployed, starts one pod, is probed on 10000 first, and logs no failed startup probe on the old port. An operator test covers the switch in both directions.
- A native service whose own process moves to another port between deploys still has that port detected, as w8/177 requires.

## Verdict (2026-11-21, `/loopx w32` worker): work, then parked for the live check

**Cause, traced to the line: the second candidate.** `status.detectedPort` carried the image's port to the native build.

- The first candidate is ruled out by the code. A service created native never carries a web-image port mode: `configureNewImageCompatibility` (`lego/backend/internal/apps/service.go:3001`) stamps one only for an image or Docker source (`followsImagePortRules`), and a switch keeps the mode (ADR089 § Port slice decisions, item 7). So `UsesWebImagePorts()` is false, `ActiveImageNetwork()` is nil and `selectWebImageHTTP` never runs. The walk's `==> Detected HTTP on port 10000; serving it` came from the configured-port branch of `releaseDetectedHTTPPort` (`lego/backend/internal/store/reconciler.go:2074`), which narrates `status.detectedPort` once `ServingPortDetected()` holds.
- The chain: on the image deploy, bound-port detection (w8/177) adopted nginx's 80 as `status.detectedPort`. After the switch back, `detectedServingPort` (`port_detect.go:97`) still returned 80, because nothing but an explicit port cleared it. The build's template was probed on 80 while its process bound `PORT` 10000 (`processPort` keeps 10000 for a detected port, w8/267). The scan of the unready pod adopted 10000 after two scans 15 s apart, the probes moved, and the Deployment rolled a second pod. The App then read `detectedPort: 10000`, and the deploy narrated it. That matches every fact the walk recorded, and the earlier switch back, made before the image had served, had nothing detected.
- Reproduced in envtest before the fix: `source_switch_port_envtest_test.go` failed at the built release's template, which was probed on the image's 6379.
- Production held no App with a `detectedPort` on 2026-11-21 (27 Apps, read on the control plane), so no existing service needs a migration.

**Render.** Its docs say only that Render "is _usually_ able to detect and use" a port other than `PORT` ([web services](https://render.com/docs/web-services#port-binding)). Its own tutorial puts the port scan on each deploy's boot, after the start command and before the health check, with `==> Detected service running on port 10000` on a successful deploy ([boot and port binding](https://render.com/tutorials/when-deploys-go-wrong/boot-and-port-binding)). Neither says that a port is remembered across deploys, so a switched program's deploy finds its own port.

**Fix (`71b462ca5`).** Each detection now records the source of the release it was found on, `status.detectedPortSource` (`image` or `build`). A release from the other source is probed on its own port first (10000 unless `PORT` or `spec.port` names one) and adopts whatever it binds, the other program's port included. The detection stays while the release that bound it serves (a save-only switch, the build, a failed or canceled switch), and goes in the status write that records the switched release served, so its deploy names no detected port. A release from the same source keeps the port and still has a moved port detected (w8/177). A Restart, rollback or image override keeps the port as before. ADR089 § Port slice decisions item 7 and ADR004 record it.

- Tests: three unit tests in `port_detect_test.go` (the probe port per source pair, Restart and legacy; adoption of the same port and of a moved one; the drop once the switched release serves). One envtest drives a private service through `Reconcile`: redis on 6379, a save-only switch to a build, the build probed on 10000 and live with no second template, a build whose process moves to 8000, the next build starting on 8000, and the switch back to redis probed on 10000 and detecting 6379. Three mutations failed them: carrying every detection, never dropping it, and adopting against the raw detected port.
- `make test`, `make lint` and the types tests passed. The backend status-watch field list names the new field.

**Left: the production walk.** The pin must carry `71b462ca5`. Then, in `bex-canary` with the released `bex`: create a free native `node` web service from `examples/default-env-probe` (process on 10000), switch it to `docker.io/library/nginx:alpine` and deploy until it is `live` serving nginx, with `status.detectedPort: 80` and `detectedPortSource: image`. Then `bex services update <id> --repo https://github.com/bex-co/bex --branch main` and `bex deploys create <id> --wait --confirm`. The deploy must start one pod, probed on 10000 (no `Startup probe failed … :80` event), go `live` with no `Detected HTTP` line, and read `detectedPort` unset. Delete the fixture to `404` and log out.
