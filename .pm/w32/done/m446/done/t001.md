## Objective

Make the onboarding failure observable, and use it to name which call in `EnsureTenant` fails on production while a workspace is creating or deploying services.

## Context

- `lego/backend/internal/api/auth.go:395-404` answers `503 tenant onboarding unavailable` for any uncoded `EnsureTenant` error and drops the error.
- Candidates, all in `internal/api/tenancy.go`:
  - the per-request tombstone read (`AccountDeletionTombstoned`, `internal/store/accounts.go:69`);
  - `TenantForOwner` (`internal/store/workspaces.go:89`);
  - `ensureGranted` (`:383-397`): `Check`, then a write of an admin tuple that already exists.
- Reproduction from sweep 134: create a free image web service in a QA workspace and poll `GET /v1/services/{id}/deploys` once a second through its first deploy and one image deploy. That gave 4 failures in about 190 calls, and 0 in about 320 calls with nothing in flight.

## Steps

1. Log the wrapped error with the request id and the identity's method at `auth.go`'s onboarding branch, without the token or email.
2. Wrap each `EnsureTenant` step's error with which step failed (tombstone, owner read, check, grant write, re-read).
3. After the change is deployed, run the reproduction on production and read the bex-api log lines for the 503s. Record which step failed and with what error class (Postgres, OpenFGA status and body, deadline), and whether the OpenFGA log shows refused duplicate writes at those times.

## Files

- `lego/backend/internal/api/auth.go`
- `lego/backend/internal/api/tenancy.go`

## Acceptance criteria

- [x] A forced store or OpenFGA error in `EnsureTenant` produces one bex-api log line naming the step and the cause, and no secret.
- [x] The production reproduction's 503s are attributed to a named step and error class, recorded in this task.

## Out of scope

- Changing what the caller is answered; that is t002 and t003.

## Result (2026-11-17, `/loopx w32`)

**Steps 1–2 (code).** `logGateFailure` (`lego/backend/internal/api/auth.go`) logs both 503s the gate answers as `auth: <answer>: rndr-id="<id>" <method> <path> credential=<bearer|session|oauth2>: <cause>`. `Rndr-Id` is the request id the edge mints, which the caller also gets back. The line has no token, session or email. `EnsureTenant` tags each step's error (`onboardingStepError`, `tenancy.go`): account deletion check, personal workspace lookup, creation and re-read (workspace store), and workspace admin grant and admin revoke (authorization service). Tests: `TestGateNamesAndLogsAnOnboardingFault`, `TestGateLogsAnAuthUpstreamFault`.

**Step 3, attribution from what production already kept.** The cause was never logged, so this reads the Traefik access log in Loki (`monitoring/loki-0`, `{namespace="bex-system"} |= "DownstreamStatus\":503" |= "api.bex.co"`) and bex-api's Prometheus counters:

- `api.bex.co` 503s come in two body sizes. 84 bytes is the gzipped `tenant onboarding unavailable`, the body sweep 134 captured at 10:02:36 on 2026-11-16. 80 bytes is the other class.
- **84-byte (onboarding):** 13 between 00:00 and 12:00 UTC on 2026-11-16, 6 more by 23:57:30, then **0** from 2026-11-17 00:00 to 11:40 (11.7 h). Pin `ef7e65cd3f46` rolled out at about 23:59 and carries w4/695 (`a77d36c92`) and w21/099 (`ef7e65cd3`). Each took 31–200 ms: a Check, then a write. The step is the **workspace admin grant (authorization service)**. An OpenFGA Check reset on a reused connection (w4/695 logged 7 such resets that day) fell through to a duplicate admin write, which OpenFGA refused with 400.
- **80-byte (`503 auth upstream unavailable`):** 17 between 2026-11-17 00:00 and 11:40, each 1–18 ms, on many routes and callers. Each one matches an increment of `bex_api_auth_introspection_misses_total{outcome="error"}` on the replica that served it. Twelve show in the per-minute increase series. The other five show where a new pod's counter first appears at 1, or where it steps 1→2→3 on `bex-api-769cbc66bb-p9fmk` at 10:48 and 10:55. Hydra logged no request at those instants. So a token introspection failed before Hydra handled it: a dropped keep-alive connection, the w4/695 mechanism on the Hydra client.
- Sweep 134's four failures split between the two classes. 09:53:05 and 10:02:36 were onboarding. 09:56:12 and 09:58:25 (the CLI stderr) were introspection. Sweep 215's CLI failure at 06:30:54 on 2026-11-17 was introspection too.
- No evidence was found for the tombstone read or `TenantForOwner` failing.
- **Fix of the remaining class:** `introspectUpstream` marks the request replayable (`core.MarkReplayable`), so the transport resends it once on a fresh connection (`TestIntrospectionSurvivesAResetReusedConnection`). The log check after the deploy is recorded below.

**After the deploy (2026-11-17).** `db48cde2b` reached production in pin `db48cde2bae9` (run 44076479949, pin commit `fc4fbf28a`). bex-api ran `bex-operator@sha256:ced899147db9…` on both replicas from 12:09 UTC. The reproduction (t004: three create + image deploy `--wait` journeys, 429 CLI and 429 REST polls between 12:13 and 12:21) produced **no 503**, so there was no failure line to read. In the same window `api.bex.co` answered no 503 to anyone (Loki). The new replicas counted 0 introspection errors (`bex_api_auth_introspection_misses_total{outcome="error"}`) against 341 successful introspections. They logged no `auth: … unavailable` and no `tenancy: admin check …` line. The log line's format and content are pinned by the gate tests above.
