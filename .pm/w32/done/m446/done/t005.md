## Objective

Check that REST, GraphQL and MCP (and the dashboard's Kratos-session requests) all get the same answer for an onboarding fault after this milestone, and that it matches Render, where a signed-in read is not refused because the workspace is busy.

## Context

- All surfaces share the auth middleware (`lego/backend/internal/api/server.go:101`).
- Render's public error schema is `{"id","message"}` (`core.WriteErr`).

## Steps

1. Force an onboarding fault in a test and compare the REST status and body, the GraphQL error, the MCP tool error and the dashboard's handling.
2. File any drift as follow-up work through `/pm`, and record the outcome here.

## Files

- `lego/backend/internal/api/`
- `docs/ADR018-render-parity.md`

## Acceptance criteria

- [x] Each surface's answer to an onboarding fault is recorded and consistent, or the drift is filed.

## Out of scope

- New surfaces.

## Result (2026-11-17, `/loopx w32`)

- **One answer on every surface.** `TestOnboardingFaultIsOneAnswerOnEverySurface` (`lego/backend/internal/api/auth_onboarding_fault_test.go`) forces an onboarding fault behind the composed handler. It calls REST `GET /v1/services`, GraphQL `{ services }` and MCP `tools/call list_services`, each with a Kratos session (the dashboard's credential) and a human OAuth bearer (the CLI's). All six get `503` and the same body: `{"error","id":"unavailable","message":"tenant onboarding unavailable: workspace admin grant failed (authorization service)"}`. The REST answer passes the Render OpenAPI response validator (`buildHandler`).
- **Dashboard:** nothing in `dashboard/src` reads either gate message. A GraphQL `503` reaches Apollo as a network error, and the page shows its generic error state. Only the message text changed, so that handling is unchanged.
- **GraphQL gets the REST-shaped body,** as it does for every gate answer except the 429 shed (`writeAuthOverloaded`). That matches the email-verification gate (ADR075 D8). It is not new drift, so nothing is filed.
- **Render:** Render's error body is `{id, message}`, and bex's is a superset (`error`). Render does not refuse a signed-in read because the workspace is busy. After this milestone bex answers 503 only for a real dependency outage. ADR018 has a new row, "A signed-in request is not refused because a dependency blinked", and ADR012 has the new §8f.
