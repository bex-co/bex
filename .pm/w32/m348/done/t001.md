## Objective

Record Render's exec contract (a command runs under `bash -c` in a new shell in the sandbox's home directory), choose the base image that carries it, and correct the documents that say bex already matches.

## Context

- Render Python SDK `render==1.8.0`, `render/experimental/sandbox/client.py:357-358`: "command is passed to ``bash -c`` in the sandbox". render.com/docs/sandboxes-executing: "Each command starts in a new shell in your sandbox's home directory". render.com/docs/sandboxes-sdk-python: relative paths "resolve under `/home/render`".
- `.pm/w22/done/001.md` concluded "Render's page names `sh`, not `bash`" from the CLI advice "Use `sh -c` to interpret operators…". That advice exists because the CLI shell-quotes its argv. It says nothing about the server's shell.
- bex today: `exec.go:120` runs `/bin/sh -c` with no working directory. The `base` template image is `alpine:3` (`cmd/api/config.go:560`), and the agent template is `BEX_AGENT_SESSION_IMAGE`.
- The image must stay digest-pinned (w7/m85 guard). The file gateway's scripts (`sshgateway/sandboxfiles/sandboxfiles.go`, the `cdParent` prelude from w32/m299) and the DNS behavior recorded in ADR104 D3 (w8/m152, `ndots:1`) assume the current image's tools and resolver.

## Steps

1. Re-read the two Render pages and the SDK docstring; note the fetch date.
2. Choose the image. Options: a public digest-pinned image that ships bash (e.g. a Debian slim), or a bex-built base image. List what the file gateway scripts need (`tar`, `gzip`, `find`, `stat`, `readlink`, …) and check the choice carries all of it.
3. Decide `HOME` and the user: keep root with `/root`, or match Render's `/home/render`. Record the reason. Relative uploads (w32/m299) follow `$HOME` either way.
4. Amend ADR104 D2 (the exec row), the ADR018 sandbox exec row, `docs/render-artifacts/ea-sandbox.md` and ADR042 (the base template), and append a correction note to `.pm/w22/done/001.md` pointing at this milestone.
