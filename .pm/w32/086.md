# A start command that exits and is started again gets one `==> Exited with status N` at the deploy's close, where Render's log writes it after each run

Why: Render parity in the deploy log of a failing deploy. Render closes each run of a start command that exits with its own verdict, so the log reads as one block per attempt. bex's reads as several attempts and a single verdict at the end.

- **Severity / estimate:** minor, likely more than 1h: the operator records each run's exit, the deploy row keeps it, and `progressLines` narrates it. Promote when picked up if it is.
- **Seen:** w32/084's triage, 2026-11-22. bex writes `==> Running '<command>'` at each recorded start of the app container (`rolloutLines`, from `status.releaseRollout.appStarts`, w32/m560), but `==> Exited with status N` and the troubleshooting line only once, at `finished_at` (`rendersVerdict`, `lego/backend/internal/logs/progress.go`). The operator settles a startup crash after two restarts (`crashSettleRestarts`, `lego/operator/internal/controller/app_controller.go`), so a failed native deploy reads `Running`, output, `Running`, output, `Running`, output, then one `Exited`.
- **Render reference (public issue logs):**
  - DerekSopok/EMS-Kahoot#3 (native Node): `==> Running 'npm start'` at 22:14:58.31, npm's error, `==> Exited with status 1` and the troubleshooting line at 22:15:02.93, then `==> Running 'npm start'` again at 22:15:06.54 and the same error.
  - rkendel1/freq#187 (Docker): a traceback, `==> Exited with status 1` and the troubleshooting line at 17:45:22.21, then the second run's identical output from 17:45:24.67.
  - darthjee/ward#109 (Docker): run 1, `==> Exited with status 1` and the troubleshooting line at 01:32:22.77, run 2, the port-scan lines, run 3.
  - muppetbrown/mana_meeples_singles_market#63: `==> Exited with status 1`, then `==> Running 'node server.js'` 0.6 s later and run 2's output. Its #84 shows two runs and only one `Exited` line, after the second, so the capture should check whether Render ever skips one.
- **Likely shape:** the operator records each run's end (the app container's `lastState.terminated`: `finishedAt` and `exitCode`, not an out-of-memory kill) beside `appStarts`, bounded the same way. The deploy row keeps it, and `progressLines` writes `==> Exited with status N` and the troubleshooting line at each recorded end before `finished_at`. The close then adds none of its own for the run already narrated.
- **Done when:** a failed native deploy whose start command exits three times reads, in `bex logs -r <srv> --type build`, `==> Running '<command>'`, `==> Exited with status N` and the troubleshooting line once per run, in that order, on REST, the subscribe stream, GraphQL, MCP and the dashboard's deploy page. A Dockerfile service reads the same without the `Running` lines. `docs/render-artifacts/live-deploy-following.md` § Platform progress-line contract and ADR018 § Logs, Build logs cite the logs above.
