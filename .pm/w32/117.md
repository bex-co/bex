# 117 — A stale `BEX_WORKSPACE` name leaks as raw `ownerId` into typed-ID sandbox, snapshot, image, credential, environment-set, object, s3, and agent commands, failing with misleading `403` errors

Why: `docs/bex-cli.md` promises that for a command reading the active workspace, an unknown `BEX_WORKSPACE` name exits `1` with `no workspace named "<x>"` so a renamed, deleted, or typoed workspace never surfaces as a cryptic permission error (`w8/038`). Because `workspaceUse` (`lego/cli/main.go:366-369`) returns `bridge.WorkspaceIfResolvable` for **any** command whose first positional argument matches `^[a-z]{3}-[0-9a-z]{20}$` regardless of whether that command sends `config.WorkspaceID()` as `ownerId`, every workspace-scoped command that accepts a typed ID (`sandboxes stop`/`exec`, `sandboxes snapshots create`/`get`/`delete`, `sandbox-groups images|builds get`/`delete` without `--group`, `sandbox-groups credentials` without `--group`, `sandbox-groups environment set`, `postgres`/`keyvalues` with `--project`/`--environment`, `agent automations|skills|secrets`, `ea objects`, and `s3 info`/`public`/`keys revoke`) silently forwards the raw stale workspace name as `ownerId` and fails with `Error: you are not allowed to take this action`, `403 FORBIDDEN`, or an unbranded upstream workspace error instead of naming the stale `BEX_WORKSPACE`.

Severity: minor. Attribution: Bex launcher. Estimate: ~45m. Source: `/qa-find-bugs-cli` routine `cli-qa` sweep `66be`, 2026-11-25. Goal: `docs/bex-cli.md` § Configuration (`BEX_WORKSPACE`) and `w8/038` / `w8/064`'s contract that every active-workspace consumer fails fast on an unresolved `BEX_WORKSPACE` name while only genuinely workspace-free direct-ID commands allow stale-workspace recovery. No dependencies and no product fix implemented by this filing.

## Root cause

In `lego/cli/main.go:339-371`, `workspaceUse` grants `bridge.WorkspaceIfResolvable` to **every** command whose first positional argument matches `typedResourceID` (`^[a-z]{3}-[0-9a-z]{20}$`, line 315):

```go
arity := pgtrust.ArityOf(root.PersistentFlags(), target.InheritedFlags(), target.Flags())
if typedResourceID.MatchString(pgtrust.DatabaseArg(rest, arity)) {
	return bridge.WorkspaceIfResolvable
}
```

When `bridge.ResolveWorkspaceName` (`lego/cli/internal/bridge/workspace.go:44-55`) runs with `WorkspaceIfResolvable`, it tries `GET /v1/owners?name=<BEX_WORKSPACE>&limit=100`, swallows the `"no workspace named ..."` error (`if use == WorkspaceIfResolvable { return nil }`), and leaves `RENDER_WORKSPACE` holding the raw unresolved workspace name (`stale-nonexistent-ws-66be`).

That shortcut was introduced in `w8/064` only for direct-by-ID routes (`pg get dpg-…`, `kv get red-…`, `deploys list srv-…`, etc.) that do not call `config.WorkspaceID()`. Every command below still calls `config.WorkspaceID()` (or Bex's `d.owner()` / `d.startWorkspace()`) even when given a typed resource ID, so leaving the raw name in `RENDER_WORKSPACE` leaks it straight into the API request:

1. `sandboxes` (`stop`, `exec`, `copy`, `get`, `logs`, etc.) and `sandboxes snapshots` (`create`, `get`, `delete`, even with `--group`): upstream `pkg/sandbox/repo.go:324,432` and `pkg/sandboxsnapshot/repo.go:21,40,111` always pass `?ownerId=<config.WorkspaceID()>`.
2. `sandbox-groups images|builds` (`get`, `delete`) and `sandbox-groups credentials` (`create`, `get`, `update`, `delete`, `versions`, `restore`) **when `--group` is omitted**: `pkg/sandboximage/service.go:45` and `pkg/sandboxcredential/service.go:53` call `groups.IDOrDefault` (`pkg/sandboxgroup/service.go:31`), which calls `GET /v1/sandbox-groups?ownerId=<config.WorkspaceID()>`. When `--group` is non-empty, they do not read `config.WorkspaceID()`.
3. `sandbox-groups environment set`: `pkg/sandboxgroup/service.go:82-109` calls `ResolveScopeInActiveWorkspace`, which calls `config.WorkspaceID()`.
4. `postgres` and `keyvalues` (`get`, `update`, `suspend`, `resume`, `delete`) **when `--project` or `--environment` is non-empty**: upstream resolves the project/environment scope in the active workspace via `ResolveScopeInActiveWorkspace`.
5. `agent automations`, `agent skills`, and `agent secrets`: Bex-native handlers call `d.startWorkspace` (`lego/cli/internal/agent/automations.go:175-192`, `lego/cli/internal/agent/config.go:853,870`), sending `?ownerId=<workspace>`. (By contrast, direct session verbs on `ags-…` call `/v1/agent-sessions/{id}` without `ownerId`.)
6. `ea objects` (`get`, `put`, `delete`): `pkg/storage/service.go:139,158` reads `config.WorkspaceID()` for `/v1/objects/{ownerId}/{region}/{key}` regardless of whether the object key happens to match `^[a-z]{3}-[0-9a-z]{20}$`.
7. `s3` (`info <bucket>`, `public <bucket>`, `keys revoke <id>`): `lego/cli/internal/s3/tools.go:194,241,303,381,451` calls `d.owner()` regardless of whether the bucket or key ID matches `^[a-z]{3}-[0-9a-z]{20}$`.

## Fix plan

1. In `lego/cli/main.go:339-371` (`workspaceUse`), restrict the `typedResourceID` → `bridge.WorkspaceIfResolvable` shortcut to an explicit allowlist of commands whose API route genuinely addresses the resource directly without reading `config.WorkspaceID()`:
   - Direct resource-ID commands: `services update`, `services delete`, `services instances`, `deploys list`, `deploys create`, `deploys cancel`, `jobs list`, `jobs create`, `jobs cancel`, `restart`, `ssh`, `psql`, `pgcli`, `kv-cli`, `environments`, `ea blueprints plan`, `ea blueprints approve`, `ea blueprints update`, `sandbox-groups delete`, `sandbox-groups default set`, `sandbox-groups environment remove`, and direct session `agent` verbs (`get`, `logs`, `files`, `send`, `wait`, `cancel`, `stop`, `archive`, `unarchive`, `delete`, `tags`, `tree`, `cost`, `open`, `pickup`, `ssh`, `update`, `chat`).
   - `postgres` and `keyvalues` (`get`, `update`, `suspend`, `resume`, `delete`) **only when both `--project` and `--environment` flags are empty**.
   - `sandbox-groups images`/`builds` (`get`, `delete`) and `sandbox-groups credentials` (`get`, `update`, `delete`, `versions`, `restore`) **only when `--group` is non-empty**.
   - Everything else (including `sandboxes *`, `sandboxes snapshots *`, `sandbox-groups environment set`, `sandbox-groups images|builds|credentials` without `--group`, `ea objects *`, `agent automations|skills|secrets *`, `s3 *`, and any future `ownerId`-scoped command) falls through to `bridge.WorkspaceRequired` and fails fast with `bex: BEX_WORKSPACE: no workspace named "<x>"; run \`bex workspaces\` to list yours`.
2. Extend `TestStaleWorkspaceNameBlocksOnlyConsumers` in `lego/cli/main_test.go:1328` to assert:
   - Stale `BEX_WORKSPACE` fails fast with `bex: BEX_WORKSPACE: no workspace named ...` on `sandboxes stop sbx-…`, `sandboxes exec sbx-…`, `sandboxes snapshots create|get|delete` (both with and without `--group`), `sandbox-groups images get|delete sbb-…` (without `--group`), `sandbox-groups credentials get crd-…` (without `--group`), `sandbox-groups environment set sbg-… evm-…`, `postgres`/`keyvalues get <id> --project <p>`, `agent automations get aut-…`, `agent skills get skl-…`, `agent secrets delete sec-…`, `ea objects get obj-…`, and `s3 info bkt-…`.
   - Direct-ID recovery still works (does not fail on stale `BEX_WORKSPACE`) on `postgres`/`keyvalues get <id>` (without `--project`/`--environment`), `deploys list srv-…`, `sandbox-groups delete sbg-…`, `sandbox-groups images get sbb-… --group sbg-…`, `sandbox-groups credentials get crd-… --group sbg-…`, `ea blueprints plan exs-…`, and `agent get ags-…`.
3. Update the `BEX_WORKSPACE` row in `docs/bex-cli.md:60` so the typed-resource-ID recovery sentence notes that it applies only to commands whose API route addresses the resource directly without an active workspace (`ownerId`).
4. Verify with `CI=true go test ./...` in `lego/cli`, `make lint`, `bash scripts/bex-cli-validate.sh`, and a read-only live check against `https://api.bex.co/v1/` with `BEX_WORKSPACE=stale-nonexistent-ws-...` confirming `sandboxes stop sbx-…`, `sandboxes snapshots get snp-…`, `sandbox-groups images get sbb-…` (no `--group`), `agent automations get aut-…`, and `s3 info bkt-…` exit `1` with `bex: BEX_WORKSPACE: no workspace named ...` while `keyvalues get red-…` and `sandbox-groups images get sbb-… --group sbg-…` still exit `0`.
