# A sandbox ended by its lifetime timeout answers 404 for up to ten minutes, then reads `terminated` at the wrong time

Why: w3/m318 made ended sandboxes readable, as on Render. On production its lifetime-expiry half fails for any sandbox younger than ten minutes. The sandbox vanishes (404, missing from `list --all`), then reappears as `terminated` with a `terminatedAt` minutes after it really ended, and the Render CLI v2.36 explanation repeats the wrong time.

- **Seen:** `/qa-find-bugs-cli` loop sweep 4488, 2026-11-12, `bex-canary`, release `bex` v0.5.0, human device login. The deploy pin is `3d66946c9e16`, which contains w3/m318's `c2eee0472`.

  | Time (UTC) | Observed |
  | --- | --- |
  | 08:14:59 | `bex sandboxes create --wait --timeout 60 …` → `sbx-dbqnb0qibtfs738vkrb0` |
  | 08:15:52 | listed `running` |
  | 08:16:02 – 08:24:56 | absent from `sandboxes list --all` and `--status terminated`; `bex sandboxes exec … -- true` and `bex sandboxes stop … --confirm` → `received response code 404 (SANDBOX_NOT_FOUND): sandbox not found`, exit 1 |
  | 08:25:16 | listed `terminated`, `terminatedAt: 2026-11-12T08:25:09.949725Z`; `exec` → `409 (SANDBOX_ENDED): … was terminated at 2026-11-12T08:25:09Z` |

  The control works: a sandbox stopped with `sandboxes stop` (sweeps 865a, 42aa) answers `409 SANDBOX_ENDED` at once, with its real end time.

- **Contract:** w3/m318's DoD: "After `POST …/terminate`, **or a lifetime expiry**, `GET /v1/sandboxes/{id}` answers 200 with `status: terminated` and `terminatedAt`…". Render's pinned OpenAPI lists a terminated sandbox under `status=terminated`, and CLI v2.36 `explainConflict` prints its `terminatedAt`.

- **Cause (traced at `e93bdc47d`):**
  - `sandbox/service.go:960` creates the OpenSandbox object with `openSandboxTimeout(timeout)` (`lifetime.go:94`), so OpenSandbox deletes the pod at its own `expireTime`, before bex's lifetime reaper (`terminateObserved`) acts.
  - The end is then recorded only by the idle sweeper's `EndAbsentSandboxes` (`sandbox/idle.go:463`, every 30 s).
  - `store/sandbox_records.go:60-69` skips records created less than 10 minutes ago. That guard protects a create not yet visible in the list, but it also hides a sandbox that was listed and then expired.
  - It stamps `terminated_at` with the sweep time (`at`), not the expiry.
  - Reads fall back only to an ended record (`EndedSandbox`, `terminated_at IS NOT NULL`), so the gap answers 404.

- **Fix:**
  1. When a live record is absent from a complete list and its expiry has passed, end it at once, with `terminatedAt` set to the expiry. The expiry is `max(createdAt, resumedAt) + timeoutSeconds` from the stored view and the sandbox's `bex.co/resumed-at` metadata (`lifetime.go:107`).
  2. Keep the ten-minute guard only for records whose expiry has not passed.
  3. Optionally make reads compute the same answer for a live record past its expiry, so the 30 s sweep gap is closed too.
  4. Add tests for a 60 s sandbox read at +90 s (terminated, `terminatedAt` = expiry) and for a fresh create not yet listed (still guarded).

- **Acceptance:** `bex sandboxes create --wait --timeout 60`, then at +90 s `bex sandboxes exec <id> -- true` prints `… was terminated at <createdAt+60s>` (409), and `bex sandboxes list --status terminated` includes it.
- **Blast radius:** REST GET, list and terminate, GraphQL `sandbox`/`sandboxes`, MCP `list_sandboxes`, the run and file token mints, and execution history of an ended sandbox all read the same record. Agent-session sandboxes end through `terminateObserved` and are unaffected.
- **Unverified:** a sandbox older than ten minutes at expiry should end within one 30 s sweep, with `terminatedAt` late by at most 30 s. Inferred from code, not timed.
- **Dedupe:** w3/m318 (blocked on its closeout live check) owns the contract. Its README gets a dated pointer here, and its closeout waits for this note.
- ~60m.
