## Objective

For each release's pre-deploy step, `status.preDeploy` records what bex-api's deploy log will narrate:

- **The command** the step ran, as the release configured it, and whether it ran through a native runtime's entrypoint.
- **When the step started**, below the second, so `==> Starting pre-deploy` sorts after the build pod's own `==> Build successful 🎉`.
- **When its container started** (the kubelet's start, whole seconds), for `==> Running '<command>'`.
- **When it ended**, precise enough that the closing line sorts after the command's last output line.
- **The exit status** of the step's container, when it exited on its own.

The operator stays database-free: these are status facts that bex-api projects.

## Context

- `PreDeployStatus` (`lego/types/v1alpha1/app_types.go:1663`): `job`, `generation`, `startedAt`, `finishedAt` (RFC3339 strings, whole seconds), `status`, `message`.
- `reconcilePreDeploy` (`lego/operator/internal/controller/app_controller.go:7648`) stamps `started` with `time.Now().UTC().Format(time.RFC3339)` on the first pass and keeps it across requeues. `preDeployEnded` (`:7901`) stamps the end from `jobFinishedAt` (the Job's `CompletionTime` or its terminal condition, whole seconds). `failedStep` (`:7870`) and `runningStep` (`:7864`) build the record.
- The command is `app.PreDeployStepCommand()` (`lego/types/v1alpha1/predeploy.go:43`), the release's own. The launch is `preDeployLaunch` (`app_controller.go:7972`). `runsNativeEntrypoint` (`deployment_projection.go:389`) is the native case, as w32/m560's `status.releaseRollout.command` uses it.
- The exit code: `terminatedContainer` (`lego/operator/internal/predeploy/predeploy.go:603`) already reads it for `FailureMessage`. Do not parse it back out of the message.
- Precedent for sub-second moments: `ReleaseRolloutStatus.StartedAt` is a `metav1.MicroTime` (w32/m560 t001). The initial deploy hook keeps whole seconds and holds its end line to the close of its second instead (`hookMoments`, `lego/backend/internal/logs/progress.go:629`). Either works if the order holds; pick one and say why.
- The legacy carried hook step (`legacyHookStep`) and the initial deploy hook share `PreDeployStatus`'s shape. Leave the hook's narration as it is.

## Steps

1. Add fields such as `command`, `native bool`, `containerStartedAt` and `exitCode *int32`, and a sub-second start and end (new `metav1.MicroTime` fields, or a documented hold in t003–t005). Document each field the way its neighbours are documented, then run `make manifests generate`.
2. Stamp the command, the launch and the start on the step's first pass. A requeue, a manager restart or a re-check of a persisted verdict never moves them.
3. Read the container's start and, when it ends, its exit code, from the Job's pod. An out-of-memory kill sets the exit code and keeps the message's own wording. A step that never ran its command (an image pull failure, no build minutes, a `StartError`, a step that could not start) records no container start and no exit code.
