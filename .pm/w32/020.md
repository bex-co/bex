# A sandbox's `createdAt` changes between reads: whole seconds while it lives, the API's microsecond clock in the create echo and once it ends

Why: on Render a resource's creation time is fixed. On bex one sandbox reads two different `createdAt` values (up to a second apart), so a client that keys, caches or orders sandboxes by it (the Render SDK's `created_at`, `list` newest first) sees the value move when the sandbox ends.

- **Seen:** `/qa-find-bugs-cli` loop sweep b3e6, 2026-11-13 ~03:22–03:34 UTC, `bex-canary` (`tea-daif693dqjvc73e7as3g`), release `bex` v0.5.0 (Render CLI v2.35.0 pin), human device login, `https://api.bex.co/v1/`, production pin `8acf1d116941`.

  ```text
  $ bex sandboxes create --timeout 300 --network-policy deny-all --confirm -o json
    "createdAt": "2026-11-13T03:33:46.762686Z", "id": "sbx-dbr8a6khd5js73auepog", "status": "running"
  $ bex sandboxes list --all -o json        # that sandbox, twice, 8 s apart
    running     createdAt 2026-11-13T03:33:46Z
  $ bex sandboxes stop sbx-dbr8a6khd5js73auepog --confirm; bex sandboxes list --all -o json
    terminated  createdAt 2026-11-13T03:33:46.762686Z   terminatedAt 2026-11-13T03:34:00.613584Z
  ```

  Rechecked on pin `54b576ac6ec9` (2026-11-13 04:48 UTC, which also carries w2/m358 image import): `sbx-dbr9d3dgp85c73b3q290` read `04:48:13.136658Z` in the create echo, `04:48:13Z` while running and `04:48:13.136658Z` once stopped. Rechecked again on pin `1c4d721bc8dc` (2026-11-13 16:45 UTC, after w5/m371 changed sandbox listing): `sbx-dbrjt7tgh3vs73b14cmg` read `16:45:19.145207Z`, then `16:45:19Z`, then `16:45:19.145207Z`. On pin `3e30e291ed3c` (2026-11-13 23:15 UTC, after w8/314 changed `records.go`), `sbx-dbrpjtruoa8c73enef20` read `23:15:03.178292Z`, then `23:15:03Z`, then `23:15:03.178292Z`.

  The same happened to `sbx-dbr854chd5js73auep00` (`--wait`, so the create echo is the CLI's follow-up read: `03:22:57Z` while running, `03:22:57.125871Z` once stopped) and `sbx-dbr85g4hd5js73auep7g` (`03:23:44Z`, then `03:23:44.508704Z`). Every ended sandbox in the workspace's list carries microseconds and every live one whole seconds.

- **Cause (traced at `bbd484b5e`; line numbers rechecked at `2356d3d04`):**
  - Live reads take OpenSandbox's `createdAt`, the Kubernetes object's whole-second creation time: `lego/backend/internal/sandbox/service.go:773` `CreatedAt: raw.Created`.
  - OpenSandbox's create echo carries no `createdAt`, so the create path stamps the API's own clock: `service.go:1011-1015` `raw.Created = &now`. It is a different instant from the Kubernetes one, read after the create returns.
  - `recordLive` (`records.go:81-87`) stores that create-time view, and its lifetime deadline (`createdAt + timeoutSeconds`). The record upsert never rewrites the view (`store/sandbox_records.go:53-55` updates only `terminated_at`), and ended reads serve it. That is why an ended sandbox reads the create echo's value and a live one reads OpenSandbox's.
- **Fix:**
  1. Give a sandbox one creation time. Stamp bex's create instant into the sandbox's metadata at create (e.g. `bex.co/created-at`, next to `bex.co/resumed-at` in `lifetime.go`, with sub-second precision). Have `sandboxFromOpenSandbox` read it first and fall back to `raw.Created` for an unstamped sandbox (agent-session sandboxes, or ones created before the change). The create echo, live reads, the record view and `recordLive`'s deadline then share that one value.
  2. The same `Sandbox` value feeds REST get/list/create, GraphQL `createdAt` (`graphql.go:126`), MCP and `newestFirst` (`service.go:1508`), all at `2356d3d04`, so one change covers them all. No dashboard sandbox list exists to update.
  3. Leave unstamped live sandboxes as they are. Each ends within its timeout, or within 30 days of a suspension.
- **Acceptance:** in `bex-canary`, for a new sandbox, `bex sandboxes create -o json` (no `--wait`), `bex sandboxes list -o json` while it runs, and `bex sandboxes list --all -o json` after `stop` all print the same `createdAt`. A test pins create, get, list and the ended read to one value.
- **Unverified:** the precision Render itself returns for sandbox timestamps. Its OpenAPI types them `date-time` only. The fix keeps whatever precision bex stamps, so it does not depend on the answer.
- **Dedupe:** no board item covers it (`rg createdAt .pm` over sandbox items: only w32/017's deadline and m297's field list). w32/017 moved the deadline onto `recordLive`'s create-time value. That deadline is self-consistent with the ended view, but it is up to a second off the live `createdAt`.
- Minor. ~45m.
