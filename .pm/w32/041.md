# The TypeScript SDK can upload a sandbox file as `application/gzip`, and bex's gateway refuses it with 415

Why: Render's released TypeScript SDK offers `application/gzip` as an upload content type. If Render accepts it, a script written against Render fails on bex with `415 unsupported upload Content-Type`, and no checklist row or ADR018 row says so.

- **Seen:** w32/035's worker, 2026-11-17, reading the released Render TypeScript SDK v1.8.0: its `SandboxUploadContentType` includes `application/gzip`.
- **bex today:** `lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go`, `(*Server).upload`, admits `application/octet-stream` (raw, no `Content-Encoding`) and `application/x-tar` (with `Content-Encoding` empty, `identity` or `gzip`). Every other media type gets `415 unsupported upload Content-Type`, so a gzip upload is always refused.
- **Unchecked:** what Render does with an `application/gzip` upload. It might store the bytes as one file, unpack a gzipped tar into a directory, or refuse the request. `docs/cli-compatibility-checklist.md` and the ADR018 sandbox file-transfer rows do not grade this content type.
- **Fix:** settle Render's behavior from its API reference, the SDK source (what the SDK sends with that type, and the path it targets), or a live call. Then make bex do the same, or record the divergence in ADR018 with the reason. Add a gateway test for the chosen behavior, and grade the row in the checklist and ADR018.
