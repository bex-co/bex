# `bex s3 cp - s3://bucket/key` fails on a pipe with `seek /dev/stdin: illegal seek`

Why: the docs say `-` is standard input, and piping (`tar c . | bex s3 cp - s3://b/x.tar`) is what it is for, but every pipe fails before the first byte is sent, and only a redirected regular file works.

- Severity: major. A documented `bex s3 cp` form is broken in its main use. Nothing is stored and nothing is lost: the command exits 1.
- Versions: released `bex` v0.9.0 (`bex-0.9.0-linux-arm64`, sha256 `cecca711…aee80`), upstream pin v2.36.0 `4fd34231b637`, production pin `f797f525f5df`. HEAD `06e0187d1` has the same code: since `bex-cli/v0.9.0`, `internal/s3` changed only the delete prompts.
- Context: cli-qa routine run r23, 2026-11-21 08:27Z, `https://api.bex.co`, workspace `bex-canary`, human device login, ephemeral key made by `bex s3`.

## Repro

```sh
bex s3 mb s3://qa-<nonce>-b1
bex s3 cp - s3://qa-<nonce>-b1/redir.txt < a.txt                # upload: - to s3://…/redir.txt, exit 0
cat a.txt | bex s3 cp - s3://qa-<nonce>-b1/pipe.txt             # exit 1
bex s3 cp - s3://qa-<nonce>-b1/p2.txt < <(echo x)               # exit 1
```

Both failing commands print `Error: unable to initialize upload: seek /dev/stdin: illegal seek` within a second, and no object is stored. The fixture was deleted (`rb --force`, then `info` answered 404).

## Cause

- `cpUp` (`lego/cli/internal/s3/cp.go:175`) hands `r.d.stdin` to `upload`. In production that is `os.Stdin` (`s3.go:74`), an `*os.File`, so it satisfies `io.Seeker`.
- `uploadParts` (`multipart.go:39`) passes it to the SDK's `manager.Uploader`. The uploader's `initSize` (`aws-sdk-go-v2/feature/s3/manager@v1.23.28/upload.go:446-455`) takes the `io.Seeker` branch and calls `seekerLen`, which seeks. A seek on a pipe returns `ESPIPE`, and the upload stops there.
- The unit test `TestStandardInputAndOutput` (`internal/s3/transfer_test.go:174`) misses it: the rig's stdin is a `*bytes.Buffer` (`rig_test.go:52-58`), which cannot seek, so the SDK streams it.

## Fix

- Hand the uploader a reader that cannot seek, such as `struct{ io.Reader }{r.d.stdin}`. A stream of unknown size then goes up in 8 MiB parts (`partSizeFor(-1)`), and the 5 GiB object cap still fails it at that mark, as the docs say.
- Wrap it unconditionally or only for a non-regular file. A redirected regular file also uploads fine as a stream.
- No server change. `readRules` (`config.go:124`) reads standard input with `io.ReadAll` and is unaffected: `cors get -o json | bex s3 cors set <b> --file -` worked live.

## Acceptance

- A regression test feeds the command an `os.Pipe()` read end as stdin, once for a stream over one part and once for an empty stream. It fails on today's code with `illegal seek`.
- Live, with a v0.9.0 successor, in `bex-canary`:
  - `cat a.txt | bex s3 cp - s3://<owned>/pipe.txt` prints `upload: - to s3://<owned>/pipe.txt` and exits 0.
  - `head -c 20000000 /dev/urandom | bex s3 cp - s3://<owned>/big` stores 20000000 bytes, as `bex s3 info s3://<owned>/big` reads.
  - `< file` still works.
  - The bucket is removed afterwards.
- The download direction (`cp s3://… -`) could not be walked on 2026-11-21. Both QA workspaces' S3 reads are refused until 2026-12-01 (ADR112 § the egress budget, live), so re-check it then.

Unverified: whether the macOS and Windows builds fail the same way (a pipe's `Seek` fails on both, so they very likely do). Dedupe: no `.pm` item mentions `illegal seek` or a piped `cp -`; w21/m540 t003 and t009 walked files only.

Estimate: ~30m.
