# A web service's Restart or rollback clears a saved build command, branch or root directory from `undeployedChanges`, though the next deploy still builds with it

Why: after a Restart or a rollback, the dashboard and GraphQL say a repo-backed web, private or worker service has no undeployed changes, while a saved build setting that never went live waits for the next deploy, as w32/055 found for static sites.

- **Severity / estimate:** minor, ~1h.
- **Seen:** w32/055's triage, 2026-11-21, on `main` at `2e02b0303` (the note asked whether a web rollback has the same gap). Found by reading the code and confirmed with a throwaway unit test, not on production.
- **Cause** (`lego/operator/internal/controller`):
  - A Restart or rollback writes its release's runtime record through `recordReleasePodTemplate` (`release_config_snapshot.go:499`) and `writeRuntimeConfigRecord` (`release_config_selection.go:582-586`). That stamps `SettingsFingerprint = releaseSettingsFingerprint(app.Spec)`, the **saved** settings, with any pending save included. The target's record fingerprint is not used.
  - `servingConfigurationDiffers` (`saved_configuration.go:330-334`) compares settings outside the record's selected fields (build command, branch, root directory, Dockerfile path and context, runtime) only through that fingerprint (`recordedSettingsMatch`). So once the selected release serves, the pending save matches its own record and reads as deployed.
  - Selected fields (start command, health path, env, replicas, port, pre-deploy command) are still compared field by field, so w32/049's control (a cleared health check path, `true` / `historical_release`) stays correct.
- **Experiment:** in `release_config_selection_test.go`'s `selectedReleaseFixture`, the saved selected fields were made equal to the target's (as in `TestIdenticalRestartDoesNotReportUndeployedChanges`) and only `BuildCommand` was saved differently. After `materializeSelectedTestRelease`, `UndeployedChanges` was `false`. The rollback release's record fingerprint equaled the saved spec's (`release-v2:2c2899fc…`), not the target record's (`release-v2:98dab31f…`). The test was not kept.
- **Expected:** as on Render, a Restart keeps the running configuration, and a rollback reuses some of the target's. The next standard deploy uses the current configuration ([render.com/docs/rollbacks](https://render.com/docs/rollbacks), [deploys § Restarting a service](https://render.com/docs/deploys)). So a saved build setting that differs from the release serving reads `true` (`historical_release` for a selected release) until a deploy ships it.
- **Fix direction:** stamp a selected release's record with the settings it actually runs: the target record's `SettingsFingerprint` for the settings a rollback takes from the target, and the saved values for the ones it takes from the current configuration. The target's fingerprint also covers plan (`Tier`) and disk, which Render's rollback keeps current. Taking it verbatim would read a plan changed since the target as undeployed, so the fingerprint needs those split out, or a selection-specific fingerprint. A record without a fingerprint keeps today's conservative path.
- **Acceptance:** with a native or Dockerfile web service, `bex services update <id> --build-command '…'`, then `bex restart <id> --confirm`: after the restart is live, GraphQL `undeployedChanges` / `undeployedChangesReason` read `true` / `historical_release`, and the next `bex deploys create <id> --wait` clears them. The same holds for a rollback, and for a saved branch. Controls: an identical Restart reads `false` (`TestIdenticalRestartDoesNotReportUndeployedChanges`), and a plan changed since the target is not reported by a rollback.
- **Dedupe:** w32/055 (static sites, fixed through each publication record's settings) and w32/049 / w32/053 (static Restart, failed deploys) do not touch runtime records. w4/m433 and w5/m107 select the recorded runtime fields, not the build settings. `rg -i 'settingsfingerprint|undeployedChanges' .pm` finds no open item on web Restart or rollback.
