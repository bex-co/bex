# An S3 read refused by the monthly egress budget says "in this region would exceed", though the budget is the workspace's and already spent

Why: the refusal sends the user the wrong way. On 2026-11-21 the routine itself made a Frankfurt bucket to get around what read as an Oregon limit, and Frankfurt was refused the same way. Nothing in the message says that reads come back when the month turns.

- Severity: minor. The message is misleading wording; the gate itself behaves as ADR112 D3 says.
- Versions: production pin `f797f525f5df`, released `bex` v0.9.0. HEAD `06e0187d1` has the same text.
- Context: cli-qa routine run r23, 2026-11-21 08:27Z, workspace `bex-canary`. Its S3 reads are refused until 2026-12-01 by design (ADR112 § "The egress budget, live").

## Repro

```sh
bex s3 mb s3://qa-<nonce>-b1                                      # oregon
bex s3 cp a.txt s3://qa-<nonce>-b1/a.txt && bex s3 cp s3://qa-<nonce>-b1/a.txt -
bex s3 mb s3://qa-<nonce>-f1 --region frankfurt
bex s3 cp a.txt s3://qa-<nonce>-f1/a.txt --region frankfurt && bex s3 cp s3://qa-<nonce>-f1/a.txt - --region frankfurt
```

Both reads exit 1 with `Error: QuotaExceeded: this workspace's object storage in this region would exceed its egress limit of 5368709120 (request …)`. A presigned GET answers `403` with the same `<Message>` in S3 XML. An 11-byte read "would exceed", and the limit is a raw byte count. Both buckets were deleted afterwards.

## Cause

- `QuotaError.Error()` (`lego/backend/internal/objectstorage/quota.go:43-45`) has one sentence for every cap. That sentence is true for the per-region `bytes` and `objects` caps, which `Gate` checks per region.
- `CheckEgressBudget` (`quota_s3.go:154-180`) is different. It sums the workspace's month-to-date egress over every region, refuses once that is at or past the larger of the stored bytes and 5 GiB, and returns `&QuotaError{Resource: QuotaEgress, …}`. So the sentence is wrong for it three times over: the budget is not per region, it has already been reached, and its end is the month's turn.
- Consumers: S3 XML in `internal/s3gw/handlers_bucket.go:85`, and `bex s3`'s `explain` (`lego/cli/internal/s3/client.go`), which prints the server's message as-is.

## Fix

- Give `QuotaEgress` its own message, naming what the docs name (`docs/bex-cli.md` § Limits). For example: `this workspace's S3 reads this month have reached its egress limit of 5 GiB (the larger of the bytes it stores and 5 GiB, in every region); reads resume on 2026-12-01 UTC`. Keep the code `QuotaExceeded` and the status 403.
- Format the limit in GiB here. The `bytes` and `objects` messages may keep their wording.
- The gate has one caller, `objects_s3.go:54`. That covers the S3 surface, including SigV4 presigned URLs. Contract A's mint keeps its own bounds (ADR112 D2), so no other route changes.

## Acceptance

- A unit test on `CheckEgressBudget`'s error asserts it holds no "in this region" and no "would exceed", and that it names the reset date for a fixed clock. A test of the `bytes` cap's message still reads "in this region".
- Live in `bex-canary` before 2026-12-01: `bex s3 cp s3://<owned>/a.txt -` prints the new message in both regions. Remove the fixture afterwards.

Dedupe: ADR112 line 505 quotes the message as observed and does not grade its wording. No `.pm` item covers it.

Estimate: ~20m.
