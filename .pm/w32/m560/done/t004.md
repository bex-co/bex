## Objective

When the release's app container got bex's `WEB_CONCURRENCY` default (t001's `webConcurrency` > 0), the deploy log writes Render's line right after `==> Deploying...`, with N set to that value. Example: `==> Setting WEB_CONCURRENCY=1 by default, based on available CPUs in the instance`.

## Context

- Render prints it about 0.1 s after `Deploying...` on native and Docker web services alike. Every one of the 30 logs in the milestone README shows it.
- [Render's docs](https://render.com/docs/environment-variables) set the default on web and private services created after 2025-12-08, to the plan's CPU count. bex's rule is `webConcurrency` (`lego/operator/internal/controller/web_concurrency.go:56`): web or private, created after `webConcurrencyCutoff` (2026-10-21), and no value of the service's own. The line follows bex's rule, because it reports what the container got.
- Qxad/openlist-for-PaaS#2 shows the line on what may be a prebuilt image. If bex image deploys get the default, write the line after their own rollout line too.

## Acceptance criteria

- [ ] Unit tests show the line, with the recorded N, right after `Deploying...` for a web and a private service that got the default.
- [ ] They show no line for a background worker, a cron job, a static site, a service that sets its own `WEB_CONCURRENCY`, or a service created before the cutoff.

## Done (2026-11-22)

`==> Setting WEB_CONCURRENCY=N by default, based on available CPUs in the instance` is held just after the rollout line, and after an image deploy's own `==> Deploying image` line too, whenever the container got bex's default. Covered by the same table test (worker, own value, prebuilt image).
