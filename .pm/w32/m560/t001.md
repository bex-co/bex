## Objective

For each release generation that rolls out an instance, the operator records in App status four facts that bex-api's deploy log will narrate:

- **When the rollout started:** the first write of the release's serving Deployment template, after its build and any pre-deploy step. It is recorded below the second, so it sorts after the build pod's own last line.
- **Each start of the release's app container** on its current-revision pods while the rollout runs.
- **The start command it launched** on a native image, and nothing for any other launch.
- **The `WEB_CONCURRENCY` default** the app container got, or 0.

The operator stays database-free: these are status facts that bex-api projects.

## Context

- Shapes to follow in `lego/types/v1alpha1/app_types.go`: `ReleaseStart` (`:1627`, stamped only on a forward move), `BuildRunStatus` (`:1677`), `InstanceExit` / `InstanceExits` (`:1734`, `:2139`, bounded at 10) and `RolloutFailureStatus` (`:1806`).
- The template write: `applyServingDeployment` (`lego/operator/internal/controller/release_config_snapshot.go:739`).
- Current-revision pods and their container states: `withInstanceExits` (`lego/operator/internal/controller/instance_exits.go:237`). The kubelet's `State.Running.StartedAt` gives the current start, and `LastTerminationState.Terminated.StartedAt` gives the one before a restart. Both are whole seconds.
- The launch decision: `appContainer` (`deployment_projection.go:434-440`). `launchNativeArgs` runs `nativeStartArgs(app.Spec.StartCommand)` through native-init. Render prints `Running '<cmd>'` only for that case: a Docker image, with or without a Docker Command, prints none (HKUDS/nanobot#6607). The command must be the release's own (the release record, `ReleaseRecordSpec.StartCommand` in `lego/types/v1alpha1/releasesnapshots.go:105`), not the App's current spec.
- The `WEB_CONCURRENCY` default: `webConcurrency` (`web_concurrency.go:56`), which is 0 unless the service is web or private, was created after the cutoff, and sets no value of its own.

## Steps

1. Add a status record, for example `status.releaseRollout {generation, startedAt metav1.MicroTime, appStarts []metav1.Time (max 10), command string, webConcurrency int32}`. Document each field the way its neighbours are documented, then run `make manifests generate`.
2. Stamp `startedAt`, `command` and `webConcurrency` when the release's template is first written. A resync, a cancel's revert or a survivor's redispatch never moves them, and a new generation replaces the record.
3. Append each distinct app-container start on that generation's pods until the release settles (live, failed or canceled), up to the bound.
4. Write nothing for a static site (it publishes, it runs no instance) or a cron job (it runs no instance at deploy).

## Acceptance criteria

- [ ] Envtest: the first template write stamps the record once, and a resync does not move it. A pod restart adds a start. A newer generation replaces the record. `command` is set only for a `launchNativeArgs` release. `webConcurrency` is non-zero only when the container got the default.
- [ ] A static site and a cron job get no record.
- [ ] `make test` passes (run it with `-timeout 30m`; the controller package takes 630–730 s on this host), and `make lint` passes.
