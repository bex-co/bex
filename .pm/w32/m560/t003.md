## Objective

`progressLines` writes `==> Deploying...` at `RolloutStartedAt` for every built deploy that started its rollout. That covers native and Dockerfile builds of a web service, a private service and a background worker.

## Context

- `lego/backend/internal/logs/progress.go:353-431` (`progressLines`) and `:599-714` (the closing lines).
- Render's evidence is in the milestone README § Render's lines. The line follows a native build's `==> Build successful 🎉` and a Dockerfile build's BuildKit output alike.
- bex's own narration for deploys that run no build stays: `==> Deploying image <image>` for an image-backed deploy or a rollback, and `==> Rolling out the current release` for a reuse rollout, both at `started_at`. Keep them unless a Render log of a prebuilt-image or rollback deploy shows otherwise. Look for one (Qxad/openlist-for-PaaS#2's `==> Starting service...` is ambiguous) and record what you find in ADR018.

## Steps

1. Add the line at `RolloutStartedAt` when the deploy built (`d.Built`, the same evidence `progressLines` uses) and a rollout start is recorded.
2. Make sure it sorts after the build's own last line. Hold it just after any build line of the same instant if the clock needs that (compare `hookLines`' whole-second handling).
3. Write no line without a recorded moment. That covers:
   - a row an older operator closed;
   - `build_failed`;
   - a cancel before the rollout;
   - a static site;
   - a cron job.

## Acceptance criteria

- [ ] Unit tests in `progress_test.go` show the line for a built web, private and worker deploy that reached its rollout (`live`, `update_failed`, canceled during the rollout).
- [ ] The same tests show no line for `build_failed`, for a cancel before the rollout, for a static site, for a cron job, or when no moment is recorded.
- [ ] A test shows that the line sorts after a native build's `Build successful` line within the same second.
