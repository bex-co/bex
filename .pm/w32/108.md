# Switching a service's repository via `bex services update --repo` without `--branch` keeps stale or placeholder `"main"` instead of resolving the new repository's default branch

Why: Switching an image-backed service (whose `branch` reads `null`) or a `main`-branch Git service to a `master`-default repository via `bex services update --repo <url>` silently saves `"branch": "main"`, leaving the next deploy with `commit: null` and a broken clone (`couldn't find remote ref main`) even though `ValidateRepo` already fetched the new repository's real default branch.

### `bex services update --repo` without `--branch` leaves a switched service on `"main"` for `master`-default repositories

- **Severity:** major
- **Versions:** released `bex v0.9.0` (`bex-0.9.0-linux-arm64.tar.gz`, sha256 `714f4e1a…`, pinned Render CLI `v2.36.0`); production pin `f46c44d9ddb1` (`eb52a59622`)
- **Context:** 2026-11-24 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login (`scripts/qa-login.sh --login-challenge`), non-TTY `-o json --confirm`

- **Expected / actual:**
  - **Expected:** Matching `services create` (`w8/m76`, `w8/343`) and Blueprint source switches (`w8/m80`), when `PATCH /v1/services/{id}` (or GraphQL `setRepo` / MCP `update_service` / build-source unlink) changes `repo` to a different repository and omits `branch` (or passes an empty `branch`), bex resolves the new repository's default branch (`"master"` for `https://github.com/render-examples/go-web-server`) from `ValidateRepo` instead of keeping an image service's hidden `"main"` placeholder or the old repository's branch. An explicit `--branch` still wins, and an update that does **not** change `repo` still preserves the existing `a.Spec.Branch`.
  - **Actual:**
    - Pure-image switch (`srv-dc2fn71npn2c73ckva5g`): exited `0` with `{"id":"srv-dc2fn71npn2c73ckva5g","repo":"https://github.com/render-examples/go-web-server","branch":"main","imagePath":null,"runtime":"docker"}` — saved `"branch": "main"` even though the repo's default branch is `"master"` and `main` does not exist.
    - Git(`main`) → Git(`master`-default) switch (`srv-dc2fn8pnpn2c73ckva80`): exited `0` with `{"id":"srv-dc2fn8pnpn2c73ckva80","repo":"https://github.com/render-examples/go-web-server","branch":"main","imagePath":null,"runtime":"docker"}`.
    - Follow-up `bex deploys create srv-dc2fn8pnpn2c73ckva80 --confirm -o json` opened `dep-dc2fnc9a05ic738s5g50` with `"commit": null` because branch `main` does not exist in `render-examples/go-web-server`.
- **Wire evidence:**
  - Pinned CLI (`pkg/service/update.go:30-35`) sends `PATCH /v1/services/{id}` with `{"repo":"https://github.com/render-examples/go-web-server"}` (`branch` omitted).
  - Server returned `200 OK` with `"repo":"https://github.com/render-examples/go-web-server","branch":"main","imagePath":null`.
  - Follow-up `POST /v1/services/srv-dc2fn8pnpn2c73ckva80/deploys` returned `{"id":"dep-dc2fnc9a05ic738s5g50","status":"queued","commit":null}`.
- **Runtime evidence:** Both disposable fixtures (`srv-dc2fn71npn2c73ckva5g`, `srv-dc2fn8pnpn2c73ckva80`) were created in `bex-canary` and deleted after the probe.
- **Attribution:** server
- **Root cause:**
  - `lego/backend/internal/apps/service.go:5547-5589` (`resolveSourcePatch`): initializes `next.branch = a.Spec.Branch` (which on an image-backed service is the hidden default `"main"`, masked as `null` by `view()` at `service.go:1264`, and on a Git service is the previous repo's branch) and falls back to `appv1alpha1.DefaultBranch` (`"main"`) when empty.
  - `lego/backend/internal/apps/settings_check.go:703-711` (`checkSourcePatch`): when `next.repo != "" && next.repo != a.Spec.Repo && s.GitHub != nil`, calls `_, repoID, err := s.GitHub.ValidateRepo(ctx, s.AppWorkspace(ctx, a), next.repo)` and explicitly discards `defaultBranch` (`// The reported default is unused: a source edit keeps its own branch rule`).
  - Contrast with `Create` (`lego/backend/internal/apps/service.go:2496-2507`, `w8/m76`/`w8/343`) and Blueprint source switches (`w8/m80`), which both apply `useRepositoryDefaultBranch` whenever a new repository is set without an explicit branch.
  - Pinned consumer: `github.com/render-oss/cli@v1.1.3-0.20261117005113-11ef59f330de` `pkg/service/update.go:30-35` omits `branch` from `UpdateServiceJSONRequestBody` unless `--branch` was passed.
- **Fix:**
  - In `lego/backend/internal/apps/settings_check.go:703-711` (`checkSourcePatch`), when `next.repo != "" && next.repo != a.Spec.Repo` and the caller did not specify a non-empty branch (`patch.Branch == nil || strings.TrimSpace(*patch.Branch) == ""`):
    - Use `defaultBranch` returned by `s.GitHub.ValidateRepo(ctx, s.AppWorkspace(ctx, a), next.repo)` via the same `useRepositoryDefaultBranch` / `store.ValidGitRef` validation `Create` uses (refusing an unsafe default branch with `400`, and falling back to `appv1alpha1.DefaultBranch` when `s.GitHub == nil` or `defaultBranch == ""`).
    - Keep `a.Spec.Branch` unchanged whenever `next.repo == a.Spec.Repo` and `patch.Branch == nil` (preserving branch on same-repo edits such as updating `registryCredentialId` or re-sending the same `repo`).
    - Ensure the resolved `next.branch` is reflected in both the preflight probe (`settings.go:243`, `probedSource` cache) and the actual write (`SetSourceAndRegistryCredential`, `build_sources.go:637`).
  - Update the stale note in `docs/cli-compatibility-checklist.md:353` if needed so it reflects that changing `repo` without `branch` resolves the new repo's default branch while same-repo edits keep their branch.
