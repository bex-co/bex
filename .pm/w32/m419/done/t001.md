## Objective

When the registry refuses the image of a service's newest release (a missing tag, a refused credential, any other `ImageRead` failure) and an earlier release has served, keep converging everything that does not need the new image on the serving release: the Ingress and its IP allow-list middlewares, replicas, suspension and hibernation. The failure stays recorded exactly as w4/533 records it.

## Context

- `lego/operator/internal/controller/app_controller.go:770-779`: the image-port branch of `Reconcile`; `resolveImageNetwork` runs before `dispatchRuntime` (`:1087`), and a refusal returns through `failBeforeDispatch` (`:777`, `:7101`).
- `release_identity.go:720` `reusableArtifactImage` returns `ActiveReleaseConfig().Image` (the per-deploy override, `lego/backend/internal/deploys/service.go:964-966`) or `spec.image`. Every later pass therefore refuses the same image again.
- `resolveDeployImage` (`:998`) already holds the serving release through `holdPendingArtifact` (`:7496`) after a recorded build failure or for a static site (`:1010-1015`; w1/m157, w8/289, w32/003).
- w4/533 (`fail_before_dispatch_test.go`): over a served release the phase and Ready keep describing it, the Rollout condition carries the failure to the deploy row, and no `server_failed` is emitted.

## Steps

1. In the image-port branch, when `resolveImageNetwork` refuses and `releaseHasServed(app)`, record the failure as `failBeforeDispatch` does (Rollout condition, `settleFailureOverPriorRelease`). Then hold the serving release instead of returning: call `holdPendingArtifact`, or an image-port variant of it that serves `Status.ServingNetwork`'s image and port.
2. Without a served release, keep today's ordinary failure.
3. Once the refusal is recorded for the same (image, release generation), do not re-read the registry on every later pass. The next deploy, or a changed image, reads it again.
4. Make sure the next successful deploy still promotes normally, and a rollback still works.

## Acceptance criteria

- [ ] An envtest App with a served release and a refused candidate image projects a changed `ipAllowListEntries` to its `-ip-allow` Middleware, and removes the Middleware when the list returns to allow-all.
- [ ] The same App, suspended, routes its hosts to the activator's suspended responder and runs zero replicas.
- [ ] The Rollout condition still carries the refusal, the deploy row still ends `update_failed`, and no `server_failed` fact is produced (w4/533's tests pass unchanged).
- [ ] With no served release, the refusal is still an ordinary failure.

## Out of scope

- Failed rollouts of an image that exists (`ProgressDeadlineExceeded`, w4/m103).
- The wording of the refusal (w4/534).
