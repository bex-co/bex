# `bex restart <dpg-id>` silently swallows every HTTP error (401/403/404/409/500) and exits `0` — upstream CLI defect, grade it in the checklist and fix `w32/111`'s acceptance step

Why: `bex restart dpg-00000000000000000000 --confirm -o json` prints `"dpg-00000000000000000000 restarted successfully"` and exits `0` even when production returns `HTTP 404` (or `409 Conflict` on a suspended database). `docs/cli-compatibility-checklist.md:244` currently grades `restart <resourceID>` `[x]` with no upstream caveat, and parked `.pm/w32/blocked/111.md` (lines 44, 66, 81) instructs the resumed worker to verify `409` through `bex restart <suspended-dpg>`'s exit code — which cannot pass on pinned Render CLI `v2.38.0` even after `f2a2996939` deploys.

### `bex restart <dpg-id>` reports success (exit `0`) on every HTTP error status

- **Severity:** major (upstream CLI defect; docs/ledger + board acceptance fix in bex)
- **Versions:** checkout build of `lego/cli` at `9c35eb2a0c` (pinned Render CLI `v2.38.0`, `github.com/render-oss/cli@v1.1.3-0.20261120013850-09b7802aa379`); production pin `ff5de0a130e6` (`d9dd27d687`)
- **Context:** 2026-11-24 UTC, `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device login (`scripts/qa-login.sh --login-challenge`), non-TTY `-o json --confirm`

- **Expected / actual:**
  - **Expected:** `bex restart dpg-00000000000000000000 --confirm -o json` exits `1` and surfaces the server's `404` (`not found`) — and on a suspended Postgres once `f2a2996939` deploys (`w32/111`), exits `1` surfacing `409 Conflict`.
  - **Actual:** `bex restart dpg-00000000000000000000 --confirm -o json` printed `"dpg-00000000000000000000 restarted successfully"` and exited `0` in a fresh CLI process. Controls: `bex restart srv-00000000000000000000` exited `1` (`received response code 404: not found`); `bex restart red-00000000000000000000` exited `1` (`key / value stores cannot be restarted`); `bex restart bogus-id` exited `1` (`unknown resource type`).
- **Wire evidence:**
  - `POST https://api.bex.co/v1/postgres/dpg-00000000000000000000/restart` → `HTTP/2 404`, body `{"error":"not found","id":"not_found","message":"not found"}`.
- **Runtime evidence:** No Postgres resource exists for `dpg-00000000000000000000`; disposable Postgres `dpg-dc2manho7jsc73b3pls0` was created and deleted in `bex-canary`.
- **Attribution:** upstream (`render-oss/cli`), not bex server or launcher. Do **not** fork the CLI or add a server/launcher workaround.
- **Root cause:**
  - Pinned upstream `github.com/render-oss/cli@v1.1.3-0.20261120013850-09b7802aa379` `pkg/postgres/repo.go:90-97` (`RestartPostgresDatabase`): calls `r.client.RestartPostgres(ctx, id)` — returning a raw `*http.Response` instead of `RestartPostgresWithResponse` — and passes `*http.Response` to `client.ErrorFromResponse(resp)`.
  - `client.ErrorFromResponse` → `firstNonNilErrorField` (`pkg/client/client.go:176-186`) dereferences the pointer and reflects for a struct field named `HTTPResponse` (`v.FieldByName("HTTPResponse")`). Because `*http.Response` has no `HTTPResponse` field, `!httpRespField.IsValid()` returns `nil` unconditionally for **every** HTTP error status (`401`, `403`, `404`, `409`, `500`), and `cmd/restart.go` prints `"<id> restarted successfully"` and exits `0`.
  - Compare sibling `pkg/service/repo.go`, which calls `RestartServiceWithResponse` (returning `*RestartServiceResponse`, which has an `HTTPResponse` field), so `bex restart srv-...` properly fails on `404`/`409`.
