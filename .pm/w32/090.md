# A failed deploy's one `==> Exited with status N` comes after the start command's first exit on Render, and at the close after its third run on bex

Why: Render parity in the deploy log of a failing deploy. Render's verdict follows the run whose exit it reports, and the command's later runs come after it. bex's log reads three `==> Running '<command>'` lines and then the verdict, so the exit it names reads as the last run's.

- **Severity / estimate:** minor, likely more than 1h: the operator records the first exit of the release's app container, the deploy row keeps it, and `progressLines` moves the verdict to it. Promote when picked up if it is.
- **Seen:** w32/086's triage, 2026-11-22. That note's premise, a pair after each run, does not hold: no public log shows Render writing the pair twice in one deploy (w32/086's closing record). Where it writes the one pair does differ from bex.
- **Render reference (public issue logs):**
  - DerekSopok/EMS-Kahoot#3 (native Node): `==> Running 'npm start'` at 22:14:58.31, npm's error, the pair at 22:15:02.93, then `==> Running 'npm start'` at 22:15:06.54.
  - rkendel1/freq#187 and #191 (Docker): the first run's output, the pair at 17:45:22.21 (status 1) and at 18:22:03.32 (status 2), then the second run's output. In #191 a port-scan line follows at 18:22:15.68.
  - darthjee/ward#109 (Docker): run 1, the pair at 01:32:22.77, run 2 (yarn's `Command failed with exit code 1.` at 01:32:28.24), a port-scan line at 01:32:30.86, then run 3 from 01:32:49.19. Neither later run gets a pair.
  - muppetbrown/mana_meeples_singles_market#63 (native Node): the pair at 05:25:58.31, `==> Running 'node server.js'` again at 05:25:59.10. omkarwarik02/DevLens#1 has the pair, then `==> Running 'node src/index.js'`.
  - The one exception is muppetbrown/mana_meeples_singles_market#84: run 1's output ends at 18:21:58.24 with no pair, and the pair follows run 2's at 18:22:04.28.
- **bex today:** the operator settles a startup crash once the app container has restarted twice and is back-off waiting (`crashSettleRestarts`, `permanentRolloutCrash`, `lego/operator/internal/controller/app_controller.go`). The close then records the last exit (`end_exit_code`), and `closingLines` writes the pair at `finished_at` (`rendersVerdict`, `lego/backend/internal/logs/progress.go`). Since w32/m560, `rolloutLines` writes a `Running` line at each recorded start, so a failed native deploy's `type=build` log reads `Running`, `Running`, `Running`, then the pair.
- **Open question:** Render may fail the deploy at the first exit and restart the instance after that. Its deploy page would then show the later runs because its window runs "shortly after the deploy finished" (w32/084). bex instead holds the deploy open for two restarts (w4/454, whose triage left "Render's exact time-to-fail" unverified). w32/085's Render account would settle it: the deploy's `finishedAt` set against the pair's timestamp. The parity-sufficient shape below does not wait on that answer.
- **Likely shape:** the operator records the first exit of the release's app container while the rollout runs, beside `status.releaseRollout.appStarts`. That is the earliest `lastState.terminated` that `withAppStarts` already reads: its `finishedAt` and `exitCode`, and not an out-of-memory kill. The deploy row keeps it (a migration, the next free number on `origin/main`). For an `update_failed` deploy, `progressLines` then writes `==> Exited with status N` and the troubleshooting line at that exit, with N that run's status. The exit is stamped in whole seconds, so the pair is held after the run's own output. The close adds no second pair. A deploy whose later run serves keeps today's lines until the open question is settled.
- **Done when:** in `bex logs -r <srv> --type build`, a failed native deploy whose start command exits three times reads `==> Running '<command>'`, `==> Exited with status N` and the troubleshooting line, then the other two `Running` lines, with nothing more at its close. A Dockerfile service reads the same without the `Running` lines. REST, the subscribe stream, GraphQL, MCP and the dashboard's deploy page show the same lines. `docs/render-artifacts/live-deploy-following.md` § Platform progress-line contract and ADR018 § Logs, Build logs cite the logs above.
