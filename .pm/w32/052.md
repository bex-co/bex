# A native service's build or start command can be saved empty, and every later deploy fails at dispatch; create and a runtime change refuse the same state with 400

Why: `bex services update <id> --build-command ''` (or `--start-command ''`, or a switch from an image back to Git) answers success, and the service then cannot build at all, while create refuses that exact configuration up front.

- **Severity / estimate:** minor, ~45m.
- **Seen:** `/qa-find-bugs-cli w32` routine, run `4aa5`, 2026-11-20 02:22–02:42 UTC. Production pin `98e053468f52` (`c8c774658`; the running images were not read, the control plane did not answer `fetch-app-kubeconfig.sh`). Released `bex` v0.7.0 (Render CLI v2.36.0, `bex-0.7.0-linux-arm64.tar.gz`, checksum verified), isolated `BEX_CLI_CONFIG_PATH`, human device login as the QA user, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), `-o json` / `-o text`, non-TTY.
- **Repro** (owned free web service `qa-20261120-4aa5-web`, `srv-dbvqu1k3j89c738ag6i0`, deleted after the run; `bex-co/bex` `main`, root `examples/default-env-probe`, runtime `node`):
  1. `bex services create --name <n> --type web_service --runtime node --repo https://github.com/bex-co/bex --branch main --root-directory examples/default-env-probe --build-command 'echo QA4AA5 build v1' --start-command 'echo QA4AA5 start v1; exec perl serve.pl' --plan free --region oregon --auto-deploy=false -o json`. It went `live`.
  2. `bex services update <id> --build-command '' -o json` → exit 0. `bex services update <id> --start-command '' -o json` → exit 0. The pinned CLI sends `PATCH /v1/services/<id>` `{"serviceDetails":{"envSpecificDetails":{"buildCommand":""}}}` (then `startCommand`), both `200`. REST reads `envSpecificDetails: {"buildCommand":"","startCommand":""}`, `undeployedChanges: true`, reason `saved`.
  3. `bex deploys create <id> --wait --confirm` → exit 1, `Build failed for deploy dep-dbvr6gc3j89c738ag6u0`, 1 s after `Deploy queued`. Build log: `==> Build failed: dispatching build: build: native runtime node requires buildCommand`.
  4. With only the build command restored (`--build-command 'echo QA4AA5 build v4'`), the next deploy `dep-dbvr6jk3j89c738ag6vg` failed the same way: `native runtime node requires startCommand`.
  5. Same end state through a source switch: `services update <id> --image docker.io/library/nginx:alpine` (exit 0; the switch drops the native commands, w8/m461), a deploy went `live` on nginx, then `services update <id> --repo https://github.com/bex-co/bex --branch main` (exit 0) put the service back on runtime `node` with `buildCommand: ""`, `startCommand: ""`. Its deploy `dep-dbvr3n150n7c739ba5ug` failed: `native runtime node requires buildCommand`.
  - In every case the previous release kept serving (`curl` 200), so nothing went down; the service just cannot deploy, and with Auto-Deploy on every push fails the same way.
- **Expected:** the save is refused with the create's own answer, `400 native runtime node requires buildCommand and startCommand`, naming what is missing, so the caller can send the command in the same update (`--repo … --build-command … --start-command …`). Render's create schema requires both for a native runtime (`nativeEnvironmentDetailsPOST.required: [buildCommand, startCommand]` in `lego/backend/internal/api/openapi/render-public-api-1.json`).
- **Root cause:**
  - Create refuses the state: `resolveBuildStrategy` (`lego/backend/internal/apps/service.go:3861`, the native branch at `:3891-3901`), "refused here rather than failed at every build" (w2/m254 t016). A runtime change refuses it too, because `checkRuntime` (`runtime_change.go:34-42`) runs the same resolver over the saved commands.
  - The commands row of the PATCH table (`settings.go:462-480`) checks only `checkCommands` (`settings_check.go:286-298`): protection, applicability, and no build command on an image. It never asks whether the result is still buildable. `SetCommands` (`service.go:5137`) is the same check, and GraphQL `setBuildCommand` / `setStartCommand` (`graphql.go:1797`, `:1813`, the dashboard's Build & Deploy fields) call it directly.
  - The source row (`settings.go` source op → `checkSourcePatch`, `settings_check.go:573`; `settleSourceSwitch`, `build_strategy.go:123`) keeps the native runtime for a switch back (w4/m202) but not the commands it dropped on the way to the image, and nothing checks the result.
  - The operator then refuses every dispatch: `validateNativeOptions` (`lego/operator/internal/build/native.go:290-300`).
- **Fix:** judge the finished probe once, after every row's check in `preflightServicePatch` (`settings.go:727-731`), with the create rule: when the resulting service builds natively (repo-backed, native runtime, not a static site, not linked to a build source) and the patch touched the commands, the source or the runtime, an empty `buildCommand` or `startCommand` answers `400 native runtime <rt> requires buildCommand and startCommand` (a cron job: `buildCommand`; its command is `command`). Do the same in `SetCommands` and in the GraphQL source setters (`setRepo`, `graphql.go:1753`, and its siblings), so the dashboard gets the same refusal. Leave a service already in that state free to take unrelated updates (name, plan, env vars).
- **Blast radius:** REST `PATCH /v1/services/{id}` and MCP `update_service` (one table); GraphQL `setBuildCommand`, `setStartCommand`, `setRepo` and the other source setters. Types: native web, private, worker and cron. Not affected: static sites (an empty build command publishes the files as they are, w8/m59), Docker and image services (an empty start command runs the image's own), a service linked to a build source (its build source builds; its own start command is still required).
- **Regression checks:** the repro's step 2 and step 5 each answer 400 and leave the service unchanged. Controls: `--build-command '' --publish-directory .` on a static site still saves; `--start-command ''` on a Docker service still saves; `--repo … --branch main --build-command A --start-command B` on an image service switched from native saves and its deploy goes `live`; a rename of a service already missing a command still saves.
- **Unverified:** Render's own answer to a `PATCH` with an empty native `buildCommand` was not observed (no Render credential, w32/039). The MCP and GraphQL paths were read from the code, not exercised.
- **Dedupe:** `rg` of `.pm` for `requires buildCommand`, `requires startCommand`, empty or cleared build/start command: w8/m59 (static site, fixed by publishing as-is), w2/m254 t016 (create-time refusal), w4/m202, w8/m461 and w8/088 (source-switch commands and runtime) cover neighbours, not this. No commit since the pin touches `settings.go`, `settings_check.go` or `build_strategy.go`.
