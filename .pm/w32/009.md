# `bex logout` and a bad `BEX_OUTPUT` name `RENDER_*` variables the user never set

Why: a user who signs in with `BEX_ACCESS_TOKEN` (the documented CI input) and runs `bex logout` is told they are "authenticated via the RENDER_API_KEY environment variable". That variable is not in their environment, so they cannot find what to unset. A mistyped `BEX_OUTPUT` is reported as `invalid RENDER_OUTPUT value` the same way.

- **Severity:** minor (misleading copy; behavior and exit codes are right)
- **Versions:** bex v0.5.0 (release, Render CLI pin v2.35.0) and a checkout build of HEAD `7fea1980d` (pin v2.36.0, `4fd34231b637`). Same result on both. Deployed revision: n/a (client-side only).
- **Context:** 2026-11-11 `/qa-find-bugs-cli w32` loop sweep, offline (the QA sign-in is still refused, see w32/m284). No production request was made: isolated `BEX_CLI_CONFIG_PATH`, placeholder tokens, and for the stored-login cases a loopback stub answering `POST /v1/oauth/revoke`. Every `RENDER_*` unset. Non-TTY, `-o text`.
- **Repro (every `RENDER_*` unset):**
  1. `BEX_ACCESS_TOKEN=<token> bex logout`, no stored login.
  2. The same with a stored login (`cli.yaml` holding `api.key`), revoke answering 204.
  3. The same, revoke answering 404.
  4. `BEX_OUTPUT=bogus bex services` (any command but `--help`).
- **Expected:** the message names the variable the user set, `BEX_ACCESS_TOKEN` or `BEX_OUTPUT`. `docs/bex-cli.md:60,110` tell the user to unset `BEX_ACCESS_TOKEN`. When the user really set `RENDER_API_KEY` or `RENDER_OUTPUT`, upstream's name stays.
- **Actual (exit 0 for 1–3, exit 1 for 4):**
  1. `You are authenticated via the RENDER_API_KEY environment variable.` / `This command cannot remove environment variable credentials.` / `To revoke access, delete the API key from your Bex dashboard.`
  2. `OAuth credentials cleared. Note: RENDER_API_KEY is still set in your environment.`
  3. `Warning: something went wrong revoking your CLI token: revoke token failed with status 404. … revoke your token in the Bex dashboard: https://dashboard.bex.co/settings#cli-tokens` / `Note: RENDER_API_KEY is still set in your environment.`
  4. `invalid RENDER_OUTPUT value: bogus`

  (v0.5.0 also still says "your Render Dashboard" and "the Render dashboard" in 1 and 3. w2/082 fixed that on HEAD; it ships with the next CLI release.)

- **Wire evidence:** cases 1 and 4 send no request. In cases 2–3 the stub saw one `POST /v1/oauth/revoke` (Authorization present, User-Agent `render-cli/2.36.0`), and `cli.yaml` was deleted.
- **Attribution:** Bex launcher. Upstream's copy is true for its own variables.
- **Root cause:** `bridge.apply` (`lego/cli/internal/bridge/bridge.go:66-80`) copies `BEX_OUTPUT` → `RENDER_OUTPUT` and `BEX_ACCESS_TOKEN` → `RENDER_API_KEY` when the upstream variable is unset, and keeps no record of having done so. Upstream then prints its own variable's name:
  - `cmd/logout.go:34,73,79`, on stdout;
  - `pkg/command/outputresolver.go:107`, printed to stderr by `printRootPreRunError` (`cmd/root.go:337-350`) inside the root `PersistentPreRunE`, before any `RunE`.

  The run-time rule never rewrites `RENDER_*` names (`lego/cli/internal/branding/runtime.go:45-50`). That is right only when the user set the upstream variable. w2/done/082 saw case 1, noted "a correct fix has to know which variable was the source", and did not file it.

- **Fix:**
  1. Have the bridge record which upstream variables it filled from a Bex input in this process (for example `bridge.Mapped()` returning only the pairs it set: `RENDER_API_KEY` ← `BEX_ACCESS_TOKEN`, `RENDER_OUTPUT` ← `BEX_OUTPUT`).
  2. `logout` stdout is already wrapped (`runtimeStdout["logout"] = plainOutput`). When `RENDER_API_KEY` was mapped, rewrite the three exact phrases to name `BEX_ACCESS_TOKEN`: "via the RENDER_API_KEY environment variable." and the two "Note: RENDER_API_KEY is still set in your environment." lines.
  3. The `RENDER_OUTPUT` error is printed outside `RunE`, so neither existing seam reaches it. Wrap the root `PersistentPreRunE` (upstream sets it in `setupRootCmdPersistentRun`, `cmd/root.go:264`, so wrap it where `branding.Refresh` runs) and rewrite "invalid RENDER_OUTPUT value:" on stderr for the length of that call only, when `RENDER_OUTPUT` was mapped. Do not validate `BEX_OUTPUT` in the launcher: `--help` must keep exiting 0 with a bad value, as upstream does.
  4. Keep exact-phrase matching, as `runtimeProse` does, so API data and a user's own `RENDER_*` value are never touched. Record the rule in `docs/bex-cli.md` § Compatibility and branding limits.

  No REST/GraphQL/MCP/UI surface is involved.

- **Blast radius:** these four strings are the only upstream run-time copy that names a variable the bridge maps (grep of the pinned module for `RENDER_(API_KEY|WORKSPACE|HOST|OUTPUT|CLI_CONFIG_PATH|CLI_CONFIG_DIR|CLI_DISABLE_ANALYTICS)` outside tests and generated clients). `RENDER_WORKSPACE`, `RENDER_HOST` and the config variables appear in no run-time message. Help text naming `RENDER_CLI_CONFIG_DIR` is already rewritten by the overlay. The one-time analytics notice ("remove RENDER_CLI_DISABLE_ANALYTICS") is a documented residual and stays out of scope.
- **Regression checks:** binary tests beside `TestLogoutRevokeFailureNamesBex` (`lego/cli/runtime_copy_test.go:189`):
  - `BEX_ACCESS_TOKEN` set, no stored login → stdout names `BEX_ACCESS_TOKEN` and not `RENDER_API_KEY`;
  - `RENDER_API_KEY` set by the user → stdout still names `RENDER_API_KEY`;
  - stored login plus `BEX_ACCESS_TOKEN`, revoke 204 and 404 → both notes name `BEX_ACCESS_TOKEN`;
  - `BEX_OUTPUT=bogus bex services` → stderr `invalid BEX_OUTPUT value: bogus`, exit 1; `RENDER_OUTPUT=bogus` → upstream's text unchanged; `BEX_OUTPUT=bogus bex --help` → exit 0.

  Then `cd lego/cli && go test ./...`.

- **Unverified:** an interactive terminal (the logout spinner path) was not run; the strings are the same `command.Println` calls. Whether "delete the API key from your Bex dashboard" is the right remedy for every `BEX_ACCESS_TOKEN` (it is an OAuth access token, `docs/bex-cli.md:86-110`) was not examined and is not part of this note.
- **Dedupe:** w2/done/082 (seen, explicitly not filed) and w2/done/073 cover product-name prose only. w8/blocked/107 is about an explicit `--output` flag not overriding a bad default (upstream PR #71), not the variable's name; its fix would not change this message for the no-flag case. Nothing open on any board covers the variable names. Not in `DO_NOT_DO.md`, the ADR018 divergences, or the residual list in `docs/bex-cli.md`.
