# A manifest change that adds a binary flag crash-loops the new pod from the Argo sync of the push until the image pin lands

Why: the operator's rollout looks failed for the 30 to 40 minutes the build takes (CrashLoopBackOff, `kubectl rollout status` stuck), and a second restart of the old pod in that window would take the operator down.

Found 2026-11-16 shipping w21/m421 t001.

- **What happened:** commit `f114fdd9f` added `--pprof-bind-address` to the manager's `args` in `lego/operator/config/manager/manager.yaml` and to `cmd/manager/main.go`. Argo CD synced the manifest from `main` at the push; the image pin (`chore(deploy): pin platform images to <sha>`, `deploy/gitops/base/bex.yaml`) lands only after `deploy.yml` has tested and built, about 35 minutes later. For that window the new ReplicaSet ran the previous image with the new argument: `flag provided but not defined: -pprof-bind-address`, exit 2, CrashLoopBackOff with 8+ restarts. The old pod kept serving because the Deployment has `maxUnavailable: 0`, so there was no outage; the old pod also restarted once (exit 137) in the window, and had the new ReplicaSet been the only one, the operator would have been down.
- **Why it recurs:** every manifest change that depends on a new binary behavior (a flag, a required env var the binary now validates, a new mount path) has this window.
- **Options:** pass new settings as environment variables or defaults (an old binary ignores an unknown variable, a new one reads it); or keep manifest changes that need the new binary out of `main` until the pin commit lands; or make `deploy.yml` commit the manifest and the pin together. Start with a guard: a test or script that fails a change to a container's `args` unless the flag already exists in the binary on `origin/main`.
- **Acceptance:** the rollout of a change like `f114fdd9f` shows no CrashLoopBackOff pod at any point, and the guard names the offending flag.
