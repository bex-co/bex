# REST `PUT` and `DELETE` of a variable a Blueprint dropped open a deploy, although Render's REST env writes deploy nothing

Why: Render documents that its env-var REST writes are saved and not deployed ("Changes will not be deployed automatically. Instead you must call the deploy API", api-docs.render.com update-env-vars-for-service, cited in `lego/backend/internal/secrets/staged.go`), and a client that sets a retained variable on bex gets a rollout it did not ask for.

Found 2026-11-17 while fixing w21/103 (a probe test, not a production observation).

- **What happens:** `SetEnvVar`, `DeleteEnvVar` and `SetEnvVars` first move a retained literal into the store (`adoptRetained`, `lego/backend/internal/secrets/retained.go`) in a write of its own. The write removes the literal from `spec.Env`, which is a release-identity input, so it rolls a release and opens a deploy row, whether or not the REST adapter marked the context staged (`WithStagedWrite`). A probe on a control-plane service with a deploy recorder showed one `config_change` row for each of the three verbs. The environment patch (`PatchEnvironment`) no longer does this: since w21/103 it holds the removal for the next deploy under save-only (`rollout.WithSaveOnly`) and opens no deploy.
- **Not a lost value:** the release a staged adoption rolls keeps the variable, because a new release consumes the pending Secret (`runtimeEnvSecret`), and a variable's value is the one the verb stored.
- **Fix to choose:** hold the removal for a staged write with `rollout.WithSaveOnly` inside `adoptRetained` (the narrowest), or move the literal in the verb's own write as the patch does. Either way the non-staged GraphQL and MCP verbs keep their immediate rollout.
