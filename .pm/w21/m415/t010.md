## Objective

Install the identities on the production Wasabi account and prove the shipped routes against it.

## Context

- `docs/ADR112-object-storage.md` t009 (Contract A part). The user said on 2026-11-15 that the Wasabi side is prepared and that either path (script or console) is fine. The four `BEX_OBJECT_STORAGE_*` names in `.env` were still empty when this was filed.
- The root credential is `TF_STATE_ACCESS_KEY` and `TF_STATE_SECRET_KEY` in `.env`; the production kube context follows the sibling scripts (`BEX_KUBE_CONTEXT=hetzner-prod`).
- Evidence rule: write conclusions and sha256 values into this task, never raw logs or dumps (`.pm/AGENTS.md`, #NO-ARTIFACTS-IN-GIT).
- If a step needs something that is missing (a failing root key, no cluster access, a bucket name already taken on Wasabi), park the task in `blocked/` naming exactly that.

## Steps

1. Run `scripts/object-storage-s3-credentials.sh provision`, then `verify`, then `install`; roll bex-api so it reads the Secret.
2. With `render ea objects`, put, get, list and delete 0 B, 1 B and 5 MiB objects in `oregon` and `frankfurt`; compare sha256 before and after.
3. Check a second workspace cannot read the first's key, a size of 5 GiB + 1 is refused at mint, and a `bex.read`-only token cannot mint a GET URL.
4. Probe whether Wasabi enforces the signed `Content-Length` by PUTting a larger body to a presigned URL, and record the result; if it is not enforced, state that the cap then rests on the mint rate limit and the sweep, and file the follow-up.
5. Update ADR112's Not verified list with each result.

## Progress (2026-11-15)

**Done, on the production Wasabi account** (root credential: the `TF_STATE_*` already in `.env`, mode tightened to 600 because the env loader refuses a world-readable file):

- `scripts/object-storage-s3-credentials.sh provision` created `bex-objects-oregon` (`us-west-1`) and `bex-objects-frankfurt` (`eu-central-2`) (the names were free), the IAM users `bex-object-storage` and `bex-object-storage-read` with their least-privilege policies, and wrote the two key pairs to `.env`. None of it printed a secret.
- `verify` passes: the read-write user puts, gets and lists in both regions; the read-only user gets and lists but is denied put and delete; both identities are denied `bex-tfstate`, `bex-agent-attachments`, `bex-disk-snapshots` and `bex-static`. The first run found a real bug, now fixed and guarded by a test: a HEAD of `bex-tfstate` sent to the `us-west-1` endpoint answers 400, not 403, so the denial probes now use the platform's own endpoint.
- Wasabi probes (a temporary program, deleted; nothing left behind): a presigned PUT signed for 10 bytes is stored when the body is exactly 10 bytes and refused with 403 `SignatureDoesNotMatch` for 20 bytes, for 5 bytes and for a chunked body with no length, so Wasabi enforces a signed Content-Length. A key with a `..` segment is stored literally, not normalized. Both are recorded in ADR112 § Not verified.

**Not done, and why:** every remaining step needs the production cluster or a deployed bex-api.

2. The code must be deployed and bex-api must roll to read the Secret (the push of this milestone's commit starts the deploy; the Secret is what turns the routes on).
3. Then, against the production API: `render ea objects` (`bex ea objects`) round trips of 0 B, 1 B and 5 MiB in `oregon` and `frankfurt` compared by sha256; a second workspace's key is unreachable; a size of 5 GiB + 1 is refused at the mint; a `bex.read`-only token cannot mint a GET URL; flip the four `ea objects` rows in `docs/cli-compatibility-checklist.md` and the ADR018 row from `[~]`/◐ to `[x]`/✅.

**To unblock:** give this worker read access to the production cluster (the `~/.ssh/id_bex` key for `scripts/fetch-app-kubeconfig.sh`), or run `BEX_KUBE_CONTEXT=<prod> scripts/object-storage-s3-credentials.sh install` yourself (the four values are already in `.env`). Until the Secret exists the routes answer their named 404 and nothing is stored.
