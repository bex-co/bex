## Objective

Install the identities on the production Wasabi account and prove the shipped routes against it.

## Context

- `docs/ADR112-object-storage.md` t009 (Contract A part). The user said on 2026-11-15 that the Wasabi side is prepared and that either path (script or console) is fine. The four `BEX_OBJECT_STORAGE_*` names in `.env` were still empty when this was filed.
- The root credential is `TF_STATE_ACCESS_KEY` and `TF_STATE_SECRET_KEY` in `.env`; the production kube context follows the sibling scripts (`BEX_KUBE_CONTEXT=hetzner-prod`).
- Evidence rule: write conclusions and sha256 values into this task, never raw logs or dumps (`.pm/AGENTS.md`, #NO-ARTIFACTS-IN-GIT).
- If a step needs something that is missing (a failing root key, no cluster access, a bucket name already taken on Wasabi), park the task in `blocked/` naming exactly that.

## Steps

1. Run `scripts/object-storage-s3-credentials.sh provision`, then `verify`, then `install`; roll bex-api so it reads the Secret.
2. With `render ea objects`, put, get, list and delete 0 B, 1 B and 5 MiB objects in `oregon` and `frankfurt`; compare sha256 before and after.
3. Check a second workspace cannot read the first's key, a size of 5 GiB + 1 is refused at mint, and a `bex.read`-only token cannot mint a GET URL.
4. Probe whether Wasabi enforces the signed `Content-Length` by PUTting a larger body to a presigned URL, and record the result; if it is not enforced, state that the cap then rests on the mint rate limit and the sweep, and file the follow-up.
5. Update ADR112's Not verified list with each result.
