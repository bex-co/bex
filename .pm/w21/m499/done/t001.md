## Objective

Run the user's `aws` against bex with the endpoint and an ephemeral key already set and the user's own AWS configuration kept out of it.

## Context

- ADR112 D3 (The command: `bex s3`). `lego/cli` imports no other module; the launcher already runs other tools (`lego/cli/internal/agent/ssh.go`, `lego/cli/internal/code/launch.go`, `lego/cli/internal/desktop/desktop.go`) and passes `ea objects` through to the pinned Render CLI.
- `bex s3 <args>` runs `aws s3 <args>`, `bex s3api <args>` runs `aws s3api <args>`, with `--endpoint-url https://objects.<base domain>` on the command line (the `AWS_ENDPOINT_URL_S3` variable needs a recent CLI and an older one would send the request to AWS), `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` of an ephemeral key minted through the REST route of m498/t003 for the signed-in person in the current workspace (twelve hours; cached in the CLI's state directory with mode 0600; replaced when under one hour remains), `AWS_REGION=oregon` (`--region` overrides), and `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` pointed at files bex owns (the config carries `s3 = addressing_style = path`). The child never sees `AWS_PROFILE` or `AWS_SESSION_TOKEN`.
- A command that outlives its key fails with a 403 the CLI does not retry; a long transfer needs a persistent key. A URL from `bex s3 presign` dies with its ephemeral key whatever `--expires-in` says; the docs say so.
- A missing `aws` prints how to install it and points at `bex s3 env`.

## Steps

1. Add the commands and the environment builder with the isolation rules.
2. Add the key mint and cache.
3. Test the environment the child sees (no profile, no token, the bex-owned config, the endpoint flag) with a fake `aws` that prints it.

## Files

- lego/cli/ (new internal package for the S3 launcher)
- lego/cli/main.go

## Acceptance criteria

- [x] The fake `aws` sees exactly the documented environment and arguments; the user's `~/.aws` is untouched.
- [x] An expired cached key is replaced; a missing `aws` gives the install hint.

## Out of scope

- `env`, `keys`, `public`, `info` (next task) and a native S3 client (ADR112 D10).

## Result

Done 2026-11-19. `lego/cli/internal/s3` (`s3.go`, `launch.go`, `session.go`, `api.go`) adds `bex s3` and `bex s3api`, registered in `main.go`: `bex s3 <args>` runs `aws s3 <args>` and `bex s3api <args>` runs `aws s3api <args>`, replacing the process (`execAWS`, the one `syscall.Exec`), with `--endpoint-url` **last** on the command line so a person's own `--endpoint-url` can never aim bex's key at another host (the CLI takes the last one). The environment is the person's own minus every `AWS_` variable not in a short keep-list of behavior settings (`AWS_PAGER`, `AWS_CA_BUNDLE`, retries, checksum modes), so no profile, session token, role, container or web-identity source, endpoint or region of theirs reaches the child, plus bex's `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, `AWS_REGION` and `AWS_DEFAULT_REGION` (`oregon`; an older botocore reads only the second), and `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` naming files under the CLI's state directory (`~/.bex/state/s3/`; the config carries `s3 =` `addressing_style = path`, the credentials file is empty, the key travels in the environment only). The key is minted through `POST /v1/object-storage/{ownerId}/access-keys` (read-write, 43,200 s, named `bex s3 on <hostname>`), cached in `key-<hash of control plane and workspace>.json` with mode 0600 in a 0700 directory, reused while more than an hour is left and replaced under it (a damaged file, another workspace or control plane, and an expired key all read as no key). A missing `aws` answers with how to install it and points at `bex s3 env`, before any key is minted. **Deviations from the task text:** the endpoint is `https://objects.onbex.co` for the production control plane and `BEX_S3_ENDPOINT` for any other (the API host `api.bex.co` and the hosting domain `onbex.co` are unrelated, so it cannot be derived; an `http://` endpoint is accepted for localhost only); `bex s3` with no argument or only `-h` prints bex's help and `bex s3 ls --help` is the AWS CLI's. **Not verified live:** whether the CLI's device login carries `bex.write` and the mint class (ADR112 § Not verified); `internal/s3/s3_test.go` and `s3_contract_test.go` run against a fake `aws` and a fake bex-api, and each launch-order and isolation behavior was mutation-checked.
