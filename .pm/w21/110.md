# 110 — A PUT that stores nothing new (the same variable, the same set, the same secret file) still patches the App, and over GraphQL and MCP rolls the service and opens a deploy

Why: a write that changes nothing should change nothing, as w21/109 made a `DELETE` of a name that is not there; a service that carries a saved change or a new deploy row after a write that stored the same bytes is the same class of defect, on every service.

- **Source:** w21/109, 2026-11-17 (checking the other verbs for the shape "project before knowing there is a change"; probed with the w21/109 rig, a control-plane service with a deploy recorder and a moving clock, on a service whose store already holds `KEEP=1` and `keep.txt`).
- **Facts:** `SetEnvVar` (`lego/backend/internal/secrets/service.go`), `SetEnvVars` and `SetSecretFile` (`files.go`) read the store through `updateMapCAS`, whose mutate callback returns false when the map would not change (`return false // no change`), and then call `materializeEnvEditing` / `materializeFiles` anyway: the `mapWrite.changed` the helper returns is never read. Result for a write of the stored value (no store write, one App patch each):
  - REST (staged): `PUT …/env-vars/KEEP` with `{"value":"1"}`, a bulk `PUT` of the same set and `PUT …/secret-files/keep.txt` of the same content each patch the App and stamp `app.bex.co/saved-config-revision`; no deploy row.
  - GraphQL `setEnvVar`/`setEnvVars`/`setSecretFile` and the MCP tools: each patches the App, bumps `restartedAt` and opens a `config_change` deploy row, rolling the workload for a write that stored nothing.
    `PatchEnvironment` (the dashboard's save) already does this right: an unchanged effective environment writes no App, rolls nothing and records no event (`batch.go`, w4/m122), so the single-variable verbs diverge from the save the dashboard makes.
- **Verify Render first** (the repo's parity rule): `PUT /services/{serviceId}/env-vars/{envVarKey}` and `PUT …/env-vars` are documented as saving without deploying ("Changes will not be deployed automatically", [update env vars](https://api-docs.render.com/reference/update-env-vars-for-service)), so the REST half is only the `saved-config-revision` notification (check whether it shows a pending change when the saved bytes equal the serving release's; if the status comparison finds none, it is harmless noise and the REST half can be dropped from the fix). Whether a GraphQL/MCP write of the same value should redeploy is a bex surface: the dashboard's Environment form offers no Save while nothing is edited, so the parity-sufficient choice is that an unchanged write is accepted (200, the same view) and changes nothing. File a stricter variant (refusing it) separately if wanted.
- **Fix:** in `SetEnvVar`, `SetEnvVars` and `SetSecretFile`, when the write changed no map and moved no retained literal (`!envWrite.changed && len(moved) == 0`), return the view without `materializeEnvEditing` / `materializeFiles`. Keep the w21/106 and w21/108 behaviors: a retained literal's move still rides the verb's own write and patch.

## Done when

- [ ] A `PUT` of the stored value (one variable, the whole set, one secret file) answers as before (200 with the same view) and, on REST, GraphQL and MCP, makes no App patch, opens no deploy row and leaves no saved-config annotation, on a plain service and on one with a retained variable (where moving the literal is still a change); a write that does change the map is unchanged (one store write, one App patch).
- [ ] A production check on a throwaway service in `bex-canary`: before the fix a GraphQL `setEnvVar` of the stored value opens one deploy row, after it none.
