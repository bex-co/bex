# 072 — Dashboard hardening notes from the round-25 audit: redirect validation, same-origin, content type, CSP, error headers, the device page, the consent token and a localhost return URL

Why: none is exploitable today (the audit found no injection point and no tenant string reaching them), but each is a gap a later change could turn into one.

- **Source:** w21/m394 round 25 audit, hardening (Dashboard), 2026-11-14. Policy note, not a vulnerability: `dashboard/src/common/server-fn/hydra-consent.ts` and `hydra-device.ts` implement a human consent screen and device bridge beyond `.pm/DO_NOT_DO.md`'s "at most a headless consent acceptor"; that is a decision for the owner.
- **Size:** about 2h; split it if one item grows.

## Items

- `safeNext` (`dashboard/src/common/lib/safe-next.ts`) and `dashboard/public/push-sw.js` accept `//host` after dot-segment collapse; the router neutralises it today.
- `isSameOrigin` (`dashboard/src/common/server-fn/same-origin.ts`) accepts a client-sent `X-Forwarded-Host`.
- The JSON endpoints (`api.sessions`, `api.connected-agents`) do not require `Content-Type: application/json`.
- CSP (`dashboard/server/security-headers.ts`): `script-src 'unsafe-inline'`, `connect-src https: wss:`, no `base-uri` or `form-action`.
- Non-2xx responses lose the route-rule headers (h3 `prepareResponse`).
- The device confirm page shows no client name, scopes, IP or time (`hydra-device.ts`); the consent CSRF token has no server secret (`hydra-consent.ts`).
- `http://localhost:5173` sits in production `allowed_return_urls` (the Kratos config under `deploy/gitops/`).

## Steps

1. One test per item that fails first, then the smallest fix; keep the Render-parity and no-OAuth2-dashboard rules in `.pm/DO_NOT_DO.md`.

## Acceptance

- Each item is fixed with a test or recorded as accepted in an ADR, and `cd dashboard && yarn lint && yarn test` pass.
