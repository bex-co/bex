# 125 — Moving a Postgres cluster onto the bex operand can leave it refusing every new connection: CloudNativePG reloads `local_preload_libraries = pgextwlist` into the old image before the pod rolls

Why: on 2026-11-24 three of the seven managed clusters refused every new connection for 12 to 16 minutes until their pods were deleted by hand (w21/m584 t005). The rollback that ADR092 D4 records, followed by a re-adoption, would race the same way on every cluster.

**Found by** w21/m584 t005, when pin `f46c44d9ddb1` adopted the gated bex operand. Full record: [ADR092 § D4](../../docs/ADR092-postgres-extension-supply.md#d4--rollout-one-rolling-restart-approved) (Rollout record).

- The bex operator rolled out at 00:00:58Z, and one `Cluster` update per database set both the new `imageName` and `pgExtensionParameters` (`lego/operator/internal/controller/database_operand.go`).
- `twenty-postgres` (`bex`, PG16), `qa-20261117-m453-hobby` (`tian-personal`, PG18) and `qa-m586-existing-pg16` (`bex-canary`, (disposable)) stayed on `ghcr.io/cloudnative-pg/postgresql:16@sha256:e38d10bb…` / `:18@sha256:d7a81cb5…`, with readiness answering 500.
- From 00:01:01Z their postgres log and the CloudNativePG operator log (`Cannot extract Pod status`) both read `FATAL: could not access file "$libdir/plugins/pgextwlist": No such file or directory (SQLSTATE 58P01)`.
- `local_preload_libraries` takes effect at the next connection without a restart. So CloudNativePG's reload made the instance still on the upstream image, which has no pgextwlist, refuse every new backend, the instance manager's own status connection included. The operator then never rolled the pod.
- The four clusters that rolled by themselves had their rollout started first: the operator logged `Pod rollout required` for each between 00:00:58Z and 00:01:04Z, while the three stuck ones logged `Cannot extract Pod status` first. It is a race.
- `kubectl delete pod <cluster>-1` recreated each pod on its PVC with the bex digest, in 46 s to about 3.5 min.

**Done when:**

- The operator adds `local_preload_libraries` (and anything else a running upstream instance cannot load at connection time) only to a `Cluster` whose instances already run a bex operand image. For example, the image change goes in one update and the preload in a later one, once the pods report the new image. A cluster moving onto the bex operand never has a reload that its running image cannot serve.
- A test drives a cluster from an upstream image to a bex operand and fails if any `Cluster` spec carries `local_preload_libraries = pgextwlist` while an instance still runs the upstream image. Revert the fix and watch the test fail.
- ADR092 D4's rollback paragraph says a re-adoption after the rollback needs no manual pod deletion.
