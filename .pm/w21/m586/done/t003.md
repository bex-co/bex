## Objective

New databases are created without `vector`; existing ones keep it and are never reconciled into dropping it.

## Context

- `lego/operator/internal/controller/database_extensions.go:85` builds the `<db>-app` CloudNativePG Database child with `extensions: [{name: vector, ensure: present}]` and `databaseReclaimPolicy: retain`; `reasonInitializingExtensions` (`database_extensions.go:56`) and `database_controller.go:1819` keep a never-served database `creating` until it applies.
- A database on an upstream image (a major whose digest is not adopted) still needs the preinstall, because it has no allowlist.
- Verify in an envtest (or on a kind cluster with CloudNativePG 1.30.1) what deleting the child, or removing the extension entry, does to an installed extension: only an `ensure: absent` drops it.

## Steps

1. Decide by observed CloudNativePG behavior how an existing database stops being managed for `vector` without a drop (keep the child without the extension entry, or delete the child under `retain`), and implement it.
2. New databases on a bex operand image: no vector entry and no extension wait. Databases on an upstream image: unchanged.
3. Keep `ExtensionsReady` meaningful or remove it where nothing remains to apply; adjust the status mapping.

## Result (2026-11-23)

- **Decision, from CloudNativePG 1.30.1's own source** (`internal/management/controller/database_controller.go`, `database_objects.go`, `finalizers.go` at `v1.30.1`): the instance manager reconciles only the extensions a Database lists, dropping one only for `ensure: absent`, and deleting a Database runs `evaluateDropDatabase`, which returns without SQL unless `databaseReclaimPolicy` is `delete`. So the operator **deletes** an existing database's `<db>-app` child (it is `retain`) and never writes `ensure: absent`; keeping a child without the entry would have managed nothing. w8/m84's real-CNPG run had already kept the rows of a `vector` table through a child deletion.
- `reconcileApplicationDatabase` (`database_extensions.go`) reads the allowlist the live Cluster spec carries (`allowlistAdmits`, `spec.postgresql.parameters["extwlist.extensions"]`): when it lists `vector`, the child is deleted and `ExtensionsReady` removed; otherwise (an upstream image: the adoption's rollback, or an unversioned cluster keeping an older projection) the w8/m84 child and the w4/m223 first-Ready wait are unchanged. `firstReadyHeldForExtensions` treats a missing condition as nothing to wait for.
- Tests: `TestNewDatabaseOnABexOperandGetsVectorOnDemand` (no child, no condition, first `Ready` on the first healthy pass, default and custom identity and the reserved name), `TestExistingDatabaseReleasesItsVectorChildWithoutDroppingIt` (served on an upstream image with the child applied, then a bex operand: the child is deleted, no write ever carries `ensure: absent`, the database stays provisioned over two passes), `TestAllowlistAdmits`; the upstream-path tests now pin an empty `bexOperandImages`, and the envtest replica and convergence specs no longer mark a child that no longer exists. The opt-in real-CNPG tests follow the new contract (`TestApplicationDatabaseExtensionsOnCNPG` runs Render's `CREATE EXTENSION vector;` and the drop on a bex operand; `TestApplicationDatabaseVectorOnCNPG` covers the upstream path and checks `vector`, the rows and the HNSW answer after the child is deleted); they were not run: this machine's container VM cannot reach `ghcr.io`, so no CloudNativePG cluster could pull its images. t004 checks the same on production.
- `make test` and `make lint` (all four modules) pass in `lego/operator`.
