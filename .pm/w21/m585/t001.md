## Objective

ADR092 lists every untrusted extension on Render's list with the majors it is admitted on and why it is safe to admit.

## Context

- Render's table ([postgresql-extensions](https://render.com/docs/postgresql-extensions)): `old_snapshot` and `pg_surgery` are "PostgreSQL 14 or later"; `pg_repack` "PostgreSQL 16 or later". PostgreSQL 17 removed `adminpack` and `old_snapshot`, so they exist on 13–16 and 14–16.
- w8/276's evidence table names the 22 refused on 18 and a sample on 16.
- The review facts in the milestone README (egress, `dblink`'s password rule, `file_fdw` and `CREATEROLE`).
- Default grants: most inspection modules revoke their functions from `PUBLIC` in their install scripts. Under pgextwlist those scripts run as the bootstrap superuser, so the revocations hold for the owner.

## Steps

1. Add a D1 table row group (or a D5 section) with each extension, its majors, and its disposition: admitted with default grants.
2. For each, note what the owner can call after `CREATE EXTENSION` (read from the extension's SQL script), and flag any module whose default leaves the owner a path beyond its own objects.
3. Write down `dblink`'s and `file_fdw`'s review and the `CREATEROLE` reopen condition.
4. If any module needs an after-create grant script, say so before w21/m584 t004 publishes.
