# The Postgres and Key Value detail pages' Overview / Metrics / Logs tabs are plain buttons that show the selected tab only by a CSS border class, so assistive technology cannot tell which view is active

Why: a screen-reader user on a database or Key Value page hears "Overview, button / Logs, button" and cannot tell whether Logs is the view they are on, while the webhook detail page next door marks its current tab.

**Severity:** minor (accessibility, WCAG 4.1.2 Name, Role, Value and 1.3.1; nothing is lost for sighted users). **Estimate:** 25m (one attribute or a switch to `Link`, two routes, tests). **Source:** live `/qa-find-bugs` pass 23, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (read-only; existing database `blockeden-forum-db` and Key Value `beancount-forum-redis`)

1. Open `/databases/dpg-d9rs3ee0ccis738kc7c0?tab=logs`. In `nav[aria-label="Database details"]` there are two `<button>` elements. Their `role`, `aria-current`, `aria-selected`, `aria-pressed` and `data-state` are all `null`. The active one (Logs) differs from the other only by class: `border-b-2 px-3 py-2 text-sm border-foreground text-foreground` against `border-transparent text-muted-foreground`.
2. Open `/keyvalue/red-d9p49kdrtmes73c34ovg?tab=metrics`. `nav[aria-label="Key Value detail navigation"]` has three `<button>` elements (Overview, Metrics, Logs) with the same nulls and the same class-only difference.
3. `main.ariaSnapshot()` on the database page lists `navigation "Database details": button "Overview", button "Logs"` with no state marker.
4. Control in the same app: the webhook detail tabs are `Link`s with `activeProps` (`dashboard/src/routes/webhook.$webhookId.tsx:136-141`), and TanStack Router's `Link` exposes `aria-current="page"` on an active link (seen live in pass 16 on the webhook header's status `Link`: `<a aria-current="page" class="active" …>`). The service tabs are sidebar links with `aria-current="page"` ([w4/m249](../w4/done/m249/README.md) Definition of done (c)). The webhook tab links themselves were not re-read this pass, because no webhook exists on the account.

**Evidence:** the attribute dump and the accessibility snapshot above are the durable probes; nothing was created.

## Root cause

- `dashboard/src/routes/databases.$databaseId.tsx:189-218`: two `<button type="button">` inside `<nav aria-label={t("databases.detailNavLabel")}>`. The state is `cn("border-b-2 px-3 py-2 text-sm", tab !== "logs" ? "border-foreground text-foreground" : "border-transparent text-muted-foreground")`, a class only. Each button navigates with `navigate({ to: ".", search: … })`.
- `dashboard/src/routes/keyvalue.$keyValueId.tsx:141-184`: the same pattern for three buttons (`keyvalue.overviewTab`, `metricsTab`, `logsTab`).

## Fix (target behavior)

The active tab is exposed to assistive technology. Any one of: `aria-current="page"` on the active button (smallest change); `Link`s with `activeProps`, as the webhook detail does; or the shared shadcn `Tabs` (`role="tablist"`, `role="tab"`, `aria-selected`). The visible styling, the `?tab=` URLs and the keyboard behavior do not change. UI only.
