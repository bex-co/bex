# 112 — `bex_s3gw_requests_total` counts a copy as `PutObject` and a part copy as `UploadPart`

Why: the Billing and metering board and the S3 alerts triage by `operation`, and an S3 copy (the call `aws s3 cp`, `mv` and bucket-to-bucket `sync` make for every object) shows up as a put.

- **Source:** w21/m498 t019, 2026-11-19, found on production: ten successful `CopyObject` calls and a refused cross-region copy appeared as `operation="PutObject"` (a 501 `NotImplemented` counted as `PutObject` 501, which no put of the walk could have made); the series list has no `CopyObject` and no `UploadPartCopy`.
- **Cause:** `lego/backend/internal/s3gw/gateway.go` records `rq.route.op` (`PutObject` for `PUT /<bucket>/<key>`, `UploadPart` for `PUT …?partNumber&uploadId`) and only the audit verb is switched for a request that carries `X-Amz-Copy-Source` (the `rt.op == "PutObject" && X-Amz-Copy-Source` and `rt.op == "UploadPart"` cases of `dispatch`).
- **End state:** a copy is recorded as `CopyObject` and a part copy as `UploadPartCopy`, in `bex_s3gw_requests_total`, the request-duration series if it has the label, the panel queries and `docs/runbooks/` text that name the operation; a test in `s3gw/metrics_test.go` drives a copy and a part copy through the handler and reads the label, and the board's "S3 requests by code" panel still renders (`scripts/gitops-validate.sh`, the rule tests). Keep the label set closed (a copy of a refused request is still labelled by its header, not by anything the client chooses).
