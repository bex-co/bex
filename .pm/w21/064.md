# A successful deploy still reads `live` 24–31 s after its new instance first serves, past w5/m369's 10 s bound: the watch m369 added closes a failed build in seconds but not this path on production

Why: w5/m369's Definition of done bullet 2 says a good deploy reads `live` within 10 s of its instance turning Ready (it was up to ~30 s); on the production pin that carries m369's watch the gap is 24.1 s and 30.7 s, so CI jobs polling a deploy, webhooks and people watching still wait about half a minute after the new instance is serving.

**Severity:** minor (latency only; the deploy and its verdict are correct). **Estimate:** ~90m (read the watch's metrics and trace which side is slow ~40m, fix ~30m, a success-path test ~20m); promote to a milestone if the slow side is the operator. **Kind:** residual of [w5/m369](../blocked/m369/README.md) bullet 2, whose t008 production replay is still open; this note gives that replay the measurement and a negative result. **Source:** live `/qa-find-bugs` pass 270, 2026-11-13 10:22–11:05 UTC, production `https://dashboard.bex.co` and `https://api.bex.co`, workspace `bex`, deploy pin `96925d2f8` ("pin platform images to 5de3d5bcce8e", 2026-11-13T09:41:40Z; the pin carries m369's `f076e96e7` and `6b185606d`, checked with `git merge-base --is-ancestor`), filed to w21 per user direction. **Status:** inbox.

## Reproduction (own Free Node web service `qa-20261113-r270-web`, `srv-dbrea08k58is73aunrk0`, `autoDeploy: "no"`, deleted at the end of the visit)

Fixture: `render-examples/express-hello-world` with `buildCommand: echo ok` and a `startCommand` that is an inline Node server answering `host=<os.hostname()>` (a new pod answers with its own name; `process.pid` is 13 in every container and cannot tell instances apart). The service was deployed once and read `live`; then:

1. A shell poller (`GET https://qa-20261113-r270-web.onbex.co/` every 0.5 s, logging each change of status code and body) ran beside a browser poller (`GET /v1/services/{id}/deploys?limit=1` every 0.5 s, logging each change of `status`).
2. `POST /v1/services/{id}/deploys` with `{}`; the times below are the pollers' own.

| run | `maxShutdownDelaySeconds` | `update_in_progress` | new pod's first response | REST reads `live` | first response → `live` |
| --- | --- | --- | --- | --- | --- |
| A | 30 (default) | 10:48:45.6 | 10:48:55.2 | 10:49:19.3 | **24.1 s** |
| B | 5 (set by `PATCH` `serviceDetails.maxShutdownDelaySeconds`, read back as 5) | 10:53:16.2 | 10:53:37.9 | 10:54:08.7 | **30.7 s** |

A third, weaker sample (the predecessor was crash-looping and answered 503, so the first 200 is the new instance; the URL was polled once a second): `update_in_progress` 10:30:59, first 200 about 10:31:31, `live` 10:31:45.7, about 14 s. Earlier healthy rollouts of the same service read `update_in_progress` to `live` in 33 s, 43 s, 46 s, 33 s.

**Control that passes (bullet 1).** `buildCommand: echo before-fail && sleep 8 && echo exiting-now && exit 1`: the build log's `error: build command … exited with code 1` is stamped 10:24:25.333, the events feed has `build_ended` at 10:24:28 and `deploy_ended` at 10:24:30, `finishedAt` is 10:24:30.740 and the first REST read of `build_failed` is 10:24:31.592, 6.3 s after the log line (round 250 measured about 46 s). The webhook half of bullet 1 was not exercised.

## Root cause (partly traced; the deciding measurement was not taken)

- **By design `live` should follow Ready by seconds.** The operator records `status.activeRevision` as soon as every pod of the new revision is Ready, naming the rollout `RolloutSettling` (`lego/operator/internal/controller/app_controller.go:3806-3820`, w4/405, w4/m320), and bex-api closes the row `live` on that status (`lego/backend/internal/store/reconciler.go:1787-1803`: `PhaseDeploying` with `ReasonRolloutSettling` and `releaseIsActive`, or `PhaseRunning` with `releaseIsActive`). m369's `AppStatusWatch` (`store/app_status_watch.go`, `f076e96e7`) is to kick the projector when a lifecycle fingerprint that includes the active revision changes, spaced `max(1 s, 3 × the last pass)` plus up to 250 ms of jitter.
- **Ruled out by experiment:** the old instance's drain. Run B lowered `maxShutdownDelaySeconds` from 30 to 5 and the gap did not shrink (24.1 s to 30.7 s).
- **Candidates, none checked:** (a) the watch's kick does not fire or is coalesced into a pass already running, so the row waits for the 30 s resync, which fits a gap that is a little under or over 30 s whatever the shutdown delay; `bex_controlplane_reconcile_kicks_total{source=watch}` and `bex_controlplane_app_status_watch_failures_total` on obs.bex.co (ADR088) would say, and were not read; (b) the operator stamps `activeRevision` about 25 s after the pod is Ready (its requeue, `currentRevisionFullyReady`, or the Deployment status it waits on). The m369 note's test list has a failed-deploy case (`TestStatusWatchClosesAFailedDeployWithoutWaitingForTheResync`, with a no-watch control) but no success-path case, so a watch that works for failures and not for this transition would pass its tests.

## Fix (target behavior)

A deploy's row reads `live` within 10 s of its new instance first serving, at the default shutdown delay and at 5 s, for every redeploy of a Free web service with a healthy predecessor.

1. Read the two watch metrics around a redeploy and decide between (a) and (b); the answer goes in this note's Done record.
2. Fix the slow side. REST, GraphQL, MCP, webhooks, events and the dashboard read the same deploy row, so one change moves all of them.
3. Add a test that closes a settling rollout through the watch without the resync, with a no-watch control, beside the failed-deploy one.

## Blast radius

Every deploy's `live` verdict: the REST and MCP `toRenderDeploy` projection, GraphQL, `deploy_ended` events, workspace webhooks, push and email, and the dashboard's 3 s deploy poll all read the row this pass writes (m369 t005). Not counted by grep this run.

## Adjacent classes

A failed build already reads Failed in 6.3 s (control above). A rollout that fails (`update_failed`) was not timed. Image and static deploys were not timed.

## Unverified (not probed this run)

The webhook receiving `deploy_ended` on time; image-service deploys (bullet 4's `startedAt`); static sites; paid plans and two-instance services; the pod's Ready time itself (first response through the edge is the proxy, so the real gap is at least as long as the figures above); obs.bex.co metrics.

## Render

Render marks a deploy Live once the new instance is healthy and traffic has moved to it. Its lag from the first request the new instance serves to Live was not captured; m369's 10 s bound is the board's own target.
