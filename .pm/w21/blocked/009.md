# Check the Deploy-to-bex link survives sign-up and the payment gate for a new account

Why: the whole point of the button is a first-time visitor, and the only path verified so far is a logged-in or already-registered user (w8/163 live check, and the 307 above); a new account must also pass sign-up and, on hosted bex, the payment-readiness gate before it can create anything.

- Reproduce as a brand-new visitor: open `https://dashboard.bex.co/deploy?repo=https://github.com/bex-co/beancount-io/tree/bex-deploy&path=bex.yaml` logged out, sign up (and sign in with GitHub), bind a card if asked, and note where the browser lands. Pass means the Blueprint wizard opens with repo, branch and path still filled; fail means the query is dropped at sign-up, at email verification, or after the card step.
- Check `next` handling on `/auth/sign-up` and the OAuth return, not only `/auth/login`; `blueprints.new.tsx` keeps the query through `requireAuth()` login (QA sweep 1280) but sign-up is a separate route.
- Check the wizard with a 15-variable `sync:false` form (the beancount.io Blueprint prompts for 15): layout, scroll, and that nothing in the URL or router state carries the values.
- Also record what the preview says on a clean workspace: the beancount.io Blueprint previews valid with a monthly estimate of about 32.97 USD (4 Starter services, 1 Postgres, 1 Key Value, a 10 GB disk) and a plan with no errors.
- If the link is lost at any step, file it as a bug with the step; do not fix inside this note.

## Partial result and block (2026-11-08, /loopx w21)

**Verified without an account (read-only).**

- Logged out, `GET https://dashboard.bex.co/deploy?repo=https://github.com/bex-co/beancount-io/tree/bex-deploy&path=bex.yaml` answers `307` to `/blueprints/new?repo=https%3A%2F%2Fgithub.com%2Fbex-co%2Fbeancount-io&branch=bex-deploy&path=bex.yaml`, which answers `307` to `/auth/login?next=%2Fblueprints%2Fnew%3Frepo%3D…%26branch%3Dbex-deploy%26path%3Dbex.yaml`. The query survives the first two hops and is carried in `next`.
- From the code: `dashboard/src/routes/auth.sign-up.tsx` accepts the same guarded `next` as login, and `dashboard/src/features/auth/lib/auth-next.ts` relays it across the sign-up → verification → login hops in `sessionStorage` (the middle hop is a Kratos-built full-page redirect that cannot carry a query).

**Hypothesis to confirm (not a verified bug).** The relay is per tab. A new visitor who opens the verification link from their mail client lands in a different tab or browser, where `sessionStorage` is empty, so `takeAuthNext()` returns nothing and they land on `/` instead of the Blueprint wizard. This matches the note's "fail means the query is dropped … at email verification". It needs a real sign-up to confirm, and, if it holds, the fix is to carry `next` in the Kratos flow itself (the return-to URL on the registration flow) instead of tab storage; file that as its own bug with the step, as this note says.

**Gate.** The remaining steps need a brand-new identity: an inbox that can receive the verification email, a GitHub account for the OAuth path, and a card for the payment-readiness step on hosted bex. The QA user already exists and cannot stand in for a first-time visitor.

**Needed from the user.** A disposable mailbox address the worker may use for sign-up (or the user running the five steps and reporting where the browser lands), a GitHub account allowed for the OAuth path, and a test card or confirmation that the payment gate may be skipped for this check.
