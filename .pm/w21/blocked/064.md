# A successful deploy still reads `live` 24–31 s after its new instance first serves, past w5/m369's 10 s bound: the watch m369 added closes a failed build in seconds but not this path on production

Why: w5/m369's Definition of done bullet 2 says a good deploy reads `live` within 10 s of its instance turning Ready (it was up to ~30 s); on the production pin that carries m369's watch the gap is 24.1 s and 30.7 s, so CI jobs polling a deploy, webhooks and people watching still wait about half a minute after the new instance is serving.

**Severity:** minor (latency only; the deploy and its verdict are correct). **Estimate:** ~90m (read the watch's metrics and trace which side is slow ~40m, fix ~30m, a success-path test ~20m); promote to a milestone if the slow side is the operator. **Kind:** residual of [w5/m369](../../w5/blocked/m369/README.md) bullet 2, whose t008 production replay is still open; this note gives that replay the measurement and a negative result. **Source:** live `/qa-find-bugs` pass 270, 2026-11-13 10:22–11:05 UTC, production `https://dashboard.bex.co` and `https://api.bex.co`, workspace `bex`, deploy pin `96925d2f8` ("pin platform images to 5de3d5bcce8e", 2026-11-13T09:41:40Z; the pin carries m369's `f076e96e7` and `6b185606d`, checked with `git merge-base --is-ancestor`), filed to w21 per user direction. **Status:** blocked (see the 2026-11-13 Investigation section).

## Root cause (partly traced; the deciding measurement was not taken)

- **By design `live` should follow Ready by seconds.** The operator records `status.activeRevision` as soon as every pod of the new revision is Ready, naming the rollout `RolloutSettling` (`lego/operator/internal/controller/app_controller.go:3806-3820`, w4/405, w4/m320), and bex-api closes the row `live` on that status (`lego/backend/internal/store/reconciler.go:1787-1803`: `PhaseDeploying` with `ReasonRolloutSettling` and `releaseIsActive`, or `PhaseRunning` with `releaseIsActive`). m369's `AppStatusWatch` (`store/app_status_watch.go`, `f076e96e7`) is to kick the projector when a lifecycle fingerprint that includes the active revision changes, spaced `max(1 s, 3 × the last pass)` plus up to 250 ms of jitter.
- **Ruled out by experiment:** the old instance's drain. Run B lowered `maxShutdownDelaySeconds` from 30 to 5 and the gap did not shrink (24.1 s to 30.7 s).
- **Candidates, none checked:** (a) the watch's kick does not fire or is coalesced into a pass already running, so the row waits for the 30 s resync, which fits a gap that is a little under or over 30 s whatever the shutdown delay; `bex_controlplane_reconcile_kicks_total{source=watch}` and `bex_controlplane_app_status_watch_failures_total` on obs.bex.co (ADR088) would say, and were not read; (b) the operator stamps `activeRevision` about 25 s after the pod is Ready (its requeue, `currentRevisionFullyReady`, or the Deployment status it waits on). The m369 note's test list has a failed-deploy case (`TestStatusWatchClosesAFailedDeployWithoutWaitingForTheResync`, with a no-watch control) but no success-path case, so a watch that works for failures and not for this transition would pass its tests.

## Fix (target behavior)

A deploy's row reads `live` within 10 s of its new instance first serving, at the default shutdown delay and at 5 s, for every redeploy of a Free web service with a healthy predecessor.

1. Read the two watch metrics around a redeploy and decide between (a) and (b); the answer goes in this note's Done record.
2. Fix the slow side. REST, GraphQL, MCP, webhooks, events and the dashboard read the same deploy row, so one change moves all of them.
3. Add a test that closes a settling rollout through the watch without the resync, with a no-watch control, beside the failed-deploy one.

## Blast radius

Every deploy's `live` verdict: the REST and MCP `toRenderDeploy` projection, GraphQL, `deploy_ended` events, workspace webhooks, push and email, and the dashboard's 3 s deploy poll all read the row this pass writes (m369 t005). Not counted by grep this run.

## Investigation 2026-11-13 (loopx w21): the slow side is the operator, not bex-api — BLOCKED on an operator reading

**Verdict: blocked.** The note's own question (which side is slow) is answered by two production probes; what the operator does during the lag is not visible from outside, and the one reading that shows it (obs.bex.co, ADR088 ops gate) needs a person the gate admits. The one implementable step, the success-path test, is shipped.

**Probes** (production, QA account, workspace `bex-canary`, 18:10–18:27 UTC; both fixtures deleted, DELETE 204 then GET 404; QA session revoked). An external HTTP poll every 0.5 s marked each new pod's first answer; in the page, REST `GET /v1/services/{id}/deploys?limit=1` every 1 s and GraphQL `service(id) { phase }` every 1.5 s (`phase` is `AppView.Phase`, the live App CR `status.phase`, `lego/backend/internal/apps/service.go:1121`) marked the row and the CR. A first attempt polled both at 2.5 requests/s each, drew `AUTH_OVERLOADED` answers and was discarded; keep to 1 request/s per endpoint.

| run | new pod's first answer | CR `phase` Running | deploy row `live` | first answer → `live` |
| --- | --- | --- | --- | --- |
| git-built Node, redeploy (`srv-dbrl5gdd9ioc73ds194g`, pod `…8ngkv`) | 18:16:58.137 | 18:17:18.319 | 18:17:18.320 | **20.2 s** |
| `traefik/whoami:v1.10.3` image, `PORT=8080`, redeploy (`srv-dbrl925gh3vs73b14j20`, pod `…xfght`) | 18:19:56.508 | 18:20:20.008 | 18:20:19.039 | **22.5 s** |
| git-built, first deploy (no predecessor; the first answer may come through the activator) | 18:14:20.223 | 18:14:53.668 | `finishedAt` 18:14:54.056 | 33.8 s |

What it shows:

1. **bex-api follows the CR within about a second.** The row and the CR phase flipped at the same poll instant in both redeploys (at most 1 s apart, inside the pollers' resolution). Candidate (a) is not the cause on this transition: the watch's kick fires, is not held for 3 × a long pass, and the pass projects the row at once. The pass is not the slow side either.
2. **The registry work in the operator's settle path is not the cause.** The image service has no repository image of its own, so `protectServingImage` and `refreshStoredImages` return before any registry call (`live_tag.go:48`, `storedImagesTimeout` 20 s), and it is as slow (22.5 s) as the git-built one.
3. **The row never read `live` before the CR phase read Running**, so the operator's early settling stamp (`status.activeRevision` while `Ready=False/RolloutSettling`, `app_controller.go:3806-3822`) did not reach the CR sooner than the settled status. Nothing in the rollout predicates (`deploymentRolloutReady`, `currentRevisionFullyReady`, `deploymentPodsReady`) waits on a clock, `minReadySeconds` is 0 for these services, and the first deploy, with no old pod to drain, was slower (33.8 s), so the old pod's drain (already ruled out by run B) is not it.
4. So about 20–34 s sit between the new pod answering and the operator writing the status. The suspects are the operator's App work queue (production runs `BEX_APP_RECONCILE_WORKERS=2`, `lego/operator/config/manager/manager.yaml:181`; [w5/m370](../../w5/blocked/m370/README.md) measures it, and [012](012.md) round 181 and [w4/603](../../w4/603.md) saw the same operator lag of a minute or more) or a fixed step inside the reconcile. The 14–34 s spread of all samples so far (14, 20.2, 22.5, 24.1, 24.1, 30.7, 33.8) fits a queue wait better than a constant.

Assumption, not measured: the pod's first answer through the edge is at or after its Ready time (an Endpoints address is published only for a Ready pod).

**Gate (what unblocks it).** The operator's reconcile timeline is not reachable from this session: obs.bex.co refuses the QA session at "Reauthenticate" (the QA password is never typed by an agent), and there is no cluster read (the gate of [012](012.md)). Either reading decides it:
