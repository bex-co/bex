# 095 — Wasabi may count the hourly sweep's listing bytes against the egress ratio

Why: a page of 1,000 keys is about 215 KB, so a workspace at the object cap lists 215 MB per region per pass, about 155 GB a month at one pass an hour, against about 67 GB of free egress on the whole shared Wasabi account, and I could not find whether Wasabi counts list responses as egress.

- **Source:** w21/088, 2026-11-15. One page of 1,000 keys measured from a pod in the production cluster to `bex-objects-oregon` with the platform credential: 215,226 bytes of XML, 1.26 to 1.28 s. The cap is `MaxWorkspaceObjects` = 1,000,000 per workspace per region ([ADR112 D8](../../../docs/ADR112-object-storage.md)), and the free egress figure is D4's measurement of 2026-11-16.
- **Arithmetic:** 1,000,000 objects / 1,000 per page = 1,000 pages x 215 KB = 215 MB per region per pass; x 24 passes x 30 days = about 155 GB a month for one workspace at the cap in one region. Ten such workspaces would be ten times that. Small workspaces are not the problem: a workspace with under 1,000 objects lists in one 274-byte answer.
- **Unknown (answered 2026-11-16 in Progress below: it counts, by Wasabi's documentation; the account's own counter is the last reading):** whether Wasabi's "egress" for the fair-use ratio includes the response bodies of LIST requests (ADR112 D4 reads the fair-use rule as monthly egress at or below active storage). Neither Wasabi's pricing FAQ nor its API pages that I read says.

So 2026-11-16 holds an excess of about 42 to 44 MB and no trace of the 100.47 MB of listing responses (counted at response size they would put the day at 150 MB or more), and the excess is in `StorageReadBytes`, not in the metadata difference. But it has two readings that both fit: 5 of the probe's 6 GETs (41.9 MB), or the m417 walk of the same day, whose 20 MiB object was read from Wasabi twice (41.9 MB), in which case the probe was not counted at all. And a bigger fact: the 300 MiB put and get of the m416 walk (2026-11-15 22:01 to 22:08 UTC, through the platform's presigned URLs, 314,572,800 bytes each way) left no trace: 2026-11-15 reads `DownloadBytes` 8,353,689 and the next day 51,127,922. **2. Check that the counter counted at all, with `-get`.** The repeat read an 8 MiB object 3 times in `-get`: exactly 25,165,824 bytes (the first probe's 6 reads, 50,331,648 bytes, read 0 per bucket on 2026-11-16). If `-get` reads that (give or take its HTTP headers), the per-bucket counter is working and the others can be read. If it reads 0 again, the per-bucket counter is void for these requests whatever credential (the first probe ran with a root-level key), and the account's record is the only reading left: `DownloadBytes` of 2026-11-17 minus the median 6.9 MB, with 25.2 MB of it the GET. If the account's record shows neither the GET (a total near 7 MB) the Stats API did not register the probe at all, it cannot answer whether a LIST counts, and that is the finding (state it in D8, keep the gap, and do not repeat it: the next source is Wasabi's support or a month of the sweep's real traffic against the account's invoice). Its blind spot is already one data point (the 300 MiB put and get of the m416 walk through presigned URLs left no trace in the account's records of 2026-11-15 and 2026-11-16), so even a clean zero for the root credential's listings does not measure the sweep's IAM credential.

**3. What the bytes mean.** The repeat sent, from the root credential, 800 full-page lists of `-list` (199,430,400 bytes of response), 1,000 one-key lists of `-small` (634,000 bytes), 3 GETs of 8 MiB (25,165,824 bytes) and about 0.5 MB of sanity listings: 200.6 MB of listing responses and 25.2 MB of object. Read the account's `DownloadBytes` of 2026-11-17 against the median 6.9 MB of an ordinary day (range 5.8 to 11.3 MB): about 32 MB (6.9 + 25.2) means listings count for nothing in the Stats API; about 233 MB or more (6.9 + 25.2 + 200.6) means a listing counts at its response size and the ADR's arithmetic is exact; in between, the ratio is (`DownloadBytes` - 6.9 MB - the GET's part) / 200.6 MB, with the GET's part read from `-get` if its record is not void and from `StorageReadBytes` - 3.9 MB if it is. If the GET's part cannot be told from the total, take the `StorageReadBytes` excess over its median 3.9 MB as the GET's part and the metadata difference (`DownloadBytes` - `StorageReadBytes`, median 3.0 MB; 4.3 MB on 2026-11-16) as the listings' part. What follows for the code, on the safe side: Wasabi's own text says a listing counts, so a reading of about zero (even on a clean day) does not by itself relax `SweepHourlyObjects` or `MinGap`, which cost freshness only and are cheap insurance, because the Stats API is shown above not to hold all egress; write the zero and the reason in D8 and keep the gap. A ratio clearly below 1 (a clean `-get` and a partial count of the listings) may lower `SweepKeyBytes` and the budget, with tests, never raise the listing rate on one reading. A count at the response size leaves the code as it is.

**5. Delete the five probe buckets** (a bucket must be empty first; a multi-object delete empties it; the `-list` bucket holds 1,000 zero-byte objects). This one is tested on a throwaway bucket (3 objects, then gone) and needs only `boto3` in a venv outside the repo (`python3 -m venv <dir> && <dir>/bin/pip install boto3`); `AK` and `SK` are the root credential as above:

```bash
AK="$(grep '^TF_STATE_ACCESS_KEY=' .env | cut -d= -f2-)" SK="$(grep '^TF_STATE_SECRET_KEY=' .env | cut -d= -f2-)" <dir>/bin/python - bex-w21-095-probe-list bex-w21-095-probe-small bex-w21-095-probe-get bex-w21-095-probe-logged bex-w21-095-probe-logs <<'EOF'
import os, sys, boto3
from botocore.config import Config
s3 = boto3.client("s3", region_name="us-west-1", endpoint_url="https://s3.us-west-1.wasabisys.com",
    aws_access_key_id=os.environ["AK"], aws_secret_access_key=os.environ["SK"],
    config=Config(request_checksum_calculation="when_required", response_checksum_validation="when_required"))
for name in sys.argv[1:]:
    gone = 0
    for page in s3.get_paginator("list_objects_v2").paginate(Bucket=name):
        keys = [{"Key": o["Key"]} for o in page.get("Contents", [])]
        if keys:
            r = s3.delete_objects(Bucket=name, Delete={"Objects": keys, "Quiet": True})
            assert not r.get("Errors"), r["Errors"]
            gone += len(keys)
    s3.delete_bucket(Bucket=name)
    print(name, "deleted", gone, "objects and the bucket")
EOF
```
