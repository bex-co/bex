# 095 — Wasabi may count the hourly sweep's listing bytes against the egress ratio

Why: a page of 1,000 keys is about 215 KB, so a workspace at the object cap lists 215 MB per region per pass, about 155 GB a month at one pass an hour, against about 67 GB of free egress on the whole shared Wasabi account, and I could not find whether Wasabi counts list responses as egress.

- **Source:** w21/088, 2026-11-15. One page of 1,000 keys measured from a pod in the production cluster to `bex-objects-oregon` with the platform credential: 215,226 bytes of XML, 1.26 to 1.28 s. The cap is `MaxWorkspaceObjects` = 1,000,000 per workspace per region ([ADR112 D8](../../../docs/ADR112-object-storage.md)), and the free egress figure is D4's measurement of 2026-11-16.
- **Arithmetic:** 1,000,000 objects / 1,000 per page = 1,000 pages x 215 KB = 215 MB per region per pass; x 24 passes x 30 days = about 155 GB a month for one workspace at the cap in one region. Ten such workspaces would be ten times that. Small workspaces are not the problem: a workspace with under 1,000 objects lists in one 274-byte answer.
- **Unknown (answered 2026-11-16 in Progress below: it counts, by Wasabi's documentation; the account's own counter is the last reading):** whether Wasabi's "egress" for the fair-use ratio includes the response bodies of LIST requests (ADR112 D4 reads the fair-use rule as monthly egress at or below active storage). Neither Wasabi's pricing FAQ nor its API pages that I read says.

## Steps

2. **DONE 2026-11-16, on production** (Progress and Production readback below). 3. **WAITING until 2026-11-17 00:40 UTC** (Waiting below). Read the counter, write the reading into ADR112 D8, delete the five probe buckets and close.

## Waiting (2026-11-16): read the counter on or after 2026-11-17 00:40 UTC

**Why it waits.** The one reading that settles how many bytes Wasabi counts for a listing is its own per-bucket counter, and that counter is a record per bucket per UTC day, created the day after: the records of 2026-11-15 were created between 00:06 and 00:10 UTC on 2026-11-16, and the test's day, 2026-11-16 (the probe ran at 16:34 to 16:50 UTC), is readable from **2026-11-17 00:40 UTC**. Nothing can produce it faster, and nothing needs doing before: no one has to watch. It clears by itself on the time. `/loopx w21` on or after it dispatches this item; the worker starts with `/pm unblock` and the steps below.

**The clock.** The five probe buckets (`bex-w21-095-probe-list`, `-small`, `-get`, `-logged` and its log target `-logs`, all in `us-west-1`) have had no request since 16:50 UTC on 2026-11-16, so the 2026-11-16 record holds the probe and nothing else. Do not list, read or write one of them before 2026-11-17 00:00 UTC (a call lands in that day's record). Reading the stats API and listing the account's buckets touch no probe bucket.

### What is left: read the counter, then close

**1. Read the per-bucket usage of 2026-11-16 UTC** with the root credential in `.env` (`TF_STATE_ACCESS_KEY`, `TF_STATE_SECRET_KEY`; never print them). `to` is exclusive, so a single day is `from=<day>&to=<next day>`. If no probe bucket is in the answer yet (`RecordCount` too small), try again later in the day; records appear at about 00:06 to 00:35 UTC:

```bash

curl -sS -H "Authorization: ${AK}:${SK}" "https://stats.wasabisys.com/v1/standalone/utilizations/bucket?from=2026-11-16&to=2026-11-17&pageSize=100" \
  | python3 -I -c 'import json,sys; [print(r["Bucket"], r["StartTime"][:10], "DownloadBytes", r["DownloadBytes"], "NumAPICalls", r["NumAPICalls"]) for r in json.load(sys.stdin)["Records"] if "probe" in r["Bucket"]]'
unset AK SK
```

The record also has `StorageReadBytes`, `NumGETCalls` and `NumLISTCalls`, but the last two read 0 on every record seen (the `bex-tfstate` bucket had 275 API calls and 586,839 download bytes on 2026-11-15 with GET 0 and LIST 0), so read `DownloadBytes` and `NumAPICalls`. The same call without the filter lists every bucket of the account; the account's own record is `GET https://stats.wasabisys.com/v1/standalone/utilizations?from=2026-11-16&to=2026-11-17` (a day of about 8 MB of downloads on a normal day, but 2026-11-16 also holds the m417 production walks, so it cannot tell 100 MB of listings apart).

**2. Check that the counter counted at all, with `-get`.** The probe read an 8 MiB object 6 times in `-get`: exactly 50,331,648 bytes. If `-get` reads that (give or take its HTTP headers), the counter is working and the others can be read. **If `-get` reads 0, the reading is void, not a "listings count for nothing":** on 2026-11-15 the per-bucket records of `bex-objects-oregon` read `DownloadBytes` 0, `UploadBytes` 0 and `NumAPICalls` 0 although that bucket took the walks' uploads and deletes that day (904,520 live bytes and 1,393,455,616 deleted bytes), and the per-bucket `DownloadBytes` of the whole account (587,481) were a fraction of the account's own (8,353,689). So the per-bucket counter may count only some of the traffic (a guess: requests of the root credential, which is what `bex-tfstate` sees, and not an IAM user's). Which key pair the probe used is not recorded (its test read `PROBE_AK` and `PROBE_SK`), so `-get` is the check. If it reads 0, repeat the probe with the root credential on a day without a walk (400 full-page lists of `-list`, 6 GETs of `-get`'s `big.bin`, 1,000 `max-keys=1` lists of `-small`, sized as in step 3), and read both the probe buckets' records and the account's record of that day, whose baseline is about 8 MB of downloads.

**3. What the bytes mean.** `-list`: 403 full pages were read, 100,470,318 bytes of response. `-small`: 1,000 one-key lists, 652,000 bytes. `-get`: 50,331,648 bytes. If `DownloadBytes` of `-list` is about 100 MB, a listing counts at its response size and the ADR's arithmetic is exact; if it is a small fraction, a listing counts for less than its size (write the ratio down, and `SweepKeyBytes` and the budget can be lowered); if it is about zero (and `-get` read), Wasabi's utilization does not count a listing and the text above is the whole of it (state that in D8 and decide, with the numbers, whether to relax `SweepHourlyObjects`, since the scaling then costs freshness for nothing).

**5. Delete the five probe buckets** (a bucket must be empty first; a multi-object delete empties it; the `-list` bucket holds 1,000 zero-byte objects). This one is tested on a throwaway bucket (3 objects, then gone) and needs only `boto3` in a venv outside the repo (`python3 -m venv <dir> && <dir>/bin/pip install boto3`); `AK` and `SK` are the root credential as above:

```bash
AK="$(grep '^TF_STATE_ACCESS_KEY=' .env | cut -d= -f2-)" SK="$(grep '^TF_STATE_SECRET_KEY=' .env | cut -d= -f2-)" <dir>/bin/python - bex-w21-095-probe-list bex-w21-095-probe-small bex-w21-095-probe-get bex-w21-095-probe-logged bex-w21-095-probe-logs <<'EOF'
import os, sys, boto3
from botocore.config import Config
s3 = boto3.client("s3", region_name="us-west-1", endpoint_url="https://s3.us-west-1.wasabisys.com",
    aws_access_key_id=os.environ["AK"], aws_secret_access_key=os.environ["SK"],
    config=Config(request_checksum_calculation="when_required", response_checksum_validation="when_required"))
for name in sys.argv[1:]:
    gone = 0
    for page in s3.get_paginator("list_objects_v2").paginate(Bucket=name):
        keys = [{"Key": o["Key"]} for o in page.get("Contents", [])]
        if keys:
            r = s3.delete_objects(Bucket=name, Delete={"Objects": keys, "Quiet": True})
            assert not r.get("Errors"), r["Errors"]
            gone += len(keys)
    s3.delete_bucket(Bucket=name)
    print(name, "deleted", gone, "objects and the bucket")
EOF
```

Then list the account's buckets (`GET https://s3.us-west-1.wasabisys.com/` signed with the root credential) and confirm none named `bex-w21-095-probe-*` is left. Write the deletion, with its date, in the ADR line of step 4.
