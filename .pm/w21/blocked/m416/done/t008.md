## Objective

Fill `object_storage_usage` so quotas, `bucket info` and the meters read real numbers.

## Context

## Result

Done by a sub-agent of this run, reviewed here. `objectstorage/sweeper.go` runs hourly under `PGStore.RunExclusive` (the lock the billing sweeps use; the attachments worker claims rows with SKIP LOCKED, which a prefix listing cannot) with a 45-minute minimum gap, so replicas do not list twice. It sweeps the workspaces the registry knows (a bucket or usage row, live or retired), lists `<tea-id>/` per region, attributes bytes and objects to a bucket by the second path segment and upserts `object_storage_usage`. Objects under an id with no row are recorded under the reserved `orphan:<tea>:<region>` usage id (counted toward the quota, deleted only by the workspace purge). A region that fails keeps its old rows and does not stop the other; a listing stops at 2,000,000 objects and records a lower bound. Wired in `cmd/api/main.go` with the control-plane store and the Wasabi credential. Tests with the fake S3 and Postgres: two buckets in one workspace get separate rows, an empty prefix, one failing region, the min gap, the orphan marker; mutation-checked. Known limits, left as follow-ups: the pass is sequential per workspace and region (a listing of 1,000,000 objects is about a thousand pages, roughly 3 to 5 minutes, and the pass has a 50-minute budget), so a few dozen workspaces at the cap would not all finish in an hour; the list is ordered by workspace id, so the head is re-listed first (the minimum gap evens this out); usage is written one statement per bucket. Bounded parallelism and a stale-first order are the fix when a deployment has that many large workspaces.
