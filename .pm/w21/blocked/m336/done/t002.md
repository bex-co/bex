## Objective

Make the billing worker's pass survive one failing row or stage: `RunOnce` runs `drainLifecycle`, `drainNotifications` and `purgeEvents` independently and joins their errors, and a store error on one row's completion or failure record is logged and skipped instead of aborting the pass.

## Context

- `RunOnce` (`lego/backend/internal/billing/worker.go:87-103`) returns on the first stage error, so a `drainLifecycle` error skips `drainNotifications` and `purgeEvents`, and a `drainNotifications` error skips `purgeEvents`.
- In `drainLifecycle` (`:108-140`) an `Enforce` or `Recover` error is already recorded on the row with backoff (`FailBillingLifecycleWork`, `continue`); the abort comes from the bare `return err` when `FailBillingLifecycleWork` (`:131`) or `CompleteBillingLifecycleWork` (`:136`) itself fails. `drainNotifications` has the same shape (`:150`, `:158`, `:163`).
- The push worker already joins its three later stages (`errors.Join(sendErr, w.checkReceipts(ctx), w.sweep(ctx))`, `lego/backend/internal/notifications/push_worker.go:229-231`); the poll loop logs a returned error and retries on the next tick (`lego/backend/internal/core/poll.go:75-93`).
- `ClaimDueBillingLifecycle` leases one row per call, so after a skipped row the loop can claim the next one; a skipped row's lease expires and it is claimed again later, with `attempt_count` bumped (visible, unlike today's silent failure).

## Steps

1. `RunOnce`: call the three stages in order, collect their errors with `errors.Join`, and return the joined error after all three ran. A failing context still stops early.
2. `drainLifecycle` and `drainNotifications`: on a failed `Complete`/`Fail` store call, remember the error (`errors.Join` into a local), `continue` to the next claimed row, and return the joined error at the end of the batch. Do not retry the same row inside the pass.
3. Tests in `lego/backend/internal/billing/worker_test.go` with a fake store: (a) a lifecycle row whose `Complete` errors does not stop a second row from completing, nor the notification drain or the purge; (b) a notification whose `Complete` errors does not stop the purge; (c) the joined error still reaches the caller.
