# 069 — The shared disk-snapshot age private key and the full-bucket S3 pair are readable by the bex-api Kubernetes token, which the setup runbook says they are not

Why: `docs/runbooks/disk-snapshot-setup.md:13` says the age key stays out of bex-api's reach, yet `bex-tenant-api` grants `secrets` get/list in every hosting namespace and `scripts/disk-snapshot-secret.sh` seeds the key into `default`, `bex-system` and every `tea-*` namespace, so one stolen bex-api token reads every tenant's snapshot decryption key and the bucket credentials and can keep them off-cluster.

- **Source:** w21/m394 round 25, finding R25-14 (hardening; ADR110 § Residuals), 2026-11-14. The token can already read tenant Secrets and rewrite any App, so the new property is off-cluster persistence.
- **Size:** about 2h. The runbook correction alone is minutes and should land first.

## Steps

1. Correct the runbook text to say what the RBAC and the seeding script do today.
2. Mint the age key per restore Job with an ownerReference to that Job, instead of one shared key in every namespace; keep the public key where backups need it.
3. Move the canonical copy of the key and the S3 pair to a namespace bex-api's role cannot read, and mount them into the Jobs from there.
4. Extend `scripts/disk-snapshot-secret.test.sh` to fail when a seeded namespace is readable by `bex-tenant-api`.

## Files

- docs/runbooks/disk-snapshot-setup.md
- scripts/disk-snapshot-secret.sh, disk-snapshot-secret.test.sh
- deploy/gitops/base/tenant-namespace-clusterroles.yaml, bex-api-namespace-rbac.yaml

## Acceptance

- bex-api's role cannot get the age private key or the S3 pair (a test over the rendered RBAC); a backup and a restore still run in `scripts/mock-cluster.sh`.

## Blocked (2026-11-14)

- **Done:** step 1. `docs/runbooks/disk-snapshot-setup.md` now says what the RBAC and the seeding script do: `bex-tenant-api` grants `secrets` get and list in each tenant namespace, and the age private key, the operator's write pair and the recipient are present in `bex-system`, the apps namespace, every `tea-*` namespace and each disk-bearing App's namespace (the operator copies them there, since a Job mounts only a Secret of its own namespace).
- **Why the rest is not about 2h.** A backup runs as a CronJob in the tenant namespace and a restore as a Job there, so the operator's write pair and the age material must sit in that namespace for as long as backups run. Minting the age key per restore Job cannot decrypt archives written to the existing recipient, and step 3's "mount them into the Jobs from there" cannot cross namespaces. Removing the exposure means the operator scheduling backup and restore Jobs itself and creating each Job's Secrets with an ownerReference to it (canonical copy in `bex-system` only), which changes ADR082 D5's pipeline, the CronJob projection in `lego/operator/internal/controller/disk_backup.go`, the restore flow and the seeding script. The acceptance also needs a backup and a restore to run on `scripts/mock-cluster.sh`, which could not be brought up on the machine this ran on (w21/079).
- **Decision needed (user):** whether R25-14 earns that redesign. It is hardening: it needs a stolen bex-api token, which already reads tenant Secrets and rewrites any App, and what it adds is that the copies outlive the token's revocation. The options are (a) the redesign above, as its own milestone; (b) accept it as a documented residual, which the runbook and ADR110 now do; or (c) a narrower change that keeps the age private key out of tenant namespaces except for the length of a restore, by having the operator copy it into the restore Job's namespace with an ownerReference and remove it afterwards, leaving the write pair as it is. Option (c) needs no CronJob change but still needs the cluster run.
- **Next action once decided:** for (a) or (c), `/pm promote w21/069` with the chosen scope.
