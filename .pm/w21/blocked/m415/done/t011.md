## Objective

Check that Contract A is consistent across the surfaces it exposes and compare it with render.com's early-access object storage; record drift as follow-up work.

## Context

- Surface: REST `/v1/objects/{ownerId}/{region}`. Render has no GraphQL, MCP or dashboard surface for objects; bex has none either (ADR112 D10).
- Reference: the pinned `render-oss/cli` `cmd/object*.go` and the `render-oss/sdk` object clients (ADR112 § Sources); there is no design document or changelog.

## Steps

1. List every field, status code and error shape the four routes return and compare with the pinned CLI and SDK clients.
2. Check the GraphQL, MCP and dashboard surfaces have nothing to keep in step; if Render adds one, file it.
3. Record each remaining difference in ADR018 and file an inbox note for anything not shipped.

## Result

Dependency changed from t010 to t009 on 2026-11-15: the parity check reads code and sources, and t010 is gated on production cluster access (see t010), so waiting on it would only delay a check that needs no production. REST is the only surface, as on Render: Render has no GraphQL, MCP or dashboard surface for objects and bex has none (ADR112 D10), nothing to keep in step. Compared with the pinned CLI (`pkg/client/storage/storage_gen.go`, `pkg/storage/repo.go`) and, read from source on 2026-11-15, the TypeScript SDK (`typescript/src/experimental/object/client.ts`) and the Python SDK (`python/render/experimental/object/client.py`): put reads `url` and `maxSizeBytes` and fails when `maxSizeBytes` differs from the local size (bex returns exactly sizeBytes), always sends Content-Length to the URL (Wasabi enforces it, see t010), and reads the ETag of that response; get reads `url` and the download's Content-Type (bex pins only Content-Disposition, never the type); delete accepts any success status (bex answers 204; the CLI accepts 200 or 204) and treats 404 as not found; list reads `items[].object.{key,sizeBytes,lastModified}`, `hasNext`, `nextCursor` and passes `limit` and `cursor` through with no cap of its own. The Python client's list reads `response.objects` with `key` and `size` through its generated ObjectApi, which was not read: it is the same generated schema as the TypeScript one, but that mapping is unverified. Render's real regions, limits, key rules and error shapes remain unpublished; ADR018's row records every bex value as unsigned (t009). No new drift found, nothing filed.
