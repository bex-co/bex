## Objective

Write the repeatable way to create the two Wasabi identities and install them, without running it against production (t010 does).

## Context

- `docs/ADR112-object-storage.md` D9: two IAM users on the platform's existing Wasabi account, scoped to `bex-objects-oregon` and `bex-objects-frankfurt`; the root credential is the existing `TF_STATE_ACCESS_KEY` and `TF_STATE_SECRET_KEY` (or `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` when set).
- Precedent to copy: `infra/wasabi/agent-attachments-s3-policy.json` (policy names the bucket literally), `scripts/agent-attachments-s3-credentials.sh` (`with_credential`, `upsert_env`, refuses any other bucket name, never prints a secret), `lego/operator/config/api/deployment.yaml:537-569` (`secretKeyRef` with `optional: true`).
- `.env.example` and `.env` already carry the four empty `BEX_OBJECT_STORAGE_*` names (added with the ADR). `docs/ADR019-infra-credentials.md:34-35` holds the neighbouring rows; `lego/backend/AGENTS.md:111` the inventory row.
- Secrets: `bex-system/bex-object-storage` (`BEX_OBJECT_STORAGE_ACCESS_KEY`, `BEX_OBJECT_STORAGE_SECRET_KEY`) and `bex-system/bex-object-storage-read` (`BEX_OBJECT_STORAGE_READ_ACCESS_KEY`, `BEX_OBJECT_STORAGE_READ_SECRET_KEY`).

## Steps

1. Write `infra/wasabi/object-storage-s3-policy.json` (get, put, delete, list on the two buckets) and `object-storage-read-s3-policy.json` (get, list on the same two).
2. Write `scripts/object-storage-s3-credentials.sh {provision,verify,install}`, idempotent: `provision` creates the two buckets in `us-west-1` and `eu-central-2` and the two users and writes the pairs to `.env`; `verify` runs a positive matrix and a denied probe for each identity on `bex-tfstate` and on one unrelated bucket; `install` creates the two Secrets.
3. Wire the two read-write variables into `lego/operator/config/api/deployment.yaml` with `optional: true`.
4. Add the ADR019 rows and the `lego/backend/AGENTS.md` inventory rows; keep `.env.example` in step.
5. Test the script the way sibling scripts are tested (stubbed `docker` and `kubectl`), and run the repository's shell checks over it.

## Acceptance criteria

- [ ] The policies name the two buckets literally and nothing else.
- [ ] `verify` fails when either identity can reach `bex-tfstate`.
- [ ] Without the Secret, bex-api starts with the store off (optional references).
- [ ] The script's own test passes and no run prints a secret.

## Out of scope

- Running `provision` or `install` against the production account (t010).

## Result

Two least-privilege policies naming the two object buckets literally, `scripts/object-storage-s3-credentials.sh {provision,verify,install}` (two identities; the root credential is the existing TF_STATE_*; each minted key is written to .env at once; `verify` proves put/get/list for both, that the read-only user cannot write or delete, and a denied probe on bex-tfstate and on the other platform buckets, skipping an absent one), an offline guard test wired into scripts.yml and the shellcheck list (mutation-checked: a PutObject in the read-only policy fails it; shellcheck v0.10.0 clean), a Go drift test tying regions.go, the policies and the script together (with the paths added to backend-test.yml; ci_test_inputs.py ok), the two read-write variables in bex-api's deployment.yaml (kustomize builds), the ADR019 row, and the backend AGENTS inventory row; `.env.example` already had the four names. `provision` and `install` were not run: they write to the production account, which is t010. The read-only Secret's variables are for objectgw (w21/m417) and are not wired into bex-api.
