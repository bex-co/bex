# Blueprint deploys sit `queued` for 20-35 minutes, sync/create answer 500/502, and a missed rollout deadline is never retried

Why: a clean deploy of a four-service Blueprint (web x3 + private service, one Postgres, one Key Value) into a second workspace could not be completed three times in a row, in ways that look like platform behavior rather than the Blueprint; the one-click path (w21/008, w21/009) depends on all three being healthy.

Observed 2026-11-08, workspace with no other builds (one unrelated idle service), `POST /v1/blueprints` from a public GitHub URL, no GitHub App:

- **Queue:** after the first builds finished, one service's deploy stayed `queued` with no `build_in_progress` for 20-35 minutes, then either started or was still waiting when I stopped. It happened to the API (twice) and to Gitea (twice). A manual `POST /services/{id}/deploys {}` did not move it. Builds in another workspace started within minutes at the same time.
- **Control plane:** `POST /blueprints/{id}/sync` answered 500 or 502 on most attempts and 200 on a later one; `POST /blueprints` answered 500 once and left a half-created service (`beancount-api`) and a Blueprint in `error` behind. Deleting a Blueprint-managed service by hand made the next sync 500.
- **Rollouts:** a service whose first rollout could not become ready (Gitea, waiting on a database schema) stayed `update_in_progress` for about 17 minutes, was marked `update_failed`, and was never retried even after the missing schema existed. The only recovery was a new deploy.
- **Deploy API:** `POST /services/{id}/deploys {}` with no commit returns a deploy with `commit: null` that replays the previous image; it does not build the branch head. `{"commitId":"<sha>","clearCache":"do_not_clear"}` builds.
- **Related, smaller:** `DELETE /services/{id}/env-vars/{key}` answers 409 `ENV_VAR_MANIFEST_MANAGED` for a variable that was removed from the manifest, and also after redeclaring it `sync: false`, so a leftover cannot be removed; `GET .../env-vars` returns 20 rows unless `limit` is passed.

Next: reproduce the queue stall with a Blueprint of that shape in a fresh workspace and read the builder's queue state for the stuck deploy; decide whether the rollout deadline should retry (Render does keep retrying a service that fails its health check). The Blueprint under test is `bex.yaml` at the root of `https://github.com/bex-co/beancount-io`.

## Triage 2026-11-08 (w21 loopx)

Checked against the code at 8b7e9630d; the evidence the note needs lives in production, which this session cannot read.

- **Gate:** every claim needs the platform's own state (the builder's queue entry for the stuck deploy, bex-api logs for the 500/502 on `POST /blueprints/{id}/sync`, the operator's events for the missed rollout). `scripts/fetch-app-kubeconfig.sh` needs `~/.ssh/id_bex`, which is absent on this machine. Release condition: the key (or a kubeconfig for the production cluster) present here; then run the `rt-fix-prod-crashes` Phase 2 sweep for the sync window and reproduce the queue stall with `bex.yaml` from `bex-co/beancount-io` in a fresh workspace.
- **`POST /services/{id}/deploys {}` replaying the previous image is not what the code does.** `deploys/service.go` (the trigger comment at line 518 onward) resolves a trigger without `commitId` to the branch head and "rebuilds from source on every trigger". A `commit: null` row with the previous image looks like a deploy that was still `queued`, i.e. a symptom of the stall, not a separate bug. Confirm with the stuck deploy's row once logs are readable.
- **`ENV_VAR_MANIFEST_MANAGED` after the key left the manifest** is derived from the App's `spec.env` literals (`secrets/service.go` `manifestEnv`). A leftover key therefore means the sync never rewrote the App; with the sync answering 500 this is probably a consequence of the first bullet, not an independent bug. `sync: false` entries have `valueFrom` set and are not owned, so redeclaring one should free the key once a sync lands.
- **Rollout never retried:** Render also marks a deploy that misses its health-check window as failed and does not retry it; a later deploy is the recovery. The note's premise needs the Render behaviour verified before it is treated as parity work (file the check as the first task when unblocked).
