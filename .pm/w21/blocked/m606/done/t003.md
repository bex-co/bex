## Objective

bex's real-CloudNativePG test proves the definition of done on bex's own Cluster projection. An owner's `pgaudit` is still in `pg_extension` after the primary pod restarts, no other database gained it, and the owner can drop it. CI runs that test, so a later CloudNativePG bump that loses the patch fails before it reaches production.

## Context

- `lego/operator/internal/controller/database_operand_test.go` `TestApplicationDatabaseExtensionsOnCNPG` and `ownerContribOnCNPG` (the owner already runs `CREATE EXTENSION pgaudit` there).
- `database_operand_cnpg_test.go`: `qualificationCNPGImage` pins the upstream operator, `verifyCNPGOperandController` requires it, and `startCNPGDatabase` creates the cluster.
- The test is opt-in (`BEX_CNPG_KUBECONFIG`, `BEX_PG_OPERAND_IMAGES`). w21/m586 t003 could not run it on the worker's machine because its container VM could not reach `ghcr.io`. A GitHub-hosted `ubuntu-24.04-arm` runner can.

## Steps

1. After `ownerContribOnCNPG`, delete the primary pod and wait for the Cluster to report healthy with a new primary pod. Then, as the owner:
   1. `SELECT count(*) FROM pg_extension WHERE extname = 'pgaudit'` is `1`.
   2. In a second database created before the restart (or `postgres`, read as the superuser through the test's existing path), it is `0`.
   3. `DROP EXTENSION pgaudit` succeeds.
2. Let the qualification controller check accept the bex build: the pinned bex digest, or upstream's for a run that proves the failure.
3. Add a CI job, in t002's workflow or its own, that:
   1. creates a kind cluster
   2. installs the pinned chart with the patched image
   3. loads the PG18 operand image
   4. runs `go test ./internal/controller -run 'TestApplicationDatabaseExtensionsOnCNPG/PG18'`
4. Run the test once against stock `1.30.1` to show it fails at step 1.1, and record that run.

## Result (2026-11-23)

- `ownerPgauditAcrossRestartOnCNPG` (`database_operand_test.go`, `4fdf3e3338`): after the owner's `pgaudit`, the superuser drops `pg_stat_statements` in the owner's database, the test deletes `pg-1`, waits for a new `pg-1` to be Ready, then for `pg_stat_statements` to come back. CloudNativePG's first pass after the start re-creates it in the same transaction in which it would drop `pgaudit`, so its return marks that pass as committed (no sleep). Then the owner's `pgaudit` count must be `1`, every other database that allows connections must have none, and the owner's `DROP EXTENSION pgaudit` must succeed. `TestApplicationDatabaseExtensionsOnCNPG` runs it at the end.
- Deviation: CI runs `TestOwnerPgauditAcrossRestartOnCNPG` (`1b34e934a9`), which shares the full test's setup (`operandQualificationCluster`) and runs Render's `CREATE EXTENSION pgaudit;` in a new database before the same step, not the whole `TestApplicationDatabaseExtensionsOnCNPG`. The full test, run in CI for the first time, never passed its existing owner export and restore phase on a real CloudNativePG (`must be owner of extension pg_stat_statements`), which it keeps red on purpose; filed as [w21/124](../../../124.md), whose end state moves CI to the full test. `BEX_CNPG_QUALIFY_TEST=TestApplicationDatabaseExtensionsOnCNPG` runs it.
- Qualification accepts the bex build (`qualificationCNPGImage`) or the release it patches (`upstreamCNPGImage`); `TestQualificationCNPGImageIsProductionsPin` holds the first to `cnpg-operator.yaml` and the second to the Dockerfile's base.
- CI: `.github/workflows/cnpg-operator-qualify.yml` and `scripts/cnpg-operator-qualify.sh` on kind (`kindest/node:v1.36.1`), production's chart archive, the pinned operator, the `bex-datastore` PriorityClass and `bexOperandImages`' PG18 operand, on `ubuntu-24.04-arm` and `ubuntu-latest`. Two first-run defects fixed: the missing PriorityClass (`1e8c899a6c`) and the export's read-only `/tmp` (`3b7c0fd657`).
