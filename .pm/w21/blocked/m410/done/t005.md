## Objective

Decide, then fix: the device confirm page shows no client name, scopes, IP or time, and the consent decision's CSRF token has no server secret.

## Result (2026-11-14)

- **Correction to this task's premise.** `.pm/DO_NOT_DO.md` forbids hand-building a Hydra login/consent *provider*; the consent screen and the device bridge are the browser half of the official Render CLI's device login (`RENDER_CLI_CLIENT_ID` in `hydra-device.ts`) and of the first-party desktop client, so they stay. Nothing to decide on whether they exist.
- **Consent CSRF token: fixed.** `consentCsrfToken` is an HMAC under `CONSENT_CSRF_SECRET` when set (the plain hash it was before when not, so a deploy without the Secret keeps working). `dashboard/deploy/deployment.yaml` reads it from the optional `dashboard-consent-csrf` Secret and `dashboard/AGENTS.md` lists the variable. Tests in `hydra-consent.test.ts` ("with CONSENT_CSRF_SECRET set": accepts the keyed token, refuses the unkeyed hash and another secret's token, hands the keyed token to the form). **Out of band:** creating the Secret (`openssl rand -hex 32`, namespace `dashboard`) is an operator step; until then the token is unkeyed.
- **Device confirm page: not changed here.** It shows only the user code. What Hydra's admin API returns for a `device_challenge` *before* the accept is not established in the code (the client id is only known from the accept's `redirect_to`), so enriching the page is filed as [w21/080](../../080.md) with that question first.
