# 098 — A subscription bex's own reclaimer cancels is treated as a payment failure: 11 cardless workspaces were put in grace, enforced and mailed

Why: the abandoned-checkout reclaimer cancels a cardless workspace's Stripe Subscription, and the dunning reducer reads the resulting `customer.subscription.deleted` as a failed payment, so a workspace that never owed anything gets a grace notice, then an enforcement and a "compute suspended" mail.

- **Source:** the w21/m336 t004 production read, 2026-11-16 ([`finding.md`](m336/finding.md)).
- **What happened.** On 2026-10-03 07:02:41 to 07:03:07 UTC the reclaimer shipped by w3/m172 cancelled and deleted 13 cardless bex Customers. For 11 workspaces the webhook `customer.subscription.deleted` arrived while the workspace still had a mapping, and `billing/lifecycle.go:147` maps every such event to `BillingOutcomeFailure` / `subscription_canceled` (`subscriptionOutcome` at `:183` does the same for a `canceled` status). Each workspace went to `grace` (7 days), then `enforcing`, then, after the w21/m336 fix, `enforced` on 2026-11-12. Their owners were mailed a grace notice (2026-10-03) and "[bex Test Mode] Workspace compute suspended for billing" (2026-11-12). None had a payment method, a paid invoice or a resource: the reclaimer only runs when Stripe confirms that.
- **Why it can come back.** `ReclaimUnboundCustomer` (`billing/reclaim.go`) still cancels subscriptions of unbound Customers every 15 minutes, and the usage emitter, the admin `provision` action and any pre-m172 mapping can still leave a cardless Subscription for it to cancel. m172 stopped Checkout from creating one, which is why only the first pass hurt.
- **Not in scope here.** The 11 existing rows are corrected by w21/m336 t004 right after this note ships and deploys (decided by the user 2026-11-16: recover all 11 to `healthy`, accept the "Billing recovered" mail). This note is only about the reducer, so a repeat cannot happen.

## Steps

1. Reproduce it on a real Postgres: record a `customer.subscription.deleted` for a workspace whose mapping has no `payment_method_bound_at` (the reclaimer's shape) and read the lifecycle: it goes to `grace` and a notice is queued.
2. Decide the narrowest rule that is true for Stripe's own cancellation after failed collection and false for bex's reclaim: for example the reclaimer stamping the Subscription it cancels (metadata) so the reducer ignores that deletion, or the reducer ignoring a deletion for a workspace that never bound a payment method. A subscription Stripe cancels after dunning for a workspace that did bind a card must still enter grace.
3. Add the regression test for both sides and make it fail on the current reducer.
