## Objective

Two causes of 500 on the Blueprint routes are on production: the sync path returns `blueprintFetchFailure`'s plain error for every fetch failure, and a sync that recreates a service whose App is still terminating returns the apiserver's `object is being deleted … already exists`. Give both the status a client can act on.

## Context

- `lego/backend/internal/apps/blueprint.go`: `blueprintFetchFailure` (393), `failSource` in `runSync` (1721), the create path's `blueprintCreateFetchError` (406: 400 or 503).
- Loki: `unavailable: Could not reach GitHub…` on 2026-11-08 10:52 to 10:54; `object is being deleted: apps.app.bex.co … already exists` 17 times 13:09 to 13:13 the same day.
- Render recreates a Blueprint resource deleted by hand on the next sync ([Blueprints](https://render.com/docs/infrastructure-as-code)).

## Steps

1. Return the classified error to the HTTP caller from `failSource` and from the other `blueprintFetchFailure` caller (1854), keeping the plain text in `blueprint_syncs.error_message`: 503 for rate-limited or unreachable, 400 for repository, path or access; auto-sync retry behavior unchanged.
2. Find where the App create hits AlreadyExists on a terminating object and make the sync wait for or retry the recreate (a bounded wait, then a 409 with a retry hint), never 500.
3. Reproduce the hand-delete then sync on the QA workspace first; tests on the real-Postgres suite for both; delete every fixture.
4. `cd lego/backend && go test ./...` with the deps up, `make lint`; ship; deploy; replay.

## Files

- `lego/backend/internal/apps/blueprint.go` and its tests, `lego/backend/internal/apps/service.go` (App create)

## Acceptance criteria

- [ ] A sync whose fetch fails answers 503 or 400 on REST, GraphQL and MCP, with the sync history still recording the failure.
- [ ] A sync after a hand-delete answers 200 or a retryable 409 on production, never 500.
- [ ] Each test fails on the code before the fix.

## Out of scope

- GitHub's own availability.
