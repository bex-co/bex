## Objective

The operator's manager container runs at its 500m CPU limit and is throttled in 92% to 99% of its CFS periods, so every reconcile takes about 2.5 s wall time for a few milliseconds of work. Raise the limit so the workers are not frozen mid-pass, make the cost of the next reading cheap (a loopback pprof endpoint), and alert on a throttled platform container so this cannot sit unseen for weeks again.

## Context

- `lego/operator/config/manager/manager.yaml`: `limits.cpu: 500m`, `memory: 128Mi` (96 Mi used), `requests.cpu: 10m`, `memory: 64Mi`; `BEX_APP_RECONCILE_WORKERS=2`.
- The node (`bex.co/pool: platform`, cx33, 4 CPUs) has 48% of its CPU requested and 86% of its memory requested, so raise limits, not requests.
- Production read in the milestone README § Findings. Go 1.26's runtime sets GOMAXPROCS from the cgroup limit.
- Existing queue alerts: `BexOperatorReconcileQueueSlow`, `BexOperatorAppReconcileSlowPasses` (`deploy/gitops/base/rules/`, promtool tests beside them).

## Steps

1. Raise the manager's CPU limit to 2 CPUs and its memory limit to 256Mi (limits only), with the reason in the manifest comment.
2. Add a `--pprof-bind-address` flag (default off, `ctrl.Options.PprofBindAddress`) and pass `127.0.0.1:6060` in the manifest: loopback only, reachable through `kubectl port-forward`, not from any pod.
3. Add a throttling alert for platform containers (`container_cpu_cfs_throttled_periods_total` over `container_cpu_cfs_periods_total` above 25% for 30 m, `bex-system`) with a promtool test, and keep the cAdvisor series it needs in `prometheus.yaml` (check it is already kept).
4. `make test`, `make lint`, `bash scripts/gitops-validate.sh`; ship, then `gh workflow run deploy.yml --ref main` and wait.
5. Re-measure after 6 h and record before and after in § Findings and in w5/m370's README.
