## Objective

The failing case of 2026-11-20 works: `bex s3 ls` on a machine with no AWS CLI, and every verb after it, on production.

## Context

- Build `bex` from the tree and run it with a PATH on which `command -v aws` finds nothing (the case that failed). Production access: `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>`; the QA user's device login for the key (`bash scripts/qa-login.sh`). Own throwaway workspace and bucket, removed after; `bex-canary`'s S3 reads are refused until 2026-12-01 (its egress budget was spent by the earlier walks): never raise the budget or touch the kill switch to get around it. Never print a key secret, a signed URL, a token or kubeconfig content.
- Walk: `ls` of the buckets, `mb` in `oregon` and `frankfurt`, 0 B, 1 B, 20 MiB and 1 GiB round trips byte-identical by sha256, `sync` up then again (zero copies) then `--delete`, `mv`, `rm --recursive`, a `presign` fetched with curl and its refusal after the key's expiry where that can be observed, a CORS and a lifecycle round trip, ten concurrent commands on an empty key cache making one key, a transfer that outlives nothing, the refusal messages for a quota and for a revoked key.
- Record what was observed, dated, as one block in ADR112 § Not verified ("bex, settled 2026-11-2x live through the native `bex s3`"), including what was not run. A defect: fix it, redeploy (`gh workflow run deploy.yml --ref main` after checking nothing is running or queued; seven old `queued` runs from October and early November do not block), and re-walk it.

## Steps

1. Run the walk and write the block; remove the throwaway workspace, bucket, objects and keys.
