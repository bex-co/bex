# Postgres Insights shows the platform's own activity as the customer's: Active processes lists 9 blank background workers above the 3 real app sessions, and Top queries is led by monitoring queries (rank 1 averages 153 s), a side effect of w4/m115's `pg_monitor` grant

Why: w4/m115's goal was "a database owner sees THEIR processes and top queries", but granting `pg_monitor` made every other role's activity visible, and the platform's own roles run constantly; the first row of the flagship diagnostic table now reports an alarming 153-second query that is not the customer's.

**Severity:** major (the page misleads on every Postgres that has a platform exporter, and pushes the customer's real sessions to the bottom). **Estimate:** 45m (two SQL filters in `insights.go`, tests; confirm the role set first). **Kind:** gap in [w4/m115](../w4/done/m115/README.md)'s guarantee. **Source:** live `/qa-find-bugs` pass 22, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Root cause

- `lego/backend/internal/postgres/insights.go:318-329` `sqlProcesses` selects all of `pg_stat_activity` (`WHERE pid <> pg_backend_pid()` only) and `ORDER BY state, duration_sec DESC NULLS LAST`. Background workers have no `state`, so the empty string sorts first, and nothing filters `backend_type`.
- `lego/backend/internal/postgres/insights.go:331-341` `sqlTopQueries` selects `FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 25` with no `userid` filter.
- Why it appeared: [ADR009 § Insights visibility](../../docs/ADR009-postgresql-management.md) (`:324-334`, w4/m115) made other roles' statements readable on purpose, by projecting the owner into `pg_monitor`, because before that every backend owned by a different role was masked (`<insufficient privilege>` rendered as "Hidden"). The platform's own roles (the CloudNativePG instance manager and the metrics exporter, role `postgres`) are among those "other roles". Before the grant their rows were masked, so they were not noise; after it they dominate.
- w4/m115's Definition of done was probed on a throwaway database with only SQL-console activity ("Processes are visible", "Top queries are visible"), and its t006 live re-probe was explicitly deferred to the next QA pass. Nobody re-ran it on a database with an application and the platform's monitoring, which is where "their processes and top queries" are drowned out.

## Fix (target behavior)

1. **Active processes** lists client backends only (`backend_type = 'client backend'`), the customer's sessions first, and leaves out the platform's own sessions; no blank "—" rows.
2. **Top queries** leaves out statements run by the platform's roles (join `pg_roles` on `pg_stat_statements.userid` and exclude the superuser and replication roles the platform uses, at least `postgres` and `streaming_replica`), keeps the owner's and any customer-created role's statements, and still ranks by `total_exec_time`. The exact role set is confirmed by reading `userid` for ranks 1 to 15; this note could not do that without running SQL on a database the QA account does not own, so it is inferred from the query text and the identical call counts.
3. The `masked` flag and password redaction stay as w4/m115 and w4/m167 left them. REST, GraphQL and MCP share both statements (`databaseProcesses`, `databaseTopQueries`, the MCP top-queries tool, `postgres/mcp.go:517`), so one change covers all three.

## Adjacent classes

- A database owner who is also running their own long query must still see it; the filter is by role, not by cost. A customer-created role's statements stay visible. A masked row (`masked: true`, a role the reader still cannot see) keeps today's "Hidden" cell and explanation.
- The platform's SQL text being visible to tenants is a smaller point (these are standard CloudNativePG queries); filtering them removes it as a side effect. Not an authorization boundary: the reader is the database owner with `pg_monitor`, as designed.
