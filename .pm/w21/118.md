# `TestBexS3RunsWithNoOtherProgramInstalled` failed its TempDir cleanup under `-race`: find what writes into HOME after the command returned

Why: it failed once with `.bex/state/analytics` not empty during cleanup (`-race`, runner `CI=true`), which is either a test that does not wait for the launcher's detached analytics sender or a real file left behind after the command exits, and a flaky test becomes a red main for whoever pushes next. The w21/115 CI-fix worker saw it and left it, since CI runs without `-race`, and no board item records it.

- **Evidence.** The test is `lego/cli/s3_contract_test.go:172`. Its environment is `s3Env` (`:104`), which calls `telemetryEnv` (`lego/cli/main_test.go:822`), which blank-sets `BEX_CLI_DISABLE_ANALYTICS` on purpose so that sending is on, against the stub API. The launcher sends through a detached sender (`analytics.IsSendSubprocess()`, `lego/cli/internal/disclosure/disclosure.go:191`; `lego/cli/internal/bridge/transport.go:33`), a process that can outlive `bex` and still touch `<HOME>/.bex/state/analytics/` while `t.TempDir` is removed. That is a hypothesis, not proven.
- **Change.** Reproduce it (`cd lego/cli && go test -race -count=20 -run TestBexS3 ./...`, with and without `CI=true`) and confirm which process writes. Then make a test that does not look at telemetry set `BEX_CLI_DISABLE_ANALYTICS=1` (this one asserts that no other program starts, not what was reported), and make a test that does look at it wait until the stub has the event and the `events` directory is empty before it returns. If the launcher itself leaves a file behind after exit, that is a product defect: fix it there and say so.
- **Where.** `lego/cli/s3_contract_test.go`, `lego/cli/main_test.go` (`telemetryEnv`), and `lego/cli/internal/disclosure` or `bridge` only if the cause is there.
- **Done when.** `go test -race -count=20` over the `TestBexS3*` tests passes 20 times in a row, under `CI=true` and without it, and the commit message names the process that wrote the file.
