# 111 — An env-group variable or secret-file PUT that stores nothing new still rolls every linked service

Why: w21/110 made a service-level `PUT` of what the service already holds change nothing; the env-group verbs are the same class of defect on another surface (a write that stored nothing rolls services), so they need the same Render check and, if Render agrees, the same fix.

- **Source:** w21/110, 2026-11-17 (found while checking the other callers of the single-item write verbs; read from the code, not yet observed on production).
- **Facts:** `SetEnvGroupVarInput`, `SetEnvGroupFile` and the bulk verbs (`lego/backend/internal/envgroups/service.go`) go through `patchEnvironmentAuthorized` with `SaveModeDeploy`. `patchContents` (`patch.go`) writes the group only when a map changed, but a save that changes nothing "goes straight to the rollout" on purpose (it is how an empty patch retries a failed rollout), so an identical `PUT` of one variable still calls `rollGroupPatch` and `rollOne` on every linked service that is not suspended or a build source, which bumps `restartedAt` and opens a deploy for each, unless `autoDeployGated` holds it back (a repo-backed service with Auto-Deploy off). Render's documented trigger is a change: "If you make changes to an environment group (including deleting it), Render kicks off a new deploy for every linked service that has autodeploys enabled" ([configure environment variables](https://render.com/docs/configure-environment-variables)).
- **Verify Render first** (the repo's parity rule): whether Render deploys linked services for a write of a value the group already holds (the dashboard's Save is disabled while nothing is edited, so the dashboard cannot make one; the API's `PUT /env-groups/{envGroupId}/env-vars/{envVarKey}` documents no effect for it). Do not infer it from the sentence above alone.
- **Fix, if Render does not redeploy:** an identical single-item write (one variable, one file or the same set) answers as before and rolls no linked service, while the explicit retry of a failed rollout (the empty patch) still rolls: the two are different requests, so the single-item verbs skip the rollout when the group's map did not change and the retry path keeps it.

## Done when

- [x] Render's behavior for an identical env-group write is recorded here with its source; a `PUT` of the saved value to a group variable, file or the whole set answers as before and, when Render does not redeploy, opens no deploy on any linked service on REST, GraphQL and MCP, while the retry of a failed rollout still rolls.

The three MCP tool descriptions say a write the group already holds rolls none. A client that retried a failed rollout by repeating its single-item `PUT` must now send the empty patch (recorded in [ADR013](../../../docs/ADR013-secrets.md) § Precedence and redeploy and [ADR018](../../../docs/ADR018-render-parity.md)'s Environment groups row).
