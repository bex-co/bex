## Objective

Serve `wrangler r2 object put --remote`, whose bytes travel in the REST call, without the 30 s server timeouts cutting a large upload.

## Context

- `docs/ADR112-object-storage.md` D3: require `Content-Length` (`10033`), refuse above 300 MiB (`100100`), extend the per-request deadlines with `http.NewResponseController` (precedent `internal/deploys/platform_rebuild.go:192`; the server's 30 s timeouts are in `cmd/api/main.go` `newHTTPServer`), run the quota gate, stream to Wasabi on a server-signed presigned PUT (no payload hash, no spooling), store `Content-Type`, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language` and `Expires` as sent, overwrite on put.
- Concurrent streams: 8 per workspace and the per-replica cap, `429` code `10058`. Traefik's `readTimeout` is 6000 s (`deploy/gitops/base/values/traefik.values.yaml:72`).
- Unverified: whether Wasabi accepts a streamed presigned PUT with a signed `Content-Length` (the production walk, t013, settles it). If it does not, fall back to a single `PutObject` with the known length and record why.

## Steps

1. Add `Client.PutStream(key, size, body, headers)` to the package and the put handler.
2. Test: no length gives `10033`; 300 MiB + 1 gives `100100`; a body slower than 30 s still completes; the ninth stream gets `429`; a quota breach gives `10042` with a message that names the cap.
3. Check wrangler's measured request shape (headers and chunking) against the handler.

## Files

- lego/backend/internal/objectstorage/client.go

## Result

`Store.PutStream` signs a presigned PUT whose only signed header is `content-length`, sends the caller's real Content-Length (`http.NoBody` for zero bytes), and passes `Content-Type`, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language` and `Expires` unsigned, stored as sent; its errors never carry the URL, whose query is a 15-minute signature (a bug found by the mutation run: net/http's error quoted it into the log). `Service.PutStream` refuses in the ADR's order before reading a byte (key, no length `10033`, 300 MiB cap `100100`, quota gate `10042` naming the cap, stream slot `10058`), then streams with nothing buffered or spooled; a body that ends early is `10013` and stores nothing, told apart from a Wasabi failure before the body was read. `extendStreamDeadlines` lifts the server's read and write deadlines for 30 minutes (`objectstorage.StreamDeadline`) through the whole middleware chain, and the same 30 minutes bounds the Wasabi call itself, so a Wasabi that stops answering cannot hold a stream slot. The fake S3 now refuses a chunked PUT against a URL that signs a length, as Wasabi does (ADR112 settled 2026-11-15), and no longer holds its lock while a body arrives. Tests: a body slower than the server's timeouts completes (removing the extension fails it), 300 MiB streams with heap growth under 64 MiB and 300 MiB + 1 is refused, the ninth concurrent stream is `10058`, a quota breach names the cap, a short body, an unreachable Wasabi is not a short body. The measured wrangler 4.162.0 request shape (Content-Length always sent, never chunked, `cf-r2-data-catalog-check: true`) is in the recorded fixture and checked by the replay test. Still unverified on production Wasabi: a body streamed from a network reader; that is t013.
