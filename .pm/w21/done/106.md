# REST `PUT` and `DELETE` of a variable a Blueprint dropped open a deploy, although Render's REST env writes deploy nothing

Why: Render documents that its env-var REST writes are saved and not deployed ("Changes will not be deployed automatically. Instead you must call the deploy API", api-docs.render.com update-env-vars-for-service, cited in `lego/backend/internal/secrets/staged.go`), and a client that sets a retained variable on bex gets a rollout it did not ask for.

Found 2026-11-17 while fixing w21/103 (a probe test, not a production observation).

- **What happens:** `SetEnvVar`, `DeleteEnvVar` and `SetEnvVars` first move a retained literal into the store (`adoptRetained`, `lego/backend/internal/secrets/retained.go`) in a write of its own. The write removes the literal from `spec.Env`, which is a release-identity input, so it rolls a release and opens a deploy row, whether or not the REST adapter marked the context staged (`WithStagedWrite`). A probe on a control-plane service with a deploy recorder showed one `config_change` row for each of the three verbs. The environment patch (`PatchEnvironment`) no longer does this: since w21/103 it holds the removal for the next deploy under save-only (`rollout.WithSaveOnly`) and opens no deploy.
- **Not a lost value:** the release a staged adoption rolls keeps the variable, because a new release consumes the pending Secret (`runtimeEnvSecret`), and a variable's value is the one the verb stored.
- **Fix to choose:** hold the removal for a staged write with `rollout.WithSaveOnly` inside `adoptRetained` (the narrowest), or move the literal in the verb's own write as the patch does. Either way the non-staged GraphQL and MCP verbs keep their immediate rollout.

## Done when

- [x] A staged (REST) `PUT` and `DELETE` of one retained variable and a bulk `PUT` that names it open no deploy, and the removal is held for the next deploy; the non-staged verbs still roll once. Each is a test on a control-plane service with a deploy recorder (the probe above is the starting point).
- [x] A production check: the REST verbs on a retained variable of a throwaway Blueprint service in `bex-canary` open no deploy row (`examples/retained-env` is the pair of manifests).

## Result

**DONE 2026-11-17** in `101544e11` (deployed by the dispatched `deploy.yml` run 44024106529, whose build and deploy jobs ran; both bex-api replicas run image digest `sha256:f249d8d74c50`, the controller digest of the pin `101544e11278`, read on both pods). The push-triggered run 44024057549 was inside the six-hour window and skipped build and deploy.

- **Choice: (a), held in `adoptRetained`, for every write, not only a staged one.** The adoption's App patch now runs under `rollout.WithSaveOnly`, so it never rolls a release itself: the verb's own write follows it and is the only rollout the caller asked for. The staged REST verbs open no deploy and the removal waits for the next one; a deploying verb rolls once and consumes the hold with its own stamp. (b), moving the literal in the verb's own write as the patch does, is not needed for parity: it saves one store write and one App patch per verb. Filed as [w21/108](../108.md) because a rejected `PUT` still moves the literal today.
- **The note's premise was incomplete: the deploying verbs opened two deploys, not one.** The probe in the note ran only the staged path. With a clock that moves, as a real one does, a GraphQL or MCP write of a retained variable rolled in the adoption (`restartedAt` bump, a deploy row) and rolled again in the verb's own write (a second row). A fixed test clock hides it, because the second bump repeats the first. Production before the fix: each REST verb opened 1 `service_updated` row, each GraphQL verb 2 (`queued` and `created`).
- **A second defect closed on the way: a re-declared name was dropped.** The adoption removed the literal with `dropSpecEnvNames`, which has no check, so a Blueprint sync that re-declared the name between the verb's read and the App patch (the locked patch re-runs on a re-read App) had the manifest's literal deleted by the verb. The adoption now removes through `dropMovedRetained`, the check the environment patch uses: it refuses with `ENV_VAR_MANIFEST_MANAGED` and the store write rolls back (`materializeEnvEditing` and `stageEnvWrite` take an edit that can refuse).
- **Value invariants.** The next deploy consumes what the verb stored: a `PUT` carries its value in the Secret the release reads, a `DELETE` of a retained variable is gone from the next release (no literal, not in the Secret), a variable the verb did not name keeps its literal. The running release keeps its literal and its references until that deploy.
- **Tests** (`lego/backend/internal/secrets/retained_verbs_rollout_test.go`, on a control-plane service with a deploy recorder and a moving clock, real-Postgres suite green in `ship-gates`): `TestAStagedWriteOfARetainedLiteralOpensNoDeploy` (REST `PUT` one, `DELETE` one, `PUT` all through the REST adapter: zero rows, no release stamp, `restartedAt` and `envFromSecret` untouched, removal held, store and Secret as written, then a deploying save takes the stored value and the removal); `TestADeployingWriteOfARetainedLiteralRollsOnce` (the three verbs through the Service, GraphQL and MCP: one `config_change` row); `TestAVerbDoesNotDropALiteralTheManifestRedeclaredMeanwhile` (six cases); `TestAFailedAdoptionOfARetainedLiteralLeavesItWhereItWas`. Mutation checks, each killed by the tests named and restored (sha256 verified): no hold (staged and deploying tests), hold only for a staged write (the deploying test: two rows), no refusal of a re-declared name (the race test), the literal left on `spec.Env` (four tests), no compensation of a failed adoption (two tests). `make lint` on all four modules: 0 issues.
- **Production** (`bex-canary`, a throwaway Blueprint from `examples/retained-env`: `render.yaml`, then pointed at `dropped.yaml` and synced; MESSAGE, EXTRA and CLICKME listed as ordinary variables; the QA user's session, never printed). Before the deploy, the REST `PUT` of MESSAGE, `DELETE` of EXTRA and bulk `PUT` each opened one deploy row and rolled the Deployment (revision 1 to 4), the GraphQL `setEnvVar`, `deleteEnvVar` and `setEnvVars` two rows each. After it: the three REST verbs opened **0 rows**; the App kept `release-generation` 1 and its `restartedAt`, `pending-source-generation` rose 2, 3, 4, and the serving Deployment stayed at revision 1 still carrying the three literals. A second run read the values in between: `PUT` MESSAGE=rest-put left the Secret holding it, `DELETE` EXTRA removed it, and the next deploy (`POST /deploys`, one `api` row) rolled the Deployment to revision 2 with MESSAGE and EXTRA gone from the literals, MESSAGE=rest-put in the Secret it consumes and the untouched retained CLICKME still a literal; a bulk `PUT` then opened 0 rows and the following deploy consumed CLICKME=rest-bulk and OTHER=2 with no dropped name left as a literal. The three GraphQL verbs opened **exactly 1 row each** (Deployment revisions 2, 3, 4, literals gone, Secret as written). Every fixture deleted (Blueprint 204, service 204 then 404, no App, Deployment or Secret left), the QA session logged out, the kubeconfig and jars deleted. Not observed: MCP on production (it needs an OAuth token; the MCP path is covered by the in-process test through the real tool registry).
