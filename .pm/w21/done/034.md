# SSH key names take neither the shared label rule nor a character count: a name with a newline and BEL is accepted, and a 41-character Chinese name that the Add SSH key form allows is refused by the server with the English "SSH key name must be 1-120 bytes"

Why: [w21/023](done/023.md) gave API key names the one label rule every other free-form name on the Settings page already uses, and the SSH key writer next to it still checks `strings.TrimSpace` plus a byte count, so Chinese users hit a limit counted in bytes while the form counts characters.

**Severity:** minor (input hygiene plus a CJK-only refusal with a unit the user cannot count; no data lost). **Estimate:** 30m (route the name through `core.TrimmedLabel`, align the dialog `maxLength`, add service tests). **Kind:** missing shared rule, plus a unit mismatch between form and server. **Source:** live `/qa-find-bugs` pass 31, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (own throwaway SSH key; every key created was deleted in the same call)

A throwaway ed25519 public key was generated locally and its private half deleted at once. The calls below are in-page GraphQL to `https://api.bex.co/graphql` with the session cookies. The final `{ sshKeys { name } }` returned the single original `tp-ms-fish`.

1. **Control characters are kept.** `createSSHKey(name: "qa-20261110-ssh\nx\u0007y", publicKey: $pub)` returns the key with the name echoed verbatim (19 code points, `echoedEqual` true). `deleteSSHKey` answers true.
2. **Length is 120, not 100.** A 120-character ASCII name (`qa-20261110-` + 108 `a`) is accepted; 121 is refused with `bad request: SSH key name must be 1-120 bytes`. The shared label rule (`core.CheckLabel`) allows at most 100 code points and no control characters.
3. **The limit is counted in UTF-8 bytes.** `qa-20261110-` + 39 `测` (51 code points, 129 bytes) and + 40 `测` (52 code points, 132 bytes) are both refused with the same "must be 1-120 bytes" message. A pure Chinese name tops out at 40 characters.
4. **The zh form promises more than the server allows.** In the zh UI (`/settings?lang=zh` → Add SSH key), 41 `测` typed into the name field is accepted (`maxLength={120}` counts UTF-16 units; 41 characters, 123 bytes) and the submit button stays enabled. Clicking 添加密钥 sends `CreateSSHKey`, answered `{"data":{"createSSHKey":null},"errors":[{"message":"bad request: SSH key name must be 1-120 bytes"}]}`. The dialog stays open and shows only a toast `SSH key name must be 1-120 bytes` (English, in the Chinese UI), with no inline error.

Nothing was created by 3 and 4.

## Root cause (code-traced)

- `lego/backend/internal/sshkeys/service.go:37` `maxKeyNameBytes = 120`, and `:120-123`: `name = strings.TrimSpace(name)`, then `if name == "" || len(name) > maxKeyNameBytes`. `len` is bytes; there is no control-character check.
- `dashboard/src/features/ssh-keys/components/ssh-keys-panel.tsx:109` `maxLength={120}` (UTF-16 code units), and `:65-66` only `name.trim().length > 0`.
- The one shared rule is `core.TrimmedLabel` / `core.CheckLabel` (`lego/backend/internal/core/errors.go:381-405`: no control characters or line separators, at most 100 code points). `grep -rln 'TrimmedLabel\|CheckLabel' lego/backend/internal` finds apikeys (after w21/023), apps ×3, core, envgroups, environments, projects, registrycreds, webhooks and workspaces; `sshkeys` is not among them.
- The sibling dialog already does it right: `dashboard/src/features/api-keys/components/create-api-key-dialog.tsx:112` `maxLength={100}`.

## Fix (target behavior)

- `Service.Create` runs the name through `core.TrimmedLabel`: empty stays the existing "name required" refusal; a control character or more than 100 code points returns the label rule's `DISPLAY_NAME_CONTROL_CHARACTER` / `DISPLAY_NAME_TOO_LONG` codes. This replaces the 120-byte cap, so a 100-character Chinese name saves.
- The dialog's `maxLength` becomes 100, like the API key dialog.
- The refusal is surfaced the way the dialog already surfaces server errors; if the "bytes" wording survives anywhere it says characters.
- All three entrypoints share `s.Create` (`sshkeys/graphql.go:54`, `rest.go:43` for REST `POST /v1/ssh-keys`, `mcp.go:53`), so one change covers REST, GraphQL and MCP.
- Existing stored names are not rewritten (no rename path exists; the list holds one key).

## Blast radius (counted by grep)

- `service_test.go` has no name-length or control-character test (its create calls at `:111,118,140` use `laptop` / `same material`). Add rejection cases (newline, BEL, 101 code points) and an acceptance case (100 Chinese characters, 300 bytes).

## Adjacent classes (traced separately)

- `apps/disks.go:346` caps disk names at 63 bytes, but that is a DNS-style identifier, not a label.
