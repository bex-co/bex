# The first dashboard save that edits a variable a Blueprint dropped is refused as stale

Why: the user did nothing wrong, and the refusal ("secret changed; refresh before saving") reads as a lost edit; the second try works.

Found 2026-11-16 while fixing w21/012 (w21/m421 t004), pinned by `TestASaveAgainstTheListedRevisionNamingARetainedLiteral` (`lego/backend/internal/secrets/retained_env_test.go`).

- **What happens:** a literal a Blueprint's manifest dropped stays on `spec.Env` and lists as an ordinary variable. A write that names it first moves it into the env store (`adoptRetainedKeys`, `lego/backend/internal/secrets/retained.go`), which advances the store revision. The dashboard's Save sends the revision it listed (`ExpectedEnvRevision`), so the save that triggers the move meets the newer revision and answers 409 `secret changed; refresh before saving`. Nothing is half-applied: the value is kept, and a save against the refreshed revision lands. REST single-key `PUT`/`DELETE` and the bulk replace have no revision to disagree with and succeed at once.
- **Fix:** do the move inside the patch's own compare-and-set write, so the listed revision is the one the patch is checked against, or have the list adopt the retained literals when a caller can write (one store write per service, once). Keep the test, changed to expect the save to land.
- **Acceptance:** a dashboard save that edits a retained variable lands on the first try, with the value and the literal's removal in one revision.

## Result

**DONE 2026-11-17** in `c48bc47fc` (deployed by the dispatched `deploy.yml` run 44003042618, whose build and deploy jobs ran; both bex-api replicas run image digest `sha256:2679208592df`, the controller digest of the pin `c48bc47fc59d`, read on both pods), with the fixtures in `63e5097c8`.

- **The note's premise, corrected.** The web dashboard's Environment editor sends a sparse patch with no `expectedEnvRevision` (`use-environment-draft-save.ts`; `docs/render-artifacts/environment-revisions.md` says so), so it never met the refusal. The callers that do check the revision they listed are the mobile app ([ADR048](../../../docs/ADR048-mobile.md)) and MCP, REST and GraphQL clients of `patchServiceEnvironment`. Their first save of a retained variable answered 409 `ENVIRONMENT_REVISION_CONFLICT` ("the service environment changed; refresh it before saving again"; the note's "secret changed" is the retry-exhausted answer of another path). Why the revision moved: the list reports the store's revision, the literal is not in the store, and `adoptRetainedKeys` wrote the store (revision n to n+1) before the patch compared the caller's n.
- **Design: the move rides the patch's own write; the list does not write.** A read that writes has hazards the patch does not (a read-only viewer cannot write, a write per list and per replica, an audit row for a list, a rollout from opening a page), so the list is untouched. In the revision-checked protocol the store takes the literal with the edit in the one compare-and-set against the listed revision, and the same locked App patch removes the literal (`finalizeEnvironmentPatch`, `dropMovedRetained`). The sparse protocol (the web editor, MCP replace-all) moves the literals inside its own read-modify-write the same way, so an edit, a delete or a rename of a retained variable is one store write and one App patch where it was two of each, and a patch that fails after the move leaves nothing moved. The single-variable verbs and the bulk replace of REST check no revision and keep adopting first.
- **Safe against concurrent writers.** A revision another writer advanced, between the list and the save or between the save's read and its write, still answers `ENVIRONMENT_REVISION_CONFLICT` and writes nothing; only the self-inflicted bump is gone. The locked App patch runs again on a re-read App, so it refuses a name a sync re-declared since the save read the App (the manifest owns it again) and the refusal rolls the store write back through the existing compensation; nothing is stored beside a manifest literal that would win at runtime, and the manifest's literal is never dropped. A failed App patch restores the store and leaves the literal.
- **Save only stays save only.** Moving a literal off `spec.Env` changes the pod template and so rolls a release. The patch's App write runs under `rollout.WithSaveOnly` for save-only, so the removal is held for the next deploy (`pending-source-generation`, no deploy row, the running pods keep the literal until the deploy); a deploying save opens one deploy. Before, the first save of a retained variable restarted the service even as save-only.
- **Tests** (`lego/backend/internal/secrets/retained_env_test.go`, real Postgres suite green): `TestASaveAgainstTheListedRevisionNamingARetainedLiteral` now expects the first save to land (one store write, revision 0 to 1, one App patch, the returned revision chains); `TestAStaleRevisionIsStillRefusedForARetainedLiteral` (changed after the list, and in the read/write gap; nothing written, the literal and its value kept, a refreshed save lands); `TestASparsePatchOfARetainedLiteralIsOneWrite` (edit, delete, rename, edit to the literal's own value); `TestASaveThatChangesNothingStillMovesTheLiteral`; `TestASaveOfARetainedLiteralRollsOnlyWhenItDeploys`; `TestARetainedLiteralTheManifestRedeclaresIsNeitherStoredNorDropped` (declared at the read, and re-declared after it); `TestAFailedSaveOfARetainedLiteralLeavesItWhereItWas`; `TestRESTWritesOfARetainedLiteralStillLand`; `TestARetainedLiteralSaveLandsFirstTryOnTheWire` (REST PATCH and GraphQL). Mutation checks, each killed by the tests named and restored: the old adopt-first order (five tests), no literal recorded in either protocol's transaction (six and four), no removal of the literal (seven), the save-only hold removed, the re-declaration check removed, the equal-map change flag removed in both protocols, the caller revision ignored. One mutation survived and was removed as dead code: copying the moved literal into the revision-checked map before the patch, which the patch overwrites.
- **Production, after the deploy** (`bex-canary`, a Blueprint from `examples/retained-env` on the public repository: sync with `MESSAGE`, `EXTRA`, `CLICKME`, `KEEPME`, then the Blueprint pointed at the manifest that drops the first three and a second sync; the QA user's session, never printed). All five variables listed with `managedBy: blueprint` before and the three dropped ones with none after, their literals still on the App. (1) A GraphQL `patchServiceEnvironment` with the revision the reveal returned, on `MESSAGE`, save-only: first try, `rolledOut: false`, the revision advanced once (the listing then returned the revision the save returned), the literal gone from `spec.env`, the others kept, `pending-source-generation` set, the Deployment still carrying `MESSAGE` and no new deploy row. (2) Another writer's `PUT` between the list and a save on `EXTRA`: the save answered `ENVIRONMENT_REVISION_CONFLICT`, `EXTRA` kept its value and its literal, the store took nothing from it. (3) The save against the refreshed revision, deploying: landed, `rolledOut: true`, the literal gone, `envFromSecret` wired. (4) One real Save only click in the dashboard's Environment editor on `CLICKME` (the sparse path): the value saved, one revision, the literal gone. Every fixture deleted (Blueprint 204, service 204 then 404, no App, Deployment or Secret left), both QA sessions logged out, the kubeconfig, the jars and the state files deleted.
