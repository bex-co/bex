# 112 — `bex_s3gw_requests_total` counts a copy as `PutObject` and a part copy as `UploadPart`

Why: the Billing and metering board and the S3 alerts triage by `operation`, and an S3 copy (the call `aws s3 cp`, `mv` and bucket-to-bucket `sync` make for every object) shows up as a put.

- **Source:** w21/m498 t019, 2026-11-19, found on production: ten successful `CopyObject` calls and a refused cross-region copy appeared as `operation="PutObject"` (a 501 `NotImplemented` counted as `PutObject` 501, which no put of the walk could have made); the series list has no `CopyObject` and no `UploadPartCopy`.
- **Cause:** `lego/backend/internal/s3gw/gateway.go` records `rq.route.op` (`PutObject` for `PUT /<bucket>/<key>`, `UploadPart` for `PUT …?partNumber&uploadId`) and only the audit verb is switched for a request that carries `X-Amz-Copy-Source` (the `rt.op == "PutObject" && X-Amz-Copy-Source` and `rt.op == "UploadPart"` cases of `dispatch`).
- **End state:** a copy is recorded as `CopyObject` and a part copy as `UploadPartCopy`, in `bex_s3gw_requests_total`, the request-duration series if it has the label, the panel queries and `docs/runbooks/` text that name the operation; a test in `s3gw/metrics_test.go` drives a copy and a part copy through the handler and reads the label, and the board's "S3 requests by code" panel still renders (`scripts/gitops-validate.sh`, the rule tests). Keep the label set closed (a copy of a refused request is still labelled by its header, not by anything the client chooses).

## Result

**DONE 2026-11-19** in `98e053468` (deployed by the dispatched `deploy.yml` run 44620029262; its pin `c8c774658` is `chore(deploy): pin platform images to 98e053468f52`, controller digest `sha256:1ec4a7c2d561`, and every pod of the operator image, `bex-s3gw`'s two included, runs it, read on each pod and Ready).

- **Choice.** `route.operation(r)` (`lego/backend/internal/s3gw/router.go`) is the one place that says what a request is: a `PutObject` route carrying `X-Amz-Copy-Source` is `CopyObject` and an `UploadPart` route carrying it is `UploadPartCopy`; every other route is its own op, whatever headers it carries. `serve` records that name, and `dispatch`'s audit-verb switch reads the same answer instead of re-testing the header, so the metric and the audit row cannot disagree. The handlers still run by the route's op (`handlers["PutObject"]` takes both), so no handler moved. The label set stays closed: it is the routes' ops plus those two, `unrouted` and `unauthenticated`, and the header's value is never copied into a label (a request refused before a route was chosen, such as `PUT /b/o?acl`, stays `unrouted`).
- **The series, the panels and the text.** `bex_s3gw_requests_total{operation,code,status}` is the only S3 series with an `operation` label (there is no request-duration histogram), and no panel, alert or runbook names an operation: the board's "S3 requests by code" panel sums by `code`, every S3 alert sums over all operations, and the one rule test that names `PutObject` is a real put. So the only prose to change was [ADR112](../../../docs/ADR112-object-storage.md) § What watches it, which now says what the label holds and that the first build labelled a copy `PutObject`. No Prometheus, rule or panel file changed, so `scripts/gitops-validate.sh` and the rule tests have nothing new to read.
