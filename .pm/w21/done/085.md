# 085 — A token revoked at Hydra is still accepted by bex-api for more than 90 seconds

Why: revocation is a security control, so how long a revoked token keeps working must be known, bounded and written down.

- **Source:** the post-deploy check of w21/m417's fixes on production, 2026-11-15. A token revoked directly at Hydra was still accepted by bex-api for more than 90 s, until `/v1/oauth/revoke` on bex-api was called enough times to reach both replicas. The cache TTL was not found. Revocation through bex-api's own `/v1/oauth/revoke` is not covered by this note.

## Steps

1. Find where bex-api caches token introspection (the OAuth middleware in `lego/backend/internal/api`) and read the TTL and the cache key.
2. Decide the bound (Render's tokens are API keys with no cache; for OAuth access tokens a short bound such as 30 s, or invalidating on `/v1/oauth/revoke` across both replicas) and write it in ADR012 as the revocation latency.
3. Implement it with a test that revokes at Hydra and asserts the token is refused within the bound.

## Done when

- [x] The revocation latency is a documented number and a test pins it.

## Result (2026-11-15)

**Found.** The cache is `oryAuth.cache` in `lego/backend/internal/api/auth.go`: one in-memory entry per bex-api replica, key the raw bearer token, value the resolved `core.Identity`, TTL `core.PositiveTTL` = 30 s (shared with the authorization caches), positives only. Revocations that pass through bex write the shared `oauth_revocations` row and need no window; a revocation made directly at Hydra waits for the entry to expire.

**The >90 s was not reproduced.** On production (Hydra v26.2.0 x2, bex-api x2) Hydra answered `active: false` within one probe round for every revoke path (RFC 7009 with the access or the refresh token, admin token delete, consent-session revoke, client delete), on both Hydra pods. Before the change each bex-api pod and `api.bex.co` refused the token 21.6 to 25.1 s after the revoke (30 s window counted from the last cache fill), for the access-token, refresh-token and consent-session paths on human device-flow tokens. No path, replica or the edge accepted it beyond 30 s, so the report in this note has no cause in the code or in Hydra that I could find. Two untested candidates for the original observation: a client that refreshed to a new token, and a revoke call that Hydra answered 200 without acting on (RFC 7009 answers 200 for a token it did not revoke).

**Decided.** Token introspection gets its own window, `introspectionTTL` = 5 s (was 30 s). render.com revokes an API key "immediately" (render.com/docs/api), so the reference is no window, but zero is not defensible: every miss is a Hydra round trip and spends the per-credential admission budget (60 a minute per replica). At 5 s a live token costs at most 12 misses a minute per replica (a fifth of the budget) and 0.2 Hydra calls a second, against a measured production average of about 0.01 introspections a second per Hydra pod. The stricter variants are filed: [090](090.md) (an operator path that writes the shared marker) and [091](../blocked/091.md) (narrow to 2 s after a week of measurement).

**Shipped** in `c132484cf`: the window, an injectable clock on the gate, `TestRevokedAtHydraIsRefusedWithinTheRevocationLatency` (five Hydra revoke calls, two replicas that share the production marker, a stepped clock; it fails at 30 s and when the cache write ignores the new constant), and `docs/ADR012-auth.md` §8d, which also corrects §8's claim that an already-issued key token stays active until its `exp`. Deployed to production the same day (`deploy.yml` run 43798430920, pin `557b6944f`).

**Measured after the deploy.** Both pods and `api.bex.co`, each warmed by one request and the token revoked at Hydra at once, polled every 0.1 s: first 401 at 3.87 to 4.85 s (three runs); the coarser probe saw it by 5.2 s. Down from 21.6 to 25.1 s. Revocation latency: **5 s at most**, written in ADR012 §8d.
