# The static-site publish directory accepts a path that can never publish (`../../../x`) and fails it at deploy as `update_failed` with "publish: rootDir/publishPath "../x" escapes the repository checkout"; a `..` that stays inside the repo publishes a directory outside the Root Directory; and neither the Settings editor nor the New Service form (Root Directory, Dockerfile Path, `PORT`, a 140000-character value) marks any of it before the server refuses

Why: a person who types `../../../x` is told "Deploy failed: publish: rootDir/publishPath "../x" escapes the repository checkout" after a deploy — an internal prefix, two wire field names and a path that is not the one they typed — and the form that could have said so at save says nothing.

**Severity:** minor (every refusal is readable or harmless; nothing is lost). **Estimate:** 50m (the escape rule at save for a repo-backed static site, the operator guard classed as a user-source failure with a plain sentence, one inline check on the publish-directory editor, the create-form rows that 045 and 047 name). **Kind:** sibling of [w21/045](045.md), [w21/047](047.md) and [w4/493](../w4/done/493.md); it records the create-form half that 045 and 047 marked Unverified, plus the publish directory that 045 also marked Unverified. **Source:** live `/qa-find-bugs` pass 56, 2026-11-11 02:4x UTC (2026-11-10 local), production `https://dashboard.bex.co`, workspace `bex`, pin `a0d5802594e9`, filed to w21 per user direction; method: a client-versus-server validation differential on the New Service form and on a static site's publish directory. **Status:** inbox.

## Reproduction

Own Free static sites `qa-20261110-sp` (`srv-dbpssjfbq3ic73c0a9s0`) and `qa-20261110-sp2`, deleted in the same visit. The New Service form never created anything.

**A. Server (REST, static site, root `examples/hello-node`).**

- `POST /v1/services` with `publishPath: "../x"` answered 201. The first deploy closed `build_failed` with `the publish directory "examples/x" does not exist in the repository at "6eadb86c…"`. The path is `rootDir` + `publishPath` normalized, so `..` stays inside the repo and names a valid sibling.
- `PATCH` with `publishPath: "../../../x"` answered 200. Deploy `dep-dbpst8thi5vc738gj1bg` (first publish, nothing live) closed `update_failed` in 14 s with `publish: rootDir/publishPath "../x" escapes the repository checkout`. The text is shown verbatim on the deploy page, in the log as `==> Deploy failed: publish: rootDir/publishPath "../x" escapes the repository checkout` and in the Events row; the header read "Service Failed".
- `PATCH` with `publishPath: "../static-site"` went live in 30 s, and `curl` answered 200 with the 1548-byte `examples/static-site/index.html`. The site published a sibling directory outside the Root Directory, although `rootDir` itself refuses `..` (`store.ValidRootDir`).

**B. Settings editor** (`/static/srv-dbpssjfbq3ic73c0a9s0/settings` → Edit publish directory): `../../../x`, `/etc` and `a\b` each leave the textbox with `aria-invalid` null and Save enabled.

**C. New Service form** (`/services/new`, Public Git URL `https://github.com/bex-co/bex`):

- Root Directory `../x`: `aria-invalid` false, Deploy Service enabled. After the click the toast reads `RootDirectory must be a relative path with no '..' components` (the wire name, as in w21/045); the form keeps every input and REST lists no new service.
- Dockerfile Path `../Dockerfile` (runtime Docker): the same, toast `DockerfilePath must be a relative path with no '..' components`.
- An environment row `PORT` = `abc`: not marked (`aria-invalid` false); the toast reads the server's `PORT must be an integer from 1 to 65535 (not 18012, 18013, 18014 or 19099, which the platform reserves)…`.
- A 140000-character `QA_BIG` value: the same; toast `…is too large: a process cannot start with a KEY=value entry over 131071 bytes; use a secret file for large payloads`.
- **Controls that do work in the same form:** an invalid environment key (`1bad key`) is marked and holds Deploy Service; secret file names `bad/name`, `..`, `a b` and a 260-character name are all marked and hold it.

## Root cause

1. **Server.**
   - `lego/backend/internal/apps/service.go:5913` `validatePublishPath` rejects only an empty value and `\r\n\x00`. Its comment says absolute paths are deliberately allowed for an image-backed static site and that the repo-backed checkout-escape guard lives in the operator, so a repo-backed save is never checked.
   - The operator guard is `lego/operator/internal/publish/publish.go:388-392` (`path.Join(RootDir, PublishPath)` equal to `..`, starting `../`, or absolute), reached from `validate(o)` (`:359`) via `publish.Ensure` (`:240`). Its error is returned and takes `r.fail(…, reasonPublishFailed, err)` (`lego/operator/internal/controller/app_controller.go:4473-4475`), which closes the row `update_failed` with the raw text. w4/493 gave only the missing-directory exit (`obs.UserError`, `:4484-4490`) the plain sentence and `build_failed`.
   - **By code, not probed live:** the create path (`apps/service.go:3430-3443`) checks only that `publishPath` is non-empty and never calls `validatePublishPath`, so even the control-character rule that update enforces is skipped at create.
2. **Dashboard.**
   - `PublishPathRow` (`dashboard/src/features/services/components/static-site-section.tsx:162`) sets `dirty={(value) => value !== "" && value !== current}` (`:188`) and nothing else.
   - The New Service form's Root Directory and Dockerfile Path are plain `TextField`s (`dashboard/src/routes/services.new.tsx:286`, `:342`) with no mirror of `store.ValidRootDir` (`lego/backend/internal/store/api.go:691`).
   - Its environment rows mirror the key rule and the secret-file-name rule but not `core.CheckEnvValue` (`lego/backend/internal/core/config.go:159-202`) — the same gap as w21/047.

## Fix (target behavior)

- **(a)** For a repo-backed static site, `checkPublishPath` (`apps/settings_check.go:264`) applies the same rule the operator applies — the joined `rootDir/publishPath` must stay inside the checkout — and the create path calls it too. Create and update answer 400 on REST, GraphQL, MCP and Blueprint, with a plain sentence that names the typed value (for example `publishPath "../../../x" leaves the repository`). An image-backed static site keeps its absolute paths.
- **(b)** The operator's escape guard is a user-source error. A path that gets past save (a value stored before the rule) closes `build_failed` with that same sentence and no `publish:` prefix or wire names, as w4/493 did for the missing directory.
- **(c)** The Publish directory editor and the create form mark that rule inline (en and zh) and hold Save.
- **(d)** The New Service form's Root Directory and Dockerfile Path mark `ValidRootDir`'s rule, and its environment rows mark the three `CheckEnvValue` rules — the same change as w21/045 and w21/047, done once in the shared validators.
- Whether a `..` that stays inside the repo but leaves the Root Directory should also be refused is a **separate decision** (Render's behavior is unverified). Shipping the same-as-operator rule is parity-sufficient and breaks nothing that works today; file the stricter variant as a follow-up, not a blocker here.
