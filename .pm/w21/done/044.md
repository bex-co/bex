# A deploy's log page shows lines that belong to another deploy whose time window overlaps it: a superseded deploy's page prints the next deploy's build error, and the failed deploy's page prints the superseded one's "Deploy canceled"

Why: Render keeps each deploy's logs separate, and a CI that fires the deploy hook twice, or two quick pushes, makes the older deploy `canceled` ("Superseded by …") while the newer one builds, so the older deploy's page then shows the newer one's build output, including its failure.

**Severity:** minor (every status, event and failure reason is right; only the log pane lies, so a user debugging reads another deploy's error under a Canceled deploy). **Estimate:** 1h (a deploy filter for the log read plus the dashboard passing it; the build-pod lines need a deploy label, see Unverified). **Kind:** gap in the per-deploy log scoping of [w5/m29](../w5/done/m29/README.md) (the deploy page): a deploy's log is cut by its `createdAt..finishedAt` window over the whole service, so any two deploys that overlap in time share lines. **Source:** live `/qa-find-bugs` pass 42, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, journey 3 (deploy hook, cancel, supersede), filed to w21 per user direction. **Status:** inbox.

## Reproduction (own Free Docker web service `qa-20261110-hook`, `srv-dbppp2nbq3ic73c0a4o0`, deleted in the same visit)

The service came from the public repo `https://github.com/bex-co/bex`, root `examples/hello-go`, auto-deploy off. Created 22:36:58; the first deploy `dep-dbppp2nbq3ic73c0a4og` was live at 22:40:32. The deploy hook URL was read from Settings and called without printing it; every call answered 200 with Render's `{"deploy":{"id":"dep-…"}}`.

1. **Controls that work.**
   - The hook creates a deploy with `trigger: deploy_hook`, commit `2b17107`, and a `deploy_started` event with `trigger.deployHook: true`.
   - Cancel (dialog "Cancel this deploy?" → Proceed, toast "Deploy canceled.") leaves the earlier deploy `live`. The URL answers 200 throughout, the header reads "Service Running · Latest deploy Canceled", and events show `deploy_ended` with `deployStatus: canceled`. GraphQL `phase` returns to `Running` within about 20 s (cancel while building: `Building` for 7 s, then `Running`; the URL answered 200 on every 2.5 s poll).
   - `imgURL` on a repo-backed service answers a clear 400 ("imgURL is not supported for repo-backed services … use ref to pin a ref instead"). A wrong, missing or malformed key answers 404 `not_found`.
   - A deploy created while another is queued supersedes it: `deployStatus: canceled`, `cancelReason: "Superseded by dep-…"`, `reasonCode: superseded`.
2. **The bug.** Two hook calls one second apart: `ref=zzzz-not-a-sha` (deploy `dep-dbpprb5hi5vc738gism0`, created 22:41:48) and `ref=abc` (deploy `dep-dbpprbfbq3ic73c0a4r0`, created 22:41:49). The second builds first and fails at 22:42:27 with "build failed in the source checkout step: fatal: couldn't find remote ref abc"; the first is superseded at 22:42:14.
   - `/services/<id>/deploys/dep-…gism0` (status Canceled, reason "Superseded by dep-…r0", ref `zzzz-not-a-sha`) shows in All logs: "Deploy queued" (its own), then "Build queued", "Building from https://github.com/bex-co/bex@main" and **"fatal: couldn't find remote ref abc"** (all three belong to the other deploy), then "Deploy canceled".
   - `/services/<id>/deploys/dep-…r0` (Build Failed) shows its own "Build queued", "Building from…" and "fatal: couldn't find remote ref abc", then **"==> Deploy canceled"** at 22:42:14 (the superseded deploy's, not its own), then "Build failed".
3. **The raw read.** GraphQL `logs(resource: "srv-dbppp2nbq3ic73c0a4o0", type: "build", startTime: "2026-11-10T22:41:40Z", endTime: "2026-11-10T22:42:30Z")` returns all of these lines for the service with no deploy field: the entry fields are `id instance level message method requestId statusCode timestamp type`.
   - Platform-authored lines carry a per-deploy `instance`: `srv-…-smiblr9hh8pl5bcgqgrq` for the `abc` deploy's "Build queued", "Building from" and "Build failed"; `srv-…-jgqra8cn66gg2echai5p` for the other deploy's "Deploy queued" and "Deploy canceled"; `srv-…-fv3u48e0mo85vt84sbk6` for the build pod's own `fatal:` line.
   - So the data to tell them apart exists for platform lines, but the viewer does not use it.
4. **Control, no overlap.** The first deploy's page and the canceled hook deploy `dep-dbppqrfbq3ic73c0a4q0`'s page show only their own lines (their windows overlap no other deploy).

## Root cause (code-traced; `origin/main` is unchanged for these files)

- `dashboard/src/features/deploys/hooks/use-deploy-logs.ts` reads "build + predeploy + app lines inside the deploy's window" with three windowed `logs(resource, startTime, endTime, type)` queries whose `resource` is the whole service. The file's own comment says the read is "scoped to `[startTime, endTime]` (the deploy's createdAt..finishedAt window)".
- The logs API has no deploy filter: `lego/backend/internal/logs/service.go` `LogEntry` has no deploy field, and `Labels` is a free map.
- Platform lines are made in `lego/backend/internal/logs/progress.go:269-275` `progressLines` (`add` sets `LabelInstance: d.ID`, timestamps come from the deploy row), so every deploy's own lines sit in the same stream and the window alone decides which ones a page prints.

## Fix (target behavior)

- A deploy's page lists only lines that belong to that deploy.
- For platform lines the `instance` is already per deploy, so the log read takes the deploy's id (a `deployId` argument on `logs`, or the viewer filtering on the deploy's instance) and drops other deploys' platform lines.
- The build pod's lines need a deploy label to be attributable. The build Job and pod are per build, so a name or label can carry the deploy id; confirm in the Loki labels.
- A window clamp alone cannot work: the two deploys were created one second apart.
- REST `GET /v1/logs` keeps Render's contract (no deploy filter there). The new argument is additive on GraphQL and the viewer.

## Blast radius (counted by grep)

- The deploy viewer has 1 production hook (`use-deploy-logs.ts`, used by `features/deploys/components/deploy-log-panel.tsx`) and 2 route aliases (`services.$serviceId.deploys.$deployId.tsx`, `static.$serviceId.deploys.$deployId.tsx`).
- `progressLines` has 1 producer.
- The Service Logs tab and `GET /v1/logs` must keep returning every deploy's lines.

## Adjacent classes

- The build-in-progress live tail (SSE) is per build pod and unaffected.
- A rollback or config rollout writes no build lines.
- App (type `app`) lines inside a deploy's window are the service's, not the deploy's, by nature and stay as they are.

## Definition of done (each bullet is repeatable with the probe above)

- On production, with two deploy-hook calls one second apart (the second with a ref that cannot resolve), the first deploy's page (Canceled, superseded) shows none of the second deploy's lines, and the second's (Build Failed) shows none of the first's "Deploy canceled".
- Each page still shows its own full story.
- The Service Logs tab and `GET /v1/logs` over the same window still return both deploys' lines.
- The new test cases fail if the viewer goes back to the window alone.
