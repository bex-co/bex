## Objective

Install the identities on the production Wasabi account and prove the shipped routes against it.

## Context

- `docs/ADR112-object-storage.md` t009 (Contract A part). The user said on 2026-11-15 that the Wasabi side is prepared and that either path (script or console) is fine. The four `BEX_OBJECT_STORAGE_*` names in `.env` were still empty when this was filed.
- The root credential is `TF_STATE_ACCESS_KEY` and `TF_STATE_SECRET_KEY` in `.env`; the production kube context follows the sibling scripts (`BEX_KUBE_CONTEXT=hetzner-prod`).
- Evidence rule: write conclusions and sha256 values into this task, never raw logs or dumps (`.pm/AGENTS.md`, #NO-ARTIFACTS-IN-GIT).
- If a step needs something that is missing (a failing root key, no cluster access, a bucket name already taken on Wasabi), park the task in `blocked/` naming exactly that.

## Steps

1. Run `scripts/object-storage-s3-credentials.sh provision`, then `verify`, then `install`; roll bex-api so it reads the Secret.
2. With `render ea objects`, put, get, list and delete 0 B, 1 B and 5 MiB objects in `oregon` and `frankfurt`; compare sha256 before and after.
3. Check a second workspace cannot read the first's key, a size of 5 GiB + 1 is refused at mint, and a `bex.read`-only token cannot mint a GET URL.
4. Probe whether Wasabi enforces the signed `Content-Length` by PUTting a larger body to a presigned URL, and record the result; if it is not enforced, state that the cap then rests on the mint rate limit and the sweep, and file the follow-up.
5. Update ADR112's Not verified list with each result.

## Result (2026-11-15): Contract A walked on production, steps 2 to 5 done

Production ran the images pinned to `b9f42ac4648e` (digest `sha256:7e70d397bbb2d6b98cd6aed0f76515f5c54055361923e5e4c0621fce6171693f`); the two Secrets were installed and bex-api (2/2) and bex-objectgw (2/2) were Ready, with no restarts after the walk. The tenants were the QA user's workspaces `bex-canary` and `tian-personal`. Everything below is also recorded, in the same words, in ADR112 § Not verified.

- **Tokens.** No password was typed or read: `scripts/qa-login.sh` signed the QA user in, and a headless device approval (`--login-challenge`) issued two human OAuth tokens for the CLI's public client: the full grant `openid offline_access bex.read bex.write bex.sensitive` (what `bex login` gets), and a grant of only `openid bex.read` (asked from Hydra's device endpoint with that scope). Both were revoked at Hydra afterwards; a re-call with each answers 401.
- **Round trips (step 2).** `bex ea objects` (a checkout build) and the unmodified pinned `render` (built from `render-oss/cli@v1.1.3-0.20261106232710-4fd34231b637`): put, list, get, delete of 0 B, 1 B and 5 MiB, in `oregon` and `frankfurt`, 12 round trips. The downloaded sha256 equals the uploaded one every time: 0 B `e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`, 1 B `bbeebd879e1dff6918546dc0c179fdde505f2a21591c9a9c96e36b054ec5af83`, 5 MiB `add77ab701977ea13ddd838c03ff1054cebec86fe91687f9d812e6255e7ef02d`. The list showed sizes 0, 1 and 5242880, the key was gone after the delete, and a get or delete of a missing key printed `object not found`. `ohio`, `virginia`, `singapore` and `Oregon` answer 400 `REGION_NOT_OFFERED`.
- **Oversize (step 3).** `sizeBytes` 5 GiB + 1 (5368709121) answers 413 `OBJECT_TOO_LARGE` in both regions; exactly 5 GiB mints (the URL was not used); a negative size answers 413, an absent one 400 `SIZE_BYTES_REQUIRED`, a `..` key 400 `OBJECT_KEY_INVALID`.
- **Scope (step 3).** With the `bex.read`-only token: list is 200, a GET URL mint is 403 `insufficient_token_scope` requiring `bex.sensitive`, a PUT mint and a DELETE are 403 requiring `bex.write`, and the object was still there. The full token mints the URL (control), which pins `response-content-disposition=attachment` and downloads as `Content-Disposition: attachment`.
- **Isolation (step 3), four ways.** (1) An API key bound to `tian-personal` (a principal that is not a member of `bex-canary`) is refused 403 `FORBIDDEN` on list, get, put mint and delete against `bex-canary`; in its own namespace it gets 404 for `bex-canary`'s key and an empty list. (2) The QA token naming a well-formed `tea-` id it is not a member of is refused 403 on all four routes, byte-identical to `GET /v1/services?ownerId=<that id>`, and nothing appeared under that prefix. (3) The same key put into both workspaces holds each one's own bytes (sha256 `8141cfe5af419dce…` in `bex-canary`, `9277b2128e6e73bd…` in `tian-personal`). (4) The root credential (`TF_STATE_*`, read by name, never printed; the pinned aws-cli image) listed `bex-objects-oregon` and `bex-objects-frankfurt`: every key matched `tea-<xid>/obk-<xid>/<key>`, the two copies sat under different `tea-` and `obk-` ids, and nothing sat outside that layout.
- **Content-Length (step 4).** Already settled by the direct probe (ADR112 § Not verified); re-confirmed through URLs minted by the real route in both regions: a URL minted for `sizeBytes: 10` stores a 10-byte body (200) and refuses 20 bytes and 5 bytes with 403 `SignatureDoesNotMatch`.
