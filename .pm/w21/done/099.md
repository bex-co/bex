# Revoking or deleting an API key answers 500 when its OpenFGA developer tuple is already gone, so the key can never be deleted

Why: a revoke that cannot finish leaves a credential the user asked to remove, and the 500 hides that the tuple is simply absent; 36 such answers were logged in 3 weeks.

Found 2026-11-16 reading production while working w21/012 (read-only).

- **Evidence:** bex-api logged `bex-api: internal error: unbind API key from workspace: revoke key membership: POST http://openfga.auth.svc:8080/stores/<id>/write returned 400 Bad Request` 36 times between 2026-10-27 and 2026-11-16 (Loki; 9 of them on 2026-11-16), and `bex_api_http_requests_total` shows `DELETE /v1/api-keys/{id}` answering 500 ten times in the last three days.
- **Cause (read from the code, not reproduced):** `tenantService.UnbindKey` (`lego/backend/internal/api/tenancy.go:540`) revokes the developer tuple first and returns its error, withholding the Hydra delete. `openfgaChecker.writeTuple` (`lego/backend/internal/authz/authz.go:172`) sends `deletes` with no `on_missing: "ignore"`, and OpenFGA answers 400 for a delete of a tuple that does not exist. The comment on `UnbindKey` says "Revoke is idempotent", which it is not: a retry after a partial revoke, or a key whose tuple was never written, fails the same way every time.
- **Fix:** delete with `on_missing: "ignore"` (check the pinned OpenFGA version supports it) or treat that 400 as success, for every revoke that is meant to be idempotent (`RevokeWorkspaceMember`, the agent-session and other deletes in `authz.go`), keeping the "tuple first, then the local row" order; a test that revokes twice and a test of a missing tuple against the real OpenFGA the backend suite already starts.
- **Acceptance:** `DELETE /v1/api-keys/{id}` of a key whose tuple is already gone answers 204 and the key stops working; the second revoke of the same key answers as the first.

## Result

DONE 2026-11-16 in `ef7e65cd3` (`deploy.yml` run 43981423473, dispatched; both bex-api replicas on image digest `sha256:79d9db9f82e9`, the controller digest of the pin `ef7e65cd3f46`, read on both pods).

- **Cause confirmed, then fixed at its root.** OpenFGA answers `/write` with 400 `write_failed_due_to_invalid_input` to a delete of a tuple that does not exist ("cannot delete a tuple which does not exist") and to a write of one that already does, unless the batch carries `on_missing` or `on_duplicate: "ignore"`. `openfgaChecker.writeTuple` sent neither, and it is the only `/write` caller in the Go tree, so one change covers every grant and revoke: `RevokeWorkspaceMember` (API-key unbind, workspace delete, member removal, leaving, account teardown, the role-change revokes) and every grant (`GrantWorkspaceRole`, `GrantWorkspaceAdmin`, `GrantWorkspaceMember`, `GrantAgentSessionWorkspace`). Deletes now send `on_missing: "ignore"` and writes `on_duplicate: "ignore"`; the "tuple first, then the local row and Hydra" order is untouched. There is no agent-session revoke in `authz.go` (a session's parent tuple is only ever written); the note's mention of one does not match the code.
- **Versions.** Production's OpenFGA is v1.18.1 (`auth/openfga`, chart 0.3.10, read from the pods) and the backend suite's pin is v1.18.3; both honor both options, probed with `curl` against each image (a write twice, a delete twice, with and without the option, and a present tuple still deleted with `on_missing`). So there is no error-code fallback to carry.
- **Reproduced first**, on the code before the fix, against the real OpenFGA the suite starts: `DELETE /v1/api-keys/{id}` of a key whose developer tuple was deleted answered 500 with the production log line (`unbind API key from workspace: revoke key membership: POST …/write returned 400 Bad Request`), and a second grant of the same tuple, a second revoke and a revoke of a tuple never written all answered 400.
- **Tests** (`internal/api/openfga_idempotent_e2e_test.go`, real OpenFGA, plus real Postgres for the route): `TestOpenFGAMembershipWritesAreIdempotentE2E` (revoke of a never-written tuple, a second grant, a second revoke, for `admin`, `developer` and `viewer`, and a second grant of an agent session's parent edge) and `TestRevokeAPIKeyWhoseTupleIsGoneE2E` (the tuple deleted behind bex's back: DELETE answers 204, the client is gone, the binding is gone, the shared revocation marker is set; the second DELETE answers 404, like a key that never existed; a key with its tuple present is unchanged). Dropping `on_missing` fails both the revoke test and the route test; dropping `on_duplicate` fails the grant tests; each restored. Full real-DB backend suite and `make lint` on all four modules green.
- **The second revoke answers 404, not 204.** That is the route's existing contract for a key bex no longer knows (`RevokeAPIKey` answers `ErrNotFound` for an unbound key, the same body as an id that never existed), so it is kept. What "answers as the first" means here is the retry of a half-finished revoke: it answered 500 for ever and now completes with 204.
- **Production, after the deploy.** A throwaway key in the `bex-canary` workspace, created through the API as the QA user (a Kratos session, never printed). Its OpenFGA developer tuple deleted directly in OpenFGA through a port-forward (`check` answered `allowed: false`); with the tuple gone the key still authenticated and authorized nothing (bearer 403). On the old build, `DELETE /v1/api-keys/{id}` answered 500 twice and the key stayed listed, with the unbind line in the pod's log. On the new build the same key: DELETE 204, a second DELETE 404 (an id that never existed: the same 404 body), the key no longer listed, no tuple left in OpenFGA, and its bearer answers 401. Read-back: the route's request counter on the new pods holds 204 once and 404 twice and no 500; the unbind line appears in neither new pod's log and Loki has no such line since the roll (before it: 36 lines over the three weeks, 18 hours with a hit, the last cluster on 2026-11-16 02:00 to 03:59 UTC, plus the two probes). The canary workspace holds only its two older keys again; the throwaway key's session was logged out, and the port-forwards, token files and the kubeconfig are deleted.
- **Not done.** The keys real users could not delete are not touched: their next DELETE completes, and the 36 logged attempts are the ones that now succeed. ADR024 already described tuple writes as "idempotent (check-before-grant, delete-tolerates-absent)"; that was only true of the first half until now.
