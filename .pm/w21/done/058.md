Why: w21/026 and w4/557 set the guarantee that Top queries shows the customer's own work; on a database with no application and no console use it still shows the panel describing itself (four rows of transaction-control statements), which the fix's author recorded as a residual but nothing on the board tracks.

**Severity:** minor (noise, no wrong data). **Estimate:** ~40m (one predicate in `sqlTopQueries` or a leaner envelope for the fixed Insights reads, plus a test against a real `pg_stat_statements`). **Kind:** residual of [w4/557](../w4/done/557.md) (itself a residual of [w21/026](done/026.md)); its closing note lists "`BEGIN READ ONLY`/`ROLLBACK` from the read-only envelope still count as the owner's" and files nothing. **Source:** live `/qa-find-bugs` pass 149, 2026-11-12 ~02:5x UTC, production `https://dashboard.bex.co`, workspace `bex`, deploy pin `c5518dc24` ("pin platform images to e7a56b07e0d7", 2026-11-12T02:23:42Z, which contains a79359077, the w4/557 fix), filed to w21 per user direction. **Status:** inbox.

## Root cause (code-traced; `origin/main` at `739ee64a7`)

- Every Insights read goes through `runAuthorizedInsight` (`lego/backend/internal/postgres/insights.go:484`, 5 call sites) into `runSQLQuery` (`query.go:360-370`), which calls `conn.BeginTx` with `AccessMode = pgx.ReadOnly` (sends `begin read only`) and defers `tx.Rollback` (sends `rollback`). `pg_stat_statements` records both utility statements under the connecting role.
- `tagInsight` (`insights.go`) tags only the SELECT, because the two envelope statements cannot carry a comment, so the `NOT LIKE '%/* bex:insights */%'` predicate in `sqlTopQueries` (`:369-381`) never matches them. The reserved-role predicate does not apply either: the connecting role is the owner or a customer credential, which is a customer role by design.
- The SQL console runs the same envelope (`query.go`, `executeAuthorizedQuery`), so a customer's console queries leave the same two statements.

## Fix (target behavior)

- On a database with no application traffic and no console use, Top queries shows the panel's existing empty-state copy (w4/557's DoD), and a statement the customer ran (including from the SQL console) still appears.
- Smallest change: leave the envelope's two exact statement texts, `begin read only` and `rollback`, out of `sqlTopQueries` (they carry no SQL and no customer information). Alternative: drop the explicit `BEGIN READ ONLY` for Insights' own fixed SELECTs, since the session already pins `default_transaction_read_only=on` and a statement timeout (`query.go:325-340`) and the SQL is constant; that keeps the console's envelope intact but leaves `rollback` unless the transaction is also dropped.
- Decide and record whether a customer's own plain `BEGIN`/`COMMIT`/`ROLLBACK` rows stay visible; the cheaper rule hides only the two texts the envelope sends.
- REST, GraphQL and MCP share `sqlTopQueries` through `TopQueries` (`insights.go:577`; callers `rest.go:427`, `mcp.go:521`), so one change covers all three; the dashboard only renders the rows.

## Blast radius (counted by grep)

`sqlTopQueries` has 1 reader (`TopQueries`, `insights.go:586`); `TopQueries` has 2 callers (`rest.go:427`, `mcp.go:521`) plus the GraphQL resolver that shares the service; `runAuthorizedInsight` has 5 call sites. Active processes uses `sqlProcesses` and is unaffected (its tagged SELECT is already excluded).

## Adjacent classes

Reserved roles and the tagged SELECTs stay excluded (unchanged). A database that already ran untagged Insights SQL keeps those rows until its statistics reset (recorded in w4/557). Hiding the envelope hides nothing a customer can act on.
