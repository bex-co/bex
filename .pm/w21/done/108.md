# 108 — A rejected PUT of a variable a Blueprint dropped still moves its literal into the store and holds its removal

Why: w21/106 holds the adoption of a retained literal for the next deploy, but the single-variable verbs adopt before they validate, so a write the API refuses still changes the service and leaves it with a saved, undeployed change.

- **Source:** w21/106, 2026-11-17 (the variant of its choice (a), "move the literal in the verb's own write").
- **Facts:** `SetEnvVar` calls `adoptRetainedKeys` (`lego/backend/internal/secrets/service.go`) before `resolveValue` and the aggregate quota check, and `DeleteEnvVar` before it knows the key exists. A REST `PUT /v1/services/{id}/env-vars/MESSAGE` with both `value` and `generateValue` answers 400, and still leaves the literal moved off `spec.Env` into the store with `app.bex.co/pending-source-generation` set (a probe on a control-plane service, 2026-11-17). Nothing a client can observe in the variable's list or value changes, but the service now carries saved changes that need a deploy. The same holds for a write refused by the aggregate quota. Each verb also writes the store and patches the App twice (the adoption, then its own write).
- **Fix:** do what `PatchEnvironment` does (w21/103): make the move inside the verb's own write, so a refused write moves nothing. The verb's store write takes the retained name as its edit (`PUT`: the new value; `DELETE`: the key is removed, found when the retained literal or the store held it; `PUT` all: the replaced set), and the same locked App patch removes the literal through `dropMovedRetained`, held under `rollout.WithSaveOnly` for a staged write. `adoptRetained` and `adoptAllRetained` can then go.

## Done when

- [x] A refused `PUT` (conflicting `value` and `generateValue`, a quota breach) and a `DELETE` of a name that does not exist leave a retained literal on `spec.Env` with no annotation set, and the staged and deploying verbs keep the behavior w21/106 pinned in `retained_verbs_rollout_test.go` with one store write and one App patch each.

- **Choice: the variant the note names, the move inside the verb's own write.** `SetEnvVar`, `DeleteEnvVar` and `SetEnvVars` no longer call anything before they validate. The store write takes the retained name as its edit (`PUT`: the new value; `DELETE`: found when the literal or the store held it, through a new `alsoHeld` argument of `deleteMapKeyAfterProjection`; `PUT` all: the replaced set), and the same locked App patch removes the literal through `dropMovedRetained`, held under `rollout.WithSaveOnly` for a staged write (`holdMovedRetained`). `adoptRetained`, `adoptRetainedKeys` and `adoptAllRetained` are gone, and the whole-set replace's two branches collapsed into `materializeEnvEditing`. A move is a change even when the stored map ends as it was (the "no change" shortcuts of `PUT` one and `PUT` all now ignore a moved literal). Each verb makes one store write and one App patch.
- **The note's premise, corrected in two places.** (1) A `DELETE` of a name that does not exist never moved another literal: the old code adopted only the named key, which is not retained. It stays a regression case; the defect was the `PUT` and `PUT` all refusals (`value` with `generateValue`, a bad name, a value over 131071 bytes, the aggregate quota). (2) The refusal of a `DELETE` of a missing name is not free of App writes, as the filing assumed: `deleteMapKeyAfterProjection` still runs the repair of a stale projection (pinned by `TestDeleteEnvVarAlreadyAbsentRepairsStaleProjection`), which patches the App on any service and, over GraphQL and MCP, rolls it and opens a deploy. That is the verb's own behavior, unrelated to a retained literal, and is filed as [w21/109](109.md); what holds for it here is the note's own claim (the literal stays, no `pending-source-generation`, no store write).
- **Order of a `DELETE` kept.** It projects and patches the App first and commits the store last, so a revoked value stops reaching the pods whatever the store does. For a retained literal that means a store commit that fails after the App patch leaves the literal removed (the delete the caller asked for) with an error answered; a retry answers not found.
