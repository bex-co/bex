# 096 — Nothing alerts when the object storage sweep stops completing

Why: w21/088 now exports how long each pass takes and when the last complete one ended, but no alert or panel reads them, so a sweep that is cut off every hour, or never gets the lock, leaves usage, the quota gate and the shadow meters stale without anyone being told.

- **Source:** w21/088, 2026-11-15. The series are `bex_usage_object_storage_sweep_pass_duration_seconds{result}`, `bex_usage_object_storage_sweep_workspace_duration_seconds`, `bex_usage_object_storage_sweep_workspaces_total{result}` and `bex_usage_object_storage_sweep_last_complete_timestamp_seconds`, in `lego/backend/internal/objectstorage/sweepmetrics.go`.
- **Scrape keep-list:** the bex-api job in `deploy/gitops/base/prometheus.yaml` keeps only the families its `__name__` regex names, so the sweep's series are named `bex_usage_object_storage_sweep_*` (the first names, `bex_object_storage_sweep_*`, were exported by the pods and stored by nothing, found on production 2026-11-16); `TestEverySweepMetricIsKeptByTheScrapeJob` guards that, and `scripts/obs-scrape-keep-check.sh` guards an alert's series.
- **Shape of the data:** only the replica that holds the advisory lock records a pass, so a series exists on one pod at a time, and the lock can move between replicas; read the series with `max()` over both. A pass that is cut off at its deadline returns an error and logs "pass cut off" once.

## Steps

1. Add rules to `deploy/gitops/base/rules/alerting_rules.yml` with a `promtool` test next to `object_storage_egress_alerts_test.yml`: a warning when `time() - max(bex_usage_object_storage_sweep_last_complete_timestamp_seconds)` is over three hours (and an `absent` branch for a fleet that never completed one), and a warning when the 50-minute pass is cut off more than once in three hours (`pass_duration_seconds_count{result="cut_off"}`).
2. Add a panel to the Billing and metering dashboard (`deploy/gitops/base/values/grafana.values.yaml`): pass duration by result against the 50-minute limit, and workspaces by result.
3. Name the runbook step: what to read first (the `pass over N workspaces took T` log line) and what raises the pool bound (`sweepWorkers`, ADR112 D8).

## Done when

- [x] A sweep that has not completed in three hours, or that is cut off repeatedly, pages, and the dashboard shows pass duration against its limit.

## Result (2026-11-16)

Shipped in [938c5cb36](https://github.com/bex-co/bex/commit/938c5cb36), deployed by `deploy.yml` run 43973746876 (a dispatch: the push-triggered run 43973692464 skipped its `build` and `deploy` jobs inside the six-hour window, as 095 found) as pin commit `a24555d5c`, and read back on production.

- **`ObjectStorageSweepStale`** (warning, `for: 30m`). `time() - max(max_over_time(bex_usage_object_storage_sweep_last_complete_timestamp_seconds[3h])) > 10800`, or an `absent` branch gated on the egress gauge. It keys off a pass that ends complete (every workspace reached, none failed), never the work done, since 095 lets a healthy pass sweep nothing. The note's plain `time() - max(gauge)` was not used: the gauge is process-local and starts at 0, so after a rollout it reads the whole epoch (and, if a new pod's first pass fails, until its next one an hour later); the three-hour look-back keeps the newest value any pod reported, so a deploy alone cannot read as stale and a sweep that stays broken still fires three hours after its last complete pass. The `absent` branch is gated on `bex_usage_object_storage_egress_month_bytes`, which the same `if` in `main.go` registers, so a fleet without a Wasabi credential stays quiet and the first names (`bex_object_storage_sweep_*`, exported and stored by nothing) would have been caught.
- **`ObjectStorageSweepCutOff`** (warning, `for: 10m`). `sum(increase(..._pass_duration_seconds_count{result="cut_off"}[3h])) > 1.5`: `increase()` extrapolates, so one cut-off reads about 1.0 and `> 1` fired on a single one (a mutation run showed it).
- **Zero export (found by this item).** The pass duration histogram and the workspaces counter are vectors, created at their first use, and only the replica that records a pass has them, so a pod's first cut-off would have been a series born at 1 that `increase()` cannot count: the same defect 095 fixed for the listing bytes. Every replica now exports each result at 0 (`TestEveryReplicaExportsEverySweepSeriesAtZero`, which fails without the loops). `last_complete` is a plain gauge, exported at 0 already.
