# 113 — S3 object metadata names come back capitalised (`X-Amz-Meta-K`), so boto3 and aws-cli read `{'K': 'v'}` where S3 returns `{'k': 'v'}`

Why: boto3 and the AWS CLI do not lowercase metadata keys, so a customer who stores `Metadata={'mtime': …}` and reads `head['Metadata']['mtime']` gets a `KeyError` on bex and not on S3.

- **Source:** w21/m498 t019, 2026-11-19, observed on production with aws-cli 1.44.87: `copy-object --metadata k=v --metadata-directive REPLACE` then `head-object` printed `{'K': 'v'}` (the aws-cli, which shows botocore's parse).
- **Cause:** `handlers_object.go` writes `h.Set("x-amz-meta-"+k, v)`, which canonicalises the name, and Traefik (a Go proxy) canonicalises a backend's header names again on HTTP/1.1, so a lowercase write in `bex-s3` would not survive the edge. The AWS SDK for Go v2 lowercases keys itself, botocore does not, rclone is expected to (not run).
- **Verify first:** that it is not fixable inside bex alone (a request over HTTP/2 gets lowercase names; HTTP/1.1 clients do not), and whether `aws` v2, rclone and boto3 show the same.
- **End state:** if no edge setting or response form returns lowercase names to HTTP/1.1 clients, the difference is a dated, evidence-backed entry in ADR018's S3 rows and in the S3 section of `docs/bex-cli.md` (with the boto3 example and the workaround of reading keys case-insensitively), and a test pins today's behaviour so a change is noticed; if a way exists, ship it with a test through the same path the walk used.

## Result

**DONE 2026-11-19.** The note's premise held and its "not fixable inside bex alone" was true, but there was a way at the edge, so the end state's second branch applied: shipped with a test through the path the walk used.

- **Verified first.** Production, a throwaway workspace made for the walk (control-plane `POST /v1/tenants` with the QA user as its admin, a two-hour read-write key over REST, all of it removed afterwards), stock aws-cli 2.39.5, boto3 1.43.125 and rclone v1.75.2, path-style, with each client's own defaults. Before: aws-cli `head-object` printed `{"Mixedcase":"Aws","Mtime":"aws"}` (and `{"K":"v"}` after a copy with `REPLACE`), boto3 returned `{'Mixedcase': 'Boto3', 'Mtime': 'boto3'}` with `X-Amz-Meta-Mtime` as the header name the library received, so `head['Metadata']['mtime']` was a `KeyError`; rclone read `mtime` in lowercase (it lowercases itself, so it is unaffected, now observed and not expected); `curl --http1.1` on a presigned GET showed `X-Amz-Meta-Mtime` and `--http2` `x-amz-meta-mtime`. The note's cause held and the case is wider than it said: S3 lowercases the whole name, so `MixedCase` was `Mixedcase` here.
- **No setting and no response form fixes it, and one edge component does.** On the v3.7.17 binary the edge runs, behind a Go backend that wrote `x-amz-meta-raw` into the header map (which `net/http` sends as written; a direct client saw it in lowercase), Traefik answered `X-Amz-Meta-Raw` for an HTTP/1.1 backend and for an `h2c` one, and its option list (`traefik --help`) has nothing for header case. A write to the response's header map after Traefik has copied the head does reach an HTTP/1.1 client as written, so the S3 route runs a Traefik local plugin, `bexS3MetadataCase`, which renames every `X-Amz-Meta-*` key to lowercase just before `WriteHeader`. The two older plugins already gave the edge the machinery (content-hashed ConfigMap, `localPlugins`, `gitops-validate`). Under a 4 GiB body it costs 6.06 GB/s against 6.42 GB/s on the real binary.
- **Shipped in three pushes, in the order the edge needs:** `fe52cf2b6` (the plugin, its compiled tests and Yaegi v0.16.1 run in `gitops.yml`, the ConfigMap, volume and `localPlugins` entry, the `gitops-validate` check; Argo rolled both Traefik pods onto it, `Plugins loaded` on each), `539f9efcd` (the Middleware, synced a wave ahead of the route, and the route's `middlewares`; `gitops-validate` pins all three together and fails on a missing one, checked with a mutation) and the closing commit (the contract suite, the docs, this record). Traefik disables a router whose middleware is missing, which is why the plugin went first.
- **After, on production:** aws-cli `{"mixedcase":"Aws","mtime":"aws"}`, `{"k":"v","other":"Two"}` and `{"mtime":"cp"}` for `aws s3 cp --metadata`; boto3 `{'mixedcase': 'Boto3', 'mtime': 'boto3'}` with lowercase wire names and `head['Metadata']['mtime']` working; rclone unchanged; `curl --http1.1` `x-amz-meta-mtime`; a 20 MiB round trip with each client sha256-identical, a ranged read 206, a missing key `NoSuchKey`, no 5xx on `objects.onbex.co` in the edge's log for the window.
- **The test through the same path:** `scripts/s3-contract.sh` now runs the gateway behind the edge's Traefik (the release `traefik.values.yaml` pins, checked, sha256-pinned per platform) with the plugin loaded from a copy of the mounted directory, so all three stock clients reach the gateway as a customer's do. `s3-contract-boto3.py` asserts `{"mtime": "42", "mixedcase": "x"}` exactly (it only warned before), and the aws phase asserts `Metadata.mtime`, `Metadata.mixedcase`, a copy with `REPLACE` and the lowercase bytes of a presigned GET over HTTP/1.1. Green locally on macOS arm64 with a real Postgres; with the middleware removed it fails with "head-object does not read Metadata.mtime as aws". `s3-contract.yml` also runs on the plugin and the Traefik values.
- **Docs.** ADR112 D3 carries the evidence and the failure modes, and its two other mentions are updated; ADR018's S3 row no longer lists the divergence (there is none to sign off: it was removed, not recorded); `docs/bex-cli.md` no longer lists it.
- **Not observed.** The plugin under a 5 GiB download (the local 4 GiB run and the production 20 MiB runs stand for it), and a rollout of the edge during an S3 transfer (the two pods roll one at a time, as for every plugin change).
- **Fixtures.** The first two `POST /v1/tenants` attempts took the wrong admin id (a `usr-` and an `own-` spelling instead of the Kratos identity), so the QA user could not reach them: both tenant rows and their two OpenFGA tuples were deleted by SQL in one transaction each (rows counted before and after), and the third workspace was deleted as the QA user with `deleteWorkspace`. The bucket, its objects and the key are gone, and the QA session was logged out.
