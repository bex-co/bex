# In the ⌘K search, a renamed service's accessible name glues its current name to its original name (`eden-dash-v3block-eden-mono`)

Why: a screen-reader user hears one invented word instead of two names, and cannot tell which of the two is the service's current name.

**Severity:** minor (accessible name only; the visible row is fine). **Estimate:** 20m, dashboard only, one component plus a test. **Source:** live `/qa-find-bugs` pass 10, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (read-only, existing services of the workspace)

1. Open `https://dashboard.bex.co/`, press Cmd+K (or click Search). The Resources group lists services; two of them were renamed after creation.
2. Chrome's own accessibility tree (CDP `Accessibility.getFullAXTree`, role `option`) returns these names, in English and in Chinese (`?lang=zh`):
   - `eden-dash-v3block-eden-mono Web Service` (zh: `eden-dash-v3block-eden-mono Web 服务`)
   - `reverse-proxy-pocblock-eden-mono-1 Web Service`

   Control rows that were never renamed are clean in the same AX-tree read (zh): `eden-cms-v2 Web 服务` and `blockeden-forum-db 数据库`.

3. DOM of the first row: `<span><span>eden-dash-v3<span>block-eden-mono</span></span><span>Web Service</span></span>`. The inner span is `display:inline` with class `ml-2 text-xs text-muted-foreground`, so the eye sees a gap (8px margin) but there is no whitespace character between the two names. `block-eden-mono` is the service's original immutable name.

**Evidence:** `.playwright-mcp/qa-search-2.png` (search for "eden-dash": the row renders as `eden-dash-v3  block-eden-mono  Web Service`, a muted second name beside the first) and `.playwright-mcp/qa-search-1.png` (the open palette). Both are gitignored and local to the hunting session; the AX-tree names in step 2 are the durable probe.

## Root cause

`dashboard/src/common/components/dashboard-layout/global-search-dialog.tsx:441-466` `SearchResultLabel`: `<span className="truncate">{name}{aka ? <span className="ml-2 text-xs text-muted-foreground">{aka}</span> : null}</span>`. The spacing between the two names exists only as a CSS margin, so the accessible-name computation (inline elements are joined without a space) glues them. `aka` comes from `originalName(service)` at `global-search-dialog.tsx:436-440`, which returns the immutable name only when it differs from the current name; that is why only renamed services are affected.

## Fix (target behavior)

The option's accessible name reads `<current name> <original name> <kind>` with whitespace between all three (for example `eden-dash-v3 block-eden-mono Web Service`), and the row looks the same as today (muted second name, same gap, still truncating the first). The smallest change is a real space text node before the muted span with a slightly smaller margin (for example `{" "}` plus `ml-1`). Whether to also label the second name as "originally …" for screen-reader users is a copy decision this note does not make; the fix only removes the glue. UI only.

## Blast radius

- `SearchResultLabel` has 6 call sites in `global-search-dialog.tsx` (lines 286, 323, 347, 367, 387, 407); only the service one (line 327) passes `aka`, so one row type changes. Rows without `aka` must keep their current name (regression-test one project row and one database row).
- Existing tests: `dashboard/src/common/components/dashboard-layout/__tests__/global-search-dialog.test.tsx` and `global-search.test.tsx`; add one asserting the renamed-service option name with a space.
- Look-alike (cause not probed): `dashboard/src/features/usage/components/charges-card.tsx:99-107` uses the same pattern, `{label}<span className="ml-2 text-xs …">{charge.tier}</span>`, in a plain row (not a named control), so any effect is on reading order only. No such row exists on the probed account's Billing or Workspace Settings pages, so it is unverified and is not part of this fix.

## Adjacent classes

Pending, empty and no-results states of the palette, and the Navigation and Projects rows, are unaffected. Not an authorization boundary.

## Unverified (not probed this run)

- Real screen-reader output (NVDA, VoiceOver); the claim rests on Chrome's accessibility tree, which is what those readers consume.
- The charges-card look-alike above.
- Whether other components join a name and a muted suffix with only a margin: a grep for the exact class string `ml-2 text-xs text-muted-foreground` finds just these two files, but other spacing utilities (`ml-1`, `gap-*` on non-flex parents) were not enumerated.
