# `TestBexS3RunsWithNoOtherProgramInstalled` failed its TempDir cleanup under `-race`: find what writes into HOME after the command returned

Why: it failed once with `.bex/state/analytics` not empty during cleanup (`-race`, runner `CI=true`), which is either a test that does not wait for the launcher's detached analytics sender or a real file left behind after the command exits, and a flaky test becomes a red main for whoever pushes next. The w21/115 CI-fix worker saw it and left it, since CI runs without `-race`, and no board item records it.

- **Evidence.** The test is `lego/cli/s3_contract_test.go:172`. Its environment is `s3Env` (`:104`), which calls `telemetryEnv` (`lego/cli/main_test.go:822`), which blank-sets `BEX_CLI_DISABLE_ANALYTICS` on purpose so that sending is on, against the stub API. The launcher sends through a detached sender (`analytics.IsSendSubprocess()`, `lego/cli/internal/disclosure/disclosure.go:191`; `lego/cli/internal/bridge/transport.go:33`), a process that can outlive `bex` and still touch `<HOME>/.bex/state/analytics/` while `t.TempDir` is removed. That is a hypothesis, not proven.
- **Change.** Reproduce it (`cd lego/cli && go test -race -count=20 -run TestBexS3 ./...`, with and without `CI=true`) and confirm which process writes. Then make a test that does not look at telemetry set `BEX_CLI_DISABLE_ANALYTICS=1` (this one asserts that no other program starts, not what was reported), and make a test that does look at it wait until the stub has the event and the `events` directory is empty before it returns. If the launcher itself leaves a file behind after exit, that is a product defect: fix it there and say so.
- **Where.** `lego/cli/s3_contract_test.go`, `lego/cli/main_test.go` (`telemetryEnv`), and `lego/cli/internal/disclosure` or `bridge` only if the cause is there.
- **Done when.** `go test -race -count=20` over the `TestBexS3*` tests passes 20 times in a row, under `CI=true` and without it, and the commit message names the process that wrote the file.

**Done 2026-11-23.** The process that wrote into HOME after the command returned is the launcher's own detached sender, `bex analytics send <HOME>/.bex/state/analytics/events/event-<uuid>.json`: upstream's `startDetached` re-executes the `bex` binary (`RENDER_CLI_ANALYTICS_SUBPROCESS=1`) as the command exits, and the child takes about 25 ms to start (more under `-race` with parallel tests). The file it wrote is `<HOME>/.bex/state/analytics/notice-shown`, with the directories above it. The cause is `disclosure.Begin`, which runs in every `bex` process and wrote upstream's marker whenever it was missing: in the child that is a second write of a file the parent had already written, and when the caller had removed HOME in the meantime (`t.TempDir`'s cleanup) it recreated `.bex/state/analytics` mid-`RemoveAll`, which then failed `directory not empty` at `.bex`, `.bex/state/analytics` or HOME itself.

- **Reproduced first.** `go test -race -count=20 -run TestBexS3` failed 11 times in 20 (`RunsWithNoOtherProgramInstalled` 6, `SignsWithBexsKeyAndTouchesNoAWSFile` 3, `APIIsGone` 2), each with `TempDir RemoveAll cleanup … directory not empty`. These are exactly the three `TestBexS3*` tests that send and do not wait for the event (`ReportsEachCommandOnce` waits). A run of the built binary followed by an immediate `rm -rf` of HOME found `.bex/state/analytics/notice-shown` back on disk in 120 of 120 runs. `CI=true` does not change it: `telemetryEnv` drops `CI`, because a `CI` run bypasses the disclosure gate, so the test child always sends detached.
- **Product fix.** `disclosure.Begin` returns before `ensureUpstreamMarker` when `analytics.IsSendSubprocess()`: the child consumes its event file and writes nothing else. The same 120 runs now recreate nothing. ADR113 D5's mechanism line says so. A script that runs `HOME=$(mktemp -d) bex …; rm -rf $HOME` met the same race, outside tests.
- **Test side.** The three tests that do not look at what was reported opt out (`s3QuietEnv`: `BEX_CLI_DISABLE_ANALYTICS=1`, as `s3_confirm_test.go` already did inline, and now through the same helper), so no sender outlives them and they no longer seed a notice marker they do not need. `ReportsEachCommandOnce` is unchanged: its event reaches the stub only after the child removed the event file, so there is no `events` directory to wait for.
- **Proof, each half alone.** The product fix with the original tests passes `-race -count=20`; the test change with the original `Begin` passes it too. With the fix reverted, `TestBeginInTheSendSubprocessWritesNothing` and the end-to-end `TestTheDetachedSenderWritesNothingButConsumesItsEventFile` (the built binary as the sender, one event file, HOME afterwards) both fail, the latter with `notice-shown` named.
- **Done when.** `go test -race -count=20 -run TestBexS3 .` passes 20 of 20 with and without `CI=true` in the runner's environment; `CI=true go test ./...` and `make lint` pass.
