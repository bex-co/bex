# 125 — Moving a Postgres cluster onto the bex operand can leave it refusing every new connection: CloudNativePG reloads `local_preload_libraries = pgextwlist` into the old image before the pod rolls

Why: on 2026-11-24 three of the seven managed clusters refused every new connection for 12 to 16 minutes until their pods were deleted by hand (w21/m584 t005). The rollback that ADR092 D4 records, followed by a re-adoption, would race the same way on every cluster.

**Found by** w21/m584 t005, when pin `f46c44d9ddb1` adopted the gated bex operand. Full record: [ADR092 § D4](../../docs/ADR092-postgres-extension-supply.md#d4--rollout-one-rolling-restart-approved) (Rollout record).

- The bex operator rolled out at 00:00:58Z, and one `Cluster` update per database set both the new `imageName` and `pgExtensionParameters` (`lego/operator/internal/controller/database_operand.go`).
- `twenty-postgres` (`bex`, PG16), `qa-20261117-m453-hobby` (`tian-personal`, PG18) and `qa-m586-existing-pg16` (`bex-canary`, (disposable)) stayed on `ghcr.io/cloudnative-pg/postgresql:16@sha256:e38d10bb…` / `:18@sha256:d7a81cb5…`, with readiness answering 500.
- From 00:01:01Z their postgres log and the CloudNativePG operator log (`Cannot extract Pod status`) both read `FATAL: could not access file "$libdir/plugins/pgextwlist": No such file or directory (SQLSTATE 58P01)`.
- `local_preload_libraries` takes effect at the next connection without a restart. So CloudNativePG's reload made the instance still on the upstream image, which has no pgextwlist, refuse every new backend, the instance manager's own status connection included. The operator then never rolled the pod.
- The four clusters that rolled by themselves had their rollout started first: the operator logged `Pod rollout required` for each between 00:00:58Z and 00:01:04Z, while the three stuck ones logged `Cannot extract Pod status` first. It is a race.
- `kubectl delete pod <cluster>-1` recreated each pod on its PVC with the bex digest, in 46 s to about 3.5 min.

**Done when:**

- The operator adds `local_preload_libraries` (and anything else a running upstream instance cannot load at connection time) only to a `Cluster` whose instances already run a bex operand image. For example, the image change goes in one update and the preload in a later one, once the pods report the new image. A cluster moving onto the bex operand never has a reload that its running image cannot serve.
- A test drives a cluster from an upstream image to a bex operand and fails if any `Cluster` spec carries `local_preload_libraries = pgextwlist` while an instance still runs the upstream image. Revert the fix and watch the test fail.
- ADR092 D4's rollback paragraph says a re-adoption after the rollback needs no manual pod deletion.

**Triage (2026-11-24): work.** The premise held: `cnpgClusterSpec` projected `pgExtensionParameters`, `local_preload_libraries = pgextwlist` among them, in the same `Cluster` update as the new `imageName` (`database_controller.go`), with no look at what the instance Pods run. `reconcileReadReplicaCluster` copied the primary's parameters into each replica cluster, so a replica had the same race.

**Done 2026-11-24.**

- **The fix:** `holdConnectionPreload` (`lego/operator/internal/controller/database_operand.go`) removes `local_preload_libraries` from a `Cluster` spec while any running instance Pod of that cluster (`cnpg.io/cluster`, `cnpg.io/podRole=instance`) has a `postgres` container image that is not a bex operand (`ghcr.io/bex-co/bex-operator:<major>.<minor>-postgres-<commit>`, `carriesPgextwlist`). It applies to the primary (`reconcileCluster`) and to every read replica cluster, each against its own Pods. The first update carries the image with every restart-only setting (`shared_preload_libraries`, `shared_buffers`) and the placeholder `extwlist.*`, `timescaledb.*` and `duckdb.*` settings, so the roll is still the one restart. The preload follows by reload once no instance runs another image. A held cluster requeues every 10 s, because nothing watches its Pods.
- **Edge cases:** a cluster with no instance Pods (new, or hibernated) gets the preload at once, because CloudNativePG creates each Pod from the current image. A finished Pod is not counted. A cluster an earlier operator left with both settings in one update, still on the upstream image, gets the preload withdrawn on the next pass, so CloudNativePG can roll it. `unobservedOperandPostgresql` no longer needs the preload to recognize an operand profile.
- **Tests** (`database_operand_reconcile_test.go`): `TestAdoptingABexOperandMovesTheImageBeforeTheConnectionPreload` drives an HA PG16 cluster from the upstream image onto a bex operand, back by the rollback and onto it again. CloudNativePG's roll is simulated one Pod at a time, and the test fails if any pass leaves `local_preload_libraries` set while a running instance is on `ghcr.io/cloudnative-pg/postgresql:`. `TestAClusterProjectedWithThePreloadBeforeItsRollRecovers` covers the stuck state, and `TestAReadReplicaTakesThePrimarysPreloadOnlyOnItsOwnOperand` covers the replicas. With `holdConnectionPreload` disabled, all three fail on that invariant. With the finished-Pod skip removed, the adoption test fails with the preload held for good. `TestBexOperandImagesArePinnedPerMajor` also checks that every adopted digest is recognized, and that no upstream pin is.
- **ADR092 D4:** § The connection preload follows the image records the two-step move. The rollout record's remedy now says a re-adoption after the rollback needs no manual pod deletion.
- **Not verified on production:** no adoption is pending there. Every managed cluster already runs the bex operand with the preload, so the next digest bump or re-adoption is the first live run.
