# 084 — The `bex-api` Prometheus job reads one replica's counters, so request panels show about half the traffic

Why: production runs two bex-api replicas behind one ClusterIP target, so every scrape lands on one pod and the rate and request panels undercount; the same flaw was fixed for objectgw in w21/m417.

- **Source:** the post-deploy check of w21/m417's fixes on production, 2026-11-15 (pin `c98a0ef59766`). The `bex-api` job has one static target, `bex-api.bex-system.svc:8091`, with no `pod` label. Reading `bex_api_http_requests_total` from each pod over three samples gave pod A 264, 286, 309 and pod B 278, 310, 338, while Prometheus read 279, 306, 337: it follows one pod only.
- **Impact today:** request and rate panels show about half the traffic. Ratio alerts are unaffected (numerator and denominator come from the same replica) and gauge alerts are unaffected (both replicas report the same value).
- **Why it is not just the objectgw change:** switching to pod discovery needs a decision first.
  - `PushDeliveryStale` reads a per-process timestamp and the push worker runs on both replicas (`lego/backend/cmd/api/main.go`, near line 1856): the replica that never delivers would trip it while the shared queue is non-empty.
  - Two Grafana panels, `sum by (state)(bex_push_queue_rows)` and `sum by (class)(bex_sandbox_live)`, would double.
  - `increase()` alerts on counters created lazily would miss the first event on each new pod (absent to 1 is not counted). objectgw avoids this because its counters start at 0.
  - `deploy/gitops/base/rules/alerts_test.yml` has 106 `job="bex-api"` references to re-check.

## Steps

1. Decide how each of the four cases above is handled (for example `max by` for the per-process timestamp, `max` instead of `sum` for the shared gauges, pre-registering the lazily created counters at 0).
2. Switch the job to pod discovery as `bex-objectgw` does, update the rules, panels and `alerts_test.yml`, and pin it in `scripts/gitops-validate.sh`.
3. On production, confirm both pods are `up == 1` targets, the panels match a sum of the two pods read directly, and no alert fires because of the change.

## Done when

- [x] Prometheus reports both bex-api replicas and the request panels equal the sum of the two pods read directly.
- [x] No alert changes behavior because of the switch (rule tests pass).

Done 2026-11-15 in `fdc224f65`, deployed by deploy.yml run 43793377096 (all four suites and the build green). Decisions for the four cases:

- **`PushDeliveryStale`** is fleet-wide: `time() - max(last success)` with the backlog read as `max` over replicas. The push queue is one table both workers drain with `SKIP LOCKED`, so the replica that loses every claim race never stamps its gauge and would have paged on a healthy fleet.
- **Shared gauges** use `max`, never `sum`: `SandboxOrphansPresent` takes `max by (class)` before adding the classes, and the push-queue, sandbox-live and push-age panels follow. Every replica's Completer recounts the whole sandbox inventory.
- **Lazily created counters:** the nine `bex_billing_operations_total{result="error"}` operations the alerts read are registered at 0 at process start (`billing.NewMetrics`), and `TestAlertedBillingOperationsStartAtZero` fails when `alerting_rules.yml` names an operation that is not registered. The billing `increase()` alerts stay per pod, since a Stripe delivery lands on one replica. The other lazily created counters behind `increase()` (webhook admissions `capped` above 100, agent-session status-read errors held for 15 minutes) need no pre-registration: a missed first event cannot change their outcome.
- **The job** discovers the Ready pods' `internal` port with a `pod` label. `scripts/gitops-validate.sh` pins the job and the Deployment's pod label and port name it keys on. The 106 `job="bex-api"` references in `alerts_test.yml` stay valid (they supply their own labels); five new two-replica tests fail against the old rules and pass against the new ones.

Production check after the deploy (kubeconfig fetched outside the repo and deleted afterwards): `up{job="bex-api"}` has two targets, both 1 (`pod` and the pod IP as `instance`); over a 79 s window the two pods read directly gave 456 and 478 requests in total against 460 in Prometheus, and 2.022 req/s against `sum(rate(...[1m]))` 2.067 (before: one pod's series only); all 150 rules evaluate healthy with the new `PushDeliveryStale` and `SandboxOrphansPresent` loaded; none of the bex-api alerts is active (the firing ones are unrelated: Watchdog, tenant-node filesystem, one custom-domain certificate); the nine billing error series exist at 0 on both pods; the three changed panel queries are in the Grafana ConfigMaps.
