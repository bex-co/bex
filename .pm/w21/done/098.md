# 098 — A subscription bex's own reclaimer cancels is treated as a payment failure: 11 cardless workspaces were put in grace, enforced and mailed

Why: the abandoned-checkout reclaimer cancels a cardless workspace's Stripe Subscription, and the dunning reducer reads the resulting `customer.subscription.deleted` as a failed payment, so a workspace that never owed anything gets a grace notice, then an enforcement and a "compute suspended" mail.

- **Source:** the w21/m336 t004 production read, 2026-11-16 ([`finding.md`](m336/finding.md)).
- **What happened.** On 2026-10-03 07:02:41 to 07:03:07 UTC the reclaimer shipped by w3/m172 cancelled and deleted 13 cardless bex Customers. For 11 workspaces the webhook `customer.subscription.deleted` arrived while the workspace still had a mapping, and `billing/lifecycle.go:147` maps every such event to `BillingOutcomeFailure` / `subscription_canceled` (`subscriptionOutcome` at `:183` does the same for a `canceled` status). Each workspace went to `grace` (7 days), then `enforcing`, then, after the w21/m336 fix, `enforced` on 2026-11-12. Their owners were mailed a grace notice (2026-10-03) and "[bex Test Mode] Workspace compute suspended for billing" (2026-11-12). None had a payment method, a paid invoice or a resource: the reclaimer only runs when Stripe confirms that.
- **Why it can come back.** `ReclaimUnboundCustomer` (`billing/reclaim.go`) still cancels subscriptions of unbound Customers every 15 minutes, and the usage emitter, the admin `provision` action and any pre-m172 mapping can still leave a cardless Subscription for it to cancel. m172 stopped Checkout from creating one, which is why only the first pass hurt.
- **Not in scope here.** The 11 existing rows are corrected by w21/m336 t004 right after this note ships and deploys (decided by the user 2026-11-16: recover all 11 to `healthy`, accept the "Billing recovered" mail). This note is only about the reducer, so a repeat cannot happen.

## Result (2026-11-16)

Shipped as `c00960a8b` and live: `deploy.yml` run 43843835018 (commit `a82eaeec8`, pin `f33aa12f6`) finished 2026-11-16T10:17:53Z, and both bex-api replicas run the digest it pinned (`ec6a1533…`).

- **The rule.** In the store (`stripeBillingEventGuards`), a `subscription_canceled` failure for a workspace whose provider mapping never stamped `payment_method_bound_at` is retained and stamped applied but moves no state and queues no notice, unless Stripe attributed the cancellation to a failed payment or a dispute (`cancellation_details.reason` is `payment_failed` or `payment_disputed`, carried on `StripeBillingEvent.CollectionFailed`, not stored). Stripe documents `cancellation_requested` as "Canceled explicitly through the API or Dashboard", which is what the reclaimer's `Subscriptions.Cancel` produces, and `payment_failed` as "Canceled automatically after payment failure".
- **Why this and not a stamp on the Subscription.** (1) One rule covers every route into the same reason: the `customer.subscription.deleted` webhook, a `customer.subscription.updated` with status `canceled`, and the reconciler's poll of a `canceled` Subscription (`BillingSnapshot` through `subscriptionOutcome`'s `canceled` case, which would otherwise put the same workspace in grace within five minutes). A stamp is read only by the webhook normalizer, and a stamp left on a Subscription whose cancel then failed would hide a later real dunning cancellation. (2) `payment_method_bound_at` is the sole authority on payment state and is never cleared when a card later lapses (ADR046 §7), so a card-bound workspace is never ignored. (3) The two ways it could still miss a real failure are closed: Stripe's own `payment_failed` and `payment_disputed` cancellations count whatever the marker says, which covers a mapping from before the marker existed (production has none: 13 mappings bound, none cardless with a Subscription), and a Stripe cancellation after dunning is always preceded by `invoice.payment_failed` and `past_due` events, which are untouched. `subscription_incomplete_expired` is left as a failure: it is Stripe's own expiry after a first payment that failed, and m172 stopped Checkout from creating a Subscription up front.
- **Reproduced first, on a real Postgres.** `TestPGStoreSubscriptionCancellationOpensGraceOnlyForAPaymentFailure` (the store matrix: cardless reclaimer cancel, card-bound cancel, Stripe's cancel after failed collection on a cardless and on a card-bound workspace, a cardless workspace's other failures, and a replay) and `TestReclaimerCancellationOfACardlessWorkspaceOpensNoGrace` (the reclaimer's own `ReclaimUnboundCustomer` cancel against the Stripe stub, its answer fed through `Lifecycle.HandleStripeEvent`) both fail with the old reducer: the cardless workspace goes to `grace` with its deadline and one notice queued. The same two tests pass for every card-bound and Stripe-attributed case, and `TestBillingSnapshotMarksOnlyCollectionCancellations` and `TestLifecycleMarksCancellationsStripeEndedAfterFailedCollection` pin the marker for the poll and the webhook. ADR046 §7 records the rule.
- **On production, after the deploy.** The reclaimer's passes at about 10:17, 10:32 and 10:47Z opened no grace row: still 1 `grace` row (the live-mode `payment_failed` row of 2026-11-16 01:02Z), 0 new grace rows, 0 new grace notices, 0 new `subscription_canceled` event rows. Honestly, that readback shows absence of harm, not a replayed reclaim: production holds no unbound live-mode mapping with a Subscription for the reclaimer to cancel (its one unbound mapping is a test-mode leftover of an excluded workspace, which the live-mode reclaimer never claims). The cause is proven by the two Postgres tests above. The 11 existing rows were recovered the same day ([w21/m336](m336/README.md)).
