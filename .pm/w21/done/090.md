# 090 — An operator who revokes a token or consent session at Hydra has no way to make every bex-api replica refuse it at once

Why: w21/085 bounds a direct Hydra revocation at 5 s, but a direct revocation never writes the shared `oauth_revocations` row, so the bound is the best bex-api can do for it; an incident response that must cut a stolen token off now needs a path that does.

- **Source:** w21/085, 2026-11-15. Revocation through bex (`POST /v1/oauth/revoke`, the dashboard's connected-app revoke, API-key revoke) already writes the row and is refused at the next request on every replica (`lego/backend/internal/store/oauth_revocations.go`, `docs/ADR012-auth.md` §8d). An operator holding Hydra's admin API, or a client calling `oauth.bex.co/oauth2/revoke` itself, bypasses it.

## Steps

1. Decide the smallest operator path: a script (`scripts/revoke-oauth-subject.sh <subject> <client>`) that revokes the consent session at Hydra admin and writes the `oauth_revocations` row for the same pair, or a bex-api admin route behind the ops-workspace gate that does both. Pick the one that needs no new credential beyond what the operator already holds, and ship it.
2. Test it against two replicas that share the marker: a token warm on both is refused on both at the next request, with no wait.
3. Name the path in `docs/ADR012-auth.md` §8d and add a short runbook under `docs/runbooks/` for cutting off a stolen token.

## Done when

- [x] One command or one admin call revokes a human's grant at Hydra and every bex-api replica refuses the token at its next request, shown by a test and once on production.

## Result (2026-11-16)

**Decided: a pod command, not a script and not an admin route.** `kubectl -n bex-system exec deploy/bex-api -- /api revoke-oauth-grant <subject> (<client-id> | --all-clients) [--apply]`, an operator-run verb like `migrate-container-policy` and `platform-rebuild`. It needs no credential beyond the cluster access the operator already holds, because Hydra's admin API, `BEX_CP_DB_URI` and `BEX_OPS_WORKSPACE` are already in the pod's environment. A script on a laptop would need Hydra's admin API and a database password (two secrets that live nowhere on a laptop). An admin route behind the ops-workspace gate would need the operator to hold an ops member's bearer, and would put a Hydra-revoking route on the public listener protected by that bearer alone (ADR088 §4's gate is Grafana's consent ACL, not an API authorization model).

**Shipped** in `5be555762` (code: `lego/backend/internal/oauthgrant`, `cmd/api/revoke_oauth_grant.go`; docs: ADR012 §8d "Operator path", [`docs/runbooks/oauth-grant-cutoff.md`](../../../docs/runbooks/oauth-grant-cutoff.md), `lego/backend/AGENTS.md`) and a follow-up commit that dropped a stderr log line (an exec session's output never reaches the pod's log, so it would have been no record). With `--apply` it deletes the `(subject, client)` consent session at Hydra (every access and refresh token of the grant), then advances the `oauth_revocations` row of the pair, then writes an `oauth.RevokeGrant` audit row in the ops workspace's trail; Hydra goes first so no replica can cache a stale "active" newer than the marker; a Hydra failure writes nothing else. Without `--apply` it lists the subject's grants (client, scopes, time) and writes nothing. It refuses a machine credential (subject equal to client: an API key's own revoke already writes the marker) and a paged listing for `--all-clients`.

**Test** `TestOperatorRevocationIsRefusedOnEveryReplicaAtTheNextRequest` (`internal/api`): two replicas sharing the marker, once in memory and once on the real Postgres store (one `PGStore` per replica), the clock frozen so the window can never end; after the command the next request on both replicas is 401, a cold replica too; another person's token on the same client, the same person's token on another client and a token revoked at Hydra alone (the control) are still 200. `internal/oauthgrant` pins the order and the failure behavior. Mutations (no marker, marker before Hydra, marker for the wrong pair) each fail them. Full real-DB backend suite (84 packages) and `make lint` on all four modules pass.

**Production, 2026-11-16** (both pods on the image built from `5be555762`, `deploy.yml` run 43862264107, digest `sha256:cb25ba4d9ebcd7c9fda437cae6f1c3c9c21911260f6932b654b78ed6c16cd190` read on both pods). The QA user's throwaway device-flow tokens of the Render CLI client, each pod probed directly through a port-forward. Control: a token revoked at Hydra alone was still accepted on both pods at the next request (entry at most 4.2 s old) and refused 5.0 and 5.5 s after the revocation. Operator command: a warm token refused on both pods at the next request with its entry at most 3.2 s old (window still open); the command answered `hydra: "deleted"`, `marker: true`, `audited: true` in 2.0 s end to end. Refresh tokens answered `invalid_grant`, the subject's grant list was empty afterwards, and the database held the marker row and the audit row (ops workspace, caller `operator`, method `exec`). Collateral: the consent-session revoke removes every token of the pair; no other QA CLI login was live, every token was this check's own. The six audit rows (one per apply, including one whose probe script aborted after launching it) stay in the ops workspace's trail as the record of the check.

**What did not work first.** Two early rounds were not discriminating: sequential cold warm-ups (a cold request costs about half a second on production: Hydra round trip, tenant onboarding, Kratos email lookup) left the entries 4.9 to 5.7 s old at the check, so the window had expired on its own. A third showed the marker is per pair: a second token of the same pair is refused with the first, so the control had to be its own phase. Warming all pairs at once and running the control before the command gave the clean comparison above. Noted for [091](../091.md): the cold-miss cost is about 0.5 s, not tens of milliseconds, on a cache miss that also onboards.

**Cleanup.** All twelve throwaway tokens answer 401 at the edge, their Kratos sessions were logged out by the helper, no probe process or port-forward is left, and the token files, the fetched kubeconfig and the scratch scripts are deleted.
