# The create forms accept duplicate environment keys and secret-file names and silently drop the earlier value; the Edit editors refuse the same input

Why: a typo'd duplicate key in New Environment Group or New Service ships with only the last value and no warning, while the Edit editors block the identical input with "Each variable key must be unique." — the two surfaces should share one contract.

**Severity:** minor (a silently lost user-entered value, but the downstream data path is consistent and the Edit editors already block it). **Estimate:** 50m, dashboard only, no backend change. **Source:** live `/qa-find-bugs` pass 5, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (own resources, all deleted afterwards)

1. **New Environment Group** (Environment Groups → New Environment Group): name `qa-20261110-eg`, Add Environment Variable twice: `ALPHA=one` and `ALPHA=two`. Create is enabled, no error shows, toast "Created qa-20261110-eg". The group page lists one variable `ALPHA`; Reveal shows `two` (`evg-dbpgd6s5ngvc73e8to80`).
2. **Control, same group:** Edit → Add variable → Add variable, Key `ALPHA`, Value `three`. The editor shows "Each variable key must be unique." and "Save and deploy" is disabled. So the Edit surface refuses the input the create dialog accepted.
3. **New Service** (`/services/new?type=web_service`, Public Git URL `https://github.com/bex-co/bex`, root `examples/hello-go`, runtime Docker): Add Variable twice, `MESSAGE=one` and `MESSAGE=two`. "Deploy Service" stays enabled, no error. After deploy (`srv-dbpgeks5ngvc73e8tobg`):
   - GraphQL `{ envVars(serviceId:"srv-dbpgeks5ngvc73e8tobg"){ envVar { key value } } }` returns `[{"envVar":{"key":"MESSAGE","value":"two"}}]`.
   - The Environment tab shows `MESSAGE` = `two` on Reveal.
   - `curl -sS https://qa-20261110-dupcheck.onbex.co/` returns `two` (HTTP 200).
   - `one` is gone with no signal anywhere.
4. **Secret files, New Service form:** Add Secret File twice, both named `dup.txt` with contents `first` and `second`. "Deploy Service" stays enabled, no error (not submitted).

**Evidence:** `.playwright-mcp/qa-env-2.png` (gitignored, local to the hunting session: the New Service form with two `ALPHA` rows, two `dup.txt` files and an enabled Deploy Service). The API and `curl` outputs above are the durable probes.

## Root cause

- **New Service consumer:** `dashboard/src/features/services/lib/create-service-input.ts:175-203` `isSubmittable` checks each env row with `VALID_ENV_KEY.test(row.key)` and each file with `isValidSecretFileName`, never uniqueness. Its only caller is `dashboard/src/routes/services.new.tsx:124` (`canSubmit`). The row editors `dashboard/src/features/services/components/create-env-var-editor.tsx:55` (`keyInvalid`, syntax only) and `create-secret-file-editor.tsx:46` (`invalid`, syntax only) render no duplicate error.
- **New Environment Group:** `dashboard/src/features/env-groups/components/new-env-group-dialog.tsx:227-229` `contentsValid` is syntax only; `:315-320` submits both rows.
- **The backend then keeps the last one by design:** `lego/backend/internal/envgroups/service.go:490-491,517` (`prepareCreateEnv` / `prepareCreateFiles`: "Duplicate keys follow the existing replace-all semantics: the last declaration wins"). For service create, `lego/backend/internal/apps/graphql.go:269-293` `gqlEnvVarInputs` appends both entries; the runtime and every read surface agree on the last one (probed: process, Environment tab, GraphQL).
- **The refusing control already exists:** `dashboard/src/features/services/lib/environment-draft.ts:205-214` marks both rows `duplicate` (w4/139 lineage), rendered via `services.environmentDuplicateKey` = "Each variable key must be unique." and `services.secretFileDuplicateName` = "Each secret file name must be unique." (`dashboard/src/features/services/locales/en.ts:5042,5288`; zh at `zh.ts:4931,5162`). The create surfaces never adopted it.

## Fix (target behavior)

In both create surfaces, two env rows whose trimmed keys are equal, or two secret-file rows whose trimmed names are equal, mark **both** rows invalid with the two existing strings above (`aria-invalid` + `aria-describedby`, as the other row errors do) and disable the submit button (Create / Deploy Service) — the same contract as the Edit editors.

- Reuse the `environment-draft.ts:205` comparison (export a small helper) rather than writing a second implementation.
- Add the uniqueness test to `isSubmittable` (so it clears the only consumer, `services.new.tsx:124`) and to `contentsValid`.
- Backend semantics stay as they are (last declaration wins for API/MCP callers) and are **not** part of this fix.

## Blast radius

- `isSubmittable`: 1 non-test caller (`services.new.tsx:124`). That one route serves all five types (web, private, worker, cron, static), so one fix covers them.
- `CreateEnvVarEditor` / `CreateSecretFileEditor`: 1 usage each (`services.new.tsx:590` / `:594`).
- `NewEnvGroupDialog`: 2 callers, `dashboard/src/routes/env-groups.tsx:130` and `dashboard/src/features/services/components/env-groups-panel.tsx:419` (the "Create group" button on a service's Environment tab, an alias of the same dialog).
- Regression tests belong on the callers that behave correctly today: distinct keys, case-different keys (`Alpha` vs `ALPHA` stay distinct), a key duplicated only after trim, and the `.env` import path (`dashboard/src/features/services/lib/dotenv-import.ts:38-41` resolves duplicates deterministically before rows exist and must stay unchanged).

## Adjacent classes

Invalid-syntax key, empty key, duplicate-with-an-env-group-var (`env-groups-panel.tsx:487` already documents the shadowing) and over-limit rows keep their existing messages; only equal-after-trim duplicates gain a new refusal. No not-found/forbidden taxonomy is involved.
