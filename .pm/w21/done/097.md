# 097 — `scripts/fetch-app-kubeconfig.sh` needs `HCLOUD_TOKEN` already exported, so reaching production is not one command

Why: w21/089 made "run `scripts/fetch-app-kubeconfig.sh <path>`" the first step of every runbook that needs the production cluster, but the script stops with `HCLOUD_TOKEN is required` unless the caller has loaded `.env` into its environment. Workers are told never to read `.env`, so each runbook carries a `grep '^HCLOUD_TOKEN=' .env | cut -d= -f2-` recipe or a `source ./.env`, and a worker that does neither concludes it has no production access.

- **Source:** w21/089, 2026-11-16. `scripts/fetch-app-kubeconfig.sh` (the `: "${HCLOUD_TOKEN:?…}"` line near the top). `scripts/lib/env-file.sh` has `bex_load_env`, the sanctioned `.env` loader with the permission guard, which other scripts already use.
- **Care:** the script runs in CI (`app-cluster.yml`, `deploy.yml` and the drills) with `HCLOUD_TOKEN` from a secret and no `.env`, and `app-cluster.yml` lists the script in its `paths`, so a change to it starts that workflow once.

## Steps

1. In the script, when `HCLOUD_TOKEN` is unset and `.env` exists at the repository root, load it through `bex_load_env` before the check. An exported token wins and is left alone.
2. Cover it in `scripts/fetch-app-kubeconfig.test.sh`: token unset with a `.env` loads it; token set is untouched; unset with no `.env` gives the same `HCLOUD_TOKEN is required` error; a group-readable `.env` is refused by the guard.
3. Shorten the runbook lines w21/089 wrote (the production bullet in `AGENTS.md`, `deploy-app-from-local`, `rt-fix-prod-crashes`, the ADR036 prerequisites) to the bare call.

## Done when

- [x] `bash scripts/fetch-app-kubeconfig.sh <path>` works from a checkout that has only `.env` and `~/.ssh/bex`, and CI's call is unchanged.

## Done (2026-11-16)

- **Script.** `scripts/fetch-app-kubeconfig.sh` reads the repository-root `.env` (resolved from the script's own location, not the cwd) only when `HCLOUD_TOKEN` is not exported, through `bex_load_env`, so the permission guard applies. `bex_load_env` exports every assignment, so each value is read in a subshell and assigned as a plain shell variable: nothing else in `.env` (S3 keys, `KUBECONFIG`, proxy settings) and not even the token reaches `curl`, `ssh` or `kubectl`. Besides the token it takes the script's own two other inputs when they are still unset, `BEX_SSH_PRIVATE_KEY_FILE` and `BEX_SSH_KNOWN_HOSTS_FILE`, because `.env.example` names them as the local settings for this script and the pin is stricter than trust-on-first-use. An exported token wins and `.env` is not read at all, so CI's call is unchanged. No token and no usable `.env` gives the same `HCLOUD_TOKEN is required` error.
- **Tests.** `scripts/fetch-app-kubeconfig.test.sh` runs a copy of the script inside a fake repository from an unrelated cwd that has its own decoy `.env`, with dummy tokens: an unset token is loaded, an unrelated variable and the token do not reach the children, an exported token wins over a different `.env` and over a 0644 `.env`, no token and no `.env` (or an empty one) gives the error with no API call, a 0640, 0644 or 0604 `.env` is refused with the fix named and no API call, and `.env`'s key and known-hosts file are used only when unset. No run's output carries a token. Six mutations of the script (export the token, read the cwd's `.env`, source the whole file, always load, ignore a set value, source without the guard) are each caught.
- **Runbooks.** `AGENTS.md`, `rt-fix-prod-crashes`, ADR036's prerequisites, `docs/runbooks/oauth-grant-cutoff.md`, `docs/runbooks/operator-kubeconfig-isolation.md` and the parked `w21/blocked/091.md` now carry the bare call; ADR019 records the rule. `deploy-app-from-local` was retired before this item ran, so there was nothing to shorten there.
- **Live.** From this checkout with `HCLOUD_TOKEN` not exported, `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>` wrote a 0600 kubeconfig and `kubectl get nodes` listed 16 nodes, all Ready; the kubeconfig was deleted afterwards.
- **Not done.** The script itself is not in `scripts.yml`'s shellcheck list: `github-actions-validate.sh` fails any workflow that names it without the `BEX_SSH_KNOWN_HOSTS` pin. It is clean at `--severity=warning` locally.
