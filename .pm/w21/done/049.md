# On a static site that has already published once, changing the publish directory to one that does not exist leaves the deploy `update_in_progress` for 18 minutes and then closes it `update_failed` with "the deploy did not become healthy within the health-gate window; check the service logs" — on a first publish the same typo closes `build_failed` in about 45 seconds with the plain sentence

Why: a person who mistypes the publish directory of a live site sees a deploy "In Progress" with a log that stops at "Building from …" and no error for 18 minutes, then a reason about health gates and service logs that a static site does not have.

**Severity:** major (the two most common static-site mistakes on an existing live site — a typo in the publish directory, and a build that succeeds but does not produce it — hang the deploy, hide the cause behind a sentence that cannot apply to a static site, and delay the failure event and notification by 18 minutes; the old site keeps serving, which is why it is not a blocker). **Estimate:** 50m (one more read in `observedDeployStatus` plus a test for the republish case). **Kind:** **regression** of [w4/m155](../w4/done/m155/README.md) (done 2026-10-04) and [w4/493](../w4/done/493.md) (done 2026-11-05): m155 required that a replacement publish over a live release reaches a terminal state with the specific missing-directory reason while the old release keeps serving; w4/493 then changed the missing directory from `update_failed` to a user-source `build_failed` recorded through `r.fail`. Its tests (`app_controller_static_publish_failure_test.go`, `publish_test.go`) assert what the **operator** records, never that bex-api closes the row. **Source:** live `/qa-find-bugs` pass 56, 2026-11-11 02:4x UTC (2026-11-10 local), extended by pass 57 (03:xx UTC, steps 4–5 and the verified-unaffected list below), production `https://dashboard.bex.co`, workspace `bex`, pin `a0d5802594e9`, filed to w21 per user direction; method: a static-site publish-directory journey, first publish versus republish over a live release. **Status:** inbox.

## Root cause (code-traced; the live CR could not be read, no cluster access; consistent with the observed 18 m 46 s and the exact sentence)

- The operator records a user-source publish failure through `r.fail(…, BuildFailedUserError, …)` (`lego/operator/internal/controller/app_controller.go:4490`, introduced by w4/493). Because `releaseHasServed(app)` is true, `r.fail` records the verdict in the **Build** condition and keeps the phase Running through `settleFailureOverPriorRelease` (`app_controller.go:6697-6714`, `:6771`). A first publish has nothing served, so it takes the `PhaseFailed` branch (`:6716`) instead.
- bex-api reads that verdict in two places, and neither fits a static row in `update_in_progress`:
  - `observedDeployStatus` (`lego/backend/internal/store/reconciler.go:1505`) maps `PhaseFailed` plus a build-failure reason to `build_failed` (`:1590`), but has no conclusion for `PhaseRunning` while the row's release is not yet active (`:1573-1577` falls through to `if !timedOut { return "" }`).
  - `recordedBuildFailure` (`:1863`) is consulted by `supersededDeployStatus` only under `isBuildPhase(open.Status)` (`:1770`; `:1360` = created, queued, build_in_progress), while a static site's row moves to `update_in_progress` once the publish begins.
- The older path that closed this row promptly, `recordedRolloutFailure` (`:1131`, called at `:1537`), reads only the **Rollout** condition, which `failPublish` wrote before w4/493 (`app_controller.go:4506`; `Rollout=False/PublishFailed` in the w4/m155 capture) and `r.fail` does not.
- The `extract` exit shares the branch. A built image that lacks the publish directory (`lego/operator/internal/publish/publish.go:327`) is the same `obs.UserError` result (`app_controller.go:4484-4490`), so it takes the same `r.fail(BuildFailedUserError)` path as the clone exit and is left to the same gate when a release has already served (reproduction steps 4 and 5). One cause, two exits; the fix covers both.
- So nothing closes the row until `defaultDeployGateTimeout = 18 * time.Minute` (`:121`), and `timedOutDeployStatus` (`:1848`) answers `update_failed` with the generic sentence at `:2078`.

## Fix (target behavior)

Over a served release, a user-source publish failure closes the row `build_failed` at the next observation pass — within seconds, as the first publish does — with the Build condition's own sentence (`the publish directory "…" does not exist in the repository at "<sha>"`), `build_ended` reporting `failed` (w4/505's `withholdBuildEndedWhilePublishing` already maps `build_failed` to failed), the prior release still serving, and the header "Service Running · Latest deploy Failed".

Smallest change: in `observedDeployStatus`, after the `recordedRolloutFailure` check (`:1537`), also return `DeployBuildFailed` when `recordedBuildFailure(app, open.Generation)` holds for a row that is already past the build phase (a static publish). `deployCloseFailureReason` (`:1072-1075`) already reads the Build condition for `build_failed`, so it supplies the message. The alternative, having `r.fail`'s served-release branch also set the Rollout verdict as `failPublish` does, would close the row `update_failed` and contradict w4/493's `build_failed`.

The target applies to both exits that report a user-source error — the clone exit (a missing directory in the repository) and the extract exit (a missing directory in the built image) — and therefore to a native static build and to a Dockerfile-built static site alike. The sentence is each exit's own (`… does not exist in the repository at "<sha>"` or `… does not exist in the built image`).

Consumers to check: `deployCloseFailureReason` and `withholdBuildEndedWhilePublishing` (events), the notification worker's deploy-failed trigger, and the dashboard header.

## Blast radius

- `observedDeployStatus` is the single mapping for every service type, so the new branch must be limited to a Build verdict attributed to the row's own generation (`recordedBuildFailure` already requires `ObservedGeneration == generation`).
- **Verified unaffected over a live release (pass 57), so the change must stay narrow and these become regression-test cases.** Each closed promptly, the URL answered 200 throughout, and the header read "Service Running · Latest deploy Failed":
  - Docker web service `qa-20261110-wf` (`srv-dbptg2vbq3ic73c0aagg`, `examples/hello-node`, live `dep-dbptg2vbq3ic73c0aah0`), missing Dockerfile path `nope/Dockerfile`: `build_failed` in 27 s, `build failed in the source checkout step: the Dockerfile "examples/hello-node/nope/Dockerfile" does not exist in the repository at "c4167a31…"`.
  - Same service, missing Root Directory `nope-dir`: `build_failed` in 39 s, `the root directory "nope-dir" does not exist in the repository at …`.
  - Same service, a start command that exits at once (`sh -c 'echo qa-crash; exit 1'`): `update_failed` in about 90 s, `container exited shortly after start and is restarting repeatedly (last exit code 1) — check the service logs for the crash output …`. The deploy page showed the `qa-crash` lines and then `==> Deploy failed: …`, and `GET /v1/logs?text=qa-crash` returned both lines.
  - Native static site `qa-20261110-sb`, a failing build command (`echo qa-build-boom; exit 3`): `build_failed` in 66 s, `build failed in the docker build step: … error: build command 'echo qa-build-boom; exit 3' exited with code 3`.
  - So the hang is specific to a user-source failure detected in the static **publish** step (clone or extract) over a served release; build-phase failures and web rollouts close promptly.
- Further regression tests: a first static publish (both exits), and a superseded row.
