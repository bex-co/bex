# 105 — A Postgres export download leaves no audit row, though Render records DownloadDatabaseBackupEvent

Why: Render's audit log records the download of a Postgres logical backup (`DownloadDatabaseBackupEvent`), but bex's `GET /v1/postgres/{id}/export` presigns a download URL for every available export and records a row only when it refuses the caller, so an admin cannot see that a whole database was taken. Render parity is the top product principle.

- **Source:** w21/094, 2026-11-16. Reading render.com/docs/audit-logs to confirm that Render has no object-storage event, the page lists `DownloadDatabaseBackupEvent` ("a Postgres logical backup was downloaded") and `DocumentDownloadEvent` as Render's two downloads of customer data, beside `ViewEnvVarValuesEvent` and `ViewConnectionInfoEvent`. Both names are in the pinned `auditLog.event` enum (`lego/backend/internal/api/openapi/render-public-api-1.json`). A search of `lego/` and `docs/` finds neither name outside that enum, so bex maps neither.
- **Facts:** `postgres.Service.ListExports` (`lego/backend/internal/postgres/recovery.go`) gates on `can_view_sensitive` and presigns each available row into a fresh 15-minute bearer URL (its comment says why: a dump is the entire database). `can_view_sensitive` is a read relation, so `core.readRelations` records the denial and no success. It is reached by REST `GET /v1/postgres/{id}/export`, GraphQL `databaseExports` and MCP's list-exports tool. w21/094 added the object store's download row (`core.RecordObjectViewed`) and made the rows that record a success a closed set, `core.auditedViews` (`lego/backend/internal/core/audit_object.go`); this would be the next member, with its own ADR line.
- **Unknown:** what triggers Render's event: a list that returns the URL, or the user's download. Render's list response carries the URL, as bex's does. The docs say only that the backup "was downloaded".

## Steps

1. Read Render's docs and OpenAPI for what records `DownloadDatabaseBackupEvent`, and decide the bex trigger that matches it with the fewest rows: one row per request that returned a URL is the default, as for `ViewConnectionInfoEvent`.
2. Add the verb to `core.auditedViews` (the pin tests in `core` and `api` fail until it is listed), record it once the URLs were minted (the `RecordSecretsViewed` shape, `metadata.database`), map it to `DownloadDatabaseBackupEvent` in `audit.renderEvents`, and cover it in `internal/audit` and the route sweeps.
3. Record the decision in ADR006 § Audit log and `docs/render-artifacts/audit-logs-api.md`.

## Done when

- [x] A successful `GET /v1/postgres/{id}/export` that returns a download URL writes one audit row that REST reports as `DownloadDatabaseBackupEvent`, a refused one still records its denial, and the three surfaces agree.

## Result

DONE 2026-11-16 in `58ef086ab` (deploy.yml run 44016317167, dispatched, success; pin `58ef086ab21d` in `7a8203c3b`, and both bex-api replicas run the pinned controller digest `sha256:b1502d349125`, the dashboard pod the pinned `sha256:449c62427ba0`).

- **Decision 1: the trigger is the request that returned a URL, once per request.** render.com/docs/audit-logs (read today) says only "A logical backup of a Render Postgres database was downloaded", for primary instances only, with no metadata keys, and does not say whether the click or the link request triggers it. bex's download is a presigned object-store URL (15 minutes, bytes from the object store, no bex download endpoint exists), so the one moment bex-api sees a download is the list that mints it: a row at "download time" is not observable, and a bex-side redirect would add a hop and a second bearer to a URL Render returns directly. `postgres.Service.ListExports` (REST `GET /v1/postgres/{id}/export`, GraphQL `databaseExports`, MCP `list_postgres_exports`) records `postgres.DownloadDatabaseBackup` through `RecordSecretsViewed` once the URLs were minted: one row however many URLs the list returned, none for a list that returned none (nothing exported, running, failed, expired, or the signer failing), the fourth member of `core.auditedViews`. REST reports `DownloadDatabaseBackupEvent` with `metadata.database` (the `dpg-` id) and `targetName`; the URL, signature, object key and export id are never stored. A refused list is the denial it recorded before (`postgres.ListExports`, `metadata.outcome: denied`), and the fresh `can_view_sensitive` check still runs before any URL is signed.
- **Decision 2 (found while checking the premise): GraphQL decides by selection, or the dashboard would flood the log.** The Recovery tab polled `databaseExports` every 25 seconds with `url` selected, so one row per request that returned a URL meant a row about every 25 seconds (about 3,500 a day) for each open tab, for a download no one made, and a bearer URL to the whole dump minted every poll. As the env var list does with `value` (w4/m321), `databaseExports` now mints and records only for a query that selects `url`; the poll selects no `url`, and the Download button runs a new `DatabaseExportLinks` query when pressed (`network-only`, one press is one URL and one row; a missing link toasts "no longer available" and refreshes the list; the eight locales carry the two new strings). Written into ADR006 § Audit log, `docs/render-artifacts/audit-logs-api.md`, ADR009, ADR018's audit row and `postgres-exports.md`.

Service tests (`internal/postgres/export_audit_test.go`): the three surfaces write the same row, several URLs are one row, nothing-to-download cases (no export, running, requested, failed, expired, past the deadline) record none, a failing or missing signer records none, a refusal and a stale-positive refusal record no download and mint no URL, and GraphQL records for `url` plain, aliased, in a fragment and in an inline fragment but not for the status fields or `urlExpiresAt` alone. The pin tests in `core` and `api` and the `audit` vocabulary and enum tests list the fourth verb. Dashboard: the poll's document selects no `url` (read from the generated AST), the download query does, pressing Download asks `network-only` and hands the link to the browser, an expired link and a failure toast. Eleven backend and five dashboard mutations (no row, a row without a URL, a row per URL, a row before the mint, the URL in the row, GraphQL still minting for a poll or for `urlExpiresAt`, the verb out of `auditedViews`, no Render mapping, the fresh check skipped, the pin set short, the poll selecting `url` again, the download query without it, a button that asks for nothing, no download opened, a cached link) each fail a test. `make lint` (four modules), the full real-Postgres backend suite and the dashboard's `yarn lint` and `yarn test` are green.
