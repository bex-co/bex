## Objective

No code path of `bex s3` runs another program, and the commands that did are gone.

## Context

- ADR112 D3 (the command) and the user's instruction of 2026-11-20 that no reference to the other tool remain. Today `lego/cli/internal/s3/launch.go` (`awsArgv`, `childEnv`, `execAWS`), the `s3api` command in `s3.go`, the bex-owned config files that `session.go` and `tools.go` write, and the missing-tool error are the launcher; `lego/cli/s3_contract_test.go`, `lego/cli/disclosure_test.go`, `lego/cli/telemetry_coverage_test.go`, `lego/cli/internal/telemetry/telemetry.go` and `lego/cli/main.go` mention it.
- ADR113 D7's coverage contract treated the launcher as a process replacer (`processReplacers`, with `telemetry.EmitLaunch` before the process is replaced). The native commands do not replace the process, so the entry goes and the commands emit through the ordinary path; read `telemetry_coverage_test.go` and keep the contract green for every new command.
- `scripts/cli-analytics.sql` maps `s3` and `s3api` to the `data` family: drop `s3api`, keep `s3`, and say in the task's notes that production's view needs `scripts/cli-analytics-bootstrap.sh` run again (it needs credentials the worker may not have; if it cannot be run, file the one-line follow-up).
- A name bex does not define answers `unknown command` and points at `bex s3 env`.

## Steps

1. Delete the files and symbols; run `go build ./... && go vet ./... && go test ./...` in `lego/cli`; run the whole-program dead-code lint (`make lint` over the four modules, as m499 did) for what the removal strands.
2. Run `git grep -n -i -w -e aws -e s3api -- lego/cli scripts/cli-analytics.sql` and clear every hit that says bex runs or wraps another tool (the SDK's import lines and its module names are expected).
