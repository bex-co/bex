## Objective

The failing case of 2026-11-20 works: `bex s3 ls` on a machine with no AWS CLI, and every verb after it, on production.

## Context

- Build `bex` from the tree and run it with a PATH on which `command -v aws` finds nothing (the case that failed). Production access: `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>`; the QA user's device login for the key (`bash scripts/qa-login.sh`). Own throwaway workspace and bucket, removed after; `bex-canary`'s S3 reads are refused until 2026-12-01 (its egress budget was spent by the earlier walks): never raise the budget or touch the kill switch to get around it. Never print a key secret, a signed URL, a token or kubeconfig content.
- Walk: `ls` of the buckets, `mb` in `oregon` and `frankfurt`, 0 B, 1 B, 20 MiB and 1 GiB round trips byte-identical by sha256, `sync` up then again (zero copies) then `--delete`, `mv`, `rm --recursive`, a `presign` fetched with curl and its refusal after the key's expiry where that can be observed, a CORS and a lifecycle round trip, ten concurrent commands on an empty key cache making one key, a transfer that outlives nothing, the refusal messages for a quota and for a revoked key.
- Record what was observed, dated, as one block in ADR112 § Not verified ("bex, settled 2026-11-2x live through the native `bex s3`"), including what was not run. A defect: fix it, redeploy (`gh workflow run deploy.yml --ref main` after checking nothing is running or queued; seven old `queued` runs from October and early November do not block), and re-walk it.

## Result

Walked 2026-11-20 on production (pin `f797f525f5df`, server unchanged) with `bex` built from the tree, on a machine with no other S3 tool (`command -v aws` empty, `PATH` an empty directory, isolated `HOME`, headless device login). The record, with what was not run and what was spent, is in ADR112 § Not verified, "bex, settled 2026-11-20 live through the native `bex s3`". Every verb of ADR112 D3 ran: `ls`, `mb` (both regions), `cp` (0 B, 1 B, 20 MiB and 1 GiB round trips byte-identical by sha256, no temporary file left), `mv`, `rm --recursive`, `sync` (a second run copies nothing, up, down and between prefixes; `--delete`; an older local file copied again), `rb --force`, `presign` (fetched with curl; 403 `InvalidAccessKeyId` after the key that signed it expired), `cors` and `lifecycle` (set, get, delete), `info` (bucket and object), `env`, `keys create|list|revoke`, `public enable|status|disable`, a persistent key from the environment with no login, ten concurrent commands on an empty key cache making one key, a revoked key's refusal message and the live `QuotaExceeded` message. Every fixture is gone (buckets removed, keys revoked, device token and sessions logged out).

- **A finding, not a defect:** the walk's 1 GiB download took `tian-personal`'s month-to-date egress (4.46 GB left by the 2026-11-19 walks) past its 5 GiB budget, so its S3 reads are refused until 2026-12-01, like `bex-canary`'s; no budget was raised and the kill switch was not touched. The user's instruction to use a throwaway workspace could not be followed to the letter: creating a workspace needs a payment method (`workspaceCreationPolicy` answers `paymentRequired: true` for `hobby`), so the read-dependent checks ran in `bex` with a few bytes and its own bucket. Reported in the run's notes.
- No server defect, no redeploy, and `scripts/cli-analytics-bootstrap.sh` was not needed: a teammate's `25725a13b` put `s3api` back in the view's `data` family because launchers before v0.9.0 still report it.
