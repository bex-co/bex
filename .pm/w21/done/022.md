# Webhook enabled/disabled state: the detail header's status link is named "Status" whatever it shows, and the list row, settings card and header tooltip print the backend's raw English reason ("disabled manually") in both languages

Why: a screen-reader or voice-control user cannot learn or say a webhook's state from its header, and a Chinese-language user sees lowercase English backend text beside the Enabled switch.

**Severity:** minor (accessible name and copy, no functional loss). **Estimate:** 30m (two independent UI fixes in `features/webhooks/components`, en/zh strings and tests). **Source:** live `/qa-find-bugs` pass 16, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (own endpoint `qa-20261110-hook`, `whk-dbpjd4c5ngvc73e8tt6g`, URL `https://qa-20261110.invalid/hook`, event Branch Deleted; deleted afterwards)

1. Create it at `/webhooks/new` (lands on `/webhook/whk-dbpjd4c5ngvc73e8tt6g`). The header badge link is `<a aria-label="Status" href="/webhook/…/settings"><span data-slot="badge">Enabled</span></a>`.
2. **Finding 1.** Chrome's own accessibility tree (CDP `Accessibility.getFullAXTree`) names that link `Status`, with no description. On Settings, switch Status off (it saves at once; the form's "Save changes" stays disabled): the same link now has visible text `Disabled`, and its AX name is still `Status`. In `?lang=zh` it is `aria-label="状态"` over the visible `已禁用`. The state is therefore absent from the header for assistive technology, and "click Enabled" (voice control) cannot find the link. The switch lower in the page is named `Status` and exposes `checked`, so the state is reachable there, not in the header.
3. **Finding 2.** With the endpoint disabled: `/webhooks?lang=en` row cells are `[endpoint+url, "Branch Deleted", "Never sent", "disabled manually", …]`, a lowercase string beside the switch; the Settings card shows the same string in a red paragraph; the header badge's tooltip is `title="disabled manually"`. In `/webhooks?lang=zh` the cells are `["…", "分支已删除", "从未发送", "disabled manually", ""]` and the zh header badge title is still `disabled manually`: everything around it is Chinese, the reason is not.
4. Re-enable from Settings: the header reads `Enabled`, the reason disappears everywhere. Then delete with the typed phrase `sudo delete webhook qa-20261110-hook`; `{ webhookEndpoints { id name } }` returns `[]` and `webhookEndpoint(id:"whk-dbpjd4c5ngvc73e8tt6g")` answers `NOT_FOUND`.

**Evidence:** the AX-tree reads and the cell texts above are the durable probes; nothing remains on the account.

## Root cause

- **Finding 1:** `dashboard/src/features/webhooks/components/webhook-detail-header.tsx:48` `aria-label={t("webhooks.settingsStatus")}` ("Status", zh "状态", `locales/en.ts:902`, `zh.ts:887`) replaces the link's content, which is the badge text (`:54-56`, `webhooks.enabledBadge` "Enabled" / `disabledBadge` "Disabled", zh 已启用 / 已禁用). WCAG 2.5.3 Label in Name and 4.1.2 Name, Role, Value. The badge's `title` (`:52`, the reason) is not part of the link's name either.
- **Precedent in the same app:** the service header link is named `Latest deploy: Live` (`dashboard/src/features/services/components/service-detail-header.tsx:135`, `` `${t("services.headerLatestDeploy")}: ${…}` ``), so the visible state is inside its name. [w4/466](../w4/done/466.md) (done) fixed the same class for the Rollback button; its scan covered 10 pages and not the webhook detail.
- **Finding 2:** the backend writes two fixed English strings, `lego/backend/internal/webhooks/service.go:717` (`"disabled manually"`, a user toggle) and `lego/backend/internal/webhooks/worker.go:119` (`"disabled automatically after repeated delivery failures"`, the auto-disable path), served as `disabledReason` on GraphQL (`graphql.go:39`). The dashboard prints the string verbatim: `webhook-row.tsx:107-112` (visible text and `title`), `webhook-settings-card.tsx:210-212` (`text-destructive`, red, even though the user's own toggle caused it) and `webhook-detail-header.tsx:52` (`title`). Mapped without translation in `hooks/use-webhooks.ts:42` and `hooks/use-webhook.ts:24`.

## Fix (target behavior)

1. **Name contains the visible state:** the header link's accessible name is the Latest-deploy shape, `Status: Enabled` / `Status: Disabled` (zh `状态: 已启用` / `状态: 已禁用`), still pointing at Settings. Compose it from the existing keys at the call site; do not change `webhooks.settingsStatus`, which is also the Settings card's own label (`webhook-settings-card.tsx:205`).
2. **Reason in the viewer's language:** the UI shows a translated reason for the two known server strings, and the raw string only for an unknown one (never hidden). A manual disable may show no reason at all, since the user has just toggled it and the switch already says so; the destructive red is for the auto-disable case only. A stable `disabledReasonCode` field is the cleaner long-term shape, but it would touch REST, GraphQL and MCP and is a separate follow-up, not a gate for this fix.
3. UI only for items 1 and 2; no API change.

## Blast radius (counted by grep on the working tree)

- Finding 1: one link (`webhook-detail-header.tsx:45-58`), rendered on both detail tabs (Activity and Settings). The existing test `dashboard/src/features/webhooks/components/__tests__/webhook-detail-header.test.tsx:59` asserts `getByRole("link", { name: "Status" })`, so it pins today's name and must change with the fix.
- Finding 2: 3 render sites (`webhook-row.tsx`, `webhook-settings-card.tsx`, `webhook-detail-header.tsx`) and 2 mapping hooks. The backend tests (`worker_test.go:977-978`, `service_test.go:827`) pin the English strings, so they stay as the wire contract; the translation lives in the dashboard.
- Class scan: on 24 routes (Overview, Blueprints, Agents, Automations and its create form, Env Groups, Webhooks, Webhooks/new, both webhook tabs, Notifications, Billing, Workspace Settings, account Settings, the service tabs, one Postgres and one Key Value) the elements with an `aria-label` that does not contain their visible text are: comboboxes and buttons that display their current value (allowed by 2.5.3, as w4/466 also found), the `Search ⌘ K` button whose name is `Search`, and this link. So the webhook header link is the only real violation found.

## Adjacent classes

- Viewers without manage rights see a Badge instead of the switch in the row (`webhook-row.tsx:93-105`, the `canManage` branch) and the same reason text; the translation applies there too.
- Not an authorization matter.
