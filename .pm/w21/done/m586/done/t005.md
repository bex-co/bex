## Objective

A new database's status (`creating` → `available`) reads the same on REST `GET /v1/postgres/{id}`, GraphQL, MCP `get_postgres` and the dashboard, with no bex-only extension-wait state left on any surface; compare with Render's create flow and flag drift as follow-up work.

## Acceptance criteria

- [x] Each surface checked on one new database; drift filed or none found.

## Result (2026-11-24)

- **`qa-m586-new-pg18` (disposable), created 01:45:05Z.** A poller read REST `GET /v1/postgres/{id}`, GraphQL `database { status statusReason statusReasonCode }`, MCP `get_postgres` and the operator's Database together, every ~1.5 s. All three API surfaces read `creating` with no `statusReason`/`statusReasonCode` until +58.2 s, then `available` in the same poll. The operator's Ready turned `Provisioned` at +55.2 s. The dashboard's detail page, open throughout, showed the badge `Creating` from 01:45:18Z and `Available` at 01:46:03Z (+58 s). Its page never mentioned an extension. `qa-m586-new-pg13` (disposable) read the same on REST, GraphQL and MCP (`creating` → `available` at +78 s).
- **Against Render:** `creating` and `available` are Render's `databaseStatus` values for a create (`lego/backend/internal/core/datastore_status.go`). The first provision's `Restarting` Ready reason maps to `creating`, not `config_restart`. No bex-only state shows on any surface: `InitializingExtensions` never fired, and `ExtensionsFailed` is reachable only where the preinstall stays (an upstream image after a rollback). No drift was filed.
- **Ledger drift fixed:** ADR018's Postgres CRUD row still said a new database's first `available` waits for its preinstalled `vector` (w4/m223). It now records the measured `creating` → `available` and where that wait stays.
