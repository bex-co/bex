# A failed native build's failure reason names the wrong step and quotes bex's own toolchain layers instead of the build command's failure: `build failed in the build environment step:` followed by `#16 extracting sha256:…` BuildKit lines, with no command output, no exit code

Why: w4/m324 made a native build's log read like Render's, but the failure summary that the deploy banner, REST `failureReason`, the `deploy_ended` event and the failure email carry now says bex's "build environment" failed and prints bex's yarn/pnpm layers, while the user's own error (`error: build command … exited with code 3`) is only in the log above it.

**Severity:** major (every failed native build — Node, Python, Ruby, Go, Rust, Elixir, native static — gets a summary that blames the platform and hides the cause; the log still has the right line, so it is not a blocker). **Estimate:** 1h (find why the failing step's verdict is missing from the captured termination message, fix it, add a test on a real-size transcript). **Kind:** gap in the guarantee of w4/m324 t002 ("the failure reason … quote the command's output without BuildKit's elapsed-time prefixes") — m324's live replay (t004) is still pending, and its unit tests feed `EnsureBuild` a synthetic termination message, so they cannot see this. **Source:** live `/qa-find-bugs` pass 122, 2026-11-11 20:1x UTC, production `https://dashboard.bex.co`, workspace `bex`, deploy pin `9126d59d7` (`8330744bd643`, contains `a9c016955`), bex-api rolled at 20:08:53Z, filed to w21 per user direction. **Status:** superseded by w4/m324 t009 (not implemented here).

## Root cause (code-traced on `origin/main` at `a9c016955`; the live pod's termination message was not read, no cluster access — cause unverified)

- The reason is built in `failureDetail` (`lego/operator/internal/build/build.go:813`, one caller, `:727`). For the buildkit container it reads `Terminated.Message`, runs `nativeCommandFailure` (`:834`, defined `:875`) and `buildkitFailureSummary` (`:916`), keeps the last 800 bytes (`failureTail`, `:959`), and names the step "build command" only if BuildKit's verdict `process "…" did not complete successfully: exit code: N` is in that message (`named`), otherwise "build environment" (`:841`).
- The message is written by `bex_run` (`classifyPrelude`, `:152-171`): `tail -c 4096 "$bex_log" > "$bex_message"`, with `bex_message=/dev/termination-log` set by `nativeLogDisplay` (`:188`).
- What came back ends at `#18 …ADD --link … pnpm` (the same point in both runs, 757 and 799 characters), which is before the failing `RUN` step and its verdict. So `named` is false and the 800-byte tail is bex's own toolchain layers, exactly what m324 meant to hide. The log's `error: build command … exited with code 3` line comes from the live stream through `bex_display`, which is why the log is right and the summary is wrong.
- Not distinguished without the pod: the kubelet returning a different window than the file's tail, or `$bex_log` not holding the failing step's output when it is copied. Check: read `status.containerStatuses[buildkit].state.terminated.message` of a failed native build Job pod and compare it with the container log.

## Fix (target behavior)

A failed native build's `failureReason` reads `build failed in the build command step:` then the command's output as it printed it, then `error: build command '<cmd>' exited with code N`, with no `#N` lines, `sha256:` digests or `/opt/bex` paths. One value feeds REST, GraphQL, MCP, the `deploy_ended` event, the deploy banner, the log's `==> Build failed:` narration and the failure email, so the operator change is enough; nothing else needs to move.

## Blast radius (counted by grep on `origin/main`)

- `failureDetail` has 1 caller (`build.go:727`); `nativeCommandFailure` has 1 caller (`:834`); `bex_message` is set in 1 place (`:188`) and read in 1 (`:161`).
- Every native runtime shares the buildkit phase (Node, Python, Ruby, Go, Rust, Elixir, native static builds); Docker-runtime and buildpack builds do not set `bex_message`, so they are unchanged.
- The same message feeds `platformFetchFailure` (`:844`), which classifies a toolchain fetch failure; a fix must keep that classification (it needs the early-step lines this bug shows).

## Adjacent classes

- A failure in the toolchain around the command (the pnpm `ADD`, the env loader) is legitimately "build environment" and keeps that name.
- A transient platform fetch failure is retried and classified before this summary exists.

## Unverified (not probed this run)

- The live pod's termination message (the mechanism above is a hypothesis).
- Python, Ruby, Go, Rust, Elixir and the native static build; the failure email and the zh banner.
- Whether a build command that prints more than 4 KiB changes the shape.
