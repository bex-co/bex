## Objective

Add one small JSON corpus per family and a Go test per family that asserts the real server validator's verdict on every entry.

## Context

- Location proposed: `lego/backend/testdata/validation/<family>.json`, an array of `{ "input": …, "valid": true|false, "why": "…", "serverOnly": false }`. The dashboard already reads backend files from its tests (`dashboard/src/test/go-source.ts`), so this follows an existing pattern. t001 may move it; the corpus must stay under 1 MiB (the repo bars larger blobs).
- Boundary inputs each family needs: zero-padded numbers (`10.0.0.0/024`), a trailing dot, a punycode TLD, a wildcard, the exact length limit and one over, multibyte text at a byte limit versus a code-point limit, control characters (NUL, BEL, newline), and leading or trailing space.
- `valid` is the author's expected verdict. Where the real server disagrees, the entry is pinned to the server's behavior and `why` says so; the question of whether the server should change is a Render-parity follow-up (see the milestone's open decision), not part of this task.

## Steps

1. Write the corpus for each chosen family.
2. Write one Go test per family (in the package that owns the validator) that loads its file and asserts the verdict for every entry, naming the entry on failure.
3. Run `cd lego/backend && go test ./...` for the touched packages.

## Files

- lego/backend/testdata/validation/*.json
- lego/backend/internal/core/*_test.go, store/*_test.go, apps/*_test.go (one test per family)

## Acceptance criteria

- [x] Each family has a corpus with the boundary inputs above and a Go test that asserts it.
- [x] Changing a server validator's verdict on any corpus entry fails the Go test until the corpus is updated.

## Out of scope

- The dashboard side (t003).
- Changing what the server accepts.
