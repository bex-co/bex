# A service whose settings are saved through `PATCH /v1/services/{id}` in the first seconds after creation never starts its first deploy: the row stays `created`, the service stays "Pending", `phase` stays empty and nothing says why — the operator holds a never-deployed service for a "pending source" that no deploy will consume

Why: a person or agent that creates a service and then sets its branch or health check path before the first build starts ends up with a service that never builds, a "First Deploy" row that never moves, no error, and a REST `undeployedChanges` that reads false.

**Severity:** major (create-then-update is the standard IaC, CLI and AI-agent sequence and bex is AI-native; REST `PATCH` and MCP `update_service` both reach it; the failure is silent and unbounded — rows were still `created` after 14 minutes — and only an extra Manual Deploy recovers; the dashboard's own Settings editors mostly mask it). **Estimate:** 1h (one condition in the operator or a re-stamp in bex-api, the deploy-row generation consumer, an envtest and a REST test). **Kind:** gap in [w8/m135](../w8/done/m135/README.md) (Render-shaped Update Service settings are saved and wait for the next deploy: the `app.bex.co/pending-source-generation` contract) for an App whose first release has not been dispatched; sibling invariant of [w4/m239/t003](../w4/done/m239/done/t003.md) ("a release the operator adopts always has a deploy row") in the opposite direction — here a deploy row exists and no release ever follows it. **Source:** live `/qa-find-bugs` pass 59, extended by pass 61, 2026-11-11 04:xx UTC (2026-11-10 local), production `https://dashboard.bex.co`, workspace `bex`, pin `a0d5802594e9`, filed to w21 per user direction; method: a race probe, a Render-shaped save landing between service creation and the operator's first build dispatch. **Status:** inbox.

## Reproduction (seventeen own Free Docker web services over two visits, all deleted at the end of their visit)

## Root cause (code-traced; the live CR could not be read, no cluster access)

- The backend marks every release-relevant Render-shaped Update Service save as saved-but-undeployed by writing `app.bex.co/pending-source-generation` to the next generation: `lego/backend/internal/rollout/rollout.go:188`, `rollout/stage.go:274-275`, `apps/service.go:4764`, `apps/deploy.go:3852`. The contract is documented at `lego/types/v1alpha1/app_types.go:71-79`. `idleTTLSeconds`, `autoDeploy` and `displayName` do not write the annotation (observed, reproduction step 8; not code-read).
- The operator's `sourceUpdatePending` (`lego/operator/internal/controller/release_identity.go:707-714`) is true while that generation is newer than the generation the deploy verbs last stamped (`app.bex.co/release-generation`). The creation's own deploy stamp is older than a save made after it.
- `prepareAppReleaseDecision` then returns `appReleaseDecision{desired: pinned, sourcePending: true}` (`release_identity.go:483`, `:497`) with the App's current fingerprints, which are empty for an App that has never dispatched a release.
- `resolveDeployImage` stops the pass: `if decision.sourcePending && app.Status.Image == "" { return "", ctrl.Result{}, true, nil }` (`lego/operator/internal/controller/app_controller.go:945`). Its comment (`:942-944`) says "a never-deployed service has no active artifact yet … Update Source must simply wait; the next deploy annotation re-enters with sourcePending=false". No build Job and no status write (phase `""`) follow, and the creation's own deploy request is not the "next deploy".
- The in-flight guard (`releaseInFlight(held) && (view != nil || releaseSourceFixed(app))`, `release_identity.go:490`) only protects a release whose build has been dispatched, which is why a save at +40 s is harmless.
- bex-api closes a build-phase row only from operator evidence (`observedDeployStatus`, `lego/backend/internal/store/reconciler.go:1505`), so the row waits for `defaultBuildGateTimeout = 125 * time.Minute` (`:95`).

## Fix (target behavior)

A save made before the first release is dispatched does not strand the first deploy: it starts within the same time as without the save, and its row reaches a terminal state. Pick one of these in one task; do not ship both:

- **(a)** bex-api treats the first deploy as consuming the save. When a Render-shaped setting is saved while the service has no dispatched release (latest deploy row `created` or `queued`, no `status.image`), it re-stamps `app.bex.co/release-generation` to the new generation and moves the row's generation with it, so the first build uses the settings as saved when it is dispatched.
- **(b)** The operator's `sourceUpdatePending` is false for an App that has never dispatched a release, so the saved settings are its first release.

Consumers to check: the deploy row's `generation` against `status.releaseGeneration` (`supersededDeployStatus`, `reconciler.go:1760`); the `source_changed` and `branch_changed` events; `undeployedChanges` (the stuck service reports false, and a service that is waiting should not); and the dashboard's "Saved changes go live when the current deploy finishes" copy ([w21/041](041.md), [w4/548](../w4/548.md)), which describes a deploy that never starts.

## Blast radius (counted by grep)

- `sourceUpdatePending(` has 2 callers (`release_identity.go:483`, `release_config_selection.go:378`); `.sourcePending` has 4 consumers (`app_controller.go:648`, `:945`, `:953`, `release_identity.go:688`); the write side has 4 sites (above).
- Entrypoints that reach it: REST `PATCH /v1/services/{id}` and MCP `update_service` (by code), the GraphQL setters that share the staging path (not probed), Blueprint sync on a just-created service (not probed).

## Adjacent classes

- A service that has served a release keeps today's contract, verified live (reproduction step 9): a save waits for the next deploy (`undeployedChanges: true`, reason `saved`), and a deploy requested just before or concurrently with the save still builds and goes live. This matches the operator's own gate, which halts only when `app.Status.Image == ""` (`app_controller.go:945`).
- The dashboard Settings health check path editor and the dashboard rename are not affected (the first creates its own `service_updated` deploy, step 5; the second is not release-relevant), so the GraphQL setter behind the editor deploys instead of staging. The stranding path is the Render-shaped REST `PATCH` (and MCP `update_service`, by code).
- A suspended service (a rolling write on one is a pending-source case, `app_types.go:71-79`) is out of scope.
- A failed first build followed by a save is [w32/003](../w32/done/003.md)'s territory.
- An env var save is not pending-source and already works (`qa-20261110-bh`).

## Unverified (not probed this run)

- The live CR state (annotations and status) was not read.
- MCP `update_service`, the GraphQL setters and Blueprint sync were not probed live. MCP shares the staging path by code; the dashboard's GraphQL editor was observed to deploy rather than stage.
- Release-relevant PATCH fields other than the four that stranded (`branch`, `healthCheckPath`, `maxShutdownDelaySeconds`, `dockerCommand`), for example `rootDir`, `buildCommand`, `dockerfilePath`, `startCommand`, `preDeployCommand`; they are expected to strand by the annotation's definition but were not each probed.
- A static site or cron job created and saved in the same window.
- Whether the window ends at the operator's first dispatch: a save at 12 s stranded, one at 40 s did not, and the build started at about 35 s.
- Render's own behavior for a save during the first deploy (no Render account).

## Render

A save made while the first deploy runs does not stop that deploy, and the deploy builds; the saved setting applies to the next one.

## Dedupe / precedent

`grep -rIl` of `.pm` for "pending-source-generation", "sourceUpdatePending" and "pending source" finds only the contract's own milestones (w8/m135 and its neighbours, w4/m239, w32/003) and no note about a first deploy that never starts. [w4/548](../w4/548.md) is about the confirmation copy for a never-live service, not the strand; w21/041 is a copy defect in a different state. Not in `DO_NOT_DO.md`.

## Definition of done (each bullet is repeatable with the probe above)

- On production, create a Free Docker web service from `examples/hello-node` with auto-deploy off and `PATCH {"branch":"main"}` or `{"serviceDetails":{"healthCheckPath":"/"}}` within 3 s: within 60 s the first deploy row reaches `build_in_progress`, by 3 minutes it is `live`, the URL answers 200, and GraphQL `phase` is no longer empty.
- The same with the branch pair `feature/ok` then `main` (the pair that stranded `-bc`).
- With an own Free Docker web service, `PATCH {"serviceDetails":{"envSpecificDetails":{"dockerCommand":"node main.js"}}}` and `PATCH {"serviceDetails":{"maxShutdownDelaySeconds":30}}` within 3 s of creation each still reach `live` within 3 minutes, while `idleTTLSeconds`, `autoDeploy` and `displayName` saves keep working.
- A save at +40 s and an env var save at +3 s still work.
- A service that has served keeps "saved, waiting for the next deploy" (`undeployedChanges: true`), and a deploy raced with a save (both orders in step 9) still goes live.
- The new tests fail if a pending source holds an App that has never dispatched a release.

**Cleanup:** the eleven services of pass 59, and the five of step 8 plus `qa-20261110-xa` of pass 61, were deleted at the end of their visits (DELETE 204, then GET 404 for each).

**Done 2026-11-11:** the operator no longer holds a first release for the save that follows creation. `sourceUpdatePending` (`lego/operator/internal/controller/release_identity.go`) is false for a service that has been requested (the creation stamped release generation 1) but has served nothing and whose build has not started (`firstReleaseReadsSavedSource`: stamp > 0, no image, no active revision, source not fixed, phase not Failed), so a branch, health check path, shutdown delay or Docker command saved within seconds of creation is part of the first release, which builds from the saved spec, writes a phase and gets a deploy row at the same generation (option (b) of the note; the first deploy is the one the save was waiting for). Once the build starts the release keeps its own source (`releaseInFlight`), a service that has served keeps "saved, waiting for the next deploy" (`undeployedChanges` true), a failed first build keeps the hold (w32/003 territory), and with no deploy requested at all Update Source still waits. `TestFirstReleaseConsumesASaveMadeBeforeItsSourceIsFixed` pins each state and fails without the change; ADR004 records the rule. The live repro (steps 2 to 8, including the seventeen services) needs the deploy and was not run; the static-site and cron-job variants, the other release-relevant PATCH fields (`rootDir`, `buildCommand`, `startCommand`) and Blueprint sync on a just-created service stay unprobed, but they share the same gate.
