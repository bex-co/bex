# 094 — An object or bucket audit row names no bucket and no key, and a successful get leaves no row

Why: w21/087 gave the object routes a verb, but a row reads `objectstorage.PutObject` on `workspace:tea-…` with an empty target, so a reader cannot tell which bucket or key was written or deleted; a successful `GetObject` writes nothing, so a download of customer bytes is invisible unless it was refused.

- **Source:** w21/087, 2026-11-16, from reading `AuthorizeWorkspaceAs` rows on production and in `TestObjectRoutesRecordAPutAndABucketCreate`.
- **Facts:** the routes authorize on the workspace before the bucket is resolved (`objects_render.go` `serve`, `cloudflare_r2.go` `route`), so the target is empty; `can_view_sensitive` is a read relation, and `core.readRelations` records only a refusal (ADR006 § Audit log), the volume rule that Render's `ViewEnvVarValuesEvent` and `ViewConnectionInfoEvent` are the exception to. Render's audit-log enum has no object event, so there is no Render behavior to match; this is a bex product decision.

## Steps

1. Decide whether a bucket name (and for put and delete, the key) belongs in the row's target, with the key bounded and never a presigned URL or a header. If yes, pass it through `AuthorizeTargetAs`-style entry and show it in REST's `metadata`.
2. Decide whether a successful get records once per request, like `ViewEnvVarValuesEvent`, and what bounds the volume for a streamed object.
3. Record both decisions in ADR112 D6 and cover them in `audit_verbs_test.go`.

## Done when

- [x] The audit log answers which bucket a put, delete or bucket change touched, and the decision on recording a successful get is written in ADR112.

## Result

DONE 2026-11-16 in `7aaa8700b` (deploy.yml run 43903148613, dispatched, success; pin `7aaa8700befa` on both bex-api replicas, image digest `sha256:49f79557434c`).

- **Decision 1: the target names the bucket, and an object row its key.** `bucket:<name>` for a bucket route, `object:<bucket>/<key>` for an object route, through the new `Base.AuthorizeWorkspaceTargetAs`, on the allowed and the denied row alike. The name is the route's path value, so no bucket is resolved before authorizing and the order is unchanged. Render's routes have no bucket in their path, so they name the workspace's system bucket (`render-oregon`), which makes both contracts read alike. REST's audit `metadata` carries `bucket` and `key`. The key is bounded to 256 bytes (`…[truncated, N bytes]`), valid UTF-8, with control, format and line-separating characters and backslashes escaped, and a signed query pasted into it becomes `?[redacted]`; nothing from a query string, header or body can enter. A bucket create names its bucket in the body, so it follows the w4/m321 create precedent: the denied row has no target and the allowed row is written once the bucket exists, so a create that failed records no allowed row.
- **Decision 2: a successful get records once per request.** `objectstorage.GetObject` is written when the bytes are handed out: Contract B once the object opened and before its first byte, Contract A once the presigned GET was minted. Not per chunk; a ranged request is one request (the route ignores `Range`); a HEAD, a list, a bucket read, a missing object and a mint the limiter refused record none; a refused get still records its denial. Why: render.com/docs/audit-logs (read today) has no object event, but it does audit the downloads of customer data it has, once per request (`DownloadDatabaseBackupEvent`, `DocumentDownloadEvent`), and bex gates a get at `can_view_sensitive`. The volume is bounded by the limiters the put's row already lives under (5 mints a second per workspace, 8 streams in flight); the looser variant (one row per caller, bucket and hour) is written into ADR112 D6 as the answer if production shows get rows drowning a log, and is not filed, because production holds 24 `PutObject` rows in all.
- **The override is closed.** `core.readRelations` is unchanged and a get's authorization still records only a refusal; the success row is written by the route (`RecordObjectViewed`), not by the authorization. The verbs that may record a read's success are one set, `core.auditedViews` (`secrets.ViewEnvVarValues`, `datastores.ViewConnectionInfo`, `objectstorage.GetObject`); `core.recordView` refuses any other verb. `TestOnlyTheAuditedViewsRecordASuccessfulRead` and `TestTheAuditedReadAllowlistIsPinned` pin it by name, and the route, tool and field sweeps still fail an allowed read that records a success under another verb.
