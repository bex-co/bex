# IP allow list forms accept CIDRs the server refuses: the environment settings dialog validates nothing (`foo` and `10.0.0.0/33` go into the list and Save), and the shared editor's `isValidCIDR` accepts zero-padded prefix lengths like `10.0.0.0/024`; both come back as a raw `"…" is not a valid CIDR` toast

Why: the shared IP allow list editor already tells the user "Enter unique, valid IPv4 or IPv6 CIDR blocks" before they save, but the environment dialog skips that, and the shared check is looser than the server's `netip.ParsePrefix` on one input class the server's own comment documents (round-21 finding 8).

**Severity:** minor (a rejected save with a poor message; nothing stored wrongly). **Estimate:** 30m (use the shared validator in the environment dialog, make it reject leading-zero prefixes, add cases). **Kind:** two client validators weaker than the server rule. **Source:** live `/qa-find-bugs` pass 35, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (own throwaway project, one rejected write, one discarded draft)

Fixtures: project `qa-20261110-cidr` with environment `qa-20261110-cenv` (deleted). The draft on the existing Postgres `blockeden-forum-db` was never saved: its `ipAllowList` was `[]` before and after (REST `GET /v1/postgres/dpg-d9rs3ee0ccis738kc7c0`).

1. New → New Project, then the environment's More actions → All settings. The dialog has "Inbound IP restrictions": rows `0.0.0.0/0` and `::/0`, a "New CIDR block" input and an "Add source" button.
2. **The environment dialog validates nothing.** Type `foo`, click Add source: the row is added with no inline error (the button is enabled for any non-empty text). The same for `10.0.0.0/33`. The draft reads `0.0.0.0/0, ::/0, foo, 10.0.0.0/33` and Save stays enabled. With only `foo` added, Save sends `SetEnvironmentACL` and the answer is:

```json
{
  "data": { "setEnvironmentACL": null },
  "errors": [
    {
      "message": "bad request: \"foo\" is not a valid CIDR",
      "path": ["setEnvironmentACL"]
    }
  ]
}
```

The dialog stays open with no inline error, and a toast reads `"foo" is not a valid CIDR`.

3. **Control, shared editor.** Databases → blockeden-forum-db → Access control → New CIDR block: `foo` and `10.0.0.0/33` followed by Add show `aria-invalid=true` and the inline text "Enter unique, valid IPv4 or IPv6 CIDR blocks." and add no row.
4. **The shared editor is looser than the server on leading-zero prefixes.** The same editor with `10.0.0.0/024` and Add: `aria-invalid=false`, the row `10.0.0.0/024` is added and "Save allowlist" is enabled. The server refuses that value: in the environment dialog, `10.0.0.0/024` added and saved answers `bad request: "10.0.0.0/024" is not a valid CIDR`.

**Server rule**, Go `netip.ParsePrefix` (go run from the session scratchpad, since removed): `10.0.0.0/024`, `10.0.0.0/08`, `10.0.0.0/00`, `::1/0128` and `2001:db8::/032` are all "bad bits after slash". `10.0.0.0/24`, `0.0.0.0/0`, `::1/128`, `2001:db8::/32`, `::ffff:1.2.3.4/96` and the host-bit form `10.0.0.5/24` load.

**Client rule**, the body of `isValidCIDR` run under node 24 with the same inputs: true for all of `10.0.0.0/024`, `/08`, `/00`, `::1/0128`, `2001:db8::/032`. Its prefix check is `/^\d+$/` then `Number(prefixText)`, so it accepts every zero-padded prefix the server refuses.

## Root cause (code-traced), two separate defects

**(a) The environment dialog has its own unvalidated list.** `dashboard/src/features/environments/components/environment-settings-dialog.tsx:109-118` `addCIDR` adds any non-empty trimmed string that is not already present; `updateEntry` (`:121-131`) edits rows freely; `save` (`:139-150`) sends them trimmed. The file never imports `isValidCIDR` and has no error slot. `grep -rn isValidCIDR` outside tests finds only `common/components/ip-allow-list-editor.tsx:5,81,88,182` and `common/lib/cidr.ts:2`. The dialog hand-rolls its list instead of using the shared `IPAllowListEditor`, which the service, Postgres and Key Value panels use (`service-networking-panel.tsx:66`, `access-control-panel.tsx:91`, `key-value-networking-panel.tsx:82`).

**(b) `isValidCIDR` accepts a leading-zero prefix.** `dashboard/src/common/lib/cidr.ts:6-7`: `if (!address || !/^\d+$/.test(prefixText)) return false; const prefix = Number(prefixText);`. A leading-zero prefix is a valid number to it. The server's comment at `lego/backend/internal/core/cidr.go:32-38` says exactly why `netip.ParsePrefix` is the grammar: `net.ParseCIDR` accepts `/024`, but the SNI-proxy enforcement path does not, so admitting it would delete the route and mark the shared proxy unhealthy for every tenant. The client test `common/lib/__tests__/cidr.test.ts` rejects `01.2.3.4/24` (a zero-padded octet) but has no zero-padded prefix case.

The refusal text comes from `core.ValidateCIDRs` (`core/cidr.go:39-49`, the only producer of "is not a valid CIDR"), reached for environments through `core.ValidateAllowList` (`core/cidr.go:236-239`) at `environments/service.go:1532`, and shared with the datastore and service writers.

## Fix (target behavior)

- The environment settings dialog validates with `isValidCIDR` the way the shared editor does: Add refuses an invalid or duplicate value and shows the same inline message, and Save is disabled while any row is invalid, including a hand-edited existing row. Simplest is to render the shared `IPAllowListEditor` in the dialog instead of its own list, keeping its protected-status and isolation toggles.
- `isValidCIDR` rejects a prefix with a leading zero unless it is exactly `0` (so `/0` stays valid; `/00`, `/08`, `/024`, `/0128` are refused, in IPv4 and IPv6), with cases added to `cidr.test.ts`.
- The server rule is unchanged and already authoritative for REST, GraphQL and MCP.
