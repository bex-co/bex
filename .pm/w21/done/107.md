# 107 — A REST or MCP client that polls the Postgres export list writes one DownloadDatabaseBackupEvent per call

Why: w21/105 records one `DownloadDatabaseBackupEvent` for every request that returned a download URL, as Render's audit log does for a download; a script that lists exports in a loop while an older export is still available hands out a URL, and so writes a row, on every call, and Render parity does not need a coarser row.

- **Source:** w21/105, 2026-11-16 (ADR006 § Audit log, the w21/105 amendment).
- **Facts:** `postgres.Service.ListExports` (`lego/backend/internal/postgres/recovery.go`) records `postgres.DownloadDatabaseBackup` once per request that minted at least one URL. REST `GET /v1/postgres/{id}/export` and MCP `list_postgres_exports` always mint; GraphQL mints only for a query that selects `url`, so the dashboard's status poll writes none. Each such row is true: the caller was handed a 15-minute bearer URL to the whole dump. Nothing bounds how often a client calls.
- **The looser variant:** one row per caller, database and URL lifetime (15 minutes), as ADR112 D6 describes for the object get. It needs a per-replica or shared record of the last row, which costs a store write or a cache, and it would hide a second download inside the window.

## Steps

1. After 2026-11-23, count production's `postgres.DownloadDatabaseBackup` rows per caller and hour (`audit_events`, read-only). If no caller wrote more than a handful in an hour, close this note with the numbers: the per-request row stands.
2. If one did, ship the coarser row for REST and MCP (GraphQL already decides by selection), record it in ADR006 § Audit log, and cover it with a test that two calls inside the window write one row and a call after it writes another.

## Done when

- [x] The per-request row is either confirmed by a week of production counts or replaced by the coarser one, with the decision written in ADR006.

**The query (read-only, aggregate only).** Run it on the platform database's primary after fetching the production kubeconfig (`bash scripts/fetch-app-kubeconfig.sh <path outside the repo>`, then `export KUBECONFIG=<that path>`); delete the kubeconfig afterwards. It reads the week `[2026-11-17 04:42 UTC, 2026-11-24 04:42 UTC)` and counts per caller (`caller` and `caller_method`), database (`target`, which is `database:<name>`, never a URL) and hour, listing only the busiest groups. Record in the note only the counts, how many callers and databases there were, and a caller as `rest`, `mcp`, `graphql` by `caller_method` where it is one of those: no emails, no workspace names, no database names, no ids.

```bash
primary=$(kubectl -n bex-system get pods -l cnpg.io/cluster=bex-db,cnpg.io/instanceRole=primary -o name)
kubectl -n bex-system exec "$primary" -c postgres -- psql -U postgres -d bex -c "
SELECT caller_method, count(DISTINCT caller) AS callers, count(DISTINCT target) AS databases,
       count(*) AS group_hours, max(n) AS most_rows_in_one_hour, count(*) FILTER (WHERE n > 12) AS hours_over_12,
       sum(n) AS rows
FROM (SELECT caller, caller_method, target, date_trunc('hour', at) AS h, count(*) AS n
      FROM audit_events
      WHERE verb = 'postgres.DownloadDatabaseBackup'
        AND at >= timestamptz '2026-11-17 04:42+00' AND at < timestamptz '2026-11-24 04:42+00'
      GROUP BY 1, 2, 3, 4) s
GROUP BY caller_method ORDER BY most_rows_in_one_hour DESC;"
```

Before reading, check the week is whole: `BEX_AUDIT_RETENTION_DAYS` is 90 (`lego/backend/AGENTS.md`), so no row of the week has been swept, and `SELECT min(at) FROM audit_events` is before the window's start.

**The decision rule.** "A handful" is **at most 12 rows per caller, database and hour** (one row every 5 minutes).

- If `most_rows_in_one_hour` is 12 or less on every `caller_method` (`hours_over_12` is 0 everywhere): close this note with the numbers, as Step 1 says, and write the decision into ADR006 § Audit log (the w21/105 amendment): the per-request row stands, with the week's maximum and the number of callers and databases.
- Otherwise: do Step 2. Ship the coarser row for REST and MCP (one row per caller, database and 15-minute URL lifetime, GraphQL already decides by selection), record it in ADR006 § Audit log, and cover it with the test Step 2 names. Because Render parity is the top principle ([ADR008](../../../docs/ADR008-vision.md#render-parity-first)), a coarser row is a divergence only in how often a row is written, not in what an audit log may hide; say in ADR006 that a second download inside the window is the case the row no longer shows, and file the stricter variant as a follow-up rather than waiting on it.
