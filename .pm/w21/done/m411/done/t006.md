## Objective

Let a disk of any size the API allows snapshot, refuse a restore key with a `..` segment, and correct the comment at `disksnapshot.go:335`.

## Context

- `internal/disksnapshot/store.go` `Put` uses `transfermanager` with its defaults: parts of 8 MiB and at most 10,000 of them, so a tar stream past about 78 GiB fails at the part cap and the disk never snapshots. The API allows disks up to 10,000 GB (`backend/internal/apps/disks.go` `diskMaxSizeGB`), so the part size has to follow the disk: about the disk's bytes over 9,000, rounded up to the MiB, with the upload concurrency lowered as the parts grow so memory stays bounded.
- `cmd/disk-snapshot/main.go` takes `BEX_DISK_SNAPSHOT_KEY`; the restore-key prefix check does not reject `..` (not reachable by a tenant, a defense in depth).
- The comment at `disksnapshot.go:335` says `os.Root` rejects absolute and escaping link targets; Go's documentation says `Root.Symlink` does not validate `oldname`. The containment holds at use, because `os.Root` refuses to follow a link that leaves the root.

## Steps

1. Find how the job learns the disk's size (PVC capacity) and pass it in; compute the part size and concurrency in one function with a table test (1 GB, 1 TB, 10,000 GB all stay under 10,000 parts).
2. Reject `..` and an absolute key in the key check, with a test.
3. Rewrite the comment, and add a test that a tar with an absolute and an escaping symlink restores as links and that writing through one is refused.
4. Check the job's memory limit against the largest part size and concurrency.

## Result (2026-11-14)

- **Part size follows the disk.** `disksnapshot.PlanUpload(capacityGB)` sizes the multipart upload: the capacity plus 10% for tar/gzip/age framing, over 9,000 parts, in whole MiB (8 MiB up to about 63 GB, about 1.2 GiB at the 10,000 GB the API allows), with concurrency lowered so the buffers stay near 256 MiB. `Store.Upload` carries it into `transfermanager`; the Job is told the capacity (`BEX_DISK_SIZE_GB`, the largest of the requested, allocated and reported sizes) and a backup's memory limit grows with the buffered parts (about 1.5 GiB at the top, unchanged 256 Mi for small disks, restore and purge untouched). Tests: `uploadplan_test.go` (every size up to 10,000 GB fits 10,000 parts, a fake multipart S3 counts the parts Put sends), `TestStoreFromEnvPlansTheUploadFromTheDiskSize`, `TestDiskSnapshotJobCarriesTheDisksCapacity`, `TestDiskSnapshotMemoryLimitCoversTheUploadBuffers`. Recorded in ADR082 D5.
- **Restore key.** `checkRestoreKey` refuses a key outside the disk's prefix, one that names no snapshot, and any empty, `.` or `..` segment (`TestRestoreKeyMustLieUnderTheDisksPrefix`).
- **The comment was wrong.** Go's documentation says `os.Root.Symlink` does not validate its target; the comment now says what holds the line (the rooted handle never follows an escaping link), and `TestExtractTreeRestoresAnEscapingLinkButNeverFollowsIt` pins it for an absolute and a `..` target.
