## Objective

Give the edge-cache sidecar the server limits it can have without cutting a legitimate stream: an idle timeout, and record why a write timeout and a whole-request read timeout are not set.

## Context

- `lego/operator/cmd/edge-cache/main.go` builds `http.Server{ReadHeaderTimeout: 10s}` and nothing else, so an idle keep-alive connection is held forever and a client may trickle a body without limit.
- A `WriteTimeout` ends a response that streams past it (server-sent events, long-poll), and a `ReadTimeout` ends a slow but legitimate upload to the origin; `cmd/staticserver/main.go` sets both because it serves files only.

## Steps

1. Read what the sidecar proxies and caches (`internal/edgecache`) to confirm which responses stream.
2. Add `IdleTimeout` (the value `staticserver` uses is the reference) through a `newServer` function like `cmd/staticserver/main.go` has, with a test on the returned fields.
3. If a body-read bound is wanted, set it per request with `http.ResponseController` only when the request is not an upgrade or a stream; otherwise record it as accepted.

## Files

- lego/operator/cmd/edge-cache/main.go
- lego/operator/cmd/edge-cache/main_test.go

## Acceptance criteria

- [x] `newServer` sets an idle timeout, a test pins it, and the reason `WriteTimeout` and `ReadTimeout` are absent is in the code.

## Out of scope

- Anything else the round-25 audit listed.

## Result (2026-11-14)

`cmd/edge-cache` builds its server in `newServer`: `ReadHeaderTimeout` 10 s and a new `IdleTimeout` 120 s. **No `ReadTimeout` or `WriteTimeout`, by design** (recorded in the code): every request goes upstream through the proxy, so a `WriteTimeout` would cut event streams, long polls and large downloads and a `ReadTimeout` would cut WebSocket upgrades and slow uploads that the app serves on purpose. `MaxHeaderBytes` stays at Go's default (a smaller bound could refuse an app's large cookies). `cmd/edge-cache/main_test.go` pins the fields.
