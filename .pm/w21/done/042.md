# The ⌘K palette lists Router for a workspace whose `routerAvailable` is false: the sidebar hides it behind a second gate the palette never got, and selecting it bounces to the overview

Why: [w21/031](done/031.md) made the palette "apply the same feature gating as the sidebar", but the sidebar has two gates (the router flag and a `routerAvailable` probe) and the palette only got the flag, so a flag-enabled workspace without the beta companion service is offered a destination its own sidebar hides and its own route refuses.

**Severity:** minor (a dead-end command: the item looks real and does nothing). **Estimate:** 25m (share one availability hook between the sidebar and the palette, one test). **Kind:** gap in the guarantee of w21/031. **Source:** live `/qa-find-bugs` pass 40, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (read-only; nothing was created; desktop, en; workspace `tea-d98210cbbpdc73dcrkvg`)

1. Open `/` and wait for network idle. The page sends `RouterAvailable` with variables `{"ownerId":"tea-d98210cbbpdc73dcrkvg"}` (`query RouterAvailable($ownerId: String!) { routerAvailable(ownerId: $ownerId) }`) and the response is `[{"data":{"routerAvailable":false}}]`.
2. The sidebar has no `a[href="/router"]` (`sidebarHasRouter: false`).
3. Press ⌘K and type `router`. The palette lists one item, `Router` (`[cmdk-item]` text).
4. Press Enter. After 2.5 s `location.pathname` is `/`: the route's own guard refused the destination.

Control: Agents and Automations in the same palette navigate to their pages (checked while verifying w21/031 in this pass).

## Root cause (code-traced; `origin/main` is unchanged for the three files, last commit `5dc99bf8c` and older)

- `dashboard/src/common/components/dashboard-layout/dashboard-nav.ts:74-90` `visibleNavGroups` filters `/router` by `flags.routerEnabled` only (`useRouterFeatureEnabled()`, `config/use-growthbook.ts:13-16`, a per-workspace flag).
- The sidebar adds a second gate: `dashboard-sidebar.tsx:104-125` `RouterNavGroups` runs `useQuery(RouterAvailableDocument, { variables: { ownerId: currentWorkspaceId ?? "" } })` and removes `/router` unless `data?.routerAvailable === true` (its comment: "Only targeted workspaces probe the optional companion service").
- The palette, `global-search-dialog.tsx:150-152`, calls `visibleNavGroups(NAV_GROUPS, { agentsEnabled, routerEnabled })` and never runs the probe.
- The route is the third gate: `dashboard/src/routes/router.tsx:16-20` `beforeLoad` queries `routerAvailable` with `network-only` and `throw redirect({ to: "/" })` when it is not true, which is the bounce in step 4.

## Fix (target behavior)

- The palette lists Router exactly when the sidebar does: `routerEnabled` AND `routerAvailable === true`.
- Share one hook, for example `useRouterNavAvailable()` returning `routerEnabled && data?.routerAvailable === true` with `skip: !routerEnabled`, used by both `RouterNavGroups` and the palette; or pass a `routerAvailable` flag into `visibleNavGroups` so the filter stays in one place.
- **Pre-settle state:** the sidebar hides Router until the query returns true, so the palette must too (no Router row while loading). The palette reads the same document and variables, so Apollo's cache serves it with no second request. A workspace without the flag must still not probe.
- Direct navigation to `/router` keeps redirecting (unchanged).
- UI only: no REST, GraphQL or MCP change.

## Blast radius (counted by grep)

- `visibleNavGroups` has 2 callers (`dashboard-sidebar.tsx:41`, `global-search-dialog.tsx:152`) plus the drift test `__tests__/global-search-dialog.test.tsx:112`.
- `RouterAvailableDocument` has 2 consumers (`dashboard-sidebar.tsx:112`, `routes/router.tsx:16`).
- `/router` appears in `dashboard-breadcrumbs.tsx` and `route-skeleton-manifest.ts` only as a label and a skeleton.
- The existing test covers only the flag-off case (`it("hides Agents, Automations and Router when their flags are off")`, `:158-163`) and mocks `useRouterFeatureEnabled` to true elsewhere. It needs a case for flag on with `routerAvailable` false (Router absent) and one for true (Router present); the sidebar must keep passing.

## Adjacent classes

- A user without the router flag sees neither palette entry nor sidebar entry (already correct).
- Not an authorization matter: `routerAvailable` only reports whether the workspace has the beta companion service ([w4/116](../w4/done/116.md): "returns `false` for a non-beta workspace rather than erroring").
