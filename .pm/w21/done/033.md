# Notifications → Mobile push: the IANA timezone check runs in the browser's Intl, so an offset such as `+05:00` passes the form, the server refuses it, and the user gets a raw server toast instead of the inline "Enter a valid IANA timezone" message

Why: the form's own inline validation is the documented way to tell the user a zone is wrong (w4/387 and w4/m231 verified `Mars/Phobos` gets it), but its rule is "whatever this browser's Intl accepts", which is wider than what the server's tz database loads.

**Severity:** minor (a rejected save with a poor message; nothing is stored wrongly). **Estimate:** 30m (make the client rule match the server's, plus a control test for the spellings the server accepts). **Kind:** client validator weaker than the server rule. **Source:** live `/qa-find-bugs` pass 30, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (one rejected write on the QA account's own push settings; re-read afterwards: unchanged)

Signed in, en; `Mobile push` is enabled on this account.

1. Open `/notifications`. The `IANA timezone` textbox reads `UTC`.
2. Fill it with `+05:00`. No inline error appears and `Save push settings` becomes enabled.
3. Click Save. The page sends mutation `UpdatePushNotificationSettings`. The response is HTTP 200 with:

```json
{
  "data": { "updatePushNotificationSettings": null },
  "errors": [
    {
      "message": "bad request: invalid notification delivery policy: timezone \"+05:00\": unknown time zone +05:00",
      "path": ["updatePushNotificationSettings"]
    }
  ]
}
```

4. The UI shows a toast with that raw text, `Invalid notification delivery policy: timezone "+05:00": unknown time zone +05:00`, and no inline `role=alert`.
5. After a reload the stored zone is still `UTC`: nothing was saved.

**Control, same page:** `Mars/Phobos` gets the inline "Enter a valid IANA timezone such as America/Los_Angeles." (w4/387).

**Client rule**, `new Intl.DateTimeFormat('en', { timeZone: z })` in the same Chrome 152 as the page: accepts `+05:00`, `-08:00`, `+0530`, and also the wrong-case spellings `utc`, `america/los_angeles`, `AMERICA/LOS_ANGELES`; rejects `Foo/Bar` and `Local`.

**Server rule**, Go `time.LoadLocation` (go1.27.3 with `time/tzdata`, run from the session scratchpad): `+05:00`, `-08:00`, `+0530` and `Foo/Bar` are "unknown time zone"; `US/Pacific`, `Asia/Calcutta`, `Europe/Kiev`, `Etc/GMT+5`, `EST5EDT`, `GMT` and `UTC` load.

## Root cause (code-traced)

- `dashboard/src/features/notifications/lib/push-policy.ts:73-77` validates the zone with `new Intl.DateTimeFormat("en", { timeZone }).format()`, after length, empty and `Local` checks at `:66-72`. It is called from `push-notification-settings-panel.tsx:210`.
- The server's write path is `lego/backend/internal/notifications/service.go:615` `assertPolicyEvaluable` → `Evaluate` → `compileDeliveryPolicy` → `delivery_policy.go:343-345` `loadLocation(zone)` → `invalidPolicyf("timezone %q: %v")` → `core.ErrBadRequest`. `normalizePushSettings` itself only checks the zone's length and NUL (`service.go:556`), so the only real rule is the tz database lookup.
- The error reaches the user through `use-update-push-notification-settings.ts:42-44`: `toast.error(mutationErrorMessage(err, t("notifications.pushUpdateError")))`, and `common/lib/graphql-error.ts:233-245` relays the server's refusal text verbatim.

## Fix (target behavior)

The form shows the inline localized `notifications.pushInvalidTimezone` for any input the server's tz loader cannot load, and never rejects a spelling it does load.

- **Offset-style input** (`^[+-]`) is rejected client-side. That is deterministic and independent of the browser's Intl engine, whose acceptance of offset zones varies by engine and version.
- **Do not** replace the rule with `Intl.supportedValuesOf('timeZone')`: that list holds canonical names only and would reject `US/Pacific`, `EST5EDT` and similar spellings the server accepts.
- **Wrong-case spellings** (`america/los_angeles`): the client accepts them. Whether the production server does depends on the filesystem: Go on macOS loaded them from the case-insensitive OS zoneinfo; the production image is `gcr.io/distroless/static`, a case-sensitive Linux tz directory, so a refusal is expected but was **not verified**. The task must verify it on Linux (a backend test or a container) and, if refused, either canonicalize the case in the client before sending (`resolvedOptions().timeZone` keeps the canonical case) or reject it inline. Pick the one that never rejects a server-accepted spelling.
- Add to `lib/__tests__/push-policy.test.ts` a rejection case for `+05:00` / `-08:00` / `+0530` and acceptance controls for `US/Pacific`, `EST5EDT`, `Etc/GMT+5`, `Asia/Calcutta` and `UTC`. The file has `Local` and range cases at `:63-68` but no offset case.
