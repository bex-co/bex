# Generate Blueprint then validate is not a no-op for the three oldest web services: the planner reports `update` with `changedFields` `[type]`, most likely because it compares an empty legacy `spec.type` with the exported `web_service` (a gap in w4/m124's closed-loop guarantee)

Why: [w4/m124](../w4/done/m124/README.md)'s goal was that a manifest bex exports from live resources re-plans as `noop` for every one of them, and on production three Git-backed Docker web services do not.

**Severity:** minor (a spurious plan item on 3 of 10 web services; no data lost, but a Blueprint sync would plan, and apply, a needless spec write). **Estimate:** 30m (normalize one comparison in the planner, add a legacy-App fixture and a negative case to the round-trip test). **Kind:** gap in the original guarantee of w4/m124. **Source:** live `/qa-find-bugs` pass 27, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (read-only: `generateBlueprint` and `validateBlueprint` are queries and apply nothing; existing resources)

From the signed-in page, for each resource kind:

```graphql
query($ids:[String]){ generateBlueprint(serviceIds:$ids){ filename manifest } }
query($y:String!){ validateBlueprint(bexYaml:$y){ valid errors plan{ mode totalActions actions{ changedFields{ path } kind name operation resourceId } } } }
```

(`postgresIds` and `keyValueIds` for the other kinds; `$ids` is the list of that kind's ids from `services` / `databases` / `keyValues`, `$y` is the manifest just generated, unmodified.) Results:

| kind | resources | operations |
| --- | --- | --- |
| private services | 3 | 3 `noop` |
| Postgres | 4 | 4 `noop` |
| Key Value | 2 | 2 `noop` |
| **web services** | 10 | 7 `noop`, **3 `update`** |

The three updates, with `mode: current_state`, `valid: true` and empty `errors`:

- `service:agentmarketcap-1:update changedFields [{"path":"type"}]`
- `service:beancount-cms-v2:update changedFields [{"path":"type"}]`
- `service:eden-cms-v2:update changedFields [{"path":"type"}]`

Their exported manifests are unremarkable (`type: web`, `runtime: docker`, `repo`, `branch`, `plan`, `region`, `autoDeployTrigger`).

**What discriminates them:** the three are exactly the three oldest web services, all created 2026-07-28. Every web service created on or after 2026-08-02 is `noop`: Docker-runtime ones too (beancount-forum 2026-08-02, crypto-price 2026-10-27, metrics-grafana and metrics-loki-gateway 2026-11-03, twenty-crm 2026-11-08) and native ones (eden-dash-v3 `node`, reverse-proxy-poc `go`). So the runtime is not the discriminator; age is.

**Evidence:** the table and the three `update` lines above, with the creation dates read from `services{ name runtime createdAt }`, are the durable probe.

## Root cause (code-traced; the live CR value is the one unverified link)

- `lego/backend/internal/apps/blueprint_plan.go:203`: the applier for field `type` is `dst.Type = want.Type`.
- `lego/backend/internal/apps/blueprint_state_plan.go` (`PlanBlueprintResource`, the service case): `:226` runs `ApplyBlueprintServiceSpec(&probe, want, svc.fields)` on a copy of the live spec, and when it reports a change, `:238` attributes it per field with `probeBlueprintServiceSpec`. A live `spec.Type` of `""` against a desired `"web_service"` therefore counts as a changed `type`, and `type` is the only path flagged.
- The rest of the service code normalizes: `effectiveType(spec.Type)` at `apps/service.go:880`, `:1074`, `:1437` and `:1607`, and the CRD states the rule: `lego/types/v1alpha1/app_types.go:400-401` "An empty spec.type is treated as TypeWebService, so pre-existing Apps keep their behavior" (the field is `omitempty`, `:489`; `Type == ""` is also treated as web at `:49`). The planner's `type` comparison does not apply that normalization.
- Why it escaped: `lego/backend/internal/apps/blueprint_roundtrip_test.go:131` `TestGeneratedBlueprintRePlansAsNoop` builds its fixtures through the create path, and a grep for `Type: ""` in `blueprint*_test.go` finds no fixture with a pre-`type` App.

## Fix (target behavior)

The planner compares effective types, so `""` equals `"web_service"`: a legacy App re-plans as `noop` and no spec write is planned for it, while a real type change (`web_service` to `private_service`, say) still reports `update` with `type`. `validateBlueprint`, `planBlueprintSync` and the sync apply share the planner on REST, GraphQL and MCP, so one change covers all three. Add an App with an empty `spec.type` to the round-trip test, plus the negative case.

## Blast radius (counted by grep on the working tree)

- The `type` applier runs in every Blueprint plan and apply for services (create, update, sync). Types other than `web_service` are always written explicitly, so only the default web alias is affected.
- Tests: `blueprint_roundtrip_test.go` (the fixture and negative case above) and the existing planner tests, which must keep passing.

## Adjacent classes

- Static, cron, worker and private services carry an explicit `type`, so the normalization never changes their result.
- A cross-type change on an existing service is a different question (Render treats the type as immutable) and is not decided here.

## Unverified (not probed this run)

- The live `spec.type` of the three Apps: reading the CRs needs cluster access this account does not have. A one-time backfill that writes `web_service` would also clear the symptom but leaves the planner fragile for any other legacy App, so the fix above does not depend on it.
- What a sync apply does to these three: it was not applied, because applying writes to resources the QA account does not own.
- Static, cron, worker and env-group kinds: none exist in the workspace, so they were not exported live.
