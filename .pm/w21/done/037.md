# The Delete environment dialog promises "Its environment groups stay in the project — they just lose this environment label", but a detached group leaves the project altogether: it is listed nowhere on the project page and only under Environment Groups as "Workspace (no Environment)" (the Delete project dialog says it right: "become unassigned")

Why: a user reads this sentence in a destructive confirmation to decide whether the environment's groups are safe, and then cannot find them in the project they were told they stay in.

**Severity:** minor (a confirmation that misdescribes where a group ends up; the group is kept and nothing is lost). **Estimate:** 15m (two en strings, two zh strings, tests). **Kind:** stale copy after w4/m264. **Source:** live `/qa-find-bugs` pass 34, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (journeys 1 and 16 on a fresh project; own fixtures, all deleted)

Fixtures: project `qa-20261110-dbl`, environment `qa-20261110-env2`, env group `qa-20261110-eg`.

1. **Control: create.** `/?lang=en` → New → New Project, name `qa-20261110-dbl` and first environment `qa-20261110-env`, double-click Create. Exactly one `CreateProject` mutation is sent, one project exists, and the page lands on the new project with its environment selected.
2. **Control: placement is consistent.** GraphQL `createEnvironment(name: "qa-20261110-env2", projectId)`, then `createEnvGroup(name: "qa-20261110-eg", ownerId, environmentId: <env2>)`. GraphQL `envGroups` returns `environmentId` = env2; REST `GET /v1/env-groups?environmentId=<env2>` returns the group and `?environmentId=<other>` returns `[]`. The project page for env2 reads "qa-20261110-env2 1 resource" and "Env Groups (1)"; `/env-groups` lists it with scope "qa-20261110-dbl / qa-20261110-env2".
3. **The dialog.** On the project page, More actions → Delete on env2 reads: `Delete environment "qa-20261110-env2"? Its environment groups stay in the project — they just lose this environment label. This action cannot be undone.` Confirm: toast `Environment "qa-20261110-env2" deleted.`
4. **After the delete.** GraphQL `envGroups` returns the group with `environmentId: null`. The project page for the project's remaining environment shows "Env Groups (0)". The project's `?env=unassigned` view reads "Env Groups (0)" and "No resources in this environment yet." `/env-groups` is where the group lives, as "Workspace (no Environment)". So the group did not stay in the project; it left it.
5. **Cleanup.** `deleteEnvGroup` returned true and `deleteProject` returned the id; the project and env group lists show nothing named `qa-20261110*`.

## Root cause (code-traced)

- The strings are `dashboard/src/features/environments/locales/en.ts:134-135` (`environments.deleteConfirmBody`) and `:139-140` (`environments.deleteConfirmBodyResources`: "…deletes all of its services, databases, and key value stores: {resources}. Its environment groups stay in the project — they just lose this environment label…"), with the zh twins at `locales/zh.ts:126` and `:131` ("其环境组仍保留在项目中，仅会移除此环境标签"). The consumer is `features/environments/components/environment-card.tsx`.
- The sentence is a leftover of the pre-[w4/m264](../w4/done/m264/README.md) wording "Its services, databases, and key-value stores stay in the project and keep running — they just lose this environment label" (quoted in m264's repro). That was true for services, which carry their own `project_id`. m264 and w6/m290 then made the dialog delete services, databases and key value stores and kept the group clause unchanged.
- Environment groups carry no project link of their own: `lego/backend/internal/envgroups/service.go:205,222` have `environmentId` and no `projectId`, so a group's project is derived from its environment. The teardown is `DetachEnvironment` (`environments/service.go:109-111,443-445`; ADR032 "Unchanged: Environment groups are still detached, because Render lists them apart from services"), which clears `environmentId`. A group without an environment belongs to no project, so "stay in the project" cannot hold.
- The sibling Delete project dialog already says it correctly: `dashboard/src/features/projects/locales/en.ts:307,321,326,332` "Its environment groups become unassigned, not deleted."

## Fix (target behavior)

The Delete environment dialog says what the data model does, in the project dialog's words, in both `deleteConfirmBody` and `deleteConfirmBodyResources`:

- en: "Its environment groups are kept but become unassigned: they no longer belong to this environment or project, and stay under Environment Groups."
- zh: 其环境组会保留但变为未分配：不再属于此环境或项目，仍可在“环境变量组”中找到。

No behavior change: ADR032 keeps groups detached. Render's own dialog for environment groups is recorded in ADR032 as not observed, so whether Render deletes them stays an open gap in ADR032, not part of this fix.
