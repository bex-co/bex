# A custom Logs range that ended in the past still shows today's application lines when Live is on (Live is the default) — a gap in w6/m111's guarantee

Why: w6/m111 fixed the live tail's lower bound only, so a window that ends before the page was opened still gets the pod's whole current log replayed into it, contradicting the page's own "The range limits history" copy.

**Severity:** major (the pane contradicts the selected window and its own helper text; line timestamps show time of day only, so nothing marks the lines as outside the window). **Estimate:** 60m, dashboard only (service Logs viewer, one shared helper, tests). **Kind:** regression of [w6/m111](../w6/done/m111/README.md) target A (upper bound). **Source:** live `/qa-find-bugs` pass 7, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (fresh page loads; own service `qa-20261110-obs` = `srv-dbph6sdme2kc73f2l490`, created 2026-11-10 04:53 local, deleted afterwards)

1. Open `/services/srv-dbph6sdme2kc73f2l490/logs?range=custom&rangeStart=2026-11-01T07%3A00%3A00.000Z&rangeEnd=2026-11-02T08%3A00%3A00.000Z` (Custom range, Nov 1 to Nov 2; the service did not exist then). Live is on by default. The pane lists 28 lines, `04:54:26 AM` to `04:55:53 AM`, for example `[3sdp0] 2026/11/10 12:55:53 GET /qa-25`, and the footer reads "Live — streaming new lines". All 28 predate the page open (about 05:03 local), so they are not lines that "arrived after the page opened".
2. **Control A**, same URL plus `&live=0` (fresh load): 0 lines and the honest empty state "No logs in this time range — No log lines fall within this time range." So the history query is correct and the stream is what injects the lines.
3. **Control B**, same Custom window, Log type = Request logs: "No matching logs" (the Loki-backed request lines honor the window). Log type = Application logs or All logs: the same 28 pod lines.
4. The Network panel (fresh load) shows exactly one tail request: `GET https://api.bex.co/v1/logs/subscribe?resource=srv-dbph6sdme2kc73f2l490&startTime=2026-11-01T07%3A00%3A00.000Z` — the window start only; the window end (`2026-11-02T08:00Z`) is never sent.

**Evidence:** `.playwright-mcp/qa-logs-1.png` (gitignored, local to the hunting session: Custom… selected, Live on, "The range limits history…" above 2026/11/10 lines). Items 1–4 are the durable probes.

## Root cause

- `dashboard/src/features/logs/components/log-viewer.tsx:199-225` — `useLiveLogs({ enabled: live && liveSupported && !planRefused, startTime: historyWindow.startTime, … })` never looks at `historyWindow.endTime`. `useLiveRange` (`dashboard/src/features/metrics/hooks/use-live-range.ts`, custom branch) returns the fixed `endTime` for a custom range, so the viewer has the value and does not use it.
- `dashboard/src/features/logs/hooks/use-live-logs.ts:80-86` — the subscribe URL carries `startTime` only (m111's lower bound). For a window that begins before the pod existed, the first connect replays the pod from its start, which is the "kubelet offset 0" behavior m111 removed for presets.
- `dashboard/src/features/logs/lib/map.ts:260-278` — `mergeLogLines(history, live, notBeforeMs)` filters `parsed < notBeforeMs` and has no upper bound, so nothing drops a streamed line newer than the window end (`log-viewer.tsx:230-235`).
- Server side: `lego/backend/internal/logs/rest.go:587` parses `endTime` for `/v1/logs/subscribe`, but whether the tail honors it is unverified, so the fix below does not depend on it.

## Fix (target behavior)

m111's own target A: the pane is exactly the selected window plus lines that arrive after the page opened. For a Custom range that means:

1. A Custom range whose end is not after the moment it was applied is a closed window. The viewer does not open the tail for it, and the Live switch shows off and disabled with a reason (reuse the paused-view semantics of w4/399, "Live off freezes the history window"). Today the footer says "Live — streaming new lines" over a window nothing can stream into.
2. A Custom range whose end is still in the future keeps tailing, and `mergeLogLines` gets an upper bound (`notAfterMs = Date.parse(historyWindow.endTime)`) so no streamed line newer than the window end is shown. Presets keep today's behavior (their end is "now").
3. UI only. REST, GraphQL and MCP are unchanged (the tail is REST/SSE only, per m111's parity note; the GraphQL `logs` read already honors `endTime`).
