# 109 — A DELETE of an env var that does not exist answers 404 and still patches the App, and over GraphQL and MCP rolls the service and opens a deploy

Why: a call that answers "not found" changes nothing on Render, and a service that carries a saved change or a new deploy row after a refused delete is the same class of defect as w21/108 (a refused write that leaves a saved change), on every service, not only one a Blueprint synced.

- **Source:** w21/108, 2026-11-17 (found while writing its refused-write tests, by a probe on a control-plane service with a deploy recorder and a moving clock; then observed on production, pin `2806a07b8`, in `bex-canary`: a GraphQL `deleteEnvVar` of a name that is not there answered `NOT_FOUND` and opened a fifth `service_updated` deploy row on a throwaway service, bumping `restartedAt` and `release-generation`; a REST `DELETE` of one answered 404, opened no row and set `app.bex.co/saved-config-revision`).
- **Facts:** `DeleteEnvVar` (`lego/backend/internal/secrets/service.go`) calls `deleteMapKeyAfterProjection` (same file), which projects the reduced set before it knows whether the key is in the store: "A retry also re-projects an already-absent key before returning not-found, repairing an older attempt that committed its source CAS first". That projection is `materializeEnv`, an App patch. On a plain service whose store holds only `KEEP`, a `DELETE …/env-vars/NOPE`:
  - over REST (staged) answers 404 and patches the App once (it gains `app.bex.co/saved-config-revision` and `app.bex.co/pending-env-secret`);
  - over GraphQL `deleteEnvVar` and MCP `delete_env_var` answers the not-found error and patches the App once with a `restartedAt` bump, `spec.envFromSecret` set and a `release-generation` stamp, so it opens a `config_change` deploy row.
    No store write is made. `TestDeleteEnvVarAlreadyAbsentRepairsStaleProjection` (`deletion_convergence_test.go`) pins the repair: a Secret that still holds a key the store no longer has is projected clean and the workload rolled.
- **Why the repair is mostly dead:** the delete now converges in the order projection first, store commit last, so the state the repair was written for (the store committed, the Secret not) no longer arises from this code. It can still arise from a delete an older release made.
- **Fix:** repair only when there is something to repair: project (and roll) an absent key's delete when the derived Secret really holds the key, and otherwise answer not found with no App patch, no deploy row and no saved change. Keep `TestDeleteEnvVarAlreadyAbsentRepairsStaleProjection` passing. Check Render's behavior first (`DELETE /services/{serviceId}/env-vars/{envVarKey}` for a key that is not there: expected 404 and nothing else changed) and cite it in the commit, as the parity rule asks.

## Done when

- [x] A `DELETE` of a name neither the store, the Secret nor `spec.Env` holds answers 404 (REST), the not-found error (GraphQL) and the tool error (MCP), and makes no App patch, opens no deploy row and leaves no saved-config annotation, on a plain service and on one with a retained variable; the stale-Secret repair still runs when the Secret holds the key.
- [x] A production check on a throwaway service in `bex-canary`: before the fix a GraphQL `deleteEnvVar` of a name that is not there opens one deploy row, after it none.

- **Render, checked first.** The pinned `render-public-api-1.json` and [api-docs.render.com/reference/delete-env-var](https://api-docs.render.com/reference/delete-env-var) document `DELETE /services/{serviceId}/env-vars/{envVarKey}` as "Delete a particular environment variable from a particular service" with 204 and a 404 ("Unable to find the requested resource"), and no other effect; Render's env-var REST writes deploy nothing ("Changes will not be deployed automatically", [update env vars](https://api-docs.render.com/reference/update-env-vars-for-service)). No Render API key exists to observe it live, so the parity-sufficient reading is the documented one: a 404 changes nothing. The note's premise held: nothing in Render's docs describes a repair.
- **Choice: repair only what is there.** `deleteMapKeyAfterProjection` (`lego/backend/internal/secrets/service.go`) now takes the App and the projection kind and, for a name the store and `spec.Env` do not hold, reads the derived Secret (`projectionHolds`): it projects the reduced set and rolls the workload only when the Secret carries the name, and otherwise answers not found with no App patch, no deploy row, no saved-config annotation and no Secret write. A Secret that does not exist carries nothing; one that cannot be read fails the delete (it cannot tell a revoked value is gone). Both branches (versioned and unversioned stores) take it. A name only the retained literal holds is still found (the 108 `alsoHeld` rule). The root cause was shared, so `DeleteSecretFile` is fixed in the same commit (its derived Secret is `<service>-files`). The invalid-name branch of `DeleteEnvVar` also patched the App (an empty merge patch) when it had no debris literal to strip; it now patches only when it strips one.
- **The ordering race.** A writer that commits the name between the delete's read of the store and its read of the Secret leaves the name in the Secret at a later revision, so the delete's repair (the older revision) is refused as superseded and the writer's value survives; the delete answers not found, as if it had run first. That case still patches the App once (the repair's roll) and is pinned only for what it must keep (the writer's value in the store and the Secret). The re-declare race of w21/106 is on the writes, not on this path.
- **Other verbs checked.** The env-group verbs (`DeleteEnvGroupVar`, `DeleteEnvGroupFile`) check the group's key and file lists before they patch: not affected. A `PUT` of an unchanged variable, the same set or the same secret file is a different defect, an accepted write that stores nothing: it patches the App on every service (REST staged: `saved-config-revision`; GraphQL and MCP: `restartedAt` and a `config_change` row), whereas `PatchEnvironment` has skipped that since w4/m122 (probed in-process; not fixed here): filed as [w21/110](110.md).
