# ship-gates runs the CLI suite and the CLI analytics suite when their paths change, as CI does

Why: our own pushes turned main red twice in one run, once in `test (bex CLI)` (a test that fails only with the runner's `CI=true`) and once in gitops.yml's `cli-analytics` job (`scripts/cli-analytics.sql`), each fixed only after the push, because `scripts/ship-gates.sh` runs gofmt and the backend, types, dashboard and native suites and nothing of the CLI.

- **Evidence.** `scripts/ship-gates.sh:183-191` computes `go_changed`, `backend_changed`, `dashboard_changed`, `suite_inputs_changed` and `native_changed`, and `:267-285` runs them; `lego/cli` has no branch. The reds: `test (bex CLI)` run 44871470449 on `ed70568c4` (fixed in `0b97bf731`) and gitops.yml run 44864392681 on `ed1452f75` (`test_command_family_mapping`, fixed in `25725a13b`).
- **Change.** Add `cli_changed` over the trigger paths of `.github/workflows/cli-test.yml` (`lego/cli/**`, `scripts/bex-cli-*.sh`, `docs/bex-cli.md`, `docs/cli-compatibility-checklist.md`) and, when it is set, run what that job runs, with `CI=true` as a hosted runner sets it: `bash scripts/bex-cli-validate.sh`, `cd lego/cli && CI=true go test ./...` and `cd lego/backend && go test ./internal/cliauth ./internal/api`. Add `analytics_changed` over `scripts/cli-analytics*.sql`, `scripts/test_cli_analytics.py`, `scripts/test_product_analytics.py` and the other trigger paths of gitops.yml's `cli-analytics` job, and run `python3 -m unittest scripts/test_cli_analytics.py scripts/test_product_analytics.py` against a Postgres (the tests read `BEX_CLI_ANALYTICS_TEST_CONTAINER`), reusing `scripts/backend-test-deps.sh` if it can supply one. If the analytics half needs more than that, file it as its own note and ship the CLI half.
- **Where.** `scripts/ship-gates.sh` (the branches and its header comment), `scripts/ci_test_inputs.py` if it must know the new inputs.
- **Done when.** A push that changes `lego/cli` runs the CLI suite in the gate. The new step run against `ed70568c4` in a throwaway worktree fails, and so does the analytics step against `ed1452f75`, so each of the two reds above would have been refused at ship. The time the gate gains is measured and written in the commit message.

**Done 2026-11-23.** `scripts/ship-gates.sh` has two new blocking gates, both run in the gate's detached worktree at `HEAD` and before the backend suite (cheapest first).

- **Gate 14, the CLI.** The paths come from `.github/workflows/cli-test.yml`'s own push list through a new `scripts/ci_test_inputs.py --triggered WORKFLOW` mode (no copy to drift), less the paths gate 2 already covers (`lego/backend/internal`, the authz model). It runs the job's three steps with `CI=true` and no `KUBECONFIG`: `scripts/bex-cli-validate.sh`, `go test ./...` in `lego/cli`, and `go test ./internal/cliauth ./internal/api` in `lego/backend` (skipped when the backend suite runs, which holds those packages in full). The `bex-cli-build.sh` release-candidate step is not run.
- **Gate 15, the analytics.** It runs when `scripts/cli-analytics.sql`, `scripts/product-analytics.sql`, either `scripts/test_*_analytics.py`, the Grafana values or an _edited_ migration change (the suites apply a fixed list, so a new migration is no read), against a Postgres container of its own from the digest gitops.yml's `cli-analytics` job pins. `scripts/backend-test-deps.sh` was not reused: it starts four services (17.7 s measured) for the one Postgres the suites need (1.3 s). The container is removed by the `EXIT` trap however the gate ends (checked with a `SIGTERM` mid-suite), and the pull, the container start, the readiness probe and the suites are each bounded (`BEX_SHIP_GATES_STEP_TIMEOUT`, 900 s), because macOS has no `timeout`.
- **Proof against the two reds**, in throwaway worktrees with the new gate: `ed70568c4` fails at the CLI step (`TestBexS3BulkDeletesAskOnATerminalLikeEaObjectsDelete/the_reference`, exit 1), the fixed `0b97bf731` passes; `ed1452f75` fails at the analytics step (`test_command_family_mapping`, exit 1).
- **Time.** A push that changes only `lego/cli`: 6 s before, 116 s after (CLI suite 69 s, adapter packages 24 s). The analytics step is about 19 s (Postgres 1.3 s, suites 17.7 s); the whole gate for an analytics-test push took 27 s.
- **One portability fix the gate needed.** `test_view_replaces_the_released_generation` used `zip(strict=True)` (Python 3.10), which errored on macOS's 3.9 and would have refused every analytics push; it checks the lengths explicitly now.
- **Tests.** `scripts/ship-gates.test.sh` covers both gates with stubbed `go` and `docker` (what runs, `CI=true`, the backend overlap, which files start the analytics gate, a failing suite, a failed start, a Postgres that is never ready, a hung suite, no container left), and eight mutations of the gate (no `CI=true`, container left behind, no backend subtraction, no bound, a new migration starting it, the adapter run twice, `KUBECONFIG` kept, the suites not run) each fail it. `scripts/test_ci_test_inputs.py` covers `--triggered`. The land skill and `lego/AGENTS.md` describe the gates.
