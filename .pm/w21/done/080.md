# 080 — The device confirm page shows only the user code: add the client, scopes and request time if Hydra's admin API can say them before the accept

Why: `/auth/device` (`dashboard/src/common/server-fn/hydra-device.ts`, `DeviceView`) asks a signed-in user to authorize a device and shows `userCode` and nothing else, so the only thing the user can check is that the code matches their terminal. The w21/m394 audit asked for the client name, the scopes, the requesting IP and the time, as a consent screen shows. The client id is only known today from the `redirect_to` the accept PUT returns, which is after the pairing; `acceptDevicePairing` refuses an unexpected client at that point.

- **Source:** w21/m410 t005, 2026-11-14 (the consent token half shipped there).
- **First question:** what Hydra's admin API returns for a `device_challenge` before the accept, in the Hydra version `deploy/gitops/` pins (a get-device-request endpoint, if there is one, and which of client, requested scopes and time it carries). The requesting IP is the CLI's, which the dashboard never sees; the claim in the audit may not be satisfiable and should be recorded as such if so.
- **Size:** about 1h if the endpoint exists (a lookup in `handleDeviceVerification`, a `DeviceView` that carries the label, the page's component and its skeleton at both widths, tests); a record and a delete if it does not.

## Steps

1. Find the endpoint in the pinned Hydra's admin API; if none, write the finding here and close the note.
2. Show the client's name (the first-party device clients are known: `RENDER_CLI_CLIENT_ID`, `bex-desktop`, `OAUTH_PLATFORM_CLIENTS`) and the scopes it asked for on the confirm page, and refuse an unexpected client *before* the accept.
3. Keep the page's loading skeleton matched to its ready state (root `AGENTS.md` rule) and check both at desktop and narrow-mobile widths.

## Finding and closure (2026-11-14)

Step 1 answered: Hydra's admin API offers no read of a device request before the accept. The dashboard's pinned Ory client (`@ory/client-fetch` v1.22.66, generated from the API spec) carries exactly three device endpoints: `PUT /admin/oauth2/auth/requests/device/accept`, `POST /oauth2/device/auth` and `GET /oauth2/device/verify` (`dashboard/node_modules/@ory/client-fetch/dist/apis/OAuth2Api.js`, lines 181, 833, 972). The client id is therefore known only from the `redirect_to` the accept returns, after the pairing, and the scopes, the requesting address and the request time are not exposed to the dashboard at all (the address is the CLI's, which never reaches it). The audit's four fields cannot be shown on the confirm page; what protects it stays what it is: the user compares the code with the terminal's, the grant is never paired on a GET, a same-origin session-bound POST pairs it, and the accept refuses an unexpected client (`unexpected_client`). A client label would need Hydra to expose the request, which is an upstream change, not a dashboard one. No code change.
