# A git-built Docker web service that listens on no port fails with "Set PORT to the HTTP listener", and never says Render's "no open port was detected … create a background worker instead", which w8/259 gave the native runtime only

Why: the commonest first-deploy mistake for a web service that opens no port is a worker created as a web service; w8/259 made the native runtime say so in Render's terms, but a Docker-runtime service with the same mistake is still told to "set PORT to the HTTP listener" and never that a service taking no traffic belongs in a background worker.

**Severity:** minor (failure-path wording; the deploy fails at the right time and the previous release keeps serving). **Estimate:** ~30m (the image-port stall hint, plus a test per variant). **Kind:** sibling of [w8/259](../w8/259.md), whose acceptance and fix cover the native runtime and a private service but not a git-built Docker web service. **Source:** live `/qa-find-bugs` pass 149, 2026-11-12 ~02:45–03:30 UTC, production `https://dashboard.bex.co`, workspace `bex`, deploy pin `c5518dc24` ("pin platform images to e7a56b07e0d7", 2026-11-12T02:23:42Z, which contains the w8/259 fix `c0f74cf29`), filed to w21 per user direction. **Status:** inbox.

## Root cause (code-traced; `origin/main` at `00192f348`)

- `rolloutStallDiagnosis` (`lego/operator/internal/controller/app_controller.go:6012-6023`) builds a web service's stall text from `stuckPodMessage`, then `imagePortStallHint` (`:6033-6054`), then, only for an HTTP-selection fallback, "No port answered HTTP during startup discovery; set PORT to the HTTP listener.", then `detectBoundPort`.
- `detectBoundPort` (`port_detect.go:138-141`) returns "" at once when `explicitServingPort(app)` holds, and that includes `app.Spec.HasImagePorts()` (`port_detect.go:84-86`). A git-built Docker service has image ports from its build, so the scan that carries `noOpenPortMessage` (`port_detect.go:199-202`) never runs for it. The native service has none, so it reaches the scan and gets the sentence.
- `imagePortStallHint` has three variants (no declared TCP ports; a port selected from the declared ports; a port set by `PORT` or a configured port). None ends with the no-traffic alternative, and the "no declared TCP ports" one tells the user to point `PORT` at "the HTTP listener" when the process listens nowhere.
- The private-service sibling (`private_ports.go:233`) already uses the no-open-port sentence.

## Fix (target behavior)

- A Docker or image-backed web service whose TCP check gets no connection ends its in-flight and final reason with Render's two points, as the native one does: no open port was detected, the server must bind `0.0.0.0` on the port in `PORT`, and a service that takes no traffic belongs in a background worker. Keep the image-specific naming of the declared ports where there are some.
- Use one helper for the sentence (`noOpenPortMessage` already exists) rather than a second copy in `imagePortStallHint`.
- An HTTP health check keeps its path-specific text, and a service whose scan found another port keeps "The process is listening on port N" (unchanged).
- Operator only: the text reaches REST, GraphQL, MCP and the dashboard through the deploy's `failureReason` and `stallReason`, so no API shape changes. The zh strings follow w4/566.

## Blast radius (counted by grep)

`imagePortStallHint` has 1 caller (`rolloutStallDiagnosis`, `app_controller.go:6018`); `noOpenPortMessage` has 2 call sites in `detectBoundPort` (`port_detect.go:158,169`) and the private-service text is separate (`private_ports.go:233`). Native web services, private services and the HTTP-selection fallback sentence are the neighbours that must keep their current text and get a regression case.

## Adjacent classes

- A Docker service bound to `127.0.0.1` only reads the same as one that listens nowhere (a closed port on a tenant pod drops the connect, per w8/259), so the same sentence covers it. Not probed here.
- A Docker service whose image declares ports and is bound elsewhere keeps the "primary port selected from the image's declared TCP ports" naming.
- A worker, a cron job and a static site take no TCP check and are unaffected.

## Render

Render's port scan is runtime-agnostic: `Port scan timeout reached, no open ports detected. Bind your service to at least one port. If you don't need to receive traffic on any port, create a background worker instead.` (quoted in w8/259 from Render's troubleshooting page).

(`imagePortStallHint`, `lego/operator/internal/controller/app_controller.go`). An HTTP health check still gets no listener hint, native and private services are unchanged. `TestImagePortStallHintOffersABackgroundWorker` covers the five hint variants, the assembled fallback text and the HTTP-check case, and fails with the old no-declared-ports wording; the full operator suite (`GOWORK=off make test`) passes. **Decision recorded:** the final text says "Nothing accepted a TCP connection on port N" and "No port answered HTTP during startup discovery", not Render's literal "No open port was detected", because the operator does not scan an image-port service's pod when the TCP check fails (`detectBoundPort` skips explicit ports) and so cannot claim nothing was open on any port; the three points Render's message makes (bind `0.0.0.0`, the port in `PORT`, a background worker for a service that needs no traffic) are all present. **Not done:** the production checks of this note's Definition of done (a Free Docker web service with `sleep 3600` ends `update_failed` with the new text, the native control unchanged), which need the deploy, and the zh wording (w4/566's table does not carry these sentences).
