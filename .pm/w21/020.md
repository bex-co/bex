# Postgres Recovery: the restore dialog's "Point in time" is sent as UTC although the recovery window beside it is shown in the viewer's local time, and nothing bounds it to the window

Why: a user restoring "to just before the bad migration at 3 PM" gets the database as of 3 PM UTC (8 hours earlier in Los Angeles, 8 hours in the future in China), and nothing on the form says the field is UTC.

**Severity:** major (a silent wrong restore point; the new restore database is paid capacity). **Estimate:** 45m (dashboard conversion, input bounds and a test; the backend bound check is an optional second layer, about 30m more). **Source:** live `/qa-find-bugs` pass 14, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (read-only; the mutation was intercepted and aborted before it left the browser)

1. Open `/databases/dpg-d9rs3ee0ccis738kc7c0` (`blockeden-forum-db`, an existing database of the workspace, 31 daily backups) and scroll to Recovery. The browser's zone was `America/Los_Angeles` (`getTimezoneOffset()` 480). The panel shows **Earliest restore point** "October 10, 2026 at 8:01 PM", whose `<time datetime>` is `2026-10-11T03:01:34Z`, and **Latest restore point** "November 9, 2026 at 7:01 PM" (`2026-11-10T03:01:05Z`).
2. Click "Restore to new instance". The dialog has `#restore-name` and `#restore-time`, a `datetime-local` input with no `min`, `max` or time-zone text; its helper says only "Leave empty to restore the latest available point."
3. Fill the name `qa-20261110-restore-probe` and the time `2026-10-10T20:01` (the earliest restore point exactly as the panel displays it), with `page.route(/\/graphql/)` set to abort any mutation, then click Restore. The captured request body:

   ```json
   [
     {
       "operationName": "RecoverDatabase",
       "variables": {
         "id": "dpg-d9rs3ee0ccis738kc7c0",
         "name": "qa-20261110-restore-probe",
         "targetTime": "2026-10-10T20:01:00Z"
       },
       "query": "mutation RecoverDatabase($id: String!, $name: String!, $targetTime: String, $plan: String, $version: String) { recoverDatabase(...) { id name plan status __typename } }"
     }
   ]
   ```

   `2026-10-10T20:01:00Z` is **7 hours before** the earliest restore point (`2026-10-11T03:01:34Z`), although the user picked the very value the panel labels earliest.

4. Without the interception, the same dialog accepts `2026-09-01T12:00` and `2027-01-01T12:00` with Restore enabled and no message (checked, then Cancel).
5. After the probe: `databases(limit:50)` still lists only the 4 original databases, so nothing was created.

**Evidence:** the request body above is the durable artifact; the aborted mutation never reached `api.bex.co`.

## Root cause

- **Conversion (certain):** `dashboard/src/features/databases/components/recovery-panel.tsx:62-63`: `const iso = targetTime ? \`${targetTime}:00Z\` : undefined;`. A `datetime-local` value is the viewer's local wall time, and the code labels it UTC. The window right above it is rendered by `LocalDateTime` (`:106`, `:115`, made viewer-local by w6/m107), so the form and its own reference points use different clocks. For a viewer at UTC−N the sent instant is N hours earlier than picked; for UTC+N it is N hours later, which for N≥1 east of the latest point is in the future.
- **The right pattern already exists in the same app:** `dashboard/src/features/metrics/components/range-select.tsx:282` `fromLocalInput` (`new Date(value).toISOString()`) and `dashboard/src/features/webhooks/components/webhook-deliveries-card.tsx:70-73` `toAPITime`. `grep -nE '\}:00Z'` over `dashboard/src` finds only this one site, so the pattern is not repeated elsewhere. The automations `schedule-picker.tsx:158` labels its zone with `help.runAt {zone}`.
- **No bounds (second layer):** `lego/backend/internal/postgres/recovery.go:255` `core.ParseTime("targetTime", …)` only checks the RFC3339 shape; `recoveryWindow` is read at `:264` but only `window.established()` (`:268`) is checked, never `earliest <= targetTime <= now`. The target goes straight to `Spec.Recovery.TargetTime` and on to CNPG `recoveryTarget.targetTime` (`lego/operator/internal/controller/database_controller.go:556-557`). ADR009 `:209` states the rule the check was built for: an unsubstantiated restore "can never provision a paid instance that cannot bootstrap (w6/m117)", and the 2026-07-28 drill (`docs/drills/2026-07-28-barman-plugin-pitr.md:25`) shows CNPG refusing to promote until an archived commit exists after the target and then retrying only a bounded number of times.

## Fix (target behavior)

1. **UI, the conversion (always):** a time picked in the dialog is sent as the instant it denotes in the viewer's zone (`new Date(value).toISOString()`, not `${value}:00Z`). Picking the wall time shown as the earliest or latest restore point sends that exact instant to the minute. The field's label or helper names the time zone ("Your local time (America/Los_Angeles)"), in `en` and `zh`.
2. **UI, input bounds:** the input carries `min` from the earliest restore point and `max` from now (as local wall-time strings), and Restore is disabled with an inline reason when the value is outside them. The upper bound is now, not the "Latest restore point" (last successful base backup, `recovery.go:182` `lastSuccessfulBackupTime`), because ADR009 `:206` says PITR is WAL-based, so a target after the last base backup but before the last archived WAL is valid.
3. **Backend (optional second layer, global):** `Service.Recover` refuses a `targetTime` before `window.earliest` or after now with a named 400, before any billing gate, as `:268` already does for an unestablished window. All callers share it: REST `POST …/recover` (`rest.go:334-339`), the Render-shaped `POST …/recovery` (`rest.go:311-329`), GraphQL `recoverDatabase` (`graphql.go:696`) and MCP `recover_postgres` (`mcp.go:285`).
4. REST, GraphQL and MCP already take an explicit RFC3339 instant, so items 1 and 2 change the dashboard only.

## Blast radius (counted by grep on the working tree)

- Dashboard: one caller of the `RecoverDatabase` mutation (`use-recovery.ts:160-164`, `targetTime: input.targetTime || null`) and one source of the value (`recovery-panel.tsx:63`). No other `${…}:00Z` in `dashboard/src`.
- Backend (item 3 only): `Service.Recover` has 4 non-test call sites in `lego/backend/internal/postgres/` (`mcp.go:285`, `graphql.go:696`, `rest.go:329`, `rest.go:339`). A 5th hit for `.Recover(` (`billing/worker.go:120`) is the billing enforcer's own method, unrelated. Existing tests pass `TargetTime: "2026-07-09T10:00:00Z"` (`advanced_test.go:298`, `:973`, `:1039`, `:1059`) against a fixture window, which must be checked against the new bounds before the check lands.
- Mobile: the native app exposes no PITR input (`docs/ADR018-render-parity.md` mobile safe-actions paragraph: "never supplies … PITR"), so no client there.

## Adjacent classes

- A target inside the window: unchanged. An empty target ("latest"): unchanged.
- A malformed string keeps its current named 400 (`advanced_test.go:347`).
- Unauthenticated, forbidden and not-found answers are decided before this check (`fetchDatabase` with `RelCanCreate`, `recovery.go:233`), so the new 400 discloses nothing a `can_create` caller could not already read from `databaseRecoveryInfo`.

## Unverified (not probed this run)

What the drill shows (CNPG refuses to promote without an archived commit after the target, then fails after bounded retries) is inferred to apply, not observed for a before-window or future target.
- Whether "Latest restore point" (the last successful base backup) understates the true WAL-based latest; not investigated.
