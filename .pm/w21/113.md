# 113 — S3 object metadata names come back capitalised (`X-Amz-Meta-K`), so boto3 and aws-cli read `{'K': 'v'}` where S3 returns `{'k': 'v'}`

Why: boto3 and the AWS CLI do not lowercase metadata keys, so a customer who stores `Metadata={'mtime': …}` and reads `head['Metadata']['mtime']` gets a `KeyError` on bex and not on S3.

- **Source:** w21/m498 t019, 2026-11-19, observed on production with aws-cli 1.44.87: `copy-object --metadata k=v --metadata-directive REPLACE` then `head-object` printed `{'K': 'v'}` (the aws-cli, which shows botocore's parse).
- **Cause:** `handlers_object.go` writes `h.Set("x-amz-meta-"+k, v)`, which canonicalises the name, and Traefik (a Go proxy) canonicalises a backend's header names again on HTTP/1.1, so a lowercase write in `bex-s3` would not survive the edge. The AWS SDK for Go v2 lowercases keys itself, botocore does not, rclone is expected to (not run).
- **Verify first:** that it is not fixable inside bex alone (a request over HTTP/2 gets lowercase names; HTTP/1.1 clients do not), and whether `aws` v2, rclone and boto3 show the same.
- **End state:** if no edge setting or response form returns lowercase names to HTTP/1.1 clients, the difference is a dated, evidence-backed entry in ADR018's S3 rows and in the S3 section of `docs/bex-cli.md` (with the boto3 example and the workaround of reading keys case-insensitively), and a test pins today's behaviour so a change is noticed; if a way exists, ship it with a test through the same path the walk used.
