## Objective

Decide and record what the 11 workspaces stuck in `enforcing` should be, make the rows settle after t001 and t002 are deployed, and confirm on production that the error is gone.

## Context

- Found 2026-11-08: 11 `billing_lifecycles` rows with `status='enforcing'`, `attempt_count` about 21,000, empty `last_error`, every tenant still existing; `billing lifecycle: no rows in result set` logged 1,147 times in 7 hours ([`finding.md`](finding.md)).
- `Enforce` has run for these rows on every lease, so their effective state is already enforced; once t001 ships, `Complete` flips the row to `enforced`. With a mapping it would also queue a notice (`notifyBillingStatus(enforcing, enforced)`); without one t001 skips it. A row whose workspace should not be enforced (first-party, comped, excluded) must be corrected first, through the sanctioned override (`SetBillingException`, `ForceBillingRecovery`).
- Reading the rows and the log needs production cluster access (`kubectl -n bex-system exec` into `bex-db`, `kubectl -n bex-system logs deploy/bex-api`); this worker has no such access today (w21/012's gate: `~/.ssh/id_bex` for `scripts/fetch-app-kubeconfig.sh`).

## Steps

1. If access exists: read the 11 rows (`workspace_id`, `reason`, `grace_deadline`, `attempt_count`, whether a `billing_provider_mappings` row exists) and decide per row what it should be: leave enforced, exclude or comp, or recover. Record the table and the reasons in `finding.md`.
2. Apply any correction before t001 ships, through the override paths above.
3. After the deploy that carries t001 and t002: count `billing lifecycle: no rows in result set` in the bex-api log over an hour (expect 0) and `SELECT count(*) FROM billing_lifecycles WHERE status='enforcing' AND attempt_count > 100` (expect 0). Record both.
4. If there is no access: record the exact commands in `finding.md` and park the milestone as BLOCKED on the cluster read once t001–t003 are shipped (the `/loopx` rule for a gate only the user can clear).
