# 090 — An operator who revokes a token or consent session at Hydra has no way to make every bex-api replica refuse it at once

Why: w21/085 bounds a direct Hydra revocation at 5 s, but a direct revocation never writes the shared `oauth_revocations` row, so the bound is the best bex-api can do for it; an incident response that must cut a stolen token off now needs a path that does.

- **Source:** w21/085, 2026-11-15. Revocation through bex (`POST /v1/oauth/revoke`, the dashboard's connected-app revoke, API-key revoke) already writes the row and is refused at the next request on every replica (`lego/backend/internal/store/oauth_revocations.go`, `docs/ADR012-auth.md` §8d). An operator holding Hydra's admin API, or a client calling `oauth.bex.co/oauth2/revoke` itself, bypasses it.

## Steps

1. Decide the smallest operator path: a script (`scripts/revoke-oauth-subject.sh <subject> <client>`) that revokes the consent session at Hydra admin and writes the `oauth_revocations` row for the same pair, or a bex-api admin route behind the ops-workspace gate that does both. Pick the one that needs no new credential beyond what the operator already holds, and ship it.
2. Test it against two replicas that share the marker: a token warm on both is refused on both at the next request, with no wait.
3. Name the path in `docs/ADR012-auth.md` §8d and add a short runbook under `docs/runbooks/` for cutting off a stolen token.

## Done when

- [ ] One command or one admin call revokes a human's grant at Hydra and every bex-api replica refuses the token at its next request, shown by a test and once on production.
