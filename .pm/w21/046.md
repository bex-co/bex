# A webhook whose Destination URL is a loopback, private or cluster-internal address is accepted ("Webhook created") and then every delivery fails as "Transport error", although the same server already refuses literal unsafe hosts at save for three other inputs

Why: pasting a local address such as `https://localhost:3000/hook` into a webhook is a common developer mistake; today the create answers success, the webhook shows Enabled, and the user finds out from a row that reads "Transport error", with a retry schedule of up to eight attempts over about 33 hours.

**Severity:** minor (the delivery detail does name the cause and the guard itself works; the miss is that the user is told the save succeeded for a destination that can never receive). **Estimate:** 35m (refuse literal unsafe hosts in `parseDestination` with the shared predicate, mirror the literal-host rule inline in the form, a clearer row label, tests). **Source:** live `/qa-find-bugs` pass 53, 2026-11-11 01:2x UTC, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction; method: a server-versus-form differential on the webhook Destination URL. **Status:** inbox.

## Reproduction (own webhook `qa-20261110-whlocal`, `whk-dbps6ldhi5vc738gj0h0`, events Deploy Started and Deploy Ended; own static site `qa-20261110-whev`, `srv-dbps6pfbq3ic73c0a8s0`, only there to fire the events; both deleted in the same visit)

1. **Server verdicts** over REST `POST /v1/webhooks` (`enabled: false`, `eventFilter: ["image_pull_failed"]`, each created webhook deleted in the same call, nothing left behind):
   - 400 for `http://example.com/hook`, `ftp://example.com/x`, `//example.com/x` and `https://exa mple.com/x` ("url must be an absolute HTTPS URL"), for `https://user:pass@example.com/x` ("url must not embed credentials in userinfo…") and for a 3000-character host ("url must be at most 2048 bytes").
   - **201** for `https://localhost/x`, `https://127.0.0.1/x`, `https://169.254.169.254/latest/meta-data`, `https://[::1]/x` and `https://x.svc.cluster.local/x`; also for `https://example.com:22/x`, `https://./x`, `HTTPS://EXAMPLE.COM/x`, `https://example.com/x#frag` and an internationalized host.
2. **The form** on `/webhooks/new`:
   - The Destination URL field keeps `aria-invalid=false` on blur for `http://example.com/hook`, `ftp://x` and `https://localhost:3000/hook`.
   - On Create webhook the `http://` value is refused inline ("Enter an absolute HTTPS URL without embedded credentials."), so the form mirrors the scheme and userinfo rules.
   - `https://localhost:3000/hook` saves with the toast "Webhook created" and Status Enabled.
3. **Firing events.** Deploying the static site produced Deploy Started at 01:22:5x and Deploy Ended at 01:23:2x. The webhook's Recent deliveries then read Deploy Started "Failed 1 Transport error", "Failed 2 Transport error" (the 30 s retry) and Deploy Ended "Failed 1 Transport error".
   - Opening a row's detail shows the request payload and, under Endpoint response, `Post "https://localhost:3000/…": destination resolves to a blocked address`, with "Next automatic attempt" a minute later.
   - So the reason exists, but only behind a click; the list row says only "Transport error".

## Root cause (code-traced; `origin/main` has no code change since the last pin)

- `lego/backend/internal/webhooks/service.go:933-952` `parseDestination` checks only scheme `https`, a non-empty host, no userinfo and at most `store.MaxWebhookURLBytes`. It has 2 callers: create (`:521`) and update (`:903`).
- The guard is dial-time only: `webhooks/worker.go:250-262`, `deliveryTransport` uses `netutil.SafeDialContext` (`lego/types/netutil/ssrf.go:103`), and redirects are never followed. So every delivery to such a host fails after the endpoint is stored.
- The same predicate already refuses a literal unsafe host at save for three other tenant-supplied destinations, all via `netutil.UnsafeOriginIP` (`lego/types/netutil/ssrf.go:71`):
  - the static-site rewrite target, `apps/service.go:5687-5720` `validatePublicRewriteHost` (an IP in a non-public range, a single-label host, or a `.localhost`, `.local`, `.internal`, `.lan`, `.svc`, `.cluster.local`, `.home.arpa` suffix);
  - a public git URL, `github/public_git.go:118`;
  - an image reference, `store/image.go:70`.

## Fix (target behavior)

- `parseDestination` refuses a destination whose literal host is unsafe, with the same literal-host rule and a message that names the reason, for example "url must be a publicly reachable HTTPS address, not a loopback, private, link-local or cluster-internal host".
- REST create and update, GraphQL and MCP share it, so one change covers all. Hostnames that merely resolve to a private address stay caught at dial time, as `validatePublicRewriteHost` documents for rewrites.
- The form mirrors the literal-host rule inline (the field's existing "Enter an absolute HTTPS URL…" message pattern), so Create is held.
- The delivery row labels a blocked destination "Destination not allowed" instead of "Transport error" for that cause; the detail text already says "destination resolves to a blocked address".

## Blast radius (counted by grep)

- `parseDestination` has 2 callers in `webhooks/service.go` (create and update), behind REST `POST` and `PATCH /v1/webhooks`, GraphQL and MCP.
- The static-site rewrite check is the model (1 caller).
- Webhooks already stored with such a host keep failing and are not migrated (an enabled one could be listed for the operator).

## Adjacent classes

- A hostname that resolves to a private address stays a dial-time failure.
- Redirects are never followed (a 3xx is a failure).
- A public host on a non-standard port such as `:22` is accepted and stays so (the guard is by address, not port).

## Render

## Dedupe / precedent

## Definition of done (each bullet is repeatable with the probe above)

- On production, a REST create or update and the form refuse `https://localhost/x`, `https://127.0.0.1/x`, `https://169.254.169.254/x`, `https://[::1]/x` and `https://x.svc.cluster.local/x` with a message naming the reason, and nothing is stored.
- A public `https://` URL still saves.
- A hostname that resolves to a private address is still refused at delivery, and its row reads "Destination not allowed".
- The new tests fail if the literal-host check is removed.
