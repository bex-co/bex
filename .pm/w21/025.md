# A Logs (and Deploys) load failure is not announced to assistive technology: the first-load error state is a plain `EmptyState` with no role, while the same viewer's later-error banner has `role="alert"`

Why: a screen-reader user who types a bad filter into the Logs search box (the new `path:/(unclosed/` field operators, w4/538) sees the list vanish and hears nothing, while a sighted user gets "Couldn't load logs" with the reason.

**Severity:** minor (accessibility, WCAG 4.1.3 Status Messages; nothing is lost for sighted users). **Estimate:** 25m (one optional prop on `EmptyState`, set at the error call sites, tests). **Source:** live `/qa-find-bugs` pass 21, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (read-only; a search filter in the URL, nothing is created)

1. Open `/services/srv-d9ndt8hmcglc739fkp50/logs?range=24h` (an existing service) and type `path:/(unclosed/` into "Search logs". The box becomes a Request path chip (`?path=%2F%28unclosed%2F`) and the pane shows the failure card "Couldn't load logs" over `Invalid path filter "/(unclosed/": error parsing regexp: missing closing ): `(unclosed``. Same in `?lang=zh` ("无法加载日志").
2. From those text nodes, walk up five ancestors: only `p` and `div` elements, no `role`, no `aria-live`. `main.querySelectorAll('[role=alert]')` is empty.
3. API control, read-only, from the page: `logs(resource:"srv-d9ndt8hmcglc739fkp50", type:"request", path:["/(unclosed/"]){ hasMore logs{ timestamp } }` answers `bad request: invalid path filter "/(unclosed/": error parsing regexp: missing closing ): `(unclosed``; a `path` value of 5000 characters answers `invalid path filter: the value is longer than 1024 bytes`; `statusCode:["abc"]` answers HTTP 200 with 0 rows (accepted, matches nothing). So the failure is a real server refusal, rendered correctly for sighted users and silent for assistive technology.

**Evidence:** the ancestor chain and the empty `[role=alert]` list are the durable probes; nothing was created.

## Root cause

- `dashboard/src/features/logs/components/log-empty-state.tsx:35-44` (`reason: "timeout"`) and `:45-54` (`reason: "failed"`) render `EmptyState` with `iconName="AlertCircle"`. `dashboard/src/common/components/empty-state.tsx:32` `EmptyState` renders the title and description as two `<p>` (`:41-42`) with no `role` and no `aria-live`.
- The same viewer already does the right thing for the other failure: when lines are already on screen and a later read is refused, `dashboard/src/features/logs/components/log-viewer.tsx:293` renders the message in a `<div role="alert">`. So only the first-load failure, the one that replaces the whole pane, is silent. The deploy detail page has the same split: its first-load failure is a bare `EmptyState` (`deploy-detail-page.tsx:93`) and its later inline retry has `role="alert"` (`:109`).
- The rest of the dashboard announces its errors: 59 non-test files use `role="alert"` (for example `dashboard/src/features/databases/components/recovery-panel.tsx:91` for its own load error).

## Fix (target behavior)

An error state announces itself. `EmptyState` gets an optional `role` (or a `tone="error"` that sets `role="alert"`), set for the four error sites below and for nothing else; the visible copy, icon and layout do not change. The 6 other `EmptyState` uses are empty or notice states ("No logs in this time range", a store-unavailable notice and the like; they were not each read for this note, so the implementer confirms none is an error) and stay silent. UI only; REST, GraphQL and MCP are unchanged.

- Only the service Logs viewer was triggered live. The datastore viewer, the deploy log panel, the deploy detail page and the Deploys list error state are traced to the same component, not triggered.

## Adjacent classes

- A search that matches nothing ("No matching logs") is an empty state, not an error, and stays silent.
- A 401 (session expired) has its own state and is not changed. Not an authorization matter.
- The server-authored English reason in the zh page ("Invalid path filter …") is the class declined in w21/017 ("Considered and not filed") and is not part of this note.
