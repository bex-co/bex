# 077 — Verify against Render the limits the validation corpus pins and no Render source states

Why: the corpus pins what bex's server does today, and several of its limits have no stated Render counterpart. Render parity is the top product rule, and a stricter-than-Render rule stands only with an ADR018 entry the user signed off. None of these is a known divergence; each needs Render's actual behavior before it is called equal, stricter or looser. Recording that now keeps the corpus from hardening an unchecked rule as parity.

- **Source:** w21/m396 t006 Render parity check, 2026-11-14. The pinned OpenAPI (`render-public-api-1.json`) was scanned for every `maxLength`, `minLength`, `pattern` and `maxItems`: none sits on a service, project, environment, Postgres or Key Value name, `rootDir`, `dockerfilePath`, `dockerContext`, `repo`, `imagePath`, `cidrBlock`, an environment variable value, a custom domain `name` or a registry credential field. The render.com pages for custom domains, environment variables, web services, private network, monorepo support, Docker, deploying an image, projects, Postgres, Key Value and deploy to Render state none of the limits below.
- **The rules** (file, corpus file):
  - label: at most 100 code points, no control characters or line separators (`core/errors.go:388`, `label.json`). ADR018:93 says "Bex policy, Render limit unverified" for a service name and :110 records the free-form name rule; no sign-off for the limit is recorded.
  - root directory, Docker build context, Dockerfile path: relative, no `..` or empty segment, no backslash, no NUL/CR/LF/TAB, at most 512 bytes (`store/api.go:697`, `root-dir.json`, `build-path.json`).
  - environment variable value: no NUL byte, and KEY=value plus the terminator at most 131072 bytes (`core/config.go:172`, `env-value.json`). The limit is Linux's `MAX_ARG_STRLEN`, a platform fact, but Render's own limit is unknown.
  - Docker image reference: at most 512 bytes, localhost, private, reserved and single-label registry hosts refused (`store/image.go:42`, `docker-image.json`). Render's page says "any registry Render can reach".
  - custom domain: each label at most 63 octets, a numeric top-level label, an IP literal, a single label and a public suffix refused (`apps/domains.go:399-445`, `custom-domain.json`). ADR018:196 records only the public-suffix refusal.
  - repository URL: `https://`, plus GitHub's two SSH spellings, no userinfo or `#`, at most 2048 bytes (`store/api.go:644`, `repo-url.json`). Render's deploy page says "full `https://` URL" and states no SSH rule (ADR026:104, w8/130, records the SSH spelling).
  - registry credential host: bare host[:port] within 253 bytes (`registrycreds/host.go:39`, `registry-host.json`). Render has no host field (its create body takes an enum), so this is a bex extension ADR018:258 records without the grammar.
- **Size:** about 20m per rule against a Render workspace; the rules that cannot be checked without a Render account are the gate.

## Steps

1. For each rule, make the smallest probe Render's dashboard or API allows (create a service with a 101-code-point name, a 513-byte root directory, a label of 64 characters in a custom domain, and so on) and record the response here.
2. A rule that is equal needs one line in ADR018's checked list. A rule that is stricter needs a conforming change to the server (the corpus then pins the conformed rule) or an ADR018 entry with the user's sign-off. A rule that is looser is recorded the same way.
3. Keep the corpus and the client validators in step with every change.
