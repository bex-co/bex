# 075 — Reconcile Render's "Only IPv4 CIDR ranges are supported" with the IPv6 entries bex's inbound IP rules accept

Why: Render parity is the top product rule (ADR008 § Render parity first). Render's inbound IP rules page states an IPv4-only rule in one sentence, and bex's shared gate `core.ValidateCIDRs` (`netip.ParsePrefix`) accepts an IPv6 entry for the same rules. ADR018:199 says a service list is saved and read back as written, `::/0` included, "as on Render and its Terraform provider", which points the other way, so which side is stale is not yet known and no divergence is recorded for it.

- **Source:** w21/m396 t006 Render parity check, 2026-11-14. Render's wording read on 2026-11-14 at `https://render.com/docs/inbound-ip-rules`: "Only IPv4 CIDR ranges are supported." and "Inbound IP rules are allowlists of IP ranges you specify using CIDR notation." The page states no maximum number of rules. The pinned OpenAPI (`render-public-api-1.json`) carries no `pattern` or `maxItems` on `cidrBlock`.
- **Evidence:** `lego/backend/internal/core/cidr.go:39` (`ValidateCIDRs`) is the one gate. Environment rules reach it at `environments/service.go:1586`, workspace rules at `workspaces/ip_rules.go:76`, project-created environments at `projects/service.go:471`, and Postgres / Key Value at `postgres/service.go:925,1413` and `keyvalue/service.go:615,1153`. The corpus `lego/backend/testdata/validation/cidr.json` pins `2001:db8::/32`, `::/0` and `::ffff:10.0.0.1/128` as valid today. ADR018:199 mentions an IPv6 side only for ingress (w8/285).
- **Conflicting evidence:** ADR018:199 records that a service `ipAllowList` containing `::/0` is saved and read back as written, as on Render and its Terraform provider, and that its middleware admits every IPv4 source and no IPv6 one (no service host publishes an AAAA record). So Render's API evidently carries `::/0` on a service rule even though the docs page says IPv4 only.
- **Not established:** whether Render's API refuses an IPv6 `cidrBlock` on a service rule (the docs say so; no response was captured), and whether Render's Postgres and Key Value rules are IPv4-only too (those pages say "CIDR notation" and are silent on the version). `core.UnrestrictedAllowList` writes `::/0` beside `0.0.0.0/0` for a datastore, so the datastore side must not change on the docs sentence alone.
- **Size:** about 45m once the Render behavior is known.

## Steps

1. Capture Render's answer to an IPv6 entry other than `::/0` (for example `2001:db8::/32`) on an environment or workspace inbound rule (a response or a dashboard message, not a docs paraphrase), and record it here beside ADR018:199's `::/0` evidence.
2. If Render refuses a non-default IPv6 entry, the parity-sufficient change is to refuse a new IPv6 entry on the service-inbound surfaces (environment, workspace) with a coded 400, while a stored IPv6 rule keeps being read and enforced so no saved rule breaks. Add the cases to `cidr.json` only as the server's verdict changes, and mirror it in `dashboard/src/common/lib/cidr.ts` (the client may not refuse what the server accepts).
3. If Render accepts it, record in ADR018 that the docs sentence is stale (and that `::/0` is the entry Render itself writes) and close this note.
4. Either way, record the datastore surfaces' IPv6 behavior in ADR018 with the source.
