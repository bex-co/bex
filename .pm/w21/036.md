# The New Project, New Environment, New Environment Group, webhook, registry credential and Blueprint name fields never apply the label rule the server enforces: a 101-character name passes the form and comes back as an English "Display name must be at most 100 Unicode code points" toast (w4/419 fixed the server, not the dashboard)

Why: the dashboard already mirrors `core.CheckLabel` as `isValidLabel` and uses it for services, Postgres, Key Value and workspaces, but the other writers that [w4/419](../w4/done/419.md) and [w4/491](../w4/done/491.md) put behind the same server rule still check only "non-empty", so a user finds out after submit, from a server toast that calls a project name a "display name".

**Severity:** minor (a refusal that the form could have prevented; no data lost). **Estimate:** 60m (one shared check in 10 form surfaces, an inline message in en and zh, tests). **Kind:** gap in the cross-surface guarantee of w4/419 and w4/491 (the dashboard was not on their list). **Source:** live `/qa-find-bugs` pass 33, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, zh UI, filed to w21 per user direction. **Status:** inbox.

The dialog stays open with no inline error, and a toast reads "Display name must be at most 100 Unicode code points": English in the Chinese UI, and "display name" for a project name.

## Fix (target behavior)

- Each form in the table validates its name with `isValidLabel`, the way the service form does. It shows the same plain inline message the Postgres form uses (`databases.nameInvalid`: "Enter a name of up to 100 characters, without line breaks or control characters.", with a per-feature key in en and zh) and keeps submit disabled while the name is invalid. The server refusal is then unreachable from the UI.
- `isValidEnvGroupName` becomes `isValidLabel`, and its stale comment is corrected. The webhook form keeps its duplicate rule.
- The input `maxLength={100}` attribute is optional. It never lets through more than 100 code points, but UTF-16 units over-count astral characters (an emoji counts as 2), so it can stop an emoji-heavy name early; the inline `isValidLabel` message is the required part.
- REST, GraphQL and MCP already refuse these names with `DISPLAY_NAME_TOO_LONG` / `DISPLAY_NAME_CONTROL_CHARACTER`, so there is no backend change.
