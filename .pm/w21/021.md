# The webhook event picker shows the raw `disk_snapshot_restored` under "Other" (en and zh): w2/064 added the served type without a picker label, the same leak w4/039 fixed for `service_moved`, and no guard test exists

Why: the subscription picker is where a customer chooses which events reach their endpoint, and one served event reads as a snake_case enum in both languages while the other 60 are humanized.

**Severity:** minor (copy leak, nothing breaks). **Estimate:** 30m (one catalog entry, en/zh strings and a test; the optional drift guard is about 30m more). **Kind:** regression of the [w4/039](../w4/done/039.md) class. **Source:** live `/qa-find-bugs` pass 15, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Reproduction (read-only; the create form was opened, never submitted)

1. Open `https://dashboard.bex.co/webhooks/new?lang=en`, then `?lang=zh`. Take `await page.locator('main').ariaSnapshot()` and list the checkboxes.
2. Both languages show 78 checkboxes in the snapshot. Exactly **one** has a snake_case accessible name (matched with `checkbox "[a-z]+(_[a-z]+)+"`): `checkbox "disk_snapshot_restored"`. It sits under the group `Other` (zh `其他`, toggle `展开/收起 其他 事件`) as the group's only member.
3. Control: the other served events all render humanized. The vocabulary read from the page is `{ webhookEventTypes }`, 61 types including `disk_snapshot_restored`, so the one raw name is the only served type the catalog does not know.

**Evidence:** the ariaSnapshot lines above (en `- text: Other` / `- checkbox "disk_snapshot_restored"`; zh `- text: 其他` / the same checkbox) and the `webhookEventTypes` response are the durable probes; nothing was created.

## Root cause

- `dashboard/src/features/webhooks/event-catalog.ts:38`: the `disk` group lists only `disk_created`, `disk_updated`, `disk_deleted`, and `SINGLES` (`:84`) holds only `branch_deleted`, `job_run_ended`, `service_moved`. So `eventLabelKey` (`:99`) returns `null` and `catalogEntries` (`:146`) places the type in the `other` group with its raw key, the deliberate unknown-future-key fallback.
- `dashboard/src/features/webhooks/locales/en.ts:607-618` (zh `:594-605`) has `webhooks.event.disk_created|updated|deleted` and nothing for `disk_snapshot_restored`.
- The label already exists in the **other** catalog, the service Events feed: `services.eventsTypeDiskSnapshotRestored` (en "Disk snapshot restored", `dashboard/src/features/services/locales/en.ts:4615`; zh "已从快照恢复磁盘", `zh.ts:4507`). That is the "dashboard event label (en/zh)" that [w2/064](../w2/done/064.md) (done 2026-11-03) delivered, so its done record is accurate for the Events tab and says nothing about this picker.
- Why it recurs: w4/039 wrote "only `service_moved` came back raw, so it is currently the only un-labeled served event" and pinned that one key (`dashboard/src/features/webhooks/components/__tests__/event-picker.test.tsx:106`), but added no check that every served type has a label. The served vocabulary (`webhooks.EventTypes`, `lego/backend/internal/webhooks/service.go:287`) is guarded against Render's fixture (`webhooks/vocabulary_test.go`), and nothing reaches the dashboard catalog, so w2/064 added a served type that nobody connected to the picker.

## Fix (target behavior)

1. Every type in the served vocabulary renders a humanized label in `en` and `zh` in the picker, with no snake_case name left. `disk_snapshot_restored` joins the `disk` group (a disk event; placing it as a bare single instead is a copy decision this note does not need), labelled in the Events catalog's wording ("Disk snapshot restored" / "已从快照恢复磁盘", matched in case to the neighbouring "Disk Created"-style labels).
2. A guard so the next served type cannot leak: a test fails when any type in the served vocabulary has no `webhooks.event.<type>` key in both locales. The backend list is the source of truth, so the guard either reads `webhooks.EventTypes` through a Go test that parses `event-catalog.ts` and both locale files, or a dashboard test over a vocabulary snapshot that a backend test keeps in step. Which side hosts it is the implementer's call; the requirement is that adding a served type without a label fails CI.
3. UI only. REST, GraphQL and MCP already serve the type correctly.

## Blast radius (counted by grep on the working tree)

- `eventLabelKey` has 4 non-test consumers: `components/event-picker.tsx` (through `catalogEntries`, `event-catalog.ts:118`), `webhook-event-chips.tsx:28`, `webhooks-panel.tsx:64` and `webhook-deliveries-card.tsx:382`. One catalog entry fixes all four.
- Only the picker was seen live. A subscribed-event chip, the panel's event list and a delivery row for this type would render the same raw string by the same function, but no webhook on the probed account subscribes to the type and no delivery exists, so those three are traced, not observed.
- Existing tests that count entries or groups (`event-picker.test.tsx:49`, `:62`, `:71`) must be re-checked after the `disk` group gains a member.

## Adjacent classes

- Unknown future keys keep degrading to "Other" with the raw key, never hidden or thrown (`event-catalog.ts:6-7`); that fallback stays, and the guard is what keeps it from being exercised in production.
- Not an authorization matter. On parity: [`docs/render-artifacts/fixtures/render-webhook-vocabulary-2026-11-02.json`](../../docs/render-artifacts/fixtures/render-webhook-vocabulary-2026-11-02.json) lists `disk_snapshot_restored` in `renderOpenAPI`, `apiOnly` and `bexSupported` and not in `renderDashboard`, but that dashboard list was captured on 2026-08-17, before the type existed, so it says nothing about what Render's picker shows today. The label is bex-side presentation of a type bex already serves; no ADR018 divergence is created either way.
