## Objective

The operand gate passes for an image whose allowlist holds the extensions that passed, and states each failure; the operator's allowlist is derived from those verdicts.

## Context

- `deploy/pg-operand/check.sh:187-206` runs one ordinary-owner restore chain: `CREATE EXTENSION timescaledb; SELECT timescaledb_pre_restore()`, `pg_restore`, `timescaledb_post_restore()`, the pg_ivm sidecar, then IMMV and hypertable checks. TimescaleDB's first step fails, so pg_ivm's owner restore has never run. The final `fail` at `check.sh:239` makes the job fail.
- The restore section has unconditional TimescaleDB lines (`check.sh:193-200`, `:212`, `:230-233`) that need `has timescaledb` guards.
- `.github/workflows/pg-operand-image.yml:168-172` loops `for arch in arm64 amd64` under `bash -e`, so a failing arm64 leg skips amd64.
- `deploy/pg-operand/matrix.json` lists `extensions` per major; `renderExtensions()` in `lego/operator/internal/controller/database_operand.go:52` is the operator's copy, kept equal by `TestPGExtensionAllowlistMatchesTheImageGate` (`database_operand_test.go:40`).
- Every major's container reported `cgroup_memory_peak_bytes=268435456`, its 256 MiB limit (run `45019148603`).

## Steps

1. Split the ordinary-owner restore into one attempt per extension family (TimescaleDB, pg_ivm, the rest), each into its own database, each printing `owner_restore_<ext>=PASS|FAIL` with its exact error kept.
2. Add a per-major `admitted` list to `matrix.json` (the extensions whose verdicts passed) beside `extensions` (what the image carries). The gate fails when an `admitted` extension fails, or when an extension passes but is not admitted (so the list cannot silently go stale).
3. Make `renderExtensions()` (or its replacement) return the `admitted` lists; update the drift test to compare against `admitted`.
4. Run both architecture legs every time and fail the step at the end if either failed.
5. Print `memory.stat` `anon` beside `memory.peak`.
