# Revoking or deleting an API key answers 500 when its OpenFGA developer tuple is already gone, so the key can never be deleted

Why: a revoke that cannot finish leaves a credential the user asked to remove, and the 500 hides that the tuple is simply absent; 36 such answers were logged in 3 weeks.

Found 2026-11-16 reading production while working w21/012 (read-only).

- **Evidence:** bex-api logged `bex-api: internal error: unbind API key from workspace: revoke key membership: POST http://openfga.auth.svc:8080/stores/<id>/write returned 400 Bad Request` 36 times between 2026-10-27 and 2026-11-16 (Loki; 9 of them on 2026-11-16), and `bex_api_http_requests_total` shows `DELETE /v1/api-keys/{id}` answering 500 ten times in the last three days.
- **Cause (read from the code, not reproduced):** `tenantService.UnbindKey` (`lego/backend/internal/api/tenancy.go:540`) revokes the developer tuple first and returns its error, withholding the Hydra delete. `openfgaChecker.writeTuple` (`lego/backend/internal/authz/authz.go:172`) sends `deletes` with no `on_missing: "ignore"`, and OpenFGA answers 400 for a delete of a tuple that does not exist. The comment on `UnbindKey` says "Revoke is idempotent", which it is not: a retry after a partial revoke, or a key whose tuple was never written, fails the same way every time.
- **Fix:** delete with `on_missing: "ignore"` (check the pinned OpenFGA version supports it) or treat that 400 as success, for every revoke that is meant to be idempotent (`RevokeWorkspaceMember`, the agent-session and other deletes in `authz.go`), keeping the "tuple first, then the local row" order; a test that revokes twice and a test of a missing tuple against the real OpenFGA the backend suite already starts.
- **Acceptance:** `DELETE /v1/api-keys/{id}` of a key whose tuple is already gone answers 204 and the key stops working; the second revoke of the same key answers as the first.
