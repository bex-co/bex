# The Add Custom Domain dialog refuses a domain under a punycode TLD (`example.xn--p1ai`) and a name with a trailing dot (`example.com.`) with "Enter a valid domain", although bex-api accepts both (201) and the regex's own comment says the backend stays authoritative — and the same regex still lets a wildcard through

Why: a person who owns a domain under an internationalized TLD, or who pastes a name from a DNS console that writes fully-qualified names with a trailing dot, is told their domain is not valid by a form whose job is to save a round trip, while the API accepts it.

**Severity:** minor (the trailing dot can be typed away, but a domain under an internationalized TLD such as .рф, .中国 or .公司 can be added only through REST, GraphQL, MCP or a Blueprint, never from the dashboard). **Estimate:** 20m (one regex, a trailing-dot trim, a test that pins it to the server rule). **Kind:** sibling of [w21/038](done/038.md), [w21/043](043.md), [w21/045](045.md) and [w21/047](047.md) (a client rule that drifted from the server rule), but in the opposite direction for the TLD: here the client is **stricter** than the server and refuses valid input. **Source:** live `/qa-find-bugs` pass 55, 2026-11-11 01:5x UTC (2026-11-10 local), production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction; method: a client-versus-server validation differential on the Add Custom Domain dialog. **Status:** inbox.

## Reproduction (own Free Docker web service `qa-20261110-dom`, `srv-dbpslb7bq3ic73c0a9dg`, deleted in the same visit)

The service came from the public repo `https://github.com/bex-co/bex`, root `examples/hello-node`, auto-deploy off. It was suspended right after creation.

1. **Server verdicts** over REST `POST /v1/services/srv-dbpslb7bq3ic73c0a9dg/custom-domains` with `{ "name": … }`, from the signed-in page. Every created claim was deleted in the same call and the final list was empty.
   - **201** for `qa-20261110.example.xn--p1ai`.
   - **201** for `qa-20261110.example.com.`, stored as `qa-20261110.example.com` (the trailing dot is normalized).
   - **201** for `QA-20261110.EXAMPLE.COM`, stored lower-case.
   - 400 for `*.qa-20261110.example.com` ("wildcard hostnames are not allowed"), `co.uk` ("it is a public suffix; use a domain registered under it"), a 64-character label ("each label must be at most 63 characters") and `qa-20261110.example.123` ("the top-level domain cannot be numeric").
2. **The dialog** on `/services/srv-dbpslb7bq3ic73c0a9dg/settings` → Add Custom Domain → type the name → Add Domain:
   - `qa-20261110.example.xn--p1ai`: the input gets `aria-invalid=true` and the text "Enter a valid domain, e.g. www.example.com." No request is sent.
   - `qa-20261110.example.com.`: the same refusal, no request sent.
   - `*.qa-20261110.example.com`, `co.uk` and the 64-character label pass the client and come back as the server's readable sentence in the dialog. Those three are fine; only the stale wildcard allowance is noted.

## Root cause (code-traced; `origin/main` has no code change since the last pin)

- `dashboard/src/features/services/components/custom-domains-section.tsx:67-70`: `VALID_FQDN = /^(\*\.)?([a-z0-9]([a-z0-9-]*[a-z0-9])?\.)+[a-z]{2,}$/i`.
  - It requires an all-letter TLD, so `xn--p1ai` fails (digits and hyphens).
  - It allows no trailing dot.
  - It allows an optional `*.` that the server refuses.
- The check runs in `submit` (`:603-609`: `const trimmed = name.trim(); if (!VALID_FQDN.test(trimmed))`); its only message is `services.domainInvalid` (`features/services/locales/en.ts:1699`).
- The server rule is `lego/backend/internal/apps/domains.go`:
  - `normalizeHostname` (`:280`) lower-cases and strips one trailing dot;
  - `canonicalHostname` (`:297`): DNS-1123 subdomain, no wildcard, a fully qualified name that is not an IP;
  - `claimableHostname` (`:322`): each label at most 63 characters, a top-level label that is not all digits (`strings.Trim(tld, "0123456789") == ""`), and a registrable domain. So `xn--p1ai` passes.
- The comment above the regex says "optional wildcard label … the backend stays authoritative". That is now false for the wildcard ([ADR005](../../docs/ADR005-custom-domain.md) and [ADR018](../../docs/ADR018-render-parity.md) record wildcard rejection as a deliberate security superset) and was never true for the TLD.
- Earlier notes recorded the server accepting these inputs and did not look at the dialog: [w4/190](../w4/done/190.md) ("`xn--…` punycode accepted (fine)") and [w4/353](../w4/done/353.md) ("Case, a single trailing dot and surrounding spaces are normalized").

## Fix (target behavior)

The dialog's pre-check agrees with `claimableHostname` for what it can cheaply mirror:

- it trims one trailing dot before testing, and sends the trimmed name, as the server stores it;
- it accepts an alphabetic TLD or an `xn--` punycode TLD (`xn--[a-z0-9-]*[a-z0-9]`);
- it drops the optional wildcard prefix, so a wildcard is marked inline with its own reason instead of costing a round trip;
- raw Unicode stays refused (the server refuses it too, w4/353);
- the length, public-suffix and registrable-domain rules stay server-side;
- a test pins the regex against a small table taken from the server cases above, so the two cannot drift again.

No API change.
