## Objective

Run the S3 surface as a Deployment of its own, so a long stream does not share pods with REST, GraphQL and MCP and a rollout waits for it.

## Context

- ADR112 D3 (Where it runs). bex-api's limits are 200m CPU and 512Mi and its drain window 15 s (`lego/operator/config/api/deployment.yaml`, `lego/backend/cmd/api/main.go`); a comment in the Deployment records both replicas OOM-killed together once.
- Precedent: objectgw's Deployment (`lego/operator/config/objectgw`, hardened like the static-server, `envFrom` the optional `bex-object-storage-read` Secret).
- `bex-s3` is the bex-api image started with the S3 surface only: the core service, Postgres, OpenFGA, OpenBao and the read-write Wasabi pair from `bex-system/bex-object-storage`. It mounts no REST, GraphQL, MCP or OAuth route.
- `terminationGracePeriodSeconds` above the 30-minute stream deadline (2,100 s); on SIGTERM it stops accepting new requests and lets streams finish.

## Steps

1. Add the start mode and the S3 mux (a test pins that it mounts nothing else, and that a bucket named `graphql`, `mcp` or `v1` is only ever a bucket).
2. Add the manifests: Deployment (two replicas, grace period, resources to be refined by the production walk), Service, the Secret mounts, kustomization and prod overlay.
3. Write the drain test: a stream that is running when SIGTERM arrives completes; a new request after it is refused.
4. Add `bex-s3` to `lego/backend/AGENTS.md`'s inventory.

## Result

Done 2026-11-19. `cmd/s3gw` (bex-s3) is the bex-api image's `/s3gw` entrypoint: it reads its own small environment (the control plane's database, OpenFGA, OpenBao, Kratos' admin URL and the read-write Wasabi pair; half a pair or a database with no OpenFGA is a startup error, a missing database, OpenBao or pair keeps it up, Ready and answering 503), serves S3 on :8080 and /healthz, /readyz and /metrics on :9090, and on SIGTERM flips readiness, keeps taking requests through a 10 s window and lets streams finish up to the 30-minute deadline plus a margin. `lego/operator/config/s3gw` is a Deployment of its own (two replicas, `terminationGracePeriodSeconds` 2,100, its own ServiceAccount with no RBAC, resources 100m/192Mi to 1 CPU/768Mi as a first guess for the production walk to refine), a Service and a PodDisruptionBudget, in the default kustomization; the Dockerfile builds `/s3gw`; a network-policy entry admits `bex-s3` to OpenFGA and Kratos' admin port only. Tests pin that the package imports no REST, GraphQL, MCP or OAuth package, that every path (a bucket named graphql, mcp or v1 included) is S3, the config rules, the 503 answers, and a drain test (a stream running at SIGTERM completes, a request in the window is served, one after it is refused, and the manifest's grace period covers the window, the stream deadline and the margin). `scripts/gitops-validate.sh` fails on this machine's macOS only at steps that fail identically on a clean checkout (the CAPI drift guard); nothing new fails. Open for the production walk (m500): bex-s3 reads OpenBao as role `bex-api` through its own ServiceAccount (`bex-s3gw` after kustomize's prefix), so `scripts/bao-k8s-auth.sh` (now binding both) must be run against production before the first S3 request, or key lookups answer 503.
