## Objective

Make an S3 key die with the person who made it, expose the key and bucket calls on REST and GraphQL, and add the publish route that replaces `dev-url`.

## Context

- ADR112 D3 (a key is disposed with the person's other keys; REST routes), D4 (`bex s3 public`) and D6.
- ADR024 w2/m163 revokes API keys when a member leaves; [ADR086](../../../docs/ADR086-account-deletion.md) deletes keys with an account; [ADR012](../../../docs/ADR012-auth.md) § 9a's workspace-enforced 2FA and the Google sign-in rule gate a member's API and SSH keys; `TestEveryMembershipEndingVerbDisposesKeys` (`lego/backend/internal/members/members_test.go`) enumerates the verbs.
- Creating a key is a `mint`-class verb (ADR012 § 7, the scope-class table; `core.Base.AuthorizeMintClass`): human only, `bex.write` and the mint class.
- Routes: REST `/v1/object-storage/{ownerId}/access-keys` (create, list, revoke), `/v1/object-storage/{ownerId}/buckets/{bucket}` (region, public host, objects and bytes from the last sweep) and `.../public` (`can_manage`, a thin adapter of `SetBucketPublic`); GraphQL beside them. Not in Render's OpenAPI, so each needs a `classifiedOps` entry (`scope_matrix_ops.go`, regenerated by `GENERATE_SCOPE_MATRIX=1 go test ./internal/api -run TestGenerateScopeMatrix`).
- No key ever holds `can_manage` (D3): the publish route is authorized from the person's own token.

## Steps

1. Join S3 keys to the member-removal and account-deletion disposal and extend the enumeration test; re-adding a creator must not revive a disposed key.
2. Apply the 2FA and sign-in gates to key creation and use.
3. Add the REST and GraphQL adapters, the bucket route and the publish route with their scope-matrix entries and audit verbs (`CreateAccessKey`, `ListAccessKeys`, `RevokeAccessKey`).
4. Test the mint class: an API key and a third-party token cannot create a key.

## Acceptance criteria

- [x] Removing a member or deleting an account leaves none of their S3 keys or secrets.
- [x] The scope matrix, authorization matrix and audit-verb sweeps pass with the new routes.
- [x] A leaked `readwrite` key cannot publish a bucket.

## Out of scope

- Dashboard UI for keys (ADR112 D10).

## Result

Done 2026-11-19. A member's removal, a member leaving and an account's deletion dispose of the S3 keys they made with their API keys (`credentialDisposal`, one teardown for both, so the members audit count includes S3 keys, and a re-added creator revives nothing because rows are deleted); a workspace delete purges its keys and secrets (`AccessKeys.PurgeWorkspace` in the post-cascade purgers). `Identity.AuditSubject` makes an S3 request authorize as the key's creator while its audit rows name the key (`MethodS3Key` reads as the `rest_api` actor), and the workspace login-requirement gate treats `MethodS3Key` like an SSH key (the creator's second factor, the key's stored sign-in stamp for Google login); the enable confirmation's list of blocked principals does not list S3 keys (they are checked at use). REST `/v1/object-storage/{ownerId}/access-keys` (create and revoke are mint-class, human only), `.../buckets/{bucket}` and `.../buckets/{bucket}/public` (publishing needs can_manage, which no key holds) with GraphQL beside them, scope-matrix, scoped-key permission, by-id, empty-list and schema-golden entries, and tests for the mint class, the secret shown once, the can_manage refusal and the disposal.
