## Objective

Let bex's read-write Wasabi identity abort a multipart upload, list its parts and list a bucket's uploads, which the S3 surface and the sweep's 7-day abort need and the installed policy lacks.

## Context

- ADR112 D9. `infra/wasabi/object-storage-s3-policy.json` grants only `s3:GetBucketLocation`, `s3:ListBucket`, `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` on `bex-objects-oregon` and `bex-objects-frankfurt`.
- Needed: `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts` and `s3:ListBucketMultipartUploads`.
- `scripts/object-storage-s3-credentials.sh {provision,verify,install}` is idempotent and never prints a secret; its root credential is `TF_STATE_ACCESS_KEY`/`TF_STATE_SECRET_KEY` from `.env` (as w21/095 used it). `verify` includes a denied probe on `bex-tfstate`.
- Never park on "no access": run the real scripts first.

## Steps

1. Add the three actions to the policy file, scoped to the two buckets as the existing statements are.
2. Extend `verify` with a real create, upload-part, list-parts, list-uploads and abort on a throwaway key, and keep the denied probe on `bex-tfstate`.
3. Run `provision` and `verify` against production with the root credential from `.env`, without printing it; record the result in the task.
4. Update ADR112 D9 and `docs/ADR019-infra-credentials.md` if its rows name the actions.

- [x] `verify` passes on production, including a multipart abort, and the denied probe on `bex-tfstate` still fails.

## Out of scope

## Result

Done 2026-11-19. `infra/wasabi/object-storage-s3-policy.json` now grants `s3:AbortMultipartUpload` and `s3:ListMultipartUploadParts` on the objects and `s3:ListBucketMultipartUploads` on the buckets; `scripts/object-storage-s3-credentials.sh verify` runs a real create, upload-part, list-parts, list-uploads and abort in both regions (aborting even when a step fails, so no part is left billed) and a denied multipart start for the read-only user. `provision` and `verify` ran against production with the root credential from `.env` and passed in both regions, with the denied probes on `bex-tfstate` and the three other platform buckets still failing; no credential value is printed or recorded. Finding: Wasabi applies a replaced IAM user policy minutes later (Oregon about 6 minutes, Frankfurt by about 18, a fresh user at once), so a `verify` that fails right after `provision` means wait (ADR112 § Not verified). Docker Desktop on this machine had no outbound TCP from containers, so the script's pinned aws-cli image could not reach Wasabi; the run used a local `docker` shim that passes the same arguments to a host awscli (a scratch file, not committed).
