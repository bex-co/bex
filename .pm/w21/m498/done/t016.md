## Objective

Check the S3 surface and its REST and GraphQL adapters against the product it is compared with, and flag drift as follow-up work. Render has no S3 API and no S3 access keys; Contract A (Render's routes) must be untouched.

## Context

- Surface: S3 on `objects.onbex.co`; REST `/v1/object-storage/{ownerId}/access-keys`, `/buckets/{bucket}` and `/buckets/{bucket}/public` with GraphQL beside them. MCP and the dashboard have no object surface (ADR112 D10).
- Render parity still applies to the shared store: `render ea objects` and S3 clients must read and write the same `render-<region>` data, and Render's four routes must answer as before.

## Steps

1. Compare the new REST and GraphQL fields and errors with the existing object routes and with the keys and publish conventions of the other services.
2. Show that an object put with `render ea objects` is listed and read through S3, and the other way round.
3. Record each difference from S3 and from Render in ADR018's `Extension` row (done in m499) or as a follow-up note.

## Files

- docs/ADR018-render-parity.md

## Acceptance criteria

- [x] Every difference from S3 is written down with its reason.
- [x] Interoperation of the Render CLI and an S3 client on `render-<region>` is shown, not assumed.

## Out of scope

- Fixing drift found here beyond one-line corrections; file it instead.

## Result

Done 2026-11-19. **Interoperation shown, not assumed:** `s3gw/render_interop_test.go` drives Contract A's service calls (`MintPut`, `MintGet`, `ListObjects`, `DeleteObject`, which its four routes adapt) with the presigned URLs the CLI is handed, and the AWS SDK on `render-oregon`: an object put the Render way is listed, sized and read through S3; an object put through S3 is listed by Render's route and read through its minted GET; a delete on either side is a delete on the other; the system bucket cannot be deleted through S3. Contract A's routes and tests are untouched. **Adapters compared** (access keys at `/v1/object-storage/{ownerId}/access-keys`, buckets and publish beside them): they follow the existing object routes' conventions (`ownerId` as the workspace, camelCase fields, typed ids `s3k-`, bex's `{id, message}` error shape through the same helpers, the secret returned once and never again, mint-class create and revoke, GraphQL beside REST), and Render has no counterpart for access keys, buckets, CORS, lifecycle or a public flag, so each is an `Extension` row, not a parity break. **Every difference from S3, with its reason, for ADR018's Extension row (m499 t005):** buckets live in two regions only (oregon and frankfurt; any other LocationConstraint is InvalidLocationConstraint) because those are the Wasabi buckets bex holds; a name is unique in a workspace, never global (BucketAlreadyOwnedByYou, never BucketAlreadyExists) and 3 to 63 lower-case letters, digits and hyphens, with `render-*` reserved for Render's namespace and `cloudflare` until Contract B goes; a bucket with an unfinished upload cannot be deleted; policies, ACLs, versioning, object lock, SSE, tags (an empty set on read), website redirects, storage classes other than STANDARD, conditional writes and signed-chunk payloads answer 501 rather than being ignored; copies stay inside one workspace and region; the delimiter is one ASCII character and ListMultipartUploads takes none; the listing continuation resumes after a prefix followed by U+10FFFF; `x-amz-copy-source-if-*` are honored (412) because the AWS CLI sends them; an upload is at most 5 GiB, 10,000 parts and 100 open per workspace, with the 5 MiB part minimum Wasabi enforces and a 7-day abort; a part writes no allowed audit row; reads are paced, capped per month by the egress budget and listings by 5 a second; ListBuckets shows the system buckets and an object's Content-Disposition defaults to attachment (ADR095 D7). No one-line correction was needed; nothing was filed as drift.
