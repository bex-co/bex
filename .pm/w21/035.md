# Registry credential names: a 253-byte cap sits behind the shared 100-code-point label rule, so a 93-character Chinese name is refused with "name must be at most 253 bytes" while a 100-character English name saves

Why: the shared label rule (`core.CheckLabel`) says a name may be up to 100 Unicode code points, and for Chinese names the registry credential writer silently lowers that to 84 characters by also counting bytes (the same unit mismatch as [w21/034](034.md) for SSH keys).

**Severity:** minor (a CJK-only refusal in a unit the user cannot count; no data lost). **Estimate:** 20m (drop the byte cap for the name, keep it for host and username, add a CJK case to the tests). **Kind:** gap in [w4/491](../w4/done/491.md)'s guarantee (see Dedupe). **Source:** live `/qa-find-bugs` pass 32, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. It is the sibling of w21/034, whose Adjacent-classes section named this case as "code-read only, cause unverified"; it is now probed live. **Status:** inbox.

## Reproduction (every credential created was deleted in the same call)

In-page GraphQL to `https://api.bex.co/graphql` with the session cookies: `createRegistryCredential(name: $n, host: "registry.qa-20261110.invalid", username: "qa", authToken: "qa-20261110-not-a-real-token")`, then `deleteRegistryCredential(id)` for each success. `{ registryCredentials { name } }` was `[]` before and after.

| name | code points | bytes | result |
| --- | --- | --- | --- |
| `qa-20261110-` + 80 × `受` | 92 | 252 | created, then deleted |
| `qa-20261110-` + 81 × `受` | 93 | 255 | refused: `bad request: name must be at most 253 bytes` |
| `qa-20261110-` + 88 × `受` | 100 | 276 | refused: the same message |
| `qa-20261110-` + 88 × `a` (control) | 100 | 100 | created, then deleted |
| `qa-20261110-` + 89 × `a` (control) | 101 | 101 | refused: `display name must be at most 100 Unicode code points` |

So the rule the product states (100 code points) holds for ASCII and fails for CJK from the 93rd code point in this probe. For a bare name the effective limit is 84 Chinese characters (253 / 3).

## Root cause (code-traced)

- `lego/backend/internal/registrycreds/service.go:247` and `:326` run `core.CheckLabel(name)` (100 code points, no control characters). The same paths then apply the byte cap: Create through `validateCredentialFields` (`:416-417` `case len(name) > maxCredentialFieldBytes` → `name must be at most %d bytes`) and Update at `:329-331`.
- `maxCredentialFieldBytes = 253` is `service.go:73`. It also bounds the host (`:418`; a DNS-hostname limit in bytes, correct) and the username (`:339`, `:420`; fine). The secret has its own constant (`maxCredentialSecretBytes`, `:422`).
- The DB column is `name text NOT NULL` (`store/migrations/0018_registry_credentials.up.sql:19`), so no storage limit forces a byte cap on the name.
- Dashboard: both dialogs expose the optional name field with no `maxLength` (`dashboard/src/features/registry-credentials/components/create-registry-credential-dialog.tsx:132-140` and `edit-registry-credential-dialog.tsx:172-178`; `grep -c maxLength` in both is 0). A user types a long Chinese name, the form accepts it, and the server answers with the byte message in English.

## Fix (target behavior)

- The name is held to `core.CheckLabel` alone (100 code points). The byte checks stay for host and username (and the secret's own cap); the label-rule refusal is the only name refusal.
- Both dialogs add `maxLength={100}`, like the API key dialog (`create-api-key-dialog.tsx:112`).
- Create, Update and the three entrypoints (REST, GraphQL, MCP) share `Service.Create` / `Update`, so the service change covers all of them.

## Blast radius (counted by grep)

- `maxCredentialFieldBytes` has 1 definition and 5 byte checks in `registrycreds/service.go`: name (`:329`, `:416`), username (`:339`, `:420`) and host (`:418`). Only the two name checks change; the host and username checks must keep their tests.
- Tests to add: an acceptance case with 100 CJK characters (300 bytes) on both Create and Update; the existing 101-code-point rejection stays.

## Adjacent classes

- w21/034 (SSH key names: no label rule, 120-byte cap): its fix and this one should land on the same shared rule.
- No other free-form label writer applies a byte cap on top of the label rule in the grep of `len(name) >`: `apps/disks.go:346` is a 63-byte DNS-style identifier, and `router/service.go:172,193` 200-byte names belong to the companion-bridge feature and were not probed.

## Dedupe / precedent

`grep` of `.pm` for the 253-byte cap and the credential name rule finds w4/491, w4/128, w4/403 and w4/m168/t005. [w4/491](../w4/done/491.md) (done) made the label rule apply to credential names. Its root-cause section describes the 253-byte cap, and its blast-radius list asks a CJK name and a 100-code-point name to keep creating, but the fix left the byte cap in place, so a 100-code-point CJK name still does not create. This is therefore a gap in 491's guarantee, not a regression: such names never created. w4/128 only records that a 5000-byte name is refused with the byte message. Not in `DO_NOT_DO.md`. `registrycreds/service.go` and the dialogs are unchanged on `origin/main`. Render: n/a.

## Definition of done (each bullet is repeatable with the probe above)

- On production `createRegistryCredential` with `qa-20261110-` + 88 × `受` (100 code points) succeeds, and 101 code points is refused with the label rule's message, never the bytes message (delete the credential afterwards).
- A 300-byte, 100-character Chinese name saves through Update too.
- A host longer than 253 bytes and a username longer than 253 bytes are still refused.
- The Create and Edit dialogs stop typing in the name field at 100 characters.

**Cleanup:** every probe credential was deleted (the list was empty before and after); only the fake host `registry.qa-20261110.invalid` and a placeholder token were used; no resource is left.
