# 094 — An object or bucket audit row names no bucket and no key, and a successful get leaves no row

Why: w21/087 gave the object routes a verb, but a row reads `objectstorage.PutObject` on `workspace:tea-…` with an empty target, so a reader cannot tell which bucket or key was written or deleted; a successful `GetObject` writes nothing, so a download of customer bytes is invisible unless it was refused.

- **Source:** w21/087, 2026-11-16, from reading `AuthorizeWorkspaceAs` rows on production and in `TestObjectRoutesRecordAPutAndABucketCreate`.
- **Facts:** the routes authorize on the workspace before the bucket is resolved (`objects_render.go` `serve`, `cloudflare_r2.go` `route`), so the target is empty; `can_view_sensitive` is a read relation, and `core.readRelations` records only a refusal (ADR006 § Audit log), the volume rule that Render's `ViewEnvVarValuesEvent` and `ViewConnectionInfoEvent` are the exception to. Render's audit-log enum has no object event, so there is no Render behavior to match; this is a bex product decision.

## Steps

1. Decide whether a bucket name (and for put and delete, the key) belongs in the row's target, with the key bounded and never a presigned URL or a header. If yes, pass it through `AuthorizeTargetAs`-style entry and show it in REST's `metadata`.
2. Decide whether a successful get records once per request, like `ViewEnvVarValuesEvent`, and what bounds the volume for a streamed object.
3. Record both decisions in ADR112 D6 and cover them in `audit_verbs_test.go`.

## Done when

- [ ] The audit log answers which bucket a put, delete or bucket change touched, and the decision on recording a successful get is written in ADR112.
