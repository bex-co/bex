Why: [w21/024](done/024.md) fixed the same hand-built dollar string on Billing (`$1000551.64`) and named only plan prices as look-alikes; this one is a separate site with its own file:line, on a feature added two days ago (w21/m278).

**Severity:** minor (formatting; the stored value is right). **Estimate:** 10m (one call to the existing helper, one test). **Kind:** hand-built money string, the class of w21/024. **Source:** live `/qa-find-bugs` pass 36, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Root cause (code-traced)

- `dashboard/src/features/agent-automations/components/automation-settings-card.tsx:82-85`: `spendLimit: tpl.maxSpendUSD != null ? \`$${tpl.maxSpendUSD}\` : t("agentAutomations.noSpendLimit")`. It stringifies the JSON number with no grouping, no minimum fraction digits and no locale.
- The same product already has the helper: `dashboard/src/features/agent-sessions/lib/spend-limit.ts:30-39` `formatPreciseUsd(amount: string, locale)` (`Intl.NumberFormat` currency USD, 2 to 6 fraction digits). It is used for the session's own limit (`failure-callout.tsx:68`, `session-spend-note.tsx`, `session-model-cost.tsx`); Billing has `money()` (`usage/lib/charges.ts:42`).
- The limit's range goes up to `SPEND_LIMIT_MAX_USD = 100000` (`spend-limit.ts:9`), so values of four to six digits are legitimate input.

## Fix (target behavior)

The card renders the limit with `formatPreciseUsd(String(tpl.maxSpendUSD), i18n.language)`, so 0.5 reads "$0.50" and 12345.5 reads "$12,345.50" in en (and the zh locale's own grouping), matching how the sessions this automation starts show the same ceiling.
