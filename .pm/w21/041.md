# A failed build on a sleeping service still says "Saved changes go live when the current deploy finishes": the operator's `undeployedChangesApplying` stays true because the parked-service failure record is not one of the shapes `requestedReleaseFailed` recognizes

Why: [w4/529](../w4/done/529.md) made "go live when the current deploy finishes" depend on the pending release not having failed and listed four failure shapes; a build that fails while the prior release is parked is a fifth shape, so the notice contradicts the failed deploy shown beside it and the CRD's own contract that "a failed release never sets" the flag.

**Severity:** minor (a wrong notice; following it costs one wait for a deploy that is never coming). **Estimate:** 30m (recognize the parked failure in `requestedReleaseFailed`, plus operator tests for parked and suspended variants). **Kind:** gap in the guarantee of w4/529 and [w4/m184](../w4/done/m184/README.md). **Source:** live `/qa-find-bugs` pass 39, 2026-11-10, production `https://dashboard.bex.co`, workspace `bex`, filed to w21 per user direction. **Status:** inbox.

## Root cause (code-traced; the live App CR was not readable from the QA account)

- The flag is the operator's `AppStatus.UndeployedChangesApplying` (`lego/types/v1alpha1/app_types.go:1944-1949`: "A Restart, rollback, cancel or failed release never sets it"). It is set by `reconcileSavedConfigurationStatus` through `inFlightCarriesSavedConfiguration` (`lego/operator/internal/controller/saved_configuration.go:143-160`), which returns false only when `releaseRequestedOrRolling` is false or `requestedReleaseFailed(app, pending)` is true.
- `releaseRequestedOrRolling` (`:170-177`) is true for a stamped release whose phase is not `Failed`.
- `requestedReleaseFailed` (`:181-196`) recognizes exactly four shapes: `Status.Phase == Failed`; a false `Rollout` condition for that generation; a Ready condition with reason `reasonPriorReleaseServing`; a failed pre-deploy step.
- A failed build over an **awake** prior release is recorded by `settlePriorRelease` (`app_controller.go:6796-6815`, reached from `settleFailureOverPriorRelease`, `:6771`, "the latest build failed" at `:6712`) with phase Running and Ready reason `reasonPriorReleaseServing`, so it is recognized. Over a **parked** prior release the same function writes phase `Hibernated` and a Ready condition False with reason `reasonAutoHibernated` (or `reasonSuspended`) and the message "<failure>; the previously deployed release stays parked". None of the four shapes matches that, so the failed release still counts as "requested or rolling" and Applying stays true.
- The dashboard only renders the key: `dashboard/src/features/services/lib/status.ts:368-386` `undeployedChangesHintKey` checks applying first, then suspended, then reason.

## Fix (target behavior)

- A pending release that failed over a parked prior release counts as failed in `requestedReleaseFailed`, so Applying is false and the service shows "Saved changes aren't live yet. Use a standard deploy to apply them." A sleeping service keeps its existing "wakes on the next request" line; a suspended one keeps "Resume the service, then deploy to apply them".
- Recognize the parked record by the Ready reason (`reasonAutoHibernated` / `reasonSuspended`) together with the `ObservedGeneration` or a dedicated failure marker, not by parsing the message.
- No API, REST, GraphQL or MCP change, and the dashboard needs none: it already maps false correctly, as the awake control shows.

## Blast radius (counted by grep)

- `requestedReleaseFailed` has 1 caller (`inFlightCarriesSavedConfiguration`, `saved_configuration.go:146`).
- `settlePriorRelease` is the writer of the parked failure record for every failure over a prior release; its callers are `app_controller.go:3909,3917,4516,6712,6735,7026,7227,7243`. The failed-build case is `:6712`; "the latest image could not be read" (`:6735`) and "the latest build has no image yet" (`:7227`) go through the same function and have the same hole for a parked service (not probed live).
- The flag is read by REST (`lego/backend/internal/apps/render.go:178-180,423`), GraphQL (`graphql.go:360`) and the dashboard header (`service-detail-header.tsx:311`).
- Tests to extend: the cases of `TestInFlightReleaseCarriesSavedConfiguration` (`release_config_selection_test.go:477`) that w4/529 added for four failure shapes, with parked and suspended variants, keeping the awake-failed and in-flight-building controls.

## Adjacent classes

- A build that fails while the service is awake is already correct (control above).
- A rollback or restart never sets the flag (unchanged); a canceled release is excluded earlier.
- A pre-deploy failure over a parked service goes through `PreDeploy` and is already recognized (not probed live: pre-deploy needs a paid plan).

## Definition of done (each bullet is repeatable with the probe above)

- On production, a Free web service that is Hibernated and then fails a build (for example a Dockerfile Path that does not exist) shows "Saved changes aren't live yet. Use a standard deploy to apply them." while still sleeping, and GraphQL reports `undeployedChangesApplying: false` for it.
- The same service awake shows the same text (control).
- An in-flight build on a sleeping service still shows "go live when the current deploy finishes" until it fails.
- The new operator test cases fail if the parked recognition is removed.
