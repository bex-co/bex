# 043 — Manual Scaling slider and numeric input have no accessible names

Why: keyboard and screen-reader users reach unnamed controls for the desired instance count, and fixing only the slider container would leave the actual focusable thumb unnamed.

**Severity:** minor. **Estimate:** 40m including the shared-consumer check below. Filed through `pm add w4` from the 2026-09-05 live `qa-find-bugs` passes. Governing contracts: [ADR007](../../docs/ADR007-restart-suspend-and-resume.md) and [ADR006](../../docs/ADR006-bex-api.md); [Render scaling capture](../../docs/render-artifacts/manual-scaling.md).

## Reproduction and durable evidence

1. Create a free QA web service and wait until it is Running.
2. Visit `https://dashboard.bex.co/services/srv-dae91rh88i5c7399e85g/scaling`, with autoscaling off.
3. Read `await page.locator('main').ariaSnapshot()`, then reload and repeat the two focused probes below.

## Root cause

- `dashboard/src/features/services/components/manual-scaling-section.tsx:76-86`: Instances is a `<p>` without a label relationship; `SliderInput` receives only `id="manual-instances"`.
- `dashboard/src/features/services/components/autoscaling-section.tsx:53-95`: `SliderInput` passes the id to the number input but no accessible name to either input or slider.
- `dashboard/src/common/components/ui/slider.tsx:22-25`: the wrapper constructs the focusable `SliderPrimitive.Thumb` without labeling props. Extra root props alone cannot label this separate thumb.
- Read the pinned dependency, `@radix-ui/react-slider` 1.4.3 (`dashboard/yarn.lock:3581`; installed `dist/index.mjs:476-500,586-594`): the **thumb** owns `role="slider"`; its fallback `getLabel` returns `undefined` for one thumb. Two thumbs instead receive Minimum/Maximum, so they must not be described as unnamed without an independent probe.

## Work items and target behavior

1. **Label the manual pair (25m).** Both focusable controls must be announced as **Instances**, translated through the existing `services.scalingManualInstances` key, with the current value announced separately. Give `SliderInput` an explicit label contract and forward it to the number input and actual thumb. Add a narrow optional thumb-label mechanism to the wrapper if needed; do not hardcode Instances globally. Preserve numeric/slider synchronization, the free cap, dirty-state handling and `scaleService` arguments. Before data settles, keep the existing skeleton/disabled behavior; mounted controls remain named while saving.
2. **Shared-consumer check (15m).** `rg -n 'SliderInput' dashboard/src --glob '*.tsx'` finds **three production single-value mounts**: manual instances (`manual-scaling-section.tsx:79`), target CPU (`autoscaling-section.tsx:349`) and target memory (`:382`). Migrate the latter two to their own translated CPU/memory names, not Instances. The common `<Slider>` has **two production call sites**, both in `autoscaling-section.tsx`: the single-value helper (`:73`) and `RangeSliderInput` (`:138`, mounted at `:306`). Preserve the two-thumb minimum/maximum distinction and its keyboard/value behavior. Add focused accessible-name assertions on the actual sliders and number inputs, including those sibling controls. Existing tests that only find text or anonymous roles are insufficient.

**Blast radius / aliases:** the proposed helper change is shared across the three single-value mounts; it must not assign one generic label to unrelated quantities. Static and cron are excluded by `services.$serviceId.scaling.tsx:42-44`; managed Postgres and Key Value use separate surfaces. No API, operator, billing, plan, permission, or scaling-limit change is requested.

**Adjacent classes:** retain forbidden/unauthenticated/error handling and the busy state. This is naming, not a fix for service existence, failed scale requests, or unavailable metrics.
