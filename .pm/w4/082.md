# 082 — Half the scope-matrix's Sensitive/Mint overrides have no fail-closed heuristic: 29 of 59 downgrade silently with the whole guard suite green

Why: `w4/m106` just shipped a fix for one scope-classification hole, and the regression net that is supposed to stop the next one covers only the REST spellings — including `GQL Query.envVars` and `MCP get_env_var`, which downgrade from Sensitive to Read with every test passing.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 30. **Read-only on production — nothing created, changed or deleted.** The finding is in shipped code and was verified by a reverted local mutation experiment (`git status` clean afterwards, confirmed). Severity: **major** — not a live disclosure today (all 59 entries are currently correct), but a 49%-coverage fail-closed control guarding exactly the class of bug `m106` was.

## The mechanism

`defaultScopeClass` classifies by verb shape: `GET`/`Query.`/`list_`/`get_` → read, everything else → write. **Every** Sensitive and Mint classification is therefore a hand-maintained entry in `scopeClassOverrides` (`scope_matrix_overrides.go`, 59 entries).

Two of the three guard tests cannot catch a missing override:

- `TestScopeMatrixCoversLiveOperations` (`scope_matrix_guard_test.go:114`) asserts `classifiedOps[op] == classifiedClass(op)` — i.e. the generated table agrees with default+override. Delete an override and this fails, but its own failure message says: _"regenerate with GENERATE_SCOPE_MATRIX=1 go test ./internal/api -run TestGenerateScopeMatrix"_. Regenerating bakes the downgrade in and the test goes green. **The drift test actively directs the developer down the silent-downgrade path.**
- `TestScopeClassOverridesAreLive` (`:145`) only checks overrides aren't stale. An absent override is invisible to it.

So the only real net is `TestMintAndSensitiveHeuristics` (`:158-201`), which matches **string literals** against op keys. Its cases are spelled for some surfaces and not others: `strings.Contains(op, "deploy-hook")` matches the REST path but not `GQL Query.deployHook` or `MCP get_deploy_hook`; `strings.Contains(op, "/env-vars") && strings.HasPrefix(op, "REST GET ")` is REST-only by construction. Where the author listed all three spellings explicitly (api-key, ssh-key, processes/top-queries, env-group var/file, env-group link) the coverage is complete — which is what makes the gaps look like oversight rather than design.

## The experiment

For each of the 59 overrides: delete the line, regenerate the matrix, run all three guard tests, restore with `git checkout`. Re-runnable verbatim from `lego/backend/`:

```bash
keys=$(grep -oE '^\t"[^"]+":' internal/api/scope_matrix_overrides.go | sed 's/^\t"//;s/":$//')
echo "$keys" | while IFS= read -r key; do
  sed -i '' "\|\"$key\":|d" internal/api/scope_matrix_overrides.go
  GENERATE_SCOPE_MATRIX=1 go test ./internal/api -run TestGenerateScopeMatrix -count=1 >/dev/null 2>&1
  new=$(grep -F "\"$key\"" internal/api/scope_matrix_ops.go | sed 's/.*core.OpClass//;s/,.*//')
  go test ./internal/api -run 'TestScopeMatrixCoversLiveOperations|TestMintAndSensitiveHeuristics|TestScopeClassOverridesAreLive' -count=1 >/dev/null 2>&1 \
    && echo "UNPROTECTED $key -> $new" || echo "pinned       $key"
  git checkout -- internal/api/scope_matrix_ops.go internal/api/scope_matrix_overrides.go
done
```

Result: **30 pinned, 29 unprotected.** The 29, by family:

| family | unprotected entries | downgrades to |
| --- | --- | --- |
| **env/secret-file value reads** | `GQL Query.envVars`, `GQL Query.secretFiles`, `MCP list_env_vars`, `MCP get_env_var`, `MCP list_secret_files`, `MCP get_secret_file` | Sensitive → **Read** |
| **deploy-hook URL** | `GQL Query.deployHook`, `MCP get_deploy_hook` | Mint → **Read** |
| | `GQL Mutation.regenerateDeployHook`, `MCP regenerate_deploy_hook` | Mint → Write |
| **database-user mint** | `REST POST /v1/postgres/{id}/users`, `GQL Mutation.createDatabaseUser`, `MCP create_postgres_user` | Mint → Write |
| **blueprints (can embed env values)** | `REST POST /v1/blueprints/{preview,generate}`, `GQL Query.blueprintPreview`, `GQL Query.generateBlueprint`, `MCP preview_blueprint`, `MCP generate_blueprint` | Sensitive → Read/Write |
| **SQL execution + dumps** | `REST POST /v1/postgres/{id}/query`, `MCP query_render_postgres`, `REST GET /v1/postgres/{id}/export`, `GQL Query.databaseExports`, `MCP list_postgres_exports` | Sensitive → Read/Write |
| **shell tickets** | `REST POST /v1/services/{id}/shell-ticket`, `GQL Mutation.createShellSession` | Sensitive → Write |
| **invite preview** (downgrade is the safe direction here) | `REST POST /v1/invites/preview`, `MCP preview_workspace_invite` | Read → Write |

Note the database-user family: **all three surfaces** of a durable-credential mint have zero net.

### Control case, verified for the reason claimed

`MCP create_api_key` was run through the identical procedure: Mint → Write, and the suite **FAILS** — because `TestMintAndSensitiveHeuristics` names `create_api_key` literally. The pinned/unprotected split is caused by the heuristic's spelling coverage, not by some other difference between the entries.

### Why Mint → Read is the sharpest consequence

`OpClassMint` is enforced at the verb and a delegated OAuth caller can **never** satisfy it (`core/base.go:320`, `core/scope.go:205`, `core/base.go:897`). A Mint → Read downgrade therefore converts "no OAuth client can ever call this" into "any `bex.read` token can" — for `Query.deployHook` / `get_deploy_hook`, that is the unguessable deploy-trigger URL. Sensitive → Read is the same escalation shape `w4/m106` fixed, now applied to `Query.envVars`.

## The forward-looking half

The gap also bites on **addition**, not just deletion. A newly registered op that is absent from the table fails the drift test with "missing", the message tells the developer to regenerate, and the generator assigns it a default class. It ships pinned only if its name happens to contain a heuristic literal.

Concrete live instance: REST and GraphQL both expose datastore connection info (`REST GET /v1/postgres/{id}/connection-info`, `GQL Query.databaseConnectionInfo`, `GQL Query.keyValueConnectionInfo`), and **MCP has no equivalent tool at all** — verified by enumerating every `MCP *postgres*`/`*key_value*` entry in the table. Whoever closes that parity gap will most naturally name it `get_postgres_connection_info`, which contains `connection_info` (underscore) — matching neither `"connection-info"` nor `"ConnectionInfo"` in the heuristic's case — and the `get_` prefix defaults it to **Read**. A credential reveal would ship at read scope with CI green.

## The fix

Preferred target behavior: **classify at the registration site, not in a parallel map.** The class is a property of the verb; a second hand-maintained table keyed by stringly-typed op names will keep drifting no matter how many literals the heuristic accumulates. If the adapters declared their class where they register (REST route, GraphQL field, MCP tool), `classifiedOps` becomes derived and the whole "missing override" failure mode disappears.

Cheaper interim fix, if the refactor is deferred: extend `TestMintAndSensitiveHeuristics` so every family lists **all three surface spellings** (REST path segment, GraphQL camelCase, MCP snake_case), and add the sweep above as a table test asserting `len(unprotected) == 0` — that way the net's own coverage is what regresses loudly, not the classifications.

Either way, also fix `TestScopeMatrixCoversLiveOperations`'s failure message: it should say that a **new** op needs a deliberate class decision before regenerating, not just "regenerate".

## Not filed as a milestone

The interim fix is one test function plus a table test — sub-hour, so it belongs here per the sizing rule. The registration-site refactor is a genuinely larger design change; promote this note only if that is the route chosen.
