## Objective

Redact statements carrying secrets (password DDL and equivalents) from Insights query text before it leaves `bex-api`.

## Context

- `sqlTopQueries` selects raw `left(query, 500)` with no redaction (`lego/backend/internal/postgres/insights.go:163`), and `maskedQuery` only handles PostgreSQL's `<insufficient privilege>` placeholder (same file, lines 47-54) — an embedded `WITH PASSWORD '…'` sails through verbatim.
- The same exposure exists for live backends: `sqlProcesses` publishes raw `left(query, 200)` (line 154), so a running `ALTER ROLE/CREATE USER … PASSWORD` shows too. Fix both in one helper.
- Reads already require `RelCanViewSensitive` (lines 294, 330) — keep that gate; redaction is defense in depth for a secret that must never display even to privileged readers.

## Steps

1. Add a redaction helper beside `maskedQuery` that replaces secret-bearing fragments (at minimum `PASSWORD '…'` / `PASSWORD $…$…` / `ENCRYPTED PASSWORD '…'` spellings, case-insensitive) with a stable placeholder, and apply it to both Top Queries and Processes rows.
2. Keep the `Masked` semantics: redacted-but-readable rows stay `Masked: false` with visibly redacted text (distinct from the privilege placeholder path).
3. Confirm no other Insights query-text publisher bypasses the helper (REST/GraphQL/MCP share these readers).

## Files

- `lego/backend/internal/postgres/insights.go`

## Acceptance criteria

- [ ] A database whose `pg_stat_statements` holds the provisioning `ALTER ROLE … WITH PASSWORD` shows the statement with the verifier redacted, on dashboard + REST + GraphQL + MCP.
- [ ] Ordinary statements (provisioning `CREATE DATABASE`, `CREATE EXTENSION`, SELECTs) still render verbatim.
- [ ] `<insufficient privilege>` rows still map to `Masked: true` with empty text.

## Out of scope

- Dashboard changes (none needed); SQL console behavior (the caller sees their own SQL); rotation of already-visible verifiers (fresh instances only — the QA fixture is deleted).
