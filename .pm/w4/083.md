# 083 — MCP can suspend a Key Value but cannot resume one: `suspend_keyvalue` ships without a `resume_keyvalue`

Why: an agent that suspends a Key Value over MCP has no MCP way to bring it back — it must switch to REST, GraphQL or the dashboard — while both sibling lifecycle pairs on the same surface (`suspend_postgres`/`resume_postgres`, `suspend_service`/`resume_service`) are complete.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 31. **Read-only on production — nothing created, changed, suspended or deleted.** The two pre-existing Key Value stores belong to the operator and were never touched; the defect is proven from the deployed tool list, not by suspending anything. Severity: **major** — the journey completes in one direction only, and the surface that caused the state cannot undo it.

## The live probe

Run from inside an authenticated dashboard page (`api.bex.co` sits behind Cloudflare and rejects bare scripts):

```js
const res = await fetch("https://api.bex.co/mcp", {
  method: "POST",
  credentials: "include",
  headers: { "content-type": "application/json", accept: "application/json, text/event-stream" },
  body: JSON.stringify({ jsonrpc: "2.0", id: 1, method: "tools/list", params: {} }),
});
const payload = JSON.parse((await res.text()).split("\n").find((l) => l.startsWith("data:")).slice(5));
const names = payload.result.tools.map((t) => t.name);
```

Complete response, 2026-09-14:

```json
{
  "status": 200,
  "toolCount": 186,
  "keyValueTools": ["create_key_value", "get_key_value", "get_key_value_logs", "list_key_value", "suspend_keyvalue", "update_key_value"],
  "hasSuspendKV": true,

  "pgPair": ["resume_postgres", "suspend_postgres"],
  "svcPair": ["resume_service", "suspend_service"]

```

`hasResumeKV` tests `/^resume_key/` against all 186 names, so the absence is not a naming near-miss.

## The other two surfaces both have the pair

| surface | suspend | resume |
| --- | --- | --- |
| REST | `POST /v1/key-value/{id}/suspend` | `POST /v1/key-value/{id}/resume` |
| GraphQL | `Mutation.suspendKeyValue` | `Mutation.resumeKeyValue` |
| MCP | `suspend_keyvalue` | **absent** |

(REST and GraphQL entries read from `scope_matrix_ops.go:674-675` and `:113`/`:167`; that table is guarded exhaustively against the live mux and schema by `TestScopeMatrixCoversLiveOperations`, so their presence is not in doubt.)

The service method the missing tool needs already exists and is what the other two surfaces call: `keyvalue/service.go:522` `Resume` → `setSuspended(ctx, name, false)`.

## Root cause, and why it is an oversight rather than a decision

`suspend_keyvalue` was added by `cb052ca07` ("feat: protect datastores in protected environments", `w6/m37`) — a milestone about **confirmation phrases**, not lifecycle completeness. Its whole frame was the destructive direction: `w6/m37/t006` is titled "MCP: `Confirm` field on `suspend_postgres`/`suspend_keyvalue`". Resume needs no confirmation gate, so it fell outside that frame and was never added.

The file header comment then generalized the rationale further than what shipped (`keyvalue/mcp.go:31-36`):

> Render's MCP server exposes no delete/suspend/resume KV tools. bex keeps delete absent, but exposes `suspend_keyvalue` as a deliberate lifecycle extension so agents can use the same protected-environment safety gate as REST, GraphQL, and the dashboard.

Two things follow. The stated reason — surface parity with REST/GraphQL/dashboard — applies to `resume` **identically**. And the comment calls it a "lifecycle extension" while only half a lifecycle shipped.

**Do not widen this into the delete question.** `w6/m37`'s README records "no MCP delete tool exists for either — deliberate, matches Render's own MCP server; **do not add one**", and `keyvalue/mcp.go:32` repeats it. Delete stays absent. This note is only about `resume`.

## The fix

Target behavior: **every lifecycle verb reachable on REST and GraphQL is reachable on MCP, unless its absence is recorded as deliberate.** Concretely, register `resume_keyvalue` in `keyvalue/mcp.go` as a near-copy of `resume_postgres` (`postgres/mcp.go:228-234`) — note that template takes the plain args struct, not the confirm-carrying one, because resume is the restoring direction:

```go
mcputil.AddTool(srv, &mcp.Tool{
	Name:        "resume_keyvalue",
	Description: "Resume a suspended managed key-value store (restart compute; the data volume, password and endpoint are unchanged). bex extension over Render's MCP.",
}, func(ctx context.Context, _ *mcp.CallToolRequest, in keyValueArgs) (*mcp.CallToolResult, KeyValueView, error) {
	v, err := s.Resume(ctx, in.KeyValueID)
	return nil, v, err
})
```

Then regenerate the scope matrix (`GENERATE_SCOPE_MATRIX=1 go test ./internal/api -run TestGenerateScopeMatrix`). The new op defaults to `OpClassWrite`, which is correct and matches `MCP resume_postgres` — no `scopeClassOverrides` entry is needed, so this addition is not exposed to the gap `w4/082` describes.

**Name it `resume_keyvalue`, not `resume_key_value`.** Its five siblings use `key_value`, so `suspend_keyvalue` is already the odd one out — but pair symmetry with the tool it undoes matters more to a calling agent than family symmetry, and renaming a shipped tool is a client-visible break. The naming inconsistency is worth a separate cleanup decision (there is precedent for removing MCP tools outright — `w1/m71` and `w1/m74` retired several), not a drive-by rename inside this fix.

Blast radius: additive. One new tool registration, one regenerated table entry. No existing caller changes behavior.

Adjacent classes: `Resume` on an already-running store is a no-op flip of `spec.suspended` (`setSuspended`); a store the caller cannot operate fails the existing `core.RelCanOperate` check in `fetchKeyValue`, i.e. forbidden, exactly as REST and GraphQL already answer.

## Two smaller things found in the same file

- **Stale comment.** `keyvalue/mcp.go:34-35` says "`rename_key_value` is likewise a bex extension, the sibling of `rename_postgres`". Neither tool exists — `w1/m74` folded both into `update_key_value`/`update_postgres`, and the very same file says so at `:158` ("replaces the retired ... `rename_key_value`/`update_key_value_plan`"). The header contradicts the tool description 120 lines below it. One-line fix while in there.
- **No verb-level surface-parity test exists.** `keyvalue/metadata_cross_surface_test.go` pins *field* parity across GraphQL and MCP for three metadata fields (`w9/m42/t003`), which is why a whole missing **verb** sailed through. A test asserting that the lifecycle verb set matches across surfaces — with an explicit allowlist for deliberate omissions like KV delete — is the thing that would have caught this and would catch the next one. That is the more valuable follow-on, and it is bigger than this note.

## Not filed as a milestone

The fix is one tool registration plus a regenerate — well under an hour. The verb-parity test above is the part that could justify a milestone; promote this note only if that is taken on with it.

## Unverified

- **The suspend→resume round trip was not executed.** Doing so would require suspending a production Key Value belonging to the operator, which the hunt's rules forbid. The claim rests on the deployed `tools/list` response plus the `Resume` service method, not on an observed recovery.
- **No completeness claim about other missing MCP verbs.** A mechanical GraphQL-mutation → MCP-tool name diff produced 85 apparent gaps and is unusable as evidence: GraphQL says `Database` where MCP says `postgres` (so `resumeDatabase`/`resume_postgres` reads as a false gap), and `w1/m71`/`w1/m74` folded roughly 40 `set*` mutations into consolidated `update_*` tools. The Key Value pair is verified **directly**; whether any other verb is genuinely missing is open, and is what the parity test above would settle.
- The dashboard's own Key Value resume control was not exercised this pass; REST/GraphQL presence is read from the guarded op table, not clicked.
- Deploy status, **ninth consecutive check**: production still serves the pre-`e6419af0b` build (Settings → API Keys has no Client ID column), so `w4/078`'s concurrency re-probe, `w4/m105`'s scoped exchange and `w4/m106`'s live refusal test all remain queued.
