# 529 — After "Save and deploy", the service says "Use a standard deploy to apply them" for ~15 s while the deploy it just started is still `created`

Why: w4/m184 promised that while a deploy already carries the saved settings, bex says they "go live when the current deploy finishes" and never asks for another deploy. Live, the saved-changes notice tells the user to deploy again for the first ~15 s after Save and deploy (or a manual deploy), until the operator flips the phase to `Deploying`. A user who follows that advice queues a second, redundant deploy. For a repo-backed service the same gate excludes the whole `Building` phase, so the window may last the entire build.

**Severity:** minor (wrong advice for ~15 s on an image service and for the whole build — ~2 min measured — on a repo-backed one; following it costs one extra deploy, nothing is lost) · **Estimate:** 40m · **Worker:** worker4 · **Status:** todo

- **Root cause:**
  - `lego/operator/internal/controller/saved_configuration.go:120-125`: `inFlightCarriesSavedConfiguration` returns false unless `app.Status.Phase == PhaseDeploying` (`:122`). Its own comment (`:114-119`) says "A normal release that has not dispatched yet has no record, but it snapshots the saved values when it does, so it carries them", but the phase gate rejects exactly that pre-dispatch window (phase still `Running`, or `Pending`/`Building`).
  - The deploy request already makes `pending > successful` at request time: `lego/backend/internal/rollout/rollout.go:195` stamps `AnnotationReleaseGeneration = generation+1` with the spec change.
  - The dashboard is not at fault: `dashboard/src/features/services/lib/status.ts:363-381` picks the hint from the backend's `undeployedChangesApplying`.
- **Fix — target behavior:**
  - `undeployedChangesApplying` is true from the moment a normal (non-restart, non-rollback, non-canceled) release newer than the serving one is requested, through `Pending`/`Building`/`Deploying`, until it serves or fails.
  - Replace the `Phase == Deploying` gate with "the requested release is not terminal": exclude `Failed` and `Canceled` (and `canceledReleaseIsLatest`), keep the restart/rollback exclusion (`ActiveReleaseConfig().SourceGeneration`/`PreserveGroupValues`) and the record comparison when a record exists.
  - Check that `savedConfigurationPredicate` (`:52-73`) requeues on the deploy request itself (generation bump), so the field flips without waiting for the 1-minute requeue.
- **Keep (w4/m184 DoD, walked item by item):**
  1. During the deploy → "go live when the current deploy finishes": now must also hold before dispatch. Failing today for ~15 s.
  2. After that deploy fails, "Use a standard deploy" returns: not probed this run. It must stay true, which is why `Failed` stays excluded.
  3. Restart, rollback, cancel, and Save only after the deploy started keep the standard hint: not probed this run. Keep the existing tests.
  4. REST, GraphQL and MCP expose the same field: GraphQL probed; REST and MCP share `AppView` (`apps/render.go:437`, `apps/graphql.go:359`).
