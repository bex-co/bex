# 232 — Deploy history silently loses an older row after a new deployment arrives

Why: a service's complete deployment history must not become a convincing, exhausted list with an older rollback candidate missing just because a new deployment starts.

- **Severity:** major: persistent missing history and an unavailable row action on the dedicated Deploys surface. The API retains the deployment; reload is a workaround. No data loss or hosting failure observed.
- **Estimate:** 55m: page-boundary/state correction 20m, caller and sibling audit 10m, behavioral regression 20m, live acceptance 5m. One bounded inbox fix.
- **Source:** user-requested functional qa-find-bugs loop, 2026-10-10 UTC pass a44, muse profile, workspace `tea-d98210cbbpdc73dcrkvg`. Research HEAD `3b60457ad`. Filing only; no implementation.
- **Goal linkage:** [ADR004 deployment](../../docs/ADR004-app-deployment.md), [ADR018 parity](../../docs/ADR018-render-parity.md), and [ADR008 hosting vision](../../docs/ADR008-vision.md). The existing Deploys page should show a continuous newest-first history and allow recovery of older entries after a live arrival. This is an active functional defect in already-shipped pagination.

## Live reproduction and controls

Owned Free image web service **qa-20261010-loop-a44-web**, `srv-db5066cb8ulc73efu2ug`, BusyBox 1.37, benign HTTP process on port 3000, auto-deploy off. One initial deployment, one dashboard Manual Deploy → Deploy latest image, then sequential normal TriggerDeploy requests to prepare 21 records. Each preceding deployment reached live before the next started; no overlapping rollout flood, response interception, artificial delay or paid change.

1. Fresh-load `/services/srv-db5066cb8ulc73efu2ug/deploys`. The head has 20 rows, newest ordinal 21 through ordinal 2. Click **Load more**. Its HTTP 200 response supplies ordinal 1. At **2026-10-10T09:26:58.537Z**, all **21** unique rows are present and Load more is absent.
2. Leave this page mounted. Send the normal TriggerDeploy mutation from a separate API request. Deployment 22, `dep-db50a0s6flus738pni5g`, is created at **2026-10-10T09:27:31.739903Z**. The dashboard poll completes at **2026-10-10T09:27:57.799Z** with the correct 20-row head, ordinals 22 through 3.
3. At **2026-10-10T09:28:20.158Z**, the service is Running / rev-22, deployment 22 is live, and an independent GraphQL read returns **22** records. The UI shows **21**, without Load more: ordinal 2, `dep-db506ic6flus738pnhr0`, disappeared; ordinal 1 remains. No navigation, filter or search change occurred between loading the tail and the arrival.
4. Reload and click Load more. At **2026-10-10T09:28:52.890Z**, the UI shows all **22** unique records. The successful older page now contains the missing ordinal 2 plus ordinal 1.
5. Repeat from that freshly loaded complete history. Trigger deployment 23, `dep-db50ascb8ulc73efu3ag`, at **2026-10-10T09:29:21.165012Z**. Its appearance changes the UI to **22** records with no Load more; ordinal 3, `dep-db506rcb8ulc73efu300`, disappears while ordinals 2 and 1 remain.
6. At **2026-10-10T09:30:40.061Z**, after the new deployment is live and the service is Running / rev-23, the API still has **23**, the UI still has **22**, and Load more is still absent. The latest-deploy header has converged to the correct new Live deployment. Reload → Load more restores all **23** at **2026-10-10T09:30:43.380Z**.

Control: after recovery, the **Live** status filter shows the sole current deployment and no older tail; returning to **All statuses** shows the correct 23-row history. It reuses the still-valid original tail, rather than promising a fresh Load more button. The first automation attempt assumed that button would reappear and timed out; that expectation was wrong, and no finding is based on it.

## Root cause and proposed correction

`dashboard/src/features/deploys/hooks/use-deploys.ts:74–86` stores appended rows and the last appended page size, tagged only by service/status filter. It stores no head-boundary cursor.

`mergeDeployPages` at **:95–110** invalidates the append only if an appended id occurs in the refreshed first page. Its comment at **:89–93** has the shift direction wrong for a new newest deployment: insertion moves the previous head's oldest row **out of** page one, leaving a gap before the already-loaded older tail. It does not move that older tail into page one.

The exact failing first case is:

```text
loaded head:    [21 … 2]       appended: [1], lastPageSize: 1
refreshed head:[22 … 3]       appended: [1]
merged UI:     [22 … 3, 1]    missing 2; no overlap; hasMore false
fresh reload:  [22 … 3]       Load more after 3 => [2, 1]
```

At **:152–159**, the derived merge retains that non-overlapping tail. At **:169–172**, its old short-page size makes `hasMore` false even though the refreshed head no longer joins that tail. The consumer `deploys-list-page.tsx:115–136` uses the merged rows and chooses the exhausted count wording from `hasMore`; **:380–390** removes Load more. This makes the incomplete array look complete.

**Target:** tag a loaded tail with the first-page boundary cursor against which it was fetched. When a refreshed head no longer ends at that boundary, or another merge condition invalidates contiguity, render the current head and reset the actual stored append rows, exhaustion size and append error together. A full 20-row head must expose Load more until a page fetched from its current last id proves exhaustion. Keep appended history across status-only updates whose boundary remains valid.

The Load more updater at **:190–204** currently reuses raw previous rows based only on filter equality. Validate/rebase that stored context as well; changing only the derived render would reproduce [w4/230](230.md)'s recovery defect. A request started under an old service/filter/head context must not revive that stale tail after the head shifts. Retag a fresh append with the current boundary and preserve one continuous, deduplicated newest-first sequence. Keep current loading/empty/error behavior, and preserve last-good rows while a read is pending or fails; an unavailable page must not become successful exhaustion.

No new API field or global Apollo policy is necessary. `DeploysQueryVariables` / `DeploysQuery` at `dashboard/src/graphql/definitions.ts:548–562` already express optional cursor/limit/status and nullable deploy rows. The wire response is a bare list with no `hasNextPage`; the dashboard's page-state bookkeeping owns exhaustion.
