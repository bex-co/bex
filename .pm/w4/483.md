# 483 — For a repo the GitHub App doesn't cover, production promises auto-deploy "via a manual git webhook with your BEX_WEBHOOK_SECRET", a secret customers can't get and that production rejects

Why: a customer who builds from a public Git URL (or a repo outside their installation's grant) sees Auto-Deploy "On Commit" plus a hint to configure a webhook with "your BEX_WEBHOOK_SECRET". On hosted bex that is the operator's shared env var. No customer has it, and production refuses it anyway (`403 manual webhook key disabled in multitenant mode`). So every push is silently ignored while the API and the dashboard both say auto-deploy is on and deliverable.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 51, 2026-11-05 06:46–06:52 UTC (`muse.env`, `bex-canary`, pin `dcdc774c1a6b`); **major** (the product promises a path that cannot work, and the user loses deploys silently); ~45m.
- **Probe:** owned web service `qa-20261105-hook` (`srv-dbm2c6oiff5c739puvfg`, public `https://github.com/bex-co/bex`, `examples/hello-go`, deleted at 06:52). bex-canary's GitHub App installation does not grant `bex-co/bex`.
  - `GET /v1/services/<id>` → `"autoDeploy":"yes","autoDeployTrigger":"commit","pushDeliveryMethod":"manual_webhook"`. GraphQL `{ service(id:…){ autoDeploy pushDeliveryMethod } }` → `{"autoDeploy":true,"pushDeliveryMethod":"manual_webhook"}`.
  - `/services/<id>/settings` → Deploy: `Auto-Deploy A push redeploys only if the repo's manual git webhook is configured with your BEX_WEBHOOK_SECRET.` (`combobox "Auto-Deploy": On Commit`).
  - Production is multitenant: `lego/operator/config/api/deployment.yaml:189` sets `BEX_CP_DB_URI`, so `cmd/api/main.go:713` sets `srv.MultitenantWebhook = true`, and `apps/webhook.go:336-338` answers a manual-key delivery `403 "manual webhook key disabled in multitenant mode; use the GitHub App webhook"`.
  - Control on the same service: the **Deploy Hook** works. Reveal, then POST (and GET) the URL → `200 {"deploy":{"id":"dep-…"}}`, and the deploys list shows `trigger: deploy_hook`. Cancel works on both a queued and an in-progress deploy (`200`, status `canceled`, `deploy_ended canceled` in Events, and the earlier Live deploy stays live).
- **Root cause:** `lego/backend/internal/apps/pushdelivery.go:113-150` `pushDeliveryMethod` returns `manual_webhook` for every repo the GitHub App doesn't grant (`:145`) and whenever the App isn't wired (`:119-125`). It never asks whether the manual key is accepted on this install. The dashboard renders `services.autoDeployViaWebhook` (`dashboard/src/features/services/locales/en.ts:2726-2731`, zh twin) for that value (`components/build-deploy-section.tsx:124`).
- **Fix (target behavior):** on a multitenant install, a repo-backed service whose repo the GitHub App doesn't cover reports a value that means "no push can reach bex". Use a new `unavailable` value, or a reason the dashboard can render, and document it in ADR026 §7a. It must not report `manual_webhook`. The dashboard then says, for example, `Auto-deploy can't run for this repo: GitHub doesn't send bex its pushes. Connect it through the GitHub app, or trigger deploys with the Deploy Hook below.` Single-tenant installs, where the shared secret is accepted, keep `manual_webhook` and the current copy, but should name the operator setting rather than "your …".
  - Plumb the multitenant flag (or "manual key accepted") from `api.Server` into `apps.Service`.
  - REST, GraphQL (`server.graphql`) and MCP `get_service` read the same view (`service.go:1497`), so all three move together. Update `services/types.ts`.
- **Tests:** `pushDeliveryMethod` with Multitenant on/off × granted/ungranted/no-App; a dashboard test for the new copy; regression tests that `github_app`, `none` (image) and `unknown` are unchanged.
- **Blast radius:** one producer (`pushDeliveryMethod`, one caller at `service.go:1497`) and one dashboard consumer (`build-deploy-section.tsx`). `grep -rln manual_webhook lego/backend/internal dashboard/src` (excluding tests) → 7 files: `apps/{service,pushdelivery}.go`; dashboard `locales/{en,zh}.ts`, `types.ts`, `build-deploy-section.tsx`, `api/server.graphql`.
- **Adjacent:** `autoDeploy` stays `yes` (Render keeps the setting on). Only the delivery claim changes. Whether to also stop defaulting `autoDeploy` on for uncovered repos is a separate decision; do not fold it in.

- **Render:** a Render service can only be created from a repo its connected Git provider covers, or from a public URL with no auto-deploy. Render never promises push-to-deploy it can't deliver (ADR026:139).
