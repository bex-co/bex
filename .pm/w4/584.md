# 584 — A `level` filter never selects request lines, though a request line now carries Render's `level` (info, warning, error)

Why: since w4/m325 a request line is labelled `level` from its status class, as Render's are (`info`, `warning` for 4xx, `error` for 5xx; `docs/render-artifacts/request-logs.md`). The label is only read, never filtered. History's `level` matcher is a Loki stream-label matcher, and request streams carry no `level`, so `GET /v1/logs?resource=…&level=error` returns app errors but no 5xx request lines. On Render, `level:error` should find them, unverified. The live tail strips `level` from its request producer, and `logLabelValues(level)` offers only app levels.

- **Source / severity / estimate:** w4/m325 t007 (`/simplify` review, 2026-11-11). **Minor**. ~1h.
- **Where:** `lokiSelectorFor` (`lego/backend/internal/logs/loki.go`); `pollRequestLogs` and the subscribe filter split (`service.go`); the shipper's `request_logs` stage (`deploy/gitops/base/log-shipper.yaml`).
- **Fix sketch:**
  - First confirm Render's behaviour with a read-only `GET /v1/logs?type=request&level=error` against the reference workspace.
  - Then either stamp `level` on request streams in the shipper (from `DownstreamStatus`, so new lines are selectable), or translate a `level` filter on request lines into a status-class matcher (works for old lines too). Discovery should then offer the request levels.
- **Dedupe:** w8/m147 (done) routed `level` to app lines on purpose, when request lines had no level.
