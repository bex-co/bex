# Cached environment membership misclassifies newly created services as workspace-scoped

Why: after an ordinary service creation, configuration actions can offer groups that cannot be linked and initialize a new group in the wrong scope until the customer reloads.

- **Source / severity / estimate:** continuous live `qa-find-bugs`, user-selected w4, 2026-10-08 cycle 2 (captures 2026-10-09 UTC); **minor**, 55m. Follow-up regression coverage for [w4/217](done/217.md), whose scope filter is deployed. ADR008 usable hosting configuration; ADR032 grouping and ADR006 / ADR018 surface contracts. Filing only.
- **Repro:** create an owned project with staging and production environments; create a staging group with synthetic `QA_GROUP_MARKER` and `qa-group-note.txt`, then clone it and move the unlinked clone to Workspace. Fresh-load the staging group detail to prime the authorized scope index. Through New → New Service → Web Service → Existing Image, create a Free BusyBox service in staging, wait for its first deploy, then open Environment without a document reload. Its Available to link list offers the workspace clone and omits the staging group. Clicking **only the owned clone's** Link returns `ENV_GROUP_SERVICE_ENVIRONMENT_MISMATCH`, leaving links empty and the false candidate enabled. Create group initializes Workspace and checks the staging service. Cancel the draft. Reload: Available to link now offers the staging group, and Create group initializes Project / staging with the same checked service.
- **Repetition / controls:** the first service reproduced this; a second creation passed; after a fresh staging-group load, the third creation reproduced at 01:21:59Z, with refused Link at 01:22:12Z and again at 390×844 at 01:23:17Z. Desktop was 1280×900. At 01:24:05Z reload corrected both existing-group availability and Create initialization. This is conditional on cached membership, not a claim that every create fails. Which overlapping query refreshed the second control was not attributed.
- **Expected / actual:** the resolved service's authoritative `environmentId` decides its compatible groups and initial Create scope. Actual derives that relationship from an older workspace membership list; a missing service entry becomes null/Workspace. No wrong link, data loss or authorization bypass occurred. The first fixture reached Live and public HTTP 200; correct-scope Link redeployed it to rev 2, serving both marker lines and the group file. After Unlink and its rollout, the public body became a single newline (neither marker nor file). All three Free services served successfully.

## Root cause, consumer check and bounded fix

- `dashboard/src/features/env-groups/hooks/use-env-group-scope-index.ts:50–75` performs a one-shot `client.query` with initial cache-first policy, copies mapped rows into local React state, and marks them ready. Its effect dependencies (`:97`) are client, owner and explicit retry, not membership changes. The map (`:112–120`) contains services mentioned by that snapshot only. Ready means the query settled; it does not establish current-service membership.
- `dashboard/src/features/env-groups/lib/scope.ts:65` maps an absent entry to null. `features/services/components/env-groups-panel.tsx:82–83` uses that as Create's initial scope, while `:146–159` filters available groups using the same map. `:275–285` passes the stale map and initial scope into NewEnvGroupDialog. These are two traced consumers of the same cause.
- **Do not repair only the default.** `features/env-groups/components/new-env-group-dialog.tsx:223–224` initializes scope and selected service IDs; its scope compatibility checks still read the supplied map. Supplying a corrected initial environment alongside the stale map would remove/refuse the selected service. Both must describe the resolved current service.
- `features/services/api/server.graphql:9` does not select `environmentId`; `features/services/types.ts` and `lib/status.ts:34` therefore do not preserve it in ServiceView. Add the existing nullable field to Server, regenerate GraphQL output, and preserve the distinction between **undefined/unresolved**, **null/known Workspace**, and a known environment ID. `lego/backend/internal/apps/graphql.go:396` already exposes it; `internal/gqlutil/gqlutil.go:103–111` resolves the Go empty relationship to GraphQL null. The exact `server` probe below proves this layer can express the target. No new API field or backend behavior is needed.
- **Allowlist the behavior change to EnvGroupsPanel.** Use the resolved Server relationship to overlay the current service's entry in a panel-local compatibility map (key it by the resolved service.id and consistently use that ID for local selection/filtering; set its environment for a known relationship and remove it only for explicitly known null). Use that map for both existing-group filtering and NewEnvGroupDialog, and use the authoritative relationship for initial scope. Never treat missing data as Workspace. If a non-null relationship's environment option is absent from the authorized index, refresh that index or show pending/error + retry; do not reset to Workspace or offer a mismatched submit. Keep the existing exact-scope backend refusal and shared helper's other callers unchanged.
- **Before settle / neighbours:** available choices and Create wait for a resolved service relationship, with stable pending geometry and actionable failures. Preserve linked rows and Unlink during this gate. Missing/forbidden/unauthenticated stay route/hook-owned; timeout or index failure cannot synthesize null. A failed refresh preserves last-good authorized context under the existing error handling. Do not add discovery or cross-workspace queries, and retain owner-generation isolation.
- **Framework read:** installed Apollo **4.1.3** matches the captured client extension. `node_modules/@apollo/client/core/ApolloClient.js:230–243` returns a query Promise; `core/QueryManager.js:319–333` resolves one result, and `:1052–1065` returns a complete cached result with `fromLink:false`. This hook does not create an ObservableQuery subscription. CreateService (`hooks/use-create-service.ts:121–145`) writes its Service result without refreshing this copied index. Cache readiness is not a freshness guarantee. The third capture's correct Project / staging breadcrumb alongside a wrong group list is consistent: `common/components/dashboard-layout/dashboard-breadcrumbs.tsx:80–98` uses reactive per-project queries, while the panel's scope hook retains its copied workspace snapshot. Do not fold the first fixture's stale breadcrumb into this fix; its independent placement presentation is outside this filing.
