## Objective

Two of the three switches on the Scaling tab's autoscaling panel are unnamed to a screen reader. The same panel also spells one word two ways.

## Context

### Verified against the real accessibility tree, not a DOM heuristic

On `/services/<srv-id>/scaling` with autoscaling on, `await page.locator('main').ariaSnapshot()` returns:

```text
- switch "Autoscaling on" [checked]
- text: Autoscaling on
- paragraph: Number of Instances
- spinbutton "Minimum instances": "1"
- slider "Minimum"
- slider "Maximum"
- spinbutton "Maximum instances": "1"
- paragraph: Target CPU Utilization
- paragraph: If average CPU utilization is significantly above or below this value, bex adds or removes instances accordingly.
- switch                                   ← unnamed
- paragraph: Target Memory Utilization
- paragraph: If average memory utilization is significantly above or below this value, bex adds or removes instances accordingly.
- switch                                   ← unnamed
- paragraph: At least one utilisation target (CPU or memory) must be enabled.
```

Probed directly, the two have no naming relationship of any kind:

```js
// #cpu-enabled and #mem-enabled:
{ ariaLabel: "", labelledby: null, labelledText: "", title: null }
```

Their adjacent text lives in `<p>` elements, not `<label for>`, so there is nothing for the accessibility tree to pick up. `#autoscaling-enabled` in the same panel **is** named ("Autoscaling on") — the in-panel control case proving the pattern is normally right.

### Relationship to `w4/043` (done)

043 fixed accessible names on this panel's **sliders and number inputs** and its fix is live — `spinbutton "Minimum instances"`, `slider "Minimum"`, `slider "Maximum"`, `spinbutton "Maximum instances"` all come back named above. The `role=switch` toggles were never in 043's scope (it was about `SliderInput` and the Radix thumb). 043's own Unverified line lists "autoscaling-on UI, CPU/memory sibling controls in production" as unprobed; this run probed them and found the sliders fixed and the switches bare. Follow 043's shape: a translated name per control, not one generic label reused.

### The spelling

`At least one utilisation target (CPU or memory) must be enabled.` — British "utilisation", sitting three lines below "Target CPU **Utilization**", "Target Memory **Utilization**", and beside "Average Memory Utilization" / "Average CPU Utilization" in the Recent Metrics panel. The rest of the dashboard uses the American spelling.

## Steps

1. Give `#cpu-enabled` and `#mem-enabled` translated accessible names distinguishing the two quantities — the natural keys are the existing "Target CPU Utilization" / "Target Memory Utilization" strings, and the switch's state should be announced as state, not baked into the name (follow how `#autoscaling-enabled` does it).
2. Sweep the panel for any other unnamed interactive control while there (the `ariaSnapshot()` above is the reference output).
3. Fix "utilisation" → "utilization" in `en.ts`, and check `zh.ts` for the paired key.
4. Grep the dashboard for other British spellings of this word so the fix is not one-off: `rg -n 'utilis' dashboard/src`.
5. Assert names with focused accessible-name queries (`getByRole("switch", { name: … })`), not text presence — a test that finds the paragraph text would pass today.
