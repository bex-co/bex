## Objective

The "Add SSH public key" dialog validates correctly and says something genuinely useful — and says it only to people who can see. The error paragraph is not associated with the field, the field is never marked invalid, and the Save button silently disables. A screen-reader user pastes a key, hears nothing, and finds an unexplained disabled button. The dialog one card away on the same page (invite a member) does this correctly, so this is an outlier, not a missing convention.

## Context

### The observation (production, 2026-09-13 pass 14)

`https://dashboard.bex.co/settings` → Access credentials → **Add SSH key**, name `qa-20260913-sshkey`, public key `not-a-key`:

```text
dialog text:  Add SSH public key
              Paste one OpenSSH public key. Comments are removed when it is saved.
              Name
              Public key
              Enter one supported OpenSSH public key (RSA must be at least 2048 bits).
              Cancel   Add key         ← disabled
```

The message is accurate and the gate is right. Probed on the textarea itself:

```js
{ "aria-invalid": null, "aria-describedby": null }
// and the error node: <p class="text-destructive text-sm">Enter one supported OpenSSH public key…</p>
//                     — no id, no role="alert"
```

So the only three mechanisms that could convey the failure non-visually are all absent, on the one control in the dialog that can fail.

### Root cause

`dashboard/src/features/ssh-keys/components/ssh-keys-panel.tsx:114-129`:

- `:114` is a **raw `<textarea>`** with hand-written classes, not the shadcn primitive — so it inherits none of the kit's `aria-invalid:` styling or conventions;
- `:125-129` renders the error as a bare `<p className="text-destructive text-sm">` with no `id` and no `role="alert"`;
- the Save button at `:136-138` is `disabled={!valid || …}` with no accessible explanation of why.

### The in-repo control case, on the same page

`dashboard/src/features/team/components/invite-member-dialog.tsx:117-137` — same dialog family, same settings surface — sets `aria-invalid={showEmailError || !!refusal}` **and** `aria-describedby` pointing at the specific error node's `id` (`invite-email-invalid` / `invite-email-refusal`), each `<p>` carrying that id. That is the target shape.

A second, weaker convention also exists: `dashboard/src/common/components/text-field.tsx:42-47` sets `aria-invalid` plus `role="alert"` on the error copy but no `aria-describedby`. **Name one: the invite dialog's** — `aria-invalid` + `aria-describedby` gives the association a screen reader can re-read on demand, which `role="alert"` (announced once, then gone) does not. Adding `role="alert"` as well is fine; replacing the association with it is not.

Most already carry either an `id` referenced by `aria-describedby` (webhooks, `webhooks_.new.tsx`, invite dialog, create-database dialog) or `role="alert"`. The ones with **neither**, and therefore this task's candidate list:

## Steps

1. In `ssh-keys-panel.tsx`, give the error `<p>` an id (e.g. `ssh-public-key-invalid`), and set `aria-invalid` + `aria-describedby` on the textarea from the same `publicKey && !keyValid` condition that already gates the message.
2. Replace the raw `<textarea>` with the kit's `Textarea` primitive if one exists with equivalent styling; if adopting it changes the rendered box, keep the raw element and note why — this is a labelling task, not a restyle.
3. Consider naming the disabled state: the button is disabled whenever `!valid`, which includes an empty name. A `title`/`aria-describedby` on the button, or simply the field-level association from step 1, is enough — do not add a second error region that repeats the first.
4. Walk the four sibling sites in the table and record the decision for each (field association vs `role="alert"` vs deliberately neither).
5. Verify in the real accessibility tree, not the DOM: with an invalid key pasted, the textarea's computed description must include the error text.

## Swept in the same pass and found correct, so not filed

The whole SSH-keys journey is in good shape; recorded so the next hunt spends its time elsewhere.

- **Create → verify → delete round trip.** A throwaway `ed25519` key added through the dialog rendered the fingerprint `SHA256:aUSa7pBHfpc9GvM8Fq1mBryzylrDGS4q0GXTxFPaaxM`, **byte-identical** to local `ssh-keygen -lf`. Deleting it removed it from both the table and `{ sshKeys { … } }` in the same beat, with the toast "Deleted qa-20260913-sshkey". Nothing was left behind.
- **The dialog's promise is kept.** "Comments are removed when it is saved" — the stored `publicKey` came back as `ssh-ed25519 AAAAC3…jdBjR` with the ` qa-0913l@bex-qa` comment stripped, and the fingerprint (which does not cover the comment) unchanged.
- **Server-side validation is not a client-side gate in disguise.** Bypassing the UI straight to `createSSHKey`: `not-a-key` → `bad request: invalid SSH public key`; a real 1024-bit RSA key → `bad request: RSA SSH public keys must be at least 2048 bits` (so the UI's "at least 2048 bits" claim is enforced where it counts); empty name → `bad request: SSH key name must be 1-120 bytes`.
- **Duplicate keys are refused honestly, and the refusal reaches the user.** The same public key under a second name → `conflict: SSH public key is already registered` from GraphQL, and through the UI the dialog **stays open** (input preserved) with the toast "This public key is already registered" — the correct shape for a failed submit.
- **Both dialog inputs are properly labelled** (`<label for="ssh-key-name">Name`, `<label for="ssh-public-key">Public key`), and the delete confirmation names the key it will delete ("Delete qa-20260913-sshkey?").
- **Unverified:** the delete dialog's claim that "New SSH connections using this key will be rejected immediately" — verifying it needs a live SSH session against the gateway, which needs a paid running service, so it was not exercised. Also unverified: whether a newly added key reaches the gateway's authorized set at all (same reason).
