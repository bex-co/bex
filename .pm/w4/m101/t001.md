## Objective

bex accepts and stores an autoscaling configuration for a cron job. The reconciler never reads it — a `cron_job` returns before the replica path exists. Refuse the configuration at the service layer for every type that cannot honor it, and resolve the undocumented background-worker exclusion instead of leaving it implicit.

## Context

### The observation (production, 2026-09-13)

Cron job `qa-0913b-cron` (`srv-daj7srogsm7s73f63o5g`), `schedule: */5 * * * *`, docker runtime, Live. Through the dashboard's own Scaling tab: toggle **Autoscaling on**, toggle **Target CPU Utilization** on, **Save Changes**. Then:

```text
GET https://api.bex.co/v1/services/srv-daj7srogsm7s73f63o5g/autoscaling → 200
{"enabled":true,"minInstances":1,"maxInstances":1,"targetCPUPercent":60}
```

The service object for the same id confirms what it is:

```text
GET https://api.bex.co/v1/services/srv-daj7srogsm7s73f63o5g → 200
{"id":"srv-daj7srogsm7s73f63o5g","name":"qa-0913b-cron","type":"cron_job",
 "serviceDetails":{…,"nextRunAt":"2026-09-13T10:50:00Z","numInstances":1,"schedule":"*/5 * * * *"},
 "phase":"Running","replicas":1,"schedule":"*/5 * * * *", …}
```

No error, no warning, and the panel renders the saved policy back. There is nothing in the product that will ever act on it.

### Why it can never be honored

- `lego/operator/internal/controller/app_controller.go:2000-2003` — _"A cron_job diverges entirely: a batch/v1 CronJob, no Deployment/Service/Ingress"_ — `reconcileCronJob` returns here.
- `:2017` — `desiredReplicas(...)` is called **after** that return, and `:2294` is the only reader of `app.Spec.Autoscaling` on the reconcile path. For a `cron_job` the line is unreachable.

### Why the validator lets it through

`lego/backend/internal/apps/service.go:4362-4402` — `autoscalingSpec` validates min/max ordering, the `MaxReplicas` ceiling, the plan cap via `checkInstanceCap`, both target percentages, and that at least one target is set. It never reads `a.Spec.Type`. `SetAutoscaling` (`:4434-4457`) then patches `spec.autoscaling` for any type.

The in-repo precedent for the missing check is `validateDisk` in `lego/backend/internal/apps/disks.go`, cited by `dashboard/src/features/services/components/service-nav.tsx:107-111`: _"Disk is type-gated to exactly what the API accepts — web, private, and worker (validateDisk …). A cron job has no long-running instance to mount a volume on, so offering the tab there would lead to an Add Disk button that always 400s."_ Autoscaling needs the same gate; the difference is that today it does not even 400, it succeeds.

### Every write entry point (grep, not estimate)

`grep -rn "autoscalingSpec(\|SetAutoscaling(\|DeleteAutoscaling(" lego/backend/internal | grep -v _test | grep -v "func "`:

| entry point | path |
| --- | --- |
| create + Blueprint `scaling:` block | `apps/service.go:2579` (`specFromCreate`) |
| `SetAutoscaling` core verb | `apps/service.go:4439` |
| REST `PUT /v1/services/{id}/autoscaling` | `apps/rest.go:1116` |
| GraphQL `setAutoscaling` | `apps/graphql.go:1683` |
| settings patch | `apps/settings.go:295` |
| MCP delete | `apps/mcp.go:865` |

The type check belongs in `autoscalingSpec` (or a sibling called by it) so all of them inherit it — not in one adapter. Note MCP has a delete but no visible setter in that grep; confirm whether a setter reaches `SetAutoscaling` through the folded settings tool (`docs/render-artifacts/mcp-setter-fold-2026-08-18.md`) and cover it if so.

### The background-worker question — resolve it, do not assume

`app_controller.go:2294`: `if app.Spec.Autoscaling != nil && app.Spec.Autoscaling.Enabled && !worker && !app.Spec.Suspended {`. A `background_worker` reaches `desiredReplicas` and is then **excluded by `!worker`**, so an accepted worker autoscaling config is discarded exactly like a cron job's — but silently, and for a type Render does support: `docs/render-artifacts/manual-scaling.md:7` says the Scaling page covers "web/private/background services". `git log -S'&& !worker && !app.Spec.Suspended'` traces the exclusion to `a58a64967` (2026-07-11, "feat(m20): per-service autoscaling — operator + API + dashboard") with **no rationale comment and no test**. So the intent is not recoverable from the repo.

## Steps

1. Decide the eligible set and write it down. `cron_job` and `static_site` have no replica concept and must be refused. For `background_worker` pick one, explicitly:
   - **honor it** — drop `!worker` at `:2294`, confirm a worker Deployment's replicas actually move under load, and check whether anything else assumed workers never autoscale (grep `worker` through `autoscale.go` and the replica clamp at `app_controller.go:3874`); or
   - **refuse it** — treat it like cron and record the divergence from Render's captured contract in `docs/ADR018-render-parity.md` with the reason.
   Do not ship a state where the API accepts it and the reconciler drops it.
2. Add the type check where every entry point inherits it, and make the error name the type and the reason — not a bare 400. Use the existing coded-error convention (`core.ErrBadRequest` plus a coded envelope if one fits) so the dashboard can key on it rather than on message text.
3. Decide what happens to the **already-stored** config. At least one production cron job (this run's, now deleted) proved the write lands, so other workspaces may hold one. State whether `GET …/autoscaling` should keep reporting a stored-but-unhonorable `enabled:true` or normalize it to disabled for an ineligible type, and whether a one-shot cleanup is warranted. Reporting it honestly is the minimum; silently continuing to echo it is what made this invisible.
4. Keep `DeleteAutoscaling` working for an ineligible type that already has a stored config — otherwise a user cannot clear the thing they should never have been able to set.
5. Re-probe: create a throwaway cron job, attempt the write on REST and GraphQL, confirm the refusal and that `GET` still reads disabled.

## Acceptance criteria

- [ ] `PUT /v1/services/<cron-id>/autoscaling` refuses with an error naming the type; `GET` still reads disabled. Test fails before the change.
- [ ] The same refusal holds for GraphQL `setAutoscaling`, the settings-patch path, and the create/Blueprint `scaling:` block — one test per entry point.
- [ ] A **web service** can still enable autoscaling with unchanged behavior (the control case) — asserted, not assumed.
- [ ] The background-worker decision is implemented, tested, and written down in the ADR.
- [ ] `DeleteAutoscaling` still clears a pre-existing stored config on an ineligible type.
- [ ] The MCP surface is confirmed either covered or genuinely absent, with the grep recorded here.
