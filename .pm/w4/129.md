# 42 of 54 usage rows are for resources that no longer exist, and only 2 of them are marked deleted

Why: the Charges tree is where a workspace answers "what am I paying for", and four-fifths of its line items name resources that return `app not found` — presented not as deleted, but as bare ids indistinguishable from current ones.

Found by live `/qa-find-bugs` 2026-09-21 pass 152 (w4-targeted, `muse.env` credentials). Read-only; nothing was created.

## The counts

`usage(ownerId:)` for the current period returns **54** `services` rows. Classified against the workspace's live `services`/`databases`/`keyValues` lists:

| class                                                          | count |
| ---------------------------------------------------------------- | ------- |
| live resource, named                                            | 10    |
| gone, `deleted: true`, name retained                             | 2     |
| **gone, `deleted: false`, `serviceName: ""`**                    | **42** |

The 42 break down as 19 `service`, 16 `sandbox`, 4 `key_value`, 3 `postgres`.

Four were spot-checked individually and every one is gone:

```graphql
database(id:"dpg-daolmeh2dbts73fi2or0")  → app not found     # usage says deleted:false, name ""
keyValue(id:"red-daolmers0ils73bgphbg")  → app not found     # usage says deleted:false, name ""
service(id:"srv-dakvq2557grc738qmmh0")   → app not found     # usage says deleted:false, name ""
service(id:"srv-dalo003ssesc73e0la40")   → app not found     # usage says deleted:true,  name "qa-20260917-web"  ✅
```

The first two are this QA loop's own pass-143 fixtures, deleted about two hours before the read. So the missing tombstone is not an age effect — a resource deleted **today** lost its flag while two deleted on 2026-09-17 kept theirs.

## What a user sees

The dashboard is doing its part correctly, which is what isolates the defect to the API:

- It **falls back to the raw id** when `serviceName` is empty (`srv-dae9lb988i5c7399e9m0 $0.01`) rather than rendering an empty cell — the same deliberate fallback the audit-log `targetName` field documents.
- It **does** render the marker when the flag is set: `qa-20260917-web(deleted) $0.01`.

So the Charges → Services section lists 19 rows, of which 5 are current services with real names, 2 are correctly marked `(deleted)`, and **14 are bare ids of resources that no longer exist and carry no marker**. A reader cannot tell those 14 from a current service whose name simply failed to resolve.

## Why it is worth fixing even though the money is small

Every one of the 42 is charging **$0.00–$0.01**, so this is an attribution defect, not a billing defect — nobody is being overcharged. But the Charges tree is the one screen whose job is to make a bill legible, and four-fifths of its rows are unattributable. The two correctly-tombstoned rows prove the intended presentation already exists; the rest simply do not reach it.

## Fix

Find why the tombstone (the `deleted` flag plus the retained display name) is present for some deleted resources and absent for others — the two populations are the whole clue, and a resource deleted today landing in the wrong one rules out a retention window. Candidates worth checking first: whether the name/flag come from a join that a hard-delete breaks, and whether `sandbox` rows (16 of the 42, UUID-keyed rather than `srv-`/`dpg-`/`red-`) have a tombstone concept at all.

Estimate: ~40m once the split is understood; the presentation half already works.

## Also checked this pass, and found correct

- **`period` is validated and the failure is precise.** `period:"banana"` → `bad request: period must be a calendar month as YYYY-MM (e.g. 2026-07)`.
- **Coverage is self-declaring rather than silently partial.** The current period reports `coverage.state: "partial"`, `through: "2026-09-01T00:00:00Z"`, and names all seven degraded sources (`direct, http, instance, key_value, postgres, sandbox, websocket`) — and the Billing page surfaces it as a **"Partial data"** badge beside the Charges heading rather than presenting the figure bare.
- **Plan quotas reconcile with reality.** "Services 5 / 100", "Postgres 3 / 25", "Key Value 2 / 25" match the live lists exactly — so the *included-usage* panel counts only live resources even though the charge tree does not, which is further evidence the 42 rows are a tombstone problem rather than a counting one.
- **Payment details are handled well.** The page states "Payment details are entered only on Stripe-hosted pages. bex never sends a Stripe server key to your browser", and the API exposes only brand and last4.
- **Credits are explained, not just shown.** "Credits applied −$39.84 → amount due $0.00" plus the note that a payment method is still required because credit covers invoices first.
