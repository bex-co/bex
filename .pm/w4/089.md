# 089 — A deploy superseded by a newer commit is reported as "Canceled" with no cause, on all three surfaces, while its build logs show it succeeding

Why: on a service that deploys often, ~40% of deploys end in a terminal state that reads as "a human cancelled this" when nothing of the sort happened — and the backend knows the real cause at the moment it decides, then discards it.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 36. **Read-only on production — nothing created, changed or deleted, and no new login session minted** (existing browser session reused, per `w4/085`). Observed on the operator's own `beancount-cms-v2`; nothing on it was touched. Severity: **major** — the journey completes, but the product tells the operator something untrue about why their deploy ended.

## What a user sees

`https://dashboard.bex.co/services/srv-d9bj8s3eg85c7390eb9g/deploys` — of the 8 most recent deploys, **3** read `Canceled`. Opening one (`dep-daju7i26m8ac739r5rc0`):

```text
Deploy status: Canceled
Created: 5:08 AM   Started: 5:08 AM   Finished: 5:26 AM   Duration: 18m
Status timeline:  Deploy created 5:08 → Deploy started 5:08 → Canceled 5:26
```

The status timeline offers three entries and no cause. Meanwhile the tail of that deploy's own build log, at the moment it was "canceled":

```text
05:26:17  #18 exporting layers 79.2s done
05:26:17  #18 exporting manifest sha256:70ba55… 0.0s done
05:26:24  #18 sending tarball 6.3s done
05:26:24  #18 DONE 85.6s
05:26:26  Getting image source signatures
05:26:26  Copying blob sha256:55afa1ec…
```

The build had **finished and was pushing the image**. So the page shows a deploy that was visibly succeeding, stopped, and labelled with a word that means someone stopped it.

## What actually happened, proven

Nothing was cancelled. Each of these was **superseded** by the next commit's deploy. From `api.bex.co/graphql`:

```graphql
{ deploys(serviceId:"srv-d9bj8s3eg85c7390eb9g", limit:8){ id status trigger failureReason startedAt finishedAt } }
```

| deploy | status | startedAt | finishedAt | failureReason |
| --- | --- | --- | --- | --- |
| `dep-daju7i26m8ac739r5rc0` | canceled | 12:08:46.989Z | **12:26:47.134Z** | `""` |
| `dep-daju920gsm7s73f64c80` | live | **12:26:47.210Z** | 12:46:28.846Z | `""` |
| `dep-dajser26m8ac739r5m8g` | canceled | 10:07:47.023Z | **10:24:28.858Z** | `""` |
| `dep-dajsmda6m8ac739r5ms0` | deactivated | **10:24:28.883Z** | 10:41:58.782Z | `""` |
| `dep-dajrrja6m8ac739r5kf0` | canceled | **`""`** | 09:34:03.862Z | `""` |

The canceled row finishes **76 ms** before its successor starts; the second pair, **25 ms**. That is not a coincidence and not a human. The third never started at all (`startedAt: ""`), which is why the list renders its duration as `—` while its siblings show one.

`failureReason` is `""` on every single row.

**This is correct platform behavior** — a newer commit should supersede an in-flight build, and builds here legitimately run 17–20 minutes while commits land every ~17, so supersession is routine. Only the reporting is wrong.

## All three surfaces agree, and all three are silent

Checked, because a disagreement would have been the more valuable finding and this is not one:

- **List** (`/deploys`): `Canceled`
- **Detail timeline**: `Canceled`, no cause
- **Events feed** (`/events`): `Build ended — Canceled` (1081s) and `Deploy ended — Canceled`, no cause

They are consistent with each other and uniformly uninformative, which is good news for the fix: **one backend change reaches all three.**

## Root cause

`store/reconciler.go:1142-1168`, `supersededDeployStatus`. The comment names the cause precisely and the code then throws it away:

```go
// A reported release generation PAST the open row's means this row's release
// was superseded before it could finish — a git-push redeploy, env-var
// change, or restart minted a newer release identity without adopting the
// row. … close it canceled.
if app.Status.ReleaseGeneration > 0 && open.Generation != 0 && app.Status.ReleaseGeneration > open.Generation {
	return DeployCanceled, true
}
```

It returns a bare status. The sibling that would carry the explanation, `deployCloseFailureReason` (`store/reconciler.go:770-787`), has cases for `DeployBuildFailed`, `DeployPreDeployFailed` and `DeployUpdateFailed`, and falls through to `return "", ""` for everything else — including `DeployCanceled`.

## The fix, and the trap in it

Target behavior: **`canceled` keeps its status (Render cancels superseded builds too — this is parity-correct), and gains a machine-readable cause that distinguishes "you cancelled this" from "a newer release replaced this", ideally naming the superseding deploy id.**

**Do not implement this by stamping `failureReason`.** Two reasons, both load-bearing:

1. `w6/m52` **deliberately** stopped stamping a failure reason for a cancel, and its README records that as correct. It was reasoning about the *user-initiated* cancel (`deploys.Cancel`, which closes the row synchronously) — where "no failure reason" is right, because the user knows what they did and it is not a failure. This note is about a **different cause** that m52 did not consider, collapsed into the same status. Reverting m52 would regress its case to fix this one.
2. The consumer would render it wrong. `DeployFailureReason` (`dashboard/src/features/deploys/components/deploy-failure-reason.tsx:20`) gates purely on presence — `if (!reason) return null` — so a populated reason **would** appear immediately at `deploy-header.tsx:118` and `deploys-list-page.tsx:202` with no UI change. But its treatment is hardcoded `text-destructive` (`:23`), so "Superseded by dep-…" would render in error red. A supersede is not an error.

So the shape is: a **cause** distinct from failure (either a new field or `reasonCode`, which `ServiceEventDetails` already exposes and which is `""` today), plus a neutral tone on the presentation component — a `tone` prop is enough; the component already documents that it owns the treatment and callers add layout only.

Blast radius: `deployCloseFailureReason` has its callers inside `store/reconciler.go` (`:722`, `:769` region); `DeployFailureReason` has **3** call sites (deploy header, deploys list row, events feed row), all of which should show the new cause and none of which should show it as destructive.

Adjacent classes, all of which must stay distinguishable after the fix: **user cancel** (`deploys.Cancel`, no reason, per `w6/m52`), **superseded** (this note), **build failed** (reason already stamped from `recordedBuildFailure`), **timed out** (`timedOutDeployReason`), and **deactivated** (a previously-live deploy replaced by a newer live one — already its own status).

## Sizing

Filed as a note: one backend case plus plumbing, one small UI tone prop, and tests. **Promote it to a milestone** if the implementer decides to model deploy-ending causes properly as a taxonomy across all five adjacent classes above rather than adding the supersede case alone — that is a bigger and arguably better piece of work.

## Unverified

- **The supersede cause was inferred from timestamps and the reconciler comment, not from a recorded field** — because no such field exists. The 76 ms / 25 ms gaps plus `ReleaseGeneration` semantics are the evidence; no log line or event says "superseded".
- **`reasonCode` was observed empty, not traced.** It exists on `ServiceEventDetails` and returned `""` on the two live events sampled; whether anything ever populates it, and whether it is the right home for this cause, was not checked in the backend.
- **Not reproduced on a service I control** — doing so would mean pushing two commits in quick succession to a `qa-` service, which needs a build slot and was out of scope for a read-only pass. The mechanism should reproduce on any repo-backed service whose build outlasts the gap between commits.
- `w4/072` (deploy events carry no actor) was re-confirmed incidentally: `actor` and `triggeredByUser` are `""` on the sampled events. Already filed; not re-filed here.
- A `serviceEvents(limit:14)` GraphQL probe returned only 2 events while the dashboard's Events tab showed the full history. That is a **probe artifact** of how `limit` interacts with that query, not a data gap — recorded so the next person does not file it as one. The exact semantics were not chased.
