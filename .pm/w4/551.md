# 551 — Deleting a Postgres credential in the dashboard takes one click on a trash icon, with no confirmation, and every connection using it fails at once

Why: retiring a credential is irreversible, and every client and service that logs in with it breaks the moment it's gone. One stray click on an icon button does that today with no warning, while every other destructive datastore control on the page asks first.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 24, 2026-11-10 14:50–15:15 UTC (`muse.env`, workspace `bex-canary`, pin `c12cd57facb1`). **Major**: irreversible, an immediate outage for clients on that login, triggered by a single mis-click. ~20m.
- **Fixture:** Free Postgres `qa-20261110-pg24` (`dpg-dbpj39dme2kc73f2l7pg`), with external access for my /32. Deleted (GET 404).
- **Probe:** connection strings were used only through the clipboard and a 0600 temp file, never printed, and both were cleared afterwards.
  1. **Original credential works.** `psql` with the copied External connection string reported `current_user = dpg_dbpj39dme2kc73f2l7pg_user`. I created table `qa_t` with one row.
  2. **Rotation works as promised.** Access control → Credentials → New credential username `qa_user_24b` → New default credential.
     - REST `GET /v1/postgres/{id}/credentials` → `[{"username":"dpg_…_user","default":false},{"username":"qa_user_24b","default":true}]`.
     - The newly copied URL connected as `qa_user_24b` and read `qa_t` (1 row).
     - The old URL still connected, so the hint's promise held: "Older credentials keep working until you delete them".
  3. **Delete happens on the first click.** Clicking `button "Delete dpg_dbpj39dme2kc73f2l7pg_user"` removed it immediately:
     - no dialog (alertdialog/dialog count 0) and no toast;
     - the list then showed only `qa_user_24b`;
     - the old URL failed with `FATAL: password authentication failed for user …`.
- **Root cause:**
  - `dashboard/src/features/databases/components/access-control-panel.tsx:175` calls `access.deleteCredential(c.username)` directly from the button's `onClick`.
  - The button is the icon labelled `databases.accessCredentialDelete`, "Delete {name}" (`features/databases/locales/en.ts:943-946`).
  - The same panel already wraps the pooler toggle in a `ConfirmDialog` (imported at `:14`, used at `:314` on origin/main since w2/m307). Every other destructive datastore control on the page confirms too.
  - The backend `DeleteCredential` (`lego/backend/internal/postgres/access.go:289-300`) retires the login exactly as Render's delete-postgres-user does. It is reached from REST (`rest.go:407`), GraphQL `deleteDatabaseCredential` (`graphql.go:747`) and MCP (`mcp.go:454`). The API needs no change.
- **Fix (target behavior):**
  - Delete opens a destructive `ConfirmDialog`:
    - title: "Delete credential {name}?"
    - body: "Every connection that uses {name} fails immediately, including services whose env vars hold its connection string. This can't be undone."
  - The credential is deleted only on confirm. Cancel sends no `deleteDatabaseCredential`.
  - Copy in en and zh.
  - Add a test that clicking Delete shows the dialog and sends nothing until confirmed.
  - The default credential stays undeletable (disabled, as today).
- **Blast radius:** one button in one panel; no shared helper.
- **Unverified:**
  - Render's own dashboard confirmation wording for deleting a credential.
  - Whether the credentials list renders empty before the first rotation. I saw this once, in a lazily mounted section, and didn't reproduce it; it isn't part of this item.
- **Dedupe:**
  - `grep -rlE "deleteCredential|accessCredentialDelete" .pm` finds only w5/m265 (done). It built rotation, and its DoD exercised retiring the old credential through REST, not a dashboard confirmation.
  - Not deploy lag: on origin/main, `access-control-panel.tsx:175` is unchanged. w2/m307 added a `ConfirmDialog` only for the pooler.
- **DoD (live):**
  - On an owned Free Postgres with two credentials, clicking Delete on the non-default one opens a confirmation naming it, in en and zh.
  - Cancel leaves the credential in place: the REST credentials list is unchanged, and the old URL still connects.
  - Confirm deletes it, and the old URL then fails authentication.
