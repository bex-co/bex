# 571 — A multi-instance web service's held image change moves all traffic to its first new instance, so capacity drops until the rest roll

Why: on Render a zero-downtime deploy brings up the new instances and then moves traffic to them. With w4/m320 a bex web image change is held until promotion and then routed early from its first Ready pod. On a service with N > 1 instances the Deployment's default `maxSurge` (25%) starts only one new pod while the hold keeps the old ones, so for a while one new instance takes every request while N old ones sit idle.

- **Source / severity / estimate:** w4/m320 t005 blast-radius audit, `/loopx w4` 2026-11-11. The same applies to w4/428 port changes, which use the same early promotion. **Minor** (paid multi-instance plans only; no error, reduced capacity during the deploy). ~1h.
- **Where:** `promoteEarly` and `templatePodReady` (`lego/operator/internal/controller/image_network.go`) promote at the first Ready pod of the written template. `projectDeployment` (`deployment_projection.go`) leaves the rolling-update strategy at its defaults.
- **Fix options:**
  - (a) While a release is held, set `maxSurge` to 100% so all N new pods start, and promote when every one is Ready.
  - (b) Promote at the first pod as today, but lift the hold one pod at a time. This is closer to the current code, but it doesn't match Render's sequence.
  - Prefer (a). Check the workspace compute quota: a 2N surge must not trip the quota block (`rolloutQuotaBlockMessage`).
- **Tests:** with replicas 3, a held image change starts 3 new pods, the Services stay pinned to the serving revision until all 3 are Ready, then move in one write.
- **DoD (live):** a paid 2-instance image web service shows both new instances in `GET …/instances` before the first response from the new version, and no response error during the deploy.
- **Dedupe:** w4/m320 (single-instance hold and promotion, in `blocked/` for its live replay) and w4/428 (port change, done). No open item covers multi-instance capacity.
