# GraphQL `renameEnvironment` accepts an EMPTY or whitespace-only environment name (REST PATCH + MCP reject it) — `Service.Rename` omits the `validateEnvironmentName` call its siblings make

Why: the environment-name non-empty check lives in `validateEnvironmentName` and is called by `CreateWithACL` (all create surfaces) and `Update` (REST PATCH + MCP `update_environment`), but NOT by the standalone `Service.Rename` that GraphQL `renameEnvironment` routes to — so a GraphQL caller can rename an environment to a blank name. A nameless environment renders blank in the dashboard environment switcher/lists and diverges from Render (which requires a name). The helper already exists; the fix is one call in `Rename`.

Source: live QA 2026-09-07, `$qa-find-bugs w4` pass 34 (write-path validation-layer fuzzing; environments-package analog of `w4/057`).

## Symptom (reproduced live on prod, authenticated GraphQL past Cloudflare)

| operation | result |
| --- | --- |
| `renameEnvironment(id:<valid env>, name:"")` | ❌ **OK** — renames to `name:""` (read-back `environment(id){name}` → `""`) |
| `renameEnvironment(id:<valid env>, name:"   ")` | ❌ **OK** — renames to `"   "` (whitespace-only, not trimmed; read-back confirmed) |
| **CONTROL (same resource, correct):** `createEnvironment(name:"")` / `"   "` | ✅ `bad request` (create validates on GraphQL) |

So the gap is the **rename verb specifically**, not the environment resource. Test project (hosting the env) was deleted, cascading the env; residual check returned zero qa-/blank projects.

Durable probe: create a valid env, then `{"query":"mutation($id:String!,$n:String!){ renameEnvironment(id:$id, name:$n){ id name } }","variables":{"id":"env-…","n":""}}` → `{"data":{"renameEnvironment":{"id":"env-…","name":""}}}` (HTTP 200, no error).

## Root cause (code-verified on `main` HEAD `568b2348a` — not deploy-lag)

- GraphQL `renameEnvironment` (`lego/backend/internal/environments/graphql.go:128`, `gqlutil.ArgMutation(environmentGQLType, "name", s.Rename)`) → `Service.Rename`.
- `Service.Rename` (`environments/service.go:618-631`) authorizes, fetches, then calls `s.Store.RenameEnvironment(ctx, id, name)` at `:626` with the **raw** name — no `validateEnvironmentName`, no trim.
- The helper `validateEnvironmentName` (`environments/service.go:1081-1087`: `name = strings.TrimSpace(name); if name == "" { return "", core.ErrBadRequest }`) **is** called by the siblings `CreateWithACL` (`service.go:526`) and `Update` (`service.go:651`). `Rename` is the lone omission.
- Surface wiring (grepped): create on all three surfaces routes through `CreateWithACL` (`rest.go:174`, `mcp.go:103`, `graphql.go:121`) → validates. REST rename is `PATCH /v1/environments/{id}` → `s.Update` (`rest.go:199`) → validates. MCP rename folds into `update_environment` → `s.Update` (`mcp.go:112`) → validates. **Only GraphQL `renameEnvironment` → `s.Rename` bypasses.**

## Target behavior / fix

Make `Service.Rename` (`environments/service.go:618`) validate the name exactly as its siblings do — at the top, before the store write:

```go
name, err := validateEnvironmentName(name)
if err != nil {
    return EnvironmentView{}, err
}
```

(then use the trimmed `name`). Reuses the existing helper (`service.go:1081`) and mirrors `Update` (`:651`) / `CreateWithACL` (`:526`). Result: `renameEnvironment` rejects empty/whitespace on GraphQL, consistent with REST PATCH, MCP `update_environment`, `createEnvironment`, and Render.

## Blast radius (exhaustive, grepped)

Environment name validation across surfaces:

- **create:** `CreateWithACL` (`rest.go:174` / `mcp.go:103` / `graphql.go:121`) — all guarded.
- **rename:** REST PATCH → `Update` (`rest.go:199`) guarded; MCP `update_environment` → `Update` (`mcp.go:112`) guarded; **GraphQL `renameEnvironment` → `Rename` (`graphql.go:128` → `service.go:618`) UNGUARDED** (the one bug).

The fix is a single call added to the one method `Service.Rename`; it changes exactly one entrypoint's behavior and cannot regress the others (they use `Update`/`CreateWithACL`). Regression test: GraphQL `renameEnvironment` now rejects empty + whitespace; REST PATCH / MCP `update_environment` / `createEnvironment` still reject (unchanged); a valid rename still succeeds.

## Adjacent classes

- valid name → renamed (unchanged).
- empty / whitespace name → **bad-request** (the fix; currently accepted on GraphQL `renameEnvironment`).
- duplicate name → store conflict via `store.MapError` (unchanged).
- unknown / forbidden env id → not-found / forbidden via `requireEnvironment` (unchanged).

## Render parity

Render requires a non-empty environment name; bex REST PATCH + MCP match, GraphQL `renameEnvironment` diverges (accepts empty/whitespace). Parity task applies (the fix brings the last surface into agreement).

## Severity

**Minor** — no data loss, no blocked journey; but a GraphQL caller can rename an environment to blank/whitespace, which renders as an empty entry in the dashboard environment switcher/lists, is a cross-surface inconsistency (REST PATCH + MCP reject, GraphQL accepts), and diverges from the sibling create verb and from Render.

## Unverified this run

- REST `PATCH /v1/environments/{id}` and MCP `update_environment` empty-name rejection are **code-verified** (both route to `Update` → `validateEnvironmentName`) but were not live-probed.
- GraphQL `renameEnvironment` empty + whitespace were **live-verified**.
- `Service.Create` (`service.go:508`) is un-validated but has **no public-surface caller** (all creates use `CreateWithACL`) — not exploitable; noted only so the fix doesn't accidentally rely on it.
