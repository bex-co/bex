# A port-changing rollout still drops 1–2 requests at promotion (a 502, or the activator's "service not ready"), after w4/428

Why: w4/428 aimed at no window without a ready endpoint on a port-changing deploy. Live, each port change still fails one or two requests at the cutover, so a `PORT` change is not zero-downtime as ADR004 promises.

Severity: minor (port-changing deploys only; same-port deploys stay clean, per m243 t012's live check). Estimate: ~45m. Source: live `/qa-find-bugs w4` loop run 92e2, 2026-10-28 UTC (`muse.env`, workspace `tea-daif693dqjvc73e7as3g`, production pin `dfbb006c1bf2`, which contains w4/428 `71e1aab38`).

## Evidence

Fixture: Free web service `qa-20261028-92e2-port` (`srv-dbgoec4bk5uc73bjujqg`, `docker.io/mendhak/http-https-echo:latest`, env `HTTP_PORT` = `PORT`), deleted afterwards. Polled `GET /x` every 0.25 s (`curl -m 5`) while the Environment page did "Save and deploy" of both variables:

| Change | Requests | Failures | Deploy |
| --- | --- | --- | --- |
| 8080 → 9090, saved 05:25:23Z | 156 | **1 × `502`** at 05:25:49 (0.54 s; the next request took 2.8 s) | `config_change` `live` 05:26:00Z, `openPorts [9090]` |
| 9090 → 8080, saved 05:28:16Z | 136 | **2 × `503`** at 05:28:32–33: `content-type: application/json`, `retry-after: 5`, body `{"error":"service not ready","retryAfter":5}` (the activator's answer) | started 05:28:30Z, `live` 05:28:47Z, `openPorts [8080]` |

The two failure shapes point at two moments:

- The `503` is the activator, reached through the platform-host fallback route (m235 t008, `1f215572f`). For about a second, Traefik had no app route for the host, probably while `promotePortChangeEarly` rewrote the Ingress backend port. The activator then answered "service not ready" for an App that was running and rolling, instead of proxying to it.
- The `502` is consistent with a request routed to a Service port that no ready pod yet listens on, or to a drained pod, in the instant the Services and the Ingress move to the new network.

## Steps

1. With cluster access, replay both directions while watching the Ingress object, the two Services' selectors and ports, and the EndpointSlices. Record the order in which `promotePortChangeEarly` (`app_controller.go`) writes them.
2. Order the writes so a ready backend exists for the host at every instant. For example, write the Services (new port + new revision) and wait for their EndpointSlices to carry a ready address before repointing the Ingress. Never delete and recreate the Ingress rule.
3. Make the activator proxy a held or fallback request for an App that is Running or Deploying with a serving release, instead of answering `service not ready`. Alternatively, make sure the fallback route cannot match a host whose app route is merely being updated.
4. Live check: the 0.25 s poll above, in both directions, gives zero non-`200` answers.

## Unverified

- Which object write opens each gap. The table above is externally observed only.
- Whether a Starter (non-Free) service, which has no activator path, shows the `502` alone.
