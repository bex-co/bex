## Objective

A resource must never be in the state observed live: dropped from its blueprint's `resources[]` while still holding that blueprint's durable ownership claim. Today the claim is released **only** by disconnect, so any resource a manifest stops declaring becomes an orphan that is also locked — managed by nobody, and adoptable by no other blueprint without a confirmation phrase naming a blueprint that disclaims it.

## Context

### The state, observed

After the takeover in [t001](t001.md), `static-site` was gone from the blueprint's resource list:

```graphql
{ blueprint(id:"blp-dan9g8rs0ils73bgp500", ownerId:"tea-…") { name path resources { id name type } } }
→ { "name":"qa-20260921-bpB", "path":"examples/cron-demo/render.yaml",
    "resources":[{"id":"srv-daohon92dbts73fi2njg","name":"cron-demo","type":"cron_job"}] }
```

…while the very same blueprint still held its claim, as the dashboard's own preview reported when asked to connect the static-site manifest:

> **Blueprint file has errors**
> service "static-site" is managed by blueprint `blp-dan9g8rs0ils73bgp500`; retry with confirm="takeover blueprint blp-dan9g8rs0ils73bgp500" to transfer ownership to this blueprint

Both statements are about the same blueprint id at the same moment: "I do not manage it" and "I manage it".

The escape hatch works and is the documented one — after `disconnectBlueprint(blp-dan9…)`, the same preview came back clean:

```graphql
{ blueprintPreview(ownerId:"tea-…", repo:"https://github.com/bex-co/bex", branch:"main",
                   path:"examples/static-site/render.yaml") { found validation { valid errors } } }
→ { "found":true, "validation":{ "valid":true, "errors":[] } }
```

But disconnecting the *surviving* blueprint to free a resource the *destroyed* one left behind is not a workflow anyone would find.

### Mechanism — the two sides are computed from different sources

- **`resources[]` is derived from the current manifest.** `apps/blueprint.go:1404` `resolveBlueprintResourcesFromIR(ctx, b, ir)` walks `ir.Resources` — what the manifest declares — and resolves each to a live object. Anything the manifest stops declaring cannot appear, by construction.
- **The claim is durable and released in exactly one place.** `store/blueprint_resource_claims.go:73` `ReleaseBlueprintResourceClaims(tenantID, blueprintID)` drops every claim held by a blueprint; `grep` finds one non-test call site, `apps/blueprint.go:1226`, inside `DisconnectBlueprint`. There is no per-resource release, and nothing runs at sync time.

So the divergence is structural, not a race: the two surfaces answer different questions and only disconnect reconciles them.

### This violates a shipped milestone's DoD

`w8/m23`'s definition of done reads: _"that resource records A as its managing blueprint (**visible on the blueprint's `resources[]`** and survivable across syncs)"_. Half of that holds. The claim survives syncs; the visibility does not. `blueprint_ownership.go:18-29` is explicit that "Disconnect clears the claim and marker" — which was written for the disconnect case and silently became the only case.

### Reach

This is not limited to the takeover path. Any sync that drops a resource — the ordinary IaC edit described in [`w4/119`](../119.md), including a rename, which is "orphan the old name, create the new one" — leaves the same locked orphan. `w4/119` says the orphan is "tracked by nothing"; the accurate statement is stronger: it is tracked by nothing and *claimed by something*.

## Steps

1. At the end of a successful sync, diff the blueprint's claim set against the resources the applied IR actually managed, and release the claims for the difference. The claim table already has the right shape (`UNIQUE(tenant, kind, name)`), and both sides are in hand at that point.
2. Do the same on a confirmed blueprint takeover (t001 step 2): the destroyed blueprint's claims must not survive it.
3. Release only the claim. The resource keeps running — that is deliberate and stays (`w4/119`: "Not deleting it is right").
4. Decide whether a released claim should be observable. At minimum the detached ids belong in `SyncBlueprintResult`, which is also `w4/119`'s ask — coordinate so the two do not implement it twice.
5. Check the interaction with `w8/m39`/`w8/m40` fencing: the release must happen under the same admitted `(generation, runID)` claim as the rest of the apply, so a retired worker cannot release claims a successor just took.

## Acceptance criteria

- [ ] After a sync that drops a declared resource, `blueprintPreview` of a manifest declaring that resource reports **no** ownership conflict.
- [ ] For any live blueprint, the set of resources holding its claim equals the set in its `resources[]` — asserted directly in a test, not inferred from the preview.
- [ ] The dropped resource is still running and still in `services(ownerId:)` — the release frees the claim and nothing else.
- [ ] A confirmed takeover (t001) leaves no claim behind from the blueprint it replaced.
- [ ] Release happens under the admitted execution claim; a fenced run cannot release.

## Out of scope

- Telling the user a resource was detached — that is `w4/119`'s plan-verb work; this task only stops the claim from outliving the management.
- Deleting detached resources.
