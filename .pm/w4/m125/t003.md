## Objective

A service, database or Key Value that a blueprint manages should say so on its own read. Today the ownership claim is invisible on every surface: the only way to learn which blueprint holds a resource is to attempt a conflicting apply and read the error.

## Context

`GET /v1/services/srv-daohokp2dbts73fi2nh0` on a blueprint-managed static site returns 35 fields — `id`, `immutableName`, `slug`, `type`, `suspended`, `owner`, `serviceDetails`, `repo`, `branch`, `autoDeploy`, `autoDeployTrigger`, `pushDeliveryMethod`, … — and nothing about the blueprint that created and claims it. GraphQL agrees: introspecting `Service` and filtering for `blue|print|manag|owner` returns exactly one field, `ownerId`, which is the *workspace*.

The claim itself is real and durable — `store/blueprint_resource_claims.go`, `UNIQUE(tenant, kind, name)`, mirrored by the `core.LabelBlueprint` label on the CR (`apps/blueprint_ownership.go:18-29`). `blueprintOwnershipConflicts` (`:62-120`) reads it to build the refusal. So the data is one lookup away from every resource read; it is simply never projected.

The consequence is a diagnostic dead end. A user whose blueprint sync is refused with _`service "X" is managed by blueprint blp-…`_ can look up that blueprint id — and, after t002 or in the `w4/119` orphan case, find a blueprint whose `resources[]` does not mention X. Nothing on X points back. With t002 that state becomes unreachable, but the read gap is worth closing on its own: "which blueprint owns this?" is an ordinary question about an IaC-managed resource, and the answer already exists in the database.

Render has no counterpart field (its Blueprint model does not enforce ownership at all — ADR018 records bex's enforcement as a deliberate documented divergence), so this is a **bex extension** and the parity task should label it as one, the way `pushDeliveryMethod` is labeled in ADR018's parity ledger.

## Steps

1. Project the claim (falling back to the CR label, matching `ownerOf` in `blueprint_ownership.go:73-80`) onto the by-id reads for service, database and Key Value.
2. Decide list-vs-single deliberately and write the decision at the site — `w4/117`'s survey found `Service.pushDeliveryMethod` is single-read-only *on purpose* because it costs a GitHub round-trip. A claim lookup is a cheap indexed read, so including it in lists is defensible; either way, say which and why, so a future single-vs-list diff does not file it as a divergence.
3. Mirror it on GraphQL and MCP, and decide whether the dashboard's service settings page shows "Managed by Blueprint <name>" with a link.
4. Name the field for what it is — the blueprint that *claims* the resource.

## Acceptance criteria

- [ ] A blueprint-managed service reports its managing blueprint id on REST by-id, GraphQL `service(id:)` and the MCP service read; an unmanaged one reports its absence unambiguously.
- [ ] The same holds for `database` and `keyValue`.
- [ ] The value agrees with the claim table for every resource in a workspace with at least one blueprint — the same assertion t002 makes, read from the API instead of the store.
- [ ] List-vs-single behavior is deliberate and documented at the site.
