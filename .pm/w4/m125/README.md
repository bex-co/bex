## Definition of done

Each bullet is a probe that was actually run in the hunt below, re-run against the fix:

- **Connecting an already-connected repo+branch does not silently replace a blueprint.** With blueprint `A` connected to `bex-co/bex` @ `main` from `examples/static-site/render.yaml`, calling `createBlueprint(repo: bex-co/bex, branch: main, path: examples/cron-demo/render.yaml, name: B)` no longer returns `{id: <A's id>, name: "B", status: "in_sync"}`. It returns a coded conflict naming the existing blueprint and the server-issued confirmation phrase — the same shape `BLUEPRINT_RESOURCE_CONFLICT` uses — identical on REST `POST /v1/blueprints`, GraphQL `createBlueprint`, and MCP `create_blueprint`, and surfaced by `blueprintPreview` so `/blueprints/new` shows it before Deploy. Passing the confirmation proceeds and the takeover is recorded in sync history.
- **`blueprints(ownerId:)` never loses a row to a create it did not name.** After the refused call above, the list still contains `A` with `path: examples/static-site/render.yaml` and its own manifest — not a row renamed to `B` pointing at a different file.
- **A resource a blueprint no longer manages holds no claim from it.** After a sync (or a confirmed takeover) drops `static-site` from what blueprint `X` manages, `blueprintPreview` of a manifest declaring `static-site` reports **no** ownership conflict, and `blueprint(id: X).resources` and the claim table agree: neither names it. Today the claim survives and the list does not, which is precisely the state `w8/m23`'s DoD ruled out ("that resource records A as its managing blueprint, **visible on the blueprint's `resources[]`**").
- **The owning blueprint is readable on the resource.** `GET /v1/services/{id}`, GraphQL `service(id:)`, and MCP's service read each report the managing blueprint id (or its absence) for a blueprint-managed service, and the same for `database` and `keyValue`. Today no read surface carries it: the only way to learn who holds a claim is to trigger the conflict.
- **Tests fail without the fix.** A test asserting a second `createBlueprint` for the same `(tenant, repo, branch)` is refused, and a test asserting the claim set equals `resources[]` after a resource is dropped, both fail against the pre-fix code.

## Source + Goal linkage

- **Source:** live `/qa-find-bugs` 2026-09-21 pass 133 (w4-targeted, `muse.env` credentials), journey 13. Full capture and mechanism in [t001](t001.md) / [t002](t002.md). In one sentence: `AdmitBlueprintCreate` is an `INSERT … ON CONFLICT (tenant_id, repo, branch) DO UPDATE SET name = EXCLUDED.name, path = EXCLUDED.path, auto_sync = …, manifest = …` (`store/blueprint_lifecycle.go:186-201`), and `CreateBlueprint` (`apps/blueprint.go:689`) calls it with no check that the row already exists — so the second connect is a wholesale overwrite reported as a successful create. Live, two creates against the same repo+branch with different paths returned the **same** id, left one row named after the second, and left `static-site` running, dropped from `resources[]`, and still holding the first blueprint's claim (the dashboard's own preview said so: _`service "static-site" is managed by blueprint blp-dan9g8rs0ils73bgp500; retry with confirm="takeover blueprint blp-dan9g8rs0ils73bgp500"`_ — while `blueprint(id: blp-dan9…).resources` listed only `cron-demo`). Fixtures deleted; workspace restored to its 5 pre-existing services.
- **Goal linkage:** tenant safety and honesty on the Blueprint surface — the same ADR049 fail-closed principle, and the same lineage, as [`w8/m23`](../../w8/done/m23/README.md), which shipped exactly this guarantee one level down. ADR018's Blueprint row records bex's refusal-instead-of-clobber as a **deliberate, documented improvement over Render** ("Render warns … without enforcing it — bex refuses with explicit takeover instead of silently clobbering"). That claim is currently true of resources and false of blueprints.
- **Expected outcome:** the IaC surface stops having a verb that destroys a blueprint while reporting success. A monorepo user — the case the `/blueprints/new` help text actively invites ("any .yaml/.yml file works (e.g. `infra/bex/stack.yaml`)") — either gets a clear refusal or a named takeover, and never discovers afterwards that their first stack is unmanaged, unbilled-for-by-anyone, and unadoptable.
- **Why now:** the storage key is `UNIQUE (tenant_id, repo, branch)` (`store/migrations/0016_blueprints.up.sql:14`) and `w8/m21` deliberately made **branch** the read-only identity key with path editable, so one-blueprint-per-repo+branch is settled design — this milestone does not reopen it. What is missing is the one thing the design implies: saying so. It is also cheap right now because the confirmation handshake, the coded-conflict shape, the preview surfacing, and the dashboard's confirm dialog all already exist from `w8/m23`/`w8/m40`; t001 reuses them rather than inventing anything. And it compounds with the already-filed [`w4/119`](../119.md): every orphan that note describes is in fact a *claimed* orphan, so the two silences stack.
- **Render parity task included** because the change adds a coded error and a new read field across REST, GraphQL, MCP and the dashboard's Blueprint create/preview surfaces.
- **DO_NOT_DO constraints honored:** no anti-goal touched; no resource deletion is added anywhere (t002 releases a *claim*, never a resource — orphan survival stays deliberate, per `w4/119`).
