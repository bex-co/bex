## Objective

Lock in the two guarantees with tests that fail against the pre-fix code, and cover the paths that must keep working.

## Context

- The store-level behavior needs a real Postgres test in the shape `w8/m37` used (disposable PG17 matching CI), because the defect lives in an `ON CONFLICT` arm — a fake store cannot express it.
- The claim/`resources[]` agreement in t002 is a property, and is the cheapest thing to assert directly rather than through the preview.

## Steps

1. Store test: two `AdmitBlueprintCreate` calls with the same `(tenant, repo, branch)` and different paths — assert the second is refused (or, post-fix, that the service layer never reaches it without a confirmation), and that the first row's `name`/`path`/`manifest` are unchanged.
2. Service test: `createBlueprint` twice → coded conflict naming the existing blueprint + confirm phrase; with the confirmation → proceeds, and the sync history records the takeover.
3. Regression test for the path that must keep working: create over a **disconnected** row succeeds with no confirmation (`w8/m37`).
4. Property test: after a sync that drops a declared resource, the blueprint's claim set equals its `resources[]`; and the dropped resource is still present in the workspace.
5. Cross-surface test asserting the conflict payload is identical on REST/GraphQL/MCP (one test, three surfaces — the `w6/m99` shape).
6. Fencing test: a retired `(generation, runID)` cannot release claims.

## Acceptance criteria

- [ ] Tests 1, 2 and 4 fail against pre-fix code and pass after.
- [ ] The disconnected-row create path is covered and unchanged.
- [ ] No tautological or snapshot-everything assertions; each names the behavior it protects.

## Out of scope
