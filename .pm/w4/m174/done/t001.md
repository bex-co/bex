## Finding (2026-10-05)

- **Mechanism:** Alloy v1.11.2 `internal/component/loki/source/kubernetes/kubetail/tailer.go:277`: `if !entryTimestamp.After(lastReadTime) { continue }`. The tailer skips any line not stamped strictly after the last line it shipped.
- **Ground truth:** a throwaway kind cluster (containerd), the DoD command as 20 Jobs, then `/var/log/pods/default_fast-*/app/0.log`. In 4 of 20 files a line was written after a line stamped later, e.g. `…45.158697625Z stdout F 100%-x` followed by `…45.158672875Z stderr F error: GAMMA-x three`. containerd copies each stream on its own goroutine and stamps the line at read time, so file order is not timestamp order. The kubelet API serves file order, and the tailer discards the stderr line. In 1 run the stderr line came first but was stamped after `ALPHA`, which would drop the stdout line instead. That is rarer, which matches production's stdout-always-complete pattern.
- **Not compared against Loki on a live stack** (the shared CAPD cluster was down). The source line plus the CRI files fully explain the 3/6 production loss. t002's file-tail fix is therefore tailing-mode related, as planned.
