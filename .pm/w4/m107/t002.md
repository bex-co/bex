## Objective

An agent reading logs over MCP has the same blindness the dashboard has: `list_logs` returns entries with no indication that the result was capped and no cursor to continue. Give it the envelope t001 defines, so all three surfaces answer the same question the same way.

## Context

- `logs/mcp.go:83` — `Logs []LogEntry \`json:"logs"\`` is the whole result struct; there is no `hasMore`.
- The agent-facing consequence is worse than the dashboard's: an agent asked to "check yesterday's errors" gets the newest 100 lines, sees no error, and answers confidently. Nothing in the response contradicts it.
- `w4/086` established that MCP's tool **set** matches REST/GraphQL; this is the response-shape half that audit explicitly did not cover.

## Steps

1. Add `hasMore` and the two cursors to the result struct, reusing t001's computation.
2. Describe them in the tool's `jsonschema` annotations so an agent knows a capped result is capped and how to continue — the description is the only documentation an agent reads.
3. Check the sibling log tools for the same omission (`get_postgres_logs`, `get_key_value_logs`) and either fix them here or record why they differ.

## Files

- `lego/backend/internal/logs/mcp.go`
- `lego/backend/internal/postgres/mcp.go`, `lego/backend/internal/keyvalue/mcp.go` (only if step 3 finds the same gap)

## Acceptance criteria

- [ ] `list_logs` returns `hasMore` and both cursors, with values identical to REST for the same query.
- [ ] The tool description tells an agent what to do when `hasMore` is true.
- [ ] Step 3's finding is written down either way — fixed, or recorded as a deliberate difference with the reason.

## Out of scope

- Adding a log-streaming/tail tool to MCP. Live tail stays a dashboard/REST concern.
