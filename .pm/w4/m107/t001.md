## Objective

The GraphQL `logs` field returns a bare `[LogEntry]`, so its callers — the dashboard above all — cannot tell a complete result from the newest 100 of many, and have no cursor to ask for the next page. Give it the same `{hasMore, nextStartTime, nextEndTime, logs}` envelope REST already returns, so the shape is one contract across surfaces rather than two.

## Context

- `logs/graphql.go:83` — `"logs": &graphql.Field{…}`, today returning a list type. Introspection on production confirms `{"kind":"LIST","ofType":{"kind":"OBJECT","name":"LogEntry"}}`.
- `logs/render.go:59-67` — the REST envelope and its doc comment; `:100-121` computes `NextStartTime` (newest line), `NextEndTime`, and `HasMore = limit > 0 && int64(len(entries)) >= limit`. **Reuse this computation; do not re-derive it.**
- `logs/service.go:111-117` — `maxLogLimit = 100`, `defaultLogTail = 100`, with the comment recording that Render caps at 100 and bex matches. Unchanged by this task.
- The field already accepts `startTime`, `endTime`, `limit` and `direction` (verified by introspection), so the inputs for paging exist; only the outputs are missing.

## Steps

1. Introduce the envelope object type (name it after the REST shape, not a new vocabulary) and change the `logs` field's return type to it.
2. Populate it from the same helper REST uses, so `hasMore` cannot drift between surfaces.
3. Establish what a **second** page actually requires: call the field with the returned `nextEndTime` as the next `endTime` and confirm it yields strictly older entries with no gap and no duplicate boundary line. Record the answer in the task — the milestone's cursors are only trustworthy once this is shown.
4. Update `dashboard/src/graphql/definitions.ts` via the offline codegen path in `dashboard/CLAUDE.md` (`SCHEMA_DUMP_PATH` → `SCHEMA_JSON=… yarn codegen`), splicing only the logs hunk.

## Files

- `lego/backend/internal/logs/graphql.go`
- `lego/backend/internal/logs/render.go` (extract the envelope computation if it is not already reusable)
- `dashboard/src/graphql/definitions.ts` (generated hunk only)

## Acceptance criteria

- [ ] `{ logs(...) { hasMore nextStartTime nextEndTime logs { timestamp } } }` answers on production-shaped data.
- [ ] `hasMore` is true when the result hit the cap and false when it did not — asserted both ways, not just the true case.
- [ ] Feeding `nextEndTime` back as `endTime` returns strictly older entries; the boundary line is neither duplicated nor skipped.
- [ ] REST's response is unchanged by this task. The cursor semantics are t008's change, and this task reuses that fixed helper.

## Out of scope

- Raising `maxLogLimit`. The cap is deliberate Render parity.
- The MCP envelope (t002) and the viewer's paging (t003).
