## Objective

Render documents log paging as "Provide the `nextStartTime` and `nextEndTime` timestamps as the `startTime` and `endTime` query parameters to fetch the next page of logs". That text is in `render-public-api-1.json` `GET /logs` and in `render-mcp-server`'s `list_logs` description. The official Render CLI's log view does exactly that on scroll: `render-oss/cli` `pkg/tui/views/logview.go:196-199` passes the stored cursors straight into the next request's `StartTime`/`EndTime` (`pkg/tui/logs.go:164`, `:199-200`; default branch, fetched 2026-09-14).

bex's REST envelope instead returns the current page's own bounds: `nextStartTime` is the newest line and `nextEndTime` the oldest (`lego/backend/internal/logs/render.go:105-108`). Following them asks for a start after the end, so page 2 is always `400 bad request: startTime must be before endTime`, in both directions.

Make the cursors name the next page's window for the query's direction, so a Render client can page to the end of its range.

## Context

- **Live probes.** 2026-09-14, w1 `/qa-find-bugs` pass 27, production.
  - Fixture: `qa-20260914-logs` (`srv-dak4bta6m8ac739r63j0`), a free web service built from `examples/hello-python` with Docker Command `python -u -m http.server $PORT`, created and deleted in the run.
  - The calls can be re-run on any service with more than 5 lines in the window:

  ```text
  GET /v1/logs?resource=<srv>&startTime=2026-09-14T19:08:00Z&endTime=2026-09-14T19:12:00Z&limit=5        (backward, the default)
  → 200, 5 rows 19:11:55.259678931Z … 19:11:56.657668582Z, hasMore:true,
    nextStartTime:"2026-09-14T19:11:56.657668582Z", nextEndTime:"2026-09-14T19:11:55.259678931Z"
  GET /v1/logs?resource=<srv>&startTime=2026-09-14T19:11:56.657668582Z&endTime=2026-09-14T19:11:55.259678931Z&limit=5
  → 400 {"error":"bad request: startTime must be before endTime","id":"bad_request",…}

  GET …&direction=forward&limit=5
  → 200, 5 rows 19:09:07.475354674Z … 19:09:13.367369047Z, hasMore:true,
    nextStartTime:"2026-09-14T19:09:13.367369047Z", nextEndTime:"2026-09-14T19:09:07.475354674Z"
  following them with direction=forward → 400, same message
  ```

- **Control.** A hand-built backward page 2 (the original `startTime`, with `endTime` set to page 1's oldest timestamp) returned 5 strictly older rows (19:11:45.942049253Z … 19:11:55.25963586Z), none repeated from page 1. The store already pages correctly when given the right window, and `endTime` behaved as exclusive at the boundary.
- **One caller.** `toRenderLogList(entries, limit, since, end)` (`render.go:100-121`) is called only from REST (`rest.go:128`). It already receives the query's resolved `since`/`end`, but not `direction`.
- **Weak test.** The only test, `TestRESTLogsEnvelopeAndFilters` (`logs_test.go:260-289`), asserts the cursors are non-empty, never that following them works.
- **ADR wording.** `docs/ADR010-observability.md:142` records the envelope as verified against Render's shape: the field names, not their semantics.
- **Why first.** t001 (GraphQL) and t002 (MCP) reuse this helper, so without this task the bug ships to three surfaces.

## Steps

1. **Set the cursors by direction.** Pass `direction` into `toRenderLogList`.
   - Backward (the default): `nextStartTime` is the query's resolved `startTime`, and `nextEndTime` is the page's oldest timestamp.
   - Forward: `nextStartTime` is the page's newest timestamp, and `nextEndTime` is the query's resolved `endTime`.
   - Keep the empty-page branch (the query's own window) and `hasMore` unchanged.
2. **Settle the boundary rule** so the boundary line is neither repeated nor skipped.
   - Confirm `startTime` and `endTime` inclusivity on both read paths: Loki (`loki.go`) and pod logs (`service.go` / `podlogs.go`).
   - If a forward cursor would repeat the newest line, advance it past that line or filter the exact boundary entry.
   - Entries that share the boundary timestamp (fan-out across instances) must not lose their siblings.
3. **Test a full chain.** Walk pages to `hasMore:false` in both directions and assert the union equals the unpaged result for the same window.
4. **Fix the docs.** Correct the doc comment at `render.go:59-61` and `ADR010-observability.md:142` to state what the cursors mean.
