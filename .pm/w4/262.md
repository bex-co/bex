# 262 — A live deploy detail stays Live after a newer release replaces it

Why: a tenant watching a deployment should see when it stops serving and be able to restore that previous release without discovering that a reload repairs the page.

- **Severity:** major: the detail page persistently misstates the selected deployment and hides its Rollback action. Hosting continued normally; a fresh page is a workaround.
- **Estimate:** 55m: detail refresh policy and cached refresh state 15m, caller/sibling audit 10m, behavioral regression 20m, Simplify and live acceptance 10m. One bounded inbox fix.
- **Source:** user-requested functional `qa-find-bugs w4` loop, pass a239, 2026-10-11/12 UTC, muse QA profile, workspace `tea-d98210cbbpdc73dcrkvg`. Research HEAD `55d03259b`. Filing only.
- **Goal linkage:** [ADR004 deployment](../../docs/ADR004-app-deployment.md), [ADR018 parity](../../docs/ADR018-render-parity.md), [ADR008 hosting vision](../../docs/ADR008-vision.md): truthful deployment state and usable recovery on the existing hosting surface.

A separate fresh B detail says **Deactivated**, Updated **00:07:19.060614Z**, adds the Deactivated timeline step, and exposes **Roll back to 5b82d6e**. REST and GraphQL both return Deactivated.

This is two real release transitions, with the second observation starting from a fresh selected detail. Live-to-Deactivated is a real later transition even though Live closes the rollout. No Rollback mutation was dispatched. Public HTTP remained v2 after C; 30 successful v2 samples in the separate HTTP artifact started **after** B's handover, so they establish the new content rather than zero-downtime continuity.

## Root cause, consumers and proposed fix

- `dashboard/src/features/deploys/hooks/use-deploy.ts:69–97` starts a 3-second query, then calls `stopPolling()` as soon as `isTerminalDeployStatus(status)` is true. The terminal vocabulary includes **live** at `lib/deploy-status.ts:11–23`. Live closes the rollout but the record can subsequently become Deactivated. `hooks/__tests__/use-deploy.test.ts:61–74` currently asserts stopping at Live.
- Actual installed/pinned **Apollo 4.1.3**: `node_modules/@apollo/client/core/ObservableQuery.js:707–710` sets `pollInterval=0`; `:844–904` cancels and clears its poll timer. This is a stopped detail reader, not a status-label mapping error.
- The **one production useDeploy caller**, `components/deploy-detail-page.tsx:39`, passes that record into **DeployHeader** (`:102–103`), **DeployActions** (`:106–112`) and **DeployTimeline** (`:117`). Header renders `updatedAt` and `status` at `components/deploy-header.tsx:65,89–92`.
- `components/deploy-actions.tsx:93–94` uses `isRollbackableDeployStatus`, which correctly accepts **deactivated only** at `lib/deploy-status.ts:47–48`. Refreshing the selected record clears this predicate; widening it to Live would regress w4/051.
- The timeline is traced separately: `components/deploy-timeline.tsx:63` calls `buildDeployTimeline(deploy, events)`; `lib/deploy-timeline.ts:55–73` adds the later Deactivated step from **that deploy's status and updatedAt**. Its matching-event query does not repair a stale deploy prop.
- Passing control: `hooks/use-latest-deploy.ts:30–46` reads **Deploys(limit:1)** with `useConvergingPoll`, which retains the **30s baseline** at `common/lib/polling.ts:11,47–59`. The header sees the new C row; it does not fetch the old B row. Apollo's shared cache config, `common/apollo/cache.ts`, has no Deploy override.
- **Target:** keep a visible selected **Live** record refreshing at the existing baseline (at most 30 seconds); continue fast refresh while rollout phases change. Stop on genuinely settled Deactivated/failed records. Preserve hidden-tab suppression and **w4/m198's 12-minute bound for a cancelled deploy whose pre-deploy step can still finish**, including its timer cleanup. Keep the global terminal-status vocabulary and rollback eligibility unchanged.

Before data resolves, keep the existing independently mounted header/timeline/log skeletons. With cached ready data, a refresh must preserve the ready layout and log/filter state. Audit `deploy-detail-page.tsx:85–93`: it currently returns the whole-page error state even with a cached deploy; added Live refresh should retain the last good detail and expose refresh failure inline instead of unmounting it. This is a source-identified implementation boundary, not another live failure claimed by this hunt.

## Shared-code audit and adjacent cases

A bounded audit is part of the 55m work. Exhaustive production census: **one useDeploy caller**, **two DeployDetailPage route consumers** (`routes/services.$serviceId.deploys.$deployId.tsx:29`, `routes/static.$serviceId.deploys.$deployId.tsx:24`), and **five isTerminalDeployStatus callers**: use-deploy, use-deploys, use-latest-deploy, lib/deploy-timeline, components/deploys-list-page. Change the selected-detail refresh policy; do not globally redefine Live.

Resource families: web/private/worker/cron use **/services**; static uses **/static**; Postgres and Key Value use separate datastore pages. `common/lib/render-alias.ts` forwards **/web, /pserv, /worker, /cron** plus suffixes to /services; static's canonical route shares the detail component, and its /services entry redirects to /static. No separate product handler is needed for these aliases. Only web-service detail was exercised live here.

Keep null/404 handling in the existing nearest-parent redirect, and preserve initial-error handling for query failures. A forbidden or unauthenticated read remains an error/session outcome, not a fabricated Deactivated record or not-found result. Timeout/5xx on a refresh retains the last good detail with an explicit error and retry. These error branches and source-only sibling families require regression verification; they were not fault-injected live.

Preserve its hidden-tab and parallel-mount guarantees while distinguishing rollout completion from record immutability.

- Anti-goals were re-read; this is an existing deployment-state bug. Latest main and targeted hook history still contain the stopping-at-Live policy; no unshipped fix was found.

[Render's retrieve-deploy API](https://api-docs.render.com/reference/retrieve-deploy) exposes both `live` and `deactivated` plus `updatedAt`. That supports preserving the correct server values. An authenticated Render dashboard's refresh timing was not observed; do not assert it. REST/GraphQL are correct here; no API/MCP contract change is proposed. MCP was not probed in this pass.
