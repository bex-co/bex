# Deleting and re-adding an environment key creates an unsavable draft

Why: replacing a stored variable through the editor's Delete and Add flows should save the unique final key once, rather than submit a batch the API rejects.

- **Severity:** major. The enabled Save cannot complete a valid final draft; the error is honest and the draft remains editable. Stored contents remain unchanged on failure; no data loss is claimed.
- **Estimate:** 55m — shared caller audit 10m, bounded serializer correction 15m, behavioral checks 20m, Simplify/live close 10m.
- **Source:** functional `$qa-find-bugs w4`, 2026-10-10 pass a118, muse.env through the login helper. [ADR013: coherent environment maps](../../docs/ADR013-secrets.md), [ADR006](../../docs/ADR006-bex-api.md), [ADR018](../../docs/ADR018-render-parity.md) and [ADR008](../../docs/ADR008-vision.md).
- **Owned fixtures, now deleted:** group `evg-db5c9kp8p0gs73ep8a8g` and Free image web service `srv-db5c9viuhcdc7389bh8g`, both named `qa-20261010-a118-generated`. No foreign resource was edited or linked.

## Reproduction, controls and target

1. On `/env-groups`, create the owned group with key `QA_A118_GENERATED`, **Generate** enabled and no selected services. Its generated value persists after reload. Link only the owned BusyBox web service. The service's response hashes the received value, matching the group's stored-value hash.
2. On the group's detail page, **Edit**, rename the key to `QA_A118_RENAMED`, leave its value **Unchanged (masked)**, and Save and deploy. This succeeds: revision 1→2, old key absent, new key has exactly the same hash, and the running service receives it. Ordinary opaque rename is a passing control.
3. **Edit → Delete QA_A118_RENAMED → Add variable → Generated secret**. Set the new row's Key to `QA_A118_RENAMED`. There is one nondeleted key, no validation alert and an enabled Save.
4. **Save and deploy**, **23:09:46.365Z**: HTTP200 with GraphQL `patchEnvGroupEnvironment:null` and `bad request: duplicate environment variable operation for "QA_A118_RENAMED"`. UI: **Couldn't save the environment. Your draft is still here.**
5. Cancel, fresh-load, recreate the same draft at **390×844**, then **Save only**, **23:11:08.485Z**. The same duplicate error repeats; the replacement row remains and Save remains enabled.
6. Independent readback after both failures: group revision stays `egr1_AAAAAAAAAAI`; retained value length 44 and SHA-256 `3bf8a5b0f83cb0bffefa2160b9b6b83954925c2fc9375d877e6c0c0ca4df0468`; exactly the same three deploy IDs remain. Public response still has that same hash. Failed generation did not replace the value or dispatch a deploy.
7. Strong control, **23:11:37.731Z**: cancel the failed draft, edit the existing value **in place** to `qa-a118-replacement-control`, and add a generated variable under the distinct new key `QA_A118_FRESH`. One Save only succeeds, revision 2→3, `rolledOut:false`, same three deploy IDs. Fresh reads confirm retained value length 27/hash `ac6ef442545bb33d29425cf8e45275cd7a42a1e6b90e951bd9898e5931b88acf` and a stored generated FRESH value length 44. Both replacement writes and generation work when each target occurs once.
8. Fresh-load at desktop, delete RENAMED and add an ordinary variable of that same name with `qa-a118-readd-literal`. Save remains enabled. Save only at **23:13:10.308Z** repeats the duplicate error. Cancel and independent readback leave revision 3 and the successful control value intact. This is not specific to generation.

**Target:** for the exact generated draft, send one operation `{key:"QA_A118_RENAMED",generateValue:true}`; for the literal draft, one `{key:"QA_A118_RENAMED",value:"qa-a118-readd-literal"}`. A single Save replaces that one stored value, preserves unrelated keys and advances the group revision once. Save only creates no deploy; Save and deploy retains its existing rollout behavior. Keep failed-save draft retention and reject genuinely conflicting direct API batches.

## Cause, consumers and bounded work

- `dashboard/src/features/services/lib/environment-draft.ts:222` validates only nondeleted rows, correctly accepting the unique final draft.
- Its shared `patchRows` at **331–367** independently serializes each row. The original tombstone emits `delete:true` at **345–347**; the new row emits a direct literal/generated write at **361–364**, even when it has that same target. `environmentDraftPatch` at **369–390** maps both into the API array.
- The one production consumer is `service-environment-editor.tsx:337`. Group hook `features/env-groups/hooks/use-env-groups.ts:432–446` forwards the patch in mutation variables without coalescing. The actual wire confirms both operations arrive unchanged.
- `lego/backend/internal/core/environmentpatch.go:180–184` rejects the second direct occurrence of the key. Its upsert at **201** already replaces stored contents; `ApplyEnvVarPatch` admits literal-or-generated values. The passing control exercises that consumer. The API's duplicate guard is correct for its current sparse-operation contract; this fix belongs before the request is sent.

**Shared audit work unit 10m:** `environmentDraftPatch` has **one production call**, and `patchRows` has **two lens calls** (variables/files). There are **two EnvironmentEditor JSX hosts**: service wrapper `service-environment-editor.tsx:124` and group wrapper `env-group-editors.tsx:30`. The service wrapper has **one production mount**, `routes/services.$serviceId.env.tsx:58`, exposed through the ordinary service and static environment route entries. Enumerate web/static/cron/worker/private behavior and the group host; Postgres/Key Value have separate editors. Apply the normalization globally to this shared draft serializer, leaving backend REST/GraphQL/MCP duplicate semantics unchanged.

**15m correction:** when a deleted original-name row is paired with one final **direct** replacement (literal, explicit empty string, generated value or file contents) at that same name, suppress its redundant deletion. Preserve unrelated source-name deletions and opaque `fromKey/fromName` renames. Do not collapse two competing writes, discard the replacement, turn it into deletion only, or weaken final-name validation. Coordinate with m195's edits to this file; its delete-plus-opaque-rename protocol must retain both operations.

**20m checks:** replay the exact group generated and literal drafts, require one successful request and fresh stored replacement, then repeat the in-place and fresh-key controls. Cover the shared service host and file lens as verification work, including empty content and deleting/replacing multiple distinct names. Assert meaningful final stored maps and unchanged unrelated values, not just the shape of a private helper. Preserve ordinary opaque rename and actual duplicate API refusal. Run relevant dashboard checks.

**10m close:** Simplify the change, repeat desktop/mobile live controls, delete owned fixtures and revoke the QA session. Compare UI pending/ready structure if touched; this finding makes no loading-geometry claim.

**Unverified:** service-local delete/re-add writes, file delete/re-add, empty literal, other service types, REST/MCP mutations, i18n, induced failures and quota/concurrency cases. Their shared serializer is source-traced; they are not additional live failures. The group's successful Save-only control was not manually deployed before cleanup; its persisted values and absence of new releases were verified.

## Dedupe, parity and cleanup

Searched open/blocked/done same-name/delete/re-add/generated/duplicate records, scanned 59 open/blocked milestone titles and re-read DO_NOT_DO. [w4/m195](m195/README.md) is **deletion plus opaque rename into that destination**, requiring ordered backend semantics; its scope is explicitly limited to that pair. This finding needs neither source-name reuse nor a rename and proposes client coalescing of a redundant delete plus direct replacement. Keep those two owners separate and coordinate shared-file changes. No applicable anti-goal.
