# w4/182 — Unknown `?type=` renders a hybrid create wizard

Why: a mistyped or legacy `?type=` deep link (e.g. `?type=worker`) should open a usable default wizard, not a form whose heading promises one type while its fields belong to none.

Live 2026-10-04 UTC (`/qa-find-bugs` loop2, muse.env): `/services/new?type=worker` and `?type=bogus123` both render heading "New Web Service" with **no** service-type radio checked and **no** type-specific fields (no Port field). `w4/102` made the heading/total-copy path total but left the form state trusting the raw param: `dashboard/src/features/services/hooks/use-new-service-form.ts:61` (`serviceType: search.type ?? DEFAULT_SERVICE_TYPE`) never applies the `isServiceType` guard that `parseNewServiceSearch` was assumed to guarantee (`dashboard/src/features/services/lib/create-context.ts:20,104-108`; the w4/102 commit message itself notes raw search reaches resolvers despite the validator).

Fix: default the form init through the guard — `isServiceType(search.type) ? search.type : DEFAULT_SERVICE_TYPE` (export the guard from `create-context.ts`) — so an unknown `?type=` opens the plain web-service wizard. Add a route test asserting `?type=bogus` renders the web wizard with the Web radio checked and the Port field present. Submitting the hybrid today would send `type: "worker"` at the API; verify the fixed wizard never emits a non-member type.
