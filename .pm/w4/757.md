# An image-backed service's image pull leaves from its published outbound IPs, as Render's does

Why: Render parity. Once `w21/m616` ships, a private registry that allowlists a service's `outboundIps` serves its builds (w4/741) but refuses the kubelet's pull of an image-backed service's image, which still leaves from whichever tenant node runs the pod.

- **Render (read 2026-11-27):** [dedicated-ips](https://render.com/docs/dedicated-ips), "Do services use dedicated IP sets while building?": "The exception is Docker image pulls, which use Render's shared outbound IP ranges", and "Workspaces without dedicated IPs use Render's default outbound IP ranges". Every bex workspace is such a workspace, so on Render its image pulls leave from the ranges its Outbound tab lists.
- **bex:** the kubelet pulls an image-backed service's image on the tenant node with the release's pull credential ([ADR004](../../docs/ADR004-app-deployment.md), "Which credential"). That is node traffic: [ADR125](../../docs/ADR125-stable-tenant-egress.md) D5's pod-selected egress gateway policy cannot redirect it, and D1 rejected moving all node traffic behind a NAT. ADR125 D5 records it as an open gap.
- **Do:** pick a mechanism that sends a tenant image pull through the gateway set without moving the rest of the node's traffic, for example a pull-through proxy pod the policy selects, set as containerd's registry mirror, or a host route for the pull alone. Keep the release's own credential the only one that can read a private image (ADR022 § registry isolation). Record the choice in ADR125.
- **End state:** an image-backed service whose private registry admits only the service's `outboundIps` deploys on bex, as it deploys on Render from a registry that admits only the published ranges.
- **Size:** likely more than 1h across more than one task; promote it when picked up.
- **Depends on:** `w21/m616`.
- **Source:** w4/741, 2026-11-27, while routing build pods through ADR125's set.
