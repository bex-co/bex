# 039 — Webhook event picker renders `service_moved` as a raw enum under "Other" (missing humanized label)

Why: The `/webhooks/new` event picker shows the shipped, subscribable `service_moved` event as the bare snake_case string "service_moved" under the "Other" group, while every other event has a humanized label — a copy leak in the subscription UI (same class as the done `w6/036` "New_commit" leak).

Found in a live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-02, workspace `tian-personal`. Read-only (create form opened, never submitted).

## Evidence

On `https://dashboard.bex.co/webhooks/new`, the "Events to send" picker lists every event humanized (e.g. "Deploy Started", "Service Woke Up", "Cron Job Run Started") **except** the "Other" group's single entry, which reads literally `service_moved`.

## Root cause

- `service_moved` is a real, subscribable backend webhook event: `lego/backend/internal/webhooks/service.go:108` (`TypeServiceMoved = "service_moved"`), asserted subscribable in `service_test.go:514` (`slices.Contains(EventTypes, TypeServiceMoved)`).
- The webhook picker's vocabulary catalog `dashboard/src/features/webhooks/event-catalog.ts` has **no** entry for `service_moved`: `eventLabelKey(type)` returns `webhooks.event.${type}` only for `KNOWN` (the `GROUPS` keys + `SINGLES` = `{branch_deleted, job_run_ended}`), else `null` → the event renders its raw `type` and lands in "Other" via the deliberate unknown-future-key fallback (event-catalog.ts:63-71, 111). `grep -rn service_moved dashboard/src/features/webhooks/` returns nothing — the label is simply absent.
- The `service_moved` humanization that **does** exist is in a **different** catalog — the service-events **feed** (`dashboard/src/features/events/service-event-catalog.ts:151` + en/zh detail lines) — which the webhook picker does not use.

## Why m134 didn't catch it

`service_moved` was introduced by open milestone **w6/m134** (2026-08-28). Its DoD (`.pm/w6/m134/README.md:22`) covers "REST, GraphQL, MCP, webhook **delivery**, and the dashboard **Events tab**" — i.e. the outbound payload and the events-feed rendering. It does **not** mention the webhook **subscription picker** label, so this surface fell outside its scope. This note is that missed surface, not a duplicate of m134. (Could alternatively be handled as `/pm add-task w6/m134`.)

## Fix (name the target behavior)

Give `service_moved` a humanized label in the webhook picker: add it to `GROUPS` (an appropriate group) or to `SINGLES` in `dashboard/src/features/webhooks/event-catalog.ts` so `eventLabelKey` resolves, and add the `webhooks.event.service_moved` string (e.g. "Service Moved") to `dashboard/src/features/webhooks/locales/en.ts` + `zh.ts`. It should no longer rely on the unknown-key fallback.

## Blast radius

Dashboard-only. The same `eventLabelKey` feeds the picker (`components/event-picker.tsx`) and the subscribed-event chips (`components/webhook-event-chips.tsx`), so one label entry fixes both. No backend change (the event type is already correct); no Render-parity concern (bex-native event, documented by m134 in ADR018). The live picker is the exhaustive check — it renders every served type and only `service_moved` came back raw, so it is currently the only un-labeled served event.

Estimate: ~15–20 min (one catalog entry + en/zh locale strings + a picker test asserting `service_moved` renders a label, not the raw key).
