# 605 — Response Times still leaves out a Free service's cold-start wake after w4/559: the Prometheus histogram never counts the first request on a Traefik series, and every wake request is one

Why: Response Times is where a Free user looks to see how slow their service feels. It still hides the slowest request they waited for, an 11 s wake, although the request log has it. The same Loki-backed read already returns it when a host filter is set.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 189, 2026-11-12 11:03–11:12 UTC (`muse.env`, workspace `bex-canary`; pin `a5be11e4e517`, which carries w4/559's `398f71cc7`). **Major**: this is w4/559's DoD 2, failing live after its fix. ~50m.
- **Fixture:** Free image service `qa-20261112-r189-m` (`srv-dbqple28vjhs73do9bn0`, `traefik/whoami:v1.10.1`), with `PATCH serviceDetails.idleTTLSeconds: 60` at 11:03:26. Deleted afterwards (DELETE 204, then GET 404).
- **Probe:**
  - **Two wakes.**
    - `service_hibernated` fired at 11:04:59. At 11:05:12, `curl -w '%{time_total}'` on `/wake-r189` returned 200 in 11.14 s.
    - The service slept again at 11:07:29. At 11:07:40, `/awake-r189` returned 200 in 12.10 s.
    - The request log recorded `responseTimeMS=10584` at 11:05:23 and `responseTimeMS=11565` at 11:07:53.
  - **The same read, two stores.** Over 10:50–11:11, `GET /v1/metrics/http-latency?resource=<srv>&resolutionSeconds=60&quantile=0.99`:

    | Read | Values (minute = seconds) |
    | --- | --- |
    | unfiltered (Prometheus router histogram) | `10:55=0.0816`, `10:57=0.0100`, `11:09=0.0247`. **Nothing at 11:06 or 11:08** |
    | `&host=qa-20261112-r189-m.onbex.co` (Loki request log) | `10:54=0.0084`, `10:55=0.0619`, `10:57=0.0068`, `10:58=0.0072`, `11:00=0.0025`, `11:02=0.0094`, `11:04=0.0171`, **`11:06=10.5849`**, **`11:08=11.4495`**, `11:09=0.0360`, `11:12=0.0533` |

    The host filter selects every request this service received, because it has one host. The unfiltered read is therefore missing two wakes and five single-request minutes.

  - **The count is right.** `http-requests?aggregateBy=statusCode` (Loki, w4/m119) has `200` at 11:06=1 and 11:04=1, matching the log.
  - **w4/559's DoD 1 passes.** `filters/http` listed `["200","301","503"]`, with the first deploy's 503s, at 10:55.
- **Root cause:**
  - **559 changed the selector, not the store.** After 559, `promQueryFor` (`lego/backend/internal/metrics/source.go:474-503`) reads `histogram_quantile(q, sum(rate(traefik_router_request_duration_seconds_bucket{router=~<App routers>}[…])) by (le))`. The router identity is right: the hibernated Ingress keeps its name and only swaps its backend to `bex-activator-<app>` (`lego/operator/internal/controller/app_controller.go:3194-3227`).
  - **Traefik's router series carry the backend Service and are deleted when it leaves the config.** In Traefik v3.7.17 (production's pin):
    - router metrics are labelled `code, method, protocol, router, service` (`pkg/observability/metrics/prometheus.go:185-204`);
    - on every configuration update, `SetDynamicConfig` (`:344-373`) queues each Service that is gone;
    - `Collect` (`:383-426`) exports those series one last time and then runs `DeletePartialMatch({"service": …})`.
  - **Every wake request lands on a fresh series.**
    - Sleeping, the route names the activator alias; waking, the operator swaps it back to the App's Service. Each swap deletes the other backend's series.
    - So the wake request creates `{router=R, service=<ns>-bex-activator-<app>-8888@kubernetes, code=200, …}` with its count already 1. That series is scraped at that value (Traefik job `scrape_interval: 15s`, `deploy/gitops/base/prometheus.yaml:413-414`) and deleted after the route swaps back.
    - `rate()` needs an increase between two samples, so a series whose first sample already holds the request reads 0. `histogram_quantile` over all-zero rates is NaN, and the minute has no point.
    - The same holds for the first request of any new `(code, method, protocol, service)` combination, and for the App's own Service after every suspend/resume or sleep/wake. That is why 10:58–11:04 (single requests after this round's suspend/resume runs) are also missing.
  - **The design note this rests on.**
    - `lego/backend/internal/metrics/service.go:1121-1124` keeps "Only the count. http_latency stays on Prometheus (its percentiles come from a histogram, and rate() is the right primitive there)". Only the count moved to Loki (`:1130`).
    - ADR010 line 225 notes the Loki source is "unaffected" by the bucket rollout.
- **Fix (target behavior):**
  - **Every request is counted.** Response Times (REST `http-latency`, GraphQL `metrics(name: http_latency)`, MCP `get_metrics`, the dashboard chart) includes every request the request log records for the service. For a minute containing a wake, p99 is within ~1 s of that request's `responseTimeMS`. A minute with a single request has a point.
  - **Concretely:** an unfiltered `http_latency` read goes to the request-log store like the count. In `requestMetric`, the branch at `service.go:1130` admits `MetricHTTPLatency` too. That uses the existing `quantile_over_time(… | unwrap latency_ns …)` builder (`lokisource.go:136-143`), which this round's `host=` probe shows answering the wakes.
    - It falls back to the Prometheus histogram only when Loki errors, as the count does.
  - **Amend the docs:** the comment at `service.go:1121-1124` and ADR010 § Request (line 225).
  - **Considered:** Prometheus v3.13.5's created-timestamp zero ingestion (`--enable-feature=created-timestamp-zero-ingestion` with protobuf scrape) would also make `rate()` count a series' first increment. That would also cover the Prometheus count fallback and bandwidth. It is a platform-wide scrape change, unverified against Traefik's exposition, so file it as a follow-up if bandwidth proves affected.
- **Blast radius:**
  - **One shared read.** `requestMetric` serves REST, GraphQL (`graphql.go:45`), MCP and the dashboard. `MetricHTTPLatency` has no other production consumer (`grep -rn MetricHTTPLatency lego/backend/internal` outside `metrics/`: only the adapters).
  - **Static sites.** They read router counters too, and their backend (the shared static-server) does not swap per request. Keep their latency tests green, and check a 7-day window answers within the read timeout on Loki.
  - **The Prometheus count fallback** (`service.go:1149-1166`) has the same first-sample loss. It is only used when Loki fails, so leave it as is.
  - **Bandwidth** (`traefik_router_responses_bytes_total`, `increase()`) may lose each fresh series' first response bytes the same way. This is reasoned, not probed. Verify it in a task step before deciding whether the follow-up is needed; do not fold it into this fix.
- **Tests:**
  - an unfiltered `http_latency` read with the request-log source wired queries Loki (`quantile_over_time`) and returns its series;
  - a Loki error falls back to the Prometheus histogram;
  - host/path-filtered and `aggregateBy=host` reads are unchanged;
  - with no request-log source wired, the read still uses Prometheus.
- **Unverified:**
  - The dashboard Response Times chart. It reads the same backend through GraphQL, but I did not open it this round.
  - w4/559 DoD 3's static-site control (not probed this round).
  - Bandwidth, above.
  - Render's handling of a spin-up wait in its response-time chart (559's Unverified, carried over).
- **Dedupe:**
  - w4/559 (done; this round records its DoD 2 failing live).
  - w4/m119 (done) moved only the count to Loki.
  - w4/502 (done) and w4/559 changed the buckets, which cannot help a request that is never in `rate()`.
  - `grep -rli "first sample\|DeletePartialMatch\|created-timestamp" .pm` finds nothing.
  - Not deploy lag: `git log a5be11e4e517..origin/main -- lego/backend/internal/metrics` is empty.
- **DoD (live):** on an owned Free web service with Idle Timeout 60 s, let it hibernate and `curl -w '%{time_total}'` it once, twice in a row.
  - Unfiltered `GET /v1/metrics/http-latency?quantile=0.99` and the dashboard Response Times p99 show each wake's minute within ~1 s of the measured time, matching the `&host=` read.
  - A minute with a single request after a Suspend → Resume has a point.
  - The `/p1` path count, the host filter, `aggregateBy=host` and a static site's Response Times are unchanged.
