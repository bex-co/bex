# 284 — Browser Back from a deploy detail discards history filters

Why: inspecting a matching deployment should let the user return to the narrowed history without entering the same search and status again.

**Severity:** minor. **Estimate:** 55m. Functional `$qa-find-bugs w4` a347, 2026-10-13 UTC, production dashboard/workspace bex. Research main `d15c1e7fc`, unchanged after pull. Filing only. [Complete safe API requests/responses and navigation receipts](evidence/284-deploy-history-back.json).

## Reproduce and expected result

Create an owned Free image web service and deploy its image twice. This pass used `qa-20261013-a347-history`, `srv-db71qnna4m3s73d9i4ag`, BusyBox 1.37 with a small public HTTP marker. Initial deployment `dep-db71qnna4m3s73d9i4b0` is Deactivated; the newer `dep-db71r3c479ic73bbj4e0` is Live.

- At 1440px, open Deploys, select **Deactivated**, and search `DEP-DB71QNNA4M3S73D9I4B0`. At **12:03:01.809Z** the one matching row is visible and both controls hold the selected values.
- Click that row's detail link. At **12:03:19.226Z** the detail is settled and the history controls are absent.
- Press browser **Back**. At **12:03:19.787Z** the history has an empty search, **All statuses**, and both deployments instead of the earlier one-row selection.
- Independently reload the history at 390px. Select Deactivated and search `DB71QNNA4M3S73D9I4B0`; the filtered one-row view is captured at **12:04:13.540Z**. Open its detail, wait for that page to settle, and press browser Back. At **12:04:16.613Z** both filters again reset and both rows appear. The page width remains 390px.

Expected: Back returns to the history selection the user left. This is loss of already-entered filter input in the ordinary list → detail → Back journey. It does not claim incorrect server filtering or a verified Render divergence.

## Cause and bounded fix

`dashboard/src/features/deploys/components/deploys-list-page.tsx:113–119` owns search and status in two empty-initialized `useState` values. Status supplies `useDeploys`; search narrows its loaded results. The detail Link at `:204–206` navigates to the sibling detail route. The live receipts show the history controls disappear there; returning constructs the history controls with their empty initial values.

The two production JSX mounts are:

- `dashboard/src/routes/services.$serviceId.deploys.index.tsx:5–16`: no search validator or retained filter state; only serviceId is passed to the page.
- `dashboard/src/routes/static.$serviceId.deploys.index.tsx:11–18`: the same arrangement. This route is intentionally reachable for static history even though there is no static sidebar Deploys tab.

Keep the history's selection in the router location and make both route wrappers pass validated search/status values and change callbacks to the shared page. The URL-owned filter pattern in `services.$serviceId.metrics.tsx:24–47` is a local precedent. Preserve the existing status vocabulary, loaded-results-only text search, and empty/default behavior of a new unfiltered location. Use replacement updates for editing the list filters so typing does not create one history entry per character; entering a detail still creates a returnable list entry. A canceled debounce or delayed update must not overwrite a later location. Do not retain filters globally across service IDs, keep the entire list mounted behind detail, or duplicate the server's status predicate in the dashboard.

Keep pagination tied to the effective service/status filter in `features/deploys/hooks/use-deploys.ts:108–165` and its appended-pages seam. Preserve status refresh, case-insensitive loaded-ID/commit/message matching, honest loaded counts, eligible rollback actions, and current desktop/mobile table geometry. No backend/API or log-filter implementation change is required. Static, private, worker, cron and alias navigation behavior are source-scoped or implementation verification; only the Free web route was live-replayed here.
