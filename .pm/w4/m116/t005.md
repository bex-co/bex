## Objective

A fresh `bex login` device approval demands the password twice (login page, then the post-Authorize login challenge shows a Kratos "Reauthenticate" form), and the repo's browser helper predates the `/auth/device` page so it cannot complete the flow at all. Get to one password entry and a working helper.

## Context

- Live repro 2026-09-17 (7 device codes; completed twice end to end via a private Playwright adaptation — password never left the helper process):
  - `bex login` → verify URL → `/auth/login` (password #1) → `/auth/device` → Authorize POST (302) → `/auth/login?login_challenge=…` showing "Reauthenticate / Confirm your identity…" → password #2 → `/auth/device/success` ("Device connected"), CLI prints "Login successful! CLI token saved."
  - Precedent: `.pm/w4/done/m99/live-acceptance.md:313` records the same double entry on 2026-09-09 ("completed after the Kratos challenge required reauthentication") — established behavior, never filed.
- Design intent says once should suffice: `dashboard/src/common/hooks/use-ory-flow.ts:281-292` short-circuits `session_already_available` + challenge straight back to Kratos with no form. Cause UNVERIFIED: either the SDK flow-creation fetch doesn't carry the seconds-old session (cross-origin fetch without credentials) so Kratos mints a fresh flow, or the challenge flow is created with refresh semantics somewhere upstream of the hook. Verify with the actual `createBrowserLoginFlow` request (cookies attached?) before changing anything.
- Helper staleness (mechanical, verified): `scripts/render-cli-auth-browser.cjs:85` waits for `/auth/consent|device/success` right after password submit, but current production lands on `/auth/device` (confirm page) first — it times out there every run. It also assumes single-form login inputs (`input[name=identifier]`), while the challenge page renders a password-method accordion with hidden prefilled identifier.

## Steps

1. Determine why the hook's short-circuit doesn't fire (request-level evidence: flow-creation call with/without session cookie, Kratos response code). If the session isn't attached, fix the client; if Kratos legitimately demands step-up here, document why and close the double-entry half as intended.
2. Update `scripts/render-cli-auth-browser.cjs` to the current flow: login → `/auth/device` Authorize click → challenge login (accordion-aware) → consent approve-if-present → `/auth/device/success` + "Device connected" assertion. Keep credentials on stdin (never argv/files/transcript).
3. Run the full `scripts/bex-cli-auth-e2e.sh` device/refresh/logout evidence pass against an available Bex auth environment.
