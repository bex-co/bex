## Objective

`bex jobs create` is accepted (200 + `job-…` record) and then always lands on a bare `failed` ~16ms later with no reason anywhere. Either make one-off jobs runnable or refuse them honestly — and record the scope decision against the DO_NOT_DO tension below.

## Context

- Live repro 2026-09-17 (twice, second in isolation), `bex v0.2.1`, live free Docker web service (debian-slim image, has `/bin/sh`):
  - `bex jobs create <srv> --start-command 'echo <marker>' --plan-id free -o json` → `{"id":"job-…","status":"failed"}` with `finishedAt - createdAt ≈ 16ms`. `jobs list` agrees; no reason field exists.
- REST re-probe 2026-09-21 (live `/qa-find-bugs` pass 106, `qa-p106-jobs` since deleted): `POST /v1/services/{id}/jobs {"startCommand":"echo qa-p106-hello"}` → `job-daoc7ors0ils73bgpcfg`, `failed`, `finishedAt - createdAt ≈ 12ms`; detail GET carries no reason — same backend, all three surfaces affected.
- Root cause (two halves):
  1. `createK8sJob` (`lego/backend/internal/jobs/service.go:289-329`) submits a plain batch Job, but bex-api's grant is read-only: `deploy/gitops/base/bex-api-apps-rbac.yaml:52-54` allows `batch/jobs` `get,list` only ("created by the operator, never by bex-api"). The `Create` is Forbidden; no bex-api role grants `create` (checked `build-boundary.yaml`, `tenant-namespace-clusterroles.yaml`). So every one-off job fails at admission, on every service type.
  2. The failure reason is swallowed: `service.go:208-214` logs the k8s error server-side and records bare `failed`. Contrast the `failureReason` excellence on deploys (w4/m103).
- SCOPE DECISION REQUIRED: `.pm/DO_NOT_DO.md` lists "One-off jobs (`/services/{id}/jobs`) … remain off-roadmap". But the endpoint shipped with tests and checklist `[x]` rows (graded on dev-9 ACK shape, never a prod run). Step 1 resolves this — do not expand scope silently.

## Steps

1. Resolve the scope question on the record: if one-off jobs stay off-roadmap, gate the endpoint (`405`/`410` with a named error, remove or re-grade the checklist rows, keep `jobs list/cancel` for history) and update/strike the DO_NOT_DO line accordingly; if they ship, continue below.
2. If shipping: grant bex-api the minimal `batch/jobs` create (tenant namespaces only, audited), harden the submitted pod to the operator's workload-admission baseline, and prove a run end to end on a free web service.
3. Either way: surface creation failures to the caller (named error at create time; a `reason` on the job view for async failures). A 16ms `failed` with no text must become impossible.
4. Update `docs/cli-compatibility-checklist.md` (`jobs` rows) to the shipped behavior.
