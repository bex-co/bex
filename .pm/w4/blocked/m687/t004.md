## Objective

Refuse a public request that carries its own `CF-Connecting-IP` from a non-Cloudflare peer with Render's answer, instead of silently replacing the value.

## Context

- Render answered such a request `403`, `text/plain; charset=UTF-8`, body `error code: 1000` (17 bytes), before it reached the app (t001). Render's PocketBase article says the same.
- The refusal sits at the edge, so it covers web services, static sites, platform hosts and custom domains alike, as Cloudflare does on Render.
- A request from a pinned Cloudflare range keeps its header (a tenant custom domain behind its own Cloudflare).

## Steps

1. Answer the 403 with t001's exact body and content type when the peer is outside the Cloudflare ranges and the request carries `CF-Connecting-IP` (any spelling the plugin already strips, `CF_Connecting_IP` included).
2. Record the access-log line so a refused request is findable by its `Rndr-Id`.

## Files

- `deploy/gitops/charts/traefik-plugins/clientipheaders/clientipheaders.go`
- its `_test.go`

## Acceptance criteria

- [ ] A forged `CF-Connecting-IP` from a non-Cloudflare peer gets t001's 403 byte for byte; the same request without it reaches the app; a Cloudflare peer's header passes.

## Out of scope

- Refusing forged `CF-IPCountry` or `CF-Ray`, which Cloudflare overwrites rather than refuses.

**Shipped 2026-11-27 (`883f00c2ab`), then turned off (`e068a54afa`):** a non-empty `CF-Connecting-IP` from outside Cloudflare gets t001's 403 byte for byte. Deviation from step 1: the underscore spelling and an empty value are stripped, not refused, because Render answered both `200` (t001). In Traefik the refused request's access-log line carried `request_Rndr-Id` `915c2dc8-5edb-fe63` and the answer `cf-ray: 915c2dc85edbfe63-FRA`.

**Turned off on production, 2026-11-27.** Once the edge carried `883f00c2ab` (about 03:20 UTC), `beancount.io` and `bex.co` answered `403 error code: 1000` with `via: 1.1 Caddy`: `beancount.io` is a custom domain on the `bex` workspace's `reverse-proxy-poc` web service, whose Caddy forwards every request header, Cloudflare's `CF-Connecting-IP` included, to other bex services through the public edge, so the second pass came from a non-Cloudflare peer with the header. `bex.co` showed the same signature. `e068a54afa` makes the edge replace the header with the peer instead (a `CDN-Loop` past 16 is still refused), and both sites answered `200` again at 03:34 UTC. The same chain on Render would meet Cloudflare's own refusal, but these sites run on bex today. **Open:** the user decides between (a) keeping the replacement and signing off ADR018's difference (4), and (b) having those proxies stop forwarding the header (Caddy `header_up -CF-Connecting-IP`, or reaching the sibling over the private network), after which a worker restores the refusal (`refused := claimed != "" && !fromCloudflare` in `clientipheaders.go`, `TestForgedConnectingIPIsRefused` from `883f00c2ab`), verifies it and the affected sites on production, and closes with t010.
