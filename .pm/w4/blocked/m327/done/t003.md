## Objective

`releaseRequestedOrRolling` (`lego/operator/internal/controller/saved_configuration.go:170-176`) stops treating `PhaseDeploying` alone as proof of a rollout. `inFlightCarriesSavedConfiguration` (`:143-163`) answers true only when a release newer than the serving one is stamped or its rollout is in progress.

## Context

- Today a Save only leaves `pending = app.Generation` (`release_identity.go:744-749`). With no record for it, `:152-154` answers true whenever the phase is Deploying, so a served release's outage reads "Saved changes go live when the current deploy finishes".
- Keep w4/529 (a requested deploy counts as applying before it rolls) and w4/m184.

## Acceptance criteria

- [x] **Unit:** a Save only, then the served release's pods go unready → `UndeployedChanges=true`, `UndeployedChangesApplying=false`.
- [x] **Unit:** a requested deploy, both before and during its rollout → `UndeployedChangesApplying=true` (the w4/529 and m184 cases).
- [x] The dashboard notice reads `services.undeployedChangesHint` in the outage case.

## Result (2026-11-11)

- `releaseRequestedOrRolling` counts Deploying as rolling only when the release is not the active one (`releaseRevision(app) != ActiveRevision`). A served release's outage, or its start after a wake, no longer says saved changes "go live when the current deploy finishes". The notice reads "Use a standard deploy to apply them".
- A requested deploy (its stamp) still counts before it rolls (w4/529), and an adopted rolling release still counts (w4/m184).
- **Tests:** `TestServedReleaseOutageIsNotADeploy` checks `releaseRequestedOrRolling` in each case, and the existing saved-configuration suites pass.
