## Objective

Record what Render's dashboard header, services list and API show while a live service's instance fails its health check, and write the target into ADR004 § Health checks: a served release's outage is not a deploy, so its phase stays `Running` and the outage is reported by `server_failed` / `server_available`.

## Context

- ADR004:322 keeps `Deploying` for the wake or resume start of the served release. That stays.
- ADR004:247 makes a saved release setting wait for a standard deploy. That stays.
- [render.com/docs/health-checks](https://render.com/docs/health-checks).

## Acceptance criteria

- [x] ADR004 § Health checks states the rule, cites Render, and names the unchanged Deploying cases (rollout, pre-deploy, wake or resume).
- [x] If Render shows a distinct unhealthy status, a follow-up is filed rather than keeping "Deploying".

## Result (2026-11-11)

- **Render's documented behaviour** ([health-checks](https://render.com/docs/health-checks)): an instance that fails its health check is removed from rotation and then restarted. That is an instance event (`server_failed` / `server_available`), not a deploy.
- **Target, recorded in ADR004 § "A live release failing its health check is not a deploy":** the service keeps its live status, the Deploys list is unchanged, and saved settings wait for a deploy.
- **Not captured live:** Render's header and services-list badge during an instance failure. That needs an induced outage on a live Render service, and the reference workspace's services are someone's production. The badge is recorded as unverified. If Render turns out to show a distinct unhealthy badge, that becomes a follow-up (the milestone's own rule).
