# A transient datastore lock conflict stops project deletion with an internal error

**Severity:** major, recoverable: a normal delete leaves a partially detached project and gives no usable recovery explanation. No data loss is observed. **Research:** main `781ec11c5`; continuous functional `$qa-find-bugs w4`, pass a698, 2026-10-16 UTC. This hunt ships the filing only. [Complete exact requests, responses, controls, local diagnostic and cleanup](evidence.json).

## Mechanism and bounded correction

- `projects/service.go:533–560` clears every child environment, then datastore project labels, then deletes the project row. Each error returns immediately; earlier writes remain. That interruption design is intentional in w7/m151 and must stay retry-safe.
- `environments/service.go:883–937` shares environment teardown between direct environment Delete and the project cascade. Its datastore departures call conditional ClearEnvironmentID. Project-label clearing calls ClearProjectID at `projects/service.go:555`.
- PostgreSQL `service.go:1655–1683,1716–1746` and Key Value `service.go:599–627,660–690` fetch/authorize, compare the expected label and perform one optimistic patch. The underlying setters return the raw patch error. There is no conflict retry here.
- Locked controller-runtime **v0.23.3**, `pkg/client/patch.go:80–119`, inserts the fetched resourceVersion into the patch. Any intervening update can reject it, including an unrelated update. It performs no automatic read/retry. Locked client-go **v0.35.0**, `util/retry/util.go:26–45,74–110`, supplies bounded RetryOnConflict and requires a fresh read and raw error classification on every attempt. `store/release_cancel.go:84` is a repository precedent, not a helper to import into these feature packages.
- `api/server.go:1631–1662` correctly redacts an unclassified Kubernetes error to `internal error`. `features/projects/hooks/use-delete-project.ts:25–41` displays `mutationErrorMessage`; `common/lib/graphql-error.ts:146–149` displays a GraphQL message, and project settings `:85–93` navigates only on success. A safe classified recovery explanation reaches this consumer without changing Apollo defaults or exposing raw provider text.

An ignored diagnostic overlay exercised the real existing PostgreSQL and Key Value service fixtures and fake-client optimistic version check. For each kind, both ClearProjectID and ClearEnvironmentID receive one unrelated annotation update between fetch and patch. All four cases produce a raw conflict after exactly one patch; a separate second call succeeds, retains that annotation and resource-owned rules, and clears only expected placement. Exact source and output are committed in the evidence. This isolates the missing retry even when placement did not change. It does not prove that a status writer caused the production conflict.

**Target:** narrowly retry the four conditional clear operations on Kubernetes lock conflict. Each attempt must freshly fetch and authorize the same namespace/resource identity, recheck the expected project/environment, preserve optimistic locking and stop if the object was replaced. A concurrent reassignment to another grouping remains untouched and makes the stale clear a no-op, as today. Do not replay a stale object, remove the version precondition or retry the whole project deletion automatically.

Use a bounded, context-aware retry consistent with the existing request budget; stop on non-conflict errors. If conflicts exhaust, return a safe domain conflict explaining that cleanup may be partial and the user must reload current placement before retrying. Use an existing public conflict/code mechanism; preserve general redaction. Permission/validation/missing-resource failures keep their existing classifications, replacement stays a classified refusal, and a request deadline retains truthful unknown-outcome semantics. No all-or-nothing transaction promise is added.

## Shared scope and verification

There are **four target methods**, two per datastore kind. ClearProjectID has **one production dispatch site**, the project-delete kind loop. ClearEnvironmentID has **two typed adapters** (databaseResources.leave and keyValueResources.leave); those adapters are dispatched from **two production locations**: environment teardown's leaveEnvironment, and omitted-member removal in setResourceMembers. Teardown itself has two roots, direct environment Delete and the project cascade. These successful removal consumers need controls.

The private setProjectID/setEnvironmentID helpers each have two callers per kind: ordinary Set and conditional Clear. Allowlist retry semantics to Clear; changing ordinary assignment could overwrite a legitimate concurrent move. SetEnvironmentIPAllowList, env-group detach and App projection are neighbors, not newly failed operations to broaden into this fix.

Project deletion has three adapters: REST `DELETE /v1/projects/{id}` (`projects/rest.go:207`), GraphQL `deleteProject` (`projects/graphql.go:81`), MCP `delete_project` (`projects/mcp.go:111`). Direct environment deletion likewise has REST `/v1/environments/{id}`, GraphQL `deleteEnvironment` and MCP `delete_environment`. Membership removal also reaches REST database-links/keyvalue-links and PATCH, GraphQL setEnvironmentDatabases/setEnvironmentKeyValues, and MCP **update_environment**; the old individual set*environment*\* tools are retired. Verify these existing names, not invented aliases. Web/static/cron/worker/private App deletion/projection remains outside the datastore patch change; live fixtures covered web only.

Required tests must compose the production service and adapter paths: one unrelated-update conflict then success; real concurrent reassignment between attempts; no-op and already-cleared members; UID replacement; bounded exhausted conflicts; non-conflict failure and canceled context. Preserve unrelated spec/status/annotations, resource-owned rules, expected-environment fencing and repeated cleanup. For a later-member failure, retain the parent for recovery, explain possible partial state, reload, and finish exactly once. Check ordinary Set and successful omitted-member removals separately. A fake that returns conflict without an actual version change is insufficient for the central regression.
