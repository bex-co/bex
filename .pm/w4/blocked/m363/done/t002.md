## Objective

Show that the new bound is safe end to end. The `<name>-files` (and `<gid>-files`) Secret holding the maximum contents plus 500 maximal names must be accepted by a real kube-apiserver and etcd. The REST, GraphQL and MCP request bodies that carry such a file must fit their limits.

## Context

- The Secret is written by `lego/backend/internal/secrets/files.go` (`filesSecretName`, `:65`). The operator mounts it in one projected `/etc/secrets` volume with each linked group's Secret (`lego/operator/internal/controller/deployment_projection.go:671-677`).
- ADR066 #6's original worry was that a map past the Secret ceiling wrote to OpenBao first and then failed at the projection. The new bound must sit at or under what the apiserver accepts, so that cannot recur.
- etcd's default `--max-request-bytes` is 1.5 MiB. Production's value was not read in run sf13.
- bex-api's REST body limit is between 1 MiB and 4 MiB (w4/422). JSON escaping can inflate a file's contents.

## Steps

1. In an envtest (real kube-apiserver + etcd), create a Secret with values totalling the bound and 500 names of 253 characters each. Then try one byte more, and record where the apiserver refuses. Set t001's constant from that result.
2. Find bex-api's request-body limits for REST, GraphQL and MCP. Confirm each carries a bound-sized file whose JSON escaping doubles its size (for example, all `"` characters). Raise a limit only if a Render-valid request would be cut off.
3. Read production etcd's `--max-request-bytes` if access allows. Otherwise record it as unverified, with the envtest result as the evidence.

## Outcome (2026-11-14)

- **Apiserver bound, settled.** The backend has no envtest suite, so the test lives in the operator's: `lego/operator/internal/controller/secret_files_bound_envtest_test.go`, "secret files bound (w4/m363)", against envtest's kube-apiserver and etcd 1.37. A Secret whose values total exactly 1,048,576 bytes, under 500 keys of 253 characters, is accepted and reads back whole. 1,048,577 bytes is refused as `Invalid`, and the error names `1048576`. An update that grows the full Secret by one byte is refused too. So the check is `> MaxSecretSize`, and t001's constant is `corev1.MaxSecretSize`.
- **Where more than one map shares a Secret.** bex-api's `<name>-files` and `<evg-id>-files` Secrets hold only their map. Revision stamps and the prepared-at claim are annotations, which `MaxSecretSize` does not count. Release snapshots copy one source each. The one place maps merge is a native or Dockerfile build: `projectNativeBuildFiles` used to write the service's files and every linked group's into one `bld-<app>-native-files` Secret. That could already overflow before this milestone (512 KiB per map, three maps), and at 1 MiB a service plus one group would. It now packs the merged files (`packSecretFiles`) in name order into as many Secrets as needed. Each one holds at most `MaxSecretSize` of values and 500 keys, so no packed Secret is larger than one source map's. The first keeps the old name, the rest are `…-native-files-2`, `-3` and so on. Stale ones are deleted, and App deletion reclaims them by artifact label. The build Job mounts them all through one projected volume (`build.Options.NativeFilesSecrets`), so `/native-files` and the Dockerfile snapshot see one set. A single file over `MaxSecretSize` cannot come from an accepted map, and fails the build by name. The envtest also packs a full service map with a full group map: two Secrets, both accepted, holding the merged set. When the group is unlinked, the second Secret is deleted.
- **Body limits.**
  - REST, GraphQL and MCP all sat behind `BEX_MAX_BODY_BYTES`, 2 MiB by default (`api/server.go`). A plain 1 MiB file fits (about 1 MiB plus 30 bytes). A 1 MiB file of `"` characters escapes to 2,097,166 bytes and was cut off with a 413, even though Render accepts it.
  - New: `secrets.MaxEnvironmentBodyBytes` = 2 × (1 MiB + 512 KiB) + 1 MiB = 4 MiB. That covers both maps full and every byte escaped to two. The cap is raised to it (never lowered, and a disabled cap stays disabled) on `/graphql`, `/mcp` and the REST secret-file writes: `PUT …/secret-files[/{name}]` for services, build sources and groups, `PATCH …/environment` for services and groups, and `PATCH /v1/env-groups/{id}/contents`.
  - Largest file carried: on every one of those surfaces, a full 1 MiB set escaped to two bytes per byte, with a full env map. On any other route, a plain 1 MiB file still fits the 2 MiB global.
  - `api.TestSecretFileWritesTakeTheEnvironmentBodyCap` pins it.
- **etcd.** Production's `--max-request-bytes` was not read: no cluster access from this run, so it is unverified. A full Secret, with 1 MiB of values plus 126 KiB of keys and about 130 KiB of managed fields, is about 1.3 MiB. That is under etcd's 1.5 MiB default, which envtest's etcd runs with and accepted.
