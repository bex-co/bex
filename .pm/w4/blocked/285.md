# 285 — Secret-file uploads drop a valid leading UTF-8 byte-order mark

Why: uploading a supported text file should preserve its contents, so the stored file remains the one the user selected.

**Severity:** minor; three leading bytes are silently removed, with no runtime consumer failure demonstrated. **Estimate:** 45m. Functional `$qa-find-bugs w4` a349, 2026-10-13 UTC, production dashboard/workspace bex. Research main `e2cc47429`, unchanged after pull. Filing only. [Exact input bytes, requests/responses, browser controls and cleanup](evidence/285-secret-file-bom.json).

## Reproduce and passing controls

Create an empty, unlinked environment group. This pass used `qa-20261013-a349-textfiles`, `evg-db722qfa4m3s73d9i4ig`; no service or paid resource was created.

1. At 1440px, enter its editor and upload three files together: empty `qa-a349-empty.txt`, CRLF text `qa-a349-crlf.txt`, and `qa-a349-bom.txt` with exact hex `efbbbf71612d613334392d626f6d0a` (15 bytes: UTF-8 BOM followed by `qa-a349-bom\n`).
2. The files are staged with no upload alert. Select Save only. The successful request at **12:18:48.719Z** already omits the leading U+FEFF from the BOM file, submitting only `qa-a349-bom\n` (12 UTF-8 bytes). GraphQL readback at **12:18:50.655Z** returns that altered content. Empty content and the full CRLF contents are preserved.
3. Independently reload at 390px, enter Edit, and upload a new `qa-a349-mobile-bom.txt` containing `efbbbf` followed by `qa-a349-mobile-bom\n` (22 bytes). Save only at **12:19:56.139Z** succeeds with the prefix already absent. Readback at **12:19:57.392Z** starts with codepoint 113 (`q`), and the fresh contents dialog at **12:21:30.523Z** contains the corresponding 19 bytes. Width remains 390px.
4. In the same group's contents dialog, enter `\uFEFFqa-a349-bom\n` directly for the first file. Save only at **12:20:46.362Z** includes U+FEFF, and readback at **12:20:47.618Z** preserves codepoint 65279. The backend can preserve this valid character; the upload path discarded it before submission.

Expected: an accepted UTF-8 upload retains the original text, including a leading byte-order mark. The existing UTF-8-only limitation does not require removing this valid prefix. `docs/bex-cli.md:139–152` and `w8/done/029` explicitly retain the text-files byte-preservation contract. This is an upload-content issue, not a new binary-file feature.

## Cause and bounded fix

`dashboard/src/features/services/components/service-environment-editor.tsx:507–547` is the upload loop. At `:530–532`, it decodes with `new TextDecoder("utf-8", { fatal: true })`. The default BOM handling omits the initial U+FEFF while leaving the remaining text valid, so the draft and subsequent patch already contain altered contents.

The [WHATWG TextDecoder definition](https://encoding.spec.whatwg.org/#interface-textdecoder) defaults `ignoreBOM` to false; its [serialization algorithm](https://encoding.spec.whatwg.org/#interface-mixin-textdecodercommon) skips the first BOM in that mode. A current-browser control at **12:21:28.692Z** shows the exact 15 input bytes decoding without U+FEFF under the current options, and with U+FEFF under `{ fatal: true, ignoreBOM: true }`. The preserving options still throw on an invalid UTF-8 byte in that local control; no product change or production malformed-file upload was made.

Set `ignoreBOM: true` on this existing strict upload decoder so it treats the mark as content while retaining `fatal: true`. Preserve filename/duplicate/size checks, NUL refusal, mixed valid/rejected batch behavior, local drafts and Save-mode semantics. Do not alter every TextDecoder: `common/lib/utils/encode.ts` and `common/server-fn/bounded-body.ts` are distinct contracts and are not this file-upload path.

The shared `EnvironmentEditor` has two production adapter JSX mounts: service adapter `service-environment-editor.tsx:124` and group adapter `features/env-groups/components/env-group-editors.tsx:30`. The latter is mounted by `routes/env-groups_.$groupId.tsx:212`; the service adapter by `routes/services.$serviceId.env.tsx:58`. Group behavior was live-replayed; service upload/mount behavior is source-traced and remains implementation verification. The new-group create form and service create form are separate editors; do not claim their contents-input paths have this decoder defect.
