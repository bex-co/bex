# 289 — Numeric log-search links silently change large identifiers

Why: opening a log-search link for an exact numeric identifier can search for a different identifier and hide the matching record.

**Severity:** minor. **Estimate:** 55m (10m shared decode boundary, 20m router/route regressions, 15m owned live replay, 5m consumer audit, 5m Simplify). Filed through `/pm add w4` from the user's functional `$qa-find-bugs` loop, 2026-10-13 pass a364. Filing only; no product fix is included.

## Reproduction and controls

Owned Free web service `qa-20261013-a364-logs`, `srv-db75ubna4m3s73d9i6j0`, became Live at 16:41:36 UTC. Its ordinary HTTP marker prints this exact stdout message:

```json
{
  "event": "qa-a364-structured",
  "counter": 9007199254740993,
  "label": "雪 café 🐟",
  "empty": "",
  "zero": 0,
  "flag": false
}
```

1. Fresh-load `/services/<owned-id>/logs?type=app&text=9007199254740993&live=0`. At desktop 1440px, 17:01:09.957 UTC, Search becomes **9007199254740992**. The actual HTTP 200 GraphQL Logs request sends that changed string and returns zero rows. The URL is rewritten to `text=%229007199254740992%22`.
2. A fresh 390px load reproduces at 17:07:59.613 UTC: changed Search, changed request, and settled **No matching logs**. The original mobile discovery at 16:51:28 UTC also shows the same change.
3. Type the original **9007199254740993** in Search. At 16:54:58.909 UTC, the actual request preserves it and returns the exact structured message. The UI writes a JSON-quoted string URL, `text=%229007199254740993%22`. A fresh reload of that generated link at 16:59:00.932 UTC retains the exact Search and matching record.
4. The correctly quoted link also passes a fresh 390px live-append control at 17:07:22.310 UTC: one existing exact record becomes two after a single owned marker GET. Unicode, empty string, zero, false, and the raw large integer remain intact. Ordinary ANSI-colored output also renders and matches display-mode search correctly.

Expected: the explicitly accepted numeric-looking **free-text** URL input retains its original digits. These are manually composed valid links, not links generated by the UI. The UI-generated quoted-link control passes; this finding does not claim those links corrupt themselves or that log data was lost.

## Cause and bounded fix

- `dashboard/src/router.tsx:14–17` uses the default TanStack search parser. Installed **@tanstack/react-router 1.170.25 / router-core 1.171.21** was read and exercised.
- `router-core/src/qss.ts:49–61` coerces a number only when converting back gives the same spelling. For the odd integer above, that check fails and leaves a string. Then `searchParams.ts:32–43` **JSON.parse** converts that string to the rounded JavaScript number.
- `dashboard/src/features/logs/lib/log-search.ts:80–85,103–118` explicitly accepts numeric query values as strings. By `str(search.text)`, the original digits are already gone. The validator cannot recover them by stringifying the number. The service route uses this validator at `routes/services.$serviceId.logs.tsx:24`.
- `searchParams.ts:74–83` quotes parseable string values when serializing them. This explains why typed text and the UI-generated quoted link remain exact.
- The other **two** production text consumers are `parseDatastoreLogSearch` (`features/logs/lib/datastore-log-search.ts:26–38`), mounted by `routes/databases.$databaseId.tsx:97–104` and `routes/keyvalue.$keyValueId.tsx:60–70`. Those comments also explicitly accept raw numeric text. Their failure was not driven live in this pass. A route/validator census found no other production URL `text` consumer; agent detail's unrelated `.text` is event data.

Add one narrow application `parseSearch` wrapper at the shared router boundary: call exported `defaultParseSearch`, then, only for a **single** top-level `text` that decoded to a finite number, retain its original URL-decoded string from the parser's raw search argument. Keep already quoted strings, unrelated keys and default stringify behavior. Use the same boundary for server rendering and client routing; do not read `window.location` inside route validation.

Preserve rejection of repeated text keys, booleans/null/arrays/objects and non-finite numeric inputs. Preserve numeric `live=0`, statusCode, paging, range/custom bounds, unknown-key behavior and aliases. Do not disable JSON parsing globally, patch dependencies, weaken validators, parse log messages as numeric JSON, or add a new serialization framework. Scientific notation `?text=1e3` normalizes to 1000 in the installed-parser control; include it as a lexical regression boundary, without claiming a second live failure.

Resource family: web, cron, worker and private Apps share the service Logs route; static runtime Logs redirect to Events and have no text viewer. Postgres and Key Value use the two datastore routes above. Legacy `/d/<id>` and `/r/<id>` aliases preserve query/hash through `common/lib/render-alias.ts`; keep them on the same decoder. Deploy-detail panels have their own range state and no URL text consumer. Before any history request settles, the initial control and query must already carry the exact text; do not display a rounded search until a later correction. Ordinary query failure and empty-state handling retain their current meanings.

This restores the existing observability promise in [ADR010](../../docs/ADR010-observability.md) and the Render-alternative hosting goal: an accepted diagnostic link searches the identifier the user supplied. The repair is timely because a valid link currently hides a record that the same page can retrieve with typed text. Backend REST/GraphQL/MCP log matching already accepts the exact string and needs no schema or serializer change.
