# Search loses its opener's keyboard focus after Escape

Why: dismissing the primary resource navigator drops keyboard users back to the document body, so Enter no longer reopens the control they just used.

**Severity:** minor. **Estimate:** 55m. Functional `$qa-find-bugs w4` passes a397–a398, 2026-10-13. Researched against main `c3d6aa86b`; filing only. Source: live dashboard navigation. Goal: predictable navigation of the hosting resources described in ADR008 and ADR018.

## Reproduction and observed result

On a fresh `https://dashboard.bex.co/`:

1. Tab to the topbar **Search** button. The durable keyboard-only receipt records all 12 Tab stops, ending at that button.
2. Press Enter, wait for the Search dialog and combobox, type `bex.co`, and press Escape.
3. Wait for the dialog to detach and another 500ms, allowing the close animation to finish.
4. Focus is now `BODY`. Pressing Enter does not reopen Search. Clicking its still-mounted button does reopen it.

Fresh 1440×1000 and 390×844 trials also focus the actual button before native Enter/Escape. Both record `before.focused: true`, then `after.focused: false`, `active.tag: BODY`, zero dialogs, and `enterReopened: 0`; their pointer controls reopen one dialog. The separate Tab-only desktop trial confirms that programmatic focus is unnecessary. This is a settled keyboard interaction failure, not a missing-label heuristic or an observation during exit animation.

Target: when Search was opened from its button and is dismissed, restore focus to that still-mounted button. Enter should then reopen Search without restarting Tab navigation. The modal-dialog expectation is to restore the invoker unless it has disappeared or a deliberate subsequent workflow has a better focus target ([WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)).

## Root cause and fix boundary

- `dashboard/src/common/components/dashboard-layout/global-search.tsx:52–55,59–77` opens the lazy dialog from a plain Button. The button is not a Radix DialogTrigger in the dialog's context and has no return-focus ref or callback. Cmd/Ctrl+K also toggles the parent open state at `:36–45`.
- `dashboard/src/common/components/dashboard-layout/global-search-dialog.tsx:61–82` renders CommandDialog and its focused input, with no opener information.
- `dashboard/src/common/components/ui/command.tsx:24–44` accepts **DialogProps**, forwards them to the Dialog **root**, and creates its own DialogContent with only className. Passing `onCloseAutoFocus` to this root is not a valid content-level fix.
- Actual installed and locked **@radix-ui/react-dialog 1.1.15** (`dashboard/yarn.lock:2842–2844`) was opened at `dashboard/node_modules/@radix-ui/react-dialog/dist/index.mjs:135–154`. Modal content's default close-auto-focus handler prevents the generic restoration event and calls `context.triggerRef.current?.focus()`. With no registered trigger, it focuses nothing. This explains the observed body focus after unmount.
- `dashboard/src/common/components/ui/dialog.tsx:49–66` accepts Radix Content props and spreads them onto the actual content, so a scoped `onCloseAutoFocus` handler is expressible there. Actual **cmdk 1.1.1** is pinned at `yarn.lock:6430–6432`; this repo uses its own Radix Dialog wrapper around Command, rather than cmdk's Dialog component.

A bounded fix can either register the real Search trigger in the same dialog context while preserving lazy loading, or carry the invoker through GlobalSearch and its lazy child to an explicit CommandDialog **content** callback. Restore focus on button-open Escape/Close. For shortcut-open dismissal, preserve the valid element focused before opening and define a logical fallback if it has disappeared. Result selection navigates; do not let a delayed return-focus callback steal focus from the destination after navigation. Scope any content-prop extension to the search caller, rather than changing every Dialog's focus policy.

Exhaustive production grep: **one GlobalSearch mount**, `dashboard-header.tsx:39`; **one lazy GlobalSearchDialog mount**, `global-search.tsx:76`; **one CommandDialog consumer**, `global-search-dialog.tsx:61`. The other CommandDialog occurrence is its declaration/export. This is the persistent header's shared palette on dashboard routes, including web/static/cron/worker/private, Postgres, Key Value, projects, groups, and Blueprints; it does not require per-resource backend handlers or route aliases. Both Cmd and Ctrl shortcuts reach the same parent toggle.

Before the lazy child is available, preserve the existing header bounds and prefetch behavior. While open, preserve input focus, literal filtering, loading/empty states, and the current false→true query reset. API responses, permission failures, unauthenticated responses, and timeouts retain their existing behavior; this change does not add reads or alter REST/GraphQL/MCP contracts.

## Acceptance and sizing

- On fresh desktop and narrow mobile pages, button-open Search → Escape after typing restores the Search button after full exit. Enter reopens it with an empty query.
- Button-open native Close behaves the same. Shortcut-open dismissal returns to the valid prior invoker or the specified fallback. Ordinary pointer dismissal preserves a logical focus target.
- Selecting a destination still navigates without a late callback moving focus away from the destination. Search remains lazy; filtering, pending results, query reset, and accessible names pass.
- Add meaningful interaction coverage using the real Radix Dialog and native keyboard activation. A mocked dialog or a test merely asserting that a callback prop exists cannot detect this failure. Verify after actual close/unmount, not during the animation.

55m: 20m scoped opener/content wiring, 10m caller and close-path audit, 15m actual-dialog interaction coverage, 10m live desktop/mobile acceptance and cleanup. Keep this as a sub-hour inbox item.

## Progress

Implemented 2026-10-13: `global-search.tsx` remembers the focused element when the palette opens (button click or Cmd/Ctrl+K) and gives the lazy dialog a `returnFocus` callback; an opener that has left the page, or a shortcut pressed with nothing focused, falls back to the Search button. `global-search-dialog.tsx` handles the dialog content's close-auto-focus: it always prevents Radix's default (which restores to an unregistered trigger, i.e. nothing) and calls `returnFocus` unless the close followed a result selection. `ui/command.tsx`'s `CommandDialog` forwards an optional `onCloseAutoFocus` to its content; it has this one consumer and other dialogs' focus policy is unchanged. Lazy loading, prefetch, the query reset (w4/265) and filtering are untouched. Tests in `global-search.test.tsx` drive the real parent, lazy dialog and Radix/cmdk: Escape returns to the button and reopens from it; Ctrl+K close returns to the button; a shortcut-open returns to the previously focused control; a vanished opener and a nothing-focused open fall back to the button; a selected result navigates without focus being pulled back, and the next dismissal restores again. All five fail with the `returnFocus` call removed (checked); the five existing reset tests still pass. Small change, reviewed inline. Dashboard `yarn lint` green; `yarn test` 513 files / 4826 tests green (raised wait timeouts under heavy unrelated machine load). Not covered locally: the Close button path and a real browser's focus ring / mobile keyboard — left to the live replay.
