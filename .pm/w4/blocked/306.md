# Searching paused live logs temporarily hides matching visible lines

Why: an operator pauses to inspect a line already on screen, searches its exact text, and receives “No matching logs” because the history request still ends before that line.

**Severity:** minor. **Estimate:** 55m (clock reset and caller wiring 20m; behavioral tests 15m; sibling controls 5m; Simplify 5m; live replay and cleanup 10m). **Status:** inbox. Source: continuous functional `$qa-find-bugs w4`, pass a497, 2026-10-15 UTC, signed in through the canonical helper with muse.env. Goal: usable hosting diagnostics under ADR008 and truthful readers under ADR010/ADR018. This filing contains no product implementation.

## Reproduction and exact evidence

Create an owned Free image cron job with BusyBox 1.37 and schedule `0 0 1 1 *`. The complete commands, native mutations, selected GraphQL requests and full responses are in [306-paused-log-search-cutoff.json](evidence/306-paused-log-search-cutoff.json). Fixture: `srv-db8297gumfhs73fe7gsg / qa-20261015-a497-search`.

1. Fresh-load its ordinary `/services/{id}/logs` page with All logs, Last hour, empty search and Live enabled. Leave that document open.
2. Trigger its twelve-second command from an Events page in a second tab. It prints five distinctive lines three seconds apart. Wait until the final line is visible in the original Logs page.
3. Turn Live off. The already visible lines correctly remain. Search the distinctive literal-line marker immediately, before the next relative history clock tick.
4. The line disappears and the settled page says **No matching logs / No logs match these filters**, although the paused page just showed that line. An otherwise identical read with only `endTime` advanced to the current time returns it.

## Cause and bounded fix

Research HEAD **6255ed8b2**, pulled successfully before filing:

- `dashboard/src/features/logs/components/log-viewer.tsx:95–112,117–128` commits text/path after the existing debounce and constructs the committed filter predicate.
- `log-viewer.tsx:173–181` asks `useLiveRange(range)` for history bounds without including the changed predicate.
- `dashboard/src/features/metrics/hooks/use-live-range.ts:25–35` samples a fresh clock only when the range's span/resolution selection changes. `:37–46` advances it on the preset timer. Last hour uses **30 seconds** (`features/metrics/lib/range.ts:18`); changing search leaves that selection unchanged.
- `dashboard/src/features/logs/hooks/use-log-history.ts:82–90` sends the new text with those old bounds unchanged. Both actual UI requests show this pairing.
- `dashboard/src/features/logs/hooks/use-live-logs.ts:163–180` correctly clears its retained buffer when text changes, including while paused, to prevent obsolete-filter rows. A pause alone preserves it. `log-viewer.tsx:183–198` keeps the paused transport disabled, so there is no replacement stream to cover the gap.

**Target:** the first history query for a newly committed service-log predicate in a relative range must end at that commit's current clock sample, with the preset's existing span and resolution. A just-observed matching in-window line is searchable immediately after pause, without reload or waiting for the timer. The stored timestamp remains authoritative.

Add a small optional reader identity to the existing `useLiveRange` selection/reset mechanism and pass a stable identity derived from the service resource and **committed** filter values at the LogViewer call site. Omitted identity preserves the existing metrics behavior. Resample during the render that observes the new identity, before `useLogHistory` constructs its query; an effect after a stale first request is insufficient. Include the identity in timer restart bookkeeping so each filter commit owns one cadence. Absolute Custom bounds remain exactly fixed and arm no timer, even when filters change.

Keep debounce, literal/display matching, reader clearing, URL adoption and writes, paging/cursors, lower-bound pruning, precision, loading/error states, pause retention and replay dedupe. Do not keep stale unfiltered rows as results, force route remounts, reopen SSE on clock ticks, shorten every preset timer, advance on each keystroke, or change API/storage time semantics. Before the new predicate settles, keep the current truthful loading state; show a no-match state only for its completed read.

## Implementation (2026-10-15)

**Status:** blocked on the post-deploy live replay. `useLiveRange` takes an optional `resetKey`; a changed key is a new selection, so the render that sees it samples the clock and restarts the one cadence (custom ranges ignore it). LogViewer passes `JSON.stringify([resource, queryFilters])` — committed values only, so drafts, URL echoes and live appends do not resample. The two metrics callers omit it and keep their behavior. Regressions: `log-viewer.test.tsx` "LogViewer search committed while paused (w4/306)" (pause at T0+10s, commit at T0+15s → every query for the search ends at T0+15s; next tick at T0+45s; clear/resource/structured-filter resample; drafts and no-op rerenders don't; Custom stays fixed) fails 3/4 without the fix; `use-live-range.test.tsx` covers the key and the fixed Custom window. Dashboard `yarn lint` green; full `yarn test` 4961/4962 with one unrelated `deploys-history-filters` test that passed 3/3 in isolation.
