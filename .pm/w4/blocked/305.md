# Cron run-detail loading does not preview its five-field responsive layout

Why: expanding a run should preserve the detail panel's structure and bounds while its fresh read resolves, so the table does not grow or change header wrapping when the same run arrives.

- **Severity:** minor. The query succeeds and the settled status, timestamps, duration and run ID are correct. The defect is the loading layout.
- **Estimate:** 55m — shared field-layout correction 15m, caller and cached/error controls 10m, Render parity 5m, Simplify 5m, meaningful browser geometry coverage 15m, live closeout 5m. Keep this as a sub-hour inbox note.

## Source trace and bounded fix

- `dashboard/src/features/services/components/cron-runs-section.tsx:287–295` adds the expanded row with `colSpan={4}`. Its sole `CronRunDetail` mount passes only service/run IDs even though the parent history row already has the run's status and timing.
- `cron-runs-section.tsx:382–384` returns one `h-16 w-full` Skeleton during the first unresolved read. It has no field labels, grid columns or intrinsic content widths.
- `cron-runs-section.tsx:393–408` renders the five-field `dl` with two columns below `sm`, four above it, horizontal gap 24 pixels and vertical gap 4 pixels. `DetailField:413–424`, the status badge, `absoluteTime:360–365` and `duration:79–88` determine the actual font, line-height and wrapping. The measured ready height is data/locale/width dependent.
- `dashboard/src/common/components/ui/table.tsx:5–15,66–85` supplies the normal automatic table layout and cell padding. The preview must preserve the detail's intrinsic sizing so the existing header columns do not change at settlement.
- `dashboard/src/features/services/hooks/use-cron-run.ts:26–43` already distinguishes fresh loading from existing data, uses the unchanged `cronJobRun(serviceId,runId)` read and preserves status/timing. This is a view correction, not an API or polling correction.

Render the pending state through the same field frame, typography and responsive columns as the ready state. Prefer passing the already-known history run into a small shared field presenter solely to size masked placeholders: its localized dates, duration, badge footprint and wrapped ID can reserve the exact existing shape without displaying them as a freshly verified detail. Keep placeholder sizing content hidden from assistive technology and show a truthful loading affordance. The fresh detail read remains authoritative, including its current explicit error state. Use the existing formatters and gap/padding classes in both states rather than copying a second layout contract.

Do not replace 64 with hard-coded 82/202 heights, approximate mobile date/ID line counts, change ready wrapping/fonts, invent a resolved status, seed or suppress the detail query, or change table, cache, polling, history, trigger or cancel behavior. A fixed height cannot represent the running/canceled/other-locale cases.
