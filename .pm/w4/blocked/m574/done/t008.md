## Objective

Put t001–t005 on the sandbox pool. Build `runsc` and `containerd-shim-runsc-v1` from the fork's release branch carrying them, and publish both as `bex-co/gvisor` release `release-20260622.0-bex.2`, outside git (root `AGENTS.md`, no build artifacts in git). Pin their sha512 digests in the machine template, and roll the pool. If a stock gVisor release already carries every fix, pin that instead.

## Context

- w4/m545 t003 did the same for `release-20260622.0-bex.1`: fork run [44955648773](https://github.com/bex-co/gvisor/actions/runs/44955648773) built both binaries with `make copy`. Its milestone README, § Record 2026-11-21, lists the steps.
- The pin lives in `infra/clusterapi/overlays/hetzner-caph/sandbox-pool.yaml`: the comment at ~:250-256, `GVURL`, `RUNSC_SHA512` and `SHIM_SHA512` at ~:269-271. `scripts/clusterapi-validate.sh` accepts a `bex-co/gvisor` `release-<version>-bex.<n>` URL.
- CAPI reads a machine template only when it creates a machine, so the change lands with a pool roll. Follow `infra/clusterapi/overlays/hetzner-caph/README.md` and roll surge first:
  1. Apply the KubeadmConfigTemplate, checking with `kubectl diff` that only the URL and digests change.
  2. Scale up, and check the new node's `sha512sum` and `runsc --version`.
  3. Cordon the old node and let its sandboxes end. Never cut off a running session.
  4. Mark the old machine `delete-machine` and scale back.
- Production access: `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>` (root `AGENTS.md`).
- `.github/workflows/sandbox-runsc-pty.yml` runs t006's extended probe against the new pin on the PR or push that changes it.

## Steps

1. Build, publish and record the digests.
2. Update the pin and its comment, then run `scripts/clusterapi-validate.sh` and the sandbox-runsc-pty check.
3. Roll the pool. Then `scripts/capi-template-drift.sh` reports no drift.
