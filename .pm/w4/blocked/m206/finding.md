# Scoped group creation traps its name; two-group moves report timeout after changing placement

**Severity:** major. **Source:** functional dashboard QA a385, 2026-10-13 UTC. **Research main:** 13d45c32e. Filing only; no product implementation.

## Reproduction and observed outcomes

Owned project `prj-db79rl2kvq8s73cjhupg` had Left `evm-db79rlikvq8s73cjhuqg` and Right `evm-db79rttoe3vs73aemrb0`. Both groups were empty and unlinked. Every native operation and the authoritative before/after queries are preserved in [evidence.json](evidence.json), under `receipts`.

1. Env Groups → New Environment Group: name `qa-20261013-a385-first`, Environment = project / Left, no vars/files/services. Create returned HTTP 200 with whole-operation `data:null`, `QUERY_TIMEOUT` at 21:10:25.702Z. A complete owner list omitted the name. Fresh-page retry at 21:13:46.554Z returned the same timeout and another complete owner list still omitted it.
2. Human-paced retry at 21:22:58.760Z was a single-operation CreateEnvGroup batch. It returned field-level `ENV_GROUP_NAME_EXISTS` after 24.128099s, without an ID. Complete owner lists at 21:24:45, 21:28:02 and 21:44:06 still omitted it. After deleting the visible control groups, the same name at Workspace scope returned that conflict again at 22:07:02.632Z (16.147s wall time). It was unavailable without a discoverable object. The physical reservation and original failure stage were not directly inspected.
3. Workspace-scope empty creation passed for `evg-db79vcqioh8c7395esbg` and `evg-db7a63doe3vs73aemrkg`. The second creation measured 17.581524s. Manage → Move group into Left passed separately in 9.191790s and 8.730122s. These separate control timings are not a stage profile of the failed scoped create.
4. In Left, select the first group → search “second” → select all visible → clear search. Both groups remain selected: this control passed.
5. Move both to Right through the project table. Native SetEnvironmentEnvGroups requested exactly both IDs for Right and returned whole-operation QUERY_TIMEOUT in 25.268932s at 21:40:04.361Z. Fresh authoritative placement at 21:44:06.862Z had the first in Right and second in Left. The ready source UI contained one row but “Selected: 2” and enabled Move.
6. Reunite the first in Left with one successful native Move group (9.584323s). Fresh-load at 390×844, select both and repeat the bulk move. It again returned whole-operation QUERY_TIMEOUT in 25.227802s at 21:57:35.075Z. By the later read at 22:00:48.860Z **both** were in Right and Left was empty; the mobile UI also showed empty Left. This is a failed acknowledgment of a completed move, not a second observation of the desktop split.

Expected: a small valid create/move finishes within the existing transport budget. An interrupted write has an honest discoverable outcome; a failed creation cannot reserve a name that the customer cannot find or delete. A timed-out move must reconcile authoritative placement before retry and reflect remaining source selections.

## Source trace and bounded correction

- `lego/backend/internal/api/graphql_cost.go:30–39` keeps execution at 25s, inside the 30s HTTP WriteTimeout; `api/server.go:1549` applies it. `server.go:1592,1619–1624` maps the deadline to QUERY_TIMEOUT with log-search guidance, even for these writes.
- The pinned `github.com/graphql-go/graphql v0.8.1` (`lego/backend/go.mod:16`) `executor.go:52,86–90` runs execution in a goroutine and can return a new whole-operation context error before that worker finishes. Thus `data:null` is not evidence of no writes or completed compensation. The actual dependency code was opened.
- `api/server.go:827–833` validates a group's environment owner by calling `environments.Service.Get`. `environments/service.go:526–538,1282–1306,1354–1359` authorizes and composes a full view, including all three datastore/group membership indexes, just to obtain OwnerID. Both create and every individual move use this callback (`envgroups/service.go:514,764,2087`). Replace this internal owner lookup with a narrow authorized lookup sharing existing scoping/row validation; keep full Get's public response and authorization. Measure stage timings before claiming this work explains all latency. Do not globally increase deadlines or remove the write margin.
- `envgroups/service.go:536–551` claims a minted ID/name before persisting. A claim error returns directly, whereas a persist error joins an owned release using an uncanceled context; post-commit view failure returns an error. `service.go:1716–1745` rejects a nonempty different claim owner without checking its operation outcome. `releaseGroupName:1748–1765` clears only the expected ID with CAS. `secrets/store.go:246–278,440–450` uses context-bound HTTP for CAS: an error is not itself proof the backing write did not commit. The confirmed structural gap is lack of owned recovery on the claim-error branch; whether the live residue arose there, from failed release, or another interrupted boundary remains unverified. Trace and recover the operation, with bounded compensation/fencing; never reclaim an apparently absent object's name while its creator might still be active, and never delete a committed group merely because response hydration failed.
- `environments/service.go:1022–1072` prevalidates all requested IDs, then mutates changed memberships serially and returns immediately on an error without compensating earlier members or returning partial status. Its group join (`:383`) calls SetEnvironmentID → MoveEnvGroup, which repeats owner/full-view work; successful completion hydrates another full environment view. This explains the ability to leave partial placement, while the exact slow stage was not profiled. Keep the full-replace contract, preserve target members passed by the caller, and define an owned, fenced consistent outcome or an explicit recoverable partial outcome if compensation is superseded.
- `dashboard/src/features/environments/hooks/use-set-environment-env-groups.ts:20–51` catches the error and returns false. `components/environment-card.tsx:133,210–263` retains every selected key unless that kind reports success; after polling removes one source member, its selected key survives. Reconcile source and target on uncertain writes, show that outcome, and prune only IDs proven absent from ready **canonical membership**. Do not prune the search-filtered rows or empty data during loading. Keep the pre-settle view marked as reconciling, with Move unavailable until the placement read settles; a read failure must retain retry-by-read and must not blindly resubmit.
- `dashboard/src/features/env-groups/hooks/use-env-groups.ts:213–239` requires a returned created ID before navigation and keeps the error path. Any recovery response must actually satisfy that predicate or explicitly describe a recoverable outcome. EnvGroupView consumers also use content revision/availability; do not replace a full response with guessed defaults.
