## Objective

Give initial group/name admission a recoverable outcome when a write may commit before acknowledgment or compensation fails. Resolve the exact owned failed-name residual through the same ownership checks; do not clear an active creator's reservation.

## Context

- Create's claim-error branch returns before the release used for persist errors. Physical live residue and failure phase were not directly inspected.
- claimGroupName has three direct callsites; Clone shares authorized creation.

## Steps

1. Trace the original blocked name's claim owner and final operation state using the existing store boundary in the implementation/recovery workflow.
2. Handle committed-CAS-with-error, persistence failure and post-commit response failure distinctly; use expected-ID/version compensation and bounded recovery where cleanup fails.
3. Retain or recover a discoverable committed group; release only the proven failed attempt's reservation. Record exact qa-20261013-a385-first disposition.

## Acceptance criteria

- [x] Failed or uncertain create cannot leave an invisible unowned-by-customer duplicate conflict without actionable recovery.
- [x] Retry yields one discoverable group; true duplicates and newer/active claim owners are preserved.

## Out of scope

- Broad production claim sweeps, lease expiry as sole proof of abandonment, forced unlock endpoints and deletion of a committed group solely for a lost response.

Done 2026-10-13: `claimGroupName` (`envgroups/service.go`) now (a) writes `claimedAt` with each reservation; (b) on finding another id's reservation, keeps `ENV_GROUP_NAME_EXISTS` when that group exists, and otherwise refuses with `ENV_GROUP_NAME_RESERVED` + `retryAfterSeconds` until two minutes have passed, after which the next create or rename takes the name over by CAS; an undated older reservation is dated at first sighting rather than reclaimed on sight; (c) releases the reservation before returning when its write failed for any reason but a lost CAS. Create, rename and Blueprint group creation share this through the one function; clone reaches it through create. Fencing is by time bound (every request path ends well inside two minutes), not by a token: a creator stalled longer than that between reserving and writing metadata is not detected. The production residue was not touched; with this deployed it frees itself through the same rule (one refused attempt dates it, a retry two minutes later succeeds) — to be confirmed in t008.
