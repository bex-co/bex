## Objective

On pin `f4f12981e455`, which carries t008's fallback route, a new web service's host behaves as this milestone promises **before** its first `200`. It answers bex's `503` first-deploy text with no raw `404`, and the first `200` came 15 s after create. **After** the deploy records `live`, though, requests are not answered as they arrive. Each one is held for 2–16 s, and they complete in bursts about 20 s apart. This lasts about 35 s in one sample and about 2 minutes in another, then latency drops back to 1–3 s from the probe host. The deploy has been `live` throughout. A client with a 5 s timeout (health checkers, CLI smoke tests) sees failures for minutes after "Your service is live 🎉". Target behavior: from the moment the deploy is `live`, every request is proxied to the app without a hold, as on Render, where a live service answers immediately. Any remaining first-deploy routing must hand over at or before promotion.

**Severity:** major (a just-deployed service's first callers time out or wait up to 16 s with the service `live`). **Source:** live `/qa-find-bugs w4` loop run 0dbc, 2026-10-27 UTC (`muse.env`, workspace `tea-daif693dqjvc73e7as3g`, pin `f4f12981e455` incl. `8ba87e838`, m243 t007/t008; m243 t009's activator port fix `5dbd5fe20` is **not** in the pin).

What the code rules out (not a cause):

- The activator's own hold timing does not produce 16 s waits that end in `200`. It polls readiness every 0.5 s (`cmd/activator/hold.go:49`) and redials every 250 ms (`:57`). Pin `f4f12981e` still has the pre-t009 `ServingPort()` dial (10000 for image-port apps), which would end in `502` after 90 s, not a late `200`.
- Candidates to check with cluster access: when the operator replaces t008's fallback and first-deploy route with the app's own Ingress, relative to `live`, and how Traefik applies it (provider throttle), which could produce the ~20 s burst cadence; the hold handler's handover path for a request that arrived before promotion; and whether the activator can see the image-port Service.

## Unverified

- The mechanism. All three samples are image-port services. A configured-port or native web service was not sampled.
- Whether the old pin `b4726243e74f` had the same post-live hold. In run 828c, 08:17Z, one 15 s-cadence probe got `200` on its first try after `live`, which is not conclusive.

**Narrowed 2026-10-28 (loopx w4), read-only production observation (`hetzner-prod`, Loki access logs, no writes):**

- **The hold is not in the activator, the app, or Traefik's proxying.** Loki's Traefik access log for `qa-20261027-0dbc-thr` has every post-live request served directly by the app's own Service (`…-qa-20261027-0dbc-thr-80@kubernetes`) with `Duration` 1.6–6.4 ms. That includes the requests the client timed at 14–16 s, so the wait is spent **before Traefik reads the request**: TCP accept, the load balancer's PROXY protocol, or the TLS handshake.
- **Requests never reached Traefik at all.** For `qa-20261027-0dbc-who`, the client's `curl -m 5` probes every 3 s from 10:26:11 all timed out. Traefik logged **no** request for that host until 10:27:16, then five quick `200`s.
- **Ruled out:** DNS (`*.onbex.co` is a Cloudflare wildcard `A 49.12.20.236`, TTL 300, so no negative caching of a new name). Steady-state edge latency: today `connect ≈ 0.2 s`, `TLS ≈ 0.45 s` for both an unknown host and a live one.
- **Leading hypothesis (unverified):** a new host's first minutes coincide with cert-manager's HTTP-01 issuance for `<app>-tls-<host>`. Traefik's TLS handshake for that SNI, or its config reloads as the solver Ingress, Service and Secret come and go, stalls new connections. cert-manager's and Traefik's own logs are not shipped to Loki, so the issuance timeline could not be read for the deleted fixtures.
- **Separate finding, fixed in this same commit:** t008's fallback Ingress was never present in production. The `bex-operator-object-namespaces` admission policy refuses operator Ingress writes in `bex-system`. It is now a platform manifest (`lego/operator/config/activator/platform-host-fallback-ingress.yaml`), so it was not a factor in these samples either.
- **Blocked:** the live reproduction needs a fresh web service fixture while watching `kubectl get ingress,certificate,secret -w` and Traefik's own log. This checkout has no QA credentials (`scripts/qa-login.sh` exits "QA_EMAIL/QA_PASSWORD are unset or empty"). A QA session with credentials, or the user, must run step 1 with those watches.

**Live re-probe on pin `d368e383fcb1` (`/qa-find-bugs w4` run 4513, 2026-10-28, contains `1f215572f`, the fallback route shipped as a manifest).** A new `docker.io/traefik/whoami:latest` web service (`srv-dbgndtnc6ors73at0vs0`) was created at 04:15:50Z, its deploy went `live` at 04:16:09Z, and it was probed with a 3 s cadence of parallel `curl -m 120 -H 'Accept: */*'`. The two pre-200 answers (04:15:58, 04:16:01) were bex's `503` "This service's first deploy is …", with no raw `404`. The first `200` came at 04:16:04, 14 s after create. **All 38 requests from 04:16:04 to 04:17:55 answered `200` in 0.51–0.77 s.** No request was held, and the ~20 s burst cadence did not recur. This meets the acceptance criterion "every request that started after `live` answered in under 3 s, for 2 min". The root-cause criterion is still open; the `1f215572f` route fix is the likely cause, since the operator could not write the fallback route before.
