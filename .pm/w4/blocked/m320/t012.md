## Objective

A second image deploy can supersede the first after the first already answers every request but before its row reads `live`. Today that closes the first release `canceled`, puts an older release back, and drops requests. The target: the first release is the one that served, so its row closes `live`, the second deploy rolls forward from it, and no request fails. This is ADR018's w8/m119 invariant, "A `canceled` row's release never served".

  - `dep-dbqhl72v3e1c73bps6sg` (1.27, 01:47:08) answered from 01:48:34.
  - `dep-dbqhm0iv3e1c73bps6vg` (1.25) was hooked at 01:48:49.
  - Polls every ~9 s: `1.27.5` at 01:48:56 and 01:49:05, then **`503` at every poll from 01:49:13 through 01:50:06**, then `1.25.5` from 01:50:14.
  - Here the first row closed `live` (finishedAt 01:49:19), which shows w4/405's early stamp did run.
- **Mechanism (partly traced):**
  - w8/m119 holds a newer release until the executing one "serves (recorded in `status.activeRevision`)" (ADR018 deploy-objects row). The planner's predicate is `releaseHasServed` = `ActiveRevision != ""` (`release_identity.go:553-555`).
  - That stays true for the **older** live revision during the whole rollout.
  - The early stamp that would name the executing release (`app_controller.go:3764-3779`, w4/405) skips any release where `routesEarly(app)` holds (`image_network.go:373-375` → `webImageReleaseHeld`, `web_image_http.go:72-76`), which is every image change on a web service that discovers its port.
  - It also needs `currentRevisionFullyReady`. So after promotion moves the Services, and until a later pass stamps it, the release that holds all traffic is not recorded as served. A supersede in that window is treated as superseding an unserved release: the row closes `canceled`, and the prior snapshot is restored (`settleCanceledRelease`, `app_controller.go:796`).
  - **Not traced:**
    - why the planner adopted B2/C2 at all instead of holding them while B1/C1 rolled;
    - what removed every ready endpoint in Run 0 for ~55 s. One hypothesis: the restore pinned the Services to a prior revision whose pods were already drained, but the Service selectors during the window were not captured.
  - The round 121 probe above measured the same window (row `update_in_progress` ~24 s after the switch). This task is the user-visible cost of that gap when a second deploy lands in it.

## Steps

1. Reproduce on the mock cluster with an image web service and no port:
   - hook a tag change;
   - when the poller first sees the new version, hook another tag;
   - capture `status.activeRevision`, `servingNetwork`, `imageNetwork`, the Services' selectors and the endpoints each pass.
2. Make the release that holds all traffic count as served at promotion. The pass that moves the Services also stamps its revision active, or the planner's hold reads "the executing release answers traffic" rather than `ActiveRevision != ""`. t004's "reads `live` in the same pass" is the same fact; if t004 lands it, this task verifies and adds the supersede tests.
3. A deploy that supersedes a promoted release rolls forward from that release's pods, as a deploy from a settled live release does (the control above). No prior-release restore and no selector move to a revision without ready pods.
4. Keep t003's guarantee: a release superseded or canceled **before** promotion still never answers, and the prior release keeps its pods.
5. Tests (operator envtest plus the store reconciler):
   - supersede after promotion → first row `live`, then `deactivated`; no restore; Services never select a revision with zero ready pods;
   - supersede before promotion → first row `canceled`, the prior release keeps serving;
   - same-image and port-changing rollouts (w4/428) are unchanged.

## Acceptance criteria

- [ ] On production, with the poller above, Runs B and C repeated (second hook 5 s and 12 s after the first new version answers) give:
  - every poll `200`;
  - versions moving only forward (old → first → second, never back to an older one);
  - the first deploy's row `live` and then `deactivated`, not `canceled`.
- [ ] A hook cancel-before-promotion (this milestone's Run B) still never shows the candidate's version.
- [ ] The control (a deploy from a settled live release) stays error-free.
