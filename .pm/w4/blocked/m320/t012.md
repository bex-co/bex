## Objective

A second image deploy can supersede the first after the first already answers every request but before its row reads `live`. Today that closes the first release `canceled`, puts an older release back, and drops requests. The target: the first release is the one that served, so its row closes `live`, the second deploy rolls forward from it, and no request fails. This is ADR018's w8/m119 invariant, "A `canceled` row's release never served".

- **Mechanism (partly traced):**
  - w8/m119 holds a newer release until the executing one "serves (recorded in `status.activeRevision`)" (ADR018 deploy-objects row). The planner's predicate is `releaseHasServed` = `ActiveRevision != ""` (`release_identity.go:553-555`).
  - That stays true for the **older** live revision during the whole rollout.
  - The early stamp that would name the executing release (`app_controller.go:3764-3779`, w4/405) skips any release where `routesEarly(app)` holds (`image_network.go:373-375` → `webImageReleaseHeld`, `web_image_http.go:72-76`), which is every image change on a web service that discovers its port.
  - It also needs `currentRevisionFullyReady`. So after promotion moves the Services, and until a later pass stamps it, the release that holds all traffic is not recorded as served. A supersede in that window is treated as superseding an unserved release: the row closes `canceled`, and the prior snapshot is restored (`settleCanceledRelease`, `app_controller.go:796`).
  - **Not traced:**
    - why the planner adopted B2/C2 at all instead of holding them while B1/C1 rolled;
    - what removed every ready endpoint in Run 0 for ~55 s. One hypothesis: the restore pinned the Services to a prior revision whose pods were already drained, but the Service selectors during the window were not captured.
  - The round 121 probe above measured the same window (row `update_in_progress` ~24 s after the switch). This task is the user-visible cost of that gap when a second deploy lands in it.

## Steps

1. Reproduce on the mock cluster with an image web service and no port:
   - hook a tag change;
   - when the poller first sees the new version, hook another tag;
   - capture `status.activeRevision`, `servingNetwork`, `imageNetwork`, the Services' selectors and the endpoints each pass.
2. Make the release that holds all traffic count as served at promotion. The pass that moves the Services also stamps its revision active, or the planner's hold reads "the executing release answers traffic" rather than `ActiveRevision != ""`. t004's "reads `live` in the same pass" is the same fact; if t004 lands it, this task verifies and adds the supersede tests.
3. A deploy that supersedes a promoted release rolls forward from that release's pods, as a deploy from a settled live release does (the control above). No prior-release restore and no selector move to a revision without ready pods.
4. Keep t003's guarantee: a release superseded or canceled **before** promotion still never answers, and the prior release keeps its pods.
5. Tests (operator envtest plus the store reconciler):
   - supersede after promotion → first row `live`, then `deactivated`; no restore; Services never select a revision with zero ready pods;
   - supersede before promotion → first row `canceled`, the prior release keeps serving;
   - same-image and port-changing rollouts (w4/428) are unchanged.

## Round 157 addendum (2026-11-12 02:10–02:19 UTC): first deploys too, and a regression of w4/405

- **The same close on a service's first deploy, with no image change and no older release.**
  - Free web service `qa-20261112-r157-race` (`srv-dbqi2viv3e1c73bps7sg`), from `docker.io/library/busybox:1.37.0`, Docker Command `sh -c '… exec httpd -f -p 10000 -h /tmp/w'`, no port. Created 02:16:30.
  - Its first deploy `dep-dbqi2viv3e1c73bps7t0` first served `200 qa157-race` at 02:17:57. In the same second, `POST /v1/services/srv-dbqi2viv3e1c73bps7sg/deploys {}` returned `201 {"id":"dep-dbqi3lav3e1c73bps7u0",…,"status":"queued","trigger":"api"}`.
  - At 02:18:19 the first row read `canceled`, and the new one `update_in_progress`. The new one read `live` at 02:19:03.
  - The URL answered `200 qa157-race` on every poll throughout, so the canceled release served for ~20 s.
  - **Control:** an untouched first deploy (`qa-20261112-r157-first`, `srv-dbqi27av3e1c73bps7qg`) first served at 02:15:42 and read `live` at 02:16:02.
- **When the second deploy fails, the service has no live row at all.**
  - `qa-20261112-r157-crash` (`srv-dbqi09djiris73e60tm0`, same image) first served `qa157-v1` at 02:11:50, and its first deploy `dep-dbqi09djiris73e60tmg` was still `update_in_progress` at 02:12:36.
  - Settings → Edit Docker Command → `sh -c '…; exit 3'` → confirm ("The service redeploys with the new command") at 02:12:27. That queued `dep-dbqi12qv3e1c73bps7og` (`service_updated`).
  - At 02:13:02 the first row closed `canceled` (`deploy_ended` reason `{"newDeploy":{"id":"dep-dbqi12qv3e1c73bps7og"}}`). The new one closed `update_failed` at 02:13:48, with a clear reason: "container exited shortly after start and is restarting repeatedly (last exit code 3) …".
  - The URL served `200 qa157-v1` on every 3 s poll from 02:12:23 to 02:13:57. Yet REST `phase` reads `Failed` and the dashboard header reads "Service Failed" with "Latest deploy: Failed". The Deploys tab lists only `Failed …` and `Canceled … Superseded by …`.
  - So the release users are getting has no live row and no Rollback action, and the user can't roll back to it.
- **Mechanism, now traced at both ends:**
  - `releaseInFlight` (`lego/operator/internal/controller/release_identity.go:374-397`) never pins a prebuilt-image release ("have no build to protect"). A newer deploy is adopted mid-rollout on any image service.
  - The backend then closes the superseded row `live` only if `servesGeneration` holds, i.e. `status.activeRevision` names it (`lego/backend/internal/store/reconciler.go:1855-1865`). Otherwise it closes `canceled`.
  - w4/405 (done 2026-10-25) added the operator's early stamp (`app_controller.go:3764-3779`) precisely so a release whose pods all serve is named before a supersede. Today it is not named within ~20 s of serving.
  - **Not traced:** whether the stamp's `currentRevisionFullyReady` or its `routesEarly` exclusion (both on that line) is what misses a first deploy.
- **Regression walk of w4/405's target:**
  1. "A release whose pods served traffic is recorded `live` and then `deactivated` … Only a release that never served closes `canceled`" **fails**: three rows here and two in round 156.
  2. "The Events feed should then show A's `deploy_ended` as `succeeded`" **fails**: it reads `canceled` with `newDeploy`.
  3. Its test (served-then-superseded image release ends `live` → `deactivated`) evidently passes in envtest, and live disagrees. Re-check what the fixture stubs (Ready pods vs. the Service's endpoints).
