## Objective

On Render, traffic moving to the new instance and the deploy becoming live are the same event. Make them one event in bex too. When the operator knows the Service routes only to the current revision, the deploy row closes `live`, and the dashboard's Cancel is no longer offered.

## Context

- **Control probe.** On a same-image redeploy, the instance switched at 19:14:35 and the row turned live at 19:14:59: a 24 s lag.
- **Operator.** It reports `RolloutSettling` ("current revision fully ready; Deployment status still converging") and records `activeRevision` early (w4/405), but keeps phase `Deploying` (`lego/operator/internal/controller/app_controller.go:3706-3715`).
- **Backend.**
  - It counts `RolloutSettling` as serving for availability (`lego/backend/internal/store/reconciler.go:2210-2216`).
  - It closes a superseded row `live` through `servesGeneration` (`:1752`, `supersededDeployStatus` `:1760`).
- **Unverified:** which write closes the row 24 s later. Candidates: Deployment status convergence (`deploymentRolloutReady`, `app_controller.go:4096-4102`), the requeue cadence, or the backend reconcile period. Trace it first.
- w4/405 accepted the gap as "serving itself is correct". This task amends that against Render's sequence.

## Steps

1. Trace which write closes the row.
2. Close the row `live` when `activeRevision` names the current release and the Service routes only to it. Keep old-pod reap as bookkeeping, not as a deploy state.
3. Test: a settling rollout closes its row `live` without waiting for the old ReplicaSet's reap.

## Files

- `lego/operator/internal/controller/app_controller.go`
- `lego/backend/internal/store/reconciler.go`

## Acceptance criteria

- [x] In the same-image control, the row reads `live` within one poll of the instance switch.
- [x] Availability events (`server_failed`/`server_available`) don't change for a settling rollout (w3/m78).

## Out of scope

- Disk-backed (Recreate) services, whose downtime is the deploy's to report.

## Result (2026-11-11)

- Traced: the backend closes a row `live` only on `PhaseRunning` (`observedDeployStatus`, `lego/backend/internal/store/reconciler.go`), which the operator writes once the Deployment status converges (`deploymentRolloutReady`, after the old pods' reap). Meanwhile it reports `RolloutSettling` with `activeRevision` already naming the release (w4/405). That reap-and-requeue is the 24 s gap.
- bex-api now closes the row `live` at the first `PhaseDeploying` pass whose Ready reason is `RolloutSettling` and whose `activeRevision` names this release (`releaseIsActive`). Availability is unchanged (w3/m78 already treats settling as serving).
- The operator records `activeRevision` early only for a rollout that does not route early (`!routesEarly`), so a held web image release or an unpromoted port change never reads live while traffic is still on the old revision.
- Tests: `TestASettlingRolloutThatServesItsReleaseIsLive` (store), `TestRolloutProgressLeavesAHeldWebImageReleaseInactive` (operator).
