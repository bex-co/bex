## Objective

While a web image release's HTTP selection is pending and an earlier release serves, the public and private Services select only the serving revision's pods. A Ready candidate takes no traffic. At promotion, routing moves to the chosen candidate in the same reconcile that records it as the serving release.

## Context

- `privateServiceProjection` (`lego/operator/internal/controller/image_network.go:306-345`) builds the selector of both serving Services. It adds `labelRevision` only when `changesImagePorts || replacedImagePorts` (`:316-325`).
- The port-change precedent is w4/428: `promotePortChangeEarly` (`image_network.go:433`) and `portChangeHoldSeconds`.
- The discovery hold is `MinReadySeconds = webImageHTTPSelectionHoldSeconds` (`deployment_projection.go:627-628`). It keeps the old pods running but doesn't keep the candidate out of endpoints.
- Discovery is pending when `webImageHTTPSelectionPending` holds; it guards serving when `webImageHTTPSelectionGuardsServing` holds (`web_image_http.go:44-56`).
- **Hazard from w4/m243 t012:** a pin during a rollout that drains the pinned pods leaves no ready endpoint. The pin is safe only while the hold keeps the serving pods, and t002 must keep it so.

## Steps

1. Add discovery-pending with a serving release to the conditions that pin `labelRevision` to the serving network's revision.
2. At promotion (`promoteImageNetwork`, `image_network.go:398`), move the selector to the candidate's revision in the pass that records it as serving. Old pods drain after that.
3. Envtest: during discovery the Services select only the serving revision, whatever the candidate's readiness. After promotion they select the candidate.

## Result (2026-11-11)

- `webImageReleaseHeld` (`lego/operator/internal/controller/web_image_http.go`): a web service whose image chooses its own HTTP port (`discoversWebImagePort`), with a serving network, whose candidate is still discovering or has a different image than the serving release. While it holds, `privateServiceProjection` (`image_network.go`) pins `labelRevision` to the serving revision on both Services (CR-named and slug, both written through `applyClusterIPService`), so a Ready candidate is never an endpoint.
- At promotion the release is routed early (`routesEarly` → `promoteEarly`, the w4/428 path, renamed from `promotePortChangeEarly`): the first Ready pod of the written (final) template moves both Services to the new revision in one write and records the replaced network in `status.priorServingNetwork`; the Services then pin the new revision (`promotedEarly`) until the rollout completes. A first deploy has no serving network and is unpinned as before.
