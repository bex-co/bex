## Objective

An image deploy that goes live reports the digest its reference resolved to, on its own row, on REST, GraphQL, MCP and the dashboard. w8/m122 (done) promised this, and production met it until this milestone's release. Since pin `f609163ada8e`, only deploys whose image digest doesn't change keep the guarantee: the first deploy, and a redeploy of the same image.

## Context

- **Found:** live `/qa-find-bugs w4` loop, round 133, 2026-11-11 19:53–20:06 UTC (`bex-canary`, pin `f609163ada8e`).
  - Fixture: Free image web service `qa-20261111-r133-rb` (`srv-dbqcfao3u30c73cf9cbg`), created from `docker.io/traefik/whoami:v1.10.1` with no port. Deleted afterwards.
- **Probes**, each a `GET /v1/services/srv-dbqcfao3u30c73cf9cbg/deploys` read 15–30 s after the row turned `live`:

  | Deploy | How | Image | `sha` |
  | --- | --- | --- | --- |
  | `dep-dbqcfao3u30c73cf9cc0` | create | `whoami:v1.10.1` | `sha256:6956a30c…72fe9` |
  | `dep-dbqcg0g3u30c73cf9cg0` | `POST …/deploys {"imageUrl":"…whoami:v1.10.0"}` | `whoami:v1.10.0` | **none** |
  | `dep-dbqch74tsr9c73d7vi9g` | `POST …/deploys {"imageUrl":"…whoami:v1.10.2"}` | `whoami:v1.10.2` | **none** |
  | `dep-dbqciqktsr9c73d7vii0` | `PATCH image.imagePath` to `…whoami:v1.10.0`, then a standard `POST …/deploys {}` | `whoami:v1.10.0` | **none** |
  | `dep-dbqckfebmqhc73f602pg` | `POST …/deploys {}` again (same image, the control) | `whoami:v1.10.0` | `sha256:31c5ef6f…b9080` |
  | `dep-dbqclj4q26jc739gcff0` | `POST …/rollback {"deployId":"dep-dbqcfao3u30c73cf9cc0"}` | ref `whoami@sha256:6956a30c…72fe9` (digest-pinned) | **none** |

  - GraphQL `deploys(serviceId:…){ imageSha }` agrees: `""` on the three image changes.
  - **The rollback row is the sharpest case.** Its `ref` carries the digest, yet it has no `sha`. In w4/531's probe (2026-11-06), a rollback row had `ref …whoami@sha256:6956a30c…` and `sha sha256:6956a30c…`. So this is not a pod read that failed: the digest exists in `status.image`, and the row closed before `recordImageDigest` ran.
- **Before this release:** w4/531's probe (2026-11-06) had an `imageUrl` override deploy of `whoami:v1.10.2` go live with `sha256:1474027c…5420`.
- **Mechanism (traced in part):**
  - **The row's sha is fixed when it closes `live`.** The close copies `status.imageDigest` for the row's own generation (`lego/backend/internal/store/reconciler.go:978`, `releaseImageDigest` `:1752-1758`). ADR004 § Deploy image digest: "Nothing is backfilled after the live close".
  - **The operator writes the digest late.** `status.imageDigest` is written only in `settleReady` (`lego/operator/internal/controller/app_controller.go:3445-3452`, via `recordImageDigest`, `image_digest.go`), which runs once the Deployment converges.
  - **t004 moved the close earlier.** bex-api now closes the row `live` on the first `PhaseDeploying` + `RolloutSettling` pass whose `activeRevision` names the release (`releaseIsActive`, `reconciler.go:1960-1965`). For a held web image release (t001), `activeRevision` is recorded at promotion. Both happen before `settleReady`, so the close finds no digest for its generation.
  - **Not traced:** why the same-image redeploy still gets its digest. Its rollout isn't held, so it may reach `PhaseRunning` before the backend observes the settling pass. Confirm this before choosing where the fix goes.

## Steps

1. Record `status.imageDigest` in the same status write that first names the release in `activeRevision`, from the pinned `status.image` digest or a Ready pod of the release's own template. That covers the promotion stamp (t001) and the `RolloutSettling` early record (`app_controller.go:3716-3722`, w4/405). The rule "a generation's digest never changes once recorded" stays.
2. Or, if step 1 can't see a Ready pod's `imageID` in that pass: let bex-api stamp `image_sha` onto a row that is already `live` when the operator later records the digest **for that row's own generation**, and amend ADR004's "nothing is backfilled". It must never copy another generation's digest.
3. Tests:
   - operator: a held image change records the digest of its release by the pass that promotes it;
   - backend: a row closed `live` in `RolloutSettling` carries the digest, or gets it afterwards, from its own generation only;
   - keep w8/m122's cases: a failed deploy has no digest, and a newer row never shows the previous release's.

## Acceptance criteria

- [ ] On an owned Free image web service:
  - `POST …/deploys {"imageUrl":"…whoami:v1.10.2"}` goes live with `image.sha` set;
  - `PATCH image.imagePath` followed by a standard deploy goes live with `image.sha` set;
  - the same-image redeploy still does.
- [ ] REST, GraphQL `imageSha`, MCP `get_deploy` and the dashboard deploy header show the same value.
- [ ] A deploy of a missing tag (`update_failed`) still carries no `sha`.
