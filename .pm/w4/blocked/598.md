# 598 — Does Render's `PUT /services/{id}/autoscaling` with `enabled: false` store the body's range and targets? bex keeps the old settings and ignores the body

Why: since w4/597 a disable keeps the autoscaling settings. bex treats `PUT` with `enabled: false` as `DELETE`: it keeps the old settings and ignores the body's `min`/`max`/`criteria`. If Render stores the body's values, a Render client that writes `{enabled: false, min: 2, max: 6, …}` (the Terraform provider, for one) reads back different values and shows a permanent diff.

- **Source / severity / estimate:** w4/597 `/simplify` review, `/loopx w4` 2026-11-11. **Minor** (API parity; only clients that send values while disabling). ~30m after the answer.
- **Gate:** Render's answer. Finding out takes a write on the reference account (`PUT …/autoscaling` with `enabled: false` and new values, then `GET /services/{id}`), and the read-only rule forbids writes.
- **If Render stores the body:** validate a disabled body as an enabled one is validated (bounds, at least one target), store it with `Enabled: false`, and answer with it. A body that is not a valid config keeps today's behavior. Create's `serviceDetails.autoscaling` with `enabled: false` gets the same rule (`apps/rest.go`, the create decode).
- **If Render ignores the body:** close this as already met.
- **Dedupe:** w4/597 (done; keeps the settings on a disable) and w4/595 (blocked on another write probe).
