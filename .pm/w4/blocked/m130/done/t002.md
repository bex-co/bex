## Objective

Apply t001's diagnosis so that `patchServiceEnvironment` returns success exactly when it wrote, and the conflict exactly when it did not.

## Context

- The correctness bar is two-sided and the DoD says so: suppressing the error is not a fix if the response still cannot describe the outcome. A caller must be able to distinguish "applied" from "refused" with certainty.
- The real-conflict behavior already works and must be preserved: a replayed or foreign revision is refused and writes nothing (verified live, `t2_replayStale` / `t3_otherKeysRev`).
- If t001 finds a concurrent writer, the likely shapes are: serialize the projection with the CAS write, take the derived-Secret claim out of the CAS-guarded path, or re-read and re-compare before classifying a `PutCAS` failure. Prefer whichever keeps the invariant at `batch.go:177-180` literally true.
- Do **not** reach for a blanket retry. A retry around a write whose outcome is unknown is how at-least-once duplication happens, and the value being written is a secret map, not an idempotent counter.

## Steps

1. Implement the fix t001's diagnosis indicates.
2. Preserve the unchanged-value case: `batch.go:177-186` deliberately advances the revision for a no-op CAS write and skips the App write and roll. Confirm that still holds.
3. Re-run the 20-iteration loop against a real store and record the failure count (must be zero).
4. Re-run the two real-conflict probes and confirm they still refuse and still write nothing.

## Acceptance criteria

- [ ] 20 consecutive read-modify-write iterations, zero errors, every value landed.
- [ ] A genuine stale-revision replay still returns the conflict and leaves value and revision untouched.
- [ ] The no-op CAS write still advances the revision without an App write or a roll.
- [ ] No retry introduced around a write with an unknown outcome.
