## Objective

Establish, by instrumentation rather than inspection, how `patchEnvironmentCAS` can return `ENVIRONMENT_REVISION_CONFLICT` for a call whose write is durably applied. Every other task depends on the answer, and the milestone README's "Where the cause is not" section already rules out the obvious readings.

## Context

- Observed: 8 calls with a freshly-read revision, 8 writes landed, 4 returned the conflict. Intermittent, ~50%, unaffected by 60s idle gaps.
- `envRevisionConflict()` has two call sites (`secrets/batch.go:139-146` pre-check, and the `PutCAS` failure branch). The pre-check precedes any write. `openBaoStore.PutCAS` has no retry; `kv()` retries only on 403.
- The sibling `patchEnvGroupEnvironment` is clean 4-for-4 — same protocol, same store. **The difference in work is the lead**: the service path additionally runs `projectCASEnv` (derived Secret claim) and `finalizeEnvironmentPatch` (App write + rollout); the group path does neither.
- `secrets/batch.go:177-180` states the invariant the protocol is supposed to provide: _"two submissions from one observed revision resolve to exactly one success and one conflict"_.

## Steps

1. Reproduce locally against a real OpenBao (the defect is intermittent and store-backed; an in-memory fake may not show it).
2. Log, per call: the `GetVersioned` version, the `expectedVersion`, the `PutCAS` result and the OpenBao HTTP status, and the stored version immediately after — so a write-that-landed-and-reported-conflict is visible in one trace.
3. Grep every writer of `envPath(service)` and list them with counts. Confirm whether `projectCASEnv` or `finalizeEnvironmentPatch` writes that path, directly or transitively.
4. If a concurrent writer is confirmed, determine whether it runs inside the same request or asynchronously, and whether it can interleave between this request's `GetVersioned` and `PutCAS`.
5. Also run the loop with `saveMode:"deploy"` and record whether the rate changes — the hypothesis predicts it should.
6. Write the conclusion into the milestone README under a "Diagnosis" heading before starting t002.
