## Objective

Establish, by instrumentation rather than inspection, how `patchEnvironmentCAS` can return `ENVIRONMENT_REVISION_CONFLICT` for a call whose write is durably applied. Every other task depends on the answer, and the milestone README's "Where the cause is not" section already rules out the obvious readings.

## Context

- Observed: 8 calls with a freshly-read revision, 8 writes landed, 4 returned the conflict. Intermittent, ~50%, unaffected by 60s idle gaps.
- `envRevisionConflict()` has two call sites (`secrets/batch.go:139-146` pre-check, and the `PutCAS` failure branch). The pre-check precedes any write. `openBaoStore.PutCAS` has no retry; `kv()` retries only on 403.
- The sibling `patchEnvGroupEnvironment` is clean 4-for-4 — same protocol, same store. **The difference in work is the lead**: the service path additionally runs `projectCASEnv` (derived Secret claim) and `finalizeEnvironmentPatch` (App write + rollout); the group path does neither.
- `secrets/batch.go:177-180` states the invariant the protocol is supposed to provide: _"two submissions from one observed revision resolve to exactly one success and one conflict"_.

## Steps

1. Reproduce locally against a real OpenBao (the defect is intermittent and store-backed; an in-memory fake may not show it).
2. Log, per call: the `GetVersioned` version, the `expectedVersion`, the `PutCAS` result and the OpenBao HTTP status, and the stored version immediately after — so a write-that-landed-and-reported-conflict is visible in one trace.
3. Grep every writer of `envPath(service)` and list them with counts. Confirm whether `projectCASEnv` or `finalizeEnvironmentPatch` writes that path, directly or transitively.
4. If a concurrent writer is confirmed, determine whether it runs inside the same request or asynchronously, and whether it can interleave between this request's `GetVersioned` and `PutCAS`.
5. Also run the loop with `saveMode:"deploy"` and record whether the rate changes — the hypothesis predicts it should.
6. Write the conclusion into the milestone README under a "Diagnosis" heading before starting t002.

## Production replay, pass 192 (2026-09-26, `/qa-find-bugs`, `muse.env` credentials)

Deployed code, live. The fixture was Free `ealen/echo-server` web service `qa-20260926-cas` (`srv-darrqpod0qnc73d79vi0`, `QA_CAS`), deleted the same pass. Loop per iteration: `service(id){ envVar(key:"QA_CAS"){ value revision } }` → `patchServiceEnvironment(saveMode, envVars:[{key:"QA_CAS", value}], expectedEnvRevision:<that revision>){ revision }` → read back.

- **The defect is still live and now far more frequent, under a different code.** With `expectedEnvRevision`, `save_only`: **18 of 20** calls errored, and **16 of those 18 landed their write anyway**. With `saveMode:"deploy"`: 3 of 4 errored, all 4 landed. The code is now **`ENVIRONMENT_RESTORATION_FAILED`** — _"the environment update failed and could not be safely restored; refresh before retrying"_ (t002's post-write compensation error) — not the old `ENVIRONMENT_REVISION_CONFLICT`. `data` is `null`, so the caller also loses the new `revision`.
- **Control: without `expectedEnvRevision`, 8 of 8 `save_only` saves were clean** and landed. The failure is specific to the CAS path, which is exactly t001's premise. The dashboard's `PatchServiceEnvironment` never sends the revision (`dashboard/src/features/services/api/env-vars.graphql:57-73`), so **dashboard saves are unaffected**. REST and MCP clients that pass the revision (MCP's schema advertises it) hit it.
- **When a call succeeds, the result `revision` is right:** the 2 clean iterations returned `revision` equal to the read-back revision (DoD bullet 4 holds on success).
- **Stale-revision guard holds:** replaying a superseded revision → `ENVIRONMENT_REVISION_CONFLICT`, with value and revision both unchanged (DoD bullet 3).
- **DoD bullets 1 and 2 fail live:** a correct read-modify-write loop does not succeed cleanly, and an error is returned for writes that landed.
- **Reading for t001:** "update failed, could not be safely restored" plus "value present" means some step **after** `PutCAS` fails on the CAS path (the README's lead is `projectCASEnv` / `finalizeEnvironmentPatch`), then the compensating restore also fails, or reports failure, while the new version stays current. That makes the restore's own CAS the next thing to instrument: restoring with the *pre-write* expected version against a store that has already advanced would conflict every time. A server-side trace of one failing call (bex-api logs for `patchEnvironmentCAS` around 2026-09-26 ~12:1x UTC) should confirm or refute this.
