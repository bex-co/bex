- **Fix:**
  - Each panel's loading state draws the frame that is present whatever the data:

    - Active sessions also draws one row, for the current session, which is always listed;

- **Regression: every direct load of `/settings` now throws React's hydration error #418.**
  - `pageerror: Minified React error #418 … args[]=HTML` fires on 4 of 4 direct loads, at 1440 and at 390.
  - It does not fire on `/` or `/workspace/settings` on the same pin.
  - It did not fire on `/settings` on pin `3c6654df60a2` (round 493's direct loads logged no page error).
  - React then discards the server HTML and client-renders the whole root. The client's `useId`s (`_r_0_`) replace the server's (`_R_3mklaq_`) in every section heading.
- **Cause:**
  - `ReservedText` (`dashboard/src/common/components/reserved-skeleton.tsx`) draws its bar with `<Skeleton>`, which renders a `<div>` (`common/components/ui/skeleton.tsx:3-5`).
  - This change puts `ReservedText` inside `<p>` in three places:
    - `features/git/components/connect-github-card.tsx:206-208` and `:218-220`;
    - `features/auth/pages/settings-page/account-deletion-card.tsx:144-151`.
  - The HTML parser closes a `<p>` when a `<div>` starts, so the server's markup parses into a different tree. A DOM diff with every read held shows it:
    - server `#git-connections-skeleton` children: `p, div.skeleton, p, div, p, div.skeleton, p`;
    - client: `p, div, p`.
  - `route-skeletons.tsx`'s own `ReservedHelp` wraps `ReservedText` in a `<div>` and is not affected.
- **Target:**
  - A reserved bar must be valid inside phrasing content. Either `ReservedText` draws a `<span>` bar (absolute, block), or the three parents become `<div>` with the same type classes.
  - Add a test that server-renders the Account Settings frames and hydrates them with no recoverable error (or asserts no block element inside a `<p>`).
  - Re-measure the frames afterwards: a `<div>` parent must keep the 250/366/420/460 px heights.
