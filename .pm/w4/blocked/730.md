# `bex.co/docs/mcp-server` tells API-key users to exchange the key for a token, and lists none of the Blueprint tools the skills deploy with

Why: the bex skills pack sends every agent to this page for the current MCP setup (`overrides/shared/bex-access.md`), and the page contradicts the pack and Render: Render's MCP page sends an API key as the bearer, and so does bex since w7/m426.

Found by the w4/m630 t005 parity check, 2026-11-25. Read `https://bex.co/docs/mcp-server` (last updated 2026-11-23):

- "Headless clients and CI use an API key. Mint one … then exchange it for a short-lived bearer token", with a `client_credentials` recipe against `https://oauth.bex.co/oauth2/token` and `BEX_KEY_ID`/`BEX_KEY_SECRET`. The pack's content lint refuses exactly that recipe (`tokenExchange` in `lego/cli/internal/skills/skills_test.go`), because a `bex_…` key is sent as `Authorization: Bearer <key>` (w7/m426). The Cursor example reads `BEX_TOKEN`, where the pack's reads `BEX_API_KEY`.
- "What the server exposes" lists `generate_blueprint` and `sync_blueprint` under blueprints, but not `create_blueprint`, `plan_blueprint`, `approve_blueprint`, `update_blueprint` or `get_blueprint`, the tools bex-deploy now drives (w4/m630, served since w2/m256).

The site's source is not in `bex-co/bex` (no file in this repository carries the page's text), so this note is first to find where `bex.co/docs` is built and who can change it.

Done when the page sends an API key as the bearer, as Render's `render.com/docs/mcp-server` does, names `BEX_API_KEY`, and lists the five Blueprint tools beside the existing ones; or, if the site cannot be changed from here, the note is parked naming its owner.
