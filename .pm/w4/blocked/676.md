# 676 — Since 10:34 UTC an OpenStatus check has requested the production canary every 60 s, so the free service never sleeps, the tenant-view canary's events stage fails every run (issue #167), and the canary can no longer tell a stalled events feed from a busy service

Why: the tenant-view canary's stage 4 exists to catch an events feed that stopped recording. It can only do that if the canary service sleeps and wakes at least once per `EVENT_WINDOW` (3600 s). An uptime check every 60 s keeps the free service awake forever, so each run of the "Production edge liveness" workflow files the same false "Tenant view is broken" alarm. Meanwhile a real events outage would look exactly the same. This is the class [w1/m173](../../w1/done/m173/README.md) fixed for one caller (a local cert-manager ACME self-check, 2026-10-07 → 10-15), now back with a different caller. Nothing detects the class by itself.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 447, 2026-11-15 19:42–20:05 UTC (`muse.env`, workspace `bex-canary`, pin `ecbddb100959`).
  - **Major for monitoring:** the production alarm is false and blind for as long as the check runs. **No tenant impact:** the events feed itself works (control below).
  - ~45m in the repo (script + workflow + fixture test), plus a few minutes of operator work on `openstatus.onbex.co`.

- **Mechanism:**
  - A free web service hibernates after about 15–16 min without requests ([w1/m173](../../w1/done/m173/README.md) DoD), and a 60 s cadence never leaves that gap.
  - Events come only from state edges (`scripts/tenant-view-liveness.sh:326-328`, `store/event_facts.go`), so a service that stays up has an empty hour, as on Render.
  - Stage 4's fast-path branch (`scripts/tenant-view-liveness.sh:318-335`) then exits 6.
  - The workflow maps exit 6 to "4/4 events (the feed did not advance)" (`.github/workflows/ssh-edge-liveness.yml:430`) and opens "Tenant view is broken: …" (`:446`). It keeps that issue open on every later run.
- **Where the caller comes from:**
  - bex self-hosts OpenStatus at `openstatus.onbex.co` (`.env.example:543-548`; the `bex-openstatus` OIDC client in `dashboard/deploy/deployment.yaml:96`).
  - Its monitors live in OpenStatus's own database, not in this repo. Who added a `hello-go.onbex.co` monitor around 10:34 UTC is unknown: no commit since 2026-11-15 00:00 touches `hello-go.onbex.co`, and `grep -ril openstatus .pm` finds only [w21/m394](../../w21/done/m394/README.md) (a security review).

## Fix

1. **Ops (needs whoever runs `openstatus.onbex.co`):** the canary fixture gets no scheduled traffic except the canary's own.
   - Point the OpenStatus check at a target meant to stay up, for example `https://api.bex.co/healthz` or a paid service.
   - If `hello-go.onbex.co` itself must be watched, set the interval longer than the idle window (≥ 30 min), accepting that each check then measures a cold wake (~14 s, w4/517).
   - Which target to use is the operator's call. It does not block step 2.
2. **Repo: stage 4 names a held-awake fixture instead of blaming the feed.**
   - In the fast-path branch, when stage 1 answered under `WAKE_THRESHOLD` and no event lies in the window, read `GET /v1/logs?type=request` over `EVENTS_START`..now and drop the probe's own `/bexProbe/` lines.
   - If the longest gap between the remaining requests is shorter than the idle window (900 s), exit with a new code **7** and print the commonest `userAgent`, `clientIP` and median interval, for example `held awake by OpenStatus/1.0 from 85.239.239.149 every 60 s`.
   - Exit 6 stays for a real stall: a gap of at least the idle window and still no `service_hibernated`, or no requests at all and no events.
   - Consumer: `ssh-edge-liveness.yml:425-431` must gain a `7)` branch, for example `stage="canary fixture held awake by a repeating caller (the events stage could not run)"`. Without it exit 7 falls to `*) configuration/probe error`, and the issue title still reads "Tenant view is broken".
   - Request logs can be relied on here: when they are dark, stage 2 already fails first (exit 4).
3. **Tests:** extend `scripts/tenant-view-liveness.test.sh` with three stubs.
   - Request logs every 60 s and an empty feed exit 7, naming the UA.
   - No requests and no events exit 6.
   - A 20-minute gap with no `service_hibernated` exits 6.

## Definition of done

- Request logs for `hello-go.onbex.co` over one hour show no `OpenStatus/1.0` line (or none closer than 30 min apart), and the canary records `service_hibernated` within about 16 min of its last real request.
- The next `ssh-edge-liveness.yml` run passes `tenant-view-liveness` with a measurable stage-1 wake and this run's own `service_woken`, and #167 closes on its own with the run id.
- `bash scripts/tenant-view-liveness.test.sh` passes the three stubs above, and fails with the exit-7 branch removed.

**Unverified:** the monitor's owner and creation time inside OpenStatus. Only two log lines were read in full, so "every line is OpenStatus" is inferred from the cadence. The 60 s cadence was read on about 24 lines, not the whole 9.5 h.

**Render:** n/a for the fix. A free Render service is also kept awake by an uptime pinger, so the product behaves as on Render; only bex's own monitoring is wrong.
