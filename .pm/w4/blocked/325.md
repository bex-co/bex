# Postgres environment changes publish stale membership after completion

Why: a completed placement change should leave the database listed in its saved environment, so the owner can trust the resource count and continue managing the correct placement.

**Severity:** minor. Stored placement and data remain correct; a later poll or reload repairs the temporary wrong row/count. **Estimate:** 55m (reuse ordered publication 15m, meaningful Apollo and consumer controls 25m, Simplify and live replay/cleanup 15m). Filing only; no product code changed. Source: functional `$qa-find-bugs w4`, a720, 2026-10-16 UTC. Research main `e620e74e9`, synced before filing.

## Reproduction and target

Create an owned project with staging and production environments and one private Free Postgres in staging. Seed three rows containing Unicode, NULL, empty text, numeric and JSON values. On `/project/<projectId>?env=<sourceId>`, select the database, choose the other environment under **Move selected resources to environment**, and click **Move** once at ordinary speed. Do not intercept, delay or replay requests.

- Desktop staging→production succeeds in the API. At **13:01:07.722Z**, the API lists staging empty and production holding the database, while the source page has **Selected: 0 / All (1) / Databases (1)** and still renders its row. The later target view and a fresh load agree with the API.
- Fresh-load production and move back. The mutation's transport completes at approximately **13:02:44.030Z**. A naturally pending **Environments** request started **13:02:29.651Z**, returns approximately **13:02:47.018Z**, and still places the database in production. From **13:03:02.684Z through 13:03:20.623Z**, selection is cleared but production still has the row/count; simultaneous direct database reads report staging. A subsequent poll started **13:03:17.047Z** and returned the correct list at approximately **13:03:38.218Z**. These are observation bounds, not a continuous stale-duration measurement.
- A fresh **390px staging→production move passes**. Its overlapping list returns the new placement; at **13:05:11.040Z** the source shows zero resources without reload. The failure is timing-dependent, not mobile-specific or universal.
- The second consumer also reproduces: in production, **Manage resources → Databases**, uncheck only the owned database and Save. Transport completes approximately **13:05:56.424Z**. An older list started **13:05:37.738Z** returns approximately **13:05:59.515Z** with the old production membership. The dialog is closed at **13:06:00.147Z**; at **13:06:10.844Z**, the ready page still shows one database, while a direct read reports `environmentId:null` and the parent project intact. The viewed mobile screenshot captures that wrong row/count.

**Target:** once the successful Postgres setter's refresh finishes, publish a genuinely post-write project-scoped Environments list. The selected source's row/count must be correct and the target list must contain the saved membership, without another poll or reload. Preserve the selected environment/URL, existing target members, parent project membership and exactly one write. Keep usable ready rows while refresh is pending; do not clear the table or patch only its count.

## Cause, consumers and bounded correction

- `dashboard/src/features/environments/hooks/use-set-environment-databases.ts:31–45` awaits named `Environments`/`Projects` refetches, then returns success. A named refetch can join a pre-write read and publish its older membership after the mutation.
- The actual **Apollo Client 4.3.3** package pinned by `dashboard/yarn.lock:65–67` was fetched and opened; the live request identifies the same version. `core/QueryManager.js:910–913` refetches included watchers; `core/ObservableQuery.js:395–424` uses network-only but retains query deduplication. `core/QueryManager.js:517–518,560–579` shares the in-flight observable by printed query and serialized variables. `core/QueryInfo.js:309–313` waits for those promises, not a distinct later snapshot. Default deduplication is enabled at `core/ApolloClient.js:77`. The checkout's stale installed 4.1.3 was not used as the pinned-version evidence.
- `common/apollo/cache.ts:6–11` has no Environment ordering policy. The newer target returned by the mutation can be overwritten by the older normalized list. The inverse and Manage captures show that ordering directly; no backend placement failure is needed to explain them.
- There are **two production calls** to this setter: `components/environment-card.tsx:138–139,238` for bulk Move, and `manage-resources-dialog.tsx:94–95,175–189` for the Databases Save. Both failed live. `environment-card.tsx:153–156` derives the rows from `environment.databaseIds`; `:260–272` clears successful selections after the hook resolves. `resource-checklist.tsx:53–55` closes the dialog after a true result. Those completed consumers therefore retain stale membership, not merely a pending indicator.
- `environments-panel.tsx:240–255` passes the selected list item to the card. Updating a database detail's `environmentId` alone cannot repair that predicate. Backend `internal/environments/graphql.go:194` calls `Service.SetDatabases`; `service.go:1021–1022,1043–1100` changes membership and returns the target view. List `:451–485` assembles canonical membership. Fresh reads confirm the saved placement and the final SQL query confirms unchanged data.

Adapt the already-shipped Key Value pattern in `use-set-environment-keyvalues.ts:36–83`: capture the successful target's immutable `projectId`, then call `publishEnvironments`. The existing helper at `lib/refresh-environments.ts:20–36` settles older active list results individually before issuing the typed project-scoped network-only query with deduplication disabled. Its `:44–60` separates a failed refresh from a committed write and retries only the read. Retain the existing Projects refresh for automatic project admission. Add matching Postgres refresh-failure copy to both locales. The existing `EnvironmentFields` fragment and mutation at `api/environments.graphql:1–24,49–53` already carry the nullable project ID and express this correction; no API/schema change is required.

Preserve mutation refusal as false with its current server error. After a confirmed write, a refresh failure keeps usable rows, reports that refresh is incomplete and offers a read-only retry; do not repeat the membership write or say it was refused. Do not invent a project ID if the nullable mutation result is absent. Existing unauthenticated, forbidden, not-found, partial-membership, timeout and unknown-write outcomes keep their distinctions. These failure controls were not induced live.
