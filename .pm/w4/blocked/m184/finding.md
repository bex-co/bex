# Undeployed-changes notice tells users to deploy while that deploy is already running

Why: during every config-change deploy the service header and Environment page say "Use a standard deploy to apply them" next to an In Progress deploy that is applying exactly those changes, which invites a redundant second deploy.

- **Severity:** minor (copy/UX; nothing breaks).
- **Repro (loop40, 2026-10-05, pin `f837cec46294`):** owned Free image service `qa-20261005-l40-acl` (`srv-db1o6b0ti8qc73bltblg`, deleted afterwards). `PATCH /v1/services/<id>` `{"serviceDetails":{"healthCheckPath":"/slow?wait=10s"}}` started config-change deploy `dep-db1obj8ti8qc73bltc20` (`update_in_progress`). The deploy detail page showed, together: the header badges `Deploying` and `Latest deploy: In Progress`, "Saved changes aren't live yet. Use a standard deploy to apply them.", and the deploy's own `Cancel` button. GraphQL `service { undeployedChanges }` was `true` for the whole 15-minute rollout.
- **Expected:** while an in-flight standard deploy carries the saved configuration, say so (for example "Saved changes go live when the current deploy finishes") or say nothing. The current hint is right only when no in-flight release carries the saved settings: Save-only, cancel, rollback, Restart (which keeps the served config), or after that deploy fails. After the deploy failed (11:26:13Z), `undeployedChanges:true` plus the hint was correct.
- **Root cause:** `lego/operator/internal/controller/saved_configuration.go:113-130` `servingConfigurationDiffers` compares saved configuration only with the **serving** release record, so the flag is true by construction for any in-flight config-change deploy. Both UI consumers render the hint on the bare flag: `dashboard/src/features/services/components/service-detail-header.tsx:301-307` and `dashboard/src/routes/services.$serviceId.env.tsx:50-55`. The copy is `services.undeployedChangesHint`, `dashboard/src/features/services/locales/en.ts:268-273`.
- **Fix:** keep `undeployedChanges` meaning "saved ≠ serving" (m145 and m165 contracts). Have the operator also report whether the pending/in-flight release (`PendingReleaseGeneration` or the candidate's config record) carries the current saved configuration. Expose it as a sibling bex extension on REST/GraphQL/MCP. Pick the dashboard copy from it: "applying" while the carrying deploy runs; the current hint otherwise. A Restart of the served release must still show the current hint, because it does not carry the saved settings.
- **Blast radius:** the two dashboard call sites above, plus any agent reading `undeployedChanges` through MCP.
- **Unverified:** a build-based (repo) service, where the same window also covers the build; the env-page notice was not screenshotted this run.
- **Render:** Render shows no "not live yet" notice while a deploy is running.
- **Estimate:** ~45m.
