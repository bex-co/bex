## Objective

On a service whose ports come from its image (`UsesImagePorts` or `UsesWebImagePorts`), the user can clear a configured port. Saving a blank Port in Settings, or the equivalent API call, returns the service to `image-v1`/`web-image-v1` with no configured port and starts a deploy, exactly as a port change does.

Services that don't take ports from their image keep requiring a port. The stall reason's "or remove it to use the image's port" is then true.

## Context

- **The promise.** The stall reason is at `lego/operator/internal/controller/app_controller.go:5927-5929` (configured-port branch, w4/m243/t011). Live round 82: "… set by the service's configured port; the image declares TCP ports (80). Change the service's port in Settings to the one it listens on, or remove it to use the image's port."
- **Nothing can clear a port today:**
  - `SetPort` (`lego/backend/internal/apps/service.go:5039-5059`) rejects anything outside 1–65535 (`validateServicePort`, `:5111-5115`).
  - The PATCH rule (`lego/backend/internal/apps/settings.go:519-533`) applies only when `Port != nil`.
  - `configuredPortMode` (`settings_check.go:289-298`) only moves a service to the configured variant.
  - GraphQL `setPort` (`graphql.go:1806`) takes a non-null int.
- **Dashboard.** `ServicePortRow` (`dashboard/src/features/services/components/service-port-row.tsx:66-73`) marks a blank draft as an error. Live: "Enter a port between 1 and 65535." with Save disabled.
- **Mode predicates.** `UsesImagePorts`/`UsesWebImagePorts` are at `lego/types/v1alpha1/image_network.go:163-172`.

## Steps

1. **Backend.**
   - Add the clear path, for example `ClearPort` behind the same `can_create` and deferred audit as `SetPort`.
   - Allow it only for image-port modes, and refuse it with a typed 400 otherwise.
   - It sets `Port` to 0 and `PortMode` to the base image mode, and bumps `restartedAt`.
   - Expose it on REST (a PATCH value that means "use the image's port"; pick the wire shape and record it), GraphQL and MCP.
2. **Dashboard.** `ServicePortRow` accepts blank when `imagePorts` is true, and saving blank calls the clear path.
3. **Or, if clearing is rejected as a design choice,** drop the clause from the stall reason and record the reason in ADR089.

## Result (2026-11-11)

Clearing is made real, so the stall reason's "or remove it to use the image's port" now names a fix that exists.

- **Backend.** `SetPort` and the service PATCH resolve the request through `portChange` (`lego/backend/internal/apps/settings_check.go`), so REST, GraphQL `setPort` and MCP `update_service` all get the same rule:
  - Port 0 on a service whose image supplies its ports (`image-*` or `web-image-*`) returns it to `image-v1`/`web-image-v1` with the default stored port, and starts a deploy.
  - Clearing a port that is not set does nothing and starts no deploy.
  - Any other service still refuses 0.
- **GraphQL.** `Service.portConfigured` is true only in the configured modes. `configuredPort` alone cannot tell, because it falls back to the resolved port.
- **Dashboard.** For an image-port service, Settings → Port shows the configured port, or blank with "From the image" when none is set. A configured port can be cleared, which saves port 0. The hint says "Clear it to use the image's port again" (en, zh).
- **Operator.** When the port comes from a PORT environment variable, the stall reason now says to change or remove the variable, since it wins over any port setting. The configured-port text is unchanged.
- **Tests:**
  - `TestClearingAnImagePortServicesPortReturnsItToTheImage`: both modes, the no-op clear, and a native service refusing 0;
  - `service-port-row.test.tsx`: clearing; blank refused for a non-image service and for one with nothing set; the placeholder.
