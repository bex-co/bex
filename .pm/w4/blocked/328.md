# Editing a precise custom range truncates its bounds to minutes

Why: refining an accepted diagnostic window should preserve its timestamps; an unchanged Apply currently rejects a valid short window or silently queries a different interval.

**Severity:** minor. **Estimate:** 55m (shared-consumer review 5m, lossless draft/input change 15m, behavioral coverage 20m, live replay and Simplify 15m). Functional `qa-find-bugs`, a761, 2026-10-16 UTC, user-selected w4. Research main `72a6f77f47b637b4825824e1058e95e47b582e9d`. Filing only.

[Complete native requests/responses, dialog receipts, passing control and cleanup](../evidence/328-a761.json). The supplementary screenshot `.playwright-mcp/qa-a761-custom-range-error.png` was checked and viewed; the durable evidence does not depend on that ignored image.

## Reproduction and target

Create an owned Free web service and open its Metrics page with `range=custom`, `rangeStart=2026-10-16T18:28:10.123Z` and `rangeEnd=2026-10-16T18:28:50.987Z`. For a later replay, use an equivalent past window within one minute. This run used `qa-20261016-a761-range` / `srv-db96q2pkoksc73a7vkhg`, now deleted.

1. On a fresh 390×844 page at **18:30:08 UTC**, the native HTTP_REQUESTS operation sends those exact bounds and returns HTTP200 with `metrics: []`, without errors. The accepted window is40.864 seconds long.
2. Click **Edit custom range**. Both inputs show `2026-10-16T11:28` in the America/Los_Angeles browser. Click **Apply** without editing either field. The dialog stays open with **The end must be after the start.** The original URL remains unchanged.
3. Fresh-load the same Metrics URL at1440px. At **18:30:32**, unchanged Apply reproduces the same rejection. A fresh service Logs page with `type=app&live=0` and those bounds also sends the exact accepted request, returns HTTP200, and reproduces the rejection at **18:30:53**.
4. On service Logs, open the wider valid past window `18:27:10.123Z–18:28:50.987Z`, retaining `type=app&live=0`. At **18:32:03**, Edit → Apply without input changes closes the dialog and changes both the URL and native Logs request to **18:27:00.000Z–18:28:00.000Z**. Start moves10.123s earlier and End50.987s earlier. Both complete requests/responses are captured; the type and paused setting remain intact.
5. **Passing control:** reopen that now minute-aligned window and Apply without edits. At **18:32:04**, the dialog closes, the URL is identical, and no validation alert appears. The initial service also reaches Live and serves its exact public HTTP200 marker.

**Target:** opening an accepted custom range and applying it unchanged preserves both UTC instants at the selection's existing millisecond precision. A valid subminute window remains valid. Editing one bound preserves the untouched bound's exact instant. Minute-aligned ranges and deliberate user edits keep working; invalid order and windows over30 days retain their current refusals.

These precise windows were supplied through supported custom deep links, rather than created by the current minute-only picker. All captured ranges return empty results: this proves changed query bounds and an unusable edit, not observed record loss or a backend subsecond-accuracy defect. The empty Logs envelope formats its next-bound cursors to whole seconds; that separate output does not account for the client losing10–50 seconds before its next request.

## Root cause and bounded fix

- `dashboard/src/features/metrics/components/range-select.tsx:76–82` seeds both draft fields through `toLocalInput`. The formatter at **233–235** ends at `getMinutes()`, discarding seconds and milliseconds before the user edits anything.
- `CustomRangeDialog.apply:154–168` reparses those reduced strings through `fromLocalInput:239–241` and passes them to `makeCustomRange`. Equal truncated minutes correctly fail order validation; different truncated minutes produce the silently changed accepted interval.
- The two inputs at **192–209** are native `datetime-local` controls with no explicit step. `common/components/ui/input.tsx:5–18` forwards their type/value/props; it adds no date conversion. The schema can carry the fix: `features/metrics/lib/range.ts:49–55,79–96` stores ISO strings and accepts positive subminute windows, while `parseRangeSearch:131–141` retains valid supplied bounds. No API field needs changing.
- The consumer propagates the changed result: `routes/services.$serviceId.logs.tsx:68–75` writes `range.startTime/endTime` back to search; `routes/services.$serviceId.metrics.tsx:39–46` does the equivalent through `rangeToSearch`. The before/after native requests confirm that fixing only URL display would leave the actual read wrong.

Keep the change local to RangeSelect's draft, formatting and two inputs. Represent the accepted seconds/milliseconds instead of overwriting them with minute-only values, and preserve the original ISO instant for an untouched bound when converting a local draft back. A fractional-second step such as `0.001` is expressible through the existing native Input. The detached browser capability control retains `2026-10-16T11:28:10.123` with that step and reports valid/no step mismatch; this is a platform capability check, not a fixed-product claim. Preserve the existing local timezone convention, focus behavior, Edit action, Cancel/Close warning clearing and relative presets. Do not round accepted links or raise the one-second API resolution floor to conceal the loss.

The lockfile pins **react-dom19.3.1**; local node_modules19.2.3 was not treated as that pin. The actual [19.3.1 npm archive](https://registry.npmjs.org/react-dom/-/react-dom-19.3.1.tgz), integrity-verified and opened at `package/cjs/react-dom-client.development.js` → `updateInput`, assigns the supplied string for a non-number input. It does not truncate dates. The archive/member hash is recorded in the evidence. The loss is already in the application formatter. The [HTML datetime-local specification](<https://html.spec.whatwg.org/multipage/input.html#local-date-and-time-state-(type=datetime-local)>) supports the local date/time control and fractional-second steps; its default step is60 seconds. No Radix or global Input change is indicated.
