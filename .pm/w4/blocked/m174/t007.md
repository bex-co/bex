## Objective

After `55403e56d` the DoD probe still loses one line in roughly one of six fast-exit runs, and the lost line varies. Find where it is dropped and fix it, so 30/30 holds every time.

## Context

- Production replays (milestone README): loop63 batch 1 lost `error: GAMMA-x three` at 03:05:14; batch 2 was 30/30. Loop64 (2026-10-06, ≥40 min after the deploy, fixture `qa-20261006-l64-cron`, `srv-db26u3k20ers738obgfg`) read 29/30. Run 03:48:45 lost the **JSON** line `{"level":"warn","msg":"DELTA-x"}` (the `level=warning` stream) while keeping the stderr line. `&level=warning`, `&text=DELTA` and a 03:48:40–50 window all agree it is absent from Loki, so this is not a read-side filter.
- Lines of one run arrive within ~100 µs (`ALPHA` .341564, `GAMMA` .341566, `BETA` .341622, `100%` .341631). The lost line belongs to a different stream label (`level=warning`) than the others in loop64, and to the same stream in loop63.
- Candidates: Alloy `local.file_match`'s sync period against a file that appears and is finished inside one period (the `tail_from_end`/initial-position default on a newly discovered file); the positions file racing pod-log GC (the Job pod is deleted soon after completion); or Loki's per-stream rate/ordering limits for streams with one line per run.

## Steps

1. On a dev stack, run the DoD Job 50× and diff each CRI file against Loki. Record which lines are lost, whether the target was discovered before or after the container exited, and Alloy's `loki_source_file_*` / `loki_write_dropped_*` metrics.
2. Fix at the cause (for example `tail_from_end = false` for newly discovered files, a shorter `sync_period`, or keeping finished Job pod logs until shipped) and prove 50/50.
