## Objective

After `55403e56d` the DoD probe still loses one line in roughly one of six fast-exit runs, and the lost line varies. Find where it is dropped and fix it, so 30/30 holds every time.

## Context

- [a321 delayed stdout corpus](delayed-stdout-a321.md): one successful 90-second plain-stdout run lacks its begin marker; a fresh second run is complete. REST/GraphQL/UI agree. This is an added control for the existing residual, not a replacement for the five-message fast-run acceptance; t008 verifies its producer/intake boundary after this task.

- Production replays (milestone README): loop63 batch 1 lost `error: GAMMA-x three` at 03:05:14; batch 2 was 30/30. Loop64 (2026-10-06, ≥40 min after the deploy, fixture `qa-20261006-l64-cron`, `srv-db26u3k20ers738obgfg`) read 29/30. Run 03:48:45 lost the **JSON** line `{"level":"warn","msg":"DELTA-x"}` (the `level=warning` stream) while keeping the stderr line. `&level=warning`, `&text=DELTA` and a 03:48:40–50 window all agree it is absent from Loki, so this is not a read-side filter.
- Lines of one run arrive within ~100 µs (`ALPHA` .341564, `GAMMA` .341566, `BETA` .341622, `100%` .341631). The lost line belongs to a different stream label (`level=warning`) than the others in loop64, and to the same stream in loop63.
- Candidates: Alloy `local.file_match`'s sync period against a file that appears and is finished inside one period (the `tail_from_end`/initial-position default on a newly discovered file); the positions file racing pod-log GC (the Job pod is deleted soon after completion); or Loki's per-stream rate/ordering limits for streams with one line per run.

## Steps

1. On a dev stack, run the DoD Job 50× and diff each CRI file against Loki. Record which lines are lost, whether the target was discovered before or after the container exited, and Alloy's `loki_source_file_*` / `loki_write_dropped_*` metrics.
2. Fix at the cause (for example `tail_from_end = false` for newly discovered files, a shorter `sync_period`, or keeping finished Job pod logs until shipped) and prove 50/50.

## Acceptance criteria

- [ ] 50/50 complete runs on the dev stack and two consecutive 6-run production probes at 30/30.

**Progress 2026-10-18 (loopx w4): cause found and fixed in the image; digest pin pending.**

- **Replay rig.** A throwaway kind cluster ran the GitOps-rendered Loki 3.6.7 and the production log-shipper, plus the DoD command as Jobs. `scripts/log-shipper-kind-replay.py` now reproduces this.
- **Loss on v1.11.2.** 4 of 800 lines were lost: `BETA-a048`, `BETA-b019`, `BETA-b089` and `100%-b091`, a different line each time. Every lost line was read from its file (`loki_source_file_read_lines_total` = 315 for 63 files) but never sent (`loki_write_sent_entries_total` = 314, nothing dropped). So it vanished inside Alloy, not in Loki.
- **Cause.** Alloy v1.11.2's `loki.source.file` `Run()` handles each target update (`updateReaders`, which every pod churns) with a temporary goroutine that drains reader entries. That goroutine is then cancelled, and an entry it holds mid-send loses the `select` to `readCtx.Done()`.
- **Fix.** v1.11.3 replaces this with one dedicated consumer and a separate `ApplyTasks`. The same rig on v1.11.3 (the carried CRI patch applies unchanged, and the 11-test log-shipper harness passes) lost 0 of 800.
- **Next.** `deploy/log-shipper/Dockerfile` now builds on v1.11.3. CI publishes it, and then the digest is pinned in `deploy/gitops/base/log-shipper.yaml`, with `test_log_delivery.py`'s version check updated.
