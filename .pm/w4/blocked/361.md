# A manual deploy queued behind a build-command change stays "queued" after it goes live

Why: a static site's deploy record read `queued` for 25+ minutes with nothing in flight. Either it never ran, or it was superseded and never closed. Either way the Deploys list and the API report a deploy that will not happen.

- **Source:** the `w4/341` live replay, 2026-10-19 07:04–07:29 UTC, bex-canary, production at `98721ad37`. The site was `qa-20261019-341b` from `examples/static-site` (since deleted).
- **Repro:**
  1. On a live static site, MCP `update_service(buildCommand: …)` (which opens its own deploy).
  2. Immediately `POST /v1/services/<id>/deploys {}`.
- **Observed** (`GET /v1/services/<id>/deploys`):
  - `dep-dbas24f51eac73b15810`: created → build_in_progress → update_in_progress → **live** (07:06:31).
  - `dep-dbas24f4b8ns73ae2dng`: **queued** from 07:04 until the site was deleted at about 07:29.
  - The served bytes were already the new build's.
- **Expected:** a deploy queued behind another either runs once that one settles, or, if it adds nothing (the same commit and config just went live), closes as superseded or canceled with a reason. It must never stay `queued` with nothing running.
- **Overlap to check first:** deploy sequencing is workstream w8's active area. Compare with w8/m117 (canceling the newer of two open deploys strands the older), w8/124 and w8/126 (a source update waits behind an in-flight release), and w8/m119/m120 before fixing. This may belong there.
- **Unverified:** whether a web service behaves the same, and whether the queued deploy would eventually have run.
- **Estimate:** unknown until triaged against w8.
