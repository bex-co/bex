## Objective

DoD 1 and DoD 2 fail on production (QA loop round 143, recorded in the README's post-release probe). Make a failed build command's reason name that command and its output, and keep the image push's digests out of the tenant's build log.

## Context

- **Fixture:** Free Node web service `qa-20261111-r143-node` (`srv-dbqelpofss2c73f2078g`, `render-examples/express-hello-world`), on pin `8330744bd643`, which contains `a9c016955`. Deleted afterwards.
- **The `failureReason`** of `dep-dbqenp8fss2c73f208gg` (build command `npm install && echo QA84 && exit 3`), 758 characters, as REST and `deploy_ended` return it:
  - It begins "build failed in the build environment step:", and continues `#15 DONE 0.1s`, `#16 [stage-0 4/12] ADD --link --checksum=sha256:… https://registry.npmjs.org/pnpm/-/pnpm-10.34.7.tgz /opt/bex/pnpm.tgz`, `#17 [stage-0 5/12] RUN mkdir -p /usr/local/lib/node_modules/pnpm && tar -xzf /opt/bex/pnpm.tgz …`, `#18 [stage-0 6/12] COPY --link --from=mwader/static-ffmpeg:9.0.2-1@sha256:f5d1…`.
  - It contains no `QA84`.
  - The build log ends with the same text as `==> Build failed: …` plus `==> #15…` through `==> #18…` lines.
- **The log's own verdict is right:**
  - the same build log shows `QA84` and `error: build command 'npm install && echo QA84 && exit 3' exited with code 3`;
  - but `==> Building from https://github.com/render-examples/express-hello-world@039c347` prints *after* that error, and then the toolchain transcript above.
- **Mechanism (traced in part):**
  - The display filter (t001, `nativeLogDisplay`) reads the BuildKit progress stream.
  - The failure reason is a separate path: `failureDetail` (`lego/operator/internal/build/build.go:813-850`) parses the failed `buildkit` container's termination message (the `FallbackToLogsOnError` tail). `nativeCommandFailure` (`:875-`) looks there for BuildKit's `process "…" did not complete successfully: exit code: N` verdict (`buildkitProcessFailure`, `:855`).
  - Here it found none, so `named` stayed false and the step became `nativeBuildEnvironmentStep` (`:841-843`). The tail kept the toolchain steps.
  - **Not traced:** what the termination message held, and why the verdict was missing. It may be the size or line cap of the kubelet's log fallback, or the regex against this command's quoting.
- **DoD 1:** the successful build's log (40 lines) has 20 lines with `sha256:`. They are the push phase's `skopeo` output (`Copying blob sha256:…`, `Copying config sha256:…`, `Writing manifest to image destination`), printed after `==> Build successful 🎉`. w4/582 covers the order of that success line, not these lines.

## Steps

1. Capture a failed native build's `buildkit` termination message (operator debug, or a mock-cluster replay of the same command). Find why the verdict is absent from what `failureDetail` reads.
2. Make the failure reason come from the same verdict the display filter already prints. Either read the progress stream's summary, or make the termination capture include BuildKit's error summary. Then `failureReason` and `==> Build failed:` read `build command 'npm install && echo QA84 && exit 3' exited with code 3` with the command's last output lines (`QA84`), never toolchain steps.
3. Keep `build environment` for real toolchain failures, for example a runtime version fetch. Use w7/m82's user-versus-infrastructure split, so a tenant's `exit 3` isn't reported as the platform's.
4. Filter or summarise the push phase's `skopeo` output for native builds. It can become Render's `==> Uploading build...` / `==> Uploaded in Ns`, coordinated with w4/582.
5. Print `==> Building from <repo>@<sha>` before the build command, not after the failure.

## Acceptance criteria

- [ ] On production, the DoD 2 command yields:
  - a `failureReason` that contains `QA84` and `exited with code 3`;
  - no `#N`, `/opt/bex`, `static-ffmpeg` or `sha256:` in the reason or the log.
- [ ] DoD 1's log has no `sha256:` line.
- [ ] A toolchain failure still reads `build environment`.

## Addendum — QA loop round 190 (2026-11-12, pin `a5be11e4e517`): reproduced, and the missing verdict traced to the kubelet

- **Reproduced on a static site.**
  - Fixture: `qa-20261112-r190-st` (`srv-dbqq04a8vjhs73do9e9g`, `octocat/Spoon-Knife`, Publish Directory `.`), deleted afterwards (DELETE 204, then GET 404).
  - Build command `echo qa-break2; exit 3`, deploy `dep-dbqq7eq8vjhs73do9es0` → `build_failed` at 11:33:29.
  - The log is right up to the verdict: `==> Running build command 'echo qa-break2; exit 3'...`, `qa-break2`, `error: build command 'echo qa-break2; exit 3' exited with code 3` (11:33:09).
  - It then prints `==> Build failed: build failed in the build environment step:`, followed by `==> #13 extracting sha256:2d5c…`, `#14 [stage-0  2/13] COPY --link --from=node:24-bookworm@sha256:d862…`, `#15 … yarn`, `#16 … /opt/bex/pnpm.tgz`, `#17 [stage-0  5/13] RUN mkdir -p /usr/local/lib/node_modules/pnpm && tar -xzf /opt`.
  - REST `failureReason` and `deploy_ended.details.failureReason` (820 characters) are the same text, with no `qa-break2` and no exit code.
- **Mechanism (the "not traced" bullet above).**
  - **What bex writes.** A native build's buildkit phase writes the last `terminationMessageBytes` = 4096 bytes of BuildKit's raw transcript to `/dev/termination-log`:
    - `nativeLogDisplay` sets `bex_message=/dev/termination-log` (`lego/operator/internal/build/build.go:189`);
    - the prelude runs `tail -c 4096 "$bex_log" > "$bex_message"` (`:160`, `:175`).
    - BuildKit's verdict `process "…" did not complete successfully: exit code: 3` is therefore at the **end** of that file.
  - **What the kubelet keeps.** It keeps only the **head** of each container's message, and the share shrinks with every container in the pod.
    - Kubernetes v1.33.0 `pkg/kubelet/status/status_manager.go:1038-1055` (`normalizeStatus`) sets `bytesPerStatus := MaxPodTerminationMessageLogLength / (containers + initContainers + ephemeralContainers)`, with `MaxPodTerminationMessageLogLength = 12 KiB` (`pkg/kubelet/container/runtime.go:785`).
    - It then cuts each `Terminated.Message` to `Message[:bytesPerStatus]`.
  - **This pod's share.** A native build pod with the build cache has 7 containers (`build.go:1406-1490`):
    - init containers: clone, cache restore, `prepare-native-build`, the runtime resolver and `buildkit`;
    - containers: `push` and cache save;
    - plus one more with secret files or signing.
    - So `buildkit` keeps its first ~1.7 KiB (≈1.5 KiB with 8 containers). That is the start of the last 4 KiB, i.e. the toolchain's `#N` progress, and the verdict is cut off.
  - **Downstream.**
    - `nativeCommandFailure` (`:918`) finds no verdict, so `named=false`, and `failureDetail` (`:856-890`) names the step `nativeBuildEnvironmentStep`.
    - `buildkitFailureSummary` (`:959`) finds no `#N ERROR:` block and returns the text unchanged.
    - `failureTail` (`:1000`) keeps its last 800 bytes.
  - **Why the cut can stay hidden.** Any test that reads the termination message directly, or a pod with few containers, passes. The kubelet cut happens only in the API pod status the operator reads.
- **What step 2 needs.** The verdict must land inside the head the kubelet keeps, whatever the container count. Either:
  - write the summary rather than the raw tail: BuildKit's `#N ERROR` / `------` block and the `process … exit code` line, or the already-rewritten `build command '…' exited with code N` with the command's last output lines, capped at well under 12 KiB ÷ the pod's container count (for example 1 KiB);
  - or put the verdict first.

  The same applies to every classifying phase that uses `bex_message` (`clone`, `push`, `prepare-native-build`): their tails are cut the same way.
- **Test to add:** a unit test that runs a ≥4 KiB BuildKit transcript, ending in the verdict, through `normalizeStatus`'s rule (first 12 KiB ÷ 7 bytes). `failureDetail` must still name `build command` and quote `exited with code 3`.
