## Objective

Make Render's trigger-then-cancel sequence work, and make a second trigger cancel the first instead of dropping it. Today `DELETE …/runs` right after `POST` answers 409 "has no active run" and the run executes anyway (README P2). Two back-to-back triggers leave the first run ID unknown forever (P3).

## Context

- `CancelCurrentCronRun` (`service.go:4157-4172`) and `CancelCronRun` (`:4138-4154`) depend on `pendingCronRun` and `cronRunByID`, which t001 extends.
- `TriggerCronRun` (`:4093-4100`) sets `spec.cancelRun` only when `pendingCronRun` finds an active run; otherwise it overwrites `spec.runAt`.
- In the operator (`app_controller.go`):
  - `cancelRequestedCronRun` returns false for a Job that doesn't exist and records nothing.
  - `manualRunSettled` treats a `cancelRun` that names the current `runAt` Job as settled.
- Preserve the guarantees of earlier milestones:
  - w5/m108: a canceled manual run is never resurrected after history eviction.
  - w4/m114: one active slot, and a canceled run stays dead.
  - w6/039: scheduled and manual runs never run concurrently.

## Steps

1. `CancelCurrentCronRun` and `CancelCronRun` cancel a request that has no Job yet. `DELETE` answers `204`, and the per-run route returns the `canceled` view with `finishedAt`.
2. A `TriggerCronRun` over such a request records it in `spec.cancelRun` before replacing `spec.runAt`.
3. The operator never creates a Job for a canceled request. It writes a durable `canceled` `CronRun` entry for it, so the request still reads `canceled` after the `cancelRun` slot is reused.
4. Check cancel races: the Job created between the cancel and its reconcile must be deleted, and the run must read `canceled`, exactly as an existing Job's cancel does today.
