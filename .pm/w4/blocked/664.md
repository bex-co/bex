# 664 — Scaling a healthy web service up records `server_failed` ("The instance failed its health check") and later `server_available`, though every existing instance kept serving

Why: on Render, a scale-up records `instance_count_changed` (or `autoscaling_started`/`autoscaling_ended`), and nothing else. On bex, the same scale also records a service-level `server_failed` with reason `unhealthy`, no `instanceID`, dated the moment the new pod is created, then a `server_available` 30–60 s later. The service never stopped answering. Events, webhooks and failure notifications therefore report an outage on every manual scale-up and every switch from autoscaling back to a larger stored count. The autoscaler's own scale-ups are probably affected too (not probed).

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 361, 2026-11-14 13:36–13:46 UTC (`muse.env`, workspace `bex-canary`; pin `c99e7815ebec`). **Minor to major** (a false outage on Events, webhooks and alerts; nothing breaks). ~1h, including the mechanism check below.
- **Fixture:** Starter web service `qa-20261114-r361-as` (`srv-dbs65glv5sfs73boalb0`, `docker.io/traefik/whoami:v1.10`, `dockerCommand: /whoami -port 10000`), created with `POST /v1/services`. Deleted afterwards (`DELETE` 204, then `GET` 404).

- **Root cause (partly verified):**
  - **Producer, verified.** A `server_failed` without `instanceID` and with `unhealthy` is the service-level availability verdict. `toFailureReason` maps `EventReasonReadinessFailed` to "The instance failed its health check" (`lego/backend/internal/events/rest.go:199-223`). `observedServiceStateFor` sets that code only on its Ready=False branches (`lego/backend/internal/store/reconciler.go:2475-2531`):
    - `servingRevisionDown` (`:2501-2506`);
    - the generic "ActiveRevision set, not parked, not RolloutSettling" branch (`:2517-2529`).
    - Per-instance exits carry an `instanceID` (compare w4/608's `nonZeroExit` fact), so they are not the source.
  - **Which branch fires, not verified.** Both branches are meant to be unreachable while ready pods of the active revision exist:
    - `servingRevisionUp` (`:2429-2435`) reads healthy when the Serving condition is True **at the App's current generation**;
    - the operator's `observeServingRevision` (`lego/operator/internal/controller/serving_condition.go:32-63`) sets Serving True when any pod of `ActiveRevision` is Ready, and `reportRolloutProgress` calls it (`app_controller.go:3953`) after stamping Ready=False `RolloutProgressing` (`:3944`). The phase stays Running for a served release (`servedReleaseOutage`, `:3966-3968`).
    - A scale changes `spec` and bumps `App.Generation`. The likely gap is a status write in the scale path that stamps Ready=False at the new generation without a Serving condition at that generation, so `servingRevisionUp` is false and the generic branch fires. Confirm this before changing anything.
- **Fix (target behavior):** a replica-count change on a service whose active-revision pods stay Ready records no `server_failed` and no `server_available`, only `instance_count_changed` or the autoscaling pair, as on Render. A real outage during a scale (every active-revision pod unready) still records `server_failed`, as w1/m185 requires.
  1. Reproduce in envtest or on the mock cluster: a Running web service at 1 replica, `numInstances` → 3. Capture the App status (Ready and Serving conditions with `observedGeneration`) on every operator write between the spec change and full readiness, and the observation each backend pass makes.
  2. Close the gap at its source: every status write that stamps Ready=False for a replica-only change also carries a current-generation Serving condition. Alternatively, `observedServiceStateFor` treats a Ready=False whose reason is rollout progress or settling, while the serving revision is the active one, as healthy, like `hasOpenDeploy` does for deploys (`:2508-2512`).
  3. Store and operator tests: a 1 → 3 scale, an autoscaling-off scale-up and an autoscaler step-up each produce no availability edge. A scale whose new pods crash still produces none while the old pods serve. A scale while every pod is unready still produces `server_failed`.
- **Blast radius:** `observedServiceStateFor` is the one availability producer for web services, private services and background workers, so the fix covers all three. Worker scale-ups go through the same `reportRolloutProgress` (`app_controller.go:3865-3868`). REST, GraphQL, MCP events, webhooks and notification emails all read the same facts, so they move together.
- **Adjacent classes:** a crash of an existing instance during the scale is still a per-instance `server_failed` (w8/m158, w4/608). A node loss is still `server_hardware_failure`. A health-check outage of the live release is still w4/m327's.
- **Unverified:** the autoscaler's scale-up (not loaded in this run); private services and workers (same code path, not probed); whether a failure notification email was sent (not checked).
- **Render:** Render's scale events are `instance_count_changed` and `autoscaling_started`/`autoscaling_ended`. `server_failed` is an instance failure.
- **Dedupe:** `grep -rlE server_failed .pm/w4 .pm/w8 .pm/w5 .pm/w3 .pm/w21 | xargs grep -lE "scal(e|ing) ?(up|…)|instance_count_changed|numInstances"` → w4/236, w4/517, w4/271 and w3/m302. None is about a scale-up's availability edge. w4/m327 (blocked) covers a live release's real health-check outage, not a scale.
- **Triage 2026-11-14 (/loopx w4), not fixed — the note's suspected mechanism is disproven, the real one is not pinned yet:**
  - Envtest repro (operator at `0c9d961f4`'s parent): a Running web image service (configured port 10000, and again in web-image-ports mode with a detected HTTP port, as the fixture was) at 1 replica with one Ready pod, scaled to 3, with the Deployment then reporting 3 replicas / 1 ready and two new unready pods present. Every pass wrote phase `Running`, `Ready=False RolloutProgressing` and `Serving=True ReleaseServing`, both at the new `metadata.generation` (2). For that status `observedServiceStateFor` answers `healthy` through `servingRevisionUp`, so no status write in the scale path stamps Ready=False without a current-generation Serving.
  - `RolloutProgressing` is written only by `reportRolloutProgress`, which refreshes Serving in the same write, so for the store to conclude `unhealthy` it must have seen an App whose `metadata.generation` was newer than both conditions for 30–60 s (or a Serving verdict that really was False). Candidates still open: operator status writes lagging or conflicting during the rollout, or a projector `Update` (`ReconcileOnce` → `applyOwnedSpec`) moving the generation past the operator's last verdict before `recordObservations` reads `cur`.
  - Next step: on the mock cluster or production, capture the App CR (`metadata.generation`, `status.phase`, Ready and Serving with `observedGeneration`) every second through a 1 → 3 scale, beside the store pass's observation. If the generation lead is confirmed, the fix is to judge Serving against the Ready verdict's generation (both come from one operator observation) instead of `metadata.generation`, with the store tests the note lists.
