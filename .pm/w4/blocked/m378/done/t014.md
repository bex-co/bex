## Objective

MCP `list_logs`'s text is byte for byte the body `GET /v1/logs` returns for the same window (DoD 2).

## Found by the t007 replay (2026-11-17 05:46 UTC, pin `58ef086ab21d`)

- `list_logs {"resource":[<srv>],"limit":2,"type":["build"],"startTime":…,"endTime":…}` and `GET /v1/logs` with the same filters parsed to equal values, but the bytes differed in key order only. MCP: `hasMore, logs, nextEndTime, nextStartTime`, each line `id, labels, message, timestamp`. REST: `hasMore, nextStartTime, nextEndTime, logs`, each line `id, message, timestamp, labels`. Both escape `>` as `\u003e`.
- Cause: the MCP tool returns `renderLogList` through go-sdk's typed path, which normalizes the text to sorted keys; REST encodes the struct in declaration order (`lego/backend/internal/logs/render.go`).
- Render's own server marshals `client.Logs200Response` / `logs.Log` (`render-mcp-server` `pkg/client/types_gen.go:3866`, `pkg/client/logs/logs_gen.go:155`, at the pinned `23fb336`). Their fields are alphabetical, the order bex's MCP text already had.

## Fix

- `renderLog` and `renderLogList` fields now follow Render's generated client (alphabetical), so REST, MCP and Render's server emit one key order.
- `TestMCPListLogsIsRESTsBody` (`lego/backend/internal/logs/mcp_render_test.go`) now also compares the MCP text with REST's body byte for byte. With the old field order it fails (`want REST's bytes`).
