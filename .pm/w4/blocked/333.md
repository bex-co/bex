# Expose the active project resource-type filter

Why: customers using assistive technology cannot discover which resource type is active because selection exists only in button styling.

**Severity:** minor. **Estimate:**45m. Ordinary functional QA a834, 2026-10-17 UTC, research main b9acddc64073e9b3284766e412001869da90add7. Filing only. Supports ADR008's dependable dashboard and ADR018's project-management surface.

## Reproduce and target

Open /project/prj-d9dgeo0bd9nc73a0vh1g?env=unassigned. In the captured read-only baseline, All(2) shows two services. At390×844, focus Services(2) and press Space: URL becomes kind=services and Services has the selected visual style. At1440×1000, fresh-load the same project with kind=databases: Databases(0) is visually selected and the empty result is truthful.

In both cases, all five buttons have no aria-pressed or other selection state. The accessibility tree has no Resource type group even though the wrapper supplies that label. The [durable evidence](../evidence/333-project-filter-state.json) retains exact executed probes, full before/after accessibility trees, button attributes/classes, URLs, controls and cleanup.

**Target:** the existing Resource type wrapper is an accessible group. Exactly the current kind's native button exposes aria-pressed=true; the other four explicitly expose false. With kind omitted, All is pressed. Mouse/Space/Enter activation and URL-provided kind keep semantics synchronized with the existing visual state, without changing button labels or filter behavior.

A temporary browser-only role=group plus per-button aria-pressed diagnostic immediately produces group Resource type and Databases(0)[pressed] in the accessibility tree. Attributes are restored in finally, with zero remaining pressed attributes afterward. This is a consumer check, not product implementation. Both screenshots were inspected; .playwright-mcp/qa-a834-project-filter-{mobile,desktop}.png are ignored supplements.
