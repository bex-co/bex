# Resuming a published static site briefly reports that its host does not exist

Why: a visitor opening a site after Resume receives a non-retryable not-found response even though the publication still exists and the dashboard and API already report Running.

**Severity:** minor, transient incorrect HTTP classification; the site recovers without intervention and no content loss was observed. **Estimate:** 55m. Functional `$qa-find-bugs w4` a520, 2026-10-15 UTC, muse.env through the login helper. Filing only. Research main `5152699f5` over `origin/main f5b0e1170`; the researched resolver, handler, entrypoint and controller files are unchanged by that sync. Goal: reliable hosting lifecycle under ADR007 and ADR029.

## Source and bounded fix

- `lego/operator/internal/staticserver/resolver.go:78–82` discards suspended Apps before retaining their published revision. Refresh replaces the entire map at :95–97. The next resume does not repopulate it until Run's next refresh (:104–117).
- `lego/operator/cmd/staticserver/main.go:111–115,164–168` configures that independent polling loop, default **10 seconds**. No BEX_STATIC_RESYNC override was found under operator config or deploy. The actual production refresh timestamps were not inspected; the exact phase relationship is inferred, not a captured timer trace.
- `lego/operator/internal/controller/app_controller.go:3864–3885` routes a suspended site to the activator. Resume takes :3895, switching the Ingress back to the static server, then stamps Running/Published at :3899–3910. There is no synchronization with the resolver snapshot. Therefore a legitimate request can reach the static server before its host returns to that map.
- Consumer `internal/staticserver/staticserver.go:212–216` maps the resulting false Resolve result directly to 404. `Site` at :122–128 carries revision/prefix/rules but cannot express known-yet-unavailable. Adding only metadata in the producer without a handler branch would either preserve the 404 or accidentally serve suspended bytes.
- Existing `applyErrorHeaders` at :607–615 supplies safe request-path custom headers; `serveSiteBusy` at :631–634 shows platform Retry-After precedence. Reuse these error conventions for a distinct temporary-unavailable message; do not call this normal lifecycle transition capacity overload.
- `resolver_test.go:34–120`, `TestPublishedSiteSuspendResumeWhileNewerBuildHeld`, explicitly expects the suspended map to disappear, then calls Refresh before every resumed HTTP read. It therefore never models the failing ordering and currently locks in the missing-host representation. Preserve its held/failed-build and cached-publication guarantees while updating the unavailable representation.

Bound the implementation to the existing static resolver and handler:

1. Keep effective host entries for **published** suspended static Apps, carrying a suspension/unavailable flag in Site. Keep no-active-revision and non-static filtering, EffectiveHosts and StaticPrefix selection intact. Do not blindly retain removed Apps/hosts indefinitely.
2. In ServeHTTP, after host resolution and normalized request-path calculation, check that flag **before object/cache lookup, rewrite, redirect or SPA fallback**. Return an explicit temporary-unavailable 503, applying existing error-header rules and setting platform `Cache-Control: no-store` and positive short Retry-After after customer rules. Never return publication bytes for this flag. Once Refresh observes resume, the same entry serves its retained publication normally.
3. Keep the activator as the settled suspended responder. Its existing negotiated suspended response, routing and lifecycle verbs need no duplication or change. If an older static snapshot sees resumed ingress first, the retained entry now yields retryable 503 until refresh. Do not replace all unknown-host 404s, shorten the polling timer as the fix, add a per-miss Kubernetes read, or introduce another controller protocol.

Before the next refresh the last known published entry must remain **unavailable**, not appear absent and not expose cached content. Refresh failure preserves that unavailable snapshot until a successful read. Errors for actual origin failure/overload/oversize, unknown hosts, unsupported methods, and ordinary API refusals retain their existing classes. HEAD must carry the temporary status/headers without a response body. Inspect through a real HTTP server: Go's response writer suppresses HEAD body bytes, whereas a bare httptest recorder does not establish that transport behavior. Local workspace Go 1.27 stdlib `net/http/server.go` Error and HEAD handling were read; the deployed Go version was not measured and needs no change.

## Implementation (2026-10-15)

**Status:** blocked on the post-deploy live replay. The resolver keeps a suspended **published** static App in its snapshot with `Site.Unavailable` (unpublished/non-static/deleted Apps still drop out). `ServeHTTP` checks it right after host resolution and path normalization, before any object/cache lookup or rule: `serveSiteUnavailable` applies the request-path custom headers, then sets platform `Cache-Control: no-store` + `Retry-After: 5`, and answers `503 static site temporarily unavailable`. The next successful Refresh after resume serves the retained publication; a failed Refresh keeps the unavailable entry. ADR029 records the handoff contract. Regressions (`resume_handoff_test.go`): resume persisted without a Refresh → 503 for warm root, cold file and rewrite with no origin access and customer Cache-Control/Retry-After overridden; failed Refresh keeps 503; Refresh → original bytes/rewrite/header with the one cached fetch; HEAD over a real `httptest.Server` → 503 with headers and no body; deleted and never-published hosts stay 404. `TestPublishedSiteSuspendResumeWhileNewerBuildHeld` now expects the temporary 503 for the suspended snapshot. Fails without the fix; operator `make test` + `make lint` green.
