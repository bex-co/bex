## Objective

A service's Metrics tab mounts `ApplicationMetricsCard` exactly once, and that mount is the one carrying data. First settle which pending/SSR mechanism creates the second, permanently-loading mount, then remove the cause — not the symptom.

## Context

- Finding 1 in [finding.md](finding.md): fresh loads of `/services/<id>/metrics` settle with 2 `Application Metrics` headings and 3 `[data-slot=card]` nodes; card 0 stays at `…` forever (no Instances selector), card 1 works. Reproduced on an owned fixture and on `hello-go`.
- One textual render site: `dashboard/src/routes/services.$serviceId.metrics.tsx:128-136`; one title site: `dashboard/src/features/metrics/components/application-metrics-card.tsx:169`.
- Suspects: `dashboard/src/routes/services.$serviceId.tsx:23-24` (`pendingComponent: RouteComponent`, `pendingMs: 0` — the pending copy renders the layout and its `<Outlet/>`), `dashboard/src/features/services/components/service-detail-layout.tsx:156-160` (`service ? <Outlet/> : <PendingTabContent/>`), the metrics route's own `pendingComponent: ServiceMetricsSkeleton`, and SSR streaming/hydration of the pending tree.
- Neither settled heading is inside a `data-skeleton-frame` or an `aria-hidden` ancestor; both are live cards in the one content column.

**Done 2026-10-19 (loopx w4).** Mechanism, with evidence: production SSR HTML for `hello-go`'s Metrics page contains exactly one `Application Metrics` card and it is the dead variant (`Memory Limit … CPU Limit …`, no Instances selector) — so the shell streams the pending-state copy and hydration's working copy is added beside the unadopted shell DOM. The cause is the parent route's `pendingComponent: RouteComponent` + `pendingMs: 0` (`services.$serviceId.tsx`, `static.$serviceId.tsx`): the pending copy renders `ServiceDetailLayout`, whose Apollo read resolves during the wait and flips to the live `<Outlet/>`. A jsdom router probe with the same options reproduces TanStack's own warning ("An `<Outlet />` was rendered inside a pendingComponent") and the child rendering through the pending copy. Fix (w3/m44's shape): a dedicated `PendingRouteComponent` in both parents renders `ServiceDetailLayout routePending` — same chrome, header skeleton + the active tab's `PendingTabContent` skeleton, never `<Outlet/>`, and never the not-found redirect/error branches. Sweep: every service tab and the static tree share these two parents, so all were exposed and all are covered; the databases/Key Value/Blueprint detail parents reuse their page as pendingComponent too but are leaf pages with no `<Outlet/>`, so they cannot leave an orphan tab copy (double query fire à la w3/m44 remains possible there — not this milestone's claim). Total Instances header re-check: not re-probed live this run (no browser); no separate filing without its own probe.
