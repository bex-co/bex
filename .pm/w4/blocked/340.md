# Deleting a service from its own Settings also toasts "That resource doesn't exist or was deleted."

Why: right after confirming a delete, the user sees an error-styled toast saying the resource they just deleted "doesn't exist", next to the success toast. A successful action then reads as a failure.

- **Severity:** minor (contradictory feedback; the deletion itself is correct).
- **Source:** live functional `/qa-find-bugs w4`, pass 7d3e19, 2026-10-19 UTC, `muse.env`, workspace `bex-canary`. Production was pinned to `d5c3373ed`; research is on main `5e75de920`. Both owned fixtures were deleted by this repro.
- **Repro (2/2):** open `/services/<id>/settings#danger-zone` on an owned service → Delete Service → type the sudo phrase → Delete Service. A `MutationObserver` installed on `[data-sonner-toast]` before the click recorded:
  - `qa-20261018-7d3e19-egress` (`srv-dbalnfu804hs73aaebm0`): `success` "Deleted qa-20261018-7d3e19-egress" at +430 ms, then **`error` "That resource doesn't exist or was deleted."** at +776 ms. The page landed on `/`.
  - `qa-20261018-7d3e19-web` (`srv-dbalikgeir4c73eq4g1g`), the first delete, read without the observer: both toasts were visible together after the redirect to `/`.
- **Control (passes, for the reason claimed):** deleting `qa-20261018-7d3e19-grp` from `/env-groups/evg-dbalnsmhvrac73cbss20` → Manage → Delete records only `success` "Environment group deleted" (+969 ms) and lands on `/env-groups`. That page guards the redirect with `!deleteInFlight` (`dashboard/src/routes/env-groups_.$groupId.tsx:104-111, 136-137`); its comment names this exact race.
- **Root cause:**
  - `dashboard/src/features/services/hooks/use-delete-service.ts:42-45` evicts the `Service` from the Apollo cache on success.
  - `ServiceDetailLayout` is still mounted at that moment and watching the evicted entity. It refetches, the server answers not-found, and `resourceNotFound` turns true (`service-detail-layout.tsx:53`).
  - `useNotFoundRedirect` (`common/hooks/use-not-found-redirect.ts:100-107`) then fires `toast.error(common.resourceNotFoundToast)` and navigates home, racing `DeleteServiceCard`'s own `navigate({ to: "/" })` (`delete-service-card.tsx:63`).
- **Fix (target behavior):** an intentional delete from the detail page shows exactly one toast, the success one, and lands on `/`. Follow the env-group precedent: suppress `useNotFoundRedirect` in `ServiceDetailLayout` while that service's own delete is in flight or has just succeeded. Clear the suppression if the delete fails, so a real later not-found still redirects with its toast. Do not remove the eviction: it is what keeps the services list from flashing the deleted row.
- **Blast radius:**
  - `DeleteServiceCard` is rendered once (`services.$serviceId.settings.tsx:352`). `ServiceSettingsPage` serves both `/services/$id/settings` and `/static/$id/settings` (`static.$serviceId.settings.tsx:2`), and `ServiceDetailLayout` wraps both families (`services.$serviceId.tsx`, `static.$serviceId.tsx`). So web, private, worker, cron and static services all share the race; only web was probed.
  - Delete hooks that evict entities: 2 (`use-delete-service.ts`, `env-groups/hooks/use-env-groups.ts:284-285`, which is already guarded).
  - `use-delete-database.ts` / `use-delete-key-value.ts` neither evict nor refetch, so by code they have no race (not probed).
  - Row-action deletes from lists are not under the detail layout.
- **Adjacent classes:** a dead id opened directly or reached by client navigation must keep the w9/m55 redirect and toast (`w4/158`). A delete that fails must keep its error toast and stay on the page. A protected-environment `confirmation_required` result must keep the dialog open.
- **Dedupe:**
  - `w4/158` (done) is about the toast *missing* on direct dead-id visits; this is the opposite case.
  - No open item matches "doesn't exist or was deleted" or the service delete flow.
  - `git log` up to `origin/main` `5e75de920` shows no change to `use-delete-service.ts` or `service-detail-layout.tsx` addressing it.
- **Render:** Render's dashboard returns to the dashboard after a delete with a single confirmation. The exact copy was not compared.
- **Acceptance:**
  - A dashboard test with a real `ApolloClient` + router shows exactly one `success` toast and zero `error` toasts for a detail-page delete, and fails on the current code.
  - Live, the observer probe above on a fresh owned Free web service records only the success toast.
  - A direct visit to a dead service id still toasts.
- **Estimate:** 45m (guard 15m, behavior test 20m, live replay 10m).

## Added evidence — pass b52e07, 2026-10-19 UTC

## Implementation done 2026-10-19 (loopx w4)

- `ServiceDetailLayout` owns a `deleting` flag and passes its setter through `ServiceDeletingProvider` (`dashboard/src/features/services/lib/service-deleting.ts`). Its `useNotFoundRedirect` is armed only while the flag is false.
- `useDeleteService` raises the flag before the mutation and clears it on any refusal (an error, or `confirmation_required`), because the service still exists. On success the flag stays up until the layout unmounts with the navigation home, which matches the env-group precedent. Eviction is kept.
- Outside the layout, the context default is a no-op.
- Deterministic test `features/services/components/__tests__/service-detail-delete-toast.test.tsx` uses a real `ApolloClient`, layout, hook and card, a scripted network, and a held home-route loader so the layout stays mounted through the not-found read:
  - A detail-page delete records exactly one `success` toast ("Deleted web") and no `error`.
  - It fails on the pre-fix code, verified by stashing the two source files.
  - A refused delete followed by a later not-found still toasts and redirects.
  - The `service-detail-dead-id` tests (direct dead id) are unchanged and pass.
- Full dashboard `yarn lint` (typecheck, eslint, knip) and `yarn test` (544 files, 5192 tests) pass. Live observer replay pending the dashboard deploy.
