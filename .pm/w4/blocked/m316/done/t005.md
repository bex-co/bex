## Objective

Check that the dashboard, GraphQL, MCP, REST and Blueprint agree on maxmemory-change semantics for Off and persisted stores, and compare them with render.com.

## Context

- Render documents that a persistence-mode change restarts the store, and that changes to or from Off lose data (render.com/docs/key-value). It says nothing about maxmemory.

## Steps

1. Look for Render's documented or observable behavior on a maxmemory change.
2. Record any divergence in ADR018 and ADR021.
3. File the runtime `CONFIG SET` follow-up if it is still open.

## Files

- `docs/ADR018-render-parity.md`
- `docs/ADR021-keyvalue-management.md`

## Acceptance criteria

- [x] Every surface agrees.
- [x] The ADRs are updated.
- [x] The follow-up is filed.

## Out of scope

- Implementing the runtime switch.

## Result (2026-11-11)

- Surfaces agree: the dashboard confirms (phrase on Off), REST/GraphQL/MCP accept and describe, Blueprints apply.
- Render (render.com/docs/key-value, read 2026-11-11): persistence changes restart the instance and a change to or from Off loses data; the page says nothing about a maxmemory change restarting. So bex's restart on a policy change is itself an undocumented divergence from Render. It is recorded in ADR018's Key Value row as an open gap with its fix filed as w4/569 (apply the policy at runtime with `CONFIG SET`), not as a signed-off difference.
- ADR021 records the restart and the Blueprint decision.
