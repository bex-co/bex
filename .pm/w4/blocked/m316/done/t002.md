## Objective

API and Blueprint callers learn what the dashboard now says: a maxmemory change restarts the store, and on Persistence Off it deletes every key. REST keeps Render's contract.

## Context

- **Writers:**
  - REST `PATCH /v1/key-value/{id}`, and `/v1/redis/{id}`;
  - GraphQL `setKeyValueMaxmemoryPolicy` (`lego/backend/internal/keyvalue/graphql.go:236-241`) and the update mutation's `maxmemoryPolicy` (`:201-216`);
  - MCP `update_key_value` (`keyvalue/mcp.go:180-187`) and `set_key_value_maxmemory_policy` (`:73`);
  - Blueprint `maxmemoryPolicy` (`apps/blueprint_plan.go:613-614`), including the auto-sync worker.
- **Precedents:**
  - w4/m263 described the plan-change restart in the MCP and GraphQL descriptions rather than refusing it.
  - w4/358 made a Blueprint refuse a restart-causing `ipAllowList` on a running Off store (`RefuseBlueprintExternalAccessRestart`, `keyvalue/service.go:1154+`).
- `requireRestartConfirmation` (`:1136-1151`) shows how a `confirm` phrase is checked.

## Steps

1. Update the MCP and GraphQL descriptions for the maxmemory writes so they name the restart and the Off data loss.
2. Decide the Blueprint behavior for a `maxmemoryPolicy` change on a running Off store, consistent with m263's plan decision and w4/358. Implement it, and record it in ADR021.
3. Leave REST acceptance unchanged. The pinned CLI `keyvalues update --maxmemory-policy` must keep working.

## Result (2026-11-11)

- GraphQL `setKeyValueMaxmemoryPolicy` carries a description naming the restart and the Off data loss (`setKeyValueMaxmemoryPolicyDescription`, `keyvalue/graphql.go`), like `updateKeyValuePlan` (w4/m263). MCP `update_key_value`'s description and its `maxmemoryPolicy` argument say the change RESTARTS the store and Persistence Off loses every key.
- REST `PATCH {maxmemoryPolicy}` (and `/v1/redis`) is unchanged and still answers 200; nothing new refuses the pinned CLI's `keyvalues update --maxmemory-policy`.
- **Blueprint decision:** apply, as for a plan change (m263), not refuse as for the external-access restart (w4/358). `maxmemoryPolicy` is a Render field Render's Blueprints apply; refusing it would make a Persistence Off store's policy unchangeable from its own Blueprint, whereas w4/358's restart is a bex-only artifact of the TLS listener. Recorded in ADR021 ("A maxmemory-policy change restarts the store too"). Test: `TestBlueprintAppliesAMaxmemoryChangeToARunningPersistenceOffKeyValue`.
