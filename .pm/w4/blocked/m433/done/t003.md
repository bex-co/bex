## Objective

After a restart that kept the running values, the saved-but-undeployed port, shutdown delay or pre-deploy command still shows in `undeployedChanges` on REST/GraphQL/MCP and in the dashboard's undeployed-changes notice, until a normal deploy applies it.

## Context

- `undeployedChanges` and its notices are bex extensions (ADR004 § w8/m135); the restart path today consumes the pending save for these three fields.

## Steps

1. Make the saved/runtime comparison include the three fields.
2. Test: save → restart → still reported; deploy → cleared.

## Files

- `lego/backend/internal/apps/`
- `lego/backend/internal/deploys/`
- `dashboard/src/features/services/`

## Acceptance criteria

- [x] The notice stays through a restart and clears on the next deploy.

## Done (2026-11-16)

- `servingConfigurationDiffers` compares `releaseRecordSpec`, which now includes `runtime`. The Restart's record keeps the running values, so `undeployedChanges` stays true (reason `historical_release`, which the dashboard notice already handles) until the next deploy clears it. Envtest asserts this. The REST, GraphQL, MCP and dashboard notice read the same status field, so no surface needed a change.
