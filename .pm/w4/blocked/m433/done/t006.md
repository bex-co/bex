## Objective

Check that the service's saved settings, the running release and `undeployedChanges` read the same on REST, GraphQL, MCP and the dashboard after a restart and a rollback, and that the result matches Render's Restart and rollback pages.

## Context

- REST, GraphQL and MCP in `lego/backend/` share one Core; the dashboard consumes GraphQL (`dashboard/AGENTS.md`).
- Render reference: render.com/docs/deploys, render.com/docs/rollbacks, render.com/docs/deploy-hooks.

## Steps

1. Compare each surface's behavior and wording for this milestone's change against Render and against each other.
2. File any drift as follow-up work through `/pm`; record the outcome here.

## Files

- `lego/backend/internal/deploys/`, `lego/backend/internal/apps/`
- `dashboard/src/features/services/`
- `docs/ADR018-render-parity.md`, `docs/ADR004-app-deployment.md`

## Acceptance criteria

- [x] Every surface behaves and reads the same, and matches Render's documented behavior, or the drift is filed.

## Done (2026-11-16, code walk; the live read rides t005)

- REST `POST …/restart` / `…/rollback`, GraphQL `restartServer` / `rollbackService` and MCP `restart_service` / `rollback_deploy` all go through `deploys.Service`'s `targetReleaseConfig`, so every surface carries the same selection. `undeployedChanges` and `undeployedChangesReason` are one operator status field, and REST, GraphQL, MCP and the dashboard notice all project it. Saved settings (`port`, `maxShutdownDelaySeconds`, `preDeployCommand`) keep reading the spec on every surface. `openPorts` reads `App.ServingPort`, so it names the port the Restart serves.
- Against Render: Restart keeps "the exact same Git commit and configuration as the running instance" (render.com/docs/deploys, read 2026-11-16). The rollbacks page lists neither the three fields nor pre-deploy, and ADR004/ADR018 record those cells as bex's choice. Nothing new to file.

## Correction (2026-11-16, t005 live run)

The saved `port` did not keep reading the spec: `settingsPort` read `ServingPort`/`ConfiguredImagePort`, which b946df6ae moved to the running selection, so GraphQL `configuredPort` and REST `serviceDetails.port` read the running port after a save-only PATCH. `configuredPort` now reads `App.SavedPort` (see t005). REST and MCP `port` keep naming the running port, as they already did for image-port services.
