# `services create --from` drops an image service's Docker Command (pinned Render CLI)

Why: after w4/209, `GET /v1/services/{id}` reports an image web/private/worker service's Docker Command as `envSpecificDetails.dockerCommand`, but the pinned Render CLI's clone still cannot carry it, so a cloned image service runs its image entrypoint instead.

- **Source:** follow-up split from w4/209 during `/loopx w4`, 2026-10-08. Verified against the pinned `render-oss/cli` (`v1.1.3-0.20260909214233-a764810a7682`).
- **Cause (upstream):** `pkg/service/clone.go` reads only `startCommand` from `envSpecificDetails` (`startCommandFromEnvDetails`). `pkg/service/create.go` `buildRuntimeEnvSpecificDetails` sends Docker details only for `runtime: docker` (registry credential alone) and native details otherwise; it never sends `dockerCommand` for `runtime: image`. bex create refuses `startCommand` on an image build (w5/090), so no bex read shape can make the clone keep the command.
- **Evidence:** adding a `dockerCommand` assertion to `lego/cli/image_predeploy_clone_contract_test.go` against a read that carries it fails for all three types: the clone POST has no `envSpecificDetails`.
- **Gate:** an upstream `render-oss/cli` change (clone `dockerCommand` into `DockerDetailsPOST.DockerCommand` for image/docker runtimes) and a pin bump. Per `DO_NOT_DO.md`, bex does not fork the CLI.
- **Done when:** the pinned CLI's `create --from` of an image service with a Docker Command sends it, and a contract test in `lego/cli` pins that.
