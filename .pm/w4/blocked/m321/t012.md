## Objective

An audit row with status `success` means the action happened. A service create that is refused after authorization, for example a 409 for a name in use, records no `CreateServerEvent`. A denial still records `error` as today.

## Context

- **Found:** QA loop round 155, 2026-11-12 (pin `8330744bd643`; see the README's round 155 probe).
- **Live repro:** from the signed-in page at 01:37:21Z, `POST https://api.bex.co/v1/services` with body `{"type":"private_service","name":"qa-20261112-r155-pserv","ownerId":"tea-daif693dqjvc73e7as3g","image":{"ownerId":"tea-daif693dqjvc73e7as3g","imagePath":"docker.io/traefik/whoami:v1.10.1"},"serviceDetails":{"plan":"starter","runtime":"image"}}`.
  - It answered `409 {"code":"CONFLICT","error":"name \"qa-20261112-r155-pserv\" is already in use",…}`. The name was the immutable name of the fixture `srv-dbqhbs5jiris73e60t0g`, which had been renamed.
  - `GET /v1/owners/tea-daif693dqjvc73e7as3g/audit-logs?startTime=2026-11-12T01:37:21.449Z` then returned one row: `CreateServerEvent`, status `success`, metadata `{"relation":"can_create"}`.
  - The same refusal through the dashboard's create form (01:32:08, alert "Name is already in use") left `aud-dbqhe65jiris73e60t2g`, also `success`.
  - `GET /v1/services?…&createdAfter=2026-11-12T01:20:00Z` lists only the two real fixtures.
- **Mechanism:**
  - `authorizeAndRecord` (`lego/backend/internal/core/base.go:886-888`) emits an allowed write row at authorization unless the caller deferred it.
  - `apps.Service.Create` (`lego/backend/internal/apps/service.go:2120-2126`) defers only for a dry-run. Every later refusal therefore follows a recorded "allowed" row:
    - the region check (`:2127`);
    - the secret-file name check (`:2130-2139`);
    - the label check (`:2144`);
    - the duplicate name (`:2152-2155`, `errServiceNameInUse` `:2941-2943`);
    - `specFromCreate`'s plan and type refusals.
  - `audit/rest.go:84-89` (`renderStatus`) maps any non-denied row to `success`.
  - w4/m122 (done) applied `WithDeferredAllowedWriteAudit` to the 48 service-feed verbs. The workspace-level create was outside that table.
- **Controls, by reading:** these defer their row until the write lands:
  - `postgres.CreatePostgres` (`postgres/service.go:875`);
  - `keyvalue.CreateKeyValue` (`keyvalue/service.go:568-`);
  - `projects.CreateWithEnvironments` (`projects/service.go:421-`, w4/m321 t010);
  - `environments.CreateWithACL` (`environments/service.go:643-`).
- **Same shape, by reading (not probed):** `envgroups.CreateEnvGroup` (`envgroups/service.go:418-423`) authorizes with no deferral and then calls `createEnvGroupAuthorized`.

## Steps

1. Do t011 with the **deferred** variant. Authorize `apps.Create` under `core.WithDeferredAllowedWriteAudit` and record `CreateServerEvent` with the new service's typed target once `create` has written it. Stamping the target onto a row written at authorization would leave this bug.
2. Give `envgroups.CreateEnvGroup` the same shape. Then grep every `RelCanCreate` authorization and list any other create verb that still records at authorization, placing each one (deferred, or excused with a reason).
3. Tests in `apps` and `envgroups`:
   - a refused create (duplicate name, bad region) records no allowed row;
   - a successful create records exactly one, naming the resource;
   - a denied create still records `error`.

## Acceptance criteria

- [ ] On production, the probe above (409 for a name in use) adds no `CreateServerEvent` row to `…/audit-logs?startTime=<t0>`.
- [ ] A real create of a `qa-` service in the same window adds exactly one `CreateServerEvent`, naming the service (t011).
- [ ] The env-group create follows the same rule, by test.

## Out of scope

- Whether the duplicate-name refusal itself should match Render. ADR018's create row records w4/m19's workspace-unique names.
