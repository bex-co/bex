## Objective

Every create or delete row in the audit log names its resource, as the Key Value and service-delete rows already do. "Who did what" is then answerable from the row alone, on REST, in the CSV export and on the dashboard.

## Context

- **Found:** QA loop round 144, 2026-11-11 (pin `8330744bd643`; see the README's post-release probe).
- **The read:** `GET /v1/owners/tea-daif693dqjvc73e7as3g/audit-logs?startTime=2026-11-11T22:38:11Z`. The `metadata` on each row:

  | Event | `metadata` |
  | --- | --- |
  | `CreateServerEvent` (`qa-20261111-r144-aud`) | `{"relation":"can_create"}` |
  | `CreateProjectEvent` (`qa-20261111-r144-proj`) | `{"relation":"can_create"}` |
  | `DeleteProjectEvent` | `{"relation":"can_create"}` |
  | `DeleteServerEvent` | `{"relation":"can_create","service":"srv-dbqet40fss2c73f208m0"}` |
  | `CreateRedisEvent` | `{"keyvalue":"red-dbqeta0fss2c73f208o0","targetName":"qa-20261111-r144-kv"}` |
  | `DeleteRedisEvent` | `{"keyvalue":"red-dbqeta0fss2c73f208o0","relation":"can_create"}` |

  - The dashboard's Audit Log shows Resource `workspace:tea-daif693dqjvc73e7as3g` for the delete rows.
- **Mechanism:**
  - `renderMetadata` (`lego/backend/internal/audit/rest.go:96-137`) names a resource only from the event's `Target` (`core.SplitTarget`, `:98-100`) and `TargetName`. It copies the authorization `relation` unconditionally (`:122-124`).
  - The Key Value create records a deferred allowed-write event with `KeyValueTarget` and the display name (`keyValueAuditEvent`, `lego/backend/internal/core/audit.go:1033-1043`).
  - Service and project creates are recorded by the plain workspace-level `Authorize(ctx, relation)` (`core/base.go:651`), before the resource has an id. They have no `Target`.
  - **Not traced:** the project delete's path.

- **More rows without a target (round 311, 2026-11-13 17:38 UTC, pin `1c4d721bc8dc`).** `GET /v1/owners/tea-daif693dqjvc73e7as3g/audit-logs?limit=200&startTime=2026-11-13T12:00:00Z` was grouped by event and by the metadata keys other than `relation` and the OAuth keys. Every row of these events carried no resource key:

  | Event | rows |
  | --- | --- |
  | `CreateServerEvent` | 12 |
  | `ApplyBlueprintEvent`, `apps.CreatePlannedBlueprint`, `apps.DisconnectBlueprint` | 6 each |
  | `envgroups.MoveEnvGroup`, `environments.SetEnvGroups` | 2 each |
  | `envgroups.CreateEnvGroup`, `DeleteEnvGroupEvent`, `CreateProjectEvent`, `DeleteProjectEvent`, `DeleteWebhookEvent` | 1 each |

  The rows that do name theirs, for contrast: `DeleteServerEvent` (17, `service`), `ViewConnectionInfoEvent` (79, `keyvalue`/`database`), `apps.SetRoutes`, `deploys.Trigger`, `Suspend/ResumeServiceEvent` (`service`), and the Postgres and Key Value create and delete events.

  Step 1 covers these too: an env group (`envGroup`), a webhook (`webhook`) and a Blueprint (`blueprint`) get their typed target, so every create, delete and move row names what it touched.

## Steps

1. For the service and project creates and the project delete, record the row with the resource's typed target and display name once it exists. Follow the Key Value pattern (a deferred allowed-write event after the write, or the target stamped onto the pending record).
2. Decide whether `relation` stays in REST metadata. It is bex's authorization term, not a Render field. Dropping it, or keeping it only on denied rows, is the parity-first default. Record the choice in ADR018's audit row.
3. Tests in `core`/`audit`:
   - each create and delete verb's row names its target;
   - the CSV export carries the same metadata.

## Acceptance criteria

- [ ] After creating and deleting a `qa-` service and a `qa-` project, their rows' `metadata` carry `service`/`project` with the id and `targetName`.
- [ ] The same holds for an env group create, move and delete, a webhook delete, and a Blueprint create, apply and disconnect (round 311).
- [ ] The dashboard's Resource column names the service or project.
- [ ] Existing Key Value and service-delete rows are unchanged.

## Out of scope

- The CSV `actor` column, which reads the identity's UUID while the dashboard shows the email. It is noted in the probe as unverified against Render's export.
