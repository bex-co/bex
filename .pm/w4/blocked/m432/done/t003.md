## Objective

When the tag a rollback names no longer resolves (deleted, registry unreachable, credential revoked), the rollback deploy ends failed with a reason that names the image, and the live release keeps serving.

## Context

- A failed image pull today surfaces through the rollout failure path; the reason vocabulary lives in the operator's status reasons and `deploys` end reasons.
- Render: "If the image is no longer available or reachable, the rollback fails."

## Steps

1. Reproduce with a registry stub in envtest.
2. Make sure the failure ends the deploy (not an indefinite pending) and the previous ReplicaSet stays live.
3. Test both a deleted tag and an unreachable registry.

## Files

- `lego/operator/internal/controller/`
- `lego/backend/internal/deploys/`

## Acceptance criteria

- [x] The rollback deploy reads failed with an image reason; the service keeps answering from the previous release.

## Done (2026-11-16)

- Deleted tag: the envtest rolls back to a removed `:v1`. The Rollout reads False/`ImagePullFailed` for the rollback's generation, with the image in the message. `rev-2` stays active, its template is untouched, and a digest rollback afterwards goes live.
- **Bug found and fixed:** after the refusal, every later pass failed with `read materialized release N`. A held selected release that never dispatched has no record of its own, and `portRuntimeApp`'s held branch had no fallback. It now reads the target's sources, as the unmaterialized-selection branch below it does (`lego/operator/internal/controller/env_port.go`). `TestEnvPortReadsAHeldSelectionThatNeverMaterialized` covers it deterministically and fails without the fix. The envtest hit it only on some runs. The full suite then caught a second reader: `planReplicas`, inside the hold, reads the selection through `runtimeRecord`. `runtimeRecord` now renders the held serving release without the selection when its own record is missing and the release stopped at its image read (`selectionHaltedBeforeDispatch`: a recorded refusal or a registry wait). Any other missing record still fails. This is covered by `TestRuntimeRecordOfASelectionHaltedBeforeDispatch`, which fails without the fallback, and the m432, w32/m419 and w32/031 envtests passed 4 of 4 runs.
- Unreachable registry: the rollback waits in Deploying with `ImageRegistryUnavailable` while `rev-2` serves, then goes live with the tag's new digest once the registry answers. This is the w32/031 rule every image deploy follows. Render's "is no longer … reachable, the rollback fails" has no stated timeout, so failing a wait is filed separately as w4/692, not changed here.
