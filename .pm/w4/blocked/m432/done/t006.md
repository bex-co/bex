## Objective

Check that a rollback's result (the deploy's `image`, `image.sha`, status and failure reason) reads the same on REST, GraphQL, MCP and the dashboard Deploys page, and matches Render's rollback page.

## Context

- REST, GraphQL and MCP in `lego/backend/` share one Core; the dashboard consumes GraphQL (`dashboard/AGENTS.md`).
- Render reference: render.com/docs/deploys, render.com/docs/rollbacks, render.com/docs/deploy-hooks.

## Steps

1. Compare each surface's behavior and wording for this milestone's change against Render and against each other.
2. File any drift as follow-up work through `/pm`; record the outcome here.

## Files

- `lego/backend/internal/deploys/`
- `dashboard/src/features/services/`
- `docs/ADR018-render-parity.md`, `docs/ADR004-app-deployment.md`

## Acceptance criteria

- [x] Every surface behaves and reads the same, and matches Render's documented behavior, or the drift is filed.

## Done (2026-11-16, code walk; the live read rides t005)

- REST `POST /v1/services/{id}/rollback`, GraphQL `rollbackService` and MCP `rollback_deploy` all call `deploys.Service.Rollback`, so the selection, the row's `image` (the target's reference) and the failure reason are the same on every surface. `image.sha` reads the digest the rollback's own release recorded once it is live, and none while it is open or after it fails, as ADR004 states.
- Dashboard: the Deploys page and the deploy detail show the row's `image`, and the confirmation names the tag behavior. The events feed's Rollback keeps the generic body because that feed carries no image. This is minor, and no follow-up is filed.
- Drift filed: w4/692. An unreachable registry waits (w32/031) instead of failing the rollback.
