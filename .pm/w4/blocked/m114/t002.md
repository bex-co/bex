## Objective

Two scheduled runs showed `pending` together for 6+ minutes, and the elder took 11 minutes past its last attempt to reach `unsuccessful`. Find (with cluster access) whether the projection lagged kube truth or kube truth itself wedged — then make the observed state impossible.

## Context

### The observation (production, 2026-09-17, all times UTC; same fixture as t001)

- 19:12:21 — scheduled run `cron-29827872` starts (same second as the manual `run-2207ebf1` from t001's trigger). Both `pending` together until 19:14:20, with 7 interleaved `p12fail-marker` attempts (19:12:20 … 19:13:00) whose gaps fit no single-job backoff (consecutive 240s→60s→660s→60s gaps; backoff is monotone).
- 19:14:20 — scheduled run `cron-29827874` is created while `29827872` still shows `pending`. Both scheduled runs `pending` together for 6+ minutes.
- 19:18:00 — `29827874` canceled by probe (3 attempts observed: :14:23, :14:36, :14:58 — clean backoff, proving it genuinely executed).
- 19:23:12 — `29827872` flips to `unsuccessful`, `finishedAt` = 19:23:12 (fresh condition time, not backdated): 11 minutes after its last possible attempt, 9 minutes after its successor's creation.

### The paradox (needs cluster truth, not armchair)

`reconcileCronJob` sets `ConcurrencyPolicy: ForbidConcurrent`, enforced by kube-controller-manager from etcd — a tick cannot materialize while a CronJob-owned job is active. `29827874`'s creation at 19:14:20 therefore says `29827872` was terminal-or-absent then; but bex showed it `pending` until a condition timestamped 19:23:12, and `toCronRun` (`app_controller.go:3769`) derives `pending` only from a listed, condition-less Job while `updateStatusIfChanged` persists any flip (full-JSON compare — verified, no suppression). Suspects to rule in/out with `kubectl`: the two Jobs' ownerReferences/UIDs (two CronJobs? UID churn across the config_change deploy?), condition timelines, pod states during 19:13–19:23 (ImagePullBackOff/Pending under pressure would explain attempt-less activity), controller-manager tick evaluations, and the operator's informer resync behavior for that one object. Also resolve the 8-digit numeric suffix vs K8s tick-timestamp naming.

### Fix shape (investigation-owned)

- Whatever the cluster says, the user-visible contract is: at most one active scheduled run; terminal within ~2 polls of the last attempt; a run that outlives its attempts with no reason is a bug, not patience. Candidates (pick by evidence): `startingDeadlineSeconds` so late ticks die instead of landing mid-manual-run, trigger-side mutual exclusion with in-flight scheduled runs, surfacing the wedged pod reason on the run row, a staleness watchdog that re-lists a lone long-pending job direct (bypassing cache).
- Do NOT "fix" by hiding the second pending row in the dashboard — the runs list told the truth; the backend state was wrong.

### Acceptance

- Incident replay (or cluster forensics + targeted regression test) showing the twin-pending state unreachable: trigger during active + late tick yields exactly one active run at every instant.
- `29827872`-shaped delay has a test: attempts stop → terminal within the poll budget.

What static reading DID establish, recorded as leads for whoever holds the
reproduction — **leads, not conclusions**, exactly as this task demands:

**Lead 1 — the 11-minute terminal delay is plausibly correct Kubernetes
behavior, not a bex defect.** `reconcileCronJob` sets no `backoffLimit` on the
cron Job template, so Kubernetes' default of **6** applies (7 attempts total),
with its default per-pod exponential backoff 10s → 20s → 40s → 80s → 160s →
320s (capped at 6m). That sums to **630s ≈ 10.5 minutes** from the first
attempt to the `JobFailed` condition — and `toCronRun` derives `pending` from
a listed, condition-less Job, so a run legitimately reads `pending` for that
entire span and then flips with a FRESH `LastTransitionTime`, which is exactly
the "not backdated" detail the observation flags as suspicious. If this is the
explanation, the DoD bullet "terminal within ~2 reconcile polls of the last
attempt" is asking bex to contradict the Job controller, and the right fix is
**surfacing the in-progress attempt/backoff state on the run row** — not a
watchdog that declares a still-retrying Job dead. Getting this wrong would
mark live, retrying runs as failed.

**Lead 2 — nothing bounds a late tick.** No `startingDeadlineSeconds` is set,
so a CronJob tick suppressed while the schedule is suspended (which
`manualCronRunActive` does for the whole span of a manual run — w6/039) can
materialize immediately on unsuspend, next to whatever is running then. That is
the most promising mechanism for the twin-pending observation, and it is
independent of `ForbidConcurrent`, which governs only concurrent CronJob-owned
Jobs. It remains a hypothesis: it does not by itself explain two SCHEDULED runs
pending together.

**Lead 3 — t001's fix touches the neighbourhood.** `manualCronRunActive`'s
`NotFound` branch read "about to be created" for a manual run whose Job a
cancel had deleted once the cancel slot was overwritten — pausing the recurring
schedule indefinitely. w4/m114 t001 closes that (the settled-run short-circuit
runs first). Whether that also removes an input to the twin-pending window is
unknown and must not be assumed; re-run the reproduction against the fixed
operator before concluding anything.
