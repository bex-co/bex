## Objective

The live replay on 2026-10-05 found that failing runs reached `unsuccessful` promptly, but no surface said why. The DoD bullet "Failures surface promptly … with the Job condition reason visible" failed:

- The run objects carry only `id`, `status`, `startedAt` and `finishedAt`.
- `cron_job_run_ended` details were just `{"status":"failed"}`.
- Render's "Cron Job Run Ended" details require `cronJobRunId` and carry a `reason` object (`nonZeroExit`, `oomKilled`, `evicted`, `timedOutSeconds`).

## Context

- Live: 19 runs of `sh -c 'echo …; sleep 20; exit 3'` on `srv-db1jl28cnepc739umehg`, for example `crr-e4imn1dqo6aklj32egcu` (05:51:27Z). None carried an exit code or reason on REST, GraphQL, the event feed or the dashboard.
- Gaps: `lego/types/v1alpha1/app_types.go` `CronRun` had no reason field; `cronRunFacts` (`lego/backend/internal/store/reconciler.go`) wrote only the status; `toRenderEvent` had nothing to project.

## Implementation (2026-10-05)

- **types:** `CronRun.FailureReason` (closed set `NonZeroExit` / `OOMKilled` / `Evicted` / `DeadlineExceeded`) and `CronRun.ExitCode`, regenerated with `make manifests generate`.
- **operator** (`cron_run_failure.go`): `observeCronRunFailure` reads the cause while the failed Job's Pod exists. It checks `execution.JobFailedReason` for `DeadlineExceeded`, then the Pod's `Evicted` reason, then the app container's terminated state (`OOMKilled`, or a non-zero exit). `cronRuns` carries an observed reason forward after the Pod is collected.
- **backend:**
  - Migration `0140_cron_run_failure_reason` adds `exit_code` / `run_id` to `service_event_facts` and admits reason codes `non_zero_exit`, `oom_killed`, `evicted`, `timed_out`. The rollback is non-lossy.
  - `cronRunFacts` stamps the code, the exit code and the `crr-` id.
  - The feed queries carry `fact_exit_code` / `fact_run_id`.
  - `cron_job_run_ended` details gain `cronJobRunId` and Render's `reason` object on REST and MCP (`toRenderEvent`), and `cronJobRunId` / `exitCode` on GraphQL.
  - Webhooks are unchanged: their payloads are thin and resolve through the events API.
- **dashboard:** the Activity row renders the reason (`services.eventsReason.non_zero_exit`: "The run exited with status {exitCode}.", plus oom_killed, evicted and timed_out, en + zh). `events.graphql` selects `exitCode`, and the types were regenerated from the schema dump.
- **docs:** ADR038 § "Why a run failed".
- **Known divergences (documented):** `oomKilled.memoryLimit` is present but empty because bex does not record the limit. The ended `status` keeps bex's `succeeded|failed|canceled` vocabulary, shared with the other `*_ended` events and the dashboard, rather than Render's `successful|unsuccessful`.

## Acceptance criteria

- [x] A failed run's `cron_job_run_ended` carries `cronJobRunId` and the reason on REST, GraphQL and MCP, and the dashboard row names it (tests).
- [ ] Live, after deploy: a fresh `exit 3` cron run's ended event reads `reason.nonZeroExit: 3` on REST/MCP and `reasonCode non_zero_exit` / `exitCode 3` on GraphQL, and the Activity row reads "The run exited with status 3."

## Out of scope

- Renaming the lifecycle `status` vocabulary to Render's `successful|unsuccessful` (shared contract; separate parity decision).
