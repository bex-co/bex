# A service's build traffic leaves from its published outbound IPs, as Render's does

Why: Render parity. Once `w21/m616` ships, a private package registry or database that allowlists a service's `outboundIps` admits the running service but refuses its build, because build Jobs keep leaving through whichever node they run on.

- **Render (read 2026-11-27):** [dedicated-ips](https://render.com/docs/dedicated-ips), "Do services use dedicated IP sets while building?": "Yes, with one exception. Services use dedicated IP sets for any outbound build traffic, such as package downloads. The exception is Docker image pulls, which use Render's shared outbound IP ranges." So Render's builds leave from the workspace's outbound set, and only image pulls leave from the region's shared ranges.
- **bex:** build Jobs run on tenant-pool nodes (`lego/operator/internal/execution/security.go`) and leave through the node's address. `w21/m616` moves serving pods, cron runs and pre-deploy Jobs onto the fixed Floating IP set and lists "Build Job egress" as out of scope (`.pm/w21/blocked/m616/t003.md`). [ADR125](../../docs/ADR125-stable-tenant-egress.md)'s follow-ups list "Build Job egress through the set, if Render documents its builds using its ranges", which this page now does.
- **Do:** first check on Render that a build step's own requests leave from the region's published ranges (a build command that fetches an IP echo service, compared with the Outbound tab). Then route build Jobs' egress, except image pulls, through the same gateway set as the service, and add build Jobs to `w21/m616`'s matrix check.
- **End state:** a build command that fetches an IP echo service reads one of the service's `outboundIps` on bex, as it reads one of the published ranges on Render.
- **Size:** about 1h after `w21/m616`; promote it if the gateway needs a second policy.
- **Depends on:** `w21/m616`.
- **Source:** w4/m688 t002, a full read of Render's dedicated-ips page, 2026-11-27.

## Parked (2026-11-27)

- **Gate:** `w21/m616` live on production. It is parked on the user's go-ahead for its t002: buying two Hetzner Floating IPv4s and switching every node's Cilium to the egress gateway datapath ([ADR125](../../../docs/ADR125-stable-tenant-egress.md) D9; `/unblock w21`). Until then no tenant egress, build or not, leaves from a fixed set, so the end state cannot be checked.
- **Render's side is settled by its docs.** No Render account is available here (`RENDER_API_KEY` is the key w32/039 also waits on), so the live Render probe was not run. It is not a gate: dedicated-ips says builds use the workspace's outbound set "for any outbound build traffic, such as package downloads", and "Workspaces without dedicated IPs use Render's default outbound IP ranges". So on Render a workspace like every bex workspace builds from its published ranges, image pulls included.
- **Done, shipped ahead of the gate:**
  - The policy needs no second rule. Build pods in `bex-build` already carry `app.bex.co/workspace`: BuildKit Jobs through `build.AppBuildPodLabels`, kpack through its pod template, static publish through `execution.PodLabels`. ADR125 D5's selector therefore takes them, and D5 now says so, instead of excluding build Jobs.
  - `scripts/verify-egress-gateway.sh` adds a build pod in `bex-build` under production's own `build-boundary.yaml` namespace and policies. It passed locally on 2026-11-27: the build pod left from its node before the policy and from the egress IP after it on 443. `bex-build` still refused 18001 through the gateway, and every earlier check was unchanged.
  - ADR018's outbound IPs row and ADR125 D5, D10, Consequences and Follow-ups now cover builds.
- **Filed:** `w4/757`. The kubelet's pull of an image-backed service's image is node traffic, which the pod-selected policy cannot redirect. On Render that pull leaves from the shared ranges.
- **Next, once `w21/m616` is live:** on production, deploy a disposable service whose build command fetches a bex-owned source echo (or an IP echo service) and prints the address. Check that it reads one of the service's `outboundIps`, then close this note.
