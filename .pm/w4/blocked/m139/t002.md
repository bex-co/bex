**Gate: a read of production data.** The pinning stream lives in production's `usage_source_streams`/`usage_source_health` rows and bex-api's `usage:` logs, which the drain session has no sanctioned access to. Needed from the user: either run the query below and paste the output here, or approve a read-only query against the production database.

```sql
-- every stream still dragging `through`, with its first non-healthy or missing hour this month
SELECT s.resource_kind, s.service_id, s.kind, s.source, s.expected_from, s.expected_through,
       min(h.window_start) FILTER (WHERE h.state <> 'healthy') AS first_unhealthy,
       count(*) FILTER (WHERE h.state = 'healthy') AS healthy_hours,
       count(h.*) AS recorded_hours
FROM usage_source_streams s
LEFT JOIN usage_source_health h USING (resource_kind, service_id, kind, source)
WHERE s.workspace_id = 'tea-d98210cbbpdc73dcrkvg'
  AND h.window_start >= date_trunc('month', now() AT TIME ZONE 'utc')
GROUP BY 1,2,3,4,5,6
ORDER BY first_unhealthy NULLS LAST;
```

**What code reading already establishes** (`lego/backend/internal/store/usage.go`): `evaluateStreamCoverage` walks each stream **contiguously** from `max(expected_from, monthStart)` and stops at the first hour that is missing or not `healthy`. `aggregateUsageCoverage` takes the minimum over active streams. So a single missing or degraded hour at `00:00Z` on the 1st, on any one open stream, pins `through` to the month start for the rest of the month, and nothing re-records an old window unless the collector retries it. A `through` of exactly `2026-09-01T00:00:00Z` in two separate observations (w4/048 and this pass) fits a **systematically missing first hour of the month**, for example a month-boundary gap in the collector or the rollup. A deleted resource's never-closed stream would pin at its last healthy hour instead, which is not what was observed. Likewise, `degradedSources` lists a source if **any** window this month was non-healthy, so one Prometheus outage hour badges it all month. Both are separate from whether dollars are missing, since `usage_hourly` totals do not read these tables. Which stream it is, and whether the first hour is the gap, is what the query above answers.
