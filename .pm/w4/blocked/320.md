## Root cause and concrete correction

- `lego/operator/internal/build/native.go:243–269` generates the primary image and calls `nativeNodeTools`. `nativepnpm.go:42–46` supplies **only pnpm**, leaving Yarn to the selected official base. The pinned Node26 base in `native.go:95` does not carry Yarn; the executable image probes establish that directly.
- `nativeresolve.go:50–104` rewrites the primary FROM and adds optional tools. Its shared JavaScript companion path is restricted to **Ruby and Python** by the two-entry map at **119**. The comment at117 saying primary Node already has these tools is false for26. Native version selection itself is working and must remain unchanged.
- A reviewed Yarn supplier already exists: `nativeresolve.go:121–146` copies `/opt/yarn-v1.22.22` from the pinned default Node24 image and creates `yarn`/`yarnpkg` links. Reuse this primitive for primary Node as well as the two companion consumers; extract Yarn-only instructions rather than copying another Node binary or repeating an installer. Keep a reviewed Yarn-bearing source explicit so changing the primary default to26 cannot silently remove the supplier.
- Put the Yarn layer before source and authored commands, under the toolchain image's PATH, alongside the existing pnpm setup. Preserve npm/npx, pnpm/pnpx, Node version selection, Ruby/Python companion behavior, primary-language tools, optional Bun, exact authored commands/PATH and static extraction. The Yarn source digest/version must participate in generated/cache inputs. No floating install, tenant workaround, CLI fork or new API field is needed.
- `native_test.go:1029–1033` currently exempts26 from its Yarn control, and its report uses `yarn --version || echo absent`. Strengthen this to execute the repaired contract instead of treating missing Yarn as a passing Node26 control. The supplier's current comments and tests explicitly explain why the gap survives the otherwise successful pnpm fix.
