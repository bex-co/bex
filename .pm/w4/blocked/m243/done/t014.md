## Objective

Since m243, a prebuilt-image web service runs its image's resolved **digest** (`<repo>@sha256:…`). The saved-configuration check still compares the serving container's image string with the saved **tag** (`spec.image`), so the two never match. Every such service reports `undeployedChanges: true` with reason `saved` from its first deploy onward. The service header and Settings show "Saved changes aren't live yet. Use a standard deploy to apply them.", or while suspended "Resume the service, then deploy to apply them.", although nothing was saved. A standard deploy does not clear it. Target behavior: a release that runs the digest resolved from the saved tag counts as running the saved image. `undeployedChanges` is `false` after a first deploy and after any standard deploy with no other saved change. A real image change, an image override (`image_override`) and a rollback (`historical_release`) keep their current reasons.

**Severity:** major (a permanent false "not live" banner on every new image web service; its stated remedy does nothing, so it teaches users to ignore the banner). **Source:** live `/qa-find-bugs w4` loop run 6406, 2026-10-27 UTC (`muse.env`, workspace `tea-daif693dqjvc73e7as3g`, pin `7d6ac874c51d`).

The deploy row records `image: docker.io/mendhak/http-https-echo:latest`, `imageSha: sha256:82b7f82a…`. In run 828c, a rolled-back whoami reported `servingImage: docker.io/traefik/whoami@sha256:80f8bb74…`, which is the digest form the pods run.

Root cause:

- `lego/operator/internal/controller/app_controller.go:685-692`: for `HasImagePorts()` apps, `resolveImageNetwork` returns `prefix + "@" + digest` (`image_network.go`), and `dispatchRuntime` puts that string in the pod template.
- `lego/operator/internal/controller/saved_configuration.go:168-178` `servingConfigurationDiffers`: for `app.Spec.Repo == ""`, it sets `imageDiffers` and `different` when the served container's `Image != app.Spec.Image`. For an image-port web service that is always true (digest vs tag).
- `saved_configuration.go:199-212` `undeployedChangesReason`: there is no `ActiveReleaseConfig()` for a standard release, so the reason falls through to `saved`.
- Git-built services (`Repo != ""`) skip the image comparison. Configured-port image services that are **not** image-port run the tag and match. Both are unaffected (code read; not probed live).

**Live control (run 5c47, 12:08–12:13Z, same pin):** a Git-built Docker web service (`https://github.com/bex-co/bex`, root `examples/hello-go`, `srv-dbg98luq7drs739qkpsg`) read `undeployedChanges: false` right after its first deploy went `live`. That is consistent with the `Repo != ""` branch skipping the image comparison, and it isolates the defect to prebuilt-image (`Repo == ""`) services.

## Steps

1. Compare the release's **source** image (the tag it was resolved from: `ImageNetworkStatus.Source` or the release record's own source field) with `spec.image`, not the resolved digest. Keep comparing digests when the saved image itself is a digest.
2. Decide and document what an upstream tag move (`latest` re-pointed) means. Render re-pulls on each deploy, so a moved tag is not a "saved change". Do not report it as `saved`.
3. Regression tests in `saved_configuration` / `undeployed_reason_test.go`: an image-port web app serving `repo@sha256:X` resolved from saved `repo:latest` gives `false`. Saved image changed to `repo:v2` gives `saved`. A trigger override gives `image_override`. A rollback gives `historical_release`. A configured-port (non-image-port) image app and a Git-built app keep today's results.
