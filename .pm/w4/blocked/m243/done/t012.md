## Objective

Every rollout of an image-port service drops traffic. This covers a config change, a manual deploy and an env-group "Save and deploy". Traefik's raw `503 no available server` is answered for 1–5 s at the moment the new pod takes over, although the Deployment itself rolls with surge 1 / unavailable 0 and a 60 s drain (ADR004 § zero-downtime). Since m243, image-port services include **every new Docker/image web service**, besides w6/m148's Git-built Docker private services, which lose internal traffic the same way. Target behavior: throughout a rollout, the stable Services (`<app>` and the slug Service) always have at least one ready endpoint that listens on the serving primary port. A 0.25 s poll of the public URL across a same-port deploy answers `200` every time, as it does for a configured-port (non-image) service. A port-changing deploy keeps the t007 guarantee (no request reaches a pod without the listener) and must not open the same gap.

**Severity:** major. A zero-downtime promise is broken on every deploy of every new Docker/image web service, and the response is Traefik's raw error, not bex's. **Source:** live `/qa-find-bugs w4` loop run e9ba, 2026-10-27 UTC (`muse.env`, workspace `tea-daif693dqjvc73e7as3g`, production pin `b4726243e74f`).

**Re-probe on pin `7d6ac874c51d` (run 42ca, 2026-10-27 11:03–11:05Z):** a dashboard-created `docker.io/traefik/whoami:latest` web service with **no** port (`web-image-v1`, `port 80` / `openPorts [80]`, `srv-dbg89fmq7drs739qkpc0`), polled every 0.25 s across a GraphQL `triggerDeploy` at 11:03:53Z, gave 67 × `200` and **1 × `503 no available server` at 11:04:06**. The gap persists on the pin that carries t007–t011, and it is not specific to the configured-port variant.

Root cause (read at HEAD; the ordering is unchanged since the deployed pin):

- `lego/operator/internal/controller/image_network.go:181-191` `privateServiceProjection` pins both stable Services' selector to `labelRevision = ActiveImageNetwork().Revision` for every `HasImagePorts()` app. Before promotion that is the **serving** revision. A `restartedAt` bump or new release is a new release generation, so the candidate pods carry a new `rev-N` even when image and port are unchanged.
- `lego/operator/internal/controller/app_controller.go:3106-3112` calls `promoteImageNetwork`, which rewrites the selector (`image_network.go:222-226`), only after `deploymentRolloutReady` (`app_controller.go:3717-3721`) holds. That requires `dep.Status.Replicas == replicas`, meaning the old ReplicaSet has already been scaled away. Its pod is terminating in the 60 s preStop drain, so its endpoint is no longer ready, and the ready new pod does not match the old-revision selector. The Service has zero ready endpoints until the operator's next pass rewrites the selector and EndpointSlices and Traefik propagate. The gap was 1 s and 5 s in the two samples, which depends on reconcile latency.
- The comment at `image_network.go:190` ("A port change must not route to old replicas that lack the new listener") justifies the pin for **port changes** only. On a same-port rollout it buys nothing and costs this gap.
- `web_image_rollout_test.go` (`TestWebImageRouteFollowsTheServingNetworkUntilPromotion`) asserts the Ingress port only. Nothing asserts endpoint continuity.

## Steps

1. Same-port rollouts: when the candidate's port set equals the serving network's, the stable Services must not pin a revision the Deployment controller is about to scale away. Either select without `labelRevision`, or move the selector to the candidate once the candidate has a ready pod and before the old ReplicaSet scales down. Name the choice in the code and in ADR089.
2. Port-changing rollouts: get the same continuity without routing to pods that lack the listener. For example, promote as soon as a candidate pod is Ready rather than after the rollout completes, or hold the old ReplicaSet until the selector has moved. Check this against t007's guarantees: failed deploy keeps serving, rollback goes `live`.
3. Regression tests (envtest): through a `restartedAt` rollout of an image-port web service and of an image-port private service, the Service's EndpointSlices never reach zero ready endpoints. A port change never selects a pod without the new port. Configured-port services are unchanged.
4. Update ADR004 § zero-downtime and ADR089 with the rule.

**Done 2026-10-28 (loopx w4), code + tests; the live criteria are owned by t006's replay.** `privateServiceProjection` now pins the serving revision only while the candidate network's ports differ from the serving network's (`changesImagePorts`). A same-port rollout (a Manual Deploy, an env-group "Save and deploy", a restart, a new image on the same ports) keeps both stable Services selecting every runtime pod, so the new pod is an endpoint before the Deployment drains the old one. Every sample in this task was such a rollout. Port changes keep the pin and t007's guarantee. **Split out as w4/428:** a port-changing rollout still has the drain-to-promotion window.
