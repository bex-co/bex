## Objective

`permanentRolloutPullFailure` (`lego/operator/internal/controller/app_controller.go:4099`) also closes a first deploy's row early (`update_failed`, e.g. "the image … was not found in its registry"). By the `stopsFirstRelease` comment, it deliberately keeps the pod retrying, "whose registry errors can still clear within it". So a pull that clears serves under a failed row, as the crash case did.

Pick one rule and implement it:

- **(a)** stop the release at the early settle, as t001 does for crashes. A pull that would clear needs a new deploy, as on Render, where a failed deploy is final.
- **(b)** don't close the row early for a pull that may still clear, and close it at the deadline.

Recommend (a): a terminal row must describe what runs.

## Context

- Round 205 saw the early settle for a missing tag (`nginx:qa-r205-no-such-tag`, `update_failed` 22 s after `created`).
- Round 214's flaky-crash case shows the consequence of a terminal row over a release that keeps retrying.

## Steps

1. Record the decision and its Render basis in this task and in ADR004's three-timer section.
2. Implement it.
3. If (a), reuse t001's verdict write.

## Acceptance criteria

- [ ] Envtest: a first release with a missing image tag either reaches 0 replicas within one pass of `update_failed` (a), or keeps its row open until the deadline (b).
- [ ] Envtest: an image pull that succeeds after the early settle never serves under a failed row.

## Out of scope

- Pull failures over a serving release, which already restore the served template.

## Decision and outcome (2026-11-14)

**Decision: (a), stop the release at the early pull settle.** Render pulls a prebuilt image as part of the deploy and fails the deploy when the pull fails ([Deploy a prebuilt Docker image](https://render.com/docs/deploying-an-image)); a failed deploy is final and the service runs again only through a new deploy ([Deploys](https://render.com/docs/deploys)). `PermanentPullFailure` only matches answers that need a new deploy (missing tag/repo, denied auth, invalid name) after its 90 s grace, and the pre-deploy step already treats the same answers as final. Transient registry errors keep the deadline. Recorded in ADR004 (§ startup crash paragraph and the w1/m179 bullet).

Implemented by t001's single verdict write: the pull settle goes through the same `settleFailedRolloutMessage`. `TestEarlyPullFailureSettleDoesNotStopAFirstRelease` was replaced by `TestEarlySettleStopsAFirstRelease` (pull and crash: Failed, `failedFirstRelease` true, reason kept), and the `stopsFirstRelease` comment that said "only the deadline stops" was rewritten.
