## Objective

Model desired versus safely applied persistence so a newly accepted mode cannot roll Valkey onto stale durable files.

## Context

The finding has two snapshot→journal losses, including SAVE plus an ordinary-restart control. KeyValueStatus has phase/generation/conditions but no applied persistence state; all writers converge on the operator.

## Steps

1. Write a concrete transition table for journal-snapshot, snapshot, off and legacy empty mode, naming the authoritative data and allowed rollout at each step. Distinguish deliberate Off data loss from durable-mode conversion and prevent resurrection of historical files.
2. Place a generation-aware gate before applyKeyValueStatefulSet can replace the serving pod's persistence flags. Decide the minimal persisted progress needed for retry, desired-mode reversal and controller/process restart; keep existing phase vocabulary or update types/codegen explicitly.
3. Keep pending/failure status truthful while the old authoritative dataset remains usable. Preserve protected-environment and authorization gates; no backend database dependency in the operator.

## Files

- `lego/types/v1alpha1/keyvalue_types.go (only if new transition status is required)`
- `lego/operator/internal/controller/keyvalue_controller.go`
- `Generated KeyValue CRD/deepcopy files if types change`

## Acceptance criteria

- [x] The transition table names an authoritative dataset and completion predicate for every mode pair.
- [x] Unsafe rollout cannot bypass conversion through retries, stale generation or a direct CR writer.
- [x] Failure leaves the previous safe dataset and exposes a truthful pending/failed condition.

## Out of scope

- Fleet migration of unrelated stores or global changes to free-plan persistence.
- Deleting historical files merely because their timestamps are older.
