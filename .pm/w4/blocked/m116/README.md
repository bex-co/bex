## Outcome (2026-09-20) — four of six findings shipped, three gates left

### Shipped

**t001 — `bex psql`/`pgcli` provision their own TLS trust.** A new `lego/cli/internal/pgtrust` package intercepts the `psql`/`pgcli` invocations in the launcher (`lego/cli/main.go:62-67`), in the same interception class as the existing root `--version` path, resolving the target through cobra's own `RootCmd.Find` so it cannot drift from the upstream command tree. It reads the database's `serverCaCertificate` (the w4/m95 field) over the upstream authenticated client, writes it to a 0600 temp file, and sets `PGSSLROOTCERT` for the child — removing the file after the delegated command exits. TLS is never downgraded and no connection string is rewritten. An explicit user choice always wins (a set `PGSSLROOTCERT`, or an existing `~/.postgresql/root.crt`); a 503 "no CA yet" becomes a named refusal naming the tool, the database and `verify-full` instead of an opaque psql failure; an internal-only database and an unmodified upstream `render` binary are both untouched. `scripts/psql-compat-verify.sh`'s stale `sslmode == require` precondition now asserts `verify-full` plus a certificate-not-key CA and exports it for the unmodified binary it drives.

**t002 — a private Key Value can be published.** `KeyValuePatch.apply` wrote `spec.ipAllowList` and never `spec.public`, and the dedicated `PUT .../ip-allow-list` route wrote the CR itself, so a store born private could never become public on any surface: the update returned 200, the CIDR round-tripped, and `bex kv-cli` kept dialing the unroutable in-cluster `.svc` host. A nonempty allowlist on update now publishes — Render's own enabling event, which bex honored at create only — and every entry point converges on the one `apply` (the PUT route now delegates to `UpdateKeyValue`). The rule is deliberately one-way: clearing the allowlist opens the endpoint to all source IPs (Render's empty list means "open", not "off") and must not tear down an endpoint running clients are using, so withdrawing is an explicit act through the new `public` field on PATCH, `setKeyValuePublic`, or `update_key_value(public:false)`. Managed Postgres gained the same explicit control (`setDatabasePublic`, `update_postgres(public:)`) — the acceptance criterion's "PG mirror" — but deliberately not the implicit allowlist rule, because a private Postgres is an explicit choice against a public default. ADR021 records both.

**t003 (half) — a job that cannot be submitted says so.** `bex jobs create` returned **201 carrying a job that was already `failed`**, ~12-16ms later, with no reason on REST, GraphQL or MCP: the Kubernetes refusal was logged server-side and dropped. `Create` now returns the refusal (`jobSubmitError`), naming the job id so the record is findable and carrying the k8s cause verbatim. An RBAC refusal maps to **Unavailable (503), not Forbidden** — the caller passed `AuthorizeApp`; it is bex-api that lacks the grant, and telling a caller they lack permission they hold would be a lie. The failed record still lands, so history survives.

**t006 — `null` where an array is declared, fixed at the one boundary.** Render's public OpenAPI declares every list response `{"type":"array"}` with no `nullable`. `core.WriteJSON` (`internal/core/http.go:234`) — the single REST serialization boundary, 127 call sites — now substitutes an empty slice for a nil one, with two deliberate exclusions where `null`/`""` would be the regression (`json.Marshaler` implementors such as `json.RawMessage`, and byte slices, which encode as base64 strings). Seven nested-field `null`s that sit _past_ that boundary were fixed at their own shared helpers: `core.AllowListCIDRs` (both datastores' `ip-allow-list` routes), agent-session capabilities, account deletion-preview, the unbound-store API-key list (also MCP `list_api_keys`), the datastore-log direct-pod fallback, git claim selections, and push notification-settings overrides — plus MCP `get_postgres_ip_allow_list`'s `entries`. GraphQL was already clean (graphql-go builds `make([]interface{}, 0, len)`; all 22 non-null list fields checked).

### Correction to the ticket's premise (t006)

**The two live repros were not bex-api bugs.** `GET /v1/workflows` has written the literal `[]` since it was stubbed (`api/server.go:1350`) and `GET /v1/sandboxes` has built `make([]SandboxEnvelope, 0, len(out))` since July (`sandbox/rest.go:80`, `b5700dc45`); both were re-verified through the real mux. The `null` comes from the **pinned upstream CLI**: `listSandboxesPage` returns a nil slice on an empty page (`render-oss/cli@a764810a7682 pkg/sandbox/repo.go:48-50`), `client.ListAll` accumulates into a nil slice, and `printJSON` marshals that to `null`. So `bex ea sandboxes list -o json` → `null` is exactly what `render` prints against render.com — bex **matches** Render here, and `.pm/DO_NOT_DO.md`'s "do not fork or vendor a CLI" forbids the only fix. DoD bullet 6 is therefore met in the only sense available; the real `null`s the finding led us to were the nine above.
