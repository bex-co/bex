## Objective

After suspend → resume, a free Postgres reads `available` while its external data path stays dead (`SSL error: unexpected eof`) for 6+ minutes across 4 consecutive probes. Make `available` mean the data path is up — or report the transitional state honestly.

## Context

- Live repro 2026-09-17, fixture `dpg-daloivd2r12c73cnghbg` (free, deleted after the sweep):
  - Pre-suspend: `bex psql -c 'SELECT 1'` exits 0 (with `PGSSLROOTCERT` provisioned per t001).
  - Suspend (direct `POST /v1/postgres/{id}/suspend`, empty body — the CLI needs `--confirm`, previewed without it) → `202 suspended`; resume via `bex postgres resume --confirm` → converges to `available` in ~70s.
  - Then 4 consecutive `bex psql` failures over ~6 min: `SSL error: unexpected eof while reading` (server `2a01:4f8:c01e:3d1f::1:5432`).
  - ~~Ruled out: allow-list intact (`162.224.81.143/32` still present)~~ — **this line is wrong and is the actual cause; see the correction below.** Egress IP unchanged (the CLI's own gate still resolves the same address, and clearing the list moves the failure to the client-side gate, proving the server was being reached).
- ~~Cause UNVERIFIED~~ — **cause identified 2026-09-21 by `w9/m164`; the candidates below are unsupported by this evidence.**
- Related: two isolated first-connection EOFs also preceded the first successful psql earlier in the sweep (then self-healed). If the same mechanism, one fix covers both; if not, split it. **See the correction: Happy-Eyeballs explains these without any self-healing.**

## Correction 2026-09-21 (`w9/m164`, recorded by `/loopx w9`)

**The "ruled out" line checked the wrong address family, and the thing it ruled
out is the cause.** `162.224.81.143/32` is an **IPv4** `/32`, while every failing
probe above names the server as the **IPv6** literal `2a01:4f8:c01e:3d1f::1`.
`*.db.bex.co` publishes both `A 49.12.20.236` and `AAAA 2a01:4f8:c01e:3d1f::1`,
so a dual-stack client connects over IPv6, and the SNI proxy enforces the allow
list against that real IPv6 source (`pg-sni-proxy/main.go:248` →
`sniproxy.AllowedBy`). No route matches, the connection is closed with nothing
written (`main.go:253`), and psql reports it as `SSL error: unexpected eof while
reading`. The allow list was intact **for IPv4** and did not contain the address
the connection actually came from. The pinned CLI's pre-connect gate resolves
the caller through `api.ipify.org`, which answers IPv4 only, so it passes — the
product says "you are allowed", then drops the connection.

**t004's own premise did not reproduce.** On 2026-09-21, on a fresh free fixture
with **both** families allow-listed, suspend → resume went `creating → available`
and `bex psql -c 'SELECT 1'` returned the probe row on the **first** `available`
reading and on 5 consecutive probes over ~2.5 min. There is no evidence of a
resume that lies about `available`, and none of the listed candidates (proxy
route not re-registered on wake, backend still starting, stale
`ExternalHost`/certificate) is supported by the 2026-09-17 evidence once the
address family is read correctly.

**Disposition:** this task is **closed as not-reproduced**. The real defect — the
dual-stack allow-list trap and the illegible denial — is owned by `w9/m164`
(Dual-stack IP allow-list trap), including the verifier leg that would have
caught it. Re-open only if a post-resume failure is observed on a fixture whose
allow list covers **both** families, with proxy-side verdict evidence attached.

## Steps

1. Reproduce on demand (create → psql-ok → suspend → resume → psql) and capture proxy-side verdict per handshake (denied vs unrouted vs backend-refused) plus CNPG pod/endpoint state across the resume window.
2. Fix the layer at fault: re-register/retain the proxy route across suspend-resume, and/or hold status out of `available` until the first backend handshake succeeds (a readiness probe, not optimism).
3. Add a regression that suspends, resumes, waits for `available`, and asserts a real query succeeds within the DoD budget.
