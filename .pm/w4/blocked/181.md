# Key Value metrics sidecar is CPU-starved: production `valkey-instances` scrapes time out

Why: the redis_exporter sidecar's fixed 10m CPU limit throttles it ~98%, so Prometheus scrapes of production Key Value stores hit the 10 s timeout and the Key Value metrics panel (memory, connected clients) goes empty for real tenants.

Evidence (w4/m144 acceptance + live QA 2026-10-03, read-only): target `valkey-instances` for `red-d9p49kdrtmes73c34ovg-0` is down with `context deadline exceeded` — scrape duration 10.0 s (= timeout), scrape success 0.2–6% over ~23 h, exporter container CFS-throttled ~98%. The other production store scrapes in 3.1 s at 93% throttling — next to fail. Only down target of 79 ([done/m144/live-acceptance.md:45](done/m144/live-acceptance.md)); this is the "separate follow-up still to file" named on the m144 line of this README.

Mechanism:

- `lego/operator/internal/controller/keyvalue_controller.go:167-172` `kvExporterResources()` = `guaranteedResources("10m","32Mi")` (requests == limits; fixed, plan-independent; unchanged since `a87f90bcf`, w5/m24). The comment assumes it "only polls INFO"; 10m ≈ 1 ms per 100 ms CFS period ≈ 100 ms of CPU across a whole 10 s scrape.
- The sidecar (`:801-814`, image `oliver006/redis_exporter` pinned at `:101`) sets only `REDIS_ADDR`/`REDIS_PASSWORD`, so every default collector runs (INFO ALL, CONFIG GET, SLOWLOG, LATENCY incl. histogram, Go runtime metrics).
- `deploy/gitops/base/prometheus.yaml:740-759` scrapes every 60 s with the default 10 s timeout and keeps only `redis_.*` — the Go/process series the exporter pays to produce are dropped.

Fix:

1. Raise the sidecar to a budget sized from the measured scrape CPU (e.g. `guaranteedResources("50m","32Mi")`, keep Guaranteed QoS). Cost is negligible: the tenant ResourceQuota is aggregate (`deploy/gitops/base/tenant-quotas.yaml:19,22`), the workspace quota counts objects, and the sidecar is not billed (KV server plans are 100m/100m/500m, `lego/types/tiers/tiers.yaml:115-127`).
2. Cut per-scrape work with exporter env (verify names against the pinned version): `REDIS_EXPORTER_REDIS_ONLY_METRICS=true`, `REDIS_EXPORTER_EXCLUDE_LATENCY_HISTOGRAM_METRICS=true`; `REDIS_EXPORTER_CONFIG_COMMAND=-` only if no consumed `redis_*` series needs CONFIG.
3. Pin budget + env in an operator unit test beside the KeyValue pod-spec tests. Changing the template rolls every Valkey StatefulSet (brief restart per store) — ship it as a deliberate rollout.

Done when: after the operator rollout, `up{job="valkey-instances"}` is 1 for every production store over 24 h, `scrape_duration_seconds` stays well under 10 s, exporter throttling is far below 98%, and `/keyvalue/red-d9p49kdrtmes73c34ovg` shows continuous memory/connection series.

## Implementation (2026-10-03)

- `kvExporterResources()` is now `guaranteedResources("50m","32Mi")` (`lego/operator/internal/controller/keyvalue_controller.go`). It stays Guaranteed QoS, so the pod stays Guaranteed with the Valkey container. Quota and billing check: the sidecar is not billed, because KV plans bill the server tier in `tiers.yaml`. The per-namespace ResourceQuota (`lego/backend/internal/store/namespaces.go` `quotaForPlan`, Hobby 3 CPU requests / 1 Key Value) absorbs the +40m. The LimitRange max (8 CPU) is not affected.
- New `kvExporterEnv()`, with names checked against the pinned image (v1.89.0, revision `cd5941f`, `main.go`/`exporter.go`): `REDIS_EXPORTER_REDIS_ONLY_METRICS=true`, `REDIS_EXPORTER_EXCLUDE_LATENCY_HISTOGRAM_METRICS=true` (skips LATENCY LATEST + HISTOGRAM), `REDIS_EXPORTER_CONFIG_COMMAND=-` (skips CONFIG GET \*), `REDIS_EXPORTER_INCL_METRICS_FOR_EMPTY_DATABASES=false`. The only series anyone consumes are `redis_memory_used_bytes` and `redis_connected_clients` (`lego/backend/internal/metrics/source.go`), plus `up`. Both come from INFO. No alert rule in `deploy/gitops` reads `redis_*`.
- Tests are in `keyvalue_exporter_test.go`. The budget is 50m/32Mi, and every container keeps requests == limits on every Valkey plan, so the pod stays Guaranteed. The trim env and the password Secret ref are pinned. A drift guard scans the backend metrics source and `deploy/gitops/base/*.yaml`, and fails if anyone starts consuming a `redis_*` series the trimmed exporter does not emit.
- Verification: `make test` and `make lint` pass on HEAD plus this change, in a clean worktree. The shared tree's controller package currently fails in `TestDesiredReplicas`/activity tests because a parallel agent has uncommitted `app_controller.go` work in flight. That failure is not related to this change.
- Rollout note: the pod-template change rolls every Valkey StatefulSet (a brief restart per store) on the operator deploy.

**Remaining (gate):** ship, then the release pipeline deploys the operator. After that, QA observes for 24 h, read-only: `up{job="valkey-instances"}` = 1 for every production store, `scrape_duration_seconds` well under 10 s, exporter CFS throttling far below 98%, and continuous memory/connection series on `/keyvalue/red-d9p49kdrtmes73c34ovg`.
