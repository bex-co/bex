## Objective

A first release, with no serving release, rolls exactly one ReplicaSet when HTTP discovery chooses a port its image doesn't declare. Discovery's result moves only the Services' target port and the route.

## Context

- Target behavior: [README § Target behavior](../README.md#target-behavior).
- Render's default health check is "TCP socket probes to one of your service's open ports". A port-agnostic default probe for a first release is parity, not a new rule.
- The exec health-probe binary (`health_probe.go:49-57`) already ships for services with a Health Check Path. An "any open port" check reads the container's own listening sockets.
- Keep three guards:
  - `webImageHTTPSelectionGuardsServing` and `webImageReleaseHeld` (w4/m320) for a deploy over a serving release;
  - the HTTP probe on the chosen port for a service with a Health Check Path;
  - one roll for a listener on its declared port (w2/078).

## Steps

1. For a first release with discovery pending and no Health Check Path, project a probe that passes on any non-reserved listening port. Keep the container ports and `PORT` at their dispatch values (or leave the ports out while pending), so `selectWebImageHTTP` changing `PrimaryPort` and `Ports` leaves the template unchanged.
2. Make sure the switch back to the normal projection after discovery doesn't itself roll. It must keep the same handler for that release, as w2/078 kept the TCP probe.
3. Make t001's envtest case pass. Keep w2/078's and w4/m320's envtests green.

## Files

- `lego/operator/internal/controller/deployment_projection.go`
- `lego/operator/internal/controller/web_image_http.go`
- `lego/operator/internal/controller/health_probe.go` and the probe binary, if the any-port mode lands there

## Acceptance criteria

- [x] t001's case rolls one template from dispatch to Running, and the Services target 10000.
- [x] A first release on its declared port, a deploy over a serving release, and a service with a Health Check Path keep their current templates and tests.

## Out of scope

- The discovery window's length (`webHTTPDiscoveryWindow`).
- Private-service discovery (w4/m323).

## Outcome (2026-11-14)

- `checksAnyOpenPort` (`deployment_projection.go`): a first release (no `ActiveRevision`, no `ServingNetwork`) of a web service whose image chooses its own HTTP port, with no Health Check Path, no edge cache and an operator that knows its own image, runs Render's default check on all three probes and declares no container ports. The check is `health-probe open-port` (new mode in `cmd/health-probe`, `internal/healthprobe/openport.go`): it reads `/proc/net/tcp{,6}` for LISTEN sockets and passes when the pod address accepts a connection on any of them, skipping `ReservedImagePorts`. `PORT` is 10000 throughout (w4/615). Discovery therefore changes only the Services and the route.
- Step 2: the choice is kept for the release while its stored template (same revision) carries the open-port probe, so going live does not roll it; the operator-upgrade helper-image freeze (`probeStale`) covers it too.
- Kept: w4/m320's `/` guard and hold for a release over a serving one; the HTTP check on the chosen port with a Health Check Path; TCP on the known port for every later release; w2/078's single roll.
- Deviation: an edge-cached first release keeps the port-bound shape (its sidecar fronts the primary that discovery moves), and so does an operator without its own image; both may still roll twice. ADR004 § "A first web image release rolls once" records this.
