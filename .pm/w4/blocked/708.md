# 708 — An environment group's "Save and deploy", link and unlink rebuild every linked Git-backed service from source, where the same save on the service's own Environment tab reruns the serving build

Why: ADR013 (w4/m180) defines an environment `deploy` as "the current build with the new values, never a source build", and keeps rebuilding for the separate "Save, rebuild, and deploy". A group's sparse patch has the same three modes (ADR013, w2/m73), and the env-group page offers them through the same editor (`features/env-groups/components/env-group-editors.tsx` renders `ServiceEnvironmentEditor`). Whatever the mode, a group write to a linked Git-backed service runs a full BuildKit build, so "Save and deploy" and "Save, rebuild, and deploy" do the same thing there. Each group edit takes a build (about 80–95 s here) per linked service. It spends build time that the plan's pipeline minutes meter. It can fail on a build error that has nothing to do with the change, and it can pick up a moved base-image tag. The same edit made on the service's own Environment tab reruns the serving image. The rollout code says the same thing: `deploys/platform_rebuild.go` notes that "a restart, rollback or configuration rollout reuses an existing artifact".

- **Source / severity / estimate:** live `/qa-find-bugs w4` round 1152, 2026-11-18 02:43–02:55 UTC, pin `14eaa71b98e5`, workspace `bex-canary`. All fixtures were deleted afterwards (DELETE 204, then GET 404). **Major:** a deploy mode does the work of the rebuild mode, on every linked service, with a build's cost and failure modes. No value is wrong. ~1h.
- **Probe** (REST through the session cookie):
  1. `POST /v1/env-groups` created `qa-20261118-r1152-eg` with `MESSAGE=qa-eg-1`. `POST /v1/services` created a free Docker web service from `https://github.com/bex-co/bex` `main` (`examples/hello-go`, which serves `$MESSAGE` at `/`), with `autoDeploy: "no"`. The first deploy went live on commit `936b61bab203` and served `OK`.
  2. `POST /v1/env-groups/{eg}/services/{srv}` (link) opened deploy `service_updated` `dep-dbuh2ede7qgs73b3472g`. It went `build_in_progress` 02:45:16 → `update_in_progress` 02:46:49 → `live` 02:47:31. Its build log over that window starts `==> Build queued`, `==> Building from https://github.com/bex-co/bex@936b61b`, `#1 [internal] load build definition from ./examples/hello-go/Dockerfile`, then pulls `golang:1.24-bookworm` (100 lines). The URL then served `qa-eg-1`.
  3. With `autoDeploy: "no"`, `PUT /v1/env-groups/{eg}/env-vars/MESSAGE {"value":"qa-eg-2"}` returned 200 and opened no deploy. The service read `undeployedChanges: true`, `undeployedChangesReason: "saved"`. That matches the Auto-Deploy gate ADR018 records for group writes (w2/m94), so it is not part of this note.
  4. After `PATCH /v1/services/{srv} {"autoDeploy":"yes"}`, the same PUT with `qa-eg-3` opened `dep-dbuh4b07ud6s739sdf20` (`service_updated`). It again went through `build_in_progress` for 83 s, and its build log again reads `==> Building from https://github.com/bex-co/bex@936b61b` and pulls the Go base image. The URL then served `qa-eg-3`.
  5. With `main` moved to `5d946be30`, Auto-Deploy back off, linking a second group (`qa-20261118-r1152-eg2`) opened `dep-dbuh65o7ud6s739sdf30`. Its build log reads `==> Building from …@936b61b` and it rebuilt for 94 s. **Control:** so the rebuild uses the release's pinned `spec.buildCommit` (`app_controller.go:2272-2285`), not the branch head. No unreviewed code ships; the defect is the build itself.
- **Cause:**
  - `lego/backend/internal/envgroups/service.go:1157-1161`: `rollLinkedService`, the one rollout every linked-service write goes through, applies the change and calls `s.Rollout.SelectServedImage`.
  - `lego/backend/internal/rollout/served_image.go:39-55`: `SelectServedImage` selects a release image only for a **prebuilt-image** service. It returns at once when `a.Spec.Repo != ""` (w4/m418 fixed the image-backed half).
  - So for a Git-backed service the patch is just `spec.RestartedAt = stamp`. Per ADR013 § "`deploy` reruns the serving build", `spec.restartedAt` is part of a source-built artifact's identity, "so the bump alone dispatched a full BuildKit build".
  - The service-level environment save solves exactly this in `lego/backend/internal/secrets/batch.go:500-518`. `selectServedBuild` → `servedArtifact` (`:202-226`) reads the served release's `ResolvedImage` and writes `rollout.SelectReleaseImage(a, image)` for Git-backed services too. That helper is private to `secrets`, so `envgroups` never reaches it.
  - Callers of `rollLinkedService`:
    - `rollLinked` (`service.go:1233-1254`): link and unlink, owner and Blueprint;
    - `rollOne` (`service.go:1375-1386`): a group value save in `deploy` mode (`patch.go:355`, from `rollGroupPatch` `patch.go:219` and the single-key writes, `service.go:904`).
  - The explicit `SaveModeRebuild` goes separately through `RebuildService` (`patch.go:346-352`) and is correct to build.
- **Fix:**
  - Target behavior: a group write in `deploy` mode, and an owner's link or unlink, roll each linked Git-backed service onto the image it serves now, with the new group values, and no build. The deploy row records that image and its commit, as the service-level "Save and deploy" does.
  - Keep building, as the service-level path does, for:
    - `rebuild` mode;
    - a static site (its environment is build-time, and `servedArtifact` already returns "" for it);
    - a service with no live release.
  - The service-level path answers `ENVIRONMENT_DEPLOY_NEEDS_LIVE_RELEASE` when there is no live release. A group fan-out must not fail the whole save for one such service. It should build that one, or list it in `pendingServiceIds`; the implementer records which.
  - Move the served-build selection (`servedArtifact` + `SelectReleaseImage`) next to `SelectServedImage` in `internal/rollout`, as one helper both packages call. Then `rollLinkedService` selects the served build for Git-backed services too.
  - Tests:
    - In `envgroups`, a group value save, a link and an unlink on a Git-backed service with a live release write `spec.releaseConfig` with that release's image and record no build.
    - `rebuild` mode still calls `RebuildService`.
    - A static site still rebuilds.
    - The w4/m418 image-backed cases and `secrets`' Git-backed regressions (w4/m180, w4/667) stay green.
- **Blast radius:**
  - `rollLinkedService` has two callers, `rollLinked` and `rollOne`, and every group surface reaches them: REST group env-var / secret-file writes, the sparse patch, link and unlink; GraphQL and MCP group mutations; the dashboard group editor; create with `serviceIds`; and Blueprint link and sync.
  - The fix is global for Git-backed web, private and worker services. Static sites are excluded by rule. Cron jobs are not probed (see Unverified).
  - Moving `servedArtifact` touches `secrets/batch.go`'s two callers (`:137` probe and `:513` selection). Both need their regression tests to stay as they are.
- **Adjacent classes:**
  - A service whose live release is gone (no history) keeps today's build.
  - A suspended service keeps w4/m234's hold.
  - An Auto-Deploy-off service keeps the w2/m94 gate for value writes and w32/m423's ungated owner link. This note changes how they deploy, not whether.
- **Unverified:**
  - I did not check whether these builds are counted in the workspace's pipeline-minutes usage.
  - I did not probe a cron job, a worker or a private service linked to a group.
  - I did not probe an unlink's deploy, a secret-file change or the dashboard editor's "Save and deploy" button. All of them reach `rollLinkedService` by code reading.
  - I did not check whether Render rebuilds on a group change: its docs say a group change "kicks off a new deploy". This note rests on bex's own `deploy` rule (ADR013 w4/m180) and the three save modes the group page offers.
- **Render:** not checked; see Unverified.
- **Done when:** on production, with a Free Docker service from a public repo linked to a qa group and Auto-Deploy on, `PUT /v1/env-groups/{eg}/env-vars/MESSAGE` opens a `service_updated` deploy whose build-log window has no `==> Building from` line, that goes live in the time a restart takes, and that serves the new value. Linking a second group does the same. "Save, rebuild, and deploy" on the group still shows a build.

## Fix (2026-11-18, `/loopx w4`)

- `rollout.Tracker.SelectServedBuild` (`lego/backend/internal/rollout/served_image.go`) now holds the served-build selection that only `secrets` had: `ServedArtifact` (moved from `secrets/batch.go`) for a source-built service, `SelectServedImage` for a prebuilt image, nothing for a static site, unknown history or a suspended service. `secrets` calls it and still words `rollout.ErrNoLiveBuild` as `409 ENVIRONMENT_DEPLOY_NEEDS_LIVE_RELEASE`.
- `envgroups.rollLinkedService` calls it through `selectServedBuild` (`envgroups/service.go`). So a group value save in `deploy` mode, a single-key write, a secret-file write, an owner's or Blueprint link and an unlink each open a `config_change` release that reruns the served build. The row records that build's image and commit. `rebuild` mode still goes through `RebuildService`.
- **Recorded choice (no live release):** a linked Git-backed service with no live build keeps building, as today. The group write does not fail, and the service is not listed in `pendingServiceIds`, because it does deploy.
- **Also keeps building:** a source-built service with a deploy in flight (`rollout.Tracker.DeployInFlight`). The group's release waits behind that deploy (Render's Wait), so rerunning the build serving at save time would roll the deploy's newer code back, the w4/667 class. The build checks out the pinned `spec.buildCommit`, so no other code ships. Residual: a group write made while a deploy is still rolling builds once, where the service-level save waits and reruns the build that deploy leaves.
- ADR013 § "`deploy` reruns the serving build" records the group rule.
- Tests: `TestEnvGroupDeploysRerunTheServedBuildOfAGitBackedService` covers link, `PatchEnvironment` deploy, the variable PUT, a secret-file write and unlink. `TestEnvGroupRebuildStillBuildsAGitBackedService` covers rebuild mode. `TestEnvGroupDeploysStillBuildWithNothingToRerun` covers a static site, no live build and a deploy in flight. `rollout` has `TestSelectServedBuild` and `TestDeployInFlight`. The first test fails with the old `SelectServedImage` call, and the in-flight case fails without the guard. The w4/m418 image-backed test and `secrets`' w4/m180 / w4/667 regressions pass unchanged.
- **Gate (release, no user action):** the next production deploy must pin the `w4/708` fix commit (`git merge-base --is-ancestor <sha> <deployed sha>`). Then a worker replays the Done-when probe on production in `bex-canary`: a group `PUT …/env-vars/MESSAGE` and a second group's link each open a `service_updated` deploy with no `==> Building from` line that serves the new value, and the group's "Save, rebuild, and deploy" still builds.
