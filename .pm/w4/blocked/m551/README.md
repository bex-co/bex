## Definition of done

On dev-4, then on production once the pin carries the change:

- From a Postgres database's **Apps** section, **Deploy app** for PgHero and for pgAdmin each creates a web service in the database's region, project and environment, with the credentials the dialog showed.
- Each app opens from **Open app**, logs in with those credentials and shows the database: pgAdmin's tree has its server without a manual "Add server", and PgHero's Queries page lists statements.
- The connection is the database's internal URL, set server side; the browser never receives a connection string it did not already have the right to read.
- A caller without `can_view_sensitive` on the database, or a Developer in a protected environment, gets the action disabled with a reason.
- Deleting the app's service makes the section offer **Deploy app** again.
- REST and MCP gain no verb; ADR018 has a "Postgres admin apps (pgAdmin, PgHero)" row recording that Render also offers this only in the dashboard.

## Source + Goal linkage

- **Source:** `/pm-brainstorm one more aspect of render parity for w4`, 2026-11-20, item 2 (dashboard-only Render features no API pin sees). Filed by `/pmx them to w4`.
- **Render:** changelog 2024-06-04, "Quickly deploy PostgreSQL admin apps from the Render Dashboard"; [render.com/docs/postgresql-apps](https://render.com/docs/postgresql-apps): pgAdmin and PgHero; the database's **Apps** page → **Deploy app** → a dialog with autogenerated credentials (optionally customized) and billing details. Render creates "a standard web service" in the database's region with "the smallest compute specs possible according to the app's requirements" and "automatically connects it to your database over your private network". The credentials are env vars: `PGHERO_USERNAME`/`PGHERO_PASSWORD` and `PGADMIN_DEFAULT_EMAIL`/`PGADMIN_DEFAULT_PASSWORD`. The app then appears in the service list, and editing its env vars "can break the app's connection to your database".
- **bex today:** the database page (`dashboard/src/routes/databases.$databaseId.tsx`, `dashboard/src/features/databases/components/database-detail-navigation.tsx`) has no Apps section, and neither the code nor the board mentions admin apps beyond a `pgadmin` repository in the Blueprint corpus. Image services, secret files and internal addresses all exist.
- **Goal linkage:** Render parity first ([ADR008](../../../../docs/ADR008-vision.md#render-parity-first)); Managed Postgres ([ADR009](../../../../docs/ADR009-postgresql-management.md), [ADR018](../../../../docs/ADR018-render-parity.md) § Managed Postgres).
- **Expected outcome:** a tenant manages and profiles their database with Render's two tools in one click, without installing a client or exposing the database publicly.
- **Why now:** Render has offered it for 29 months with no board owner; every building block is in place, so the work is assembly plus a server-side verb.
- **Risk:** both apps' official images are on Docker Hub, whose anonymous quota can stall a new docker.io image service while [w4/429](../429.md) is blocked. t002 sets each port explicitly so no image-port discovery read is needed, and prefers a non-Docker-Hub registry if t001 shows Render uses one.
- **Render parity:** included (t007): GraphQL and the dashboard; Render has no REST or MCP surface for admin apps.
- **Open point (the proposal's recommendation, not a user decision):** the image, plan, port, service name and connection variable follow Render's bundle (t001). Where the bundle settles nothing, t002 records bex's choice where Render is uncaptured: the apps' official images (`ankane/pghero`, `dpage/pgadmin4`) on bex's smallest paid plan that runs them. ADR018's new row lists each such value as open until a capture confirms it.
- **Open point settled (t001, 2026-11-22):** Render's bundle names every value, so none is bex's guess: PgHero is `docker.io/ankane/pghero:latest` on free; pgAdmin is built from `render-examples/pgadmin` (not `dpage/pgadmin4` directly, whose file capability fails under no-new-privileges) on starter with a 1 GB disk; the service is named `<app>-<database id>`; the connection is `DATABASE_URL` for PgHero and `servers.json` + `pgpassfile` for pgAdmin. bex sets PgHero's port (8080) rather than detecting it.
