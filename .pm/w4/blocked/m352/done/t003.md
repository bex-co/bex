## Objective

REST `POST /v1/services/{id}/shell-ticket`, GraphQL `createShellSession`, native SSH (raw `ssh` and `render ssh`) and the Web Shell agree: a service with a live deploy and a deploy in progress opens a session on its serving instance, and keeps it open until that instance stops.

## Steps

1. Exercise all four surfaces during a `pre_deploy_in_progress` deploy (raw `ssh` and `render ssh` need a disposable `qa-` SSH key, deleted afterwards).
2. Compare against Render: its CLI "verifies a live deploy" (ADR035 § Context). Capture what Render does to an open session during a deploy, if a Render account is available, and record it in ADR035.

## Acceptance criteria

- [ ] The four surfaces agree with the target behavior. Any drift is filed as a follow-up.

## Outcome (2026-11-14)

- All four surfaces go through one gate: REST `shell-ticket` and GraphQL `createShellSession` → `CreateShellSession` → `sshSessionReady`; the Web Shell and native SSH (raw `ssh`, `render ssh`) → `ResolveSSHSession` at connect and every tick. Tests pin each during `Building`/`Deploying` (mint, resolver, web-shell stream, native single-channel stream).
- Render check (render.com/docs/ssh § Automatic session closure, 2026-11-14): Render closes sessions when "the service is redeployed or restarted", and "you cannot SSH into an instance that is no longer running"; zero-downtime deploys keep the old instance until the new one is healthy. bex closes when the instance is replaced, not when a deploy starts. Recorded in ADR035 § Sessions across a deploy; no ADR018 divergence needed.
- Not done here: the live four-surface exercise on production with a disposable `qa-` key, and a live Render comparison (no Render account in this run). Both ride t006's production replay.
