# 682 — A git-built web service's rebuild answers with the new body 2–4 s before its deploy row reads `live`

Why: Render moves traffic to a new release when its deploy goes live, and [w4/m320](done/m320/README.md)'s DoD asks that the new body never answer before the row reads `live`. The operator now switches traffic once, to one instance, but on a git-built service the row still trails that switch by a few seconds.

- **Source / severity / estimate:** w4/m320's closing replay, `/loopx w4` 2026-11-16 06:46–06:55 UTC, pins `14af7282d9ac` / `971a79648213` (both carry `c18fbeac1`), workspace `bex-canary`. **Minor**: one clean switch, every poll `200`, and the gap is inside w5/m369's 10 s verdict bound. ~1h.
- **Probe:** a Free Docker web service from `bex-co/bex` `examples/hello-go` with no `PORT` (`qa-20261116-m320b-go`, `srv-dbtabadhm8qs73bgl4dg`, deleted afterwards). Run `PUT …/env-vars/MESSAGE` and then `POST …/deploys {"clearCache":"clear"}`. Poll the `.onbex.co` URL every ~0.6 s and `GET …/deploys?limit=1` every ~1.3 s.
  - `dep-dbtadlkeqavs73ai1jcg`: new body first at 06:50:06.89, `finishedAt` 06:50:09.05 (2.2 s).
  - `dep-dbtag7gjgo0s73diqvv0`: new body first at 06:54:44.63, the row still `update_in_progress` at 06:54:47.87, `finishedAt` 06:54:48.29 (3.7 s).
  - Control: an `imageUrl` change on a no-port nginx service closes 0.8–1.1 s after its switch (`dep-dbta9k422v0c7382u69g`, `dep-dbtabcthm8qs73bgl4g0`).
- **Cause (unverified):** two candidates, not yet told apart.
  - The control plane spaces watch-driven projector passes by `max(minWatchPassGap, 3 × lastPass)` plus up to 250 ms of jitter (`lego/backend/internal/store/reconciler.go:490-514`), so a slow pass delays the next record.
  - Or the operator writes the settled status a pass after it moves the Services on this path (`lego/operator/internal/controller/image_network.go`, `deployment_projection.go`).
  - Separate the two by reading the App's `status.activeRevision` change time (`kubectl get app -o yaml` managedFields, or the operator log) against `finishedAt`.
- **End state:** across three git-built rebuilds on production, the poll that first returns the new body comes no earlier than one deploy-row poll (≤1.5 s) before the row reads `live`, as on the image path.
- Related: [w21/064](../w21/blocked/064.md) (the old 24–31 s operator-side lag, now down to seconds).

## Traced and fixed, 2026-11-16 07:01–07:12 UTC (`/loopx w4`)

- **Cause: the operator, not the projector.** A live replay on production (pin `971a79648213`, `bex-canary`, `qa-20261116-w4682-go` / `srv-dbtakbseqavs73ai1jt0`, deleted afterwards: DELETE 204, GET 404; QA session revoked) watched the App CR, the Services and bex-api's pass metrics next to the body and row polls:

  | Deploy | Services → new revision | New body | App status names it active | Row `finishedAt` |
  | --- | --- | --- | --- | --- |
  | `dep-dbtamfkeqavs73ai1k30` | 07:07:57.57 | 07:07:58.03 | 07:08:00.16 | 07:08:00.33 |
  | `dep-dbtao2fhaims738pkb4g` | 07:11:34.57 | 07:11:35.27 | 07:11:38.96 | 07:11:39.22 |

  The projector closed the row 0.2–0.3 s after the operator's write, so its watch-kick spacing is not the lag. The operator wrote the status naming the release active 2.6–4.4 s after its promotion pass moved the Services. In between, that pass ran `protectServingImage` (`live_tag.go`): the per-app registry credential checks, the `live-<generation>` tag PUT and a repository listing that resolves every tag one request at a time against zot. All of these ran before the status write (`reportRolloutProgress`, and `settleReady` on the Running pass). An image outside the App's own repository returns from it at once, which is why prebuilt-image deploys closed within about 1 s.
- **Fix:** `protectPublishedImage` runs the protection after the status naming the release active is written, and writes what it records separately. The image digest still goes out in the same write, as w4/m320 t011 requires. Regression test: `published_image_protection_test.go` reads the stored App when the fake registry receives the tag. It fails with `["rev-2"]` without the fix, for both the settling and Running paths.
- **Remaining gate (clears by itself):** a production deploy whose pin contains this fix, `fix(operator): a built release reads live as soon as it serves, before its image is tagged (w4/682)` (check with `git merge-base --is-ancestor <sha> <deployed sha>`). Then a worker replays three git-built rebuilds as above and closes this note if, in each one, the new body first answers no more than one row poll (≤1.5 s) before the row reads `live`.
