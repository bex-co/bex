## Objective

Postgres, Key Value and cron pods use the t002 per-environment policy. Existing App pods gain `environment-id` in one deliberate rollout, so production moves to the new model without a partition.

## Context

- Database and Key Value pods already carry `environment-id` (`database_controller.go:1098-1099`, `keyvalue_controller.go:754`).
- Their peer policies currently admit App pods by `network-isolation` (`environment_network_policy.go:41-80`, `keyvalue_internal_network.go:53-59`).
- Cron pods got the isolation label in w4/m185 t003 (`reconcileCronJob`).
- Round 177 did not probe a datastore across a toggle.

## Steps

1. Point the datastore and Key Value client selectors at `environment-id`. Keep the store's own Jobs (backup, purge, export) admitted as today.
2. Give cron Job pods `environment-id`.
3. **Migration order:** roll existing App pods to carry `environment-id` while the old label-based policies still admit them. Only then switch the selectors, so no pod is refused in between.
   - Document the order in the commit.
   - Confirm a workspace with an isolated environment keeps intra-environment traffic through the upgrade.

## Acceptance criteria

- [ ] An App in an isolated environment reaches that environment's Postgres and Key Value across an isolation toggle with no refused connection, and a datastore outside it stays refused.
- [ ] The upgrade rollout is the only restart this milestone causes.

## Outcome (2026-11-14)

Done. The datastore peer policy, the Key Value internal-proxy clients and the per-App policy admit `[network-isolation=<env>, environment-id=<env>]`, and the store Jobs are still admitted. Build datastore reach targets an isolated environment by `environment-id`. Cron and pre-deploy pods carry `environment-id`. **Migration changed from the planned rollout:** nothing restarts. `relabelAppPods` adds `environment-id` to running App pods in place on the upgraded operator's first pass, through the existing `bex-operator-pod-labels` admission. Templates adopt it lazily. `network-isolation` stays mirrored on pods in place, so an old bex-api running next to the new operator (or the reverse) keeps the boundary. Not verified live here; t006 replays it.
