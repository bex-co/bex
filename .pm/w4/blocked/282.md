# 282 — Deploy Blueprint enables before the first preview has reviewed the file

Why: the primary deploy action should wait through the initial preview delay, so a user can review the resources or missing-file error before deployment becomes available.

- **Severity:** minor. A short UI availability gap, reproduced on two fresh pages. No CreateBlueprint or Sync was submitted, no workload or Blueprint was created, and no server-side validation bypass, charge or provisioning failure is claimed.
- **Estimate:** 55m: hook fix/Simplify 10m, shared-caller verification 10m, meaningful regressions 25m, live UI/Render comparison 10m. Keep as a sub-hour inbox note.
- **Source:** continuous functional `$qa-find-bugs`, pass a318, 2026-10-12 local / 2026-10-13 UTC, user-selected w4, muse.env through the login helper. Research HEAD includes `aac3a6f78`; product code unchanged.
- **Goal linkage:** ADR008 usable hosting, ADR049 Blueprint review/apply semantics, ADR018 Render-compatible Blueprint creation and ADR006 shared API contracts.

   - **02:48:35.536Z:** disabled.

   - **02:48:35.949Z:** disabled again. The available interval is **404ms**. No clock, network response or product code was changed.

**Expected:** from the render that first completes the raw repo/branch inputs, the loading/review state blocks Deploy through the 400ms debounce and actual preview request. Once settled, valid, missing/invalid and transport-error cases retain their existing policies.

**Actual:** the old debounced inputs still say skip, hiding pending state for the first 400ms even though raw inputs make the creation action available.

## Root cause and concrete fix

- `dashboard/src/features/blueprints/hooks/use-blueprint-preview.ts:40–47` retains previous inputs for 400ms. At **49**, empty previous branch/repo makes `skip=true`. At **63–66**, raw-vs-debounced inequality correctly makes `settled=false`. But **78** returns `!skip && (loading || !settled)`, suppressing that known pending state.
- `dashboard/src/routes/blueprints.new.tsx:108–126` explicitly intends to keep Deploy disabled until fetch/parse. Its canSubmit reads raw source/branch but this hook's false loading, and `previewBlocks` is false when preview is null. The blank review follows the same wrong loading value in the render at **320 onward**. Both consumer predicates need the existing loading contract to be accurate.
- The hook's declared boolean loading field can express the fix without schema or API changes. Return pending for input mismatch independently of skip, for example **`loading: !settled || (!skip && loading)`**. Preserve skipped/null preview when raw inputs are incomplete. Clearing raw inputs is already blocked by the create page's source/branch checks; do not emit a new request while inputs are skipped.
- Preserve the documented settled transport-error fallback in new.tsx:110–112: it permits the backend to revalidate. Do not “fix” this by globally requiring non-null preview, changing error semantics or removing debounce. Missing/invalid settled previews still block; takeover-only validation retains its current confirmation policy.
- **Pre-settle behavior:** the first render after the raw source becomes complete must show pending and a disabled primary button, before any timer advances or response arrives. An effect that only disables it after the delay leaves the observed gap.
- Pinned Apollo Client **4.1.3**, actual `react/index.js:6` exports `hooks/useQuery.js`. Its `useOptions:85–106` maps skip to fetchPolicy standby; the hook's own guard above is what suppresses unsatisfied input readiness. React **19.2.3** state initializer/effect paths were already read during the shared-clock research; the ordinary live timing matches the retained-state plus delayed effect mechanism.
- Backend passing boundary, source-audited: `lego/backend/internal/apps/blueprint.go:986–1044` independently discovers the requested file and compiles/plans it before admission. The missing-file UI response and source justify a minor UI classification. Actual create was deliberately not exercised, so no stronger backend outcome is asserted.
