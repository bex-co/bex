## Objective

A liveness restart gives the process Render's shutdown window, `maxShutdownDelaySeconds` (default 30 s), between SIGTERM and SIGKILL, as a deploy or a manual restart does. It does not give the 60-second drain on top. t001's drain now returns at once for an instance whose check fails, so the drain's seconds left in the pod grace only lengthen the SIGKILL wait.

## Mechanism

- The arithmetic: 60 s of liveness failures (10 s × 6; `lego/operator/internal/controller/deployment_projection.go:104`, `:145-154`, `:434-439`) plus the full pod grace of 90 s comes to about 150 s.
- How the grace is spent:
  - The kubelet runs the preStop drain first (`healthProbeDrainHandler`, `health_probe.go:81-96`). The drain checks once, fails, and returns at once.
  - SIGTERM follows. The process ignores it, so the kubelet waits out the rest of the grace before SIGKILL.
- Where the grace comes from: `terminationGracePeriodSeconds` = drain + `maxShutdownDelaySeconds` = 60 + 30 (`deployment_projection.go:611`, `:620-630`, `drainSeconds` `:557`).
- The kubelet's liveness kill uses `livenessProbe.terminationGracePeriodSeconds` when it is set, else the pod's (`setTerminationGracePeriod`, `pkg/kubelet/kuberuntime/kuberuntime_container.go:1390-1408` at v1.34.9, production's version). There is no feature gate on that path.
- The milestone README (§ Mechanism, last bullet) rejected the probe-level grace while the preStop was a native `sleep 60`, because a shorter grace would have cut the sleep. Since t001 the drain is an exec that returns at once when the check fails, and a liveness kill only happens after the same check has failed six times. That objection no longer applies to the liveness path.
- Render: SIGTERM, then SIGKILL after `maxShutdownDelaySeconds` (default 30 s). Its health-restart path is not documented separately (README § Unverified). The same process on Render would restart at about 60 + 30 = 90 s.

## Fix (target behavior)

- Set `livenessProbe.terminationGracePeriodSeconds` = `maxShutdownDelaySeconds` (default 30) + the drain check's timeout (`healthCheckTimeoutSeconds`, 5 s, `deployment_projection.go:101`), on every pod that uses the checked drain (`p.drainCheck && usesHealthProbeBinary`).
  - Keep the pod's `terminationGracePeriodSeconds` = drain + delay, so a deletion still drains a healthy instance (w1/m154, w8/180).
  - Pods with a native `sleep` preStop (no helper) keep today's grace, because there a shorter grace would cut the sleep.
- A pod is restarted only when its own liveness check has failed six times. An instance that recovers in the instant between that sixth failure and the drain's own check would have its drain cut to the probe grace, then get the kubelet's 2-second minimum before SIGKILL. Record that trade-off in the code comment and in ADR004 § Rollout headroom.
- **Amend DoD 2** to name both fixtures:
  - a process that exits on SIGTERM restarts no later than 75 s after its checks start failing;
  - one that ignores SIGTERM restarts no later than 60 s + `maxShutdownDelaySeconds` + 15 s (≤ 105 s by default).

## Tests

- Projection unit test, for a web service and a private service, with and without `maxShutdownDelaySeconds`: the liveness probe carries `terminationGracePeriodSeconds` = delay + check timeout, and the pod keeps drain + delay.
- A worker and a disk-attached service, which have no drain, carry no probe-level grace.

## Done — 2026-11-16

Each fails when its half of the change is reverted.
