## Objective

A build-command or start-command edit saved in Settings opens a config-change deploy that goes `live` in 13–30s — and the running container executes the *previous* image's baked command. The edit is stored (the API serves it back) but never takes effect until an unrelated rebuild (manual deploy, deploy hook) happens to bake it in. Make artifact-class config changes rebuild, so the deploy Settings promises ("Service will redeploy with the new build command") is the deploy the platform runs.

## Context

### The observation (production, 2026-09-17)

Native-runtime (`builder: native`) free web service `qa-20260917-web` (`srv-dalo003ssesc73e0la40`), created from Public Git URL `https://github.com/render-examples/express-hello-world` (deleted at the end of the QA run). Three Settings saves in sequence, each confirmed through its dialog:

1. Env var `QA_TEST_VAR=qa-hello-123` → `dep-daloaq300vpc73cofreg`, Config Change, live in 16s.
2. Start command → `sh -c "echo QAENV:$QA_TEST_VAR && npm start"` → `dep-daloc1300vpc73cofrh0`, Config Change, live in 13s.
3. Build command → `npm install && echo QA_BUILD_MARKER` → `dep-dalohe52r12c73cngh9g`, Config Change, live in 30s.

None of the three emitted Build started/ended events (the Events tab shows only Deploy started/ended), none printed build steps (only the synthetic narration lines — see t004), and all three resolved the rev-1 image `…-qa-20260917-web:gen-1@sha256:f825b7…`. The API serves the new commands back (`GET /v1/services/{id}` → `startCommand: "sh -c \"echo QAENV:$QA_TEST_VAR && npm start\""`, `revision: rev-6`), so the spec mutation persisted.

The complete instance-filtered log of the rev-7 pod (`…-724ngr3t07n0q3fr6mrm`) shows it runs the rev-1 baked command — npm start with no echo:

```text
11:29:32 PM  [724ng]
11:29:32 PM  [724ng] > express-hello-world@1.0.0 start
11:29:32 PM  [724ng] > node app.js
11:29:32 PM  [724ng]
11:29:32 PM  [724ng] Example app listening on port 3000!
```

`logs?text=QAENV` matches nothing for rev-5/6/7. The control that isolates the config-change path: a deploy-hook trigger (`dep-dalokpb00vpc73cofrr0`, same spec) ran a real multi-minute build, and its pod (`…-7h3vv…`) prints `QAENV:qa-hello-123` as its first line. Hook/manual deploys rebuild; Settings config-change deploys do not. (The hook deploy also proves the env var itself reaches the process once an image is actually built.)

### The contract this violates

- `lego/types/v1alpha1/app_identity.go` `SpecRollsRelease` classifies `BuildCommand` and `StartCommand` as `IdentityArtifact|IdentityRelease` — a rebuild is owed, not just a rollout.
- `lego/operator/internal/controller/release_identity.go:119-130` puts both fields into the artifact fingerprint (`StartCommand` for native/buildpack, `BuildCommand` unconditionally), and `app_controller.go:655-680` rebuilds whenever `artifactChanged`, tagging `gen-<release-generation>`.
- `lego/operator/internal/controller/deployment_projection.go:220-225` deliberately sets *no* container command override for native builders because the start command is baked into the image — so a reused image can never pick up the edit.

### The fork (read before building on it)

Static reading says a rebuild is unavoidable here, and the deployed platform images are pinned to `bdb08dba7361` (`.pm` pin commit `2905584cc`), which is **identical to HEAD on this entire path** — `git log bdb08dba7361..HEAD` is empty for `release_identity.go`, `app_controller.go`, `internal/build/`, `types/v1alpha1/app_identity.go`, `backend/internal/apps/service.go`, and `backend/internal/rollout/`. So this is not deploy lag of a main fix, and no main version ever reused the artifact for these fields (the identity file was born with them in `b58265e6c`, and pre-identity operators rebuilt on everything). The fixer, with cluster access the QA run does not have, must determine which of the following holds and record the evidence in this task before changing code:

- the app-cluster operator binary diverges from the pin (which image is actually running in the hetzner app cluster, and what do its logs say for rev-5/6/7?); or
- a runtime path invisible to static reading skips the build (failed build dispatch that still rolls, a Job-name collision that observes an old success, an annotation-driven rollout racing identity computation).

Do not "fix" this by adding a container command override for native builders: that would paper over the stale artifact while leaving every other baked-in field (build command, build env) stale, and it contradicts the documented projection rule.

### Acceptance

- The milestone DoD's "Command edits rebuild" bullet passes live: start-command edit → new digest + echo in the new pod's logs; build-command edit → marker in the build log + new digest.
- The previously-passing shapes still hold: env-literal edits roll without a rebuild *only if* nothing artifact-class changed (fingerprint decides, not the mutation verb); manual/hook deploys of an unchanged spec still reuse; rollbacks still reuse the target image.
- A behavioral regression test exists that fails on today's prod behavior: open a config-change deploy for a start-command edit and assert the resolved image digest differs (or, at the operator level, that `artifactChanged` is true and a new build Job is created).

## Investigation, 2026-09-18 (w4 drain) — the fork's first branch is ruled out

The fork this task set up is now half-resolved, with evidence:

**The deployed operator does NOT diverge from HEAD on this path.** Production
(`bex-system/bex-controller-manager`, Hetzner app cluster) runs
`ghcr.io/bex-co/bex-operator@sha256:f074cd3a…`, which is the digest pinned in
`deploy/gitops/base/bex.yaml:29` at HEAD (pin commit `6f2975248`, source commit
`f4be22797e9e`). `git log f4be22797e9e..HEAD` is **empty** for
`release_identity.go`, `app_controller.go`, `internal/build/`,
`types/v1alpha1/app_identity.go`, `backend/internal/rollout/` and
`backend/internal/apps/service.go` — the same result the filing run got for the
older `bdb08dba7361` pin. Prod and HEAD are byte-identical on the whole
identity path.

**HEAD's identity code is provably the code that produced production's
fingerprints.** A live native App in the Hetzner cluster —
`tea-d98210cbbpdc73dcrkvg/tea-d98210cbbpdc73dcrkvg-qa-20260919-p13-web`, the
same `render-examples/express-hello-world` shape as the QA service, `builder:
native`, `runtime: node` — carried
`status.artifactFingerprint = artifact-v1:737b9bce64c8…` and
`status.releaseFingerprint = release-v1:f9698cfe48fa…`. Feeding that App's exact
spec to HEAD's `desiredAppReleaseIdentity` reproduces **both** strings
byte-for-byte, and applying either Settings edit flips the artifact:

- start command → `artifact-v1:6bdd63ffedbb…` (changed)
- build command → changed

That is now pinned as `TestSettingsCommandEditsDemandAFreshArtifact`
(`lego/operator/internal/controller/release_identity_test.go`), which also
asserts the gate that actually decides build-vs-reuse —
`reusableArtifactImage` returns `("", false)` — and that `ReleaseGeneration`
advances to the requested generation (so a rebuild would tag `gen-6`, not reuse
`gen-1`). It passes on HEAD.

**The backend write path reads correct too.** The dashboard's Start/Docker
Command editor calls GraphQL `setStartCommand`
(`dashboard/src/features/services/hooks/use-start-command.ts`) → `apps.Service.
SetCommands` → `patchFetched` → `rollout.Tracker.Patch`, whose `Snapshot.Stamp`
sets `app.bex.co/release-generation = generation+1` whenever
`SpecRollsRelease` is true — which it is for both commands. No source patch is
involved, so `app.bex.co/pending-source-generation` (the one annotation that
*would* pin the artifact and reuse `status.image`, via `sourceUpdatePending`)
is never stamped on this path.

### What is left, and why it is blocked

Every statically-readable explanation is eliminated. What remains is the fork's
second branch — a runtime path invisible to static reading — and closing it
requires **reproducing the failure live**: create a native web service from a
Public Git URL, let it build, edit its start command, and capture the App CR's
annotations + `status.{artifactFingerprint,releaseGeneration,image}` and the
operator's logs across that reconcile. The QA service is deleted, so the
reproduction has to be made, not read.

That needs one of:

- **authorization to run the reproduction on production** (one throwaway
  native service on `dashboard.bex.co` under the QA credentials, one
  start-command edit, then delete) — this is the environment the bug was
  observed in and the only one known to exhibit it; or
- **a full local stack** — `scripts/mock-cluster.sh` plus `scripts/dev-env.sh 4
  up` with an in-cluster BuildKit/Zot native build — which reproduces the code
  path but has never been shown to reproduce the *behavior*.

Until one of those runs, there is nothing correct to change: the note's own
guardrail ("do not 'fix' this by adding a container command override for native
builders") rules out the only edit that could be made without the evidence.
