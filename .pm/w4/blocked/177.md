# Report suspended Postgres SQL execution as unavailable

Why: an intentional suspension is an expected lifecycle state, but the enabled SQL console reports a platform failure and gives no recovery instruction.

**Severity:** minor · **Estimate:** 55m · **Worker:** worker4 · **Status:** todo

Found during continuous `$qa-find-bugs`, sweep 29, 2026-10-02 local / 2026-10-03 UTC, using the user-selected `muse.env` and w4. Research HEAD `82d3820b0` (code unchanged from `1263d12ae`; intervening commit updates platform image pins). This ships the filing, not the fix.

## Reproduction and target

1. Create an owned Free Postgres, public access off. This run created `qa-20261002-lifecycle-r29`, ID `dpg-db06iiude41s73cao24g`, then renamed it to `qa-20261002-renamed-r29` during provisioning.
2. Wait for Available. Through SQL console, confirm and run `CREATE TABLE qa_r29_probe AS SELECT 29 AS id, 'qa-r29-resume'::text AS marker;`. It affects one row.
3. Suspend through the dashboard. Wait for Suspended and zero database pods. Run `SELECT id, marker FROM qa_r29_probe;` in SQL console: **internal error**. REST query is **500 internal_error** and MCP returns **isError:true / internal error**.
4. Resume, wait for Available, and repeat the read. The row and original generated database/user names survive. Suspend again, reload the detail page, open SQL console, and run `SELECT 29 AS marker;`: same error at 02:37:48Z. The button remains enabled with Suspended visible above it.
5. A harmless SELECT with `allowWrites:true` also fails with the generic error. The same suspended database's Top Queries control correctly returns **503 / unavailable / service unavailable: database is suspended**.
6. Resume again. REST, MCP and UI queries succeed. Delete through the renamed typed confirmation.

**Target:** after existing authorization, an explicitly suspended database refuses SQL execution with the established `ErrUnavailable` class and the safe reason `database is suspended` (REST 503/id unavailable, GraphQL field error, MCP tool error). The dashboard preserves the SQL draft/history, explains that the database must be resumed, and disables both Run and keyboard execution while suspended. This is a lifecycle explanation, not a claim that SQL should work while compute is stopped.

**Before fresh data settles:** pass the detail query's existing database state into the console. A cached Suspended state stays visibly disabled; when the current state is not yet known, avoid claiming that execution is ready. The server guard remains authoritative for a stale Available cache. After resume, allow retry once the detail reaches Available, without clearing the draft/history.

## Root cause and scoped fix

- `dashboard/src/routes/databases.$databaseId.tsx:264` passes only `id` into the sole production `SQLConsole` mount. `components/sql-console.tsx:31,82,129` (under `dashboard/src/features/databases/`) knows nothing about suspension; requestRun checks loading/empty SQL and the Run button checks the same two conditions. The mutation hook at `hooks/use-execute-database-query.ts:20–29` passes through the server error; `sql-console.tsx:72` renders its message. The client is not inventing the failure.
- `lego/backend/internal/postgres/query.go:107,125,179–211`: Query and ExecuteQuery both reach executeAuthorizedQuery after their normal permission gates. That helper validates SQL, reads the connection Secret and dials without checking `db.Spec.Suspended`. The retained Secret during hibernation is expected (ADR009), not stale credentials.
- `query.go:328–330` converts a failed pgx connection into `errQueryConnClose`; its declaration at `:80` is a plain `core.Err`. `core/errors.go:201–206` shows this is a string error with no domain class. `core/http.go:331–346` does not publish unclassified errors; WriteErr emits 500/internal error. GraphQL's sanitizer at `api/server.go:1572–1601` and MCP's `core.MCPError` / `mcputil/mcputil.go:63` apply the same boundary. **Do not weaken these shared sanitizers or globally relabel connection failures.**
- Control implementation: `postgres/insights.go:331–344` TopQueries fetches, freshly authorizes, checks Suspended and wraps ErrUnavailable before reading its Secret. Reuse that narrow pattern in executeAuthorizedQuery, after its fresh permission checks and SQL validation, before credential resolution/execution. Keep existing write-protection confirmation precedence in ExecuteQuery.
- Dependency verification: pinned `pgx/v5 v5.10.0`, `conn.go:155–160,278–281`, passes its connection error back; our adapter deliberately replaces it. Pinned `graphql-go v0.8.1`, `gqlerrors/formatted.go:34–56`, preserves the resolver error wrapper; the existing resolverError helper explicitly peels it. The mutation result at `postgres/graphql.go:674` is nullable, so a classified field error is expressible. Pinned MCP SDK `v1.6.1`, `mcp/server.go:340–355`, turns a regular handler error into a tool result with isError=true; HTTP 200 on MCP is expected. The production request additionally identifies Apollo 4.1.3; no Apollo change is needed.
