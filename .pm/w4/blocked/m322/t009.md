## Objective

A cron job whose object name is past `MaxCronJob` (a 28–30-character service name) charts and meters its scheduled and manual runs, as t001 intended.

## Context

- **Found:** QA loop round 166, 2026-11-12 04:22–04:31 UTC, pin `e7a56b07e0d7`, which contains t001's `c1cc477b8`. DoD 2 fails live; see the README's round 166 probe.
- **Fixtures**, both deleted afterwards (GET 404). Both are Starter crons, image `busybox:1.36`, command `sh -c 'echo start host=$(hostname); sleep 45; echo done'`:
  - A `qa-20261112-r166-cr` (`srv-dbqjufq140ds739rb8r0`, 19 characters, `0 0 1 1 *`);
  - B `qa-20261112-r166-longcronjob12` (`srv-dbqjug6rbf4s73estu4g`, 30 characters, `*/5`).
- **Runs** (`GET /v1/cron-jobs/{id}/runs`), all `successful`:
  - A, manual: 04:23:56–04:24:45, 04:25:12–04:26:00, 04:26:33–04:27:22;
  - B: manual 04:23:58–04:24:47, scheduled 04:25:00–04:25:48.
- **Metrics** (`GET /v1/metrics/{cpu,memory,instance-count}?resource=<id>&startTime=2026-11-12T04:20:00Z&resolutionSeconds=60`):
  - A: `cpu` returns 3 series, one per run instance. `memory` returns 3 and `instance-count` returns 1. **DoD 1 passes.**
  - B: all three return `[]`. **DoD 2 fails.**
- **The run pods' names**, read from each run's `start host=$(hostname)` line in `GET /v1/logs?…&type=app&text=start`:
  - A, manual: `tea-daif693dqjvc73e7as3g-qa-20261112-r166-cr-r4354488b-km6c5` (60 characters). This is `<obj>-r<8 hex>-<5>`, matched by the existing two-segment form.
  - B, scheduled: `tea-daif693dqjvc73e7as3g-qa-20261112-r1-5309e6408859-29907625-k`. That is 63 characters, the kubelet's hostname cut.
  - B, manual: `tea-daif693dqjvc73e7as3g-qa-20261112-r1-5309e6408859-r6d3f1282` (62 characters). That is the Job name `<cronjob>-r<8 hex>` itself, with the kubelet's trailing `-` trimmed.
  - Both B hostnames show that the pod names run past 63 characters: the Job name, `-`, then the 5 random characters. They are `<cronjob(52)>-29907625-<5>` (67) and `<cronjob(52)>-r6d3f1282-<5>` (68).
- **The matcher's assumption:** t001 added `|<cronJob>-[a-z0-9]{10}` (`lego/backend/internal/egressquery/podname.go:77-86`). Its comment reads "That name is always MaxCronJob long, so every run pod's generateName base is past the cut: the pod is the truncated single segment". Live, Job pods are not truncated to 63, so no B pod matches.
- **Not read:** the Job controller or apiserver name-generation code at the cluster's Kubernetes version, which would say why these pods escape the 58-character `generateName` cut that ReplicaSet pods get (w6/m110). The probe shows the outcome, not the mechanism.

## Steps

1. Read the cluster's actual pod names, e.g. on the mock cluster at production's Kubernetes version, for:
   - a 30-character cron's scheduled run and its manual run;
   - a ~22-character web service. That is the control: its truncated shape was verified in w6/m110.
2. Extend `PodNameRegex` for an object past `MaxCronJob` to match the untruncated two-segment forms under the hashed CronJob name: `<cronJob>-[0-9]+-[a-z0-9]{5}` for scheduled and `<cronJob>-r[0-9a-f]{8}-[a-z0-9]{5}` for manual. Keep the truncated alternative only if step 1 shows it occurs.
3. Fix the comment. Extend t002's tests with the two observed 67- and 68-character names, plus a sibling that must not match (another App whose CronJob hash differs).
4. The usage meter shares the matcher (`usage/service.go`). Check that a long-name run meters its seconds once this lands (DoD 3).

## Acceptance criteria

- [ ] On production, a 30-character `*/5` cron charts its scheduled run and one manual run in `cpu`, `memory` and `instance-count`, one series per run instance.
- [ ] The short-name case (DoD 1) and a web service's Metrics are unchanged.
