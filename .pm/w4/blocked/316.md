# Preserve recorded starts on fast failed pre-deploys

Why: a pre-deploy that fails between observer passes loses its start and duration even though the operator and its owned Job record when the step began.

**Status:** todo · **Severity:** minor · **Estimate:** 55m. Functional dashboard QA, 2026-10-15, pass a628. This files the fix; product code is unchanged.

## Reproduce and controls

Use an owned Free prebuilt BusyBox web service with a healthy prior release. In Settings → Edit Pre-Deploy Command, save `printf '%s\n' QA_A628_FAST_SECOND; exit 19`, wait for `pre_deploy_failed`, then freshly open that deploy detail at desktop and 390px.

On `srv-db8jvjt23p2c7388on5g` / `qa-20261015-a628-predeploy`:

| --- | --- |
| First fast failure, exit 17, `dep-db8k09d23p2c7388on7g` | GraphQL `startedAt:""`; REST omits `startedAt`; fresh mobile detail omits Started and Duration. Its pre-deploy-start event is `21:05:41Z`. |
| Second fast failure, exit 19, `dep-db8k3il23p2c7388onjg` | Same omission on fresh desktop and mobile. Matching generation-5 `status.preDeploy.startedAt` and owned Job `status.startTime` are both `2026-10-15T21:12:42Z`; the deploy finishes at `21:12:49.201167Z`. |
| Slow failure, `printf '%s\n' QA_A628_SLOW_CONTROL; sleep 12; exit 19`, `dep-db8k4kd23p2c7388onlg` | Observer captures `pre_deploy_in_progress`; start `21:15:04.310232Z` survives the failed close at `21:15:18.888058Z`. REST includes it and the fresh detail shows Started and **14s**. |

The failure status, exit-code reason and marker logs are correct. The old pod keeps serving HTTP200, including throughout the sampled fast failure. Successful replacement and clearing the optional step also pass. The new finding is the lost recorded start on the fast failed branch.

[Durable evidence](../evidence/316-predeploy-start-time.json) contains the exact native mutations, complete GraphQL/REST responses, observer samples, operator/Job probes, fresh DOM and cleanup. Both screenshots named there were viewed; they are local supplements, not the durable basis.

## Located cause and target

- `lego/backend/internal/store/reconciler.go:922–926` supplies `buildRunStart` to `TransitionDeploy` only for `build_failed` or `live`. A direct `created → pre_deploy_failed` close supplies no start, although its recorded step ran. The slower control gets its start from the previously observed executing phase.
- `reconciler.go:1216–1235,1263–1278` already uses the recorded pre-deploy times for step events, including terminal-only observations. `lego/types/v1alpha1/app_types.go:1312–1325` defines the Job, release generation and start. **Do not use `preDeployTimes`'s now fallback as execution evidence.**
- For this failed-close branch, supply the raw nonzero, parseable start from the **failed pre-deploy record matching the open deploy's positive release generation**. Reuse the existing parser/attribution conventions (`parseObservedTime`, `preDeployStatusAt`) rather than the current App metadata generation. Stale, absent or malformed evidence must leave the start unknown.
- `lego/backend/internal/store/store.go:2408–2420` already accepts the supplied timestamp through `COALESCE(started_at, $9)`; the memory store has the same preserve-existing rule. Keep that rule: the slow control's already-recorded start remains byte-for-byte unchanged. No schema, status, failure-reason or timestamp-format change is needed.

The target fast exit-19 result is `startedAt: "2026-10-15T21:12:42Z"`, with its existing finish retained. This is the operator's second-resolution Job start, not the container's later start, row creation or failure observation. Same-second fractional creation times are not a reason to replace it.

## Consumers, aliases and boundary

REST list/get and MCP `list_deploys`/`get_deploy` consume `toRenderDeploy` (`lego/backend/internal/deploys/rest.go:74,117–128`; `mcp.go:147,164`). GraphQL `deploys` and `deploy` share the field at `graphql.go:50,97,142`. Preserve their existing missing-value encodings: omitted on REST/MCP and empty string on GraphQL when evidence is genuinely absent.

Dashboard detail uses `deploy-header.tsx:69–81` and filters missing Started/Duration facts; `deploy-presentation.ts:38–48` requires a valid start to compute duration. Exhaustive production TSX search finds **two** duration-formatting consumers: header and history list (`deploys-list-page.tsx:87`). `deploy-timeline.ts:41–42` adds the start step only when supplied. Populating the shared row clears those predicates; a UI fallback to Created would fabricate evidence. The shared routes are `/services/:id/deploys`, `/services/:id/deploys/:dep`, `/static/:id/deploys` and `/static/:id/deploys/:dep`; static and cron do not support this pre-deploy setting, so they gain no new timestamps.

Live coverage is Free web, REST, GraphQL and fresh desktop/mobile detail. MCP/CLI, private/worker, repo-backed execution and the additional historical/timeout/cancel variants are source-traced or pending regression work. No claim of authenticated Render execution: [ADR004](../../../docs/ADR004-app-deployment.md)'s existing first-executing-phase contract is the target, with Render wire compatibility retained.

## Implementation and acceptance — 55m

1. **15m:** wire generation-attributed failed-step start evidence into the normal reconciler close. Audit both reconciler calls (`reconciler.go:783,926`) and the `CloseDeploy` terminal wrapper (`store.go:2457`); change only the normal observation call. Missing-App cleanup and explicit terminal closes keep their existing behavior. Scope this to `pre_deploy_failed` with a matching failed record.
2. **25m:** meaningful reconciler plus PG/memory regressions for terminal-only failure with recorded start, nil/stale/zero/malformed evidence, and an existing in-progress start. Preserve build-failure/success-skip, queued or undispatched cancellation, timeout, supersede and deactivation contracts. Do not fabricate a start from a helper's fallback clock.
3. **10m:** repeat both immediate-failure commands on an owned Free web fixture, with the observer missing the running phase. Fresh 1440px/390px detail shows Started and a duration based on the recorded start and retained finish; REST/GraphQL agree. Repeat the slow failure and keep its existing start unchanged. The service remains HTTP200. Delete the fixture and revoke only the QA session.
4. **5m:** simplify the scoped change and check the unchanged list/get/MCP and shared UI mappings. No new endpoint, synthetic start or history rewrite.
