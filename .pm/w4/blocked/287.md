# 287 — Cancel can fail with an internal error while a deployment is rolling

Why: an ordinary control-plane update can reject Cancel before it records any cancellation, allowing the deployment the user tried to stop to go Live.

**Severity:** major · **Estimate:** 55m · **Worker:** worker4 · **Status:** todo

Functional `$qa-find-bugs w4`, production dashboard, 2026-10-13 UTC pass a357. Research main `fd46f58c0`. This entry schedules the fix; this hunt changes only the filing. [Complete requests, responses, platform error excerpts, controls and cleanup](evidence/287-cancel-update-conflict.json).

5. These are Kubernetes optimistic-lock conflicts during the marker patch, not terminal-deploy refusals inferred from an error string.

**Target:** absorb a bounded transient resource-version conflict, re-read the same service and decide the marker from current state, then complete the existing cancellation. If contention exhausts that budget, return the established retryable domain conflict rather than an internal platform error. Preserve an already-terminal deployment's existing 409 semantics and the row-close winner rules. Do not claim Cancel succeeded until the marker and existing close path actually succeed.

**Observed controls:** the initial native build cancels correctly. A third queued image deployment on the switched service, `dep-db73otk479ic73bbj60g`, cancels at **14:13:13.573Z**; the prior release remains available. A later explicit manual deployment reaches Live at **14:14:53.188486Z** and serves the exact marker. ## Cause and bounded correction

- `lego/backend/internal/store/release_cancel.go:77–89`, `markReleaseCanceled`, performs one `core.RereadApp`, keeps an equal/newer cancellation marker, and makes one optimistic merge patch. A concurrent status/spec update between read and patch returns immediately. The two platform errors identify precisely this patch.
- `lego/backend/internal/deploys/service.go:917–931` checks the deployment's finished state, calls `store.CancelRelease`, then closes its row. A failed marker returns before CloseDeploy, so the requested rollout remains uncanceled and can reach Live.
- `lego/backend/internal/api/server.go:1604–1628` preserves classified public errors but logs and replaces this unclassified Kubernetes error with "internal error". Keep that general error handling; classify the exhausted cancellation conflict at its producer.
- Installed **controller-runtime v0.23.3**, `pkg/client/patch.go:89–92,103–119`, puts the original resourceVersion into an optimistic patch. It supplies no automatic retry. Installed **client-go v0.35.0**, `util/retry/util.go:26–33,74–105`, supplies a bounded RetryOnConflict and requires a fresh read per attempt and an unwrapped patch error inside its callback.
- Use that dependency or an equivalently bounded existing-layer loop around the marker decision. Every attempt must re-read through `core.RereadApp` (`core/base.go:1434–1445`), preserve the original service identity, recompute whether an equal/newer marker makes the write unnecessary, and patch with the newly read version. Keep the deployment row's original generation; never substitute metadata.generation or overwrite a newer cancellation. Wrap/classify only after retry classification.
- `rollout.PatchAppLocked` at `rollout/rollout.go:204–220` is a useful bounded-retry precedent, but **store cannot import rollout**: rollout already imports store. Do not create an import cycle or a new broad patch abstraction for this small fix.

Shared caller census: **two production CancelRelease calls**—explicit `deploys.Service.Cancel` (:923), and suspended-release settlement in `store/reconciler.go:825`. The latter already tries again on its next reconcile pass; preserve that behavior and its marker-before-history ordering. **Three explicit mutation adapters** reach the same Cancel verb: REST `deploys/rest.go:275–282`, GraphQL `deploys/graphql.go:245–250`, and MCP `deploys/mcp.go:167–177`. Dashboard Cancel consumes GraphQL. No per-adapter retry, automatic click replay, release-trigger change or optimistic Canceled UI row is needed.

## Verification and limits

The 55m unit covers **15m** for the bounded marker retry/classification, **20m** for behavior tests through Cancel and the shared suspended-close path, **15m** for functional replay/parity/checks and **5m** for Simplify.

- Inject one real optimistic patch conflict followed by an updated same-service read through the client interceptor. Cancel must stamp its original release, close that deployment once and preserve the prior serving release. The current one-attempt implementation must fail this assertion.
- Cover exhausted conflicts (bounded classified refusal, no false canceled row), a non-conflict patch/read failure (no inappropriate retry), an equal/newer marker appearing between attempts, service replacement between attempts, build-delete failure after a successful stamp, and suspension's shared path. Preserve the existing terminal/CloseDeploy-CAS winner controls; a completion race stays a domain conflict.
- Keep build deletion best effort after a successful stamp and preserve the operator's level-triggered cleanup. Verify error class consumption in REST/GraphQL/MCP through their real adapters, then run appropriate backend checks.
- Fresh desktop and mobile owned-Free replay must demonstrate a cancel during rollout retaining the previous response, a truthful Canceled history row, and a subsequent manual deployment reaching Live. Delete only the fixtures and revoke only that hunt session.

[Render's deployment documentation](https://render.com/docs/deploys#canceling-a-deploy) describes Cancel on an in-progress deployment; the [Cancel deploy API](https://api-docs.render.com/reference/cancel-deploy) exposes the same verb. Bex's own successful controls establish the intended local behavior. No authenticated Render race comparison was performed.

Live failing requests are GraphQL on one Free web service. REST/MCP cancellation failures, other service kinds, suspension under this exact conflict and deterministic retry injection were researched rather than live exercised. No deploy interruption or bad-image impact is asserted beyond the two accepted rollouts continuing to Live after rejected cancellation. The runtime label discrepancy is retained as context but not filed here. The source-switch replay is partial m202 acceptance: it uses a different marker and lacks the original environment-value control.

## Progress

Implemented 2026-10-13: `markReleaseCanceled` (`lego/backend/internal/store/release_cancel.go`) wraps its read–decide–patch in client-go's `retry.RetryOnConflict` (`DefaultBackoff`: four attempts, about 0.3s at most). Every attempt re-reads through `core.RereadApp`, so a recreated namesake is still refused and an equal or newer marker that landed meanwhile is kept without a second write; the stamp is always the deploy row's own generation. Only a lost lock is retried. A stamp that still loses returns `core.ErrConflict` ("the service kept changing while its deploy was being canceled; retry the cancel"), which REST, GraphQL and MCP already map as a conflict, so no adapter changed. Build deletion stays best effort after the stamp, and the suspended-release path (`store/reconciler.go`) shares the retry and still tries again on its next pass. Tests: `release_cancel_test.go` adds a real lost lock then success (the other writer's change kept), exhausted conflicts (bounded attempts, conflict class, nothing stamped), patch and read failures that are not retried, a newer cancel landing between attempts, and a namesake recreated between attempts; `deploys/cancel_rollback_test.go` adds `Service.Cancel` surviving a concurrent rollout write (row canceled once, generation 4 stamped) and a cancel that keeps losing answering 409 over REST with the row left open and a later Cancel succeeding. Six of these fail on the one-attempt marker (checked by restoring it); the non-retry case is a control. GraphQL and MCP were not driven separately: they call the same `Cancel` verb and share the error mapping. Small change, reviewed inline. `go test ./...` in `lego/backend` and `make lint` green locally; the real-Postgres suite ran in the ship gate.
