## Objective

Decide what an audit-derived service event should be keyed by, and how rows already written under the old key are treated. Everything else in this milestone follows from this decision, so it is made once, in writing, before any query changes.

## Context

- `store/events.go:464-467` states the split in its own words: deploys key on `app_id`, audit rows key on `core.ServiceTarget(appName)`. The audit arm is `WHERE ((a.target = $2 AND a.workspace_id = ANY($3)) …`.
- A service's control-plane row id is not reused — pass 156 confirmed the re-created service got a different `srv-` id — so it is a candidate key that cannot collide.
- The blocker to consider first: **an audit row is written by `core`'s authorize path, which knows the target name, not necessarily the app row id.** Establish whether the app id is available at that point at all. If it is not, the options narrow to (a) resolve and store it at write time, (b) keep the name and add a disambiguator (the app row's `created_at`, or a generation counter), or (c) scope the join by the app's lifetime window. Say which and why.
- `w4/120` solved a structurally identical problem for blueprints by making the *revival* explicit rather than by re-keying; that is a third shape worth naming even if rejected here, because the feed's contract differs (a blueprint revival is deliberate, a name reuse is coincidental).

## Steps

1. Read the audit write path in `core` (`core/base.go`'s authorize-and-audit) and record whether the app row id is in scope when the row is written.
2. Enumerate the candidate keys with their costs: app id at write time (needs a resolve on the write path), name + app-lifetime window (no schema change, but needs the app's create/delete timestamps and breaks for a name reused twice inside one window), name + generation.
3. Choose one and write the rationale into the milestone README under a new "Decision" heading.
4. Decide the fate of existing rows explicitly: backfillable, abandoned as legacy-window-only, or left readable under the old join behind a cutoff timestamp. State which in t003's terms.
5. State whether the chosen key ends the documented cross-tenant shared-name attribution (`webhooks.go:713-719`) as a side effect. If it does, flag it for the user rather than changing it silently.
