## Objective

Pin both defects and, just as importantly, the cases that behave correctly today and could be broken by the fix.

## Context

- The whole defect is in SQL, so the load-bearing tests are Postgres-backed — `w4/117`'s fix is the precedent: it reproduced the exact reported blanks pre-fix and passed post-fix, and asserted the list answer was non-empty first so it could not pass vacuously. Copy that discipline.
- The regression risk is the arm that is already right. A test that only checks "no inherited events" passes trivially if the feed returns nothing at all.

## Steps

1. Postgres-backed: create an app, write audit-derived events, delete it, create a new app with the same name and a different id, assert the new app's feed contains only its own rows — and assert the old app's rows still exist in the store, so the test distinguishes "not attributed" from "deleted".
2. Assert the control in the same test: a never-used name yields no pre-creation rows.
3. Assert the deploy-derived arm is unchanged — `deploy_started`/`deploy_ended`/`service_hibernated`/`service_woken` still appear for the app that produced them, in order.
4. Cover `webhookEventsQuery` with the same fixture, since a subscriber is the more serious consumer.
5. Verify each test fails before the fix. Remove the fix locally and record which assertions fire — a test that passes both ways is not coverage.
6. Service-layer: a refused `SetIdleTTL` records no event, an accepted change records one, and the no-op behaves as t004 decided.
7. Assert every id from a full `serviceEvents` page resolves through the by-id read.
