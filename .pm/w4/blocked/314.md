# Generate Blueprint reports copied when clipboard access fails

Why: users should know whether their generated configuration reached the clipboard, so they can retry or use the working download action.

**Severity:** minor. **Estimate:** 30m. Functional `$qa-find-bugs`, a610, 2026-10-15, user-selected w4. Research HEAD `a660d760b87f444844b864a0229ace76f80c92ee`; filing only. Goal: ADR008 usable hosting and ADR049/ADR018's Generate Blueprint workflow.

## Reproduction and controls

This is an **intentionally induced browser clipboard-denial case**, not a claim that ordinary allowed copying fails.

1. Create an empty owned workspace environment group, select **only it** in `/blueprints` → Generate Blueprint, and Generate. This pass used `qa-20261015-a610-copy` / `evg-db8gpu5eelgc73d2i7gg`, with no service links or values.
2. With clipboard access allowed, click Copy. At **17:28:40.007Z**, the clipboard exactly matches the 58-character preview. Let that success toast dismiss.
3. Seed `QA_A610_UNCHANGED`, then temporarily set the actual browser's clipboard-write permission to **denied** for this origin and isolated context. Click the native Copy button.
4. At **17:28:53.357Z**, permission is denied, the clipboard remains unchanged, and the browser emits a **NotAllowedError pageerror**: Write permission denied. Despite this, a new **render.yaml copied** success toast appears. The dialog stays open.
5. Fresh reload at **390×844**, regenerate only the owned group and repeat. At **17:30:58.206Z**, the same false success and pageerror occur with no preceding toast. **Download render.yaml still succeeds while clipboard writes are denied**, and its 58 UTF-8 bytes match the generator response.
6. Restore clipboard access and retry Copy. At **17:31:04.159Z**, the preview is copied correctly, permission is granted and the retry emits no pageerror.

[Durable evidence](evidence/314-blueprint-copy-failure.json) includes exact UI actions, native browser-permission setup/repro code, both failures, unchanged-clipboard checks, full owned Generate requests/responses and cleanup. Permission state was changed in the browser engine; no application function, DOM or server response was replaced.

**Expected:** a rejected write shows a localized copy error, emits no copied-success message or uncaught rejection, and leaves preview, retry and Download usable. **Actual:** the action always announces success and abandons the rejected promise.

## Root cause, reuse and scope

`dashboard/src/features/blueprints/components/generate-blueprint-dialog.tsx:235–242` executes `void navigator.clipboard.writeText(manifest)` at **238**, then immediately calls `toast.success(t("blueprints.generateCopied"))` at **239**. Neither resolution nor rejection controls the toast.

Reuse the existing `useCopyToClipboard` hook in this dialog. Its `common/hooks/use-copy-to-clipboard.ts:38–48` already awaits the write, toasts success only after resolution and catches rejection. Pass the existing translated `blueprints.generateCopied` success text plus a new, specific en/zh copy-error message; `blueprints.generateError` says generation failed and is the wrong outcome. Remove the dialog's unconditional success toast and call the hook from the existing text button, preserving its appearance and accessible name. The shared hook itself needs no behavior change.

Exhaustive production search finds **1 manifest write/copy-success site** and **1 GenerateBlueprintDialog render site**, `routes/blueprints.tsx:169`. The same callback handles generated service, Postgres, Key Value and environment-group output; service selection includes the supported web/private/worker/cron/static families. Only environment-group output was denied live. There is no second resource-specific copy handler or separate alias to repair.

The existing hook has **2 production callers**: `common/components/copy-button.tsx:24` and `common/components/code-block.tsx:12`. These are source-established reuse precedents, not additional native denied-copy controls. Add this dialog as a caller; avoid changing their contracts. Generation queries, selection, manifest bytes, Download, Back/Close and resource APIs retain their current behavior.
