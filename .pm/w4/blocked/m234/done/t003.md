## Objective

While a service is suspended, its Environment editor offers only Save only. Save and deploy and Save, rebuild, and deploy are disabled with the reason Manual Deploy shows. The pending-changes notice tells the user to resume and then deploy.

## Context

- `dashboard/src/features/services/components/service-environment-editor.tsx`:
  - `:965-1009`: the primary Save and deploy button and the three menu items are gated only on `saveDisabled`.
  - `:170-181`: the deploy result counts as deployed when `rolledOut` is true.
  - `:644-651`: the success toast (`services.environmentSaveDeploySuccess`, `locales/en.ts:4692-4695`).
  - `:127-132`: the rebuild toast prints `rolloutError` verbatim.
- Manual Deploy's gate: `manual-deploy-button.tsx:98-110` reads the `deploy` decision through `gateAction` (`features/capabilities/lib/resource-actions.ts:180`). Precondition `suspended` maps to `capabilities.blockedSuspended`: "Unavailable while the service is suspended. Resume it first."
- The notice is chosen by `features/services/lib/status.ts:329-335` `undeployedChangesHintKey`. It is used by `service-detail-header.tsx:311` and `routes/services.$serviceId.env.tsx:55`, and the copy is at `locales/en.ts:280-285`.
- The editor is shared with environment groups (`EnvironmentEditor`), so the gate must be per service, not global.

## Steps

1. Pass the service's `deploy` decision (or `service.suspended`) into the service editor. When blocked by `suspended`, make Save only the primary action and disable the two deploying items with the shared `PermissionTooltip`/`gateReason` copy.
2. Add a suspended variant to `undeployedChangesHintKey`, e.g. "Saved changes aren't live yet. Resume the service, then deploy to apply them." Add the zh string too.
3. Keep the success toast keyed to `rolledOut`. With t001 in place, a stale-tab deploy save on a just-suspended service shows the backend's `rolloutError` instead.
4. Check the pending and ready states at 1440 and 390 px.
