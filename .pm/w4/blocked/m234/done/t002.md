## Objective

A deploy-mode (or rebuild-mode) environment-group save treats a suspended linked service as it treats an Auto-Deploy-off one: the group's values are saved, that service is listed in `pendingServiceIds`, and it gains no deploy row. Running linked services roll as today.

## Context

- `lego/backend/internal/envgroups/patch.go:217-252` `rollGroupPatch`: `rollLink` → `rollOne` (`envgroups/service.go:1263`) skips only `autoDeployGated` services. A suspended one goes through `rollLinkedService` (`service.go:1101`) → `rollout.PatchLocked`, which opens a row the reconciler cancels. `RolledOut` is then reported true for it.
- Rebuild mode calls `RebuildService`, which refuses a suspended App (409), so that service lands in `FailedServiceIDs`. That is a retryable failure that can never succeed while the service is suspended.
- The dashboard group editor reads `pendingServiceIds` and `failedServiceIds` (`dashboard/src/features/env-groups/components/env-group-editors.tsx`).
- This was code-read only; it was not probed live in pass 9d0542.

## Steps

1. In `rollLink`, check `a.Spec.Suspended` before both the rebuild and the roll branches. Return `skipped=true`, `err=nil`, so the service lands in `PendingServiceIDs`.
2. Confirm the group's pending copy reads truthfully for a suspended service. If it says "Auto-Deploy is off", give suspension its own reason. Coordinate with t003 on the strings.

## Acceptance criteria

- [x] A group with one suspended and one running linked service: deploy mode rolls only the running one, and `pendingServiceIds` contains the suspended one. `failedServiceIds` is empty and `rolledOut` is true.

- [x] Auto-Deploy-off services keep today's pending behavior (regression test).
