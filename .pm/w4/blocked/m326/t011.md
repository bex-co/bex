## Objective

Turn on wildcard custom domains in production. Until this lands, bex-api refuses every wildcard as `CUSTOM_DOMAIN_WILDCARD_UNAVAILABLE` (`BEX_ACME_DELEGATION_ZONE` unset).

## Context

- A wildcard's certificate is issued by DNS-01. The tenant's `_acme-challenge` CNAME points to `<slug>.<delegation zone>`, and cert-manager (`cnameStrategy: Follow`) writes the challenge TXT there.
- **The zone must host nothing else, with a token scoped to it alone** (docs/ADR005-custom-domain.md § Wildcard domains). Inside `onbex.co`, a tenant could steer that TXT write to `<victim>.onbex.co`, which stops the `*.onbex.co` wildcard answering for the victim. The onbex.co token (ADR093) must not be reused.

## Steps

1. **User:** register or pick a domain dedicated to ACME delegation (Render's analogue is `renderdns.com`) on Cloudflare.
2. **User:** create an account API token scoped to that zone only (DNS Edit + Zone Read).
3. **User:** add the token as `BEX_ACME_DELEGATION_DNS_TOKEN` to `.env`, `.env.example` and the `production-deploy` environment.
4. **Worker:**
   - install the token as `cert-manager/acme-delegation-dns-token`, stdin-only, as `scripts/onbex-dns01-token-secret.sh` does, from the deploy workflow;
   - add a `letsencrypt-dns01-delegated` ClusterIssuer (Let's Encrypt prod, `dns01.cloudflare` with that Secret, `cnameStrategy: Follow`) to `deploy/gitops/charts/cert-manager-issuers`, and pin its shape in `scripts/gitops-validate.sh`;
   - set `BEX_ACME_DELEGATION_ZONE` on bex-api and `BEX_WILDCARD_CLUSTER_ISSUER` on the operator in the prod overlay;
   - record the token in ADR019.
5. Then t006's live replay.

## Acceptance criteria

- [ ] A wildcard on an owned service gets a trusted certificate through the delegation, and `gitops-validate.sh` pins the issuer.
