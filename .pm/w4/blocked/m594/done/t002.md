## Objective

On a Postgres or Key Value in a protected environment, only a workspace Admin changes its inbound IP rules. A non-Admin's `PATCH` that carries `ipAllowList`, and the dedicated `SetIPAllowList` routes, answer `403` `PROTECTED_ENVIRONMENT_ADMIN_REQUIRED` and write nothing. A Blueprint's own sync keeps Render's exception.

## Context

- `UpdatePostgres` (`lego/backend/internal/postgres/service.go:1811`, guard at `:1903`) and `UpdateKeyValue` (`keyvalue/service.go:1345`, guard at `:1373`) ask `protectedDatabasePatchVerb` / `protectedKeyValuePatchVerb` (`postgres/protection.go:47`, `keyvalue/protection.go:35`) for ONE verb per patch, and none of those verbs is restricted since w8/187. A patch carrying `version` and `ipAllowList` returns `upgrade` today, so adding `ipAllowList` as another `case` would be shadowed. Check the IP rules as their own restricted verb (for example `"change access control"`) independently of the existing switch.
- `SetIPAllowList` (`postgres/access.go:64`, `keyvalue/service.go:1105`) routes through those patches, so the one gate covers REST `PATCH`, the dedicated IP routes, GraphQL and MCP.
- Re-sending the stored list unchanged should pass, as the Scale gate does for the environment list (ADR032, w8/m137). Decide whether a no-op write passes and record it.
- The environment-level fan-out (`SetEnvironmentIPAllowList`) and the workspace fan-out are not member writes; leave them alone.
- Blueprint: `core.BlueprintSync(ctx)` (`core/environment.go:87`) marks the identity-less sync worker. Render: non-Admins "can still modify those resources by publishing an update to the corresponding render.yaml file". A member's manual sync stays gated, as for placement (w3/m292).

## Steps

1. Add the verb to `core.ProtectedVerbRestricted` and gate a patch whose `IPAllowList` differs from the stored rules, using t001's coded refusal (or add it here if t002 lands first).
2. Admit `core.BlueprintSync(ctx)`.
3. Tests per package: Admin allowed; Developer refused with the code and the CR unchanged; a mixed patch (`version` + `ipAllowList`) refused; unprotected Developer allowed; unchanged list allowed; Blueprint sync allowed.

## Record (2026-11-23)

- `VerbChangeAccessControl` ("change access control"), asked on its own in `checkUpdateFields` / `updateKeyValue` whenever `core.AllowListPatchChanges` says the patch changes the rules in effect (`ipAllowList`, or `public`, which bex applies as the same access control). A mixed patch (rename or upgrade with rules) is refused; re-sending what a read returned is no change and stays open (decided: Render's dashboard re-sends the list it shows, and the Scale gate treats an unchanged list the same way). A description-only edit is a change.
- `SetIPAllowList` routes through the patch, so REST, GraphQL `setDatabaseIpAllowList`, MCP `update_postgres` / `update_key_value` and the dry-runs share it.
- Blueprint: the apply patches an existing datastore directly (`applyDatabase`, `applyKeyValue`), never through `UpdatePostgres`, so a pushed `render.yaml` keeps Render's exception with no `BlueprintSync` branch; `TestBlueprintSyncChangesAProtectedDatastoresRulesForADeveloper` pins it.
