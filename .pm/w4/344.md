# Billing's resource-cap tile says "Near limit" for a cap that is full

Why: at 1 / 1 Postgres the workspace cannot create another (the create dialog says "Postgres limit reached"), but Billing → Included usage calls the same state "Near limit". That understates a hard stop, and the two screens contradict each other.

- **Severity:** minor (wrong state label; the cap itself is enforced correctly). **Estimate:** 25m.
- **Source:** live functional `/qa-find-bugs w4`, pass 7b1f38, 2026-10-19 UTC, `muse.env`, workspace `bex-canary` (Hobby). Production was pinned to `5e75de920`; research is on main `f69f440c9`. Screenshot `.playwright-mcp/qa-billing-cap-7b1f38.png` is local and gitignored.
- **Repro:**
  1. Billing (`/billing#included-usage`; `/usage` redirects here) at 01:12:52Z reads `Services 8 / 25 · Postgres 1 / 1 Near limit · Key Value 0 / 1`. The progress bars report `Postgres aria-valuenow=1 aria-valuemax=1`.
  2. New Postgres (`/?new=database`), Name `qa-20261019-7b1f38-pg`, plan **Free**, Create database (01:12:29Z). The dialog stays open with **"Postgres limit reached"** / "workspace is limited to 1 Postgres database; delete an existing Postgres database to create another" / "Upgrade plan".
  3. `GET /v1/postgres?ownerId=…` still lists only the pre-existing foreign `qa-20261017-64552e-pg14`, so nothing was created.
- **Expected:** at or above the cap the tile states that the limit is reached, consistent with the create refusal. "Near limit" stays for 80–99 %.
- **Root cause:** `dashboard/src/features/usage/components/resource-caps.tsx:35-41` has one state: `nearLimit = used / limit >= 0.8` (`NEAR_LIMIT_RATIO`). Any ratio at or above 1 also renders `usage.resourceCapsNearLimit` (`:57-62`). The en and zh locales define no at-limit string.
- **Fix (target behavior):**
  - Three states per tile: below 80 % shows nothing; 80–99 % shows "Near limit"; `used >= limit` shows "Limit reached", with the copy and severity used by the create refusal (`databases.…` "Postgres limit reached" family).
  - `used > limit` (possible after a downgrade or while resources are finishing deletion, w6/m129) also reads "Limit reached" and does not clamp the visible numbers.
  - Optionally link the at-limit state to the plan change, as the create dialog does.
- **Blast radius:**
  - One component. `CapTile` renders all three tiles (Services, Postgres, Key Value) and is mounted once (`usage-page.tsx:135`).
  - Every Hobby workspace with one Postgres or one Key Value shows this today, because those caps are 1.
- **Adjacent classes:**
  - The terminating count line (`w6/m129`) is unchanged.
  - Error and null-limit states (`resource-caps.tsx:141` returns null on error) are unchanged.
  - Services at 25/25 gets the same treatment.
- **Unverified:**
  - Key Value and Services at their caps were not live, though they share the code.
  - zh rendering was not probed.
  - Render's plan-limit display was not compared.
- **Dedupe:**
  - `w4/339` (done) fixed the create-refusal plural, not this tile.
  - `w6/m129` added terminating counts.
  - No item mentions "Near limit".
  - `git log` on `resource-caps.tsx` shows only `aa59d4b26`/`51d92f87c`/`2856ae055`, none addressing the at-limit state.
- **Acceptance:**
  - A component test covers 0/1 (no badge), 4/5 (Near limit), 1/1 and 2/1 (Limit reached), and fails on current code.
  - Live, bex-canary's Postgres tile reads "Limit reached" while the create dialog refuses.
