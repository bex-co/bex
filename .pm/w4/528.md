# 528 — Creating a service from a public GitHub repo returns `500 internal error` while GitHub refuses bex's anonymous repo lookup

Why: in a workspace with no GitHub connection, every repo-backed create first asks GitHub anonymously whether the repo is public. When GitHub refuses that lookup (anonymous rate limit or an upstream 5xx), the create fails with a bare `500 {"error":"internal error"}`. The customer can't tell that the failure is temporary and upstream, gets no hint to retry, and no service is created. The `APIError` contract in `github/client.go:182-183` says callers must map these errors "to a clean bex error (never a raw 500)". `ValidateRepo` doesn't.

**Severity:** major (a core journey, "deploy from a public repo", fails with a misleading 500 for the whole refusal window; nothing is lost and a later retry works) · **Estimate:** 45m · **Worker:** worker4 · **Status:** todo

- **Root cause** (cause probable: the bex-api log line `bex-api: internal error: checking public repository access: github: unexpected status N` was not read, so the upstream status is inferred):
  - `lego/backend/internal/github/service.go:1149-1153`: when the workspace has no grant, `ValidateRepo` calls `LookupRepo(ctx, "", owner, repo)` anonymously. Any error is wrapped as `checking public repository access: %w` with no bex sentinel.
  - `lego/backend/internal/github/client.go:558-567`: `LookupRepo` maps 404 to "not public" and 2xx to OK. Every other status, including GitHub's anonymous primary rate limit (`403` with `x-ratelimit-remaining: 0`, 60 requests/hour per egress IP, shared by every customer on that IP), secondary rate limit (`403`/`429` with `retry-after`) and 5xx, becomes an `*APIError`. Transport errors are wrapped plainly (`:553`).
  - `lego/backend/internal/core/http.go:311-347`: `WriteErr` matches no sentinel, so `IsPublicError` is false and the reply is the generic 500. The GraphQL sanitizer shares `IsPublicError`, so GraphQL and MCP answer the same way.
  - The `APIError` doc comment (`client.go:182-183`) promises the opposite.
- **Fix — target behavior:**
  - A GitHub refusal during `ValidateRepo` is classified, never a 500:
    - Rate limit (`429`, or `403` with `x-ratelimit-remaining: 0` / `retry-after`) → `503` with a coded error, e.g. `GITHUB_RATE_LIMITED`. The message is "GitHub is rate-limiting bex right now. Try again in a few minutes.", wording reused from the Blueprint classifier `apps/blueprint.go:429-431`. Send `Retry-After` when GitHub gave one.
    - 5xx or transport error → `503` `GITHUB_UNAVAILABLE`, "Could not reach GitHub to check the repository. Try again in a few minutes." (`blueprint.go:434-435`).
    - Upstream body text never reaches the client (w6/005).
  - `LookupRepo` must keep the rate-limit headers on `APIError`, or return a typed rate-limit error, so the classifier can tell a rate-limit `403` from any other `403`.
  - The dashboard create form shows that message in place of "internal error".
  - Optional follow-up, filed separately if wanted: authenticate the public-repo lookup (the GitHub App's JWT/installation-less token or a server token) so the budget isn't 60/h per IP.
- **Blast radius:** `ValidateRepo` has 3 callers (grep `ValidateRepo(` in `lego/backend/internal`, non-test):
  - `apps/service.go:2190`: create, REST/GraphQL/MCP.
  - `apps/deploy.go:3551`: Blueprint branch resolution, via `resolveBlueprintBranch`.
  - `apps/settings_check.go:484`: changing a service's repo.
  - All three get the same 500 today and the same fix. The installation branch (`grantedRepo`: `MintInstallationToken`/`LookupRepo` with a token, `service.go:1145`, `:1208-1223`) has the same untyped path for a connected workspace when GitHub refuses or is down. Classify it with the same helper.
  - The anonymous budget is shared with the first-deploy commit lookup (w4/458's class), so a burst of creates can also leave deploys commitless.
- **Adjacent classes:** 404 (private or missing) stays the existing `400` "not accessible" message (`service.go:1154`), with no existence oracle (w4/105). A real 401/403 on an installation token (revoked or suspended installation) is not a rate limit: map it to `400` "bex's GitHub app is not authorized…" as `blueprint.go:426-428` does. Store and Kubernetes errors stay 500.
