## Objective

Give image-backed web/private/worker services an editable Docker Command row on the Settings page, backed by the existing `setStartCommand` mutation.

## Context

- `BuildDeploySection` (which owns the Docker Command editor) renders only when `service?.repo` (`dashboard/src/routes/services.$serviceId.settings.tsx:227,268`), so image services get no command editing anywhere. The repo-backed docker editor is the template: `dashboard/src/features/services/components/build-deploy-section.tsx` (~line 330, `dockerCommand` branch).
- Backend `SetCommands`/`checkCommands` accept `startCommand` for every non-static type (`lego/backend/internal/apps/service.go:3821`, `lego/backend/internal/apps/settings_check.go:122`); the GraphQL `setStartCommand` field already exists (`lego/backend/internal/apps/graphql.go:1605`).
- The `use-start-command.ts` hook backs the repo editor — reuse it rather than a second mutation path.

## Steps

1. Render a Docker Command row for image-backed services (web/private/worker): either a slim standalone row or `BuildDeploySection` in a command-only mode, whichever fits the file's existing `show*` prop pattern.
2. Saving calls `setStartCommand` and triggers the same redeploy semantics as the repo-backed editor.
3. Keep static_site excluded (backend rejects it) and cron on its existing Command section.

## Files

- `dashboard/src/routes/services.$serviceId.settings.tsx`
- `dashboard/src/features/services/components/build-deploy-section.tsx`
- `dashboard/src/features/services/hooks/use-start-command.ts`

## Acceptance criteria

- [ ] Image web service Settings shows Docker Command with the current value; saving updates `spec.startCommand` and starts a new deploy.
- [ ] Worker/private image services show the same row; static sites do not.
- [ ] A previously crash-looping image (e.g. `alpine:3.20` with `tail -f /dev/null`) becomes runnable from the dashboard alone.

## Out of scope

- Create-wizard field (t001); native-runtime Start Command behavior (unchanged).
