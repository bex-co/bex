# Valid zero-padded cron schedules display malformed clock times

Why: someone pasting an accepted cron schedule sees an invalid-looking time beside it, even though the server correctly schedules the job for 09:05 UTC.

**Severity:** minor. **Estimate:** 35m (trace 5m, shared formatter 5m, focused tests 10m, both forms and parity 10m, simplify 5m). Source: user-directed continuous functional `$qa-find-bugs`, w4, 2026-10-12 a292. Filing only; no product fix implemented.

## Live reproduction

On `https://dashboard.bex.co/services/new`, choose Cron Job → Existing Image, a Free BusyBox 1.37 job, and enter the schedules below. Repeat in an owned job's Settings → Edit schedule.

| Input | Actual preview | Expected preview |
| --- | --- | --- |
| `5 9 * * *` | Every day at 09:05 | same |
| `05 09 * * *` | Every day at 09:05 | same |
| `0005 0009 * * *` | Every day at 0009:0005 | Every day at 09:05 |
| `0000 * * * *` | Every hour at minute 0000 | Every hour |
| `0005 0009 001 * *` | On day 001 of every month at 0009:0005 | On day 1 of every month at 09:05 |

The last two rows were unsaved typing probes. The daily padded expression was actually created, reached Live, and saved again after an equivalent ordinary numeric save. Both fresh server reads returned `nextRunAt: "2026-10-13T09:05:00Z"`; fresh Settings at 390×844 still showed `0009:0005`. Fresh Chinese Settings showed `每天 0009:0005 · 使用 UTC`. The preserved schedule text and server projection are correct.

Controls: `MON` previews Monday; `*/5` previews every five minutes; `*/40` has no false uniform-interval description; `99 99 * * *` shows the format error and disables Save. Cancel restores the accepted daily schedule. No scheduled invocation at tomorrow's time was waited for.

## Cause and scope

- `dashboard/src/features/services/lib/cron.ts:56–69` parses numeric fields as numbers, stripping leading zeros for validation. `cronScheduleProblem` at :169–182 validates before bounded expansion, so these schedules correctly pass.
- The separate preview path calls `canonicalField` at :206–209, which resolves names and `?` but leaves numeric text untouched. `hhmm` at :212–213 only pads to a minimum of two characters; it never removes excess zeros. Daily/weekly/monthly time construction at :282–292 therefore interpolates the raw padded strings. The hourly zero comparison at :275–278 and monthly day interpolation at :291–292 expose the same missing whole-token normalization.
- Exhaustive production search found **two preview callers**: `dashboard/src/routes/services.new.tsx:94–96` and `dashboard/src/features/services/components/cron-deploy-section.tsx:88–92`. One Settings mount at `routes/services.$serviceId.settings.tsx:169–173` covers image/Git/buildpack/Dockerfile crons. `routes/cron.$.tsx:5–7` redirects through `common/lib/render-alias.ts:17,40,63–70` to the same canonical Settings/create routes.
- Resource census: cron only; web, private, worker and static types do not enter these schedule previews; Postgres and Key Value have separate forms. The shared validation consumer `features/services/lib/create-service-input.ts:156` does not describe schedules and needs no behavior change.
- Server acceptance and next-run projection use `cron.ParseStandard` in `lego/backend/internal/apps/service.go:4340–4353,1320–1334`. The pinned dependency is `robfig/cron/v3 v3.0.1` (`lego/backend/go.mod:20`); its installed `parser.go:321–340` resolves numeric tokens with `strconv.Atoi`. The complete live create/update/read responses agree with that code. Current main still contains the formatter defect.

## Target behavior and acceptance

Normalize already-validated whole unsigned numeric tokens **for the preview only**, before phrase selection and clock/day interpolation. Keep the raw input and saved schedule exact. Reuse the shared helper; do not patch each form or tighten acceptance to reject padding. Keep named tokens, `?`, compound ranges/lists/steps, current best-effort fallbacks, localized catalogs, zero-step/never-fires guards and command write semantics intact.

Extend existing `features/services/lib/__tests__/cron.test.ts:85–104` with ordinary/padded equivalence for daily, weekly, monthly and hourly-zero shapes in en/zh. Assert the expected canonical clock/day and unchanged acceptance, including the existing long-leading-zero vector in `lego/backend/internal/apps/testdata/cron-schedule-vectors.json:19`. Preserve the named-token and interval-boundary tests; compound expressions and plus-prefixed tokens can retain their existing best-effort fallback. Recheck Create and fresh saved Settings at desktop and 390×844, Cancel, invalid input, and unchanged API schedule/next-run values. Run applicable dashboard checks and simplify the small helper change.
