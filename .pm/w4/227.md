# w4/227 — Cron “Last run” labels the last successful run

Why: a failed or canceled run should not make the header appear stale; name the successful-run timestamp the API actually provides.

**Severity:** minor (misleading metadata label; execution/history/last-success data remain correct). **Estimate:** 30m. **Status:** open. Source: live `$qa-find-bugs w4`, 2026-10-09 pass a27, QA workspace `bex` (`tea-d98210cbbpdc73dcrkvg`). Filing only; product code is unchanged.

## Live reproduction

1. Create a Free cron from Existing Image `docker.io/library/busybox:1.37`, name `qa-20261009-loop-a27-cron`, schedule `0 0 1 1 *` (UTC; prevents scheduled firings during this test). Give it synthetic `MESSAGE=qa-a27 cron env marker` and file `qa-a27.txt` containing two marker lines. The exact wizard mutation is below.
2. Events → Trigger Run → confirm. Run `crr-r6n1aovhkf1jilhc1ol9` finishes `successful` at **11:06:43 UTC**; its stdout contains the environment marker, both file lines, and end marker.
3. Settings → Deploy → Edit command. Save a bounded command that prints the markers, sleeps 3 seconds, emits a synthetic error, and exits **7**. Events → Trigger Run → confirm. Run `crr-8ov5qrd02o9tjgbcuhh9` finishes `unsuccessful` at **11:09:12 UTC**. Activity correctly says “Failed — The run exited with status 7”; Recent Runs lists it newest.
4. Fresh reload at **11:09:29.179 UTC**, desktop 1440×1000: header says **“Last run: 2m”**. Its actual `<time datetime>` is **11:06:43Z**, the earlier successful finish, while the latest run started 11:09:05Z and finished 11:09:12Z. The exact GraphQL query reports that same instant under the accurately named `lastSuccessfulRunAt`. REST run history and MCP get-run agree on the newer failure.
5. Fresh `?lang=zh` load at **11:10:22.602 UTC**, 390×844: header says **“上次运行：3m”** with the same 11:06:43Z instant. The newest run correctly says 失败 at 11:09:12Z. Document width remains 390px.

This persists after reload; the timer itself advances. The API field is the last **successful completion**, whereas the catalog labels it the last run of any outcome. This is a copy defect, not lost history or failed execution.

The REST/MCP render mapping in `apps/render.go:376,417` carries that same value. The direct captures below and the later-success control confirm the field's intended semantics.
- Catalog plumbing is expressible with the existing key and no type/schema change: `i18n/index.ts:45–50` extracts each entry's **message**, not description; English aggregates the service catalog, and `i18n/resources-zh.ts:47` does likewise for Chinese. `common/hooks/use-translations.ts` forwards the key to react-i18next. Render deep-link families `/web`, `/pserv`, `/worker`, `/cron`, and `/static` route through the shared service family (`common/lib/render-alias.ts`); no alias-specific copy is needed. Postgres/Key Value use separate headers and do not consume this key. Only the two en/zh definitions and this header consume the key in production; tests are additional literal consumers.

**Adjacent classes:** this catalog edit does not change mutation success, authorization, not-found, timeout, unknown service, or loading routing.
