# w4/193 — Generate Blueprint returns 500 "Internal error" for a plain git/Docker service, and one bad service sinks the whole export

Why: Generate Blueprint is how users turn running services into a committable `render.yaml`. Today selecting the workspace's most ordinary git-backed service gives a bare "Internal error" toast, with nothing to act on, and blocks every other service selected alongside it.

Live 2026-10-04 UTC (`/qa-find-bugs` loop12, muse.env, `bex-canary`). Read-only: nothing was created or changed.

- Dashboard `/blueprints` → Generate → check `hello-go` → Generate shows the toast "Internal error" (`.playwright-mcp/qa-blueprint-generate-500-1.png`). Adding a good service (`qa-20261003-f592c7-zero`) to the selection also shows "Internal error".
- REST, from the dashboard origin: `POST /v1/blueprints/generate {"ownerId":"tea-daif693dqjvc73e7as3g","serviceIds":["srv-daif6dsmg29s73d1umvg"]}` returns `500 {"error":"internal error"}` (with or without `ownerId`).
- Controls, same call, 200:
  - the cron `srv-dap3v694dm7c7390q930` gives `runtime: image`, `schedule`, `startCommand`;
  - the image web service `srv-db09u90ehcmc739j12cg` gives `envVars: [{key: HTTP_PORT, sync: false}]`.
  - With no ids the call gives a proper 400 "select at least one resource".
- `hello-go`'s shape (REST/GraphQL): `web_service`, `repo: https://github.com/bex-co/bex`, `branch: main`, `rootDir: examples/hello-go`, `runtime: docker`, `dockerContext: examples/hello-go`, `healthCheckPath: /`, one env var `MESSAGE`. It has no secret files, routes, headers, build filter or pre-deploy command, and GraphQL `linkedEnvGroupIds: []`.

Narrowing (cause unverified; no production log access this run):

- The self-validation branch (`lego/backend/internal/apps/blueprint_generate.go:196-203`) is **ruled out for the reconstructed shape**. A throwaway local test fed the manifest `generateServiceEntry` would emit for the fields above, with and without `dockerContext`, through `CompileBlueprintIR` + `parseCompiledStack`, and both passed (test deleted).
- In `generateServiceEntry` (`:238-350`) and `generateEnvVars` (`:361-416`) the only remaining error return is `resolveEnvGroupExport` → `envgroups.ExportEnvGroup` (`:400-406`, `envgroups/service.go:426-442`). It runs for each `spec.envFromSecrets` entry matching `evg-…-env`. A stale entry (the group is gone or moved, but the App spec still references it) whose error is not `core.ErrNotFound` would surface exactly as this 500. That is consistent with `linkedEnvGroupIds` (group-side metadata) reading empty. **Confirm from bex-api logs for these calls (around 01:2x UTC 2026-10-05) before fixing.**
- Separately, every non-public error from `GenerateBlueprint` (including its own "generated Blueprint failed self-validation (…); this is a bex bug") is masked as `internal error`. So even the generator's self-diagnosis never reaches the caller.

Fix:

1. Read the logged cause and fix it. If it's the stale-link case, skip an unresolvable linked group the way `ErrNotFound` is already skipped, and list the keys as `sync: false` only when known.
2. Return a coded, value-free error that names the failing resource id (e.g. `BLUEPRINT_GENERATE_FAILED`, `{resourceId}`), so the dashboard can say which service blocked the export. Keep the "this is a bex bug" self-check distinguishable.
3. Test: an App whose `envFromSecrets` references a deleted group exports successfully (200) on REST/GraphQL/MCP `generate_blueprint`.

Unverified: the exact cause (above); whether MCP `generate_blueprint` and GraphQL `generateBlueprint` fail identically (same service function, not probed). Render: n/a (Render has no generate-from-existing). Severity: major (a primary export flow is unusable for this service, and its error is opaque). Estimate: ~1h.
