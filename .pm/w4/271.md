# Webhook Settings stays dirty after an accepted trimmed save

Why: a successful webhook edit should show the accepted values and stop offering the same save again.

- **Severity:** minor; persistence is correct, but the mounted form retains padded inputs and permits repeated successful no-change PATCHes.
- **Source:** functional `$qa-find-bugs w4`, 2026-10-12 UTC, pass a273; workspace `tea-d98210cbbpdc73dcrkvg`. Own endpoint `whk-db68t73dn4ls739pjndg` was created disabled, remained disabled through every edit, then was deleted. No delivery or product-code change in this pass.
- **Estimate:** 55m: scoped form/hook correction and behavior tests.

## Reproduction and target

On `/webhook/<id>/settings`, paste a valid Name and Destination URL with two surrounding spaces, then click **Save changes**. At 07:40:48.766 UTC the real UI mutation sent trimmed values and returned HTTP 200 with the accepted endpoint. A fresh API query at 07:40:50.053 returned the trimmed name `qa-20261012-a273-picker-雪` and URL `https://qa-20261012-a272-hook.onbex.co/qa-a273-trimmed`; the detail heading also showed the accepted name. The controlled inputs still contained their spaces and Save remained enabled. Clicking Save again without editing sent the same name/URL patch and returned another 200 at 07:41:25.522.

A full reload restored canonical inputs and disabled Save. Starting from that clean page, padding **Name alone** reproduced the defect: successful mutation 07:42:14.229, padded input and enabled Save 07:42:15.552. A second full reload followed by padding **URL alone** reproduced it separately: successful mutation 07:43:19.353, padded input and enabled Save 07:43:20.643. The final fresh query at 07:45:30.899 still returned the exact accepted URL while the 390px form input retained its spaces and Save stayed enabled.

**Target:** after an accepted save, submitted Name/URL fields that have not been edited again display the values returned by that successful mutation. When no newer draft differs from those accepted values, Save is disabled and a second click cannot submit the same patch. If a newer edit was entered while awaiting the response, preserve that edit and leave Save enabled. Preserve existing trimmed persistence; storing padded strings would make the state agree by breaking the accepted contract.

Controls actually run: ordinary unpadded rename + explicit event selection became clean immediately (07:40:47.930); selecting All persisted the compact `eventTypes: []` sentinel and reloaded as all 53 catalog events; removing Deploy Ended persisted 52 explicit keys with a mixed master checkbox; raw-key search and no-match search preserved selection; the 390px form's main region remained 390/390 client/scroll width. The API, heading and inputs are deliberately recorded separately: accessibility snapshots collapse visible whitespace, so the defect relies on exact `inputValue()` strings, not the snapshot's flattened display.

## Root cause and bounded fix

- `dashboard/src/features/webhooks/components/webhook-settings-card.tsx:56` seeds Name/URL local state from endpoint props. `:76–81` compares the raw drafts against accepted values. `:97–103` trims outgoing Name/URL but neither consumes the successful result nor adopts accepted values.
- `dashboard/src/features/webhooks/hooks/use-update-webhook.ts:20–22,48–52` exposes only `Promise<boolean>` and discards the mutation data. The response already selects Name/URL plus endpoint identity in `features/webhooks/api/webhooks.graphql`.
- `dashboard/src/routes/webhook.$webhookId.settings.tsx:19` keeps the same form keyed by endpoint id. A save changes the normalized endpoint and heading without remounting the draft. Remounting on every endpoint change would discard unfinished edits.
- Server `lego/backend/internal/webhooks/service.go:811–842` merges omitted fields and returns the accepted endpoint; `:850–867` trims the URL and `:948–954` trims Name. That behavior is correct. REST PATCH, GraphQL update and MCP update share this service; they do not need a new normalization contract.
- Actual installed/locked dependencies: React **19.2.3**, Apollo Client **4.1.3**. Read `react-dom/cjs/react-dom-client.development.js:8264–8293` (mount state), Apollo `react/hooks/useMutation.js:87–112` (returns mutation response), and `core/QueryInfo.js:205–235,274–284` (writes accepted mutation data to cache). The accepted response is available; the application hook throws it away. A cache refetch by itself cannot replace these controlled drafts.

Return a typed accepted result from `useUpdateWebhook` instead of only success. It may expose the accepted Name/URL subset with an explicit success/failure distinction; reuse the existing endpoint read mapping if returning the whole view (`use-webhook.ts:15–31`). Do not cast raw generated rows into draft state or turn a missing accepted record into empty strings. Capture submitted draft values before awaiting, and use field-specific functional setters to adopt the accepted Name/URL only when that field's current draft still equals the submitted draft. Do not add an unconditional props-to-state effect or change the route key.

**Consumer census:** exhaustive non-test `useUpdateWebhook(` search found one production caller, WebhookSettingsCard; its one route mount is `/webhook/$webhookId/settings`. The create page uses a different create hook. EventPicker has two production field consumers, Create and Settings, through WebhookEventPickerField; its search/selection logic does not need changing. The list and Activity view read the normalized endpoint and should retain their current behavior. No REST/GraphQL/MCP schema or runtime rollout change is proposed.

**Adjacent behavior:** failed/validation-rejected saves retain drafts and current feedback; preserve optional patch fields, disabled delivery state, busy guards, event selection and the all-events sentinel. Name/URL remain editable while saving today (`webhook-settings-card.tsx:167,199`); the new result adoption must preserve later input. Do not broaden this item into external-update conflict handling.
