# 474 — Adding a registry credential silently binds it to every service that pulls a public image from the same host, and the credential then cannot be deleted

Why: a user who adds a Docker Hub credential for one private image, or a wrong or expired one, changes the pull identity of every existing public `docker.io` image service in the workspace without being told. Its next deploy pulls with that credential and fails if the token is bad (Docker Hub rejects invalid credentials even for public images). Deleting the credential is refused as "still used by service X", yet X shows no credential and has nothing to remove. Render binds a credential only when it is chosen on the service.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 12, 2026-11-04 13:16 UTC (`muse.env`, pin `9d4e3a138783`). **Major**: it silently changes production pull identity, and the credential cannot be undone. ~1h, possibly a milestone once the decision below is made.
- **Repro** (workspace `bex`, which a fresh login lands in; this run added a credential there by mistake while aiming for `bex-canary`):
  1. Settings → Registry Credentials → Add: host `docker.io`, a username and a throwaway token, name `qa-20261104-reg`. The toast reads "Added a credential for docker.io" and REST lists `rgc-dblj0iug3pks73ck0kn0`.
  2. `DELETE /v1/registrycredentials/rgc-dblj0iug3pks73ck0kn0` → **409** `{"code":"REGISTRY_CREDENTIAL_IN_USE","message":"registry credential \"rgc-dblj0iug3pks73ck0kn0\" is still used by service \"tea-d98210cbbpdc73dcrkvg-crypto-price-clickhouse\"; remove it from the service first"}`.
  3. That service (`srv-dbg4lfdn83uc738uug70`, image `docker.io/clickhouse/clickhouse-server:23.8`, last updated 2026-10-27, so untouched by this run) reads `registryCredentialId: null` on REST and GraphQL. The dashboard has nothing to "remove".
  4. Of the workspace's 12 services, it is the only image-backed one on `docker.io`. Repo builds never host-match (`registrycreds/pullsecret.go:101-102`).
- **Root cause:**
  - `registrycreds/pullsecret.go:74-119` `resolvePullCredential`: for an App with no explicit `registryCredentialId`, it uses the **newest** workspace credential whose host matches the image (`store.GetRegistryCredentialByHost`, `store/registrycredentials.go:163`, `ORDER BY created_at DESC LIMIT 1`; fallback `credentialForHost` at `pullsecret.go:305-319`). Expiry is not considered.
  - `materializePullSecret` (`:135-166`) then writes that credential into the App's `<app>-registry-pull` Secret on its next create or deploy (`apps/pullsecret.go:110-114`).
  - `appBoundToCredential` (`pullsecret.go:270-302`, added by w4/m82 t003) counts that implicit match as "in use", so `Delete` (`registrycreds/service.go:383-394`) refuses. The only way out is editing every matching service to an explicit `registryCredentialId: ""`, which "explicit clear" honors at `pullsecret.go:75-76`.
  - `UpdateRequest` (`service.go:290-296`) cannot change the host, and expiry does not disable the match.
- **Render:** [render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image), fetched 2026-11-04: "The **Credential** dropdown includes any existing credentials you've already added … You can reuse the same credential across multiple services." Credentials are selected per service. "You can't remove a credential if at least one service uses it": that is, uses it by explicit selection.
- **Decision for `/unblock w4` (parity-sufficient default first):**
  1. **Parity (recommended):** stop host auto-matching for services that never chose a credential. Bind only explicitly, as Render does. Migrate existing apps that currently rely on an implicit match by writing their resolved credential ID explicitly once, so private pulls that work today keep working, and record it in ADR018.
  2. A smaller interim step: keep host matching but exclude it from `appBoundToCredential`, and ignore credentials created after an app's last successful pull.
- **Blast radius:** every image-backed service (web, private, worker, cron) whose image host has a workspace credential and no explicit ID; Docker builds' `FROM` pulls are excluded. Callers of `resolvePullCredential`: `materializePullSecret`, `ValidatePullSecret` (create/update validation) and `appBoundToCredential`'s mirror logic. Surfaces: dashboard Settings → Registry Credentials and the service Source card, REST `/v1/registrycredentials`, GraphQL and MCP credential tools.
