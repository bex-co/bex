## Objective

Decide and write down the enforcement semantics before any code: which resources an environment's IP rules apply to, how workspace/environment/service layers compose, and how bex migrates from empty-means-open to Render's empty-means-deny without locking out existing tenants.

## Context

- `docs/render-artifacts/protected-environments.md:38` — Render: rules apply to eligible public web services/static sites + datastores; a source must pass every applicable workspace, Environment, and service rule; deleting every rule = deny-all; dashboard seeds `0.0.0.0/0`; IPv4 CIDRs only.
- bex today: `Environment.ipAllowList` fans only to member Postgres/Key Value; empty = open. Service-level allow-lists exist per-datastore; the service (App) object's `ipAllowList` shipped via the spec field-diff rounds — verify its current enforcement point.
- bex has no workspace-level rule surface today — decide whether to include it now or record it as an explicit deferral.
- Migration risk: a flag-day flip of empty→deny-all locks every existing environment's members out. Likely answer: seed `0.0.0.0/0` into existing rows, then adopt deny-all semantics.

## Steps

1. Verify Render's semantics against its current docs (re-capture if needed).
2. Inventory bex's current enforcement points (datastore SNI allow-lists, Traefik middleware from w7/m32/w6/m30 groundwork, App CR fields).
3. Write the decision (targets, composition, defaults, migration, IPv4-only stance) into `docs/ADR032-environments.md` (new § Inbound IP rules) and update the artifact doc's drift paragraph with the plan.
