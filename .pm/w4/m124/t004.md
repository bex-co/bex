## Objective

Make generate → validate a guarded loop, so the exporter and the planner cannot drift apart one field at a time. Two independent fields broke it in one pass; a per-field fix without a guard just waits for the third.

## Context

- The kinds to cover: web, static, cron, worker, private, Postgres, Key Value, env group. Only web and key-value were probed live in pass 110.
- `blueprint_generate_test.go` already exists and has fixtures; the guard belongs beside it, driving the real planner rather than a stub.
- The guard has to build each fixture with its optional fields *populated* — the bug was in `domains`, a field an empty fixture would never emit.
- Open question this task answers: does a spurious `update` cause a real `syncBlueprint`/`createBlueprint` apply to write? If apply is a no-op in practice, this is a trust bug; if it writes, it is a correctness bug and the severity rises.

## Steps

1. Write the guard: for each kind, build a resource with optional fields set, export it, plan the export against it, assert `noop` and empty `changedFields`.
2. Run it against every kind and fix or file what it catches.
3. Determine what apply actually does for a spurious `update`, and record the answer.
4. If any kind cannot round-trip for a reason that is deliberate, encode that as an explicit exemption with its reason, the way the env-group branch does.
