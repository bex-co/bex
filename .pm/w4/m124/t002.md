## Objective

An exported key-value block re-plans as `update` with every declared field listed. Find out why. This is its own claim: the service-side cause is traced, this one is not, and assuming they share a root cause is how a fix lands on the wrong line.

## Context

- Live: the exported entry `{ipAllowList: [], maxmemoryPolicy: allkeys-lru, name, persistenceMode: journal-snapshot, plan: starter, type: keyvalue}` re-plans as `update`; changing `maxmemoryPolicy` to `noeviction` produces byte-identical output, so the reported fields say nothing either way.
- `ipAllowList` could not be isolated by omission — the schema requires it (`at '/services/0': missing property 'ipAllowList'`). Dropping `maxmemoryPolicy`, `persistenceMode` or `plan` individually still yields `update`.
- **Candidate, not conclusion:** `ipAllowList` is the only list-valued field in the block, and the list-valued `domains` is the proven cause on the service side. `ApplyBlueprintKeyValueSpec` (`blueprint_plan.go:340-356`) does `dst.IPAllowList = slices.Clone(want.IPAllowList)`, and `reflect.DeepEqual(nil, []T{})` is false — so a live `nil` against an exported `[]` would do it.
- ~~The two enum-ish values are a second candidate: REST reports `maxmemoryPolicy: "allkeys_lru"` and `persistenceMode: "journal_snapshot"` (underscores) while the manifest uses hyphens.~~ **Weakened by live evidence, pass 120 — start with `ipAllowList` instead.** The write path accepts *both* spellings: `setKeyValueMaxmemoryPolicy(maxmemoryPolicy: "allkeys_lfu")` — the underscored form a read returns — was accepted **and applied** (`noeviction` → `allkeys_lfu`, confirmed by re-read), as was `persistenceMode: "journal_snapshot"`. Only genuinely unknown values are refused. So a canonicalizing parse does exist somewhere on that path, and the enum spelling is unlikely to be what flips `DeepEqual`. Still worth confirming that `ApplyBlueprintKeyValueSpec` sees the canonical form rather than the raw manifest string, but it is no longer the leading hypothesis.
- Both candidates are testable directly against `ApplyBlueprintKeyValueSpec` in a unit test with a real spec — do that rather than guessing from the wire.

## Steps

1. Unit-test `ApplyBlueprintKeyValueSpec` with a probe spec matching the live resource and the exported field set; find which assignment flips `DeepEqual`.
2. Fix that one, then re-run the whole exported block for `noop`.
3. Check the same two candidate classes on the Postgres and service appliers — the hyphen/underscore question applies wherever a manifest enum meets a stored enum.
4. If `ipAllowList` is the cause, check whether the required-ness of `ipAllowList` in the key-value schema is itself right; a required field that most users do not want to set is worth a note.
