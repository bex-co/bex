# 615 — A web image service is restarted with `PORT` set to the port bex found it listening on (8080, or the image's `EXPOSE` 80), not Render's 10000; an image that also uses `$PORT` for an internal listener then crash-loops and never goes live

Why: Render's rule is "The default value of `PORT` is `10000` for all Render web services", and finding another port changes only where traffic goes. w8/267 made bex follow it for natively built services, but a Docker image web service still has the selected port written into its environment. Every such service sees a `PORT` Render does not give it. The w8/267 app shape — a public listener on a fixed port, an internal one on `$PORT` — runs on its first start, then binds the same port twice. The crash hint then tells the user to "listen on $PORT (8080)", which the process already does.

- **Root cause:**
  - `processPort` (`lego/operator/internal/controller/port_detect.go:100-105`) keeps `PORT` at the default only when `servingPortDetected` (`:89-91`) holds, and that reads `Status.DetectedPort` alone — the native detection (w8/177, w8/202).
  - A web image service's port comes from its image network instead: `ServingPort()` returns `Spec.EffectivePort()` for image-port services (`lego/types/v1alpha1/image_network.go:211-216`), resolved from the image's `EXPOSE` set or the HTTP selection (`HTTPSelectionDetected`, `lego/operator/internal/controller/web_image_http.go:166-181`, w8/m141).
  - So `appEnv` (`app_controller.go:5860-5880`) writes that port as `PORT`, and the changed template rolls a new instance with it.
  - The crash hint has the same gap. `crashHintPort` (`port_detect.go:110-115`) uses the same predicate, and the web image path skips it, passing the raw port to `permanentRolloutCrash` and `stuckPodMessage` (`web_image_http.go:238`, `:256`).
- **Fix (target behavior):** for a web service with image ports, no configured port and no `PORT` variable (`discoversWebImagePort`, `web_image_http.go:44-48`), the process receives `PORT=10000` on every instance, whatever the image declares or the scan selects. Container port, Service, Ingress and probes keep following the selected port.
  - Extend the predicate `processPort` and `crashHintPort` share to cover that case.
  - Pass `crashHintPort(app, port)` at `web_image_http.go:238` and `:256`, so a crash hint never names a detected port as `$PORT`.
  - Keep `noOpenPortMessage`'s "it listened on port N before" wording (`port_detect.go:198-210`, w8/281) working for both paths.
- **Blast radius:**
  - `processPort` has 2 callers, `appEnv` (`app_controller.go:5878`) and `noOpenPortMessage` (`port_detect.go:205`). `appEnv` feeds the app container (`app_controller.go:5685`, `deployment_projection.go:288`) and the pre-deploy Job (`app_controller.go:7171`).
  - `crashHintPort` has 2 callers (`app_controller.go:3787`, `:6075`), plus the 2 web image call sites above.
  - Private `image-v1` services keep "`PORT` is the resolved primary", a divergence ADR004 (§ Image-port private services) documents. They are out of scope and need a regression test that they are unchanged.
  - An explicit port or a user `PORT` keeps winning (`configuredPortMode`, `Status.EnvPort`).
- **Tests:**
  - an operator unit test over `processPort` and `crashHintPort` for a web image with `HTTPSelectionDetected`, and for one with an `EXPOSE`-declared primary → 10000 and 0;
  - controls: explicit port, user `PORT`, a private `image-v1` service → unchanged;
  - an envtest that the detection rollout's new template carries `PORT=10000`.
- **Unverified:**
  - Render's behavior for an image whose `EXPOSE` names another port. Render's docs say 10000 "for all Render web services", but no Render Docker capture was taken.
  - Whether the px deploy eventually settles failed at the deadline. It was still `update_in_progress` at 20:29:06 with both instances listed, and at 20:30:28 when it was deleted. That is the w4/m351 class.
- **Render:** [web services § port binding](https://render.com/docs/web-services#port-binding): "The default value of `PORT` is `10000` for all Render web services", and "If you bind your HTTP server to a different port, Render is _usually_ able to detect and use it."
- **Dedupe:**
  - [w8/267](../../w8/done/267.md) (done) fixed native detection. Its own Unverified line says "Image-backed services with an undeclared listener (w8/205's path) were not run", and this is that path.
  - [w4/m350](m350/README.md) t001 step 3 asked to "file that Render divergence separately" if the first instance's `PORT` isn't 10000. This note is that filing. m350's double roll is independent and stays open.
  - w8/281 (done) fixed the native no-open-port wording.
  - Not deploy lag: `git log 33e1b1e6117c..origin/main -- lego/operator lego/types` touches only the build termination-message budget (w8/295).

## The create wizard documents the behavior this note changes — 2026-11-13 (round 249)

Read live while creating a web service from New Service → Existing Image (pin `c328714af1dd`). The Port field's hint reads "Optional. bex publishes every TCP port the image declares (EXPOSE); 3000 if declared, else the lowest declared, else 10000, becomes $PORT and the health-checked primary. Set a port to choose the primary yourself." That is `services.createFieldPortImageHint` (`dashboard/src/features/services/locales/en.ts:3649-3654`; zh `zh.ts:3574`).

- The fix changes `$PORT` for **web** services only. The hint must then say that the selected port becomes the health-checked primary, while `$PORT` stays 10000 unless set.
- A private `image-v1` service keeps "becomes $PORT" (ADR004 § Image-port private services), so the wizard needs two variants, chosen by service type. Today one string serves both, per its description: "a Docker-built or prebuilt-image web or private service".
- The tab's own line, `services.createImagePortHint` ("bex uses the port the image declares (EXPOSE). …", `en.ts:3619-3623`), says nothing about `$PORT` and can stay.
- Add a DoD bullet: the web wizard's Port hint no longer says the declared port "becomes $PORT", and the private wizard's still does. Check en and zh.
