## Objective

Name the actual cause from cluster state, not from inference, before anything is changed.

## Context

- Probes and candidates: [README § Finding](../README.md#finding-round-253) and § Unverified.
- Issuance: `lego/operator/internal/controller/database_public_tls.go` (`preparePublicTLS` `:154`, `settlePublicTLS` `:313`, condition `PublicCertificateReady` `:97-100`). ClusterIssuer: `BEX_DB_CLUSTER_ISSUER=letsencrypt-prod` (`lego/operator/config/prod/kustomization.yaml:111`).

## Steps

1. Create a throwaway public Free Postgres (`qa-<date>-…`) in `bex-canary`.
2. In its workspace namespace, read:
   - `kubectl get certificate,certificaterequest,order,challenge` for `<db>-public-tls`, and `kubectl describe` each;
   - the Database CR's `status.externalCertificate` and the `PublicCertificateReady` condition;
   - cert-manager's controller log for the Order.
3. Check for Let's Encrypt's rate-limit error, e.g. "too many certificates (50) already issued for "bex.co" in the last 168h". Count this week's `*.db.bex.co` and `*.kv.bex.co` orders from the cluster's Certificate history, since crt.sh lags.
4. Record the cause, with the exact messages, in the README.

## Acceptance criteria

- [ ] The README names the cause, with the quoted Order or Challenge status and the condition reason. t002's approach follows from it.

## Outcome (2026-11-14, done)

The cause is Let's Encrypt's new-certificates-per-registered-domain limit for `bex.co` (50 per rolling week, refilled about one per 202 minutes), exhausted by QA rounds that each create a public datastore; cert-manager's 1 h → 32 h failure backoff then stretched each stall past the refill. Evidence, quoted statuses and the fresh fixture's run are in [README § t001 diagnosis](../README.md#t001-diagnosis--the-bexco-lets-encrypt-budget-2026-11-14-12261250-utc): a fixture created with room in the bucket issued in 45 s (`PubliclyTrusted`, `Issued`, Let's Encrypt YR1, verify 0); certspotter shows 95–99 `bex.co` certificates in the 168 h before each failed round and one issuance per refill after 02:00 on 2026-11-13. The failed window itself had rotated out of cert-manager's log (which now holds only `onbex.co` 429s, w4/650).
