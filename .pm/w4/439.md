# Production stops deploying under steady manifest pushes: every finished run is superseded, nothing pinned for 7 h+

Why: w2/050 accepted "about two run durations" as the worst case after a manifest push. Manifest-changing commits now land about once an hour, while a run takes 1.5–2.6 h from creation to its write-back, so every finished run is superseded and production stays on an old build indefinitely. Fixes on `main` do not reach users.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-10-30 04:10 UTC; **major** (no hosting fix or feature reaches production while it lasts), ~1–2 h. Deploy pipeline (`deploy.yml`, `scripts/deploy-superseded.sh`); residual of `w2/done/050.md` and `w1/116`.
- **Evidence:**
  - The last pin is `chore(deploy): pin platform images to 2ac6fd95402e`, committed 2026-10-29T21:19:16Z.
  - Since then, 24 commits under `lego/` or `dashboard/` have landed, and none of them is live.
  - Two runs completed `success` but logged at write-back `##[notice]superseded by a newer run — images built but intentionally not pinned; skipping the rollout`:
    - `885d61317`: created 22:34:09Z, ended 00:06:13Z.
    - `d7bb78a30`: created 01:11:46Z, ended 03:49:59Z.
  - Every intermediate run (`dffe10a88`, `982ab4a17`, `8d411e708`, `5689bfe0d`, `a1f63153a`, `2de693f18`, `b24ac4b42`, …) was cancelled by the `bex-production-deploy` concurrency group.
  - Manifest-changing commits since the pin (`git log 2ac6fd954..origin/main -- deploy/opensandbox deploy/gitops .github/workflows/deploy.yml lego/operator/config`), committer time −07:00:
    - `3ae1e6f35` 15:43

    That is one every 20–100 minutes, each shorter than the run that would have pinned.
- **Root cause:** `scripts/deploy-superseded.sh` (header, lines 15-24; rc 0) correctly refuses to pin images built from a tree older than newer **manifests**: the stale-digest guard. `deploy.yml`'s concurrency then cancels every pending run except the newest. The newest pending run starts only when the current one finishes, builds for 1.5–2.6 h, and by then a newer manifest commit has usually landed, so it is superseded too. Nothing bounds this while manifest pushes arrive faster than one run's duration. w2/050 shipped only the superseder naming and explicitly left this case "by design" (its Acceptance note).
- **Target behavior:** under steady pushes, including manifest pushes, production pins a build of a recent `main` within about one run's duration of a quiet moment, and never more than about 2 h after the last pin, without ever pinning images onto manifests newer than their tree.
- **Fix options (decide in the fix; all keep the stale-digest guard):**
  1. **Build from the tip, not the trigger.** When a run starts, re-resolve `origin/main` and check out its tip, so the images' tree is the newest manifests at build start. Then only manifest commits landing during the build can supersede it.
  2. **Rebuild-on-supersede instead of skip.** When the write-back guard finds newer manifests, re-dispatch a run for `origin/main`'s tip immediately, before newer pushes queue behind it, and make that run non-cancellable by later pushes until it pins.
  3. **Shorten the window.** Skip the CVE and signing steps, or make them async, for images already scanned at an identical digest, so a run fits inside the typical manifest push interval.

  Option 1 is the smallest change. Measure the build-to-write-back window after it.
- **Tests:** extend `scripts/deploy-superseded.test.sh` with a simulated sequence of manifest commits landing every N < run-duration minutes, and assert that a pin happens within the bound. Keep the existing cases: rc 0 for newer manifests, rc 1 for docs-only, rc 3 for image-source-only.
- **Unverified:** whether queue time (waiting for the concurrency slot) or the build itself dominates the 1.5–2.6 h. Both runs' step timings should be read before choosing an option.
- **Dedupe:** `w2/done/050.md` is the same mechanism, closed with this case excluded as by design. `w1/116` fixed image-source starvation (rc 3). No open item covers manifest-drift starvation. No DO_NOT_DO item applies.
- **Not a red-main fix:** runs are green, so the "fix CI first" rule does not apply. This is a throughput defect, filed so a worker owns it.
