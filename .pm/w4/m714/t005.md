## Objective

Every Postgres that existed before t002 ends up with all of its instances on encrypted volumes, losing no data and costing the tenant at most one CNPG switchover.

## Context

- A claim's class is immutable and the hcloud driver formats LUKS only on a new volume, so a volume cannot be encrypted in place: each instance has to be rebuilt on a new claim.
- CNPG can add an instance (it streams a base backup onto a new PVC), switch the primary over, and destroy a chosen instance with its PVC.
- The operator owns each Cluster's `instances`, so a temporary extra instance needs the operator's cooperation (a migration state on the Database), not a hand edit it would revert.
- Render's `/maintenance` scheduling is a recorded non-goal, so this is a platform operation.

## Steps

1. Implement the move in the operator: for a Database with any PVC off the encrypted class, add one instance on the new class, wait until it is streaming, switch over to it, destroy the old instance, and return to the plan's instance count. HA: rebuild the standby first, then switch over and rebuild the old primary. Read-replica clusters move the same way. Report progress in a status condition.
2. Start it per Database (an annotation or an operator verb) so production can move one at a time, and write the runbook.
3. Move bex's own fixture databases first, then every other database, checking each one's row counts and connection after its switchover.

## Files

- `lego/operator/internal/controller/database_controller.go` (+ tests), `docs/runbooks/<new>.md`.

## Acceptance criteria

- [ ] envtest: the move ends with every PVC on the encrypted class and the plan's instance count, and the move is idempotent when it is interrupted at each step.
- [ ] On dev-4 a database with data moves, and its data and connection string are unchanged.
- [ ] On production no Database PVC remains on `hcloud-volumes` (counted with `kubectl get pvc -A -l cnpg.io/cluster`).

## Out of scope

- The platform's own CNPG clusters (`bex-postgres`, `auth-dbs`).
