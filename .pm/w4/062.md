# Return the authenticated user ID in CLI whoami

Why: the pinned CLI now prints and serializes the authenticated user's ID, but Bex's REST projection drops it and returns a misleading empty ID even after successful human login.

- Severity: minor; server compatibility. Identity login succeeds; this breaks identity output rather than access authorization.
- Source: continuous CLI QA for w4, 2026-09-09 PDT / 2026-09-10 UTC; ADR006/ADR018, identity conventions ADR020, prior user-trait resolution w4/m25.
- Versions: installed `/opt/homebrew/bin/bex` v0.2.1, build `423855d5512091bb349585641937260582fab77d`; Render CLI v2.27.0 / `a764810a768202704e7206eb7b87a47211fcd98e`; checkout `f232d00b4`; deployed platform revision unknown.
- Context: human device OAuth, isolated 0600 CLI config, `BEX_HOST=https://api.bex.co/v1/`, `BEX_WORKSPACE=tea-d98210cbbpdc73dcrkvg` (bex), non-TTY JSON. No resource creation needed.

## Reproduction and complete response

After successful isolated `bex login`, run `bex whoami -o json` in fresh processes. It repeatedly exits 0, empty stderr; timed retry 0.34s. Complete stdout:

```json
{"email":"puncsky@gmail.com","id":"","name":""}
```

Raw diagnostic request: `GET https://api.bex.co/v1/users`, `Accept: application/json`, `User-Agent: render-cli/2.27.0 (macOS - 26.5.1)`, `Authorization: Bearer <this run's human OAuth token>`. HTTP 200, 0.29s; complete response body:

```json
{"email":"puncsky@gmail.com","name":""}
```

Expected: the stable authenticated human subject in `id`, with the existing email/name semantics preserved. Empty name is a supported legacy identity state and is not this finding. No JWT/config/device code is needed in evidence.

## Root cause and concrete fix

- Pinned consumer `pkg/client/types_gen.go:3518-3524` declares `User.Id string` as `json:"id"`, described as the authenticated user's ID. `cmd/whoami.go:27-47` returns this generated type through `command.NonInteractive` and prints its ID in text mode. Missing wire `id` silently decodes as `""`.
- Producer `lego/backend/internal/workspaces/render.go:52-58` defines `renderUser` with only Email/Name and copies only those fields. `workspaces/service.go:631-634` likewise omits identity from UserView; `CurrentUser` at `:649-681` already has the authenticated subject and resolves machine credentials through KeyOwners when needed. REST `workspaces/rest.go:34-39` is the only production caller of CurrentUser and toRenderUser (searched all backend non-test Go files).
- Add an ID field to UserView and the REST projection. For human session/device OAuth callers retain the authenticated subject; for bound machine credentials use the resolved owning human's ID alongside that human's traits. Never mint a new ID, substitute the workspace ID, expose a client secret, or return a Hydra client ID as a human ID. Preserve the documented honest fallback for an unbound key: no fabricated owner identity merely because an earliest-admin email is available.
- Authorize before returning identity; unauthenticated/forbidden behavior stays 401/403. Lookup miss/unbound-key fallback must not become an identity-enumeration route. No new endpoint, arbitrary subject parameter or GraphQL/MCP identity tool is needed.
