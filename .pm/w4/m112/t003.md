## Objective

With the stall reason available on UI-read APIs (t002), render it on the deploy detail page's In Progress state — naming the failing probe path and observed result — so a health-gated stall stops looking identical to a slow image pull.

## Context

### The observation (production, 2026-09-17)

Deploy `dep-dam2bvjs0ils73bgove0`'s detail page showed `Deploy status: In Progress`, a one-entry timeline ("Deploy created"), and a log stream whose last line was `Example app listening on port 3000!` — for the full stall window. No element on the page mentioned health checks, probes, or waiting-for-ready; the events tab's rows were equally bare. A user cannot distinguish this from a slow pull or a wedged builder.

### Fix shape

- On the deploy detail's In Progress state only, render the t002 reason as a status-adjacent line (same visual family as the existing `failureReason`/`cancelReason` terminal lines, not a toast): probe type + path + observed outcome, both locales.
- Pre-settle state: before the reason arrives (~2 min), the page renders exactly as today — no skeleton, no placeholder copy.
- The line clears the moment the deploy leaves In Progress (live / failed / canceled); the terminal states keep their existing copy untouched.
- Respect the dashboard skeleton rule for any loading state touched (AGENTS.md): pending geometry must match the ready state at desktop and narrow-mobile widths.

### Acceptance

- The milestone DoD's "stall names the probe" bullet passes live in `en` + `zh`, desktop and narrow-mobile.
- No other deploy state gains, loses, or rewords any line (snapshot the terminal states before/after).
