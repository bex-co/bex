# 536 — A staged env-group link or unlink on an Auto-Deploy-off service never sets `undeployedChanges`: the group reads linked or unlinked, the header says nothing is pending, and the service keeps running the old set

Why: the dashboard and the API both tell the owner the change is done or that nothing is waiting, while the running service has the opposite configuration until a deploy the owner was never prompted to start.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 3, 2026-11-10 08:08–08:27 UTC (`muse.env`, workspace `bex-canary`, pin `4630a48a765e`). **Major**: the product misleads about what is running. ~60m.
- **Fixtures** (created in the dashboard and deleted; by-id GET 404):
  - Free web service `qa-20261110-env` (`srv-dbpd242j0hgs73eavmsg`; Public Git URL `https://github.com/bex-co/bex`, root `examples/hello-go`, Docker, Auto-Deploy off, env `MESSAGE=svc-v1`). `hello-go` serves `$MESSAGE`, or `OK` when it is unset.
  - Env group `qa-20261110-grp` (`evg-dbpd2c20mi5c73c5phag`; `MESSAGE=grp-v1`, `GROUP_ONLY=grp-only`).
- **Controls that passed:**
  - Linking marked `MESSAGE` "(Overridden by this service's own MESSAGE environment variable)".
  - Save only, deleting the service's `MESSAGE`, set `undeployedChanges` true (reason `saved`) and showed the banner "Saved changes aren't live yet. Use a standard deploy to apply them." The URL kept serving `svc-v1`.
  - The next deploy served `grp-v1`, so the link applied at deploy time.
  - The unlink toast stated w4/390's rule.
  - The deploy after the unlink served `OK`.
- **Probes:** GraphQL `query{server(id:"srv-dbpd242j0hgs73eavmsg"){undeployedChanges undeployedChangesApplying undeployedChangesReason}}`, REST `GET /v1/services/{id}` (`undeployedChanges`), `GET /v1/env-groups/evg-dbpd2c20mi5c73c5phag` (`serviceLinks`), and `curl https://qa-20261110-env.onbex.co/`.

    - The group's `serviceLinks` is `[]`, and the service's Environment tab reads "Linked (0)".
    - `undeployedChanges` is false with reason `""`, and the header shows no banner (`.playwright-mcp/qa-env-1.png`, Revision `rev-2`).
    - `curl` kept answering `grp-v1`, the unlinked group's value, at 08:17:48, 08:18:14, 08:18:39, 08:19:05 and 08:19:30.
    - `POST /v1/services/{id}/deploys {}` (`dep-dbpd7ia0mi5c73c5phn0`) then served `OK` at 08:22:15.
  - **Link** at 08:23, from a fresh page load, after `dep-dbpd7ia0mi5c73c5phn0` went live at 08:23:24.
    - `serviceLinks` is `[{id: srv-dbpd242j0hgs73eavmsg, name: qa-20261110-env, type: web}]`.
    - `undeployedChanges` is false with reason `""` from 08:23:24 on.
    - `curl` answered `OK` at 08:24:03, 08:24:23, 08:24:44 and 08:25:04, so the link is not live.
    - An earlier link, at 08:11, likewise read `undeployedChanges` false before the next deploy.
- **Root cause:**
  - A gated link or unlink is staged only in the `app.bex.co/pending-env-group-links` annotation:
    - `lego/backend/internal/rollout/grouplinks.go:106` (`StageGroupLink`; sole caller `lego/backend/internal/envgroups/service.go:1174`) writes it.
    - The next release folds it in (`FoldStagedGroupLinks`, `:122`).
    - Readers see `EffectiveGroupSecrets` (`:114`). See ADR013 § Precedence and redeploy, and w4/m239.
  - `undeployedChanges` is the operator's `Status.UndeployedChanges` (`lego/backend/internal/apps/service.go:1137`). It is written only by `reconcileSavedConfigurationStatus` (`lego/operator/internal/controller/saved_configuration.go:90-103`), from `servingConfigurationDiffers` (`:187`).
  - That comparison checks the served release's record against the saved spec and never reads `AnnotationPendingGroupLinks`. There are zero references to it in `lego/operator`.
  - `savedConfigurationPredicate` (`:53-71`) does not requeue on that annotation either.
  - Static sites return before any comparison (`:87`), so a staged link on a static site (w4/m239's own fixture type) is just as invisible.
- **Fix (target behavior):**
  - While `AnnotationPendingGroupLinks` holds a non-empty settled delta, the service reports `undeployedChanges` true with reason `saved` on REST, GraphQL and MCP. The single source is the operator status.
  - The existing header banner "Saved changes aren't live yet. Use a standard deploy to apply them." then shows (`dashboard/src/features/services/components/service-detail-header.tsx:306`).
  - The flag clears when the next release folds the links, which deletes the annotation.
  - Add `AnnotationPendingGroupLinks` to `savedConfigurationPredicate`'s key list.
  - Decide and record the static-site case, which the controller skips today. The parity-sufficient choice is the same flag, derived from the annotation alone.
- **Blast radius:**
  - `Status.UndeployedChanges` consumers:
    - `apps/service.go:1137-1138` (`AppView`), `render.go:436` (REST) and `graphql.go:357`;
    - `savedChangePending` (`saved_configuration.go:180`, used by `servingConfigurationDiffers`);
    - dashboard `features/services/lib/status.ts:53-61`, `undeployedChangesHintKey` (`status.ts:368-385`) and `service-detail-header.tsx:306`.
  - Link, unlink and group delete all reach `StageGroupLink`; ADR013 says a delete is staged the same way.
  - Regression tests:
    - a value-only Save only still sets the flag;
    - a link on an Auto-Deploy-on service still opens a deploy and never sets the flag;
    - a rollback does not fold staged links (ADR013), so the flag stays set across it.
- **Unverified:**
  - Deleting a group while it is linked to a gated service.
  - A value-only edit of a linked group on a gated service. ADR013 says it also waits for the next deploy; whether that reaches `undeployedChanges` was not probed.
  - MCP output, reasoned from the shared `AppView` rather than probed.
- **Dedupe:**
  - w4/m239 (done) built the staging and verified that the served value waits. It did not cover the pending signal.
  - w4/390 (done) fixed the link and unlink copy, which is only a transient toast.
  - w4/322, w4/480 and w6/067 are about the precedence display.
  - No open item ties `AnnotationPendingGroupLinks` or `pending-env-group-links` to `undeployedChanges`.
  - Neither `saved_configuration.go` nor `rollout/` changed between `4630a48a765e` and HEAD, so this is not deploy lag.
- **Render:** an env-group change deploys only the services with Auto-Deploy on (ADR013 quotes Render). `undeployedChanges` is a bex extension, so the defect is bex's own pending signal disagreeing with the running service.
- **DoD** (live): use a Free `hello-go` web service with Auto-Deploy off and no `MESSAGE`.

  2. Deploy. `curl` answers `g`, and the flag clears.
  3. Unlink. The flag is true and the banner shows, while `curl` still answers `g`.
  4. Deploy. `curl` answers `OK`, and the flag clears.
  5. Delete the fixtures.
