# 666 — Canceling a deploy queued behind a Rollback, Restart or image override in progress also ends that release

Why: a cancel ends one deploy. Since w4/661 a git push, a configuration change, a Blueprint sync or a build-source fan-out waits behind a selected release in progress (Render's Wait). Canceling the queued deploy should leave the release ahead to finish, as w8/m117 does for a source build or a saved image.

- **Source / severity / estimate:** `/loopx w4` closeout of w4/661 (2026-11-14), recorded open in ADR018's List / get deploy objects row. **Minor** (the service settles back on the release that served before the Rollback). ~2h.
- **Gap, from the code:**
  - `cancelSurvivor` (`lego/backend/internal/deploys/service.go`) names no survivor when the deploy ahead selects an image of its own (`selectsImage(o)`), so `CancelUnservedRelease` stamps the cancel with no `AnnotationSurvivingReleaseGeneration`.
  - The operator's canceled branch (`prepareAppReleaseDecision`, `latestRequestCanceled`) then settles on the last served release and abandons the Rollback in flight.
  - Naming it is not enough on its own: `survivorInFlight` reads a saved-image survivor as one to roll again on the saved spec (`redispatchSurvivor`), which for a selection the operator has not adopted would run the saved image under the Rollback's generation. A selected survivor must pin on its adopted view only (`selectedRelease`), and must not rewrite `spec.buildCommit`.
- **Tests:** canceling a push queued behind a Rollback rolling out leaves the Rollback to go `live` and the push `canceled`; canceling the Rollback itself still settles on the prior release; a selection not yet adopted still ends with the cancel.
- **DoD (live):** on a Free repo-backed service, roll back, push a commit while the rollback reads `update_in_progress`, then cancel the push's queued deploy: the rollback goes `live`. Delete the fixture.
