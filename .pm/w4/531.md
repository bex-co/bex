# 531 — Regression of w4/414's control: rolling an image service back to the deploy of its saved tag still says "Saved changes aren't live yet. Use a standard deploy to apply them."

Why: when the running release is exactly what the service's saved settings describe, nothing is pending. w4/414 recorded that a Rollback to the deploy of the saved image clears the notice, "because the saved and running images match again". Live, the notice stays after that rollback. It tells the user to redeploy for a change that does not exist, and `undeployedChanges` stays `true` on REST and GraphQL.

- **Root cause:**
  - `lego/operator/internal/controller/saved_configuration.go:206-223`, `servesSavedImage`: a served digest counts as the saved image only if `served == spec.Image`, or a serving or candidate network records `Source == spec.Image`.
  - A rollback deploys the target's recorded digest. `resolveDeployImage` hands `resolveImageNetwork` that digest (`app_controller.go:700-708`), and `resolveImageNetwork` records it as its own source (`image_network.go:179`, `source := image`; stored at `:241`). So `Source` is `whoami@sha256:6956…`, never the tag `whoami:v1.10.1`, and the check fails.
  - `servingConfigurationDiffers` (`:177-183`) then sets `different = true`. `undeployedChangesReason` (`:233-246`) labels it `historical_release` because the rollback's `ReleaseConfigReference` carries `SourceGeneration = target.Generation` (`lego/backend/internal/deploys/rollback_config.go:65`).
  - The dashboard shows the standard hint for that reason (`dashboard/src/features/services/lib/status.ts:363-381`).
  - Likely regressed when w4/m243 moved image-port services to digests. t014 added `servesSavedImage` for the tag-resolved case, but only for networks resolved from the tag itself.
- **Fix — target behavior:**
  - A rollback whose target deploy was resolved from the currently saved image reference, and which serves that deploy's digest, is not an undeployed change: `undeployedChanges: false`, reason `""`, and no notice, the same as after the original deploy.
  - A rollback to a deploy built from a different reference (an override such as `v1.10.2`, or an older saved tag) keeps `true` / `historical_release` and the standard hint.
  - Mechanism, either works:
    - carry the target deploy's original image reference (the tag it resolved from) into the rollback's release config, and record it as the network `Source`;
    - or let `servesSavedImage` accept a digest whose recorded release (via `SourceGeneration`) resolved it from `spec.Image`.
  - A tag the registry has since re-pointed still counts as saved, as `servesSavedImage`'s comment says (Render re-pulls a tag on each deploy).
