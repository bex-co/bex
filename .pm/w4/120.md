# `disconnectBlueprint` is a soft-detach, and re-creating the same repo+path revives the old row with its history

Why: `createBlueprint` on a repo+path that was previously connected does not create anything — it resurrects the disconnected row, so the "new" blueprint arrives carrying someone else's sync history and a `createdAt` from before it existed, which the dashboard renders as a plain lie ("Created 1d" on a blueprint that is seconds old).

Found by live `/qa-find-bugs` 2026-09-21 pass 132 (w4-targeted, `muse.env` credentials), as a side effect of the blueprint journeys in `w4/119`. Fixtures deleted.

## Evidence

Across passes 128, 131 and 132 I ran `createBlueprint` → `disconnectBlueprint` three times for the same repo and path (`https://github.com/bex-co/bex`, `examples/static-site/render.yaml`). Every create returned **the same id**, `blp-dan9g8rs0ils73bgp500`, even though each was preceded by a `disconnectBlueprint` that returned `true` and removed it from `blueprints(ownerId:)`.

Reading the third one, seconds after creating it:

```graphql
blueprint(id:"blp-dan9g8rs0ils73bgp500") {
  name       → "qa-20260921-bp3"          # the name I just passed — so it is a NEW connection
  createdAt  → "2026-09-19T14:11:47Z"     # two days earlier, and before this QA loop began
  lastSync   → "2026-09-21T11:50:14Z"
}
blueprintSyncs(id:…) → 9 entries
```

The dashboard renders that as **Created 1d**, and its Sync History shows nine syncs — including ones from earlier connections, with their commit sha and error text.

The `createdAt` predates this QA loop entirely, so the row was first created by someone else's connection on 2026-09-19 and has been revived by every subsequent create since.

## Why it matters

- **`createdAt` is wrong on its face.** A resource created seconds ago reports an age of two days, on both the API and the dashboard. Any "created" column, sort, or retention rule reading it is wrong.
- **History crosses a disconnect boundary.** Whoever reconnects a repo+path inherits the previous connection's sync history: commits, timestamps, and full error strings. Within one workspace that is a confidentiality non-event, but it is still one user's operational record showing up under another's newly-named blueprint.
- **The verb is misleading in both directions.** `disconnectBlueprint` reads as "remove this connection" and does hide it from the list; `createBlueprint` reads as "make a new one" and does not. Neither name suggests a soft-delete/revive pair.

## The decision this needs

Reviving is a defensible design — reconnecting a repo and keeping its history is arguably a feature, and it makes `createBlueprint` idempotent for the same repo+path, which is useful for automation. If that is the intent, then:

- `createdAt` should be the **connection's** creation time, not the row's, or the field should be renamed so it is clearly the row's; and
- the dashboard should say the blueprint was reconnected, rather than presenting inherited history as its own.

If reviving is **not** intended, `disconnectBlueprint` should delete the row (or tombstone it so a later create starts clean).

Either way the current state is the one combination that cannot be right: a new connection reporting an old creation time with no indication that anything was inherited.

Estimate: ~30m for the `createdAt` semantics plus a test that create-after-disconnect reports the new connection's time; longer if the product decides disconnect should hard-delete, since that needs a call on the retained sync history.

## Unverified

- Whether the revived row also carries other prior-connection state (`autoSync`, `path` when the new create passes a different one) was not probed — only `name` was observed to update.
- Whether a **different workspace** connecting the same repo+path gets its own row was not tested, and matters: if row identity is keyed on repo+path alone rather than per workspace, the history carry-over would cross a tenant boundary, which is a much more serious defect than the one described here. That test needs a second workspace.
