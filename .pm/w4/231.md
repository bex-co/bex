# Created environment stays absent after the create refresh finishes

Why: a successful environment creation should make that environment selectable immediately after its refresh settles, so a user can continue configuring it without waiting for another poll or creating a duplicate.

**Severity:** minor. The environment is stored correctly; the ready UI temporarily omits it. A later poll repaired the display. No data loss, persistent absence or running-service failure was observed. **Estimate:** 55m (bounded creation refresh 20m, real Apollo regression/control checks 25m, live replay and closeout 10m). Inbox sizing; filing only.

Source: continuous `$qa-find-bugs w4`, 2026-10-10 UTC pass a42, credentials consumed privately from muse.env, workspace bex (`tea-d98210cbbpdc73dcrkvg`). Research main `6ddecc3f53e738401c5f5f2ba215bb3051341409`. Only an owned empty project and its four empty environments were changed.

## Reproduction and target

1. Create an owned project, then fresh-load its Overview. Open **New Environment** as soon as available, enter a fresh qa-prefixed name at ordinary typing speed, and submit while the page's initial Environments read is still pending. Do not intercept, slow or reorder production requests.
2. Wait for the mutation and create dialog to finish. Open **Selected environment**. The successfully created environment is absent from the ready selector. On an initially empty project, the page can still say **No environments yet**.
3. Repeat from a fresh page using another name. Record the earlier list request and its later response; a run without overlap is a control, not a reproduction.
4. Let the next poll settle, or reload: the environment appears. On an already settled page, ordinary creation starts a genuinely post-save Environments request, and the new environment is selectable when the dialog closes.

**Target:** after a committed creation and its refresh settle, the selector and ready environment list include the created immutable ID according to a fresh authoritative list. Keep the previous content and busy dialog while that refresh is pending. Preserve the selected environment and URL policy; do not force a new selection or append an invented local row over a later authoritative result.

## Root cause, consumer and bounded fix

- `dashboard/src/features/environments/hooks/use-create-environment.ts:26-39` uses `refetchQueries: ["Environments"]` with `awaitRefetchQueries: true`, then announces success. Waiting for that refetch does not prove its read began after the write.
- `dashboard/src/features/environments/components/new-environment-dialog.tsx:57-62` closes on the returned ID. `environments-panel.tsx:103`, :182-195 and :266-270 derive the selectable options/empty state from `useEnvironments`. That hook maps only `data.environments` at `use-environments.ts:127-136`; it cannot discover the new entity from the mutation alone. Its 30s polling (:123 and `common/lib/polling.ts:11`) later repairs the list.
- Apollo **4.1.3**, confirmed in yarn.lock:73-74, installed package metadata and actual request extensions: `core/QueryInfo.js:335-352` collects named refetch results and awaits them; `core/QueryManager.js:903-921` invokes ObservableQuery.refetch; `core/ObservableQuery.js:366-396` forces network-only but retains the query context. `QueryManager.js:512-576` deduplicates by printed query and variables and reuses an existing in-flight observable. `awaitRefetchQueries` can therefore complete with the pre-save list. This is application ordering, not a claimed Apollo defect.
- Mutation data normalizes an Environment entity by typename/id (`cache/inmemory/helpers.js:4-24`). `dashboard/src/common/apollo/cache.ts:6-13` has no Environment or environments-list policy that adds its ID to the project list. The generated `EnvironmentsQuery` type (`graphql/definitions.ts:723`) and existing `EnvironmentsDocument` (:2237) already express the required full list; no schema change is needed.
- Backend GraphQL `internal/environments/graphql.go:58-71` reads `Service.List`; `service.go:438-464` obtains the project rows before assembling memberships. Creation returns the newly stored environment through :558-606. The old response's two-item list is consistent with its earlier request, not evidence that the mutation failed. `internal/api/server.go:1491-1502` executes a batch's operations serially and writes the complete batch afterward; a response arriving late is not proof that its Environment read occurred late. Its individual resolver timing was not measured.

After the single successful mutation, settle older Environments reads that could still publish a pre-save list, then issue an explicit project-scoped network-only `EnvironmentsDocument` read with `context: {queryDeduplication:false}` before completing creation refresh. Use the real typed document so its cache publication reaches the existing consumers. `features/projects/hooks/use-rename-project.ts:39-48` is an existing ordering pattern from w4/m186: settle individual refetch results, then perform a fresh non-deduplicated read. Adapt it to this list rather than modifying the global Apollo client or shared fetch policy. A non-deduplicated fresh read started alongside an older read is insufficient if the older response can overwrite it afterward.

Separate write success from refresh failure: never retry create or report that the environment was not created merely because a post-success refresh failed. A retry must re-read only. Mutation rejection/missing-ID remains a creation error. Preserve existing unauthenticated/forbidden/not-found handling; refresh rejection/timeout retains existing rows and identifies the refresh as incomplete. These failure classes were not induced live.
