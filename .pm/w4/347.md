# "Save, rebuild, and deploy" of environment changes is recorded as a Manual Deploy, not a configuration change

Why: the same environment save is attributed differently depending on whether the member also asked for a rebuild. A team member reading Deploys or Activity sees "Manual Deploy" with `envUpdated:false` for what was an env-var, secret-file or env-group edit. That contradicts w6/m51's rule that configuration writes which force a rollout are `config_change` deploys.

- **Severity:** minor (deploy-cause attribution; the deploys themselves are correct). **Estimate:** 45m.
- **Source:** live functional `/qa-find-bugs w4`, pass d2b8f4, 2026-10-19 UTC, `muse.env`, workspace `bex-canary`. Production was pinned to `5e75de920`; research is on main `238e7e7bf`. The fixture (`qa-20261019-d2b8f4-buildenv`, `srv-dban7ei472qs73cq7p00`) and group (`qa-20261019-d2b8f4-grp`, `evg-dban8d023mpc73e3rq20`) were deleted (204 → 404).
- **Repro:** a Free Git service from `https://github.com/bex-co/bex`, root `examples/docker-build-env`, runtime Docker, with its own `GREETING` and `.env` secret file. Then:

| Action (dashboard) | Deploy | REST `trigger` | Deploys list | `deploy_started.details.trigger` |
| --- | --- | --- | --- | --- |
| Create (first deploy) | `dep-dban7ei472qs73cq7p0g` | `other` | First Deploy | `firstBuild:true` |
| Create group with the service linked | `dep-dban8d023mpc73e3rq2g` | `service_updated` | Config Change | `envUpdated:true, manual:false` |
| Service Environment: delete own var + file → **Save, rebuild, and deploy** | `dep-dban91g23mpc73e3rq40` | `api` | **Manual Deploy** | `envUpdated:false, manual:true` |
| Group: change `GREETING` → **Save, rebuild, and deploy** | `dep-dban9oo23mpc73e3rq60` | `api` | **Manual Deploy** | `envUpdated:false, manual:true` |

The control is pass 7d3e19's service "Save and deploy" (`dep-dbalpkuhvrac73cbss70`), recorded as `service_updated`.

- **Root cause:**
  - **Service path:** `dashboard/src/features/services/components/service-environment-editor.tsx:152-171` implements "rebuild" as a `save_only` patch followed by the client's generic `trigger(serviceId)` (the Manual Deploy "Deploy latest commit" mutation).
  - **Group path:** `envgroups/patch.go:332-338` calls `RebuildService`, wired at `lego/backend/internal/api/server.go:881-884` to `deploysSvc.Trigger(ctx, serviceID, deploys.TriggerParams{})`.
  - Both open a `store.TriggerAPI` deploy. `events/service.go:913-917` maps that to `Manual: true`, and `EnvUpdated` only for `TriggerConfigChange`. That comment is the w6/m51 rule: "Manual stays false: nobody clicked Deploy."
- **Fix (target behavior):** a deploy opened because an environment save asked to rebuild carries the configuration-change cause on every surface: bex trigger `config_change`, REST `service_updated`, `envUpdated:true`, `manual:false`, and the dashboard's "Config Change" label. It must still do a full rebuild from the latest commit.
  - Add an explicit cause to `deploys.TriggerParams` (for example `Trigger: store.TriggerConfigChange` with a rebuild), used by both the group `RebuildService` binding and a server-side service-environment rebuild. Prefer giving `PatchEnvironment` a `rebuild` save mode, as env groups already have, over the client's save-then-trigger.
  - Keep the composed save + rebuild atomic from the user's view (one deploy, the retry semantics of w5/m44).
- **Blast radius:**
  - `deploysSvc.Trigger` has 1 internal caller (`api/server.go:882`) plus the public Manual Deploy surfaces (GraphQL `triggerDeploy`, REST `POST /v1/services/{id}/deploys`, MCP), which must stay `api`/manual.
  - Dashboard callers of the shared `trigger`: the service editor's rebuild and its `retryRollout` (`:173`).
  - Consumers of the trigger: Deploys list labels, Activity, REST/GraphQL/MCP events and deploy reads, and `TestRenderConformance` (which seeds every `store.AllTriggers` value).
- **Adjacent classes:**
  - A genuine Manual Deploy (including "Clear build cache & deploy") stays `api`/manual.
  - Deploy hooks, rollbacks and restarts are unchanged.
  - A rebuild retry after a failed trigger keeps the config-change cause.
- **Unverified:**
  - Render's own label for a "Save, rebuild, and deploy" was not observed; Render's event `trigger.envUpdated` is the field this maps to.
  - MCP was not probed.
- **Also verified clean (record):** `w1/m178` Dockerfile build inputs follow env-group precedence live.
  - Service-owned `GREETING`/`.env` baked `svc-d2b8f4-1`/`19` bytes, and stayed after the group link rebuilt.
  - Deleting the service's own values and rebuilding baked the group's `grp-d2b8f4-1`/`13`.
  - A group "Save, rebuild, and deploy" baked `grp-d2b8f4-2`.
  - The menu-path saves do toast (about 1.35 s after the click, so sample later than 1.2 s).
- **Dedupe:**
  - `w4/216` (no-op saves claiming a deploy), `w5/m44` (editor parity) and `w6/m108` (group rollout failure) are other behaviors.
  - ADR018:137 documents `config_change` for configuration writes but not the rebuild path.
  - No item mentions rebuild attribution.
- **Acceptance:**
  - Backend tests: a group rebuild records `config_change`/`envUpdated` and a manual `triggerDeploy` stays `api`.
  - A dashboard test of the editor's rebuild path, failing on current code.
  - Live, both rebuild saves show "Config Change" in Deploys and `envUpdated:true` in events, and a Manual Deploy still shows "Manual Deploy".
