## Objective

`http_requests` is built as `sum(rate(...))` on both of its sources, so every surface that calls it (REST, GraphQL, MCP, dashboard) receives **requests per second** while the response declares `unit: "count"` and the MCP tool is literally named `http_request_count`. Make the metric return the number of requests in each bucket, so the declared unit is true and a caller can sum the series to get the requests in the window.

## Context

Live probe, 2026-09-16 (production, `srv-dal3f2rkmutc73d7q9l0`, a free web service). 12 `curl` requests were sent at `06:38:25Z`; the access log shows them. The GraphQL read over the hour containing them:

```graphql
query M($query: MetricsQueryInput!) {
  metrics(query: $query) {
    labels {
      field
      value
    }
    unit
    values {
      time
      value
    }
  }
}
# variables: {"query":{"filters":[{"field":"RESOURCE","values":["srv-dal3f2rkmutc73d7q9l0"]}],
#             "name":"HTTP_REQUESTS","start":"2026-09-16T05:42Z","end":"2026-09-16T06:42Z"}}
```

```json
{
  "data": {
    "metrics": [
      {
        "labels": [{ "field": "resource", "value": "srv-dal3f2rkmutc73d7q9l0" }],
        "unit": "count",
        "values": [
          { "time": "2026-09-16T06:37:36Z", "value": 0 },
          { "time": "2026-09-16T06:38:36Z", "value": 0.17777777777777776 },
          { "time": "2026-09-16T06:39:36Z", "value": 0 }
        ]
      }
    ]
  }
}
```

`0.1777… = 8/45` — a rate, not the ~12 requests that happened. The control, a service sustaining real traffic (`srv-d9bj8s3eg85c7390eb9g`), returns values around `7.0` for every bucket: ≈7 req/s, which the UI then sums into "727 requests" for a 12h window in which ≈300k requests were actually served.

Both builders produce a rate:

- `lego/backend/internal/metrics/source.go:407` — `promQueryFor`'s default branch, `sumRate("traefik_service_requests_total", matchers, window, groupLabel(req.GroupBy))` → `sum(rate(...[Ns]))` (`sumRate` at `source.go:409-414`).
- `lego/backend/internal/metrics/lokisource.go:114-119` — `lokiRequestQueryFor`'s `MetricHTTPRequests` branch, `rate(<selector><pipeline> [Ns])` wrapped in `sum` / `sum by (…)`. This is the branch a host/path/status-filtered read takes (`w5/m58`).
- `lego/backend/internal/metrics/service.go:1036-1044` — `requestUnit` returns `unitCount` for `http_requests`, so the wire contract already claims a count.

The correct primitive is already in the tree and already used for money: `lego/backend/internal/egressquery/query.go:143-145` `Increase` (`sum(increase(counter[Ns]))`) backs the usage/metering read at `lego/backend/internal/usage/service.go:1229` and the metrics page's own month-to-date bandwidth figure at `lego/backend/internal/metrics/source.go:502`.

`http_latency` is **not** affected: it is `histogram_quantile(...)` / `quantile_over_time(...)` in seconds, correct as-is. Bandwidth is the same `rate` shape but is handled separately in `t003` because its live numbers did not reconcile cleanly. Gauges (`cpu`, `memory`, `instance_count`, the `*_limit`/`*_target` metrics) are unaffected.

## Steps

1. Change the Prometheus builder's `http_requests` branch to an increase over the step: `sum(increase(traefik_service_requests_total{…}[Ns]))`, keeping the `by (<groupLabel>)` grouping and the `code=~` status matcher exactly as they are.
2. Change the Loki builder's `MetricHTTPRequests` branch from `rate(...)` to `count_over_time(...)` over the same `[Ns]` window, keeping `lokiRequestPipeline` and the `sum by (status|method)` grouping.
3. Check the step used in the query is the same step the series is sampled at — an `increase`/`count_over_time` window narrower or wider than the sampling step double-counts or drops requests at the seams. `stepSeconds(req.Resolution)` already supplies both; assert they cannot drift.
4. Decide and record what a partial leading bucket returns (a window that starts mid-bucket). Prometheus `increase()` extrapolates; say in the code comment whether that is accepted or clamped, so a future reader does not "fix" a fractional count back into a rate.
5. Leave `requestUnit`'s `unitCount` as-is — after this change it is finally accurate. Add a comment at `source.go`'s `sumRate` naming which metrics may use it (none, once `http_requests` moves off, unless `t003` keeps bandwidth there) so the next metric does not pick the rate builder by copy-paste.

## Acceptance criteria

- [ ] Send exactly 20 `curl` requests to a test service, wait one scrape, read `HTTP_REQUESTS` over a window containing them: `Σ values ≈ 20`, not `20/step`.
- [ ] The status-filtered and host-filtered reads (the Loki branch) return the same total as the unfiltered read when the filter matches every request.
- [ ] `group by status` and `group by method` still return one series per group, and the groups sum to the ungrouped total.
- [ ] REST `GET /v1/metrics/http-requests`, GraphQL `metrics(name: HTTP_REQUESTS)` and MCP `http_request_count` return identical values for an identical window.
- [ ] `http_latency` values are byte-for-byte unchanged for the same window (the quantile path must not be disturbed).
