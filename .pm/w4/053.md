# Metrics GraphQL query returns "internal error" for invalid input (bad metric name, missing RESOURCE filter, inverted time range) instead of a bad-request validation error

Why: the metrics input parser returns bare `fmt.Errorf` errors that the GraphQL sanitizer replaces with the opaque "internal error", so a client sending a bad metric name / no resource / an inverted range gets no actionable message and a misleading 5xx-class error — inconsistent with the same endpoint's other validations, which correctly use `core.ErrBadRequest`.

Source: live QA 2026-09-07, `$qa-find-bugs w4` (error-taxonomy probing, sibling of `w4/052`).

## Symptom (reproduced on prod, deterministic)

Authenticated GraphQL `metrics(query: MetricsQueryInput!)` on `srv-da40m1qii7bs73drbqlg`:

| input | result |
| --- | --- |
| `name:"MEMORY"` (valid — control) | ✅ 1 series |
| `name:"FOO_METRIC"` (unknown metric) | ❌ `errors:["internal error"]` |
| inverted range (`start` > `end`, valid MEMORY) | ❌ `errors:["internal error"]` |
| `filters:[]` (no RESOURCE, valid MEMORY) | ❌ `errors:["internal error"]` |
| `resolution:-5` / `resolution:0` | ✅ 1 series (silently clamped — acceptable) |

Durable probe (in-page `fetch(..., {credentials:'include'})`): body `{"operationName":"Metrics","query":"query Metrics($query: MetricsQueryInput!){ metrics(query:$query){ unit values{time value} } }","variables":{"query":{"filters":[{"field":"RESOURCE","values":["srv-da40m1qii7bs73drbqlg"]}],"name":"FOO_METRIC","start":"2026-09-07T00:00:00Z","end":"2026-09-07T06:00:00Z","resolution":300}}}` → HTTP 200, `{"errors":[{"message":"internal error"}],"data":null}`.

## Root cause (code-verified on `main`)

`metricsQueryInputFromArgs` (`lego/backend/internal/metrics/graphql.go:369-410`) returns **bare** errors for invalid input:

- `:373` `fmt.Errorf("query is required")`
- `:379` `fmt.Errorf("unknown metrics name %q", name)` ← unknown metric name
- `:391` `fmt.Errorf("filters must include a RESOURCE entry")` ← empty/missing resource

None is wrapped in `core.ErrBadRequest`. The inverted-range case is unguarded: `windowFromInput` (`graphql.go`) parses `start`/`end` but does **not** check `start < end`, so an inverted range flows downstream to `promQueryRange` (`source.go:169`) → Prometheus errors → also bare. The sibling `unknown metric` checks at `service.go:409` and `datastore.go:368` are bare too.

`sanitizeGraphQLErrors` (`lego/backend/internal/api/server.go:1328-1337`) then replaces any resolver error that is **not** `core.IsPublicError` with the literal `"internal error"` (logging the real cause). A bare `fmt.Errorf` is not public → becomes `"internal error"`.

**Control case (load-bearing):** the *same* metrics service wraps its other validations in `core.ErrBadRequest` — `service.go:346` (fan-out), `:360` (points-per-series), `:380` (statusCode format), `:389` (host/path applicability), `:445` (quantile count), `:964`/`:969` (outputFilters). Those surface to the client **with their message** (verified path: `IsPublicError(ErrBadRequest)` is true → `sanitizeGraphQLErrors` keeps the message). So the input-parser errors are an inconsistent omission, not a design choice.

## Target behavior

Invalid metrics query input (unknown `name`, missing RESOURCE filter, `start >= end`, malformed `query`) must return a **client-facing bad-request error carrying its descriptive message** (e.g. `unknown metrics name "FOO_METRIC"`), exactly like the endpoint's existing `core.ErrBadRequest` validations — never the opaque `"internal error"`. A genuine upstream failure (Prometheus/Loki down) must **still** be `"internal error"` (redacted).

**Fix:** wrap the input-validation errors in `core.ErrBadRequest`: `graphql.go:373,379,391`, add a `start < end` guard in `windowFromInput` (or the service) wrapped in `ErrBadRequest`, and `service.go:409` + `datastore.go:368` (`unknown metric`). Verified correct via `sanitizeGraphQLErrors`' `IsPublicError` branch — wrapping makes the message survive.

## Blast radius

- Primary: the `metrics` GraphQL query (`graphql.go:279`) — reached by the dashboard Metrics page and the Scaling "Recent Metrics" panel; input parsed by `metricsQueryInputFromArgs` (the confirmed site).
- Sibling: `datastoreMetrics` query (`graphql.go:315` → `datastoreMetricsQueryInputFromArgs` :436; unknown-metric at `datastore.go:368`) — Postgres/Key Value metrics; same class, **not live-probed** (code-traced).
- `service.go:409` unknown-metric is shared by the ranged path.
- REST/MCP metrics surfaces (if any) that reuse the same service/parse errors — **not probed** this run; apply the same wrapping.

## Adjacent classes

- valid input → data (unchanged).
- invalid input (bad name / no resource / inverted range / malformed) → **bad-request with message** (the fix; currently "internal error").
- real Prometheus/Loki/upstream failure → **"internal error"** (must stay redacted).
- out-of-range-but-clampable resolution (`-5`, `0`) → currently silently clamped to a default → **ok** (acceptable; not part of this fix).

## Render parity

Render returns a validation error (not a 5xx/opaque error) for an unknown metric name or malformed metrics query. bex diverges on these input-parse paths. Parity applies across GraphQL + any REST/MCP metrics surface.

## Severity

**Minor** — no data loss, no blocked journey (the dashboard always sends valid input). It's an error-taxonomy/DX defect: API/MCP clients get an opaque "internal error" with no actionable message for their own bad input, and it pollutes server error logs (`bex-api graphql: internal error: …`) with client-caused entries.

## Unverified this run

- Only the **GraphQL `metrics`** query was probed live (unknown name / inverted range / empty filters). `datastoreMetrics` (Postgres/KV), and any REST/MCP metrics surface, are code-traced to the same bare-error/unknown-metric sites but not live-probed.
- The inverted-range downstream error origin (Prometheus vs an earlier guard) was inferred from `windowFromInput` lacking a `start<end` check + the observed "internal error", not stepped through.
