# A sandbox terminal processes typed-ahead input at once, so Ctrl-C interrupts a program that is not reading it

Why: in a bex sandbox, typing a line ahead while a program runs (`ls`, Enter) and then pressing Ctrl-C does not interrupt the program, and nothing typed after that line is echoed, until the program reads its terminal. On Linux, and so in Devin and on a developer machine, both happen at once. Found by w4/m574's line discipline harness, 2026-11-22.

- **Cause.** gVisor's `inputQueueTransformer.transform()` (`pkg/sentry/fsimpl/devpts/line_discipline.go`, master and the fork's `bex/line-discipline` alike) returns at once when canonical mode has a complete line waiting (`if ICANON && q.readable { return 0, false }`). The input queue's read buffer holds a single line, and `queue.read()` returns all of it, so later input waits unprocessed in the wait buffer: no echo, no signal, no flow control, no erase. Linux's `n_tty` keeps processing into one ring buffer, marks each line's end in `read_flags`, and `canon_copy_from_read_buf()` returns one line per read.
- **Repro** (Python, a PTY in cooked mode, no reader): write `ls\n`, then `ab`, then `\x03`. Native Linux echoes `ls\r\n`, `ab`, `^C`, and the replica then reads nothing (the flush discarded both lines). `release-20260622.0-bex.2` echoes `ls\r\n` only, and the replica reads `ls\n`. That is case `c6a` of the w4/m574 harness.
- **The fix.** Let the canonical read buffer hold several lines: record each line's end (an EOF line included), make a canonical read return up to the first line end, report `FIONREAD` as Linux's `inq_canon()` does, keep VERASE, VWERASE, VKILL and VREPRINT within the line being typed, and let the signal flush clear every line. Add `test/syscalls/linux/pty.cc` cases for typeahead echo, Ctrl-C and Ctrl-S after an unread line, two lines read one per `read()`, and an EOF between them. Build it into the next `release-20260622.0-bex.<n>`, and send it upstream with the user's DCO sign-off, as w4/m574 t007.
- **Also left by w4/m574** (ADR104 § Terminals in a sandbox, ADR018's terminal row): erasing a tab from the screen (Linux's `ECHO_OP_ERASE_TAB` moves back to where the tab started; gVisor echoes nothing for it), ECHOPRT's `\…/` echo, and `tcflow()` (`TCXONC`). Fix them in the same release, or keep them in ADR018 for the user's sign-off.

Done when each case above matches native Linux in the fork's syscall tests and on a production sandbox, and ADR104 and ADR018 drop the differences this fixes.
