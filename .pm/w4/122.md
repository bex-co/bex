# GraphQL can create a sandbox in a chosen workspace and then cannot list, read or terminate it there

Why: `createSandbox` takes `ownerId` and every other GraphQL sandbox operation ignores the workspace entirely — so the one surface that lets you place a sandbox is the one that cannot reach it afterwards, while REST binds `?ownerId` on every route and MCP binds `workspaceId` through middleware.

Found by live `/qa-find-bugs` 2026-09-21 pass 135 (w4-targeted, `muse.env` credentials), sweeping the agent-session / sandbox surface, which this loop had never touched. All probes were read-only; nothing was created.

## The asymmetry, per operation

| operation      | REST                                                          | GraphQL                                   | MCP                                       |
| ---------------- | --------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------- |
| create          | `POST /v1/sandboxes` — `?ownerId` or body (`rest.go:52-56`)      | `createSandbox(ownerId:)` ✅                | `spawn_sandbox` `ownerId` + middleware ✅   |
| list            | `GET /v1/sandboxes` — `WithWorkspace(?ownerId)` (`rest.go:73`)   | `sandboxes` — **no argument at all**        | `list_sandboxes` + middleware ✅            |
| read one        | `GET /v1/sandboxes/{id}` — same (`rest.go:88`)                   | **no `sandbox(id:)` field exists**          | — (list covers it)                          |
| terminate       | `POST …/{id}/terminate` — `lifecycleREST` (`rest.go:160-161`)    | `terminateSandbox(id:)` — **no `ownerId`**  | `stop_sandbox` + middleware ✅              |

Live schema introspection confirms the GraphQL column:

```graphql
{ __type(name:"Query"){ fields{ name args{ name } } } }
→ { "name": "sandboxes", "args": [] }          # every other list root takes ownerId
   …and no "sandbox" field anywhere in Query

{ __type(name:"Mutation"){ fields{ name args{ name } } } }
→ createSandbox    args: template, plan, ownerId, region, timeoutSeconds, networkPolicy
   terminateSandbox args: id
```

`{ sandboxes { id status owner workspace } }` answers `[]` without complaint — it is not rejected for a missing argument, it simply answers about whichever workspace the caller resolves to by default.

## Why "no argument" means "wrong workspace", not "all workspaces"

The service layer is correctly scoped — this is not an isolation hole. `Service.List` (`sandbox/service.go:943-983`) authorizes, takes `ws := s.WorkspaceOrDefault(ctx)`, drops anything failing `validOwnedSandbox(r, ws)`, and then returns only the caller's own sandboxes plus, for a workspace admin, other members'. `Get` (`:987-999`) and `Terminate` (`:1014`, through `lifecycle`) scope the same way.

So everything hinges on what `ctx` carries. REST puts it there explicitly — `core.WithWorkspace(r.Context(), r.URL.Query().Get("ownerId"))` at `rest.go:73`, `:88`, and in `lifecycleREST` at `:160-161`. MCP puts it there uniformly in middleware: `api/mcp_workspace.go:83-88` binds each call's `workspaceId` and validates membership, and only the eight caller-scoped tools in `mcpCallerScopedTools` (`:38-47`) opt out — `list_sandboxes` and `stop_sandbox` are not among them.

GraphQL's `sandboxes` and `terminateSandbox` resolvers (`sandbox/graphql.go:62-67`, `:96-106`) call straight through with `p.Context` and never set it. `WorkspaceOrDefault` then falls back to `Tenant(ctx)` → `resolveWorkspaceUncached` → the identity's own default workspace (`core/base.go:651-656, 968-973`). This account reaches three workspaces (`bex`, `tian-personal`, `bex-canary`), so for any caller in more than one, the GraphQL sandbox list is pinned to one of them with no selector.

Note that `createSandbox` already threads `ownerId` into `CreateRequest.OwnerID` — so the mutation half of the surface knows perfectly well that a sandbox belongs to a chosen workspace.

## Fix

- Add `ownerId` to `sandboxes` and `terminateSandbox` and bind it with `core.WithWorkspace` the way REST does, so all three surfaces scope identically (`docs/ADR006-bex-api.md`).
- Add a `sandbox(id:, ownerId:)` query to match `GET /v1/sandboxes/{id}`, which GraphQL has no equivalent of.
- Prefer doing this in the resolvers rather than per-verb, since the pattern already exists elsewhere (`apps.CreateBlueprint` opens with `ctx = core.WithWorkspace(ctx, ownerID)`).

Estimate: ~45m including the by-id query and a test asserting the three surfaces agree for a sandbox in a non-default workspace.

## Also checked this pass, and found correct

The agent-session surface (the populated sibling of sandboxes — 83 real sessions) held up under a deliberate filter/pagination sweep, which is the class the hunt brief calls out as high-yield. Recording it so nobody re-runs it:

- **Every list filter narrows, and an invalid one errors instead of being ignored.** `phases:["completed"]` → 17, `["canceled"]` → 32, `["failed"]` → 22 (= 71 unarchived); `phases:["not-a-phase"]` → `unknown phase filter`; `repo:"bex-co/bex"` → 14, all that repo; a nonexistent repo → an honest empty list; `createdAfter`/`createdBefore` shift the window.
- **`archived` is a validated tri-state, and the arithmetic checks out.** `"false"` → 71, `"true"` → 12, `"all"` → 83; `"only"` and `"banana"` → `archived must be one of false|true|all`; `""` behaves as the default. It is typed `String` rather than `Boolean` because it is three-valued — passing `true` gives a type error, which a client must know, but the values are documented in the error itself.
- **Cursor pagination does not overlap or repeat.** Two `limit:3` pages share no ids and descend by `createdAt`; an unknown cursor yields an empty page rather than an error, which is the documented id-as-cursor style (`core/cursor.go:60-80`), not the keyset style that 400s.
- **Transcript paging is exact and deliberately bounded.** On a 264-part transcript: `afterSeq` is exclusive and contiguous, `nextAfterSeq` is the page's last seq, a huge `afterSeq` returns an empty page echoing the input, a negative one clamps to the head, and `limit:0`/`limit:-3` are refused with `limit must be a positive integer`. The default page of 200 and the cap of 1000 are explicit (`agentsessions/service.go:672-683, 873-874`) alongside a 4 MiB payload bound (`:869`), per ADR065 D2 — **not** an instance of the "a list inventing a third rule" hazard that `core/pagination.go:270-283` warns about, so do not file it as one.
- **No credential leaked into a list.** `AgentSession.ticket`, `sshAddress` and `streamUrl` were all empty on every terminal session; the values were length-checked rather than printed.
