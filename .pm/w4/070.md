Why: the members table exists to answer "who is in this workspace and what can they do", and for 2 of 5 rows it answers with an opaque id and a UUID — an admin cannot tell whether that row is a colleague, a machine, or an identity that no longer exists, and nothing on any surface says which.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 pass 14, sweeping workspace members. **Read-only — no member was invited, removed, or had their role changed, and nothing was created for this finding.**

## Root cause — one discarded boolean

`lego/backend/internal/members/service.go:425-430` (`Service.List`):

```go
if s.Identities != nil {
    if attrs, ok := s.Identities.LookupIdentity(ctx, m.Subject); ok {
        mv.Email = attrs.Email
        mv.MFAEnabled = attrs.MFAEnabled
    }
}
```

`ok` is the only place the distinction exists, and it is dropped on the floor. `MemberView` has no field that can carry it, so no surface can report it: REST, GraphQL and MCP all render the same `""`. Two adjacent facts make the silence worse rather than better:

- **`status` is a constant, not a fact.** `lego/backend/internal/workspaces/render.go:116-118` hardcodes `Status: "active"` with the comment _"bex tracks no invited/deactivated member state yet — every row in `tenant_members` is an active member."_ The one field in Render's `teamMember` shape that could express "this identity is gone" always says `active`.
- **The UI's fallback is indistinguishable from a real identity.** `dashboard/src/features/team/components/member-row.tsx:44` — `const identity = member.email || member.userId || member.subject` — is correct as a never-blank rule (its docstring says so), but it renders `own-d9csjmcc3bis73evo8n0` in exactly the typography a resolved email gets. Nothing tells the reader this row is a fallback.

## Target behavior (naming it, not "make it consistent")

**A member whose identity the platform cannot resolve must say so, on every surface, and `""` must stop being the only signal.** Concretely:

1. `MemberView` carries the discarded boolean — e.g. `identityResolved bool` — set from `ok`, and REST/GraphQL/MCP all expose it. REST's Render-shaped `teamMember` is a pinned schema, so the honest place for it there is **`status`**: stop hardcoding `"active"` and report an unresolved identity distinctly. Render's own enum for that field is what decides the spelling — capture it before inventing a value, and if Render has no such value, keep `status: "active"` on the Render adapter and expose the flag on the bex-native GraphQL/MCP surfaces only, recording the divergence in `docs/ADR018-render-parity.md`.
2. The Team row marks the fallback — a muted badge next to the id, not a changed primary line. Keep `member-row.tsx:44`'s never-blank chain exactly as it is; add the marking, don't alter the fallback order.
3. **The lifecycle question gets an answer in writing:** does bex reap a `tenant_members` row whose Kratos identity is gone, or does it keep it and let an admin remove it by hand? Keeping it is defensible (an identity can be restored; deleting authorization silently is worse), but it must be a decision in `docs/ADR024-members.md`, not an accident. Removal already works either way — the remove mutation keys on `subject` (`member-row.tsx:117`), which is present.

## Blast radius of the same discarded `ok`

`grep -rn "LookupIdentity\|LookupEmail" lego/backend/internal --include='*.go' | grep -v _test` — **6** non-test sites, one interface declaration each in `members` and `notifications`, and four real consumers:

| site | what the miss does today |
| --- | --- |
| `members/service.go:426` (`List`) | this finding — `""` email on all three surfaces |
| `members/service.go:495` (`memberWithEmail`, the duplicate-invite guard) | a member whose identity is unresolvable **cannot be detected as already-a-member**, so re-inviting that address is not caught by this predicate |
| `members/service.go:703` (invite preview `inviterEmail`) | the preview omits who invited you |
| `notifications/service.go:183`, `:811` · `webhooks/worker.go:760` | email notification for that subject is skipped silently |

The notification skips are **correct** for a genuinely deleted identity and must stay — but they are indistinguishable from a misconfigured `BEX_KRATOS_ADMIN_URL`, which is the same underspecification in a place where it costs deliverability. `memberWithEmail` is the one that deserves its own look: it is a guard, and a guard that silently cannot see one member is a different class of problem from a blank cell.

## Checked, and deliberately **not** filed

- **The REST-vs-GraphQL role spelling is faithful to Render, not a bug.** The same member reads `WORKSPACE_VIEWER` on REST and `VIEWER` on GraphQL. That looked like drift and is not: Render's *public API* enum is `ADMIN · DEVELOPER · WORKSPACE_CONTRIBUTOR · WORKSPACE_BILLING · WORKSPACE_VIEWER` (`docs/render-artifacts/owners-api.md:125-137`) while Render's *dashboard GraphQL* enum is `ADMIN · DEVELOPER · CONTRIBUTOR · VIEWER · BILLING` (`docs/render-artifacts/team-members.graphql:47-49`). bex reproduces both deliberately — `workspaces/render.go:79-94` maps the lowercase FGA relations onto the REST spelling, and `members/graphql.go:24-29` records the GraphQL contract. Recorded here so the next hunt does not re-file it.
- **The subject on the Team row is a recorded decision, not a leak regression.** `member-row.tsx:31-32` and `:62-66` demote the raw subject to a muted secondary line on purpose ("the raw subject stays the mutation key", w6/m10). That is a different question from `w4/069` (which is about API-keys/audit rendering a subject *where an email belongs*, with no id beside it), and `069`'s claim that members was settled by `w6/m7` still holds: the members `userId` **is** a minted `own-` id. Whether the subject line should also resolve is 069's call to make, not a new finding.
- **Seats are counted honestly.** "5 seats used" equals 5 member rows, and paid plans are unlimited (`store/plans.go:74-82` — only Hobby caps at 1), so the unresolvable rows cost nothing today. On a **Hobby** workspace the same situation would consume the single seat and block every invite via `CanAddMember` (`plans.go:125-128`); worth a sentence in whichever fix lands, not a separate finding.
- The whole SSH-keys journey was exercised in the same pass and is **correct** — see the "Swept and found correct" list at the end of `w4/m101/t012`, which is where this pass's only other finding lives.

## Unverified

- **Whether those two Kratos identities actually exist.** The inference that they were deleted rests on the fact that an existing Kratos identity always has an email identifier, so a miss means "not found" rather than "no trait"; the Kratos admin API was not queried (no admin credential in a QA session, by design). A fix must confirm it against `BEX_KRATOS_ADMIN_URL` before choosing reap-vs-keep.
- **MCP** was not called this run. `list_workspace_members` returns the same `MemberView` through the same enrichment (`members/members_surface_parity_test.go:88-113` exercises all three surfaces off one `List`), so it carries the same `""` — traced in code, not observed.
- Neither the last-100 audit events nor any pending invite mentions either subject (`workspaceInvites` → `[]`), which is consistent with dormant identities but proves nothing about their existence.
