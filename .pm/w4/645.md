# 645 — Deleting a Postgres from its own page sometimes also toasts "That resource doesn't exist or was deleted.", the datastore sibling w4/340 said to file if it recurred

Why: the user confirms a typed `sudo delete postgres …`, and is told both that the delete started and that the resource they were looking at does not exist. w4/340 fixed this race for services with an own-delete guard. It reasoned the datastore pages safe, saw the race once on Postgres (round 183), and said "If it recurs, file it". It recurred.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 329, 2026-11-13 22:36–22:52 UTC (`muse.env`, workspace `bex-canary`; pin `1c4d721bc8dc`). **Minor** (a false error toast beside a successful delete; the delete and the landing on `/` are right). ~40m.

- **Root cause:**
  - The only emitter of that toast is `useNotFoundRedirect` (`dashboard/src/common/hooks/use-not-found-redirect.ts:97-110`). `databases.$databaseId.tsx:145` and `keyvalue.$keyValueId.tsx:108` call it with no own-delete guard.
  - `useDeleteDatabase` (`dashboard/src/features/databases/hooks/use-delete-database.ts:33-57`) awaits the mutation, toasts success, and only then does the danger card call `onDeleted` → `navigate({ to: "/" })` (`database-danger-actions.tsx:62-77`; route `:179`/`:377`). Between the delete's commit and the navigation, the page stays mounted with several independent reads of the same root field `database(id: …)`:
    - `useDatabase`'s own poll (`use-database.ts:40-58`, 25 s at rest, 3 s while converging);
    - the Access control section's `DatabaseIpAllowList`, which selects `database(id: $id)` (`databases.graphql:147-148`) and polls every 25 s on its own clock (`use-access-control.ts:40-46`);
    - `DatabaseCredentials`, which polls beside it.
  - A read that lands in that window answers `database: null` + not found. Whichever query it belongs to, Apollo writes `null` to the shared `ROOT_QUERY.database({"id":…})`. The cache-first `Database` watcher then settles empty, so `resourceNotFound` (`use-not-found-redirect.ts:23-29`) holds and the redirect toasts.
  - w4/340's service fix is the `deletingSelf` flag that `ServiceDetailLayout` threads through `ServiceDeletingProvider` (`service-detail-layout.tsx:63-69,187`; `services/lib/service-deleting.ts`). Nothing like it exists outside the service layout.
- **Fix (target behavior):** a delete started from a resource's own page shows only its own success (or error) toast and lands on `/`. A direct visit to a dead id still toasts "That resource doesn't exist or was deleted." and redirects (the w9/m55 / w4/158 control).
  - Mark the resource as being deleted **before** the mutation fires, and clear the mark if the mutation fails. While marked, the route's `useNotFoundRedirect` neither toasts nor navigates, because the delete flow owns navigation.
  - Prefer one shared mechanism over a provider per route: for example, the delete hooks register the id and `useNotFoundRedirect` consults the registry. The service layout's `deletingSelf` can then fold into it.
- **Blast radius:**
  - `useNotFoundRedirect` has 9 callers: `blueprints.$blueprintId.tsx:249`, `databases.$databaseId.tsx:145`, `env-groups_.$groupId.tsx:136`, `keyvalue.$keyValueId.tsx:108`, `project.$projectId.tsx:63`, `w.$.tsx:64`, `webhook.$webhookId.tsx:79`, `deploy-detail-page.tsx:64` and `service-detail-layout.tsx:68` (already guarded).
  - Those that host their own delete need the guard: Postgres, Key Value, webhook, Blueprint, project and env group. `w.$` (membership) and the deploy page have no own delete.
  - Key Value has the same sibling-read shape. `KeyValueIpAllowList` polls in `use-key-value-networking.ts:41`, and the persistence and maxmemory reads sit beside it.
  - Tests:
    - a not-found answer from a sibling query, and from the page's own poll, during an own delete toasts nothing;
    - a failed delete leaves the redirect armed;
    - a direct dead-id visit still toasts (keep w4/158's test).
