## Objective

Put t001–t004 onto the production sandbox pool: build `runsc` reproducibly from the fork's release branch carrying m545 + m574 + t001–t004, publish `release-20260622.0-bex.3` on `bex-co/gvisor` (outside git), pin its SHA-512 in `sandbox-pool.yaml`, and surge-first roll the sandbox pool.

## Context

- `w4/m574` t008 documented the exact reproducible `go build` procedure from gVisor's go-branch tree (used because GitHub had disabled Actions on `bex-co/gvisor`; if Actions are re-enabled, fork CI may build it instead) and kept `release-20260622.0-bex.1`'s unchanged `containerd-shim-runsc-v1`.
- Pin location: `infra/clusterapi/overlays/hetzner-caph/sandbox-pool.yaml` (`GVURL`, `RUNSC_SHA512`, `SHIM_SHA512`, and the comment above them).
- Surge-first roll procedure (`infra/clusterapi/overlays/hetzner-caph/README.md`):
  1. Apply the updated `bex-sandbox` `KubeadmConfigTemplate`, checking with `kubectl diff` that only the URL and digests change.
  2. Scale `MachineDeployment/bex-sandbox` up to 2; verify `sha512sum` and `runsc --version` on the new node.
  3. Cordon the old node and wait for any running sandbox/agent sessions to finish cleanly — never cut off a running session.
  4. Annotate the old machine `cluster.x-k8s.io/delete-machine` and scale back to 1.
- Production access: `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>`.

## Steps

1. Cherry-pick/port t001–t004 onto `bex/release-20260622.0-echo-signal-chars`, build `runsc` reproducibly (verify identical sha512 across clean builds), and publish `release-20260622.0-bex.3` on `bex-co/gvisor` with the patch and build command in the release notes.

3. Roll the production sandbox pool surge-first and verify `scripts/capi-template-drift.sh` reports no drift.
