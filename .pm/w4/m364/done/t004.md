## Objective

Scaling and autoscaling behave the same on REST, GraphQL, MCP and the dashboard, and match render.com.

## Steps

1. Check that REST `POST …/scale`, GraphQL `scaleService` and MCP `scale_service` share the t003 behavior.
2. Re-read Render's scale and autoscaling docs on the day. File any drift, such as the 202 body bex sends where Render documents none, as a follow-up.
3. Amend the ADR018 rows at lines 99 and 100: autoscaling's dependency on the metrics read, the paused state, and the manual-scale rule.

## Acceptance criteria

- [ ] The README records the comparison, and ADR018 is updated.

## Outcome (2026-11-14)

- REST `POST …/scale`, GraphQL `scaleService` and MCP `scale_service` all call `apps.Service.Scale`, so they share t003's behavior; a test drives all three.
- Render, re-read 2026-11-14: [Scale a service](https://api-docs.render.com/reference/scale-service): "Render ignores this value as long as autoscaling is enabled for the service"; 202 with **no body**. [Scaling](https://render.com/docs/scaling): "If you configure both manual scaling and autoscaling for a service, Render enables autoscaling and ignores the manual scaling configuration"; scales up immediately, waits "a few minutes" before scaling down; autoscaling events appear on the Events page. Nothing about unavailable metrics, and nothing about what the manual count does when autoscaling is turned off (bex runs it, the w5/130 rule).
- bex now matches on the ignored manual scale. The paused state (`metricsUnavailable`, the Scaling page notice) is a bex extension; Render documents none.
- Drift found, not changed (follow-up to file): bex's scale 202 carries the service body, Render documents none.
- ADR018 amended: the Manual scale row (the under-autoscaling rule and the 202-body drift) and the Autoscaling config row (dependency on the `metrics.k8s.io` read, the production refusal, the condition/metric/alert and the paused state).
