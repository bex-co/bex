# 412 — A Docker Command `sh -c '<script starting with NAME=…>'` never starts: the quoted script reaches `sh` with its quotes and fails "not found"

Why: `sh -c 'i=0; …'`, `sh -c 'FOO=bar exec ./app'` and `sh -c 'PORT=8080 node server.js'` are ordinary Render Docker Commands. On bex the container crash-loops with `sh: <the whole script>: not found` and the deploy never goes Live. The command is valid, it runs on Render and it ran on bex before w8/164. The failure is easy to misread as the user's own mistake.

**Severity:** major (a valid start command cannot run; regression from w8/164, `7866fb3ee` 2026-10-21). **Estimate:** ~30m. **Source:** live `/qa-find-bugs w4` loop run v3l5, 2026-10-24 UTC (`muse.env`, `bex-canary`, pin `23750eda6b21`). Fixture: Free BusyBox web service `qa-20261024-v3l5-tail` (`srv-dbekqeco539c73f0v34g`). It was deleted (`GET` → `404`); session revoked.

## Probe

1. `POST /v1/services` with `envSpecificDetails.dockerCommand` = `sh -c 'i=0; (while true; do i=$((i+1)); echo v3l5-tick-$i; sleep 2; done) & while true; do printf "HTTP/1.1 200 OK\r\nContent-Length: 2\r\nConnection: close\r\n\r\nok" | nc -l -p 10000 >/dev/null; done'`. `GET` returns the command stored verbatim.
2. The deploy stays `update_in_progress`, and the URL answers `503`. App logs, repeated: **`sh: i=0; (while true; … done: not found`**.
3. Controls from earlier runs: the same `sh -c '…'` pattern whose script starts with `while` or `B=$(…)` ran fine (runs f2s9, p7r1, r5e3).

## Root cause (reproduced against the operator's code)

A throwaway test in `lego/operator/internal/controller` showed:

- `shellCommand(<that command>)` → `["sh", "-c", "'i=0; (while … done'"]`. The script keeps its outer single quotes, so `sh` runs a single command literally named `i=0; (while …`.
- `shellCommand` (`shell_command.go:124-137`) unwraps the script only if `splitShellWords(script)` returns one word.
- `splitShellWords` (`:39-99`) ends with `if len(words) == 0 || isAssignment(words[0]) { return nil, false }`. That rejects any first word shaped `NAME=…` **even when the word was quoted**:
  - `splitShellWords("'x=1'")` → `ok=false`;
  - `'i=0'` → `ok=false`;
  - `'i=0; echo $i'` → `ok=false`;
  - controls `'echo hi; sleep 2'` and `'(echo a) & echo b'` → `ok=true, n=1`.
- To a shell, `'x=1'` is a quoted word, not an assignment. Only an unquoted leading `NAME=value` is one.

## Fix

- Track whether each word contained any quoting. Apply `isAssignment` only to a first word that was entirely unquoted, which is the case the check exists for (`FOO=bar cmd` needs a shell).
- Alternatively, in `shellCommand`'s `sh -c` branch, unwrap a script that is exactly one single- or double-quoted token without asking `splitShellWords` about assignments.
- Tests (table, alongside w8/164's):
  - `sh -c 'i=0; echo $i'`, `sh -c 'FOO=bar exec app'` and `/bin/sh -c 'X=1 Y=2 cmd'` produce `[sh -c <unquoted script>]`;
  - unquoted `FOO=bar cmd` still goes through `/bin/sh -c`;
  - w8/164's existing cases are unchanged.
- Existing services with such a command are crash-looping now. After the fix, a redeploy restarts them, so mention that in the release note.

**Unverified:** how many live services carry a quoted script that starts with an assignment (not queried); the Blueprint `dockerCommand` path (the same operator function, read from code).
