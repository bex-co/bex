# 071 — The SQL console answers every query mistake with a bare SQLSTATE code, and the redaction it inherits has no sink left to protect

Why: the console's whole purpose is iterating on a query, and `bad request (SQLSTATE 42703)` does not tell you which column you got wrong — while the two error classes that _are_ classified come back as clear prose, proving the channel can carry a message.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 pass 15, journey 11. Fixture `qa-20260913-pg` (`dpg-dajgf7a6m8ac739r5em0`), **free** plan, public access, created and deleted inside the run.

## Four different mistakes, four bare codes

`mutation { executeDatabaseQuery(id:"dpg-…", sql:"<below>"){ rowCount truncated columns } }`, complete `errors[].message` each time:

| sql sent | message returned | what Postgres would have said |
| --- | --- | --- |
| `selct 1` | `bad request (SQLSTATE 42601)` | `syntax error at or near "selct"` **+ a character position** |
| `select 1; select 2` | `bad request (SQLSTATE 42601)` | `cannot insert multiple commands into a prepared statement` |
| `select nosuchcol from pg_class limit 1` | `bad request (SQLSTATE 42703)` | `column "nosuchcol" does not exist` |
| `select * from definitely_not_here` | `bad request (SQLSTATE 42P01)` | `relation "definitely_not_here" does not exist` |
| `select 'x'::int` | `bad request (SQLSTATE 22P02)` | `invalid input syntax for type integer: "x"` |

Note the second row: the console's own copy says "Run a **single** SQL statement", yet breaking that rule reports the same generic `42601` as a typo does — the one error the product could have anticipated in its own words.

**REST is identical** (`POST https://api.bex.co/v1/postgres/dpg-…/query`):

```text
{"sql":"select nosuchcol from pg_class limit 1"}
→ 400 {"error":"bad request (SQLSTATE 42703)","id":"bad_request","message":"bad request (SQLSTATE 42703)"}
```

And the dashboard renders exactly that string — the UI is a faithful messenger, so **no dashboard change is needed** beyond optionally using `Position` once it exists.

## The control case: the two classified classes are excellent

Same endpoint, same session, minutes apart:

```text
create table qa_20260913_t(i int)   (allowWrites omitted)
→ bad request: read-only transaction; write and DDL statements are not permitted

select pg_sleep(15)
→ bad request: query exceeded the statement timeout
```

So prose flows through this channel intact. The defect is precisely the unclassified default branch, not the transport, not the UI, and not GraphQL's error shape.

## Root cause — one deliberate line, with a rationale worth re-examining

`lego/backend/internal/postgres/query.go:365-380`:

```go
// mapPGError collapses a Postgres/driver error to one of the fixed, value-free
// sentinels. Non-classified DB errors surface only their SQLSTATE code — never the
// Postgres message, which can echo a query token or a literal value.
func mapPGError(err error) error {
	…
	case pgerrcode.ReadOnlySQLTransaction: return errQueryReadOnly
	case pgerrcode.QueryCanceled:          return errQueryTimeout
	}
	return fmt.Errorf("%w (SQLSTATE %s)", core.ErrBadRequest, pgErr.Code)   // :380
```

This is **deliberate, documented, and test-pinned** — `query_test.go:81-91` asserts it with the comment _"Syntax error echoes a query token in .Message; the mapped error must not"_ and the fixture `syntax error at or near "SECRETVALUE"`. So this note is not reporting an oversight; it is asking to narrow a decision, and the decision's own premise is what makes the narrowing safe:

- **The value the message echoes is the caller's own SQL**, returned in the response to the request that sent it. `SECRETVALUE` reaches the person who typed `SECRETVALUE` one round trip earlier.
- **The audit trail cannot receive it.** `audit_events` (`store/audit.go:108-125`) has **36 typed columns and no free-text/error column at all** — outcome is an enum, everything else is a named field. There is no sink in the audit path for a Postgres message to leak into, which is the strongest form of the guarantee `internal/api/CLAUDE.md` states ("the audit event carries the verb name, the caller, and the target NAME — never a verb argument's value").
- **The caller already has read access to everything the message could quote** — they are authenticated as a workspace member running SQL as the database's own user, so `column "x" does not exist` and `relation "y" does not exist` disclose schema they can enumerate with one `\dt`.

## Target behavior (narrow, not a reversal)

**Classify the schema-and-syntax classes and return their Postgres message plus `Position` to the caller; keep collapsing everything else; never write the message to a log line, metric label, or event.** Concretely:

1. Add to the classified switch the SQLSTATEs whose messages can only quote the caller's own SQL text or their own schema identifiers — at minimum `42601` (syntax_error, with `Position` so the console can point at the offending character), `42703` (undefined_column), `42P01` (undefined_table), `42883` (undefined_function), `42P02` (undefined_parameter), `3D000`/`3F000` (invalid catalog/schema name). Surface `pgErr.Message` for these.
2. **Keep the collapse for the classes whose messages quote stored data** — integrity violations are the clear line: `23505` unique_violation names the conflicting key **value**, `23503` foreign_key_violation names the referenced row, `22P02` invalid_text_input quotes the failing literal. Those stay `bad request (SQLSTATE …)`. Say this in the code comment so the next reader sees a boundary, not an omission.
3. Give the multi-statement case its own sentence, the way read-only and timeout already have one: the console advertises single-statement, so violating it should read like the copy, e.g. `bad request: only one statement per query`. Decide this by checking whether `42601` from a `;` is distinguishable from a plain typo — if not, detect it before dispatch rather than guessing from the SQLSTATE.
4. Update `query_test.go:81-91`: the current assertion ("mapped error must not contain the message") becomes a **per-class** assertion — message present for the classified schema/syntax set, absent for the integrity set. The `SECRETVALUE` fixture keeps its value as a test of the integrity path, moved to a `23505`-style error.
5. Record the narrowed rule where the original was decided. `docs/ADR009-postgresql-management.md` has no SQL-console section today (`grep -n -i "sql console\|SQLSTATE" docs/ADR009-postgresql-management.md` → no matches), which is part of why the rule survives only as a code comment.

## Blast radius — measured

`grep -rn "mapPGError" lego/backend/internal --include='*.go' | grep -v _test` → **5 call sites, all inside `postgres/query.go`** (`:261`, `:267`, `:320`, `:326`, `:353`) plus the definition. Nothing outside that file calls it, so the change cannot reach another feature.

Three entrypoints share the collapsed error and must move together:

| entrypoint | probed this run? |
| --- | --- |
| GraphQL `executeDatabaseQuery` (`postgres/graphql.go:618-627`) | ✅ live, all five SQL cases |
| REST `POST /v1/postgres/{id}/query` (`postgres/rest.go:206-214`) | ✅ live, two cases, byte-identical |
| MCP `query_render_postgres` (`postgres/mcp.go:149-156`, via `s.Query`) | ✅ **measured 2026-09-14 pass 23** — byte-identical (below) |

The MCP one is the reason this is worth more than console polish: an agent iterating on SQL through `query_render_postgres` cannot self-correct from `SQLSTATE 42703`, and agent-driven work is ADR008 pillar 4. **That is now measured rather than inferred** — over `POST https://api.bex.co/mcp` against a throwaway free instance (`dpg-dajpcua6m8ac739r5fq0`, created and deleted in pass 23), `tools/call query_render_postgres`:

```text
sql "select 1 as one"                      → {"columns":["one"],"rowCount":1,"rows":[[1]],"truncated":false}
sql "select nosuchcol from pg_class limit 1" → isError:true  content: bad request (SQLSTATE 42703)
sql "selct 1"                                → isError:true  content: bad request (SQLSTATE 42601)
```

Byte-identical to REST and GraphQL, delivered to the caller as an MCP tool error — so the agent receives a code and no message, which is exactly the case this note argues is worth fixing. It is also the only one of the three with a **Render counterpart tool of the same name**, so what Render's MCP server returns for a bad query is the parity question to capture — not captured this run, and not assumed here.

## Swept this pass and found correct, so not filed

- **Free tier for both datastores.** Postgres defaults to "Free — 256 MB RAM, 0.1 CPU, 1 GB" and Key Value to "Free — 128 MB RAM · 0.1 CPU", so journey 11/12 needs no purchase. Both reached `available` in **under 30 seconds**.
- **The IP allowlist is really enforced, and reversibly.** Three-state round trip on my own fixture: open → external psql returns a row; `setDatabaseIpAllowList(cidrs:["10.99.0.0/32"])` (a range that excludes this machine) → after ~50s the same command fails at the TLS layer (`SSL error: unexpected eof while reading`); `cidrs:[]` → after ~45s `REACHABLE_AGAIN`. The clear-and-recheck is what proves the block was the allowlist rather than an unrelated blip. REST reads it back in Render's object shape (`[{"cidrBlock":"10.99.0.0/32","description":""}]`) while GraphQL uses a flat string list — the same deliberate two-vocabulary pattern as the member-role enums, not drift.
- **The SQL console's row cap is disclosed, not silent.** `select generate_series(1,600)` returns "500 rows returned" **and** "Result capped at 500 rows", paginated 10 pages of 50. A cap that reported only "500 rows returned" would have been the more serious finding; it does not.
- **Insights is real.** Live storage (`7926 kB`), active processes with PID/state/duration, on a database seconds old.
- **Recovery is honestly plan-gated:** "Backups aren't enabled for this plan, so recovery isn't available. Upgrade to a plan w…" — the correct answer for a free instance, not an empty backup list pretending to be a backup list.
- **Nearly filed and wrong:** seven of the Postgres page's ten sections (SQL console, High Availability, Metrics, Instance type, Insights, Recovery, Access control) measure `innerText.length === 0` on load while the sidebar links to all ten. They are **lazily rendered** — each populates on `scrollIntoView`, and every anchor target id exists. Checked before writing it down; it is not a bug.
- **Cleanup:** both fixtures deleted via their own verbs (`deleteDatabase`/`deleteKeyValue` → `true`), and a follow-up list shows only the 3 pre-existing databases and 2 pre-existing Key Values, none `qa-`-prefixed. The local CA file was removed; the fixture's credentials died with it.
