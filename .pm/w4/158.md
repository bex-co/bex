# A dead-id URL opened directly redirects home with no "doesn't exist" toast: the lazy Toaster mounts after the toast fires

Why: `w9/done/m55`'s promise was "lands on `/` (with a "not found" toast), never an inline dead-end". On a direct visit (bookmark, pasted link, CLI-printed URL), six of the eight route families now drop the user on the Overview with no explanation at all. It looks like the link silently went to the wrong page. This is a regression: `w9/done/m60` t004 later made the `<Toaster>` lazy, and sonner does not replay toasts published before a Toaster subscribes.

Found live in `/qa-find-bugs` pass 213 on 2026-09-26 (w4-targeted, `muse.env` credentials), read-only against the deployed `726042a28`. The probe runs a `MutationObserver` installed with `page.addInitScript` before navigation, which records every `[data-sonner-toast]` text. It then does a hard `page.goto` to each URL and waits 6 s:

| Direct visit | Lands on | Toast recorded |
| --- | --- | --- |
| `/services/srv-doesnotexist00000000` | `/` | **none** ❌ |
| `/databases/dpg-doesnotexist00000000` | `/` | **none** ❌ |
| `/keyvalue/red-doesnotexist00000000` | `/` | **none** ❌ |
| `/project/prj-doesnotexist00000000` | `/` | **none** ❌ |
| `/env-groups/evg-doesnotexist00000000` | `/` | **none** ❌ |
| `/webhook/whk-doesnotexist00000000` | `/` | **none** ❌ |
| `/blueprints/blp-doesnotexist00000000` | `/` | `That resource doesn't exist or was deleted.` ✅ |
| `/services/<live srv>/deploys/dep-doesnotexist00000000` | that service's Deploys tab | `That resource doesn't exist or was deleted.` ✅ |
| **Client-side** navigation from `/` to `/databases/dpg-doesnotexist00000001` | `/` | `That resource doesn't exist or was deleted.` ✅ |

The redirect half of `w9/m55` holds everywhere. Only the toast is lost, and only when the page is the first thing loaded.

## Mechanism

- `dashboard/src/common/hooks/use-not-found-redirect.ts` (`useNotFoundRedirect`) calls `toast.error(..., {id: "resource-not-found"})` and then `navigate({replace: true})` in a `useEffect` once the detail query settles empty. There are 9 callers: `w.$`, `env-groups_.$groupId`, `keyvalue.$keyValueId`, `databases.$databaseId`, `webhook.$webhookId`, `blueprints.$blueprintId`, `project.$projectId`, `deploy-detail-page`, `service-detail-layout`.
- `dashboard/src/common/providers/root-provider.tsx:15,50-52` mounts the Toaster as `lazy(() => import("./ory-toaster"))` inside `<Suspense fallback={null}>` (`w9/m60` t004, to move `react-intl` out of the entry chunk).
- sonner 2.0.7 (`node_modules/sonner/dist/index.mjs:921,956-957`): `Toaster` starts at `useState([])` and subscribes to `ToastState` in a `useEffect`. `Observer.publish` (`:133`) only calls current `subscribers`, and nothing replays `ToastState.toasts` into a Toaster that subscribes later. A toast published before the lazy chunk has mounted is therefore gone.
- On a hard load the detail loader has already resolved the dead id during SSR, so the not-found effect runs during hydration, ahead of the lazy Toaster. Blueprints and the nested deploy happen to settle later and win the race; the other six lose it. The result is a race, not a per-route bug, so it can vary with network and cache timing. On a client-side navigation the Toaster is already mounted, which is why that path works.

## Fix

Target behavior: **every toast raised after the app starts hydrating is displayed**, whether or not the Toaster chunk has arrived. Two acceptable shapes; choose one and note why:

- Mount sonner's `<Toaster>` eagerly (in the entry chunk). Lazy-load only the Ory `react-intl` wrapper that Ory's `DefaultToast` needs, for example by rendering Ory toasts through a lazily loaded custom component. `w9/m60`'s bundle win is kept for `react-intl`, and the Toaster itself is always subscribed.
- Keep the lazy Toaster, but on mount replay the toasts that sonner already holds (`ToastState.toasts` / `toast.getToasts()` in 2.x) that were published before subscription. This relies on sonner internals, so it needs a version-pinned test.

Tests:

- A hydration-order test: render the root with a child that calls `toast()` in its first effect before the Toaster resolves, and assert the toast is displayed.
- Per-route not-found tests on a first render with pre-resolved data, for at least `databases` and `services`. The existing tests cover redirect vs stay-put, not the toast on a cold mount.

Blast radius: any toast fired from a mount-time effect on a hard load.

- The 9 `useNotFoundRedirect` callers were probed (above).
- Toasts after an async step on first load could hit the same race on a slow chunk load. Unverified, not probed: `features/team/hooks/use-invite-redemption.ts:79` (invite accepted), `features/workspaces/hooks/use-workspace-creation-billing.ts:166`, `features/databases/hooks/use-recovery.ts`.

Render: n/a. The redirect-home-with-toast behavior is a bex user decision recorded in `w9/m55` t005.

Estimate: ~45m.
