## Objective

New prebuilt-image web services from Docker Hub stopped resolving their image port in production. The first deploy stays `update_in_progress` with `port: 0` and `openPorts: []` and never starts a pod (no app logs). No `stallReason` and no `failureReason` appear, so the dashboard shows "In Progress" with nothing to act on. Meanwhile the host answers Traefik's raw `404 page not found`. A ghcr.io image created alongside went live in 4 s, and the same docker.io image went live within a minute in passes earlier the same morning. Target behavior: a registry read that cannot complete never leaves a deploy silent. Within the reconcile budget it either resolves or the deploy carries a named waiting reason ("Waiting for the image registry …", as t008 specifies for 429/5xx/timeouts). Only a definitive answer fails it. Find out what the deployed pin actually did. On `b4726243e74f`, any `ReadImageConfig` error should end the deploy `ImageMetadataUnavailable` (t008's evidence), and here nothing ended.

**Severity:** major (a docker.io first deploy never comes up and never says why; Docker Hub is the default registry). **Source:** live `/qa-find-bugs w4` loop run 65c6, 2026-10-27 UTC (`muse.env`, workspace `tea-daif693dqjvc73e7as3g`, production pin `b4726243e74f`).

What the code says (not a verified cause):

- Pin `b4726243e74f`: `resolveImageNetwork` (`image_network.go` at the pin, lines 87-160) returns every `ReadImageConfig` error, and the caller fails the deploy as `ImageMetadataUnavailable` (t008 Context: `app_controller.go:682-684` at the pin). Reads are bounded (`registry/image_config.go:246` `boundedhttp.WithTimeout`). So a 429, 5xx or timeout should have **failed** the deploy, not left it silent. Something else is happening: a reconcile that never re-runs, a requeue without status, or a read that succeeds yet produces no network.
- `BEX_APP_RECONCILE_WORKERS` defaults to 1 (`cmd/manager/main.go:394`). The ghcr fixture reconciled promptly, so the queue was not wedged as a whole.
- HEAD's t008 rewrote this path (cache by source tag, retryable 429/5xx/timeout with a waiting reason). It may or may not cover the observed state.
- The raw 404 on the host is m235 t008's fallback route (`8ba87e838`, not yet deployed). Here it lasted 10+ minutes, not m235's ~2.5 s.

**Re-probe (run 0dbc, 10:25–10:32Z):** three `docker.io/traefik/whoami:latest` web services each resolved `port 80` and went `live` 18–26 s after create (`srv-dbg7o7nqu9cs73co5s80`, `srv-dbg7pkd9rkoc73apiefg`, `srv-dbg7qdl9rkoc73apiehg`). Production had been re-pinned to `f4f12981e455` (pin commit `4bb1e44e2`, 09:13Z), which carries this milestone's t008 image-metadata rewrite. The 09:44–09:54Z stall therefore falls inside, or shortly after, that operator rollout. A transition-time cause is now more likely than a steady-state one, and the task should start from the rollout's operator logs.
