## Objective

Since m243 every new Docker/image web service reads its image config from the registry. That read must not burn the cluster's shared anonymous Docker Hub quota on every reconcile. When the registry does throttle (`429`) or blip (`5xx`), the deploy must back off and retry rather than end `update_failed`.

**Severity:** major (two deploys failed at the same instant on a registry 429, one of them five minutes into its rollout; every tenant shares the cluster's egress IPs and therefore one anonymous Docker Hub limit). **Source:** live `/qa-find-bugs w4` loop run 661f, 2026-10-26 UTC, pin `b4726243e74f`, `bex-canary` (same probes as t007).

## Context

- Live: `dep-dbfk7e5n83uc738ut9q0` (whoami, started 12:12:40) and `dep-dbfk9qkd3d3c73capdt0` (echo, started 12:17:48) both ended `update_failed` at **12:18:11** with `failureReason: "image metadata request returned status 429"`. A rollback created at 12:21:44 then sat at `created` for 5+ min (cause shared with t007, unverified).
- Cache miss (read from code, consistent with the live timing): `resolveImageNetwork` caches only when `cached.Image == image` (`lego/operator/internal/controller/image_network.go:98`). The cached value is the digest form `prefix@sha256:…` (`:159`), but for a prebuilt image `reusableArtifactImage` (`release_identity.go:644-645`) passes the **tag** (`app.Spec.Image`), so every reconcile of an in-flight release re-reads the registry: token, index, child manifest and config blob (`registry/image_config.go:180-300`).
- Terminal on throttle: any `ReadImageConfig` error goes straight to `r.fail(ctx, &app, "ImageMetadataUnavailable", err)` (`app_controller.go:682-684`), which closes the deploy as `update_failed`. A `429` (or `5xx`/timeout) is transient.
- Docker Hub's anonymous limit is per source IP, and tenant egress is a shared pool (the dashboard's Outbound IPs list shows the same five addresses for every service).

## Steps

1. Make the cache key match whichever reference form reaches it (compare the tag reference the release was resolved from, or the resolved digest), so a release reads the registry once per image change, not once per reconcile. Keep the configured-port condition.
2. Classify registry `429`, `5xx` and timeouts as retryable: requeue with backoff (honor `Retry-After` when present) and keep the deploy open with a statusReason such as "Waiting for the image registry (rate limited)". Fail only on definitive answers (404 manifest, no linux/amd64, digest mismatch) or the rollout budget.
3. Never flip a serving release's routing or status because a metadata re-read failed (with t007).
4. Optional, if cheap: use the platform's authenticated Docker Hub pull credential for metadata reads when one is configured, to lift the anonymous limit.

## Acceptance criteria

- [ ] Unit/envtest: repeated reconciles of one image release make one registry read sequence (fake registry request counter).

- [ ] Live (post-deploy): one image web service deploy plus a redeploy shows no `ImageMetadataUnavailable` failure, and the run's registry request count is bounded (operator log or metric).
