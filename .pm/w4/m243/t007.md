## Objective

A port-changing or failed deploy of a Docker/image web service must never take the live service down. Today the Ingress moves to the candidate release's port at rollout start, while the Services keep only the serving release's ports until promotion. Traefik drops the route and the host answers its raw `404 page not found` until something else fixes it, which after a failed deploy is never.

**Severity:** major (an outage of a running service caused by an ordinary port change; after a failed deploy it persists and rollback does not recover it). **Source:** live `/qa-find-bugs w4` loop run 661f, 2026-10-26 UTC, pin `b4726243e74f`, `bex-canary`, REST through the run's session jar (Playwright MCP down).

## Context

Probes (REST, `https://api.bex.co/v1`):

1. `POST /v1/services` image `docker.io/traefik/whoami:v1.10.3`, Free, no `PORT` → 201, `200` in 19 s, `openPorts: [{port: 80}]`. The m243 core DoD holds.
2. `PUT …/env-vars/PORT {"value":"80"}` + `POST …/deploys` → `live`, `200` throughout (control).
3. `PUT …/env-vars/PORT {"value":"9999"}` + `POST …/deploys` (`dep-dbfk7e5n83uc738ut9q0`): the URL went `200` → `404 page not found` 9 s later and stayed 404, while the old instance (`…-ldd1p…`, created 12:12:11) kept running. REST `openPorts` and GraphQL `port` already read 9999.
4. `mendhak/http-https-echo:35` (EXPOSE 8080/8443) live on 8080, then `HTTP_PORT=9090` + `PORT=9090` + `POST …/deploys` (`dep-dbfk9qkd3d3c73capdt0`): 1 s polls read `000`/`404` from 4 s after the deploy and `404` for all of the next 68 s.
5. Both deploys then ended `update_failed` (t008). Both hosts stayed `404` for 8+ min with GraphQL `phase: Failed` and `port` = the failed candidate's (9999 / 9090).
6. `POST …/rollback {"deployId":"dep-dbfk76ln83uc738ut9og"}` (the last live deploy, `PORT=80`) → 201 `dep-dbfkbm4d3d3c73cape1g`, then stuck at `created` with no reason for 5+ min, host still `404`.

Fixtures `srv-dbfk6dtn83uc738ut9kg` and `srv-dbfk9a5n83uc738ut9ug` were deleted (`GET` → 404).

Root cause:

- `lego/operator/internal/controller/app_controller.go:681` — `resolveImageNetwork` (`image_network.go:87-160`) returns the **candidate** primary port.
- Dispatch passes it to `ingressBackend` at `app_controller.go:2620`, which returns `(app.Name, port)` at `:2991`, so `reconcileIngressWithMiddlewares` points the Ingress at Service port 9999/9090.
- `applyClusterIPService` (`:3212`) builds ports from `privateServiceProjection` (`image_network.go:171-189`), which uses `ActiveImageNetwork()` = `ServingNetwork` (`tcp-80`, or `tcp-8080`+`tcp-8443`) plus a revision selector until `promoteImageNetwork` (`image_network.go:193-217`, called at `app_controller.go:3098`) runs after readiness.
- The Ingress names a Service port that does not exist, so Traefik drops the router: `404`. `promoteImageNetwork` moves only the two Services, never the Ingress, and nothing reverts the Ingress when the candidate fails.
- m182's readiness-safe named target (`servingTargetPort`, `:3233-3263`) is skipped for `HasImagePorts` apps (`:3217`), so neither guard covers this path.

**Render:** a failed deploy leaves the previous deploy serving, and a port change is zero-downtime.

## Steps

1. For `HasImagePorts` web services, route the Ingress to the **serving** network's `PrimaryPort` (`ActiveImageNetwork().PrimaryPort`) until promotion, and move Services and Ingress together in `promoteImageNetwork`.
2. A failed or canceled candidate leaves Ingress, Services and status on the serving network. REST `openPorts`, GraphQL `port` and MCP report the serving port, not the candidate's.
3. Keep the m235 first-deploy route for a never-served app.
4. Blast radius: `ingressBackend` has 3 call sites (`app_controller.go:2620`; `:3044` with port 0; `:6592` with `plan.prior.port`). Check `:6592`'s prior-port path for the same mismatch. Verify the slug Service `<slug>:<port>` internal address and service-ref env propagation (ADR041/ADR049) also follow the serving network. Private services (w6/m148) have no Ingress.
5. Determine whether the rollback stall (probe 6) is this route issue or t008's metadata loop; fix it here if it is routing.
