# 096 — The datastore reveal is fetch-gated end to end: no DOM residue, no cache shortcut, no web-storage persistence

Why: `w4/095` proved the secret is absent *before* the reveal and named the rest as the open question — what lands in the DOM after clicking, whether navigation clears it, and whether a repeat reveal still reaches the server. This closes all three, which is what makes the server-side fresh-authorization assertion actually load-bearing in the product.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 44. **Read-only on production — nothing created, changed or deleted.** No credential value entered the transcript: every result below is a membership boolean or an operation name. **No defect found.**

## The full lifecycle, on Postgres

Each step re-fetches the true value inside the page and asks only whether *that exact string* is present.

| step | password in DOM | reveal control |
| --- | --- | --- |
| page loaded, before click | **false** | `Reveal connection info` present |
| after clicking reveal | **true** | gone (replaced by revealed state) |
| after an **in-app** navigation to `/` | **false** | n/a (different page) |
| after `goBack()` to the database | **false** | **present again — re-gated** |

The navigation steps are deliberately **in-app** — a link click and a history back, not `page.goto`. A full reload would clear the JS heap and prove nothing; these keep Apollo's cache alive in memory, which is the case where a cached sensitive payload could leak back onto the page. It does not.

## A repeat reveal still goes to the server

The crux, because a cache hit here would silently skip the backend's re-authorization. Instrumenting `page.on("request")` for GraphQL operations matching `/ConnectionInfo/i`:

```json
{"firstRevealOps": ["DatabaseConnectionInfo"],
 "regatedButtonPresent": true,
 "secondRevealOps": ["DatabaseConnectionInfo"]}
```

Reveal → navigate away in-app → back (re-gated) → reveal again: the second reveal issues the **same network operation** as the first. Apollo never answers it from cache, so every reveal reaches the verb that asserts `core.RelCanViewSensitive` — including the uncached fresh re-assertion the secrets path performs specifically so a revocation inside the positive-TTL window cannot ride a cached positive to one last read.

## No persistence outside the live component

```json
{"inLocalStorage": false, "inSessionStorage": false, "localStorageKeys": 1, "sessionStorageKeys": 3}
```

The revealed connection string is in neither store. The handful of keys present belong to other concerns (language preference and router state) and do not contain it.

## Key Value behaves identically

Same shape on `beancount-forum-redis`: `internalConnectionString` absent from the DOM with a single `Reveal connection info` control, present after the click. So the gate is not a Postgres-only affordance.

## What this adds

`w4/m106`, `w4/082` and `w4/088` all audited the **server**: which verb, which scope class, which relation. None of them could say whether the client honours the gate — a dashboard that fetched the secret eagerly and masked it with CSS, or served it from cache on a second view, would satisfy every one of those audits and still hand the value to anyone with the page open. That gap is now closed by measurement rather than assumption, on both datastore types.

## Unverified

- **One database and one Key Value**, both in the operator's workspace. Other instances are assumed to share the component, not observed.
- **Copy-to-clipboard was not exercised.** The reveal panel offers copy controls; whether copying writes the value anywhere beyond the clipboard was not checked.
- **No revocation race was attempted.** That every reveal re-hits the server is shown; that the server *refuses* a reveal after access is revoked mid-session is inherited from the backend tests, not demonstrated live here.
- **The revealed state's lifetime was not bounded.** Whether it auto-hides after a timeout, or stays visible indefinitely while the page is open, was not measured.
- **No second browser profile / lower-privileged member** was used, so the gate was only observed from an account that legitimately holds the sensitive scope. What a `WORKSPACE_VIEWER` sees at the same control is untested.
