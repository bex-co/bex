# A crash-looping Docker web service says "Waiting for the container to start" for 15 minutes instead of naming the crash

Why: an image web service whose process exits on start shows a hopeful "waiting" hint for the whole 15-minute rollout budget. The same crash on a service with `PORT` set is diagnosed within minutes, so image users wait far longer to learn their start command is broken.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop run 813c, 2026-10-29 UTC (`muse.env`, pin `69f0b17d1fad`); **minor** (the terminal failure is correct; only the in-progress diagnosis lies), ~40m. ADR004 deploy status; follows the w8/m141–m142 image-port discovery work.
- **Repro (REST from the dashboard page, QA workspace):**
  - Failing: `POST /v1/services` `{"type":"web_service","name":"qa-<date>-img","ownerId":"<tea>","image":{"ownerId":"<tea>","imagePath":"docker.io/library/busybox:1.36"},"serviceDetails":{"plan":"free","runtime":"image","envSpecificDetails":{"dockerCommand":"httpd -f -p 10000 -h /nonexistent"}}}`.
  - Control: the same body plus `"envVars":[{"key":"PORT","value":"10000"}]`.
  - After 3 minutes, `GET /v1/services/<id>/events?limit=5` → `deploy_started.details.stallReason`:
    - control: `container exited shortly after start and is restarting repeatedly (last exit code 1) — check the service logs for the crash output. If the crash is a port bind: the process must listen on $PORT (10000).`
    - failing: `Waiting for the container to start before detecting its HTTP port`. The deploy page shows the same text under "In Progress".
  - A first run (`srv-dbhnarakl95s73b45ch0`) kept the waiting text from 16:33:49 until the deadline. At 16:49:03 it closed `update_failed` with the correct crash-loop `failureReason` (duration 14m 59s).
- **Expected:** while the candidate pod is in a terminal-looking state (CrashLoopBackOff, a start error, CreateContainerConfigError, an unpullable image), the stall reason is that diagnosis, worded exactly as on the configured-port path. "Waiting for the container to start…" is shown only while the container is genuinely starting (pending, pulling, or inside `portDetectGrace`). The deploy stays in progress until the existing rollout deadline; this changes the message, not the timing or the terminal state.
- **Root cause:** `lego/operator/internal/controller/app_controller.go:2668` calls `reportDeploymentStarting` before the ordinary not-ready diagnosis at `:3565` (`rolloutStallDiagnosis` → `stuckPodMessage`, `:5664`, which names CrashLoopBackOff at `:5680`). For an unconfigured image web service, `web_image_http.go:212` → `selectWebImageHTTP` (`:95`) returns `Waiting for the container to start…` (`:101`) whenever no Running candidate exists, and the pass halts in `reportWebHTTPSelection` (`:189`). That path checks only `rolloutDeadline` and `permanentRolloutPullFailure` (`:190-195`) and never calls `stuckPodMessage`, so the crash diagnosis cannot surface before the deadline settles the rollout.
- **Fix:** in `reportWebHTTPSelection`, after the deadline and pull checks, call `rolloutStallDiagnosis(ctx, app, dep, port)`. When it returns a terminal-looking reason (not `HealthCheckFailing`, which is meaningless before a port is chosen), set the Ready condition to that reason and message instead of `ReasonHTTPPortDiscovery`, keep the phase Deploying, and keep the 5 s requeue. The backend already passes `CrashLoopBackOff` through as a stall reason (`lego/backend/internal/store/reconciler.go:1908`), so REST, GraphQL, MCP and the dashboard pick it up unchanged.
- **Tests:** an operator unit test with an unconfigured image web App whose pod is in CrashLoopBackOff (last exit 1). The Ready condition must carry the crash message while discovery is pending. Regression tests: a pod genuinely starting (ContainerCreating, or Running within grace) still reports the waiting text, and a pod that becomes Running proceeds to discovery as today.
- **Blast radius:** `reportWebHTTPSelection` has one caller (`web_image_http.go:212`), and only unconfigured image web services (`webImageHTTPSelectionPending`) reach it. Configured-port, build-from-repo, private, worker and static services already take the `:3565` path. `stuckPodMessage`'s existing callers are unchanged.
- **Unverified:** the image-pull-error and CreateContainerConfigError variants were not probed live this run; `permanentRolloutPullFailure` may already cover unpullable images.
- **Render:** Render reports a start crash as soon as the process exits ("Exited with status 1 while running your code"); it does not show a waiting state.
- **Dedupe:** searched `.pm` for the waiting string, `stuckPodMessage`, and crash-loop items. `w4/m243` t011 (stall-hint naming of a configured primary) and the open `w4/429` (Docker Hub quota stall) are different states. No fix to `web_image_http.go` on `main` since `1bafd858f`. No DO_NOT_DO item applies.
- **Cleanup:** all three `qa-20261029-813c-*` services were deleted (REST `204`; a name search returns `[]`).
