# REST `GET /v1/blueprints` and `/syncs` return bare objects with no `cursor`, so Render clients cannot page or decode them

Why: every other bex list endpoint returns Render's `[{<resource>, cursor}]` envelope and pages with `limit`/`cursor`. The two blueprint lists return bare rows, ignore paging, and flatten fields Render nests. A Render SDK or tool decoding `blueprintWithCursor` / `syncWithCursor` gets empty objects. `w2/done/m62`'s definition of done ("`GET /v1/blueprints/{id}/syncs` behave[s] per Render's OpenAPI … cursor/limit; sync = `id · commit.id · …`") was closed without this being true.

Found live in `/qa-find-bugs` pass 208 on 2026-09-26 (w4-targeted, `muse.env` credentials), read-only against the deployed `726042a28`, workspace `bex`. A paging sweep used `?limit=1` and followed each item's `cursor` until an empty page, then compared against `?limit=100`:

| List | Envelope | Paged vs full |
| --- | --- | --- |
| `/v1/services`, `/v1/key-value`, `/v1/postgres`, `/v1/owners`, `/v1/notification-settings/overrides` | `[{<resource>, cursor}]` ✅ | identical, no dup/missing ✅ |
| `/v1/blueprints?limit=1` | bare objects, keys `id name repo branch path autoSync manifest status lastSync createdAt updatedAt`, **no `cursor`** ❌ | cannot page |
| `/v1/blueprints/{id}/syncs?limit=1` | bare `{"id":"bsr-…","state":"error","startedAt":…,"completedAt":…,"errorMessage":…}`, **no `cursor`, no `commit`** ❌ | cannot page |

Render's pinned schema (`lego/backend/internal/api/openapi/render-public-api-1.json`) says:

- `GET /blueprints` → `array<blueprintWithCursor>`, with `required: [blueprint, cursor]`. `blueprint` requires `id name status autoSync repo branch path`.
- `GET /blueprints/{id}/syncs` → `array<syncWithCursor>`, with `required: [sync, cursor]`. `sync` requires `id`, `commit: {id}` and `state`.

## Mechanism

- `lego/backend/internal/apps/rest.go:1337` returns `s.ListBlueprints(...)` (`apps/blueprint.go:1062`) as-is. There is no envelope, no `core.PageParams`, and no `core.StablePage` (`core/pagination.go:335`), so `limit`/`cursor` are ignored. `manifest` (the whole YAML) rides every list row.
- The syncs route serves `[]apps.BlueprintSyncView` (`apps/blueprint.go:484`): flat `commitId,omitempty` where Render nests a required `commit.id`, and again no envelope or paging. The store row carries `CommitID` (`store/blueprints.go:59`), so the data exists.
- The test pins the divergence instead of catching it. `api/render_openapi_blueprint_test.go:266` ("GET syncs returns the run history") unmarshals the body as bare `[]apps.BlueprintSyncView`. No test validates either list response against the pinned schema (the `w6/m126` response-conformance check covers projects only).

## Fix

1. Give both REST lists the envelope and paging every sibling uses:
   - `GET /v1/blueprints`: `[{blueprint, cursor}]`, paged by `core.PageParams` + `core.StablePage` on the id. The Render `blueprint` object is `id name status autoSync repo branch path lastSync`; drop `manifest` from list rows, since it stays on the by-id read.
   - `GET /v1/blueprints/{id}/syncs`: `[{sync, cursor}]`, where `sync` = `{id, commit: {id}, state, startedAt, completedAt}`. bex's `errorMessage`/`note` stay as extensions inside `sync`.
   - Leave the bex id prefixes (`blp-`, `bsr-`) as they are (ADR020).
2. Decide the `commit.id` value for a manual sync with no recorded commit (the live row above had none). Render requires the field, so state the choice explicitly (for example, the blueprint's branch head at sync time) rather than omitting it.
3. GraphQL and MCP are bex-native and keep their shapes. The dashboard reads GraphQL (`use-blueprint-syncs.ts`), so it is unaffected.
4. Tests:
   - Replace the bare-slice unmarshal at `render_openapi_blueprint_test.go:266`.
   - Validate both list responses against the pinned `blueprintWithCursor` / `syncWithCursor` schemas.
   - Assert that `limit=1` + `cursor` walks every row exactly once.

Unverified: which Render clients call these two lists (Render CLI, Terraform provider, SDKs). The breakage is inferred from the schema, not observed in a client. An owner-less `GET /v1/projects` 400 was seen in the same sweep, but it is the known divergence commented at `projects/rest.go:121-125` (owned by `w6/m126`) and is not filed here.

Estimate: ~60m.
