# 486 — REST `PATCH /v1/notification-settings` treats every omitted field as `false` and ignores unknown fields, so a partial or empty PATCH silently turns deploy-failure email off

Why: a script or the CLI that sets one preference (or sends a typo'd one) switches the other two off without saying so; for the default member that means the only email they get, "a deploy failed", stops arriving, and nothing in the response shows it was a side effect.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-04 ~22:00 UTC (`muse.env`, workspace `bex`); **major** (a PATCH answers 200 and disables failure alerts; no data lost, but an outage can go unnoticed); ~30m.
- **Probe** (from the dashboard page, `fetch(..., {credentials:'include'})`, `ownerId` = `tea-d98210cbbpdc73dcrkvg`). I first ran these against the QA member's own preferences by mistake, expecting a validation error, and restored them at the end (below):

  | # | Request | Response |
  | --- | --- | --- |
  | 1 | `GET /v1/notification-settings?ownerId=tea-d98210cbbpdc73dcrkvg` | `200 {"deployStarted":false,"deploySucceeded":false,"deployFailed":true}` |
  | 2 | `PATCH /v1/notification-settings` body `{"ownerId":"tea-d98210cbbpdc73dcrkvg","notificationsToSend":"bogus"}` | `200 {"deployStarted":false,"deploySucceeded":false,"deployFailed":false}` |
  | 3 | `PATCH /v1/notification-settings` body `{"ownerId":"tea-d98210cbbpdc73dcrkvg","foo":1}` | `200`, same all-false body |
  | 4 | `PATCH /v1/notification-settings` body `{"ownerId":"tea-d98210cbbpdc73dcrkvg"}` | `200`, same all-false body |
  | 5 | restore: `PATCH /v1/notification-settings?ownerId=tea-d98210cbbpdc73dcrkvg` body `{"deployStarted":false,"deploySucceeded":false,"deployFailed":true}`, then `GET` | `200`, back to row 1's values |

  Row 2 changed `deployFailed` from `true` to `false` although the body named none of the three fields. The comparison control is the same family on a strict-decoded route: `PATCH /v1/key-value/{id}` with `{"bogus":1}` answers `400 … request body contains unknown field "bogus"`.

- **Root cause:**
  - `lego/backend/internal/notifications/rest.go:63-68` decodes the body with `core.DecodeBody[SettingsView]` and passes `req.DeployStarted/DeploySucceeded/DeployFailed` straight to `UpdateSettings`.
  - `SettingsView` (`notifications/service.go:289-293`) has plain `bool` fields, so a missing key is `false` and cannot be told from an explicit `false`.
  - `UpdateSettings` (`service.go:345-366`) writes all three through `Store.UpsertNotificationSettings`. The verb is PATCH, the behavior is a full replace.
  - `core.DecodeJSON` (`core/http.go:55-70`) only disallows unknown fields when the request context is strict (`strictJSONDecoding`, set for the pinned-Render-contract routes). This bex-extension route is not, so `notificationsToSend`, `foo` and a misspelled `deployFaild` are all accepted and ignored.
  - `ownerId` is read from the query string (`rest.go:68`), not the body, so a body `ownerId` is ignored too. Rows 2–4 therefore hit the caller's default workspace, which happened to be `bex`.
- **Control cases (checked, not assumed):**
  - GraphQL `updateNotificationSettings` declares all three arguments required (`notifications/graphql.go:312-314`), so it cannot omit one.
  - MCP `update_notification_settings` takes `updateSettingsArgs` (`notifications/mcp.go:31-35`) with non-pointer bools. I did not call it this run, so whether its generated schema marks them required is unverified.
  - The dashboard Notifications page sends all three together on each toggle; I did not read its request this run.
- **Fix (target behavior):**
  - REST PATCH is a partial update: only fields present in the body change. Use `*bool` fields (or a presence-aware decode) in the REST body type and read the stored row first for the others.
  - An empty body `{}` returns the current row unchanged (200), not a write.
  - An unknown field is a 400 that names it, as `PATCH /v1/key-value/{id}` does, so a typo cannot silently do nothing. This is the same strict context the Render-contract routes get.
  - Service-level `UpdateSettings` keeps its three-argument signature for GraphQL and MCP, or takes pointers if MCP's schema does not already require all three.
- **Blast radius:** callers of `UpdateSettings`: REST `rest.go:68`, GraphQL `graphql.go:317`, MCP `mcp.go:54` (run `grep -rn "UpdateSettings(" lego/backend/internal` for the count before editing; three at the time of writing). Add a regression test that GraphQL and MCP still write all three values.
- **Adjacent classes:** an invalid `ownerId` stays 403/404 as today; a body field of the wrong type (`"deployFailed":"yes"`) must be a 400, not coerced to false.
- **Unverified:** MCP's required-field behavior (above); whether the CLI or the dashboard ever sends a partial body; the sibling `PATCH /v1/notification-settings/push` and `PATCH /v1/notification-settings/overrides/services/{id}`, which were not probed this run and may share the pattern.
- **Sibling checked, 2026-11-04 (follow-up probe, read-only):** `PATCH /v1/notification-settings/push` (`rest.go:97-103`) has the same replace-on-PATCH shape (`PushSettingsView` plain `Enabled bool` and slices, `service.go:396-405`), but `normalizePushSettings` (`service.go:529-535`) rejects a missing `timeZone` or `maxDeferralSeconds`. Live: `{}` and `{"foo":1}` both answer `400 … timeZone must be between 1 and 64 bytes` and a follow-up `GET` shows the settings unchanged. So an empty or typo-only body is safe there; a body that carries those two fields but omits `enabled` or `events` would still reset them (reasoned from the code, not written live). `PATCH /v1/notification-settings/overrides/services/{id}` uses pointer fields (`apps/rest.go:1882-1890`) and is partial as it should be.
- **Render:** n/a. Render exposes notification settings through the owner-level `PATCH /notification-settings/owners/{ownerId}`, which bex deliberately does not mount (`notifications/rest.go:26-45`, `DO_NOT_DO.md` round 14 for the Slack half); the PATCH semantics there are partial.
- **Dedupe:** `grep -rli "notification-settings" .pm` finds w4/435 (unsaved push changes), w4/410 (headings), w4/168 (Render's owner path unmounted) and w4/m128 (workspace scoping). None covers the omitted-field behavior. No `.pm/DO_NOT_DO.md` item applies.
- **Cleanup / state change to report:** the QA member's own preferences were changed by rows 2–4 and put back by row 5 (verified by the follow-up GET). Nothing else was created. This run's Kratos session is revoked after the hunt.
