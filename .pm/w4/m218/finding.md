# Initial plan-catalog errors leave hosting create forms unexplained and without Retry

**Severity:** major: a valid create draft cannot continue or recover in place after an initial catalog execution error. Reload is a working workaround but resets the typed draft. **Source:** functional live QA a785, 2026-10-16 UTC; research main `4052136f3`. This is a reproducible frontend failure under browser-local fault injection, not evidence of a production backend outage.

## Root cause and target

- **Service producer:** `dashboard/src/features/services/hooks/use-new-service-form.ts:58` drops `loading` and `error` from `useInstanceTypes`; offered catalog filtering/defaulting at131–145 yields `plan:""` with no usable tiers. The returned object at180–187 carries the list but no query state/retry. `routes/services.new.tsx:468–481` treats `instanceTypes.length===0` as pending. Main's329 fix replaces the old deployed80px block with PlanTierSlots but keeps this predicate, so the current source still renders a pending preview after a terminal error. Do not re-file its already-fixed geometry or make deployment lag the cause of this finding.
- **Postgres producer:** `features/databases/components/create-database-dialog.tsx:81` consumes only `instanceTypes`;100–105 derives an empty plan/no selected tier,127–135 correctly disables creation, and280–305 maps the empty list into an empty selector. The catalog error never reaches this form's rendering. Mutation errors are a separate path.
- **Key Value producer:** `routes/keyvalue.new.tsx:89` consumes the list and loading but drops error.105–110 derives an empty plan and disables creation;169–181 shows pending slots only while loading and otherwise renders PlanCardGrid with the empty list. Main's330 pending fix therefore leaves the settled error branch empty.
- **Three shared hooks:** `features/services/hooks/use-instance-types.ts:31–51`, `features/databases/hooks/use-database-instance-types.ts:20–51`, `features/keyvalue/hooks/use-key-value-instance-types.ts:20–40` each read Apollo `data/loading/error`, normalize missing catalog data to an empty array and return query state but **no refetch**. Add an explicit retry capability and propagate state to the three create producers. Do not invent a fallback Free tier or change prices, plan eligibility, backend schema or create semantics.
- **Actual pinned mechanism:** `dashboard/yarn.lock:65–67` pins Apollo4.3.3, also reported by native request extensions. Opened actual4.3.3 package source in `.playwright-mcp/qa-a720-apollo-source/package`: `core/QueryManager.js:644–649` throws CombinedGraphQLErrors for default `errorPolicy:none`; `core/ObservableQuery.js:1416–1431` turns a network error notification into `error` and `loading:false`, preserving a previous result only where appropriate. A cold missing catalog therefore reaches the hooks as no usable tiers plus a settled error; it is not a forever-loading Apollo request. `react/hooks/useQuery.js:60–82` binds observable methods including refetch; `core/ObservableQuery.js:395–423` refetches network-only. Exposing that existing action is sufficient; no new client or reload is needed.
- **Retry and pre-settle details:** `common/apollo/retry-link.ts:8–57` retries transient read transport errors up to3 attempts, but GraphQL execution errors arrive as results and bypass RetryLink. This explains why removing the interceptor does not itself recover the settled form. `common/apollo/default-options.ts:3–25` sets notifyOnNetworkStatusChange false to protect mounted drafts. A retry affordance must manage its visible in-flight state explicitly or opt in locally without unmounting stateful inputs. Initial pending remains an inert shape-matching preview; a settled error must have an explanation and recoverable read action. If valid cached choices exist, preserve them and the draft during a failed refresh rather than replacing the form. Cached-refetch behavior is source-based verification work, not a live failure captured here.

Target an accessible, localized catalog-specific message and Retry **within each affected plan region**, retaining name/source/commands/env/file/project state. Retry only the catalog read; a successful real catalog restores the existing eligible default/selection and validation. Remain disabled without a real eligible plan. Do not automatically replay writes or unmount/reset the form. A settled successful empty catalog needs an honest unavailable explanation, separate from pending; its exact product copy and retry policy are verification work. Preserve authentication/verification navigation and existing error classifiers; do not relabel403,404,timeout or malformed catalog data as an empty success or fabricate plans. These adjacent classes were not injected in this run.
