## Objective

Account for every consumer of the request-line text and decide the `text` filter's semantics, so search matches what the user sees.

## Context

- **Readers:**
  - `lego/backend/internal/logs/loki.go`: history, the path and host filters, `text` as a LogQL line filter on the stored JSON;
  - `lego/backend/internal/metrics/lokisource.go`: counts, latency and discovery;
  - the live-tail store poll (w4/m237);
  - the deploy page's per-deploy leg (`684391bc9`, w21/044);
  - the CLI `bex logs`, which prints the REST message;
  - static-site request lines (static-server, w4/m113).
- **Search mismatch.** Today `text=KubernetesIngressName` matches every request line and `text=responseTimeMS` matches none.

## Steps

1. List each reader here, and whether it reads the stored or the projected text.
2. **Decide `text` for `type=request`.** Either:
   - (a) match the projected summary, by filtering after projection or translating known keys; or
   - (b) keep matching the stored record, and document it in ADR010.

   Pick (a) if feasible within the store's limits.
3. **Add regression tests:** path, host and status filters, request metrics and latency, and a static site's request line.

## Acceptance criteria

- [ ] The inventory and the `text` decision are recorded here, and the regression tests pass.
