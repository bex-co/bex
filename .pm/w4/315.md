# System theme ignores later browser preference changes

Why: The System choice should update an open dashboard when the user's preferred color scheme changes, while preserving explicit Light and Dark choices.

**Severity:** minor. **Estimate:** 35m. Functional `$qa-find-bugs`, read-only resource pass a612, 2026-10-15, user-selected w4. Research HEAD `499590c8b99c83d3da7936f392da3684e642e1a9`; filing only. Goal: ADR008 usable hosting and the existing global theme preference.

## Reproduction and controls

Preference changes were induced through the **browser's native per-page media emulation**, not by replacing app functions or changing the host machine's settings.

1. At `https://dashboard.bex.co/`, set the browser preference to light and choose Avatar → Theme → **System** (Chinese **跟随系统** in this pass).
2. At **17:52:09.748Z**, stored mode is **system**, `matchMedia("(prefers-color-scheme: dark)").matches` is false, `<html>` has class **light**, and body background is `oklch(0.98 0.002 260)`.
3. Change only the browser preference to dark. It reports matches=true, but at **17:52:12.560Z** the page still has class light and the same light background. The stored choice remains system.
4. Independently reload at **390×844** while the preference is dark. At **17:53:38.737Z**, system mode correctly renders dark, background `oklch(0.12 0.008 260)`.
5. Change the preference to light. A read-only observer receives a real MediaQueryList **change** event with matches=false. At **17:53:41.450Z**, the app remains dark with its dark background and stored mode system.
6. Passing controls at **17:57:41–43Z**: explicit Light stays light under a dark preference; explicit Dark stays dark under a light preference. Switching **from an explicit mode back to System** applies the current preference. Explicit dark persists through reload. Language switching and reload persistence pass separately.

[Durable evidence](evidence/315-system-theme-change.json) contains both timelines, computed backgrounds, delivered media event, controls, exact setup and restoration. This is ongoing reactivity missing after load/mode selection, not a claim that the System choice or initial snapshot always fails.

## Root cause and bounded fix

`dashboard/src/common/providers/theme-provider/index.tsx:88–110` applies the document class from a hydrated effect whose dependencies are only **theme** and **isHydrated**. At **103**, it calls `getSystemTheme()` once for system mode; it never subscribes to preference changes. The helper in `theme-provider/utils.ts:3–11` correctly reads the current match state, and the bootstrap `common/components/document/theme-script.js.txt` correctly provides a startup snapshot. Neither supplies an ongoing listener.

In the hydrated provider, apply the current preference immediately and subscribe to the media query's **change** event **only while mode is system**. Apply the new resolved class without converting the user's stored/context mode into an explicit light/dark choice. Clean up on mode change and unmount. Keep the hydration guard, explicit modes, current URL/storage priority and startup behavior. [CSSOM View's MediaQueryList contract](https://drafts.csswg.org/cssom-view/#the-mediaquerylist-interface) defines the change event; the browser delivered it in this actual failing run.

Exhaustive production search finds:

- **1 ThemeProvider mount:** `common/providers/root-provider.tsx:38`.
- **1 RootProvider mount:** `common/root-route/root-component.tsx:49`, so this is a global provider fix for dashboard routes and their existing aliases, not per-resource patches.
- **2 active UI useTheme callers:** `common/components/user-nav.tsx:91` and `common/components/ui/sonner.tsx:15`. UserNav's desktop submenu and flat mobile options share the same setTheme action (`:135–145,190–221`).
- **2 getSystemTheme call expressions:** the provider and `theme-provider/hooks.ts:17` inside useIsDarkTheme. That derived hook has **0 external production callers**; it is not an additional live failure claim. No new theme architecture is required for this repair.

The fix is global to mounted System mode. It must preserve both explicit-mode controls, the stored preference and the existing consumers' context contract. No service/datastore API, resource-type or alias handler changes are needed.
