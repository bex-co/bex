# In a protected environment a Developer sees Delete enabled on a service, a Postgres and a Key Value, types the phrase, and reads "Forbidden"

Why: Render lets only Admins delete a protected environment's resources, so a Developer must see Delete disabled with Render's reason before typing the phrase, never a bare 403 after it. Found by w4/m578 t005 on 2026-11-22.

- **What happens (dev-4, OpenFGA enforced, 1440 and 390):** as a Developer in a protected environment, the service Settings danger zone's **Delete service**, **Delete Database** and **Delete Key Value Instance** are enabled. Typing the phrase and confirming answers `FORBIDDEN`, the dashboard shows a bare "Forbidden" toast, and nothing is deleted. The service's delete dialog then stays open. The verbs refuse by `requireUnprotected(ctx, …, "delete")` (`lego/backend/internal/apps/service.go` `Delete`, `postgres/service.go` `DeletePostgres`, `keyvalue/service.go`).
- **Why the dashboard offers it:** `DeleteServiceCard` (`dashboard/src/features/services/components/delete-service-card.tsx`) has no permission gate at all. `DatabaseRowActions`, `DatabaseDangerActions` and `KeyValueDangerActions` gate Delete on the workspace `can_create`, which a Developer holds (`deploy/gitops/authz/model.json`). No projection carries a `delete` row: `serverActions` has none, and `databaseActions` excludes it deliberately (`postgres/actioncaps.go`).
- **End state:** the three projections report `delete` with the w4/m578 rule (`core.RestrictedDecision`, reason `protected_environment_admin_required`), and every Delete control gates on it: disabled with _This action is limited to admins._ for a Developer in a protected environment, enabled for an Admin and in an unprotected environment, with the role reason for a Viewer. A raced 403 names the same reason instead of "Forbidden". Tests per surface; REST and MCP are unchanged.
