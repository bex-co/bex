# 527 — A Resume shortly after Suspend is recorded as `service_hibernated` + `service_woken`; neither `service_suspended` nor `service_resumed` is ever emitted

Why: w4/508 fixed a Resume recorded as an idle wake when `service_suspended` had already been recorded. Live on the new pin, a Resume that lands before the event projection has observed the suspension still loses both lifecycle events. Events then tell the owner their service went to sleep and woke on its own, and both the "suspended" and "resumed" push notifications are lost (`service_hibernated`/`service_woken` are never pushed, `notifications/push_worker.go:762`, w6/m47).

- **Root cause:** `lego/backend/internal/store/event_facts.go:605-613`.
  - On the Running → Hibernated edge, the projection chooses `service_suspended` or `service_hibernated` from `obs.Suspended`, which is `spec.suspended` at the moment the pass observes the App.
  - The observation lags the operator: here the pass that first saw `Hibernated` ran about 15 s after the Suspend and about 5 s after the Resume, when `spec.suspended` was already false again. So it recorded an idle sleep.
  - The checkpoint (`checkpointServiceSuspended`, `:554-560`) then holds `suspended=false`, and the Hibernated → Running edge at `:619-627` emits `service_woken`.
  - The w4/508 fix (`cab9b7996`) only keeps a reason that was already recorded from falling. It cannot recover one that was never observed.
- **Fix:**
  - Target: whether a Hibernated episode is a user suspension is decided by the Suspend action, not by `spec.suspended` at observation time. Any Running → Hibernated edge whose window contains a `suspender_added` (user) audit record emits `service_suspended`, and its wake emits `service_resumed`, even if the Resume already happened.
  - Options, in order of preference:
    1. When computing the Hibernated edge, also consult the audit trail (`suspender_added` after the previous checkpoint `changedAt`).
    2. Have the Suspend verb (`apps.Suspend`) write the checkpoint's suspended reason directly, so the projection does not depend on catching the flag.
  - Edge case: if Suspend and Resume both happen before the operator ever scales to zero, there is no Hibernated phase. Decide whether that should still emit the suspended/resumed pair. On Render, Suspend then Resume always produces both events.
  - Keep w4/508's guarantee and m230's (an idle sleep and wake stay `service_hibernated`/`service_woken`, and a wake is never recorded as a recovery).
- **Tests:** a store test where the first Hibernated observation already has `Suspended=false` but a `suspender_added` audit row exists inside the edge window. It must emit `service_suspended`, then `service_resumed` on the wake. Keep the existing idle-sleep and w4/508 tests as regression controls.
- **Blast radius:** `observedStateFacts` emits every observed lifecycle fact. Phase edges are shared with datastore observations (`datastore_event_facts.go`), so check whether Postgres/Key Value suspend has the same window. Push notifications (`notifications/push_worker.go`) and webhooks read these fact types.
