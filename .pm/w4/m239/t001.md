## Objective

For an Auto-Deploy-gated service (`autoDeployGated`, `lego/backend/internal/envgroups/service.go:1125-1129`), a group link must not touch any field in the operator's release identity until the owner's next deploy. Today `rollLinked` (`:1131-1147`) bare-patches `spec.envFromSecrets`/`filesFromSecrets`. Both are in `releaseIdentityInput` (`lego/operator/internal/controller/release_identity.go:207-208`) and the native artifact identity (`:174-175`, `:185`), so the operator adopts a new release that has no deploy row.

## Context

- See [finding.md](finding.md) for the timeline, from 06:26:55 to 06:28:48: a republish with no row.
- `requestedReleaseGeneration` (`release_identity.go:672-676`) falls back to `app.Generation` when the stamped annotation is not newer.
- The deploy mint path is `deploys/service.go:264-290`, `:737`, `:796` and `:831`. It already applies staged changes through `rollout.Snapshot.Stamp`.

## Steps

1. Choose where the pending link lives. One option is a staged-links annotation or status entry that the next deploy's `openRelease` mutate folds into `spec.envFromSecrets`/`filesFromSecrets`. Another is keeping it only in the group's link set and materializing the link at deploy time.
   - Record the choice and why in ADR032 (env groups) or ADR004.
   - The group's `serviceLinks` read keeps listing the service.
2. Gated `rollLinked` writes only the staged form. The rolled (Auto-Deploy on) path is unchanged.
3. Every deploy mint (manual, API, hook, rollback?) applies the staged links.
   - Decide rollback explicitly: rolling back to a release from before the link should not apply it.
