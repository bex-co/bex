# Short custom Metrics ranges report zero bandwidth despite retained samples

Why: a valid short time range silently turns recorded outbound traffic into a flat zero chart, misleading a user investigating a running service.

**Severity:** major — misleading settled chart data. **Estimate:** 55m (shared-call audit 10m, bandwidth-only validation and client sampling 15m, behavioral tests 20m, Simplify and owned live replay 10m). **Status:** open. Source: functional `$qa-find-bugs w4`, pass a70, 2026-10-10 UTC, using the muse.env login helper.

Goal: dependable hosting diagnostics ([ADR008](../../docs/ADR008-vision.md), [ADR010](../../docs/ADR010-observability.md), [ADR018](../../docs/ADR018-render-parity.md)). Repair an existing accepted-input gap; keep the documented bandwidth approximation and per-bucket byte unit.

## Reproduction and target

1. Create an owned Free BusyBox Web service, port 3000, with this Docker command:

   ```sh
   sh -c 'mkdir -p /tmp/qa-a70; printf "qa-a70-live\n" > /tmp/qa-a70/index.html; exec httpd -f -p 3000 -h /tmp/qa-a70'
   ```

2. After Live, GET its public URL twice, `/index.html` twice, `/qa-a70-missing` twice and `/qa-a70-other-missing` once. This pass used `qa-20261010-loop-a70-metrics`, `srv-db5687kb8ulc73efu7tg`, created at 16:13:18.451Z, Live by 16:14:11Z; the seven requests ran at 16:14:47–51Z. The platform also generated ambient requests; this is not an exactly-seven request-count test.
3. Open Metrics → **Time range** → **Custom…**. In the America/Los_Angeles browser, enter Start `2026-10-10T09:10` and End `2026-10-10T09:15`, then Apply. For a new replay, choose the equivalent five-minute window containing its own traffic.
4. The URL retains the correct UTC bounds. The automatic resolution is **3 seconds**. After settling, **Outbound Bandwidth** is a zero line; HTTP request and latency data are present. Reopen the same URL on a fresh page with status All, host All and no path filter: the bandwidth request again uses 3 seconds and its 101 points are all zero.
5. In that same signed-in browser, POST the controls below with identical resource/start/end, changing only resolution to 30 and 60 seconds. Both return positive bandwidth over that exact window, HTTP 200, no GraphQL errors. All three carry the same `degraded_sources: direct` label.

These sums establish available data versus systematic zeros. Their disagreement at 30/60 seconds is the already accepted alignment approximation; neither is an exact-byte or invoice control. The positive month-to-date footer is a different window and is not proof of traffic within these five minutes. The degraded direct source is not isolated as healthy in this pass; it is held constant across the decisive controls.

**Target:** the five-minute UI range keeps its selected start/end and requests bandwidth at a supported sampling interval, displaying positive retained data. Other metrics keep their finer resolution. Explicit API bandwidth input below the supported minimum receives a named bad-request error, rather than fabricated zero-valued buckets. Preserve `bytes` per bucket and the requested resolution for accepted API input.

## Root cause and concrete fix

- `dashboard/src/features/metrics/lib/range.ts:64–65,75–90` derives approximately 120 buckets, floored at 1 second. A five-minute span becomes 3 seconds.
- `dashboard/src/features/metrics/components/network-metrics-card.tsx:131` passes this unmodified window to its bandwidth `useMetrics` call. `hooks/use-metrics.ts:148–169` sends that value as GraphQL `resolution`.
- `lego/backend/internal/metrics/service.go:430–459` validates the window, resource and filters, then normalizes the query and checks the point budget. Normalization defaults nonpositive resolutions to one minute; it does not reject positive, sub-scrape bandwidth resolutions.
- `lego/backend/internal/metrics/source.go:152–156,424–428` uses the same requested resolution for both Prometheus query-range step and `egressquery.SumIncreases`' lookback.
- `lego/backend/internal/egressquery/query.go:144–167` evaluates `sum(increase(counter[seconds])) or vector(0)` per source, then sums the sources. When the lookback contains fewer than two counter samples, `increase` emits no element; the fallback converts missing computation into a numeric zero.
- `deploy/gitops/base/prometheus.yaml:349–350,395–396` configures 15-second Traefik/cAdvisor scrapes. The repository pins Prometheus chart 25.27.0 in `deploy/helm-artifacts.lock:19`. The actual v2.54.1 [extrapolatedRate implementation](https://github.com/prometheus/prometheus/blob/v2.54.1/promql/functions.go#L68) requires more than one float sample and otherwise drops the result. The [primary increase documentation](https://prometheus.io/docs/prometheus/latest/querying/functions/#increase) describes its extrapolation. Runtime image and raw production scrape timestamps were not inspected.

Proposed bounded change:

1. After the existing authorization, filter checks and normalization in the shared Metrics service, enforce a named **60-second minimum for BANDWIDTH resolution** (four current scrape intervals). Return `core.ErrBadRequest` explaining the minimum for a finer explicit query. Keep the default 60-second resolution and accepted larger values unchanged; do not silently rewrite explicit API resolution. Also specify unsupported spans below 60 seconds with a clear bandwidth-range error rather than sampling a larger hidden time window; that adjacent span case needs verification and was not live-replayed here.
2. At the single NetworkMetricsCard bandwidth call, send `Math.max(60, window.resolutionSeconds ?? 60)`, preserving start/end and polling cadence. Keep the CPU, memory, instance, request-count and latency calls unchanged. The chart accepts returned timestamps directly (`svg-line-chart.tsx:319–347`), so bandwidth need not share the other charts' point count.
3. Document this Bex bandwidth minimum on GraphQL/MCP without expanding the pinned REST parameter contract. Keep lookback equal to step for these byte buckets. **Do not apply the CPU/latency rate-lookback floor alone:** evaluating a 60-second byte increase every three seconds repeatedly counts overlapping bytes.
4. Keep month-to-date totals, usage metering, billing and the composed HTTP/WebSocket/direct source set unchanged. Do not replace composed bandwidth with HTTP-only logs or introduce an event stream.

## Shared callers, aliases and verification work

Production-only exhaustive searches found one caller of `SumIncreases` (metrics/source.go:428), one of `IncreaseOrZero` (SumIncreases), one of `promQueryFor` (source factory at :152), and one composition caller of `NewPrometheusRequestSource` (cmd/api/main.go:578). The proposed guard is metric-specific in the shared service; the egress helpers need no behavioral change.

The dashboard hook has three production component callers: ApplicationMetricsCard (10 calls), NetworkMetricsCard (3 calls), and ScalingRecentMetrics (7 calls). Of those 20 calls, the NetworkMetricsCard call is the single bandwidth call. Guard that call only. `egressquery.Increase` is also used separately by usage metering and the month-to-date read; preserve both.

Entry points to verify:

- GraphQL `metrics` names `BANDWIDTH` and `ENRICHED_BANDWIDTH` map to the same metric (metrics/graphql.go:46–47); input `resolution` is an Int and the existing parser converts it to a duration.
- MCP `get_metrics`: native `bandwidth` and Render alias `bandwidth_usage` (metrics/mcp.go:145–159), with Render `resolution` taking precedence over legacy `resolutionSeconds`.
- REST `GET /v1/metrics/bandwidth`: `resource` and legacy `service` resource spellings. Its pinned allowed parameters exclude resolutionSeconds (api/render_metrics_contract_test.go:52). Retain that rejection; do not add a REST parameter as part of this fix.
- Resource family: Web was live-reproduced. Static uses the same network card; private, worker and cron Apps share the backend bandwidth path. Those sibling types were not live-replayed for this finding. Postgres and Key Value use datastore metric reads and are outside this App bandwidth guard.

The shared-caller verification is a discrete part of this inbox item: test direct GraphQL/MCP fine-resolution refusal, valid 60s and 300s, missing resolution, both GraphQL aliases, both MCP names/parameter spellings, and unchanged REST parameter rejection. Test the five-minute UI request and positive chart with retained 15-second counter samples. Exercise linear traffic, counter reset, missing scrape, quiet service and bucket boundaries without requiring exact burst-byte equality. Keep finer non-bandwidth queries working.

Before settling, MetricSection keeps its chart-shaped skeleton; existing polling retains data while refreshing. Preserve the existing source-unavailable, transient error, throttled and degraded-source states; insufficient bandwidth granularity must not appear as successful zero data. Keep the established window/resource/filter error order. This is functional input validation, not a change to resource access behavior.
