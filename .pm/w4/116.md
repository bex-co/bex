# Router key writes ignore their own availability gate and fail as `internal error`

Why: `routerAvailable` exists precisely to say whether this workspace has the router, the three write verbs never consult it, and a caller outside the beta workspace gets an opaque `internal error` where a named refusal belongs — a small fix, and the check is already written one function above.

**Impact today is near-zero and triage should treat it that way.** The router is beta-gated to a single workspace (`tenant == BetaWorkspace`), and the dashboard hides the surface when `routerAvailable` is false, so no dashboard user can reach this. It is filed because the error class is wrong, not because anyone is hitting it.

Found by live `/qa-find-bugs` 2026-09-21 pass 123 (w4-targeted, `muse.env` credentials).

## Repro

```
query    { routerAvailable(ownerId:"tea-d98210cbbpdc73dcrkvg") }
→ false

mutation { createRouterKey(name:"qa-20260921-rk", ownerId:"tea-d98210cbbpdc73dcrkvg") }
→ { "data": { "createRouterKey": null },
    "errors": [ { "message": "internal error", "path": ["createRouterKey"] } ] }
```

## Root cause

`lego/backend/internal/router/service.go:79-85` — `Available` is the gate, and it is a pure local check:

```go
func (s *Service) Available(ctx context.Context) (bool, error) {
    if err := s.Authorize(ctx, core.RelCanView); err != nil { return false, err }
    tenant, ok := s.Tenant(ctx)
    return ok && tenant == BetaWorkspace && s.URL != "" && len(s.Secret) >= 32 && s.Members != nil && s.Authz != nil, nil
}
```

`Create` (`service.go:132-146`) authorizes, length-checks the name, then goes straight to `s.workspace(ctx)` and an upstream `createAccessKey` call. It never asks `Available`. For a workspace outside the beta the upstream call cannot succeed, and the failure surfaces as the generic `internal error`. `Update` and `Delete` are built the same way — `graphql.go:61-68` wires all three with no availability check.

## Fix

Gate the three write verbs on `Available` and return a named refusal — the codebase's own idiom for a capability the caller does not have, rather than a 500-class error. Decide and state which class it is: this is "the feature is not enabled for this workspace", which is nearer `forbidden` than `not found`, and it should not become an existence oracle for the beta workspace's identity.

Worth checking in the same change whether `routerOverview` has the same hole — it authorizes on `RelCanViewSensitive` and calls `s.keys(ctx)` without consulting `Available` either, though it was not probed live.

Estimate: ~25m including the three verbs, the error class decision, and a test that an unavailable workspace gets the named refusal rather than `internal error`.

## Also checked this pass, and found correct

- **IP allow-list validation is solid**, which is the useful contrast with `w4/115`'s unvalidated Postgres parameters. Across `setServiceIpAllowList`:
  - `not-a-cidr` → `bad request: "not-a-cidr" is not a valid CIDR`
  - `203.0.113.0/99` → same named refusal
  - `203.0.113.7` (bare IP, no mask) → same named refusal
  - `203.0.113.0/24`, `2001:db8::/32` (IPv6), `203.0.113.5/24` (legal but non-canonical, host bits set) and `[]` → all accepted
  
  So the CIDR surface validates precisely and names the offending value. `w4/115`'s parameter surface is the outlier among the config-write paths probed so far, not the norm.
- **`routerAvailable` itself is honest** — it returns `false` for a non-beta workspace rather than erroring, and the dashboard uses it to hide the feature.
