## Objective

`http_requests` is built as `sum(increase(traefik_service_requests_total[Ns]))`
(`lego/backend/internal/metrics/source.go:436`), and Prometheus `increase()`
extrapolates partial-window counters — so 25 bursty requests read back 27.8 in
one query alignment and 6.67 in another. Make the metric return the number of
requests in each bucket for any traffic shape, restoring the m108 DoD: N driven
requests sum to N ±1 for any alignment, reconciling with the access-log line
count.

## Context

- Live probe, 2026-09-20 (production, `srv-dansb83s0ils73bgpaj0`, since
  deleted). 25 `curl` GETs at ~11:41–11:42Z; the access log shows exactly them:
  `GET /v1/logs?resource=<id>&type=request&limit=100` →
  `nlogs: 25, hasMore: False`. The same Traefik origin, two consumers disagree:
  - `GET /v1/metrics/http-requests?resource=<id>&startTime=11:23:39Z&endTime=11:43:39Z&resolutionSeconds=60`
    → `[{"labels":[resource],"unit":"count","values":[{"11:42:54Z",6.666666666666666},{"11:43:54Z",0}]}]`
  - Same read with `aggregateBy=statusCode` over a shifted window →
    `[{"labels":[resource,statusCode=200],"values":[{"11:42:19Z",27.795666666666666},{"11:43:19Z",0},{"11:44:19Z",0}]}]`
  - Both non-integer, mutually inconsistent, neither within ±1 of 25.
- Root cause: `promQueryFor` in `lego/backend/internal/metrics/source.go:409`
  renders `sumIncrease(counters.requests, …)` =
  `sum(increase(traefik_service_requests_total[60s]))` (`source.go:436`). The
  `[Ns]`==step comment at `source.go:405-408` assumes one bucket covers exactly
  one sample, but `increase()` scales the first-to-last delta by
  window/sampled-duration, so a burst occupying part of the bucket is
  extrapolated up or down depending on where the samples land.
- The exact primitive already exists: `lokiRequestQueryFor` renders
  `count_over_time(…[60s])` (`lego/backend/internal/metrics/lokisource.go:116`)
  behind the same `RequestMetricsSource` signature — but today it is reached
  only for host/path-filtered reads (`service.go:320-330`), while the
  unfiltered read goes to Prometheus. Either route the unfiltered
  `http_requests` read through the exact-count path, or replace `increase()`
  with an extrapolation-free PromQL formulation. Target behavior is the m108
  bullet (N in, N ±1 out, any alignment), not merely "the two alignments
  agree" — normalizing onto one wrong variant must fail review.
- Blast radius: `promQueryFor` also serves `http_latency`
  (`histogram_quantile` over `sumRate` — percentile math legitimately needs a
  rate; out of scope) and bandwidth (`egressquery.SumIncreases`,
  `source.go:413` — same extrapolation caveat; t002 verifies it live rather
  than assuming). REST, GraphQL, and MCP share the one `RequestMetrics` verb,
  so one fix covers all three surfaces plus the dashboard chart.

## Steps

1. Reproduce live: drive N curls at a fixture, confirm the alignment-dependent
   misread on REST before changing anything.
2. Change the `http_requests` query construction so unfiltered reads return
   exact per-bucket counts (Loki `count_over_time` routing or an
   extrapolation-free PromQL form — whichever keeps the m108 steady-traffic
   behavior and the static-site router-scoped attribution from w4/m113).
3. Re-run the DoD probes: three alignments, REST + GraphQL + MCP, access-log
   reconciliation.
