## Root cause and bounded fix

- `dashboard/src/features/deploys/hooks/use-deploy-logs.ts:181` combines older pages plus current build/predeploy/app pages; build precedes predeploy for this first-page collision. At lines 190–191 it sorts equal timestamps and deduplicates before the caller selects a type.
- `dashboard/src/features/logs/lib/map.ts:26` defines identity as millisecond timestamp + instance + message, deliberately excluding type. At line 123, `dedupeLogLines` keeps the first occurrence. Both captured records therefore have the same key; the retained record is `type=build`. This is our own merge logic, not an inferred Apollo serializer failure: both complete typed responses contain the correct record. The observed single All-logs marker is predicted by this mechanism, not evidence that the predeploy request failed.
- `dashboard/src/features/deploys/components/deploy-log-panel.tsx:49` defines Application as non-build (including predeploy); lines 125–129 apply that predicate to the already collapsed array, discarding the retained build copy. The erased predeploy provenance cannot satisfy that predicate.
- `deploy-detail-page.tsx:99` uses **createdAt**, not startedAt, as the default log-window lower bound. The marker at `02:54:41.610280087Z` predates the projected deploy startedAt `02:54:43.627934Z`, but is inside the createdAt window. Do not “fix” this by widening timing bounds: All logs already contains it.

**Target:** a line returned by both build and predeploy appears once in All, once in Build, and once in Application. Application-only rows stay out of Build; build-only rows stay out of Application. Preserve each bucket's text/instance filtering and one-copy rendering.

Prefer a deploy-local change that applies the selected source bucket **before cross-source deduplication**, retaining the three existing query/page states and filtering the live build leg consistently. Passing the choice into the deploy merge must not include it in backend query variables/paging reset identity: a client-side bucket switch should retain loaded older pages. Alternatively retain source membership through the deploy-specific merge and let the consumer predicate use that membership. Do not merely reverse the input order (that trades a broken Application bucket for a broken Build bucket), include `type` globally in the identity (that duplicates All), remove durable build attribution, relabel all build lines, or modify API mixed-type validation.

**Counted boundary:** one production `useDeployLogs` caller (DeployLogPanel), one panel mount (DeployDetailPage), two detail route mounts (`services.$serviceId.deploys.$deployId.tsx:29`, `static.$serviceId.deploys.$deployId.tsx:25`). Shared `dedupeLogLines` has six production call sites across four modules: map/mergeLogLines (1), use-older-log-pages (1), use-log-history (2), use-deploy-logs (2); keep the common primitive unchanged if using the source-selection approach. Service route covers web/private/worker/cron; pre-deploy applies to web/private/worker, while static/cron do not run that step. Only Free web was live-probed. Postgres and Key Value use their own viewers, not DeployDetailPage.

**Pre-settle and adjacent cases:** a live predeploy copy can arrive before its durable build twin; later build ingestion must not make a selected Application row disappear. Preserve loading/error states, authorization/not-found behavior, absent durable-store explanation, and actual empty results. No REST/GraphQL/MCP schema or error-class changes. When only one source exists, retain the existing bucket semantics; this finding does not promise Application output after the live predeploy pod is TTL-reaped. Never mix predeploy with other types in a single backend request.
