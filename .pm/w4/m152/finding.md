# Finding — stable pages freeze compact ages and cron countdowns

**Severity:** minor. The cron scheduler and stored timestamps are correct; relative labels can misstate recency or time remaining until another render. This is a presentation defect, not evidence of a missed run. **Estimate:** 30m clock fix + 30m shared-consumer verification, with parity/quality/behavioral checks bringing the milestone to about 2h 5m.

## Root cause and intended scope

- **Producer and types are correct:** `lego/backend/internal/apps/service.go:437–442,1063,1129,1276–1285` projects last success from run history and computes the next UTC schedule instant. `apps/graphql.go:387–390`, `apps/render.go:130–131,369–370,410–411` carry those instants; MCP `get_service` uses the same service projection. No wire-shape change is needed. `dashboard/src/features/services/types.ts:90–101` permits the existing nullable strings; `lib/status.ts:60–62` preserves them.
- **Consumer lacks a clock input:** `dashboard/src/common/components/relative-time.tsx:8–23,25–47` accepts the source instant, but subscribes to no changing clock. Its `format(value)` executes only on render. `features/services/lib/format.ts:25–46,51–68` already supports an injected `now`; otherwise it samples `Date.now()` once per call. `service-detail-header.tsx:223,232,532` uses the wrapper for Last run, Next run and Created.
- **Polling is not a clock subscription:** `features/services/hooks/use-server.ts:49–71` uses cache-first data, memoizes the normalized view by `data`, and polls on the shared cadence. `common/apollo/default-options.ts:23` deliberately disables network-status notifications (w1/m153's protection for dialogs, drafts and focus).
- **Pinned framework path was opened:** Apollo **4.1.3**, React **19.2.3** (installed package metadata; network requests also identify Apollo 4.1.3). `dashboard/node_modules/@apollo/client/core/ObservableQuery.js:126–155` suppresses deeply equal results/variables and suppressed network-status emissions; `react/hooks/useQuery.js:115–139` likewise avoids store-change notification for equal results/variables. This expected Apollo behavior means an unchanged poll cannot be relied on to rerender a time label.
- **Verified control mechanism:** `common/hooks/use-now.ts:14–20` owns a one-minute state timer with cleanup; `features/deploys/components/deploys-list-page.tsx:106,178–182` passes that changing clock into `formatTimeAgo`. The deploy list is below the header's route outlet, while `service-detail-layout.tsx:43–45` supplies the header from its own queries. A child timer does not refresh the header. Exhaustive production `useNow(` search found **one caller**, that deploy-list page, plus the hook definition.
- **Fix scope:** global correction of compact relative-time consumers, with shared cadence/reuse and bounded lifecycle cost. Reuse the existing clock behavior where appropriate; do not add an interval for every rendered row, a new API poll, or `notifyOnNetworkStatusChange: true` to force renders. t002 decides the smallest shared arrangement after auditing all callers. Keep scalar strings at API boundaries and all existing auth/error/loading behavior.

Before a query settles, retain the existing initial skeleton/fallback and cache-first rendering contract; clock ticks must never claim that cached facts were refetched. Missing or invalid values keep the caller's fallback, without an invalid `datetime`. Hidden-tab resume, exact bucket boundaries, negative/past future timestamps and unmount cleanup need explicit verification. Forbidden/unauthenticated/not-found/timeout classes stay on the current route error paths; changing time presentation confers no additional access or existence information.
