## Objective

Deleting a project currently `DELETE FROM projects` cascades away its child environments while member App/Database/KeyValue CRs keep `spec.environmentIPAllowList` forever — a deny-all environment leaves its members blocked until someone clears them by hand. Route the cascade through the environment-clear fan-out so no member CR outlives its environment's rules.

## Context

- `lego/backend/internal/projects/service.go` — Delete verb; the DB cascade removes child environments rows without any member-CR fan-out.
- `lego/backend/internal/environments/service.go` — owns the Delete path that already clears members correctly (m28 covered every environments-owned path, including its own Delete).
- Fix sketch from `.pm/w4/done/025.md` item 2: either projects.Delete enumerates child environments and delegates to the environments Delete path (composition-root wiring), or the store returns the list of cascaded environment ids and that drives the same member-clear fan-out. Pick whichever keeps the projects package ignorant of environments internals.

## Steps

1. Choose the wiring (delegate vs store-returned cascaded ids) consistent with the composition root's existing dependency direction; record the choice in the code where it lives.
2. Implement: project delete ⇒ every child environment's members lose their `spec.environmentIPAllowList` stamp (Apps via projector, DBs/KVs via their services' existing clear paths).
3. Test: project with an environment holding non-empty rules (including a deny-all case) + one member of each kind ⇒ delete project ⇒ all three member CRs carry no environment layer.
