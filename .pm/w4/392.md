# 392 — A missing or inaccessible `ghcr.io` image still stays "In Progress" for the full 15 minutes: GHCR's `403 Forbidden` is not in w4/162's permanent-pull answers

Why: w4/162 made a typo'd image tag fail in about 90 s instead of 15 minutes. That fix only knows docker.io's spellings. GHCR, the second most common registry, answers every missing, private or wrong-credential pull with `403 Forbidden` at its token endpoint. Those deploys still sit "In Progress" for the whole rollout budget.

**Severity:** minor (a failure that is already certain is reported 13 minutes late; the cause text is shown meanwhile, and nothing is lost). **Estimate:** ~30m. **Source:** live `/qa-find-bugs w4` loop run v6n2, 2026-10-23 UTC (`muse.env`, `bex-canary`, pin `b3cd5bc74de8`). Fixtures:

- Registry credential `qa-20261022-v6n2-cred` (`rgc-dbdcc3i8ohec73f9fv5g`, host `ghcr.io`, a fake token), added in Settings → Registry Credentials.
- Free image services `qa-20261022-v6n2-pull` (`srv-dbdcc7q8ohec73f9fv70`, with that credential) and `qa-20261022-v6n2-anon` (`srv-dbdcfl3op2ec73c1ojhg`, no credential), both on `ghcr.io/bex-co/qa-v6n2-missing:1`.

All were deleted (`GET` → `404`); session revoked.

## Probe

- Both first deploys (`dep-dbdcc7q8ohec73f9fv7g`, `dep-dbdcfl3op2ec73c1oji0`) read `update_in_progress`, polled every 30 s, with the stall reason `image pull is failing: Back-off pulling image "ghcr.io/bex-co/qa-v6n2-missing:1": ErrImagePull: … failed to authorize: failed to fetch oauth token: unexpected status from GET request to https://ghcr.io/token?scope=repository%3Abex-co%2Fqa-v6n2-missing%3Apull&service=ghcr.io: 403 Forbidden`.
- `dep-dbdcc7q8ohec73f9fv7g` started `02:27:46.72Z` and closed `update_failed` at `02:42:49.36Z`, **902 s** later, which is the full rollout budget. w4/162's live check closed a docker.io NotFound tag in 108 s.
- GHCR's answer is the same with or without a credential (re-runnable from anywhere):
  - `curl -s -o /dev/null -w "%{http_code}" "https://ghcr.io/token?scope=repository:bex-co/qa-v6n2-missing:pull&service=ghcr.io"` → `403`
  - The same with `-u qa-v6n2:not-a-real-token-v6n2` → `403`

## Root cause

`lego/operator/internal/predeploy/predeploy.go:320-339` `PermanentPullFailure` matches only `code = notfound`, `manifest unknown`, `manifest_unknown`, `: not found`, `404 not found`, `unauthorized`, `authentication required`, `pull access denied`, `repository does not exist` and `insufficient_scope`. GHCR's `… : 403 Forbidden` matches none of them, so the pull counts as transient and the rollout runs to its deadline.

Callers (exhaustive, `grep -rn 'PermanentPullFailure(' lego/operator`): the rollout path `controller/app_controller.go:3621` (`permanentRolloutPullFailure`) and the pre-deploy Job path `predeploy.go:307`. Both inherit the fix.

## Fix (target behavior)

- Treat a registry token or authorization answer of `403 forbidden` (and the `denied:` error code registries use for the same refusal) as permanent after the existing 90 s `imagePullGrace`, exactly like `unauthorized`.
- Keep rate limits (`429` / `toomanyrequests`) and 5xx transient.
- Table tests with this run's literal GHCR message, plus regression tests keeping the docker.io NotFound / `unauthorized` cases and a `toomanyrequests` transient control.

**Unverified:** other registries' 403 spellings (GitLab, ECR, GAR), and whether a pre-deploy Job on a GHCR image behaves the same. It shares the classifier, so it should, but that was not probed.
