## Objective

A database's header menu and Info actions, and a Key Value's Info actions, gate Suspend and Resume on `databaseActions` / `keyValueActions` as the service surfaces gate on `serverActions`. With t001's change, a Developer in a protected environment then sees both disabled with t002's admin-only reason, and an Admin and an unprotected Developer keep them.

## Context

- Today they gate on the workspace `can_operate` only (`useCapabilities`): `dashboard/src/features/databases/components/database-row-actions.tsx` (the `lifecycle` branch: Suspend, Resume and Restart), `database-danger-actions.tsx` and `features/keyvalue/components/key-value-danger-actions.tsx`. A datastore view has no environment, so the projection is the only source of the protection answer. `key-value-row-actions.tsx` has no lifecycle items.
- `features/capabilities/hooks/use-resource-actions.ts` `useProjection` serves `serverActions` and `deployActions`. `databaseActions` and `keyValueActions` take the same `id` + `ownerId` (`gqlutil.OwnedIDVerb`, `lego/backend/internal/postgres/graphql.go:525`, `keyvalue/graphql.go:139`). Add their queries to `features/capabilities/api/resource-actions.graphql`, then run `yarn codegen`.
- Restart stays on `can_operate`: it is not a restricted verb (`core.ProtectedVerbRestricted`). The Postgres projection's `restart` row says the same.
- Delete stays on `can_create` here. A protected Delete is t005's to walk.
- The service components show the pattern to follow, including the dispatch recheck (`useBoundActionConfirm`, w4/m159). Reuse `gateAction`/`gateReason` rather than a datastore copy.

## Steps

1. Add `useDatabaseActions` / `useKeyValueActions` on `useProjection`.
2. Gate Suspend and Resume in the three components on the decision, with the same disabled-with-reason presentation as now. Keep the existing confirm dialogs.
3. Update their tests (`features/databases/components/__tests__/database-row-actions.test.tsx`, `database-danger-actions.test.tsx`, `features/keyvalue/components/__tests__/key-value-danger-actions.test.tsx`). For a protected denial, the action is disabled with the admin-only reason and sends nothing. An allowed decision runs it. A checking projection disables it with the checking reason.
