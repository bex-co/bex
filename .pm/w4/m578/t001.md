## Objective

On a member of a protected environment, `serverActions`, `databaseActions` and `keyValueActions` report `suspend` and `resume` as `denied` for a caller who fails the fresh workspace `can_manage` the verbs ask. They use the same predicate and the same check. An Admin there keeps today's answer. A Viewer still pays no protection or admin read.

## Context

- Verbs: apps `setSuspended` → `requireUnprotected` (`lego/backend/internal/apps/protection.go:130-142`: `core.ProtectedVerbRestricted`, `appProtected`, `AuthorizeAppFresh(ctx, core.RelCanManage, a)`). Postgres and Key Value go through `core.RequireEnvironmentAdmin` (`core/confirmation.go`) with `AuthorizeDatabaseFresh` / `AuthorizeKeyValueFresh` on `can_manage` (`postgres/protection.go:28-32`, `keyvalue/protection.go:55-59`).
- Projections: `apps/actioncaps.go:41-107`, `postgres/actioncaps.go:33-63`, `keyvalue/actioncaps.go:32-61`. Each computes `operate` once and composes preconditions only when it is allowed.
- `core.DecideAction` drops the precondition of a decision that is not allowed (`core/decision.go`). `core.ClassifyDecision` maps `ErrForbidden` to `denied`/`insufficient_permission`, an insufficient-scope error to `missing_oauth_scope`, and anything else to `unavailable`.
- ADR032:96 says the projection "still reports `protected_confirmation_required` for suspend as a hint that a client should confirm with its user". Keep that hint for an Admin.

## Steps

1. Add one core helper next to `RequireEnvironmentAdmin`. It projects a restricted verb's guard: given `operate`, a protection predicate and the admin check, it returns `operate` on an unprotected member, and on a protected one the admin check's decision. Neither read runs when `operate` is not allowed. A failed protection read reads as `unavailable`, never as a role refusal.
2. Give the admin refusal its own bounded reason in `core/decision.go` (for example `protected_environment_admin_required`), so t002 can show Render's copy rather than the generic role text. An insufficient-scope or outage answer keeps its own reason. The dashboard and mobile normalizers read an unknown reason as generic, so nothing breaks before t002.
3. Use it in all three projections for both `suspend` and `resume`. Both are restricted verbs, and they share one protection read and one fresh check per projection. Suspend's precondition stays state first, then the protection hint. Resume's stays state first, then billing.
4. Rewrite `TestActionCapabilities_SuspendPreconditionMatchesGuard` (`apps/actioncaps_test.go:47-90`, today it pins the mismatch) and add the same test to `postgres/actioncaps_test.go` and `keyvalue/actioncaps_test.go`. Each is a table over {Admin, Developer} × {suspend, resume} × {protected, unprotected} that runs the projection and the verb and asserts they agree (`asAdmin` / `asNonAdmin`, `apps/protection_test.go:56-57`; find or add the datastore equivalents). Keep `TestActionCapabilities_ViewerDeniedWithoutPreconditionLeak`, and make it assert that a Viewer causes no protection read.
5. Amend ADR032:96: a non-Admin now reads suspend and resume as denied with the new reason, and an Admin keeps the suspend hint.
