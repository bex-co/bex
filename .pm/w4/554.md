# 554 — The env-group link and unlink copy says a service with auto-deploy off picks the change up with its next deploy, but an image-backed service (which REST reports as `autoDeploy: "no"`) deploys it immediately

Why: an image-backed service shows no auto-deploy setting at all, and REST calls it off. So the copy tells its owner that unlinking a group waits for their next deploy, when it restarts the service right away. For anyone holding a change for a maintenance window, that is the wrong promise.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 38, 2026-11-10 20:04–20:14 UTC (`muse.env`, workspace `bex-canary`, pin `c12cd57facb1`). **Minor** (the copy contradicts the behavior). ~25m.
- **Fixtures** (both deleted, GET 404):
  - Free image service `qa-20261110-eg38` (`srv-dbpnhcdme2kc73f2leb0`) from `docker.io/mendhak/http-https-echo:35`, with `ECHO_INCLUDE_ENV_VARS=1` and its own `QA_OWN=own-1`. REST reports `autoDeploy: "no"`, `autoDeployTrigger: "off"`.
  - Group `qa-20261110-eg38-grp` (`evg-dbpni8tme2kc73f2lecg`) with `QA_G=g-1` and `QA_OWN=grp-own`.
- **Probes:**
  - **Linked from the create dialog.** This started deploy `dep-dbpni8tme2kc73f2led0` (trigger `service_updated`), live at 20:07:00. The process served `QA_G=g-1` and `QA_OWN=own-1`, so the service's own value wins, as on Render.
  - **Edited in the group:** `QA_G=g-2`, then "Save, rebuild, and deploy". `dep-dbpnjis5ngvc73e8u2cg` was live at 20:09:30, and the process served `g-2`.
  - **Unlinked from the group page.** The toast read: "Service unlinked — The service's configuration changed. With auto-deploy on it deploys the change now; with it off it picks it up with its next deploy."
    - Yet `dep-dbpnlftme2kc73f2lefg` (`service_updated`) was created at 20:12:54 and live at 20:13:30.
    - The Linked Services card states the same rule.
- **Root cause:**
  - **By design, the auto-deploy gate applies only to repo-backed services.** [ADR013](../../docs/ADR013-secrets.md) line 103: "The gate applies only to repo-backed services: bex defaults `spec.autoDeploy` to false for an image-backed service because there is no branch to watch". See also w2/m94.
  - **The copy written by w4/390 states only the repo-backed rule.**
    - `dashboard/src/features/env-groups/locales/en.ts:409-412`: `envGroups.servicesDescription`, rendered at `components/linked-services-card.tsx:67`.
    - `en.ts:490-493`: `envGroups.linkChangeNote`, used by both toasts in `hooks/use-env-groups.ts:310-312` and `:330-332`. That hook also serves Link and Unlink on the service's Environment tab.
    - The zh counterparts are `zh.ts:397-399` and `:475-476`.
  - **The toast can't tell which outcome happened.** The link and unlink GraphQL mutations return a bare Boolean (`lego/backend/internal/envgroups/graphql.go:378-393`), so it can't distinguish a staged link from a deployed one.
- **Fix (target behavior):**
  - The card and both toasts say that a repo-backed service with auto-deploy off picks the change up with its next deploy. Every other service, whether auto-deploy is on or it is image-backed, deploys it now. In en and zh.
  - Optionally, the toast names the actual outcome for its one target service, using that service's source type.
  - Update `locales/__tests__/redeploy-copy.test.ts` to assert the image-backed clause.
  - No backend change.
