# The API-key "created" dialog still says `Optional scope=bex.read bex.write bex.sensitive`, but `w4/112` made Hydra refuse every one of them

Why: a user who follows the dialog's own instructions to mint a least-privilege token gets `invalid_scope` from `oauth.bex.co`, and the copy keeps implying that read-only machine keys exist. By design (`w4/112`, ADR012), a machine key carries no capability scopes and holds full workspace authority, including connection strings.

Found live, `/qa-find-bugs` pass 172, 2026-09-26 (w4-targeted, `muse.env` credentials), account → Access credentials. Fixture: API key `qa-20260926-key`, created and revoked the same pass. The two existing keys (`m43-verify-temp`, `tp-ms-fish`) were not touched.

- **Repro:** Settings → Access credentials → Create API key. The "API key created" dialog reads: _"Exchange it at https://oauth.bex.co/oauth2/token: grant_type=client_credentials&client_id=…&client_secret=… **Optional scope=bex.read bex.write bex.sensitive.** Use the returned access_token as Authorization: Bearer."_
- **Probe** (`curl -X POST https://oauth.bex.co/oauth2/token -d grant_type=client_credentials -d client_id=… -d client_secret=… [--data-urlencode scope=…]`):

  | `scope`                          | result                                                                                                  |
  | -------------------------------- | ------------------------------------------------------------------------------------------------------- |
  | _(omitted)_                      | token issued, `scope: ""`, `expires_in: 899`                                                            |
  | `bex.read`                       | `invalid_scope` — "The OAuth 2.0 Client is not allowed to request scope 'bex.read'."                    |
  | `bex.read bex.write bex.sensitive` | `invalid_scope`                                                                                       |
  | `bex.write` / `bex.sensitive`    | `invalid_scope`                                                                                         |
  | `openid`                         | token issued, `scope: "openid"`                                                                         |

  The scope-less token then returned 200 on `GET /v1/services` **and** on `GET /v1/postgres/dpg-d9nqg95cavls73fp8m20/connection-info` (password present), which is full authority, as designed.
- **Root cause:** `lego/backend/internal/apikeys/service.go:512-529` (the `hydraClient.Scope` doc comment) records the deliberate `w4/112` reversal of `w4/m105`: minted keys carry **no** scope, so Hydra refuses a capability request instead of echoing a restriction the platform would not enforce. The m105-era copy survived. `dashboard/src/features/api-keys/locales/en.ts:122` (and the zh twin) still advertise the scopes, and `docs/ADR012-auth.md:186` still states "Minted keys grant the advertised capability scopes (w4/m105)".
- **Fix:** drop the `Optional scope=…` sentence (en + zh) and say plainly that a key acts with full workspace authority, so it should be treated like a password and scoped by workspace, not by capability. Correct ADR012:186 to describe the `w4/112` behavior. `grep -rn 'bex.read bex.write bex.sensitive' dashboard/src docs` at filing hit exactly those three files (en, zh, ADR012). Re-run it at fix time.
- **Checked and correct this pass:** the secret is shown once. Revoking the key immediately invalidated its already-issued access token (`GET /v1/services` → 401) and further exchanges (`invalid_client`), matching the confirm dialog's "stop working immediately".

Estimate: ~20m.
