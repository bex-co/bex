# 500 — `GET /v1/services?environmentId=<env>` without `ownerId` returns `[]` when the environment is in another of the caller's workspaces

Why: the environment id already names its workspace, yet a Render-shaped client that filters by environment gets a confident empty list unless it repeats `ownerId`. The dashboard (which passes the workspace) shows the service, so REST and the UI disagree about what the environment contains.

**Severity:** major (silent wrong result on a REST filter) · **Estimate:** 45m · **Worker:** worker4 · **Status:** todo

- **Source:** live `/qa-find-bugs w4`, production, 2026-11-05 18:12–18:22 UTC, round 91. QA account; its default workspace is `bex` and the fixtures were in `bex-canary`. Prod pin `cc3c51e12952`; research on main `d2b00c61e`.
- **Probe (from the dashboard page, `fetch(…,{credentials:'include'})`):**
  1. `POST /v1/projects {name:"qa-20261105-proj91", ownerId:"tea-daif693dqjvc73e7as3g", environments:[{name:"staging"},{name:"production"}]}` → 201. It returned `prj-dbmce6srv9ic73d23et0` with environments `evm-dbmce6srv9ic73d23etg` (staging) and `…eu0` (production).
  2. In the dashboard New Web Service wizard: Existing Image `docker.io/traefik/whoami:v1.10`, Project `qa-20261105-proj91`, Environment `staging`, then Deploy. The service `srv-dbmcehkrv9ic73d23evg` went Live.

  3. List probes:

     - `GET /v1/services?limit=100` → 200, the caller's default-workspace (`bex`) services only
- **Root cause:** `lego/backend/internal/apps/rest.go:841-878`.
  - The handler lists `core.ListOwners(ctx, owners, s.List)` first. With no `ownerId`, that is `s.List(ctx, "")`: the caller's default workspace (`apps/service.go:1381-1393`, `core/pagination.go:91-94`).
  - Only afterwards does it filter that slice by `environmentId` in memory (`:876`). An environment in any other workspace can never match.
  - Omitted `ownerId` → default workspace is a documented bex rule (ADR018 lines 84, 262; w4/475 for projects). This note is about the filter that names a resource whose workspace is known.
- **Fix:**
  - Target: when `ownerId` is omitted and `environmentId` is given, the list resolves the owner(s) from those environments, as by-id verbs resolve a resource's own workspace (w4/m134, m169, m172 precedent). Authorize `can_view` there and list only those workspaces.
  - An environment the caller cannot view, or that does not exist, contributes no workspace. The answer stays `[]` either way, so the fix opens no existence oracle.
  - An explicit `ownerId` keeps today's behavior (intersection).
  - The dashboard is unaffected (it passes the workspace).
- **Blast radius:** the same list-then-filter shape exists in
  - `postgres/rest.go:99`
  - `keyvalue/rest.go:312`
  - `envgroups/rest.go:31` (`EnvGroupListFilter.EnvironmentIDs` beside `OwnerIDs`)

  Fix all four with one shared helper (owners-from-environments), plus a regression test each for the default-workspace and explicit-`ownerId` cases.
- **Unverified:**
  - Postgres, Key Value and env-group lists were traced, not probed: the environment held only a service.
  - GraphQL/MCP list arguments were not checked.
  - Whether the Render CLI or Terraform provider sends `environmentId` without `ownerId` was not checked.
  - Render returns services across every workspace the key can access when `ownerId` is omitted (its spec marks `ownerId` optional); its exact answer for an environment filter was not captured.
- **Render:** `GET /v1/services` with `environmentId` returns that environment's services; `ownerId` is an optional filter, not a precondition.
- **Dedupe:**

  - m134/m169/m172 fixed by-id verbs, not list filters.
  - `grep -ril "environmentId" .pm` found no open item on list scoping. Not in `DO_NOT_DO.md`. No fix on main.
