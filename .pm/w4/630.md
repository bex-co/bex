# 630 — A new service that runs out of memory at startup is reported as an ordinary crash with a port-bind hint, and its `deploy_ended` carries `oomKilled.memoryLimit: ""`

Why: the user is told to check the service logs and the port. The logs are empty, because the kernel killed the process before it printed anything, and the port has nothing to do with it. bex knows the cause: the structured reason on the same event says `oomKilled`. Render names it on the deploy as "Out of memory: Your instance ran out of memory during startup", and its API's `oomKilled.memoryLimit` names the limit. A user moving from Render loses the one clue that says "pick a bigger instance".

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 275, 2026-11-13 08:37–08:45 UTC (`muse.env`, workspace `bex-canary`; pin `4c3c68e6b05b`). **Minor** (misleading diagnosis; nothing is lost). ~50m.
- **Fixture:** Free web service `qa-20261113-r275-oom` (`srv-dbrcomg2er5s73bkil2g`), created by REST with `docker.io/library/python:3.12-alpine` and this Docker Command:

  ```
  python3 -c "import time; a=bytearray(900*1024*1024); print('alloc-r275'); time.sleep(600)"
  ```

  It was deleted afterwards (`DELETE` 204, then `GET` 404).

- **Probe:**
  - Deploy `dep-dbrcomg2er5s73bkil30` → `update_failed` at 08:39:14. Its `failureReason` (REST deploy, the `deploy_ended` event, and what the dashboard's failure line shows) was:

    ```
    container exited shortly after start and is restarting repeatedly (last exit code 137) — check the service logs for the crash output. If the crash is a port bind: the process must listen on $PORT (10000).
    ```

  - The same event's structured reason (`GET /v1/events/evt-20uir4e70ua75014e2ce` and GraphQL `serviceEvents { details { reason { failure { … } } } }` agree):

    ```
    {"failure": {"earlyExit": true, "evicted": false, "nonZeroExit": 137, "oomKilled": {"memoryLimit": ""}}}
    ```

  - `GET /v1/logs?resource=srv-dbrcomg2er5s73bkil2g&startTime=2026-11-13T08:30:00Z` → `"logs":[]`. The "crash output" the message points to does not exist.
  - **Control:** sibling `qa-20261113-r275-exit` (`sys.exit(3)`) read `last exit code 3`, `reason.failure {earlyExit, nonZeroExit: 3}` and logged `boom-r275`. The crash wording fits that case.
- **Render:**
  - [Troubleshooting deploys](https://render.com/docs/troubleshooting-deploys), read 2026-11-13, startup failures table: `Out of memory`, "Your instance ran out of memory during startup", listed separately from `Exited with status <N>`.
  - The pinned OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`, the `failureReason` shared by Deploy Ended and Server Failed) has `oomKilled: {memoryLimit: string}`, with `memoryLimit` required.
- **Root cause:**
  1. **Sentence.** `crashLoopMessage` (`lego/operator/internal/controller/app_controller.go:6303-6317`) words every crash loop the same way: the exit code plus the port-bind hint. It never reads `LastTerminationState.Terminated.Reason == "OOMKilled"`, which `recordRolloutExit` (`:4086-4089`) already uses to set `rolloutFailure.oomKilled`.
     - It has 2 callers: `permanentRolloutCrash` (`:4181`, the early settle and the terminal text) and the in-flight stall diagnosis (`:6258`).
     - The pre-deploy path already has an OOM sentence, `DeployReasonPreDeployOutOfMemory` (`lego/types/v1alpha1/deploy_reasons.go:74`, `:183`). The service container does not.
  2. **`memoryLimit`.** `failureFromEnd` (`lego/backend/internal/events/service.go:750-765`) builds `OOMKilledInfo{}` with no limit. `withMemoryLimit` (`:710-717`) fills it only when `ev.Type == TypeServerFailed`. Both of its callers run it:
     - the service-feed list (`:1086`);
     - the by-id read (`:1201-1207`), which also gates on `server_failed`.

     So a `deploy_ended` OOM always says `""`. That value is only right for a cron run, whose plan is unknown (`:699-702`).
- **Fix (target behavior):**
  - **Sentence.** When the app container's last termination reason is `OOMKilled`, the crash diagnosis (in-flight and terminal) reads, for example: "the instance ran out of memory during startup (512Mi limit on its instance type; exit code 137) — reduce memory use or choose a larger instance type". There is no port-bind hint and no "check the service logs" advice.
    - Make it a stable template in `deploy_reasons.go`, beside `pre_deploy_out_of_memory`, with `{memory}` and `{code}` params, so GraphQL `failureReasonTemplate` and the dashboard (en and zh locales) word it, as w4/566 does for the others.
    - The operator reads the limit with `tiers.Compute.Resources(app.Spec.Tier)`, the same source `resourcesForTier` (`:2155`) uses.
  - **`memoryLimit`.** A `deploy_ended` whose `reason.failure.oomKilled` is set gets `memoryLimit` from the service's plan, exactly as `server_failed` does ("512Mi" on Free). Apply it on both reads (`:1086`, `:1201-1207`). REST, GraphQL and MCP all read this one `Details`, so they move together.
    - The webhook payload carries no reason, so it is unaffected.
    - Cron runs keep `""` (their plan is unknown).
- **Blast radius:**
  - Both `crashLoopMessage` callers: web, private and worker rollouts, first or over a serving release.
  - The exit-code crash wording (`last exit code N` plus the port hint) must stay byte-identical for a non-OOM crash. Keep `TestPermanentStartupCrashSettlesBeforeRolloutDeadline` and `port_detect_test.go:196` (no `$PORT` hint once the port is detected) green.
  - `withMemoryLimit` has 2 callers. `server_failed`'s existing fill (w8/m158) is unchanged.
