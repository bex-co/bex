## Objective

Close two more ways the Key Value status disagrees with the store, both observed live in pass 166 (2026-09-25) on throwaway `qa-20260925-kv3` (`red-darm44uuag9c73eddc2g`, Free, public; deleted the same pass).

1. **Resume reads `available` while the store is still down.** Resume was clicked at about 06:14:06Z. UI and GraphQL both reported `available` / `not_suspended` from **06:14:10**, while `redis-cli … GET persist-me` kept failing (`SSL_connect failed`) until **06:14:28**: about 18s of `available` with nothing serving. The data did survive.
2. **A config save never shows the restart in the header.** After switching Persistence Mode to "Snapshot only" (06:15:40Z), GraphQL reported `creating` from 06:15:44 to 06:16:01, and redis was unreachable from about 06:15:42 to 06:16:10. The detail page, **without reload, showed "Available" for the entire window**. (Pass 159's header did flip, because a baseline poll happened to land inside that window.)

## Context

- **(1) root cause:** the operator marks a suspended store `KVPhaseReady` with reason `Suspended` (`lego/operator/internal/controller/keyvalue_controller.go:828-834`). Clearing `spec.suspended` leaves that stale `Ready` in place until the next reconcile observes the new generation, and `kvStatus` maps it to `available`. t001's "stale Ready (condition `ObservedGeneration < Generation`) → not available" rule covers this if it is applied before the `suspended` check drops out. Add resume as an explicit case in t001's table test, and decide with t004 whether the right value is `config_restart` or `creating` (Render's `databaseStatus` has no "resuming").
- **(2) root cause:** `dashboard/src/features/keyvalue/hooks/use-key-value.ts:37-41` polls fast only while `isConverging(keyValue)`, which is false once settled, so it falls back to the baseline cadence. `use-set-key-value-persistence-mode.ts:46` and `use-set-key-value-maxmemory-policy.ts:59` refetch only their own section query, never the detail query. A ~25s restart can fall entirely between baseline polls.

## Acceptance criteria

- [ ] After Resume, status is not `available` until the pod serves (re-run the redis poll above).
- [ ] After a maxmemory or persistence save, the detail header polls fast (for example `eagerRefetch` on the detail query) and shows t003's "Restarting" for the duration, then settles.
- [ ] Both cases are covered by tests (backend table row for resume; dashboard hook test for post-save fast polling).
