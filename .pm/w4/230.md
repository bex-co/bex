# Cron history Load more cannot recover older runs after a new arrival

Why: someone reviewing a cron job loses access to retained older executions after a new run arrives; successful Load more requests keep returning rows the dashboard hides until reload.

- **Severity:** major — the run-history read cannot complete normally without reload. The API retains the runs; no execution failure or stored-history loss is claimed.
- **Estimate:** 55m: hook correction 20m, shared caller/state audit 10m, real-cache recovery regression 20m, live acceptance 5m. One bounded inbox fix.
- **Source:** continuous `$qa-find-bugs w4`, functional hosting pass a40, 2026-10-10 UTC / America/Los_Angeles, using `muse.env` through the login helper.
- **Goal:** dependable hosting observability under [ADR008](../../docs/ADR008-vision.md) and [ADR038](../../docs/ADR038-cron-jobs.md). Retained run history must remain readable while the dashboard refreshes it; this closes a specific recovery guarantee left incomplete by [w4/138](done/138.md).

## Live reproduction and controls

Owned Free image cron `qa-20261010-loop-a40-cron`, `srv-db4v8sep9h1c73df3lgg`, public image `docker.io/library/busybox:1.37`; canonical page `https://dashboard.bex.co/services/srv-db4v8sep9h1c73df3lgg/events`. The schedule was kept at a future annual instant (`0 1 1 1 *`); eight runs were triggered sequentially through the normal confirmed UI, waiting for each to settle. No interception, artificial network failures, concurrent run flood, or paid plan was used.

1. Build at least six retained successful runs. Load more once: six rows appear. A subsequent page-one background poll at **08:20:56Z** keeps all six visible.
2. Trigger another run and wait for it to finish. The refreshed first page correctly contains the newest five; Load more is offered again.
3. Click Load more. At **08:22:22Z** its HTTP 200 response contains the older two runs, but the table remains at five rows and the button stays visible. The preceding attempt also remained at five for a 30-second UI wait; that wait timed out because the harness expected the button to disappear. The timeout itself is not the bug.
4. **Fresh-page reproduction:** reload at 08:22:54Z with seven retained runs, then Load more at **08:22:56Z**: seven rows correctly appear and the button disappears. Trigger run eight, which succeeds from 08:23:10Z to 08:23:14Z. At **08:23:19Z**, Load more returns three older runs, yet only five rows render and the button remains.
5. Read all eight retained runs, reload, and click Load more again at **08:23:58Z**: eight rows appear and the button disappears. The failing and recovered Load more transactions have **identical requests, status, and complete responses**. Expand the oldest recovered row: its exact id, successful status, start, finish, and 6-second duration all agree with its detail query.

**Target:** after a shifted first page invalidates the previously appended history, the next successful Load more appends the page fetched from the current cursor, renders each retained run once in API order, and updates exhaustion from that page. For this eight-run capture the result is eight rows and no Load more button. Merely re-enabling the button does not meet the target.

## Root and exact scope

`dashboard/src/features/services/hooks/use-cron-runs.ts:88–94` correctly detects an appended page whose anchor is absent from the refreshed head. At **:190–202**, the hook substitutes `NO_APPENDED` only in the derived `scoped` value and rendered `runs`; it never clears or replaces the underlying `appendedState`. Exhaustive production grep finds **one** `setAppendedState` call, at **:234**, exclusively in Load more.

Load more gets the current visible cursor at **:220**, receives the correct network page at **:224–230**, then its updater reuses raw previous state whenever the service id matches (**:234–245**). `anchorId: carried.anchorId || cursor` preserves the old, now-invalid anchor. In the fresh reproduction the loaded head was `[7,6,5,4,3]`, tail `[2,1]`, anchor 3. Arrival eight shifts the head to `[8,7,6,5,4]`. Fetching after 4 correctly returns `[3,2,1]`, but the updater keeps anchor 3. The next merge still drops the entire append because 3 is absent from the head. `scoped.lastPageSize` resets to null only in the derived result, so **:212–215** keeps claiming more may be loaded. Repeated clicks reuse the same cursor.

The raw carried rows can also accumulate duplicate hidden entries on repeated requests because **:233–240** filters against the rendered head, not the invalid prior tail. This is a source-supported consequence; the live table showed five unique rows, not visible duplicates. Do not file it as a separate observed defect.

The installed, lockfile-pinned **React / React DOM 19.2.3** path was opened: `dashboard/node_modules/react-dom/cjs/react-dom-client.development.js:7934–7936` invokes functional state actions on stored state; **:8789–8805** keeps useMemo's result in its own hook slot. Returning `NO_APPENDED` from useMemo does not reset the useState slot. **Apollo 4.1.3** `core/ApolloClient.js:230–243`, `core/QueryManager.js:220–243,319–332` exposes query results through the promise the hook awaits. The captured success has real data and no errors. `common/apollo/cache.ts:6–13` has no cron pagination policy; the append is local React state. No React/Apollo patch or global cache policy is needed.

`AppendedPages` at **:44–61** already expresses service id, rows, anchor, and last-page size, including a genuinely empty/reset state. No schema widening is required. `CronRunsSection` consumes `runs` at `components/cron-runs-section.tsx:104` and renders them plus the hasMore button at **:199–282**; repairing the stored/carry state clears that consumer's predicate.

Production call counts: **one** `useCronRuns` consumer, **one** `CronRunsSection` mount (`routes/services.$serviceId.events.tsx:352–354`, gated by `isCron`), and **one** `mergeCronRunPages` caller, inside the hook. The repair is local to this cron-history hook. Image-backed and repo-backed cron jobs share it; only the Free image case was exercised. Web, static, worker, private, Postgres, and Key Value do not mount this cron-history table. Their general Events/log/history flows are separate.

Canonical `/services/<cron-id>/events` and legacy `/cron`, `/web`, `/worker`, `/pserv` service aliases preserve subpath/query/hash through `common/lib/render-alias.ts:12–19,58–87`. `/static/<cron-id>/events` is normalized to the compute-service tree by `service-detail-loader.ts:96–100`. Alias behavior is source-traced, not an independent live reproduction.

Backend `apps/graphql.go:1167–1174` calls `Service.ListCronRuns` (`service.go:3594–3603`), which pages the retained status rows. The same verb has **three production adapters**: that GraphQL query, REST `rest.go:1078–1080` (both `/v1/cron-jobs/<id>/runs` and `/v1/services/<id>/runs`), and MCP `mcp.go:738` (`list_cron_job_runs`). Only GraphQL was live-probed here. No backend, operator, REST/MCP contract, or mobile change is requested; run retention remains bounded by the existing ten-entry status limit.

## Bounded fix and acceptance

Normalize the invalid carried append before accepting the next page, or apply invalidation to stored state with an identity-safe transition. A restarted append uses the cursor of the current visible head, clears old rows/anchor/exhaustion, and records the successful new page once. A late response for an obsolete service, cursor, or head must not revive a discarded append; an effect-based reset must not erase a newer successful page. Preserve the existing gap/overlap protection, bounded history, and id dedupe.

Repair the shared-hook recovery and audit its single table consumer in this inbox unit. Extend the existing real `InMemoryCache` + `MockLink` test at `hooks/__tests__/use-cron-runs-freshness.test.tsx:175–219`: it currently stops at `hasMore === true` after a gap and never calls Load more again. Add that second actual query and assert all current retained ids, order, current anchor, and correct exhaustion; another arrival must remain recoverable. Keep unchanged-head tail retention, overlap, pending-to-terminal freshness, failed-refresh last-good rows, service navigation, and late-response isolation controls. A button-only assertion would repeat the missed guarantee.

Live acceptance: on an owned Free cron with seven retained successful runs, fresh-load Events → Load more (seven rows) → Trigger Run and await success → Load more again (eight unique rows, no button), without reload between the arrival and recovery. Repeat once from fresh state. Expand the oldest row and compare its id/status/times with the detail response. Run the affected dashboard tests, lint and typecheck; record actual results. Preserve last-good rows during pending/failed refresh and current loading/empty/error presentation. Existing request failures retain their current handling; do not interpret unavailable data as a successful empty page or introduce unrelated error-taxonomy behavior.
