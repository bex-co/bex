# Every production deploy now fails: the `*.onbex.co` fallback certificate is inside its 30-day renewal window

Why: `deploy.yml` refuses a fallback certificate that expires within 30 days. The served `*.onbex.co` certificate expires 2026-11-30 01:00 UTC, so from 2026-10-31 ~01:00 UTC every deploy fails before the GitOps write-back and nothing reaches production until the certificate is renewed and the secret updated.

- **Source / severity / estimate:** `/qa-find-bugs w4` loop, 2026-10-31 04:45 UTC; **blocker for deploys** (main is red; tenant traffic is unaffected until 2026-11-30), ~20m once credentials are at hand. **Needs the user:** renewal requires the onbex.co DNS/ACME credentials and the local `.env`.
- **Evidence:**
  - Deploy run for `e60b99f25` failed at step `validate onbex.co fallback TLS certificate` (`deploy.yml:480-484`, `bash scripts/onbex-default-tls-secret.sh --validate-only`) with `error: BEX_ONBEX_TLS_CERT expires inside the 30-day minimum validity window` (04:10:32Z).
  - Live: `openssl s_client -connect qa-nonexistent-….onbex.co:443 -servername …` → `subject=CN=*.onbex.co`, `issuer=C=US, O=Let's Encrypt, CN=YE2`, `notAfter=Nov 30 01:00:06 2026 GMT`, SAN `DNS:*.onbex.co`. The `onbex.co` apex itself is served by a separate Google Trust Services certificate (`notAfter=Dec 1 02:01:13 2026`), unaffected.
  - Production is still on `25b99d8a373a`. The queued `e264ddb6a` will fail the same way.
- **Fix (user):**
  1. Re-issue the `*.onbex.co` wildcard (Let's Encrypt via DNS-01, as the current one was).
  2. Point `BEX_ONBEX_TLS_CERT_FILE` / `BEX_ONBEX_TLS_KEY_FILE` in `.env` at the new PEMs.
  3. Run `bash scripts/gh-secrets.sh` to push them to the production environment secrets.
  4. Re-run the latest failed `deploy.yml` (`gh run rerun <id> --failed`) and confirm the step passes.
- **Follow-up (worker):** the certificate has no automated renewal and no repo documentation. Add a short runbook (for example under `docs/`) and an early warning, such as a scheduled check that opens an issue at 45 days. That way the deploy guard is never the first notice.
- **Dedupe:** no open GitHub issue and no `.pm` item covers renewal. `w1/done/131.md` covers the edge canary's classification of TLS failures. `w3/blocked/m173` covers secret scoping, not expiry. No DO_NOT_DO item applies.
- **Not a red-main code fix:** the failure is an expiring credential, not a defect in the push, so `fix(ci)` cannot clear it.
