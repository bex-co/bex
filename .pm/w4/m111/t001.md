## Objective

`NewEnvGroupDialog` lists every workspace service as a link candidate with no scope filtering and no way to set the group's scope, so checking any service that lives in an environment deterministically fails the create with `ENV_GROUP_SERVICE_ENVIRONMENT_MISMATCH`. Add an Environment scope picker (default Workspace) that filters the candidate list to compatible services and passes the scope through creation.

## Context

### The observation (production, 2026-09-17)

Service `qa-20260917-p3-web` (`srv-dalpb5l2r12c73cngju0`) in environment `qa-env`; all five other workspace services environment-less. On `/env-groups`, **New Environment Group**, name `qa-20260917-p3-evg`, check only the QA service → toast:

> Couldn't create qa-20260917-p3-evg
> linked services must have the same Environment scope as the environment group

The dialog offers no scope control at all — the group is silently created workspace-scoped while any checked in-env service guarantees rejection. Workaround verified live: create unlinked → **Manage → Move group** to `qa-env` → link from the detail page (the detail dropdown then correctly lists only the one `qa-env` service, and linking redeploys).

### Root cause (all verified on `main`)

- `dashboard/src/features/env-groups/components/new-env-group-dialog.tsx:426-456` maps over ALL `services` with no filter.
- The create mutation never sends a scope: `dashboard/src/features/env-groups/api/env-groups.graphql:77-83` declares no `$environmentId`, and `use-env-groups.ts:208-216` sends only name/ownerId/envVars/secretFiles/serviceIds.
- The backend already accepts and validates it: `createEnvGroup` takes `environmentId` (`lego/backend/internal/envgroups/graphql.go:244`, `CreateEnvGroupRequest.EnvironmentID` at `service.go:170`, same struct serves REST/MCP), enforced by `prepareCreateServices` (`service.go:554`) → `validateLinkedServiceEnvironments` (`service.go:1280`) → `ENV_GROUP_SERVICE_ENVIRONMENT_MISMATCH` (`service.go:1270`).
- The correct filter pattern already exists in the same feature: `linked-services-card.tsx:45-54` (`serviceEnvironmentId === group.environmentId`), fed by `useEnvGroupScopeIndex()` which returns both `environments` (picker options) and `serviceEnvironmentById` (candidate filter) — `use-env-group-scope-index.ts:89-106`. The `/env-groups` route already calls that hook (`routes/env-groups.tsx:85`).

### Fix shape

- Add an `environmentId` prop (default `null` = Workspace) plus a scope picker row to the dialog, reusing `useEnvGroupScopeIndex` data and the Move dialog's option labels ("Workspace (no Environment)" + env names).
- Filter the checkbox list to services whose `serviceEnvironmentById` matches the picked scope; services outside the scope are hidden or disabled with a reason naming their environment (match the detail page's `incompatibleLink` wording family; update `en` + `zh` locales).
- Thread the picked scope: add `$environmentId` to `CreateEnvGroupDocument`, accept `environmentId` in `CreateEnvGroupInput`/`createGroup`, pass it from the dialog. Unchecking all links with a scope picked still creates the group in that scope (backend supports it — `scope_clone_test.go:51`).
- Scope switch clears now-incompatible checked ids (never submit a stale cross-scope selection).

### Acceptance

- The milestone DoD's "Workspace create filters candidates" and "In-env create works in one step" bullets pass live.
- Existing unlinked workspace creates are byte-identical in behavior (no scope arg sent when Workspace is picked, or explicit null — whichever the backend treats as today; prove with the current passing tests).
- Both locales render the picker + reason strings (no raw `{placeholder}`).
