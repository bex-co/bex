# PostgreSQL upgrades offer and accept targets the operator rejects

Why: a user can select PostgreSQL 14 or 15 for a PostgreSQL 13 database, receive a successful update response, then see Unavailable even though the original database still answers SQL.

**Severity:** major — an offered hosting operation cannot complete and leaves failed desired configuration. **Estimate:** 55m. Functional `$qa-find-bugs w4`, a580/a581, 2026-10-15 UTC; source checked on synced main `42c862ed1`. Filing only.

## Reproduction and controls

1. Create an owned private Free PostgreSQL 13 database. Wait for Available; SQL confirms actual major 13.
2. Open Details → Upgrade, choose PostgreSQL 14, and confirm. The native `UpdateDatabaseVersion(id, version:"14")` returns HTTP 200 with data and no GraphQL errors. The operator then rejects the requested Cluster image change.
3. Reload. The dashboard and GraphQL read show `unavailable`, `statusReasonCode:"ClusterFailed"`, and the generic configuration-rejected reason. The Database CR has desired version 14 and observed version 13.
4. On a second fresh PostgreSQL 13 database, repeat 14 from the desktop page, then reload and choose 15. Both are accepted by bex and rejected by CNPG. Its generation-matched Ready condition names target 15 and says “major upgrades are only supported to version 16 or higher”.

First 14 accepted **12:41:14.115Z**; fresh read **12:42:20.817Z** retained the failure. The original PostgreSQL 13 SQL process still returned all three seeded rows: Unicode, SQL NULL and empty text. A fresh 390px screenshot was inspected and is supplementary evidence.

**Supported-target control:** from that failed desired state, native Upgrade to PostgreSQL 16 was accepted **12:46:38.723Z**, entered `upgrading`, and reached Available/version 16 by **12:48:29.536Z**. SQL at **12:49:02.476Z** reported PostgreSQL 16.15 with every seeded row intact. The second fixture's 14 request at **12:53:52.666Z** and 15 request at **12:54:35.294Z** independently reproduce the unsupported-target class; its PostgreSQL 13 process also still answered SQL.

This establishes a rejected upgrade and misleading availability presentation, not a measured outage or lost data. [Complete native requests, full observable responses, SQL controls and cleanup](evidence/308-postgres-upgrade-target-floor.json) survive the handoff.

## Root cause and bounded fix

- `lego/backend/internal/postgres/service.go:1543–1585` checks known provisioning versions, an upgrade already running, observed version, upward-only ordering and backup prerequisites. It never checks CNPG's minimum upgrade target. `checkUpdate:1407–1452` runs before the patch in both `updatePostgres:1378–1405` and `SetVersion:1592–1605`; add the compatibility check there through the existing shared validator.
- `dashboard/src/features/databases/lib/versions.ts:4–9` reuses the creation catalog and accepts every higher major. Its sole production consumer, `database-version-control.tsx:37–43,109–123`, therefore offers 14/15 when current is 13. Filter upgrade targets to **known versions that are newer than observed and at least 16**. Keep the creation catalog 13–18: its separate consumer is `create-database-dialog.tsx:317`.
- `lego/operator/internal/controller/database_controller.go:815–826,932–960` projects the desired image through CNPG admission; its rejection reaches `dbFail:1583–1586`, which sets Failed. The API's generic ClusterFailed presentation is a downstream effect here. Prevent this invalid write instead of changing shared failure-to-availability mapping.
- The actual framework was checked: lockfile chart **0.29.0** resolves to **CNPG 1.30.0**, matching the live Deployment image. At release commit `4b5e244a7d031f67e025c83c1555e7726ecbbfa1`, [validateImageChange](https://github.com/cloudnative-pg/cloudnative-pg/blob/v1.30.0/internal/webhook/v1/cluster_webhook.go#L1397) rejects a higher major below 16 because its lower-target collation handling is not implemented. Initial creation does not take that upgrade branch. The exact live admission message agrees.

**Target:** an authorized update from observed 13 to 14/15 fails **before any Database patch**, with a named 400 such as `POSTGRES_UPGRADE_TARGET_UNSUPPORTED` and copy identifying supported newer targets. Use `core.NewBadRequestError` (`internal/core/errors.go:239–263,327–333`): REST already maps it to 400, GraphQL carries its code in error extensions, and MCP prefixes the same code in its tool error text. No schema or transport redesign is needed. Keep equal/downgrade handling as `POSTGRES_VERSION_NOT_NEWER`, unknown target as `POSTGRES_VERSION_UNKNOWN`, and the existing unobserved/in-progress/backup refusals. Keep current authorization, protection and billing-check order.

## Shared callers and verification work

Exhaustive production census under `lego/backend`: **7 references to UpdatePostgres, 3 to UpdatePostgresDryRun and 1 to SetVersion, at 10 call sites**. Version-bearing public paths are REST `PATCH /v1/postgres/{id}` (real and dry-run), GraphQL `updateDatabaseVersion`, and MCP `update_postgres` (real and dry-run). The other shared paths are rename, disk autoscaling, publication, allowlist and Insights parameter updates; omitted version patches must remain unchanged. PostgreSQL's sole update-time spec.version assignment is `service.go:1135`.

The dashboard has **one target-helper consumer, one DatabaseVersionControl mount and one DatabaseMetadataCard route mount**. Canonical `/databases/<id>` and the `/d/<id>` redirect reach the same control. Web/static/cron/worker/private services and Key Value do not consume this PostgreSQL target helper. Preserve the current pre-query/loading geometry, latest-first target order, downtime warning, observed source version during an accepted upgrade and post-mutation polling.

## Dedupe, parity and limits

Searched **9,169 board Markdown files**, reviewed **72 actual open/blocked milestone titles** and DO_NOT_DO, and checked the last 40 product commits plus targeted validator/picker history. The only precise-term matches were an unrelated kpack minimum-version task and billing checklist item counts. These relevant code/dependency files are unchanged between the live-pass HEAD and synced main; no target-floor fix has landed.

[w8/done/m12](../w8/done/m12/README.md) owns the original upgrade feature. Its closeout exercised 16→17 and 17→18, not the lower targets; this is a missed compatibility boundary, not proof that a previously working 14/15 upgrade regressed. Preserve each original DoD class: public/UI upgrades with retained data; named unknown/downgrade refusals; durable-plan backup refusal; and honest upgrade progress. This run verifies only Free 13→16 and the rejected targets; durable plans and the full original all-surface closeout are not claimed. The dry-run checks added by w5/m116 must stay aligned. w8/m65 and w7/m156 concern different CNPG logging/metrics issues.

[Render's current upgrade documentation](https://render.com/docs/postgresql-upgrading) distinguishes in-place upgrade to its latest supported major from migration to a chosen supported major. Bex's selectable targets and programmatic upgrade verbs are existing extensions. This fix should accurately bound that extension to its installed mechanism; it does not claim Render supports selectable in-place 14/15 targets or propose removing bex's working 16/17 choices.

Unverified live: REST/MCP mutations and dry-runs, CLI, source version 14, durable plans, extensions, larger data sets, exact downtime, other CNPG versions and authenticated Render. Treat these as verification scope, not observed guarantees.
