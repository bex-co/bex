The correct target is **last linked wins**, so `[Z,A]` means A wins. Do not change runtime or normalize the API to the stale display. ADR013 explicitly preserves this rule. [Render's current documentation](https://render.com/docs/configure-environment-variables#linking-a-group-to-a-service), checked 2026-10-16, describes service-level env overrides and an unguaranteed group collision rule currently favoring most recently created. That deliberate bex divergence remains; Render's authenticated display was not tested.

## Root and bounded repair

`dashboard/src/features/services/components/env-groups-panel.tsx:54–61` passes **only group-list refetch** to `useEnvGroupMutations`, while reading the service through `useServer(...,{poll:false})`. Link and Unlink await that callback (`features/env-groups/hooks/use-env-groups.ts:300–338`); their boolean mutation returns no Server object. Group membership becomes current while `service.linkedEnvGroupIds` remains cached. At `env-groups-panel.tsx:139–150`, the newly linked ID is absent from the cached rank and receives -1, below the old group. The shadow maps at :153–181 and badge consumers at :388–408,432–472 then mark the actual winner as losing.

The detail layout is the designated Server polling owner (`service-detail-layout.tsx:44`); `use-server.ts:49–70` uses cache-first reads and shared converging polling. Baseline interval is30s, converging3s (`common/lib/polling.ts:11–18`). This explains eventual correction, not a reliable post-write refresh. **Apollo4.3.3** is pinned at `dashboard/yarn.lock:65–67` and reported by native request extensions. The exact packed4.3.3 implementation was opened: QueryManager passes default `refetchQueries:[]`; QueryInfo writes the selected mutation result under ROOT_MUTATION and has no supplied query updater; ObservableQuery's later poll uses network-only. A bare boolean cannot update the cached Server order. Local installed4.1.3 was stale and was not used as deployed implementation evidence; exact source excerpts/hash are in the JSON.

Compose the panel's existing group refetch with its existing `refetchService`, wiring the fresh affected Server read into successful link/unlink completion. Keep this local to the service panel; its create-with-initial-service path also currently receives the group-only callback (:323–324), so audit that alias and use the same refresh where appropriate. Creation with an initial link is a source-traced regression requirement, not a live failure observed here.

**Before both reads settle**, preserve a visibly pending state or suppress uncertain group-vs-group ordering/markers. Do not paint a fresh membership list with stale winner claims. Existing `linkedEnvGroupIds?:string[]|null` (`services/types.ts:177`) and the panel's unknown-order behavior can express uncertainty without an API/schema change; keep known service-local override markers. A network timeout, partial/errorPolicy-all result, or failed Server refresh after an accepted write must leave the write accepted, mark precedence unknown and offer read retry. `bestEffortRefetch` (:159–167) intentionally swallows refresh rejection; merely adding a throwing Promise.all is insufficient to provide that honest error state. Do not encourage a duplicate link retry or silently restore stale claims. Forbidden/unauthenticated/not-found mutation errors retain their existing treatment and authorization order.
