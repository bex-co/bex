# Blueprint apply creates a service, then 400s on an unknown `fromService` target, leaving it half-configured

Why: `POST /v1/blueprints/deploy` answers `400 … whose address is not yet known` for a manifest whose `fromService` names a service that exists nowhere, but by then it has already created and started deploying the referring service, without the env var. The caller is told nothing happened, while a live resource appeared. Validate already refuses the same manifest correctly.

- **Severity:** major (a failed mutation leaves a running resource behind; the error wording misleads).
- **Repro (loop53, 2026-10-05, pin `c7afefad5`, `bex-canary`):**
  ```
  POST https://api.bex.co/v1/blueprints/deploy
  {"ownerId":"tea-daif693dqjvc73e7as3g","bexYaml":"services:\n  - type: web\n    name: qa-20261005-l53-b\n    runtime: image\n    image:\n      url: traefik/whoami:latest\n    plan: free\n    envVars:\n      - key: X\n        fromService:\n          type: web\n          name: qa-20261005-l53-nope\n          property: host\n"}
  → 400 {"error":"bad request: service \"qa-20261005-l53-b\": fromService references service \"qa-20261005-l53-nope\" whose address is not yet known", ...}
  ```
  Immediately after: `GET /v1/services?ownerId=…&name=qa-20261005-l53-b` → `srv-db1va2gti8qc73bltdkg`, created `19:05:46Z`. Its deploy is `update_in_progress` (`bexTrigger: create`), GraphQL phase `Deploying`, and `GET …/env-vars` is `[]`: `X` was dropped. Deleted afterwards.
  - Controls in the same run, all 400 with **nothing** created: duplicate service name, unknown `type`, unknown `fromGroup`, invalid `fromDatabase.property`, YAML syntax error, unknown key `healthCheckPathh`.
- **Root cause:**
  - `lego/backend/internal/apps/deploy.go:751-766`: apply's `lookupSlug` maps `GetApp` → `ErrNotFound` to `""`.
  - `resolveServiceRefs` (`:1031-1043`) treats every empty slug as a forward reference to a stack sibling ("sibling not created yet") without checking that the stack declares that name.
  - `applyStackServices` (`:958-962`) then creates the service.
  - Only the second pass, `patchDeferredStackServices` (`:996-1002`), notices the target is still unknown and returns the "unreachable" error, after the write.
  - Validate does the right check: `blueprint_ownership.go:593-614` (`validateWorkspaceReferences`, w8/026) refuses an undeclared target that `GetApp` cannot find, with "fromService references unknown service … (declare it under services: or create it in this workspace first)". Apply never calls it. Database and Key Value undeclared refs are pre-resolved before any write (`resolveExistingBlueprintReferences`, `deploy.go:1053`); host refs are not.
- **Fix:** before any write in `deployParsedStack`, refuse undeclared `fromService` host targets that do not exist in the workspace with validate's message and pointer, so apply and validate share one predicate. Make `patchDeferredStackServices`' branch genuinely unreachable (or an internal error).
- **Blast radius:** every apply entry point that reaches `deployParsedStack`: REST `POST /v1/blueprints/deploy`, GraphQL/MCP deploy-stack, and Blueprint repo sync (`POST /v1/blueprints/{id}/sync`, auto-sync). One fix covers all of them.
- **Adjacent classes:** any other second-pass failure (for example `applyBlueprintCreate` erroring in `patchDeferredStackServices`) still leaves first-pass services created. That is a broader atomicity question for apply; record it as follow-up rather than folding it in. Existing-service targets (resolvable via `GetApp`) must keep working, as must same-file forward references (both legitimate per w9/m57).
- **Unverified:** the sync path (reasoned from the shared `deployParsedStack`, not probed); MCP/GraphQL deploy entry points.
- **Render:** a Blueprint referencing a nonexistent `fromService` fails validation before any resource is created.
- **Estimate:** ~45m (pre-write check plus tests: unknown target creates nothing; existing-service and in-file forward refs still apply).
