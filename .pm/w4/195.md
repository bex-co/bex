# w4/195 — Datastore log search with no matches says "No database logs yet" over logs that exist

Why: after typing a search into a Postgres or Key Value Logs tab, the user is told the store has no logs "yet". That reads as "logging is broken" when only the filter matched nothing, so a working search looks like a failed one.

Live 2026-10-04 UTC (`/qa-find-bugs` loop15, muse.env, `bex-canary`). Owned Free Postgres `qa-20261004-l15-pg` (`dpg-db1ft8lctccs73fiarh0`, deleted to 404):

- **Logs work:** the Logs tab showed Postgres startup lines. A failing SQL-console query (`select * from qa_l15_marker_table_does_not_exist`) appeared as an `ERROR: relation … does not exist` line within 45 s, and searching `qa_l15_marker` narrowed to exactly that line.
- **The bug:** searching `PASSWORD` (no matches) renders the title **"No database logs yet"** with the body "No database logs match the current filters." (`.playwright-mcp/qa-dblogs-filtered-empty-1.png`). The title contradicts the body and the visible history.
- Side check, recorded here: no `PASSWORD`, `SCRAM`, `ALTER ROLE` or `STATEMENT` lines appear in a fresh database's logs, so the provisioning verifier that w4/m167 redacted from Insights does not leak through logs.

Root cause: `dashboard/src/features/logs/components/datastore-log-viewer.tsx:116-124` always passes `t(`${kind}.logsEmptyTitle`)` ("No database logs yet" / the Key Value twin). It switches only the description to `logsEmptyFilteredBody` when `text || instance` is set.

Fix: when a text or instance filter is active, use a filtered title too (new `databases.logsEmptyFilteredTitle` / `keyvalue.logsEmptyFilteredTitle`, e.g. "No matching logs", en + zh), and keep "…yet" for the unfiltered empty range. The `history.hasMore` branch (w4/m140) wraps the same `empty` node, so it inherits the fix. Add a component test for unfiltered-empty vs filtered-empty titles on both kinds.

Severity: minor (copy). Estimate: ~20m.
