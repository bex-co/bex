## Objective

A blueprint that omits its publish directory is told to set `publishPath` — a key the blueprint validator rejects. The shared create-request validator speaks REST's field names, which are correct for REST and wrong for a manifest author.

## Context

### The closed loop (production, 2026-09-13, each step verified)

1. The example's shape (`staticPublishPath` + `plan`) → `at '/services/0': additional properties 'staticPublishPath' not allowed`
2. Obey it, remove `staticPublishPath` → `service "qa-static-bp": bad request: publishPath is required for a static_site`
3. Obey that, add `publishPath: .` → `at '/services/0': additional properties 'publishPath' not allowed`

Step 2 comes from `lego/backend/internal/apps/service.go:2450-2457`:

```go
if svcType == appv1alpha1.TypeStaticSite {
    …
    if strings.TrimSpace(req.PublishPath) == "" {
        return fmt.Errorf("%w: publishPath is required for a static_site", core.ErrBadRequest)
    }
```

`publishPath` is the right name for its REST caller — `POST /v1/services` takes `publishPath` — and `docs/ADR006-bex-api.md:167` records the split explicitly: "`staticPublishPath` ✅ static-site publish dir; **`publishPath` is rejected**". That line is about the *manifest*, and step 3 confirms it live. So the message is correct for one caller and actively misleading for the other.

### Callers of the shared validator

Enumerate them before choosing where the fix goes — `grep -rn` the validator function's name in `lego/backend/internal/apps`, and record the count. It is reached at least from the REST create path, the GraphQL/MCP create paths, and the blueprint compiler's per-service validation (which is how step 2 surfaced). The REST/MCP wording must not change; only the blueprint surface needs translating.

## Steps

1. Enumerate the callers and paste the grep count here.
2. Pick the seam and say why. Two shapes:
   - **translate at the blueprint boundary** — the compiler maps the create-validator's field names into manifest keys before building its `BlueprintSourceProblem` (it already builds those with a `Path`, so it knows it is in manifest space); or
   - **carry both names in the error** — e.g. a coded error with a field identifier the caller renders in its own vocabulary.
   The first keeps REST byte-identical and confines the change; the second scales if more field names diverge. Check whether any other create-validator message names a field whose manifest key differs before deciding — if `publishPath` is the only one, translation at the boundary is enough; if there are several, the coded shape earns itself.
3. Ensure the translated message names `staticPublishPath` and, ideally, points at the service's source location the way the schema problems do (`BlueprintSourceProblem.Line/Column` already exists).
4. Verify the loop converges: the manifest from step 1 of the Context, fixed only as each successive message instructs, must reach a valid manifest.
