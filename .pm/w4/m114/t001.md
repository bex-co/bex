## Objective

A user-canceled manual cron run came back to life and executed. Close the recreation hole: a terminal (canceled) manual run must never be recreated while its `runAt` persists.

## Context

### The observation (production, 2026-09-17, all times UTC)

Fixture `srv-dam3habs0ils73bgp0v0`, schedule `* * * * *`, command `echo p12fail-marker; exit 3`.

- 19:12:1x — `runCronJob` (GraphQL) while a scheduled run was active → accepted, returned pending run `crr-h24run3qoased7o02cnh` (`…-run-2207ebf1`); the active scheduled run flipped `canceled` (server-side preemption, tested behavior per `TestTriggerCronRunReturnsPendingRunAndCancelsActive`).
- 19:14:20 — `cancelCronJobRun(run-2207ebf1)` → `canceled`. No attempts from it afterwards (schedule suspended 19:17:5x for a clean watch).
- 19:18:00 — `cancelCronJobRun(cron-29827874)` (a scheduled run) → `canceled`.
- 19:21:05 — resume. Immediately: `run-2207ebf1` back to `pending` with `startedAt` reset (`19:20:57`), then FRESH EXECUTING attempts 19:21:13 and 19:21:35 from new instances (`p12fail-marker` lines). A canceled run resurrected by resume.

### Root cause (read, not guessed)

Three facts compose:

1. `TriggerCronRun`/`CancelCronRun` record intent in the single-slot `Spec.CancelRun` (`lego/backend/internal/apps/service.go:3021,3120`): the 19:18 cancel of the scheduled run OVERWROTE `{run-2207ebf1}` with `{cron-29827874-job}`.
2. The no-recreate guard `cancelsManualRun` (`app_controller.go:3675`) only holds while `CancelRun.Name` still names the manual job — after the overwrite it is false.
3. Nothing clears `Spec.RunAt` when its manual job ends, so on resume (`!suspended` true again) `ensureManualRun` (`app_controller.go:3683`) sees runAt set + job gone (deleted by the cancel) + guard false → recreates the canceled job, which executes.

Minimal repro needs no suspend: trigger → cancel the manual run → cancel any other run → next reconcile recreates the manual job. (Suspend in the observed incident only delayed step 3's effect.)

### Fix shape

- Preferred: consult terminal history, not the single-slot intent — `ensureManualRun` (or its caller) must not (re)create a manual job whose name is terminal (`succeeded`/`failed`/`canceled`) in `app.Status.Runs` (the retention loop already keeps terminal entries across GC). Alternatively: clear `Spec.RunAt` when its manual job reaches terminal or is canceled. Either way the fix is in the operator, one decision, with the other path as fallback if the first proves racy.
- Keep the legitimate paths green: trigger→new-runAt→create, trigger-preempts-active (CancelRun + new runAt together), re-reconcile idempotence (`TestTriggerCronRunBumpsRunAt` semantics).

### Acceptance

- Controller-level test with a fake client replaying the incident (trigger, cancel manual, cancel scheduled, resume) asserting the manual job is created exactly once and never recreated — the suite must fail on today's code.
- Live proof deferred to t006 (same three-call shape, then resume, then zero attempts).
