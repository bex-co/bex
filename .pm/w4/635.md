# 635 — An image-backed service's deploy that is already rolling out is canceled by the next trigger, though ADR018 claims Render's Wait overlap policy; the deploy hook also answers 200 with a new id, where Render's Wait answers 202

Why: Render's **Overlapping Deploy Policy** defaults to **Wait** for workspaces created on or after 2025-07-14: "Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy". It applies to every deploy of a service. Under Wait, Render's deploy hook answers `202 Accepted` with no deploy ID when "a different deploy is already in progress".

ADR018 (`docs/ADR018-render-parity.md:138`) says bex matches Wait: "an executing row remains open through `live`, one latest-pending row is `queued`". That holds for repo-backed builds (w2/018, w8/m119). For a prebuilt image, a second deploy, hook call, CI push or user retry abandons the rollout already under way and cancels its row. The request that was in progress never serves.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 287, 2026-11-13 11:41–11:49 UTC (`muse.env`, workspace `bex-canary`; pin `5de3d5bcce8e`). **Minor** (the final state is the newest request, as under Override; the in-progress deploy and the hook's answer differ from Wait). ~1h, or more if the operator change is larger than a pin rule.
- **Fixture:** Free web service `qa-20261113-r287-hook` (`srv-dbrfevgk58is73auo0ag`), `docker.io/library/busybox:1.37`, serving its BusyBox banner. Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe 1 (REST):**
  - `POST /v1/services/{id}/deploys` → A `dep-dbrfhjok58is73auo0l0`. Polled every 2 s until A read `update_in_progress` (11:47:37).
  - A second `POST …/deploys` → `201 {"id":"dep-dbrfhm8k58is73auo0mg","status":"queued"}`, the row-level Wait.
  - Ten seconds later (11:47:47): A `canceled` ("Superseded by dep-dbrfhm8…") and B `update_in_progress`. B went `live` at 11:48:18, and the previous live deploy went `deactivated`.
  - A never served. Under Wait, A goes `live` first and then B runs.
- **Probe 2 (deploy hook; URL from GraphQL `deployHook(serviceId:)`, key never printed):**
  - The first `POST` → `200 {"deploy":{"id":"dep-dbrfgp8k58is73auo0hg"}}`.
  - Once that deploy read `update_in_progress` (11:46:01), a second `POST` → `200 {"deploy":{"id":"dep-dbrfgu9ens8c73fghkmg"}}`.
  - The first went `canceled` ("Superseded by dep-dbrfgu9…") within 3 s, and the second ran.
  - Render's Wait answers the second call `202` with no ID and runs it after the first.
- **Root cause:**
  - `releaseInFlight` (`lego/operator/internal/controller/release_identity.go:374-397`) pins a release through its rollout only when `pinnableSourceRelease` (`:427-435`) holds: `app.Spec.Repo != ""` and `app.Spec.Image == ""`.
  - Its comment says "Prebuilt-image, suspended, direct-static-publish and selected (Rollback, Restart) releases have no build to protect and never pin". So the operator adopts the newer generation at once.
  - The store's reconciler then closes the executing row through `supersededCancelReason` (`lego/backend/internal/store/reconciler.go:1855-1868`) once `status.releaseGeneration` passes it.
  - w8/m119 recorded the prebuilt-image path as an "honestly canceled" control (`.pm/w8/done/m119/finding.md:110`, t005). That control triggered twice back-to-back, so the intermediate release had not started rolling. Here it had.
  - The hook's 200 comes from `DeployHookHandler` (`lego/backend/internal/deploys/deployhook.go:332`), which returns the new row's id whatever its overlap state. ADR018:137 says "202 queuing is not modeled", with no user sign-off.
- **Fix (target behavior):** under Wait, which is Render's default for this workspace's age, a deploy that has started executing finishes for every runtime: prebuilt image, Docker, native or static. Later triggers coalesce into one latest-pending `queued` row that starts when it settles.
  - **Operator:** pin a prebuilt-image release once it is executing, as `releaseInFlight` does for a source release. A release that has not started yet may still be replaced.
  - **Hook:** a hook call that lands in the pending slot answers `202 Accepted` with no `deploy.id`, as Render documents. A call that starts a deploy at once keeps `200 {"deploy":{"id":…}}`.
  - **Decide and record:**
    - whether Rollback and Restart (the other "never pin" cases) also wait; w5/m284 already made Restart wait at the row level;
    - whether bex offers Render's workspace setting with Override. Without that setting, Wait is the only policy.
  - **ADR:** fix ADR018:138's claim or its scope, and ADR018:137's "not modeled".
- **Blast radius:**
  - `releaseInFlight`/`pinnableSourceRelease` gate `heldRelease`, `prepareAppReleaseDecision` and the w8/m120/m121 held-release rendering. A prebuilt image gaining a pin must render its own image and settings while held.
  - The hook handler's status change touches REST callers and the CLI's hook use.
  - Regression tests:
    - a source release still pins (m119's tests);
    - two back-to-back image triggers before the first starts still cancel the first;
    - an image deploy rolling out survives a newer trigger and goes `live` before it.
- **Unverified:**

  - Whether Render's hook also answers 202 when only a queued, not executing, deploy exists.
  - Docker and native services were not re-probed this round. w8/m119's live DoD covered native.
