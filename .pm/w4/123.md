# Three disk invariants are enforced when you attach a disk, and by nothing that can break one afterwards

Why: `SetPlan` and `Scale` never look at `spec.disk`, so on a disked service they write the store row first and only then hit the CRD's CEL rejection — leaving the row (which every read projects from) describing a state the cluster will refuse forever.

Found by live `/qa-find-bugs` 2026-09-21 pass 136 (w4-targeted, `muse.env` credentials), sweeping the persistent-disk surface (ADR082), which this loop had never touched. Everything below is read from code except the three control probes at the end, which were run live on a `qa-` fixture that was deleted.

## The invariants, and where each is enforced

`validateDisk` (`apps/disks.go:304-339`) states three rules in its own error strings, and the CRD restates all three as CEL (`lego/types/v1alpha1/app_types.go:278-280`):

| invariant                              | at attach (`addDisk`)           | CRD CEL          | `SetPlan` | `Scale` | `SetAutoscaling` |
| ---------------------------------------- | --------------------------------- | ------------------ | ----------- | --------- | ------------------ |
| paid tier only                          | `disks.go:319-321`               | `app_types.go:278` | **none**  | —       | —                |
| at most one instance                    | `disks.go:322-325`               | `app_types.go:279` | —         | **none** | —               |
| no autoscaling                          | `disks.go:326-329`               | `app_types.go:280` | —         | —       | **none**         |

`grep -n "Spec.Disk" lego/backend/internal/apps/*.go` outside `disks.go` returns exactly two hits — `disk_snapshots.go:202` and the view projection at `service.go:988`. Neither is a guard. So no verb that can violate one of these rules consults the disk.

## Why the CRD does not save it

The cluster is safe — CEL rejects the write, so no ReadWriteOnce volume is ever multi-attached and no disked pod lands on the free tier. The damage is on the API side, and it comes from write ordering.

`SetPlan` (`service.go:3204-3241`) and `Scale` (`:3332-3362`) both finish through `writeThroughStoreFetched` (`:4125-4138`):

```go
if s.Store != nil {
    if id := managedAppID(a); id != "" {
        if err := writeRow(ctx, id); err != nil {          // row FIRST
            return AppView{}, fmt.Errorf("update source of truth: %w", err)
        }
    }
}
return s.patchFetched(ctx, a, mutate)                       // CR patch second — can now fail
```

Its own doc comment reasons only about the row write failing: _"if the row write fails, the CR is left untouched (the row is already wrong, so retrying is safe)"_. There is no rollback for the opposite case, because for these fields the CR patch was never expected to be rejected. The disk CEL rules make it rejectable.

So `scaleService(numInstances: 3)` on a disked service should: write `replicas = 3` to the row, get the CR patch rejected by `app_types.go:279`, and return an error — with the row already changed. The row is the projection source every read uses, and the projector is documented as owning the field (`service.go:4110-4112`), so it will keep re-applying `3` and keep being rejected. `updateServicePlan("free")` is the same shape via `SetAppTier`.

`SetAutoscaling` (`:4632-4655`) is the contrast that shows the fix: it goes straight to `patchFetched`, CR-only, so its CEL rejection is clean and atomic. Only the two row-writing verbs can half-apply.

## This breaks the codebase's own convention

Every other CEL invariant reachable from an API verb has a matching pre-check that runs **before** the row write — `SetPlan` alone already pre-checks worker-on-free, billing, maintenance-mode-on-free, and the instance-cap downgrade (`planDowngradeError`, `:3301-3317`). Three live probes on a free `qa-` static site confirmed the pattern holds where it is implemented:

```graphql
addDisk(serviceId:…, mountPath:"/data", sizeGB:1)
→ "bad request: a static_site cannot have a disk; disks are supported on
   web services, private services and background workers"      # type gate, pre-write

scaleService(id:…, numInstances:3)
→ "bad request: the free plan is limited to 1 instance(s) and cannot scale to 3"
   …and the row is untouched: replicas still 1 on GraphQL and on REST

setImage(id:…, image:"nginx:1.27")
→ "bad request: a static_site builds from a Git repo; a prebuilt image is
   not supported"                                              # mirrors CEL app_types.go:282
```

Each of those mirrors a CRD rule at the API, before the row. The three disk rules are mirrored only at attach time.

## Fix

Give `SetPlan`, `Scale` and `SetAutoscaling` the same pre-check shape the neighbouring guards already use, reading `a.Spec.Disk` off the App they have already fetched. The messages should tell the caller what to do, matching the existing precedent (_"disable maintenance mode before changing to the free plan"_):

- plan → free with a disk: _"detach the disk before changing to the free plan"_
- scale > 1 with a disk: _"a service with a disk cannot run more than one instance; detach the disk first"_
- autoscaling on with a disk: reuse `validateDisk`'s own wording, _"turn autoscaling off first"_ inverted

Also mirror them in `PreviewSetPlan` (`:3247-3268`), which runs the same validation set for dry-run and would otherwise promise a downgrade that cannot happen. And carry them across REST/GraphQL/MCP together, since each surface has its own scale/plan/autoscaling verb.

Estimate: ~50m. Borderline for a milestone — the three guards share one helper and are a few lines each, but the test matrix (three verbs × three surfaces × preview) is the bulk. Promote if the adjacent concern below is taken on at the same time.

## The adjacent concern, named but not folded in

`writeThroughStoreFetched` leaving the row changed when the CR patch fails is a property of the **shared** helper, not of these two verbs — `setSuspended`, `SetIdleTTL`, `SetDisplayName` and others all ride it. Whether it should roll the row back, or whether pre-checks are the only defence, is a design call with a blast radius worth counting before anyone changes it (`grep -c writeThroughStoreFetched` across `apps/`). The three guards above fix the reachable cases without touching it; deciding the general question is separate work.

## Also checked this pass, and found correct

- **`validateDisk` is thorough and ordered well.** Type gate first (so a static site gets the useful message rather than a tier complaint), then paid tier, replicas, autoscaling, name length, mount path, size. The mount-path rules reject relative paths, a trailing slash, over-length, and a reserved-path list (`/etc`, `/opt/render/project/src`, …) with an actionable _"mount a subdirectory of it instead"_.
- **The CRD restates every one of those invariants as CEL**, including the one-way `sizeGB` rule (`app_types.go:281`, _"a disk is never shrunk"_) — so the store and the cluster cannot disagree about what a legal disk is, only about whether a service is currently legal.
- **`addDisk` gates on billing, not on the weaker mutation gate** (`disks.go:115-120`), with the reasoning written at the site: a disk bills from the moment it exists.
- **The scale guard writes nothing when it refuses.** After a rejected `scaleService(3)`, GraphQL and REST both still reported `replicas: 1` / `numInstances: 1` — verified in the same request pair.
