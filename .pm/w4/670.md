# 670 — A first deploy reads `update_in_progress` through its whole pre-deploy command: the row reaches `update_in_progress` at dispatch, and the lifecycle refuses the move back to `pre_deploy_in_progress`

Why: Render's deploy goes `pre_deploy_in_progress` while the pre-deploy command runs, then `update_in_progress`. On bex, the first deploy of an image service with a pre-deploy command reads `update_in_progress` for the whole command. The Deploys list, REST, GraphQL and the CLI all say the release is rolling out while a migration is still running. A later deploy of the same service reads `pre_deploy_in_progress` correctly.

The row also stays on the 18-minute deploy gate instead of the 35-minute pre-deploy gate. A first deploy whose migration runs longer than 18 minutes may then be judged by the wrong timer. That outcome was not probed.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 392, 2026-11-15 05:03–05:12 UTC (`muse.env`, workspace `bex-canary`; pin `2d9bbae6bb8d`). **Minor** (wrong status for a pre-deploy window); the long-pre-deploy timeout consequence is unverified. ~45m.
- **Fixture:** Starter image web service `qa-20261115-r392-sh` (`srv-dbsjq8v35ies73daahag`, `docker.io/library/nginx:1.27-alpine`, `preDeployCommand: sleep 120`), created with `POST /v1/services`. Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe:**
  - **First deploy** (`dep-dbsjq8v35ies73daahb0`). `GET …/deploys?limit=1` was polled every ~8 s:

    ```
    05:03:31 created                       (deploy_started; narration "==> Deploy queued")
    05:03:51 startedAt                     (narration "==> Deploying image …")
    05:04:06 update_in_progress            (instances [])
    05:04:29 event pre_deploy_started
    …        update_in_progress on every poll   (instances [], w4/663 holds)
    05:06:33 event pre_deploy_ended {"preDeployStatus":"succeeded"}
    05:06:40 update_in_progress, instance …-3v0fng5vsnabhnq3sm12 created 05:06:38
    05:07:17 live
    ```

    No poll read `pre_deploy_in_progress`. The narration has no pre-deploy line.
  - **Control, a later deploy** of the same service: `POST …/deploys {}` at 05:09:16 (`dep-dbsjsv735ies73daahe0`). REST `GET …/deploys/{id}` and GraphQL `deploys { status }` were polled every 3 s. Both read `created` (05:09:17), `pre_deploy_in_progress` (05:09:24, five seconds after `pre_deploy_started` at 05:09:21), `update_in_progress` (05:11:41, after `pre_deploy_ended` at 05:11:25), then `live` (05:11:59).
  - Round 361 (pin `c99e7815ebec`) read `pre_deploy_in_progress` on the first deploy of the same shape (w4/m352 t006). So this is a race whose outcome changed with this pin. The likely cause: w4/665's fix (`47827d789`) now dispatches before the pre-deploy Job exists, where the slower controller used to create both in one pass.
- **Root cause:**
  - **The guard.** `CanTransitionDeploy` (`lego/backend/internal/store/deploy_lifecycle.go:131-133`) admits `pre_deploy_in_progress` only from `created`, `queued` or `build_in_progress` (`:117`). Once a row reads `update_in_progress`, the reconciler's later `pre_deploy_in_progress` verdict is refused. So is a `pre_deploy_failed` verdict, whose predecessors (`:118`) also omit `update_in_progress`.
  - **The early `update_in_progress`.** `observedDeployStatus` reports `pre_deploy_in_progress` only once the App's `status.preDeploy` is `Running` for the release (`lego/backend/internal/store/reconciler.go:1733-1741`). The operator records `Running` when it creates the pre-deploy Job (`lego/operator/internal/controller/app_controller.go:7337-7339`). Between dispatch and that Job (05:03:51 → 05:04:29 here), the App is in `PhaseDeploying`, and the row is mapped to the rollout's status (`reconciler.go:1791` on).
  - **The gate.** `deployTimedOut` picks the timer from the row's current status (`reconciler.go:1690-1704`). A row stuck in `update_in_progress` uses `defaultDeployGateTimeout` (18 min, `:123`), not `defaultPreDeployGateTimeout` (35 min, `:98`; Render allows 30, w22/010).
- **Fix (target behavior):** a release with a pre-deploy command reads `pre_deploy_in_progress` from dispatch until its pre-deploy ends, then `update_in_progress`, on the first deploy as on every later one. Its timer is the pre-deploy gate.
  - Either do not map a release to `update_in_progress` while it has a pre-deploy command whose step has not succeeded for its generation (the App spec names the command; `status.preDeploy` names the step), or have the operator record a pending pre-deploy at dispatch.
  - Do not widen the guard to admit `update_in_progress` → `pre_deploy_in_progress` in general. It exists to stop phase regressions once a rollout has begun.
- **Blast radius:** every service type that runs a pre-deploy command (web, private, worker; image and Git-built). A Git-built release goes `build_in_progress` → pre-deploy, which the guard admits. It would only hit this if a pass samples it between the build's end and the Job. Not probed.
  - Tests: an image service's first release with a pre-deploy command reads `pre_deploy_in_progress` from dispatch; a later release is unchanged; a release without a pre-deploy command still goes straight to `update_in_progress`.
- **Unverified:** what a first deploy's pre-deploy longer than 18 minutes closes as (the deploy gate fires while the guard refuses `pre_deploy_failed`); Git-built services; the dashboard's wording during the window.
- **Render:** a deploy's status is `pre_deploy_in_progress` while its pre-deploy command runs, and the dashboard says so.
- **Dedupe:** `grep -rlE pre_deploy_in_progress .pm/w4 .pm/w5 .pm/w8 .pm/w2 | xargs grep -lE "first deploy|update_in_progress"` → w4/663, w4/m352, w8/287 and w2/m38 t004. None is this transition. w8/287 is the build-side sibling (`queued` through a whole build).
