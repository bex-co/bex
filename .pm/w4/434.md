# Notifications: unsaved mobile-push changes are silently lost on navigation, beside email switches that autosave

Why: the Notifications page mixes two save models. The email switches save on click, while the mobile-push section needs an explicit "Save push settings", and that button gives no sign of unsaved changes and is always enabled. A user who ticks a push event filter and leaves the page loses the change with no warning.

Severity: minor (lost input on a bex-extension settings page; no data loss beyond the edit). Estimate: ~30m. Source: live `/qa-find-bugs w4` loop run eec3, 2026-10-29 UTC (`muse.env`, pin `b33dd43c4428`).

## Evidence

- `/notifications`: the email "Deploy started" switch persisted across a reload with no Save (autosave). It was restored afterwards.
- In "Mobile push → Event filters", ticking "Deploy started (Routine)" and then clicking the sidebar's "Blueprints" link navigated away with no prompt and no unsaved banner. Returning to `/notifications`, the box was unticked again.
- On a clean reload, "Save push settings" is **enabled**, so the button's state never shows whether there are pending changes.

## Cause

- `dashboard/src/features/notifications/components/push-notification-settings-panel.tsx:172` holds the edit in a local `draft` (`clonePushSettings(initialSettings)`), with no dirty comparison and no navigation guard. The Save button (`:356`) is gated only on `busy`.
- The established pattern is `service-environment-editor.tsx:384-390`: `saveDisabled = !dirty || …` and `useBlocker({ shouldBlockFn: () => dirty, enableBeforeUnload: dirty, withResolver: true })` with a confirm dialog.

## Fix

- Compute `dirty` as the draft differing from the last saved settings. Disable "Save push settings" while the form is clean, and show an "Unsaved changes" hint next to it while it is dirty.
- Add the same `useBlocker` guard: an in-app navigation asks to discard or stay, and a reload or tab close triggers `beforeunload`.
- Tests: ticking a filter enables Save and arms the blocker. Saving, or reverting the tick, disarms it. The email switches keep autosaving.

## Unverified

- Other push fields (timezone, working/quiet hours, per-service overrides) were not probed individually. They share the same `draft`, so the same behaviour is expected.
