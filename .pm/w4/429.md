# 429 — Image-port discovery reads Docker Hub anonymously, so the cluster's shared egress quota stalls every new docker.io image service for up to 25 minutes

Why: since w4/m243 every new prebuilt-image web service reads its image config from the registry before its first pod. For Docker Hub that read is anonymous, and every tenant shares the cluster's few egress IPs and therefore one anonymous pull budget. On 2026-10-27 09:30–09:54Z every anonymous metadata read returned `429` (72 retries in the operator log), so every docker.io image service created in that window waited, and only ghcr.io images went live. w4/m243 t008/t013 made the wait retried and visible; this note removes its cause.

**Severity:** major when it hits (Docker Hub is the default registry). **Estimate:** ~45m once a credential exists. **Source:** w4/m243 t013's root cause, recorded in the loopx w4 drain, 2026-10-28 (operator log via Loki, read-only).

## Fix (target behavior)

- Read Docker Hub image metadata with a platform Docker Hub credential (a paid or verified-publisher account's access token), stored as a Secret the operator reads, used only for `registry-1.docker.io` metadata reads of images that carry no tenant credential. Keep the anonymous read as the fallback when the Secret is absent.
- Never attach the platform credential to a tenant's pod (`imagePullSecrets`); it lifts only bex's own metadata reads.

## Gate

- **Needs a Docker Hub account and access token from the user.** No platform Docker Hub credential exists in `deploy/`, `lego/operator/config` or `.env.example`.

## Files

- `lego/operator/internal/controller/image_network.go` (`resolveImageNetwork`, the external branch), `lego/operator/internal/registry/image_config.go`
- `lego/operator/config/manager/manager.yaml` (the Secret reference), `.env.example` / `scripts/gh-secrets.sh` if the token is CI-provisioned
