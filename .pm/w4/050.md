# Metrics memory chart shows usage above the plan's stated limit — the running pod is not constrained to that limit

Why: the service Metrics page renders memory usage over 100% of the plan limit (up to 153% observed), which is only possible if the pod's enforced memory limit ≠ the plan it displays — so either the metrics "Limit" line lies or the operator isn't enforcing the plan's memory limit on the running pod (density / noisy-neighbor / cost risk if the latter is systemic).

Source: live QA 2026-09-07, `$qa-find-bugs w4`.

## Symptom (reproduced on prod)

On `dashboard.bex.co` → a service → Metrics → **Application Metrics → Memory (Percentage)**, the chart draws memory usage **above** the stated plan limit. For `tianpan-v4-web` (`srv-da40m1qii7bs73drbqlg`, plan **Starter**, chart shows "Limit 512 MiB"): current **68.6%** (=351 MiB), and the Y-axis maxes at **153%** because the working-set peak over the last-12h window was **782 MiB**. Working set can't durably exceed a hard cgroup limit without an OOM kill, so the displayed limit is not the enforced limit.

## Durable probe (GraphQL, run from the page: `fetch(..., {credentials:'include'})`)

```
operationName: Metrics
variables.query = {
  filters:[{field:"RESOURCE",values:["srv-da40m1qii7bs73drbqlg"]}],
  name:"MEMORY", start:"2026-09-06T19:22:50.754Z", end:"2026-09-07T07:22:50.754Z", resolution:300
}
```

Response: `metrics` = **1 series** (unit `bytes`), instance label `tea-da2isimlm39c739m4ofg-tianpan-v4-web-6b9d4c6c99-pdwx8`, 145 samples, **min 242814976, max 820019200 (=782 MiB @ 2026-09-07T07:07:50Z), last 368422912 (=351 MiB)**. One pod only, no multi-pod samples — so this is a single container's working set, not an old+new-pod restart sum.

## Why the metric is correct (rules out a query bug)

`promResourceQueryFor` builds `sum by (pod)(container_memory_working_set_bytes{namespace=..,pod=~..,container!=""})` — `lego/backend/internal/metrics/source.go:261`, with `PodNameMatcher`'s `container!=""` at `lego/backend/internal/egressquery/podname.go:92` excluding the pod-level rollup. So 782 MiB is a real single-container working set, not a double-count.

## Why the limit should be enforced (the contradiction)

Starter (and free) map to `memory: 512Mi` in `lego/types/tiers/tiers.yaml:47-51` (free 512Mi at `:36-46`). `resourcesForTier` (`lego/operator/internal/controller/app_controller.go:1289`) sets `guaranteedResources` with **requests == limits == 512Mi** (Guaranteed QoS, `app_controller.go:1307-1313`) — a hard cgroup limit. A 782 MiB working set under a hard 512 MiB limit is impossible without an OOM kill, and the pod (ReplicaSet `6b9d4c6c99`) has been Live single-instance since the Aug 30 deploy with **no restart**. Conclusion: **this pod is running best-effort / without the plan's memory limit applied.**

## Root cause

**Confirmed:** the running pod is not constrained to its plan's memory limit. **Unverified (needs cluster access — no kubectl in the QA env):** which mechanism —

- (a) legacy pod created before the tier-resources projection and never re-projected — limits only apply on the next deploy (a reconcile-completeness gap), or
- (b) the App CR `Spec.Tier` ≠ the catalog id the displayed "Starter" plan implies, so `resourcesForTier` returns `{}` (best-effort) while the dashboard/plan still shows 512 MiB (tier-mapping drift).

**First step before any fix:** `kubectl get pod <pod> -o jsonpath='{.spec.containers[*].resources}'` and the App CR's `spec.tier`, to pick (a) vs (b).

## Target behavior

A running pod's enforced memory limit must equal the plan the dashboard/metrics display, and the metrics "Limit" line + memory Percentage must be computed against the **enforced** limit so healthy usage never shows >100%. If (a): the operator must re-project resources onto existing Deployments on reconcile (not only on deploy). If (b): the operator's `Spec.Tier`→resources mapping must agree with the backend's plan reporting (single source of truth).

## Blast radius / still unverified

Only `tianpan-v4-web` (16d old) was checked. The two recently-created services (`srv-daf4sgcrrsrs73ev9j80`, `…jb0`) use ~1–3 MiB, too little to tell whether **new** pods also lack limits. Must verify a fresh service's pod resources to know if this is legacy-only or systemic. If systemic, tenants can exceed their plan's memory with no enforcement — raising severity from "metrics mislead" (major) toward a real isolation/enforcement gap. Promote to a milestone once (a) vs (b) and legacy-vs-systemic are settled.

## Render parity

Render enforces plan memory limits and shows usage against them — memory never sits durably above 100% of the plan. bex diverges here.
