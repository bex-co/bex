# Project Settings loading cards shift when the editor and delete action appear

Why: the pending preview replaces the name editor and delete section with generic text bars, so their descriptions and controls move into new positions when loading finishes.

Severity: **minor**. Estimate: **50m** (route-specific placeholders 15m, consumer/behavior checks 20m, desktop/mobile verification and simplify 15m). Functional QA a428, 2026-10-13 Pacific / 2026-10-14 UTC, user-selected w4 and muse.env login helper. Filing only; source main `fde35ffcc`.

## Reproduction and measured target

On your own disposable project, enter `/project/{id}/settings` while its normal **Project** read is pending. Compare that state with the settled page at the same viewport.

The recorded production probe delays **only that owned read's unchanged response by seven seconds**, using the actual router's public navigate method. It changes no mutation, credential, server response content or foreign resource. The route handler is removed in `finally`. The observed router matches are `__root__`, `/project/$projectId`, and `/project/$projectId/settings`; the parent correctly chooses the Settings skeleton.

At **1440×1000** and a fresh **390×844** page, both pending cards contain one title bar and two generic 16px text bars. They reserve neither description regions nor the name input/Edit-button row and Delete-button slot. The ready cards have those elements.

Keep loading placeholders inert and free of the unresolved project name. The ready page should occupy the geometry previewed during pending navigation.

## Root cause and bounded work

`dashboard/src/common/components/route-skeletons.tsx:812–829` renders the page heading as `h-6` and both cards as `CardSkeleton rows={2}`. The generic helper at `common/components/detail-skeletons.tsx:113–134` provides one title bar and stacked text rows, without a CardDescription or a control/action row.

The ready consumer is `routes/project.$projectId.settings.tsx:105–186`: a `text-xl` heading, a titled/described name card with a disabled Input and Edit button, and a titled/described delete card with its button. The actual shared Card/CardHeader/CardDescription/CardContent primitives were opened at `common/components/ui/card.tsx:5–70`; they expose the necessary slots. The mismatch is caused by substituting a different card structure, not by a wrong route, failed data load or a missing frame.

Replace those two uses with placeholders shaped for this page, preserving its outer padding, `max-w-2xl`, card spacing and region markers. Reserve the real translated descriptions' responsive heights; don't hardcode the observed English mobile height as a universal value. Reserve the name control plus Edit action on one row and the delete action in its own slot. A small shared ready/pending frame can keep wrapping and spacing aligned, but no global CardSkeleton redesign is required.

Two production wiring sites consume this skeleton: `project.$projectId.settings.tsx:30` as the child pending component, and `ProjectRouteSkeleton` at `route-skeletons.tsx:834–850` during parent loading for that child. The latter was observed in both probes. The canonical URL is `/project/{id}/settings`; the route inventory contains no separate project-settings alias. Other generic CardSkeleton callers are outside this bounded change.

Pinned framework inspected: router-core **1.171.21**, react-router **1.170.25**. Router construction exposes the public instance at `router-core/src/router.ts:1151–1153`; the app parent declares `pendingMs: 0` and ProjectRouteSkeleton at `routes/project.$projectId.tsx:28–29`. This explains the actual pending route captured by the probe. Existing rendering tests/manifest coverage identify regions and route dispositions, but no Project Settings pending-versus-ready geometry assertion was found.
