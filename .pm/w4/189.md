# w4/189 — Blueprint takeover confirmation says "Protected environment confirmation required"

Why: the one dialog that stands between a user and replacing another Blueprint's stack gives the wrong reason. It calls the takeover a protected-environment check and never names the Blueprint being replaced, so the user can't make an informed decision on a destructive action.

Live 2026-10-04 UTC (`/qa-find-bugs` loop7, muse.env, `bex-canary`): on `/blueprints/new`, I chose Public Git URL `https://github.com/bex-co/bex`, branch `main`, path `examples/static-site/render.yaml`.

- The preview alert reads "Already connected — deploying will take it over". It then shows the raw API message: _"blueprint blp-db136288mmqc73d4hpug ("bex") already tracks https://github.com/bex-co/bex@main from "render.yaml"; update it with updateBlueprint to change its path, or retry with confirm="takeover blueprint blp-db136288mmqc73d4hpug" to replace it"_. "updateBlueprint" and `confirm=` are API-call wording a dashboard user can't act on.
- Clicking **Deploy Blueprint** opens a dialog titled **"Protected environment confirmation required"**, with the body _"takeover blueprint blp-db136288mmqc73d4hpug belongs to a protected environment. Type the exact command below to continue."_. Nothing there is a protected environment, and the sentence is not English. I cancelled; nothing was created.
- Evidence (local): `.playwright-mcp/qa-blueprint-takeover-dialog-1.png`.

Raw probe (re-runnable, refused server-side, no side effects): `mutation{ createBlueprint(repo:"https://github.com/bex-co/bex", branch:"main", path:"examples/static-site/render.yaml", name:"x", ownerId:"tea-daif693dqjvc73e7as3g"){ id } }` returns `extensions: {code: "BLUEPRINT_CONNECTION_CONFLICT", blueprintId, blueprintName: "bex", repo, branch, path: "render.yaml", confirm: "takeover blueprint blp-…"}`.

Root cause:

- `dashboard/src/features/services/lib/protected-confirmation.ts:13-29` `protectedConfirmationFromError` deliberately folds three handshakes into one bare phrase string, dropping which kind it was: the protected-environment guard, the blueprint-resource takeover (w8/m23, "is managed by blueprint") and the blueprint-connection takeover (w4/m125, "already tracks").
- `dashboard/src/routes/blueprints.new.tsx:455-470` and `dashboard/src/routes/blueprints.$blueprintId.tsx:704-723` (sync) then always render `ProtectedConfirmationDialog`, using the `common.protectedConfirmationTitle`/`Body` copy (`dashboard/src/common/locales/en.ts:8-15`).
- `protectedServiceName` only parses `sudo … service|database|key value …` phrases, so the takeover phrase is shown verbatim as the "name".

Fix: classify the handshake from the GraphQL `extensions.code`, not the message text: `BLUEPRINT_CONNECTION_CONFLICT`, `BLUEPRINT_RESOURCE_CONFLICT`, or the protected-environment code. Return `{kind, phrase, details}`.

- For the two takeover kinds, render a takeover-specific title and body from the extensions, e.g. "Replace Blueprint "bex"?". The body should say that it currently tracks `render.yaml` on `bex-co/bex@main`, and that deploying repoints it to this file and takes over its resources.
- Render the preview alert from the extensions too, not the raw message.
- Keep the typed phrase as the authorization (unchanged server contract).
- en+zh copy.

Blast radius: `protectedConfirmationFromError` has 8 caller modules (`use-create-blueprint`, `use-sync-blueprint`, the database/key-value/service delete and lifecycle hooks). The non-blueprint callers must keep today's protected-environment dialog, so add regression tests asserting each still shows it. Test: `BLUEPRINT_CONNECTION_CONFLICT` and `BLUEPRINT_RESOURCE_CONFLICT` errors open the takeover dialog naming the blueprint; a protected-environment error still opens the protected dialog.

Unverified: the resource-takeover variant (`is managed by blueprint`) and the detail-page sync dialog were reasoned from code, not probed live this run.
