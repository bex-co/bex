## Objective

When bex's image metadata read passed but the node's kubelet then fails the pull (`ErrImagePull`/`ImagePullBackOff`), word the Ready condition with the same shared deploy-reason templates the metadata read uses, choosing one of Render's four causes from the kubelet's waiting message, instead of the raw `image pull is failing: <image>: <kubelet message>`.

## Context

- Kubelet path: `lego/operator/internal/controller/app_controller.go:4541-4549` (rollout) and `:6889-6893` (served release); `ImagePullStallWaiting` in `lego/types/v1alpha1/stall_message.go:29`; pre-deploy's own copy in `lego/operator/internal/predeploy/predeploy.go:588`.
- Metadata-read path to match: `imageRefusalError` (`lego/operator/internal/controller/image_network.go:825-845`) and the templates in `lego/types/v1alpha1/deploy_reasons.go:42-51`, `:222-226`.
- `r.platformPullFailure` (`app_controller.go:4546`) already rewords bex's own registry failures; keep it.
- containerd/kubelet messages carry the registry's answer: `not found`/`manifest unknown` (404), `unauthorized`/`denied`/`403 Forbidden`, `429 Too Many Requests`/`toomanyrequests`.

## Steps

1. Add a classifier over the kubelet waiting message: not found → `image_not_found`; unauthorized or forbidden → `image_credential_refused` when the service has a credential, else `image_access_refused`; 429 → t002's rate-limited reason; anything else → a registry-unavailable reason worded from Render's "Registry unavailable" remedy.
2. Use it at both kubelet sites and in pre-deploy, keeping the kubelet's text as a trailing detail only where the cause is unknown.
3. Unit-test the classifier with real containerd messages for Docker Hub, GHCR and a self-hosted registry.
