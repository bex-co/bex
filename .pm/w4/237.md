# Trigger Run omits its replacement warning while cron history catches up

Why: a user can replace a newly accepted cron run or cancel an active execution without the confirmation explaining that consequence, because observed history briefly contains only terminal rows.

- **Severity:** minor — a reproducible confirmation-copy gap; this pass does not claim failed execution, lost stored history or concurrent containers.
- **Estimate:** 45m: caller/state audit 10m, English/Chinese copy 10m, meaningful confirmation tests 15m, Simplify and live closing check 10m.
- **Source:** continuous `$qa-find-bugs w4`, functional hosting pass a53, 2026-10-10 UTC, using the supplied `muse.env` through the login helper.
- **Goal:** truthful hosting controls under [ADR008](../../docs/ADR008-vision.md) and [ADR038](../../docs/ADR038-cron-jobs.md), completing the warning guarantee in [w4/m114](done/m114/README.md) without changing cancel-and-replace behavior.

## Reproduction and controls

Initial deploy `dep-db52pasb8ulc73efu4p0` reached Live. The annual schedule avoids automatic runs during the pass. Ordinary Events controls at `https://dashboard.bex.co/services/srv-db52pasb8ulc73efu4og/events`; no response interception or injected fault.

1. At **12:18:56.401Z**, Trigger Run accepts `crr-mkfbm72ml3h3opkphmla` as pending. At **12:19:04.930Z**, triggering again shows only “This runs the job's command immediately, outside its schedule. Only one run can be active at a time.” It accepts replacement `crr-pj0r3g86uja4ika73g60`. Subsequent complete history shows the earlier run started at **12:19:02Z** and was canceled at **12:19:04.837136591Z**. Thus the unqualified dialog preceded a real active-run cancellation.
2. **Known-active control after a fresh load:** at **12:20:09Z**, the table and direct GraphQL read both show `crr-pj0r3g86uja4ika73g60` pending/Running. The next dialog correctly says an active run will be canceled. The replacement is accepted. This is not a missing translation key or universally wrong dialog.
3. **Fresh-page second sequence:** reload the Events page, with only terminal runs, then trigger at **12:21:26.281Z**. Its immediate history response already includes new pending `crr-3qbk6ejas07eqf8f8bi3`, so the next dialog correctly contains the active-run warning.

The mutation returns pending `crr-fucv0f9n8lq4r69d3om0`, but the **12:21:42.459Z** refetch contains five terminal rows, including the newly canceled predecessor, and no replacement row. At **12:22:13Z** the accepted replacement appears in history, and it succeeds at **12:23:02Z**.
5. Functional controls: an early explicit Cancel accepted `crr-u6nfqvfvqd0qg77oeg06` as canceled at **12:18:29Z**; this and the three preempted rows stayed canceled through the final read. The final successful run's expanded detail shows its exact id, start/finish, and 49-second duration. `lastSuccessfulRunAt` advances only to the successful run's finish.

**Expected:** every confirmation explains that this action replaces a pending manual request and cancels any active run before starting the replacement, even when a history query has not observed the new run. An empty/terminal history must not be treated as proof that replacement cannot occur.

**Actual:** only the currently loaded active-history branch carries that explanation. The default branch promises a trigger with no mention of canceling/replacing prior work.

## Root cause and bounded fix

- `dashboard/src/features/services/components/cron-runs-section.tsx:304–307` chooses the copy solely from `hasActiveRun`. `features/services/hooks/use-cron-runs.ts:204–206` derives that flag only from rendered history. Its trigger at **278–280** discards the accepted run object and then refetches. A successful refetch can legitimately precede materialization of the new Job.
- The default messages at `features/services/locales/en.ts:2730–2734` and `zh.ts:2674–2677` explain single-run concurrency without stating cancel-and-replace. The separate active messages exist at **en:2735–2740 / zh:2678–2682**, matching the passing control.
- Backend `lego/backend/internal/apps/service.go:3551–3590` returns a deterministic pending object immediately after patching cancel/run intent. The list at **3594–3605** reads observed `status.runs`. ADR038's cancellation section explicitly requires foreground deletion before the replacement Job is materialized. The complete refetch therefore supports the state gap; it does not prove a failed write or broken query.
- Actual pinned Apollo **4.1.3** was opened: `cache/inmemory/helpers.js:4–23` identifies `CronRun:<id>`, and `writeToStore.js:239–300` writes identified objects as references. The app cache config (`dashboard/src/common/apollo/cache.ts:6–12`) has no CronRun or history-field policy. Normalizing the mutation entity does not insert it into a query's returned history array. The second gap's complete HTTP 200 response contains only terminal rows; this is not explained by a transport error or delayed DOM paint.

**Fix target:** change the default confirmation in both locales to always explain the action's replacement semantics without asserting that an active run definitely exists. For example: “This requests a run outside its schedule. It replaces any pending manual run request and cancels any active run before the replacement starts.” Keep the known-active branch's explicit warning. Avoid promising that a new process starts immediately while foreground deletion is still pending. This copy change handles the recorded missing-history window and an execution arriving between a read and confirmation, without inventing runtime facts.

Do not change the API's observed-history contract, disable Trigger Run during active execution, add optimistic run rows, alter cancellation timing, or interpret a canceled run's termination grace as resurrection. The deliberately chosen server preemption behavior stays intact. Update the existing no-active confirmation test, which currently explicitly excludes “cancels it,” to assert a truthful conditional explanation rather than assuming no loaded active row means no possible preemption.

**Blast-radius work (10m):** exhaustive production searches found **one** `useCronRuns` consumer, **one** `CronRunsSection` mount (`routes/services.$serviceId.events.tsx:352–355`, guarded by `isCron`), and **one** production selection per confirmation key, with two locale definitions. The default-copy fix is global across that cron confirmation. Web/static/worker/private branches do not mount this card; Postgres/key-value have separate routes. `/cron/<id>/events` redirects to the canonical route via `routes/cron.$.tsx` and `common/lib/render-alias.ts:15–22,71–78`; the five service-segment aliases preserve the same subpath, rather than implementing independent dialogs. Mobile has its own controls and is not a consumer of these messages; no mobile change is proposed.

REST/GraphQL/MCP mutation semantics remain as documented in ADR038. This pass exercised UI GraphQL, list/detail reads and app logs; REST/MCP triggering, alias navigation, Chinese display and narrow-mobile handoff were not run. The filing proposes a dashboard copy fix, not a cross-surface API change. Permission, suspension, billing, terminal-cancel refusal, timeout and generic transport errors keep their existing gates/error handling; none are reclassified by a description change.
