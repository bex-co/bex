## Objective

Every Postgres writes an hourly row of its provisioned storage capacity in GB × the seconds it held it. This is a new usage kind beside `storage_gb_seconds`, which keeps measuring used bytes for Postgres and Key Value. Nothing is billed differently yet (t002).

## Context

- Meter loop: `datastoreMeterKinds` and `processDatastoreMeterWindow` (`lego/backend/internal/usage/service.go:812`). The unavailable-health map for a datastore whose names could not be retained is at `service.go:1040`. Storage rows carry the plan as `tier` (w4/427).
- Kinds: `lego/backend/internal/store/usage.go:30`. The newest kind-constraint migration is `0284_cron_minimum.up.sql`. Copy its two `CHECK` lists and add the new kind. The next number is the next free one after `0354` on `origin/main`.
- Proposed kind name: `storage_capacity_gb_seconds`, after Render's "Storage capacity" in its faq. It is user-visible as a `kind` in the usage API, so report the name you pick in the result's `decisions:`.
- **Unit:** the product's GB. The operator provisions `<storageGB>Gi` (`lego/operator/internal/controller/database_controller.go:528`), so a "10 GB" database has a `10Gi` request. Bill 10, not 10.74: divide request bytes by 2^30.
- **Source, recommended:** kube-state-metrics' `kube_persistentvolumeclaim_resource_requests_storage_bytes{namespace,persistentvolumeclaim}`. The job is `deploy/gitops/base/prometheus.yaml:557`, scraped every 60 s. Its chart values set no `collectors:` list, so the PVC collector should be on.
  - It carries history, so a catch-up after an outage bills a resize from the hour it happened.
  - Use `sum_over_time(…[3600s])` × the scrape interval, or a step count like `instanceSecondsQuery`. A database created or deleted mid-hour is then prorated: `avg_over_time` × window would bill it the full hour.
  - Match the PVCs with the pattern `queryStorageGBSeconds` uses (`^<datastoreClusters>-[0-9]+$`). That counts the primary, the HA standby (`<name>-2`) and each read replica cluster (`<name>-r-<hash>-N`).
- **Before building on it, check that the series exists for tenant PVCs on production.** Run a read-only instant query through a port-forward to `prometheus-server.monitoring` with the app cluster kubeconfig (`scripts/fetch-app-kubeconfig.sh`).
- **Fallback if it is missing:** the logical size `tiers.Postgres.EffectiveStorageGB(plan, spec.storageGB, status.allocatedStorageGB)` (as `lego/backend/internal/metrics/datastore.go:371` reads it) × the billed instance count × the seconds alive in the window. This is exact for the live hour but retroactive on catch-up. Write down why if you take it.
- **Never** use `kubelet_volume_stats_capacity_bytes`. That is the physical Hetzner volume with its 10 GiB floor (`metrics/datastore.go:301`).

## Steps

1. Run the production check of the kube-state-metrics series, then pick the source.
2. Add the store constant and the up/down migration for both `usage_hourly` and `usage_monthly`.
3. Add the query and wire it into the meter loop for `ResourceKindPostgres` only. Give it source health from the closed vocabulary in `store/usage.go` (reuse `storage`, or add one presentation-safe value) and add it to the unavailable-health map.
4. Unit tests against a stub Prometheus:
   - a full hour of a 10Gi PVC reads 36,000;
   - an HA pair and a replica sum;
   - a half-hour creation is prorated;
   - an unavailable query writes no row and records health;
   - a Key Value writes no capacity row.

## Outcome (2026-11-28)

- **Source: kube-state-metrics, checked on production first.** A read-only instant query through a port-forward to `prometheus-server.monitoring` (app cluster kubeconfig from `scripts/fetch-app-kubeconfig.sh`, 2026-11-28T05:10Z) found `kube_persistentvolumeclaim_resource_requests_storage_bytes` (job `kube-state-metrics`, v2.13.0 with `persistentvolumeclaims` among its `--resources`) for every tenant claim: 32 series fleet-wide. The `bex` fixture's 10 GB Postgres (`dpg-dbnukjpngmjs739tgukg-1`, `10Gi`) read 644,245,094,400 byte-steps over `[3599s:60s]` at 2026-11-28T04:00Z, which is 600 GiB-steps × 60 s = **36,000 GB-seconds**, with the exporter up at 60 of 60 steps; its `kubelet_volume_stats_capacity_bytes` reads 9.75 GiB (the Hetzner floor), which the meter never reads. The fallback (logical size × instances) was not needed.
- **Kind:** `storage_capacity_gb_seconds` (`store.UsageKindStorageCapacityGBSeconds`), migration `0355_storage_capacity_meter` (both `CHECK` lists; the down removes the kind's rows and streams).
- **Meter:** `queryStorageCapacityGBSeconds` (`lego/backend/internal/usage/service.go`) sums each claim matching `^<datastoreClusters>-[0-9]+$` (primary, HA standby, each read replica's cluster) at every 60 s step of the hour, `÷ 2^30 × 60`. A second query counts the exporter's up steps: none (or a failed query) writes no row and records the `storage` source unavailable; fewer than 60 writes the row degraded. Only a Postgres has the meter (`datastoreEntry.meterKinds`); the name-capture failure path records its health too. The stream expects rows from the first window the meter measures (`datastoreEntry.expectedFrom`), so November does not read as partial on deploy.
- **Tests:** `TestQueryStorageCapacityGBSeconds` (full hour 36,000; HA pair + replica sum; half-hour 18,000; no volume 0; partial exporter degraded; the claim pattern takes `-1`, `-2` and a replica's instance, not `-1-wal`), `TestStorageCapacityUnavailableWritesNoRow`, `TestDatastoreWindowWritesCapacityForPostgresOnly`, `TestStorageCapacityCatchUpReadsEachWindow`, `TestStorageCapacityMigrationDownUpPG`. The backend suite passed against real Postgres, OpenFGA and OpenBao.
