# 649 — The registry still restarts zot once when its storage settings change (`ensureStorageActive`, w8/m156), including on a fresh install's first App, though zot v2.1.22 reloads those settings live: drop the restart as w4/m347 did for credentials

Why: w4/m347 found that the pinned zot (v2.1.22) reloads its password file and access-control config while running, and replaced the credential-activation restart with a pod-annotation nudge. The one remaining routine restart is `ensureStorageActive` (`lego/operator/internal/registry/storage_active.go`), which rolls the single zot pod when the storage settings (garbage collection, retention) change — on a fresh install that is the first App's build. A zot restart drops in-flight pushes and pulls for every workspace (round 190's failure mode).

- **Source / severity / estimate:** `/loopx w4` closeout of w4/m347 (2026-11-14), from the implementer's reading of zot v2.1.22. **Minor** (rare: storage settings change on install and on deliberate config changes). ~40m.
- **Premise to verify first:** zot v2.1.22 applies a changed `storage.gc`/`retention` config without a restart. The implementer read that retention reloads only when zot's metadata database is enabled; check the pinned config (`deploy/gitops/base/` zot values) and zot's config watcher at v2.1.22. If a setting truly needs a restart, keep the restart for that setting only and say so in ADR022.
- **Fix:** write the storage settings, nudge the pod as `verify.go` does for credentials, and confirm activation by observing the setting (or keep a last-resort restart behind the same `bex_registry_activation_restarts_total` alert).
- **Tests:** a storage-setting change patches no pod template and deletes no pod; the last-resort path still restarts after its timeout.
- **DoD:** on the mock cluster, a storage-setting change leaves `zot-0`'s restart count unchanged and the new setting is in effect.
