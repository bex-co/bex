# 523 — Opening `/agents/<unknown session id>` leaves the page empty for about five seconds before "Couldn't load this session", and the tab is titled "Page not found" the whole time

Why: a mistyped or stale agent-session link (or one from another workspace) shows a page with only breadcrumbs for ~5 s, with no skeleton, spinner or message, and a tab title that says "Page not found" while the eventual body says "Couldn't load this session — Forbidden". A user cannot tell whether the page is loading, broken or empty, and the two statements disagree.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 113, 2026-11-05 UTC (`muse.env`, `bex-canary`); **minor**; ~30m.
- **Probe:** read-only, signed in. The workspace has no agent sessions, so any id is unknown. `page.goto("https://dashboard.bex.co/agents/qa-not-a-session", { waitUntil: "commit" })`, then `document.title`, skeleton count and `main` text sampled every 250 ms (changes only), t = 0 at navigation:

  | t (ms) | `document.title` | skeleton elements | `main` text |
  | --- | --- | --- | --- |
  | 771 | `Something went wrong ・ bex Dashboard` | 0 | empty |
  | 1276 | `Something went wrong ・ bex Dashboard` | 3 | `Agents qa-not-a-session Search ⌘ K New P` |
  | 1530 | `Page not found ・ bex Dashboard` | 3 | same |
  | 2044 | `Page not found ・ bex Dashboard` | 0 | same (breadcrumbs and header only) |
  | 6894 | `Page not found ・ bex Dashboard` | 0 | `… All sessions Couldn't load this session Forbidden` |

  - Between about 2.0 s and 6.9 s nothing is announced or drawn: no skeleton, no spinner, no `[aria-busy]`, no live-region text. The sampler saw no change in that window; an earlier probe read the same empty `main` at 1 s, 3 s and 6 s.
  - A 200-status GraphQL response comes back each time (5 `POST /graphql` in the first probe), so this is not a transport hang.
  - Control: the other detail routes handle an unknown id differently and consistently. `/services/<id>`, `/blueprints/<id>`, `/env-groups/<id>`, `/keyvalue/<id>` and `/databases/<id>` redirect to `/` within 300 ms with the toast `That resource doesn't exist or was deleted.`, and `/webhooks/<id>` shows a full 404 page.
- **Root cause:**
  - Blank gap: `dashboard/src/routes/agents_.$agentSessionId.tsx:123-130` renders three mutually exclusive branches: `<DetailSkeleton />` when `loading && !session`, `<LoadErrorState />` when `!loading && !session && error`, and the chat column when `session`. The fourth state, `!loading && !session && !error`, renders nothing. The timing suggests the page sits in that state until the first poll returns the error: `useAgentSession` (`features/agent-sessions/hooks/use-agent-session.ts:28-52`) is `cache-first`, starts polling at `AGENT_SESSION_ACTIVE_POLL_MS = 5_000` (`hooks/use-agent-sessions.ts:23`) while the session is not loaded, and the error card appears about one interval after the skeleton disappears (2.0 s → 6.9 s). This mechanism is inferred from the code and the timeline; I did not read Apollo's cache-first internals.
  - Title: the route's title loader (`:79-92`) returns `not-found` when the query has no data and either no error or a `NOT_FOUND` code (`common/lib/document-head/index.ts:129-131`), and `routeResourceTitle` maps that to `common.notFoundTitle` ("Page not found"). The earlier `Something went wrong` is the transient error title. Which of the two conditions applies here (an error dropped by `errorPolicy: "all"`, or a `NOT_FOUND` code on the Forbidden answer) is not verified.
- **Fix (target behavior):**
  - The page never renders an empty content area: when no session is loaded and no query is in flight, it shows the error or not-found state immediately instead of waiting for the next poll (for example treat `!session && !loading` as the error state with the `common.loadErrorRetry` fallback message, or surface the title loader's failed result to the hook).
  - The tab title names the same state as the body. The API deliberately answers Forbidden for an unknown or inaccessible session, so the body's wording stays non-revealing and the title should not claim "Page not found" when the body says it could not load.
  - Keep `useLoaderErrorRetry` and the 5 s poll as they are.
- **Tests:** a page-level test that mocks `useAgentSession` as `{ session: null, loading: false, error: undefined }` and asserts a visible state (never an empty content area), and a head test that the title and body agree for the failed-load case.
- **Blast radius:** one route. The same three-branch shape was not searched for in other routes; the detail routes I probed handle unknown ids through the shared dead-id redirect and are not affected.
- **Adjacent classes:** forbidden and not-found stay indistinguishable to the caller (no existence oracle); unauthenticated keeps its own state (`common/lib/document-head/index.ts:127`).
- **Unverified:** an existing session (the workspace had none, and starting one costs money), an id from another workspace that exists, narrow-width and zh renderings, and whether the 5 s comes from the poll (inferred) rather than a retry.
- **Render:** n/a (the reference for agent sessions is Devin; its behavior for an unknown session link was not compared).
- **Dedupe:** `grep -rli "Couldn't load this session" .pm` finds only w5/m80 (done), which is about server-side failure reliability; no item covers the blank interval or the title. No DO_NOT_DO item applies.
