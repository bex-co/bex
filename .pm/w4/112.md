# A machine token is granted `scope: "bex.read"` and then writes: the scope is echoed but never applies

Why: `client_credentials` against a workspace API key returns `{"scope":"bex.read"}`, and that token then performs a persisted write — correctly, by design, because capability scopes are a human-delegation concept and machine keys deliberately carry none; but nothing tells the caller that, so anyone who mints a key and asks for `bex.read` believes they are holding a read-only credential and is wrong.

**This is not an authorization bypass.** The behavior matches the design recorded in `core.Identity.CanonicalScopes` (`lego/backend/internal/core/identity.go:57-61`): _"Empty for Kratos sessions and machine API keys, which are not human-delegation grants and must not acquire one from a default."_ `w4/m106` scoped its enforcement work to **human** OAuth for the same reason. The defect is that the grant advertises a restriction the platform never promised to honor.

Found by live `/qa-find-bugs` 2026-09-21 pass 115 (w4-targeted, `muse.env` credentials), on throwaway service `qa-20260921-scope` and eight throwaway API keys, all deleted/revoked.

## Repro

```
# 1. mint a workspace API key, then exchange it for a read-scoped token
POST https://oauth.bex.co/oauth2/token
     grant_type=client_credentials&client_id=<key id>&client_secret=<secret>&scope=bex.read
→ 200 {"access_token":"<opaque>", "scope":"bex.read"}          ← the grant says read

# 2. use it to write
PATCH https://api.bex.co/v1/services/srv-daofja3s0ils73bgpec0
      Authorization: Bearer <that token>
      {"serviceDetails":{"maxShutdownDelaySeconds":61}}
→ 200

# 3. read back, independently, with session auth
GET  https://api.bex.co/v1/services/srv-daofja3s0ils73bgpec0
→ serviceDetails.maxShutdownDelaySeconds = 61      (was 137)
```

The write persisted. Verified as a genuine delta, not a no-op 200: the value was 137 before and 61 after, read back through a different credential.

## What the surfaces currently tell a caller

| surface                                                    | says                                                            |
| ---------------------------------------------------------- | --------------------------------------------------------------- |
| `api.bex.co/.well-known/oauth-protected-resource` (RFC 9728) | `scopes_supported: ["bex.read","bex.write","bex.sensitive"]`     |
| `oauth.bex.co/.well-known/openid-configuration`               | `scopes_supported: ["offline_access","offline","openid"]` — no `bex.*` |
| the token response for a machine key                          | `"scope":"bex.read"` — granted, echoed, not enforced             |
| an unknown scope                                              | `400 invalid_scope … not allowed to request scope 'bex.nonexistent'` |

A client that discovers scopes the documented way (the protected-resource document) will request `bex.read`, be told it was granted, and hold a credential with full workspace authority.

## Options

- **(a) Refuse `bex.*` on `client_credentials` for a machine key.** The loudest and least surprising: the request fails the way `bex.nonexistent` already does, so nobody can hold a token whose `scope` claim is inert. Risk: an existing integration that requests `bex.read` today would start failing — check whether the official CLI or MCP client does before choosing this.
- **(b) Grant it but say so** — return the scope alongside something that makes the semantics explicit, and document in ADR012/ADR025 that machine keys are workspace-role credentials whose scope string is not a capability restriction.
- **(c) Make it real** — give machine keys genuine scope enforcement. The largest change, and it argues against the recorded design rather than with it, so it needs a decision rather than an implementation.

Recommend (a) plus the ADR line from (b): a credential should never claim a restriction it does not have.

Estimate: ~40m for (a) + the ADR note + a test that a machine `client_credentials` exchange cannot acquire a `bex.*` scope; more if the CLI turns out to request one.

## Blast radius to check first

`grep` the CLI and MCP client for `bex.read` / `scope=` on the `client_credentials` path — `docs/bex-cli.md:100` and `docs/ADR025-connect-an-agent.md:54` both document `https://oauth.bex.co/oauth2/token`, so at least one first-party client may be requesting these scopes today. Option (a) is only safe once that is known.
