# Generate Blueprint accepts selection changes while returning the previous selection's manifest

Why: an accepted checkbox change during generation is silently replaced by an export of the older selection, making the copy/download preview disagree with the selection retained by Back.

**Status:** todo. **Worker:** worker4. **Severity:** minor. **Estimate:** 55m (consumer review 5m, pending selection lock 15m, behavioral regressions 25m, live replay and cleanup 10m). Functional dashboard QA a262, 2026-10-12 UTC; source HEAD `2c7d9d58959e1a0a8d9afa5aebce78e0408d408f`. Deployed dashboard revision was not observed. The relevant component is unchanged between this hunt's initial `7a4923b39` and updated main.

**Target behavior:** keep the selection submitted to Generate fixed while that operation is pending. Disable its resource checkboxes immediately when generation begins; do not accept edits that the pending output cannot represent. After a successful preview, Back restores the same selection and enables editing. After an error, keep the submitted selection editable for retry. Closing remains available and fresh reopen stays empty.

## Cause, consumer census and bounded fix

- `dashboard/src/features/blueprints/components/generate-blueprint-dialog.tsx:25–49`: private SelectableList has no pending/disabled input; its controlled Checkbox always forwards onCheckedChange to toggle.
- `:109–120`: toggle updates selected and clears manifest during the request. `:122–138`: handleGenerate submits the then-current four ID arrays and unconditionally sets the returned manifest when its promise resolves. Changing selected does not change those submitted variables.
- `:169–192`: **four** production SelectableList uses in this one component: Services, Databases, Key Value and Environment Groups. `:210–217`: only Generate uses selectionEmpty || loading. The loading signal is already explicitly enabled by notifyOnNetworkStatusChange:true at :79–84.
- **Consumer opened:** `common/components/ui/checkbox.tsx:7–25` accepts the real primitive props and spreads them onto CheckboxPrimitive.Root. Installed/lockfile-pinned **@radix-ui/react-checkbox 1.3.3**, `node_modules/@radix-ui/react-checkbox/dist/index.mjs:96–119`, renders a native button with disabled and toggles controlled checked state through its click handler. The [official checkbox API](https://www.radix-ui.com/primitives/docs/components/checkbox) also exposes disabled. A local disabled prop can express the required behavior without changing the shared Checkbox wrapper.
- **Actual query framework opened:** installed/lockfile-pinned **@apollo/client 4.1.3**, `node_modules/@apollo/client/react/hooks/useLazyQuery.js:52–60,103–118`, subscribes to the observable result and executes observable.reobserve with the explicit executeOptions.variables. An unrelated React selection update does not resubmit these variables. The network receipts agree with that path. This is not a query-cache bug: this component already uses no-cache, and both requests and responses faithfully represent the original IDs.
- **One production entry:** exhaustive component/symbol search finds one GenerateBlueprintDialog definition and one mount, `routes/blueprints.tsx:168–170`, conditioned on generating. Canonical entry is /blueprints → Generate Blueprint. There are no separate service/datastore route mounts of this dialog. The service selector includes web/static/cron/worker/private kinds; the remaining categories cover Postgres, Key Value and environment groups. The live timing reproduction covers only owned web + group.
- **Backend control opened:** `lego/backend/internal/apps/graphql.go:1263–1281` copies the supplied ID arrays into GenerateBlueprintRequest. `blueprint_generate.go:178–188,221–227` resolves only explicitly selected groups and emits envVarGroups only for a nonempty request EnvGroupIDs array. The service-only and combined live requests prove the current generator works for these cases. Preserve its request/serialization semantics.
- **Existing test gap:** `generate-blueprint-dialog.test.tsx:15–17` permanently mocks loading:false. Its successful selection/preview and wide-manifest tests cannot exercise this pending transition.

**Work:** pass a pending disabled flag through these four private lists, guard selection changes while the operation is pending, and preserve the current enabled selection after settlement. Review whether a local synchronous in-flight intent is needed between execute and its loading emission; retain the query's loading notification and existing double-submit guard. Scope this to this export dialog. Keep Close cancellation, Back, download bytes, Unicode names and the fixed bounded preview geometry. Keep the shared Checkbox component and API adapters unchanged.

**Pre-settle and adjacent states:** before a response arrives, show the same checked selection with disabled resource toggles and the existing pending Generate state. Success opens that selection's result. Generation errors/missing data keep the selected IDs and restore editing through the existing toast path. Existing session, permission, transport, timeout and validation outcomes remain in their current paths; this change does not introduce new error classifications.
