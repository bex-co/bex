# Keep first Blueprint cron reapply idempotent

Why: an unchanged cron Blueprint should not create another deployment solely to move its command between equivalent fields.

**Status:** todo · **Worker:** worker4 · **Estimate:** 50m. Found during w4/m146 serialized apply regression work on 2026-10-02. Goal: ADR049 repeat-apply idempotence and ADR008 dependable hosting.

The five-kind regression exposed a separate command difference when a cron manifest includes `startCommand: echo ok`: initial Blueprint creation stores `App.spec.startCommand`, while identical reapply also populates `App.spec.command`. The image-default cron fixture isolates m146's empty-environment bug; this note retains the independent finding.

`lego/backend/internal/apps/deploy.go`'s `serviceCreate` constructs `CreateRequest.StartCommand` for every service kind. `specFromCreate` stores that field, while `applyOptionalCreateSpec` only fills cron Command from `CreateRequest.Command`. Conversely, `applyBlueprintCommand` in `blueprint_plan.go` uses StartCommand as a fallback for cron Command. The operator already falls back from Command to StartCommand, so execution works; the defect is a false change and unnecessary deployment.

Canonicalize the Blueprint cron create request and add create → JSON reload → unchanged plan/apply regressions for both manifest command aliases. Assert noop, unchanged ID/spec/restart timestamp and no additional deployment; preserve genuine command updates and existing direct API command behavior. Run the backend suite and lint.

Dedupe: w4/done/m124 covers exported canonical cron state → replan, not this newly-created representation. Existing w1 command-projection work addresses direct REST/runtime behavior. This is a source/local regression finding; no new production fixture or live claim is involved.
