# 601 — The Events tab shows a deploy's duration as raw rounded seconds ("930s"), while its own Deploys list and header show "15m 29s"

Why: the same deploy reads two different durations on two tabs of one service, in two formats and off by a second. A long build or a failed health gate reads as an unparsed seconds count only on Events.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 175, 2026-11-12 07:28 UTC (`muse.env`, workspace `bex-canary`; pin `10acf5314735`). **Minor** (cosmetic, but it is a disagreement between surfaces). ~20m.
- **Fixture:** Starter web service `qa-20261112-r175-web` (`srv-dbqm93s5ph4s73f9gpbg`), deleted afterwards. Its deploy `dep-dbqmas45ph4s73f9gph0` (nginx with a Health Check Path that 404s) failed `update_failed`. REST has `startedAt 2026-11-12T07:06:39.955445Z` and `finishedAt 2026-11-12T07:22:09.80142Z`, which is 929.85 s.
- **Probe (accessibility snapshots, `?lang=zh`; en renders the same strings):**
  - Deploys list: the row reads `row "失败 dep-dbqmas45ph4s73f9gph0 … 6 分钟前失败 API 部署 15m 29s"`.
  - Events: both the `部署已完成` and the `部署已开始` rows read `text: docker.io/library/nginx:1.27-alpine 930s`.
  - Other deploys this round read the same way on Events: `60s` (`qa-20261112-r175-as`'s first deploy) and `29s` (`qa-20261112-r175-sup`'s suspended deploy).
- **Root cause:** Events hand-rolls its own duration.
  - `dashboard/src/routes/services.$serviceId.events.tsx:475-482` computes `Math.round((finishedAt - startedAt) / 1000)`, and `:564` renders it as `{deployDuration}s`.
  - The deploy surfaces use the shared `formatDeployDuration` (`dashboard/src/features/deploys/lib/deploy-presentation.ts:38-62`). It floors to whole seconds, with a minimum of 1 s, and formats `Ns` / `Nm Ns` / `Nh Nm`. Its two production callers are `deploys-list-page.tsx:89` and `deploy-header.tsx:86`.
  - Different rounding (round vs floor) and different units, so 929.85 s reads `930s` on one tab and `15m 29s` on the other.
- **Fix (target behavior):**
  - The Events row's duration is `formatDeployDuration(startedAt, finishedAt)`, character for character what the Deploys list and header show for that deploy: `15m 29s` here, `1m` for a 60 s deploy, `29s` for 29 s.
  - It renders nothing when that returns null (no `startedAt`, or `finishedAt` before `startedAt`), as the list does.
  - Delete the hand-rolled computation.
  - Test: an Events row for a 929.85 s deploy renders `15m 29s`, and a deploy with no `startedAt` renders no duration.
- **Blast radius:**
  - One call site changes.
  - `formatDeployDuration` itself is unchanged, so its two existing callers are unaffected.
  - `grep -rn '}s</span>' dashboard/src/routes` finds only `:564`.
- **Adjacent, not in scope:**
  - The `m`/`s`/`h` unit letters are not translated in zh, in either place.
  - Cron run durations (`features/services/components/cron-runs-section.tsx`) have their own formatter, not probed this round.
- **Render:** n/a. This is an internal disagreement; Render's dashboard shows one duration format per deploy.
- **Dedupe:**
  - w4/089 (done) recorded `Build ended — Canceled` with `(1081s)` in its Events probe without flagging the format.
  - w4/m156 and w6/m123 (done) concern zero or missing durations, not their format.
  - `grep -rln "deployDuration" .pm` finds no open item.
  - Not deploy lag: the one later commit to the route, `2499fc785` (w8/m158), does not touch the duration.
- **DoD (live):** on an owned service with a deploy longer than a minute, the Events tab's duration for that deploy equals the Deploys list's (`Nm Ns`), in en and zh.
