# 490 — A malformed resource id in the path answers `500 internal error` instead of 404: Postgres and Key Value (an id containing `/`), and projects, environments and registry credentials (invalid UTF-8); w4/052 guarded only the App path

Why: a mistyped or hostile id is reported as a server failure, which pollutes 5xx monitoring and alerting, shows a customer "internal error" instead of "not found", and diverges from the 404 that Render and bex's own services, env groups and blueprints already give for the same input.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-05 ~01:15 UTC (`muse.env`, workspace `bex`; read-only GETs, 450 ms apart, no rate-limiting involved); **minor** (a malformed id was never going to resolve; the defect is the status class and message); ~45m.
- **Regression of / extension of:** w4/052 (done 2026-09-07). Its title and Why are about exactly this ("a malformed resource ID returns HTTP 500 'internal error' instead of 404"), but its fix and its regression tests cover only `core.Base.AuthorizeApp` and `GetApp` (the services path), and its verification table probed only `dpg-!!`, `dpg-`, `red-!!`, `evg-!!`, all valid path segments. The two classes below are not in that table and are still live.
- **Probe** (in-page `fetch(..., {credentials:'include'})` against `https://api.bex.co`; each cell is the status of `GET <route>/<id>`, `500` bodies are `{"error":"internal error","id":"internal_error","message":"internal error"}`; reproduced twice, once as part of a 128-request sweep and once on its own):

  | id sent (URL-encoded) | `/v1/postgres/{id}` | `/v1/key-value/{id}` | `/v1/postgres/{id}/connection-info` | `/v1/projects/{id}` | `/v1/environments/{id}` | `/v1/registrycredentials/{id}` |
  | --- | --- | --- | --- | --- | --- | --- |
  | `a%2Fb` (decodes to `a/b`) | **500** | **500** | not run | not run | not run | 404 |
  | `..%2F..%2Fetc` (decodes to `../../etc`) | **500** | **500** | **500** | 404 | 404 | 404 |
  | `%C0%80` (overlong NUL, invalid UTF-8) | 404 | 404 | 404 | **500** | **500** | **500** |
  | `%ED%A0%80` (lone surrogate, invalid UTF-8) | 404 | 404 | not run | **500** | **500** | **500** |
  | `%FF%FE` (invalid UTF-8) | 404 | 404 | not run | **500** | **500** | **500** |
  | `a%20b`, `a%23b`, `a%3Ab`, `a%5Cb`, `a%2A`, `a%0Ab`, `t%C3%A9a` (é), `DPG-ABC`, 3000 × `x` | 404 | 404 (é) | not run | 404 (é) | not run | 404 (é) |

  Controls on the same request: `GET /v1/services/{id}`, `/v1/env-groups/{id}`, `/v1/blueprints/{id}`, `/v1/webhooks/{id}`, `/v1/disks/{id}` and `/v1/build-sources/{id}` answered `400`/`404` for every id above, never 5xx. `%00` and `a%00b` as a path segment never reach the API from a browser (`fetch` fails before a response; an edge or server refusal), so they are not part of this finding.

- **Root cause A (Postgres, Key Value: a path id containing `/`):**
  - Both by-id resolvers go through `findDatabase` / `findKeyValue` (`lego/backend/internal/core/base.go:1618`, `:1640`), which call `getInDatastoreNamespaces` (`core/base.go:1670-1682`, 2 callers: `:1620`, `:1642`). That function does `b.Client.Get(ctx, client.ObjectKey{Namespace: ns, Name: name}, out)` with the caller's raw `name` and returns any error that is not `NotFound`.
  - client-go refuses a name that is not a valid path segment (`/`, `%`, `.`/`..`) before it reaches the apiserver, and that client-side error is not `IsNotFound`, so it is returned and rendered as 500.
  - w4/052's fix put `pathvalidation.IsValidPathSegmentName(candidate)` guards in front of the `Get` calls at `core/base.go:1227` (`AuthorizeApp`) and `:1885` (`GetApp`) and skipped the name when it fails. `getInDatastoreNamespaces` has no such guard. That is the whole asymmetry between the services row (404) and the datastore rows (500).
  - `a/b` is the only trigger I verified; `%` and `.`/`..` are also invalid path segment names, but `..` is normalised away by the router before the handler (`GET /v1/postgres/..` answered 404) and `a%25b` (a literal `%`) was not run against Postgres.
- **Root cause B (projects, environments, registry credentials: invalid UTF-8):**
  - These three are Postgres-backed. Their by-id reads bind the path id as a SQL parameter: `PGStore.GetProject` (`store/projects.go:43-52`), `PGStore.GetEnvironment` (`store/environments.go:94-97`), `PGStore.GetRegistryCredentialByID` (`store/registrycredentials.go:122-129`).
  - `classify` (`store/store.go:2904-2919`) turns `pgx.ErrNoRows` into `ErrNotFound` and three constraint codes (`23505`, `23503`, `23514`) into typed errors, and returns every other error untouched. An error the handler cannot classify becomes the generic 500.
  - PostgreSQL's `text` type rejects bytes that are not valid UTF-8, so a bound `$1` that is invalid UTF-8 raises a data-exception error (SQLSTATE class `22`) instead of matching no row. That fits the set that fails (overlong NUL, a lone surrogate, `FF FE`) against the set that passes (valid Unicode such as `é`, spaces, `#`, `:`, 3000 characters). I could not read the server log to see the driver's message, so the SQLSTATE is inferred from the observed set, not quoted.
  - The services, env-group, blueprint, webhook, disk and build-source routes either resolve ids through Kubernetes or validate the id shape first, which is why they are the clean controls.
- **Fix (target behavior):**
  - **A:** `getInDatastoreNamespaces` skips any name for which `pathvalidation.IsValidPathSegmentName(name)` reports problems and returns not-found, the same way `AuthorizeApp`/`GetApp` do. One change covers Postgres and Key Value, every verb that resolves through `findDatabase`/`findKeyValue`, and REST, GraphQL and MCP.
  - **B:** an id that is not valid UTF-8 resolves to not-found before it is bound as a SQL parameter, or `classify` maps SQLSTATE class `22` data exceptions to `ErrNotFound`/`ErrInvalid` so each `Get*` stops turning them into 500. Prefer the second, because it also covers the other `$1`-bound lookups (see Blast radius) with one edit; add the first as a guard where an explicit 404 is wanted.
  - A real store or apiserver failure (connection refused, timeout, cancelled context) must stay a 500/503, as in w4/052. The tests need a failing store to prove it.
- **Blast radius:**
  - **A:** `getInDatastoreNamespaces` has 2 callers (`core/base.go:1620`, `:1642`), which feed `AuthorizeDatabase`/`AuthorizeKeyValue` and so every by-id Postgres and Key Value verb. Regression tests must include the ids that resolve today (`dpg-…`, `red-…`, legacy names) so the new guard cannot start rejecting a legal id.
  - **B:** `classify` is called from the store's by-id readers across the package; `grep -c 'classify(' store/projects.go store/environments.go store/registrycredentials.go` gives 4, 4 and 7. Changing `classify` is global to every store entity that uses it (`workspace`, `environment group`, and others), so list the callers before editing and add a regression test on one that already answers correctly.
  - The same `$1`-bound path ids also feed the related reads under each of those resources (`/v1/environments/{id}/…`, `/v1/projects/{id}/…`, `/v1/registrycredentials/{id}` PATCH/DELETE); only the GETs were probed.
- **Adjacent classes:** well-formed but unknown id stays 404; a resource that exists in another workspace stays 403/404 exactly as today (no existence oracle: the new checks look only at the string); unauthenticated stays 401.
- **Unverified:**
  - Write verbs (`PATCH`, `DELETE`, `POST …/suspend`, …) on the same ids: read-only run, and they share the resolvers, so they are expected to 500 identically.
  - GraphQL (`database(id:)`, `project(id:)`) and MCP (`get_postgres`, `get_key_value`, `get_project`) with these ids.
  - Cause B's SQLSTATE (inferred), and whether a literal `%` (`a%25b`) triggers cause A on Postgres.
  - `/v1/owners/{id}`: it answered `503 authorization service unavailable` for ids with a space, newline, `#`, `:` or 256+ characters. That is a third mechanism (OpenFGA rejecting the object, mapped by `checkAuthz`) and is recorded as an addendum to w4/489, not here.
- **Render:** Render answers an unknown or malformed id with a JSON `404`; none of its documented routes returns a 5xx for a bad path id.
- **Dedupe:** w4/052 (above) is the same class on a different resource family; w4/053 and w4/054 are "internal error" for bad metrics/logs input (done, unrelated routes); w4/489 is the `ownerId` query-parameter 503. No item covers a `/` in a datastore id or invalid UTF-8 in a project, environment or registry-credential id. Nothing in `.pm/DO_NOT_DO.md` applies. The fix is not on `main`.
