# Global Search declares no matches while result lists are still loading

Why: a user searching for an existing resource sees a definitive empty result while the index is still arriving and can leave before its matching option appears.

**Severity:** minor. **Estimate:** 55m (scoped UI state + temporal regression tests + live acceptance). `/pm add w4`, user-requested functional `$qa-find-bugs` loop, 2026-10-10 pass a38, muse.env, main `ebaca0dee`. Filing only; no product fix is implemented here.

Read-only workspace `tea-d98210cbbpdc73dcrkvg`. Existing Blueprint `discourse_docker` / `blp-d9nqg95cavls73fp8m10`; its API status is error, but the successful read still supplies its name and it becomes a valid search option after loading.

## Expected state and scoped fix

While any required resource list has not completed its initial read, show an explicit non-selectable **Loading…** status and keep already-matching navigation/resources usable. Show **No matching pages or resources.** only after the search’s relevant lists have settled and its computed navigation/resource matches are empty. Once the pending Blueprint arrives, show the matching option without losing the entered text or focus. Closing/reopening retains the existing reset behavior.

- `dashboard/src/common/components/dashboard-layout/global-search-dialog.tsx:73` renders `CommandEmpty` outside `SearchResults`, so it has no query-loading information.
- `:102–110,160–172` loads **six categories** and computes aggregate loading plus the total count of all loaded resources. `:212,233` only renders a loading item when `loading && resourceCount === 0`. A cached, unrelated service makes resourceCount positive, suppressing the loading item even if the searched-for Blueprint is still pending.
- `:207–212` guards Resources by matched arrays, so with no currently matching items both groups can be absent. The outer CommandEmpty then sees zero registered items and displays the definitive empty text.
- Actual installed **cmdk 1.1.1**, pinned by `dashboard/yarn.lock:6432`, was opened at `node_modules/cmdk/dist/index.mjs:1`: its `J()` with shouldFilter=false sets filtered.count to the registered item set’s size; `Command.Empty` renders precisely when filtered.count===0. It has no knowledge of Apollo requests. `common/components/ui/command.tsx:85–92` delegates directly to that primitive.

Move the empty/pending decision into the component that knows both loading and the explicitly filtered arrays, or lift that state to the dialog. Gate complete-empty on settled sources **and** zero computed matches, rather than relying solely on cmdk registration timing (a newly arriving item can register after a render). Render loading while the index is incomplete even when unrelated cached lists are populated. Keep the existing literal matcher, resource options and group/separator guards. No fetch-policy, API, shared CommandEmpty wrapper or cmdk patch is needed.
