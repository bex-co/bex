# Logs "Filters" popover opens partly off-screen on short windows, hiding the Level control

Why: on a laptop-height window the filter panel is cut off at the top (Level is unreachable) or at the bottom (Request path is clipped), because the shared popover never caps its height to the space available, unlike the repo's own Select and DropdownMenu.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop run e38f, 2026-10-29 UTC (`muse.env`, pin `b0804030f4d3`); **minor** (scrolling the page before opening is a workaround), ~25m. Dashboard usability.
- **Repro:** open any running service's `/services/<id>/logs`, set the window to 999×549 (CSS px) and click **Filters**. Measured with `boundingBox()` on the `dialog`:

  | viewport | Filters button y | popover top → bottom | result |
  | --- | --- | --- | --- |
  | 999×549 | 293 | −77 → 289 | top 77 px off-screen; **Level** select at y −36 can't be clicked (Playwright: "element is outside of the viewport") |
  | 1280×640 | 253 | 289 → 655 | bottom 15 px clipped (Request path input) |
  | 1366×768, 1440×900 | 253 | 289 → 655 | fits |
  | 390×844 | — | 464 → 830 | fits |

  The panel is a fixed 366 px tall: four selects plus a path input.

- **Expected:** the popover never extends past the viewport. When neither side has room for the full height, it caps at the space Radix reports and scrolls inside, so every control stays reachable.
- **Root cause:** `dashboard/src/common/components/ui/popover.tsx:30` (`PopoverContent`) has no `max-h`/`overflow-y-auto`. Radix flips to whichever side has more room (`avoidCollisions` defaults on) but cannot shrink content. The siblings already handle this: `select.tsx:63` uses `max-h-(--radix-select-content-available-height) … overflow-y-auto`, and `dropdown-menu.tsx:45` does the same with the dropdown variable.
- **Fix:** add `max-h-(--radix-popover-content-available-height) overflow-y-auto` to the shared `PopoverContent` base classes. Keep `p-4`, the width and the animations. Callers' own `className` still merges after it.
- **Blast radius (4 production callers, `grep -rl "<PopoverContent" dashboard/src`):**
  - `features/logs/components/log-filter-bar.tsx:222`: the defect.
  - `features/events/components/service-event-filter.tsx:114` (`p-0`, inner `ScrollArea max-h-80`): caps itself today. Check that the outer cap does not create a second scrollbar; a single scroll container is the target.
  - `features/git/components/git-credentials-menu.tsx:98` (inner `ul max-h-64 overflow-y-auto`): same check.
  - `common/components/ui/combobox.tsx:243` (`p-0`, explicit width; 3 `<Combobox>` callers): its list should keep scrolling inside the list, not the shell.

  Add a component test asserting the class is present, and do a manual 999×549 / 1280×640 / 390×844 check on Logs → Filters and on the Events filter.

- **Adjacent states:** the filter count badge, Escape and outside-click close, and focus return to the Filters trigger are unchanged.
- **Unverified:** the Events filter, git-credentials menu and combobox popovers were not measured at short heights this run.
- **Also probed and passed (same run):** a busybox web image printing `qa-out N alpha` to stdout and `qa-err N bravo` to stderr every 3 s. Live tail appended both streams. Search `alpha` returned 35 lines, all of them `alpha` lines. Search `response:404` narrowed to httpd's request lines.

- **Dedupe:** `.pm` has no popover-height item. `w4/done/179.md` covered a mobile Postgres dialog and plan menu overflowing horizontally, which is a different component and axis. Nothing on `main` touches `popover.tsx`. No DO_NOT_DO item applies.
