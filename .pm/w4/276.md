# Cron settings can undo a previous save after a late refresh

Why: Saving only Command can undo the schedule just saved, and saving only Schedule can restore an older command that then runs.

- Severity: **major** — persisted schedule/command rollback, reproduced in both directions.
- Estimate: **55m**: caller audit 5m, local ordered refresh and refresh-failure state 20m, real Apollo behavioral tests 15m, live/parity replay 10m, simplify 5m. One bounded cron-settings correction; inbox sizing.
- Source: continuous functional `$qa-find-bugs`, pass **a289**, 2026-10-12 UTC, requested w4 destination. Credentials stayed inside the login helper. Research main `f4b8970b2`; filing only.

## Reproduction and observable target

Create an owned Free BusyBox image cron, initially schedule `0 0 15 * *`, with a harmless printf command. Wait for Running/Live, then open Settings. The two persisted rollback reproductions below deliberately hold **one actual, unmodified background Server response** until after a successful UI save. This controls ordinary network response ordering; it does not invent API data, change production response bodies, or write backend state outside the normal dashboard mutations. Naturally stale readonly schedule values were also observed after a save, but their request ordering was not captured and is not the proof of persistence here.

**Desktop, 1440px:** the older Server read captured `0 0 15 * *` at **11:31:04.460**. Save Schedule as `0 0 16 * *`: UpdateCronJob succeeds at **11:31:04.803**, and the disabled field immediately shows the new schedule while the older response is still held. A fresh independent API read at **11:31:05.061** confirms the new schedule and nextRunAt **2026-10-16T00:00:00Z**. Release the older response. At **11:31:05.314** Settings displays day 15 again. Edit **only Command**, save at **11:31:05.686**: the request replays day 15. Fresh read at **11:31:05.883** confirms that schedule and nextRunAt **2026-10-15T00:00:00Z**. No schedule edit occurred in this second save.

**Mobile, 390×844:** the older Server read captured command `sh -c 'printf "qa-a289-after-stale\n"'` at **11:33:14.713**. Save Command as the corresponding `qa-a289-mobile-live` marker. The new command appears immediately at **11:33:15.063** while the response remains held, and a fresh read at **11:33:15.266** confirms it. Release the older response. At **11:33:15.522** the disabled Command has reverted to the old marker; the screenshot below captures that state. Edit **only Schedule**, then Save: the request at **11:33:17.470** replays the old command. A fresh read confirms it persisted. Document width remains 390px.

The resulting deploy **dep-db6cavc2kg9s73fdsnt0** is Live at **11:33:26.338144Z**. Trigger Run returns **crr-6chni3b4cbacoc5d52l4** pending; it finishes successful at **11:36:10Z**, with native app output **qa-a289-after-stale**, proving the restored command reaches runtime. The backend executed the command the second UI request supplied.

**Target:** once a cron save commits, both rows stay unavailable for another write until pre-save service reads settle and a genuinely fresh read of that same service publishes the authoritative configuration. During that refresh show the accepted value or an honest refreshing state. The next Command-only save must preserve the last accepted Schedule; the next Schedule-only save must preserve the last accepted Command. A newer authoritative configuration wins; a failed refresh must not make stale rows writable or retry the committed mutation.

**Passing controls:** command-then-schedule saves without an overlapping older response preserve both values. Cancel discards an unsaved schedule draft. Both create and Settings accept leap day and mixed day-of-month/weekday schedules, reject February 31 with a star weekday, and avoid uniform interval claims for uneven 40-minute/5-hour steps. Fresh API next-run values were correct. These checks do not close the entire older cron milestones.

## Root cause and shared scope

- `dashboard/src/features/services/hooks/use-cron-job.ts:43–69`: one hook awaits UpdateCronJob, toasts success, returns true and drops busy. It neither settles older Server reads nor publishes an authoritative post-write read.
- `dashboard/src/features/services/hooks/use-server.ts:49–71` reads ServerDocument cache-first and polls. The service detail layout owns its normal timer at `components/service-detail-layout.tsx:44`; settled cadence is **30s**, converging **3s**, in `dashboard/src/common/lib/polling.ts:11,18,47–60`.
- `components/cron-deploy-section.tsx:99–100` replays the current nonempty command when saving Schedule. `:116–117` replays the current schedule when saving Command. Those props can have been replaced by the older normalized Server result.
- `components/editable-field-row.tsx:137–140,159–165` intentionally renders persisted props outside editing and seeds Edit/Cancel from them. Busy already disables inputs and Save/Cancel at `:219–295`. Keep its mounted-draft semantics; this is not the Build Filters local-state initialization defect.
- `api/server.graphql:120–123` selects schedule/command/next-run; `routes/services.$serviceId.settings.tsx:169–173` passes them into **one production CronDeploySection mount**. There is **one production useCronJob caller**, that section, with **two row save callers**. The `/cron/$` compatibility route reaches the same Settings page. All cron source modes use this editor; only Existing Image was live-tested here.
- Exhaustive production search gives **15 useServer call sites**, shared across other service tabs, sidebar/breadcrumbs, deploys and static pages. Audit their cache ownership, but keep this correction local to the cron write completion path. No other write path is claimed broken from this fixture.
- Installed Apollo **4.1.3** is behaving as designed: `dashboard/node_modules/@apollo/client/core/QueryInfo.js:131–139` writes accepted query data to the cache. `core/ApolloClient.js:450–468` exposes individual refetch results as well as the aggregate Promise. Do not change global normalization or polling merely to conceal this ordering.
- The API write is correct: `lego/backend/internal/apps/graphql.go:1427–1441` intentionally requires schedule and allows optional command. `apps/service.go:4301–4320` applies supplied schedule and command. Each fresh read and runtime control agrees with the payload. Preserve null-means-keep and empty-means-clear.

## Bounded fix and meaningful verification

Use the existing ordered-refresh pattern in `dashboard/src/features/projects/hooks/use-rename-project.ts:25–48` as a reference: settle each pending relevant read before a final network-only read that cannot join an older in-flight request. For cron, scope that work to ServerDocument and the written immutable service ID; keep both rows busy through publication. Await each selected result individually, then read by ID with `queryDeduplication:false`; a one-shot refetch that deduplicates onto the held old response is insufficient. Reuse the native Apollo primitives and the repository's existing error/toast conventions.

A committed write followed by a read failure stays a committed write. Offer a read-only refresh retry and keep stale settings unavailable until it succeeds; never replay UpdateCronJob to recover a read. Preserve refusal drafts, Cancel/Escape, explicit empty command clearing, service identity changes and newer authoritative values. Avoid an optimistic merge that makes the just-saved value permanently override later real edits.

Extend the cron hook/section coverage using a **real InMemoryCache and controlled MockLink**, not only mocked useMutation. Current `hooks/__tests__/use-cron-job.test.ts:1–12,37–95` verifies wire values and success/errors but cannot exercise cache arrival ordering. Test both recorded directions; one older result rejected while another remains pending; final refresh rejection and read-only retry with exactly one mutation; unchanged/canceled/refused drafts; null and empty command intent; navigating to another service while refreshing; and the passing no-overlap two-save control. In the first direction assert final next-run calculation stays on day 16; in the reverse direction assert the new command remains configured and runs after the carrying deploy is Live. Run required dashboard checks and simplify the bounded change.

Live replay at desktop and narrow mobile should retain the accepted values through the controlled late response, keep subsequent save payloads correct, reload consistently, and run the intended marker. Preserve the existing API contracts across GraphQL/REST/MCP; only the GraphQL dashboard path was exercised here.
