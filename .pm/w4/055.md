# `logLabelValues` (+ its datastore variants) is a MISSED ALIAS of w4/054 — the `start<end` guard must live in the shared `q.validate()`, not in `QueryLogs`, or the fix ships partial

Why: w4/054 proposes adding the inverted-range (`start<end`) guard "in the logs query validation path (`QueryLogs`, `service.go:460`)" and its blast radius names only `logs` / REST `/v1/logs` / `/v1/logs/subscribe` as funneling through `QueryLogs`. But `LogLabelValues` (`lego/backend/internal/logs/service.go:637`) is a **separate** method that never calls `QueryLogs` — so a fix placed in the `QueryLogs` body leaves `logLabelValues` still returning "internal error" for an inverted range. This corrects 054's fix **location** (and enumerates the aliases) before anyone implements it, so the fix is complete rather than partial.

Source: live QA 2026-09-07, `$qa-find-bugs w4` pass 27 (error-taxonomy fuzzing of the untested read-only GraphQL log surfaces; correction/extension of `w4/054`, batch with `w4/053`).

## Root cause (code-verified on `main`; HEAD `5f15508c8`, guard absent — not deploy-lag)

The shared validator `func (q LogQuery) validate()` (`lego/backend/internal/logs/service.go:264-283`) checks only `direction` and log `type` (+ predeploy/build exclusivity). It has **no `Since < End` (start<end) ordering check**. `Since`/`End` are `LogQuery` fields (`:238-239`); the only `Since`/`End` comparisons in the package are per-entry result filters at `:415-420` (`t.Before(q.Since)` / `t.After(q.End)`), never a range-direction guard.

**All** log entrypoints run through `validate()`:

- `logs` → `QueryLogs` (`:460`) calls `q.validate()` at `:481`.
- `logLabelValues` → `LogLabelValues` (`:637`) calls `q.validate()` at `:648`.
- `databaseLogs` → `queryPostgresLogs` (`:523`) → `validatePostgres()` (`:557`) → `q.validate()` at `:558`.
- `keyValueLogs` → `queryKeyValueLogs` (`:570`) → `validateKeyValue()` (`:604`) → `q.validate()` at `:605`.
- `postgresLogLabelValues` (`:675`) / `keyValueLogLabelValues` (`:706`) → validatePostgres/validateKeyValue → validate().

An inverted range therefore passes validation on **every** path and reaches the Loki source (`loki.go`), whose query errors on `end < start`; that error is not `core.ErrBadRequest`, so `sanitizeGraphQLErrors` (`api/server.go:1328-1337`) redacts it to `"internal error"` (same mapping as `w4/053`/`w4/054`).

**Control (load-bearing):** `serviceEvents` accepts the same inverted range and returns an empty list — it is not a logs-package caller, so it does not share the missing guard. That negative control confirms the defect is specific to the logs-package validators, not a global inverted-range handling issue.

## Target behavior / fix (SUPERSEDES 054's fix location)

Put **one** `Since < End` guard, wrapped in `core.ErrBadRequest` (e.g. `startTime must be before endTime`), inside the shared `func (q LogQuery) validate()` at `service.go:264` — **not** in the `QueryLogs` body. That single placement covers `logs`, `logLabelValues`, `databaseLogs`, `keyValueLogs`, and both datastore label-value variants in one spot (`validatePostgres:558` and `validateKeyValue:605` both call `validate()` first). A real Loki/upstream failure must still surface as `"internal error"` (redacted). Batch with `w4/053` (metrics: same missing `start<end` guard on a different parser) — 053 is a metrics-package guard, this is the logs-package guard; two call sites of the same class.

## Blast radius / aliases (enumerated)

The guard fixes every reachable name of the logs-package validators across REST + GraphQL + MCP:

- **GraphQL:** `logs` (`graphql.go`), `logLabelValues` (`graphql.go:102-114`), `databaseLogs`, `keyValueLogs`.
- **REST:** `GET /v1/logs`, `GET /v1/logs/subscribe`, and `GET /v1/logs/values` (the `LogLabelValues` adapter at `rest.go:86`) — the last is the REST alias of `logLabelValues`, also currently unguarded.
- **MCP:** the log + label-value tools that reuse the same `Service` methods.

## Adjacent classes (unchanged from 054)

- unknown type / malformed time → **bad-request** (already correct via validate/parse).
- inverted range → **bad-request** (the fix; currently "internal error").
- real Loki/upstream failure → **"internal error"** (must stay redacted).
- out-of-range limit → clamped by `normalized()` (acceptable; unchanged).

## Render parity

Render returns a validation error for an inverted log time range on the values/label-discovery surface too, not a 5xx/opaque error. Parity applies across GraphQL + REST `/v1/logs/values` + MCP.

## Severity

**Minor** — no data loss, no blocked journey (the dashboard sends valid ranges); error-taxonomy/DX defect + client-caused server error-log noise. Its importance is that it **corrects `w4/054`'s fix** so the fix is complete rather than partial.
