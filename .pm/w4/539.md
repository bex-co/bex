# 539 — Regression of w6/m135: deleting a pending auto-added www sibling warns that its apex is removed too, but only the sibling is removed

Why: the confirmation names a domain the delete does not remove. A user either cancels a safe delete, or walks away thinking the apex claim is gone while it stays claimed and pending.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 6, 2026-11-10 08:53–09:02 UTC (`muse.env`, workspace `bex-canary`, pin `4630a48a765e`). **Minor**: the copy contradicts the result, but nothing was being served. ~20m.
- **Fixture:**
  - Free web service `qa-20261110-dom` (`srv-dbpdn8aj0hgs73eavo50`, `examples/hello-go`; deleted, GET 404).
  - Throwaway, unregistered apex `qa20261110-bexqa-nx.com` (whois: "No match"). Every claim on it was removed in the same visit (final `GET /v1/services/srv-dbpdn8aj0hgs73eavo50/custom-domains` → `[]`).
- **Controls that passed:**
  - Add answered the pair:
    - the apex is `ALIAS @ → qa-20261110-dom.onbex.co`, with an A fallback of `49.12.20.236`;
    - `www.qa20261110-bexqa-nx.com` is a `CNAME www` with `redirectForName: qa20261110-bexqa-nx.com`;
    - both read `unverified`, certificate `pending` and server `pending`.
  - `POST …/custom-domains/qa20261110-bexqa-nx.com/verify` answered `202` with an empty body, and the claim stayed `unverified`.
  - The unverified hosts did not route: `curl --resolve qa20261110-bexqa-nx.com:443:49.12.20.236 https://qa20261110-bexqa-nx.com/qa-probe` → `404 page not found`, and the same for HTTP on `:80` and for `www`.
  - Deleting the canonical apex while its generated `www` was pending showed "This removes the pending claims for qa20261110-bexqa-nx.com and www.qa20261110-bexqa-nx.com…" and removed both (the list read `[]`).
  - Deleting a lone pending apex showed the single-claim copy.
- **Probe:**
  - On `/services/srv-dbpdn8aj0hgs73eavo50/settings` → Custom Domains → "Actions for www.qa20261110-bexqa-nx.com" → Delete, the dialog read: "Delete www.qa20261110-bexqa-nx.com? This removes the pending claims for www.qa20261110-bexqa-nx.com and qa20261110-bexqa-nx.com. Neither was verified, so nothing was served on them and no certificate was issued."
  - After Delete (toast "Removed www.qa20261110-bexqa-nx.com"), `GET /v1/services/srv-dbpdn8aj0hgs73eavo50/custom-domains` returned only `cdm-dbpdneq0mi5c73c5pi30 qa20261110-bexqa-nx.com` (`redirectForName ""`, `unverified`).
  - The apex survived, exactly as ADR005 § www ↔ apex pairing specifies: "deleting only the generated sibling preserves the canonical claim unchanged".
- **Root cause:**
  - In `dashboard/src/features/services/components/custom-domains-section.tsx:204-226`, an unverified domain (`!domain.dnsVerified`) with a sibling always gets `services.domainDeletePendingPairConfirmBody` (`features/services/locales/en.ts:1660-1663`, "removes the pending claims for {name} and {sibling}"). That branch never checks `domain.redirectForName`.
  - The verified branch does check it, and uses `domainDeleteGeneratedConfirmBody` (`en.ts:1648-1652`, "This removes only {name}…").
  - The pending branch came from w4/142 (`6e1aaf87b`, 2026-09-27). It runs before w6/m135's generated-versus-canonical split (`2bd2ece5e`, 2026-08-28), so it regressed m135 for pending claims.
- **Fix (target behavior):** the pending branch mirrors the verified one.
  - A pending generated sibling (`redirectForName` set) gets a new `services.domainDeletePendingGeneratedConfirmBody`, in en and zh: "This removes only the pending claim for {name}. {canonical} stays as the canonical domain. It was never verified, so nothing was served on it and no certificate was issued."
  - A pending canonical with a generated sibling keeps the pair copy, which is correct today.
  - A lone pending domain keeps the single-claim copy.
- **w6/m135 DoD walk:**
  1. _Decided delete results:_ held live for pending, apex-first (deleting the sibling keeps the canonical; deleting the canonical removes both). www-first and verified claims were not probed this run.
  2. _No silent change from redirecting to serving:_ held. The surviving apex read `redirectForName ""` before and after.
  3. _REST, GraphQL, MCP and the dashboard agree on the post-delete claims:_ REST and the dashboard table agreed. GraphQL and MCP were not probed.
  4. _"The dashboard confirmation names every domain that will be removed or explains the surviving sibling's exact behavior":_ **fails** for a pending generated sibling (this note).
  5. _Authorization, uniqueness, TLS and idempotency:_ not probed.
  6. _Live www-first and apex-first matrix for pending and verified pairs:_ only apex-first pending was run.
- **Blast radius:** one component. `deleteDescription` has four branches (`custom-domains-section.tsx:204-226`). Keep the verified generated and pair copies and the lone-pending copy unchanged, and add a regression test for each branch.
- **Unverified:**
  - A www-first add, where the generated sibling is the apex. It takes the same branch but was not probed.
  - Verified pairs, since an unowned domain cannot be verified.
