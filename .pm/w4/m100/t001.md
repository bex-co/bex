## Objective

A signed-in dashboard session that issues one page's worth of concurrent GraphQL queries is shed with `429 RATE_LIMITED`. The budget doing the shedding is not `BEX_RATE_LIMIT` — it is the auth-admission **per-credential in-flight** bound, hard-derived as `BEX_AUTH_MAX_INFLIGHT / 8 = 8`. Separate the two concerns: keep `w1/m67` t002's anti-amplification guarantee against *invalid* credentials exactly as it is, and stop a *valid* caller's ordinary parallelism from colliding with it.

## Context

### The observation (production, 2026-09-13, workspace `tea-d98210cbbpdc73dcrkvg`)

All probes run from inside a signed-in `https://dashboard.bex.co` page via `page.evaluate` + `fetch(..., {credentials:'include'})`, so Cloudflare bot protection is not in the path.

**Rate is not the cause.** After a 90s idle, 90 sequential requests:

```js
// → {"first429": -1, "n429": 0, "total": 90}
const out = [];
for (let i = 0; i < 90; i++) {
  const r = await fetch("https://api.bex.co/v1/services?limit=1", {
    credentials: "include",
  });
  out.push(r.status);
}
```

90 requests in ~10s is well over 500/min and produced **zero** 429s.

**Concurrency is the cause.** Immediately afterwards, 25 *parallel* identical `Metrics` queries:

```js
// → {"n429": 1, "n200": 24}
const q = {
  operationName: "Metrics",
  query:
    "query Metrics($query: MetricsQueryInput!) { metrics(query: $query) { unit values { time value } } }",
  variables: {
    query: {
      filters: [{ field: "RESOURCE", values: ["srv-daj6sj0gsm7s73f63nmg"] }],
      name: "INSTANCES",
      start: "2026-09-12T21:00:00.000Z",
      end: "2026-09-13T09:00:00.000Z",
      resolution: 300,
    },
  },
};
await Promise.all(
  Array.from({ length: 25 }, () =>
    fetch("https://api.bex.co/graphql", {
      method: "POST",
      credentials: "include",
      headers: { "content-type": "application/json" },
      body: JSON.stringify(q),
    }).then((r) => r.status),
  ),
);
```

**The real page reproduces it.** One load of `https://dashboard.bex.co/services/srv-daj6sj0gsm7s73f63nmg/metrics`, from a bucket verified healthy seconds earlier by the 90-request probe above, issued 25 GraphQL POSTs of which 2 returned 429. An earlier load issued 34 of which 8 returned 429. The shed response, verbatim:

```text
POST https://api.bex.co/graphql → 429
retry-after: 1
{"data":null,"errors":[{"extensions":{"code":"RATE_LIMITED"},"message":"rate limit exceeded"}]}
```

The two shed operations captured were `Metrics` with `name: "INSTANCES"` and `MetricsFilters` with `outputFilters: ["STATUS_CODE"]`.

### The code path

- `lego/backend/internal/api/authadmission.go:108-113` — `NewAuthAdmission` sets `a.credentialMaxInflight = maxInflight / 8`, where `maxInflight` is `BEX_AUTH_MAX_INFLIGHT` (default `64` — `cmd/api/config.go:554`). So the per-credential concurrent-auth ceiling is **8**, with no knob of its own.
- `:175-184` — `acquireCredential` returns `false` once a credential has `credentialMaxInflight` upstream auth calls outstanding; `admit` turns that into `errAuthOverloaded` (`:143-146`).
- `:212-215` — `writeAuthOverloaded` sets `Retry-After: 1` and delegates to `writeTooManyRequests`, which for `/graphql` emits exactly the observed `RATE_LIMITED` envelope (`api/ratelimit.go:143-155`). This is why the shed is indistinguishable from a rate-limit shed on the wire.
- `lego/backend/internal/api/auth.go:572-579` — `whoami` calls `admission.admit` on **every** session request, with the comment _"Kratos sessions are not positively cached here, so every session request is an upstream call and is metered as one (w1/m67 F1)"_. This is what makes in-flight slots scarce for exactly one class of caller: the browser.
- The general limiter is **not** implicated: `NewRateLimiter(500, 0)` → `burst = ceil(rpm) = 500` (`api/ratelimit.go:68-77`, `core/ratelimit.go:77-90`), and `BEX_RATE_LIMIT` is unset in `lego/operator/config/api/deployment.yaml` so the default stands.
- **Origin:** `w1/m67` t002 (`.pm/w1/done/m67/done/t002.md`) step 3 asked for "a semaphore around upstream introspection/whoami" and its acceptance criteria include _"A valid caller's requests are unaffected (limiter still identity-keyed inside)"_. That criterion is not met for a concurrent valid caller; `maxInflight / 8` is where the guarantee slipped.

## Steps

1. Probe the control case first, before changing anything: mint an API key, run the same 25-parallel probe with `Authorization: Bearer …`, and record the result. The claim under test is that a bearer caller is unaffected because `introspect` positively caches while `whoami` does not. If the bearer caller sheds too, the fix is broader than the session path and this task's shape changes — say so rather than proceeding.
2. Decide and write down the target behavior. `credentialMaxInflight` exists to stop one credential monopolizing upstream auth capacity; it must not be `BEX_AUTH_MAX_INFLIGHT/8`. Options to weigh explicitly, picking one:
   - its own env knob (e.g. `BEX_AUTH_MAX_INFLIGHT_PER_CREDENTIAL`) with a default that admits an ordinary page load with headroom, `0` ⇒ unbounded, mirrored into `.env.example` + the `lego/backend/CLAUDE.md` env table + `docs/ADR006-bex-api.md`;
   - **queue, bounded, instead of shed** for a credential that has already authenticated successfully (a valid session waiting 20ms is strictly better than a dropped chart), keeping immediate shed for the unauthenticated/invalid path where queuing is the amplification the bound exists to prevent;
   - positively cache Kratos sessions for a short TTL so concurrency stops being the scarce resource at all — note this reopens the revocation-semantics question `w1/m67` deliberately avoided, so it needs the `revocationEpoch` treatment `introspect` already has, or it is out of scope.
   Whichever is chosen, the bound must stay **keyed on the credential**, never relaxed process-wide.
3. Implement it. Keep the global `a.inflight` ceiling and the per-source failure budget untouched.
4. Distinguish the two shed classes on the wire. Today a valid caller shedding on concurrency and a rate-limited caller are byte-identical, which is why this took three weeks and two QA runs to attribute. Give the admission shed its own `extensions.code` (or a distinguishing field) while keeping the HTTP status at 429 and the body Render-shaped — and hand t003 whatever the dashboard should key on.
5. Re-run the probes from Context against a build with the fix and paste the new numbers into this task.
