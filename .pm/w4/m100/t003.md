## Objective

When a metrics query comes back `429 RATE_LIMITED`, the Metrics page shows no sign of it. The user reads a chart that is missing data as a chart that has no data. Make a throttled read say so.

## Context

On the production loads measured 2026-09-13, 2–8 of 25–34 GraphQL POSTs returned:

```text
{"data":null,"errors":[{"extensions":{"code":"RATE_LIMITED"},"message":"rate limit exceeded"}]}
```

and the page rendered every panel with values and no error anywhere in `main`'s text. Two reasons, both worth fixing on this side:

- **Duplicates masked it.** A shed `Metrics(INSTANCES)` had a twin that succeeded, so `Total Instances` showed `2`; a shed `MetricsFilters(STATUS_CODE)` had a twin that succeeded, so the Status Code dropdown still listed its options. t002 removes the duplicates — which means these failures stop being hidden and start being *visible as emptiness* unless this task lands with it.
- **The suppression rule is load-bearing.** `dashboard/src/features/metrics/components/metric-section.tsx:44-58` computes `errorEmpty = !!result.error && result.series.length === 0` and only then renders `<MetricError/>`; a refetch error over existing data deliberately keeps the chart. Combined with `use-metrics.ts:176-177` (`fetchPolicy: "cache-and-network"`, `errorPolicy: "all"`), a cache hit from any earlier load leaves `series` non-empty, so the error never surfaces at all.
- **The dashboard has no handling for this code.** `RATE_LIMITED` appears exactly once in `dashboard/src/`, in a test fixture (`common/lib/__tests__/graphql-error.test.ts:31`). The `hasGraphQLErrorCode` / `extensions.code` precedent that `w6/m49` set for `PLAN_LIMIT` is the pattern to follow.

## Steps

1. Recognize the throttled class explicitly via `extensions.code`, not message text — reusing `dashboard/src/common/lib/graphql-error.ts`'s helpers. Key on whatever code t001 settles on for an admission shed as well as `RATE_LIMITED`.
2. Decide what the user sees, and write it down. A throttled read is **transient** — it must not render as `METRICS_UNAVAILABLE` ("metrics aren't wired") or as a generic failure, both of which misattribute it. The honest shape is a retry: back off per `Retry-After` and refetch, showing a brief "catching up" state, and only escalate to a visible error if the retry also fails.
3. Make a stale-cache render honest. If the retry has not yet succeeded and the chart is painting cached series, say the data may be stale rather than presenting it as current — the `w9/m86` distinction `metric-section.tsx` already draws between "no data" and "error with data" is the seam.
4. Test the pre-settle state: what renders between the shed and the successful retry, on both a cold load (no cache) and a warm one (cached series).
