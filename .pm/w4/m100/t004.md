## Objective

A deploy opened by a configuration save records **no commit**, on every surface, for every service type. The deploy history therefore cannot answer "what code is currently live?" — which is the question a rollback decision turns on. Carry the commit of the release the config change is re-rolling.

## Context

### The observation (production, 2026-09-13)

Repo-backed docker service `qa-20260913-web` (`srv-daj6sj0gsm7s73f63nmg`, `github.com/bex-co/bex`, root `examples/hello-go`). Created with `MESSAGE=qa-initial`; then one environment-variable edit saved with **Save and deploy**. The second deploy reached `live` and the running process did serve the new value (`curl https://qa-20260913-web.onbex.co/` → `qa-updated`), so the code that ran is the same commit as before. Yet:


No `commit` key on the live row. `/services/<id>/deploys` renders it the same way: the `Config Change` row shows only status, id, timestamp and duration, while the superseded `First Deploy` row shows `5ef5e18 update`. The **live** deploy is the one with no commit.

### The cause

`lego/backend/internal/rollout/rollout.go:161`:

```go
if _, err := t.Store.CreateDeploy(ctx, snapshot.appID, trigger, a.Spec.Image, generation, store.CommitInfo{}); err != nil {
```

An unconditional empty `store.CommitInfo{}`. Every other writer resolves one: `deploys/service.go:569` passes the resolved `commit` for explicit deploys, `apps/service.go:2908` for `new_commit`, `apps/deploy.go:2861` for `blueprint`, and `store.CreateRollbackDeploy` takes one too.

### What the fix must not use

`a.Spec.BuildCommit` is **not** a record of the running release. `lego/types/v1alpha1/app_types.go:421-433`: _"Set by the CreateDeploy API's commitId body field; the subsequent deploy always resets it to empty so the next trigger reverts to Branch HEAD."_ It is empty in the steady state. Reject it.

### The consumer already accepts a hash with no message

`dashboard/src/features/deploys/components/deploys-list-page.tsx:206-218` gates on `d.commitId` and renders `commitMessage` only if present. So a carried-forward commit that supplies the SHA alone renders correctly — no dashboard change is required for the row to start showing it.

### Render

`docs/render-artifacts/deploy-detail-page.md:10` — Render's deploy object carries `commit { id, message, createdAt }` for Git-backed deploys; `:17` — history rows show "the available status, commit/message, trigger, deployed time, duration … without placeholders".

## Steps

1. Pick the source of the carried commit and justify it in this task. The two shapes:
   - **Read in `rollout.Tracker.record`** — widen the `DeployStore` interface (`rollout.go:46-50`, today `CreateDeploy` only) with a lookup for the app's current live/most-recent deploy and pass its `CommitInfo`. Explicit, but adds a read to a path that currently does one write and swallows its error.
   - **Inherit inside `PGStore.CreateDeploy`** (`store/store.go:1775`) — when the caller passes a zero `CommitInfo`, carry the previous deploy's commit forward for the same app. One place, uniform for every caller, no interface change; but it makes an empty argument mean "inherit" rather than "none", which must be documented on `CommitInfo` (`store/store.go:209-218`) or it will surprise the next caller. If chosen, confirm no existing caller relies on an empty argument meaning "definitely no commit".
2. Implement it so an **image-backed** service still gets an empty commit — there is no prior commit to inherit, and synthesizing one would be worse than omitting it. `CommitInfo`'s own contract already says zero value = unknown, "never load-bearing".
3. Decide what happens to `message`. Carrying the hash alone is acceptable (the consumer handles it); carrying the previous row's message too is more useful and costs nothing if the source is the previous row. State the choice.
4. Verify on a real repo-backed service: save an env change, then re-run the `GET …/deploys?limit=3` above and confirm the new `config_change` row's `commit.id` equals the superseded row's, and that the deploys list renders the short SHA.
5. Check the two sibling surfaces read the same row (they do — one `deploys` row behind REST, GraphQL and MCP), and confirm the deploy **detail** page (`/services/<id>/deploys/<dep-id>`) now shows the commit too.

## Acceptance criteria

- [ ] A `config_change` deploy on a repo-backed service carries a `commit` whose `id` equals the commit of the release it re-rolls — verified live and asserted by a test that fails before the change.
- [ ] A `config_change` deploy on an **image-backed** service still carries no `commit` — asserted by a test.
- [ ] REST, GraphQL and MCP all show it (one row, three readers — assert at least REST and GraphQL).
- [ ] The deploys list and the deploy detail page both render the commit on a config-change row.
- [ ] Whichever layer was chosen, the meaning of an empty `CommitInfo` argument is documented where the next caller will read it.

## Out of scope

- Resolving a *fresh* commit from git at config-change time (a config change does not rebuild from a new commit; carrying the running one forward is the correct semantics).
- The four callers' own regression coverage — that is t005.
