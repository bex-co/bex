## Objective

Let a client chain two revision-aware saves without a round trip in between, by returning the revision the write produced — which the env-group result already does and the service result does not.

## Context

- `EnvironmentPatchResult` exposes `envVarKeys`, `rolledOut`, `secretFileNames` and no revision (confirmed live by introspection).
- `EnvGroupEnvironmentPatchResult.revision` exists and is populated — verified live: four chained group saves each returned the next revision and needed no re-read.
- `patchEnvironmentCAS` already has the value in hand: `newVersion` from `PutCAS`, the same number `decodeEnvRevision` round-trips.
- The sparse (non-CAS) path has no revision semantics, so decide and state what the field holds there — most likely null rather than a fabricated value, since a sparse patch makes no CAS promise.

## Steps

1. Add `revision` to `EnvironmentPatchResult` and populate it from `newVersion` on the CAS path.
2. Decide the sparse-path value explicitly and record the reason at the site.
3. Expose it on GraphQL, REST and MCP together.
4. Confirm the encoding matches what `expectedEnvRevision` accepts, by feeding a returned revision straight back into the next patch.

## Files

- `lego/backend/internal/secrets/batch.go`
- `lego/backend/internal/secrets/graphql.go`, `rest.go`, `mcp.go`

## Acceptance criteria

- [ ] A returned revision is accepted verbatim as the next call's `expectedEnvRevision`.
- [ ] The sparse path's value is deliberate and documented.
- [ ] The field appears on all three API surfaces.

## Out of scope

- Adding revisions to the sparse protocol.
