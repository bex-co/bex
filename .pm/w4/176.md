Why: Users deciding whether to link or unlink shared configuration need to know that the running service can change even with auto-deploy off.

## Reproduction and target

Fresh group page https://dashboard.bex.co/env-groups/evg-db05706de41s73cao150 said:

> Linking or unlinking redeploys linked services that have auto-deploy on. A repo-backed service with auto-deploy off keeps serving its current release and picks the change up on its next deploy.

Fixture: Free native-Go web **qa-20261002-files-r21 / srv-db057c45o9vs73dt7ud0**, public https://github.com/bex-co/bex, main, root examples/hello-go, build `go build -o app .`, autoDeploy false. Start command:


2. Service Environment → Link at 01:03:59Z. Auto-deploy remained false, but service entered Building then Running rev-2 (01:06:01Z). History retained only the initial Live row. Service marker still won: precedence works.
3. Delete service-owned file through Environment → Edit → Save and deploy at 01:06:39Z. This deliberate deploy produced dep-db05a7ude41s73cao180, Live 01:08:25Z, rev-3, HTTP 200 group marker.

5. Reload group page; Link Service 01:11:08Z reproduced the reverse: by 01:13:01Z HTTP 200 group marker and rev-5, autoDeploy false, same two history rows. No manual deploy/restart or Git push occurred between those observations.
6. Control: edit group file to qa-r21-group-v2, Save and deploy 01:13:26Z. At 01:14:09Z explicit file read returned v2, while service remained Running rev-5 and external GET returned v1. This content-only write obeys the gate; do not globally claim every service restarts.

**Target copy:** “Linking or unlinking changes service configuration and can restart services even when auto-deploy is off.” Successful link/unlink should say the link changed without reusing a content-update rollout promise. Preserve accepted runtime behavior and REST/GraphQL/MCP mutation semantics. Do not suppress reconciliation or add history rows under this copy fix.
