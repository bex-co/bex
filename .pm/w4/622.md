# 622 — A service on a repo whose pushes can't reach bex is created and saved with Auto-Deploy "On Commit", although Render offers no auto-deploy for a public Git URL; a rollback then says it turns off an auto-deploy that could never run

Why: Render's rule is plain: "Auto-deploys require a connected Git provider. Services that use a prebuilt Docker image or a public Git repository URL must be deployed manually." bex stores and reports `autoDeploy: yes` for such a service, and its Settings show a disabled "On Commit" beside a hint that it can't run. A Render client, or a user reading REST, believes pushes deploy. The rollback dialog promises "Auto-deploy will be turned off", and Events record `auto_deploy_disabled` from `commit` for a trigger that never fired.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 248, 2026-11-13 01:11–01:31 UTC (`muse.env`, workspace `bex-canary`; pin `c328714af1dd`). **Minor** (the hint is honest, the stored setting is not). ~45m.
- **Fixture:** `qa-20261113-r248-rb` (`srv-dbr67g95t55c738j9oeg`), the [w4/621](621.md) fixture: repo `https://github.com/bex-co/bex`, which this workspace's GitHub App does not cover. Deleted afterwards.
- **Probe:**
  1. `POST /v1/services {…,"autoDeploy":"yes"}` → `201`, `autoDeploy: "yes"`, `autoDeployTrigger: "commit"`.
  2. Rollback from the Deploys tab.
     - The confirm read "… Auto-deploy will be turned off. …".
     - Events recorded `auto_deploy_disabled {"reason":"rollback","fromTrigger":"commit"}` at 01:18:53, shown as "Auto-deploy updated". The service then read `autoDeploy: "no"`.
  3. `PATCH /v1/services/srv-dbr67g95t55c738j9oeg {"autoDeploy":"yes"}` → `200`, `autoDeploy: "yes"`, `autoDeployTrigger: "commit"`.
     - GraphQL `service { autoDeploy pushDeliveryMethod }` → `{"autoDeploy":true,"pushDeliveryMethod":"unavailable"}`.
     - Settings: `combobox "Auto-Deploy" [disabled]: On Commit` under "Auto-deploy can't run for this repo: GitHub doesn't send bex its pushes. Connect the repo through the GitHub app, or trigger deploys with the Deploy Hook." (`dashboard/src/features/services/locales/en.ts:2890`).
  - Round 246's dashboard create from the Public Git URL tab offered an Auto-Deploy toggle as well (it was turned off there).
- **Root cause:**
  - Create defaults auto-deploy on for every repo-backed service, and an explicit value wins (`lego/backend/internal/apps/service.go:3580-3588`). Neither path asks whether pushes can reach bex.
  - `setAutoDeployFetched` (`:5270-5273`) refuses `enabled` only for a prebuilt image (`errPrebuiltImageField`, `apps/blueprint_compiler.go:401`, the w4/418 precedent).
  - The answer already exists: `pushDeliveryMethod` (`lego/backend/internal/apps/pushdelivery.go:130-175`) returns `PushDeliveryUnavailable` (`:56`) for a repo the GitHub App does not cover, on an install that rejects the shared manual key (w4/483).
- **Fix (target behavior):** when `pushDeliveryMethod` is `unavailable`:
  - a create without `autoDeploy` stores it off (`autoDeploy: "no"`, `autoDeployTrigger: "off"`);
  - a create or `PATCH` with `autoDeploy: "yes"` (REST, GraphQL `setAutoDeploy`, MCP `update_service`) is refused with `400`. The message names the reason and the way out, e.g. "auto-deploy needs a connected Git provider: bex doesn't receive this repo's pushes. Connect it through the GitHub app, or deploy with the Deploy Hook". This matches the prebuilt-image refusal;
  - the dashboard's Public Git URL create form offers no Auto-Deploy control for such a repo, just the hint.
  - `unknown` (GitHub lookup failed) and `manual_webhook` (an install that accepts the manual key) keep today's default, since pushes may arrive.
  - A repo that becomes covered (`github_app`) can be switched on normally.
  - Existing services keep their stored value, and the w4/483 hint keeps explaining it. With a default of off, a new service's rollback dialog takes the existing no-auto-deploy variant (`dashboard/src/features/deploys/components/deploy-actions.tsx:277`) and records no `auto_deploy_disabled`.
- **Blast radius:**
  - 2 write paths: the create default (`apps/service.go:3580-3588`, also reached by Blueprint applies) and `setAutoDeployFetched` (`apps/service.go:5246`, `:5264`, `apps/settings.go:388`: REST `PATCH`, GraphQL, MCP).
  - The rollback's `disablesAutoDeploy` (`lego/backend/internal/deploys/service.go:1290`) is unchanged; it simply finds auto-deploy off.
  - Build-source-linked services (`req.BuildSourceID`) are not repo pushes and stay as they are.
- **Tests:**
  - create on an `unavailable` repo → `autoDeploy: "no"`; explicit `yes` → 400 on REST, GraphQL and MCP;
  - controls: `github_app` → `yes` default; `unknown` → `yes` default; prebuilt image unchanged.
- **Unverified:**
  - Render's API answer to `autoDeploy: "yes"` for a public-URL service (refuse or store off) was not captured. bex refuses here for the same honesty reason as w4/418, and a Render capture may change the shape, not the stored value.
  - A Blueprint `autoDeploy: true` on an uncovered repo was not probed.
- **Render:** [Deploys](https://render.com/docs/deploys), read 2026-11-13: "Auto-deploys require a connected Git provider. Services that use a prebuilt Docker image or a public Git repository URL must be deployed manually."
- **Dedupe:**
  - w4/483 (done) fixed the delivery claim and named this a separate decision ("Whether to also stop defaulting `autoDeploy` on for uncovered repos is a separate decision"), but it was never filed.
  - w6/m99 (done) made the hint and `pushDeliveryMethod` agree. w4/418 (done) refused `autoDeploy` for prebuilt images.
  - Not deploy lag (see w4/621's `git log`; `apps/service.go` and `apps/pushdelivery.go` unchanged since `c328714af1dd`).
- **DoD (live):** create a Free web service from the Public Git URL tab (or `POST /v1/services` without `autoDeploy`) on a repo the workspace's GitHub App doesn't cover:
  - it reads `autoDeploy: "no"`, and Settings show Auto-Deploy Off with the hint;
  - `PATCH {"autoDeploy":"yes"}` → 400 naming the reason;
  - its rollback dialog says nothing about turning auto-deploy off, and Events record no `auto_deploy_disabled`.

  - Creation stores `AutoSync: true`: `CreateBlueprint`, `lego/backend/internal/apps/blueprint.go:1395`, and the deploy-time upsert at `:2192`.
- **Render.** [Blueprints](https://render.com/docs/infrastructure-as-code), read 2026-11-13: "Each push to the linked branch that modifies your Blueprint file triggers a deploy of any added or modified resources". Setup connects a Git provider repository. No auto-sync is documented for a public Git URL, matching "Auto-deploys require a connected Git provider" for services.
- **Target, added to this note's fix.** When the repo's `pushDeliveryMethod` is `unavailable`:
  - the Blueprint preview says future file changes need a Manual Sync, or a connected repo, instead of promising automatic sync;
  - a new Blueprint is created with `autoSync: false`;
  - an explicit `autoSync: true` on REST, GraphQL or MCP gets the same 400 as the service's `autoDeploy`;
