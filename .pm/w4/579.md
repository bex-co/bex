# 579 — A service's `updatedAt` can read earlier than its `createdAt`: `hello-go` says it was updated 0.25 s before it was created, and `updatedBefore=<its createdAt>` lists it

Why: `updatedAt` is supposed to be the last API write on a resource that already exists. A resource "updated" before it existed breaks the one ordering every client may assume. An incremental sync on `updatedAfter`/`updatedBefore` puts the resource on the wrong side of its own creation.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 129, 2026-11-11 18:52–19:00 UTC (`muse.env`, workspace `bex-canary`; release pin `f609163ada8e`). **Minor**: a wrong timestamp ordering on REST and GraphQL, invisible in the dashboard. ~20m.
- **Probe** (signed-in page, read only, on the workspace's long-lived `hello-go`; nothing of another run's was touched):
  - `GET /v1/services/srv-dbkq3hdhhjfs73eiahe0` → `"createdAt":"2026-11-03T08:56:38Z"`, `"updatedAt":"2026-11-03T08:56:37.745392795Z"`, `"revision":"rev-3"`.
  - GraphQL `{ service(id:"srv-dbkq3hdhhjfs73eiahe0"){ createdAt updatedAt } }` → the same two values.
  - `GET /v1/services?ownerId=tea-daif693dqjvc73e7as3g&updatedBefore=2026-11-03T08:56:38Z` → `["hello-go"]`. The service's own `createdAt` is the bound, so it was "updated before" it was created.
- **Not reproduced fresh: 0 of 12 creates.** The persisted value reads back every time; a new resource rarely lands in that state.
  - Twelve `qa-20261111-r129-*` Free web services were created with `POST /v1/services`: three image services one after another, six in parallel, and three Git services (`bex-co/bex`, `examples/hello-go`) in parallel.
  - Every one answered `updatedAt` in the same whole second as `createdAt` and later than it. For example, `createdAt 18:57:38Z` with `updatedAt 18:57:38.984778541Z`, so the stamp-to-write gap was under 16 ms.
  - All twelve were deleted afterwards (DELETE 204, then GET 404).
- **Root cause:**
  - **Two clocks, two precisions.** Each create stamps `app.bex.co/updated-at` with bex-api's clock, to the nanosecond, **before** the Kubernetes write (`resourcemeta.Touch`, `lego/backend/internal/resourcemeta/metadata.go:197-206`):
    - services: `apps/service.go:2886` in `materializeNewAppLocked`;
    - Postgres: `postgres/service.go:936` in `CreatePostgres`;
    - Key Value: `keyvalue/service.go:647` in `CreateKeyValue`.
  - **`createdAt` is the API server's `creationTimestamp`,** which Kubernetes keeps to the whole second. The views format it as RFC 3339 seconds: `apps/service.go:1066-1069`, `postgres/service.go:556-559`, `keyvalue/service.go:293-296`.
  - **When the two cross.** Whenever a second boundary falls between the stamp and the write, `updatedAt` reads earlier than `createdAt`. That happens when the write is slow, or when bex-api's node clock runs behind the API server's.
  - **Nothing corrects it on read.** `resourcemeta.UpdatedAt` (`metadata.go:219-238`) returns the annotation unchanged.
  - **Not traced:** which of the two made `hello-go`'s gap at least 255 ms on 2026-11-03.
- **Fix (target behavior):**
  - `updatedAt` is never earlier than `createdAt`. A resource with no write since its create reads `updatedAt` equal to its `createdAt`.
  - In `resourcemeta.UpdatedAt`, when the stamped time is before the object's `creationTimestamp`, return the `creationTimestamp` instead, in the same format.
  - That one change covers every surface: REST, GraphQL, MCP (it shares REST's view) and the `updatedBefore`/`updatedAfter` filters, which read the same view.
  - **Leave the ordering of real writes alone.** A write after the create still reads its own stamped time, which is later than `createdAt`. The w4/373 rule that status writes never move `updatedAt` is unchanged.
- **Blast radius:**
  - `resourcemeta.UpdatedAt` has exactly 3 callers: `apps/service.go:1173`, `postgres/service.go:618` and `keyvalue/service.go:324`. All three get the clamp.
  - Env groups and projects take both timestamps from their own store rows and are out of scope.
  - **Test:** extend `resourcemeta/metadata_test.go` with an annotation 0.3 s before a whole-second `creationTimestamp` (expect the `creationTimestamp`) and an annotation after it (expect the annotation). Keep the existing w4/373 cases.
- **Unverified:**
  - Render's own value for a never-updated resource. The assumption is that `updatedAt` equals `createdAt` at birth.
  - Whether any Postgres or Key Value in production reads the same inversion. Only one service was observed, plus one Postgres and one Key Value that read correctly.
- **Render:** see Unverified. Render's schema defines both fields as `date-time` with no ordering note.
- **Dedupe:**
  - w4/373 (done) stopped status writes from moving `updatedAt`. w4/m109 (done) made project renames move it.
  - `grep -rli "updatedAt.*before.*createdAt\|updated before.*created" .pm` finds nothing.
  - Not deploy lag: `metadata.go:219-238` is unchanged on `origin/main`.
- **DoD (live):**
  - `GET /v1/services/srv-dbkq3hdhhjfs73eiahe0` reads `updatedAt` ≥ `createdAt`. With no write since, it reads `2026-11-03T08:56:38Z`, and GraphQL agrees.
  - `GET /v1/services?ownerId=tea-daif693dqjvc73e7as3g&updatedBefore=2026-11-03T08:56:38Z` no longer lists `hello-go`.
  - A fresh Free image service created through `POST /v1/services` still answers `updatedAt` ≥ `createdAt`. A Settings save then moves `updatedAt` to that save's time.
