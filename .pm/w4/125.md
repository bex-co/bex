# GraphQL reports `maintenanceMode` on cron jobs and private services, and its `NonNull` wrapper means the `w6/m130` remedy cannot be applied as-is

Why: REST emits `maintenanceMode` only for `web_service` — the type gate is explicit and cites Render's schema — while GraphQL returns `{enabled:false, uri:""}` for every service type, and because the field is declared `NewNonNull` the established fix (resolve it to `null` off the applicable types) is a schema-breaking change rather than the one-line value-emptying that closed the last three.

Found by live `/qa-find-bugs` 2026-09-21 pass 138 (w4-targeted, `muse.env` credentials), running the `AppView` type-gate sweep that [`w4/124`](124.md) called for. Fixtures `qa-20260921-cron`, `qa-20260921-pv2`, `qa-20260921-wk`, all deleted.

## Repro

```graphql
{ service(id:"<cron_job>")       { type maintenanceMode { enabled uri } renderSubdomainPolicy } }
→ { "type":"cron_job",        "maintenanceMode":{"enabled":false,"uri":""}, "renderSubdomainPolicy":null }

{ service(id:"<private_service>") { type maintenanceMode { enabled uri } renderSubdomainPolicy } }
→ { "type":"private_service", "maintenanceMode":{"enabled":false,"uri":""}, "renderSubdomainPolicy":null }
```

```
GET /v1/services/<cron_job>     → serviceDetails: {command, env, nextRunAt, numInstances, plan, region, runtime, schedule}
GET /v1/services/<private>      → serviceDetails: {env, internalAddress, maxShutdownDelaySeconds, numInstances, plan, region, runtime}
GET /v1/services/<web_service>  → serviceDetails: {…, maintenanceMode:{enabled:false,uri:""}, renderSubdomainPolicy:"enabled", …}
```

**The data proves the gate is by type, not by value.** The web service's `maintenanceMode` is also `{enabled:false, uri:""}` and REST includes it anyway; the cron and private services carry the identical value and REST omits the key entirely. So "omitted because empty" is ruled out by construction.

And the same GraphQL payload answers `renderSubdomainPolicy: null` for both — the sibling field that `w6/m130` fixed. Two fields, one response, one of them gated and one not.

## Why this one is harder than `url`

`lego/backend/internal/apps/render.go:434-442` — the REST gate, with the contract written at the site:

```go
if svcType == renderWebService {
	// Render's maintenanceMode is required on webServiceDetails (never
	// omitted), unlike the mostly-optional fields above — docs/render-
	// artifacts/maintenance-mode.md.
	details["maintenanceMode"] = map[string]any{...}
}
```

`lego/backend/internal/apps/graphql.go` — the three fields side by side, and the reason the remedies differ:

| field                     | declaration                                              | can it express absence?                     |
| --------------------------- | ---------------------------------------------------------- | --------------------------------------------- |
| `renderSubdomainPolicy`    | `gqlutil.OptionalStrField(...)` (`:457`)                   | yes — `w6/m130` resolves it to `null`         |
| `url`                      | `gqlutil.StrField(...)` (`:318`)                           | `""`, which reads as "no URL" — `w4/124`      |
| `maintenanceMode`          | `Type: graphql.NewNonNull(maintenanceModeGQLType)` (`:519`) | **no** — the schema forbids `null`            |

So the m130 pattern ("empty the VALUE in `view()` so GraphQL's flat field agrees with REST's omission") does not reach this field. Emptying `AppView.MaintenanceMode` still yields `{enabled:false, uri:""}`, which is exactly what it returns today.

## The decision this needs

Two defensible answers, and the note is not picking one:

- **Make the field nullable** (`maintenanceMode: MaintenanceMode`) and resolve `null` for every non-`web_service` type, matching REST's omission and `renderSubdomainPolicy`'s precedent. This is a schema change: any client that relies on the non-null guarantee — including generated TypeScript in `dashboard/src/graphql/schema-types.ts` — sees the type loosen. Worth checking whether the dashboard reads it on a non-web page at all before assuming that is painful.
- **Leave the shape and fix the meaning**: keep it non-null, but say at the site and in ADR018 that off `web_service` the object is a schema artefact rather than a claim, and make sure nothing downstream branches on `maintenanceMode.enabled` for a type that cannot have it.

The first is the one that makes the surfaces agree, which is what ADR006 asks for; the second is the one that breaks no client. Whoever takes it should decide explicitly and record it, because the "just gate it" instinct will produce a breaking change without anyone noticing it was one.

Estimate: ~40m either way, plus the client check. **Do this together with [`w4/124`](124.md)** — same sweep, same `view()`, same test file (`subdomain_policy_test.go`'s shape). If both are taken on along with the remaining audit, promote the pair to a milestone; separately each is sub-hour.

## Also checked this pass, and found correct

The sweep covered 23 scalar/object fields across `cron_job`, `private_service` and `web_service`, comparing GraphQL against REST by-id in the same session. **Exactly two divergences exist and both are now filed** — `url` (`w4/124`) and `maintenanceMode` (this note). Everything else lines up:

- **`renderSubdomainPolicy` → `null`** on GraphQL and absent on REST for cron and private; `"enabled"` on both for the web service. `w6/m130` verified live.
- **`maxShutdownDelaySeconds` → `null`** on GraphQL and absent on REST for the cron job; `30` on both for private and web. The value-based gate (`> 0`) and the GraphQL resolver's explicit `if == 0 return nil` agree.
- **`autoscaling` and `disk` resolve `null`**, not empty objects, for every type that has neither.
- **`url`, `internalAddress`, `healthCheckPath`, `publishPath`, `sshAddress` are `""` on GraphQL wherever REST omits them** — so they read as absent even though the wire shape differs. `private_service.url` is the sole exception, which is `w4/124`.
- **`routes` and `headers` are `[]`** for non-static types rather than null or fabricated entries.
- **A cron job's `nextRunAt` is computed and correct** — `0 5 * * *` created at 14:16Z reported `2026-09-22T05:00:00Z` on both surfaces, the right next occurrence.
- **A background worker cannot be created on the free plan** and create resolves it to `starter` rather than failing — `errWorkerFreePlan` is reachable only when a caller names `free` explicitly. Its REST `serviceDetails` carries `sshAddress` and correctly carries neither `url` nor `internalAddress`.
