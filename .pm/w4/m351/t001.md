## Objective

When `permanentRolloutCrash` settles a release that never served, record the release-scoped `ConditionRollout` False verdict. Then `failedFirstRelease` holds and `planRelease` runs the workload at zero in the same pass, as the deadline path does under `stopsFirstRelease`.

## Context

- Mechanism and probes: [README § Finding](README.md#finding-round-214).
- The settle: `settleFailedRolloutMessage` (`lego/operator/internal/controller/app_controller.go:4001`).
- The deadline's stop condition: `stopsFirstRelease` (`:3966-3975`), and its verdict write (`:3954-3960`).
- The reader: `failedFirstRelease` (`release_plan.go:380-386`).
- The two callers of the crash settle are `reportRolloutProgress` (`app_controller.go:3787-3788`) and `reportWebHTTPSelection` (`web_image_http.go:238-239`).

## Steps

1. In the never-served branch of the crash settle, write `ConditionRollout{Status: False, Reason: CrashLoopBackOff, Message: msg, ObservedGeneration: releaseGeneration(app)}` when `stopsFirstRelease(app, dep)` holds. Write it in the same status update as `Phase=Failed`.
2. Confirm that the next pass scales the Deployment to 0, and that a new deploy, restart or resume clears the stop, as w1/m179's envtests already assert for the deadline.
3. Keep the served-release branch unchanged: it restores the served template.

## Files

- `lego/operator/internal/controller/app_controller.go`
- `lego/operator/internal/controller/web_image_http.go`, only if its caller needs the same write

## Acceptance criteria

- [ ] Envtest: a first release whose container crash-loops reaches `update_failed`, then 0 replicas and no pod, well before the progress deadline.
- [ ] Envtest: a container that would start fine after its third restart never serves under the failed release.
- [ ] Envtest regressions:
  - a crash over a serving release restores and keeps the serving release (w1/m172, w4/454);
  - the deadline stop (w1/m179) still holds.
