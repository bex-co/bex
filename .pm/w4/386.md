# 386 — `RENDER_INSTANCE_ID` is the raw pod name, so a service cannot match it to its own instance in the API, logs or metrics

Why: w5/m148 gave every service Render's default variables. Its `RENDER_INSTANCE_ID`, however, is the Kubernetes pod name. That is not the instance id that bex-api reports for the same instance on `GET /v1/services/{id}/instances`, which logs, metrics and SSH selectors also use. So a process cannot correlate itself with the instance it appears as. The value also exposes internal naming: the workspace id, the CR name and the ReplicaSet hash.

**Severity:** minor (the variable is present but inconsistent with every other surface; nothing breaks outright). **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run e2v5, 2026-10-21 UTC, `muse.env`, workspace `bex-canary`, pin `a3f66521f93d`. Fixture: a Free image service `qa-20261021-e2v5-env` (`srv-dbcad3603oos73cqipm0`, `busybox:1.37`, one instance), deleted in-run (404). The session was revoked.

## Probe

The service ran `env | grep -E "^(RENDER|IS_PULL|PORT=|WEB_CONC)" | sort` into a file served by `httpd` on `$PORT`. `PORT=8080` was set by the user, and w5/m149's PORT override worked: `serviceDetails.port: 8080` and served 200.

```
GET https://qa-20261021-e2v5-env.onbex.co/e.txt
RENDER_INSTANCE_ID=tea-daif693dqjvc73e7as3g-qa-20261021-e2v5-env-5ff6c9466c-l4hnb
RENDER_SERVICE_ID=srv-dbcad3603oos73cqipm0
… (RENDER, IS_PULL_REQUEST, RENDER_CPU_COUNT, RENDER_DISCOVERY_SERVICE, RENDER_EXTERNAL_HOSTNAME/URL,
   RENDER_SERVICE_NAME/TYPE, RENDER_WEB_CONCURRENCY, WEB_CONCURRENCY all correct)

GET /v1/services/srv-dbcad3603oos73cqipm0/instances
[{"id":"srv-dbcad3603oos73cqipm0-0geqpi3ufkm37qmb6951","createdAt":"2026-10-21T11:48:28Z"}]
```

One instance, two different ids.

Control: a static site's build env (`env | grep ^RENDER` in its build command) matched Render's set exactly, including `RENDER_GIT_COMMIT=2b7ceb59d856…`, `RENDER_GIT_BRANCH=main`, `RENDER_GIT_REPO_SLUG=bex-co/bex` and `RENDER_SERVICE_TYPE=static`. No `RENDER_INSTANCE_ID` appears there, which is correct for a build.

## Root cause

- `platformEnv` (`lego/operator/internal/controller/platform_env.go:44-60`) sets `RENDER_INSTANCE_ID` from the downward API `metadata.name`, the pod name. This is recorded as a decision in `.pm/w5/done/m148/README.md:36` ("`RENDER_INSTANCE_ID` is the pod name").
- Every API surface instead names an instance `id.ServiceInstanceID(serviceID, podName)` = `srv-…-<sha256-derived 20 chars>` (`lego/backend/internal/id/instance.go:31`, `id.go:204-214`, w4/m87).
- A container cannot compute that hash from the downward API, so the env value can never equal the public id under the current scheme.

## Fix (target behavior)

`RENDER_INSTANCE_ID` must equal the `id` that `GET /v1/services/{id}/instances`, the logs `instance` label and the metrics `instance` label report for the same running instance, which is Render's contract for the variable.

Pick one approach and record it in ADR020/ADR018:

- **(a) The operator stamps it.** For example, a mutating step or init container writes the derived id into the container's env or a file the entrypoint exports. Note that downward-API env can read a pod annotation only if the annotation exists at creation.
- **(b) Make the public id derivable in-pod.** Define it from values the downward API exposes, for example `srv-<id>-<pod-name suffix>`. Because issued ids and SSH selectors change, keep the legacy resolve path that `LegacyServiceInstanceID` already models.

Either way, the value must not expose the workspace id or CR name.

Cron runs and pre-deploy jobs set the same variable (the m148 README): define what they report, for example the job pod's derived id, and keep it consistent.

## Acceptance

- Live: a one-instance service's `RENDER_INSTANCE_ID` equals `GET …/instances[0].id` and the `instance` label on its own log lines.
- An operator test covers the env projection, and a backend test confirms the id derivation agrees with the in-pod value.
- `make test` (operator), backend `go test ./...` and `make lint` pass.

## Unverified

- Render's exact `RENDER_INSTANCE_ID` format; no signed-in Render capture. The contract asserted here is only that it names the instance the platform reports.
- Cron and pre-deploy values were not probed: cron is paid-only, and pre-deploy was not run.
