# A Developer's Suspend and Resume on a protected environment's service read as allowed, then answer 403

Why: Render lets only Admins suspend or resume in a protected environment, so a Developer must see the control disabled with the reason, never click it and read a 403. The per-service menu and the service page still offer it to a Developer. Found by w4/m550 on 2026-11-21.

- **What happens:** the `serverActions` projection decides `suspend` on `can_operate` alone. For a protected member it adds the precondition `protected_confirmation_required` (`lego/backend/internal/apps/actioncaps.go`, `ActionCapabilities` and `suspendPrecondition`). The dashboard's `gateAction` presents that precondition as ready (`dashboard/src/features/capabilities/lib/resource-actions.ts`). Since w8/187 the verb itself asks for a fresh `can_manage` in a protected environment (`requireUnprotected` in `lego/backend/internal/apps/protection.go`) and issues no phrase. `actioncaps_test.go` (~:55-76) pins both halves: the projection says allowed, and the verb answers `ErrForbidden` for a non-Admin.
- **Resume** has no protection precondition at all in the projection, but the verb refuses a non-Admin the same way.
- **Where it shows:** the service row menu (`service-row-actions.tsx`) and the settings card (`suspend-service-card.tsx`, `resume-service-button.tsx`) enable Suspend and Resume for a Developer on a protected member. Datastores gate on the workspace `can_operate` only (`database-row-actions.tsx`, `key-value-row-actions.tsx`) and have the same gap.
- **End state:** for a protected member, the projection reports `suspend` and `resume` denied for a caller without a fresh `can_manage`, by the same predicate `requireUnprotected` uses. The dashboard then shows each per-resource Suspend and Resume disabled with a reason for a Developer, and enabled for an Admin. A backend test pins the projection against the verb for both roles. The bulk toolbar (w4/m550) already gates this way, on the workspace grant.
