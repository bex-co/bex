# w4/259 — Cron start events omit the required run ID

Why: a customer consuming a cron-start event cannot use its details to identify the run, although the matching run object and completion event already have a stable public ID.

**Severity:** minor API parity defect. **Estimate:** 55m. Functional live QA a206, 2026-10-11 UTC, `https://dashboard.bex.co`, credentials handled by `scripts/qa-login.sh` from `muse.env`. Research pin: `7911ab99f`. Filing only; no product fix was made.

- **Repro:** create owned Free image-backed cron `qa-20261011-a206-failure` (`srv-db5rklshj6ks739l0msg`), `docker.io/library/busybox:1.36.1`, schedule `* * * * *`, command `sh -c 'echo qa-a206-start; sleep 7; echo qa-a206-exit-17; exit 17'`. Wait for a scheduled run. Read its events through REST and GraphQL. Change Command to `sh -c 'echo qa-a206-recovered-start; sleep 7; echo qa-a206-recovered-done; exit 0'`, let its configuration deploy reach Live, and observe a successful scheduled run. Save annual schedule `0 0 1 1 *`, then use Trigger Run and confirm. Reload the desktop page and repeat the reads.
- **Actual:** the scheduled start at 16:34:00 and manual start at 16:38:04 each have REST `details:{}`; GraphQL returns `cronJobRunId:""`. All five observed starts lack that ID. Each matching completion carries the correct `crr-` ID. A fresh desktop read at 16:38:36 and direct retrieval of the manual start at 16:39:22 reproduce it. This is an event-association/contract defect; no cron execution failure is attributed to it.
- **Expected:** started details contain the same public `cronJobRunId` as the actual run and its eventual completion. The ID is available while the run is active; it must not depend on completion. Both scheduled and manual runs use the same rule.
- **Render:** the pinned `lego/backend/internal/api/openapi/render-public-api-1.json` and [current public Render OpenAPI](https://api-docs.render.com/openapi/render-public-api-1.json), fetched and parsed on 2026-10-11 at 16:47 UTC, both define inline **Cron Job Run Started** details as `{"title":"Cron Job Run Started","type":"object","required":["cronJobRunId"],"properties":{"cronJobRunId":{"type":"string"}}}`. Location: `paths["/events/{eventId}"].get.responses["200"].content["application/json"].schema.properties.details.oneOf[0].oneOf[10]`. This is contract evidence, not an authenticated Render execution capture.
- **Root cause:** `lego/backend/internal/store/reconciler.go:525–532` records a start without `RunID`, whereas the ended fact at 548–555 uses `ids.Derive(ids.CronRun, run.Name)`. `apps/service.go:1271–1278` derives the public run object from exactly the same name. The store's list and retrieve queries carry `run_id` (`store/events.go:447,606`), and `events/service.go:1014` forwards it to neutral details. Independently, `events/rest.go:244–246` assigns the REST field only for `TypeCronJobRunEnded`; fixing the producer alone leaves started REST/MCP output broken.
- **Serialization / declaration:** `renderDetails.CronJobRunID` is already a string with `json:"cronJobRunId,omitempty"` (`events/rest.go:123`), and `core/http.go:236–240` calls `encoding/json`. The installed Go 1.27 encoder `encode.go:734–736` skips empty fields, explaining the missing REST key; production toolchain provenance was not read. GraphQL uses the existing nullable String field (`events/graphql.go:99`, `gqlutil/gqlutil.go:61`); pinned `graphql-go/graphql v0.8.1` `scalars.go:307–315` preserves a string value through coercion, explaining the empty string. No schema widening is needed.
- **Fix target / historical records:** set started facts' RunID using the existing canonical derivation, and copy the ID for started and ended events in the REST formatter while keeping the reason object exclusive to ended events. Existing starts must also read correctly: insertion uses `ON CONFLICT (source_key) DO NOTHING` (`store/event_facts.go:246–253`), so a producer-only change never enriches old rows. Prefer a small, type-scoped neutral-view fallback for a blank started ID from a validated canonical `fact:cron:<appID>:<run.Name>:started` key (`store/events.go:405` and `reconciler.go:527`), reusing `ids.Derive`. The stored nonempty ID wins. Do not derive from timestamps, service display names, event IDs or a new random ID; malformed/noncanonical keys must not manufacture an association. Keep original event IDs, timestamps, source keys, cursors, order and exactly-once facts, including after Job GC/history retention. This avoids a global writer/upsert migration.
- **Shared scope / aliases:** exhaustive non-test searches find two callers of neutral `events.view`: List and Get (`service.go:811,847`). `toRenderEvent` has four production use sites: the list mapper, REST retrieve callback, MCP retrieve, and MCP list_events. The list mapper has two callers: REST list and legacy MCP list_service_events. Entry points: `GET /v1/services/{id}/events`, `GET /v1/events/{eventId}`, GraphQL `serviceEvents` / `serviceEvent`, MCP `list_events` / `list_service_events` / `get_service_event`. Allowlist the changed semantics to cron starts; web/static/worker/private, Postgres and Key Value events keep their type-specific details. Dashboard Activity consumes the same feed but currently does not select/use this run-ID field; no new UI feature is required. Outbound webhooks remain thin and hydrate through event retrieval; notification delivery is not changed.
