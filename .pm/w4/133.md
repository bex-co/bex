# Manage resources discards an unsaved membership selection when the user switches tabs

Why: inspecting another resource kind silently reverses the user's checkbox edits, so the environment assignment dialog cannot retain a draft long enough to review it before saving.

- **Severity:** major — lost **unsaved** form input only. No persisted membership loss was observed.
- **Estimate:** 55m, including the four callers' regression/control coverage; one inbox-sized dashboard fix.
- **Source:** live `/qa-find-bugs` on `https://dashboard.bex.co`, 2026-09-21 America/Los_Angeles (2026-09-22 UTC), filed in w4 at the user's request. Journey 1: project/environment resource management.
- **Goal linkage:** reliable hosting management under [ADR032](../../docs/ADR032-environments.md) and [ADR018's Projects & environments row](../../docs/ADR018-render-parity.md). Users must be able to review a membership draft without tab navigation resetting it.

## Reproduction and durable evidence

On `/project/prj-dap10294dm7c7390q6s0?env=env-dap106h4dm7c7390q6tg`:

1. Open the environment's **Manage resources** dialog. QA service `srv-dap10ep4dm7c7390q6vg` is initially checked on **Services**.
2. Uncheck that service: its checkbox becomes unchecked.
3. Click **Databases**, then **Services**: the same checkbox is checked again. No Save was clicked.
4. Reload the page and repeat, switching through **Key Value** instead: the same checked → unchecked → checked sequence occurs.

**Expected:** the unchecked draft survives both tab round trips until the user explicitly closes/cancels the dialog or successfully saves a tab. **Actual:** returning to Services restores the persisted checked value and loses the draft.

**Evidence:** `.playwright-mcp/qa-projects-1.png` (existence verified before filing; local, gitignored supporting screenshot). The API control below is the durable evidence that this is a local draft reset, not a background membership mutation. Send from an authenticated browser with credentials included:

```http
POST https://api.bex.co/graphql
Content-Type: application/json

{"query":"query { environment(id:\"env-dap106h4dm7c7390q6tg\") { id serviceIds } }"}
```

HTTP **200**, complete response after the no-save round trip:

```json
{
  "data": {
    "environment": {
      "id": "env-dap106h4dm7c7390q6tg",
      "serviceIds": ["srv-dap10ep4dm7c7390q6vg"]

```

No failing request is needed to produce the symptom: the successful read still names the original member, as expected when no Save occurred. Re-run with replacement QA fixture IDs after this hunt's fixtures are cleaned up.

## Root cause and consumer trace

`dashboard/src/features/environments/components/resource-checklist.tsx:42` owns `checked` in local state and initializes it from `initialChecked` on each mount. Its callers sit inside ordinary `TabsContent` at `manage-resources-dialog.tsx:124`, `:138`, `:154`, and `:170`. The wrapper at `dashboard/src/common/components/ui/tabs.tsx:90` forwards to Radix without changing its mounting behavior.

The actual pinned framework path was read: `dashboard/yarn.lock:3720` resolves `@radix-ui/react-tabs` **1.1.13**. Its installed `dist/index.mjs:157` uses `present: forceMount || isSelected`, and `:173` renders `children: present && children`. Switching away unmounts the checklist; returning initializes a new checklist from unchanged server membership. That predicts both the checkbox reset and the unchanged GraphQL control.

The consumer matters because this is a **full replacement**, not a delta: `resource-checklist.tsx:55` passes `[...checked]` to `onSave`, closing only when its result is true. `use-set-environment-services.ts:47` submits those exact IDs; `:37` awaits the Environments/Projects refetches; `:49` returns true on success and `:57` returns false on failure. The sibling hooks have the same contract. `api/environments.graphql:42`, `:48`, `:54`, and `:60` declare non-null lists of non-null strings, so an intentionally empty selection must continue to submit `[]`.

## Fix and blast radius

Own the four draft ID sets in `ManageResourcesForm`, which remains mounted across tab changes, and make `ResourceChecklist` controlled. Seed drafts from the environment when opening; preserve them across tab changes and unchanged background refetches. Keep inactive panels unmounted so only the active checklist and its Save/Cancel controls are accessible. Do not change the global Tabs primitive.

A bare `forceMount` is insufficient: Radix sets `hidden: !present` at `dist/index.mjs:164`, so forcing inactive panels present would also expose them unless separately hidden.

The exhaustive production usage search found **four `ResourceChecklist` call sites**, all in this dialog:

| Caller in `manage-resources-dialog.tsx` | Draft | Save mutation |
| --- | --- | --- |
| `:125` | Services | `setEnvironmentServices` |
| `:139` | Postgres | `setEnvironmentDatabases` |
| `:155` | Key Value | `setEnvironmentKeyValues` |
| `:171` | Env Groups | `setEnvironmentEnvGroups` |

There is **one production dialog mount**, `environment-card.tsx:440`, and **one production card mount**, `environments-panel.tsx:233`. The entry route is `/project/$projectId/`, with optional `?env=<id>` selection; no sibling dialog alias/importer was found. The Services caller covers web, static, cron, worker, and private services. The change is scoped to these four callers; REST, GraphQL, MCP, backend membership semantics, and their authorization remain unchanged.

**Save/close semantics:** clicking Save still writes only the active tab's replacement set. A successful Save closes the dialog as today, ending that dialog's drafts; it must not silently save other tabs. Cancel or dismissal also discards drafts. Reopening seeds from the latest persisted environment. A failed Save keeps the dialog and drafts for correction/retry.

**Pre-settle state:** keep the existing environment skeleton before data arrives; the management dialog starts from a rendered environment card. Do not reset an open draft whenever a poll supplies a new array instance.

**Adjacent classes:** forbidden, not-found, and timeout failures retain the existing hook error messages and false result, leaving the draft open; no error taxonomy or existence-disclosure change. Session-expiry handling stays with the existing application auth flow. Concurrent server membership conflict resolution is outside this finding.

## Definition of done and regression controls

- Repeat the two observed live round trips with a disposable QA member: uncheck on Services, visit Databases or Key Value, return to Services, and observe the checkbox **still unchecked**. The membership query above must still report the saved member until Save is clicked.
- On returning to Services, Save submits the retained current Services draft as its complete replacement set, including `[]` when the last member was unchecked. It closes on success; reopening reflects the saved membership. This is follow-up verification to run during the fix, not behavior exercised during this hunt.
- Cover all four callers with a parameterized component test: alter a selection, leave its tab, return, then save and assert the exact retained list reaches the correct setter. Also verify independent drafts in two tabs and that only the active tab's setter runs on Save.
- Preserve the working controls: persisted IDs are initially checked; Cancel/dismiss/reopen restores persisted state; successful Save closes; failed Save stays open with the draft; unchanged refetches preserve the draft; inactive panels' controls are absent from the accessibility tree. The existing six tests at `manage-resources-dialog.test.tsx:137` cover first-visit/save behavior but never switch away and back after editing.
