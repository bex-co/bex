# 217 — Service Environment offers groups from a different environment, then refuses every Link

Why: a correctly scoped group is advertised as available to a service that cannot use it, turning an ordinary configuration action into a predictable error despite the group-detail picker already enforcing the right rule.

- **Severity:** minor; backend scope enforcement works, with no cross-environment linkage or lost configuration observed.
- **Source:** continuous live `qa-find-bugs`, 2026-10-08 cycle 13, filed in w4 by user direction. Governing ADRs: ADR032 environment groups, ADR018 parity; supports ADR008's usable hosting configuration.
- **Estimate:** 55m: panel filter/readiness/copy 20m; behavioral regressions and correct sibling controls 15m; desktop/mobile, en/zh and parity verification + simplify/checks 15m; cleanup 5m. Inbox-sized UI fix; no backend boundary change.

## Reproduce and target behavior

1. In one owned `qa-` project, create two environments, Source and Target. Create a Free image-backed web service in each. Create a group in Source with synthetic MESSAGE and `qa-c13.txt`, link it to the Source service, then clone the group into Target. The clone copies both values but has no links. Edit its values independently.
2. Fresh-load `/services/<source-service-id>/env`. Under **Linked Environment Groups → Available to link**, the Target clone appears with an enabled **Link**, despite the service's Source scope. Click it: the toast reports that linked services must have the same Environment scope. The clone remains available and enabled.
3. Repeat after another desktop reload and at 390×844. Same refusal, with exact distinct environment IDs. Captured at 09:40:02, 09:40:46 and 09:42:32 UTC; no rate-limit response.
4. Control: open `/env-groups/<clone-id>` and its service picker. It offers the Target service, excludes the Source service, and linking succeeds. The Target public URL subsequently serves both clone beta markers; Source keeps both original alpha markers. Unlink Target: after its rollout, the public response becomes `unlinked\nno-file\n` and both link arrays are empty.

**Target:** the service panel lists only unlinked groups whose environment equals the service's resolved environment, using bex's existing exact-equality rule, including null/workspace equality. Counts and empty copy describe the compatible set; do not say every workspace group is already linked merely because all remaining groups are incompatible. Before scope resolution, show a pending state instead of enabled candidates or a settled zero count. An unresolved service or failed scope query must not default to workspace scope; offer an actionable failure/retry. Existing linked groups and Unlink remain visible, including legacy scope drift. Preserve the backend refusal for a direct or stale cross-scope request.

## Root cause and bounded fix

- `dashboard/src/features/services/components/env-groups-panel.tsx:137–140` filters **only** `!group.serviceLinks.includes(serviceId)`. Its rendered list (`:205–216`) therefore includes the clone. The Link control (`:386–399`) is disabled only while busy. The same component already loads `useEnvGroupScopeIndex` (`:78`), but uses scope for Create initialization rather than this list.
- Producer `features/env-groups/hooks/use-env-groups.ts:43–55` preserves `environmentId` as `string | null` (`types.ts:8`). Direct reads below prove the backend supplied distinct scopes. This is a missing native JavaScript predicate, not an Apollo/Radix conversion problem.
- Correct sibling `features/env-groups/components/linked-services-card.tsx:45–53` requires scope readiness and `serviceMatchesGroupScope`; its legacy-link warning (`:133`) retains unlink access. Its passing live picker has exactly one option, the Target fixture, before the successful write.
- Reuse `features/env-groups/lib/scope.ts:27–44`'s existing exact-scope predicate in the **service panel only**. Its map's missing entry means workspace only after authoritative scope/service resolution; `use-env-group-scope-index.ts:28–148` supplies owner-bound loading/error/ready/retry state. Handle its error/loading before offering new links, and preserve its workspace-generation guard. No semantics change to the shared helper or Create/group-detail consumers is needed.
- `lego/backend/internal/envgroups/service.go:1111–1162` authorizes and validates Link, including a second scope check under group CAS; `:1370–1382` correctly returns `ENV_GROUP_SERVICE_ENVIRONMENT_MISMATCH`. Leave this boundary intact. Forbidden, unauthenticated, unavailable, missing service and timeout remain their own error classes; none become an empty compatible set or an existence-revealing response.

**Blast radius, exhaustively searched on main `532cecc57`:** one production JSX `EnvGroupsPanel` mount, in `routes/services.$serviceId.env.tsx:59`; the shared `ServiceEnvPage` has two route entrypoints, `/services/$serviceId/env` and `/static/$serviceId/env`. Web/private/worker/cron use the service route; static has its own shared-page route. `/web/…`, `/pserv/…`, `/worker/…`, `/cron/…` splat aliases preserve subpaths and redirect to `/services` via `common/lib/render-alias.ts`. Postgres and Key Value do not mount this panel. Existing helper production call expressions: `serviceMatchesScope` has two Create-dialog uses plus the wrapper; `serviceMatchesGroupScope` has two uses in LinkedServicesCard (availability and drift warning). The latter has one production mount in the group-detail route. Keep those correct callers unchanged and regression-check them when adding the panel call.
