# w4/183 — Unlinking a deleted service's env-group link always 404s, stranding the link

Why: deleting a service should not permanently pollute its env groups with an unlinkable row; today the dead link can only go away with the whole group.

Live 2026-10-04 UTC (`/qa-find-bugs` loop3, muse.env): linked env group `evg-…q0m0` (scope `qa-loop3-env`) to service `srv-…9qsg`, then deleted the service. The group page keeps the row — raw service ID plus the "Legacy link outside this group's Environment" warning (`dashboard/src/features/env-groups/components/linked-services-card.tsx:133-141`, scope match fails because the service record is gone) — and its Unlink button always toasts "Not found".

Root cause: `UnlinkService` authorizes+fetches the service first and returns the error before dropping the group-side link (`lego/backend/internal/envgroups/service.go:1196-1205`), so a deleted service aborts the unlink. The sibling `detach` (DeleteEnvGroup's bulk path, same file) already tolerates `ErrNotFound` — "a since-deleted service just drops from the group" — which is why deleting the whole group still works.

Fix shape: in `UnlinkService`, on `ErrNotFound` from the service fetch, skip the App detach/roll and still remove the service from the group link set via the existing `mutateMetaCAS` path. Careful with the `w6/m17` authz shape: only tolerate `NotFound` (never `Forbidden`), and the group fetch's own authorization stays the gate; the removal writes only own-workspace group metadata. Add a backend test: link → delete service → unlink succeeds and the link set is empty. Optional dashboard follow-up: label a link whose service no longer resolves as deleted rather than "outside this group's Environment".
