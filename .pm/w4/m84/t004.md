## Objective

Let a tenant create a pending claim, copy its TXT record, retry verification, and distinguish ownership verification from certificate activation consistently in REST, GraphQL, MCP, and the dashboard.

## Context

`DomainView` currently returns the traffic CNAME/ALIAS instruction plus TLS-derived `verificationStatus`/`serverStatus`. The new lifecycle needs a stable ownership-proof instruction without conflating it with the record that routes traffic. The challenge is a bearer-like proof token: it is returned only after authorization and must not enter URLs, logs, analytics, or broad list responses unless the surface contract intentionally requires it.

## Steps

1. Extend the neutral domain view with explicit claim/ownership state and an ownership TXT instruction; keep traffic DNS instructions separate.
2. Align REST add/get/verify, GraphQL mutations/types, and MCP tools/error mapping on the same core fields and state transitions.
3. Update the dashboard custom-domain hook/component to show pending ownership, copy-ready TXT name/value, Verify action, and later certificate/server activation without claiming traffic is live early.
4. Add English and Chinese copy plus accessible loading/error/success states.

## Acceptance criteria

- [ ] All three API adapters expose the same pending/verified semantics and named failures.
- [ ] Dashboard users can copy the ownership TXT instruction and explicitly retry verification.
- [ ] Ownership-pending, certificate-pending, and active are visually/textually distinct.
- [ ] Challenge values do not appear in paths, query strings, logs, metrics, or unauthenticated responses.

## Out of scope

- Registrar automation, DNS-provider OAuth, mobile UI, or exposing Cloudflare-for-SaaS operations to tenants.
