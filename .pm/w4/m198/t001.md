## Objective

Resolve the continued step's real end for the requested canceled deploy through the existing events API. Keep the resolver local to the deploy feature and preserve the API's type, cursor and scope semantics.

## Context

- finding.md contains successful/error post-cancel facts with explicit details.deployId.
- events/graphql.go:168–177 supports type/startTime/endTime/cursor/limit; event timestamps are RFC3339 at second precision.
- The existing DeployTimelineEvents document lacks type/cursor, and useDeployTimeline closes its read at deploy.finishedAt; using it unchanged would omit the fact.
- Prefer a small deploy-local typed query/hook. The generic service-events pager is reference code; do not alter its other consumers casually.

## Steps

1. Add/reuse a typed paginated read for type pre_deploy_ended, selecting id/timestamp/cursor/details.deployId. Pin the event-search interval and cursor identity across pages; its end must include the observation of the completed step rather than stop at cancellation.
2. Resolve only the matching deploy's fact, scanning further cursor pages when the first page is capped. Return explicit loading/found/missing/error states and avoid taking a later deploy's event.
3. Define the event timestamp's precision and the inclusive log-end conversion. Do not silently clip fractional log times in the same second.
4. Do not add new API fields or store columns when existing event data expresses the result. If code evidence disproves this preferred path, document the specific representation gap before widening scope.

## Acceptance criteria

- [ ] A matching event behind a full first cursor page is found and another deploy's event is ignored.
- [ ] The search interval stays stable across pagination and reaches a fact after cancellation.
- [ ] Loading/missing/read-error states remain distinguishable; missing/actually-stopped steps cannot cause endless polling.
