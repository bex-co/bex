## Objective

The create-service form behaves like Render's: as the user types (or accepts the repo-derived auto-fill), a debounced availability check runs; a taken name shows **"Name is already in use"** inline under the input with the suggested free name offered as a one-click fix, and a create that still races into a 409 surfaces the same message instead of a generic toast.

## Context

- Form: `dashboard/src/routes/services.new.tsx` — name input `:476-492`, client validation `nameValid` `:239` via `isValidDnsLabel` (`dashboard/src/common/lib/utils/dns-label.ts`), auto-fill from repo/image slug `:225-237` (`nameEdited` gate `:201`).
- Create hook: `dashboard/src/features/services/hooks/use-create-service.ts:51-53` — currently a generic `toast.error` for every failure; must special-case the conflict error from t003.
- Known drift to fix while here: dashboard's `isValidDnsLabel` (leading letter, ≤63) vs backend `ValidAppName` (`[a-z0-9]`-start, ≤30) — align the client rule to the backend's.
- Locale keys: `dashboard/src/features/services/locales/{en,zh}.ts`.

## Steps

1. Add the debounced `serviceNameAvailable` query (Apollo) on the name field; on taken: inline "Name is already in use" + a suggestion chip/button that fills the input (`beancount-cms-v2-1`), disable submit while taken.
2. When the auto-filled repo slug is already taken (same repo → second service), prefill/offer the suggestion instead — the user's "same repo creates multiple services" case.
3. Map the create-mutation conflict error to the same inline message (race window), keep the generic toast for other failures.
4. Align `isValidDnsLabel` with backend `ValidAppName` (≤30, digit-start allowed).
5. Locale keys (en + zh); component test for the taken → suggest → accept → submit-enabled flow.
