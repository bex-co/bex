## Objective

A cheap tenant-scoped availability check the dashboard can debounce against: given a candidate name, answer `available: true/false` and, when taken, a concrete suggestion — the next free `<name>-N` (`beancount-cms-v2` taken → `beancount-cms-v2-1`, then `-2`, …), respecting the 30-char name cap.

## Context

- Nothing exists today — no availability query, no suggestion logic (mapped 2026-07-12).
- Uniqueness scope is the caller's tenant (`UNIQUE (tenant_id, name)`); the check must not reveal other tenants' names — it only answers within the caller's workspace (global collisions are absorbed silently by the t002 slug suffix).
- Render has no public availability API — this is a dashboard-serving convenience, so GraphQL is the primary adapter; expose REST/MCP only if it falls out naturally of the core method (one core, thin adapters — docs/ADR006).
- Suggestion must itself pass `ValidAppName` (`lego/backend/internal/store/api.go:407`): truncate the base before appending `-N` if needed.

## Steps

1. Core method on the apps service: `NameAvailable(ctx, name)` → `{available, suggestion}`; suggestion loops `name-1`, `name-2`, … against the tenant's existing names (single store/list query, then in-memory probe).
2. GraphQL query (e.g. `serviceNameAvailable(name: String!)`) wired to it; requires an authenticated caller with a tenant.
3. Unit tests: free name → available, no suggestion; taken → first free `-N`; `-N` chain occupied → next; 30-char boundary truncation; invalid input → 400-shaped error.

## Files

- `lego/backend/internal/apps/service.go` (or sibling)
- `lego/backend/internal/apps/graphql.go`
- tests alongside

## Acceptance criteria

- [ ] Query returns `available: false, suggestion: "beancount-cms-v2-1"` when `beancount-cms-v2` is taken in the caller's workspace and `-1` is free.
- [ ] The check never reflects other tenants' names.
- [ ] Suggestions always pass backend name validation.
