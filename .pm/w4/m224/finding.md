## Cause and proposed correction

- `dashboard/src/features/metrics/hooks/use-metrics-filter-values.ts:21-30`: `useQuery(MetricsFiltersDocument)` has variables and errorPolicy only. The combined `outputFilters:[INSTANCE,STATUS_CODE]` is intentional, but there is no poll interval, explicit refetch, or menu-open refresh. Resource-only variables remain unchanged when the live chart window ticks.
- `dashboard/src/features/metrics/components/network-metrics-card.tsx:111-152`: local status state and discovered codes feed All/classes plus sorted exact choices. `:223-227` renders arbitrary returned strings, consistent with204/409 immediately appearing after reload. The new API value never reaches this consumer before a fresh read.
- `dashboard/src/common/apollo/default-options.ts:23-25`: global watchQuery overrides only `notifyOnNetworkStatusChange:false`; it supplies no freshness policy. The actual native requests identify **@apollo/client4.3.3**, matching yarn.lock and the inspected primary package. `core/QueryManager.js:702` defaults to cache-first. `core/ObservableQuery.js:870-934` cancels polling without `pollInterval`; configured polling uses network-only and supports `skipPollAttempt`. A re-render with unchanged variables does not create freshness. Relevant primary-source excerpts and hashes are in evidence.json.
- `dashboard/src/routes/services.$serviceId.metrics.tsx:78-82` shares one moving window and sets `pollIntervalMs:0`; chart updates change start/end. Discovery has neither of those variables. Adding another chart timer is not the correction.

Provide one visible30s owner for the combined discovery query using `RESOURCE_POLL_INTERVAL_MS` and `skipPollWhenHidden` from `common/lib/polling.ts`. A concrete small option is an explicit ownership flag on this hook, enabled only by NetworkMetricsCard, which is unconditionally mounted by ServiceMetricsPage; ApplicationMetricsCard remains a cache observer of the same document and variables. Another implementation is acceptable if it proves one owner. Do not enable an independent timer in both hook callers or split the combined query back into two reads.

Keep the last usable discovery answer scoped to the current resource during a transient failure and while a poll is pending. Preserve initial class presets, the ready card structure and global notify behavior. Retain the selected exact code in its choices if a later answer temporarily omits it; discovery must not silently switch the request filter to All. That disappearance/error behavior is a required regression check, not an observed failure in this healthy-only hunt. Reuse the existing Logs discovery pattern only where its semantics fit; its separate document and timers are not this query's owner.
