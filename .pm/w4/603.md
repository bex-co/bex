# 603 — Turning maintenance mode off answers visitors `503 {"error":"service not ready"}` (a "waking up" page in a browser) until the route moves back, though the service is running and ready

Why: an owner ends maintenance on a paid, always-on web service, and visitors get a "not ready" 503 instead of the site until the operator repoints the host. That took about 55 s in round 181. Each such request also runs the free-tier wake path against a service that never sleeps.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 181, 2026-11-12 09:09–09:14 UTC (`muse.env`, workspace `bex-canary`; pin `3d66946c9e16`). **Minor** (a transient outage with the wrong reason; its length is the operator's reconcile latency). ~40m.
- **Fixture:** Starter web service `qa-20261112-r181-maint` (`srv-dbqo2ba6krac73d83fs0`, `traefik/whoami:v1.10.1`), deleted afterwards.
- **Probe:** each PATCH answered 200. `curl` polled `https://qa-20261112-r181-maint.onbex.co/`.

  | PATCH `serviceDetails.maintenanceMode` | At | Public host |
  | --- | --- | --- |
  | `{"enabled":true,"uri":""}` | 09:09:44 | still the app (200) until 09:10:57; the default page "This site is currently under maintenance." (503, `cache-control: no-store`) from 09:11:06, about 80 s |
  | `{"enabled":true,"uri":"https://example.com/"}` | 09:11:22 | `503` with `<title>Example Domain</title>` at 09:11:28 (6 s) |
  | `{"enabled":false,"uri":""}` | 09:11:35 | **`503 {"error":"service not ready","retryAfter":5}`** at 09:11:41, 09:11:50, 09:11:59, 09:12:07, 09:12:16 and 09:12:24; the app (200) from 09:12:33 |
  | enable again | 09:13:30 | maintenance page by 09:13:41 |
  | disable again | 09:13:47 | the app (200) at the first sample, 09:13:54 |

  Events and REST agree:
  - `maintenance_mode_enabled {"enabled":true}` at 09:09:44 and `{"enabled":false}` at 09:11:35;
  - `maintenance_mode_uri_updated` at 09:11:22 and 09:11:35;
  - no deploy row was created.
- **Root cause:**
  - **The activator reads the App's spec as soon as it changes.** That is why the URI change applied in 6 s.
  - **The route moves back only on the operator's next reconcile.** That pass repoints the host's Ingress from the activator back to the app, and took 80 s and 55 s on the slow passes and seconds on the fast ones.
  - **In between, the handler skips maintenance and treats the request as a wake.** `newHoldingHandler` (`lego/operator/cmd/activator/main.go`) no longer takes the maintenance branch (`:181-187`). It passes the suspended, first-deploy and static-site checks, because the App is Running with an active revision. It then runs the wake path:
    - `wakeApp` (`:319-348`) patches `last-active` and, if needed, the replicas;
    - `writeWakeResponse` (`:356-365`) answers 503 "service not ready", or the HTML wake page for a browser.
  - **That handler answers an App with ready instances.** The path assumes every request reaching the activator belongs to a sleeping or unready App, which a running service whose route has not yet moved back is not.
  - **The sibling w4/516 (done)** fixed the same route-lag shape for a deleted App by dropping it from the host cache (`refreshOnce`).
- **Fix (target behavior):**
  - From the moment the disable PATCH returns, a request to a non-hibernated, non-suspended App with a ready instance gets **the app's own response**. The activator proxies it to the App's Service immediately, with `holder`'s existing reverse proxy (`cmd/activator/hold.go:127`, used by `serve` `:274-296` after a wake).
  - No 503, no wake page, no `last-active` or replicas patch.
  - An App with no ready instance keeps today's answer: the readiness hold (`writeWakeResponse`) and the wake for a hibernated App.
  - Whether the App is ready is read from its cached status (Ready condition `True` for the current generation), the same cache the maintenance branch reads.
  - The same holds on enable: until the route moves, a visitor still reaches the app, which is today's behavior and is correct.
- **Blast radius:**
  - Only the activator's fall-through for a ready App changes.
  - Every other branch stays as it is, in order: unknown host, maintenance, suspended, failed first release, first deploy, static site, robots and wake. Each needs its existing test to stay green.
  - The other route-lag windows that reach the same fall-through for a ready App get the same fix. A resume, a move out of maintenance during a suspend, and a scale-up from 0 are reasoned, not probed.
- **Tests:**
  - With maintenance just turned off on a Running App with a ready instance, the handler proxies to its Service and patches nothing.
  - A Running App with no ready instance still gets `service not ready`.
  - A hibernated App still wakes.
- **Unverified:**
  - The HTML answer during the gap. Round 181's gap samples were taken without `Accept: text/html`; the HTML branch of `writeWakeResponse` is read from code.
  - Render's behavior. Render's maintenance toggle has no documented gap; the target is the app's own response.
- **Also seen (recorded on w21/012):** the 80 s enable came with a first deploy that queued 3 m 06 s (09:04:45 → 09:07:51).
  - The App's spec reached the activator within 6 s (the URI change), so the lag is the operator's reconcile of the App, not bex-api's projection.
- **Dedupe:**
  - w4/516 (done) covers the deleted-App case only.
  - `docs/render-artifacts/maintenance-mode.md`'s CAPD record says "disable restored the original Ingress backend immediately", on an idle cluster.
  - `grep -rl -i maintenance .pm | xargs grep -l "not ready"` finds only 516.
  - Not deploy lag: nothing after `3d66946c9` touches `cmd/activator`.
- **DoD (live):** on an owned Starter web service, enable maintenance and wait for the default page. Then disable it and poll the host every 2 s with and without `Accept: text/html`. Every sample is either the maintenance page or the app's own 200, never `service not ready` or the wake page. Repeat three times.
