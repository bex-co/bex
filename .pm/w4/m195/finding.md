# Renaming into a name deleted in the same environment draft cannot be saved

Why: the staged editor should save a unique, valid final map in one transaction while preserving an existing opaque value or file's contents.

- **Severity:** major. Both variables and files have a valid final draft that cannot be saved; a delete-only save followed by a rename-only save works. Failed saves report the error and retain the draft. No data loss is claimed.
- **Source:** functional qa-find-bugs, 2026-10-10 UTC pass a73, muse profile, workspace `tea-d98210cbbpdc73dcrkvg`; research HEAD `9abb6fdca7fec2a0a4963dceb24055a7a9dfb8ee`. Filing only.
- **Estimate:** 3h across client ordering, backend bookkeeping, shared-caller verification and closing tasks.
- **Owned fixtures:** Free BusyBox web service `srv-db56vn46flus738pnmtg` / **qa-20261010-a73-renames** and standalone, unlinked group `evg-db575ic6flus738pnn2g` / **qa-20261010-a73-rename-group**. Both deleted; cleanup receipts below.

## Root cause and bounded fix

- `dashboard/src/features/services/lib/environment-draft.ts:332–367`: `patchRows` emits operations in stored row order. Tombstones emit an original-name deletion at :345–347; unchanged opaque rows emit `fromKey` / `fromName` renames at :350–353. User click order does not determine wire order. NEW before RIGHT produces rename-first on the service; DEST before SOURCE produces delete-first on the group. Final nondeleted-row validation at :294–319 accepts these unique names.
- `lego/backend/internal/core/environmentpatch.go:139–160`: `applyRenameOp` checks the current destination map at :154–155. Rename-first sees the still-present destination and refuses it.
- `applyMapPatch` at :167–195 uses one `seen` map for operation names. The duplicate check at :180–183 rejects the second destination operation even when an explicit deletion at :190–195 already freed that destination. Delete-first therefore also fails.
- The locked `graphql-go/graphql v0.8.1` actual source `values.go:133–153` coerces a List by ascending slice index and appends each element in that order. This is not serializer reordering: the captured Apollo 4.1.3 wire order matches the client producer.

**Target:** emit explicit stored-row deletions before opaque renames in the draft producer. In core, distinguish explicit destination deletion from a destination write and source consumption enough to permit exactly one opaque rename from a distinct existing source into that explicitly deleted name. Source bytes move unchanged; the source disappears and the intentionally deleted destination bytes are replaced. Validate the full candidate batch before committing stores/projections.

Preserve the ordered API contract: an arbitrary rename-first direct API request may retain its occupied-destination error; the UI must send the admissible delete-first sequence. Do not add cycle normalization or a general arbitrary-order graph planner. Retain refusals for undeleted occupied destinations, duplicate writes/deletes, repeated source use, missing sources, rename mixed with payload/delete and delete mixed with payload; retain name validation/recovery and no-op rules. Preserve changed-content rename sequencing, readonly-row omission, the limited single-value service CAS protocol, group expectedRevision, rollout defaults and compensation. A fix must not reveal contents or secretly split one UI Save into two writes.

The one production `environmentDraftPatch` consumer is `service-environment-editor.tsx:337`. The shared `EnvironmentEditor` has two hosts: service wrapper :124 and `env-group-editors.tsx:30`. It retains the draft while saving or after a refusal; successful saves refetch/adopt persisted names. Preserve those pre-settle and failure behaviors.
