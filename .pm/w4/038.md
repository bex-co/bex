# 038 — `GET /v1/projects` rejects a missing `ownerId` with an opaque `bad request`

Why: A REST/CLI client that lists projects the way Render's own spec allows (no `ownerId`) gets an unactionable `400 {"error":"bad request"}` — every validator-gated sibling route instead names the offending parameter, so projects is the odd one out and the caller is left guessing.

Found in a live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-02, workspace `tea-da2isimlm39c739m4ofg`.

## Evidence (re-runnable)

Probe from inside an authenticated page (`fetch(url, {credentials:'include'})`) — `api.bex.co` sits behind Cloudflare, which 403s bare non-browser User-Agents.

```
GET /v1/projects                                             -> 400 {"error":"bad request","id":"bad_request","message":"bad request"}
GET /v1/projects?limit=1 | ?limit=20 | ?limit=100           -> 400 same bare body (limit value is irrelevant)
GET /v1/projects?ownerId=tea-da2isimlm39c739m4ofg&limit=100 -> 200 (3 projects)   [ownerId is the ONLY thing that flips 400->200]
GET /v1/environments   (missing required projectId)         -> 400 {"error":"invalid query parameter \"projectId\"", ...}   [descriptive SIBLING]
GET /v1/services?limit=101   (out-of-range)                 -> 400 {"error":"invalid query parameter \"limit\"", ...}       [descriptive CONTROL]
```

## Root cause

`lego/backend/internal/projects/rest.go:79-83` — the `GET /v1/projects` handler returns a bare `core.ErrBadRequest` when `ownerId` is empty.

The descriptive errors on the sibling routes do **not** come from their handlers (the environments handler _also_ returns bare `core.ErrBadRequest` for a missing `projectId`). They come from the kin-openapi request validator wired at `internal/api/server.go:1091` (`newRenderRequestValidator`) / `internal/api/render_openapi.go`, which validates each request against Render's pinned public OpenAPI spec and emits `invalid query parameter "X"`. Render's spec marks `ownerId` **optional** on `GET /v1/projects`, so the validator passes the `ownerId`-less request through as valid and bex's handler is the **sole** source of the 400 — so the message is opaque _and_ the 400 itself diverges from Render's contract (a Render-conformant client expects 200).

## Fix (name the target behavior)

Emit a descriptive error from the handler, e.g. `fmt.Errorf("%w: invalid query parameter %q", core.ErrBadRequest, "ownerId")`, so the caller learns which param is required — matching the validator-gated siblings and the deliberately-parallel `GET /v1/environments`. Do **not** silently reverse the intentional requirement here.

The deeper parity question (Render marks `ownerId` optional; bex requires it — see `w1/done/m32/done/t003.md:21`, which made environments' `?projectId=` required "matching Projects' required `?ownerId=`") is a separate product decision and belongs with the projects-parity rework already open in `w6/m126`; do not fold it in.

## Blast radius

REST-only, one handler. GraphQL `projects` makes `ownerId` a `gqlutil.ReqArg` (`graphql.go:46` — schema-enforced, gives its own validation error) and MCP `list_projects` uses `core.NamedWorkspace(ctx)` (defaults like siblings), so neither needs the change.

## Dedup

- Projects REST **response-shape** parity is the open milestone `w6/m126` — a different concern (POST/PATCH/links return the internal view, not this list-route error).

- "Unfiltered list defaults to first workspace" is the documented/tested contract (`w6/m14/t008`, `w6/m18/t001`) — not filed.

## Render

Render's `GET /v1/projects` treats `ownerId` as an optional filter; bex's hard requirement is a deliberate divergence, but the opaque message is not.

Estimate: ~20–30 min (one-line handler change + a `rest_test.go` assertion that the missing-`ownerId` 400 body names `ownerId`).
