# 366 — A Blueprint sync that changes a suspended service still files a deploy that can only be canceled

Why: w4/m234 made every configuration writer hold a change on a suspended service for its next deploy, with no deploy row. Blueprint sync is the one release-rolling writer that does not go through `rollout.Snapshot.Stamp`, so it still opens a `blueprint` row that the reconciler closes "Canceled: the service was suspended", plus a `deploy_started`/`deploy_ended` pair per sync.

**Source:** w4/m234 simplify review, loopx w4, 2026-10-19 (code-read; not probed live).

## Where

- `lego/backend/internal/apps/deploy.go`, the Blueprint service update: when the deploy spec changed it stamps `AnnotationReleaseGeneration` itself, resolves the branch tip into `BuildCommit`, files the row (`recordBlueprintRedeploy`) and bumps `restartedAt`.
- The m234 hold to mirror: `rollout.Snapshot.Stamp` writes `AnnotationPendingSourceGeneration` instead of a release stamp on a suspended App, and the operator keeps the prior release through Resume (`TestPendingSourceWaitsForADeployGeneration`).

## Decide, then do

- Hold it like the other writers: on a suspended App, persist the Blueprint intent and spec, write the pending-source hold instead of the release stamp, and skip the commit resolution, the row and the `restartedAt` bump. The sync result should say the service is suspended and the change waits for a deploy. Or record why a sync stays a deploy (Render documents nothing for a suspended service).
- Keep w5/m114: Resume never rolls a release without a row. Keep w4/m171: a deploy interrupted by suspend still closes canceled.
- Test: a sync that changes a suspended service's start command opens no row, leaves the release annotation alone and sets the hold; the running-service control still opens one `blueprint` row.
