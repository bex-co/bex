# 396 — REST `GET /v1/env-groups` (the list) now returns every secret value and refuses the whole list to Viewer/Contributor/Billing; Render's list is metadata only

Why: w8/182 put values on Render's **retrieve** schema, which requires them, but applied the same reveal to the **list**. Render's list returns `envGroupMeta` (no `envVars`). So a CLI or script that lists groups now prints every secret of every group. A member whose role may read resource lists but not secrets gets `403` for the whole list instead of names.

**Severity:** minor (read-path parity, plus wider value exposure on a list call; the dashboard uses GraphQL and is unaffected). **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run j5r3, 2026-10-23 UTC (`muse.env`, `bex-canary`, pin `fa8ac5bba24a`). Fixtures: project `qa-20261022-j5r3-proj` (`prj-dbder208dkas73a0v4fg`), environment `prod` (`evm-dbder208dkas73a0v4g0`) and group `qa-20261022-j5r3-grp` (`evg-dbder288dkas73a0v4h0`, `QA_J5R3=secret-v1`). All were deleted (`GET` → `404`); session revoked.

## Probe

- `GET /v1/env-groups?ownerId=tea-daif693dqjvc73e7as3g` (Admin session) → `200`, with each item carrying `"envVars":[{"key":"QA_J5R3","value":"secret-v1"}]`.
- Pinned Render schema (`lego/backend/internal/api/openapi/render-public-api-1.json`):
  - `GET /env-groups` 200 is `array<envGroupMeta>`. `envGroupMeta` = `{id, name, ownerId, createdAt, updatedAt, serviceLinks, environmentId}`, with no `envVars` or `secretFiles`.
  - `GET /env-groups/{envGroupId}` is `envGroupMeta` + required `envVars`/`secretFiles`. That retrieve shape is what w8/182 correctly targeted.
- Controls from the same run, all correct: retrieve carries values; default paging gives Render's first page in stable order; `cursor` continues; `limit=101` → `400`; `DELETE` of a non-empty environment/project → `409 ENVIRONMENT_NOT_EMPTY` / `PROJECT_NOT_EMPTY`; an inline environment without ACL fields keeps the allow-all seed.

## Root cause

`lego/backend/internal/envgroups/rest.go:80-99`: the list handler pages, then calls `s.revealGroups` (`render.go:123-160`). That authorizes **`can_view_sensitive` on every group, fresh**, and fails the whole response if any one is refused. Per `docs/ADR024-members.md:20-23`, `viewer` ("read-only resource lists… not sensitive fields"), `contributor` and `billing` lack `can_view_sensitive`, so for them the list is a `403`. The ADR018 env-group row (w8/182) records the list as deliberately revealing.

## Fix (target behavior)

- `GET /v1/env-groups` answers Render's `envGroupMeta` items (no values or contents) under `can_view`, the same gate as other resource lists.
- `GET /v1/env-groups/{id}` and the write responses keep values behind `can_view_sensitive`, as now.
- Conformance: validate the list against `envGroupMeta` (no `envVars` key). Add a role test: Viewer and Contributor get the metadata list, and `403` on retrieve.
- Update the ADR018 env-group row (w8/182 note) to match.

**Unverified:** the Viewer/Contributor `403` live (the QA workspace has no non-Admin member; the behavior is read from `revealGroups`); whether any bex client relies on list values (the dashboard does not; it uses GraphQL).
