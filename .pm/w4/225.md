# Clearing a service label falsely says its name resets to the immutable ID

Why: users should be able to distinguish the restored service name from its stable resource ID after an ordinary Settings edit.

**Severity:** minor. **Estimate:** 30m. **Source:** production `$qa-find-bugs w4`, 2026-10-09, pass a25; filing only.

## Reproduction and target

Create an owned Free image web service named `qa-20261009-loop-a25-identity`, wait for Live, and set its Service Name to `qa-20261009-loop-a25-clear-repro`. Reload `/services/srv-db4c1foec12s73fjue8g/settings`; Edit service name → clear the input → Save changes. At `10:29:18.976Z`, the heading and disabled input correctly restored `qa-20261009-loop-a25-identity`, while the toast said **“Service name reset to its immutable ID.”** The separate Service ID and hint still showed `srv-db4c1foec12s73fjue8g`.

An earlier 390×844 clear produced the same English toast. A fresh Chinese page at `/settings?lang=zh`, after setting `qa-20261009-loop-a25-clear-zh`, reproduced at `10:31:30.995Z`: **“服务名称已重置为其不可变 ID。”** Its heading/input likewise restored the original name.

**Target:** replace `services.displayNameCleared` in both supported catalogs with truthful label-clearing copy, such as **“Custom service name cleared.” / “自定义服务名称已清除。”** Keep the existing correct fallback to the immutable original name, typed ID, routing, revision, mutation and validation behavior. This neutral copy also accommodates the component's last-resort ID fallback when no name is available.

## Cause and scope

- `dashboard/src/features/services/locales/en.ts:1176–1178` and `zh.ts:1150–1152` author the false ID wording.
- `hooks/use-display-name.ts:23–27` selects that key only after a successful empty-label mutation. `components/display-name-row.tsx:30–37` correctly displays `current || name || serviceId`; Settings supplies the fetched name at `routes/services.$serviceId.settings.tsx:110–114`.
- `lego/backend/internal/apps/service.go:4677–4704` clears only the label. `apps/render.go:689–698` returns `DisplayName` or the immutable App name, while GraphQL `apps/graphql.go:305` uses that same helper. This is authored toast copy, not a backend/serializer discrepancy.
- The catalog extraction in `src/i18n/index.ts:46–50` passes each entry's message to the translation resources; `common/hooks/use-translations.ts` delegates to i18next. The installed lockfile-pinned i18next 26.3.4 `dist/esm/i18next.js:718–789` returns the resolved/interpolated message; Sonner 2.0.7 `dist/index.mjs:142–174,212–217` publishes the supplied success message. No missing key or library-generated ID claim is involved.

**Blast radius / aliases:** exhaustive production searches found one `useDisplayName` caller, one `DisplayNameRow` mount and exactly two `displayNameCleared` catalog definitions (`en`, `zh`). The shared `ServiceSettingsPage` serves `/services/<id>/settings` and `/static/<id>/settings`; the latter imports it explicitly. Web/private/worker/cron/static use this App family; Render aliases `/web`, `/pserv`, `/worker`, `/cron`, `/static` canonicalize through the shared service routes. Postgres and Key Value have separate rename surfaces and do not call this hook. Change these two catalog messages, preserving other callers and keys.

**Adjacent states:** nonempty rename keeps its named success toast. No-op empty clear stays unsavable. Rejected length/control/ID/uniqueness writes retain their draft and error feedback; auth, forbidden, not-found, timeout and saving states retain their existing behavior. Success copy appears only after a successful mutation. This finding makes no new claim about those server error classes.
