# 580 — Measure the cron run time that was never metered (manual runs, and every run of 28–30-character cron jobs), then decide whether to repair it

Why: until w4/m322 the usage meter's pod selector saw no manual cron run, and no run of a cron job whose service name is 28–30 characters. Those seconds were recorded as healthy zeros, and the months already rolled up won't revisit them. w4/m322 fixes the selector going forward. Whether to backfill is a billing decision.

- **Source / severity / estimate:** w4/m322 t003 step 2, `/loopx w4` 2026-11-11. **Minor–major** (unbilled paid usage). ~1h read-only, then a decision.
- **Method (read-only, like w4/m173 t002):**
  - For each cron App, compare the summed run durations in Kubernetes Job history (or the run facts in the events store, `recordCronRunFacts`) with the metered `instance_seconds` per hour since the cron feature shipped.
  - Report per workspace: the unmetered seconds, at list rate, and which ones fall in billed periods (paid plans, Stripe-emitted rows).
- **Decision:** within `catchupLimit` (48 h), re-roll the hours, or record the rest as accepted history in ADR040. If billed periods are affected, the user decides, as with w4/m173.
- **Dedupe:** w4/m173 (blocked; the instance-seconds arithmetic repair decision) and w4/m322 (the selector fix).
