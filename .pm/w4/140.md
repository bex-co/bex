# The dashboard's Registry Credentials page ignores the workspace switcher on all five verbs

Why: every other resource list in the dashboard scopes itself to the switcher's selected workspace, but the registry-credentials feature sends no `ownerId` at all — so a user who switches to a second workspace sees, creates, edits and deletes the **default** workspace's credentials while the switcher says otherwise.

Filed while working [`w4/128`](128.md), which fixed the API half. Found by reading the feature's five hooks and its GraphQL document, not by a live probe.

## The gap, in one file

`dashboard/src/features/registry-credentials/api/registry-credentials.graphql` declares no `$ownerId` variable on any operation, and none of the five hooks in `dashboard/src/features/registry-credentials/hooks/` imports `useWorkspace`:

| hook | operation | sends `ownerId`? |
| --- | --- | --- |
| `use-registry-credentials.ts` | `registryCredentials` | no |
| `use-registry-credential.ts` | `registryCredential(id:)` | no |
| `use-create-registry-credential.ts` | `createRegistryCredential` | no |
| `use-update-registry-credential.ts` | `updateRegistryCredential` | no |
| `use-delete-registry-credential.ts` | `deleteRegistryCredential` | no |

Contrast `dashboard/src/features/services/hooks/use-services.ts:43-48`, the established idiom: read `currentWorkspaceId` from `useWorkspace()`, pass it as `ownerId`, and `skip` the query until the selection resolves so the hook never fires a fetch-then-refetch pair against a null id.

## Why it is filed separately from w4/128

`w4/128` was scoped to the server: `registryCredential`, `updateRegistryCredential` and `deleteRegistryCredential` accepted no `ownerId` at all, so no client could have sent one. That is fixed — all five GraphQL verbs and all five REST routes now bind an optional `ownerId`, so this is now purely a client-side wiring gap. It is also **wider** than `w4/128`'s finding: list and create are affected here too, and `w4/128` correctly recorded those two as already carrying the argument on the wire.

## Fix

Add `$ownerId: String` to all five operations in the `.graphql` document, and thread `currentWorkspaceId` through the five hooks with the `use-services.ts` skip-until-resolved shape. Estimate: ~45m including the hooks' existing `__tests__` coverage.

## Unverified

- Not reproduced live. The evidence is the document and the hooks read directly; the behaviour follows from the server resolving the caller's default workspace when no `ownerId` is named (`core/base.go:651-668`).
- Whether any other dashboard feature has the same omission was not swept.
