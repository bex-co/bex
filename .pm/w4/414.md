# 414 — A per-deploy image override (`imageUrl` / hook `imgURL`) makes the service claim "Saved changes aren't live yet", and its advice reverts the deploy

Why: deploying a specific tag is the normal image-service release flow on bex (API `imageUrl`, deploy-hook `imgURL`, w8/042). Afterwards every service page says the user has unapplied saved changes, though they saved nothing. It tells them to "Use a standard deploy to apply them", and that deploy quietly swaps the running tag back to the older saved one.

**Severity:** major (the UI misstates what happened and steers the user into undoing their own release). **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run r2b9, 2026-10-24 UTC (`muse.env`, `bex-canary`, pin `297e3b070771`). Fixture: Free image web service `qa-20261024-r2b9-roll` (`srv-dbeod6bjkr2s739s7rag`, `docker.io/traefik/whoami:v1.10.1`, env `PORT=80`). It was deleted (`GET` → `404`); session revoked. Also seen in run h7d2 the same day, after a deploy-hook `imgURL` deploy.

## Probe

1. Create the service on `whoami:v1.10.1` and wait for Live. GraphQL `service(id){undeployedChanges undeployedChangesApplying imagePath}` → `false, false, "docker.io/traefik/whoami:v1.10.1"`; no banner.
2. `POST /v1/services/<id>/deploys {"imageUrl":"docker.io/traefik/whoami:v1.10.3"}` → `201`; the deploy goes `live` with `image.ref …:v1.10.3`.
3. About 15 s later the same GraphQL query returns **`undeployedChanges: true`**, `undeployedChangesApplying: false`, `imagePath …:v1.10.1`. `/services/<id>` and `/deploys` show the header status: **"Saved changes aren't live yet. Use a standard deploy to apply them."**
4. Control: a dashboard **Rollback** to the v1.10.1 deploy (dialog: "Saved settings stay unchanged and apply with the next standard deploy") went live as `trigger: rollback`, and the banner cleared because the saved and running images match again. A rollback announces the saved/running split up front; the override does not.

## Root cause

- `lego/backend/internal/deploys/service.go:795-799`: an `ImageURL` trigger keeps `Spec.Image` and selects the runtime image via `Spec.ReleaseConfig = {Generation: release, Image: p.ImageURL}`. This is the documented contract (ADR018 line 69: "only the tag or digest changes, without changing the saved image"). The deploy hook forwards `imgURL` into the same field (`deployhook.go:379`).
- `lego/operator/internal/controller/saved_configuration.go:163-168` (`servingConfigurationDiffers`): for an image service, any running container image ≠ `app.Spec.Image` sets `different = true`. That bit becomes `status.UndeployedChanges` (`:95`). The backend projects it to `AppView.UndeployedChanges` (`apps/service.go:1125`) and GraphQL `undeployedChanges`. The dashboard renders `services.undeployedChangesHint` from it (`features/services/lib/status.ts:350-359`, `service-detail-header.tsx:312`, `routes/services.$serviceId.env.tsx:55`).
- The status has one boolean and no cause, so a deliberate override and a Save-only edit render the same copy. The locale description (`features/services/locales/en.ts:301-305`) lists Save only, cancellation, rollback and restart, but not a deploy override.
- The two cases can be told apart today: a rollback's `ReleaseConfigReference` carries `SourceGeneration = target.Generation` (`deploys/rollback_config.go:65`), while an `ImageURL` override leaves it `0`.

## Fix (target behavior)

- After an `imageUrl`/`imgURL` deploy with no other saved change, the service must not claim saved changes. Show an override-specific notice that names both images, e.g. "This deploy runs `whoami:v1.10.3`, chosen for this deploy. The saved image is `whoami:v1.10.1`; a standard deploy returns to it." Add `t()` keys in en and zh.
- Operator: record why `UndeployedChanges` is set, e.g. a typed `status.undeployedChangesReason` of `saved` | `image_override` | `historical_release`. Use `image_override` when the only difference is the container image and the active `ReleaseConfig` came from a trigger override (`SourceGeneration == 0` with `Image` set) rather than a rollback. Any genuine Save-only change still wins as `saved`.
- Expose the reason on GraphQL and in the REST/MCP service views that already carry `undeployedChanges`, so all three agree. The dashboard picks its copy from it.
- Tests:
  - operator: an override-only release → `UndeployedChanges` true with reason `image_override`; override plus a Save-only env change → `saved`; rollback to an older image → `historical_release` (unchanged copy);
  - dashboard: each reason renders its own copy.

**Unverified:** whether render.com's `imageUrl` deploy updates the service's saved image URL (if it does, the parity-correct fix is to save the tag instead, and this notice disappears with it); the zh copy; whether a Blueprint sync on a service in override state reverts the tag (not probed).
