# 488 — `GET /v1/metrics/http-latency` with `quantile` above 1 answers `200` with an empty body, and a `quantile` of 0 or below is silently replaced by p95

Why: a client that asks for a percentile outside 0–1 gets either a "success" it cannot parse (`res.json()` throws on an empty `application/json` body) or the p95 it did not ask for, with nothing saying which; an invalid parameter should be a 400 that names it, as `quantile=abc` already is.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-05 ~00:40 UTC (`muse.env`, workspace `bex`; read-only GETs on the existing service `srv-dbg5uqkd3d3c73caqn80`); **minor** (API contract; no data lost; a normal dashboard request never sends these values); ~40m.
- **Probe** (in-page `fetch(..., {credentials:'include'})` against `https://api.bex.co`; every request carries `resource=srv-dbg5uqkd3d3c73caqn80&startTime=<now-1h>&endTime=<now>&resolutionSeconds=60`, `Content-Type` is `application/json` on all of them):

  | `quantile=` | Status | Body |
  | --- | --- | --- |
  | _(omitted)_ | 200 | one series, value `0.095` s (p95) |
  | `0.95` | 200 | same series, `0.095` |
  | `0.5` | 200 | `0.05` |
  | `1` | 200 | `0.1` |
  | `0.99999` | 200 | a normal series |
  | `0` | 200 | **same as omitted: `0.095`, the p95**, not the minimum |
  | `-1` | 200 | **same as omitted: `0.095`** |
  | `1.0000001` | 200 | **length 0, empty body** |
  | `2` | 200 | **length 0, empty body** |
  | `1e308` | 200 | **length 0, empty body** |
  | `abc` | 400 | `{"error":"invalid query parameter \"quantile\"","id":"bad_request",…}` |
  | `NaN`, `Inf`, `+Inf`, `-Inf` | 400 | the same message |
  | `0.95,0.5` | 400 | the same message |
  | `0.95&quantile=0.5` | 200 | two series, each labelled with its `quantile` |

  Control: `GET /v1/metrics/cpu?…&quantile=2` answers `400 unsupported query parameter "quantile" for get-cpu`, so only the latency route reaches the code below.

- **Root cause:**
  - `lego/backend/internal/metrics/rest.go:439-451` parses each `quantile` with `strconv.ParseFloat` and appends it; there is no range check. (NaN and the infinities are refused earlier, by the request validator, which is why they 400.)
  - `lego/backend/internal/metrics/service.go:198-200` treats `q.Quantile <= 0` as "not set" and substitutes `defaultQuantile = 0.95` (`service.go:73`). An explicit `0` or a negative value is therefore indistinguishable from an omitted one. `MetricsWithQuantiles` does the same for its echoed label (`service.go:608`).
  - For a value above 1 the request reaches Prometheus as `histogram_quantile(<q>, …)` (`metrics/source.go:512`), which returns `+Inf` for φ > 1. The handler then calls `core.WriteJSON(w, 200, toRenderMetrics(all))` (`rest.go:322`).
  - `core.WriteJSON` (`core/http.go:242-246`) writes the `Content-Type` header and the status first, then calls `json.NewEncoder(w).Encode(...)` and discards the error with `_ =`. `encoding/json` refuses `+Inf` ("unsupported value"), so nothing is written: status 200, JSON content type, zero bytes. The 0.99999 and 1 rows show the encoder is fine for finite values.
- **Fix (target behavior):**
  - **Range:** reject a `quantile` outside `[0, 1]` with `400` naming the parameter (`quantile must be between 0 and 1`), in the same place the other metric parameters are refused (`rest.go` parse step), so it applies to every value of a repeated `quantile`. GraphQL and MCP get the same check through the shared `MetricQuery` builder if they construct it separately (see Unverified).
  - **Explicit zero:** an explicit `quantile=0` is the minimum, not "unset"; the default applies only when the parameter is absent. That needs presence tracking (a `*float64`, or the `HasQuantile` flag `graphql.go:168` already carries) instead of the `<= 0` sentinel at `service.go:198`.
  - **Encoder failure:** `core.WriteJSON` should marshal into a buffer first and answer a JSON `500` if marshalling fails, instead of a bodiless 200. This is the general fix; the range check above is the specific one. Keep both: the range check gives the caller an actionable 400, the buffering stops the next non-finite number from reintroducing the empty body.
- **Blast radius:**
  - `core.WriteJSON` has 143 non-test call sites and `core.HandleJSON` (which calls it) 88 (`grep -rn 'core\.WriteJSON(' --include='*.go' lego/backend` and `core\.HandleJSON(`). Buffering is behavior-neutral for every successful response; the only visible change is that a response that today is a silent empty 200 becomes a 500. Run the whole backend suite, and add one test that a body containing `math.Inf(1)` yields a 500 with an error body.
  - Large list responses are now held in memory once more before writing; the biggest are the paginated list routes (bounded by `limit ≤ 100`), so the cost is small, but say so in the change.
  - The `quantile` zero/negative change affects only the latency metric (`MetricHTTPLatency`) and the per-quantile "All" overlay (`normalizeQuantiles`, `service.go:638`), which the dashboard's percentile picker uses with 0.5, 0.95 and 0.99.
- **Adjacent classes:** an unknown `resource` stays 404 and a forbidden one stays 403 (both are decided before the quantile is read); a range error is a 400 like the existing `startTime must be before endTime`; a repeated `quantile` with one bad value fails the whole request rather than dropping the bad one.
- **Unverified:**
  - GraphQL `metrics(query:{quantile})` and MCP `get_metrics` were not probed with an out-of-range value; `graphql.go:167-190` builds its quantile list separately from `rest.go`, so it may need its own check. A `+Inf` in a GraphQL float field would be a serialization error rather than an empty body, but that was not exercised.
  - Whether Render's schema bounds `quantile` to `[0, 1]`: my search of `internal/api/openapi/render-public-api-1.json` for a `quantile` parameter on `/metrics/http-latency` found none, so the bound here is the mathematical one, not a quoted Render rule.
  - The Loki-backed request-log latency path (`metrics/lokisource.go`) was not probed for the same values.
- **Render:** Render documents `quantile` as the latency percentile (0.5, 0.95, 0.99 in its dashboard); I did not verify what it returns for out-of-range values.
- **Dedupe:** `grep -rli quantile .pm` finds w4/258 (older instance's value), w4/279 (custom-range errors), w4/401 (repeated `host`/`path` filters) and w4/029 (budgets register); none covers the value range or the empty-body 200. Nothing in `.pm/DO_NOT_DO.md` applies. The fix is not on `main`.
