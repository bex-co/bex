## Objective

Make sustained webhook admission pressure visible to operators without leaking tenant identity or recreating the queue amplification through logs, metrics, or evidence rows.

## Context

t001 returns bounded aggregate overflow information and t002 prevents a noisy workspace from monopolizing claim batches. Operators still need to distinguish ordinary endpoint failure from admission pressure and know when the configured ceiling is chronically too low or a tenant is producing an abnormal event rate.

## Steps

1. Register a counter for capped deliveries and a gauge or bounded observation for queue pressure using only closed labels such as result/reason.
2. Emit rate-limited aggregate logs per worker interval; never label or log workspace ids, endpoint ids, destination URLs, or payloads.
3. Add a Prometheus alert for sustained cap pressure, with an actionable runbook description and a promtool rule test.
4. Document the ceiling knob, disable semantics, and operator response.

## Acceptance criteria

- [ ] Metric labels are statically bounded and carry no tenant or destination data.
- [ ] Repeated overflow is aggregated/rate-limited rather than logged once per delivery.
- [ ] The alert fires and clears in `promtool test rules` coverage.
- [ ] Documentation explains whether to investigate event amplification, endpoint health, or raise capacity.

## Out of scope

- Per-tenant dashboards, billing webhook deliveries, or automatic plan-based limit changes.
