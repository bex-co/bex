## Objective

Give the dashboard's GraphQL source-update path everything Render's Update Source dialog submits in one call — repo + branch + runtime + buildCommand + startCommand/command + publishPath (or image + registryCredentialId, or buildSourceId + startCommand/command) — and trigger **one** deploy immediately when requested, returning the triggered deploy ID so the dashboard can navigate to it, while REST `PATCH /v1/services/{id}` and MCP keep their save-without-deploy contract.

## Context

- `lego/backend/internal/apps/graphql.go:1760-1807`: `setRepo` (`id`, `repo`, `branch`, `buildCommand`, `startCommand`, `confirm`) and `setImage` (`id`, `image`, `registryCredentialId`, `confirm`) currently save via `ApplyServicePatch` / `SetSourceAndRegistryCredential` (`service.go:5327`, which calls `markSourcePending` + `patchUntracked`) and never trigger a deploy. `setRepo` does not accept `runtime`, `publishPath`, or cron `command`.
- `lego/backend/internal/apps/build_sources_graphql.go:228`: `linkBuildSource` (`serviceId`, `buildSourceId`, `startCommand`, `dryRun`) calls `LinkBuildSource` (`build_sources.go:1113`), which also stages without deploying.
- `lego/backend/internal/apps/settings.go:62`: `ServicePatch` already carries `Repo`, `Branch`, `Runtime`, `BuildCommand`, `StartCommand`, `Command`, `PublishPath`, `Image`, `RegistryCredentialID`, and `ApplyServicePatch` applies them atomically with two-pass preflight validation.
- `lego/backend/internal/deploys/graphql.go:232`: `triggerDeploy` delegates to `deploys.Service.TriggerDeploy`. Check how `api` wires `apps` and `deploys` together (avoiding circular imports) so the GraphQL resolver can run the atomic source patch and then trigger one deploy (returning the `Deploy` or `deployId`).
- Protected environments: `lego/backend/internal/apps/protection.go:68-80` (`protectedSourceVerb`) and `requireUnprotected`.
- Golden schema + scope/permission guards: `lego/backend/internal/api/testdata/schema.graphql`, `scope_matrix_ops.go`, `key_permission_ops.go`.

## Steps

1. Choose the cleanest backwards-compatible GraphQL contract (e.g., extending `setRepo`, `setImage`, `linkBuildSource` with `runtime`/`publishPath`/`command` and a `deploy: Boolean` flag plus a `Service` field or a dedicated payload/mutation such as `updateServiceSource` returning `{ service, deploy }`, keeping existing callers intact; check `schema_dump_test.go`, `scope_matrix_ops.go`, and `key_permission_ops.go`).
2. Wire the source patch through `ApplyServicePatch` (for Git source updates carrying `runtime`/`buildCommand`/`startCommand`/`command`/`publishPath`), `SetSourceAndRegistryCredential` (for image switches), and `LinkBuildSource` (for build sources), ensuring:
   - Validation runs before any write: a rejected runtime, command, publish path, image, or build source writes nothing and opens no deploy.
   - Static sites accept `repo` + `branch` + optional `buildCommand` + `publishPath` (and refuse `image`, `buildSourceId`, `runtime`, `startCommand`).
   - Cron jobs map the confirmed command to `spec.command` (not `spec.startCommand`), and support switching runtime (Docker vs native), image, or build source.
   - Switching between Docker and native (or Image → Git, Build Source → Git) updates runtime and commands atomically in one `ApplyServicePatch` and triggers **one** deploy (never two — verify `ApplyServicePatch` doesn't open an implicit rollout AND a second `TriggerDeploy`!).
   - Handle suspended services and build sources with no succeeded build yet cleanly (per t001's capture and bex's deploy rules: do not fail after already mutating source without a clear contract; test both cases explicitly).
   - REST `PATCH /v1/services/{id}` and MCP `update_service` / `link_service_to_build_source` remain save-without-deploy.
3. Regenerate the golden GraphQL schema (`UPDATE_SCHEMA_GOLDEN=1 go test ./internal/api -run TestGraphQLSchemaMatchesTheGolden`) and add unit tests covering all five service types, validation refusals, single-deploy guarantee, and REST/MCP non-deploy preservation.
