# Postgres Insights duplicates table rows when dotted names collide

Why: database owners must be able to trust the table sizes and scan counts shown in Insights after normal refreshes.

- **Severity:** minor; phantom observability rows and ambiguous names, with stored data and SQL results intact.
- **Estimate:** 55m: caller audit 10m, pair keys and qualified labels 15m, reorder regressions 15m, live repeat and Simplify 15m.
- **Source:** continuous functional `$qa-find-bugs w4`, pass a174, 2026-10-11 UTC; muse.env through the login helper.
- **Goal:** trustworthy managed Postgres observability under [ADR009](../../../docs/ADR009-postgresql-management.md), consistent with the existing Insights surface in [ADR018](../../../docs/ADR018-render-parity.md).

## Reproduction and target

Owned private Free PostgreSQL 18 `qa-20261011-a174-schemas`, `dpg-db5ll62ek99c73ahuqhg`, now deleted. Detail: `https://dashboard.bex.co/databases/dpg-db5ll62ek99c73ahuqhg#insights`.

1. Create the seven tables with the confirmed SQL-console DO statement below. Two distinct tables are `"qa.a174".widgets` and `qa."a174.widgets"`; these are ordinary valid quoted identifiers. The other tables include `public.shared`, `qa_a174.shared`, a space/Unicode name, and two size controls.
2. At **09:46:43.638Z**, a read-only schema-qualified UNION returns the correct five distinct marker rows. There is no wrong-schema query or data-loss finding.
3. Open Insights at **1440×1000**. At **09:46:54.100Z**, the API returns seven table-size entries; the DOM has seven rows. Both dotted tables display the identical label `qa.a174.widgets`.
4. Confirm the INSERT of 5,000 rows into `qa_a174.move_control`. It reports **5,000 rows affected** at **09:47:10.842Z**. Its size rises from **8192 bytes** to **528 kB**, moving it ahead of the original **240 kB** control.
5. Refresh Insights. The **09:47:23.287Z** response still has **seven** tables, with two distinct 72 kB dotted-name entries. The **09:47:23.804Z** DOM has **eight** rows, including **three** indistinguishable `qa.a174.widgets / 72 kB` rows. The extra row is absent from the API.
6. **Fresh-page control:** switch to **390×844**, reload, and open/refresh Insights. At **09:47:49.952Z**, the DOM correctly has seven rows matching the response; document width is 390.
7. **Fresh-page reproduction:** confirm `TRUNCATE TABLE qa_a174.move_control;` at **09:48:16.504Z**, then refresh. The **09:48:48.764Z** API still returns seven tables, with the emptied control last. The **09:48:49.194Z** DOM again has eight rows and three identical dotted-name entries. The inspected screenshot `.playwright-mcp/qa-insights-dotted-a174-mobile.png` shows all eight Storage rows.
8. At **09:49:49Z**, a separate GraphQL query and both REST forms for sizes and scans return the correct separate schema/table pairs. Storage remains eight DOM rows. Table scans has seven DOM rows in this capture, but both dotted tables have the same ambiguous visible label.

**Target:** Storage and Table scans render exactly one row per returned schema/table pair through sorting, insertion, deletion and refresh. The two names must be visibly distinct: `"qa.a174"."widgets"` versus `"qa"."a174.widgets"`. Preserve exact sizes/counts and their API order. A hard reload is not required to remove stale rows.

## Root cause, dependency and scope

- **Storage:** `dashboard/src/features/databases/components/insights-panel.tsx:98–104` uses `schema + "." + name` as both the React key (**100**) and display label (**104**).
- **Table scans:** the independent map at **275–281** repeats the same key (**277**) and label (**281**). Both distinct pairs serialize to `qa.a174.widgets`. The ambiguous labels were observed on both tables; extra-row reconciliation was reproduced on Storage.
- Actual pinned **react / react-dom 19.2.3**: `dashboard/yarn.lock:10351–10353,10518–10520`. Opened installed `node_modules/react-dom/cjs/react-dom-client.production.js`: **3319–3326** builds a Map keyed by existing sibling keys, so a duplicate overwrites the earlier fiber; **3570–3578** looks up a new child by that key; **3683–3713** removes matched keys and deletes only entries remaining in the Map. A reordered list loses track of the overwritten sibling, matching the extra retained DOM row. No console warning was emitted by the live production build.
- The producer remains correct: `lego/backend/internal/postgres/insights.go:347–354` quotes schema and table separately when computing sizes, and **357–366** selects separate scan identifiers. `graphql.go:273–296` exposes distinct string fields. `dashboard/src/features/databases/api/databases.graphql:350–380` selects both; `hooks/use-database-insights.ts:131–145` filters null rows without concatenating identities. This layer can express the full pair already.
- **Exhaustive caller search:** two matching concatenated keys, both in this component; one production InsightsPanel mount at `routes/databases.$databaseId.tsx:319`. The canonical Postgres route and its `/d/<id>` alias share the component. Web/static/cron/worker/private/key-value use separate detail surfaces.
- **Proposed fix:** use a stable pair encoding such as `JSON.stringify([schema, name])` for both map keys. Use one small local formatter that double-quotes each identifier and doubles embedded double quotes, then joins the two quoted parts with a dot. Always quote both parts, including ordinary names, so the label is unambiguous without inventing a PostgreSQL keyword list. If this formatter is shared, its initial caller count is exactly two. No API field, SQL statement, identifier validation, or backend identity change.
- Keep the existing null-row filtering, empty/error states, polling behavior, loading card bounds and responsive layout. en/zh headings remain translated; database identifiers are literal names. Authentication, missing-resource and timeout responses retain their current handling.
- Existing `components/__tests__/insights-panel.test.tsx:60–82` mocks `sizes: null` and `tableScans: []`. Its masked-query tests cannot catch either collision. Extend the fixture with the seven rows and **rerender** after reordering: assert exact row count, labels, size/scan association and order. Include insert/delete transitions, same table name in separate ordinary schemas, spaces/Unicode and embedded quotes. Keep the existing query/masking tests. A static render or assertion about the key string alone is insufficient.
