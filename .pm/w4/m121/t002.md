## Objective

A caller can set a port but cannot read it back. `GET /v1/services/{id}` returns no `port` key, GraphQL answers `Cannot query field "port" on type "Service".`, and the only way to learn the value is to parse the `<slug>:<port>` suffix off `serviceDetails.internalAddress`. Expose the port as a first-class read on all three API surfaces so a client can round-trip the value it just wrote.

## Context

- Live probe, 2026-09-21: `GET /v1/services/srv-daodndjs0ils73bgpcng` → `serviceDetails` held `"internalAddress":"qa-20260921-port:8080"` and no `port`.
- Live probe, same run: `{ createService(… port: 8080){ id name port } }` → `{"data":null,"errors":[{"message":"Cannot query field \"port\" on type \"Service\"."}]}`; dropping `port` from the selection set succeeded.
- `lego/backend/internal/apps/service.go:2067` — `Port: a.Spec.Port` already flows the value into an internal view, so the plumbing exists up to the boundary.
- Render's service read has no `port` field (it detects the bound port instead), so this is a bex **extension** on the parity ledger, not a parity fix — t006 records it as such.

## Steps

1. Add the port to the REST service view under `serviceDetails`, beside `internalAddress` whose suffix it already explains.
2. Add `port` to the GraphQL `Service` type, sourced from the same view field — not recomputed.
3. Add it to the MCP service read tool's output.
4. Assert the three agree with each other **and** with the `internalAddress` suffix, so the two representations of the same number cannot drift.

- [ ] The MCP service read returns the same number.
