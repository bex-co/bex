# Cron Recent Runs never adds scheduled executions while the Events page stays open

Why: a user watching a scheduled job sees its old run history indefinitely even after new executions have succeeded and the API reports them, so the dashboard cannot reliably show whether the schedule is running without a page reload.

**Severity:** major. **Estimate:** 60m, confined to cron-list freshness and its existing pagination. **Source:** continuous `$qa-find-bugs`, new loop pass 3, 2026-09-21 America/Los_Angeles / 2026-09-22 UTC, filed in w4 at the user's request. **Goal:** ADR008 hosting observability and [ADR038](../../docs/ADR038-cron-jobs.md)'s first-class cron history remain useful while the operator creates runs independently of a dashboard mutation.

## Root, scope, and measured cache behavior

- `dashboard/src/features/services/hooks/use-cron-runs.ts:45–50` requests `CronJobRunsDocument` with `{serviceId, limit: 5}` and `cache-and-network`, but configures no polling, subscription, or arrival invalidation. Manual Trigger calls `refetch()` at `123–130`; scheduled runs do not execute that callback.
- `features/services/components/service-detail-layout.tsx:43` owns the `useServer` poll. `hooks/use-server.ts:49–71` uses `useConvergingPoll` and `skipPollWhenHidden`; `common/lib/polling.ts:11,18` supplies 30s settled / 3s converging cadence. The Events page's secondary `useServer(serviceId, {poll:false})` at `routes/services.$serviceId.events.tsx:91` correctly avoids a duplicate timer for that same document.
- `features/services/api/server.graphql:112–118` includes `Service.runs`; `api/cron-runs.graphql:3–10` reads the separate root `cronJobRuns` list. Both contain the same GraphQL `CronRun` type (`lego/backend/internal/apps/graphql.go:570`). Apollo can update already-referenced run entities through the Server poll, but that does not insert new references into the root history array.
- **Actual installed Apollo 4.1.3 was exercised in memory**, using the repository's cache-policy shape. Seed the history array `[r2 pending, r1 successful]`, then write a Server result containing `[r3 successful, r2 successful, r1 successful]`: reading the history still returns only `[r2 successful, r1 successful]`, while `CronRun:r3` exists in the normalized cache. This distinguishes entity freshness from array membership; no library-version assumption or mock-only claim is needed. No files or live resources were mutated by this local proof.
- The installed implementation confirms the result: `dashboard/node_modules/@apollo/client/cache/inmemory/helpers.js:4–20` identifies entities by typename/id; `policies.js:410–451` keys fields by their own name/arguments; `writeToStore.js:171–222,235–295,308–315` writes the selected field and its array references. `common/apollo/cache.ts:6–11` has no `CronRun` or `Query.cronJobRuns` policy linking the two lists. `ObservableQuery.js:844–861` does not establish polling without a poll interval.
- **Exact production consumers:** one `useCronRuns` call, in `components/cron-runs-section.tsx:95`; one `<CronRunsSection>`, in `routes/services.$serviceId.events.tsx:336`, gated to cron services. The `/cron/*`, `/web/*`, `/worker/*`, and `/pserv/*` splat routes all use `common/lib/render-alias.ts` to reach `/services`, preserving the subpath, query, and hash; these segments intentionally accept any service id. A cron id under `/static/<id>/events` is also canonicalized to `/services/<id>/events` by `service-detail-loader.ts:99–100`. These are code-confirmed aliases, not separate live reproductions. The actual resource-type gate excludes web, private, worker, and static services; Postgres and Key Value use separate detail families and are outside this hook's scope. The single expanded-row detail hook at `hooks/use-cron-run.ts:26–31` already polls a selected id; it cannot discover an unknown new id. No global Apollo, backend, or operator change is required.

## Fix the list and preserve its existing paging

Refresh cron history itself at the shared visible-tab cadence, including a settled history that currently contains no active run. The absence of an active row cannot suppress the baseline discovery tick. Reuse the existing polling/visibility helpers; retain last good data on a transient failed refresh and avoid replacing loaded rows with a skeleton during background work. Preserve the existing unauthenticated, forbidden, and not-found handling and authorization checks: do not reinterpret those responses as an empty successful history, expose another service's cached rows, or create an existence oracle.

**Adding `pollInterval` alone is insufficient.** `use-cron-runs.ts:77–96` currently concatenates fetched older pages into the first-page result via `fetchMore.updateQuery`; `loadedMore` / `hasMore` at `41–43,66–75` retain separate pagination state. Apollo 4.1.3's `ObservableQuery.js:467–479` writes that merged list under the original variables. A second in-memory proof seeded ten rows in that entry, then wrote a fresh five-row first page: only five remained. After a previously exhausted page, `loadedMore=true` can leave `hasMore=false`, dropping older rows and their recovery affordance. This is a required regression check for the proposed polling fix, not a separately live-observed defect.

Keep the change local. One option is an authoritative growing head window: request five initially, increase the requested limit when loading older rows, and poll the current expanded window instead of concatenating into a fixed-five-row cache entry. The API already supports that limit; `apps/service.go:3132–3141` pages the bounded status history, capped at ten in `operator/internal/controller/app_controller.go:3494,3754–3790`. Alternatively, use the established `features/deploys/hooks/use-deploys.ts` separation of a refreshed head and loaded tail with explicit id dedupe/reconciliation. Whichever approach is chosen, routine refreshes must preserve loaded older rows that remain in the API's retained history, unique ids, order, a usable Load more state, and service-id isolation. Do not accumulate records beyond the authoritative retained history indefinitely.

Extend `hooks/__tests__/use-cron-runs.test.ts` beyond its current mocked trigger/refetch checks, using real Apollo cache/network behavior and controlled time where needed. Cover a new scheduled arrival while the component remains mounted, existing pending-to-terminal updates, hidden-tab skipping, failed refresh retaining rows, service navigation discarding stale completions, and six or more rows through Load more plus subsequent arrival/refresh. Preserve manual trigger, cancellation, expanded detail, and the existing error/empty/loading states. Run affected dashboard tests and required type/lint checks, then repeat both live observations after deployment without reloading until the new rows appear. No API shape or backend contract change is proposed.
