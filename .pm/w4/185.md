# w4/185 — Insights/SQL console show the probe's own session rails as observed parameter values

Why: a user who overrides `statement_timeout` sees the dashboard insist the live
value is `10000 ms` from source `client` forever, which reads as "your override
didn't apply" when the mechanism itself works fine.

## Repro (Free Postgres, 2026-10-04)

1. Insights → Parameter overrides → declare `statement_timeout = 30s`, save.
2. Wait 4+ minutes for reconcile. The row's Observed setting stays
   `10000 ms`, and Non-default parameters lists
   `statement_timeout 10000 ms client`.
3. SQL console: `SELECT setting, source FROM pg_settings WHERE
   name='statement_timeout'` → `10000, client`.
4. Control: declaring `log_min_duration_statement = 2500` appears as
   `2500 ms, configuration file` within ~2 minutes — the override projection
   mechanism works; only the observation of `statement_timeout` is wrong.

## Mechanism

`lego/backend/internal/postgres/query.go:336` (`buildQueryConnConfig`) pins
`statement_timeout` as a pgx `RuntimeParams` startup parameter on every
console/insights connection, so `pg_settings.source` is `client` in every probe
session. Any read of that parameter through this path returns the probe's own
10s rail, never the global value. Same class: `:333-335` pins
`default_transaction_read_only=on`, which likewise shows up in the Non-default
parameters table as `on, client` — the probe measuring itself.

## Fix sketch (pick one)

- Probe parameter reads over a connection without the rails (context deadline
  already bounds the round-trip at `:349`), or
- exclude `client`-sourced rows that match the probe's own rails from the
  Non-default table / Observed column (or annotate them as "probe session").
