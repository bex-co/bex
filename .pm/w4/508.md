# 508 — Regression of w4/m230: a user Resume can be recorded as `service_woken` (an idle wake) instead of `service_resumed`

Why: Events then tells the owner their service woke from free-tier sleep when they resumed it themselves. `service_woken` is deliberately never pushed (`notifications/push_worker.go:753-759`), so the "Service resumed" notification Render sends is likely lost too. w4/m230's DoD promised this exact control.

  2. Settings → Suspend → confirm. REST read `suspended: suspended`, `suspenders: ["user"]`, `/instances` `[]`; GraphQL `phase: Hibernated`. The URL answered 503 "This service is suspended."

  5. Control (m230's own live check, `.pm/w4/done/m230/README.md:63`): the same suspend → resume once recorded `service_resumed`. That resume came 33 s after `service_suspended`; this one came about 47 s after.
- **Root cause:** `lego/backend/internal/store/event_facts.go:546-551` `checkpointServiceSuspended`.
  - The checkpoint keeps `previousSuspended` only when `checkpointServicePhase` holds a transient phase (`:497-502`).
  - A Resume clears `spec.suspended` while the observed phase is still `Hibernated`. A reconcile pass at that moment sees Hibernated → Hibernated (no hold) and writes `suspended=false`. That write is guarded by the change tuple at `:452-458`, which the comment at `:446-449` added for the opposite direction.
  - The next pass sees Hibernated → Running with `previousSuspended=false`, and `observedStateFacts` (`:605-611`) emits `service_woken`.
  - It is a timing race: whether a pass lands between the flag flip and the phase change. That explains why m230's control passed.
- **Fix:**
  - Target: while the checkpoint phase stays `Hibernated`, the recorded suspend reason may go false → true (suspending an already-hibernated App) but never true → false. The reason it went down is fixed until it comes back up.
  - So Hibernated → Running after a user suspend always records `service_resumed`, and an idle sleep still records `service_woken`.
  - Implement it in `checkpointServiceSuspended`. Add store tests for both orderings: a pass with Hibernated + suspended=false between Resume and Running, and none.
- **Blast radius:**
  - One caller (`event_facts.go:431`).
  - Consumers of the resumed/woken split: the Events feed (REST/GraphQL/MCP), webhooks (`webhooks/service.go:229-231`), and push notifications (`push_worker.go:751-759`).
  - Add regression tests that an idle sleep/wake still records `service_hibernated`/`service_woken`, and that a suspend of an already-hibernated App still records `service_suspended` (the `:446-449` case).
