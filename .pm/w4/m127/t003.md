## Objective

Carry out whichever answer t001 gave for the SQL console — guard it, or document the limit where a user meets it.

## Context

- Live on a protected database, all accepted with no confirmation: `CREATE TABLE qa_probe(x int)`, `INSERT INTO qa_probe VALUES (1)`, `DROP TABLE qa_probe`.
- The verb is `executeDatabaseQuery(id, sql, allowWrites)` on GraphQL — **no `confirm` argument** — plus the REST console route and the MCP tool.
- `ExecuteQuery` (`postgres/query.go:124`) already authorizes hard: `can_create` **and** `can_view_sensitive`, both re-asserted uncached in `executeAuthorizedQuery` (`:161-180`). Do not weaken or duplicate any of that; the guard is an addition, not a replacement.
- The read-only path (`Query`, and `allowWrites: false`) must stay untouched — protection is about changing things, and the ADR's own principle excludes verbs that only observe or restore.
- If the answer is "guard it": the phrase should name the operation the user is really performing, and the dashboard console already has a confirmation step to hang it on, so the UI change is to source the phrase from the server error instead of confirming locally.
- If the answer is "document it": the console is the place, not just the ADR — a user typing `DROP TABLE` against a protected database should be able to see that protection does not cover this.

## Steps

1. Implement t001's answer for `allowWrites: true` only.
2. If guarding: add the guard in `ExecuteQuery` after the existing authorization, add `confirm` to GraphQL/REST/MCP, and make the dashboard console retry with the server-issued phrase rather than its own dialog text.
3. If documenting: put the statement in the console UI and the protection toggle copy, and cite it from ADR032.
4. Either way, leave `Query` and the read-only console path unchanged.

## Files

- `lego/backend/internal/postgres/query.go`, and the GraphQL/REST/MCP adapters
- `dashboard/src/features/databases/` (console + protection copy)

## Acceptance criteria

- [ ] `DROP TABLE` through the console on a protected database behaves per t001's written rule, and the rule is discoverable by a user.
- [ ] Read-only queries are unaffected.
- [ ] The existing dual-relation authorization and its uncached sink re-assertion are intact.

## Out of scope

- Anything about direct connection-string access, which bypasses the API entirely — t001 records whether that makes the guard advisory.
