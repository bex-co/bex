# 548 — Settings change confirmations promise that the current version keeps serving, even for a service that has never gone live

Why: the confirmation is the one moment a customer reads what a change will do. Telling someone whose site has never been published that "your site keeps serving its current published version" describes a safety net that doesn't exist.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, rounds 16 and 19, 2026-11-10 UTC (`muse.env`, workspace `bex-canary`, pin `c12cd57facb1`). **Minor** (copy honesty at a confirm). ~30m.
- **Fixtures** (both deleted, GET 404, URL 404; after the fix in each probe below, each went live and served 200):
  - Round 19: static site `qa-20261110-st19` (`srv-dbphbak5ngvc73e8tp90`, `examples/static-site`).
  - Round 16: web service `qa-20261110-badstart` (`srv-dbpg8hc5ngvc73e8tnk0`).
- **Probes:**
  - **Static site, never published (round 19).**
    - The first build, `echo qa-build-start && exit 3`, ended `build_failed`. The URL answered `503` with `x-render-routing: no-server` ("service unavailable").
    - Settings → Edit build command → Save opened `alertdialog "Change build command to echo qa-build-ok?"`. It read: "This starts a rebuild with the new build command. Your site keeps serving its current published version until the new build publishes successfully."
    - There was no published version.
  - **Web service, never live (round 16).**
    - The first deploy ended `update_failed`; the service never went live, and the URL answered 503.
    - Edit Start Command → Save read: "The service redeploys with the new command. In-flight requests finish before old instances are replaced."
    - There were no old instances.
- **Root cause:** the confirm bodies are fixed strings that assume a live deploy.
  - Probed:
    - `services.buildCommandConfirmBodyStatic` (`features/services/locales/en.ts:2542-2544`, chosen at `build-deploy-section.tsx:245-249`).
    - `services.startCommandConfirmBody` (`en.ts:2486-2488`, `deploy-card.tsx:162`).
  - Same assumption, read from source:
    - `services.buildCommandConfirmBody` (`en.ts:2539`, `build-deploy-section.tsx:248`).
    - `services.buildDeployConfirmBody`, the root-directory change (`en.ts:2331`, `build-deploy-section.tsx:219`).
    - `services.planPickerConfirmBody`, the resize (`en.ts:1555`, `instance-type-picker.tsx:195-196`).
- **Precedent and control:** [w4/334](done/334.md) made the cancel-deploy confirm truthful in both cases. `services.eventsCancelConfirmBody` (`en.ts:4805-4810`) reads: "If an earlier deploy succeeded, it stays live; otherwise nothing will be serving."
- **Fix (target behavior):**
  - When the service has no live deploy, each of these confirms says the change takes effect with the new deploy or build, and that nothing is serving until it succeeds. Static example: "Your site isn't published yet — it goes live when this build succeeds."
  - With a live deploy, today's copy stays.
  - Use the service's existing live-deploy state from the header or deploys data; the task picks the field. Don't infer it from a failed latest deploy alone: a failed redeploy over a live one keeps the live one serving.
  - en and zh copy. Test both branches at each of the five call sites.
- **Blast radius:** 5 locale keys across 3 components: `build-deploy-section.tsx`, `deploy-card.tsx` and `instance-type-picker.tsx`.
- **Unverified:**
  - The root-directory, web build-command and resize confirms were read from source, not opened on a never-live service.
  - What Render says in the same dialogs.
- **Dedupe:**
  - [w4/246](done/246.md) (done) introduced the static-site copy, and w1/m148 the "pods roll" copy. Neither considered a service that was never published.
  - w4/334 fixed only cancel.
  - `grep -rlE "In-flight requests finish|current published version|old instances are replaced" .pm` finds nothing open.
  - Not deploy lag: `git log c12cd57facb1..origin/main` on these files is empty.
- **DoD (live):**
  - On an owned static site whose first build failed, Edit build command → Save shows the not-yet-published wording, in en and zh. The site goes live after the build succeeds.
  - On an owned web service whose first deploy failed, Edit Start Command → Save shows the not-yet-live wording.
  - On a live service, both dialogs still show today's copy.
