# 234 — Renaming a file and replacing its old filename cannot be saved in one draft

Why: users should be able to move an existing opaque file and put new contents at its vacated name with the staged editor's single Save.

- **Severity:** major. A valid final draft is refused twice; splitting it into a rename save followed by an upload save works. The UI honestly reports failure and retains the draft; no stored change, lost contents, or rollout was observed on either failed save.
- **Estimate:** 55m: bounded operation-bookkeeping fix 15m, shared callers/alias review 15m, meaningful behavioral vectors 20m, live replay and cleanup 5m. Keep as a sub-hour inbox fix.
- **Source:** user-requested functional qa-find-bugs loop, 2026-10-10 UTC pass a49, muse profile, workspace `tea-d98210cbbpdc73dcrkvg`; research HEAD `0f8ce1de9`. Filing only.
- **Goal linkage:** [ADR006 coherent environment saves](../../docs/ADR006-bex-api.md), [ADR013 stored environment maps](../../docs/ADR013-secrets.md), [ADR018 parity](../../docs/ADR018-render-parity.md) and the staged configuration workflow introduced by [w5/m44](../w5/done/m44/README.md) and [w2/m73](../w2/done/m73/README.md). This corrects ordinary multi-file editing with no new product capability.

## Live reproduction and controls

Owned workspace-scoped group **qa-20261010-loop-a49-group**, `evg-db51i7kb8ulc73efu41g`, had no variables, no Environment assignment and no linked services.

1. Create it through **New Environment Group** with `qa-a49-original.txt` containing `qa-a49 initial file\nopaque original snow 雪\n`. Fresh-load its detail page.
2. **Edit**, rename that existing file to `qa-a49-renamed.txt`, and leave its contents masked. Upload three small UTF-8 files: a replacement named `qa-a49-original.txt`, an empty `qa-a49-empty.txt`, and `qa-a49-unicode.txt`. The replacement contains CRLF lines; the Unicode file has 雪, café, an emoji and no final newline.
3. The final draft has **four distinct valid filenames**, **0 variable operations · 4 file operations**, and an enabled Save. Choose **Environment save options → Save only**.
4. At **10:54:58.643Z**, the HTTP 200 GraphQL response contains `bad request: duplicate secret file operation for "qa-a49-original.txt"`, with `patchEnvGroupEnvironment:null`. The UI says **Couldn't save the environment. Your draft is still here.**
5. Cancel, fresh-load, restage the same draft, and Save only. At **10:56:05.394Z** the complete request and error repeat. Independent REST reads immediately before/after the second failure have identical revision `egr1_AAAAAAAAAAE`, original filename, timestamps and empty links.
6. Strong controls: Cancel of the same four-operation draft leaves metadata unchanged. Remove the three uploaded rows from the failed draft and save **only the opaque rename**: succeeds at **10:56:32.150Z**, revision 2. Without revealing the original before that save, upload those three files in a separate draft: succeeds, then fresh independent reads confirm every exact byte, including preserved original contents under the renamed filename.
7. Repeat the upload-only control with a complete retained response: delete only those three newly uploaded files, Save only, then upload them again and Save only. At **11:04:31.432Z** it succeeds from revision 4 to 5. Fresh-load and read all four files: renamed original, new replacement, empty string and Unicode/no-final-newline text are exact. No affected/failed service IDs and `rolledOut:false`.

The first upload-control mutation body was retained in network index 6275, but its response-body capture was unavailable after an early reload interrupted the harness. It is **not** used as a complete transaction receipt. The fully captured replay below independently establishes that control. The early-reload confirmation dialog was a harness timing event, not a separate bug finding.

## Root cause, consumer and target fix

`lego/backend/internal/core/environmentpatch.go:104–125` converts each secret-file write to a neutral map operation. In `applyMapPatch:181–186`, the **same seen map** rejects duplicate destination names. In `applyRenameOp:153–165`, that map also tracks rename sources: moving original→renamed marks **original** seen and removes it from the working map. The next direct upsert of original therefore fails as a duplicate even though the name is now vacant. The actual request order matches this mechanism exactly; the two extra uploads are not reached on the failed batch.
