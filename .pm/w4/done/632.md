# 632 — Blueprint validation points a YAML syntax error at the wrong line, usually one line early, and always at column 1: yaml.v3 reports a 0-based line for parser errors, and bex passes it on as Render's 1-indexed `line`

Why: Render's Validate Blueprint says `line` is "the line number in the YAML file (1-indexed)". The dashboard prints it as "line N, column M" beside the problem. A user who mistyped one bracket is sent to the line above it, and the column says nothing.

w4/397 noticed "the line imprecision" and left it as "yaml.v3's own report, not bex's". The number is yaml.v3's, but it is in a different unit: for parser errors it is 0-based. Translating it into Render's 1-indexed contract is bex's job.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 284, 2026-11-13 10:52–11:00 UTC (`muse.env`, workspace `bex-canary`; pin `5de3d5bcce8e`). **Minor** (a misleading position; the message itself is right). ~1h. No resource was created: Validate is read-only.
- **Probe:** each file was posted as Render's multipart form:

  ```
  curl -F ownerId=tea-daif693dqjvc73e7as3g -F file=@<file> https://api.bex.co/v1/blueprints/validate
  ```

  The control is PyYAML's own marks for the same files, shown as 1-based (line, column).

  | file (`printf` source) | bex `line`/`column` | real position (PyYAML context / problem) |
  | --- | --- | --- |
  | `services:\n  - type: web\n    name: [unclosed\n    runtime: image\n` | 2 / 1 | `[` at (3, 11); problem at (4, 12) |
  | `a: 1\nb: 2\nc: 3\nd: [1, 2\ne: 5\n` | 3 / 1 | `[` at (4, 4); problem at (5, 2) |
  | `services:\n  - type: web\n    name: ok\n   runtime: image\n` (mis-indented line 4) | 1 / 1 | context (2, 3); problem at (4, 4) |
  | `services:\n  - type: web\n\tname: tab\n` (tab on line 3) | 2 / 1 | problem at (3, 1) |
  | `services:\n  - type: web\n    name: "unterminated\n    runtime: image\n` | 3 / 1 | quote at (3, 11); problem at (5, 1) |

  Only the unterminated quote, a scanner error, lands on the right line. Every message is right, for example "Blueprint is not valid YAML: did not find expected ',' or ']'".

- **Root cause:**
  - `yamlSyntaxLocation` (`lego/backend/internal/apps/blueprint_compiler.go:983-999`) reads the `line N` out of yaml.v3's error string and returns `(N, 1)`. Its caller is `parseBlueprintSource` (`:844-847`).
  - yaml.v3 v3.0.1 (`gopkg.in/yaml.v3`, pinned in `lego/backend/go.mod:30`) builds that `N` in `(*parser).fail` (`decode.go:112-137` in the module cache):
    - when `context_mark.line != 0` it uses `context_mark.line`, otherwise `problem_mark.line`;
    - both marks are **0-based**, and it adds 1 only when `parser.error == yaml_SCANNER_ERROR`;
    - so a parser error ("did not find expected …") reports the line before the construct it means;
    - the marks' columns are never in the string, which is why bex's column is always 1.
  - The fix is therefore a bex translation, not an upstream bug to wait for.
- **Fix (target behavior):** a YAML syntax error's `line` and `column` are the 1-based position of the construct the message names. Use the opening `[`, `{` or quote when there is one, else the offending token, as PyYAML's marks show in the table.
  - **Expected values:**
    - row 1 → 3 / 11;
    - row 2 → 4 / 4;
    - row 3 → 2 / 3 (the mapping the bad line breaks) or 4 / 4. Pick one and document it;
    - row 4 → 3 / 1;
    - row 5 → 3 / 11.
  - **Options:**
    - Locate the error with a position-aware pass only when yaml.v3 fails, for example a scanner walk over the bytes, or `github.com/goccy/go-yaml`'s error positions. The decode stays on yaml.v3.
    - Or correct yaml.v3's number by error class (parser +1, scanner as is). That still lacks a column, and it means keeping a list of yaml.v3's scanner and parser messages in step with the pinned version.
  - **Surfaces:** `CompileBlueprintSource` serves REST validate, preview and apply, GraphQL `validateBlueprint`/`blueprintPreview`, MCP `validate_bex_yml`/`preview_blueprint` (ADR018's Blueprint validation diagnostics, w4/m102), and the dashboard's `blueprint-error-list.tsx`, which prints "line N, column M". So one change fixes all of them.
