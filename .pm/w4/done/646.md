# 646 — The zh dashboard names one product term several ways: Secret Files is 密钥文件 or 机密文件, a workspace plan 套餐, 计划 or 方案 (both on the Billing page), Env Groups 环境组 or 环境变量组, Unlink 取消关联 or 取消链接

Why: a Chinese-speaking user reads two different terms for the same thing. The Environment page, the new-service form and the env-group pages each mix them. The service's Environment page describes itself as managing "环境变量、机密文件和已关联的环境组", then heads the section "密钥文件" with the button "添加密钥文件". The new-service form says "添加机密文件". 密钥 also means a cryptographic key, so "密钥文件" reads as a key file, not an arbitrary secret file such as `.npmrc`, `.env` or a certificate.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 347, 2026-11-14 09:36–09:45 UTC (`muse.env`, workspace `bex-canary`, `?lang=zh` with the `i18nextLng=zh` cookie; pin `706a389d5924`). **Minor** (i18n consistency; nothing is lost). ~20m for Secret Files; ~50m with the round 348 extension below.
- **Fixture:** Free busybox web service `qa-20261114-r347-zh` (`srv-dbs2nifnl79c738fm030`), deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe (dashboard, zh):**
  - `/services/<id>/env?lang=zh` → Edit → Add variable. The page text reads, in order:
    - "环境变量、机密文件和已关联的环境组。";
    - the heading "密钥文件" and "添加密钥文件";
    - "暂无密钥文件".
  - `/services/new?lang=zh` → 已有镜像: the button is "添加机密文件".
  - In the same run, the zh copy was otherwise consistent:
    - the duplicate-name create showed "该名称已被使用";
    - an invalid key showed the translated naming rule;
    - the zh sweep of 16 hosting pages (round 344) found no untranslated English in `main`.
- **Where (one English term, two Chinese ones):**
  - `en` "Secret Files" is `services.secretFilesTitle` → zh "密钥文件" (`dashboard/src/features/services/locales/zh.ts:879`). It is also `services.createFieldSecretFilesTitle` → zh "机密文件" (`:4024`).
  - The 6 "机密文件" messages, all in `services/locales/zh.ts`: `createFieldSecretFilesTitle` (`:4024`), `createFieldSecretFilesAdd` (`:4032`), `environmentPageDescription` (`:5344`), `secretFileDuplicateName` (`:5609`), `secretFileDelete` (`:5666`) and `secretFileDeleteOne` (`:5670`).
  - The 20 "密钥文件" messages are in `services/locales/zh.ts` (e.g. `:879`, `:895`, `:900`, `:908`) and `env-groups/locales/zh.ts` (e.g. `:13`, `:25`).
  - Count: `grep -rho '机密文件' dashboard/src --include='zh.ts' | wc -l` → 6, and `grep -rho '密钥文件' dashboard/src --include='zh.ts' | wc -l` → 20.
- **Fix (target behavior):** every zh message for "secret file(s)" uses **机密文件**. It means "confidential file", which is what the feature holds; 密钥 means a cryptographic key.
  - Rewrite the 20 密钥文件 messages: services (Environment page, secret-file dialogs, the not-available state) and env groups (`pageDescription`, `createDescription` and the group page).
  - Add a guard beside w4/573's 您 rule in `dashboard/src/i18n/__tests__/locale-parity.test.ts:201-205`: no zh message contains 密钥文件.
  - Keep 密钥 where the English is a key or a generated secret value. The scope here is the file feature only.
- **Blast radius:** zh copy only, in two locale files. Every en message and key is unchanged. The dashboard tests that assert zh strings need their expectations updated: `grep -rln '密钥文件' dashboard/src --include='*.test.*'`.
- **Unverified:**

  - Not deploy lag: both strings are on `origin/main` today.
- **DoD (live):**
  - `/services/<id>/env?lang=zh`, `/services/new?lang=zh` (已有镜像) and `/env-groups?lang=zh` show 机密文件 in every secret-file heading, button, description and empty state, and 密钥文件 nowhere.
