# 498 — A cron job's Settings has no Source card, so an image cron's image can never be changed (or even seen) in the dashboard

Why: a customer who deploys a cron job from a prebuilt image has no dashboard path to move it to a new image, switch it to Git, or link a build source. The only options are the API or deleting and recreating the job, which loses its run history.

**Severity:** major · **Estimate:** 50m · **Worker:** worker4 · **Status:** todo

- **Source:** live `/qa-find-bugs w4`, production, 2026-11-05 17:10–17:16 UTC, round 86. Workspace `bex-canary`. Prod pin `cc3c51e12952`; research on main `0ceb5ff2b`.
- **Repro:**
  1. `POST /v1/services` creates `{type:"cron_job", name:"qa-20261105-cron86", ownerId:"tea-daif693dqjvc73e7as3g", image:{imagePath:"docker.io/library/busybox:1.36"}, serviceDetails:{schedule:"*/30 * * * *", plan:"starter", runtime:"image", envSpecificDetails:{dockerCommand:"sh -c \"echo qa86-hello; date\""}}}`. It returned 201 `srv-dbmbgtv2j1is73dev0fg`; the deploy went Live in 6s.

  4. Control: `PATCH /v1/services/srv-dbmbgtv2j1is73dev0fg {"image":{"imagePath":"docker.io/library/busybox:1.37"}}` returned 200, and `GET` returned `imagePath=docker.io/library/busybox:1.37`. After a reload, the Settings page had **0** occurrences of `busybox`. The backend supports the change; only the dashboard lacks it.
- **Root cause:** `dashboard/src/features/services/lib/settings-sections.ts:67-72`.
  - The `cron` branch pushes only `deploy` (plus `runtime`/`build` when `repo` is set).
  - `source` is pushed only in the non-cron branch (`:74`).
  - An image cron (`repo` empty) therefore gets neither the unified `ServiceSourceCard` nor the legacy inline Source/Branch rows, which `BuildDeploySection` renders only inside Build (`build-deploy-section.tsx:221`, mounted with `showSourceFields={cron}` at `routes/services.$serviceId.settings.tsx:267`).
  - A git cron keeps only those legacy repo/branch rows. It cannot switch to Existing Image or link a build source, although w2/m262 made linked crons work.
  - The route already passes `cron ? service.command : service.startCommand` into `ServiceSourceCard` (`settings.tsx:228`), a branch that is unreachable today. The gating dates from w5/m124 (`5c6a40e9e`), which kept the pre-m124 `!cron` source condition.
- **Fix:**
  - Target: every non-static type, cron included, mounts the same Source card. Its Image tab saves through `setImage`, the Git tabs through `setRepo`, and the Build source tab through `linkBuildSource`.
  - In `serviceSettingsSections`, push `source` for `cron_job` too, ordered General → Source → Deploy, as for other services.
  - Mount Build with `showSourceFields={false}` for a git cron so source edits have one home, and delete `LegacySourceFields` if it has no other caller.
  - `route-skeletons.tsx:2206` already derives its regions from the same list, so the pending skeleton follows. Verify it side by side at 1440px and 390px.
  - No REST/GraphQL/MCP change: the REST `PATCH` was probed, and GraphQL `setImage`/`setRepo` and MCP `update_service` reach the same setter (w4/m202 census).
- **Blast radius:** `serviceSettingsSections` has 2 callers: `routes/services.$serviceId.settings.tsx:101` and `common/components/route-skeletons.tsx:2206`. The `/cron/*` alias reaches the same Settings route. Update `settings-sections` unit tests for image cron and git cron, and add regression cases asserting web/private/worker/static section lists are unchanged.
- **Unverified:**

  - render.com's live cron Settings UI was not opened this run. Render documents prebuilt-image cron jobs and an editable image for image-backed services.
- **Render:** a Render cron job can run a prebuilt image ([render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image)), and the image is changed from the service's Settings, as for other image-backed services.
