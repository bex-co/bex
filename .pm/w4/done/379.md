# 379 — A restart is recorded as a "Manual Deploy" and never emits `server_restarted`

Why: restarting a service shows up everywhere as an ordinary manual deploy. The "Server Restarted" event offered in the Events filter and the webhook picker therefore never fires in production. A webhook subscribed only to restarts gets nothing, and the activity history cannot tell a restart from a deploy. The w3/m19 contract promised `server_restarted` with the triggering user and "no dead choices".

**Severity:** major (the history misleads and a subscribable event is dead). **Estimate:** ~50m. **Source:** live `/qa-find-bugs w4` loop run f6a4, 2026-10-20 UTC, `muse.env`, workspace `bex-canary`. The fixtures (Free image service `qa-20261020-f6a4-hook` `srv-dbbhm7ecbnls73997dl0` as its own webhook receiver, webhook `whk-dbbhmfecbnls73997dn0`, project `prj-dbbhl3hq56vc73bn8c20`) were deleted in-run; the session was revoked.

## Probes (production, session-authenticated from the dashboard page)

1. Webhook `qa-20261020-f6a4-wh` → `https://qa-20261020-f6a4-hook.onbex.co/hook-f6a4`, events `deploy_started`, `deploy_ended`, `server_restarted` (created in the dashboard). Its target is the same service, so each delivery is visible in the webhook's own delivery history (`responseBody` echoes the request).
2. `POST /v1/services/srv-dbbhm7ecbnls73997dl0/restart` at 07:42:33Z → `200`.
3. After 60 s, `GET /v1/webhooks/whk-dbbhmfecbnls73997dn0/events`:

   ```
   [["deploy_ended",200,"2026-10-20T07:42:49Z"],["deploy_started",200,"2026-10-20T07:42:37Z"]]
   ```

   No `server_restarted`. Both deliveries reached the receiver (`POST /hook-f6a4`, `Webhook-Signature` present, payload `{"type":"deploy_ended",…,"status":"succeeded"}`).

4. `GET /v1/services/srv-dbbhm7ecbnls73997dl0/events` → `deploy_ended 07:42:46Z`, `deploy_started 07:42:33Z`, and the first deploy's pair. No `server_restarted`.
5. The restart's deploy row, on every surface:
   - REST: `{"id":"dep-dbbhmqecbnls73997do0","status":"live","trigger":"api","bexTrigger":"api"}`.
   - GraphQL `deploys{trigger}` → `"api"`.
   - Deploys tab row: `Live … Manual Deploy`.
   - Events tab: `Deploy started · Manual deploy · by puncsky@gmail.com`.
6. The Events tab's **Filter events** list offers **Server restarted** (Service Status group). The webhook create page offers **Server Restarted**.

## Root cause

- `deploys.Service.Restart` (`lego/backend/internal/deploys/service.go:563-592`) takes one of two paths:
  - it reuses the retained running release through `restartSelectedRelease` (`deploys/rollback_config.go:150`), whose row comes from `CreateRestartDeploy` (`rollback_config.go:141` → `lego/backend/internal/store/store.go:2082-2083`), hard-wired to `TriggerAPI`;
  - or it falls through to `triggerFetched(…, store.TriggerAPI)` (`service.go:592`).

  `TriggerAPI` is "an authenticated POST …/deploys" (`store.go:236`). A restart and a manual deploy are the same row shape.
- `server_restarted` is mapped only to the audited verb `apps.Restart` (`lego/backend/internal/events/service.go:380`; webhooks `lego/backend/internal/webhooks/service.go:169`). The events package's own note (`events/service.go:347-352`) says that verb delegates to `deploys.Restart` whenever a control-plane store is wired. So `server_restarted` "fires only on the store-less CR-only path": never in production.
- `docs/render-artifacts/service-events.md:33` still lists "Server Restarted | `server_restarted` | Existing: accepted restart with triggering user". Its rule that unsupported mechanisms never appear as dead choices is broken for this entry.

## Fix (target behavior)

- `deploys.Restart` records a distinguishable bex trigger `restart`:
  - the dashboard labels it **Restart** on the Deploys tab and in Events;
  - GraphQL `trigger` = `restart`;
  - REST/MCP keep Render's closed `trigger` enum (map to `other`) with `bexTrigger: "restart"`, as `config_change` does (ADR018:137).
- The same accepted restart also records a `server_restarted` service event with `details.triggeredByUser`, so the Events feed, the filter and webhooks subscribed to Server Restarted all receive it. `deploy_started`/`deploy_ended` still fire for the deploy row, since bex models a restart as a release (ADR018:89).
- **Blast radius:** every restart entry point shares the verb, per ADR018:89: REST `POST …/restart`, GraphQL `restartServer`, MCP `restart_service`, dashboard Manual Deploy → Restart service, and the services-list Restart. A restart refusal (cron, no live deploy, suspended) emits nothing new.
- **Adjacent:** both restart paths (retained release and fall-through rebuild) record `restart`. A rollback keeps `rollback`.

## Acceptance

- Replay the probe:
  - the restart's row reads `bexTrigger:"restart"`; the Deploys tab and Events say "Restart";
  - the service's events include `server_restarted` with the caller;
  - the webhook subscribed to Server Restarted records a 2xx delivery of it;
  - a webhook subscribed only to `deploy_*` still gets the deploy pair.
- Backend tests on the `deploys.Restart` trigger and the event mapping (both store-backed and store-less), and a dashboard label test.
- Update `service-events.md:33` and the ADR018 Restart row.
