# 085 — `scripts/qa-login.sh` never revokes the session it mints, and the QA loop has now buried the operator's Active Sessions list under 122 live `curl/8.7.1` sessions

Why: the loop's own tooling has quietly degraded a **security** feature to uselessness — the operator can no longer spot a suspicious session in their own account — and every abandoned session is a live credential that nothing will ever revoke.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 32. **This one is self-inflicted by the harness, not a product defect** — filing it because it is a real repo problem with a real fix, and because the hunt's own rules say anything left behind gets reported loudly. Severity: **major** for the tooling; the product code is not at fault.

## What is there now

`https://dashboard.bex.co/settings` → Active sessions, read from the live accessibility tree and DOM:

```json
{ "totalButtons": 147, "signOutish": 123 }
```

122 revocable session rows, every sampled one identical in shape:

```json
{ "ariaLabel": "Sign out", "rowText": "curl/8.7.1\tUS\t18m\t" }
{ "ariaLabel": "Sign out", "rowText": "curl/8.7.1\tUS\t36m\t" }
{ "ariaLabel": "Sign out", "rowText": "curl/8.7.1\tUS\t1h\t" }
```

`curl/8.7.1` is `scripts/qa-login.sh`'s user agent, and the ages fan out in a steady ladder matching this loop's cadence across ~32 passes.

## Root cause

`scripts/qa-login.sh` completes a real Kratos password flow and keeps the resulting `ory_kratos_session` cookie. Its only cleanup is the temp directory:

```bash
# scripts/qa-login.sh:46
trap 'rm -rf "$tmp"' EXIT
```

Nothing ever calls Kratos logout. The comment at `:16` ("when the hunt ends: it carries a live session cookie") shows the authors were thinking about the *file* on disk in the `--caps=storage` variant, not about the session itself. So every invocation leaves one more permanent session on the account, and the `--serve` mode this loop uses — which deliberately keeps nothing on disk — leaves no trace the script itself could later clean up.

## Why it matters beyond tidiness

The Active Sessions card exists (`w4/m18`, from inbox `w4/006`) so a human can audit "every browser and device currently signed in as you" and revoke anything they don't recognize. With 122 indistinguishable `curl/8.7.1` rows, a genuinely hostile session would be invisible in the noise. The loop has not broken the feature's code — it has destroyed its signal.

Compounding it: those rows are **exactly** the ones `w4/084` shows are announced to a screen reader as 122 identical `button "Sign out"`.

## The fix

The session has to outlive the script — the browser uses it for the whole hunt — so revocation cannot go in the existing `EXIT` trap. Two parts:

1. **`scripts/qa-login.sh --logout`**: a mode that completes Kratos's self-service browser logout (`GET /self-service/logout/browser` → `logout_token` → `GET /self-service/logout?token=…`) for a supplied cookie jar, so a hunt can hand its session back at the end.
2. **A cleanup step in `.claude/skills/qa-find-bugs/SKILL.md` Phase 8**, alongside the existing instruction to delete the `--caps=storage` state file. Today Phase 8 tracks `qa-`-prefixed *resources* and says nothing about the session, which is why this went unnoticed for 32 passes.

Worth considering instead of, or alongside, the above: have `--serve` mint a **short-lived** session, so an abandoned one expires on its own rather than depending on a cleanup step that a crashed hunt would skip. That is the more robust shape — cleanup steps are missed exactly when things go wrong.

## The 122 existing sessions were deliberately NOT revoked

The hunt's rules forbid destroying anything not provably created by this harness. Every one of those rows is *probably* mine, but `curl/8.7.1` is not a harness-exclusive marker, and the bulk **"Sign out other sessions"** control is indiscriminate — it would also sign out the operator's real browser sessions. So nothing was touched.

Two things make the cleanup safe when someone does choose to do it:

- The **current** session renders no button at all (`session-row.tsx:36`, `session.current ? null : …`), so revoking every visible row cannot sign out the actor doing the cleanup.
- Each row's revoke is individually confirmable, so a `curl/8.7.1`-only sweep is possible without the blunt bulk control.

**This needs an explicit decision from the operator**, since it is their account: either revoke the `curl` rows individually, or accept them and let Kratos expiry drain them.

## Unverified

- **Kratos's configured session lifespan was not read**, so whether these 122 ever expire on their own is unknown — that value decides how urgent the cleanup is and should be checked first (`docs/ADR012-auth.md` and the Kratos config in `deploy/gitops/`).
- The exact Kratos logout endpoint shape above is from the standard self-service flow, **not** tested against this deployment.
- Whether any of the 122 `curl/8.7.1` sessions belongs to something other than this harness was not established — it is the reason nothing was revoked.
- The count is the number of revocable rows rendered after the list's "Load more" had been expanded by prior interaction; the true total may be higher.

## Closed 2026-09-15

`scripts/qa-login.sh --logout` completes Kratos's browser logout flow for a storage-state JSON or Netscape jar (defaults to `.playwright-mcp/qa-storage-state.json` or `qa-session.jar`). The 122 existing production `curl/…` sessions were not bulk-revoked — still the operator's call.
