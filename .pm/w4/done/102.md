# Any unknown `?type=` crashes `/services/new` to the error boundary instead of falling back

Why: a hand-edited, bookmarked, or mistyped deep link (`?type=worker` instead of `?type=background_worker`) kills the whole create wizard with an uncaught TypeError, when the validator two files over already promises "unknown values dropped".

## Record

- Severity: minor
- Repro: 1. sign in; 2. open `/services/new?type=worker` (or `?type=bogus_value`); 3. page reads "Something went wrong / Cannot read properties of undefined (reading 'titleKey')". Live 2026-09-19, reproduced twice with two values. Control: `?type=background_worker` renders "New Background Worker".
- Expected / Actual: unknown values fall back to the default web-service wizard (what `parseNewServiceSearch` documents) / uncaught crash in the route `head`.
- Root cause: `serviceTypeCreateCopy` (`dashboard/src/features/services/lib/create-context.ts:74-79`) defaults only on nullish (`??`), so a non-empty unknown string indexes `SERVICE_TYPE_CREATE_COPY` to `undefined` and `.titleKey` throws. The route's `validateSearch` (`parseNewServiceSearch`, `create-context.ts:96`) does drop unknown values — but the `head` resolver (`dashboard/src/routes/services.new.tsx:63-67`) reads the raw `match.search?.type`, which still carries the unknown string (proven live: the stack's first frame is `Object.head`). The in-component call (`services.new.tsx:79`) is safe today (validated search), but only by accident of its input.
- Fix: widen `serviceTypeCreateCopy` to `(type: string | undefined)` and return the default entry for any non-member string (reuse the existing `isServiceType` guard), so the contract "absent or unknown resolves to the default" holds at both call sites. No `head`/router change needed.
- Blast radius: 2 call sites of `serviceTypeCreateCopy`, both in `services.new.tsx` (head + heading); `SERVICE_TYPE_CREATE_COPY` has no other readers. `index.tsx:109-112` also reads `match.search`, but only strict string comparisons — safe.
- Adjacent classes: absent `?type=` (already defaults — unchanged); valid values (unchanged); other unknown search params (`projectId`/`environmentId` are dropped by the validator and never crash — unchanged).
- Unverified: whether TanStack passes raw or validated search to `head` by design at the pinned version (the fix doesn't depend on the answer — the helper becomes total either way).
- Render: n/a (bex-only wizard deep link).
- Estimate: 20m

## Resolution (2026-09-21)

Done as filed: `serviceTypeCreateCopy` now takes `string | undefined` and resolves any non-member value through the existing `isServiceType` guard, so the contract `parseNewServiceSearch` already documents — "unknown values dropped" — holds at **both** call sites rather than only at the validated one. No `head` or router change, as the note predicted.

The note's open question (whether TanStack passes raw or validated search to `head` at the pinned version) is left unanswered on purpose, exactly as the note framed it: the helper is now total, so the answer cannot change the outcome. That is a better resting place than pinning behavior we would have to re-verify on every router bump.

Covered by `resolves an unknown type to the default instead of throwing`, which exercises the live repro value (`worker`, the near-miss of `background_worker`) plus an empty string, a wrong-case member, and `__proto__` — the last because an object-prototype key is the other way an index into a plain-object table stops being a member without being nullish. Not re-probed live.
