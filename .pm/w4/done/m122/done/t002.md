## Objective

Make "Custom domain verified" mean the claim was promoted. Today every authorized call to `VerifyDomain` mints the event, so a domain that has never verified accumulates one row per Re-check click.

## Context

- `lego/backend/internal/events/service.go:341` — `"apps.VerifyDomain": TypeCustomDomainVerified`.
- `lego/backend/internal/apps/domains.go:683-750` — `VerifyDomain`. Three terminal paths matter: already `verified` (returns the view, promotes nothing), TXT mismatch (records `RecordDomainVerificationAttempt`, returns 409 `DOMAIN_OWNERSHIP_PENDING`), and success (`PromoteDomainClaim` → `projectDomainClaims` → `Kick`). Only the third is the event.
- `allFactTypes` (`events/service.go:370-396`) has no domain type, so under Option B the fact must be added there too or the promotion will be invisible — the exact regression shape `w4/m118` was repairing.
- The live 409 body carries `recordName`/`recordHost`/`recordZone`; whatever replaces the bogus event must not lose that detail from the caller's error.

## Steps

1. Apply t001's mechanism so the event is minted only on the promotion path.
2. Confirm the already-verified path mints nothing — re-verifying a verified domain changed no state.
3. Check whether the rendered Activity row names the hostname (the live payload had `details: {}`); if it does not, say so and decide whether this milestone adds it or files it separately.
4. Confirm the 409's coded body and its three record params are unchanged.

## Acceptance criteria

- [x] Five failing verifies produce zero events.
- [x] One succeeding verify produces exactly one, and a second verify on the now-verified domain produces none.
- [x] The `DOMAIN_OWNERSHIP_PENDING` body is byte-identical to today's.
- [x] The hostname question is answered in writing either way.
