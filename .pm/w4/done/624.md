# 624 — A build that fails reads "Build in progress" for about 45 s after the build command exits, and `build_ended`/`deploy_ended` go out that late; the control plane learns an App's new status only on its next 30 s resync

Why: on Render a failed build turns the deploy Failed as the error prints. On bex the log already shows the error and `exited with code 1`, yet the deploy, the service header and the Deploys row still read in progress for most of a minute. Every notification and webhook waits for the same pass. A CI job polling the deploy, or a user watching it, waits ~45 s for a verdict the cluster had 3 s after the failure.

- **Root cause:**
  - The operator has the verdict within seconds. `build.Ensure` returns `PhaseFailed` once the Job carries `JobFailed` (`lego/operator/internal/build/build.go:785-805`), and the operator re-observes a running build every `buildObserveRequeue` = 5 s (`lego/operator/internal/controller/app_controller.go:1059`, `:1318-1321`). It then writes the App's failed status (`r.fail`, `:1310`).
  - The control plane, which owns deploy rows, events and webhooks, reads that status only in `ReconcileOnce` → `recordObservations` → `recordDeploy` (`lego/backend/internal/store/reconciler.go:687`, `:515-518`).
    - `ReconcileOnce` runs on a 30 s ticker (`defaultResyncPeriod`, `:83`; `Run`, `:469-471`, through `core.PollWake`, `lego/backend/internal/core/poll.go:58-65`), or on a `Kick`.
    - Kicks come only from API writes (`apps/service.go:2855`, `:2929`, `apps/deploy.go:4056`, `deploys/service.go:327`, `apps/domains.go:1067`, workspaces; `cmd/api/main.go:1578`). Nothing kicks on a cluster-side status change.
    - The client is uncached (`client.New`, `cmd/api/main.go:244`), so there is no informer to hook.
  - `build_ended` looks prompt only because it is back-dated to the Job's failure time (`buildLifecycleFacts`, `reconciler.go:1216-1258`, w8/287). It is written, and delivered, in the same late pass.
- **Fix (target behavior):** the control plane records an App's terminal deploy transitions — `live`, `build_failed`, `update_failed`, `pre_deploy_failed`, `canceled` by the cluster — within a few seconds of the operator writing them, not on the next resync.
  - Watch App CRs, an informer or a `Watch` on `apps.app.bex.co` across workspace namespaces. `Kick()` the reconciler when the status fields `recordDeploy` reads change: phase, build and release conditions, `status.build`, `releaseStart`.
  - Keep the 30 s resync as the level-triggered backstop.
  - `Kick` coalesces (`reconciler.go:461-466`). Still measure the pass duration, so a busy cluster cannot turn every status write into a back-to-back full pass. If needed, kick only on the transitions above, or reconcile just the changed app.
  - REST, GraphQL, MCP, webhooks and the dashboard all read the rows this pass writes, so they move together.
- **Blast radius:**
  - Every deploy's terminal edge, not just failed builds: the same pass marks a deploy `live`, so a successful deploy's Live also lands up to ~30 s late. Round 248's first build: `build_ended` 01:15:49 → `live` 01:16:35.
  - The sampled availability edges (`server_failed`/`server_available`) already carry transition times (w5/m113) but are recorded in the same pass.
  - w4/604's Suspend race and w4/609's back-dated `startedAt` are siblings of this cadence. A watch would shorten both, but their fixes stay as filed.
