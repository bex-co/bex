# 090 — When the month-to-date bandwidth query fails, the figure silently vanishes: `network-metrics-card.tsx:375` gates on nullity and never reads the error it is handed

Why: this is the exact swallow-all-errors pattern `w9/m86` set out to eliminate and `w1/m50`'s definition of done forbade ("never a silently absent chart"), surviving in the one spot neither covered — a text figure rather than a chart — and the number it hides is the billing-adjacent "133 GiB used this month".

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 38. **Read-only on production — nothing created, changed or deleted, and no new login session minted** (existing browser session reused, per `w4/085`). Severity: **major** — a usage figure disappears with no indication anything failed. The counter-argument is fair and worth stating: an *absent* number misleads less than a wrong one. It still reads as "nothing to report" on a figure that informs cost.

## Control and failing case, side by side

Both runs on `https://dashboard.bex.co/services/srv-d9bj8s3eg85c7390eb9g/metrics`, same session, minutes apart.

**Control — query succeeds.** The Network card renders:

```text
… 0 B | 782.2 KiB | 1.5 MiB |  | 133 GiB used this month *
```

**Failing — only `MonthToDateBandwidth` is failed, everything else untouched:**

```js
await page.route("**/graphql", async (route) => {
  const pd = route.request().postData() || "";
  if (pd.includes("MonthToDateBandwidth"))
    return route.fulfill({ status: 429, contentType: "application/json", body: '{"errors":[{"message":"RATE_LIMITED"}]}' });
  return route.continue();
});
```

Result: the "used this month" line is **absent entirely**, and a scan of the whole `main` region for `/error|failed|unavailable|couldn't|retry/i` returns **false**. Nothing on the page says a query failed. Every other panel renders normally, so there is no ambient signal either.

## Root cause

`dashboard/src/features/metrics/components/network-metrics-card.tsx:375`:

```tsx
{monthToDate.egressBandwidthMB != null && (
```

That is the only gate. `monthToDate.error` is **never read** — grepped: the sole `monthToDate.` references in the file are `:375`, `:379`, `:381`, `:387`, `:389`, all value or `degradedSources` reads.

The hook hands the error over deliberately (`hooks/use-month-to-date-bandwidth.ts:23-40`): it sets `errorPolicy: "all"`, returns `egressBandwidthMB: data?.monthToDate?.egressBandwidthMB ?? null` — `null`, not `0`, precisely so a caller can tell "unknown" from "none" — and returns `error` alongside. The producer did its half correctly; the consumer discards it, and `null` then means both "no bandwidth" and "we could not read it".

## The same card already does this right, one branch above

`:357-361`, on the bandwidth **chart**:

```tsx
result={bandwidth}
// A real query error is not "No data in range" — the w1/m50 masking
// fix, now folded into MetricSection's shared error branch (w9/m86)
// with bandwidth's own message.
errorMessage={t("metrics.bandwidthError")}
```

So the chart half of the Network card was fixed twice over and the text figure beside it was not. `w9/m86`'s definition of done even reaches for this case — "If the t001 audit finds sibling chart panels (service metrics) share the swallow-all-errors pattern, they are fixed too" — and missed it, plausibly because the audit looked for *panels* and this is a line of text. `w1/m50` verified "month-to-date 83.1 MB as data with degradedSources", i.e. it made the figure render as data, without giving it a failure state.

Not a duplicate of either: both are closed, and neither's DoD asserts this branch.

## Blast radius: 1 of 1, with a positive control next door

Every `!= null &&` / `!== null &&` gate in `src/features/metrics/components/`:

| site | disposition |
| --- | --- |
| `network-metrics-card.tsx:375` | **the defect** — query result gated on nullity, error ignored |
| `svg-line-chart.tsx:145`, `:335` | chart internals (`referenceY`, `referenceValue`), not query results |
| `range-select.tsx:201` | `{error !== null && (` — **renders its error**; the feature's own correct convention, in the same directory |

Of the metrics feature's five hooks, the other four are covered: `use-metrics` and `use-datastore-metrics` feed `MetricSection`'s shared error branch (`w9/m86`), `use-metrics-filter-values` and `use-live-range` do not render standalone figures. So the fix is one call site, not a sweep.

## The fix

Target behavior: **the card distinguishes three states, and never conflates them** — a figure when the value is known, an explicit "couldn't read this month's bandwidth" when `monthToDate.error` is set, and the existing degraded-sources annotation (`*`) when sources are partially unhealthy. "Show something on error" is not the spec; the point is that *unknown* and *none* stop looking identical.

Reuse the treatment already in the file rather than inventing one — `t("metrics.bandwidthError")` exists for the chart, and `range-select.tsx:201` shows the inline shape. New copy needs entries in **both** `en.ts` and `zh.ts` (`locale-parity.test.ts` enforces it).

Adjacent classes after the fix: genuinely-zero egress renders `0 B` (a known value, not absent); partially-degraded sources keep the `*` and its tooltip; a failed query says so; and `loading` must not flash the error state before the first result settles — the hook polls at 60s with `cache-and-network`, so the pre-settle render is a cache hit or nothing.

## Also observed, and deliberately NOT filed

**The metrics page issues 29 GraphQL operations per load**, with duplicates — `Workspaces` ×2, `Deploys` ×2, `Metrics` ×3+ — measured by instrumenting `page.on("request")`. During this pass that produced real `429 RATE_LIMITED` responses: five on one load, then one (`MonthToDateBandwidth`) once the bucket recovered.

**That 429 is mine, not the product's.** This session had been probing the API heavily; after a 70-second idle the same page load put 28 of 29 operations through cleanly. Per the hunt's own rule — "only a 429 that survives idling at human pace is real" — it does not survive, and is not filed. The request *count* is recorded here only because it is what made the swallowed error visible, and because a page that fires 29 queries with duplicates will be the first to trip any limit that does bite. It is an efficiency observation, not a defect claim.

## Unverified

- **Only the 429 failure mode was exercised.** A network-level failure, a GraphQL `errors` array with a 200 status, and a timeout were not tested; `errorPolicy: "all"` means a partial-data response could behave differently again.
- **Not checked on a service with genuinely zero month-to-date bandwidth**, which is the case that must keep rendering `0 B` rather than the new error state — the distinction the fix exists to make.
- The `zh.ts` copy was not drafted; only the parity requirement was confirmed from `dashboard/CLAUDE.md`.
- Whether `w9/m86`'s t001 audit consciously excluded non-chart figures or simply did not see them was **not** established from its task file; the milestone is closed and only its README was read.
- Deploy status, **sixteenth consecutive check**: production still serves the pre-`e6419af0b` build, so `w4/078`'s re-probe, `w4/m105`'s scoped exchange and `w4/m106`'s live refusal test all remain queued.

## Closed 2026-09-15

`network-metrics-card` now distinguishes known month-to-date bandwidth (incl. `0`), an explicit `role="alert"` error when `monthToDate.error` is set with no value, and silence while the first result is still settling — no more nullity-only gate that swallowed the failure. Added `metrics.monthToDateBandwidthError` (en+zh) and three card tests covering error / zero / loading.
