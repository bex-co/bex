# 454 — A web service whose start command crashes stays "in progress" for the full 15-minute rollout budget, though the crash is diagnosed in seconds

Why: Render fails a deploy whose process exits during startup ("Exited with status N … Your application exited or crashed during startup"). bex already knows the crash within about 15 s and words it correctly, but holds the deploy `update_in_progress` until the progress deadline. A user, the pinned CLI's `--wait` and any CI deploy gate therefore wait 15 minutes to learn the start command is broken. bex already settles early for the analogous permanent image-pull failure.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-01 UTC (`muse.env`, `bex-canary`, pin `fdd51c53ef3f`); **minor** (the message is honest, only the terminal state is late), ~1h. ADR004 (rollout timers) / ADR018 parity.
- **Repro (REST, QA workspace):**

  ```
  POST /v1/services {"type":"web_service","name":"qa-<date>-crash","ownerId":"<tea>",
    "image":{"ownerId":"<tea>","imagePath":"docker.io/library/busybox:1.37"},
    "serviceDetails":{"runtime":"image","plan":"free","region":"frankfurt",
      "envSpecificDetails":{"dockerCommand":"sh -c 'echo qa-boom-start; exit 3'"}}}
  ```

  Fixture `srv-dbjht9bea3ic73dakijg`, deploy `dep-dbjht9bea3ic73dakik0` (deleted after the run).

- **Actual:**
  - `GET /v1/services/<id>/events` → by 11:12:37Z, `deploy_started.details.stallReason` already read `container exited shortly after start and is restarting repeatedly (last exit code 3) — check the service logs for the crash output. …`.
  - `GET …/deploys/<dep>` polled every 10 s read `update_in_progress` from 11:12:53Z until the deadline. It then closed `{"status":"update_failed","startedAt":"2026-11-01T11:12:50.688498Z","finishedAt":"2026-11-01T11:27:50.712831Z","failureReason":"container exited shortly after start and is restarting repeatedly (last exit code 3) — …"}`, exactly 900.0 s later. `deploy_ended` carries the same reason.
  - Instances: `[{"id":"srv-dbjht9bea3ic73dakijg-jnqiddlgob4bohvt2t53",…}]` at 11:28:47Z, then `[]` at 11:29:52Z, which is w1/m179's stop-at-zero working as recorded.
- **Expected (target behavior):** once every live pod of the desired revision has its app container in CrashLoopBackOff, or exited with a non-zero code before it was ever Ready, after a bounded number of restarts (proposal: the kubelet's own CrashLoopBackOff verdict plus `restartCount >= 2`, which is about 30–40 s), the deploy settles `update_failed` with the same `failureReason` it ends with today. The current-release-serving / first-release-stops-at-zero shape is unchanged. For a crash that happens after the pod was once Ready (a rollout that served and then died), keep today's deadline path, since that is a runtime failure rather than a startup one.
- **Root cause:** `lego/operator/internal/controller/app_controller.go:3578-3584` (`reportRolloutProgress`) settles early only for `rolloutDeadline` and `permanentRolloutPullFailure` (`:3820`). A crash loop reaches only `rolloutStallDiagnosis` → `stuckPodMessage` (`:5689`, crash branch `:5705-5718`), which stamps the Ready message and requeues every 5 s until `ProgressDeadlineExceeded`. Same shape on the unconfigured-image-port path: `web_image_http.go:190-195`.
- **Fix direction:** add `permanentRolloutCrash` beside `permanentRolloutPullFailure`, restricted to current-revision, non-deleting pods, the app container, never Ready, with a restart floor. Call it in both `reportRolloutProgress` and `reportWebHTTPSelection` and settle through the existing `settleFailedRolloutMessage(…, crashLoopBackOff, msg)` using `stuckPodMessage`'s wording, so REST, GraphQL, MCP, the events feed and the dashboard pick it up unchanged (the backend already passes the reason through, `lego/backend/internal/store/reconciler.go`).
- **Blast radius:** `reportRolloutProgress` serves web, private and worker services. Decide per type (Render fails all of them on a startup exit) and state it. `StartError` (w4/m177, `runtimeStartError`) and CreateContainerConfigError should settle the same way. A health-check failure (process running, probe failing) must **keep** the 15-minute budget (ADR004 `:107` three-timer contract, w4/m112). Regression tests: a running-but-unready pod and a ContainerCreating pod still wait; a pod that was Ready once and later crashes still takes the deadline path; the pull-failure early settle is unchanged.
- **Adjacent:** free-tier deferred park (w6/m147) must not race the early settle. The verdict lands before any park, as with pull failures.
- **Unverified:** Render's exact time-to-fail and whether it retries a crashed start once. No signed-in Render capture this run; its docs say only that the deploy fails ("Exited with status <N>" — render.com/docs/troubleshooting-deploys) and that "If any command fails or times out, the entire deploy fails" (render.com/docs/deploys). Workers, private services and build-from-repo web services were not probed.
- **Dedupe:** w4/437 changed only the in-progress message and explicitly kept the timing; w4/131 measured the 900 s budget for a stalled deploy; w4/m112 and w6/080 are health-check and Pending stalls. No open item covers early settlement of a startup crash, ADR018 records no divergence for it, and no DO_NOT_DO item applies.
- **Cleanup:** fixture service deleted (`GET` 404, workspace list `[]`); session revoked.

## Done 2026-11-01 (loopx w4)

`permanentRolloutCrash` (`app_controller.go`) settles a never-Ready, all-pods CrashLoopBackOff rollout after 2 restarts through `settleFailedRolloutMessage`, in `reportRolloutProgress` and `reportWebHTTPSelection`; wording shared with the in-flight diagnosis (`crashLoopMessage`). Applies to web, private and worker. Was-Ready, running-unready, <2 restarts, old-revision and CreateContainerConfigError keep the deadline. Test `TestPermanentStartupCrashSettlesBeforeRolloutDeadline`; ADR004 records it. Live replay (crash fixture settles `update_failed` in ~40 s) runs after the release pins the operator.
