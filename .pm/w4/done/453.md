# A pre-deploy command's outbound traffic is not counted toward its service's bandwidth

Why: a pre-deploy Job runs the user's own command, but its pod carries `app.bex.co/app` without `bex.co/app-id`, so it is never selected as a Service backend (w4/m181). Since w4/452 the direct egress meter skips such pods, so their public egress is never attributed to the service. Render counts a service's outbound bandwidth; whether that includes pre-deploy is unverified.

- **Source / severity / estimate:** w4/452 root cause, loopx w4, 2026-11-01; **minor** (undercount, never invented), ~45m.
- **Fix direction:** give pre-deploy Job pods an egress-only identity label (for example `app.bex.co/egress-app-id`, set to the App's id) that the meter reads when `bex.co/app-id` is absent, while Service selectors keep requiring `bex.co/app-id`. Leave platform Jobs (static publish, purge, disk backup) unattributed. Check Render's docs or a live service for whether pre-deploy bandwidth is billed before shipping.
- **Tests:** a meter attribution test for a pre-deploy pod with the egress label, and an operator test that its pre-deploy Job carries it while the Service selector still excludes it.
- **Dedupe:** w4/452 (meter health) is done. No other item covers it. No DO_NOT_DO item applies.

**Done (loopx w4, 2026-11-01).** Render counts "network communication initiated by any Render service or one-off job over the public internet" toward outbound bandwidth (render.com/docs/outbound-bandwidth), and a pre-deploy runs the service's own command. Its Job pod now carries `app.bex.co/egress-app-id` set to the App's id (`predeploy.Options.EgressAppID`), and still no `bex.co/app-id`, so no Service selects it. The egress meter attributes a pod by `bex.co/app-id`, falling back to the egress label. Platform Jobs (publish, purge, disk backup) stay unattributed. Tests: `TestJobPodNamesItsServiceForEgressOnly` and `TestDesiredPodResourcesAttributesPreDeployEgress`. Not yet verified live: needs a pin with this operator and meter image.
