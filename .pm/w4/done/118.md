# `validateBlueprint` passes a manifest whose `fromDatabase` reference cannot resolve, and it has the workspace context to know better

Why: validation is the step that exists to catch a manifest before it touches production, and a dangling `fromDatabase` clears it with `valid: true` and a clean plan — the correct error already exists and fires at apply, so the only thing missing is running the check one step earlier, in a resolver that is already handed the workspace it needs.

Found by live `/qa-find-bugs` 2026-09-21 pass 129 (w4-targeted, `muse.env` credentials). All probes were read-only `validateBlueprint` calls; nothing was created.

## The asymmetry

Same manifest shape, two reference kinds, opposite treatment:

```graphql
# fromDatabase → a database that exists NOWHERE
envVars: [{ key: REF, fromDatabase: { name: qa-no-such-database-anywhere, property: connectionString } }]
→ valid: true, errors: [], plan: [ service:qa-20260921-r3:create ]

# fromService → a service that exists nowhere
envVars: [{ key: REF, fromService: { name: qa-no-such-service-anywhere, type: web, property: hostport } }]
→ valid: false
   "service …: fromService references unknown service \"qa-no-such-service-anywhere\"
    (declare it under services: in the same file)"

# fromService → a service that DOES exist in the workspace (eden-dash-v3)
→ valid: false, same message
```

`fromService` is same-file-only, so it is fully checkable from the manifest and is checked. `fromDatabase` may legitimately name a database that exists in the workspace but not in the file — `beancount-forum-db` validates clean, correctly — which is why it cannot be checked from the file alone.

## It is three reference kinds, not one (pass 130)

The whole family was probed, and the split is perfectly consistent — which makes this a design-wide property rather than a `fromDatabase` quirk:

| reference                     | declared in-file | names an existing workspace resource | names nothing at all |
| ------------------------------- | ------------------ | -------------------------------------- | ---------------------- |
| `fromService` → a web service    | valid              | **rejected at validate**                | **rejected at validate** |
| `fromDatabase`                  | valid              | valid                                  | **valid** — deferred    |
| `fromService` → a Key Value      | valid              | valid                                  | **valid** — deferred    |
| `fromGroup`                     | valid              | not probed                             | **valid** — deferred    |

The rule underneath: **same-file-only references are checked at parse; workspace-resolvable references are deferred to apply.** `fromService`→web is the only same-file-only kind, and it is the only one validated early — including rejecting a *real* existing service (`eden-dash-v3`), which is correct under its own contract.

So the fix is not a one-field patch. It is "run the three workspace resolvers during validation too", and the symmetry makes that a cleaner change than the original framing suggested.

## The checks already exist — one step too late

All four resolvers exist with precise, actionable messages. Only the first runs at validate:

| kind                  | site                  | message                                                                              |
| ----------------------- | ----------------------- | -------------------------------------------------------------------------------------- |
| `fromService` → service | `deploy.go:1952` (parse) | `fromService references unknown service %q (declare it under services: in the same file)` |
| `fromDatabase`         | `deploy.go:1117` (apply) | `fromDatabase references unknown database %q in this workspace`                         |
| `fromService` → KV      | `deploy.go:1160` (apply) | `fromService references unknown Key Value %q in this workspace`                          |
| `fromGroup`            | `deploy.go:1584` (apply) | `fromGroup references unknown env group %q (declare it under envVarGroups: or create it first)` |

`resolveUndeclaredDatabases` and `resolveUndeclaredKeyValues` both also handle an ambiguous-name case, which validation would inherit for free.

`lego/backend/internal/apps/deploy.go:1099-1125`, `resolveUndeclaredDatabases`:

```go
found, duplicate := uniqueDatabaseByDisplayName(databases.Items, scoped, tenantID, name)
if duplicate { return … "fromDatabase reference %q is ambiguous in this workspace" }
if found == nil { return … "fromDatabase references unknown database %q in this workspace" }
```

That is exactly the right error, with the right wording, including an ambiguity case. It runs on the **apply/deploy** path, where the workspace snapshot is loaded (`listWorkspaceDatabases`).

`validateBlueprint` already takes `ownerId` and resolves a workspace — it is how the same call produces a `current_state` plan that distinguishes `create` from `noop` against live resources. So the lookup the check needs is available at validate time; it simply is not performed.

## Fix

Run the same resolution during validation and surface its two errors as validation errors. The cost is one workspace database list, which the plan step is already paying for in order to classify `create`-vs-`noop`.

If deferring is deliberate — "validate checks the file, apply checks the environment" — then say so at the site and in ADR018, because the current split is not obvious: `fromService` is an environment-independent check that runs early, `fromDatabase` is an environment-dependent one that runs late, and nothing tells a manifest author which they are getting.

Estimate: ~35m including the ambiguous-name case and a test that a dangling `fromDatabase` fails validation with the same wording apply uses.

## Also checked this pass, and found correct

- **In-manifest `fromDatabase` resolves and orders correctly.** A manifest declaring a database and a service that references it plans both, as `postgres:qa-20260921-bpdb:create` and `service:qa-20260921-bpweb:create`.
- **A `fromDatabase` naming a real workspace database validates clean** — the superset over Render's same-blueprint-only rule works as intended.
- **`fromService`'s rejection message names the offending service and tells the author what to do** ("declare it under services: in the same file"), which is the standard this note is asking `fromDatabase` to meet.

## Outcome (2026-09-21)

Fixed for the two kinds that can be, and the third is deferred with a written reason rather than by omission — which is the alternative the note explicitly offered.

`fromDatabase` and `fromService`→Key Value now resolve at validate through `resolveExistingBlueprintReferences`, the exact call the apply path makes, so both errors — unknown and ambiguous — arrive in apply's own wording and the two steps cannot develop two vocabularies for one refusal. A reference to a database that *does* exist in the workspace still validates, which is the deliberate superset over Render's same-blueprint-only rule and is pinned by its own test.

**`fromGroup` stays deferred, on a real constraint rather than an oversight.** Its check lives in `preflightBlueprintEnv` behind an uncached `AuthorizeFresh(can_view_sensitive)` re-assert, because a group link materializes secret values to workload code. `validateBlueprint` is a `can_view` verb, so running that check at validate would either refuse a viewer's validate or weaken the gate. The split is now stated at the site and in ADR018's Blueprint row, which was the note's requirement either way: a manifest author can tell which checks they are getting.

A caller with no resolved workspace is skipped — it has no workspace for a name to resolve against, and failing there would be an answer about the environment rather than the manifest. A cluster read failure is likewise not a manifest problem; the apply path remains the enforcement point.
