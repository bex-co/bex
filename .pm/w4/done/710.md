# 710 — Build and pre-deploy events omit Render's required `buildId` and `deployCommandExecutionId`, though bex already has an id for each

Why: Render requires `buildId` on `build_started`/`build_ended` and `deployCommandExecutionId` on `pre_deploy_started`/`_ended`; bex omits them, while w8/m442 already made a service build's id its deploy's `dep-` id, so a receiver cannot follow a build event to `GET /v1/logs?build=…`.

- **Source:** `/pm-brainstorm one aspect of render parity for w4` (the service events and outbound webhooks aspect), 2026-11-18, item 4; filed by `/pm them to w4`, 2026-11-19. ~50m. Land it before w4/m510, since both edit `lego/backend/internal/events/rest.go`.
- **Render:** the pinned OpenAPI `retrieve-event` members: Build Started `required: [buildId, trigger]`; Build Ended `required: [buildId, status, reason, buildStatus]`; Pre Deploy Started `required: [deployCommandExecutionId, deployId]`; Pre Deploy Ended `required: [deployCommandExecutionId, deployId, status, preDeployStatus, reason]`; Deploy Ended's optional `buildId`, "Set when the deploy shipped a build published by the service's linked build source."
- **bex:**
  - `lego/backend/internal/events/rest.go:453-466` maps `build_ended`, `pre_deploy_ended` and `deploy_ended` without these ids, while `pipeline_minutes_exhausted` already sends `buildId` as the deploy id (`:467-468`).
  - `lego/backend/internal/logs/build_filter.go:30-36` (w8/m442): "a service build's ID is its deploy's `dep-` id".
  - A build-source build's id is `deploys.BuildID` (`lego/backend/internal/deploys/build_sources.go:88`), carried as the deploy object's `buildId` (`lego/backend/internal/deploys/rest.go:74`).
  - `lego/backend/internal/events/render_member_test.go:55-60` pins `buildId` and `deployCommandExecutionId` as missing; ADR018's allowlisted "Service event types and details" row lists them.
- **Fix:**
  1. `build_started`/`build_ended` send `buildId`: the deploy's `dep-` id, the id the logs `build` filter takes; a build-source build sends its `bld-` id.
  2. `deploy_ended` sends `buildId` when the deploy shipped a build-source build: the deploy object's own `buildId`.
  3. `pre_deploy_started`/`_ended` send `deployCommandExecutionId` as the deploy id, since bex's pre-deploy run is its deploy's own, as its build is. This is bex's choice where Render's value is uncaptured (`w10/blocked/002`); record it in ADR018.
  4. GraphQL event details carry the same (MCP shares REST's). Remove those `missing` entries from the member test; ADR018's allowlist row keeps only the deprecated integer `status` and the other entries it already lists.
- **Acceptance:** `GET /v1/events/{id}` for a `build_ended` reads `buildId` equal to its deploy id, and `GET /v1/logs?build=<that id>` returns that build's lines; a `pre_deploy_ended` reads `deployCommandExecutionId`; a build-source deploy's `deploy_ended` reads the deploy's `buildId`; the member test passes with those entries removed; `cd lego/backend && go test ./...` passes.
- **Done (2026-11-19):** `build_started`/`build_ended` (and `pipeline_minutes_exhausted`) carry `buildId` (`dep-` for a service build, `bld-` for a build-source carrier); `deploy_started`/`deploy_ended` carry `buildId` from `deploys.build_id` when the deploy shipped a build-source build; `pre_deploy_started`/`pre_deploy_ended` carry `deployCommandExecutionId` as the deploy id (bex's choice where Render is uncaptured, `w10/blocked/002`, recorded in ADR018). GraphQL `ServiceEventDetails` exposes `buildId` and `deployCommandExecutionId` (golden schema updated); MCP shares REST's. `rendertest.Allowlist` dropped `build_ended`'s `buildId` (`allowlistSize` 23 → 22), `TestRenderEventDetailsMatchTheirMember` dropped all four `missing` entries, and unit, Postgres store, and API end-to-end (`GET /v1/events/{id}` → `GET /v1/logs?build=…`) tests pass.
