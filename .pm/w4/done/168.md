# Render's Postgres recovery, Postgres credentials and owner notification-settings paths are unmounted; bex serves them under other names

Why: a Render client or script calling Render's documented `GET /v1/postgres/{id}/recovery`, `GET /v1/postgres/{id}/credentials` or `GET /v1/notification-settings/owners/{ownerId}` gets a bare `404 page not found` against bex, although bex implements every one of these features under a bex-invented path. ADR018 marks the rows ✅ (l.150 "users", l.235 notifications, PITR recovery). Nothing enforces that a Render operation is either mounted or listed as a documented omission, which is how `w4/167`'s `/query/*` family slipped through too.

Found live in `/qa-find-bugs` pass 247 on 2026-09-27 (w4-targeted, `muse.env` credentials) against the deployed `4a0422577`. Read-only: a `GET` sweep of the 59 in-scope `GET` paths in Render's embedded spec (`lego/backend/internal/api/openapi/render-public-api-1.json`, 102 `GET` paths minus the ADR018 `—` non-goals: dedicated IPs, maintenance, log/metric streams, workflows/tasks, orgs, jobs, `/redis`). Real ids from `tea-d98210cbbpdc73dcrkvg` (e.g. `dpg-d9nqg95cavls73fp8m20`).

- 52 answered 200.
- 4 answered a deliberate typed error: `headers`/`routes` on a web service (400, static-only), `bandwidth-sources` (501, named), and `active-connections`/`replication-lag` on a service (400, named).
- **3 answered `404 page not found` (unmounted)**, besides the four `/query/*` paths already in `w4/167`:

| Render operation | Render path | bex serves it at |
| --- | --- | --- |
| `retrieve-postgres-recovery-info` | `GET /postgres/{id}/recovery` | `POST /postgres/{id}/recovery-info` (`postgres/rest.go:245`) — also the wrong **method** |
| `recover-postgres` | `POST /postgres/{id}/recovery` | `POST /postgres/{id}/recover` (l.246) |
| `list-postgres-users` / `create-postgres-user` | `GET`/`POST /postgres/{id}/credentials` | `GET`/`POST /postgres/{id}/users` (l.284-285) |
| `delete-postgres-user` | `DELETE /postgres/{id}/credentials/{username}` | `DELETE /postgres/{id}/users/{user}` (l.299) |
| `retrieve-owner-notification-settings` / `patch-owner-notification-settings` | `GET`/`PATCH /notification-settings/owners/{ownerId}` | `GET`/`PATCH /notification-settings` (`notifications/rest.go:59`) |

The `POST`/`PATCH`/`DELETE` rows are from the route table and the spec; only the `GET`s were sent (a mutation on the user's databases or settings is out of bounds).

## Fix

Target: every Render operation in the embedded spec is either mounted at Render's path and method, or listed in ADR018 as a documented omission. Bex-named paths stay as aliases.

- Mount Render's spellings as the canonical routes on the same handlers:
  - `GET /postgres/{id}/recovery` → `RecoveryInfo`
  - `POST /postgres/{id}/recovery` → recover
  - `…/credentials[/{username}]` → the users handlers
  - `/notification-settings/owners/{ownerId}` → the member-defaults handlers, scoped by the path owner
- Keep `/recovery-info`, `/recover`, `/users` and `/notification-settings` as aliases (the dashboard and CLI may call them; grep before retiring). Register every new spelling in `scope_matrix_ops.go` with the same class as its alias. Postgres user create/reveal is Sensitive/Mint per `w4/082`.
- Response shapes: validate each new route's response against its Render operation schema through the existing conformance harness (`conformance_test.go`), adding `conformanceAllowlist` entries only for documented divergences.
- Guard (covers `w4/167` too): a test that walks every operation in the embedded spec and fails unless the gated server routes its method+path, or the operation id is in an explicit omission list, each entry citing its ADR018 `—` row.
- Correct ADR018 l.150, l.235 and the PITR row to name the Render paths.

Unverified: whether Render's `/notification-settings/owners/{ownerId}` has workspace-level (owner) semantics that differ from bex's per-member defaults. The fix must read the Render schema before aliasing, and if they differ, record it as a divergence rather than alias. `POST`/`PATCH`/`DELETE` behaviour was not exercised.

Render: paths and methods per its public OpenAPI (embedded).

Estimate: ~55m.

Closed 2026-09-27: Added Render recovery GET/POST and credential GET/DELETE routes with conformance tests, owner credential inclusion, default-role deletion protection, and unchanged native aliases. Corrected the premise: owner notification policy is already a documented omission, and Render credential POST rotates the default role rather than creating an auxiliary role. These incompatible operations remain explicitly documented omissions. A full optional-feature route census now requires every pinned Render operation to be mounted or individually documented. Full backend suite passed. No live production re-probe performed.

## Live verification

Verified on production 2026-09-28 (`/qa-find-bugs` pass 251, deploy `6b6d99ea8`, `muse.env` credentials): `GET …/credentials` 200 (1 user) and `GET …/recovery` 200 (`AVAILABLE`). `/notification-settings/owners/{ownerId}` stays 404 — a documented deliberate omission (ADR018 l.383: workspace-wide policy bex does not implement), which answers this note's open question.
