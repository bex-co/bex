# 065 — Blueprint "Managed Resources" tells a synced blueprint to sync

Why: the blueprint detail page's empty state instructs an action the user has already taken — and which failed — so the one screen that should explain a broken blueprint explains nothing.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 (read-only; this is a pre-existing first-party blueprint, nothing was created, synced or deleted).

## What renders

`https://dashboard.bex.co/blueprints/blp-d9nqg95cavls73fp8m10` (`discourse_docker`), header badge **Error**, `Last synced` **17d**, Sync History showing 8 × `Success` and 12 × `Error` — the most recent error being `conflict: this domain already exists on another site`. The Managed Resources section reads:

> No resources yet — sync the Blueprint to apply your render.yaml.

Source: `dashboard/src/features/blueprints/locales/en.ts:397-400` (`blueprints.resourcesEmpty`), rendered by `dashboard/src/routes/blueprints.$blueprintId.tsx:458-481` whenever `blueprint.resources` is empty — with no branch on `status` or `lastSync`.

The backend genuinely returns nothing:

```text
POST https://api.bex.co/graphql
{"query":"{ blueprint(id:\"blp-d9nqg95cavls73fp8m10\"){ id status lastSync resources { id name type } } }"}
→ 200 {"data":{"blueprint":{"id":"blp-d9nqg95cavls73fp8m10","lastSync":"2026-08-26T10:26:53Z","resources":[],"status":"error"}}}
```

(REST `GET /v1/blueprints/{id}` has no `resources` field at all — keys are `id, name, repo, branch, path, autoSync, manifest, status, lastSync, createdAt, updatedAt`. That may be deliberate; noting it, not filing it.)

## The bounded fix

Branch the empty state on what is known. A blueprint with `lastSync` set and `status: error` should say the last sync failed and point at the Sync History row's error, not advise a sync. A never-synced blueprint keeps the current copy. Both strings already have somewhere to live (`blueprints.resourcesEmpty` plus one sibling key, en + zh). Sub-hour; one component branch and two locale entries.

## What is NOT claimed here

The manifest declares `blockeden-forum` (web), `blockeden-forum-redis` (keyvalue) and `blockeden-forum-db` (database). Two of those three exist in the workspace right now (`red-da4086iii7bs73drbqh0`, `dpg-d9rs3ee0ccis738kc7c0`, both `Available`); the web service does not exist at all (`GET /v1/services?limit=50` lists 5 services, none named `blockeden-forum`). So the manifest has been partially applied and the page says "no resources yet".

Whether those two resources were created **by this blueprint** is **unverified** — and it matters, because `resolveBlueprintResourcesFromIR` (`lego/backend/internal/apps/blueprint.go:1283-1370`) deliberately reports only resources whose durable claim or `bex.co/blueprint-id` label attributes them to the blueprint, so that a name match cannot adopt a foreign resource (`:1271-1281`, w8/m40). Durable claims landed in `bb85560cb` on **2026-09-09**, after this blueprint's last successful syncs (~1mo ago), so if the apply path did not also write the CR label back then, pre-claim resources are orphaned from their blueprint permanently with no backfill path. Confirming that needs cluster read access to the App/Database/KeyValue labels in `tea-d98210cbbpdc73dcrkvg`, which a browser-only hunt does not have. If someone confirms it, the backfill is its own item — do not fold it into the copy fix above.
