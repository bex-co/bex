## Objective

Stop a policy change from rolling the StatefulSet, and apply it to the running Valkey as the platform user.

## Result

- **2026-11-11 (loopx w4):** done. `keyvalue_maxmemory_runtime.go`: `applyKeyValueStatefulSet` writes the template with the policy its server started with when that is the only difference (else with the current one, so a roll that happens anyway starts the new server with it; a template without the platform user takes the new policy, as before). `reconcileKeyValueMaxmemory` runs one `CONFIG SET maxmemory <budget> maxmemory-policy <p>` (no budget and `noeviction` for an unset policy) on the running server (Valkey takes CONFIG while it loads) of the current StatefulSet revision, so a pod about to be replaced never takes a new plan's budget, and while the template holds an older policy every pass re-applies the current one, which corrects a server restarted from it; once template and process agree nothing is dialed. A suspended store's template takes the current policy outright. A refusal keeps the store serving and requeues within 5s (`kvRuntimePendingRequeue`). `status.maxmemoryPolicy` records what the running process was confirmed to run. The old body is `writeKeyValueStatefulSet`; `keyValueTLSRequeue` became `keyValueRuntimeRequeue`.
