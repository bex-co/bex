# "Import from .env" rejects a standard multi-line quoted value (a PEM key) and blames the wrong thing

Why: a real `.env` commonly holds a private key or certificate as a double-quoted value spanning several lines. The widely used `dotenv` parser accepts that. bex's import refuses the **whole paste** with "Line 4 isn't a valid dotenv assignment.", and line 4 is a well-formed assignment whose quote simply closes two lines later. A user migrating a working `.env` has to hand-convert every multi-line secret to `\n` escapes, and nothing tells them so.

Found live in `/qa-find-bugs` pass 216 on 2026-09-26 (w4-targeted, `muse.env` credentials) against the deployed `726042a28`. The fixture was a free web service `srv-das8dapsmc7s73cq5np0` (`qa-20260926-dotenv`). The draft was cancelled; `GET …/env-vars` still showed only `WHOAMI_PORT_NUMBER`. The service was then deleted (`DELETE` 204, then `GET` 404). Steps: Environment → **Edit** → **Add variable ▾** → **Import from .env** → paste → **Add variables**:

| Pasted `.env` | Result |
| --- | --- |
| `QA_URL=https://example.com/a#frag` · `export QA_EXPORTED=yes` · `QA_EQ=a=b=c` · `QA_PEM="-----BEGIN KEY-----` ⏎ `MIIBOgIBAAJBAKj` ⏎ `-----END KEY-----"` · `QA_AFTER=1` | dialog stays open, textbox `[invalid]`, alert **"Line 4 isn't a valid dotenv assignment."** ❌; nothing is imported, including the four valid lines |

## Mechanism

- `dashboard/src/features/services/lib/dotenv-import.ts`: `parseDotenv` splits the text into lines **before** parsing values. `parseValue` therefore sees `"-----BEGIN KEY-----` with no closing quote and throws `DotenvParseError(line, "quote")`. A quoted value can never span lines. No test covers a literal multi-line value; the `w2/m95` property test round-trips only `formatEnvExport` output, which always escapes newlines.
- `dashboard/src/features/services/components/env-import-dialog.tsx:47,95-99` keeps only `error.line` and renders `services.envImportLineError` ("Line {line} isn't a valid dotenv assignment.") for every `reason`: `assignment`, `key`, `quote` or `trailing`. The parser already knows it is an unterminated quote; the user is told the assignment is invalid.

## Fix

1. Let a double-quoted (and single-quoted) value continue across physical lines until its closing quote, with the literal line breaks kept in the value. This matches `dotenv` ≥ 15 and Render's "valid `.env` syntax". The error line of any later failure must still point at the right physical line.
   - The `w2/m95` escape contract is unchanged. `parseDotenv(formatEnvExport(x)) === x` still holds, because export never emits a raw newline inside quotes.
   - An unquoted value still ends at its line.
2. Show the reason the parser already computed: unterminated quote ("the quote opened on line N is never closed"), invalid key, text after a closing quote, and not an assignment. Each gets its own locale string, in `en` and `zh`.
3. Tests:
   - A literal PEM block imports with its line breaks intact and round-trips through save.
   - A truly unterminated quote reports `quote` with the opening line.
   - The existing `env-round-trip` property test still passes.

Related: `w2/done/m95` made multi-line values survive the value field and the escaped import form, but its DoD never exercised a literal multi-line value in an import. This note is that remaining gap, not a regression of it.

## Done (2026-09-27)

- `parseDotenv` (`dashboard/src/features/services/lib/dotenv-import.ts`) lets a double- or single-quoted value continue across physical lines until its closing quote, keeping the line breaks, the way `dotenv` parses a PEM key. An unquoted value still ends at its line. Later assignments keep their true line numbers. It re-scans only when an appended line holds the quote character, so a long certificate stays linear. A never-closed quote reports `quote` at its opening line, and text after a multi-line value's closing quote reports `trailing` at the physical closing line. The `w2/m95` escape contract and `env-round-trip.test.ts` are unchanged.
- `EnvImportDialog` keeps the parse error's reason and says what is wrong: "Line N isn't a KEY=value assignment." / "Line N: the name must be letters, digits, and underscores…" / "The quote opened on line N is never closed." / "Line N has text after its closing quote." (en + zh). Both callers (service Environment editor and New Environment Group) share it.
- Tests: four parser cases (the pass-216 paste with the PEM plus a single-quoted multi-line value, the unterminated quote's opening line, the trailing text's closing line, and an unquoted value still ending at its line) and a new `env-import-dialog.test.tsx` (PEM imports, quote message, key message). Dashboard `yarn lint` + `yarn test` (450 files / 3738 tests) are green.
