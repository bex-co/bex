# Running cron jobs keep Cancel disabled with a stale “no active run” reason

Why: after a manual run appears as Running, its Cancel button can still use the pre-run state, preventing cancellation until the separate action refresh or a page reload.

- **Severity:** minor; a temporary functional dashboard regression. Cancel was still disabled nearly eight seconds after the accepted run on fresh desktop and mobile pages; the separate refresh cadence is 30 seconds. The job itself continued normally.
- **Source:** continuous user-requested `qa-find-bugs w4`, 2026-10-11 UTC, pass a145, QA login helper using muse.env. This filing ships the researched issue only.
- **Estimate:** 55m: 25m local run-state refresh wiring, 20m meaningful hook/component coverage, 10m simplify, parity review and fresh live replay/cleanup.
- **Goal:** ADR008 dependable hosting and ADR038 usable cron run cancellation.

## Reproduce and expected behavior

Create an owned Free Existing Image cron job using `docker.io/library/busybox:1.37`, schedule `0 0 1 1 *`, and command:

```sh
sh -c 'printf "qa-a145-start\n"; date -u +%Y-%m-%dT%H:%M:%SZ; sleep 75; printf "qa-a145-complete\n"'
```

Fixture: `qa-20261010-a145-run-cancel`, `srv-db5gc90k3t2s73e5vakg`, workspace `tea-d98210cbbpdc73dcrkvg`. It is deleted.

1. Wait for a settled history with no active run. Freshly load `/services/<id>/events`, wait for Trigger Run to enable, and immediately confirm a manual run.
2. Once Recent Runs shows the new Running row, inspect its Cancel button. Hover its disabled wrapper on desktop.
3. Query the same resource's `serverActions` and `cronJobRuns` as shown below.
4. Reload while the run remains active, then click Cancel → Proceed.

**Expected:** discovering a new active run refreshes the action state for that same service/workspace promptly. While that read settles, show the checking reason and keep dispatch disabled. Once the fresh server decision is allowed with no precondition, Cancel enables without waiting for the unrelated 30-second cadence or reloading. A newly active row must not keep presenting a settled “There is no active run to cancel right now.” decision from before the run.

**Actual desktop, 1440×1000:** the page's ServerActions response at **03:47:31.129Z** says `cron_cancel_run: allowed/no_active_run`. Trigger at **03:47:31.690Z** accepts `crr-gqra8puqgrcog1nr57gv`. At **03:47:33.697Z, 03:47:36.588Z and 03:47:39.328Z**, Recent Runs shows Running and Cancel is disabled; its tooltip says **“There is no active run to cancel right now.”** All three fresh reads return that run as pending with a start time, and the fresh action response returns allowed with `precondition:null`. The captured page makes only its original ServerActions read during this interval. Reload enables Cancel at **03:47:57.543Z**; normal UI cancellation succeeds at **03:47:58.146Z**.

**Fresh mobile, 390×844:** after the preceding run finished, the page reads no_active_run at **03:50:07.582Z** and accepts `crr-q7vjbqiu5qccnfipstvu` at **03:50:08.177Z**. At **03:50:10.183Z, 03:50:12.910Z and 03:50:15.519Z**, the new row is Running but Cancel is disabled, while fresh reads again show an active run and an unblocked cancel decision. Reload enables Cancel at **03:50:34.987Z**, and cancellation succeeds at **03:50:35.534Z**. Mobile focus did not expose a tooltip; only the desktop tooltip wording is claimed.

Evidence, both inspected: `.playwright-mcp/qa-a145-cancel-disabled.png` (109,558 bytes) and `.playwright-mcp/qa-a145-cancel-disabled-mobile.png` (62,384 bytes). The ignored complete journey ledger is `.playwright-mcp/qa-cron-cancel-refresh-a145-ledger.json`; durable API probes follow below.

## Cause and precise fix target

- `dashboard/src/features/services/components/cron-runs-section.tsx:104–126` reads history and `useServerActions` separately. At **:137–140**, a successful trigger closes the dialog without refreshing that local action projection. At **:241–248**, the newly active row renders Cancel but disables it using that older projection.
- `features/services/hooks/use-cron-runs.ts:274–281` awaits RunCronJob and refetches only CronJobRuns. At **:204–210**, active history switches its own query to the fast converging cadence. Neither mechanism refreshes the separate action snapshot when a previously absent active run arrives.
- `features/capabilities/hooks/use-resource-actions.ts:45–48,57–105,107–112` holds the projection in local React state. Its automatic refresh depends on workspace/resource/access-generation/checkedAt/eligibility; a cron run transition does not change that lease. The hook already exposes a `refresh()` that uses the current binding, makes a fresh read, and rejects obsolete results.
- `features/capabilities/context/capabilities-provider.tsx:257–263` supplies the ordinary refresh; `common/lib/polling.ts:11,18` defines 30,000ms baseline and 3,000ms converging intervals. Different history and action schedules explain the bounded mismatch.
- The actual dependency is Apollo **4.1.3**, pinned in `dashboard/yarn.lock:72–74` and installed package.json. Opened `node_modules/@apollo/client/core/QueryManager.js:728–733,1085–1086`: no-cache forbids cache writes and reads from the link. The action hook uses `client.query(fetchPolicy:"no-cache")` and copies its result to local state. Opened `core/ObservableQuery.js:844–891`: history polling independently performs network reads at its configured interval. A CronRun mutation/history cache update has no mechanism to replace that local action result.
- The server's state is correct in the failing interval: `lego/backend/internal/apps/actioncaps.go:85–90` computes no_active_run from the current pending run; `apps/service.go:3671–3678` scans the run status. `features/capabilities/lib/resource-actions.ts:93–103,180–207,230–231` accepts a null precondition as ready and maps actual no_active_run to the captured reason. The wire type can express the correct state.

**Fix locally in CronRunsSection:** refresh the existing same-target action projection when the observed active-run identity/status changes, including a run arriving later after an accepted trigger. A refresh only immediately after the trigger is insufficient: the accepted run can precede its history row, as the fourth run demonstrated. Use a stable run/resource/workspace signature and avoid a refresh loop from every render, timestamp poll or refreshed callback. Mark the action decision as checking for the newly observed run until the matching refresh settles; preserve the pending row and open dialog/draft state. Terminal/canceled transitions must stop reusing an active-run decision too.

Keep the existing server decision and dispatch behavior. Do not infer permission from a Running row, waive no_active_run, change global lease timing, alter the server's cancellation/preemption contract, or optimistically invent history rows. The next implementation should use the hook's existing bound refresh API and preserve its failure/stale-result behavior.

## Scope, controls and neighbouring states

The shared `useServerActions` hook has **three production call sites**: CronRunsSection, `service-row-actions.tsx:119`, and `suspend-service-card.tsx:60`. The proposed refresh wiring is local to CronRunsSection; the other two remain passing-control targets if the implementation expands into the shared hook. `useProjection` also backs `useDeployActions`; changing its timing globally would expand scope and require those callers' coverage.

CronRunsSection has **one production JSX mount**, `routes/services.$serviceId.events.tsx:352–353`, gated by isCron. Web, private, background worker and static services do not mount these run controls; Postgres and Key Value use separate resource pages. `routes/cron.$.tsx:5–8` redirects the Render-shaped /cron alias to the canonical service route through `common/lib/render-alias.ts`; that alias was traced, not driven live.

The read projection is GraphQL-only (`apps/graphql.go:1163`). Cancellation itself remains `cancelCronJobRun` (**:1452–1459**), REST per-run/current cancellation (`apps/rest.go:1086–1110`) and MCP `cancel_cron_job_run` (`apps/mcp.go:761–764`). REST registers both `/v1/cron-jobs/{id}/runs` and `/v1/services/{id}/runs`: DELETE addresses the active run, and POST `.../{runId}/cancel` addresses a specific run. Only ordinary UI GraphQL cancellation was executed this pass; REST/MCP cancellation and alias navigation were not replayed.

Before settling, initial unknown/checking/unavailable action state remains disabled with its existing reason. A failed refresh must preserve history and keep the action unavailable; do not present a stale no-active answer as the new run's settled state. Terminal rows omit Cancel. Suspended, billing-blocked and denied states keep their current decisions. No missing-resource, timeout, transport, or other error is reclassified by this UI refresh fix.

**Unverified:** scheduled-arrival replay, short runs finishing inside the delay, Chinese display, hidden-tab/reconnect transitions, transport failure, alias navigation, paid services, REST/MCP cancellation and changed-access contexts. These are implementation verification boundaries, not additional live findings.
