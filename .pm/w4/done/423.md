# 423 — A service plus its linked env groups can exceed the kernel's whole-environment limit, and an `argument list too long` start reads only as `readiness_failed`

Why: w4/422 caps each `KEY=value` entry at the kernel's `MAX_ARG_STRLEN`, but the 512 KiB aggregate cap applies to the service's own vars and to each linked group separately. Five or more full sets can push a container's merged environment past `ARG_MAX` (about 2 MiB with the default 8 MiB stack), and then every new instance fails to exec with the same `E2BIG`. When that happens, the deploy's failure says only `readiness_failed`, not why.

**Severity:** minor (reasoned from the quota layout, not probed live). **Estimate:** ~1h. **Source:** split from w4/422 in the loopx w4 drain, 2026-10-26 (the note's "Adjacent" bullets).

## Fix (target behavior)

- Cap the merged environment (the service's vars plus every linked group's) at link time and at deploy time, with a coded 400 naming the limit. Or document, with a measured `ARG_MAX` for tenant pods, why the merged size cannot reach it.
- When an instance's start fails with `exec …: argument list too long`, the deploy's failure reason says so (the operator classifies it today only as `readiness_failed`).

## Files

- `lego/backend/internal/secrets/service.go` (`envMapWithinQuota`), `lego/backend/internal/envgroups/service.go` (link)
- the operator's rollout failure classification (`lego/operator/internal/controller/`)

**Dedupe:** w4/422 (done) covers the per-entry limit only. No `DO_NOT_DO.md` conflict.

**Done 2026-10-26 (loopx w4).** **Merged cap, enforced once per release in the operator, not at each bex-api write.** A write-time check would have to read every linked service's and group's secret values on each write. `checkMergedEnvSize` (`lego/operator/internal/controller/env_size.go`) runs in `ensureSavedReleaseConfigSnapshot` before a new release's config is snapshotted or its template rolls. It reads the mutable env sources in envFrom precedence and counts what execve counts (each `KEY=value`, its NUL and its pointer). Over `maxMergedEnvBytes` (2 MiB `ARG_MAX` for the default 8 MiB stack, minus 128 KiB headroom for the command line and platform variables), the deploy fails `DeployFailed` naming the total and the limit, and the serving release keeps running. This covers all three growth paths (link, service write, group write) at the moment they would ship. **Failure reason:** runc's `exec: "<prog>": argument list too long` StartError now reads "the environment is too large to start …" with the per-entry and whole-environment limits, instead of the generic launch failure. Tests: `env_size_test.go` (own set + 2 groups snapshots; + 3 groups refused before the snapshot flips; E2BIG message). Not replayed live, and whether a live E2BIG surfaces as a StartError rather than a readiness stall is unverified.
