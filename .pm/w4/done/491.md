# 491 — A webhook or registry-credential name accepts control characters, and a NUL byte in it answers `500 internal error`; w4/419's `CheckLabel` rule covers env groups, projects and environments only

Why: every other resource's name follows `core.CheckLabel` (no control characters, at most 100 code points), but these two accept a newline, a bell or a tab, and the one character PostgreSQL cannot store turns a create into a server error instead of a 400.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-05 ~01:35 UTC (`muse.env`, workspace `bex`; creates through the run's session, every object deleted in the same call); **minor** (input hygiene plus a wrong status class; no data lost); ~30m.
- **Extends w4/419** (done, `Environment group, project and environment names accept control characters and unbounded length`). 419's root cause is the same ("check only `strings.TrimSpace` + non-empty, never `core.CheckLabel`") and its fix is `core.TrimmedLabel` at the env-group, project and environment writers. Its scope list does not include webhooks or registry credentials, and neither was ever probed.
- **Probe** (in-page `fetch(..., {credentials:'include'})`; `POST /v1/webhooks {"name":N,"ownerId":"tea-d98210cbbpdc73dcrkvg","url":"https://example.com/h","enabled":true,"eventFilter":[]}` and `POST /v1/registrycredentials {"name":N,"ownerId":…,"registry":"GITHUB","username":"u","authToken":"t"}`; `N` = `qa-20261105-` plus the suffix shown; the control row is `POST /v1/env-groups {"name":N,"ownerId":…}`):

  | `name` suffix | `/v1/webhooks` | `/v1/registrycredentials` | `/v1/env-groups` (control) |
  | --- | --- | --- | --- |
  | `a\nb` (newline) | **201** | **201** | 400 `DISPLAY_NAME_CONTROL_CHARACTER` |
  | `a\u0007b` (BEL) | **201** | **201** | not run |
  | `a\tb` (tab) | **201** | **201** | not run |
  | `a\u0000b` (NUL) | **500** `internal error` | **500** `internal error` | 400 `DISPLAY_NAME_CONTROL_CHARACTER` |
  | 138 × `x` (150 characters) | **201** | **201** | not run |
  | `a‮b` (right-to-left override) | 201 | 201 | not run |
  | `"   "` (blank) | 400 `WEBHOOK_NAME_INVALID` | 201 (the name falls back to the host, by design, `registrycreds/service.go:243-245`) | not run |

  The same NUL name also answered `400` on `POST /v1/projects`, `/v1/key-value` and `/v1/postgres` in an earlier sweep, so those writers validate it; webhooks and registry credentials are the two that do not. Every object that came back `201` was read back and then deleted (`DELETE` 204 for all 13 in this probe, plus 7 from the earlier sweep).

- **Root cause:**
  - **Webhooks:** `normalizeName` (`lego/backend/internal/webhooks/service.go:1004-1012`) is `strings.TrimSpace` plus "must not be empty" (`WEBHOOK_NAME_INVALID`). It has two callers, create (`:490`) and update (`:870`). No `CheckLabel`, no length cap.
  - **Registry credentials:** create trims (`registrycreds/service.go:235`) and `validateCredentialFields` (`:402-415`) caps the name at `maxCredentialFieldBytes` = 253 **bytes** (`:73`), which is why 150 characters pass. Update repeats the same trim and byte cap (`:319-325`). Neither looks for control characters.
  - **Why NUL is a 500 and not just accepted:** the name is stored in a PostgreSQL `text` column (`webhook_endpoints.name`, `registry_credentials`), which cannot hold `0x00`. The unclassified SQL error falls through `store.classify` (`store/store.go:2904-2919`) and becomes the generic 500. The driver's message was not read (no server-log access), so the missing-NUL-support part is inferred; the other writers' `DISPLAY_NAME_CONTROL_CHARACTER` 400 for the same byte shows the rule would have caught it first.
- **Follow-up probe, 2026-11-05 ~01:55 UTC (updates, and the credential `username`):** same session, own fixtures (one webhook, one credential, one project with its environment, one env group), all deleted in a `finally` (204 ×4, then a credential created for the `username` rows, 204). `PATCH` answers:

  | Request | Answer |
  | --- | --- |
  | `PATCH /v1/webhooks/{id}` `{"name":"…a\u0000b"}` | **500** `internal error` |
  | `PATCH /v1/webhooks/{id}` `{"name":"…a\nb"}` | **200** (a newline name is stored) |
  | `PATCH /v1/webhooks/{id}` `{"url":"https://example.com/a\u0000b"}` | 400 `WEBHOOK_URL_INVALID` |
  | `PATCH /v1/registrycredentials/{id}` `{"name":"…a\u0000b"}` | **500** |
  | `PATCH /v1/registrycredentials/{id}` `{"username":"u\u0000x"}` | **500** |
  | `PATCH /v1/registrycredentials/{id}` `{"authToken":"t\u0000x"}` | 200 (the token is kept in the secret store, not a SQL column) |
  | `POST /v1/registrycredentials` `{"username":"u\u0000x",…}` | **500** |
  | `POST /v1/registrycredentials` `{"username":"u\nx",…}` | **201** |
  | `POST /v1/registrycredentials` `{"username":"u"×300,…}` | 400 `username must be at most 253 bytes` |
  | `PATCH /v1/projects/{id}`, `/v1/environments/{id}`, `/v1/env-groups/{id}` with a NUL name | 400 `DISPLAY_NAME_CONTROL_CHARACTER` (the controls) |

  So the update paths fail the same way as create, and the **`username`** is a third free-text field with the same gap (`validateCredentialFields` caps its bytes at `registrycreds/service.go:408` and never looks for control characters). The fix section below should cover `username` as well: reject control characters, and NUL in particular, on create and update. Env-group values already do this (`PUT …/env-vars/{key}` with a NUL value answers `400 ENVIRONMENT_VARIABLE_VALUE_INVALID`), which is the precedent for the message shape. Not part of this note, seen in the same probe: an env-var value containing an unpaired surrogate (`"a\ud800b"`) answers 200 and reads back as `a�b`, i.e. the stored value differs from the one sent without any signal; a secret-file content with a NUL is accepted and read back intact.
- **Fix (target behavior):**
  - Both writers apply `core.TrimmedLabel` (or `CheckLabel` after trim) to an explicitly supplied name, on **create and update**: control characters and line separators → `400 DISPLAY_NAME_CONTROL_CHARACTER`, over 100 code points → `400 DISPLAY_NAME_TOO_LONG`, exactly as env groups and projects answer after w4/419. REST, GraphQL, MCP and the dashboard all reach the same two service methods, so the change is in `webhooks/service.go` and `registrycreds/service.go` only.
  - **Registry credentials:** the blank-name fallback to the host (`:243-245`) must not be put through the 100-code-point cap, or a credential for a long registry host becomes impossible to create; validate only a name the caller supplied.
  - **Existing rows** with a longer name or a control character stay readable and deletable; only a new write or rename is refused.
  - **Not fixed by this:** `CheckLabel` allows U+202E (right-to-left override) because it is a format character, not a control one (`core/errors.go:368-380`); the RLO rows above would still be accepted, as they are for env groups. Whether to refuse bidi overrides in display names is a separate decision, not part of this note.
- **Blast radius:** `normalizeName` has 2 callers (`webhooks/service.go:490`, `:870`) and the credential name check 2 (create `:234-245`, update `:319-325`). Regression tests must keep a webhook and a credential with an ordinary name, a name with spaces inside, an accented or CJK name, and a 100-code-point name creating, renaming and listing exactly as today. The webhook delivery records and the dashboard lists render the name; nothing else reads it.
- **Adjacent classes:** a blank webhook name stays `WEBHOOK_NAME_INVALID`; an over-long name that today passes (101 to 253 bytes for a credential) becomes a 400 on the next write, which is the intended tightening and should be named in ADR notes as a behavior change; an unknown webhook or credential id on update stays 404 before the name is looked at.
