# 484 — A service younger than one chart step shows "No data captured in the past 48 hours", because metric reads restart the step grid at the service's creation

Why: right after a deploy, the moment a user most wants to see their new service's CPU, memory and instance count, the Scaling page's Recent Metrics says "No data captured in the past 48 hours" on all three charts for 24 minutes. The data is in Prometheus; finer steps return it. The empty state lies, and every chart with a step longer than the service's age does the same.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 52, 2026-11-05 07:08–07:16 UTC (`muse.env`, `bex-canary`, pin `dcdc774c1a6b`); **minor** (dishonest empty state; it self-heals after one step); ~40m.
- **Probe:** owned Free image service `qa-20261105-shell` (`srv-dbm2mvgj8n6s73baguc0`, `docker.io/traefik/whoami:latest`, `createdAt` 07:08:46, Live at about 07:09:46, light `curl` traffic, deleted at 07:16).
  - At 07:14 and again after a reload at 07:15, `/services/<id>/scaling` → Recent Metrics reads `No data captured in the past 48 hours` under Average Memory Utilization, Average CPU Utilization and Total Instances.
  - From the page, `GET /v1/metrics/instance-count?resource=<id>&startTime=<now-Nh>&endTime=<now>&resolutionSeconds=R` at 07:15:59:
    - `48h@1440` → `[]`, `2h@1440` → `[]`, `1h@1440` → `[]`, `48h@600` → `[]`, `1h@600` → `[]`
    - `48h@300` → 1 point at `07:13:46`
    - `48h@60` → 7 points, last `07:15:46`
    - `cpu@1440` → `[]` and `cpu@60` → 6 points.
  - Every returned timestamp sits on `07:08:46 + k·R`, whatever `startTime` was requested. That is the creation-anchored grid: the point at creation has no samples yet, and the next point lies one step later, in the future while the service is younger than `R`.
- **Root cause:** `lego/backend/internal/metrics/service.go:517-524` (w8/m124 t003) sets `q.Start = created` when the request starts before the App existed. Prometheus `query_range` evaluates at `start + k·step` (`metrics/source.go:168-176`), so moving `start` moves the whole grid onto the creation instant. The Scaling card asks for a fixed 48h window at 24-minute steps (`dashboard/src/features/services/components/scaling-recent-metrics.tsx:32-38`), so it gets no point at all for the first 24 minutes. The Metrics tab's longer presets hit the same thing for their own step.
- **Fix (target behavior):** a service with samples in the window always charts its most recent step, and the returned grid stays on the requested `start + k·step`. Keep w8/m124's guarantee, "no point before the App's creation and no predecessor series", by filtering instead of moving the grid:
  - Leave `q.Start` as requested.
  - Rely on the existing per-pod creation filter for pod-scoped queries (`source.go` `own(...)` / `NotBefore`, `:287-296`).
  - Drop returned points timestamped before `created` for the families without a pod filter (request and bandwidth series).
  - If `created ≥ End`, keep returning `[]`.
- **Tests:** a service created 5 minutes ago, read with `48h@1440`: the last point is at `end`, CPU/memory/instance-count are non-empty, and no point precedes creation. Rerun w8/m124's recreated-namesake tests unchanged, as the regression guard.
- **Blast radius:** the clamp at `:519` runs for every `/v1/metrics/*` read through `Service.Metrics`: cpu, memory, the limits, instance-count, http requests/latency and bandwidth. REST, GraphQL `metrics` and MCP share it. `AppNotBefore` has 7 callers in `lego/backend/internal`. Only `:519` moves the grid. `:876` (the pod filter) and `:1271` (the month-to-date window, w4/468) must be left as they are.
- **Unverified:** the Metrics tab presets and the request/bandwidth families were not probed this round. The instance-count series also read `2` from 07:09 to 07:11 for this 1-instance service, which is likely the create rollout overlap. It is not filed.
- **Render:** Render's Recent Metrics shows a new service's first minutes as soon as they are scraped.
- **Dedupe:** w8/m124 (done) introduced the clamp, and its DoD only asserts "no point before creation". w7/m43 (done) built the card. `grep -ril "No data captured in the past 48" .pm` → only m43. No DO_NOT_DO item applies.

Closed 2026-11-05: `Service.Metrics` no longer moves `q.Start` to the App's creation; it keeps the requested grid and drops points timestamped before creation (`dropPointsBefore`), keeping the `[]` answer when creation is at or after End. Pod-scoped queries keep their `NotBefore` floor. Tests: `TestYoungServiceChartsItsFirstStep`, `TestMetricsKeepTheRequestedGridAndDropPointsBeforeTheApp`; ADR010 'Service incarnations' updated.
