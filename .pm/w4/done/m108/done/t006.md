## Objective

Check that every change this milestone makes is consistent across the surfaces it exposes — REST, GraphQL and MCP in `lego/backend/`, plus the `dashboard/` UI — and compare each against render.com's equivalent behavior, recording deliberate divergence as divergence.

## Context

- Three of this milestone's four findings change a surface with four representations. `docs/ADR006-bex-api.md`: REST + GraphQL + MCP live together, so a fix in one must be a fix in three.
- The metric surfaces to check: REST `http-requests` (`internal/metrics/rest.go:41`), GraphQL `HTTP_REQUESTS` (`internal/metrics/graphql.go:44`), MCP `http_request_count` (`internal/metrics/mcp.go:152`) — the MCP name asserts a count, which after `t001` is finally true.
- The deploy surfaces to check: REST's nested `commit` object (`internal/deploys/rest.go:38-69`), GraphQL `commitId`/`commitMessage`, MCP, and the Deploys tab + deploy header.
- `docs/ADR018-render-parity.md`'s Metrics and Deploys rows, and `docs/render-artifacts/metrics-page.md`'s accepted-drift list (which says nothing today about rate-vs-count, and must after `t003`).

## Steps

1. For one service and one window, read `http_requests` through all three APIs and assert identical values; do the same for a deploy's `commit` through all three.
2. Compare each against render.com: what its Total Requests chart plots and how its aggregate is worded; whether its public-repo deploys carry a commit; how it words a rollback's provenance line.
3. Update the ADR018 rows and `docs/render-artifacts/metrics-page.md` where the shipped behavior moved; file any newly-noticed drift as follow-up rather than silently diverging.
