## Objective

Commit provenance is resolved exclusively through a GitHub **App installation** for the repo's owner. A service created from the create form's **Public Git URL** source — one of its three first-class options — has no such installation, so every deploy it ever makes carries no commit at all: not the first deploy, not a config-change redeploy, not a rollback. Give those deploys the commit they actually built.

## Context

Live capture, 2026-09-16. Service `qa-20260915-1a-web` (`srv-dal3f2rkmutc73d7q9l0`), created through **New Service → Web Service → Public Git URL** against `https://github.com/render-examples/express-hello-world` (branch `main`, free plan; deleted at the end of the QA run).

```
GET https://api.bex.co/v1/services/srv-dal3f2rkmutc73d7q9l0/deploys?limit=5
```

```json
[
  {
    "deploy": {
      "id": "dep-dal3gp3kmutc73d7q9t0",
      "status": "update_in_progress",
      "trigger": "config_change",
      "createdAt": "2026-09-16T06:34:12.914021Z"
    }
  },
  {
    "deploy": {
      "id": "dep-dal3f2rkmutc73d7q9lg",
      "status": "live",
      "trigger": "create",
      "createdAt": "2026-09-16T06:30:35.927371Z"
    }
  }
]
```

No `commit` on either. The control — `srv-d9bj8s3eg85c7390eb9g`, same workspace, same API call, a GitHub-App-connected repo — returns `"commit": {"id": "6008f9d3…", "message": "feat(seo): …", "createdAt": "2026-09-16T05:25:03Z"}` on every row. In the UI the difference is stark: the connected service's Deploys tab rows read `7489f0f fix(seo): backfill seo_title…`, while the public-repo service's rows read only `First Deploy` / `Config Change`, and the "Roll back to this deploy?" dialog names no code at all.

The build itself knows the commit — the deploy log for the same service prints `==> Building from https://github.com/render-examples/express-hello-world@main` and checks out a real SHA.

Root cause, and the whole call graph:

- `lego/backend/internal/github/service.go:935-963` `resolveCommit` — requires `s.Store.GetGitConnectionByOwner(ctx, workspaceID, owner)`; `ErrNotFound` returns `ok=false` and the deploy proceeds with no metadata. Its doc comment (`service.go:924-934`) records this as deliberate best-effort behavior.
- It is reached through exactly one adapter, `commitSource.ResolveCommit` (`github/service.go:915-918`), wired in the composition root at `internal/api/server.go:800` (deploys) and `server.go:841` (apps).
- Two consumers, both of which inherit any fix: `deploys.Service.resolveCommit` (`internal/deploys/service.go:711-734`, used by `Trigger` at `service.go:594`) and `apps.Service.resolveDeployCommit` (`internal/apps/commit.go:52-64`, the create-path first deploy and the blueprint redeploy). Rollback copies the target deploy's commit, so it inherits the gap rather than adding one.
- Storage can already hold it: `store.CommitInfo{Hash, Message, AuthorAt}` (`internal/store/store.go:218-222`) is all-`omitempty`, and `deploys/rest.go:125-131` emits the nested Render `commit` object whenever `CommitID != ""` — so a hash-only commit serializes cleanly if a message is unavailable.

`w9/001` (done, `.pm/w9/done/001.md`) built this mechanism and listed its own remaining gaps — a branch that moves between resolution and clone, and the push-webhook path opening no deploy row. The public-Git-URL case is **not** among them, so this is a new gap in that feature, not a re-file.

**Name the target behavior before coding.** Two shapes are viable and they are not equivalent:

- **Resolve at deploy-open time, unauthenticated.** Extend `github.Service.resolveCommit` so that when there is no installation for the owner it falls back to an unauthenticated `GET /repos/{owner}/{repo}/commits/{ref}`, which GitHub serves for public repos. Cheapest change, reuses the existing seam, gives hash + message + authorAt. Costs: GitHub's unauthenticated limit is 60 requests/hour **per IP**, shared across the whole bex-api fleet, so it needs a cache and a failure path that still opens the deploy; and it only works for GitHub-hosted public repos, not the arbitrary git URL the field accepts.
- **Report back from the build.** The operator's build already fetches the ref and can verify it (`lego/operator/internal/controller/app_controller.go:872` passes `ExpectedCommit`; `lego/operator/internal/build/build.go:1295-1296` puts `EXPECTED_COMMIT` in the build env). Have the build publish the checked-out SHA and write it onto the deploy row. Works for any git host and reports the commit that was *actually built* rather than the one that was HEAD at trigger time — which also closes `w9/001`'s own "branch moved between resolution and clone" gap. Costs: a new operator→backend write path, and the commit arrives after the deploy row opens, so the row is briefly commit-less.

Pick one, write down why, and say what the row shows before the value lands if the answer is the second.

## Steps

1. Decide between the two shapes above; record the decision and its rationale in the code comment that replaces `resolveCommit`'s current "no connection ⇒ no metadata" note, and in `docs/ADR004-app-deployment.md`.
2. Implement it. If the unauthenticated path is chosen, cache per `(repo, ref)` with a short TTL, treat every failure as today's `ok=false`, and never let it delay or fail a deploy.
3. Confirm the fix reaches all three deploy-opening callers — create-path first deploy (`apps`), `Trigger` (`deploys`), and blueprint redeploy — not just the one used to reproduce.
4. Place the adjacent classes explicitly: a **private** repo with no connection, a **deleted/unknown ref**, a **non-GitHub** git URL, and a GitHub outage must each still open the deploy and omit `commit` — never a fabricated, placeholder, or partially-filled value. A non-existent repo must not be distinguishable from a private one through this path (no existence oracle).
5. Check the UI renders a hash-only commit (no message) without breaking the Deploys row or the deploy header, in case the chosen path yields a SHA before a subject.
6. Re-run the end-to-end journey on production and re-capture the `GET …/deploys` response for the first deploy, a config-change redeploy, and a rollback.

## Acceptance criteria

- [ ] A service created from **Public Git URL** against a repo with no GitHub App connection exposes `commit` on its first deploy, on a config-change redeploy, and on a rollback, over REST, GraphQL and MCP.
- [ ] Its Deploys tab rows render `<short-sha> <subject>` (or `<short-sha>` alone, rendered cleanly, if the chosen path has no message).
- [ ] The rollback confirmation dialog names the commit being restored.
- [ ] Private-repo-without-connection, unknown-ref, non-GitHub-URL and provider-failure cases each still deploy successfully and omit `commit` — asserted by tests, not by inspection.
- [ ] No deploy path can be made slower or failable by commit resolution: a hung or erroring provider call cannot block the deploy opening.

## Out of scope

- The two gaps `w9/001` already recorded as open (push-webhook rows, the resolution-vs-clone window) — unless the report-back shape closes the second one for free, in which case say so.
- Adding non-GitHub git-provider integrations (`.pm/DO_NOT_DO.md` rejects GitLab and Bitbucket provider work; resolving a commit from a public URL is not a provider integration, and this task must not grow into one).
