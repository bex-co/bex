## Objective

The Outbound Bandwidth chart is built from the same rate primitive `t001` is removing from `http_requests`, while the month-to-date figure printed directly beneath it is built from `increase`. Determine which is right for the chart and make the page self-consistent — or, if the chart is deliberately a rate, label it as one.

## Context

**This finding is plausible, not confirmed.** The code shape is unambiguous; the live numbers did not reconcile, and that discrepancy must be explained before anything is changed.

The code, all in one file:

- `lego/backend/internal/metrics/source.go:387` — the chart: `egressquery.SumRates(egressquery.App(...), stepSeconds(req.Resolution))`, i.e. `(sum(rate(counter[Ns])) or vector(0)) + …` (`egressquery/query.go:147-160`) → **bytes per second**.
- `lego/backend/internal/metrics/source.go:502` — the "N used this month" line under the same chart: `egressquery.Increase(spec, …)` → `sum(increase(counter[Ns]))` → **bytes**.
- `lego/backend/internal/usage/service.go:1229` — billing/metering: also `egressquery.Increase`. Money is measured with the count primitive; the chart is not.
- `lego/backend/internal/metrics/service.go:1036-1044` — `requestUnit` declares `unitBytes` for bandwidth either way.

The live capture, 2026-09-16, `srv-d9bj8s3eg85c7390eb9g`, 30-minute window:

```json
{
  "data": {
    "metrics": [
      {
        "unit": "bytes",
        "values": [
          { "time": "2026-09-16T06:19:14Z", "value": 1000633.311111111 },
          { "time": "2026-09-16T06:20:14Z", "value": 917044.0222222222 },
          { "time": "2026-09-16T06:22:14Z", "value": 1037244.1333333332 }
        ]
      }
    ]
  }
}
```

The dashboard rendered that as a chart with a `0 B / 1.0 MiB / 2.0 MiB` y-axis and the line `164 GiB used this month *` beneath it.

**The anomaly to resolve first:** if those points are bytes/second, ≈1 MB/s sustained is ≈86 GB/day, which over the ~16 elapsed days of the month would be ≈1.3 TB — not 164 GiB (≈10 GB/day ≈ 118 KB/s). The chart is ≈8.5× the month's average rate. That is possible for a genuinely bursty service captured at a peak, but it is not proof, and it is equally consistent with the points being something other than a plain per-second rate. Do not change the query until this is explained — a "fix" aimed at the wrong mechanism is the failure mode this task exists to avoid.

## Steps

1. Reproduce the capture: read `BANDWIDTH` for a busy service over a short window, and independently read the same counter over the same window with `increase()` directly against Prometheus. The ratio between them must equal the step in seconds. If it does not, the mechanism is not the one described above — record what it actually is and re-aim the task.
2. Reconcile against the month-to-date number: sum the chart's implied bytes over a full day and compare with the `Increase`-derived daily figure for the same day.
3. Decide, with the evidence from 1–2:
   - **If the chart is a rate and should be a count:** move it to `egressquery.Increase` over the step, matching the month-to-date figure and the metering read.
   - **If the chart is deliberately a rate:** leave the query, but make the wire and the UI say so — the `unit` string and the axis label must distinguish bytes from bytes/second, since today both read "bytes".
4. Record the decision and its evidence in `docs/render-artifacts/metrics-page.md`, whose accepted-drift list currently says nothing about rate-vs-count on either chart. Note what render.com's own Bandwidth chart plots.
5. If the query changes, check every consumer of the bandwidth series: the chart, the month-to-date line, and anything in `usage/` that reads the metrics feature rather than the metering path.
