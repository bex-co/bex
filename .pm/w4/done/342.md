# Search can't find services by kind ("Cron Job" says no matches while three are listed)

Why: Cmd-K labels every service by its kind and its own code intends "cron"/"private" to match by kind, but the filter only reads names and ids. A user who types the kind they can see gets "No matching pages or resources." for resources that exist.

- **Severity:** minor (search fails to narrow by a visible attribute; an empty state that isn't true). **Estimate:** 30m.
- **Source:** live functional `/qa-find-bugs w4`, pass c91d4a, 2026-10-19 UTC, `muse.env`, workspace `bex-canary` (read-only; no fixture). Production was pinned to `5e75de920`; research is on main `8943c158e`. Screenshot `.playwright-mcp/qa-search-cronjob-c91d4a.png` is local and gitignored.
- **Repro:** header Search (⌘K) in a workspace with three cron jobs (`qa-20260922-cd9361-boundary`, `-longcronxx`, `-nativecron`). The empty-query list labels all three "Cron Job". Results at 2026-10-19T00:54:38Z:

| Typed | Results |
| --- | --- |
| `service` | all 8 services (control: the generic token works) |
| `cron` | only `…-longcronxx` and `…-nativecron` (whose **names** contain "cron"); `…-boundary`, also a Cron Job, is missing |
| `Cron Job` | nothing; the dialog reads **"No matching pages or resources."** |
| `Web Service` | nothing (5 web services exist) |
| `Database` | `qa-20261017-64552e-pg14 Database` (control: other kinds do match their type word) |

- **Root cause:** `dashboard/src/common/components/dashboard-layout/global-search-dialog.tsx`.
  - The filter is the literal `matchesQuery` over a per-kind haystack (`:116-118`, `:196-220`), introduced with `shouldFilter={false}` in `2e95ff0cb` (2026-08-24).
  - The service haystack (`:203-207`) is `serviceSearchText` (name, immutable name, slug, id; `:424-433`) plus the generic `common.topbarServiceResource` ("Service"). It has no kind.
  - `w4/049` (`3a3bac0c2`, 2026-09-07) added the kind label only to the `CommandItem` `value` (`:299-301`), whose comment says it is there so "cron"/"private" match too. With `shouldFilter={false}`, cmdk never filters on `value`, so that matching never took effect.
  - Databases, Key Value, environment groups, blueprints and projects append their kind word to the haystack (`:197-220`), so only services are inconsistent.
- **Fix (target behavior):** a service matches when the query is a substring of its name, immutable name, slug, id, the generic "Service", **or its displayed kind label** (`t(SERVICE_TYPE_LABEL[deriveServiceType(type)])`: Web Service, Private Service, Background Worker, Cron Job, Static Site).
  - Build the filter haystack and the item `value` from one helper so they cannot drift again.
  - Use the translated label, so a zh user typing the kind word shown on screen also matches.
  - Keep the literal substring rule. It is what stopped the id over-matching that `2e95ff0cb` fixed.
- **Blast radius:**
  - One component; `filteredServices` feeds the Resources group only.
  - Pages, projects, datastores, environment groups and blueprints are unchanged.
  - The existing tests (`__tests__/global-search-dialog.test.tsx:61-81`) assert only the displayed labels; none types a kind.
- **Adjacent classes:**
  - Very short queries such as "web" or "job" will now also match by kind. That is intended, and it does not reintroduce id fuzzy matching.
  - The Loading state (`w4/229`) and empty-query reset (`w4/265`) are unaffected.
- **Unverified:**
  - Private service, background worker and static-site kinds were not live (none exist in the workspace); they share the same label table.
  - The zh locale was not probed.
  - Render's dashboard search behavior was not compared.
- **Dedupe:**
  - `w4/049` (done) delivered the labels, and its live repro checked display only.
  - `w4/229`, `w4/265` and `w4/291` are other search behaviors.
  - No open item mentions kind matching.
  - `git log` on the component since `3a3bac0c2` shows no fix.
- **Acceptance:**
  - A dialog test with web, cron, private and static services: typing each kind label returns exactly those services, and fails on current code. "cron" returns every cron job, including one without "cron" in its name.
  - Live, on bex-canary's three cron jobs: "Cron Job" lists all three.

## Implementation done 2026-10-19 (loopx w4)

- `global-search-dialog.tsx` builds one `serviceHaystack`: the service's names and id, the generic "Service", and its translated kind label (`SERVICE_TYPE_LABEL[deriveServiceType(type)]`). The filter matches against it, and the item `value` reuses it. The literal substring rule is unchanged, so no id fuzzy matching returns.
- Dialog tests use six services with neutral ids, one of each kind plus a second cron job without "cron" in its name. "Web Service", "Cron Job", "cron", "Private Service", "Background Worker" and "Static Site" each return exactly their services, and the zh kind label matches as well. All seven fail on the pre-fix dialog.
- Dashboard `yarn lint` and `yarn test` (5208 tests) pass. `/simplify`: reuse and efficiency are clean, and the comment was corrected (cmdk never filters on `value` here).
