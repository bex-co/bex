# Clearing a cron job's Command reports success but preserves the old override

Why: the Command field explicitly offers a blank value to remove the override, yet Save converts that intent into “keep the existing command” and tells the user the settings were saved.

- **Severity:** major — misleading successful save of an ordinary settings edit. The old command remains persisted; no claim of stored-data loss or an observed image-default run is made.
- **Estimate:** 55m, including both save callers and their mutation/authorization regression controls; one inbox-sized dashboard fix.
- **Source:** live `$qa-find-bugs`, new continuous pass 3, **2026-09-21 America/Los_Angeles / 2026-09-22 UTC**, filed in w4 at the user's request. Journey 10, cron settings.
- **Goal linkage:** reliable hosting configuration under [ADR038](../../docs/ADR038-cron-jobs.md), whose command contract distinguishes an optional override from the image default. The user must be able to remove an override as well as replace it.

## Reproduction and durable evidence

1. From a fresh page load, click **Edit command**, empty the **Command** input, and click **Save changes**.
2. The UI leaves edit mode and the original command reappears. The toast says **Cron job settings saved.** with **The operator will apply the new schedule on its next reconcile pass.**

## Producer, serialization, and consumer

`dashboard/src/features/services/components/cron-deploy-section.tsx:92–105` renders Command as optional and forwards the edited string with the persisted schedule. Its localized hint at `features/services/locales/en.ts:1852–1855` explicitly says to leave the field blank to run the image's own command. Shared `EditableFieldRow` defaults to trimming (`:122`, `:152`), permits the nonempty-to-empty change (`:155`), and calls `onSave(normalized)` (`:170`). Empty and whitespace-only input therefore both reach the hook as `""`.

The defect is `dashboard/src/features/services/hooks/use-cron-job.ts:44`: `command: command || null` replaces explicit empty with null. The hook toasts success and returns true at `:47–50`. `EditableFieldRow` then exits editing at `:171`; its displayed value at `:140` becomes the unchanged persisted prop. That explains the original command reappearing without an error.

The wire shape is supported; no schema widening or unsafe cast is needed. `features/services/api/services.graphql:68–83` declares `$command: String` and selects the returned `id`, `schedule`, and `command`. Generated `graphql/definitions.ts:1734–1742` permits `command?: string | null | undefined`. The production browser uses `BatchHttpLink` (`common/apollo/factory.client.ts:21–28`), matching the captured array. Pinned Apollo **4.1.3** (`dashboard/yarn.lock:72–74`) puts the operation variables in its body (`node_modules/@apollo/client/link/http/selectHttpOptionsAndBody.js:62–63`) and serializes the batch with `JSON.stringify` (`link/batch-http/BaseBatchHttpLink.js:70–83`). That preserves the difference between `""` and null; it is not the source of the conversion.

The backend distinction is intentional:

- `lego/backend/internal/apps/graphql.go:1398–1406` requires schedule, accepts an optional string command, and passes it through `gqlutil.StrPtr`.
- The actual pinned `github.com/graphql-go/graphql` **v0.8.1** (`lego/backend/go.mod:14`) preserves empty strings: `values.go:133–135` maps null to nil, `:351–363` resolves variable values, and `:60–65` omits null arguments without defaults. `isNullish` at `:299–321` does not treat an empty string as null; `scalars.go:307–314` retains the empty string. These dependency paths were read from the installed module and are not edit targets.
- `lego/backend/internal/gqlutil/gqlutil.go:383–388` returns nil for absent/null input, but a nonnil string pointer for `""`.
- `apps/service.go:3849–3853` defines nil as **keep existing** and a nonnil empty command as **clear**. `:3888–3889` assigns the trimmed command only when that pointer exists; `:1020` echoes the persisted `Spec.Command` in the view.

The operator's two scheduled/manual consumers share `cronPodSpec` (`lego/operator/internal/controller/app_controller.go:3547`, `:3742`). At `:3857–3862` it uses `Spec.Command`; if that is empty, non-native/non-buildpack legacy `Spec.StartCommand` can be a fallback, otherwise the container keeps the image command. This filing targets removal of the displayed override. It does not change or claim live verification of those runtime fallback rules.

## Exact scope and the authorization constraint

Exhaustive production searches found **one `useCronJob` consumer**, `CronDeploySection` at `cron-deploy-section.tsx:35`, with **two calls**: Schedule save at `:89` and Command save at `:104`. There is **one production section mount**, `routes/services.$serviceId.settings.tsx:213–220`, gated to exactly `cron_job` by `features/services/lib/service-type.ts:68–69`. Both image-backed and repo-backed cron jobs, including Docker/native builders, use it. Web, static, worker, private, Postgres, and Key Value do not. Creation and run/cancel hooks are separate consumers of other mutations.

Canonical entry: `/services/<cron-id>/settings#deploy`. `/cron/`, `/web/`, `/worker/`, and `/pserv/` splat aliases preserve `/settings`, query, and hash through `common/lib/render-alias.ts:58–87`; their segment/type mismatch is deliberately permitted. `/static/<cron-id>/settings` canonicalizes to `/services/...` through `service-detail-loader.ts:98–100,116–124` and `service-base.ts:15–18`. An actual static site fails the cron gate.

| Action | Required wire command | Existing permission/protection behavior to preserve |
| --- | --- | --- |
| Save Schedule with no existing command | null or omitted | Schedule-only `can_operate`; no command redefine confirmation |
| Save Schedule with an existing command | Existing trimmed nonempty command | Current caller replays that command, so it requires `can_create` and the existing protected-environment handshake |
| Replace Command | New nonempty string | `can_create`; protected redefine confirmation when applicable |
| Clear Command | Explicit `""` | `can_create`; protected redefine confirmation when applicable |

The distinction is load-bearing: `SetCronJob` selects authorization from **command presence** at `service.go:3860` and invokes the protected redefine guard at `:3867–3870`. The UI deliberately mirrors this at `cron-deploy-section.tsx:40–49,101`. Simply removing `|| null` while keeping both current caller arguments unchanged would turn a commandless Schedule edit into an explicit command write, changing authorization and confirmation requirements.

**Scoped fix:** allow a nullable/optional command at the hook boundary and forward it unchanged. Have Schedule save keep its current behavior: send the persisted trimmed nonempty command, or null/omitted when none exists. Have Command save send the normalized edited string, including `""`. Preserve the current schedule-on-command-bearing capability policy rather than broadening this fix into a role change.

There are **two production calls to the backend `SetCronJob` verb**: `apps/graphql.go:1406` and shared `ServicePatch` application at `apps/settings.go:211`, which carries the REST/MCP patch surface. Keep the backend, REST, GraphQL, MCP, shared string helper, and operator contracts unchanged.

**Pre-settle and errors:** `cron-deploy-section.tsx:38,74,101` disables both controls while schedule is null. Invalid schedules continue to block Save. A failed mutation returns false and retains the edit; forbidden, not-found, network/timeout, and unauthenticated handling remain on their existing paths. `withProtectedRetry` (`features/services/lib/protected-confirmation.ts:63–75`) must retry the same explicit empty command with only the returned confirmation added. Dismissal retains the blank draft without a success toast. No new read or existence disclosure is introduced.

## Closed 2026-09-22

Fixed at the two places the note identified, and only those. The backend, REST/GraphQL/MCP surfaces, the shared string helper and the operator are untouched — the dashboard simply reaches the contract that was already there (`apps/service.go`'s nil-means-keep / nonnil-empty-means-clear, proven by the existing `TestSetCronJobClearsCommand`, re-run green).

- **`use-cron-job.ts`** — `command` is now `string | null` and is forwarded unchanged. `command || null` collapsed three distinct intents into two: keep (`null`), replace (nonempty), and **clear** (`""`) all had to survive, and the third was being rewritten into the first.
- **`cron-deploy-section.tsx`** — the Command row forwards exactly what the user left behind, including `""`. Schedule save now sends `null` when there is no stored command and replays the trimmed stored command when there is.

That second half is the note's load-bearing constraint, and removing `|| null` alone would have broken it: `SetCronJob` selects its authorization from **command presence**, so a commandless reschedule sending `""` would have become an explicit command write, requiring `can_create` and the protected-environment handshake for what is a plain settings change. A test asserts `null` — not `""` — is what a commandless reschedule sends, and it fails if the caller is reverted.

Coverage, all mutation-checked (reverting either half fails them):

- `use-cron-job.test.ts:54` — the test that **asserted the defect** ("converts an empty command to null") is replaced by explicit-empty-preserved, plus a separate null-preserved control.
- Protected retry for an explicit clear: the refusal is answered and the mutation re-sent with the **same** `command: ""` and only `confirm` added — the retry is the call that actually persists, so this is where a lost clear intent would surface. Dismissal returns false with no success toast and no error toast.
- `cron-deploy-section.test.tsx` gains five tests: clearing sends `""`; whitespace-only also sends `""` (the shared row trims); a commandless reschedule sends `null`; a command-bearing reschedule still replays the trimmed command; and a failed clearing save keeps the blank draft open for retry.

`yarn tsc --noEmit`, `yarn lint`, and the full `yarn test` are green (437 files, 3638 tests); `go test ./internal/apps/ -run TestSetCronJobClearsCommand` green.

**Owed to a live pass:** the note's DoD — repeat Edit command → clear → Save on a disposable cron, confirm `command: ""` on the wire and an empty row after reload, and re-run the nonempty positive control. The note's remaining unverified list (repo-backed/native cron, role-restricted and protected-environment saves live, alias entrypoints, REST/MCP clearing) stands as written; the whitespace-only case and the protected-retry path are now covered at the component/hook level rather than being owed.

**Explicitly not claimed:** that a cleared cron then runs its image's own command. That is the operator's `cronPodSpec` fallback behaviour, which this note deliberately did not change or verify, and neither does this fix.
