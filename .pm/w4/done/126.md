# The `host` filter suggests one of the three hosts a service actually serves, because its values come from `Status.URLs` while the filter matches the log line

Why: `logLabelValues(label:"host")` is answered from the App's own `Status.URLs` while `logs(host:…)` matches inside the log line, so the two sets can disagree — and on a real production service they do, by two hosts out of three, leaving traffic a user can filter but never discover.

Found by live `/qa-find-bugs` 2026-09-21 pass 139 (w4-targeted, `muse.env` credentials), journey 7. Entirely read-only — no fixtures were created.

## What the service actually serves

`beancount-forum` (`srv-d9nqg9dcavls73fp8m2g`) answers on **three** platform hosts. `curl` from outside the browser, with an unrouted host as the control:

```
beancount-forum.onbex.co    /  → 404 len=12   /forum → 200 len=212720  text/html
tianpan-forum.onbex.co      /  → 404 len=12   /forum → 200 len=222822  text/html
blockeden-forum.onbex.co    /  → 404 len=12   /forum → 200 len=220218  text/html
nosuch-qa-20260921.onbex.co /  → 404 len=19   /forum → 404 len=19      text/plain
```

The 12-byte 404 is the application's own (Discourse serves under `/forum`); the 19-byte one is Traefik's `404 page not found`. So all three hosts are genuinely routed, and the control proves the difference is observable.

The request logs agree. Parsing `RequestAddr` out of 100 request lines for this one resource:

```
beancount-forum.onbex.co   82 lines
tianpan-forum.onbex.co     12 lines
blockeden-forum.onbex.co    6 lines
```

…and all 100 name the same backend — `KubernetesServiceName: tea-d98210cbbpdc73dcrkvg-beancount-forum`, `ServiceAddr: 10.244.34.108:3000`, namespace `tea-d98210cbbpdc73dcrkvg` — so this is one service behind three Ingresses, **not** log misattribution across services or tenants. That was checked first, because it would have been the more serious finding.

## The divergence

```graphql
logs(resource:"srv-…", type:"request", host:["tianpan-forum.onbex.co"])   → 50 lines, all that host
logs(resource:"srv-…", type:"request", host:["blockeden-forum.onbex.co"]) → narrows correctly too
logs(resource:"srv-…", type:"request", host:["nope.example.com"])         → 0, honest empty

logLabelValues(resource:"srv-…", label:"host") → ["beancount-forum.onbex.co"]     ← one of three
```

The filter accepts values the suggester will never offer.

## Mechanism

`lego/backend/internal/logs/service.go:727-731`:

```go
if label == LabelHost {
	// `host` is not a stream label (the cardinality budget keeps it in the line),
	// so its values come from the App itself — which is why it resolves even with
	// no store wired.
	return core.HostsFromURLs(app.Status.URLs), nil
}
```

`lego/backend/internal/logs/loki.go:128-133` says the same from the other side: _"`host` never reaches here — it is answered from the App's own URLs, not from a stream label."_

Every other discoverable label goes to Loki and therefore reflects the data — which is why they are complete and correct here: `statusCode` returned 13 distinct values, `method` 5, `type` 2, `instance` 1, `level` 1. `host` is the only one whose suggestions come from a different source than the thing being filtered.

The decision to keep host out of the stream labels is sound and reasoned (cardinality). The gap is that nothing reconciles the two sources, so the suggester silently under-covers.

## Where a user hits it

Not the Logs tab — its dropdowns are `level`, `instance`, `method`, `statusCode` only (`dashboard/src/features/logs/types.ts:61-64`). It is the **Metrics** host dropdown: `dashboard/src/features/metrics/api/metrics.graphql:44` records that it "is discovered via the logs `logLabelValues(label:"host")` read". So per-host charts for `tianpan-forum` and `blockeden-forum` cannot be selected, though their traffic is real and is already being counted somewhere in the totals.

## Fix

Two directions, and the second needs diagnosis first:

- **Make the suggestion reflect the data.** Derive host values from a bounded scan of recent lines (the same range the query already has) and union them with `Status.URLs`, so a host that is serving traffic is always offerable. The cardinality argument is about stream labels, not about a bounded read.
- **Or fix whatever makes `Status.URLs` incomplete** — see Unverified. If `Status.URLs` were right, today's implementation would be right with it.

Estimate: ~30m for the union approach plus a test that a host present only in the lines is still suggested.

## Unverified

- **Why `Status.URLs` holds one host is not diagnosed.** `AppSpec.EffectiveHosts` (`lego/types/v1alpha1/app_types.go:878-898`) returns `Host` + the platform subdomain + `Hosts`, and `setStatusURLs` (`operator/.../app_controller.go:2722-2729`) writes all of them — so if the other two hosts were in this App's spec they should already be in `Status.URLs` and in REST `urls`. They are not (`urls: ["https://beancount-forum.onbex.co"]`, `customDomains` empty). The Ingress names in the log lines are `tea-…-blockeden-forum` and `tea-…-tianpan-forum`, which is **not** how the operator names an Ingress for an App called `beancount-forum` — so these are most likely hand-applied Ingresses pointing at the service, outside the App spec, which bex has no obligation to report. Confirming that needs cluster access this hunt does not have. **If it turns out they are spec-derived, this note is the wrong fix and the `Status.URLs` projection is the bug.**
- Whether the metrics host dropdown is the only consumer was not swept beyond the one `metrics.graphql` reference.

## Also checked this pass, and found correct

Journey 7's log half is in good shape; recording it so it is not re-run:

- **Every filter narrows and the invalid cases are principled.** `type:"app"` / `"request"` partition cleanly; an unknown type errors with `unknown log type "banana" (want app|request|build|predeploy)`; `statusCode:["404"]` returns only 404s; `method:["POST"]` only POSTs; an unknown method or level returns an honest empty page (they are label matches, so empty is right, while `type` is an enum, so erroring is right).
- **`level` is honest about a service with no levels.** `logLabelValues(label:"level")` returns exactly `["unknown"]`, and `level:["unknown"]` returns 50 rows all of `type: "app"` — so the earlier-looking "level filter returns nothing" is the data, not the filter.
- **An unknown label is named rather than answered emptily**: `unknown log label "path" (want host|instance|level|method|statusCode|type)`, with the site's comment explaining that an empty list would read as "this service has no such values".
- **Limits clamp to the shared bound**: `limit:101` and `limit:5000` both return 100; `limit:0` and `limit:-5` fall back to the default 20 rather than erroring or returning everything.
- **Ranges narrow, invert safely, and fail loudly**: a one-minute window returned 37 lines all inside it with `hasMore:false`; a future window returned an honest empty; an inverted range gives `startTime must be before endTime`; `startTime:"yesterday"` gives the exact Go parse error naming the expected layout.
- **Pagination walks backwards without gaps** — `nextEndTime` is exactly 1ns before the page's earliest line, and entries are ascending within a page.
- **Request-log rendering is verbatim by design, not an oversight.** The dashboard shows the raw Traefik JSON line, and `log-line-list.test.tsx:79` pins that (`expect(screen.getByText('{"RequestPath":"/health"}'))`). Worth a product decision rather than a bug report, with one thing to weigh: the raw line carries `KubernetesIngressName`, `KubernetesIngressNamespace`, `KubernetesServiceName`, `RouterName` and the pod `ServiceURL` into a tenant-facing view.

## Closure — diagnosed 2026-09-22

Closed as a coverage record with its proposed fix withdrawn: the note's own unmanaged-Ingress caveat is confirmed. Read-only production inspection found `spec.host` and `spec.hosts` absent and `status.urls` containing only `https://beancount-forum.onbex.co`. The `tianpan-forum` Ingress was created 2026-08-09 by `kubectl-client-side-apply`, which owns both its rules and its App owner reference; the reference therefore does not prove operator projection. Both extra Ingresses route to the beancount-forum Service.

This is already documented manual routing: `docs/drills/2026-08-21-datastore-namespace-cutover-prep.md:62` explicitly preserves the three extra Ingresses; `docs/runbooks/datastore-namespace-cutover.md:177` calls resolving them a product/ops decision. `EffectiveHosts` and `setStatusURLs` correctly project the managed App contract. No cluster objects were changed.

The traffic observations and QA coverage above remain valid. Extending suggestions to unmanaged request hosts is a separate product enhancement, not evidence of a broken status projection; a bounded line scan would also provide sampled rather than complete discovery. No implementation or production routing change is warranted by this finding.
