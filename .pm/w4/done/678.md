# 678 — Any empty bucket can be deleted while an upload into it is still in flight, which silently orphans that upload. For `render-<region>` this always happens on the next Render CLI call: the bucket comes back under a new id, and a presigned PUT minted before the delete writes under the old id, where no API lists, reads or deletes it and the sweep still bills it

Why: Contract A's `render-<region>` bucket is the Render CLI's whole namespace. A customer (or a teammate with `can_create`) who runs `wrangler r2 bucket delete render-oregon` on an empty namespace gets `200`. The next `render ea objects` call recreates the bucket with a new `obk-` id. Any upload through a presigned URL minted before the delete (valid 15 min) still answers `200 OK` from Wasabi, but lands under the old id:

- `list` does not show it.
- `get` answers `404 object not found`, and `delete` cannot reach it.
- The hourly sweep counts it as `orphan:` usage against the workspace's quota and storage meter.

That is silent data loss that keeps being billed. Render has no way to delete this namespace, and an R2 bucket that is deleted makes later puts fail instead of vanish.

- **Mechanism:**
  - `MintPut` (`lego/backend/internal/objectstorage/objects.go:65-101`) signs a URL for `Prefix(workspace, systemBucket.ID)+key`, valid `PresignTTL = 15 * time.Minute` (`limits.go:75`). The bytes then go straight to Wasabi, and bex never sees the upload.
  - `DeleteBucket` (`service.go:163-185`) checks emptiness with one `ListObjectsV2` and deletes the row. It has no notion of outstanding presigned URLs, and it treats system buckets like any other ("ADR112 is silent on deleting a system bucket, so it follows the same rule", `service.go:160-162`).
  - An upload after the delete therefore writes under an id with no row. The sweep files it under `OrphanBucketID` (`sweeper.go:74-90`, `:278-331`), which still feeds the quota gate (`quota.go:55-77`) and the storage meter.
- **The same race on named buckets (Contract B):** `PutStream` (`stream.go:138`) resolves the bucket row before streaming up to 300 MiB through bex-api. A concurrent `DeleteBucket` that lists before the stream's first part lands can delete the row mid-stream. Same orphan; *cause unverified*, reasoned from the code only.

## Fix

Target behavior: an upload through any URL bex minted, or any stream bex accepted, either lands in a bucket the customer can still list, read and delete, or fails. It never succeeds into a prefix no row maps.

1. **System buckets are not deletable.** `DeleteBucket` refuses a `system` row before listing, answering Cloudflare `403 10003` with the message "render-<region> is the Render CLI's object namespace and cannot be deleted". wrangler prints `errors[0].message`. Contract A has no delete for the namespace, as on Render.
2. **Named buckets (Contract B):** close the check-then-delete window.
   - `DeleteBucket` first marks the row `deleting` (under the workspace's object-bucket lock, `lockObjectBuckets`), then lists, then deletes.
   - `PutStream` refuses a row marked `deleting` before its first byte, and re-reads the row after the stream completes. If the row is gone, it deletes the object it just wrote and answers `404 10006`.
3. **Tests (mock cluster / `fakes3`):**
   - A `render-oregon` delete answers 403, and a Contract A put minted before a delete attempt still lists afterwards.
   - A Contract B stream racing a delete either 404s with no object left behind, or completes with the bucket kept.
   - Regression: deleting an empty named bucket still answers 200, and a non-empty one still answers `409 10008`.

## Definition of done

- `DELETE https://api.bex.co/cloudflare/client/v4/accounts/<tea>/r2/buckets/render-oregon` answers `403` with code `10003`, and `render-oregon` keeps its `creation_date` and `dev-url get` `bucketId` across the call.
- The racing-stream test above passes, and fails with the `deleting` mark removed.

**Unverified:** the orphan itself, on production, and the Contract B stream race.

**Render:** Render has no buckets. `render ea objects` has no way to delete its namespace, so refusing the delete is parity. R2 (the Contract B reference) requires an empty bucket and gives a put after the delete `NoSuchBucket`, never a silent success.
