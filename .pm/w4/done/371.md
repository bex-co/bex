# 371 — Deleting a missing Postgres user on a real database reads as a bare "not found"

Why: w4/154 named every missing child of an existing **service** (`env var not found`, `secret file not found`, …), but the Postgres user child was never in its scope: `DELETE /v1/postgres/{db}/users/{missing}` on an authorized, existing database answers the neutral `not found`, indistinguishable from a missing database.

**Severity:** minor. **Estimate:** ~20m.

**Source:** live `/qa-find-bugs w4` loop run 47, 2026-10-20 UTC, `muse.env`, workspace `bex-canary`, on the run's own free Postgres `dpg-dbbdet54c21c738t0700` (created, probed, deleted this run; session revoked).

## Probes (production, session-authenticated REST)

- `POST /v1/postgres/{db}/users {"name":"qa_reader"}` → `201` (password returned once, not recorded here).
- Duplicate create → `400 user "qa_reader" already exists` (named, correct).
- `DELETE /v1/postgres/{db}/users/qa_reader` → `204`.
- `DELETE /v1/postgres/{db}/users/nope_user` → `404 {"code":"NOT_FOUND","message":"not found"}` — bare, on a database that exists and was authorized.
- Controls from earlier runs on services: `DELETE …/env-vars/NOPE` → `env var not found`; `DELETE …/secret-files/nope.txt` → `secret file not found`; deploy detail miss → `deploy not found`.

## Root cause

`DeleteUser` (`lego/backend/internal/postgres/access.go:203-218`) fetches and authorizes the parent database (`fetchDatabase(ctx, core.RelCanCreate, name)`), then returns the bare sentinel at `:218` (`return core.ErrNotFound`) when the role is absent from `spec.users`. The w4/154 fix converted the service-child sites to `core.NotFound("<child>")` (`lego/backend/internal/core/errors.go:556`); the Postgres access path was outside its `{jobs,secrets,apps}` grep scope. The REST route is `DELETE /v1/postgres/{id}/users/{user}` (`lego/backend/internal/postgres/rest.go:382-385`); GraphQL/MCP user-delete surfaces share the verb.

## Fix (target behavior)

- Return `core.NotFound("user")` at `access.go:218` (message `user not found`), keeping 404 / `id: not_found` and the `errors.Is(err, core.ErrNotFound)` chain unchanged. A missing or unauthorized **database** keeps the neutral parent answer, so this never becomes an existence oracle.
- Check the sibling read path for the same child (retrieve/list single user, if routed) and name it identically.

## Acceptance

- Replaying the probe: deleting a missing user from an existing database returns `404` with message `user not found`; deleting from a missing database still returns the bare `not found`.
- One regression test beside the existing postgres access tests asserting both messages.
- `cd lego/backend && go test ./internal/postgres/...` passes.

## Out of scope

- `core.ErrNotFound` for an unprovisioned connection secret inside the SQL/insights paths (`lego/backend/internal/postgres/query.go:214,235`, `insights.go:417`): a provisioning-state answer for an existing database, not a named-child lookup; not probed live as a defect here.
- w4/154 itself is done and stays closed; this is its Postgres remainder.

**DONE 2026-10-20 (loopx w4).** `DeleteUser` (`lego/backend/internal/postgres/access.go:218`) now returns `core.NotFound("user")` for a role absent from `spec.users` — message `user not found`, same 404 / `NOT_FOUND` code and `errors.Is(err, core.ErrNotFound)` chain; a missing or unauthorized database keeps the bare parent answer (verified by test), so it is not an existence oracle. REST, GraphQL (`graphql.go:660`), and MCP (`mcp.go:418`) all share this verb, so one fix covers every surface. Sibling-read check: no single-user read route exists (only `ListUsers`, parent-scoped), so there was nothing else to name.
