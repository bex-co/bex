# Eight form fields show a visible validation message that assistive technology never receives: the input is `aria-invalid` but the message has no id, no `aria-describedby` and no live region

Why: a screen-reader user who types a bad name into New Key Value or New Web Service hears the field is "invalid" and nothing else, so they cannot tell what to fix; sighted users read "Enter a name of up to 100 characters, without line breaks or control characters." directly under the field (WCAG 3.3.1 Error Identification, 4.1.3 Status Messages). This is the class behind w4/m101/t012 and w4/098, which each fixed or noted one form.

Source: live `/qa-find-bugs w4` loop run, round 14, 2026-11-02 UTC (`muse.env`, QA workspace `bex`; read-only, typed into forms and never submitted, no write request sent). Severity: minor (accessibility; nothing is lost). Estimate: 1h (8 field sites + one shared-pattern test); promote to a milestone if sized above that.

## Repro (https://dashboard.bex.co, desktop)

1. `/keyvalue/new`: type three spaces in the Name field `#kv-name`.
2. `/services/new?type=web_service`: choose Public Git URL, type three spaces in `#svc-name`.

| error text | "Enter a name of up to 100 characters, without line breaks or control characters." |

Controls on the Add Custom Domain dialog (`/services/srv-dbavjsm05jqs73cjk3og/settings`), typing `not a domain` (client-side check, no write sent):

- It sets `aria-invalid="true"` and `aria-describedby="custom-domain-invalid"` pointing at the message, so it is linked, but the message has no role and focus stays on the "Add Domain" button, so it is silent until the field is focused.
- The same field's server-error path, `custom-domains-section.tsx:678-684`, renders `<p id="custom-domain-error" role="alert">`. So one field announces one error and not the other (lines 670-676 vs 678-684).

## Root cause (read from source; the two forms above also confirmed live)

`dashboard/src/routes/keyvalue.new.tsx:163-170` renders `<Input aria-invalid={showNameError}>` followed by `<p className="text-sm text-destructive">` with no id and no `aria-describedby`; the same shape is in the other 7 files.

Counts from grep over non-test `dashboard/src` (excluding `common/components/ui/`): 26 files set `aria-invalid`.

**Class A, the message never reaches assistive technology.** 8 files contain neither `aria-describedby` nor `role="alert"` nor `aria-live` anywhere (only the first two were exercised live):

- `routes/keyvalue.new.tsx`
- `routes/services.new.tsx`
- `features/workspaces/components/workspace-details-card.tsx`
- `features/databases/components/access-control-panel.tsx`
- `features/env-groups/components/env-group-actions.tsx`
- `features/services/components/create-secret-file-editor.tsx`
- `features/services/components/create-env-var-editor.tsx`
- `features/services/components/service-source-picker.tsx`

**Class B, read only once the field is focused.** 4 more files have `aria-describedby` but no live region (read from source, not probed live), plus the custom-domain client path above:

- `features/databases/components/create-database-dialog.tsx`
- `features/ssh-keys/components/ssh-keys-panel.tsx`
- `features/services/components/static-site-section.tsx`
- `features/services/components/editable-field-row.tsx`

The convention already exists in the repo: `common/components/text-field.tsx:45-48` pairs `aria-invalid` with `<p role="alert">`, 36 non-test files use `role="alert"`, and the invite-member dialog is the reference the SSH-key fix (w4/m101/t012) copied. But only 3 files render `<TextField`, and just 1 of the 8 class-A files imports it.

## Fix

Target behavior: wherever a field is marked `aria-invalid` with a visible message, the message has a stable id that the input lists in `aria-describedby` AND is announced when it appears: either `role="alert"` on the message (the existing convention, `text-field.tsx:48`) or focus moved to the first invalid field on a blocked submit, not both (no double announcement). Prefer one shared field-error helper or `TextField` over eight hand-edits so the pattern cannot drift. Message text and visuals must not change.

- **Blast radius:** the 8 class-A files, the 4 class-B files, and the custom-domain client path. The 14 files that already combine `aria-invalid` with a live region are correct today and need regression tests (their current tests must stay green); the 3 existing `TextField` users must not gain a second `aria-describedby`.
- **Adjacent classes:** disabled-submit forms (New Web Service and New Key Value both disable their submit while invalid, probed live: "Deploy Service" and "Create Key Value Instance" are `disabled`) give a keyboard user no focusable place to learn why. That is a separate decision (Render uses disabled submits too) and is not part of this note. Toasts and server errors already use `role="alert"` and are out of scope.
- **Unverified:** the other 6 class-A sites and all 4 class-B sites live; screen-reader output (I inspected attributes only, not a real assistive technology); the web-service Git URL, branch and port fields on `/services/new`, which have their own validation.
- **Render:** Render's forms tie inline errors to their fields and announce them (standard); verify wording against the live Render dashboard before copying.
