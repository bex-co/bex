# 492 — GraphQL answers `200` with `"internal error"` / `INTERNAL` when `operationName` does not select exactly one operation (several operations and no name, or an unknown name), instead of a request error

Why: a client that forgets or mistypes `operationName` is told the platform failed ("internal error", code `INTERNAL`, no location), which sends it to retry or to file a server bug, when the answer is a plain "name the operation you want"; graphql-go already produces that exact message and bex's error redaction throws it away.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-05 (`muse.env`, workspace `bex`; read-only `POST https://api.bex.co/graphql` from the dashboard page with `fetch(..., {credentials:'include'})`, 450 ms apart); **minor** (a client-input error reported as a server error; no data exposed or changed); ~30m.
- **Probe** (document `query A { viewer { id } } query B { viewer { id } }` unless stated; the single-operation row uses `query A { viewer { id } }`; `viewer` is any field the caller may read):

  | `operationName` | Document | Status | First error |
  | --- | --- | --- | --- |
  | _(omitted)_ | two named operations | 200 | **`"internal error"`**, `extensions.code: "INTERNAL"`, `locations: []` |
  | `""` | two named operations | 200 | the same |
  | `"Nope"` | two named operations | 200 | the same |
  | `"Nope"` | one operation `A` | 200 | the same |
  | `"A"` | two named operations | 200 | data for `A` |
  | `"B"` | two named operations | 200 | data for `B` |
  | `7` (a number) | one operation | 400 | JSON decode error (the body type is checked before GraphQL runs) |
  | _(omitted)_ | one anonymous operation | 200 | data |

  Other request-shape failures in the same sweep answered correctly: no credentials 401, empty or non-JSON body 400, a batch of 100 operations 400, `GET /graphql` 405, more than 10 aliases, selection nesting above 15, a fragment cycle and a body above 2 MiB all rejected with a specific message or status (`413` for the body).

- **Root cause (both halves read):**
  - graphql-go v0.8.1 `buildExecutionContext` (`executor.go:109-143`) returns plain `errors.New("Must provide operation name if query contains multiple operations.")` and ``fmt.Errorf(`Unknown operation named "%v".`, …)`` for these two cases. They are not a `gqlerrors.Error` with a location; `FormatError` wraps them with `OriginalError` set and no locations, which is why `locations` is empty in the probe.
  - `sanitizeGraphQLErrors` (`lego/backend/internal/api/server.go:1779-1814`, one non-test caller at `:1716`) treats an error as a pure parse/validation error and keeps its message only when `OriginalError()` is nil. Anything with an original error that is not a public error (`core.IsPublicError`) or a deadline exceeded is logged as `bex-api graphql: internal error: …` and rewritten to `"internal error"` with `extensions.code = core.CodeInternal`. The two executor errors arrive with a non-nil original error, so they take that path.
  - So the user-facing text graphql-go wrote ("Must provide operation name …", "Unknown operation named …") is exactly what the redaction was built to hide for resolver failures, and it hides it here by accident.
- **Fix (target behavior):**
  - The operation-selection failure answers a request error, not `INTERNAL`: the message graphql-go produced (`Must provide operation name if query contains multiple operations.` / `Unknown operation named "Nope".`) with `extensions.code` equal to the code the other client-input GraphQL errors use (`BAD_USER_INPUT` if `core` already defines it; otherwise the validation code `sanitizeGraphQLErrors` leaves on pure validation errors), HTTP status as the neighbours answer (the GraphQL-over-HTTP precedent is `400` for a request that cannot be executed; bex answers `200` with an `errors` array for validation errors today, so follow that for consistency and say so in the change).
  - Do it in `executeGraphQL` (`server.go:~1670-1727`) before `graphql.Do`: parse once (or use the parse result `Do` produces) and check the selection there, so the classification does not depend on matching graphql-go message text. If matching the message is the only option, pin it with a test against the vendored version so an upgrade that rewords it fails loudly rather than silently reverting to `INTERNAL`.
  - Resolver failures that are genuinely internal keep `internal error` / `INTERNAL`, and public errors keep their message and code.
- **Blast radius:** `sanitizeGraphQLErrors` has 1 non-test caller and `executeGraphQL` 2 (`grep -rn 'sanitizeGraphQLErrors(\|executeGraphQL(' --include='*.go' lego/backend/internal/api`). Every GraphQL client (the dashboard, the CLI's GraphQL calls, third-party tools) reaches it. The dashboard's Apollo client sends `operationName` for every named operation, so the matching case is the one that matters for non-regression; add a test that a named operation in a multi-operation document still executes. REST and MCP do not use this path.
- **Adjacent classes:** unauthenticated stays `401` and a malformed body stays `400`, both decided before the operation is selected; a scope-restricted API key sending an unknown `operationName` is still checked by `requireGraphQLScopeFrom` (`api/scope_matrix.go:310`), which inspects every operation when the name does not match, so the new error must not become a way to skip the scope check; a mutation with a bad name must not execute any operation.
- **Unverified:**
  - The exact `extensions.code` used for other client-input errors (read `core/errors.go` before choosing); this note does not assume `BAD_USER_INPUT` exists.
  - Whether the log line `bex-api graphql: internal error: Must provide operation name …` appears on each such request (probable from the code path, not read from the server log), which would also count these requests as server errors in any log-based alerting.
  - MCP/REST are unaffected by construction; not probed.
  - Render: Render's public API is REST, so it has no counterpart; the reference is the GraphQL specification (a request error for an operation that cannot be selected).
- **Dedupe:** `grep -rli "operationName\|operation name" .pm` finds nothing on this behavior. w4/053 (metrics input answering "internal error") and w4/490 (path ids answering 500) are the same family on other routes; this one is the GraphQL entry. Nothing in `.pm/DO_NOT_DO.md` applies. The fix is not on `main`.
