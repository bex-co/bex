# w4/194 — `DELETE /v1/api-keys/{id}` returns 403 for the caller's own key unless `?ownerId=` names its workspace

Why: revoking a leaked key is the one API call that must work first time. Today a multi-workspace user's REST/CLI revoke of their own key "fails" with a bare `forbidden`, the key stays live, and nothing says why.

Live 2026-10-04 UTC (`/qa-find-bugs` loop14, muse.env). The QA user belongs to `bex` (default), `tian-personal` and `bex-canary`. Keys `qa-20261004-l14-key2`/`-key3` were created in `bex-canary` (`tea-daif693dqjvc73e7as3g`); all are revoked now.

- `DELETE /v1/api-keys/<key2 id>` (no `ownerId`) → **403** `{"error":"forbidden"}`. The key stayed listed and its client credentials still exchanged at `oauth.bex.co` (200) and called the API (200).
- `DELETE /v1/api-keys/<key2 id>?ownerId=tea-daif693dqjvc73e7as3g` → **204**, and the key disappears from `GET /v1/api-keys?ownerId=…`.
- Control (key3, with `ownerId`): before revoke 200; revoke 204; the old access token gets **401 at +0 s**; re-exchanging the credentials gets **401**. Revocation itself is immediate and correct. The dashboard's Revoke button also works (it passes the workspace).
- Also verified working: a bex-canary key sees only bex-canary in `/v1/owners`, and gets 403 on listing, reading or reading env vars of a `bex`-workspace service.

Root cause: `lego/backend/internal/apikeys/service.go:456-476` `RevokeAPIKey` scopes to `core.WithWorkspace(ctx, ownerID)`, the request's `ownerId` or else the caller's **default** workspace. It then returns `core.ErrForbidden` when `Binding.TenantForKey(id)` (already known) differs from that workspace. The REST route forwards an optional `?ownerId` (`internal/apikeys/rest.go:53-58`).

Fix: when `ownerId` is absent, resolve the workspace from the key's binding (`TenantForKey`) and authorize `RelCanManageKeys` on **that** workspace, as env groups do (`envgroups.fetchGroup`) and w4/m169 does for Blueprints.

- Keep a supplied-but-mismatched `ownerId` as today.
- Adjacent classes: a key in a workspace where the caller lacks `can_manage_keys`, or isn't a member, should return the same 404 as an unknown id. Today it's 403 vs 404, which reveals that the key exists elsewhere; key ids are UUIDs, so the oracle is weak but free to close.
- Check GraphQL/MCP revoke for the same default-workspace scoping.
- Tests: revoke without `ownerId` for a non-default-workspace key → 204; non-member → 404; mismatched `ownerId` → 404/403 unchanged.

Unverified: GraphQL and MCP revoke without an owner (not probed). Render: API keys are user-scoped and revoked from the dashboard (n/a for REST). Severity: minor. Estimate: ~40m.

Hunt note: this run leaked one 26-character client secret for a QA key into the session transcript (a redaction regex sized for 30+ characters). That key (`qa-20261004-l14-key`) was revoked minutes later through the dashboard and is no longer listed.

Done 2026-10-04 (loopx). `RevokeAPIKey` now picks its workspace through `revokeScope` (`lego/backend/internal/apikeys/service.go`): an explicit `ownerId` or a workspace the request already names still decides (a mismatch stays 403), but with neither, a bound key resolves its own workspace from `TenantForKey` and `can_manage_keys` is authorized there. A non-member or a member without `can_manage_keys` gets the same 404 as an unknown id. GraphQL `revokeApiKey`, MCP `revoke_api_key` and the CLI self-revoke all call this one function, so all surfaces are fixed together. `TestRevokeAPIKeyWithoutOwnerResolvesKeyWorkspace` covers a no-`ownerId` revoke of a second-workspace key (204, unbound), a non-member, a viewer and an unknown id (404), and a named mismatched workspace (403). A mutation check confirms that both 404 cases fail on the old mapping. Backend suite + `make lint` green. Live replay not run.
