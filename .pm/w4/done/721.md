# A managed Postgres logs each statement that runs longer than 2 seconds, as on Render

Why: Render's Postgres logs have a `duration:` line for each slow query, which is where a user debugging a slow app looks first. bex's have none unless the user sets a parameter override. Found by w4/m553 t002 on 2026-11-22 from Render's changelog of 2023-06-30 ("We now log when a query takes longer than 2s") ([disposition table](../../docs/render-artifacts/render-changelog.md)).

- **Render:** [render.com/docs/postgresql-creating-connecting](https://render.com/docs/postgresql-creating-connecting) says "Queries that take longer than 2 seconds are logged with a line that starts with `duration:` followed by the SQL statement."
- **bex:** the operator's default parameters are `pg_stat_statements.track=all`, `log_lock_waits=on` and `max_connections` (`lego/operator/internal/controller/database_controller.go`). `log_min_duration_statement` can be set only as a tenant parameter override (`lego/types/v1alpha1/database_types.go`).
- **End state:** a new and an existing database log a statement that runs past 2 s with Render's `duration: … ms  statement: …` line in its Logs (REST, GraphQL, MCP and the dashboard), and a faster one does not. A user's own override still wins. An operator test covers the default and the override.

**Done 2026-11-23.** The operator now sets `log_min_duration_statement=2000` beside `log_lock_waits=on`, under the tenant's legacy `spec.parameters`. A declared value in any spelling replaces the default rather than sitting beside it (`database_controller.go`). `TestClusterSpecLogDefaults` covers both defaults and their overrides on both operands, and it fails without the change.

- **Existing database.** The check ran on the local CAPD cluster with the operator built from this change. An existing dev-4 database adopted the setting with no restart: the postmaster start time, the pod uid and the restart count were all unchanged. It logged `duration: 2505.841 ms  statement: …` for a 2.5 s `pg_sleep`, and nothing for a 1.2 s one.
- **New database.** A free database (disposable) logged `duration: 2204.260 ms  statement: select …` for a 2.2 s statement, and nothing for a 1.5 s one. The line read the same on REST `GET /v1/logs`, GraphQL `logs`, MCP `list_logs` and the dashboard's Logs tab, at 1440 and 390.
- **Read path.** dev-N's log shipper ships only `type=app`, so these reads went through a second dev-4 bex-api that reads the pods directly. The production shipper path is covered by `tenant-log-lines.json` instead. The captured record was added there, and both Go direct reads keep it with its statement text. `gitops.yml` runs the shipper's Alloy pipeline on the same table (`scripts/test_log_shipper.py`); that run could not finish locally, because the pinned Alloy image was downloading at about 120 KB/s.
- **Docs.** [ADR009 § Slow statements are logged](../../../docs/ADR009-postgresql-management.md#slow-statements-are-logged-w4721), the ADR018 Postgres log history row, `postgres-logs.md`, and the changelog row for 2023-06-30, now `matched`.
