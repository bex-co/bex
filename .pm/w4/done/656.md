# 656 — The secret-files quota refusal carries no `code`, while sibling secret-file refusals carry `SECRET_FILE_INVALID`

Why: clients key refusals on codes; w4/m363's 1 MB refusal is uncoded on every surface.

- **Source / estimate:** follow-up from w4/m363 (2026-11-14). **Minor**. ~20m.
- **Fix:** give it a stable code (Render's, once observed; else a bex code recorded in ADR018) on REST, GraphQL and MCP.
- **DoD:** an over-quota write answers the code on all three surfaces.
- **Closed 2026-11-14 (/loopx w4):** the map quota refusals are coded: `SECRET_FILE_LIMIT` for the secret-files count and 1 MiB contents bound, `ENVIRONMENT_VARIABLE_LIMIT` for the env-var map, both with params `maxCount` and `maxBytes` (`secrets.mapQuota.check` builds a `core.NewBadRequestError`, so every writer, service and group, answers it on REST `code`, GraphQL `extensions` and the MCP prefix; the message drops the `bad request: ` sentinel prefix, as every coded refusal does). Render's code was never observed, so the codes are bex's, recorded in ADR006 and ADR018's Secret files row. Tests: `secrets.TestPatchEnvironmentQuotaRefusalIsIdenticalAcrossAdapters` and `envgroups.TestEnvGroupPatchQuotaRefusalIsIdenticalAcrossAdapters` now pin the code on all three surfaces; backend `GOWORK=off go test ./...` passes.
