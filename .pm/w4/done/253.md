# A parameter refresh silently discards an unfinished edit after another tab saves

Why: a normal saved-value refresh erases the customer's unsaved database tuning work and removes the Save/Discard controls without an explicit choice.

**Severity:** major — lost form input. **Estimate:** 55m (shared-call audit 10m, guarded editor synchronization 15m, parent-level behavior tests 20m, Simplify and owned live replay 10m). **Status:** open. Source: functional `$qa-find-bugs w4`, pass a166, 2026-10-11 UTC, muse.env login helper.

Goal: dependable managed hosting and configuration editing ([ADR008](../../docs/ADR008-vision.md), [ADR009](../../docs/ADR009-postgresql-management.md)). This restores an existing editor journey; no new database capability is needed.

## Reproduction and target

1. Create an owned Free private PostgreSQL 18 database. Open its **Insights → Parameter overrides**. This pass used `qa-20261011-a166-params`, `dpg-db5k9o0mmd8c73drring`, created at 08:12:16.541Z and Available before the first parameter save.
2. Add `work_mem=8MB` and `random_page_cost=1.25`, then **Save overrides**. The UI and API return the saved declarations. Observed `8192 kB` is the correct normalized `8MB`; it is not a mismatch.
3. In tab A change work_mem to **16MB**, leaving it unsaved. Save is enabled and Discard changes is present. An unchanged-spec poll at 08:17:47.003Z preserves that draft and those controls.
4. Open the same owned database in normal tab B. Save **12MB** there, retaining random_page_cost. Immediately afterward tab A still shows its **16MB** draft. Without Save or Discard in A, it subsequently shows **12MB**, Save is disabled, Discard is gone, and no alert or notification explains the loss.
5. Fresh-load A at **390×844**. It starts from saved 12MB; draft **20MB** locally. B saves **24MB** at 08:18:44.307Z. A immediately still has 20MB and both draft controls; by the next follow-up it has 24MB, disabled Save and no Discard. The follow-up listener was installed after this replacement had already occurred; it is not the exact transition capture.
6. Repeat at **1440×1000** with a listener installed in A before B's save. A drafts **28MB**; B saves **32MB** at 08:19:35.186Z. A still has 28MB, enabled Save and Discard at 08:19:35.192Z. Its normal poll returns saved 32MB at 08:19:49.555Z. At 08:19:49.558Z A shows **32MB**, disabled Save, no Discard, no alert and no toast.

**Target:** an automatic saved-value refresh preserves dirty rows and their local input. An untouched editor adopts the latest saved rows. Explicit Discard restores the latest saved set, and an acknowledged local Save updates its baseline. During a pending refresh keep the current editor and draft visible; observation-only changes continue to update the diagnostics without resetting local edits. Reset state when the database identity changes. Preserve the existing full-set replacement contract; this item does not add a server revision or cross-client compare-and-swap contract.

## Root cause and bounded fix

- `dashboard/src/features/databases/hooks/use-database-insights.ts:89–94` polls the declared set every 15 seconds while visible. `:105–109` saves the complete set and refetches both declared and observed reads.
- `dashboard/src/features/databases/components/insights-panel.tsx:316–323` keys ParameterOverridesEditor by the saved names and values. A new saved value changes that key.
- `parameter-overrides-editor.tsx:89–93` initializes local rows and savedRows from the latest props. A new instance loses the old local rows. `:102–103,292–294,302–314` derives dirty/Save/Discard from that freshly equal pair, so the customer cannot recover the lost draft.
- The installed and lockfile-resolved **react-dom 19.2.3** `cjs/react-dom-client.production.js:3808–3866` matches children by key, deletes a mismatched old child and creates a new fiber. `:4765–4780` initializes the new state hooks. The [primary React state-preservation documentation](https://react.dev/learn/preserving-and-resetting-state#option-2-resetting-state-with-a-key) describes the same key reset. The symptom follows the application key choice; no React defect is claimed.
- Replace the saved-value key with stable database identity and synchronize saved props inside the editor with a dirty guard. Simply deleting the key is incomplete: the existing state initializers would then leave pristine rows stale. Keep a current saved baseline for explicit Discard and successful Save, without overwriting dirty rows on refresh. Use existing translations unless new explanatory copy is necessary.

The backend response is correct. `lego/backend/internal/postgres/insights.go:656–699` reads the declared set and produces name-sorted values plus point-in-time observations. REST `rest.go:429`, GraphQL `graphql.go:443` and MCP `mcp.go:506–509` expose that same read. REST and GraphQL were live-read in this pass; MCP was traced but not live-called. No transport or operator change is required.

## Controls, dedupe and parity

Removing random_page_cost at 08:20:44.076Z sends only work_mem=32MB. REST and GraphQL return that one declaration at 08:21:02Z; SQL at 08:21:16.336Z returns **32MB / 4**, confirming the removed cost returned to its default while work_mem remained. Clearing all at 08:21:29.680Z sends an empty set. REST returns [] and SQL at 08:22:01.640Z returns **4MB / 4**; the UI shows the empty-declarations message with disabled Save. These controls isolate local draft loss from persistence or PostgreSQL application failure.

Open and done board searches for the editor, parameter overrides and draft/refresh terms found no scheduled item covering a changed saved set discarding dirty rows. The **74 open/blocked README** scan also found no owner. [w4/m132](done/m132/README.md) covers observations and preserves an unchanged declared-set draft; that control passes here. [w6/m133](../w6/done/m133/README.md) established the declared/observed separation; retain it. [w4/238](238.md) covers Top queries geometry and is separate. The source key is still present on current main; targeted history and the latest dashboard/lego commits show no pending fix. No anti-goal applies.

Render's [Postgres documentation](https://render.com/docs/postgresql) documents the managed database surface, but the equivalent signed-in parameter editor and concurrent-tab behavior were not observed. This is a reproducible Bex lost-input finding; no authenticated Render parity failure is claimed. Keep the existing API semantics and diagnostics.
