## Objective

The ⌘K global search input has **no** accessible name, and the cause is subtler than a missing attribute: cmdk points the input's `aria-labelledby` at a label element the app never fills, which suppresses the placeholder fallback that would otherwise have named it. The obvious fix — adding `aria-label` — does not work.

## Context

### The observation (production, 2026-09-13)

`⌘K` from any page, then `await page.locator('[role=dialog]').ariaSnapshot()`:

```text
- dialog "Search":
  - heading "Search" [level=2]
  - paragraph: Search dashboard pages and workspace resources.
  - combobox [expanded]                     ← no name
  - listbox "Suggestions":
    - group "Navigation": …
```

Probed directly:

```js
{ tag: "INPUT", role: "combobox",
  ariaLabel: null,
  labelledby: "radix-_r_6_",
  labelledText: "",                          ← the target element is EMPTY
  placeholder: "Search pages and resources…",
  hasLabelEl: true }
```

The dialog is named and described; only the control a screen-reader user actually types into is anonymous.

### The mechanism, read from the pinned dependency

`cmdk@^1.1.1` (`dashboard/package.json:72`; installed `dashboard/node_modules/cmdk/dist/index.mjs`):

- the `Command` root **always** renders its label element, filled from its own `label` prop:

  ```js
  t.createElement("label", { "cmdk-label": "", htmlFor: U.inputId, id: U.labelId, style: Te }, b)
  ```

  (`Te` is the visually-hidden style; `b` is the `label` prop.)

- the `Input` **unconditionally** sets `"aria-labelledby": b.labelId`.

The app never passes `label`, so that element renders empty and the input's accessible name computes from an empty `aria-labelledby` — which, per the accname algorithm, takes precedence over `placeholder`. So the placeholder that would have named the control is actively suppressed. An empty `aria-labelledby` target is worse than no labelling at all.

### Why `aria-label` is the wrong fix

`aria-labelledby` wins over `aria-label`. Adding `aria-label` to `CommandInput` would change nothing in the tree — this is the trap to avoid, since it is the first thing anyone will try and it will look like a fix in the diff while the a11y tree stays bare. The correct fix is cmdk's own `label` prop on the `Command` root.

### The wrapper currently cannot express that fix

`dashboard/src/common/components/ui/command.tsx:24-39` — `CommandDialog` is typed `DialogProps & { shouldFilter?: boolean }` and spreads `{...props}` onto **`<Dialog>`**, not onto `<Command>`. A `label` passed by a consumer would land on the Radix dialog and be dropped. So the fix has two parts: plumb a `label` through `CommandDialog` to `Command`, and pass it at the call site.

### Blast radius — exhaustive

`grep -rn "CommandInput" dashboard/src | grep -v __tests__ | grep -v "ui/command.tsx"` → exactly **one** production mount: `dashboard/src/common/components/dashboard-layout/global-search-dialog.tsx:65`. `CommandDialog` likewise has one consumer. The fix is confined; no allowlist question.

## Steps

1. Widen `CommandDialog` to accept and forward a label to `Command` (cmdk's `label` prop), rather than spreading it onto `Dialog`.
2. Pass a translated label at `global-search-dialog.tsx:65` — the existing `common.topbarSearch` key is already used for the `sr-only` `DialogTitle` at `:61` and reads correctly for the input too; decide whether to reuse it or add a dedicated key, and keep the placeholder as the placeholder.
3. Verify in the real tree, not the DOM: `ariaSnapshot()` must show `combobox "…"` with a name. Confirm the `aria-labelledby` target is now non-empty rather than that an `aria-label` appeared.
4. Assert with `getByRole("combobox", { name: … })` inside the dialog. A test that finds the placeholder text would pass today and prove nothing.
