## Objective

A static site's custom header rules reach only its successful and redirected responses. Every error the site serves — 404, 400, 413, 502, 503 — carries none, so a `/*` security or CORS header the customer configured is absent from exactly the responses an attacker or a browser is most likely to see unprotected.

## Context

### The observation (production, 2026-09-13)

Static site `qa-0913b-static` (`srv-daj7r28gsm7s73f63o20`, repo `github.com/bex-co/bex`, root `examples/static-site`, publish `.`), one saved redirect rule (`Redirect /old-path → /`) and one saved header rule (`path=/*`, `X-Qa-Marker: qa-20260913b`):

```text
$ curl -sSI https://qa-0913b-static.onbex.co/
HTTP/2 200
content-type: text/html
x-qa-marker: qa-20260913b          ← present

$ curl -sSI https://qa-0913b-static.onbex.co/old-path
HTTP/2 301
location: /
x-qa-marker: qa-20260913b          ← present

$ curl -sS -D - https://qa-0913b-static.onbex.co/nope.html
HTTP/2 404
content-type: text/plain; charset=utf-8
x-content-type-options: nosniff
content-length: 10
                                    ← absent
not found
```

`/nope.html` matches `/*`. The UI's own copy on the Headers tab is _"Custom response headers added to responses whose path matches."_

### The code says "every response" and does not do it

`lego/operator/internal/staticserver/staticserver.go:215-218`:

```go
// requestPath is the visitor's normalized path and stays immutable: custom
// headers match against it on every response (Render's request-path
// contract, w4/m94), while the (possibly rewritten) served path drives
// origin keys, content type, and the default cache policy.
```

`applyHeaders` (`:513-519`) has exactly two production call sites — the redirect branch (`:265`) and `serveObject` (`:344`). `grep -n "http.Error\|WriteHeader" lego/operator/internal/staticserver/staticserver.go` gives all ten response sites:

| line | status | site resolved? | applies headers |
| --- | --- | --- | --- |
| 205 | 405 method not allowed | **no** (precedes `Resolve`) | no — correct, no rules exist |
| 211 | 404 unknown host | **no** | no — correct, no rules exist |
| 262 | 400 invalid redirect target | yes | **no** |
| 265→266 | 301 redirect | yes | yes |
| 273 | 404 overlong key, no rule | yes | **no** |
| 281 | 404 rewrite target overlong | yes | **no** |
| 303 | 404 miss after rules + SPA fallback | yes | **no** |
| 311 / 314 / 316 (`serveOriginError`) | 413 / 503 / 502 | yes | **no** |
| 334 | 503 live-body shed | yes | **no** |
| 344→346 (`serveObject`) | 200 | yes | yes |

Six resolved-site response classes apply nothing.

### Why m94 is not the owner of this

`w4/m94` fixed object-vs-rule precedence and made headers match the immutable request path. Its t003 audit recorded "applyHeaders has two [production calls] (redirect and success)" as existing state to preserve while changing precedence, and its DoD states "The live hunt did not exercise origin errors". So the error classes were knowingly out of its scope — this is a gap beside m94's fix, not a regression of it. m94's request-path contract (headers match the visitor's path, the served path drives content type and cache) must keep holding after this change.

## Steps

1. Decide, per class, whether custom headers apply — and write the reasoning into the code where the next reader will find it. A defensible default: **every response served for a resolved site applies them** (that is what the comment at `:215-218` already claims, and what the UI promises), including 404 and the origin-failure classes. The two no-site responses (`:205`, `:211`) stay headerless because there is nothing to match against — and that is a distinction worth stating, since the alternative would need a site lookup to answer a request for a host bex does not serve.
2. Watch the disclosure question on `:211` specifically: applying anything host-derived to an unknown-host response would turn it into an existence oracle. Leave it as it is, and say so.
3. Implement it. `http.Error` writes `Content-Type`, `X-Content-Type-Options` and the status itself, so custom headers must be set on `w.Header()` **before** the `http.Error` call. Prefer one helper (e.g. an `errorf(w, site, requestPath, status, msg)` seam) over six scattered `applyHeaders` calls, so the next response class added cannot forget.
4. Protect the error body's integrity. A rule named `Content-Type`, `Content-Length`, or `Transfer-Encoding` must not make an error response lie about what its body is. Decide whether such names are skipped on error paths (recommended) or refused at write time in the API, and cover it with a test either way.
5. Keep `Retry-After` on the 503 paths (`:313`, `:333`) intact — a custom rule must not clobber it, or ordering must put the platform's value last.
6. Re-probe live: one static site, one `/*` rule, then `curl -sSI` a missing path, and record the output here.
