## Objective

The dashboard offers a cron job a Scaling tab and a working autoscaling editor. Two sibling gates in the same two files already get this right for manual scaling and for Disk; apply the same gate to the autoscaling card and the nav entry.

## Context

### The card escapes a gate that is right next to it

`dashboard/src/routes/services.$serviceId.scaling.tsx:40-58`:

```tsx
// Only service types with a replica concept scale manually — cron jobs have
// no long-running pods and static sites serve from the object store (the
// same gating the Settings page applies to its scaling-adjacent rows).
const scalable =
  service != null && !isCron(service) && !isStaticSite(service);

return (
  <div className="space-y-6">
    <AutoscalingSection autoscaling={autoscaling} />      {/* :47 — ungated */}
    {scalable && autoscaling.loading && <CardSkeleton rows={2} />}
    {scalable && !autoscaling.loading && !autoscaling.enabled && (
      <ManualScalingSection … />                          {/* :51-58 — gated */}
    )}
    <ScalingRecentMetrics serviceId={serviceId} />
  </div>
);
```

`<AutoscalingSection>` sits **above** the `scalable` gate. The comment's reasoning — "cron jobs have no long-running pods" — applies to autoscaling at least as much as to manual scaling.

This is also why `w4/043`'s claim that "Static and cron are excluded by `services.$serviceId.scaling.tsx:42-44`" read as true: it is, for the manual card only. That sentence was accurate for 043's scope; it is not a statement about the autoscaling card.

### The nav has the same shape, with an explicit precedent it did not follow

`dashboard/src/features/services/components/service-nav.tsx:107-115`:

```tsx
// Disk is type-gated to exactly what the API accepts — web, private, and
// worker (validateDisk in lego/backend/internal/apps/disks.go). A cron job
// has no long-running instance to mount a volume on, so offering the tab
// there would lead to an Add Disk button that always 400s.
const diskEligible = type === "web" || type === "private" || type === "worker";
const manageTail =
  type === null ? [] : [...(diskEligible ? [DISK] : []), SHELL, SCALING, PLAN];
```

`DISK` is gated with a written rationale; `SHELL` and `SCALING` are in `manageTail` for every non-static type. A static site takes the separate `type === "static"` branch (`:87-96`) whose comment says it "has no runtime Logs/Shell/Scaling/Plan" — so static is already right, and **cron** is the gap.

`SHELL` on a cron job is a different case and should be left alone: it is offered, but it renders an honest explanation — _"Shell access isn't available. Shell access requires a running paid web, private, or background service and an active SSH gateway."_ (verified live this run). That is the second acceptable pattern for an ineligible surface, and it is why this task is about Scaling specifically.

## Steps

1. Move `<AutoscalingSection>` inside the type gate, or give it its own gate derived from the same predicate t001 settles on in the backend. Keep the two in agreement — if t001 decides workers are eligible, the UI must not hide it from workers.
2. Decide between the two established patterns for the Scaling surface on an ineligible type, and say which:
   - **remove the nav entry** (Disk's pattern — the tab does not exist); or
   - **keep the tab and explain** (Shell's pattern — the page states why scaling does not apply to this type).
   Shell's pattern is friendlier for a user who arrives by URL or bookmark; Disk's is less surface. Either is defensible; pick one and apply it consistently to both the nav and the route.
3. Whichever is chosen, the route must behave when reached **by direct URL**, not just via nav — a static site's nav already omits Scaling, yet `/services/<static-id>/scaling` would still render the ungated card today.
4. Specify the pre-settle state. `service` is `null` while the type query is in flight and `type === null` already suppresses type-specific nav entries; make sure the autoscaling card does not flash for a cron job before the type resolves (the same "must never flash a Deploys tab" rule the nav comment states at `:97-102`).
5. Verify at desktop and narrow-mobile widths that removing the card does not leave a gap or shift the Recent Metrics panel (per `dashboard/CLAUDE.md`'s skeleton/geometry rule).
