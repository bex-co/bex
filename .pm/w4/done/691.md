# 691 — A cron job's run meters about 45 s more `instance_seconds` than it ran, because the meter credits every terminated pod 45 s past its last sample

Why: Render bills a cron job per second of run time. A 50 s run metered as 95 s overbills short cron jobs by about 90%, and it holds w4/m322's DoD 3 (±15 s per run) open.

- **Source / severity / estimate:** w4/m322 t004 replay, `/loopx w4` 2026-11-16. **Major** for billing accuracy on short runs; negligible for long-lived services. More than an hour, because it is a meter-design change; promote it if the chosen fix spans tasks.
- **Evidence** (production, pin `3c6654df60a2`, workspace `bex-canary`, fixtures since deleted):
  - Cron A ran three manual runs of 49 + 50 + 50 = 149 s. `GET /v1/usage` metered 285 s.
  - Cron B (30-character name) ran 50 + 50 + 49 = 149 s and metered 270 s.
  - Both total about run time + 45 s per run, which is the designed tail: `instanceLivenessSeconds = 59` with 15 s steps credits a terminated pod three steps past its last sample (`lego/backend/internal/usage/service.go`, w5/m111).
  - Raw cAdvisor samples per 50 s run, read with read-only Prometheus queries: three samples spanning 29–43 s, with 11–25 s between them.
  - kube-state-metrics' `kube_pod_status_phase` is scraped every 60 s. Gating the meter on `phase="Running"` metered 60 s for the 149 s, so it is not a fix either.
- **Candidate fixes** (pick the one that matches Render's per-second run billing):
  1. **Meter cron Apps from run facts.** Use each run's `startedAt` and `finishedAt` (`recordCronRunFacts` / `GET /v1/cron-jobs/{id}/runs`), clipped to the hour. This matches Render's basis exactly.
  2. **Trim the tail with a look-ahead.** Credit a step only when the pod also reports in the following 59 s, or reported in the last 15 s. Needs the rollup to run at least 59 s after the hour closes, or a continuously running pod loses its last minute.
- **End state:** a cron job's run meters within ±15 s of its duration from `GET …/runs` (w4/m322 DoD 3). A web service's hourly `instance_seconds` does not change.
- **Dedupe:** w5/m111 (done) chose the 59 s bound for always-on pods. w4/m173 (blocked) owns repairing the arithmetic of past rows. w4/580 (blocked) measures the run time that was never metered before w4/m322.

**Done 2026-11-16 (`/loopx w4`):** candidate fix 1. A cron App's `instance_seconds` is now each run's own `startedAt`→`finishedAt` clipped to the hour: finished runs from the `cron_job_run_*` facts (`store.CronRunsOverlapping`), plus `status.runs` for a run in flight (`usage.queryCronRunSeconds`); web services keep the pod measure unchanged. `TestCronInstanceSecondsMeterRunTime` pins the replay's three runs at 149 s (the pod path read 3600 against the same fake Prometheus). The cron branch of the zero-degrade check (w4/m322) is gone with the pod path it guarded. A deleted cron App's final hour still meters from pods (its retired record carries no type). The live ±15 s check stays w4/m322 DoD 3 (t004) once this deploys. ADR023 amended.
