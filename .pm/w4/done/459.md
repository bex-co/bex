# Closing a plain (form) dialog drops keyboard focus to the page body: 30 of 32 `<Dialog>` sites are controlled, render no trigger, and nothing restores focus

Why: a keyboard or screen-reader user opens New Project, New Environment Group, New Environment or Add Custom Domain, presses Escape or Cancel, and lands on `<body>`; their next Tab restarts from the sidebar, so they must walk the page again. WAI-ARIA dialog guidance returns focus to the invoking control. This is the sibling of w4/408, which fixed only `ConfirmDialog`.

Source: live `/qa-find-bugs w4` loop run, round 12, 2026-11-01 UTC (`muse.env`, QA workspace `bex`; read-only: dialogs opened and closed, nothing submitted). Severity: minor (keyboard accessibility, nothing is lost). Estimate: 45m.

## Repro (https://dashboard.bex.co, desktop)

## Root cause

- `dashboard/src/features/projects/components/new-project-dialog.tsx:70-76` and `features/environments/components/new-environment-dialog.tsx:65-71` render `<DialogTrigger>` only when `controlled` is false (`{controlled ? null : <DialogTrigger …>}`). Every caller passes a controlled `open` (`routes/index.tsx:367`, `routes/env-groups.tsx:130`, `features/environments/components/environments-panel.tsx:325`), so Radix has no trigger to restore focus to.
- The shared `dashboard/src/common/components/ui/dialog.tsx` `DialogContent` has no `onCloseAutoFocus`.
- `confirm-dialog.tsx:156-162` (w4/408) already solves this for AlertDialog: it remembers the last focused element and re-focuses it if still connected. The plain Dialog never got that.
- Counts from grep over non-test `dashboard/src`: 32 plain `<Dialog` sites in 29 files; 30 pass `open=`; 9 files contain `<DialogTrigger` (the ones I probed still render no trigger because their caller is controlled); 27 files have `open=` with no `onCloseAutoFocus`. `onCloseAutoFocus` appears only in `confirm-dialog.tsx`, `ui/command.tsx` and `global-search-dialog.tsx`.

## Fix

Target behavior: when any plain Dialog closes by Escape, Cancel, or overlay click, focus returns to the element that had focus when it opened, if it is still in the document. If the action removed it (create then navigate, delete), normal navigation focus applies and nothing is forced.

Do it once in the shared `DialogContent`, or in a small shared hook that `ConfirmDialog` also uses (replacing its own copy), so all 32 sites are covered. Trigger-based sites must keep Radix's own restore and not double-focus.

- **Blast radius:** every `DialogContent` consumer (29 files), including `sheet.tsx`, which shares the same Radix primitive and was not probed. Regression tests are needed on the trigger-based path that is correct today (Invite, API-key create, registry credential create), on a closed-by-navigation create (New Project), and on an opener that unmounted.
- **Adjacent classes:** `ConfirmDialog` (done, w4/408), global search (w4/291) and the command palette (`ui/command.tsx` passes its own handler) keep their handlers. Select, DropdownMenu and Popover are Radix-owned and out of scope.
- **Unverified:** the other 25 plain-dialog sites individually (read from the shared component, not probed live), Sheet panels, and a screen-reader announcement on return.
- **Render:** Render's dialogs return focus to the opening control (standard dialog behavior).

## Dedupe

grep of `.pm` and `docs` for return/restore focus found w4/408 (`ConfirmDialog` only; its blast-radius scan counted `<ConfirmDialog` sites and did not include `<Dialog`) and w4/291 (global search). No item covers the plain Dialog primitive, so this is the sibling class, not a duplicate. Evidence is the probe table above; screenshots are session-local.

## Done 2026-11-02 (loopx w4)

Shared `DialogContent` (`ui/dialog.tsx`) remembers the last element focused outside any dialog (document-level focusin) when the content opens and returns focus to it on close unless the caller prevents it or the opener was removed; trigger-based dialogs land on the same element, so there is no double focus. `ConfirmDialog` keeps its own handler. Tests in `ui/__tests__/dialog.test.tsx`; dashboard suite green (5734).
