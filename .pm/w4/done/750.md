# Every native service last built before the Ghostscript-fixed common image is rebuilt, or its owner is told the cutoff, as Render did for Upload2Shell

Why: Render parity and security. Render patched the Ghostscript its native runtime ships and told customers to redeploy any service not deployed since 2026-11-20 20:00 UTC. bex's common image carried the vulnerable package until 2026-11-21, and a native service built before then still runs it, with no rebuild and no notice.

- **Render (read 2026-11-27):** [advisory-upload2shell](https://render.com/docs/advisory-upload2shell): "check whether your service has deployed successfully at least once since November 20, 2026 20:00 UTC … If not, redeploy".
- **bex:** the common image ships Ghostscript (`deploy/native-base/install.sh`). Its image's SBOM shows `10.0.0~dfsg-11+deb12u8` in the pin from `71914199f9` (2026-11-16) and the fixed `deb12u9` (Debian DLA-4914-1) from `0f4ab445b0` (2026-11-21) on (`lego/operator/internal/build/nativebases.go`). The last `platform-rebuild.yml` run was 2026-11-19T08:08Z, before the fix. [ADR060](../../docs/ADR060-build-worker-reliability-and-performance.md) still records `deb12u8`.
- **Do:** find when production first ran a pin carrying `0f4ab445b0`, list the native services whose current image predates it, and run `platform-rebuild.yml` for them (or all). Correct ADR060's version line. Tell the owners through the advisory practice of `w4/749`.
- **End state:** no running native service's image carries Ghostscript `deb12u8`, checked from the images' SBOMs or `dpkg -s ghostscript` over SSH on a sample, and ADR060 names `deb12u9`.
- **Size:** about 45m.
- **Source:** w4/m688 t002, a full read of Render's advisory-upload2shell page, 2026-11-27.

## Outcome (2026-11-27, `/loopx w4`)

Done. One running service carried `deb12u8`, and it now runs `deb12u9`. Nothing of another tenant's ran or could resume on it, so no owner had a redeploy to make.

- **Fix and cutoff.** The CVE is CVE-2026-125396 ("Upload2Shell"). Debian fixed it for bookworm in `10.0.0~dfsg-11+deb12u9` (DLA-4914-1), and the security tracker lists `deb12u8` as vulnerable. The image SBOMs agree with the note: the common image pinned until `0f4ab445b0` (`sha256:4b8096…`) carries `ghostscript`, `libgs10`, `libgs10-common` and `libgs-common` `deb12u8`. The pin `0f4ab445b0` set (`49dbbd…`) and today's (`9c3fac…`) carry `deb12u9`, and no later commit went back. Production first ran a pin carrying `0f4ab445b0` with `a4db56cd97` (pin of `7e481dece7ac`, 2026-11-21T15:35:58Z), and the operator rolls out 2–4 minutes after a pin. That makes bex's cutoff 2026-11-21T15:36Z, against Render's 2026-11-20 20:00 UTC. Ghostscript entered the native image on 2026-10-29 (`710a57a9e3`), so a build from before then carries none.
- **What ran it.** Three checks were run on production. The first was a read-only `/api platform-rebuild --since 2026-11-21T16:00:00Z`, with the cutoff rounded up so that a build during the roll counts as pending. The second classified every running tenant image in the registry by its layers, against the old and the fixed common images (18 images). The third ran `dpkg-query` inside bex's own pods. The results:
  - `tianpan-v4-web` (`tian-personal`) was built on 2026-11-20 and ran `deb12u8`. It was the only running image on the old base.
  - `block-eden-mono-1` (`bex`) was pending in the plan, but its 2026-10-30 Go image has no Ghostscript.
  - Two customer services (keyed hashes `ws#880210` and `ws#23759a`) were pending, but neither has ever had a live deploy (every deploy is `build_failed`). Nothing of theirs runs, and their next successful build starts from the fixed image.
  - One suspended customer native service runs nothing. Its artifact is from 2026-10-08, before Ghostscript was in the image.
- **Rebuild.** `platform-rebuild --apply --limit 2` opened deploys only for the two first-party services. The limit and the order were chosen so that no customer service could be rebuilt, and the batch refused the customer service it reached ("no live deploy to restart") before changing anything. `dep-dc4gf3uiskfc73d4gme0` (`block-eden-mono-1`) and `dep-dc4gf4eiskfc73d4gmeg` (`tianpan-v4-web`) went live at 04:38Z and 04:43Z.
- **End state, 2026-11-27T04:45Z.** `dpkg-query` in the new `tianpan-v4-web` pod reads `deb12u9` for all four packages, and `/healthz` answers 200. The image sweep finds 16 running images: none on the old base, 4 on the fixed one and 12 with no common image. The plan has 5 done and 2 pending, and the 2 pending are the customer services with no live deploy.
- **Docs.** ADR060's Ghostscript row names `deb12u9`, the fix and the cutoff. The `advisory-upload2shell` row in `docs/render-artifacts/docs-pages.md` stays `partial`: what remains is the public advisory, which `w4/749` owns. That advisory has no affected customer workspace to email for this fix.
