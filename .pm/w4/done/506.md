# 506 — The shell-ticket and native SSH refusals answer one sentence, "service is not eligible and running", for a Free plan, a suspended service, a static or cron service, and a service that is not running yet

Why: the Shell journey promises that it either attaches or fails with a real reason. Four different blockers, each with a different remedy (upgrade the plan, resume, use another service type, wait), come back as the same `409` text, so an API, MCP or `ssh` client cannot tell which one to fix.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 99, 2026-11-05 UTC (`muse.env`, `bex-canary`); **minor** (copy of a refusal; the dashboard already explains the Free-plan case inline, see w4/m183); ~30m.
- **Probe:** two owned web services from `examples/hello-go`, `qa-20261105-shfree` (`srv-dbmeu7crv9ic73d23gg0`, plan `free`) and `qa-20261105-shpaid` (`srv-dbmeu84rv9ic73d23gi0`, plan `starter`), both deleted at the end of the round. Requests from the signed-in page, `POST /v1/services/<id>/shell-ticket`:

  | Service state | Status and body |
  | --- | --- |
  | `free`, deploy `created` (not running yet) | `409 {"error":"conflict: service is not eligible and running","id":"conflict","message":"conflict: service is not eligible and running"}` |
  | `starter`, deploy `created` (not running yet) | the identical `409` body |
  | `free`, deploy `live`, instance running | the identical `409` body (also with `?instance=<id>-nonexistent` and `?instance=srv-00000000000000000000-abc`) |
  | `starter`, deploy `live` | `201 {"ticket":"…","url":"wss://ssh.bex.co/shell","expiresAt":"…"}` |

  So the Free-plan refusal on a running service reads exactly like "not running yet". The suspended, static-site and cron-job cases share the same gate by code (below) and were not probed live.
  - Control: the paid service's ticket is minted, and `?instance=srv-00000000000000000000-abc` is refused `400 instance does not belong to this service`. The ticket for `?instance=<id>-nonexistent` is also minted (`201`), by design: the doc comment on `CreateShellSession` says the gateway re-validates the instance. I did not open the gateway websocket.
- **Root cause:** `sshSessionReady` (`lego/backend/internal/apps/service.go:1292-1297`) folds `!sshEligible(v)` (suspended, unknown or Free plan, or a type other than web, private service or background worker; `:1272-1286`) together with `Phase != Running`, an empty `Revision` and an empty `Image` into one `fmt.Errorf("%w: service is not eligible and running", core.ErrConflict)`. It has two callers: `ResolveSSHSession` (`:1626`, the native SSH transport) and `CreateShellSession` (`:1700`, the browser shell ticket, behind REST `POST /v1/services/{id}/shell-ticket` at `apps/rest.go:943` and the GraphQL shell-session mutation at `apps/graphql.go:1614`).
- **Fix (target behavior):** keep `409 Conflict` and the status classes, but make the message name the blocker, checked in this order, one message per cause, for example:
  - suspended: `shell access is unavailable while the service is suspended; resume it first`,
  - Free or unknown plan: `shell access needs a paid instance type; Free services have no SSH or shell`,
  - a type that has no instance to attach to (static site, cron job): `shell access is available for web services, private services and background workers`,
  - not running: `the service has no running instance yet; wait for the current deploy to go live`.
  - Both transports share the helper, so REST, GraphQL, MCP and the native `ssh` refusal move together. Do not add a new error class or change who gets the answer: `AuthorizeApp` and the protected-environment check still run first, so a caller without access never reaches these messages (`service.go:1681-1691`).
- **Tests:** a table test over `sshSessionReady` with one `AppView` per cause asserting each message and `errors.Is(err, core.ErrConflict)`; the existing shell and SSH tests stay as the success controls. `grep -rln "not eligible and running" lego dashboard/src docs` finds only `service.go`, so no test or client pins the old text.
- **Blast radius:** one helper, two callers, no other matches. The dashboard does not read this string (its Shell tab decides from `sshAddress` and `plan`, w4/m183), so there is no UI change; the Chinese dashboard catalog is not involved.
- **Adjacent classes:** unauthenticated and forbidden are decided before this gate and stay as they are; a missing service stays `404`. The gate does not disclose anything new: the plan and suspension state are already in the caller's own `GET /v1/services/{id}`.
- **Unverified:**
  - The suspended, static-site and cron-job refusals were read from code, not probed.
  - The GraphQL mutation, the MCP tool and the native `ssh` gateway text were not exercised; they are inferred from the shared helper. What an `ssh` client prints for a refused native session was not seen.
  - The websocket handshake at `wss://ssh.bex.co/shell` was not opened, so "attaches" is not verified this round.
- **Render:** Render's SSH documentation excludes Free web services; the exact wording of Render's refusal was not compared.
- **Dedupe:** w4/143 and w4/m183 (both done) made the dashboard state the Free and suspended reasons; neither touched the API refusal text. `grep -rli "not eligible and running" .pm` finds nothing. No DO_NOT_DO item applies.

Closed 2026-11-05: `sshSessionReady` (shared by `ResolveSSHSession` and `CreateShellSession`, so REST, GraphQL, MCP and native SSH move together) now names the blocker, still as a 409: suspended, then service kind with no instance (static site, cron job), then Free/unknown plan, then not running. The kind is checked before the plan (a deliberate swap of the note's order: a static site or cron job is not helped by a paid plan, and a static site has no plan). Test: `TestSSHSessionReadyNamesTheBlocker`. The suspended/static/cron refusals were not probed live, and the gateway handshake was not opened.
