## Objective

Make the managed-datastore deletion controls reflect `can_create` before interaction, including row actions and detail-page danger zones. Plan changes and suspend/resume/restart remain available because their shared Core verbs require `can_operate`.

## Context

- Postgres controls live in `database-plan-section.tsx`, `database-danger-actions.tsx`, and `database-row-actions.tsx`.
- Key Value controls live in `key-value-plan-section.tsx`, `key-value-danger-actions.tsx`, and `key-value-row-actions.tsx`.
- The backend already rejects unauthorized plan/lifecycle mutations; this task changes only the first-party presentation and pre-interaction affordance.

## Steps

1. Consume `canCreate` at the database and Key Value control boundaries.
2. Disable plan-change, delete, and other create-gated destructive controls with the shared permission tooltip/reason instead of allowing a doomed confirmation flow.
3. Preserve existing lifecycle-phase, billing, and safety-confirmation disable reasons, composing permission state without hiding more specific operational reasons from authorized users.

## Acceptance criteria

- [ ] A contributor sees plan and destructive lifecycle actions disabled with a permission reason on Postgres and Key Value list/detail surfaces.
- [ ] Disabled controls open no confirmation and issue no protected mutation.
- [ ] Authorized users retain the current phase, payment-gate, confirmation, and mutation behavior.
- [ ] Permission gating does not weaken or replace the server-side OpenFGA checks.

## Out of scope

- Changing datastore plans, lifecycle semantics, payment gating, or adding new destructive operations.
