## Objective

Thread the existing `canCreate` capability through every service and Environment Group env-var write control so a contributor can inspect permitted values but cannot enter an add, edit, delete, import, or save flow the server will reject.

## Context

- `dashboard/src/features/services/components/env-vars-panel.tsx`, `env-var-row.tsx`, and `create-env-var-editor.tsx` own the service write affordances.
- `dashboard/src/features/env-groups/components/env-group-editors.tsx` shares the env-var editing model at workspace scope.
- `dashboard/src/features/capabilities/hooks/use-capabilities.ts` and the permission-tooltip/disabled-reason primitives from `w9/m84` are the authority and presentation precedent.

## Steps

1. Read `canCreate` at the owning panel boundary and pass it to row, creation, import, and Environment Group editor controls without deriving a role locally.
2. Disable every protected write affordance with the shared permission reason while retaining read and sensitive-reveal behavior governed by their existing relations.
3. Ensure disabled controls do not open dialogs, enter row-edit mode, or call a mutation handler.

## Acceptance criteria

- [ ] A contributor sees all `can_create`-gated env-var write controls disabled with the standard reason on both service and Environment Group surfaces.
- [ ] Attempting to activate a disabled control opens no editor/dialog and sends no mutation.
- [ ] An authorized user can add, edit, delete, import, and save exactly as before.
- [ ] Reveal/copy behavior continues to use `can_view_sensitive`, not `can_create`.

## Out of scope

- Changing env-var server authorization, secret storage, wire shapes, or adding the forbidden database-link picker.
