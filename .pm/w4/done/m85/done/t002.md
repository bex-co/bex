## Objective

Apply the same viewer-capabilities contract to Build Filters so users without the mutation relation can read the configured paths but cannot edit or save them.

## Context

- `dashboard/src/features/services/hooks/use-build-filter.ts` owns the Build Filter query/mutation seam.
- `dashboard/src/features/services/components/build-deploy-section.tsx` renders the Build Filters editor with the other create-gated build settings.
- `w9/m84` already gates neighboring build/deploy fields through `useCapabilities`; this task extends that established pattern rather than adding a new permission model.

## Steps

1. Confirm the shared Core mutation uses the existing `can_create` relation and consume the already-projected `canCreate` capability.
2. Disable Build Filter inputs and save/reset affordances with the standard permission reason when false.
3. Keep the current configured filter readable and prevent disabled handlers from issuing the mutation.

## Acceptance criteria

- [ ] A contributor can read the effective Build Filters but cannot edit, reset, or save them.
- [ ] Disabled Build Filter interactions issue no GraphQL mutation and explain the required permission.
- [ ] Authorized editing and validation remain byte-identical.
- [ ] No new capability field or client-side role mapping is introduced unless the shared server relation proves different, in which case the projection is extended consistently and tested.

## Out of scope

- Changing Build Filter matching semantics, adding new filter types, or moving authorization out of the server Core.
