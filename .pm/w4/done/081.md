## The registry is complete, by enumeration rather than by pattern

`36457c620` escalates a document to `OpClassSensitive` when its selection set names a field in:

```go
var graphQLSensitiveNestedFields = map[string]struct{}{
	"envVar":     {},
	"secretFile": {},
}
```

The definitive question is whether a **third** nested field could return a secret. A nested GraphQL resolver can only reach data through a reader the composition root attaches to the context. Enumerate those:

```text
grep -rn "^func .*From(ctx context.Context)" lego/backend/internal/core/*.go | grep -v _test   → 10
```

Of the ten, seven are identity/workspace plumbing (`IdentityFrom`, `SubjectFrom`, `WorkspaceFrom`, `resolvedWorkspaceFrom`, `ActingTenantFrom`, `ConfirmFrom`, `FreshBearerValidatorFrom`). **Three** are data readers:

| reader | nested resolvers | returns a secret? |
| --- | --- | --- |
| `core.EnvVarsFrom` (`core/envvars.go:60`) | `envVarKeysResolve` (`apps/graphql.go:691`), `envVarValueResolve` (`:703`) | keys-only / **value** |
| `core.SecretFilesFrom` (`core/secretfiles.go:54`) | `secretFileNamesResolve` (`:727`), `secretFileContentResolve` (`:739`) | names-only / **value** |
| `core.OutboundIPsFrom` (`core/outboundips.go:54`) | the service's egress IP list | **no** — public infrastructure detail, rendered in the dashboard's own Networking panel |

So exactly **two** nested resolvers return a secret, and the registry's two entries are exactly those. A third could only appear by adding a fourth context reader or by routing an existing one into a new field — which is what the guard heuristics `36457c620` added to `scope_matrix_guard_test.go` are there to catch.

This closes the limit both prior sweeps recorded: `w4/m106`'s Query-side walk (pass 26) and `w4/080`'s credential-word walk (pass 28) each matched **field names**, and each said so. This one matches on **capability**, and agrees with both.

## The walk resists the three evasions worth trying

Read from `scope_matrix.go:348-380`:

- **Aliasing does not evade it.** The check is `graphQLSensitiveNestedFields[n.Name.Value]`, and in `graphql-go`'s AST an alias lives in `n.Alias` while `n.Name` stays the schema field. `{ service(id:…){ x: envVar(key:"K"){ value } } }` still matches `envVar`.
- **Fragments do not evade it.** `walkGraphQLSensitiveNested` recurses through `*ast.InlineFragment` and fragment spreads with a `visiting` cycle guard, and `selectedGraphQLOperations` applies the same named-op/multi-op rules as the top-level collector — so a sensitive selection cannot hide in an unnamed sibling operation.
- **Introspection fields are skipped** (`strings.HasPrefix(n.Name.Value, "__")`), which is correct: they carry schema, not data.

## The depth cap is defense-in-depth, not a fail-open hole

`walkGraphQLSensitiveNested` stops at `maxGraphQLSensitiveWalkDepth = 64` and returns **false** — i.e. "no sensitive selection", which is the fail-**open** direction. That looks like a hole: nest `envVar` below depth 64 and the escalation never fires.

It is not reachable, because a separate limiter rejects the document first:

```go
// lego/backend/internal/api/graphql_cost.go:46-54
gqlMaxDepth      = 15   // nesting depth
gqlMaxAliases    = 50
gqlMaxFields     = 2000
gqlMaxOperations = 10
gqlMaxAliasesPerField = 10
```

**15 < 64**, so any document deep enough to hide a field past the walk's cap is refused for depth before it can execute — and the ordering does not matter, since both checks must pass for the request to run. Whoever revisits this should **not** "fix" the 64 by raising it or by flipping the default to sensitive; the margin is deliberate headroom under a tighter external bound. If `gqlMaxDepth` is ever raised above 64, this stops being true — that is the coupling to watch, and it is worth a comment linking the two constants.
