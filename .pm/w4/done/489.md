# 489 — An `ownerId` containing a NUL byte or invalid UTF-8 answers `503 authorization service unavailable` instead of a 4xx, on routes that name a workspace

Why: a value the caller typed wrongly (or a probe) is reported as the platform's authorization service being down, which is a server-side status class that availability alerts and client retry loops act on, and it hides the real answer ("that is not a workspace id").

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-05 ~00:55 UTC (`muse.env`, workspace `bex`, read-only GETs); **minor** (fail-closed: every one of these requests is denied, nothing is exposed or changed; the defect is the status class and message); ~30m.
- **Probe** (in-page `fetch(..., {credentials:'include'})` against `https://api.bex.co`, spaced 400–500 ms after a 70 s cool-down, so the 503s are not rate-limit side effects; base request `GET /v1/services?limit=1&ownerId=<value>`; the caller's own default workspace `tea-d98210cbbpdc73dcrkvg` answers `200`):

  | `ownerId` (URL-encoded) | Status | Body |
  | --- | --- | --- |
  | `%00` | **503** | `{"error":"authorization service unavailable","id":"unavailable","message":"authorization service unavailable"}` |
  | `a%00b` | **503** | the same |
  | `tea-d98210cbbpdc73dcrkvg%00` (a real id plus a NUL) | **503** | the same |
  | `%C0%80` (overlong NUL, invalid UTF-8) | **503** | the same |
  | `%ED%A0%80` (a lone surrogate, invalid UTF-8) | **503** | the same |
  | `tea-nope` | 403 | `{"code":"FORBIDDEN","error":"forbidden",…}` |
  | `%01`, `a%20b`, `a%23b`, `a%3Ab`, `a%2A`, `a%40b`, `a%2Fb`, `a%25b`, `a%5Cb`, `a%22b`, `a%7Bb`, `a%09b`, `a%0Ab`, `a%0Db`, `a%7F` | 403 | the same forbidden body |
  | `t%C3%A9a` (é), `%F0%9F%98%80` (emoji) | 403 | the same |
  | 256, 257 and 2000 `x` characters | 403 | the same |

  The same `ownerId=%00` also answered `503` on `GET /v1/postgres`, `GET /v1/key-value` and `GET /v1/registrycredentials` in an earlier, faster sweep. That sweep also drew 109 `429`s from my own request rate, so the other list routes (`env-groups`, `projects`, `owners`, `blueprints`, `webhooks`, `disks`, `build-sources`, `logs`) were not confirmed either way.

- **Root cause (the exact code path is read; the driver error is inferred):**
  - A non-default `ownerId` reaches `resolveWorkspaceUncached` (`lego/backend/internal/core/base.go:747-770`). When it differs from the caller's own tenant it calls `requireMember` (`base.go:1998-2003`).
  - `requireMember` calls `Workspace.IsMember` (`api/tenancy.go:388-401`), which runs `PGStore.IsMember` (`store/store.go:878-886`): `SELECT EXISTS (SELECT 1 FROM tenant_members WHERE subject = $1 AND tenant_id = $2)` with the raw `ownerId` bound as `$2`.
  - Any error from that call is logged (`core: workspace membership unavailable: …`) and returned as `ErrAuthzUnavailable` (`base.go:2001-2002`), which renders as `503 authorization service unavailable`. A well-formed value the caller does not belong to returns `exists = false` and so `403`, which is the whole 403 column above.
  - The set that fails (NUL, overlong NUL, a lone surrogate) is exactly what PostgreSQL's `text` type refuses: it cannot hold `0x00` or bytes that are not valid UTF-8, and rejects them with an encoding error rather than a no-match. Valid Unicode, control characters other than NUL, `#`, `:`, spaces and very long values all pass, as the table shows. I could not read the server log line to see the driver's actual error, so this is the best fit to the observed set, not a quoted error.
  - Not the cause: OpenFGA. A value with a space or `#` would be an invalid OpenFGA object and would also reach `checkAuthz` (`base.go:897-918`, which maps any checker error to the same 503); those answered `403`, so they never got that far.
- **Fix (target behavior):**
  - A workspace id that is not valid UTF-8 or contains NUL is refused before any store or authorization call, with a `400` that names the parameter (`invalid query parameter "ownerId"`, the wording the request validator already uses for other malformed parameters, e.g. `quantile=abc`). The check belongs where the named workspace enters the context (`core.WithWorkspace`, 86 non-test callers) or at the top of `resolveWorkspaceUncached`, so REST `ownerId`, GraphQL `ownerId`/`workspaceId` and the MCP workspace middleware share it.
  - `requireMember` stops turning every store error into "authorization unavailable": a PostgreSQL data-exception class error (SQLSTATE `22…`, e.g. `22021`) is a client error (`403`/`400`), while a connection failure, timeout or cancelled context stays `503`. This is the general fix; the input check above is the specific one. Keep both.
  - Well-formed ids the caller is not a member of stay `403`, unchanged (no existence oracle: the check looks only at the string's validity, never at membership).
- **Blast radius:** 53 non-test `Query().Get("ownerId")` reads and 86 non-test `WithWorkspace(` callers (greps over `lego/backend/internal`), all funnelling through `resolveWorkspaceUncached`; `requireMember` has 4 callers. Regression tests belong on the callers that already answer `403` for ordinary garbage (the table's 403 rows), so the new check cannot start refusing a legal id: the real id shapes are `tea-` plus 20 base32 characters.
- **Adjacent classes:** a real database outage must still answer `503` (assert with a failing store, not only the new input check); unauthenticated stays `401`; a valid but foreign workspace stays `403`. The audit row a denied request writes (`authorizeAndAudit`) may also carry the raw value into Postgres; whether that insert fails on NUL was not probed.
- **Unverified:**
  - The PostgreSQL encoding error itself (see above); the log line `core: workspace membership unavailable: …` for a `%00` request would confirm it in one read.
  - GraphQL (`ownerId` arguments) and MCP (`workspaceId`) with the same values.
  - The routes listed above that were rate-limited in my first sweep.
  - Whether any path puts the raw value into an audit or event insert.
- **Addendum, 2026-11-05 (`GET /v1/owners/{id}`, a second mechanism for the same 503):** the path form of the workspace id skips the membership shortcut and goes straight to the authorization check. Probed 450 ms apart: `a%20b`, `a%0Ab`, `srv-%0A`, `a%23b`, `a%3Ab`, 256, 257, 300 and 3000 `x` characters all answer `503 authorization service unavailable`, while `a%2Fb` answers 403. These are values OpenFGA refuses as an object name (whitespace, `#`, `:`, more than 256 characters in `workspace:<id>`); `checkAuthz` (`core/base.go:897-918`) logs the checker error and maps every one of them to `ErrAuthzUnavailable`, exactly like `requireMember` does for the SQL error. The fix is the same family: classify a checker/store error that is a rejection of the input (OpenFGA validation 4xx, PostgreSQL data exception) as a client error, and keep 503 for a connection failure, timeout or 5xx from the upstream. The OpenFGA response itself was not read. Related but separate: w4/490 (malformed path ids that answer 500).
- **Addendum, 2026-11-05 (the same NUL in a request body):** `ownerId` is also read from the JSON body on create. A body `"ownerId":"tea-d98210cbbpdc73dcrkvg\u0000"` answered `503 authorization service unavailable` on all six create routes probed (`POST /v1/env-groups`, `/v1/projects`, `/v1/webhooks`, `/v1/registrycredentials`, `/v1/key-value`, `/v1/postgres`), 6 of 6, and nothing was created. The fix belongs at the same place (the named workspace entering the context), so it covers the body field too. Related but separate: w4/491 (a NUL in a webhook or credential **name** answers 500).
- **Render:** n/a. Render's own API answers an unknown `ownerId` with `404`/`403`; it has no authorization-service status to leak.
