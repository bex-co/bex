# 663 — While a pre-deploy command runs, the service's instance list includes the pre-deploy Job's pod: a first deploy lists an instance before anything serves, and the Web Shell picker offers it

Why: `GET /v1/services/{id}/instances` and GraphQL `serviceInstances` are Render's list of a service's running instances, and the Web Shell instance picker is built from them. During `pre_deploy_in_progress` bex adds the pod that runs the pre-deploy command. On a first deploy the list names one instance while the Shell page says "The service has no running instance yet". On later deploys it names an extra instance that disappears when the command ends. Picking it in the Web Shell cannot attach, because the shell gate only accepts pods of the serving release.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 361, 2026-11-14 13:31–13:42 UTC (`muse.env`, workspace `bex-canary`; pin `c99e7815ebec`). **Minor** (a wrong list for the pre-deploy window; the shell refuses safely). ~30m.
- **Fixture:** Starter image web service `qa-20261114-r361-sh` (`srv-dbs65glv5sfs73boald0`, `docker.io/library/nginx:1.27-alpine`, `preDeployCommand: sleep 150`), created with `POST /v1/services`. Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe (REST, polled about every 10 s):**
  - **First deploy** (`dep-dbs65glv5sfs73boaldg`, created 13:31:46): at 13:35:20, during `pre_deploy_in_progress`, `GET …/instances` → `[{"id":"srv-dbs65glv5sfs73boald0-1418pq58uihl330e46ku","createdAt":"2026-11-14T13:33:31Z"}]`.
    - At the same moment `POST …/shell-ticket` → `409 {"error":"conflict: the service has no running instance yet; wait for the current deploy to go live"}`, and the Web Shell panel showed that sentence.
    - The service's real first instance, `…-kkffe1l4a99lu3fhku85`, was created at 13:36:20, after the 150 s command. Its nginx started at 13:36:28.
  - **Second deploy** (`POST …/deploys {}` at 13:38:25, `dep-dbs68kfla3oc73cu7lbg`):

    | time (UTC) | deploy | `…/instances` (id suffixes) |
    | --- | --- | --- |
    | 13:38:36–13:41:03 | `pre_deploy_in_progress` | `dmmejl` (created 13:38:34), `fhku85` |
    | 13:41:13–13:41:24 | `pre_deploy_in_progress` | `fhku85` |
    | 13:41:34 | `update_in_progress` | `s7livf` (new release), `fhku85` |
    | 13:41:45 on | `update_in_progress`, then `live` | `s7livf` |

    `dmmejl` appeared 9 s after the deploy was created and left 150 s later, which is the pre-deploy command's lifetime. It never served: every app log line in the window came from `fhku85`, then `s7livf`.
- **Root cause:**
  - `ListInstances` (`lego/backend/internal/apps/service.go:1697-1711`) lists every pod from `OwnAppPods`, dropping only terminating, `Succeeded` and `Failed` pods.
  - `OwnAppPods` → `AppPodsIn` (`lego/backend/internal/core/base.go:2236-2253`) selects on `app.bex.co/app=<name>` alone. `DropOtherIncarnations` (`:2275-2282`) keeps an unlabeled Job pod created after the App ("Job pods carry no id").
  - The pre-deploy Job's pod carries that same label: `execution.PodLabels` (`lego/operator/internal/execution/security.go:93-111`) sets `app.bex.co/app` plus `app.bex.co/component=predeploy` (`lego/operator/internal/predeploy/predeploy.go:67`, `:182-188`). It runs in the App's namespace, so the list includes it.
  - Control, behaving correctly: `readySSHInstances` (`service.go:1904-1940`) uses the same pod list but keeps only `readyCurrentAppPod` (the serving image and revision). That is why the shell refuses, and why the list and the shell disagree.
- **Fix (target behavior):** the instance list names only the service's own runtime instances, the pods of its Deployment, on REST, GraphQL and the Web Shell picker together.
  - In `ListInstances`, skip pods whose `app.bex.co/component` is not the runtime component (at least `predeploy`). Or select on the Deployment's pod selector, as `observeServingRevision` does (`lego/operator/internal/controller/serving_condition.go:39`).
  - A first deploy in pre-deploy then lists `[]`, which agrees with the shell's "no running instance yet".
- **Blast radius:**
  - `ListInstances` has two entrypoints: REST `GET /v1/services/{id}/instances` (`apps/rest.go:893`) and GraphQL `serviceInstances` (`apps/graphql.go:1339`), which feeds the Web Shell picker (`dashboard/src/features/services/hooks/use-service-instances.ts`, `web-shell-panel.tsx`).
  - `OwnAppPods` has 8 other callers: `readySSHInstances` (`service.go:1905`), `crash_loop.go:217` and six in `lego/backend/internal/metrics/service.go` (`:555`, `:744`, `:973`, `:1004`, `:1065`, `:1370`). Check whether each should also skip pre-deploy pods. The metrics callers build per-pod limit denominators and instance counts. Not probed here.
  - Regression tests: a web service, a private service and a background worker with a pre-deploy pod in the namespace each list only their Deployment pods. A service with no pre-deploy is unchanged.
- **Unverified:** whether the Metrics instance-count series and the `crash_loop` watcher count the pre-deploy pod; whether Render's own list ever shows the pre-deploy instance (Render documents the pre-deploy command as running before the new instances start).
- **Render:** Render's List instances returns the service's running instances; the pre-deploy command runs on its own before them.
- **Dedupe:** `grep -rlis "pre-deploy pod\|pre-deploy job\|pre-deploy instance" .pm` finds only unrelated done items (w4/316, 322, 426, 452, 615, m123, m198, m224, m225). None is about the instance list. w4/m352's DoD names "the one `/instances` lists from before the deploy" without noting the extra pod.
- **Closed 2026-11-14 (/loopx w4):** Premise held (the pre-deploy Job's pod carries `app.bex.co/app`, and `OwnAppPods` kept it). `core.OwnAppPods` now drops every pod carrying `app.bex.co/component` (new `core.PodLabelComponent`): the operator stamps it on every execution step's pod (pre-deploy, and a build or publish run in the App's namespace) and never on an instance. One change covers REST `GET /v1/services/{id}/instances`, GraphQL `serviceInstances` and the Web Shell picker, and also the other `OwnAppPods` callers, which all mean instances: `readySSHInstances`, the crash-loop sweeper and the six metrics reads (per-pod limit denominators, the metrics-server snapshot and instance-count fallbacks, the instance filter values). Logs keep reading the step's pod through `AppPodsIn`. Not changed: the Prometheus-ranged instance-count series, which does not read this list. Tests: `TestListInstancesSkipsThePreDeployPod` (web, private, worker; a first deploy in pre-deploy lists `[]`, a later one only the serving pod); backend `go test ./...` passes, `apps` also against real Postgres + OpenFGA. Live DoD replays after the next production deploy.
