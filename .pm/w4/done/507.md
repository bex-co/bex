# 507 — REST/MCP `cron_job_run_ended` reports `status: succeeded|failed` where the same run object says `successful|unsuccessful`

Why: a Render client reads `details.status` on the "Cron Job Run Ended" event with Render's run vocabulary. bex sends its internal lifecycle words, so `status == "unsuccessful"` never matches, and the event disagrees with `GET /v1/cron-jobs/{id}/runs` for the same run. ADR038 lists this as a "known divergence", but ADR018 does not record it and no user signed it off, so under the AGENTS.md parity rule it does not stand.

**Severity:** minor (Render-contract wording on a REST/MCP field; the dashboard is unaffected) · **Estimate:** 35m · **Worker:** worker4 · **Status:** todo

- **Source:** live `/qa-find-bugs w4`, production, 2026-11-05 22:44–22:47 UTC, round 108. Workspace `bex-canary`. Prod pin `cc3c51e12952`; research on main `faf1a3612`. Round 86 (17:11 UTC) supplied the successful-run half.

  1. `POST /v1/services {type:"cron_job", name:"qa-20261105-cronfail108", image busybox:1.36, schedule "0 3 * * *", dockerCommand 'sh -c "echo qa108 about-to-fail; exit 3"'}` created `srv-dbmgdscrv9ic73d23hug`; its deploy went `live`.

- **Root cause:** `lego/backend/internal/events/rest.go:218`.
  - `toRenderEvent` copies the stored lifecycle `e.Details.Status` into `details.status` for every type.
  - The `TypeCronJobRunEnded` case (`:277-281`) adds `cronJobRunId`/`reason` but never maps the status onto Render's run enum (`pending|successful|unsuccessful|canceled`, `render-public-api-1.json` `cronJobRun.status`; ADR018:102).
- **Fix:**
  - Target: on REST and MCP, `cron_job_run_ended.details.status` uses the run object's enum: `succeeded→successful`, `failed→unsuccessful`, `canceled→canceled`.
  - Map it in the `TypeCronJobRunEnded` branch only. `build_ended`/`pre_deploy_ended`/`job_run_ended` keep their documented `succeeded|failed|canceled`.
  - `reasonCode` stays a bex extra.
  - Keep GraphQL's bex vocabulary, which the dashboard timeline reads (`dashboard/src/features/events/lib/timeline.ts`), or move GraphQL too and update that consumer in the same change.
  - Update ADR038:147 to drop the divergence and the ADR018 cron row to match.
- **Blast radius:**
  - `toRenderEvent` has 4 call sites: REST list `rest.go:313`, REST get `:349`, MCP get `mcp.go:114`, MCP list `:145`. All four get the fix together.
  - Add a regression test per surface for a failed and a successful run, plus one asserting `build_ended` is unchanged.

  - The exact live Render event-detail value was not captured; the target is Render's own run enum as recorded in ADR018:102 and ADR038:147.
- **Render:** Render's "Cron Job Run Ended" event carries the run status in Render's run vocabulary (`successful`/`unsuccessful`), per ADR038's own note.
