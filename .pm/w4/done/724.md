# In a protected environment a Developer sees Delete enabled on a service, a Postgres and a Key Value, types the phrase, and reads "Forbidden"

Why: Render lets only Admins delete a protected environment's resources, so a Developer must see Delete disabled with Render's reason before typing the phrase, never a bare 403 after it. Found by w4/m578 t005 on 2026-11-22.

- **What happens (dev-4, OpenFGA enforced, 1440 and 390):** as a Developer in a protected environment, the service Settings danger zone's **Delete service**, **Delete Database** and **Delete Key Value Instance** are enabled. Typing the phrase and confirming answers `FORBIDDEN`, the dashboard shows a bare "Forbidden" toast, and nothing is deleted. The service's delete dialog then stays open. The verbs refuse by `requireUnprotected(ctx, …, "delete")` (`lego/backend/internal/apps/service.go` `Delete`, `postgres/service.go` `DeletePostgres`, `keyvalue/service.go`).
- **Why the dashboard offers it:** `DeleteServiceCard` (`dashboard/src/features/services/components/delete-service-card.tsx`) has no permission gate at all. `DatabaseRowActions`, `DatabaseDangerActions` and `KeyValueDangerActions` gate Delete on the workspace `can_create`, which a Developer holds (`deploy/gitops/authz/model.json`). No projection carries a `delete` row: `serverActions` has none, and `databaseActions` excludes it deliberately (`postgres/actioncaps.go`).
- **End state:** the three projections report `delete` with the w4/m578 rule (`core.RestrictedDecision`, reason `protected_environment_admin_required`), and every Delete control gates on it: disabled with _This action is limited to admins._ for a Developer in a protected environment, enabled for an Admin and in an unprotected environment, with the role reason for a Viewer. A raced 403 names the same reason instead of "Forbidden". Tests per surface; REST and MCP are unchanged.

**Done 2026-11-23.** w4/728 (`e5d6088cc3`) had already made a raced refusal read _This action is limited to admins._ in `useDeleteService`, `useDeleteDatabase` and `useDeleteKeyValue`; this closes the rest.

- **Projection:** `serverActions` (every service type), `databaseActions` and `keyValueActions` report `delete` by the verb's own rule: `can_create`, and on a protected member the fresh workspace-manage check (`core.RestrictedDecision`), sharing each projection's one protection read and admin check. A Developer there reads `denied` / `protected_environment_admin_required`, a Viewer `insufficient_permission`, a failed protection read `unavailable`. `postgres/actioncaps.go` no longer excludes delete. REST and MCP are unchanged.
- **Dashboard:** every Delete control reads that row through `useAdminOnlyActions` (now also `"service"` → `serverActions`): the service Settings danger zone's Delete Service, a Postgres's Delete Database (Info actions) and Delete (header and list-row menus), and a Key Value's Delete Key Value Instance (Info actions) and Delete (list-row menu). Before, a Developer in a protected environment had all of them enabled, typed the phrase and read "Forbidden". After, each is disabled with _This action is limited to admins._ in its tooltip and no dialog opens; a Viewer reads the role reason, and an Admin, or anyone outside a protected environment, keeps Delete. ADR018 and ADR032 record it.
- **Tests:** `TestActionCapabilities_DeleteAgreesWithTheVerb` (Admin and Developer, protected and not, the projection against `Delete`), `TestActionCapabilities_DeleteOnEveryType`, the Viewer and failed-read cases, the datastores' `TestActionCapabilities_CredentialsAndIPRulesAgreeWithTheVerbs` with a delete row against `DeletePostgres` / `DeleteKeyValue`, the GraphQL `TestLifecycleProjectionsGraphQLProtectedAdminRule`, the projection routing in `resource-action-freshness.test.tsx`, and a Developer and a Viewer case on each of the five Delete controls. Each fails with its fix reverted. Not replayed live on dev-4: its bex-api runs fail-open, and the OpenFGA-and-three-identities recipe of w4/m550 t005 was not kept as a script (as for w4/725).
