# 048 — Billing/usage page never surfaces `usage.coverage`, presenting a partial/degraded metering estimate as authoritative

Why: the Billing page shows confident dollar amounts built on a metering estimate the backend flags as `partial` with every source degraded, but discloses only the generic "an estimate, not an invoice" — the Metrics page already surfaces the analogous degraded-source caveat, so Billing is the honesty outlier on a money surface.

Found in a live `$qa-find-bugs w4` hunt of `dashboard.bex.co`, 2026-09-06, workspace `tian-personal` (`tea-da2isimlm39c739m4ofg`). Read-only for this finding (queried the API from inside the page).

Severity: minor (missing honesty caveat on financial data; the numbers aren't wrong, but they're under-disclosed — and it's about money).

## Symptom

The Billing page (`/billing`) "Charges" section shows a confident month-to-date total and projected total (e.g. "Total month to date $2.45 USD", "Projected total for September $12.31 USD") with only the generic disclaimer "An estimate, not an invoice." But the backend `usage.coverage` reports the estimate is `partial` and every metering source is degraded. The UI never surfaces this. By contrast, the **Metrics** page **does** surface degraded metering ("Partial data" badge + tooltip "The {sources} egress source was unhealthy for part of this window — bandwidth may be undercounted."). Billing is the honesty outlier.

## Repro

1. Sign in; open `https://dashboard.bex.co/billing` (workspace with any usage).
2. Read the Charges/summary: only "An estimate, not an invoice." No partial / degraded / as-of indicator.
3. From inside the page, query the usage API (below) — `coverage.state` is `"partial"`, `through` is the start of the period, `degradedSources` lists 5 sources.

## Expected / Actual

- Expected: when `usage.coverage.state != "complete"`, the Charges/usage section surfaces a caveat (e.g. a "Partial data" notice: estimate complete only through `{through}`; N metering sources degraded), mirroring the Metrics page's degraded-source badge — so a user reading dollar amounts knows the estimate itself is built on incomplete/degraded data.
- Actual: the `coverage` object is never requested or rendered; the totals are presented as authoritative apart from the generic estimate disclaimer.

## Evidence

- `.playwright-mcp/qa-billing-01-charges-no-coverage-caveat.png` — Charges expanded, confident totals, no partial/degraded indicator.
- Durable API probe (run from inside the page, `credentials:'include'`, `POST https://api.bex.co/graphql`):
  ```
  query($o:String!){ usage(ownerId:$o){ period coverage{ state through degradedSources } estimatedCost{ totalUsd } } }
  variables { o: "tea-da2isimlm39c739m4ofg" }
  →
  {
    "period": "2026-09",
    "coverage": { "state": "partial", "through": "2026-09-01T00:00:00Z",
                  "degradedSources": ["direct","http","instance","key_value","websocket"] },
    "estimatedCost": { "totalUsd": "2.45" }
  }
  ```
- UI text scan of `<main>`: matches only "estimate" and "not an invoice"; **no** "partial"/"through"/"coverage"/"degraded"/"as of"/"incomplete", and it does not render the `through` date.
- Note: an initial UI `$2.43` vs API `$2.45` was a live-refetch timing artifact — after the page settled UI == API == `$2.45` and the per-service rows reconcile. That is **not** the bug; the coverage-disclosure gap is.

## Root cause

`dashboard/src/features/usage/api/usage.graphql` — the `Usage` query selects `workspaceId`, `period`, `estimatedCost{...}`, `billing{...}` but **never** selects `coverage { state through degradedSources }`. So the coverage object never reaches the client, and nothing in the usage feature (`usage-page.tsx` / `charges-card.tsx`) renders it. `grep -rin "coverage|degraded|partial|through" dashboard/src/features/usage` returns only locale/test noise — zero rendering path. The schema **has** it: `UsageSummary.coverage: UsageCoverage!` `{ state, through, degradedSources }` (verified by introspection). `docs/ADR040-billing-metronome.md:82` documents the intent — "failures degrade to estimate-only rather than turning the usage endpoint into a 500" — i.e. `coverage` is the designed signal for exactly this degraded state, meant to be consumed.

## Control case (the pattern to mirror)

The Metrics page already does this for its own degraded sources: `dashboard/src/features/metrics/components/network-metrics-card.tsx:363-364` renders `<BandwidthDegradedBadge sources={bandwidth.degradedSources} />` when `degradedSources.length > 0`, with strings `metrics.bandwidthDegraded` ("Partial data") + `metrics.bandwidthDegradedDetail`. Billing should surface `usage.coverage` the same way.

## Fix (name the target behavior)

Add `coverage { state through degradedSources }` to the `Usage` query, then in `charges-card.tsx` / `usage-page.tsx` render a caveat when `state != "complete"`: a "Partial data" notice naming the `through` boundary and summarizing/counting degraded sources (reuse the metrics degraded-badge shape + new `usage.*` locale strings). Dashboard-only; **no** backend change (`coverage` is already served; REST `GET /v1/usage` and MCP `get_usage` return whatever the caller selects). Requires `yarn codegen` (offline via the backend schema dump) to regenerate the typed query.

## Blast radius

Dashboard usage feature only: `usage.graphql` (add the field) and the render site in `usage-page.tsx` / `charges-card.tsx` (add the caveat). No shared backend helper. The billing amounts themselves are unchanged — this adds disclosure, not a recalculation. Add a usage-page/charges-card test asserting a partial-coverage `UsageSummary` renders the caveat and a complete-coverage one does not.

## Resolution (2026-09-07)

Done. The Billing page's Charges section now discloses degraded metering instead of presenting a partial estimate as authoritative. Added `coverage { state through degradedSources }` to the `Usage` GraphQL query (regenerated `definitions.ts` offline via the backend schema dump — clean per-feature splice, only the Usage query changed) and threaded a typed `Coverage` through `use-usage`'s summary. `ChargesCard` gained a `coverage` prop and renders a `CoverageCaveat` — an amber "Partial data" line whose tooltip names the coverage `through` boundary (date-sliced from the UTC RFC3339 string, hydration-safe) and the degraded meter names — mirroring the Metrics page's `BandwidthDegradedBadge`. Shown only when `state != "complete"` AND there's something concrete to disclose (a `through` bound or named sources), so an indeterminate `unknown` read with nothing to show stays silent. Dashboard-only; no backend change (`coverage` was already served). en/zh locale strings added. Tests: a `use-usage` mapping test for a partial read, and four `ChargesCard` caveat cases (partial shows + names the boundary/meters; complete hidden; empty-unknown silent; absent-coverage back-compat). `yarn typecheck`/`yarn lint`/full dashboard suite green. Live re-probe of the deployed fix deferred to the next QA pass.
