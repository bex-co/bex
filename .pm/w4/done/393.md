## Probe

- nginx: workers started at `03:06:48Z` (app logs). The deploy stayed `update_in_progress` and closed `update_failed` at `03:21:49Z`, 902 s after starting. `serviceDetails.port` stayed `10000`.
- python: the app log shows `03:26:58 Serving HTTP on 0.0.0.0 port 8000 (http://0.0.0.0:8000/) ...`. At `03:29:07Z`, more than two minutes later, the deploy was still `update_in_progress`. That is well past the design's ≥20 s running plus two scans ≥15 s apart.
- In both, the stall reason never gained the sentence `detectBoundPort` appends on the first successful scan (" The process is listening on port N."). The full text stayed: "the container is running but its startup health check has not succeeded, so the rollout is waiting: a TCP connect to port 10000. - The same pin's other operator features work live in the same run: a static-site miss → `404` with the site's `404.html`, and a rewrite to `https://httpbin.org/anything/*` proxies GET/POST with query and headers. So the operator/static-server image is current.

## Where it stops (code read; the live cause is unverified)

`lego/operator/internal/controller/port_detect.go:81-138` returns `""` with no stall text when the scan errors. A scan error is logged only at `V(1)` ("port detection scan failed"), so it is invisible from the product. `portscan.Dialer.Scan` (`lego/operator/internal/portscan/portscan.go:63-116`) dials all 65,535 ports with 512 workers and a 400 ms dial timeout under the 15 s `portDetectTimeout` (`port_detect.go:58`). If packets to the pod are **dropped** rather than refused, a full sweep needs about 51 s. The context then expires, or `ErrUnreachable` is returned (no refusal seen), and nothing is ever detected. Candidate causes to confirm with `kubectl`:

1. The new `allow-operator-probe-ingress` NetworkPolicy (`lego/backend/internal/store/namespaces.go:573,694-712`) is missing from the existing `tea-daif693dqjvc73e7as3g` namespace. It reaches existing namespaces only on the namespace reconciler's resync.
2. A Cilium cluster-wide or tenant-node policy (`deploy/gitops/base/tenant-node-egress.yaml`, `network-policies.yaml`) drops manager → tenant-pod traffic before the namespace policy applies.
3. The manager pod is not `unreadyPodIP`-eligible (e.g. a revision-label mismatch), so no scan runs at all.

## Fix (target behavior)

- The two fixtures above go `live` on production with `status.detectedPort` 80 / 8000. The deploy log names the detected port, and `GET /` returns the nginx welcome page and the directory listing respectively.
- A failed scan must not be silent. Surface "port detection could not reach the instance" in the stall reason (or at least at info level), so this class of failure is visible next time.
- Bound the scan so a dropped-packet path cannot exceed `portDetectTimeout` without a verdict: a smaller port set first (common HTTP ports), then the full sweep.
- Re-run w8/177's own "Live after deploy" acceptance and record it there.

**Unverified:** which of the three causes is real (no cluster access from the product); whether native (repo-built) services behave the same; MCP/GraphQL `detectedPort` exposure.

## Root cause found (w8/202, 2026-10-26)

The scan never starts. `detectBoundPort` returns early on `app.Spec.Port > 0`, and every real App has `spec.port: 10000` (API create default plus the CRD default). On platform pin `2331a3dad`, a native hapi service bound to 0.0.0.0:3000 failed with no detection text of either kind. The fix is tracked in [w8/202](../../w8/done/202.md). After it deploys, re-run this item's nginx and `http.server 8000` acceptance. Only if the w4/393 "could not reach the instance" text then appears do the three network candidates above matter.
