# 465 — A hand edit to `lego/operator/config/api/deployment.yaml` makes the deploy guard throw away a finished, green run ("generated field reshaped"), so production waits for the next run

Why: since w4/439, newer manifests are no reason to skip a pin (rc 4), because Argo already runs them on older images. But `api/deployment.yaml` is both the hand-written bex-api Deployment and the file that holds the generated agent-sandbox image field. So any ordinary env-var or spec edit to it takes the stricter "reshaped generated field" exit (rc 0, never pin). A green run that has already built all images then pins nothing. On 2026-11-03 this discarded the `6a0eb6e4a` run (deploy steps 11:34 UTC, all `SUPERSEDED: true`), and production stayed on `0acc15714458` from 02:42 UTC onward.

- **Source / severity / estimate:** found by the live `/qa-find-bugs w4` loop, 2026-11-03 11:42 UTC. **Major**: no data is lost, but every deployable fix waits at least one more full run (about 1.5–3.5 h). ~45m.
- **Evidence:** deploy run `41615699297`, head `6a0eb6e4a`, all tests green, ended 11:35 UTC. Its `pin image digests in GitOps (write-back)` step printed:

  ```text
  superseded by a substantive generated-file change on origin/main (changed by: 18c935cf); this run's images will not be built/pinned
  ##[notice]not pinned (generated field reshaped, or older than the current pin) — images built but intentionally not pinned; skipping the rollout
  ```

  `18c935cf8` (ADR095 attachments) only appended four optional `BEX_AGENT_ATTACHMENTS_S3_*` `env` entries to `lego/operator/config/api/deployment.yaml` (`+33` lines at `@@ -519`). The generated `bex-agent-sandbox` value line is untouched.

- **Root cause:** `scripts/deploy-superseded.sh`.
  - Lines `82-88`: the first pass excludes the five generated-digest files from the manifest diff.
  - Lines `107-139`: the second pass compares each of those files after normalizing only its digest field. Any other difference counts as `changed`.
  - Lines `142-146`: `changed` exits **0** ("substantive generated-file change … will not be built/pinned").
  - So a real manifest change inside one of these files is treated more harshly than the same change in any other manifest file, which sets `manifests_moved=true` and takes **rc 4** (pin; lines `182-184`).
  - The rc 0 rule was meant for a reshaped generated field: a write-back targeting the wrong shape, per the header comment at lines `32-34`. It was never meant for unrelated edits elsewhere in the file.
  - The tests encode the old behavior: `scripts/deploy-superseded.test.sh:132-135` ("agent manifest drift beyond digest" → `0`), written 2026-08-02 (`6abfd4b95`), before w4/439's rc 4 policy.
- **Fix (target behavior):** for each of the five files, split the second pass into two checks:
  1. **Field reshaped:** the generated field's pattern no longer matches exactly once in either revision, or the captured prefix (regex group 1: image name, tag shape, surrounding keys) differs between the two revisions. Only this keeps **rc 0**.
  2. **Rest of the file differs** after normalizing the digest: set `manifests_moved=true` and continue, so the run reaches the rollback guard and then **rc 4**, exactly as for any other manifest path.
  - Update `deploy-superseded.test.sh:132-135` to expect `4` for "drift beyond digest". Add a case where the agent-sandbox line itself changes shape (for example tag → a different image name), which must stay `0`.
  - Keep the rollback refusal (lines `176-181`) ahead of rc 4. It still applies.
- **Blast radius:** only `scripts/deploy-superseded.sh`. Its two callers are in `.github/workflows/deploy.yml`: the pre-build `check-supersession` step (line `168`), which already treats rc 4 as skip-before-build, and the write-back guard, which treats rc 4 as pin. Both already handle rc 4, so no workflow change is needed.
  - Hand-edit frequency over the last 30 days (non-pin commits): `api/deployment.yaml` **7**; `deploy/gitops/base/bex.yaml`, `dashboard.yaml`, `deploy/opensandbox/kustomization.yaml` and `values/opensandbox-controller.values.yaml` **0** each. So `api/deployment.yaml` is the file that triggers this in practice. The fix applies to all five uniformly.

Whether the pre-build check also skipped otherwise buildable runs for this reason; at that stage it is harmless, because the queued run builds the newer tree.
