## Objective

When a service fails the `services[]` `anyOf`, bex reports the complaint of whichever branch had the fewest leaf failures. On a tie that is the first branch in schema order, which is the wrong service kind — so the user is told the one field they got *right* is illegal, and the field that is actually illegal is never mentioned.

## Context

### The symptom (production, 2026-09-13)

A static service with one disallowed key (`plan`) is reported as:

```text
at '/services/0': additional properties 'staticPublishPath' not allowed
```

`staticPublishPath` is legal for a static service (`#/definitions/staticService` lists it; `docs/ADR006-bex-api.md:167` documents it as the accepted key). Removing it makes things worse; removing `plan` makes the manifest valid. Both verified — see t001's table.

### The mechanism

`lego/backend/internal/apps/blueprint_compiler.go:1082-1102`:

```go
if _, isAnyOf := validation.ErrorKind.(*kind.AnyOf); isAnyOf && len(validation.Causes) > 1 {
    closest := validation.Causes[0]
    for _, cause := range validation.Causes[1:] {
        if blueprintSchemaLeafCount(cause) < blueprintSchemaLeafCount(closest) {
            closest = cause
        }
    }
    appendBlueprintSchemaProblems(closest, locations, problems)
    return
}
```

The intent is right and the comment says so — "Only the closest alternative is useful to a Blueprint author… avoiding misleading errors from unrelated service kinds". The defect is the metric:

- `blueprintSchemaLeafCount` (`:1116-1125`) returns **1** for any single-leaf failure, so "one extra property" on the wrong branch ties with "one extra property" on the right branch.
- The comparison is strictly `<`, so a tie keeps `Causes[0]` — the **earliest** branch.
- `#/definitions/resources.properties.services.items.anyOf` is ordered `[redisServer, cronService, serverService, staticService]`, so `serverService` precedes `staticService` and wins the tie.

A static service is not ambiguous: `staticService` pins `type: const "web"` **and** `runtime: const "static"`, `cronService` pins its own, and so on. The instance's discriminating values identify the intended branch exactly, independent of how many other keys are wrong.

### The env-var forms are far worse — measured 2026-09-13 pass 9

This was listed as unprobed when the milestone was filed. It is now probed, and it changes the severity and the mechanism.

Five manifests, each a **valid** `serverService` (`type: web`, `runtime: docker`, `repo`, `branch`, `plan: free`) differing only in one injected env-var fault, all return the **identical three errors**:

```text
at '/services/0': missing property 'ipAllowList'
at '/services/0': additional properties 'runtime', 'repo', 'branch', 'envVars' not allowed
at '/services/0/type': value must be one of 'keyvalue', 'redis'
```

The faults were: a bogus field inside `fromDatabase`; an invalid `fromDatabase.property`; a bogus field beside a literal `value`; a `fromService` missing its required `type`; and both `value` and `fromDatabase` on one entry. **Every one** reports only `redisServer`'s complaints — a resource type the manifest never mentions — and **none** mentions the actual mistake. The output carries no information about what the author got wrong.

Control (run in the same batch, so the base manifest is not itself at fault): the same manifest with a clean literal env var, with no `envVars` at all, and with a clean `fromDatabase` plus a matching `databases:` entry are all `valid: true`.

### This corrects the mechanism described above

"Ties keep `Causes[0]`" is not the whole story, and the env-var case shows why: `redisServer` fails with **3** leaves, while the correct `serverService` branch fails with **more** — because it got far enough to evaluate the **nested** env-var `anyOf`, where the one bad entry fails all five inner forms and each failure contributes its own leaves. So leaf-count does not merely tie-break badly; it **systematically prefers the branch that failed earliest and shallowest**, and the deeper a manifest's real error is, the more reliably the wrong branch wins.

That reframes the fix: discriminator-aware selection is not a refinement on top of leaf counting — it is the fix, and leaf counting should be the last resort only when no discriminator matches. Step 1 below should confirm these leaf counts by instrumentation, but the direction no longer depends on the tie theory.

### Adjacent classes

The same selector serves every `anyOf` in the schema, which the code comment names: the env-var forms (`envVarFromDatabase` / `envVarFromService` / `envVarFromGroup` / `envVarFromKeyValue` / literal) — now measured above. A fix must state what happens when:

- **exactly one** branch's discriminators match → report only that branch (the static/cron/redis case);
- **no** branch matches (e.g. `type: web, runtime: nonsense`) → today's leaf-count heuristic is the sensible fallback, but the message must still name something actionable, and the enum error must list the full accepted set (see the separate enum bullet below);
- **several** branches match or a branch has no discriminator (the env-var forms discriminate by which key is *present*, not by a `const`) → decide and document; presence-based discrimination may need its own rule rather than being forced into the const-matching one.

### The enum message is a second, smaller defect in the same area

`type: nonsense` answers `at '/services/0/type': value must be one of 'web', 'worker', 'pserv'` — but `type: cron` **validates** (verified). The set in the message comes from one branch's `type` enum, not from the union of branches, so a cron-job author is told cron is not a service type.

## Steps

1. Instrument first: for the t001 manifest, log each `anyOf` cause's leaf count and identity, and confirm the tie-plus-order explanation before changing anything. If the counts are not tied, the mechanism is different and this task's shape changes — say so.
2. Add discriminator-aware selection: before falling back to leaf count, check each branch's `const`-pinned discriminators (`type`, `runtime`) against the instance and, when exactly one branch matches, report only its causes.
3. Read the pinned validator's API before assuming the shape: `santhosh-tekuri/jsonschema` at the version in `lego/backend/go.mod` — `ValidationError.ErrorKind`, `kind.AnyOf`, `kind.AdditionalProperties`, and how `Causes` nest for a `$ref`'d branch. The existing `kind.AdditionalProperties` special case at `:1105-1107` is the precedent for reaching into a kind.
4. Fix the enum message to enumerate the union of accepted `type` values across branches (or to be produced after branch selection, so it is the selected branch's set).
5. Keep the strictness: this changes only which cause is *reported*. A manifest that is invalid must stay invalid, and a manifest that is valid must stay valid.
