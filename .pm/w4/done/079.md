# 079 — `createWebhookEndpoint` mints a show-once signing secret but is classified as an ordinary write

Why: four other verbs that mint a durable show-once credential are `core.OpClassMint`, a class no delegated OAuth caller can satisfy — this one is `core.OpClassWrite`, so a `bex.write` token can mint a webhook signing secret but not an API key.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-14 pass 27, while doing the `Mutation`-side half of the audit `w4/m106` asked for. **`w4/m106` has since been implemented and closed** (`36457c620`, which walks the selection set for nested secret fields) — that fix addressed the nested-field gap and did **not** touch this classification, so this is the surviving remainder rather than a duplicate. Filed as a note because it is one ~30m change.

## The finding

`createWebhookEndpoint` returns a fresh 38-character signing secret, shown exactly once, and is classified `core.OpClassWrite`. Every other verb in the codebase that mints a durable show-once credential is `core.OpClassMint`, a class that OAuth callers can never satisfy. So a `bex.write` token cannot mint an API key or a database password, but can mint a webhook signing secret.

## Context

### Measured live (production, 2026-09-14 pass 27)

```text
mutation { createWebhookEndpoint(name:"qa-…", url:"https://qa-….invalid/h",
                                 eventTypes:["deploy_ended"], enabled:true){ id name secret } }
  → secret: 38 chars, prefix "whse…"        ← minted, returned once

query { webhookEndpoint(id:"whk-…"){ secret } }
  → secret: ""                               ← never returned again
```

Show-once is exactly the hygiene an API-key secret gets (`apiKeys.secret` also reads back `""`, verified in pass 26). The endpoint was pointed at a reserved `.invalid` host and deleted in the same run.

### The classification, and its control set

`lego/backend/internal/api/scope_matrix_ops.go`:

| verb | returns | class |
| --- | --- | --- |
| `GQL Mutation.createApiKey` (`:43`) | API-key secret, show-once | **`core.OpClassMint`** |
| `GQL Mutation.createDatabaseUser` (`:49`) | generated DB password | **`core.OpClassMint`** |
| `GQL Mutation.regenerateDeployHook` (`:96`) | deploy-hook URL (unguessable token) | **`core.OpClassMint`** |
| `GQL Query.deployHook` (`:226`) | the same URL token | **`core.OpClassMint`** |
| **`GQL Mutation.createWebhookEndpoint`** (`:60`) | **webhook signing secret, show-once** | **`core.OpClassWrite`** |

Four verbs with the same shape are mint; this one is not. That is the whole finding — it is a classification inconsistency, not a missing mechanism.

### Why mint matters more than "one class higher"

`core.OpClassMint` is not a fourth OAuth scope. `core/scope.go:205` and `core/base.go:897-907` gate it **at the verb** via `AuthorizeMintClass`, and `base.go:320` records that a nil mint-capability means "a delegated (OAuth) caller can never pass that". So mint verbs are refused to token callers outright. Classifying this verb correctly does not tighten a scope — it moves the verb out of reach of delegated callers entirely, which is a **behavior change for any existing integration that creates webhook endpoints with an API key**. Decide that deliberately:

- **(a) Mint** — consistent with the four controls; breaks token-driven webhook creation.
- **(b) Sensitive** — requires `bex.sensitive` rather than barring delegated callers; weaker than the controls but non-breaking for scoped tokens that ask for it.
- **(c) Stay write, and stop returning the secret at mint** — the endpoint would then need a separate reveal/rotate verb, which is a bigger change but arguably the cleanest: the secret stops riding a write response at all.

Name the choice and its rationale in the commit; do not pick silently.

### What the secret actually authorizes

It is the HMAC key bex signs outbound deliveries with. Holding it lets someone forge payloads **to the customer's receiver** as though they came from bex — the opposite direction from an API key, but a durable secret with real consequence, and the codebase's own show-once treatment says it is understood as one.

## Steps

1. Decide (a)/(b)/(c) above and record why.
2. Apply the classification, and check `updateWebhookEndpoint` and `resendWebhookDelivery` for the same shape while you are there — does any of them return or rotate the secret?
3. Check the REST and MCP siblings: the matrix must agree across surfaces, as it already does for the API-key mint. Enumerate `REST POST /v1/webhooks*` and `MCP create_webhook_endpoint` and classify identically.
4. If (a) is chosen, search for existing callers that would break — the dashboard uses a session (unaffected), but the CLI, MCP agents, and any documented integration path need a migration note the way `w4/076` documents the pre-m105 key situation.

## Out of scope

- `createDatabaseExport` (`:48`, `core.OpClassWrite`) returns a `url` for a database export — plausibly a signed link to real data, and plausibly a mint too. **Not probed this run** (it needs a database and an export), so it is recorded as a lead rather than folded in. Check it while classifying.
- The nested-field gap, which `w4/m106` closed in `36457c620` — this is a root-level misclassification, independent of that selection-set walk.

## Closed 2026-09-15 — decision (a) Mint

Chose **(a) Mint** for consistency with API-key / DB-user / deploy-hook show-once credentials. Applied across GQL/REST/MCP (`OpClassMint` + `AuthorizeMintClass` on `Create`). `updateWebhookEndpoint` / `resendWebhookDelivery` stay write (no secret mint/rotate). Guard heuristic + delegated-refusal tests land with the change. `createDatabaseExport` left write: ADR018 documents short-lived `can_view_sensitive`-gated download URLs, not a durable show-once signing secret.

Migration: machine API keys and third-party OAuth `bex.write` tokens can no longer create webhook endpoints — use a session or platform client (official CLI). Dashboard sessions unaffected. Recorded in ADR012 § mint row.
