# 516 — A deleted web service answers `503 service not ready, retryAfter 5` for ~20 s, and its request runs the wake path, before the host turns into a 404

Why: after `DELETE /v1/services/{id}` returns `204`, the public host keeps telling clients and uptime monitors to retry in 5 seconds, as if the service were waking. It also sends the deleting App through `wakeApp`, which writes the App's wake annotations and patches its Deployment's replicas. A deleted service should read as gone: Render's `404` "no-server" answer, which bex already gives once the App leaves the activator's index.

**Severity:** minor (transient, but the answer is wrong and a write lands on a deleting App) · **Estimate:** 30m · **Worker:** worker4 · **Status:** done

- **Source:** live `/qa-find-bugs w4`, production, 2026-11-06 02:53 UTC, round 124 (rollback journey). Workspace `bex-canary`; prod pin `92ff0029334d`; research on main `289268d59`. Round 123 saw the same `503` after deleting a static site (`qa-20261106-st123`), but did not time it.

- **Root cause:** `lego/operator/cmd/activator/main.go`.
  - `hostCache.refreshOnce` (`:808-830`) indexes every App from a cluster-wide `List`, including an App whose `deletionTimestamp` is set. A deleted App keeps `app.bex.co/finalizer` while `handleAppDeletion` (`internal/controller/app_controller.go:7385`) reclaims build artifacts, registry images and credentials, so it stays listed and indexed for that whole window.
  - `newHoldingHandler` (`:166-276`) checks unknown host, maintenance, suspension, failed or never-served first release, static site and robots. It never checks deletion, so a deleting web App falls through to `wakeApp` (`:319`). That patches `app.bex.co/last-active` and the wake annotation on the App, sets the Deployment's replicas to 1 if they are 0, and then answers `writeWakeResponse` (`:356`) with `503` and `Retry-After: 5`.
  - `grep -rn DeletionTimestamp lego/operator/cmd/activator` finds 0 hits.
- **Fix:**
  - Target: from the moment an App carries a `deletionTimestamp`, its hosts answer exactly like an unknown host: `writeUnknownHostResponse` with `404`, `x-render-routing: no-server`, the same negotiated page/JSON/text. Nothing is written to the App or its Deployment.
  - Preferred: skip deleting Apps in `refreshOnce`, so `lookup` and `claims` both drop them. The maintenance-page fetch denylist then stops counting a deleted service's hosts as claimed, which is also correct. Alternative: a guard `if !app.DeletionTimestamp.IsZero()` right after the `lookup` in the handler; keep `claims` consistent with whichever you choose.
  - Tests in `cmd/activator`: a deleting App's host → `404` no-server, with no patch reaching the fake client (no `last-active` write, no replica patch), for web, image-port and static-site Apps and for a suspended or maintenance-mode App that is being deleted. A held (non-browser) request for a deleting App must not be held.
- **Blast radius:**
  - `hostCache` has 3 consumers in `main.go`: `lookup` (the public handler), `claims` (the maintenance custom-page denylist) and `refreshOnce` (the appwatch loop).
  - The guard changes only Apps being deleted. Every live App keeps its current branch, so the existing wake, suspension, maintenance and first-deploy tests stay as regression controls.
  - The suspended and maintenance answers for a deleting App also move to `404`. That is intended: the service no longer exists.
- **Adjacent classes:** unknown host stays `404`. Suspended (`503`, `Retry-After: 3600`), first deploy, waking and readiness hold (`503`, `Retry-After: 5`) are unchanged for Apps that are not being deleted. Nothing new is disclosed: the `404` is exactly what any host without a service already returns.
