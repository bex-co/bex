## Objective

Make MCP's view of notification settings match the decided scope, and make sure the allowlist that encodes that view is reviewed rather than inherited.

## Context

- `api/mcp_workspace.go:38-47` is an explicit allowlist of tools that receive **no** workspace binding, introduced with the comment that everything else "is a workspace resource operation and is scoped uniformly here instead of growing adapter-specific ownerId or transport-session state in each feature package". Both `get_notification_settings` and `update_notification_settings` are in it.
- If t001 chose per-workspace, they must come out, and the middleware will then bind `workspaceId` and validate membership for them like every other resource tool.
- **The other six entries were audited in pass 146 and are all correctly classified** — so this task is about the notification pair only, and the re-derivation below is a recording exercise rather than a hunt:

  | entry                                              | store keying                                                              | caller-scoped correct? |
  | ---------------------------------------------------- | --------------------------------------------------------------------------- | ------------------------ |
  | `add_ssh_key` · `delete_ssh_key` · `list_ssh_keys`  | `ssh_keys` is keyed on `subject` alone — no `tenant_id` column (`0029_ssh_keys.up.sql:5-14`) | yes                    |
  | `preview_workspace_invite` · `accept_workspace_invite` | `tenant_invites` has `tenant_id`, but both verbs address the invite by **token**, which carries the workspace; the caller is not yet a member, so a workspace binding would fail the middleware's own membership check | yes                    |
  | `list_workspaces`                                   | answers about the caller                                                   | yes                    |

  That makes the notification pair the only misclassification, and supports the reading that the list was correct when written and was not re-derived when `notification_settings` was given a `tenant_id`.
- Note the asymmetry this leaves today: MCP is the only surface with a general workspace-binding mechanism, and it is the one that opted these tools out of it.

## Steps

1. Move the two tools out of (or leave them in) `mcpCallerScopedTools` per t001.
2. If removed, confirm the tools' own argument structs do not also need an `ownerId` — the middleware supplies it, and duplicating it is the drift the comment warns about.
3. Re-check the remaining allowlist entries against the store's actual keying and record the result in the comment.
