## Objective

Settle whether a member's deploy-notification preferences are **per workspace** or **per user**, and make the store, the mail fan-out, and all four surfaces agree. Today three of those say per-workspace and the API says per-user, and nothing reconciles them.

## Context

### What the storage says

`lego/backend/internal/store/migrations/0013_notification_settings.up.sql`, header comment and index:

```sql
-- Each row is one member's override of their per-workspace deploy-email
-- preferences (Render's /notification-settings).
--   tenant_id/subject  the workspace + member the preference belongs to
-- One row per (tenant, subject): a member customizes their own preferences only.
CREATE UNIQUE INDEX notification_settings_member_idx ON notification_settings (tenant_id, subject);
```

So a member may hold **one row per workspace**.

### What the mail fan-out says

`store/notifications.go:122-130`, `ListNotifyRecipients(tenantID)` — the notification service's fan-out source:

```sql
SELECT m.subject, COALESCE(n.deploy_started, false), COALESCE(n.deploy_succeeded, false), COALESCE(n.deploy_failed, true)
FROM tenant_members m
LEFT JOIN notification_settings n ON n.tenant_id = m.tenant_id AND n.subject = m.subject
WHERE m.tenant_id = $1 AND m.kind = 'user'
```

Whether you are emailed about a deploy in workspace B is decided by **workspace B's row**.

### What the API says

`notifications/service.go:249-296` — both verbs key on `s.Base.Tenant(ctx)`:

```go
func (s *Service) GetSettings(ctx context.Context) (SettingsView, error)          // no workspace argument
func (s *Service) UpdateSettings(ctx context.Context, deployStarted, deploySucceeded, deployFailed bool) (SettingsView, error)
```

`Base.Tenant(ctx)` resolves the caller's **default** workspace when none is named (`core/base.go:957-972` → `resolveWorkspaceUncached`), and none is named, because no adapter offers the argument. Verified live:

```graphql
{ notificationSettings { deployStarted deploySucceeded deployFailed } }   # no ownerId argument exists
→ { "deployStarted": false, "deploySucceeded": false, "deployFailed": true }
```

```
GET /v1/notification-settings                                  → 200 {"deployStarted":false,"deploySucceeded":false,"deployFailed":true}
GET /v1/notification-settings/owners/tea-d98210cbbpdc73dcrkvg  → 404      (bex workspace)
GET /v1/notification-settings/owners/tea-da2isimlm39c739m4ofg  → 404      (tian-personal)
GET /v1/notification-settings/owners/tea-daif693dqjvc73e7as3g  → 404      (bex-canary)
GET /v1/notification-settings/qa-not-a-route                   → 404      (control)
GET /v1/notification-settings/overrides/services/{srv-id}      → 200      (Render's exact sibling path, implemented)
```

So the member-defaults half sits at a bex-only unscoped path while the service-overrides half sits at Render's exact path.

### What MCP says

`api/mcp_workspace.go:38-47` lists the tools that *deliberately* receive no workspace binding, "tools that operate on the caller rather than on a workspace" — and both notification tools are in it:

```go
"get_notification_settings":    {},
"update_notification_settings": {},
```

That is a third opinion, and it is the opposite of the schema's.

### The consequence, stated plainly

For an account in three workspaces, the product can read and write exactly one `notification_settings` row — the default workspace's. The other two rows are unreachable through any surface, yet they are what `ListNotifyRecipients` consults. A member who turns deploy-failure email **off** still receives failure mail from their other workspaces, and nothing in the product will show them why.

A single-workspace account cannot observe any of this, which is presumably why it has survived.

### The two answers

- **Per workspace (Render's model).** Render exposes `/notification-settings/owners/{ownerId}` — cited in `.pm/DO_NOT_DO.md` round 14 as *"Render's owner-level `slackEnabled` on `PATCH /notification-settings/owners/{ownerId}`"*. Adopting it means adding the argument across surfaces, dropping the two tools from `mcpCallerScopedTools`, and making the dashboard panel workspace-aware. The store and fan-out already work this way — nothing migrates.
- **Per user.** Simpler to explain and matches what the API accidentally implements today. Costs a migration collapsing `(tenant_id, subject)` to `subject` (with a rule for members holding conflicting rows), and a change to `ListNotifyRecipients`. Diverges from Render, so ADR018's row must say so.

Prefer the first unless there is a product reason not to: it is the one where no data has to be discarded, and the store's own comment already committed to it.

## Steps

1. Pick the scope and write it into ADR024 beside the other member-scoped surfaces.
2. Say explicitly which of the four opinions (schema, fan-out, REST/GraphQL, MCP) changes.
3. If per-user: define what happens to members who already hold different values in different workspaces — silently picking one is a preference change made on the user's behalf.
4. Record the Render comparison in ADR018's Notifications row either way.

## Outcome (2026-09-21)

Decided per workspace — the schema and the mail fan-out are right; the API and MCP are what change. Written into ADR024 with the enumeration of all four opinions, the reason per-user was rejected (it discards data and needs a conflict rule), and the native-push half recorded as a known gap rather than silently fixed.
