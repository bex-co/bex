# 597 — Turning autoscaling off forgets its instance range and targets, while Render keeps them for the next time it is turned on

Why: an owner who pauses autoscaling for a while and turns it back on finds the Scaling page reset to 1 instance and 60% targets, and has to re-enter the range and targets they had tuned. On Render the settings survive the toggle.

- **Source / severity / estimate:** found while working w4/m335, `/loopx w4` 2026-11-11. **Minor**. ~1h.
- **Render evidence:** a read-only GET on the reference account (2026-11-11) returned an `autoscaling_config_changed` event (`evt-d9ct0267r5hc73996cbg`, 2026-07-17) for a disable. Its `toConfig` keeps the old values with `enabled: false`: `{"criteria":{"cpu":{"enabled":true,"percentage":60},"memory":{"enabled":true,"percentage":60}},"enabled":false,"max":2,"min":1}`.
- **Root cause:** `DeleteAutoscaling` (`lego/backend/internal/apps/service.go`) sets `spec.autoscaling = nil`. The Scaling page (`autoscaling-section.tsx`) then seeds its form from the zeroed view: min 1 and both targets at `DEFAULT_TARGET_PERCENT` (60).
- **Fix (target behavior):**
  - Disabling keeps `spec.autoscaling` with `enabled: false`. The operator and every read already treat a disabled spec as off; check the HPA teardown and the instance-count paths.
  - GET `…/autoscaling` returns the kept values with `enabled: false`, and the Scaling page pre-fills them.
  - The enable event's `fromConfig` carries the kept values, as on Render; w4/m335 reads it as zeros today. A disable's `toConfig` already keeps them (w4/m335).
  - The REST PUT with `enabled: false` behaves like DELETE.
- **Tests:** disabling, then reading, returns the kept range and targets with `enabled: false`. Re-enabling from the page submits them unchanged. An enable after a disable shows the kept values in `fromConfig`.
- **Dedupe:** w4/596 (a service read lacks Render's `serviceDetails.autoscaling`; a different field), w4/m335 (records the targets; an enable's `fromConfig` reads as zeros) and w4/568 (done). No open item covers keeping the settings.

- **2026-11-11 (loopx w4):** done. `DeleteAutoscaling` (REST `DELETE`, `PUT` with `enabled: false`, GraphQL `disableAutoscaling`, MCP `disable_autoscaling`) and a Blueprint `numInstances` now turn autoscaling off through `turnOffAutoscaling`, which keeps the range and targets with `Enabled: false`; a type autoscaling never applies to has them cleared. `GET …/autoscaling`, the REST disable answer and `serviceDetails.autoscaling` read the kept settings with `enabled: false`, and the Scaling page pre-fills them. The operator, metrics, the disk guard, the plan-downgrade cap and Blueprint export already gate on `Enabled`. An enable after a disable records the kept settings as its from side: migration `0234_audit_autoscaling_enabled_from` stores whether that side was running, REST `fromConfig` reads it with `enabled: false` as on Render, GraphQL gains `autoscalingEnabledFrom`, and the Events line reads that side as Off. Tests: `TestDeleteAutoscalingKeepsTheSettingsTurnedOff`, the enable-after-disable leg of `TestAutoscalingEventsRecordTheTargets`, the REST disable answer, the Blueprint no-diff case, `TestAutoscalingEventDetailsCarryTheTargets`, the PG round trip, and the dashboard Scaling and Events tests. Review: the Blueprint `numInstances` path also cleared the settings and is fixed; whether Render's `PUT` with `enabled: false` stores the body's values is filed as w4/598 (blocked on a write probe).
