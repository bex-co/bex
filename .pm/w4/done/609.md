# 609 — A prebuilt-image deploy's `startedAt` is the backend pass that noticed it, 7–10 s after its new instance was already running, so "==> Deploying image" prints after the app's own first lines and Duration under-counts

Why: the deploy page, `bex deploys list`, REST/GraphQL `startedAt` and the `deploy_ended` event all date the rollout's start. Today that date is when the backend's observer happened to see the row in `update_in_progress`, not when the rollout began. The operator already records the dispatch moment (`status.releaseStart`, w4/449), but the backend uses it only for a row first seen already live.

- **Root cause:**
  - `recordDeploy` picks the evidence-backed start in `lego/backend/internal/store/reconciler.go:1023-1038`.
    - For `DeployBuildFailed`, `DeployPreDeployInProgress` and `DeployUpdateInProgress` it uses only `buildRunStart` (`:1025-1029`, the w8/287 fix).
    - A prebuilt image has no build window, so that is `nil`.
  - `TransitionDeploy` then stamps `COALESCE(started_at, $9, clock_timestamp())` for a dispatch-observing status (`lego/backend/internal/store/store.go:3089`; `DeployStatusStampsDispatch` includes `update_in_progress`, `deploy_lifecycle.go:91-97`). That clock is the pass that observed the row.
  - The operator's dispatch record is already there. `stampReleaseStart` (`lego/operator/internal/controller/release_identity.go:793-805`, called at `app_controller.go:656`) writes `status.releaseStart` when `ReleaseGeneration` moves forward.
    - The backend reads it through `releaseDispatchStart` (`reconciler.go:2111-2120`), but only in the `DeployLive` case (`:1030-1033`, w4/449).
- **Fix (target behavior):** a deploy with no build window has `started_at` equal to the operator's dispatch of its own release generation, `status.releaseStart.startedAt`. The pass that notices the row is used only when that record is absent.
  - In the `DeployPreDeployInProgress` and `DeployUpdateInProgress` cases, fall back to `releaseDispatchStart(cur, open)` when `buildRunStart` is `nil`, as the `DeployLive` case already does.
  - `releaseStart.startedAt` is RFC3339 with second precision. Clamp the start to no earlier than the row's `createdAt`, so "Deploy queued" still prints first when dispatch fell in the same second as creation. Apply the same clamp to the `DeployLive` fallback.
  - Leave `DeployBuildInProgress` alone. Its first observation is w8/287's open part.
