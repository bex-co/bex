# Every read of a service's activity feed errored: `w4/m112` added `stall_reason` to the outer SELECT and not to the CTE it reads from

Why: `ListServiceEvents` is the only query behind the service Activity tab, and it failed outright — `ERROR: column "stall_reason" does not exist` — for every service on the new build, because `serviceEventsQuery`'s `feed` CTE never produced the column its own outer `SELECT` names.

Found on 2026-09-21 while running the Postgres-backed suite with a live database to verify [`w4/117`](117.md). Nothing in `go test ./...` touches this SQL, so it had never been executed in this repository's default test run.

## What failed

```
--- FAIL: TestPGStore
    store_pg_test.go:100: image-pull facts = []
      (err list service events: ERROR: column "stall_reason" does not exist (SQLSTATE 42703))
```

Reproduced on unmodified `main` against a clean database, so it was not a side effect of the w4/117 change being verified.

## Mechanism

`serviceEventsQuery` is a `feed` CTE of four `UNION ALL` branches — deploy-started, deploy-ended, audit, fact — followed by an outer `SELECT` that reads the branches' columns **by name**. Only the first branch carries `AS` aliases; the other three are positional.

`w4/m112` added `stall_reason` in exactly two of the three places it had to: the outer `SELECT` list (`events.go:438`) and the sibling by-id query's projection (`:552`). The `feed` CTE was missed, so the outer `SELECT` named a column no branch produced and the whole statement failed to plan.

## Fix

`d.stall_reason` on the deploy-started branch — the only one that can carry it, since an ended deploy is terminal and `failure_reason` owns that story, which is the rule `w4/m112` itself wrote — and an empty string in the other three, keeping the branches positionally aligned.

`TestServiceEventsFeedBranchesAgree` is the cheap guard that needs no database: every `UNION ALL` branch must select the same number of expressions, and every name the outer `SELECT` reads out of `feed` must be an alias the first branch declares. Verified by removing the fix — it reports both symptoms and names `stall_reason` exactly.

## Outcome (2026-09-21)

Fixed and guarded. The full Postgres-backed suite (`internal/store`, then the whole backend with `BEX_TEST_DB_URI` set) is green.

**Worth noting for the next pass:** this is the second time in this drain that a defect was invisible to `go test ./...`. The Postgres-backed tests exist and are good; they are simply skipped without `BEX_TEST_DB_URI`, so a change to raw SQL can reach production unexecuted. That is a CI question rather than a code one, and it is recorded here rather than acted on.
