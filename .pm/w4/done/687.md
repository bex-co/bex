# 687 — A tracking issue keeps its first failure's title: `tracking-issue.sh open` rewrites an open issue's body but never its title, so #167 still reads "Tenant view is broken: 4/4 events" over a body that says the canary was held awake

Why: an operator reads the issue list by title. [w4/676](blocked/676.md) taught the tenant-view canary to name a held-awake fixture (exit 7) so that the alarm stops reading as an events outage. The first scheduled run after that fix sent the right title, but the open issue kept the old one.

- **Source / severity / estimate:** `/qa-find-bugs w4` round 494, 2026-11-16 07:27 UTC. Workflow run `43822245431` ("Production edge liveness", scheduled 07:13 UTC) is the first run after w4/676 steps 2–3. **Minor:** monitoring hygiene, with no tenant impact. ~20m.
- **Probe:**
  - `gh issue view 167 --json title,body`:
    - title: `Tenant view is broken: 4/4 events (the feed did not advance)`;
    - body: `Failing stage: **canary fixture held awake by a repeating caller (the events stage could not run)** (exit 7).`, whose probe output reads `was held awake by OpenStatus/1.0 from 85.239.239.149 every 60s`.
  - The run's "Open or update the tracking issue" step passed `--title "Tenant-view canary cannot run: canary fixture held awake by a repeating caller (the events stage could not run)"` (`.github/workflows/ssh-edge-liveness.yml:453`). `updatedAt` moved to 07:15:46Z, but the title did not change.
- **Cause:** `open_or_edit` (`scripts/lib/tracking-issue.sh:49-70`) runs `gh issue edit "$existing" … --body-file "$body_file"` on an existing open issue (`:54`, and `:65` after a lost create). It uses `$title` only in `gh issue create` (`:58`). `append` (`:80-92`) ends in the same `open_or_edit`.
- **Fix:**
  - When an open issue with the label exists, edit its title with its body: `gh issue edit "$existing" --title "$title" --body-file "$body_file"`. The title then always states the current failure.
  - Keep one open issue per label.
  - Extend `scripts/tracking-issue.test.sh` (stateful `gh` stub) with a case: `open` twice with different titles leaves one issue carrying the second title.
- **Blast radius:**
  - 11 workflows make 17 `open`/`append` calls.
  - Four pass a title that depends on the failure:
    - `deploy-canary.yml:121` (`steps.probe.outputs.stage`);
    - `ssh-edge-liveness.yml:123` and `:159` (`$class`);
    - `ssh-edge-liveness.yml:453` (the probe's title).
  - The other 13 pass fixed strings, for which a retitle is a no-op.
  - `close` is unchanged.
- **Unverified:** whether any workflow relies on an issue's title staying fixed (none was found by grep, and the helper finds the open issue by label, `open_issue` at `:43-46`).
- **Render:** n/a (bex's own monitoring).
- **Done when:**
  - The next `ssh-edge-liveness.yml` run that fails while #167 is open retitles #167 to that run's `steps.probe.outputs.title`.
  - `bash scripts/tracking-issue.test.sh` passes with the new case and fails without the `--title` edit.
- **Done 2026-11-16:** `open_or_edit` now passes `--title "$title"` on both edit paths (`scripts/lib/tracking-issue.sh`), so an update retitles the open issue; `scripts/tracking-issue.test.sh` gained the two-titles case, which fails with the old edit ("an update kept the first title") and passes with the fix. #167 is still open after failing run `43822245431`; the next failing `ssh-edge-liveness.yml` run retitles it to that run's `steps.probe.outputs.title` (`gh issue view 167 --json title`).
