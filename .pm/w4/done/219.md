# Long Docker-command confirmations hide Save and Cancel below the mobile viewport

Why: a valid service command can make the required confirmation impossible to use with a pointer on a small screen; scrolling cannot bring its actions into view.

**Severity:** major on the affected mobile workflow. **Estimate:** 55m. Live `$qa-find-bugs w4` continuous loop, cycle a1, 2026-10-08 local / 2026-10-09 UTC, credentials loaded from `muse.env` without exposing them. This schedules a fix; no product code changed.

## Reproduction and target behavior

1. Create an owned Free web service from Existing Image `busybox:1.37`, port 3000, with a command that serves a file using BusyBox httpd. This run's fixture was `qa-20261008-loop-a1-web`, `srv-db43mjjfuh0c73ao9dbg`.
2. Open `/services/<id>/settings` at **390×667**, choose **Edit Docker Command**, paste the 818-character command in the captured request below, and choose **Save changes**. Substitute the new fixture's URLs if desired; the long command must remain valid and comparable in length. Do not confirm yet.
3. After the entrance animation settles, the alertdialog is **358×998**, x16, y−165.5. Save is y727.5–763.5 and Cancel y771.5–807.5, both entirely below the 667px viewport. The start of the title is above the screen. The dialog has `overflow-y: visible`, `scrollHeight = clientHeight = 996`, and `scrollTop: 0`. A wheel gesture over it does not move the dialog or document. At **390×844**, Cancel is still wholly offscreen (860–896), and Save is partly clipped (816–852). Screenshot: `.playwright-mcp/qa-settings-a1-command-mobile-1.png`, verified on disk and viewed.
4. Escape, reload, and repeat: the same settled geometry returns, with no diagnostic styles. Escape can dismiss it; the finding is inaccessible pointer actions, not an inescapable browser.
5. Control: `httpd -f -p 3000 -h /tmp/www` produces a 358×270 dialog at 390×667; Save is 363.5–399.5 and Cancel 407.5–443.5. Both are reachable and Cancel works.
6. Control: the **same 818-character command** fits at **1280×900** (512×710, y95–805; both buttons 744–780), saves with GraphQL HTTP 200, and reaches Live at rev-3. External `curl -fsS https://qa-20261008-loop-a1-web.onbex.co` returns the command's complete metadata JSON. This is accepted runnable input, not a refused or failing command.
7. Target: on the same long-command dialog at both mobile sizes, keep the dialog inside the viewport and make its complete title/command, explanation, Save and Cancel reachable by **internal vertical scrolling**, with no horizontal overflow. Keep the short-command and desktop controls usable. Cancel/Escape must send no mutation, and confirmation must still save the exact command and start its deploy.

A temporary **DOM-only** diagnosis applied `maxHeight = "90vh"` and `overflowY = "auto"` to this alertdialog. At 390×667 it became y33.35–633.65, height 600.30; scrolling advanced `scrollTop` to 398 and brought Save to 528.35–564.35 and Cancel to 572.35–608.35. Reload discarded these styles and reproduced the defect. This proves the scoped remedy can express the target; it is not a deployed fix.

## Root cause and proposed fix

- `dashboard/src/features/services/components/deploy-card.tsx:135` puts the complete new command in the confirmation title for native Start Command, repository Docker Command and Existing Image Docker Command.
- `dashboard/src/features/services/components/editable-field-row.tsx:306` passes that title to ConfirmDialog without a content height/scroll cap.
- `dashboard/src/common/components/ui/alert-dialog.tsx:51` positions the content fixed at 50%/50% with a negative half-height translation, but supplies no maximum height or internal overflow. A taller-than-screen title therefore puts the top and footer beyond the viewport.
- ConfirmDialog already accepts `contentClassName` and forwards it to AlertDialogContent (`common/components/confirm-dialog.tsx:148`). Apply a viewport-height cap and internal vertical scrolling **only to EditableFieldRow's confirmation**, using that existing prop; do not silently change every ConfirmDialog or shrink/refuse/truncate valid commands. The temporary DOM probe establishes that these styles reach the actual consumer.
- Framework verified at the locked versions: **@radix-ui/react-alert-dialog 1.1.15** `dist/index.mjs:17–21,57–80` uses a modal Dialog, focuses Cancel with `preventScroll: true`, and prevents interaction outside. **@radix-ui/react-dialog 1.1.15** `dist/index.mjs:100–116` puts RemoveScroll on the overlay with the content as a permitted shard. **react-remove-scroll 2.7.2** `dist/es2015/SideEffect.js:103–111,130–146` prevents wheel/touch movement when that shard has no scrolling path. Radix permits scrolling inside properly bounded content; it does not give this application content a height cap.
- The layer accepts this command: `lego/types/v1alpha1/app_types.go:531` allows up to 4096 characters for StartCommand. `lego/backend/internal/apps/service.go:4042–4063` authorizes, validates and persists it; `settings_check.go:177–186` checks protection/type. The complete successful UI request and response below are stronger confirmation than the declaration alone.

## Blast radius and implementation units

1. **Scope audit — 10m.** Exhaustive production JSX search: EditableFieldRow has **22 sites in 15 files**. Exactly **six sites opt into confirmation**, in two files: DeployCard's command row and BuildDeploySection's Root Directory, Build Command, Dockerfile Path, legacy Source and Branch. Apply the cap to that shared confirmation path and cover all six; do not modify the 16 non-confirming row sites or the global alert-dialog primitive. The already-working short command needs a regression control.
2. **Scoped layout — 20m.** Cap the existing confirmation's height and allow internal scrolling through `contentClassName`. Preserve the full value, confirmation-before-write semantics, focus behavior and desktop layout.
3. **Real-browser regression and parity — 25m.** Use real Radix components and settle fonts/animations at 390×667, 390×844 and 1280×900. Assert bounds, scroll the footer into view, cancel with no mutation, and confirm the exact command once. Verify the five sibling confirm fields and the short-command control; a jsdom CSS-class assertion does not establish reachability.

Entrypoints: `/services/:id/settings`; the native/repository-Docker/image command variants share DeployCard. `/static/:id/settings` reuses ServiceSettingsPage for its applicable build fields. Render aliases `/web/*`, `/pserv/*`, `/worker/*`, `/cron/*` redirect to the service routes. Resource family: web/private/worker share applicable command rows; static has build-field confirmations but no runtime command; cron's schedule/command rows use EditableFieldRow without this confirmation; Postgres and Key Value naming/policy rows are non-confirming. Those siblings are source-traced, not all live-tested.

**Adjacent classes:** no REST/GraphQL/MCP shape or error taxonomy changes. Authorization, protected-environment retries, unauthenticated/forbidden/error/timeout handling retain their current behavior. No new resource-existence disclosure. Before confirmation the unchanged field draft is local and no write has occurred; normal save-pending behavior remains.

**Unverified:** native and repository-Docker command dialogs, the five sibling fields, static/cron/private/worker/datastore pages, Chinese copy, touch gestures and an authenticated Render mobile confirmation were not exercised. Wheel scrolling, Cancel/Escape, fresh load, short command and desktop save were exercised. Require sibling and touch verification during implementation rather than claiming this sweep proved them.

**Render:** [Render's deploy documentation](https://render.com/docs/deploys#start-command) supports changing Docker Command from service Settings and running compound commands. It does not specify the mobile confirmation geometry; no pixel-parity claim. ADR004 and ADR008 govern runnable deployment configuration and usable hosting. The fix is UI-only; retain the accepted backend command and deploy contract on all transports.
