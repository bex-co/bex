# 638 — A Git-backed service's first deploy never carries `commit.createdAt`: `CreateApp`'s deploy insert drops the resolved commit's author time, so REST, MCP and GraphQL omit it on the `create` deploy and show it on every later deploy of the same commit

Why: w2/m42 promised that "a Git-backed deploy's REST/GraphQL/MCP representations carry `commit.createdAt` equal to the commit's author timestamp", omitted only when resolution is unavailable. Here resolution succeeded: the first deploy carries the commit id and message, and a manual deploy of the same commit a minute later carries the time. Every Git-backed service's first row in Deploy history lacks the commit time that every later row shows.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 308, 2026-11-13 16:51–17:00 UTC (`muse.env`, workspace `bex-canary`; pin `1c4d721bc8dc`). **Minor** (a missing optional field on one row). ~30m.
- **Fixture:** static site `qa-20261113-r308-s` (`srv-dbrk0cdgh3vs73b14d2g`), created through REST from `https://github.com/bex-co/bex` `examples/static-site`, branch `main`, `autoDeploy: no`. Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe:**
  - The create deploy `dep-dbrk0cdgh3vs73b14d30` (`bexTrigger: create`), once `live`, on `GET /v1/services/{id}/deploys?limit=1`:
    - `"commit":{"id":"eaff00a60d398f6641dea074f813e37474299c3b","message":"docs(pm): w8/308 production check passed …"}`, with no `createdAt`;
    - MCP `get_deploy` returns the same `commit` without `createdAt`.
  - `POST /v1/services/{id}/deploys {}` → `dep-dbrk0ttgh3vs73b14d7g`, the same commit, `"createdAt":"2026-11-13T16:49:59Z"`.
  - GraphQL `deploys(serviceId:…) { id trigger commitId commitCreatedAt }`:

    ```
    [{"commitCreatedAt":"2026-11-13T16:49:59Z","commitId":"eaff00a6…","id":"dep-dbrk0ttgh3vs73b14d7g","trigger":"api"},
     {"commitCreatedAt":"","commitId":"eaff00a6…","id":"dep-dbrk0cdgh3vs73b14d30","trigger":"create"}]
    ```

  - The same pattern holds on a service this round did not create: `hello-go`'s create deploy `dep-dbkq3hdhhjfs73eiaheg` (read only) has no `commit.createdAt`, and its later deploys do.
- **Root cause:**
  - `Service.Create` resolves the branch once (`resolveDeployCommit`, `lego/backend/internal/apps/service.go:2725`; `commit.go:54-66`). It hands the full `store.CommitInfo` to `CreateApp` as `FirstDeployCommit` (`:2751`). `CommitInfo` carries `Hash`, `Message`, `AuthorAt` and `BuildID` (`lego/backend/internal/store/store.go:343-350`).
  - `CreateApp` (`store.go:1097`) opens the first deploy with `INSERT INTO deploys (id, app_id, trigger, image, generation, commit, commit_message, status, triggered_by)` (`:1145-1148`). `commit_author_at` is never written, so the row's `CommitAuthorAt` is nil.
  - Every other deploy insert writes it: `CreateDeploy` (`:2514`), the new-commit path (`:2454`) and `CreateRollbackDeploy` (`:2840`).
  - The readers are right as they are: REST `toRenderDeploy` emits `createdAt` only when `CommitAuthorAt` is set (`lego/backend/internal/deploys/rest.go:146-152`), and GraphQL `commitCreatedAt` formats the same pointer (`graphql.go:60`).
- **Fix (target behavior):** the create deploy stores `a.FirstDeployCommit.AuthorAt` in `commit_author_at`. Its `commit.createdAt` (REST, MCP) and `commitCreatedAt` (GraphQL) then equal the commit's author time, as on a later deploy of the same commit, and stay absent only when resolution failed.
  - The same insert also drops `FirstDeployCommit.BuildID`. Decide in the same change whether a service created from a build source should carry `build_id` on its first deploy, as Render's `deploy.buildId` describes ("the build this deploy shipped").
  - **Not verified:** whether `BuildID` is ever set at create.
- **Blast radius:**
  - One insert. It serves every `CreateApp` caller: REST/GraphQL/MCP create, Blueprint apply, and the dashboard's create.
  - Image-backed services have no commit and are unchanged.
  - A regression test in the store's create tests can assert that the first deploy row reads back `CommitAuthorAt`.
- **Unverified:** rows created before the fix keep no time. A backfill would need the GitHub resolution again; leave them as they are.
- **Dedupe:**
  - w2/m42 (done) added `commit_author_at`; its DoD covered "a Git-backed deploy", and the create path was missed.
  - w4/072 and w4/232 (done) touch deploy rows but not this column.
  - `grep -rln "commit_author_at\|commitCreatedAt" .pm` finds nothing on the first deploy.
  - Not deploy lag: `git log 1c4d721bc8dc..origin/main -- lego/backend/internal/store/store.go` is empty.
- **DoD (live):**
  - Create a static site from `examples/static-site` through REST and wait for `live`. `GET …/deploys?limit=1`, MCP `get_deploy` and GraphQL `commitCreatedAt` on the create deploy all carry the commit's author time, equal to a manual deploy's of the same commit.
  - Delete the fixture (`GET` 404).

- **Closed 2026-11-14 (`/loopx w4`):** `CreateApp`'s first-deploy insert (`store/store.go`) now writes `commit_author_at` and `build_id` from `FirstDeployCommit`, as every other deploy insert does, so the create deploy's REST/MCP `commit.createdAt` and GraphQL `commitCreatedAt` carry the commit's author time. `BuildID` is not set at create today (`resolveDeployCommit` leaves it empty), so `NULLIF` keeps the column null; writing it costs nothing if a future create path sets it. Older rows stay without the time. Test: `TestPGFirstDeployKeepsTheCommitAuthorTime` (real Postgres). Live DoD replays after the next production deploy.
