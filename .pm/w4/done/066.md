# 066 — Key Value `persistenceMode` is invisible and unchangeable in the dashboard, though `w6/m127` made it updatable

Why: `w6/m127`'s goal was "persistence is changeable after create **like every other Key Value setting**" — it is, on REST/GraphQL/MCP, but not on the dashboard, which is the surface the original bug was found on and the only one most users touch.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 pass 3, journey 12. Fixture `qa-0913c-kv` (`red-daj8i4ggsm7s73f63oa0`), free plan, deleted at end of run.

## The API half works — verified live, which closes `w6/m127`'s own deferred check

```text
PATCH https://api.bex.co/v1/key-value/red-daj8i4ggsm7s73f63oa0
{"persistenceMode":"snapshot"}
→ 200  options: {"maxmemoryPolicy":"allkeys_lru","persistenceMode":"snapshot"}

GET https://api.bex.co/v1/key-value/red-daj8i4ggsm7s73f63oa0
→ 200  options: {"maxmemoryPolicy":"allkeys_lru","persistenceMode":"snapshot"}
```

Created through the dashboard form with the default `Journal + Snapshot`, then changed to `snapshot` by one PATCH. Exactly what `w6/m127` t002 shipped.

## The dashboard half was never wired

After that PATCH the detail page still shows no persistence anywhere. Its sections are: Details, Connections, Networking, Instance type, Maxmemory Policy, Danger Zone — `persistenceMode` is neither **displayed** nor **editable**, while its sibling `maxmemoryPolicy` has a full editable section of its own.

The asymmetry is exact, and `maxmemoryPolicy` is the control case at every layer:

| | `maxmemoryPolicy` | `persistenceMode` |
| --- | --- | --- |
| backend GraphQL read field | ✅ `keyvalue/graphql.go:49` | ✅ `keyvalue/graphql.go:49` |
| backend setter | ✅ `setKeyValueMaxmemoryPolicy` | ✅ `setKeyValuePersistenceMode` (`graphql.go:231`) |
| dashboard detail query selects it | ✅ `keyvalue/api/keyvalue.graphql:94` | ❌ absent |
| dashboard mutation document | ✅ `keyvalue.graphql:157-160` | ❌ absent |
| dashboard hook | ✅ `hooks/use-set-key-value-maxmemory-policy.ts` | ❌ absent |
| dashboard detail section | ✅ "Maxmemory Policy" | ❌ absent |

`grep -rn "persistenceMode" dashboard/src | grep -v __tests__` returns hits in only three places, all on the **create** path: `routes/keyvalue.new.tsx:98,118,222`, `hooks/use-create-key-value.ts:24,76`, and the `CreateKeyValue` mutation (`keyvalue.graphql:110,121`). The detail route never reads or writes it.

The backend's own comment names the pairing it expected (`lego/backend/internal/keyvalue/graphql.go:227-232`):

> `setKeyValuePersistenceMode` is the sibling of `setKeyValueMaxmemoryPolicy` (w6/m127): `persistenceMode` becomes updatable post-create through the same [path]

## Bounded fix

Mirror `maxmemoryPolicy` exactly, one layer at a time: add `persistenceMode` to the detail query's selection set, add a `SetKeyValuePersistenceMode` mutation document and a `use-set-key-value-persistence-mode.ts` hook next to its sibling, and render a section modelled on the Maxmemory Policy one — same copy shape ("The operator applies the new policy on the next reconcile"), the three CRD values (`journal-snapshot` / `snapshot` / `off`), and the en+zh strings the create form already has. The `definitions.ts` splice follows `dashboard/CLAUDE.md`'s per-feature rule (offline codegen to reconcile, never a wholesale accept).

Worth deciding while there: a persistence change **rolls the pod** (`update_key_value`'s own description says so), so the section should say that, the way the Instance type section already warns "a rolling update that preserves data".

Sub-hour and single-surface, so an inbox note rather than a milestone.
