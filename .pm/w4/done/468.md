# 468 — A service's "used this month" bandwidth goes down between reads, because it is one `increase()` extrapolated over a window that keeps growing

Why: a month-to-date total that shrinks while traffic only grows is the Metrics page contradicting itself. Every reload shows a different, lower number, and the figure never matches what billing records for the same bytes.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 3, 2026-11-04 11:02–11:13 UTC (`muse.env`, `bex-canary`, pin `fb6098dd2e37`); **minor** (the dashboard misstates a total; no invoice effect shown); ~1h.
- **Probe (owned Free image service `qa-20261104-sleep`, `srv-dblh0a4ncp7s738f0u70`, created 10:59:53, deleted 11:13):**
  - **Dashboard,** `/services/<id>/metrics` → Outbound Bandwidth footer: `941 B used this month` (11:02) → `880 B` (11:07) → on three fresh loads `893 B` (11:08:06) → `887 B` (11:08:34) → `883 B` (11:09:03). Request logs grew from 17 to 18 lines over the same span.
  - **GraphQL, the source of truth** (from the page, `credentials:'include'`): `query($r:String!){monthToDateBandwidth(resourceId:$r){egressBandwidthMB httpEgressBandwidthMB degradedSources}}` with `r = srv-…` → ×1048576 = `2291.94 B` (11:11:43) → `3208.11 B` (11:12:28, after scanner traffic) → `3203.78 B` (11:13:13, no new request). `degradedSources` is `[]` throughout. The fractional byte counts are the signature of extrapolation.
- **Root cause:**
  - `lego/backend/internal/metrics/service.go:1269-1273`: the window is `[monthStart, now]`, and for an App created this month it starts at creation.
  - `metrics/source.go:657-690`: `NewMonthToDateBandwidthSource` runs one instant `egressquery.Increase(spec, elapsed)` per source (`egressquery/query.go:164-166`, `sum(increase(counter[Ns]))`).
  - Prometheus `increase()` scales the first-to-last delta by `(sampled span + edge extrapolation) / sampled span`. With a flat counter the delta stays fixed while the sampled span grows, so each read is smaller and approaches `last − first`. That limit is itself short of the truth, because the bytes counted before the router series' first scrape (`first`) are never included.
  - w4/m119 t002 accepted `increase()` here because "the edge error is bounded by about one scrape interval at each end … under ~0.01% across a month". That holds only for a month-long, fully sampled window. It fails for every App created this month and every counter born mid-window (a new router series on first request, or a pod restart).
- **Fix (target behavior):** the month-to-date figure is monotonic within a month and equals billing for completed hours. Compose it as the sum of this App's recorded `egress_bytes` usage rows for completed hours since `monthStart` (ADR023's metered, health-gated hours, from the usage store), plus the current partial hour from the existing `Increase` read. GraphQL `monthToDateBandwidth`, REST `/v1/metrics/bandwidth` and the dashboard footer all read that one value. `degradedSources` keeps its meaning.
- **Blast radius:** `egressquery.Increase` has two callers, `metrics/source.go:677` (this footer) and `usage/service.go:1509` (hourly billing). Billing's hour window is short and fixed and is health-gated (`queryEgressSourcesEvidence`, `:1486-1530`), so it is not changed here.
  - **Unverified:** whether a router series born inside a billed hour loses its first-scrape bytes in the metered row too (the same `first` omission). Check it in the same pass with an owned fixture, and file separately if real.
  - The Outbound Bandwidth chart uses `SumIncreases` per bucket (m119 t002's documented divergence) and is not in scope.
- **Tests:** a source test where a flat counter read at two later instants yields a non-decreasing figure; completed hours come from usage rows (real-DB); and a regression keeps the current-hour estimate for a service with no completed hour yet.
- **Render:** Render's `monthToDateBandwidth` is the month's accumulated egress and never decreases within a month.
- **Dedupe:**
  - w4/m119 (done) t002 is the origin decision. This note shows its bound fails for short or young windows and makes the footer monotonic; it does not reopen the chart.
  - w1/m50 and w1/m155 (done) cover the source split and the REST contract.
  - `git log -S"NewMonthToDateBandwidthSource"` → `119800de8` (w1/m50) is the only change, so nothing is pending deploy. No DO_NOT_DO item applies.

- 2026-11-04: fixed by the loopx w4 drain without the usage-row composition: `metrics.monthToDateIncrease` sums ended UTC hours (`egressquery.CompletedHoursIncrease`, a hour-aligned subquery evaluated on the hour, fixed once an hour ends) plus the current partial hour, so a flat counter never reads lower. Usage rows were not used because they store one total per hour with degraded sources skipped, losing the HTTP/direct/WebSocket split the footer shows. Recorded in ADR023. The unverified "first-scrape bytes" question stays open as the existing limit.
