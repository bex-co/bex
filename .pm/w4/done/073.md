# 073 — The Deploys tab never shows a deploy that starts while you are watching: the header polls `Deploys(limit:1)`, the list's `limit:20` array never refetches

Why: the same page simultaneously said "Building… Deploying… Live" in its header and showed a deploy list that did not contain that deploy — for 96 seconds and indefinitely until navigation — so the surface that exists to answer "what is deploying?" is the one that cannot see it.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 pass 17, journey 3 (cancel + deploy hook). Fixture `qa-20260913-hk` (`srv-dajhn2ggsm7s73f63vs0`), free plan, `examples/hello-go`, docker runtime — created, deployed five times, cancelled twice, hook-fired once, deleted inside the run.

## The measurement

Fresh load of `/services/srv-dajhn2ggsm7s73f63vs0/deploys`, then the service's **deploy hook** fired from the same page — a genuinely external trigger, the exact case a CI pipeline or a teammate produces. Nothing was navigated or reloaded for the next 96 seconds; the header and the list were sampled from the one live DOM:

```text
POST <deploy-hook-url>  → 200 {"deploy":{"id":"dep-dajhsiogsm7s73f6401g"}}

 t=16s   rows 4   new rows: none   header: Service | Running  | Latest deploy | Live
 t=32s   rows 4   new rows: none   header: Service | Building | Latest deploy | Building
 t=48s   rows 4   new rows: none   header: Service | Building | Latest deploy | Building
 t=64s   rows 4   new rows: none   header: Service | Deploying| Latest deploy | Building
 t=80s   rows 4   new rows: none   header: Service | Running  | Latest deploy | Live
 t=96s   rows 4   new rows: none   header: Service | Running  | Latest deploy | Live

API at t=96s: dep-dajhsiogsm7s73f6401g  status live  trigger deploy_hook   ← the row the list never grew
```

The header narrated the entire lifecycle correctly. The list stayed at its four pre-existing rows and never acquired a fifth. A reload shows it immediately.

## Root cause — two reads of the same document, one polling, keyed apart by variables

Both hooks execute **`DeploysDocument`**; Apollo caches a root-field result **per variable set**, so they are two independent arrays:

| hook | variables | poll |
| --- | --- | --- |
| `features/deploys/hooks/use-latest-deploy.ts:30-46` (header badge) | `{ serviceId, limit: 1 }` | ✅ `useConvergingPoll` — 3s while non-terminal, 30s baseline, `skipPollWhenHidden` |
| `features/deploys/hooks/use-deploys.ts:92-96` (the list) | `{ serviceId, status, limit: 20 }` | ❌ none — `fetchPolicy: "cache-and-network"`, `errorPolicy: "all"`, no `pollInterval` |

`cache-and-network` refetches when the **hook mounts or its variables change** — not on a timer. So while you sit on the tab, the `limit:20` array is frozen at whatever the page load returned.

**Why existing rows still advance, which is what makes this subtle.** Measured separately in the same run: a deploy already in the list moved **Building → In Progress → Live** in place without navigation. That is Apollo's *normalized entity* update — the polling `limit:1` query rewrites the `Deploy:dep-…` entity, and the list re-renders because it holds a reference to that same entity. What a poll of a *different* variable set cannot do is append an id to the `limit:20` array. Hence the exact split: **statuses update, arrivals do not.**

This is the anomaly in my own capture that pinned the mechanism — the header and list disagreed while both read the same field of the same document, which is only possible if they are separately-keyed cache entries.

## Target behavior

**Poll the deploys list on the same converging cadence the header already uses, so a deploy's arrival is as visible as its progress.** `useDeploys` adopts `useConvergingPoll` + `skipPollWhenHidden` (already imported by its sibling), converging while any listed deploy is non-terminal **or** the service's phase is non-terminal, and falling back to `RESOURCE_POLL_INTERVAL_MS` (30s, `common/lib/polling.ts:11`) otherwise — a settled history still needs the slow tick, because that is the only thing that can notice a *new* deploy.

**One hazard the fix must handle, or it will trade a stale list for a corrupt one:** `use-deploys.ts` implements its own pagination — `loadMore` imperatively queries past the last-loaded id and appends pages into component state (`:99-113`), merged with a plain spread at `:106-109`. A poll that returns a **new** newest deploy shifts the keyset by one, so page 1's tail moves into territory an appended page already holds, and the spread will render a duplicate row (React key collision on the deploy id). Dedupe by id when merging, and decide explicitly whether a poll that changes page 1 should drop appended pages the way a filter change already does (`:104`).

## Relationship to `w6/m46/t005` — the mirror image, not a regression

`w6/m46/t005` fixed the **inverse** asymmetry and is why the header is the good half today: it added the converging poll to `useLatestDeploy`, and its own write-up records the then-current state as _"the deploys list DOES update correctly and promptly — only the header pill lags."_

That sentence was **true and still is**, for the case it was about: status changes on an existing row, which this run re-verified working (Building → In Progress → Live in place). The arrival of a *new* row was never in its view. So this is not a regression of m46 and not a contradiction of it — it is the half of the same asymmetry that the fix left on the other side. Worth stating in the fix's comment so the next person does not "restore symmetry" by removing the header's poll.

## Severity and the classes around it

**Major** — the product misleads on a core hosting surface, and the affected triggers are the ones a real team uses: a Git push (auto-deploy), a CI deploy hook, `bex deploy` from the CLI, a teammate's click, and any deploy started in another tab. A user who clicks **Manual Deploy** in *this* tab is fine, because the mutation refetches — which is exactly why this survives ordinary single-user clicking and shows up the moment a second actor exists.

Adjacent states, all unchanged by the proposed fix: a **filter** change already refetches (variables change), **`loadMore`** stays imperative, an **errored** poll keeps the last good array via `errorPolicy: "all"`, and a **hidden tab** must keep skipping polls (`skipPollWhenHidden`) so a backgrounded dashboard does not bill a request every 3 seconds.
