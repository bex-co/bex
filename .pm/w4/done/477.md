# 477 — Month-to-date bandwidth still goes down between reads inside the current hour (w4/468 regression residual)

Why: w4/468 promised a month-to-date figure that "is monotonic within a month". The fix only made ended hours fixed. The current hour is still one `increase()` over a window that grows with every read, so a new service, or any service during a quiet stretch of the hour, still reads lower on each reload.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 43, 2026-11-05 04:54–04:58 UTC (`muse.env`, `bex-canary`, pin `dcdc774c1a6b`, which contains the 468 fix `c09ded60e`); **minor** (the dashboard misstates a total; billing is unaffected); ~45m.
- **Probe:** owned Free Docker web service `qa-20261105-replay` (`srv-dbm0mcgj8n6s73bags40`, `github.com/bex-co/bex` `examples/hello-go`). It was created 04:50:58, got 31 `curl` requests at 04:54:41 and no traffic from this run afterwards, and was deleted at 05:05. From the dashboard page (`credentials:'include'`), `POST https://api.bex.co/graphql` `query($r:String!){monthToDateBandwidth(resourceId:$r){egressBandwidthMB httpEgressBandwidthMB degradedSources}}` with `r = srv-dbm0mcgj8n6s73bags40`, read every 45 s; `egressBandwidthMB × 1048576`:
  - `04:54:47 4127.38` → `04:55:32 4125.97` → `04:56:18 4123.54` → `04:57:03 4123.82` → `04:57:48 4122.60` → `04:58:34 4122.01`. `degradedSources` is `[]` throughout.
  - The fractional byte counts are still the signature of extrapolation.
- **Root cause:** `lego/backend/internal/metrics/source.go:971-990` `monthToDateIncrease`:
  - When `since` and `at` fall in the same UTC hour (every App in its first hour), `:975` returns one `egressquery.Increase(spec, at−since)`. That is the pre-468 read exactly.
  - Otherwise `:986` adds `egressquery.IncreaseOrZero(spec, partial)` with `partial = at − hourStart`. This is the same growing-window `increase()`, now bounded to the hour. So every service's figure can still fall within the hour, and only the ended-hours term (`CompletedHoursIncrease`, `egressquery/query.go`) is fixed.
  - The 468 tests (`metrics/metrics_test.go:1156-1205`) feed canned per-query values, so they cannot see Prometheus extrapolation. The 468 note's own Tests bullet ("keeps the current-hour estimate for a service with no completed hour yet") pinned the broken path.
- **Fix (target behavior):** with no new egress, two successive reads of `monthToDateBandwidth` (and REST `/v1/metrics/bandwidth`, and the Metrics footer, which read the same source) return a non-decreasing value, including in an App's first hour. The current-hour term must not extrapolate. Candidates, to be checked against the Prometheus version production runs:
  - a non-extrapolating per-series delta over `[hourStart, at]` that handles resets (for example, the sum of positive sample-to-sample deltas); or
  - clamp the current-hour term per source to at least the last value this hour already returned (needs state, so less preferred).
  - Pick one, record it in ADR023 next to the w4/468 paragraph, and keep the ended-hours term unchanged.
- **Tests:** a test against a real Prometheus (or a PromQL engine test) where a flat counter read at two later instants inside one hour yields a non-decreasing figure, for both the first-hour path (`:975`) and the partial-hour path (`:986`).
- **Blast radius:** `egressquery.Increase` / `IncreaseOrZero` also back billing (`usage/service.go`, fixed hour windows) and the chart (`SumIncreases`). Change only the month-to-date current-hour read.
- **Unverified:** an older service (with ended hours) was not probed this round; the `:986` path is inferred from code, not observed.
- **Render:** Render's month-to-date bandwidth never decreases within a month.
- **Dedupe:** regression residual of w4/468 (`.pm/w4/done/468.md`, whose DoD this does not meet). `grep -ril "partial hour" .pm` finds only 468 and unrelated billing items (w4/m173 t007). No DO_NOT_DO item applies.

Closed 2026-11-05: the current-hour term is now `egressquery.ExactDelta` (counter minus its value at the hour start, no extrapolation) for both the first-hour and partial-hour paths; recorded in ADR023. Real-engine check is `TestExactDeltaOnPrometheus` (promtool).
