## Objective

Pick one trigger-during-active behavior and implement it on both surfaces: today the dashboard forbids what the server performs.

## Context

### The observation (production, 2026-09-17, same fixture)

- Dashboard Events → Recent Runs: Trigger Run `disabled` with `title="A run is already in progress"` while a run is active.
- Same instant, direct GraphQL `runCronJob` → `200 {"id":"crr-h24…","status":"pending"}`; the active scheduled run flipped `canceled` (server-side preemption). Preemption is deliberate and tested (`TestTriggerCronRunReturnsPendingRunAndCancelsActive`; operator comment "a manual trigger explicitly cancels the active Job").
- Sting: the disabled button blocks the in-UI recovery for this milestone's own zombie (trigger-to-preempt a wedged run) — the probe had to drop to raw GraphQL.

### Fix shape

- Recommended: enable Trigger Run during an active run with a confirm dialog ("A run is in progress — triggering cancels it and starts a new run. Proceed?"), matching the existing Cancel-run confirm pattern. The server already implements exactly this semantic; no backend change.
- Alternative (only with product sign-off): make the server reject trigger-during-active with 409 like the dashboard implies, and update the preemption test + operator comment. Do not leave the split.
- Either way the tooltip/disabled-reason copy must describe the SHIPPED behavior, not the other surface's.

### Acceptance

- One behavior, both surfaces: UI permits-then-confirms iff the server preempts; UI disables iff the server 409s. Verified live in t006 (button state + mutation response on an active run).
