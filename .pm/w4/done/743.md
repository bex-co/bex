# A new Key Value instance always runs Valkey 8, with no version choice, as Render's does

Why: Render parity. Render's create form has no version field, and "Newly created Render Key Value instances run Valkey 8". bex's form, GraphQL and CRD let a customer create a Valkey 7 store Render never offers, and ADR018 does not record it.

- **Render (read 2026-11-27):** [valkey-faq](https://render.com/docs/valkey-faq): "When you create a new Render Key Value instance, that instance automatically runs Valkey"; [key-value](https://render.com/docs/key-value): "Newly created Render Key Value instances run Valkey 8". The `/new/redis` form's fields are Name, Project, Region, Maxmemory Policy, Persistence Mode and Instance Type ([key-value.md](../../docs/render-artifacts/key-value.md)).
- **bex:** the create form has a "Valkey version" select with Default, Valkey 8 and Valkey 7 (`dashboard/src/features/keyvalue/pages/new-key-value-page.tsx`, `VERSIONS = ["8", "7"]`). GraphQL `createKeyValue` takes `version` (`lego/backend/internal/keyvalue/graphql.go`), and the CRD's `spec.version` enum allows `"7"` (`lego/types/v1alpha1/keyvalue_types.go`).
- **Do:** drop the select from the form and stop accepting `version` on GraphQL create (or accept only `8`), as Render's surfaces do. Keep existing Valkey 7 instances running and readable. Record in ADR018 § Other datastores & storage: Key Value (Valkey / Redis) that a new instance always runs Valkey 8.
- **End state:** the create form has no version field, a GraphQL create with `version: "7"` is refused or ignored, and every new instance reports Valkey 8.
- **Size:** about 45m.
- **Source:** w4/m688 t002, a full read of Render's valkey-faq page, 2026-11-27.

**Done 2026-11-27 (w4/743):** no create surface offers a version, and every new store runs and reads Valkey 8. The create form has no Valkey version select (its route skeleton region and the three translated strings went with it), GraphQL `createKeyValue` has no `version` argument (a call naming one gets GraphQL's unknown-argument refusal), MCP `create_key_value` has none (its schema refuses one), and a REST `POST /v1/key-value` or `/v1/redis` body naming `version` is refused 400 as an unknown field, as it was a bex extension Render's `keyValuePOSTInput` lacks. A new store leaves `spec.version` empty, which the operator runs as Valkey 8. The CRD still admits `"7"`, so a store created on Valkey 7 keeps running it and reads `7` on REST, GraphQL and MCP. Pinned by `TestKeyValueCreateOffersNoVersionAndRunsValkey8` (composed REST gate and GraphQL; fails with the fix reverted), `TestMCPCreateKeyValueOffersNoVersion` (also fails reverted), `TestExistingValkey7StoreStillReadsValkey7` and the create page's test. Recorded in ADR018 § Other datastores & storage: Key Value (Valkey / Redis), ADR021 §6 and its version-change assessment, the REST extension table in `openapi-request-validation.md`, and the `valkey-faq` row of `docs-pages.md` (now `matched`).
