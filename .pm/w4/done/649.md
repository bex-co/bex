# 649 — The registry still restarts zot once when its storage settings change (`ensureStorageActive`, w8/m156), including on a fresh install's first App, though zot v2.1.22 reloads those settings live: drop the restart as w4/m347 did for credentials

Why: w4/m347 found that the pinned zot (v2.1.22) reloads its password file and access-control config while running, and replaced the credential-activation restart with a pod-annotation nudge. The one remaining routine restart is `ensureStorageActive` (`lego/operator/internal/registry/storage_active.go`), which rolls the single zot pod when the storage settings (garbage collection, retention) change — on a fresh install that is the first App's build. A zot restart drops in-flight pushes and pulls for every workspace (round 190's failure mode).

- **Source / severity / estimate:** `/loopx w4` closeout of w4/m347 (2026-11-14), from the implementer's reading of zot v2.1.22. **Minor** (rare: storage settings change on install and on deliberate config changes). ~40m.
- **Premise to verify first:** zot v2.1.22 applies a changed `storage.gc`/`retention` config without a restart. The implementer read that retention reloads only when zot's metadata database is enabled; check the pinned config (`deploy/gitops/base/` zot values) and zot's config watcher at v2.1.22. If a setting truly needs a restart, keep the restart for that setting only and say so in ADR022.
- **Fix:** write the storage settings, nudge the pod as `verify.go` does for credentials, and confirm activation by observing the setting (or keep a last-resort restart behind the same `bex_registry_activation_restarts_total` alert).
- **Tests:** a storage-setting change patches no pod template and deletes no pod; the last-resort path still restarts after its timeout.
- **DoD:** on the mock cluster, a storage-setting change leaves `zot-0`'s restart count unchanged and the new setting is in effect.
- **Closed 2026-11-14 (/loopx w4):** The premise holds, checked in zot v2.1.22's source (tag cloned to a scratch directory). `HotReloader.reloadConfig` (`pkg/cli/server/config_reloader.go`) stops the background tasks, calls `Controller.LoadNewConfig` and starts them again. `Config.UpdateReloadableConfig` (`pkg/api/config/config.go`) copies `storage.gc`/`dedupe`/`gcDelay`/`gcInterval`, and copies `storage.retention` whenever the running config already enables retention (`isRetentionEnabledInternal`, backed by the metadata DB `InitMetaDB` opens at start). `RunGCTasks` (`pkg/api/controller.go`) rebuilds GC and retention from the new values. Every operator-written config since w7/m36 keeps tags by count, and zot cannot start before `zot-config` exists (a non-optional Secret volume), so no operator storage change needs a restart and none is kept. ADR022 § Credential activation records this and names `rootDirectory` as the one non-reloadable field (the operator writes a constant there). `ensureStorageActive` and `storage_active.go` are deleted. A storage change rides the same `zot-config` write as the ACL, and that write already ends with the `recordWrite` nudge. A broken reload still trips the credential last resort behind `RegistryCredentialActivationRestarted`. On the mock cluster (zot v2.1.22 at the production digest), writing the m156 rule order, retention count 6 and `gcInterval: 2h` into `zot-config` and nudging `zot-0` reloaded in about 1 s: `loaded new configuration settings` showed the new retention and GCInterval 2h, the next GC pass logged `retained by mostRecentlyPushedCount:6 policy` (and `:10` for `live-` tags), and no "outside the reloadable set" warning appeared. `zot-0`'s UID and restart count were unchanged, and the original block was written back afterwards. Tests: `TestAStorageChangeReloadsWithoutRestart` replaces `TestAStorageChangeRestartsZotOnce` (a fresh install, then a storage-only change: one nudge, no pod delete, the new block projected), and `TestRestartOnlyWhenHotReloadFails` still covers the last resort. `GOWORK=off make -o test-tool-download test` and `scripts/gitops-validate.sh` pass. Live DoD replays after the next production deploy.
