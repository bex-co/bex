## Objective

Download the resolved release asset and atomically replace the running binary, restoring the previous binary if any step fails.

## Context

- Researched pattern (`w4/030.md`): `creativeprojects/go-selfupdate` (maintained fork; per-target asset selection, rollback on failure, hash/signature validators). Evaluate it vs. a small hand-rolled replace — pick one and record why in the code comment. If adopting the dep, add it to `cli/go.mod` and keep it confined to the upgrade package.
- Atomic replace = write to a temp file in the target dir, `chmod +x`, then rename over the running binary (Unix rename-over-self is safe); keep the old binary until success so rollback is possible.

## Steps

1. Download the t001-resolved asset to a temp file alongside the target binary.
2. (Verification hook is t003 — call into it before replace once it lands.)
3. Atomically rename the new binary over the running one; on any failure restore the prior binary and return a clear error.
4. Print the resulting `vOLD → vNEW` line on success.

## Files

- `cli/internal/upgrade/` (new) or `cli/main.go`
- `cli/go.mod` / `cli/go.sum` (only if `go-selfupdate` is adopted)

## Acceptance criteria

- [ ] A newer release is downloaded and atomically replaces the running binary.
- [ ] A simulated failure mid-replace leaves the original binary intact (rollback works).
- [ ] Success prints the old→new version transition.

## Out of scope

- Signature/checksum verification (t003) — leave a clear call site.
- Package-manager path detection (t004).
