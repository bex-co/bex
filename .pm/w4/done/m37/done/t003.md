## Objective

Before the t002 replace, verify the downloaded asset against the release's `checksums.txt` (mandatory) and its cosign signature (reuse the platform's cosign infra). Abort the upgrade — leaving the running binary untouched — on any verification failure.

## Context

- m35's `.github/workflows/cli-release.yml` already produces `checksums.txt`; confirm whether release assets are cosign-signed and, if not yet, add signing there (the platform already runs cosign for tenant images — reuse that infra/keys per `w4/030.md`).
- Verification must run **after** download and **before** the atomic rename in t002 — a failed check must never replace the binary.
- Trust bar: a bad checksum or bad/missing signature is a hard failure, not a warning.

## Steps

1. Fetch `checksums.txt` from the release; compute the downloaded asset's SHA-256 and require an exact match.
2. Fetch the asset's cosign signature + public key (or keyless/Rekor per the platform's existing pattern) and verify; hard-fail on mismatch or absence.
3. Wire the verification call into t002's replace path so replace only proceeds on success.
4. If release assets aren't signed yet, add cosign signing to `cli-release.yml`.

## Files

- `cli/internal/upgrade/` (verification)
- `.github/workflows/cli-release.yml` (only if signing must be added)

## Acceptance criteria

- [ ] Checksum mismatch aborts before replace; running binary untouched.
- [ ] Missing/invalid cosign signature aborts before replace.
- [ ] Valid checksum + signature proceeds to replace.
