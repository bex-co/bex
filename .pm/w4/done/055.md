# CLI health-check updates fail when a Dockerfile service omits its runtime

Why: the official Render CLI needs the current runtime to construct a partial service update; omitting it prevents tenants from changing the health-check path.

Source: the w4 README-only inbox entry originally numbered 052, reported 2026-09-07 while fixing eden-cms-v2. Renumbered to 055 during triage because 052.md already tracks malformed service IDs. Historical code references to w4/052 about runtime mean this note.

## Original report

`bex services update` can't change `healthCheckPath` (or any `serviceDetails` field) for a Dockerfile-runtime web service — the read API omits `runtime`/`env`, so the CLI can't round-trip it on PATCH ← found 2026-09-07 while fixing the `eden-cms-v2` (`srv-d9e40ei9086p3l1jri30`) deploy pipeline via the CLI. **Impact:** that service's health check was stuck on `/` (heavy homepage SSR: blog-feed disk reads + external `bex.co/forum` fetch + changelog + full SSR stream), which stopped passing the cold-container health check as the blog corpus grew — every deploy since built fine then failed after the ~18 min health-check timeout. The app already ships `/healthz` (a bodyless, no-SSR liveness probe) for exactly this, but `healthCheckPath` **cannot be repointed to it via the CLI** — only the dashboard or raw API works. **Repro (CLI `bex vdev`, Render CLI v2.22.0-compatible):** (1) `bex services update srv-… --health-check-path /healthz --confirm` → `Error: unsupported runtime ""` (CLI sends an empty runtime); (2) add `--runtime docker` → `Error: cannot switch runtimes via the CLI; use the API directly, or create a new service and delete the old one when you're ready`. **Root cause:** `bex services -o json` returns **no** `runtime`/`env` field anywhere in the service object (verified by recursive key scan), so the CLI can't preserve the current runtime on a partial update — with none supplied the backend rejects the empty value, and supplying the (correct) `docker` is treated as a runtime switch. Two suspected loci: backend GET-service serializer drops `runtime`/`env`; and CLI `services update` hard-requires runtime instead of doing a field-scoped PATCH. **Suggested fix:** have GET return `runtime`/`env`, and/or make `services update` a true partial PATCH that doesn't resend/flag an unchanged runtime. Note: did **not** test other `--runtime` values against the live service (a wrong guess risks a real runtime switch). Parity check vs upstream Render CLI (where `services update --health-check-path` works) would confirm the regression.

## Triage — 2026-09-07

Already fixed in the current code by `cca2f571d` (Dockerfile runtime projection), extended by `d58245084` / w9/m93 for prebuilt images. `effectiveRuntime` in `lego/backend/internal/apps/service.go` supplies `docker` for a repo with the default/auto/dockerfile builder, preserving explicit runtimes. `renderServiceDetails` emits both `runtime` and the deprecated `env` alias plus the matching Docker details. GraphQL/MCP consume the same view.

The upstream CLI error is local to its update builder, before PATCH; this was a missing read contract, not a backend rejection of an empty runtime in an incoming PATCH. No CLI fork or runtime switch is needed.
