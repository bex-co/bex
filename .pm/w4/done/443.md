# A webhook link opened while another workspace is selected redirects home, though the API now resolves webhooks by id

Why: w4/m172 made `/v1/webhooks/<id>` and its GraphQL/MCP twins find the webhook's own workspace, as w4/m169 did for Blueprints. The dashboard still sends the *selected* workspace as `ownerId` on every by-id webhook read and mutation. A shared or bookmarked `/webhook/<whk-id>` link from another of the user's workspaces therefore reads "not found" and silently redirects to `/`, which is the exact symptom m169 fixed for Blueprint links.

- **Source / severity / estimate:** w4/m212 live replay, loopx w4, 2026-10-31 (`muse.env`, `bex-canary`, pin `d147703d7657`); **minor**, ~30m. Same class as w4/m169 t002 (Blueprint deep links).
- **Repro:** with workspace `bex` selected, open `https://dashboard.bex.co/webhook/<whk-id>/settings` for a webhook owned by `bex-canary`. The page lands on `/`. After selecting `bex-canary`, the same URL opens normally.
- **Root cause:** `dashboard/src/routes/webhook.$webhookId.tsx:36-39` (loader `ownerId: context.workspaceId`) and `features/webhooks/hooks/use-webhook.ts:53` (`ownerId: currentWorkspaceId`) pin the selected workspace. The by-id mutations do the same: `use-set-webhook-enabled.ts:33`, `use-update-webhook.ts:62`, `use-delete-webhook.ts:32`, `use-resend-webhook-delivery.ts:51` and `use-webhook-deliveries.ts:209,258`. The backend's explicit-`ownerId` rule then answers a mismatched owner with 404 (`core.Base.ScopeByID`). `useNotFoundRedirect` turns that into the redirect.
- **Fix:** follow m169 t002. Drop `ownerId` from the by-id webhook reads and mutations, so the backend resolves the owner. Keep it on list and create (`use-webhooks.ts:76`, `use-create-webhook.ts:69`). Decide whether to show the owning workspace in the header or offer a switch, matching what the Blueprint page does.
- **Tests:** a route/hook test that the by-id `WebhookEndpoint` query and the enable/update/delete/resend mutations send no `ownerId`, and that list/create still do. Then a live check: with `bex` selected, a bex-canary webhook link opens its Settings and the toggle works.
- **Blast radius:** other dashboard by-id pages may pin the selected workspace the same way (registry credentials, environments). Sweep `ownerId: currentWorkspaceId` in by-id hooks while here, and record which pages were checked.
- **Dedupe:** w4/m169 covered Blueprints only; m172 was backend-only by design. No open item covers dashboard webhook links. No DO_NOT_DO item applies.

**Done 2026-10-31 (loopx w4):** the webhook detail loader (`routes/webhook.$webhookId.tsx`) and the by-id hooks (`use-webhook`, `use-set-webhook-enabled`, `use-update-webhook`, `use-delete-webhook`, `use-resend-webhook-delivery`, `use-webhook-deliveries`) no longer send the selected workspace as `ownerId`. The backend resolves the webhook's own workspace, as w4/m169 did for Blueprints. List and create still scope to the selected workspace. Live API check before the change, with bex-canary not the default workspace: GraphQL `webhookEndpoint`, `setWebhookEndpointEnabled`, `updateWebhookEndpoint`, `webhookDeliveries` and `deleteWebhookEndpoint` all answer for a bex-canary webhook without `ownerId` (the throwaway endpoint was deleted, REST 404). Tests: a new `use-webhook.test.ts`, and the resend/update/deliveries tests now assert no `ownerId`; the webhooks/routes suites (592) and lint pass. **Sweep:** the other `ownerId: currentWorkspaceId` hits are list/create calls, API-key revoke (its own w4/194 contract), or registry credentials. Registry credentials have no by-id route: the detail read only backs the edit dialog opened from the workspace-scoped list, and `workspace-scope.test.ts` pins that deliberately. A briefly filed w4/448 was withdrawn as invalid for that reason. The live "bex selected, bex-canary link opens" check rides the next dashboard pin.
