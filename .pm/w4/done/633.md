# 633 — One Blueprint apply that changes an env group and a linked service opens two deploys for that service: a `config_change` deploy from the group roll, canceled in the same second by the Blueprint's own deploy

Why: every such sync leaves a Canceled deploy on the service's Deploys page and a `deploy_started` → `deploy_ended (canceled)` pair in Events, webhooks and notifications, for a deploy nobody asked for. For a Git service, the first deploy can also start a build that the second throws away. A Render Blueprint sync deploys each affected service once.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 285, 2026-11-13 11:07–11:13 UTC (`muse.env`, workspace `bex-canary`; pin `5de3d5bcce8e`). **Minor** (a spurious canceled deploy and its events; the final state is right). ~1h.
- **Fixtures** (REST; deleted afterwards, `DELETE` 204 then `GET` 404):
  - env group `qa-20261113-r285-grp` (`evg-dbreuv0k58is73aunsv0`) with `GRP_A=group-one`;
  - Free web service `qa-20261113-r285-web` (`srv-dbreuv8k58is73aunt0g`), `docker.io/library/busybox:1.37`, `SVC_B=service-two`, linked to the group. Its page prints its `SVC_*`/`GRP_*` environment.
- **Probe:**
  1. **Round trip.** `POST /v1/blueprints/generate {"serviceIds":[S],"envGroupIds":[G]}` returned a manifest: the group key as `generateValue: true`, `SVC_B` as `sync: false`, and `fromGroup`. `POST /v1/blueprints/deploy {"ownerId":…,"bexYaml":<that manifest>}` returned 200 and changed nothing: no deploy, and the values were kept. This is correct.
  2. **The finding.** The same manifest, edited, was deployed at 11:09:58:
     - group: `GRP_A: value: group-changed` plus `GRP_NEW: generateValue: true`;
     - service: `SVC_C: value: three`.

     `GET …/deploys` then had two rows created at 11:09:58:

     ```
     dep-dbrf01gk58is73aunt4g  queued    bexTrigger=blueprint
     dep-dbrf01gk58is73aunt40  canceled  bexTrigger=config_change   ("Superseded by dep-dbrf01gk58is73aunt4g")
     ```

     Events carry `deploy_started` for both at 11:09:58 (`trigger.envUpdated: true` on the first) and `deploy_ended` `canceled` at 11:10:11. The Blueprint deploy went live at 11:10:59. The page then served `GRP_A=group-changed`, a generated `GRP_NEW`, `SVC_B=service-two` and `SVC_C=three`, so the final state is right.
- **Root cause:**
  - `DeployStack` applies env groups first (`lego/backend/internal/apps/deploy.go:963`, `applyStackEnvGroups` `:1044-1076` → `EnvGroups.ApplyEnvGroup`, `:1052`).
  - `ApplyEnvGroup` (`lego/backend/internal/envgroups/service.go:1490`) ends in `rollGroupPatch(ctx, g.ID, SaveModeDeploy, result)` (`:1573`). That rolls every linked service through `rollLinkedService` (`:1140-1145`) with `store.TriggerConfigChange`, which opens a deploy row.
  - The stack's service step then applies the service's own change and records its Blueprint deploy (`recordBlueprintRedeploy`, `deploy.go:4237`). That deploy supersedes the first.
  - `ApplyEnvGroup` has a single caller (`deploy.go:1052`), so the group roll inside it exists only for Blueprint applies.
- **Fix (target behavior):** in one Blueprint apply, each service whose effective config changes gets exactly one deploy row, with the Blueprint trigger (`blueprint`, which REST reports as Render's sync trigger). That holds whether the change came from its own declaration, a linked group's values, or both. A linked service that changed only through the group also gets one deploy, also with the Blueprint trigger.
  - **Mechanism options:**
    - `ApplyEnvGroup` saves with `SaveModeOnly` and returns the affected linked services. The stack rolls each of them once, in its service step, with the Blueprint trigger, merged with that service's own change.
    - Or pass the Blueprint trigger down and make the service step reuse a deploy row this apply already opened.
  - **Unchanged:**
    - an env-group edit from the dashboard, REST or MCP outside a Blueprint keeps its `config_change` roll of linked services, including the auto-deploy gating at `service.go:1147`;
    - an unchanged re-apply (probe 1) still opens no deploy.
- **Blast radius:**
  - `ApplyEnvGroup` has 1 caller (`deploy.go:1052`). `rollGroupPatch` has 2 callers in `envgroups/service.go` (`:891` for the ordinary group patch, which keeps its behavior; `:1573`).
  - Services linked to the group but not declared in this Blueprint must still be redeployed once, as today.
  - Regression tests:
    - a Blueprint apply with group + service changes opens 1 deploy;
    - group-only changes open 1 per linked service;
    - a re-apply opens 0;
    - a dashboard group edit opens its `config_change` deploys as before.
- **Unverified:**
  - Render's trigger name and count for a linked service whose group a sync changes. Render's docs say a sync deploys affected services, without the env-group case spelled out.
  - A Git-backed service, whose first, canceled deploy may already have started a build, was not probed.
- **Dedupe:**
  - `grep -rln -i "blueprint" .pm | xargs grep -li "superseded\|canceled.*config_change"` finds w4/174 (cron re-apply idempotence) and unrelated items. None is about a double deploy from one sync.
  - **Sibling, not a duplicate:** w8/306 (`15cf8f49c`, on `main` after this pin) fixed the same symptom, a first deploy canceled by a `blueprint_sync` one, for a different cause. There a service referenced a sibling declared later (`fromService`), and `referencedFirst` now orders the writes. It leaves the env-group roll (`ApplyEnvGroup` → `rollGroupPatch`) untouched, which is this item's cause.
  - Not deploy lag: `git log 5de3d5bcce8e..origin/main` over `envgroups/service.go` and `apps/deploy.go` shows only that commit.
- **DoD (live):**
  - Replay probe 2 on a fresh pair. `GET …/deploys` gains exactly one row, `bexTrigger: blueprint`, with no `canceled` sibling.
  - Events show one `deploy_started`/`deploy_ended` pair.
  - The page serves the four values.
  - Replay probe 1: no new deploy.
  - Delete the fixtures (`GET` 404).
- **Closed 2026-11-14 (/loopx w4):** `envgroups.ApplyEnvGroup` no longer rolls linked services itself. On a change it returns a `roll(ctx, deployed)`. `deployParsedStack` runs that roll after the service step, the fromService reference pass and ownership stamping. The roll goes through the existing `rollGroupPatch` with `store.TriggerBlueprintSync`, so it keeps the Auto-Deploy gate, the suspended and build-source skips, and stale-link pruning. It skips every service in `deployed`, a context-carried set like the host-claim scope. `patchChangedStackService` adds a service to that set once the patch for its Blueprint deploy lands, and that release already reads the group's new values. So each affected service gets exactly one `blueprint` deploy. A service changed by both its own declaration and its group gets only the service step's deploy. A service changed only through the group, declared or not, gets the roll's deploy. Choices: (1) a service changed only through its group gets the Blueprint trigger, as the note asks; Render's own value is unverified. (2) The roll also runs when a later step of the apply fails (deferred, `context.WithoutCancel`): the group's values are already written, so a retry would find the group unchanged and owe nothing. Non-Blueprint group edits (`SetEnvGroupVars`, `PatchEnvironment`, link and unlink) pass `store.TriggerConfigChange` explicitly and are unchanged. Tests: `apps/blueprint_env_group_roll_test.go` checks three things: a group + service change opens 1 deploy and no group roll; a group-only change rolls the declared service and an undeclared linked one; a failed service step still rolls. `envgroups/blueprint_roll_test.go` checks five: no deploy until the roll, then one `blueprint` row; a deployed service is skipped; an unchanged re-apply owes nothing; a dashboard edit still opens `config_change`. A mutation check (dropping the `deployed` note) fails the first test. `GOWORK=off go test ./...` and the real-deps suite (`BEX_TEST_REQUIRE_DEPS=1 go test -p 1 ./...` on `scripts/backend-test-deps.sh`) pass. Not covered, a possible follow-up: a sync that adds a new `fromGroup` link to an existing service still links it through `LinkEnvGroup`'s own `config_change` roll after the service step. Live DoD replays after the next production deploy.
