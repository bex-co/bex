# Cancel dialog promises "the last successful deploy remains live" when nothing is live yet

Why: canceling a service's very first deploy shows a reassurance that is false — after confirm, the service reads Canceled with nothing serving — so the dialog misleads exactly when the user is deciding whether cancel strands them.

## Record

- Severity: minor
- Repro: 1. create any service; 2. while its first deploy is Building, Cancel; 3. the confirm body reads "The in-progress deploy will be stopped. The last successful deploy remains live." Live 2026-09-19 on `qa-20260919-p30-priv` (`srv-danacqbs0ils73bgp5cg`, since deleted): after Proceed, header + list + events all read Canceled and no revision ever served.
- Expected / Actual: the body names the first-deploy outcome ("No version is live yet — canceling leaves the service with nothing serving") / the unconditional remains-live sentence.
- Root cause: `dashboard/src/features/deploys/components/deploy-actions.tsx:218-222` renders the single `services.eventsCancelConfirmBody` string (`dashboard/src/features/services/locales/en.ts:3933-3936`, + zh) for every cancel, with no first-deploy branch.
- Fix: thread a has-live-release flag into the cancel confirm (the deploy list already knows every row's status) and pick between two locale strings: keep the current sentence when a live release exists; render the nothing-serving sentence when the canceled deploy is the service's first (en + zh + the deploy-actions test).
- Blast radius: one dialog body + 2 locale files; `eventsCancelConfirmBody` has exactly 1 consumer (`deploy-actions.tsx:220`). Rollback confirm (`rollbackBody`) already varies and is untouched.
- Adjacent classes: canceling a later deploy (live release exists — current sentence stays true); canceling a queued vs building deploy (same body — unchanged); rollback dialog (unchanged).
- Unverified: the zh rendering (string change only — needs a locale-table test, not a live pass).
- Render: n/a (bex-own dialog copy; the fix makes bex's own dialog truthful).
- Estimate: 25m

## Resolution (2026-09-21)

Done. `DeployActions` takes an optional `trigger`, and the cancel confirm picks between two locale strings: the existing "the last successful deploy remains live" sentence, or — when the deploy being canceled is the service's first (`trigger: "create"`) — "This is the service's first deploy, so no version is live yet — canceling leaves the service with nothing serving." en + zh both added.

Threaded at all three call sites: the deploys list and the deploy detail page pass the deploy's own trigger string; the events feed passes `"create"` when the event's Render-shaped `trigger.firstBuild` flag is set, which is the same cause under the other vocabulary.

**The discriminator is "first deploy", not "nothing is live", and the difference is worth stating.** A service whose first build *failed* and whose second deploy is then canceled also has nothing serving, and still gets the generic sentence. Closing that would need a has-live-release signal none of the three call sites holds today: the deploys list is paged (so "does any row read live" is not answerable from what is in hand), the detail page has one deploy, and the rollback capability's `no_eligible_rollback_target` means something different — it is also false when exactly one release is live, since there is nothing to roll back *to*. The first-deploy case is the one the note reported and the common one; the remainder is named here rather than silently absorbed.

The fallback direction is deliberate: a caller that does not pass a trigger gets the pre-existing, less alarming body, pinned by its own test.

Covered by `DeployActions — the cancel dialog tells the truth about what stays live`: the first-deploy body appears and the remains-live promise does not, four non-create triggers keep the original sentence, and an unknown trigger falls back safely. The note's unverified zh rendering is covered by the locale-parity test (both keys present in both files); not re-probed live.
