## Objective

A manifest that declares `domains:` must leave an already-matching service's spec untouched. Today applying it moves the primary domain out of `Spec.Host` into `Spec.Hosts`, so an exported manifest re-plans as `update` forever.

## Context

- `blueprint_generate.go:469-475` — `appDomains` exports `Host` first, then `Hosts...`, flattened into one list.
- `service.go:1687` — `CreateRequest` has only `Hosts []string`; there is no `Host`, so `specFromCreate` always leaves `want.Host == ""`.
- `blueprint_plan.go:153-161` — the applier writes `dst.Host = want.Host` (empty) and `dst.Hosts = want.Hosts`, which is the whole defect.
- Live isolation: removing `domains:` from the exported service entry is the single edit that turns `update` into `noop`.
- The applier already handles the sibling nil-vs-empty trap for `Hosts` and says so in a comment — match that care, and keep that behavior.

## Steps

1. Decide the canonical representation and write it down: either the applier re-splits the declared list into `Host` (first) + `Hosts` (rest) to match what the exporter flattened, or the spec stops carrying a separate `Host`. Pick one; do not normalize both sides into a shape neither the CRD nor the exporter uses.
2. Confirm the choice against the CRD's meaning of `Spec.Host` — is it the primary/canonical domain, or just the first? `effectiveHosts`/`EffectiveHosts` in the operator is the authority.
3. Apply the fix so an exported manifest is a no-op, and a manifest that genuinely adds or removes a domain still reports `update`.
4. Check ordering: `domains: [a, b]` vs `[b, a]` on a service holding both — decide whether order is significant and make the diff agree.

- [x] The `Hosts` nil-vs-empty behavior the existing comment describes still holds.
