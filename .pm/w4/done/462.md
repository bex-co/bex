# 462 — After the w4/459 fix, closing Add Custom Domain still drops keyboard focus to `<body>`

Why: w4/459 named Add Custom Domain as one of four dialogs that drop focus on close, and is closed as done. The shared `DialogContent` fix now works for New Project and New Environment Group, but not for this dialog, so a keyboard or screen-reader user who cancels adding a domain still restarts from the sidebar.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-02 UTC (`muse.env`, `bex-canary`, pin `36c4ba2166fe`, which includes `6cfb10f34`); **minor** (accessibility), ~45m. A partial regression of `w4/459`: the fix shipped, but this site still fails the 459 Definition of done.
- **Probe (Playwright, Settings of a Free `traefik/whoami` service `srv-dbk64bniofks73bgauu0`, deleted afterwards; nothing submitted):**
  - Clicking "Add Custom Domain" (focus moves to `INPUT#custom-domain-name`), then pressing Escape, leaves `document.activeElement` = `BODY`.
  - Focusing the button, pressing Space, then clicking Cancel → `BODY`.
  - Typing `not a domain` and pressing Add (a client-side reject, so no write) then Escape → `BODY`.
  - Focus trace across open and close: `focusin BUTTON:Add Custom Domain` → `focusout BUTTON → INPUT` → `focusin INPUT` … Escape → `focusout INPUT → null`. There is no later `focusin` on the button. The button keeps the same DOM node the whole time (`isConnected: true`, never replaced) and never becomes `disabled`.
  - **Controls that pass on the same pin:** New Project (on `/`), Escape → `BUTTON:Create new project`; New Environment Group (on `/env-groups`), Escape → `BUTTON:New Environment Group`.
- **Expected:** closing the dialog by Escape, Cancel or the close button returns focus to the "Add Custom Domain" button, as for the two controls (459's DoD row 4).
- **Where to look (cause unverified):** the dialog uses the shared primitive (`features/services/components/custom-domains-section.tsx:37-43`, `<Dialog open onOpenChange={(o) => { if (!o) reset(); }}>` with a plain `<Button onClick={() => setOpen(true)}>` and `<DialogContent>` at `:595` and `:609`). The fix lives in `common/components/ui/dialog.tsx`: a module-level `focusin` tracker, captured in `handleOpenAutoFocus`, then `opener.focus()` in `handleCloseAutoFocus` unless `!opener?.isConnected`. The trace shows the button is connected yet never refocused. So either `handleCloseAutoFocus` doesn't run for this instance (for example, `DialogContent` remounts while open and loses `openerRef`, or `reset()` unmounts the content before Radix fires `onCloseAutoFocus`), or `openerRef` captured something else. Instrument `handleOpenAutoFocus` / `handleCloseAutoFocus` in a dev build on this dialog to tell which, then compare `reset()` with the env-group dialog's close path (`features/env-groups/components/env-group-actions.tsx`).
