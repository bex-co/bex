## Objective

A service's (and an environment group's) secret files are accepted up to the bound the API states: "the combined size of all secret files cannot exceed 1 MB (1048576 bytes)". Every total at or below that bound answers 2xx and mounts. One byte more answers the existing 400 `SECRET_FILE_LIMIT`. Nothing in that range answers 500.

## Found by the closeout replay (QA loop round 393, 2026-11-15 05:19–05:24 UTC, pin `2d9bbae6bb8d`)

Fixture: Free web service `qa-20261115-r393-sf` (`srv-dbsk0rn35ies73a66120`, `python:3.12-alpine`, the README's DoD fixture). Deleted afterwards (`GET` 404).

- `PUT /v1/services/{id}/secret-files/qa-big1.txt` with 614,400 bytes of `a` → 201 (DoD 1 holds).
- `PUT …/secret-files/qa-fill.txt` with 434,176 bytes, which brings the contents to exactly 1,048,576 → `500 {"error":"internal error","id":"internal_error","message":"internal error"}`. This held on every try (six tries over three minutes).
- One byte more (1,048,577) → `400 {"code":"SECRET_FILE_LIMIT","error":"the combined size of all secret files cannot exceed 1 MB (1048576 bytes)",…,"params":{"maxBytes":1048576,"maxCount":500}}`. That is the right answer for that total.
- Totals of 1,000,000, 1,040,000 and 1,048,000 → 201. A bisection put the largest accepted total at 1,048,322: 254 bytes short of the stated bound. Every total from 1,048,400 to 1,048,575 answered 500.
- Totals at or below 1,048,322 mount whole: after a deploy, `curl https://qa-20261115-r393-sf.onbex.co/s/qa-big1.txt | wc -c` → 614400 and `…/qa-fill.txt` → 433922 (DoD 3's mount, via REST).
- Late in this probe the API began answering 502, then 503, to every request for about 20 s. See [w4/671](../../671.md). Do not repeat this bisection on production.

## Mechanism (code read; the OpenBao error itself was not seen)

- The whole files map of a service is one OpenBao KV v2 entry: `filesPath` = `services/<name>/files` (`lego/backend/internal/secrets/files.go:62`), written as `json.Marshal({"data": map})` (`lego/backend/internal/secrets/store.go:227-228`).
- Production OpenBao runs integrated raft storage with no `max_entry_size` (`deploy/gitops/overlays/prod/values/openbao.values.yaml:50-61`). Raft's default entry cap is 1 MiB. A stored entry carries the contents plus keys, quotes, JSON escapes and KV v2 version metadata. So the contents can reach about 1 MiB − 254 bytes when they need no escaping.
- Contents that do need escaping (a `"`, `\`, control characters, and possibly `<`, `>` and `&` if HTML-safe escaping applies) would fail lower still. A PEM bundle's newlines are the common case. Not measured.
- The quota guard (`lego/backend/internal/secrets/service.go:986`, `:1020-1022`) counts raw contents against `corev1.MaxSecretSize`. It cannot see the store's encoded size. The w4/m363 envtest exercised Kubernetes and etcd, not OpenBao.

## Fix options (pick one and record why)

1. Raise OpenBao's raft `max_entry_size` (for example to 2 MiB) in base and prod values. It must cover the worst-case escaped map plus metadata. Check the raft snapshot and backup paths at that size.
2. Store each secret file as its own KV entry (or chunk the map) so no entry approaches the cap. This touches every read and write of the files map, revisions and the purger (`secrets/batch.go`, `files.go`, `purger.go`, `revision.go`).
3. Keep the store layout and bound the encoded size. The guard measures `json.Marshal({"data": map})` against the store's cap and refuses with the 400 `SECRET_FILE_LIMIT` before writing. The stated bound and its message then must name the real limit, and the bound must stay at or above Render's 1,000,000 bytes even for escaped contents.

Whatever the choice, a store-write failure must never surface as `500 internal error` for a size the guard admitted.

## Acceptance criteria

## Done (2026-11-17, `/loopx w4`): option 2, chunked values

- **Mechanism confirmed on real raft.** A local OpenBao 2.5.5 server with integrated raft storage (single node, default `max_entry_size`) reproduced production's boundary exactly: a KV v2 write of the DoD's two-file map at 1,048,000 and 1,048,322 content bytes → 200, at 1,048,400 and 1,048,576 → 500.
- **Why option 2.** Option 1 (raise `max_entry_size`) only takes effect when each OpenBao pod restarts. The chart's StatefulSet is `OnDelete` and every restarted pod comes back sealed until someone presents the Shamir keys from `.env` (ADR013 §3), so a deploy cannot clear it. Option 3 would put the accepted bound below 1 MiB for escaped contents (a PEM's newlines alone add about 1.5 %), which fails this task's first criterion.
- **Fix.** `lego/backend/internal/secrets/chunks.go`. When a map's write body passes 512 KiB, its largest values move to chunk entries under `<path>.chunks/<nonce>/`. Each chunk holds at most 384 KiB of the value, base64-encoded, so escaping cannot grow it. The map entry keeps every key, plus a NUL-prefixed manifest key that no file name or env key can collide with.
  - Writes store the chunks first, under a nonce that no other write uses, then the map (plain or compare-and-set). A lost compare-and-set drops its own chunks. A landed write deletes the chunks of the version it replaced.
  - Reads reassemble the values, and re-read the map if a concurrent write deleted the chunks between the two reads.
  - `Delete` and `Retire` remove every chunk under the path. Service and environment-group maps share the adapter (`envgroups/values.go`), so groups get the same layout.
- **Tests.**
  - `secrets.TestFilesMapAtTheBoundFitsTheRaftEntryCap` and `TestEveryFilesWriterStoresTheBoundUnderTheRaftEntryCap` use a KV v2 fake with raft's entry cap. They cover every service files writer, plain and PEM-like (newlines, quotes, backslashes), at exactly 1,048,576 bytes.
  - `TestChunkedMapLifecycle` covers replace, a lost CAS, a shrink back inline, and `Delete`.
  - `TestFilesMapAtTheBoundOnRealOpenBao` is opt-in and writes a service path and an env-group path. It passed against the local raft server, together with the rest of the package's real-OpenBao suite.
  - With offloading disabled, all of them fail with `openbao versioned secret write failed`.
  - The one-byte-over 400 is unchanged (`TestEveryFilesWriterTakesExactlyTheContentsBound`).
- **Deviation.** The raft check ran against a standalone OpenBao raft container, not the CAPD mock cluster's OpenBao. The store code path is the same.

Production replay (2026-11-17, pin `58ef086ab21d`): exactly 1,048,576 bytes → 201 (plain and PEM-like, service and group), and one byte over → 400 `SECRET_FILE_LIMIT`. See [t008](t008.md).
