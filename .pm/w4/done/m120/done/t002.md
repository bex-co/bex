## Objective

`SetEnvVar`, `SetEnvVars`, `DeleteEnvVar`, and `PatchEnvironment` refuse a key that exists on the App's manifest-owned `spec.Env` with a named error ("managed by the blueprint manifest; edit render.yaml"), writing nothing. No silent store write that k8s `env` then shadows.

## Context

- `lego/backend/internal/secrets/service.go:350` — `SetEnvVar`: store CAS with no `spec.Env` check (the App `a` is already in hand via `scope`).
- `lego/backend/internal/secrets/service.go:300` — `SetEnvVars` (bulk replace); `:392` — `DeleteEnvVar`; `batch.go:80` — `PatchEnvironment`.
- `lego/backend/internal/apps/service.go:1904-1912` — the shadow hazard, documented for the interactive path: k8s `env` beats `envFrom`.
- Precedent for the refusal shape: `ENV_GROUP_SERVICE_ENVIRONMENT_MISMATCH`-style named errors; check `core.NewConflictError`/`CodedError` (used per `w6/m49`) for the stable signal.

## Steps

1. Add a helper `manifestOwnedKeys(a) map[string]bool` (spec.Env literal names; same skip rule as t001).
2. Guard all four write verbs: any targeted key in the set → named refusal, no mutation (bulk replace is all-or-nothing — refuse the whole write, naming the offending keys).
3. The refusal must name the remedy (edit the manifest / use `sync: false` for dashboard-managed vars).
4. Unit-test each verb: manifest key refused + store untouched; adjacent non-manifest key in the same bulk write also untouched (atomicity); regular service writes unchanged.

## Acceptance

- Same-key PUT/DELETE/PATCH on a blueprint service fail loudly; reads after the refusal show the manifest value unchanged.
- New-key writes and `sync: false` vars behave exactly as today.
