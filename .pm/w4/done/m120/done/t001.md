## Objective

`ListEnvVars` / `ListEnvVarsPage` / `GetEnvVar` return the union of the mutable store and the App's manifest-owned `spec.Env` literals, with manifest entries flagged (e.g. `managedBy: "blueprint"`, read-only) so callers can render and guard them. All three API surfaces move together because they share these verbs.

## Context

- `lego/backend/internal/secrets/service.go:207-227` — `readAuthorizedEnvMap` is the one read boundary; today store-only.
- `lego/backend/internal/secrets/service.go:284-294` — `GetEnvVar` maps missing key → `core.ErrNotFound`; after the merge a manifest key resolves.
- `lego/backend/internal/apps/service.go:2019-2024` — why blueprint literals stay on `spec.Env` (writership decision; this task changes reads only, not writership).
- `lego/backend/internal/apps/deploy.go:2258-2317` — `classifyServiceEnv`: which entries land on `spec.Env` (plain literals) vs the store (sync:false/generateValue) vs refs.
- Callers that inherit the merge: REST list/get (`secrets/rest.go:81,100`), GraphQL `envVars` (`secrets/graphql.go:171`) + single-key read, MCP list/get (`secrets/mcp.go:121,133`).
- `EnvVarView` needs the new flag field; check the GraphQL/MCP serializers can express it (nullable string/enum, not a non-null breaking change).

## Steps

1. Extend `EnvVarView` (and GraphQL/MCP projections) with a manifest-managed flag.
2. In `readAuthorizedEnvMap` (or a wrapper used by all three read verbs), union store map + `a.Spec.Env` literals (skip `ValueFrom` entries — not representable, same rule as `takeCreateEnvLiterals`), flagging the latter.
3. Keyset pagination stays over the merged key-sorted list.
4. Unit-test: merged list/get, store-wins vs manifest (disjoint by construction — assert no key appears twice), `ValueFrom` skipped.

## Acceptance

- REST `GET env-vars` / `GET env-vars/{key}` on a blueprint service show manifest entries flagged; GraphQL/MCP identical.
- Regular service reads byte-identical to today (merge is a no-op when `spec.Env` is empty).
