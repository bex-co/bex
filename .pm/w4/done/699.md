# 699 — A repo build fails when one secret file is over 500 KiB, because each file reaches BuildKit as one `--secret` and BuildKit refuses a secret past 500 KiB

Why: w4/m363 lets a service or environment group hold Render's 1 MB of secret files, and a single file up to that size is accepted, stored and mounted at runtime. On a repo-backed service, though, every build then fails with `secret bex-file-0 too big. max size 500KiB`. The service cannot deploy until the file shrinks, so a configuration Render accepts for builds ("For non-Docker services, … available … during builds") breaks the deploy.

- **Source / severity / estimate:** w4/m363 t008 live replay, 2026-11-17 05:11–05:20 UTC, production pin `58ef086ab21d`, workspace `bex-canary`. **Minor, parity.** Builds with files at or under 500 KiB work. ~1h.
- **Repro (production, fixture since deleted):** a static site from `https://github.com/bex-co/bex` `main`, `rootDir` `examples/static-site`, publish `out`. Build command `mkdir -p out && cp index.html out/ && wc -c < /etc/secrets/qa-build.txt | tr -d " " > out/check.txt`, created over REST with one secret file `qa-build.txt` of 614,400 bytes (`srv-dbtu3tfok1cs73a3mt40`).
  - First deploy `dep-dbtu3tfok1cs73a3mt4g` → `build_failed` in about 50 s. Build log: `==> error: secret bex-file-0 too big. max size 500KiB`, then `==> Build failed: build failed in the build environment step:`.
  - Control on the same service: the file replaced with a 21-byte marker. Deploy `dep-dbtu5q7ok1cs73a3mtfg` went live, and `/check.txt` reads `21`.
- **Cause (code read):**
  - The native builder passes each secret file as its own BuildKit secret: `lego/operator/internal/build/build.go:1249-1251` (`--secret id=bex-file-<i>,src=/native/files/<name>`, id from `native.go:64`).
  - BuildKit's session secrets provider refuses any secret over `MaxSecretSize = 500 * 1024` (`github.com/moby/buildkit@v0.32.2/session/secrets/secretsprovider/secretsprovider.go:15`, checked at `:39`).
  - Dockerfile builds pass files the same way (`dockerinputs.go:114`, `id=<renderSecretFileID(name)>`), so they probably fail too. Not run live.
  - `render-env` is also one BuildKit secret (`build.go:1247`). The env-var map's cap is 512 KiB of names plus values, so a near-full env set may also fail native builds. Not measured.
- **Fix direction:** keep each BuildKit secret at or under 500 KiB. For the native builder, split a larger file into numbered parts (`bex-file-<i>-<part>`) and have the generated Dockerfile reassemble them under `/etc/secrets/<name>` and the service root before the build command runs. For `render-env`, do the same or bound it. For Dockerfile builds, the tenant's Dockerfile names the secret id, so splitting cannot be transparent. Check what Render does there (BuildKit too?) before choosing, and record the choice in ADR018's Secret files row.
- **Acceptance:** on production, the repro static site with a 614,400-byte file (and with a 1,048,576-byte set of two files) goes live and `/check.txt` reads `614400`. A native Go web service with a 600 KiB file builds and goes live. A regression test drives `buildctlRecipeArgs` and the generated Dockerfile with a file over 500 KiB and asserts that no `--secret` source exceeds BuildKit's cap. The Dockerfile-build case is decided and recorded.

## Outcome (w4/699 loopx worker, 2026-11-16)

- **Shipped (native builds):** the controller hands the build each secret file's size (`buildInputs.fileSizes` → `build.Options.NativeFileSizes`). A file over BuildKit's 500 KiB secret limit is cut by the preparer into parts of at most 512,000 bytes (`/native/file-parts/<name>/<p>`, secret ids `bex-file-<i>-<p>`). When any file is split, the build RUN mounts `/etc/secrets` as a RUN-only tmpfs, mounts every file's secrets under `/run/bex-files/<i>/<p>`, and the env loader concatenates them into `/etc/secrets/<name>` before the build command runs (`nativeFileMounts`, `native.go`). Builds whose files all fit one secret keep their Dockerfile and Job args byte for byte. A file that grew past its planned part count fails the preparer by name.
- **Decided (Dockerfile builds):** the tenant's Dockerfile names the secret id, so a file cannot be split without the tenant noticing. A file over 500 KiB is left out of the build secrets (`dockerBuildSecretArgs`), so builds that never mount it still succeed. It stays in the build-context root, and the build log names it as not mountable (`dockerOversizedSecretNotice`). This is recorded in ADR018's Secret files row. Render also builds with BuildKit and has the same 500 KiB limit, but its behavior with a file this large has not been observed.
- **Tests:** `internal/build/secretparts_test.go` runs the real preparer for a 614,400-byte file, a 1 MiB two-file set beside a small file, exactly 500 KiB, one byte over and a single 1 MiB file. It asserts that no `--secret` source exceeds 512,000 bytes, that the mounts match buildctl's ids, and that the assembly reproduces the exact bytes. With `nativeFileParts` forced to 1, it fails with `--secret bex-file-0 is 614400 bytes`. `TestNativeSecretFilesInPartsPinnedBuildKit` (opt-in `BEX_BUILDKIT_INTEGRATION=1`) passed locally on the pinned `moby/buildkit:v0.30.0`: `check.txt` reads `614400`, the joined bytes match, and nothing under `etc/secrets` or `run/` reaches the layer. A controller test proves the sizes are passed.
- **Not done:** `render-env` (the base64 env bundle) is still one BuildKit secret. A near-cap env set over 500 KiB encoded would still fail a native build. That was not measured and is left as a follow-up.
- **Gate (clears by itself):** once production pins this commit, replay the acceptance on `bex-canary`. The repro static site with a 614,400-byte file, and with a 1,048,576-byte two-file set, goes live with `/check.txt` reading `614400`. A native Go web service with a 600 KiB file builds and goes live.
