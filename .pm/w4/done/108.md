# A revealed multi-line secret file renders as one line

Why: secret files are files — PEM keys, service-account JSON, certificate chains — and Reveal displays them with `white-space: normal`, so every newline collapses and a 20-line key shows as one unreadable run-on line; the bytes are stored and returned correctly, only the display is wrong, which makes this a small fix with an outsized effect on the one screen where users check a secret they cannot see anywhere else.

Found by live `/qa-find-bugs` 2026-09-21 pass 109 (w4-targeted, `muse.env` credentials) on environment group `qa-20260921-eg` (`evg-daoefmrs0ils73bgpda0`), since deleted.

Repro:

1. Create an environment group with a secret file whose content has line breaks — `qa-marker.txt` = `"line-one\nline-two pass109\n"`.
2. Open the group, **Secret Files** → **Reveal**.
3. The value renders as `line-one line-two pass109` on a single line.

The bytes are fine — only the rendering is not:

```js
// the <code> element that holds the revealed value
textContent      → "line-one\nline-two pass109\n"   // newlines intact
getComputedStyle → { whiteSpace: "normal", wordBreak: "break-all" }
className        → "min-w-0 break-all text-sm"
getBoundingClientRect().height → 20   // one line, for a two-line file
```

Fix: render the revealed value with `whitespace-pre-wrap` (keep `break-all` for long unbroken base64 runs). The element is already a `<code>`, so this is a class change plus a check that the surrounding layout still bounds a tall value — a 40-line PEM should scroll or clamp, not push the page.

Check the sibling surfaces in the same pass, since they share the reveal affordance and none was probed this run: the **service** Environment tab's Secret Files, and the **Export** output for both groups and services. Environment *variable* values are single-line in practice but go through the same component — multi-line values are explicitly supported (`w2/m95`), so they have the same defect if they share the class.

This is the display half of a `w2/m95` DoD bullet whose storage half now verifies live: "a multi-line value pasted into any env value field is saved with its line breaks" is **true** — confirmed this run at the group level, DOM and API both carrying `\n`. m95 is blocked on live verification and stays blocked; this note is the separate rendering defect that verification turned up, not a claim about m95's own bullets.

Estimate: ~25m including the sibling surfaces.

## Resolution (2026-09-21)

Done, and the sibling surfaces the note asked about are covered by the same one-line change: the revealed-value `<code>` lives in `SensitiveViewItem` inside the shared `EnvironmentEditor`, which the env-group editors import directly — so the service Environment tab's secret files, the env-group's, and env **values** (multi-line since `w2/m95`) all gain it at once.

`whitespace-pre-wrap` preserves the newlines; `break-all` stays for long unbroken base64 runs. The note's layout concern is handled rather than left open: the element is now `block max-h-48 overflow-auto`, so a 40-line PEM scrolls inside its own row instead of pushing the page.

Covered by `reveals a multi-line value with its line breaks intact`, which asserts the preserved `textContent` **and** both classes — the text assertion alone would pass with the old CSS, since the bytes were never the problem.

Export output was checked and needs nothing: it is generated text handed to a download/clipboard, not rendered through this element.
