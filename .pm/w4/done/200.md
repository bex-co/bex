# w4/200 — The operator flips an App's Ready condition ~40 s after its pod failed readiness, so `server_failed` still lands late

Why: w4/196 now stamps availability edges with the Ready condition's transition time, but on the failure edge that time is itself about 40 s late. The event feed still reports a ~19 s outage for a ~62 s one, which understates outages ~3×.

**Re-scoped 2026-10-05 (code review): likely a backend cause, not the operator.**

- `availabilityEdgeAt` (`lego/backend/internal/store/event_facts.go:474`) backdates to the Ready transition only when that transition is after the checkpoint's `updated_at`.
- The debounced first unhealthy pass (`store/reconciler.go:284`) still records the phase change to Deploying, which moves `updated_at` past the transition.
- The edge then falls back to the next pass's observation time, about one 30 s resync late.

The fix and a live replay of this note's probe are filed as [w5/m113](../w5/m113/README.md). Do the operator diagnosis below only if m113's replay still shows the lag.

Live 2026-10-05 UTC (`/qa-find-bugs` loop35, muse.env, `bex-canary`, pin `f837cec46294`). Owned Free `qa-20261004-l35-hc` (`srv-db1kjlsq11qc73f6oehg`, `traefik/whoami`, health check `/health`, deleted). `POST /health` with body `500` at 06:56:11Z; `curl /` every ~5 s from outside:

- 200 until 06:56:27, **503 from 06:56:32** (the pod is out of the Service endpoints, so kubelet's readiness had already failed), then 200 again from 06:57:34.
- `GET /v1/services/<id>/events`: `server_failed` **06:57:11Z** (`readiness_failed`) and `server_available` 06:57:30Z.
- The recovery edge is accurate. The failure edge is ~40 s after traffic stopped. Because the edge now uses `ReadyTransitionAt`, the App's Ready `LastTransitionTime` itself is ~06:57:11.

Where to look (cause unverified):

- The operator derives Ready from `Deployment.Status.ReadyReplicas` (`lego/operator/internal/controller/app_controller.go:2422`, `:2815-2904`) and watches Deployments and Pods with `ResourceVersionChangedPredicate` (`:6113-6124`). So a missing trigger is not the obvious cause.
- Candidates:
  - a deliberate settle/grace window before Ready=False on a running release (`settleRequeue` at `:636`; `RolloutSettling`/`concreteContainerFailure` gates);
  - Ready=False being written only when the stall diagnosis classifies, rather than on the first `ReadyReplicas` drop;
  - reconcile-queue latency (`MaxConcurrentReconciles`).
- Read the App's Ready condition `LastTransitionTime` against the pod's `Ready` condition `lastTransitionTime` in a replay to pick the cause.

Fix: when a serving release's `ReadyReplicas` drops to 0 (pod readiness False) outside a rollout, set Ready=False with that transition time. Alternatively, stamp `LastTransitionTime` from the pod's readiness transition instead of the reconcile instant, keeping any anti-flap guard on emission (the backend's `debounceUnhealthy` already provides one).

- Test: the operator's Ready transition time is within one probe period of the pod readiness flip.
- Live: the replay above shows `server_failed` within ~10 s of the first 503.

Severity: minor (incident-timing truthfulness). Estimate: ~45m (mostly diagnosis).

**Done 2026-10-05, fixed by [w5/m113](../w5/done/m113/README.md).** The lag was the backend, not the operator. The debounced first unhealthy pass's phase write moved the edge floor past the Ready transition. The operator flips Ready within the same second as the pod: on dev-5 the pod went Ready=False at 23:27:23 and the App at 23:27:23. With the fix, `server_failed.at` was 23:27:23, 0 s after traffic stopped (it was ~40 s). No operator change was needed.
