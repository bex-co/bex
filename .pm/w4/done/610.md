# 610 — After a credential rotation, a Postgres's Details still name the original user as its "User", even once that user is deleted and can no longer log in, while Connections already use the new default

Why: the Details card is where an owner reads which user to connect as. After "New default credential" and deleting the original, it names a login that was revoked, and Connections on the same page disagree. Render: "The default user's credentials appear in your database's connection URLs shown in the Render Dashboard".

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 210, 2026-11-12 16:56–17:10 UTC (`muse.env`, workspace `bex-canary`; pin `77531cc764d3`). **Minor** (the connection strings are right; only the Details fact is stale). ~35m.
- **Fixture:** Free Postgres `qa-20261112-r210-pg` (`dpg-dbquvnvs9cvc73b61u40`), created from New → New Postgres with Database name `qa_r210` and Database user `qa_r210_owner`. Deleted afterwards.
- **Probe:**
  1. Access control → Credentials → New credential username `qa_r210_user2` → New default credential.
     - `GET /v1/postgres/{id}/credentials` → `[{"username":"qa_r210_owner","default":false},{"username":"qa_r210_user2","default":true}]`.
     - Reveal connection info → Copy psql command reads `PGPASSWORD=<pw> psql -h <id>.db.bex.co -U qa_r210_user2 qa_r210`. The External connection string's user is `qa_r210_user2`.
     - Locally, the copied command printed `qa_r210_user2|2` for `select current_user, count(*) from qa210`, a table `qa_r210_owner` had created.
  2. Delete `qa_r210_owner` → "Delete credential" (toast "Revocation requested for qa_r210_owner.").
     - `GET …/credentials` → `[{"username":"qa_r210_user2","default":true}]`.
  3. Fresh loads of `/databases/dpg-dbquvnvs9cvc73b61u40`:
     - en: Details `term: User` → `definition: qa_r210_owner`;
     - zh: `用户` → `qa_r210_owner`;
     - Credentials list only `qa_r210_user2 Default`.
     - GraphQL `{ database(id:…) { databaseUser } databaseCredentials(id:…) { username default } }` → `{"databaseUser":"qa_r210_owner"}`, `[{"default":true,"username":"qa_r210_user2"}]`. REST `GET /v1/postgres/{id}` → `"databaseUser":"qa_r210_owner"`.
- **Root cause:**
  - `pgView` sets `DatabaseUser` from `d.Spec.EffectiveDatabaseUser(d.Name)` (`lego/backend/internal/postgres/service.go:580`, `:625`), the immutable create-time owner.
  - The login the connection info uses is `DatabaseSpec.DefaultCredential` (`lego/types/v1alpha1/database_types.go:394-400`: `spec.defaultUser` when set, else the owner). w5/m265 added it with the rotation.
  - The dashboard's Details card prints `database.databaseUser` (`dashboard/src/features/databases/components/database-metadata-card.tsx:82-85`).
- **Fix (target behavior):** the Details "User" fact shows the database's current default login, `DefaultCredential`: the user every connection string and the psql command use.
  - Expose it as a GraphQL `Database.defaultUser` (bex extension) from `pgView`, and print it in the card.
  - It arrives in the same query as the rest of the card, so there is no stale pre-settle state.
  - en and zh keep their labels ("User" / "用户").
  - **REST and MCP `databaseUser` stay the create-time owner** for now. That is Render's create input ("databaseUser … default randomly generated"), and Render's read after a rotation is not captured.
    - Capture Render's `GET /v1/postgres/{id}` after `POST …/credentials` in this change. If Render reports the new default there, move REST, MCP and GraphQL `databaseUser` to `DefaultCredential` in the same change. Either way, record it on the ADR018 "Access control · users · pooler" row.
- **Blast radius:**
  - `pgView` has 4 callers in `lego/backend/internal/postgres` (get, list, create and update replies).
  - A new field changes none of them. Moving `databaseUser` would reach REST, GraphQL, MCP and Blueprint export.
  - Tests:
    - the card shows the default after a rotation;
    - it shows the owner when no credential was ever added;
    - GraphQL `defaultUser` equals the `default:true` credential.
- **Unverified:**
  - MCP `get_postgres` output (not called).
  - Render's dashboard and API username after a rotation (only its docs were read: "Whenever you add a PostgreSQL user to your database, that user becomes the database's new 'default' user").
- **Dedupe:**
  - w5/m265 (done) shipped the rotation and its Credentials section, and doesn't mention the Details fact.
  - w6/m38 (done) added create-time `databaseName`/`databaseUser`.
  - `grep -rl databaseUser .pm` finds none about rotation.
  - Not deploy lag: `git log 77531cc764d3..origin/main -- lego/backend/internal/postgres/service.go dashboard/src/features/databases/components/database-metadata-card.tsx` is empty.
- **Also verified this round (all pass):**
  - **Create.** Free Postgres from the dashboard dialog with custom database and user names: `creating` → `available` in about 2 min 13 s. REST reads `databaseName: qa_r210`, `databaseUser: qa_r210_owner`, version 18, `ipAllowList` `0.0.0.0/0` and `::/0`.
  - **Copied URL connects.** Copy External connection string → toast "Copied to clipboard". Locally, `psql "$(pbpaste)"` connected as `qa_r210_owner` to `qa_r210` on PostgreSQL 18, with `pg_stat_ssl.ssl = t`. The copied psql command ran `create table` / `insert` / `select` (`rows|2`).
  - **SQL console.** `select id, current_user from qa210` → "2 rows returned", the same two rows.
  - **Recovery** on Free reads "Backups aren't enabled for this plan…".
  - **IP allowlist enforced, both ways.**
    - Saving only `203.0.113.0/24` made the copied psql command fail within 6 s, three times over 30 s ("SSL error: unexpected eof while reading"; the bare close was already dispositioned in w4/071 and w4/586).

- **DoD (live):** on an owned Free Postgres, after New default credential `…_user2` and deleting the original user:
  - the Details "User" fact reads `…_user2` (en and zh), the same user as Copy psql command's `-U`;
  - GraphQL `database { defaultUser }` reads `…_user2`;
  - a database that never rotated still reads its create-time user;
  - REST `databaseUser` matches what the captured Render behavior requires, recorded on the ADR018 row.

- **Closed 2026-11-14 (`/loopx w4`):** The Details "User" fact now names the current default login: `pgView` sets a GraphQL-only `DefaultUser` (`spec.defaultUser` after a rotation, else the owner; `json:"-"` so REST and MCP keep Render's create-time `databaseUser`), GraphQL `Database.defaultUser` exposes it, and the card prints `defaultUser ?? databaseUser`. Render's own read after a rotation could not be captured from this loop (no Render account), so REST/MCP stay on the owner and the uncertainty is recorded on ADR018's access-control row. Tests: `default_user_test.go` (before/after rotation, REST JSON unchanged) and the card test. Live DoD replays after the next production deploy.
