## Scaling still offered on a cron job — deploy lag, not a regression

The cron job's sidebar carries **Shell, Scaling and Plan**, and `/services/<cron-id>/scaling` renders the autoscaling editor ("Automatically scale this service up or down based on CPU and memory utilization. / Autoscaling off").

`w4/m101`'s definition of done says the opposite must hold: *"The dashboard stops offering it. `/services/<cron-srv-id>/scaling` does not render an autoscaling editor, and the cron job's sidebar has no Scaling entry."*

Its fix is `de4945aec` ("refuse unscalable autoscaling and honor static error headers"), which `w4/093` already established **postdates the deployed build** — production is still behind `e6419af0b`. So this is the same pipeline-wide deploy lag, **not filed**, and recorded here so it is not mistaken for a regression. It is also a fourth observable discriminator for the stalled deploy: *if a cron job's Scaling tab renders an autoscaling editor, the build predates `de4945aec`.*

## Two near-misses, both mine

**"There is no cron runs UI."** The sidebar has no Runs entry and `/runs`, `/cron` and `/jobs` all 404 — while the API has a full cron-run verb set. Wrong conclusion: `CronRunsSection` renders on the **Events** tab (`dashboard/src/routes/services.$serviceId.events.tsx:321`), and it has been in the deployed build since 2026-08-26 (`20b68db54`). Those three routes 404 because they do not exist by design, not because the feature is missing.

**"Trigger Run fires nothing."** Instrumenting every `api.bex.co` request across a click returned **zero requests**, and the button reported `disabled: false` with computed `pointer-events: none` — which reads like an enabled-looking control that cannot be operated. Also wrong. `cron-runs-section.tsx:122` shows `onClick` only calls `setConfirmTrigger(true)`; the mutation runs from `handleTrigger()` on confirm. The `pointer-events: none` was the **modal overlay** — the button was sitting behind the dialog I had opened and never completed.

The lesson worth carrying: **zero network requests after a click is not evidence the control is dead — check for an open dialog first.** Filing that as "a primary action button does nothing" would have been badly wrong, and the shape is easy to repeat.

Also mine, twice: wrong GraphQL names (`cronJobRuns(id:)` instead of `serviceId:`, and type `CronJobRun` instead of `CronRun`). Both surfaced as explicit errors rather than silent empties, which is how `w4/092`'s correction should have arrived.

## One observation, deliberately not filed

The schedule field sets `aria-invalid="true"` and announces via `role="alert"`, but has **no `aria-describedby`** linking the message to the input. `w4/m101/t012`'s acceptance for the SSH-key dialog was "the textarea is `aria-invalid` and its **accessible description** is the validation message" — so by that standard this field is two-thirds done. It is not filed because `role="alert"` does the announcing and the gap is marginal; it belongs in any future pass over that form rather than as its own item.

## Unverified

- **Only a manual run was observed.** Whether the `0 3 * * *` schedule actually fires on time was not waited for, so scheduled execution — as opposed to triggered execution — is untested.
- **The one-active-run constraint was not exercised.** The dialog promises "Only one run can be active at a time"; a second trigger during an active run was not attempted, and `hasActiveRun` disabling the button was read from source (`cron-runs-section.tsx:120`), not observed.
- **Cancel was not exercised.** `cancelCronJobRun` and the per-row cancel for pending rows exist; the run completed too quickly to catch one.
- **Run-scoped log filtering was not checked** — logs were queried for the whole service and the marker matched, so whether the UI can scope logs to a single run is unknown.
- **Background workers remain entirely uncovered**, the last untouched type in journey 10.
