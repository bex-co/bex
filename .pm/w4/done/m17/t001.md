## Objective

Confirm (or refute) inbox `010`'s prediction in a real browser: a user already holding a live Kratos session who starts an agent OAuth authorization lands on `/auth/login?login_challenge=…`, where Kratos answers the JSON flow-init with `200 null`, and the login page dead-ends (skeleton, or the challenge-less redirect bootstrap that abandons the authorization).

## Context

- Observed against Kratos v1.3.1 + Hydra v2.2.0 in the e2e harness: `GET {kratos}/self-service/login/browser?login_challenge=…&return_to=…` with `Accept: application/json` and a live session cookie returns **`200` with body `null`** — no `ui.nodes`, no `redirect_browser_to`, no `Location`.
- `dashboard/src/common/hooks/use-ory-flow.ts` (~line 221) expects Kratos to *throw* `browser_location_change_required` here (the "OAuth2 short-circuit"); `docs/ADR012-auth.md` §7 documents that expectation.
- m16's e2e (`scripts/auth-oauth21-e2e.sh`) sidesteps this by driving each authorization from a fresh cookie jar — that's why all 12 legs pass.
- The sandboxed Playwright browser previously couldn't reach the e2e stack's localhost ports; run the stack + a browser that can reach it (or drive Playwright against a reachable host).

## Steps

1. Stand up the m16 e2e stack (see `scripts/auth-oauth21-e2e.sh` for the Kratos/Hydra/dashboard topology) and sign into the dashboard in a real browser.
2. In the same browser profile, start an agent authorization (mint a DCR client and open its authorize URL, as the e2e's unblessed-client legs do).
3. Observe the login page: does it render a skeleton, bootstrap a challenge-less flow, or complete the short-circuit to Hydra's continue URL?
4. Capture the network trace of the flow-init call (status, body) and record the outcome in `w4/m17/README.md`.
