## Objective

Record how bex builds Render's Apps page before code: one server-side verb, the link from a database to its admin apps, authorization and the network path.

## Context

- [ADR009](../../../../../docs/ADR009-postgresql-management.md) (Postgres management); [ADR018](../../../../../docs/ADR018-render-parity.md) Managed Postgres.
- Image services, secret files and a database's internal URL already exist; the dashboard must not assemble the service itself, because that would round-trip the connection string through the browser.
- Docker Hub risk: image-port discovery reads Docker Hub anonymously and can stall a new docker.io image service for up to 25 minutes while the shared quota is exhausted ([w4/429](../../../blocked/429.md)).

## Steps

1. Add an "Admin apps" section to ADR009: GraphQL `postgresAdminApps(databaseId)` (catalog + deployed state) and `deployPostgresAdminApp(databaseId, app, credentials)`; the service is created through the shared create path (payment gate, plan, region, the database's project and environment) and carries a label linking it to the database and naming the app; the connection is the database's internal URL, injected server side.
2. Authorization: the caller needs service create in the target environment and `can_view_sensitive` on the database (the app receives its credentials); a protected environment limits it to Admins, as Render limits secret reads there.
3. Set each app's port explicitly so no image-port discovery read is needed; if t001 shows Render pulls from a non-Docker-Hub registry, use it.
4. Where t001 could not settle a value, record the proposal's recommendation as bex's choice where Render is uncaptured: the apps' official images (`ankane/pghero`, `dpage/pgadmin4`) on bex's smallest paid plan that runs them; this is a recommendation pending capture, not a user decision.
