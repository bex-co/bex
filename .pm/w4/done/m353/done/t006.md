## Objective

A health-check outage records one `server_failed` (`unhealthy`) and one `server_available`, as this milestone's README promises ("the events stay `server_failed` and `server_available`") and as round 229 recorded. The platform's own liveness kill of the failing instance is part of that outage, not a second failure. It must not appear as the app exiting on its own.

## Found by the closeout replay (QA loop round 394, 2026-11-15 05:34–05:39 UTC, pin `2d9bbae6bb8d`)

Fixture: Free `traefik/whoami:v1.10` web service `qa-20261115-r394-hc` (`srv-dbsk8ucos7qc739hkp6g`), `dockerCommand: /whoami -port 10000`, `healthCheckPath: /health`. Deleted afterwards (`GET` 404).

`GET /v1/services/{id}/events` after `curl -X POST --data 500 …/health` at 05:37:04:

```
05:37:17 server_failed {"reason":{"evicted":false,"unhealthy":"The instance failed its health check"}}
05:38:09 server_failed {"instanceID":"srv-dbsk8ucos7qc739hkp6g-u40odo14sip1ujms870v","reason":{"evicted":false,"nonZeroExit":2}}
05:38:18 server_available {}
```

App log: `Update health check status code [500]` at 05:37:04.464, and the next `Starting up on port 10000` at 05:38:11.882 (DoD 1's timing holds: 67 s). Exit status 2 is Go's default on SIGTERM, which is how whoami answers the kubelet's liveness kill. Round 229 (before t001's drain change) recorded only the `unhealthy` failure and `server_available` (README § Finding).

## Mechanism (code read; timing consistent, the operator's write order not observed)

- `recordInstanceExits` (`lego/operator/internal/controller/instance_exits.go:66`) records the serving release's last container exit.
- `unreadyBefore` (`:106`) marks an exit that followed an outage (`AfterUnready`) only while the pod still shows a not-ready `Ready` condition. Its comment says: "A pod that is ready again no longer says when it was not, so it answers false: the exit is then taken as the cause."
- Before t001, the 60 s preStop sleep held the killed container unready for a minute, so the exit was read while the pod was still down and folded into the outage.
- With t001, the liveness kill restarts the container at once. The replacement process passes readiness about 6 s later (05:38:11.9 → 05:38:18). If the operator's pass first sees the exit after that, `AfterUnready` is false and the exit becomes a new failure.

## Fix (target behavior)

An exit caused by the platform's liveness kill is never its own `server_failed`.

- Option: record the exit while the container is terminated (requeue on the not-ready transition, as `lastExit` already prefers reading before the restart).
- Option: take the kubelet's own signal (the pod's liveness-failure event, or a recent `Unhealthy` liveness record) as proof the exit followed the outage, whatever the pod's current readiness.
- A crash of an instance that was healthy still records `nonZeroExit` (w8/m158, w4/608). An OOM kill still records `oomKilled`.

## Acceptance criteria

- [x] Operator test: a liveness-killed container whose replacement is already Ready when the exit is first read records the exit as `AfterUnready` (or not at all), so the store emits no second `server_failed`.
- [ ] Production replay of DoD 1: the Events list reads exactly `server_failed` (`unhealthy`), then `server_available`.
- [ ] w4/608's and w8/m158's crash cases are unchanged.

## Data point — QA loop round 410 (2026-11-15 10:14–10:15 UTC, pin `89ac87445bec`)

The same whoami health-check outage (`traefik/whoami:v1.10.1`, `/health` flipped to 500, on w4/m327's replay fixture) recorded only `server_failed {"unhealthy"}` (10:14:35) and `server_available` (10:15:25), with no `nonZeroExit` row. The instance restarted in place 56 s after the flip.

So the extra exit event of round 394 does not appear every time, which fits the mechanism above: a race between the exit read and the pod turning Ready again.

## Done — 2026-11-16

- Fixed by the remembered outage (`unreadyRuns` in `lego/operator/internal/controller/instance_exits.go`), the second option above in operator form. A liveness kill comes about 45 s after readiness failed, and the passes that readiness change wakes record the running, not-ready run. The exit that ends it is then `afterUnready` however late it is first read.
- Test: `TestInstanceExitsRememberAnOutageTheRestartedPodNoLongerShows` reproduces round 394's order. It fails with the memory disabled, which leaves `afterUnready: false`, the extra event. It also covers a later crash of the healthy replacement and a crash after a recovery in the same run; both still record their own failure. The w8/m158 and w4/608 cases in `instance_exits_test.go` pass unchanged.
- The production replay of DoD 1 moves to [t005](../t005.md).
