# 047 — Projects/Overview resource list "Type" column collapses every service type to a generic "Service" badge

Why: the resource table lies about what each resource is — a cron job, a private service, and a web service all render the badge "Service", inconsistent with the detail header (which shows the correct kind) and with Render, which labels each resource by its specific type.

Found in a live `$qa-find-bugs w4` hunt of `dashboard.bex.co`, 2026-09-06, workspace `tian-personal` (`tea-da2isimlm39c739m4ofg`). Read-only — inspected pre-existing resources, nothing created or deleted.

Severity: minor (misleading label + internal inconsistency + Render-parity loss; journey completes, no data loss).

## Symptom

On `https://dashboard.bex.co/` (Overview → "Ungrouped Resources", and the project-grouped tables) the "Type" column badge reads the literal string **"Service"** for every service, regardless of its actual kind. Live in this workspace, three rows of three different types all badge "Service":

- `tianpan-v4-web` — `web_service`
- `qa-20260906-private` — `private_service`
- `qa-20260906-private-probe` — `cron_job`

Opening any of them shows the detail header + page title with the **correct** specific type (the cron job's page title is `qa-20260906-private-probe ・ Cron Job ・ bex Dashboard`; a web service shows "Web Service"). So the list view is internally inconsistent with the detail view and drops the Render-style distinction.

## Repro

1. Sign in; open `https://dashboard.bex.co/` in a workspace with mixed service types.
2. Read the Type-column badges in the resource table — all read "Service".
3. Open the cron job at `/services/srv-daf4utsrrsrs73ev9jb0` — header/title reads "Cron Job".

## Expected / Actual

- Expected: the list Type column shows the specific kind (Web Service / Private Service / Background Worker / Cron Job / Static Site), matching the detail header and Render.
- Actual: every service row shows generic "Service".

  - (No console errors on the Overview page.)

## Root cause

`dashboard/src/features/projects/components/resource-table.tsx:200` and `:205` render `<ResourceTypeBadge kind={row.kind} />`. `ResourceTypeBadge` (`dashboard/src/features/projects/components/resource-type-badge.tsx:5-20`) maps every `kind:"service"` to `projects.typeService` = "Service" and never consults `row.service.type`, even though `ResourceRow` already carries the full service view (`dashboard/src/features/projects/types.ts:27` — `service?: ServiceView`, which has `type`).

The correct per-type label machinery already exists and is used by the service detail header: `ServiceTypeBadge` (`dashboard/src/features/services/components/service-type-badge.tsx`) + `deriveServiceType` / `SERVICE_TYPE_LABEL` (`dashboard/src/features/services/lib/service-type.ts:8-29`), which already map `web_service`/`private_service`/`background_worker`/`cron_job`/`static_site` to "Web Service"/"Private Service"/"Background Worker"/"Cron Job"/"Static Site".

## Fix (name the target behavior)

For `row.kind === "service"`, render the **specific** service-type label so the list matches the detail header and Render — delegate to the existing shared `ServiceTypeBadge service={row.service}` (or use `SERVICE_TYPE_LABEL[deriveServiceType(row.service.type)]`). Keep the generic labels for `database`/`keyvalue`/`envgroup` kinds. UI-only; **no** REST/GraphQL/MCP change (the backend already returns `type`, verified live above).

## Blast radius

`ResourceTypeBadge` has exactly 2 call sites, both in `resource-table.tsx` (line 200 mobile-stacked, line 205 desktop column) — `grep -rn ResourceTypeBadge dashboard/src` returns only its definition + these two. Both are service-capable rows in the same merged table, so one delegation fixes both. `ServiceTypeBadge` is already shared with the detail header, so the list and header cannot drift after the fix.

## Adjacent / unverified

- Database and key-value rows map to `projects.typeDatabase` / `projects.typeKeyValue`; whether those read Render's "PostgreSQL" / "Key Value" vs a generic label was **not** verified this run (no datastores existed in either workspace to observe live). Out of scope for this note unless the same collapse is found there.
- Background worker and static site service types were not present live this run; the proposed fix covers them by construction via `deriveServiceType` (unknown/legacy still falls back to the neutral "Service", intended per `service-type-badge.tsx:13`).

## Render

Render's project/list views label each resource by its specific type (Web Service, Private Service, Cron Job, Static Site, Background Worker, PostgreSQL, Key Value), not a single generic "Service".

Estimate: ~20–30 min (delegate service rows to `ServiceTypeBadge` in `resource-table.tsx` + a resource-table test asserting a cron/private row renders its specific label, not "Service"; the badge machinery and locale strings already exist).

## Resolution (2026-09-07)

Done. `resource-table.tsx` now delegates service rows to a small `RowTypeBadge` wrapper that renders the shared `ServiceTypeBadge service={row.service}` for `row.kind === "service"` (falling back to the generic `ResourceTypeBadge` for database/keyvalue/envgroup and for a service row missing its view) — so both the mobile-stacked and desktop Type-column badges show the specific kind (Web Service / Private Service / Background Worker / Cron Job / Static Site), matching the detail header and Render, and they can't drift since the header uses the same component. UI-only; no REST/GraphQL/MCP change. Regression test in `resource-table.test.tsx` asserts a web/cron/private row renders its specific label and that the generic "Service" collapse is gone. `yarn typecheck`/`yarn lint`/dashboard tests green. Shipped with **w4/049** (sibling entrypoint). Live re-probe of the deployed fix deferred to the next QA pass.
