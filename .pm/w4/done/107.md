# The Postgres page tells you to "Enable a pooler" and the dashboard cannot enable one

Why: the Connection pooling panel's only content on an unpooled database is an instruction the dashboard is structurally unable to carry out — the pooler write exists on REST alone, and `w2/024` excluded it from GraphQL deliberately on parity grounds without noticing that the dashboard is a GraphQL client, so the copy became a dead end for every dashboard user.

Found by live `/qa-find-bugs` 2026-09-21 pass 108 (w4-targeted, `muse.env` credentials) on `qa-20260921-pg` (`dpg-daoe9l3s0ils73bgpd50`, free plan), since deleted.

## What the user sees

`/databases/<id>` → **Connection pooling** → **Reveal pooled strings**:

> Connection pooling isn't enabled for this database. Enable a pooler to get pooled connection strings.

There is no pooler control on that page, and none in the New Postgres form (its fields are name, database name, database user, instance type, version, disk size, project/environment, public access). A full-page `innerText` scan for "pool" returns only this message, the section blurb, and the "pool connections" phrase in the Access control heading — no button, switch, or link.

## Where the write actually lives

| surface | create | update | read                                                                                          |
| ------- | ------ | ------ | --------------------------------------------------------------------------------------------- |
| REST    | ✅ `pooler` / `connectionPool` (`rest.go:353-382`) | ✅ `PATCH` (`resolvePooler`, `service.go:331-337`) | ✅                                          |
| GraphQL | ✖ — `createDatabase(…)` has no `pooler` arg | ✖ — no mutation at all | ✅ `poolerEnabled`, `connectionPool`, both pooled strings (`graphql.go:58-59,178-179`) |
| MCP     | ✖ | ✖ | ✖ — `grep -i 'pooler\|connectionPool' lego/backend/internal/postgres/mcp.go` → **0** hits       |

Live proof that the capability is real and not plan-gated — on the **free** plan:

```
PATCH /v1/postgres/dpg-daoe9l3s0ils73bgpd50   {"pooler":true}
→ 200
GET   /v1/postgres/dpg-daoe9l3s0ils73bgpd50
→ "poolerEnabled": true, "connectionPool": "pgbouncer"
```

The panel then filled in with internal and external pooled strings, and the external one connects:

```
PGSSLROOTCERT=… psql 'postgresql://…@dpg-…-pool.db.bex.co:5432/…?sslmode=verify-full' -c 'select count(*) from qa_t'
→ 5000
```

So the mechanism is complete end to end. Only the dashboard's path to it is missing.

## The decision this needs

`.pm/w2/done/024.md` (DONE 2026-08-23) says: _"GraphQL/MCP writes deliberately untouched (no Render contract)."_ That is a **parity** argument — Render has no GraphQL, so there was no contract to conform to — and it is sound on its own terms. What it did not weigh is that the dashboard talks GraphQL, so excluding the write from GraphQL excluded it from the product's primary UI. This note does not re-open that decision on parity grounds; it asks for the product call that was never made:

- **(a) Add the control.** A pooler toggle on the database page (and optionally the create form), which needs a GraphQL write — the siblings `updateDatabaseDiskAutoscaling`, `updateDatabasePlan`, `updateDatabaseVersion` already establish the per-field mutation shape, so this is additive and does not change REST. ~2h across dashboard + GraphQL + tests + an ADR018 note; **promote to a milestone if chosen**.
- **(b) Make the copy honest.** Keep the dashboard read-only here and say how pooling is actually enabled ("Enable pooling with `PATCH /v1/postgres/{id} {\"pooler\": true}`" or a docs link), the way Recovery already does for a plan-gated feature ("Backups aren't enabled for this plan… Upgrade to a plan with backups"). ~20m, and it fits this note as-is.

(b) is the smaller fix and stops the dead end today; (a) is what a Render user would expect. Recommend (b) now and (a) as a separate milestone if the product wants parity with its own API.

## Root cause

- `dashboard/src/features/databases/` — the Connection pooling panel renders the instruction with no affordance; there is no pooler mutation for it to call.
- `lego/backend/internal/postgres/graphql.go` — pooler is read-only here; `createDatabase` and every `updateDatabase*` mutation omit it.
- `lego/backend/internal/postgres/rest.go:353-382` + `service.go:331-337` — the only write path, create and PATCH.

Not a duplicate of `w4/m121` (service port, same _class_ — a message naming a control the dashboard never renders — but a different resource, different field, and m121's fix would not touch this). Worth cross-reading the two: if a third instance turns up, the pattern deserves its own sweep.

## Resolution (2026-09-21) — took option (b), the note's own recommendation

The dead end is closed by making the copy honest. The Connection pooling panel now reads:

> Connection pooling isn't enabled for this database, so there are no pooled connection strings. Turn it on through the API — `PATCH /v1/postgres/{id}` with `{"pooler": true}` — and the pooled strings appear here.

That is the shape `databases.recoveryDisabled` already uses for a feature this page cannot turn on: name the real path instead of instructing the reader to use a control that does not exist. en + zh.

**Option (a) — the pooler toggle — is not taken here, and is a product call, not an engineering one.** The note is right that it is what a Render user would expect and that the siblings (`updateDatabaseDiskAutoscaling`, `updateDatabasePlan`, `updateDatabaseVersion`) already establish the per-field mutation shape, so it is additive and would not change REST. It is also ~2h across GraphQL + dashboard + tests + an ADR018 note, which is milestone-sized by the board's own rule. **Ask for it as a milestone if the product wants the dashboard to reach its own API here** — nothing in this change makes that harder, and the copy above is what a user sees until then.

The cross-reference the note asks for is worth recording: this is the same *class* as `w4/m121` (a message naming a control the dashboard never renders), which was fixed by building the control. Two instances now. A third turning up would justify sweeping the pattern rather than fixing instances.
