## Objective

Use the matching continued-step end to make the default log window include post-cancel completion/error output. Preserve the deploy's cancellation timestamps and existing range controls.

## Context

- deploy-detail-page.tsx:97–106 passes finishedAt as the default endTime.
- use-deploy-logs.ts:151–172 sends that bound to all three sources; a longer ingestion grace with the same bound cannot fix this.
- Both success and error fresh-load replays and the finite wider-bound API control are in finding.md.

## Steps

1. Allowlist the additional fact resolution to canceled deploys with a final continued-step outcome; calculate the diagnostic end from the later of cancellation and the matching step end.
2. Keep createdAt as the lower bound and preserve explicit ?r= relative-range overrides. Keep actual deploy timestamps/duration/status/image/cancel reason unchanged.
3. While the end fact resolves, preserve the log panel's controls, outer geometry and existing skeleton regions; show checking rather than an authoritative empty result from the known-truncated bound.
4. For a missing legacy fact or a read failure, expose an honest limited-window/retry state and existing range affordance. Keep the normal bounds for no-step, ordinary terminal and truly stopped/superseded cases.
5. Ensure a late fact/step outcome changes the query variables and refreshes the default view, including when the layout's latest-deploy query has moved to another row.

## Acceptance criteria

- [ ] The default All logs search displays the observed successful completion and error markers once after the fact settles.
- [ ] Cancellation finishedAt and duration stay unchanged; a relative-range switch and return both retain the marker.
- [ ] Desktop and narrow-mobile pending/ready states preserve panel geometry; no misleading empty flash during end-fact resolution.
- [ ] The new end belongs to this deploy; changing deploy IDs resets the resolver.
