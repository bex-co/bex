# 642 — The static-site create form says "`.` for the repository root", but the publish directory resolves from the Root Directory: with Root Directory `examples/static-site`, `.` publishes that folder

Why: a user with a monorepo sets Root Directory, reads that `.` means the repository root, and types a path from the repo root instead, such as `examples/static-site/dist`. That path is resolved under the Root Directory and misses. bex's own editor copy says the opposite of the hint: "A publish directory is resolved from the Root Directory" (`services/locales/en.ts:3033`).

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 324, 2026-11-13 20:52–21:02 UTC (`muse.env`, workspace `bex-canary`; pin `1c4d721bc8dc`; dashboard driven from an isolated headless Chromium). **Minor** (wrong copy). ~15m.
- **Probe:**
  - `/services/new?type=static_site` → Public Git URL. With Publish Directory blank, the hint reads: "Required. Enter the built output directory to serve as the site root (e.g. dist, build, public, or . for the repository root)."
  - The site was created from that form: repo `https://github.com/bex-co/bex`, branch `main`, Root Directory `examples/static-site`, Publish Directory `.`, auto-deploy off. Fixture `qa-20261113-r324-st` (`srv-dbrnha5gh3vs73b150cg`).
  - It went live and served `examples/static-site/index.html` at `/` (200). So `.` meant the Root Directory, not the repository root.
  - REST agrees: `rootDir: examples/static-site`, `serviceDetails.publishPath: "."`. ADR029:9 says the publish Job "publishes `rootDir/publishPath`".
- **Root cause:**
  - `services.createFieldPublishPathRequired` in `dashboard/src/features/services/locales/en.ts:3965-3970` (rendered by `routes/services.new.tsx:517`).
  - Its zh twin says the same, "或用 . 表示仓库根目录" (`locales/zh.ts:3880-3884`).
- **Fix:** say "`.` for the Root Directory (the repository root when Root Directory is blank)" in both locales. Keep `services.createFieldPublishPathHint` (`en.ts:3960-3964`), which names no root. The Build Filters copy ("relative to the repository root") is right and stays.
- **Render:** its form describes the publish directory as relative to the service's root directory.
- **Also verified this round through the UI (all pass):**
  - The site was created from the form: the toast read "Deploying qa-20261113-r324-st…" and the page landed on the first deploy.
  - Redirects/Rewrites → Add rule → Redirect `/qa-old` → `/qa-new` → Save routes: toast "Routes updated", and the host answered `301 /qa-new`.
  - Headers → Add header `/*` `X-Qa-R324: yes` → Save headers: toast "Headers updated". The rule survived a reload, and the host sent `x-qa-r324: yes`.
- **Dedupe:**
  - w4/332 (done) made the field required and added this hint. It did not check the root wording.
  - `grep -rln "for the repository root" .pm` finds only w4/332.
- **DoD:**
  - The create form's Publish Directory hint, in en and zh, names the Root Directory.
  - A dashboard locale test pins the string.
  - Delete the fixture (`GET` 404).

- **Closed 2026-11-14 (`/loopx w4`):** The create form's Publish Directory hint (`services.createFieldPublishPathRequired`, en + zh) now says the path is relative to the Root Directory and that `.` is the Root Directory itself (the repository root when Root Directory is blank). `services.new.test.tsx` pins the en string. The round-324 fixture deletion is the QA run's own step. Live DoD replays after the next production deploy.
