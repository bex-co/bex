# w4/258 — Raw application-metrics headlines show an older instance's value

Why: the default CPU headline can say **0.1%** while the running instance is at **~100%** and its line is visible in the same chart, misleading a customer diagnosing load or deciding how to scale.

**Severity:** major. **Estimate:** 55m. Functional live QA a186, 2026-10-11 UTC, `https://dashboard.bex.co`, `muse.env` through the login helper. Research pin: `646ca653029ac28b693facab57adfdf44617446e`. Filing only; no product fix was made.

- **Repro:** create owned Free image-backed web service `qa-20261011-a186-lifecycle` (`srv-db5o5uhrl00c73fu5fkg`, `python:3.13-alpine`, port 3000) with the ordinary HTTP command in the complete Create receipt below. Rename to a Unicode display name, suspend, resume and clear the display name; these journeys passed. Save the second Docker Command below through its confirmation: it runs the same HTTP server beside a CPU loop, bounded by the Free instance's 0.1 CPU. Wait for Running/Live, then open `/services/<id>/metrics?range=30m`, Raw + Percentage, all instances. The window includes the original, resumed and replacement instances.
- **Observed:** fresh desktop 1440×1000 at 12:44:40 shows CPU **0.1%** while the newer instance's API points reach **92.55276727078095%**. Fresh mobile 390×844 at 12:45:38 reproduces **0.1%**; its actual Metrics(CPU, percentage:true) response has the first historical instance's final point `12:39:37Z = 0.13470908047852115`, and the running instance's `12:45:37Z = 100.04089244388521`. The summary is the former, rounded to one decimal. Selecting only the running instance changes the header to **99.9%** and returns `12:45:52Z = 99.90017490161782`. Max returns one aggregate series and **100.0%**, matching `12:47:37Z = 99.99772292754182`. The exact requests and complete operation responses are below.
- **Expected / fix target:** a Raw view with multiple nonempty instance series has no unique scalar latest value. Keep its per-instance lines and labeled legend, limits, target and instance chooser, but omit the unqualified singular CPU/memory usage scalar. When exactly one series has points, use that series's last value, including an explicitly selected historical instance; ignore empty series when deciding this. An aggregate's single resulting series retains its scalar. Do not silently introduce max/average/sum into Raw, discard history, prefer a backend response order, or change the user's selection.
- **Root cause:** `dashboard/src/features/metrics/lib/series.ts:1–6` explicitly takes the last point of **series[0]**, without comparing timestamps or indicating its instance. `components/application-metrics-card.tsx:442–447` passes `latestValue(series)` to the unlabeled usage header for Raw multi-series results. Its `ResourceSection` has **two** JSX calls, Memory at 246–258 and CPU at 259–271. The chart itself maps all returned series and their instance labels; it correctly shows the newer high-CPU line. `LatestValue` at 478–498 already treats a null scalar as no scalar and preserves its initial loading text.
- **Producer / consumer trace:** `use-metrics.ts:192–194` passes the settled Metrics data to `lib/graphql-series.ts:30–45`, which maps non-null arrays in order and retains each point's timestamp/value. The metrics GraphQL resolver at `lego/backend/internal/metrics/graphql.go:298–312` returns the series without any promise that the first is newest. The current-instance API returned only `…-i83gtv2lnbe4gp34gprr`, while the Metrics response deliberately retained historical series. Installed Apollo Client **4.1.3** matches the recorded request extension: `dashboard/node_modules/@apollo/client/react/hooks/useQuery.js:125–140,185–193` forwards result data through its observable result; it does not supply a newest-instance summary. This is a presentation error over useful API history, not an API percentage or timestamp correction.
- **Bounded scope / aliases:** keep the shared `latestValue` contract unchanged. An exhaustive production search finds **five call sites**: four in ApplicationMetricsCard (two autoscale targets, Total Instances, and the shared usage ResourceSection), plus datastore disk capacity. Change only ResourceSection's usage-scalar decision. ApplicationMetricsCard has **one** production JSX consumer, `routes/services.$serviceId.metrics.tsx:129`; web/private/worker/cron resources share it. Actual static sites hide this card and show Network metrics; Postgres and Key Value use the separate datastore panel. The `web/worker/pserv/cron/static` URL aliases in `common/lib/render-alias.ts:13–19,68–76` redirect service subpaths to the same canonical route. Only Free web was live-tested.
