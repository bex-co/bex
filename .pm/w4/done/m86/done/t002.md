## Objective

Run the freshness resolver on a fixed schedule and maintain one actionable GitHub issue when upstream digests move, following the repository's existing staleness-workflow pattern.

## Context

- `scripts/cli-release-staleness.sh` and `.github/workflows/cli-release-staleness.yml` are the open/update/close issue precedent.
- The workflow needs only public registry metadata and repository issue permission; it must not receive cluster, registry-push, signing, or tenant credentials.
- A changed digest is a review request, not an authorization to update executable supply-chain input.

## Steps

1. Add a scheduled and manually dispatchable workflow that runs the resolver from t001.
2. Open or update one labelled issue containing affected logical images, exact old/new digests, and the files a reviewer must update; close it when drift clears.
3. Add local self-tests for no-drift, new-drift, issue-update, and issue-close decisions.

## Files

- `.github/workflows/`
- `scripts/`
- `scripts/cli-release-staleness.sh`
- `.github/workflows/cli-release-staleness.yml`

## Acceptance criteria

- [x] The schedule detects a fixture digest change and emits deterministic issue content with exact replacement values.
- [x] Repeated drift updates one issue rather than creating duplicates, and no-drift closes the owned issue.
- [x] Workflow permissions are least privilege and no production secret is referenced.
- [x] The workflow never edits, commits, or merges a digest change.

## Out of scope

- Dependabot/Renovate adoption, automatic pull-request merging, or unattended executable updates.
