# Deploy detail page offers "Rollback" on the current live deploy — clicking it restarts the service and lands on the same image

Why: an action labeled "Rollback" on the deploy you're already running silently restarts the service (real, if brief, downtime — worse on single-instance/free) and creates a redundant deploy that changes nothing; the deploys list correctly hides it, so list and detail disagree.

Source: live QA 2026-09-07, `$qa-find-bugs w4`.

## Symptom (reproduced on prod)

On a service's deploy **detail** page (`/services/<id>/deploys/<deployId>`) for the deploy that is currently **Live**, a **Rollback** action is shown. The deploys **list** (`/services/<id>/deploys`) does **not** show Rollback on the same Live row. "Rolling back" to the deploy that is already live is meaningless as a rollback — and it is not a no-op.

## Repro

1. Create any web service; let its first deploy reach **Live** (verified with a fresh free image service `qa-20260907-whoami`, `srv-daf8dsrh2g1c73dgc620`, `dep-daf8dsrh2g1c73dgc62g`).
2. Open the deploy detail page → a **Rollback** button appears next to the Live status.
3. Open the deploys list → the same Live/first-deploy row's Actions cell is **empty**.

Applies to **any** service's current live deploy, not just first deploys.

## Which surface is correct

The **list**. Rollback means "restore a **previous** (deactivated) deploy"; the currently-live deploy is not a previous deploy, so it must not be a rollback target. Render offers Rollback only to prior deploys, never the active one.

## Root cause (code-verified on `main`)

- Shared control `dashboard/src/features/deploys/components/deploy-actions.tsx:86` gates Rollback on `canRollback = isRollbackableDeployStatus(status)`.
- `isRollbackableDeployStatus` (`dashboard/src/features/deploys/lib/deploy-status.ts:42`) returns `status === "live" || status === "deactivated"` — **it includes `"live"`**.
- The **list** wraps `DeployActions` in an OUTER guard `hasListAction = isCancelableDeployStatus(d.status) || d.status === "deactivated"` (`deploys-list-page.tsx:176-177`, rendered at `:250`) — deactivated only, so the live row never renders the action.
- The **detail page** renders `DeployActions` with **no** outer guard (`deploy-detail-page.tsx:85`), so `canRollback` is true for the live deploy and the button shows. On click it calls `rollbackService(serviceId, deployId)` with `deployId` = the live deploy's own id (`deploy-actions.tsx:61-63`).
- Backend `Rollback` (`lego/backend/internal/deploys/service.go:764`) **allows** the live deploy as a target: the reject arm at `:789` is `target.Status != DeployLive && target.Status != DeployDeactivated || ResolvedImage==""` — i.e. Live **passes**. It then `SetAppImage`(current image), patches the App with `RestartedAt=now` (`:804`) + a new release generation, and `CreateRollbackDeploy`. Net effect of "rolling back to the current live deploy": a **real pod restart** plus a redundant deploy, ending on the identical image.

## Target behavior

A deploy is a rollback **target** only when it reached live, has a resolved image, **and is not the service's current live deploy** (status `deactivated`). Make all surfaces agree:

- **UI:** exclude the current live deploy from the detail-page Rollback (mirror the list's deactivated-only gate). Cleanest: change `isRollbackableDeployStatus` to `status === "deactivated"` (drop `"live"`); its **only** consumer is `DeployActions` (grep-confirmed), and the list already excludes live via `hasListAction`, so no list regression — the detail page stops offering it.
- **Backend:** mirror it — `Rollback` should reject the currently-live deploy as a target with a clear 409 ("deploy is already live — nothing to roll back to"), so REST/GraphQL/MCP callers can't trigger the redundant restart either. Do **not** rely on the UI gate alone.

## Blast radius

- `DeployActions` has exactly **two** production callers: `deploys-list-page.tsx:250` (guarded) and `deploy-detail-page.tsx:85` (unguarded).
- `isRollbackableDeployStatus` has **one** consumer (`DeployActions`).
- Backend `Rollback` is one function; check its **REST/MCP aliases** (`rollbackService` is the GraphQL mutation, `graphql.go:225`; verify whether a REST `POST …/rollback` and an MCP tool exist and route through the same `service.go:764` check — they must get the same new guard).
- Regression-test **both** surfaces: list still shows Rollback on `deactivated` and hides on `live`; detail page now hides on `live`, still shows on `deactivated`.

## Adjacent classes

- `deactivated` + resolved image → rollback target (unchanged, correct).
- `live` → **not** a target (the fix).
- `failed`/`build_failed`/`canceled`/`created` → not rollbackable (unchanged; no resolved image / never live).
- `deactivated` whose image was pruned → backend still rejects at the `ResolvedImage==""` arm (unchanged).

## Render parity

Render shows Rollback only for previous deploys, never the active one; bex's detail page diverges. Parity applies across UI + GraphQL + any REST/MCP rollback alias.

## Severity

**Minor** — no data loss, no blocked journey. But an action labeled "Rollback" on the current deploy silently restarts the service (real, if brief, disruption) while changing nothing, and the list/detail surfaces disagree.

## Resolution (2026-09-07)

Done — fixed on every surface, with a nuance the original analysis missed.

**The nuance.** The note proposed rejecting *any* live target. But a deploy stays `DeployLive` until a NEWER deploy goes live — a *failed* deploy never deactivates the prior (verified in `store.go`: deactivation happens only on a live close). So after a failed rollout, `spec.image` can drift off the still-live last-good deploy, and rolling back to that live deploy is a legitimate **recovery** — exactly what `TestRollbackRestoresPreviousLiveImage` documents. Rejecting all live targets would have broken it. So the guard keys on the **image**, not merely the status.

**Backend (`internal/deploys/service.go`, authoritative).** `Rollback` now refuses the target with a 409 when `target.Status == DeployLive && target.ResolvedImage == a.Spec.Image` — the true no-op (the deploy is live and already the running image, so the rollback would only restart the service and mint a redundant deploy). A live-but-drifted target (recovery) and every `deactivated` target still succeed. All three surfaces (REST `POST …/rollback`, GraphQL `rollbackService`, MCP `rollback_deploy`) route through this one verb, so they're covered together. New tests: `TestRollbackRefusesCurrentLiveNoOp` (no-op → 409), `TestRollbackToLiveDeployRecoversDriftedImage` (drift → allowed); `TestRESTCancelAndRollback` updated to roll back to a deactivated target.

**Dashboard.** `isRollbackableDeployStatus` drops `"live"` (now `deactivated`-only) — its one consumer is `DeployActions`, mounted on **three** surfaces, all now consistent: the deploys **list** already gated on `deactivated`; the deploy **detail** page (unguarded `DeployActions`) stops offering Rollback on the live deploy; and the **events feed** — a third surface the note flagged as unverified — had `hasAction = … || status === "live"`, which showed Rollback on a `deploy_ended`/succeeded row (mapped to live); it now mirrors the list's `… || status === "deactivated"`. Tests updated: `deploy-status.test.ts`, `deploy-actions.test.tsx` (+ a "no Rollback on the current live deploy" case), and the events-page rollback tests now exercise a deactivated deploy.

**Docs.** ADR018's Rollback parity row records the no-op guard, the image-keyed recovery exception, and the all-surfaces-agree UI behavior (Render never offers Rollback on the active deploy).
