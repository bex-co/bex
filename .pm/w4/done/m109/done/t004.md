## Objective

Confirm the two field fixes are consistent across every surface a project is exposed on, and compare against render.com's project object.

## Context

- `w6/m126` t004 concluded that GraphQL and MCP "were already internally consistent (all project verbs return the bex-native `ProjectView`)" — meaning those surfaces expose `ownerId`, not an `owner` object. A live probe on 2026-09-16 confirms it: `{ project(id: "…") { owner { … } environments { … } } }` answers `Cannot query field "owner" on type "Project". Did you mean "ownerId"?`. So `t002` is REST-only unless the view gains the field; `t001`'s `updatedAt` may reach further, since it lives on `ProjectView`.
- `docs/ADR018-render-parity.md`'s Projects row, and `docs/cli-compatibility-checklist.md` (the pinned `render-oss/cli` is the client that reads these fields).

## Steps

1. Read a project through REST, GraphQL and MCP after the fixes; record which fields each exposes and confirm nothing disagrees where they overlap.
2. Compare with render.com's project object: what it returns for `owner` and `updatedAt`, and whether its `updatedAt` moves on a rename.
3. Check the dashboard's project pages for anywhere an owner or a modification time is displayed — if a surface shows a raw `tea-…` id where a name is now available, either fix it or file it as follow-up.
4. Update the ADR018 Projects row and the CLI compatibility checklist if either now describes stale behavior.
