## Objective

`GET /v1/projects/{id}` reports `updatedAt` equal to `createdAt` forever: the REST mapper hardcodes the copy, and the view type has nowhere to carry the real value even though the store maintains it. Read the real column and return it.

## Context

Live probe, production, 2026-09-16 — a successful rename that does not move the timestamp:

```
GET   /v1/projects/prj-dal49f3kmutc73d7qaig
  createdAt 2026-09-16T07:26:52.362014Z   updatedAt 2026-09-16T07:26:52.362014Z

PATCH /v1/projects/prj-dal49f3kmutc73d7qaig  {"name":"qa-20260916-p1-renamed"}  -> 200
  "createdAt":"2026-09-16T07:26:52.362014Z","updatedAt":"2026-09-16T07:26:52.362014Z"

GET   /v1/projects/prj-dal49f3kmutc73d7qaig
  name is "qa-20260916-p1-renamed"; updatedAt is STILL 07:26:52.362014Z
```

The chain, top to bottom:

- `lego/backend/internal/projects/rest.go:56-66` — `toRenderProject` ends with `UpdatedAt: p.CreatedAt`. Since `w6/m126` every project verb funnels through this function, so every verb returns the frozen value.
- `lego/backend/internal/projects/service.go:156-164` — `ProjectView` has `CreatedAt` but **no `UpdatedAt` field**, so the mapper has nothing truthful to read.
- `lego/backend/internal/store/projects.go:59` — `UPDATE projects SET name = $2, updated_at = now() WHERE id = $1`. The column exists and is maintained. Lines `194` and `203` do the same for the link/unlink paths (`UPDATE apps SET … updated_at = now()`) — check whether those touch the *project* row's `updated_at` or only the app rows, and make the link verbs move the project's timestamp if they are supposed to.

The control that proves this is a projects bug and not a bex-wide convention, captured in the same session: an environment-group rename **does** advance its `updatedAt` (`2026-09-16T07:30:06.935495138Z` → `07:30:36.896913093Z`) and bumps its `revision`.

## Steps

1. Add `UpdatedAt time.Time` to `ProjectView` and populate it from the store read; check the `SELECT`s in `internal/store/projects.go` actually project the `updated_at` column.
2. Change `toRenderProject` to use it. Keep `CreatedAt` as-is.
3. Walk all seven project handlers (`GET` list, `GET` one, `POST`, `PATCH`, and the three link `PUT`s) and confirm each returns the freshly-read value rather than a pre-mutation copy — a handler that renders from its request input instead of re-reading will still return the stale timestamp.
4. Decide what a project with no recorded modification returns (rows created before the column was maintained, if any): `updatedAt == createdAt` is the right answer there, and it must be reached by reading, not by hardcoding.
5. Check GraphQL and MCP project shapes for the same field — if either exposes `updatedAt`, it must move too; if neither does, note that in the task's result so `t004` does not re-derive it.

## Acceptance criteria

- [ ] A rename makes `updatedAt` strictly greater than the previous `updatedAt` and than `createdAt`.
- [ ] Each of the three link `PUT`s moves it too, or it is documented why a link is not a project modification.
- [ ] `POST /v1/projects` returns `updatedAt == createdAt` for a brand-new project.
- [ ] The env-group control is re-run and still advances.
- [ ] No handler returns a timestamp read before its own mutation.
