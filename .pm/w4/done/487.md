# 487 — Secret-file writes (single PUT, whole-set PUT, DELETE) leave no Events-feed row, while env-var writes and env-group links do

Why: someone reading a service's Events tab to find out who changed its configuration sees every env-var edit and env-group link but never a secret-file edit, even though a secret file is the more sensitive of the two (certificates, keys, `.env` files).

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-04 ~22:50 UTC (`muse.env`, workspace `bex`); **minor** (audit and observability gap; nothing is lost or misapplied); ~30m.
- **Probe** (fixture `qa-20261104-envsvc`, `srv-dblr5d8g64rs73avmdg0`, a free `ghcr.io/traefik/whoami:latest` web service, plus env group `evg-dblr5d8g64rs73avmdeg`; both deleted afterwards, `GET` 404 and absent from the lists). All calls from the dashboard page with `fetch(..., {credentials:'include'})`; the count is `GET /v1/services/srv-dblr5d8g64rs73avmdg0/events?limit=40`, length of the returned array:

  | # | Request | Status | Events after |
  | --- | --- | --- | --- |
  | 0 | baseline | | 10 |
  | 1 | `PUT /v1/services/{id}/secret-files` body `[{"name":"set1.conf","content":"x\n"},{"name":"set2.conf","content":"y\n"}]` | 200 | 10 |
  | 2 | `DELETE /v1/services/{id}/secret-files/set1.conf` | 204 | 10 |
  | 3 | `PUT /v1/services/{id}/env-vars/QA_THREE` body `{"value":"3"}` | 200 | 11 |
  | 4 | `DELETE /v1/services/{id}/env-vars/QA_THREE` | 204 | 12 |

  Earlier in the same run, `PUT /v1/services/{id}/secret-files/qa.conf` (201), `qa2.conf` and `qa3.conf` also added no row, while `POST /v1/env-groups/{eg}/services/{id}` and the matching `DELETE` added `env_group_linked` and `env_group_unlinked`. The event types present at the end were `env_vars_changed`, `env_group_linked`, `env_group_unlinked`, `deploy_started`, `deploy_ended`: none for the files. The secret-file contents were saved (`GET …/secret-files` listed them) and `undeployedChanges` read `true`, so the writes themselves worked.

- **Root cause:**
  - `secrets/files.go:150` `SetSecretFile`, `:198` `SetSecretFiles` and `:657` `DeleteSecretFile` never call `RecordAppConfigChanged`. The env-var verbs do: `secrets/service.go:569` (`SetEnvVars`), `:633` (`SetEnvVar`), `:663` and `:676` (`DeleteEnvVar`), `:752` (`SeedEnvVars`), and `secrets/batch.go:446` (`PatchEnvironment`).
  - The Events feed is built from those audit rows through the verb map at `events/service.go:444-455` (`secrets.SetEnvVar` → `env_vars_changed`, `secrets.PatchEnvironment` → `service_environment_changed`). No `secrets.*SecretFile*` verb exists in that map, and none is in the fixed vocabulary `appConfigVerbs` (`core/audit.go:530`), which `RecordAppConfigChanged` enforces (`core/audit.go:567-571`: an unlisted verb is refused with a log line).
  - The type that already describes this case is `service_environment_changed`; its documented meaning is "env vars + files; names and values absent" (`events/service.go:41-52`). So the dashboard's batch Save (`PatchEnvironment`) does record file changes, and only the per-file and replace-all entrypoints skip it.
- **Fix (target behavior):** a successful secret-file create, replace, replace-all or delete writes one Events row of type `service_environment_changed` (or a new `secret_files_changed` if the owner prefers the env-var split; the repo's own precedent is the first), with names and contents absent, exactly as env-var rows redact. A no-op write (same content) records nothing, as `SetEnvVar` does. Add the three verbs to `core/audit.go` and to the `appConfigVerbs` set, map them in `events/service.go`, and call `RecordAppConfigChanged` after the write lands (after `materializeFiles` succeeds, so a compensated failure records nothing).
- **Blast radius:**
  - Callers of the three service methods (grep over non-test code, 7 call sites): REST `secrets/rest.go:179` (`SetSecretFiles`), `:202` (`SetSecretFile`), `:206` (`DeleteSecretFile`); MCP `secrets/mcp.go:238`, `:246`; GraphQL `secrets/graphql.go:277`, `:288`. One change in `files.go` covers all three surfaces.
  - The audit-log view lists verbs from `core/audit.go`; check for an exhaustive table test over `AllAuditVerbs` and any dashboard label map for event types (`en.ts`/`zh.ts`), which must gain a label if a new type is chosen. With `service_environment_changed` no UI change is needed.
- **Adjacent classes:** failures stay as they are (a quota or validation refusal records nothing); a denied caller records the usual authorization audit and no config-change row; a secret-file write on a suspended App records the row like an env-var write does.
- **Unverified:**
  - The dashboard's own secret-file editor goes through `PatchEnvironment` (`secrets/batch.go:446`) and should already record; it was not exercised in the browser this run.
  - GraphQL and MCP secret-file writes were reasoned from the shared service method, not probed.
  - Whether the audit-log (not the Events feed) has a row for these writes: the ordinary authorize-time audit may already record a generic verb. Check `GET` of the audit log for the fixture before choosing the verb names.
- **Render:** Render's service events list has no event named for secret files that I verified, so this is a bex-extension completeness gap (consistent with how bex already extends events for env vars and env-group links), not a Render-parity divergence.
- **Dedupe:** `grep -rli "secret.file" .pm/w4 .pm/w6` finds w4/067 (env group page copy), w4/075 (coverage record), w4/100 (Events feed vs deploys list wording for a config-change deploy). None mentions a missing event for secret-file writes. Not covered by `.pm/DO_NOT_DO.md`. The env-var-versus-env-group deploy-row difference I saw in the same run (env-group link opens a `service_updated` deploy, env-var and secret-file saves open none and set `undeployedChanges`) is documented in ADR004 § Ordinary Save-only differences (w4/m145) and ADR004:243, so it is not filed.
- **Cleanup:** fixture service and env group deleted; this run's Kratos session revoked.

- **Closed 2026-11-05:** secret-file verbs record service_environment_changed (secrets/files.go, core/audit.go, events/service.go).
