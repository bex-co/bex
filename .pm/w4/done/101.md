# Blueprint detail's Managed Resources names are plain text — nothing links to the resource

Why: every other resource table in the product links names to their detail pages, but a blueprint's managed resources are a dead end — the reader must leave the page and search the resource by name.

## Record

- Severity: minor
- Repro: Blueprints → `qa-20260919-p28-bp` (`blp-dan9g8rs0ils73bgp500`, since deleted) → Managed Resources row `static-site` is a `<td>`, not a link. Live 2026-09-19.
- Expected / Actual: the name links to the resource's detail page (service → `/services/:id`, static → `/static/:id`, Postgres → `/databases/:id`, Key Value → `/keyvalue/:id`, env group → `/env-groups/:id`) / plain text.
- Root cause: `dashboard/src/routes/blueprints.$blueprintId.tsx:467-471` renders `{r.name}` in a `TableCell` while `r.id` sits unused beside it (only the row `key`); no type→route helper exists.
- Fix: add a `blueprintResourceHref(type, id)` helper (`dashboard/src/features/blueprints/`, with en/zh unchanged — no new copy) mapping the backend's closed type set (`lego/backend/internal/apps/blueprint.go:1472-1496`: `effectiveType(App)` for services, `"postgres"`, `"key_value"`, `"environment_group"`) onto the five dashboard routes, and render the name cell as a link. Unknown future types fall back to plain text (never a broken href).
- Blast radius: one table cell + one new helper; the only producer of `BlueprintResource.type` is `blueprint.go:1472-1496` (4 call sites, enumerated above).
- Adjacent classes: resources whose backing object was deleted out-of-band still render plain text (no id to link); sync-history and manifest cards untouched.
- Unverified: env-group–bearing blueprints (this run's manifest had a static site only) — the `environment_group → /env-groups/:id` arm needs a live click.
- Render: n/a (Render has no blueprint detail page with managed resources; this aligns bex's own tables).
- Estimate: 20m

## Resolution (2026-09-21)

Done as filed. `blueprintResourceHref(type, id)` (`dashboard/src/features/blueprints/lib/resource-href.ts`) maps the backend's closed type set onto the dashboard routes, and the Managed Resources name cell renders a `Link` when it resolves.

**One correction to the note's plan.** It specified `static → /static/:id` as its own arm; the helper instead defers the five *service* types to the existing `serviceBaseForType` (`features/services/lib/service-base.ts`), which already owns the "a static site is canonical under `/static/<id>`, everything else under `/services/<id>`" rule from w5/m57. Writing a second copy of that rule here is how the blueprint table would eventually disagree with every other service link in the product.

Unknown types and id-less rows both return `null` and render as plain text — the pre-fix behavior for everything — so a future backend resource kind, or a resource whose backing object was deleted out of band, can never produce a broken href.

Covered by `blueprintResourceHref` unit tests: every one of the seven type arms, the static-site base, and both no-href cases. The note's one unverified item — the `environment_group → /env-groups/:id` arm, which this run's manifest could not exercise — is now covered by test rather than by a live click; a live confirmation still belongs to the next QA pass. Not re-probed live.
