# 693 — The dashboard shows a resource's region as the API slug `frankfurt`, lowercase and in every language, where Render names the place

Why: the region is a display value on four dashboard surfaces. The API answers Render's slug (`frankfurt`), which is correct for clients. The dashboard prints that slug verbatim, so English reads a lowercase identifier and the ja, de and zh dashboards show the same untranslated English word under a translated label ("リージョン frankfurt"). Render's region docs name each region by place ("Frankfurt, Germany", "Oregon, USA", …).

- **Source / severity / estimate:** live `/qa-find-bugs w4` round 528, 2026-11-16 16:00–16:10 UTC, pin `bf2ab888d7dc`, workspace `bex-canary`. Read-only: the canary `hello-go` (`srv-dbkq3hdhhjfs73eiahe0`) and the leftover Key Value `qa-20261110-81b5-kv` (`red-dbpf5q5me2kc73f2l0og`) were viewed, not changed. **Minor:** copy and i18n; nothing is lost. ~30m.
- **Probe:**
  - A headless crawl of 22 dashboard pages at 1440 with the `i18nextLng` cookie (and `localStorage`) set to `en`, `ja` and `de`. It collects every visible text node plus each `aria-label`, `placeholder` and `title`, then diffs the locales.
  - Key Value page `/keyvalue/red-dbpf5q5me2kc73f2l0og`: the metadata row reads `Region` / `frankfurt` in en, `リージョン` / `frankfurt` in ja, and the German label over `frankfurt` in de.
  - Service Settings `/services/srv-dbkq3hdhhjfs73eiahe0/settings`: `page.getByRole('textbox', { name: 'Region', exact: true }).inputValue()` → `frankfurt` (the disabled Region field).
  - `GET /v1/services/srv-dbkq3hdhhjfs73eiahe0` → `serviceDetails.region: "frankfurt"`. `GET /v1/key-value/red-dbpf5q5me2kc73f2l0og` → `region: "frankfurt"`. The API values are right; only the display is wrong.
  - Every other string the crawl found identical across locales is deliberate:
    - product and plan names the locale files keep in every language (Web Service, Background Worker, Key Value, Blueprints, Deploy Hook, Free, Starter, Pro, …);
    - German loan words (Dashboard, Logs, Shell, Rollback, …);
    - Ory Elements' own strings ("Notifications alt+T", "Unlink github"), which are upstream;
    - the typed confirmation phrase "delete my account";
    - resource names, IDs, commit messages and user agents.
- **Cause:** four sites render the field verbatim, and `dashboard/src` has no region label map.
  - `dashboard/src/routes/services.$serviceId.settings.tsx:145` (`value={service.region}`)
  - `dashboard/src/features/keyvalue/components/key-value-metadata-card.tsx:87`
  - `dashboard/src/features/databases/components/database-metadata-card.tsx:118`
  - `dashboard/src/features/projects/components/resource-table.tsx:221` (the project page's Region column)
  - `grep -rnE "[a-zA-Z]\.region\b|\{region\}" dashboard/src --include='*.tsx'`, without tests, lists these four. It also lists the sandbox group dialog (`features/sandbox-groups/components/new-sandbox-group-dialog.tsx:260`, a bex extension with no Render counterpart) and the skeleton's presence checks (`common/components/route-skeletons.tsx:2165`, `:2188`).
- **Fix:**
  - Add one `regionLabel(slug)` helper with a locale key per alias in `resourcemeta.RenderRegions` (`lego/backend/internal/resourcemeta/metadata.go:141`: `frankfurt`, `ohio`, `oregon`, `singapore`, `virginia`), in all eight locales. An unknown value renders verbatim.
  - English labels name the place as Render does. Check Render's dashboard for the exact label of an existing resource before shipping; its docs say "Frankfurt, Germany".
  - Use the helper at the four sites. REST, GraphQL and MCP keep the slug, as Render's API does.
  - Test each site: `frankfurt` renders as the en label and as the ja label.
- **Unverified:**
  - the project page's Region column (the workspace has no project);
  - the Postgres card (the workspace has no Postgres);
  - Render's exact dashboard label for an existing resource's region. Its docs were read, and its dashboard was not opened.
- **Done when:** on production, the Key Value page's Region row and the service Settings' Region field read the English place label at `i18nextLng=en` and the Japanese label at `ja`, while `GET /v1/services/{id}` still answers `serviceDetails.region: "frankfurt"`.

**Done 2026-11-16 (`/loopx w4`):** `regionLabel(slug, t)` (`dashboard/src/common/lib/region-label.ts`) maps each `resourcemeta.RenderRegions` alias to a `common.region*` key in all eight locales. The English labels are Render's region docs names (render.com/docs/regions: "Frankfurt, Germany", "Ohio, USA", "Oregon, USA", "Singapore", "Virginia, USA"); Render's dashboard was not opened. An unknown slug (e.g. `fsn1`) renders verbatim. The service Settings Region field, the Key Value and Postgres Details cards and the project Region column use it; REST, GraphQL and MCP keep the slug. Tests on all four sites assert `frankfurt` → "Frankfurt, Germany" (en) and "フランクフルト（ドイツ）" (ja), and an unknown slug stays verbatim. With the helper returning the slug, 6 of them fail. The live replay of the DoD rides the next production pin.
