# 457 — A failed deploy's build log shows its failure detail lines in reverse order, under the headline

Why: The dashboard's closing build-log lines (the failure cause) read backwards, with the "Build failed: …:" headline last and ending in a dangling colon, so the cause is hard to read where customers look first. Render's build log is strictly chronological.

Source: live `/qa-find-bugs w4` loop run, 2026-11-01 UTC (`muse.env`, QA workspace `bex`). Severity: minor. Regression of an interaction between `w8/m116` (backward pages newest-first, `d5c3373ed`) and `w4/m192` ("equal stamps keep source order").

## Repro (https://dashboard.bex.co)

1. New > Service > Web Service > Public Git URL `https://github.com/bex-co/bex`, branch `main`, Root Directory `examples/hello-go`, Runtime Docker, Dockerfile Path `./does-not-exist/Dockerfile`, Free > Deploy Service (fixture `qa-20261101-badbuild`, `srv-dbk0mfdcqbus73fijh8g`, deleted in-run).
2. After ~3 min the deploy is "Build Failed". Open the deploy's log.

- **Expected:** closing lines chronological: `==> Build failed: build failed in the clone step:`, then `==> From https://github.com/bex-co/bex`, `==> * branch 77307722… -> FETCH_HEAD`, `==> the Dockerfile "examples/hello-go/does-not-exist/Dockerfile" does not exist in the repository at …`.
- **Actual:** the dashboard renders the Dockerfile line, then `* branch`, then `From`, and the `Build failed: build failed in the clone step:` headline last.

## Probes (run from the page with credentials, `https://api.bex.co`)

- `GET /v1/logs?resource=srv-dbk0mfdcqbus73fijh8g&type=build&direction=forward&limit=50` returns the four terminal lines in the **correct** order, all stamped `2026-11-02T04:05:52.074359Z`.
- `direction=backward` returns the exact reverse, which is correct for backward.
- The dashboard's only logs request is `GET …/v1/logs?…&type=build&direction=backward&limit=50`. The GraphQL `logs` query (default) returns the same newest-first order. So the API is right and the dashboard is wrong.

## Root cause

`dashboard/src/features/logs/lib/map.ts` `mergeLogLines` (~L254-272) and `dashboard/src/features/deploys/hooks/use-deploy-logs.ts:205` sort by timestamp with a stable sort; the comment says "Equal stamps keep source order (history, then arrival)" (m192, decided when pages were oldest-first). Since `w8/m116` backward pages arrive most-recent-first, so every group of lines sharing an exact instant renders reversed.

The synthesized terminal lines (`lego/backend/internal/logs/progress.go:303-306`, `terminalLines` at `:317`, each segment `add(d.FinishedAt, …)`) share one timestamp by construction, so every multi-line failure reason (`build_failed`, `pre_deploy_failed`, `update_failed`) is affected. A Live deploy's "Detected HTTP on port N; serving it" and "Your service is live" lines share `FinishedAt` too (cause traced, order on a live deploy not probed).

## Fix

Target behavior: within a tie, the order the forward API returns. Make each backward page chronological before the stable merge (reverse the page, or tie-break on the page's source index) in `useOlderLogPages` / `toLogLines`, so `mergeLogLines` keeps "equal stamps keep chronological source order". The API (REST/GraphQL/MCP/CLI) does not move. Do not fix it only with backend per-line sub-microsecond offsets: real pod lines that tie would still reverse.

- **Blast radius (grep):** `mergeLogLines` has 4 callers (`deploys/hooks/use-deploy-logs.ts:264`, `logs/components/log-viewer.tsx:230`, `logs/components/datastore-log-viewer.tsx:231`, `logs/hooks/use-log-history.ts:168`), plus `compareLogTimestamps` in `use-deploy-logs.ts:205` and `:256`. All share `useOlderLogPages`, so the fix is global. Controls needing regression tests: distinct stamps, live-tail append order, the m217 same-millisecond distinct-ID cases, the m192 stampless-neighbor case.
- **Adjacent classes:** none (ordering only, no access semantics).
- **Unverified:** whether the live SSE tail while the build is still running shows the same reversal (it was seen on a page open through the failure and again after a fresh reload); the service logs viewer and datastore log viewer (reasoned from the shared hook, not probed); a Live deploy's two same-instant lines.
- **Render:** build log is strictly chronological.
- **Estimate:** 45m.

## Dedupe

grep of `.pm` open and `done/` for identical/same timestamp/equal stamp/tie found only `w4/m192` (`verification.md` L8 sets the equal-stamps rule), `w4/m217` (distinct IDs at one millisecond) and `w8/m116` (newest-first backward pages). None covers tie order after m116, so this is a new interaction, not a duplicate.

Evidence is the probes above; the `.playwright-mcp` screenshots are session-local.

## Done 2026-11-01 (loopx w4)

`toLogLines` returns each newest-first page oldest-first so `mergeLogLines` keeps chronological tie order for all four viewers; tests in `map.test.ts`; dashboard logs+deploys vitest green.
