# Restart tells users to retry a revision that has no deploy record

Why: a user needs a recovery step when waiting and retrying cannot establish the deploy record required by Restart.

- **Severity:** minor, misleading recovery guidance. Restart deliberately refuses an unresolved current release. The app remains available and a standard deploy restores a usable tracked release; no outage or wrong artifact selection is claimed.
- **Estimate:** 55m: reason-specific server copy 15m, shared adapter and consumer review 10m, behavioral refusal/control tests 20m, owned live replay and cleanup 10m. Keep this as an inbox fix.
- **Source:** continuous functional qa-find-bugs, user-directed w4, 2026-10-12 UTC pass a246; muse profile via QA login helper, workspace `tea-d98210cbbpdc73dcrkvg`, Free Node service. Research HEAD `a84eb3ae5`. Filing only.
- **Goal linkage:** [ADR004 deployment](../../docs/ADR004-app-deployment.md), [ADR013 environment groups](../../docs/ADR013-secrets.md), [ADR018 parity](../../docs/ADR018-render-parity.md), and usable recovery on the existing hosting surface.

## Reproduction

Create an owned Free web service from public repo `https://github.com/bex-co/bex`, main, root directory `examples/hello-node`, runtime Node, build `npm install`, start `npm start`, port 3000 and Auto-Deploy off. This pass used **qa-20261011-a246-node**, `srv-db63ilfd2afc73cd1dng`. Create workspace group **qa-20261011-a246-group**, `evg-db63j7e7vdus73e6d2tg`, with harmless `MESSAGE=qa-a246-group-v1 雪`.

1. Link the group through its **Linked Services** controls. This changes the native artifact inputs and eventually serves rev-2. No deploy row is opened by the Auto-Deploy-off link. At 01:39:06.547Z the service is Running/rev-2 and its only row is the original canceled first deploy.
2. Open **Manual Deploy → Restart service → Restart**. The initial attempt (response preserved by network request 2287) refuses with **“is serving rev-2 but no deploy records that release; retry shortly.”** Fresh-load the page and repeat: the complete captured response at **01:42:57.376Z** is the same refusal. The service has already been observed Running for over three minutes. No row for that release is created by the retry.
3. Stage group v2 with **Save only**: the stored value changes while the app continues serving v1. Save group v3 with **Save and deploy**: `pendingServiceIds` names this Auto-Deploy-off service. Then choose **Deploy latest commit**. The new tracked deploy reaches Live/rev-3, and external HTTP 200 serves group v3.
4. **Passing control:** fresh-load and Restart at **01:45:33.887Z**. It opens a real deploy, reaches Live/rev-4 by **01:45:47.696937Z**, and keeps the current artifact. This is the same service and Restart control, after a standard deploy established a tracked serving release.
5. Set a service-level `MESSAGE=qa-a246-service-override 雪` through its Environment editor and **Save and deploy**. The tracked config-change deploy reaches Live/rev-7; external HTTP 200 serves the service value with the group still linked.
6. Unlink the group at **01:48:36.065Z**. Wait: at **01:49:51.379Z** the service is Running/rev-8, the group is absent from `linkedEnvGroupIds`, and history still has four rows, newest the prior tracked rev-7 release. HTTP 200 retains the correct service-level value. Thus the repeat is from an established tracked service, independent of the initial first-deploy projection timing.
7. Fresh page → Restart at **01:50:07.724Z** refuses **“is serving rev-8 but no deploy records that release; retry shortly.”** Another fresh-load retry at **01:50:46.778Z** repeats the exact refusal and no new deploy row. The accessibility tree includes the same full error toast.

The problem is the recovery instruction attached to a valid refusal. Preserve the refusal. A standard deploy is a different user action and applies saved configuration/current source; do not describe it as a Restart that preserves the current runtime.

## Target and bounded fix

Give the **missing serving deploy row** branch an actionable explanation, for example: **“The current release has no deploy record, so Restart cannot preserve it. If this persists, run a standard deploy to establish a tracked release. A standard deploy applies saved configuration.”** The repo-backed dashboard action is **Manual Deploy → Deploy latest commit**; it also uses the current branch head, so the guidance must not imply it is an equivalent preservation action.

A missing row can also be a brief dispatch window: allow a short retry, but do not promise waiting will repair a persistent rowless release. Do not infer permanence solely from one request. This pass establishes persistent examples and the successful standard-deploy control.

Keep the current `ErrConflict`/no-write behavior and all selection rules. No automatic deploy, fabricated Live row, fallback to an older SQL-Live release, gate change, new capability action or release-record reconstruction is requested. This is a server-message fix, with consumer verification.

## Root cause and consumers

- `lego/backend/internal/deploys/rollback_config.go:202–218` resolves the serving `rev-N` to a deploy by app ID + generation. An empty result correctly refuses at :217.
- `rollback_config.go:233–234` formats **every** unresolved reason with **“retry shortly”**. The missing-row branch can be long-lived: `envgroups/service.go:1261–1266` deliberately uses `rollout.PatchAppLocked` for repo-backed Auto-Deploy-off links/unlinks, without opening a deploy row. The native group-ref artifact identity described in ADR013 can nevertheless converge to a new serving revision. This is the explicit w2/m94 link decision, not a request to reverse it.
- `store/store.go:2350–2360` looks up the existing app/generation row; it does not create one. Repeating Restart is not a row-creation/reconciliation operation when selection refuses.
- `dashboard/src/features/services/hooks/use-trigger-deploy.ts:81–89` catches the resolver error and displays `mutationErrorMessage`. `common/lib/graphql-error.ts:22–27,146–148` preserves the server reason, changing its first-letter case. The complete captured toast confirms this consumer receives the misleading instruction.
- Actual pinned Apollo **4.1.3** `node_modules/@apollo/client/core/QueryManager.js:165–166` throws `CombinedGraphQLErrors` on a mutation error with the default none policy; `errors/CombinedGraphQLErrors.js:1–9` joins the returned messages. HTTP 200 with GraphQL `errors` is therefore a refusal, not a successful Restart. No HTTP transport failure was observed here.

**Counted blast radius:** `unresolvedServing` has **3 production call sites** in one file: missing configuration record (:187), missing deploy row (:217), unresolved image/current-attempt mismatch (:227). Limit the new recovery wording to **the missing-row call**; preserve the other outcomes. `servingDeploy` has **2 production callers**, both in Restart selection (unlocked selection check and locked selection). This message change must not alter selection or lock behavior.

`deploys.Service.Restart` has **2 production dispatch callers**: GraphQL at `deploys/graphql.go:236–242`, and the REST/MCP bridge at `api/server.go:874–883`. `apps/service.go:3542–3547` relays the same error. Aliases are GraphQL **restartServer**, REST **POST /v1/services/{id}/restart** (`apps/rest.go:781`), and MCP **restart_service** (`apps/mcp.go:787–791`). These route through the same verb; REST and MCP were source-traced, not live mutation probes in this pass.

The dashboard hook has **2 production callers**: ManualDeployButton and the Environment editor. Only ManualDeployButton consumes its Restart function; the editor uses normal trigger for rebuild. Canonical service `/services/<id>` and static `/static/<id>` headers share that control. Families: web observed; private and worker use the compute path but were not replayed; cron has no Restart menu; static has separate static selection/fallback behavior; Postgres and Key Value use separate datastore verbs. No claim that those unprobed families exhibit this missing-row message.

**Adjacent outcomes:** keep missing current image, current-attempt mismatch, unavailable configuration record, no served release/legacy fallback, store/read failures, canceled/in-progress history and explicit rollback behavior as currently specified. Denied/unauthenticated/deleting/replaced/billing/unavailable-store/transport failures retain their existing adapters; none was induced. Do not change any of these to success or a fabricated deployment.
