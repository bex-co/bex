## This is deploy lag, not a failed fix — two independent signals

1. **The arithmetic matches the old bound.** The fix replaced `credentialMaxInflight = maxInflight / 8` with an explicit `BEX_MAX_INFLIGHT_PER_CREDENTIAL`, default **64** (`lego/backend/CLAUDE.md` env table, added by the same commit). At 64 a 25-burst cannot shed at all; shedding exactly 5 of 25 is what the **old** `64/8 = 8` produces.
2. **The sibling fix from the same batch is also absent.** `f35701695` ("surface client_id and grant advertised scopes on mint" — the `w4/m105` fix) rewrites the dashboard's API-keys panel. Production's Settings → API Keys still renders the **old** table (`Name / Created / Created by / Last used / Actions`), and the string `client_id` appears nowhere on the page. Both images are pre-fix, which also rules out "bex-api deployed but the change regressed".

**Do not read the 40-burst's 23-vs-17 as a regression.** One sample of a noisy measurement at a different time of day against a shared cluster; nothing in the diff could raise the shed rate while leaving the 25-burst bit-identical. Re-measure both bursts a few times after the deploy if it matters.

## What should happen

Both milestones are already `done/` with `- [x]` in the workstream README, and this note does **not** reopen them — that is the owner's call. But `.pm/CLAUDE.md` and the standing Closeout rule both say a milestone lands in `done/` "when its observable end state is real, not merely when the code is written", and for m100 it is not yet. Either:

- **(a) Re-verify after the deploy and leave the milestones closed** — the cheap path, and what this note assumes. The steps are below.
- **(b) Reopen m100 until the live probe passes**, if the project wants `done/` to mean live-verified rather than merged.

### The re-probe, once production serves the post-`e6419af0b` image

1. **Confirm the deploy first.** Cheapest tell available today is the sibling fix: Settings → API Keys shows a **Client ID**. (bex-api exposes no version/build endpoint — adding one would make every future deploy-lag question a single request instead of an inference. Worth its own note if someone agrees.)
2. 90 sequential `GET /v1/services?limit=1` → 90 × 200, then 25 parallel `metrics` POSTs → **25 × 200**, then 40 → **40 × 200**.
3. **Re-run the anti-amplification control in the same session** — a flood of unique invalid bearers from one source must still shed, and `w1/m67`'s bounded-upstream-call assertions must still hold. t001's whole point was separating the two budgets; verifying only the permissive half would accept a fix that removed the protection.
4. **Re-check the bearer control case** (m100's own "Bearer control case" section: bearer callers shed 0 × 429 before the fix). They must still shed nothing — if bearers now shed, the new per-credential bound was applied too broadly.
5. **t004's repo-backed half:** save an env-var change on a **repo-backed** service and confirm the new `trigger: "config_change"` row carries a `commit.id` equal to the deploy it superseded. The **image-backed** half is already verified live (pass 18, recorded in `w4/m101/t013`): that row has no `commit` key at all and carries `image.ref` — the fix must preserve exactly that.
6. **m105's half:** mint a key and confirm the UI shows its `client_id`, then that a `client_credentials` exchange requesting `scope=bex.read` succeeds rather than returning `invalid_scope`. Note `w4/076` records that **pre-m105 keys keep an empty Hydra scope** and must be reminted — so test with a freshly minted key, not `m43-verify-temp`.
