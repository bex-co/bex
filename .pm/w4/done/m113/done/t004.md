## Objective

`type=request` returns `{"logs":[]}` for a static site with real traffic — the shipper structurally drops every static access line — so request logs and the Loki-served host/path-filtered metrics read are both dark for static. Attribute static request lines to their App (preferred: shipper-side, no new cardinality) or emit them from the static-server.

## Context

### The observation (production, 2026-09-17)

Same fixture (`srv-dam398js0ils73bgp0lg`, ~25 requests incl. distinct methods/paths/hosts): GraphQL `logs(resource, type: request)` → `{"logs":[]}`; `logLabelValues(label: method|statusCode)` would likewise answer `[]` (same store the w6/m131 outage emptied for compute).

### Root cause (read, not guessed)

Static traffic flows to the shared static-server Service (ADR029: each static host's Ingress points at it), so Traefik's `ServiceName` is a platform Service (`bex-system` namespace), not `<tenant-ns>-<app>-<port>@kubernetes`. The shipper's attribution regex (`deploy/gitops/base/log-shipper.yaml` `loki.process.request_logs`) only matches `tea-<xid>`/`default` namespaces, and the static host is not in the platform-host allowlist — so every static access line drops as `not_a_tenant_app`. bex-api's LogQL selector (namespace + app pinned to the caller's App) then honestly finds nothing. The w6/m131 lesson applies twice: the fix must be asserted against a static `ServiceName`, and `logs-verify.sh`'s `default`-namespace fixture cannot be the only acceptance.

### Fix shape (shipper-side preferred)

- Option A (preferred): attribute by router/host instead of ServiceName for the static-server Service — the static host maps to exactly one App (the operator already resolves host→App for serving), so a bounded lookup (host allowlist is per-request data — keep `host` line-only per the cardinality budget; the App label is the attribution, not a new high-cardinality axis) labels the line with the tenant `{namespace, app}`.
- Option B: the static-server emits its own access records (stdout JSON → existing Alloy app pipeline as `type=request` with App labels). Heavier but precise; introduces a second request-log producer to keep in sync.
- Either way: no cross-tenant leakage (query pins namespace+app; a wrong label only hides), no new label cardinality (`path`/`host` stay out of labels per `TestPathAndHostNeverBecomeLabels`), and the platform-host allowlist discipline stays closed-vocabulary.
- This also lights up the host/path-filtered `http_requests`/`http_latency` read for static (`requestMetric`'s Loki branch, `metrics/service.go`), which needs no separate fix once the store has the lines.

### Acceptance

- `TestShipperRegex*`-style coverage extended with a static-server `ServiceName` (+ host) asserting attribution to the exact `{namespace, app}` bex-api queries by — the guard w3/m8 lacked, applied to the static shape.
- Live proof in t007: `type=request` returns the driven lines with method/status on a throwaway static site.

## Result, 2026-09-18 — Option A, on captured production ground truth

Neither option as sketched survived contact with the real access line, which
was captured rather than assumed (the w6/m131 lesson, applied):

```json
{"KubernetesIngressNamespace":"default","KubernetesIngressName":"hello-static",
 "ServiceName":"default-bex-static-hello-static-8080@kubernetes",
 "RequestHost":"hello-static.onbex.co","DownstreamStatus":200,"RequestMethod":"GET", …}
```

— production Traefik (`traefik/traefik-776c44f94f-l9bfd`), 2026-09-19, from a
live request to `https://hello-static.onbex.co/`.

**The filed root cause was close but wrong in a way that mattered.** Static
lines are not dropped as `not_a_tenant_app`: the ServiceName DOES match the
attribution regex (namespace `default`, and the `.+` app group happily claims
`bex-static-hello-static`). They ship — with an `app` label naming the
per-App ExternalName alias the operator creates (`staticServerAliasName` =
`"bex-static-" + appName`, `app_controller.go:3377`) rather than the App. So
bex-api's selector, which pins `app = app.Name`, finds nothing. Misattribution,
not a drop — same symptom, different fix.

**Option A as sketched (attribute by router/host) is not tractable.** The
router name is `[<entrypoint>-]<ns>-<ingress>-<host-with-dots-as-dashes>@kubernetes`
(e.g. `websecure-default-hello-static-hello-static-onbex-co@kubernetes`), and
both the App name and the host contain dashes, so splitting them apart needs a
backreference RE2 does not have. **Option B** (a second request-log producer
in the static-server) was rejected for the cost the task already names.

**What shipped instead** is smaller than either: Traefik already puts the
answer on the line. `KubernetesIngressName` **is** the App CR name — the
operator names each App's Ingress after the App — and that holds for compute
too, verified the same day on a second captured line
(`ServiceName: "tea-d98210cbbpdc73dcrkvg-tea-d98210cbbpdc73dcrkvg-eden-cms-v2-3000@kubernetes"`
alongside `KubernetesIngressName: "tea-d98210cbbpdc73dcrkvg-eden-cms-v2"` —
identical). So the pipeline extracts it and prefers it, with the ServiceName
regex as the fallback. It also survives the ≤63-char sha256 truncation
`platformAliasName` applies to a long alias name, which no ServiceName-parsing
fix could.

**Gated on the regex having matched** (`{{ if and .Value .ingress_name }}`):
a platform edge line (api.bex.co et al.) carries a `KubernetesIngressName`
too, and letting it set `app` would route it down the tenant branch of the
namespace/platform_service templates and lose the fixed platform pair the
w4/m88 + w5/053 allowlist exists to preserve. The regex misses those (their
namespace is neither `tea-<xid>` nor `default`), so the override cannot reach
them — pinned by `TestShipperIngressNameNeverAttributesAPlatformEdgeLine`.

**Coverage.** Both captured lines are pinned verbatim in
`internal/logs/shipper_attribution_test.go`, executed through the REAL config:
the ServiceName regex and the `app` stage.template are read out of
`deploy/gitops/base/log-shipper.yaml`, un-escaped (Helm tpl + River quoting)
and run as the Go templates Alloy runs. `TestShipperAttributesStaticSiteRequestLines`
carries the pre-fix control inline (the regex alone yields the `bex-static-`
name). `TestShipperComputeAttributionIsUnchanged` asserts the two sources agree
for compute, which is the property that makes the override safe to apply
unconditionally. `scripts/gitops-validate.sh` passes.

No new label cardinality (`ingress_name` is extracted, never labeled;
`stage.labels` is unchanged), and no cross-tenant exposure: the query pins
namespace AND app to the caller's own resolved values, so a wrong label can
only hide a line.
