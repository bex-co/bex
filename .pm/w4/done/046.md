## Root cause and concrete fix

- `dashboard/src/features/keyvalue/hooks/use-set-key-value-maxmemory-policy.ts:44` passes `policyQuery.data?.keyValue?.maxmemoryPolicy` through unchanged. API output intentionally uses underscores: `lego/backend/internal/keyvalue/service.go:190,251`, exposed by `graphql.go:48`.
- The component builds options from eight hyphen-spelled CRD policy values in `dashboard/src/features/keyvalue/lib/labels.ts:23–32`; `key-value-maxmemory-policy-section.tsx:28–40` supplies these to the shared `EditableFieldRow`.
- Consumer checked: `dashboard/src/features/services/components/editable-field-row.tsx:217–234` supplies the mismatched string as Select.value and leaves SelectValue children empty. Pinned `@radix-ui/react-select` **2.2.6** (`yarn.lock:3523–3525`) compares `context.value === value` (`node_modules/@radix-ui/react-select/dist/index.mjs:808`) and only portals the matching item's text (`:925`). `allkeys_lfu` matches no `allkeys-lfu` item; `noeviction` matches literally. This is not a loading or localization failure.
- Normalize the API read into the existing UI option vocabulary at this hook boundary (underscore → hyphen, preserving empty/unrecognized states appropriately), so the read-only display, edit draft, cancel/reset baseline and dirty comparison all use the same UI values. Keep REST/GraphQL/MCP wire spelling and the generic select unchanged; the backend already accepts hyphen input on save.
- **Blast radius:** exhaustive production hook search finds **one consumer**, `KeyValueMaxmemoryPolicySection`. Scope the fix there. Its eight policies comprise seven underscore/hyphen cases and the unchanged `noeviction` control. The shared `EditableFieldRow` does not need a global normalization rule. Other service types (web/static/cron/worker/private/Postgres) do not use this hook. Key Value list/create and programmatic setter paths must retain their existing contracts.
- **Tests:** the existing component test mocks the hook as `policy: "allkeys-lru"` (`components/__tests__/key-value-maxmemory-policy-section.test.tsx:7–22`), bypassing the real wire shape. Exercise the real hook with Apollo underscore fixtures, assert visible policy, correct selected option, no-op Save disabled, cancel restoration and saved/refetched value. Keep `noeviction` as a control. Do not make the generic select convert arbitrary strings.
- Pending and failed reads must not fabricate the recommended policy; preserve the loading state and do not turn forbidden/unauthenticated/not-found/timeout into a guessed saved value. Error UX beyond the vocabulary mismatch is unverified and outside this small fix.

## Resolution (2026-09-07)

Done. bex-api reads the eviction policy back with underscores (`allkeys_lfu`) while the dashboard's option vocabulary and CRD/save path use hyphens (`allkeys-lfu`), so the detail-page Select matched no option and rendered blank. Added a narrow `maxmemoryPolicyToUi` helper in `keyvalue/lib/labels.ts` that maps a known underscored policy onto its hyphen UI form (`noeviction` unchanged; empty and unrecognized values pass through untouched — never fabricating a policy), and applied it at the one hook boundary `use-set-key-value-maxmemory-policy.ts` so the read-only display, edit draft, cancel/reset baseline, and dirty check all read the same normalized value. Save is unchanged (already sends the hyphen UI value the backend accepts); REST/GraphQL/MCP wire spelling and the generic Select are untouched. Blast radius is the single consumer `KeyValueMaxmemoryPolicySection`. Tests: an exhaustive `maxmemoryPolicyToUi` unit table, plus a real-hook integration test (`.wire.test.tsx`, mocking only Apollo with the underscored value) asserting the selector shows `allkeys-lfu` instead of blank, that the normalized baseline disables no-op Save, and that an absent read stays blank rather than guessing. `yarn typecheck`/`yarn lint`/dashboard keyvalue tests green. Live re-probe of the deployed fix deferred to the next QA pass.
