# 562 — Suspending a sleeping Free service records no `service_suspended`, and its Resume is reported as "Service resumed" only when the next request wakes it, which can be days later

Why: the feed, the "Service resumed" push and the `service_resumed` webhook should mark the moment the owner acted. For a service that was already asleep, the suspension never appears, and the resume is stamped on whatever request next wakes the service. The real wake then has no event of its own.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 60, 2026-11-11 01:23–01:45 UTC (`muse.env`, workspace `bex-canary`, pin `a0d5802594e9`). **Minor**: lifecycle event type and time. The `suspender_*` events still show both user actions. ~40m.
- **Fixture:** Free image service `qa-20261110-sl60` (`srv-dbps71dhi5vc738gj0lg`, `traefik/whoami:v1.10.1`). Live at 01:24:31. Deleted afterwards (204, then 404).
- **Probe (REST from the page):**
  1. **It fell asleep.** With no traffic after 01:24:31, `service_hibernated` fired at 01:40:27, and the header read "Service Sleeping".
  2. **Suspend.** At 01:41:06, Settings → Suspend Service → Suspend in the dialog.
     - REST read `suspended: "suspended"`, `suspenders: ["user"]` and `/instances` `[]`. The header read "Service Suspended", and the URL answered 503 "This service is suspended."
     - Events gained only `suspender_added @01:41:07`. **No `service_suspended`.**
  3. **Resume.** At about 01:41:56, the Resume button, with no dialog.
     - REST read `not_suspended`, and the header read "Service Sleeping". The service stayed asleep.
     - Events gained `suspender_removed @01:41:57`, and nothing else.
  4. **Wake.** At 01:42:51, `curl https://qa-20261110-sl60.onbex.co/qa60` returned 200 after 12.09 s.
     - Events gained **`service_resumed @01:43:02`**, with details `{}`. There is no `service_woken`.
  5. **Dashboard Events tab, newest first:** "Service resumed · 1m", "Resumed by puncsky@gmail.com · 2m", "Suspended by puncsky@gmail.com · 3m", "Service went to sleep · 3m".
- **Root cause:** `lego/backend/internal/store/event_facts.go`.
  - **Suspending while asleep emits nothing.** `checkpointServiceSuspended` (`:554-566`) lets the recorded reason rise while the phase stays `Hibernated` (w4/508: "suspending an already-sleeping App … the wake edge consumes it"). But `observedStateFacts` (`:594-`) emits only on a phase edge, so the suspend writes the checkpoint and records nothing. `event_facts_test.go:164-173` pins that: "suspending an already-sleeping service makes its wake a resume", expecting **no** fact at the suspend.
  - **The resume is attributed to the wake.** The resume's flag fall is also not an edge while the phase stays `Hibernated`. The next `Hibernated → Running` edge (`:629-641`) turns the held reason into `service_resumed`, stamped at that wake's Ready transition.
  - **The design assumes Resume wakes the service at once.** It does not for an idle Free service: it stays `Hibernated` until a request arrives, and that request's wake is reported as the resume.
  - **The same fact feeds push and webhooks.** Push sends "Service resumed — <name> resumed." (`lego/backend/internal/notifications/push_worker.go:751-752`). Webhooks map it to `service_resumed` (`lego/backend/internal/webhooks/service.go:235`).
- **Fix (target behavior):**
  - **Suspending a sleeping service** records `service_suspended` at the pass that sees `spec.suspended` rise, with the phase already `Hibernated`. This is the action Render records ([w4/527](done/527.md): "Render records both actions however quickly they follow each other").
  - **Resuming a service that stays asleep** records `service_resumed` at the pass that sees the flag fall, and the checkpoint reason falls with it. The later request-driven wake then records `service_woken` (bex's extension, never pushed) or nothing.
  - **Resuming a service that wakes because of the resume** still records exactly one `service_resumed`, at its Ready time, and no extra `service_woken`. That keeps the guarantees of `event_facts_test.go`'s w4/508 race case and the transient-phase case (`:150-161`, `:175-185`).
    - One discriminator to tell the two apart: the activator's `app.bex.co/wake-started` stamp (`lego/operator/cmd/activator/main.go:57-62`, `:330`), present only on a request-driven wake. Whether the observation carries it today is unverified.
  - REST, GraphQL, MCP, webhooks and push all follow from the fact, so the fix is backend only.
