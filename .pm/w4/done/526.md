# 526 — Signed-in dashboard HTML (`/services`, `/settings`, …) is served with no `Cache-Control`

Why: the server-rendered pages carry the signed-in user's data, and nothing tells a browser or intermediary how to treat them. w4/522 made every bex-api answer `no-store`; the dashboard's own SSR responses are a separate process and were left for this follow-up.

- **Source:** split from w4/522 (loopx w4, 2026-11-06). Its probe saw `GET https://dashboard.bex.co/services` and `/settings` → 200 with no `Cache-Control`, `cf-cache-status: DYNAMIC`.
- **Open choice:** `no-store` vs `private, no-cache`. Chrome's back/forward cache treats `no-store` pages specially, so pick the value after checking bfcache behavior on the dashboard's navigations. `private, no-cache` still keeps shared caches out.
- **Where:** the dashboard SSR server (`dashboard/server/`, TanStack Start). Its header source has not been opened yet.
- **Tests:** a server test asserting the header on an authenticated page, and that static assets keep their own caching.
- **Estimate:** ~30m.

- **Closed 2026-11-06 (loopx w4):** chose `private, no-cache`: shared caches never keep a page, the browser revalidates every load, and the back/forward cache still works (`no-store` would interfere with it). The Nitro route rules moved into `server/security-headers.ts` (`buildRouteRules`). There, `/**` gets the security headers plus `Cache-Control: private, no-cache`; hashed `/assets/**` keep `public, max-age=31536000, immutable`; and the two `.well-known` association documents keep `public, max-age=300`. I checked a local production build (`vite build`, then `.output/server`): `/auth/login` → `private, no-cache`, an asset → `immutable`, `assetlinks.json` → `max-age=300`. The 307 auth redirect for `/` carries no `Cache-Control`; it has no body to protect. New tests in `server/__tests__/security-headers.test.ts`.
