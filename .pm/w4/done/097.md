# 097 — A private service gets no public URL and is not served at its slug host, verified against a web-service control

Why: "private service is not publicly reachable" is journey 10's security-shaped promise and had never been exercised; this records the evidence, the control that makes it mean something, and the one respect in which the test is weaker than it looks.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 45. A `qa-` private service was created and **deleted** (`srv-dak55hggsm7s73f64kqg`, verified gone by id; no `qa-`-named service remains in the workspace). Free plan, $0.00. **No defect found.**

## The API withholds the public URL, and the control proves that is deliberate

Same field set queried on the new private service and on an existing web service:

| field | `qa-20260914e-priv` (private) | `beancount-cms-v2` (web, control) |
| --- | --- | --- |
| `url` | **`""`** | `https://beancount-cms-v2.onbex.co` |
| `sshAddress` | **`""`** | `srv-d9bj8s3eg85c7390eb9g@ssh.bex.co` |
| `internalAddress` | `qa-20260914e-priv:3000` | `beancount-cms-v2:3000` |
| `dashboardUrl` | `…/pserv/srv-…` | `…/web/srv-…` |
| `type` | `private_service` | `web_service` |

The control matters: without it, an empty `url` could just mean "not assigned yet". ADR018 records that bex derives `serviceDetails.url` **at creation** for web services and static sites, so a web service having one immediately while the private service has none — both read seconds apart — is the distinction working as designed. `sshAddress` is withheld too.

## The slug host is not served

```text
https://qa-20260914e-priv.onbex.co/            → 404   (resolves to 49.12.20.236 via the *.onbex.co wildcard)
https://beancount-cms-v2.onbex.co/             → 200   (control: a real web service)
https://qa-definitely-no-such-service-xyz.onbex.co/ → 404   (control: the generic no-route answer)
```

The private service's host resolves only because `*.onbex.co` is a wildcard — every nonexistent name does — and the edge answers it exactly as it answers a name that was never created. Re-checked after a further 45 seconds: still 404.

## Where this test is weaker than it looks

**The service never reached Live.** `nginx:alpine` listens on 80 while bex's internal address advertises `:3000`, so the deploy stayed `In Progress`. That is **my own bad input**, not a defect — the web-service control shows `:3000` as well, so 3000 is the platform's internal-port convention (the `PORT` variable a PaaS image is expected to honour), and nginx does not honour it.

The consequence for this record: "not publicly reachable" is partly trivially true, because a service that never started could not have been served regardless. The parts that stand on their own are the **API's empty `url`/`sshAddress`** and the **control comparison**; the 404 is consistent with them but is not by itself proof that a *running* private service stays unexposed. A future pass should redo the edge check with an image that listens on 3000.

## Smaller observations

- **`/pserv/srv-…` redirects to `/services/srv-…/deploys`** — the Render-shaped alias the API hands out in `dashboardUrl` resolves to the canonical route. `location.pathname` was checked rather than assumed, per this hunt's own recorded trap.
- **The private-service create form has Project and Environment selectors** (Environment disabled until a Project is chosen). Worth contrasting with `w4/091`'s observation that the env-group create dialog has neither — so the absence there is a per-form gap, not a platform-wide pattern.
- **Deleting mid-deploy works**: `deleteService` returned true while the deploy was still `In Progress`, and the id was `not found` three seconds later.
- The type deep-link `?type=private_service` sets the radio, heading, description and document title together, matching what `w4/092` found for `?type=static_site`.

## Unverified

- **No port control exists on the create form or in Settings** for an image-backed private service. The `PORT` environment-variable convention is the presumed mechanism, but it was **not** tested — setting `PORT` and watching a redeploy reach Live was out of this pass's budget. Until someone does, whether a private service from an image listening on a non-3000 port can be made reachable is an open question, and it is the first thing to resolve if a user reports one that never goes healthy.
- **Internal reachability was never demonstrated.** That a private service *is* reachable from a sibling service inside the platform network — the other half of the promise — needs a second service to call it from, and was not attempted.
- **The Settings controls were all disabled** during the in-progress deploy (Service Name, Region, Health Check Path, Notifications). That looks like a deliberate lock, but whether they re-enable once a deploy settles was not observed.
- **The cron half of journey 10 was not covered** — schedule, manual run, and run logs remain unexercised, as do background workers.
