# 631 — A user-triggered cron run never names who triggered or canceled it: Render's `cronJobRun.triggeredBy`/`canceledBy` and `cron_job_run_ended.user` are absent, even in the trigger response, where the caller is known

Why: Render's cron run object names the user who triggered and the user who canceled a run, and its `cron_job_run_ended` event carries the user. On bex a manual run reads exactly like a scheduled one. A team cannot tell from the run list, the trigger response or the event which member started a run that, for example, re-ran a billing job. ADR038 omitted the fields because "Kubernetes Jobs do not retain the API caller identity". That reason predates w3/m366, which builds run history from durable facts. The caller is also in hand at the trigger call itself. ADR018 records no signed divergence.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 281, 2026-11-13 10:08–10:16 UTC (`muse.env`, workspace `bex-canary`; pin `5de3d5bcce8e`, the deploy carrying w3/m366). **Minor** (parity; no data loss). ~1h.
- **Fixture:** Starter cron job `qa-20261113-r281-cron` (`srv-dbre37pens8c73fghegg`), `docker.io/library/busybox:1.37`, schedule `0 0 1 1 *` (no scheduled run in the window). Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe (all 13 runs triggered by the QA user through `POST /v1/cron-jobs/{id}/runs`):**
  - The trigger response was `200 {"id":"crr-opn9gckd7fhft3p165k9","status":"pending"}`, with no `triggeredBy`. The same shape came back for all 13.
  - `GET /v1/cron-jobs/srv-dbre37pens8c73fghegg/runs?limit=100` listed all 13 (w3/m366 works, see below), each with only `{id, status, startedAt, finishedAt}`, for example:

    ```
    {"cronJobRun":{"id":"crr-8n3lme5q0dqhdqkai5k3","status":"successful","startedAt":"2026-11-13T10:14:18Z","finishedAt":"2026-11-13T10:14:23Z"},"cursor":"crr-8n3lme5q0dqhdqkai5k3"}
    ```

  - `GET …/runs/crr-tus0bg302bdc7bbjn070`, the failing run (`exit 3`), gave `{"id":…,"status":"unsuccessful","startedAt":"2026-11-13T10:15:35Z","finishedAt":"2026-11-13T10:15:40Z"}`.
  - Round 277 (pin `4c3c68e6b05b`) saw the same for events. Its `cron_job_run_ended` details were `{"status":"canceled","cronJobRunId":"crr-nm2mmuc2evtqo51ou09v"}`, with no `user`, for a run canceled by the user's own manual trigger and by `DELETE /v1/cron-jobs/{id}/runs`.
- **Render** (pinned OpenAPI `lego/backend/internal/api/openapi/render-public-api-1.json`):
  - `cronJobRun` has `triggeredBy` ("user who triggered the cron job run") and `canceledBy` ("user who canceled the cron job run"), both strings.
  - The event schema "Cron Job Run Ended" has `user: {id, email}` ("User who triggered the action").
- **Root cause:**
  - `renderCronJobRun` (`lego/backend/internal/apps/render.go:812-828`) declares `TriggeredBy`/`CanceledBy`, but `toRenderCronJobRun` never fills them, and `CronRunView` (`apps/service.go:428-438`) has no actor field.
  - GraphQL `CronRun` (`apps/graphql.go:643-654`) has no actor field either.
  - `TriggerCronRun` (`apps/service.go:4270-4300`) has the caller in `ctx` and the run's id (`ids.Derive(ids.CronRun, jobName)`) before it returns, but it records neither in the App spec nor in a run fact.
  - The cancel paths (`CancelCronRun`, `:4406`, and the trigger's own preemption at `:4292-4294`, `CronRunCancellation`) drop the actor the same way.
  - `cron_job_run_ended`'s REST details (`lego/backend/internal/events/rest.go:397-402`) set no `User`.
  - `docs/ADR038-cron-jobs.md:104` and `:112` record the omission with the pre-m366 reason.
- **Fix (target behavior):** a run started by a user carries that user everywhere Render shows one. A scheduled run carries none.
  - **Trigger response and run reads.** `triggeredBy` = the triggering user, in the same form as Render's string. Decide the form (email or `usr-` id) from Render's API before implementing.
  - **`canceledBy`.** The user who canceled: through `DELETE …/runs`, per-run cancel, or the manual trigger that preempted the run.
  - **Event.** `cron_job_run_ended.user` = `{id, email}`, as Render's member carries, on REST, MCP and GraphQL.
  - **Durable source.** Record the actor at the request:
    - `TriggerCronRun` puts the caller on the run's intent (`spec.runRequestedBy`, or a store row keyed by the derived `crr-` id);
    - the cancel paths put it on `CronRunCancellation`;
    - the operator copies both onto the Job as annotations, which survive into the run facts w3/m366 reads.
  - **Surfaces.** REST, MCP (`trigger_cron_job`, run reads) and GraphQL `CronRun` add the fields together. Webhook payloads are unchanged (Render's are thin).
  - **ADR.** Rewrite ADR038's row and its "Actor fields are omitted" bullet.
- **Blast radius:**
  - Every cron run read: REST list, get and trigger responses; MCP; GraphQL `CronRun` (both the `Service.runs` field at `:415` and the first-class list at `:1300`); the dashboard Runs page (w2/m360), which may show the actor.
  - Older runs and runs whose Job predates the change stay actor-less, which is honest.
  - Scheduled runs must not gain an actor.
- **Unverified:**
  - Render's exact `triggeredBy` string form.
  - Whether Render fills `canceledBy` when a manual trigger preempts a run.
  - Whether its `cron_job_run_ended.user` names the trigger or the canceler.
  - The dashboard Runs page was not opened (the browser was held by another session).

- **Dedupe:**
  - `grep -rln "triggeredBy\|canceledBy" .pm` finds only service-deploy and restart actor items: w4/391 (`suspendedByUser`/`resumedByUser`/`trigger.user`, done), w4/379 and w4/602. None covers cron runs.
  - w3/m366 (blocked on its closeout) and w2/m360 do not mention the actor.
  - Not deploy lag: `git log 5de3d5bcce8e..origin/main -- lego/backend/internal/apps/render.go lego/backend/internal/events/rest.go` shows only `31b6d1682` (w10/m373, schema both ways). It leaves `renderCronJobRun` and the `cron_job_run_ended` details as they are.
- **DoD (live):**
  - On a cron job triggered by the QA user, the trigger response and `GET …/runs/{id}` carry `triggeredBy` naming the QA user.
  - A run the user cancels with `DELETE …/runs` reads `canceledBy` = the QA user.
  - That run's `cron_job_run_ended` carries `user: {id, email}` on REST `GET /v1/events/{id}`.
  - A scheduled run carries none of the three.
  - Delete the fixture (`GET` 404).

- **Closed 2026-11-14 (/loopx w4):** bex-api now records who triggered and who canceled each cron run in a new `cron_run_actors` table (migration 0259, keyed by app + derived `crr-` id, cascades with the app). `TriggerCronRun` writes the caller before patching the intent (a failed write refuses the trigger), and `CancelCronRun`, `CancelCurrentCronRun` and the trigger's preemption of the active run write the canceler. Run reads resolve the subjects to emails: `triggeredBy`/`canceledBy` on the trigger response, list, get and cancel over REST and MCP, and GraphQL `CronRun` (`cronJobRuns`, `cronJobRun`, `service(id).runs`). `cron_job_run_ended` carries Render's `user: {id, email}` on REST, MCP and GraphQL (feed and by-id queries join the actors). The dashboard run detail shows Triggered by / Canceled by (en + zh). Account deletion anonymizes both columns (ADR086). No operator or CRD change. Decisions (recorded in ADR038 § Run actors, all unverified against Render because its OpenAPI gives no example): the string form is the email; a preempting manual trigger fills the replaced run's `canceledBy` with its caller; `canceledBy` shows only on a run that ended canceled; the event names the canceler of a canceled run, else the trigger. Scheduled runs and pre-change runs stay actor-less. Webhooks unchanged. Tests: `apps/cron_run_actors_test.go` (REST trigger/list/get/cancel and `DELETE …/runs`, GraphQL, MCP, store failures), `events` user projection + Render member validation, `store/cron_run_actors_pg_test.go` against real Postgres, dashboard run-detail and trigger-hook tests; backend suite with deps, dashboard `yarn lint` + `yarn test` pass. Live DoD replays after the next production deploy.
