# 419 — Environment group, project and environment names accept control characters and unbounded length

Why: every other resource's name follows `core.CheckLabel` (no control characters or line separators, at most 100 code points; w8/034 closed this for service renames), but an environment group, a project or an environment can be named `"line1\nline2"`, `"bell\aend"` or a 5,000-character string. These names then render in the dashboard, the CLI, Blueprints (`fromGroup:`) and every list.

**Severity:** minor (input hygiene; such names break list layouts and `fromGroup` references and can mislead in a table). **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run 758c, 2026-10-26 UTC (`muse.env`, `bex-canary`, pin `b4726243e74f`), REST through the run's session jar. All nine owned groups were deleted (`DELETE` 204, `GET` 404).

## Probes

`POST https://api.bex.co/v1/env-groups {"name":<N>,"ownerId":"tea-daif693dqjvc73e7as3g","envVars":[{"key":"A","value":"1"}]}`:

| `name` | Answer | Stored name (list read) |
| --- | --- | --- |
| `""`, `" "` | `400` "env group name is required" | — |
| `" pad "` | `201` | `pad` (trimmed) |
| `"line1\nline2"` | `201` | `line1\nline2` |
| `"tab\tsep"` | `201` | `tab\tsep` |
| `"bell\u0007end"` | `201` | `bell\x07end` |
| `"g"×101` | `201` | 101 code points |
| `"z"×5000` | `201` | 5,000 code points |

Control: a service create or rename with the same names is refused by `core.CheckLabel` (`DISPLAY_NAME_CONTROL_CHARACTER` / `DISPLAY_NAME_TOO_LONG`, `core/errors.go:368-380`). The response JSON itself is correctly escaped.

## Same gap on projects and environments (run d11a, same day and pin)

`POST /v1/projects {"name":<N>,"ownerId":…}` → `201` for `"line1\nline2"`, `"bell\aend"`, `"p"×101` and `" pad "` (stored trimmed); `""` → `400`. `POST /v1/environments {"name":<N>,"projectId":…}` → `201` for `"env\ntwo"`, `"bell\aenv"`, `"e"×101` and `"e"×5000` (read back as `'env\ntwo'`, `'bell\x07env'`). A third environment in one project is refused by the Hobby cap, which is not a length rule. All four owned projects and their environments were deleted (`GET` → 404).

## Root cause

These name writers (three for env groups, four for projects and environments) check only `strings.TrimSpace` + non-empty, never `core.CheckLabel`:

- create, `lego/backend/internal/envgroups/service.go:423-426`
- rename, `:752-756`
- Blueprint `envVarGroups` apply, `:1404-1408`
- project create, `lego/backend/internal/projects/service.go:423` (and the REST pre-check, `projects/rest.go:174`)
- inline environment names on project create, `projects/service.go:434`
- project rename, `projects/service.go:551` (REST `projects/rest.go:199`)
- environment create/rename, `lego/backend/internal/environments/service.go:1396`

## Fix (target behavior)

- Run `core.CheckLabel` in every writer listed above, after the existing trim and required-name check: refuse control characters and line separators with `DISPLAY_NAME_CONTROL_CHARACTER`, and names over 100 code points with `DISPLAY_NAME_TOO_LONG`.
- REST, GraphQL (`createEnvGroup` / rename), MCP and Blueprint validate/apply all go through these, so they move together. Blueprint validate should report the refusal at `envVarGroups[N].name`.
- Existing groups with such names: inventory them (production likely has none outside QA) and decide rename vs grandfather; reads must not break.
