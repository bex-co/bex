## Objective

`ChangeRole` commits the Postgres row before the OpenFGA tuple writes. When the **revoke** fails, every retry lands in the `m.Role == role` branch, which repaired only the grant — so the stale, possibly higher, role tuple survived forever.

## Context

- `lego/backend/internal/members/service.go` — the `m.Role == role` branch called `grantRole`. Its comment reasoned about "a missing grant", which is the wrong half: the row is already updated, so the only thing a retry can still be missing is the **revoke**.
- `deploy/gitops/authz/model.fga:61-75` — the model ORs the five role relations, so a surviving `admin` tuple keeps admin effective regardless of the `viewer` tuple next to it.
- `reconcileExactRole` (same file) already does exactly the right thing and was already used by invite redemption for the identical "caller doesn't know the prior role" situation.

## Acceptance criteria

- [x] The same-role branch calls `reconcileExactRole`.
- [x] The authz-off path stays a bare idempotent grant (unchanged behavior — a missing tuple can't be told from a present one without a checker).

## Resolution (2026-08-09)

Swapped `grantRole` → `reconcileExactRole` inside the existing `s.Base != nil && s.Base.Authz != nil` guard, which preserves the authz-off no-op exactly (`reconcileExactRole` returns after the grant when there is no checker). Rewrote the comment to name the real failure mode. Backend suite green.

Not done here, deliberately: the report's stronger recommendation — a durable outbox/reconciler that continuously makes OpenFGA match Postgres — is a real design item, not a one-line fix. Filed as part of `w4/029.md`.
