# 652 — A Rollback or a deploy with an image override still cancels the deploy in progress, and a Rollback, Restart or image-override deploy in progress is still canceled by the next trigger, where Render's Wait lets the deploy in progress finish

Why: under Render's default Overlapping Deploy Policy, **Wait**, "Only one deploy can run at a time per service" and the in-progress deploy finishes before "the most recently triggered deploy" runs ([render.com/docs/deploys](https://render.com/docs/deploys)). Render documents a rollback as "a _new_ deploy using the target deploy's build artifact" ([render.com/docs/rollbacks](https://render.com/docs/rollbacks)) and a restart as "a special form of manual deploy", so both wait like any other deploy. w4/635 made a saved-image release wait like a source build, and w5/m284 made a Restart wait at the row level. A release that `spec.releaseConfig` selects is still outside both.

- **Source / severity / estimate:** `/loopx w4` closeout of w4/635 (2026-11-14), recorded as open in ADR018's List / get deploy objects row. **Minor** (the final state is the newest request, as under Override). ~3h; promote to a milestone if the deferral needs a worker.
- **Gap, from the code:**
  - The operator never pins a selected release: `releaseInFlight` returns false when `status.selectedReleaseGeneration` is the release in flight, and `pinnableRelease` is false while `ActiveReleaseConfig()` is set (`lego/operator/internal/controller/release_identity.go`). A pinned selected release cannot render its own selection yet: the newer trigger clears `spec.releaseConfig`, and `heldReleaseView` returns nil while the saved spec selects.
  - `Rollback` (`lego/backend/internal/deploys/service.go`, `openSelectedRelease`) and an image-override `Trigger` write the selection to the CR at once, so the operator adopts them over the deploy in progress, and the reconciler closes its row `canceled` ("Superseded by …").
  - The deploy hook answers an `imgURL` call that lands behind a deploy in progress with Render's `202` (w4/635), but the operator then replaces the deploy in progress instead of running the call after it.
- **Fix (target):** defer a selection made while a deploy is in flight at the row level, as `CreateDeferredRestart`/`DeferredRestartWorker` (`deploys/restart_wait.go`) do for Restart: a `queued` row carrying its selection, written to the CR only once nothing is in flight; a newer trigger replaces it in the pending slot. Then a release a selection opened is the one in flight only when nothing waits, and the operator's pin rules need no selected case.
- **Tests:** a Rollback, and an `imageUrl` deploy, behind an image deploy rolling out leave it to go `live`, then run; the hook's `imgURL` 202 run order matches; a Restart still waits; two selections in a row leave one pending.
- **DoD (live):** on a Free busybox service, trigger A, then while A reads `update_in_progress` roll back to an earlier deploy: A goes `live`, then the rollback runs. Repeat with `imgURL` on the hook (answer `202`). Delete the fixture.
- **Closed 2026-11-14 (/loopx w4):** Premise held (`Rollback`/`openSelectedRelease` and an `imageUrl` `Trigger` wrote their selection to the CR at once, and the operator never pins a selected release). bex-api now holds a selected deploy at the row level, generalizing w5/m284's deferred Restart into a deferred deploy: a Rollback or an `imageUrl`/`imgURL` deploy behind a deploy in flight answers a `queued` row (the hook's bare `202`) with no release and no App change, carrying its request in `deploys.deferred_request` (migration 0264; `restart_deferred` now marks every waiting row), and `DeferredDeployWorker` runs it as that same row once nothing is in flight (`rollbackFetched`/`triggerFetched` under `store.WithDeferredDeploy`, promoting the row in place, `resolved_image` set for a rollback). A deploy bex-api opens (Manual Deploy, API, hook, "Save, rebuild, and deploy") behind a selected release in flight waits the same way; a newer trigger replaces a waiting row (`Superseded by dep-…`, or `Canceled by restart` for a Restart), Cancel closes it, and a wait past 3h closes it with the new `deploy_wait_timed_out` reason (en/zh dashboard wording). Decision: the operator pin for a selected release is not taken here; a git push, a rolling configuration save, a Blueprint sync and a build-source fan-out still replace a selected release in progress — recorded open in ADR018 and filed as w4/661. ADR018's List / get deploy objects and Rollback rows amended; operator comments updated. Backend `go test ./...` passes; `store`, `deploys`, `api` pass against real Postgres + OpenFGA; operator `make test` passes. Live DoD replays after the next production deploy.
