# After saving a new port on a web image service, Settings → Port shows the old port until the deploy is live

Why: Render's Port setting shows the value you just saved. On a web image service in `web-image-configured-v1`, `setPort` answers with the serving network's primary port. That's `App.ServicePort()`, which by w4/m243 t007 publishes a new port only after promotion. So the mutation result writes the **old** port into the Apollo cache, and the field snaps back from the typed value to the old one. It catches up only when the `config_change` deploy goes live (about 30 s for BusyBox, minutes for a slow image). A user who saves 3000 sees 3001 and reasonably concludes the save failed.

Severity: minor (misleading read during every port edit on an image web service; routing is correct). Estimate: ~45m. Source: loopx w4 m182 replay, 2026-10-29 UTC (`bex-canary`, pin `55d99e66808d`, fixture `qa-20261029-lx01-m182`).

## Evidence

- `setPort(id, 3001)` on the service serving 10000 returned `{"port":10000}`. `service { port }` read 3001 only after `dep-dbhdqb6krqkc73bailo0` went live.
- Dashboard, 3001 → 3000: Edit Port → 3000 → Save changes at 05:48:18Z. Field values sampled every 2 s from 05:48:23Z to 05:48:33Z were all `3001`. After the deploy went live (05:48:49Z) the field showed `3000`, and a reload agreed.
- Dashboard, 3000 → 3001 hard-load: the `SetPort` response body was `{"setPort":{"__typename":"Service","id":"srv-dbhc4scu5jqc738unhj0","port":3000}}`.

## Direction

Report the saved value to the Settings row without moving the published `port`/`internalAddress` before promotion (m243 t007 keeps those equal to what serves). For example, expose the desired port (`spec.port`) as its own read for the Settings row, or have the row keep the saved value while a `config_change` deploy is in flight. Check Render's API for whether `serviceDetails.port`-style reads report the saved or the serving value before choosing.
