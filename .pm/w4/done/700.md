# 700 — The Events tab's count badge reads 20 when the service's 30-day window holds 261 events, and grows by 20 with each "Load older events"

Why: w6/m122 t001 kept the badge beside the Activity title to answer "how much happened" in the window. The code comment and the route test say the same. But the page reads 20 rows at a time, and the badge counts the rows loaded so far, `events.length`. A quiet service reads its true total. A busy one reads 20, then 40, then 60 as the user pages, while the 720-hour window the page asks for holds more. The badge's aria label, "20 recent events", gives a screen-reader user the same wrong number.

- **Source / severity / estimate:** live `/qa-find-bugs w4` round 602, 2026-11-17 07:12–07:25 UTC, pin `21762a1df1fb`, workspace `bex-canary`. Read-only on the canary `hello-go` (`srv-dbkq3hdhhjfs73eiahe0`). **Minor:** a misleading count, the list itself is right. ~30m.
- **Probe:**
  - REST: `GET /v1/services/srv-dbkq3hdhhjfs73eiahe0/events?limit=100&startTime=<now-29d>`, following each page's `cursor` until `200 []`, returns **261** events (2026-11-03T08:56:37Z … 2026-11-16T14:30:26Z): 121 `service_woken`, 121 `service_hibernated`, 5 `deploy_started`, 5 `deploy_ended`, 4 `build_started`, 4 `build_ended`, 1 `server_restarted`.
  - Dashboard (headless Chromium at 1440, en): `/services/srv-dbkq3hdhhjfs73eiahe0/events` shows `Activity` with the badge `20` (aria label `20 recent events`) and a `Load older events` button.
  - Clicking `Load older events` turns the badge into `40 recent events`, and clicking it again into `60 recent events`. The page made no 4xx/5xx request and logged no console error.
  - zh shows the same `20` on load.
- **Cause:**
  - `dashboard/src/routes/services.$serviceId.events.tsx:195-206` renders `events.length` as the badge. The comment on line 195 says it "Counts what the API returned for the window", but `useServiceEvents` (`limit: 20`, line 150) only holds the pages read so far, and `hasMore` (line 148) says when more exist.
  - The route test "counts the window's own feed, not the post-filter subset" (`dashboard/src/routes/__tests__/services.$serviceId.events.test.tsx:1101`) mocks a feed of 3 with no further page, so it never sees a paged window.
- **Fix:**
  - Target behavior: the badge never states a total it has not read. While `hasMore` is true it reads `{count}+` with the aria label "At least {count} recent events". Once the window's history end is reached (`hasMore` false, the "You've reached the beginning of this service's history." line), it reads the exact count as today. Filtering still leaves it unchanged (w6/m122).
  - Add the "at least" plural forms in all 8 locales that carry `services.eventsCount_*`: `en`, `de`, `es`, `ja`, `ko`, `pt`, `ru` and `zh`.
  - Tests: a paged feed (`hasMore: true`, 20 rows) reads `20+` and its aria label; after `loadMore` resolves to the end it reads the exact total; the existing filter test keeps passing.
- **Blast radius:** one render site. `ServiceEventsPage` is shared by `/services/$serviceId/events` (web, private, worker, cron) and `/static/$serviceId/events` (`static.$serviceId.events.tsx` imports it), so the fix moves both. `services.eventsCount` is used nowhere else (`grep -rn "services.eventsCount" dashboard/src` → this route and the 8 locale files; tests aside).
- **Unverified:** a static site's Events tab live (the shared component is the only renderer, but no static site was opened); the ja badge; Postgres and Key Value pages having no count badge, which was checked only by grep.
- **Render:** `docs/render-artifacts/service-events.md` captures no count on Render's Events page (not re-checked live). This note keeps w6/m122's badge and makes the number true. It does not reopen whether bex shows a count at all.
- **Done when:** on production, the canary `hello-go`'s Events tab reads `20+` (aria label `At least 20 recent events`) on load and `40+` after one `Load older events`. A service whose whole window fits in one page reads its exact count, with no `+`.

## Outcome (w4/700 loopx worker, 2026-11-17)

- **Shipped:** `dashboard/src/routes/services.$serviceId.events.tsx` reads `hasMore` beside `events.length`. While older events remain, the badge reads `{count}+` and is labelled `services.eventsCountAtLeast` ("At least {count} recent events"). Once the history end is reached (`hasMore` false, the "You've reached the beginning of this service's history." line), it reads the exact count with `services.eventsCount`, as before. Filtering still leaves it unchanged. `services.eventsCountAtLeast_*` is added in each of the 8 locales in that locale's own plural forms (zh `最近至少 {count} 条事件`, ja `最近のイベント {count} 件以上`, ko `최근 이벤트 {count}개 이상`). The static Events route shares the component, so it changes too.
- **Tests:** a new block in `services.$serviceId.events.test.tsx` (w4/700) pages a real `useServiceEvents` over a mocked `fetchMore`. A full first page of 20 reads `20+` with the label "At least 20 recent events", and hiding every row keeps it at `20+`. After "Load older events" returns a short last page, the badge reads `25` ("25 recent events") and the history-end line shows. zh reads `最近至少 20 条事件`. With the route fix reverted, both new tests fail. The existing w6/m122 filter test now also asserts its window's exact `3` by label. Two of that block's assertions queried a filter-empty title the page no longer has ("No events match this filter"). They now query the current "No matching events".
- **Nuance:** `hasMore` is also true when the window is read but the service is older than 30 days, because "Load older events" then opens the previous window. Such a service reads `N+` even when its 30-day window fits in one page. That is true, and it matches the button beneath. The DoD's exact-count half needs a service created within 30 days that has fewer than 20 events.
- **Gate (clears by itself):** once production pins the commit that ships this, replay the DoD on `bex-canary`. The canary `hello-go` (`srv-dbkq3hdhhjfs73eiahe0`) Events tab reads `20+` (label `At least 20 recent events`) on load and `40+` after one "Load older events". A service under 30 days old with fewer than 20 events reads its exact count, with no `+`.
