# 643 — A suspended service's page offers no way to resume it: the header still shows Manual Deploy with both items disabled ("Resume it first"), and Resume exists only near the bottom of Settings

Why: a suspended service's Deploys, Events and Logs pages all read "Suspended". The one action button in the header, Manual Deploy, opens a menu whose items are disabled, and the tooltip says "Unavailable while the service is suspended. Resume it first." Nothing on that page resumes it. The owner has to know to open Settings and scroll to the danger-zone card. w4/m183 already routes the Shell page's Connect menu to `settings#suspend` for the same reason.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 327, 2026-11-13 21:36–21:46 UTC (`muse.env`, workspace `bex-canary`; pin `1c4d721bc8dc`; dashboard driven from an isolated headless Chromium). **Minor** (a discoverability gap; Resume works where it is). ~30m.
- **Fixture:** Free web service `qa-20261113-r327-ops` (`srv-dbro5vtgh3vs73b152bg`, `docker.io/library/busybox:1.37`, serving its hostname). Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe (UI):**
  - Manual Deploy → Restart service → the confirm "…restarts on the commit or image it is running now…" → Restart. Toast "Restart started on the running release." The host then served a new pod name, and Events recorded `server_restarted` with `triggeredByUser`. This part passes.
  - Settings → Suspend → "The service scales to zero… you can resume it at any time" → Suspend. Toast "Suspending qa-20261113-r327-ops…". The header read "Service Suspended", and the host answered `503 This service is suspended.` This part passes too.
  - Then, on `/services/{id}`, `/deploys` and `/events`:
    - no control on the page is named Resume or Suspend;
    - Manual Deploy opens "Deploy latest image" and "Restart service", both `aria-disabled`;
    - hovering shows the tooltip "Unavailable while the service is suspended. Resume it first." (`.playwright-mcp/qa-r327-suspended-menu.png`).
  - Only `/settings` has the "Resume Service" button. It worked: toast "Resuming…", and the host served 200 again within 10 s.
- **Root cause:**
  - The header renders only Connect and Manual Deploy for every state (`dashboard/src/features/services/components/service-detail-header.tsx:91`, `:180-182`).
  - Manual Deploy's items take `permissionReason` from the deploy-action gate (`manual-deploy-button.tsx:96-118`, `:203-246`), whose suspended reason is `capabilities` en `:56` ("…Resume it first.").
  - Resume lives only in `SuspendServiceCard` (`suspend-service-card.tsx:53`), mounted by `routes/services.$serviceId.settings.tsx:407`.
- **Fix (target behavior):**
  - While a service is suspended, its header offers **Resume Service** as the primary action, in place of Manual Deploy or beside it.
  - It calls the same verb and confirm as the Settings card, gated by the same `resume` action decision, so a caller without `can_operate` sees the same disabled reason.
  - The disabled Manual Deploy reason names where to resume, or points at the header button.
  - Static sites and cron jobs share `ServiceDetailLayout`, so they get the same header action.
- **Blast radius:**
  - `ServiceDetailHeader` serves every service type (`/services` and `/static`).
  - Reuse `useSuspendResume` (or whatever `SuspendServiceCard` calls) rather than a second mutation path.
  - Tests: a suspended fixture renders Resume in the header, and a running one does not.
- **Render:** Render's dashboard shows Resume on a suspended service's page. Its exact placement was not captured here; verify before matching copy.
- **Dedupe:**
  - w4/m183 (done) fixed the Shell page's Connect → Resume path only.
  - w4/547 (done) fixed the header's Instances count.
  - w4/203 (done) fixed cron Trigger Run while suspended.
  - `grep -rln "Resume it first" .pm` finds no item about a Resume control on the service page.
  - Not deploy lag: `git log 1c4d721bc8dc..origin/main -- dashboard/src/features/services/components/manual-deploy-button.tsx dashboard/src/features/services/components/service-detail-layout.tsx` is empty.
- **DoD (live):**
  - Suspend a fresh `qa-` Free service from Settings. Its Deploys page header shows an enabled Resume Service, and clicking it resumes the service (the host serves 200 again).
  - On a running service, the header shows no Resume.
  - Delete the fixture (`GET` 404).

- **Closed 2026-11-14 (`/loopx w4`):** A suspended service's header now offers Resume (`ResumeServiceButton`, new) beside Manual Deploy on every service page, including static sites and cron jobs through `ServiceDetailLayout`. It is the same `resume` action decision, pre-dispatch recheck, protected-phrase retry and `useServiceLifecycle` verb the Settings card uses; the card now renders the same component, so there is one Resume path. A running service shows none. The disabled Manual Deploy reason ("Resume it first.") is unchanged now that Resume sits next to it. Tests: `service-detail-header.test.tsx` (suspended → Resume resumes; running → none). Live DoD replays after the next production deploy.
