## Triage (loopx w4, 2026-11-05)

Read from code; no production data was available to this session.

- **Coverage arithmetic is not wrong.** `store/usage.go` `evaluateStreamCoverage` stops a stream's watermark at the first expected hour with no healthy health row, and `aggregateUsageCoverage` takes the minimum over active streams. One unrecorded hour early in the month therefore pins `through` there until the month rolls over, by design ("undercount, never invent").
- **Hours are not retried after 48 h.** `usage/service.go` `catchupLimit` is 48 h, and catch-up fills gaps after a meter's latest recorded window, so an hour that was skipped while later hours succeeded is not re-metered (the w4/442 note says the same for October).
- **Most likely cause:** the three workspaces' pinned hours (`2026-11-01T00:00Z`, `T02:00Z`) fall before the w4/442 fix (`5c1607804`) reached production. Until then `egressquery.Health` gated `direct` fleet-wide and degraded 40–55% of hours, so early-November hours were skipped for every app. The same note recorded that already-degraded hours stay degraded. This fits the observation that `through` does not move after later deploys. It does not explain why `http`, `instance`, `postgres` and `websocket` are also degraded in those hours; that needs the per-stream health rows.
- **Nothing to fix in code until the data is read.** The two questions the note asks (missing hours per source per workspace; whether usage rows or Stripe meter events are short) need a read-only production DB session: `psql "$DATABASE_URL" -v ws=<tea-…> -f scripts/usage-coverage-diagnose.sql` for the three workspaces.
- **Decision for the user after that read:** (1) re-meter the degraded November hours that Prometheus still retains (a one-off repair that writes `usage_hourly` rows for past hours, so it changes billable usage and needs approval), or (2) accept `partial` through 2026-11-30 and rely on the 442 fix keeping later months complete.

## Production read and fix (w6 session, 2026-11-11; user: "use the .env credentials and handle it yourself")

Read-only on the `bex-system/bex-db` standby (`bex-db-1`, `BEGIN READ ONLY`), with the operator's production kubeconfig; nothing printed.

- **What pins `through`:** `usage_source_health` for November held 1014 `instance` hours, 221 `direct`, 81 `postgres`, 64 `http`, 60 `websocket` and 3 `key_value` hours in state `degraded`, still accruing. `evaluateStreamCoverage` stopped every stream's watermark at its first non-healthy hour, so one degraded hour on November 1 showed "complete only through 2026-11-01" all month, although `usage_hourly` holds a row for every later hour (the diagnose script's `usage_hours` equals `expected_hours` less the current one).
- **Cause 1, false (`instance`):** 988 of the 1014 hours belong to four Apps whose first release ended Failed or Canceled — `nginxtyey`, `nginxhdjdjs`, `base-notebook2` (workspace `tea-db9f0dkfcf2c73c2mq4g`) and `market-size` (`tea-da1eg9gbiuuc73bd8uag`): no `ActiveRevision`, Deployments at zero, no pods. `expectsRunningPods` saw `spec.replicas > 0` and marked their honest zero degraded every hour. One more hour was w6's deliberately failing build probe (`srv-dbpp3ithi5vc738girig`). The remaining instance hours are Apps that did serve (`hello-go`, `klivzo`, `metrics-loki*`): genuinely suspicious zeros, left as they are.
- **Cause 2, real (egress):** `direct` (about a dozen hours a day), `postgres` (2–4 resources a day), and `http`/`websocket` on November 2 and 5 failed the per-source scrape-health gate and were skipped for that hour: an undercount, customer-favorable.
- **Decision (made here under the user's delegation):** do not re-meter the skipped egress hours. The health gate failed because the counters in those windows cannot be trusted; re-reading Prometheus reads the same samples, so a re-meter would invent usage (ADR023: undercount, never invent). Fix the false degradation and the watermark instead.
- **Shipped `7fea1980d`:** `expectsRunningPods` exempts an App whose first release ended Failed/Canceled without serving (a first rollout in progress is still checked); the watermark passes over degraded hours (metered) and stops only at missing/unavailable ones, and an ended stream metered to its end no longer drags `through`; Billing and mobile read "Metered through {date}"; `scripts/usage-coverage-diagnose.sql` mirrors it (fixtures `srv-degmid`, `srv-unavail` verified against a migrated local database); ADR023 amended.

**Deployed and corrected (2026-11-11).** `7fea1980d` went live with the 14:49 UTC deploy of `f609163ad`. On the primary (`bex-db-2`), one transaction set the five Apps' November `instance` rows from `degraded` to `healthy`, asserting the count first: 1,017 rows (254 hours × 4 Apps, plus the probe's one). No billing row changed. Re-read: the four Apps' workspace (`tea-db9f0dkfcf2c73c2mq4g`) now reads metered through the latest closed hour with nothing behind; `bex` moved from `2026-11-01T00Z` to `2026-11-08T13Z`, still partial for real egress skips.

**What still held `through` back, and the follow-up fix.** The diagnose script showed two more kinds of hole, both permanent. A deleted App's last egress hours are never metered (the deleted-resource pass meters only instance and build seconds), and a disk stream lost one rollup hour on 2026-11-08 13:00. bex-canary, where the QA loop deletes services daily, was pinned at `2026-11-01T02Z` by the first kind. The rollup can no longer write an hour older than its 48 h catch-up window, so such a hole is treated as skipped (the follow-up `fix(usage)` commit below; live with the deploy after it): `through` passes it and the source reads degraded (`store.UsageCatchupWindow`, plus the disk meter's one extra hour; boundary tests; the diagnose script mirrors it). A hole younger than that still stops `through`, because the rollup may still fill it.

**Filed:** `w4/575`, a disk deleted from a live service leaves its stream open, which the settled rule would now report as `disk` degraded.
