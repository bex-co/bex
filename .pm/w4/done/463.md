# 463 — Dialogs whose content has an `autoFocus` child still drop keyboard focus to the page body on close, so w4/459's shared fix misses them

Why: w4/459 is marked done, and its replay on production shows New Project, New Environment Group, New Environment and Invite all return focus. The dialogs that autofocus their first field do not, so a keyboard user who opens Add Custom Domain or Import from .env and presses Escape lands on `body` and restarts from the skip link. Verified live on Add Custom Domain and the .env import dialog; the secret-file contents dialog is from source.

Source: live `/qa-find-bugs w4` loop run, round 23, 2026-11-02 UTC (`muse.env`, QA workspace `bex`; read-only replay of w4/459 after the pin `36c4ba2166fe` went live; dialogs opened and closed, no mutation request sent in any probe). Severity: minor (keyboard accessibility, nothing is lost). Estimate: 30m.

## Root cause (traced)

`dashboard/src/common/components/ui/dialog.tsx:81-100` records the opener only inside `handleOpenAutoFocus` (`openerRef.current = lastOutsideFocus()`) and restores it in `handleCloseAutoFocus`.

Radix FocusScope dispatches that open event only when nothing inside the dialog is focused yet (`dashboard/node_modules/@radix-ui/react-focus-scope/dist/index.mjs:92-96`):

```js
const hasFocusedCandidate = container.contains(document.activeElement);
if (!hasFocusedCandidate) { /* dispatch autoFocusOnMount ... */ }
```

A child rendered with React's `autoFocus` is focused during commit, so `hasFocusedCandidate` is true, `handleOpenAutoFocus` never runs, `openerRef` stays null, and `handleCloseAutoFocus` returns early at the `isConnected` check, leaving Radix's default (`body`).

The module-level `lastFocusedOutside` tracker (`dialog.tsx:12-25`) is correct at that moment (the `focusin` on the autofocused input is ignored because it is inside `role=dialog`), so the opener is available; it is just never read.

**Second mechanism in the .env case:** it is opened from a dropdown menu item, which unmounts when the menu closes. So even a correctly recorded opener would be a disconnected node; the control the user activated is the menu's trigger (Add variable).

## Fix

Target behavior: when any `DialogContent` closes by Escape, Cancel or overlay click, focus returns to the control that had focus when it opened, including dialogs whose first field is autofocused. When that control was a menu item that no longer exists, return to the menu's trigger button. If the action removed the opener, leave navigation focus alone.

Record the opener at mount time, independent of Radix's open-autofocus event (for example in a layout effect in `DialogContent`, or when `Dialog`'s `open` flips). Keep the existing `onCloseAutoFocus` pass-through and the trigger-based path unchanged (no double focus). Add tests that render a `DialogContent` with an `autoFocus` child and one opened from a menu item.

- **Adjacent classes:** `ConfirmDialog` has its own handler (w4/408); global search and the command palette keep theirs. Sheet panels share the primitive and were not probed.
- **Unverified:** the secret-file contents dialog and the API-key and registry-credential dialogs live; Sheet panels; screen-reader output.
- **Render:** standard dialog behavior; focus returns to the invoking control.
