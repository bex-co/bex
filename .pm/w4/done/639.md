# 639 — `build_started` carries only `deployId`, without Render's required `trigger`: the store joins a fact's deploy row for its trigger only for `pipeline_minutes_exhausted`

Why: Render's "Build Started" details require `buildId` and `trigger`, the same `{firstBuild, envUpdated, manual, deployedByRender, clearCache, rollback, user, …}` object `deploy_started` carries. A webhook or Events consumer that reads why a build started (first build, env update, manual, who) finds nothing on bex's `build_started`, though bex knows it: the same deploy's `deploy_started` carries it.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 310, 2026-11-13 17:22–17:28 UTC (`muse.env`, workspace `bex-canary`; pin `1c4d721bc8dc`). **Minor** (parity; a required field missing on one event type). ~40m.
- **Fixture:** Free Node web service `qa-20261113-r310-bf` (`srv-dbrkentd9ioc73ds16lg`), created through REST from `https://github.com/bex-co/bex` `examples/hello-node` with build command `echo qa-r310-boom >&2; exit 3`. Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe:**
  - `GET /v1/services/{id}/events?startTime=2026-11-13T17:00:00Z`. The build failed as intended (`build_failed`, with a `failureReason` naming the exit code).
    - `deploy_started` → `"trigger":{"firstBuild":true,"envUpdated":false,"manual":false,"deployedByRender":false,"clearCache":false,"rollback":false,"deployHook":false,"user":{"id":"usr-…","email":"…"}}`;
    - `build_started` → `{"deployId":"dep-dbrkentd9ioc73ds16m0"}`;
    - `build_ended` → `{"deployId":"dep-dbrkentd9ioc73ds16m0","buildStatus":"failed","reason":{}}`.
  - `GET /v1/events/evt-it4ad861rueerh9o3puv` (that `build_started`) → `"details":{"deployId":"dep-dbrkentd9ioc73ds16m0"}`.
- **Render** (pinned `render-public-api-1.json`, `GET /events/{eventId}` → "Build Started"): `required: ["buildId", "trigger"]`. `trigger` is the deploy trigger object with `firstBuild`, `envUpdated`, `manual`, `deployedByRender`, `clearCache`, `rollback` required.
- **Root cause:**
  - Build lifecycle events are facts. The store's composed events query joins a fact's deploy row (`LEFT JOIN deploys dc ON dc.id = f.deploy_id`, `lego/backend/internal/store/events.go:532`, and `fd`, `:849`). It selects the deploy's `trigger`, `triggered_by` and `clear_cache` only when `isPipelineMinutesFact` holds (`:291-294`, used at `:487`, `:494`, `:529`, `:747`, `:779`, `:830`). Every other fact gets `''`.
  - `events.view` sets `Details.Trigger = deployTrigger(r)` only for `pipeline_minutes_exhausted` (`lego/backend/internal/events/service.go:1457-1460`). `build_started` has no arm.
  - So the trigger `deploy_started` renders is available on the joined row and dropped.
- **Fix (target behavior):** `build_started` carries the same `trigger` object as the deploy's `deploy_started`.
  - Widen the predicate to name both facts (for example `factCarriesDeployTrigger`), and add `TypeBuildStarted` beside `TypePipelineMinutesExhausted` in `view`. REST, MCP `list_service_events`/`get_service_event`, GraphQL and webhook projections share `view`, so they move together.
  - `buildId` stays omitted, as w3/m302 t002 recorded ("not recorded by bex"). It is not reopened here.
- **Blast radius:**
  - The predicate has 6 uses in the two queries (list and retrieve-by-id). Both must change, or REST list and `GET /v1/events/{id}` disagree.
  - `pipeline_minutes_exhausted` must keep its trigger, and every other fact must keep none. Regression tests are needed on both.
- **Unverified:**
  - Render's `reason` on a **failed** `build_ended`. bex sends `{}` (`buildEndReason`, `service.go:742-749`, fills only a supersede cancel). Render's reason schema offers `buildFailed`, `newBuild`, `newDeploy` and `failure`, none required, so `{}` is schema-valid. Which one Render fills for a failed build was not captured, and it is not filed.
  - Webhook payloads were not captured this round.
- **Dedupe:**
  - w3/m302 (blocked on its closeout) made `build_ended`'s keys Render's and recorded the `buildId` omission. It does not name `build_started`'s `trigger`.
  - w9/m345 (done) added the join for `pipeline_minutes_exhausted` only.
  - `grep -rln "build_started" .pm | xargs grep -l -i trigger` finds w4/624 and m147/m148/m239, which are about delivery timing, not details.
  - Not deploy lag: `git log 1c4d721bc8dc..origin/main -- lego/backend/internal/events lego/backend/internal/store/events.go` is empty.
