# 067 — An environment group's own page says its secret files are "mounted into this service"

Why: an environment group is a workspace resource shared by N services (possibly zero), so copy borrowed from the single-service Environment tab tells the user the wrong thing about what a group is and what editing one affects.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 pass 4, journey 4. Fixture group `qa-0913d-group` (`evg-daj98da6m8ac739r56m0`) and service `qa-0913d-web` (`srv-daj99i26m8ac739r56ng`), both deleted at end of run.

## What renders (live, read from the accessibility tree)

On `https://dashboard.bex.co/env-groups/evg-daj98da6m8ac739r56m0`:

```text
- text: Secret Files Store files with secret contents (certificates, credentials)
        mounted into this service at deploy time.
…
- text: Linked Services Linking or unlinking redeploys the affected service.
- text: This group isn't linked to any services yet. It is still fully editable.
```

Three sentences in sequence: the first two say "this service" / "the affected service" (singular), and the third says the group is linked to **no** services at all.

## Cause

`dashboard/src/features/env-groups/components/env-group-editors.tsx:1` imports `EnvironmentEditor` from `@/features/services/components/service-environment-editor` and renders it for a group. That editor hardcodes service-scoped copy at `service-environment-editor.tsx:694`:

```tsx
description={t("services.secretFilesDescription")}
```

`dashboard/src/features/services/locales/en.ts:740-743` — _"Store files with secret contents (certificates, credentials) mounted into **this service** at deploy time."_ Its `description` field even says "Environment tab secret-files section description", i.e. the string knows it is service-scoped.

Grepping the shared editor's `services.*` keys for the word "service" finds **four** that are service-scoped by wording and reachable from the group page's editor:

| key | message | seen rendered on the group page? |
| --- | --- | --- |
| `services.secretFilesDescription` | "…mounted into **this service** at deploy time." | **yes** |
| `services.secretFilesEmptyBody` | "Add a file to mount secret contents into **this service**." | no — needs a group with no secret files |
| `services.envEmptyBody` | "Add a variable to configure **this service**." | no — needs a group with no variables |
| `services.secretFileDeleteConfirmBody` | "**The service** will redeploy without this file." | no — see below |

Separately, `envGroups`' own Linked Services copy is singular for a fan-out action: "Linking or unlinking redeploys the affected service." Linking/unlinking a group affects every linked service, and a group edit redeploys all of them.

## Bounded fix

Make the shared editor take its section copy from the caller instead of hardcoding `services.*`. The precedent is in the same file family: `SecretFilesEditor` already accepts a `copy` object (`secret-files-panel.tsx:70-82` builds one), so `EnvironmentEditor` can do the same and `EnvGroupEditors` can pass group-scoped `envGroups.*` strings ("…mounted into every service linked to this group", "Add a variable to configure the services linked to this group"). Pluralize the Linked Services line. en + zh for each new key. Sub-hour, one surface, no API change — hence an inbox note.

## Checked so the note does not overstate

- **`services.secretFileDeleteConfirmBody` does not surface in the group editor.** Deleting a secret file there stages it ("qa-note.txt · Will be removed · Undo") and commits through the footer's "Save and deploy" — no confirm dialog appears. Its only passer is `SecretFilesPanel` (`secret-files-panel.tsx:81`), and `grep -rn "SecretFilesPanel" dashboard/src | grep -v __tests__` returns **only its own definition** — no production consumer. So that string is probably unreachable today; worth a look from `/routine-dead-code` rather than a copy fix here.
- **The Linked Services line has no plural sibling already in use** — an earlier read of the page's `innerText` suggested it said "services", but the accessibility tree shows the singular. There is no in-page control case; the plural has to be written.

## Not bugs — verified during the same journey, recorded so a later pass does not re-litigate

- **"Add variable" is a dropdown trigger, not an action button.** Clicking it and then finding no new row, with the footer still reading "0 variable operations", looks exactly like a broken button — it is a `DropdownMenuTrigger` (`service-environment-editor.tsx:1261-1266`) whose menu offers "Add variable" / "Generated secret" / "Import from .env". Selecting the menu item adds the row and the counter goes to "1 variable operation" (verified). This also explains a second red herring: while a Radix menu is open the rest of the page is `aria-hidden`, so `page.locator('main').ariaSnapshot()` collapses to a single paragraph and the editor looks empty. Same shape as the "New Service" submenu trap already recorded for pass 1.
- **A group's variable reaches the running process.** `MESSAGE=from-group` added to the group, group linked to `qa-0913d-web` through the Link button → a `config_change` deploy ran → `curl https://qa-0913d-web.onbex.co/` returned `from-group` (baseline before linking was `OK`).
- **Deleting a linked group fans out correctly.** `DELETE /v1/env-groups/{id}` on a group with one linked service returned 204 and opened a new `config_change` deploy on that service, so the service rolls without the group's values rather than keeping stale ones.
- **A failed rollout keeps the old version serving, and the 15-minute wait is by design.** With `dockerCommand` patched to `/bin/qa-nonexistent-binary`, the build still succeeded, a `server_failed` event with `reasonCode: readiness_failed` fired ~40s later, the public URL kept returning 200 from the previous version, and the deploy row stayed `update_in_progress`. That is not a stuck state: `deployment_projection.go:105-135` sets a **900s** rollout budget explicitly matching Render's documented "if this condition is not met within 15 minutes, Render cancels the deploy and continues routing traffic to your service's existing instances", with bex-api's `DeployGateTimeout` deliberately longer at 18m so the specific verdict lands first. **The terminal state past 15 minutes was not observed this run** — journey 14's failure verdict, its `failureReason` text, and the notification/webhook content remain unverified and are worth a dedicated pass that waits the budget out.
- **`w4/m100`'s missing-commit finding reproduced on a second caller.** The env-group **link** deploy (`dep-daj9bc0gsm7s73f63ok0`, `trigger: config_change`) also carried no `commit`, which is `envgroups/service.go:1115` — one of the four `rollout.Tracker` callers `w4/m100/t005` enumerates. No new item; this is corroboration for that task's caller list.
