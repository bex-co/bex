# Reading one webhook endpoint returns blank latest-delivery fields that reading all of them populates

Why: `webhookEndpoint(id:)` reports `latestStatus`, `latestSentAt` and `latestParentStatus` as empty strings while `webhookEndpoints()` returns `delivered` / a timestamp for the very same endpoint **in the same request** — so a client that fetches one endpoint is told it has never delivered anything, and the two write verbs return the same blanks.

Found by live `/qa-find-bugs` 2026-09-21 pass 124 (w4-targeted, `muse.env` credentials). Fixtures `qa-20260921-wh`, `qa-20260921-hook`, `qa-20260921-trig`, all deleted.

## Repro — one request, two answers

```graphql
query {
  one: webhookEndpoint(id:"whk-…", ownerId:"tea-…") { id latestStatus latestSentAt latestParentStatus }
  all: webhookEndpoints(ownerId:"tea-…")             { id latestStatus latestSentAt latestParentStatus }
}
```

```json
"one": { "latestStatus": "",          "latestSentAt": "",                     "latestParentStatus": "" }
"all": { "latestStatus": "delivered", "latestSentAt": "2026-09-21T10:49:25Z", "latestParentStatus": "delivered" }
```

Same endpoint, same fields, same moment, same HTTP request — so timing, caching and permissions are all ruled out by construction. The endpoint had four successful deliveries behind it, the most recent 30 seconds earlier.

## Root cause

`lego/backend/internal/store/webhooks.go`:

- **`ListWebhookEndpoints` (`:185-201`)** selects the endpoint columns **plus** a `LEFT JOIN LATERAL` that computes `latest.status`, `latest.sent_at` and `latest.parent_status` from `webhook_delivery_attempts`.
- **`GetWebhookEndpoint` (`:232-234`)** selects only `webhookEndpointColumns` (`:71` — `id, tenant_id, name, url, event_types, enabled, disabled_reason, created_by, created_at, updated_at`). No join, no latest columns, so the three struct fields stay zero-valued.

`toView` (`webhooks/service.go:346-368`) is shared and faithful — it renders whatever the store row carries — so the divergence is entirely in the SQL, not in the projection.

**Three call sites are affected, not one** (`grep -n webhookEndpointColumns store/webhooks.go` → 4 hits, one of which is the definition):

| call site                                   | line  | consequence                                        |
| --------------------------------------------- | ----- | ---------------------------------------------------- |
| `GetWebhookEndpoint`                           | `:234` | single-endpoint read reports no delivery history      |
| `SetWebhookEndpointEnabled` … `RETURNING`      | `:251` | the enable/disable response reports none either       |
| the update verb … `RETURNING`                  | `:286` | same for `updateWebhookEndpoint`                      |

## Why the dashboard is not visibly broken

The Webhooks list page renders "Latest delivery: Successful / now" correctly, because it reads `webhookEndpoints` — `dashboard/src/features/webhooks/components/webhook-row.tsx:36-45` branches on `entry.latestStatus`. Any dashboard surface that switches to the single-endpoint read, and every API/CLI/MCP caller fetching one endpoint today, gets the blanks.

## This is isolated, not the tip of a pattern (pass 125)

Worth knowing before anyone opens an audit: a systematic single-vs-list diff across the other paired read roots found **no** second instance. Every scalar field was compared on a real production resource, in one request per pair:

| type                 | fields compared | divergences |
| ---------------------- | ----------------- | ------------- |
| `Blueprint`             | 11                | none          |
| `Database`              | 24                | none          |
| `KeyValue`              | 18                | none          |
| `Project`               | 8                 | none          |
| `Service`               | 51                | one — see below |

`Service.pushDeliveryMethod` differs (list `""` / REST omits the key; single `"github_app"`, on all five repo-backed services) and is **deliberate**, documented at the site: `apps/service.go:1315-1321` records that push deliverability is computed "HERE and nowhere else (w6/m99) … while List and the projections mutations and previews return, which the field is no part of the contract for, keep paying nothing for a lookup that costs GitHub round-trips", with a memo cache at `:213-218` explaining the per-service GitHub cost. Not a defect; do not "fix" it into the list.

So the webhook case is a one-off, and the fix below should stay local rather than becoming a sweep.

## Fix

Either share the lateral join with the single-row and `RETURNING` paths, or drop the three fields from the views those paths produce so a caller cannot mistake "not selected" for "never delivered". Prefer the first — the fields are genuinely useful on a single-endpoint read, and the second makes the type's meaning depend on which query produced it.

Whichever is chosen, `latestParentStatus` moves with the other two; it has the same origin and the same blank.

Estimate: ~30m including a test that asserts the single read and the list agree for an endpoint with at least one attempt.

## Also checked this pass, and found correct

Webhook delivery is in good shape end to end — this was the first pass in the loop to exercise it, and the payload never left bex (the receiver was a throwaway echo service in the same workspace).

- **All four subscribed events delivered.** `deploy_started`, `deploy_ended`, `service_suspended`, `service_resumed` each recorded `status: "delivered"`, `statusCode: 200`, `attemptNumber: 1`, empty `transportError` — and the receiver's own logs show the matching `POST /webhook … 200`.
- **The payloads are genuinely signed, not decoratively.** Deliveries carry Standard Webhooks headers — `webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64>` — and the signature **verifies**: HMAC-SHA256 over `{msg_id}.{timestamp}.{body}` keyed with the base64-decoded `whsec_` secret reproduces the header value exactly. Two other plausible keyings (raw secret with and without the `whsec_` prefix) do not, which confirms the implementation follows the spec rather than coincidentally matching.
- **The payload shape is clean**: `{"type":…,"timestamp":…,"data":{"id":"evt-…","serviceId":…,"serviceName":…}}`.
- **The delivery ledger matches reality** — `webhookDeliveries` lists exactly the four attempts the receiver logged, with correct types, ids and timestamps.

## Outcome (2026-09-21)

Fixed at all three sites the note identified, and the fix is structural rather than three copies: the `LEFT JOIN LATERAL` and its two column expressions are now named constants (`webhookEndpointLatestJoin`, `webhookEndpointLatestColumns`), and every read of an endpoint composes them. The list query had them inline, which is how one read could disagree with another about the same row.

The two mutation sites needed one more step — a `RETURNING` clause cannot join — so each `UPDATE` feeds a CTE that the same lateral then joins. `scanWebhookEndpoint` (the latest-less scanner) had no callers left and was deleted, so a new read cannot accidentally pick the shape that started this.

Proven in `webhooks_latest_delivery_pg_test.go`, which is Postgres-backed because the divergence lives entirely in SQL — `toView` renders whatever the row carries and was never wrong. Verified both ways against a local Postgres: it reproduces the exact reported blanks on the pre-fix SQL (`latestStatus ""`, `latestSentAt <nil>` from all three sites) and passes on the fixed one, and it asserts the list's own answer is non-empty first so it cannot pass vacuously.

The note's finding that this is isolated held: the single-vs-list sweep it recorded found no second instance, and the fix stayed local.
