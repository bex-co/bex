# 559 — A web service's Metrics leave out every request the activator answers: a Free service's 11.8 s cold-start wake never reaches Response Times, and first-deploy 503s are in the request chart but missing from the Status Code picker

Why: Response Times is where a Free user looks to see how slow their service feels. It leaves out the slowest response they actually waited for, and the Status Code picker can't select a code the chart shows right next to it.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 54, 2026-11-10 23:55 – 2026-11-11 00:16 UTC (`muse.env`, workspace `bex-canary`, pin `a0d5802594e9`). **Major**: Response Times hides a Free service's cold starts. ~55m.
- **Fixture:** Free image service `qa-20261110-mt54` (`srv-dbpqtolhi5vc738giu6g`, `docker.io/traefik/whoami:v1.10.1`). Deleted afterwards: DELETE 204, GET 404, URL 404.

  - **The request chart counts the 503s.** `GET /v1/metrics/http-requests?resource=<srv>&startTime=<now-1h>&endTime=<now>&aggregateBy=statusCode` returns `statusCode=200` 67 and `statusCode=503` 5 (3 at 23:56, 2 at 23:57).

- **Controls (correct today):**
  - The path filter `/p1` gives 20, on the dashboard and REST `path=/p1` alike.
  - The host filter and `aggregateBy=host` are correct.
  - Two 400s match Render's pinned spec (`render-public-api-1.json`):
    - REST `statusCode=` on http-requests. Render's params there are `startTime, endTime, resolutionSeconds, resource, service, host, path, aggregateBy`.
    - `resolutionSeconds` on bandwidth. Render's params there are `startTime, endTime, resource, service`.
  - filters/http `host: []` and filters/path `[]` are recorded in ADR018 (w1/m155). Not filed.
- **Root cause:**
  - **The Ingress routes to the activator in three states.** It points at the activator alias Service (`bex-activator-<app>`, port 8888) whenever the App is:
    - auto-hibernated;
    - awaiting its first serve;
    - held after a wake until a pod is ready.

    See `lego/operator/internal/controller/app_controller.go:3191-3196`, with the alias at `:4845-4859`.

  - **The activator holds, then proxies.** It reverse-proxies the woken request (`lego/operator/cmd/activator/hold.go:274-296`; `holdBound` 90 s at `:47`). Traefik counts those requests under the alias's service label.
  - **Prometheus-backed reads select only the App's own Service.** For every non-static App, `requestCounters` (`lego/backend/internal/metrics/source.go:558-567`) returns `serviceCounters` with `service="<ns>-<app>-<port>@kubernetes"` (`traefikServiceLabel`, `:473-475`). Only static sites use router counters (`routerScopedRequests`, `lego/backend/internal/metrics/service.go:1183-1185`). Three reads go through this selector:
    1. **http_latency**, through `promQueryFor` (`source.go:490-515`, `traefik_service_request_duration_seconds_bucket`). So Response Times leaves out every request the activator answered.
    2. **STATUS_CODE discovery**, through `filterValuesMatch` (`source.go:849-858`), then `MetricsFilters` (`service.go:1411-1416`) and `filterValuesOrEmpty` (`:1424-1446`). It feeds:
       - REST `/v1/metrics/filters/http` (`rest.go:243-261`);
       - GraphQL `metricsFilters` (`graphql.go:352`);
       - the dashboard picker (`dashboard/src/features/metrics/hooks/use-metrics-filter-values.ts`, `components/network-metrics-card.tsx:115-121` and `:162-168`).
    3. **The http_requests counter fallback**, used when Loki fails (`service.go:1149-1166`).
  - **The count comes from a different store.** The http_requests count and its statusCode breakdown come from the request-log store (`service.go:1121-1148`, w4/m119). That store attributes lines by Ingress, so it includes the activator path. Hence the chart and the picker disagree.
  - **The discovery code states the rule it now breaks** (`source.go:868`): "Discovery must read the SAME series the chart reads, or the dropdown and the graph disagree".

- **Fix (target behavior):**
  - **Count every request on the App's public routes.** Every request metric for a compute App counts every request answered there, whichever backend Service answered it. That includes wake-held and first-deploy responses, and (unverified) maintenance responses.
  - **Concretely,** the three Prometheus-backed reads (http_latency, STATUS_CODE discovery, the http_requests fallback) select either:
    - the App's router identities (`traefik_router_*{router=~<App routers>}`, the shape static sites and bandwidth already use through `TraefikRouterNames`); or
    - a service selector that also names the App's activator alias.
  - **Whichever is chosen, the result must satisfy:**
    - (a) Response Times for a window containing a wake shows the held request's duration (p99 ≥ ~11 s for an 11.8 s wake).
    - (b) The Status Code picker, REST filters/http and GraphQL `metricsFilters` list every code that the http_requests statusCode breakdown returns for the same resource (503 here).
    - (c) The counter fallback equals the Loki count over the same window.
  - **One backend change covers every surface.** REST, GraphQL, MCP `get_metrics` and the dashboard share these reads.
  - **Tests:**
    - **New fixture.** A Prometheus fixture with series under both the App's own Service and its activator alias (or its router). Assert that the latency quantile includes the alias-served bucket, discovery returns the alias's code, and the fallback count sums both.
    - **Static sites.** The router-scoped tests stay green.
    - **Image-port apps.** The published-port tests stay green (w4/m243 `TestImagePortRequestMetricsUseThePublishedPort`).
- **Blast radius:**
  - **Callers.** `requestCounters` has 2 production callers: `source.go:495` (`promQueryFor`) and `:850` (`filterValuesMatch`). `routerScopedRequests` has 3: `service.go:1160`, `:1201` and `:1433`.
  - **Check the operator's idle detector separately; don't assume.** `lego/operator/internal/controller/activity.go:150` reads `traefik_service_requests_total{service=<app svc>}`, so it also can't see requests the activator proxies after a wake. Confirm whether the activator's own last-active stamp covers them before changing it.
- **Unverified:**
  - Maintenance-mode responses (a paid-plan feature; not probed).
  - Whether a held wake that times out (activator 503) shows the same gap.
  - Private services. They have no public route, so are probably unaffected.
  - Whether Render's response-time chart includes a Free instance's spin-up wait.
- **Render:** Render's Metrics page charts response times and status codes for all of a service's HTTP traffic. How it records the spin-up hold is unverified.

- **DoD (live):** on an owned Free web service:
  1. **First deploy.** Poll its URL during the first deploy until it is Live, then send 20 GETs. The dashboard Status Code picker and `GET /v1/metrics/filters/http` list every code that `http-requests?aggregateBy=statusCode` returns for the window, including any 503 from the first deploy.
  2. **Wake.** Let it hibernate (the `service_hibernated` event), then `curl -w '%{time_total}'` its URL once. The dashboard Response Times (p99) and `GET /v1/metrics/http-latency?quantile=0.99` for that minute show a value within ~1 s of the measured wake time.
  3. **Controls unchanged:** the `/p1` path count, the host filter, `aggregateBy=host`, and a static site's Response Times.
