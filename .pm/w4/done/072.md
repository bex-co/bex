# 072 — A deploy event can never say who triggered it: the `deploys` row has no caller, so the service Events feed drops the actor the audit log keeps

Why: "who rolled this back?" is the first question of any incident review, and the service Events feed — the surface built to answer it — silently omits the answer for every deploy, while the fields to carry it already exist on all three surfaces and the UI is already wired to render them.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 pass 16, journey 3. Fixture `qa-20260913-rb` (`srv-dajh3d26m8ac739r5epg`), free plan, repo `bex-co/bex` root `examples/hello-go`, docker runtime — created, deployed three times, rolled back, and deleted inside the run.

## What three deliberately different triggers produce

Three deploys, each triggered a different way by a known caller (me, one session, one workspace), then read back through GraphQL:

```text
POST /v1/services                              → dep-dajh3d26m8ac739r5eq0  (first deploy)
POST /v1/services/srv-…/deploys                → dep-dajh4li6m8ac739r5er0  (manual, via API)
Rollback clicked in the dashboard               → dep-dajh5l0gsm7s73f63vq0  (rollback, via GraphQL)

query { serviceEvents(serviceId:"srv-dajh3d26m8ac739r5epg", limit:14){
  type timestamp details { deployId deployStatus actor triggeredByUser
                           trigger { firstBuild manual rollback envUpdated clearCache deployedByRender } } } }
```

| event | deploy | trigger flags | `actor` | `triggeredByUser` |
| --- | --- | --- | --- | --- |
| `deploy_started` 21:12:20 | `dep-…5eq0` | `firstBuild: true` | `""` | `""` |
| `deploy_started` 21:15:02 | `dep-…5er0` | `manual: true` | `""` | `""` |
| `deploy_started` 21:17:08 | `dep-…5vq0` | `rollback: true` | `""` | `""` |
| every `build_started` / `build_ended` / `deploy_ended` | all three | `null` | `""` | `""` |

Ten events, three distinct human-initiated triggers, **zero** attribution. The trigger classification is perfect — `rollback: true` on exactly the rollback, `firstBuild: true` on exactly the first, and the rollback correctly emits **no build events** because it reuses an existing image — so the feed knows precisely *what* happened and never *who* did it.

## The UI is already built for the value, and degrades honestly

`dashboard/src/routes/services.$serviceId.events.tsx:247` passes `actor={details?.actor || details?.triggeredByUser || ""}`, and `:424` renders `{actor ? <span>{t("services.eventsActor", { actor })}</span> : null}`. With both empty the row simply omits the clause — no "Unknown", no raw id. So there is nothing to fix client-side and nothing dishonest on screen; the value is absent at the source. The `services.eventsActor` translation key exists and is dead for deploys.

## Root cause — the deploy branch never sets it, and the column it would read does not exist

`lego/backend/internal/events/service.go` builds each event from one of two sources. Only the **audit** branch attributes anything (`:737-746`):

```go
case store.EventSourceAudit:
	switch ev.Type {
	case TypeSuspenderAdded, TypeSuspenderRemoved: ev.Details.Actor = r.Caller
	case TypeServerRestarted:                      ev.Details.TriggeredByUser = r.Caller
	…
```

The **deploy** branch (`EventSourceDeploy`, which produces `deploy_started`/`deploy_ended`) sets status, pre-deploy status and failure fields, and never touches `Actor`/`TriggeredByUser`. The package's own header comment documents this as the intended mapping — `suspender_added (details.actor = the caller)`, `server_restarted (details.triggeredByUser = the caller)` — and lists `deploy_started`/`deploy_ended` with no actor at all.

It cannot do otherwise today: **the `deploys` table has no caller column.** `0005_deploys.up.sql:10-20` creates 9 columns, and across the 42 migrations exactly 6 columns have been added to it (`pre_deploy_status`, `commit_message`, `updated_at`, `commit_author_at`, `failure_reason`, plus the lifecycle set) — none an actor. Meanwhile `audit_events` has `caller` + `caller_method` (`store/audit.go:110`), which is why the workspace audit log answers the same question correctly: this run's own writes appear there with a caller.

**That contrast is the control case, and it is a real one** — same product, same run, one surface attributes and the other does not, for a mechanical reason (which table the row came from), not a policy one.

## Target behavior

**Every deploy a person initiates names that person on all three surfaces; a deploy nobody initiated names nothing and is attributed by its commit instead.** Concretely:

1. Add a caller column to `deploys` (`triggered_by`, the identity subject, matching `audit_events.caller`'s form), written by each verb that opens a row. Prefer this over correlating deploy rows to audit rows by `(app, verb, timestamp)` — the correlation is fragile and the column is one migration.
2. Populate `Details.TriggeredByUser` from it in the deploy branch. Use **`triggeredByUser`, not `actor`** — the header comment already assigns `actor` to the suspend pair and `triggeredByUser` to `server_restarted`, which is the nearer neighbour of a deploy, and the UI's fallback chain reads both anyway.
3. **Place the unattributed classes explicitly.** A Git-push auto-deploy (`deployedByRender`/new-commit trigger) and a deploy-hook fire have no session identity — those must stay empty, not acquire a synthetic actor. For them the commit is the attribution, and the feed already renders the commit. A deploy triggered by an **API key** should name the key's identity, not a human — decide and pin which form that takes, since `audit_events.caller_method` distinguishes session from bearer and the deploy row will need the same distinction to be honest.
4. **Resolve the subject to something a human reads.** A bare Kratos subject in the Actor position is the defect `w4/069` is already filed for on two other surfaces; whatever shared resolver 069 lands must be used here too, or this fix trades a blank cell for an unreadable one. **Do 069 first or together** — landing this alone would make the Events feed the fourth surface printing raw subjects.

## Render

Render's deploy object does not carry an actor either, so this is **not** a REST-parity gap — the fix lands on bex's own `triggeredByUser`/`actor` event fields (already bex extras) and the dashboard. Render's dashboard *does* attribute deploys in its own UI ("Deployed by …"), which is what makes the product expectation reasonable; `docs/render-artifacts/deploy-detail-page.md` is the capture to check before choosing the wire spelling, and this note does not assume what it says.

## Dedupe

`grep -ril "triggeredByUser\|triggered_by\|eventsActor" .pm --include="*.md"` → **one** file, `w4/069`, and only at its fourth row, which marks `events.tsx:247` **unverified** with the guess "may already carry a resolved value". That row is now answered — and answered the other way: the value is not an unresolved subject, it is nothing at all. 069 has been amended to record the measurement and point here. The two are complementary, not duplicates: 069 is a client-side rendering fix for surfaces that *have* a subject; this is a backend data-capture fix for a surface that has none. No `DO_NOT_DO.md` anti-goal applies.

Sub-hour on its own (one migration, one branch, the caller threading) — but sequenced behind/with `w4/069`, so an inbox note rather than a milestone.

## Journey 3 verified correct, so not filed — rollback works end to end

This is the first live end-to-end rollback in the loop's record; `w4/m100`'s "Unverified" list called out "rollback execution (the Rollback action was observed as offered on the deactivated row, never clicked)". It was clicked, and it is right:

- **Offered in exactly the right place.** The deploys list put **Rollback** on the Deactivated row and not on the Live one — `w4/051`'s fix confirmed in production, on the surface it was filed against.
- **Confirmation is honest:** "Roll back to this deploy? The service will redeploy from the image used in this deploy." → Proceed → toast "Rollback triggered."
- **It restored the right artifact.** The new deploy's image is `…/tea-…-qa-20260913-rb:gen-1@sha256:057b2e7d…` — generation **1**, i.e. the first deploy's build, not the second's — and `rollbackOf: "dep-dajh3d26m8ac739r5eq0"` names the target it restored.
- **Terminal states agree across all three surfaces.** After it settled: the rollback deploy `live`, both predecessors `deactivated`, on the REST list, on the detail page, and in the events feed; the service header read Running / Latest deploy Live / `rev-3`.
- **Public URL kept serving** — `curl -sSI https://qa-20260913-rb.onbex.co/` → `HTTP/2 200`, `content-length: 2` before the rollback, and the service stayed Running through it.
- **No build was re-run for the rollback** (no `build_started`/`build_ended` pair), which is the correct behavior for restoring an existing image and is why it completed in ~20s versus ~75s for a build.

## Two near-misses, checked and killed

- **The Activity feed dumps a 2,483-character commit body into each row** — my own multi-paragraph commit message, six times, 16 KB of `main` innerText for 10 events. Not a bug: the paragraph carries `class="line-clamp-1"`, so it renders as one clamped line. The full text is in the DOM (a screen reader would read all of it, which is a mild a11y cost worth remembering if someone touches that row) but nothing is visually broken.
- **`deploy.image` is absent on the two Git-built deploys and present only on the rollback**, which looked like the view exposing the *requested* image where it should expose the *resolved* one. It is faithful instead: the pinned Render spec says of `deploy.image`, verbatim, _"Image information used when creating the deploy. **Not present for Git-backed deploys**"_ (`deploys/rest.go:48-52`). Recorded so the next hunt does not re-file it. One residual, deliberately **not** filed for lack of a parity capture: on the rollback row that `ref` is an internal cluster address (`zot.bex-registry.svc:5000/…`), which is truthful but unusable to the caller — whether bex should expose it at all is a design question, not an observed defect.
