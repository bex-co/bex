# 475 — `GET /v1/projects` without `ownerId` returns 400 although Render marks `ownerId` optional, and ADR018 does not record the divergence

Why: AGENTS.md says a divergence stands only when ADR018 records it with the user's sign-off, and the only record of this one is w4/038 calling it "deliberate" and "a separate product decision"; a Render-conformant client (Render CLI, SDK, Terraform provider) that lists projects with no filter gets an error where Render returns 200.

Source: live `/qa-find-bugs` w4 loop run, round 34, 2026-11-04 UTC (`muse.env`, workspace `bex`; read-only, in-page `fetch` from dashboard.bex.co, no mutation). Severity: minor (parity, REST only). Estimate: 30m.

## Repro

From a signed-in dashboard.bex.co page:

```js
await fetch("https://api.bex.co/v1/projects", { credentials: "include" });
```

| Request | Result |
| --- | --- |
| `/v1/projects` | 400 `{"error":"bad request: invalid query parameter \"ownerId\"","id":"bad_request"}` |
| `/v1/projects?limit=5` | the same 400 |
| `/v1/projects?ownerId=` (empty) | 400 |
| `/v1/projects?ownerId=tea-d98210cbbpdc73dcrkvg&limit=5` | 200 with projects |

Controls in the same session, all 200 with no `ownerId`: `/v1/services?limit=1`, `/v1/postgres?limit=1`, `/v1/key-value?limit=1`, `/v1/env-groups?limit=1`.

## Root cause

- `lego/backend/internal/projects/rest.go:121-128` returns `core.ErrBadRequest` when `ownerId` is empty. Its own comment says "Render marks ownerId optional here; bex requires it (the w6/m126 parity rework owns that divergence)".
- w6/m126 is the project write-shape milestone and did not take that on: `docs/ADR018-render-parity.md:35` covers shapes and inline environments, not this.
- w4/038 (done) only improved the message and left "the deeper parity question" undecided (`.pm/w4/done/038.md:29,44`).
- `listBare` (`lego/backend/internal/projects/service.go:361-374`) already calls `AuthorizeWorkspace(ctx, RelCanView, workspaceID)`, which resolves an empty id to the caller's default workspace (the behavior w4/m128 documents for the unscoped notification routes), so the fix is to stop rejecting.

## Fix (target behavior)

- `GET /v1/projects` with no `ownerId` returns 200 and lists the caller's default workspace, like the sibling lists above.
- An explicit `ownerId` keeps today's behavior. An `ownerId` the caller cannot view stays the same forbidden/not-found it is today.
- Record in ADR018's Projects row that an omitted `ownerId` is a default-workspace list, not Render's all-workspaces list, as a narrower divergence needing the user's sign-off. Or list across all of the caller's workspaces if that is cheap with the existing store.
- Tests: replace the w4/038 `rest_test.go` assertion that the missing-`ownerId` 400 names `ownerId`, and add a conformance test against the pinned schema.

## Blast radius and adjacent classes

- One handler. `GET /v1/environments` requires `projectId`, which Render also requires (ADR018 says "required `projectId`"), so it does not move.
- GraphQL `projects(ownerId: String!)` is bex-native and not a Render surface, so it is left alone. MCP was not checked.
- Unauthenticated stays 401. A workspace the caller cannot view stays as today.

## Unverified

- What Render returns for a user in several workspaces (all of them, per its spec wording).
- MCP list-projects with no workspace.
- The Terraform provider or CLI call that would hit this.
