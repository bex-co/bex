# Autoscaling ranges match Render's: `minInstances` at least 1, and targets at most 90%

Why: bex accepts `minInstances: 0`, stores it, and reads it back, while the operator always runs at least one instance, so the setting a user reads is not the one that runs; Render's own schema and dashboard bound the range at 1 instance and 90%.

- **Render:** its pinned Blueprint schema (`lego/backend/internal/apps/schema/render.yaml.json`, `serverService.scaling`) has `minInstances` `"minimum": 1` and `targetCPUPercent`/`targetMemoryPercent` `"maximum": 90`. Its Scaling page (`docs/render-artifacts/manual-scaling.md:34`) has a 1–100 instance slider and 1–90% targets. Render's REST bounds are not published.
- **bex:** `lego/backend/internal/apps/service.go:7188-7213` allows `minInstances` ≥ 0 and targets 1–100 on REST, GraphQL and MCP; the operator clamps to at least 1 (`lego/operator/internal/controller/autoscale.go:292-297`).
- **Do (recommendation, Render's REST bounds unverified):** refuse `minInstances` below 1 and targets above 90 on every surface with a named 400, as the Blueprint schema already does; check that no stored autoscaling config holds 0 or more than 90 before shipping, and record the bounds in ADR018.
- **End state:** an autoscaling write with `minInstances: 0` or a target of 95 is refused with a message naming Render's range; reads always match what runs.
- **Size:** about 45m.

**Done 2026-11-27 (loopx w4).** `autoscalingSpec` (`lego/backend/internal/apps/service.go`), the one check behind `PUT …/autoscaling`, a create's `serviceDetails.autoscaling`, GraphQL `setAutoscaling`, MCP `update_service(autoscaling:)` and a Blueprint `scaling` block, now refuses a minimum outside 1–100 with 400 "minInstances must be 1–100" and a target outside 1–90 with "targetCPUPercent must be 1–90" (or `targetMemoryPercent`), before any write. A turned-off criterion's kept percentage is held to the same 90 ("criteria.memory.percentage must be 0–90"; 0 still clears it), as Render's dashboard keeps the slider's 1–90 value. The App CRD's markers carry the same bounds (`minReplicas` minimum 1, the four percentages maximum 90), and MCP's argument descriptions say 1-100 and 1-90 instead of "≥ 0; default 1" and 1-100. A Blueprint already met the explicit values through the pinned schema; one that leaves out `minInstances` (Render's Blueprint spec marks it "Required", render.com/docs/blueprint-spec read 2026-11-27) is now refused at `services[i]` instead of being stored as 0. Production held one autoscaling config across 28 Apps on 2026-11-27, inside both ranges, so no stored value needed changing and reads match what runs. Tests: `autoscaling_range_test.go` (every surface, the boundaries 1 and 90 accepted and read back, memory, kept percentage, create, Blueprint), each failing with the fix reverted; `TestDisabledAutoscalingPercentageRules` moved to the 0–90 bound. Recorded in the ADR018 services-lifecycle autoscaling row.
