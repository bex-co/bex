# 369 — PATCH with the GET-emitted `envSpecificDetails.preDeployCommand` shape fails as a bare "bad request"

Why: `GET /v1/services/{id}` emits `preDeployCommand` inside `serviceDetails.envSpecificDetails`, but sending that exact shape back in a PATCH is rejected with an opaque `{"message":"bad request"}` that names no field — a GET→modify→PATCH round-trip breaks with no hint that the write channel is the sibling `serviceDetails.preDeployCommand` field.

**Severity:** minor. **Estimate:** ~30m.

**Source:** live `/qa-find-bugs w4` loop run 11, 2026-10-19 UTC, `muse.env`, workspace `bex-canary`, on the run's own fixture `qa-20261019-loop11-go` (`srv-dbbadkqbpdss73ci0oi0`, native Go; deleted after the run, session revoked).

## Probes (production, session-authenticated REST)

- `GET /v1/services/srv-dbbadkqbpdss73ci0oi0` → `serviceDetails.envSpecificDetails = {buildCommand, preDeployCommand: "", startCommand}`.
- `PATCH {"serviceDetails":{"envSpecificDetails":{"buildCommand":"go build -o app .","startCommand":"./app","preDeployCommand":"false"}}}` → `400 {"error":"bad request","id":"bad_request","message":"bad request"}`.
- `PATCH {"serviceDetails":{"envSpecificDetails":{"buildCommand":5}}}` (wrong type) → same bare `bad request`.
- Contrast: `PATCH {"bogusField":1}` → `400 bad request: request body contains unknown field "bogusField"` — the top-level strict decoder names the field; the nested path does not.
- The documented write channel works: `PATCH {"serviceDetails":{"preDeployCommand":"false"}}` → `200`, next deploy `pre_deploy_failed` with `failureReason: "the pre-deploy command exited with code 1; check the pre-deploy logs"`, prior deploy kept serving `200` throughout; reverting to `""` rolled out `live`. Pre-deploy itself is healthy — only the error surface is broken.

## Root cause

The read/write asymmetry is deliberate and must stay: GET projects `preDeployCommand` into `envSpecificDetails` because the pinned CLI reads it only there (`lego/backend/internal/apps/render.go:518-608`, native branch `:604-608`), while the Render-faithful write field is `serviceDetails.preDeployCommand` (`lego/backend/internal/apps/rest.go:268-271`, consumed `:852-854`).

The defect is one line: the PATCH nested `envSpecificDetails` decoder (`lego/backend/internal/apps/rest.go:873-893`) has no `preDeployCommand` field, and on any decode failure returns the bare sentinel at `:882` (`return patchFields{}, core.ErrBadRequest`), discarding the field-level detail that `core.safeJSONDecodeError` (`lego/backend/internal/core/http.go:217-233`) produces for the top-level strict path (`render_openapi.go:652` marks these routes strict). Sibling decoders name the problem instead — e.g. `decodeMaintenanceMode` returns `"%w: serviceDetails.maintenanceMode requires enabled and uri"`.

## Fix (target behavior)

- In `resolveFields`' nested env-specific decode (`rest.go:881-883`), wrap the decode error with its safe detail instead of the bare sentinel (e.g. `fmt.Errorf("%w: %s", core.ErrBadRequest, core-safe message)`), so unknown-field and wrong-type failures inside `envSpecificDetails` name the field exactly like top-level failures do. Do not accept `preDeployCommand` in the nested block — the documented write channel stays `serviceDetails.preDeployCommand`.
- Audit the other bare `core.ErrBadRequest` returns on nested-fragment decodes in the same file (`:1148`, `:1294`, `:1316`, `:1367`) and give them the same treatment where the underlying error is a safe decode error.

## Acceptance

- Replaying probes A/C above returns `400` whose message names the offending field (`preDeployCommand` / `buildCommand`); probe B's message is unchanged.
- `PATCH {"serviceDetails":{"preDeployCommand":"false"}}` still applies and rolls out as before (covered by existing patch-pipeline tests plus one new case asserting the nested-decode error message).
- `cd lego/backend && go test ./internal/apps/...` passes.
