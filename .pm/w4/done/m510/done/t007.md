## Objective

Check that both types read the same on REST, GraphQL, MCP, webhook payloads and the dashboard, and match Render's members; check that no build-source link change still reads as `source_changed` anywhere.

## Context

## Outcome

Audited REST, GraphQL, MCP, webhooks, and the dashboard against Render's pinned `retrieve-event` OpenAPI members (`Artifact Source Changed`, `Artifact Fetch Failed`) and against each other:

- **Schema & wire shape:** `TestRenderEventDetailsMatchTheirMember` passes for `artifact_fetch_failed` (`required: [buildId, message]`) and all three `artifact_source_changed` shapes (attach, switch, detach; absent side omitted) with zero missing or extra fields. REST list/retrieve and MCP (`list_events`, `get_service_event`) share `toRenderEvent` and return identical details; GraphQL serves `fromBuildSourceId`, `toBuildSourceId`, `buildId`, and `message` on `ServiceEventDetails` alongside all sibling string detail fields.
- **No residual `source_changed` on build-source links:** Audited every `LinkBuildSource`, `CreateBuildSource` (`serviceIds`), `SetSourceAndRegistryCredential` (unlink), and Blueprint (`persistBlueprintIntent`, `recordStackSettingChanges`) path; none emits `source_changed` for a build-source attach, switch, or detach. Pre-`w4/m510` legacy `apps.LinkBuildSource` rows without sides are excluded from service events and webhooks so historical rows stay clean.
- **Dashboard & webhooks:** Both event types appear in the dashboard Events filter (`Deploy` / `Configuration`), icons, chart failure markers, and webhook event picker (`GROUPS.deploy`), with translations in all 8 locales (`en`, `zh`, `de`, `es`, `ja`, `ko`, `pt`, `ru`). No drift to file; the unverified choice to emit `artifact_fetch_failed` instead of `image_pull_failed` on linked services is recorded in `docs/ADR018-render-parity.md` and `docs/render-artifacts/webhooks-api.md`.
