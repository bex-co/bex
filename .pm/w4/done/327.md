## Root, consumer and bounded correction

`dashboard/src/features/logs/lib/ansi.ts:141–142` reads `input[i]`, one UTF-16 code unit. At `:212–215` each unit occupies one `Cell` and advances the cursor. U+1D49C occupies two such cells; after carriage return, the two ASCII replacement letters fill those cells and leave the original `Z`. `stripAnsi:226–230` uses that same parser. Executing the **unmodified TypeScript module** with Node22.17.1 produced `stripAnsi("𝒜Z\rAB") === "ABZ"`; the same local probe preserves ordinary ASCII overwrite, untouched Unicode and SGR styling. These are actual module imports, not a reimplemented algorithm.

By contrast, `lego/backend/internal/logs/display.go:44–48` uses `[]rune`, and its ordinary write at `:59–72` advances once per code point. `service.go:477–486` applies that projection only when `textMode=display`. The correct existing result is `AB`. The [ECMAScript string-iterator specification](https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype-@@iterator) distinguishes code-point iteration from indexed UTF-16 units; the local probe confirms that this character has two units and one code point.

Correct the shared browser parser's ordinary-character reads to consume a complete code point and advance its input offset by that character's UTF-16 length, while advancing its existing logical cursor once. Keep escape-sequence parsing, carriage-return/newline positions, erase-in-line modes, SGR runs and plain-text fast path intact. Its `Cell.ch` is already a string and can hold the complete pair. No new dependency or backend search change is required. This restores the existing Go/client code-point model; it does not add grapheme clustering, terminal column-width calculation or cursor-motion emulation.

**Shared scope, reviewed separately (10m):** grep of production source finds two parser entry paths: `map.ts:52` for rendered rows and `stripAnsi` for the deploy panel's local matcher. `map.ts:38–56` preserves the raw message and dedupe key while attaching spans; `log-line-list.tsx:350,367–368` renders those spans. Its three presentation consumers are service `LogViewer`, `DeployLogPanel` and `DatastoreLogViewer`; history, older pages and live frames converge through that map. Deploy local search is `deploy-log-panel.tsx:133–139`. Service history/live intentionally opt into server display matching at `log-viewer.tsx:179–193`. Apply the correction globally to this shared parser, with controls for all three views; do not add a service-only workaround.

**Families/aliases:** the canonical service/deploy views are shared by web, static, cron, worker and private service routes; the datastore view is used for Postgres and Key Value. Only a Free image web service's service/deploy views were exercised here. Datastore renderers and other service families are source-traced compatibility obligations, not separately observed failures. REST, GraphQL, MCP and CLI keep their raw message bytes and current raw/default versus opt-in display semantics.
