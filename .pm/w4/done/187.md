# 187 — A superseded deploy keeps `preDeployStatus: running` forever; its page says "Pre-deploy command running" after it finished

Why: a finished, canceled deploy that claims a step is still running misleads anyone diagnosing the rollout it interrupted.

Live `/qa-find-bugs` Loop13 2026-10-04 (`muse.env` QA login, bex-canary):

1. Git-source web service `qa-20261004-loop13-web`
   (`srv-db12d408mmqc73d4hp3g`, repo `https://github.com/bex-co/bex`,
   root `examples/hello-go`, runtime Docker) — first deploy Live, 200 `OK`.
2. Set env `MESSAGE=loop13-ok` → config-change deploy Live, app 200
   `loop13-ok`. Working.
3. Set Pre-Deploy Command `echo loop13-predeploy-ok` ("Pre-Deploy Command
   updated.") — this minted config-change deploy `dep-db12gpo8mmqc73d4hp6g`.
   13s later a Manual Deploy → `dep-db12gt08mmqc73d4hp80` superseded it.
4. `dep-db12gpo8mmqc73d4hp6g` now reads `status: canceled`,
   `cancelReason: "Superseded by dep-db12gt08mmqc73d4hp80"`,
   `finishedAt` set — but `preDeployStatus: "running"` forever. Its deploy
   page header shows "Pre-deploy command running" under a Canceled status,
   even though All logs proves the command already printed
   `loop13-predeploy-ok` before the cancel. The superseding deploy closed
   correctly (`live`, `preDeployStatus: succeeded`).

Root cause: `recordDeploy` projects pre-deploy evidence onto the row only
when the row's generation still matches the CR's
(`lego/backend/internal/store/reconciler.go:688-697`); the supersede-cancel
close (`supersededDeployStatus`, same file) transitions the row to canceled
without touching `pre_deploy_status`. `TransitionDeploy`
(`lego/backend/internal/store/store.go:2281-2334`) clears `stall_reason` on
every terminal close (w4/m112 precedent, `:2324-2326`) but leaves
`pre_deploy_status` alone — so a row canceled mid-pre-deploy keeps
`running` permanently. The dashboard renders it unconditionally
(`dashboard/src/features/deploys/components/deploy-header.tsx:54`,
`deploys-list-page.tsx:184`).

Fix (sub-hour): settle `pre_deploy_status` when a row goes terminal —
either clear it like `stall_reason` in `TransitionDeploy`, or stamp a
terminal value (e.g. `canceled`) on the supersede path in `recordDeploy`.
Keep the generation guard: never copy the *current* release's pre-deploy
evidence onto a superseded row (the comment at `:719-723`).

Out of scope: w4/180's log-filter gap (separate surface, already filed);
the pre-deploy failure path itself, which 180 verified working.

Fixtures: `qa-20261004-loop13-web` + `qa-20261004-loop13-proj` removed
(service URL 404-verified). No other workspace touched.

## Done 2026-10-04 (loopx)

`TransitionDeploy` settles a still-`running` pre-deploy step on every terminal close, beside the w4/m112 `stall_reason` clear: `succeeded` when the close is `live` (the release passed its pre-deploy), otherwise the new `canceled` value. Already-settled (`failed`/`succeeded`) and absent (`""`) steps are untouched, and the generation guard in `recordDeploy` is unchanged. The memStore fake mirrors it. The dashboard maps `canceled` to "Pre-deploy command canceled" (en/zh); `hasPreDeploy` stays true, so the pre-deploy log leg is still read. REST/GraphQL/store vocabulary comments list `canceled`. Evidence: `predeploy_close_pg_test.go` against real Postgres 16 — superseded-mid-step and went-live fail on the old SQL (`running` kept), pass now; the controls pass on both. Store/deploys/full backend suites, lint, 1014 dashboard tests + lint green.
