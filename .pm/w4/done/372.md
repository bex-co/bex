# 372 — A duplicate inline environment at project create conflicts without naming it

Why: creating an environment directly names a duplicate (`an environment named "qa-env" already exists in this project`), but the same duplicate supplied inline in the project-create body answers `environment: already exists` — the caller cannot tell which of several inline environments collided.

**Severity:** minor. **Estimate:** ~20m.

**Source:** live `/qa-find-bugs w4` loop run 76, 2026-10-20 UTC, `muse.env`, workspace `bex-canary`. The duplicate create was rejected atomically (a retry with distinct names succeeded under the same project name); the project was deleted this run and the session revoked.

## Probes (production, session-authenticated REST)

- `POST /v1/projects {"name":"qa-20261019-loop76-proj","ownerId":…,"environments":[{"name":"staging"},{"name":"staging"}]}` → `409 {"id":"conflict","message":"conflict: environment: already exists"}`.
- Control (run 17, same workspace): `POST /v1/environments {"name":"qa-env","projectId":…}` twice → `409 an environment named "qa-env" already exists in this project`.
- Retry with `staging` + `prod` inline → `201`, both environments listed; project delete → `204`; later environment list → named `project not found`. Atomicity and cleanup are correct — only the message lacks the name.

## Root cause

The named message lives in the environment verb: `conflictOrMapError` (`lego/backend/internal/environments/service.go:688-696`, w6/m49) wraps `store.ErrConflict` with the attempted name. Project create with inline environments does not go through that verb — it writes project + environments in the grouping transaction (`lego/backend/internal/store/grouping_tx.go`, driven from `lego/backend/internal/projects/service.go`, whose own duplicate-project naming sits at `service.go:504-508`) and falls through to `store.MapError`, whose classify text is the unnamed `environment: already exists`.

## Fix (target behavior)

- On the project-create path, an environment-name conflict returns the same named conflict as `POST /v1/environments`: `an environment named "<name>" already exists in this project` (same `CONFLICT` code, 409 unchanged). Name the first colliding inline environment.
- Keep the rejection atomic (no partial project), as today.

## Acceptance

- Replaying the duplicate-inline probe returns `409` naming `"staging"`; distinct inline names still create both environments in one call.
- One regression test beside the existing project-create tests asserting the named message; the direct-environment control message is unchanged.
- `cd lego/backend && go test ./internal/projects/... ./internal/environments/...` passes.

- KV create response's doubled `bad request: bad request body:` prefix (`lego/backend/internal/keyvalue/rest.go:159`): cosmetic only — field, code, and status are correct; noted, not filed.

**DONE 2026-10-20 (loopx w4).** The project-create grouping transaction (`lego/backend/internal/projects/service.go`) mapped an inline-environment conflict through `store.MapError`, which keeps the class but drops the name. The rejection stays atomic (the error aborts the grouping tx, as probed live at filing).
