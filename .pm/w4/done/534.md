# 534 — A deploy of a missing image tag fails with "image metadata request returned status 404", naming neither the image nor the fix

Why: a typo'd tag is the most common image-deploy mistake. bex now fails it quickly (26 s), but the deploy row, the `deploy_ended` event and the dashboard all show the registry client's raw error. It does not say which image, that the tag or repository was not found, or what to check. The startup-failure path already explains itself in plain words (the w4/m243-era `/bin/sh` message), so this one is the odd one out.

**Severity:** minor (copy; the failure is correct and fast) · **Estimate:** 30m · **Worker:** worker4 · **Status:** done

- **Source:** live `/qa-find-bugs w4`, production, 2026-11-06 23:03–23:04 UTC, round 204, pin `a3fcf1d5e` (`9f8c280144a5`), workspace `bex-canary`. Same probe as w4/533.
- **Probe:** free image web service `qa-20261106-bt204` (`srv-dbn5on90k25c7383pvog`, deleted afterwards), `POST /v1/services/<id>/deploys {"imageUrl":"docker.io/traefik/whoami:qa-no-such-tag-204"}`.
  - Deploy `dep-dbn5pjp0k25c7383pvq0`: `update_failed` at 26 s with `failureReason: "image metadata request returned status 404"`.
  - The `deploy_ended` event carries the same text.
  - Contrast, round 180: a Docker Command naming a missing `/bin/sh` produced "container could not start: the startup program "/bin/sh" does not exist in this image. The program never ran, so there is no application output in the logs. A Docker Command runs through /bin/sh -c, so clear the Docker Command to use the image's default program, or use an image that includes /bin/sh."
- **Root cause:**
  - `lego/operator/internal/registry/image_config.go:64-67`: `statusFailure` builds `"%s returned status %d"`. For the metadata read, `what` is `"image metadata request"` (`:324`); for the token step it is `"registry token request"` (`:234`).
  - `lego/operator/internal/controller/app_controller.go:712-714` passes that error unchanged to `r.fail(…, "ImageMetadataUnavailable", err)`, whose `err.Error()` becomes the Ready message and the deploy row's `failureReason`.
  - The plain-language startup diagnosis lives in `app_controller.go:6060-6080` and has no counterpart for registry refusals.
- **Fix — target behavior:** a definitive registry refusal names the image reference and the likely cause, in the same style as the startup diagnosis:
  - **404 / manifest unknown:** "The image `docker.io/traefik/whoami:qa-no-such-tag-204` was not found in its registry: the repository or tag does not exist. Check the image URL and tag, or deploy a digest that exists."
  - **401 / 403 (no credential, or a credential the registry refused):** "The registry refused access to `<ref>`. If the image is private, add a registry credential for `<host>` to this service."
  - **429 / 5xx** stay transient and retried, as today (w4/m243 t008, w5/176). If they exhaust, they say the registry is unavailable or rate-limiting, not that the image is missing.
  - Never include registry response bodies or tokens.
- **Blast radius:**
  - `statusFailure` has 2 callers (`image_config.go:234` token, `:324` metadata).
  - `ReadImageConfig` has 2 callers (`controller/image_network.go:192` built image, `:205` external image).
  - The message reaches REST `failureReason`, GraphQL/MCP deploy `failureReason`, the `deploy_ended` event, webhooks and the dashboard deploy row. They all read the one field, so one change covers them.
  - Keep w4/162's pull-path wording and classification as they are.
- **Unverified:**
  - The 401/403 wording, which was not probed (it would need a private image).
  - Whether the dashboard row truncates a longer message.
- **Render:** a missing image fails the deploy with a message naming the image and that it could not be pulled.
- **Dedupe:**
  - w4/162 (done) made a missing tag fail fast on the pull path.
  - w5/176, w8/201 and w4/m243 t008/t013 (done) fixed the mechanisms behind the 429 and 307 variants of this same string, not its wording.
  - `grep -rli "metadata request returned" .pm` finds no item on the message itself. Not in `DO_NOT_DO.md`.
- **Cleanup:** see w4/533.

- **Closed 2026-11-08 (loopx w4):** the registry client now types its definitive refusals: `registry.RefusedError{Status}` from `statusFailure`. The Error() text is unchanged, and 429 and 5xx stay `TransientError` and are retried.
  - At the pre-dispatch metadata read, `imageRefusalError` names the requested image reference and the fix.
  - **404:** "the image `<ref>` was not found in its registry: the repository or tag does not exist. Check the image URL and tag, or deploy a digest that exists".
  - **401/403:** "the registry refused access to the image `<ref>`. If the image is private, add a registry credential for `<host>` to this service".
  - **Other statuses:** the image and the HTTP status.
  - No registry body or token is included. One message feeds the deploy row, `deploy_ended`, webhooks and the dashboard.
  - Tests: `TestImageRefusalNamesTheImageAndTheFix` and `TestStatusFailureTypesARefusal`. The controller suite (envtest) and the registry suite pass.
  - The 401/403 wording was not replayed live.
