# Editing an existing CIDR rule drops focus after one keystroke in Postgres and Key Value

Why: an ordinary CIDR correction removes the focused input and discards subsequent keystrokes, preventing users from reliably editing a networking rule before saving it.

- **Severity:** major — interrupted editing and lost subsequent **unsaved** keystrokes. No persisted allowlist change or stored-data loss was observed.
- **Estimate:** 55m, including the shared editor's three production callers and regression controls; one inbox-sized dashboard fix.
- **Source:** live `$qa-find-bugs`, new continuous pass 2, **2026-09-21 America/Los_Angeles / 2026-09-22 UTC**, filed in w4 at the user's request. Journeys 11–12: managed Postgres and Key Value.
- **Goal linkage:** usable hosting controls under [ADR008](../../docs/ADR008-vision.md), [ADR009 access control](../../docs/ADR009-postgresql-management.md#access--connection), and [ADR021 networking](../../docs/ADR021-keyvalue-management.md). Both datastore ADRs specify external CIDR rules with descriptions; users must be able to edit those rules without the form dropping their keyboard input.

## Reproduction and durable evidence

These two routes were each reproduced **twice after fresh page loads**:

- Postgres: `https://dashboard.bex.co/databases/dpg-dap15ih4dm7c7390q790#access-control`.
- Key Value: `https://dashboard.bex.co/keyvalue/red-dap15v3bdpcs73f5eda0#networking`.

On each route:

1. In the allowlist editor, add `203.0.113.0/24` as a **local draft** rule. Do not click Save.
2. Click the existing-row CIDR input for rule 1, put the caret at the end, and press Backspace.
3. The input value becomes `203.0.113.0/2`, but the input no longer has focus; `document.activeElement.tagName` is `BODY`.
4. Type `4` on the keyboard. The input remains `203.0.113.0/2`: the next keystroke does not reach it.
5. Control: editing the existing row's description retains focus and the appended text. The Key Value control appended ` abc`; Postgres retained `qa control`.

**Expected:** Backspace changes the value while the same input retains focus/caret; the next `4` restores `203.0.113.0/24`. **Actual:** the first CIDR change removes the focused input, so continuous typing stops after one change. The description control does not fail this way.

**Evidence:** `.playwright-mcp/qa-keyvalue-5.png` and `.playwright-mcp/qa-databases-6.png`, both checked to exist before filing. These local, gitignored screenshots support the visible states; the steps and focus observations above are the durable interaction record. No allowlist Save was clicked.

## Root cause: the editable value is part of the row identity

`dashboard/src/common/components/ip-allow-list-editor.tsx:43` initializes the draft. Its `replace` function at `:71–81` updates the selected field, and the CIDR input at `:104–106` calls it on every change. The containing row at `:100` uses ``key={`${index}-${entry.cidrBlock}`}``. Thus changing `203.0.113.0/24` to `203.0.113.0/2` changes the row's identity. Description edits at `:113–115` do not change that key, which predicts the working control.

The actual installed framework path was inspected, not inferred from the symptom. `dashboard/yarn.lock:10345–10346` and `:10512–10513` pin React DOM and React **19.2.3**. In `dashboard/node_modules/react-dom/cjs/react-dom-client.production.js`:

- `updateSlot` at `:3503–3518` compares the new element key to the old fiber key and returns null on this mismatch.
- Array reconciliation at `:3622–3648` leaves the positional pass. It maps remaining old children by key (`:3319–3325`, `:3684`) and looks up the new key (`:3551–3575`). That key is absent, so `updateElement` creates a new fiber at `:3389`.
- Remaining old fibers are queued for deletion at `:3710–3713` through `deleteChild` (`:3304–3309`). Host deletion at `:9199–9231` removes the old row's DOM subtree.

The focused input belongs to the removed subtree; the live probes measured focus on BODY afterward. This is a row remount on a local change, not an observed poll reset or network error. Dependency paths establish the mechanism and are not edit targets.

## Scope, consumers, and the fix

The exhaustive `<IPAllowListEditor` usage search found **three production callers and one test mount**:

| Production caller | Entry surface | Server-list reset key |
| --- | --- | --- |
| `features/databases/components/access-control-panel.tsx:57` | `routes/databases.$databaseId.tsx:320`, `#access-control` | The containing `AllowListSection` at `:40` |
| `features/keyvalue/components/key-value-networking-panel.tsx:44` | `routes/keyvalue.$keyValueId.tsx:232`, `#networking` | `:45` |
| `features/services/components/service-networking-panel.tsx:54` | `routes/services.$serviceId.settings.tsx:322`, `#networking` | `:55` |

Paths in the table are under `dashboard/src/`. Service Settings gates this panel through `publiclyRoutable` (`services.$serviceId.settings.tsx:85`, `:306`; `features/services/lib/service-type.ts:127`), which excludes private services, background workers, and cron jobs. The known eligible types are **web services and static sites**. `routes/static.$serviceId.settings.tsx:6–17` delegates to the same settings page. `common/lib/render-alias.ts:13–20` maps `/d` to `/databases`, `/r` to `/keyvalue`, and `/web`, `/worker`, `/pserv`, `/static`, and `/cron` aliases to `/services`; `:55–73` preserves subpath/query/hash. The actual resource type controls panel visibility regardless of a service alias's spelling. The environment allowlist uses a separate editor and is not a fourth caller.

Give each editor draft row one stable local identity, allocated when the row is initially seeded or added. Preserve it through field edits, moves, and removal of neighboring rows. Key the row by that identity. Index alone is insufficient because `move` (`:83–88`) reorders rows; CIDR and freshly generated render-time values also cannot serve as stable identity. Keep the fix in the common editor and its tests, covering every caller above without changing shared Input behavior.

**Consumer constraint:** keep local identities out of the public data shape. `common/lib/ip-allow-list.ts:1–7` defines `{cidrBlock, description}` and compares lists with `JSON.stringify`. The editor passes `draft` to `onSave` at `:196`. `features/databases/hooks/use-access-control.ts:74`, `features/keyvalue/hooks/use-key-value-networking.ts:46`, and `features/services/hooks/use-service-networking.ts:23` forward those entry objects directly as GraphQL variables. `graphql/schema-types.ts:852` and `lego/backend/internal/gqlutil/gqlutil.go:314–320` declare input fields `cidrBlock` and `description` only. Adding an enumerable local ID to the current public draft would also corrupt dirty comparison and leak an unsupported input field. Use an editor-local row wrapper/identity and project the ordered plain entries for comparison, validation, and Save.

**Existing behavior to preserve:** the callers deliberately reset their editor when the authoritative server list changes, including after successful Save. Retain that policy; an unchanged poll must not reset a draft merely because an array instance is new. All three save hooks catch errors, display the existing message, and return false; retain the draft for correction/retry and keep Save disabled while saving. This fix does not change ACL enforcement, datastore publication, empty-list meaning, authorization, or REST/GraphQL/MCP contracts.

**Pre-settle and adjacent classes:** datastore queries use cache-and-network with `errorPolicy: "all"` and initially normalize absent data to `[]` (`use-access-control.ts:36–64`, `use-key-value-networking.ts:24–41`). Keep their existing loading/server-list reset behavior; the reproduced failure occurred after a local row existed. Query-loading/conflict policy is outside this fix. Forbidden, unauthenticated, not-found, timeout, and failed-save handling stay on their existing paths; no lookup or error classification changes and no new existence disclosure.

## Closed 2026-09-22

Fixed in the shared editor, as the note scoped it. Each draft row now carries a stable editor-local `id`, allocated when the row is seeded or added and preserved through field edits, moves, and neighbour removal; the row is keyed by that id.

The identity is a **wrapper** (`{ id, entry }`), not a field on the entry, for the reason the note spelled out: `IPAllowListEntryDraft` is the wire shape — the three save hooks forward these objects straight into GraphQL variables, and `ipAllowListEntryKey` compares them with `JSON.stringify` — so an id on the entry would corrupt the dirty check and send an input field the schema does not declare. `draftEntries` projects the ordered plain entries, and dirty, validation and `onSave` all read that projection. A test asserts the saved payload's keys are exactly `cidrBlock` and `description`.

One deviation worth recording: ids are **derived from the current rows** (`max(id) + 1`) rather than held in a `useRef` counter. The ref version worked, but the repo's React-compiler lint correctly rejects reading a ref during render, and the lazy state initializer runs at render time. Deriving keeps `add` pure and still never reuses an id after a removal.

The callers' server-list reset policy is untouched — they remount the editor via `key={ipAllowListEntryKey(...)}`, so the seeded ids are allocated fresh per authoritative list, exactly as before.

Coverage in `ip-allow-list-editor.test.tsx` (11 tests, up from the one that only checked accessible names), all using **sequential keyboard input** rather than a one-shot fill, which is precisely why the old test could not have caught this. **Mutation-checked: restoring the `${index}-${entry.cidrBlock}` key fails 7 of them.**

- The live probe itself: Backspace leaves `203.0.113.0/2` **in the same focused element** (asserted against `document.activeElement`, the thing the hunt measured on BODY), and the following `4` restores the complete CIDR.
- A whole CIDR retyped one keystroke at a time, with the row's description pairing intact afterwards.
- A **freshly added** row, not only a server-seeded one.
- Reorder plus neighbour removal, then editing the moved row — the case a positional key breaks — with order, pairings and payload shape asserted on Save.
- Invalid/duplicate CIDRs stay editable and focused while Save is blocked; `[]` is still submitted for an intentionally emptied list; a reverted edit returns the form to clean; a failed Save retains the draft; nothing is sent before Save; and the description control (the live control that passed) still works.

`yarn tsc --noEmit`, `yarn lint` and the full `yarn test` are green (437 files, 3621 tests). No change to ACL enforcement, datastore publication, empty-list meaning, authorization, or the REST/GraphQL/MCP contracts.

**Owed to a live pass:** the note's DoD is a browser reproduction on disposable Postgres and Key Value fixtures. These are jsdom tests against the real component and the real React 19.2.3 reconciliation the note traced, so they prove the mechanism is gone — but not the deployed page. The note's remaining "Unverified" list (live web/static settings entrypoints, editing an already-persisted rule, Save success/failure live) is covered by the regression tests above at the component level and still owed at the browser level.
