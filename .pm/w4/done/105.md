# Service create with an inaccessible repo URL succeeds; the build then fails with git's misleading auth error

Why: the source-edit path fails fast with a clear 400 ("repository is not accessible … connect its owner … or use a public repository"), but create accepts the same URL and the failure surfaces minutes later as `could not read Username` — which reads as a platform auth problem, not a bad URL.

## Record

- Severity: minor
- Repro: 1. `POST /v1/services {"name":"qa-p86-events","type":"web_service","repo":"https://github.com/render-oss/render-examples-go-gin"}` → 201 (`srv-dao3c8bs0ils73bgpb9g`); that repo is 404 on the GitHub API and the org lists no such repo. 2. first deploy → `build_failed`, `failureReason`: "build failed in the clone step:\nfatal: could not read Username for 'https://github.com': terminal prompts disabled". 3. manual redeploy → identical failure. Live 2026-09-20, 2/2. Control: the same shape with `https://github.com/render-examples/go-gin-web-server` cloned fine (it failed later at docker build — no Dockerfile at root, fixture config, not product). Both fixtures deleted (DELETE 204, re-GET 404).
- Expected / Actual: create returns the existing source-edit 400 and creates nothing / 201, then minutes later a clone failure that misdirects toward auth.
- Root cause: `lego/backend/internal/apps/service.go:3556-3560` — `SetSourceAndRegistryCredential` is the only production caller of `GitHub.ValidateRepo` (exhaustive grep: one caller); `Create`/`create` (`service.go:1778/1801`) validates name, secret files, environment, billing, and duplicates but never repo accessibility, so an inaccessible URL sails into a build whose clone stderr passes through unclassified (the operator's classify step maps the container to "clone" only, `lego/operator/internal/build/build.go:645`).
- Fix: in `create`, after spec resolution, call `s.GitHub.ValidateRepo(ctx, tenantID, desired.Repo)` under the same `repo != "" && s.GitHub != nil` guard shape, returning the 400 before any k8s/store write. REST/GraphQL/MCP creates share `apps.Service.Create`, so one call covers all three; the dashboard create form surfaces the 400 as-is. Target behavior: POST with an inaccessible repo returns the existing ValidateRepo message and creates nothing.
- Blast radius: create path only; `ValidateRepo` is safe when GitHub is off or the host is not github.com (returns nil, `lego/backend/internal/github/service.go:1028-1031`). Verify whether the blueprint/stack `applyCreate` path funnels through `create()` (gains the same gate — desired) or needs its own call.
- Adjacent classes: private-but-ungranted repos get the same clear 400 as the edit path — no existence oracle (the message does not distinguish nonexistent from ungranted); a transient GitHub outage fails create loudly with "checking … access" instead of failing the build (the tradeoff the edit path already makes).
- Unverified: why the builder's fetch of a missing repo drew a 401-style Username prompt while an identical local `git fetch` 404s "Repository not found" — stale CloneSecret stamped vs GitHub challenging builder egress; needs build-pod forensics. It does not change the fix.
- Render: render.com rejects unknown repos at service creation (source-connect step); bex's edit path already matches that, create lags it.
- Estimate: 30m

## Resolution (2026-09-21)

Done as filed. `create` now calls `s.GitHub.ValidateRepo` under the same `repo != "" && s.GitHub != nil` guard the edit path uses, returning the existing 400 before any k8s or store write. REST, GraphQL and MCP creates all share `apps.Service.Create`, so one call covers all three, and the dashboard surfaces the 400 as-is.

Placed **after** the duplicate-name check and before the first write: a name conflict is the cheaper, more specific answer and still wins, and a refused create leaves nothing behind — asserted in the test, since failing before the write rather than during the build is the whole point.

**The note's open question, answered: the blueprint path does NOT inherit the gate.** `applyCreateWithFields` (`deploy.go:2651`) reaches `createFromStack`, not `create()`, so a manifest declaring an inaccessible repo still fails at clone time. That is left as-is deliberately rather than extended on the spot: a blueprint sync applies many services at once, so failing the whole sync on one GitHub hiccup has a materially different blast radius from failing one interactive create, and the note scoped itself to "create path only". Worth a separate decision if a manifest author hits it.

The accepted tradeoffs are the edit path's, inherited unchanged: a private-but-ungranted repo gets the same message as a nonexistent one (no existence oracle), and a GitHub outage now fails the create loudly instead of failing the build later.

Covered by `TestCreateRefusesAnInaccessibleRepository` (refusal + exactly one ValidateRepo call + nothing written) and `TestCreateStillAcceptsSourcesValidateRepoHasNoOpinionAbout` (accessible repo, image-backed create never consulting GitHub, GitHub unwired). Mutation-spot-checked. Not re-probed live.
