# 517 — Regression of w4/m230: a Free wake's `service_woken` lands ~34 s after the woken service already answered 200, and the phase reads `Deploying` meanwhile

Why: w4/m230's definition of done says each `service_woken` timestamp lies within 2 s of that cycle's first 200. Live, the event and the `Running` phase arrived 34 s after the woken instance had already served a request. Activity, webhooks and the API then put the wake at the wrong moment, and for half a minute the service reads `Deploying` while it serves.

**Severity:** minor (timing and status truthfulness; no failed request) · **Estimate:** 45m · **Worker:** worker4 · **Status:** done

- **Root cause (partially traced):**
  - The woken timestamp comes from `availabilityEdgeAt(obs.ReadyTransitionAt, previousChangedAt, obs.At)` (`lego/backend/internal/store/event_facts.go:575-580`, used at `:619-627`).
  - `ReadyTransitionAt` is the App's `Ready` condition `LastTransitionTime` (`lego/backend/internal/store/reconciler.go:2120-2124`). Hibernation sets `Ready=False` (`lego/operator/internal/controller/app_controller.go:3350`), so on wake that time is when the operator writes `Ready=True` and `phase: Running`. If the time is unusable, the fallback is the noticing pass `obs.At`.
  - The w4/m230 fix (`7ed5b463a`) assumed the App's Ready edge marks when the instance came back. But the activator's hold path serves a held request straight from the ready pod (`lego/operator/cmd/activator/hold.go:274`, w8/178), before the operator has written `Ready=True`. So the first 200 precedes the App's Ready edge.
  - The operator watches Pods and Deployments and requeues a waking App every 5 s (`app_controller.go:7312-7314`, `release_plan.go:261` `wakeReadyPoll`). The 34 s gap is therefore not explained by the watch alone. Which of these holds is **not verified**:
    - (a) the operator's Ready/Running write after a wake really lags the pod's readiness by ~30 s, for example waiting for the public route to move off the activator;
    - (b) the backend's observation pass ran ~34 s late and `availabilityEdgeAt` fell back to `obs.At` because `ReadyTransitionAt` was zero or not after the checkpoint.
- **Fix:**
  - Target: a wake's `service_woken` is stamped within 2 s of the first instant the woken instance answers a request, as m230 promised. GraphQL/REST phase reads `Running` (not `Deploying`) from that moment, or at most within the same 2 s.
  - First pin the mechanism. During a wake, record the App's `Ready` and `Serving` condition `lastTransitionTime`, the pod's `Ready` condition time, the activator log line for the held request, and the backend observation time. Then either:
    - make the operator write `Ready=True`/`Running` from the pod's Ready time (and stamp it with the pod's time), or
    - have the backend take the edge from the earliest pod-Ready time it can read.
  - Keep m230's other guarantees: no `server_available`/`server_failed` on a wake, the outage control still pages, and a Resume still records `service_resumed` (see w4/508).
  - Add a store test: a woken App whose `Ready` `lastTransitionTime` is after the first served request still stamps the wake no later than that request. Also an operator or activator test that the Ready edge follows pod readiness on the wake path.
- **Blast radius:** `availabilityEdgeAt` has 3 callers: `event_facts.go:626` (the woken/resumed phase edge), `event_facts.go:634` (`server_failed`/`server_available`), and `datastore_event_facts.go:261` (Postgres/Key Value availability edges, w4/196). Changing the helper moves all three, so prefer fixing the input (`ReadyTransitionAt`) on the wake path only. The outage-pair tests (`TestPGObservedCrashEdgeEmitsExactlyOnePair`) and the datastore edge tests stay as regression controls.

- **Closed 2026-11-05 (loopx w4):** mechanism (a), found by reading the operator. On the pass that first sees the woken pod Ready, `discoverPrivatePorts` ran `scanPrivatePorts` (`private_ports.go`) before `markRunning`. After a sleep longer than `privatePortScanInterval` (2 min) the rescan was always due, and the full TCP sweep runs up to `portDetectTimeout` (15 s). The production manager has only 2 App reconcile workers, all doing those sweeps, so the pass could also queue behind another App's. Fixes:
  - (1) A due rescan of a revision already scanned waits until the App is Running; a wake keeps its revision, and a new revision still scans at once (`TestScanPrivatePortsWaitsForRunningOnAKnownRevision`).
  - (2) The Ready=True that ends an AutoHibernated/Suspended park takes its `lastTransitionTime` from the earliest Ready time of a current-revision pod, never before the park and never after now (`wakeReadySince`, `TestWakeReadyIsStampedFromThePod`). bex-api stamps `service_woken`/`service_resumed` from that time.
  - Operator controller suite (envtest) and lint pass.
  - Residual risk: if bex-api checkpoints a `Deploying` observation after the pod became Ready, `availabilityEdgeAt` still falls back to the observation time. Fix (1) shrinks that window to one pass. The live replay of m230's 2 s bound follows the release.
