# 378 — Apex domain setup never shows the A-record fallback value ADR005 says it prints

Why: when a registrar has no ALIAS/ANAME support (common), the apex setup says only "create an A record for @ using the IP addresses the Target resolves to". It shows no address and gives no warning that the address can change. ADR005 records that bex prints the currently resolved edge addresses and names ALIAS as the form that survives a change. A user left to `dig` an IP pins a record that silently breaks when the edge moves.

**Severity:** minor. **Estimate:** ~40m. **Source:** live `/qa-find-bugs w4` loop run e5f3, 2026-10-20 UTC, `muse.env`, workspace `bex-canary`. Fixture Free image service `qa-20261020-e5f3-who` (`srv-dbbhhahq56vc73bn8btg`); the test claim was deleted in the same visit.

## Probe (production)

1. Service → Settings → **Add Custom Domain** `qa-e5f3-bextest.org`. The "Domain added — set up DNS" dialog shows:
   - `Type ALIAS · Host @ · Target qa-20261020-e5f3-who.onbex.co`;
   - the guidance paragraph above, with no IP anywhere;
   - an auto-added `www.qa-e5f3-bextest.org` CNAME → same target, "redirects to qa-e5f3-bextest.org".
2. `GET /v1/services/srv-dbbhhahq56vc73bn8btg/custom-domains` returned, for the apex, `{"type":"ALIAS","name":"@","value":"qa-20261020-e5f3-who.onbex.co"}`. No address field exists on any surface; GraphQL `CustomDomainFields.dnsRecord` is `{type,name,value}` (`dashboard/src/features/services/api/custom-domains.graphql:24-28`).
3. `dig +short qa-20261020-e5f3-who.onbex.co A` → `49.12.20.236`. That is the value a user without ALIAS support needs, and bex never shows it.
4. Controls, correct:
   - the www ↔ apex pairing is created;
   - deleting the apex says it removes both pending claims, and it does (list empty).

## Root cause

- The copy `services.domainDnsApexGuidance` (`dashboard/src/features/services/locales/en.ts:1702-1707`), rendered at `dashboard/src/features/services/components/custom-domains-section.tsx:348`, tells the user to resolve the target themselves.
- The domain view carries only the single traffic record. Nothing resolves or returns the edge addresses.
- `docs/ADR005-custom-domain.md:52` ("the `A` fallback value shown to a tenant is the platform host's currently resolved edge addresses, with ALIAS named as the form that survives an edge-address change") and `:96` ("bex prints the platform host's currently resolved edge addresses") landed in the same commit as this copy (`a8c215fdf`, w5/m137). The implementation stopped short of the record.

## Fix (target behavior)

- For an apex domain, the setup (the add dialog and the expanded DNS row) shows the fallback `A @ <address>` rows. These are the platform host's addresses resolved by bex-api at read time, one row per address, each with Copy.
- The rows are labeled as current edge addresses that can change, with ALIAS/ANAME/flattening named as the record that keeps working.
- Expose the addresses as an additive field on the GraphQL domain view, for the dashboard's consumer. REST/MCP keep Render's shape; whether they also carry the field is the parity call ADR005 §additive read fields already sets out.
- A resolution failure shows the guidance without addresses. It does not show an empty or stale value.
- Non-apex domains are unchanged (single CNAME).
- Alternative, if product decides not to print addresses: correct ADR005:52 and :96, and make the copy warn that an A record pinned to today's address can break. One of the two must change; today they contradict each other.

## Acceptance

- Re-add an apex test claim. The dialog and the DNS row show `A @ 49.12.20.236` (or whatever the host resolves to at that moment) with the change caveat. The www row is unchanged. Delete the claim (both rows gone).
- Tests: the apex view carries addresses from a fake resolver; a resolver error yields none and the guidance still renders; the subdomain view has none.
- Dashboard `yarn lint`/`yarn test` and the backend tests for the domain view pass.
