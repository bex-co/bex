# A repo-backed deploy whose trigger-time commit lookup fails stays commitless forever, even after its build ran and went Live

Why: Render's deploy list and Events always name the commit a Live deploy runs; a Live deploy with no commit leaves the customer unable to tell what code is serving.

Source: live `/qa-find-bugs w4` loop run, round 4, 2026-11-01 UTC (`muse.env`, QA workspace `bex`). Severity: minor-to-major (provenance missing on a deploy that was Live and served as a rollback target).

## Repro (https://dashboard.bex.co)

1. New Service > Web Service > Public Git URL `https://github.com/bex-co/bex`, branch `main`, Root Directory `examples/hello-go`, Docker, Free (fixture `qa-20261101-deploys`, `srv-dbk206lcqbus73fijhk0`, deleted in-run).
2. While the first deploy builds, cancel it (Cancel > Proceed).
3. Manual Deploy > Deploy latest commit (`dep-dbk218dcqbus73fijhmg`); it reached Live (~5 min, later Deactivated).
4. Settings > Deploy Hook > POST the hook URL (`dep-dbk21ntcqbus73fijhng`).

Round 1's control (a same-repo create, `srv-dbk0i123o9ns73fsikjg`) read `==> Building from https://github.com/bex-co/bex@7730772` with the full SHA in FETCH_HEAD.
- Control scan (read-only, same page): `GET /v1/services/{id}/deploys` for the 9 git-backed web services listed showed no commitless deploys (for example `beancount-cms-v2` `manual:live` has a commit, 1/1). Only the image-backed private service `crypto-price-clickhouse` is commitless on every row.

**Expected:** every deploy of a git-backed service records the commit it built, as Render's does, including when the trigger-time lookup failed. **Actual:** the row stays commitless for its whole life (Live, Deactivated, and as a rollback target).

## Cause (partly traced)

`lego/backend/internal/deploys/service.go` `resolveCommit` (~L874-903) is best-effort by design (w9/001): any lookup error or `!ok` returns the zero `CommitInfo`, so `CreateDeploy(…, commit, …)` (~L817) writes a row with no commit. The build then follows the branch (w5/138: "An unresolved tip still builds the branch"; w5/152 chose "fall back to building the branch when a fresh lookup is refused" because the unauthenticated lookup shares GitHub's 60-requests-an-hour-per-IP limit). Nothing later backfills the row from what the clone checked out.

The canceled first deploy (`dep-dbk206lcqbus73fijhkg`) and the manual deploy, created about a minute apart, both missed; the hook deploy about 5 minutes later resolved. That is consistent with a transient refusal, but the refusal itself was not observed.

## Fix

Target behavior: a deploy row ends up naming the SHA its build checked out. Choose and record one in the task:

- (a) the operator/clone step reports the checked-out SHA and the deploy row is stamped when the build settles if resolution was empty. REST, GraphQL, MCP and the dashboard all read the same `store.Deploy` commit, so one write serves all four, plus the build log's `Building from …@<sha>` line. This fixes provenance for builds that already ran.
- (b) a failed trigger-time lookup retries or queues before the clone, never starting an unpinned branch build. This keeps builds pinned.

- **Blast radius:** `resolveCommit` callers are every trigger path (manual, hook, API, rollback label, new_commit, create's first deploy, Blueprint redeploy); grep the exact count before changing. Rows for image-backed services must stay commitless ("omitted, not faked"). A deploy that follows a moved branch must record the SHA it really built, not a stale resolved one.
- **Adjacent classes:** GitHub 404/private/forbidden lookups (the `ValidateRepo` precedent, w4/105) must not become an existence oracle; an unauthenticated rate-limit refusal is the likely transient class.
- **Unverified:** why the lookup failed at 9:31–9:32 PM local (GitHub anonymous rate limit vs timeout vs singleflight/cache; needs bex-api logs for `srv-dbk206lcqbus73fijhk0`); whether the operator's clone exposes the checked-out SHA to the reconciler; the scan covered only the first 12 services of the list, in one run.
- **Render:** the Deploys list and Events always show the deploy's commit for git-backed services.
- **Estimate:** 1h30m (operator report + store stamp + tests); promote to a milestone if sized as >1h across tasks.

## Dedupe

grep of `.pm` for `resolveCommit`/`ResolveCommit`/"carries no commit"/"rate limit … github" found w9/001 (best-effort by design), w4/m108 t004 (Public Git URL deploys carry a commit; its DoD assumes the lookup succeeds), w5/138 and w5/152 (an unresolved tip builds the branch; 10s memo). None records the commit being backfilled once the build ran, so this is the residual those items leave, not a duplicate.

## Done 2026-11-02 (loopx w4)

Option (a) via the image the build already stamps: the clone step writes the checked-out SHA into the image's `org.opencontainers.image.revision` label, which the operator caches in `status.imageRevision`. The reconciler's live close now backfills an empty `deploys.commit` from it (`builtCommit`, `RanImage.Commit`, `TransitionDeploy`), only for repo-backed services, only when the cached label is for the image that ran, and never over a recorded commit. One write serves REST, GraphQL, MCP and the dashboard. Test `TestLiveCloseBackfillsAMissingCommitFromTheBuiltImage`. Not done: the commit message/author time stay empty on a backfilled row, and the trigger-time lookup is unchanged (cause of the original refusal unobserved).
