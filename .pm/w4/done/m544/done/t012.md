## Objective

A session on the default `registries` tier fetches the exact patch its `PYTHON_VERSION` names (t006), instead of falling back to the line's baked patch, because the egress catalog admits the host Docker Hub serves layers from.

## Context

- The t011 replay on 2026-11-22 (pin `19fdb46f1758`): with `PYTHON_VERSION=3.11.9`, every fetch on the `registries` tier, in a session and in a snapshot build, failed `curl: (6) Could not resolve host: production.cloudfront.docker.com`, and the session ran 3.11.18 with the named fallback. A `full`-tier session, whose traffic leaves through the egress proxy, fetched and ran exactly 3.11.9, so the fetch itself works.
- Docker Hub answers a blob read with a `307` to `production.cloudfront.docker.com` (seen from this host on 2026-11-22, and in w8/201 and ADR104 since 2026-10-25), the pull host Docker's allowlist names ([docs.docker.com/desktop/setup/allow-list](https://docs.docker.com/desktop/setup/allow-list/), read 2026-11-22). The catalog (`registryDomains`, `lego/backend/internal/sessionegress/policy.go`) named only `production.cloudflare.docker.com`. t006's tests used an offline fixture registry, which serves blobs without a redirect.

## Steps

1. Add `production.cloudfront.docker.com` to `registryDomains`, keeping `production.cloudflare.docker.com`.
2. A test that every phase's policy (setup, agent, build) and the default catalog admit Docker Hub's token service, registry and blob host.

## Files

- `lego/backend/internal/sessionegress/policy.go`, `policy_test.go`

## Acceptance criteria

- [x] `TestDockerHubPullHostsAreInTheDefaultRegistryCatalog` passes, and fails with the host removed.

## Outcome

Done 2026-11-22. `registryDomains` names `production.cloudfront.docker.com`; the new test fails on the old catalog (setup, agent and build policies and `DefaultRegistryDomains()` each lack it). The production check (a `registries`-tier session with `PYTHON_VERSION=3.11.9` runs exactly 3.11.9) is t011's, once the pin carries the fix.
