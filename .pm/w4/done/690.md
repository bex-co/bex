# 690 — A rollback's `deploy_started` event says `rollback: true` but never names the deploy it rolled back to: Render's `trigger.rollbackTargetDeployId` is never sent, though the deploy row records `rollbackOf`

Why: Render's event trigger object carries `rollbackTargetDeployId` ("Deploy ID that was rolled back to"). An integration that reads events or follows webhooks to `GET /v1/events/{id}` can tell a rollback happened, but not which release it restored. bex already knows the target: the rollback deploy row answers `rollbackOf`.

- **Source / severity / estimate:** live `/qa-find-bugs w4` round 504, 2026-11-16 09:57–10:03 UTC, pin `f114fdd9f5a6`, workspace `bex-canary`. **Minor:** a Render-parity gap in an optional field; nothing is lost. ~40m.
- **Probe** (a Free image web service, `qa-20261116-r504-web`, `docker.io/traefik/whoami:v1.10`, deleted afterwards):
  - Create the service with `WHOAMI_NAME=v1`; the first deploy `dep-dbtd79h9hcnc73acimpg` is live in 43 s.
  - `PUT …/env-vars/WHOAMI_NAME {"value":"v2"}`: no deploy follows, as on Render.
  - `POST …/deploys {}` → `dep-dbtd7ru004dc73ajmhdg` is live, and the body serves `Name: v2`.
  - `POST …/rollback {"deployId":"dep-dbtd79h9hcnc73acimpg"}` → `dep-dbtd856004dc73ajmhk0` is live and serves `Name: v1`, the target's recorded environment (ADR018's rollback row).
  - `GET /v1/services/{id}/deploys/dep-dbtd856004dc73ajmhk0` answers `trigger: "rollback"`, `rollbackOf: "dep-dbtd79h9hcnc73acimpg"`.
  - Three surfaces give that deploy's `deploy_started` (`evt-d79ro1p24lu7d0uhgsvp`) the same trigger object, and none of them carries `rollbackTargetDeployId`:
    - `GET /v1/services/{id}/events`;
    - `GET /v1/events/evt-d79ro1p24lu7d0uhgsvp`;
    - MCP `get_service_event {workspaceId, id}`.

    The object they all return:

    ```json
    {"firstBuild": false, "envUpdated": false, "manual": false, "deployedByRender": false, "clearCache": false, "rollback": true, "deployHook": false, "user": {"id": "usr-d9a5qasbt3bc73fiphn0", "email": "puncsky@gmail.com"}}
    ```

- **Cause:**
  - The deploy-row projection selects the deploy's `trigger`, `triggered_by` and `clear_cache` but not `rollback_of` (`lego/backend/internal/store/events.go:342`, `:354`, `:389`). Its two readers are `ListServiceEvents` (`:585`) and `GetServiceEvent` (`:903`), and `ServiceEventRow` has no such field (`:73`).
  - `deployTrigger` sets only booleans (`lego/backend/internal/events/service.go:1509-1528`). The `Trigger` type (`:637`) and Render's wire shape `renderTrigger` (`events/rest.go:321-333`, mapped at `:386-396`) have no target field.
  - GraphQL's trigger type stops at `rollback` (`events/graphql.go:56`).
- **Fix:**
  - Select the deploy's `rollback_of` in the started-phase projection.
  - Carry it through `deployTrigger` as `RollbackTargetDeployID`.
  - Serialize it as `rollbackTargetDeployId`, omitted when empty, on `deploy_started` of a rollback deploy. It is the same `dep-` id the deploy row answers.
  - Add the same field to the GraphQL trigger type.
  - Pin it with an events test: a rollback's `deploy_started` names its target, and a non-rollback's omits it.
- **Aliases:** `toRenderEvent` (`events/rest.go:359`) serves every surface below, and GraphQL reads `toRenderEvent(e).Details` (`events/graphql.go:332`):
  - REST `GET /v1/services/{id}/events` and `GET /v1/events/{eventId}` (`:553`);
  - MCP `get_service_event`, `list_events` and `list_service_events` (`events/mcp.go:104`, `:116`, `:152`).
- **Unverified (reasoned from code, not probed):**
  - **Two more trigger fields Render's object has that bex never sends:** `newCommit` ("Commit that triggered the deploy") and `updatedProperty`.
    - A git-push redeploy is stored as `new_commit` (`store/store.go:297`), so its event could name the commit.
    - No git-push deploy was run this round, so this is reasoned from `renderTrigger` alone. The fixer should decide whether to add `newCommit` in the same change.
  - The dashboard Events tab's wording for a rollback (it reads GraphQL).
  - Webhook payloads, which name the event id that clients then read through these same surfaces.
- **Render:** the public OpenAPI's deploy trigger object (`lego/backend/internal/api/openapi/render-public-api-1.json`) defines `rollbackTargetDeployId`, `newCommit` and `updatedProperty` beside the required booleans.
- **Done when:**
  - After the release pins the fix, the same journey's rollback `deploy_started` carries `"rollbackTargetDeployId": "<the target dep- id>"` on REST list and get, on MCP, and on GraphQL.
  - The first and the API-triggered deploys omit it.
  - Backend `go test ./...` passes.

**DONE 2026-11-16** — the started-phase deploy projection (list, by-id, and the `build_started`/`pipeline_minutes_exhausted` facts) selects `rollback_of`; `deployTrigger` carries it as `rollbackTargetDeployId` on a rollback and `newCommit` (the deploy's commit) on a git-push redeploy, both omitted otherwise, on REST, MCP and GraphQL (`DeployTrigger.rollbackTargetDeployId`/`newCommit`). `updatedProperty` stays unsent: bex records no per-property trigger.
