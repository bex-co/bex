# 651 — A dashboard load that meets a rollout's old/new pod overlap can still end on "Something went wrong": reload once, guarded, on Vite's `vite:preloadError`

Why: w4/m348 made a missing chunk answer `404 no-store`, so nothing poisons a cache any more and TanStack Router's one-shot reload recovers most loads. When several chunks of one load land on different pods during the few seconds of a rollout's overlap, the one-shot reload is already spent and the page ends on the error screen until the user clicks Try again.

- **Source / severity / estimate:** w4/m348's implementation report (2026-11-14), reproduced locally with two builds behind an alternating proxy: one load in that setup ended on "Something went wrong", and Try again recovered once the old server was gone. **Minor** (seconds per rollout). ~30m.
- **Fix:** listen for `vite:preloadError` (Vite's documented hook for a failed dynamic import) and reload the page once per build version, guarded by a `sessionStorage` key holding the build id so a persistent failure cannot loop. Keep w4/269's Try again and TanStack's own reload.
- **Tests:** a `vite:preloadError` event reloads once; a second one with the same build id does not; a new build id re-arms it.
- **DoD:** with two builds behind an alternating proxy (w4/m348 t002's harness), every load ends on the page, not the error screen.
- **Closed 2026-11-14 (/loopx w4):** `dashboard/src/common/lib/preload-error-reload.ts` listens for `vite:preloadError` and reloads once per build, guarded by the `bex:preload-error-reload` sessionStorage key holding the build id. A second failure from the same build stays put, and a newer build re-arms the reload. The event is not cancelled, because Vite would then hand the importer an undefined module, so TanStack's reload and w4/269's Try again are unchanged. `getRouter` installs it once in the browser. `vite.config.ts` stamps `import.meta.env.VITE_BEX_BUILD_ID` once per build; a production build was checked and carries the stamped id in its entry chunk. Tests: `preload-error-reload.test.ts` (reloads once, not again for the same build id, a new build id re-arms it, the event stays uncancelled). Dashboard `yarn lint` and `yarn test` pass (686 files, 7275 tests). **Local harness, which the DoD does not meet:** two builds behind a proxy, a fresh browser context per load. Strict alternation is deterministic: the entry chunk always lands on the other build, so every load stays an un-hydrated SSR shell, both with and without this change. With per-request random routing, about half the loads miss the entry chunk itself, which no in-page handler can catch. Among the loads that hydrated, 14 of 38 reached the page with the change, against 7 of 20 on a baseline pair without it. One extra reload does not help measurably when every request is a coin flip between two builds. A real overlap lasts seconds, so most loads see one stray chunk at most, which is the case this change covers. Live DoD replays after the next production deploy.
