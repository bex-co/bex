## Objective

When a member approves an OAuth client on the dashboard consent page (or a client is auto-accepted for the first time), bex-api records `GrantOAuthAccessEvent` in each workspace the member belongs to, after confirming the grant at Hydra.

## Context

- `dashboard/src/common/server-fn/hydra-consent.ts:510` `acceptConsent` is the only accept call; it runs on the interactive POST (around line 836) and the headless GET path (around line 664, trusted or `skip`/`skip_consent` clients, line 301).
- The revoke path already calls bex-api with the user's cookie: `hydra-connected-agents.ts:156` → `POST /v1/oauth/revocations` → `lego/backend/internal/cliauth/service.go:164` `recordRevocation` (session-authenticated humans only).
- bex-api can read Hydra's consent sessions: `oauthgrant.Revoker.Grants(ctx, subject)` (`lego/backend/internal/oauthgrant/oauthgrant.go:279`) returns `Grant{ClientID, Scopes, HandledAt}`; `BEX_HYDRA_ADMIN_URL` (`lego/backend/cmd/api/config.go:448`, used at `main.go:319`).
- Audit seam: `core.AuditEvent` + `audit.Service` `renderEvents` (`lego/backend/internal/audit/service.go`); w9/m452 needs the same "one row per current workspace" write, so reuse a shared helper if it has landed.

## Steps

1. Add `POST /v1/oauth/grants` beside `recordRevocation`: body `{clientId}`, session-authenticated humans only, bounded like the revoke.
2. bex-api confirms Hydra holds a consent session for (subject, client) handled within the last few minutes; otherwise it records nothing and answers 404 (no forged rows).
3. Record `GrantOAuthAccessEvent` (verb mapped in `renderEvents`) once per workspace the subject belongs to: actor the user, target the client, metadata `client_id`, `client_name` (Hydra's client name), `scopes` (space-joined). Never a token. Use a derived event id per (subject, client, handled_at, workspace) so a retried call records once.
4. In `acceptConsent`, call the route after Hydra's accept succeeds, only when Hydra did not `skip` (a remembered consent is not a new grant) and the client is not one of the platform's own sign-in clients (the bex CLI human client, `isPlatformHumanClient` in `cliauth`; the ops Grafana client). A failed call is logged and never fails the consent.

## Acceptance criteria

- [x] An approve records one row per workspace; a remembered consent, a refresh and a CLI device-flow login record none.
- [x] A `POST /v1/oauth/grants` for a client with no Hydra consent session records nothing (test).
- [x] An audit write failure never changes the consent's redirect.

## Out of scope

- `LoginEvent`/`LogoutEvent` (w9/m452); `source_ip`/`user_agent` (w9/m450).

## Done (2026-11-16)

- bex-api `POST /v1/oauth/grants` (`internal/cliauth` `recordGrant`, session-authenticated members only, the `{clientId}` body bounded like the revocation's) hands the report to `internal/oauthgrant` `Access.RecordGrant`. It lists the member's consent sessions at Hydra and records only when the newest one for the client was handled within `GrantWindow` (5 min, 1 min of clock skew tolerated) by a client without `skip_consent`; otherwise it records nothing and answers 404. `skip_consent` is the structural test for "the platform's own sign-in clients": only the operator's admin API sets it (the bex CLI, desktop, mobile, `bex-obs`, `bex-openstatus` in `scripts/auth-bootstrap-client.sh`), never a DCR registrant.
- One row per workspace of the member (`store.SubjectWorkspaceIDs`), written in one batch through the new fail-open `core.RecordAuditEvents` (the seam w9/m452 can reuse): verb `oauth.GrantAccess` (`core.AuditVerbGrantOAuthAccess`), actor the member (`session`), target `oauth-client:<client_id>`, target name Hydra's `client_name`, the newest consent's scopes in the new `audit_events.oauth_grant_scopes` column, `at` = Hydra's `handled_at`. The id derives from (subject, client, handled_at, workspace), so a retried report records nothing more. The existing `oauth_scopes` column could not hold them: its CHECK admits only the closed capability vocabulary, not `openid`/`offline_access`.
- Dashboard: `hydra-consent.ts` `reportGrant` posts after Hydra's accept succeeds, with the member's cookie, User-Agent and True-Client-IP (w9/m450's `ssrForwardedHeaders`, so the rows' `source_ip`/`user_agent` are the browser's), without holding the redirect (bounded to 3 s; bex-api writes the rows even if the dashboard stopped waiting), only when Hydra did not `skip` and the client is not `skip_consent` (in practice the human-decision path, plus a first grant to an `OAUTH_TRUSTED_CLIENTS` client, an empty list in production). A failed report is logged and the redirect is unchanged.
