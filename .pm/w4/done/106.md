# Activity calls an image deploy a "First build"; the Deploys surfaces call the same deploy "First Deploy"

Why: the same deploy reads two different words on two tabs, and on an `image`-runtime service the Activity wording asserts a build step that never ran — the cheapest kind of UI lie to fix, and it is the same class as `w6/m43`'s "worker shown the `$PORT` image hint" copy correction.

Found by live `/qa-find-bugs` 2026-09-21 pass 106 (w4-targeted, `muse.env` credentials), on `qa-20260921-img` — a Web Service created from **Existing Image** `docker.io/library/nginx:alpine`, since deleted.

Repro:

1. Create a Web Service with source **Existing Image** (no build stage exists for `runtime: image`).
2. Open `/services/<id>/deploys/<depId>` — the first deploy is labelled **"First Deploy"**.
3. Open `/services/<id>/events` — the same deploy's Activity row is labelled **"First build"**, under "Deploy started".

Captured Activity text: `Deploy started / In Progress / First build / by puncsky@gmail.com / Deploy dep-daodm212dbts73fi2jsg / docker.io/library/nginx:alpine`.

Two separate label vocabularies for one trigger:

- `dashboard/src/routes/services.$serviceId.events.tsx:73` — `if (trigger.firstBuild) return "services.eventsTriggerFirstBuild";` → `dashboard/src/features/services/locales/en.ts:3584` = `"First build"`. The comment above `triggerKey` (`:58-61`) records why this mapping is separate: `ServiceEventDetails.trigger` is a boolean-flag object while `Deploy.trigger` is a plain string, so the two surfaces derive their labels independently.
- `dashboard/src/features/deploys/locales/en.ts:116` = `"First Deploy"`.

Fix: render one word for one trigger, and pick the one that is true for every runtime. "First Deploy" is correct for both `image` and repo-backed services; "First build" is only ever correct when a build actually ran. The flag's name (`firstBuild`) comes from Render's own Trigger object and should stay on the wire — this is the label, not the field. Mirror into `locales/zh.ts`.

Not covered by `w4/m118` (which fixed cron facts missing from the feed, not event labels) or `w6/m43` (which fixed create-wizard copy for workers).

Unverified: whether render.com's own Events feed says "first build" for an image-backed service — the wording choice above stands on bex's own truthfulness, not on parity.

Estimate: ~20m.

## Resolution (2026-09-21)

Done as filed: the events feed's `firstBuild` label is now **"First Deploy"** (en + zh), matching `deploys.triggerCreate` word for word. The wire field keeps its Render name — this was the label, not the field, exactly as the note framed it.

Shipped in the same pass as the `w4/100` and `w4/104` label corrections, which fixed the two other entries in the very same `triggerKey` function. That makes three labels in one function that disagreed with the Deploys tab; with this one the function's whole vocabulary now matches.

Covered by a case in the existing trigger-label suite asserting the new label **and** the absence of "First build". Mutation-spot-checked. The note's unverified item — render.com's own wording for an image-backed service — is still unverified and deliberately not load-bearing: the choice rests on bex's own truthfulness, since an `image`-runtime service has no build stage to have a "first build" of.
