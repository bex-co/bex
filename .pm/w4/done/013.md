# Honor the audit-log `direction` param (or reject it)

`GET /v1/owners/{ownerId}/audit-logs` + GraphQL `auditLogs` accept `direction` and silently ignore it (always newest-first) — `docs/ADR018-render-parity.md` §Audit logs documents the drift. Either implement oldest-first ordering or return a named 400, per the "nothing accepted is ignored" principle w3/m8 established (store-only filters 503, unknown values 400). Sub-hour: one ordering flag through `internal/audit`'s `Service.List` + cursor semantics check.

## Resolution (2026-07-15) — done: implemented, not 400'd

Chose the implement branch (real parity beats a named refusal — Render pins `direction` as enum `backward` (default, newest-first) / `forward` (oldest-first), verified live at api-docs.render.com `list-owner-audit-logs`, the same vocabulary bex's logs feature already honors):

- **One ordering flag through the stack:** `audit.Filter.Direction` (validated in `Service.List` — the verb, so REST and GraphQL cannot diverge; unknown value ⇒ named `core.ErrBadRequest` 400 citing the offending value) → `store.AuditFilter.OldestFirst` → `ListAuditEvents` picks `pageOldestFirst`, a new exact mirror of `pageNewestFirst` (shared `pageKeyset` helper: `ASC` + cursor resumes strictly NEWER; deploys' newest-first path byte-identical).
- **Cursor semantics checked:** the cursor is a row id in both directions — backward resumes strictly older, forward strictly newer; proven against real Postgres (`store_pg_test.go`'s `assertAuditEvents` now asserts the reversed total order + a forward second page).
- Surfaces: REST `direction` query param + GraphQL `auditLogs(direction:)` arg. Tests: `TestListDirectionMapsToStoreOrdering`, `TestListRejectsUnknownDirection` (audit), `TestAuditDirectionSurface` (REST+GraphQL parity incl. the named 400 on both). ADR018 §Audit logs + ADR006 §Audit log updated ("accepted and ignored" → honored).
