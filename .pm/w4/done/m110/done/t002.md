## Objective

After any rollout, the Metrics **Total Instances** headline and the `INSTANCES` series count recently-terminated pods alongside the live ones, because the query counts every pod with a sample inside Prometheus's 5-minute lookback. A 1-replica service reads 4 instances right after a rollout. Count live pods, so the chart agrees with the header's instance count on the first post-rollout bucket.

## Context

### The observation (production, 2026-09-17)

Service `qa-20260917-web` (`srv-dalo003ssesc73e0la40`, 1 replica, free; deleted at the end of the QA run). After three rapid rollouts (manual redeploy, rollback, config change) and then *zero* changes for 16 minutes, the `Metrics` GraphQL read for `INSTANCES` (resolution 300) returned:

```json
{"time": "2026-09-17T05:55:00Z", "value": 1},
{"time": "2026-09-17T06:00:00Z", "value": 3},
{"time": "2026-09-17T06:05:00Z", "value": 2},
{"time": "2026-09-17T06:10:00Z", "value": 1},
{"time": "2026-09-17T06:15:00Z", "value": 1}
```

The Metrics page headline read **Total Instances 4** at 06:00:48 while the service header read **Instances 1** (`replicas: 1` on both REST and GraphQL). The series decays 4 → 3 → 2 → 1 → 1 with nothing changing — the signature of dead pods aging out of a lookback window, not of live concurrency (rollout overlap for 1 replica caps at 2). Evidence screenshot: `.playwright-mcp/qa-metrics-instances-4.png` (gitignored, local to the QA session).

Root cause: `lego/backend/internal/metrics/source.go:278` renders the metric as an instant query,

```promql
count(sum by (pod) (container_memory_working_set_bytes{<matchers>}))
```

evaluated at each range step with Prometheus's default 5m lookback — so every pod terminated within the last 5 minutes still counts. Nothing else shares this exact shape (the per-pod memory/CPU series are gauges where stale points merely extend a line; only the *count* turns staleness into phantom instances).

This is not `w4/050` (concurrent duplicate series for OOM-restarting pods, fixed via `max by (container)`) and not `w6/m110` (pod-name matching leaving cards blank): both concern which live pods match, while this concerns dead pods matching at all. No open or done note covers lookback inflation of the count.

### Fix direction (not a prescription)

Count pods with a sample in the last scrape interval rather than the default lookback — e.g. `count(count_over_time(container_memory_working_set_bytes{…}[90s]) > 0)` — or drive the count from kube-state-metrics (`kube_pod_info` filtered to Running) instead of cAdvisor. Either way the headline (`latestValue` in `dashboard/src/features/metrics/lib/series.ts`) needs no change once the series is honest. Keep `unit: "count"` and the REST/MCP twins (`instance-count` in `internal/metrics/rest.go`) on the same query so the three surfaces cannot drift again.

### Acceptance

- The milestone DoD's "Instance counts are live counts" bullet passes live: roll a 1-replica service and read `INSTANCES` on the first post-rollout bucket — 1, not 2+.
- A unit test pins the rendered PromQL against the dead-pod case (a matcher window containing one live series and N stale series counts 1), following the existing `source.go` query-shape tests.
- Memory/CPU per-pod charts are unchanged in shape (same series, same labels) — only the count query changes.
