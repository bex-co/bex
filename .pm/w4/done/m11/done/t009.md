## Objective

t002's one remaining manual check (browser WebAuthn enroll/challenge) was attempted live against prod (`dashboard.bex.co`) using Playwright with a CDP virtual authenticator — the standard way to automate a WebAuthn ceremony without physical hardware. It found the feature is not merely "unverified," it is **actively broken** by two independent bugs, both root-caused and fixed in source. Neither fix is deployed yet.

## Findings

1. **Dashboard CSP blocks Kratos's WebAuthn glue script.** `dashboard/vite.config.ts`'s `Content-Security-Policy` header sets `script-src 'self' 'unsafe-inline'` with no allowance for `auth.bex.co`. Kratos's settings/login flows return a `UiNodeScriptAttributes` node (`<script src="https://auth.bex.co/.well-known/ory/webauthn.js">`) that Ory Elements injects to define `window.__oryWebAuthnRegistration`/`__oryWebAuthnLogin` — cross-origin from `dashboard.bex.co`, so the CSP silently blocks it (confirmed via browser console: "Loading the script '.../webauthn.js' violates ... script-src"). Clicking "Add security key" (or the aal2 login's "Use your security key") calls `@ory/elements-react`'s `triggerToWindowCall`, which polls for the global function for 10s then throws "Unable to load Ory's WebAuthn script. Is it being blocked...?" — exactly this failure. **Fixed:** `dashboard/vite.config.ts` now derives the Kratos public origin (from `VITE_KRATOS_PUBLIC_URL`, same fallback as `src/common/lib/ory/config.ts`) and adds it to `script-src`.
2. **Kratos's identity schema never marks `email` as a WebAuthn identifier.** `deploy/gitops/base/values/kratos.values.yaml`'s `identity.schema.json` only had `"credentials": { "password": { "identifier": true } }` on the `email` trait — no `"webauthn": { "identifier": true }`. Submitting a real, browser-produced WebAuthn attestation directly to Kratos's settings-flow API (bypassing the CSP bug entirely, to isolate this) returned `400` with error `4000009`: "Could not find any login identifiers. Did you forget to set them? This could also be caused by a server misconfiguration." — Kratos's webauthn strategy needs a schema trait flagged as a webauthn identifier to build `user.name`/verify the credential against. **Fixed:** added `"webauthn": { "identifier": true }` alongside the existing `password` entry. Verified the fix renders correctly: `helm template`/`helm lint` against the pinned chart (`ory/kratos@0.62.1`) with the edited values file succeed, and the local overlay doesn't shadow `identitySchemas` (inherits the base fix unmodified).

## How this was verified without a real security key

A CDP `WebAuthn.addVirtualAuthenticator` (ctap2/usb, automatic presence simulation) attached to a real Playwright-driven Chrome session against **prod** `dashboard.bex.co` — the standard way Chrome's own WebAuthn testing API lets a real ceremony run without physical hardware. A throwaway account (`mfa-webauthn-verify-1752522000@bex.co`, left in place — no self-service account deletion exists, and `scripts/auth-mfa-e2e.sh`'s own prod runs already do the same) reproduced both bugs against the real, currently-deployed Kratos + dashboard.

## Resolution (2026-07-14)

Shipped as `2c2562a`; CI (test-backend/operator/dashboard + build+push+GitOps pin) went green, Argo auto-synced both the dashboard and Kratos. Re-ran the exact same live browser check against prod post-deploy:

- The `webauthn.js` CSP violation is gone entirely (confirmed via console); `window.__oryWebAuthnRegistration` now loads via the normal `<script src>` tag Ory Elements injects, no manual injection needed.
- "Add security key" (after a privileged-session reauth prompt — session had gone stale over the ~3h investigation, an orthogonal Kratos recency check, not a bug) persisted a real credential: Settings now lists "playwright-post-deploy-key" with a Remove control, plus a "Settings updated" confirmation toast.
- Logged out and back in: password login presented "Second factor authentication / Continue with hardware key"; completing the WebAuthn assertion (virtual authenticator) upgraded the session, confirmed via `GET /sessions/whoami` → `authenticator_assurance_level: "aal2"`.

Both bugs are conclusively fixed and live-verified. `w4/m11`'s full DoD now holds — see `t002`'s updated acceptance criteria and the milestone README's closeout.

One pre-existing, unrelated issue surfaced during CI verification: the `gitops (render)` GitHub Actions check is failing on `main` due to a traefik chart schema mismatch (`additional properties 'logs' not allowed`) and a stale prometheus alert-rule test fixture — confirmed via a clean worktree at the commit before this fix that it predates this work entirely, and confirmed it does not gate `deploy (bex via Argo)` (a fully independent workflow). Left unfixed as out of scope for this task; worth a follow-up inbox note.
