# 655 — GraphQL `serviceEvent.details` exposes only `leaderId` of the datastore event details REST and MCP now carry

Why: w4/m379 gave datastore events Render's details on REST and MCP (user, pool, disk, HA, replica and upgrade from/to values, Key Value restart reason/message); GraphQL `serviceEvent.details` still exposes only `leaderId`, so the dashboard cannot show them.

- **Source / estimate:** follow-up from w4/m379 (2026-11-14). **Minor**. ~40m.
- **Fix:** add the fields to the GraphQL details type from the same view, and show them on the datastore Events rows where useful (en + zh).
- **DoD:** GraphQL returns the same values as REST for each datastore event type.

- **Closed 2026-11-14 (/loopx w4):** GraphQL `ServiceEventDetails` gained `enabled`, `fromDiskSize`/`toDiskSize`, `fromStatus`/`toStatus`, `fromReplicas`/`toReplicas`, `fromVersion`/`toVersion`, `restartReason` (Render's Key Value `reason`; GraphQL's `reason` is already the deploy end-reason object) and `message`, all read from the same `toRenderEvent` details REST/MCP send (computed once per event in the `details` resolver); `user` was already exposed. The dashboard half was skipped: datastores have no Events rows to show them on (the database detail page has only Overview and Logs tabs, `dashboard/src/routes/databases.$databaseId.tsx:198-212`; datastore events reach clients only through Retrieve event). ADR018 updated. Tests: `TestDatastoreEventDetailsOnRetrieve` now checks every REST member against GraphQL for each datastore type (a broken resolver fails it); the gqlutil opaque-resolver budget is raised by these six string fields; `GOWORK=off go test ./...` passes. Live DoD replays after the next production deploy.

- **Live check (QA loop round 395, 2026-11-15, pin `89ac87445bec`, which carries the fix): holds.** GraphQL `serviceEvent(id:)` on round 393's datastore events: `postgres_created` (`evt-e99rm0e7qt9bpcegdh04`) and `postgres_restarted` (`evt-dh9dfu3dlo4dcn2cke3t`) → `details { user { id email } }` = the QA user; `key_value_config_restart` (`evt-92nn00992odl6dbe8gbu`) → `details { restartReason message }` = `config_change` / "Persistence mode changed to off; the instance restarted to apply it."; `postgres_unavailable` (`evt-75423j21ouio3v350sfu`) → `details { reasonCode }` = `readiness_failed`. These match REST `GET /v1/events/{id}`. In GraphQL the KV restart reason is `restartReason`, because `details.reason` is the deploy-end object (`BuildDeployEndReason`).
