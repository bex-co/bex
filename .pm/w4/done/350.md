# A never-healthy service can still record "Service recovered" with no failure

Why: an App whose first instance never became healthy keeps an empty availability baseline outside hibernation. Its first unhealthy conclusion latches silently, so the later healthy pass emits an unpaired `server_available` ("Service recovered") to Activity, push and webhooks. This is the same broken pairing `w4/m230` fixed for wakes.

- **Source:** `w4/m230` t003 adjacent-class audit, 2026-10-19 (loopx w4). Reasoned from code, not probed live.
- **Path:** `store/event_facts.go` `observedStateFacts` emits `server_failed` only from a `healthy` baseline, plus, since m230, a concrete failure from the held Hibernated baseline. `""` → `unhealthy` otherwise latches with no fact, and `unhealthy` → `healthy` then emits `server_available`. Two ways to reach it:
  - A first deploy whose instance crash-loops after its deploy row closes. The `concreteContainerFailure` conclusion is observed with no deploy open, and a later fixing deploy turns healthy.
  - A brand-new service whose first instance goes unready (no deploy row) before it was ever healthy.
- **Precedent:** the datastore projector already refuses this. `nextDatastoreAvailability` never latches `unhealthy` from a non-healthy baseline, so provisioning and suspension arm nothing (`TestObservedDatastoreProvisioningAndSuspensionArmNothing`).
- **Fix direction:** extend the App checkpoint the same way. Do not latch `unhealthy` from `""` except where `w4/m230` deliberately records a failed wake. Keep the Running-healthy crash edge (`TestPGObservedCrashEdgeEmitsExactlyOnePair`) and the m230 wake tests unchanged. Add a real-Postgres test for both paths above.
- **Estimate:** 45m.

**Done 2026-10-19 (loopx w4):** `store/event_facts.go` `heldAvailability` now holds an unhealthy conclusion from an empty baseline outside a Hibernated wake ("never seen healthy"). A checkpoint's first observation is held the same way, both in the PG insert and in `memStore`. Such a service records neither edge, so its first healthy pass is no "Service recovered". That mirrors the datastore projector's `nextDatastoreAvailability`.
- **Paths covered:**
  - a first deploy crash-looping after its row closed, then fixed;
  - crash-looping from the first pass;
  - a checkpoint first written mid-outage;
  - never served, then a real outage, which still pairs.
- **Tests:** `TestAServiceThatNeverServedRecordsNoRecovery` (unit); new cases in `TestPGWakeRecordsOnlyItsLifecycleFact`; `TestPGFirstUnhealthyObservationIsNoBaselineToRecoverFrom`, which covers the insert path. Mutations of the rule and of both insert paths are caught.
- **Unchanged controls:** `TestPGObservedCrashEdgeEmitsExactlyOnePair` and the m230 wake and failed-wake cases.
- **Accepted trade-offs:**
  - A service whose only healthy window fell between two 30 s passes now records neither edge, where it used to record a lone recovery.
  - Checkpoints that already latched `unhealthy` from `""` before this change still emit one unpaired recovery on their next healthy pass. No migration was written for that one-time event.
