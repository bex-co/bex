## Objective

Some rejections name the offending field; others answer `{"error":"bad request"}` with nothing to act on. The opaque variant has now been filed three times.

## Context

Measured 2026-09-13 on `PUT /v1/services/{id}/autoscaling`:

| body | response |
| --- | --- |
| missing `enabled` | `invalid request body at /enabled` ✅ actionable |
| missing `min` | `invalid request body at /min` ✅ |
| missing `criteria` | `invalid request body at /criteria` ✅ |
| schema-conformant, handler-incompatible | `bad request` ❌ nothing to act on |
| union of both shapes | `bad request` ❌ |

`safeRenderValidationMessage` (`internal/api/render_openapi.go:471-490`) already does the right thing when a `SchemaError` carries a JSON pointer, and falls back to "request body does not match the Render API schema" otherwise — which is still more than the bare `bad request` observed here. So the opaque responses are coming from somewhere else: most likely `core.ErrBadRequest` wrapped with no detail, or a detail that is being dropped on the way out.

`w4/038` and `w4/041` (both done) are the same complaint on the projects routes. Their fixes made those two routes specific; the general path was left alone, which is why it resurfaced.

## Steps

1. Find where a bare `bad request` is produced for a body rejection — start from the autoscaling path, and check whether an error's detail is being flattened by the REST error writer.
2. Make every body rejection carry either a field pointer or a named reason. "Bad request" alone should be unreachable for body validation.
3. Keep the security boundary the existing helper is careful about: `safeRenderValidationMessage` is deliberately *safe* — it must not echo request content or internal schema paths beyond the pointer. Do not widen it into an error that reflects attacker-supplied values back.
4. Check the sibling classes stay distinct: unauthenticated, forbidden, not-found and rate-limited must not be swept into the new body-error wording.
