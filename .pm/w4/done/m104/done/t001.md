## Objective

`PUT /v1/services/{id}/autoscaling` rejects every body shape that can be constructed for it. Make it work, and decide explicitly which wire shape is canonical rather than leaving two half-supported ones.

## Context

### The probes (production, 2026-09-13 pass 9)

Two fixtures, both created and deleted in the run: `qa-0913i-web` (`srv-dajd930gsm7s73f63p60`, free web service — autoscaling is **legitimate** here, so this is the control that matters) and `qa-0913i-st` (`srv-dajd7togsm7s73f63p40`, static site).

On the **web service**, three bodies, each with `min`/`max` of 1 and a 60% CPU target:

| body | response |
| --- | --- |
| `{"minInstances":1,"maxInstances":1,"targetCPUPercent":60}` — bex's own `SetAutoscalingRequest` shape | `400 {"error":"invalid request body at /enabled"}` |
| `{"enabled":true,"min":1,"max":1,"criteria":{"cpu":{"enabled":true,"percentage":60},"memory":{"enabled":false,"percentage":0}}}` — Render's pinned schema, exactly | `400 {"error":"bad request"}` |
| the **union** of both objects | `400 {"error":"bad request"}` |

After each, `GET /v1/services/<id>/autoscaling` still read `{"enabled":false,"minInstances":0,"maxInstances":0}`. Identical results on the static site, which rules out type-gating as the explanation.

Walking the validator's demands one field at a time gave the schema it wants: omit `enabled` → `at /enabled`; add it → `at /min`; add `min`+`max` → `at /criteria`; supply `criteria` → the pointer disappears and a bare `bad request` remains.

### The same intent succeeds on GraphQL, seconds later, same service

```text
mutation { setAutoscaling(id:"srv-dajd930gsm7s73f63p60", minInstances:1, maxInstances:1, targetCPUPercent:60) { enabled minInstances maxInstances targetCPUPercent } }
→ {"data":{"setAutoscaling":{"enabled":true,"maxInstances":1,"minInstances":1,"targetCPUPercent":60}}}

GET /v1/services/srv-dajd930gsm7s73f63p60/autoscaling
→ {"enabled":true,"minInstances":1,"maxInstances":1,"targetCPUPercent":60}
```

So the REST **read** works, the REST **write** does not, and the GraphQL write does — which localizes the defect to the REST PUT adapter and excludes authz, service type, plan, and the instance cap.

### The two layers

- **Contract:** `lego/backend/internal/api/openapi/render-public-api-1.json`, `PUT /services/{serviceId}/autoscaling` request body — `required: ["enabled","min","max","criteria"]`; `criteria.required: ["cpu","memory"]`; each of `cpu`/`memory` `required: ["enabled","percentage"]`. `internal/api/render_openapi.go:455-490` validates against it and renders the `invalid request body at /<pointer>` messages.
- **Handler:** `internal/apps/rest.go:1111-1117` → `core.DecodeBody[SetAutoscalingRequest]`, and `SetAutoscalingRequest` is `{minInstances, maxInstances, targetCPUPercent?, targetMemoryPercent?}` (`internal/apps/service.go:4349-4354`). `renderAutoscaling` (`internal/apps/render.go:182-190`) — the **response** shape — uses `minInstances`/`maxInstances` too, so the response side does not match Render's request vocabulary either.

### The anomaly to resolve first

The two-layer story does not explain the **union** result. That body carried valid `minInstances`/`maxInstances` **and** Render's `enabled`/`min`/`max`/`criteria`, so it should have passed the schema and decoded to a usable spec — yet it returned a bare `bad request`. Candidates: a strict decoder rejecting unknown fields, `autoscalingSpec` failing for another reason, or a response-side validation of the `renderAutoscaling` output. Instrument it before designing the fix; a fix aimed at the wrong layer will look like it works on one shape and leave the others broken.

## Steps

1. Reproduce locally and instrument: log which layer rejects each of the three bodies. Resolve the union anomaly explicitly — that answer decides where the fix goes.
2. Decide the canonical wire shape and write it down. The default should be **Render's** (`enabled`/`min`/`max`/`criteria`), because the pinned contract is the compatibility promise and `w4/041` set the precedent of moving the handler to the contract rather than loosening the contract. Map it onto `SetAutoscalingRequest` at the adapter boundary so `autoscalingSpec` and the service verb are untouched.
3. Decide what happens to the internal shape. Either accept it as a documented bex alias (and say so in `docs/ADR006-bex-api.md`) or reject it with a message naming the accepted keys — not a bare 400.
4. Fix the response side too if it diverges: Render's response for this endpoint should be checked against the pinned schema, since `renderAutoscaling` currently answers in `minInstances`/`maxInstances`.
5. Re-probe all three bodies plus the GraphQL control against the built API and paste the results here.
