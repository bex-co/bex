# SQL results render null and the literal text NULL identically

Why: a user inspecting query results cannot tell whether a cell contains missing data or the actual string `NULL`, even though the API preserves that distinction.

**Severity:** minor. **Estimate:** 35m. **Status:** done. Functional `$qa-find-bugs w4` pass a406, 2026-10-13 local / 2026-10-14 UTC. Source checked after syncing main to `73fbf863b`. Filing only. Goal: faithful presentation of managed Postgres query results, the SQL-console journey shipped by w5/m28 under ADR009 and ADR018.

## Fresh reproduction

Create an owned private Free Postgres database, wait until Available, open `/databases/<id>#sql-console`, and run this ordinary read-only statement:

```sql
SELECT value
FROM (VALUES
  (1,NULL::text),
  (2,'NULL'::text),
  (3,'null'::text),
  (4,''::text),
  (5,'雪 café'::text)
) AS sample(ord,value)
ORDER BY ord;
```

The native ExecuteDatabaseQuery request has `allowWrites:false`. Its complete response retains five distinct row values: `null`, `"NULL"`, `"null"`, `""`, and `"雪 café"`. In the ready results table, the first two cells both have text and innerHTML `NULL`, the same classes and computed color/font/style/background, and no title or accessible label. The real accessibility tree calls both `cell "NULL"`.

This reproduces on the initial desktop page, a full fresh desktop reload, and a full fresh 390×844 mobile reload with another native run. The inspected mobile screenshot confirms the first two cells look identical. A semantic control, `SELECT NULL::text IS NULL AS missing, 'NULL'::text IS NULL AS literal_is_missing`, returns and displays `true` and `false`; these are meaningfully different data states, not two spellings of one value.

Target: show an actual SQL null using a distinct null marker with a separate accessible meaning, while leaving literal strings exactly as returned. The visual distinction must include typography/shape/text treatment rather than depend solely on color. For example, render the null marker with italic or badge treatment and accessible cell content meaning “SQL NULL / no value”; retain ordinary unstyled `NULL` for the string. Preserve lowercase `null`, empty text, whitespace, Unicode, and all other returned cell strings.

## Root cause and bounded fix

- `dashboard/src/features/databases/components/sql-console.tsx:196–209` applies the same TableCell classes to every result. Its null/undefined branch substitutes the translation `databases.sqlNull`; otherwise it inserts the string. Because that translation is `NULL`, both input states render the same ordinary text node.
- `dashboard/src/features/databases/locales/en.ts:1421–1424` and `zh.ts:1370–1373` both define the null marker as `NULL`. Preserve the SQL token if desired, but add a distinguishable visual and accessible treatment for its semantic role. Any new accessible copy must follow the existing locale structure.
- `dashboard/src/features/databases/hooks/use-execute-database-query.ts:38–44` copies each result row's values without converting null to text. Native receipts confirm the null remains available to the component. This hook needs no conversion change.
- `dashboard/src/common/components/ui/table.tsx:81–93` renders a normal `td`, forwarding its props. It has no conditional null decoration and can express a cell-level accessible label or content treatment. Keep the implementation in SQLConsole or a small SQL-specific renderer; do not change shared TableCell or turn API null into a magic string.
- `lego/backend/internal/postgres/graphql.go:339–354` projects DatabaseQueryRow/DatabaseQueryResult. The actual response is correct. No backend serializer, REST, GraphQL, or MCP shape change is needed.

Exhaustive production grep: **one SQLConsole mount**, `dashboard/src/routes/databases.$databaseId.tsx:272`, keyed by database ID under the deferred `#sql-console` section. The other occurrences are its declaration and lazy import. Canonical `/databases/<id>` and the `/d/<id>` Render alias (`routes/d.$.tsx:5–10`) reach that same page. Web/static/cron/worker/private services and Key Value do not mount this Postgres console. Scope the fix to this results presentation; other tables retain their own formatting.

Before any query finishes, preserve the existing empty/loading state. Error clearing, non-SELECT confirmation, row count, truncation, pagination, query history, and suspended-database behavior remain unchanged. Unauthenticated, forbidden and timeout responses retain their existing handling. This finding is about successfully returned rows.
