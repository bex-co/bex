# Static sites ignore saved ETags during browser revalidation

Why: returning visitors download unchanged static files again even after the owner saves a valid ETag, and clients requesting a particular version receive a successful body when that version condition fails.

**Source:** functional `$qa-find-bugs` pass a277, 2026-10-12, dashboard QA account through the login helper with `muse.env`, filed to w4 per user direction. **Estimate:** 55m. **Status:** inbox. **Impact:** minor functional delivery/performance defect; this is ordinary HTTP cache and download behavior.

## Reproduction and expected result

Create the owned static site `qa-20261012-a277-static` from public repo `https://github.com/bex-co/bex`, branch `main`, root `examples/static-site`, publish directory `.`, and auto-deploy off. Its accepted build command creates `version.txt` containing exactly `qa-a277-version-1\n` (18 bytes), plus a 77,824-byte text file for the separate range control. Service `srv-db69tfocjuds73bjk82g` reached Running / Live / `rev-1`.

In the dashboard Headers page, save `{path:"/version.txt", name:"ETag", value:"\"qa-a277-v1\""}`. `SetStaticHeaders` accepted it at **08:53:17.029Z**. A fresh GraphQL read at **08:54:15.947Z** and REST `GET /v1/services/{id}/headers` at **08:57:57.154Z** returned that exact rule. The public response also carried `Etag: "qa-a277-v1"`; the save itself works.

A fresh Chromium **155.0.8059.40** page made three ordinary `fetch('/version.txt?browser-a277=2')` calls. The first fetched the file normally. At **08:55:20.689Z** and **08:55:20.858Z**, the next two browser requests automatically sent `If-None-Match: "qa-a277-v1"`. Both actual network responses were **200**, with `Content-Length: 18` and the complete unchanged file. These are network responses with recorded conditional request headers, rather than a claim based only on the browser's normalized Fetch status. Explicit browser conditional GET and HEAD with `cache:"no-store"` repeated the incorrect 200.

Two independent native-client rounds, **08:57:19.624941Z–08:57:33.266373Z**, used fresh query URLs and `Accept-Encoding: identity`. Every response still carried the saved ETag:

| Request on existing version.txt | Expected | Actual, both rounds |
| --- | --- | --- |
| GET/HEAD with matching If-None-Match | 304, no body | 200; GET retransmits 18 bytes |
| GET with weak matching If-None-Match, matching member of a tag list, or wildcard | 304, no body | 200, 18 bytes |
| GET/HEAD with a mismatching If-Match | 412, no successful file body | 200; GET returns 18 bytes |
| GET with weak If-Match against the strong saved tag | 412 | 200, 18 bytes |
| Ordinary GET/HEAD, matching strong If-Match, or mismatching If-None-Match | 200; HEAD has no body | Pass |

Before adding any ETag, `If-None-Match: *` on the existing file also returned 200 on GET and HEAD. A genuinely missing `.txt` path returned 404, so the existing-object control is not an SPA miss disguised as a file.

[RFC 9110 sections 13.1.1–13.1.2 and 13.2](https://httpwg.org/specs/rfc9110.html) require evaluating these preconditions: a matching If-None-Match on GET/HEAD yields 304, while a failed If-Match yields 412. Weak comparison is used for If-None-Match and strong comparison for If-Match. The wildcard existing-object case does not require generating an automatic ETag. The practical observed effect is repeated transfer of an unchanged file and ignored version conditions. Impact on larger assets is an inference; this replay measured 18-byte conditional bodies.

## Cause, consumers and bounded fix

Current main **b35a3ee30**, synced during the hunt, still has the same mechanism:

- `lego/operator/internal/staticserver/staticserver.go:333–359`: `serveObject` applies content type, default Cache-Control and saved custom headers, then **unconditionally writes 200** and the whole body. It never evaluates request validators.
- `staticserver.go:580–588`: `applyHeaders` correctly emits the saved ETag, with the last matching rule winning. This is why Chromium sends the validator on its next request.
- The three successful delivery consumers are direct objects (**251**), rewrite targets (**300**) and SPA fallback (**310**). Only direct file delivery was exercised live; the other two paths are source-established consumers to cover in regression tests. Directory indexes use the same object resolution.
- `lego/operator/cmd/staticserver/main.go:164–168` wires this handler behind the host resolver. One shared edge fix covers platform-host and custom-domain resolutions; a custom-domain live replay was not performed.
- Configuration is already shared: backend `apps/service.go:5164–5180` saves the header CR field; REST `rest.go:1230,1251`, GraphQL `graphql.go:1754–1761`, and MCP `mcp.go:998,1009` call the same list/set methods. GraphQL and REST saved reads passed live; MCP was traced in source only. Dashboard canonical `/services/$serviceId/headers` and `/static/$serviceId/headers` mount the same `ServiceHeadersPage` / `HeadersEditor`. No API schema or dashboard workaround is needed.

Fix the successful-byte response at the shared handler, after selecting the effective headers and before committing a success status. Prefer Go's existing conditional delivery over writing another entity-tag parser: the installed **Go 1.26.5** `net/http/fs.go:214–245` documents `http.ServeContent` over an `io.ReadSeeker`, using an already-set ETag; **483–508,532–559,645–675** implement strong/weak comparison and the 412/304 branches. The existing in-memory object can be served through `bytes.NewReader(obj.Body)`, without another body allocation or an S3 round trip. The platform Dockerfile pins the Go 1.26 builder family; this inspection does not claim production's exact patch version was queried.

Preserve request-path header matching, last-matching-rule precedence, content-type selection, zero HEAD bodies, immutable revision-keyed caching and the existing live-body lease over actual body writes. Do not invent a Last-Modified time or an automatically generated ETag. Audit the standard helper's inherited Range handling and error-header behavior explicitly if delegating to it; adding range support is not an acceptance requirement of this finding. Keep origin failures and missing-object handling ahead of successful-representation preconditions. Use the existing standard-library machinery directly rather than introducing a new delivery abstraction or copying Go's private parser.

Meaningful verification for the fix:

1. Exercise the real handler with GET and HEAD, matching/mismatching strong tags, weak tags, tag lists and wildcards. Assert status, no body on 304/HEAD and no successful file body on failed If-Match; preserve passing ordinary-read controls.
2. Run that contract on direct files, a rewrite and SPA fallback. Assert the effective ETag and custom Cache-Control survive 304, while normal 200 bytes and header precedence stay unchanged. A real HTTP server should cover framing and body delivery, alongside the existing reserved-header and memory-budget tests.
3. Replay the ordinary three-fetch browser journey and the native controls after deployment, using a fresh owned fixture. The browser's conditional network responses must be 304, with the correct file still available to Fetch through its cache. Remove the fixture and revoke the session.

This is a small shared-handler fix plus behavioral regression coverage and a bounded live replay (55m). This filing contains no product implementation or product test run.

The separate range probe returned the complete 77,824-byte file with 200 for `Range: bytes=0-18`; [RFC 9110 section 14.2](https://httpwg.org/specs/rfc9110.html) permits ignoring Range, so that result is **not filed as a defect**. HEAD omitted Content-Length and returned no body; omitted HEAD length is not filed either.
