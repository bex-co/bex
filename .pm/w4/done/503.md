# 503 — A service that is being deleted still answers 200 on its env-vars, secret-files, custom-domains, events, jobs, instances and autoscaling reads, while `GET /v1/services/{id}` already answers 404

Why: w3/m81 promised one answer to "does this service still exist?" on every by-id read. Seven sibling reads still answer `200` with an empty or default body during the deletion window, so a client that polls them after a delete sees a live-looking service.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 93, 2026-11-05 UTC (`muse.env`, `bex-canary`); **minor** (a transient window of a few minutes, no data loss or leak, but it breaks the w3/m81 contract); ~45m.
- **Probe:** owned static site `qa-20261105-dom` (`srv-dbmdcuf2j1is73dev200`), created for a custom-domain validation pass. `DELETE /v1/services/<id>` → `204`, then `GET /v1/services/<id>` → `404`. The following reads ran from the signed-in page within about one to three minutes of the `DELETE`. Status and body prefix of each:

  | Route (all `GET /v1/services/<id>…`) | Status during the window |
  | --- | --- |
  | `` (the service), `/deploys`, `/headers`, `/routes`, `/deploy-hook`, `/runs`, `/disk`, `/preview-pr` | `404 {"code":"NOT_FOUND",…}` |
  | `/events`, `/env-vars`, `/secret-files`, `/custom-domains`, `/jobs`, `/instances` | `200 []` |
  | `/autoscaling` | `200 {"enabled":false,"min":0,"max":0,"criteria":{"cpu":{"enabled"…` |

  - A second sweep a few minutes later returned `404` for every one of those routes, so the App CR had finished terminating. The inconsistency is a window, not a permanent state.
  - Control, same session: a never-existing id (`srv-00000000000000000000`) answers `404` on `custom-domains`, `env-vars`, `deploys`, `headers`, `routes`, `secret-files` and `events`. So the `200`s come from the terminating App being found, not from a route that skips the existence check altogether.
- **Root cause:** `core.NotFoundIfDeleting` (`lego/backend/internal/core/base.go:1506-1522`) is the m81/m35 read contract, and its doc says read verbs call it after `Authorize*`. The service, deploys, routes and headers reads do (`lego/backend/internal/apps/service.go:1481` and the five other callers in that file, plus `deploys/service.go`). These seven reads call `AuthorizeApp` and stop there:
  - env-vars and secret-files: `secrets.Service.scope` (`lego/backend/internal/secrets/service.go:201-224`, reached by `readAuthorizedEnv` at `:342`),
  - custom-domains: `ListDomains` (`lego/backend/internal/apps/domains.go:729-733`),
  - events: `events.Service.List` (`lego/backend/internal/events/service.go:926-930`),
  - jobs: the list verb in `lego/backend/internal/jobs/service.go` (REST at `jobs/rest.go:104`; line not pinned),
  - instances: `ListInstances` (`lego/backend/internal/apps/service.go:1515-1519`),
  - autoscaling: `GetAutoscaling` (`lego/backend/internal/apps/service.go:5982-5987`).
- **Fix (target behavior):** during the deletion window, every tenant by-id read under `/v1/services/{id}` answers `404 NOT_FOUND`, the same body a never-existing id gets, exactly as `GET /v1/services/{id}` already does. Authorization runs first, so a caller without access still gets the forbidden answer it gets today and the check is not an existence oracle.
  - Add the `NotFoundIfDeleting` check right after `AuthorizeApp` in the seven verbs above, or add one helper (for example `AuthorizeLiveApp`) that wraps both and move these callers to it.
  - Do not change `AuthorizeApp` itself. Lifecycle teardown must still authorize the CR it is removing; the `NotFoundIfDeleting` doc says so.
  - REST, GraphQL (`apps/graphql.go`) and MCP read through the same service verbs, so all three move together. The dashboard needs nothing: its dead-id redirect already keys on the service read.
- **Tests:** a table-driven test over every `GET` route registered under `/v1/services/{id}`, run against a fake App carrying a `DeletionTimestamp`. It asserts `404` on each, so the next sibling read someone adds fails it. Keep the existing `apps/service_deletion_test.go` cases as the controls, and add a case that an active App still answers `200` on all seven.
- **Blast radius:** `AuthorizeApp` has 90 non-test callers (`grep -rn "\.AuthorizeApp(" lego/backend/internal --include='*.go' | grep -v _test`), 32 of them with `RelCanView`. `NotFoundIfDeleting` has 23 call sites in 11 files. The fix is allowlisted to the seven read verbs, not global. The remaining `RelCanView` callers (logs, metrics, disks, edge cache, outbound IPs and others) are not probed here, so the table-driven test is also how the rest gets enumerated; any it flags belong to this note, not to new ones.
- **Adjacent classes:** forbidden and unauthenticated stay ahead of not-found (authorize first, then the deleting check). A write against a deleting service is out of scope here: w5/m116 already added the check to settings and plan changes, and this note did not probe other writes.
- **Unverified:**
  - The GraphQL and MCP counterparts were not exercised; they are inferred from the shared verbs.
  - The window's length was not measured (about one to three minutes here, ended before the next sweep).
  - The jobs verb's exact line and the `RelCanView` callers outside the seven were not traced.
  - Whether a non-static service (a Deployment-backed web service with a longer finalizer) has a longer window was not probed.
- **Render:** a deleted service's sub-resource reads answer `404`; Render has no "deleting" phase for an API read to expose.
- **Dedupe:** residual of w3/m81 (done), whose DoD names list, service, routes, deploys, headers, GraphQL, MCP, the dashboard route and the URL, but not these seven. `grep -rli "env-vars" .pm | xargs grep -li "deleting"` finds no item on them; w4/183 (done) is about unlinking an env-group row and w4/m129 (done) is about a re-created service's Activity feed. No DO_NOT_DO item applies.

Closed 2026-11-05: new `core.Base.AuthorizeLiveApp` (authorize, then `NotFoundIfDeleting`) backs the reads that were missing the check: custom-domains (`ListDomains`, `GetDomain`), instances, autoscaling, outbound IPs, disks list by service, cron runs (list/get), events list, jobs list/get, and env vars / secret files (`secrets.scope` for `RelCanView`/`RelCanViewSensitive`; writes keep reaching the CR for teardown). REST, GraphQL and MCP share these verbs. Tests: `core/authorize_live_app_test.go`, `apps/service_deletion_reads_test.go`, and one deleting-service case each in secrets, events and jobs. Not changed, and not probed: metrics, logs and the deploy-hook/deploys reads (`metrics/service.go`, `logs/service.go`), which still use `AuthorizeApp`; the note's table-driven sweep over every registered GET route was replaced by the per-verb cases above, so a read added later still needs its own case.
