# BLOCKER: no new service can deploy since `cae30d1e0` — the release-config snapshot reads tenant Secrets through a cache scoped to another namespace

Why: since deploy `cae30d1e0` (w1/m152 t001, live 2026-09-28 16:47Z), a newly created service's first release closes `update_failed` before it touches the Deployment, so no new service can go live. This is reproduced twice, with a repo build and with an image. An existing service's release succeeded once after the rollout (below); why it escapes is unverified, so existing services may be affected on some paths. Every tenant App lives in a workspace namespace (`tea-…`, ADR043), and the snapshot step reads Secrets through a cached client whose Secret informer only watches the legacy apps namespace.

Found live in `/qa-find-bugs` pass 257 on 2026-09-28 (w4-targeted, `muse.env` credentials) against the deployed `cae30d1e0`. The fixture was a free web service `qa-20260928-snap` (`srv-dat9r17vlo4s73e5gd00`), built from `examples/hello-go` with `MESSAGE=v1` in workspace `bex` (`tea-d98210cbbpdc73dcrkvg`). It was deleted afterwards (`DELETE` 204, then `GET` 404).

- `POST /v1/services` → 201. The build ran (`build_started` 17:01:56Z, `build_ended` 17:04:02Z).
- The deploy `dep-dat9r17vlo4s73e5gd0g` closed **`update_failed`** at 17:04:02Z with `failureReason`: **`snapshot tea-d98210cbbpdc73dcrkvg-qa-20260928-snap-env for generation 1: unable to get: tea-d98210cbbpdc73dcrkvg/tea-d98210cbbpdc73dcrkvg-qa-20260928-snap-env-r1 because of unknown namespace for the c[ache]`**.
- `https://qa-20260928-snap.onbex.co/` stayed `404 page not found` (nothing was ever projected) through a 15-minute poll.
- **Repro 2** (image, no build, 16 s): `qa-20260928-snap2` (`srv-datakokpot5s73asjc80`, `docker.io/traefik/whoami:v1.10`, env `MESSAGE=v1`), created 17:57Z. Its first deploy was `update_failed` with the identical `snapshot …-snap2-env for generation 1: … unknown namespace for the cache`. Deleted (`DELETE` 204, then `GET` 404).
- **Existing service, same namespace, succeeded:** `beancount-cms-v2` (pods in `tea-d98210cbbpdc73dcrkvg`, per its request logs' `KubernetesIngressNamespace`) had a `new_commit` deploy created 17:03Z, after the rollout, which went `live` at 17:50Z. So the failure is not "every App in a workspace namespace on every release". **Unverified cause of the difference:** an existing App may take a path that skips the snapshot or reuses the mutable names (lazy migration, `status.configSnapshotGeneration`), or the source Get may happen to succeed through a different client. The fix must explain it, not just the new-App case.
- Live services still answer 200 (`agentmarketcap-1`, `beancount-cms-v2`, `eden-cms-v2`, `block-eden-mono`).

## Mechanism

- `lego/operator/cmd/manager/main.go:269` builds the manager with `controller.NamespacedSecretCacheOptions(appsNamespace)`. `internal/controller/secret_cache.go:41` scopes the **Secret** informer to that one namespace, deliberately, because the operator's ClusterRole cannot list Secrets cluster-wide. Its comment spells out the rule: Secrets that live in a workspace namespace must go through an **uncached** client (`KeyValueReconciler.SecretClient`, `AppReconciler.uncachedSecretClient`).
- `internal/controller/release_config_snapshot.go` `copyConfigSecret` (called from `ensureReleaseConfigSnapshot`, l.178) uses the **cached** `r.Get` for both the existing snapshot (`<source>-r<gen>`) and the source Secret (`<name>-env` / `-files` / `<evg>-env` / `-files`) in `app.Namespace`. It also writes with `controllerutil.CreateOrUpdate(ctx, r.Client, …)`, which does a cached Get first. For any App outside `appsNamespace`, controller-runtime answers `unknown namespace for the cache`. That is not `IsNotFound`, so the error propagates and fails the release.
- The existing uncached path is right beside it: `AppReconciler.uncachedSecretClient()` (`app_controller.go:1962`, used at l.1377 for the disk passphrase Secret in the App's own namespace).
- Why tests passed: the envtest App lives in the namespace the cache watches.

## Fix

Target: a release in a workspace namespace snapshots its sources and rolls out exactly as in the envtest. `hello-go` with `MESSAGE=v1` serves `v1`; changing `MESSAGE` to `v2` makes the next release serve `v2`; and rolling back to the first deploy serves `v1` again (the m152 promise).

- Route every Secret read and write in `release_config_snapshot.go` through `r.uncachedSecretClient()`: the copy-once Get, the source Get, the `CreateOrUpdate`, and the snapshot GC's List/Delete.
- Grep the rest of the m152 t001 diff for any other cached Secret access in `app.Namespace`.
- **Also t002 (`1353244f1`, deploying 2026-09-28 ~20:05 local):** `settleConfigSnapshotTo` adds two more cached `r.Get(ctx, client.ObjectKey{Namespace: app.Namespace, …}, &corev1.Secret{})` probes (`release_config_snapshot.go` ~l.101 and ~l.128) to check that every source of the target generation still has its copy. Through the cached client they would return `unknown namespace for the cache` instead of `IsNotFound`, so the cancel-revert path can error out the same way. Route them through `uncachedSecretClient()` as well; do not treat the cache error as "copy missing".
- Test: an envtest App in a namespace **other** than the cache's `appsNamespace` (the production shape) whose release succeeds and projects `-r1`. Add a regression test that fails with `unknown namespace for the cache` on the old code.
- Urgency: until this ships, no new service can go live, which blocks onboarding and every create path (dashboard, REST, GraphQL, MCP, Blueprint). Consider rolling production back to the previous pin (`0c983ef0c` → `6b6d99ea8da2`) as the immediate mitigation; the lazy migration means no App has been moved to snapshots yet, so a rollback does not strand pod templates. **Unverified:** whether any App reached `status.configSnapshotGeneration=1` before failing. The failure occurs at the first Get, before the generation flip is persisted, per `ensureReleaseConfigSnapshot`'s order.

Blast radius: confirmed for every new service's first release. Existing services on other release paths (env save, env-group write that redeploys, rollback, plan change) are unverified. One existing-service `new_commit` release succeeded. Datastores are unaffected (separate reconcilers, already uncached). Related: `w1/m152` (this is its t001's defect).

Estimate: ~30m (plus an immediate rollback decision).

## Closed 2026-09-29 (w1/m152 t011, `/loopx w1`)

Fixed by `280377a6b`: every snapshot Secret call goes through the uncached client, and the migration is lazy so the fix rolls no existing service. The fix reached production with pin `6f29f3c31` (build `96f988b65`). It had been stuck for 14 hours behind deploy supersession, fixed as w1/116. Live on that build: a new free web service from `examples/hello-go` created **with** `MESSAGE=v1` (`qa-20260929-m152b`) went `live` at 08:26:48Z and served `v1`.
