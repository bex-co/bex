# 599 — Deleting a registry credential names the blocking service by its Kubernetes object name, and keeps refusing for ~25 s after that service was deleted and answers 404

Why: the refusal tells the user which service still uses the credential. It names it `tea-daif693dqjvc73e7as3g-qa-20261112-r170-bound`, a name no dashboard surface shows. Right after the user deletes that service, the same refusal still names it while `GET /v1/services/<id>` answers 404. The user is told to "remove it from the service first" for a service that no longer exists.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 170, 2026-11-12 05:22–05:26 UTC (`muse.env`, workspace `bex-canary`; pin `e7a56b07e0d7`). **Minor.** ~25m.
- **Fixtures**, all deleted afterwards (GET 404):
  - registry credential `qa-20261112-r170-cred` (`rgc-dbqkqjerbf4s73estuk0`, `DOCKER`, a deliberately invalid token);
  - Free image services `qa-20261112-r170-anon` (`srv-dbqkqja140ds739rb94g`, no credential) and `qa-20261112-r170-bound` (`srv-dbqkqji140ds739rb96g`, `image.registryCredentialId` = the credential).
- **Probe**, from the signed-in page:
  1. `DELETE /v1/registrycredentials/rgc-dbqkqjerbf4s73estuk0` while bound → `409 {"code":"REGISTRY_CREDENTIAL_IN_USE","error":"registry credential \"rgc-dbqkqjerbf4s73estuk0\" is still used by service \"tea-daif693dqjvc73e7as3g-qa-20261112-r170-bound\"; remove it from the service first",…}`. Its `params.appName` carries the same object name.
  2. `DELETE /v1/services/srv-dbqkqji140ds739rb96g` → 204, and `GET` → 404.
  3. About 6 s later, `DELETE` of the credential → the same 409, naming the deleted service. At 05:25:41, about 25 s after the service delete, → 204.
- **Root cause:** `appBoundToCredential` (`lego/backend/internal/registrycreds/pullsecret.go:274-292`).
  - It lists the workspace's App CRs, including one still terminating, and returns `a.Name`, the tenant-prefixed CR name. `Delete` (`registrycreds/service.go:395-401`) puts that into the message and `appName`.
  - The guard exists so a deleted credential never strands a live App's derived `<app>-registry-pull` Secret (comment at `pullsecret.go:267-273`). A terminating App's Secret is reaped with the App, so it doesn't need the guard.
- **Fix (target behavior):**
  - **Skip an App whose deletion has begun** (`DeletionTimestamp` set). The service is gone on every read surface, and its pull Secret goes with it.
  - **Name a still-bound service the way the user sees it:** its display name and `srv-` id (e.g. `still used by service "qa-20261112-r170-bound" (srv-dbqkqji140ds739rb96g)`), from the App's labels (`LabelServiceName` / `LabelAppID`).
  - Return the `srv-` id in `params` (e.g. `serviceId`) instead of the CR name.
  - REST, GraphQL and MCP share the verb. The dashboard's delete dialog shows this message (w4/186).
- **Blast radius:**
  - One helper with one caller (`Delete`).
  - Tests:
    - a terminating App doesn't block;
    - a live bound App still blocks, named by service name and `srv-` id;
    - a sibling workspace's App never counts.
- **Unverified:** what Render answers when deleting a registry credential a service still uses. Render may detach it instead of refusing; this note keeps bex's refusal and fixes only its subject and timing.
- **Also verified (w4/m301's DoD):**
  - the service with no credential deployed `live` from public `docker.io` while the workspace held a bad docker.io credential;
  - the bound service failed with "docker.io refused this service's registry credential for the image docker.io/traefik/whoami:v1.10.1 (HTTP 401). Check the credential's username and token, or remove the credential from this service to pull a public image anonymously";
  - an unbound credential deletes with 204.
- **Dedupe:**
  - w4/186 (done) fixed the dialog's promise;
  - w4/474 (done) made credentials apply only to services that select them, and its probe shows the same CR-name message without flagging it;
  - w4/m301 (blocked) owns the rule.
  - `grep -rli "is still used by service" .pm` finds only those.
  - Not deploy lag: the only newer change under `registrycreds` on `origin/main`, `c769dc69c` (w4/577), validates hosts and does not touch the binding check.
