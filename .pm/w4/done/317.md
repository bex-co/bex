# Match PostgreSQL parameter observations regardless of name case

Why: an applied, valid `timezone` override currently looks pending or invalid because the observation read cannot match PostgreSQL's `TimeZone` spelling.

**Status:** done — the remaining lowercase/canonical, API/UI and cleanup live gate passes in a886, 2026-10-17. Original filing and implementation notes below are historical.

**Severity:** minor. The setting applies; its diagnostic state misleads the user. **Estimate:** 55m (shared lookup 10m, regression and surface checks 25m, inline simplify 5m, live acceptance 15m). Filing only.

Source: continuous `$qa-find-bugs w4`, 2026-10-15 UTC, pass a642. Native dashboard settings on an owned Free/private PostgreSQL 18 instance, `dpg-db8m0cg3260c738as7b0` (`qa-20261015-a642-params`). Complete relevant requests, responses, fresh ready-state ARIA snapshots, passing controls, and cleanup are in [evidence/317-parameter-name-case.json](../evidence/317-parameter-name-case.json).

## Reproduction

1. Record the three settings through the native SQL console: `SELECT name, setting, unit, source FROM pg_settings WHERE lower(name) IN ('timezone', 'work_mem', 'default_statistics_target') ORDER BY lower(name);`. Baseline at 23:24:45.326Z is `TimeZone=Etc/UTC`, `work_mem=4096 kB`, and `default_statistics_target=100`.
2. Insights → Parameter overrides: save `timezone=Europe/Berlin`, `work_mem=6MB`, and `default_statistics_target=125`. The native `SetDatabaseParameterOverrides` returned 200 at 23:25:24.413Z.
3. At 23:26:07.333Z, the same SQL query shows **all three applied**, from `configuration file`: `TimeZone=Europe/Berlin`, `work_mem=6144 kB`, and statistics target 125. At 23:26:09.172Z, `databaseParameterSpec` reports the numeric settings as `observed` but `timezone` as `not_observed`, with both observed fields null.
4. A fresh 390px page at 23:26:36.158Z says beside `timezone`: “Requested override not observed. It may be pending or invalid.” The other two rows show their live values.
5. Change only that declared name to canonical `TimeZone`, preserving its value and both siblings. Native save 200 at 23:26:54.641Z; the23:26:57.500Z read immediately reports `TimeZone` as `observed`, with `observedSetting: "Europe/Berlin"`.
6. Change the name back to lowercase, native save 200 at 23:27:20.625Z. A fresh desktop page at 23:27:50.215Z repeats the warning. REST `GET /v1/postgres/{id}/parameters` and MCP `list_postgres_parameters` at 23:28:22.302Z return the same false absence, including MCP's text and structured results. A second native SQL read at 23:28:44.519Z still shows all three applied.

PostgreSQL 18 explicitly documents that parameter names are case-insensitive ([Setting Parameters](https://www.postgresql.org/docs/18/config-setting.html#CONFIG-SETTING-NAMES-VALUES)). This is an accepted configuration with a false observation, rather than an invalid setting or a delayed reload.

## Cause and bounded fix

- `lego/backend/internal/postgres/insights.go:370` reads non-default `pg_settings` rows with PostgreSQL's name spelling. `ParameterSpec` at:656–674 passes those observations and the original declaration map to `parameterSpecViews`.
- At:677–688, that helper indexes `byName[row.Name]` and looks up `byName[name]` with exact Go string equality. `TimeZone` therefore cannot corroborate a declaration named `timezone`.
- Fold **only the observation lookup keys** consistently on both sides. Preserve each declared name and value verbatim, the stable output ordering, normalized observed setting/unit, and the existing meaning of `observed`: a non-default runtime setting exists for this name; it does **not** promise the requested value has applied. Do not rewrite configuration maps, validate new setting names, change duplicate-name policy, or alter operator/CNPG behavior in this fix.
- Extend `parameter_observation_test.go` with differently cased declared/runtime names and preserved declaration spelling/value. Extend the real-Postgres `parameter_observation_pg_test.go` using a connection-local `TimeZone` startup setting and a lowercase declaration, preserving its existing unit normalization, unknown-name and connection-failure controls. Make the new case fail against the old helper. No production mutation belongs in these tests.

**Consumer census:** one production `parameterSpecViews` call, inside `Service.ParameterSpec`. Its three public entrypoints are REST `rest.go:429`, GraphQL `graphql.go:443`, and MCP `mcp.go:509`; all were exercised live. The dashboard's `DatabaseParameterSpec` query feeds `use-database-insights.ts:178`, then `parameter-overrides-editor.tsx:240–259` renders the status. Fix the shared producer; no API shape, client-side status override, or generic table change is needed. `GetParameterSpec` returns the declared map without observations and stays unchanged. The write aliases keep their existing full-replacement behavior.
