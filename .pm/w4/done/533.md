# 533 — Regression of w4/161: a bad-tag deploy over a healthy image web service emits `server_failed` for a service that never went down (image-metadata path)

Why: w4/161 guaranteed that a failing **new** release over a serving prior release is a deploy failure only, with no `server_failed`. Since w4/m243 moved prebuilt-image web services onto image-port discovery, a missing tag fails before any pod is dispatched, with Ready reason `ImageMetadataUnavailable`. The availability projection does not recognise that reason as pre-runtime. Once the deploy row closes, it reads the healthy prior release as down. The Events feed, the `server_failed` webhook and the Critical push rule all fire on a phantom outage, while the app answers 200.

**Severity:** major (false outage notification on the most common deploy mistake, a typo'd tag; nothing is down) · **Estimate:** 45m · **Worker:** worker4 · **Status:** done

- **Source:** live `/qa-find-bugs w4`, production, 2026-11-06 23:02–23:06 UTC, round 204, pin `a3fcf1d5e` (`9f8c280144a5`), workspace `bex-canary`.
- **Probe:** free image web service `qa-20261106-bt204` (`srv-dbn5on90k25c7383pvog`, `docker.io/traefik/whoami:latest`), live, deleted afterwards (`204` → `404`).
  1. `POST /v1/services/<id>/deploys {"imageUrl":"docker.io/traefik/whoami:qa-no-such-tag-204"}` → `201 dep-dbn5pjp0k25c7383pvq0`.
  2. The deploy row read `created` at 2 s and `update_failed` at 26 s, with `failureReason: "image metadata request returned status 404"` (the wording is filed separately as w4/534).
  3. `curl https://qa-20261106-bt204.onbex.co/` about 2 min later → **200**. The prior release kept serving.
  4. `GET /v1/services/<id>/events`:

     ```text
     23:03:34 deploy_ended   succeeded  (the create deploy, whoami:latest)
     23:03:43 deploy_started            (the bad-tag deploy)
     23:04:04 deploy_ended   failed / update_failed, "image metadata request returned status 404"
     23:04:28 server_failed  {"reasonCode":"readiness_failed"}   ← phantom
     ```

     There was no `server_available` before deletion, about 1 min later.
- **Root cause:**
  - `lego/operator/internal/controller/app_controller.go:707-714`: for an image-port service, `resolveImageNetwork` reads the registry before `dispatchRuntime`. On a definitive refusal it calls `r.fail(ctx, &app, "ImageMetadataUnavailable", err)`, so Ready becomes False with that reason. No pod of the new revision exists, and the `ActiveRevision` pods keep serving.
  - `lego/backend/internal/store/reconciler.go:2143-2148` (the check is at `:2146`): the Ready=False branch skips pre-runtime gates through `preRuntimeFailure` (`:2076-2082`), but that list holds only `ProtectedSecretReference`, `PerAppRegistryCredsFailed` and `RegistryPullSecretFailed`, not `ImageMetadataUnavailable`.
  - Once the deploy row closes (`hasOpenDeploy` false, `:2165`), the branch at `:2171-2181` sets `Availability = "unhealthy"`, `ReasonCode = readiness_failed`, because `ActiveRevision != ""`. That is exactly the prior-release case w4/161 said must not mint an outage.
  - `store/event_facts.go` turns healthy→unhealthy into `EventFactServerFailed`, and webhooks and pushes carry it (w4/161's blast radius).
- **Fix — target behavior:** availability describes what is serving. A release that failed **before runtime dispatch** (any operator `r.fail` reason raised before `dispatchRuntime`) says nothing about the serving release: no `server_failed` and no later `server_available`, and the prior release stays `healthy`. The failure stays on the deploy row (`failureReason`, `deploy_ended`).
  - Add `ImageMetadataUnavailable` to `preRuntimeFailure`.
  - Better still, have the operator say so structurally rather than through a name list: either a `PriorReleaseServing`-style Serving=True condition on the pre-dispatch fail path, or the reason list exported from `lego/types` next to the reason constants. Then the next pre-dispatch reason cannot regress this silently.
  - Keep the first-deploy case and a crash-looping **serving** revision reporting as w4/161 left them.
- **Blast radius:**
  - `r.fail` is called with 14 distinct reasons across `lego/operator/internal/controller` (grep of `r.fail(ctx, …, "<Reason>"`: DeployFailed ×10, BadSpec ×6, ServiceFailed ×4, PerAppRegistryCredsFailed ×2, ImageMetadataUnavailable ×2, and one each of WorkerCleanupFailed, StaticUnavailable, StaticCredentialUnavailable, StaticCleanupFailed, RegistryPullSecretFailed, ProtectedSecretReference, PauseFailed, MaintenanceRoutingFailed, EndpointFailed).
  - Classify each as pre-dispatch or not, and add tests for every pre-dispatch one over a serving release.
  - The second `ImageMetadataUnavailable` site (`app_controller.go:852`, "served release has no matching image network metadata") needs its own verdict.
  - Consumers: Events, `server_failed`/`server_available` webhooks, Critical push.
- **Tests:** a store test where Ready=False with reason `ImageMetadataUnavailable`, `ActiveRevision` set, a serving observation healthy, and no open deploy → no `server_failed`. Regression controls: w4/161's ImagePullBackOff-over-serving case, a crash-looping serving revision (still `server_failed`), and the first deploy.
- **Unverified:**
  - Whether availability stays `unhealthy` until the next successful deploy (no `server_available` was seen in the ~1 min before deletion).
  - Whether the push or webhook was actually delivered (the fact was observed; delivery was not).
  - Repo-backed services, which do not take the image-port path.
- **Render:** a failed deploy over a live service shows "Deploy failed" while the service stays live. No server-failed event or alert fires.
- **Dedupe:**
  - w4/161 (done 2026-09-27, live-verified 2026-09-28 with a bad tag) is the guarantee that regressed. Its fixture went through `ImagePullBackOff` because image-port discovery did not exist yet. w4/m243 (done, 2026-10) added the pre-dispatch metadata read that now fails first.
  - w4/422 (done) saw the same `server_failed readiness_failed` beside an `image metadata request returned status 429` failure but filed the env-size cause.
  - No open item names this. Not in `DO_NOT_DO.md`.
- **Same round:** the bad tag now fails in 26 s instead of 15 min (w4/162's goal holds), and the prior release kept serving 200.
- **Cleanup:** `qa-20261106-bt204` deleted (`204` → `404`). This run's session was revoked.

  - At 23:21:27 the subject got `POST /deploys {"imageUrl":"docker.io/traefik/whoami:qa-no-such-tag-205"}`. All three were deleted afterwards (`204`).
- **Observed, polled every 20 s for 6 min:**
  - `deploy_ended(failed)@23:21:48`, then `server_failed(readiness_failed)@23:22:09`. Reproduced a second time.
  - **Webhook delivered:** `server_failed` sent at 23:22:14, and the receiver answered `200`. This settles the earlier Unverified line: the phantom outage does reach webhook subscribers.
  - **No `server_available` in 6 min.** The service stays "failed" until something else changes it.
  - **GraphQL `phase: "Failed"` the whole time**, while `curl https://qa-20261106-pf205.onbex.co/` answered `200` every 30 s from 23:24:03 to 23:27:51.
  - **Dashboard:** the detail header read `Service Failed` / `Latest deploy: Failed`, and the Overview row read `qa-20261106-pf205 Web Service Failed`. Screenshot (local, repo root, gitignored by `/*.png`): `qa-deploys-205.png`.
- **This also regresses w4/m103 DoD item 3** ("A rollout failure over a healthy prior release does NOT change the phase … the service keeps reading the state that describes what is actually serving").
- **Corrected root cause (operator, not only the store):**
  - `lego/operator/internal/controller/app_controller.go:6572-6603` `fail()` restores the prior release, via `settleFailureOverPriorRelease`, Running phase and Ready describing the serving release, **only** for `IsBuildFailureReason(reason)` over a release that has served (`:6582-6599`).
  - Every other reason falls through to `app.Status.Phase = PhaseFailed` plus a Not-Ready condition (`:6601-6602`). `ImageMetadataUnavailable` (`:712-714`) is raised before `dispatchRuntime` over a serving release, so the service reads Failed. The store then reads Ready=False as an outage (`store/reconciler.go:2171-2181`), which is the `server_failed` above.
- **Fix, preferred:**
  - In `fail()`, treat every pre-dispatch reason over a release that has served the way build failures are treated: call `settleFailureOverPriorRelease(ctx, app, "the image could not be read")`.
  - The phase then stays Running, Ready describes the serving release, and the store needs no name list. Adding `ImageMetadataUnavailable` to `preRuntimeFailure` alone would fix the events but leave the phase and the dashboard reading Failed.
  - The deploy row keeps `update_failed` and its reason, the w4/534 wording.
- **Severity stays major:** a correct service reads Failed on every surface and pages webhook subscribers after the most common deploy mistake.
