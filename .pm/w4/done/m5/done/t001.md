## Objective

Write the ADR that anchors the tenant-secrets substrate: why OpenBao (Linux Foundation fork of Vault, MPL-2.0 — passes the same governance test as Ory/CNPG in docs/auth.md §1, whereas Vault itself is BUSL), what it stores (tenant runtime credentials, explicitly NOT the platform's own deploy secrets — that's w1/m7 t003), which storage backend (integrated Raft on a PVC vs a CNPG Postgres cluster like `kratos-db`/`hydra-db`), and the unseal strategy (static unseal keys held out-of-band in `.env`, re-unseal on pod restart via script, vs auto-unseal options).

## Context

- Pattern to follow: `docs/auth.md` (the Kratos+Hydra ADR) — context / decision / verification / alternatives / consequences, mermaid diagram.
- Alternatives to reject with reasons: HashiCorp Vault (BUSL license), External-Secrets-Operator-only (sync tool, not a store), Infisical (heavier, less standard API), plain k8s Secrets (etcd plaintext, no versioning/policy/audit).
- The consumer story: bex-api (m6) authenticates via the Kubernetes auth method and reads/writes `tenants/<tenant>/services/<app>/env`.
- Boundary statement: tenant runtime credentials ≠ platform git secrets (w1/m7 t003 sealed-secrets/SOPS).
