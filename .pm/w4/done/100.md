# Events feed calls a Settings-edit deploy "Environment updated" while the deploys list calls it "Config Change"

Why: the same deploy shows two different triggers on two surfaces, and "Environment updated" is factually wrong when no environment value changed — a Settings edit (start command, schedule) misleads the reader about what happened.

## Record

- Severity: minor
- Repro: on a cron job (or any service), Settings → edit the Command → Save changes; open the Deploys tab (row reads Trigger "Config Change") and the Events tab (row reads "Deploy started / Environment updated"). Live 2026-09-19: `qa-20260919-p19-cron` fixture, since deleted; deploy `dep-dan5uv12dbts73fi29sg` (command `echo p20-v1` → `echo p20-v2`).
- Expected / Actual: both surfaces name the one trigger the same way ("Config Change") / deploys says "Config Change", events says "Environment updated".
- Root cause: the backend maps `store.TriggerConfigChange` onto the Render-shaped `envUpdated` flag for every config write — "the nearest flag in its vocabulary for the deploys a Settings field, env var, secret file, or env-group link now opens" (`lego/backend/internal/events/service.go:727-731`) — and the dashboard renders that flag as the literal `services.eventsTriggerEnvUpdated` = "Environment updated" (`dashboard/src/routes/services.$serviceId.events.tsx:75`, copy in `dashboard/src/features/services/locales/en.ts:3581` + `zh.ts:3505`), while the deploys list maps the same trigger string to `deploys.triggerConfigChange` = "Config Change".
- Fix: rename the events label to the shared "Config Change" string (en + zh + the events test), since the flag now covers all config writes. Do NOT split the backend flag — Render's vocabulary has no finer trigger and the deploys list already settled the wording.
- Blast radius: events-feed trigger label only; the only non-generated consumer of the flag is `services.$serviceId.events.tsx:75` (plus GraphQL/REST pass-through, untouched).
- Adjacent classes: other triggers (Rollback, Manual deploy, First build, Cache cleared, Platform deploy) keep their existing events labels; only the `envUpdated` → text mapping moves.
- Unverified: nothing — both surfaces probed live on the same deploy.
- Render: n/a (Render has no per-service events feed with trigger labels; the fix aligns bex's own two surfaces).
- Estimate: 20m

## Resolution (2026-09-21)

Done as filed, and exactly as scoped: the events label for the `envUpdated` flag is now the shared **"Config Change"** string (en + zh), matching what the Deploys tab has always said. The backend flag was **not** split — Render's trigger vocabulary has no finer name for a config write, and the deploys list had already settled the wording.

Shipped together with `w4/104`, its sibling: both are the same defect class (the events feed renaming a trigger the deploys list already names), they touch the same `triggerKey` function and the same locale files, and fixing one without the other would have left the feed half-corrected.

Covered by `ServiceEventsPage — a deploy's trigger is named the way the Deploys tab names it`, which asserts the new label *and* the absence of the old one, plus a regression case pinning that an API deploy is still "Manual deploy". Verified failing against the pre-fix copy by stash-run. Not re-probed live — no production access this session.
