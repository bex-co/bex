## Resolution (2026-08-16)

`mobile/src/features/notifications/registration-controller.ts`'s `unregisterCurrent` flipped the local preference to disabled and reported `"disabled"` **before** calling the server's `unregister` — a failed remote call left the app believing push was off locally while the server-side device row stayed bound to the old subject, and `inspectAndRepair` never re-registers a device whose local preference already says disabled, so ownership never self-healed. Reordered: the remote `unregister` call runs first; the local preference and state only flip on success. The existing test (`registration-controller.test.ts`) encoded the old order as intended behavior ("disables locally before a best-effort remote unregister fails") — rewritten to assert the fix ("keeps the local preference enabled when the remote unregister fails"), plus a new test for the success path. `yarn test:unit`, `yarn typecheck`, `yarn lint` all green.

## Objective

Close `029.md` finding #15: a failed remote unregister must not strand the server-side device row bound to a signed-out subject.

## Files

- `mobile/src/features/notifications/registration-controller.ts`
- `mobile/src/features/notifications/__tests__/registration-controller.test.ts`

## Acceptance criteria

- [x] `unregisterCurrent` calls the remote `unregister` before mutating local state.
- [x] A failing remote call leaves the local preference enabled (so a later `inspectAndRepair` can retry/re-register under the new subject).
- [x] A succeeding remote call still disables locally as before.
