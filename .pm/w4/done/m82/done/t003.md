## Resolution (2026-08-16)

`registrycreds.Service.Delete` removed the Postgres metadata row and the OpenBao secret value but never touched the derived per-App `<app>-registry-pull` Kubernetes Secret(s) — those Secrets carry no ownerRef by design (materialized before the App CR may even have a UID) and are only reaped on the App's own delete, not the credential's, so a deleted credential's password lived on indefinitely in any still-referencing App's namespace.

`Delete` now calls a new `appBoundToCredential` (in `pullsecret.go`, alongside the existing pull-secret materialization logic it mirrors) that lists Apps in the credential's workspace namespace and checks both binding paths `materializePullSecret` itself resolves through: explicit (`spec.registryCredentialId == id`) and implicit (an unbound App whose image's registry host matches `cred.Host`). A match refuses the delete with `core.NewConflictError("REGISTRY_CREDENTIAL_IN_USE", …)` (409), naming the blocking App so the caller knows what to unbind first.

New tests in `service_test.go`: explicit-binding refusal, host-match refusal, and an "explicit binding to a *different* credential must not false-positive via host match" case (explicit always overrides implicit). `newTestService`'s fake `Service` now carries a fake k8s client so the existing tests exercise the real (empty-result) list path rather than skip it. `go build ./... && go vet ./... && go test ./internal/registrycreds/...` all green.

## Objective

Close `029.md` finding #12: "registry credential delete ≠ revoke" — deleting credentials must not leave a live, unrecoverable Secret behind.

## Acceptance criteria

- [x] Deleting a credential still explicitly bound to an App is refused with a 409-mapped error.
- [x] Deleting a credential an App reaches only via legacy host-match is also refused.

- [x] Deleting an unbound credential still succeeds and still clears the row + secret.
