## Objective

One load of `/services/<srv-id>/metrics` issues 25–34 separate GraphQL POSTs, several of them duplicates of each other. That fan-out is what pushes a single user's page load over the per-credential concurrency budget (t001), and the duplicates are also what accidentally hides the resulting failures — a shed query's chart renders fine because its twin succeeded. Collapse the fan-out.

## Context

Measured on production, 2026-09-13, one load of `https://dashboard.bex.co/services/srv-daj6sj0gsm7s73f63nmg/metrics`:

- 25 GraphQL POSTs on one load (2 × 429), 34 on another (8 × 429), 25 again on a third (2 × 429). The count moves with what else the route fetches.
- Duplicates observed: `Metrics` with `name: "INSTANCES"` was issued more than once per load — one instance shed with 429 while another returned 200, so **Total Instances still rendered a value**. Same for `MetricsFilters` with `outputFilters: ["STATUS_CODE"]`: one shed, yet the Status Code dropdown still listed `All / 2xx / 4xx / 5xx / 200`.
- Steady state is *not* the problem: with the page open and idle for 180s, only 25 requests went out, none of them `Metrics` — `ViewerCapabilities` ×6, `Workspaces` ×6, `Deploys(limit:1)` ×5, `Server` ×5, `MonthToDateBandwidth` ×3. The charts do not poll aggressively; the **initial load** is the burst.

Call sites and wiring:

- `dashboard/src/features/metrics/components/application-metrics-card.tsx` — one `useMetrics` per series (`cpu`, `memory`, `cpu_limit`, `memory_limit`, `cpu_target`, `memory_target`, `instance_count`).
- `dashboard/src/features/metrics/components/network-metrics-card.tsx` — `http_requests`, `http_latency`, `bandwidth`.
- `dashboard/src/features/metrics/hooks/use-metrics.ts:137-178` — each hook is its own `useQuery(MetricsDocument, …)`, so each is its own HTTP POST.
- `dashboard/src/features/metrics/hooks/use-metrics-filter-values.ts` — the `MetricsFilters` reads.
- `dashboard/src/common/apollo/factory.client.ts` — a plain `HttpLink`, no batching.

`w6/028` recorded this same fan-out (17–20 POSTs) and closed it as *"efficiency, not correctness"* because it believed the only budget in play was `BEX_RATE_LIMIT`. It is correctness: see the milestone README's Source section and t001.

## Steps

1. Find and remove the **duplicate** operations first — the same `Metrics(INSTANCES)` and `MetricsFilters(STATUS_CODE)` being requested twice per load is redundant work regardless of any budget, and it is what masks failures. Prefer one shared hook/query whose result both consumers read over letting Apollo's cache coincidentally dedupe (it demonstrably did not here: both hit the network).
2. Collapse the remaining per-series reads. Two shapes to weigh, picking one: GraphQL **aliases** in a single document (one POST, one `metrics` field per alias — no server change, no batch-link semantics to reason about), or an Apollo **batch link** (applies to every page, but changes error attribution and cache behavior app-wide). Record why.
3. Keep the per-series *loading* and *error* identity intact — a chart must still be able to show its own pending and failed state after the collapse, which t003 depends on. A single combined query that fails wholesale must not turn one shed series into a blank page.
4. Re-measure: load the page once with a healthy bucket and record the GraphQL POST count.

## Out of scope

- The backend concurrency budget (t001) — this task reduces the load, it does not fix the limit.
- The chrome's `ViewerCapabilities` / `Workspaces` / `Server` / `Deploys` polling cadence, which measured at ~8 requests/min per open tab. Real but separate; file it if it still looks wrong after this lands.

## Resolution

Fix landed: per-cred knob + `AUTH_OVERLOADED`; GraphQL batch + `BatchHttpLink`; throttle UI; commit carry via `LatestDeployCommit`.
