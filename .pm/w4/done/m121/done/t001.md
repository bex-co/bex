## Objective

Give a service's port an update path. Today `apps.Service` has 23 `Set…` mutators and none of them is `SetPort`, so the port chosen at create is permanent on every surface; `PATCH /v1/services/{id}` answers `400 bad request: request body contains unknown field "port"`. Add the verb once in the service layer and thread it through REST, GraphQL and MCP so all three move together (ADR006).

## Context

- `lego/backend/internal/apps/service.go:2513-2522` — `normalizeCreateDefaults` bounds-checks `req.Port` (`1-65535`, `0` ⇒ `appv1alpha1.DefaultPort`). Reuse that validation; do not write a second one.
- `lego/backend/internal/apps/service.go:2772` — `applyCreateToSpec` already copies `dst.Port = want.Port`; only create calls it.
- `lego/backend/internal/apps/service.go:3167-4077` — the existing `Set…` mutators and the shared `patch`/`patchTracked`/`patchUntracked` helpers. `SetHealthCheckPath` (`:3779`) is the closest shape: a single scalar that changes how traffic reaches the container.
- `lego/backend/internal/apps/rest.go:321` and the `patchServiceRequest` struct above it — REST's patch decoder; the unknown-field refusal comes from its strict decode.
- Changing the port changes routing, so it must open a deploy the way a config change does, not mutate silently — follow whichever of `patchTracked` / `patchUntracked` the routing-affecting siblings use, and record which and why.

## Steps

1. Add `func (s *Service) SetPort(ctx context.Context, name string, port int32) (AppView, error)` next to `SetHealthCheckPath`, validating through the same bounds `normalizeCreateDefaults` uses and refusing the port for App types that expose no port (see t005 for the type list — this task only needs the guard to exist).
2. Decide whether a port change is tracked (opens a deploy) or untracked, using the routing-affecting siblings as precedent. Write the reason into the function's doc comment.
3. REST: add the port field to `patchServiceRequest` (Render spells service configuration under `serviceDetails` — match the neighbours' placement rather than inventing a top-level key, and say which you chose) and wire it to `SetPort`.
4. GraphQL: add the matching mutation argument next to the other per-field setters.
5. MCP: add the port argument to the service update tool that already carries the sibling scalars.
6. Confirm the refusal for portless types is identical on all three surfaces — same code, same sentence.

## Acceptance criteria

- [x] `PATCH /v1/services/<id>` carrying the port returns `200` and the new value survives a following `GET`.
- [x] The same change through GraphQL and through MCP produces byte-identical stored state (asserted, not assumed).
- [x] An out-of-range port (`0`, `65536`, negative) is refused with the same coded 400 on all three surfaces.
- [x] A port change on a `background_worker`, `cron_job` or `static_site` is refused with one shared coded error.
