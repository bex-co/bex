## Objective

Check that the port field this milestone adds is consistent across every surface it touches — REST, GraphQL and MCP in `lego/backend/` (same field name, same semantics, same error shapes per `docs/ADR006-bex-api.md`) and the `dashboard/` UI — and compare against render.com's equivalent behavior, recording drift as drift rather than diverging silently.

## Context

- Render has **no** port setting: it detects the port the service binds and documents `PORT` as a user-overridable variable. bex refuses `PORT` (ADR018 row 117, `w2/m95`) and instead owns the port on the spec. So the bex port field is an **extension**, and the ledger must say so with that word.
- `docs/ADR018-render-parity.md` is the ledger; the MCP column is hash-pinned (`render-mcp-tools.json`, `TestMCPParity*`) — adding an MCP argument moves a row's classification, so check what it moves to.

## Steps

1. Diff the port field across REST, GraphQL, MCP and the dashboard: name, type, bounds, default, refusal code for portless types, and read-back shape.
2. Re-run the MCP parity guard and record the resulting classification change for the affected tools.
3. Update `docs/ADR018-render-parity.md` row 117 (and any adjacent row this touches) with the extension, the surfaces, and the reasoning.
4. File any drift found and not fixed here as a follow-up inbox note rather than leaving it unrecorded.
