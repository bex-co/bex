# 596 — A service read carries no `serviceDetails.autoscaling`, where Render's schema puts the policy, so a Render client sees autoscaling as unset on a service that has it on

Why: Render's `webServiceDetails`, `privateServiceDetails` and `backgroundWorkerDetails` each declare `autoscaling`, in the same `{enabled, min, max, criteria}` shape `PUT /services/{id}/autoscaling` takes. bex returns its own dialect at the top level instead. A Render CLI, SDK or Terraform client that reads the service object finds no policy.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 164, 2026-11-12 03:53–03:57 UTC (`muse.env`, workspace `bex-canary`; pin `e7a56b07e0d7`). **Minor** (API parity; the dashboard and the `/autoscaling` subresource are right). ~30m.
- **Fixture:** Starter private service `qa-20261112-r164-sc` (`srv-dbqjg8urbf4s73esttu0`, `traefik/whoami:v1.10.1`), deleted afterwards.
  - Scaling → Manual 1 → 2 → Save.
  - Then Autoscaling on, Minimum 1, Maximum 2, Target CPU on (60%) → Save.
- **Probe**, from the signed-in page:
  - `GET /v1/services/srv-dbqjg8urbf4s73esttu0/autoscaling` → `{"enabled":true,"min":1,"max":2,"criteria":{"cpu":{"enabled":true,"percentage":60},"memory":{"enabled":false,"percentage":0}}}`. This is correct, and Render's shape.
  - `GET /v1/services/srv-dbqjg8urbf4s73esttu0`:
    - `serviceDetails` keys are `env, internalAddress, maxShutdownDelaySeconds, numInstances, openPorts, plan, port, region, runtime, sshAddress`, with no `autoscaling`;
    - top-level `autoscaling` is `{"enabled":true,"minInstances":1,"maxInstances":2,"targetCPUPercent":60}`.
- **Render's contract (pinned `lego/backend/internal/api/openapi/render-public-api-1.json`):** `webServiceDetails`, `privateServiceDetails` and `backgroundWorkerDetails` all list `autoscaling`, with `$ref` to the `PUT …/autoscaling` request schema. It is optional, so the response validator (`internal/rendertest`) doesn't catch the omission.
- **Root cause:**
  - `renderServiceDetails` (`lego/backend/internal/apps/render.go:456-`) never sets `autoscaling`.
  - The top-level field `Autoscaling *renderAutoscaling` (`render.go:213-216`, struct `:273-279`; the `BuildSourceID` field sits just above it) uses bex's GraphQL/MCP dialect. Its comment wrongly calls that "Render's autoscaling sub-object".
  - ADR018's autoscaling row (`docs/ADR018-render-parity.md:99`) records "Nested `service.autoscaling` on list/detail remains the bex dialect (documented extension)". The extension is documented; the missing Render field is not.
- **Fix (target behavior):**
  - For a web, private or worker service with autoscaling configured, list and retrieve carry `serviceDetails.autoscaling` in Render's shape. Use the subresource's mapper, `renderAutoscalingConfigFromView` (`render.go:328-`, used by `rest.go:1393-1399`), so the two reads can't disagree.
  - Keep the top-level bex field. Fix its comment, and record both in ADR018's autoscaling row.
  - **Disabled:** emit `{"enabled":false,…}` as the subresource does when a policy was stored, and omit the field when none ever was. Render's choice here is unverified.
  - REST only: GraphQL and MCP keep their own dialect.
- **Blast radius:**
  - `renderServiceDetails` serves list, retrieve, create and update responses.
  - `rendertest` should gain a positive check that a configured service carries the field.
  - Cron and static types must stay without it, per the w4/m101 type rules.
- **Unverified:**
  - What Render returns for a service whose autoscaling is off, or was never set.
  - Whether the official CLI's `services` output prints this field.
- **Render:** see the contract above.
- **Dedupe:**
  - w5/m146 (done) took `serviceDetails.autoscaling` on **create** input only.
  - w4/m104 (done) set the subresource's Render wire shape.
  - `grep -rn "serviceDetails.autoscaling" .pm` finds only those two.
  - Not deploy lag: `renderServiceDetails` has no newer change on `origin/main`.
- **DoD (live):** on an owned Starter private service in `bex-canary`, enable autoscaling (1–2, CPU 60%):
  - `GET /v1/services/{id}` carries `serviceDetails.autoscaling` equal to `GET …/autoscaling`'s body;
  - the top-level bex field is unchanged.

- **2026-11-11 (loopx w4):** done. List and retrieve put Render's `serviceDetails.autoscaling` on a web, private or worker service with a policy (`renderServiceDetails`, `lego/backend/internal/apps/render.go`). They use `renderAutoscalingConfigFromView`, the mapper `GET …/autoscaling` uses, so the two reads agree. The field is omitted when no policy is configured, and on cron jobs and static sites. The top-level bex field stays, with its comment corrected, and ADR018's autoscaling row records both. `TestRESTServiceReadCarriesServiceDetailsAutoscaling` checks the read against the subresource through the Render response validator. It also covers a service without autoscaling and a cron job. A disabled policy reads `{"enabled":false,…}` once one is kept (w4/597); today a disable removes the policy, so the field is omitted.
