## Objective

After `restartDatabase` / `POST /v1/postgres/{id}/restart`, the API must not read `available` again until the restart has actually happened. Today it briefly reads `available` for about 1.7 s, then `config_restart` for about 21 s, then `available`. The dashboard's single post-verb refetch lands in that first window, so the header never shows the restart (DoD bullet 2 fails on the dashboard surface).

## Context

- Live evidence (2026-10-05, production `24482892a`, fixture `dpg-db1h4j68inbs73f0v7e0`, deleted):
  - REST restart response `config_restart` at 03:33:52. The next reads, polled every ~200 ms, were `available` ×3 (about 1.7 s), then `config_restart` ×40 (about 21 s), then `available`.
  - The dashboard Restart Database click ran at 03:31:48. Its eager `Database` refetch at 03:31:48 read `available`. The next reads came only on the 30 s cadence (03:32:19, 03:32:49), while psql was refused from 03:31:52 to 03:32:10. The header read "Available" throughout.
- Mechanism:
  - `Restart` (`lego/backend/internal/postgres/lifecycle.go:72-86`) patches `spec.restartedAt`, which bumps `metadata.generation`. The mutation response therefore reads `config_restart` via `core.DatastoreReadyStatus` (`lego/backend/internal/core/datastore_status.go:45-54`, `ObservedGeneration < generation`).
  - The operator's next reconcile copies the annotation to the CNPG Cluster (`setLifecycleAnnotations`, `lego/operator/internal/controller/database_controller.go:1363`). Then `reconcileDatabaseReadiness` (`:1316-1326`) reads `status.readyInstances`, which CNPG has not lowered yet. It sets `Ready=True` with `ObservedGeneration` equal to the new generation, so the stale-Ready guard is satisfied and `dbStatus` returns `available`.
  - The dashboard side is `useDatabaseLifecycle.run` → `refetch` → `eagerRefetch` (`dashboard/src/common/lib/polling.ts:27-33`). The mutation result (`config_restart`) flips `isConverging` true, and the refetch's `available` flips it false. `useConvergingPoll` (`:47-60`) then resets to `RESOURCE_POLL_INTERVAL_MS` (30 s), cancelling the eager 3 s cadence.
- Key Value does not show this gap (a config save on an open page read "Restarting" exactly while `redis-cli` was refused, 2026-10-05). The difference is CNPG's asynchronous reaction to the annotation.

## Steps

1. On the local CAPD cluster, confirm how CNPG acknowledges `kubectl.kubernetes.io/restartedAt`: whether instance pods carry the annotation after the rollout, and whether the Cluster phase or a condition changes before `readyInstances` drops. Pick an acknowledgement signal from observed objects, not from memory.
2. Operator: do not set `Ready=True` for a generation whose `spec.restartedAt` CNPG has not yet acknowledged and finished. Keep the phase non-Ready, so `dbStatus` returns `config_restart` via `DatastoreNotReadyStatus(Provisioned)`. Bound the wait so a CNPG that ignores the annotation cannot wedge the store.
3. Dashboard, defence in depth (decide in-task whether to keep): after a lifecycle verb, keep the converging cadence for a short bounded grace window rather than letting the first settled read cancel it.
4. Tests: an operator envtest/unit test where a restart generation with `readyInstances` still full stays non-Ready until acknowledgement, and the bound releases it. A dashboard hook test for the grace window, if kept.

## Progress (2026-10-05)

Implemented; the live replay remains (it needs the operator deploy).

- **Acknowledgement signal, from CNPG v1.30.0 source** (chart `cloudnative-pg` 0.29.0, `deploy/helm-artifacts.lock`). `checkClusterHasDifferentRestartAnnotation` (`internal/controller/cluster_upgrade.go:607-622`) rolls every instance Pod whose `kubectl.kubernetes.io/restartedAt` differs from the Cluster's. The Pod it brings back carries the Cluster's value: `cluster_create.go:1569-1574` for a recreated Pod, and `updateRestartAnnotation` (`cluster_upgrade.go:278-298`) for an in-place primary restart. `readyInstances` does not drop until CNPG acts, which is the gap the API was reading.
- **Operator** (`lego/operator/internal/controller/database_controller.go`): `restartPending` holds `reconcileDatabaseReadiness` off Ready while `spec.restartedAt` is on the Cluster and fewer than `desiredInstances` non-terminating, PodReady instance Pods (`cnpg.io/cluster=<name>`, `cnpg.io/podRole=instance`) carry that value. The phase stays `Provisioning` with Ready reason `Restarting`, so `dbStatus` reads `config_restart` through `DatastoreNotReadyStatus(Provisioned)`. While a restart is pending the reconcile requeues every 3 s, because nothing watches CNPG Pods for this reconciler. `restartRolloutBound` (10 min) stops the hold so a CNPG that ignores the annotation cannot wedge the store. The Pod cache is unfiltered (only Secrets are scoped, `secret_cache.go`), and the operator already holds cluster-wide `pods get;list;watch`.
- **Dashboard (step 3): not needed.** With the hold in place the API is monotonic: from `restartDatabase` (generation bump, `DatastoreReadyStatus` stale-Ready guard) until the last instance is back, every read is `config_restart`. The detail page's post-verb `eagerRefetch` therefore sees a converging status and keeps the 3 s cadence.
- **Tests** (`database_restart_test.go`): the instance still carries the old restart, so the Database stays not Ready with reason `Restarting` and a ≤3 s requeue, then becomes Ready for the new generation once the instance carries it. A restarted but not-yet-ready instance does not count. The hold is bounded. Both behavior tests fail with the hold disabled, and the bound test fails with the bound removed.
- **Checks:** operator `make test` (envtest, controller 85.9%) and `make lint` (all four modules, 0 issues) pass.
- **Remaining:** ship and deploy, then replay on production. A REST restart polled every ~200 ms must never read `available` before psql answers, and a Restart Database click on the open detail page must show "Restarting" while psql is refused. Then t007 closes the milestone.
