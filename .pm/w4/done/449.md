# A fast prebuilt-image deploy closes Live without a start time

Why: when a prebuilt-image release rolls out between observer passes, its deploy goes straight from created to live and is stored with no `startedAt`. REST then omits it, GraphQL returns an empty value, and the detail shows no Started or Duration, although the rollout ran and the operator saw it begin. This is the same class of loss as w4/316 (fast failed pre-deploys), on the success path.

- **Source / severity / estimate:** w4/316 live replay, loopx w4, 2026-11-01 (`bex-canary`, pin `d147703d7657`); **minor**, ~45m.
- **Evidence:** a Starter BusyBox image web service `qa-20261101-9d3b80-316` (`srv-dbja0phf06vc73aao820`); its first deploy `dep-dbja0phf06vc73aao82g` reads `{status: live, createdAt: 02:13:58.68Z, finishedAt: 02:14:16.09Z}` with **no `startedAt`** (REST). Later deploys that the observer saw in progress, or that 316's failed-pre-deploy rule covers, carry one.
- **Cause:** `lego/backend/internal/store/reconciler.go:957-966` supplies a start only from `buildRunStart` (a build window) or, since 316, `failedPreDeployStart`. A prebuilt image has no build window, so a direct `created → live` close passes `nil`. `TransitionDeploy`'s `COALESCE(started_at, $9)` keeps it unknown.
- **Fix direction:** for a live close with no build window, take the start from the operator's own rollout evidence for this release generation, for example the App status' rollout/serving-revision transition time or the Deployment's `Progressing` NewReplicaSetCreated time for the matching revision. Use the same attribution discipline as 316: stale, other-generation, zero or malformed evidence leaves it unknown, and the observation clock is never used as evidence. Keep an observed in-progress start unchanged.
- **Tests:** a reconciler test for a direct `created → live` prebuilt close with a matching rollout start (start set) and with a stale one (start unknown), plus the existing build and pre-deploy cases.
- **Render:** `startedAt` is an optional field of Render's Deploy, but Render's dashboard shows start and duration for image deploys. Exact authenticated parity is unverified.
- **Dedupe:** w4/316 covered `pre_deploy_failed` closes only. No open item covers prebuilt live closes. No DO_NOT_DO item applies.

**Done (loopx w4, 2026-11-01).** The operator now records `status.releaseStart {generation, startedAt}` when a pass moves `ReleaseGeneration` forward (`stampReleaseStart`, `release_identity.go`). A cancel's revert or a survivor's redispatch never re-stamps. A live close with no build window takes that record as its start only when the generation is the row's own (`releaseDispatchStart`, `store/reconciler.go`). A stale, malformed or zero record leaves the start unknown, and an observed in-progress start is kept by `COALESCE`. Tests: `TestReconcileImageDeployFirstSeenLiveUsesReleaseDispatch` (own, other generation, malformed, zero) and `TestStampReleaseStart`. The m156 unknown-start test is unchanged. Not yet verified live: needs a deploy whose pin includes this commit and the operator image.
