# Global Search retains its previous query after selection or Ctrl+K close

Why: reopening the primary resource navigator keeps an old filter after common close actions, hiding the other destinations until the user replaces the query.

**Severity:** minor. **Estimate:** 55m. Functional `$qa-find-bugs w4` pass a254, 2026-10-11 local / 2026-10-12 UTC. Source checked after syncing main to `fad8e3010369763bae2a71f95e2599dcfdfd4495`. Filing only.

## Reproduction and target behavior

An owned empty project, `qa-20261011-a254-search-雪` / `prj-db651855tvcs738aqorg`, was created in the QA workspace.

1. Freshly load `https://dashboard.bex.co/`, click topbar **Search**, type **a254-search-雪**, and select the project using Enter. Navigation succeeds.
2. Open Search with Ctrl+K. Its input still contains **a254-search-雪**, and other destinations remain filtered out. A preceding mouse-selection trial also retained that query.
3. From a fresh project page, search **Environment Groups**, click its Navigation option, and reopen Search on `/env-groups`. **Environment Groups** remains in the input and filters the list.
4. Reload `/env-groups`, open Search with Ctrl+K, type **Environment Groups**, close with Ctrl+K, wait until the dialog is hidden, and reopen with Ctrl+K. The same query remains. A separate settled Ctrl+K-close/topbar-open trial also retains the project query.
5. Passing controls: type an unmatched query, close with Escape, and reopen: input is empty and normal navigation/resources return. The dialog's **Close** button followed by Ctrl+K also resets to an empty input.

Target: after **each ordinary close action**, the next opening starts immediately with an empty query, matching the existing Escape/Close behavior. Preserve the typed query while the dialog is open, including pending reads. Result selection must still navigate to the selected canonical route.

Replacing the input is a workaround, so this is minor navigation friction. Renaming the owned project to **qa-20261011-a254-renamed-雪** correctly updates search results; its new name and ID fragment match, and the former project name gives settled true-empty. The resource API returns the correct name and ID. No backend indexing failure is asserted.

## Root cause and actual dependencies

- `dashboard/src/common/components/dashboard-layout/global-search-dialog.tsx:50` owns the controlled search state. `:55–58` resets it only inside CommandDialog's onOpenChange callback; `:68–69` feeds it back to the input.
- Result selection bypasses that callback: `:73` passes `close={() => onOpenChange(false)}` directly to SearchResults. `:110–113` calls close before navigation. Both the project template at `:243` and Navigation template at `:227` use this function; the two live symptoms have their own traced selection sites.
- `dashboard/src/common/components/dashboard-layout/global-search.tsx:36–46` handles Cmd/Ctrl+K by directly toggling parent open state at `:41`. `:76` passes that controlled open prop to the child. The dialog remains mounted after its first open (`:13–18,74–78`), so its child search state survives those parent-driven closes.
- Actual installed **cmdk 1.1.1**, pinned in `dashboard/yarn.lock:6430–6432`, was opened in `node_modules/cmdk/dist/index.mjs:1`: the item handler reaches the provided onSelect for click/keyboard selection. Repo `common/components/ui/command.tsx:25–53,66–74` forwards dialog and input props.
- Actual installed **@radix-ui/react-dialog 1.1.15**, pinned at `yarn.lock:2842–2844`, uses controlled open in `node_modules/@radix-ui/react-dialog/dist/index.mjs:34–51`. Its dismiss handler at `:230` and Close handler at `:271` invoke context.onOpenChange(false), explaining the passing Escape/Close controls. Repo `ui/dialog.tsx:9–12,77–85` delegates to these primitives.
- Actual installed **@radix-ui/react-use-controllable-state 1.2.2** was verified from package.json and opened at `dist/index.mjs:16–17,32–45`: changing a controlled prop does not itself invoke onChange. Its setter invokes the callback when called with a different value. Thus an external parent open=false cannot be relied on to trigger the child's reset wrapper.

A concrete fix is to lift the query to GlobalSearch, pass typed query/change props to the lazy dialog, and use one parent open-change handler that synchronously clears the query when closing. Route both the keyboard toggle and dialog/result callbacks through that handler. Keep the keyboard handler's current-open value correct; a stale event-listener closure would reintroduce broken toggling. An equivalent design is acceptable if it covers both bypasses and the first reopened render is empty. Resetting only SearchResults.close leaves Ctrl+K broken. Preserve the mounted dialog and its close animation; a delayed reset effect must not paint the old query on reopen.
