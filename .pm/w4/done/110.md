# `deployActions` reports `rollback: allowed` on a service with nothing to roll back to

Why: `deployActions` exists so a client can bind an affordance to a capability without guessing, and its `precondition` field already expresses "permitted, but not applicable right now" for `cancel_deploy` — rollback simply never uses it, so every non-dashboard consumer (CLI, MCP, a script) is told an action is available that answers `409` on every possible target.

Found by live `/qa-find-bugs` 2026-09-21 pass 112 (w4-targeted, `muse.env` credentials), journey 3, on `qa-20260921-dep` (`srv-daof2ers0ils73bgpdpg`), since deleted.

## Repro

On a freshly created service whose only deploy is its first:

```
query { deploys(serviceId:"srv-…", limit:10) { id status trigger } }
→ [ { id: "dep-daof2ers0ils73bgpdq0", status: "live", trigger: "create" } ]      // exactly one

query { deployActions(serviceId:"srv-…") { action outcome precondition reason } }
→ [ { action: "deploy",         outcome: "allowed", precondition: null },
    { action: "cancel_deploy",  outcome: "allowed", precondition: "no_active_deploy" },
    { action: "rollback",       outcome: "allowed", precondition: null } ]        // ← no precondition

POST /v1/services/srv-…/rollback  {"deployId":"dep-daof2ers0ils73bgpdq0"}
→ 409 {"error":"conflict: deploy \"dep-daof2ers0ils73bgpdq0\" is already live — nothing to roll back to"}
```

The only candidate target is the live deploy, and rolling back to it is refused — correctly. So `rollback` is not actually available, and nothing in the capability response says so.

## The shape of the fix already exists

`cancel_deploy` is returned as `outcome: "allowed"` with `precondition: "no_active_deploy"` — permitted in principle, not applicable until something is in flight. Rollback wants exactly that treatment: a precondition such as `no_previous_deploy`, set whenever the service has no deploy in a rollback-eligible terminal state. The 409's wording ("already live — nothing to roll back to") is the server already knowing the answer; it just is not surfaced ahead of the attempt.

## Why this is minor rather than major

The dashboard is **not** misled: it consumes `deployActions` (`dashboard/src/features/capabilities/hooks/use-resource-actions.ts`, `use-bound-action-confirm.ts`) but gates the Rollback control on a deactivated row as well, so a single-deploy service correctly renders no Rollback button anywhere — verified live on the same fixture. The exposure is to consumers with no second gate: the CLI, MCP, and anything binding buttons straight to the capability response, which is what that query is for.

Estimate: ~30m including a test that the precondition appears exactly when the rollback would 409.

## Also checked this pass, and found correct

Journey 3 otherwise came back clean, so the next pass need not re-walk it:

- **Manual deploy → cancel is coherent.** `POST …/deploys` → `201 created`; `POST …/deploys/<id>/cancel` → `200` with `status: canceled` and a `finishedAt`; the deploys list, the deploy detail and the service phase all agreed immediately (`canceled` / `canceled` / `Running`), and the previously-live deploy stayed `live`.
- **A superseded deploy is cancelled, not abandoned.** Two deploy-hook deploys fired 0.7s apart: the later one went `live`, the earlier one `canceled`, the original create deploy `deactivated`, and the service settled `Running` at `rev-4`. Four deploys, four coherent terminal states, nothing left hanging.
- **The deploy hook works and is refused without a valid key.** `POST /v1/deploy-hooks?key=dhk-…` → `200 {"deploy":{"id":"dep-…"}}` with no credentials; a single-character-tampered key → `404 app not found`; no key at all → `404`. `GET` with a valid key also triggers a deploy — side-effecting, but that matches Render, which documents GET on deploy hooks.
- **The events feed is honest about the cancel.** Exactly four rows — `deploy_started`/`deploy_ended` per deploy — with `deployStatus: "canceled"` in the ended row's details and correct trigger flags (`manual: true` for the API deploy, `firstBuild: true` for the create). No intent-verb row, so `w4/m118`'s doctrine holds here.

## Noticed, not filed — `deploy_started` details carry `finishedAt`

Both `deploy_started` rows carried a `finishedAt` for a deploy that had already ended, and the canceled deploy's `deploy_started` carried `finishedAt` with no `startedAt` at all. That suggests the historical row is rendered from the deploy's current state rather than captured at the time, so it mutates after the fact and a consumer cannot trust `finishedAt` on a "started" event. Not traced to code this run and low impact — recorded here so a future pass can pick it up with evidence rather than rediscover it.

## Outcome (2026-09-21)

Fixed, and the cause was one predicate short rather than a missing vocabulary word: `PrecondNoEligibleRollbackTarget` already existed and was already wired — the projection just computed it with `RollbackEligible`, which the verb does not use alone.

`Rollback` refuses on two conditions: a target that never went live (`RollbackEligible`), **and** the currently-live deploy when it is already the running image (w4/051 — rolling back to it changes no image while still restarting the service and minting a redundant deploy). A freshly created service is exactly the second case, so the projection scanned its one deploy, found it eligible, and reported ready.

`RollbackActionable(d, currentImage)` composes both, and the verb now refuses through the same function, so the answer `deployActions` gives and the answer `Rollback` gives cannot drift. The narrowness is preserved and tested: once `spec.image` drifts off the still-live deploy — what a failed rollout leaves behind — rolling back to it is a legitimate recovery and both sides say ready again.
