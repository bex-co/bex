# GraphQL hangs `latestDeployId` on the `Service` type, where every ordinary read answers it empty

Why: REST deliberately carries this id in Render's `serviceAndDeploy` **create envelope** so the service object never claims to know its latest deploy, while GraphQL exposes it as a field on `Service` — so `service(id:)` and `services()` return `""` 100% of the time, and a client that binds the obvious-looking field gets a value that is always wrong and never an error.

Found by live `/qa-find-bugs` 2026-09-21 pass 155 (w4-targeted, `muse.env` credentials), sweeping journey 14 — a deliberately failing deploy — which this loop had never run. Two `qa-` image-backed services were created and deleted; the workspace is back to baseline.

## The divergence

REST puts the id **outside** the service object, in the envelope Render specifies (`apps/rest.go:1050-1051`):

```go
// Render: create => 201, body wraps the service under serviceAndDeploy.
core.WriteJSON(w, http.StatusCreated, serviceAndDeploy{Service: s.restService(r.Context(), app), DeployID: app.LatestDeployID})
```

That is `w2/m47`'s deliberate work — it added `DeployID` to `serviceAndDeploy` precisely so create returns `{service, deployId}` as Render's `POST /v1/services` does. Consequence, verified live: `GET /v1/services/{id}` carries **no** deploy key at all. Filtering the response's own keys for `/deploy/i` returned only `["autoDeploy","autoDeployTrigger"]`. REST is honest — the field exists exactly where it is knowable.

GraphQL instead declares it as a `Service` field (`apps/graphql.go:551-554`) resolving straight off the view:

```go
"latestDeployId": &graphql.Field{
    Type:    graphql.String,
    Resolve: gqlutil.Field(func(a AppView) any { return a.LatestDeployID }),
},
```

and the view field says outright that reads cannot populate it (`apps/service.go:596-599`):

```go
// LatestDeployID is the id of the first deploy row, populated by Create only
// (w3/m14). The dashboard uses it to navigate to the in-flight deploy page
// immediately after a git-sourced service is created. Empty on Get/List.
LatestDeployID string `json:"latestDeployId,omitempty"`
```

Only `Create` ever sets it — `service.go:2279`, `v.LatestDeployID = firstDeployID`, one assignment, after `s.view(a)`. The `omitempty` tag is what keeps REST clean; GraphQL has no equivalent, so the resolver emits `""`.

```graphql
→ beancount-cms-v2   latestDeployId:""  phase:"Running"

   eden-dash-v3       latestDeployId:""  phase:"Running"

```

Seven for seven, including five long-lived production services with real deploy history, and including the two services whose create call had just returned the id. `service(id:)` answers the same. Meanwhile `deploys(serviceId:…, limit:1)` returns the deploy perfectly well in the same request — the data is a sibling field away.

This is not an isolation or authorization issue and the value is never *stale*; it is simply never answered.

## The consumer, checked before proposing anything

The dashboard's only use is the create path, exactly as the comment claims:

- `features/services/api/services.graphql:144` selects `latestDeployId` **inside the `CreateService` mutation's selection set** — it is the sole occurrence in the file, and no query document selects it.
- `features/services/hooks/use-create-service.ts:132` — `const deployId = svc?.latestDeployId ?? undefined;`, used to navigate straight to the in-flight deploy page.
- `dashboard/src/graphql/definitions.ts:1770` confirms it from the generated side: it appears on `CreateServiceMutation` and on no query type.

So **nothing reads it on a read path**, and making reads stop answering it breaks no first-party client. MCP never exposes it at all — `grep -rn latestDeployId lego/backend/internal/` outside `apps/` returns zero hits, so GraphQL is the only surface with the problem.

## Fix

Name the target behavior rather than "make them agree", because there are two ways to agree and only one is cheap:

- **Preferred — make the field null on reads, not `""`.** `graphql.String` is already nullable, so return `nil` when `LatestDeployID` is empty, matching what `omitempty` gives REST. A client then sees `null` ("we are not telling you") instead of `""` ("there is no deploy"), and the create path is untouched. This is the same shape `w4/124` and `w4/125` settled for `url` and `maintenanceMode` — a GraphQL field filled unconditionally from a view whose REST counterpart gates emission. That makes this the **third** instance of the family, which is the argument for fixing it in the resolver the way those two were.
- **Or actually populate it on reads** from the latest deploy row. Truer to the field's name, but it puts a deploy lookup on every service read and list — a per-row query on `services()` — so it needs a join or a projected column before it is acceptable. Do not take this branch casually.

Either way, correct the doc comments, which currently describe the limitation without conceding that GraphQL exposes it anyway.

Estimate: ~25m for the nullable branch plus a test that `service(id:)` returns `null` while `createService` still returns the id.

## Adjacent, smaller, and not separately filed

Both surfaced in the same journey; each is real but too thin for its own note. Fix in passing if the files are already open.

- **The Activity feed attributes a rollout-deadline expiry to a person.** The dashboard's Events tab renders `Deploy ended · Failed · by puncsky@gmail.com` for a deploy that nothing human ended — the 900s `ProgressDeadlineExceeded` did. The API is the source: `details.triggeredByUser` on `deploy_ended` is the same user id as on `deploy_started`, and `events/service.go:39` documents that deliberately ("`deploy_ended` … `triggeredByUser` as above", i.e. the opener). The data is defensible; the **wording** is not, and it cuts against bex's own convention in `docs/render-artifacts/service-events.md:30-33`, where triggering-user attribution is reserved for *accepted user intent* (`suspender_added`, `server_restarted`). Render publishes no capture showing a user label on `deploy_ended`. Cheapest fix is in the dashboard: only show "by <user>" on `deploy_ended` when the ending was a user action (a cancel), not a deadline or a natural finish.
- **`deploy_started` is timestamped from the deploy's `createdAt`, not its `startedAt`.** Live: `qa-20260921-silent`'s deploy had `createdAt 03:03:41.839562Z` and `startedAt 03:03:59.020452Z`, and its `deploy_started` event reads `03:03:41Z` — **17 seconds before the deploy started**, and identical to the other service's event despite the two starting 17s apart. Whether the feed should date the event at queue time or at start is a real decision (`at` is documented as "the original occurrence time", `service-events.md:68`); worth stating explicitly either way, since the Activity feed and the deploy detail page currently disagree by the queue delay.

## Also checked this pass, and found correct

Journey 14 — a deliberately failing deploy — had never been run by this loop, and it holds up thoroughly. Recording it so nobody re-runs it. Two free image-backed web services on `alpine:3.20`, each with a `startCommand` chosen to fail a different way: `qa-20260921-crash` (`echo BOOM_QA_155; exit 1`) and `qa-20260921-silent` (`echo SILENT_QA_155; sleep 3600` — runs forever, never binds the port).

- **The two failure modes are diagnosed distinctly and correctly**, in prose a user can act on. `crash` got _"container exited shortly after start and is restarting repeatedly (last exit code 1) — check the service logs for the crash output. If the crash is a port bind: the process must listen on $PORT (8080), and tenant containers cannot bind ports below 1024 (all Linux capabilities are dropped)."_ `silent` got _"the container is running but its startup health check has not succeeded, so the rollout is waiting: a TCP connect to port 8080… an unset Health Check Path falls back to a TCP connect, which only asks whether the process is listening."_ This is `w4/m112`'s `stallReason` work paying off. **Note the timing trap:** at 100s `crash` still had an empty `stallReason` while `silent` already had one, which looks like an asymmetry and is only the operator not yet having seen enough restarts — do not file that.
- **The stall reason's advice is actionable, not decorative.** It says to check the logs, and the logs have it: `crash` returned 6 `app` lines, all `BOOM_QA_155`, at 03:03:47 / 03:04:03 / 03:04:36 / 03:05:26 / 03:06:58 / 03:09:48 — the CrashLoopBackOff curve visible in the timestamps — and `silent` returned exactly 1, `SILENT_QA_155`. 
- **The rollout terminalizes on a real budget, and it is Render's.** `rolloutBudgetSeconds = 900` (`operator/internal/controller/deployment_projection.go:131`) → `ProgressDeadlineExceeded` → `settleFailedRollout` (`app_controller.go:2845-2859`). Live, `crash` went terminal at `finishedAt 03:18:42.268495Z` against `startedAt 03:03:42.064687Z` — 900.2s, to the budget. A stalled deploy is **not** a state that never resolves; anyone probing this must wait out the full 15 minutes before calling it stuck.
- **The terminal state is consistent on every surface, and the transition is clean.** `phase` `Deploying` → `Failed`; deploy `status` `update_in_progress` → `update_failed`; the diagnosis is **promoted** from `stallReason` into `failureReason` and `stallReason` is **cleared** — m112's rule that a terminal row carries no stall reason, holding live. REST `GET /v1/services/{id}/deploys` agreed field for field, including the identical `failureReason` prose.
- **The failure event says it failed.** `deploy_ended` carries `details.deployStatus: "failed"`, `details.fullDeployStatus: "update_failed"` and the complete `failureReason` — so a feed consumer never has to infer the outcome from the event type alone.
- **The dashboard tells the truth in all three places at once**, with no stale paint: header `Service Failed` / `Latest deploy Failed`, the deploys list row `Failed … Failed 2 minutes ago · First Deploy · 15m`, and the Events tab `Deploy ended · Failed` — each rendering the full reason inline rather than a generic "deploy failed".
- **Neither host ever served over a failing deploy.** `curl -sSI` from outside the browser gave `503` on both `qa-20260921-crash.onbex.co` and `qa-20260921-silent.onbex.co` while the dashboard said `Deploying` — no "Live badge over a 404" instance here.
- **Deleting a failed service is clean.** Both deleted without a confirm phrase (they were in no protected environment) and the workspace returned to its baseline of 5 services / 3 databases / 2 key values / 3 projects / 0 environments.

## Closed 2026-09-22

Took the note's **preferred** branch: `latestDeployId` is `null` on reads, never `""`. The resolver (`apps/graphql.go`) returns `nil` for an empty view field, which is exactly what `omitempty` already gives REST — and the field was already nullable in the schema, so this is a value change, not a contract change.

The second branch (populate it on reads from the latest deploy row) was declined for the reason the note gives: it puts a per-row deploy lookup on `services()`, and the data is one sibling field away in `deploys(serviceId:)` for any caller that actually wants it.

This is the third member of the family, fixed the same way as `url` (`w4/124`) and `maintenanceMode` (`w4/125`) — a GraphQL field filled unconditionally from a view whose REST counterpart gates emission — and its test lives beside theirs in `apps/public_url_test.go`.

- `TestM131_LatestDeployIDIsNullOnReads` covers `service(id:)` and `services()`, and controls that a **populated** id still passes straight through, so the create path — the one place the id is knowable — is untouched. Mutation-checked: both read assertions fail with the nil branch removed.
- The doc comment on `AppView.LatestDeployID` now states the requirement both surfaces are meeting, instead of describing the limitation while GraphQL quietly exposed it anyway.

**No client change needed**, confirmed against the generated types rather than assumed: `schema-types.ts:3578` already declares `latestDeployId: Maybe<Scalars['String']['output']>`, `definitions.ts:1776` has it on `CreateServiceMutation` and on no query type, and `use-create-service.ts:132` reads it as `svc?.latestDeployId ?? undefined` — which treats `null` and `""` identically. Full `go test ./...` green in `lego/backend`.

**The note's two adjacent items are left as it filed them** — both are "fix in passing if the files are already open", and neither file was open for another reason:

- `deploy_ended`'s `triggeredByUser` making the Activity feed read "Deploy ended · Failed · by \<user\>" for a 900s `ProgressDeadlineExceeded` that nothing human ended. The API data is deliberate (`events/service.go:39`); the cheapest fix is in the dashboard, showing "by \<user\>" on `deploy_ended` only when the ending was a user action.
- `deploy_started` timestamped from the deploy's `createdAt` rather than its `startedAt` (17s apart live), which leaves the Activity feed and the deploy detail page disagreeing by the queue delay. That one is a **decision** about what `at` means, not a defect — `service-events.md:68` documents it as "the original occurrence time" — so it wants stating explicitly either way rather than silently changing.

The note's "Also checked this pass, and found correct" section is the durable half of its value: journey 14 (a deliberately failing deploy) had never been run by this loop and holds up completely, including the 900s rollout budget being real and to-the-second. Preserved here so nobody re-runs it — and note its two traps: a stalled deploy needs the **full 15 minutes** before it is stuck, and an empty `stallReason` early in a crash loop is the operator not yet having seen enough restarts, not an asymmetry to file.
