# 413 — "Clear build cache & deploy" is recorded as `clearCache: false`, and dashboard deploys are reported as `trigger: "api"` instead of Render's `manual`

Why: the Events feed and webhooks are how a team audits "why did this rebuild from scratch?" and "who clicked Deploy?". A clear-cache deploy is recorded as an ordinary one, so a slow cold build looks unexplained. A dashboard click is labelled as an API call, which a Render client's `trigger == "manual"` filter never matches.

**Severity:** minor (audit and parity accuracy; the deploy itself runs). **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run b6c4, 2026-10-24 UTC (`muse.env`, `bex-canary`, pin `23750eda6b21`). Fixture: Free Git web service `qa-20261024-b6c4-cache` (`srv-dbelsl6t3iis73adjvqg`, `bex-co/bex` `examples/hello-node`). It was deleted (`GET` → `404`); session revoked.

## Probe

1. Dashboard `/services/<id>` → **Manual Deploy** offers "Deploy latest commit", "Deploy a specific commit", **"Clear build cache & deploy"** and "Restart service". Choosing **Clear build cache & deploy** shows the toast "Deploy triggered." and creates `dep-dbeltqet3iis73adjvs0`.
2. `GET /v1/services/<id>/deploys` → that deploy reads `trigger: "api"`, `bexTrigger: "api"`.
3. `GET …/events` → its `deploy_started.details.trigger` = `{"firstBuild":false,"envUpdated":false,"manual":true,"deployedByRender":false,"clearCache":false,…}`. **`clearCache` is false**, and `manual: true` contradicts the deploy's own `trigger: "api"`.
4. The pinned Render spec's deploy `trigger` enum: `api, blueprint_sync, deploy_hook, deployed_by_render, manual, other, new_commit, rollback, service_resumed, service_updated`.

## Root cause

- `lego/backend/internal/events/service.go:931-944` builds the `deploy_started` `Trigger` with `FirstBuild`, `EnvUpdated`, `Manual`, `DeployHook`, `Rollback` and `DeployedByRender`, but **never sets `ClearCache`**. The field exists (`:571`, REST `events/rest.go:174`, GraphQL `events/graphql.go:46`), so it is always false.
- The deploy path does honour the request. The dashboard sends `clearCache: "clear"` (`manual-deploy-button.tsx:170-174`), and `stampClearCacheRelease` (`deploys/service.go:770`, `:832-843`) marks the release, but that marker never reaches the event record.
- `Manual: r.Trigger == store.TriggerAPI`, and `renderTrigger` maps `TriggerAPI` → `"api"`. A dashboard click and an API call are the same store trigger, so the REST deploy can't say `manual` and the event can't say otherwise.

## Fix

- Persist the clear-cache choice on the deploy row (or read the release's clear-cache marker), and set `Trigger.ClearCache` from it on REST, GraphQL, MCP and webhook payloads.
- Distinguish a dashboard deploy from an API deploy, e.g. a `TriggerManual` set by the dashboard's GraphQL `triggerDeploy` (or by a session caller rather than an API key). Map it to Render's `manual`, keep `api` for API-key calls, and make `trigger.manual` agree with it.
- Tests: a clear-cache deploy's event has `clearCache: true` and a normal one has `false`; a dashboard-triggered deploy reads `trigger: "manual"` with `trigger.manual: true`; an API-key deploy reads `api` with `manual: false`.

**Unverified:** whether the cache was actually skipped (`hello-node`'s Docker build had no `CACHED` steps either way, so the logs can't show it); webhook payload shape (read from code only).
