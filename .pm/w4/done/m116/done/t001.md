## Objective

A stock `bex psql` (and `pgcli`) against a new free public Postgres fails before any SQL runs, because the server pins `sslmode=verify-full` against a private CNPG CA no stock client holds. Restore the out-of-box journey without weakening TLS.

## Context

- Live repro 2026-09-17, `bex v0.2.1`, workspace `bex-canary`, fixture `dpg-daloivd2r12c73cnghbg` (free, allow-listed caller `/32`, deleted after the sweep):
  - `bex psql <id> -c 'SELECT 1 AS bex_probe;'` → `psql: error: ... root certificate file "/Users/tianpan/.postgresql/root.crt" does not exist`, exit 1.
  - Control: with `PGSSLROOTCERT=<serverCaCertificate from connection-info>` the same command exits 0 and returns the probe row. The gap is trust provisioning, nothing else.
- Producer: `lego/backend/internal/postgres/service.go:758-763` pins `sslmode=verify-full` on every external string; the comment at `:715-719` (w4/m95) explicitly forbids downgrading the mode instead.
- Consumer: pinned upstream `pkg/tui/views/psql.go:75` (`render-oss/cli a764810a7682`) passes `connectionInfo.ExternalConnectionString` verbatim to stock `psql` — it cannot provision a CA, and upstream will never read a bex extension field.
- Regression evidence: `scripts/psql-compat-verify.sh:301` asserts `sslmode == require` and ran stock `render psql` with no CA step (green 2026-07-18); the string now carries `verify-full`, so that precondition fails today. `docs/cli-compatibility-checklist.md` still grades `psql` `[x]`.
- `w4/m95` is not a duplicate: it delivers the CA to the *dashboard* panel for manual `psql`; the CLI path was never covered.

## Steps

1. Decide the mechanism (do not downgrade TLS): launcher-side CA provisioning for the `psql`/`pgcli` subcommands (fetch `serverCaCertificate`, point the child at it — same interception class as the existing root `--version` path), or a public-CA TLS edge for Postgres (infra, mirrors the dashboard-facing posture).
2. Implement the chosen path; keep the request/response contract byte-identical for unmodified `render` binaries.
3. Update `scripts/psql-compat-verify.sh` (the `sslmode==require` precondition is stale either way) and the `psql`/`pgcli` rows in `docs/cli-compatibility-checklist.md`.
4. Re-run the DoD probe from a machine with no `root.crt` and no `PGSSLROOTCERT`.
