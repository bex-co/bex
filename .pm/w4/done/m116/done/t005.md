## Done 2026-10-03 — the second password is Kratos's designed OAuth2 re-authentication, evidenced live; the helper completes production unmodified

**Step 1: request-level evidence (production, released `bex v0.2.1`, QA identity, fresh headless Chrome, private `BEX_CLI_CONFIG_PATH`).** A private instrumented copy of the helper logged only cookie **names**, query-parameter **names**, status codes and flow booleans. No values, codes or challenges were recorded:

```text
LEG /auth/login                     (password #1, no session yet)
REQ GET auth.bex.co/self-service/login/browser q=[return_to] cookies=[]
RES 200 … {"refresh":false,"requested_aal":"aal1"}
LEG /auth/device                    (ory_kratos_session@.bex.co now held) → Authorize
REQ GET oauth.bex.co/oauth2/device/verify … cookies=[ory_hydra_device_csrf, ory_kratos_session]   (no ory_hydra_session)
LEG /auth/login?login_challenge=…
REQ GET auth.bex.co/self-service/login/browser q=[return_to, login_challenge] cookies=[csrf_token_*, ory_kratos_session] origin=https://dashboard.bex.co
RES 200 … {"refresh":true,"requested_aal":"aal1","has_challenge":true,"skip":false,"req_prompt":none,"req_max_age":false,"msgs":[1010003]}
(password #2) → POST /self-service/login 422 browser_location_change_required → login_verifier → consent_verifier (ory_hydra_session set here) → /auth/device/success
```

So the client is **not** dropping the session. The challenge-bound `createBrowserLoginFlow` carries the seconds-old `ory_kratos_session`, and Kratos answers `200` with a **refresh** flow (message `1010003`, "confirm this action by verifying that it is you"). It never answers `session_already_available`, so the `use-ory-flow.ts:281-292` short-circuit has nothing to catch. The cause is upstream and deliberate. Kratos v1.3.1 `selfservice/flow/login/handler.go:526-530` (`createBrowserLoginFlow`) rewrites the request to `refresh=true` whenever Hydra's login request has `skip == false`. Hydra sets `skip` only when this browser already holds a remembered Hydra login (`ory_hydra_session`). The request URL carried no `prompt`/`max_age`. bex does not ask for this; Kratos forces fresh authentication before it hands an OAuth2 grant to a browser Hydra does not yet remember.

**Control, same browser profile, second ceremony:** with `ory_kratos_session` **and** `ory_hydra_session` held, the Authorize click went straight through. The challenge-bound flow creation was handed back to Kratos by the hook (`bootstrapViaKratos`) and accepted with **zero** password entries (`login_verifier` → `consent_verifier` → `/auth/device/success`, `bex login` → `Login successful!`). The short-circuit therefore works exactly when Kratos allows it.

**Resulting entry count, by design:** signed out + first OAuth2 grant in this browser = 2 (sign-in, then Kratos's OAuth2 refresh). Signed in to the dashboard, first grant = 1. Browser already remembered by Hydra = 0. Closed as **intended upstream behavior**. Removing the double entry would mean bypassing Kratos's refresh (bex-side Hydra admin accept) or reordering the device confirmation ahead of sign-in. Both are security-design changes and out of this task's scope (no TTL/challenge changes, per Out of scope). They are not filed.
