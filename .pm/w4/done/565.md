# 565 — A static site published from the repository root serves its `.git` directory: `/.git/HEAD`, `/.git/config`, `/.git/index`, `/.git/logs/HEAD` and loose objects all answer 200

Why: scanners probe `/.git/HEAD` on every new `*.onbex.co` host within minutes (w1/m151). An exposed `.git` directory hands them four things:
- the repository's remote URL, which for a private repo is its owner and name;
- the internal publish pod's hostname, which carries the workspace id;
- the index;
- every published object, which git tooling can reassemble into a repository.

Render publishes a static site's files, not its git metadata.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 73, 2026-11-11 04:38–04:45 UTC (`muse.env`, workspace `bex-canary`, pin `a0d5802594e9`). **Major (security hygiene).**
  - The checkout is `--depth 1`, so the objects match the published working tree. No older history leaks.
  - The clone token does not land in `.git/config`. It comes from a `-c` credential helper that is not persisted.
  - ~50m.

- **Root cause:**
  - **The publish copy includes `.git`.** The publish Job's clone container (`lego/operator/internal/publish/publish.go:604-612`) runs `git init` in `/work` and fetches `--depth 1`. It then runs `cd "/work/$SRC_DIR"` and `cp -a . <out>/`.
  - **The repository root contains it.** With a publish path of `.` and no root directory, `$SRC_DIR` is the repository root, so `.git/` is staged and uploaded with the site.
  - **The server serves it as an object.** The static server (`lego/operator/internal/staticserver/staticserver.go:250-`) answers an existing object first, before redirect and rewrite rules, so `/.git/*` is served like any other file.
  - A subdirectory publish path (e.g. `examples/static-site`) does not contain the root `.git`.
- **Fix (target behavior):**
  - **Publish never uploads git metadata.** Exclude `.git` at every depth from what is staged: the root directory, and the `.git` files that submodule checkouts leave (the `directSubmodules` step, `publish.go:579-584`).
  - **The static server refuses `.git` paths.** Answer 404 for any request path with a `.git` segment (`/.git`, `/.git/…`, `/<dir>/.git/…`), whether or not such an object exists. This covers sites published before the fix without a republish. Custom redirect and rewrite rules cannot reach those paths either.
  - **The build path gets the same rule.** A Docker or native build whose `staticPublishPath` holds a `.git` (for example `COPY . .` then publish `.`) is covered by the server-side rule.
  - **Round 74 control (2026-11-11 04:53–04:57 UTC):** the native build path does not upload `.git`.
    - Fixture: static site `qa-20261110-sb74` (`srv-dbpv9efbq3ic73c0agmg`) from the same repo, branch `master`, publish path `.`, build command `echo built > built.txt`.
    - Result: `/built.txt` and `/README` gave 200; `/.git/HEAD`, `/.git/config`, `/.git/index` and `/.git/logs/HEAD` gave 404.
    - So the leak is the no-build publish Job (`publish.go:604-612`).
    - A Docker build that copies `.git` into its output is still unverified.

- **2026-11-11 (loopx w4):** fixed on both sides. The direct publish's clone script removes every `.git` under the publish directory before it copies it (`find . -name .git -prune -exec rm -rf -- {} +`, `lego/operator/internal/publish/publish.go`), so a publish of `.` uploads the files and no git metadata. The static server answers 404 for any request path with a `.git` segment before it looks for an object, and `get` never reads one from the origin, so sites published before the fix stop serving it and no rewrite destination reaches it (`hasGitSegment`, `lego/operator/internal/staticserver/staticserver.go`); `.gitignore` and `/.well-known/…` still serve. Tests: `TestDirectPublishOfTheRepositoryRootLeavesGitMetadataOut` (real clone script, fails without the fix), `TestGitMetadataIsNeverServed`. The live DoD replays after the next production deploy.
