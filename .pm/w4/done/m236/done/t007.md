## Objective

On the deployed t001 fix, a fresh load of `/services/<id>/metrics` still settles with 2 `Application Metrics` headings and 3 cards, the first frozen at `Limit …`. t001 removed the pending/SSR copy: the server HTML now carries one card. The duplicate is therefore created client-side, after hydration. Remove that client-side mechanism so exactly one Application Metrics card exists at every point after load.

## Context (live, `/qa-find-bugs w4` loop run e5f3, 2026-10-20 UTC)

- **Deployed build:** the dashboard is pinned to `94533d795067` (`f641abe92`, 05:33Z), and `ebfefea26` (t001/t002) is its ancestor.
- **Server HTML:** `page.request.get('/services/srv-dbbhhahq56vc73bn8btg/metrics')` → 200, `"Application Metrics"` ×1 and `data-slot="card"` ×2. The pending-copy mechanism t001 fixed is gone.
- **Hydrated DOM over time**, on the owned Free image service `srv-dbbhhahq56vc73bn8btg` at 1440 and 390, sampled from the navigation commit:
  - up to ~2 s: `{cards:2, apps:1}`;
  - from ~2.5 s through 20 s: `{cards:3, apps:2}`.
- **Card contents:** card 0 reads `Application Metrics … Memory Limit … CPU Limit …` with no Instances selector. Card 1 has the Instances selector. Card 2 is Network.
- **DOM position:** all three are React-managed siblings (`__reactFiber$…` present) of one `div.mx-auto.w-full.max-w-4xl`. The duplicate is not an orphaned SSR node outside the tree.
- **Console:** no errors or warnings during the load.
- **Evidence:** `.playwright-mcp/qa-metrics-e5f3-1440.png` (local).
- **Lead, by reading code and React; not yet reproduced in a test:**
  - `dashboard/src/routes/services.$serviceId.metrics.tsx` renders `ApplicationMetricsCard key={serviceId}` (`:130`, `71f125fc0`, w5/m91) and `NetworkMetricsCard key={serviceId}` (`:138`, added by `4df47e1f7`, w4/m224 on 2026-10-17, two days before this milestone's finding). They are siblings in the same fragment, alongside the conditional `{timelineShown && …}` and `{showApplicationCard && …}` slots.
  - In react-dom 19.3.1 (the version the dashboard lockfile pins), `mapRemainingChildren` (`node_modules/react-dom/cjs/react-dom-client.production.js:3598-3605`) indexes old fibers in a `Map` by key. A duplicate key overwrites the earlier fiber. After the keyed pass, only fibers still in the Map are deleted (`:3993`).
  - So when a slot change knocks reconciliation off the fast path, for example `showApplicationCard` toggling as `useServer` settles, the overwritten Application Metrics fiber is neither reused nor deleted. Its DOM stays mounted and frozen, and a fresh card is created beside it. That fits a frozen card 0 holding its first-render placeholders.
- The grep for `key={serviceId}` across `dashboard/src/routes` and `features` finds no other same-parent duplicate. `static.$serviceId.metrics.tsx` has no key.

## Steps

1. Reproduce in a component test: render the metrics route content with the service unresolved, then resolved (and a timeline toggle). Assert exactly one Application Metrics heading. It must fail on today's code.
2. Give the two cards distinct keys, or key their common wrapper once by `serviceId`. Keep the w5/m91 (instance selection per service) and w4/m224 (status choices reset per service) intents: each card still remounts when `serviceId` changes.
3. If the test does not reproduce the duplicate with the key fix in place, keep instrumenting (mount/unmount logs) until the client-side mechanism is named. Do not hide the card with CSS or dedupe the query.
4. Live: replay the DoD probe at 1440 and 390 after the next dashboard deploy.
