## Objective

Make `compensateEnvironment` restore an empty prior map, which today silently fails in production.

## Context

- Live on `srv-db1ebs8a8tcs73b1a0q0`: with zero prior files, a failed `patchServiceEnvironment` (254-character name) left the name in the store. After adding `good.txt`, the identical patch was restored correctly.
- Path: `batch.go:652` `restoreSourceMaps` → `service.go:723` `storeMap(ctx, path, {})` → `store.go:268` `openBaoStore.Delete` (KV-v2 **metadata** DELETE). The non-empty restore uses `Put`.
- Cause unverified. Suspects: the bex-api OpenBao policy lacks `delete` on `<mount>/metadata/<tenant>/...`, or the delete is swallowed. `deleteMapKeyAfterProjection` writes an empty map via `PutCAS`, which works (a single bad-key delete returned 204 live).

## Steps

1. Pull bex-api logs for the 23:5x UTC 2026-10-04 `patchServiceEnvironment` failures and read the joined `restore secret store` error.
2. Fix by cause: either restore with `Put`/`PutCAS` of an empty map instead of a metadata delete, or grant the capability (record which in the commit). Also check the env-map restore, which uses the same `storeMap`.

Cause from logs (2026-10-04, Loki `{namespace="bex-system",container="api"}`): the failed no-prior-files patches at 23:49:14 and 23:49:27 UTC logged only the Kubernetes refusal (`Secret "…-l6-img-files" is invalid … must be no more than 253 characters`) — no `restore secret store` error was joined, so the empty-prior restore (a KV-v2 **metadata DELETE**) reported success while the name stayed listed. bex-api's OpenBao policy is not in the repo, so why the delete did not clear it is not determined. Fix: `storeMap` now writes an empty map as data (`Put`, the request the single-key delete's working `PutCAS` makes) instead of deleting metadata; env and files restores share it.
