# 087 — `TestAuthzGuardsEveryVerb` walks 325 verbs but its sanity floor is 19, and it skips verbs by name across 62 `core.Base` method names

Why: this is the guard that proves every verb refuses an unauthorized caller, and its own self-check would still pass after a filter regression that silently dropped 94% of the verbs it walks.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 34. **Read-only on production — nothing created, changed or deleted, and no new login session minted** (existing browser session reused, per `w4/085`). Severity: **minor** — no verb is unguarded today and no name collision exists today; this is a defense-in-depth gap in a security control, the same family as `w4/082`.

## Measured

`wantMinSweptVerbs = 19` (`internal/api/server_test.go:1102`) is the floor both reflection sweeps check their walk against — `TestAuthzGuardsEveryVerb` and `TestAuditCoversEveryWriteVerbExactlyOnce`, deliberately shared "so the two sweeps' thresholds can't drift apart".

The actual walk is **325**. Measured by temporarily adding `t.Logf("SWEPT_ACTUAL=%d", swept)` before the floor check, running the test, and reverting (`git checkout`; tree verified clean):

```text
server_test.go:1151: SWEPT_ACTUAL=325
--- PASS: TestAuthzGuardsEveryVerb (0.04s)
```

So the floor sits **17× below reality**. A change to `isVerbMethod`'s predicate — a convention shift where verbs take a request struct first, or return a typed error rather than `error` last — could drop whole service packages out of both sweeps and still pass, taking the audit-coverage guarantee down with it, because the same constant guards both.

## The mechanism that would cause exactly that

`isVerbMethod` (`server_test.go:1044-1053`) skips a method when `baseMethods[m.Name]` — a match on **name**, not on declaring type:

```go
func isVerbMethod(baseMethods map[string]bool, m reflect.Method) bool {
	if baseMethods[m.Name] {
		return false
	}
	…
}
```

`baseMethodNames()` reflects over `*core.Base` and today yields **62** exported names. Several are ordinary enough to collide with a real verb: `GetApp`, `Can`, `ListByTenant`, `PurgeByTenant`, `AppPods`, `BuildPods`, `DatabasePods`, `KeyValuePods`. A service that declared its own method under any of those names would shadow the promoted helper legally in Go, and be silently dropped from both sweeps on that service — unguarded, unaudited, and invisible.

**No such collision exists today.** Checked exhaustively across every non-test file in `internal/*/`: three methods share a `core.Base` name, and none is on a swept service type —

| name | receiver | file |
| --- | --- | --- |
| `Tenant` | `*tenantService` | `internal/api/tenancy.go` |
| `RequirePaymentMethod` | `*PaymentGate` | `internal/billing/payment_gate.go` |
| `GetApp` | `*PGStore` | `internal/store/store.go` |

So this is latent, not live. It is worth recording because it is the concrete path by which the count could fall — which is exactly what a tight floor would catch.

## The fix

Replace the floor with a **pinned exact count**, the way `classifiedOps` pins the operation table: assert `swept == wantSweptVerbs` (325 today) and require the number to move deliberately in the same commit that adds or removes a verb. The failure message should say "a verb was added or removed — update the pin", so the number is reviewed rather than nudged.

Prefer that over raising 19 to a near-325 floor: a floor still silently absorbs the removal of a verb, which is the direction that matters here. Secondarily, `isVerbMethod` could skip by declaring type instead of by name (compare `m.Func` against the promoted `core.Base` method) — that removes the collision class outright, and makes the pin's stability meaningful.

Blast radius: test-only. `wantMinSweptVerbs` has exactly two readers, both in `internal/api/server_test.go` (`TestAuthzGuardsEveryVerb:1151`, and `TestAuditCoversEveryWriteVerbExactlyOnce` via `sweepVerbPairs`).

**What is already right, and should not be "fixed":** the service inventory itself is guarded. `sweepableServices` (`:939-978`) lists 27 services and `TestSweepCoversEveryWiredService` fails if it diverges from `features()` — added by `w1/m53` precisely because five wired services had been silently omitted. That is the strong half of this apparatus and the reason the omission class is closed; only the *verb*-level count is loose.

## The audit that produced this, and its real conclusion

This pass was the argument/authorization-level cross-surface parity audit `w4/086` named as its follow-on. The structural finding:

**bex's MCP surface is rigorously pinned against upstream Render, and bex's three own surfaces are not pinned against each other.** `mcp_parity_test.go` compares bex's live `tools/list` against a hash-pinned capture of `render-oss/render-mcp-server` (`renderMCPToolsSHA256`), with an accepted-divergence list guarded against staleness, a guard for upstream tools bex neither implements nor declines, and a weekly `scripts/render-mcp-drift.sh`. Nothing equivalent compares bex REST ↔ bex GraphQL ↔ bex MCP for the same verb's arguments. That is the hole in the apparatus, and it is why `w4/083`'s `resume_keyvalue` gap could ship.

Eight candidate divergences were chased and **all eight are deliberate** — recorded here so they are not re-filed:

| candidate | disposition |
| --- | --- |
| `create_postgres` exposes both `diskSizeGB` and `diskSizeGb` | Documented alias — `diskSizeGb` is Render's spelling, `diskSizeGB` the legacy bex one, precedence pinned at `postgres/mcp.go:62-65,78` (`w2/m91`) |
| Key Value `create` takes `region` on REST but not GraphQL/MCP | Accepted divergence in ADR018's ledger. REST accepts it for Render compatibility and ignores it; the view always reports `s.Metadata.PlatformRegion()` (`keyvalue/service.go:265`), so GraphQL and MCP are arguably *more* honest by not offering a dead knob |
| REST/GraphQL say `ownerId`, MCP says `workspaceId` | Tracks Render's own REST-vs-MCP inconsistency, which bex mirrors per surface |
| REST create has no `ipAllowListEntries` | REST's single `ipAllowList` is already the object form (`cidrBlock` records); the second spelling exists on the surfaces whose first spelling is a string list |
| the four from `w4/086` (MCP autoscaling, GraphQL static rules, REST rollback, MCP webhook event types, REST agent-session resume) | Re-confirmed; see `w4/086` |

## Unverified

- **Only the Key Value create family was compared argument-by-argument.** Postgres and web-service create were fetched from the live `tools/list` and eyeballed, not diffed field-by-field against their REST structs and GraphQL args. Every other verb is uncompared — the cross-surface argument audit is **started, not finished**, and remains the open follow-on.
- **Authorization parity was not compared per surface at all.** The reflection sweep proves each *Service method* refuses; it does not prove that REST, GraphQL and MCP all reach that method rather than a laxer sibling. Adapters calling an `…Authorized`/`…Fresh` variant directly were not enumerated.
- The claim that a `core.Base` name collision would be silently skipped is read from `isVerbMethod`'s predicate; it was **not** demonstrated by adding a colliding method and watching the sweep miss it.
- `325` is today's count on this checkout; it was measured once, not across build tags or optional feature wiring.
- Deploy status, **twelfth consecutive check**: production still serves the pre-`e6419af0b` build, so `w4/078`'s re-probe, `w4/m105`'s scoped exchange and `w4/m106`'s live refusal test all remain queued.

## Closed 2026-09-15

Replaced `wantMinSweptVerbs = 19` with pinned `wantSweptVerbs = 332` (HEAD; was 325 when filed) shared via `assertSweptVerbCount`. `isVerbMethod` now skips promoted `*core.Base` helpers by declaring type (AST of non-test source) instead of by name, so a service that shadows a Base name still joins the sweeps. `TestAuthzGuardsEveryVerb` and `TestAuditCoversEveryWriteVerbExactlyOnce` both pass.
