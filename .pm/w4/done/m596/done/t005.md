## Objective

Every `GET /v1/metrics/*` operation Render now scopes by project answers for a whole project or environment when given `project` or `environment` (and `region`), with `resource` narrowing it, and refuses what Render refuses, with Render's codes and its new 404.

## Context

- Render, live OpenAPI of 2026-11-23, on `active-connections`, `bandwidth`, `bandwidth-sources`, `cpu`, `cpu-limit`, `cpu-target`, `disk-capacity`, `disk-usage`, `filters/application`, `filters/http`, `filters/path`, `http-latency`, `http-requests`, `instance-count`, `memory`, `memory-limit`, `memory-target` and `replication-lag`:
  - `project`: "The query covers the resources in the project that you can view, so `resource` is optional when this is provided. If `resource` is also provided, the query covers only those resources, and each must belong to the project. Only one project can be provided. A project that doesn't exist or that you can't access returns a 404."
  - `environment`: the same rules for an environment. "If `project` is also provided, the environment must belong to that project."
  - `region`: "The region to query when querying by `project` or `environment`. Required when the project's or environment's resources are in more than one region."
  - Each operation now documents a 404 and the new `400MetricsBadRequest`: `too_many_resources` above 50 resources and `multiple_regions`. `bandwidth-sources`' own 400 keeps its cap of 30 "whether they are named with `resource` or come from a `project` or `environment` filter".
- bex today:
  - `parseMetricParams` answers "resource is required" without a `resource` (`lego/backend/internal/metrics/rest.go:425-431`).
  - `too_many_resources` exists only for bandwidth-sources above 30 (`metrics.TooManyResourcesCode`, `metrics/bandwidth_sources.go:46-51`, w5/m583).
  - The multi-resource datastore series landed in `0b23cceaf5`.
- Which resources a project contributes depends on the metric: services for HTTP and bandwidth, Postgres for `replication-lag`, Postgres and Key Value for `active-connections`. Check Render's behavior for a kind the metric does not apply to (skipped, or refused).
- bex runs one region. Use the same `region` and `multiple_regions` decision as t004.

## Steps

1. Parse `project`, `environment` and `region` in `parseMetricParams` (and in each operation's own parser that bypasses it), so `resource` is optional when either scope is given.
2. Resolve the readable resources of the project or environment, filtered to the kinds the metric applies to, and intersected with `resource`, refusing a named resource outside the scope.
3. Answer 404 for an unknown or unreadable project or environment, 400 `too_many_resources` above 50 (30 for `bandwidth-sources`), and 400 for an environment outside the given project.
4. Give GraphQL `metrics` and MCP `get_metrics` the same scope, or record why not. Upstream `get_metrics` takes no `project` (`render-mcp-tools.json`), so on MCP it is a bex extension.
