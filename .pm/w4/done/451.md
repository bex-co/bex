# Moving a Key Value into or out of an environment restarts it

Why: assigning a Key Value to an environment, or removing it, recreates its pod, causing a brief outage and a `config_restart` status, although only its grouping changed. Postgres does not restart on the same change, and Render does not restart resources when they move between environments.

- **Source / severity / estimate:** w4/364 / w4/m214 follow-up, loopx w4, 2026-11-01 (`bex-canary`, pin `d147703d7657`); **minor-to-major** (a Key Value move causes downtime), ~1h.
- **Evidence:** Free Key Value `red-dbjajapf06vc73aao8qg` (deleted). Pod `-0` before: created 02:56:28Z (uid `81179a45…`). `POST /v1/environments/<id>/resources {resourceIds:[kv]}` → 200, and 25 s later the pod was recreated at 02:59:02Z (uid `0e6df87a…`). `DELETE …/resources?resourceIds=kv` → 204, recreated again at 02:59:37Z (uid `f7f80ea8…`). Each read `config_restart` for ~4–5 s. On the same project, a Free Postgres assigned and unassigned stayed `available` throughout, with no restart. m214's project delete also showed the Key Value at `config_restart`.
- **Likely cause (verify):** the environment change alters something in the Valkey StatefulSet's pod template. Candidates: the environment IP allow-list layer copied into the Key Value spec (`EnvironmentIPAllowList`) feeding a template annotation such as `app.bex.co/credential-revision`, or a config/ACL hash. Compare the rendered template before and after an assign. Postgres applies its allow-list layer without a restart.
- **Fix direction:** apply environment membership and its allow-list layer to a Key Value without changing the pod template (proxy/NetworkPolicy side, as Postgres does), and mark that generation restart-free like w4/m233's Key Value rule.
- **Tests:** an operator test that an environment assign/unassign leaves the StatefulSet pod template unchanged, and a backend test that it reads `available`.
- **Dedupe:** w4/m233 made Key Value allow-list/rename saves restart-free; environment membership was not covered. No DO_NOT_DO item applies.

**Done (loopx w4, 2026-11-01).** Cause confirmed: the Valkey StatefulSet and its internal-proxy Deployment carry the CR's environment label on their pod templates (NetworkPolicies select by it), so every assign or unassign changed the template and rolled the pod. The environment label now follows the isolation label's w8/220 rule (`inPlacePodLabels`, `keyvalue_isolation.go`): an existing workload's template keeps its value unless it rolls for another reason, and running pods are relabelled in place. In bex-api, `markRestartFree` treats the environment allow-list layer (applied by the SNI proxy) as restart-free, and the environment, project and allow-list writers mark their write, so the store reads `available` throughout. Tests: `TestKeyValueEnvironmentMoveNeverRollsTheTemplate`, `TestSyncKeyValuePodIsolationRelabelsTheEnvironment` and `TestEnvironmentMembershipIsRestartFree`.
