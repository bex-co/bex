# A Postgres plan change reads Available for a moment before it reads config_restart

Why: right after a plan change is accepted, the database briefly reports `available` again, before the real restart begins. A client that stops fast-polling on `available` (the dashboard does) can miss the restart and show a stale Available. This is the same pre-acknowledgement class that w4/m215 fixed for major upgrades, here for resource changes.

- **Source / severity / estimate:** w4/364 live control, loopx w4, 2026-11-01 (`bex-canary`, pin `d147703d7657`); **minor**, ~1h.
- **Evidence:** on a Free PG18 (`dpg-dbjac79f06vc73aao8kg`), `PATCH {"plan":"basic-256mb"}` answers `config_restart`. 2 s polls then read `available, config_restart ×16, available`. A second change (`basic-1gb`) with 0.5 s polls read `available, config_restart ×19, available`. The first read after the accepted change says `available` both times.
- **Not the API read path:** bex-api uses an uncached client (`cmd/api/main.go:212`), and the restart-free mark is correctly absent for a plan change (`postgres/service.go:467-480`). `dbStatus` reads Ready's `ObservedGeneration` from the CR.
- **Likely cause (verify):** the database controller re-stamps Ready=True at the new generation on the pass that patches CNPG with the new resources. CNPG is still "Cluster in healthy state" until it starts the rolling restart, so the operator reports the new generation served before it is. Compare `reconcileDatabaseReadiness` (`lego/operator/internal/controller/database_controller.go`) with m215's `majorUpgradePending`. Hold Ready=False (`config_restart`) for a resource/plan generation until CNPG reports that generation applied: its phase leaves healthy and returns, or its pods carry the new resources.
- **Tests:** an operator regression for the frame after a plan/resource patch while CNPG still reads healthy (Ready must not be True at the new generation), and that an unchanged-resources generation stays Ready.
- **Dedupe:** w4/364 (restart-free saves) and w4/m215 (major upgrades) are done. No open item covers resource-change pre-acknowledgement. No DO_NOT_DO item applies.

**Done (loopx w4, 2026-11-01).** Cause confirmed: readiness counted only CNPG's `readyInstances`, which stays at full strength until CNPG starts rolling the new resources. The pass that patched the Cluster therefore stamped Ready at the new generation. `resourcesPending` (`database_controller.go`) now holds Ready=False (`Restarting`, so the API reads `config_restart`) until every desired instance is ready with the Cluster's `spec.resources` on its `postgres` container. Only the Cluster's keys are compared: a read-only check on production showed live instances also carry an `ephemeral-storage` request and limit the Cluster never sets. A list error or an empty list never holds. Test: `TestDatabaseResourceChangeStaysNotReadyUntilInstancesCarryIt`. The restart tests' fixture now carries its plan's resources, and the unchanged-resources path stays Ready. Not yet verified live: needs a pin with this operator image.
