## Objective

When a database is `unavailable` because its reconcile failed, show a value-free reason on REST, GraphQL and MCP and in the dashboard Details, so "Unavailable" is never a dead end.

## Context

- `dbFail` (`lego/operator/internal/controller/database_controller.go:1484-1488`) writes the reason and message to the Ready condition. `dbStatus` maps `Phase=Failed` to `unavailable`, and `PostgresView`/the GraphQL `Database` type have no reason field.
- Live: three fixtures showed only "Unavailable"; the Logs tab said "No database logs yet".

## Steps

1. Pick the field name to mirror the service/deploy precedent (e.g. a `statusReason`/`statusMessage` string). Sanitize it: no credentials or Secret names.
2. Render it in `dashboard/src/features/databases` Details next to Status, in en and zh.
3. While here, read the actual condition message for the reserved-role case and record it in t002/t001 notes (closes the hunt's unverified mechanism).

## Acceptance criteria

- [ ] A failed database exposes a reason on all four surfaces, and an available one exposes none.

Mechanism read from production 2026-10-05 (Loki, bex-system `manager`, `dpg-db1esrpj8bls738hh190` 00:27 UTC): every reconcile failed with `admission webhook "vcluster.cnpg.io" denied the request: Cluster.cluster.cnpg.io … is invalid: spec.managed.roles: Invalid value: "postgres": This role is reserved for operator use` — the ClusterFailed path (`dbFail`), surfaced now as the fixed `statusReason` "The database cluster rejected its configuration…".
