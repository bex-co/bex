# 654 — A Postgres version upgrade records no caller, so `postgres_upgrade_started` carries no `user`

Why: Render's Postgres Upgrade Started details offer an optional `user`; bex's upgrade facts come from watching the database status, so no caller reaches them (w4/m379 t002 left it out).

- **Source / estimate:** follow-up from w4/m379 (2026-11-14). **Minor** (optional field). ~45m.
- **Fix:** record the caller of the PATCH that set `spec.version` (for example on the audit row or an annotation the observed fact reads), and carry it on `postgres_upgrade_started` and its by-id read.
- **DoD:** an upgrade started from the dashboard by the QA user carries `user {id, email}` on `GET /v1/events/{id}`.

- **Closed 2026-11-14 (/loopx w4):** both version writes (REST `PATCH /v1/postgres/{id}` with `version` via `UpdatePostgres`, and the dashboard's GraphQL `updateDatabaseVersion` via `SetVersion`) now record a deferred `postgres.SetVersion` audit row only after the write succeeds (`core.DatabaseVersionChanged`; no event of its own), and `GetServiceEvent` lateral-joins the newest such row before a `postgres_upgrade_started` fact as its caller, so Retrieve event (REST/MCP) carries `user {id, email}`; no migration (the `audit_events (target, at)` index serves the join).
