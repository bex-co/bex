# An awake, unhealthy Free service answers public requests with "service hibernated"

Why: an API client investigating a readiness outage receives an idle-sleep diagnosis even though the instance is running; preserving the retry behavior while reporting readiness truthfully avoids sending users to the wrong cause.

- **Severity:** minor (misleading diagnostic; the 503, retry interval, routing hold and liveness recovery work).
- **Estimate:** ~45m, one responder change plus handler-level regression controls and contract documentation.
- **Source:** live `qa-find-bugs` loop, 2026-10-07 sweep 14; workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, source HEAD `ed2a44850`. Owned Free image service `qa-20261007-r14-health-4d9c82`, `srv-db33lejr0hnc73dqghs0`. Two complete failure/recovery rounds reproduced this; a fresh dashboard reload during round 2 confirmed the API state. No implementation is included in this filing.

## Reproduce

1. Create an owned Free web service from `docker.io/library/busybox:1.37`, port 3000. Its Docker Command copies a mounted executable CGI into writable `/tmp/www/cgi-bin/health.cgi`, writes a fixed root marker, and runs `httpd -f -p "$PORT" -h /tmp/www`. The CGI's `?mode=fail` creates an ephemeral sentinel; while it exists the CGI returns HTTP 503. A container restart removes that sentinel and restores HTTP 200. Exact synthetic script and creation response are in the local browser evidence.
2. Settings → Edit Health Check Path → `/cgi-bin/health.cgi` → Save changes. Wait for Live and Running. The actual pod has HTTP startup/readiness/liveness probes on that path, five-second timeouts, and liveness 10-second period × six failures.
3. Request `/cgi-bin/health.cgi?mode=fail`. After readiness removes the pod, GET the root with `Accept: application/json`. Compare the GraphQL query below and the pod's state at the same time. **Actual:** public JSON says hibernated; App phase is Deploying, Ready=False/HealthCheckFailing, and the same pod is running with `started:true`. The latest deploy remains live; no deployment was requested by the failure control.
4. Wait for liveness recovery and repeat after a fresh dashboard reload. Both rounds returned the fixed root marker again with the same pod UID and incremented restart count (0→1→2). Removing traffic for a normal sleep provides the cold-wake control described below.

Synthetic CGI used in the repro (mount as `qa-health.sh`, then copy/chmod into `/tmp/www/cgi-bin/health.cgi`):

```sh
#!/bin/sh
case "$QUERY_STRING" in
  mode=fail) touch /tmp/qa-health-fail ;;
  mode=pass) rm -f /tmp/qa-health-fail ;;
esac
if [ -f /tmp/qa-health-fail ]; then
  printf 'Status: 503 Service Unavailable\r\nContent-Type: text/plain\r\n\r\nqa-r14-health-fail-4d9c82\n'
else
  printf 'Content-Type: text/plain\r\n\r\nqa-r14-health-pass-4d9c82\n'
fi
```

## Cause and target fix

- `lego/operator/internal/controller/app_controller.go:2827-2835` correctly keeps the public route on the activator when a sleep-eligible web service has no ready endpoint, even while awake. Preserve this w6/m94 readiness hold; removing it would restore the raw Traefik error race.
- `lego/operator/cmd/activator/main.go:136-177` handles maintenance and suspension first, then sends every other routed request through the same wake response. `writeWakeResponse:210-218` unconditionally writes the literal hibernation message, ignoring the already-resolved App state.
- **Target:** make the shared non-HTML readiness/wake response `{"error":"service not ready","retryAfter":5}` for both awake-unready and genuinely sleeping clients. Retain HTTP503, Retry-After5, no-store, content negotiation and HEAD body suppression. This deliberately changes the documented JSON error text for cold wakes too; update that contract and its exact-body tests together. Keep immediate responses, routing and wake behavior. Do not branch on phase: the real cold-wake control below also transitions to Deploying before it becomes ready.
- The consumer `writeBody:251-257` takes a plain body string and writes it with `io.WriteString`; no JSON serializer/schema replaces it. The fix needs no new enum, state field or lookup. Before cache/refetch settlement, the shared response remains the same neutral not-ready message: it does not infer sleep from a stale App phase. The existing five-second host-cache refresh and retained snapshot on refresh failure stay intact.
- Framework check: local Go1.26.5 `src/io/io.go:314-319` sends the same string directly to StringWriter/Writer; the platform module declares Go1.26.0. The deployed patch version was not queried, and the hard-coded diagnostic does not depend on it.

## Scope, controls and dedupe

There is **one production call** of writeWakeResponse (main.go:177), plus its declaration and one direct test call. Repository searches found the current literal in that responder, its tests and documentation/comments; no dashboard/CLI/script consumer branches on it. Public platform and custom-domain hosts and paths share this handler; GET and HEAD were exercised. Web services (including legacy untyped web) use the readiness hold; private/worker/cron have no public App-host path. Static suspension returns through the earlier suspended branch; Postgres/Key Value use their separate TCP proxies.

Keep unknown-host 503, explicit suspension without wake, paid maintenance and its bounded origin errors, IP denial, real app responses, and genuine cold-wake scaling/recovery intact. No authenticated not-found/forbidden/unauthenticated behavior changes. Add handler-level controls for asleep zero replicas, awake unready nonzero replicas, unknown phase, JSON/wildcard/HTML negotiation, and HEAD; preserve annotation/scale behavior and the List-free request path.

The genuine sleep/wake control passed: before the first public request at 12:47:24 UTC, App phase was Hibernated, Ready=False/AutoHibernated, and Deployment desired/ready replicas were 0/0. The same GET URL and Accept above at 12:47:25 UTC returned HTTP/2 503, `cache-control: no-store`, `content-type: application/json`, `date: Wed, 07 Oct 2026 12:47:25 GMT`, `retry-after: 5`, `content-length: 45`, and the complete body `{"error":"service hibernated","retryAfter":5}`. At +6.553s it still returned that body while App phase was Deploying; at +13.032s it returned HTTP 200 with `qa-r14-root-4d9c82`, Running, same served revision rev-3. This proves why phase-based wording is insufficient and why the cold-wake tests must adopt the neutral text while preserving recovery.

The invalid non-slash health path was refused with a useful toast and retained draft. Clearing the saved path produced a new Live release with TCP probes; the HTTP health endpoint then returned 503 while the root returned 200, Ready stayed true and the container had zero restarts for 84 seconds. This verifies the mode switch, not a fix for the message.
