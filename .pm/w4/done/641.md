# 641 — Key Value, Postgres, environment group, project, Blueprint and webhook pages never adopt their own workspace: opened while another workspace is selected, the switcher, sidebar and capabilities stay on that one, and a delete lands on its Overview

Why: w6/091 fixed this for services. A service page now makes its owning workspace the selection, so its controls are judged by the caller's role in that workspace. Every other resource detail page still uses whatever the switcher last held. On a link from email, search, a teammate or a webhook payload, the page shows another workspace's sidebar and switcher, gates its controls on the caller's role in that other workspace, and after a delete sends the user to that workspace's Overview.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 323, 2026-11-13 20:36–20:50 UTC (`muse.env`; pin `1c4d721bc8dc`; dashboard driven from an isolated headless Chromium). **Minor** (it fails closed: a wrong-workspace role can only disable controls; the landing is misleading). ~1h.
- **Account:** the QA user is a member of `bex` (listed first), `tian-personal` and `bex-canary`. All probed resources are in `bex-canary`.
- **Probe 1, Key Value created and deleted through the UI:**
  - New → New Key Value, name `qa-20261113-r323-kv` (`red-dbrna3td9ioc73ds1iu0`), Free, Public access off → landed on `/keyvalue/red-dbrna3td9ioc73ds1iu0`. It read Available at 20:38.
  - Reveal connection info showed the internal URL and CLI command, and "Not public. Add an inbound IP rule under Networking to enable external access."
  - In a fresh context, opening `/keyvalue/red-dbrna3td9ioc73ds1iu0` left the switcher on **bex**, with cookie `bex.selectedWorkspaceId=tea-d98210cbbpdc73dcrkvg`.
  - Danger Zone → typed `sudo delete key value qa-20261113-r323-kv` → toast "Deleting qa-20261113-r323-kv…" → landed on `/`, listing bex's `beancount.io` and other projects, not bex-canary's `hello-go`. REST then answered 404 for the store.

- **Control:** a bex-canary service page in the same fresh context switches to bex-canary (w6/091). The cookie race on that first visit is w4/640.
- **Root cause:**
  - Only three pages call `useAdoptResourceWorkspace` (`dashboard/src/features/workspaces/hooks/use-adopt-resource-workspace.ts`): `services/components/service-detail-layout.tsx:58` and two automation pages. `grep -rln useAdoptResourceWorkspace dashboard/src` finds no others.
  - The detail routes `keyvalue.$keyValueId.tsx`, `databases.$databaseId.tsx`, `env-groups_.$groupId.tsx`, `project.$projectId.tsx`, `blueprints.$blueprintId.tsx` and `webhook.$webhookId.tsx` never adopt.
  - Their controls read `useCapabilities()`, for example `keyvalue/components/key-value-plan-section.tsx:39`, `connection-info-panel.tsx:54` and `key-value-row-actions.tsx:36`. That provider is scoped to `currentWorkspaceId` (`features/capabilities/context/capabilities-provider.tsx:124-160`), so a Contributor here and Admin there sees the wrong enablement, the w6/091 failure.
- **Fix (target behavior):** every resource detail page makes its owning workspace the selection on entry, as `ServiceDetailLayout` does.
  - It calls `useAdoptResourceWorkspace(id, ownerId)` once the resource's `ownerId` resolves. Each detail query must select `ownerId`: the Key Value, Database, EnvGroup, Project, Blueprint and Webhook reads.
  - It renders the pending state the hook reports, so role-gated controls never paint for the wrong workspace first.
  - A non-member's selection is unchanged and fails closed, as w6/091 specifies.
  - Pair with w4/640, so adoption on a first visit also persists the cookie.
- **Blast radius:**
  - The six detail routes above and their nested tabs: Key Value and Postgres Overview/Metrics/Logs, env group, project index and settings, Blueprint detail, webhook index and settings.
  - Their post-delete navigations to `/` are fixed by the same change.
  - Regression tests follow `use-adopt-resource-workspace.test.ts`: a mismatched selection per page, a non-member, and no undo after a deliberate switch.
- **Unverified:**
  - The Postgres, project, Blueprint and webhook pages were not opened: there was no bex-canary fixture of those kinds, and the one Free Postgres slot was held by another session earlier. They are read from code.
  - Disabled controls under a differing role could not be shown: the QA user holds the same role in every workspace.
- **Dedupe:**
  - w6/091 (done) is services only. Its fix note says "ServiceDetailLayout, the shared chrome for `/services` and `/static`".
  - w9/086 (done) is automations.
  - w4/640 is the first-visit cookie race on the adopting pages.
  - `grep -rln "useAdoptResourceWorkspace\|adopt" .pm` finds no item for datastores, groups, projects, Blueprints or webhooks.
  - Not deploy lag: `git log 1c4d721bc8dc..origin/main -- dashboard/src/features/workspaces dashboard/src/routes` is empty.
