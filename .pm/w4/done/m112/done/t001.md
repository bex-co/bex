## Objective

`stuckPodMessage` only inspects containers in `Waiting` state (CrashLoopBackOff, ImagePullBackOff, config errors), so a pod that is `Running` but never `Ready` because its startup/readiness probe fails — the entire health-gated stall class — falls through to the generic "waiting for the current Deployment revision and pods to become ready" message. Extend the diagnosis to name the failing probe, its path, and the observed result.

## Context

### The observation (production, 2026-09-17)

`config_change` deploy `dep-dam2bvjs0ils73bgove0` (service `srv-dam2aih2dbts73fi25tg`, health path `/qa-bogus-health`, 404s): new pod logged `Example app listening on port 3000!` at 10:40:27 and stayed unready; the deploy sat `update_in_progress` with the log stream simply stopping. The operator's Ready condition for the whole window could only have been the generic `reportRolloutProgress` message — `stuckPodMessage` (`lego/operator/internal/controller/app_controller.go:4176-4190`) `continue`s past every container whose `State.Waiting` is nil, and a probe-failing pod is `Running`, never `Waiting`.

### Fix shape

- In or alongside `stuckPodMessage`, detect the case: current-revision pod `Running` + `Ready=False` + a startup or readiness probe whose recent result is failure. Name the probe (startup vs readiness), the configured path (`/qa-bogus-health`), and the observed outcome where kubelet exposes it (HTTP status / connection failure).
- Keep the existing Waiting-state cases byte-identical (they are the t003 regression controls); the probe case is additive and must not fire for TCP-mode port checks that pass.
- Respect the `currentRevisionPodsReady` inconclusive-true semantics: a missing pod list stays silent rather than guessing.
- Where the diagnosis lands (Ready-condition reason/message on the App, as today) stays the same; t002 moves it to UI-readable surfaces.

### Acceptance

- Unit coverage at the `stuckPodMessage` call site: a fake Running-unready pod with a failing HTTP probe yields a message naming the path; the existing Waiting cases render exactly as before.
- The message fits the existing condition-message budget (short, no pod-name spam — aggregate by reason, not by pod).
