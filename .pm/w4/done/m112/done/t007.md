Per DoD bullet:

- **The stall names the probe** — operator `TestProbeStallMessage` (the live
  fixture's exact shape: a Running, unready pod whose startup probe targets
  `GET /qa-bogus-health` on port 3000 yields a message naming probe type,
  path and port, plus the restart count when liveness has already acted);
  dashboard `deploy-header.test.tsx` "names what an in-progress rollout is
  waiting on". Both cases the old code could not express: `stuckPodMessage`
  `continue`d past every non-Waiting container, and `DeployHeader` had no
  such field.
- **The events feed carries the same reason** — by construction, not by a
  parallel implementation: the feed query reads the same `deploys.stall_reason`
  column through its outer join, scoped to the `deploy_started` phase, and the
  row renders it through the same `DeployFailureReason` component the deploy
  page uses. See t002's recorded seam decision for why this is a column rather
  than a `reasonCode` fact.
- **Existing stall signals unchanged** — `TestStuckPodMessage` (crash loop
  with/without `$PORT`, image-pull, merely-progressing) is untouched and
  green, `TestCrashLoopWinsOverProbeStall` pins the precedence, and
  `TestObservedServiceStateExcludesRolloutSettling` plus the new
  `TestProbeStallIsNotAnOutageWhileTheDeployIsOpen` keep the w3/m78 exclusion
  intact — the stall mints no outage fact, webhook or push.
- **The settle itself is untouched** — no change to `settleFailedRollout`,
  `settlePriorRelease`, `progressDeadlineSeconds`, or the deploy transition
  model. The one terminal-side change is the WORDING of an already-failing
  deploy's `failure_reason`: it now inherits the probe diagnosis instead of
  the generic health-gate line (`TestFailedDeployInheritsTheProbeDiagnosis`),
  which is the same verdict with a better sentence.
