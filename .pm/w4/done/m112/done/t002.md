## Objective

The operator's stall diagnosis (t001) lives on the App CR's Ready condition, which no UI-readable field carries — the deploy detail page and events feed can only show a bare "In Progress". Project the reason onto a surface the dashboard already reads while the deploy is still open.

## Context

### What exists (verified on `main`, not live-probed — confirm before building on it)

- Service events carry `reasonCode` end to end: `ServiceEventDetails.reasonCode` (`dashboard/src/features/services/api/events.graphql:48`) renders through `services.eventsReason.*` locale keys (`dashboard/src/routes/services.$serviceId.events.tsx:472-474`).
- The backend vocabulary already has `readiness_failed` (`lego/backend/internal/store/event_facts.go:105`), but today it is emitted only for post-hoc outage observations (`reconciler.go:1506`, datastore/unhealthy availability) — never for an in-progress rollout stall. The w3/m78 `RolloutSettling` exclusion exists precisely so in-progress windows do NOT mint outage facts.
- Deploy rows carry `failureReason`/`cancelReason`, set at terminal states — nothing names a mid-flight stall cause.

### Fix shape

- Decide the seam explicitly (record the decision in the task file): extend the `reasonCode` vocabulary with a stall-during-rollout code emitted as a non-outage service event, or add an in-progress reason field on the deploy projection fed from the operator condition. Either way the new signal must NOT trip outage pages, webhook `server_failed` payloads, or push notifications — the w3/m78 exclusion is the control.
- Wire operator condition → backend projection on the existing poll/reconcile path (no new watch); the reason must appear within ~2 minutes of the stall starting and clear when the rollout completes, fails, or is canceled.
- Keep REST/GraphQL/MCP consistent: whatever carries the reason must read identically on all three (the events surface already does).

### Acceptance

- The milestone DoD's events-feed bullet passes live: a reason renders on the in-progress deploy's rows and agrees with the deploy detail page (t003).
- No new outage/webhook/push traffic attributable to the stall signal (prove with the w3/m78 exclusion tests + a live events-feed capture).

## Seam decision, 2026-09-18 — an observation column on the open deploy row

**Chosen:** a `stall_reason` column on `deploys` (migration `0130`), projected
from the App CR's Ready condition on the reconciler's existing `recordDeploy`
pass and cleared inside `TransitionDeploy` the moment the row goes terminal.

**Rejected:** minting a service event fact. A fact is append-only, so "clears
when the rollout completes, fails, or is canceled" would have to be expressed
as a second compensating fact; worse, every fact type flows through the
availability/outage machinery this task forbids touching — `RecordObservedServiceState`,
the `server_failed` webhook mapping (`webhooks/worker.go:513`), and the
Critical push policy. A column carries no such blast radius: it is read, never
dispatched.

**Why it satisfies the no-side-effects requirement, structurally rather than
by configuration:**

- `observedServiceStateFor` is untouched, so the w3/m78 `RolloutSettling`
  exclusion and the `hasOpenDeploy && !concreteContainerFailure` guard still
  decide availability exactly as before. `HealthCheckFailing` is deliberately
  NOT added to `concreteContainerFailure` — pinned by
  `TestProbeStallIsNotAnOutageWhileTheDeployIsOpen`.
- No new fact type, so no webhook event, no push notification, no outage page.
- `SetDeployStallReason` writes only `WHERE finished_at IS NULL AND
  stall_reason IS DISTINCT FROM $2`, and never touches `updated_at` — a stall
  that lasts the full budget costs one UPDATE and churns no updated_at-keyed
  reader.

**Surfaces.** One column reaches all of them: `store.Deploy.StallReason` →
`deploys.DeployView.StallReason` → REST `stallReason` (in the shared
`renderDeploy`, which MCP's `list_deploys`/`get_deploy` also return) and
GraphQL `Deploy.stallReason`. The events feed reads the same column through
the feed query's outer `deploys` join, scoped to the `deploy_started` phase, so
**the feed and the deploy detail page cannot disagree** — which is the DoD
bullet's actual requirement. It is carried as `ServiceEventDetails.stallReason`
rather than as a `reasonCode` value, because a `reasonCode` would have meant a
fact, which is exactly what this decision rejected.
