## Objective

Collect and verify a payment method for the reserved workspace without handling raw card data or borrowing the current workspace's Stripe Customer.

## Context

- Current setup-mode Checkout requires an existing tenant/Customer/Subscription (`billing/sessions.go`) and therefore cannot run before `createWorkspace`.
- Stripe's documented setup flow supports a server-created Customer + SetupIntent followed by Payment Element and Stripe.js `confirmSetup` in the authorized browser.
- `stripe-go/v86.1.1` exposes SetupIntent primitives directly; do not fall back to legacy Card Element, Tokens, Sources, or server-side PAN collection.
- Dynamic payment methods stay enabled: do not send `payment_method_types`. Billing email should become the Customer email; all provider objects need attempt/reserved-workspace metadata and deterministic idempotency keys.

## Steps

1. Add a narrow provider seam to prepare a Customer + SetupIntent from an authorized attempt and return only the publishable key/client secret/opaque attempt data the browser needs.
2. Create or recover the dedicated Stripe Customer and SetupIntent idempotently, stamp safe correlation metadata, and validate test/live mode consistency.
3. Verify success by re-reading Stripe objects and/or a signature-verified `setup_intent.succeeded` event; prove Customer, SetupIntent, PaymentMethod, attempt, and subject-reserved workspace correlation before accepting it.
4. Bind the verified method as Customer/contract default, preserve the existing `payment_method_bound_at` source-of-truth rule, and add cleanup for expired unfinalized Customers/Intents.
5. Wire and validate the publishable-key configuration alongside the restricted server key, including `.env.example`, backend env inventory, GitOps/secret plumbing, and mode mismatch refusal.

## Acceptance criteria

- [x] Each attempt gets its own Stripe Customer with the submitted email and reserved `tea-*` correlation; no current-workspace Customer/card is read or reused.
- [x] Only a succeeded, same-mode SetupIntent tied to the caller's attempt can advance finalization.
- [x] Duplicate prepare/webhook/finalize delivery converges without duplicate Customer, SetupIntent, Subscription, or payment marker.
- [x] No `payment_method_types`, raw PAN/CVC, server key, client secret, or provider response body is persisted/logged beyond the minimum safe fields; client secrets are only returned to the authorized browser flow.
- [x] Expired attempt cleanup cancels/removes provider artifacts safely and is retryable.
- [x] Stripe stub/sandbox tests cover success, SCA/redirect continuation, cancellation, expiry, replay, wrong subject/attempt, and livemode mismatch.
