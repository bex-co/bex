# 390 — Linking an env group still warns that an Auto-Deploy-off service "may restart", though since w4/m239 it waits for the next deploy

Why: the copy now tells users the opposite of what happens. A user holding a link for a maintenance window reads that it will restart now, and a user who needs the change live gets no hint that they must deploy.

**Severity:** minor (copy contradicts behavior; no data loss). **Estimate:** ~40m. **Source:** live `/qa-find-bugs w4` loop run c2w6, 2026-10-23 UTC (`muse.env`, `bex-canary`, pin `b3cd5bc74de8`, which includes w4/m239). Fixtures: static site `qa-20261022-c2w6-site` (`srv-dbdaovi8ohec73f9ftp0`; public Git `bex-co/bex` `main`, root `examples/static-site`, build `echo "grp=$QA_C2W6 own=$QA_OWN" > v.txt`) and group `qa-20261022-c2w6-grp` (`evg-dbdap7nvlr1c73fj19s0`). ## Probe

1. With Auto-Deploy on, the group was created linked in the dashboard and served `grp=one own=svc1` (the service's own `QA_OWN` wins, as on Render). Save and deploy of `QA_C2W6=two` served `grp=two` about 2 min later. Both correct.

5. The Linked Services card description reads "Linking or unlinking changes service configuration and can restart services even when auto-deploy is off."

## Root cause

- The copy was written by w4/176 (2026-10-04), when link/unlink did roll gated services. w4/m239 (done 2026-10-22, live on pin `51e6dc76c8fe`) staged gated links in `app.bex.co/pending-env-group-links` until the owner's next deploy (ADR013 § "Link, unlink and group delete are staged the same way"). The copy was never updated.
- `dashboard/src/features/env-groups/locales/en.ts:409-412` `envGroups.servicesDescription` and `:490-493` `envGroups.linkChangeNote`; zh at `zh.ts:397-399`, `:475-476`.
- Used by `linked-services-card.tsx:67` and both toasts in `hooks/use-env-groups.ts:310,330`. That shared hook also serves the service Environment tab's Link/Unlink (`env-groups-panel.tsx`, via `useEnvGroupMutations`), so both entry points are wrong.
- `locales/__tests__/redeploy-copy.test.ts` pins the old premise ("link copy must warn of a restart even with auto-deploy off").

## Fix (target behavior)

- The card description and both toasts state the m239 rule: a service with Auto-Deploy on redeploys now, and one with it off picks the change up with its next deploy. en + zh.
- If the toast can know the target's Auto-Deploy (the panel has `service`; the group page lists linked services), it names the actual outcome. Otherwise the rule wording is enough.
- Update `redeploy-copy.test.ts` to assert the new premise, and that no link/unlink copy says "restart … even with auto-deploy off".
- Group delete copy: check the delete-confirm keys say the same.

**Unverified:** group delete on an Auto-Deploy-off service (not probed this run).
