# 456 — A brand-new service briefly says "Saved changes aren't live yet. Use a standard deploy to apply them." while its first deploy finishes

Why: nothing was saved after create, so the banner's advice is wrong: it invites a needless Manual Deploy on top of the deploy that is already applying the configuration. It shows on every new service for ~10 s, at the moment users are watching the page.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-01 UTC (`muse.env`, `bex-canary`, pin `fdd51c53ef3f`), seen on the Shell tab of a fresh service; **minor**, ~45m. ADR004 (saved vs served configuration, w4/m184, w4/414).
- **Repro (REST + GraphQL, QA workspace):** `POST /v1/services` a Free `docker.io/traefik/whoami:latest` image web service with nothing else. Then poll `{ service(id:"<id>"){ phase revision undeployedChanges undeployedChangesApplying undeployedChangesReason } }` every second. Fixture `srv-dbjl0tjbb81s739b3dg0` (deleted):

  ```
  14:45:10 created
  14:45:10 {phase: '',        revision: '',      undeployedChanges: False, applying: False, reason: ''}
  14:45:11 {phase: Deploying, revision: '',      undeployedChanges: False, applying: False, reason: ''}
  14:45:43 {phase: Deploying, revision: 'rev-1', undeployedChanges: True,  applying: False, reason: 'saved'}
  14:45:54 {phase: Running,   revision: 'rev-1', undeployedChanges: False, applying: False, reason: ''}
  ```

  The dashboard header renders the banner whenever `undeployedChanges` is true (`dashboard/src/features/services/components/service-detail-header.tsx:307`). It was on screen for `srv-dbjkvpbea3ic73dakj4g` at its Shell tab while "Latest deploy: In Progress". After a reload, once the window passed, it was gone.

- **Expected (target behavior):** with no save after create, `undeployedChanges` stays `false` from create through Running on REST, GraphQL and MCP, and the banner never renders. A save made during the first deploy keeps today's `undeployedChangesApplying` / `saved` semantics (w4/m184).
- **Where it comes from (traced, exact field unverified):** the flag flips exactly when `Status.ActiveRevision` is first stamped while the rollout is still converging. That is w4/405's early stamp in `reportRolloutProgress` (`lego/operator/internal/controller/app_controller.go:~3589-3597`), and it makes `releaseHasServed` true (`release_identity.go:549`). From then on `servingConfigurationDiffers` (`saved_configuration.go:151-196`) compares the saved spec against generation 1's runtime record and returns `different` with `UndeployedReasonSaved`, until the Running pass makes them agree. Candidates for the transient difference: the record's container image versus `servesSavedImage` (digest vs `:latest`, `:177-183`); `ConfigSnapshotGeneration` still 0 for the newly served generation (`:165`); or the settings fingerprint (`:192-196`). Without cluster access this run, the worker must read the App status and record at the stamped moment to name the field.
- **Fix direction:** make the comparison treat a first release that is still settling (served revision stamped, phase Deploying, generation == the only release) as carrying the saved configuration, or make whichever record field lags agree at stamp time. Do not suppress the flag generally: a save during a rollout must still read `applying`, and a cancel-over-served must still read `saved`.
- **Tests:** an operator test where an App has `ActiveRevision` freshly stamped by the 405 path, phase Deploying, and no save → `UndeployedChanges=false`. Regressions: a save during the first rollout → `applying`; w4/414's image override → `image_override`; w8/m135's PATCH-without-deploy → `saved`.
- **Unverified:** whether build-from-repo and static sites show the same window (static sites are excluded at `saved_configuration.go:84`), and whether a second (non-first) standard deploy has a matching window.
- **Render:** Render shows no unsaved-changes notice on a new service; its first deploy simply runs.
- **Dedupe:** w4/414 (image override → its own reason), w4/m184 (applying wording), w4/216/243/281 (save flows) and w8/m135 (PATCH saves without deploying) cover other causes. No open item in any workstream mentions this window, and `saved_configuration.go` is unchanged on `main` since the pin. No DO_NOT_DO item applies.
- **Cleanup:** all three `qa-20261101-1442-sh*` services deleted (`GET` 404, workspace list `[]`); session revoked.
