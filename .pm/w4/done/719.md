# A new stable Go release reaches native Go builds within about a day, as on Render

Why: Render's changelog of 2026-04-16 ("Automatic Go version updates") moves its native Go to the latest stable Go 1.x, "usually within 24 hours of a new release". bex's Go line moves when someone commits a reviewed digest bump after a weekly freshness issue, so a new Go release can take a week or more to reach a build. Found by w4/m553 t002 on 2026-11-22 ([disposition table](../../../docs/render-artifacts/render-changelog.md)).

- **bex:** `lego/operator/internal/build/native.go` pins one Go line (`golang:1.27-bookworm@sha256:…`, w5/m144) and says it tracks Go's latest stable. `.github/workflows/build-toolchain-freshness.yml` runs on Thursdays and opens a tracking issue when a digest moves. `scripts/image-pin-validate.sh` requires every image to stay digest-pinned.
- **End state:** a new stable Go 1.x release (a new patch or a new minor line) is in the native Go builder within about a day, with nobody's action, and the image stays digest-pinned with its checks run before it ships. A test or the freshness self-test covers the new release being picked up.

## Outcome (2026-11-23, done)

- **Mechanism.** `.github/workflows/go-line-bump.yml` runs every three hours. `toolchain-freshness.py go-release` compares go.dev's newest stable release with the `GOLANG_VERSION` the pinned image sets on linux/amd64 and linux/arm64. Once the official `golang:<line>-bookworm` index carries the new release on both, `scripts/go-line-smoke.sh` builds a module declaring `go <release>` in that image with the network off, on an arm64 and an amd64 runner. Then `go-apply` rewrites the line, the default line and the digest in `native.go` and the `native-go` inventory entry. The inventory validation, `scripts/image-pin-validate.sh` and the operator's `internal/build` tests run, and the commit is pushed to main as `github-actions[bot]` (`contents: write`, no secret). deploy.yml deploys it after every suite passes. A release the official image has not published yet waits for a later run, and a Debian rebuild with the same Go stays in the weekly review. [ADR060 D7](../../../docs/ADR060-build-worker-reliability-and-performance.md) records the exception, and the Render changelog row is now `matched`.
- **Tests.** `scripts/build-toolchain-freshness.test.sh` covers these plans: current, an older feed release, a new patch, a new minor, Go's `go1.28` naming, an unpublished tag and one platform behind. It checks the exact two-line rewrite on the real `native.go`'s entry shape, the no-op and refusal cases, and the workflow's write boundary. `scripts/go-line-smoke.test.sh` covers the smoke checks, and `TestNativeGoLineIsItsImageTag` guards the entry shape. Each of five mutations of the planner and applier, and two of the Go guard, failed the suites.
- **Live checks.** `go-release` against go.dev and Docker Hub answers `current` (1.27.4). With a fixture release of 1.27.9 it answers `wait`. `go-line-smoke.sh` passes on the pinned image for 1.27.4 and fails for 1.27.5 with Go's own `go.mod requires go >= 1.27.5 (running go 1.27.4; GOTOOLCHAIN=local)`. A simulated 1.27 → 1.28 bump of the real tree passed validation, the pin guard and the `internal/build` tests. The first try surfaced two tests that hardcoded 1.27; they now read the line from the table. The first real bump waits for Go's next release.
