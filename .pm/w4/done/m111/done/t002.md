## Objective

The service Environment tab's **Create group** opens the same dialog with ONLY the current service listed and pre-checked (`initialServiceIds=[serviceId]`) — so from any in-environment service the create is un-succeedable by construction: the one offered link is the one the backend rejects. After t001's scope support, thread the service's environment into the dialog so the pre-checked path succeeds.

## Context

### The observation (production, 2026-09-17)

On `/services/srv-dalpb5l2r12c73cngju0/env` (service in `qa-env`), **Create group** → dialog shows a single checked checkbox (`qa-20260917-p3-web`) → name `qa-20260917-p3-evg2` → **Create Environment Group** → same toast as t001: `Couldn't create … / linked services must have the same Environment scope as the environment group`. Evidence screenshot: `.playwright-mcp/qa-p3-evg-create-scope-fail.png` (gitignored, local to the QA session). The user made no choice at all — the UI pre-selected the failing option.

### Root cause (verified on `main`)

`dashboard/src/features/services/components/env-groups-panel.tsx:211-219` renders `NewEnvGroupDialog` with `services={service ? [service] : []}` and `initialServiceIds={[serviceId]}` but no scope — the dialog defaults to a workspace-scoped create, which `validateLinkedServiceEnvironments` (`lego/backend/internal/envgroups/service.go:1280`) rejects for the in-env service. Note the panel already computes scope-aware `available` groups for linking (same file, above the dialog) — the create path is the only scope-blind spot.

### Fix shape

- Pass the service's environment id into the dialog as its initial scope (t001's picker prop), so the pre-checked service is compatible by construction and the group lands in the service's environment.
- The panel's `service` is a `ServiceView`, which carries no `environmentId` (`dashboard/src/features/services/types.ts:7-60`) — resolve it via the existing `useEnvGroupScopeIndex().serviceEnvironmentById` (same source the detail card uses), not a new query.
- Keep the picker visible (not locked): switching scope away must uncheck/clear the now-incompatible pre-check per t001's stale-selection rule, with the same reason copy.

### Acceptance

- The milestone DoD's "Service-page create succeeds" bullet passes live for both an in-env service (group lands in the env, link attached) and a workspace-scoped service (today's working behavior preserved).
- No new GraphQL round trip attributable to this path (scope index is already loaded by the feature).
