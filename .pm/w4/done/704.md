# 704 — One failed events read fails the whole tenant-view canary as "the feed did not advance": stage 4 exits 6 on the first transport error, where stages 2 and 3 poll through it

Why: run `44178319668` ("Production edge liveness", 2026-11-17 21:17 UTC) failed at `FAIL(4/4 events): GET /v1/services/srv-dbkq3hdhhjfs73eiahe0/events failed`. It then reopened #167 as "Tenant view is broken: 4/4 events (the feed did not advance)". The feed was fine, and nothing was stalled: the one read failed to complete (curl transport error). The same call answered 200 at 21:4x. The issue now tells the operator the tenant view is broken.

- **Source / severity / estimate:** live `/qa-find-bugs w4` round 887, 2026-11-17 21:27–21:45 UTC, pin `e0a5ba20aac8`. The same probe shows the OpenStatus pinger still live, with 15 of the canary's 16 request lines in the 15 minutes to ~21:35 UTC coming from `OpenStatus/1.0` at `85.239.239.149` ([w4/676](blocked/676.md)). **Minor:** a false alarm, and no tenant is affected. ~20m.
- **Probe:**
  - The run's jobs: `public-edge-liveness` success, `request-logs-liveness` success, `tenant-view-liveness` failure.
  - Its log reads `==> 4/4 events: the newest event must be within 3600s (budget 120s)`, then immediately `FAIL(4/4 events): GET /v1/services/srv-dbkq3hdhhjfs73eiahe0/events failed`, then the issue step with `(exit 6)`.
  - Re-probe as the QA user right after: `GET /v1/services/srv-dbkq3hdhhjfs73eiahe0/events?startTime=<now-1h|2h|24h>&limit=20` answers **200** in 291–328 ms. Each answer is `[]`, correctly: the canary's last events are the 2026-11-16 deploy, and it has not slept since, see [w4/676](blocked/676.md).
- **Cause:**
  - `scripts/tenant-view-liveness.sh:286-292`: `fetch_events` runs `acurl … 2>/dev/null` and, if curl itself fails, prints `FAIL(4/4 events): … failed` and **`exit 6`**.
  - `acurl` (`scripts/lib/canary-api.sh:88-90`) is `curl -sS -K … --connect-timeout 5 --max-time 60` with no `-f`, so only a transport error (connect or read timeout, reset, DNS) reaches that branch. The `2>/dev/null` also drops curl's own error text.
  - `poll_events` (`:296-304`) calls `fetch_events` on every tick, so a single blip anywhere in the 120 s budget ends the run.
  - Stages 2 and 3 treat the same failure as "not yet" and keep polling inside their budgets. Stage 2 does this at `:180-198` (`if acurl …; then … fi` inside `while [ "$waited" -lt "$LOG_BUDGET" ]`), and stage 3 the same way around `:249`.
  - The workflow maps exit 6 to `4/4 events (the feed did not advance)` (`.github/workflows/ssh-edge-liveness.yml:431`). Three real stall paths use the same code: `:376` (the wake's `service_woken` never arrived), `:399` (no event in the window) and `:411` (the newest event is too old).
- **Fix:**
  - Target behavior: a transport error on the events read is retried inside the stage's budget, as stages 2 and 3 do. `fetch_events` returns non-zero instead of exiting, and `poll_events` treats that as an empty tick.
  - Only a read that never succeeds within the budget fails the stage, under its own label. Give it a distinct exit code, for example `8` mapped to `4/4 events (the events read never answered)`, and print curl's error by capturing stderr instead of discarding it.
  - Exit 6 stays reserved for a feed that answered and did not advance.
  - Tests: extend the script's fixture tests (if any; otherwise a small bats-style harness with a stub `acurl`) so that one failed read followed by a good read passes, an always-failing read exits 8, and a stalled feed still exits 6.
- **Blast radius:** `fetch_events` has one caller, `poll_events`, which both stage-4 paths use: the `service_woken` path at `:364` and the newest-event path at `:383`. `acurl` is shared with stages 2 and 3, which already tolerate failures, so it should stay as it is.
- **Unverified:** the transport error's exact kind. The script discards curl's stderr, which is part of the fix.
- **Render:** n/a (bex's own monitor).
- **Done when:** a stubbed single read failure no longer fails the run, an always-failing read exits 8 with its own label and curl's error text, and the workflow's stage map names code 8.
