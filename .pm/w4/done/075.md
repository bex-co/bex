## Four transitions, each producing a new pod and the right value

The service was created with **no** `WHOAMI_NAME` of its own, so every observation below is attributable to the group or to the override, never to leftover service state.

| # | action | `curl https://qa-20260913-eg.onbex.co/` → `Name:` line | deploy |
| --- | --- | --- | --- |
| 0 | baseline, group not linked | **absent** | `create` → live |
| 1 | `linkEnvGroup(id, serviceId)` | `from-env-group` within 60s | `config_change` |
| 2 | `PUT …/env-vars/WHOAMI_NAME = service-level-value` | `service-level-value` within 75s | `config_change` |
| 3 | `DELETE …/env-vars/WHOAMI_NAME` | back to `from-env-group` within 75s | `config_change` |
| 4 | `unlinkEnvGroup(id, serviceId)` | **absent** again within 75s | `config_change` |

Each step rolled a new pod (hostnames `7f857c766f-558nq` → … → `f47d55b69-rbmw6`), so the value genuinely came from a fresh container environment rather than a cached page.

**Step 2/3 is the interesting pair: a service-level variable overrides the linked group's, and removing the override restores the group's value** — precedence is evaluated live, not frozen at link time. That matches Render's documented behavior (service env vars win over env-group vars), so it is parity-correct as well as internally sensible.

**Step 4 matters most, because removal paths are where this class usually breaks:** unlinking did not merely drop the association, it removed the variable from the running process.

## The surrounding surfaces are honest too

- **GraphQL** `envGroup(id:)` reports `serviceLinks: ["srv-dajkqh0gsm7s73f640fg"]` while linked, and the list read masks the value (`envVars: [{key:"WHOAMI_NAME", value:""}]`) — the same secret hygiene the service-level env vars and secret files show (pass 18).
- **The service's Environment page** renders `Linked Environment Groups → Linked (1) → qa-20260913-group → WHOAMI_NAME → Unlink`, so it names the key you are inheriting, not just the group. Its counterpart empty state read `Available to link (0) — Every workspace environment group is already linked.`, which was **accurate**: that group was the workspace's only one.
- Both `linkEnvGroup` and `unlinkEnvGroup` return a bare `Boolean` (`true`), not a domain object — worth knowing before writing a mutation against them, and the reason my first two attempts errored with `must not have a sub selection`.

## Two schema shapes that cost me a round trip each, noted for the next person

Neither is a defect; both are just non-obvious from the verb name:

- `createEnvGroup(envVars:)` takes **`[EnvGroupVarInput!]`**, not the `[EnvVarInput!]` the service-level env-var mutations use.
- `EnvGroup.serviceLinks` is **`[String]`** (bare ids), not an object list — `serviceLinks { id name }` is a schema error.
