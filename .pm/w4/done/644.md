# 644 — A replaced instance keeps drawing its last memory reading for five minutes after it stopped, so the Memory chart, its Max/Avg aggregates and their headline describe a pod that is gone

Why: after every deploy or restart, the Metrics page's Memory chart keeps the old instance's line flat at its last value for about five minutes. Its **Max** and **Avg** replica aggregates, and the headline percentage beside the chart, include that line. A service that just shed 48 MiB still reads 48 MiB at Max for five minutes. CPU and **Total Instances** on the same page drop the old pod within about 90 s, so the charts disagree with each other and with the header's `Instances 1`.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 328, 2026-11-13 22:13–22:32 UTC (`muse.env`, workspace `bex-canary`; pin `1c4d721bc8dc`). **Minor** (a misleading chart for five minutes after each rollout; nothing is lost). ~45m.
- **Fixture:** Free web service `qa-20261113-r328-logs` (`srv-dbrod15gh3vs73b152fg`), `docker.io/library/busybox:1.37`. Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe (REST, then the dashboard):**

  2. `PATCH` the command back to `sh -c 'echo ok > /tmp/index.html; exec httpd -f -p $PORT -h /tmp'`, then `POST …/deploys`. B (`…-g5jlin2ha0sitkslr3pp`) went `live` at 22:17:23 using 0.4 MiB, and `GET …/instances` listed only B.
  3. A stopped reporting at about 22:18:30. Its CPU series ends at 22:18:30, and `instance-count` reads 1 from 22:20:00.
  4. `GET /v1/metrics/memory?resource=…&startTime=…22:12:00Z&resolutionSeconds=30` still returned A, flat at 48.5 MiB, through **22:23:00**. The instance before A (`…-7mbuf…`) did the same, ending at 22:19:30 after its CPU ended at 22:15:30.
  5. With `aggregateAllMethod=MAX`, every point from 22:17 to 22:21 read 48.5 MiB. With `AVG`, the points from 22:20 to 22:21 read 24.4 MiB, the mean of A's stale 48.5 and B's 0.4.
  6. Replayed at 22:25–22:31 in the dashboard (`/services/{id}/metrics?range=1h`, Memory, **Max**). The heavy instance (`…-h5mnl…`) stopped at about 22:28:00 (CPU end; count 1 from 22:29:30).   7. **Same cause, second symptom:** at 22:31:53, `…&endTime=2026-11-13T22:40:00Z` returned memory points for the live instance up to **22:36:30**, five minutes in the future. CPU ended at 22:32:00 and `instance-count` at 22:33:00.
- **Root cause:**
  - `resourceUsageQuery` (`lego/backend/internal/metrics/source.go:333-349`) reads memory with an instant selector: `sum by (pod) (max by (pod, container) (container_memory_working_set_bytes{…}))` (`:348`).
  - At each range step, an instant selector returns a series' last sample if it is up to five minutes old (Prometheus's default lookback). A series stops inside that window only when it gets a staleness marker.
  - The `kubernetes-cadvisor` job (`deploy/gitops/base/prometheus.yaml:468-491`) scrapes cAdvisor samples that carry their own timestamps. Prometheus writes no staleness markers for those unless the job sets `track_timestamps_staleness`, and this job does not. w5/m111 measured the same thing for billing (`.pm/w5/done/m111/done/t001.md:16`).
  - So a stopped pod's memory line runs on for up to five minutes, and a range ending in the future gets five minutes of invented points.
  - CPU does not, because `rate(…[Ns])` is a range selector with no lookback. The instance count does not either, because w4/m110 t002 gated it with `count_over_time(…[instanceLivenessWindow])` (`source.go:304-320`, window `90s` at `:277`). That task's note (`.pm/w4/done/m110/done/t002.md:36`) judged memory's stale points to "merely extend a line". The MIN/MAX/AVG replica aggregates (`aggregateReplicasAtTimestamps`, `select.go:138`, applied at `:226-227`) fold those points into a wrong value, and the headline reports it.
- **Fix (target behavior):** a memory series ends within one liveness window of its pod's last real sample, as the instance count does, and no read returns a point after the request time.
  - Read memory as `last_over_time(container_memory_working_set_bytes{…}[instanceLivenessWindow])` inside the same `max by (pod, container)` / `sum by (pod)` reduction. A range selector has no lookback, and sharing the 90 s window keeps the memory lines and Total Instances in step.
  - Bound the Prometheus range end at now for cpu, memory and instance count. Logs already bound it (`lokiRange`, `lego/backend/internal/logs/loki.go:364`: `earlier(q.End, now.Add(lokiFutureGrace))`).
  - Optional platform follow-up, not required: `track_timestamps_staleness: true` on the cAdvisor job (needs Prometheus ≥ 2.48), which w5/m111 t002 (`.pm/w5/done/m111/done/t002.md:19`) noted "also fixes the Metrics page". Keep the PromQL fix anyway, so the chart does not depend on scrape config, which is m111's reason for its billing choice.
- **Blast radius:**
  - `resourceUsageQuery` has 3 callers: service cpu/memory (`source.go:302`), the default branch (`:322`) and datastore cpu/memory (`promDatastoreResourceQuery`, `:747`). Only the memory branch changes.
  - Datastore pods keep their names across a restart (`<cluster>-1`, `<kv>-0`), so `max by (pod, container)` there takes the larger of the old container's stale value and the new one's for five minutes. That was reasoned, not probed.
  - `range_test.go:185` pins the memory PromQL string (1 test). Add a fixture test: a pod whose samples stop at t has no point after t + 90 s, and a live pod's values are unchanged.
  - Billing (`usage/service.go:1388`) is already liveness-gated (w5/m111) and is unaffected.
