# 375 — A new Key Value's breadcrumb omits its Project and Environment until a reload

Why: right after creating a Key Value into a project environment, its page's breadcrumb reads only `Key Value › <name>`, with no Project › Environment trail and no switchers. It stays that way indefinitely (71 s observed), although every API surface already reports the placement.

**Severity:** minor. **Estimate:** ~40m. **Source:** live `/qa-find-bugs w4` loop run c7a1, 2026-10-20 UTC, `muse.env`, workspace `bex-canary`. Both owned stores and the project were deleted in-run; the session was revoked. Evidence: `.playwright-mcp/qa-kv-c7a1-breadcrumb-after-create.png` (local).

## Probe (reproduced twice)

1. Fresh document load of `/keyvalue/new`. Name `qa-20261020-c7a1-kv2`, Free, Project `qa-20261020-c7a1-proj`, Environment `Staging`. **Create Key Value Instance** navigates in-app to `/keyvalue/red-dbbgc8b581vs73bjhi0g`.
2. The breadcrumb `<nav>` text was sampled every 5 s from the create click:

   ```
   6s–36s [Creating]: Key Value › qa-20261020-c7a1-kv2
   41s–71s [Available]: Key Value › qa-20261020-c7a1-kv2
   GET /v1/key-value/red-dbbgc8b581vs73bjhi0g -> {"projectId":"prj-dbbfu9r581vs73bjhh60","environmentId":"evm-dbbg6t99a20c7385ra70","status":"available"}
   ```

3. A reload shows `qa-20261020-c7a1-proj › Staging › qa-20261020-c7a1-kv2`. The first store (`red-dbbga399a20c7385rab0`) behaved the same way.
4. Control: moving that store Staging → Production from the project page, then opening it in-app, showed `… › Production › …` at once. The project page polls Projects/Environments, which refreshed the shared cache.

## Root cause

- `DatastoreBreadcrumbs` (`dashboard/src/common/components/dashboard-layout/dashboard-breadcrumbs.tsx:205-230`) finds the store's project by membership. It searches `useProjects({ poll: false })` for `keyValueIds`/`databaseIds`, then searches environments the same way.
- `useProjects` reads `PRIMED_FETCH_POLICY` = `cache-first` (`dashboard/src/common/lib/fetch-policy.ts:15`) with polling off. A Projects list cached before the create therefore never learns the new id. `use-create-key-value.ts` refetches nothing.
- The store's own detail queries omit its placement: `query KeyValue` (`dashboard/src/features/keyvalue/api/keyvalue.graphql:30`) and `query Database` (`dashboard/src/features/databases/api/databases.graphql:30`). The GraphQL type has `projectId`/`environmentId`; the create mutations select them (`keyvalue.graphql:147-148`, `databases.graphql:277-278`). This is exactly what `w4/144`'s filing recommended reading.
- `ServiceBreadcrumbs` (`:78-95`) uses the same membership-in-a-non-polling-list derivation. It was correct after a service create this run for an **untraced** reason (some mounted reader refreshed Projects). It is the same class and must not be treated as a passing control.

## Fix (target behavior)

- Each detail breadcrumb takes its project and environment from the resource's own `projectId`/`environmentId`: add them to the `KeyValue` and `Database` detail queries; the `Server` query already carries `environmentId`. The Projects/Environments lists supply only labels and switcher options.
- Pre-settle state: while a label lookup for a known id is pending, render a neutral skeleton crumb. Never fall back to the ungrouped `Key Value`/`Database` crumb for a store whose own read says it is placed. The ungrouped crumb is only for `projectId == null`.

## Acceptance

- Replay the probe: within one detail poll after create (and immediately after a fresh load), the breadcrumb reads `<project> › <environment> › <name>` with no reload, for a Free Key Value. Check Postgres too if the workspace's Free Postgres slot is available (this run's was occupied).
- Component tests cover a stale Projects cache that omits the id while the detail read carries `projectId`/`environmentId`. They must fail on today's code. Also cover the ungrouped and pending cases.
- Dashboard `yarn lint` and `yarn test` pass.
