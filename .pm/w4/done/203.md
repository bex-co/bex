# Trigger Run stays enabled on a suspended cron job and fails with a raw English error

Why: the backend already answers `cron_run_now` with `precondition: "suspended"`, and the dashboard has localized copy for it, but the Recent Runs card ignores the projection. Users get a confirm dialog and then a raw `cron job "srv-…" is suspended` line, untranslated and showing an internal id.

- **Severity:** minor (UI lies about an available action; nothing runs).
- **Repro (loop41, 2026-10-05, pin `c7afefad5`):** owned Free cron `qa-20261005-l41-cron` (`srv-db1p0fu7q7bs739ppbng`, `alpine:3`, deleted afterwards). `POST /v1/services/<id>/suspend` → 202 (header shows **Suspended**). Then:
  - REST `POST /v1/cron-jobs/<id>/runs` → **409** `{"code":"CRON_SUSPENDED","message":"cron job \"srv-db1p0fu7q7bs739ppbng\" is suspended"}`. Correct.
  - GraphQL `serverActions(id:"srv-db1p0fu7q7bs739ppbng", ownerId:"tea-daif693dqjvc73e7as3g")` → `{"action":"cron_run_now","outcome":"allowed","precondition":"suspended"}`. Correct: the server says it is blocked.
  - Dashboard Events page, Recent Runs card: **Trigger Run** enabled (`isDisabled() === false`, no title or reason). Clicking it opens "Trigger a run now?". Confirming closes the dialog with no toast, and the card then shows inline `cron job "srv-db1p0fu7q7bs739ppbng" is suspended`.
- **Expected:** the button reads the `cron_run_now` decision like Manual Deploy and Suspend do. While suspended it is disabled with `capabilities.blockedSuspended` ("Unavailable while the service is suspended. Resume it first.", en + zh). A server refusal that still slips through renders localized copy by error `code`, never the raw message.
- **Root cause:** `dashboard/src/features/services/components/cron-runs-section.tsx:120-136` gates the button only on `triggering` and never calls `useServerActions` (`dashboard/src/features/capabilities/hooks/use-resource-actions.ts:126-130`). Its only consumers are `service-row-actions.tsx:119` and `suspend-service-card.tsx:60`. `dashboard/src/features/services/hooks/use-cron-runs.ts:281-287` puts `e.message` into `triggerError` verbatim. The server side is already right: `lego/backend/internal/apps/service.go:3398-3403` (`CRON_SUSPENDED`) and the w4/132 projection.
- **Fix:** dashboard only. Consume `useServerActions(serviceId)` in `CronRunsSection` for `cron_run_now` (disable plus reason via the existing capabilities blocked-reason mapping). Do the same for the row-level cancel with `cron_cancel_run` / `no_active_run`. Keep the m114 t003 rule: an active run is **not** a blocker, because the server preempts and the projection does not report `no_active_run` for `cron_run_now`. Map `CRON_SUSPENDED` (and the active-run code) to translated text in `use-cron-runs.ts`; fall back to `services.cronTriggerError`.
- **Blast radius:** the `CronRunsSection` trigger and its cancel action. REST/GraphQL/MCP are unchanged and already consistent.
- **Adjacent classes:** billing-blocked (`billing_blocked`) and protected-confirmation preconditions should flow through the same mapping. Unauthenticated/forbidden stay with the existing capability gates.
- **Unverified:** the zh rendering; billing-blocked workspaces.
- **Render:** the run-now action is unavailable on a suspended cron job.
- **Estimate:** ~45m.

**Done 2026-10-08:** `CronRunsSection` reads `useServerActions` and gates Trigger Run on `cron_run_now` and each run's Cancel on `cron_cancel_run` through the shared `gateAction`/`gateReason` mapping (disabled + `PermissionTooltip` reason, e.g. `capabilities.blockedSuspended`; an active run is still not a blocker, per w4/m114 t003). `useCronRuns.trigger` renders `CRON_SUSPENDED` as `capabilities.blockedSuspended` and other refusals through `mutationErrorMessage` (generic copy for non-GraphQL failures). Component tests cover the suspended trigger and the no-active-run cancel; hook test covers the coded refusal; dashboard services suite (879) + `yarn lint` green. zh rendering and billing-blocked workspaces unverified live (both flow through the same mapping).
