## Objective

Connecting a repo+branch that a blueprint in this workspace already tracks must not report a successful create while replacing that blueprint's name, path and manifest. Refuse it with the coded conflict + server-issued confirmation phrase the product already uses for resource takeover, and only proceed when the caller confirms.

## Context

### The live capture (2026-09-21, production, workspace `bex` / `tea-d98210cbbpdc73dcrkvg`)

Two creates, same repo, same branch, different manifest paths:

```graphql
# 1
mutation { createBlueprint(ownerId:"tea-…", repo:"https://github.com/bex-co/bex", branch:"main",
                           path:"examples/static-site/render.yaml", name:"qa-20260921-bpA") { id name path resources { id name type } } }
→ { "id":"blp-dan9g8rs0ils73bgp500", "name":"qa-20260921-bpA",
    "path":"examples/static-site/render.yaml",
    "resources":[{"id":"srv-daohokp2dbts73fi2nh0","name":"static-site","type":"static_site"}] }

# 2 — different path, no confirm, no warning
mutation { createBlueprint(ownerId:"tea-…", repo:"https://github.com/bex-co/bex", branch:"main",
                           path:"examples/cron-demo/render.yaml", name:"qa-20260921-bpB") { id name path resources { id name type } } }
→ { "id":"blp-dan9g8rs0ils73bgp500",          ← the SAME id
    "name":"qa-20260921-bpB",
    "path":"examples/cron-demo/render.yaml",
    "resources":[{"id":"srv-daohon92dbts73fi2njg","name":"cron-demo","type":"cron_job"}] }
```

Afterwards, on both GraphQL and REST `GET /v1/blueprints`, the workspace has **one** blueprint for that repo — named `qa-20260921-bpB`, carrying `examples/cron-demo/render.yaml` and that file's manifest. `qa-20260921-bpA` does not exist anywhere: not in the list, not by id (its id is now B's). `static-site` is still Running (`GET /v1/services/srv-daohokp2dbts73fi2nh0` → `"phase":"Running"`, `"url":"https://static-site.onbex.co"`), managed by nothing.

The caller asked to create a blueprint. What happened was: a different blueprint was destroyed, and its stack orphaned.

### Mechanism

`lego/backend/internal/store/blueprint_lifecycle.go:186-201` — `AdmitBlueprintCreate`:

```sql
INSERT INTO blueprints (…) VALUES (…, 'syncing', 1, $9)
ON CONFLICT (tenant_id, repo, branch) DO UPDATE SET
    name  = EXCLUDED.name,
    path  = EXCLUDED.path,
    auto_sync = EXCLUDED.auto_sync,
    manifest  = EXCLUDED.manifest,
    status = 'syncing', execution_generation = blueprints.execution_generation + 1, …
WHERE blueprints.active_run_id IS NULL
```

The conflict arm is a full overwrite. `lego/backend/internal/apps/blueprint.go:689-763` (`CreateBlueprint`) calls it with `AutoSync: true` and never asks whether the row exists — the only guards before it are payment method and the action plan. The `WHERE blueprints.active_run_id IS NULL` clause makes a *concurrent* overwrite fail with `BLUEPRINT_SYNC_BUSY`; a sequential one succeeds.

The unique key is `UNIQUE (tenant_id, repo, branch)` — `lego/backend/internal/store/migrations/0016_blueprints.up.sql:14`. Note `path` is **not** in it.

### Why this is a gap and not a design question

One blueprint per repo+branch per workspace is settled: the migration header says "a workspace-scoped repo+branch+manifest record", and `w8/m21` made **branch** the read-only identity key on the detail page with name and path editable. So the fix is not "add path to the key". The fix is that the product must say what it is doing.

The comparison that makes this sharp is `w8/m23`, which is **done** and titled _"Blueprint resource ownership: stop silent cross-blueprint overwrite"_. Its whole premise — recorded in ADR018 as a deliberate divergence — is that bex refuses instead of clobbering where Render clobbers. `lego/backend/internal/apps/blueprint_ownership.go:44-49` already mints the phrase:

```go
func BlueprintTakeoverConfirmation(owningBlueprintID string) string {
	return "takeover blueprint " + owningBlueprintID
}
```

Everything needed exists: the coded error class (`BLUEPRINT_RESOURCE_CONFLICT`), the confirm round-trip on all three APIs, the preview surfacing, and the dashboard's confirm dialog. Only the blueprint row itself was left outside the guarantee.

Note the second create above slipped past the *resource* guard for an ordinary reason, not a bug in it: B declared only `cron-demo`, which nothing owned yet. The resource guard fires per declared resource; nothing guards the row.

### The UI actively invites the case

`/blueprints/new` is headed **"New Blueprint Instance"** and its path field reads: _"The path to the Blueprint file in your repo — any .yaml/.yml file works (e.g. `infra/bex/stack.yaml`). Defaults to render.yaml at the root of your repository."_ A monorepo user reads that as "one blueprint per manifest". The blueprints list has no Path column, so two such blueprints would be indistinguishable there even if they could coexist.

## Steps

1. In `CreateBlueprint`, before admission, look up the existing `(tenant, repo, branch)` row. If one exists and is not disconnected, return the coded conflict naming it and `BlueprintTakeoverConfirmation(<its id>)`, unless `req.Confirm` matches.
2. Decide and write down what a confirmed takeover means for the old blueprint's tracked resources — it must not silently orphan them either; the natural answer is to run the same release/transfer path t002 builds, and to record the takeover in sync history so the disappearance is auditable.
3. Surface the conflict in `blueprintPreview` (the same place the resource conflict already appears) so `/blueprints/new` shows it with Deploy disabled and offers the confirmation, reusing the existing dialog.
4. Keep `updateBlueprint(id, name, path, autoSync)` as the supported way to repoint an existing blueprint — the error message should name it, since that is what a user attempting a second connect usually wants.
5. Confirm the disconnected-row case still re-establishes cleanly: `blueprint.go:689`'s documented "a disconnected row is deliberately re-established under a fresh generation" must keep working (see `w4/120`, which is about that path's `createdAt`, not about refusing it).

## Files

- `lego/backend/internal/apps/blueprint.go` (`CreateBlueprint`, and the preview/validate path)
- `lego/backend/internal/apps/blueprint_ownership.go` (reuse the confirmation + conflict shape)
- `lego/backend/internal/store/blueprint_lifecycle.go` (`AdmitBlueprintCreate` — the conflict arm may need a create-vs-revive distinction)
- `dashboard/src/features/blueprints/` (`/blueprints/new` review section)

## Acceptance criteria

- [x] A second `createBlueprint` for a `(tenant, repo, branch)` already held by a live blueprint is refused with a coded conflict naming the existing blueprint and its confirmation phrase — same code and shape on REST, GraphQL and MCP.
- [x] After that refusal, `blueprints(ownerId:)` still shows the original blueprint with its original `name`, `path` and `manifest`.
- [x] `blueprintPreview` reports the conflict, and `/blueprints/new` renders it with Deploy disabled.
- [x] Passing the confirmation proceeds, and the sync history records that it took over a named blueprint.
- [x] Creating over a **disconnected** row still succeeds without a confirmation (unchanged `w8/m37` behavior).

## Out of scope

- Changing the uniqueness key to include `path` (multiple blueprints per repo+branch) — settled design, see Context.
- `createdAt` on a revived row — that is [`w4/120`](../120.md).
- Deleting orphaned resources — never; see `w4/119`.

## Outcome (2026-09-21)

CreateBlueprint refuses a create that would repoint a live blueprint with BLUEPRINT_CONNECTION_CONFLICT + the takeover phrase; confirmed replacement proceeds and is recorded on the sync run's new note column (migration 0131). Path, not name, decides what counts as a replacement — re-connecting the same path is also the retry path after a failed apply, which one confirm field could not otherwise resolve alongside a resource phrase. blueprintPreview takes an optional blueprintId so an existing blueprint does not conflict with itself.
