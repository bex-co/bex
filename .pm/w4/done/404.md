# 404 — INCIDENT: about half of production secret-store reads fail with "secret store not configured", and each failed create then blocks its service name for 12 minutes

Why: since roughly 06:10–06:51 UTC on 2026-10-24, about every second request that touches env vars or secret files fails. That covers the Environment tab, the env-var REST/GraphQL/MCP reads and writes, and any service create that carries env vars. The error tells the user the store is "not configured", and each failed create leaves the name unusable ("still being created or deleted; retry shortly") for 12 minutes, so retrying makes it worse. Running services are not affected; the operator reads Kubernetes Secrets.

**Severity:** major, close to a blocker (a core journey, create-with-env and env editing, fails half the time on production). **Estimate:** ops diagnosis unknown (needs cluster access); code fixes ~45m. **Source:** live `/qa-find-bugs w4` loop run j3n8, 2026-10-24 06:51–07:08 UTC (`muse.env`, `bex-canary`, pin `29d63e1f7bea`, no deploy completed since; run `40070503856` for `c5cd67329` still pending). Every probe used `qa-20261024-j3n8-*` names. The services that did get created (`srv-dbe5cvg3uhtc73e2h8u0`, `srv-dbe5hdgc4ppc73ep3tg0`) were deleted (`GET` → `404`); session revoked.

Every failure answered in 224–342 ms, so it is not a timeout. That points to one of two bex-api replicas (or one store backend) failing every read while the other succeeds.
- `POST /v1/services` (Free image service, `envVars:[{key:"HTTP_PORT",value:"10000"}]`):
  - `qa-20261024-j3n8-c` → `503 SECRETS_UNAVAILABLE`;
  - immediately after, `qa-20261024-j3n8-d` → `201`.
- Before the incident, env-var and secret-file reads and writes all succeeded: runs e9v4 ~05:40 UTC and s5f7 ~06:10 UTC.
- **Name held after a failed create:**
  - `qa-20261024-j3n8-job` failed at 06:51:2x UTC (`503`). Every create of that name then answered `409 {"error":"conflict: a service of this name is still being created or deleted; retry shortly"}`, through 07:00:22 (polled every 20 s, list `[]` throughout). At 07:05 the takeover window had passed, and the create reached the store again and got `503`.

## Root cause

1. **Production (unverified; needs cluster access).**
   - `readVersionedEnvMap` (`lego/backend/internal/secrets/service.go:368-375`) maps **any** `GetVersioned` error to `envSourceUnavailable()`.
   - The underlying OpenBao error is discarded, so the response cannot tell sealed, permission denied, expired token and network apart.
   - Neither recent gitops change plausibly explains it: `a612f9a68` (06:21 UTC) adds `openrouter.ai` to the agent egress admission policy; `c5cd67329` (06:30 UTC) bumps the kpack builder.
   - Check first: per-pod bex-api logs and OpenBao token/lease state for each replica (`kubectl -n bex-system get pods -l app=bex-api`, compare responses per pod), OpenBao seal/HA status, and whether one replica's token expired without renewing.
2. **The error lies about its cause.**
   - `core.ErrSecretsUnavailable` reads "secret store not configured" (`core/errors.go:82`). It is reused for read failures on a configured store.
   - The cause is not logged at the masking site either, so diagnosis needs pod-level debugging.
3. **A failed create strands its name.**
   - The create's compensation (`secrets/files.go:344-351`) calls `abortProjection` (`:442-447`). That runs `retireMap` (a store write) **before** `deleteSecret`.
   - With the store failing, `retireMap` errors and returns, so the ownerless claim Secret is never deleted.
   - `createPreparedSecret` (`:378-420`) then refuses every create of that name with `errSecretNameHeld` until `preparationWindow` (6 × `core.CreateSecretsTimeout` = 12 min, `projection.go:252-254`) lets `vacated` take it over (w5/135).

## Fix

- **Ops (now):** restore the failing replica's store access. Then re-run the 20-read probe and expect 20 × `200`.
- **Code:**
  - `abortProjection` deletes the claim Secret even when `retireMap` fails. Delete it first, or always, joining the errors. A store map left behind is harmless and gets retired by the next write.
  - A failed create must not make its own name answer "still being created" afterwards.
  - Split the error: keep `SECRETS_UNAVAILABLE` "secret store not configured" for `Store == nil`. Use a distinct message, e.g. `SECRETS_UNAVAILABLE` "the secret store could not be read; try again", for read/write failures, and log the wrapped cause (never values) at `readVersionedEnvMap` and its write twins.
  - Readiness: consider failing bex-api's readiness when its store client cannot read, so a broken replica leaves the Service instead of serving half the traffic.
- **Tests:**
  - A store that fails `retireMap` still leaves no claim Secret, and an immediate re-create of the name proceeds. Today it gets `409`.
  - A store read error yields the new message, and the cause is logged.

## Loopx w4 verdict (2026-10-25) — code done, ops gate remains

Code shipped: `abortProjection` always attempts both halves (errors joined), so a failing `retireMap` no longer strands the claim Secret — the w5/148 keep-the-Secret test was rewritten to this contract, and an immediate re-create of the name proceeds and replaces leftover maps wholesale. Store read/write failures now answer `SECRETS_UNAVAILABLE` "the secret store could not be read; try again" (still `errors.Is` → `ErrSecretsUnavailable`; the not-configured message stays for `Store == nil`), with the cause logged via `HideCause` at `readVersionedEnvMap`, `readMap`, `updateMapCAS` and the batch patch sites. The readiness-probe suggestion was considered and not taken: failing readiness on a transient store read would flap healthy replicas out of the Service.

**Blocked on ops (user/cluster access):** restore the failing replica's store access — per-pod bex-api logs, OpenBao seal/HA and token/lease state per replica (`kubectl -n bex-system get pods -l app=bex-api`) — then re-run the 20-read probe expecting 20 × `200`. Until that lands, roughly half of production secret-store reads may still fail.

**Ops half closed, loopx w4 (2026-10-29).** The likely mechanism is the one w4/m130 traced live today. Since 2.5, an OpenBao raft standby serves reads locally, and bex-api read through `openbao.secrets.svc`, which load-balances across all three pods. After the 2026-10-24 node roll, a standby that could not answer reads correctly would fail every read routed to it (about half, alternating) while writes, forwarded to the leader, kept working. It would then recover with no deploy, as observed. The 10-24 OpenBao logs have rotated, so this specific standby is not proven. The fix removes that failure path either way: bex-api now dials `openbao-active.secrets.svc:8200` (`479bd3fe2`, pinned by `gitops-validate`). Re-probe on production after the rollout: 20 × `GET /v1/services/{id}/env-vars` at 1 s spacing gave **20 × `200`**. The code half shipped 2026-10-25 (above).
