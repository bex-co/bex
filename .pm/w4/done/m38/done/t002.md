## Objective

Make `refreshToken` idempotent across bex-api replicas: two concurrent refreshes of the same token return the same pair and exactly one reaches Hydra, closing the revoke-each-other race.

## Context

- `lego/backend/internal/cliauth/service.go:211` `refreshToken` → `proxyForm` to Hydra. Traefik round-robins the CLI TUI's two concurrent refreshes onto **different replicas**, so an in-memory singleflight cannot dedupe them — the shared point must be Postgres.
- Mechanism (per `FUTURE-MAYBE.md:33`): take a `pg_advisory_xact_lock` keyed on the refresh-token hash, then inside the lock check the t001 idempotency store; serve the cached pair if present (≤ its short TTL), else proxy to Hydra once and persist the result before releasing.

## Steps

1. Hash the inbound refresh token; derive a stable 64-bit key for `pg_advisory_xact_lock` (e.g. first 8 bytes of the hash).
2. Within one transaction holding the advisory lock: look up t001's store; on hit return the cached pair; on miss call `proxyForm` to Hydra once, persist the pair keyed by hash, and return it.
3. Preserve the exact response body/status/error shape the CLI expects on both the deduped and fresh paths (byte-identical OAuth token response); a Hydra error is not cached.
4. Keep the existing rate limiter + body limit in front.

## Files

- `lego/backend/internal/cliauth/service.go`

## Acceptance criteria

- [ ] Two concurrent same-token refreshes yield one Hydra call and an identical pair to both callers.
- [ ] A distinct refresh token is unaffected (independent lock key).
- [ ] Upstream Hydra errors are surfaced unchanged and not cached.

## Out of scope

- The migration/store (t001); the Hydra client lifespan value (t003).
