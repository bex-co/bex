# 42 of 54 usage rows are for resources that no longer exist, and only 2 of them are marked deleted

Why: the Charges tree is where a workspace answers "what am I paying for", and four-fifths of its line items name resources that return `app not found` — presented not as deleted, but as bare ids indistinguishable from current ones.

Found by live `/qa-find-bugs` 2026-09-21 pass 152 (w4-targeted, `muse.env` credentials). Read-only; nothing was created.

## The counts

`usage(ownerId:)` for the current period returns **54** `services` rows. Classified against the workspace's live `services`/`databases`/`keyValues` lists:

| class                                                          | count |
| ---------------------------------------------------------------- | ------- |
| live resource, named                                            | 10    |
| gone, `deleted: true`, name retained                             | 2     |
| **gone, `deleted: false`, `serviceName: ""`**                    | **42** |

The 42 break down as 19 `service`, 16 `sandbox`, 4 `key_value`, 3 `postgres`.

Four were spot-checked individually and every one is gone:

```graphql
database(id:"dpg-daolmeh2dbts73fi2or0")  → app not found     # usage says deleted:false, name ""
keyValue(id:"red-daolmers0ils73bgphbg")  → app not found     # usage says deleted:false, name ""
service(id:"srv-dakvq2557grc738qmmh0")   → app not found     # usage says deleted:false, name ""
service(id:"srv-dalo003ssesc73e0la40")   → app not found     # usage says deleted:true,  name "qa-20260917-web"  ✅
```

The first two are this QA loop's own pass-143 fixtures, deleted about two hours before the read. So the missing tombstone is not an age effect — a resource deleted **today** lost its flag while two deleted on 2026-09-17 kept theirs.

## What a user sees

The dashboard is doing its part correctly, which is what isolates the defect to the API:

- It **falls back to the raw id** when `serviceName` is empty (`srv-dae9lb988i5c7399e9m0 $0.01`) rather than rendering an empty cell — the same deliberate fallback the audit-log `targetName` field documents.
- It **does** render the marker when the flag is set: `qa-20260917-web(deleted) $0.01`.

So the Charges → Services section lists 19 rows, of which 5 are current services with real names, 2 are correctly marked `(deleted)`, and **14 are bare ids of resources that no longer exist and carry no marker**. A reader cannot tell those 14 from a current service whose name simply failed to resolve.

## Why it is worth fixing even though the money is small

Every one of the 42 is charging **$0.00–$0.01**, so this is an attribution defect, not a billing defect — nobody is being overcharged. But the Charges tree is the one screen whose job is to make a bill legible, and four-fifths of its rows are unattributable. The two correctly-tombstoned rows prove the intended presentation already exists; the rest simply do not reach it.

## Fix

Find why the tombstone (the `deleted` flag plus the retained display name) is present for some deleted resources and absent for others — the two populations are the whole clue, and a resource deleted today landing in the wrong one rules out a retention window. Candidates worth checking first: whether the name/flag come from a join that a hard-delete breaks, and whether `sandbox` rows (16 of the 42, UUID-keyed rather than `srv-`/`dpg-`/`red-`) have a tombstone concept at all.

Estimate: ~40m once the split is understood; the presentation half already works.

## Closed 2026-09-22

The split had one cause, and it is the coupling the note suspected: `Deleted` was set **only inside the branch that found a retained name** (`usage/service.go`, `resolveServiceNames`). Names are captured opportunistically **by the usage read itself** — "the one place every metered resource is enumerated" — so a resource created and deleted between two usage reads is never captured, and then fails both halves at once: no live resource, no retained name, therefore `serviceName: ""` **and** `deleted: false`. The two rows that kept their tombstone are simply the two that a usage read happened to observe while they were alive. That is exactly why a resource deleted today landed in the wrong population while two deleted on 2026-09-17 did not — it is a capture-timing effect, not a retention window.

The fix resolves the name and the flag **independently**. A usage row is itself proof the resource existed, so absence from a live enumeration is the tombstone; the name is a separate best-effort lookup that may legitimately come back empty, which presenters already handle by falling back to the id.

Deletion is only ever claimed from an enumeration that actually answered:

- **service** — `ListApps`; a failed listing claims nothing.
- **postgres / key_value** — the Database/KeyValue CRs, and only when a Kubernetes client is wired. `listDatastores` answers `(nil, nil)` with no client, which is an unwired store rather than an empty cluster, and must not read as "everything is deleted".
- **sandbox** — the note's open question ("do sandbox rows have a tombstone concept at all") turned out to have a **second defect** behind it. `SandboxLabels` resolves labels for **reaped** sandboxes on purpose — its own doc comment says so — so the old code putting those labels into the live set meant a terminated sandbox with an owning agent session read `deleted: false` **with a name**, indistinguishable from a running one. A label is evidence of ownership, never of liveness. Liveness now comes from the compute meter's own per-sandbox phase cursor (`sandbox_meter_states`, migration 0061) via a new `store.LiveSandboxes`, which gives three answers rather than two: running, terminated, and never-metered. Only the middle one is a tombstone.

The capture write is also narrowed to resources still standing, so a dead sandbox's session label no longer keeps rewriting the retained record long after the sandbox is gone.

All three adapters funnel through `monthToDateAt`, so REST and MCP are fixed with GraphQL — closing the note's "whether REST and MCP report the same 42 rows was not checked" as fixed-for-all rather than checked-for-one; `TestRetainedNamesAgreeAcrossAdapters` holds the three surfaces to identical name-and-flag output.

Coverage:

- `TestShortLivedResourceIsTombstonedWithoutARetainedName` — the note's case directly, across service, postgres and key_value: metered, never captured, gone, and now marked deleted while still billing under a bare id.
- `TestFailedEnumerationNeverTombstones` — a failing `ListApps` and an absent Kubernetes client claim nothing, so a transient outage cannot mass-tombstone a healthy workspace.
- `TestSandboxRowsAreLabelledNotBareUUIDs` — extended with the case the session label used to hide: a **reaped** sandbox that still resolves a label is now labelled *and* marked deleted.
- `TestDeletedResourceKeepsItsRetainedName` — updated to the corrected semantics; its `srv-never-named` row asserted `deleted: false`, which was this defect written down as an expectation.
- `TestLiveSandboxesPG` — the new store query, including the never-metered absence and workspace isolation (skips without `BEX_TEST_DB_URI`).

Full `go test ./...` green in `lego/backend`. No dashboard change: the note verified the presentation half already renders `(deleted)` when the flag is set and falls back to the id when the name is empty, which is precisely the pair this now produces.

**Not addressed, deliberately:** the missing *names* on those rows. Recovering them needs a capture point earlier than the usage read (a create/delete hook in four packages), which the resolver's doc comment rejects by design. The rows now say "deleted" and bill under their id, which is the legible outcome the note asked for; a name for a resource bex never observed alive is not recoverable after the fact.

The note's "Explicitly NOT this note" (estimate-vs-rated skew) and its "Unverified" future-period clamp are untouched, as it directed.
