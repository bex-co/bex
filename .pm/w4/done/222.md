# 222 — Revealed datastore connection panels retain external URLs after access is disabled
Why: after disabling external access, users can still copy the old external URL from Connections even though the database is private and the URL no longer connects.

**Severity:** minor. **Estimate:** 55m. Found in the user-requested production `$qa-find-bugs` loop, 2026-10-08 (America/Los_Angeles), sweep 5; credentials consumed privately from `muse.env`. Filing only.

## Repro and target

On an owned Free Postgres or Key Value instance:

1. Add source-specific IPv4 and IPv6 rules through Networking and save. Wait for Available and verify an authenticated external connection.
2. Reveal connection info. Leave Connections revealed, remove both source rules, and save the empty allowlist.
3. Observe **Public access: No**. After the raw API reaches `available`, `public:false`, `externalHost:""`, and `externalConnectionString:""`, Connections still has one external URL copy button. Key Value was repeated from a fresh reload; Postgres was independently reproduced after entering its detail page anew.
4. Key Value's retained copy actually put a `rediss` URL for `red-db44qrpgovas7388men0.kv.bex.co` on the clipboard (password presence checked as a boolean; value never recorded). Fresh external handshakes were refused after clear. A later capability refresh remasked the panel. Fresh private Reveal returned internal info with no external URL/copy row for both resource types.

**Target:** when a confirmed saved public-access change arrives, immediately remask the already revealed Connections snapshot. Require another deliberate Reveal; when private and converged, it must show current internal connection information without an external URL or an old external CLI/CA target. Preserve the backend's successful access closure. No eager credential query.

This is temporary UI staleness, with no measured maximum duration. The initial Key Value probe at 298ms was still `config_restart` and correctly returned a credential-convergence conflict; the settled probe below also found the old copy button. Do not treat ordinary status/host propagation delay in Metadata as another defect.

## Traced cause and bounded repair

- Key Value `dashboard/src/features/keyvalue/hooks/use-connection-info.ts:24`: `info` is local state; lines 31–41 clear only on access generation, resource ID, or loss of sensitive permission. Lines 48–59 copy a one-time `client.query` result into that state. Postgres has the independently traced same mechanism at `dashboard/src/features/databases/hooks/use-connection-info.ts:27` (resets 34–44, response copy 58–64). Neither hook receives publication intent.
- Consumers `dashboard/src/features/keyvalue/components/connection-info-panel.tsx:92` and `dashboard/src/features/databases/components/connection-info-panel.tsx:91` decide whether to render the external copy row from that retained string. CLI command and Postgres CA instructions also derive from the retained snapshot.
- Mounts `dashboard/src/routes/keyvalue.$keyValueId.tsx:231` and `dashboard/src/routes/databases.$databaseId.tsx:260` pass only the immutable ID. Their detail models already expose `public:boolean` (`keyvalue/types.ts:26`, `databases/types.ts:25`). The two allowlist mutations return resource ID, typename and the saved public boolean; their networking hooks save/refetch without invalidating Connections. The parent detail queries observe the normalized resource.
- Actual installed Apollo **4.1.3** was read: `dashboard/node_modules/@apollo/client/core/ApolloClient.js:230` delegates `query`; `core/QueryManager.js:319` returns a single fetch Promise; `network-only` uses the link at 1083. This local React snapshot is not a watched connection-info query. A cache eviction or fetch-policy substitution alone does not clear it.
- Backend producers are healthy once converged: `lego/backend/internal/keyvalue/service.go:946` freshly authorizes, rejects credentials still converging, and builds the external URL from observed external host. `lego/backend/internal/postgres/service.go:802` freshly authorizes, obtains CA for public intent, and builds external strings from observed host. The narrow settled probes returned empty external strings. Keep authorization and TLS behavior.
- Later automatic remasking is consistent with `dashboard/src/features/capabilities/context/capabilities-provider.tsx:110` and 249–325: capability freshness expires, polling/focus refresh can clear eligibility, and the existing connection hooks reset on that change. Keep this protection.

Implement a bounded publication context at **both** mounts, for example a remount key containing resource ID and the authoritative public boolean. Discard the old snapshot and any late old Reveal response when that context changes. Verify the mutation's normalized write drives the parent context immediately; if it does not, propagate the confirmed result explicitly rather than waiting for a poll. A same-ID rename or status poll should not gratuitously remask. Do not introduce a new abstraction for these two tiny mounts.

Before a save is confirmed, keep the valid current context; rejected saves retain it. Once confirmed, show the masked panel before operator convergence or the next Reveal settles. Preserve the existing loading/error behavior for unprovisioned, unavailable, convergence-conflict, unauthenticated, forbidden and timeout results; do not convert those into empty successful credentials or weaken the permission gate. Resource deletion retains its existing not-found behavior.
