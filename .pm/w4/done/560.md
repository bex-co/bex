# 560 — A Deploy-to-bex link without `/tree/<branch>` fills Branch with a hard-coded `main`, so a public repo whose default branch is `master` opens on "Branch main does not exist", while typing the same URL resolves the default branch

Why: the one-click Deploy button is meant to deploy the repository's default branch, as on Render. For any public repo whose default isn't `main`, the first thing the visitor sees is a branch error and a disabled Deploy Blueprint button.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 56, 2026-11-11 00:31–00:45 UTC (`muse.env`, workspace `bex-canary`, pin `a0d5802594e9`). **Minor**: the one-click flow fails until the user retypes the branch; the error itself is honest. ~25m.
- **Fixture:** none created; previews only.
- **Probe:**
  - **The link guesses `main`.** `https://dashboard.bex.co/deploy?repo=https://github.com/octocat/Hello-World` redirects to `/blueprints/new?repo=https%3A%2F%2Fgithub.com%2Foctocat%2FHello-World`. 15 s later the page still shows:
    - `combobox "Branch": main`;
    - `alert: Branch not found Branch main does not exist in this repository.`;
    - `button "Deploy Blueprint" [disabled]`.
  - **Same in zh.** `/blueprints/new?repo=…&lang=zh` shows `combobox "分支": main` and `alert: 未找到分支 该仓库中不存在分支 main。`.
  - **The branch list is empty for public repos.** GraphQL `repoBranches(repo:"https://github.com/octocat/Hello-World", ownerId:"tea-daif693dqjvc73e7as3g")` returns `{"data":{"repoBranches":[]}}`. `https://github.com/render-examples/express-hello-world` also returns `[]`. Neither repo is in the workspace's GitHub App.
- **Controls:**
  - **Typing the URL resolves the default branch.** In `/blueprints/new`, on the Public Git URL tab, I typed `https://github.com/octocat/Hello-World` with Branch empty. 10 s later the field read `combobox "Branch": master`, with the honest `alert: Blueprint file not found render.yaml does not exist on branch master`.
  - **An explicit branch works.** `/deploy?repo=https://github.com/octocat/Hello-World/tree/master` fills Branch with `master` and shows the same honest alert.
  - **A `main`-default repo works by coincidence.** `/deploy?repo=https://github.com/render-examples/express-hello-world/tree/main` fills Branch with `main` and previews "Blueprint file parsed successfully — 1 resource will change. Create express-hello-world Service". That repo's default branch happens to be `main`.
  - **Other errors are honest.** `path=infra/nope.yaml` shows "Blueprint file not found"; a nonexistent repo shows "Repository not found".
- **Root cause:**
  - **The route hard-codes the guess.** `dashboard/src/routes/blueprints.new.tsx:85-90` seeds `branch` with `linked.branch ?? linkSearch.branch ?? "main"` and marks it `branchGuessed`.
  - **The only correction never runs for public repos.** It is at `:139-148` and fires "once, when the branch list first loads". The list comes from `useRepoBranches` (`dashboard/src/features/services/hooks/use-repo-branches.ts`), a query that only covers repos in the workspace's GitHub App. The hook itself says it "returns an empty list … for … no GitHub App connection". So for any public repo outside the App, the list stays `[]` and the guess is never corrected.
  - **The correction's own pick is wrong too.** Even when the list loads, it chooses `master` if present, else `branches[0]`. Neither is necessarily the default branch.
  - **The path that does find the default never fires.** In w4/532's path (`:150-163`), a Public Git URL previewed with Branch empty names `preview.branch`, and the page fills it into the field once per repo. Here Branch is `main` from mount, so the preview never runs with an empty branch.
  - **The parser is not at fault.** `parseDeployRepo` (`dashboard/src/features/blueprints/lib/deploy-link.ts`) leaves `branch` undefined when the URL has no `/tree/`. The guess is added only in the route.
  - **The original target named the right rule.** w8/163 (done) said "The branch is the default unless `repo` ends with `/tree/<branch>`", matching Render's [Deploy to Render](https://render.com/docs/deploy-to-render) docs.
  - **The test that should catch this mocks the wrong state.** `routes/__tests__/blueprints-new.test.tsx:771-779` ("falls back to the default branch when the link names none") sets `branchesState.branches = ["develop","master"]`. Production never reaches that state for a public repo, so the test passes.
- **Fix (target behavior):**
  - **Mount with Branch empty.** A link with neither `/tree/<branch>` nor `branch=` starts with Branch empty, so the preview resolves the repository's default branch and the w4/532 effect fills it in. octocat/Hello-World then shows `master`; a repo whose default is `develop` shows `develop`.
  - **Drop the guesses.** Delete the `"main"` seed and the `master`/`branches[0]` heuristic. The `repoBranches` list can stay as combobox options.
  - **Before the preview settles,** Branch is empty (placeholder `main`) and the preview shows its loading state. Deploy Blueprint stays disabled until a branch is resolved; `:185` already requires a non-empty branch.
  - en and zh.
  - **Tests:**
    - Replace the 771-779 case with one where `repoBranches` is `[]` and the preview returns `branch: "master"`: the field reads `master`.
    - Keep the `/tree/dev` and `branch=` cases.
    - Add a case where the preview resolves `develop` while `repoBranches` lists `["develop","master"]`: the field reads `develop`.
- **Aliases:** `/deploy?repo=` (it redirects, in `dashboard/src/routes/deploy.tsx`) and `/blueprints/new?repo=` render the same component.
- **Unverified:**
  - **A repo inside the workspace's GitHub App** (`repoBranches` non-empty) whose default is neither `main` nor `master`.
  - **GitLab URLs.** Out of scope: ADR018's "Git connections" row marks them ◐. `https://gitlab.com/gitlab-org/gitlab-foss` shows "bex's GitHub app cannot access it". Noted, not filed.
- **Render:** the Deploy button deploys the repository's default branch unless the URL ends in `/tree/<branch>`.
- **Dedupe:**
  - w8/163 (done) built the link; its target names the default-branch rule.
  - w4/532 (done) resolves the default branch for a typed Public Git URL.
  - w21/blocked/008 and 009 cover the docs and the sign-up path.
  - No open item covers this.
  - **Not deploy lag:** `git log a0d5802594e9..origin/main -- dashboard/src/routes/blueprints.new.tsx dashboard/src/features/blueprints` is empty.
- **DoD (live), signed in:**
  - **The default branch is used.** Open `https://dashboard.bex.co/deploy?repo=https://github.com/octocat/Hello-World`. Branch reads `master` and the preview says `render.yaml does not exist on branch master`, in en and zh, never "Branch main does not exist".
  - **Explicit branches are unchanged:** `/deploy?repo=…/tree/master` and `…express-hello-world/tree/main`.
  - **A `main`-default repo still works:** `/deploy?repo=https://github.com/render-examples/express-hello-world` still previews "Create express-hello-world Service".

- **2026-11-11 (loopx w4):** fixed: a Deploy link with neither `/tree/<branch>` nor `branch=` starts with Branch empty, so the review resolves the repository's default (w4/532's fill) — octocat/Hello-World reads `master`, a `develop` default reads `develop`; the hard-coded `main` and its `master`/`branches[0]` correction are gone. The fill now runs only for the Public Git tab's own settled review, so a link's default no longer carries into the GitHub tab after a switch. Route tests: an empty branch list resolving `master`, a list resolving `develop`, and the tab switch.
