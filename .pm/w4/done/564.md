# 564 — Moving a service together with its environment group still warns "This move leaves linked groups behind" and lists that same group

Why: the warning exists to stop a service leaving its environment's group behind (w4/m238). When the user moves the two together, nothing is left behind, but the dialog says it is. The only way forward is "Move anyway", which reads as accepting a misconfiguration that isn't there.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 63, 2026-11-11 02:08–02:16 UTC (`muse.env`, workspace `bex-canary`, pin `a0d5802594e9`). **Minor**: a false warning; the move itself is correct. ~20m.
- **Fixtures** (all deleted; DELETE 204, then GET 404):
  - project `qa-20261110-mg63` (`prj-dbpss2lhi5vc738gj190`), with environments `qa-one` (`evm-dbpss2lhi5vc738gj19g`) and `qa-two` (`evm-dbpss2lhi5vc738gj1a0`);
  - Free image service `qa-20261110-mg63-svc` (`srv-dbpss2vbq3ic73c0a9pg`) in `qa-one`;
  - group `qa-20261110-mg63-grp` (`evg-dbpst8nbq3ic73c0a9u0`), scoped to `qa-one` and linked to the service through `POST /v1/env-groups/{id}/services/{srv}`, which returned 200.
- **Probe** (project page `/project/prj-dbpss2lhi5vc738gj190?env=evm-dbpss2lhi5vc738gj19g`):
  1. **Control: the group alone.** I ticked only the group, chose "Move selected resources to environment" → `qa-two` → Move.
     - GraphQL `SetEnvironmentEnvGroups` returned `ENV_GROUP_MOVE_INCOMPATIBLE_SERVICES`, "move the linked services to the target Environment or unlink them before moving this group", which the toast shows.
     - This is correct and honest.
  2. **The case: both together.** I ticked both the service and the group ("Selected: 2"), chose `qa-two` → Move.
     - `alertdialog "This move leaves linked groups behind"` opened: "These environment groups stay linked to the moving service, and their variables and files keep applying to it until the group is unlinked or moved:" with the list item "qa-20261110-mg63-grp qa-20261110-mg63 / qa-one".
     - That group was part of the move.
  3. **"Move anyway" does the right thing.** The toasts read `Environment groups for "qa-two" updated.` and `Services for "qa-two" updated.`. REST then gave the group `environmentId` `evm-dbpss2lhi5vc738gj1a0`, the service `environmentId` the same, and `serviceLinks` still `[srv-dbpss2vbq3ic73c0a9pg]`. Nothing was left behind.
- **Root cause:**
  - **Only the moving services are passed to the guard.** `dashboard/src/features/environments/components/environment-card.tsx:286-315` (`handleMove`) collects `movingServiceIds` from the selection and calls `guard.strandedFor(movingServiceIds, target.id)`. The env groups in the same selection are ignored.
  - **The guard sees the group's current scope.** `strandedGroupsForDestination` (`dashboard/src/features/env-groups/lib/stranded.ts:14-26`) flags every scoped group whose `environmentId !== destinationEnvironmentId` and that links a moving service. A co-moving group is still on its old `environmentId`, so it is flagged.
- **Fix (target behavior):**
  - **Treat co-moving groups as already at the destination.** A group in the same selection, which `performMove` moves to the same target (`:318-352`), is in scope after the move. So the confirmation lists only groups that genuinely stay behind, and with none it doesn't open.
  - **One way to do it:** pass the moving group ids into `strandedFor` / `strandedGroupsForDestination` and exclude them.
  - **Guard against a race.** `performMove` starts every kind's setter at once. Check that the service write still precedes the group write, so the backend never refuses the group move with `ENV_GROUP_MOVE_INCOMPATIBLE_SERVICES` in mid-move. Live, both arrived in one batched GraphQL request and succeeded.
