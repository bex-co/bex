# GraphQL still returns a private service's cluster-internal address in `url` — the fourth instance of the family `w6/m130` closed for `renderSubdomainPolicy`

Why: REST and MCP deliberately omit `url` for a `private_service` because Render does and because bex once "leaked the cluster-internal URL there" — but GraphQL's flat `Service.url` reads the shared `AppView` rather than the gated emission site, so it still hands back `http://<slug>:<port>` in the field that means "the public URL".

Found by live `/qa-find-bugs` 2026-09-21 pass 137 (w4-targeted, `muse.env` credentials), journey 10. Fixture `qa-20260921-priv` deleted.

## Repro — one workspace, two surfaces, same moment

```graphql
{ services(ownerId:"tea-…", limit:50) { name type url internalAddress } }
→ { "name":"qa-20260921-priv", "type":"private_service",
    "url":"http://qa-20260921-priv:8080",          ← the internal address, in url
    "internalAddress":"qa-20260921-priv:8080" }
```

```
GET /v1/services?limit=50
→ { "name":"qa-20260921-priv", "type":"private_service",
    "serviceDetails": { "internalAddress":"qa-20260921-priv:8080", … } }
                                                   ← no url key at all
```

Every `web_service` in the same two responses carries a real `https://…onbex.co` in both. Only the private service diverges, and it diverges by carrying the same value twice — once correctly labelled, once in the public-URL field.

The by-id reads agree with their lists: GraphQL `service(id:)` → `url: "http://qa-20260921-priv:8080"`; REST `GET /v1/services/{id}` → no `url`.

## The gate exists and GraphQL is on the wrong side of it

`lego/backend/internal/apps/render.go:411-417`:

```go
// Render's serviceDetails carries url for web_service/static_site but
// OMITS it for private_service (captured 2026-07-26,
// docs/render-artifacts/service-addresses.md §3) — bex used to leak the
// cluster-internal URL there; the address now travels in internalAddress.
if a.URL != "" && svcType != renderPrivateService {
	details["url"] = a.URL
}
```

That gate is at the **emission site**. MCP is safe for the same reason — `renderServiceResult` → `toRenderService(app)` → the same `renderServiceDetails` (`mcp.go:1105-1113`). GraphQL is not: it resolves `Service.url` from `AppView.URL`, which `view()` fills unconditionally from `a.Status.URL` (`service.go:930, 950`), and the operator sets that to the internal URL precisely when there is no public host (`operator/internal/controller/app_controller.go:2550` → `internalURL`, `:2712-2717`).

**The sibling field in the same payload proves the intended shape.** `renderSubdomainPolicy` came back `null` on GraphQL for this same private service, because `w6/m130` emptied the **value** in `view()` rather than only gating the emission — its comment at `service.go:918-925` says so explicitly:

> _"Emptying the VALUE here is what lets GraphQL's flat field agree with REST/MCP's omission — GraphQL reads this AppView, not renderServiceDetails (which gates again at the emission site, belt-and-suspenders like ipAllowList)."_

`url` never got that treatment. Same function, same type-gate, one field behind.

## It is a family, and this is the fourth member

`w6/m130`'s own summary names the lineage: disk (`w1/m86`) → `ipAllowList` (`w6/m106`) → `renderSubdomainPolicy` (`w6/m130`). Each was "a field emitted for a service type that cannot have it", each fixed by gating once in `view()`. `url` for `private_service` is the same defect with the same fix, and the fact that three rounds of it did not catch this one is the argument for auditing the rest of `AppView` in the same pass rather than patching a fourth field alone.

## The rest of the type family is already correct

The operator assigns `status.URL` per type, so the exhaustive check is cheap and it lands well everywhere else:

| type              | `status.URL`                                     | correct? |
| ------------------- | -------------------------------------------------- | ---------- |
| `web_service`      | `https://<host>` (`app_controller.go:2596, 2723`) | yes      |
| `static_site`      | `https://<host>` (same path)                      | yes      |
| `background_worker`| `""` — _"a worker has no HTTP endpoint"_ (`:2744`) | yes      |
| `cron_job`         | `""` — _"a cron_job has no serving URL"_ (`:3568`) | yes      |
| `private_service`  | `http://<slug>:<port>` (`:2550`)                  | **the one** |

So the fix is narrow: empty `URL` in `view()` for `private_service` the way `subdomainPolicy` is emptied two lines above, leaving `internalAddress` as the single place the address travels. The operator's `status.URL` can stay as it is — it is an internal field, and `internalURL` is also what the activator and routing paths read.

Estimate: ~30m including a test asserting REST-omits / MCP-omits / GraphQL-null for all three non-routable types, in the shape `subdomain_policy_test.go` already uses.

## Unverified

- **Only `private_service` was created live.** The worker and cron rows above are read from the operator's explicit assignments and their comments, not observed — though both are `""` by construction, so there is nothing for GraphQL to leak.
- Whether any **other** `AppView` field is emitted for a type that cannot have it was not swept. Given this is the fourth instance, that sweep is the more valuable half and is why the fix should not stop at `url`.

## Also checked this pass, and found correct

Journey 10's actual promise — _"a private service is not publicly reachable"_ — holds, and holds well:

- **The platform host does not serve it.** `curl https://qa-20260921-priv.onbex.co/` → `404 page not found`, 19 bytes, from Traefik's default backend — byte-identical to the response for a hostname that has never existed (checked against pass 134's control). No Ingress is created, so the private service is not even distinguishable from an unregistered name at the edge. DNS resolves (the wildcard `*.onbex.co` A record) but nothing routes.
- **`internalAddress` is `<slug>:<port>`, derived from the contract** (`a.Spec.InternalAddress(a.Name)`), with the comment at `service.go:951-953` recording that the surfaced string and the operator's resolvable slug Service cannot drift (ADR041 D2/D4).
- **The dashboard gets this exactly right.** `/pserv/<id>` shows **"Service Address qa-20260921-priv:8080"** with a **Copy internal address** button — no URL, no clickable link, no `http://`. It reads `internalAddress`, which is why the defect above is invisible in the UI and only reaches raw GraphQL clients.
- **`renderSubdomainPolicy` is `null`** on GraphQL and absent on REST for the private service — `w6/m130` verified live on production, and it holds.

## Outcome (2026-09-21)

Fixed, and the audit the note asked for found the gate should not be the type after all.

`view()` now empties `url` unless it is `https://` — the scheme, not the type. Every public URL the operator publishes is `"https://"+host` (`setStatusURLs`), and every internal fallback it writes is `http://`, in two different shapes (`http://<slug>:<port>` and `http://<name>.<ns>.svc:<port>`). A type gate would have fixed the reported private-service case and missed the one beside it: an **exposed** service whose platform subdomain is off with no custom domain takes the same `len(hosts) == 0` branch, so REST — which gates on `private_service` alone at its emission site — was leaking the internal URL for a `web_service` too, on every surface.

`internalAddress` still carries the address, which is the point: it travels in the field that says what it is, and `publicRoutingNotice` (w7/m79) explains the absence. `Status.URLs` needed no change — the operator already nils it on the same branch.

`public_url_test.go` asserts REST-omits / MCP-omits / GraphQL-null across private service, unrouted web service and unrouted static site, plus a control that a service with a real host still reports it — so the guard cannot be satisfied by never reporting a url.
