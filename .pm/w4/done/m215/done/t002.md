## Step 1: isolated controls (2026-10-31, loopx w4) — DONE, with a defect found and fixed

Run in isolation: my own namespace `tea-w4m215local` on the local CAPD cluster, driving its existing operator read-only (`bex-operator:w2-m247`, built 2026-10-30 and containing m215's t001). A private kind cluster with **CloudNativePG 1.30.1**, production's version, provided the CNPG half. Nothing in another workstream's stack was changed. Afterwards both Database CRs, the namespace, the imported images and the kind cluster were removed.

- **Initial unknown version:** a fresh Database (`version: 17`) sampled every second went Provisioning → InitializingExtensions → Ready/Provisioned and **never** `Upgrading`. The empty-version window lasted under a second.
- **Unchanged healthy major:** a Ready 16 database with spec 16 stays Ready/Provisioned.
- **Pre-acknowledgement frame:** on `spec.version: 16 → 17`, the first frame was `Upgrading / MajorVersionUpgrade` with `currentVersion 16` while CNPG still read "Cluster in healthy state". This is the m215 fix.
- **Failure injection:** a user table with a `regproc` column makes `pg_upgrade --check` refuse ("Your installation contains one of the reg* data types in user tables"). The CNPG Job retried to `BackoffLimitExceeded`.
- **Defect found: CNPG never reports this failure in its phase.** On local CNPG 1.27 *and* on CNPG 1.30.1, with the Job `Failed=True`, the cluster phase stays "Upgrading Postgres major version" and the CNPG controller logs "Major upgrade job not completed." every 30 s, indefinitely (watched for over 8 minutes on 1.30.1). The operator recognised a failure only by a phase containing "fail" ("Failed to upgrade Postgres major version"), so a real pg_upgrade failure left the Database `Upgrading` forever with no server running and no automatic revert.
- **CNPG half of the revert (1.30.1, without bex):** setting the Cluster image back to `postgresql:16`, which the operator's failed branch writes, removed the failed Job and restarted the 16 server, healthy within ~15 s. `SHOW server_version` = 16.15, and the marker row `keep-me` was intact.
- **Operator half of the revert:** emulating the failed-phase report on the local cluster (status subresource phase "Failed to upgrade Postgres major version", the pg_upgrade failure itself being real) made the operator set `Failed / MajorVersionUpgradeFailed` and revert `spec.version` to 16. This is the existing w5/110 branch.
- **Fix (`database_controller.go`):** while CNPG reports a running upgrade, `failedMajorUpgradeJob` reads CNPG's major-upgrade Job (`cnpg.io/cluster`, `cnpg.io/jobRole=major-upgrade`, already in the operator's Job cache and RBAC). A `Failed=True` Job now counts as `majorUpgradeFailed()`, so the existing failed branch reverts and CNPG 1.30 recovers as measured above. The Ready message names the pg_upgrade failure. Regressions: `TestFailedUpgradeJobBehindARunningPhaseRollsBack` (fails on the old code) and `TestRunningUpgradeJobStaysUpgrading`. Operator `GOWORK=off make test` and `make lint` pass.
