# w4/261 — Deploy log search claims 100 matching lines when none match

Why: users need to distinguish partially loaded history from search matches while diagnosing a deploy; the current cap notice contradicts the empty result.

**Severity:** minor (copy). **Estimate:** 50m. Functional `$qa-find-bugs w4` a227, 2026-10-11 UTC, production dashboard, workspace bex. Research main `5de910490`; helper-owned `muse.env` login. Filing only. [ADR010 observability](../../docs/ADR010-observability.md) and [ADR018 parity](../../docs/ADR018-render-parity.md).

Use an owned completed deployment with more than 100 build records. **Expected:** while older source history remains, this deploy panel says **Only part of this time range is loaded. Load older to search earlier lines.** Keep the working Load older button, loading state and empty-result copy. Do not claim any number of matches or hide older history when the local filter matches nothing. When every leg is complete, remove the notice. The same wording must remain accurate after additional pages and under type/instance filters.

**Strong controls:** the direct API on the exact deploy window returns raw build `100 / hasMore:true`, raw app `1 / false`, no-match build/app `0 / false`, and positive build search `2 / false`. UI seed requests carry no `text`, so their caps describe source pages, not client matches. Pagination works and no lost records were observed. The initial two-result desktop search automatically fetched older history and cleared the notice; the stable reproduced defect is the no-match pane, where no LogLineList mounts. This finding does not report the automatic paging control as broken.

## Cause and bounded work

- `dashboard/src/features/deploys/components/deploy-log-panel.tsx:81–88,127–146`: type/text/instance filters run locally over merged loaded records. Its search uses displayed text after ANSI stripping. `366–371` passes the source `hasMore` into the shared notice with its default caption, irrespective of the filtered result.
- `dashboard/src/features/deploys/hooks/use-deploy-logs.ts:20,92–116,171–185,223–224`: Each type leg fetches at most 100 unfiltered records; any incomplete leg makes the combined source incomplete. A merged view is not one server-filtered 100-row page.
- `dashboard/src/features/logs/components/log-truncation-notice.tsx:11–32` defaults `partial=false`, selecting `logs.truncatedNotice`. English `features/logs/locales/en.ts:128–138` and Chinese `locales/zh.ts:126–138` both hard-code **100 matching**. Simply passing `partial={filtered.length < 100}` would also misdescribe this as the server's time-budgeted search; the transport never searched these local filters.
