# 636 — A static site that has served answers "This service's first deploy is in progress" for about 19 s after Resume: the activator's static-site branch gives every unsuspended site the first-deploy page while its route moves back

Why: an owner resumes a static site that was live a few minutes earlier. For the next 19 s every visitor gets a 503 page titled "First deploy in progress". No deploy runs: Resume created no deploy row, and the same live deploy serves afterwards. A monitor or a visitor reads it as a site that never went live.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 301, 2026-11-13 15:07–15:16 UTC (`muse.env`, workspace `bex-canary`; pin `5de3d5bcce8e`). **Minor** (a transient with the wrong reason; the site recovers by itself). ~1h.
- **Fixture:** static site `qa-20261113-r301-static` (`srv-dbrifgok58is73auoc10`), built from `https://github.com/bex-co/bex` `examples/static-site` (`publishPath: .`, no build). Its first deploy `dep-dbrifgok58is73auoc1g` went live at 15:08:25. Deleted afterwards (`DELETE` 204, then `GET` 404).
- **Probe:** `POST /v1/services/{id}/suspend`, then `POST /v1/services/{id}/resume` (both 202). The host was polled every 2–3 s.

  | after Resume at | `curl https://qa-20261113-r301-static.onbex.co/` |
  | --- | --- |
  | 15:11:18 (plain) | 503, `This service's first deploy is in progress. Try again in a few seconds.`, until 15:11:37; the site's own 200 from 15:11:39 |
  | 15:13:21 (`Accept: text/html`) | 503, `<title>bex &mdash; First deploy in progress</title>`, `retry-after: 10`, `x-render-routing: no-server`, until 15:13:37; the site's own 200 from 15:13:40 |

  - `GET …/deploys` still lists only `dep-dbrifgok58is73auoc1g` (`live`), so Resume started no deploy.
  - Events: `suspender_removed` at 15:11:18, then `service_resumed` at 15:11:40. That is the moment the route moved back.
- **Root cause:**
  - **The operator moves the route on its next reconcile.** While a static site is suspended, its Ingress points at the activator's suspended responder. "Resume points the Ingress back at the static-server on the next reconcile" (`lego/operator/internal/controller/app_controller.go:4767-4787`). That took about 19 s in both probes.
  - **Meanwhile the activator answers the first-deploy page.** In `newHoldingHandler` (`lego/operator/cmd/activator/main.go`), the resumed App passes the suspended check (`:198`) and the never-served check (`:216-224`). It then reaches the static-site branch (`:226-235`), which calls `writeFirstDeployResponse` (`:427-435`) for every unsuspended static site. Its comment already names the case: "after its first publish (or, for a second, on resume)".
  - The page's copy and JSON (`firstDeployText`/`firstDeployJSON`, `:432-435`) describe a first deploy whatever `status.activeRevision` says.
- **Fix (target behavior):** a static site with an active revision that reaches the activator unsuspended gets **the site's own response**.
  - The activator reverse-proxies the request to the static-server Service. The static-server already sees the resumed spec within seconds: its resolver reloads on every App change (`internal/appwatch`; `staticHandoverDelay` comment, `app_controller.go:4694-4697`), and it applies the site's rules and headers itself.
  - The activator needs the static-server's address, the operator's `BEX_STATIC_SERVER_SERVICE`, in its own environment.
  - If the proxy is not configured, or the static-server answers its handoff 503 (`serveSiteUnavailable`, `lego/operator/internal/staticserver/staticserver.go:1037-1047`), fall back to an interstitial that says the site is resuming, not that a first deploy is running.
  - The first-deploy page stays for a site with no active revision (`:216-224`).
  - The same branch also serves the 2 s handover after a first publish (`staticHandoverDelay`). With an active revision recorded, proxying is right there too.
- **Blast radius:**
  - Only the activator's static-site branch changes. Unknown host, maintenance, suspended, failed first release, first deploy, robots and wake keep their order and tests.
  - The sibling **w4/603** (open) has the same route-lag shape for a web service leaving maintenance, and proposes proxying to the App's Service. Both use `holder`'s reverse proxy (`cmd/activator/hold.go`). Do them together, or let the second reuse the first's proxy.
- **Tests:**
  - A resumed static site with `status.activeRevision` set is proxied to the static-server, and no first-deploy page is written.
  - A static site with no active revision still gets the first-deploy page.
  - A suspended site still gets the suspended page.

- **Closed 2026-11-14 (`/loopx w4`):** In the activator's static-site branch (`cmd/activator/main.go`), a site with an active revision that reaches the activator unsuspended (a resume, or the handover after a publish) is now reverse-proxied to the shared static-server through the holder's proxy (`hold.static`, from `BEX_STATIC_SERVER_SERVICE`/`BEX_STATIC_SERVER_PORT`/`POD_NAMESPACE`, now set on the activator Deployment and listed in `lego/operator/AGENTS.md`), so visitors get the site's own page, with its host, while the route moves back.
