# 092 — The custom-domain DNS panel labels both records "Host" but gives one a relative label and the other a fully-qualified name

Why: a user who pastes both records as shown into a normal DNS provider creates the ownership TXT one zone too deep, verification then never succeeds, and the panel keeps saying "Pending" with no way to tell a typo from slow propagation.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 40. Journey 5 exercised end to end on a `qa-` static site created and **deleted** this pass (`srv-dak2fra6m8ac739r62ag`, verified gone by id; no domain claim survived the cascade). Severity: **major** — a core hosting journey can silently fail to complete, in a way indistinguishable from "DNS hasn't propagated yet".

## What the panel shows

Adding `qa-20260914.example.com` to a static site renders two records under one "DNS setup" heading, each with a column literally headed **Host**:

```text
First, add this TXT record to prove ownership; the domain is not routed until verification succeeds.
This host holds one TXT record per domain — add this value as an additional record and keep any
bex-domain-verification values already there.
   Type    TXT
   Host    _bex-challenge.example.com
   Target  bex-domain-verification=lg_i8JUdZPirKfi7Cf7pI3s_sSNZrSb-

Traffic record
Create the following record at your DNS provider, then re-check.
   Type    CNAME
   Host    qa-20260914
   Target  qa-20260914b-static.onbex.co
```

One **Host** is a fully-qualified name. The other is a bare label relative to the zone. Same word, same panel, two conventions.

## Why that breaks

Mainstream DNS providers (Cloudflare, Route 53's console, Namecheap, and the rest) treat the Name/Host field as **relative to the zone** and append the zone themselves. Pasting these two verbatim into `example.com` therefore yields:

| record | lands at | correct? |
| --- | --- | --- |
| CNAME `qa-20260914` | `qa-20260914.example.com` | ✅ |
| TXT `_bex-challenge.example.com` | `_bex-challenge.example.com.example.com` | ❌ |

The traffic record works, so the domain resolves — and ownership never verifies. The panel's only feedback is `Verified Status: Pending` and a **Re-check** button, which will keep reporting pending forever. Nothing distinguishes "you put the TXT in the wrong place" from "DNS is still propagating".

## Root cause: the two names are built to different contracts

**Traffic record** — `apps/domains.go:269-279`, `dnsRecordFor`. Its type's doc comment (`:142-146`) is explicit that the value is relative:

```go
Name  string // the record host to create: the subdomain label(s), or "@" for apex
```

```go
// Subdomain: strip the trailing two labels (the root zone) to get the record name.
labels := strings.Split(host, ".")
name := host
if len(labels) > 2 { name = strings.Join(labels[:len(labels)-2], ".") }
return DNSRecordView{Type: "CNAME", Name: name, Value: platformHost}
```

**Ownership record** — `apps/domains.go:84-86`, which returns an FQDN into the same `Name` field:

```go
func ownershipDNSRecordName(host string) string {
	return "_bex-challenge." + ownershipDomain(host)   // ownershipDomain = registrableDomain(host)
}
```

So the ownership record violates `DNSRecordView.Name`'s own documented contract. The dashboard is a faithful renderer and not at fault: `custom-domains-section.tsx:436-438` prints `record.name` verbatim under `t("services.domainRecordHost")` for both records.

**The `_bex-challenge.<registrable-domain>` *value* is correct and deliberate** — ownership is proven once per registrable domain, which is why the copy says the host is shared and to keep existing values (`w6/055`, `w4/m84/t003`). This note is **only** about which form that name is presented in.

## The fix

Target behavior: **every "Host" in this panel is relative to the zone the user is editing**, because that is what a DNS provider's Host field means and what the traffic record already assumes. For `qa-20260914.example.com` the TXT host becomes `_bex-challenge` — and for an apex domain it stays `_bex-challenge`, since the zone *is* the registrable domain.

Two things make this less trivial than it looks, and the implementer should decide both explicitly:

1. **The zone is not always the registrable domain.** A user may run `example.com` and `sub.example.com` as separate zones. A relative name is only unambiguous against a stated zone — so the panel should name the zone it is relative to ("in the `example.com` zone"), which the traffic record does not do today either.
2. **`ownershipDNSRecordName` is also the verifier's lookup key** (`requireDomainOwnership`, `domains.go:105-110`, resolving the TXT). Changing the *presentation* must not change what is resolved. Keep the FQDN internally and derive the display form, or the fix breaks verification for every existing claim.

Blast radius: `ownershipDNSRecordName` has callers in `apps/domains.go` for both the view and the verifier; the display path additionally surfaces on REST (`renderDNSRecord`, `:1116`, `:1151`) and GraphQL (`apps/graphql.go:654-656`), so all three surfaces show the same string and must move together. The MCP surface was not checked for a domain-instruction read.

Adjacent classes after the fix: an **apex** domain's traffic record is `@` (already relative); a **verified** domain hides the TXT panel entirely (`custom-domains-section.tsx:374`, gated on `!domain.ownershipVerified`); a **sibling claim** under the same registrable domain keeps sharing the host with its own value (`w6/055`).

## Verified working in the same pass

- **`w6/055` is fixed and the fix is live.** The TXT panel now carries exactly the guidance that note asked for: "This host holds one TXT record per domain — add this value as an additional record and keep any `bex-domain-verification` values already there."
- **The static-site create flow is consistent**: selecting Static Site updates heading, description, document title (`New Static Site ・ bex Dashboard`) and URL (`?type=static_site`) together, and offers no instance-type selector, which is right for object-storage serving.
- The add-domain dialog states the contract up front — "Enter a domain you own. Point its DNS to this service, and bex issues a TLS certificate automatically."
- Both statuses render as distinct columns (`Verified Status: Pending`, `Certificate Status: Pending`) rather than one conflated state.
