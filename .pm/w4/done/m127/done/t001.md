## Objective

Answer one question that `w6/m19` and `w6/m37` never had to: does `protectedStatus` protect only the datastore *object* — its lifecycle, plan and topology — or also the **data inside it**, reached through the SQL console. Write the answer into ADR032 so it is a decision rather than an omission.

## Context

### The full live matrix (2026-09-21, production, free-plan fixtures in a fresh protected environment)

| verb                                                    | result on a protected member |
| --------------------------------------------------------- | ------------------------------ |
| `suspendDatabase`                                        | **refused** — `sudo suspend database qa-20260921-db` |
| `suspendKeyValue`                                        | **refused** — `sudo suspend key value qa-20260921-kv` |
| `deleteDatabase`                                         | **refused** — accepted with the phrase (this was the cleanup) |
| `deleteKeyValue`                                         | **refused** — accepted with the phrase |
| `executeDatabaseQuery(allowWrites:true)` `CREATE TABLE`  | accepted |
| `executeDatabaseQuery(allowWrites:true)` `INSERT`        | accepted |
| `executeDatabaseQuery(allowWrites:true)` `DROP TABLE`    | accepted |
| `setKeyValuePersistenceMode("off")`                      | accepted |
| `setKeyValueMaxmemoryPolicy("allkeys_lru")`              | accepted |
| `failoverDatabase`                                       | accepted (`true`) |
| `renameDatabase`                                         | accepted (renamed) |

So a protected environment refuses to pause the database and permits `DROP TABLE` inside it.

### The guard, and where it stops

Two call sites per package, and that is all:

- `lego/backend/internal/postgres/protection.go:32` — `requireUnprotected`; used at `service.go:684` (delete) and `lifecycle.go:55` (suspend).
- `lego/backend/internal/keyvalue/protection.go:32` — same; used at `service.go:509` (delete) and `:541` (suspend).

The accepted verbs are structurally outside it: introspection shows `deleteDatabase(id, confirm)` and `suspendKeyValue(id, confirm)` carry a `confirm` argument, while `failoverDatabase(id)`, `renameDatabase(id, name, dryRun)`, `setKeyValueMaxmemoryPolicy(id, maxmemoryPolicy, dryRun)`, `setKeyValuePersistenceMode(id, persistenceMode, dryRun)` and `executeDatabaseQuery(id, sql, allowWrites)` carry none. A caller who wanted to confirm could not.

### Be fair to the SQL console — it is not unguarded, it is guarded by something else

`postgres/query.go:124-150` is careful, and the decision should not pretend otherwise. `ExecuteQuery` with `allowWrites` requires **both** `can_create` and `can_view_sensitive`, re-asserted **uncached at the sink** because, in its own words, _"arbitrary SQL is a sensitive/destructive sink, so a membership revoked inside PositiveTTL must not ride a cached positive to one last query"_ (codex round 9 #7, round 18). Its doc also says `allowWrites` is _"an explicit opt-in used only after the dashboard confirmation"_.

So the real gap is narrower and more precise than "the console is open":

- the confirmation that exists is a **dashboard-side** one, not the protected-environment mechanism, and
- it is not enforced for REST, GraphQL or MCP callers, who reach the same verb with no confirmation of any kind.

That is the thing to decide about.

### The two defensible answers

- **Protection covers the data plane.** Then `executeDatabaseQuery(allowWrites: true)` joins the guarded set with its own phrase (`sudo write database <name>` or similar). This matches the plain reading of the control — a user who ticks "protected" on their production environment almost certainly believes it covers `DROP TABLE` — and it costs one guard call plus a `confirm` argument.
- **Protection is a control-plane guarantee only.** Then say so, loudly: in ADR032, in the dashboard's protection toggle copy, and ideally in the console itself. The argument for this answer is that writable SQL is already gated on a strictly stronger authorization pair than anything else in the product, and that a tenant with `can_create` + `can_view_sensitive` on a database can always connect with the connection string directly — so an API-level confirmation is theatre against anyone determined.

  That second argument is worth testing rather than assuming: check whether protection blocks anything at the connection-string level. If it does not, the confirmation genuinely is advisory, which is still useful against accident but should be described that way.

## Steps

1. Decide the data-plane question and write it into ADR032's `protectedStatus` bullet with its reasoning.
2. Take the control-plane rule from [`w4/m126`](../m126/README.md) t001 and apply it to the datastore verbs rather than deciding a second, possibly different rule — the two milestones must not end up with different definitions of "protected".
3. Classify each accepted verb above under that rule: durability (`persistenceMode`), eviction (`maxmemoryPolicy`), topology (`failover`), identity (`rename`), plus plan/parameter changes through `UpdatePostgres` (`postgres/service.go:1246`), which the hunt did not exercise.
4. If the answer is "control plane only", write the limitation where a user will actually meet it — the environment protection toggle and the SQL console — not only in the ADR.
