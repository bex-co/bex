## Objective

Confirm that REST `GET /v1/logs?resource=red-…|dpg-…`, GraphQL `logs`, and MCP `list_logs` return the same `{hasMore,nextStartTime,nextEndTime,logs}` envelope for datastore resources, and that following the cursors reaches `hasMore:false` with every line exactly once, as `w4/m107` proved for services. Compare with render.com's datastore log paging and record any drift as follow-up.

## Acceptance criteria

- [ ] A cursor chain on a `dpg-` and a `red-` resource is recorded for all three surfaces.
- [ ] Any drift is filed, not silently accepted.

## Result (2026-09-26)

All three adapters share one `pageCursors` over one core query, and the new backend test `TestDatastoreLogsPageCursorsChainOnEveryAdapter` (`lego/backend/internal/logs/datastore_paging_test.go`) walks an 11-line window at limit 4 for a `dpg-` and a `red-` resource on REST, GraphQL, and MCP. Each chain reaches `hasMore:false` with every line exactly once. Drift fixed: MCP `list_logs`'s description and `resource` schema named only services and Postgres, although Key Value (`red-`) was served. It now names all three. Render's dashboard scrolls datastore history back (m107's citation), so there is no UI drift left.
