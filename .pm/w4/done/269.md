# Try again cannot recover dashboard routes after a bundle update

Why: a customer whose open tab references a replaced JavaScript chunk cannot recover an otherwise healthy project through the offered Try again action, although a fresh document opens the same saved project.

**Severity:** minor — the existing tab is blocked until a manual document reload; the created project is preserved. **Estimate:** 55m (retry/caller audit 10m, scoped recovery action 10m, behavioral tests 20m, Simplify and browser verification 15m). **Status:** open. Source: continuous functional `$qa-find-bugs w4`, pass a269, 2026-10-11 local / 2026-10-12 UTC, muse.env login helper.

Goal: reliable hosting dashboard navigation and recovery under [ADR008](../../docs/ADR008-vision.md), [ADR006](../../docs/ADR006-bex-api.md) and [ADR018](../../docs/ADR018-render-parity.md). Recover the customer's current destination without repeating its already-completed create action.

## Live reproduction and controls

1. Fresh-load the signed-in Overview at **06:05:10.675Z**. Create an owned empty project through **Create new project → New Project → Create Project**, named `qa-20261011-a269-clone`. The actual CreateProject request is recorded as HTTP 200, with response Date **06:05:47 GMT**. Its response body was unavailable in the later network capture; the complete independent Projects read below proves the resulting `prj-db67heuh0inc73821ja0` exists.

The first retained error-page observation is **06:07:44.118Z**; no main element exists. The browser actually fetched three referenced chunks — project-sidebar, project detail and project index — with HTTP 200, but received HTML and reported module MIME errors. This was a natural product navigation; no intercepted response, forced asset deletion or production rollout was used.
3. Click the offered **Try again** at **06:10:09.562Z**. At **06:10:11.108Z** the same destination still displays the same chunk error and has no main. Repeat at **06:12:50.469Z**: by **06:12:52.504Z** the error persists, and the document still uses `/assets/index-Bb-mMKWy.js`.
4. **Fresh-document control:** at **06:11:31.427Z**, an ordinary second tab opens that exact project URL, displays its name and empty Environments section, and uses `/assets/index-C6qkybRe.js`. The original tab remains failed at **06:11:31.457Z**. The resource and destination are healthy; the original document's code graph is old.
5. **Working-home and repeated-navigation control:** Go home in the original tab. At **06:15:38.322Z**, Overview works with the old `index-Bb-mMKWy.js` document. Its actual owned-project link reads `qa-20261011-a269-cloneNo resources yet`. Click that link: the same destination fails again at **06:15:38.556Z**, with the same missing-module message.
6. **Recovery control:** reload that failed document once. At **06:15:39.997Z**, the exact same project URL displays the saved project and empty Environments, now using `index-C6qkybRe.js`. No create mutation is repeated.

The changed entry filenames, failed prior chunk and working fresh document establish the observed bundle mismatch. A deployment replacing the old asset set is the likely trigger, consistent with Vite's documented behavior; the exact rollout timing and the router's prior sessionStorage reload-guard state were not inspected. The two failed Try again actions, repeated navigation failure and successful reload are directly observed. This is one naturally encountered version transition, not a claim of multiple independent deployment transitions or a fresh-mobile failure.

## Root cause and bounded fix

Research baseline: main `2994bbb7a`. The pull from `139d37976` changes image pins only; ErrorPage and router source are unchanged.

- `dashboard/src/common/root-route/error-page.tsx:16–28,74–81`: every Try again runs `router.invalidate().then(reset)`. That refreshes route data and resets the boundary while retaining the current document and its original import URLs. There is no module-error branch that obtains a current document. The live old/new script observations and reload control show why retrying this document does not recover this destination.
- Installed and lockfile-resolved **@tanstack/react-router 1.170.25**, **@tanstack/router-core 1.171.21**, **Vite 7.3.6** were checked. `router-core/src/load-client.ts:61–100` retries route lazy loading using its existing lazy function; a rejection clears the lazy promise, not the document's code graph. `react-router/src/lazyRouteComponent.tsx:48–70` contains a separate, guarded automatic reload path for a module error encountered by that component. The mounted global ErrorPage action has no equivalent explicit recovery. This filing does not claim that every SDK auto-reload path is broken.
- `router-core/src/utils.ts:499–511` supplies bounded Chrome, Firefox and Safari module-error message prefixes. Its source is a useful classification precedent; React Router's public barrel does not expose that helper. Use a small application-local classifier or an existing declared dependency export if appropriate; no vendor patch is needed.
- **Two production registrations, one shared component:** `dashboard/src/router.tsx:22` sets defaultErrorComponent; `routes/__root.tsx:20` sets the root errorComponent. All routes inheriting that fallback share its retry action. Other resource-load cards retain their own retry owners. The live failure is the project route; other route families, browsers, mobile layouts and error classes were traced rather than independently failed.
- `error-page.test.tsx` already uses a real Router to verify that Try again retries a failed beforeLoad and preserves `/agents?archived=all#history`. That data-error behavior is correct and must remain.
- `error-page.tsx:20–22` calls the isomorphic route-error reporter. Preserve its existing SSR behavior, error title, Go home, Go back, translated labels and destination state.

For a recognized module-load error, make the explicit recovery action perform a **full document reload at the current href**. It must retain path, query and hash and must not re-run the user's create mutation. For ordinary loader/API/validation errors, retain the current invalidate-then-reset behavior. Match known module-load messages narrowly; a generic TypeError or Failed to fetch from a data request must not select document reload. Keep recovery user initiated so a persistently unavailable chunk cannot produce an automatic reload loop.

[Vite's primary load-error documentation](https://vite.dev/guide/build#load-error-handling), checked 2026-10-12 UTC, describes old documents importing chunks removed by a new deployment and identifies document refresh as a recovery option. [TanStack's lazyRouteComponent reference](https://tanstack.com/router/latest/docs/framework/react/api/router/lazyRouteComponentFunction) describes its lazy component helper; the installed source above establishes the actual versions and guarded behavior. No authenticated Render comparison was available; this is bex's own failed recovery action, not a claimed Render divergence.
