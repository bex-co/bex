# 408 — Closing a confirmation dialog drops keyboard focus to the page top: 35 of 43 ConfirmDialog sites never return focus to the button that opened them

Why: a keyboard or screen-reader user opens Suspend or Delete Service on the long Settings page, presses Escape or Cancel, and lands on `<body>`. Their next Tab starts from the sidebar, so they have to walk the whole page again to get back. WAI-ARIA dialog guidance (and Radix's own default when it owns the trigger) returns focus to the invoking control.

**Severity:** minor (keyboard accessibility; nothing is lost). **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run f6t1, 2026-10-24 UTC (`muse.env`, `bex-canary`, pin `c5583c80bef9`). Read-only on `hello-go` `/services/srv-daif6dsmg29s73d1umvg/settings`: dialogs opened, then Escape; nothing confirmed. Session revoked.

## Probe

For each control: focus it, press Enter, check focus, press Escape, check `document.activeElement`.

| Control              | Dialog opens | Focus on open           | After Escape               |
| -------------------- | ------------ | ----------------------- | -------------------------- |
| **Suspend**          | yes          | inside, on Cancel       | `BODY` (trigger not focused) |
| **Delete Service**   | yes          | inside, on Cancel       | `BODY`                     |
| _control:_ **Edit service name** (inline, no dialog) | n/a | n/a | the button itself |

## Root cause

- `dashboard/src/common/components/confirm-dialog.tsx:176-188` renders Radix `AlertDialog`, and an `AlertDialogTrigger` only when the caller passes `trigger`. Radix restores focus on close only to its own Trigger.
- Callers that open the dialog from their own button via controlled `open`/`setOpen` get no restore, e.g. `features/services/components/delete-service-card.tsx:92-104` and `suspend-service-card.tsx`.
- Blast radius: a scan of non-test `.tsx` finds **43** `<ConfirmDialog` sites, **35** without `trigger=`. They are spread across services (delete, suspend, manual deploy, instance type, autoscaling, custom domains, disk, edge caching, maintenance, runtime, environment editor, cron runs, row actions), deploys (`deploy-actions.tsx`, the Cancel deploy dialog), databases, Key Value, env groups, environments, blueprints, project settings, git credentials and agent sessions.

## Fix

- In `ConfirmDialog`, when no `trigger` is passed, capture `document.activeElement` when `open` turns true. In `AlertDialogContent`'s `onCloseAutoFocus`, `preventDefault()` and focus that element if it is still connected; otherwise fall back to a caller-supplied `returnFocusRef`. `global-search.tsx:51-60` already does this for the search dialog (w4/291) and can be shared.
- If the action removed the trigger (e.g. after a successful Delete navigates away), let normal navigation focus apply; don't force focus back.
- Tests:
  - controlled `ConfirmDialog` opened from a separate button returns focus to it on Escape and on Cancel;
  - trigger-based sites are unchanged;
  - a removed trigger doesn't throw.

**Unverified:** each of the 35 sites individually (two were probed live, the rest are read from the shared component).

## Loopx w4 verdict (2026-10-25)

Done: `ConfirmDialog` now returns focus for the controlled-without-trigger shape — it remembers the last element focused while closed, and on close hands focus back to it (or to a new optional `returnFocusRef`), unless that element has left the page (a successful Delete that navigates away keeps normal navigation focus). The trigger shape keeps Radix's own restore. Tests pin focus return on both Escape and Cancel.
