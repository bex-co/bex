# Denied-read audit writes can serialize on AuthorizeApp's name-collision fallback loop

`core.Base.AuthorizeApp`'s cross-tenant name-collision fallback (`lego/backend/internal/core/base.go`, the `for i := range list.Items` loop over `LabelServiceName` matches once the direct-name candidates miss) calls `authorizeAndAudit` once per candidate App sharing a public name — one distinct authorize decision per distinct resource, by design. Before w4/m20/t001, a denied **read** relation (`can_view`/`can_view_logs`/`can_view_sensitive`) never reached `emit`, so this loop was audit-free for reads. After t001 widened denied-read recording to match denied-write recording, a denied read can now write one `audit_events` row per rejected candidate in that loop, each a synchronous sink call bounded by `auditRecordTimeout` (2s) — so a GET against a common colliding name (many tenants named a service "web") can serialize multiple blocking audit writes before the request 403s.

This exact per-candidate-synchronous-audit shape already existed, unchanged, for denied **writes** since w4/m10 — t001 didn't introduce the mechanism, only widened which relations reach it, which was its explicit goal. Not a correctness bug (each candidate genuinely is a distinct authorization decision worth its own row), but a latency/DB-load concern on a read path that reads dominate by volume.

Two shapes worth considering, not decided here:

1. Detach the fallback loop's audit write from the response path (a bounded background goroutine, the same fire-and-forget shape `internal/apikeys/service.go`'s `TouchAPIKey` already uses) — but this loosens the AuditSink's current "recorded before the caller sees the outcome" guarantee, a real semantics change worth its own decision, not a drive-by fix.
2. Cap how many candidates the fallback loop will individually audit before giving up and recording one aggregate denial — changes today's "one row per candidate" semantic.

Source: `/simplify` (efficiency pass) over w4/m20's diff, 2026-07-14 — filed rather than fixed inline per t004's "file drift as a follow-up, never silently."

## Resolution (2026-07-15) — done: shape 2 (cap + one aggregate row)

Decided for **shape 2** and implemented it. Rationale: shape 1 (detach to a background goroutine) bounds latency but not DB write amplification, and loosens the "recorded before the caller sees the outcome" guarantee — two costs for one benefit. The cap bounds both latency (worst case `(cap+1) × auditRecordTimeout` instead of unbounded) and rows (one denied request can no longer insert one row per colliding tenant — a 403-read amplification an attacker controls by probing a common name), keeps recording synchronous, and preserves full per-candidate detail for the legitimate case (a handful of workspaces naming a service "web").

- `core.maxFallbackCandidateAudits = 3` (`audit.go`, doc'd next to `auditRecordTimeout`): the fallback loop's first 3 rejected candidates record individually exactly as before; the remainder are still **fully checked** (an allowed candidate past the cap is served, and an allowed WRITE past the cap still records — the write-audit invariant is never suppressible) but not individually recorded; when the loop exhausts past the cap, ONE aggregate denial row is recorded against the **caller's own** workspace (`ServiceTarget(name)`), so the trail still shows the probe continued.
- Mechanism: `authorizeAndAudit` refactored over a new `authorizeAndRecord(..., recordDenial bool)` — all other call sites byte-identical (`recordDenial=true`).
- Applied uniformly to denied reads AND writes in that loop: the amplification is identical for both, and per-candidate write denials past the cap are the same probe signal the first 3 rows + aggregate already record.
- Tests: `TestAuthorizeAppFallbackCapsPerCandidateDeniedAudits` (below-cap unchanged / past-cap 3+1 aggregate with caller-workspace resource / allowed-candidate-past-cap still served). Docs: ADR006 §Audit log.
