# A bad deploy over a healthy release emits `server_failed` (webhooks, Critical push) for a service that never went down

Why: a user who pushes a typo'd image tag gets paged "server failed" for 14 minutes, and then "server available", while their app answered 200 the whole time. The Events feed, the `server_failed` webhook and the Critical push rule all fire on a phantom outage. That is exactly the noise `w3/m78` and `w4/m112` set out to prevent ("an in-progress window mints no outage"). It is also the case customers hit most often, because a bad release over a good one is the common failure.

Found live in `/qa-find-bugs` pass 239 on 2026-09-27 (w4-targeted, `muse.env` credentials) against the deployed `4a0422577`. The fixture was a free web service `qa-20260927-pull` (`srv-daskr2rncejs739qitvg`, `docker.io/traefik/whoami:v1.10`, live), deleted afterwards (`DELETE` 204, then `GET` 404).

1. `POST /v1/services/<srv>/deploys {"imageUrl":"docker.io/traefik/whoami:v0.0.0-qa-nonexistent"}` at 17:08:40Z → `201 dep-daskr6a1pbgc73a24kn0`.
2. `curl https://qa-20260927-pull.onbex.co/` at 17:10:49, 17:11:10 and 17:11:30 → **200** each time. The prior release kept serving.
3. `GET /v1/services/<srv>/events?startTime=…`:

```text
deploy_ended       17:08:40Z   (the previous, successful deploy)
image_pull_failed  17:08:41Z
deploy_started     17:08:41Z
server_failed      17:09:23Z   ← phantom: the service was serving 200
deploy_ended       17:23:53Z   (the bad deploy, update_failed)
server_available   17:23:53Z   ← phantom recovery
```

The deploy row itself was right throughout: `stallReason` named the pull from 18 s, and it closed `update_failed` with `failureReason: "image pull is failing: … NotFound …"`.

## Mechanism

- `lego/backend/internal/store/reconciler.go` `observedServiceStateFor` (~l.1536): with a deploy open, a `Ready=False` condition is ignored as "ordinary rollout progress" **unless** `concreteContainerFailure(reason)` holds (`ImagePullBackOff`, `CrashLoopBackOff`, `CreateContainerConfigError`, ~l.1506). In that case it sets `Availability = "unhealthy"` whenever `app.Status.ActiveRevision != ""`.
- That guard reads the failing container as "the serving instance failed". Over a prior release it is the **new** revision's pod failing, while the `ActiveRevision` pods keep serving. `ActiveRevision != ""` is exactly the prior-release case, so the one condition meant to confirm a real outage selects the non-outage.
- `store/event_facts.go:485-487` turns healthy→unhealthy into `EventFactServerFailed`. `store/push_deliveries.go:588` routes `server_failed` to the service-event push rule, and the webhook fan-out carries it too.
- `w4/m103` fixed the service **phase** for this case (a failed rollout over a prior release stays `Running`), and `w8/m44` records the rollout verdict beside a `PriorReleaseServing` Ready. Availability, the input to events, pushes and webhooks, was left on the old rule.

## Fix

Target behavior: availability describes **what is serving**. A concrete container failure counts as unhealthy only when it belongs to the serving revision:

- the first deploy, with no prior release;
- the prior release's own pods, for example crash-looping after a node restart.

A failing **new** revision over a serving prior release is a deploy failure. That belongs on the deploy row (`stallReason` / `failureReason` / `deploy_ended`), and it must not mint `server_failed`.

- In `observedServiceStateFor`, skip the `concreteContainerFailure` branch when the operator reports the prior release serving: the Ready reason `PriorReleaseServing`, or the failing pods' revision ≠ `status.ActiveRevision`. Use whichever signal the operator already exposes; do not infer it from timing.
- Keep the first-deploy case unhealthy. That is still a real "cannot start" (`w7/m79`).
- Tests:
  - A rollout with `ImagePullBackOff` over an `ActiveRevision` emits no `server_failed` / `server_available` pair, and the prior release stays `healthy`.
  - The first-deploy `ImagePullBackOff` and a crash-looping *serving* revision still emit `server_failed`, as regressions for the callers that are correct today.

Blast radius: every consumer of `ServerFailed` / `ServerAvailable` facts, meaning the Events feed, webhooks (`server_failed`, `server_available`) and Critical push notifications. All of them read the same fact, so one fix covers them.

Unverified: whether the notification email/push for this pair was actually delivered to the workspace owner. The fact, and the rule that routes it, were observed; the delivery was not.

Estimate: ~45m.

Closed 2026-09-27: the operator now records live active-revision pod readiness separately from rollout diagnostics (`ConditionServing`); the store uses only a matching-generation serving observation to suppress phantom outage facts. Regression tests cover a healthy prior release, a crashed serving release, a first deploy, disappeared pods and stale observations. Operator `make test` and backend store tests passed; no live production re-probe performed.

Premise correction: a first deploy has no healthy availability baseline, so the existing store contract does not emit a healthy-to-unhealthy `server_failed` edge for it. Its deploy failure remains visible; this fix preserves that contract rather than inventing an outage before the service has served.
