# Project and environment rename fields have no accessible name on three dashboard surfaces

Why: the controls that change a project's or environment's name expose only their current value to assistive technology, so users cannot identify the field by its purpose even though the equivalent create forms label it correctly.

Severity: **minor**. Estimate: **50m**; keep this as an inbox note. Dashboard-only accessibility and console-warning fix; no API defect or wire-contract change is alleged.

Source: live `$qa-find-bugs w4`, new continuous pass 1 at the user's request, **2026-09-21 America/Los_Angeles / 2026-09-22 UTC**. Each editable rename field below was reproduced twice after a fresh page load; the Settings read-only state was also observed. The QA fixture was project `qa-20260921-pass1` (`prj-dap10294dm7c7390q6s0`) with environment `qa-20260921-staging` (`env-dap106h4dm7c7390q6tg`).

## Reproduction and durable evidence

1. Open `https://dashboard.bex.co/project/prj-dap10294dm7c7390q6s0` and click the project's **Edit** control. The **Rename project** dialog contains an unnamed textbox.
2. On the same project overview, open the environment's **More actions → Rename**. The **Rename environment** dialog also contains an unnamed textbox.
3. Open `https://dashboard.bex.co/project/prj-dap10294dm7c7390q6s0/settings` and click **Edit** in **Project Name**. Its editable textbox is unnamed. Click **Cancel**: the disabled, read-only textbox is unnamed too.
4. Control: open **New Environment**. Its textbox is named **Name** in the same browser and accessibility tree.

Relevant excerpts from the live accessibility snapshots, with unrelated nodes omitted:

```yaml

- dialog "Rename project":
    - textbox: qa-20260921-pass1

# Environment, More actions → Rename
- dialog "Rename environment":
    - textbox: qa-20260921-staging

- textbox: qa-20260921-pass1

# Project Settings, Cancel / read-only state

# Control, New Environment
```

Both rename dialogs also emit this console warning when opened:

```text
Warning: Missing `Description` or `aria-describedby={undefined}` for {DialogContent}.
```

Expected: the project fields have accessible name **Project name** and the environment field **Environment name**, regardless of their current value or editable/read-only state. The dialog descriptions are valid, or the simple dialogs intentionally opt out of a description. Actual: the field names are empty, and both dialog containers reference a missing description element.

Screenshots, all checked to exist before filing: `.playwright-mcp/qa-projects-4.png` supports project overview; `.playwright-mcp/qa-projects-2.png` supports environment rename; `.playwright-mcp/qa-projects-3.png` supports project Settings. These are local, gitignored illustrations; the reproduction and accessibility excerpts above are the durable evidence. No REST/GraphQL/MCP contract probe is required for this DOM-only defect.

## Independent roots and exact scope

| Surface | Root cause |
| --- | --- |
| Project overview rename | `dashboard/src/routes/project.$projectId.index.tsx:174-181` renders `Input` with value and handlers but no associated label, `aria-label`, or `aria-labelledby`. The enclosing `DialogTitle` at line 172 names the dialog, not the input. |
| Environment rename | `dashboard/src/features/environments/components/environment-card.tsx:397-404` independently makes the same omission; its dialog title is at line 395. |
| Project Settings rename | `dashboard/src/routes/project.$projectId.settings.tsx:124-133` renders the unnamed editable input, and `:159-164` renders its unnamed disabled/read-only counterpart. The **Project Name** card title at line 116 is not associated with either control. |

The shared `dashboard/src/common/components/ui/input.tsx:5-17` is a native `<input>` forwarding caller props. It neither discards an accessible name nor manufactures one. This is a **scoped caller fix**, not a change to shared Input or Dialog behavior.

Production-callsite searches across `dashboard/src`, excluding tests and hook definitions, find **two** `useRenameProject()` callers (the overview and Settings routes), **one** `useRenameEnvironment()` caller (`EnvironmentCard`), **one** `EnvironmentCard` caller (`environments-panel.tsx:233`), and **one** `EnvironmentsPanel` caller (project overview at line 151). Thus the fix covers **three rendering owners and four Input render sites**. Switching environments on overview reaches the same card implementation; Settings is a separate project-rename entrypoint and must be fixed separately.

The live control is correct for a specific reason: `new-environment-dialog.tsx:84-88` associates `<Label htmlFor="environment-name">` with `<Input id="environment-name">`. The code-traced New Project sibling does the same at `new-project-dialog.tsx:90-92`; it was not separately exercised in this naming probe.

## The description warning is a separate omission

The two rename `DialogContent` callers (`project.$projectId.index.tsx:170` and `environment-card.tsx:393`) supply neither `DialogDescription` nor an explicit opt-out. The wrapper at `common/components/ui/dialog.tsx:61-69` forwards content props unchanged.

The actual installed dependency, **`@radix-ui/react-dialog` 1.1.15** (pinned in `dashboard/yarn.lock:2843-2845`), explains the warning: `dashboard/node_modules/@radix-ui/react-dialog/dist/index.mjs:225-228` gives the dialog `aria-describedby=context.descriptionId`, then spreads the caller's content props. Its `DescriptionWarning` at `:302-309` warns when the referenced description element does not exist. The dialog title is separately connected through `aria-labelledby` at line 226.

Adding a description alone will not label the textbox. For these simple rename forms, explicitly pass `aria-describedby={undefined}` if no useful explanation is needed; otherwise supply a meaningful localized `DialogDescription`. Keep that decision at the two callers, preserving descriptions on other dialogs.

## Fix and acceptance

- Give the project inputs the localized accessible name **Project name** and the environment input **Environment name**. Prefer visible labels associated through unique ids; the Settings heading can instead be explicitly associated with both of its mutually exclusive input states. Keep the name independent of the mutable value.
- Handle the two dialog descriptions intentionally as above. Do not globally suppress warnings or change the shared Input/Dialog contract.
- Repeat the four live states from the reproduction. The accessibility tree must show `textbox "Project name"` on overview and in both Settings states, and `textbox "Environment name"` in environment rename; opening the rename dialogs emits no missing-description warning. New Environment remains correctly named.
- Strengthen the existing rename behavior tests to select the input by its accessible name: `routes/__tests__/project.$projectId.test.tsx:258` and `features/environments/components/__tests__/environment-card.test.tsx:335` currently use bare `getByRole("textbox")`; `routes/__tests__/project.$projectId.settings.test.tsx:127` uses `getByDisplayValue`. Preserve their mutation assertions and cover the Settings read-only name. Preserve Enter/save, Cancel, and existing validation behavior.
- Before data settles, retain the current loading/route behavior; the new labels must not depend on resolved resource names or appear only after a save. Forbidden, unauthenticated, not-found, and timeout handling remain on their existing paths; the change introduces no new lookup or disclosure.

## Closed 2026-09-22

All four Input render sites across the three rendering owners now expose an accessible name, and both rename dialogs opt out of a description explicitly.

| Surface | How it is named now |
| --- | --- |
| Project overview rename dialog | Visible `<Label htmlFor="project-rename-name">` → **"Project name"**, matching the working `new-environment-dialog.tsx` pattern the note identified as the control |
| Environment rename dialog | Visible `<Label>` → **"Environment name"**. Its input id carries the environment id, because `environments-panel.tsx` renders one card per environment |
| Project Settings, editable | `aria-labelledby` → the **Project Name** card heading |
| Project Settings, read-only | Same heading, so the control is named in both mutually exclusive states |

Settings took the note's own alternative — "the Settings heading can instead be explicitly associated with both of its mutually exclusive input states" — rather than a fourth visible label duplicating the card title two lines above it. One consequence worth stating precisely: the resulting accessible name there is **"Project Name"**, the card's own casing, not the "Project name" the acceptance text spells. It is the heading's text, which is the point of associating with it.

The **missing-description warning** is fixed at the two callers, as the note directed: `aria-describedby={undefined}` on both rename `DialogContent`s. No description was invented for a one-field form, no warning was suppressed globally, and other dialogs' descriptions are untouched. The shared `Input` and `Dialog` contracts are unchanged.

Tests, strengthened exactly where the note asked (and mutation-checked — reverting either half fails them):

- `project.$projectId.test.tsx:258` and `environment-card.test.tsx:335` now select by accessible name instead of a bare `getByRole("textbox")`, which is the query that would have caught this. Their rename mutation assertions are unchanged.
- `project.$projectId.settings.test.tsx:127` moved off `getByDisplayValue` — a query that passes precisely *because* the control is identified by its value — and asserts **both** states: the read-only textbox is named and disabled, the editable one is named and enabled.
- A new test opens the rename dialog and asserts the dialog carries no `aria-describedby` and that nothing logged mentions a missing description. It fails when the opt-out is removed.

`yarn tsc --noEmit`, `yarn lint`, and the full `yarn test` are green (437 files, 3611 tests).

These are jsdom tests over the real components, so they prove the names and the absent description reference, but not the deployed page. Re-run the note's four-step reproduction after this deploys.
