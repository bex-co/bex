# 653 — Offer Render's workspace Overlapping Deploy Policy setting: Override (cancel the deploy in progress and start the new one) alongside the default Wait

Why: Render lets each workspace choose its Overlapping Deploy Policy on its Settings page: **Wait** ("Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy", the default for workspaces created on or after 2025-07-14) or **Override** ("Immediately cancel the in-progress deploy and start the new one", the default before then) ([render.com/docs/deploys](https://render.com/docs/deploys)). The deploy hook's `202` "can only occur in workspaces with their overlapping deploy policy set to Wait" ([render.com/docs/deploy-hooks](https://render.com/docs/deploy-hooks)). Since w4/635 bex runs Wait for every runtime and offers no setting.

- **Source / severity / estimate:** `/loopx w4` closeout of w4/635 (2026-11-14). An optional variant: every bex workspace is newer than 2025-07-14, so Wait is the default Render would give it. **Minor**. ~4h; promote to a milestone if taken.
- **Scope:**
  - A workspace field (`overlappingDeployPolicy`: `wait` default, `override`) on the workspace settings surfaces (REST/GraphQL/MCP where Render's API exposes it — check Render's OpenAPI first; the dashboard's workspace Settings page).
  - Override: the newest trigger cancels the deploy in progress (store `prepareDeployCreate` closes the active row instead of queuing; the operator skips the pin for the workspace), and the deploy hook answers `200` with the new id.
- **Premise to verify first:** whether Render's public API reads or writes the setting, or only its dashboard does.
- **Tests:** per policy, a second trigger behind a deploy in progress queues (Wait) or cancels it (Override) on every runtime; the hook answers `202` or `200` accordingly.
- **Closed 2026-11-14 (/loopx w4):** Premise checked: Render's public API does not read or write the setting (its live OpenAPI `owner` schema has only `id`, `name`, `email`, `ipAllowList`, `twoFactorAuthEnabled`, `type`; the Render MCP tool list has nothing either) — only its dashboard's Workspace Settings → Overlapping Deploy Policy section does ([render.com/docs/deploys](https://render.com/docs/deploys); section order captured in `docs/render-artifacts/workspace-lifecycle.md`). So bex offers it on GraphQL and the dashboard, and REST/MCP stay absent by parity. Shipped: `tenants.overlapping_deploy_policy` (migration 0265, `wait` default, `override`); GraphQL `Workspace.overlappingDeployPolicy` (every member, refused with the coded 2FA 403 like `ipAllowList` to a member a workspace's 2FA requirement blocks) and `setWorkspaceOverlappingDeployPolicy(id, policy)` (Admin, `can_manage`; an unknown value is 400 `INVALID_OVERLAPPING_DEPLOY_POLICY`); the dashboard's Overlapping Deploy Policy card after Build Pipeline (Render's two sentences verbatim, en/zh, matching skeleton, right-rail link). Under Override the store never queues: a trigger behind a deploy in progress cancels it (`Superseded by dep-…`, or `Canceled by restart dep-…`) and starts at once, no deferred Restart/Rollback/image override (w5/m284, w4/652), so the hook answers `200 {deploy:{id}}`; the projector labels the workspace's Apps `app.bex.co/overlapping-deploy-policy=override` and the operator's `releaseInFlight` holds nothing for them. Decision: the operator follows a policy change within one projector pass (≤30s), bex-api at once. ADR018 gains a Workspace Overlapping Deploy Policy row; its List / get deploy objects row now points to it.
