# 405 — A deploy that already serves traffic is recorded "Canceled — Superseded" if a newer deploy starts before bex marks it Live

Why: the deploy history is how a user answers "what was running at 11:12?". Here it says nothing was. A release whose pods answered real requests for about 20 seconds is listed only as canceled and never Live. So the record contradicts what users actually received, and a rollback or incident timeline built from it is wrong.

**Severity:** minor (history accuracy; serving itself is correct and the newer deploy goes Live). **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run g6e2, 2026-10-24 11:12–11:20 UTC (`muse.env`, `bex-canary`, pin `c5583c80bef9`). Fixtures:

- Free busybox web service `qa-20261024-g6e2-svc` (`srv-dbe953coi59c73ajef40`), which serves `G=$QA_G`;
- env groups `qa-20261024-g6e2-grp` (`evg-dbe953c67tqc738jtt90`) and `-grp2`.

All were deleted (`GET` → `404`); session revoked.

## Probe (reproduced twice)

1. **Organic case:**
   - Create the service at 11:12:13 (deploy `…ajef4g`, `trigger: other`).
   - Link the group at 11:12:15 (deploy `…ajef50`, `service_updated`).
   - The URL served `G=g-v1`, the linked value, at 11:12:28, while both rows still read `update_in_progress`.
   - `PUT …/env-groups/<id>/env-vars/QA_G {value:"g-v2"}` at 11:12:42 started `…8jtta0`.
   - Both earlier rows then closed `canceled`, `cancelReason: "Superseded by dep-dbe95ak67tqc738jtta0"`. Neither was ever `live`, though `…ajef50` had served.
2. **Controlled replay** (in-page, 1 s polling of `GET /v1/services/<id>/deploys/<A>` and the public URL):
   - `PUT …/env-vars/QA_G {value:"svc-override"}` (no deploy), then `POST …/deploys` → A.
   - 13 s: A `update_in_progress`, URL serves `G=svc-override` (A's config). Trigger B.
   - 16 s: A still `update_in_progress`, still serving A's config.
   - 33 s: A `canceled`, `cancelReason: "Superseded by dep-dbe972k67tqc738jttd0"`.

## Root cause

- `supersededDeployStatus` (`lego/backend/internal/store/reconciler.go:1578-1620`) closes a row whose release generation is behind `status.releaseGeneration` as `live` only if `servesGeneration` (`:1569-1573`) holds, i.e. `status.activeRevision` names it. Otherwise, absent a recorded failure, it closes `canceled`. The comment's "a prebuilt image superseded mid-rollout" case is exactly this.
- The observed serving shows the operator stamps `activeRevision` (and the row reaches `live`) several seconds after the new revision's pods take traffic. A newer release dispatched inside that gap supersedes the row before the stamp lands.
- **Unverified:** whether the operator abandons the in-flight image release on the newer dispatch without stamping it, or stamps it after the backend already closed the row (read from the reconciler only; the operator's `activeRevision` writer was not traced live).

## Fix (target behavior)

- A release whose pods served traffic is recorded `live` and then `deactivated` when the newer one serves, the same as an ordinary replacement. Only a release that never served closes `canceled`.
- Either stamp `activeRevision` when the revision's pods become Ready (the moment the Service routes to them), or have the operator record a "served" fact for the generation before it abandons it, and let `supersededDeployStatus` accept that fact.
- The Events feed should then show A's `deploy_ended` as `succeeded`, not `canceled`.
- Test: an image release whose Ready pods exist, superseded before the `activeRevision` stamp, ends `live` → `deactivated`. A release superseded before any pod is Ready still ends `canceled`.

**Render:** a newer deploy cancels one still in progress, but Render shifts traffic only when a deploy goes live. So on Render a canceled deploy never served. The bex record must keep that meaning.
