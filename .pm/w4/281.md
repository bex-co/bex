# Auto-Deploy keeps an old value after receiving newer saved settings

Why: the dashboard can show Off while auto-deploy is enabled, and its stale editing baseline makes the current setting appear unchanged.

**Severity:** major, misleading saved deployment policy. **Estimate:** 55m (bounded row change 10m, shared caller review 10m, behavior regressions 20m, simplify and live closeout 15m). **Status:** open. Source: continuous functional QA a312, 2026-10-12 Pacific / 2026-10-13 UTC, normal helper login using muse.env, w4. Diagnosis source `fd9adc6a3` on main; deployed revision unobserved. Filing only.

## Reproduction

Owned Free image web `qa-20261012-a312-autodeploy` / `srv-db6nsmp5i38c73fd5opg` initially becomes Live/rev-1 at **00:42:21.905625 UTC** and serves `qa-a312-original\n` with HTTP200. Stage public Git `https://github.com/bex-co/bex` / main through Source → Edit; source save retains the serving artifact and opens no new deploy. Auto-Deploy initially shows Off.

1. Load Settings in tabs A and B. Leave A's Auto-Deploy row untouched.
2. In B, Edit Auto-Deploy → On Commit → Save changes. Actual SetAutoDeploy at **00:43:57.285 UTC** returns true.
3. Bring A to the foreground so its normal poll runs. Its actual Server response at **00:44:13.328 UTC** returns `autoDeploy:true`; A still shows **Off** at **00:44:28.652 UTC**. A second response at **00:44:44.045 UTC** also returns true.
4. A → Edit still shows Off and Save changes disabled at **00:45:03.370 UTC**. Cancel/full reload shows the correct On Commit value. This is a stale saved baseline, not merely an unsubmitted draft.
5. With A freshly loaded On Commit, B → Off → Save returns false at **00:45:08.056 UTC**. A receives false at **00:45:36.879 UTC**, but at 390×844 still shows **On Commit**, with Save disabled. Choosing Off enables Save even though Off is already stored; Cancel restores stale On Commit, while reload restores Off (**00:46:28.715 UTC**).
6. Start from that fresh **390px Off** page. B → On Commit saves true at **00:46:55.341 UTC**; A's response at **00:46:59.256 UTC** returns true, yet A still shows Off at **00:47:08.165 UTC**. Repeat is independent of the first page load.
7. B successfully restores Off at **00:47:35.085 UTC**. The final read confirms false, Running/rev-1 and exactly the original Live deploy; the public endpoint still serves the same HTTP200 marker. No Git push was induced and no webhook deployment behavior is claimed.

Expected: an untouched row displays the latest saved server value after a successful poll; entering Edit starts from it; Cancel returns to it; genuinely edited drafts survive a read. Actual: the parent's local copy pins the old saved value through polling and Cancel until a full reload.

## Cause and bounded fix

- `dashboard/src/features/services/components/build-deploy-section.tsx:159,180–194` initializes `autoDeployOn` with `useState(autoDeploy)`, uses that copy for the row value, and changes it only for this component's saves. There is no prop synchronization.
- Producer/consumer: `service-detail-layout.tsx:44` owns the Server poll; `hooks/use-server.ts:51–82` reads that document; `common/lib/polling.ts:11,47–64` supplies the 30-second settled cadence. Settings `routes/services.$serviceId.settings.tsx:84,200–214` consumes the same cache with polling disabled and passes the saved boolean to BuildDeploySection. Actual captured responses prove reads arrive; adding another poll or refetch would not clear the local state.
- `editable-field-row.tsx:139–166` already separates persisted `value` from an editing draft, initializes on Edit, dirty-compares against value, and returns to value on Cancel. It receives the wrong baseline from the parent. Keep this shared component unchanged.
- Installed **React/React DOM 19.2.3**: `react-dom/cjs/react-dom-client.development.js:8264–8294` initializes hook state only at mount; its update dispatcher `:26505–26512` uses the existing reducer state rather than a new initializer. This matches both reload controls.
- Installed **Apollo Client 4.1.3**: `use-auto-deploy.ts:26–54` saves the boolean; the actual mutation returns `Service/id/autoDeploy`. The shared cache config has no Service key override (`common/apollo/cache.ts:6–13`); default normalization keys that result by typename/id. Successful normalized mutation and Server reads can update the prop without resetting the separate local copy.

**Fix:** remove the redundant optimistic `autoDeployOn` state and its setters from this row. Bind value to `autoDeploy ? "commit" : "off"`; onSave returns the existing `setAutoDeploy(serviceId, value === "commit")` result. The child keeps the chosen draft while busy/editing, the accepted mutation publishes the saved boolean, failure keeps the draft for retry and Cancel uses the latest persisted prop. Preserve current disabled selection, permission/busy controls, Off/On Commit vocabulary and truthful push-delivery hint. Do not change API contracts, global Apollo policy, polling cadence or backend auto-deploy behavior.

**Pre-settle:** continue showing the last authoritative saved value until newer data arrives; an open draft continues showing its own selection. A pending save stays busy. Errors remain errors; do not set the policy from a failed response or equate timeout with a completed save.
