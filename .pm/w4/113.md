# bex's MCP tells every agent it is operating a "Render workspace" — 180 of 188 tools, one constant

Why: the consumer of an MCP tool schema is an LLM agent deciding what product it is driving, and the only product-identity string in bex's schemas names the wrong product — so an agent that reads it is being told, on almost every tool, that the workspace belongs to a competitor's platform; it is a one-line fix with no parity argument holding it in place.

Found by live `/qa-find-bugs` 2026-09-21 pass 117 (w4-targeted, `muse.env` credentials), driving `https://api.bex.co/mcp` over `client_credentials` with a throwaway API key, since revoked.

## What the surface says

```
tools/list  →  188 tools
  180  carry  workspaceId.description =
         "The ID of the Render workspace to use. Reuse the workspaceId the user confirmed from list_workspaces."
   35  carry a description ending "bex extension over Render's MCP."
    2  mention Render nowhere at all  (list_workspaces, preview_workspace_invite)
```

The surface is internally inconsistent about which product it is: the 35 **descriptions** are bex correctly *explaining its relationship to* Render ("bex extension over Render's MCP", "Tracks Render's …"), while the 180 **schemas** assert the caller's workspace *is* a Render workspace. The first is useful context; the second is a mislabel.

## Root cause

`lego/backend/internal/api/mcp_workspace.go:32`

```go
const mcpWorkspaceIDDescription = "The ID of the Render workspace to use. Reuse the workspaceId the user confirmed from list_workspaces."
```

One constant, applied by `mcpWorkspaceMiddleware` to every tool that is not caller-scoped — the 8 exceptions are listed right below it in `mcpCallerScopedTools`, which is why 180 of 188 carry it.

**No parity rationale holds it in place**, checked rather than assumed:

- The constant carries **no comment**, unlike this codebase's deliberate Render divergences, which are consistently documented at the site.
- The pinned upstream contract `lego/backend/internal/api/openapi/render-mcp-tools.json` (22 tools) does **not** contain the string — `'The ID of the Render workspace to use' in json.dumps(...)` → `False`. That file records which tools upstream *registers*, for the ADR018 parity classification; it does not pin descriptions, so nothing requires byte-identical wording here.
- `grep -rn "Render workspace" --include='*.go' lego/` → **1** hit, this constant. It is bex's own text, not inherited.

## Fix

Say `bex workspace`. Keep the second sentence — `list_workspaces` is a bex tool and the advice is good.

The 35 "bex extension over Render's MCP" descriptions should **stay**: they tell an agent something true and useful about compatibility. The distinction worth writing into the change is that bex may *refer to* Render when explaining compatibility, and must not *call itself* Render. Worth a line in `docs/ADR018-render-parity.md` next to the MCP rows so the next tool description lands on the right side of it.

Estimate: ~20m including the ADR line and a test that no MCP tool schema names Render as the caller's own platform.
