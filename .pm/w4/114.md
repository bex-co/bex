# MCP cannot create an image-backed service at all: the schema requires two fields the server refuses

Why: `image` is a documented bex extension to `create_web_service`, and it is unreachable — omitting `buildCommand`/`startCommand` fails schema validation, supplying them fails a business rule, and no third value exists; REST and GraphQL create the same service happily, so an agent is the only caller locked out of a supported service type.

Found by live `/qa-find-bugs` 2026-09-21 pass 118 (w4-targeted, `muse.env` credentials), driving `https://api.bex.co/mcp` with a throwaway API key, since revoked.

## The deadlock, both halves measured

```
tools/call create_web_service
  {workspaceId, name, runtime:"image", image:"docker.io/traefik/whoami:latest", plan:"free", port:8080, envVars:[…]}
→ isError: validating "arguments": validating root: required: missing properties: ["buildCommand" "startCommand"]

tools/call create_web_service
  …same, plus buildCommand:"IGNORED-BY-BEX", startCommand:"IGNORED-BY-BEX"
→ isError: bad request: prebuilt image services cannot declare buildCommand; remove it or deploy from repo instead
```

No value satisfies both: the schema rejects their absence, the handler rejects their presence.

The same service over REST, without those fields, in the same minute:

```
POST /v1/services
  {name, ownerId, type:"web_service", image:{ownerId, imagePath:"docker.io/traefik/whoami:latest"},
   serviceDetails:{runtime:"image", plan:"free"}}
→ 201  srv-daofvpp2dbts73fi2m1g
```

GraphQL `createService(runtime:"image", image:…)` needs neither field either — it is how every image fixture in this QA loop has been created.

## Root cause

`lego/backend/internal/apps/mcp.go:184-186` — three fields on `createWebServiceArgs` carry no `,omitempty`, so the generated JSON schema marks them required:

```go
Runtime      string `json:"runtime"      jsonschema:"Render runtime: node, python, go, rust, ruby, elixir, or docker"`
BuildCommand string `json:"buildCommand" jsonschema:"command used to build a native-runtime service; ignored for docker"`
StartCommand string `json:"startCommand" jsonschema:"command used to start a native-runtime service; ignored for docker"`
```

The two command fields' own descriptions say they are **ignored** for non-native runtimes, and the schema then requires them.

**This is inherited parity that stopped fitting once bex extended the tool.** The comment directly above the struct (`mcp.go:168-172`) says it plainly: _"name/repo/branch/plan/envVars track Render's tool; **image**/port/replicas are **bex extensions** (Render's tool is git-only and has no port/replicas) … Runtime/buildCommand/startCommand use Render's native contract."_ And the pinned upstream contract agrees:

```
lego/backend/internal/api/openapi/render-mcp-tools.json → create_web_service
  required: ["buildCommand", "name", "runtime", "startCommand"]
  args:     [autoDeploy, branch, buildCommand, envVars, name, plan, region, repo, runtime, startCommand, workspaceId]
  'image' in args: False
```

Upstream's required set is coherent **because upstream is git-only**. bex added the `image` path and kept the required set verbatim, so the extension is blocked by a rule that only makes sense for the path it does not take.

## Fix

Make the three fields conditionally required: required for a repo build, optional (and refused, as today) for `runtime: image`. JSON Schema expresses this with `anyOf`/`if-then`, which this codebase already uses for Blueprint validation (`w4/m102` made bex's `anyOf` handling discriminator-aware, so the machinery and the lesson both exist).

**Do not simply drop them to `omitempty`** — that would silently weaken the git path, where a missing `startCommand` is a real error worth catching at the schema. And check the sibling tools in the same pass: `create_cron_job`'s pinned upstream entry has the identical `required: ["buildCommand", "name", "runtime", "schedule", "startCommand"]`, and bex's cron tool also accepts `image`, so it is very likely to have the same deadlock — untested this run.

Estimate: ~45m including the cron sibling and a test that every service type bex documents as image-capable can actually be created over MCP.

## Unverified this run

- `create_cron_job`, `create_private_service` and `create_background_worker` were **not** probed; the cron one is flagged above from its pinned contract, not from a live call.
- Whether the `port` extension has a parallel problem (upstream has no `port`) was not tested.

## Also checked this pass, and found correct

- **MCP error shapes are precise and keep the classes apart** — the discipline this board asks for:
  - unknown service → `app not found`
  - unknown workspace → `cannot access workspace tea-not-a-real-workspace: forbidden` (forbidden, not "not found" — no existence oracle)
  - unknown tool → JSON-RPC `-32602 unknown tool "no_such_tool_qa"`
  - schema violation → names exactly which properties are missing
- **Every failure came back as `isError: true` with a readable message**, not a transport-level 500.
