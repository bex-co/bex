# 422 — An environment variable over 128 KiB is accepted, and every deploy that carries it fails with `exec …: argument list too long`

Why: the kernel refuses to start a process whose environment holds a single string over `MAX_ARG_STRLEN` (131072 bytes). bex only checks the 512 KiB aggregate, so it saves a value that guarantees the service's next instance can never start. The deploy then fails for a reason the API never states.

**Severity:** minor (an edge case, but the outcome is a service that cannot be redeployed until the value is removed, and nothing says why). **Estimate:** ~30m. **Source:** live `/qa-find-bugs w4` loop run 8066, 2026-10-27 UTC (`muse.env`, `bex-canary`, pin `b4726243e74f`), REST through the run's session jar. Owned fixtures `evg-dbg1bn5n83uc738uu87g` and `srv-dbg1bssd3d3c73caqca0` were deleted (`GET` → 404).

## Probe

1. `PUT /v1/env-groups/{grp}/env-vars/BIG256 {"value": "v"×262144}` → **200** (32 KiB → 200; 1024 KiB → 400 "total environment variable size limit of 524288 bytes exceeded"; 4096 KiB → 413 body limit).
2. Free image web service (`traefik/whoami:v1.10.3`) → live. `POST /v1/env-groups/{grp}/services/{srv}` → 200, then `POST /v1/services/{srv}/deploys` → `update_in_progress` for 7 min.
3. Service logs, type `app`, the new instance at 03:16:00: **`exec /whoami: argument list too long`**. The old instance kept answering `200` throughout (zero-downtime held).
4. The deploy finally ended `update_failed` with `failureReason: "image metadata request returned status 429"` (the Docker Hub throttle, w4/m243/t008), which hid the real cause. Events also show `server_failed {"reasonCode":"readiness_failed"}`.

## Root cause

`lego/backend/internal/secrets/service.go:857-873` `envMapWithinQuota` enforces 500 keys and a 512 KiB **aggregate** (`maxSecretMapBytes`), but no per-value bound. Service env vars and env groups share it. Linux execve refuses any single `KEY=value` string over 131072 bytes (`MAX_ARG_STRLEN`), so any value over about 128 KiB minus the key length is unrunnable.

## Fix (target behavior)

- Refuse at write any env var whose `KEY=value` exceeds 131072 bytes (or a rounder 128 KiB cap) with a coded 400. Something like `ENVIRONMENT_VARIABLE_TOO_LARGE` with `params: {key, maxBytes}`, naming the limit and pointing at secret files for large payloads.
- Apply it on every writer: service env-var PUT/PATCH/replace, env-group writes, create bodies, GraphQL, MCP and Blueprint apply/validate (`envVars[N].value`).
- Adjacent, worth a check in the same change: the per-set 512 KiB caps apply to the service's own vars and each linked group separately, so a service plus several groups can exceed the kernel's ~2 MiB `ARG_MAX` for the whole environment and hit the same `E2BIG`. Either cap the merged environment at link and deploy time, or document why it can't happen.
- When an instance's start fails with `argument list too long`, the deploy's failure reason should say so (it is classified today only as `readiness_failed`).

## Tests

- A value of exactly 131072 − len(key) − 1 bytes is accepted; one byte more is refused on each writer.
- A Blueprint with an oversized `value` is refused at validate.
- The existing aggregate checks are unchanged.

**Unverified:** Render's own per-value limit (Render's containers are subject to the same kernel rule); the merged-environment case (service + groups > 2 MiB) was reasoned about, not probed. **Dedupe:** no item mentions `argument list too long`, `MAX_ARG_STRLEN` or a per-value env limit. The confounding 429 is already w4/m243/t008. No `DO_NOT_DO.md` conflict.
