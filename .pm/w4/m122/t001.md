## Objective

Pick how the feed learns that a verb failed, and write the decision down before any code moves. The two candidate mechanisms have different blast radii and different failure modes, and the rest of the milestone depends on which one is chosen.

## Context

- **Option A — carry an operation outcome on the audit row.** `core.AuditEvent.Outcome` today is `allowed`/`denied`, an authorization verdict set in `Base.emit` (`lego/backend/internal/core/audit.go:918-933`) at authorize time, before the verb body runs. Adding a real outcome means the row is written (or amended) after the verb returns, which touches every audited write path — the widest change, but it fixes all 48 `eventTypes` entries at once and keeps the audit log's "who attempted what" record intact.
- **Option B — excuse the intent verbs and record facts instead.** Exactly what `w4/m118` did for the three cron verbs: drop the verb from `eventTypes`, add it to the excused list with the reason, and emit a fact at the moment the state actually changes. Narrow and precedented, but it has to be repeated per verb, and it needs a fact emitter for each — `allFactTypes` (`events/service.go:370-396`) has no domain types today.
- `Base.emit`'s contract note ("audit recording must never fail the verb it's recording") constrains Option A: the outcome must not make the audit write block or fail the operation.
- The no-op case is the discriminator. `addCustomDomain` on an already-pending claim returned **200** in the live evidence while changing nothing. An outcome flag that only distinguishes error from success still mints an event there; a fact emitted at the point of change does not.

## Steps

1. Write both options out with their blast radius: for A, the count of call sites that would need the deferred/amended write; for B, the number of verbs needing a fact emitter.
2. Decide, and record the rejected option and why — in the comment block above `eventTypes` (`events/service.go:279-307`), which already carries this kind of reasoning for `w4/m118`.
3. State where each adjacent class lands (denied, refused, failed, no-op) — the milestone README lists them; the decision must answer all four.
4. If Option A: define whether the outcome is a new field or a reuse of `Outcome`, and what an older stored row without it projects to.
