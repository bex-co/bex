## Objective

The run that `TriggerCronRun` returns must be readable as `pending` from the moment the API acknowledges it, not only after the operator writes `status.runs`. Today `GET …/runs/{id}` answers 404 and the list omits the run for 2.6–9 s (README P1).

## Context

- `lego/backend/internal/apps/service.go:4071-4104` `TriggerCronRun` derives the run ID from `ManualCronRunJobName(app, runAt)` and patches `spec.runAt`.
- `ListCronRuns` (`:4107-4119`) and `GetCronRun` (`:4122-4133`) read only `a.Status.Runs`, through `cronRunViews` and `cronRunByID`. So does `pendingCronRun` (`:4174-4181`).
- `AppView.Runs` and `LastSuccessfulRunAt` are built at `service.go:1165-1166`.
- The operator-side handling of `spec.runAt` is in `lego/operator/internal/controller/app_controller.go` (`convergeCronRuntime`, `manualRunSettled`, `manualRunHandled`).
- GraphQL `startedAt` and `finishedAt` are `gqlutil.StrField`s (`graphql.go:633-634`), which answer `""` for an empty value.

## Steps

1. Add one shared read model in `apps/service.go`. Wherever `status.runs` has no entry naming the `spec.runAt` request's Job, and that request is not settled, it adds the request as a `pending` run.
2. Route `ListCronRuns`, `GetCronRun`, `pendingCronRun` and `AppView.Runs` through it. Keep the newest-first order, and keep cursors stable on the `crr-` ID.
3. A pending run that hasn't started carries no `startedAt`. GraphQL `startedAt` and `finishedAt` answer `null` instead of `""`, and REST omits them.
4. `LastSuccessfulRunAt` never counts the request entry.

- [ ] Unit test: right after `TriggerCronRun`, before any operator status write, `GetCronRun(X)`, `ListCronRuns` (X first) and `AppView.Runs` all return X as `pending` with no `startedAt`.
- [ ] Unit test: once the operator writes X's status entry, there is exactly one X, and it carries the operator's fields.
- [ ] GraphQL `cronJobRun` answers `startedAt: null` for that pending run.
- [ ] An unknown ID and another service's run ID still answer `404 CRON_RUN_NOT_FOUND`.
