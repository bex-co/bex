# 502 — Response-time percentiles are bucket-interpolation artifacts for any service faster than 100 ms: p50, p95 and p99 always read exactly 50, 95 and 99 ms, because Traefik runs with its default histogram buckets

Why: the Metrics page and `GET /v1/metrics/http-latency` tell every owner of a healthy, fast service that half its requests take 50 ms and 5% take 95 ms or more, when the real figures are about 4 ms and 20 ms, so the response-time chart cannot show a regression, an improvement or a slow endpoint until latency passes 100 ms.

- **Source / severity / estimate:** live `/qa-find-bugs w4` round, 2026-11-05 ~17:09 UTC (`muse.env`, workspace `bex`, deploy pin `cc3c51e12952`); **major** (a headline observability number is wrong for the common case and looks plausible, so nobody questions it; no data lost); ~40m for the config change plus a verification pass, longer if the Loki-based alternative below is chosen.
- **Probe** (own throwaway Free web service `qa-20261105-met`, `ghcr.io/traefik/whoami:latest`, deleted afterwards, 204):
  1. 12 requests, one per second, `curl https://qa-20261105-met.onbex.co/qa-metrics-probe` from outside the browser, 17:06:34–17:06:57 UTC, all `200`.
  2. After 100 s, the true server-side duration of each request from the ingress access log (`GET /v1/logs?…&resource=<id>&text=qa-metrics-probe`, the `Duration` field in nanoseconds), sorted, in ms: `2.28 2.79 2.99 3.27 3.42 3.79 3.93 4.71 7.12 9.30 9.79 19.50`. True **p50 = 3.79 ms, p95 = 19.50 ms, p99 = max = 19.50 ms**.
  3. `GET /v1/metrics/http-latency?resource=<id>&startTime=<now-15m>&endTime=<now>&resolutionSeconds=60&quantile=<q>`:

     | `quantile` | API value | True value (step 2) |
     | --- | --- | --- |
     | 0.5 | **50.0 ms** | 3.79 ms |
     | 0.95 | **95.0 ms** | 19.50 ms |
     | 0.99 | **99.0 ms** | 19.50 ms |
     | 1 | **100.0 ms** | 19.50 ms |

  4. The same exact `0.1 × quantile` pattern appeared earlier on the long-running service `srv-dbg5uqkd3d3c73caqn80` (`quantile` 0.5 → `0.05`, 0.95 → `0.095`, 1 → `0.1`; see w4/480's table), so it is not specific to the probe service.
  5. Control: the request **count** for the same window is exact: `GET /v1/metrics/http-requests?…&aggregateBy=statusCode` sums to 12.00 and the access log has 12 lines, so only latency is affected.
- **Root cause (read, with one part inferred from the output):**
  - `lego/backend/internal/metrics/source.go:512` builds `histogram_quantile(<q>, sum by (le) (rate(traefik_service_request_duration_seconds_bucket[…])))` (router variant at `:540`). That is a standard Prometheus estimate: it finds the bucket the quantile falls in and interpolates **linearly inside that bucket**.
  - `deploy/gitops/base/values/traefik.values.yaml:179-183` enables Traefik's Prometheus metrics (`entryPoint`, `addEntryPointsLabels`, `addServicesLabels`, `addRoutersLabels`) and sets **no `buckets`**, so Traefik's built-in default applies: upper bounds 0.1, 0.3, 1.2 and 5.0 seconds (and `+Inf`).
  - Every request faster than 100 ms therefore lands in the first bucket `(0, 0.1]`. With all observations in that bucket, interpolation returns `0.1 × q` for every quantile, which is exactly the table above. The estimate carries no information about where inside 0 to 100 ms the requests really are.
  - I did not read the live `/metrics` scrape, so the default bounds are inferred from the exact `0.1 × q` result plus Traefik's documented default; the first thing to check is the `le` label set on `traefik_service_request_duration_seconds_bucket` in Prometheus.
- **Fix (target behavior):** latency percentiles for a service that answers in a few milliseconds are within one bucket width of the truth, i.e. a 4 ms service reads in the single-digit milliseconds and a 20 ms service reads about 20 ms.
  - **Config (small):** set Traefik's `metrics.prometheus.buckets` (the chart value; confirm the key against the pinned chart's schema) to a set with resolution below 100 ms, for example `0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10`. No backend code change is needed, since `source.go:512` already aggregates by `le`.
  - **Consequences to check in the same change:** the first scrapes after the rollout have new `le` series, so a latency window that straddles the rollout mixes old and new buckets and is wrong for one range-length; series count per (service, code, method) goes from 5 to 12 `le` values (about 2.4×), so look at Prometheus memory and retention before and after; the Loki-backed request source (`lokisource.go`) does not use these buckets and is unaffected.
  - **Alternative (larger):** compute latency from the access log's exact `Duration` through Loki (`quantile_over_time(… | unwrap Duration …)`), which is exact rather than bucketed and is what w4/m175 already uses for request counts. Prefer the config change first; this is a follow-up if per-request accuracy is wanted.
- **Blast radius:** one production caller builds the latency query (w4/214 counted one `sumRate` caller, `source.go:424-434`; the router variant is `:540`); REST (`/v1/metrics/http-latency`), GraphQL, MCP `get_metrics` and the dashboard's Response-time chart (p50/p95/p99 picker) all read it, so one config change fixes all four. Regression checks: the request-count series, CPU and memory are untouched; a service whose real latency is above 100 ms (for example 400 ms) must keep reading in the right bucket range.
- **Adjacent classes:** a service with no traffic in the window keeps returning an empty series (not `0`); `quantile` range validation (w4/488) is unchanged; the metrics API's 400/404 behavior is unchanged.
- **Unverified:**
  - The live bucket bounds (see Root cause), and Prometheus headroom for 2.4× series.
  - Static sites and cron jobs: their latency source was not probed.
  - A second oddity from the same probe, **not** part of this note: the latency point's timestamp was `17:07:42`, off the 60 s grid, while the request-count points of the same request were on it (`17:07:00`); cause not traced (w4/484 is the related grid-anchoring item).
  - Whether Render's own percentile figures for sub-100 ms services are exact; I did not measure Render.
- **Render:** Render's Metrics page reports real p50/p95/p99 response times for fast services; a flat 50/95/99 ms line would be an obvious defect there.
- **Dedupe:** w4/214 (done) is the rate lookback window for the same query; w4/m108 and w4/m175 (done) are count semantics; w4/480 and w4/488 are the `quantile` parameter range and show this artifact in their tables without naming it. No open item covers bucket resolution. Nothing in `.pm/DO_NOT_DO.md` applies. The fix is not on `main`.
