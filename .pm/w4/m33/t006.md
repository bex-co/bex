## Objective

Four workflows accept `workflow_dispatch`, check out the event-selected ref, and then run branch-controlled scripts with production credentials. Anyone who can dispatch can pick their own branch.

## Context

- `.github/workflows/deploy.yml` — `workflow_dispatch: {}`, workflow-level `contents: write` + `packages: write` + `id-token: write`; `build-and-deploy` gates only on `check-supersession`, never on `github.ref`.
- `.github/workflows/app-cluster.yml` — `HCLOUD_TOKEN` + `BEX_SSH_PRIVATE_KEY` (fetches the production kubeconfig).
- `.github/workflows/openbao-restore-drill.yml` — `BAO_ROOT_TOKEN` + the three Shamir unseal keys.
- `.github/workflows/snapshot.yml` — `HCLOUD_TOKEN`.
- Calibration: dispatching requires repo write, so this is a privilege boundary between "can push a branch" and "can reach production", not an unauthenticated hole. Cheap to close regardless.

## Steps

1. Add `if: github.ref == 'refs/heads/main'` to every job that touches a production secret (or gate the whole workflow at the job level where all jobs are credentialed).
2. Prefer a main-only GitHub **environment** with required reviewers for `deploy.yml`'s `build-and-deploy` and `openbao-restore-drill.yml` — that is repository-enforced rather than expression-enforced.
3. Leave credential-less validation jobs (the three test suites, `secret-scan`) dispatchable from any ref.

## Acceptance criteria

- [ ] Dispatching each workflow from a non-main ref skips every credentialed job before checkout or secret access.
- [ ] The three test-suite jobs still run from any ref (they gate PRs).
- [ ] `docs/ADR019-infra-credentials.md` records the CI trust boundary.

## Out of scope

- Pinning `actions/checkout` to an immutable SHA of the reviewed commit — the report suggests it, but with a main-only gate the ref is already reviewed; note the residual (a race between dispatch and a new push to main) rather than building SHA promotion.
