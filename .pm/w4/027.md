# GetApp/AuthorizeLabeled has the same redundant-resolution shape AuthorizeApp's collision loops had before w4/m30

← filed by w4/m30/t005's `/simplify` pass (altitude review), 2026-07-16.

`w4/m30` hoisted `AuthorizeApp`'s acting-workspace resolution above its three name-collision candidate loops via `resourceWorkspaceFor(ctx, acting, actingErr, labels)` (`lego/backend/internal/core/base.go`), cutting N colliding candidates down to exactly one `Workspace.Tenant` store query (asserted by `TestAuthorizeAppCollisionFallbackResolvesActingWorkspaceOnce`).

`GetApp` (`base.go:769-822`, called by `AuthorizeLabeled` at `base.go:846-847`) has the identical shape — three loops over candidate Apps (byID, direct-name, `LabelServiceName` collision fallback), each iteration calling `AuthorizeLabeled(ctx, relation, labels)`, which itself unconditionally calls `resolveWorkspace(ctx)` on every invocation. For N Apps colliding on `LabelServiceName` reached via `GetApp` (the same "two workspaces share a name" scenario, a real reachable path), this still costs N redundant `Workspace.Tenant` round trips — the same inefficiency `AuthorizeApp` had before this milestone.

Left out of `w4/m30`'s scope deliberately: `t003` named only `AuthorizeApp`'s loops, and `GetApp`/`AuthorizeLabeled` is a distinct call path with its own tests — extending the fix there would have been scope creep beyond what was reviewed/tested for this milestone.

Fix: either give `AuthorizeLabeled` a pre-resolved variant mirroring `resourceWorkspaceFor` and thread it through `GetApp`'s three loops, or (better, per the altitude review's suggestion) consider a more general fix — memoizing `resolveWorkspace`'s `(acting, err)` pair once per request context (e.g. a `sync.Once`-guarded field, or a context-stashed value on first resolution) so any current or future collision-prone call site benefits without per-call-site plumbing.
