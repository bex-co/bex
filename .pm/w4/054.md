# Logs query returns "internal error" for an inverted time range (startTime > endTime) — the logs sibling of w4/053

Why: like the metrics query (`w4/053`), the logs query validates most bad input cleanly but not an inverted time range, so `startTime > endTime` surfaces as the opaque "internal error" instead of a bad-request — no actionable message, a misleading 5xx-class error, and client-caused entries in the server error log. Same fix (a `start < end` guard) as 053, different code path; worth batching.

Source: live QA 2026-09-07, `$qa-find-bugs w4` pass 19 (error-taxonomy fuzzing; sibling of `w4/053` metrics and `w4/052` services-id).

## Symptom (reproduced on prod)

Authenticated GraphQL `logs(resource,type,startTime,endTime,limit)` on `srv-da40m1qii7bs73drbqlg`, `type:"app"`:

| input | result |
| --- | --- |
| valid range | ✅ entries |
| `type:"notatype"` | ✅ `bad request: unknown log type "notatype" (want app|request|build|predeploy)` — **good validation** |
| `startTime:"not-a-time"` | ✅ `bad request: startTime: parsing time … cannot parse` — **good validation** |
| **inverted range** (`startTime` 06:00 > `endTime` 00:00) | ❌ `errors:["internal error"]` |
| `resource:"srv-!!"` (malformed) | ❌ `errors:["internal error"]` — **corroborates `w4/052`** (logs resolves the resource via the App-path helper) |
| `limit:-5` / `limit:1e8` | ✅ clamped (acceptable) |

Durable probe: body `{"query":"query L($resource:String!,$type:String,$startTime:String,$endTime:String,$limit:Int){logs(resource:$resource,type:$type,startTime:$startTime,endTime:$endTime,limit:$limit){timestamp message}}","variables":{"resource":"srv-da40m1qii7bs73drbqlg","type":"app","startTime":"2026-09-07T06:00:00Z","endTime":"2026-09-07T00:00:00Z","limit":20}}` → HTTP 200 `{"errors":[{"message":"internal error"}],"data":null}`.

## Root cause (code-verified on `main`)

`lego/backend/internal/logs/service.go` validates log type (`:270,:403`), pre-deploy/build exclusivity (`:277,:280`), live-tail constraints (`:340,:356`), the `MaxQueryHours` window cap (`:171-173`), and datastore-specific limits — all with `core.ErrBadRequest`. But there is **no `start < end` (Since < End) check** anywhere in the package (grep for a `Since`/`End` ordering comparison returns nothing; `:417`/`:420` are per-entry `t.Before(q.Since)`/`t.After(q.End)` result filters, not a range-direction guard). An inverted range therefore passes validation and reaches the Loki source (`lokisource.go`), whose query errors on `end < start`; that error is not `core.ErrBadRequest`, so `sanitizeGraphQLErrors` (`api/server.go:1328-1337`) redacts it to `"internal error"` (same mapping as `w4/053`).

**Control (load-bearing):** the same logs service returns proper bad-request messages for the neighbouring invalid inputs (unknown type, malformed time) — so the inverted-range omission is an inconsistent gap, not a design choice.

## Target behavior

An inverted time range (`startTime >= endTime`) must return a client-facing **bad-request** with a clear message (e.g. `startTime must be before endTime`), consistent with the logs endpoint's other validations and with the fix proposed for metrics in `w4/053`. A real Loki failure must still be `"internal error"` (redacted).

**Fix:** add a `start < end` guard (wrapped in `core.ErrBadRequest`) in the logs query validation path (`QueryLogs`, `service.go:460`, alongside the existing type/window checks) — and apply the identical guard in the metrics path (`w4/053`). Batch the two: both are the same missing check on two call sites.

## Blast radius

- GraphQL `logs`, REST `GET /v1/logs`, and `GET /v1/logs/subscribe` all funnel through `logs.Service.QueryLogs`/validation (one service, three surfaces), so one guard fixes all three. Postgres/Key Value log queries reuse the same `LogQuery` window — the guard covers them too.
- The malformed-`resource` → 500 half is **not** new here: it's `w4/052`'s App-path resolution reached via the logs query's resource lookup — fixing 052 fixes it. (Corroboration only; do not double-file.)

## Adjacent classes

- unknown type / malformed time → **bad-request** (already correct).
- inverted range → **bad-request** (the fix; currently "internal error").
- real Loki/upstream failure → **"internal error"** (must stay redacted).
- out-of-range limit → clamped (acceptable; unchanged).

## Render parity

Render returns a validation error for an inverted log time range, not a 5xx/opaque error. Parity applies across GraphQL + REST + subscribe.

## Severity

**Minor** — no data loss, no blocked journey (the dashboard sends valid ranges). Error-taxonomy/DX defect + client-caused server error-log noise.

## Unverified this run

- Only the **GraphQL `logs`** query was probed live (inverted range + malformed resource). REST `/v1/logs` and `/v1/logs/subscribe` share `QueryLogs` (code path) but were not probed.
- The inverted-range error originating in Loki (vs an earlier point) is inferred from the absent `start<end` guard + the observed "internal error", not stepped through.
