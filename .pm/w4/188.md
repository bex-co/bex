# w4/188 — REST create may drop an image service's `envSpecificDetails.dockerCommand`

Why: a Render-CLI/REST caller creating an Existing Image service with a Docker Command could get a service whose CMD override silently vanished — the same crash-loop m166 fixed for the dashboard.

Filed from the w4/m166 t003 parity check, 2026-10-04 (code reading, not a live repro).

- REST create maps `serviceDetails.envSpecificDetails.dockerCommand` onto `startCommand` only when `runtime` is `docker` (`lego/backend/internal/apps/rest.go:482-492`); for `runtime: image` it reads only `envSpecificDetails.startCommand`.
- REST update maps `dockerCommand` regardless of runtime (`rest.go:887-889`), so create and update disagree for the same field.
- Blueprints already accept `runtime: image` + `dockerCommand` (`blueprint_compiler_test.go:166`); MCP `create_web_service` documents `dockerCommand` as "applies only when runtime is docker" (`apps/mcp.go:204`).
- The dashboard (GraphQL `startCommand`) and `specFromCreate` accept an image Docker Command (`apps/image_create_test.go` `TestImageRuntimeAcceptsADockerCommand`).

Step 1: confirm against Render's public OpenAPI whether `envSpecificDetails` for `runtime: image` carries `dockerCommand`. If it does, accept it on REST create (and MCP) for `runtime: image` with the same one-spelling guard the docker branch uses, plus a regression test. If it does not, delete this note citing the spec.
