# w4/192 — Scaling "Recent Metrics" says "No limit configured" for every sleeping or suspended service

Why: the Scaling page tells a Free user their service has no memory/CPU limit, so utilization is "undefined". Meanwhile the Metrics tab for the same service shows real percentages against the plan's 512 MB / 0.1 CPU. Two surfaces disagree, and the false one sits next to the controls a user would use to change their limits.

Live 2026-10-04 UTC (`/qa-find-bugs` loop11, muse.env, `bex-canary`), read-only on the existing sleeping Free web service `hello-go` (`srv-daif6dsmg29s73d1umvg`):

- `/services/<id>/scaling` → Recent Metrics shows "Average Memory Utilization — No limit configured — percentage is undefined", and the same for CPU (`.playwright-mcp/qa-scaling-nolimit-1.png`).
- Control: `/services/<id>/metrics` for the same service shows Memory **0.5%** and CPU **0.1%**, each with a 4-point chart.
- API probe from the dashboard origin, 48 h window: `metrics(query:{filters:[{field:RESOURCE,values:[<id>]}], name:MEMORY|MEMORY_LIMIT|CPU_LIMIT, …})`. `MEMORY` returns 5 series with values across wake windows; `MEMORY_LIMIT` and `CPU_LIMIT` return `[]`.
- Workspace sweep, 6 h window: both other Free web services showed the same pattern (memory present, both limits empty). The three Free cron jobs returned limits (536870912 bytes, 0.1 CPU) because recent job pods exist.

Root cause:

- `lego/backend/internal/metrics/service.go` `resourceLimitMetric` (around 893-920) reads limits from the **current pods** (`AppPodsIn`) and emits one current-value point, so a scaled-to-zero service has none. This is documented as intentional for that verb.
- The Metrics tab already works around it with the server-side percentage read (w5/m90 t008; `dashboard/src/features/metrics/components/application-metrics-card.tsx:92-96,370-378`, `percentage: true`), whose points carry own-limit history.
- `dashboard/src/features/services/components/scaling-recent-metrics.tsx:49-59,82-87,140-152` never adopted that path. It still divides usage client-side by `latestValue(memory_limit|cpu_limit)` (`src/features/metrics/lib/series.ts:2-6`) and falls to `metrics.noLimitConfigured` whenever that is null.

Fix: make `AvgUtilizationSection` use `useMetrics(serviceId, "memory"|"cpu", {…window, percentage: true})` and average those percentage series. Keep "No limit configured" only for a truly limitless App, and show `metrics.percentageUnavailable` when usage exists but no percentage survived, exactly as `application-metrics-card.tsx` does.

- Test: a sleeping service with usage history renders a percentage chart, not the no-limit copy. A pending skeleton must match the ready layout.
- No backend change: `memory_limit`/`cpu_limit` stay current-pod reads (other callers rely on that), so the fix is global to this one card.

Unverified: whether the Scaling card also misreports during the seconds after a wake (not probed). Render: its Scaling page charts utilization for sleeping instances; n/a beyond that. Severity: minor (misleading copy, no data loss). Estimate: ~40m.
