# The three lifecycle action projections never consult the resource's suspended state, so `resume` reads `allowed` on a running resource and `suspend` reads `allowed` on a suspended one

Why: `serverActions`, `databaseActions` and `keyValueActions` compute exactly two preconditions — protection for `suspend`, billing for `resume` — and neither asks whether the resource is already in the state the verb would put it in, so a capability projection whose whole job is to tell a client which buttons do something reports the same three decisions in every state; the vocabulary term for this already exists and is used correctly two lines below, in the same function.

Found by live `/qa-find-bugs` 2026-09-21 pass 157 (w4-targeted, `muse.env` credentials), journeys 3 and 10. Fixtures `qa-20260921-web157`, `qa-20260921-cron157`, `qa-20260921-priv157` and `qa-20260921-kv157`, all deleted; workspace back to baseline.

## Live, on two resource types, in both states

**A web service** (`srv-dap063jbdpcs73f5ecg0`), driven through suspend and back:

```
state: phase Running,    suspended not_suspended
  serverActions → restart:allowed  suspend:allowed  resume:allowed
  resumeService(...)  → ACCEPTED, suspended stays "not_suspended"   ← no-op

suspendService(...) → ACCEPTED, suspended "suspended"

state: phase Hibernated, suspended suspended
  serverActions → restart:allowed  suspend:allowed  resume:allowed   ← identical
  suspendService(...) again → ACCEPTED, suspended stays "suspended"  ← no-op

resumeService(...) → ACCEPTED
state: phase Deploying,  suspended not_suspended
  serverActions → restart:allowed  suspend:allowed  resume:allowed   ← identical
```

**A key-value store** (`red-dap09rjbdpcs73f5ecj0`), same shape:

```
status creating,  suspended not_suspended → keyValueActions: suspend:allowed  resume:allowed
suspendKeyValue → ACCEPTED
status suspended, suspended suspended     → keyValueActions: suspend:allowed  resume:allowed
```

Three readings of `serverActions` across three distinct states produced byte-identical output, and two readings of `keyValueActions` across two states did the same. No precondition is ever reported.

## The control, in the same request and the same file

`deployActions` on the **same service** does carry preconditions, and correctly:

```
deploy:allowed
cancel_deploy:allowed/no_active_deploy
rollback:allowed/no_eligible_rollback_target
```

That is `w4/110`'s fix working — the note that established the rule this one breaks: a projection reporting `allowed` for a verb with nothing to act on binds a control that does nothing. And the vocabulary is not missing. `core/decision.go:129-143` defines it and says what it is for:

```go
// The bounded precondition vocabulary: why a PERMITTED action cannot execute
// right now. Empty means ready. …
	// The resource's current state does not admit the verb (e.g. suspended).
	PrecondSuspended = "suspended"
	// Nothing for the verb to act on right now.
	PrecondNoActiveDeploy           = "no_active_deploy"
	PrecondNoActiveRun              = "no_active_run"
	PrecondNoEligibleRollbackTarget = "no_eligible_rollback_target"
```

`PrecondSuspended`'s own comment — _"the resource's current state does not admit the verb"_ — describes this case exactly.

## Mechanism

`apps/actioncaps.go:67-70`:

```go
out := []core.ActionDecision{
    core.DecideAction(core.ActionRestart, operate, ""),
    core.DecideAction(core.ActionSuspend, operate, precond(func() string { return s.suspendPrecondition(ctx, a) })),
    core.DecideAction(core.ActionResume, operate, precond(billing)),
}
```

`suspendPrecondition` is protection only (`:95-97`, `core.ProtectionPrecondition(s.appProtected(ctx, a))`); `resume`'s is the billing gate only. Neither reads `a.Spec.Suspended`.

**And the correct pattern is eleven lines below, in the same function** — the cron branch does consult it:

```go
core.DecideAction(core.ActionCronRunNow, operate, precond(func() string {
    if a.Spec.Suspended { // TriggerCronRun's guard order: state, then billing
        return core.PrecondSuspended
    }
    return billing()
})),
core.DecideAction(core.ActionCronCancelRun, operate, precond(func() string {
    if _, ok := pendingCronRun(a); !ok { // CancelCurrentCronRun's scan
        return core.PrecondNoActiveRun
    }
    return ""
})),
```

So this is not a missing concept or a missing predicate — it is two decisions that were not given the check their neighbours have.

`grep -rn --include='*.go' "ActionCapabilities" lego/backend/internal/` returns four implementations. Three share the defect; one is the control:

| ------------------- | --------------------------------- | -------------------- | ------------------- | --------------- |
| `serverActions`     | `apps/actioncaps.go:67-70`        | protection           | billing             | **no**          |
| `databaseActions`   | `postgres/actioncaps.go:47-54`    | protection           | billing             | **no**          |
| `keyValueActions`   | `keyvalue/actioncaps.go:46-52`    | protection           | billing             | **no**          |

The two datastore projections are textually near-identical to each other (`suspendPre`/`resumePre` computed in one `if operate.Allowed()` block), so the fix lands the same way in both.

## Who consumes it

Not hypothetical — the dashboard renders a blocked reason straight from this field:

- `dashboard/src/features/capabilities/hooks/use-resource-actions.ts:33,96` carries `precondition` through.
- `dashboard/src/features/capabilities/locales/en.ts:57` and `zh.ts:50` already hold a string described as _"Blocked reason for suspended precondition"_ — so the UI is **already able** to render `PrecondSuspended`; it is simply never sent one for these two verbs.
- ADR087 / `w6/m136` are the governing decisions, and they scope these projections as the **mobile** action set — a client that binds a button's enabled state to `outcome` alone is exactly the consumer this was built for.

## Fix

Give `suspend` and `resume` the state check the cron verbs already have, in all three projections:

- **`suspend` on an already-suspended resource** → `core.PrecondSuspended`. The constant fits without extension, and its comment already licenses this reading.
- **`resume` on a resource that is not suspended** → needs a new term; there is no `not_suspended` in the vocabulary. Add one rather than overloading `PrecondSuspended`, whose meaning is the opposite.
- **Guard order matters and is already documented**: the cron branch records _"TriggerCronRun's guard order: state, then billing"_. Follow the same order so the projection and the verb refuse for the same reason — state first, then billing/protection.

**One compatibility point to state rather than discover.** `core/decision.go:126-129` says the vocabulary is bounded and that _"an unknown one reads as blocked on every client (fail closed)"_. So adding `not_suspended` makes an older client render the Resume button as blocked-for-unknown-reason on a running resource — which is the **safe** direction and arguably the desired one, but it is a behavior change for shipped clients and should be called out, not slipped in. The dashboard needs the matching `en`/`zh` locale strings in the same change or it will show an untranslated key.

Estimate: ~55m — three one-block edits, one constant, two locale strings, and tests for three types × two states. Sub-hour but only just; promote to a milestone if the implementer decides the vocabulary addition needs its own client-compatibility review.

## Unverified

- **`databaseActions` was read in code, not exercised.** The two live proofs are `serverActions` and `keyValueActions`. Postgres was not driven through suspend/resume this pass — a free database takes longer to settle and the two datastore projections are textually near-identical, so it was judged redundant. Whoever picks this up should still probe it, since "identical in shape" is an argument, not an observation.
- **Whether the dashboard's Suspend/Resume controls gate on state by a second route** was not checked. `w4/110` found exactly that for rollback — the dashboard gated it separately, which confined the exposure to non-browser clients. If the same is true here, the severity drops to CLI/MCP/mobile and the note should say so.
- **REST and MCP were not probed for these projections.** Only the GraphQL roots were read; whether the same decisions are exposed on the other two surfaces (and so need the same fix) is unconfirmed.

## One observation, deliberately not filed

Suspending a web service set `phase: "Hibernated"` — the same phase free-tier auto-sleep uses, so `phase` alone cannot distinguish "an operator suspended this" from "it fell asleep to save money". The `suspended` field does distinguish them (`suspended` vs `not_suspended`), and the activator already answers the two cases differently (`Retry-After: 3600` for suspended vs `5` for hibernated, `cmd/activator/main.go:229-246`), so no surface is actually lying and every consumer has what it needs. Recording it because "Hibernated" is a surprising word to see after clicking Suspend, and a future note about phase vocabulary should start from here rather than rediscovering it.
