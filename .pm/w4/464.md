# 464 — api.bex.co and dashboard.bex.co through Cloudflare stall for up to 60 s and intermittently return 525, while the origin load balancer answers in under a second

Why: every dashboard page load and API call goes through the Cloudflare proxy. For at least 20 minutes on 2026-11-03, they took 2–53 s, sometimes timed out, or failed with Cloudflare `525` (SSL handshake to the origin failed). The cluster served the same requests in milliseconds, so customers see a broken product while bex looks healthy.

- **Source / severity / estimate:**
  - Found by the live `/qa-find-bugs w4` loop, 2026-11-03 03:37–04:05 UTC, pin `0acc15714458`.
  - **Major**: no data loss, but the dashboard and API are unusable for long stretches.
  - ~45m to diagnose; the fix is probably configuration, not code.
- **Probe:** run from a client whose own path was healthy: 1.1.1.1 at 0.2 s, ping 20–30 ms. Repeat it:

  ```bash
  # through Cloudflare (proxied A/AAAA 104.21.29.76 / 172.67.148.151)
  curl -s -o /dev/null -w '%{http_code} ttfb=%{time_starttransfer}\n' https://api.bex.co/healthz
  # straight to the Hetzner LB (its IP is what ssh.bex.co resolves to: 49.12.20.236 / 2a01:4f8:c01e:3d1f::1)
  curl -sk -o /dev/null --resolve api.bex.co:443:49.12.20.236 -w '%{http_code} ttfb=%{time_starttransfer}\n' https://api.bex.co/healthz
  ```

  - **Through Cloudflare:** about 30 samples between 03:47 and 04:04 UTC took 0.26–46 s.
    - Two returned `525` after ~41–43 s, at 03:47 and 03:54.
    - Two got no response at all within 60 s (`000`): `api` at 03:56 and `dashboard` at 04:00.
    - `dashboard.bex.co/` took 3–53 s. The edge was `cf-ray …-SJC`.
  - **Straight to the LB, alternating with the requests above:**
    - IPv4: 18 of 18 returned 200 in 0.54–1.6 s, with TLS done by 0.4 s.
    - IPv6: 4 of 4 returned 200 in 0.54–0.63 s.
  - **Inside the cluster:** Traefik access logs for the same window show `api.bex.co` answered in 2–5 ms and `dashboard.bex.co` in 12–37 ms.
    - Both Traefik pods were up for 18 h, and both `bex-api` pods for 74 min.
    - All 12 nodes were Ready, and node CPU was at most 38%.
    - `bex-api` logged no errors or warnings in the last 40 min.
- **So the delay sits between the Cloudflare edge and the Hetzner LB**, not in Traefik, bex-api or the dashboard.
  - At the time, cloudflarestatus.com reported "Partial System Outage". The only degraded components it listed were SJO and SCL, not SJC.
  - So the cause may be external and transient. It may also be our side: Cloudflare's SSL mode or origin settings, or Hetzner LB limits on Cloudflare's source IPs. The LB uses proxy protocol on 80/443, per `infra/terraform/main.tf` (the `traefik` LB, health checks every 15 s, `use_private_ip = true`).
- **Cause unverified.** Next steps:
  1. Re-run the probe pair. If Cloudflare is still slow while the LB is fast, look at Cloudflare analytics for origin response time and 52x by colo.
  2. Check the zone's SSL mode and origin certificate. A 525 means the TLS handshake to the origin failed.
  3. Check the Hetzner LB metrics (open connections, connections per second, and whether targets flapped as unhealthy) for 03:30–04:10 UTC.
  4. Check whether Cloudflare's origin connections land on targets whose NodePort health check fails. With `externalTrafficPolicy=Local`, only the 2 Traefik nodes should be healthy targets.
  - If it cleared by itself and Cloudflare's incident log covers that window, close this note with that evidence.
- **Unrelated noise seen in the Traefik logs (not the cause):** repeated `Error configuring TLS … secret tea-d98210cbbpdc73dcrkvg-block-eden-mono-tls-blockeden.xyz does not exist`. A custom domain's certificate secret is missing. The direct-LB path is fast despite it.
- **Dedupe:** no open or done item mentions a 525 from the edge or Cloudflare-to-origin latency. `w4/m140` (done) was a 502 on a 7-day log search, which is a different path. No DO_NOT_DO item applies.
- **Cleanup:** read-only probes and read-only `kubectl get/logs/top`. Nothing was created, and no session was opened for this.
- **Still happening at 04:12–04:17 UTC, and worse** (re-probe, client ping 15–18 ms):
  - Through Cloudflare, `api.bex.co/healthz` returned `525` after 46 s, `502` after 48.6 s, then twice no response within 60 s. One request came back at 0.36 s.
  - Dashboard loads took 4–43 s.
  - Straight to the LB, 5 of 5 returned 200 in 0.62–1.08 s.
- **Tenant apps are not affected.** `*.onbex.co` hostnames are DNS-only: `beancount-forum.onbex.co` resolves straight to the LB (`49.12.20.236`) and has no `cf-ray` header. They answered in 0.54–0.61 s across 4 of 4 samples.
  - So only the Cloudflare-proxied `bex.co` hostnames stall: the dashboard, the API, and anything else orange-clouded.
- **Cloudflare status:** the only unresolved Cloudflare incident is "Cloudflare Container Issues" (since 04:12 UTC), which doesn't obviously match. Our stall started before it, by 03:47 at the latest.
- **Possible stop-gap (a user decision, not taken):** switch `api.bex.co` and `dashboard.bex.co` to DNS-only until the Cloudflare leg is fixed. That brings back sub-second responses, as the direct probes show. The cost: losing Cloudflare's WAF and bot protection, which currently answers `Python-urllib` with `1010`, plus Cloudflare caching, and exposing the LB IP for those hostnames. That IP is already public through `ssh.bex.co` and `*.onbex.co`.
