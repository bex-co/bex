## Objective

The one networking save that still restarts a store (the first enable) is announced before it happens on every surface. A Persistence Off store can't lose its data to it without the typed confirmation the persistence change already requires.

## Context

- Copy: `dashboard/src/features/keyvalue/locales/en.ts:617-619` `keyvalue.networkingHint` ("Internal access is unchanged."), plus `zh.ts`. The Postgres twin is `databases/locales/en.ts:793`, pending t001's verdict.
- Precedents: the Maxmemory card ("Saving restarts the store, so connections drop for up to a minute") and the Persistence dialog ("Delete all data and change persistence?" + `sudo clear key value <name>`). The protected-environment `confirm` echo is the API precedent.
- Panel: `dashboard/src/features/keyvalue/components/key-value-networking-panel.tsx`.

## Steps

1. Backend: when an `UpdateKeyValue`/`setKeyValuePublic` call would roll the pod (per t002, the first enable), refuse it without `confirm`, using a coded error that names the restart. With Persistence Off, the error also names the data loss. Accept a matching `confirm` on REST, GraphQL and MCP.
2. Dashboard: show the restart notice before Save when the save would trigger it. With Persistence Off, require the typed confirmation, then send `confirm`.
3. Reword `networkingHint` so it is true for every save it accompanies (en and zh). Keep the skeleton geometry identical (AGENTS.md).

## Acceptance criteria

- [ ] REST, GraphQL and MCP each refuse the restarting save without `confirm` (coded) and accept it with `confirm`. Non-restarting saves need no `confirm`.
- [ ] Dashboard tests cover the notice, the Off confirmation, and no prompt for a rule change while access stays on.

## Out of scope

- Changing the persistence or maxmemory flows.
