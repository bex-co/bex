## Objective

An external-access toggle that no longer restarts the store (t002) must not read `config_restart` either. Live (pass 0a57a8), every such save answered `status: config_restart` in its own PATCH response and on reads for 1–3 s, though uptime and the key prove nothing restarted. That misses the DoD's "never reads `config_restart`". A save that does restart must still never read a stale `available` (w4/m137).

## Context

- `lego/backend/internal/core/datastore_status.go:47-56` `DatastoreReadyStatus` answers `config_restart` whenever the Ready condition's `ObservedGeneration` trails `metadata.generation`. w4/m137 added that rule on purpose, to close the stale-`available` window before a restarting change rolls the pod.
- Since t002, an allowlist or `public` change bumps the generation but rolls nothing. The rule now over-reports until the operator observes the generation (about 2 s).
- Two callers: `keyvalue/service.go:235` (`kvStatus`) and `postgres/service.go:433` (`dbStatus`). The Postgres side has the same shape for its non-restarting writes (cause unverified live; no Postgres fixture this pass).
- The backend already knows which Key Value writes restart (`externalAccessRestarts`, `keyvalue/service.go:904`), and the operator knows which spec fields enter the pod template.

## Steps

1. Pick where the "this generation restarts" fact lives. For example, the operator records the last generation whose change rolled the pod (or the template hash it served), and status reads `config_restart` only while that generation is unserved. Or the backend stamps restart-requiring generations on write.
2. Apply it to `kvStatus`. Apply the same rule to `dbStatus` only if t001's Postgres verdict found non-restarting writes there.
3. Keep w4/m137's guarantee: a persistence, eviction, plan or first-enable change still reads `config_restart` from the PATCH response until the new pod serves.

## Acceptance criteria

- [x] On a store that has had external access once, `PATCH {"ipAllowList":[]}` and the re-add both answer `status: available`, and reads stay `available` at 1 s polling.
- [x] A Maxmemory Policy or Persistence Mode change, and a first enable, still read `config_restart` immediately and then `available` once served (w4/m137 regression test).
- [x] The tests fail on today's generation-only rule.

## Done 2026-10-19 (loopx w4)

- **Where the fact lives:** the backend stamps it on write. `keyvalue.UpdateKeyValue` records the generation a restart-free write lands at in `app.bex.co/restart-free-generation` (`markRestartFree`: only the name, the store's own allow-list or `public` changed, and turning access on does not add the listener; a spec-unchanged save marks nothing). `kvStatus` reads `available` while that is the only generation a Ready store has not observed (`restartFreePending`). The write is a merge patch locked to the resourceVersion it read (`patchKeyValueLocked`, re-read and retried on conflict), so the mark cannot land on a racing writer's generation.
- **The second window:** the live blip on an access flip is mostly the operator rebuilding the immutable connection Secret (phase `Provisioning`, reason `ConnectionSecretRebuilding`, a requeue of at least 1 s). That rewrite touches no pod, so the operator now leaves a serving store's Phase and Ready alone during it (`keyvalue_controller.go`); a store not yet serving still reports the rebuild. Connection info hands out the external URI only while `spec.public` is set, so the endpoint retired by turning access off is not shown during that pass.
- **w4/m137 kept:** a persistence or eviction change, a plan change, a first enable, or any generation the write did not mark still reads `config_restart` until observed.
- **Tests:** `TestARestartFreeChangeReadsAvailable` (status table: marked/unmarked, one or two pending generations, a stale mark; write table: allow-list empty and re-add marked, first enable and persistence change not marked; an unchanged save not marked), `TestARestartFreeMarkNeverLandsOnARacingWrite` (interceptor: a racing write with the same rules plus a plan change takes the generation, the save re-reads and does not mark it), `TestKeyValueConnectionSecretRebuildKeepsAServingStoreReady` (operator, serving and not serving), and a private store with a leftover `externalHost` gets no external URI (`TestConnectionInfoGatesImmutableCredentialRevision`). Each fails with its guard removed (mutation-checked: the status override, the no-op guard, the optimistic lock, the operator Ready guard, the `spec.public` URI guard).
- **Postgres (step 2):** t001 found Postgres external-access changes restart nothing (CNPG re-signs and reloads), so `dbStatus` likely over-reports the same way, but no Postgres fixture has shown it live and its writers differ. Split to [w4/364](../364.md) rather than shipping unverified behavior.
- **Live:** replayed in t007 after the deploy.
