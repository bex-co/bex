## Objective

A service linked before this change may hold its group refs in link order. That order changes only in a write that already mints a release its owner started: a deploy, a restart, a rebuild, or a Settings write that already rolls (never a rollback). The operator never reorders a spec, so no running service flips value without a deploy row. This is the concern ADR018 gave for keeping last-linked-wins.

## Context

- `FoldStagedGroupLinks` (`lego/backend/internal/rollout/grouplinks.go:122-128`) is already called by every writer that mints a release (ADR013 rule 3, w4/m239). It is the natural place to also sort the group refs.
- Group refs are release identity (w4/m239). Changing them outside a release would make the operator ship a release that no deploy row records.
- A rollback does not apply staged links (ADR013). It must not re-sort either: a rollback restores the old release's own order.

## Steps

1. Extend the release-minting fold so it also sorts the group refs into creation order with t001's helper. Rename it if that reads better, e.g. `PrepareGroupRefsForRelease`.
2. Leave the rollback path untouched.
3. Before the release, the Environment page shows the order the service runs, from `linkedEnvGroupIds`. Decide whether it also flags "the next deploy changes which group wins". If so, word it in en and zh and add it to t003. Otherwise note why not.

## Acceptance criteria

- [ ] Unit: an App whose spec lists `[B-env, A-env]` (B newer) keeps that order after a Save only write, a link of an unrelated group's staging, and an operator reconcile.
- [ ] Unit: after a manual deploy write it lists `[A-env, B-env]`.
- [ ] Unit: a rollback write leaves the order unchanged.
