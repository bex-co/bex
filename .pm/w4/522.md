# 522 — Credential-bearing API responses (Postgres `connection-info` with the password, env vars, Key Value `connection-info`) carry no `Cache-Control`, while the deploy-hook route already sends `no-store` for the same reason

Why: the Postgres connection-info answer contains the database password in clear (twice: `password` and inside `internalConnectionString`), and nothing tells a browser, extension or intermediary cache not to keep it. The API already treats this as a rule for the deploy hook; the secrets that matter more do not follow it.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 130, 2026-11-05 UTC (`muse.env`, `bex-canary`); **minor** (hardening gap; no cache was observed serving a secret); ~40m.
- **Probe:** read-only, signed in, `page.request.get` (so the real response headers are visible; a cross-origin `fetch` hides them). Response headers and, for the secret fields, shape only (values were not printed):

  | Request | Status | `Cache-Control` | `Pragma` | Body shape |
  | --- | --- | --- | --- | --- |
  | `GET /v1/postgres/<id>/connection-info` | 200 | none | none | `{"password":<64 chars>,"internalConnectionString":<URL with embedded password>,"externalConnectionString":"","psqlCommand":…}` |
  | `GET /v1/key-value/<id>/connection-info` | 200 | none | none | `{"internalConnectionString":…,"externalConnectionString":"","cliCommand":…}` |
  | `GET /v1/services/<id>/env-vars?limit=1` | 200 | none | none | `[]` for this service (no values to inspect) |
  | `GET /v1/owners`, `GET /v1/services?limit=1` | 200 | none | none | ordinary lists |
  | `GET https://dashboard.bex.co/services`, `/settings` | 200 | none | none | server-rendered HTML for the signed-in user |

  - Round 131 follow-up, with a throwaway env group `qa-20261105-cc` holding the dummy value `qa-not-a-real-secret` (deleted in the same run, `DELETE` → 204, no `qa-20261105` group left): `GET /v1/env-groups/<id>` → 200, no `Cache-Control`, the response carries the value; `GET /v1/env-groups/<id>/env-vars/QA_SECRET` → 200, no `Cache-Control`, carries the value; the list `GET /v1/env-groups?…` → 200, no value in the body.
  - Cloudflare answered `cf-cache-status: DYNAMIC` on each, so the edge did not cache them. No `ETag`, `Last-Modified` or `Vary: Cookie` either; the API's `Vary` is `Accept-Encoding, Origin`.
  - Control: `GET /v1/services/<id>/deploy-hook` sets `Cache-Control: no-store` (code below).
  - Not probed: Postgres `credentials` (answered `200` with a different shape, one object), and the `Reveal` of an env value.
- **Root cause:**
  - `lego/backend/internal/api/security.go:36-47` (`withSecurityHeaders`) sets `X-Content-Type-Options`, `X-Frame-Options`, a CSP and HSTS on every response, and no `Cache-Control`.
  - Cache headers are set one route at a time where someone thought of it: `lego/backend/internal/deploys/rest.go:210,219` (deploy hook: the comment at `:205-207` says "The URL itself is the credential, so prevent intermediary/browser caches from retaining either a read or a newly rotated value"), `deploys/deployhook.go:341`, `agentsessions/rest.go:246`, `agentsession/pullrequest.go:148`, `sshgateway/sandboxfiles/sandboxfiles.go:475`. The database, Key Value, env-var and secret-file routes were not given one (inferred from the probe above; their handlers were not each opened).
  - The dashboard HTML is served by a separate process; where its response headers are set was not opened.
- **Fix (target behavior):** an authenticated response that can carry a credential is sent with `Cache-Control: no-store`, the same value the deploy-hook routes use.
  - The smallest correct shape is a default on the API: `Cache-Control: no-store` for every authenticated `/v1` and `/graphql` response in `withSecurityHeaders` (or a sibling wrapper), with an opt-out only where a route deliberately sets a cacheable policy (none was found in the `grep` above). It also covers GraphQL, MCP and routes added later.
  - If a global default is judged too wide, the minimum is the credential-bearing routes: Postgres and Key Value `connection-info` and `credentials`, env-var and secret-file reads, API-key creation and reveal.
  - Dashboard HTML for signed-in pages: add `Cache-Control: no-store` (or `private, no-cache`) there too; decide with the dashboard owner, since it affects back/forward cache behavior (not assessed).
- **Tests:** a handler test that requests `connection-info` (Postgres and Key Value) and an env-var read and asserts `Cache-Control: no-store`; the deploy-hook test stays as the control; if the default is global, one test over the mux asserts the header on a plain list and that a route that sets its own policy keeps it.
- **Blast radius:** not counted. `grep -rn "Cache-Control" lego/backend` finds 5 handler files that set it today (`deploys`, `agentsession`, `agentsessions`, `sshgateway/sandboxfiles`, plus `sshgateway/*` stream headers); the number of response writers a global default would touch is every REST/GraphQL/MCP route behind `withSecurityHeaders`, including the SSE streams, which set `no-cache` themselves (`sshgateway/sandboxsse/sandboxsse.go:193`) and must not be overridden.
- **Adjacent classes:** unauthenticated `401`/`404` bodies hold no secret and may stay as they are; `Pragma: no-cache` is HTTP/1.0 legacy and not needed.
- **Unverified:** whether any browser, extension or proxy actually retained one of these responses (the API sends no validator, so heuristic caching should not apply, which is why this is a hardening note and not an incident); the dashboard HTML header source; the service env-var reveal and secret-file responses (the service probed has no env vars; the env-group reads above show the same missing header); MCP and GraphQL secret fields.
- **Render:** not compared (Render's API headers were not checked); the rule here is bex's own, already stated at `deploys/rest.go:205-207`.
- **Dedupe:** `grep -rliE "cache-control|no-store" .pm` finds only static-site cache/ETag items (w4/272, 341 and similar) and unrelated notes; none covers API secret responses. No DO_NOT_DO item applies (its only cache item is the static-site purge non-goal).
