## Objective

A service whose allow-list holds the caller's exact CIDRs still answers `403 Forbidden` to that caller over both IPv4 and IPv6. Find the layer at fault (projection vs edge source-IP strategy) and fix it.

## Context

- Live repro 2026-09-17, `bex v0.2.1`, free Docker web service (live, serving `200` before the allow-list):
  - `bex services update <srv> --ip-allow-list cidr=162.224.81.143/32,description=qa-cli-probe --confirm` → exit 0, entry round-trips on read-back. `curl` (v6 egress) → `403` (correct deny at that point).
  - Added `cidr=2600:1700:45f0:963f:5114:fffa:2ed7:9ced/128` (verified current egress via `ifconfig.me`, stable across the sweep) → exit 0, both entries round-trip. After 2+ min: `curl -4` → `403`, `curl -6` → `403`. Bare `Forbidden` body (9 bytes, no server headers) — Traefik ipAllowList's refusal shape, not the app (which serves the marker on `200` without the middleware).
- Producer/consumer split: producer is the operator's Traefik Middleware projection (`lego/operator/internal/controller/app_controller.go:421-458`, contract pinned by `ip_allow_list_test.go` at creation level only) plus the edge source-IP strategy (what client IP Traefik matches behind Cloudflare/LB); consumer is Traefik itself (external). The CLI/API store-and-read path works — this is enforcement-only.
- Cause UNVERIFIED (no cluster access from the hunt): prime suspect is the middleware matching an upstream proxy/LB address instead of the client (ipStrategy depth), which would deny every listed client exactly as observed; v6 handling is the secondary suspect (ruled OUT as the sole cause — listed v4 is denied too). Pull the live Middleware object + edge topology before changing anything.
- Dedupe: `.pm/w4/done/025.md`, `w4/m32`, `w4/m6/t005` cover the *environment*-level layer, not service enforcement. No open item covers this. No `--clear-ip-allow-list` exists for services (upstream flag surface, same on render.com — not filed, noted here so the fix's live-verify plans around it).

## Steps

1. Capture the live Middleware object for a repro service (source ranges attached, strategy/depth) and the address Traefik actually matches (edge access logs or a header-echo probe): prove depth vs projection vs v6 handling.
2. Fix the layer at fault (projection, strategy, or both). If the edge cannot see true client IPs for this path, say so and gate the feature honestly instead of shipping a list that denies everyone.
3. Re-run the DoD matrix live (v4+v6 allow, non-listed deny).
