## Objective

Stop a refused `setIdleTimeout` from recording `idle_timeout_changed`, and correct the classification comment that allowed it — including re-checking the two verbs `w4/m122` grouped with it, so the same claim is not left wrong about them too.

## Context

- `events/service.go:320-329` asserts what remains ungated is deliberate, listing `apps.SetIdleTTL` under "has no validation, type gate or no-op path at all". Both halves are false: `apps/service.go:3450-3452` rejects out-of-range values **after** `AuthorizeApp`, and setting the current value is a no-op path.
- The doctrine in the same comment names the test and names this exact case: _"a wrong service type, an out-of-range value, a quota, a conflict, or an idempotent no-op is [routine]"_. So this is a misapplication of a correctly-written rule, not a missing rule.
- The gating shape already exists and is named in the comment: authorize under `core.WithDeferredAllowedWriteAudit` and record the effect after the mutation succeeds (`RecordPlanChanged`, `RecordAutoDeployChanged` are the models). `apps.SetRootDir` is a nearby example that already wraps its authorize call.
- Live proof (pass 156): one refused call took the feed from 6 to 7 events; `idleTTLSeconds` read back unchanged.
- The other two verbs in the same bucket: `apps.SetDisplayName` (no validation, but it *does* have a no-op path — setting the same label twice) and `deploys.RegenerateDeployHook` ("a rotation always rotates", plausibly correct). The three verbs in the neighbouring "validates BEFORE it authorizes" bucket were re-read in pass 156 and are correctly placed — do not churn `SetIPAllowList`, `SetNotifyOnFail`, `SetNotificationsToSend`.

## Steps

1. Wrap `SetIdleTTL`'s authorize call in `core.WithDeferredAllowedWriteAudit` and record an idle-timeout effect after the write succeeds, following `RecordPlanChanged`'s shape.
2. Decide the no-op question explicitly and write the decision into the doctrine comment: does 60 → 60 mint an event? The doctrine says a no-op is routine, so the default answer is no — but an accepted write arguably belongs in an audit. Pick one and say why.
3. Re-check `apps.SetDisplayName` and `deploys.RegenerateDeployHook` against the same test and move whichever needs moving.
4. Correct the comment at `events/service.go:320-329` so it describes what the code does.
5. Note in the commit message that this is `w4/m122/t004`'s classification being wrong about one verb, so the history is traceable.
