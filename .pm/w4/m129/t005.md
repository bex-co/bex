## Objective

Make the list and the by-id read agree, and decide whether the list's default time window may silently omit an event the dashboard shows.

## Context

- Pass 156, all eleven ids from one `serviceEvents` response fed back through `serviceEvent(id:)`: ten resolved and reported the queried service; the inherited row answered `EVENT_NOT_FOUND` with `extensions.code: EVENT_NOT_FOUND`. This is how the whole defect was noticed.
- t002 may fix this as a side effect — if the inherited row stops being listed, the divergence has no instance left. **Check before writing code**, and if so, this task becomes a regression test plus the window decision rather than a fix.
- The window half is independent: `serviceEvents(serviceId:…, limit:50)` with no range returned 10 rows; with an explicit `startTime`/`endTime` it returned 11; the dashboard's Activity header read 11. So the API's default answer is narrower than the UI's, on the same data, with nothing saying so.
- `w4/117` is the precedent for single-read-vs-list divergence in this area and its resolution shape: make both reads compose the same SQL rather than fixing the symptom twice.

## Steps

1. Re-run the eleven-id control after t002 and record whether any divergence remains.
2. If it does, find whether the by-id query's predicate differs from the list's audit arm, and compose them from shared SQL as `w4/117` did.
3. Determine `serviceEvents`' default time window by reading the code, and state it in the field's own description — a default that omits data must be discoverable from the schema.
4. Decide whether the dashboard should pass an explicit range or the API's default should widen, and make the two agree.
