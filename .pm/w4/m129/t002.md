## Objective

Apply t001's decision to the two queries that compose service events, so a service's feed and its outbound webhook deliveries both contain only that service's audit-derived events — without touching the deploy-derived arms, which are already correct.

## Context

- `store/events.go:240` `serviceEventsQuery` — a `feed` CTE of `UNION ALL` branches. The deploy branches use `WHERE d.app_id = $1`; the audit branch uses the name-derived `$2` target.
- `store/webhooks.go:708` `webhookEventsQuery` is the "workspace-wide, ascending twin", and its audit arm joins on the target name too. It must change in the same commit — a subscriber receiving the wrong attribution is worse than a reader seeing it.
- **Regression risk, named because it is the whole danger of this task:** the four event types that behave correctly today (`deploy_started`, `deploy_ended`, `service_hibernated`, `service_woken`) are correct *because* they key on `app_id`. They need regression coverage, not just the broken path.
- `w4/117` is the precedent for the shape of the mistake to avoid here: the `feed` CTE's branches must all select the same expressions in the same order, and `w4/done/127.md` records that adding a column to the outer SELECT but not the CTE broke every read of the feed. Any new column crosses both.

## Steps

1. Change the audit arm's predicate in `serviceEventsQuery` per t001.
2. Change `webhookEventsQuery`'s audit arm the same way, preserving its ascending keyset and its workspace-wide shape.
3. If the change adds a column to the CTE, add it to **every** branch and to the outer SELECT, and to the by-id query — the three places `w4/done/127.md` proved must move together.
4. Re-run the branch-agreement guard `TestServiceEventsFeedBranchesAgree`, which exists precisely to catch step 3 going wrong.
5. Verify by hand against a local Postgres that the deploy arms return identical rows before and after.
