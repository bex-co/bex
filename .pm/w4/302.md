# Mobile avatar removes the dashboard's language and theme controls

Why: signed-in users at narrow widths can retain a desktop-selected language or theme but have no visible control to change either while using the hosting dashboard.

**Severity:** minor. **Estimate:** 50m. **Source:** user-requested infinite functional `$qa-find-bugs` loop, `muse.env` through the login helper, requested w4, pass a458, 2026-10-14. **Goal linkage:** [ADR008](../../docs/ADR008-vision.md) pillar 1, usable hosting journeys across supported layouts; `dashboard/AGENTS.md` explicitly locates authenticated language selection in UserNav. Filing only; no resource or account-setting mutation.

## Fresh reproduction and controls

1. At 390×844, fresh-load `/keyvalue/new` while signed in. Click the top-right P avatar. It navigates to `/settings` instead of opening the desktop menu.
2. After Settings fully resolves, no Language, Theme or Appearance control is present. Playwright's actual accessible-role queries return zero matches for buttons, comboboxes, menuitems, radios and links named for those preferences. The Settings section inventory is account, integrations, access, security and danger-zone. Inspect the mobile Sidebar as well: its navigation has no preference controls.
3. At 1440×1000 on the same hosting create route, the same avatar opens the menu with **Theme / System** and **Language / English**.
4. Use the native desktop menu to choose Dark and 中文. The document becomes dark and Chinese immediately. Fresh reload at 390×844 retains both; the avatar still navigates to Settings, whose accessible-role queries for the Chinese preference labels all return zero. Document width stays 390px.
5. Restore English/System through the native desktop menu, restore the original absent `vite-ui-theme` local-storage entry, and repeat the fresh English mobile journey. The same missing controls reproduce at **13:00:08.774Z**.

This is missing UI reachability, not a claim that the locale/theme engines cannot update or that manually editing a URL cannot override them. The desktop controls and persisted mobile state prove those engines work. No resource was submitted from the create form. No profile, password, key, session-list or account-deletion action was invoked.

## Root cause, framework and callers

`dashboard/src/common/components/user-nav.tsx:134–139` returns a bare UserAvatarButton with `onClick={handleSettings}` whenever `useIsMobile()` is true. This branch never mounts the DropdownMenu containing Theme at `:162–198` and Language at `:200–222`. `common/hooks/use-mobile.ts:4–29` uses UA detection for initial state, then the 768px media boundary after hydration; the reproduced 390px branch is therefore intentional rendering logic, not a pending-state flash.

`features/auth/pages/settings-page/index.tsx:31–121` supplies no preference replacement. Its Account, integrations, access, compliance and deletion sections do not call a language/theme selector. The Sidebar's navigation likewise has none. Census of production switching code: UserNav owns authenticated language/theme selection; `features/i18n/language-switcher.tsx` is mounted only in `features/auth/components/auth-page-shell/index.tsx:49`, the unauthenticated shell. `i18n/utils.ts:11–13` persists language and `i18n/init.ts` registers the lazy catalog before switching; `common/providers/theme-provider/index.tsx:111–129` persists/updates the theme. Preserve these existing handlers and persistence semantics.

Native consumer trace: `common/components/ui/dropdown-menu.tsx:10–29` delegates Root/Trigger to the installed `@radix-ui/react-dropdown-menu` **2.1.16**. Its actual compiled `dist/index.mjs:62–86` renders a button with menu attributes, pointer toggle and Enter/Space/ArrowDown handling. Nothing there creates a preference menu for the mobile branch, which returns before the Root exists. This is not a Radix inability to support a narrow viewport.

UserNav has **one production JSX consumer**, `common/components/dashboard-layout/dashboard-header.tsx:56`; DashboardHeader has **one**, `dashboard-layout/index.tsx:47`. The global authenticated dashboard chrome therefore affects hosting detail, list and create pages, not just Key Value. AuthPageShell's independent switcher remains outside this change. Existing tests at `common/components/__tests__/user-nav.test.tsx:28` mock `useIsMobile` as false, so their language-switch coverage cannot expose the omitted branch.

**Target:** at narrow signed-in widths, provide an operable language selector and Light/Dark/System theme selector reachable from the avatar, while retaining an Account Settings action. Reuse the existing UserNav menu/handlers with responsive presentation rather than duplicating locale/theme state, adding a new settings model or restyling the Ory forms. Opening the preference control must not unexpectedly navigate away from the hosting page; selecting a preference must update immediately and survive reload. Preserve desktop behavior and current shared menu actions without changing their semantics.
