# 041 — `POST /v1/projects` opaquely rejects the Render-contract `environments` field

Why: A Render-compatible REST/SDK/CLI client that creates a project the documented Render way — `{name, ownerId, environments:[{name:"production"}]}` (Render **requires** `environments`) — gets an unactionable `400 {"error":"bad request"}` and cannot create a project; only `{name, ownerId}` works. bex's own pinned contract advertises `environments` as acceptable, so this is a REST/Render-parity gap plus an opaque error.

Found in a live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-04, workspace `tea-d98210cbbpdc73dcrkvg` (bex). All `qa-` resources cleaned up (the one created project deleted, 204).

**Severity:** major — a documented Render create-project journey fails for REST/SDK/CLI clients that follow Render's contract. The dashboard is **not** affected (it uses GraphQL `createProject{name, ownerId}`, which honestly omits `environments`).

## Evidence (re-runnable)

Probe from inside an authenticated dashboard page (`fetch(url,{credentials:'include'})`) — `api.bex.co` 403s bare non-browser User-Agents.

```
POST /v1/projects {"name":"p","ownerId":"tea-…"}                                        -> 201 (project created)
POST /v1/projects {"name":"p","ownerId":"tea-…","environments":[{"name":"production"}]} -> 400 {"error":"bad request","id":"bad_request","message":"bad request"}
POST /v1/projects {"name":"p","ownerId":"tea-…","environments":[]}                      -> 400 {"error":"bad request",...}   (even an empty array)
POST /v1/projects {"name":"p","ownerId":"tea-…","zzzBogus":1}                           -> 400 {"error":"bad request",...}   (ANY unknown field)
POST /v1/projects {"name":123,"ownerId":"tea-…"}                                        -> 400 {"error":"invalid request body at /name",...}   (validator-level errors ARE detailed)
```

## Mechanism (confirmed by reading the code, not inferred)

- The kin-openapi request validator sets strict JSON decoding on the context before calling the handler: `lego/backend/internal/api/render_openapi.go:389` (`core.WithStrictJSONDecoding(r.Context())`), so `core.DecodeBody` runs with `DisallowUnknownFields`.
- The create-project handler decodes into a struct with only `{Name, OwnerID}`: `lego/backend/internal/projects/rest.go:107-113`. Any other property (including `environments`) is an "unknown field" → decode error → the handler returns the opaque `core.ErrBadRequest` ("bad request").
- But the contract layer deliberately **accepts** `environments`: `render_openapi.go:68-75` `renderRequiredCompatibility["create-project"]={"environments"}` relaxes it from Render-required to optional **while keeping it a documented schema property**, and the surrounding comment (`render_openapi.go:64-67`) states relaxed fields "remain type-checked whenever supplied" — i.e. supplying `environments` is meant to be valid and type-checked, not rejected. The handler's strict-decode reject **contradicts that stated intent**: contract says "environments is acceptable", handler says "unknown field, reject".

## Target behavior (name it)

`POST /v1/projects` with a Render-shaped `environments:[{name:…}]` array must **succeed** — create the project **and** the named environments — and return them in `environmentIds` (Render creates the environments inline in the same call). "Accept + silently ignore environments" is **not** acceptable (a client that asked for `production`/`staging` would believe they exist; later env-scoped calls then fail — silent data loss). At minimum, if honoring inline is out of scope, the field must not produce an **opaque** error — it must name what was rejected, matching the validator's own `invalid request body at /<field>` quality.

## Cross-surface (ADR006)

Only REST advertises `environments` (it sits behind the pinned Render contract). GraphQL `createProject` args = `{name, ownerId}`; MCP `create_project` props = `{name, workspaceId}` — both honestly present bex's "create bare project, environments created separately (`create_environment`)" model, so they are self-consistent. The fix is REST-scoped: make REST honor the contract it advertises. Decide whether GraphQL/MCP should also gain inline environments for symmetry or stay separate-create (document the choice).

## Blast radius / siblings

The strict-decode-rejects-unknown-fields-opaquely behavior is generic to every create/patch handler whose decode struct is narrower than its advertised contract. `renderRequiredCompatibility` relaxes 6 operations: `create-env-group` {ownerId,envVars}, `create-key-value` {ownerId,plan}, `create-postgres` {ownerId,plan,version}, `create-project` {environments}, `create-service` {ownerId,type}, `create-webhook` {ownerId,enabled,eventFilter}. `create-project`/`environments` is the confirmed instance because `environments` is the one relaxed field its handler does **not** include in its decode struct; the other five relax fields the handlers **do** read. A blast-radius pass should grep each handler's decode struct against its relaxed field(s) and confirm none of the other five silently rejects a contract-valid field (**unverified this run** — reasoned, not probed per-endpoint). Also worth normalizing: the opaque-vs-detailed error inconsistency (handler strict-decode → "bad request"; validator → "invalid request body at /field") so unknown-field rejections name the field.

## Adjacent classes

The "invalid body" branch of the request-error taxonomy. Validator-level type/format errors already land as detailed 400s (`invalid request body at /name`); handler-level strict-decode unknown-field errors land as opaque 400s — the fix should bring the latter to the former's quality (name the offending field) so the two invalid-body sub-classes are consistent.

## Render

Render's `POST /v1/projects` requires `environments` and creates the project with those environments in one call, returning their ids. bex diverges by rejecting the field entirely.

## Estimate

~1h — widen the REST create-project handler to accept `environments` and honor it (create the named environments via the project/environment service; return `environmentIds`); regression test for create-with-environments **and** a test that an unknown field yields a field-naming 400 rather than an opaque one. Promote to a small milestone if inline environment creation needs new service-layer support or if the blast-radius audit of the other 5 relaxed operations is bundled in.
