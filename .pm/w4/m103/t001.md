## Objective

A first deploy whose container cannot start reaches a terminal `update_failed` deploy row at the 900s rollout budget, but the App's `status.phase` stays `Deploying` — so the service header contradicts its own deploy list, on every surface. Settle the phase.

## Context

### The observation (production, 2026-09-13)

Service `qa-0913e-bad` (`srv-daj9umggsm7s73f63olg`), free web service, `examples/hello-go`, docker runtime, created via `POST /v1/services` with `serviceDetails.envSpecificDetails.dockerCommand = "/bin/qa-nonexistent-binary"`. Nothing had ever served: `Revision: —`.

Events and deploy, verbatim:

```text
deploy_started  13:04:26   {firstBuild:true, …}
build_started   13:05:47
build_ended     13:06:59   {status:"succeeded"}       ← the BUILD is fine
deploy_ended    13:25:17
```

```text
GET /v1/services/srv-daj9umggsm7s73f63olg/deploys?limit=3  (at 13:28:19)
status:       "update_failed"
finishedAt:   "2026-09-13T13:25:17.046721Z"
failureReason: "container exited shortly after start and is restarting repeatedly
  (last exit code 127) — check the service logs for the crash output. If the crash
  is a port bind: the process must listen on $PORT (3000), and tenant containers
  cannot bind ports below 1024 (all Linux capabilities are dropped)."
```

898 seconds from rollout start (13:06:59) to `update_failed` (13:25:17) — the documented 900s budget, working exactly as designed.

But the phase does not follow:

```text
GET /v1/services/srv-daj9umggsm7s73f63olg        (13:28:19) → phase: "Deploying"
GraphQL server(id:"srv-…"){ phase }              (13:29:33) → phase: "Deploying"
```

and the dashboard header, read from the page at 13:29:40:

```text
qa-0913e-bad
Service  Deploying          ← service badge
Latest deploy  Failed       ← deploy badge
…
Failed  dep-daj9umggsm7s73f63om0
  container exited shortly after start and is restarting repeatedly (last exit code 127) …
  Failed September 13, 2026 at 6:25 AM · First Deploy · 19m 29s
```

### Why the phase never moves

- `rolloutBudgetSeconds = 900` (`lego/operator/internal/controller/deployment_projection.go:130`) is set as the Deployment's `progressDeadlineSeconds` (`:315`) and as the startup-probe budget. Kubernetes marks the Deployment `Progressing=False`; it is **not** a reconcile error.
- `PhaseFailed` has exactly one writer: `r.fail(...)` at `app_controller.go:4240`, reached from reconcile **error** returns (build failure, `failPreDeploy`, network-policy failure, …). `grep -rn "PhaseFailed" lego/operator/internal/controller/*.go | grep -v _test` → the only assignment for Apps is that line.
- So the operator, having applied the Deployment successfully, keeps returning a healthy reconcile and leaves `Deploying` in place, while **bex-api's** control-plane reconciler independently closes the deploy row at its own gate (`DeployGateTimeout`, named in the `rolloutBudgetSeconds` comment at `:110-118` as the 18m observer). Two components, two clocks, one of them with no verdict to write.

### The taxonomy this must fit

`lego/types/v1alpha1/app_types.go:1127-1149` documents the rules and the reasoning, including the two prior fixes:

- `PhaseFailed`: "the App could not be converged and **nothing is serving**. A BUILD failure reaches this state only when no earlier release ever succeeded (`Status.Image` empty)."
- `PhaseCanceled` (w6/m52): added because reusing `PhaseFailed` for a cancel "made a service contradict its own deploy history".

This case satisfies `PhaseFailed`'s own words — nothing converged, nothing is serving, no earlier release — but the code only gets there through a build failure.

## Steps

1. ~~**Establish whether it is permanent or merely late.**~~ **Answered 2026-09-13 pass 8 — it does not settle.** A second fixture (`qa-0913h-bad`, `srv-dajc7c26m8ac739r57ag`, same bad `dockerCommand`) was watched well past the deploy's terminal state:

   | time (UTC) | observation |
   | --- | --- |
   | 15:39:28 | `deploy_started` (`firstBuild: true`) |
   | 15:40:47 → 15:41:47 | `build_started` → `build_ended status: succeeded` |
   | 15:57:57 | deploy still `update_in_progress`, phase `Deploying` |
   | **15:59:58** | `deploy_ended` + deploy `update_failed`, `finishedAt` set, specific `failureReason` recorded |
   | 16:02:30 | phase `Deploying` |
   | 16:06:36 | phase `Deploying` on **both** REST and GraphQL |
   | **16:14:40** | phase `Deploying` on both, and **no event since `deploy_ended@15:59:58`** |

   So: **14m42s** past the terminal deploy, unchanged, with the reconciler quiet. Treat it as permanent — and note the structural reason rather than only the elapsed time: the 900s rollout budget has expired, bex-api's 18m deploy gate has already fired (it is what closed the row), and no further timer exists that could revisit the phase. Do not spend time re-measuring this; spend it on step 2.

   **One timing caveat for the implementation:** the verdict landed at **1091s** after `build_ended` here, versus **898s** in pass 5. Both fixtures were identical in shape, so the close is reconciler-poll jittery around the 900s budget and can drift to the 18m gate — do not hard-code 900s as the moment a test should expect the transition, and do not read the late close as an ordering violation: the recorded `failureReason` was the mechanism's own specific crash-loop diagnosis both times, not a generic gate message.
2. **Explain the missing `server_failed`.** This service emitted no `server_failed` event at all, while pass 4's crash loop *on a service with a prior release* emitted `server_failed / readiness_failed` within ~40s. Find why (likely a phase-edge-triggered fact that needs a `Running → …` transition it never had). That answer probably names the right hook for the phase fix too.
3. Decide the terminal phase and justify it against the taxonomy comment. `PhaseFailed` is the natural reading of its own definition; if a new state is warranted (as `PhaseCanceled` was), say why the existing one misleads. Update the doc comment either way — it currently describes only the build path.
4. Implement the trigger. Options to weigh: the operator observing its own Deployment's `Progressing=False` past the deadline (keeps the verdict in the component that owns `status.phase`), or bex-api's reconciler projecting the phase when it closes the row (keeps one clock but moves phase ownership across the module boundary, which `lego/CLAUDE.md`'s DAG discourages). Prefer the operator.
5. Keep the deploy row's `failureReason` byte-identical — it is already the best part of this flow.
