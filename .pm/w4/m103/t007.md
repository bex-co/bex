## Objective

This milestone's evidence comes from a **crash-loop** first deploy, whose row closed at 898s. A second failure class — **an image that cannot be pulled** — reproduces the same stuck phase, but its row is not closed by the 900s rollout budget at all: it survives to bex-api's 18-minute `DeployGateTimeout`. So the milestone's "the two clocks agree" bullet is written against a timing the image-pull class does not follow, and t001's fix has to settle the phase for a row that can close on either of two different timers.

### Two facts this adds to the milestone

1. **The stuck phase is not specific to crash-loops.** `phase: "Deploying"` persisted after the row reached `update_failed`, exactly as t001 describes — so t001's fix must cover the image-pull path too, and the milestone's DoD should assert it on both classes rather than only the crash-loop fixture.
2. **1091s, not ~900s.** `deployTimedOut` (`lego/backend/internal/store/reconciler.go:1047-1065`) selects `r.DeployGateTimeout` (18m) for an open row whose status is `update_in_progress`; only `DeployCreated`/`DeployQueued`/`DeployBuildInProgress` take `BuildGateTimeout` and `DeployPreDeployInProgress` takes `PreDeployGateTimeout`. Nothing in that function applies the operator's 900s rollout budget. For the crash-loop class the operator's own mechanism evidently produces a failure the row observes near 900s (m103 measured 898s); for the image-pull class it does **not**, and the row waits for the control-plane observer.

   That inverts the intent documented at `lego/operator/internal/controller/deployment_projection.go:110-122`, which states the observer is _"deliberately LONGER (18m), so the mechanism's own specific verdict lands before the generic health-gate message."_ Here the mechanism never lands — though note the **message** is still the specific one, because `deployCloseFailureReason` (`reconciler.go:722`, `:769`) sources the operator's diagnosis at close time regardless of which timer fired. So the defect is timing, not wording: **do not "fix" this by changing the failure text.**

### Why the fast-fail question is open, not decided here

A nonexistent tag can never succeed, so 18 minutes of "Deploying" buys nothing — and bex has the diagnosis at t+0 (it emitted `image_pull_failed` from `reconciler.go:1019-1037`, reading `condition.Reason == "ImagePullBackOff"`). But the 900s budget is deliberately Render-matched ("If this condition is not met within 15 minutes, Render cancels the deploy"), and **no capture exists of how fast Render fails an unpullable image** — `docs/render-artifacts/` has nothing on it. So this task does not assert Render drift. Decide between:

- **(a) Fail fast on a terminal pull failure** — needs a Render capture first, or an explicit recorded divergence.
- **(b) Show the diagnosis while the budget runs** — the cheap half, no timing change: the reconciler pass that emits `image_pull_failed` already holds the message, so an in-progress row could carry it and the Deploys tab/header could show "image pull is failing" instead of a bare "In Progress" for 18 minutes.

(b) is recommended and independent of t001; (a) is a product decision to record either way.

### What the user sees during those 18 minutes

- **Deploys tab + header:** `Service Deploying` / `Latest deploy In Progress`, and the string "pull" appears **nowhere** on the page (checked with a regex over `main`'s text).
- **Events tab:** already honest at t+0 — "Image pull failed · Deploy dep-… · The runtime could not pull the configured image.", with the image path on the `deploy_started` row. So the information exists one tab away, which is what keeps this at (b)-sized rather than a blocker.

## Steps

1. Re-run t001's phase fix against **this** fixture shape (image-backed, nonexistent tag) as well as the crash-loop one, and assert the phase settles for both.
2. Decide (a) vs (b) above in writing. If (b), carry the existing `ImagePullBackOff` diagnosis onto the open row so the Deploys surface can render it mid-rollout.

## Journey 14's notification half, verified correct in the same pass

A webhook endpoint `qa-20260913-hook` was pointed at `https://qa-20260913-sink.invalid/hook` — the reserved `.invalid` TLD, which cannot resolve, so **no payload left the platform** — subscribed to `deploy_started`/`deploy_ended`/`build_started`/`build_ended`, and deleted at end of run. Its delivery records are exemplary:

```text
status "failed" · statusCode 0 · attemptNumber 1 then 2 · parentStatus "pending"
transportError: Post "https://qa-20260913-sink.invalid/…": lookup qa-20260913-sink.invalid
                on 10.96.0.10:53: no such host
sentAt 00:00:16 → 00:00:46 (30s), nextAttemptAt 00:10:46 → growing backoff
```

- The **transport** failure is reported as a transport failure (`statusCode 0`, not a fake 5xx), and names the DNS cause.
- `parentStatus: "pending"` while the attempt is `failed` — the logical notification is still retrying, the attempt is immutably failed. That distinction is what `webhooks/service.go:301-307` documents, and it holds on the wire.
- The URL is **truncated** in the stored error (`…/…"`), consistent with the store bounding its evidence.
- **A near-miss checked and dismissed:** two `deploy_started` events appeared within a minute, which looked like duplicate notifications. They carry different `eventId`s **and different `serviceId`s** — one was `srv-d9bj8s3eg85c7390eb9g`, a pre-existing workspace service that deployed concurrently. A workspace-scoped endpoint correctly receives both. Each event produced exactly one attempt-1 and one attempt-2. No duplication.
- **Unverified:** a **successful** delivery (needs a reachable sink, which would mean sending payloads to a third-party service — deliberately not done), the `resendWebhookDelivery` verb, the signature header's correctness, and the failure-notice email that `worker.go:741` sends after N consecutive failures.
