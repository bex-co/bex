## Objective

An idle wake or a user Resume whose only `Ready=False` reason is ordinary scale-up progress is not an availability conclusion. Through that startup the service checkpoint keeps its hibernated availability baseline (`""`). The first healthy pass sets the baseline to healthy and emits no `server_available`. The cycle records exactly `service_woken` / `service_resumed`.

## Context

- `lego/operator/internal/controller/app_controller.go:3256-3257`: during a wake the App reads `Phase=Deploying`, `Ready=False`, reason `RolloutProgressing`. With the full current-revision complement ready but Deployment bookkeeping lagging, the reason is `RolloutSettling`, which is already excluded.
- `lego/backend/internal/store/reconciler.go:1862-1866`: the rollout-progress exemption requires `hasOpenDeploy`. A wake has no deploy row, so `:1873-1878` concludes `unhealthy` / `readiness_failed`.
- `reconciler.go:293`: `unhealthyConfirmAfter = 10s` (`w4/207`, `cc281d02e`) confirms the second sighting.
- `store/event_facts.go:467-472`: `checkpointServicePhase` already holds Hibernated through the transient startup phases. `:547-549` emits `server_available` on `unhealthy` → `healthy`.
- The single caller is `observedServiceStateFor`, `reconciler.go:476`.
- Live evidence: [finding.md](finding.md) §1 and [evidence.json](evidence.json), wake 1.

## Steps

1. Choose the seam and record the choice in the PR/commit:
   - **(a)** `RecordObservedServiceState` treats a non-concrete `readiness_failed` observation as availability-unseen while the held checkpoint phase is Hibernated. It needs the observation to carry whether the Ready reason was a `concreteContainerFailure`.
   - **(b)** The operator writes a distinct waking reason that the backend treats like `parkReason`.
   - Prefer (a): one module, and it reuses the held baseline.
2. Key the rule on the hibernated baseline, never on the `RolloutProgressing` reason alone. A running service (healthy checkpoint) whose only instance becomes unready without a deploy must still conclude unhealthy.
3. Leave the debounce, the stale-transition guard and the deploy-row exemption unchanged.
4. Add a failing-direction store test: Hibernated → Deploying/RolloutProgressing (two passes ≥ `unhealthyConfirmAfter` apart) → Running/Ready. It must assert no `server_available`, and it must fail on the pre-fix code.
