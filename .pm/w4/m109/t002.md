## Objective

Every project REST response embeds `owner: {id, name, email, type}` with `name` and `email` as empty strings. The three sibling resource families populate them through a shared resolver that `internal/projects/` does not import. Wire it in.

## Context

Live, production, 2026-09-16 — same workspace, same session, four families:

```
/v1/projects?ownerId=…  "owner":{"id":"tea-d98210cbbpdc73dcrkvg","name":"","email":"","type":"team"}
/v1/services?limit=1    "owner":{"id":"tea-d98210cbbpdc73dcrkvg","name":"bex","email":"puncsky@gmail.com","type":"team"}
/v1/postgres?limit=1    "owner":{"id":"tea-d98210cbbpdc73dcrkvg","name":"bex","email":"puncsky@gmail.com","type":"team"}
/v1/key-value?limit=1   "owner":{"id":"tea-d98210cbbpdc73dcrkvg","name":"bex","email":"puncsky@gmail.com","type":"team"}
```

`/v1/env-groups` and `/v1/blueprints` have no `owner` object at all (they expose a bare `ownerId`), so they are a different shape, not a fourth instance of this defect.

- `lego/backend/internal/projects/rest.go:61` — `Owner: renderOwner{ID: p.OwnerID, Type: "team"}`. No lookup; `Type` is also hardcoded to `"team"` rather than read from the owner, which is a second small truth problem to check while here.
- `lego/backend/internal/resourcemeta/metadata.go:53-63` — the shared seam. `OwnerResolver.ResolveResourceOwners(ctx, ids) map[string]Owner`, with `ResolveOwners` batching and de-duplicating. Its doc is explicit about the failure mode this task must not reproduce: _"A missing key means the owner is unavailable or not visible and must be omitted, never replaced with an id-as-name placeholder."_
- `lego/backend/internal/apps/service.go:73-75` — `Owners resourcemeta.OwnerResolver` on the service struct, wired in the composition root; the pattern to copy.
- `internal/projects/` imports `resourcemeta` nowhere — confirmed by grep.

`w9/m41` (done) adopted this seam for "postgres, apps, keyvalue" and retired `.pm/w6/done/016.md`, which had described this exact defect. Projects was outside that milestone's scope and still shows it.

**Batch, do not N+1.** `GET /v1/projects` renders a page of projects; resolve the distinct owner ids once per request through `ResolveOwners`, not once per project.

**Place the adjacent classes.** Decide and implement what each of these returns, and say so in the code:

- owner resolves → `name`/`email` populated.
- owner not resolvable / not visible to the caller → per the seam's contract, omitted. Note that `renderOwner`'s `Name`/`Email` have no `omitempty` today, so "omitted" needs either struct tags or a pointer — and the pinned Render schema must still accept the result. A caller who cannot see the owner must not be able to tell "no such owner" from "not visible to you".
- the control-plane store is unavailable → the project still renders; a project read must not fail because owner metadata could not be fetched.

## Steps

1. Add an `Owners resourcemeta.OwnerResolver` field to `projects.Service` and wire it in `internal/api/server.go` exactly as `apps.Service` and the datastore services are wired.
2. Resolve owners in the list and single-read paths, batched, and thread the resolved `Owner` into `toRenderProject` (it will need the resolved value as a parameter rather than deriving it from `p.OwnerID`).
3. Cover the write verbs too — `POST`, `PATCH` and the three link `PUT`s all funnel through the same mapper since `w6/m126`, so they must not regress to a blank owner.
4. Read `Type` from the resolved owner instead of hardcoding `"team"`, or document why `"team"` is always correct for a project owner.
5. Re-run the four-family comparison above and confirm projects now matches its siblings.

## Acceptance criteria

- [ ] `owner.name` and `owner.email` on every project verb match `GET /v1/owners` for the same id.
- [ ] One page of N projects issues one owner resolution, not N.
- [ ] An unresolvable owner produces the documented shape — never `""` masquerading as a real name — and does not fail the project read.
- [ ] `GET /v1/services`, `/v1/postgres`, `/v1/key-value` owner blocks are byte-identical before and after.
- [ ] `owner.type` is either resolved or its hardcoding is justified in a comment.
