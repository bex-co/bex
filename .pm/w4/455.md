# 455 — REST returns `idleTTLSeconds` at the service's top level but `PATCH` rejects it there with "unknown field"

Why: a REST client that reads a service's idle window and writes it back the same way gets a 400. GraphQL and MCP accept the field where they return it, and ADR018 says REST `PATCH` writes it, so REST is the one surface whose write shape disagrees with its own read shape.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-01 UTC (`muse.env`, `bex-canary`, pin `fdd51c53ef3f`), found while setting a short idle window for the sleep→wake journey; **minor** (bex extension, the nested spelling works), ~30m.
- **Probe (fixture `srv-dbjibbbbb81s739b3cpg`, Free image web service, deleted after the run):**
  - `GET /v1/services/srv-dbjibbbbb81s739b3cpg` → top-level `"idleTTLSeconds":0` (beside `replicas`, `revision`, `urls`). `serviceDetails` has no such key.
  - `PATCH /v1/services/srv-dbjibbbbb81s739b3cpg` `{"idleTTLSeconds":120}` → `400 {"error":"bad request: request body contains unknown field \"idleTTLSeconds\"","id":"bad_request",…}`.
  - Control: GraphQL `mutation { setIdleTimeout(id:"srv-dbjibbbbb81s739b3cpg", idleTTLSeconds:120){ id } }` → 200, and the next REST `GET` read `idleTTLSeconds: 120`.
- **Root cause:** the REST read places the field on the top-level service view (`lego/backend/internal/apps/render.go:197`). The PATCH body declares it only inside `serviceDetails` (`lego/backend/internal/apps/rest.go:71-74`, resolved at `:945`), and the strict decoder refuses unknown top-level keys. `port`, `healthCheckPath`, `preDeployCommand` and `schedule` already accept both spellings, with the nested one winning (`rest.go:80-85`, `:934-958`; rationale w4/m121: "a caller reading back a service finds the port under serviceDetails").
- **Fix (target behavior):** `PATCH` accepts `idleTTLSeconds` both at the top level (where REST returns it) and under `serviceDetails` (kept for existing callers), with the nested value winning when both are sent, exactly as for `port`. Both funnel through `SetIdleTTL` (`service.go:4199`) with `checkIdleTTL`'s 0–604800 bound and error unchanged. The read shape is unchanged. Update ADR018 `:90`, which already says REST `PATCH` writes the knob, to name both spellings.
- **Tests:** a REST PATCH test where top-level `{"idleTTLSeconds":120}` → 200 and the read returns 120; both spellings → the nested one wins; top-level `-1` / `604801` → the same 400 as nested; the existing nested test stays green.
- **Blast radius:** `patchServiceRequest` only. GraphQL `setIdleTimeout` (`graphql.go:1587`) and MCP `update_service` (`mcp.go:90`) already take it flat; create (`rest.go:1112`, `serviceDetails.idleTTLSeconds`) was not probed this run.
- **Render:** n/a. Render has no idle-window field (bex extension, ADR018 `:90`).
- **Dedupe:** `.pm` mentions `idleTTLSeconds` only in GraphQL captures (w4/044, 252, 236, 263, 268, 274, 276, 281) and MCP field lists (w4/078). No item covers REST's write shape, no DO_NOT_DO item applies, and nothing on `main` since the pin touches `rest.go`.
- **Cleanup:** fixture deleted (`GET` 404, workspace list `[]`); session revoked.
