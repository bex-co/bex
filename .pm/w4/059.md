# Metrics `instance` series label leaks the raw tenant-prefixed k8s pod name instead of the masked public instance id — inconsistent with `serviceInstances`, violates the documented "PodName remains internal" invariant

Why: `serviceInstances` returns a clean masked instance id (`srv-<id>-<opaque>`, Render-style) and the codebase explicitly documents that pod names stay internal, but the `metrics` feature labels every series' `instance` with the **raw** k8s pod name `tea-<tenantid>-<name>-<replicaset>-<pod>`. That leaks the internal tenant id, the CR metadata.name, and the replicaset topology into the metrics API and the dashboard metrics legend, disagrees with `serviceInstances` for the same instances, and diverges from Render (which labels metric series by public instance id). The system already has the masked form; metrics is the one surface that bypasses it.

Source: live QA 2026-09-08, `$qa-find-bugs w4` pass 38 (UI-driven metrics inspection + cross-surface identity comparison).

## Symptom (reproduced live on prod — service `srv-d9bkcspg9s7c73d0n8ug` "agentmarketcap-1")

- GraphQL `metrics(name:MEMORY, RESOURCE=srv-…)` → series labels `[{field:"instance", value:"tea-d98210cbbpdc73dcrkvg-agentmarketcap-1-8645b77f5c-hg25t"}, {field:"resource", value:"srv-d9bkcspg9s7c73d0n8ug"}]` — the raw pod name (incl. the `tea-` tenant id + CR name + replicaset hash).
- The dashboard Metrics page (`/web/srv-…/metrics`) renders these raw pod names verbatim as the per-series legend under Memory/CPU.
- **CONTROL (same instances, masked correctly):** `serviceInstances(id:srv-…)` → `{id:"srv-d9bkcspg9s7c73d0n8ug-465tcls9t0au7s9mnlhf"}` — clean `srv-<id>-<opaque>` public id. `currentInstances = 1` (the 3 pods in the 12h metrics view are historical within the window — **not** an over-provisioning bug; header "Instances 1" is honest).

Durable probe: `{"query":"query Metrics($query: MetricsQueryInput!){ metrics(query:$query){ labels{ field value } } }","variables":{"query":{"filters":[{"field":"RESOURCE","values":["srv-d9bkcspg9s7c73d0n8ug"]}],"name":"MEMORY","start":"2026-09-07T20:00:00Z","end":"2026-09-08T08:00:00Z","resolution":600}}}` → instance label = `tea-d98210cbbpdc73dcrkvg-agentmarketcap-1-<rs>-<pod>`.

## Root cause (code-verified on `main` HEAD `fb7411c34` — not deploy-lag)

- Metrics labels each series' `instance` with the raw pod name: `lego/backend/internal/metrics/service.go:601` (`Labels: {"resource": q.App, "instance": u.Pod}`, instant/usage path) and `:695` (`"instance": pod.Name`, limit path); the ranged/Prometheus path passes Prometheus's own `instance`=pod label through raw at `lego/backend/internal/metrics/source.go:233` and `:506` (`labels["instance"] = pod`).
- The documented invariant it violates: `apps/service.go:1348` — "PodName remains internal; ID is the Render-compatible public instance id." `serviceInstances` honors it: `ListInstances` (apps/service.go:1305) maps each pod to `ids.DeriveServiceInstance(publicID(a), podInstanceIdentity(pod))` at `:1334`, yielding `srv-<id>-<opaque>`.
- So two surfaces identify the same instance two ways: `serviceInstances` = masked `srv-<id>-<opaque>`; `metrics` = raw `tea-<tenantid>-<name>-<rs>-<pod>`.

## Target behavior / fix

The metrics `instance` label must be the **public instance id** (masked), consistent with `serviceInstances` and logs — never the raw pod name. Name the shape the surfaces must agree on: the **same** public instance id `serviceInstances` returns.

**Fix nuance (confirm-the-layer-can-express-it):** `podInstanceIdentity` (apps/service.go:1536) derives the masked id from `pod.UID`, but every metrics path has only the pod **name** string (service.go:601 `u.Pod`, :695 `pod.Name`, source.go Prometheus `instance`=pod), and historical/terminated pods in the query window have no live UID to look up. So the fix **cannot** just call the existing UID-based helper — the public instance id must be **derivable from the pod name**. Cleanest: unify `serviceInstances` + `metrics` (+ logs/shell) on a name-derived public instance id (e.g. `DeriveServiceInstance(publicID, podName)`), so a live pod and its metric series resolve to the identical id. A live-pod name→id map with a name-hash fallback for terminated pods is the alternative but produces two derivations and risks live-vs-historical mismatch — the fix must state which it chooses.

## Blast radius (grepped)

Metrics `instance` labeling — `service.go:601` (instant), `:695` (limit), `source.go:233` + `:506` (ranged/Prometheus app pods); the `instance` GroupBy/filter (`service.go:145`) and any client-supplied `instance` filter value must use the same masked id after the change. Surfaces: GraphQL `metrics`, REST metrics, MCP metrics all return these labels (one series builder); the dashboard Metrics page renders them. Datastore metrics (`source.go:471` `pvc`, `:506` `pod`) should be checked for the same raw-name exposure. If `serviceInstances`' derivation changes to name-based, regression-test that its ids stay stable and that shell/exec instance targeting (which also uses the public instance id) still resolves.

## Adjacent classes

- own-workspace metrics only (authz via `AuthorizeApp`) — **not** cross-tenant (a user sees only their own tenant id): low-sensitivity internal-identifier exposure + contract/parity/consistency, not a cross-tenant leak.
- valid instance → masked id (the fix).
- historical/terminated pod in window → still a stable masked id (the fix must cover it — hence the name-derivable requirement).
- unknown/forbidden resource → unchanged (authz first).

## Render parity

Render labels metric series by the public instance id, not the raw orchestrator pod name. bex metrics diverges; `serviceInstances` already matches. Parity task applies (GraphQL + REST + MCP metrics + dashboard legend move together).

## Severity

**Minor** — no data loss, no blocked journey, own-tenant only; but it is (1) a documented-invariant violation ("PodName remains internal"), (2) a cross-surface inconsistency (`serviceInstances` masks, metrics doesn't) for the same instances, (3) a Render-parity divergence, and (4) internal-identifier exposure (tenant id + CR name + replicaset topology) surfaced in the dashboard and API.

## Unverified this run

- Only GraphQL `metrics` + the dashboard Metrics page were live-probed; REST `/v1/metrics` and MCP metrics share the same series builder (code-traced, same raw label expected). Datastore (Postgres/KV) metrics instance labels were not probed.
- The over-provisioning angle was ruled **out** live (`serviceInstances`=1; the 3-pod view is the 12h window).
- Whether changing `serviceInstances`' derivation to name-based affects shell/exec targeting was reasoned, not exercised.
