# 086 — Verb-parity closure for `w4/083`: across 15 resource families, `resume_keyvalue` is the sole genuine gap, and five look-alikes are not

Why: `w4/083` filed the Key Value resume gap but explicitly left open "whether any other verb is genuinely missing", warning that a mechanical name diff is unusable — this is the per-family audit that settles it, so nobody re-runs the noisy diff and nobody treats the five false positives below as work.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 33. **Read-only on production — nothing created, changed or deleted, and no new login session minted** (the existing browser session was reused, per `w4/085`). **No new defect found.**

## Result

Fifteen families were walked across REST, GraphQL and MCP: service lifecycle + autoscaling, custom domains, disks, static rules, deploys, env groups, projects + environments, jobs + cron, webhooks, blueprints, agent sessions + sandboxes, workspace members + invites, credentials (API key / SSH / registry), notifications, and git. Postgres and Key Value were covered in pass 31.

**The only genuine verb-parity gap in the whole surface is the one already filed** — MCP's `suspend_keyvalue` with no `resume_keyvalue` (`w4/083`). That raises 083's priority: it is not one of many rough edges, it is the single exception in an otherwise complete matrix.

## The five look-alikes, and why each is not a gap

Every one of these read as a missing verb from the op table and dissolved on inspection. They are recorded because each will look like a bug again to the next person:

| apparent gap | why it is not |
| --- | --- |
| MCP can `disable_autoscaling` but has no set/enable tool | Folded into `update_service`'s `autoscaling` argument (`apps/mcp.go:119`), and the divergence is deliberate and documented at `:834-835` — "autoscaling is an `update_service` argument REST keeps behind its own PUT route" |
| GraphQL can `setStaticHeaders`/`setStaticRoutes` but appears to have no read | `routes` and `headers` are **nested fields on the Service type** (`apps/graphql.go:485,489`), not root Query fields, so a root-field grep cannot see them |
| REST has no rollback route while GraphQL and MCP do | It exists — `POST /v1/services/{id}/rollback` (`deploys/rest.go:267`, `scope_matrix_ops.go:707`). A family regex keyed on "deploy" misses it because the route says "rollback" |
| MCP has no webhook event-types tool, so an agent cannot discover valid `eventTypes` | `list_webhook_endpoints` returns the full vocabulary in its result (`webhooks/mcp.go:37-39,94`), and `create_webhook_endpoint`'s jsonschema says so at `:45` |
| REST has no agent-session resume while GraphQL and MCP do | `POST /v1/agent-sessions` accepts `resumeSessionId` (`agentsessions/models.go:137`), which `Create` routes straight to `Resume` (`service.go:429-430`) |

Four distinct mechanisms produced those: **consolidation** into an `update_*`/create verb (`w1/m71` and `w1/m74` retired ~40 setters this way), **nested GraphQL fields**, **data returned by a sibling tool**, and plain **regex misses** — `Mutation.createRegistryCredential` and `Query.apiKeys` also failed case-sensitive family patterns this pass. Any future audit here must check all four before believing a gap.

## Deliberate omissions confirmed, not gaps

- **MCP has no workspace create/delete/rename.** Workspace creation is a multi-step prepare/finalize/cancel flow (`Mutation.prepareWorkspaceCreation` …) bound to the dashboard.
- **MCP git tools are read-only** (`get_git_connection`, `list_git_connections`, `list_repos`) — connect/claim/disconnect are browser-bound OAuth installation flows.
- **MCP has no device/web-push notification subscriptions.** Those are mobile-client concerns; the per-service parts an agent could want (`notifyOnFail`, `notificationsToSend`) are folded into `update_service`.
- **MCP has no Postgres or Key Value delete** — documented at `keyvalue/mcp.go:32` and recorded in `w6/m37`'s README as "deliberate, matches Render's own MCP server; do not add one".

## What this does not establish

- **Name parity is not behavior parity.** This audit matched verbs, not semantics: it did not check that a matching pair takes the same arguments, enforces the same authorization, or returns the same error shape. A surface that exposes the right verb with a narrower argument set or a weaker gate would pass this audit and still be a defect. That is the natural next audit and is genuinely larger than this one.
- The four **read** families (logs, metrics, usage/billing, service events) were not walked — the sweep targeted lifecycle verbs, where a one-way door actually strands a caller.
- Sandbox `pause`/`resume` exist on REST (`POST /v1/sandboxes/{id}/pause|resume`) and on neither other surface; `GET /v1/sandboxes/{id}` likewise has no single-item sibling on GraphQL or MCP. Both were judged REST **extras** rather than gaps in the other two, but that judgement was not checked against how the sandbox feature is meant to be driven.
- Deploy status, **eleventh consecutive check**: production still serves the pre-`e6419af0b` build (Settings → API Keys has no Client ID column), so `w4/078`'s re-probe, `w4/m105`'s scoped exchange and `w4/m106`'s live refusal test all remain queued.
