# 362 — REST refuses `?confirm=` on the three datastore routes whose own refusal asks for it

Why: over REST, a protected Postgres rename, version upgrade or failover, a protected Key Value rename or eviction/durability change, and w4/m233's first enable of external access on a Persistence Off Key Value can never be completed. The refusal tells the caller to "retry with confirm=…", and the retry is rejected before it reaches the handler.

**Source:** live `/qa-find-bugs w4` pass 0a57a8, 2026-10-19 UTC, pin `db7e50ced338`, workspace `bex-canary`, during the w4/m233 replay. The fixtures (`qa-20261019-0a57a8-kv1` `red-dbasmd5212nc73a1i6v0`, `qa-20261019-0a57a8-kv2` `red-dbasoll212nc73a1i730`) are deleted.

## Probe (signed-in page `fetch`, `credentials:"include"`)

1. On the Persistence Off, never-public `kv2`, `PATCH /v1/key-value/red-dbasoll212nc73a1i730` `{"ipAllowList":[{"cidrBlock":"<runner>/32","description":"qa runner"}]}` → `400 {"code":"KEY_VALUE_RESTART_CONFIRMATION_REQUIRED","error":"turning on external access for \"qa-20261019-0a57a8-kv2\" restarts it, and with persistence off that deletes every key; retry with confirm=\"sudo clear key value qa-20261019-0a57a8-kv2\"",…}`. This is correct.

The GraphQL path works: `setKeyValueIpAllowList` without `confirm` → `extensions.code KEY_VALUE_RESTART_CONFIRMATION_REQUIRED` with the phrase. The dashboard path works too: the typed "Delete all data and enable external access?" dialog → `config_restart` about 41 s → `available`, public.

## Root cause

- `lego/backend/internal/api/render_openapi.go:142-171` `renderQueryExtensions` is the allowlist of bex query parameters a Render operation may carry. `"update-key-value"` (`:156`) and `"update-postgres"` (`:166`) allow only `dryRun`, and `"failover-postgres"` is absent. Every other operation whose handler reads `confirm` is listed: `update-service`, `create-deploy`, `rollback-deploy`, the service, Key Value and Postgres delete/suspend/resume verbs, and `restart-postgres`. The refusal is emitted at `:739`.
- The handlers read the query parameter anyway:
  - `lego/backend/internal/keyvalue/rest.go:391` (`handleUpdateKeyValue`: the w4/m127 protected phrase, and w4/m233's restart phrase).
  - `lego/backend/internal/postgres/rest.go:498` (`handleUpdatePostgres`: the w4/m127 rename/upgrade phrase).
  - `postgres/rest.go:281-282` (the `failover` handler, guarded at `postgres/lifecycle.go:102`).
- **History.** These `confirm` entries arrived with the validator itself (a2dda880e, 2026-07-20). w4/m127 later guarded failover, rename, major-version upgrade, durability and eviction, and recorded "REST reads `?confirm=`", but never extended the allowlist. So this REST path has refused since m127 shipped, and w4/m233's restart phrase inherited it.
- **Not affected:** `scale-service` also rejects `confirm`, but its handler never reads it and `Scale` has no guard. The bex-only `PUT /v1/key-value/{id}/ip-allow-list` is outside Render's spec, so it is not validated, and its `confirm` reaches the handler (`keyvalue/rest.go:325`).

## Fix (target behavior)

- Add `"confirm": {}` to `update-key-value`, `update-postgres` and `failover-postgres`, beside their existing entries.
- Add a structural test, routed through the validating mux, that maps every handler reading `confirm` to its Render `operationId` and asserts it is allowlisted. Then the next guarded verb cannot repeat this.
- Live acceptance: step 2 succeeds and enables access (`config_restart`, then `available`, public). A wrong phrase still returns the coded refusal, and the controls are unchanged.
- **Unverified:** MCP (`update_key_value` / Postgres tools take `confirm` as an argument, not a query parameter). The Postgres guards were reached only at the validator, with no protected fixture.

Estimate: 30m. Unblocks the REST bullet of w4/m233's DoD.
