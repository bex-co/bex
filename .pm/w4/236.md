# Metrics puts runtime service changes under Configuration

Why: choosing Lifecycle should show when the service actually stops or resumes, so those transitions can be compared with its metrics.

**Severity:** minor · **Estimate:** 55m · **Worker:** worker4. Source: continuous functional qa-find-bugs pass 52, 2026-10-10, using the muse.env login helper; user-directed w4 placement. Research HEAD: `08d5d57b97ba0927c240849960074f8979a09734`. Goal linkage: ADR010 observable hosting, ADR008 reliable human workflows, and the existing Metrics timeline contract from w5/m36/t004.

## Reproduce and target behavior

1. Create an owned Free image web service and wait for its initial deploy to reach Live. The fixture below served `qa-a52-web-v1\n` from its public URL.
2. Suspend it through Settings and wait for the runtime event. Resume it and wait for the original marker to serve again. These operations worked; the actual runtime events exist in the API.
3. Open `/services/<id>/metrics?range=30m`, reveal Event timeline, then choose Lifecycle. Only `suspender_added` and `suspender_removed` appear.
4. Choose Configuration. The actual `service_suspended` and `service_resumed` transitions appear beside `display_name_changed` and `idle_timeout_changed`.
5. Reload, reveal the timeline again, and repeat both choices. All includes all nine events; Lifecycle still shows two intent events while Configuration shows five, including the two runtime transitions. Repeat at 390px width: the same classification fails with no outer page overflow.

**Expected on the captured nine-event dataset:** All retains nine events; Deploys retains its two deploy events; Lifecycle includes the two existing suspension-intent events plus the actual suspended/resumed runtime events (four); Configuration keeps the two name changes and idle-timeout change (three). In the broader known runtime family, server_failed, server_available, service_hibernated and service_woken also belong to Lifecycle, rather than falling into Configuration. Those four siblings were not emitted during this pass.

The All view, time-range filtering and legacy lifecycle entries work. This is wrong categorization; events are not missing from the API or All view. The existing coarse category selector remains the product design; this does not request Render's checkbox tree.

Viewed evidence: `.playwright-mcp/qa-metrics-timeline-a52-filter.png` includes the selected Configuration control and the two misplaced runtime events. `qa-metrics-timeline-a52-configuration.png` shows the timeline alone and is supplementary. `qa-service-a52-ledger.json` retains the full journey; `qa-service-a52-console.txt` has zero warnings/errors before logout. Complete inputs/results below survive handoff; screenshots are ignored local artifacts.

## Root cause and fix

- `dashboard/src/features/events/lib/timeline.ts:11–18` has a six-member LIFECYCLE_TYPES allowlist with older intent names and selected scaling/restart names. It omits the six current runtime-status names. At :35, Lifecycle accepts only that set; at :36–40, Configuration accepts every non-deploy/non-lifecycle event. Thus both captured runtime facts deterministically land in Configuration.
- The existing Events catalog at `service-event-catalog.ts:42–54` already groups the nine status names under serviceStatus, including the six missing runtime names. They are established vocabulary, not proposed new event types. Backend constants are in `lego/backend/internal/events/service.go:174–189`, and the observed fact producer uses `store/event_facts.go:37–44`; suspend/resume are separate facts from the older suspender intent records.
- `event-timeline.tsx:35–41` receives the complete serviceEvents data through the shared hook and invokes the classifier; its rendering at :81 onward uses the returned list. The route `services.$serviceId.metrics.tsx:77,119–126` passes the selected toolbar state as the filter prop. The fresh All/Configuration/Lifecycle results prove that state and data reach this consumer correctly. A backend filter or event-producer change cannot repair this local omission.
- The helper checks timestamp bounds before category, so the captured ISO timestamps inside the selected range rule out a time-zone or expired-window explanation. The cause is plain Set membership; no framework serializer or request failure is being inferred.

**Bounded target:** add the complete known runtime-status family to Lifecycle while preserving the six already accepted lifecycle types. This means the nine catalog serviceStatus types plus the three already accepted instance_count_changed, autoscaling_config_changed and plan_changed. Keep current deploy classification, configuration changes, and unknown/missing-type fallback behavior unchanged. Reuse existing vocabulary where that avoids drift, without merging the fine-grained Events-tab inclusion filter with this coarse classifier. Test the independent expected category mapping, not a list derived from the same set under test.

It does not change chart marker classification: `chart-events.ts` shares window semantics but does not call filterTimelineEvents; Metrics chart markers continue to show all events as the current accepted design does. Keep legacy suspender events, restart, instance-count, autoscaling-config and plan-change entries in Lifecycle. Ordinary settings events stay Configuration; unknown and missing types remain admitted by All and the current Configuration fallback; invalid/out-of-range timestamps remain excluded by every category. Existing deploy/start/end and cron-run handling remains. Other missing deploy-family category names are an adjacent source-only question, not a live claim or scope expansion in this note. Error/loading/empty timeline states and pagination remain unchanged.

**Unverified:** live sleep/wake, failed/available runtime facts, private/worker/cron/static category journeys, REST/MCP event reads, Chinese UI and physical screen-reader behavior. GraphQL already supplies complete correct events; the acceptance fix is in the dashboard. Renderer tests must preserve nullable type/timestamp handling.

Render's current exact treatment of these Bex-only runtime facts was not measured. No API parity claim or new checkbox-tree feature is invented.
