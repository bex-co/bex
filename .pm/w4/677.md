# 677 — an agent-session transcript harvest holds about 5× the driver log in bex-api memory, once a minute per running session on every replica

Why: this was half of w4/671's outage. Both bex-api replicas harvested the same 64k–88k-chunk session about once a minute, and each harvest's transients alone neared the old 128Mi limit. w4/671 raised the limit to 512Mi, but several large sessions running at once can still stack these transients.

- **Source / severity / estimate:** follow-up of [w4/671](done/671.md), 2026-11-15 (`/loopx w4`). Minor now that the limit is 512Mi. ~1h30m.
- **Evidence:**
  - `harvestTranscript` (`lego/backend/internal/agentsessions/completion.go`) reads the whole log as one string, up to `maxTranscriptLogBytes` = 16 MiB (`lego/backend/internal/sandbox/service.go`).
  - `parseTranscriptLog` then copies every line (`[]byte(line)` and `json.RawMessage`), and `agenttranscript.Coalesce` builds the items.
  - Parse + coalesce of a 16 MiB log allocated about 68 MiB in a local measurement (GOGC=off, 30,804 chunks).
  - Production log `ags-dbsjomf35ies73daah60` was harvested by both replicas at 05:13–05:20 UTC on 2026-11-15.
- **End state:**
  - A harvest's peak allocation stays within 2× the log size. Do it by streaming lines from the exec reader instead of holding the whole string, and by not re-copying each line.
  - Only one replica harvests a given session per tick, for example through the existing store claim/lease pattern.
  - A test pins the allocation bound with `testing.AllocsPerRun` or a `MemStats` delta on a 16 MiB log.
- **Render:** n/a (platform resource use).
