# 518 — The agent-session list filters `tag`, `repo` and `cursor` (REST and GraphQL), and the tool-output `toolCallId`, answer `500` / `INTERNAL` for a NUL byte or invalid UTF-8; a NUL in an agent-session id answers "authorization service unavailable" — the w4/485-492 input class on the agent surface

Why: a request string that cannot be a Postgres text value reaches the database bind and comes back as a server fault (a 500 that only says "internal error"), where the same list already answers an unknown cursor, tag or repo with an empty page and an unknown session id with `FORBIDDEN`. The class was fixed route by route for services, projects, environments and registry credentials in w4/485-492; the agent routes were not covered, and the dashboard turns a URL query string into one of these requests.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 116, 2026-11-05 UTC (`muse.env`, `bex-canary`); **minor** (a crafted input yields a 5xx; no data effect); ~40m.
- **Probe:** read-only, signed in, from the page; workspace `tea-d98210cbbpdc73dcrkvg`, real session `ags-dbijobqt5fis7381jmv0`.

  | Request | Answer |
  | --- | --- |
  | GraphQL `agentSessions(ownerId:…, limit:3)` | `200` data, 3 sessions |
  | `agentSessions(…, tag:"\u0000")` | `200` `{"errors":[{"message":"internal error","extensions":{"code":"INTERNAL"}}]}` |
  | `agentSessions(…, repo:"\u0000")` | the same `INTERNAL` |
  | `agentSessions(…, cursor:"\u0000")` | the same `INTERNAL` |
  | `agentSessions(…, cursor:"not-a-cursor")`, `tag:"<5000×x>"`, `repo:"no such repo"` | `200` `{"agentSessions":[]}` (the intended "unknown ⇒ empty page") |
  | `agentSessionToolOutput(id:<real>, turn:1, toolCallId:"\u0000")` | `INTERNAL: internal error` |
  | `agentSession(id:"\u0000")`, `agentSessionTranscript(id:"\u0000")`, `agentSessionAttachments(id:"\u0000")` | `authorization service unavailable` (no `code`) |
  | `agentSession(id:"asn-00000000000000000000")`, `agentSession(id:"qa-not-a-session")` | `FORBIDDEN: forbidden` |
  | `agentAttachment(id:"\u0000")` | `AGENT_ATTACHMENT_NOT_FOUND: agent attachment not found` (the correct handling) |
  | REST `GET /v1/agent-sessions?ownerId=…&limit=1` | `200` |
  | REST `…&tag=%00`, `…&repo=%00`, `…&cursor=%00`, `…&tag=%FF` | `500 {"error":"internal error","id":"internal_error","message":"internal error"}` for each |

  - The dashboard reaches it: `/agents?tag=%00` renders "Couldn't load" while 20 session links were still counted on the page.
  - A NUL in a REST path segment (`/v1/agent-sessions/%00`) is refused by the browser before it reaches the server, so the REST id case was not probed.
- **Root cause:**
  - `lego/backend/internal/store/agentsessions.go:528-584` `ListAgentSessions` binds `q.Tag` (`:549`), `q.Repo` (`:552`) and `q.Cursor` (`:564`) as text parameters and returns the driver error unclassified at `:570`. Postgres raises SQLSTATE 22021 for NUL or invalid UTF-8, and nothing maps it, so it surfaces as `INTERNAL` / `500`. The sibling helper `textBindable` (`store/store.go:2930`) exists for this and is used by `store/{environments,projects,registrycredentials}.go`, but not by the agent-session store.
  - `store/agenttranscripts.go:216-219` `AgentSessionToolOutputs` binds `toolCallID` the same way.
  - The id cases answer `authorization service unavailable` before the store is reached; the mechanism is not opened here. It matches w4/489's finding for an `ownerId` with NUL or invalid UTF-8 (the authorization check cannot take the string), which suggests the same boundary.
- **Fix (target behavior):** the agent surface answers these inputs the way it already answers their ordinary-unknown neighbours.
  - `tag`, `repo` and `cursor` that cannot be bound return the same empty page as an unknown value (`ListAgentSessions` returns `[]` early when any of the three fails `textBindable`); a `toolCallId` that cannot be bound is a not-found/empty tool output like an unknown one.
  - An agent-session id that cannot be a stored id answers `FORBIDDEN: forbidden`, the same body as `asn-0000…` and `qa-not-a-session`, so that "no such session" and "not yours" stay indistinguishable (no existence oracle) and no authorization-service fault is reported.
  - REST, GraphQL and MCP read through the same service, so all three move together; the dashboard needs nothing.
- **Tests:** a store-level table test over `ListAgentSessions` and `AgentSessionToolOutputs` with `"\x00"`, `"\xff"` and a valid control, asserting an empty result and a nil error; REST and GraphQL handler tests asserting `200 []` / no `INTERNAL` for the filter cases and `FORBIDDEN` for the id case. Keep the existing unknown-cursor test as the control.
- **Blast radius:** 2 text-bound call sites in the agent store found by reading (`ListAgentSessions`: 3 parameters, `AgentSessionToolOutputs`: 1); other agent-session store methods taking a caller string (transcript `afterSeq` is numeric; attachments, tags on write, repo on create, PR lookups) were not enumerated and belong to the same pass. Global versus allowlisted: allowlisted to the agent store, mirroring w4/490's per-method guards.
- **Adjacent classes:** unknown session ⇒ `FORBIDDEN` stays; unauthenticated stays ahead of all of it; `agentAttachment` shows the not-found shape the other id routes should take.
- **Unverified:** the id path through the authorization service (cause inferred from w4/489), mutations that take caller strings (`createAgentSession` tags, repo, prompts) were deliberately not exercised because they create billable sessions, MCP tools, and the REST id route with a NUL.
- **Render:** n/a (the reference for agent sessions is Devin; its handling of malformed filters was not compared). The sibling Render-parity rule (w4/489, 490) is to answer 4xx or an empty page, never a server fault.
- **Dedupe:** w4/489 (`ownerId`), 490 (path ids on postgres, key-value, projects, environments, registry credentials), 491 (webhook and registry-credential names) and 492 (`operationName`) are done; none names the agent routes. `grep -rli "agentSessions\|agent-sessions" .pm/w4` finds no NUL/UTF-8 item. No DO_NOT_DO item applies.
