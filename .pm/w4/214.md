# Last 30 minutes hides collected CPU and response-time metrics

Why: the Metrics page can tell a running service's owner “No data in range” for CPU and response times even though the same retained time window contains samples; its 15-second chart step is also used as the rate lookback, equal to the configured scrape interval.

Severity: minor. Estimate: 50m, one backend rate-window fix with behavioral coverage and consumer checks. Source: continuous `$qa-find-bugs`, 2026-10-07 local / 2026-10-08 UTC, cycle 6, `muse.env` account, workspace `bex`. Repository examined: `12bb73242`. Goal: ADR008 dependable hosting and ADR010 truthful observability; ADR018's service Metrics surface.

## Repro and controls

1. Create an owned Free image web service. This sweep used `qa-20261007-c6-web-e94a`, `srv-db3j8us3a6ns73b87og0`, BusyBox 1.37 with HTTP on port 3000. Its create and two hook-triggered deploys reached Live; external HTTPS served the fixture marker. The instance was several minutes old when the metrics were read, before the later sleep test.
2. Open `/services/<id>/metrics`, select **Last 30 minutes**, wait for queries to finish. Memory and instance history render, but CPU and Response Times show **No data in range**. Fresh-page reproduction at 06:25:22Z: the same two empty panels, memory 0.2% against 512 MiB and a visible instance chart. The UI requests `resolution: 15` for this preset.
3. Select **Last hour**: CPU and HTTP latency return collected samples. Return to Last 30 minutes: both are empty again. A changing time window is not the sole control: replay the identical fixed bounds `06:14:52.508Z`–`06:21:52.508Z` while changing only resolution. CPU: 15s → zero series; 30s → 3 series / 14 points; 60s → 3 series / 10 points. HTTP latency p90: 15s → zero series; 30s → 1 series / 4 points; 60s → 1 series / 5 points. All six responses are HTTP 200, without GraphQL errors; their complete requests and responses are below.

**Alignment caveat:** an earlier integer-aligned `06:14:00Z`–`06:21:00Z` control did return 7 CPU points at 15s, versus 10 at 30s and 60s. Its 15s latency stayed empty. Do not claim that every 15s CPU query is empty: the observed defect is an empty or sparse rate series depending on sample/evaluation alignment. This anomaly is consistent with a range that barely admits two samples when scrape timing varies; raw production scrape timestamps were not inspected, so that timing explanation is an inference.

**REST boundary:** REST CPU and latency at `resolutionSeconds=15` correctly return HTTP 400 `invalid query parameter "resolutionSeconds"`; 60s returns data. The dashboard uses the accepted GraphQL 15s path. Preserve REST's validation; do not expand its resolution contract as part of this fix. MCP was not called live.

Evidence inspected: `.playwright-mcp/qa-metrics-c6-rate-window-ready.png` shows settled memory and empty CPU (the first `rate-window.png` captured polling skeletons and is not proof); `.playwright-mcp/qa-metrics-c6-fresh-30m-ui.json`, `qa-metrics-c6-30m.json`, `qa-metrics-c6-1h.json`, `qa-metrics-c6-same-bounds-matrix.json`, `qa-metrics-c6-fixed-window-matrix.json` and `qa-metrics-c6-rest-control.json`. Screenshots and these files are session-local; the durable API probes below carry the finding.

## Mechanism and fix

- `dashboard/src/features/metrics/lib/range.ts:17` offers the 30-minute preset with a 15s resolution. `use-metrics.ts` sends that value as GraphQL `query.resolution`; the fixed-window probes show the backend result, not a chart mapping failure.
- `lego/backend/internal/metrics/source.go:302-303`, `promResourceQueryFor`'s CPU branch, builds `rate(container_cpu_usage_seconds_total[stepSeconds(req.Resolution)s])`.
- `source.go:424,432-434`, `promQueryFor`'s HTTP-latency branch, uses that same step as the histogram buckets' `rate` lookback. These are separately traced branch sites; `sumRate` has one production caller, this latency branch.
- `deploy/gitops/base/prometheus.yaml:350,396` configures Traefik and cAdvisor scrapes at 15s. A 15s rate window cannot reliably contain two counter samples. The reviewed chart pin is `prometheus|25.27.0` in `deploy/helm-artifacts.lock:19`; its [upstream Chart.yaml](https://github.com/prometheus-community/helm-charts/blob/prometheus-25.27.0/charts/prometheus/Chart.yaml) declares Prometheus v2.54.1. That version's [extrapolatedRate](https://github.com/prometheus/prometheus/blob/v2.54.1/promql/functions.go#L68) drops float-counter series with fewer than two samples. [Prometheus range-selector semantics](https://prometheus.io/docs/prometheus/latest/querying/basics/#range-vector-selectors) exclude the left boundary. The actual running server image and raw scrape timestamps were not read.

Keep the requested query-range step, and choose a separate rate lookback with a safe floor for the reviewed 15s scrape cadence, for example `max(step, 60s)`, only in the CPU and Prometheus histogram-latency branches. Record the floor's scrape-cadence dependency. Keep existing namespace/pod/router selectors, counter-reset handling, CPU percentage normalization and quantile/group labels.

**Shared-code scope:** grep of non-test Go found one production caller each for `promResourceQueryFor` (`source.go:223`) and `promQueryFor` (`source.go:152`), the two source factories. `stepSeconds` has **12** production calls: `source.go:156,223,303,344,413,424,633,669,719,739` and `lokisource.go:62,129`. Do not globally clamp it: it also controls chart spacing, datastore reads and count/byte windows. In particular, HTTP_REQUESTS and BANDWIDTH use per-bucket counts/increases; widening their lookbacks would overlap buckets. The Loki latency path already has its own bucket implementation and should stay unchanged.

REST `/v1/metrics/cpu` and `/http-latency`, GraphQL `metrics(name: CPU|HTTP_LATENCY)`, and MCP `get_metrics` share the metric service. MCP `cpu_usage` aliases `cpu`, and `resourceId/resource`, `resolution/resolutionSeconds` are the current input aliases. The dashboard hook has **three** production component consumers: ApplicationMetricsCard, NetworkMetricsCard and ScalingRecentMetrics (besides its own definition). Apply the fix in the backend branches rather than hiding empty data in one card.

**Resource family:** live failing/control evidence is web only. CPU applies to App pod histories (web/private/worker/cron); static sites have no App pods, though their router-backed Prometheus latency uses the request builder. Postgres and Key Value have their separate datastore metric paths, with unserved CPU pairs already refused by w8/061. These sibling surfaces are code-traced, not live-verified here.

**Adjacent states:** a genuinely new pod with fewer than two scrapes and a truly traffic-free histogram may remain empty; no invented zero series or new “warming up” response field. Unavailable sources remain errors; invalid resolution/window remains a named refusal. Existing authorization and not-found behavior stays unchanged, including no resource-existence disclosure to unauthorized callers. None of those states becomes “no data” through a new catch-all.
