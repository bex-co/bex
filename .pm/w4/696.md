# 696 — A refused autoscaling metrics read is logged as `"error":"unknown"`, so the log cannot tell a 403 from a metrics-server outage

Why: w4/m364 made a failed utilization read visible, but the operator log carries no cause. An operator paged by `AutoscalingMetricsUnavailable` cannot tell a lost RBAC grant from metrics-server being down without reproducing it.

- **Source / severity / estimate:** w4/m364 DoD 4 replay, `/loopx w4`, 2026-11-17 00:53–00:58 UTC, local CAPD cluster (`bex-operator:dev`, carries `71f81e13f`); **minor** (diagnostics only); ~30m.
- **Probe:** removed the `metrics.k8s.io` rule from `bex-manager-role` (`kubectl auth can-i list pods.metrics.k8s.io --as=system:serviceaccount:bex-system:bex-controller-manager` = `no`). A Starter autoscaled App then logged `autoscaling metrics read failed; holding the instance count` with `app`/`namespace`, but `"error":"unknown"`. The condition and the recovery worked.
- **Mechanism:** `NewMetricsServerReader` (`lego/operator/internal/controller/autoscale.go`, the `cs.Discovery().RESTClient().Get()…DoRaw(ctx)` call) returns client-go's generic server-response error. The discovery REST client does not decode the 403's `Status` body, so the error's message is `unknown`.
- **End state:** a refused read logs an error naming the HTTP status and reason (for example `metrics.k8s.io pods list: 403 Forbidden: …`), and a metrics-server outage logs a different one. A unit test with a fake REST server answering 403 and 503 asserts both messages.
