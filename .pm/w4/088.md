# 088 — Per-surface authorization parity closes clean: no adapter reaches a laxer path than its peers, and the layering makes that divergence structurally impossible

Why: `w4/087` recorded "authorization parity was not compared per surface at all" as its largest open limit — this closes it, and identifies *why* it closes, so the next person knows the guarantee rests on an architectural invariant rather than on 84 files happening to be written correctly.

Record from the live `/qa-find-bugs` loop, 2026-09-14 pass 35. **Read-only on production — nothing created, changed or deleted, and no new login session minted** (existing browser session reused, per `w4/085`). **No defect found.**

## The question

`TestAuthzGuardsEveryVerb` proves each exported **Service** verb refuses an unauthorized caller (325 of them — `w4/087`). It does not prove that REST, GraphQL and MCP each *reach* that verb. An adapter could call an unexported sibling that skips the gate, or reach past the service into the store, and the sweep would stay green while one surface was open.

## Three probes, all negative

**1. No adapter reaches past the service layer.** Every `*/rest.go`, `*/graphql.go`, `*/mcp.go` was scanned for direct `s.Store.…` / `s.Client.…` / `s.Secret.…` / `s.Authz.…` / `s.Pool.…` calls:

```text
no direct store/client access from any adapter file
```

**2. Every unexported method an adapter calls is harmless.** 60 distinct `s.<lowercase>(` call targets across the adapter files, and each falls into one of four classes — route/tool registrars (`registerDiskRoutes`, `registerLifecycleMCP`, …), pure renderers (`renderPostgres`, `toKeyValueList`, …), delegators to an exported swept verb, or self-authorizing. The four worth naming, because they are the only single-surface *mutating* paths:

| helper | surface | disposition |
| --- | --- | --- |
| `createWithAllowList` (`apps/mcp.go:1094`) | MCP only | resolves allow-list inputs, then `s.Create(ctx, req)` — the exported, swept verb |
| `applyServicePatch` (`apps/mcp.go:782`) | MCP only | dispatches to `s.Get` / `s.PreviewSetPlan` / exported setters |
| `applyEnvironmentPatch` (`environments/mcp.go:137`) | MCP only | dispatches to `s.Update` / `s.SetServices` |
| `applyProjectPatch` (`projects/mcp.go:126`) | MCP only | dispatches to `s.Rename` / `s.SetServices` / `s.SetDatabases` / `s.SetKeyValues` |

Two more that looked risky and are not: `monthToDateAt` (`usage/service.go:177`, called by all three adapters instead of the exported `MonthToDate`) authorizes itself at `:179` with `core.RelCanView`; and the REST-only live-log subscription path authorizes in `subscriptionWorkspace` (`logs/rest.go:282-299`) with `core.RelCanViewLogs` for app, database and key-value alike, then streams through the exported `FollowLogs`.

**3. The file-name assumption was checked, not assumed.** Adapters do not all live in `rest.go`/`graphql.go`/`mcp.go`: of **84** files that register a route, tool or GraphQL field, **7** are named otherwise (`api/server.go`, `apps/disks.go`, `apps/disk_snapshots.go`, `cliauth/service.go`, `store/api.go`, plus the `gqlutil`/`mcputil` helper libraries). Re-probing those found one that calls the store directly in the same file as its adapters — `apps/disks.go` — and every one of its verbs authorizes first:

| verb | gate |
| --- | --- |
| `AddDisk:106` | `AuthorizeApp(RelCanCreate)` at `:107`, before `Store.CreateDisk:133` |
| `ListDisks:150` | `AuthorizeApp(RelCanView):152`, or workspace-wide `Authorize(RelCanView):165` |
| `GetDisk:189` | `authorizeDisk(RelCanView):190` |
| `UpdateDisk:201` | `authorizeDisk(RelCanCreate):202`, before `Store.UpdateDisk:224` |
| `DeleteDisk:241` | `authorizeDisk(RelCanCreate):242`, before `Store.DeleteDisk:246` |

`authorizeDisk` (`:261`) is worth copying elsewhere: it runs the workspace `Authorize(relation)` at `:268` **before** `Store.GetDisk` at `:273`, then re-authorizes against the owning app at `:277`. Because the workspace check precedes the ID lookup, a caller who lacks access cannot use a disk id to learn whether that disk exists — the existence-oracle trap, already avoided here.

## Why this closes by construction rather than by luck

Adapters call only exported Service verbs; exported Service verbs are exactly what the reflection sweep walks. So **a per-surface authorization divergence cannot exist while that layering holds** — the Service layer is the single choke point, and proving the choke point is sufficient. `w4/087`'s worry about "a laxer sibling" is answered structurally.

That reframes what is worth defending. The valuable guard is not a new per-surface authz test; it is the **layering invariant itself** — "no adapter touches the store, the k8s client, the secret store, or the authz checker directly". Probe 1 above is three lines of `grep` and would make that invariant enforceable in CI, which today it is not. That is the cheap, durable follow-on, and it is a better use of effort than re-checking 84 files by hand next time.

## Unverified

- **Relation correctness was not judged, only presence.** Every verb authorizes; whether each asserts the *right* relation (`RelCanView` vs `RelCanViewSensitive` vs `RelCanCreate`) is a separate question this pass did not open. `w4/082` covers the scope-class analogue of it.
- **The residual way divergence could still occur was not swept**: two exported verbs for the same operation with different relations, where one adapter calls one and its peers call the other. The layering invariant does not exclude that; nothing was found suggesting it, but nothing was enumerated either.
- Probe 2 classified 60 call targets by reading names and delegation lines; the four mutating helpers were read in full, the registrars and renderers were not.
- `gqlutil`/`mcputil` were excluded as shared helper libraries rather than inspected.
