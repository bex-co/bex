## Objective

`GET /.well-known/oauth-protected-resource` advertises `scopes_supported: ["bex.read","bex.write","bex.sensitive"]`, but a minted API key is refused when it requests one. Decide which side is right — this is the part of the milestone with security weight, not cosmetics.

## Context

Measured live (2026-09-13):

```text
GET https://api.bex.co/.well-known/oauth-protected-resource
→ {"authorization_servers":["https://oauth.bex.co"],"bearer_methods_supported":["header"],
   "resource":"https://api.bex.co/mcp","scopes_supported":["bex.read","bex.write","bex.sensitive"]}

POST https://oauth.bex.co/oauth2/token  grant_type=client_credentials&client_id=…&client_secret=…&scope=bex.read
→ {"error":"invalid_scope","error_description":"… The OAuth 2.0 Client is not allowed to request scope 'bex.read'."}

# same request with no scope parameter
→ access_token, and that token reads /v1/services and /v1/owners/{id}/limits with 200
```

Cause: `apikeys/service.go:495-506` creates the Hydra client with `ClientName`, `GrantTypes: ["client_credentials"]`, `AuthMethod: "client_secret_post"` and `Metadata` — and **no `Scope`**. Hydra therefore allows no scopes, so any `scope=` is refused and every API-key token is scopeless.

Relevant existing position: `dashboard/CLAUDE.md` records that `OAUTH_API_SCOPE` is "**ignored as a second matrix** (w8/m27)" and that consent uses the closed vocabulary `bex.read`/`bex.write`/`bex.sensitive` "(plus identity scopes; `bex.api` is stripped from third-party grants)". That decision is about **third-party consent**; whether it was meant to leave first-party machine keys scopeless is exactly what this task must establish rather than assume.

## Steps

1. Read `w8/m27` and ADR012 §7/§8 and state what scopes are *for* in bex today. If they only constrain third-party consent, then a scopeless first-party key is intentional and the **discovery document** is the thing that is wrong for this audience — say so and narrow what it advertises, or document that `scopes_supported` describes the consent vocabulary rather than what a client-credentials key may request.
2. If scopes are meant to constrain API keys, grant the client the scopes it should have at mint and make the gate enforce them.
3. **Answer the privilege question explicitly**, because it is the reason this task exists: a scopeless token today reads `/v1/services` and `/v1/owners/{id}/limits` successfully. Determine whether it can also reach the `bex.sensitive` class — connection strings, env-var values, secret files. If a scopeless key can read those, the closed vocabulary is not gating anything for API keys and that should be a conscious decision, not a side effect of an omitted struct field.
4. Whatever is decided, a caller who follows the discovery document must not be refused.
