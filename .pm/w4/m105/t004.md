## Objective

Record how bex's API-key credential model relates to Render's, so the divergence reads as a decision rather than drift.

## Context

Render's API keys are opaque bearer tokens (`rnd_…`) used directly in `Authorization: Bearer`. bex mints Hydra `client_credentials` clients requiring a token exchange — a deliberate ADR012 choice, but one that changes the user's workflow and is currently undocumented at the point of use. That difference is why using the secret as a bearer 401s, which is the first thing any Render-shaped client will do.

`docs/ADR018-render-parity.md` has an identity/keys row; `docs/ADR012-auth.md` §7/§8 owns the model.

## Steps

1. Record the divergence in `docs/ADR018-render-parity.md`: Render bearer vs bex client-credentials, and what it means for a client generated from Render's spec.
2. Check the three surfaces agree on what they expose for a key — REST, GraphQL and MCP should all offer the id now that it is user-facing.
3. Reflect t002's scope decision in ADR012.
4. File residual drift as a w4 note.
