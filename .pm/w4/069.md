# 069 — The audit log and API-keys table still show a raw Kratos subject where webhooks show an email

Why: the audit log exists to answer "**who** did what" and answers with `c73bb20d-40ff-42df-8597-c9a428697d12`; the resolver that turns that into an email already exists in this codebase and is used on exactly one of the three surfaces that need it.

Found in the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-09-13 pass 12, sweeping account settings. **Read-only — nothing was created, changed or deleted for this finding.**

## The control case: webhooks resolve it, on the same page-load's data

`/webhook/<whk-id>` renders **"Created by puncsky@gmail.com on September 13, 2026"** (observed in pass 7). The backend gives it the same raw subject — `webhooks/graphql.go:43` and `apikeys/graphql.go:35` both return `CreatedBy` verbatim, and both store the minting caller's identity subject (`apikeys/service.go:45`: "minting caller's identity subject"). The difference is entirely client-side:

`dashboard/src/features/webhooks/hooks/use-webhook-creator.ts:10-28` looks the subject up against `WorkspaceMembers` and returns `member?.email || member?.userId || subject` — resolving when it can, falling back to the raw value only when it cannot. Despite its name it is **fully generic**: it takes a subject string and knows nothing about webhooks.

## This is an unfinished application of a position the project already took

`w6/001` records that `w6/m7` fixed this exact class on the members surface: bex "**mints** stable opaque `own-<xid>` ids per identity … and reports them as the members `userId` — **no more raw Kratos subject leaking there**." So "don't leak Kratos subjects to users" is settled; it just was not carried to these two surfaces. There are now three treatments in play — minted `own-` id (members), resolved email (webhooks), raw subject (api keys, audit) — so the fix should **name one** rather than merely "make them consistent".

**Target behavior:** a human-readable identity where a human reads it — the webhook treatment, i.e. the member's email, falling back to `own-`/`userId` and only then to the subject. The audit log is the one that matters most, since its column header is literally "Actor" and its stated purpose is who-did-what.

## Bounded fix

Move `use-webhook-creator.ts` to a shared hook (it needs no webhook knowledge — rename to something like `useMemberIdentity(subject)`), use it in `api-key-row.tsx` and `audit-event-row.tsx`, and check the fourth site. Two considerations worth deciding rather than guessing:

- **A subject that is not a current workspace member must still render something honest** — a revoked member, or a machine caller that is an API key rather than a person. The existing fallback chain already handles this; keep it rather than rendering "Unknown".
- **The audit log is a long table**: one `WorkspaceMembers` query shared across rows (the hook already uses `fetchPolicy: "cache-first"`), not one lookup per row.

Sub-hour across one hook move and two or three call sites, so an inbox note rather than a milestone. It is deliberately **not** folded into `w4/m101`'s accessible-name tasks: that milestone is about control *labelling*, this is about *data* rendering.
