# 383 — Blank project and environment names are refused with a bare "bad request" that names no field

Why: a REST, GraphQL or CLI caller that sends a blank project or environment name, or an out-of-range notifications `limit`, gets `{"message":"bad request"}`, which says nothing about what to fix. `core.DecodeBody` (w4/m104) promises that "a bare 'bad request' alone is unreachable for body validation". Earlier fixes (w4/038, w4/369) were made one route at a time, and these sites were missed.

**Severity:** minor. **Estimate:** ~45m. **Source:** live `/qa-find-bugs w4` loop run p7r3, 2026-10-21 UTC, `muse.env`, workspace `bex-canary`, pin `9cace6b6e25d`. The fixture project `qa-20261021-p7r3-proj` (`prj-dbc4kohv5vjs73b9haeg`) was deleted in-run, and its environments return 404. The session was revoked.

## Probes (session-authenticated, from the page)

```
POST /v1/environments {"name":"  ","projectId":"prj-…"}    -> 400 {"error":"bad request","id":"bad_request","message":"bad request"}
PATCH /v1/projects/prj-… {"name":""}                        -> 400 {"error":"bad request",…,"message":"bad request"}
GraphQL renameEnvironment(id:"evm-…", name:"  ")             -> errors[0].message "bad request"
GET /v1/notifications?limit=0                                -> 400 {"error":"bad request",…,"message":"bad request"}
```

Controls that already name the problem:

- `GET /v1/environments` without `projectId` → `invalid query parameter "projectId"`.
- A duplicate environment name → `409 an environment named "prod" already exists in this project`.

## Root cause

These sites return the bare sentinel `core.ErrBadRequest` instead of wrapping it with a detail (`fmt.Errorf("%w: …", core.ErrBadRequest, …)`):

- `lego/backend/internal/environments/service.go:1276` (`validateEnvironmentName`, shared by create, update and rename).
- `lego/backend/internal/projects/service.go:425`, `:534` (project name).
- `lego/backend/internal/projects/rest.go:175`, `:197` (REST create and patch name/ownerId).
- `lego/backend/internal/notifications/rest.go:145` (`limit`).

A grep finds 18 `return …, core.ErrBadRequest` lines in non-test code under `internal/`. Not all of them are reachable bare: `GET /v1/environments`, whose source line `environments/rest.go:130` is bare, answered with a named parameter. So audit each site before changing it.

## Fix (target behavior)

- Every client-input rejection names the field and the rule, for example `name: must not be blank` and `query parameter "limit" must be between 1 and N`.
- The `bad_request` id and the 400 status stay the same.
- Because the detail is added in the shared verbs, REST, GraphQL and MCP get the same message.
- Leave non-input sites alone; only messages change:
  - `github/service.go:1567` (an upstream 4xx).
  - `apps/service.go:1687-1691` (SSH username parse).
- Add a source guard test so that a new bare `core.ErrBadRequest` return in a validation helper fails CI. Include an explicit allowlist for intentional ones.

## Acceptance

- The four probes above return messages that name `name` or `limit`.
- Regression tests cover the environment create, update and rename paths, project create and update, notifications `limit`, and the two controls (unchanged).
- Backend `go test ./...` and `make lint` pass.
