## Objective

t001 closes the two nested fields this hunt found. This task proves that two is the whole list — and makes it impossible to add a third without classifying it.

## Context

- The hunt's own grep found exactly two value-returning nested resolvers: `grep -rn "EnvVarsFrom\|SecretFilesFrom" lego/backend/internal --include='*.go' | grep -v _test` → `apps/graphql.go:691` (`envVarKeysResolve`, names only), `:703` (`envVarValueResolve`, **value**), `:727` (`secretFileNamesResolve`, names only), `:739` (`secretFileContentResolve`, **value**). That grep keys on two specific context readers and is therefore **not** exhaustive over "fields that return something sensitive".
- `TestMintAndSensitiveHeuristics` (`scope_matrix_guard_test.go:158-201`) already encodes the project's intent — "env-var value read must be sensitive", "secret-file value read must be sensitive", "env-group value read must be sensitive", "live SQL text must be sensitive" — but evaluates it over `classifiedOps`' keys, which are root fields only.

## The schema-graph half of this audit is already done — 2026-09-14 pass 26

A live introspection walk plus targeted probes narrowed this considerably. **The result strengthens `t001`'s scope rather than widening it: the gap is exactly the two `Service` fields.** Redo the resolver-level half (step 1 below) to confirm, but start from this.

**Method:** full `__schema` introspection, then a depth-4 walk from **every** `Query` root through the object graph, flagging any leaf field named `secret|password|content|value|*ConnectionString|*ConnectionPoolString|psqlCommand|snapshotKey|authToken`. 150 object types; 37 root→leaf paths found. Each path under a **read**-classified root was then probed live for whether it actually returns a value.

| path (root → leaf) | root's class | returns a value? |
| --- | --- | --- |
| `service.envVar.value` · `service.secretFile.content` | **read** (`:274`) | **YES — the gap `t001` fixes** |
| `service.envVarKeys.value` · `service.secretFileNames.content` | read | no — `""` (verified) |
| `envGroup.envVars.value` · `envGroup.secretFiles.content` | **read** (`:231`) | **no — `""` (verified live this pass)** |
| `envGroups.…` (same two leaves) | read (`:234`) | no — same masking |
| `webhookEndpoint(s).secret` | **read** (`:289`) | **no — `""` (verified live this pass)** |
| `apiKeys.secret` | read (`:196`) | no — `""` (verified; secret shown once at mint only) |
| `envGroupVar.value` · `envGroupSecretFile.content` | **sensitive** (`:233`, `:232`) | yes — correct, these are the reveal roots |
| `databaseConnectionInfo.*` (password, 4 connection strings, psqlCommand, replica strings) | **sensitive** (`:209`) | yes — correct |
| `keyValueConnectionInfo.*` | **sensitive** (`:246`) | yes — correct |
| `envVars.envVar.value` | **sensitive** (`:235`) | yes — correct |
| `customDomain(s).ownershipDnsRecord.value` | read | yes — **not a secret**: the TXT challenge is deliberately returned on authorized reads so the dashboard can recover the instruction after the add dialog closes (`docs/ADR005-custom-domain.md:28`) |
| `service.headers.value`, `metrics/datastoreMetrics.{labels,values}.value`, `databaseParameterSpec.value` | read | yes — not secrets |
| `diskSnapshots.snapshotKey` | — | **unchecked**; per `lego/backend/CLAUDE.md` it is an HMAC-signed *reference to* an object, not its contents, so probably fine — confirm rather than assume |

So every secret-bearing path under a read root **masks**, except the two `Service` fields. The env-group and webhook-endpoint cases are the strongest controls: they are the same shape (secret nested under a read-classified root) and they get it right, which is what makes the `Service` pair a defect rather than a design.

**Limits of this method, which step 1 must still cover:** it matched on *field names*, so a sensitive field with an unexpected name is invisible to it; it was depth-limited to 4; and it walked **`Query` only**, not `Mutation`.

## Steps

1. Enumerate every GraphQL field whose resolver can return a credential, secret, connection string, or live SQL text — not just the two found. Candidates to check by name and by resolver: env groups (`envGroupVar`, `envGroupSecretFile` exist as roots — do they also nest under an `EnvGroup` type?), datastore connection info (`databaseConnectionInfo`/`keyValueConnectionInfo` are roots — is there a nested `Database.connectionInfo`?), API keys, SSH keys, deploy-hook URLs, registry credentials, agent-session credentials. Paste the grep and the count.
2. Do the same sweep for **mutations**: the collector treats Query and Mutation identically, so a sensitive nested selection under a write-classified mutation root has the same shape of gap. State whether any exists.
3. Extend the guard so the audit cannot rot: a field reachable from a root classified below sensitive, whose resolver reaches a sensitive reader, fails the test with a message naming the field.
4. Record the resulting registry (or classification table) somewhere a reviewer will look — `docs/ADR012-auth.md` §7 is where the scope vocabulary lives.
