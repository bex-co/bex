## Objective

`collectGraphQLTopLevel` classifies a GraphQL document by its **root fields only**, so `{ service(id:){ envVar(key:){ value } } }` is classified `GQL Query.service` → `core.OpClassRead` even though it returns a secret. Make the class the document actually needs, so a `bex.read` token cannot select a sensitive nested field.

## Context

- `lego/backend/internal/api/scope_matrix.go:217-246` — `collectGraphQLTopLevel` appends `"GQL "+kind+"."+n.Name.Value` for each `*ast.Field` and **never recurses into `n.SelectionSet`**. It does recurse through `InlineFragment`/`FragmentSpread`, but only to find more *top-level* fields.
- `lego/backend/internal/api/scope_matrix_ops.go:274` — `"GQL Query.service": core.OpClassRead`; `:279` the same for `Query.services`.
- The two nested resolvers that return values: `apps/graphql.go:347-353` (`Service.envVar` → `envVarValueResolve` at `:698`) and `:361-367` (`Service.secretFile` → `secretFileContentResolve` at `:739`). Both reach the secrets feature through the context readers (`core.EnvVarsFrom` / `core.SecretFilesFrom`).
- The classified siblings that already demand sensitive: `REST GET /v1/services/{id}/env-vars` (`:601`), `MCP list_env_vars` (`:399`), `GQL Query.envVars` (`:235`).

## Steps

1. Pick the mechanism and write down why. Two credible shapes:
   - **(a) Walk the selection set** and escalate the document's class when a field path matches a registry of sensitive nested fields (`Service.envVar`, `Service.secretFile`, plus whatever t002 finds). Keeps one gate, costs one deeper AST walk per request — the document is already parsed once for cost/scope, so reuse that parse.
   - **(b) Classify by type+field** rather than by root, i.e. key the matrix on `GQL <Type>.<field>` for every field that has a resolver, not just roots. More faithful, much larger table, and the CI generator must change with it.
   (a) is the smaller change and is recommended; (b) is the more complete model if the project wants field-level scoping generally.
2. Whichever is chosen, the escalation must be **fail-closed**: an unrecognized nested field under a known root keeps today's behavior, but a nested field that resolves through a sensitive reader and is *not* in the registry must fail the guard test (t002), not silently pass as read.
3. Preserve the keys-only projections at read: `Service.envVarKeys` and `Service.secretFileNames` must stay `read`, or every service page starts demanding `bex.sensitive`.
4. Keep the FGA role gate untouched — `secrets/service.go:207-217`'s double assertion (including the uncached `AuthorizeAppFresh`) is a different axis and still has to refuse a non-sensitive role.
5. Check aliases: the collector is shared by the scope gate **and** `graphqlOperationDims` (`scope_matrix.go:249-262`), which derives bounded telemetry labels from the same walk. Escalating the class must not change the telemetry label's cardinality — that bound is what keeps a hostile client from minting a metric series per request.

## Acceptance criteria

- [ ] A document selecting `service { envVar { value } }` classifies as sensitive; one selecting `service { envVarKeys { key } }` stays read; a test covers both.
- [ ] The same holds for `service { secretFile { content } }` vs `service { secretFileNames { name } }`.
- [ ] Fragments and inline fragments reach the same verdict as the equivalent inline selection — a sensitive field hidden behind a fragment spread must not evade escalation.
- [ ] A non-sensitive **role** is still refused by the FGA gate regardless of scope.
- [ ] Telemetry labels remain bounded and unchanged in cardinality.
- [ ] `cd lego/backend && go test ./...` and `make lint` green.

## Out of scope

- Per-field scoping as a general model (option (b)) unless chosen in step 1 — record the decision either way.
- Mutations with the same nesting shape: t002 sweeps for them and this task fixes only what t002 finds, or a follow-up is filed.
