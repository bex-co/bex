## Objective

The milestone's central claim — that a `bex.read` token can read secrets through GraphQL today — is read from the classification code, not observed, because production cannot currently mint a scope-limited token. Close that gap with a real token once it can, so the fix is proven against the thing it protects.

## Context

- `w4/076` records that **pre-m105 API keys carry an empty Hydra `scope`** and that requesting `scope=` on them returns `invalid_scope`; they must be reminted.
- `w4/078` records that m105's fix (`f35701695`), which mints clients with the advertised scopes, is **merged but not deployed** — production's API-keys panel still shows no Client ID.
- So this task is blocked on the same deploy as `w4/078`'s re-probe, and the two should be run in one session.

## Steps

1. Wait for the m105 deploy (same discriminator `w4/078` uses: Settings → API Keys shows a Client ID).
2. Mint a **fresh** key, exchange `client_credentials` for a token requesting **only** `bex.read`, and confirm the granted scope is what was requested — not a superset.
3. With that token, run the two probes from the milestone DoD. **Before t001 they should succeed** (that is the bug, finally demonstrated); after t001 they must be refused.
4. With the same token, confirm the already-correct surfaces still refuse: `GET /v1/services/{id}/env-vars` and MCP `list_env_vars`.
5. With a `bex.sensitive` token, confirm all of them succeed — the permissive control, so the fix is not just "deny everything".
6. Paste all four transcripts into this task.

None — live verification.

## Acceptance criteria

- [ ] A token granted exactly `bex.read` is refused both nested GraphQL secret reads.
- [ ] The same token is refused the REST and MCP equivalents (unchanged behavior).
- [ ] A `bex.sensitive` token is granted all of them.
- [ ] The pre-fix behavior is captured too, so the milestone has a before/after rather than only an after.
