## Objective

Confirm the scope change leaves REST, GraphQL, MCP and the dashboard consistent, and record the Render relationship as a deliberate extension rather than inventing a behavior to match.

## Context

- The three surfaces already agree that a secret read is sensitive (`scope_matrix_ops.go:601` REST, `:399` MCP, `:235` `GQL Query.envVars`); this milestone brings the nested GraphQL path into line, so the sweep is confirming consistency rather than discovering it.
- The dashboard authenticates with a **Kratos session**, not a scoped OAuth token, so its masked-list-then-reveal flow should be untouched by a scope-class change. That is the control case worth checking rather than assuming.

## Steps

1. Re-check that REST, GraphQL and MCP agree on the class of a secret read, and that none of them changed **what** they return — the fix changes who may ask, not the payload.
2. Verify the dashboard's service Environment page still lists keys masked and reveals a value on demand under a session credential (the flow verified live in pass 18).
3. Record the Render relationship: Render's API keys are unscoped, so it has no equivalent vocabulary and there is **no parity gap to close** — bex's scope classes are a documented extension. Note it in `docs/ADR018-render-parity.md` next to the existing auth rows.

## Acceptance criteria

## Out of scope

- Changing the scope vocabulary itself, or the dashboard's credential class.
