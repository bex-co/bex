# 570 — The API's persistence-mode writes don't say that switching to or from Off deletes every key, though the dashboard asks for a phrase and Render documents the loss

Why: an API or agent caller that changes `persistenceMode` gets no warning that the restart empties the store. The dashboard requires `sudo clear key value <name>` for the same change, and Render's docs say "if you change your mode to _or_ from Off, your instance's data is lost after the restart" (render.com/docs/key-value, read 2026-11-11).

- **Source / severity / estimate:** w4/m316 t003 writer audit, `/loopx w4` run 2026-11-11. **Minor** (documentation of a destructive write; the behavior itself matches Render). ~20m.
- **Where:**
  - GraphQL `setKeyValuePersistenceMode` has no description (`lego/backend/internal/keyvalue/graphql.go`, beside `setKeyValueMaxmemoryPolicy`).
  - MCP `update_key_value`'s description says only "A persistenceMode change re-derives the AOF/RDB flags and rolls the pod on the next sync" (`keyvalue/mcp.go`). Its `persistenceMode` argument says Off is "lost on restart", but not that switching mode is itself the restart that loses it.
- **Fix:** give both the disclosure that w4/m263 and w4/m316 gave plan and maxmemory changes: the change restarts the store (unavailable for a few seconds), and a switch to or from Off deletes every key. Keep REST's acceptance unchanged (the pinned CLI's `keyvalues update --persistence-mode` must keep working). Extend `TestRestartingWritesDiscloseThePersistenceOffDataLoss` (`keyvalue/restart_disclosure_test.go`) to cover the new text.
- **DoD:** the GraphQL schema description and the MCP tool and argument text state the restart and the Off data loss, and the test pins them.
- **Dedupe:** w4/m263 covers plan and w4/m316 covers maxmemory. No item covers the persistence-mode API text.
