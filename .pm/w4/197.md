# w4/197 — A cron schedule that can never fire (e.g. `0 0 31 2 *`) is accepted and shown as "Next run: now", backed by `nextRunAt: "0001-01-01T00:00:00Z"`

Why: the cron header promises when the job will next run. For a schedule with no future occurrence it says "now", forever, so a user who typed the wrong day/month believes the job is about to run when it never will. REST and GraphQL leak Go's zero time as a real timestamp.

Live 2026-10-05 UTC (`/qa-find-bugs` loop21, muse.env, `bex-canary`). Owned Free cron `qa-20261004-l21-cron` (`srv-db1gna5fivpc73fcq20g`, `busybox:1.37`, deleted to 404):

- Create wizard, Schedule `0 0 31 2 *` (February 31): accepted with only the generic hint, while `60 * * * *`, `*/0 * * * *` and 6-field specs show "Enter a valid 5-field cron expression".
- `GET /v1/services/<id>` → `serviceDetails.nextRunAt: "0001-01-01T00:00:00Z"`. GraphQL `server(id){ nextRunAt }` returns the same.
- Dashboard header on every service tab: "Schedule: 0 0 31 2 * **Next run: now**", from `<time datetime="0001-01-01T00:00:00Z">now</time>` (`.playwright-mcp/qa-cron-nextrun-zero-1.png`).
- Control: the existing every-minute cron `srv-dap3v694dm7c7390q930` reported `nextRunAt: 2026-10-05T02:31:00Z` at 02:30:31Z (correct).
- The same fixture's run journey is correct, recorded so it isn't re-litigated: Events → Runs → Trigger Run gave API `pending`/UI "Running"; Cancel → Proceed gave `canceled` within 8 s with a 38 s duration on both API and UI; Logs show `QA_L21_START` and no `QA_L21_END`.

Root cause: `lego/backend/internal/apps/service.go:1282-1291` `nextCronRunAt` returns `sched.Next(now).UTC().Format(time.RFC3339)` with no zero check. robfig/cron v3's `Next` returns the zero `time.Time` when no matching time exists within its search horizon (an impossible date like Feb 30/31, or Apr 31). Create/update validation (`service.go:4115-4125`) only checks that `cron.ParseStandard` parses. The dashboard header (`dashboard/src/features/services/components/service-detail-header.tsx:229-233`) renders any non-empty `nextRunAt` through the relative-time formatter, which shows a past instant as "now".

Fix:

1. In `nextCronRunAt`, return `""` when `Next` is zero, matching the existing "no next run" contract the dashboard already hides. This covers legacy Apps carrying such a schedule.
2. Refuse such schedules at create/update/Blueprint validation with a named 400 ("schedule never fires"), via the shared schedule validator so REST/GraphQL/MCP/Blueprint agree, and mirror it in the wizard's schedule hint.
3. Tests: `0 0 31 2 *` and `0 0 30 2 *` are refused, `0 0 29 2 *` (leap day) is accepted, and the read surfaces omit `nextRunAt` for a legacy never-firing App.

Unverified: the Kubernetes CronJob controller's behavior with such a schedule (expected to log "no next schedule" and never fire). Render's handling of impossible dates (its docs only say "valid cron"). Severity: minor. Estimate: ~40m.
