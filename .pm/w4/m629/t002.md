## Objective

The MCP TypeScript SDK v1 registers a client without `scope`, and Hydra then allows it only its default scopes (`offline_access offline openid`), so the later authorize request for `bex.read`/`bex.write` may fail with `invalid_scope`, and a token without a granular scope is refused by `auth.go:649` (w8/m27). Make sure such a client can still be granted bex's capability scopes, with consent still deciding.

## Context

- Hydra's DCR default scope (`oidc.dynamic_client_registration.default_scope`, `driver/config/provider.go` in v26.2.0).
- `deploy/gitops/base/values/hydra.values.yaml` (DCR block near :64-69), `deploy/gitops/overlays/local/values/hydra.values.yaml`, `scripts/dev-env/values/hydra.values.yaml`.
- RFC 9728 metadata already lists `bex.read bex.write bex.sensitive bex.cloud_agents`.

## Steps

1. Reproduce with a DCR registration that omits `scope` (locally or on dev-4, never on production) and authorize with the scopes Claude Code requests.
2. If it fails, set `dynamic_client_registration.default_scope` to include the capability scopes in every Hydra values file, keeping the consent screen as the gate.
3. If it already works, record the evidence here and change nothing.

## Files

- The three Hydra values files above
- `scripts/gitops-validate.sh` if a guard is added

## Acceptance criteria

- [ ] A client registered without `scope` can be granted `bex.read` (and `bex.write` when asked) after consent, shown locally.
- [ ] Consent still decides; nothing is auto-granted.
