# 672 — A web image release started within seconds of the previous one going live deletes the serving instance: the Deployment controller cleans up the just-promoted pods (Ready, not yet available under the 150 s hold) while the Services pin their revision, so the URL answers Traefik's `no available server` for 60–80 s

**Dedupe correction (round 401):** this is the outage half of [w4/m320 t012](blocked/m320/t012.md) (open since round 156). That task records the same failure: a second deploy just after an image release takes all traffic gives 503 `no available server`, or puts an older release back, and its endpoint loss was left "Not traced". This note carries that trace and the reproductions. t012 has the summary and owns the fix; fix it there, and close this note with it. Round 401 adds `deploys {}` (70 s of 503) and Restart (D0's older image served for about 20 s) in the window; see t012's addendum.

Why: Render's deploys, rollbacks included, keep the serving instance in rotation until the new one is healthy. On bex, a Free image web service lost every backend for 63 s (round 397) and 78 s (round 398) when a rollback started within seconds of the previous image deploy going live. ## Round 398: reproduced on demand, and the mechanism (2026-11-15 07:00–07:11 UTC, pin `89ac87445bec`)

- **A, reproduced** (`qa-20261115-r398-a`, `srv-dbslgutdergc73ccgihg`). Fixture as below; URL polled about once a second with `curl -m 3`.
  - D0 `busybox:1.36` went `live` at 07:00:51.
  - D1 (`POST …/deploys {"imageUrl":"docker.io/library/busybox:1.37"}`) went `live` at 07:02:11.5 (`deploy_ended` 07:02:10).
  - At 07:02:11.9, a rollback to D0 (`dep-dbslhsuoou4c73fdrh80`) read `created`, then `update_in_progress` from about 07:02:22.
  - The URL answered `200 BusyBox v1.37.0` until 07:02:51, then **`503 no available server` on all 73 polls from 07:02:52.5 to 07:04:09.2 (78 s)**, then `200 BusyBox v1.36.1` from 07:04:10.3.
  - The rollback read `live` at 07:04:11.9 (`deploy_ended` 07:04:10, image `busybox@sha256:73aaf090…`). Events recorded no `server_failed` in the window.
- **B, control: the same flow with the rollback 90 s after D1's `live`** (`qa-20261115-r398-b`, `srv-dbslja6oou4c73fdrhcg`).
  - D1 went `live` at 07:08:05.5. The rollback (`dep-dbsllbuoou4c73fdrhj0`) was requested at 07:09:36, read `update_in_progress` at 07:09:46.7 and `live` at 07:11:09.
  - **All 251 polls were `200`**; the page switched from `1.37` to `1.36` at 07:11:08.5.
- **The pattern across all seven runs:** every outage had the next release start within seconds of the previous image release going `live`. That covers this A (0.4 s), round 397 run 1 (3 s) and round 396 run 1, where the queued rollback started as soon as A went `live`. The runs that stayed at `200` started it later (B: 90 s) or had no release in flight behind an image change.
- **Mechanism.** Code read. Kubernetes' own code was read at the production version (v1.34.9, `infra/clusterapi/overlays/hetzner-caph/cluster.yaml:1470`). The operator's write order was not observed.
  1. D1 changes the serving image, so it is a held release (`webImageReleaseHeld`, `lego/operator/internal/controller/web_image_http.go:72-76`).
     - The projection gives the Deployment `minReadySeconds = webImageHTTPSelectionHoldSeconds` (150 s; `web_image_http.go:39-41`, `deployment_projection.go:728-731`) and the held strategy (surge 100 %, `maxUnavailable` 0; `:692-696`).
     - The Deployment controller copies `minReadySeconds` onto D1's ReplicaSet, the new one. D0's ReplicaSet is held at 1.
  2. `promoteEarly` (`image_network.go:508-527`) promotes D1 as soon as its pod is Ready, and D1 reads `live`.
     - `ServingNetwork` becomes D1's network and `PriorServingNetwork` D0's.
     - D1's pod is Ready, but not *available* for 150 s, so the rollout is not complete.
  3. The rollback is a new template that changes the serving image, so it is held too. The Services pin `ActiveImageNetwork().Revision`, which is D1's (`image_network.go:347-348`), and `minReadySeconds` stays 150.
  4. Kubernetes `reconcileOldReplicaSets` (`pkg/controller/deployment/rolling.go:128-136`) now counts D1's ReplicaSet as old.
     - The counts: 2 pods (D0, D1), `minAvailable` 1, and a new ReplicaSet with 0 unavailable, so `maxScaledDown` is 1.
     - `cleanupUnhealthyReplicas` (`:155-189`) first scales down old ReplicaSets with fewer available pods than replicas, oldest first.
     - D0's ReplicaSet (1 replica, 1 available) is skipped. **D1's ReplicaSet (1 replica, 0 available, since its pod has been Ready for well under 150 s) goes to 0.**
     - `getNewReplicaSet` syncs `minReadySeconds` onto the new ReplicaSet only (`sync.go:164-166`), so D1's ReplicaSet keeps 150.
  5. D1's pod is deleted and leaves the endpoints.
     - The Services still select only D1's revision. D0's pod, Ready and running the very image the rollback restores, is not selected, and the rollback's own pod is not selected until it is promoted.
     - Traefik has no server until that promotion. That is 78 s here, because the rollback's image is discovered again, as a new image's always is.
  6. In B, the next pass after D1's promotion had projected `minReadySeconds` 0 and the default strategy (`deployment_projection.go:719`, `:731-733`). D1's ReplicaSet was available and D0's gone (`PriorServingNetwork` cleared, `app_controller.go:3509`), so nothing was left to clean up. This step is inferred from B staying at `200`. The window between `live` and that pass was not measured: it is at least 3 s (round 397) and closes within 20 s (round 399).

## Fix (target behavior)

No release removes the serving pods before its own promotion, and the Services never pin a revision whose pods the Deployment is scaling down.

- **Recommended:** release the hold in the pass that promotes.
  - When `promoteEarly` promotes a held web image release, write the Deployment's `minReadySeconds` 0 and the default strategy in the same pass, before the deploy can read `live`. The promoted ReplicaSet is then available before any later template exists.
  - Also, before writing a new template while the serving revision's ReplicaSet has Ready pods that are not available, patch that ReplicaSet's `minReadySeconds` to 0. The Deployment controller never syncs an old ReplicaSet's value, so the patch sticks.
- **Alternative:** hold the next release's template (requeue) until the previous rollout completes, i.e. `PriorServingNetwork` is nil and the Deployment reports the serving ReplicaSet available. This costs the next release up to that wait.
- **Tests:** envtest runs no Deployment controller, so it cannot reproduce this.
  - A projection unit test: the promoting pass leaves `minReadySeconds` 0 and the default strategy.
  - A kind replay on the mock cluster: D0, then D1 with an image change, then a rollback within 1 s of `live`. A 0.5 s poll must see no non-`200`. Repeat with a second `imageUrl` deploy in place of the rollback.
- **Siblings (unverified):**
  - The port-change hold (`portChangeHoldSeconds` 15 s, `deployment_projection.go:720-722`) should expose the same 15 s window after a port change is promoted early.
  - A non-held next release (a restart, a same-image deploy) inside the window should lose D1's pod the same way. With nothing pinned, though, it would serve D0's pod, the previous image, until the new release is Ready: an old version back, not a 503. An environment save on an image service is held, not this case (round 399 above).
- **Severity / estimate:** **major.** The outage is a full one, and deterministic when the next release starts inside the window: a rollback right after a bad deploy goes live, or a queued deploy (w4/652) starting the moment the deploy ahead goes live. ~2h with the kind replay.
- **Cleanup:** A and B deleted (`GET` 404).
