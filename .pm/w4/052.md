# A malformed resource ID returns HTTP 500 "internal error" instead of 404, because the caller's id is used raw as a Kubernetes label value

Why: client-supplied malformed IDs (e.g. `srv-`, `not-an-id!!`, an id with a space) make the App/DB/KV resolution helper build an invalid k8s label selector, whose `List` error is mapped to 500 — a dishonest error taxonomy (a bad/unknown id is not a server failure), it pollutes 5xx monitoring/alerting, and it diverges from Render (which 404s). Shared helper ⇒ every by-id endpoint across REST/GraphQL/MCP for every resource type.

Source: live QA 2026-09-07, `$qa-find-bugs w4`.

## Symptom (reproduced on prod, deterministic)

`GET /v1/services/{id}` with a **malformed** id returns `500 {"id":"internal_error","message":"internal error"}`, while a well-formed-but-nonexistent id correctly returns `404 {"id":"not_found"}`.

## Durable probes (in-page authenticated `fetch(..., {credentials:'include'})`, so past Cloudflare)

| id (`GET /v1/services/<id>`) | status | body.id |
| --- | --- | --- |
| `srv-zzzzzzzzzzzzzzzzzzzz` (well-formed, nonexistent — control) | 404 | `not_found` |
| `foo` (no prefix) | 404 | `not_found` |
| `srv-UPPERCASE123` (wrong charset, valid label value) | 404 | `not_found` |
| `srv-` (prefix only / empty xid) | **500** | `internal_error` |
| `not-an-id!!` (special chars) | **500** | `internal_error` |
| `srv-%20x` (space) | **500** | `internal_error` |
| `not-an-id!!` repeated | **500** | `internal_error` (deterministic) |

`GET /v1/postgres/dpg-zzzzzzzzzzzzzzzzzzzz` (well-formed nonexistent) → 404 `not_found` (control for the sibling resource).

The 500 body is bex's own error envelope (`{"error":"internal error","id":"internal_error"}`), not a Cloudflare page.

## Root cause (code-verified on `main` — not deploy-lag)

`core.Base.AuthorizeApp` (`lego/backend/internal/core/base.go:1034`) resolves the public id by using the caller-supplied `name` **directly as a Kubernetes label value**:

```
if err := b.Client.List(ctx, &byID, client.MatchingLabels{LabelAppID: name}); err != nil {
    return nil, err   // base.go:1047-1049  → mapped to 500
}
```

k8s label values must match `(([A-Za-z0-9][-A-Za-z0-9_.]*)?[A-Za-z0-9])?` (≤63 chars). Malformed ids that are **not valid label values** — trailing `-`/empty segment (`srv-`), special chars (`!`), whitespace (space) — fail selector construction, so `List` errors and the handler returns it as 500. Ids that happen to be valid label values (`foo`, `srv-UPPERCASE123`) pass the selector, match nothing, and fall through to the name-based `Get` candidates → NotFound → 404. There is **no upstream id-format validation** in the Get path (`getService` → `restVerb` → `s.Get` → `AuthorizeApp`; grep for `WellFormed`/`id.Valid` in the apps/core Get path returns nothing).

## Target behavior

An **unresolvable** resource id — malformed OR well-formed-but-nonexistent — must return **404 not-found** (matching bex's existing majority behavior and Render), never **500**. A genuinely malformed id may alternatively be **400 bad request**, but 404 is the simpler, consistent choice and avoids an existence oracle. Crucially, a **real** List failure (apiserver/etcd down) must **still be 500** — do not blanket-map all `List` errors to 404.

**Fix (shape):** in the shared resolution helpers, guard the label-value lookups so a `name` that is not a valid k8s label value **skips** the `LabelAppID`/`LabelServiceName` `List` (a malformed id can never be a stored label value anyway) and falls through to the name-based `Get` candidates, which already yield a clean 404 — OR distinguish an invalid-selector/invalid-label-value error (→ 404/400) from a transport List error (→ 500). Pre-validating with `id.WellFormed(name)` and short-circuiting to NotFound is the cleanest single guard.

## Blast radius (shared core.Base helpers)

Same raw-`name`-as-label-value pattern at `base.go`:
- `AuthorizeApp` — `:1048` (`LabelAppID`), `:1081` (`LabelServiceName` fallback)
- `GetApp` — `:1476` (`LabelAppID`), `:1509` (`LabelServiceName` fallback)
- sibling authz helpers `AuthorizeDatabase` (`:1171`) and `AuthorizeKeyValue` (`:1178`) resolve `dpg-`/`red-` ids the same way.

So the defect reaches **every by-id verb** (get/patch/delete/scale/suspend/rollback/connection-info/…) for **every resource family** (web · static · cron · worker · private · Postgres · Key Value), across **REST + GraphQL + MCP** (all call these helpers). Fix once in the shared helpers; regression-test that valid ids still resolve, well-formed-nonexistent still 404s, and malformed now 404s (not 500) — for App, Database, and KeyValue.

## Adjacent classes

- well-formed nonexistent → **404** (unchanged).
- malformed / invalid-label-value → **404** (the fix; currently 500).
- exists but forbidden → **403** (unchanged — must not collapse to 404 and become an existence oracle).
- real apiserver/etcd List failure → **500** (must stay 500; don't hide infra outages).

## Render parity

Render returns 404 for a malformed/unknown service id, not 500. bex diverges. Parity task applies (REST + GraphQL + MCP share the helper).

## Severity

**Minor** — no data loss, no blocked journey (valid ids work), and it is not an existence oracle (it 500s uniformly for the malformed class). But it is a dishonest error taxonomy on client input, pollutes server-error monitoring with client-caused 5xx, and is a broad shared-helper + Render-parity defect.

## Unverified this run

- Only **REST `GET /v1/services/{id}`** malformed ids were probed live (+ one well-formed postgres control). Malformed **Postgres/Key Value** ids and the **GraphQL/MCP** by-id surfaces were not probed, but share the same helpers — confirm they 500 identically (expected) and are fixed by the same change.
- The exact controller-runtime mechanism (whether `client.MatchingLabels`→selector build errors client-side, or the apiserver rejects the invalid selector) was inferred from the k8s label-value rules + the observed 500, not stepped through; the fix (guard/validate before the label List) is correct either way.
