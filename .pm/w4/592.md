# 592 — Resuming a suspended cron job immediately runs it once, off schedule, for the slot that passed while it was suspended

Why: owners suspend a cron job to stop what it does, often because its last runs misbehaved. The Resume card promises only "Resuming this cron job resumes scheduled runs". Instead the job runs its command within seconds of Resume, at a time no schedule names, with every side effect of a run.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 154, 2026-11-12 01:09–01:21 UTC (`muse.env`, workspace `bex-canary`; pin `8330744bd643`). **Major**: an unrequested execution of the tenant's job (see Unverified for Render). ~1h.
- **Fixture:** Starter cron job `qa-20261112-r154-cron` (`srv-dbqh3hiv3e1c73bps640`).
  - Image `docker.io/library/busybox:1.37.0`, schedule `*/2 * * * *`, command `sh -c 'echo qa154-fail; exit 7'`.
  - Deleted afterwards (`GET /v1/services/srv-dbqh3hiv3e1c73bps640` → 404).
- **Probe:** Settings → **Suspend** → confirm at 01:17:40; wait past the 01:18:00 slot; **Resume** at 01:18:38. Then `GET /v1/services/srv-dbqh3hiv3e1c73bps640/events?limit=6`, from the page:

  | timestamp (UTC) | type | details |
  | --- | --- | --- |
  | 01:17:40 | `suspender_added` | |
  | 01:18:02 | `service_suspended` | the 01:18:00 slot did not run (correct) |
  | 01:18:38 | `suspender_removed` | |
  | 01:18:45 | `cron_job_run_started` | `crr-9lrohql8td40aulk7dv6` |
  | 01:18:46 | `service_resumed` | |
  | 01:18:50 | `cron_job_run_ended` | `unsuccessful`, `nonZeroExit: 7` |

  The next slot the schedule names was 01:20:00.

- **Control: an overlap delay that is correct.**
  - A manual **Trigger Run** at 01:13:28 (`crr-b73vndaf7bgi6qpgkecr`, `sleep 90`) spanned the 01:14:00 slot, which did not start. After **Cancel** (run ended `canceled` at 01:14:35), a run started at 01:15:16 (`crr-av8fmrvocri8u7ab3fbt`).
  - This is the delayed 01:14 slot. It matches Render's documented single-run guarantee ("Render _delays_ the next scheduled run until the active run finishes", render.com/docs/cronjobs), and the operator's comment at `app_controller.go:5097-5099`.
  - **Not traced:** why it waited 41 s after the cancel. A Command save at 01:15:11 came just before it.
- **Root cause:** `reconcileCronJob` (`lego/operator/internal/controller/app_controller.go:5092-5111`).
  - `scheduleSuspended := suspended || manualRunActive || cancelPending` (`:5092`) becomes `cj.Spec.Suspend` (`:5103`). The CronJob sets no `StartingDeadlineSeconds`.
  - `k8s.io/api@v0.37.1/batch/v1/types.go:808-825` defines that field as the "deadline in seconds for starting the job if it misses scheduled time for any reason". With it unset, a slot that passed while `suspend` was true has no deadline, so the CronJob controller starts it as soon as `suspend` flips back to false.
  - **The same mechanism produces both cases above:** the correct delay after an overlapping manual run, and the wrong catch-up after a user suspension.
  - **Not read:** the kube-controller-manager CronJob controller code (`pkg/controller/cronjob`). It is not in the module cache. The mechanism is inferred from the field docs plus the probe.
- **Fix (target behavior):**
  - **After a user Resume,** the next run is the first slot the schedule names after the resume. A slot that fell inside the suspension never runs, so the probe above has no run at 01:18:45 and its next run is at 01:20:00.
  - **Unchanged:**
    - a scheduled slot that overlaps a manual run or a pending cancel still waits and starts when that run ends (Render's delay);
    - a manual Trigger Run while suspended is still skipped (ADR038).
  - **Candidate mechanisms** (pick one after a mock-cluster check of the controller's missed-slot rule):
    1. When `app.Spec.Suspended` goes true → false, write the CronJob's `status.lastScheduleTime` to the resume time before clearing `suspend`. This needs `cronjobs/status` RBAC.
    2. Recreate the CronJob on a user resume. Its new creation time bounds missed slots. ADR038's scheduled-Job identity checks key on the current CronJob UID, so history and deadline adoption must survive the new UID.
  - Do **not** set a short `StartingDeadlineSeconds` globally. It would also drop Render's delayed run after a long manual run (up to the 12 h bound).
- **Blast radius:**
  - Only the `cron_job` branch of `reconcileCronJob`.
  - The disk and Key Value backup CronJobs (`disk_backup.go:239-242`, `keyvalue_backup.go:272-274`) already set a starting deadline and are untouched.
  - Every entry point that suspends a cron funnels into `spec.suspended`, so one operator fix covers them all: REST suspend/resume, GraphQL, MCP, the dashboard's Settings card and row actions.
  - **Tests:** envtest runs no CronJob controller. Assert the operator's resume-time write (the chosen mechanism), and add the overlap-delay case as a regression test.
- **Unverified:**
  - Render's resume behavior: render.com/docs/cronjobs says nothing about suspend or resume. If a live Render check shows Render also runs the missed slot on resume, record that in ADR018's cron row and close this note as parity.
  - Whether a long suspension (more than 100 missed slots) changes the controller's behavior.
