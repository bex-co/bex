# Logs `instance` field + `logLabelValues(instance)` + the instance filter all expose/consume the raw tenant-prefixed k8s pod name instead of the masked public instance id — the LOGS sibling of w4/059

Why: same class as `w4/059` (metrics), different package. `serviceInstances` returns a masked `srv-<id>-<opaque>` instance id and the code documents "PodName remains internal" (apps/service.go:1348), but the logs feature returns the **raw** k8s pod name `tea-<tenantid>-<name>-<replicaset>-<pod>` as each log entry's `instance` field, enumerates raw pod names from `logLabelValues(label:"instance")`, and matches the instance **filter** against the raw pod name. So log entries, the instance-discovery endpoint, and instance filtering are all inconsistent with `serviceInstances`, leak the tenant id + CR name + replicaset topology into the API and the dashboard logs UI, and diverge from Render. `w4/059`'s metrics fix does **not** cover logs (different package/code path); filed separately and batched with 059.

Source: live QA 2026-09-08, `$qa-find-bugs w4` pass 39 (observability instance-identity sweep; logs sibling of `w4/059`).

## Symptom (reproduced live on prod — service `srv-d9bkcspg9s7c73d0n8ug`)

- GraphQL `logLabelValues(resource:srv-…, label:"instance")` → `["tea-d98210cbbpdc73dcrkvg-agentmarketcap-1-8645b77f5c-hg25t","tea-…-8645b77f5c-n5kkt","tea-…-d66989ffd-qrf8j"]` (raw pod names, incl. `tea-` tenant id + CR name + replicaset hash).
- GraphQL `logs(resource:srv-…, type:"app"){ instance }` → every entry `instance: "tea-d98210cbbpdc73dcrkvg-agentmarketcap-1-8645b77f5c-hg25t"`.
- **CONTROL (same instances, masked correctly):** `serviceInstances(id:srv-…)` → `srv-d9bkcspg9s7c73d0n8ug-465tcls9t0au7s9mnlhf`.

Durable probe: `{"query":"query($r:String!,$l:String!){ logLabelValues(resource:$r,label:$l) }","variables":{"r":"srv-d9bkcspg9s7c73d0n8ug","l":"instance"}}` → `{"data":{"logLabelValues":["tea-d98210cbbpdc73dcrkvg-agentmarketcap-1-<rs>-<pod>", …]}}`.

## Root cause (code-verified on `main` HEAD `9ad6da2c8` — not deploy-lag)

- The logs package maps the public `instance` label to Loki's raw `pod` label: `lego/backend/internal/logs/loki.go:444` (`{LabelInstance, "pod"}`), so a LogEntry carries `Labels["instance"] = <pod name>`, and `logLabelValues(instance)` returns the Loki `pod` label values (raw pod names) via `s.LabelValues` (loki.go:138/214 build/read the `pod` label).
- GraphQL surfaces it raw: `logs/graphql.go:37` (`"instance": e.Labels["instance"]`).
- The pod-log (fallback) path also sets it raw: `logs/service.go:1299` (`"instance": pod`).
- The instance **filter** matches the raw pod name: `logs/service.go:367-370` (`slices.Contains(q.Instance, pod)`), plumbed raw through GraphQL (`graphql.go:139`), REST (`rest.go:436`), MCP (`mcp.go:50,106`).
- Violates the same invariant `w4/059` cites: apps/service.go:1348 "PodName remains internal; ID is the Render-compatible public instance id"; `serviceInstances` honors it via `ids.DeriveServiceInstance(publicID(a), podInstanceIdentity(pod))` (apps/service.go:1334). Datastore log labels do the same (`service.go:688`/`:719` treat instance == pod for Postgres/KV).

## Target behavior / fix

LogEntry `instance`, `logLabelValues(instance)` values, and the dashboard logs instance chip must be the **same masked public instance id** `serviceInstances` returns (`srv-<id>-<opaque>`), never the raw pod name.

**Consumer check (load-bearing):** the instance filter currently matches the raw pod name (service.go:370); after masking, the filter must accept the masked id and translate it **back** to the Loki `pod` label for the query (loki.go:214) — otherwise filtering by the (now masked) instance id silently returns nothing. Same **name-derivable** requirement as `w4/059`: Loki only exposes the pod name (no UID), so the public id must be derivable from the pod name — use the **same** unified name-derived id as 059 so metrics and logs agree with `serviceInstances`.

## Blast radius (grepped, logs package)

- `loki.go:444` (instance→pod label map), `:138`/`:214` (build/read pod label)
- `service.go:1299` (pod-log path instance=pod), `:367-370` (instance filter matches pod), `:99` (DiscoverableLabels incl instance), `:688`/`:719` (Postgres/KV instance==pod)
- `graphql.go:37` (LogEntry.instance field), `:56`/`:139` (instance filter arg), `:102-114` (logLabelValues field)
- `render.go:36`/`:76` (REST LogEntry render); `mcp.go:50`/`:106` (MCP instance field+filter); `rest.go:436` (REST instance filter)

Surfaces: GraphQL `logs` + `logLabelValues`, REST `/v1/logs` + `/v1/logs/values` + `/v1/logs/subscribe`, MCP log tools, and the dashboard Logs UI (instance chip/filter). Fix must move the field, the discovery values, **and** the filter together, across app + Postgres + Key Value log resources.

## Adjacent classes

- own-workspace logs only (authz via `AuthorizeApp`/`AuthorizeDatabase`/`AuthorizeKeyValue`) — **not** cross-tenant; low-sensitivity internal-identifier exposure + contract/parity/consistency.
- valid instance → masked id (the fix).
- instance filter by masked id → translated to pod for Loki (the fix's consumer half).
- unknown/forbidden resource → unchanged (authz first).

## Render parity

Render labels log lines / instance filters by the public instance id, not the raw orchestrator pod name. bex logs diverge; `serviceInstances` already matches. Parity applies across GraphQL + REST + MCP + dashboard.

## Severity

**Minor** — no data loss, no blocked journey, own-tenant only; but documented-invariant violation ("PodName remains internal"), cross-surface inconsistency (`serviceInstances` masks; logs + metrics don't), Render-parity divergence, and internal-identifier exposure surfaced in the dashboard + API. Same severity/class as `w4/059`.

## Related / batch
