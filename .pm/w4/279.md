# Cancel leaves old custom-range errors beside restored valid dates

Why: reopening a canceled time-range edit tells the user their valid saved window is invalid, so ordinary Logs and Metrics investigations show contradictory guidance.

**Severity:** minor. **Estimate:** 35m (trace 5m, shared close handler 5m, meaningful tests 10m, caller/live controls 10m, simplify 5m). Source: user-directed continuous functional `$qa-find-bugs`, w4, 2026-10-12 a295. Filing only.

## Reproduction

On an owned service's Logs page, apply a valid custom window and open **Edit custom range**:

1. Change Start to equal End and Apply. The correct “The end must be after the start.” error appears.
2. Click the dialog's **Cancel** button.
3. Reopen **Edit custom range**. The saved valid Start/End are restored, but the old error remains.

Independently reproduced after a fresh 390×844 load and a fresh 1440px reload. Actual restored local dates were **2026-10-12 13:53–13:54 America/Los_Angeles**, with the unchanged accepted URL/API UTC bounds **20:53–20:54Z**. The one-minute interval is valid.

Fresh service Metrics reproduces the other validation branch: start 2026-09-01 exceeds the 30-day limit and correctly errors; Cancel/reopen restores **2026-10-12 13:52–13:53**, yet still says “Choose a window of 30 days or less.” The accepted CPU request used the valid one-minute UTC window and returned 200.

Controls: Close (X) on the stale Logs warning and Escape on the stale Metrics warning clear it before reopening. Successful Apply of the restored valid range also clears it. Logs filtering correctly includes the known startup marker in 20:52–20:53Z and excludes it in 20:53–20:54Z. Cancel and unchanged Apply preserve URL, search, app-log type and paused Live. Range validation and backend results are correct; only the dismissed warning survives.

## Root cause and fix

`dashboard/src/features/metrics/components/range-select.tsx:152–167` retains local error state in CustomRangeDialog. The parent keeps that component mounted (:124–133), while `openPicker` (:76–83) reseeds valid dates.

The dialog's onOpenChange wrapper (:174–177) clears errors before forwarding close. The footer Cancel button at **:221** calls the parent callback directly, bypassing that wrapper. The parent changes open but the error hook remains alive. Close/Escape use the wrapper and work, exactly matching the live controls.

The UI wrapper `common/components/ui/dialog.tsx:3–13` forwards controlled props to the pinned Radix Dialog **1.1.15**. Its installed `dist/index.js:86–90` binds open/onChange; `@radix-ui/react-use-controllable-state 1.2.2` at `dist/index.js:69–81` calls onChange from its setter. Updating the controlled prop through the feature's parent callback does not simulate a Radix close callback. [Radix's controlled-dialog reference](https://www.radix-ui.com/primitives/docs/components/dialog#root) supports the API contract; the actual installed code supplies the mechanism.

Use one **feature-local** open-change/close handler that clears the warning whenever the picker closes; route both Radix dismissal and footer Cancel through it. Keep the valid Apply path, draft reseeding, accepted range, minute precision, UTC conversion, translations and validation rules unchanged. Do not modify the global Dialog wrapper, URL parser, shared date precision or API limits.
