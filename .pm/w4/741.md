# A service's build traffic leaves from its published outbound IPs, as Render's does

Why: Render parity. Once `w21/m616` ships, a private package registry or database that allowlists a service's `outboundIps` admits the running service but refuses its build, because build Jobs keep leaving through whichever node they run on.

- **Render (read 2026-11-27):** [dedicated-ips](https://render.com/docs/dedicated-ips), "Do services use dedicated IP sets while building?": "Yes, with one exception. Services use dedicated IP sets for any outbound build traffic, such as package downloads. The exception is Docker image pulls, which use Render's shared outbound IP ranges." So Render's builds leave from the workspace's outbound set, and only image pulls leave from the region's shared ranges.
- **bex:** build Jobs run on tenant-pool nodes (`lego/operator/internal/execution/security.go`) and leave through the node's address. `w21/m616` moves serving pods, cron runs and pre-deploy Jobs onto the fixed Floating IP set and lists "Build Job egress" as out of scope (`.pm/w21/blocked/m616/t003.md`). [ADR125](../../docs/ADR125-stable-tenant-egress.md)'s follow-ups list "Build Job egress through the set, if Render documents its builds using its ranges", which this page now does.
- **Do:** first check on Render that a build step's own requests leave from the region's published ranges (a build command that fetches an IP echo service, compared with the Outbound tab). Then route build Jobs' egress, except image pulls, through the same gateway set as the service, and add build Jobs to `w21/m616`'s matrix check.
- **End state:** a build command that fetches an IP echo service reads one of the service's `outboundIps` on bex, as it reads one of the published ranges on Render.
- **Size:** about 1h after `w21/m616`; promote it if the gateway needs a second policy.
- **Depends on:** `w21/m616`.
- **Source:** w4/m688 t002, a full read of Render's dedicated-ips page, 2026-11-27.
