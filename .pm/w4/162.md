# A deploy to a nonexistent image tag stays "In Progress" for 15 minutes, although bex knew in one second the tag does not exist

Why: a registry `NotFound` is permanent; waiting cannot fix a typo'd tag. bex records `image_pull_failed` one second after the deploy starts and names the cause on the row within 18 s, yet the deploy only closes `update_failed` at the 900 s rollout budget. For 15 minutes the Deploys list says "In Progress", auto-deploy queues behind it, and a user watching waits for an outcome that was already known. `w8/m44` gave the pre-deploy path a 90 s pull grace, but the rollout path still waits out the whole budget.

## Mechanism

- `lego/operator/internal/controller/deployment_projection.go:131` `rolloutBudgetSeconds int32 = 900` is projected onto `Deployment.spec.progressDeadlineSeconds`. The rollout verdict (`ConditionRollout` False, read by `store/reconciler.go:836` `recordedRolloutFailure`) is only written when that deadline passes (`settleFailedRollout` on `ProgressDeadlineExceeded`, `app_controller.go:~2857`).
- `w8/m44` added `predeploy.PullFailure` (a 90 s grace on `ErrImagePull`/`ImagePullBackOff`, then fail) for the **pre-deploy Job** only. The **rollout** has no equivalent, so a permanent pull failure there is indistinguishable from a slow start until the 15-minute deadline.

## Fix

Target: a rollout whose new-revision pods are in `ErrImagePull`/`ImagePullBackOff` with a **permanent** registry answer (`NotFound` / manifest unknown / 404, or `unauthorized` with no credential change pending) closes `update_failed` after the same bounded grace the pre-deploy path uses (about 90 s). The failure reason names the image, and the prior release keeps serving. Transient pull errors (timeouts, 5xx, rate limits) keep the full budget.

- Have `settleFailedRollout` (or a sibling) settle early on the same pull evidence `predeploy.PullFailure` already classifies, and reuse that classifier so the two paths cannot drift.
- Tests: a nonexistent tag over a prior release settles within the grace; a transient pull error does not settle early; a slow-starting but pullable image still gets the full 900 s.

Render: Render fails a deploy with an unpullable image shortly after the pull error rather than after a long health window. Not measured here, so treat the exact timing as unverified.

Estimate: ~45m.
