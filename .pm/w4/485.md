# 485 — A native build that fails its build command quotes BuildKit's step-progress trace ahead of the real cause, then repeats the error three times

Why: the one block a customer reads when a build fails opens with about twenty lines of `#20 merging` / `#21 DONE 0.1s` bookkeeping, so on the deploy row, the detail page, Events and the failure email the actual cause ("build command … exited with code 3") only shows up at the very end, after being said three times.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, 2026-11-04 ~21:20 UTC (`muse.env`, workspace `bex`, build pin as deployed at that time); **minor** (diagnosability and copy); ~30m. Same family as w4/467 (git fetch chatter ahead of a source-check failure), a different producer.
- **Probe (fixture `qa-20261104-broken`, `srv-dblq26gg64rs73avmclg`, deleted afterwards, `GET` 404 and absent from `GET /v1/services?name=qa-20261104-broken`):**
  1. `POST /v1/services` with `{"type":"web_service","name":"qa-20261104-broken","ownerId":"tea-d98210cbbpdc73dcrkvg","repo":"https://github.com/bex-co/bex","branch":"main","rootDir":"examples/hello-node","serviceDetails":{"runtime":"node","plan":"free","region":"frankfurt","envSpecificDetails":{"buildCommand":"echo compiling && exit 3","startCommand":"node index.js"}}}` returns 201.
  2. About 2 min later `GET /v1/services/srv-dblq26gg64rs73avmclg/deploys?limit=1` returns status `build_failed`, `finishedAt` `2026-11-04T21:21:16Z`, and this complete `failureReason`:

The same string is on the dashboard Deploys list row and the deploy detail page (both start with `build failed in the docker build step: #20 merging 0.2s done …`), in the `deploy_ended` event's `details.failureReason` (1237 bytes of details JSON), and in GraphQL `deploys(serviceId:){failureReason}`. All four surfaces agree, so this is the producer, not a UI rendering problem.

- **Root cause:**
  - `lego/operator/internal/build/build.go:745` sets `tail = failureTail(nativeCommandFailure(t.Message))`, where `t.Message` is the failing container's termination message (the kubelet keeps up to 4 KiB / 80 lines of BuildKit's `--progress=plain` output).
  - `failureTail` (`build.go:804-818`) only keeps the last `failureTailBytes = 800` bytes (`:802`) and trims to a line boundary. Its comment ("errors conclude output, they don't open it") assumes the error block is most of those bytes. For BuildKit it is about 330 of them, so the remainder is the preceding steps' `#N DONE` lines.
  - BuildKit says the failure three times in that tail: the `#25 ERROR:` progress line, the `------ > [stage-0 11/12] RUN …:` summary block, and the final `error:` line. `nativeCommandFailure` (`build.go:776-795`) rewrites each into the tenant's terms but removes none.
  - The message is composed in `lego/operator/internal/controller/build_failure.go:94-103` as `"%s%s:\n%s"`, so nothing downstream trims it.
- **Fix (target behavior):**
  - The quoted tail of a BuildKit failure starts at the failing step. Drop leading BuildKit progress bookkeeping (lines matching `^#\d+ (DONE|CACHED|merging|\[.*\] (FROM|COPY|WORKDIR|ADD))` and blank separators) until the first `ERROR` line or the first line of the `------` block, then cap at the same 800 bytes.
  - It names the cause once. Keep the final `error: …` line and the `------` block with the command's own output (`0.087 compiling`); drop the duplicate `#25 ERROR:` line and the `> [stage-0 …]` header.
  - Expected shape for this probe: `build failed in the docker build step:` + the command's output (`compiling`) + `error: build command 'echo compiling && exit 3' exited with code 3`.
  - A failure that is not BuildKit output (git fetch, the registry push, buildpack) keeps today's byte-tail unchanged.
  - Surfaces move together because they read one string: deploy row, detail page, Events, GraphQL, failure email. No UI or API change is needed.
- **Blast radius:**
  - `failureTail` is called from `build.go:745` (Job pods) and `build/kpack.go:176` (buildpack builds); `nativeCommandFailure` only from `:745`. Run `grep -rn "failureTail(" lego/operator` for the exact count before editing.
  - The Dockerfile-runtime path shares `:745`, so a failing Dockerfile `RUN` gets the same treatment; `build_failure_test.go` and the tests around `nativeCommandFailure` pin today's wording and need updating.
  - Regression: a clone-step failure (w4/467), a registry-push failure and a timeout/infra fault must produce byte-identical messages to today.
- **Adjacent classes:**
  - The infra fault class never quotes output (`build_failure.go:79-86`) and the timeout class never has a tail, so neither changes.
  - A BuildKit failure whose tail has no `ERROR` marker (an OOM kill with no summary) keeps the byte-tail rather than returning an empty reason.
- **Unverified:**
  - A Dockerfile-runtime build that fails a `RUN` was not probed this run; it shares `build.go:745` by reading, but its transcript shape is not captured here.
  - The buildpack path (`kpack.go:176`) and a static-site Hugo build were not probed.
  - The failure email body was not read; it is assumed to reuse `failureReason`.
- **Render:** Render's build failure reason is a short status ("Build failed"), with the build log carrying the command output.
- **Dedupe:** `grep -rli "#20 merging\|step-progress\|BuildKit.*failure reason" .pm` finds nothing. w4/467 (done) trimmed git fetch chatter only. w6/m123 t003 (done) made BuildKit output reach the log and the tail. w8/052 is the `build command '<cmd>'` rewrite this note builds on. No `.pm/DO_NOT_DO.md` item applies.
