# 368 — A deploy-auto-registered Blueprint reads "In Sync" with no sync ever recorded

Why: the Blueprint detail page contradicts itself — the header badge says **In Sync** (Auto-sync On) while the same page says `Last synced —`, "No syncs yet", and "No resources yet — sync the Blueprint to apply your render.yaml". A reader cannot tell whether the manifest was ever applied.

**Severity:** minor. **Estimate:** ~45m.

**Source:** live `/qa-find-bugs w4` loop run 2, 2026-10-19 UTC, `muse.env`, workspace `bex-canary`, on the pre-existing production Blueprint `blp-db136288mmqc73d4hpug` (`bex`, repo `https://github.com/bex-co/bex`, created 15d ago by an earlier QA loop's deploy; its manifest names one service, since deleted). Read-only — nothing was synced or mutated; the run's own fixtures were deleted and its session revoked.

## Probes (production, from the signed-in page)

- Dashboard `/blueprints/blp-db136288mmqc73d4hpug`: badge `In Sync`, `Auto-sync On`, `Last synced —`, Managed Resources "No resources yet — sync the Blueprint to apply your render.yaml.", Sync History "No syncs yet."
- REST `GET /v1/blueprints/blp-db136288mmqc73d4hpug` → `200`, `status: "in_sync"`, `autoSync: true`, no `lastSync` field, no `resources` field.
- REST `GET /v1/blueprints/blp-db136288mmqc73d4hpug/syncs?limit=5` → `200`, `[]`.
- Validate on the same page reports "Manifest is valid — no errors found", so the row is healthy apart from its history claim.

## Root cause

Git-connected creates sync immediately (w2/m62, dispositioned in w8/009 — stored `created` is deliberately unreachable there). This row never took that path: a manifest deploy auto-registers the Blueprint afterwards in `lego/backend/internal/apps/blueprint.go:1757-1781` (`upsertBlueprint`, called from `deploy.go` after a successful `deployStack`), stamping `Status: store.BlueprintStatusInSync` and `AutoSync: true` on insert — but it records no sync row and leaves `LastSyncAt` nil, so `toBlueprintView` (`blueprint.go:2051-2073`) emits `in_sync` with no `lastSync`, forever. The upsert's conflict arm writes the manifest only (`lego/backend/internal/store/blueprints.go:98-105`), so later deploys never repair the history either. Pre-m62 legacy rows get the same reading via the `active → in_sync` mapping at `blueprint.go:2053-2055`.

The apply that auto-registered the row really did converge the manifest at that moment, so `in_sync` was true at insert; the defect is that the one sync that justifies the status exists in no history surface, and nothing ever records it later (auto-sync only fires on pushes to that repo+branch).

## Fix (target behavior)

- A deploy whose apply auto-registers (or refreshes) a Blueprint records a sync row for that apply — state `success`, the resolved commit when known — and sets `LastSyncAt`, through the same store seam the git-connected sync lifecycle uses (`lego/backend/internal/store/blueprint_lifecycle.go`), so `GET …/syncs`, `lastSync` and the badge agree on every surface (REST/GraphQL/MCP/dashboard).
- A row that has genuinely never applied (no sync rows, `LastSyncAt` nil) must not read `in_sync`: project it as `created` (`store.BlueprintStatusCreated`, which exists and is never written today) at the `toBlueprintView` mapping, covering pre-m62 `active` rows that also have no syncs. Rows with any recorded sync keep their lifecycle status untouched.
- Control cases: a fresh git-connected create still goes `syncing → in_sync` with its first sync row unchanged; a paused blueprint stays `paused`; the w8/009 "created unreachable" note in ADR018 gets updated to name this one reachable path.

## Acceptance

- Replaying the probes above on an auto-registered Blueprint (fresh MCP/REST manifest deploy into a scratch workspace): `GET …/syncs` returns the apply's success row, `lastSync` is set, status `in_sync`.
- A seeded never-applied row (legacy `active`, no syncs) reads `created` on REST/GraphQL/MCP and the dashboard badge matches.
- Existing blueprint lifecycle tests pass (`go test ./...` for `internal/apps` + `internal/store`, real-DB gate).
