# 535 — Regression of w6/035: a first deploy's `build_started` is stamped at the row's creation while it is still `created` or about to queue (live: 2m03s and 14s early)

Why: the Events timeline, the `build_started` webhook payload and the metrics build marker say a build began minutes before it did. w6/035 promised that `build_started` rides the real dispatch and is withheld until then, and w7/m66's DoD item 1 says the same ("a `build_started` event when its BuildKit build Job begins").

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 2, 2026-11-10 07:51–08:03 UTC (`muse.env`, workspace `bex-canary`, pin `1672bb379c0c`). The pin advanced to `4630a48a765e` at 08:02. `reconciler.go` and `deploy_lifecycle.go` are unchanged between `1672bb379c0c` and HEAD, so this is not deploy lag. **Minor** (timestamp accuracy on three consumers), but a regression of a shipped guarantee. ~45m.
- **Fixture:** Free web service `qa-20261110-hook` (`srv-dbpcpq9pjd2c73f0qr8g`; Public Git URL `https://github.com/bex-co/bex`, root `examples/hello-go`, Docker, auto-deploy off). It was created in the dashboard and deleted at the end (GET 404, gone from the services list). Round 1's cron job `qa-20261110-cron` (`srv-dbpceuf5g1is7398kqd0`) showed the same first-deploy pattern: `build_started` 07:27:53, equal to its `createdAt`, with `startedAt` 07:28:57.
- **Probe** (from the signed-in dashboard page): `GET /v1/services/srv-dbpcpq9pjd2c73f0qr8g/deploys/{id}` and `GET /v1/services/srv-dbpcpq9pjd2c73f0qr8g/events?limit=30`.

  | deploy | trigger | `createdAt` | `startedAt` | `build_started` event |
  | --- | --- | --- | --- | --- |
  | `dep-dbpcpq9pjd2c73f0qr90` | first deploy | 07:51:05 | 07:53:08 | **07:51:05**, 2m03s early |
  | `dep-dbpcrvppjd2c73f0qrl0` | deploy hook, later canceled | 07:55:43 | 07:55:57 | **07:55:43**, 14 s early |
  | `dep-dbpcsvn5g1is7398kt80` | deploy hook with `ref` | 07:57:50 | 07:58:27 | 07:58:27, correct |

  A 10 s poll of the first deploy read `created` at 07:51:52, `queued` from 07:52:02 to 07:53:04, and `build_in_progress` from 07:53:14. The correct third row was observed `queued` first (`created` 07:58:01, `queued` 07:58:11).

- **Root cause:**
  - `buildStartedAt` (`lego/backend/internal/store/reconciler.go:1271`) treats only `DeployQueued` as "not dispatched yet".
  - `recordLifecycleFacts` (`:1149`, call at `:1158`) calls `buildLifecycleFacts` on every pass, including passes where nothing moved (`newStatus ""`). So a row that is still `created`, with `StartedAt` nil, falls through to `return open.CreatedAt, true` (`:1306`) and emits `build_started` at creation.
  - The fact is idempotent by `source_key` (`deploy:<id>:build_started`), so the later real dispatch never corrects it.
  - A `created` → `build_in_progress` transition takes the same `CreatedAt` path, instead of now.
  - The comment's premise (`:1264`, "A never-queued deploy keeps riding CreatedAt: it is dispatched as the row opens") is false live: rows open `created`, sit there, and then queue before dispatch.
  - Two tests are built on that premise or miss the case. `TestBuildFactsForSuccessfulSkip` (`reconciler_test.go:2794`) pins `created` → `build_failed` to `created_at`. `TestBuildStartedRidesRealDispatchNotRowCreation` (`reconciler_test.go:156`) covers only `queued` rows.
- **Fix (target behavior):**
  - A row that has not dispatched (`created` or `queued`) emits no build facts.
  - Leaving either for a status that stamps dispatch (`DeployStatusStampsDispatch`: build, pre-deploy or update in progress) dates `build_started` at now. That is the same instant `TransitionDeploy` stamps `started_at`.
  - A `created` row observed straight at a terminal failure uses the operator's recorded build window (`evidencedStart`), as a `queued` one does.
  - Update the two tests above, and add cases for `created` + `""` and for `created` → `build_in_progress`.
- **Blast radius:** `buildLifecycleFacts` has 3 callers: `reconciler.go:934` (lower-generation settle), `:1158` (`recordLifecycleFacts`) and `:1248` (`CanceledBuildLifecycleFacts`, so a cancel while `created` today also emits `build_started` plus `build_ended(canceled)` for a build that never ran). The fact feeds the Events/Activity timeline, the `build_started` webhook payload and the metrics build marker (per w6/035's consumer check). The Deploys list Duration column uses the row's `startedAt` and is unaffected.
- **Adjacent:** a row canceled while `created` emits neither fact, as one canceled while `queued` already does (w6/m128). Image-backed deploys still emit none (w6/061).
- **Unverified:** the webhook payload and the metrics marker were not probed this run. Why some first passes see `created` before the operator's `BuildQueued` reason was not traced.
- **Dedupe:** w6/035 (done; fix `754f20d3a`) fixed only the `queued` case, and its live verification used a row that opened `queued`. w6/m128 (cancel mid-build), w4/m156 and w6/m123 (skip and failure paths) are adjacent. No open item touches `buildStartedAt`.
- **Render:** Render's Events show "Build started" when the build begins, not when the deploy is created.
- **DoD** (live, after the fix deploys): create a Free web service from `examples/hello-go` in `bex-canary`. For its first deploy, the `build_started` timestamp from `GET …/events` equals `startedAt` from `GET …/deploys/{id}` to the second, and never `createdAt`. Fire the deploy hook twice back to back and check both deploys the same way. Delete the fixture.
