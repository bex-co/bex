## Objective

Pin the guarantee with a test that fails against the pre-fix code, and cover the membership boundary the new argument opens.

## Context

- The pre-fix behavior to encode: with a member in two workspaces holding different `notification_settings` rows, the API returns and writes the same row regardless of which workspace is named — because no argument exists to name one.
- The strongest test is the one the DoD states: for each workspace the caller belongs to, the API read equals the stored `(tenant_id, subject)` row. It fails today for every workspace but the default.
- The fan-out side deserves its own test: `ListNotifyRecipients(B)` must reflect a preference the member set *for B*, which is the behavior users actually care about.
- A real-Postgres test is appropriate here — the defect lives in the relationship between a unique index and a query, which a fake store cannot express (the shape `w8/m37` used).

## Steps

1. Two-workspace fixture, different preference values in each.
2. Assert read/write per workspace matches the store.
3. Assert `ListNotifyRecipients` for each workspace reflects that workspace's values.
4. Membership boundary: naming a workspace the caller does not belong to is refused; another member's row is never returned.
5. Back-compat: the unscoped route still resolves the default workspace.
