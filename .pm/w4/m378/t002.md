## Objective

`list_logs` returns the same envelope and line shape as `GET /v1/logs`, which is what Render's server returns: it marshals the REST response.

## Context

- Today it returns `listLogsResult{Logs []LogEntry}` (`lego/backend/internal/logs/mcp.go:83-88`). Its labels are a map keyed `service`, and the lines have no `id`.
- The REST rendering (`renderLabels`, `logs/render.go:46-60`) maps `service` → `resource` and orders the labels.
- `mcpLogEntries` (`logs/mcp.go:203-215`) filters label keys but keeps the map.

## Steps

1. Render MCP lines through the REST path: the same `id`, the same ordered `[{name, value}]` labels, the same message rendering (w4/m325).
2. Keep `hasMore`, `nextStartTime` and `nextEndTime`, and every filter.
3. Apply the same rendering to the dedicated datastore log tools (`get_postgres_logs`, `get_key_value_logs`) if they share `LogEntry`. If they are bex-only and keep their shape, say so.

## Acceptance criteria

- [ ] For one fixture window, a test shows the MCP text and the REST body decode to equal values.
- [ ] No `service` label key appears in MCP output.
