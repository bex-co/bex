## Objective

A cron job's ~50 s run charts in Memory and Total Instances at every resolution the dashboard asks for, as CPU already does (DoD 1's "never reads No data in range for a window holding a run").

## Context

- **Found:** t004's live replay, 2026-11-16 09:19 UTC, pin `3c6654df60a2`. Fixture A `qa-20261116-m322-cr` (`srv-dbtcihvhaims738pkef0`) ran three manual runs, 09:14:10–09:14:59, 09:15:30–09:16:20 and 09:16:32–09:17:22.
- **Dashboard.** The first load of A's Metrics page (Last 12 hours, the GraphQL `Metrics` reads at `resolution: 300`) listed the three instances and charted CPU. Memory and Total Instances read "No data in range". A reload 45 s later charted all three, because its start time, and with it every evaluation point, had moved.
- **REST.** At 09:20:09, `GET /v1/metrics/memory` and `instance-count` with `startTime=2026-11-15T21:19:00Z&resolutionSeconds=300` returned `[]`. At `resolutionSeconds=60` both chart every run.
- **Cause.** Memory is `last_over_time(…[90s])` and instance-count `count_over_time(…[90s])` (`lego/backend/internal/metrics/source.go`, w4/644 and w4/m110). Neither widens with the step, so at a 300 s step each evaluation point reads only its trailing 90 s, and a run that ends more than 90 s before the next point is never read. CPU's rate lookback is the step (`rateLookbackSeconds`), so it charted.

## Fix

- Memory reads `last_over_time` over `max(step, 90s)` (`bucketWindow`): the last reading inside its step. At a step of 90 s or less the query is unchanged.
- Instance-count above a 90 s step is `max_over_time((<the 90 s-gated count>)[<step>s:15s])`: the most instances live at once inside the step. Sequential runs in one step are not added together, and w4/m110's liveness gate stays 90 s.
- Checked on production Prometheus (read-only port-forward, the A fixture, 07:19–09:29 at step 300): the old memory and instance-count queries return 0 series. The new memory query returns the three run pods at 09:19, and the new instance-count returns `2` at 09:19. That `2` comes from the same 90 s gate that reads `2` at 09:16 at step 60, because runs 30 s apart overlap inside the gate.
- `TestCoarseStepReadsTheWholeStep` (`range_test.go`) pins both queries at 30 s, 90 s, 300 s and 1 h steps. Reverting `source.go` fails it. [ADR010](../../../../docs/ADR010-observability.md) records the window.
