# 623 — Canceling a deploy from the Deploys list (or the Events tab) shows no "Deploy canceled." toast, although the cancel succeeds; the same cancel from the deploy's own page toasts

Why: the toast is the only confirmation the click did something. From the list, the Cancel button disappears and a row turns Canceled, with no message. The user can't tell their cancel from a deploy that failed or was superseded on its own.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 248, 2026-11-13 01:23–01:27 UTC (`muse.env`, workspace `bex-canary`; pin `c328714af1dd`). **Minor** (missing feedback; the action works). ~30m.
- **Fixture:** `qa-20261113-r248-rb` (`srv-dbr67g95t55c738j9oeg`, the [w4/621](done/621.md) fixture). Each run was a Deploy Hook call (`POST https://api.bex.co/v1/deploy-hooks?key=…` → `200 {"deploy":{"id":"dep-…"}}`, trigger `deploy_hook`), canceled during `build_in_progress`. Toasts were captured with a MutationObserver plus a 30 ms poll on `[data-sonner-toast]`.

  - The dialog ("Cancel this deploy? … Any changes you saved stay saved and ship with the next deploy.") closed normally each time.
- **Root cause:**
  - The list renders `<DeployActions>` only while the row has an action: `hasListAction = isCancelableDeployStatus(d.status) || (d.status === "deactivated" && …)` (`dashboard/src/features/deploys/components/deploys-list-page.tsx:222-224`, used at `:340-342`). The Events tab does the same with `hasAction` (`dashboard/src/routes/services.$serviceId.events.tsx:337-340`).
  - The cancel mutation's result writes `status: canceled` into the cache. The row loses its action and `<DeployActions>` unmounts before `await cancelDeploy(…)` resumes.
  - The unmount cleanup of `useBoundActionConfirm` sets `mounted.current = false` and calls `clearConfirm()` (`dashboard/src/features/capabilities/hooks/use-bound-action-confirm.ts:161-167`). `isIntentCurrent(binding)` (`:116-128`) then fails, and `handleConfirm` returns before `toast.success(t("services.cancelDeploySuccess"))`, also skipping `onChanged?.()` (`dashboard/src/features/deploys/components/deploy-actions.tsx:204-214`, `:239`).
  - The deploy page always mounts `<DeployActions>` (`deploy-detail-page.tsx:126`), so its cancel toasts.
  - Rollback from the list toasts ("Rollback triggered.", seen this round): its target row stays `deactivated`, so it stays mounted.
- **Fix (target behavior):** a cancel that succeeded toasts "Deploy canceled." from every surface (list, Events, detail), unless the user has since left the service or switched workspace. The w4/m159 guard is meant against a toast on another page.
  - Either keep the row's `<DeployActions>` mounted while its confirm is pending or in flight,
  - or base the post-dispatch toast on a context check that does not need the component mounted: same workspace, resource and access generation, from `latest`.
  - Do not drop the guard: a cancel resolved after a workspace switch must still not toast.
- **Blast radius:** `useBoundActionConfirm` has more callers than deploys (restart, suspend, resume, cron run/cancel; `SERVER_ACTIONS`, `use-bound-action-confirm.ts:51-57`). Any of them whose control unmounts when its own success lands loses its toast the same way. `grep -rn "useBoundActionConfirm(" dashboard/src` and check each for a status-gated mount. Callers that toast today need regression tests.
- **Tests:** a `deploys-list-page` test where the cancel mutation resolves with `status: canceled` asserts the toast; the detail-page case stays green; a cancel resolved after a workspace change does not toast.
- **Unverified:** the Events tab path was read from code, not clicked. Other `useBoundActionConfirm` callers were not audited.
