# 608 — A crash before the sampler has ever seen a new service healthy (its first ~30 s live) records `server_failed` and never `server_available`, so the event stays open

Why: w8/m158 t010 (done) closed a quick crash's event with `server_available`, but only for a service the event checkpoint had already seen healthy. A new service that crashes in its first pass interval keeps an open "Instance failed" on its Events tab, its webhooks and its alerts after it recovered. Apps that crash on their first real request are common.

- **Source / severity / estimate:** live `/qa-find-bugs w4` loop, round 197, 2026-11-12 13:23–13:50 UTC (`muse.env`, workspace `bex-canary`), replaying w8/m158 t010 on pin `f018ce9455c8`, which carries t010's `96fbaec6a`. **Minor** (an event left open; the service recovered). ~30m.


## Target behavior

An exit-caused `server_failed` is closed by one `server_available` when the service is Ready again, also when the event checkpoint has never recorded the service healthy. That is the case for every service in the first pass interval after its first deploy goes live, and for one with no checkpoint row yet.

- **Mechanism:**
  - **The pairing skips an unseen checkpoint.** `pairInstanceExit` (`lego/backend/internal/store/event_facts.go:293-321`) returns without doing anything when the checkpoint row is missing or its `availability` is not `"healthy"` (`:300`). Its comment counts that as "a checkpoint already down has its outage". A service whose first deploy has not been sampled healthy has `availability` `""`: never seen, not down.
  - **Unseen to healthy is not an edge.** The next pass sees it healthy, but `observedStateFacts` emits `server_available` only for `unhealthy` → `healthy` (`:865`). `""` → `healthy` is the ordinary first sighting.
  - **Result:** the exit's `server_failed` is never paired.
  - A checkpoint with no row at all is reached the same way (`ErrNoRows`, `:300`).

## Fix (steps)

1. In `pairInstanceExit`, return early only for a checkpoint that is `"unhealthy"`, which pairs through its own recovery.
   - Treat `""` and a missing row like `"healthy"`: pair at a healthy transition after the exit, or else record the checkpoint `unhealthy` from the exit's `at`, inserting the row when it is missing.
   - The next healthy pass then records the one `server_available`.
2. Keep the cases w4/m230 and w4/562 rely on: a hibernated checkpoint, whose availability is also `""`, still pairs a waking instance's failure the existing way. Check whether that branch and this one can both fire.
3. **Store tests:**
   - an exit on a checkpoint with `availability ""` → one `server_available` after the next healthy pass;
   - an exit with no checkpoint row → the same;
   - t009's and t010's subtests stay green.
