# A prebuilt background worker, cron job or configured-port web service over 10 GB compressed is refused before the pull too

Why: Render parity. Render's 10 GB limit on an image's compressed size covers every image-backed service, but bex's refusal (w4/734) runs in the image metadata read, which only web and private services with image ports make.

- **Render:** [render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image) § Image size: "The Docker image's compressed size cannot exceed 10 GB." The page names no service type it exempts.
- **bex today (w4/734, 2026-11-27):** `resolveImageNetwork` (`lego/operator/internal/controller/image_network.go`) refuses a prebuilt image whose `registry.ImageConfig.CompressedBytes` is over `appv1alpha1.MaxImageCompressedBytes`, failing the deploy under `ImagePullFailed` with `image_too_large`. The read runs only when `app.Spec.HasImagePorts()` is true (`lego/operator/internal/controller/app_controller.go`, the block before `dispatchRuntime`): a web service stamped `web-image-v1*` or a private service stamped `image-v1*` at create (`configureNewImageCompatibility`, `lego/backend/internal/apps/service.go`). A prebuilt background worker, a cron job, and a web service created before w4/m243 in a configured-port mode skip it, so their node pulls an image of any size.
- **Do:** before dispatching a prebuilt image's release for those types, read its platform manifest through the same gated path (`readExternalImageConfig`, with the registry wait and the final verdict of `failBeforeDispatch`) and refuse it over the limit with the same reason. A manifest GET counts as a Docker Hub pull ("Using GET emulates a real pull", docs.docker.com/docker-hub/usage/pulls), as the web and private services' read already does. Read the manifest once per release, as `reusableImageNetwork` does, not on every reconcile. A cron job's release is its CronJob template, so the refusal has to land before that template names the new image.
- **Done when:** an envtest deploys a background worker and a cron job with an image of 10,000,000,001 compressed bytes and sees each fail with `image_too_large` while the previous release keeps its pod template, and one of exactly 10 GB deploys as before.
- **Size:** about 1h30m. Filed by w4/734.
