## Objective

Settle which service verbs a protected environment guards, state the rule that generates that set, and record it in ADR032 — so the answer for the next verb added to the API is derivable rather than absent.

## Context

### The live matrix (2026-09-21, production)

A `qa-` private service (`mendhak/http-https-echo:latest`, one env var) was placed in a freshly created environment with `protectedStatus: "protected"`, then every reachable mutation was run against it:

| verb                  | result on a protected member                                                            |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| `suspendService`       | **refused** — `retry with confirm="sudo suspend service qa-20260921-pe" to suspend it`     |
| `deleteService`        | **refused** — same shape; accepted once the phrase was supplied                            |
| `setImage`             | accepted — `imagePath` went `:latest` → `:35` with no confirmation (see the correction below) |
| `setEnvVar`            | accepted — config change, rolled a release                                                 |
| `setEnvVars`           | accepted — same                                                                            |
| `scaleService`         | accepted                                                                                   |
| `setIdleTimeout`       | accepted                                                                                   |
| `restartServer`        | accepted — **documented as deliberately ungated**, not part of this milestone              |

Deploy history after the run: `create:live` → `api:canceled` → `config_change:canceled` → `config_change:update_in_progress`, ending `rev-6`. Rollouts on a protected service, no confirmation asked for once.

**Correction (pass 147).** The row above originally credited the rollout to `setImage`. Four mutations were issued back to back and the `api`-triggered deploy belonged to `restartServer`, not `setImage`. Re-tested in isolation: `setImage` changes the stored image and mints **no** deploy — the service stays on its revision with the previous deploy live — and the staged image rolls out on the next deploy, which is the documented "next deploy uses it" contract (`apps/service.go`, `patchFetched`'s comment on `SetSourceAndRegistryCredential`). The guard question is unchanged: the call is accepted on a protected member without a confirmation and has no `confirm` argument to offer one. If anything it is worse, because the change is invisible until an unrelated trigger applies it.

The delete case is the control: the guard was armed the whole time.

### The guard, and the shape of the gap

`lego/backend/internal/apps/protection.go:84-103` — `requireUnprotected(ctx, a, verb)`; `:51-54` mints `ProtectedConfirmation(verb, name)` as `"sudo <verb> service <name>"`, deliberately per-verb so *"a confirm typed for one destructive verb can't accidentally arm another"*.

`grep -n requireUnprotected lego/backend/internal/apps/*.go` → three call sites: `service.go:2301` (delete), `service.go:4098` (suspend), `deploy.go:2716` (stack-apply override). Nothing else.

It is not just that the newly-identified verbs skip the check — **they cannot express it**. Introspecting the mutation arguments: `suspendService(id, confirm)` has a `confirm`; `setImage(id, image, registryCredentialId)`, `setEnvVar(serviceId, key, value, generateValue)`, `setEnvVars(serviceId, envVars)`, `scaleService(id, numInstances)` and `restartServer(serviceId)` have none. A caller who *wanted* to confirm has no way to.

### What the ADR already says, and what it does not

[`docs/ADR032-environments.md`](../../../docs/ADR032-environments.md) § `protectedStatus` lists the guarded set positively — `Delete`, `Suspend`, and the stack-apply override — and gives reasons for two exclusions:

- `Resume` is excluded because *"a protected environment blocks taking availability away, not restoring it"*.
- The webhook auto-deploy path is excluded because it *"stays unauthenticated-by-webhook-signature and ungated by design"*.

What it does not say is why the set stops there, or what rule a new verb should be tested against. Two candidate rules, and the task is to pick one:

- **"Takes availability away or redefines the service"** — pulls in `setImage`/`setRepo` (redefines), maintenance-mode-on (takes availability away, the same effect as suspend, which is guarded), and arguably plan/scale reductions.
- **"Mints a release"** — pulls in every verb that `patchFetched` records a deploy row for (`service.go:4155-4170` lists them: start/build command, root dir, Dockerfile path, pre-deploy command, health check path, plan, disks), which is a larger and more mechanical set.

The second is easier to enforce and harder to drift, because the deploy-history gate already enumerates it. The first is closer to the ADR's own language. Pick deliberately and say which.

### Prior art to match

`w6/m37` extended this guard from services to Postgres and Key Value, closing a gap `w6/m19`'s closeout had flagged. That milestone's shape — decide, extend, mirror across surfaces, test — is the one to follow here.

## Steps

1. Choose the rule and enumerate the resulting verb set explicitly.
2. Check each member against the "availability" rationale so the Resume-style exclusions stay coherent (a verb that only *restores* should stay ungated).
3. Decide what happens to **maintenance mode**: enabling it takes availability away exactly as suspend does. It is paid-web-only, so this hunt could not exercise it — see Out of scope for why it is called out rather than assumed.
4. Write the rule and the set into ADR032's `protectedStatus` bullet, keeping the existing exclusions and their reasons.
5. Record the decision in the ADR018 Environments row if the parity story changes.
