Why: completing an environment deletion should leave the project on an existing environment or its correct empty view, with New Service pointing to a valid placement.

**Severity:** minor. Deletion is durable, but the ready page retains the removed environment and offers its dead ID for service creation until another refresh. No service creation against that ID or data loss was tested. **Estimate:** 55m (ordered deletion publication 15m, real Apollo regressions and passing controls 25m, live replay and closeout 15m). ## Root cause and bounded fix

- `dashboard/src/features/environments/hooks/use-delete-environment.ts:22–34` names Environments in `refetchQueries`, awaits it, then reports delete success. Waiting does not guarantee that the request started after deletion. `environment-card.tsx:205–207` closes the dialog on that result.
- Actual installed **Apollo4.1.3**: `core/QueryInfo.js:335–352` waits for named refetch results; `core/QueryManager.js:903–921` calls ObservableQuery.refetch; `core/ObservableQuery.js:366–396` forces network-only but retains context; `core/QueryManager.js:512–576` deduplicates the printed document and variables onto an existing in-flight observable. This is application ordering, not a claimed Apollo defect.
- `environments-panel.tsx:124–143` selects and canonicalizes from that cached list. A stale list still contains the deleted ID, so the missing-ID fallback never runs. Its New Service link at :207–213 also uses that selected environment. The passing control confirms this consumer already expresses the correct target once given a post-write list.
- Reuse `features/environments/lib/refresh-environments.ts:20–37`: settle older reads individually, then publish a project-scoped network-only EnvironmentsDocument read with `queryDeduplication:false`. A fresh read started alongside an older one is insufficient if the old answer can overwrite it later.
- Supply the known parent project from `environment.projectId` through the sole production caller (`environment-card.tsx:125`), e.g. `useDeleteEnvironment(environment.projectId)`; keep `remove(id,name)` and its boolean committed-delete contract. Do not look up the deleted environment afterward to discover its project.
- Separate the mutation from refresh publication. A refused delete remains an error with its dialog intact. A committed delete whose read fails receives a refresh warning and read-only retry, never another delete or a failed-delete toast. Keep existing ready layout stable while refreshing and keep the delete pending until publication settles. After a successful read, the URL, selector, card and New Service target must derive from the remaining list. Preserve existing first-environment/Unassigned/empty selection rules; no backend deletion-policy change.

**Blast radius:** one production delete-hook consumer, EnvironmentCard, on `/project/$projectId`. There are eight environment mutation hooks: create, rename, delete, set-services, set-databases, set-keyvalues, set-env-groups and set-acl. Create and Key Value membership already use the ordered publisher; the other six retain named list refetches. Allowlist this change to deletion and preserve both existing publisher callers with regression controls. Group membership was exercised and passed; no sibling ordering failure is asserted. No global Apollo defaults, list fetch policies or configuration controls should change. Web/static/cron/worker/private, Postgres, Key Value and group membership are not separate deletion-hook entrypoints.

REST `DELETE /v1/environments/{id}`, GraphQL `deleteEnvironment`, and MCP `delete_environment` expose the server operation; this filing changes only dashboard publication after that operation. UI/GraphQL deletion plus independent REST GET were exercised, not REST/MCP deletion.
