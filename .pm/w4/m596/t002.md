## Objective

`POST /v1/build-sources/{buildSourceId}/builds` accepts Render's `deploy` object and answers Render's 201. That 201 is the build, plus `deploys` (one `{serviceId, deployId}` per deploy the build started) and `skippedServices` (one `{serviceId, reason}` per service in scope that got no deploy).

## Context

- Render, live OpenAPI of 2026-11-23, `trigger-build-source-build`:
  - With no `deploy`, every linked service with autodeploy on is deployed. `deploy.serviceScope` overrides that.
  - `autodeploy_only` covers every linked service with autodeploy on, including those set to deploy after CI checks pass. Services with autodeploy off get no deploy.
  - `none` deploys nothing: the build runs and deploys no service.
  - `custom` deploys the linked services in `serviceIds`, whatever their autodeploy setting. `serviceIds` is required with `custom` and not allowed with the other scopes, and the caller must be allowed to trigger a deploy for each service listed.
  - `deploys` and `skippedServices` are required in the 201. A skip's `reason` is `suspended` or `deploys_shut_off`, the latter when Render has paused deploys for the service's plan tier. For `autodeploy_only`, suspended services are not listed.
- bex today:
  - `deploys.Service.TriggerBuild` (`lego/backend/internal/deploys/build_sources.go:116-131`) decodes only `clearCache` (`:406-414`).
  - The fan-out to linked services runs after the build succeeds (`sourceBuild.fanout`, the `store.BuildFanoutLedger` retry, `:186-197`, `:320-380`), so no deploy ids exist when the trigger answers.
  - Render's wording ("The deploys that the build started, one for each service") means the deploys exist when it answers. bex therefore needs a deploy row per service in scope at trigger time, waiting on the build. Alternatively, it reserves the ids then and has the fan-out create the rows under them. Whichever you pick, a deploy listed in `deploys` must be readable through `GET /v1/services/{id}/deploys/{deployId}` right away, and must end in a terminal status if the build fails.
  - Map Render's autodeploy rule onto bex's `autoDeployTrigger` (`commit` and `checksPass` both count as on). Map `deploys_shut_off` onto bex's nearest refusal: a billing-enforced workspace (`core.ErrBillingEnforced`) is the candidate. Otherwise record that bex never emits it.
- GraphQL and MCP: find bex's build-source trigger on each (`lego/backend/internal/deploys/build_sources.go`, the GraphQL `BuildRun` types next to it) and give them the same scope.
- The dashboard's build-source page: check whether Render's dashboard offers a scope when you trigger a build by hand. Follow it if it does, and record it if it does not.

## Steps

1. Decode `deploy` and validate it: an unknown scope, `serviceIds` with a scope other than `custom`, `custom` with no `serviceIds`, and a service not linked to this build source each answer 400 with the field named. A listed service the caller cannot deploy answers 403 or 404, as `create-deploy` does for it.
2. Resolve the services in scope under the trigger lock, create or reserve their deploys, and record the skipped ones with their reasons.
3. Make the fan-out honor the scope chosen at trigger time, so that `none` never deploys, `custom` deploys exactly its list, and a retry from `BuildFanoutLedger` keeps both rules.
4. Answer the 201 with `deploys` and `skippedServices`, both always present, even when empty.
5. Mirror the scope on GraphQL and MCP. Update the dashboard only if Render's does.

## Acceptance criteria

- [ ] With no `deploy`, a build deploys exactly the linked services with autodeploy on, as before, and lists each in `deploys` with a readable deploy id.
- [ ] `none` answers `deploys: []` and no deploy is ever created. `custom` deploys exactly `serviceIds`, whatever their autodeploy setting.
- [ ] A suspended service in a `custom` scope is listed in `skippedServices` with `reason: suspended`. In `autodeploy_only` it is not listed.
- [ ] A failed build ends every deploy it listed in a terminal status. None stays pending forever.
- [ ] The response validates against the re-pinned schema (`rendertest`), and the bad request shapes answer 400 with the field named.
