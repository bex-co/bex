## Objective

A service whose store already holds two or more unprojectable names must be recoverable through single-key deletes.

## Context

- `lego/backend/internal/secrets/service.go:863-903` `deleteMapKeyAfterProjection` projects the reduced set **before** removing the key from the store. With two bad names stored, deleting either still projects the other, so every REST/MCP `DELETE .../secret-files/<name>` returned 500 and removed nothing (live, `srv-db1e42oa8tcs73b1a0bg`). One bad name alone deletes fine (204).
- The dashboard's batch patch recovered by deleting both in one save. Single-key REST/MCP clients have no such route.

## Steps

1. Let a delete commit when the reduced set is no worse than the current one, e.g. remove the key from the store when its projection fails only on keys that already failed before, or skip invalid keys (after t001's rule) when projecting during a delete.
2. Apply the same check to the env-var delete path.

## Files

- `lego/backend/internal/secrets/service.go`, `lego/backend/internal/secrets/files.go`

## Acceptance criteria

- [ ] Test: seed two 254-character names, then delete each with 204; afterwards `PUT ok.txt` returns 200 and the store matches the projected Secret.
