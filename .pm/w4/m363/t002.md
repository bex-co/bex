## Objective

Show that the new bound is safe end to end. The `<name>-files` (and `<gid>-files`) Secret holding the maximum contents plus 500 maximal names must be accepted by a real kube-apiserver and etcd. The REST, GraphQL and MCP request bodies that carry such a file must fit their limits.

## Context

- The Secret is written by `lego/backend/internal/secrets/files.go` (`filesSecretName`, `:65`). The operator mounts it in one projected `/etc/secrets` volume with each linked group's Secret (`lego/operator/internal/controller/deployment_projection.go:671-677`).
- ADR066 #6's original worry was that a map past the Secret ceiling wrote to OpenBao first and then failed at the projection. The new bound must sit at or under what the apiserver accepts, so that cannot recur.
- etcd's default `--max-request-bytes` is 1.5 MiB. Production's value was not read in run sf13.
- bex-api's REST body limit is between 1 MiB and 4 MiB (w4/422). JSON escaping can inflate a file's contents.

## Steps

1. In an envtest (real kube-apiserver + etcd), create a Secret with values totalling the bound and 500 names of 253 characters each. Then try one byte more, and record where the apiserver refuses. Set t001's constant from that result.
2. Find bex-api's request-body limits for REST, GraphQL and MCP. Confirm each carries a bound-sized file whose JSON escaping doubles its size (for example, all `"` characters). Raise a limit only if a Render-valid request would be cut off.
3. Read production etcd's `--max-request-bytes` if access allows. Otherwise record it as unverified, with the envtest result as the evidence.
