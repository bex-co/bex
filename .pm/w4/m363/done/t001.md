## Objective

Give secret-file maps their own byte cap: the combined contents, not names plus contents, up to the bound t002 confirms the apiserver accepts in one Secret (target 1 MiB, never below Render's 1,000,000 bytes). Every writer of a service's or environment group's files map must apply it. Environment-variable maps keep `maxSecretMapBytes` (512 KiB) and their 500-key limit.

## Context

- `lego/backend/internal/secrets/service.go:962-1026`: `maxSecretMapBytes` is shared by `envMapWithinQuota` and `filesMapWithinQuota`, and `mapBytes` counts `len(k) + len(v)`.
- Every files-map writer goes through `filesMapWithinQuota`. `grep -rn "filesMapWithinQuota\|ValidateFilesMapQuota\|ValidatePatchFilesMapQuota" lego/backend/internal | grep -v _test` finds 6 call sites and 2 exported wrappers:
  - `secrets/files.go:174` and `:267`: per-key set and replace-all.
  - `secrets/files.go:498`: the files a create seeds.
  - `secrets/batch.go:347`: the batch `PATCH …/environment` behind the dashboard editor, GraphQL `patchServiceEnvironment` and MCP `patch_service_environment`.
  - `envgroups/service.go:612` (`ValidateFilesMapQuota`): environment-group writes.
  - `envgroups/patch.go:191` (`ValidatePatchFilesMapQuota`): the environment-group batch patch.
  - The wrappers themselves are at `secrets/service.go:1003` and `:1014-1015`.
- Kubernetes counts only values: `k8s.io/api@v0.37.1` `core/v1/types.go:8288`, `:8326`.

## Steps

1. Add a files-only byte constant and a contents-only byte count. Leave `envMapWithinQuota` untouched.
2. Word the refusal in Render's terms ("combined size of secret files exceeds 1 MB" or similar), keeping the 400 and `bad_request` id.
3. Check that `patchWithinQuota`'s "an over-quota map may shrink but not grow" rule still holds for files.
4. Update `secrets/quota_guard_test.go` and `envgroups/quota_guard_test.go` cases to the new bound. The env-var cases must not move.

## Files

- `lego/backend/internal/secrets/service.go`, `files.go`, `batch.go`, their tests
- `lego/backend/internal/envgroups/service.go`, its quota guard test

## Acceptance criteria

- [ ] A files map whose contents total exactly the bound is accepted, and one byte more is refused, on per-key PUT, replace-all PUT, batch PATCH, create seeding and env-group writes.
- [ ] Long names no longer count against the bound. The 500-file and 253-character name limits still apply.
- [ ] A 600 KiB env-var set is still refused with the existing message.

## Out of scope

- Raising the env-var caps.
- The dashboard (t003).

## Outcome (2026-11-14)

- The bound is `maxSecretFilesBytes = corev1.MaxSecretSize` (1,048,576 bytes) of contents. Names are not counted (`contentBytes`). t002's envtest showed the apiserver takes exactly that much.
- `secrets/service.go` now has a `mapQuota` per map (`envQuota`, `filesQuota`), and each one names its own size measure and refusal. `patchWithinQuota` takes the quota, so its "shrink but not grow" comparison uses the same measure as the check. Renaming a file of an over-quota map adds no contents and stays allowed.
- Every files writer goes through `filesQuota`: per-key PUT, replace-all PUT, `SeedSecretFiles`, create seeding (`CheckCreateSecrets`/`createFiles`), the batch `PatchEnvironment`, and the group writes (`ValidateFilesMapQuota`, `ValidatePatchFilesMapQuota`).
- One byte over answers `400 bad request: the combined size of all secret files cannot exceed 1 MB (1048576 bytes)`, still `bad_request`.
- Env vars are unchanged: 500 keys, and 512 KiB of keys plus values with the same sentence.
- The quota guard tests in both packages moved their file cases to `maxSecretFilesBytes+1`, and their env cases did not move.
