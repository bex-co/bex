# w4/020 — `mfaEnabled` false positive: Kratos mints a webauthn credential stub at registration

**Filed:** 2026-07-15, by w4/m25's live verification (drift finding).

`KratosIdentities.Lookup` (`lego/backend/internal/workspaces/kratos.go`) derives
`mfaEnabled` from the *presence* of a `totp` or `webauthn` entry in the
identity's credentials map (w6/m10). Verified live against dev-4: a user who
registers with **password only** already carries a `webauthn` credentials entry
— Kratos mints a stub (`config.user_handle` only, no registered keys) because
webauthn is an enabled method with `identifier: true` in the schema — so the
owners/members surfaces and the dashboard report `mfaEnabled: true` for a user
with no second factor enrolled.

**Proposal:** tighten the derivation to inspect the credential's contents
(webauthn counts only when `config.credentials` is a non-empty list), keeping
totp presence-based (Kratos only writes it on enrollment). One unit test per
shape: stub-only webauthn ⇒ false, enrolled key ⇒ true, totp ⇒ true.

Pre-existing behavior, not introduced by m25 (which only added the `name`
trait to the same lookup); scope is one function + tests.
