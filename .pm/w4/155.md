# Renaming a project or environment onto an existing name answers the unnamed `conflict: project: already exists`

Why: `w6/m49` gave duplicate-name conflicts a specific reason that names the value ("a project named "x" already exists in this workspace"), but only on the create paths. A rename onto a taken name still returns the store's generic text on every surface. That text names neither the value nor the scope, and it carries no `CONFLICT` code.

Found live in `/qa-find-bugs` pass 201 on 2026-09-26 (w4-targeted, `muse.env` credentials), against the deployed `726042a28`. The fixtures were throwaway projects `qa-20260926-proj` / `qa-20260926-proj2b` and their environments. All of them were deleted afterwards; `GET /v1/projects/{id}` and `GET /v1/environments/{id}` both returned 404.

| Probe (target name already taken) | Answer |
| --- | --- |
| Dashboard **New Project** named `qa-20260926-proj` (create) | toast `A project named "qa-20260926-proj" already exists in this workspace` ✅ |
| Dashboard **New Environment** named `qa-staging` again (create) | toast `An environment named "qa-staging" already exists in this project` ✅ |
| Dashboard **Project settings → Edit → Save** as `qa-20260926-proj` | toast `Conflict: project: already exists` ❌ |
| `PATCH /v1/projects/{id} {"name":"qa-20260926-proj"}` | `409 {"error":"conflict: project: already exists","id":"conflict",…}` ❌ |
| GraphQL `renameProject(id:…, name:"qa-20260926-proj")` | `errors[0].message: "conflict: project: already exists"`, no `extensions.code` ❌ |
| `PATCH /v1/environments/{id} {"name":"qa-dev"}` | `409 … "conflict: environment: already exists"` ❌ |
| GraphQL `renameEnvironment(id:…, name:"qa-dev")` | `"conflict: environment: already exists"` ❌ |

The Project settings page labels the field "A unique name for your project", so a user who hits this is being told the rule without being told which name broke it.

## Mechanism

- Create routes the store error through each package's `conflictOrMapError(err, name)`: `lego/backend/internal/projects/service.go:450` and `lego/backend/internal/environments/service.go:610`. That helper returns `core.NewConflictError("CONFLICT", "a project/an environment named %q already exists in this …", nil)`.
- Rename calls `store.MapError(err)` directly instead:
  - `projects/service.go:469`: `Service.Rename`. Serves REST `PATCH /v1/projects/{id}`, GraphQL `renameProject` (`projects/graphql.go:84`), MCP `update_project` `name` (`projects/mcp.go:102`), and the dashboard hook `use-rename-project.ts`.
  - `environments/service.go:634`: `Service.Rename`. Serves GraphQL `renameEnvironment` (`environments/graphql.go:128`) and `use-rename-environment.ts`.
  - `environments/service.go:672`: the `Update` rename half. Serves REST `PATCH /v1/environments/{id}`, GraphQL `updateEnvironment`, and MCP `update_environment` `name`.
- The dashboard needs no change. Both rename hooks pass the refusal through `mutationErrorMessage` (`dashboard/src/common/lib/graphql-error.ts:85`), which renders the server's reason. That is why the toast shows the raw store text.

## Fix

Swap `store.MapError(err)` for the existing `conflictOrMapError(err, name)` at the three rename call sites. After the fix, a rename conflict returns the create path's shape on every surface:

- REST: 409 `conflict` with a `code` field.
- GraphQL: `extensions.code: "CONFLICT"`.
- MCP: the stable conflict prefix.
- The message names the attempted value and its scope ("in this workspace" / "in this project").

Other errors are unaffected, because non-conflict errors still fall through to `store.MapError`. Add unit tests in both packages asserting that a rename onto a taken name returns the named `CONFLICT`, mirroring the `w6/m49` create tests. Add a regression test that a rename to the row's own current name still succeeds (no self-conflict).

Sibling rename paths are already correct and were read, not changed:

- Postgres `UpdatePostgres` and Key Value `UpdateKeyValue` (`ensureDatabaseNameAvailable` / `ensureKeyValueNameAvailable` with an exclude-id).
- Services (`apps/service.go:1913`, `:2165`).

Pass 202 re-probe: MCP `update_project {id, name:<taken>}` returns `isError: true` with text `conflict: project: already exists`. That confirms the gap on MCP too. Control: env groups are already correct on both create and rename. REST `PATCH /v1/env-groups/{id}` answers `409 {"code":"ENV_GROUP_NAME_EXISTS","message":"Environment group name already exists.","params":{"name":…,"workspaceId":…}}`, and GraphQL `renameEnvGroup` returns the same `extensions.code`. Still unverified: MCP `update_environment` `name` (same `Update` verb as REST `PATCH /v1/environments/{id}`; not called live).

Render: Render's project/environment update APIs do not document a uniqueness conflict, so this is bex's own consistency (`w6/m49`), not a parity item.

Estimate: ~30m.
