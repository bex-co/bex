# Postgres Recover copies a protected environment's data out of its environment and allow-lists

Why: `postgres.Service.Recover` needs only `can_create` on the source. It builds the new instance with tenant labels alone, so a point-in-time copy of a database in a protected, isolated or allow-listed environment lands outside that environment, its inbound-IP layer and the source's own IP allow-list. This is the copy-shaped twin of the move side doors w4/m232 closed: the data leaves the admin boundary even though the source stays put.

- **Source:** `w4/m232` security review, 2026-10-19 (loopx w4). Reasoned from code, not probed live.
- **Path:** `lego/backend/internal/postgres/recovery.go:231` `Recover`:
  - `fetchDatabase(ctx, core.RelCanCreate, name)`, with no `can_manage` on an ACL-bearing source environment.
  - The new `Database` (`:302-322`) gets `core.TenantLabels(tenantID)` only: no `core.LabelProject` / `core.LabelEnvironment`, no `spec.ipAllowList` from the source, no environment IP layer.
- **Effect:** a developer can materialize a protected production database's contents as a fresh workspace-scoped instance governed by whatever a new database defaults to. Not verified: what that default exposes, whether the export or read-replica paths share the shape, and Render's documented behavior (does a recovered database inherit the source's environment and access control?).
- **Decision/fix sketch:**
  - Either require a fresh `can_manage` when the source's environment is ACL-bearing (the w4/m232 exit rule applied to copies),
  - or create the recovered instance in the source's environment with its allow-lists, so it inherits the boundary.
  - Check Render first, record parity in ADR018, and add REST/GraphQL/MCP tests with a `developerChecker`.
- **Estimate:** 1h (check Render, implement, test).
