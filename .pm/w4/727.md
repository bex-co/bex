# 727 — The CLI suite fails on a host that has a coding-provider key in its environment

Why: `scripts/ship-gates.sh` runs the CLI suite on the developer's host, and that host's `ZAI_API_KEY` or `KIMI_API_KEY` makes a test fail. Every worker on such a host first sees a red gate and has to work out that CI does not set those keys.

**Severity:** minor. **Estimate:** ~30m. **Source:** `/loopx w4` orchestrator, 2026-11-23, from the w4/m578 worker's gate runs, reproduced on this host.

## Evidence

- On a host with `ZAI_API_KEY` and `KIMI_API_KEY` set, `cd lego/cli && go test -run TestBexNativeGroupsWithoutAWordAreUnchanged -count=1 .` fails. `usage_contract_test.go:105` reports `stdout lacks "bex code keys set glm"`, because `bex code` prints `key from ZAI_API_KEY (environment)` instead of the "no key" hint. With `env -u ZAI_API_KEY -u KIMI_API_KEY` the same command passes.
- The child's environment comes from `bexAgainst` (`lego/cli/sandbox_id_contract_test.go:101`): `withoutRenderEnv(os.Environ())` plus a temporary `HOME`. It keeps every provider key `lego/cli/internal/code/provider.go` reads (`KeyEnvs`: `ZAI_API_KEY`, `GLM_API_KEY`, `MOONSHOT_API_KEY`, `KIMI_API_KEY`, and those of the other providers).

## Fix

1. Strip every provider's `KeyEnvs` from the environment the CLI tests hand to `bex`, in `bexAgainst` and in any other helper that builds a child environment from `os.Environ()` (`main_test.go`, `disclosure_test.go`). Read the list from `provider.go` rather than copying it, so a new provider is covered.
2. Tests that need a key keep setting it explicitly, as `main_test.go:972` does with `ZAI_API_KEY=test-provider-key`.

## Acceptance criteria

- [ ] `ZAI_API_KEY=x KIMI_API_KEY=y GLM_API_KEY=z MOONSHOT_API_KEY=w go test ./...` in `lego/cli` passes.
- [ ] A test fails if a provider's key variable is missing from the stripped set.
