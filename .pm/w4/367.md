# 367 — Logs "Live" shows a request line about 30 s after the app line from the same request, under "Live mode appends new lines as they arrive"

Why: someone debugging a live service watches their app's stdout line appear within a second or two, while the HTTP request line for the very same request turns up about half a minute later. Request logs are not live in the tab that promises live lines, and Render's `subscribe-logs` streams every log type in real time.

**Source:** live `/qa-find-bugs w4` pass cc398c, 2026-10-19 UTC, pin `108cdb3acca8`, workspace `bex-canary`. Two owned Free web services, deleted afterwards (`DELETE` 204, then `GET` 404); only that run's session was revoked:

- `qa-20261019-cc398c-logs` (`srv-dbatj5hkv6rc73en2cf0`): `traefik/whoami:v1.10`.
- `qa-20261019-cc398c-go` (`srv-dbatmdhkv6rc73en2cng`): `examples/hello-go`, which logs `GET <path>` to stdout for every request.

## Probes

- **Dashboard** `/services/<id>/logs`, defaults "All logs", "Last hour", Live on. The page says "The range limits history. Live mode appends new lines as they arrive." A single `GET https://<service>.onbex.co/qa-cc398c-<tag>` was sent, and the page text was sampled every 1 s:

| Service, tag | App stdout line `GET /qa-cc398c-<tag>` visible after | Request line (access JSON) visible after |
| --- | --- | --- |
| whoami, `tail` | — (whoami logs nothing per request) | 28 s |
| whoami, `dash1` / `dash2` | — | 25 s / 29 s |
| hello-go, `ctl1` | **2 s** | **24 s** |
| hello-go, `ctl2` | **1 s** | **30 s** |

- **Control, REST** `GET /v1/logs?resource=<id>&type=request&text=qa-cc398c-<tag>&startTime=<now-5m>`, polled every 1 s: the line is readable **1.6 s, 1.6 s and 1.7 s** after the request, and its record timestamp is 0.1 s after the send. The log store has the line almost at once, so the delay is the dashboard's delivery.
- **History paging and filters are correct.** 60 uniquely-pathed requests paged with `limit=10` backward and forward return all 60 once, in order, with `hasMore` ending correctly. `path`, `path` with `*`, `text`, `method` and `statusCode` narrow as expected, and `limit=1000` → `400`.

## Root cause

- The live tail streams only pod stdout. `lego/backend/internal/logs/service.go:385-392` (`tailSupports`) refuses `type=request` and request-only filters ("the live tail reads pod logs, so it cannot stream request logs…"), and `liveSubscribable` (`:396-401`) names app and build stdout as its only producers.
- With "All logs" selected, the dashboard opens the SSE tail (`dashboard/src/features/logs/hooks/use-live-logs.ts`, `GET /v1/logs/subscribe`) for app lines. Request lines reach the page only when the history query is refetched.
- The capture shows one `Logs` GraphQL request per about 30 s, alongside the page's resource polls (`RESOURCE_POLL_INTERVAL_MS = 30_000`, `dashboard/src/common/lib/polling.ts:11`). The exact hook that drives that refetch was not traced (cause unverified).
- The copy is `logs.*` in `dashboard/src/features/logs/locales/en.ts:10`.
- ADR018's request-log row records that the tail "auto-disables (with a note) while a store-only filter is active". It says nothing about request lines arriving late on "All logs" with Live on.

## Fix (target behavior)

In Live mode on "All logs" (and when the type is Request), a new request line appears within about 5 s of the request, close to the 1–2 s an app line takes. For example:

- the subscribe stream gains a log-store producer for `type=request` (a short-interval Loki read or Loki's tail API, merged in timestamp order, carrying the same filters);
- or, at minimum, the dashboard runs a short live poll for request lines only (moving `startTime`, de-duplicated by record id, as the history merge already is).

If neither ships, the copy must stop promising "as they arrive" for request lines and say how often they refresh. REST, GraphQL and MCP history are unchanged.

**Render:** `subscribe-logs` (pinned OpenAPI, `/logs/subscribe`) takes the same filter vocabulary, `type` included, and says "Logs are streamed in real-time as they are generated." That is why the backend producer is the parity fix.

**Unverified:** the zh copy; datastore log viewers (no request logs); the exact refetch hook.

Estimate: 60m (promote to a milestone if the backend producer route is chosen).
