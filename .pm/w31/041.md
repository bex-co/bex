# 041 — `agentsessions.Service.reactivate` (`resume_agent_automation` / `take_over_agent_automation`) performs two separate non-transactional updates, jumping `version` by +2 and risking a stuck `enabled=true, next_fire_at=NULL` row

Why: `agentsessions.Service.reactivate` (`lego/backend/internal/agentsessions/automations.go:524-540`) commits `SetAgentAutomationPaused(ctx, row.ID, false, "")` (setting `enabled = true`, bumping `version` once, and leaving `next_fire_at` as `NULL`) and then issues a separate `UpdateAgentAutomation(ctx, resumed, resumed.Version)` to write `next_fire_at` and bump `version` a second time — so every resume jumps `version` by +2 and any transient error or concurrent-edit `409` between the two writes leaves the automation committed as `enabled = true` with `next_fire_at = NULL`, invisible to the scheduler.

### `resume_agent_automation` jumps `version` by +2 and is non-atomic between `enabled = true` and setting `next_fire_at`

- **Severity:** major
- **Versions:** deployed pin `8b9d780f45` (`cdaa0a248615`, active on production during run; zero diff in `lego/backend/internal/agentsessions/automations.go` and `lego/backend/internal/store/agentautomations.go` vs `HEAD` `5ef2b31e0d`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`
- **Context:** 2026-11-25, endpoint `/mcp` (`https://api.bex.co/mcp`), workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), disposable automation `aut-dc3l2s4g1jgc73dafv10` (deleted after run), run-minted all-permissions API key (revoked)

- **Expected / actual:**
  - **Expected:** A single `resume_agent_automation` (or `take_over_agent_automation` resuming a `creator_lost_access` pause) should atomically set `enabled = true`, clear `paused_reason`/`paused_at`/`pause_notified_at`, reset `consecutive_failures`/`notify_failure_streak`, set `next_fire_at` (and `created_by` on takeover), and increment `version` by **1** in a single `UPDATE` statement (never committing an intermediate `enabled = true, next_fire_at = NULL` state).
  - **Actual:** On `aut-dc3l2s4g1jgc73dafv10`, `pause_agent_automation` returned `version: 3` (`enabled: false`, `nextFireAt: null`), and the immediately following single `resume_agent_automation` call returned **`version: 5`** (`enabled: true`, `nextFireAt: "2027-01-01T00:00:00Z"`), skipping `version: 4` because two separate Postgres `UPDATE` queries ran back to back.
- **Wire evidence:**
  - `update_agent_automation` -> `version: 2`, `enabled: false`, `nextFireAt: null`.
  - `pause_agent_automation` -> `version: 3`, `enabled: false`, `nextFireAt: null`.
  - `resume_agent_automation` -> `version: 5`, `enabled: true`, `nextFireAt: "2027-01-01T00:00:00Z"`.
- **Attribution:** server (`lego/backend/internal/agentsessions`, `lego/backend/internal/store`)
- **Root cause:**
  - `agentsessions.Service.reactivate` (`lego/backend/internal/agentsessions/automations.go:524-540`) runs two separate store calls with no enclosing transaction:
    1. `resumed, err := s.Automations.SetAgentAutomationPaused(ctx, row.ID, false, "")` (`automations.go:533`, implemented in `store/agentautomations.go:326-348`), which commits `enabled = true`, clears `paused_reason`/`consecutive_failures`/`notify_failure_streak`, does **not** touch `next_fire_at` (still `NULL`), and increments `version = version + 1`.
    2. `resumed.CreatedBy, resumed.NextFireAt = row.CreatedBy, next` followed by `s.Automations.UpdateAgentAutomation(ctx, resumed, resumed.Version)` (`automations.go:537-538`), which writes `next_fire_at` and `created_by` and increments `version = version + 1` a second time.
  - If the second call fails (transient DB error, context cancellation, or a concurrent update bumping `version` → `ErrAgentAutomationVersion` / `409`), the first `UPDATE` has already committed `enabled = true` with `next_fire_at = NULL`. Because `ClaimDueAutomations` (`store/agentautomations.go:365-369`) filters `WHERE enabled AND next_fire_at <= $1`, an enabled automation with `next_fire_at = NULL` is silently skipped forever and never fires (nor does it report paused).
- **Fix:**
  - Replace the two-step write in `reactivate` (`lego/backend/internal/agentsessions/automations.go:524-540`) with a single atomic store method (e.g. `ResumeAgentAutomation(ctx, id, expectedVersion, createdBy, nextFireAt)` in `lego/backend/internal/store/agentautomations.go`, or extend the resume path in `SetAgentAutomationPaused` / `PGStore`) that performs one `UPDATE agent_automations SET enabled = true, paused_reason = NULL, paused_at = NULL, pause_notified_at = NULL, consecutive_failures = 0, notify_failure_streak = 0, created_by = $2, next_fire_at = $3, version = version + 1, updated_at = now() WHERE id = $1 AND version = $4 RETURNING ...`.
  - Also check `PauseAgentAutomation` (`automations.go:464-471`) so pausing clears `next_fire_at = NULL` in the same `UPDATE` if desired, and keep `expectedVersion` optimistic concurrency checking so a concurrent edit cannot overwrite a newer template or schedule.
  - Surface impact: fixes MCP `resume_agent_automation` / `take_over_agent_automation`, REST `POST /v1/agent-automations/{id}/resume` & `/take-over`, and GraphQL `resumeAgentAutomation` / `takeOverAgentAutomation` together.
