# 164 — `sandbox.Service.UpdateGroup` / `store.PGStore.SetSandboxGroupLimit` unconditionally writes to Postgres and bumps `updatedAt` on no-op `concurrencyLimit` updates across MCP, REST, and GraphQL

Why: Unlike its two sibling methods immediately below it in the same file (`SetSandboxGroupEnvironment` at `lego/backend/internal/store/sandbox_groups.go:269-271` and `SetDefaultSandboxGroup` at `:302-305`, both of which short-circuit without modifying `updated_at` when the target state already holds), `store.PGStore.SetSandboxGroupLimit` (`store/sandbox_groups.go:243-252`, called by `sandbox.Service.UpdateGroup` at `sandbox/groups.go:385-402`) unconditionally runs `UPDATE sandbox_groups SET concurrency_limit = $3, updated_at = now()` even when the clamped `concurrencyLimit` equals the group's current `concurrency_limit` — advancing `updatedAt` and writing to Postgres on every identical or ceiling-clamped no-op `update_sandbox_group` / `PATCH /v1/sandbox-groups/{id}` / `updateSandboxGroup` call.
