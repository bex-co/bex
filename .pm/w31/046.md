# 046 — `sshkeys.Service.List` and `Delete` query `ssh_keys` by the API key's client UUID instead of refusing machine callers or resolving the creator, silently returning `[]` and `NOT_FOUND` on MCP, REST, and GraphQL

Why: `sshkeys.Service.Create` (`lego/backend/internal/sshkeys/service.go:98`) calls `s.AuthorizeMintClass(ctx)` and refuses every API key with `403 FORBIDDEN`, so an API key's Hydra client UUID can never own any row in `ssh_keys`; yet `sshkeys.Service.List` (`:146-158`) and `sshkeys.Service.Delete` (`:160-179`) omit `AuthorizeMintClass` and query `s.Store.ListSSHKeys(ctx, id.Subject)` / `DeleteSSHKey(ctx, id.Subject, id)` verbatim, causing an `All` API key to silently receive `{"sshKeys":[]}` and `NOT_FOUND` even when the user who minted the key has registered SSH keys.

- **Expected / actual:**
  - **Expected:** `ssh_keys` is a human-account credential table (keyed by Kratos subject, with no `tenant_id` column, and enrollment locked to `AuthorizeMintClass`). Calling `list_ssh_keys` or `delete_ssh_key` (and REST `GET/DELETE /v1/ssh-keys` / GraphQL `sshKeys`/`deleteSSHKey`) with an API key should either:

- **Attribution:** server (`lego/backend/internal/sshkeys`)
- **Root cause:**
  - `sshkeys.Service.Create` (`lego/backend/internal/sshkeys/service.go:98`) enforces `s.AuthorizeMintClass(ctx)`, preventing any API key or third-party OAuth client from creating an SSH key under its own subject.
  - `sshkeys.Service.List` (`service.go:146-158`) and `sshkeys.Service.Delete` (`service.go:160-179`) call `s.Authorize(ctx, core.RelCanManageSSHKeys)` and then `callerSubject(ctx)` (`service.go:53-59`), which returns `id.Subject` verbatim — for an API key, its Hydra client UUID, which can never exist in `ssh_keys.subject`.
  - `lego/backend/internal/api/key_permission_ops.go:557,689` maps `list_ssh_keys` and `delete_ssh_key` (and their REST/GraphQL twins) to `{core.KeyNoGrant}` (blocking scoped keys, admitting `All` keys).
- **Fix:**
  - Decide consistently with `sshkeys.Service.Create` and `ADR024` (note SSH keys are account-global, not workspace-scoped, whereas an API key is bound to one workspace):
    - Recommended: reject API keys / machine callers in `sshkeys.Service.List` and `sshkeys.Service.Delete` (e.g. `if id.IsAPIKey() || !id.Human` or `AuthorizeMintClass` on `Delete` + `if id.IsAPIKey()` on `List` with a clear refusal explaining SSH keys are account-level human credentials), so a workspace-bound API key neither falsely claims the user has no SSH keys nor reaches across workspaces to delete account-global SSH keys.
    - Keep human sessions and first-party CLI OAuth tokens working unchanged.
  - Surface impact: fixes MCP (`list_ssh_keys`, `delete_ssh_key`), REST (`GET /v1/ssh-keys`, `DELETE /v1/ssh-keys/{id}`), and GraphQL (`sshKeys`, `deleteSSHKey`) uniformly through `sshkeys.Service`.
