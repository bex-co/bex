# 030 — `postgres.Service.Failover` never checks `d.Spec.HighAvailability`, so MCP `failover_postgres`, REST `POST /v1/postgres/{id}/failover`, and GraphQL `failoverDatabase` falsely succeed on non-HA databases and leave a stale `spec.failoverAt` armed

Why: `postgres.Service.Failover` stamps `d.Spec.FailoverAt` and returns success (`{"accepted":true}` / `202 Accepted`) even when `d.Spec.HighAvailability` is `false`, while the operator silently ignores `spec.failoverAt` on non-HA databases — misleading callers into believing a failover occurred and leaving an unconsumed `spec.failoverAt` timestamp on the CR that will fire an unintended switchover if HA is enabled later.

### `failover_postgres` (MCP) and `POST /v1/postgres/{id}/failover` (REST) return success on non-HA (including `free`) Postgres databases

- **Attribution:** server (`lego/backend/internal/postgres`)
- **Root cause:**
  - `Service.Failover` (`lego/backend/internal/postgres/lifecycle.go:104-123`) checks `requireUnprotected` (`:113`) and `d.Spec.Suspended` (`:116`), then unconditionally patches `d.Spec.FailoverAt = s.Now().UTC().Format(time.RFC3339)` (`:119-121`) without checking `d.Spec.HighAvailability`.
  - In the operator, `lego/operator/internal/controller/database_controller.go:2108` only executes a switchover when `db.Spec.HighAvailability && db.Spec.FailoverAt != "" && db.Spec.FailoverAt != db.Status.LastFailoverAt` — so on a non-HA database the operator ignores the write completely, leaving `spec.failoverAt` armed with `status.lastFailoverAt == ""` until HA is ever enabled later (at which point the stale timestamp immediately triggers an unintended switchover).
- **Fix:**
  - In `Service.Failover` (`lego/backend/internal/postgres/lifecycle.go:104-123`), refuse when `!d.Spec.HighAvailability` (e.g. `core.NewBadRequestError("POSTGRES_HIGH_AVAILABILITY_REQUIRED", fmt.Sprintf("Postgres %q does not have high availability enabled; enable high availability before failing over", name), map[string]any{"postgresId": d.Name})`, or `409 Conflict` if matching `suspended` — check Render's exact status for non-HA failover, `400` is listed in `render-public-api-1.json` while `409` is not, so `400` matches Render's OpenAPI responses table).
  - Also check whether `!d.Status.HighAvailabilityEnabled` while HA is still converging should return a clear error or remain accepted once `d.Spec.HighAvailability` is true (at minimum, `!d.Spec.HighAvailability` is never valid and must fail without touching `spec.failoverAt`).
  - Update existing unit-test fixtures that seeded a default non-HA Database CR for the happy path (`TestFailoverREST` in `lego/backend/internal/postgres/ha_test.go:306` and `running control still stamps failoverAt` in `lego/backend/internal/postgres/lifecycle_suspended_test.go:351`) to set `HighAvailability: true`, and add regression tests asserting `Failover` on a non-HA database fails across service, REST `POST /v1/postgres/{id}/failover`, GraphQL `failoverDatabase`, and MCP `failover_postgres` without stamping `spec.failoverAt`.
  - Surface impact: fixes MCP `failover_postgres`, REST `POST /v1/postgres/{id}/failover`, and GraphQL `failoverDatabase` together (all call `postgres.Service.Failover`).
