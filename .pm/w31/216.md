# 216 — Scoped `services: read_write`, `build_sources: read_write`, and `blueprints` API keys bypass `core.KeyWorkspaceRegistry` (`workspace.registry.view`) to bind private workspace registry credentials and read credential names across MCP, REST, and GraphQL

Why: `lego/backend/internal/core/keygrant.go:108,241,365` restricts `core.KeyWorkspaceRegistry` (`workspace.registry.view`, "View registry credentials") to the `workspaces` API-key permission, and `lego/backend/internal/api/key_permission_ops.go:446-448,631,696,985-986` enforces `core.KeyWorkspaceRegistry` on `list_registry_credentials`, `get_registry_credential`, `GET /v1/registrycredentials*`, and `GQL Query.{registryCredentials,registryCredential,isDeployableImage}`. Yet `registrycreds.Service.resolvePullCredential` (`lego/backend/internal/registrycreds/pullsecret.go:74-110`), `pullSecretSource.ResolveCredentialNames` (`:222-235`), `pullSecretSource.FindCredentialIDByName` (`:242-259`), and their callers in `apps` (`lego/backend/internal/apps/pullsecret.go:68-73,119-131`, `deploy.go:1917-1955`) never call `RequireKeyGrant(ctx, core.KeyWorkspaceRegistry)` — letting a `services: read_write`-only or `build_sources: read_write`-only API key (with zero `workspaces` permission) bind any workspace private registry credential (`registryCredentialId`) onto services or build sources, materialize its OpenBao registry password into a Kubernetes `dockerconfigjson` pull Secret on create/deploy, and read back the credential's display name (`registryCredential.name`) across MCP, REST, and GraphQL.

- **Expected / actual:**
  - **Expected:** Consistent with `lego/backend/internal/api/key_permission_ops.go:33-37`, `GQL Query.isDeployableImage` (`key_permission_ops.go:448`), and `w31/060`–`w31/061`, any scoped API key that supplies a non-empty `registryCredentialId` (on service or build-source create/update across MCP, REST, and GraphQL) or references a workspace credential by name via Blueprint `fromRegistryCreds` must hold `core.KeyWorkspaceRegistry` (`workspace.registry.view`), or be refused with `403 api_key_permission_denied` before looking up the credential or reading its OpenBao secret. Clearing a binding (`registryCredentialId: ""`) or updating unrelated fields on a service that already has a binding should remain allowed for `services: read_write`.
  - **Actual:**
    - All three controls (`list_registry_credentials`, `get_registry_credential`, `GQL Query.isDeployableImage`) denied `key-svc-rw` with `api_key_permission_denied` (`required: ["workspace.registry.view"]`).

On create/deploy, `MaterializePullSecret` reads the credential's OpenBao password (`s.storedSecret`) and materializes it into a Kubernetes `dockerconfigjson` Secret on the service, allowing an unprivileged key to pull private corporate images into an attacker-controlled container.

- **Attribution:** server (`lego/backend/internal/registrycreds`, `lego/backend/internal/apps`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go` checks only the primary service/build-source/blueprint permission at dispatch (`KeyServicesManage`, `KeyBuildSourcesManage`, `KeyBlueprints*`), never `core.KeyWorkspaceRegistry`.
  - `registrycreds.Service.resolvePullCredential` (`lego/backend/internal/registrycreds/pullsecret.go:74-110`, invoked by both `ValidatePullSecret` at `:193` and `MaterializePullSecret` at `:199`) looks up the credential (`:91`) and fetches its OpenBao password (`s.storedSecret` at `:106`) without checking `s.RequireKeyGrant(ctx, core.KeyWorkspaceRegistry)`.
  - `apps.Service.Create` (`lego/backend/internal/apps/service.go:2797`), `apps.Service.checkSourcePatch` (`lego/backend/internal/apps/settings_check.go:703`, backing `SetSourceAndRegistryCredential`, `update_service`, `PATCH /v1/services/{id}`, GraphQL `setImage`/`setRegistryCredential`, and `UpdateBuildSource`), `apps.Service.CreateBuildSource` (`lego/backend/internal/apps/build_sources.go:247,255`), and `apps.Service.resolveBlueprintRegistryCredentials` (`lego/backend/internal/apps/deploy.go:1917-1955`, `blueprint.go:858,1508`, calling `FindCredentialIDByName` at `pullsecret.go:242`) never call `s.RequireKeyGrant(ctx, core.KeyWorkspaceRegistry)` when binding a new non-empty credential ID or resolving `fromRegistryCreds` by name.
- **Fix:**
  - Require `core.KeyWorkspaceRegistry` via `s.RequireKeyGrant(ctx, core.KeyWorkspaceRegistry)` (`lego/backend/internal/core/keygrant.go:620`) whenever a caller-initiated request explicitly binds a non-empty `registryCredentialId` or resolves a `fromRegistryCreds` credential name:
    1. In `apps.Service.Create` (`apps/service.go`, and `CreateBuildSource` / `checkSourcePatch` when `patch.RegistryCredentialID != nil && strings.TrimSpace(*patch.RegistryCredentialID) != ""` and it differs from the existing `a.Spec.RegistryCredentialID`, so changing an unrelated field or re-deploying an already-bound service with a `deploys_run`-only key is not broken): call `s.RequireKeyGrant(ctx, core.KeyWorkspaceRegistry)` before `validateExternalRegistryCredential` / `ensureExternalRegistryPullSecret`.
    2. In `apps.Service.resolveBlueprintRegistryCredentials` (`apps/deploy.go:1917-1955`): when any declaration names a `registryCredentialName`, call `s.RequireKeyGrant(ctx, core.KeyWorkspaceRegistry)` (non-identity webhook/auto-sync callers pass through `RequireKeyGrant` as a no-op).
    3. Verify `ResolveCredentialNames` / `RegistryCredentialName` enrichment behavior for `services: read`-only keys: either keep safe name enrichment for already-bound services or gate on `KeyWorkspaceRegistry` — crucially, never let a dry-run bind probe arbitrary credential IDs to read their display names without `KeyWorkspaceRegistry` (which step 1 blocks before validation/rendering).
  - Surface impact: protects MCP, REST, and GraphQL uniformly across services, build sources, and Blueprints while preserving deploys/restarts of already-bound services for `deploys_run`-only keys and explicit clears (`""`) for `services: read_write` keys.
- **Blast radius:** `lego/backend/internal/apps/{service,settings_check,build_sources,deploy}.go`, `lego/backend/internal/registrycreds/pullsecret.go`, and scoped-key tests in `lego/backend/internal/api/` and `lego/backend/internal/apps/`.
