# 141 — `sandbox.ownerID` and `sandboxFromOpenSandbox` leak raw internal Kratos/Hydra UUIDs in `Sandbox.owner`, lock non-admin developers out of API-key sandboxes, and record Hydra client UUIDs in `sandbox_executions`

Why: `sandboxFromOpenSandbox` (`lego/backend/internal/sandbox/service.go:835`) copies `raw.Metadata["bex.co/owner"]` verbatim into `Sandbox.Owner` without mapping subjects through `core.PublicUserIDs(ctx, s.UserIDs, ...)` — leaking raw internal Kratos UUIDs across MCP `list_sandboxes`, REST `GET /v1/sandboxes{,/{id}}`, and GraphQL `sandboxes`/`sandbox` even while `list_sandbox_executions` on the same sandbox maps the same user to `usr-…` — and `ownerID(ctx)` (`service.go:504-514`) plus execution recorders (`exec.go:225`, `connect.go:182`, `file_connect.go:191`) write an attributed API key's raw Hydra client UUID instead of resolving `s.KeyCreator(ctx)`, leaking client UUIDs in `Sandbox.owner` and `Execution.userId` and locking non-admin developers out of sandboxes created with their own API keys (`ownerCheck` at `service.go:703-719`).

- **Attribution:** server (`lego/backend/internal/sandbox`)
- **Root cause:**
  - `sandbox.Service` already has `UserIDs core.UserIDLookup` (`lego/backend/internal/sandbox/service.go:253`) and embeds `*core.Base` (which carries `KeyCreators` / `s.KeyCreator(ctx)`).
  - Yet `sandboxFromOpenSandbox` (`service.go:835`) sets `Owner: raw.Metadata[metadataOwner]` verbatim, and neither `List`, `Get`, `Create`, nor `endedView` (`records.go:123,200+`) ever translates `Sandbox.Owner` through `core.PublicUserIDs(ctx, s.UserIDs, ...)`.
  - `ownerID(ctx)` (`service.go:504-514`) is a package-level helper that uses `id.Subject` verbatim without resolving an attributed API key's human creator via `s.KeyCreator(ctx)`. Thus:
    - `sandboxMetadata` (`service.go:518`) stamps an API key's Hydra client UUID into `bex.co/owner` (and `writeRecord` persists it in `sandbox_records.owner`).
    - `ownerCheck` (`service.go:703-719`) compares `owner == ownerID(ctx)`, so a non-admin developer whose API key created a sandbox fails `owner == caller` when reading, exec-ing, suspending, or stopping it from their human session (or a second API key) and gets `404 SANDBOX_NOT_FOUND` (and misses it in `list_sandboxes`).
  - `openExecution` (`exec.go:225`), `ConnectRun` (`connect.go:182`), and `ConnectFile` (`file_connect.go:191`) likewise record `idn.Subject` verbatim into `sandbox_executions.subject`, so an API-key execution misses `core.PublicUserIDs` in `executionViews` (`executions.go:303-312`) and leaks the Hydra client UUID in `execution.userId`.
- **Fix:**
  - Replace package-level `ownerID(ctx)` with a method `(s *Service) actorSubject(ctx context.Context) (string, error)` that resolves an attributed API key's human creator via `s.KeyCreator(ctx)` when `id.IsAPIKey()` (failing closed on `KeyCreators` errors), and applies the label-safe fallback for `bex.co/owner` metadata. Use it in `sandboxMetadata`, `ownerCheck`, `openExecution` (`exec.go:225`), `ConnectRun` (`connect.go:182`), and `ConnectFile` (`file_connect.go:191`). (In `ownerCheck`, also accept the raw caller key ID as a read-compat match for already-running sandboxes stamped before the fix.)
  - Translate `Sandbox.Owner` to the public `usr-…` ID via `core.PublicUserIDs(ctx, s.UserIDs, ...)` on `Create`, `Get`, `List`, and `endedSandboxes`/`endedSandbox` (matching `executionViews` at `executions.go:297-320`, and resolving any legacy stored API-key UUID through `s.KeyCreators` when available). Keep the internal subject in `bex.co/owner` and `sandbox_records.owner` for authorization matching, and project `usr-…` only on the wire `Sandbox` view.
  - Surface impact: aligns `Sandbox.owner` and `Execution.userId` across MCP (`spawn_sandbox`, `list_sandboxes`, `list_sandbox_executions`), REST (`/v1/sandboxes…`), GraphQL (`sandboxes`, `sandbox`, `sandboxExecutions`), and the dashboard sandbox drawer.
