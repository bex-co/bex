# 098 — Scoped `postgres_credentials: read` API keys execute arbitrary write SQL (`CREATE TABLE` / `DROP TABLE`) on private Postgres databases via `REST POST /v1/postgres/{id}/query` and GraphQL `executeDatabaseQuery` (`allowWrites: true`)

Why: `lego/backend/internal/api/key_permission_ops.go:157,1118` maps both `GQL Mutation.executeDatabaseQuery` and `REST POST /v1/postgres/{id}/query` solely to the read-only `{core.KeyPostgresCredentials}` action (`postgres_credentials: read`, "View connection strings and credentials"), and `postgres.Service.ExecuteQuery` (`lego/backend/internal/postgres/query.go:160-195`) never calls `s.RequireKeyGrant(ctx, core.KeyPostgresManage)` when `allowWrites` is `true` — letting a read-only API key with zero Postgres write grants run arbitrary DDL/DML transactions over `bex-api`'s private in-cluster CNPG connection even on a private (`public: false`, `ipAllowList: []`) database.

### Read-only `postgres_credentials: read` API keys bypass write-grant checks via `allowWrites: true` on REST and GraphQL SQL console endpoints

- **Expected / actual:**
  - **Expected:** Under `docs/ADR024-members.md` § "An API key carries a chosen set of permissions", `lego/backend/internal/core/keygrant.go:84-87,219`, and `lego/backend/internal/postgres/query.go:150-159`, `postgres_credentials: read` (`postgres.credentials.view`) grants read-only access ("View connection strings and credentials"). When `allowWrites: true`, `ExecuteQuery` already requires BOTH `RelCanCreate` and fresh `RelCanViewSensitive` (composing to `bex.write` + `bex.sensitive` on OAuth tokens); for a scoped API key it must likewise require `core.KeyPostgresManage` (`postgres: read_write`, "Create, update, and delete databases") in addition to `core.KeyPostgresCredentials`, returning `403 api_key_permission_denied` on both REST and GraphQL when the key lacks `postgres.manage`.
  - **Actual:**
    - Controls worked as expected: MCP `query_render_postgres` is strictly read-only (`bad request: read-only transaction`), and the `postgres_credentials: read` key was refused `update_postgres` (`Create, update, and delete databases`) and `create_postgres_user` (`Create and delete database credentials`) with `api_key_permission_denied`.
    - Yet using that exact same `postgres_credentials: read`-only key on a private (`public: false`, `ipAllowList: []`) database, `POST /v1/postgres/<dpg-id>/query` with `allowWrites: true` returned `200 OK` and created `qa_ro_key_write_probe` (verified by `SELECT * FROM qa_ro_key_write_probe` returning `[]` via MCP `query_render_postgres`), and GraphQL `executeDatabaseQuery(allowWrites: true)` returned `200 OK` and dropped the table.

- **Attribution:** server (`lego/backend/internal/postgres`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:157` (`"GQL Mutation.executeDatabaseQuery"`) and `:1118` (`"REST POST /v1/postgres/{id}/query"`) map both endpoints to `{core.KeyPostgresCredentials}` so read-only SQL console calls (`allowWrites: false`) remain callable with `postgres_credentials: read`.
  - However, `postgres.Service.ExecuteQuery` (`lego/backend/internal/postgres/query.go:160-195`) — the sole handler shared by REST (`postgres/rest.go:266`) and GraphQL (`postgres/graphql.go:838`) — enforces the `allowWrites` write-capability upgrade only via OpenFGA (`RelCanCreate` + `AuthorizeDatabaseFresh(ctx, RelCanViewSensitive, db)`, which also enforces OAuth `bex.write` + `bex.sensitive`), and never calls `s.RequireKeyGrant(ctx, core.KeyPostgresManage)` when `allowWrites` is `true`.
  - Compare the existing conditional key-grant checks in `lego/backend/internal/secrets/service.go:1001`, `lego/backend/internal/secrets/files.go:711`, and `lego/backend/internal/agentsessions/terminal.go:142`, which already use `s.RequireKeyGrant` / `s.KeyGrantAllows` when a single route's required action depends on a request parameter or runtime branch.
- **Fix:**
  - In `postgres.Service.ExecuteQuery` (`lego/backend/internal/postgres/query.go:160-195`), when `allowWrites` is `true`, call `if err := s.RequireKeyGrant(ctx, core.KeyPostgresManage); err != nil { return QueryResult{}, err }` before opening a read-write transaction (ahead of `fetchLiveDatabase` / `requireUnprotected`, matching `requireKeyGrant`'s refusal before existence/protection checks so a denied key receives `403 api_key_permission_denied` naming `"Create, update, and delete databases"` without probing database existence).
  - Keep `key_permission_ops.go:157,1118` at `{core.KeyPostgresCredentials}` so read-only queries (`allowWrites: false`) continue working with `postgres_credentials: read`, while `allowWrites: true` requires both `postgres.credentials.view` (gate) and `postgres.manage` (service).
  - Surface impact: protects both REST (`POST /v1/postgres/{id}/query`) and GraphQL (`Mutation.executeDatabaseQuery`) identically; MCP `query_render_postgres` calls `s.Query` (`readOnly: true`) and is unaffected. Dashboard SQL console runs on human Kratos sessions (`KeyGrant` returns `AllKeyGrant()` for non-API-key callers, `core/keygrant.go:606-608`) and is unaffected.
- **Blast radius:** `lego/backend/internal/postgres/query.go` and tests in `lego/backend/internal/postgres/query_test.go` + `lego/backend/internal/api/` key-grant tests. No other `REST POST`/`GQL Mutation` in `keyPermissionOps` maps a write flag to a read-only action (audited all 1,152 entries in `key_permission_ops.go`).
