# 156 — `postgres.normalizeQueryValue` omits `pgtype.Range`, `pgtype.Multirange`, and 6 geometric types, crashing queries with `500` (`"internal error"`) and corrupting `±infinity` range bounds to `-1`/`1` across MCP, REST, and GraphQL

Why: `lego/backend/internal/postgres/query_values.go:159-206` (`normalizeQueryValue`) implements `w4/m157`'s shared query-value policy for scalars and `[]any` arrays/records, but never handles `pgtype.Range[any]`, `pgtype.Multirange[pgtype.Range[any]]`, or the six `pgtype` geometric structs that lack `MarshalJSON` (`Box`, `Circle`, `Line`, `Lseg`, `Path`, `Polygon`). Valid read-only SQL queries returning temporal ranges/multiranges outside years `0–9999` or geometric values with `NaN`/`±Infinity` coordinates fail `json.Marshal` and return `500` / `"internal error"` across MCP `query_render_postgres` (a shared Render MCP tool), REST `POST /v1/postgres/{id}/query`, and GraphQL `executeDatabaseQuery`; meanwhile `±infinity` temporal range/multirange bounds silently serialize as raw `int8` numbers `-1`/`1` instead of `"-infinity"`/`"infinity"`.

- **Attribution:** server (`lego/backend/internal/postgres`)
- **Root cause:**
  - `queryRowValues` (`lego/backend/internal/postgres/query.go:351-369`) passes every cell decoded by `rows.Values()` through `normalizeQueryValue` (`lego/backend/internal/postgres/query_values.go:159-206`) before `collectRenderRows` (`query_render.go:48,91`, MCP) or `collectQueryRows` (`query.go:342`, REST & GraphQL) runs `json.Marshal` and maps any marshal error to `errQueryFailed` (`500` / `"internal error"`).
  - `normalizeQueryValue`'s type switch only handles `float64`, `float32`, `pgtype.Numeric`, `pgtype.InfinityModifier`, `[16]byte`, `time.Time`, and `[]any`:
    1. `pgtype.RangeCodec.DecodeValue` (`pgx/v5@v5.11.0/pgtype/range_codec.go:381-386`) returns `pgtype.Range[any]`, and `pgtype.MultirangeCodec.DecodeValue` (`pgx/v5@v5.11.0/pgtype/multirange.go:322-327`) returns `pgtype.Multirange[pgtype.Range[any]]` (a named slice type `[]pgtype.Range[any]`, which does not match `case []any:`). Because neither type is matched, `Lower` and `Upper` are never visited: `time.Time` bounds outside years `0–9999` crash `time.Time.MarshalJSON`, and `pgtype.InfinityModifier` bounds serialize as raw `int8` values `-1`/`1`.
    2. `pgtype.Box`, `pgtype.Circle`, `pgtype.Line`, `pgtype.Lseg`, `pgtype.Path`, and `pgtype.Polygon` (`pgx/v5@v5.11.0/pgtype/{box,circle,line,lseg,path,polygon}.go`) hold raw `float64` / `pgtype.Vec2` fields and implement no `MarshalJSON` (unlike `pgtype.Point` at `pgtype/point.go:100`). Any `NaN`/`±Infinity` coordinate fails `encoding/json.Marshal`, which `renderRowJSON` (`query_render.go:48-51`) and `collectQueryRows` (`query.go:342-345`) turn into `errQueryFailed`.
- **Fix:**
  - In `lego/backend/internal/postgres/query_values.go` (`normalizeQueryValue`, `:159-206`):
    1. Add `case pgtype.Range[any]:` to recursively normalize `v.Lower` and `v.Upper` when `v.Valid` (preserving `LowerType`, `UpperType`, `Valid`, and leaving `Unbounded`/`Empty` zero bounds untouched so `nil` stays `null`).
    2. Add `case pgtype.Multirange[pgtype.Range[any]]:` to normalize each element range in place and return the normalized slice (keeping `nil` as `nil`).
    3. Handle `pgtype.Box`, `pgtype.Circle`, `pgtype.Line`, `pgtype.Lseg`, `pgtype.Path`, and `pgtype.Polygon` so non-finite `float64` coordinates never fail `json.Marshal` — either by returning their canonical PostgreSQL text representation via their existing `Value()` (`driver.Valuer`) when any coordinate is non-finite (or consistently for all geometric values, matching `pgtype.Point.MarshalJSON` — check whether any existing test asserts the raw struct JSON shape of finite geometric types first!), or by converting non-finite `float64` fields to a JSON-safe representation carrying `"NaN"`/`"Infinity"`/`"-Infinity"`.
  - Also update the doc comment at `query_values.go:21` (which still cites `v5.10.0` while `lego/backend/go.mod:94` pins `v5.11.0`) to document range/multirange and geometric handling.
