# 082 — `delete_sandbox_group` (and REST/GraphQL twins) destroys Admin-only sandbox group credentials and protected-environment groups without `sandboxes.credentials` or Admin role

Why: `sandbox.Service.DeleteGroup` (`lego/backend/internal/sandbox/groups.go:476-552`) authorizes only `core.RelCanCreate` (Developer) and `core.KeySandboxesGroups` (`sandboxes: read_write`), yet `finishGroupDelete` unconditionally purges every Admin-only credential row and OpenBao secret in the group (`purgeGroupCredentials`) and deletes groups placed in protected environments without enforcing `core.RelCanManage` (Admin) or `core.KeySandboxesCredentials` (`sandbox_credentials: write`).

### `delete_sandbox_group` bypasses `sandboxes.credentials` (`sandbox_credentials: write`) and Admin / protected-environment gates

- **Severity:** blocker
- **Versions:** deployed pin `c767c1bbd9` (`9b91284a4a2e`, active on production during run; zero diff in `sandbox/groups.go` or the affected `key_permission_ops.go` entries vs `origin/main` `0177bc40ad`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`
- **Context:** 2026-11-26, endpoints `/mcp` (`https://api.bex.co/mcp`) and REST `/v1/sandbox-groups/{sandboxGroupId}`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), run-minted `sandboxes: read_write`-only API key (zero `sandbox_credentials`, revoked) + disposable groups `sbg-dc41h59m1rus738h05sg` and `sbg-dc41io9m1rus738h06k0` with Admin-only credentials `qa-cred-7f3a` / `qa-cred2-7f3a` (all deleted and verified `404`)

- **Expected / actual:**
  - **Expected:** Deleting a sandbox group that holds credentials must enforce the same authorization as `DeleteGroupCredential` (`sandbox/credentials.go:502-506`): Admin role (`core.RelCanManage`) and scoped API key permission `core.KeySandboxesCredentials` (`sandbox_credentials: write`), refusing with `403 forbidden` / `403 api_key_permission_denied` before `MarkSandboxGroupDeleting`. Deleting a sandbox group placed inside a protected environment must also enforce the protected-environment Admin gate (`PROTECTED_ENVIRONMENT_ADMIN_REQUIRED`), matching `CreateGroup` (`sandbox/groups.go:293,318`) and `SetGroupEnvironment` (`sandbox/groups.go:409-435`).
  - **Actual:**
    - Controls refused direct credential deletion on both MCP (`api_key_permission_denied: ... Create, update, and delete credentials`) and REST (`403 forbidden`, `required: ["sandboxes.credentials"]`).
    - The same `sandboxes: read_write`-only key succeeded on both MCP `delete_sandbox_group` (`200 OK {"deleted":true}`) and REST `DELETE /v1/sandbox-groups/{id}` (`204 No Content`), permanently removing the group, its credential rows, and its OpenBao secrets (`get_sandbox_group` and `get_sandbox_group_credential` both returned `SANDBOX_GROUP_NOT_FOUND` / `404`).

- **Attribution:** server (`lego/backend/internal/sandbox`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:139,556,824` maps `GQL Mutation.deleteSandboxGroup`, `MCP delete_sandbox_group`, and `REST DELETE /v1/sandbox-groups/{sandboxGroupId}` statically to `{core.KeySandboxesGroups}` alone (which is right for an empty, unprotected group).
  - `sandbox.Service.DeleteGroup` (`lego/backend/internal/sandbox/groups.go:476-498`) calls `s.writableGroup(ctx, id)` (`groups.go:440-452`, authorizing only `core.RelCanCreate` Developer) and jumps straight to `s.Groups.MarkSandboxGroupDeleting` (`groups.go:481`), then `finishGroupDelete` (`groups.go:504-537`) unconditionally runs `s.purgeGroupCredentials(ctx, g)` (`groups.go:530-552`) and deletes the group row (cascading all credentials) without checking:
    1. Whether the group has any credentials (`s.Credentials` non-empty) — which `DeleteGroupCredential` (`sandbox/credentials.go:502-506`) restricts to `core.RelCanManage` (Admin) + `core.KeySandboxesCredentials`.
    2. Whether `g.EnvironmentID` is a protected environment — unlike `CreateGroup` (`groups.go:293,318`) and `SetGroupEnvironment` (`groups.go:409-435`), which both enforce `PROTECTED_ENVIRONMENT_ADMIN_REQUIRED`.
- **Fix:**
  - In `sandbox.Service.DeleteGroup` (`lego/backend/internal/sandbox/groups.go:476-491`), fetch the existing group (`s.storedGroup(ctx, id)`) before `MarkSandboxGroupDeleting` and enforce both conditional gates:
    1. **Protected environment gate:** if `g.EnvironmentID != ""`, resolve the environment and enforce `RequirePlacement` / protected-environment Admin check (`PROTECTED_ENVIRONMENT_ADMIN_REQUIRED`) for non-Admin callers, matching `CreateGroup` and `SetGroupEnvironment`.
    2. **Credentials cascade gate:** if `s.Credentials != nil` and the group has any credentials (e.g. `ListSandboxGroupCredentials` or `ListSandboxGroupCredentialSecretRefs` is non-empty), require both `s.Authorize(ctx, core.RelCanManage)` (Admin) and `core.KeySandboxesCredentials` on scoped API keys (`403 api_key_permission_denied` naming `sandboxes.credentials`, matching `DeleteGroupCredential`).
    3. Re-check or keep the gate ahead of `MarkSandboxGroupDeleting` so an unauthorized delete never hides the group from reads or enqueues it for the sweeper.
  - Surface impact: fixes MCP `delete_sandbox_group`, REST `DELETE /v1/sandbox-groups/{sandboxGroupId}`, and GraphQL `deleteSandboxGroup` uniformly without adding extra permission requirements when deleting an unprotected group that has no credentials.
- **Blast radius:** `lego/backend/internal/sandbox/groups.go` and sandbox group tests in `lego/backend/internal/sandbox/` + `lego/backend/internal/api/`.
