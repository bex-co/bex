# 081 — MCP `update_service` (`apps.Service.ApplyServicePatch`) silently discards `notifyOnFail` when both `notifyOnFail` and `notificationsToSend` are passed in one request

Why: Unlike `autoDeploy` + `autoDeployTrigger` (rejected via `errAutoDeployBoth`, `lego/backend/internal/apps/rest.go:847`), `apps.Service.ApplyServicePatch` (`lego/backend/internal/apps/settings.go:540-563`) has no mutual-exclusion guard when a caller supplies both `notifyOnFail` and `notificationsToSend` — `NotifyOnFail` runs first (`:540-550`) and `NotificationsToSend` runs second (`:552-563`), silently overwriting `notifyOnFail` with `NotifyOnFailForNotificationsToSend(notificationsToSend)` (and on non-`dryRun`, executing two sequential writes where the second clobbers the first).

### Passing conflicting `notifyOnFail` and `notificationsToSend` to MCP `update_service` silently overwrites `notifyOnFail` instead of returning `400 bad request`

- **Severity:** minor
- **Versions:** deployed pin `c767c1bbd9` (`9b91284a4a2e`, active on production during run; zero diff in `lego/backend/internal/apps/settings.go` vs `origin/main` `7cde7889e5`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`
- **Context:** 2026-11-26, endpoint `/mcp` (`https://api.bex.co/mcp`), workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), disposable free image web service `srv-dc40jo6sfruc73ft2890` (`qa-20261126-8a7c75-web`, deleted and verified `404`), run-minted `All` API key (revoked)
- **Repro:**
  ```sh
  # 1. Conflicting notifyOnFail:"ignore" + notificationsToSend:"all":
  python3 scripts/qa-mcp.py --key-file <key.json> call update_service \
    '{"workspaceId":"tea-daif693dqjvc73e7as3g","serviceId":"<srv-id>","notifyOnFail":"ignore","notificationsToSend":"all","dryRun":true}'

  # 2. Opposite conflict notifyOnFail:"notify" + notificationsToSend:"none":
  python3 scripts/qa-mcp.py --key-file <key.json> call update_service \

  ```
- **Expected / actual:**
  - **Expected:** Just as `update_service` rejects sending both `autoDeploy` and `autoDeployTrigger` in the same request (`errAutoDeployBoth`, `apps/rest.go:847`), sending both legacy `notifyOnFail` and `notificationsToSend` (especially contradictory pairs like `notifyOnFail: "ignore"` + `notificationsToSend: "all"`) in the same `update_service` call should return `bad request` instructing the caller to pass one or the other (preferring `notificationsToSend`), rather than silently ignoring `notifyOnFail` and executing two conflicting sequential writes on non-`dryRun`.
  - **Actual:**
    - Call 1 (`notifyOnFail: "ignore"`, `notificationsToSend: "all"`, `dryRun: true`) succeeded (`200`) and returned `"notificationsToSend": "all", "notifyOnFail": "notify"` — silently discarding `notifyOnFail: "ignore"`.
    - Call 2 (`notifyOnFail: "notify"`, `notificationsToSend: "none"`, `dryRun: true`) succeeded (`200`) and returned `"notificationsToSend": "none", "notifyOnFail": "ignore"` — silently discarding `notifyOnFail: "notify"`.
- **Wire evidence:**
  - `POST /mcp` `update_service` (`notifyOnFail: "ignore"`, `notificationsToSend: "all"`, `dryRun: true`, `rndr-id: 125f08ac-771f-d780`) → `200 OK`, `structuredContent.notificationsToSend: "all"`, `structuredContent.notifyOnFail: "notify"`.
  - `POST /mcp` `update_service` (`notifyOnFail: "notify"`, `notificationsToSend: "none"`, `dryRun: true`, `rndr-id: f1addd62-280d-8d1e`) → `200 OK`, `structuredContent.notificationsToSend: "none"`, `structuredContent.notifyOnFail: "ignore"`.
- **Attribution:** server (`lego/backend/internal/apps`)
- **Root cause:**
  - `servicePatchTable` in `lego/backend/internal/apps/settings.go:540-563` defines two independent rows: `NotifyOnFail` (`:540-550`, setting `probe.Spec.NotifyOnFail = normalized; probe.Spec.NotificationsToSend = ""` and applying `SetNotifyOnFail`) followed immediately by `NotificationsToSend` (`:552-563`, setting `probe.Spec.NotificationsToSend = normalized; probe.Spec.NotifyOnFail = appv1alpha1.NotifyOnFailForNotificationsToSend(normalized)` and applying `SetNotificationsToSend`).
  - Neither `ApplyServicePatch` nor `apps/mcp.go` (`update_service` handler) rejects a patch where both `p.NotifyOnFail != nil` and `p.NotificationsToSend != nil`, so `NotificationsToSend` always clobbers `NotifyOnFail` silently (and triggers a redundant intermediate `SetNotifyOnFail` write on non-`dryRun`).
- **Fix:**
  - In `lego/backend/internal/apps/settings.go` (`probeServicePatch` / `ApplyServicePatch`), reject `p.NotifyOnFail != nil && p.NotificationsToSend != nil` with `core.ErrBadRequest` (e.g. `"you can't set both notifyOnFail and notificationsToSend in the same request; use notificationsToSend"`), mirroring `errAutoDeployBoth` (`apps/rest.go:847`).
  - Update the `notifyOnFail` / `notificationsToSend` schema descriptions in `lego/backend/internal/apps/mcp.go:136-137` to note they are mutually exclusive.
- **Blast radius:** `lego/backend/internal/apps/{settings,mcp}.go` and unit tests in `lego/backend/internal/apps/`. REST `PATCH /v1/services/{id}` only accepts `notifyOnFail` (not `notificationsToSend`), so only MCP `update_service` (and direct `ServicePatch` callers) can supply both simultaneously.
