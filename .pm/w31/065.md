# 065 — Blueprint apply operations (`deploy`, `sync_blueprint`, `approve_blueprint`, and REST/GraphQL twins) omit `buildsources.manage` and `buildsources.env.set`, letting scoped API keys create build sources and write build-time secrets

Why: `lego/backend/internal/api/key_permission_ops.go:36-37` explicitly requires every Blueprint apply operation (`MCP deploy`, `MCP sync_blueprint`, `MCP approve_blueprint`, `REST POST /v1/blueprints`, `POST /v1/blueprints/deploy`, `POST /v1/blueprints/{id}/approve`, `POST /v1/blueprints/{id}/sync`, and `GQL Mutation.createBlueprint`, `syncBlueprint`, `approveBlueprint`) to hold the write action of every resource kind a Blueprint can create or change, yet lines `67,89,280,495,559,751,1067-1068,1072-1073` omit `core.KeyBuildSourcesManage` and `core.KeyBuildSourcesEnvSet`, and `applyStackBuildSources` (`lego/backend/internal/apps/blueprint_build_sources.go:306-407`) performs no `RequireKeyGrant` check — letting a scoped API key with zero `build_sources` or `build_source_env` permissions create/update build sources and seed build-time environment variables via Blueprint apply.

- **Attribution:** server (`lego/backend/internal/api` and `lego/backend/internal/apps`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:67,89,280,495,559,751,1067-1068,1072-1073` maps the 10 Blueprint apply operations (`GQL Mutation.approveBlueprint`, `GQL Mutation.createBlueprint`, `GQL Mutation.syncBlueprint`, `MCP approve_blueprint`, `MCP deploy`, `MCP sync_blueprint`, `REST POST /v1/blueprints`, `REST POST /v1/blueprints/deploy`, `REST POST /v1/blueprints/{id}/approve`, `REST POST /v1/blueprints/{id}/sync`) to `{KeyBlueprintsManage, KeyServicesManage, KeyServicesEnvSet, KeyPostgresManage, KeyKeyValueManage, KeyEnvGroupsManage, KeyEnvGroupsValuesSet, KeyProjectsManage}` — omitting `core.KeyBuildSourcesManage` and `core.KeyBuildSourcesEnvSet` added for Build Sources (`w3/m270`).
  - `apps.Service.applyStackBuildSources` (`lego/backend/internal/apps/blueprint_build_sources.go:306-407`) calls `createBuildSourceCarrier`, `updateStackService`, `EnvGroups.LinkEnvGroup`, and `seedBuildSourceEnv` without checking `s.RequireKeyGrant(ctx, core.KeyBuildSourcesManage)` or `s.RequireKeyGrant(ctx, core.KeyBuildSourcesEnvSet)`.
- **Fix:**
  - Add `core.KeyBuildSourcesManage` and `core.KeyBuildSourcesEnvSet` to the Blueprint apply entries in `lego/backend/internal/api/key_permission_ops.go:67,89,280,495,559,751,1067-1068,1072-1073` (matching the file's documented policy at `:36-37`, `"applying a Blueprint needs the write of every resource kind a Blueprint can create or change"`) — OR, to avoid breaking scoped keys that apply Blueprints without any `buildSources`, enforce `s.RequireKeyGrant` dynamically at the top of `applyStackBuildSources` / `validateBlueprintBuildSources` (`lego/backend/internal/apps/blueprint_build_sources.go:306-315`) before any write: require `core.KeyBuildSourcesManage` whenever `len(st.buildSources) > 0 || st.linksBuildSources()`, and `core.KeyBuildSourcesEnvSet` whenever any declared build source seeds env vars (`len(b.svc.seedLiterals) > 0 || len(b.svc.seedGenerates) > 0`). (Applying both or choosing the service-level dynamic check + matching tests cleanly closes all 10 Blueprint apply paths across MCP, REST, and GraphQL.)
  - Surface impact: protects MCP (`deploy`, `sync_blueprint`, `approve_blueprint`), REST (`POST /v1/blueprints`, `/deploy`, `/{id}/sync`, `/{id}/approve`), and GraphQL (`createBlueprint`, `syncBlueprint`, `approveBlueprint`) uniformly.
