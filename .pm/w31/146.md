# 146 — Scoped `services: read_write` API keys bypass `envgroups.manage` and `envgroups.values.view` via GraphQL `createService(envGroups: [...])` (`WithInitialEnvGroupIDs` / `CheckInitialEnvGroupIDs`)

Why: `31da91be6f` (`w4/731`) added `envGroups: [String!]` to GraphQL `Mutation.createService` (`lego/backend/internal/apps/service.go:2816-2823,3515-3517`), delegating to `envgroups.Service.{CheckInitialEnvGroupIDs,WithInitialEnvGroupIDs}` (`lego/backend/internal/envgroups/initial_links.go:44-54,76-93,104-128,213-227`), while `keyPermissionOps` (`lego/backend/internal/api/key_permission_ops.go:114`) maps `GQL Mutation.createService` solely to `{core.KeyServicesManage}` and neither `apps.Service.Create` nor `envgroups` checks `core.KeyEnvGroupsManage` or `core.KeyEnvGroupsValues` — letting a scoped API key with only `services: read_write` (zero `env_groups` or `env_group_values` permissions) link arbitrary workspace environment groups into new attacker-controlled services and materialize every secret value on first deploy.

- **Expected / actual:**
  - **Expected:** Consistent with `lego/backend/internal/api/key_permission_ops.go:35` ("an operation that changes two areas needs both") and `envgroups/service.go:1157-1164` ("A link materializes every group value inside caller-controlled workload code, so it is a sensitive read even though the API response stays masked"), `createService` with a non-empty `envGroups` list must require both `core.KeyEnvGroupsManage` and `core.KeyEnvGroupsValues` on scoped API keys (matching standalone `linkEnvGroup` / `link_env_group` post-`w31/083`) and refuse keys lacking either grant with `403 api_key_permission_denied` **before** reading the group row or running `dryRun` — never creating a service or revealing whether an `evg-…` ID exists in the workspace.
  - **Actual:**
    - All four controls (`MCP list_env_groups`, `MCP get_env_group_var`, `MCP link_env_group`, `GQL linkEnvGroup`) returned `api_key_permission_denied`.
    - Yet using that exact same `services: read_write`-only key, `GQL createService(..., envGroups: ["evg-dc4invi3u9qc73carjfg"], dryRun: true)` returned `200 OK`, and live `GQL createService(..., envGroups: ["evg-dc4invi3u9qc73carjfg"])` returned `200 OK` and created `srv-dc4io0a3u9qc73carjjg`.

- **Attribution:** server (`lego/backend/internal/apps`, `lego/backend/internal/envgroups`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:114` maps `"GQL Mutation.createService"` solely to `{core.KeyServicesManage}`.
  - `apps.Service.Create` (`lego/backend/internal/apps/service.go:2816-2823` for `dryRun`/plan and `:3515-3517` for live writes, added in `31da91be6f` / `w4/731`) passes `req.EnvGroupIDs` to `s.EnvGroups.CheckInitialEnvGroupIDs` / `s.EnvGroups.WithInitialEnvGroupIDs` without checking the caller's scoped API key grant for `core.KeyEnvGroupsManage` or `core.KeyEnvGroupsValues`.
  - Inside `lego/backend/internal/envgroups/initial_links.go:104-128,213-227`, `resolveInitialGroups` → `initialGroupByID` (`:76-93`) and `validateInitialGroup` (`:213-227`) check only OpenFGA workspace relations (`RelCanCreate` and `authorizeGroupSensitiveFresh` → `RelCanViewSensitive` at `envgroups/service.go:1935-1937`), which pass for any API key minted by a Developer or Admin regardless of its scoped `core.KeyGrant`.
  - Secondary ordering defect in `initialGroupByID` (`initial_links.go:76-93`): it calls `s.readGroup(ctx, gid)` (`:81`) and returns `400 bad request: env group "<gid>" does not exist` **before** checking `s.AuthorizeLabeled` (`:89`) or `s.authorizeGroupSensitiveFresh` (`:217`), turning `createService(envGroups: [...], dryRun: true)` into an env-group ID existence oracle (`400` vs `403`) even for a `bex.write`-only OAuth token lacking `bex.sensitive`.
- **Fix:**
  - In `envgroups.Service.resolveInitialGroups` (`lego/backend/internal/envgroups/initial_links.go:104-110`), before resolving or reading any group row:
    1. For callers using an attributed scoped API key, require `{core.KeyEnvGroupsManage, core.KeyEnvGroupsValues}` (via `core.Base.KeyGrantAllows` / `RequireKeyActions`, matching `w31/061` and `w31/083`) and return `core.NewKeyPermissionDeniedError` before touching `s.readGroup`.
    2. Check workspace-level `s.AuthorizeFreshOn(ctx, core.RelCanViewSensitive, core.WorkspaceObject(a.Labels[core.LabelTenant]))` up front before the `for _, ref := range refs` loop (`:113`), so a `bex.write`-only OAuth token or non-Developer role receives `403 forbidden` uniformly regardless of whether a supplied `evg-…` ID exists in the workspace.
  - Also ensure `apps.Service.Create` (`apps/service.go:2816`) enforces the same `KeyEnvGroupsManage` + `KeyEnvGroupsValues` check when `len(req.EnvGroupIDs) > 0` (alongside `w31/061`'s `KeyServicesEnvSet`/`KeyBuildSourcesManage`/`KeyProjectsMove` checks).
  - Surface impact: closes the GraphQL `createService(envGroups: [...])` bypass (and protects any future REST/MCP caller of `CreateRequest.EnvGroupIDs` as well as Blueprint initial-group links through the shared `resolveInitialGroups` path; verify Blueprint apply tests keep passing when `WithInitialEnvGroups` runs under Blueprint keys once `w31/083` updates Blueprint apply grants if needed).
