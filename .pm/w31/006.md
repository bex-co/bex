# 006 — MCP `get_metrics` / `get_datastore_metrics` (and GraphQL `metrics`) bypass `minResolutionSeconds = 30`, overflow `time.Duration`, and reject float `resolution`

Why: `w8/351` aligned REST `parseTimeWindow` with Render's `number` (`minimum: 30`) `resolutionSeconds` contract and `maxResolutionSeconds = 1e9` overflow clamp, but MCP `get_metrics` / `get_datastore_metrics` and GraphQL `windowFromInput` kept unvalidated integer `* time.Second` conversions — rejecting Render-valid floats like `60.5`, allowing 1-second Prometheus queries (~316 KB / 3,600 samples per hour), and silently turning `<= 0` and overflowing values (`1e10`) into 60 s.

### MCP `get_metrics` / `get_datastore_metrics` and GraphQL `metrics` accept `< 30` / negative / overflowing `resolution`, while MCP rejects float `resolution`

- **Expected / actual:**
  - **Expected:** Per Render's pinned MCP server (`lego/backend/internal/api/openapi/render-mcp-tools.json`: `get_metrics.argTypes.resolution` is `{"type": "number"}`), Render's OpenAPI spec (`resolutionSeconds`: `type: number, minimum: 30`), and bex's own REST `parseTimeWindow` (`lego/backend/internal/metrics/rest.go:469-490`, `w8/351`), all three surfaces (REST, MCP `get_metrics`/`get_datastore_metrics`, GraphQL `metrics`) must enforce the same resolution contract: accept finite JSON numbers `>= 30` (rounded to whole seconds, clamped at `maxResolutionSeconds = 1e9` so `time.Duration` cannot overflow) and reject values `< 30` (including `0`, negative numbers, `NaN`, and `±Inf`) with `core.ErrBadRequest` (`resolution must be a number of at least 30`).
  - **Actual:**
    - MCP `get_metrics` with `resolution: 60.5` fails SDK schema validation (`the value has type "number", want one of "null, integer"`), whereas REST `resolutionSeconds=60.5` returns `200 OK`.
    - MCP `get_metrics` and `get_datastore_metrics` with `resolution: 1` both succeed (`isError: false`), querying Prometheus at 1-second step and returning ~316 KB / ~280 KB (3,600 samples/hour for a single metric), whereas REST `resolutionSeconds=5` returns `400 bad_request` (`invalid query parameter "resolutionSeconds"`).
    - MCP `get_metrics` with `resolution: -1`, `0`, or `10000000000` (which overflows `int64` nanoseconds to a negative `time.Duration`) silently succeeds at 60 s default; `get_datastore_metrics` with `resolution: -1` or `10000000000` does the same.
    - GraphQL `metrics` with `resolution: 5` succeeds with 5-second step timestamps, and `resolution: -1` silently succeeds at 60 s default.

- **Attribution:** server (`lego/backend/internal/metrics`)
- **Root cause:**
  - `lego/backend/internal/metrics/rest.go:469-490` validates `resolutionSeconds` (`float64`, `>= minResolutionSeconds` = 30, `!math.IsInf`, clamped to `maxResolutionSeconds = 1e9`), but that logic lives only inside the REST adapter (`parseTimeWindow`).
  - `lego/backend/internal/metrics/mcp.go:50-51,118-120,284` (`getMetricsArgs`) and `:390-391,398-400,426` (`getDatastoreMetricsArgs`) type `Resolution`/`ResolutionSeconds` as `*int64` (emitting JSON Schema `integer` instead of Render's `number`), skip the `>= 30` check entirely, and compute `time.Duration(secs) * time.Second` directly — allowing `< 30` through to Prometheus, letting `<= 0` silently fall back to `defaultResolution` (`service.go:207`), and overflowing `int64` nanoseconds past ~`9.22e9` s.
  - `lego/backend/internal/metrics/graphql.go:749-751` (`windowFromInput`) similarly runs `resolution = time.Duration(n) * time.Second` with no `minResolutionSeconds` check or overflow guard.
- **Fix:**
  - Extract a shared `parseResolutionSeconds(param string, v float64) (time.Duration, error)` helper in `lego/backend/internal/metrics/` (used by REST `parseTimeWindow`, MCP `get_metrics` / `get_datastore_metrics`, and GraphQL `windowFromInput`) that enforces `v >= minResolutionSeconds` (30), rejects `NaN`/`±Inf`, rounds to whole seconds, and clamps at `maxResolutionSeconds = 1e9` before converting to `time.Duration`.
  - Change `Resolution` and `ResolutionSeconds` on `getMetricsArgs` (`mcp.go:50-51`) and `getDatastoreMetricsArgs` (`mcp.go:390-391`) from `*int64` to `*float64` so MCP JSON Schema emits `"type": ["null", "number"]`, matching Render's pinned `render-mcp-tools.json` (`"type": "number"`) and bex REST; validate whenever the selected pointer is non-nil (so an explicit `0` or `-1` fails with `bad request` instead of silently defaulting to 60 s).
  - In `graphql.go:749-751` (`windowFromInput`), validate any explicitly provided `resolution` via `parseResolutionSeconds("resolution", float64(n))` (confirming first that no dashboard preset passes `< 30`; existing dashboard presets start at 30 s per `w4/m175`).
  - Note: REST is unchanged (`60.5` already works, `< 30` already 400s); MCP and GraphQL now enforce the same resolution bounds as REST.
