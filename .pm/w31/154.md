# 154 — `metrics.Service.Metrics` silently ignores `percentage: true` on non-CPU/memory service metrics, diverging from REST (`400`), `DatastoreMetrics` (`400`), and `activeConnections` (`400`)

Why: `lego/backend/internal/metrics/service.go:593-690` (`metricsInWindow`) never validates `q.Percentage` against `MetricCPU`/`MetricMemory`, unlike `DatastoreMetrics` (`lego/backend/internal/metrics/datastore.go:465-468`), `activeConnections` (`lego/backend/internal/metrics/rest.go:158-160`), and REST's OpenAPI schema (which rejects `?percentage=true` on non-CPU/memory endpoints with `400`). As a result, MCP `get_metrics` and GraphQL `metrics` on any `srv-` service accept `percentage: true` for `cpu_limit`, `memory_limit`, `http_request_count`/`http_requests`, `http_latency`, `bandwidth_usage`/`bandwidth`, `instance_count`, `cpu_target`, and `memory_target`, and silently return raw absolute units (`cpu`, `count`, `bytes`, `seconds`) with `200 OK`.

- **Attribution:** server (`lego/backend/internal/metrics`)
- **Root cause:**
  - `lego/backend/internal/metrics/service.go:593-690` (`metricsInWindow`) enforces metric-specific option guards for `statusCode` (`:615`), `host`/`path` (`:623`), `cpuAggregation` (`:637`), `aggregateBy=host` (`:640`), and `quantile` (`:643`), and reads `q.Percentage` only inside `resourceMetric` (`:895, 930, 1088, 1095`), which runs solely for `MetricCPU` and `MetricMemory`. No guard rejects `q.Percentage` when `q.Metric != MetricCPU && q.Metric != MetricMemory`.
  - REST only rejects `?percentage=true` on non-CPU/memory endpoints because the REST OpenAPI validator (`internal/api/openapi_validate.go`) checks query params per path (`rest.go:551` parses `percentage` for every path in `metricPaths`). GraphQL `MetricsQueryInput` (`graphql.go:131`) and MCP `get_metrics` (`mcp.go:56, 283`) accept `percentage` on the shared query object and forward `q.Percentage` directly to `Service.Metrics`.
- **Fix:**
  - Add the exact same guard already used in `datastore.go:466` and `rest.go:158` to `metricsInWindow` in `lego/backend/internal/metrics/service.go` (alongside the `statusCode` / `host` / `cpuAggregation` checks, before any `AppNotBefore` / `withinRetention` short-circuit):
    ```go
    if q.Percentage && q.Metric != MetricCPU && q.Metric != MetricMemory {
        return nil, fmt.Errorf("%w: percentage applies only to cpu and memory metrics", core.ErrBadRequest)
    }
    ```
  - Check existing dashboard callers (`dashboard/src/`) and `lego/backend/internal/metrics/*_test.go` (including multi-metric MCP `get_metrics` calls) to confirm no legitimate caller sends `percentage: true` on non-CPU/memory metrics. (Note: `DatastoreMetrics` already rejects mixed multi-metric calls like `["cpu_usage", "cpu_limit"]` with `percentage: true`, and `render_contract_test.go:1004` asserts `active_connections` rejects `percentage: true`; if mixed `get_metrics` calls such as `["cpu_usage", "http_request_count"]` with `percentage: true` should instead scope `Percentage` to `cpu`/`memory` only when `len(in.MetricTypes) > 1`, decide explicitly and keep services and datastores consistent.)
