# 062 — `keyPermissionOps` maps `import_sandbox_image` and `delete_sandbox_image` to `KeySandboxesManage` on MCP and GraphQL instead of REST's `KeySandboxesGroups`

Why: `lego/backend/internal/api/key_permission_ops.go:140,156,553,625` maps `MCP import_sandbox_image`, `MCP delete_sandbox_image`, `GQL Mutation.importSandboxImage`, and `GQL Mutation.deleteSandboxImage` to `{core.KeySandboxesManage}` (`"Create and terminate sandboxes"`), while lines `820,1119` map the identical REST routes (`POST /v1/sandbox-groups/{sandboxGroupId}/builds`, `DELETE /v1/sandbox-groups/{sandboxGroupId}/builds/{buildId}`) to `{core.KeySandboxesGroups}` (`"Create, update, and delete sandbox groups"`), causing MCP/GraphQL and REST to disagree on the required permission reported in `api_key_permission_denied` errors.

### MCP and GraphQL sandbox-image mutations require `sandboxes.manage` while their identical REST routes require `sandboxes.groups`

- **Severity:** minor
- **Versions:** deployed pin `043827a8e8` (`2bd6e1f415d3`, active on production during run; zero diff in `lego/backend/internal/api/key_permission_ops.go` vs `origin/main` `f283757db2`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`
- **Context:** 2026-11-26, endpoints `/mcp` (`https://api.bex.co/mcp`) and REST `/v1/sandbox-groups/…/builds/…`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), run-minted read-only scoped API key without `sandboxes: read_write` (revoked)

  # With any scoped API key lacking sandboxes: read_write:
  python3 scripts/qa-mcp.py --key-file <ro-key.json> call delete_sandbox_image \

    '/v1/sandbox-groups/sbg-00000000000000000000/builds/sbb-00000000000000000000'

- **Expected / actual:**
  - **Expected:** Under ADR006 (same core verb ⇒ same authorization contract across REST, GraphQL, and MCP) and `lego/backend/internal/sandbox/ratelimit.go:200-201` (which already classifies `MCP import_sandbox_image` and `MCP delete_sandbox_image` as `RateClassGroupWrite`), all three surfaces for sandbox-group image import/delete should require the same catalog action (`core.KeySandboxesGroups`, `"Create, update, and delete sandbox groups"`).
  - **Actual:**
    - `MCP delete_sandbox_image` refused with `"api_key_permission_denied: this API key is not granted the permission this request needs: Create and terminate sandboxes"` (`sandboxes.manage`).
    - `REST DELETE /v1/sandbox-groups/…/builds/…` refused with `403` `"this API key is not granted the permission this request needs: Create, update, and delete sandbox groups"` (`params.required: ["sandboxes.groups"]`).
- **Wire evidence:**

- **Attribution:** server (`lego/backend/internal/api`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:140,156,553,625` maps `"GQL Mutation.deleteSandboxImage"`, `"GQL Mutation.importSandboxImage"`, `"MCP delete_sandbox_image"`, and `"MCP import_sandbox_image"` to `{core.KeySandboxesManage}`, whereas lines `820,1119` map `"REST DELETE /v1/sandbox-groups/{sandboxGroupId}/builds/{buildId}"` and `"REST POST /v1/sandbox-groups/{sandboxGroupId}/builds"` to `{core.KeySandboxesGroups}`.
  - Today `sandboxes: read_write` bundles both actions (`KeySandboxesManage` and `KeySandboxesGroups`), so access control does not diverge yet, but the reported `required` action and error text disagree across surfaces and would diverge in behavior if those two actions are ever offered separately.
