# 185 — MCP `upload_agent_attachment` JSON Schema (`contentBase64`) advertises `"at most 4 MiB decoded"`, contradicting the enforced 1 MiB cap (`maxMCPUploadBytes`), and empty uploads leak REST `"Content-Length"` jargon

Why: When `w9/m171/t007` lowered `maxMCPUploadBytes` from 4 MiB to 1 MiB (`lego/backend/internal/agentsessions/limits.go:41`) so base64 payloads fit under `/mcp`'s 2 MiB `BEX_MAX_BODY_BYTES`, it updated the tool description (`mcp.go:487`) to read dynamically from `maxMCPUploadBytes>>20` (`1 MiB`), but left the struct tag on `uploadAttachmentArgs.ContentBase64` (`mcp.go:219`) hardcoded as `"the file's bytes, standard base64, at most 4 MiB decoded"` (pinned into `testdata/mcp_tools.golden.json:16970`). An MCP client reading `inputSchema.properties.contentBase64.description` sends 1–4 MiB files that always fail with `AGENT_ATTACHMENT_TOO_LARGE` (or HTTP `413` above ~1.5 MiB on `/mcp/cloud-agents`), and an empty `contentBase64: ""` upload returns REST HTTP jargon (`"an attachment upload needs a non-empty body with Content-Length"`) from `attachments.go:158`.
