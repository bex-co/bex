# 044 — `members.Service.AcceptInvite` and `AcceptOrganizationInvite` do not refuse API keys, letting a single-workspace API key seat its own client UUID as a `kind='user'` member in another workspace or organization

Why: Unlike `LeaveWorkspace` (`lego/backend/internal/members/service.go:1344`, which refuses machine callers with `MEMBER_IS_MACHINE`) and `Invite` (`:682`, which calls `AuthorizeMintClass`), neither `AcceptInvite` (`:889-921`) nor `AcceptOrganizationInvite` (`lego/backend/internal/members/organizations.go:394-428`) rejects API-key / machine callers, so an `All`-permissions API key passes authorization and reaches `AcceptInviteByToken` / `AcceptOrganizationInviteByToken` with `id.Subject` (the key's Hydra client UUID), which inserts `(tenant_id, subject=<api-key-uuid>, role, kind='user')` into `tenant_members` and writes an OpenFGA role tuple for the key in an arbitrary invited workspace or organization.

### API keys bypass machine-caller guards on `accept_workspace_invite` and `accept_organization_invite` (MCP, REST, GraphQL)

- **Severity:** blocker
- **Versions:** deployed pin `8b9d780f45` (`cdaa0a248615`, active on production during run; zero diff in `lego/backend/internal/members/{service,organizations}.go` and `lego/backend/internal/store/{members,organizations}.go` vs `HEAD` `4d6c50f9ad`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`
- **Context:** 2026-11-25, endpoints `/mcp` (`https://api.bex.co/mcp`), REST `POST /v1/invites/accept`, and GraphQL `acceptWorkspaceInvite` / `acceptOrganizationInvite`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), run-minted all-permissions API key (revoked after run)

- **Expected / actual:**
  - **Expected:** An API key is bound to one workspace (`docs/ADR024-members.md`, `w6/m18`) and cannot hold human workspace or organization memberships. Calling `AcceptInvite` or `AcceptOrganizationInvite` (and `PreviewInvite` / `PreviewOrganizationInvite` if human-only, or resolving creator carefully) with a machine/API-key credential must be refused before any token lookup or redemption (e.g. `403 FORBIDDEN` via `AuthorizeMintClass`, matching `Invite` and `key_permission_ops.go`'s `{core.KeyNoGrant}` mapping, or `MEMBER_IS_MACHINE` matching `LeaveWorkspace`).
  - **Actual:** All five calls (`MCP accept_workspace_invite`, `MCP accept_organization_invite`, `REST POST /v1/invites/accept`, `GraphQL acceptWorkspaceInvite`, `GraphQL acceptOrganizationInvite`) passed `s.Authorize(ctx, core.RelCanView)` with the API key and executed `AcceptInviteByToken` / `AcceptOrganizationInviteByToken`, failing only with `INVITE_INVALID` because the probe token was synthetic. With a real pending invite token:
    1. `redeemInvite` (`store/members.go:546-553`) executes `INSERT INTO tenant_members (tenant_id, subject, role) VALUES ($1, $2, $3)` (default `kind = 'user'`) with `subject = <api-key-client-uuid>`, seating the machine client as a human member in a second workspace, consuming a plan seat, and writing an OpenFGA `user:<key-uuid>` role tuple (plus joining that workspace's org in `organization_members`).
    2. `AcceptOrganizationInviteByToken` (`store/organizations.go:800-801`) inserts `(organization_id, <api-key-client-uuid>, role)` into `organization_members` and writes an OpenFGA `organization:<id>` role tuple for the API key.
    3. Meanwhile, control `MCP leave_workspace` refused the same API key with `MEMBER_IS_MACHINE: that is an API key's workspace binding, not a member; manage it on the API keys page`.

- **Attribution:** server (`lego/backend/internal/members`)
- **Root cause:**
  - `members.Service.AcceptInvite` (`lego/backend/internal/members/service.go:889-921`) and `members.Service.AcceptOrganizationInvite` (`lego/backend/internal/members/organizations.go:394-428`) check only `s.Authorize(ctx, core.RelCanView)` and `core.IdentityFrom(ctx)` — never `AuthorizeMintClass(ctx)` or `id.IsAPIKey()` / `!id.Human`.
  - `PreviewInvite` (`service.go:834-879`) and `PreviewOrganizationInvite` (`organizations.go:349-386`) likewise pass `id.Subject` directly into `GetTenantMember` / `GetOrganizationMember` without rejecting API keys, so an API key's `alreadyMember` check always evaluates against its client UUID instead of a human member.
  - `lego/backend/internal/api/key_permission_ops.go:490-491,704-705` maps all four invite-redemption/preview operations to `{core.KeyNoGrant}`, which blocks *scoped* API keys but still admits every `All`-permissions API key.
- **Fix:**
  - Refuse machine / API-key callers (e.g. `if err := s.AuthorizeMintClass(ctx); err != nil` or `if id.IsAPIKey() || !id.Human`) at the top of `AcceptInvite` (`lego/backend/internal/members/service.go:889`) and `AcceptOrganizationInvite` (`lego/backend/internal/members/organizations.go:394`) — before touching `s.Store` — so no API key or third-party client can ever redeem an invite into a workspace or organization (check `PreviewInvite` and `PreviewOrganizationInvite` for the same human-only boundary so preview and accept agree).
  - Verify `scope_matrix_ops.go` classification if `AuthorizeMintClass` is used (aligning with `OpClassMint` or explicit machine-caller refusal consistent with `LeaveWorkspace`).
  - Surface impact: protects MCP (`accept_workspace_invite`, `accept_organization_invite`, and previews), REST (`POST /v1/invites/accept`, `GET /v1/invites/preview`), and GraphQL (`acceptWorkspaceInvite`, `acceptOrganizationInvite`, `previewWorkspaceInvite`, `previewOrganizationInvite`) through the single `members.Service` seam.
- **Blast radius:** `lego/backend/internal/members/{service,organizations}.go` and tests; human session and human OAuth callers redeeming invites in the dashboard/CLI/MCP are unaffected (if `AuthorizeMintClass` is used, verify whether human OAuth MCP clients are meant to redeem invites or only direct sessions/first-party CLI — refusing `id.IsAPIKey() || !id.Human` preserves consented human OAuth while blocking every API key/machine credential; choose explicitly and document in test).

    2. A human caller still redeems both workspace and organization invites cleanly.
