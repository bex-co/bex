# 007 — HTTP latency `quantile=0` silently returns p95 on REST/MCP/GraphQL, and multi-quantile `quantiles` silently drops `0` and `1`

Why: `lokisource.go:499` (`lokiQuantile`) rewrites `q <= 0` to `0.95`, `metrics/mcp.go:281` never sets `QuantileSet` for an explicit `httpLatencyQuantile: 0`, and `service.go:808` (`normalizeQuantiles`) filters `q <= 0 || q >= 1` — so callers requesting minimum latency (`quantile=0`) silently get p95 (60× higher in live repro) and callers requesting `[0, 0.5, 1]` silently lose both `0` and `1`.

- **Expected / actual:**

  - **Actual:** On minute `2026-11-25T08:59:00Z` (containing two ~4.7 ms and two ~304 ms requests):
    - `quantile=0.01` → `0.00488905603` s; `quantile=0.5` → `0.1545517245` s; `quantile=0.95` → `0.30393627095` s; `quantile=1` → `0.303991403` s.

- **Attribution:** server (`lego/backend/internal/metrics`)
- **Root cause:** Three layered bugs in `lego/backend/internal/metrics/`:
  1. **`lokisource.go:498-503` (`lokiQuantile`)**: `if q <= 0 { return defaultQuantile }` unconditionally rewrites `0` back to `0.95` inside the Loki LogQL builder (`lokisource.go:157`). `RequestMetricsRequest` (`service.go:282`) carries `Quantile float64` without `QuantileSet`, so even when `MetricQuery.normalized()` preserves `0` via `QuantileSet: true` (`service.go:210`), production Loki silently turns `0` back into `0.95` on REST, GraphQL, and MCP alike.
  2. **`mcp.go:280-286`**: `get_metrics` sets `Quantile: in.quantile()` without setting `QuantileSet: in.HTTPLatencyQuantile != nil || in.Quantile != nil`, so `MetricQuery.normalized()` (`service.go:210`) overwrites an explicit `httpLatencyQuantile: 0` or `quantile: 0` with `0.95` before any backend source is even called.
  3. **`service.go:804-816` (`normalizeQuantiles`) and `:786-790`**: `normalizeQuantiles` drops `q <= 0 || q >= 1` instead of `q < 0 || q > 1`, silently discarding valid boundary quantiles `0` and `1` from any multi-quantile request (`REST ?quantile=0&quantile=0.5&quantile=1`, MCP `quantiles: [0, 0.5, 1]`, GraphQL `parameters: [{quantile: 0}, ...]`). In addition, `MetricsWithQuantiles` (`service.go:759-765,786-790`) sets `qq.Quantile = quant` without setting `qq.QuantileSet = true`, which would otherwise rewrite `0` to `0.95` inside `s.Metrics(ctx, qq)`.
- **Fix:**
  - Add `QuantileSet bool` to `RequestMetricsRequest` (`service.go:282`), propagate `q.QuantileSet` from `Service.Metrics` when constructing `RequestMetricsRequest`, and update `lokiQuantile(q float64, set bool)` (`lokisource.go:498-503`) to preserve `0` when `set && q == 0` (confirming Loki's `quantile_over_time(0, ...)` computes the exact minimum, just as Prometheus `histogram_quantile(0, ...)` does).
  - In `lego/backend/internal/metrics/mcp.go:280-286`, set `QuantileSet: in.HTTPLatencyQuantile != nil || in.Quantile != nil` on `MetricQuery` (mirroring `rest.go:567`).
  - In `lego/backend/internal/metrics/service.go:804-816`, change `normalizeQuantiles` to keep the full closed interval `[0, 1]` (`if q < 0 || q > 1 || math.IsNaN(q) || seen[q]`), and set `qq.QuantileSet = true` whenever `MetricsWithQuantiles` assigns `qq.Quantile` from `quants` (`:761-765` and `:786-790`).
  - All three surfaces (REST, GraphQL, MCP) share `Service.MetricsWithQuantiles` and `NewLokiRequestMetricsSource`, so fixing all three spots repairs REST, GraphQL, and MCP together.
- **Blast radius:** `lego/backend/internal/metrics/service.go`, `lokisource.go`, `mcp.go`, and callers of `normalizeQuantiles` (`service.go`, `project.go`). Existing callers passing `0.5`/`0.9`/`0.95`/`0.99` or omitting quantile (default `0.95`) are completely unchanged.
