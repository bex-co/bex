# 155 — `events.Service.List` (`checkWindow`) never rejects inverted (`startTime > endTime`) time ranges, silently returning `200 []` across MCP, REST, and GraphQL

Why: `lego/backend/internal/events/service.go:1169` calls `s.checkWindow(since, until)` (`:1349-1360`), which only checks whether `until.Sub(since) > MaxQueryHours` (and returns `nil` early when `MaxQueryHours <= 0`) without calling `core.ValidateInclusiveQueryRange(since, until)` or `core.ValidateQueryRange`. When a caller passes an inverted window (`startTime > endTime`), `until.Sub(since)` is negative, `checkWindow` succeeds, and MCP `list_events` (a shared Render tool), MCP `list_service_events`, REST `GET /v1/services/{id}/events`, and GraphQL `serviceEvents` all silently return `200 []` — unlike `logs.Service` and `metrics.Service`, which reject inverted ranges with `400 bad_request`.

- **Attribution:** server (`lego/backend/internal/events`)
- **Root cause:**
  - `lego/backend/internal/events/service.go:1349-1360` implements its own `checkWindow(since, until)` instead of using `core.ValidateInclusiveQueryRange` (or `core.CheckQueryWindow`), checking only `until.Sub(since) > time.Duration(s.MaxQueryHours)*time.Hour` (and skipping all checks when `s.MaxQueryHours <= 0`). An inverted range has a negative `until.Sub(since)` and silently passes through to `s.Store.ListServiceEvents`, which returns `0` rows.
  - Note on defaulted `since` (`events/service.go:1159-1161`): when a caller supplies ONLY `endTime` in the past (with `startTime` omitted and `OpenStart == false`), `:1161` currently defaults `since = s.Now().Add(-DefaultWindow)`, which also makes `since > until` if `endTime < now - 1h`. Validate `core.ValidateInclusiveQueryRange(filter.Since, filter.Until)` on the **explicit** caller bounds before defaulting `since` (and when `filter.Since.IsZero() && !filter.Until.IsZero() && !filter.OpenStart`, consider anchoring the 1h default window to `filter.Until.Add(-DefaultWindow)` rather than `s.Now().Add(-DefaultWindow)` so historical `endTime`-only queries do not accidentally produce an inverted default window — check `events/service_test.go` for existing `endTime`-only tests first).
- **Fix:**
  - In `lego/backend/internal/events/service.go`:
    - Call `core.ValidateInclusiveQueryRange(filter.Since, filter.Until)` before applying defaults (and regardless of `s.MaxQueryHours <= 0`), so any explicit `startTime > endTime` returns `core.ErrBadRequest` (`"startTime must be before or equal to endTime"`) on MCP, REST, and GraphQL while preserving single-instant `[t, t]` queries.
    - Check whether `filter.Since.IsZero() && !filter.Until.IsZero() && !filter.OpenStart` should default `since` relative to `filter.Until` (`until.Add(-DefaultWindow)`) instead of `s.Now().Add(-DefaultWindow)`, and whether explicit `startTime` with omitted `endTime` where `startTime > s.Now()` should stay allowed (future-events empty window) or reject — keep consistent with `logs.Service`.
