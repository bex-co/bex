# 016 — Cron-job run listing disagrees three ways on non-positive `limit`: REST silently returns 1 item, MCP returns 10, and GraphQL returns 20

Why: `GET /v1/cron-jobs/{id}/runs` (and `GET /v1/services/{id}/runs`) is a bex extension outside `render-public-api-1.json` (so OpenAPI validation does not run) and parses `limit` with `core.PageParams` (`lego/backend/internal/apps/rest.go:1360`), which clamps `?limit=0` and `?limit=-1` to `1` — silently returning a 1-item page on REST while MCP `list_cron_job_runs` returns 10 items and GraphQL `cronJobRuns` returns 20 items.

- **Attribution:** server (`lego/backend/internal/apps`)
- **Root cause:**
  - `GET /v1/cron-jobs/{id}/runs` (`lego/backend/internal/apps/rest.go:1359-1362,1377,1382`) is a bex extension absent from `render-public-api-1.json`, so `internal/api/openapi_validate.go` does not enforce `limit ∈ [1, 100]` before dispatch.
  - `apps/rest.go:1360` calls `core.PageParams(r.URL.Query())` (`lego/backend/internal/core/pagination.go:381-390`), which parses `0` or `-1` into `limit` and passes it to `core.PageLimit(limit)` — clamping any `< 1` to **`1`**! `ListCronRuns` (`apps/service.go:4711`) then sees `limit = 1` and returns a 1-item page.
  - Meanwhile, MCP `list_cron_job_runs` (`lego/backend/internal/apps/mcp.go:250-254,839-842`) uses non-pointer `Limit int` and rewrites `limit < 1` to **`10`** (`if limit < 1 { limit = 10 }`).
  - Meanwhile, GraphQL `cronJobRuns` (`lego/backend/internal/apps/graphql.go:1370-1372`) passes `gqlutil.Int(p.Args, "limit")` directly to `ListCronRuns`, which calls `core.PageLimitOrAbsent(limit)` (`apps/service.go:4711`) and rewrites `limit <= 0` to **`20`** (`core.DefaultPageLimit`).
- **Fix:**
  - On REST `listCronRuns` (`lego/backend/internal/apps/rest.go:1359-1362`), parse `limit` with `core.QueryLimit` (rejecting non-integer or `<= 0` with `400 bad_request`, and optionally rejecting `> core.MaxPageLimit` to match Render-validated REST lists) instead of `core.PageParams`, so `?limit=0` and `?limit=-1` never silently return a 1-item page.
  - On MCP `list_cron_job_runs` (`lego/backend/internal/apps/mcp.go:250-254,839-842`), change `listCronJobRunsArgs.Limit` to `*int` so omitted `nil` keeps the documented default of `10` while explicit `<= 0` (or `> 100`) returns `core.ErrBadRequest`.
  - On GraphQL `cronJobRuns` (`lego/backend/internal/apps/graphql.go:1370-1372`), parse `limit` with `gqlutil.PositiveLimit(p.Args)` (checking `dashboard/` callers of `cronJobRuns` first to ensure none passes `limit: 0`) so explicit `<= 0` is rejected consistently across all three surfaces.
  - Also audit any other non-OpenAPI-validated REST routes calling `core.PageParams` to confirm none has the same `?limit=0 -> 1 item` trap.
