# 015 — Cloud-agent MCP list/wait tools silently accept non-positive `limit` and `timeoutSeconds: 0`, diverging from REST `400` and GraphQL errors

Why: Cloud-agent MCP tools (`list_agent_automations`, `list_agent_automation_runs`, `list_agent_skill_versions`, `list_agent_sessions`, `get_agent_session_transcript`, `list_agent_session_attachments`, `wait_agent_sessions`) decode `limit`/`timeoutSeconds` into non-pointer `int` fields (and `AgentAutomations`, `AgentAutomationRuns`, `AgentSkillVersions`, and `ListAttachments` silently default `limit <= 0`), so MCP accepts explicit `limit: 0` (and negative limits on automations/skills/attachments) where REST and GraphQL return `bad request: limit must be a positive integer`, and `wait_agent_sessions(timeoutSeconds: 0)` silently blocks for 25 s instead of rejecting `timeoutSeconds`.

### Cloud-agent MCP list tools accept `limit: 0` / `-1` and `wait_agent_sessions` accepts `timeoutSeconds: 0` while REST and GraphQL reject them

- **Expected / actual:**
  - **Expected:** Per ADR006 (shared core semantics across REST, GraphQL, and MCP) and ADR094 D6 (`timeoutSeconds: 1-25`), every cloud-agent list tool should reject an explicit `limit <= 0` on MCP just as REST (`core.QueryLimit`) and GraphQL (`gqlutil.PositiveLimit` / `automationLimitArg`) already do, and `wait_agent_sessions` should reject an explicit `timeoutSeconds: 0` with `AGENT_SESSION_INPUT_INVALID: timeoutSeconds must be 1-25` rather than silently blocking for 25 seconds when an agent passes `0` expecting a non-blocking poll.
  - **Actual:**
    - `list_agent_automations` with `limit: 0` and `limit: -1` both return `200` (`isError` unset, `{"automations":[],"ownerId":"tea-daif693dqjvc73e7as3g"}`), while REST `GET /v1/agent-automations?limit=0` / `?limit=-1` returns `400` and GraphQL `agentAutomations(limit: 0 / -1)` returns a GraphQL error (`"bad request: limit must be a positive integer"`).
    - `list_agent_skill_versions` with `limit: 0` and `limit: -1` (reproduced on disposable skill `skl-dc3d49dksp0s73b5omp0`, deleted) both return `200` (`isError` unset, 1 version), while REST `GET /v1/agent-skills/{id}/versions?limit=0` / `?limit=-1` returns `400` and GraphQL `agentSkillVersions(limit: 0 / -1)` returns `"bad request: limit must be a positive integer"`.
    - `list_agent_sessions` with `limit: 0` returns `200` (`isError` unset, `{"agentSessions":[]}`), while `limit: -1` returns `AGENT_SESSION_FILTER_INVALID: limit must be a positive integer` and REST/GraphQL reject `limit: 0` with `"bad request: limit must be a positive integer"`.
    - `wait_agent_sessions` with `timeoutSeconds: 0` bypasses `timeoutSeconds must be 1-25` (falling through to `waitSnapshot`, `FORBIDDEN: forbidden` on a synthetic id, or a 25 s wait on a live working session), whereas `timeoutSeconds: -5` and `999` fail fast in `normalizeWait` with `AGENT_SESSION_INPUT_INVALID: timeoutSeconds must be 1-25`.
    - Code inspection confirms the same non-pointer `Limit int` / silent `limit <= 0` fallback in `list_agent_automation_runs`, `get_agent_session_transcript`, and `list_agent_session_attachments`.

- **Attribution:** server (`lego/backend/internal/agentsessions`)
- **Root cause:**
  - MCP input structs use non-pointer `int`, making explicit `0` indistinguishable from omitted:
    - `listArgs.Limit` (`lego/backend/internal/agentsessions/mcp.go:81`)
    - `transcriptArgs.Limit` (`lego/backend/internal/agentsessions/mcp.go:127`)
    - `listAgentSkillVersionsArgs.Limit` (`lego/backend/internal/agentsessions/mcp.go:196`)
    - `listAttachmentsArgs.Limit` (`lego/backend/internal/agentsessions/mcp.go:227`)
    - `listAutomationsArgs.Limit` (`lego/backend/internal/agentsessions/automations_mcp.go:31`)
    - `listAutomationRunsArgs.Limit` (`lego/backend/internal/agentsessions/automations_mcp.go:54`)
    - `WaitRequest.TimeoutSeconds` (`lego/backend/internal/agentsessions/wait.go:34`, coerced at `wait.go:188`: `if secs == 0 { secs = defaultWaitSeconds }`)
  - Worse, `AgentAutomations` (`automations.go:278`), `AgentAutomationRuns` (`automation_run.go:116`), `AgentSkillVersions` (`skills_versions.go:114`), and `ListAttachments` (`attachments.go:412`) do not even reject negative `limit` values inside the service (`if limit <= 0 { limit = default... }`), relying solely on REST (`core.QueryLimit`) and GraphQL (`gqlutil.PositiveLimit` / `automationLimitArg`) while MCP bypasses both.
- **Fix:**
  - Change the MCP input fields above to `*int` (so omitted `nil` uses the default while explicit `<= 0` is rejected before calling the service, or pass through a small `positiveMCPLimit(*int)` helper returning `core.ErrLimitNotPositive` / the coded invalid error) and update `WaitRequest.TimeoutSeconds` (or a dedicated `waitArgs` MCP struct) to `*int` so explicit `0` returns `AGENT_SESSION_INPUT_INVALID: timeoutSeconds must be 1-25` while omitted `nil` defaults to `25`.
  - In `AgentAutomations`, `AgentAutomationRuns`, `AgentSkillVersions`, and `ListAttachments`, also reject `limit < 0` in the service (matching `normalizeLimit` in `service.go:1228-1239`) so no direct caller can slip a negative limit past validation.
  - Update `lego/backend/internal/agentsessions/testdata/mcp_tools.golden.json` if pointer types change `"type": "integer"` to `["null", "integer"]` (or keep `"type": "integer"` with `mcputil` schema overrides if required by the golden contract — check `TestMCPToolsGolden` and `TestMCPArgumentErrorsNeverEchoTheValue`).
  - No REST or GraphQL regression; aligns MCP with the existing REST/GraphQL `limit` contract across all seven cloud-agent tools.
