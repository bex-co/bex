# 080 — `delete_env_group` (and REST/GraphQL twins) unlinks arbitrary services and triggers service rollouts on an `env_groups: read_write`-only API key, bypassing `services.manage` (`unlink_env_group`)

Why: `lego/backend/internal/api/key_permission_ops.go:127,545,802` maps `GQL Mutation.deleteEnvGroup`, `MCP delete_env_group`, and `REST DELETE /v1/env-groups/{id}` solely to `{core.KeyEnvGroupsManage}`, and `envgroups.Service.DeleteEnvGroup` (`lego/backend/internal/envgroups/service.go:874-903`) deletes the group and detaches every `deleted.ServiceLinks` without checking `core.KeyServicesManage` — letting an `env_groups: read_write`-only key explicitly denied `unlink_env_group` mutate linked services' specs and trigger rollouts (superseding queued deploys) across all linked services.

### An `env_groups: read_write`-only key detaches linked services and triggers rollouts via `delete_env_group` without `services.manage`

- **Expected / actual:**
  - **Expected:** Matching `unlink_env_group` / `DELETE /v1/env-groups/{id}/services/{serviceId}` (`key_permission_ops.go:759,805` → `{core.KeyEnvGroupsManage, core.KeyServicesManage}`) and sibling cascade-permission fixes (`w31/056`, `w31/059`), deleting an **unlinked** environment group requires only `core.KeyEnvGroupsManage`, whereas deleting an environment group with active `ServiceLinks` modifies every linked service's spec and rolls those services — so it must require `core.KeyServicesManage` (and refuse with `403 api_key_permission_denied` before deleting the group row) when `len(g.ServiceLinks) > 0`.
  - **Actual:**
    - Control confirmed `key-evgmgr` (`env_groups: read_write`, zero `services`, zero `deploys_run`) was refused `MCP unlink_env_group` with `api_key_permission_denied` (`Create, update, and delete environment groups; Create, update, and delete services`).

- **Attribution:** server (`lego/backend/internal/envgroups`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:127,545,802` statically maps `GQL Mutation.deleteEnvGroup`, `MCP delete_env_group`, and `REST DELETE /v1/env-groups/{id}` to `{core.KeyEnvGroupsManage}` only.
  - `envgroups.Service.DeleteEnvGroup` (`lego/backend/internal/envgroups/service.go:874-903`) authorizes `core.RelCanCreate` and `requireGroupAdmin`, deletes the group row inside `WithEnvGroupContentLock`, and then detaches every service in `deleted.ServiceLinks` (`s.detach(ctx, gid, svc)`) without checking `s.RequireKeyGrant(ctx, core.KeyServicesManage)` (or `core.KeyBuildSourcesManage` if a linked entry is a `bds-…` build source) before deleting the row.
- **Fix:**
  - Inside `envgroups.Service.DeleteEnvGroup` (`lego/backend/internal/envgroups/service.go:883-887`), inside `WithEnvGroupContentLock` and **before** calling `s.Groups.DeleteEnvGroup(ctx, gid)`, re-read the group's current `ServiceLinks`; if non-empty, require `core.KeyServicesManage` (for regular services) and `core.KeyBuildSourcesManage` (if any linked ID is a `bds-…` build source) via `s.RequireKeyGrant`, returning `api_key_permission_denied` before deleting the row if the key lacks the grant.
  - Keep unlinked `DeleteEnvGroup` working with `env_groups: read_write` alone.
- **Blast radius:** `lego/backend/internal/envgroups/service.go` and scoped-key tests in `lego/backend/internal/{envgroups,api}/`. Fixes MCP, REST, and GraphQL together from one service method. Callers with `All` keys, human sessions, or deleting unlinked env groups are unaffected.
