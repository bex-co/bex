# 107 — Scoped `postgres_credentials: write`-only API keys bypass `postgres_credentials: read` (`postgres.credentials.view`) and mint live plaintext Postgres passwords via `create_postgres_user`, `POST /v1/postgres/{id}/users`, and GraphQL `createDatabaseUser`

Why: `lego/backend/internal/api/key_permission_ops.go:97,536,1125` maps `GQL Mutation.createDatabaseUser`, `MCP create_postgres_user`, and `REST POST /v1/postgres/{id}/users` solely to `{core.KeyPostgresCredentialsManage}` (`postgres_credentials: write`, `requiredRole: "developer"`), omitting `core.KeyPostgresCredentials` (`postgres.credentials.view`) — violating `key_permission_ops.go:33-34`'s own rule ("an operation that reveals a secret value needs the secret's own view") — and `postgres.Service.CreateUser` (`lego/backend/internal/postgres/access.go:133-184,253`) echoes a live plaintext database login password while checking only `core.RelCanCreate` and never `core.RelCanViewSensitive`.

### Write-only `postgres_credentials: write` keys are refused `connection-info` and `list_postgres_users` yet receive plaintext login passwords from `create_postgres_user` across MCP, REST, and GraphQL

- **Severity:** blocker
- **Versions:** deployed pin `ec6211f2ca` (`11695fb886cb`, active during live probe; zero diff on `key_permission_ops.go:97,536,1125` or `postgres/access.go` vs `HEAD` `918667a83f`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`

- **Expected / actual:**
  - **Expected:** Per `lego/backend/internal/api/key_permission_ops.go:33-34` ("an operation that reveals a secret value needs the secret's own view (env-var values, connection strings, exports), not the resource's") and `lego/backend/internal/postgres/access.go:152-154` (which explicitly distinguishes `CreateCredential`, echoing no password, from `CreateUser`, echoing the one-time password), calling `create_postgres_user` / `POST /v1/postgres/{id}/users` / `createDatabaseUser` must require **both** `core.KeyPostgresCredentialsManage` and `core.KeyPostgresCredentials` (`postgres_credentials: read_write`), and `CreateUser` must authorize `core.RelCanViewSensitive` alongside `core.RelCanCreate`. A write-only `postgres_credentials: write` key (intended for blind rotation via `create_postgres_credential` / `delete_postgres_credential` without ever obtaining live database passwords) must receive `403 api_key_permission_denied` naming `postgres.credentials.view`.
  - **Actual:**
    - All three controls refused the `postgres_credentials: write` key with `403 api_key_permission_denied` (`required: ["postgres.credentials.view"]`).
    - Yet `MCP create_postgres_user` (`200 OK`), `REST POST /v1/postgres/{id}/users` (`201 Created`), and `GraphQL createDatabaseUser` (`200 OK`) all succeeded and returned live plaintext login passwords directly to the write-only key.
- **Wire evidence:**

- **Attribution:** server (`lego/backend/internal/api` and `lego/backend/internal/postgres`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:97,536,1125` maps `GQL Mutation.createDatabaseUser`, `MCP create_postgres_user`, and `REST POST /v1/postgres/{id}/users` identically to `create_postgres_credential` (`{core.KeyPostgresCredentialsManage}`), overlooking that `CreateUser` returns the newly generated password in plaintext (`postgres/access.go:253`) whereas `CreateCredential` does not (`access.go:152-162`).
  - `postgres.Service.CreateUser` (`lego/backend/internal/postgres/access.go:133-145`) delegates to `createUser(..., asDefault=false)` (`:164-184`), which authorizes `core.RelCanCreate` (`:166,173`) and `requireUnprotected(ctx, d, core.VerbViewCredentials)` (`:181`), but never checks `core.RelCanViewSensitive` (which `ConnectionInfo`, `ListUsers`, and `Query` require).
- **Fix:**
  - In `lego/backend/internal/api/key_permission_ops.go:97,536,1125`, require `{core.KeyPostgresCredentialsManage, core.KeyPostgresCredentials}` on `GQL Mutation.createDatabaseUser`, `MCP create_postgres_user`, and `REST POST /v1/postgres/{id}/users` (keeping `{core.KeyPostgresCredentialsManage}` on Render's passwordless `create_postgres_credential` / `POST /v1/postgres/{id}/credentials` / `createDatabaseCredential` and on the delete verbs).
  - In `lego/backend/internal/postgres/access.go:164-184`, when `!asDefault`, also check `s.AuthorizeDatabaseFresh(ctx, core.RelCanViewSensitive, d)` alongside `core.RelCanCreate` so returning a plaintext database password requires sensitive-read capability as well as create capability.
  - Surface impact: protects MCP (`create_postgres_user`), REST (`POST /v1/postgres/{id}/users`), and GraphQL (`createDatabaseUser`) uniformly; `All` keys, `postgres_credentials: read_write` keys, and human Developer/Admin sessions continue working unchanged.
- **Blast radius:** `lego/backend/internal/api/key_permission_ops.go`, `lego/backend/internal/postgres/access.go`, and scoped-key/authz tests in `lego/backend/internal/api/` and `lego/backend/internal/postgres/`.
