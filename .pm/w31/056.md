# 056 — Scoped `env_groups: read_write` API keys bypass `envgroups.values.view`/`set`, `services.manage`, `deploys.run`, and `projects.move` via `create_env_group` and `clone_env_group` across MCP, REST, and GraphQL

Why: `lego/backend/internal/api/key_permission_ops.go:80,95,505,515,1083-1084` maps `create_env_group` / `POST /v1/env-groups` / `Mutation.createEnvGroup` and `clone_env_group` / `POST /v1/env-groups/{id}/clone` / `Mutation.cloneEnvGroup` solely to `{core.KeyEnvGroupsManage}`, and `envgroups.Service.CreateEnvGroup` / `CloneEnvGroup` perform no additional key-grant checks — allowing an API key holding only `env_groups: read_write` (with zero `env_groups_values`, `services`, `services_env`, `deploys`, or `projects` grants) to write env vars and secret files, clone secret values from existing groups, place groups into environments, and link + immediately deploy arbitrary services in the workspace.

- **Attribution:** server (`lego/backend/internal/api` and `lego/backend/internal/envgroups`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:80,95,505,515,1083-1084` statically maps all six create/clone operations (`MCP create_env_group`, `MCP clone_env_group`, `REST POST /v1/env-groups`, `REST POST /v1/env-groups/{id}/clone`, `GQL Mutation.createEnvGroup`, `GQL Mutation.cloneEnvGroup`) to `{core.KeyEnvGroupsManage}` only.
  - `envgroups.Service.CreateEnvGroup` (`lego/backend/internal/envgroups/service.go:424-510`) and `CloneEnvGroup` (`lego/backend/internal/envgroups/clone.go:36-93`) authorize OpenFGA workspace/group relations (`RelCanCreate`, `RelCanViewSensitive`) but never check the caller's scoped `core.KeyGrant` for the composite sub-actions carried in `req` (`EnvVars`/`SecretFiles` → `KeyEnvGroupsValuesSet`; `ServiceIDs` → `KeyServicesManage`; `EnvironmentID` → `KeyProjectsMove`; clone source read → `KeyEnvGroupsValues` + `KeyEnvGroupsValuesSet`).
  - Because `requireKeyGrant` (`lego/backend/internal/api/scope_matrix.go:135-156`) only inspects the static operation name before decoding arguments, the composite fields on `CreateEnvGroupRequest` and `CloneEnvGroupRequest` bypass the separate permissions completely.
- **Fix:**
  - Enforce dynamic/composite `KeyGrant` checks inside `envgroups.Service.CreateEnvGroup` and `envgroups.Service.CloneEnvGroup` (using `s.KeyGrant(ctx)` on `core.Base`, returning `core.NewKeyPermissionDeniedError(missing)` when `!grant.All`), and update static `keyPermissionOps` where unconditional:
    - `CloneEnvGroup` (`key_permission_ops.go:80,505,1084`): always reads source secrets and writes cloned secrets, so map statically to `{core.KeyEnvGroupsManage, core.KeyEnvGroupsValues, core.KeyEnvGroupsValuesSet}` (and check `core.KeyProjectsMove` in `CloneEnvGroup` when `req.EnvironmentID != ""`).
    - `CreateEnvGroup` (`envgroups/service.go:424-485`): keep static `{core.KeyEnvGroupsManage}` so creating an empty env group still works with `env_groups: read_write`, and before mutating require:
      - `core.KeyEnvGroupsValuesSet` when `len(req.EnvVars) > 0 || len(req.SecretFiles) > 0`;
      - `core.KeyServicesManage` when `len(req.ServiceIDs) > 0` (matching `link_env_group`);
      - `core.KeyProjectsMove` when `strings.TrimSpace(req.EnvironmentID) != ""` (matching `move_env_group`).
  - Audit sibling composite create verbs (`apps.Service.Create` with `Env`/`SecretFiles`/`EnvironmentID`, `build_sources` create with `Env`/`SecretFiles`, `postgres`/`keyvalue` create with `EnvironmentID`) to verify whether their `KeyGrant` policy is intentionally covered by their primary manage action or needs the same conditional check (note `w31/051` covers build-source vs service env permissions separately).
  - Surface impact: fixes MCP (`create_env_group`, `clone_env_group`), REST (`POST /v1/env-groups`, `POST /v1/env-groups/{id}/clone`), and GraphQL (`createEnvGroup`, `cloneEnvGroup`) uniformly from one place.
