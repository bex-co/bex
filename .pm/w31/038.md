# 038 — Scoped API keys falsely report all permissions `"allowed"` on `get_viewer_capabilities`, `GET /v1/viewer/capabilities`, and GraphQL `viewerCapabilities` / `*Actions` projections

Why: `members.Service.Capabilities` (`lego/backend/internal/members/service.go:457-512`) and all five resource action projections (`apps/actioncaps.go`, `deploys/actioncaps.go`, `postgres/actioncaps.go`, `keyvalue/actioncaps.go`, `envgroups/protection.go`) probe OpenFGA and OAuth scopes through `CanDecisionOn` / `AuthorizeFreshOn` without ever intersecting with the caller's scoped API key grant (`core.Base.KeyGrant`), so even a read-only or Clear-All zero-grant API key is told every workspace capability and destructive action is `"allowed"` while every actual verb call fails with `api_key_permission_denied`.

### Capability and resource-action projections ignore scoped API key grants across MCP, REST, and GraphQL

- **Expected / actual:**
  - **Expected:** Capability projections exist so clients and agents can gate actions before invoking them (ADR087). For a scoped API key, `get_viewer_capabilities` / `GET /v1/viewer/capabilities` / GraphQL `viewerCapabilities` and the five `*Actions` projections must intersect the creator's workspace role with the API key's granted permissions — reporting `"denied"` (and `false` on the booleans) for capabilities/actions outside the key's grant (and denying all capabilities for a Clear-All `grants: []` key).
  - **Actual:**
    - With the `services:read` key, MCP `get_viewer_capabilities`, REST `GET /v1/viewer/capabilities`, and GraphQL `viewerCapabilities` all returned `role: "ADMIN"`, every boolean (`canCreate`, `canOperate`, `canManage`, `canManageKeys`, `canViewSensitive`, `canViewLogs`, `canViewBilling`, `canManageBilling`, `canViewActivity`) = `true`, and all 10 `grants` as `outcome: "allowed"`. GraphQL `serverActions` returned `outcome: "allowed"` for `restart`, `suspend`, `resume`, `delete`, `shell`, and `toggle_maintenance_mode` — even though calling `restart_service`, `suspend_service`, `delete_service`, `list_env_vars`, `get_usage`, `list_logs`, `list_webhook_endpoints`, and `list_postgres_instances` all returned `api_key_permission_denied`.
    - With the Clear-All zero-grant key (`grants: []`), both MCP `get_viewer_capabilities` and REST `GET /v1/viewer/capabilities` still returned all 10 capabilities `true` / `outcome: "allowed"`.
    - With the read-only `deploys:read` + `postgres:read` + `key_value:read` + `env_groups:read` key, GraphQL `deployActions`, `databaseActions`, `keyValueActions`, and `envGroupActions` returned `outcome: "allowed"` for every write and credential-reveal action (`deploy`, `cancel_deploy`, `rollback`, `restart`, `suspend`, `resume`, `view_connection_info`, `update_ip_allow_list`, `delete`, `view_env_vars`, `update_env_vars`), while invoking `suspend_postgres`, `list_postgres_credentials`, `GET /v1/postgres/{id}/connection-info`, `GET /v1/key-value/{id}/connection-info`, `trigger_deploy`, `get_env_group_var`, and `delete_env_group` all failed with `403 api_key_permission_denied`.

- **Attribution:** server (`lego/backend/internal/core`, `lego/backend/internal/members`, `lego/backend/internal/apps`, `lego/backend/internal/deploys`, `lego/backend/internal/postgres`, `lego/backend/internal/keyvalue`, `lego/backend/internal/envgroups`)
- **Root cause:**
  - `keyPermissionOps` (`lego/backend/internal/api/key_permission_ops.go:469,622,1008`) maps `viewerCapabilities`, `get_viewer_capabilities`, and `GET /v1/viewer/capabilities` to `core.KeyAnyGrant`, and maps the five `*Actions` GraphQL queries to their read actions (`services.view`, `deploys.view`, `postgres.view`, `keyvalue.view`, `envgroups.view`), so scoped keys reach the handlers.
  - Inside `members.Service.Capabilities` (`lego/backend/internal/members/service.go:457-512`) and all five `ActionCapabilities` methods (`lego/backend/internal/apps/actioncaps.go:59-138`, `lego/backend/internal/deploys/actioncaps.go:217-240`, `lego/backend/internal/postgres/actioncaps.go:43-94`, `lego/backend/internal/keyvalue/actioncaps.go:39-75`, `lego/backend/internal/envgroups/protection.go:70-92`), every probe runs through `CanDecisionOn` / `AuthorizeFreshOn` (`lego/backend/internal/core/decision.go:108`, `lego/backend/internal/core/base.go:1026`).
  - `checkAuthz` checks OAuth scope (`checkCapability`) and OpenFGA + creator ceiling (`keyCeiling`), never consulting `Base.KeyGrant(ctx)` (`lego/backend/internal/core/keygrant.go:620-626`). Unlike field-level projections (`envgroups/render.go:145`, `envgroups/service.go:1799`, `apps/blueprint.go:1696`, `webhooks/service.go:1128`, `agentsessions/spend.go:207`) that explicitly call `KeyGrantAllows`, the six capability projections were built in `w6/done/m136` before scoped API keys shipped in `w9/done/m496` and were never updated.
- **Fix:**
  - In `lego/backend/internal/core/decision.go`, add a shared helper `IntersectKeyGrant(ctx context.Context, d Decision, actions ...KeyAction) Decision` on `*Base`: if `!d.Allowed()`, return `d`; otherwise call `b.KeyGrantAllows(ctx, actions...)`, mapping an error to `Decision{Outcome: DecisionUnavailable, Reason: ReasonAuthzUnavailable}` and `false` to `Decision{Outcome: DecisionDenied, Reason: ReasonInsufficientPermission}` (preserving ADR087's bounded reason vocabulary, or adding a dedicated `missing_api_key_permission` reason if ADR087 is amended).
  - Intersect every action in the five `ActionCapabilities` projections with the exact `KeyAction` its verb enforces in `lego/backend/internal/api/key_permission_ops.go` (before computing preconditions so denied actions pay no billing/protection/deploy-scan reads):
    - `lego/backend/internal/apps/actioncaps.go:106-136`: `restart`/`suspend`/`resume`/`delete`/`toggle_maintenance_mode` → `KeyServicesManage`; `shell` → the exact `KeyAction` `createShellSession` enforces in `key_permission_ops.go`; `cron_run_now`/`cron_cancel_run` → `KeyServicesJobs`.
    - `lego/backend/internal/deploys/actioncaps.go:235-239`: `deploy`/`cancel_deploy` → `KeyDeploysRun`; `rollback` → `KeyDeploysRollback`.
    - `lego/backend/internal/postgres/actioncaps.go:86-93`: `restart`/`suspend`/`resume`/`update_ip_allow_list`/`delete` → `KeyPostgresManage`; `view_connection_info` → `KeyPostgresCredentials`.
    - `lego/backend/internal/keyvalue/actioncaps.go:68-74`: `suspend`/`resume`/`update_ip_allow_list`/`delete` → `KeyKeyValueManage`; `view_connection_info` → `KeyKeyValueConnection`.
    - `lego/backend/internal/envgroups/protection.go:87-91`: `view_env_vars` → `KeyEnvGroupsValues`; `update_env_vars` → `KeyEnvGroupsValuesSet`; `delete` → `KeyEnvGroupsManage`.
  - In `lego/backend/internal/core/keygrant.go` and `lego/backend/internal/members/service.go:476-502`, intersect each of the 10 workspace capability probes (including `can_view`) with the caller's `KeyGrant`:
    - Add a catalog-derived `KeyGrant.CoversRelation(relation string) bool` in `core/keygrant.go` (returning `true` when `g.All`, `false` for Clear-All `grants: []`, and for a scoped key checking the granted levels in `KeyPermissionCatalog` — e.g. `can_view_logs` requires `KeyMonitoringLogs`, `can_view_billing` requires `KeyWorkspaceSettings`, `can_manage_billing` requires `KeyWorkspaceSettingsManage`, `can_manage_keys` requires `KeyNoGrant` / `false` for scoped keys, and `can_view` / `can_operate` / `can_create` / `can_view_sensitive` / `can_manage` / `can_view_activity` check whether any granted level carries that relation in `KeyPermissionCatalog`). Note also `can_view` in `Capabilities` (`members/service.go:484-486`) is currently hardcoded `true` after `Authorize(RelCanView)` — for a Clear-All key (`grants: []`), `can_view` must reflect the empty grant too.
  - Surface impact: fixes MCP `get_viewer_capabilities`, REST `GET /v1/viewer/capabilities`, and GraphQL `viewerCapabilities`, `serverActions`, `deployActions`, `databaseActions`, `keyValueActions`, and `envGroupActions` simultaneously; `All` keys and human/OAuth sessions remain unchanged.
