# 052 — `keyPermissionOps` requires all 8 cross-resource write actions on plan-only `MCP create_blueprint` and `REST POST /v1/blueprints/{id}/syncs`, blocking `blueprints: read_write` keys

Why: Both `MCP create_blueprint` (`apps/blueprint_onboarding.go:1038-1047`) and `REST POST /v1/blueprints/{id}/syncs` (`apps/rest.go:1700-1711`) only create a planned sync without creating or mutating any services, databases, key-value stores, env groups, or projects (those changes occur only on `approve_blueprint` / `POST /v1/blueprints/{id}/approve`), yet `key_permission_ops.go:512,1074` requires all 8 cross-resource write permissions — diverging from `MCP plan_blueprint` (`:702`), `GQL Mutation.createPlannedBlueprint` (`:100`), and `GQL Mutation.planBlueprintSync` (`:171`), which require only `blueprints.manage`.

- **Expected / actual:**
  - **Expected:** Under `w5/m283` and Render's pinned MCP Blueprint onboarding contract, `MCP create_blueprint` and `REST POST /v1/blueprints/{id}/syncs` create only a Blueprint record and/or a planned sync (`PlanBlueprint`) without modifying any services, datastores, env groups, or projects. Matching `MCP plan_blueprint` (`key_permission_ops.go:702`), `GQL Mutation.createPlannedBlueprint` (`:100`), and `GQL Mutation.planBlueprintSync` (`:171`), both should require only `{core.KeyBlueprintsManage}` (`blueprints: read_write`), while `approve_blueprint` / `POST /v1/blueprints/{id}/approve` and `sync_blueprint` / `deploy` continue requiring the full apply permission set.
  - **Actual:**
    - `MCP create_blueprint` and `REST POST /v1/blueprints/{id}/syncs` both refused the `blueprints: read_write` key with `api_key_permission_denied` demanding 8 actions (`blueprints.manage`, `services.manage`, `services.env.set`, `postgres.manage`, `keyvalue.manage`, `envgroups.manage`, `envgroups.values.set`, `projects.manage`).
    - Control `MCP plan_blueprint` — which calls the exact same `s.PlanBlueprint` method as `REST POST /v1/blueprints/{id}/syncs` — passed the permission gate and returned `NOT_FOUND: blueprint not found`.
- **Wire evidence:**
  - `POST /mcp` `create_blueprint` (`rndr-id: b9890793-f9f1-808d`) → `200`, `isError: true`: `"api_key_permission_denied: this API key is not granted the permission this request needs: Update and disconnect Blueprints; Create, update, and delete services; Set environment variable and secret file values; Create, update, and delete databases; Create, update, and delete instances; Create, update, and delete environment groups; Set environment group variable and secret file values; Create, update, and delete projects and environments"`.
  - `POST /v1/blueprints/exs-00000000000000000000/syncs` (`rndr-id: e6f2ef96-f30f-d073`) → `403`, `params.required: ["blueprints.manage", "services.manage", "services.env.set", "postgres.manage", "keyvalue.manage", "envgroups.manage", "envgroups.values.set", "projects.manage"]`.
  - Control `POST /mcp` `plan_blueprint` (`rndr-id: de5bf176-dd29-9cc0`) → `200`, `isError: true`: `"NOT_FOUND: blueprint not found"`.
- **Attribution:** server (`lego/backend/internal/api`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:512` (`"MCP create_blueprint"`) still carries the pre-`w5/m283` apply-at-once 8-action slice from before `create_blueprint` was converted to Render's plan-only onboarding flow (`apps/blueprint_onboarding.go:1038-1047`).
  - `lego/backend/internal/api/key_permission_ops.go:1074` (`"REST POST /v1/blueprints/{id}/syncs"`) was given the same 8-action slice as `"REST POST /v1/blueprints/{id}/sync"` (`:1073`), even though `POST /v1/blueprints/{id}/syncs` calls only `s.PlanBlueprint` (`apps/rest.go:1700-1711`), the exact same method as `"MCP plan_blueprint"` (`:702` → `{core.KeyBlueprintsManage}`) and `"GQL Mutation.planBlueprintSync"` (`:171` → `{core.KeyBlueprintsManage}`).
  - Note: `"REST POST /v1/blueprints"` (`:1067`) still accepts the legacy apply-at-once body (`{"repo": …}` alongside Render's planned `{"source": …}` body, `blueprint_onboarding_test.go:429`), so keep the apply check on legacy apply-at-once calls (either leaving `:1067` as-is or checking the apply actions only on the legacy apply branch).
- **Fix:**
  - In `lego/backend/internal/api/key_permission_ops.go`:
    - Change `"MCP create_blueprint"` (`:512`) and `"REST POST /v1/blueprints/{id}/syncs"` (`:1074`) to `{core.KeyBlueprintsManage}` (matching `"MCP plan_blueprint"`, `"GQL Mutation.createPlannedBlueprint"`, and `"GQL Mutation.planBlueprintSync"`).
    - Keep `"MCP approve_blueprint"`, `"REST POST /v1/blueprints/{id}/approve"`, `"GQL Mutation.approveBlueprint"`, `"MCP sync_blueprint"`, `"REST POST /v1/blueprints/{id}/sync"`, `"MCP deploy"`, and `"REST POST /v1/blueprints/deploy"` requiring the full 8-action apply set.
  - Surface impact: restores parity between MCP `create_blueprint` / `plan_blueprint`, GraphQL `createPlannedBlueprint` / `planBlueprintSync`, and REST `POST /v1/blueprints/{id}/syncs` for least-privilege `blueprints: read_write` API keys.
