# 139 — `billing.normalizeBillingInfo` skips `billingInfoField` on `taxId.type`, bypassing control-character/length checks and echoing arbitrary untrusted input verbatim into errors across MCP, REST, and GraphQL

Why: Every other field in `billing.normalizeBillingInfo` (`companyName` at `lego/backend/internal/billing/billing_info.go:181`, all six `address.*` fields at `:186-196`, and `taxId.value` at `:210`) passes through `billingInfoField` (`:227-238`), which rejects ASCII/Unicode control characters and line separators and enforces a rune cap without echoing caller input; `taxId.type` (`:209,217`) skips `billingInfoField` and formats `&fieldError{"taxId.type", fmt.Sprintf("%q is not a Stripe tax ID type", t.Type)}`, accepting arbitrarily long or control-character-bearing values and echoing them verbatim into `error`, `message`, `params.reason` / `extensions.reason`, and MCP tool error text across MCP `update_billing_info`, REST `PUT /v1/workspaces/{workspaceId}/billing/info`, and GraphQL `setWorkspaceBillingInfo`.

- **Root cause:**
  - `lego/backend/internal/billing/billing_info.go:207-223`: `normalizeBillingInfo` trims and lowercases `t.Type` directly (`:209`) without calling `billingInfoField`, and at `:217` constructs `&fieldError{"taxId.type", fmt.Sprintf("%q is not a Stripe tax ID type", t.Type)}`, bypassing both `billingInfoField`'s control-character/line-separator/length checks (`:227-238`) and the value-free error pattern used by `address.country` (`:202`).
