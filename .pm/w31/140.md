# 140 — `sandbox.displayImage` misses OpenSandbox suspend/resume snapshot URIs (`snap-gen<N>`), leaking internal Zot cluster registry addresses and substrate UUIDs in `Sandbox.image` across MCP, REST, and GraphQL (and breaking `buildDependents`)

Why: When OpenSandbox suspends and resumes a sandbox, it commits the rootfs to `zot.bex-registry.svc:5000/snapshots/<ws>-sandbox/<substrate-uuid>-sandbox:snap-gen<N>` and overwrites `raw.Image.URI`; `displayImage` (`lego/backend/internal/sandbox/images.go:836-844`) matches only imported-image (`sbb-…@sha256:…`) and restored-snapshot (`snp-…@sha256:…`) URIs, so `sandboxFromOpenSandbox` (`service.go:838`) leaks the raw in-cluster Zot registry host, port, tenant sandbox namespace, and substrate UUID across MCP `list_sandboxes`, REST `GET /v1/sandboxes` / `GET /v1/sandboxes/{id}`, and GraphQL `sandboxes` / `sandbox`, while `buildDependents` (`images.go:719`) loses track of an imported image (`sbb-…`) once a dependent sandbox suspends and resumes.

- **Attribution:** server (`lego/backend/internal/sandbox`)
- **Root cause:**
  - `lego/backend/internal/sandbox/images.go:832-844` (`displayImage`) only matches `importedImage` (`…/images/(sbb-[0-9a-v]{20})@sha256:[0-9a-f]{64}$`) and `restoredImage` (`snapshots.go:266`, `…/snapshots/(snp-[0-9a-v]{20})@sha256:[0-9a-f]{64}$`) and returns `uri` unchanged otherwise.
  - When OpenSandbox suspends and resumes a sandbox, it commits a rootfs snapshot to `zot.bex-registry.svc:5000/snapshots/<ws>-sandbox/<substrate-id>-sandbox:snap-gen<N>` and replaces `raw.Image.URI` with that internal reference.
  - `sandboxMetadata` (`service.go:516-529`) stamps only `bex.co/template` (the template name, e.g. `"base"`), never the original `sbb-`/`snp-` source ID or template image, so after suspend/resume neither `sandboxFromOpenSandbox` (`service.go:838`), `buildDependents` (`images.go:719`), nor `Meter.Label` (`meter.go:288`) can recover the original public image, and `displayImage` passes the internal cluster registry address through verbatim.
- **Fix:**
  - Stamp the sandbox's create-time source identifier (`sbb-…` or `snp-…` in a Kubernetes-label-safe metadata key such as `bex.co/source-image`, since `bex.co/template` already names the template) at creation in `createWithID` (`lego/backend/internal/sandbox/service.go:981-990`).
  - Resolve the sandbox's public image in one helper used by `sandboxFromOpenSandbox` (`service.go:838`), `buildDependents` (`images.go:719`), and `Meter.Label` (`meter.go:288`): prefer the stamped `sbb-…`/`snp-…` metadata when present; fall back to `displayImage(raw.Image.URI)`; and when `raw.Image.URI` is an internal suspend-snapshot URI (`…/snapshots/<ws>-sandbox/<id>-sandbox:snap-gen<N>`), never return the raw internal registry URI — resolve the template's configured `Template.Image` via `s.Templates[raw.Metadata[metadataTemplate]]` (or empty string if unknown).
  - Surface impact: fixes `Sandbox.image` consistently across MCP (`list_sandboxes`), REST (`GET /v1/sandboxes`, `GET /v1/sandboxes/{id}`), GraphQL (`sandboxes`, `sandbox`), usage labels, and `delete_sandbox_image` dependency protection (`buildDependents`).
