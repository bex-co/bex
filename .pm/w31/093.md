# 093 — `core.KeyPermissionCatalog` gives `deploys` ("Deployment information") a phantom `run` level identical to `read` (`deploys.view`), so API keys granted `deploys: run` silently fail `trigger_deploy`, `cancel_deploy`, and `rollback_deploy`

Why: `lego/backend/internal/core/keygrant.go:306-314` defines `deploys` ("Deployment information") with two levels — `KeyLevelRead` and `KeyLevelRun` — that both require only `RelCanViewActivity` (`viewer`) and grant the exact same single action `KeyDeploysView` (`deploys.view`), while placing `KeyDeploysRun` and `KeyDeploysRollback` solely on a separate `deploys_run` ("Run deployments") permission, so `list_api_key_permissions`, `GET /v1/api-keys/permissions`, GraphQL `apiKeyPermissionCatalog`, and the dashboard permission picker advertise a misleading `deploys: run` level that can never run deploys.

- **Attribution:** server (`lego/backend/internal/core`)
- **Root cause:**
  - `lego/backend/internal/core/keygrant.go:306-314` (introduced in `e09ea5065d`, `w9/m496`):
    ```go
    {ID: "deploys", Name: "Deployment information", Levels: []KeyPermissionLevel{
        lvl(KeyLevelRead, rels(RelCanViewActivity), KeyDeploysView),
        lvl(KeyLevelRun, rels(RelCanViewActivity), KeyDeploysView),
    }},
    {ID: "deploys_run", Name: "Run deployments", Levels: []KeyPermissionLevel{
        lvl(KeyLevelRun, rels(RelCanOperate), KeyDeploysRun, KeyDeploysRollback),
    }},
    ```
  - Line 309 attaches a duplicate `KeyLevelRun` level to `deploys` with `RelCanViewActivity` and only `KeyDeploysView`. Because `apikeys.Service.PermissionCatalog` (`lego/backend/internal/apikeys/service.go:855-856`) and `core.ValidateKeyGrant` both read `KeyPermissionCatalog`, the phantom level is exposed verbatim on MCP, REST, GraphQL, and the dashboard permission picker (`dashboard/src/features/api-keys/hooks/use-api-key-permission-catalog.ts`).
- **Fix:**
  - Remove the duplicate no-op `lvl(KeyLevelRun, rels(RelCanViewActivity), KeyDeploysView)` entry from `deploys` in `lego/backend/internal/core/keygrant.go:309` so `deploys` ("Deployment information") offers only `KeyLevelRead` (`deploys.view`) and `deploys_run` ("Run deployments") owns `KeyLevelRun` (`deploys.run`, `deploys.rollback`) — or confirm against Render's live permission picker whether `deploys_run: run` should also include `KeyDeploysView` (Render's docs note that `Run` covers viewing deploys as well).
  - Add a catalog-invariant test in `lego/backend/internal/core/keygrant_test.go` asserting that no permission in `KeyPermissionCatalog` defines two levels with identical action sets (and update line 277's duplicate-permission test fixture to use a permission that genuinely has two distinct levels, e.g. `services:read` + `services:read_write`).
  - Keep backwards compatibility for any persisted key row containing `"deploys:run"` in `KeyGrantFromEntries` (e.g. map or treat as `deploys.view` rather than crashing) while rejecting new `"deploys:run"` grants in `ValidateKeyGrant`.
  - Surface impact: fixes MCP `list_api_key_permissions`, REST `GET /v1/api-keys/permissions`, GraphQL `apiKeyPermissionCatalog`, key creation/update validation, and the dashboard API key permission picker.
