# 208 — Pre-authorization input validation in `PATCH /v1/postgres/{id}`, `PUT /v1/object-storage/{ownerId}/buckets/{bucket}/public`, `PATCH /v1/api-keys/{id}`, and GraphQL `Mutation.{setRepo,setServiceIpAllowList}` returns `400 bad_request` instead of `403`/`404`

Why: `bex-api`'s authz-before-validation contract requires workspace/resource authorization to run before caller-supplied write fields are validated so unauthorized callers (foreign workspaces, unprivileged roles, or nonexistent targets) receive `403 FORBIDDEN` / `404 NOT_FOUND` (and record denied audit rows) instead of `400 bad_request`. Five remaining REST and GraphQL mutation adapters not covered by `w31/182`, `184`, `197`, `202`, `204`, or `206` validate inputs before invoking their authorized service verbs: `REST PATCH /v1/postgres/{id}` (`postgres/rest.go:497`, the REST twin of `w31/182`'s MCP `update_postgres`), `REST PUT /v1/object-storage/{ownerId}/buckets/{bucket}/public` (`api/object_storage_admin.go:172`), `REST PATCH /v1/api-keys/{id}` (`apikeys/rest.go:85-88`), and GraphQL `Mutation.setRepo` (`apps/graphql.go:1852`) and `Mutation.setServiceIpAllowList` (`apps/graphql.go:2079-2088`).

- **Root cause:**

  - `lego/backend/internal/apikeys/rest.go:81-89` (`PATCH /v1/api-keys/{id}`): rejects `req.Permissions == nil` with `permissions: required` before calling `s.UpdateAPIKeyPermissions` (which checks `AuthorizeMintClass` and workspace authorization).
  - `lego/backend/internal/apps/graphql.go:1852-1854` (`Mutation.setRepo`): checks `if startCommand != nil && command != nil` before calling `s.ApplyServicePatch` (which authorizes the App first in `preflightServicePatch`).
  - `lego/backend/internal/apps/graphql.go:2079-2088` (`Mutation.setServiceIpAllowList`): checks `!entriesSet && !cidrsSet` (`:2079`) and calls `serviceAllowListInputs(...)` (`:2082`) before calling `s.SetIPAllowList` (whose own pre-authz CIDR check is tracked in `w31/202`).
- **Fix:**
  - `postgres/rest.go:493-512`: carry raw `ConnectionPool *string` alongside `Pooler *bool` on `PostgresPatch` and run `resolvePooler` inside `updatePostgres` **after** `fetchToChange` authorizes the database (coordinating with `w31/182` so both REST `PATCH /v1/postgres/{id}` and MCP `update_postgres` share the exact same post-authz path).
  - `api/object_storage_admin.go:168-181`: pass `*bool` into `a.SetBucketPublic` (or authorize with `WithDeferredAllowedWriteAudit` first — coordinating with `w31/150` and `w31/184`) and return `ENABLED_REQUIRED` only after authorization succeeds.
