# 012 — MCP `list_logs` (and GraphQL `logs`) silently accept out-of-range `limit` (`0`, `-5`, `101`, `9999`), diverging from Render's pinned MCP contract (`1..100`) and REST `GET /v1/logs`

Why: `listLogsArgs.Limit` (`lego/backend/internal/logs/mcp.go:70,154`) and GraphQL `logs(limit:)` (`lego/backend/internal/logs/graphql.go:159,193-195`) pass any integer straight into `LogQuery.normalized()` (`logs/service.go:469-479`), silently turning `<= 0` into `20` and clamping `> 100` to `100` instead of rejecting out-of-range limits as Render's pinned `render-mcp-server` (`1..100`) and bex's own REST `GET /v1/logs` (`400 bad_request`) do.

Omitting `limit` continues to default to 20. GraphQL `logs` should similarly reject invalid explicit `limit` values instead of silently coercing `-5` or `0` to `20`.
  - **Actual:**
    - MCP `list_logs` with `limit: 0`, `-5`, `101`, and `9999` all succeed (`isError` absent) and return `{"hasMore":false,"logs":[],...}`.
    - GraphQL `logs` with `limit: 0`, `-5`, `101`, and `9999` all succeed (`{"data":{"logs":{"hasMore":false}}}`).

- **Attribution:** server (`lego/backend/internal/logs`, sibling datastore log adapters in `internal/postgres` and `internal/keyvalue`)
- **Root cause:**
  - `lego/backend/internal/logs/mcp.go:68-71` defines `listLogsArgs.Limit` as a non-pointer `int64` (`json:"limit,omitempty"`) with no JSON Schema `minimum`/`maximum` constraint, so explicit `0` is indistinguishable from omitted `limit`.
  - `lego/backend/internal/logs/mcp.go:154` assigns `q.Limit = in.Limit` with no range check, and `LogQuery.validate()` (`lego/backend/internal/logs/service.go:434-467`) does not validate `q.Limit`; `LogQuery.normalized()` (`logs/service.go:469-479`) silently rewrites `<= 0` to `defaultLogLimit` (`20`) and clamps `> maxLogLimit` (`100`) to `100`.
  - `lego/backend/internal/logs/graphql.go:193-195` assigns `q.Limit = int64(n)` without validating `n`, and `logs/rest.go:1021` relies solely on the REST OpenAPI request validator (`render_openapi_logs_limit_test.go:28-55`) rather than shared service validation (`core.QueryLimit64` only parses int64 without bounds).
  - Sibling `get_postgres_logs` (`lego/backend/internal/postgres/mcp.go:227,249`) and `get_key_value_logs` (`lego/backend/internal/keyvalue/mcp.go:227,244`) have the same non-pointer `Limit int` with silent `<= 0` defaulting.
- **Fix:**
  - Change `listLogsArgs.Limit` (`lego/backend/internal/logs/mcp.go:70`) to `*int64` so omitted vs explicit `0` are distinct, and validate when non-nil that `1 <= *in.Limit <= 100` (returning `fmt.Errorf("%w: limit must be an integer between 1 and 100", core.ErrBadRequest)`, matching Render's `parseLogsLimit` bounds). Also emit `minimum: 1` / `maximum: 100` on `list_logs.limit`'s JSON Schema if `mcputil` exposes numeric bounds (check `TestMCPArgumentTypesMatchUpstream` and `TestMCPArgumentErrorsNeverEchoTheValue` so out-of-range errors never echo secret values).
  - Validate explicit `limit` on GraphQL `logs` (`lego/backend/internal/logs/graphql.go:193-195`): reject `n < 1 || n > maxLogLimit` (check all dashboard GraphQL `logs(...)` callers first to ensure none pass `limit: 0` or `limit > 100`).
  - Keep REST `GET /v1/logs` accepting `1..1000` (w3/m475 CLI compatibility: `TestRenderListLogsAdmitsTheCLIPageLimit`), while verifying `logs/rest.go` itself also rejects `limit < 1` if called directly without the OpenAPI wrapper.
  - Apply the same `*int` `1..100` check to sibling `get_postgres_logs` (`postgres/mcp.go:227,249`) and `get_key_value_logs` (`keyvalue/mcp.go:227,244`) and their GraphQL counterparts (`databaseLogs` / `keyValueLogs`).
