# 127 — `postgres.Service.QueryDatabaseLogs` omits `ids.KindOf(name) == ids.Postgres`, letting `get_postgres_logs`, `GET /v1/postgres/{id}/logs`, and GraphQL `databaseLogs` return live logs for arbitrary `srv-` services and `red-` Key Value stores

Why: Unlike sibling `keyvalue.Service.QueryKeyValueLogs` (`lego/backend/internal/keyvalue/logs.go:47`, which delegates to `s.KeyValueLogs` only when `kind == ids.KeyValue`), `postgres.Service.QueryDatabaseLogs` (`lego/backend/internal/postgres/logs.go:46-48`) unconditionally delegates every `name` to `s.DatabaseLogs` (`datastoreLogsAdapter(logSvc)` at `api/server.go:1106`), whose `logs.Service.QueryLogs` (`logs/service.go:1063-1071`) routes `red-` to Key Value logs and everything else to `AuthorizeApp` — so passing a web service (`srv-…`) or Key Value (`red-…`) ID to `get_postgres_logs`, `GET /v1/postgres/{id}/logs`, or GraphQL `databaseLogs` returns `200 OK` with live app or Valkey logs instead of `404 Not Found`.

- **Root cause:**
  - `lego/backend/internal/postgres/logs.go:45-48`: `QueryDatabaseLogs` checks only `if s.DatabaseLogs != nil` without guarding the resource kind (`ids.KindOf(name) == ids.Postgres`), unlike `lego/backend/internal/keyvalue/logs.go:47` (`if kind, ok := ids.KindOf(name); ok && kind == ids.KeyValue && s.KeyValueLogs != nil`).
  - `lego/backend/internal/api/server.go:1106` wires `pg.DatabaseLogs = datastoreLogsAdapter(logSvc)`, which calls `logs.Service.QueryLogs` (`lego/backend/internal/logs/service.go:1063-1071`). `QueryLogs` accepts `dpg-`, `red-`, and any App name/ID, authorizing each against its own resource type instead of restricting to Postgres — so any caller holding `monitoring:read` + `postgres:read` (or a broad key) can read App or Key Value logs through the Postgres log endpoint (and vice versa, a Postgres-only permission check on `GET /v1/postgres/{id}/logs` / `get_postgres_logs` can read `srv-` / `red-` logs without `services:read` / `key_value:read`!).
