# 043 — `keyPermissionOps` maps deploy-hook and workspace-invite verbs (12 operations across MCP, REST, and GraphQL) to grantable API-key actions even though `AuthorizeMintClass` refuses every API key

Why: `lego/backend/internal/api/key_permission_ops.go` assigns `KeyDeploysRun` to all six `deploy-hook` verbs (`get_deploy_hook`, `regenerate_deploy_hook` + REST/GraphQL) and `KeyWorkspaceMembersManage` to all six workspace-invite verbs (`invite_workspace_member`, `resend_workspace_invite` + REST/GraphQL), so a scoped API key receives a misleading `api_key_permission_denied` telling the user to grant `"Trigger and cancel deploys"` or `"Update member roles and remove members"`, even though `deploys.Service.GetDeployHook`/`RegenerateDeployHook` (`lego/backend/internal/deploys/deployhook.go:131,163`) and `members.Service.Invite`/`ResendInvite` (`lego/backend/internal/members/service.go:682,787`) call `AuthorizeMintClass` and unconditionally reject every API key — including an Admin's `All` key — with bare `403 FORBIDDEN`.

- **Expected / actual:**
  - **Expected:** `keyPermissionOps` (`lego/backend/internal/api/key_permission_ops.go`) and the underlying service credential-class gate (`AuthorizeMintClass` vs `AuthorizeExportClass`) must agree:
    - Any operation that stays human-only via `AuthorizeMintClass` (which `docs/ADR024-members.md` § `w9/116` explicitly requires for workspace invites, and `deploys/deployhook.go:122-133` currently enforces for deploy hooks per codex round-7 F3) must be mapped to `{core.KeyNoGrant}` (like all 28 other `AuthorizeMintClass` operations in `key_permission_ops.go`) — and never tell the user to grant a scoped catalog permission that still fails with `403 FORBIDDEN`.
  - **Actual:**
    - With the scoped key, all four MCP calls and both REST calls returned `api_key_permission_denied` naming `"Trigger and cancel deploys"` (`params.required: ["deploys.run"]`) or `"Update member roles and remove members"` (`params.required: ["workspace.members.manage"]`).

- **Root cause:**
  - Across all 40 `core.OpClassMint` operations in `lego/backend/internal/api/scope_matrix_ops.go`:
    - 10 operations use `AuthorizeExportClass` (`create_webhook_endpoint`, `create_postgres_user`, `change_workspace_member_role` + REST/GraphQL) and legitimately work for attributed API keys with their catalog permission (`w9/m481`, `w9/116`, `w9/117`).
    - 18 operations use `AuthorizeMintClass` and are correctly mapped to `{core.KeyNoGrant}` (`create_api_key`, `update_api_key_permissions`, `add_ssh_key`, `createObjectAccessKey`, `revokeObjectAccessKey`, `invite_organization_member`, `change_organization_member_role`, `createRouterKey` + REST/GraphQL).
    - The remaining **12** `AuthorizeMintClass` operations were left mapped to grantable catalog actions in `lego/backend/internal/api/key_permission_ops.go`:
      - `GQL Query.deployHook` (`:377`), `GQL Mutation.regenerateDeployHook` (`:175`), `MCP get_deploy_hook` (`:591`), `MCP regenerate_deploy_hook` (`:708`), `REST GET /v1/services/{id}/deploy-hook` (`:987`), `REST POST /v1/services/{id}/deploy-hook/regenerate` (`:1135`) -> `{core.KeyDeploysRun}` while `deploys/deployhook.go:131,163` calls `AuthorizeMintClass`.
      - `GQL Mutation.inviteWorkspaceMember` (`:159`), `GQL Mutation.resendWorkspaceInvite` (`:188`), `MCP invite_workspace_member` (`:628`), `MCP resend_workspace_invite` (`:713`), `REST POST /v1/workspaces/{workspaceId}/members` (`:1161`), `REST POST /v1/workspaces/{workspaceId}/invites/{inviteId}/resend` (`:1160`) -> `{core.KeyWorkspaceMembersManage}` while `members/service.go:682,787` calls `AuthorizeMintClass` (and `docs/ADR024-members.md:284-286` explicitly keeps inviting human-only).
- **Fix:**
  - Update all 12 entries in `lego/backend/internal/api/key_permission_ops.go` to `{core.KeyNoGrant}` so scoped API keys are never told to grant `deploys.run` or `workspace.members.manage` for human-only `AuthorizeMintClass` verbs (note: check `core.KeyNoGrant`'s denial wording too — for `AuthorizeMintClass`-only operations, an `All` key is also refused, so avoid claiming `"(create a key with All)"` when no API key can call the verb, or keep consistent with `create_api_key`/`add_ssh_key` while removing the false `deploys.run`/`workspace.members.manage` claim).
  - Add a guard test in `lego/backend/internal/api/` asserting that every `core.OpClassMint` operation in `classifiedOps` either uses `{core.KeyNoGrant}` or is explicitly in the documented `AuthorizeExportClass` allowlist (`webhooks` create, `postgres` user create, `members` role change), preventing future drift.
  - Surface impact: aligns MCP, REST, and GraphQL scoped-key error responses on all 12 operations.
