# 048 — Image-backed build sources refuse `envVars`, `secretFiles`, and `envGroupIds` at creation, yet post-create env-var, secret-file, and env-group mutations succeed across MCP, REST, and GraphQL

Why: `apps.Service.CreateBuildSource` (`lego/backend/internal/apps/build_sources.go:222-225`) enforces Render's rule that build-time environment variables, secret files, and environment groups are only valid for git-backed build sources, yet neither `secrets.Service` (`lego/backend/internal/secrets/{service,files,batch}.go`) nor `envgroups.Service.linkFetched` (`lego/backend/internal/envgroups/service.go:1149`) checks whether a `TypeBuildSource` carrier is image-backed (`a.Spec.Repo == ""` / `a.Spec.Image != ""`) — letting callers store dead build-time secrets and link env groups onto image-backed build sources that can never run a build across MCP, REST (`/v1/build-sources/{id}/…`), and GraphQL.

### Post-create env-var, secret-file, and env-group mutations succeed on image-backed build sources across MCP, REST, and GraphQL despite create-time refusal

- **Expected / actual:**

  - **Actual:**
    - `create_build_source` with `image` + `envVars` refused with `bad request: envVars, secretFiles and envGroupIds are only valid for git build sources`.
    - Yet every post-create mutation on `bds-dc3mkqnfct6s73fs0fh0` succeeded and persisted unused secrets/links onto the image-backed carrier:

      - GraphQL `setEnvVar` and `linkEnvGroup` both returned `200` (`true`).
    - Linking an env group to an image build source also blocks moving that env group into an environment later (`validateLinkedServiceEnvironments` in `envgroups/service.go:1544`), even though the image build source can never consume the group.

- **Attribution:** server (`lego/backend/internal/secrets`, `lego/backend/internal/envgroups`)
- **Root cause:**
  - `apps.Service.CreateBuildSource` (`lego/backend/internal/apps/build_sources.go:222-225`) guards `req.Image != nil && (len(req.EnvVars) > 0 || len(req.SecretFiles) > 0 || len(req.EnvGroupIDs) > 0)`, and `deploys.Service.TriggerBuild` (`lego/backend/internal/deploys/build_sources.go:217-220`) guards `carrier.Spec.Repo == ""`.
  - In `lego/backend/internal/secrets/`:
    - `SetEnvVars` (`service.go:673`), `SetEnvVar` (`service.go:770`), `SetSecretFiles` (`files.go:206`), `SetSecretFile` (`files.go:150`), and `PatchEnvironment` (`batch.go:96`) authorize the build-source carrier via `scopeForWrite`, which never checks whether `core.IsBuildSource(a) && a.Spec.Repo == ""` (or `a.Spec.Image != ""`).
  - In `lego/backend/internal/envgroups/`:
    - `linkFetched` (`service.go:1149`) checks tenant match, sensitive auth, and environment compatibility, but never refuses an image-backed build source (`core.IsBuildSource(a) && a.Spec.Repo == ""`).
- **Fix:**
  - Add a small shared predicate in `lego/backend/internal/core/` (or beside `core.IsBuildSource`) — e.g. `core.IsImageBuildSource(a *appv1alpha1.App) bool` (`IsBuildSource(a) && a.Spec.Repo == ""`) — matching `deploys/build_sources.go:217`.
  - In `lego/backend/internal/secrets/`:
    - Refuse image-backed build sources with `fmt.Errorf("%w: build-time environment variables and secret files are only valid for git build sources", core.ErrBadRequest)` in `SetEnvVars`, `SetEnvVar`, `SetSecretFiles`, `SetSecretFile`, and `PatchEnvironment` (when the patch sets/generates any var or file; keep `DeleteEnvVar`, `DeleteSecretFile`, and delete-only `PatchEnvironment` / reads working so existing dead data can still be inspected and cleaned up).
  - In `lego/backend/internal/envgroups/service.go`:
    - In `linkFetched` (`service.go:1149`, after tenant/authz checks and before mutating the App or group), refuse `core.IsImageBuildSource(a)` with `fmt.Errorf("%w: environment groups can only be linked to git build sources", core.ErrBadRequest)` (keep `UnlinkService` / `DeleteEnvGroup` working so any already-linked group can be detached).
  - Surface impact: fixes MCP, REST (`/v1/build-sources/{id}/env-vars`, `/secret-files`, `/env-groups`), and GraphQL (`setEnvVar`, `setEnvVars`, `setSecretFile`, `setSecretFiles`, `patchServiceEnvironment`, `linkEnvGroup`) together at the shared service layer.
