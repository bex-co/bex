# 029 — `CreateKeyValue` and the `KeyValue` CRD never validate `storageGB`, accepting negative (`-1`) and unbounded (`999999` GB) storage on `free` and paid plans across MCP, REST, and GraphQL

Why: Unlike `postgres.CheckDatabaseAdmission` (which rejects negative storage, forbids expanding `free` past 1 GB, and caps paid storage), `CreateKeyValue` copies `req.StorageGB` straight into `KeyValueSpec.StorageGB` with zero backend or CRD bounds checks, and the operator's `resolveKVPlan` runs `growOnlyStorage(spec.StorageGB, plan.StorageGB)` (`max(requested, floor)`) — so MCP, REST, and GraphQL all accept `storageGB: -1` and even `storageGB: 999999` on `plan: "free"` through dry-run and CRD admission.

- **Attribution:** server (`lego/backend/internal/keyvalue`, `lego/types`, `lego/operator`)
- **Root cause:**
  - `CreateKeyValue` (`lego/backend/internal/keyvalue/service.go:662-755`) validates `Name`, `Region`, `Plan`, `IPAllowList`, `MaxmemoryPolicy`, and `PersistenceMode`, then copies `req.StorageGB` directly into `kv.Spec.StorageGB` (`:714`) without validating `StorageGB` at all.
  - `KeyValueSpec.StorageGB` (`lego/types/v1alpha1/keyvalue_types.go:64`) and the generated CRD (`lego/operator/config/crd/bases/app.bex.co_keyvalues.yaml:174-179`) have no `+kubebuilder:validation:Minimum=0` or maximum bound.
  - On reconciliation, `resolveKVPlan` (`lego/operator/internal/controller/keyvalue_controller.go:155`) computes `growOnlyStorage(spec.StorageGB, plan.StorageGB)` (`lego/operator/internal/controller/storage.go:106`: `max(requested, floor)`), so a free Key Value store created with `storageGB: 999999` requests a 999,999 GiB PVC on a free tier (and `storageGB: -1` is accepted silently as a valid create).
- **Fix:**
  - Add Key Value storage validation in `CreateKeyValue` (`lego/backend/internal/keyvalue/service.go`, mirroring `lego/backend/internal/postgres/admission.go:58-81` and `ValkeyCatalog.MaxStorageGB` in `lego/types/tiers/tiers.go`):
    - Reject `req.StorageGB < 0` with `400 KEY_VALUE_STORAGE_INVALID` (`storageGB must not be negative`).
    - On `free` (or empty default plan resolving to `free`), reject `req.StorageGB > plan.StorageGB` (1 GB) with `400 KEY_VALUE_STORAGE_PLAN_UNSUPPORTED` (fixing free-tier storage at 1 GB, matching Postgres free tier).
    - On paid plans, enforce a sensible ceiling (e.g. `ValkeyCatalog.MaxStorageGB(plan)`) with `400 KEY_VALUE_STORAGE_LIMIT_EXCEEDED` (and check whether Render's Key Value contract fixes storage per plan or allows overrides — document/enforce consistently).
  - Add `+kubebuilder:validation:Minimum=0` (and `+kubebuilder:validation:Maximum=...`) on `KeyValueSpec.StorageGB` in `lego/types/v1alpha1/keyvalue_types.go:64` and run `make manifests` in `lego/operator/` so CRD admission enforces the same floor/ceiling.
  - Surface impact: fixes MCP `create_key_value`, REST `POST /v1/key-value` & `POST /v1/redis`, GraphQL `createKeyValue`, and direct CR admission together.
