# 051 — Scoped API key checks on MCP and GraphQL env-var, secret-file, and env-group-link operations always enforce `services.*` permissions even when targeting a build source (`bds-…`), diverging from REST `/v1/build-sources/{id}/…`

Why: REST routes under `/v1/build-sources/{buildSourceId}/env-vars`, `/secret-files`, and `/env-groups/{envGroupId}` enforce `buildsources.env.view` / `buildsources.env.set` / `buildsources.manage` (`key_permission_ops.go:794-796,869-872,1077,1166-1169`), but MCP and GraphQL reuse the `serviceId` operations (`list_env_vars`, `get_env_var`, `set_env_var`, `update_env_vars`, `delete_env_var`, `list_secret_files`, `get_secret_file`, `set_secret_file`, `delete_secret_file`, `patch_service_environment`, `link_env_group`, `unlink_env_group` and their GraphQL twins) via `secrets.Service.envScope` / `envgroups.Service.ScopeBuildSourceID`, while `requireKeyGrant` checks only `services.env.*` / `services.manage` — letting a `services_env`-only key read and write build-source secrets while refusing a `build_source_env` key on MCP and GraphQL.

- **Attribution:** server (`lego/backend/internal/api`, `lego/backend/internal/secrets`, `lego/backend/internal/envgroups`)
- **Root cause:**
  - `requireKeyGrant` (`lego/backend/internal/api/scope_matrix.go:135-156`) checks only static operation names in `keyPermissionOps` (`key_permission_ops.go`), where every MCP and GraphQL env-var/secret-file/env-group-link verb (`list_env_vars`, `get_env_var`, `set_env_var`, `update_env_vars`, `update_environment_variables`, `delete_env_var`, `list_secret_files`, `get_secret_file`, `set_secret_file`, `delete_secret_file`, `patch_service_environment`, `link_env_group`, `unlink_env_group`, and their GraphQL equivalents) maps statically to `core.KeyServicesEnv` / `core.KeyServicesEnvSet` / `core.KeyServicesManage`.
  - Unlike REST (which separates `/v1/services/{id}/…` from `/v1/build-sources/{buildSourceId}/…`), MCP and GraphQL multiplex both `srv-…` services and `bds-…` build sources onto those same `serviceId` operations via `secrets.Service.envScope` (`lego/backend/internal/secrets/staged.go:103-109`, wired in `secrets/mcp.go:123-245` and `secrets/graphql.go:161,217`) and `envgroups.Service.ScopeBuildSourceID` (`envgroups/mcp.go:267,275`, `envgroups/graphql.go:241`).
  - `secrets/staged.go:113-118` already defines `envValueKeyGrant` to pick `core.KeyBuildSourcesEnv` vs `core.KeyServicesEnv` for nested GraphQL `BuildSource.envVar`/`secretFile` (added in `w2/m614`), but top-level MCP and GraphQL `secrets` and `envgroups` verbs never perform that target-kind check.
- **Fix:**
  - Enforce the target-kind key grant (`ids.KindOf(serviceID) == ids.BuildSource` → `KeyBuildSourcesEnv` / `KeyBuildSourcesEnvSet` / `KeyBuildSourcesManage`, else `KeyServicesEnv` / `KeyServicesEnvSet` / `KeyServicesManage`) so both directions hold on MCP and GraphQL:
    - Either support target-aware key-grant checks in `requireKeyGrant` (e.g. a small dynamic key-action resolver for the `serviceId`-multiplexed `secrets`/`envgroups` operations, inspecting the `serviceId` argument on MCP tool calls and GraphQL arguments before admitting the call, falling back to `KeyServices*` for non-`bds-` ids), **or** gate `KeyAnyGrant` at the static op table for the multiplexed ops and enforce the exact `core.Base.RequireKeyAction(ctx, action)` inside `secrets` and `envgroups` handlers immediately on entry (before any lookup/side effect, with audit parity via the same denial path).
    - Keep `TestKeyPermissionsCoverLiveOperations` asserting every op's required actions (for both `srv-` and `bds-` target kinds).
  - Also verify `REST /v1/services/{id}/env-vars` does not accept `bds-…` ids (already isolated because REST does not wrap `/v1/services` with `envScope`, only `/v1/build-sources` with `BuildSourceScope`, `secrets/rest.go:87-93`).
  - Surface impact: aligns MCP and GraphQL with REST `/v1/build-sources/{id}/…` and Render's `build_source_env` / `build_sources` permission catalog; no schema breaking change.
