# 070 — Build-source-linked services bypass `sameImageRepository`, `validateTrigger`, and operator `verifiedLinkedImage`, allowing arbitrary OCI image execution via `imageUrl` (plus `commitId` and `deployMode: "deploy_only"`)

Why: On a service linked to a build source (`a.Spec.BuildSource != nil`), both `a.Spec.Repo` and `a.Spec.Image` are empty — so `deploys.Service.validateTrigger` (`lego/backend/internal/deploys/service.go:818,826,830,840`) skips its repo, image, and `sameImageRepository` (`service.go:878-881`, `if configured == "" { return nil }`) guards and writes `a.Spec.ReleaseConfig.Image = p.ImageURL` (`service.go:1095-1097`), while the operator's `reusableArtifactImage` (`lego/operator/internal/controller/release_identity.go:856-859`) returns `ref.Image` ahead of `linkedBuildImage`/`verifiedLinkedImage` (`app_controller.go:1145,1175`), letting any deploy caller (Contributor, `deploys_run: run` key, or unauthenticated deploy hook `?imgURL=…`) run an arbitrary untrusted OCI image with the service's secrets on any `background_worker`, `cron_job`, or configured-port service (`!app.Spec.HasImagePorts()`).

- **Attribution:** server (`lego/backend/internal/deploys/service.go`) + operator (`lego/operator/internal/controller/{release_identity,app_controller,build_source}.go`)
- **Root cause:**
  - `deploys.Service.validateTrigger` (`lego/backend/internal/deploys/service.go:818-843`) only checks `a.Spec.Repo != ""` (for `deploy_only` and `imageUrl`) and `a.Spec.Repo == "" && a.Spec.Image != ""` (for `commitId`). When `a.Spec.BuildSource != nil`, both `a.Spec.Repo` and `a.Spec.Image` are empty, so `imageUrl`, `commitId`, and `deployMode: "deploy_only"` all pass validation.
  - `sameImageRepository` (`lego/backend/internal/deploys/service.go:878-881`) returns `nil` when `configured == ""`, turning an empty `a.Spec.Image` into an unconditional allow.
  - `triggerFetched` (`lego/backend/internal/deploys/service.go:1095-1097`) then writes `a.Spec.ReleaseConfig = &ReleaseConfigReference{Generation: release, Image: p.ImageURL}`, and `reusableArtifactImage` (`lego/operator/internal/controller/release_identity.go:856-859`) returns `ref.Image` before `app_controller.go:1175` reaches `linkedBuildImage`/`verifiedLinkedImage`.
  - In `resolveImageNetwork` (`lego/operator/internal/controller/image_network.go:258-261`), any service with `!app.Spec.HasImagePorts()` (`background_worker`, `cron_job`, or configured-port `web_service`/`private_service`) skips image-repo inspection entirely and runs `ref.Image` directly.
- **Fix:**
  - In `deploys.Service.validateTrigger` (`lego/backend/internal/deploys/service.go:799-860`):
    - When `a.Spec.BuildSource != nil`, refuse `p.ImageURL != ""` (`"imageUrl is not supported for services linked to a build source; use buildId instead"`), `p.CommitID != "" && !p.restart` (`"commitId is not supported for services linked to a build source; build the commit on the build source and deploy with buildId"`), and `p.DeployMode == "deploy_only"` (`"deployMode \"deploy_only\" is not supported for services linked to a build source"`).
    - Change `sameImageRepository` (`service.go:878-881`) to fail closed (`core.ErrBadRequest`) when `configured == ""` instead of returning `nil`.
  - Defense in depth in the operator (`lego/operator/internal/controller/app_controller.go:1145-1182` and `build_source.go:98-123`):
    - When `app.Spec.BuildSource != nil`, verify any `ActiveReleaseConfig().Image` against the linked build source's repository/image (or allow only an already-copied digest in `appIdentity(app).Repo()` for rollbacks/restarts, never an arbitrary external image outside the linked carrier).
