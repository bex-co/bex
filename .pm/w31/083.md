# 083 — `link_env_group` (and REST/GraphQL service & build-source link routes) materializes env-group secrets into workloads without `envgroups.values.view` (`env_group_values: read`)

Why: `envgroups.Service.linkFetched` (`lego/backend/internal/envgroups/service.go:1157-1164`) explicitly classifies linking an environment group to a service or build source as a sensitive secret read ("A link materializes every group value inside caller-controlled workload code"), yet `keyPermissionOps` (`lego/backend/internal/api/key_permission_ops.go:165,637,1082,1090`) omits `core.KeyEnvGroupsValues` (`envgroups.values.view`) and `authorizeGroupSensitiveFresh` (`envgroups/service.go:1928-1930`) never checks the API key grant — allowing a scoped API key without `env_group_values: read` to attach any secret env group to a workload it controls.

### Scoped API keys without `env_group_values: read` bypass secret-read denial via `link_env_group` (MCP, REST, GraphQL)

- **Severity:** blocker
- **Versions:** deployed pin `c767c1bbd9` (`9b91284a4a2e`, active on production during run; zero diff in `envgroups/service.go` or the affected `key_permission_ops.go` entries vs `origin/main` `0177bc40ad`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`
- **Context:** 2026-11-26, endpoints `/mcp` (`https://api.bex.co/mcp`) and REST `/v1/env-groups/{id}/services/{serviceId}`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), run-minted scoped API key with ONLY `env_groups: read_write` + `services: read_write` (zero `env_group_values`, zero `services_env`, zero `deploys_run`; revoked) + disposable web service `srv-dc41ek1m1rus738h0500` and disposable env groups `evg-dc41hsusfruc73ft2ci0` / `evg-dc41jresfruc73ft2d0g` (all deleted and verified `404`)
- **Repro:**
  ```sh
  # 1. With an All key, create a disposable env group holding a secret variable and a disposable web service.
  # 2. Mint a scoped API key with ONLY env_groups: read_write + services: read_write (NO env_group_values).

  # 3. Controls — direct secret read is masked/refused on the scoped key:
  python3 scripts/qa-mcp.py --key-file <evg-link.json> call get_env_group \
    '{"workspaceId":"tea-daif693dqjvc73e7as3g","id":"<evg-id>"}'
  # -> masked (keys only, no values)
  python3 scripts/qa-mcp.py --key-file <evg-link.json> call get_env_group_var \
    '{"workspaceId":"tea-daif693dqjvc73e7as3g","envGroupId":"<evg-id>","key":"QA_TOP_SECRET"}'
  # -> api_key_permission_denied: ... View environment group variable and secret file values

  # 4. Bypass — the exact same key links the secret env group to a caller-controlled service on MCP and REST,
  #    mounting the group's Kubernetes Secret values into the running container and triggering a rollout deploy:
  python3 scripts/qa-mcp.py --key-file <evg-link.json> call link_env_group \
    '{"workspaceId":"tea-daif693dqjvc73e7as3g","id":"<evg-id>","serviceId":"<srv-id>"}'
  python3 scripts/qa-mcp.py --key-file <evg-link.json> rest POST \
    "/v1/env-groups/<evg-id-2>/services/<srv-id>"
  ```
- **Expected / actual:**
  - **Expected:** Matching `envgroups/service.go:1157-1164` ("A link materializes every group value inside caller-controlled workload code, so it is a sensitive read even though the API response stays masked") and `scope_matrix_ops.go:600` (which already classifies `MCP link_env_group` as `core.OpClassSensitive` requiring `bex.sensitive`), linking an environment group to a service or build source must require `core.KeyEnvGroupsValues` (`envgroups.values.view` / `env_group_values: read`) on scoped API keys and refuse keys lacking it with `403 api_key_permission_denied`.
  - **Actual:**
    - Controls confirmed `get_env_group` returned only masked keys and `get_env_group_var` returned `api_key_permission_denied` (`View environment group variable and secret file values`).
    - Both MCP `link_env_group` (`200 OK {"ok": true}`) and REST `POST /v1/env-groups/{id}/services/{serviceId}` (`200 OK` with `"serviceLinks":[{"id":"srv-..."}]`) succeeded on the same key, mounting the env group's secrets into the workload and triggering rollout deploy `dep-dc41ht9m1rus738h05v0`. Because `services: read_write` also lets the key create or update a service's image/command, any key with `env_groups: read_write` + `services: read_write` (or `build_sources: read_write`) can exfiltrate every env-group secret in the workspace without `env_group_values: read`.

- **Attribution:** server (`lego/backend/internal/api`, `lego/backend/internal/envgroups`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go` omits `core.KeyEnvGroupsValues` on all four link entries:
    - `GQL Mutation.linkEnvGroup` (`key_permission_ops.go:165`): `{core.KeyEnvGroupsManage, core.KeyServicesManage}`
    - `MCP link_env_group` (`key_permission_ops.go:637`): `{core.KeyEnvGroupsManage, core.KeyServicesManage}`
    - `REST POST /v1/build-sources/{buildSourceId}/env-groups/{envGroupId}` (`key_permission_ops.go:1082`): `{core.KeyBuildSourcesManage, core.KeyEnvGroupsManage}`
    - `REST POST /v1/env-groups/{id}/services/{serviceId}` (`key_permission_ops.go:1090`): `{core.KeyEnvGroupsManage, core.KeyServicesManage}`
  - Meanwhile `envgroups.Service.authorizeGroupSensitiveFresh` (`lego/backend/internal/envgroups/service.go:1928-1930`) only calls `s.AuthorizeFreshOn(ctx, core.RelCanViewSensitive, core.WorkspaceObject(g.TenantID))` (which checks OpenFGA + OAuth `bex.sensitive`), never checking `core.KeyEnvGroupsValues` on scoped API keys. (Note: also verify `REST POST /v1/blueprints*` / `MCP deploy` / `sync_blueprint` if a blueprint links a pre-existing env group rather than creating a new one with values — Blueprint apply currently lists `KeyEnvGroupsValuesSet` without `KeyEnvGroupsValues`; check whether linking an existing pre-populated group via Blueprint should also check `KeyEnvGroupsValues` inside `linkFetched`.)
- **Fix:**
  - Add `core.KeyEnvGroupsValues` to `keyPermissionOps` (`lego/backend/internal/api/key_permission_ops.go:165,637,1082,1090`) for all four link operations:
    - `GQL Mutation.linkEnvGroup` → `{core.KeyEnvGroupsManage, core.KeyEnvGroupsValues, core.KeyServicesManage}`
    - `MCP link_env_group` → `{core.KeyEnvGroupsManage, core.KeyEnvGroupsValues, core.KeyServicesManage}`
    - `REST POST /v1/env-groups/{id}/services/{serviceId}` → `{core.KeyEnvGroupsManage, core.KeyEnvGroupsValues, core.KeyServicesManage}`
    - `REST POST /v1/build-sources/{buildSourceId}/env-groups/{envGroupId}` → `{core.KeyBuildSourcesManage, core.KeyEnvGroupsManage, core.KeyEnvGroupsValues}`
  - Defense-in-depth in `envgroups.Service.authorizeGroupSensitiveFresh` (`lego/backend/internal/envgroups/service.go:1928-1930`): also assert `core.KeyEnvGroupsValues` on scoped API keys (ensuring every path through `linkFetched` — including service links, build-source links, and any composite path that attaches an existing group — cannot materialize secret values without `envgroups.values.view`; exempt only internal/acting-tenant calls if appropriate, and update Blueprint apply `keyPermissionOps` if Blueprint sync links existing groups via `linkFetched`).
  - Surface impact: enforces the `env_group_values: read` boundary consistently across MCP, REST, and GraphQL without affecting `unlink_env_group` (unlinking does not reveal values).
