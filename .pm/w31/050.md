# 050 — `keyPermissionOps` maps five env-var/secret-file patch operations (`patch_service_environment`, `patch_env_group_environment`, `PATCH /v1/services/{id}/environment`, and GraphQL twins) to `projects.move` instead of `services.env.set` / `envgroups.values.set`

Why: `lego/backend/internal/api/key_permission_ops.go:168-169,699-700,1044` maps `patch_service_environment`, `patch_env_group_environment`, `PATCH /v1/services/{id}/environment`, `Mutation.patchServiceEnvironment`, and `Mutation.patchEnvGroupEnvironment` to `core.KeyProjectsMove` ("Move resources into or out of an environment") instead of `core.KeyServicesEnvSet` / `core.KeyEnvGroupsValuesSet` — allowing a scoped API key holding only `projects: read_write` to modify service and environment-group environment variables and secret files across MCP, REST, and GraphQL, while refusing scoped keys that hold `services_env: read_write` and `env_group_values: read_write`.

- **Attribution:** server (`lego/backend/internal/api`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go` conflated "environment" (runtime env vars and secret files) with "Environment" (project `evm-…` membership) on five entries:
    - Line `168`: `"GQL Mutation.patchEnvGroupEnvironment": {core.KeyProjectsMove}` (calls `envgroups.Service.PatchEnvironment`, `envgroups/graphql.go:296`).
    - Line `169`: `"GQL Mutation.patchServiceEnvironment": {core.KeyProjectsMove}` (calls `secrets.Service.PatchEnvironment`, `secrets/graphql.go:226`).
    - Line `699`: `"MCP patch_env_group_environment": {core.KeyProjectsMove}` (calls `envgroups.Service.PatchEnvironment`, `envgroups/mcp.go:203`).
    - Line `700`: `"MCP patch_service_environment": {core.KeyProjectsMove}` (calls `secrets.Service.PatchEnvironment`, `secrets/mcp.go:121`).
    - Line `1044`: `"REST PATCH /v1/services/{id}/environment": {core.KeyProjectsMove}` (calls `secrets.Service.PatchEnvironment`, `secrets/rest.go:79`).
  - Meanwhile, `REST PATCH /v1/env-groups/{id}/environment` (`key_permission_ops.go:1028`, `envgroups/rest.go:169`) actually calls `MoveEnvGroup`, so `{core.KeyProjectsMove}` is accurate there; `REST PATCH /v1/env-groups/{id}/contents` (`key_permission_ops.go:1027`, `envgroups/rest.go:162`) calls `PatchEnvironment` and is already mapped to `{core.KeyEnvGroupsValuesSet}`.
- **Fix:**
  - In `lego/backend/internal/api/key_permission_ops.go`:
    - Change `"GQL Mutation.patchEnvGroupEnvironment"` (`:168`) and `"MCP patch_env_group_environment"` (`:699`) from `{core.KeyProjectsMove}` to `{core.KeyEnvGroupsValuesSet}` (matching `"REST PATCH /v1/env-groups/{id}/contents"` at `:1027`).
    - Change `"GQL Mutation.patchServiceEnvironment"` (`:169`), `"MCP patch_service_environment"` (`:700`), and `"REST PATCH /v1/services/{id}/environment"` (`:1044`) from `{core.KeyProjectsMove}` to `{core.KeyServicesEnvSet}` (matching all other service env-var/secret-file write operations; coordinate with `w31/051` for `bds-…` targets on MCP/GraphQL).
    - Keep `"REST PATCH /v1/env-groups/{id}/environment"` (`:1028`) as `{core.KeyProjectsMove}` because that route invokes `MoveEnvGroup`.
  - Surface impact: aligns MCP, REST, and GraphQL scoped API key authorization with the documented permission catalog and sibling env-var/secret-file verbs; no wire schema or UI change.
- **Blast radius:** `lego/backend/internal/api/key_permission_ops.go` and scoped-key authorization tests in `lego/backend/internal/api/`. Any caller using a `projects: read_write` key to patch service/env-group env vars was relying on an unintended permission mismatch; callers with `services_env: write|read_write` and `env_group_values: write|read_write` gain the documented access.
