# 045 — `notifications.Service` reads and writes `notification_settings` by `id.Subject` verbatim, so API keys silently read defaults and write dead rows that `ListNotifyRecipients` can never email

Why: `lego/backend/internal/api/key_permission_ops.go:603,769` explicitly grants API keys access to `get_notification_settings` (`workspace.notifications.view`) and `update_notification_settings` (`workspace.notifications.manage`) across MCP, REST, and GraphQL, yet `notifications.Service.GetSettings` (`lego/backend/internal/notifications/service.go:463`), `UpdateSettings` (`:493`), `GetPushSettings` (`:609`), `UpdatePushSettings` (`:652`), push subscriptions (`subscriptions.go:202,215`), and push inbox (`inbox.go:161,180`) key directly on `id.Subject` — which for an API key is the key's Hydra client UUID rather than its human creator — even though `store.ListNotifyRecipients` (`lego/backend/internal/store/notifications.go:122-130`) filters `WHERE m.kind = 'user'` because "an API key's binding has no mailbox".

### API-key calls to `get_notification_settings` / `update_notification_settings` operate on a dead phantom row keyed by the API key's client UUID

- **Severity:** major
- **Versions:** deployed pin `8b9d780f45` (`cdaa0a248615`, active on production during run; zero diff in `lego/backend/internal/notifications/` and `lego/backend/internal/store/notifications.go` vs `HEAD` `4d6c50f9ad`); `serverInfo`: `bex 0.1.0`; negotiated MCP protocol: `2025-06-18`; Render MCP pin: `render-oss/render-mcp-server@a18ef3ee866716933710fa5054323fd5c1ed0eb1`
- **Context:** 2026-11-25, endpoints `/mcp` (`https://api.bex.co/mcp`), REST `GET /v1/notification-settings`, and GraphQL `notificationSettings`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), run-minted `All` and scoped read-only API keys (revoked after run) + QA user's Kratos session (logged out)
- **Repro:**
  ```sh
  # 1. Scoped API key without workspace.notifications.* is explicitly told to grant those catalog permissions:
  python3 scripts/qa-mcp.py --key-file <ro-key.json> call get_notification_settings '{"workspaceId":"tea-daif693dqjvc73e7as3g"}'
  python3 scripts/qa-mcp.py --key-file <ro-key.json> call update_notification_settings '{"workspaceId":"tea-daif693dqjvc73e7as3g","deployStarted":false,"deploySucceeded":false,"deployFailed":true}'

  # 2. All-permissions API key (or a key granted workspace.notifications.view/manage) calls the same tools:
  python3 scripts/qa-mcp.py --key-file <all-key.json> call get_notification_settings '{"workspaceId":"tea-daif693dqjvc73e7as3g"}'
  python3 scripts/qa-mcp.py --key-file <all-key.json> rest GET '/v1/notification-settings?ownerId=tea-daif693dqjvc73e7as3g'
  python3 scripts/qa-mcp.py --key-file <all-key.json> graphql 'query { notificationSettings(ownerId: "tea-daif693dqjvc73e7as3g") { deployStarted deploySucceeded deployFailed } }'
  ```
- **Expected / actual:**
  - **Expected:** Either:
    - an attributed API key resolves its human creator via `s.KeyCreator(ctx)` so `get_notification_settings` / `update_notification_settings` actually read and update the creator's own `(tenant_id, human_subject)` preferences (matching `GET /v1/users` and `key_permission_ops.go`'s `workspace.notifications.*` grants), OR
    - personal member notification/push-preference verbs explicitly refuse machine/API-key callers (and `key_permission_ops.go` stops advertising `workspace.notifications.view`/`manage` for them, reserving those permissions for the workspace-level `owner_notification_settings` verbs).
  - **Actual:**
    - Scoped keys are told to grant `"View notification settings"` / `"Update notification settings"`.
    - Once granted (or with an `All` key), `GetSettings` queries `notification_settings WHERE tenant_id = $1 AND subject = <api-key-uuid>`, misses the human creator's row, and silently returns `defaultSettings` (`{deployStarted: false, deploySucceeded: false, deployFailed: true}`).
    - `UpdateSettings` inserts/updates a dead orphan row `(tenant_id, <api-key-uuid>, ...)` in `notification_settings`. That row never alters the human creator's preferences and is permanently ignored by `ListNotifyRecipients` (`WHERE m.kind = 'user'`, `store/notifications.go:130`).
    - The same `identity.Subject` keying affects `GetPushSettings`, `UpdatePushSettings`, `subscriptions.go` (device/web-push subscriptions), and `inbox.go` (push notification inbox).
- **Wire evidence:**
  - Scoped key `MCP get_notification_settings` (`rndr-id: 8d26a8fb-37e9-215f`) → `isError: true`: `"api_key_permission_denied: this API key is not granted the permission this request needs: View notification settings"`.
  - Scoped key `MCP update_notification_settings` (`rndr-id: deef3403-5550-6ab9`) → `isError: true`: `"api_key_permission_denied: this API key is not granted the permission this request needs: Update notification settings"`.
  - `All` key `MCP get_notification_settings` (`rndr-id: 194f7367-b6da-f1d4`), `REST GET /v1/notification-settings` (`rndr-id: 9c1e2c0d-9480-dd1d`), `GraphQL notificationSettings` (`rndr-id: 07e54a60-ed13-5521`) → `200`, `{"deployFailed":true,"deployStarted":false,"deploySucceeded":false}` (always hits `store.ErrNotFound` for the freshly minted key UUID and returns `defaultSettings`).
- **Attribution:** server (`lego/backend/internal/notifications`, `lego/backend/internal/api`)
- **Root cause:**
  - `notifications.Service.GetSettings` (`lego/backend/internal/notifications/service.go:459-463`) and `UpdateSettings` (`:489-493`) pass `id.Subject` straight into `s.Store.GetNotificationSettings` / `UpsertNotificationSettings`, with no `s.KeyCreator(ctx)` lookup and no machine-caller guard.
  - `GetPushSettings` (`service.go:605-609`), `UpdatePushSettings` (`:640-652`), `subscriptions.go:198-215`, and `inbox.go:157-180` do the exact same raw `identity.Subject` lookup/write.
  - Meanwhile `store.PGStore.ListNotifyRecipients` (`lego/backend/internal/store/notifications.go:122-130`, fixed in `w5/m103`) explicitly joins `tenant_members m WHERE m.tenant_id = $1 AND m.kind = 'user'`, so any row written under an API key's Hydra client UUID (`kind = 'machine'`) can never be fanned out to any email or push recipient.
  - `lego/backend/internal/api/key_permission_ops.go:603,769` (and REST/GraphQL entries for `/v1/notification-settings` and `notificationSettings`/`updateNotificationSettings`) maps them to `KeyWorkspaceNotifications` / `KeyWorkspaceNotificationsManage`, explicitly inviting API keys to call them.
- **Fix:**
  - Add a shared caller-subject helper on `notifications.Service`:
    - For personal deploy-email settings (`GetSettings`, `UpdateSettings`): resolve an attributed API key's human creator via `s.KeyCreator(ctx)` (failing closed on lookup error, and refusing an unattributed legacy key with no creator) so an agent operating with a user's workspace API key reads and updates that user's real `(tenant_id, creator_subject)` row — which `ListNotifyRecipients` actually reads.
    - For native-push settings/subscriptions/inbox (`GetPushSettings`, `UpdatePushSettings`, `subscriptions.go`, `inbox.go`): either apply the same attributed-creator resolution or explicitly refuse machine/API-key callers (push device tokens and web-push browsers are per-human-session surfaces; refusing API keys on device/web-push subscriptions while resolving creator on `GetSettings`/`UpdateSettings` avoids orphaned rows in both tables).
  - Clean up or ignore any existing `notification_settings` rows whose `subject` is a machine binding (`kind = 'machine'`).
  - Surface impact: aligns MCP (`get_notification_settings`, `update_notification_settings`), REST (`GET/PUT /v1/notification-settings` and push routes), GraphQL (`notificationSettings`, `updateNotificationSettings`), and deploy email fan-out (`ListNotifyRecipients`).
- **Blast radius:** `lego/backend/internal/notifications/{service,subscriptions,inbox}.go` and tests; workspace-level `GetOwnerSettings`/`UpdateOwnerSettings` (keyed only on `tenantID`, not `subject`) are unaffected.
- **Regression checks:**
  - Unit + real-DB tests proving:
    1. A human member updates deploy-notification settings in a workspace; an attributed API key minted by that member reads back the same non-default values via `GetSettings` (MCP, REST, GraphQL), updates them via `UpdateSettings`, and both the human member's next `GetSettings` and `ListNotifyRecipients` reflect the updated values.
    2. An unattributed machine credential without a human creator cannot write an orphan `notification_settings` row.
    3. Push subscription/inbox verbs never store or query rows under an API key's Hydra client UUID.
