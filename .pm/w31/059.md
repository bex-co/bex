# 059 — Scoped `projects: read_write` API keys permanently delete arbitrary services, Postgres databases, and Key Value stores via cascading `delete_environment` and `delete_project` on MCP and GraphQL

Why: `lego/backend/internal/api/key_permission_ops.go:131,133,546,549` maps MCP `delete_environment`/`delete_project` and GraphQL `deleteEnvironment`/`deleteProject` solely to `{core.KeyProjectsManage}`, while `environments.Service.Delete` (`environments/service.go:1141-1209`) and `projects.Service.Delete` (`projects/service.go:605-688`) cascade directly into `s.Services.Delete`, `s.PostgresDeleter.DeletePostgres`, and `s.KeyValueDeleter.DeleteKeyValue` without checking `s.KeyGrantAllows` for `services.manage`, `postgres.manage`, or `keyvalue.manage` — letting a `projects: read_write`-only key (with zero `services`, `postgres`, or `key_value` grants) move any workspace resource into a disposable environment via `update_environment` (`projects.move`) and permanently destroy it.

- **Attribution:** server (`lego/backend/internal/environments` and `lego/backend/internal/projects`)
- **Root cause:**
  - `lego/backend/internal/api/key_permission_ops.go:131,133,546,549` maps `GQL Mutation.deleteEnvironment`, `GQL Mutation.deleteProject`, `MCP delete_environment`, and `MCP delete_project` solely to `{core.KeyProjectsManage}`.
  - Unlike REST `DELETE /v1/environments/{id}` (`environments/rest.go:222`) and `DELETE /v1/projects/{id}` (`projects/rest.go:211`), which call `DeleteIfEmpty` and reject occupied containers with `409`, MCP and GraphQL call `environments.Service.Delete` (`environments/service.go:1141-1210`) and `projects.Service.Delete` (`projects/service.go:605-688`), which invoke `s.Services.Delete`, `s.PostgresDeleter.DeletePostgres`, and `s.KeyValueDeleter.DeleteKeyValue` directly in-process — bypassing the API dispatch gate `requireKeyGrant` completely. Neither service checks `s.KeyGrant(ctx)` before cascading into those deleters.
- **Fix:**
  - Add a preflight helper (using `s.KeyGrant(ctx)` and `core.NewKeyPermissionDeniedError(missing)`) in both `environments.Service.deleteEnvironment` (`environments/service.go:1170`, when `deleteServices == true`) and `projects.Service.deleteProject` (`projects/service.go:618`, when `deleteServices == true`) **before** any member deletion or membership clear:
    1. Enumerate the member services (`doomed`), Postgres databases, and Key Value stores belonging to the environment/project (matching the exact sets about to be deleted).
    2. Build the required action slice: `core.KeyServicesManage` if `len(doomed) > 0`, `core.KeyPostgresManage` if any Postgres member exists (when `PostgresDeleter != nil`), and `core.KeyKeyValueManage` if any Key Value member exists (when `KeyValueDeleter != nil`).
    3. If `!grant.All`, check every required action against `grant` and return `core.NewKeyPermissionDeniedError(missing)` before touching any resource.
  - Deleting an empty environment or project (or an environment holding only env groups, which are detached rather than deleted) still requires only `projects: read_write` (`core.KeyProjectsManage`), and human callers / `All` keys are unaffected.
  - Surface impact: protects MCP (`delete_environment`, `delete_project`) and GraphQL (`deleteEnvironment`, `deleteProject`) uniformly; REST (`DeleteIfEmpty`) already refuses occupied containers with `409`.
