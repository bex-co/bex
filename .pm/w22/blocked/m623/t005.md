## Objective

On production one user runs 600 sandbox execs inside a minute with none refused, and w22/m443 resumes by itself once production carries the fix.

## Context

- `scripts/measure-sandbox-rate.sh`, run by `gh workflow run sandbox-measure.yml -f leg=rate`, sends `BEX_MEASURE_RATE_EXECS` (600) execs in waves of `BEX_MEASURE_RATE_EXEC_PARALLEL` (20). Each wave waits for its slowest exec, so 30 waves have to finish in 60 s. If the check fails only on time, its own message says to raise the parallelism.
- w22/m443's line in `.pm/w22/README.md` and its `blocked/m443/README.md` say its gate is this milestone. Its worker names the commit as the gate.
- Run 45279460837 (2026-11-23, pin `9fdf7e0a1171`) is the baseline: 206 of 600 redeems answered 400, and the 600 took 76 s.

## Steps

1. Once t001–t004 and t006–t008 are on `origin/main`, write the gateway and bex-api fix commit into w22/m443's BLOCKED line as ``pin must carry `<sha>` ``, replacing "on w22/m623". Then park this milestone in `blocked/` with the same gate, and ship both board changes.
2. When production's pin carries it, run `gh workflow run sandbox-measure.yml -f leg=rate` and read its `MEASURE` lines. Record the run id, the pin, the exec count, the seconds, the refusals by status, and `bex_ssh_gateway_limit_rejections_total` by scope before and after, in this README and in w22/m443's.
3. If the run fails, find out why before changing anything: a refusal from the gateway means t001's bound, a time failure with no refusal means the leg's parallelism, and anything else is its own item.
