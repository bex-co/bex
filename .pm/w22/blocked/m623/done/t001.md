## Objective

A sandbox exec or file stream no longer spends the SSH session limiter. It takes a slot from a sandbox stream limiter of its own, whose per-identity bound lets Render's 1,000-a-minute `exec` and `files` classes bind first. Native SSH, the web shell and agent attach keep `BEX_SSH_MAX_SESSIONS` 100 and `…_PER_IDENTITY` 5, and sandbox streams no longer take those 100 slots.

## Context

- `lego/backend/cmd/ssh-gateway/main.go:218` builds one `sshgateway.NewSessionLimiter` and hands it to `nativessh.Server`, `webshell.Server`, `sandboxsse.Server`, the sandbox file server (`sandboxfilegateway.Server`) and agent attach.
- `sandboxsse.go:126` acquires `claims.Subject`. `sandboxfiles.go:118` acquires `c.LimitKey(sandboxexec.SystemSubject)`, so bex-api's own platform transfers (agent-session uploads, `agent_files.go`) and the Completer's reads (`reachability.go:54`) share one system subject.
- The `active_sessions` gauge brackets the shared limiter's slot ("how close is the process to `BEX_SSH_MAX_SESSIONS`"), and `limit_rejections_total{scope}` reads `global` or `identity` (`internal/sshgateway/metrics.go`). Production's dashboards and alerts read both.
- Sandbox exec runs through the `DrainingExecutor` (`BEX_SSH_DRAIN_BUFFER_PER_CHANNEL` 64 MiB, `…_TOTAL` 128 MiB). A spent total falls back to unbuffered backpressure (`drain.go:37`), so it does not refuse. The gateway pod's limits are 500m CPU and 512Mi (`lego/operator/config/ssh/deployment.yaml`).
- Render documents no concurrency limit on commands or transfers (render.com/docs/sandboxes-limits, read 2026-11-23). The w22/m443 run measured about 1.9 s a slot for `true`. A command that runs for its full timeout holds a slot far longer.

## Steps

1. Add the sandbox stream limiter in `main.go` (a second `SessionLimiter`, or a scope on the existing type if that reads better) and pass it to `sandboxsse.Server` and the file server only. Name its variables in the `BEX_SANDBOX_…` or `BEX_SSH_…` family the code already uses, read with `intEnv`.
2. Size it. The parity-sufficient choice is no per-identity bound below what Render's per-minute classes imply, plus a process-wide bound that protects the pod's memory and CPU. Measure what one stream costs (a `true` exec and a streaming one) on a local gateway or from the kube exec path, and write the numbers and the chosen defaults into the task. A per-identity bound kept as an abuse control is bex's own and goes to ADR018 as a divergence awaiting sign-off (t004). The variant without it is then filed as its own item.
3. Keep the system subject from starving users and users from starving it: decide its key (for example, the platform subject gets a bound of its own) and say why.
4. Give the new limiter its own metric scope or label, so `limit_rejections_total` and the active gauge still tell SSH sessions and sandbox streams apart. Update any alert or dashboard that reads them.
5. Tests in `sandboxsse` and `sandboxfiles` (and one in `cmd/ssh-gateway` if the wiring is only visible there): more than 5 concurrent exec streams and file transfers for one subject are served, the new bound refuses with 429 at its edge, and a sixth native SSH session and a sixth web shell for the same subject are still refused.

## Result (2026-11-24)

- **The limiter.** `sshgateway.SandboxStreamLimits` (`lego/backend/internal/sshgateway/limiter.go`): two `SessionLimiter` pools, callers and platform, behind one `Admit(metrics, key, platform)` that returns the stream's end (it frees the slot and records `sessions_total`/`session_duration_seconds` once, however often it is called). `sandboxsse` and `sandboxfiles` take it as their `Limits`; native SSH, the web shell and agent attach keep the session limiter, and the types keep a sandbox server from being handed it. `gatewayLimits` in `cmd/ssh-gateway/main.go` builds both from `intEnv`.
- **Defaults.** Callers: `BEX_SANDBOX_MAX_STREAMS` 100 per replica, `BEX_SANDBOX_MAX_STREAMS_PER_IDENTITY` defaulting to the pool, so no per-identity bound below it (the parity-sufficient choice). Platform: `BEX_SANDBOX_MAX_PLATFORM_STREAMS` 32, `…_PER_KEY` 5.
- **The system subject (step 3).** A ticket whose subject `sandboxexec.PlatformSubject` names (the Completer's reads under `system:agent-session-completer`, the command probe under `system:sandbox-command-probe:<ws>`) and a platform file copy (keyed per session by `Claims.LimitKey`) take the platform pool, 5 per key as before. Users cannot starve the Completer, and the Completer cannot take users' slots; neither takes native SSH's.
- **Per-stream cost it rests on.** Measured on a throwaway kind cluster (`kindest/node:v1.36.1`, deleted afterwards) with a program that ran the gateway's own `sandboxsse` handler, `DrainingExecutor` (64 MiB / 128 MiB) and `KubeExecutor` against a pod there, the client in a child process: a held `sleep` stream kept 1.32 to 1.39 MiB of heap and stack and 22 goroutines, the same at 100, 250 and 500 held (a heap profile at 100 put 98 of 135 MB in `compress/flate.NewWriter`, SPDY's header compressor); 600 `true` execs at 20 parallel took 3.3 to 3.6 ms of gateway CPU each; 20 streams of 50 MB took 4.97 s of CPU for 959 MiB, about 5 ms a MiB, with heap peaking at 52 MiB. Production's gateways sat at 16 and 23 MiB idle (`kubectl top`, 2026-11-24).
- **Why 100 and not more.** At the bounds, 100 SSH sessions and 132 sandbox streams hold about 320 MiB beside the 128 MiB drain buffer and 64 MiB of archive indexes, about 535 MiB live, so t003 raises the pod's limit to 768Mi (`GOMEMLIMIT` 700MiB). A larger pool needs a cheaper stream: the WebSocket executor measured 0.28 to 0.30 MiB a held stream, filed as w22/036. The capacity bound one user can reach within Render's rates is ADR018's divergence awaiting sign-off, filed as w22/035 with the parity-sufficient and the stricter variants.
- **Metrics (step 4).** `limit_rejections_total{scope}` reads `sandbox_global`, `sandbox_identity`, `sandbox_platform_global`, `sandbox_platform_identity`; `bex_ssh_gateway_active_sandbox_streams{pool=caller|platform}` is new, and `active_sessions` no longer counts sandbox streams. No alert reads either metric; t003 adds the gauge to the Grafana panel, whose rejection panel groups by scope already.
- **Tests.** `TestOneCallerHoldsMoreThanFiveExecStreams` (8 streams of one subject served, the ninth 429 `sandbox_global`, platform subjects admitted behind a full caller pool, then refused at their own edge), `TestOneCallerHoldsMoreThanFiveTransfers` (8 uploads and downloads, the ninth 429, a platform copy admitted), `TestSandboxStreamsDoNotSpendSSHSessionSlots` in `cmd/ssh-gateway` (100 sandbox streams of one subject held while its sixth SSH session, the limiter the web shell shares, is refused, and the 100 session slots stay whole), `TestSandboxStreamLimitsReadTheirEnvironment`, `TestSandboxStreamPools`, `TestSandboxStreamPerIdentityBound`. `go test ./internal/sshgateway/... ./cmd/ssh-gateway/...` and `make lint` pass.
