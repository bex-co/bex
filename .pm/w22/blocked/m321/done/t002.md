## Objective

Add `Creds.EnsureSandboxMeterCreds`: idempotently provision the reader (`bex-sandbox-meter`, `read` on `snapshots/**`) and the reaper (`bex-sandbox-reaper`, `read` + `delete` on `snapshots/**`).

## Context

- Mirror `EnsureSnapshotCreds` (`lego/operator/internal/registry/snapshot_creds.go`): `ensureHTPasswdEntry`, `ensureZotConfigEntry`, `tryBounce` on any write. The Secret uses the placement t001 chose, with keys `reader-username`, `reader-password`, `reaper-username`, `reaper-password` (or as t001 decides).
- The reader must never hold `delete`; neither user may reach any repository outside `snapshots/`.

## Steps

1. Write the ensure function with a self-healing Secret (a missing or empty password regenerates and re-syncs its htpasswd hash).
2. Tests beside `snapshot_creds_test.go`: both Secret pairs, both htpasswd entries, the exact ACL actions and scope, idempotence (a second run writes nothing and does not bounce), regeneration after the Secret is deleted, and that `bex-builder` and the per-namespace `snap-*` users survive.

## Acceptance criteria

- [ ] The reader's ACL has `read` only and the reaper's has `read` and `delete`, both scoped to `snapshots/**`
- [ ] A second run is a no-op

## Out of scope

## Result — 2026-11-10

`Creds.EnsureSandboxMeterCreds` (`lego/operator/internal/registry/sandbox_meter_creds.go`): a self-healing Opaque Secret with a generated password per user, an htpasswd entry for each, and `grantZotRepoUser` for the ACLs. **A bug the tests caught first:** `ensureZotConfigEntry` replaces a repository's policy, so the second user erased the first and every run rewrote the config; two users on one pattern need per-user policies, which `grantZotRepoUser` provides. Tests: the reader has `read` only, the reaper `read` and `delete`, neither can push, the users appear on no pattern but `snapshots/**`, `bex-builder` and the per-namespace `snap-*` users survive; a second run rewrites nothing; a Secret that lost a password or was deleted heals with the htpasswd hash re-synced.
