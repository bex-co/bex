## Objective

Check that the change is consistent across every surface it exposes, and compare it with render.com's observable behavior; record drift as follow-up work instead of diverging silently.

## Context

- Surfaces: GraphQL (`setWorkspaceRequireTwoFactor`, `requireTwoFactor`), REST and MCP (no setter is expected: Render's REST has no workspace-mutation API, ADR018 "Workspace lifecycle" row), the dashboard Workspace Settings card, the audit-log read (REST `GET /v1/owners/{ownerId}/audit-logs` and GraphQL), the coded 403 on REST, GraphQL and MCP, and the SSH gateway.
- Render: [render.com/docs/login-settings](https://render.com/docs/login-settings) and the pinned `lego/backend/internal/api/openapi/render-public-api-1.json` (audit-log event enum `ChangeTeam2FAEnforcementEvent`; owner and member response shapes, including whether any field carries the setting).

## Steps

1. Re-read the Render page and the pinned OpenAPI; confirm the audit-log entry's `event` type and `data` shape match what bex returns.
2. Check the member response's `mfaEnabled` (Render's per-member `otpEnabled`, ADR024) is unchanged and still correct for a blocked member.
3. Compare the blocked member's experience with Render's description (resources and settings blocked; SSH and API keys blocked). Record any behavior Render has that bex lacks (and the reverse, such as the lock-out guard and the coded error, labeled as bex-owned).
4. Update the ADR018 row from t001 with what shipped and any drift; file each drift as an inbox note on a workstream (`/pm add`), never leave it implicit.
