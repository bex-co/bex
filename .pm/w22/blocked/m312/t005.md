## Objective

Prove or disprove that the Cilium allow-list and the platform floor still hold when `--net-raw` (and `--allow-packet-socket-write`) is on.

## Context

- Platform floor (ADR042, ADR104 D3): nodes, the Kubernetes API, the metadata endpoint, private ranges and other tenants stay closed under every policy.
- Allow-list semantics: HTTPS only, exact FQDN plus matching SNI, `*.example.com` covers one subdomain level.
- Per ADR104 D6, any success rules out the shared-pool option and the pool-wide option and leaves a separate pool or a signed divergence.

## Steps

1. Under an allow-list policy, attempt source-IP spoofing and ARP/NDP spoofing from inside the pod.
2. Reach a denied destination by crafting raw packets.
3. Bypass the FQDN/SNI allow-list through the nested Docker's own DNS resolver.
4. Probe each platform-floor target (node IP, API server, metadata, a private range, another tenant) from the Docker pod and from a container inside it.
5. Record each attempt and result; run once with only `--net-raw`, once with `--allow-packet-socket-write` too.

## Files

- Results go into the ADR104 D6 table (t007)

## Acceptance criteria

- [ ] Every attempt has a pass/fail with the command used
- [ ] Any bypass is reported to the user the same day, not buried in a table

## Out of scope

- Fixes or policy changes

## Blocked — 2026-11-10

Needs a Kubernetes node with Cilium and bex's allow-list policy; no isolation result exists for bex. The packet-crafting mechanics are in `scripts/sandbox-docker-spike.sh --isolation` and were exercised only locally with `--lab-no-cilium` (REACHED/BLOCKED, not an isolation result). What the local VM did show: with `--net-raw` the sandbox can send a raw IP packet with a forged source, and with `--allow-packet-socket-write` also forged ARP and Neighbor Advertisement frames (ADR104 D6, capability facts).
