# Sandbox groups: the optional project environment on "+ New > Sandbox Group"

Why: Render's dashboard lets a new sandbox group be placed in a project environment (render.com/docs/sandboxes-creating, read 2026-11-10), while bex always returns `environmentId: null` and offers no picker; recorded by w22/m311 t012 as the one Render dashboard drift.

- Render's pinned OpenAPI has a nullable `environmentId` on the group response but no `environmentId` on the create body (`create-sandbox-group` takes `ownerId`, `name`, `region`), so how the dashboard sets it is not visible in the pin. Read the live OpenAPI and the SDK first.
- bex has environments (ADR032, `evm-` ids). Decide what binding a group to an environment means for bex: which services or sandboxes it scopes, and who may see it.
- Not drift, checked: changing a group's concurrency limit is SDK/API only in Render's docs, so the dashboard showing the limit only at creation matches Render. A group list or detail page is not documented by Render either.
- Size: likely 1-2 hours plus a design question, so promote it with `/pm promote w22/003` when its turn comes.

## Blocked

Blocked 2026-11-10 (`/loopx w22`). Checked against Render's live API reference for `create-sandbox-group`: the request body is `ownerId`, `name` and `region` only; the response carries a nullable `environmentId` ("Environment this group is bound to"); no update endpoint is documented. So bex already matches the public contract, and how Render's dashboard sets the binding is not visible, which leaves any picker an invention. The parity-sufficient state is the current one (`environmentId: null`).
