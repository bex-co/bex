## Objective

Show on production that the limits are Render's: creates stop at 100 a minute and execs do not stop at 500.

## Context

- The weekly sandbox isolation matrix already runs against production as a disposable QA workspace; w22/m311 added its resume-429 probe and w22/m414 its `egress` leg. Add a leg there instead of a new workflow.
- The group concurrency limit also answers 429. Terminate each sandbox as it is created, or use a group whose limit is above 100, so the leg measures the rate limit; assert on the refusal's code, not only the status.
- Production deploys are batched: the leg can only pass after the deploy that carries t003 and t004.

## Steps

1. Add a `rate` leg: with two API keys of one user, send 101 creates inside a minute and expect exactly one rate-limit 429, then terminate everything it created.
2. In one running sandbox, run 600 short execs inside a minute and expect no rate-limit refusal.
3. Record the run id and the observed codes in the milestone README under "Production check".
4. If the deploy has not happened yet, park the milestone with that as the gate; do not close on local evidence.
