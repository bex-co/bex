## Objective

Write down Render's sandbox rate table as the contract, assign every bex sandbox operation to exactly one class, and settle the bucket key, before any code changes.

## Context

- Render's table (render.com/docs/sandboxes-limits, read 2026-11-16): create 100, terminate 1,000, execute 1,000, file or directory transfer 1,000, read sandbox and group resources 400, write group resources 100, capture a snapshot 10, all per minute, "per user, shared across that user's API keys", 429 over the limit.
- bex's general limiter: `lego/backend/internal/api/ratelimit.go` (subject bucket plus an optional workspace bucket), default 500 per minute (`lego/backend/cmd/api/config.go` ~line 770).
- Sandbox operations are listed in `lego/backend/internal/api/scope_matrix_ops.go` (REST, GraphQL and MCP entries) and mounted in `lego/backend/internal/sandbox/` (`rest.go`, `groups_surfaces.go`, `images_surfaces.go`, `connect.go`, `file_connect.go`, `graphql.go`, `mcp.go`).

## Steps

1. Re-read Render's page and record the table and the read date in ADR104 D7.
2. List every sandbox operation bex serves on REST, GraphQL and MCP and assign each a class. Decide and record the cases the table does not name: sandbox update and suspend or resume, image and build imports, deletes and reads, exec history reads, and the named refusals (snapshots, credentials).
3. Find where an exec and a file transfer are countable in bex-api: the run and file connect-token mints, or the request itself. One customer exec must spend one unit.
4. Settle the key: how the limiter resolves a session, an API key and an OAuth token to one user, so two keys of one user share a bucket.
5. Record the recommendations from the milestone README (sandbox routes leave the general budget; the workspace aggregate bucket stays above Render's table) as recommendations, with the sizing of the workspace bucket.
6. Add the ADR018 row, marked as not yet shipped.
