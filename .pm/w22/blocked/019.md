# Sandbox CPU: decide whether to bill the measured CPU divided by a gVisor overhead factor

Why: bex bills a sandbox's CPU as measured at the pod's cgroup, which under gVisor includes the sentry, so a customer pays about 10% more CPU-seconds than the same work uses on Render's Firecracker; ADR104 D8 names the subtraction as a separate follow-up.

From w22/m314 (2026-11-17), the variant ADR104 D8 and `/unblock w22` (2026-11-16, option 2) set aside. It blocks nothing: the measured CPU is billed from 2026-11-18T00:00:00Z.

- **What is measured (w22/m314 t001, 2026-11-15):** a pure CPU load read 1.098× its own CPU-seconds at the pod; an idle sandbox 0.45% of a core; a syscall-heavy thread read the pod's whole CPU quota (2.00 cores on `1c-2g`), so its true ratio is not known.
- **The variant:** `sandbox_cpu_seconds` × rate ÷ a factor (for example 1.1). One factor fits the CPU-bound case only; a syscall-heavy load still reads high.
- **What it needs before any code:** a measured factor with a runc reference (the reference pod was refused by PodSecurity `restricted` in `opensandbox-system`, so run it in a namespace that admits it), and the user's choice, since it changes what every sandbox customer pays. bex's rate is already 0.70 of Render's, so a unit of real work costs about 23% less than on Render without the factor.
- **Where it would go:** `pricing.yaml` `sandboxUsage` (a divisor beside the rates, not code), `pricing.rateFor`, the Stripe unit conversion (`Sheet.SandboxUsageWeightedUnits`), ADR030 §17 and ADR104 D8.
- **Done when:** the factor is measured and recorded in ADR104 D8, and the user has either chosen it (then it ships with a dated effective instant, like the switch) or declined it (then D8 says so and this note closes).

## Measured, then parked for the user's choice (2026-11-24, /loopx w22)

- **Verdict: blocked.** The factor is measured and recorded in ADR104 D8. What is left is the user's choice, which this note's own done-when names: it changes what every sandbox customer pays, and declining it is a decision too. Render parity does not gate it: a running sandbox is already billed on used CPU, as on Render, in every workspace.
- **How it was measured.** The `cpu` leg of `sandbox-measure.yml` now runs the same loads in the sandbox and in a plain runc pod on the same node, with the sandbox's image and its one-CPU limit, so both pods have the same quota (w22/020). The runc pod now carries what PodSecurity `restricted` requires, and `opensandbox-system` admitted it. Each load counts its own work, so the comparison is CPU per unit of work, not raw CPU-seconds: a load that fills the quota reads the same CPU-seconds in both pods. Shipped in `ada14ea352` and `0ca3ea981f`. The first run, [45396288630](https://github.com/bex-co/bex/actions/runs/45396288630), lost its sandbox to the 900 s idle suspension: `kubectl exec` is not activity bex-api sees.
- **The numbers** ([run 45400701235](https://github.com/bex-co/bex/actions/runs/45400701235), one `1c-2g` sandbox (disposable) and its runc reference on one gVisor node):

  | Load | gVisor sandbox | runc pod | Factor |
  | --- | --- | --- | --- |
  | One core of shell arithmetic, 10 × 60 s and 5 × 60 s | 599.58 pod CPU-seconds, 1.026× the load's own count; 217,866 loops per pod CPU-second | 295.94, 1.000×; 227,981 loops per CPU-second | **1.046 per unit of work** |
  | `dd bs=1`, one thread, 3 × 60 s each | 181.57 (the quota), 1.244× its own count; 51,118 bytes per pod CPU-second | 181.61 (the quota); 790,340 bytes per CPU-second | **15.5 per unit of work** |
  | Idle, 600 s | 2.08 CPU-seconds, 0.35% of a core | — | — |

- **How firm each figure is.** The CPU-bound overhead within one pod is stable: 1.026× its own count in both runs, 1.018× in run 45147416800. The cross-pod figure is not. The same sandbox load on the same node did 139,605 loops per CPU-second in the first run and 217,866 in the second, 30 minutes apart. So the 1.046 includes the node's load at the time, and the CPU-bound factor is between 1.02 and 1.05. The syscall figure is far outside that noise.
- **What this changes from the note's premise.** The about 10% (1.098×) dates from before w22/020, when the pod's quota was 2 cores and the sentry could add its CPU to a full core. At the plan's quota a CPU-bound load costs 2–5% more than under runc, below the ±5% line w22/m314 t001 fixed. At 0.70 of Render's rate that is about $0.086–0.088 per CPU-hour of work, against Render's $0.12. Syscall-dense work is where gVisor costs more: up to 15.5× the CPU per byte, so about $1.30 per runc CPU-hour of work at bex's rate. That is about 11× Render's price for the same work, if Firecracker runs syscalls near runc's speed, which is not measured. Such a load also runs 15.5× slower, because both pods are held to one core.
- **The choice for the user** (`/unblock w22`):
  1. **Decline** (the worker's recommendation, not a decision): ADR104 D8 keeps billing the measured CPU, and this note closes. No single divisor fits both loads. The CPU-bound one (1.02–1.05) is within the run-to-run noise. A divisor large enough for syscall-dense work would bill a CPU-bound hour at a fifteenth of its cost. The syscall cost is gVisor's speed, which a divisor cannot change; closing it is runtime work (the gVisor platform, or the runtime), and that would be its own item.
  2. **Adopt a divisor**, for example 1.026, the CPU-bound overhead within the pod. Every sandbox CPU charge drops about 2.5%. It ships with a dated effective instant in `pricing.yaml` `sandboxUsage`, `pricing.rateFor`, `Sheet.SandboxUsageWeightedUnits`, ADR030 §17 and ADR104 D8.
