# The used-CPU meter can bill more CPU than the sandbox pod's counter shows: read the counter without `increase()`'s extrapolation

Why: a sandbox is billed for used CPU since 2026-11-18, ADR104 D8 chose the pod's cgroup counter because a customer can reproduce it, and on production the meter read 307 CPU-seconds from a pod whose counter totalled 298.42; w22/m314 and w22/020 both wait on the usage leg that this fails.

Found by w22/m314's production check, 2026-11-21, [sandbox-measure run 44867679299](https://github.com/bex-co/bex/actions/runs/44867679299) (leg `usage`).

- **Symptom.** `FAIL: busy: metered CPU matches the pod-level counter (metered 307, pod counter moved 297.475 during the load and totals 298.42295)`. The interval ran 333 s (five 60 s one-core loops, then about 20 s idle, then a pause). The other 15 checks passed.
- **Cause (derived from the code and the figures; the raw samples were not read on production's Prometheus).** `PrometheusCPU.PodCPUSeconds` (`lego/backend/internal/sandbox/cpu_meter.go`) reads `sum(increase(sandbox_pod_cpu_usage_seconds_total{namespace,pod}[N s]))`. `increase()` takes the growth between the first and last sample in the window and extrapolates it to the window's edges at the window's average rate. A pod's last scrape is up to 15 s before it stops, so the tail is filled in at the average rate even when the sandbox was idle then: 298.42 × (1 + about 9 s ÷ about 310 s) ≈ 307. The code's comment calls the result "the counter's increase over (from, to]", which it is not.
- **Size.** At most about one scrape interval (15 s; the extrapolation stops at 16.5 s) times the interval's average cores, once per running interval, at its end; it is an under-read by the same bound when a sandbox is busier at the end than on average. At an hour boundary inside an interval the two sides cancel on average. In money: at most about $0.0004 per core per interval. On a 5-minute interval it is 2.9%, which is what the leg's bound (the counter's total × 1.02 + 2 s) catches; with this load the leg fails whenever the last scrape falls more than about 9 s before the pause, so it fails often, not always.
- **Precedent.** Egress met the same function: `ExactDelta` and `Billed` in `lego/backend/internal/egressquery/query.go` (w4/477, w6/m455), and ADR023 § New series count from zero. Billing windows there kept `increase()` on purpose, with a health gate; read that reasoning before choosing.
- **Fix to try.** Read each window as the counter's last value in it minus its last value before it, per series, with a series that starts inside the interval counted from zero (a pod's cgroup counter starts at zero with the pod) and a reset never going negative. Consecutive windows then add up to the pod's last scraped value: never above what the customer can read, and short by at most the last 15 s before the pod stopped. Decide what a scrape gap longer than the lookback does (defer, as a missing reading does today, not count from zero). If `increase()` is kept instead, say in ADR023 and ADR104 D8 that the figure is an estimate that can exceed the counter by one scrape interval at the average rate, and widen the leg's bound by exactly that: one or the other, with the reason.
- **Done when:** a test with a fake Prometheus shows a busy-then-idle interval reading no more than the counter's last value (it fails on today's query); `gh workflow run sandbox-measure.yml -f leg=usage -f usage_idle_seconds=600` prints PASS on production with the fix deployed; ADR023 § Sandbox CPU billed on use and ADR104 D8 describe the read as it is. w22/m314 (t003, t005, t009) and w22/020 need only that PASS: record the run id in both.
- **Not in scope:** re-pricing the three days already billed (the bound above is under a cent per sandbox).
