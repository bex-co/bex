# Deleting an environment or project that holds the workspace's default sandbox group: decide whether bex refuses it, as Render's dashboard does

Why: Render's dashboard refuses the delete ("Make another group the default first"), while bex deletes the environment and keeps the group in no environment, so the two products end in different states.

Found by w22/m603 t005, 2026-11-23, reading Render's dashboard bundle (entry `assets/index-9Nb9X1Dz.js`, no sign-in):

- The bundle has the refusal "This ${t} contains the default sandbox group. Make another group the default first.", where `${t}` is environment or project, on the environment and project delete flows.
- Whether the refusal comes from Render's API or only from its dashboard is not known. Render's environment object lists no groups, and the public OpenAPI documents no such error for `DELETE /environments/{id}` or `DELETE /projects/{id}`.
- **bex today.** `sandbox_groups.environment_id` is `ON DELETE SET NULL` (migration 0270, w22/m412), so the delete succeeds and the group reads `environmentId: null`. REST's `DeleteIfEmpty` (`lego/backend/internal/environments/service.go`) counts no groups, so an environment that holds only groups is not refused with `409 ENVIRONMENT_NOT_EMPTY`.
- [render-artifacts/sandbox-groups.md](../../docs/render-artifacts/sandbox-groups.md#the-project-environment) records this as unknown, not enforced.

Needs: find out whether Render's API refuses it, for example from a Render workspace or from a client that surfaces the error. Then either refuse the delete on every surface with Render's code and message (dashboard, GraphQL, MCP and REST), or record that only Render's dashboard refuses it and match that in bex's dashboard alone.

Done when: deleting an environment or project that holds the default group behaves as on Render on every surface where Render's behavior is known, and ADR018's sandbox groups row says which.
