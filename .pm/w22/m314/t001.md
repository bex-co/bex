## Objective

Measure whether cAdvisor's CPU series for a gVisor sandbox pod is accurate enough to bill on, and record one of three verdicts: pass, escalate to the user, or fail.

## Context

- The `kubernetes-cadvisor` Prometheus job lists every node (no filter), so the tainted sandbox pool is scraped; confirm the series exist with `pod` and `container` labels for sandbox pods (`deploy/gitops/base/prometheus.yaml`, job `kubernetes-cadvisor`).
- gVisor's sentry spends host CPU emulating syscalls, so a syscall-heavy workload may read higher than it would under runc; Render's Firecracker has no such cost (ADR104 D8).
- Policy from ADR104 D8: bill the measured cgroup CPU with no subtraction. Starting thresholds: pass within ±5% of one CPU-minute; escalate to the user if a syscall-heavy load reads more than 2× its runc figure or an idle baseline exceeds 2% of one core. This task fixes the final numbers before running and records why.

## Steps

1. Write down the final thresholds before any measurement.
2. Run `stress-ng` at one core for 60 s inside a gVisor sandbox on production; read `increase(container_cpu_usage_seconds_total)` for that pod.
3. Measure an idle sandbox's baseline over 10 minutes.
4. Run a syscall-heavy load in a sandbox and the same load in a plain pod on the same node type under runc; compare.
5. Record the verdict in ADR104 D8: pass → continue; escalate → park this milestone with the exact question for the user; fail → t004 takes the fallback branch.
