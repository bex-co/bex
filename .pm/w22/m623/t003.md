## Objective

Production runs t001's sandbox stream limiter at the values t001 chose, and the next reader finds its variables where the gateway's other bounds are listed.

## Context

- `lego/operator/config/ssh/deployment.yaml` sets `BEX_SSH_MAX_SESSIONS` "100" and `BEX_SSH_MAX_SESSIONS_PER_IDENTITY` "5" on 2 replicas, with 500m CPU and 512Mi. 128Mi of that is the drain buffer.
- `lego/backend/AGENTS.md` lists the gateway's bounds (the `BEX_SSH_MAX_SESSIONS` and `BEX_SSH_MAX_CHANNELS` rows).
- The Grafana panels for the gateway read `bex_ssh_gateway_active_sessions` and `limit_rejections_total` by scope (`deploy/gitops/base/values/grafana.values.yaml`).

## Steps

1. Add the new variables to the gateway Deployment with t001's defaults and a comment that says what they bound and why. Raise the pod's CPU or memory only if t001's measurement says the process-wide bound needs it.
2. Add a row for them to `lego/backend/AGENTS.md`, and say there that `BEX_SSH_MAX_SESSIONS[_PER_IDENTITY]` no longer covers sandbox streams.
3. If t001 changed the metric's scopes or added a gauge, show them in the Grafana panel.
4. Run `make test` (from `lego/operator/`) and any manifest or kustomize test that reads the Deployment.

## Files

- `lego/backend/AGENTS.md`
- `deploy/gitops/base/values/grafana.values.yaml` (if the metrics changed)
