## Objective

When the gateway refuses a sandbox stream for concurrency, the client gets Render's over-limit status: HTTP 429 with `Retry-After`, which the Render SDK reads as `RateLimitError` and the pinned CLI prints with its wait. Today it gets 400 `too many concurrent exec sessions`, which the SDK reads as `ClientError`.

## Context

- `mintAndDial` maps the gateway's 429 to `errExecSessionLimit` (`lego/backend/internal/sandbox/exec.go:361`), a `fmt.Errorf("%w: …", core.ErrBadRequest)` (`reachability.go:56`).
- `Transient` (`reachability.go:66`) treats `errExecSessionLimit` as a passing failure of a session read. That must still hold.
- `core.NewTooManyRequestsError(code, msg, params)` renders 429, and `WriteErr` sets `Retry-After` from `params["retryAfterSeconds"]` (`internal/core/http.go:354`). w22/m443's rate classes answer `rate_limited` with `Retry-After` and `RateLimit-*` (ADR104 D7 § API rate limits).
- The file redeem proxies the gateway's response (`internal/sandbox/file_connect.go`, the `httputil.ReverseProxy`), so the gateway's 429 `{"error":"session limit reached"}` reaches the client unchanged, without bex's envelope or `Retry-After`. `UploadAgentSessionFiles` retries a 429 itself (`agent_files.go:64`) and keeps doing so.
- Exec surfaces: the connect redeem (`ConnectStreamHandler` → `StreamExec`), the single-step `POST /v1/sandboxes/{id}/exec`, MCP's `sandbox_exec`, and the resume-wait path, where the SSE stream is already open and a failure is an SSE error event (`StreamExec`'s doc comment, w32/m299).
- `lego/backend/internal/sandbox/testdata/sdk-v1.10.0-contract.json` records that a 429 on a connect-token mint, exec stream or file transfer is Python's `RateLimitError`.

## Steps

1. Make `errExecSessionLimit` a coded 429 with `retryAfterSeconds` (a short fixed wait, or the gateway's own `Retry-After` if t001 sends one), with a message that says the user has too many sandbox commands or transfers running at once. Keep `errors.Is` working for `Transient`.
2. In the file redeem, turn the gateway's 429 into the same coded answer instead of passing its body through.
3. Check what the resume-wait SSE path and MCP's `sandbox_exec` show for it: the SSE error event carries the 429's code and message, and the MCP tool error names it as a rate limit the way w22/m443's `rate_limited:` errors do.
4. Tests for each surface: a gateway double that answers 429 gives the client 429 with `Retry-After` (REST redeem, single-step exec, file upload and download), the SSE error event (resume wait), and the MCP tool error. A session read still treats it as transient.
