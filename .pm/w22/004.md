# Sandbox group list and paging: the places bex's answers differ from Render's error vocabulary

Why: w22/m311 t008 (Render parity) found small differences in `GET /v1/sandbox-groups` and the group routes that are outside the milestone's scope but must not go unrecorded; the pinned OpenAPI `errorCode` vocabulary is the reference, and live Render behavior was not checked.

Found 2026-11-10, none fixed:

1. `GET /v1/sandbox-groups` without `ownerId` answers a codeless 400, and a repeated `ownerId` passes with the first value winning. Render's vocabulary has `invalid_owner_id`, though the pin does not tie it to this operation.
2. A `limit` outside 1..100 gives REST a codeless 400 (Render's vocabulary: `invalid_limit`), while GraphQL and MCP clamp. The three surfaces differ; this is repo-wide pagination policy, not groups only.
3. An unknown or malformed `cursor` returns an empty page; the vocabulary says `invalid_cursor` (400). Also repo-wide.
4. GraphQL and MCP group lists carry no cursor field, and the MCP description does not say the cursor is the last group's id. Harmless while a workspace has at most 10 groups and the default page is 20.
5. With the group cap turned off, `store.maxSandboxGroupsListed = 1000` truncates the list silently.
6. A non-member's `ownerId` answers 403 (the repo convention) where the pin lists 404 for create and list; the pin also lists a 409 on update that bex never returns.

Also open, to be settled by the production walk (w22/m311 t007): after a terminate the binding is released at once, so a sandbox OpenSandbox still lists as Running for a moment is counted under the default group.

Size: a few small fixes plus a decision on whether pagination errors should follow Render's vocabulary everywhere; promote it with `/pm promote w22/004` when its turn comes, and read Render's live API first.
