# The ssh-gateway's pods/exec streams over WebSockets: a held stream costs a fifth of the memory SPDY's does

Why: every exec stream the gateway holds (sandbox commands and transfers, native SSH, the web shell) keeps about 1.4 MiB of heap over SPDY, which is what sizes the sandbox stream pool at 100 per replica (w22/m623); client-go's WebSocket executor keeps about 0.3 MiB, so the same pod would carry about four times the streams.

From w22/m623 t001 (2026-11-24). Measured on a throwaway kind node (Kubernetes v1.36.1) through the gateway's own sandbox exec handler and `DrainingExecutor`, the client in another process (ADR104 D7 § Concurrent commands and transfers):

- **SPDY** (`remotecommand.NewSPDYExecutor`, `KubeExecutor` in `lego/backend/internal/sshgateway/exec.go`): 1.32 to 1.39 MiB of heap and stack and 22 goroutines per held stream, at 100, 250 and 500 held. A heap profile at 100 held puts 98 of 135 MB in `compress/flate.NewWriter`, the SPDY framer's header compressor. A `true` exec cost 3.3 to 3.6 ms of CPU.
- **WebSocket** (`remotecommand.NewWebSocketExecutor`, protocol `v5.channel.k8s.io`): 0.28 to 0.30 MiB and 11 goroutines per held stream, and 2.7 ms of CPU a `true` exec. Production's kube-apiserver is v1.34.9, which serves it.
- **The change.** `KubeExecutor` uses client-go's fallback executor (WebSocket first, SPDY when the server refuses the upgrade), keeping every exit-code, terminal-target and not-ready classification the transports rely on, with TTY resize for native SSH and the web shell. Then w22/035 can raise `BEX_SANDBOX_MAX_STREAMS`.
- **Done when:** a gateway test runs an exec over the WebSocket protocol and keeps the exit code, stdout and stderr apart and the terminal-target classification; the per-stream heap is measured again on a kind node and written in ADR104 D7; and native SSH and the web shell still resize a terminal.
