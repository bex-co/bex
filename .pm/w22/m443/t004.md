## Objective

A sandbox operation spends the same class bucket whichever surface carries it, and a refused call looks like the existing limiter's refusal on that surface.

## Context

- `lego/backend/internal/sandbox/graphql.go` and `mcp.go` expose the sandbox, group and image operations.
- The general limiter runs as HTTP middleware, so it sees one GraphQL POST or one MCP call, not the operation inside it. The class must be charged where the operation is known.
- The existing 429 writer is in `lego/backend/internal/api/ratelimit.go`.

## Steps

1. Charge the class in each GraphQL resolver and MCP tool for a sandbox operation, through one helper shared with REST.
2. Decide and record how the general budget treats a GraphQL or MCP request that contains only sandbox operations, so it matches REST's exemption as closely as the transport allows; write the residual difference into ADR104 if there is one.
3. Return the surface's own rate-limit error shape (GraphQL error with the existing code, MCP tool error) and keep `Retry-After` on the HTTP response where the transport has one.
4. Tests: create through REST 60 times and GraphQL 40 times, and the next create on MCP is refused.

## Files

- lego/backend/internal/sandbox/graphql.go
- lego/backend/internal/sandbox/mcp.go
- lego/backend/internal/api/ratelimit.go

## Acceptance criteria

- [ ] The cross-surface test passes: the three surfaces share one bucket per user and class.
- [ ] A refused GraphQL or MCP sandbox call carries the same error code as the existing limiter's refusal on that surface.

## Out of scope

- Dashboard changes: the dashboard has no sandbox flow that approaches these rates.
