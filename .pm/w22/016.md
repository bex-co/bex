# The sandbox build list answers Render's `invalid_limit` and `invalid_cursor`, as the group list does

Why: the pinned `list-sandbox-builds` documents `400 invalid_cursor` and `invalid_limit`, and bex's build list clamps a limit outside 1 to 100 and returns an empty page for any cursor (`docs/render-artifacts/sandbox-images.md`); w22/004 gave the REST group list those codes and left the build list on the repository's paging policy because the user's decision covered the group list. Found shipping w22/004, 2026-11-14.

- **Fix.** The same two pieces as the group list: `renderOperationRefusals["list-sandbox-builds"]["limit"]` in `lego/backend/internal/api/render_openapi.go` (the map already holds this operation's `status` refusal) answers `invalid_limit`, and a query check for a malformed cursor (not an `sbb-` id) answers `invalid_cursor`, next to `sandbox.ValidateGroupListQuery`. A well-formed cursor naming no build stays an empty page. GraphQL and MCP keep clamping.
- **Tests.** A table test beside `render_openapi_sandbox_groups_test.go`, mutation-checked; update the line in `docs/render-artifacts/sandbox-images.md` and the ADR018 row.
- **Size.** Under an hour.
