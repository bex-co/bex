## Objective

A group at its `concurrencyLimit` answers 429 on create and on resume, suspended sandboxes do not count, and lowering the limit never stops a running sandbox.

## Context

- Resume happens explicitly and implicitly: exec, upload and download each resume a suspended sandbox (w2/m278 t010), so all three paths must hit the same check.
- Render's defaults are targets, not capacity (ADR104 D7): 1,000 per group and 10 groups per workspace are configurable constants. If an env var is added, document it in `lego/backend/AGENTS.md` and mirror its name in `.env.example`.
- `lego/backend/internal/sandbox/idle.go` and `service.go` are where suspend and resume live.

## Steps

1. Implement one `admit(group)` check used by create and by every resume path; count only statuses t001 decided count.
2. Make it race-safe: count and admit under a transaction or advisory lock keyed by the group, so parallel creates cannot exceed the limit.
3. Enforce the per-workspace group cap (10) with the error t001 chose.
4. Return Render's 429 body shape through REST, and a matching named error for GraphQL and MCP.

## Files

- `lego/backend/internal/sandbox/service.go`, `idle.go`, `rest.go`
- `lego/backend/internal/store/sandbox_groups.go`
- `lego/backend/AGENTS.md` if a variable is added

## Acceptance criteria

- [x] With limit 2: the third create answers 429; after suspending one, a create succeeds; resuming it while two others run answers 429
- [x] Lowering the limit below the running count stops nothing
- [x] A parallel-create test never exceeds the limit

## Out of scope

- Per-workspace aggregate cap and egress alert (t006)
