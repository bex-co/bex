## Objective

Prove on a real cluster that the two matchers fit what kubelet and kube-state-metrics actually report when Zot is gone, not only the fixtures the promtool tests were written from.

## Context

- `scripts/mock-cluster.sh` brings up the local kind/CAPD cluster with the "Traefik edge + Zot + MinIO" substrate and checks "Zot registry on every node". It is pre-approved to run (AGENTS.md, 2026-09-09); it never touches production.
- **Never scale Zot on production.** This drill is local only.
- A tenant pod whose image is in Zot, restarted while Zot is down, fails its pull because tenant containers use `PullAlways` (`app_controller.go`, `tenantImagePullPolicy`).
- `scripts/alerts-verify.sh` shows how the repo stands up a throwaway Prometheus/Alertmanager from the pinned charts in a scratch namespace; the mock cluster may have no Prometheus or kube-state-metrics.
- Drill records live in `docs/drills/` (for example `2026-09-09-build-cache-enablement.md`). Record text and numbers only; no screenshots or raw dumps in git (`#NO-ARTIFACTS-IN-GIT`).

## Steps

1. Bring the local cluster up (`bash scripts/mock-cluster.sh`, then `bash scripts/mock-cluster.sh operator`), and deploy a Git-built-style App whose image is in Zot (`scripts/deploy-sample.sh`, or push a tiny image to Zot with the `bex-builder` credential the bring-up check uses).
2. `kubectl -n bex-registry scale statefulset/zot --replicas=0`. Note the time. Delete the App's pod. Record how long the new pod takes to show `ErrImagePull` and then `ImagePullBackOff`, and copy the exact `image` string and `waiting.reason` values from `kubectl get pod -o json`.
3. Compare those strings with the matchers in t001 and t002. If either does not match, fix the rule and its test in this task and say so in the record.
4. If the cluster has (or can cheaply get, per `alerts-verify.sh`) kube-state-metrics and Prometheus, load the rule pack and record whether `ZotRegistryNotReady` and `TenantRegistryImagePullFailing` reached `firing`, and when. If not, replay the two expressions with promtool over a fixture built from the real labels copied in step 2, and say plainly that the live firing was not observed.
5. Scale Zot back to 1, record the time to ready and that the pod pulled and became Ready, then write `docs/drills/<date>-registry-outage.md`.

## Files

- docs/drills/ (new `<date>-registry-outage.md`)
- deploy/gitops/base/rules/alerting_rules.yml and its `*_test.yml` only if step 3 finds a mismatch

## Acceptance criteria

- [ ] The drill record states the real `image` and waiting-reason labels, the observed timings, and whether the alerts fired live or against replayed fixtures.
- [ ] Zot is back at 1 ready replica on the local cluster and the App pod is Ready again.
- [ ] A matcher mismatch found in the drill is fixed with a failing-then-passing promtool case.

## Out of scope

- Any drill against production.
- Measuring a production Zot restart (t001 reads that from Prometheus, read-only).
