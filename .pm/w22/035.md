# Sandbox streams: the user signs off on, raises or replaces the ssh-gateway's 100 concurrent commands and transfers per replica

Why: Render documents no limit on how many sandbox commands or file transfers run at once, and since w22/m623 bex refuses a stream once one gateway replica's callers together hold 100, a divergence ADR018 lists as awaiting the user's sign-off.

From w22/m623 (2026-11-24). The milestone took sandbox streams off native SSH's 5 per user and 100 per replica and gave them a pool of their own, sized to what one replica's memory carries.

- **Where.** `BEX_SANDBOX_MAX_STREAMS` (100) and `BEX_SANDBOX_MAX_STREAMS_PER_IDENTITY` (default the pool) in `lego/operator/config/ssh/deployment.yaml`, read by `sessionLimits` in `lego/backend/cmd/ssh-gateway/main.go`; the row "Concurrent sandbox commands and file transfers" in `docs/ADR018/render-operation-omissions.md`; [ADR104 D7 § Concurrent commands and transfers](../../docs/ADR104-sandbox-render-parity.md#concurrent-commands-and-transfers-w22m623).
- **When it differs from Render.** One user keeping more than about 200 commands or transfers running at once on production's two replicas (Render's 1,000 a minute admits that for commands longer than about 12 s), or several users' long commands filling one replica's 100. The answer is 429 `rate_limited` with `Retry-After: 1`.
- **What it rests on.** A held exec stream keeps about 1.4 MiB of the gateway's heap over SPDY (measured 2026-11-24, ADR104 D7), and the pod's limit is 768Mi.
- **The choices.** Sign the 100 as a capacity divergence; raise it (with w22/036's cheaper stream, more memory or more replicas), which is the parity-sufficient direction; or add a per-user share of the pool (`BEX_SANDBOX_MAX_STREAMS_PER_IDENTITY` below the pool) so one user cannot fill a replica for everyone, which is stricter than Render.
- **Done when:** the ADR018 row carries the user's decision and its date, and the manifest matches it.
