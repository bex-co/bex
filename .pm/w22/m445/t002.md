## Objective

A table in the milestone README: for each SDK code, the situation that produces it, what bex answers there today, and the verdict.

## Context

- bex's sandbox error codes are constants in `lego/backend/internal/sandbox/` (for example `CodeImageInUse` in `images.go`, `CodeInvalidSandboxName`, the `SANDBOX_*` named refusals in `notoffered.go`, the group codes in `groups.go`). Some are Render's lowercase codes and some are bex's uppercase names.
- w22/004 and w22/016 already moved the list and paging refusals to Render's vocabulary (`invalid_owner_id`, `invalid_limit`, `invalid_cursor`).

## Steps

1. For each code in the fixture, find the bex code path for the same situation and record status and code.
2. Mark each row: same; different spelling; situation exists but bex answers a generic error; situation cannot occur on bex (say why and which milestone would make it occur).
3. Note every place a bex-named uppercase code answers where the SDK expects a Render code: the SDK would fall back to the generic `ClientError` there.
4. Write the table into the milestone README under "Code comparison"; it is the work list for t003 and t004. If t003 turns out much larger than 60 minutes, split it with `/pm add-task` instead of stretching it.
