# Pin sandbox `bash -c`, the list `limit` cap and the 40 GB filesystem with tests

Why: ADR104 gap 4. Three Render sandbox rules are described as shipped but no test pins them, so a refactor could break them unnoticed; the 40 GB figure may not be enforced at all.

- **Exec runs via `bash -c`.** Render's exec contract (render.com/docs/sandboxes-executing). Add a test in `lego/backend/internal/sandbox/exec_test.go` that a command with shell syntax (a pipe, `&&`) behaves as under `bash -c` and that a nonzero exit code is data, not an error.
- **List `limit` is capped at 100.** Render caps `limit` at 100 on `GET /sandboxes`. Add a test in `lego/backend/internal/sandbox/service_test.go` (or `rest.go`'s handler test) for 100 accepted, 101 clamped or refused as Render does (check the pinned OpenAPI `list-sandboxes` first).
- **40 GB writable filesystem per plan.** ADR104 D7 notes it is "not yet pinned by a test or an ephemeral-storage limit". A 2026-11-10 grep of `lego/backend/internal/sandbox/*.go` and `deploy/opensandbox/*.yaml` found no `ephemeral-storage` limit. Pin what exists with a test; if the sandbox pod has no limit, add one to `deploy/opensandbox/batchsandbox-template.yaml` and record it in ADR018's plan row and ADR104 D7.

Est. about 1h, so an inbox note rather than a milestone. Not covered by w32/m284 (its tasks are the SDK walk and wire gaps).
