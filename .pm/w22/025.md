# Deleting a sandbox image that a snapshot came from: decide whether bex refuses it, as Render does

Why: Render's CLI v2.37.0 says an image "that sandboxes or snapshots still use can't be deleted" and that the error names them, while bex deletes an image whatever snapshots exist, so the same command gives a different answer.

Found by w22/m444 t007 (Render parity), 2026-11-21.

- **Render.** `render sandbox-groups images delete --help` at v2.37.0 (`cmd/sandboximagesdelete.go`): "An image that sandboxes or snapshots still use can't be deleted. The error names them; terminate the sandboxes and delete the snapshots, then retry." The release notes say the same. Render's public OpenAPI describes `409 image_in_use` without listing a field for the dependents; the CLI prints the error's message only.
- **bex today.** `DeleteImage` (`lego/backend/internal/sandbox/images.go`) reads only sandboxes that have not terminated (`buildDependents`). A filesystem snapshot (w32/m285, `snapshots.go`) is a full copy in a repository of its own, so it keeps working after its source image is deleted, and nothing is refused. The `bex sandbox-groups images delete` help still mentions snapshots, because the launcher shows upstream's text.
- **Not known.** Whether Render's refusal covers every snapshot taken from a sandbox that started from the image, or only snapshots that still share its layers. No Render account was used here; a check on render.com with a snapshot of a sandbox started from an imported image would settle it.
- **Options.** (a) Refuse as Render does: record the source build on a snapshot at capture and name the snapshot ids in `image_in_use`. This costs users a step that bex's storage does not need. (b) Keep deleting, and record the difference in ADR018 with the user's sign-off.
- **Done when:** either a delete of an image with a live snapshot answers `409 image_in_use` naming the snapshot on REST, GraphQL and MCP, with a test, or ADR018 records the difference as signed off. The checklist row `sandbox-groups images delete` and ADR018's round-7 paragraph name this note and are updated either way.
