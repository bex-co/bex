## Objective

Decide the placement of the storage meter's credential Secret and how the operator gets to write it, before any code.

## Context

- w22/006 (promoted here): bex-api needs a read-only Zot user (sizing) and one with read and delete (the reaper) on `snapshots/**`; bex-api has none (`BEX_SANDBOX_SNAPSHOT_REGISTRY_*`, w22/m313).
- The machinery exists for per-namespace users: `lego/operator/internal/registry/snapshot_creds.go` (`EnsureSnapshotCreds`) mints a `kubernetes.io/dockerconfigjson` Secret, an `htpasswd` entry and a read-only ACL entry; `SandboxNamespaceRegistryReconciler` calls it per sandbox namespace.
- **Constraint found 2026-11-10:** `config/manager/manager.yaml` says the manager caches Secrets only in the apps namespace (`BEX_APPS_NAMESPACE`) "so its namespace Role is sufficient". bex-api runs in `bex-system` and a `secretKeyRef` cannot cross namespaces, so the Secret must live in `bex-system`, where the operator may have neither a cached read nor a Role to create Secrets.
- `bex-api` consumes env vars; a `dockerconfigjson` Secret is not directly usable by `secretKeyRef`, so this Secret should carry plain `username`/`password` keys.

## Steps

1. Read how `Creds.Client` reaches `bex-registry` Secrets today (cache scope, Role) and what the operator's ServiceAccount may do in `bex-system`.
2. Choose: an uncached API reader plus a small Role in `bex-system`, or minting from bex-api's side, or an out-of-band script like `scripts/snapshot-registry-secrets.sh` (which cannot edit the operator-owned `zot-config`). Prefer the choice that keeps the operator's cache scope unchanged.
3. Record the choice, the Secret name and its keys, and the two users' exact ACLs in ADR042 § D5 (or ADR023 § Sandbox snapshot storage).
