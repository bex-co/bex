## Objective

Apply Render's rule as its CLI states it — "Moving a group into or out of a protected environment requires an admin" — to both the environment the group leaves and the one it joins.

## Context

- Render CLI v2.38.0 `cmd/sandboxgroupsenvironmentset.go:26`; SDK v1.10.0: "Creating a group in a protected environment requires the Admin role in the workspace."
- bex already refuses placing a group at create in a protected environment for a non-Admin (w22/m412 via `placeGroup`, `docs/render-artifacts/sandbox-groups.md:32`), and the other member kinds' moves use the protected-environment checks of w4/m232 and w3/m281 (`lego/backend/internal/environments/protected_placement_test.go`).
- w4/728 (`e5d6088cc3`) made every Admin-only verb in a protected environment answer `PROTECTED_ENVIRONMENT_ADMIN_REQUIRED`.

## Steps

1. Reuse the existing protected-placement check for the target environment on add, and for the source environment the group leaves on add (a move) and on remove.
2. Check before anything changes, so a refused request changes no member of any kind.
3. Tests: non-Admin into, out of, and between protected environments (403); Admin succeeds; unprotected moves unaffected for a Developer.

## Files

- lego/backend/internal/environments/resources.go
- lego/backend/internal/environments/protected_placement_test.go

## Acceptance criteria

- [ ] Each case above holds on REST, and the refused request leaves the group where it was.

## Out of scope

- Restricting delete, edit or read of a group in a protected environment: Render documents none of it (`sandbox-groups.md`, w22/m412).
