## Objective

Record, in files tests can read, exactly what Render's two clients send and expect when they put a group in an environment, move it or take it out, so the server change is tested against the clients and not against a reading of them.

## Context

- SDK: `render-oss/sdk` tag `typescript/v1.10.0`, `typescript/src/sandboxes/index.ts` lines 1183–1316 (`createGroup`, `setGroupEnvironment`, `addGroupToEnvironment`, `removeGroupFromEnvironment`); Python `python/render/sandbox/client.py` (`create_group`, `set_group_environment`) at `python/v1.10.0`.
- CLI: `render-oss/cli` tag `v2.38.0` (`09b7802a…`): `cmd/sandboxgroupsenvironmentset.go`, `…remove.go`, `pkg/sandboxgroup/service.go` (`SetEnvironment`, `ClearEnvironment`, `resolveEnvironmentID`), `pkg/sandboxgroup/repo.go` (`AddToEnvironment`, `RemoveFromEnvironment`), and its fake `internal/fakes/renderapi/environments.go` (what it answers for a group, including 404 "sandbox group not found").
- Existing fixtures: `lego/backend/internal/sandbox/testdata/`, `lego/cli/testdata/`.

## Steps

1. Read both clients at their tags (in the scratch directory, not the repository) and record the commits.
2. For each call, record method, path, query, body, the status the client treats as success, and what it reads afterwards (both clients re-read the group).
3. Record the Python client's requests too, and note any difference from TypeScript; the release notes say they match.
4. Write a small JSON fixture under `lego/backend/internal/sandbox/testdata/` with the versions and commits, and a README line on how to regenerate it.

## Files

## Acceptance criteria

- [ ] The fixture lists the create, set (add), move (add to another environment) and clear (read, then remove) sequences for both clients, with their source commits.
