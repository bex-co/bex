# Sandbox rate limits: one bucket per user and class across bex-api replicas

Why: each bex-api replica keeps its own sandbox rate buckets, so on production's two replicas a user can be admitted up to twice Render's documented rate (200 creates a minute where Render refuses the 101st).

From w22/m443 t007 (2026-11-20), recorded in ADR104 D7 § API rate limits and the ADR018 row. Never stricter than Render, so it blocks nothing.

- **Where.** `lego/backend/internal/sandbox/ratelimit.go` builds each class on `core.KeyedRateLimiter`, an in-process token bucket, like every bex-api limiter (ADR006 § rate limits says a distributed counter is the follow-up when bex-api scales out).
- **What to decide first.** Whether to share only the sandbox classes or every limiter, and on what: the control-plane Postgres (a row per user and class, as the snapshot capture count already is) or the Valkey the SSH gateway's nonce guard uses.
- **Done when:** with two bex-api replicas, the 101st create of one user inside a minute is refused whichever replica serves it, `scripts/measure-sandbox-rate.sh` expects one bucket instead of one per replica, and ADR104 D7 and the ADR018 row drop the difference.
