# One user's concurrent sandbox execs are capped at 5 per ssh-gateway replica, so a user cannot reach Render's 1,000 execs a minute

Why: since w22/m443 the rate limiter admits 1,000 execs a minute per user, as Render documents, but the gateway's SSH session cap refuses a user's sixth concurrent exec on a replica with a 400. On production one user tops out near 300 short execs a minute, and an agent that runs commands in parallel gets errors Render would not give.

Found by the w22/m443 worker, 2026-11-23, running m443's production check.

- **Symptom.** [Run 45279460837](https://github.com/bex-co/bex/actions/runs/45279460837) of `sandbox-measure.yml` (leg `rate`, 22:26Z, production pin `9fdf7e0a1171`) ran 600 execs (mint a run connect token, then redeem it) in one sandbox, 20 at a time. `MEASURE execs`: all 600 mints answered 201, 394 redeems streamed exit code 0, and 206 redeems answered **400**. None was rate limited. The burst took 76 s, not the minute the leg allows.
- **Where the 400 comes from.**
  - The redeem path is `ConnectStreamHandler` → `StreamExec` → `dialGateway` → `mintAndDial` (`lego/backend/internal/sandbox/connect.go`, `exec.go`).
  - The gateway's exec server refuses when `Limits.Acquire(claims.Subject)` fails, with 429 `session limit reached` (`lego/backend/internal/sshgateway/sandboxsse/sandboxsse.go:126`).
  - bex-api turns any gateway 429 into `errExecSessionLimit`. That error wraps `core.ErrBadRequest` (`lego/backend/internal/sandbox/reachability.go:56`), so the client reads HTTP 400 `too many concurrent exec sessions`.
- **The cap.**
  - Each gateway process has one `SessionLimiter`, shared by native SSH, web shell, agent attach, sandbox exec and sandbox file transfers (`lego/backend/cmd/ssh-gateway/main.go:218`).
  - Production runs it at `BEX_SSH_MAX_SESSIONS_PER_IDENTITY` 5 and `BEX_SSH_MAX_SESSIONS` 100 on 2 replicas (`lego/operator/config/ssh/deployment.yaml`). So one user holds at most 10 concurrent execs, and fewer whenever the load balancer puts a sixth on one replica.
  - Production's Prometheus scrapes the gateway through its Service, one replica per scrape. Its `bex_ssh_gateway_limit_rejections_total{scope="identity"}` read 2 at 22:26:00Z and 107 at 22:31:00Z.
- **Throughput it allows.** 394 execs of `true` completed in 76 s on at most 10 slots, so each held a slot for about 1.9 s. That puts one user's ceiling near 300 execs a minute, below Render's exec class (1,000 a minute) and below the 600 that w22/m443's definition of done names. File transfers spend the same limiter against Render's 1,000 a minute. That is not measured.
- **Render.** [render.com/docs/sandboxes-limits](https://render.com/docs/sandboxes-limits), read 2026-11-23, documents no limit on concurrent commands, streams or transfers. Its only exec limit is "Execute a command: 1,000" requests per minute per user, shared across the user's API keys, and an over-limit request fails with HTTP 429. Its only concurrency limit is sandboxes per group.
- **Fix direction (not decided here).**
  - Hold sandbox exec and file streams to a limiter of their own, sized so Render's per-minute classes bind first. Native SSH, web shell and agent attach keep the 5 per identity.
  - If a bound remains, it is a bex-owned abuse control: ADR018 must record it as a divergence awaiting sign-off, as w22/022 records the workspace bound.
  - A concurrency refusal answers 429 with `Retry-After`, not 400.
  - The 5-per-identity cap was a hardening choice. Under the parity rule its ADR is amended, not kept.
- **Done when:**
  - A gateway test holds more than 5 concurrent sandbox exec streams for one subject on one replica, and a native SSH session is still refused at its sixth.
  - bex-api answers a gateway concurrency refusal with 429, and a test covers it.
  - ADR104 D7 and ADR018 state the bound, or that there is none.
  - The w22/m443 line in this workstream's README names the fix commit in its gate (``pin must carry `<sha>` ``).
  - Once production runs that commit, `gh workflow run sandbox-measure.yml -f leg=rate` prints PASS: 600 execs inside a minute, none refused.
- **Likely size:** more than an hour across the gateway, bex-api, the operator's gateway config, two ADRs and the production leg. Promote it if so.

## Promoted (2026-11-24)

Promoted to [w22/m623](../blocked/m623/README.md) by the `/loopx w22` worker: the fix spans the ssh-gateway, bex-api, the gateway's manifest, ADR104, ADR018 and ADR035, and a production leg that waits for a deploy, which is more than an hour across several tasks. The premise holds at `origin/main` `3829308659`: `sandboxsse.go:126` and `sandboxfiles.go:118` still take the shared limiter's slot, `exec.go:361` still maps the gateway's 429 to `errExecSessionLimit` (`reachability.go:56`, a 400), and the file redeem's proxy passes the gateway's 429 through without `Retry-After`. w22/m443's gate now names m623.
