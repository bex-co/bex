# Provision the storage meter's registry users as operator-managed Zot credentials

Why: w22/m313 reads a suspended sandbox's image size from Zot and deletes a gone sandbox's images, and bex-api has no registry credential of its own; found by w22/m313 t004 on 2026-11-10.

- **Finding.** bex-api needs two Zot identities scoped to the snapshot prefix: a read-only one (`BEX_SANDBOX_SNAPSHOT_REGISTRY_USER`/`_PASSWORD`, actions `read` on `snapshots/**`) for sizing, and a separate one with `read` and `delete` on `snapshots/**` (`BEX_SANDBOX_SNAPSHOT_REGISTRY_GC_USER`/`_PASSWORD`) for the reaper. The only credential that can do either today is `bex-builder`, which holds Zot's `adminPolicy` and also pushes build images, so it must not be handed to bex-api. The operator already mints a read-only `snap-<ns>` user per sandbox namespace (`lego/operator/internal/registry/snapshot_creds.go`, `SandboxNamespaceRegistryReconciler`); a platform-wide pair needs the same treatment: an `htpasswd` entry in the `zot-htpasswd` Secret and an ACL entry in `zot-config` (`lego/operator/internal/registry/zotconfig.go`).
- **Work.** (1) Add the two users and their ACL entries to the operator's Zot config generation, with a test that no other repository is readable or deletable by them. (2) Mint their secrets (`scripts/snapshot-registry-secrets.sh` is the pattern) into a Secret bex-api mounts. (3) Set `BEX_SANDBOX_SNAPSHOT_REGISTRY_URL=http://zot.bex-registry.svc:5000` and the user and password variables in `lego/operator/config/api/deployment.yaml`. (4) Confirm bex-api's pods may reach `bex-registry:5000` (the network policy admits `bex-system`).
- **Gate.** w22/m313 t006's production check needs this, and so does `SandboxStorageUnsized` stopping to fire.
- **Sizing.** About two hours; promote with `/pm promote w22/006` if the operator change grows.
