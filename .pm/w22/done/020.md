# A sandbox pod's CPU quota is 2 cores whatever its plan below that: give the init container the plan's CPU limit

Why: from 2026-11-18 a sandbox is billed for the CPU its pod uses, and a `starter` or `1c-2g` pod can use, and be billed for, up to 2 cores, twice what `1c-2g` names and four times `starter`.

Found by w22/m314 t004 step 0, 2026-11-17 (read on production; ADR104 D8 records it).

- **Cause.** A sandbox pod has one container at the plan's CPU and one init container, `execd-installer`, with no limit of its own. The `<workspace>-sandbox` LimitRange gives it the default (`cpu: 2`, `memory: 4Gi`; the pod carries the `kubernetes.io/limit-ranger` annotation). A pod's effective CPU limit is the larger of the sum of its containers and its largest init container, and under gVisor the sentry and the workload share the pod cgroup, so the container's own limit does not bind below the pod's.
- **Evidence.** A 4-CPU agent pod: container `cpu: 4`, init container `cpu: 2`, pod cgroup `container_spec_cpu_quota` 400000 over a 100000 period. The w22/m314 t001 spike read exactly 2.00 cores from one syscall-heavy thread in a `1c-2g` sandbox. The `1c-2g` pod's own quota was not read on a node; `sandbox-measure.yml` leg `usage` prints it (`MEASURE pod-cpu-quota`).
- **Effect on the bill.** `1c-2g` worst hour: 2 × $0.084 + $0.027 = $0.195, against $0.111 if capped at 1 core and $0.108 on the old weighted meter. Render does not document whether a sandbox can exceed its plan's CPU; a plan named `1c-2g` reads as one CPU.
- **Fix to try.** Stamp the init container's CPU limit (and memory, if it holds) at the plan's, where bex-api builds the sandbox template (`lego/backend/internal/sandbox/client.go`, the resources it sends; the init container comes from the OpenSandbox controller, so this may need the pinned controller's template or a patch under `lego/operator`), or lower the LimitRange default CPU for sandbox namespaces if nothing else relies on it. Check that the install step still finishes in time on `starter` (0.5 CPU).
- **Done when:** a new `1c-2g` sandbox's pod reads `container_spec_cpu_quota` 100000 over 100000, a syscall-heavy load in it reads at most about 1 core in `sandbox_cpu_seconds`, sandbox create time on `starter` is measured before and after, and ADR104 D8 and ADR030 §17 say the cap is the plan's CPU.

## Outcome 2026-11-17 (/loopx w22): fix shipped, parked on its production reading

- **Verdict: work.** The premise held: `execd-installer` had no CPU limit, and four agent pods read on production on 2026-11-17 carried container `cpu: 4` and init container `cpu: 2`.
- **What shipped.** Two changes, either of which caps a new pod at its plan's CPU:
  - `deploy/opensandbox/sandbox-cluster.toml` sets `[kubernetes.execd_init_resources]` to a 500m CPU limit and a 100m request. The pinned server 0.2.2 reads this option (`KubernetesRuntimeConfig.execd_init_resources`); the rendered config was loaded through the server's own model and gave the init container `{cpu: 500m}` / `{cpu: 100m}`. `scripts/gitops-validate.sh` guards the three lines.
  - The sandbox namespaces' LimitRange default CPU limit is 500m instead of 2 (`store.SandboxDefaultCPULimit`, `limitRangeFor`; hosting keeps 2). This covers a sandbox created before the deploy the next time its pod is created, because its stored template names no limit.
  - 500m is the smallest plan's CPU, so the pod's quota is the sum of its containers on every plan. `TestNoSandboxPlanIsSmallerThanTheNamespaceDefaultCPULimit` refuses a plan below it, and `TestSandboxRegimeLimitRangeDefaultsCPUToTheSmallestPlan` pins the LimitRange; both fail when the constant is changed.
- **Not changed: memory.** The init container still takes the LimitRange's 4Gi default, so a pod below 4 GiB has a 4Gi pod-level memory limit. It does not move a bill (memory is billed as allocated). Lowering it would bind a `starter` pod at 512Mi including the sentry for the first time and needs its own measurement; not filed by this worker.
- **Not changed: pods already running.** A quota is set when a pod is created, so a pod running at the deploy keeps 2 cores until it is next started.
- **Create time, before.** On the four production pods the install step started and finished within the same second at its 2-CPU limit (`initContainerStatuses[].state.terminated`). No `starter`-plan or `1c-2g` sandbox was running to read.
- **Production check, added to leg `usage` of `sandbox-measure.yml`** (`scripts/measure-sandbox-usage.sh`). It now fails unless: the default plan's pod reads a CPU quota equal to its plan's CPU (1 core for `1c-2g`); a `starter` pod reads 0.5; and four syscall-heavy loops for 60 s in the `starter` sandbox move the pod's counter by 24 to 36.5 CPU-seconds (about half a core; the old quota allowed 120). `MEASURE pod-cpu-quota` and `MEASURE cap` print each pod's `start.installSeconds` and `start.createdToStartedSeconds`, which is the "after" create time. The script was checked for syntax and its helpers on sample pods; it has not run against production.
- **Gate (clears by itself, nothing is needed from the user):** the deploy carrying this commit, then `gh workflow run sandbox-measure.yml -f leg=usage -f usage_idle_seconds=600` must print PASS. The deploy restarts the OpenSandbox server once (its config changed), so sandbox calls answer 503 for that window.
- **Then:** record the quota, the load's cores and the two start times in ADR104 D8, and move this note to `done/`. If the `starter` install step takes more than a few seconds at 500m, raise only the init container's limit question again, not the LimitRange.
