## Objective

Prove on production that the meter counts a sandbox's real egress, so the alert's number means something.

## Context

- The user authorized short production probes through `sandbox-measure.yml` on 2026-11-14 (D1 of `/unblock w22`): one disposable, billing-excluded workspace, bounded load. The base sandbox image is `bash:5.3` (busybox `wget`, `dd`, `df` available; no curl or python3). `scripts/lib/sandbox-measure.sh` has the REST, exec, pod and Prometheus helpers; `scripts/measure-sandbox-kubelet.sh` is the model for a leg. The new operator image and the DaemonSet's `bex.co/sandbox` toleration must be deployed before this runs: production deploys in batches (`deploy.yml` deploys a push only when the production pin is at least 6 h old; the pin was 3 h old at 2026-11-15 08:50 UTC). The leg is `scripts/measure-sandbox-egress.sh`, written and registered in `sandbox-measure.yml`; dispatch it with `gh workflow run sandbox-measure.yml -f leg=egress` once the batch has deployed.

## Steps

1. Add an `egress` leg (`scripts/measure-sandbox-egress.sh`, and its option in `.github/workflows/sandbox-measure.yml`): create an allow-all sandbox, read the series `bex_app_direct_egress_bytes_total{namespace="<ws>-sandbox"}` through a Prometheus port-forward, **upload** a known size from the sandbox (the meter counts bytes the pod SENDS, source = the pod's IP: a download moves only acknowledgements), wait two scrapes, read again; the delta must be within about 10% of what the sandbox itself transmitted (its own `eth0` counter in `/proc/net/dev`, read before and after), and the sandbox's pod must carry `bex.co/sandbox-id`.
2. Dispatch it (`gh workflow run sandbox-measure.yml -f leg=egress`), record the run id and the two numbers in this task.
3. If the meter does not see gVisor traffic, say what it sees and open a follow-up.

## Done 2026-11-16

- **Run 43791684803 (leg `egress`, production, all checks passed):** one allow-all sandbox in a disposable, billing-excluded workspace; its pod carried `bex.co/sandbox-id`. The sandbox wrote a 50 MiB file and POSTed it over HTTPS to a public speed-test endpoint (busybox `wget`, exit 0, `HTTP/1.1 200 OK`). The meter's series `bex_app_direct_egress_bytes_total{namespace="<ws>-sandbox", app_id="sandboxes"}` rose from 0 to **52,805,956** bytes; the sandbox's own transmit counter (`/proc/net/dev` eth0) rose by **52,886,602**: a ratio of **0.9985**, inside the 10% the check allows. The workspace, principals and sandbox were cleaned up by the leg's own cleanup (the run's last line).
- **The design is uploads, not downloads:** the meter counts bytes the pod sends, so the task's title ("downloaded bytes") was corrected here and in the README; ADR104 D11 already says a download barely registers.
- **Leg defects found and fixed along the way (none in the product):** the sink `speedtest.tele2.net` on plain port 80 timed out from the sandbox, so the upload goes to `speed.cloudflare.com` over HTTPS with the image's wget (`17cc1baf5`, `b3590f992`); busybox `wget --post-file` reads the file as one C string, so a random file stopped at its first NUL and sent only its handshake (3 KB of 50 MiB, run 43791202887; the meter and the sandbox's counter still agreed, at 2.8 KB and 3.0 KB), fixed by a printable body (`d641f73dd`); and a port-forward poll that could exit the leg on one failed read (`e5dff5697`). Earlier runs 43788895192, 43789638453, 43790513858 and 43790998888 are those failures.
- ADR104 D11's meter paragraph and gap 14 now say egress is verified on production.
