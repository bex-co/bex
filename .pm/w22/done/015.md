# The board validator rejects moving a milestone back out of blocked/ when another workstream uses its number

Why: `scripts/pm-board-validate.py` documents that "moving a milestone within its own workstream is not a duplicate", but `check_duplicates` builds `added` from (number, workstream, directory) tuples, so `blocked/m321` to `m321` counts as an addition and fails because `w4` also has an `m321` (`.pm/w22/m321 adds milestone m321, already used by w4`). Found restoring w22/m321 with `/unblock w22` on 2026-11-14, which therefore stayed in `blocked/`.

- **Fix.** Compare on (number, workstream): a pair already present at the merge base is not an addition, whatever directory it moved to. Add cases to `scripts/test_pm_board_validate.py`: a milestone moved `blocked/` to live with its number also used by another workstream passes; a milestone newly added under a number another workstream uses still fails.
- **Then.** `/pm unblock w22/m321` moves `.pm/w22/blocked/m321` back to `.pm/w22/m321`: its gates are cleared (see its 2026-11-14 record), and `/loopx w22` works t005 and t008.
- **Size.** Under an hour.

## Outcome (2026-11-14)

- **Done.** `check_duplicates` in `scripts/pm-board-validate.py` now skips the "already used by" check for a (number, workstream) pair the merge base already held, so a milestone moving between live, `blocked/` and `done/` under its own workstream is never an addition. A number newly added under another workstream's number still fails. Two tests in `scripts/test_pm_board_validate.py` (a historical duplicate moves live and to `done/`; a new milestone under another workstream's number still fails); the first fails without the fix. The real move `.pm/w22/blocked/m321` to `.pm/w22/m321` passes.
- `/pm unblock w22/m321` can now move m321 back (its gates are cleared; see its 2026-11-14 record).
