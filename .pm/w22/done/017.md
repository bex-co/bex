# Deleting a workspace leaves its suspended sandboxes' images in the registry

Why: the storage production check of 2026-11-15 (sandbox-measure run 43693931198, w22/m321 t005) found eight `snapshots/<workspace>-sandbox/…` namespaces in Zot whose workspace namespace no longer exists, including the disposable workspaces earlier runs created and deleted with a sandbox still suspended; the lifecycle map of 2026-11-14 read the same gap in code: `WorkspacePurger` (`lego/backend/internal/sandbox/purger.go`) terminates a workspace's sandboxes and deletes only imported and built images, and `sandbox_storage_objects` cascades away with the tenant row, so no `reap_pending` row ever asks the reaper to delete a suspended rootfs image.

- **Evidence.** The `orphan-snapshot-namespaces` line of the run: `tea-d9nsrt740dkc73eacpc0-sandbox`, `tea-dbp81mpv2n4c73anb7sg-sandbox`, `tea-dbpg7hs5ngvc73e8tncg-sandbox`, `tea-dbq0jiqk10fs73dvojug-sandbox`, `tea-dbs0h0cplt9c73bhrp30-sandbox`, `tea-dbs0ml4plt9c73bhrpmg-sandbox`, `tea-dbs25fsplt9c73bhs0c0-sandbox`, `tea-dbslefmoou4c73fdrgag-sandbox`. Zot's volume is a shared 100 Gi and retention keeps the newest five tags per repository forever, so each leaks at least one image (about 100 MB in the probe).
- **Fix.** Before a workspace's rows are deleted, queue its suspended sandboxes' images for the reaper, or delete the `snapshots/<ws>-sandbox/` repositories in the purger with the delete credential (`bex-sandbox-reaper`); then a one-time sweep of the repositories whose workspace is gone (list the catalog, drop the prefixes without a tenant). Tests: a real-Postgres purge with a suspended sandbox leaves no `snap-gen*` tag, a repository of another workspace is untouched, and a failed delete retries.
- **Size.** About two hours: promote it with `/pm promote w22/017` when its turn comes.

## Outcome (2026-11-15)

- **Done in code.** `PurgeWorkspace` now deletes the `snap-gen*` tags of every suspended, resumed or queued `/v1/sandboxes` rootfs image the workspace still has (`SandboxRootfsRefs`, before the tenant row cascades; after the sandboxes are terminated so a pause cannot commit a new image behind the delete; a registry failure fails the delete for a retry, and one refused repository does not stop the others), and an `OrphanSweeper` (`lego/backend/internal/sandbox/orphan_sweep.go`, its own loop beside the meter, per-replica gate of 3 hours, at most 100 repositories and 2 minutes a round, default control-plane identity only) deletes the images of `snapshots/<ws>-sandbox/` prefixes whose workspace no longer exists (a tenant row at any stage of delete, or a creation attempt in progress, counts as existing); it deletes only `snap-gen<N>` and `image` tags by tag, skips a round on a catalog or lookup error, and counts what it reaps in `bex_sandbox_storage_orphan_repositories_reaped_total`.
- **Tests:** real-Postgres purge and sweep tests against an in-memory Zot fake (including a mid-delete workspace and a `prepared` creation attempt kept, another workspace's repository untouched, retry after a registry failure), 11 mutations caught; ADR023 and ADR104 D11 updated.
- **Not yet shown on production:** the eight orphan repositories clear after the next batched deploy (the `orphan-snapshot-namespaces` line of the next `sandbox-measure` storage run should read none). No alert on the sweep's failure counter yet, and a catalog beyond 10,000 repositories is swept only for its first 10,000.
