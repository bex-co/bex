# A sandbox image import Render fails with `unsupported_platform`, `missing_boot_tools` or `invalid_image` is refused at once on bex, or imports and fails only at start

Why: Render's SDK v1.10.0 reads a failed import's `failureCode`, and its `images.import()` then `waitUntilReady()` raise `SandboxImageFailedError` naming the reason; on bex an image with no linux/amd64 variant is a `400 SANDBOX_IMAGE_INVALID` with no build, so the same code raises a plain `ClientError` at the import, and an image with no `/bin/sh` imports `succeeded` and fails only when a sandbox starts from it.

- **Found by:** w22/m445 t007, 2026-11-23. Render's `sandboxBuildFailureCode` vocabulary at `render-oss/sdk` `0529a77a19fd` (`go/pkg/render/internal/client/sandboxes/sandboxes_gen.go`; frozen as `image.failureCode.values` in `lego/backend/internal/sandbox/testdata/sdk-v1.10.0-contract.json`) has eight values. bex records five (`lego/backend/internal/sandbox/images.go` `buildFailureCode`) and never `invalid_image`, `missing_boot_tools` or `unsupported_platform`: `resolveSource` refuses a source without linux/amd64 while the request waits, and ADR104 § Images says an image without `/bin/sh` and `sleep` fails to start.
- **Not established:** whether Render checks the platform while the import request waits (its 201 needs `sourceDigest`, so it resolves the image then) or only in the background. The vocabulary says some images fail after the 201 with these codes. Read Render's `create-sandbox-build` reference and sandbox images docs, and if they are silent, import an arm64-only image and a distroless one on Render.
- **End state:** each of the three situations answers as Render does (for an asynchronous failure: 201, then `failed` with that `failureCode` and a `failureReason`), with a router test per code in `sdk_compat_test.go`, or ADR018 records the divergence with the user's sign-off.
