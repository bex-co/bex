# A service PATCH behind a queued deploy waits 15 s per held setting, so two settings answer 503

Why: Render's Update Service answers at once (200 in 0.98 s in its own Terraform recording), but bex's waits up to 15 s for each setting it holds behind a deploy the operator has not adopted, so a PATCH that changes the repo and the runtime while a deploy is queued runs past bex-api's 28 s request budget, answers 503 and leaves the service half changed. It is class 13 of the [Terraform checklist](../../docs/terraform-compatibility-checklist.md#failure-classes), the one bex-side failure Run K found (w22/m605).

Found by w22/m605 t001 (Run K, 2026-11-24) on dev-10 built from production's pin `ff5de0a130e6`:

- **The test.** `TestWebServiceResource_RuntimeUpdate` (`render-oss/terraform-provider-render` `06af456`) passes steps 1 and 2 and stops at step 3 of 4, twice: `PATCH /v1/services/{id}` with `repo: https://github.com/render-examples/bun-docker` and `serviceDetails.runtime: docker` answers 503 `REQUEST_TIMEOUT` after 28.0 s. It is sent seconds after step 2's `POST …/deploys` (202) queued a deploy behind the first build, which is still in progress. Render's cassette answers the same request 200 in 0.98 s. Run H (2026-11-18, before the change below) passed the test.
- **By hand with `curl`, behind the same queued deploy** (a native web service from `render-examples/express-hello-world`, a runtime `PATCH`, then `POST …/deploys`):
  - `repo` alone: 200 in 15.6 s; `serviceDetails.runtime` alone: 200 in 15.2 s;
  - `repo` and `runtime` together: 503 in 28.0 s, and the service then read the new repo with the old runtime;
  - a start-command change, which holds nothing for the next deploy: 200 in 0.04 s.
- **bex-api's log** says, 16 s into the request, `rollout: the deploy ahead of … was not adopted within 15s; writing through`, then `apps: publish srv-… after a failed patch: context deadline exceeded`.
- **The code.** `apps.Service.ApplyServicePatch` (`lego/backend/internal/apps/settings.go`) saves every row only (`rollout.WithSaveOnly`, w8/m135) and runs the rows one after another. A row that holds a change for the next deploy (the repo through `markSourcePending`; the runtime too, by the timings above) first calls `rollout.AwaitAdoptionBeforeHold` (`lego/backend/internal/rollout/adoption.go`, `DefaultAdoptionWait` 15 s). Since w6/163 (`14cf6f55fb`) and its follow-up #230 (`f5ca4e0968`, both 2026-11-23) that wait also covers a deploy queued in the latest-pending slot behind an adopted release, which the operator adopts only once the build ahead ends. So each held row waits the whole 15 s, and two exceed `core.RequestBudget` (28 s).
- **Production.** Unverified there, but nothing in the path is specific to a dev stack: any build longer than 15 s leaves the queued deploy unadopted for the whole wait.
- **Done when:**
  - The PATCH above, behind a queued deploy, answers 200 within a second or two on REST, MCP `update_service` and the GraphQL setters, and still leaves the queued deploy running the settings it was requested with (what w6/163 protects).
  - A test holds a two-setting patch behind an unadopted queued deploy to Render's answer: one response, both settings saved, no 503, and no half-applied patch.
  - `TestWebServiceResource_RuntimeUpdate` passes all four steps on a `dev-N` stack (`TF_VERIFY_RUN='^TestWebServiceResource_RuntimeUpdate$' scripts/terraform-provider-verify.sh webservice`), and the checklist's class 13 and webservice row say so.
