## Objective

Expose the new verbs on the Render-compatible REST surface: `POST /v1/services` creating a service (201 with the created `service` object) and `DELETE /v1/services/{id}` (204), request/response shapes verified against Render's OpenAPI spec — the same verification standard `rest.go` already follows for list/get/verbs.

## Context

- Render's create body nests details under `serviceDetails` (`env`, `plan`, image/repo source); bex accepts the fields it honors and omits what it doesn't (build plans, regions, disks) — the established "safe superset / omit what bex can't honor" rule (`docs/bex-api.md`).
- Routes must also serve under the `/v1/apps` alias like every other service route.
- Verify against the local Render spec artifact (`render-public-api-1.json`, referenced throughout `docs/bex-api.md`).

## Steps

1. Add the two routes to `lego/backend/internal/apps/rest.go`, delegating to `Service.Create`/`Service.Delete`.
2. Map validation errors → 400 with a Render-shaped error body; `ErrNotFound` → 404.
3. Update `docs/bex-api.md` REST table (create 201 / delete 204 rows).

## Files

- `lego/backend/internal/apps/rest.go`
- `docs/bex-api.md`

## Acceptance criteria

- [ ] `POST /v1/services` with a valid body → 201 + the created `service` object; invalid → 400.
- [ ] `DELETE /v1/services/{id}` → 204; unknown id → 404.
- [ ] Shapes match Render's OpenAPI for the fields bex serves (superset rule documented).
