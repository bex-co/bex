# Two narrow ADR057 #4 residuals: day-to-day identity VAP coverage + exact BuildKit-shape modeling

From the `w10/m9 t004` design note (`docs/ADR057-security-review-round6.md` finding #4's 2026-08-19 update). The broad ask — a `ValidatingAdmissionPolicy` scoping what the operator identity may author cluster-wide by namespace label, ServiceAccount, and no-foreign-Secret-mounts — is already live (`deploy/gitops/base/operator-workload-admission.yaml`, `matchConditions` on `system:serviceaccount:bex-system:bex-controller-manager`). Two narrow, self-documented residuals remain, both sub-hour:

1. **Day-to-day identity uncovered by the VAP.** `operator-workload-admission.yaml`'s `matchConditions` name only `bex-controller-manager`; `system:serviceaccount:kube-system:bex-operator` (the day-to-day credential, `operator-daytoday-rbac.yaml`) isn't matched by any of the three policies. Its current grant is narrow (`pods/exec`, `pods:delete`, `jobs:delete`; `jobs:create` removed by ADR063 #2) so live exposure is small today — but if that role is ever broadened, the VAP won't enforce it, the exact gap ADR061 #2 flagged. Fix: add a second `matchConditions` entry (or a parallel policy) for `system:serviceaccount:kube-system:bex-operator`.
2. **Exact BuildKit-shape modeling in `bex-build`.** ADR063 line 118's own explicit residual: `bex-build` is a shared privileged-Pod-Security namespace with only the generic `hostUsers=false` + restricted-container grammar (ADR063 #13); there's no admission constraint pinning the *exact* hardened BuildKit Job template shape ADR061 #6 called for. Fix: one CEL match in the VAP (or a dedicated policy) asserting the BuildKit Job's container/volume/security-context shape matches the known-good template exactly.

Touch `deploy/gitops/base/operator-workload-admission.yaml` (+ its test/validation harness, if any — check `scripts/gitops-validate.sh` and any admission-policy dry-run tooling). Verify against a real cluster (VAPs are CEL — a syntax/logic error fails only at apply time, not locally) before considering either done.
