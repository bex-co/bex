## Objective

Answer ADR059 D7's three questions against the deployed OpenSandbox, and pick the hibernate implementation: **A** (retain the native `Suspend` snapshot past pod reclamation and resume from it) or **B** (self-owned tar → object storage + initContainer hydrate). Write the answer back into ADR059 (D3 choice, Status → Accepted).

## Context

- What we know from our side: `sandbox/service.go` `Suspend` runs `/usr/local/bin/bex-pre-snapshot` (credential scrub) then snapshots; `Client.Resume` un-suspends the SAME pod. Unknown: snapshot location (node-local? object storage?), durability past Terminate, per-instance cardinality behavior.
- Where to look: the OpenSandbox controller/server sources under `deploy/opensandbox/` + its upstream repo; the BatchSandbox CRD's snapshot fields; live inspection on the prod/mock cluster (where does a suspended sandbox's state land — node disk, PVC, registry, S3?).
- Decision rule (from the ADR): A only if the snapshot is **durable past Terminate, object-storage-backed, and scales to many sandboxes**; anything less ⇒ B.

## Steps

1. Read the OpenSandbox snapshot/suspend implementation; identify the storage backend and lifecycle.
2. Empirically verify on a cluster: suspend a sandbox, locate the artifact, terminate, check survival; note size/time for a realistic workspace.
3. Record findings + the A/B verdict in ADR059 (edit D3 + Status), and a short evidence note in this milestone.
