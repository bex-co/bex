## Objective

Found in the t007 production walk (2026-11-08 05:47–05:56 UTC, QA workspace `tea-daif693dqjvc73e7as3g`, bex CLI v2.35 built from main). Two linked defects leave a customer with a Blueprint that can never sync again.

## Context

**Reproduction:**

1. `bex ea blueprints create --repo https://github.com/bex-co/bex --branch main --path examples/static-site/render.yaml --existing-resources adopt` returned `planned` with `create static-site`. `approve` reached `success` and created `srv-dbo0q0svg1gs7387qp10`.
2. `DELETE /v1/blueprints/exs-db136288mmqc73d4hpug` returned 204, and `DELETE /v1/services/srv-dbo0q0svg1gs7387qp10` returned 204 (a later GET returned 404).
3. Re-running `create` with the same repo and path revived the same id `exs-db136288mmqc73d4hpug`, with `status: created`, `resources: []` and `planningOutcome: no_changes`.
4. After that:
   - `ea blueprints plan` still returns `no_changes` with no actions, 45 s later and with the service gone.
   - `POST /v1/blueprints/{id}/sync` returns 409 `BLUEPRINT_AWAITING_APPROVAL`.
   - `ea blueprints approve` returns 409 `BLUEPRINT_NOTHING_TO_APPROVE`, because the newest sync is `bsr-dbo0ptkvg1gs7387qovg` (`success`), from the previous connection.

The Blueprint is stuck: nothing can apply it, and its defined service never comes back. The test Blueprint was deleted afterwards.

**Render:** "Manually deleting a resource does not remove it from your Blueprint. The next time you sync your Blueprint, Render detects that a defined resource is missing and recreates it." (render.com/docs/infrastructure-as-code, read 2026-11-08). On Render, a `no_changes` outcome also needs no approval (the CLI's own next step reads "No changes to approve. No further action is needed").

## Steps

1. Planning compares the manifest with the resources that exist now, not with the last applied sync. A defined resource that is missing is planned as `create`.
2. A Blueprint in `created` whose first plan is `no_changes` leaves `created` (it is in sync), or `sync` and `approve` otherwise have a working path. No state should accept neither.
3. A revived row's first plan ignores the previous connection's sync history when deciding what to apply (see t013's reconnection note).
4. Minor: the REST 409 `BLUEPRINT_CONNECTION_CONFLICT` message names the GraphQL mutation `updateBlueprint`. It should name the surface being used: `PATCH /v1/blueprints/{id}` on REST.

## Acceptance criteria

- [ ] The reproduction above ends with `plan` → `planned` (`create static-site`), and `approve` recreates the service.
- [ ] A Blueprint whose first plan is `no_changes` can be synced afterwards: never stuck in `created` with nothing to approve.
- [ ] Tests cover a deleted managed resource being re-planned, and the `no_changes` first plan.
