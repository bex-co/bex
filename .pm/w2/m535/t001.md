## Objective

Provision the Sandbox Broker CA (cert-manager self-signed CA Issuer/Certificate or dedicated Secret in `bex-system`) so `bex-ssh-gateway` mounts the private key + cert, `bex-ssh-gateway`'s Service exposes the broker port inside the cluster, and only the public CA certificate is available to sandbox Pods (never the private key).

## Context

- `deploy/gitops/base/` and `deploy/gitops/overlays/prod/` manage `bex-ssh-gateway` and cert-manager resources; `scripts/gitops-validate.sh` validates every rendered manifest.
- `bex-api` and tenant sandbox namespaces must never have RBAC to read the Broker CA private key Secret in `bex-system`.

## Steps

1. Add the cert-manager CA Certificate/Secret manifest for the Sandbox Broker CA in `bex-system` (and expose the broker port on the `bex-ssh-gateway` Service + mount the CA Secret into `bex-ssh-gateway` with the env vars from `w2/m534/t005`).
2. Add a safe distribution path for the **public-only** CA PEM (`ca.crt`) to sandbox Pods (e.g. `bex-api` reads only the public cert ConfigMap/PEM file configured via env and injects it into sandbox Pods or mounts it read-only, never touching the private key).
3. Add `scripts/gitops-validate.sh` assertions ensuring the broker CA private key stays in `bex-system` and is mounted only into `bex-ssh-gateway`.

## Files

- `deploy/gitops/base/*` (ssh-gateway Service/Deployment, broker CA Certificate/ConfigMap)
- `deploy/gitops/overlays/prod/*` (if overlay wires env/replicas)
- `scripts/gitops-validate.sh`
- `lego/backend/AGENTS.md`

## Acceptance criteria

- [ ] `bex-ssh-gateway` mounts the Sandbox Broker CA cert+key and exposes its cluster-internal broker port; neither `bex-api` nor any `<ws>-sandbox` namespace can read the private key.
- [ ] `bash scripts/gitops-validate.sh` exits 0.
