## Objective

On production, every successful build source create answers `500 internal_error` while the source is created. So a client retry makes a duplicate, and the source carries a `srv-` id instead of Render's `bds-`. Make the create return `201` with the created object, under a `bds-` id.

## Context

Live probe, `/qa-find-bugs w4` loop, 2026-11-03 16:12–16:20 UTC, pin `611df30d8f9c`, QA workspace `tea-daif693dqjvc73e7as3g`. All three sources were deleted afterwards; the list was empty after 15 s and GET by id returned 404.

- **Request:** `POST /v1/build-sources` with `{"ownerId":"tea-daif693dqjvc73e7as3g","name":"qa-20261103-bs","git":{"repoUrl":"https://github.com/render-examples/express-hello-world","branch":"main","runtime":"node","buildCommand":"yarn"}}`.
  - It returned **HTTP 500** `{"error":"internal error","id":"internal_error","message":"internal error"}`.
  - The same happened 3 of 3 times: with and without `buildCommand`, and once more after the bex-api pods rolled.
  - Controls behaved correctly. A body with neither `git` nor `image` returned 400 "exactly one of git or image is required". An `image` body without `image.ownerId` returned 400.
- **The source exists anyway.** Right after each 500, `GET /v1/build-sources?ownerId=…` listed it, for example `{"id":"srv-dbl0g207bpes73ai8s5g","name":"qa-20261103-bs"}`. `GET /v1/build-sources/srv-dbl0g207bpes73ai8s5g` returned 200 with the full object (`git.repoUrl`, `branch`, `buildCommand:"yarn"`, `runtime:"node"`, `region:"frankfurt"`).
  - Three 500s left three sources: `srv-dbl0g207bpes73ai8s5g`, `srv-dbl0gho7bpes73ai8s80`, `srv-dbl0gpr67o7c7382ug9g`.
  - None appeared under `/v1/services`: GET by id returned 404 and the service list did not include them. So the "never a service" rule holds.
- **Server log:** `bex-api: internal error: app: not found`, once per create (16:12:57, 16:14:00, 16:14:31; request `cf-ray a54cac20680ea43c-SJC`).
- **Root cause:**
  - `apps.CreateBuildSource` (`lego/backend/internal/apps/build_sources.go`) mints `id := ids.New(ids.BuildSource)` (prefix `bds`, `lego/backend/internal/id/id.go:144`). It passes that id through `create.buildSource`, and `service.go:2522` hands it to `Store.CreateApp` as `ID: req.buildSource.rowID()`.
  - `PGStore.CreateApp` (`lego/backend/internal/store/store.go:1021-1022`) begins with `a.ID = ids.New(ids.Service)` and unconditionally replaces it. The row is inserted as `srv-…`.
  - `CreateBuildSource` then calls `s.Store.SetAppDisplayName(ctx, id, req.Name)` and `s.GetBuildSource(ctx, id)` with the `bds-` id (`build_sources.go:200-205`). There is no such row, so the store's `app: not found` comes back. It is not `core.ErrNotFound`, so it maps to 500.
  - The line is identical at the deployed pin and on `main`.
  - **Unverified:** whether the unit tests (`build_sources_test.go` `TestBuildSourceLifecycle`) run against a fake store that keeps the supplied id. That would explain why they pass; check before relying on it.

## Steps

1. In `PGStore.CreateApp`, keep a caller-supplied `a.ID` (only build-source carriers pass one) and mint `srv-` only when it is empty. Keep the name-collision retry loop working with a fixed id, or make it id-agnostic.
2. Add a PG-backed test (real store): `CreateBuildSource` returns the created view with a `bds-` id, and `GetBuildSource`/list/DELETE all use that id.
3. Decide what happens to carriers already stored under `srv-` ids. Production had none left after this probe's cleanup; check `apps` rows with `build_source` markers before shipping.
4. Confirm `SetAppDisplayName` and any other post-create step cannot turn a successful create into a 500. If a follow-up step fails, the response must say the source exists, or roll it back. Never answer 500 and leave a source behind.
