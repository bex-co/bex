## Objective

A service linked to a native-runtime build source starts its own start command through the generic shell override (`container.Command = shellCommand(start)`). That replaces the image's `native-init` ENTRYPOINT and runs the command under `sh` (dash) for anything beyond a simple command. A native service built from the same repo runs `ENTRYPOINT ["/native-init"]` plus `CMD ["/bin/bash","-c",start]`. Make the linked service start the same way.

## Context

- `lego/operator/internal/controller/deployment_projection.go` `shellRunsStartCommand`/`appContainer`: a linked service has no repo or image and builder `auto`, so it gets the shell override.
- `lego/operator/internal/build/nativeinit.go` `nativeEntrypoint`: SIGTERM forwarding and subreaping for `npm start`/`yarn start` (w8/m88).
- `release_config_selection.go` `launch()` records how a release launched; it would need to recognise the new shape.
- The carrier's builder is known where the link is verified (`controller/build_source.go` `verifiedLinkedImage`).
- Found by the t016 review (2026-11-03).

## Steps

1. When a linked service's carrier is native, set `container.Args = ["/bin/bash","-c",start]` and leave `Command` unset, so the baked entrypoint still applies.
2. Teach `launch()` the new shape; keep Docker/image carriers on the current path.
3. Deployment-projection tests for a service linked to a native and to a Docker carrier.

## Acceptance criteria

- [ ] A service linked to a native Node source runs under `/native-init` with its start command in bash; a bash-only start command works.
- [ ] A service linked to a Docker source keeps the image's own ENTRYPOINT/CMD.
