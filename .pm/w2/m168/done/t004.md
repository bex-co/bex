## Objective

`oauth.bex.co` must never issue an authorization code or device grant for an unverified subject, including `skip_consent` clients (`bex-forum`, `bex-desktop`, `bex-mobile`, `bex-obs`, `bex CLI`). Hydra reuses the Kratos session at login, so the consent step is the choke point.

## Context

- `dashboard/src/common/server-fn/hydra-consent.ts`: the trusted/skip path (`~278`) and the ops-gate (`~339`) are separate gates. This one must run before both, including on the auto-accept path.
- Hydra `skip_consent` clients still pass through the consent acceptor (ADR088 §4 comment, `~508`).
- **Coordinate:** the `bex6` checkout stages `OAUTH_IDENTITY_CLIENTS` + `lego/backend/internal/identityclaims`, which already resolves `email_verified`. Reuse that resolver if it has landed. Otherwise read verification from the consent request's Kratos session/identity and leave a seam for it.
- Anti-goals: no hand-built Hydra login provider, and no OAuth-izing the dashboard (`.pm/DO_NOT_DO.md`).

## Steps

1. Resolve the subject's verification state at consent (fail closed when it can't be resolved).
2. Unverified: reject the consent request (`access_denied` with a description), or redirect to `/auth/verification` carrying the challenge so the flow resumes after verifying. Pick one and record it in ADR075.
3. Tests in `dashboard/src/common/server-fn/__tests__/hydra-consent.test.ts` for skip, trusted, ops and ordinary clients.
