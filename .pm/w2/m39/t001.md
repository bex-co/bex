## Objective

Write the architecture and security contract before granting any component `pods/exec`: define authentication, authorization, target resolution, supported SSH channels, failure behavior, deployment isolation, and the exact Render CLI wire contract.

## Context

- Render's current CLI reads `serviceDetails.sshAddress`, lists `/v1/services/{id}/instances`, verifies a live deploy, then launches the local `ssh` binary.
- The operator must remain mechanism-only and DB-free; SSH identity/authz belongs in `lego/backend`.
- `pods/exec` is materially stronger than the API's current pod/log read access and needs a separately reviewable trust boundary.

## Steps

1. Add `docs/ADR033-ssh.md` covering the gateway/data flow, key ownership, host-key custody, app/pod eligibility, shell selection, PTY/resize/exit semantics, session termination, audit facts, limits, and excluded channel types.
2. Verify the current Render docs/OpenAPI and `render-oss/cli` source; capture the service, instance, and SSH username/host formats bex must satisfy.
3. Threat-model cross-workspace targeting, stale/deleted keys, pod-name confusion, shell/command injection, session exhaustion, host-key rotation, and a compromised gateway.
4. Change the parity ledger from deliberate non-goal to a planned gap without claiming implementation.

## Acceptance criteria

- [ ] The design names one concrete component and protocol path from SSH handshake to Kubernetes exec.
- [ ] The minimum RBAC, authz relation, supported service types/plans, and every fail-closed case are explicit.
- [ ] Basic running-instance SSH is cleanly separated from ephemeral shells, jobs, browser shell, SFTP, and port forwarding.

## Out of scope

- Implementing the gateway or any public endpoint.
