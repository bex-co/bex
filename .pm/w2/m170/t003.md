## Objective

Make a `bex-db` CA renewal reach every pinned consumer without a human, while the analytics reader passwords stay under sealed custody.

## Context

- Grafana mounts `ca.crt` as a file from the Secret (`extraSecretMounts`, no `subPath`), so kubelet refreshes the file when the source object changes; `sslRootCertFile` is read when a connection opens and `connMaxLifetime: 300` recycles connections — a mirrored CA should be picked up without a Grafana restart (verify in t005).
- The CA certificate is public material; only the reader password is secret. Today both live in one sealed Secret, which is why a CA renewal requires a reseal.
- Options: **(a)** split `ca.crt` out of the reader Secret into a dedicated object kept in sync from `bex-system/bex-db-ca` by a least-privilege mirror (get one Secret in `bex-system`, write one object in `monitoring`); **(b)** a long-lived, user-provided CA via CNPG `spec.certificates` (cert-manager-issued) — wider blast radius because it changes TLS for every `bex-db` client. Prefer (a) unless t002 shows a consumer (a) cannot serve.
- Custody contract: `scripts/lib/analytics-bootstrap.sh` (w7/m153) — the bootstrap stops writing `ca.crt`; drift detection moves to the mirror/alert (t004).

## Steps

1. Choose (a) or (b) with t002's evidence; record the decision in this README.
2. Implement it in GitOps with least-privilege RBAC; point both `extraSecretMounts` at the mirrored CA.
3. Remove `ca.crt` from the reader Secrets and from `analytics-bootstrap.sh` (password-only); update `scripts/analytics-bootstrap.test.sh`.
4. Add a fail-closed check (`scripts/gitops-validate.sh` or the bootstrap test) that no sealed manifest carries a `ca.crt` for `bex-db`.
5. Update `docs/runbooks` / ADR088 where the reseal procedure is described.

## Acceptance criteria

- [ ] Reader passwords remain sealed; no committed manifest carries the `bex-db` CA.
- [ ] Changing `bex-db-ca` updates the readers' trusted CA with no manual step.
- [ ] The validator fails on a fixture that reintroduces a sealed CA copy.

## Out of scope

- Changing TLS for in-namespace `bex-db` clients (unless option (b) is chosen with evidence).

## Revised 2026-10-19 (t002 findings)

Option (a) is rejected: `bex-db-ca` carries `ca.key`, so an automated mirror would expose the CA private key to a long-lived identity (README `## Decisions`). Implement option (b) instead:

1. cert-manager `Issuer` (selfSigned) → CA `Certificate` `bex-db-server-ca` (`isCA: true`, multi-year, `privateKey.rotationPolicy: Never`) → CA `Issuer` → server `Certificate` `bex-db-server-tls` (90d, dnsNames `bex-db-rw`, `bex-db-r`, `bex-db-ro` and their `.bex-system`, `.bex-system.svc`, `.bex-system.svc.cluster.local` forms) in `deploy/gitops/base/bex-postgres.yaml`.
2. `bex-db` `spec.certificates.serverCASecret: bex-db-server-ca`, `serverTLSSecret: bex-db-server-tls` (client CA stays CNPG-managed).
3. Bootstrap reads the CA from `bex-db-server-ca` instead of `bex-db-ca`; reseal both readers once; update the bootstrap test.
4. Alert on `certmanager_certificate_expiration_timestamp_seconds{name="bex-db-server-ca"}` within 60 days, with a promtool test and a panel.
5. Prove on a dev stack first (t005), then ship under the user's authorization; the probe confirms production.
