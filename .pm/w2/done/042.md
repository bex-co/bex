# Preserve image-service pre-deploy commands when the CLI clones a service

Why: a clone can report a successful deployment while silently skipping the source service's migration or setup step.

**Severity:** major. **Attribution:** server response projection. **Estimate:** 55m, one focused inbox fix. **Status:** todo. Source: the user-requested live CLI QA loop, 2026-10-03 UTC. Goal: dependable deployment configuration and the unchanged Render CLI contract (ADR004, ADR006, ADR018).

## Reproduction and observed result

Production `https://api.bex.co/v1/`, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device OAuth in an isolated config, non-TTY JSON output. Installed `/opt/homebrew/bin/bex` **v0.2.1** and a checkout launcher built at **`f296747d9`** both reproduce. Both use Render CLI **v2.27.0**, commit **`a764810a768202704e7206eb7b87a47211fcd98e`**. Deployed API revision was not observable; the omission remains in the inspected checkout.

Use a fresh nonce and the QA workspace/config. The observed nonce was `500f75`:

```sh
bex services create --name qa-20261003-500f75-presrc \
  --type web_service --runtime image \
  --image docker.io/mendhak/http-https-echo:35 \
  --pre-deploy-command 'echo QA_PREDEPLOY_CLONE_500f75' \
  --env-var HTTP_PORT=3000 --plan free --health-check-path / \

# Wait for the source deploy to become live and verify its marker.
bex deploys list "$SOURCE_ID" -o json
bex logs -r "$SOURCE_ID" --type build \

# Do not repeat --pre-deploy-command: --from should preserve it.
bex services create --from "$SOURCE_ID" \
  --name qa-20261003-500f75-prerelease --region frankfurt \
  --plan free --env-var HTTP_PORT=3000 --confirm -o json

# Repeat with the checkout launcher and a fresh clone name.
# Then inspect each clone's deploy and the same marker query.
```

## Wire evidence and failing boundary

Read-only diagnostic requests used the same QA config and the unmodified pinned client's `RetrieveServiceWithResponse`. These are separate authenticated GETs, not an intercepted CLI trace. Each request was `GET https://api.bex.co/v1/services/<fixture-id>`, with no query/body, `User-Agent: render-cli/2.27.0 (macOS - 26.5.1)`, and returned **200**, `Content-Type: application/json`. Authorization was not captured. The evidence retains every response-body field; only `owner.email` is replaced with `[QA_EMAIL]`.

The source body includes:

```json
{
  "serviceDetails": {
    "runtime": "image",
    "preDeployCommand": "echo QA_PREDEPLOY_CLONE_500f75"
  }
}
```

This is a **field excerpt**; the complete body is in the evidence. `serviceDetails.envSpecificDetails` is absent. Both clone bodies omit the command entirely. Actual create POST bytes were not intercepted; the pinned client's request construction was separately exercised offline against the captured source response.

The consumer path is `cmd/servicecreate.go` → `ServiceFromAPI` → `NormalizeAndValidateCreateInput` → `BuildCreateRequest` → `POST /v1/services`. In the pinned module:

- `pkg/service/clone.go:156–159` reads web build/start/pre-deploy defaults from `details.EnvSpecificDetails`; it never falls back to the sibling `serviceDetails.preDeployCommand`. Private and worker cases use the same pre-deploy helper.
- `pkg/service/clone.go:335–346`, `preDeployCommandFromEnvDetails`, decodes that nested object as native/Docker details. Missing nested data yields no command.
- `pkg/types/service/servicecreate.go:214–234` normalizes empty build/start fields away; adding only a nested pre-deploy field does not introduce prohibited image build/start flags.
- `pkg/service/create.go:162` writes the preserved value to `serviceDetails.preDeployCommand` in the create request. The server already accepts and runs that field, as both live controls prove.

At checkout `f296747d9`:

- `lego/backend/internal/apps/render.go:413` emits the existing sibling `preDeployCommand`.
- `render.go:432` asks `envSpecificDetails` for the nested object. Its `:506–519` early return omits all image-runtime details except a cron's `startCommand`, dropping the pre-deploy field required by the cloning consumer.
- `apps/service.go:1102` already carries `App.spec.preDeployCommand` into `AppView`; create persists it at `:2716`. This is not missing storage or operator execution.

An **offline counterfactual**, not a product fix, adds only `envSpecificDetails: {preDeployCommand: <source value>}` to the captured response. The unchanged pinned normalize/default/validate/build pipeline then emits the command in the clone POST for **all three** `web_service`, `private_service`, and `background_worker` shapes. Without that nested field, all three omit it. All six complete generated bodies are in the evidence; these offline controls use `starter` and perform no HTTP writes or paid provisioning.

## Fix and shared-code verification

Project a nonempty image-runtime pre-deploy command into `serviceDetails.envSpecificDetails.preDeployCommand` for the three service types that support the phase. Retain the existing sibling field for compatibility. Do not add invented repository/build/start fields or modify the imported client. Preserve the image-cron command projection and the absent nested object for an ordinary image service with no applicable settings; legacy empty runtime and static/cron phase restrictions stay intact.

Counted boundary: `envSpecificDetails` has **one production caller**, `renderServiceDetails`; that has **one production caller**, `toRenderServiceWithMetadata`. Its two wrappers feed REST and MCP. REST has six direct `restService` call sites (scale, the shared verb handler, plan preview, patch, dry-run create, create), plus the list path; the verb handler also serves get/suspend/resume/restart. MCP's `renderServiceResult` uses the same projection, and `toRenderServices` feeds both list and stack results. The fix therefore belongs in the shared projection, not in one GET handler. Affected runtime/type combination: image × web/private/worker, **three kinds**.

GraphQL already exposes the flat `AppView.PreDeployCommand` in `apps/graphql.go:475`, which the dashboard consumes. Preserve that value and the existing REST/MCP sibling while testing the nested addition. No new UI or operator behavior is needed. The projection runs after authorization: retain existing unauthenticated, forbidden, absent-resource, and mutation error handling without extra reads or existence disclosure.

Acceptance / regression work:

- Backend read-shape cases for image web/private/worker with a pre-deploy command; empty image, image cron, static, legacy-runtime, native and Docker controls.
- A pinned-client contract test using the real normalize/default/validate/build pipeline, following `lego/cli/image_cron_clone_contract_test.go`; assert exact pre-deploy preservation and no invented build/start fields.
- Separately verify the shared REST list/detail/write-response and MCP list/verb/stack consumers, plus the unchanged flat GraphQL value. Cover explicitly clearing/overriding the command and existing authorization/not-found neighbors.
- Repeat the source → clone journey above without restating `--pre-deploy-command`; require both source and clone marker logs and live deploys. Delete the owned fixtures and verify list/detail/runtime absence.

## Dedupe, contract and limits

Searched open, blocked and done `.pm` for clone/pre-deploy combinations and `envSpecificDetails`; checked `git log -S PreDeployCommand -- lego/backend/internal/apps/render.go`. **w1/m167** repairs the image-cron command case only. **w9/m165** repairs Docker-cron command aliases. **w1/m33** supplies pre-deploy execution; its explicit-control behavior passes. None covers losing an image service's pre-deploy command during cloning. This omission remains in current inspected code, so it is not merely an already-fixed production lag.

The exact pinned client is the cloning oracle. Render's [prebuilt-image documentation](https://render.com/docs/deploying-an-image) explicitly supports a pre-deploy command, and ADR004's pre-deploy contract makes that step a rollout gate. No Render account was mutated. Upstream client-only startup-command restrictions, environment-variable copying, region aliases, paid-plan policy, and broader Docker/native clone behavior are separate from this finding.

Live coverage is image **web services** with harmless commands. Private/worker impact and the proposed shape are pinned-client/source verified offline; no paid fixtures were created. The full unmodified Render executable was not independently run. Actual migrations, empty-command override semantics and all auth-neighbor cases remain regression work, not claimed live results.

Cleanup completed: both clones, then source, deleted by creation-proven IDs; deploy children matched this run's recorded mutations and one-off-job lists were empty. All IDs disappeared from the service list, baseline services remained, and all three former public URLs returned HTTP 404. Filing only; no application code was changed.

REST get/list and MCP share the projection; GraphQL's flat field is untouched. Backend goldens `lego/cli/testdata/image-predeploy-clone-source-<type>.json` feed `lego/cli/image_predeploy_clone_contract_test.go`, which drives the pinned normalize/validate/build pipeline and fails for all three kinds without the nested field.
