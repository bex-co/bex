## Objective

Let a REST caller update an existing service's `healthCheckPath` after creation. Today `POST /v1/services` (create) accepts `serviceDetails.healthCheckPath` and threads it into `spec.healthCheckPath`, but there is no update path — `PATCH`/settings-update handlers silently drop the field.

## Context

- `lego/backend/internal/apps/rest.go` — REST handlers for services, including create and whatever update/settings endpoint exists today.
- `lego/backend/internal/apps/deploy.go` — where `serviceDetails.healthCheckPath` is threaded into `spec.healthCheckPath` on create.
- `lego/types/v1alpha1/app_types.go` — `AppSpec.HealthCheckPath` (or equivalent field name — confirm exact name).
- The operator already reconciles `spec.healthCheckPath` into a `ReadinessProbe` (`w1/m23/t001`, `app_controller.go` `reconcileKubernetes`) — this task is pure API plumbing, no operator change needed.

## Steps

1. Find the REST update/settings-patch handler for services (likely alongside instance-type/plan updates from `w1/m8`/`w5/m7`).
2. Add `healthCheckPath` to the accepted update fields, writing through to `spec.healthCheckPath` on the `App` CR.
3. Confirm empty-string / unset semantics match create (empty ⇒ default `/`).

## Files

- `lego/backend/internal/apps/rest.go`
- `lego/backend/internal/apps/deploy.go` (if the update path shares the create-side field-mapping helper)

## Acceptance criteria

- [ ] `PATCH` (or the existing settings-update REST verb) on a service updates `spec.healthCheckPath` on the underlying `App` CR.
- [ ] A subsequent `GET` on the service reflects the new value.
