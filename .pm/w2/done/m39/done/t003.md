## Objective

Expose the SSH-key core through thin REST, GraphQL, and MCP adapters with identical fields, validation errors, ownership semantics, and audit behavior.

## Context

- bex's API-first rule forbids a dashboard-only identity feature even though Render primarily documents key setup in its dashboard.
- All adapters register into the shared roots in `internal/api`; no adapter owns business logic.
- Responses may return the public key/fingerprint but never gateway internals or unrelated users' keys.

## Steps

1. Add list/create/delete routes, GraphQL fields/mutations, and MCP tools over the one `sshkeys.Service`.
2. Define a stable response containing id, name, fingerprint, public key, and created time; normalize all adapter errors through existing core helpers.
3. Wire the service in the API composition root and name write verbs in audit/event guard registries as appropriate.
4. Add surface-parity tests that drive the same inputs through all three adapters.

## Acceptance criteria

- [x] A caller can add, list, and delete only their own SSH public keys on all three surfaces.
- [x] Malformed, duplicate, unknown, and foreign key operations have consistent error codes/shapes.
- [x] Adapter-parity and authz-guard tests pass.

## Out of scope

- Dashboard UI and accepting SSH connections.
