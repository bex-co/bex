## Objective

Deploy the SSH gateway as an isolated, observable production component with a persistent host key, public TCP/22 endpoint, stable DNS, network policy, and namespace-scoped exec permission—without weakening node-admin SSH or bex-api RBAC.

## Context

- The official CLI invokes OpenSSH without a port override, so `sshAddress` must resolve to public port 22.
- Node-admin `:22` and its authentication-only baseline are unrelated and must not be replaced or exposed through this service.
- A regenerated host key causes alarming client warnings; custody/rotation must be deliberate and documented.

## Steps

1. Add a separate Deployment, ServiceAccount, Role/RoleBinding, Service/TCP route, NetworkPolicy, probes, metrics, limits, and disruption behavior for the gateway.
2. Provision a persistent host-key Secret out of band, document fingerprint publication/rotation, and fail startup if it is absent or malformed.
3. Route `ssh.<domain>:22` to the gateway, update firewall/LB and DNS automation as required, and set `BEX_SSH_HOST` only after reachability is real.
4. Add manifest validation proving the gateway has only App/pod read plus `pods/exec create`, while bex-api still lacks exec.

## Acceptance criteria

- [x] Public `ssh.<domain>:22` presents the documented stable fingerprint and reaches only the gateway.
- [x] The gateway can exec only in the configured tenant namespace; it cannot read Secrets or exec in platform/auth namespaces.
- [x] Existing node SSH, kube API, HTTP ingress, and bex-api permissions are unchanged.

## Out of scope

- Static source-IP allowlists for port 22 or changing the node-admin SSH trust model.
