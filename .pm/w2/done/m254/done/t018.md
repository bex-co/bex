## Objective

A web service created with `serviceDetails.buildSourceId` never rolls out on production. The operator's deploy registry gate waits for the service's own pull credential (`reg-pull-<ns>-<app>`), but nothing ever creates one for a linked service. The 503 "first deploy is in progress" page never clears. Make a linked service get, or reuse, a pull credential that zot accepts, and roll out.

## Context

Production walk, `/qa-find-bugs w4` loop, 2026-11-03 21:54–22:16 UTC, pin `fb6098dd2e37`, QA workspace `tea-daif693dqjvc73e7as3g`. Both resources were deleted afterwards.

- **Build source:** `bds-dbl5ajn73ids73e34clg` (express-hello-world, node, `yarn`); builds `succeeded` (see t016's walk).
- **Linked service:**
  - `POST /v1/services` `{"type":"web_service","name":"qa-20261103-linked","ownerId":…,"serviceDetails":{"plan":"free","buildSourceId":"bds-dbl5ajn73ids73e34clg","envSpecificDetails":{"startCommand":"node app.js"}}}` returned 201 `srv-dbl5g7f73ids73e34co0`, `url: https://qa-20261103-linked.onbex.co`.
  - Adding `runtime` returned a named 400 ("runtime cannot be set with buildSourceId; the build source provides it"), which is correct.
- **Deploys:**
  - The first deploy `dep-dbl5g7f73ids73e34cog` (`trigger:"other"`, `buildId:null`) stayed `created`.
  - After `POST /v1/build-sources/{id}/builds` succeeded, fan-out created `dep-dbl5l2f73ids73e34cp0` (`trigger:"new_commit"`, `buildId:"bld-dbl5kinpehks73fta5q0"`). It stayed `queued` for 7+ min.
  - Events show `deploy_started` for both and nothing after.
  - `https://qa-20261103-linked.onbex.co/` answered 503 "This service's first deploy is in progress" throughout.
- **App CR** (read-only `kubectl get apps.app.bex.co tea-daif693dqjvc73e7as3g-qa-20261103-linked`): `spec.buildSource.image: zot.bex-registry.svc:5000/tea-daif693dqjvc73e7as3g/tea-daif693dqjvc73e7as3g-bds-dbl5ajn73ids73e34clg:gen-2@sha256:7ec41f65…`. `status` is empty (no phase, no conditions) after 18 min.
- **Operator log** (`bex-controller-manager`), every ~15 s: `ERROR registry credential probe failed; requeueing … "error": "read credential for probe: get pull secret: secrets \"reg-pull-tea-daif693dqjvc73e7as3g-tea-daif693dqjvc73e7as3g-qa-20261103-linked\" not found"`.
- **Cause:**
  - `deployRegistryGate` (`lego/operator/internal/controller/app_controller.go:2832-2843`) runs `awaitRegistryCredActive` for any registry-hosted image, which includes the linked image.
  - The credential it awaits is minted only by `ensurePerAppRegistryCreds` (`:2331`), which returns early unless `appNeedsRegistryCred` (`:2323-2326`) is true.
  - That predicate checks `Spec.Repo`, `Spec.Image`, `Status.Image` and `Status.ArtifactImage`. A linked service has none of these; its image is `Spec.BuildSource.Image` (`lego/types/v1alpha1/app_types.go:459`). So the secret is never created and the gate requeues forever.
  - `copyLinkedBuild` (`controller/build_source.go:129-138`) also needs this App's registry auth (`builderAuthHeader`) to copy the carrier build into the service's repository.
- **Not fixed on `main`:** `9d4e3a138` (w2/m262) does not change `appNeedsRegistryCred`.
- **Not traced:** why the CR shows no `status.phase`/conditions while the gate holds. `awaitRegistryCredActive` passes `PhaseDeploying` and a waiting message, so the dashboard and API may never get the "waiting for the registry" explanation.

## Steps

1. `appNeedsRegistryCred`: also return true when `app.Spec.BuildSource != nil` and its image is registry-hosted. The linked service then gets its own credential, which `copyLinkedBuild` and the gate both need.
2. Confirm the gate's waiting state is written to the CR status while it holds. If not, set it, so a stuck rollout explains itself on the deploy and events instead of a bare `queued`.
3. Tests: an operator test that a linked App with no `Repo`/`Image` mints its pull secret and passes the gate, plus a regression test that an image-only or repo App still behaves as today.

## Implementation (2026-11-05, `/loopx w2`) — awaiting production verification

- **Predicate:** `appNeedsRegistryCred` is now also true for an App whose `spec.buildSource.image` is registry-hosted. A linked service therefore mints its own pull credential, which both `copyLinkedBuild` and the deploy gate need.
- **Gate status:** a failed credential probe now also stamps `Deploying` / `RegistryCredsPending` with the waiting message. A held rollout explains itself on the App and its deploy instead of showing an empty status.
- **Tests:**
  - `TestAppNeedsRegistryCredForALinkedBuildSource` (unit): linked with a registry build, linked with no build yet, linked with an external image, repo, external image only.
  - The envtest "mints the pull Secret for a service linked to a build source".
  - `GOWORK=off make test` passes.
- **Still open:** the production acceptance above (linked Free service Live, second build fans out, no `reg-pull-… not found` loop), once this commit is deployed.
