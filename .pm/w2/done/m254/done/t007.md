## Objective

Expose the same verbs on GraphQL and MCP, matching bex conventions.

## Context

- `gqlutil`, `mcputil` patterns; MCP pin has no build-source tools — these are bex extensions named after REST verbs.

## Steps

1. Add queries/mutations and MCP tools over the same service verbs.

## Files

- lego/backend/internal/buildsources/

## Acceptance criteria

- [x] Same semantics and errors as REST.

## Out of scope

- Anything outside this milestone's definition of done.

## Outcome (2026-11-03)

- **GraphQL:** queries `buildSources` (REST's `name`/`projectId`/created/updated filters, `cursor`/`limit` paging), `buildSource`, `builds` and `build`; mutations `createBuildSource` (git or image, seeding `envVars`/`secretFiles`), `updateBuildSource`, `deleteBuildSource` and `triggerBuild`. `buildId` on `triggerDeploy` landed with t013.
- **MCP:** `list_build_sources`, `get_build_source`, `create_build_source` (takes REST's request shape), `update_build_source`, `delete_build_source`, `trigger_build_source_build`, `list_build_source_builds` and `get_build_source_build`.
- **Build-time environment:** a build source's env vars, secret files and env-group links use the existing GraphQL/MCP env verbs with its `bds-` id as `serviceId` (`gqlutil.ScopeArg`, `mcputil.Scoped`, `secrets.envScope`). Every write there is staged, as on REST, and `patchServiceEnvironment` refuses a deploying `saveMode` on a build source. REST's `/v1/services` routes still never reach a carrier.
