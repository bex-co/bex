## Objective

Verify that idle suspend/resume (`w2/m278`) and filesystem snapshot capture/restore (`w32/m285`) keep brokered credentials working on the resumed/restored sandbox with zero secret material ever persisted into a rootfs or snapshot image, and document the `HTTPS_PROXY` vs Render transparent-443 difference honestly in `ADR104` and `ADR018`.

## Context

- Idle resume (`lego/backend/internal/sandbox/idle.go`) and snapshot restore (`lego/backend/internal/sandbox/snapshots.go`) recreate the sandbox Pod from a committed rootfs image.
- Because secrets never enter the sandbox container, a snapshot image committed from a sandbox using brokered credentials must carry zero secret bytes, while the restored sandbox inherits the group's live credentials (never stale secrets from capture time).

## Steps

1. Add tests covering idle suspend → resume and snapshot capture → restore: confirm the recreated Pod carries `bex.co/sandbox-group`, broker proxy env, and Broker CA trust, respects updated/disabled credentials after resume/restore, and contains zero credential secret values in Pod env/metadata or snapshot records.
2. Walk the broker end to end on `dev-2` (or local test harness with real `bex-api` + `bex-ssh-gateway`) verifying a live credential create → injected request → disable → immediate cutoff → resume/restore continuity.
3. Update `docs/ADR104-sandbox-render-parity.md` and `docs/ADR018-render-parity.md` to record the `HTTPS_PROXY` + Broker CA vs Render's Firecracker transparent TCP-443 interception difference honestly as awaiting user sign-off.
