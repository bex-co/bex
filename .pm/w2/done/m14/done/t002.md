## Objective

Extend the operator's `imagePullSecrets` resolution so an App whose `image` references a registry host the workspace has stored credentials for gets a materialized `kubernetes.io/dockerconfigjson` Secret in its namespace, referenced in the pod's `imagePullSecrets` — additive to, not replacing, the existing internal-Zot pull-secret path.

## Context

- `lego/operator/internal/controller/app_controller.go:303-312`'s `imagePullSecrets` today only handles the internal Zot registry (`r.RegistryPullSecret`/`r.Registry`) and leaves any other image untouched (assumed public).
- The App CR itself doesn't currently carry a registry-credential reference — bex-api (not the operator) resolves which credential (if any) matches the image's host at reconcile time, and materializes the Secret bex-api creates for the operator to reference (mirrors the clone-secret pattern: bex-api creates the opaque Secret, the operator copies/references it, never reads the token itself — `copyCloneSecret`).
- The operator must stay DB-free (mechanism only, per `CLAUDE.md`) — matching credentials to hosts is bex-api's job at write time, not something the operator queries the control-plane store for.

## Steps

1. Decide the materialization point: when bex-api creates/updates a service pointing at a private-registry image, it looks up a matching `registry_credentials` row by host, and creates/updates a `kubernetes.io/dockerconfigjson` Secret in the App's namespace (named predictably, e.g. `<app>-registry-pull`).
2. Extend the operator's `imagePullSecrets` to also include this Secret's name when present (checked via a well-known Secret name or an annotation bex-api sets on the App CR).
3. Confirm both pull-secret sources (internal Zot + external registry) can coexist without conflict for different images.

## Files

- `lego/operator/internal/controller/app_controller.go`
- bex-api's service create/update path (wherever it materializes the clone-secret, mirror that pattern)

## Acceptance criteria

- [ ] An App referencing a private external-registry image gets the correct `dockerconfigjson` Secret in its `imagePullSecrets`.
- [ ] The internal-Zot pull-secret path is unaffected for Zot-hosted images.

## Out of scope

- Auto-rotating credentials — bex only stores and surfaces what the tenant supplies (t007 surfaces staleness, doesn't rotate).
