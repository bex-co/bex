## Objective

Add a `SetPlan` verb to the Postgres service layer that validates the target plan, writes the control-plane row first (when the instance is store-managed) then patches `Database.spec.plan` on the CR — mirroring `apps.Service.SetPlan`'s row-then-CR ordering and its Render-plan-spelling mapping exactly.

## Context

- `lego/backend/internal/apps/*.go` — `SetPlan` and its tests (`TestSetPlanValidatesAndMapsRenderSpelling`, `TestSetPlanManagedAppWritesRowThenCR`, `TestSetPlanUnmanagedAppSkipsStore`, `TestSetPlanRowWriteFailureLeavesCRUntouched`) are the reference implementation to mirror.
- `lego/types/v1alpha1/database_types.go` — `Plan string` is already a mutable spec field; no CRD change needed.
- `lego/backend/internal/postgres/` — service layer package; add the verb alongside existing lifecycle verbs (`lifecycle.go`).

## Steps

1. Add `Service.SetPlan(ctx, id, plan string)` to `lego/backend/internal/postgres`, validating the plan against the known Postgres plan catalog (reject unknown plans as `core.ErrBadRequest`, no-op).
2. Row-then-CR ordering: if store-managed, write the CP row's plan first; only patch the `Database` CR after the row write succeeds (a row-write failure must leave the CR untouched, matching `apps.SetPlan`'s guarantee).
3. Unmanaged (hand-applied CR, no CP row) instances skip the store and patch the CR directly.

## Files

- `lego/backend/internal/postgres/lifecycle.go` (or a new `plan.go`)
- `lego/backend/internal/postgres/postgres_test.go`

## Acceptance criteria

- [ ] `SetPlan` on a store-managed instance writes the CP row, then the CR, in that order.
- [ ] `SetPlan` on an unmanaged instance patches the CR directly, no store write.
- [ ] An unknown plan name returns `core.ErrBadRequest` and touches neither the row nor the CR.
- [ ] A row-write failure (store-managed) leaves the CR untouched.

- REST/GraphQL/MCP wiring (t002).
