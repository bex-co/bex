## Objective

Decide what happens to API keys created by a departing member, with the trade-off written down — this is a product decision with a real cost on each side, and the implementation is short once it is settled.

## Context

- bex keys are **workspace-owned**: `BindClient` (`lego/backend/internal/store/store.go:800`) gives the Hydra client id its own `tenant_members` row at role `developer`, and `ListAPIKeys`/`RevokeAPIKey` scope by that binding (`internal/apikeys/service.go:349,405`). `CreatedBy` is recorded as provenance only (`service.go:45`).
- Render's keys are **user-owned** — they leave with the user. That divergence is the heart of the decision.
- The account-deletion path already chose revocation: `AccountTeardown.CleanupSubject` (`apikeys/service.go:114`) unbinds then deletes every key with a matching `CreatedBy`.
- The cost of revoking on member removal: a departing employee's key may be the one a production CI pipeline authenticates with; silently killing it is an outage. The cost of not revoking: a removed member retains developer access indefinitely through a credential nobody attributes to them.
- Middle option: retain but surface — mark the key as "created by a removed member" on the API-keys list so a remaining admin can decide.

## Steps

1. Write the three options with their failure modes into the milestone README.
2. Check what the API-keys UI shows today (is `createdBy` even rendered? `apikeys/graphql.go:35` exposes it) — an option that relies on visibility is only viable if the surface shows it.
3. Decide, and record the decision plus reasoning; name which ADR gets the amendment (ADR024 for the membership rule, ADR086 for the disposition table).
4. Note explicitly whether the same rule applies to the `w5/m102` leave path (it should).
