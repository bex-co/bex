# 075 — Creating a service under a name whose App is still being deleted may answer 500

Why: the w2/m256 t015 fix (2026-11-08) handles a still-terminating App's name in the Blueprint plan path. A plain `POST /v1/services` (and GraphQL/MCP create) with that name likely meets the same AlreadyExists ("object is being deleted") inside `planNewApp`/`writeNewApp` and returns 500. This is unverified.

- **Reproduce:** on dev-2, delete a service, then immediately create one with the same name.
- **Render:** check whether Render lets a just-deleted name be reused. Then answer the same way, or with a named 409 ("the earlier service with this name is still being deleted; retry shortly"), never a 500.
- **Acceptance:** a REST/GraphQL/MCP test with a terminating holder. The dev-2 walk returns no 500.

## Done (2026-11-08, `/loopx w2`)

- **Repro on dev-2:** the holder App was kept Terminating with a temporary finalizer. The usual answer was a misleading `409 CONFLICT "already in use"`, because `nameTaken` counted the Terminating App. A 500 is reachable only in the race where that probe misses and the dry-run or real create meets AlreadyExists ("object is being deleted").
- **Fix:** a name held by a deleting App now answers `409 SERVICE_NAME_STILL_DELETING` ("…was just deleted and its cleanup is still finishing; retry in a minute") on REST, GraphQL and MCP. A raw AlreadyExists from the plan or the write is re-read and named the same way. A live holder keeps the name-in-use refusal.
- **Tests:** `create_name_deleting_test.go` (apps and api: REST, GraphQL, MCP, with API-server-like dry-run semantics) and `create_name_deleting_pg_test.go`. Each fails without the fix. The real-DB suite and `make lint` pass.
- **dev-2 re-walk:** while the App was Terminating, every surface answered `409 SERVICE_NAME_STILL_DELETING`. After the release, create returned 201. No 500 at any point.
- **Render:** Render accepts a same-named create at once (names are not locked; the subdomain gets a suffix). bex cannot yet, because the App object name derives from the service name. ADR018's "Address a service by name" row records this as a divergence awaiting the user's sign-off.
