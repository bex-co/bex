## Objective

Guarantee web push is a second **transport**, not a second **policy model**: the existing per-member push policy (enabled, event filter, minimum urgency, timezone, working/quiet hours, bounded deferral, per-service overrides) decides whether a logical push notification exists at all, and every transport — Expo and webpush — delivers the same already-policy-filtered rows. No new policy table, no per-transport event picker.

## Context

- Policy evaluation: `lego/backend/internal/notifications/delivery_policy.go` + `push_policy_test.go` — the `PushWorker` evaluates the member's policy before materializing `push_notifications`/`push_deliveries` rows (ADR052 §c).
- Policy storage: `notification_settings` rows (see migration references in `lego/backend/internal/store/migrate_test.go` — `0028_notification_deploy_started`, `0032_notification_failure_only`); push policy read/write via `GET/PATCH /v1/notification-settings/push` in `rest.go` and `pushNotificationSettings` in `graphql.go` (~line 202).
- t002's `webpush_subscriptions.preference_id` references `notification_settings` exactly as `device_push_subscriptions.preference_id` does.
- Dashboard policy picker already exists: `dashboard/src/features/notifications/components/push-notification-settings-panel.tsx` + `lib/push-policy.ts` — t005 reuses it untouched for event selection.

## Steps

1. Audit the t003 fan-out: confirm webpush deliveries are created strictly downstream of the existing policy gate (one logical `push_notifications` row → N transport deliveries), never from a parallel evaluation path.
2. Verify per-service overrides, quiet hours, and minimum-urgency deferral apply identically: a policy that suppresses/defers a notification suppresses/defers it for browser subscriptions too (table-driven test beside `push_policy_test.go`).
3. Ensure disabling push in the member's policy stops webpush deliveries without touching subscriptions (re-enabling resumes with the same registered browsers).
4. Confirm the settings surface needs no new fields: `PATCH /v1/notification-settings/push` remains the single write path; document in code comments that transports share the policy.

## Files

- `lego/backend/internal/notifications/delivery_policy.go`, `push_worker.go` (+ `push_policy_test.go` additions)
- `lego/backend/internal/notifications/rest.go`, `graphql.go` (read-only verification; changes only if a availability field is needed)

## Acceptance criteria

- [ ] One policy evaluation produces the logical row consumed by both transports (asserted in a test: policy-suppressed event ⇒ zero deliveries of either kind).
- [ ] Quiet-hours deferral defers the browser delivery identically to the native one.
- [ ] Per-service override filtering applies to webpush deliveries.
- [ ] No new policy table or per-transport event-selection field exists.

## Out of scope

Per-transport policy granularity (e.g. "urgent only on phone, everything in browser") — a deliberate non-goal until user demand exists; ADR052 policy vocabulary changes.
