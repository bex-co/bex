## Objective

Give the dashboard a browser-notifications flow: a service worker that displays pushes and handles notification clicks (allowlisted relative-route navigation), a settings toggle that runs the `Notification.requestPermission()` + `PushManager.subscribe(applicationServerKey: <VAPID public key>)` flow and registers the subscription via t002's API, and honest states (unsupported browser, permission denied, channel not configured server-side). Same-origin only; Kratos HttpOnly-cookie auth is untouched — the DO_NOT_DO no-OAuth2-dashboard rule stands.

## Context

- Existing settings surface: `dashboard/src/routes/notifications.tsx` renders `dashboard/src/features/notifications/components/notification-settings-panel.tsx` + `push-notification-settings-panel.tsx`; hooks `use-notification-settings.ts`, `use-update-push-notification-settings.ts`; GraphQL doc `dashboard/src/features/notifications/api/notification-settings.graphql`; locales `locales/en.ts` + `zh.ts` (both must gain strings).
- The push panel already reports "not configured" when the server transport is absent (availability endpoint `GET /v1/notification-settings/push/availability`) — extend, don't fork, for web-push availability + the VAPID public key the client needs.
- `dashboard/public/` currently holds only `favicon.ico`/`logo.png` — the service worker file (e.g. `public/push-sw.js`) lives here so it's served same-origin at a stable scope; dashboard is TanStack Start + Apollo (see `dashboard/CLAUDE.md` before editing).
- Push payload is ADR052's closed envelope with an allowlisted **relative** route — the SW click handler must only ever navigate within origin.

## Steps

1. Add `dashboard/public/push-sw.js`: `push` event ⇒ decode envelope, `showNotification(title, {body, data.route, tag/collapse})`; `notificationclick` ⇒ focus/open the relative route only (reject absolute/external URLs).
2. Add a subscribe hook (`use-web-push-subscription.ts`): feature-detect (`'serviceWorker' in navigator && 'PushManager' in window`), fetch the VAPID public key from the availability surface, register SW, subscribe, POST subscription (endpoint + p256dh/auth) to t002's register verb; unsubscribe path calls `pushManager.getSubscription().unsubscribe()` + the unregister verb.
3. Extend `push-notification-settings-panel.tsx` (or a sibling web-push section) with the toggle + states: unsupported browser, permission `denied` (with recovery hint), server not configured, subscribed-on-this-browser. Event selection stays the existing picker (t004 — shared policy).
4. Add en/zh locale strings; update `notification-settings.graphql` if a new field/mutation is exposed; component tests beside `__tests__/push-notification-settings-panel.test.tsx` (mock `PushManager`).

## Acceptance criteria

- [ ] Toggle on in a real Chromium/Firefox profile ⇒ permission prompt ⇒ subscription registered server-side; toggle off unsubscribes both browser- and server-side.
- [ ] SW displays an OS notification from a pushed envelope and clicking it navigates to the in-app route; external URLs in `data` are ignored.
- [ ] Unsupported/denied/unconfigured states render honest copy in en + zh; `yarn test` passes.
- [ ] No auth change: registration rides the existing Kratos session cookie on same-origin fetches.

## Out of scope

Full PWA installability (manifest/offline) — separate work; iOS Safari verification narrative lives in t006; native app (w11) untouched.
