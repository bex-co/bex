## Objective

Add a Web Push protocol transport (RFC 8291 `aes128gcm` payload encryption + RFC 8292 VAPID JWT auth) beside the Expo adapter, and teach the push worker to fan a due logical notification out to the member's active browser subscriptions through the same durable `push_notifications`/`push_deliveries` machinery — at-least-once, leased, TTL'd, with 404/410 responses pruning exactly the dead subscription.

## Context

- Worker: `lego/backend/internal/notifications/push_worker.go` — tails the feed via `push_watermark`, materializes one logical inbox row + at-most-one leased delivery per active installation; `classifyPushError` (~line 705) returns `(code, terminal, prune)` and `w.prune` (~line 722) revokes the exact destination on `DeviceNotRegistered`. Web push's equivalent prune signal is HTTP 404/410 from the push service.
- Transport boundary: `lego/backend/internal/notifications/push/transport.go` (provider-neutral `Transport`, payload caps: `MaxPayloadBytes` 4096 etc.); Expo impl `push/expo.go` with loopback fake `push/loopback_test.go`. Adapter seam: `push_adapter.go`.
- Store: `lego/backend/internal/store/migrations/0063_push_deliveries.up.sql` (`push_notifications`, `push_deliveries`, `push_watermark`); `lego/backend/internal/store/push_deliveries.go` (8-attempt retry, 90-day sweep — reuse, don't fork).
- Payload stays ADR052's closed four-field envelope (schema version, notification id, event type, status copy + allowlisted relative route) — never secrets/emails/logs.
- Config from t001 (`WebPushConfig`); subscriptions from t002.

## Steps

1. Implement `push/webpush.go`: encrypt the envelope per RFC 8291 for a subscription's `p256dh`/`auth`, sign a VAPID JWT (`aud` = endpoint origin, `sub` = `BEX_WEBPUSH_SUBSCRIBER`, short `exp`), POST to the endpoint with `TTL` and `Urgency` headers; use a vetted Go webpush library or std-crypto implementation — decide and record in the task log.
2. Map responses: 201 ⇒ delivered; 404/410 ⇒ error classified `prune=true`; 429/5xx ⇒ retryable; 400/413 ⇒ terminal. Extend `classifyPushError` or give the webpush transport its own classifier feeding the same `(code, terminal, prune)` contract.
3. Extend the worker/adapter so a due notification produces deliveries for BOTH active Expo installations and active webpush subscriptions (each its own `push_deliveries` row/lease); `prune` revokes the matching t002 subscription row.
4. Loopback fake push service test (mirroring `push/loopback_test.go` + the fake Expo pattern) proving encryption round-trip shape, 404/410 prune, retry on 5xx.
5. Extend `push_metrics.go` labels so web-push operations are distinguishable from Expo.

## Acceptance criteria

- [ ] A due notification with one Expo installation + one browser subscription yields two independent leased deliveries; each retries/completes independently.
- [ ] A 410 from the fake push service prunes exactly that subscription (revoked in store, metered like `invalid_token`).
- [ ] Payload on the wire is encrypted (fake service asserts `aes128gcm` content-encoding + VAPID `Authorization` header) and ≤ 4 KB.
- [ ] Web-push transport nil ⇒ worker behavior byte-identical to today (Expo-only tests unchanged).
