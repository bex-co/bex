## Objective

An App whose **current generation's** terminal build failure is already recorded on the Ready condition must not re-run its build when the failed Job disappears. Today `buildFromSource` calls `build.EnsureBuild` (create-if-absent) **before** consulting `buildOutcomeAlreadyRecorded`, so once the failed Job is TTL-reaped, the next reconcile touch — an operator restart resyncs every App — re-creates the Job and re-runs the whole doomed build (clone, npm/BuildKit, a build slot, metering).

## Context

Live prod evidence (`hetzner-prod`, 2026-08-20, operator rollout ~22:14Z):

- `tea-da1eg9gbiuuc73bd8uag/market-size`: Ready `BuildFailedUserError` observedGeneration 1 recorded **2026-08-17**, yet `bex-build/bld-…-market-size-gen-1` was 17m old — re-created on restart, re-ran `npm install` against a repo with no `package.json`, failed again.
- `default/beancount-forum`: Ready condition from **2026-08-02** (gen 29), Job `bld-beancount-forum-gen-29` re-created 32m ago — re-ran a clone that fails auth every time.
- Side effect: the re-dispatch path calls `setPhase(PhaseBuilding, …)`, which **overwrites the durable Failed marker's reason**, so the `buildOutcomeAlreadyRecorded` gate misses on the next failure and the outcome is **double-metered** (`recordBuildOutcome` re-recorded — the w7/m83 SLO series corruption the gate exists to prevent) and the App's phase flaps Failed→Building→Failed on the dashboard.
- The `build.PhaseFailed` branch comment (app_controller.go ~739) already promises "Returning nil leaves the App Failed until the tenant bumps generation" — the promise only holds while the failed Job still exists.

## Steps

1. In `buildFromSource`, before the registry-cred wait / caps / secret relocation / `EnsureBuild`, check whether the Ready condition records a terminal build-failure reason (`BuildFailedUserError` / `BuildFailedInfrastructure` / `BuildFailed`) at `ObservedGeneration == app.Generation`; if so `return halt(ctrl.Result{}, nil)` without touching the build plane.
2. Keep the escape hatches: a generation bump (new push/deploy) re-dispatches normally; an explicit deploy trigger that bumps release generation is unaffected.
3. Confirm the pre-deploy analogue (`reconcilePreDeploy` already does terminal bookkeeping that "guards against re-creating the Job after its TTL reap") — mirror its pattern, don't invent a new one.
