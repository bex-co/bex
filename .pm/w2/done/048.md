# 048 — Every production GitOps sync stalls while the tenant pool is full: Argo waits on the `tenant-headroom` placeholder

Why: `bex-system/tenant-headroom` is a negative-priority placeholder that is _supposed_ to sit Pending when the tenant pool has no free slot, but Argo treats its Deployment health as a sync gate, so a full tenant pool silently freezes every platform change (secrets, alerts, CronJobs, operator config) until capacity frees up.

**Seen:** 2026-10-20 06:17Z–06:41Z+ (during `w2/m170`'s rollout), read-only on `hetzner-prod`.

## Evidence

- `bex-platform-prod` `status.operationState`: `phase: Running`, `message: "waiting for healthy state of apps/Deployment/tenant-headroom"`, started 06:17:01Z for revision `45fd398e4`; the newer `e7d71fd10` (m170's resealed SealedSecrets + probe CronJob) stays OutOfSync behind it.
- `tenant-headroom-cdfcffddc-kshcg` Pending 52m: `0/11 nodes are available: 3 Insufficient cpu, 3 Insufficient memory, 8 node(s) had untolerated taint(s) … preemptionPolicy=Never`; cluster-autoscaler `NotTriggerScaleUp … 3 max node group size reached`. Requests 1 CPU / 2Gi (`deploy/gitops/base/tenant-headroom.yaml`, from `d82cc98cd`).
- Real tenant pods were Pending at the same time (QA CronJob runs and a `w6/m148` probe in `bex-canary`), i.e. the pool was genuinely at its maximum — exactly the condition in which the placeholder can never become Ready.

## Do

1. Confirm in Argo's resource tree / sync waves why this Deployment gates the operation (wave ordering vs. app health) and how long a stall can last (no operation timeout?).
2. Remove the gate without weakening real health checks: e.g. move the placeholder to its own child Application (root app does not assess child Application health), or give it a health customization that treats a Pending placeholder as Healthy. Do not shrink or delete the headroom itself — it is the w1 rollout-eviction fix.
3. Prove on the local cluster: fill the tenant pool so the placeholder is Pending, change another platform manifest, and show the sync completes.

## Acceptance

- [ ] With the placeholder Pending, a platform manifest change syncs to completion.
- [ ] `scripts/gitops-validate.sh` green; the headroom still preempts and reserves as before.

**Done 2026-10-20.** Root cause: in the prod root app the placeholder Deployment sat in sync wave 0 while waves 1–4 hold the child Applications, so Argo waited for it to turn healthy before applying wave 1 — and a placeholder that cannot fit a full pool never does. Fix: `deploy/gitops/base/tenant-headroom.yaml` puts the Deployment in its own final wave (`"10"`), where nothing waits on it; it still applies and still reserves a slot as soon as one exists (priority, preemption, pool and size unchanged). `scripts/gitops-validate.sh` now fails closed unless the headroom wave is strictly greater than every other wave in the rendered prod root app (red-checked: wave 3 fails against the wave-4 `bex-postgres` Application).
