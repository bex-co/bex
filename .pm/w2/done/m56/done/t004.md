## Objective

Stop the dashboard from saying a service has already scaled when the GraphQL mutation has only accepted the desired replica count.

## Context

- `use-scale-service.ts` currently emits “Scaled to N” immediately after mutation success, before the operator and Deployment converge.
- The mutation's success means the requested intent was accepted, not that two ready replicas exist.
- Existing service phase, desired-replica, and error refresh paths should be reused rather than inventing a dashboard-only operation state.

## Steps

1. Change the localized success acknowledgement to an accepted/in-progress form such as “Scaling to N…” or “Scaling requested.”
2. Refresh the existing service state after mutation and expose convergence or failure where the current page already has enough API state to do so.
3. Preserve optimistic desired-replica behavior only where it is visually distinguishable from ready capacity.
4. Add focused tests for accepted, rejected, pending, and failed scale requests in English and Chinese.

## Files

- `dashboard/src/features/services/hooks/use-scale-service.ts`
- `dashboard/src/features/services/`
- `dashboard/src/**/locales/`
- `dashboard/src/**/*.test.tsx`

## Acceptance criteria

- [ ] A successful mutation never uses completed-tense copy before convergence is known.
- [ ] API rejection and later reconciliation failure remain visible and are not overwritten by an optimistic success toast.
- [ ] Desired replicas and ready/current replicas are not presented as the same fact.
- [ ] English and Chinese copy and tests stay in sync.

## Out of scope

- A new generic operations framework, a service-page redesign, or new API fields without a demonstrated contract gap.
