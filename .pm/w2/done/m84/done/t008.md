## Objective

Verify the account-deletion experience against current Render behavior and keep bex's API/safety differences explicit.

## Context

- Render exposes account deletion at the bottom of the user profile/settings page with a confirmation, but its documented public API exposes `GET /v1/users` and no self-delete operation.
- bex's ADR008 API-first rule means its dashboard action must still be backed by an API. This does not require giving a machine key or delegated agent the power to erase the human owner.
- Multi-workspace disposition is a bex safety contract because public Render material does not document the cascade/leave/block semantics.

## Steps

1. Re-check the live/current Render settings placement, copy, confirmation, post-delete behavior, and public OpenAPI before closeout; record dated evidence without copying private data.
2. Update `docs/ADR018-render-parity.md` with the dashboard match and deliberate REST/GraphQL extension, direct-session-only restriction, and MCP omission.
3. Confirm REST and GraphQL preview/request semantics and error shapes are identical over the one Core service.
4. Flag any new drift as follow-up rather than weakening the deletion safety contract silently.
