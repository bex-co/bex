## Objective

Classify every workspace the deleting subject belongs to and converge it through delete, leave, or blocker behavior without orphaning administration.

## Context

- `workspaces.Service.Delete` is already the complete workspace teardown: FGA tuples, OpenBao/env groups, managed datastores, sandboxes, Stripe subscription, tenant FK cascade, projector kick, and App CR purge.
- `members.Service.Remove` already expresses revoke-before-row-delete and last-admin safety, but it is an admin-removes-member verb; self-account offboarding needs a narrow internal seam, not a forged admin request.
- Account policy from t001: only member → delete workspace; another admin exists → preserve workspace and remove subject; other members but no other admin → typed blocker requiring promote/remove/delete first.

## Steps

1. Add a store-backed preview that returns stable workspace ids/names grouped into `delete`, `leave`, and `blocked`, without exposing other members' subjects.
2. Re-check the preview atomically when beginning deletion; lock workspace membership decisions in deterministic order and return typed blocker details before writing irreversible intent.
3. Extract/reuse narrow internal workspace-delete and member-offboard seams so account cleanup gets the existing purgers, FGA ordering, last-admin concurrency guards, and cache invalidation instead of cloning them.
4. On a surviving shared workspace, clear `owner_identity_id` when it names the deleting subject and preserve the tenant/resources/members; do not assign another human's personal-workspace binding.
5. Make every delete/leave step idempotent for worker retry, including already-absent tuples, memberships, tenant rows, and post-cascade artifacts.

## Acceptance criteria

- [ ] Preview and mutation return the same delete/leave/block disposition from authoritative state.
- [ ] A blocker prevents the deletion intent and names the workspace plus the required remedy.
- [ ] Sole-member workspaces use the full existing teardown; no resource/purger class is skipped.
- [ ] Shared workspaces with another admin remain accessible and unchanged except for the deleting member/provenance binding.
- [ ] Concurrent role/remove/delete operations cannot leave a surviving workspace with zero admins.
- [ ] Re-running after any intermediate step is harmless and converges.

## Out of scope

- General self-service workspace ownership transfer.
