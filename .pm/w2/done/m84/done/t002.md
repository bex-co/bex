## Objective

Create the durable, race-safe boundary that prevents a deleting identity from being onboarded into a fresh personal workspace.

## Context

- `internal/api/auth.go` calls `Onboarding.EnsureTenant` for every human Kratos session and human OAuth token.
- `tenantService.EnsureTenant` creates a personal tenant whenever `TenantForOwner` returns not found. Deleting that tenant before deleting Kratos and then retrying would recreate it unless deletion intent is authoritative.
- Cleanup crosses Postgres and several external systems; it cannot rely on one request staying alive.

## Steps

1. Add the next store migration for a minimal `account_deletions` intent/state row keyed by identity subject, with claim/retry metadata and bounded diagnostic text but no copied email or bearer credential.
2. Add store methods to begin idempotently, claim, advance, fail/retry, and finish deletion; make concurrent requests converge on one intent.
3. Make onboarding check the intent before invite redemption, cache lookup, grant repair, or workspace mint and return a typed pending/deleted result instead of a generic 503.
4. Evict tenant/auth caches when deletion begins so a positive cache cannot bypass the tombstone.
5. Add a bounded poll worker/metric for retrying incomplete intents and surfacing age/failure without logging identity traits or secrets.

## Acceptance criteria

- [ ] Beginning deletion twice creates one durable intent and one cleanup stream.
- [ ] A pending subject cannot redeem invites, receive grants, resolve a cached personal workspace, or mint a new one.
- [ ] The worker safely reclaims abandoned/in-flight attempts after restart and exposes bounded observability.
- [ ] No email, session cookie/token, API-key secret, or Ory credential is stored in the intent row or logs.
- [ ] Store-off or required dependency-off mode fails before accepting deletion.

## Out of scope

- A grace-period/cancel-deletion feature.
