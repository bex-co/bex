## Objective

`apps.Service.Restart` (~`lego/backend/internal/apps/service.go:960`) and GraphQL `restartServer` bump `Spec.RestartedAt` directly on the App CR, completely bypassing the `deploys` package — no deploy-history row is ever created, unlike every other rollout-triggering verb (Trigger, Rollback). Route restart through `deploys.Trigger(deployMode: deploy_only)` instead, so a restart finally shows up in `list_deploys`/the Events tab like everything else.

## Context

- `lego/backend/internal/apps/service.go` `Restart` — current implementation, direct CR patch.
- `lego/backend/internal/apps/graphql.go` — `restartServer` mutation resolver, calls `apps.Service.Restart`.
- `lego/backend/internal/deploys/service.go` — `Trigger`, now accepting `deployMode` after t003.
- `dashboard/src/features/services/components/service-row-actions.tsx` — the `restart` `LifecycleAction`, called from the services list rows (`hideRestart` prop already added this session for the header context — the list still uses the full menu including Restart).
- `dashboard/src/features/services/hooks/use-service-lifecycle.ts` — the `restart` mutation wiring (`RestartServerDocument`) the list rows call today.

## Steps

1. Decide the shape: either (a) `apps.Service.Restart` internally calls `deploys.Trigger(..., deployMode: deploy_only)` instead of patching `RestartedAt` directly (keeps the existing `restartServer` GraphQL mutation name/shape, changes only its internals), or (b) deprecate `restartServer` and point the dashboard's restart action at `triggerDeploy(deployMode: deploy_only)` directly. Prefer (a) — smaller blast radius, no GraphQL schema/mutation-name churn, no dashboard rewiring beyond what's already needed.
2. Implement the internal call-through; keep `apps.Service.Restart`'s existing signature/authorization (`core.RelCanOperate`) unchanged.
3. Verify a restart on a repo-backed service still just restarts (doesn't accidentally rebuild) — `deploy_only` on a repo-backed service is REJECTED per t003, so restart must call `Trigger` with the mode that's actually valid for that service's backing (this task needs to reconcile: restart is meant to be "just bounce the pods," but t003 says repo-backed `deploy_only` is rejected. Resolve this explicitly — likely: for a repo-backed service, "Restart" still means a full rebuild+redeploy via `deployMode: build_and_deploy` (bex's honest reality, already true today via the `RestartedAt`→generation-bump path) — the consolidation's value is the deploy-history row, not a new no-rebuild guarantee this milestone explicitly said bex can't deliver. For an image-backed service, `deploy_only` applies and is a true no-rebuild restart.
4. Update `dashboard/src/features/services/components/manual-deploy-button.tsx`'s "Restart service" wiring is t006, not this task — this task is backend-only.

## Acceptance criteria

- [ ] Calling `restartServer` (or its REST/MCP equivalents) creates a deploy-history row, visible via `list_deploys`.
- [ ] A repo-backed service's restart still rebuilds (unchanged real behavior — t003 established that's the honest constraint), now just with a history row; an image-backed service's restart is a true no-rebuild pod bounce via `deploy_only`.
- [ ] `ServiceRowActions`' existing restart flow (list rows) and its tests still pass unmodified in behavior — only the underlying verb's side effects (a new deploy row) change.

## Out of scope
