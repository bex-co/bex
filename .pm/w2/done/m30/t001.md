## Objective

Decide whether `clearCache` can be a real, actionable verb or must be an honest no-op. bex's build path (`lego/operator/internal/build/build.go`, shipped `w1/m5`) dispatches a rootless BuildKit Job per generation — determine whether that Job (or BuildKit's daemon/cache mount) persists any cache across separate build Jobs, or whether every build already starts cold.

## Context

- `lego/operator/internal/build/build.go` — the Job spec BuildKit runs under.
- If each build Job is a fresh pod with no shared cache volume/registry cache export, then every build is already cache-free and `clearCache` has nothing to do — document that plainly rather than pretending to honor an enum with no effect.
- If a cache does persist (e.g. a PVC-backed cache mount, or `--export-cache`/`--import-cache` against a registry), `clearCache: "clear"` should actually invalidate it (skip the cache import for that one build).

## Steps

1. Read `build.go`'s Job spec for any cache volume, `--export-cache`/`--import-cache` flags, or persistent BuildKit daemon.
2. If found: note exactly what "clearing" means mechanically (delete a PVC's contents? skip an import flag for one build?).
3. If not found: write the one-line finding into this task's completion note — it feeds t003/t005 directly.
