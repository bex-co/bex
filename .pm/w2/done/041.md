# 041 — Blueprint validation accepts a health-check path that service updates reject

Why: automation receives a successful validation result for a configuration that violates the documented health-check contract; create and update should enforce the same path rule.

- **Severity:** minor (false validation success; no runtime outage demonstrated).
- **Source / goal:** user-requested looping `/qa-find-bugs-cli`, targeting w2, 2026-10-02; dependable Render-compatible hosting automation (ADR008 / ADR006 / ADR049).
- **Versions/context:** installed `/opt/homebrew/bin/bex` v0.2.1, Render CLI v2.27.0 (`a764810a768202704e7206eb7b87a47211fcd98e`); reproduced with checkout launcher `00c5aeba9`. Production `https://api.bex.co/v1/`, deployed revision unknown, human device OAuth, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), non-TTY JSON output.

## Reproduction and complete relevant output

Save this as `render.yaml` (validation does not create resources):

```yaml
services:
  - type: web
    name: qa-validation-only-20261002
    runtime: image
    image:
      url: docker.io/mendhak/http-https-echo:35
    plan: free
    healthCheckPath: missing-slash
```

Run with an isolated, authenticated QA config and the workspace above:

```sh
bex blueprints validate ./render.yaml -o json
```

Actual, reproduced in fresh processes with both binaries: exit **0**, empty stderr; released-binary repeat took **0.89 s**. Complete stdout:

```json
{"plan":{"services":["qa-validation-only-20261002"],"totalActions":1},"valid":true}
```

Expected: HTTP 200 validation result with `valid:false`, a located `errors[]` entry at `services[0].healthCheckPath` (line 8, column 22), and CLI exit 1. Reuse the existing message `health check path must start with /`. Render's [Blueprint reference](https://render.com/docs/blueprint-spec#healthcheckpath) and [health-check instructions](https://render.com/docs/health-checks) require a leading `/`. Render account behavior was not exercised; this expectation is documentation-backed and agrees with Bex's existing update contract.

Controls: omitting the field validates successfully; `maxShutdownDelaySeconds: 0`, misspelled `healthChekPath`, duplicate `plan`, and a nonexistent `fromService` reference each produce located validation errors and exit 1. On this run's disposable free image service `srv-db02bec5o9vs73dt7s70`, `bex services update <id> --health-check-path missing-slash --confirm -o json` exited 1 in 1.50 s with `Error: received response code 400: bad request: health check path must start with /`. The valid control deployed live and served HTTP 200; it was deleted and all four baseline services remained present.

## Root cause, fix, and blast radius

At `00c5aeba9`, `apps/schema/render.yaml.json:971` constrains this field only to a string. `apps/blueprint.go:639` compiles/parses then calls the shared service validation; `apps/deploy.go:1326` calls `specFromCreate`. `apps/service.go:2479` validates the creation request, but `validateTypeSpecificCreate:2638` has no health-path check, and `:2567` copies the raw value into the App spec. In contrast, `apps/settings_check.go:43` trims and checks the leading slash for settings updates.

Use one path normalization/validation helper for creation and updates, retaining empty/omitted TCP health checks and the established service-kind policy. Invoke it before any creation/store mutation; keep the vendored Render schema truthful rather than editing the upstream artifact to hide a missing semantic check. Map the refusal to the actual Blueprint field through the existing source-location machinery.

`specFromCreate` has **four non-test call sites**: interactive create (`service.go:1903`), Blueprint validation (`deploy.go:1327`), Blueprint apply (`deploy.go:2725`), and current-state planning (`blueprint_state_plan.go:202`). Create adapters on REST (`rest.go:576`), GraphQL (`graphql.go:1400`), and MCP (`mcp.go:262`) all supply the field; Blueprint validation/preview and dashboard consumers inherit the shared fix. The operator's `deployment_projection.go:298` directly projects the path into `HTTPGetAction`; it is not the admission boundary. Test web/private and existing worker/cron/static policy without silently widening health-check support.

- Regression checks: same malformed YAML returns located `valid:false` and CLI exit 1; `/health`, empty and omitted paths remain valid with correct HTTP/TCP semantics. Invalid shared creates must fail before persistence; valid create/update and all three API adapters retain their contracts. Existing malformed persisted values require an explicit compatibility decision, not an automatic migration.
- Auth neighbors: preserve existing unauthenticated/forbidden/workspace-not-found behavior; do not expose workspace resources through error messages.
- **Unverified:** malformed direct create, actual Blueprint apply, runtime behavior of a missing-slash probe, and GraphQL/MCP/UI live behavior were not exercised. These are code-traced affected paths, not claimed live failures.
