## Objective

Give PostgreSQL and Key Value list/header menus the same permission behavior as their detail controls, including an explanation that works with pointer and keyboard navigation.

## Context

- Delete and PostgreSQL lifecycle verbs have multiple placements. Gating only the detail danger row leaves an alternate 403 path.
- Disabled Radix menu items need an explicit accessible tooltip/wrapper pattern; a disabled item alone cannot reliably explain itself.

## Steps

1. Apply the exact `can_create` delete and `can_operate` lifecycle gates to every datastore row/header action placement.
2. Reuse or extract a small permission-aware menu/button wrapper so denial reasons are consistent and focusable without breaking menu semantics.
3. Guard all event handlers as well as presentation so a denied item cannot open a dialog through keyboard, pointer, or stale state.

## Files

- `dashboard/src/features/databases/components/database-row-actions.tsx`
- `dashboard/src/features/keyvalue/components/key-value-row-actions.tsx`
- `dashboard/src/features/capabilities/components/**`

## Acceptance criteria

- [x] List, header, and detail placements agree on the governing relation and denial copy.
- [x] Mouse and keyboard users can discover the reason, and denied actions cannot open confirmation dialogs or execute callbacks.

## Out of scope

- Project/Environment moves and redesigning the action-menu information architecture.
