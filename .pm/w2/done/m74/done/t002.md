## Objective

Make PostgreSQL plan, lifecycle, and delete controls predict their distinct server authorization outcomes before a dialog or mutation begins.

## Context

- `DeletePostgres` requires `can_create`; `SetPlan`, suspend, resume, and restart require `can_operate`.
- The current plan cards and detail danger row are role-blind, so a blanket `can_create` fix would wrongly remove valid contributor operations.

## Steps

1. Gate plan selection/save and suspend/resume/restart on definitive `canOperate` denial with the localized operation reason.
2. Gate delete on definitive `canCreate` denial with the localized create reason.
3. Compose permission, busy, suspended, billing, and protected-resource states so denied controls never open confirmation flows or call hooks.

- `dashboard/src/features/databases/components/database-plan-section.tsx`
- `dashboard/src/features/databases/components/database-danger-actions.tsx`

## Acceptance criteria

- [x] A contributor can still select/save plans and run lifecycle operations but cannot begin delete; a viewer missing `can_operate` cannot begin either class.
- [x] Every definitive denial has the correct localized reason and issues no mutation.

## Out of scope

- Changing backend relations, billing/plan eligibility, or resource-protection confirmation rules.
