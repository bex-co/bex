## Objective

A service's explicitly set secret file beats a linked environment group's file of the same name, the same rule env vars already follow. The operator projects the service's own files Secret last into `/etc/secrets`, whatever its position in `spec.filesFromSecrets`, so the result is independent of whether the file or the link came first. Between groups, last linked wins, consistent with t003.

## Context

- The service's own `<name>-files` Secret joins `spec.filesFromSecrets` by `addString` when its first file is saved (`lego/backend/internal/secrets/files.go:224-228`), so on a created-with-files service it is **first**. A linked group's `<evg>-files` Secret is appended at link time (`lego/backend/internal/envgroups/service.go:1084`), so it comes **later**.
- `secretFileMounts` projects `filesFromSecrets` in list order into one `/etc/secrets` volume with no duplicate-path guard (`lego/operator/internal/controller/app_controller.go:3894-3925`). The later source's `qa.txt` is what the pod sees.
- The env-var contrast: `envFromSources` deliberately puts the service's own Secret **last** so "a service's own variable overrides a linked group's — matching Render" (`app_controller.go:3847-3878`). Files got no equivalent ordering.
- Live evidence (w1/095, 2026-09-14): a service created with `qa.txt = "from-service"` served `from-service`, then after `POST /v1/env-groups/<evg>/services/<srv>` (group holding `qa.txt = "from-group"`) served `from-group`, while `GET /v1/services/<srv>/secret-files/qa.txt` still returned `from-service`.
- A service created **without** files that links a group and adds a file later is already service-last today (same `addString`), so the fix must be order-independent.
- Render documents precedence for env vars only ("that value always takes precedence over any linked environment groups") and is silent on files.

## Steps

1. In `secretFileMounts`, identify the service's own files Secret (`<name>-files`, or the pending annotation the pending-files path uses) and place it last in the projected sources regardless of list position. Keep group sources in `filesFromSecrets` order so last linked still wins between groups.
2. Confirm removing the service's file falls back to the group's file, and that restart and redeploy do not reshuffle the order.
3. Operator test: a projection-order test where the service files Secret is last with groups linked before and after the first service file; a control where no group defines the same name.
4. Note the kubelet's observed duplicate-path behavior (later projected source wins) in the test comment, since that is the mechanism the ordering relies on.
