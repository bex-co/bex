## Objective

Implement ADR054 D4: for `ags-…` targets only, honor `subsystem: sftp` by exec-ing the fixed sandbox `sftp-server` path, so Zed's automatic local-download-then-upload fallback installs `zed-remote-server` without any egress change.

## Context

- Sandbox egress stays closed — `zed.dev` is NOT added to any allowlist; Zed's in-sandbox `curl` fails, then it uploads over SSH preferring the SFTP subsystem (`crates/remote/src/transport/ssh.rs`).
- `nativessh/session.go`: subsystem requests currently `Reply(false)`. New behavior: name must be exactly `sftp` AND target is a sandbox → `runExec` with the fixed argv `/usr/lib/openssh/sftp-server` (never caller input, no `/bin/sh` wrapper needed — decide argv shape in review); anything else unchanged. `isSCPProtocolCommand` rejection stays.
- `lego/agent-image/Dockerfile` (Debian bookworm-slim): add `openssh-sftp-server` to the apt install line; binary lands at `/usr/lib/openssh/sftp-server`. Uploads land in `/home/bex/.zed_server/` (writable rootfs, uid 10001) and die with teardown — correct per ADR054.
- Optional fast path (baked pinned `zed-remote-server`) is explicitly deferred — not this task.

## Steps

1. Session-handler branch + fixed-argv exec for the `sftp` subsystem, sandbox targets only.
2. Dockerfile package addition.
3. Tests: sftp subsystem on a sandbox target execs the fixed path; on an `srv-…` target still refused; subsystem name `sftp-anything` refused; scp protocol still refused.
