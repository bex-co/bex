## Objective

Check that the change is consistent across every surface it exposes: REST, GraphQL and MCP in `lego/backend/`, the `dashboard/` UI, Blueprints and the CLI. Compare `https://oidc.bex.co/<tea>/.well-known/{openid-configuration,jwks.json}` with Render's live documents (fields, status codes for malformed ids and the root path, content types) and confirm bex adds no REST/GraphQL/MCP/UI surface Render lacks. Flag any drift as follow-up work rather than silently diverging.

## Progress (2026-11-18)

Checked without production:

- **No new REST, GraphQL, MCP, dashboard, CLI or Blueprint surface**, as on Render, which has none: the issuer is a host-routed handler outside the three adapters (`internal/api/server.go`), and no fragment, schema field, tool or route under `/v1` was added.
- **Documents on dev-2 against Render's live ones** (t006's rehearsal): same fields in the same order, same `Content-Type` and `Cache-Control`, Render's JWKS members, Go's `404 page not found` for `tea-abc`, `tea-d0000000000000000001`, `/` and `/<tea>`, and `405 Allow: GET` with no body for `POST`/`HEAD` on a document's path, malformed id included (Render re-probed 2026-11-18).
- **Known differences, none tenant-visible:** bex adds its usual security headers (`Content-Security-Policy`, `X-Frame-Options`, `Vary: Origin`) and the limiter's `RateLimit-*` headers; Go's router answers an uncleaned path (`//tea-…/…`) with a 307 to the cleaned one where Render answers 404 (recorded in ADR116 D1; no provider sends one); Render's full token claim set is unverified (no sample token is published; ADR116 D3).

**Left:** the same comparison against `https://oidc.bex.co` (status codes, content types, the certificate) once the production pin carries `68b45459b`.

## Production comparison (2026-11-18, pin `1ec5007be0fa`)

`https://oidc.bex.co/tea-daif693dqjvc73e7as3g` and `https://oidc.render.com/tea-c0000000000000000000`, probed side by side, matched on every probe:

- **Documents:** both answer `200 application/json`. Discovery has the same five keys in the same order. Every JWKS key has the members `use, kty, kid, crv, alg, x, y` in that order (t006 checks the values).
- **Refusals:** `tea-abc` (either document), `tea-d0000000000000000001`, `/`, `/<tea>`, `/<tea>/.well-known/` and `/<tea>/.well-known/foo` each answer `404 text/plain; charset=utf-8` `404 page not found`.
- **Methods:** `POST` and `HEAD` on a document's path, malformed id included, answer `405` with `Allow: GET` and no body.
- **Certificate:** both are publicly trusted certificates from Google Trust Services WE1.
- **No other surface:** the issuer host serves none of bex-api's routes (`/v1/services` and `POST /graphql` answer 404), and `api.bex.co` does not serve the issuer's documents (404).

Nothing new to fix or file. The known differences above still hold, none of them tenant-visible. One differs in shape on production: bex-api itself still answers an uncleaned path (`//tea-…/.well-known/jwks.json`) with a 307 to the cleaned one. Production's edge cleans the path before bex-api sees it, though, so a doubled slash gets the document itself (`200`) where Render answers 404. That happens for every `*.bex.co` host (`api.bex.co//healthz` answers 200). ADR116 D1 now says so. No relying party sends such a path.
