## Objective

Render's `GET /v1/blueprints/{id}` returns `resources[]` — the managed resources with `id`, `name`, and `type` (`web_service`, `static_site`, `private_service`, `background_worker`, `cron_job`, `postgres`, `key_value`, `environment_group`, …). Add the same array to bex's by-id read on REST, the GraphQL `Blueprint` type, and MCP `get_blueprint`, resolving the manifest's declared resource names to their current live ids.

## Context

- The manifest names services/databases/keyValue/envGroups; current ids live in the control-plane store (services `srv-…`, postgres `dpg-…`, keyvalue `red-…`, env groups). Resolve name → id within the owner workspace at read time; a declared resource that no longer exists is omitted (Render lists only existing managed resources) — never an error.
- `BlueprintView` (`lego/backend/internal/apps/blueprint.go:51-61`) is the shared shape all three adapters render; add the field once there.
- Type vocabulary must be Render's exact strings (see `docs/ADR018-render-parity.md` service-type rows).

## Steps

1. Resolver: parse stored manifest → declared names/kinds → store lookups → `[]BlueprintResource{ID, Name, Type}`.
2. Thread through REST by-id, GraphQL type (new object type), MCP `get_blueprint`; list endpoints stay lean (Render's list omits resources).
3. Tests: mixed stack resolves all kinds; deleted resource omitted; foreign-workspace resource never leaks.

## Files

- `lego/backend/internal/apps/blueprint.go`, `graphql.go`, `mcp.go`, `rest.go`
- `lego/backend/internal/apps/blueprint_test.go`

## Acceptance criteria

- [ ] Names resolve to canonical ids (`srv-`/`dpg-`/`red-`), not display names.
