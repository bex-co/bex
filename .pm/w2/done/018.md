# Backend deploy-status: record a rolled-out-then-superseded generation truthfully

Follow-up flagged by `w2/m72` t006 (Render-parity check) — see [docs/ADR060-build-worker-reliability-and-performance.md](../../../docs/ADR060-build-worker-reliability-and-performance.md) §D1a "Render-parity check".

**Gap.** After the ADR060 §D1a operator change, under a push cadence faster than the build, the run-to-completion build rolls out an intermediate generation whose deploy row bex-api already marked `canceled` (the DB-only newest-wins `cancelOpenDeploys` in `lego/backend/internal/store/store.go` fires at deploy-create, before that generation went live). So an intermediate commit briefly serves live traffic while its deploy row reads `canceled` — Render instead shows an in-flight deploy going live, then superseded.

**Not a bug / not blocking.** Superseded→`canceled` is Render-consistent, and the forward-progress guarantee + latest-row `build_in_progress`→`live` progression already hold from the operator change. This is a deploy-history fidelity refinement.

**Possible fix (needs sizing → likely a milestone, touches all 3 surfaces).**

- Add a distinct non-terminal→terminal `superseded` status to the `store.go` deploy-status vocabulary + `openDeployStatuses`, OR let an in-progress row reach `live` before the newer row supersedes it (don't force-close a row that's actively `build_in_progress`/`update_in_progress` at create time — only cancel `queued` rows).
- Reconcile `observedDeployStatus`/`supersededDeployStatus` (`lego/backend/internal/store/reconciler.go`) with the new state.
- Mirror across REST/GraphQL/MCP + dashboard deploy history; compare against Render's deploy-status vocabulary.

Prereq context: the operator now pins `status.releaseGeneration` to the in-flight build (`w2/m72`), so the CR-side signal for "which generation is actually live" is already truthful; this is purely the bex-api deploy-row model.

**Resolved 2026-08-16.** Implemented the second option without adding a bex-only wire status: one executing deploy remains open, one latest overlap is internally marked pending and exposed as `queued`, and a newer trigger cancels only the replaced pending row. The reconciler processes both rows while projecting App evidence only onto the matching release generation, so an executing generation reaches `live` before the later generation deactivates it. REST, GraphQL, MCP, and dashboard keep Render's existing eleven-value vocabulary. Store/reconciler tests cover coalescing, capacity-queued active builds, evidence isolation, and live→deactivated progression; the migration and concurrent-trigger invariant were also exercised against real PostgreSQL.
