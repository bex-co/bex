# 050 — Production deploys starve under concurrent pushes: a ready fix waited ~2 h because every run was superseded

Why: with several sessions pushing to `main`, `deploy.yml` cancels pending runs and skips the pin of a finished run whenever newer production manifests exist, so a shipped fix can sit unpinned for hours while each newer run is superseded in turn.

**Seen 2026-10-28** (w2/m169): `f1e28beb3` (SSH fix) was pushed 09:17Z; run `f1e28beb3` cancelled, `bb0cac58e` cancelled, `e2c8e7baf` cancelled, `fa918b387` **succeeded at 10:16Z but logged** `superseded by newer production manifests on origin/main (fe594754); this run's images will not be built/pinned` and skipped the rollout — although `fe5947541` was a `docs(pm)` commit. The fix reached production only with the `d66f96c06` pin (`9d0b7fa51`), about two hours after the push.

## Do

1. Confirm what "production manifests" the supersession check compares and why a `.pm`-only commit counted (or whether `d66f96c06` was the real superseder and the message named the newest HEAD).
2. Make a successful run pin its images unless a newer run is **actually going to pin** (e.g. only defer to a newer in-progress run that touches production inputs; never to doc-only commits), so a quiet minute is enough for the newest code to reach production.
3. Keep the existing stale-digest protection (`deploy.yml` normalized-compare) intact.

## Acceptance

- [ ] A run whose only newer commits are docs/`.pm` pins and rolls out.
- [ ] Under a burst of code pushes, the newest successful run pins within one run's duration of the last push.

## Resolved 2026-10-29 (`/loopx w2`)

**The premise was half wrong.** The docs commit did not supersede `fa918b387`. `scripts/deploy-superseded.sh` only diffs the manifest paths Argo syncs (`deploy/gitops`, `deploy/opensandbox`, `lego/operator/config`, `deploy.yml`). `git log fa918b387..fe5947541 -- <those paths>` shows exactly one commit, **`d66f96c06`** ("fix(runtime): bind image ports to selected release configuration", which changed `lego/operator/config`). That was a real manifest change. Pinning images built from the older tree onto it is exactly what the guard must refuse. Its own run then pinned (`9d0b7fa51`). The script's message printed **origin/main's tip** (`fe594754`, a `docs(pm)` commit) instead of the commit that moved the manifests, and that sent this note's diagnosis after the wrong commit.

**Fix (shipped with this closure):** the superseded messages now name the manifest-changing commits (`changed by: <sha…>`). On a shallow CI checkout the script deepens history on that rare path first. If it still cannot resolve the range, it says so instead of naming the tip. Test: `deploy-superseded.test.sh` now asserts that a manifest commit with a docs commit on top is named, and the docs tip is not.

**Acceptance:**

- [x] A run whose only newer commits are docs/`.pm` pins and rolls out. This already held (rc 1). Pinned by the existing `non-triggering (docs)` case.
- [x] Under a burst of code (image-source) pushes, the newest successful run pins: rc 3 builds and pins (w1/116). The narrower case that cannot be "fixed" without breaking the stale-digest guard is a push that changes **manifests** while a run is building. That run must not pin, and the next serialized run pins. Worst case is therefore about two run durations after such a push. That is by design, and acceptance does not cover it.
