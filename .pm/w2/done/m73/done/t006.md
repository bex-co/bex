## Objective

Create one revision-aware Core patch for Environment Group env vars and secret files, with opaque preservation and explicit save intent, so a staged dashboard edit commits atomically and causes zero or one rollout/rebuild per linked service rather than one rollout per changed row.

## Context

- `w5/m44` already established sparse opaque environment patches, `SecretKVSnapshot`/`PutCAS`, compensation rules, and `save_only`/`deploy`/`rebuild` semantics for service-local configuration.
- Group list/get intentionally expose keys/names only; a staged patch must preserve unchanged secret values without revealing them to the browser.
- Existing per-key/replace endpoints are compatibility contracts and currently roll immediately.
- A group fans out to several services, so “one rollout” means at most one selected action for each linked service after one successful source/projection commit.

## Steps

1. Define a neutral sparse group patch over env/file upsert, delete, and rename operations plus expected revision and save mode; reuse service-environment types/helpers where their secrecy semantics match.
2. Apply env and files with CAS and compensation that cannot overwrite a newer winner; return names/revision/affected-service outcomes only.
3. Project both group Secrets as one logical commit, then execute `save_only`, deploy, or rebuild exactly once per linked service with explicit partial-failure reporting/retry boundaries.
4. Expose the patch identically through REST, GraphQL, and MCP; keep old item routes and implement them via the new primitive with their legacy immediate-deploy default.
5. Ensure generated upserts use t001's server-side primitive and all errors redact values/content.

## Acceptance criteria

- [ ] One patch can add/update/delete/rename several vars and files while preserving every omitted opaque value.
- [ ] Stale revision conflicts are coded and leak no values; concurrent winner and compensation tests prove no lost update.
- [ ] `save_only` changes durable/projection state without rolling; deploy/rebuild cause at most one corresponding action per linked service and never an intermediate rollout.
- [ ] A post-persistence deployment failure is retryable without replaying or losing the secret patch.
- [ ] REST, GraphQL, and MCP share one Core contract/result/error vocabulary.
- [ ] Legacy single-item writes retain documented behavior through the new primitive.
