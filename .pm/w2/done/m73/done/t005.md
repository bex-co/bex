## Objective

Add Render's Manage → Move group workflow so an authorized user can move a group between compatible Environments or back to workspace scope without rebuilding the Environment membership UI or overwriting unrelated groups.

## Context

- Core already models `EnvGroupView.EnvironmentID` and Environment membership full-replace verbs; the group detail lacks a move action.
- Calling `setEnvironmentEnvGroups` naively with only the current group would detach sibling groups.
- A move that would strand incompatible service links must fail atomically with actionable, non-secret detail.

## Steps

1. Add a Manage-menu Move group dialog reusing existing Project/Environment selectors and the scope labels from t004.
2. Build the target membership update from freshly fetched Environment group ids so unrelated memberships survive.
3. Validate source access, target workspace/environment, linked-service compatibility, and pin the group id throughout; reject rather than partially unlink/move.
4. Support moving to workspace scope and idempotent selection of the current scope.
5. Reconcile Apollo caches for group detail, group list, source Environment, and target Environment after success.

## Acceptance criteria

- [ ] Move dialog lists only authorized targets and clearly identifies workspace scope/current Environment.
- [ ] A successful A → B move preserves every unrelated group membership in A and B and updates list/detail without reload.
- [ ] Moving to workspace scope works; choosing the current scope is a no-op.
- [ ] Incompatible existing links cause one coded failure with no membership or link mutation.
- [ ] REST/GraphQL/MCP membership behavior remains consistent, with integration coverage for preservation and rollback.

## Out of scope

- Automatically moving services with the group.
- Adding Environment selection to the create dialog unless the parity pass proves Render now exposes it there.
