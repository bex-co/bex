## Objective

De-risk t002. Show that a CNPG `Cluster` with `spec.certificates.serverTLSSecret` + `serverCASecret` (issued by cert-manager) serves that certificate on 5432, while CNPG keeps managing the client/replication CA, so an HA pair still replicates.

## Steps

1. On `dev-2` (local CAPD cluster), create a two-instance tenant database through bex. Then issue a cert-manager `Certificate` for its public SNI name from a local CA issuer (a stand-in for Let's Encrypt).
2. Patch the CNPG Cluster's `spec.certificates` with the server secrets, keeping CNPG's `clientCASecret`/`replicationTLSSecret`. Record which fields CNPG requires together.
3. Verify that `openssl s_client -starttls postgres` shows the issued cert, `psql` with `sslmode=verify-full sslrootcert=<local CA>` connects, and replication lag stays 0 across a write.
4. Renew the certificate (`cmctl renew` or delete the secret) and record whether CNPG reloads it without a restart.

## Acceptance criteria

- [ ] Findings (fields, reload behavior, any CNPG version caveat) recorded in the milestone README.
