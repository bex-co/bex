## Objective

Build `lego/backend/internal/keyvalue/` mirroring `internal/postgres/` (`service.go` + `tiers.go`): a core service that lists/gets/creates/deletes `KeyValue` CRs (`lego/types/v1alpha1`) in the watched namespace and derives connection info from the credentials Secret — internal `redis://` URI always, external `rediss://` only when `spec.public` and `status.externalHost` are set, plus the `cliCommand`.

**Id decision (revised during implementation):** use the KeyValue **name as the id**, exactly like its managed-Postgres sibling — NOT a minted `red-` id. `docs/identifiers.md` § Known deviations already records managed databases as name-keyed CRs with no separate opaque key; KeyValue has identical properties, so extending that deviation keeps the two datastore surfaces uniform. Minting a `red-` kind while Postgres uses name-as-id would make sibling surfaces inconsistent — a worse outcome than either uniform choice. The `internal/id` registry is left unchanged (no `red-` kind), and the deviations note in `docs/identifiers.md` is extended to name key-value stores alongside databases (done in t007's ledger/doc pass).

## Context

- Mechanism contract (w1/m14, live in prod): CR spec `plan`/`version`/`storageGB`/`public`; status `phase`/`host`/`port`/`secretName`/`externalHost`; Secret keys `host`/`port`/`username`/`password`/`uri`. Plans come from `lego/types/tiers` (`Valkey` catalog: `free`/`starter`/`standard`).
- Follow `internal/postgres/service.go` for the Core-method + k8s-client shape and `tiers.go` for the plan mapping; docs/bex-api.md one-core/thin-adapters rule.
- `id.New(kind)` only — never hand-concatenate (docs/identifiers.md); adding the Kind updates the package registry, and its guard test enforces it.
- Render object shape per the t001 capture (id/name/plan/status enum/…); fields the CR lacks (`maxmemoryPolicy`, `persistenceMode`, `ipAllowList`) are omitted or fixed-default for now — record the divergence for t007.

## Steps
