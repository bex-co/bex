# Service/Deploy REST response wire-shape bugs found by the CLI-compat checklist

`w9/m2`'s Render CLI walk found two live wire-type mismatches in bex-api's Service/Deploy REST responses, both sub-hour serializer fixes:

- **`Service.autoDeploy` is a JSON boolean; Render's OpenAPI (and every generated client) expects the string enum `"yes"`/`"no"`.** Breaks `GET /v1/services` (list), delete, and anything else that decodes a full `Service` object client-side — confirmed against the real `render-oss/cli`: `json: cannot unmarshal bool into Go struct field Service.service.autoDeploy of type client.AutoDeploy`. ADR006/ADR018 already document the *create* body as using `"yes"/"no"` correctly; only the read path regressed to a bare bool. Not caught by `w7/done/m30`'s conformance allowlist — worth adding a case there once fixed so it can't silently regress again.
- **`Deploy.image` is a bare string; Render expects `{ref, registryCredential, sha}`.** `render deploys list` fails: `json: cannot unmarshal string into Go struct field Deploy.deploy.image of type struct{Ref *string; RegistryCredential *string; Sha *string}`.

Also worth a look while in this area: `render services instances <id>` gets `failed to list instances: 404 Not Found` — not yet root-caused (could be a missing route, or a downstream symptom of the autoDeploy decode failure resolving the service first); check both.

Evidence + full repro harness: `docs/cli-compatibility-checklist.md` (root causes RC2 and the `deploys list`/`services instances` rows).

Source: `w9/m2` (Render CLI compatibility), 2026-07-15.

Update 2026-07-15: both wire-shape bugs shipped and were re-verified live (`Service.autoDeploy` in `dfff3034`; `Deploy.image` in the subsequent CLI-compatibility pass). The genuinely separate `GET /v1/services/{id}/instances` 404 is now materialized as **w6/m26** by explicit user direction. This note is therefore retired rather than left as duplicate ownership.
