## Objective

Confirm the two REST changes are consistent with what GraphQL, MCP and the dashboard already expose, and match the pinned Render spec's `retrieve-webhook` and `list-notification-overrides` operations. Record any drift instead of silently diverging.

## Steps

1. **Event types across surfaces.** Compare REST `GET /v1/webhooks/event-types` with GraphQL `webhookEventTypes` and the vocabulary MCP `list_webhook_endpoints` returns. Same set, same identifiers. Render has no event-types route; this is a bex extension, and the ADR018 row 228 (Outbound event webhooks) note should say so.
2. **Overrides across surfaces.** Compare the REST list's per-service projection with the per-service REST `GET`, GraphQL and MCP reads of `notificationsToSend`/`previewNotificationsEnabled`. Same values for the same service. Confirm the `default`-service decision from t002 against Render's documented response, and check whether the official Render CLI calls `list-notification-overrides` (`docs/cli-compatibility-checklist.md`).
3. **Envelope check.** Validate the list response against the spec's `notificationOverrideWithCursor` schema through the strict validator's response path if one exists, else by field-by-field comparison.
4. **Record.** Update `docs/ADR018-render-parity.md` rows 227 and 228 and `docs/render-artifacts/notify-on-fail.md` with what was checked and when. File any drift as a `w2/NNN` inbox note.

## Acceptance criteria

- [ ] The event-type vocabulary is identical on REST, GraphQL and MCP.
- [ ] A service's override values are identical on the REST list, the per-service REST read, GraphQL and MCP.
- [ ] ADR018 rows 227 and 228 and `notify-on-fail.md` are updated with the check date. Any drift is filed.
