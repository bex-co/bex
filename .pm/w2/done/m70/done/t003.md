## Objective

Make cron webhook events describe observed run lifecycle rather than API intent: every scheduled or manual run produces a stable start fact and one terminal fact with the Render outcome, while cancellation requests remain ordinary audit intent.

## Context

- `App.status.runs` already exposes run name, start/finish times, and running/succeeded/failed/canceled state through `internal/apps/cron_runs_test.go` and `types.AppStatus`.
- `internal/webhooks/service.go` currently maps `TriggerCronRun` to started and cancel verbs to ended, so scheduled runs are invisible and cancel acceptance masquerades as completion.
- `internal/store/reconciler.go` is the existing bex-api observer that derives durable facts from operator status without importing backend persistence into the operator.

## Steps

1. Add checked cron-run start/end fact types and stable source keys derived from the run identity.
2. Have the control-plane reconciler append them idempotently from `App.status.runs`, translating terminal state to `succeeded|failed|canceled`.
3. Remove the misleading trigger/cancel audit-to-webhook mappings and project the observed facts instead.

## Acceptance criteria

- [x] Scheduled and manual runs both emit exactly one `cron_job_run_started` and one `cron_job_run_ended` across repeated reconciliation.
- [x] Ended payload status matches the observed terminal state; an accepted cancel request emits no ended event before status convergence.
- [x] A store/reconciler restart neither loses nor duplicates a cron lifecycle fact.

## Out of scope

- Changing cron scheduling, retention, concurrency, or run-control APIs.
