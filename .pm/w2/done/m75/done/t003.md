## Objective

Move static-site object identity to the t001 workspace-scoped S3 prefix: a labeled `static_site` App's publish Job syncs to the new prefix and its delete-time purge removes the new prefix, while the static-server resolves a host to whichever prefix the App's current published revision actually lives under (dual-read), so already-published legacy sites keep serving unchanged until migrated (t004) or republished.

## Context

- `lego/operator/internal/publish/publish.go` — `Options.Prefix()` returns `<appID>/<revision>/` (line 144); `Options.AppID` is documented as "the service name — the first object-key segment" (line 118); the delete-time purge builds `s3://<bucket>/<appName>/` at line 487 (the `aws s3 rm` Job); publish Job naming uses the `pub-` prefix (line ~464). Env contract: `BEX_STATIC_S3_*`, `BEX_STATIC_PUBLISH_S3_SECRET`, `BEX_REGISTRY_BUILD_PULL_SECRET` (CLAUDE.md operator table; docs/ADR029-static-sites.md).
- `lego/operator/internal/staticserver/staticserver.go` — `Site` (line 85) carries `AppID` + `Revision`; `objectKey` = `AppID + "/" + Revision + "/" + path` (line 96); the host→Site resolver watches App CRs (`BEX_STATIC_NAMESPACE`). Origin reads: `lego/operator/internal/staticserver/s3origin.go` `Get(ctx, key)`.
- `lego/operator/internal/controller/app_controller.go` wires publish (Ensure/Observe per ADR068 finding 6) and populates the static-server-visible status; `app_controller_staticsite_test.go` + `lego/operator/internal/publish/publish_test.go` + `lego/operator/internal/staticserver/staticserver_test.go` are the test surface.
- Dual-read shape: the prefix is recorded per published revision (a revision prefix is immutable, staticserver.go:24), so the cleanest fallback is "App status records which scheme its current revision was published under; the resolver builds the key from that", not probing S3 twice.

## Steps

1. Thread workspace identity into `publish.Options` (new field alongside `AppID`) and compute `Prefix()` per t001 for labeled Apps; keep bare `<appID>/` for unlabeled ones.
2. Record the published prefix scheme (or the full prefix) in App status / the resolver's Site so the static-server serves legacy revisions from the legacy prefix and new publishes from the new one.
3. Point the delete-time purge Job at the prefix(es) the App actually published under.
4. Extend publish + staticserver unit tests: same-named Apps in two workspaces map to disjoint prefixes; legacy Site still resolves.
5. `make test` from `lego/operator/`.
