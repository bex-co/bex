## Objective

Flip the supersede semantics per the t001 decision: a newer generation arriving while a build runs writes `pendingGeneration` (overwriting any older pending value) and **never deletes the running Job**; when the active build reaches a terminal state (success, failure, timeout), the slot dispatches immediately with the latest generation. Once the image is pushed, that generation's rollout proceeds — the pending slot waits for it. The explicit Cancel verb still deletes the running Job (human intent); a canceled/failed/timed-out build releases the slot on the same reconcile pass.

## Context

- t001's ADR decision defines the guarantee: ≥1 completed deploy per build-duration window; convergence to latest within one cycle of pushes stopping.
- Current cancel-active path lives in lego/operator/internal/build (newest-wins delete before dispatch) — this is the code being retired.
- bex-api's Cancel verb (w2/m10) computes `bld-<name>-gen-<generation>` in `BEX_BUILD_NAMESPACE` and deletes it directly — that path must keep working and must be distinguishable (t005 labels) from supersede.
- `BEX_MAX_CONCURRENT_BUILDS` admission applies at slot-dispatch time like any other admission.

## Steps

1. Replace the cancel-active-then-dispatch path with write-pending-slot; ensure spec updates during a build never touch the running Job.
2. On terminal Job observation (t003 watch), release the slot: admit + dispatch `pendingGeneration` if set, clear it if it equals the just-built generation.
3. Preserve Cancel-verb preemption: a Job deleted out from under the operator is observed as terminal and releases the slot (no wedge).
4. Guard the rollout point-of-no-return: image pushed ⇒ Deployment update proceeds for that generation even if a newer generation is pending.
5. envtest: rapid-generation sequence (5 spec bumps during one build) ⇒ exactly one running Job throughout, one dispatch after, final image = latest generation.
