# Tenant restart loop: eden-cms-v2 liveness-killed 33×/16h while pegged at its CPU limit

From the 2026-08-20 `hetzner-prod` inspection. `tea-d98210cbbpdc73dcrkvg-eden-cms-v2` restarted 33× in 16h: the pod runs at 497m of its 500m CPU limit (free-tier Guaranteed 500m/512Mi), so the liveness `GET /` (timeout 5s, failureThreshold 6) times out under throttle → kubelet SIGTERM → clean exit 0 → loop. `beancount-cms-v2` and `block-eden-mono` on the same tenant pool show intermittent readiness/liveness timeouts too.

Mostly a tenant-sizing problem, but check the platform response: (1) did the ADR052 crash/restart-loop notification actually fire for this service? (2) consider whether liveness timing for small tiers should tolerate CPU-throttle (longer `timeoutSeconds`/`periodSeconds` derived from tier) — a CPU-starved-but-serving app is arguably better left unkilled; (3) the dashboard should make "you are pinned at your CPU limit" visible next to the restart count. Investigate/decide first — no mechanism change without evidence.

**DONE 2026-08-23 — investigated, decisions recorded, no mechanism change.** Evidence:

1. **Did the ADR052 notice fire?** Partially. The fact pipeline fired — `service_event_facts` shows 1399 `server_failed`/`server_available` pairs all-time for `srv-d9e40ei9086p3l1jri30` (eden-cms-v2), last 2026-08-21 20:55Z, covering the 2026-08-20 loop window. But **delivery is push-channel-only** (`device_push_subscriptions`/`webpush_subscriptions`) and this tenant has **zero subscriptions and zero `notification_settings` rows** → nothing was ever deliverable. Email (`notifications/service.go`) covers only deploy started/succeeded/failed, never availability. So the loop reached no human.
2. **Tier-aware probe timing: rejected.** The loop was the platform correctly killing an oversubscribed app (497m/500m, liveness `GET /` 5s×6). The tenant has since upgraded to 1 CPU / 2Gi (live Deployment confirms) — 0 restarts since the 01:58Z deploy, CPU now 241m/1000m. Sizing was the right fix and it happened; slowing liveness for small tiers would delay detection of real hangs to protect a mis-sized tier.
3. **Dashboard CPU-limit visibility: deferred** to FUTURE-MAYBE (with the `server_failed` email/flap-digest gap from finding 1) — trigger: a second throttle-driven restart loop or a tenant asking why they weren't alerted.
