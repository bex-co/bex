## Objective

Retire the older silent-failure: the service Connect→SSH menu and the Shell page hand out `ssh srv-…@ssh.bex.co` regardless of key state today. Gate both with `RequiresSshKey`, and — because services already have the shipped in-browser Web Shell — present the zero-key fallback as **two doors**: "Add SSH key → native ssh/editor" and "Open a browser terminal" (no key needed).

## Context

- `ServiceConnectButton` in `dashboard/src/features/services/components/service-detail-header.tsx` (SSH row) and `service-shell-page.tsx` (copy-ready `ssh` command).
- Zero-setup door: the existing Web Shell (`web-shell-panel.tsx` / `web-shell-terminal.tsx`, w2/m55) authenticates with the dashboard session, not an SSH key — the natural "works now" alternative. Only offer it where the service is Web-Shell-eligible (paid, running); otherwise the single add-key door.
- Keep the Internal-address row and any non-SSH menu content unchanged — the gate wraps only the SSH payload.
- The Shell page's in-browser terminal itself needs no key (session-auth) — so the *page* stays usable; the gate applies to the copy-ready `ssh` command block it also shows.

## Steps

1. Wrap the SSH command row (Connect menu + Shell page) in `RequiresSshKey`; fallback = two-door CTA (add key with `returnTo=/services/<id>` + open Web Shell) gated on Web-Shell eligibility.
2. Leave Internal address + Web Shell terminal mounting unchanged.
3. Tests: no-key eligible service → two doors; no-key ineligible → add-key door only; has-key → the `ssh` command; fail-open on query error.
