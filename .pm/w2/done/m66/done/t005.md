## Objective

Make the activation funnel observable: emit client events for the gate's decision points and document the server-side proxy (the gateway auth metric) so we can tell whether the gate is actually reducing dead-ends.

## Context

- Funnel: `affordance-shown(no-key) → add-key-cta-clicked → key-added → (later) gateway auth accepted`. The last hop can't be seen from the browser — the proxy is the gateway's `bex_ssh_gateway_authentications_total{result="rejected_key"|"accepted"}` (this is exactly how the w2/m65 dead-end was root-caused live).
- Use the dashboard's existing telemetry/analytics seam if one exists; if there is none, keep the events minimal + behind a no-op-safe sink rather than inventing an analytics stack (out of scope). Do not add PII — event names + coarse surface labels only, matching the gateway's no-identifying-labels rule.
- Deliverable includes a short runbook note (where to read the proxy metric, what "working" looks like: `rejected_key` share for `ags-…`/`srv-…` trending down as `accepted` rises).

## Steps

1. Emit `ssh_gate_shown{surface,state}` and `ssh_gate_cta_clicked{surface}` (+ reuse the existing key-added signal from the create mutation) through the existing telemetry seam.
2. Add the proxy-metric note to the ADR035/ADR054 observability context (or the milestone evidence), citing the metric names + the PromQL to watch.
3. Confirm no new PII/identifiers leave the client.

## Files

- `dashboard/src/features/ssh-keys/` (event emission at the gate)
- `docs/ADR035-ssh.md` or milestone evidence (the proxy-metric runbook note)

## Acceptance criteria

- [ ] Gate shown/clicked events fire with bounded, PII-free labels through the existing seam (or a no-op sink if none exists, documented).
- [ ] The gateway proxy metric + watch query is written down so "did the gate help" is answerable.

## Out of scope

- Building a net-new analytics pipeline; per-user tracking.
