## Objective

Close `docs/ADR015-openbao-backup-restore.md`'s standing warning — "⚠ Untested against a live cluster... verify the first real snapshot + restore end-to-end before relying on it" — by actually performing the restore drill.

## Context

- The backup CronJob (`deploy/gitops/charts/openbao-backup/cronjob.yaml`) exists and runs, but the restore path has only ever been structurally reviewed, never executed.
- Restore mechanism (already documented in ADR015): `bao operator raft snapshot restore <latest>.snap` against a running, unsealed OpenBao, unsealed afterward with the **same** `.env` unseal keys used when the snapshot was taken (restore does not rotate keys).
- OpenBao holds every tenant credential (env-vars API, `docs/ADR013-secrets.md`) — pick a known tenant secret to verify post-restore.

## Steps

1. Take a real snapshot from the live/current OpenBao (or a faithful non-prod replica if restoring in place against prod is too risky — document which was chosen and why).
2. Note a known tenant secret's value beforehand.
3. Perform the restore per ADR015's documented runbook exactly as written.
4. Confirm OpenBao unseals with the existing `.env` keys and the known secret is recovered correctly.
5. Record the drill (date, duration, any runbook corrections needed) — feeds into t007's ADR.

## Files

- none (drill against existing infra, not a code change — unless the runbook itself needs a correction, in which case update `docs/ADR015-openbao-backup-restore.md`)

## Acceptance criteria
