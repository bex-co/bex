# Keep the product analytics sampling test inside its intended UTC day

Why: The full backend suite fails near UTC midnight because a same-day sampling assertion accidentally spans two daily records.

Found while validating w2/038 and w2/039 on 2026-10-02 with fresh real Postgres, OpenFGA and OpenBao. `TestPGProductAnalyticsLifecyclePrivacyAndSampling` in `lego/backend/internal/store/product_analytics_pg_test.go` starts at the current wall clock and adds two minutes before asserting that the latest daily row has `was_live=true`. The run at 23:58 UTC crossed midnight and returned the correct new-day `live=false,was_live=false`, failing at line 63. `RecordProductHosting` in `product_analytics.go` explicitly scopes `was_live` to each UTC day; this is a fixture assumption error, not a production aggregation defect.

Anchor this same-day sequence at UTC noon, retain the sampling, stale-observation, privacy and retention assertions, reproduce the old assumption with a private midnight clock overlay, and verify the complete backend suite on a fresh database. Scope: a focused test-only repair; no production or schema change.


Closed 2026-10-02: the fixture now anchors its unchanged two-minute sampling sequence at UTC noon. No production code or schema changed. An overlay forcing the old fixture to 23:59 UTC fails when the first next-day sample is correctly admitted; the same forced clock with the noon anchor passes. The ordinary focused test also passed. Independent review confirmed that stale-write, TLS, privacy and relative 100-day/90-day retention assertions are preserved. Final `GOWORK=off go test -p 1 ./...` passed with real private PostgreSQL/OpenFGA/OpenBao (unchanged packages cached; store suite 25.791s), and affected store lint returned zero issues. Cleanup is recorded at [040-cleanup.json](040-cleanup.json).
