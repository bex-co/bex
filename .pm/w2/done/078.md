# 078 — A brand-new service's first deploy reports `PriorReleaseServing` and rolls two ReplicaSets

Why: in the w2/m293 t003 dev-2 walk (2026-11-08), the repo-built `hello-go` showed `Serving=True` with reason `PriorReleaseServing` and rolled two ReplicaSets on its first deploy. A new service has no prior release. The extra roll may slow first deploys or add events. This is not w4/161 or w4/533, which are about a bad deploy over a healthy release.

- **Do:** reproduce on dev-2 and find what triggers the second roll. Candidates: an operator patch (pull policy or env), per-App credential activation, or the registry gate's requeue.
  - Make a first deploy roll once and report the right reason.
  - Check Render's first-deploy event sequence.
- **Acceptance:** a test pins one ReplicaSet and the correct `Serving` reason for a first deploy, and the dev-2 walk confirms it.
- **Render parity:** applies if the reason or events are customer-visible.

## Done (2026-11-09, `/loopx w2`)

- **Repro on dev-2:** both an image service (`traefik/whoami`) and a repo-built one (`examples/hello-go`) rolled two ReplicaSets on their first deploy. The pod templates differed only in the probes: RS1 used an HTTP GET `/` probe, RS2 a TCP probe.
  - **Cause:** the w8/m142 guard forces an HTTP probe while HTTP port selection is pending, so a binary listener cannot drain a serving release. It applied to first releases too, which have no serving release to protect. Once the port was detected the probe reverted, the template changed, and the Deployment rolled again.
  - **Reason label:** `PriorReleaseServing` was stamped because the first deploy's own revision is recorded as active during `RolloutSettling`, and `settleReady` never refreshed it.
- **Fix:**
  - The HTTP probe is now forced only while an earlier release serves (`webImageHTTPSelectionGuardsServing`).
  - A new `ReasonReleaseServing` applies when the active revision is the Deployment template's own; `PriorReleaseServing` stays for a newer template rolling over the active one.
  - `settleReady` re-observes Serving.
- **Customer-visible:** the deploy rows and events (`deploy_started`, `build_*`, `deploy_ended`) already matched Render's first-deploy sequence. The backend reads only the Serving status, not its reason.
- **Tests:** `first_deploy_rollout_envtest_test.go` asserts one template from first deploy to Running, `ReleaseServing`, and that a second deploy rolls a new template with `PriorReleaseServing`. It fails with the old gate. The serving-reason and probe-gate tables are extended. `GOWORK=off make test` and `make lint` pass.
- **Re-walk on dev-2:**
  - Both kinds roll one ReplicaSet and reach `Serving=True/ReleaseServing`; the image deploy took 53 s, down from 64 s.
  - A second deploy rolls exactly one new ReplicaSet.
  - Upgrading the operator did not roll running services.
