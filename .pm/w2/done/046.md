# 046 — MCP `update_environment_variables`, exactly as Render's official MCP server defines it

Why: agents written for Render's official MCP server call `update_environment_variables`; bex does not register it, and bex's own `update_env_vars` always replaces the whole set, so an agent switching hosts either fails or — through a naive alias — wipes every variable it did not mention.

**Estimate:** ~60m (at the inbox-note bound). **Source:** `/pm-brainstorm for w2` (2026-10-19), item 5, chosen by the user "as long as it's parity with render".

## Render's contract (the oracle — match it exactly)

Upstream `render-oss/render-mcp-server` `pkg/service/tools.go`, function `updateEnvVars`, read at commit `c6b8bb11196c` (2026-10-20):

- **Name** `update_environment_variables`; **annotations** `readOnlyHint: false`, `destructiveHint: true`, `openWorldHint: true`, title "Update environment variables".
- **Arguments:** `serviceId` (string, required); `replace` (boolean, default `false`); `envVars` (array, required) of objects with `additionalProperties: false`, required `key` and `value` (both strings) — **no** `generateValue`. bex's centrally injected optional `workspaceId` matches the pinned arg list (`lego/backend/internal/api/openapi/render-mcp-tools.json:336-347`).
- **Merge (default):** list the service's existing variables, overlay the inputs by key (a later duplicate input wins), write the merged set. **`replace: true`:** write exactly the given set.
- **Then trigger one deploy** (`clearCache` false). Result text, verbatim: `Environment variables updated. A new deploy has been triggered to pick up the changes.\n\nResponse from deploying service: <deploy JSON>`; when the deploy request is accepted but no deploy object exists yet: `Environment variables updated. A deploy was requested to pick up the changes; the request was accepted but the deploy has not been created yet. Use list_deploys to check on the service's deploys.`
- Errors (missing `serviceId`, empty `envVars`, list/write/deploy failures) are tool-result errors, not protocol errors. Secret files are untouched.

## bex today

- Not registered: `lego/backend/internal/api/mcp_parity.go:130-135` lists it in `mcpKnownUpstreamOnly` as "NOT a deliberate omission".
- `update_env_vars` (`lego/backend/internal/secrets/mcp.go:137-147`) is replace-only and accepts `generateValue`.
- The right primitive already exists: `PatchEnvironment` with `saveMode: deploy` (`lego/backend/internal/secrets/batch.go`) applies one sparse patch and rolls the service exactly once.

## Do

1. Register `update_environment_variables` in `lego/backend/internal/secrets/mcp.go` with Render's schema and annotations (reject `generateValue` and unknown properties, as upstream's schema does).
2. Merge → one `PatchEnvironment` of `set` ops for the inputs with `saveMode: deploy`. Replace → one patch that sets the inputs and deletes every existing key not in them, `saveMode: deploy`. One logical save, one rollout either way; secret files untouched.
3. Return Render's result text, embedding bex's Render-shaped deploy object for the rollout when it exists, otherwise the "accepted but not created yet" text. Compare a suspended service against upstream (env saved; the deploy step's error surfaced) and match it.
4. Remove the entry from `mcpKnownUpstreamOnly` so the pinned parity guard classifies the tool as implemented; update ADR018's MCP parity paragraph. Leave `update_env_vars` as bex's own tool.

## Acceptance

- [ ] Merge keeps keys the call did not mention; `replace: true` drops them; duplicate keys resolve last-wins.
- [ ] Exactly one rollout per call; result text matches upstream byte-for-byte apart from the deploy JSON.
- [ ] `generateValue`, extra properties, a missing `serviceId` or empty `envVars` are refused as tool errors.
- [ ] Authorization matches the other env-var writers (`can_create`; no secret value echoed beyond what upstream returns).
- [ ] The MCP parity guard passes with the tool classified as implemented; backend tests and `make lint` green.
