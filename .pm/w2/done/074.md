# 074 — Blueprint Sync History repeats the reconnection note on every row

Why: on production (2026-11-08) one Blueprint's Sync History showed "re-established a previously disconnected connection… earlier sync history below belongs to that connection" on several rows, including 7-day-old ones, so a customer cannot tell where the reconnection happened. w2/m256 t013 meant it to mark the boundary once.

- **Fix:** show the note only on the first sync row of each reconnection, the boundary between connections. Check whether the API stamps the note on every later row or the dashboard repeats it.
- **Acceptance:** a Blueprint reconnected twice shows exactly two boundary notes; dashboard test (and an API test if the note is stored per row).
- **Render parity:** UI.

## Closed 2026-11-08 (`/loopx w2`): premise not reproduced

- **Each note is written once:** on the first row of a revived connection. That is the admitted run on the legacy create path, or the planned row on Render's planned create, which keeps the note through approval.
- **Nothing copies it forward:** the store list and the dashboard each render a row's own note.
- **Test:** `TestReconnectedTwiceRecordsTwoBoundaryNotesPG` connects, syncs, disconnects, reconnects twice (once via the planned path, once via the legacy path) with further syncs, and gets exactly two notes, each on the first row of its connection. The dashboard test "shows one reconnection note per reconnection boundary" covers rendering.
- **Likely cause of the production view:** that Blueprint had been revived by many QA probes, each usually a single never-approved plan superseded by the next reconnect. Nearly every row really was a boundary.
- **Adjacent gap:** a revived connection whose first plan is `no_changes` writes no row, and so gets no boundary note. It is cosmetic and was not filed separately.
- **Out of scope:** Render deletes history on delete, while bex keeps it by decision w4/120. That is a separate product call and was not reopened here.
