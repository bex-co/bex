## Objective

Make the Render-compatible Key Value connection-info command tell `redis-cli` the public datastore hostname explicitly so the unmodified official Render CLI can complete TLS/SNI routing through bex's shared Valkey edge.

## Context

- The post-PROXY production run reached `bex-kv-sni-proxy` with the real client address and passed both allowlist layers, but the proxy rejected the TLS ClientHello because it carried no SNI name.
- bex currently returns `redis-cli -u rediss://...`. `redis-cli` 8.0.3 enables TLS from the URI but does not derive a TLS server name from that URI; its supported `--sni <host>` option is required by bex's exact-host router.
- The official CLI v2.21.0 splits `cliCommand` on spaces and launches the returned executable and arguments unchanged, so an explicit public-only `--sni` argument remains inside the existing Render connection-info contract and requires no CLI fork.

## Steps

1. For a public Key Value, emit `redis-cli --sni <externalHost> -u <externalUri>`; preserve the existing internal command for private stores.
2. Validate the operator-owned external host before placing it in the space-delimited command, and fail without echoing the credential-bearing URI if the public Secret/status contract is inconsistent.
3. Update unit, live-gated, parity, and acceptance expectations to prove public SNI and private compatibility.
4. Rebuild the production acceptance image and rerun the official CLI by opaque id and display name through the real public edge.

## Acceptance criteria

- [x] Public connection-info returns an explicit, validated `--sni <externalHost>` before its credential-bearing `rediss://` URI; private connection-info remains unchanged.
- [x] Invalid or missing public external-host status fails safely without placing the URI or password in an error.
- [x] Unit and live-gated assertions cover the exact public command shape and the unchanged private command.
- [x] The unmodified official CLI reaches Valkey by id and name through the production TLS/SNI edge.

## Result

Public connection-info now validates the operator-owned DNS-1123 external host and emits `redis-cli --sni <host> -u <rediss-uri>`; private stores retain `redis-cli -u <redis-uri>`. The invalid-status test proves the error contains neither password nor URI. Focused/full backend tests and the production id/name acceptance pass.

## Out of scope

- Changing the connection-info schema, teaching the official CLI bex-specific behavior, bypassing SNI routing, or changing private in-cluster connectivity.
