## Objective

Make PostgreSQL and Valkey source allowlists enforce the real public client address after the Terraform-owned Hetzner TCP load balancer by enabling PROXY protocol on only those two listeners and consuming its original-source header in both shared SNI proxies.

## Context

- The post-DNS m57 production run reached `bex-kv-sni-proxy`, but the proxy rejected the exact public `/32` allowlist before dialing Valkey; direct TLS also closed before a certificate was returned.
- Hetzner TCP load balancers do not preserve an application-visible client address unless PROXY protocol is enabled. `externalTrafficPolicy: Local` preserves the load balancer-to-node source but cannot recover the address the load balancer replaced.
- `infra/terraform/main.tf` currently sets `proxyprotocol = false` on both datastore listeners. Both proxy binaries apply resource and environment CIDRs to `conn.RemoteAddr()`, so the load balancer's private address fails every exact public-client allowlist.
- A PROXY header is authoritative only from the fixed Terraform-owned load balancer private address. Direct public NodePort clients must not be able to forge an allowlisted source.

## Steps

1. Add a bounded shared PROXY protocol v1/v2 reader that preserves non-PROXY PostgreSQL/TLS bytes, rejects malformed headers, and trusts asserted source addresses only from explicit CIDRs.
2. Wire both datastore proxies to read the optional header before their PostgreSQL/TLS protocol detection and use the resulting source for both allowlist layers.
3. Configure the production proxy pods to trust only `10.10.0.7/32`, enable PROXY protocol on the Terraform PostgreSQL and Valkey listeners, and gate the rendered/IaC contract.
4. Add parser and end-to-end proxy tests proving trusted source routing, untrusted spoof rejection, direct-connection compatibility, and both address families.
5. Document the client-IP trust chain and deploy in compatibility-first order: header-capable proxies first, then listener enablement; rerun the external CLI acceptance.

## Acceptance criteria

- [x] A trusted v1 or v2 header supplies the source address used by both datastore allowlist layers; direct headerless clients retain `RemoteAddr()` behavior.
- [x] A PROXY header from outside the configured trusted CIDRs, an invalid address/port, or an oversized/malformed header fails closed before SNI routing.
- [x] Production manifests trust only the Terraform-owned load balancer's `10.10.0.7/32`; datastore listeners enable PROXY protocol while SSH/HTTP/HTTPS remain unchanged.
- [x] A saved-plan CI handoff prevents Terraform from enabling either listener until the same commit's exact proxy image digest is Ready on both DaemonSets.
- [x] Focused proxy tests, `make test`, Terraform validation, and the GitOps validation gate pass.
- [x] The live official CLI run completes by id and name with its exact public source CIDR and all disposable resources are removed.

## Result

The compatibility-first production acceptance temporarily rolled the header-capable proxies before enabling the two datastore listeners, then passed the exact-source CLI run. The permanent CI handoff now applies the same order: Terraform saves its plan and waits only when that plan enables datastore PROXY protocol; the matching deploy cannot succeed until both proxy DaemonSets run its exact built digest. All parser/proxy suites, operator envtest, lint, Terraform 1.10.5 validation, and GitOps guards pass. Because the source changes remain uncommitted, production was safely restored in reverse order after evidence: headers disabled first, then the published Argo revision restored Healthy/Synced.

## Out of scope

- Trusting arbitrary private-network sources; weakening or bypassing resource/environment allowlists; changing REST/GraphQL/MCP/dashboard contracts; enabling PROXY protocol on SSH or HTTP listeners.
