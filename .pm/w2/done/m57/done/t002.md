## Objective

Build one safe, repeatable live verifier that provisions a short-lived public bex Key Value, waits for the real external TLS endpoint, invokes t001's official-CLI PTY probe by both opaque id and display name, proves data operations, and removes the fixture on every exit path.

## Context

- dev-9 does not run `BEX_KV_DOMAIN`, cert-manager, or the public datastore edge; this verifier is opt-in for production or an equivalent full-stack environment.
- `KeyValueConnectionInfo` chooses the external `rediss://` URI only when the operator-generated Secret has `externalUri`; otherwise the official CLI receives the internal `.svc` URI, which is intentionally unreachable from the verifier host.
- The official Render CLI create schema has no bex-only `public` field. Fixture setup may use authenticated REST `POST /v1/key-value` with `public:true`; all connection and data operations must still run through unmodified `render kv-cli`, never through a directly invoked `redis-cli`.
- The public proxy preserves source IP and enforces resource/environment allowlists. Require an explicit caller CIDR rather than briefly opening the disposable store to the internet.
- `scripts/ssh-verify.sh` is the lifecycle/redaction precedent; `scripts/cli-compat.sh` already supplies the official CLI host, token, workspace, and isolated config.

## Steps

1. Add `scripts/keyvalue-cli-verify.sh` with strict preflights for the API origin, bearer, workspace, official CLI binary/version, explicit allowed source CIDR, and the t001 PTY probe prerequisites.
2. Create a unique Key Value through authenticated REST with `public:true` and only the supplied source CIDR; retain its `red-` id and display name in memory and install a cleanup trap immediately after creation.
3. Poll the public resource until bex reports available, connection-info has an external `rediss://` endpoint, DNS resolves, and the endpoint is ready for a bounded CLI attempt. Never print the connection-info body.
4. Through t001, run `PING` by id, write a unique key/value by id, read the exact value by display name, and delete the key. This proves both upstream resolution branches and a real authenticated Valkey round-trip.
5. Delete the Key Value through its public API on success, failure, signal, or timeout; poll until the resource is gone and report cleanup failure separately from the primary result.

## Acceptance criteria

- [ ] One command creates a source-restricted public fixture, reaches it only through two unmodified `render kv-cli` invocations (id and name), proves `PING` plus exact `SET`/`GET`, and deletes it.
- [ ] The verifier fails clearly on absent external URI, DNS/TLS/connect timeout, allowlist denial, API resolution failure, missing local Redis-compatible client, wrong value, and cleanup failure.
- [ ] Tokens, passwords, connection strings, Secret bodies, and kubeconfig contents never reach stdout/stderr or persisted evidence.
- [ ] Cleanup runs after success, assertion failure, timeout, and interrupt, and targets only the exact verifier-created `red-` id.

## Out of scope

- Making dev-9 a public-edge environment; changing Key Value create/update semantics; testing Postgres `pgcli`; patching, forking, or vendoring `render-oss/cli`.
