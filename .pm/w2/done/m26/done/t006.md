## Objective

Root-cause how `tenant_invites` ended up owned by the `postgres` role instead of `bex` (every sibling table's owner), which caused `permission denied for table tenant_invites` on every authenticated call and silently broke invite redemption (`w4/m12`) on prod — then add a guard so this can't recur unnoticed.

## Context

- Already fixed live: `ALTER TABLE tenant_invites OWNER TO bex`.
- Open question from the incident note: was this a hand-run migration (bypassing the normal migration runner, which presumably runs as the `bex` role)?
- Control-plane migrations live under `lego/backend/internal/store/migrations/` (or wherever `w1/m2`'s Postgres store put them).

## Steps

1. Check migration history / audit trail for `tenant_invites`'s creation — was it applied by the normal migration runner or hand-run as a different role?
2. Audit all other control-plane tables for the same ownership drift (`SELECT tablename, tableowner FROM pg_tables WHERE schemaname = 'public'` against prod, or the equivalent CI check).
3. Add a guard: either a CI check that asserts expected table ownership against a migration dry-run, or a documented migration-runner convention (always run as `bex`, never hand-run as `postgres`) with a startup check in bex-api that fails loudly on ownership mismatch.

## Files

- `lego/backend/internal/store/migrations/`
- CI workflow or a startup health-check in bex-api

## Acceptance criteria

- [ ] Root cause identified (or ruled out with evidence) for how the ownership drift happened.
- [ ] No other control-plane table has the same drift (or any found are fixed).
- [ ] A guard exists (CI check or startup assertion) that would have caught this before it reached prod.

## Out of scope

- General migration-tooling rewrite — a minimal, targeted guard is sufficient.
