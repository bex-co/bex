# 084 — A service name stays taken while its teardown outlasts 20 s: decouple the App object name from the service name

Why: Render accepts a just-deleted service's name at once. w2/m361 made bex wait up to 20 s for the old App's teardown, which covers an ordinary delete (1–15 s). A static site whose object purge runs longer (up to 15 min), or a stalled finalizer, still answers `409 SERVICE_NAME_STILL_DELETING`, an open gap in ADR018's "Address a service by name" row.

- **Source:** w2/m361 (2026-11-13). The inventory below came from its t001.
- **The fix:** a re-created service gets its own App object name, for example `<tenant>-<name>-<4 chars>`, while keeping the requested name as its service-name label and `apps.name`. Then the old App can tear down beside it.
- **What has to change** (paths relative to `lego/`):
  - `apps.object_name` column, written at create (`backend/internal/apps/service.go` create and the Blueprint stamp near the stack write) and read by the projector's re-create (`backend/internal/store/reconciler.go` ~2587), the pull-secret name (reconciler ~2648 vs `apps/service.go` ~2998), build-source fan-out (`backend/internal/deploys/build_sources.go` ~355) and the usage pod fallback (`backend/internal/usage/service.go` ~1453). All of these compute `core.CRName(tenant, name)` today.
  - By-name resolution skips Apps being deleted: `core.Base` `appByDisplayedName` (`backend/internal/core/base.go` ~1383), the `appCandidateNames` tier (~1841) and the label sweep (~1289, ~1968). Without that, old and new answer `409 SERVICE_NAME_AMBIGUOUS`.
  - The slug: the deleted row frees `<slug>.onbex.co`, but the old App's Ingress and internal `<slug>` Service live until garbage collection, so the new service would race them for the host and the `AlreadyOwned` Service. Either mint a slug no App being deleted still holds, or have the operator's `handleAppDeletion` delete the Ingress and slug Service first.
  - A retried `DELETE` of the old service, which is still reachable by its `srv-` id, purges OpenBao paths keyed by tenant and service name (`backend/internal/secrets/purger.go` ~105), so it would wipe the new service's env vars. Short-circuit an App already being deleted in `apps.Service.Delete`.
  - Keyed safely already: Loki (`app` + `app_id` + notBefore), Prometheus (pod regex + NotBefore), the registry repo, static S3 prefix and Zot user (they follow the object name, so they become separate), custom domains (a deleted service's domain stays refused until its finalizer ends). Object names stay within 63 characters: 55 today, 60 with a suffix.
- **Not this:** moving cleanup out of the finalizer. Registry, S3 and Zot cleanup follow the object name, so a reused name would lose the new service's artifacts.
- **Acceptance:** on production, delete a static site whose purge is still running and create the same name. The create answers 201 at once and serves, while the old site finishes tearing down beside it. The old and new services never share a host, a Service, logs, metrics, env vars or artifacts. `SERVICE_NAME_STILL_DELETING` is no longer produced. ADR018's open gap is closed.
- **Size:** about a day with tests, so this note is a milestone when promoted.
