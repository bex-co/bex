# 070 — Audit payment-method changes made in the Stripe-hosted portal

Why: w2/067 records `UpdateWorkspacePaymentMethodEvent` for the dashboard's Add/Update payment method (a bex Checkout Session), but a member can also change the default card inside the Stripe Billing Portal, which bex never hears about — so that change leaves no audit entry, unlike Render's.

- **Today:** `internal/billing/webhook.go` handles only `checkout.session.completed` and the subscription/invoice lifecycle (`lifecycleEventTypes`); the portal's change arrives as `customer.updated` (`invoice_settings.default_payment_method`), which the live endpoint is not subscribed to (`scripts/stripe-webhook-drift.sh`).
- **Do:** handle `customer.updated` when the default payment method changed (re-read the Customer, map it to the workspace by `bex_workspace` metadata), record the audit row keyed on the Stripe event id; attribute it to the member who opened the portal session (record the opener when `CreatePortalSession` runs) or to `system` if none; add the type to `HandledStripeEventTypes` and subscribe the live endpoint (needs Stripe dashboard access).
- **Acceptance:** changing the default card in the test-mode portal adds one `UpdateWorkspacePaymentMethodEvent`; `stripe-webhook-drift.sh` green.

**Blocked 2026-11-03 (`/loopx w2`).** The handler is small, but it only works once the live Stripe endpoint (`https://api.bex.co/v1/webhooks/stripe`, on the Stripe account shared with beancount/blockeden/cuckoo/tianpan) subscribes to `customer.updated`. That is a production change to a shared account, which needs the user's go-ahead. Shipping the handler first would also turn `scripts/stripe-webhook-drift.sh` red, because `HandledStripeEventTypes` would list a type the endpoint does not send. Release condition: the user adds `customer.updated` to the endpoint's enabled events (Stripe dashboard → Developers → Webhooks), or approves an agent doing it with the Stripe key. Then implement and ship the handler in the same change.

## 解阻复核（2026-11-04，复核证据，待用户决定）

- **现有工具：** `scripts/stripe-billing-setup.py` 的 `ensure_webhook_endpoint` 按 URL 只创建或校验 bex 自己的 endpoint，发现漂移时报错，不会修改。
- **最小改法：** 加一个只针对 `https://api.bex.co/v1/webhooks/stripe` 这一个 endpoint 的 update 模式，把 `customer.updated` 追加进 `enabled_events`。脚本自己读 Stripe key，不经过 agent 上下文；不碰共用账号上其他产品的 endpoint。
- **影响：** 该 endpoint 会收到账号内所有客户的 `customer.updated`（Stripe endpoint 是账号级的），handler 按 `bex_workspace` metadata 过滤。
- **仍需用户决定：** 自己在 Stripe dashboard 加，或者授权 agent 以上述方式修改。

## 解阻决定（2026-11-04，来源：用户决定 D4=A）

- **决定：** 授权 worker 修改共用 Stripe 账号上 bex 自己的那一个 webhook endpoint（按 URL `https://api.bex.co/v1/webhooks/stripe` 识别），只追加 `customer.updated` 一个事件，不碰其他产品的 endpoint。
- **怎么改：**
  - 给 `scripts/stripe-billing-setup.py` 加一个只做追加的 update 模式，并把 `customer.updated` 加入 `WEBHOOK_EVENTS`。
  - Stripe key 由脚本自己读取，绝不经过 agent 上下文。
  - handler 与订阅在同一次变更里上线，避免 `scripts/stripe-webhook-drift.sh` 变红。
- **worker 下一步：**
  1. 实现 `customer.updated` handler：默认付款方式变更时写一条 `UpdateWorkspacePaymentMethodEvent`，按 `bex_workspace` metadata 过滤无关客户，以 Stripe event id 去重，归属到开启 portal session 的成员，没有则记为 `system`。
  2. 在 test mode 验证。
  3. 对 live endpoint 运行追加模式。
  4. 确认 `stripe-webhook-drift.sh` 为绿。
- **验收：** 在 test-mode portal 改默认卡后，审计日志新增一条记录；live endpoint 的 `enabled_events` 含 `customer.updated`，且其他事件不变。
