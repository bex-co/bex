## Objective

Verify the GitHub Connect capability now works consistently for both the browser (dashboard) path and the existing API/agent (Bearer) path.

## Steps

## Verification status (2026-07-14)

- Production now runs the state-aware callback: an uncredentialed callback with missing state returns `302` to `https://dashboard.bex.co/settings?git_error=missing_state` with `Referrer-Policy: no-referrer`.
- Browser path verified with the normal signed-in production Chrome profile. The Settings card showed the existing `bex-co` connection; the UI disconnect was confirmed, the resulting **Connect GitHub** button was clicked, and GitHub followed `installations/new?state=…` → `select_target?state=…` → the real organization installation `90623475`. Because the installation already exists, GitHub required its own sudo-mode **Confirm access** before changing repository grants. No grants were changed; the UI-minted signed state and existing installation completed the Setup-URL callback, returned to `/settings`, and the card visibly showed **Connected as bex-co**. A forged-state browser check returned to the same card with the bounded visible error, “This connection request couldn't be verified.”
- The production Bearer baseline is partly green: a short-lived `bex-bootstrap` token sees the existing `bex-co` connection, `POST /v1/git/connect` now returns an install URL containing `state`, and replaying installation `90623475` preserves the connection. The replay exposed one compatibility regression: production returns `302 /settings` instead of the legacy `200 {"status":"connected"}` JSON whenever `BEX_DASHBOARD_URL` is configured. The local fix now redirects only state/browser callbacks and has a regression test with `DashboardURL` configured; it is not live yet.
- Current [Render GitHub documentation](https://render.com/docs/github) describes the same primary transition—dashboard → GitHub authorization/install → dashboard repo list—and sends existing-installation users to `github.com/apps/render/installations/new` to manage grants. Current [GitHub installation documentation](https://docs.github.com/en/apps/using-github-apps/installing-a-github-app-from-a-third-party) likewise requires account selection, repository selection, permission review, and Install/Request. No bex-specific behavior drift remains; GitHub's sudo prompt for an existing organization installation is provider behavior shared by Render's management link.

After the local compatibility fix is shipped, repeat the credentialed callback once and require `200 {"status":"connected"}` plus the same persisted `bex-co` installation. That is the only open t007 acceptance gate.
