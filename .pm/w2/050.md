# 050 — Production deploys starve under concurrent pushes: a ready fix waited ~2 h because every run was superseded

Why: with several sessions pushing to `main`, `deploy.yml` cancels pending runs and skips the pin of a finished run whenever newer production manifests exist, so a shipped fix can sit unpinned for hours while each newer run is superseded in turn.

**Seen 2026-10-28** (w2/m169): `f1e28beb3` (SSH fix) was pushed 09:17Z; run `f1e28beb3` cancelled, `bb0cac58e` cancelled, `e2c8e7baf` cancelled, `fa918b387` **succeeded at 10:16Z but logged** `superseded by newer production manifests on origin/main (fe594754); this run's images will not be built/pinned` and skipped the rollout — although `fe5947541` was a `docs(pm)` commit. The fix reached production only with the `d66f96c06` pin (`9d0b7fa51`), about two hours after the push.

## Do

1. Confirm what "production manifests" the supersession check compares and why a `.pm`-only commit counted (or whether `d66f96c06` was the real superseder and the message named the newest HEAD).
2. Make a successful run pin its images unless a newer run is **actually going to pin** (e.g. only defer to a newer in-progress run that touches production inputs; never to doc-only commits), so a quiet minute is enough for the newest code to reach production.
3. Keep the existing stale-digest protection (`deploy.yml` normalized-compare) intact.

## Acceptance

- [ ] A run whose only newer commits are docs/`.pm` pins and rolls out.
- [ ] Under a burst of code pushes, the newest successful run pins within one run's duration of the last push.
