## Objective

Determine, from the running image rather than assumptions, which directory Discourse serves uploads from in this multisite deployment, where each recovered file must land, and the disk's `mountPath` and `sizeGB`.

## Context

- Candidate paths from `w7/done/042.md`: `/var/www/discourse/public/uploads` and `/var/discourse/shared/uploads` (both empty on 2026-09-06); `DISCOURSE_RELATIVE_URL_ROOT=/forum`.
- Multisite: the default site (beancount) stores under `uploads/default/`; the other sites under `uploads/<db key>/` from `_infra/bex/multisite.yml` (resolved at boot by `start.rb`, `discourse_docker` commit `b6cbd62`). The recovered files all sit under `uploads/default/` because each forum was single-site before consolidation — the database `url` column, not the old layout, decides the target path.
- [ADR082](../../../../docs/ADR082-persistent-disks.md): one disk per service, `mountPath` denylist, Blueprint default `sizeGB: 10`, paid plans only (`standard` qualifies), single instance, `Recreate` deploys.
- `_infra/bex/README.md`: the container runs as UID 0 without `DAC_OVERRIDE` — ownership of the mounted volume must be writable by the Discourse process user. `w6/m149` (Render-compatible privilege policy, in progress) may change this; read its current state before deciding.

## Steps

1. Read-only `kubectl exec` into the forum pod: resolve symlinks for both candidate paths, read the `FileStore::LocalStore` upload root, and list the multisite db keys.
2. Map each t001 "recoverable" URL to its absolute target path.
3. Choose `mountPath` (the real upload root, not a symlink) and `sizeGB` (≥ current need plus growth; default 10).
4. Determine how the volume's ownership is set under ADR082 (fsGroup / init) and whether Discourse's user can write to it; record the approach.
