# 059 — `highAvailabilityEnabled` reads false right after creating or enabling HA

Why: a customer who runs `bex postgres create --high-availability` (or flips HA on) gets back `highAvailabilityEnabled: false`, so the CLI, REST, GraphQL and MCP all appear to have ignored the request until the standby comes up minutes later. Whether Render returns the configured value immediately is **not yet verified**.

- **Found:** w2/m171 t011 production walk, 2026-10-31. `dpg-dbiqsb2t5fis7381js40` was created with `--high-availability`; its CR had `spec.highAvailability: true` and CNPG `instances: 2`, but REST/CLI reported `highAvailabilityEnabled: false` while `creating`, then `true` once `available`.
- **Cause:** `PostgresView.HighAvailabilityEnabled` is projected from `d.Status.HighAvailabilityEnabled` (observed state, `lego/backend/internal/postgres/service.go:582`), not from the desired `spec.highAvailability`. This is a recorded design choice: ADR009 § High availability says the field "reflects the operator's observed state, not just the spec intent".
- **First step:** verify Render's actual behavior (its API reference for `highAvailabilityEnabled`, or a live create on a Render account) before changing anything. If Render also reports observed state, close this note as matching Render and record that in ADR018.
- **Fix (only if Render reports the configured value):** project the configured value (`spec`) on the wire, so disable also reads `false` immediately. Keep `status` for the consumers that need an observed standby (metrics replication-lag gating, `internal/metrics/datastore.go:282`). Check every surface reading the view (REST, GraphQL, MCP, dashboard HA panel/state copy, Blueprint export) and the dashboard's "standby being added/removed" state, which may need the observed value separately.
- **Done when:** create/update responses and immediate reads return the requested HA value on REST, GraphQL, MCP and the pinned CLI; the metrics gate still waits for the observed standby; tests cover the creating window.
