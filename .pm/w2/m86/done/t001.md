## Objective

Confirm the Hetzner worker node image can open LUKS volumes: `cryptsetup` must be present on the baked `bex-worker` snapshot the CAPH machine templates point at. If it is absent, add it to the packer bake and roll a fresh snapshot; if present, record the evidence and move on.

## Context

- w1/m83 shipped the `hcloud-volumes-luks` StorageClass but never verified this prereq (`.pm/w1/done/m83/README.md:24,36`).
- The node image is a packer-baked Hetzner snapshot (`infra/packer/`, baked via the `workflow_dispatch` CI bake — see `.github/workflows/snapshot.yml` and the w1/m36 lineage).
- hcloud-csi's LUKS support shells out to `cryptsetup` on the node during volume staging.

## Steps

1. Inspect the current packer template/provisioner package list under `infra/packer/` for `cryptsetup`.
2. Check a live production worker node (`ssh` via operator custody, or a debug pod with host access) for the `cryptsetup` binary as ground truth.
3. If missing: add `cryptsetup` to the packer apt list, run the CI bake, and point the worker `HCloudMachineTemplate` at the new snapshot (same flow w1/m36 used).
4. Record the verification evidence (command output) in the task/milestone notes.

## Files

- `infra/packer/`
- `.github/workflows/snapshot.yml`
- `infra/clusterapi/` (worker machine template, only if a re-bake is needed)

## Acceptance criteria

- [ ] Evidence recorded that the node image serving the tenant pool has `cryptsetup` available (or a new baked snapshot that does, with templates updated).

## Out of scope

- Flipping `BEX_DISK_STORAGE_CLASS` (t003).
- Rolling existing nodes beyond what a snapshot update requires.
