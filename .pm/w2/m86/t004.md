## Objective

Prove the full disk lifecycle on the encrypted class against a live cluster: create a disk-bearing App, confirm the volume is genuinely LUKS-encrypted on the node, grow it online, and run the snapshot + restore drill against it.

## Context

- w1/m87 ran this drill on the default class (CAPD, 2026-08-25); this re-run must be on `hcloud-volumes-luks`, which requires a real Hetzner volume — the mock CAPD cluster has no hcloud-csi. Use production custody (operator kubeconfig) with a throwaway workspace/App, mirroring how w1/m86's cluster drill ran.
- Drill reference: `docs/runbooks/disk-snapshot-setup.md`, `scripts/disk-snapshot-secret.sh`.
- The w1/m86 drill caught a real bug (LUKS Secret read through a single-namespace cache) — expect this class of failure and fix in-milestone.

## Steps

1. Create a throwaway App with `spec.disk` (10 GB) in a test workspace; wait for the PVC on `hcloud-volumes-luks` to bind and the pod to mount.
2. On the node: `cryptsetup status` on the mapper device / `lsblk -f` — record the LUKS mapping evidence.
3. Grow the disk (grow-only resize) and confirm the filesystem expands online.
4. Trigger the snapshot CronJob path and run the restore Job; verify restored content.
5. Delete the App; confirm PVC/Secret cleanup. Record all evidence in the milestone.

## Result so far (2026-09-02)

Mechanism drill PASSED on production (scratch namespace): PVC bound on `hcloud-volumes-luks` in 32 s, `nodePublishSecretRef` templated per-PVC, filesystem on `/dev/mapper/…` with **LUKS1 aes-xts-plain64 512-bit active**, 10→11Gi grow applied online (mapping + ext4, pod running, data intact), namespace deleted and the Hetzner volume reclaimed.

Operator-path drill PASSED the same day after the env rolled out (App → LUKS PVC → CronJob → clean teardown), armed the prod snapshot store end to end (`provision` + all six `verify` separation checks PASS), and surfaced **four latent defects, all fixed in this milestone**: the provision script's first-run pipefail abort (orphaned IAM keys), the never-implemented `bex-system/bex-disk-snapshot` secretKeyRef contract (no backup CronJob could ever arm from the manifest), the backup Job's ro claim source (EBUSY beside the app's rw LUKS mount — running apps unbackupable on the encrypted class), and the snapshot/restore container's non-root uid (permission denied on any real ext4 volume, **any** class). Full evidence: `evidence/2026-09-02-luks-drill.md`. The remaining unchecked box needs the fixed operator image deployed and is what gates t008.
