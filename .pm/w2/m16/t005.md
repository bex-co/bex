## Objective

Confirm the operator's reconcile loop actually resizes a running Postgres/Key Value instance's pod resources when `spec.plan` changes on the CR — this is a standard k8s controller watch, but must be proven with a test, not assumed.

## Context

- Operator reconcilers for `Database`/`KeyValue` project `spec.plan` into CNPG `Cluster`/Valkey `StatefulSet` resource requests at create time (`lego/operator/internal/controller/`); confirm the same mapping fires on an update, not just create.
- envtest is the existing harness (`lego/operator/Makefile` `make test`).

## Steps

1. Write an envtest that creates a `Database` (or `KeyValue`) CR, waits for the CNPG `Cluster`/`StatefulSet` to reach the initial plan's resource requests, then patches `spec.plan` to a different tier and asserts the underlying resource's requests update within one reconcile.
2. If the reconciler does NOT currently react to a plan-only spec change (e.g. it's gated on generation/hash comparison that misses a plan-only diff), fix the reconcile predicate — this is the one place this milestone could hit real design work rather than pure plumbing.

## Files

- `lego/operator/internal/controller/*_controller_test.go`
- `lego/operator/internal/controller/*_controller.go` (only if the predicate needs a fix)

## Acceptance criteria

- [ ] envtest proves a `spec.plan` patch on a `Database` CR updates the CNPG `Cluster`'s pod resource requests within one reconcile.
- [ ] Same proof for `KeyValue` → Valkey `StatefulSet`.
- [ ] No data loss (PVC/Secret untouched) across the plan change.

## Out of scope

- Storage size changes (`spec.StorageGB`) — plan changes only; storage-resize semantics are a separate, already-documented ("storage can only...") concern.
