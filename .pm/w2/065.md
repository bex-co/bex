# 065 — Blueprint responses carry `ownerId`; Blueprint PATCH accepts `branch`

Why: Render's 2026-11-02 OpenAPI makes `ownerId` a required field of every Blueprint object and lets `PATCH /blueprints/{id}` change `branch` (round-5 drift, w2/m251); bex omits the first and rejects the second as an unknown field.

- **Render:** `blueprint` / `blueprintDetail` `required` now includes `ownerId` (`list-blueprints`, `retrieve-blueprint`, `update-blueprint` responses); `update-blueprint` request body gains `branch` (string, minLength 1; "Updating this field does not plan a sync").
- **bex:** `lego/backend/internal/apps/rest.go` `renderBlueprint` (no `OwnerID`) and the `PATCH /v1/blueprints/{id}` body struct (`name`, `autoSync`, `path`, `ownerId` only) → strict decoding 400s `branch`.
- **Do:** add `ownerId` (the Blueprint's workspace) to list/get/patch responses; accept `branch` on PATCH through `UpdateBlueprint` (validate the branch has the Blueprint file at `path`, as Render requires; do not plan a sync); same on GraphQL/MCP update if they expose path/autoSync.
- **Acceptance:** response validation against the pinned schema passes for list/get/patch; PATCH `{"branch":"other"}` changes the branch and the next manual sync reads it; a branch without the file is a named 400.
