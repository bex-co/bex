## Objective

Today every deploy reads `update_in_progress` from the moment it opens until it either converges (`live`) or fails (`update_failed`) — the reconciler never distinguishes "the BuildKit Job is still running/failed" from "the built image is deployed but the rollout/health-check is still converging/failed." Now that `w1/m5`'s in-cluster BuildKit Job exists as an observable resource, wire the reconciler to watch it and report the correct phase.

## Context

- `lego/backend/internal/store/store.go:78-96` — the status vocabulary; add `DeployBuildInProgress = "build_in_progress"` and `DeployBuildFailed = "build_failed"` alongside the existing four.
- `lego/backend/internal/store/reconciler.go` — the write-back path (`status = DeployLive` etc., ~line 250/264) that currently only ever produces the four existing statuses.
- `lego/operator/internal/build/build.go` / `lego/operator/internal/controller/app_controller.go` — the build Job's lifecycle (`bld-<name>-gen-<N>` Jobs) the reconciler needs to observe to know "still building" vs "build done, now rolling out."
- A repo-backed deploy's real lifecycle is now: opened → build Job running (`build_in_progress`) → build Job done → Deployment rolling out (`update_in_progress`) → converged (`live`) or rollout failed (`update_failed`); a build Job failure is `build_failed`, distinct from `update_failed`. An image-backed deploy skips the build phase entirely — goes straight to `update_in_progress`.

## Steps

1. Add the two new status constants.
2. In the reconciler's status-writing path, check whether a repo-backed deploy's build Job (keyed by generation, matching `Cancel`'s existing `buildJobName` lookup pattern) exists and its state (running/failed/complete) before falling through to the existing rollout-status logic.
3. Image-backed deploys are unaffected — no build Job, straight to `update_in_progress`/`live`/`update_failed` as today.

## Files

- `lego/backend/internal/store/store.go`
- `lego/backend/internal/store/reconciler.go`

## Acceptance criteria

- [ ] A repo-backed deploy whose build Job is still running reads `build_in_progress`, not `update_in_progress`.
- [ ] A repo-backed deploy whose build Job failed reads `build_failed`, not `update_failed`.
- [ ] An image-backed deploy's status progression is unchanged (no build phase to report).
- [ ] A repo-backed deploy that builds successfully still reaches `update_in_progress` then `live`/`update_failed` exactly as today, once the build phase is behind it.

## Out of scope

- `pre_deploy_in_progress`/`pre_deploy_failed` (no pre-deploy-command feature exists in bex) — genuinely out of reach, not deferred.
