# 056 — Hobby workspaces hit the PVC and Pod count caps long before the 25-database cap

Why: after w2/m247 t001 a Hobby workspace's datastores are bounded by their count caps (25 Postgres / 25 Key Value), as on Render. But `tenant-quota` still charges every datastore volume and Pod against Hobby's `persistentvolumeclaims: 8` and `pods: 50`. A `2c-4g` HA database uses 2 PVCs (plus WAL, if separate) and 2+ Pods, so a Hobby workspace can run only about 3–4 HA databases. Render has no such cap.

## Do

1. Count the PVCs and Pods per datastore shape (single, HA, readers, pooler, Key Value) from the operator.
2. Raise Hobby's `persistentvolumeclaims`, `pods` and `requests.storage` so that the datastore count caps bind first, without letting services bypass the compute quota. Or exclude datastore PVCs through a storage class or quota scope if Kubernetes allows it. Record the derivation in `quotaForPlan`'s comment.
3. Verify in a Hobby workspace with several HA databases.

## Acceptance

- [ ] A Hobby workspace's datastore count caps bind before its PVC, Pod or storage quotas.
