## Objective

Design the three `/blueprints` resource verbs: `POST /v1/blueprints/validate` (dry-run a `bex.yml`, per-entry errors, no apply), `GET /v1/blueprints` (list known blueprint sources), and `POST /v1/blueprints/{id}/sync` (re-apply) — mirroring Render's Blueprint resource verbs.

## Context

- `w1/m24` (Multi-service `bex.yml`: Blueprint-shaped stack deploys) — the deploy verb and all-or-nothing validation logic this reuses. **This milestone depends on `w1/m24` landing first.**
- `docs/ADR018-render-parity.md`'s Blueprint row: "`/blueprints` resource (validate/list/sync) stays untracked, low."
- Render's `/blueprints` REST resource (api-docs.render.com) — the shape to mirror.

## Steps

1. Decide what identifies a "known blueprint source" for `list` (a repo+path+branch tuple already tracked via git-connect, most likely).
2. Decide `validate`'s response shape: per-entry errors, matching `w1/m24`'s all-or-nothing validation error format.
3. Decide `sync`'s semantics: re-run the same idempotent apply `w1/m24`'s deploy verb already performs, just re-triggerable by id rather than requiring the full payload again.
