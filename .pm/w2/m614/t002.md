## Objective

Implement the **Trigger Build** dialog on git-backed Build Sources exposing Render's round-9 `deploy.serviceScope` (`autodeploy_only`, `none`, `custom` with linked-service multi-select) and `clearCache` (`do_not_clear` / `clear`), and surfacing the returned `deploys` and `skippedServices` clearly.

## Context

- Backend GraphQL `triggerBuild` (`lego/backend/internal/deploys/build_sources.go:799-829`) accepts `buildSourceId`, `clearCache`, and `deploy: { serviceScope, serviceIds }` and returns `Build` including `id`, `deploys: [{ serviceId, deployId }]`, and `skippedServices: [{ serviceId, reason }]`.
- Render refuses `serviceIds` unless `serviceScope === "custom"` and requires non-empty `serviceIds` when `serviceScope === "custom"`.

## Steps

1. Build `TriggerBuildDialog` triggered from the Build Source header button (and Builds tab empty state):
   - Radio group for Deploy scope:
     - **Auto-deploy linked services** (`autodeploy_only`, default)
     - **Build only (don't deploy)** (`none`)
     - **Selected services** (`custom`) — displays checkboxes for each linked service in `serviceLinks` (requiring ≥1 selected before submit).
   - Checkbox / toggle for **Clear build cache** (`clear` vs `do_not_clear`).
2. On submit, invoke `useTriggerBuild` and display a clear confirmation state/banner or navigate to `/build-sources/$buildSourceId/builds/$buildId`, showing:
   - Clickable links to any queued `deploys` (`/services/$serviceId/deploys/$deployId`);
   - Any `skippedServices` (e.g., suspended services with reason).
3. Refetch `BuildSourceBuilds` so the new build appears immediately in the list.

- [ ] Returned `deploys` and `skippedServices` are surfaced to the user without silently dropping skipped services.
