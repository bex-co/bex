## Objective

Route the same fetch failures that hit manual sync of an existing Blueprint and the webhook-driven auto-sync worker through t001's classifier, so a sync run's recorded error and the detail page's copy stop leaking `github:` text and commit SHAs too.

## Context

- The auto-sync worker is `lego/backend/internal/apps/blueprint_auto_sync_worker.go`; it fetches the manifest with the same GitHub client and hits the same `APIError` shapes.
- `blueprint_syncs.error_message` (migration 0098, `w6/m50`) records the real `applyErr` from both sync call sites (`CreateBlueprint`'s initial sync and the shared `runSync` engine). That message is exposed on REST, GraphQL `BlueprintSync.errorMessage`, and MCP `list_blueprint_syncs`, and rendered on `dashboard/src/routes/blueprints.$blueprintId.tsx`.
- Fetch-stage failures (wrong branch after a rename, path removed, installation revoked) are the cases the classifier covers; apply-stage failures keep their existing messages.

## Steps

1. Identify the fetch stage in `runSync` and the auto-sync worker and wrap its error through the classifier from t001.
2. Persist the human-readable message (not the raw `github:` string) as `error_message`, and prefix or annotate it with the reason code in a way the dashboard can key on without parsing prose (for example a `reason` column only if a stored code is required; otherwise a stable leading token).
3. Confirm the Blueprint detail page's sync-history rendering shows the new message and no SHA.

## Files

- `lego/backend/internal/apps/blueprint.go` (`runSync`, `CreateBlueprint`)
- `lego/backend/internal/apps/blueprint_auto_sync_worker.go`
- `dashboard/src/routes/blueprints.$blueprintId.tsx` (verify rendering only)

## Acceptance criteria

- [ ] A sync run whose fetch fails on a missing branch records a message naming the branch and no `github:` text or SHA.
- [ ] Auto-sync and manual sync produce the same message for the same failure.
- [ ] `cd lego/backend && go test ./internal/apps/...` is green.

## Out of scope

- Apply-stage error messages (already handled by `w6/m50` and `w4/m102`).
- A new stored `reason` column unless the dashboard cannot key on the message otherwise; if added, note the migration number in the milestone README.
