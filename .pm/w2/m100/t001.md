## Objective

`GET /v1/webhooks/event-types` is registered, authz-classified and documented, and no client can reach it: the strict Render validator matches the request to Render's `GET /webhooks/{webhookId}` template, `event-types` fails the `webhookId` id pattern, and the request dies with `400` before bex's handler runs. Make the validator recognize that a request routed to a bex mux pattern with a literal segment where the Render template has a parameter is a bex-native route, not the Render operation, and let it through. Keep validation for every real intersection. Add a reverse inventory test so the next shadowed route fails CI.

## Context

- The route exists: `lego/backend/internal/webhooks/rest.go:250-254` registers `GET /v1/webhooks/event-types`. Its comment claims it is "what the dashboard's event-type picker lists"; that is untrue, the picker reads GraphQL `webhookEventTypes` (`dashboard/src/features/webhooks/api/webhooks.graphql:40-42`) and MCP returns the vocabulary in `list_webhook_endpoints` (`lego/backend/internal/webhooks/mcp.go:94`).
- The validator claims it: `renderRequestValidator.ServeHTTP` (`lego/backend/internal/api/render_openapi.go:360-409`) passes a request through only when bex's mux has **no** pattern for it. This route has one, so the validator asks the pinned spec (`lego/backend/internal/api/openapi/render-public-api-1.json`) for a route, `FindRoute` matches `GET /webhooks/{webhookId}` (`retrieve-webhook`), and the id-pattern check fails.
- Why tests miss it: `TestRenderRouteIntersectionInventory` (`render_openapi_test.go:183-223`) walks only Render templates against bex's mux, never bex literal paths against Render templates. `TestRenderRequestValidatorPassThroughBoundaries` (`:428-457`) uses a synthetic mux. `crossworkspace_rest_test.go:151` and `scope_matrix_ops.go:620` classify the route as if it were reachable.
- Blast radius (from `w1/089`, exhaustive): a segment-wise comparison of all 183 non-test `Handle`/`HandleFunc` patterns under `lego/backend/internal` against the spec's 208 operations found exactly **one** shadowed route, this one.
- Live at filing: `GET https://api.bex.co/v1/webhooks/event-types` → `400 {"error":"invalid path parameter \"webhookId\"","id":"bad_request","message":"invalid path parameter \"webhookId\""}`; `GET /v1/webhooks/whk-dajvu9ogsm7s73f64gc0` (well-formed, nonexistent) → the canonical `404 {"error":"app not found","id":"not_found",…}` from `w4/done/038`.

## Steps

1. In `ServeHTTP`, after bex's mux reports a matching pattern and `FindRoute` returns a Render operation, compare the two patterns segment by segment. When the bex pattern has a literal segment at a position where the Render template has a `{param}`, and the spec has no exact literal operation for the bex path, skip Render validation and pass the request to bex's handler. Every other case keeps today's behavior.
2. Keep `TestRenderRouteIntersectionInventory`'s list byte-identical: the set of real intersections must not change.
3. Fix the comment at `webhooks/rest.go:250-251` to say GraphQL serves the dashboard picker and REST serves API clients.
4. Add a reverse inventory test next to `TestRenderRouteIntersectionInventory`: enumerate every registered bex route (reuse the mux-walking helper the forward test uses, or the composed server's pattern list), match each against the pinned spec with the same rule as step 1, and fail with the route list when any bex literal is shadowed by a Render parameter with no exact literal operation. Before step 1 lands it must name exactly `GET /v1/webhooks/event-types`; after, it passes.
5. Add a composed-server test: `GET /v1/webhooks/event-types` → `200` carrying `EventTypes`; `GET /v1/webhooks/whk-<20 chars>` → still validated, still the canonical `404` for an unknown id; `GET /v1/webhooks/not-an-id` → still `400`.
