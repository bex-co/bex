# Bound the agent-session background-dispatch fan-out

Follow-up from `w2/m64` (accept-fast agent sessions). `agentsessions.Service.runBackground` (`lego/backend/internal/agentsessions/service.go`) spawns a bare `go fn()` per Create/Steer/Resume with no concurrency cap. Each goroutine is time-bounded (`dispatchTimeout = 15m` + `context.WithoutCancel` → the sandbox client uses `http.NewRequestWithContext`, so a hung mechanism call genuinely cancels — not a true leak), but under a burst or a degraded OpenSandbox backend where calls sit near the ceiling, in-flight goroutines can accumulate (worst case ≈ request-rate × 15m, each holding an HTTP call + up to two DB round-trips). Nothing sheds or queues.

Options (pick when scheduled):

- A buffered-channel semaphore in `runBackground` (small fixed pool, mirroring the operator's `BEX_MAX_CONCURRENT_BUILDS` intent), or a per-workspace cap to bound blast radius.
- Tighten `dispatchTimeout` for the create/egress path (15m is very loose for the documented "tens of seconds"; a cold image pull is the only slow case — a per-phase ceiling would be tighter).

Not a correctness bug (the m64 tests + CAS race guard cover convergence); purely a resilience/back-pressure hardening. Surfaced by the m64 `/simplify` efficiency review, 2026-08-09. Sub-hour scoping look first; promote only if it turns out to need a real pool + shutdown drain.
