## Objective

Prove the new narration reaches every log surface unchanged because it is produced in the one core verb, and prove `failureReason` is not repurposed for a live wait.

## Context

- The progress follower feeds REST `GET /v1/logs`, GraphQL `logs`, MCP log reads and the SSE tail through the same core path (`lego/backend/internal/logs/`, `w1/m48`). At filing time the claim that they carry only `==> Build queued` came from `progress.go`, not from probes.
- `failureReasonFor` (`lego/backend/internal/store/reconciler.go:1320-1323`) is the only place the operator message reaches the deploy row, and only on timeout ("the build never started: …"). The DoD requires `deploys { failureReason }` to stay `""` during the wait.

## Steps

1. Trace the follower's output to each adapter (REST `logs/rest.go`, GraphQL `logs/graphql.go`, MCP `logs/mcp.go`, SSE) and confirm no adapter filters, rewrites or truncates narration lines.
2. Write one adapter-level test (or extend an existing composed-server test) that seeds a `queued` row with a `BuildQueued` reason and reads the build log through REST, GraphQL and MCP, asserting the identical line text on each.
3. Assert in the same test that the deploy row's `failureReason` is empty on REST and GraphQL while queued.
4. Note in the m99 README any adapter that needed a change (expected: none).

## Files

- `lego/backend/internal/logs/` (adapters; read, expected unchanged)
- a test under `lego/backend/internal/logs/` or `lego/backend/internal/api/`

## Acceptance criteria

- [ ] One test reads the same queued narration line through REST, GraphQL and MCP and they match byte for byte.
- [ ] `failureReason` is asserted empty while the row is `queued`.
- [ ] The SSE tail path is confirmed by code reading to share the same producer; recorded in the README.
