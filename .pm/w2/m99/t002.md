## Objective

Every queued-wait reason the operator can write maps to a narration line a tenant may see. The workspace cap names the tenant's own builds; the cluster cap and the scheduler wait use tenant-neutral copy that reveals nothing about other tenants' build activity; `RegistryCredsPending` reads as "preparing registry credentials".

## Context

- `noun` is `workspace` or `cluster` in the operator message (`lego/operator/internal/controller/app_controller.go:1119-1122`); the message itself always carries `<active>/<limit>` (`:806`). For the cluster cap, `4/4` would reveal platform-wide activity of other tenants.
- The scheduler wait is `"waiting for build capacity: " + obs.Message` (`:937-938`) where `obs.Message` is a Kubernetes scheduler message, also not tenant-scoped.
- `RegistryCredsPending` is the other reason that maps to `queued` in `observedDeployStatus` (`lego/backend/internal/store/reconciler.go:868-885`).
- t001 keys re-emission on `(reason, message)`; for the cluster and scheduler cases the rendered line must be stable even as the underlying counts change, or the follower would re-emit a neutral line on every count change. Key on the rendered line, or on `reason` alone for those cases.

## Steps

1. In the mapping t001 introduced, add entries: workspace cap → `==> Waiting for a build slot: this workspace has <active>/<limit> builds running`; cluster cap → `==> Waiting for platform build capacity`; scheduler wait → `==> Waiting for platform build capacity`; `RegistryCredsPending` → `==> Preparing registry credentials`.
2. Parse the noun from the operator message defensively (prefix match on `workspace has` / `cluster has`); anything unrecognized under `BuildQueued` falls back to the neutral line.
3. Make sure the cluster and scheduler lines never contain digits from the operator message, and are not re-emitted when only the counts change.
4. `cd lego/backend && go test ./internal/logs/...`.
