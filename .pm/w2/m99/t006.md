## Objective

Meaningful tests for what m99 shipped. A queued deploy narrates its reason, a changed reason produces a new line, the cluster cap leaks no counts, and the pre-existing lines are untouched.

## Steps

1. **Follower tests** in `lego/backend/internal/logs/` with a fake deploy/App source driven tick by tick:
   1. A `queued` row with `BuildQueued` and `workspace has 2/2 concurrent builds active; waiting for a slot` emits `==> Build queued` then exactly one `==> Waiting for a build slot: this workspace has 2/2 builds running`.
   2. The same reason and message on three more ticks emit nothing new; changing the message to `1/2` emits one new line.
   3. `BuildQueued` with `cluster has 4/4 …` and the scheduler-wait message each emit `==> Waiting for platform build capacity`, and the emitted text contains no digit from the message.
   4. `RegistryCredsPending` emits `==> Preparing registry credentials`.
   5. Once the row reaches `build_in_progress`, `==> Building from …` is emitted as before and no further wait line appears.
2. **Controls.** The existing `==> Build queued` / `==> Building from …` assertions in the current progress tests still pass unchanged.
3. **Failure mode.** A `queued` row whose `Ready` condition is absent or unreadable emits no wait line and does not stall the follower.

## Acceptance criteria

- [ ] Each new test is shown failing on the pre-fix code.
- [ ] `cd lego/backend && go test ./...` is green.
