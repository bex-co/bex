## Objective

Write the ADR that the five Managed OIDC milestones (w2/m476–m480) implement, and point the parity ledgers at them.

## Context

- Render: [render.com/docs/oidc](https://render.com/docs/oidc) (read 2026-11-17). Issuer `https://oidc.render.com/{WORKSPACE_ID}` (a `tea-` id); `sub` = `workspace:<tea>:environment:<evm-…|default>:service:<srv-…>` (the three components on Render's page; template from the [Keycard guide](https://docs.keycard.ai/guides/deploy-to-render-without-secrets/)); `aud` per provider; Pro workspaces and higher.
- Render's [engineering post](https://render.com/blog/how-we-built-render-oidc): each token expires 60 minutes after issuance; a daemon outside the container writes it to a read-only directory before the service starts and refreshes it; one workspace's tokens are rejected by another workspace's trust (per-workspace issuer); audiences are bound per provider.
- Live probe 2026-11-17: `GET https://oidc.render.com/tea-c0000000000000000000/.well-known/openid-configuration` → 200 `{"issuer":"https://oidc.render.com/tea-c0000000000000000000","jwks_uri":"https://oidc.render.com/tea-c0000000000000000000/.well-known/jwks.json","response_types_supported":["id_token"],"subject_types_supported":["public"],"id_token_signing_alg_values_supported":["ES256"]}`. Any well-formed `tea-` id answers (format check, no existence check); `tea-abc` and `tea-d0000000000000000001` answer `404 page not found` (text/plain), and so does the host root. The JWKS holds one EC P-256 ES256 key (`use: sig`) whose `kid` (`_VSjJvQvo0AvEDG68QvXH01Ps2ZPj4Wl_ZIQZNo6PvU`, a 43-character base64url value, consistent with an RFC 7638 SHA-256 thumbprint) is the same for every workspace probed.
- Provider triggers on Render (set as ordinary service env vars, then redeploy): AWS `AWS_ROLE_ARN` → `AWS_WEB_IDENTITY_TOKEN_FILE` (aud `sts.amazonaws.com`); GCP `GCP_WORKLOAD_IDENTITY_PROVIDER` (+ optional `GCP_SERVICE_ACCOUNT_EMAIL`) → `GOOGLE_APPLICATION_CREDENTIALS` (a generated credential configuration; aud = the provider's default audience); Anthropic `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID`, `ANTHROPIC_WORKSPACE_ID` → `ANTHROPIC_IDENTITY_TOKEN_FILE` (aud `api.anthropic.com`); OpenAI `OPENAI_IDENTITY_PROVIDER_ID`, `OPENAI_SERVICE_ACCOUNT_ID` → `OPENAI_IDENTITY_TOKEN_FILE` (aud `api.openai.com`). Render says not to set the `*_FILE`/credentials variables by hand. No REST/CLI/MCP/Blueprint field exists. Build time: native runtimes get the token, Dockerfile builds do not. OIDC does not authenticate ECR image pulls.
- **Brainstorm recommendations, not user decisions** (record the chosen answer and its basis in the ADR): D2 issuer host `oidc.<root domain>` (`oidc.bex.co` in production, configurable for self-hosters); D3 deliver the token through a per-App Secret that bex-api refreshes and the pod mounts read-only (kubelet keeps Secret volumes in tmpfs; residual: a ≤60-minute token sits in etcd), with memory-only CSI delivery filed to FUTURE-MAYBE as the stricter variant; D4 below Pro the trigger variable is accepted and kept, no token is mounted, and the deploy log says why (Render's Hobby behavior is **unverified**); D5 one shared ES256 P-256 key set in a `bex-system` Secret, not OpenBao transit, so token refresh does not depend on OpenBao's manual unseal.
