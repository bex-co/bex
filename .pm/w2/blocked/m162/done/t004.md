## Objective

Give an admin who administers several installations a way to choose which one to bind. Without it, t002 trades one dead end (`no_claimable_installation` on a bound-elsewhere installation) for another (`ambiguous_installation` with no way to resolve it) — and ambiguity becomes the *common* case exactly for the multi-workspace users this milestone serves.

## Context

- The selector cannot be a start-time parameter alone: **the dashboard knows no installation id before the OAuth round trip**. The candidate set is only discoverable with the user token minted from the single-use `code`. Hence a deferred selection; the start-time `installationId` from t002 stays as the shortcut when an id is already in hand.
- At the moment ambiguity is detected, the callback has already completed every proof for every candidate: state, nonce, initiator, fresh `can_manage`, and `VerifyInstallationAdmin` per installation. The selection row is a **memo of a completed proof**, never a substitute for one.
- Design: [ADR078 §3a "The claim selector is not optional"](../../../../../docs/ADR078-github-workspace-connections.md).

## Steps

1. New `github_claim_selections` table: selection id, workspace id, initiating subject, the proved `(installation_id, account_login)` set, `expires_at` (5 min). Migration + store verbs.
2. On ambiguity, persist the proved set and redirect to the dashboard with the selection id instead of `git_error=ambiguous_installation`. Do **not** store or replay the OAuth `code`.
3. Authenticated `GetClaimSelection(id)` — subject-matched and workspace-matched — returning only account logins and installation ids for rendering.
4. `SelectGitClaim(selectionId, installationId)`: consume the row atomically (`DELETE … RETURNING`, so a replay finds nothing), re-check `can_manage` at that moment, and bind **only** an installation drawn from the stored set.
5. Expiry, unknown id, consumed id, and a foreign subject all fail closed to the ordinary `ambiguous_installation` message, whose remedy becomes "start the claim again".

## Acceptance criteria

- [x] Two administered installations ⇒ the callback lands on a selection id, not a bare error code; choosing one binds it.
- [x] The selection id is single-use: a replay binds nothing.
- [x] An `installationId` outside the stored set is refused; the client can choose among proved options but can never introduce a new one.
- [x] A different subject presenting a valid selection id is refused; so is one past its TTL.
- [x] `can_manage` is re-checked at selection time, not inherited from the callback.
- [x] The OAuth `code` is never persisted.
