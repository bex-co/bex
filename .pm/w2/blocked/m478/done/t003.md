Deviation: the cross-audience check is a sibling script, `scripts/oidc-audience-verify.sh`, not an extension of `oidc-aws-verify.sh`. The two share `scripts/lib/oidc-sts.sh`. The self-test is `scripts/oidc-audience-verify.test.sh`, wired into `scripts.yml`.

**Cross-audience check.** The service was a busybox worker `srv-dbupl0hjg4rd8m4ufl6g` in workspace `tea-dbupkv9jg4rd8m4ufl5g`, set to Pro in dev-2's database, created through `POST /v1/services` with `AWS_ROLE_ARN`, `ANTHROPIC_FEDERATION_RULE_ID` and `OPENAI_IDENTITY_PROVIDER_ID`. It ran on bex-api and the operator built from the tree. The operator recorded `providers: [aws, anthropic, openai]`, and bex-api wrote `aws-token`, `anthropic-token` and `openai-token`. `KUBECONFIG=.pm/w2/dev-2/.kubeconfig OIDC_ISSUER_BASE=http://oidc.localhost:54020 bash scripts/oidc-audience-verify.sh tea-dbupkv9jg4rd8m4ufl5g srv-dbupl0hjg4rd8m4ufl6g` exited 0:

- Each file variable named its read-only file, and each token carried Render's claims for its own audience, all with one `sub`.
- An STS for each audience issued credentials for its own provider's token and refused the other two: six refusals, each `azp must match configured OpenID Client ID`.
- `oidc-aws-verify.sh` (with `OIDC_WAIT_REFRESH=0`) also passed on the same service, using the shared lib.

**The example builds on bex.**

- `examples/oidc-ai/render.yaml` validates on dev-2 (`POST /v1/blueprints/validate`: `valid: true`).
- The native Python build of `5bbc7f938` failed before reaching the example. The pinned common run image `ghcr.io/bex-co/bex-cnb-run@sha256:4b809600…` (w8/335) has no linux/arm64 manifest ("no match for platform in manifest"), so no native build runs on the local arm64 cluster. Production nodes are amd64.
- The example therefore gained a `Dockerfile` (`e4a3b1fb4`). As a Docker web service, `srv-dbuq9e9jg4rd8m4uflcg`, it built from `main` and went live. `/healthz` answered 200, and `ANTHROPIC_IDENTITY_TOKEN_FILE` and `OPENAI_IDENTITY_TOKEN_FILE` named the two files in `/var/lib/render/oidc`.
- With placeholder ids, the Anthropic SDK posted the mounted token to `api.anthropic.com/v1/oauth/token`. It was refused (`federation_rule_id is not a well-formed fdrl_ tagged ID`). The OpenAI SDK's exchange at `auth.openai.com` was refused too (`OAuthError`). No provider trusts a dev issuer, so these are the expected answers.
- The first answer exposed an unhandled `WorkloadIdentityError` (500). `main.py` now catches `anthropic.AnthropicError` and answers 502 with the SDK's error.
- A local harness ran the example against stub endpoints with the pinned SDKs (`anthropic` 2.10.0, `openai` 3.55.0). Each SDK exchanged the file's token, and the OpenAI path sent a refreshed file. A stored key answers 503, and a refused exchange answers 502 (failing before the fix).
