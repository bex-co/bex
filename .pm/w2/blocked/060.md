# 060 — A deploy refused by the workspace compute quota says "Waiting for the container to start" until it times out

Why: a Hobby customer who deploys a service larger than the workspace's compute allowance sees the deploy sit "in progress" with a hopeful hint for the whole rollout budget, and is never told the real reason (the quota), so they cannot act on it.

- **Found:** w2/m247 t004 production check, 2026-10-31. In Hobby workspace `tian-personal`, `POST /v1/services` (image `traefik/whoami`, plan `pro_plus`, 4 CPU) → `dep-dbirorqt5fis7381jsag` stayed `update_in_progress` with `deploy_started.details.stallReason` "Waiting for the container to start before detecting its HTTP port", while the namespace showed `FailedCreate … exceeded quota: tenant-compute-quota, requested: requests.cpu=4` on the ReplicaSet. No Pod ever existed.
- **Likely cause:** the same path as `w4/437`: for an unconfigured image web service, `reportWebHTTPSelection` (`lego/operator/internal/controller/web_image_http.go`) reports the waiting hint and never runs the ordinary stall diagnosis. A quota refusal is a ReplicaSet `FailedCreate` / `ReplicaFailure` condition rather than a Pod state, so check that `rolloutStallDiagnosis` names it on the configured-port path too.
- **Fix:** surface `exceeded quota` as the stall reason (and the terminal failure reason) on every web/worker path, worded for the customer (which plan/limit, how to fix: smaller instance type or upgrade the workspace). Coordinate with `w4/437` so both land in one change to `reportWebHTTPSelection`.
- **Parity question:** split into [`w2/061`](061.md) (whether Hobby keeps a services compute cap at all; a user decision).
- **Done when:** the same request shows a quota-specific stall reason within one reconcile, on REST/GraphQL/MCP/dashboard, and the deploy ends with that reason instead of a generic timeout.
