## Objective

While a deploy row is `queued` because of `BuildQueued` or `RegistryCredsPending`, the build-log narration states the operator's current reason, for example `==> Waiting for a build slot: this workspace has 2/2 builds running`, and emits a new line whenever the reason or message changes. The change lives in the one core verb the progress follower runs, so REST, GraphQL, MCP and the SSE tail stay identical by construction.

## Context

- The operator writes the reason: `lego/operator/internal/controller/app_controller.go:796-797` sets phase `Building`, reason `BuildQueued`, message `"<noun> has <active>/<limit> concurrent builds active; waiting for a slot"` (message built at `:806`). `noun` is `workspace` for the per-workspace cap and `cluster` for the cluster-wide one (`:1119-1122`). A scheduler wait uses `"waiting for build capacity: " + obs.Message` (`:937-938`).
- The backend keeps the status but drops the message: `observedDeployStatus` maps `BuildQueued` to deploy status `queued` (`lego/backend/internal/store/reconciler.go:868-885`). The message surfaces only through `failureReasonFor` (`:1320-1323`), and only when a queued row times out. The `deploys` table has no reason column for an open row.
- The narration has one line for the whole wait: `lego/backend/internal/logs/progress.go:84-90` emits `==> Build queued` at `CreatedAt` and nothing more until `StartedAt`.
- The progress follower already reads deploy state each tick (`progress.go`, `w1/m48`).
- Observed 2026-09-14: `dep-dajsm18gsm7s73f647o0` sat `queued` 10:23:01 → 10:31:40 behind two genuine `build_in_progress` rows while the page showed only **Queued** / `==> Build queued`.

## Steps

1. Read `progress.go` and the follower's tick loop; find where deploy state is fetched per tick and whether the App object (or its `Ready` condition) is reachable from there.
2. Decide the carrier for the reason. Prefer reading the App's `Ready` condition (`reason` + `message`) live on each tick while the row is `queued`. If the follower cannot reach the App without a new dependency, add a nullable wait-reason column on `deploys` written by the reconciler alongside `observedDeployStatus`, with a migration. Record the choice and its rationale in the m99 README.
3. Emit a narration line when the row is `queued` and a reason is present, keyed on `(reason, message)`; re-emit only when that key changes. Keep `==> Build queued` at `CreatedAt` and `==> Building from …` at `StartedAt` unchanged.
4. Use a plain phrasing for the workspace cap that names the tenant's own builds: `==> Waiting for a build slot: this workspace has <active>/<limit> builds running`. Leave cluster/scheduler/registry copy to t002 but structure the mapping so t002 is a table entry.
5. Run `cd lego/backend && go test ./internal/logs/... ./internal/store/...`.

## Acceptance criteria

- [ ] A `queued` row with `Ready` reason `BuildQueued` and the workspace message produces one `==> Waiting for a build slot: …` line after `==> Build queued`.
- [ ] The same reason and message on subsequent ticks emit no further line; a changed message emits exactly one new line.
- [ ] `==> Build queued` and `==> Building from …` are byte-identical to before.
- [ ] The carrier decision (live `Ready` read vs stored column) is written in the m99 README with the reason.
