## Objective

Render's `list-notification-overrides` (`GET /notification-settings/overrides`) lists a workspace's per-service notification overrides. bex serves only the per-service `GET`/`PATCH …/overrides/services/{id}` and answers the list with a bare `404 page not found`, while `docs/ADR018-render-parity.md` row 227 marks notifications ✅ on every surface and names every other divergence but not this one. Serve the list as a read-only projection of the same `App.spec.notificationsToSend` the per-service route reads, in Render's envelope, scoped to the caller's workspace. If, after checking Render's response semantics, the list is deliberately not implemented, record it as an explicit divergence instead; the milestone's DoD assumes it is implemented.

## Context

- Contract, pinned spec `lego/backend/internal/api/openapi/render-public-api-1.json`, operation `list-notification-overrides`: optional `ownerId`, `serviceId`, `cursor`, `limit` query parameters; `200` returns an array of `notificationOverrideWithCursor` (`{notificationOverride, cursor}`).
- bex registers only `GET`/`PATCH /v1/notification-settings/overrides/services/{id}` (`lego/backend/internal/apps/rest.go:1334-1341`, classified at `lego/backend/internal/api/scope_matrix_ops.go:570` and `:644`) and member defaults `GET`/`PATCH /v1/notification-settings` (`lego/backend/internal/notifications/rest.go:44-47`).
- The validator passes a route that exists only in Render's spec to bex's mux, which returns its plain `404` (`lego/backend/internal/api/render_openapi.go:360-366`).
- Live at filing (2026-09-14, workspace `tea-d98210cbbpdc73dcrkvg`): `GET /v1/notification-settings/overrides` → `404 "404 page not found"`, same with `?ownerId=`; the per-service control `GET …/overrides/services/srv-dak0pg26m8ac739r60u0` → `200 {"notificationsToSend":"default","previewNotificationsEnabled":"default"}`; `GET /v1/notification-settings/owners/<tea-id>` → `404` is the already-recorded divergence ("workspace defaults remain per-member", ADR018 row 227).
- `docs/render-artifacts/notify-on-fail.md:21-22` lists only the two per-service routes.
- Sibling list routes with `cursor`/`limit` (for example `GET /v1/services/{id}/custom-domains`, `w7/m38`) show the house paging pattern via `core.StablePage`.

## Steps

1. Read the pinned spec's `list-notification-overrides` and `notificationOverrideWithCursor` schemas. Check Render's docs for whether a service whose override is `default` is listed; record the answer (and its date) in the m100 README under a short `## Render semantics` note, and implement whichever Render does.
2. Add `GET /v1/notification-settings/overrides` next to the per-service route in `apps/rest.go`: resolve `ownerId` the way the sibling routes do (the caller's workspace; a foreign `ownerId` yields nothing, never another workspace's rows), list the workspace's Apps, project each to `{serviceId, notificationsToSend, previewNotificationsEnabled}` using the same reader as the per-service `GET`, filter by `serviceId` when given, and page with `cursor`/`limit` in the `{notificationOverride, cursor}` envelope.
3. Classify the new route as `core.OpClassRead` in `scope_matrix_ops.go` beside the per-service entry.
4. Update `docs/ADR018-render-parity.md` row 227 to name the list as served (or, if not implemented, as an explicit divergence with the reason) and add the route to `docs/render-artifacts/notify-on-fail.md`.
5. Add a composed-server test through the strict validator (see t005 for the full matrix; at minimum here: a `failure` service appears, a foreign workspace's service never appears).

## Acceptance criteria

- [ ] `GET /v1/notification-settings/overrides` returns `200` through the strict Render validator with an array of `{notificationOverride, cursor}` entries.
- [ ] A service patched to `notificationsToSend: failure` appears with `failure`; a `default` service is listed or omitted exactly as Render does, with that decision written in the README.
- [ ] `?serviceId=` narrows to one service; `?cursor`/`?limit` page; malformed values get the sibling routes' named `400`.
- [ ] A second workspace's services never appear, including when `?ownerId=` names that workspace.
- [ ] The route is classified read in `scope_matrix_ops.go` and the scope-matrix guard tests stay green.
- [ ] ADR018 row 227 and `notify-on-fail.md` name the route.
