## Progress (2026-11-18)

Checked without production (dev-2, bex-api and operator from the tree):

- **Render has no OIDC field on any surface, and bex adds none** (ADR116 D8): the trigger is an ordinary variable. bex reads it from the release's own environment (a literal, the service's variables, a linked group's), so every surface that writes a variable delivers the same token: REST (the dev-2 service was created through `POST /v1/services` with `AWS_ROLE_ARN`), and the envtests cover the service's own Secret, a linked group and a literal, which is where GraphQL, MCP, the dashboard and Blueprints write.
- **Runtime variables and files against render.com/docs/oidc:** `AWS_WEB_IDENTITY_TOKEN_FILE` is set by the platform and wins over a value the service sets (Render: "Do not manually set"); the token is read-only in memory-backed storage at `/var/lib/render/oidc`, Render's directory. Render publishes no file name, so `aws-token` is unverified.
- **Below Pro, on every surface:** the deploy log (REST `GET /v1/logs` on dev-2; GraphQL and MCP read the same logs service) says `==> Managed OIDC requires a Pro workspace or higher: AWS_ROLE_ARN is set, but no identity token is mounted`. Render's Hobby behavior is unverified, so this wording is bex's.

- **New services are born with the plan label** (create path), so their first deploy decides with it; verified on dev-2 with two services created through REST.
- **Not walked on dev-2:** setting the variable after create through GraphQL (`setEnvVar`), MCP, the dashboard or an env group. dev-2 runs without OpenBao, so every env write after create answers `SECRETS_UNAVAILABLE` there; only `dev-env.sh 2 agent-up` brings it, with the whole agent stack. The operator side of those sources (the service's own Secret, a linked group) is covered by the envtests.
