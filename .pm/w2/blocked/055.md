# 055 — Bound the barman-cloud sidecar's resources in a planned window (it restarts every backed-up tenant Postgres)

Why: the CNPG barman-cloud plugin sidecar sets no resources, so the namespace LimitRange defaults give it `limits: cpu 2, memory 4Gi`. A 1-CPU Postgres instance Pod therefore reports 3 CPU / 6 Gi of limits. After w2/m247 t001 this no longer touches the compute quota, and limits do not affect scheduling, but it misstates each Pod's ceiling and lets a misbehaving sidecar take 2 CPU.

## Ready

Commit `8685c0a79` (branch `worktree-agent-ad5c00b1035154da4`, not merged) sets the `bex-tenant-postgres` ObjectStore's `instanceSidecarConfiguration.resources` to requests 100m/128Mi and limits 1 CPU/1Gi, with a `gitops-validate.sh` guard. Verified locally with the pinned plugin v0.13.0.

## Gate

The operator copies the ObjectStore into every tenant namespace, and the plugin rolls each Cluster's instance Pods on a sidecar change. So the rollout **restarts every backed-up tenant Postgres once**: a few seconds of downtime for single-instance databases and a switchover for HA ones. It needs either a user-approved maintenance window or a staggered rollout that touches one namespace at a time.

## Acceptance

- [ ] Every tenant Postgres instance Pod shows the bounded sidecar resources; no unplanned downtime.

## Blocked 2026-10-30

Needs the user to choose between a maintenance window and accepting a staggered rollout (one namespace at a time, with a few seconds of downtime per single-instance database), because every backed-up tenant Postgres restarts once. The worker can then merge `8685c0a79` and run it.
