# 037 — m162's `github_claim_selections.subject` needs a disposition before it ships

Why: the in-flight ADR078 N:N work adds a new subject-bearing table, and ADR086's closing rule ("future subject/provenance columns must extend this table and cleanup before shipping") is currently enforced by one narrow test that this change will turn red — better to land the declaration with the feature than to discover it in CI.

**Status: heads-up for work already in the tree, not a defect.** Migrations `0123_git_connections_many_to_many` and `0124_github_claim_selection` plus `lego/backend/internal/store/github.go` are **uncommitted** in the working tree as of 2026-09-16.

Two things `0124` needs before it lands:

1. **The census.** `github_claim_selections.subject` will appear in the `information_schema` query at `lego/backend/internal/store/accounts_pg_test.go:280-330`, whose `want` list does not include it — the identity/provenance census fails until the column is declared. That is the guard working as designed.
2. **The disposition.** ADR086's § Data disposition table needs a row for it. The likely answer is *hard-delete on account deletion* (it is a short-lived, single-use, subject-bound memo of a completed proof — the same class as `github_connect_transactions.subject`, which is already hard-deleted in `CleanupAccountSubject`). Worth confirming the piggybacked expiry sweep really bounds the table: the sweep is a `DELETE` on write, so if no further claim is ever made, the last rows persist with their subject until the next one.

Also check `workspace_id` on the new table: it has no FK to `tenants`, so its rows outlive a deleted workspace. `w2/m164/t002`'s tenant-scope census will flag it; a cascade is cheaper to add now, in the same migration, than as a follow-up pair.
