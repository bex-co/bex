## Objective

Add a backend capability that, given a workspace's GitHub connection, a repo, a branch, and an optional root directory, returns the top-level file names of that subtree — the raw material for runtime detection. One shallow listing (non-recursive at the root directory level), authenticated with the existing installation-token plumbing, bounded and cached enough to be wizard-interactive.

## Context

- GitHub App connection + installation tokens: `lego/backend/internal/github/` (`client.go`, `service.go` — repo listing already exists; follow its auth/pagination idioms).
- GitHub API: `GET /repos/{owner}/{repo}/contents/{path}?ref={branch}` (or the git/trees API) — contents at a path is the natural fit for a Root Directory-scoped probe.
- Authorization: same relation the repo-listing query requires (the caller must already see the connection/repo).
- Keep it read-only and side-effect free; a short TTL cache (the `core.TTLCache` idiom) is acceptable if needed for re-infer-on-keystroke behavior, but debouncing belongs in the dashboard.

## Steps

1. Add a `ProbeRepoTree`-style method to the github service returning the entry names (files only, names + type) at the given path.
2. Handle: missing path (404 → empty result), empty repo, rate-limit/backoff → typed error the caller can treat as "unknown".
3. Unit-test against the package's existing fake/recorded client pattern.

## Acceptance criteria

- [ ] Probe returns correct entry names for a nested root directory; 404/empty/rate-limit paths return the typed "unknown" outcome, never an error that would surface in the wizard.
