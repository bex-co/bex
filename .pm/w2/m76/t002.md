## Objective

Store per-member browser push subscriptions (push-service `endpoint` URL + `p256dh`/`auth` ECDH keys) with the same ownership/cascade discipline as native device subscriptions, and expose register/unregister on the existing notification-device-subscription surface so the dashboard can bind a browser to the caller.

## Context

- Native precedent: `lego/backend/internal/store/migrations/0062_device_push_subscriptions.up.sql` — `device_push_subscriptions` PK `(tenant_id, subject, device_id)`, FK cascade from `tenant_members`, `token_digest` sha256 uniqueness among active rows, `revoked_at` soft revoke. **Repo fact:** it CHECK-constrains `provider = 'expo'` and `platform IN ('ios','android')` — web push needs either a migration relaxing those CHECKs or (cleaner) a sibling `webpush_subscriptions` table keyed on endpoint digest.
- Store layer: `lego/backend/internal/store/device_subscriptions.go` (+ `_test.go`, `_pg_test.go`); service layer: `lego/backend/internal/notifications/subscriptions.go`.
- REST surface: `lego/backend/internal/notifications/rest.go` — `GET/POST /v1/notification-device-subscriptions`, `DELETE .../{deviceId}` via `UnregisterDeviceSubscription`. All caller-scoped ("always me"), no workspace path param.
- Latest migration is `0087_...`; the new one is `0088_webpush_subscriptions`.
- MCP deliberately has NO device-registration tool (ADR052 / ADR018 line 27) — keep that scope for web push.

## Steps

1. Migration `0088_webpush_subscriptions.{up,down}.sql`: `(tenant_id, subject, browser/device id)` PK, `endpoint` (bounded length), `p256dh`, `auth`, `endpoint_digest` unique among active rows, `revoked_at`, `preference_id REFERENCES notification_settings ON DELETE SET NULL`, FK cascade from `tenant_members` — mirroring 0062's comments and constraints.
2. Store methods in a new `lego/backend/internal/store/webpush_subscriptions.go` (register-revokes-prior-owner on endpoint reuse, list-active-for-member, revoke, prune) with pg tests following `device_subscriptions_pg_test.go`.
3. Service verbs in `lego/backend/internal/notifications/subscriptions.go` (or sibling): `RegisterWebPushSubscription` / `UnregisterWebPushSubscription` / list; validate endpoint is HTTPS and keys are base64url.
4. REST: extend the `/v1/notification-device-subscriptions` family in `rest.go` (a `kind`/dedicated path such as `/v1/notification-webpush-subscriptions`); GraphQL mutation beside `pushNotificationSettings` in `lego/backend/internal/notifications/graphql.go`; no MCP tool.
5. Endpoint URLs and keys never appear in list responses beyond what the owner needs (digest/created-at style metadata, matching the token-free native list).

## Acceptance criteria

- [ ] Register/list/unregister round-trips for the caller; another member cannot see or delete the subscription.
- [ ] Re-registering an endpoint owned by a different subject revokes the old owner (0062's bearer-capability rule).
- [ ] Membership/workspace deletion cascades subscriptions away (FK verified in pg test).
- [ ] With `BEX_WEBPUSH_*` unset the register verb reports the channel unavailable (503/`not configured`), storing nothing.

## Out of scope

Delivery (t003), dashboard subscribe flow (t005). Relaxing `device_push_subscriptions` CHECKs for non-Expo native providers.
