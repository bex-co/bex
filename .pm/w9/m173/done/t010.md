## Objective

Steady manifest commits must not keep production on an old pin. On 2026-11-06 production stayed on 92ff00293's pin from 00:51 to past 13:00 UTC:

- every deploy run (379af6c08, 3310f6484, 8c498d33c, …) passed its tests, then skipped `build`/`deploy` in `check-supersession`, because newer manifests had landed (exit 4);
- with tests taking 1–2.5 h on contended runners, a manifest commit almost always landed in that window, including this workstream's own `deploy.yml` fixes.

## Done (2026-11-06)

- `scripts/deploy-pin-stale.sh <max-seconds>` reports whether the last `chore(deploy): pin platform images to …` commit on origin/main is older than the bound. A pin with no commit in reach counts as stale. Its unit test is `scripts/deploy-pin-stale.test.sh`, wired into `scripts.yml`.
- In deploy.yml `check-supersession`, exit 4 now skips only while the pin is under 2 h old. Past that the run builds and pins, which the write-back guard already allows on 4. Exit 0 (never pin: a reshaped field or a rollback) still always skips.
- Monitoring lesson: a deploy run's `success` conclusion does not mean it deployed, because a superseded run also succeeds with `build`/`deploy` skipped. Check the gitops pin commit, or that `deploy` ran, instead.
