# Recreating an app with the same name can run the previous image (gen-1 tag reuse)

Filed by `w9/m44/t005` (sample lifecycle sweep, 2026-07-18). During the sweep, `hello-python` was deployed, deleted, and re-deployed under the **same name** several times. One re-deploy built the corrected image but the pod ran the **old** code:

```
# build cloned github.com/bex-co/bex@b42f681 (has CMD ["python","main.py"]) and
# pushed …-hello-python:gen-1@sha256:341e43e9… — yet the running pod logged:
Error: Could not locate a Flask application …   # the PRE-fix `flask run` image
```

**Mechanism.** The operator tags every tenant image `<name>:gen-<generation>` and references it **by tag** (`build.Options.ImageRef()` → `zot…/hello-python:gen-1`; not by digest). A freshly-created App always starts at **generation 1**, so delete + recreate of the same name pushes to the *same* tag `hello-python:gen-1` that a prior incarnation already populated. When the new pod pulls `hello-python:gen-1`, it can get a **stale image** — the node's cached `gen-1` layer, or a pull that races the new push — instead of the just-built one. Confirmed by contrast: the same fix under a **unique** name deploys the correct image first try.

**Why it matters.** A real user who deletes a service and recreates it with the same name (or two users reusing a common name across workspaces — mitigated by the `tea-…-` repo prefix, but not within one workspace) can silently run stale code. It also makes rollbacks/gen-1 collisions nondeterministic.

**Fix options:**

- **Reference tenant images by digest** (`@sha256:…`) on the Deployment/CronJob/publish Job, resolving the digest from the build's push output rather than the mutable `gen-N` tag. Deterministic; also lets kubelet skip re-pull safely. Preferred.
- **Never reuse a tag:** derive the tag from something monotonic/unique per build (a build id / xid), not a per-App generation that resets to 1 on recreate.
- At minimum set `imagePullPolicy: Always` for tenant pods AND ensure the pull resolves the current digest (Always still trusts the tag→digest mapping, so this alone is insufficient if Zot serves a stale manifest).

**Evidence/repro:** `scripts/samples-lifecycle.sh hello-python` twice in quick succession (same name) vs. once with `NAME_SUFFIX=-x1`. The sweep now uses unique names to sidestep this while it's open.

~1 milestone. Source: w9/m44 prod sweep, 2026-07-18. Related: the digest-pin discipline the platform already uses for its OWN images (`chore(deploy): pin operator+dashboard to <sha>`), not yet applied to tenant images.
