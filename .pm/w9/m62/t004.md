## Objective

Feature hooks default to `fetchPolicy: "cache-and-network"`, which fires a network request on mount even when the Apollo cache is warm from SSR dehydration or a w9/m68 route-loader prefetch — throwing away the prefetch. Make loader/SSR-primed queries render from cache without a duplicate mount-time fetch, while keeping freshness via the existing polling.

## Context

- `dashboard/src/router.tsx:35-44` — SSR dehydrates `client.cache.extract()` and restores it client-side (correct). But nearly every `features/*/hooks` read uses `cache-and-network`, so the warm cache is immediately re-fetched.
- The title loaders already solve this correctly: `titleLoaderFetchPolicy` → `cache-first` on `stay` (`common/lib/document-head/index.ts:139`) — reuse/extend that pattern rather than inventing a new one.
- **Coordinate with w9/m68** (relocated from w5): its loaders prime the overview + service/static detail + one list route. This task covers at minimum those routes' mount hooks; a blanket hook-default change is fine if tests prove no staleness regression (polling still delivers freshness).

## Steps

1. Decide the seam with m68's shipped shape in view: per-hook `cache-first` on the loader-primed queries vs a shared "primed" fetch-policy helper. Prefer the shared helper (one place, greppable).
2. Apply to the m68-covered routes' primary hooks; verify in devtools: hover-prefetch → click → **no** duplicate query on mount; SSR first-load → hydrate → no immediate refetch; data still updates on the poll interval.
3. Check mutation paths that relied on `cache-and-network` freshness (refetchQueries already handle post-mutation refresh) — no behavior change expected; note anything found.
