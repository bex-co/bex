## Objective

An Admin's API key creates and repoints a webhook endpoint, as Render's keys do ("Create, update, and delete webhooks"). Delegated third-party OAuth tokens and other machine clients stay refused, as w4/079 intended.

## Context

- `webhooks.Service.Create` (`lego/backend/internal/webhooks/service.go:521`, gate at `:531`) and `Update` (repoint, `:936`) call `core.Base.AuthorizeMintClass` (`internal/core/base.go:1170`). That gate admits only a Kratos session or a human OAuth token from a platform client.
- An API key authenticates as a non-human `oauth2` identity whose `ClientID` is the key (`internal/api/auth_apikey.go:143`). Telling a bex key from any other client_credentials client needs `KeyCreator`'s `isKey` with a non-empty creator.
- w4/079's reasoning is in `docs/ADR012-auth.md`. The dispatch-time op class (`core/scope.go` `RequireOpClass`) already treats mint as write, so only the verb gate refuses.

## Steps

1. Add a gate for "a session, a platform human OAuth token, or a bound bex API key with a recorded creator". Use it on webhook create and on a repoint only. The relation check (`RelCanManage`, Admin) still decides the role.
2. Leave `AuthorizeMintClass` unchanged everywhere else: API keys, SSH keys, invites, role changes, Postgres users, deploy hooks, organization and workspace creation.
3. Amend ADR012 (w4/079's entry): an API key is a first-party credential that a human minted through the mint-class gate, it is revoked with its creator's membership, and Render admits it.

## Files

- `lego/backend/internal/core/base.go` (or `webhooks/service.go`), `internal/webhooks/`, `docs/ADR012-auth.md`, tests

## Acceptance criteria

- [ ] An Admin's key creates a webhook (201 with its secret) and repoints one. A Developer's key gets 403. A delegated `bex.write` OAuth token and a non-key client_credentials client are still refused.
- [ ] A key is still refused `POST` API key, SSH key enrollment and invites.

## Out of scope

- Admitting keys to other mint verbs (each is a follow-up from t009).
