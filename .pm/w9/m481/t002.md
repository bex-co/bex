## Objective

A key minted by an Admin acts as Admin in that workspace. A key minted by a Developer acts as Developer.

## Context

- `apikeys.Service.CreateAPIKey` (`lego/backend/internal/apikeys/service.go`) runs `AuthorizeMintClass`, `Authorize(RelCanManageKeys)` and `AuthorizeFresh(RelCanManageKeys)`, then binds under `WithTenantAdvisoryLock`.
- `tenancy.Service.BindKey` (`internal/tenancy/tenancy.go:612`) calls `GrantWorkspaceMember` (always `developer`) and rolls the binding back if that fails. `GrantWorkspaceRole` (`internal/authz/authz.go:252`) writes any role.
- `store.BindClient` writes the key's `tenant_members` row at `developer`.

## Steps

1. Read the creator's current role from their own `tenant_members` row inside the mint's lock. Refuse the mint if the row is missing, or if the creator's own role reconciliation is still pending (fail closed).
2. Write the key's row and tuple at that role, keeping the rollback on a failed grant.
3. Keep `UnbindKey` revoking whatever role the key holds (it revokes `developer` today).

## Files

- `lego/backend/internal/tenancy/tenancy.go`, `internal/apikeys/service.go`, `internal/store/` (bind), tests beside them

## Acceptance criteria

- [ ] The real-DB backend suite shows an Admin's new key holds `admin` and a Developer's holds `developer`, in both `tenant_members` and OpenFGA.
- [ ] A mint while the creator's own role is unsettled is refused and binds nothing.
- [ ] Revoking a key removes its tuple whatever its role.
