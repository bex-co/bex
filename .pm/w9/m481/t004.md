## Objective

Enforce invariant I1 at request time, in the form t001 chose, so that a lagging or failed tuple write never lets a key act above its creator's current role. Prove I2 and I3 with tests.

## Context

- `core.Base.Authorize` / `authorizeAndAudit` (`lego/backend/internal/core/base.go:747`) and the fresh variants used before durable writes.
- `guardCallerRoleSettled` (`internal/members/service.go:1565`) is the existing veto for a human caller whose own demotion has not converged (round-19 #3).
- `KeyCreator` (`internal/apikeys/service.go:827`) is the cached key → creator lookup that the login-requirements gate already calls on every key request.

## Steps

1. Apply the cap or veto from t001 to every key caller. A key whose creator is still being demoted is refused the higher relations on its next request, fresh checks included.
2. Leave a key with no `createdBy` at its Developer binding. It never gains the creator path (I3).
3. Make a creator lookup that cannot answer (Hydra down) fail closed, the way the login-requirements gate does.

## Files

- `lego/backend/internal/core/base.go` (or the seam t001 picks), `internal/members/service.go`, tests beside them

## Acceptance criteria

- [ ] A test leaves a key's `admin` tuple in place (a failed revoke) after its creator's demotion to Developer. The key is refused every `can_manage` write.
- [ ] A test seats the creator as Admin in workspace B. Their workspace-A key is refused in B on every verb (I2).
- [ ] A creatorless key never passes a `can_manage` check.
- [ ] Each of these tests fails when its guard is reverted.

## Out of scope

- Changing human callers' cache TTLs.
