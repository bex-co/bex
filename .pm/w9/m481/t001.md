## Objective

Choose the mechanism that makes a bex API key act with its creator's current workspace role, following it up and down and never exceeding it, and record it with its security reasoning before any code changes.

## Context

- Render: a key's permissions go up to "every permission your member role allows", and "Your key's access adjusts to match your new member role" ([render.com/docs/api-keys](https://render.com/docs/api-keys), read 2026-11-18).
- bex: `BindKey` (`lego/backend/internal/tenancy/tenancy.go:612`) writes the key subject `user:<clientID>` a `developer` tuple. ADR024 § Roles and § A member is a person describe the key's `tenant_members` row. ADR012 §8e covers the bearer form.
- Creator: `apikeys.APIKey.CreatedBy` is stored in the Hydra client's metadata. `KeyCreator` (`internal/apikeys/service.go:827`) already resolves key → creator, and the login-requirements gate uses it on every request (`internal/twofactor/gate.go:512`).
- Role convergence: human role changes go through `RoleReconciliationStore` (`internal/members/service.go:211`), and `guardCallerRoleSettled` (`:1565`) vetoes `can_manage` while a caller's own role write is pending.
- Minting needs `can_manage_keys` (developer or admin; `deploy/gitops/authz/model.fga`), so a key's role is admin or developer today.

## Steps

1. Compare these mechanisms against the boundary in the milestone README (I1–I5):
   - **(a) Mirrored tuples:** the key's role tuple equals its creator's, written at mint and on every role change, ordered so that a demotion revokes the key's tuple no later than the creator's.
   - **(b) Mirrored tuples plus a request-time cap:** a key caller's decision also requires its creator to pass the same check, or the creator's pending reconciliation vetoes the key's writes as it vetoes the creator's own.
   - Rule out evaluating the request as the creator: that would leak the creator's other workspaces, which I2 forbids.
2. Pick one and state how it meets I1 under a failed or pending tuple write and under caches. State its cost per key request.
3. Check production for keys with no `createdBy`, read-only (Hydra admin list through `scripts/fetch-app-kubeconfig.sh`, or bex-api's own read). Record the count. Whatever it is, I3 applies.
4. Amend ADR024 (roles table and § A member is a person), ADR012 §8e and ADR018's members and API keys rows (as on Render, no divergence left). Record the security reasoning: threats, the invariants and the residual risk.
