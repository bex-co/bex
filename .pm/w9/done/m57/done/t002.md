## Objective

Prove (or refute) ADR041 gap 1 live: for a store-managed stack, `fromService: {property: host}` injects the bare bex.yml name while the k8s Service is named `<tenant>-<name>`, so the injected hostname does not resolve. This is the regression baseline t004 fixes against.

## Context

- Literal injection: `lego/backend/internal/apps/deploy.go:1426` (`host` → `ref.Name`), `:1430` (`hostport`); asserted bare by `stack_test.go:242`.
- CR naming since w4/m19: `core.CRName(tenant, name)` = `<tenant>-<name>` (`lego/backend/internal/core/base.go:728`); the Service is named after the CR (`app_controller.go:1114`).
- Counter-case that kept this invisible: legacy/hand-applied CRs have bare CR names, where the literal resolves — the basis of ADR006 §Blueprint's now-stale claim.
- Cluster: `bash scripts/mock-cluster.sh` (kind + CAPD) or a dev cluster with the control-plane store enabled (`BEX_CP_DB_URI`) — the gap only exists on the store-managed path.

## Steps

1. Deploy a two-service `bex.yml` stack via bex-api (web + private, one `fromService` host link) into a store-managed workspace.
2. Exec/log from the consumer pod: show the injected env var value and that connecting to it fails DNS resolution, while `<tenant>-<name>:<port>` connects.
3. Append the repro transcript to ADR041 gap 1 (dated, cluster noted); if the gap does NOT reproduce, correct ADR041 and record why (that finding reshapes t004).
