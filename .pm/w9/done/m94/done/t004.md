## Done 2026-10-02 — live-verified on production

Released `bex v0.2.1` (`/opt/homebrew/bin/bex`, pin v2.27.0), production `https://api.bex.co/v1/` (deploy pin `1263d12ae3fa`, which contains the m94 commits), human device login in an isolated config, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`). The sandbox baseline was empty.

```text
$ bex ea sandboxes create --plan=starter --timeout=600 -o json
→ exit 0 (3 s) · {"id":"sbx-…","status":"running","plan":"starter","timeoutSeconds":600}
$ bex ea sandboxes copy ./probe sbx-…:/tmp/probe --confirm
→ exit 0 · Uploaded ./probe to sbx-…:/tmp/probe          # passes the client's ^(sbx-…): parser
$ bex ea sandboxes copy sbx-…:/tmp/probe ./probe.back --confirm
→ exit 0 · Downloaded … ; bytes identical ("qa-probe")
$ bex ea sandboxes exec sbx-… -- true                                → exit 0
$ bex ea sandboxes exec sbx-… -- sh -c 'echo out; echo err >&2; exit 7' → out / err, exit 7
$ bex ea sandboxes list -o json                                      → ["sbx-…"]
$ bex ea sandboxes stop sbx-… --confirm                              → exit 0
$ bex ea sandboxes list -o json                                      → null (REST GET /v1/sandboxes → 200 [])
$ bex ea sandboxes exec sbx-… -- true → exit 1 · 404 (SANDBOX_NOT_FOUND): sandbox not found
```

Cross-surface checks used the same QA bearer. `GET /v1/sandboxes/sbx-…`, GraphQL `sandbox(id:)` plus `sandboxes`, and MCP `list_sandboxes(workspaceId:)` each reported the identical `sbx-…` id. A bare-UUID id (`GET /v1/sandboxes/00000000-…` and `bex ea sandboxes exec 00000000-… -- true`) answered `404 SANDBOX_NOT_FOUND` with the non-enumerating body, never 500. The fixture was stopped and is absent from list/GET, so no `qa-` sandbox residue remains. The `ea sandboxes create` row of `docs/cli-compatibility-checklist.md` now cites this result.

Side observation, not filed: the client prints `null` for an empty `list -o json` while the server returns `[]`. That is the pinned client's nil-slice encoding, not a bex defect.
