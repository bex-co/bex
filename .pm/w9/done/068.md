# 068 — A free web service cannot be cloned: bex refuses the `maintenanceMode` it just emitted

Why: `services create --from` is unusable for every free web service, and the reason is bex rejecting an inert value of its own making — refusing to *disable* a feature the plan doesn't have.

Live, 2026-09-21 (sweep 3), production, `bex v0.2.1` / pin v2.27.0, workspace `bex-canary`, human device-flow OAuth. Fixture `qa-20260921-f16fa42b-nweb` (free web service), created and deleted in-sweep.

```text
$ bex services create --from srv-daoqa7rs0ils73bgphvg --name qa-…-clone --region frankfurt --confirm
Error: received response code 400: bad request: maintenanceMode requires a paid web service plan
```

`--region frankfurt` is already the documented workaround for the *other* clone blocker (`w9/done/m56` t001: a source reporting `fsn1` fails the pinned client's closed region enum). With that applied, cloning is still impossible — this is a second, undocumented blocker behind the first.

## The contradiction, isolated

`GET /v1/services/<free web service>` returns:

```json
"serviceDetails": { "plan": "free", "maintenanceMode": {"enabled": false, "uri": ""}, … }
```

Echoing that exact value back on create — which is precisely what the pinned client's clone does — is refused:

| create body (free plan, otherwise identical)      | result                                                        |
| -------------------------------------------------- | ------------------------------------------------------------- |
| `maintenanceMode` omitted                           | **201**                                                       |
| `maintenanceMode: {"enabled": false, "uri": ""}`    | **400** `bad request: maintenanceMode requires a paid web service plan` |

So the rejected value is the inert default, not an attempt to use the feature.

## It is exactly one field

Every other field a free web service reads back round-trips cleanly. Each was echoed back individually into an otherwise-valid free create (`dryRun`):

```text
envSpecificDetails       200
healthCheckPath          200
maintenanceMode          400  bad request: maintenanceMode requires a paid web service plan
maxShutdownDelaySeconds  200
numInstances             200
renderSubdomainPolicy    200
```

## Root cause

`lego/backend/internal/apps/service.go:672-683`:

```go
func validateMaintenanceEligibility(serviceType, tier string, mode *MaintenanceModeView) error {
	if mode == nil { return nil }
	if serviceType != appv1alpha1.TypeWebService { … }
	if tier == "" || tier == "free" {
		return fmt.Errorf("%w: maintenanceMode requires a paid web service plan", core.ErrBadRequest)
	}
	return nil
}
```

The gate fires on the field being **present**, never on `mode.Enabled`. A disabled maintenance mode is a no-op on any plan, so presence is the wrong trigger.

## Fix

Gate on *enabling*, not on presence: reject only when `mode.Enabled` is true on a free/empty tier (and keep the existing URI validation). Then the read shape round-trips and `--from` works.

Do **not** fix this by omitting `maintenanceMode` from the read shape for free plans. [`w4/125`](../w4/125.md) establishes the opposite constraint from Render's schema, quoting the gate at `apps/render.go:434-442`: "Render's maintenanceMode is required on webServiceDetails (never omitted)". The read side is correct; the write side is wrong.

Check the same presence-vs-value mistake on the sibling branch two lines up (`serviceType != TypeWebService`) — a non-web service that ever carries a disabled `maintenanceMode` would fail identically. REST omits the field for non-web types today, but GraphQL returns `{enabled:false, uri:""}` for every type (`w4/125`), so anything round-tripping a GraphQL read into a REST write hits it.
