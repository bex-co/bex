# A new Key Value's connection info answers 409 "credentials are still converging" until it is up, where Render answers it at once

Why: Render's Terraform provider reads `connection-info` straight after `POST /v1/key-value` to fill its connection attributes, so every `render_keyvalue` and `render_redis` create fails on bex. The same read fails for any client that fetches the URL right after creating the store.

- **Found by:** w9/m474, dev-9, 2026-11-18 ([checklist](../../docs/terraform-compatibility-checklist.md), class 4). All 4 Key Value and Redis provider tests stop here.
- **Render:** `keyvalue_datasource_cassette.yaml`. Create answers 201 with `status: "creating"`, then `GET /v1/key-value/{id}/connection-info` answers 200 `{"internalConnectionString":"redis://red-…:6379","externalConnectionString":"rediss://red-…:<password>@oregon-keyvalue…:6377","cliCommand":"…"}` in the same second.
- **bex:** `lego/backend/internal/keyvalue/service.go` `KeyValueConnectionInfo` answers `409 conflict: key value credentials are still converging` while `Status.CredentialRevision` is empty, which it is until the operator records it once the pods serve. w8/305 removed the same refusal for restarts; a new store still hits it.
- **Fix direction:** the password is chosen at create and never changes (w2/m61), so connection info can be assembled from the credential Secret and the store's address as soon as both exist, without waiting for pods. If the Secret itself is written later, write it at create.
- **Done when:** `connection-info` answers 200 with Render's three fields within a second of a create on REST, GraphQL and MCP, a test covers a store with no recorded revision, and `TestAccKeyvalueDataSource` gets past its first step.

## Resolution

**DONE 2026-11-18.** Two changes in `lego/backend/internal/keyvalue/service.go`:

- **No recorded revision is served.** `KeyValueConnectionInfo` refuses only a recorded `status.credentialRevision` that differs from the credential Secret's password. Until the pods serve, no other password exists for a client to split against.
- **A read before the first reconcile waits for it.** `awaitFirstReconcile` re-reads the store every 50 ms, for at most 5 s, until the operator has written its status. The first live probe showed why: before the operator's first pass, a public store answered 503 "no external host" for its first 45 ms, and a private store would have answered 404.

Tests in `first_reconcile_test.go`:

- `TestConnectionInfoServesAStoreWithNoRecordedRevision` covers a store with no recorded revision on REST (`/v1/key-value`, `/v1/redis`) and GraphQL. It fails with the old gate restored (409).
- `TestConnectionInfoWaitsForTheFirstReconcile` covers a first pass that lands mid-read, a store never reconciled and a store deleted during the wait. It fails without the wait (404).

MCP has no Key Value credential read, and neither does Render's MCP server. ADR021 step 4 and ADR018's Key Value row record the change.

**Live check on dev-9** (bex-api from this tree, the shared operator, host load average about 70), reading connection info right after `POST /v1/key-value`:

- A public store answered REST 200 at +978 ms and GraphQL 200 at +1302 ms, while still `creating`.
- A private store answered REST 200 at +659 ms.
- The external string is `""` and `externalCertificate` is `pending` until the TLS listener opens (w8/237).

**Terraform recheck** (`terraform-provider-verify.sh keyvalue redis`, recordings sha256 `d627c85a…`):

- `TestAccKeyvalueDataSource` and `TestAccRedisDataSource` now apply. The create's connection-info read answered 200, the data source read too, and checks 1–10 pass. They stop at checks 11–13, the shape of the three strings, which is filed as w9/122.
- `TestKeyValueResource` and `TestRedisResource` get past connection info to `log_stream_override` (`404`), a recorded omission.
- The sweep deleted what the failing tests left. The probe stores were deleted (204).
