## Objective

English users currently download the entire Chinese catalog in the entry chunk (and vice versa). Bundle only the default language eagerly and lazy-load the other on demand, so per-locale cost scales as languages are added.

## Context

- `dashboard/src/i18n/index.ts:1-53` statically imports all 26 `en` + 26 `zh` namespaces; `src/i18n/init.ts` passes the combined `resources` to `i18n.init()` at module load (entry chunk).
- Proof: Chinese strings are present in the entry chunk of an English session.
- Language switching runs through `i18n.changeLanguage()` (called from `routes/__root.tsx` `beforeLoad` and the language switcher).

## Steps

1. Keep `DEFAULT_LANGUAGE`'s namespaces statically imported; convert the other locale to a `import()`-based loader that calls `i18n.addResourceBundle` per namespace before `changeLanguage` resolves.
2. Handle SSR: the server must still render either locale synchronously (load both on the server, split only the client bundle) with no hydration mismatch.
3. Verify: switch en→zh in the browser — every namespace renders translated after the lazy load, no flash of translation keys; `yarn build` shows zh strings out of the entry chunk (own async chunk).

## Files

- `dashboard/src/i18n/index.ts`
- `dashboard/src/i18n/init.ts`
- `dashboard/src/routes/__root.tsx` (only if `changeLanguage` needs to await the loader)

## Acceptance criteria

- [ ] Entry chunk of a production build contains no zh catalog strings.
- [ ] Live en→zh switch renders fully translated UI (no raw keys), and a zh-preference session SSRs/hydrates without mismatch.
- [ ] Locale-parity tests still pass unchanged.

## Out of scope

- Adding further languages.
