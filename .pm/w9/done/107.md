# A bex API key always acts as a Developer, where Render's key carries up to its creator's member role, so Terraform cannot manage webhooks, registry credentials, owner notification settings or protected environments

Why: Render's provider authenticates with an API key. On bex every key is bound as a Developer, and webhook creation refuses any non-human caller, so four resources an Admin manages through Render's API fail through Terraform on bex.

- **Found by:** w9/m474, dev-9, 2026-11-18 ([checklist](../../../docs/terraform-compatibility-checklist.md), class 3).
- **Render:** [render.com/docs/api-keys](https://render.com/docs/api-keys) (read 2026-11-18): "Your member role in the selected workspace determines which permissions you can grant an API key", "Enable all: Grants every permission your member role allows", and classic keys "have the same permissions as your member role in every workspace you belong to". The provider's recordings show an API key creating a webhook (201), patching owner notification settings (200) and creating protected environments (201).
- **bex:** `lego/backend/internal/api/tenancy.go` `BindKey` writes the key's `developer` tuple (ADR024's role table). Admin-only writes are then 403 for every key:
  - `PATCH /v1/notification-settings/owners/{id}`;
  - `POST /v1/registrycredentials` (`internal/registrycreds/service.go` `Create`, `RelCanManage`);
  - a protected environment.

  `POST /v1/webhooks` is also refused by `AuthorizeMintClass`, because a key is not a human caller (`internal/webhooks/service.go` `Create`, w4/079). With the key granted Admin in dev-9's OpenFGA, registry credentials applied, re-planned clean and destroyed, and `TestProject` passed. The webhook stayed 403.
- **Open questions:** whether a key takes its creator's role at mint time or follows it, which is Render's "up to your member role"; whether Render's fine-grained per-resource permissions are in scope; and whether w4/079's mint-class rule should admit an API key minted by a human Admin. ADR008 makes the parity-sufficient option the default; record the security reasoning in ADR024 and ADR018. Likely more than an hour: promote it.
- **Done when:** a key minted by an Admin creates a webhook and a registry credential and patches owner notification settings on REST, a Developer's key still cannot, and the provider's webhook and notification-setting tests get past their first step.

**Promoted 2026-11-18** to [w9/m481](../blocked/m481/README.md) (12 tasks) by `/loopx w9`. Render behavior re-checked the same day: "What happens to an API key if my member role changes? Your key's access adjusts to match your new member role" ([render.com/docs/api-keys](https://render.com/docs/api-keys)), so the key follows its creator's role.
