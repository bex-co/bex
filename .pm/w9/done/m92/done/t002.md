## Objective

Make the sidebar "Search sessions" box actually narrow the visible list for a
realistic query. The filtering code exists and runs client-side, but the
matcher it uses (`fuzzyMatch`, a prefix→substring→**subsequence** fallback
built for short mention-style names) is far too permissive against long,
free-text task descriptions: a short query like "typo" matches almost every
session's task text as a subsequence, so in practice the list barely changes
no matter what's typed — which reads to a user as "search does nothing."

## Context

- Live repro: typing `typo` into the sidebar search (there is exactly one
  search box in the app, in the sidebar's `AgentSessionsNavSection` — the main
  `/agents` route has no search box of its own) left the rendered session list
  visually unchanged, even though ~6 of the ~70 sessions have "typo" in their
  actual title (e.g. "find and fix typo"). Confirmed via network trace: no
  GraphQL request fires when typing (expected — filtering is client-side), but
  the *rendered result* did not narrow either.
- The filter itself:
  `dashboard/src/common/components/dashboard-layout/agent-sessions-nav-section.tsx:60-66`:
  ```
  const filtered = useMemo(
    () => sessions.filter(
      (s) => fuzzyMatch(query, sessionTitle(s)) || fuzzyMatch(query, s.repo),
    ),
    [sessions, query],
  );
  ```
  rendered at lines 117-130 (`filtered.map(...)`) — the wiring is correct.
- `fuzzyMatch`/`matchQuality`, `dashboard/src/features/agent-sessions/lib/mention.ts:77-93`
  — designed for short `@mention`-style names (prefix → substring →
  subsequence fallback). Against a multi-sentence task title, the subsequence
  fallback matches almost any short query (e.g. the letters t-y-p-o appear in
  order inside huge amounts of unrelated prose), so the filter rarely excludes
  anything.

## Steps

1. For session search specifically, use a matcher suited to prose: substring
   match (case-insensitive) against the title and repo, without the mention
   matcher's subsequence fallback. Either add a dedicated matcher or pass an
   option to `fuzzyMatch`/`matchQuality` that disables the subsequence tier for
   this call site.
2. Verify the sidebar's "no matches" empty state
   (`agentSessions.sidebarNoMatches`, line 117-120) still renders correctly
   when a substring genuinely doesn't match anything.
3. Leave `fuzzyMatch`'s existing behavior untouched for its other consumers
   (e.g. `@`-mention autocomplete) — don't change the shared matcher's default
   semantics, only how session search calls it.

## Acceptance criteria

- [ ] Typing a query that's a substring of exactly N sessions' titles (e.g.
      "typo") narrows the sidebar list to those N sessions.
- [ ] Typing a query that matches nothing shows the "no matches" empty state.
- [ ] The `@`-mention autocomplete's own tests (if any use `fuzzyMatch`'s
      subsequence tier) still pass unchanged.
- [ ] New test asserts session search filters by substring and does not
      over-match on unrelated subsequence hits.

## Out of scope

- Adding server-side/GraphQL text search (`AgentSessions` has no such
  parameter today; client-side filtering over the already-fetched list is
  sufficient at current session volumes).
