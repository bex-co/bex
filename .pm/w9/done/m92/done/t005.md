## Objective

A terminal (Failed) session that ran for 38m26s and produced 1 turn shows only
"The conversation stream is unavailable right now." on its detail page — no
transcript at all, giving the user zero visibility into what the agent did
before failing. Per the gateway's own design, a terminal session should
receive a **replay-only** ticket and serve its durable transcript from
Postgres rather than attempting a live pod connection, so this looks like a
gap between the intended replay path and what actually happens for at least
this session.

## Context

- Live repro: `https://dashboard.bex.co/agents/ags-da2i7o2rmfbs73eu90b0`
  (Failed, `bex-co/bex`, 38m26s duration, 1 turn).
- Dashboard: the fallback message is purely `useChat`'s `error` state —
  `dashboard/src/features/agent-sessions/components/session-conversation-impl.tsx:152,272-278`:
  ```
  if (error) { ... {t("agentSessions.conversationUnavailable")} }
  ```
  (locale key `dashboard/src/features/agent-sessions/locales/en.ts:571`,
  described in its own comment as "Degraded-state message when the m43 stream
  endpoint errors or is unconfigured"). This is a transport-level error, not
  the app's separate "genuinely empty" 204 case
  (`session-conversation-impl.tsx:170-173`).
- Transport: `dashboard/src/features/agent-sessions/lib/transport.ts` —
  `createAgentSessionTransport` builds a `DefaultChatTransport` against
  `${config.apiBaseUrl}/v1/agent-sessions/{id}/stream`; `resumeStream()` fires
  on mount (lines 179-193).
- That route is served by the **ssh-gateway**, not bex-api:
  `lego/backend/cmd/ssh-gateway/main.go:365-369` registers it, handled by
  `lego/backend/internal/sshgateway/agentattach/agentattach.go`. Per its own
  doc comment (lines 24-27) and `AttachTicket`
  (`lego/backend/internal/agentsessions/service.go:1439-1451`), a terminal
  session with no live sandbox (`SandboxID == ""`) should still mint a
  **replay-only** ticket gated on `finishedPhase(record.Phase)`
  (`service.go:709,1446`) and the gateway should serve the durable transcript
  from Postgres. The generic "unavailable" fallback fires only on an actual
  transport failure: ticket mint rejected (e.g.
  `AGENT_SESSION_NOT_ATTACHABLE` for a phase the gate doesn't recognize as
  attachable), a non-2xx/network error from the gateway, or
  `s.Enabled()` false (`agentattach.go:329-331`, 503 when
  `BEX_AGENT_ATTACH_ADDR`/the ticket secret is unset).

## Steps

1. Reproduce against a real Failed session (the one above, or a fresh one) and
   determine exactly which of the three failure modes above is firing —
   inspect the `/stream` request/response for this session id directly
   (status code, body) rather than only the dashboard's swallowed `useChat`
   error.
2. If the transcript genuinely was never persisted for Failed sessions (a
   backend gap), fix the persistence path so a Failed session's turns are
   durably stored the same way a Completed session's are.
3. If the transcript *was* persisted but `finishedPhase`/the attach-ticket gate
   doesn't recognize `Failed` as a replayable phase, fix the phase check.
4. If it's a configuration/availability issue specific to this environment
   (`BEX_AGENT_ATTACH_ADDR` unset, etc.), that's out of scope for a code fix —
   downgrade this task's finding to a config/ops note instead, but only after
   confirming code-path is otherwise correct.
5. Whatever the root cause, make sure the dashboard's fallback message
   distinguishes "no transcript exists" (rare, acceptable dead end) from "the
   gateway is misconfigured/erroring" (an operational problem that shouldn't
   look like a routine empty state) if the two are distinguishable from the
   response.
