## Objective

Stop the dashboard from rendering a `#0` PR badge (with the PR icon) for agent
sessions that never opened a pull request. Root cause is a truthy/null
confusion on both the backend (which returns the Go zero value `0` instead of
`null` for a nonexistent PR number) and the dashboard (which checks
`prNumber == null`, which does not catch `0`).

## Context

- Live repro: `https://dashboard.bex.co/agents/ags-da2i7o2rmfbs73eu90b0` (Failed
  session, no PR) shows a `#0` badge in the detail header, yet its "···" menu
  correctly omits "Open pull request" — proving the badge is fake.
- Dashboard render sites, all using `== null` / `!= null`, which is `false` for
  a numeric `0`:
  - `dashboard/src/features/agent-sessions/components/session-list.tsx:78` —
    `PrBadge`: `if (session.prNumber == null) { ... }`
  - `dashboard/src/features/agent-sessions/components/session-detail-header.tsx:470-480`
    — `HeaderPrBadge`: `if (session.prNumber == null) return null;`
  - `dashboard/src/common/components/dashboard-layout/agent-sessions-nav-section.tsx:168,187`
    — `hasPrLink = session.prNumber != null && Boolean(session.prUrl)` and a
    second inline `session.prNumber != null` check.
  - Mapping: `dashboard/src/features/agent-sessions/lib/mapper.ts:62-63` —
    `prNumber: wire.prNumber ?? null` (`??` doesn't substitute for `0`).
- Backend source of the `0`:
  - `lego/backend/internal/agentsessions/models.go:167` — `PRNumber int` (plain,
    non-pointer; `json:"prNumber,omitempty"` only affects REST JSON encoding,
    not the GraphQL resolver).
  - `lego/backend/internal/agentsessions/graphql.go:91` — resolves via
    `gqlutil.IntField(func(v View) any { return v.PRNumber })`: the GraphQL
    field is typed nullable `Int` but the resolver always returns the raw Go
    `int`, never substitutes `nil` for the zero value.
  - `lego/backend/internal/agentsessions/service.go:1564` copies
    `record.PRNumber` straight from the DB row
    (`lego/backend/internal/agentsessions/store/agentsessions.go:85`, also a
    plain `int`).

## Steps

1. Backend: make the GraphQL resolver (and REST encoding, which already has
   `omitempty` but should be verified) emit `null`/absent for `prNumber` when
   there is no real PR, instead of `0`. The cleanest fix is at the resolver in
   `graphql.go:91` — return `nil` when `v.PRNumber == 0` (a PR number of `0`
   never occurs on GitHub, so `0` unambiguously means "no PR"). Do not change
   the DB/store types; this is a serialization-boundary fix.
2. Dashboard: harden the three render sites (`session-list.tsx:78`,
   `session-detail-header.tsx:470-480`, `agent-sessions-nav-section.tsx:168,187`)
   to also treat a falsy/zero `prNumber` as "no PR" — e.g. gate on
   `Boolean(session.prUrl)` (the more reliable signal) rather than
   `prNumber == null` alone, so the UI is defensive even if the backend ever
   regresses.
3. Confirm `mapper.ts:62-63` doesn't need to special-case `0` once the backend
   sends `null` — `?? null` becomes correct once the wire value is `null`.

## Files

- `lego/backend/internal/agentsessions/graphql.go`

## Acceptance criteria

- [ ] A session with no PR (`ags-da2i7o2rmfbs73eu90b0` or an equivalent fixture)
      shows no PR badge in the sidebar, the main list, and the detail header.
- [ ] A session with a real PR (e.g. `#59`) is unaffected — badge still renders
      and still links to GitHub.
- [ ] Backend unit test asserts the GraphQL `prNumber` field resolves to `null`
      (not `0`) for a session with no PR, and REST JSON omits the field.
- [ ] Dashboard unit test asserts none of the three badge components render a
      `#0` badge when `prNumber` is `0`/`null` and `prUrl` is empty.

## Out of scope

- Any change to how a real PR number is computed or stored.
