## Objective

The same session can show two different lifecycle statuses depending on which
part of the UI is looking at it. Repro: `ags-da38m165qpic73e6v48g` (#10,
"Create VERIFY-mobile-loop.txt…") shows "Working…" in both the sidebar and the
main `/agents` list — implying it's actively running — while its own detail
page shows the badge "Hibernated" and the banner "This session is idle —
sending redispatches a new turn on the same branch." Since this app's own
model treats "hibernated" and "actively working" as distinct phases
(`isHibernated` vs. the active/working state), the list is showing a stale or
mis-derived status for at least this session.

## Context

- Status/phase model: `dashboard/src/features/agent-sessions/lib/mapper.ts`:
  - `isTerminalPhase(phase)` (line 31) and the idle-resume phase list (lines
    23-27, includes `"hibernated"`).
  - `isHibernated: phase === "hibernated"` (line 76).
  - `isFinished: isTerminalPhase(phase) || phase === "hibernated"` (line 78).
  - `isTerminal: isTerminalPhase(phase)` (line 79) — note hibernated is
    **not** terminal by this definition.
  - `agentSessionStatusPhraseKey` (line 167) — the function both the sidebar
    row and (likely) the list row call to render the human status phrase.
- List/sidebar rendering:
  `dashboard/src/common/components/dashboard-layout/agent-sessions-nav-section.tsx`
  `SessionRow` renders `t(agentSessionStatusPhraseKey(session))` (line ~185)
  using the `session` object from `useAgentSessions()`'s Apollo query result.
- Polling: `dashboard/src/features/agent-sessions/hooks/use-agent-sessions.ts:76-92,143-152`
  — `pollInterval` alternates between `AGENT_SESSION_ACTIVE_POLL_MS` (5s) and
  `AGENT_SESSION_IDLE_POLL_MS` (30s) based on
  `anyActive = sessions.some((s) => !s.isTerminal)`. Since `isHibernated`
  sessions are **not** `isTerminal`, `anyActive` should stay true and the list
  should still be polling at the 5s cadence — so a naive "polling stopped"
  explanation doesn't fully account for the staleness; the detail page may be
  reading a fresher value via a different query/fetch-policy than the
  sidebar's Apollo-cached list, or there's a cache-normalization gap between
  the two queries for the same session id.

## Steps

1. Reproduce live: open the sidebar/list showing "Working…" for a session,
   then open its detail page and observe whether it flips to "Hibernated"
   immediately, after a poll tick, or not at all without a manual refresh.
2. Determine whether the detail page fetches the session via a separate query
   than `useAgentSessions()` (check the detail route's data loading) and, if
   so, whether Apollo's cache normalization (same `id` field) should already
   be keeping both queries' views of that session in sync — if normalization
   *should* work but doesn't, look for a `fetchPolicy` or field-policy gap.
3. Fix root cause so the sidebar/list phrase for a given session id never
   lags behind what the detail page shows for the same id by more than one
   poll interval, and ideally updates immediately when the detail page's own
   fetch resolves a newer phase (cache-driven, not poll-only).
