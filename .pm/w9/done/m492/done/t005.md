## Prepared — 2026-11-18

Everything but this check is in place: the bucket, its expiry and the `bex-build/bex-build-cache-s3` credential are live and verified on production (t001), and the production overlay enables the backend for every workspace (t004). Until the pin carries the backend the manager reads `BEX_BUILD_CACHE=s3` as off, which is safe.

- **Pin:** the latest `chore(deploy): pin platform images to <sha>` commit on `origin/main`; the check starts once `git merge-base --is-ancestor <this milestone's commit> <sha>` holds and the manager's log says `S3 build cache enabled`.
- **Per build:** each cache phase's outcome is its container's termination message, e.g. `kubectl -n bex-build get pod <build pod> -o jsonpath='{range .status.initContainerStatuses[*]}{.name}={.state.terminated.message}{"\n"}{end}'` (and `.status.containerStatuses` for `cache-save`): a cold build reads `cache-restore=miss` and `cache-save=saved <bytes>`, a warm one `cache-restore=hit <bytes>`, a clear-cache release `cache-purge=purged`. The fleet view is `bex_build_cache_phase_seconds_count` by `phase`/`outcome`.
- **Store:** list a fixture's prefix with the cache credential (`aws s3 ls s3://bex-build-cache/<tea-id>/<app-uid>/ --recursive --endpoint-url https://s3.eu-central-2.wasabisys.com`); after deleting the fixture the prefix must be empty, and its `cache-purge-<app>-<hash>` Job gone from `bex-build`.
- **Zot:** no `<repo>_cache` repository may appear for the fixtures (`/v2/_catalog` with the builder credential, or the Zot PVC usage before and after).
- **Credential isolation:** the build pod's `buildkit` container has no `envFrom` and mounts no Secret but its own pull credential.

- **Speed-up.** The Dockerfile build's BuildKit time halved (77 s → 39 s), and clone to pushed image fell from 123 s to 78 s. The native build's BuildKit time fell by 27 % (170 s → 124 s), and its build pod's time by 33 % (283 s → 189 s).
- **What a warm build spends.** Its steps take about 2 s. Most of the rest is BuildKit re-exporting the imported cache: `exporting cache to client directory` took 33.7 s warm against 9.7 s cold, because imported layers must be fetched before they are written. The native layout is 1 GB because `mode=max` keeps the toolchain image's layers. This is a cost of a warm build, not a failure, and no follow-up is filed for it.
- **Self-healing.** After docker 5 the layout named 14 blobs and the prefix held exactly those 14, so the save healed the deleted blob.
- **Credential isolation.** In the Dockerfile, native and Build Source pods, the `buildkit` container has no `envFrom` and mounts only emptyDirs. `bex-build-cache-s3` reaches only `cache-restore` and `cache-save`, and the per-App registry credential only `push`.
- **Zot.** `/v2/_catalog` read 42 repositories with no `_cache` one before the walk, and 50 with no `_cache` one after it. The new repositories were the three fixtures' image repositories and other runs' fixtures. The fixtures' repositories held only `gen-N`/`live-N` tags, no cache tag. The three `-cache`-suffixed repositories in workspace `bex` are service names and predate the walk. The Zot PVC went from 41,916,268,544 to 42,252,034,048 bytes, all of it image pushes across the cluster in that window.
- **Fleet view.** `bex_build_cache_phase_seconds_count{kind="layer"}` read `miss` 7, `hit` 5, `purged` 2, `incomplete` 1 and `saved` 15, with no `error`.
- **Cleanup.** The two services and the Build Source were deleted at 09:52:26Z (`204`), and each `GET` now answers `404`. Their Apps were gone within 20 s, and the finalizer's three `cache-purge-…` Jobs completed and were removed from `bex-build`. All three `bex-build-cache/tea-daif693dqjvc73e7as3g/<uid>/` prefixes hold 0 objects. Zot answers `NAME_UNKNOWN` for the fixtures' image repositories, and the tenant namespace and `bex-build` keep nothing of them. The QA session was logged out, and its cookie now gets `401`.
