## Production check (2026-11-22, `/loopx w9`): PASS

- **Images.** Pin `1a5a8e872398` sets `bex-operator@sha256:65ef4f0d…` for the controller and kv-sni-proxy. `bex-controller-manager`, both `bex-api` pods and the three `bex-kv-sni-proxy` pods run that digest, from pods started 2026-11-23T04:29–04:30Z, after the pin commit. `bex-pg-sni-proxy` keeps its held `sha256:ca059b40…`, as the pin sets (its code did not change).
- **Fixtures.** The QA user signed in with `bash scripts/qa-login.sh` and created, in `bex-canary`, the free Postgres `qa-20261122-w9142-pg` (`dpg-dc1s4g8oodks73aucv80`, disposable) and the free Key Value `qa-20261122-w9142-kv` (`red-dc1s4hvqbg1c739j15kg`, disposable), each with `ipAllowList: []`. Both answered `public: false`. The free Postgres slot was empty, and the workspace's existing Starter store was not touched.
- **Strings while private.** The CRs read `status.reservedExternalHost` `<id>.db.bex.co` and `<id>.kv.bex.co`, with `status.externalHost` empty, no Certificate and no external Service port.
  - Postgres: REST `connection-info` and GraphQL `databaseConnectionInfo` answer the same `postgresql://<user>:<password>@<id>.db.bex.co:5432/<db>` (no `sslmode`) and `PGPASSWORD=… psql -h <id>.db.bex.co -p 5432 -U <user> <db>`, with no `externalCertificate`. The pooled strings are empty.
  - Key Value: REST `/v1/key-value` and `/v1/redis` `connection-info` and GraphQL `keyValueConnectionInfo` answer the same `rediss://<id>:<password>@<id>.kv.bex.co:6379` and ` REDISCLI_AUTH=… valkey-cli --user <id> -h <id>.kv.bex.co --sni <id>.kv.bex.co -p 6379 --tls`, with no `externalCertificate`.
  - MCP has no credential read, as on Render: `get_postgres`, `get_key_value` and `get_postgres_ip_allow_list` answer each store with `public: false` and an empty allow list, and carry no password or connection string.
  - Dashboard (headless Chromium at 1,280 px, after **Reveal connection info**): the Key Value's External Key Value URL and Valkey CLI command each read "Not public. Add an inbound IP rule under Networking to enable external access.", and its Networking panel says external connections are disabled. The Postgres Connections panel shows the masked external string and psql command over `<id>.db.bex.co`, and its Access control panel reads "External connections are disabled. Save one or more IP rules to enable access."
- **Refused while private.** Both reserved hosts resolve to the shared edge, which accepts TCP on 5432 and 6379. `psql` with the external string and with the psql command as written failed in about 1 s: the edge closed the TLS handshake (`SSL error: unexpected eof`), then closed the plaintext retry. `redis-cli` 8.10.1 (for `valkey-cli`) with the CLI command as written and with the URL's parts failed with `SSL_connect failed: unexpected eof`. Nothing authenticated.
- **Connects after one rule.** One allow-list rule for this host's own public IPv4 address (a `/32`) was added to each store with `PATCH`. Both read `public: true`, and each external certificate read `publiclyTrusted` within 40 s (Postgres) and 80 s (Key Value). The re-read external strings and commands were identical to the private ones. The strings saved while private then connected: `psql` answered `select 1`-style queries as the database user over both forms, and `redis-cli --tls` answered `PONG` over both forms.
- **Cleanup.** Both `DELETE` calls answered 204, and `GET /v1/postgres/<id>`, `GET /v1/key-value/<id>` and `GET /v1/redis/<id>` answered 404 within 3 s. No Pod, Service, PVC, Certificate or CR of either fixture was left in the namespace. The API key minted for MCP was revoked, the QA session was logged out (`--logout` ok, then 401) and its files deleted, and the admin kubeconfig and the run's scratch files were deleted. No password or connection string was printed or kept.
- **Closed:** every step of the check holds on production, so w9/134 and w9/140 hold live: a private store answers Render's external strings and admits nothing until a rule makes it public, on the same strings.
