# An Admin's API key cannot change a member's role, where Render's key can ("Update member roles and remove members")

Why: Render's public API serves `PATCH /v1/owners/{ownerId}/members/{userId}` to an API key with that permission; bex refuses every API key there because role changes are mint-class (round 24, H-1), so Terraform or a script cannot manage a team.

- **Render**: the pinned OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`) has `PATCH` and `DELETE /owners/{ownerId}/members/{userId}`; the API keys page lists "Update member roles and remove members" among a key's permissions.
- **bex**: `workspaces.Service.UpdateMember` → `members.Service.ChangeRole` calls `AuthorizeMintClass` first, which refuses every machine caller (w9/m481 I4 kept it). `RemoveMember` has no mint-class gate; check what a key gets there.
- **Security:** a key changing roles is the self-promotion path round 24 closed for delegated tokens. A key is capped by its creator (w9/m481), so an Admin's key re-roling others is an Admin re-roling others; the creator's own row must still be out of reach (`guardSelf` on the key's creator, not only on the key), and a key must never promote anyone above its creator.
- **Done when:** an Admin's key changes a member's role and removes a member on REST, GraphQL and MCP; a Developer's key is 403; a key cannot change its creator's role or its own binding; a security note in the lineage records the decision.
- Filed by w9/m481 t009.

## Record (2026-11-19, `/loopx w9` worker)

**Shipped in `78b610386`.** `members.ChangeRole` takes `AuthorizeExportClass` instead of `AuthorizeMintClass`: a session, a platform client or a bex API key with a recorded creator; a delegated third-party OAuth token is still refused (H-1 holds for it). Both member verbs hold a key to its creator (`keyCreatorRole`, `guardKeyCreatorRole`): the creator as target is 409 `CANNOT_CHANGE_OWN_ROLE` / `CANNOT_REMOVE_SELF`; a new role, or a member, above the creator's current role (read from their row) is 403 `ROLE_ABOVE_KEY_CREATOR` (`members.RoleWithin`, pinned to `model.fga`); a key with no person behind it, or whose creator's own role change is still queued, is 403. Found and fixed on the way: `Remove` has no class gate and `guardSelf` compared only the key's subject, so an Admin's key could remove its own creator. Inviting stays human-only (Render's public API has no invite endpoint). Recorded in [ADR024 § An API key manages members as its creator](../../../docs/ADR024-members.md#an-api-key-manages-members-as-its-creator-w9116) (I11, I12), ADR012 § 7, ADR018's API keys and members rows, ADR107 H-1 (amended) and the security review [ADR120](../../../docs/ADR120-security-review-key-member-management.md).
