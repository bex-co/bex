## Objective

Close meaningful coverage gaps so future changes cannot silently collapse Postgres id and name again or turn the compatibility migration into a destructive rollout.

## Context

- Existing tests overwhelmingly seed `metadata.name` and expect `ID == Name`; they need explicit legacy and new-contract cases rather than a mechanical expectation rewrite.
- The most important invariant is negative: rename/backfill must not create/delete/re-key Kubernetes/CNPG state.
- Tests must assert real behavior and failure modes; trivial snapshots or mocks that bypass the Kubernetes client do not prove this contract.

## Steps

1. Add backend unit/integration cases for opaque-id create/recover, legacy fallback, name-only/mixed/dry-run rename, uniqueness, invalid input, cross-tenant authz, and stable references.
2. Add operator/envtest coverage proving a display-name-only spec patch leaves child resource names/owner refs/backup keys untouched.
3. Add GraphQL/MCP/dashboard tests for stable URLs, refreshed labels, and failure behavior.
4. Add shell-level dry-run/idempotence/no-secret-output checks and strengthen the official-CLI verifier to assert id and Kubernetes uid stability.
5. Run `make test`, backend `go test ./...`, dashboard `yarn typecheck && yarn lint && yarn test`, and relevant script validation.

## Acceptance criteria

- [x] Tests fail if a new Postgres lacks a `dpg-…` id or if a rename changes id/uid/data-plane object identity.
- [x] Legacy CRs without `spec.name` and backfilled CRs are both covered.
- [x] Duplicate/invalid/cross-workspace/dry-run/mixed-patch failure modes are asserted through real adapter paths.
- [x] UI tests prove the route id stays fixed while the displayed name changes.
- [x] All required suites and the official-CLI verification pass without gaming coverage.

## Out of scope

- Raising repository-wide numeric coverage with unrelated or tautological tests.
