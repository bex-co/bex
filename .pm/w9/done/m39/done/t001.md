## Objective

Convert the one genuine escapee from m38's error-dialect sweep: the SSE-connection-limit 429 in the logs feature still emits the retired bare `{"error":"too many active log subscriptions"}` body — no `message`, no `id` — so a Render client (the official CLI keys on `message`) that hits `BEX_MAX_SSE_CONNS` gets an unreadable error.

## Context

- `lego/backend/internal/logs/rest.go:134` — `core.WriteJSON(w, http.StatusTooManyRequests, map[string]string{"error": …})`; 13 lines below, the same function's "streaming unsupported" 500 was already converted to `core.WriteErrStatus` by commit `aeddef79`.
- The round-16 mine swept the rest of the backend: every other non-2xx `WriteJSON` site (`deployhook.go:285`, `api/ratelimit.go:156`, `github/rest.go:178`) already carries `message`+`id`; `store/api.go` is the annotated deliberate :8091 survivor. This is the only escapee.
- The m38 regression test `lego/backend/internal/api/error_dialect_test.go` covers 401 + GraphQL 400 + deploy-hook 405 — not this 429.

## Steps

1. Replace the `WriteJSON` call with `core.WriteErrStatus(w, http.StatusTooManyRequests, "too many active log subscriptions")`.
2. Extend the error-dialect regression test to hit `/v1/logs/subscribe` with `MaxSSEConns` exhausted and assert the body carries `error` + `message` + `id` in Render's shape.
3. `cd lego/backend && go build ./... && go test ./...`.
