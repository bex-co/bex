## Objective

Accept the `serviceDetails.envSpecificDetails.registryCredential` object Render's Terraform provider sends on every Docker or image cron job create: a non-empty `id` binds that registry credential, an empty one binds none, and the object's read-only fields are ignored.

## Context

- Provider: `internal/provider/cronjob/resource/internal/create.go:63` (Docker) and `:73` (image) reuse the response type `client.DockerDetails`, so the request carries `"registryCredential":{"id":"","name":"","registry":"","updatedAt":"0001-01-01T00:00:00Z","username":""}` when none is set. Other service types send `registryCredentialId`.
- Render: `internal/provider/cronjob/resource/testdata/docker_cassette.yaml` records that create answered `201`.
- bex: every Render operation decodes strictly (`api/render_openapi.go:795` → `core/http.go:71` `DisallowUnknownFields`), and `envSpecificDetailsReq` (`apps/rest.go:350`) has no `registryCredential`, so the create answers `400 … unknown field`.
- Decision state: this accepts only this one field Render's own client sends. Relaxing strict decoding for every unknown field was deliberately **not** proposed (ADR006:64 and ADR049's closed-world compiler are an intentional design; one recording is not enough to overturn it).

## Steps

1. Add `registryCredential` (`{id, …}`) to `envSpecificDetailsReq`; map a non-empty `id` to the same path `registryCredentialId` takes; ignore `name`, `registry`, `username`, `updatedAt`.
2. Refuse a body carrying both a non-empty `registryCredential.id` and a different `registryCredentialId` by name.
3. Test Docker and image cron creates with the provider's exact body.

## Acceptance criteria

- [x] The provider's recorded Docker cron create body answers `201` on bex.
- [x] A non-empty `registryCredential.id` binds that credential, visible on the service read.

## Out of scope

## Result (2026-11-18)

- `envSpecificDetailsReq` declares `registryCredential` (`registryCredentialObject`, `lego/backend/internal/apps/rest.go`). A non-empty `id` becomes the nested `registryCredentialId` and binds through the same path. An empty `id` binds none, and `name`, `registry`, `username` and `updatedAt` are decoded and ignored. A different `registryCredentialId` beside it is refused as `serviceDetails.envSpecificDetails.registryCredential.id conflicts with registryCredentialId`. A different `image.registryCredentialId` is refused by the existing `conflicting values` check. An undeclared key inside the object is still refused by strict decoding.
- Only POST changes: the provider's PATCH uses `registryCredentialId` (`EnvSpecificDetailsForPATCH`).
- Tests: `TestRESTCreateAcceptsTerraformRegistryCredentialObject` covers the provider's recorded Docker cron body verbatim (`docker_cassette.yaml`, 201, nothing bound), the same body naming `rgc-one` (bound, pull secret materialized, read back on the response), and the image cron body. `TestRESTCreateRefusesConflictingTerraformRegistryCredential` covers the refusals. `TestCreateWireFieldsReachTheRequest` has rules for the five new leaves (id → `RegistryCredentialID`, the rest inert). All fail with the fix reverted.
