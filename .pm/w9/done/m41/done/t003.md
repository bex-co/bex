## Objective

Confirm the audited metadata fields (`owner`/`region`/`dashboardUrl`/`updatedAt`) are Render-consistent across every surface they expose, and flag any drift as follow-up rather than diverging silently.

## Context

- Render compatibility contract: `docs/ADR006-bex-api.md` (one core, thin adapters), `docs/ADR018-render-parity.md` (the parity ledger's datastore/service rows).
- The wire shaping is REST-boundary-only (`render*` layers); GraphQL/MCP read the neutral `View` directly and carry `ownerId` (bex's flat extension) instead of nested `owner`. Verify this is a deliberate, documented split, not accidental drift.

## Steps

1. Compare the emitted `owner` shape against Render's `components.schemas.owner` (`{id,name,email,type}`) and `region`/`dashboardUrl`/`updatedAt` against Render's Postgres/KeyValue/Service detail schemas.
2. Confirm GraphQL + MCP consistency: either they expose the same fields, or the divergence (flat `ownerId`, no `owner`) is intentional and recorded — do not silently diverge.
3. Update `docs/ADR018-render-parity.md` if the audit changed any cell; note `w6/016`'s resolution in the backlog table if not already reflected.

## Files

- `docs/ADR018-render-parity.md` (if a cell changed)
- `docs/ADR006-bex-api.md` (if a verified-parity note is worth adding)

## Acceptance criteria

- [x] `owner`/`region`/`dashboardUrl`/`updatedAt` match Render's schemas on the REST surface; any GraphQL/MCP divergence is documented as intentional.
- [x] Parity ledger reflects the resolved `w6/016` state and any audit outcome.

## Out of scope

- Building GraphQL/MCP nested-`owner` support if it's a deliberate REST-only shape (record as follow-up, don't build here).

## Result

REST owner shape matches Render's `{id,name,email,type}`; region/dashboardUrl/updatedAt omission rules match ADR006's metadata contract. GraphQL/MCP intentionally keep flat `ownerId` — confirmed as the only expected divergence, except GraphQL additionally drops `updatedAt` entirely and Postgres/KeyValue GraphQL/MCP carry no `region`/`dashboardUrl` at all (their neutral Views never carried those fields; only `AppView` bakes them in). Recorded as a follow-up in `docs/ADR018-render-parity.md`, not built (out of scope). ADR018's stale "Postgres unverified" note corrected to reflect the clean t002 audit.
