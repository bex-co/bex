# Docker builds and the native layer cache print none of Render's build-cache restore lines

Why: Render's build log says when it restores a build cache, for Docker builds too, and a bex build that restores one says nothing, so a user cannot tell a warm build from a cold one, or see what the restore cost.

- **Found by:** w9/m493 t005, 2026-11-18. Render prints `==> Downloading cache...` and then `==> Transferred <size> in <N>s. Extraction took <N>s.` after the clone, on native and Docker builds alike (Render build logs quoted on community.render.com, e.g. a Docker build's `Transferred 149MB in 9s. Extraction took 0s.`).
- **On bex since w9/m493:** a native build prints the pair for its `$XDG_CACHE_HOME` archive only (`xdgCacheRestore`, `xdgBuildctl` in `lego/operator/internal/build/xdgcache.go`). Its BuildKit layer cache, which `cache-restore` fetches beside it (`s3CacheRestoreLayer`, `s3cache.go`), is not counted. A Dockerfile build prints nothing for its layer cache at all. Its log is BuildKit's own transcript, where only `CACHED` steps show the hit.
- **Done when:** a Dockerfile build that restores a layer cache prints `==> Downloading cache...` and a `==> Transferred … in …s. Extraction took …s.` line before its first step, and a native build's `Transferred` size covers the layout and the archive together. A first build prints neither line, as on Render, and a test pins both lines' shape for both builders.

**DONE 2026-11-20** by `/loopx w9`. `cache-restore` now lists the layout's `index.json` (and on a native build the archive) before it fetches anything and says `==> Downloading cache...` once when the store holds either. A Dockerfile build's restore prints `==> Transferred <size> in <N>s. Extraction took 0s.` itself, before BuildKit's first step (`s3CacheRestored`, `lego/operator/internal/build/s3cache.go`). A native build's restore leaves `<layout bytes> <archive bytes> <seconds>` in `/xdg-in/transfer` and the wrapper prints their sum with the seed's seconds as the extraction (`xdgCacheRestored`, `xdgBuildctl` in `xdgcache.go`). A first build prints neither line, and a restore with nothing usable prints `bex: no usable build cache; building clean` once. `TestS3CacheRestoreSaysRendersRestoreLinesOnADockerfileBuild` and `TestXDGCacheRestoreLinesCoverTheLayoutAndTheArchiveTogether` pin both lines' shape for both builders; five guards were each reverted and caught. Drilled with the pinned aws-cli image against SeaweedFS and the wrapper on BuildKit's busybox ([ADR060 D3 S3 amendment](../../../docs/ADR060-build-worker-reliability-and-performance.md#d3-amendment-w9m492--the-s3-backend-off-zot)). Not yet observed on a production build log; it shows on the first warm build after the pin carries this commit.
