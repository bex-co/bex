## Objective

Reject an invalid crontab expression on the cron job **update** path in bex-api before any `App` CR is written, using the Render-compatible error shape. The create path already validates; the update/settings path does not, so `99 99 * * *` is accepted, persisted, and pushed to the operator, flipping the App to `Failed`.

## Context

- Reproduced live 2026-08-20: cron Settings → Edit schedule → `99 99 * * *` → Save → toast "Cron job settings saved" → App status `Running → Failed`.
- Create-form validation already exists (client blocks Deploy + inline "Enter a valid 5-field cron expression"); find where the create path validates server-side and apply the same check to update.
- Cron schedule lives on `App.spec.schedule` (`docs/ADR038-cron-jobs.md`); the update handler is in `lego/backend/` service layer (the `Core` update path feeding REST/GraphQL/MCP). Reuse whatever cron parser the create path uses — do not hand-roll a second validator.
- Error shape: `core.WriteErr` / `core.IsPublicError` with a `message`, matching Render's `Invalid cron spec` (see w9/m38 "one error dialect").

## Steps

1. Locate the cron create-path schedule validation and the update-path handler in `lego/backend/`.
2. Add the same validation to update/patch, fail-closed with a Render-shaped 4xx before mutating the App CR.
3. Confirm the three surfaces (REST/GraphQL/MCP) all route through the validated path.
4. (Defense in depth) note whether CRD OpenAPI/admission validation on `spec.schedule` is worth a follow-up; do not block this task on it.

## Files

- `lego/backend/internal/...` (cron create + update service layer)
- `lego/backend/internal/api/...` (REST/GraphQL/MCP cron handlers, if validation is at the edge)

## Acceptance criteria

- [ ] `PATCH`/update with `99 99 * * *` or `not a cron` returns a Render-shaped error and writes no App CR.
- [ ] A valid schedule (`*/5 * * * *`) still updates successfully.
- [ ] The same rejection happens via GraphQL and MCP, not just REST.
