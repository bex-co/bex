# 074 — Sandbox nodes join without gVisor: fail closed, catch template drift, stop calling it a capacity limit

Why: on 2026-11-04 every production agent session failed to start for ~2 days because the sandbox node joined the cluster without the gVisor runtime, and customers were told `SANDBOX_CAPACITY_LIMIT` (a plan limit) instead.

- **Incident (resolved 2026-11-04).** The live `bex-capi/bex-sandbox` KubeadmConfigTemplate was an old copy that downloaded gVisor from `releases/release/latest/` (now 404). The pinned, sha512-checked template committed in `2c17bea65` (security round 18) had never been applied. Each new sandbox node's `wget -q` failed silently and the node joined without `containerd-shim-runsc-v1`.
- **Remediation, with user authorization (surge first, then delete old).** Applied the repo template; surged a replacement cx33 node (`bex-sandbox-cgqq6-p8wcg`) and verified a gVisor pod (`uname` → `4.19.0-gvisor`); deleted the broken node. User rule recorded: when replacing a node, first create the new machine, then delete the old; if no capacity is available, find another way.
- **Fix 1: fail closed.** A sandbox node must not join (or must be tainted unschedulable) when runsc or the shim is missing. Make the install a hard gate, e.g. retry the download, then a final `test -x /usr/local/bin/containerd-shim-runsc-v1` whose failure aborts kubeadm join. Check how CAPI runs preKubeadmCommands.
- **Fix 2: drift guard.** A check, script or CI, that the live CAPI templates match `infra/clusterapi/overlays/hetzner-caph/*.yaml`. Also document that infra template changes must be applied (README).
- **Fix 3: honest error.** `FailedCreatePodSandBox`, or a missing runtime, must not map to `SANDBOX_CAPACITY_LIMIT`. Surface a platform-side "sandbox runtime unavailable" error (503-class).
- **Done when:** a test or dry-run shows a node without the shim does not become schedulable; the drift check reports a drifted template; the error mapping has a test.

## Implementation notes (2026-11-04, fork; uncommitted)

- **Why the old checks never stopped anything.** CAPI renders `preKubeadmCommands` as cloud-init `runcmd` items directly before `- {{ .KubeadmCommand }} && {{ .SentinelFileCommand }}` (kubernetes-sigs/cluster-api `bootstrap/kubeadm/pkg/cloudinit/node.go:33-36`). cloud-init runs all items from one `/bin/sh` script without `-e`, so a failing item never stopped the join. The live node's log matched: commands after the failed `wget` chain still ran, and the node joined.
- **Fail closed.**
  - `sandbox-pool.yaml` retries the download 5 times (`wget -T 60`, back-off).
  - A gate item placed after the containerd runtime config `exit 1`s the script before `kubeadm join` unless both binaries are installed, match the pinned SHA-512, and containerd is configured for runsc.
  - A new `bex-sandbox-unhealthy` MachineHealthCheck (`nodeStartupTimeout: 20m`, no remediationTemplate) deletes and recreates a machine that never joins. The HCloud remediation reboots, and runcmd does not re-run after a reboot.
  - `scripts/capi-sandbox-bootstrap.test.sh` runs the real rendered items under `/bin/sh` with stubs: a good install joins; a failed download (5 attempts), a digest mismatch or a non-x86_64 node stop before the join. Mutation-checked against the old template and against a gate without `exit`.
- **Drift guard.** `scripts/capi-template-drift.sh` runs `kubectl diff` (server-side dry run, read-only) for every KubeadmConfigTemplate and HCloudMachineTemplate in the hetzner-caph overlay. Exit 1 on drift, 2 when a template can't be compared. Covered by `scripts/capi-template-drift.test.sh`; both harnesses run in `scripts/gitops-validate.sh`, and `gitops.yml` triggers on `infra/clusterapi/**`.
- **Prod run, 2026-11-04 (read-only):** 24 templates match; 3 compares failed with transient TLS handshake timeouts (`bex-tenant-xxl-k134-ccx43`, `bex-tenant-burst-k134`, `bex-tenant-burst-k134-cx33`), so re-run those. The only drift is `KubeadmConfigTemplate bex-sandbox`, exactly this uncommitted gate edit; the live template otherwise equals HEAD after today's apply.
- **Not applied to prod yet:** the gate template and the new MachineHealthCheck. Apply them per the new hetzner-caph README section after this ships.
- **Honest error.** A pod-ready timeout is `SANDBOX_CAPACITY_LIMIT` only when the workspace's live sandboxes × template limits exceed the plan's limits (`store.SandboxComputeLimits`). Otherwise it is `SANDBOX_START_FAILED` (503), recorded on the session as "sandbox did not start (platform issue)".
  - Today every plan's limits are 116 CPU / 264Gi, while live agent sandboxes are capped at 5 at admission, so the old capacity message was effectively never true.
  - A plan or list lookup failure keeps the capacity answer.
  - The dashboard upgrade callout still keys only on `SANDBOX_CAPACITY_LIMIT`.
  - ADR047's w5/m132 section is updated. The pod's real cause (stale informer etc.) stays in `w10/008`.
