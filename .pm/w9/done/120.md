# Deleting a workspace leaves its API keys live: their Hydra clients and OpenFGA tuples survive, and no list can show or revoke them

Why: a key whose workspace is gone still authenticates, appears in no key list, and its creator can never revoke it.

- **Found by** w9/119, 2026-11-18. Production's 8 `m35-*` fixture workspaces went through `deleteWorkspace`. It revoked the tuples of the 8 bootstrap rows (`kind='user'`) and none of the 16 tuples of the API keys bound there (`kind='machine'`). The keys' Hydra clients would also have survived; they were deleted by hand.
- **Cause.** `workspaces.Service.deleteWorkspace` revokes the members `ListTenantMembers` returns, and `ListMembersOfTenants` reads `kind = 'user'` only (`lego/backend/internal/store/workspaces.go:503`). No pre-cascade purger revokes the workspace's keys (`lego/backend/cmd/api/main.go:1081`). The row cascade then drops the binding, so `RevokeAPIKey` answers not-found for the key from then on.
- **On production now.** Hydra lists one bex API key (`bex.co/api-key: true`) whose client id has no `tenant_members` row. It was created 2026-08-03 and carries a creator stamp. [ADR024 § Production keys](../../docs/ADR024-members.md) records a 2026-08-03 fixture minted by an operator-provisioned client, which this is likely to be. It was left untouched.
- **Paths:**
  - `lego/backend/internal/workspaces/service.go` (`deleteWorkspace`)
  - `lego/backend/internal/tenancy` (`UnbindKey`)
  - `lego/backend/internal/apikeys` (Hydra delete)
  - `lego/backend/cmd/api/main.go` (purgers)
- **Done when:**
  - Deleting a workspace revokes every API key bound in it (every role tuple, the binding, the Hydra client) before the cascade, and a retried delete converges.
  - A real Postgres and OpenFGA test proves it: after the delete, no tuple names the key and Hydra no longer knows it.
  - Every production key with no binding is listed with its creator. Each one whose workspace is confirmed deleted is revoked.

**Done 2026-11-18.**

- **Fix.** `apikeys.WorkspacePurger` runs first among the workspace delete's pre-cascade purgers (`lego/backend/internal/api/server.go`, `preCascadePurgers`). For every key bound to the workspace, whoever minted it, it calls `tenancy.Service.RevokeWorkspaceKey`, which takes every role tuple and writes the permanent revocation marker but keeps the binding row. Then it deletes the Hydra client and leaves the row to the tenant cascade. A failure at any step fails the delete with the row still there, so the retried delete finds the key and finishes. ADR024 § Guardrails records it.
- **Tests.**
  - `TestDeletingAWorkspaceRevokesItsAPIKeysE2E` runs against real Postgres and OpenFGA. An Admin's key and a Developer's key are bound in the deleted workspace, and Hydra drops one delete. The first attempt fails, with both keys already tupleless and refused and the dropped one still bound. The retry converges: no tuple names either key (OpenFGA `/read`), Hydra no longer knows them, and no binding row is left. The Admin's key in another workspace is untouched. With the purger unwired, the test fails.
  - `TestWorkspacePurgerRevokesEveryKeyBoundThere` and `TestWorkspacePurgerConvergesOnRetry` are unit tests in `apikeys`, and `TestRevokeWorkspaceKeyKeepsTheBindingForTheRetry` is in `tenancy`.
- **Production keys.** Hydra holds 8 bex API keys. 7 are bound to live workspaces.
  - The unbound one is `055984d8-620c-480a-88fd-ab325dc30ea5` (`dev-agent`, 2026-08-03, creator `c73bb20d-40ff-42df-8597-c9a428697d12`, never used since the audit window opened). It is not the m42 fixture the note guessed; that key, `e6a91fbb…`, is bound to `tea-d9ntub3vim9c73bag5n0`, which is live.
  - `055984d8` lost its binding on 2026-09-07, when its creator removed it as a member of `tea-d98210cbbpdc73dcrkvg`. That workspace is live and `guardMachine` now refuses that removal. The key holds no tuple, so it authenticates but can do nothing. Its workspace is not deleted, so it was left for its creator to delete.
- **Production tuples.** Two keys of a workspace deleted today had kept their tuples:
  - The tuples were `workspace:tea-dbuh7ide7qgs73b347f0#developer` for `user:61f68de4-9a9a-4ef4-be9c-3fa472719227` and `user:020a0594-0577-49a2-9f41-6407349ef19d`. They were minted at 02:57:41 and 02:57:59 (`apikeys.CreateAPIKey`), and the workspace was deleted at 03:07:51.
  - The owner's account deletion at 03:08:04 deleted their Hydra clients and wrote their markers. It could not revoke the tuples, because the bindings were already gone.
  - Their workspace, bindings, Hydra clients and Kratos identities were confirmed gone, and only those two tuples were deleted (OpenFGA `/write`). `/read` then answered no tuple for either.
  - No `developer` tuple remains on a deleted workspace. The 28 tuples still on deleted workspaces are `admin` and `viewer` tuples of people and of the `m35-*`, `m39-*` and `m42-*` fixture principals, not API keys, and were left alone.
- **Follow-up.** w9/121: the first attempt of a delete already revokes every member, so a purger failure leaves a workspace its admin can no longer retry deleting.
