## Objective

Decide, verb by verb, which `can_operate` writes are service or datastore **settings** (Render: Contributor ❌ "Modify service configuration", ❌ "Manage inbound IP rules"; the role description says "Can't create, modify, or delete most resources") and which are **runtime actions** that stay with a Contributor, and write that line into the docs before any code moves.

## Context

- `deploy/gitops/authz/model.fga:86`: `define can_operate: contributor or developer or admin`.
- `lego/backend/internal/apps/settings.go` `servicePatchTable`: rows on `canOperate` are DisplayName, MaintenanceBeforeFreeDowngrade, Plan, IdleTTLSeconds, MaxShutdownDelaySeconds, CacheProfile, BuildFilter, AutoDeploy + AutoDeployChecksPass, HealthCheckPath, NotifyOnFail, NotificationsToSend, PreviewNotificationsEnabled, RenderSubdomainPolicy, IPAllowList, MaintenanceMode, Autoscaling. REST `PATCH /v1/services/{id}`, MCP `update_service` and the GraphQL setters share this table.
- Direct setters on `can_operate` in `apps/service.go`: `Scale`, `SetAutoscaling`, `DeleteAutoscaling`, `SetCronJob`'s schedule-only branch (`apps/service.go:5701`, the w1/m68 comment), the maintenance-mode setters; `apps/edge_cache.go` `SetCacheProfile`; `apps/domains.go` `addOne`, `VerifyDomain`, `DeleteDomain`.
- Datastores: `postgres/service.go` `updatePostgres`, `setPlan`, `SetVersion`; `keyvalue/service.go` `updateKeyValue`, `setPlan`.
- Runtime actions that **stay** on `can_operate`: restart, suspend and resume (service, Postgres, Key Value), cron run trigger and cancel, cache purge, Postgres restart and failover. Render's table restricts none of them and calls the Contributor "Similar to the Developer role" with listed restrictions. This is an assumption; record it as one.
- The service notification override rows move to `can_create`, not to Admin: Render's "Configure notification settings" (Admin only) is the workspace setting (its API-key catalog files it under Workspaces), and bex's own key catalog maps `PATCH /v1/notification-settings/overrides/services/{id}` to `KeyServicesManage` (`lego/backend/internal/api/key_permission_ops.go:1024`).
- The key catalog already puts service and datastore management at `can_create` (`lego/backend/internal/core/keygrant.go` services read-write, `KeyPostgresManage`, `KeyKeyValueManage`), so today a Contributor cannot grant a key what they can do themselves.
- ADR012 § Authorization holds the canonical role × relation matrix and claims to mirror Render's page as fetched 2026-07-06. ADR024 § Roles and § The contributor boundary (w1/m68) describe the Contributor; ADR024's developer row still says "every member's API keys", which w9/m539 changed.

## Steps

1. List every write gated on `can_operate` across `lego/backend/internal` (services, domains, edge cache, Postgres, Key Value, cron) and classify each as setting or runtime action, citing the Render row.
2. Save Render's role table and role descriptions as `docs/render-artifacts/team-members-roles-2026-11-23.md` (text, the date read, the URL).
3. Amend ADR012 § Authorization: the matrix and the enforcement paragraph name which verbs are settings (`can_create`) and which runtime actions stay `can_operate`.
4. Amend ADR024 § Roles (contributor row: no settings, no cron schedule; developer row: their own API keys, per w9/m539) and § The contributor boundary; amend ADR087's Contributor experience.
