# A disabled autoscaling criterion reads back percentage 0, where Render keeps the percentage that was sent

Why: Render's Terraform provider sends both criteria with their percentages (`memory: {enabled: false, percentage: 70}`) and stores the response. bex answers 0 for the disabled one, so the apply aborts with "Provider produced inconsistent result after apply: .autoscaling.criteria.memory.percentage".

- **Found by:** w9/m474, dev-9, 2026-11-18 ([checklist](../../../docs/terraform-compatibility-checklist.md), class 7). It hits the worker, private-service and web-service autoscaling tests.
- **Render:** `backgroundworker/resource/testdata/scaling_cassette.yaml`. The create carries `criteria: {cpu: {enabled: true, percentage: 60}, memory: {enabled: false, percentage: 70}}`, and the response and `PUT …/autoscaling` echo `memory.percentage: 70`.
- **bex:** `lego/backend/internal/apps/render.go` `setAutoscalingRequestFromRender` keeps a percentage only for an enabled criterion, and `renderAutoscalingConfigFromView` answers `{enabled: false, percentage: 0}` for the other.
- **Done when:** a disabled criterion's percentage is stored and read back on create, `PUT …/autoscaling` and GraphQL/MCP, scaling still ignores it, a test covers it, and `TestWebServiceResource_Autoscaling` gets past its first step.

## Resolution

**DONE 2026-11-18.** `spec.autoscaling` keeps a turned-off criterion's percentage in two new optional fields, `disabledCPUPercent` and `disabledMemoryPercent` (1–100; unset reads 0). The operator and the target metrics read only `targetCPUPercent`/`targetMemoryPercent`, so a kept percentage never scales.

- **Render's REST body** (`lego/backend/internal/apps/render.go`): a criterion with `enabled: false` names its percentage (`split`), and every read answers it back (`renderAutoscalingCriterionFrom`). That covers the create's `serviceDetails.autoscaling`, `PUT`/`GET …/autoscaling`, service reads and MCP `get_service`. `0` clears it; outside 0–100 answers 400 `criteria.<cpu|memory>.percentage must be 0–100`.
- **GraphQL and MCP** read it as `Autoscaling.disabledCPUPercent`/`disabledMemoryPercent` and in `get_autoscaling`. Their writes (`setAutoscaling`, `update_service(autoscaling:)`), like a Blueprint's `scaling` block, cannot name it, so they keep the one stored (`keptPercent`).
- **No scaling change:** `autoscalingChanged` ignores a kept percentage, so changing it alone records no `autoscaling_config_changed` and needs no Pro plan. That event still reads only the enabled targets in its criteria.
- **Not changed:** the dashboard's Scaling page still seeds an off criterion's slider with 60.

Tests, each failing with its part of the change reverted:

- `TestDisabledAutoscalingCriterionKeepsItsPercentage` (`internal/apps/terraform_provider_test.go`) sends the provider's recorded worker create and `PUT …/autoscaling` through the strict Render gate. It reads memory `{enabled: false, percentage: 70}` back on the create response, REST `GET` (service and `…/autoscaling`), the `PUT` answer, GraphQL, MCP `get_service` and `get_autoscaling`, with the stored spec's memory target unset. A GraphQL and an MCP write keep it, and a `PUT` of 0 clears it.
- `TestDisabledAutoscalingPercentageRules` covers the 0–100 refusal, an enabled criterion keeping nothing, a Blueprint `scaling` block keeping it, and `autoscalingChanged` ignoring it.

ADR018's autoscaling and Terraform rows and the [checklist](../../../docs/terraform-compatibility-checklist.md) (class 7, run F) record the change.
