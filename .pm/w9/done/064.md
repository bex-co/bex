# 064 — dev-N Hydra sent `bex login` to the PRODUCTION dashboard

Why: `scripts/dev-env/values/hydra.values.yaml` overrode `urls.login` and
`urls.consent` with the local dashboard but left `urls.device.*` unset, so
`deploy/gitops/base/values/hydra.values.yaml`'s production values won. Every
`dev-N` stack therefore redirected a local device login to
`https://dashboard.bex.co/auth/device`: the user code and the whole
authentication happened against **production**, where a local test identity does
not exist, so it failed as "the provided credentials are invalid" with nothing
indicating the flow had left the machine. The local CLI device-login path could
not be exercised on any `dev-N` stack.

## Evidence (2026-09-21, dev-9)

- `kubectl -n dev-9-auth get cm hydra -o yaml` before the fix:
  `verification: https://dashboard.bex.co/auth/device`,
  `success: https://dashboard.bex.co/auth/device/success` — while `login`/
  `consent` were correctly `http://localhost:50090/...`.
- A browser probe of the local device URL showed the navigation chain
  `302 /oauth2/device/verify → 302 /auth/device → 307 /auth/login`, with the
  resulting Kratos flow's `request_url` reading
  `https://auth.bex.co/self-service/login/browser?return_to=https://dashboard.bex.co/auth/device?...`
  — production, from a localhost-only stack.

## Fix (done)

Added the `device.verification` / `device.success` pair to the `dev-N` template,
pointing at `__DASHBOARD_PORT__`, mirroring
`deploy/gitops/overlays/local/values/hydra.values.yaml`. After
`bash scripts/dev-env.sh 9 up`, all four URLs resolve to `localhost:50090`, and
`scripts/bex-cli-auth-e2e.sh` completes the full local device flow.

Found while clearing the local-env half of `062`.
