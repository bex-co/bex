# A Viewer, Contributor or Billing member cannot mint an API key, where Render lets them mint one capped at their role

Why: Render ties a key's permissions to the creator's role rather than gating who may mint; bex refuses the mint outright below Developer (`can_manage_keys`), so a Viewer cannot get a read-only key for a dashboard script.

- **Render** ([render.com/docs/api-keys](https://render.com/docs/api-keys), read 2026-11-18): "Your member role in the selected workspace determines which permissions you can grant an API key." The page does not restrict minting by role.
- **bex**: `apikeys.Service.CreateAPIKey` requires `can_manage_keys` (Developer or Admin, `deploy/gitops/authz/model.fga`); `store.BindClientForCreator` seats only admin or developer creators. Since w9/m481 a key acts with its creator's current role and is capped by it at request time, so a Viewer's key could never exceed Viewer.
- **Open question for the work:** who lists and revokes such keys (today `can_manage_keys` gates the list too); check Render's API keys page for a Viewer before deciding.
- **Done when:** a Viewer, Contributor or Billing member mints a key on every surface; it acts with exactly their role (the e2e of w9/m481 extended to those roles); listing and revoking follow Render.
