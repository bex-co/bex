# 131 — A Developer and an Admin see every member's API keys, where Render shows each person their own

Why: Render manages API keys per person on Account Settings ("Go to your Account Settings page in the Render Dashboard and click **Create API key**"), so each person sees the keys they created. bex's API keys panel, on the same Account Settings page, shows a Developer and an Admin every key in the workspace, which no Render member sees on that page.

- **Source:** w9/m514 t007 (2026-11-19), which gave every member role their own keys and left Developer and Admin on the workspace-wide view it found, as its milestone asked ("whether that view should narrow to one's own keys, as on Render, is a parity question t007 files rather than decides"). [render.com/docs/api-keys](https://render.com/docs/api-keys), re-read 2026-11-19, describes creating, changing and revoking keys only from one's own Account Settings and names no page where an Admin sees others' keys. Render serves no key API, so its dashboard is the only reference.
- **Today:** `apikeys.Service.ListAPIKeys` (`lego/backend/internal/apikeys/service.go`) returns every key bound to the workspace to a caller holding `can_manage_keys`, and only the caller's own keys to anyone else (I10, [ADR024 § Every member mints and manages their own API keys](../../docs/ADR024-members.md#every-member-mints-and-manages-their-own-api-keys-w9m514)). `RevokeAPIKey` lets a Developer or an Admin revoke any key there; `UpdateAPIKeyPermissions` lets an Admin edit any key's grant within its creator's role.
- **Open question for the user:** narrow a Developer's and an Admin's list to their own keys, as on Render, or keep the workspace-wide view as a recorded divergence. Removing it would take away the only place an Admin sees, and revokes, a departed or demoted member's keys before the membership exit revokes them (w2/m163), and the leftover `m35-*` fixture keys of w9/119; an Admin-only "all keys" view beside the own list is a third option. Until decided, ADR018's API keys row records the divergence.
- **Do (if narrowed):** `ListAPIKeys` shows every caller their own keys by default; an Admin's workspace-wide view stays reachable (a filter or a separate panel) so offboarding has a place; REST, GraphQL, MCP and the dashboard agree. Amend ADR018's row and ADR024's section.
- **Accept:** a backend test pins each role's list; the dashboard's panel shows a Developer only their own keys; ADR018 records the decision.

**Promoted 2026-11-20** to [w9/m539](../m539/README.md) (10 tasks) by `/loopx w9`. The open question is settled by AGENTS.md's parity rules, not by the user. Render's API keys page, re-read 2026-11-20, shows each person only the keys on their own Account Settings and has no page where an Admin manages other members' keys; its only Admin view is the read-only report in the enforce-SSO confirmation, which bex already mirrors. So every role's list narrows to its own keys. Every membership exit already revokes the member's keys (w2/m163, `members.Service.endMembership`), but a demotion does not, and creator-less keys are no one's own. So an Admin keeps an opt-in `allMembers` view with revoke, which m539 t007 records in ADR018 as a divergence pending the user's sign-off.
