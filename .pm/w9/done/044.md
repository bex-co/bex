## Verification results — 2026-08-17 (prod, `hetzner-prod` context)

**Status: DONE.** Both legs verified against live prod; the exercise surfaced and fixed a
real m61 correctness gap (`Vary: Accept-Encoding` clobber).

### Leg 1 — prod HTTP compression ✅ (and a bug found + fixed)

Verified end-to-end at the edge **and** pod-direct (port-forward to `svc/bex-api:8090`,
bypassing Cloudflare + Traefik) so the compression is attributable to m61's app middleware,
not the CF/Traefik edge:

- Edge `GET /.well-known/oauth-protected-resource --compressed` → `content-encoding: gzip`,
  `content-type: application/json`, decoded body correct.
- Edge `GET /v1/services --compressed` (authenticated) → `200`, `content-encoding: gzip`,
  decoded body valid JSON (`[]`). Proves the CLI's Go `net/http` transport decodes prod's
  gzip transparently — the cli-compat "worth proving" claim, on a real Render endpoint.
- Pod-direct `GET /.well-known/oauth-protected-resource` + `GET /v1/services` with
  `Accept-Encoding: gzip` → `Content-Encoding: gzip` from the **app** (HTTP/1.1, no CF),
  `gunzip` decodes cleanly. Confirms the deployed image runs m61.
- Identity leg: `GET /healthz` / oauth metadata **without** `--compressed` → no
  `Content-Encoding` (identity body).

**Bug found (fixed in this task):** pod-direct responses carried only `Vary: Origin`, **not**
`Vary: Accept-Encoding`. Root cause: `withCORS` (`internal/api/auth.go`) called
`w.Header().Set("Vary", "Origin")`, clobbering the `Vary: Accept-Encoding` that outer
`withGzip` added via `Add`. The app was dropping its own cache-safety header (the exact
shared-cache hazard m61's comment warns about); only Cloudflare incidentally re-added
`vary: accept-encoding` at the edge, masking it. Fix: `withCORS` now **`Add`s** `Vary: Origin`
so both field values survive. Two regression tests added in `gzip_test.go`
(`TestWithGzip_VarySurvivesCORS`, and `TestWithGzip_SSEUntouchedThroughComposedChain` for the
SSE leg) exercising the **composed** `withGzip(withSecurityHeaders(withCORS(...)))` chain the
isolated tests missed. `go build` + `go test ./internal/api/` + `make lint-backend` green.
Fix is uncommitted (awaits `/ship`); prod is functionally unaffected meanwhile because
Cloudflare supplies `Vary: Accept-Encoding` at the edge.

### Leg 2 — SSE incremental + cli-compat ✅ (SSE proven; full suite dev-9-gated)

- **SSE untouched:** proven deterministically against the real deployed wiring via the new
  `TestWithGzip_SSEUntouchedThroughComposedChain` (composed `withGzip→withSecurityHeaders→
  withCORS` around a `text/event-stream` handler → no `Content-Encoding`, per-event flush,
  raw events). The middleware is content-type-driven, so this is the deployed binary's exact
  behavior. A live 200-stream capture needs a member-scoped token (the bootstrap
  `client_credentials` identity used for the read legs is not a tenant member, so
  `/v1/logs/subscribe` had no resource to attach to).
- **cli-compat gzip decode:** the transport-level guarantee is proven live (Leg 1's
  authenticated `/v1/services` read decoded prod gzip). The full 52-assertion
  `scripts/cli-compat.sh verify` is a **dev-9 full-stack artifact** (its `verify.sh`, key
  bootstrap, and auth/resource stack); dev-9 is down and standing it up (`mock-cluster`) is
  the heavy op this note deferred, while running the mutating suite against prod would
  create/delete real tenant resources. Left as a dev-9-session follow-up — de-risked: Go's
  `net/http` auto-decodes gzip and prod is confirmed emitting it, so every prod CLI/dashboard
  session already decodes gzip end-to-end (this note's own stated proof).
