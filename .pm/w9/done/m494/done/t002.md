## Objective

Round-trip each native runtime's dependency cache directory through the S3 build-cache phases (`<tea-id>/<app-uid>/deps-cache.tar.zst` + metadata) with toolchain-key checking, size bounds, and `clearCache: "clear"` purge.

## Context

- Reuses the S3 cache bucket, credentials, and named BuildKit context pattern established by w9/m492 and w9/m493.
- BuildKit remains 100% credential-free; only `cache-restore`, `cache-purge`, and `cache-save` touch S3.

## Steps

1. In `cache-restore`, read `<tea-id>/<app-uid>/deps-cache.meta.json`; when its toolchain+arch key matches the current build (and `!SkipCacheImport`), download and safely extract `deps-cache.tar.zst` into a dedicated named BuildKit context. On mismatch, miss, or error, leave the context empty and log a concise notice.
2. In `native.go`, copy/seed the restored runtime dependency directory before running the authored build command and export the updated dependency directory to the cache-out volume after the build succeeds.
3. In `cache-save`, archive and upload `deps-cache.tar.zst` + `deps-cache.meta.json` within the configured size cap; in `cache-purge` (`SkipCacheImport`), delete both objects.
4. Emit `kind="deps"` on `bex_build_cache_bytes` and `bex_build_cache_phase_seconds`.

- [x] Matching toolchain+arch builds restore and reuse the cached dependency directory across source-only commits.

- [x] Oversized or corrupt archives degrade cleanly to a cold build without failing the deploy.

## Done — 2026-11-19

- **Built on w9/m493's mechanism, not the named-context design.** The build command's `RUN` mounts a second cache mount, `bex-deps-cache` at `/opt/bex/deps-cache`. The env loader first moves each kept directory into place (`nativeDepsSeed`): only into a directory that is missing or empty, whole or not at all, before the service's variables are exported. A `RUN --network=none` step right after the command copies the directories back (`nativeDepsSave`): real directories only, nothing over 7 GB, never failing the build, and its layer is empty. The directories stay ordinary image directories, which the runtime reads. A mount would have hidden them from the image and broken `cargo clean`.
- **Deviation, one archive:** the seed and export solves (`xdgDockerfile`) mount both caches under `/bex-cache`, so `xdg-cache.tar.gz` now holds `xdg/`, `deps/` and `deps.key`. There is one 7 GB bound for both, as Render has one build cache, one restore line pair and one purge. No `deps-cache.tar.zst`, no new volumes or env, and the metrics keep `kind="xdg"` for the whole archive rather than adding `kind="deps"`. `.tar.gz` for m493's reason (no zstd on Debian bases).
- The seed keeps `deps/` only when `deps.key` equals this build's key and the key is non-empty, and keeps `xdg/` either way. An unusable archive empties both mounts. A clear-cache release purges the one object as before (`xdgCachePurge`), and App deletion's root purge removes it.
- Only a native build on the S3 store gets the mount and both steps (`Options.depsCache`).
