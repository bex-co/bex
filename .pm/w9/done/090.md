# A deploy refused by the platform's admission policy shows the customer the raw Kubernetes error

Why: when the operator's Deployment write is refused, the service's Events tab and failed deploy show the API server's text verbatim. On 2026-11-12, fixture `srv-dbqrqpg44das73c8s0cg` showed `deployments.apps "tea-…" is forbidden: ValidatingAdmissionPolicy 'bex-operator-workloads' with binding 'bex-operator-workloads' denied request: operator-authored containers outside the execution boundary …`. That exposes internal policy names and the tenant namespace, and gives no customer action. Render shows a platform-side failure as "an internal error occurred; contact support" with a request id.

- The App's `Ready=False DeployFailed` message is copied into the deploy's failure and the events feed. Map a Forbidden/Invalid response from the API server on an operator write to a fixed customer sentence plus a support reference, and keep the raw text in the operator log.
- Cover it with an operator test that a refused Deployment write yields the fixed sentence.

## Done (2026-11-12)

The operator masks API-server refusals of its own writes (Forbidden, Invalid, admission denials and failed webhook calls, but not quota) behind a fixed customer sentence with reference `g<release generation>-<8 hex>`. It logs the raw text once under that reference. This covers Ready, the Build and Rollout verdicts, pre-deploy and the served release's pod-creation refusals. There is a new `platform_error` deploy reason (en and zh), and `/bex-health` is reserved as a disk mount path.

Tests: a fake-client test, a refusal table, an envtest against a real refusing admission policy, and the backend disks and deploy-reason tests. Reverting the masking fails eight of them.
