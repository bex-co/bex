## Objective

A Developer reads the workspace's billing details (usage, estimated and real cost, invoices, credit grants, billing readiness) and a Contributor or Viewer reads none of them, on every surface.

## Context

- `lego/backend/internal/usage/service.go:288` (`MonthToDate`, `AuditVerbMonthToDate`) on `can_view` today, so a Viewer and a Contributor read usage and the estimate; `:321-327` and `:381` attach the Stripe projection only for `can_manage_billing`, so a Developer gets no invoices.
- `lego/backend/internal/billing/service.go:262` (`Status`, billing readiness) on `can_manage_billing`; `:224` and `:241` (Checkout, Portal) stay.
- `lego/backend/internal/workspaces/pipeline.go:84` `SetPipelineSpendLimit` stays `can_manage_billing`.
- Surfaces: REST `GET /v1/usage`; GraphQL `usage`, `workspaceBillingReadiness`; MCP `get_usage`, `get_billing_readiness` (`lego/backend/internal/api/key_permission_ops.go` maps them to `KeyWorkspaceSettings`).

## Steps

1. Gate `MonthToDate` on `can_view_billing`, and attach the billing projection for `can_view_billing`.
2. Gate the readiness read on `can_view_billing`.
3. Check that the API key catalog level covering these reads caps a key at its creator's `can_view_billing`.

## Acceptance criteria

- [ ] A Developer's `GET /v1/usage` carries the billing projection; a Contributor's and a Viewer's answer 403 on REST, GraphQL and MCP.
- [ ] A Developer still cannot open Checkout or the Portal or change the spend limit.

## Record (2026-11-24)

- `usage.monthToDateAt` (REST `GET /v1/usage`, GraphQL `usage`, MCP `get_usage`) authorizes `can_view_billing`, so a Contributor and a Viewer are refused the whole read (usage, estimate, included usage, agent model spend). The Stripe projection (real cost, invoices, credit grants) is attached for every caller who passed, after an uncached re-assert of the same relation (`AuthorizeFresh`), keeping round 13's rule that a just-revoked member reads no invoice on a stale positive. `mayManageBilling` is gone: the relation check already composes the OAuth capability and an API key's creator ceiling, and the three usage operations already require `workspace.settings.view` of a scoped key at dispatch.
- `billing.Status` (REST `GET /v1/workspaces/{id}/billing`, GraphQL `workspaceBillingReadiness`, MCP `get_billing_readiness`) authorizes `can_view_billing`; `billing.authorize` takes the relation, and Checkout and Portal keep `can_manage_billing` (and their fresh re-assert).
- `workspaces.PipelineSettings` (GraphQL `pipelineSettings`) reads with `can_view_billing`, as readiness does; `SetPipelineSpendLimit` stays `can_manage_billing`.
- **API keys:** the catalog's Workspaces Read level (`workspace.settings.view`, granted on `can_view`) needs no change: a key acts with its creator's role (w9/m481), so a Viewer's or Contributor's key holding that level is still refused by the relation; `TestKeyDecisionIsItsGrantAndItsCreator` now draws `can_view_billing` too.
- **OAuth:** `can_view_billing` maps to `bex.read`, so a third-party token a Developer delegated `bex.read` to reads the projection; before, the projection needed `bex.write` because it borrowed `can_manage_billing`'s capability (`TestBillingDetailsOAuthCapability`).
- Tests: `TestBillingDetailsPerRole` (five roles; a refused read returns no figure and never calls the Stripe reader), `TestBillingRevokedMidCacheWindow`, `TestBillingStatusGatesOnCanViewBilling`, `TestBillingVerbsGateOnCanManageBilling` (Checkout and Portal refuse a Developer's `can_view_billing`), and `representativeVerbRelations` pins `usage.MonthToDate`, `billing.Status`, `workspaces.PipelineSettings` on `can_view_billing` and `billing.Checkout`, `billing.Portal`, `workspaces.SetPipelineSpendLimit` on `can_manage_billing`.
