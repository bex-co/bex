# The mobile app drops the `agent_automation_paused` push

Why: w9/m343 sends an automation's creator a push when the platform pauses it, but the mobile client accepts only its closed event list, so on iOS and Android that push is silently ignored (web push in the dashboard opens it fine).

- `mobile/src/features/notifications/deep-link.ts:1-20` (`notificationEvents`) has no `agent_automation_paused`, and its `routes` allow only `/services/`, `/databases/`, `/key-values/` and `/sessions/`; a `/automations/aut-…` route fails `routes.some(...)` (`:86`).
- The mobile app has no automations screen. Route the push to the inbox entry (or open `https://dashboard.bex.co/automations/<id>` in the browser), add the event and route pattern, and cover it in `mobile/src/features/notifications/__tests__/deep-link.test.ts`.
- Coordinate with w11 (mobile client) before release.

## Done (2026-11-12)

The mobile client now accepts `agent_automation_paused` with the route `/automations/aut-…` (`mobile/src/features/notifications/deep-link.ts`). Its inbox row and tap require `can_create`, as the backend's destination policy does (`destination-access.ts`).

The app has no automations screen, so both open paths in `notifications-provider.tsx` send a tap to the dashboard page in the browser (`notificationWebURL`). The page's origin is `mobileConfig.dashboardOrigin`: `EXPO_PUBLIC_BEX_DASHBOARD_URL`, HTTPS only, defaulting to `https://dashboard.bex.co`, and listed in `.env.template`. A failed browser launch is caught. Every other route still opens in the app.

The GraphQL types were regenerated: `PushNotificationEvent` gains `AGENT_AUTOMATION_PAUSED`. `deep-link.test.ts` covers the route, the event, the dashboard URL, the `can_create` action and the rejected malformed routes; `config.test.ts` covers the origin's default, override and HTTPS rule.

Mobile unit tests (373), typecheck, lint, prettier and `expo:check` pass, after `/simplify` with three review agents. This changes the code only: phones get it with w11's next store build.
