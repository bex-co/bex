## Objective

Write down, once, where a cron job's command lives on the wire — so create, update, read, blueprints, GraphQL and MCP stop each having their own answer.

## Context

Today there are three spellings in play for one fact: top-level `command`, `serviceDetails.command`, and `serviceDetails.envSpecificDetails.{startCommand,dockerCommand}`. Observed live on 2026-09-21:

| body                                                     | result                          |
| -------------------------------------------------------- | ------------------------------- |
| `PATCH {"command": "…"}`                                  | `200`, stored                   |
| `PATCH {"serviceDetails":{"command":"…"}}`                | `400`                           |
| `PATCH {"serviceDetails":{"envSpecificDetails":{"dockerCommand":"…"}}}` | `200`, stored, invisible on read |

The pinned CLI sends the last of these on update and the native-shaped `startCommand` on create, so bex must accept both spellings regardless; the question is which one is canonical on **read**, and whether `serviceDetails.command` should be accepted rather than 400.

An open question worth answering here because it decides ownership: does Render accept a native-shaped `envSpecificDetails` on a docker cron? If it does, upstream's no-runtime-branch cron builder is fine and bex must be liberal. If it does not, this is an upstream defect worth reporting separately — and bex should still be liberal, but the ledger should say so.

## Steps

1. Check Render's public OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`) for the cron job details schema and which field carries the command.
2. Decide the canonical read spelling and the accepted write spellings.
3. Record it in `docs/ADR018-render-parity.md` (its create row already claims "Docker honors context, Dockerfile path, and command" — make that claim true or qualify it) and in `docs/cli-compatibility-checklist.md`.
4. If upstream is at fault for the create shape, note it in `lego/cli/UPSTREAM_RENDER_CLI.md` as a pin-bump re-check item.

## Decision (2026-09-21)

**A cron's command is runtime-independent on the wire.** Evidence from the
pinned client, both directions: its cron builder emits
`envSpecificDetails.startCommand` for every runtime (`pkg/service/create.go`
`buildCronEnvSpecificDetails`, no docker branch), and its clone path reads a
cron's command back through `AsNativeEnvironmentDetails().StartCommand` only
(`pkg/service/clone.go:143,328-334`, also no docker branch).

So bex is **liberal on write** — either spelling is accepted for a cron, with
`dockerCommand` winning when both are sent — and **explicit on read**: a docker
cron emits the command in `dockerCommand` (for the runtime-keyed readers: the
dashboard and blueprint generation) *and* in `startCommand` (for the client that
re-sends it). A docker web service is untouched and keeps the plain docker
shape. Recorded in `docs/ADR006-bex-api.md` (cron_job paragraph) and the
`--cron-command` row of `docs/cli-compatibility-checklist.md`.

The third half only surfaced because the fix was exercised live: after t001 and
t002 every bex-side read looked correct while `create --from` still cloned an
empty command.
