## Objective

A Docker-runtime cron created with `--cron-command` must store that command. Today it stores nothing.

## Context

- `lego/backend/internal/apps/rest.go:476-486` — inside `if r.ServiceDetails.EnvSpecificDetails != nil`, the docker branch does `startCommand = r.ServiceDetails.EnvSpecificDetails.DockerCommand`, unconditionally replacing the value just read from `StartCommand` on the line above.
- `rest.go:498-500` — the cron bridge `if command == "" && r.Type == appv1alpha1.TypeCronJob { command = startCommand }`, whose comment already states the CLI encodes the cron command in `envSpecificDetails.startCommand`.
- The pinned CLI proves the comment: `pkg/service/create.go:315-330 buildCronEnvSpecificDetails(buildCommand, cronCommand)` builds `NativeEnvironmentDetails{BuildCommand, StartCommand: cronCommand}` with **no runtime branch**, unlike `buildRuntimeEnvSpecificDetails` (same file, ~289-309) which does branch on docker.
- So for a docker cron the command lands in `StartCommand`, gets overwritten by an empty `DockerCommand`, and the bridge assigns `""`.
- Live proof (2026-09-21): the CLI-shaped body returns `201` with no `command`; the same body with `runtime: "go"` stores it.

## Steps

1. Make the docker branch preserve a `StartCommand` when `DockerCommand` is absent/empty — or, better, resolve the cron command from whichever of the two the client sent, since for a cron they mean the same thing.
2. Keep the precedence unambiguous when both are present, and write the rule down (t003 records it).
3. Do not regress the non-cron docker path: a `web_service` must keep taking its command from `DockerCommand` only.
4. Red-test first: a table case for (docker cron, startCommand-only) that fails before the change.

- [ ] At least one new test fails on the pre-fix code.

## Outcome (2026-09-21)

`rest.go`'s docker branch no longer overwrites the cron's `startCommand`
unconditionally: for a `cron_job` the docker spelling is used when present and
the native one survives when it is not, so the cron bridge three lines below
picks it up. Every non-cron docker service keeps the exact prior rule (pinned by
`TestRESTCreateDockerWebServiceIgnoresNativeStartCommand`). Live on dev-9 the
pinned CLI's `services create --type cron_job --runtime docker --cron-command`
now stores and returns the command.
