## Objective

`w9/done/m56` promised that every supported create/update flag "either round-trips exactly or fails explicitly — never as a silent no-op". Make that true for the docker cron command, and make the verifier fail if it stops being true.

## Context

- m56's README records that its verifier covers "the dev-9 audit's environment-blocked `--env-var`, `--secret-file`, `--registry-credential`, and **native** `--cron-command` paths". The docker cron command was never covered — which is exactly the case that broke.
- `w9/done/m44` t004 hit the symptom and read it as a CLI quirk: "Render CLI requires `--cron-command` even for an image-entrypoint cron … Added `--cron-command "/cron-demo"`". The run fired, so the workaround looked like it worked — a cron running its image entrypoint is indistinguishable from one running the same command explicitly. A verifier that only asserts "a run happened" cannot catch this.

## Steps

1. Add a docker-runtime cron leg to `scripts/cli-services-parity-verify.sh`: create with `--cron-command <unique marker>`, read back, assert the marker is present in the canonical field t003 chose.
2. Add the update leg: change the command, assert the **response** carries the new value (not just that the request returned 200).
3. Make the assertion distinguish "ran the command" from "ran the image entrypoint" — use a marker the image's own entrypoint cannot produce.
4. Prove the new legs fail against the pre-t001/t002 behavior.
