## Objective

Make sure the cron command reads and writes identically on REST, GraphQL, MCP and the dashboard, and that any remaining divergence from render.com is recorded rather than implicit.

## Context

- Only REST was probed live on 2026-09-21. GraphQL and MCP share `AppView` but have their own projections (`lego/backend/internal/apps/graphql.go`, `mcp.go`) and may or may not carry the same `render.go:495` bug.
- The dashboard has cron settings that read the same shape.
- ADR018's create row claims Docker honors context, Dockerfile path, and command — t003 either makes that true or qualifies it; this task verifies it across surfaces.

## Steps

1. Enumerate every surface that reads or writes a cron command.
2. Verify each reports the canonical field after t001/t002.
3. Compare against render.com's documented behavior; record drift in ADR018 rather than silently diverging.

## Files

- `lego/backend/internal/apps/{graphql,mcp}.go`, `dashboard/` cron settings
- `docs/ADR018-render-parity.md`, `docs/cli-compatibility-checklist.md`

## Acceptance criteria

- [ ] REST, GraphQL, MCP and the dashboard agree on the cron command for the same service.
- [ ] Divergence from Render is recorded with rationale.

## Out of scope

- Parity work unrelated to the cron command.

## Outcome (2026-09-21)

REST, GraphQL and MCP agree on one stored fact. GraphQL exposes the cron command
as `command` straight from `AppView.Command` (`graphql.go:379`) and MCP reads the
same view, so neither carried the defect; REST's runtime-keyed projection was
the only divergent reader and is now fixed.
`TestDockerCronCommandAgreesAcrossRESTAndGraphQL` pins the agreement. Render
parity: Render's own client is the oracle here, and the decision in t003 is
exactly what that client reads and writes.
