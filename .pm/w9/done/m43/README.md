## Definition of done

On a cluster whose zot pod has been running continuously since before the App existed, creating a brand-new App (e.g. via the official Render CLI `services create --repo …`) results in a first deploy that reaches `live` / App phase `Running` with **no manual `rollout restart statefulset/zot` and no pod deletion** — verified live on production (2026-07-17's failure scenario re-run hands-free) and covered by an operator regression test. The false hot-reload claim in `lego/operator/internal/registry/creds.go` (~line 31) is corrected to describe the real mechanism.

## Decision record (t001, 2026-07-17)

- **Root cause (empirical, docker lab against the exact prod image `ghcr.io/project-zot/zot:v2.1.18` + two prod repros):** zot loads `/secret/htpasswd` and the `accessControl` config **once at process start** (`HTPasswd.Reload` logged only at boot). A kubelet-style atomic `..data` symlink swap of both Secret mounts activates nothing. SIGHUP is caught by zot's `config_reloader.go` but shuts the server down (`failed to start controller, exiting`) — it is an ungraceful restart, not a reload. A plain restart activates: after `docker restart`, `loaded htpasswd file users:2` and the new user authenticates. The mock cluster runs no zot, so the repro used the docker lab (stronger: exact version, controlled swaps) plus the two live prod failures.
- **Mechanism chosen: operator-side verify-then-bounce** (`registry.EnsureActive`, verify.go). Before any workload rolls to a registry-hosted image, probe zot with the App's own credential against its own repo (`GET /v2/<name>/tags/list`, basic auth — exercises htpasswd **and** the per-repo ACL). Rejected within a 30s grace (anchored to the htpasswd write when this process performed it — for repo-backed Apps the build minutes have already elapsed, so the first rejected probe can bounce) ⇒ requeue; past it ⇒ delete the zot pod (label `app.kubernetes.io/name=zot`, StatefulSet restarts it), rate-limited to one bounce per 2m across all Apps; probe errors (zot down, bounce failure) surface as errors and requeue without blaming the credential. Accepted credentials are memoized until RotateCreds/RevokeCreds, so the steady state adds zero I/O; rotation re-enters the pending window by design; revocation triggers the same bounce best-effort (the running zot otherwise keeps accepting removed credentials — the previously undocumented revocation half of the same no-reload bug). Rejected alternatives: chart-side hot reload (no working zot mechanism to enable), unconditional restart-on-write (restarts zot even when already loaded, e.g. after operator restarts or on no-op reconciles), sidecar SIGHUP (SIGHUP is just a crash, and `shareProcessNamespace` adds surface for nothing), build-aware bounce deferral (accepted blast radius instead: a bounce can fail an in-flight push; the cooldown bounds the churn).
- **Blast radius accepted:** a zot bounce interrupts concurrent pulls/pushes for the restart window (seconds); kubelet retries pulls and the 2m cooldown bounds the churn. RBAC for the bounce is namespace-scoped in `deploy/gitops/base/operator-registry-rbac.yaml` (pods get/list/delete in `bex-registry` only) — live-verified on prod via `kubectl auth can-i` (yes in `bex-registry`, no in `default`).

## Source + Goal linkage

- **Source:** live prod failure found 2026-07-17 by deploying `examples/hello-go` through the official Render CLI (session memory `prod-zot-stale-creds-first-deploy.md`): build pushed fine, but the tenant pod sat in `ImagePullBackOff` — kubelet got **401** from `zot.bex-registry.svc:5000` with the correct `reg-pull-<name>` secret. Reproduced twice on prod (throwaway tenant + user workspace); both recovered instantly after `kubectl rollout restart statefulset/zot -n bex-registry`. The operator's w7/m36 design comment ("Zot hot-reloads htpasswd on each auth request and reloads config.json on SIGHUP or pod restart", `creds.go:31-33`) does not hold for the deployed zot: neither the new htpasswd user nor its ACL entry is loaded until restart.
- **Goal linkage:** deploy experience (w9's theme) and the core Render-alternative promise — `git push`/`services create` → live URL. Today that promise is broken for **every newly created App** on prod; only redeploys of pre-existing Apps work.
- **Expected outcome:** first deploys of new Apps succeed hands-free on prod and every dev-N; the ImagePullBackOff-401 class disappears; no operator ever needs to know zot exists.
- **Why now:** this is a silent, total failure of the first-run funnel (a new user's very first deploy fails with no tenant-visible reason — events/logs show only `update_failed`), and it recurs on every new App until someone with cluster admin restarts zot. Found and twice-reproduced today; the workaround knowledge lives only in session memory.
- **Render parity closing task omitted:** operator-internal mechanism (registry credential plumbing); no REST/GraphQL/MCP/dashboard surface changes. The related-but-separate tenant-facing gap (rollout failure reason invisible in events/logs) is deliberately out of scope here — file separately if wanted.
