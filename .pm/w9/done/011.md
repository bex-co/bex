# Image services on fixed/privileged ports: no listening-port auto-detection

Filed by `w9/m44/t005` (sample lifecycle sweep, 2026-07-17). Deploying `traefik/whoami` (the `examples/whoami-app.yaml` prebuilt-image sample) via `render services create --image traefik/whoami` reached build-less deploy but crash-looped:

```
2026/07/17 23:33:22 Starting up on port 80
2026/07/17 23:33:22 listen tcp :80: bind: permission denied
==> update_failed
```

**Two compounding causes:**

1. **Privileged port + hardening.** Tenant pods drop **ALL** Linux capabilities incl. `NET_BIND_SERVICE` (`lego/operator/internal/controller/app_controller.go` `tenantSecCtx()`; the hardening test even says "high port needs no NET_BIND_SERVICE", w7/m2, `docs/ADR022`). So a container cannot bind a port <1024 even as root. `traefik/whoami` defaults to `:80`. Deliberate posture — but it silently breaks common port-80 images (nginx, httpd, whoami) that work on Render.
2. **No listening-port auto-detection.** bex assigns an image service the default port **3000** (`lego/backend/internal/apps/service.go` / `deploy.go`, `port <= 0 ⇒ 3000`) and injects `PORT=3000`, then routes/health-checks 3000. Render instead **detects** the port the process actually listens on. `whoami` ignores `$PORT` (it reads `WHOAMI_PORT_NUMBER`), so even without the cap issue, bex would route 3000 while the app listens elsewhere.

**In-milestone stopgap (done in t005):** the harness and `examples/whoami-app.yaml` now set `WHOAMI_PORT_NUMBER=3000`/`port: 8080` so whoami binds bex's routed high port — lifecycle then GREEN on prod. But that's whoami-specific knowledge a user shouldn't need.

**The real gap (this follow-up):** decide + implement one of —
- (a) **Document loudly** that image services must listen on `$PORT` (bex's convention, default 3000) and cannot bind <1024 — surface it in the create error (today it's an opaque `update_failed` with the crash only in app logs), the dashboard image-service create form, and `docs/ADR004`/`ADR022`. Cheapest; keeps the hardening posture.
- (b) **Auto-detect the listening port** (Render parity) — probe the container's exposed/listening port and route to it. Most user-friendly; larger.
- (c) **Add back `NET_BIND_SERVICE`** for tenant pods so <1024 works. Weakens the w7/m2 posture — least preferred; note the security trade-off.

At minimum do (a): turn the silent `update_failed` into an actionable message ("container exited: cannot bind :80 — listen on $PORT (bex assigns a port ≥1024)").

**Evidence:** `scripts/samples-lifecycle.sh whoami` reproduces (revert the `WHOAMI_PORT_NUMBER` env to see the crash). Cross-check Render's behavior for the parity ledger (`docs/ADR018`) and `docs/cli-compatibility-checklist.md`.

~1 milestone (option b/c) or ~1 task (option a). Source: w9/m44 prod sweep, 2026-07-17.

---

**RESOLVED 2026-07-17 — option (a) implemented (same-day follow-through of the
m44 closeout).** The silent `update_failed` is now actionable end to end:

- **Operator:** the readiness gate inspects the stuck Deployment's pods
  (`stuckPodMessage`, web + worker paths; new pods get/list RBAC) and stamps an
  actionable Ready-condition message for `CrashLoopBackOff` (exit code + "listen
  on $PORT (N); tenant containers cannot bind ports below 1024" — port hint
  omitted for workers) and `ImagePullBackOff`/`ErrImagePull`.
- **bex-api:** failing deploy closes now carry `failure_reason` (migration 0042,
  `TransitionDeploy` threads it; the reconciler stamps the condition message for
  the operator's concrete diagnoses, else a synthesized health-gate-timeout
  line) — surfaced as `failureReason` on the deploy object across REST, GraphQL,
  and MCP (renderDeploy is shared).
- **Dashboard:** the deploy detail header shows the failure reason; the
  image-service create form gained the "$PORT (default 3000), no ports < 1024"
  hint (en+zh).
- **Docs:** ADR004 (listen on $PORT, no auto-detection, no <1024) + ADR022 (new
  "Tenant container hardening" section documenting the drop-ALL posture and its
  user-visible consequence).

Options (b) auto-detection and (c) NET_BIND_SERVICE were not taken — (a) keeps
the w7/m2 hardening posture; revisit (b) only if real-user friction shows up
with the new diagnosis in place. Tests: `TestStuckPodMessage`,
`TestFailureReasonFor`, reconciler close tests, dashboard suite.
