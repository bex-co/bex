# A new Key Value's connection strings are not shaped like Render's: the external one is empty, the internal one carries the password, and the CLI command is `redis-cli -u`

Why: Render's Terraform provider acceptance tests check all three strings straight after the create, so `TestAccKeyvalueDataSource` and `TestAccRedisDataSource` now stop at their checks 11–13, right after w9/108 got their create past connection info. A client that copies Render's strings sees the same three differences.

- **Found by:** w9/108's recheck on dev-9, 2026-11-18 ([checklist](../../docs/terraform-compatibility-checklist.md), class 10). Harness `scripts/terraform-provider-verify.sh keyvalue redis`, provider pin `06af456`. Recordings sha256 `d627c85a…`, not uploaded (run output).
- **Render** (`internal/provider/keyvalue/datasource/testdata/keyvalue_datasource_cassette.yaml`, a public store with two allow-list entries, read while `creating`):
  - `externalConnectionString`: `rediss://red-…:<password>@oregon-keyvalue.<domain>:6377`.
  - `internalConnectionString`: `redis://red-…:6379`, with no credentials.
  - `cliCommand`: ` REDISCLI_AUTH=<password> valkey-cli --user red-… -h oregon-keyvalue.<domain> -p 6377 --tls`.
- **bex** (`lego/backend/internal/keyvalue/service.go` `KeyValueConnectionInfo`, the same create on dev-9):
  - `externalConnectionString` is `""` until the store's TLS listener opens, about a minute after a first enable (w8/237). The provider stores it as unset, and check 11 fails with `expected to be set`.
  - `internalConnectionString` is `redis://default:<password>@red-….<namespace>.svc:6379`. It drops the credentials only once `status.internalAuthOptional` confirms the auth-injecting front (w5/m268).
  - `cliCommand` is `redis-cli -u <internal URL>`, or `redis-cli --sni <host> -u <external URL>` once the external URL is served.
- **Open questions to settle against render.com first:**
  - Whether a new store's internal URL on Render really carries no credentials. Render documents internal authentication as off until enabled.
  - Whether w8/237's withholding of the external URL until the TLS listener opens should give way to Render's answer at create. Amend w8/237's record in [ADR021](../../docs/ADR021-keyvalue-management.md) if so.
  - Which parts of the test regexes are Render's own infrastructure (`oregon-keyvalue.` hosts, port `6377`) and so a test assumption for the checklist, not a bex defect.
- **Done when:** a new public Key Value's connection info carries an external URL, an internal URL and a CLI command in Render's shapes on REST (`/v1/key-value` and `/v1/redis`) and GraphQL, or ADR018 records each remaining difference with the user's sign-off. `TestAccKeyvalueDataSource` and `TestAccRedisDataSource` must pass checks 11–13, or the checklist must record why each check cannot pass against any non-Render host.
- **Promoted 2026-11-19** to [w9/m521](../m521/README.md) by `/loopx w9`. The work is more than one sitting:
  - the operator routes a new store's Service through its auth proxy from birth;
  - a `<id>` ACL user arrives without restarting running stores;
  - the backend's three strings change, along with the dashboard's Connect panel;
  - then a dev-9 harness recheck and a production check.

  Triage on `ca468bd9d` confirmed the premise and settled the open questions:
  - In the provider's cassettes at `06af456`, all nine Render stores, including three created with `ipAllowList: []`, answer `redis://red-…:6379`, the `rediss://red-…:<password>@…` URL and the `REDISCLI_AUTH=… valkey-cli` command on their first read while `creating`.
  - w8/237's withholding gives way to that answer.
  - Only `oregon-keyvalue.`, Render's regional shared hostname, is Render's own infrastructure. The regexes admit port 6379.
