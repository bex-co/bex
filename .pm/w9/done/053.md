# Cron run live-tail: duplicated log lines + "Live tail disconnected" banner

Observed 2026-08-20 (Playwright QA of cron jobs on dashboard.bex.co, Logs tab during a manual run).

- The run command `sh -c "date; echo hello-from-qa-cron"` emits two lines, but the Logs view rendered them **twice each** — identical timestamp (`08:51:50 PM`) and same run pod (`...-run-...-rs2qx`) — i.e. 4 lines for 2 log records. Looks like a live-tail dedup/append glitch rather than the job actually printing twice.
- A transient banner "Live tail disconnected — reconnecting…" appeared during the tail. Possibly related: a reconnect that re-appends already-shown lines without deduping on log-record identity.
- Investigate the live-tail SSE append/dedup path (log-line list ingest). Cross-check with the virtualized log list (w9/m83) and the ANSI-parse-at-ingest change (w9/m63) — the reconnect may replay a window.
- Low severity (cosmetic), but duplicated lines undermine trust in the log view.

---

## Resolution — 2026-08-22

**Status: DONE (fixed).** Root cause: client dedupe keyed on the raw-string triple `timestamp|instance|message` (`logLineKey` in `dashboard/src/features/logs/lib/map.ts`); the same record redelivered with a precision-drifted timestamp (nanoseconds vs milliseconds) produced a different key and double-rendered, while the second-precision clock display made the copies look identical. Exact-key reconnect replays were already deduped (regression-tested), and no backend resume cursor exists to wire (SSE frames are `data:`-only; the k8s follow replays from offset 0 on every resubscribe). Fix: `logLineKey` normalizes the timestamp to epoch milliseconds via `Date.parse` (raw-string fallback for unparseable stamps); ordering and the virtualized list untouched. Regression tests in `map.test.ts` + `use-live-logs.test.ts` (drop → reconnect → ns-stripped replay appends nothing), proven to fail without the fix; logs/deploys/database/keyvalue suites green (344 tests). Follow-up recorded here: the real replay-window eliminator is backend SSE resume (`id:` per frame + `Last-Event-ID` → k8s `SinceTime`), which would still need this ms-dedupe for the boundary second.
