# MCP `list_logs` doesn't enforce BEX_MAX_QUERY_HOURS

Discovered while wiring GraphQL's `logs`/`logLabelValues` startTime/endTime args to the same window cap REST already enforces (w9/m1/t002/t008, 2026-07-14): REST's `checkWindow` (`lego/backend/internal/logs/rest.go`) is the only caller of the cap today — GraphQL now calls it too, but MCP's `list_logs` tool (`mcp.go`) never has. Pre-existing gap, not introduced by w9/m1 — MCP has always been able to scan an unbounded startTime..endTime range where REST/GraphQL refuse anything wider than `BEX_MAX_QUERY_HOURS`.

- Fix: call `s.checkWindow(q)` in `mcp.go`'s `list_logs` handler after `logQueryFromArgs`-equivalent parsing, mirroring the REST/GraphQL call sites.
- Low urgency (agents polling logs rarely request pathologically wide windows), but worth closing for surface consistency — same standard `docs/ADR006-bex-api.md`'s "one core, three adapters" holds everywhere else.

**Done (2026-07-14):** `s.checkWindow(q)` now called in both `list_logs` and `list_log_label_values` (label discovery scans the same store range, so it's capped too — matching REST's `logsValues`). `TestMCPLogsMaxQueryHoursBounds` covers both tools.
