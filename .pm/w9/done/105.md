# Render's Terraform provider aborts every apply whose configuration names a Render region other than `frankfurt`

Why: bex accepts any Render region and reads back its own, so `terraform apply` of a service, Postgres or Key Value written for Render (`region = "oregon"`) fails with "Provider produced inconsistent result after apply" on bex. On Render the same configuration applies.

- **Found by:** w9/m474's provider acceptance run on dev-9 with production's region mapping (`BEX_REGION=fsn1`), 2026-11-18 ([docs/terraform-compatibility-checklist.md](../../docs/terraform-compatibility-checklist.md), class 1).
- **Render:** `render-oss/terraform-provider-render` `06af456`. `POST /v1/services` with `serviceDetails.region: "oregon"` answers 201 with `region: "oregon"` in every recording. `region` is a required `RequiresReplace` attribute that the provider stores from the response (`internal/provider/types/resource/services.go` `Region`, `webservice/models.go`, `postgres/models.go`, `keyvalue/models.go`).
- **bex:** the same create answers 201 with `region: "frankfurt"` (`lego/backend/internal/resourcemeta/metadata.go` `CheckRequestedRegion` accepts any Render region and places the resource in `BEX_REGION`; `RenderRegion` reads `fsn1` back as `frankfurt`). Terraform core then refuses the new state: `.region: was cty.StringVal("oregon"), but now cty.StringVal("frankfurt")`. 20 of the 47 recorded tests stopped here in run A.
- **Decision needed (user):** ADR049's one-region policy says the request value is never persisted (user decision D1, w8/152) and readback is `frankfurt` (D7, w8/218). Terraform parity needs the readback to echo the region each resource was created with, while placement stays `BEX_REGION`, or ADR018 records that a Terraform configuration must say `frankfurt` on bex. A configuration that says `frankfurt` already applies.
- **Done when:** the decision is recorded in ADR049, and either `TestWebServiceResource_Autoscaling`'s create (`region = "oregon"`) gets past apply on dev-9 with `BEX_REGION=fsn1`, or ADR018's region row records the Terraform consequence with the sign-off.

## Triage — 2026-11-18 (`/loopx w9`): work, not a user decision

- **No user decision gates this.** D1 (w8/152) chose to accept every Render region and place it in `BEX_REGION` instead of refusing it. D7 (w8/218) chose a Render-enum readback so `--from` clones work, and recorded it as "不记为差异" (no divergence). Neither chose to diverge from Render, and ADR018 records no region-readback divergence with the user's sign-off. The root `AGENTS.md` rule (Render parity first) says to amend an ADR that conflicts with parity, and never to park parity work on an optional decision. Reading back the created region is the parity-sufficient option, and it keeps both decisions' outcomes: placement stays `BEX_REGION`, and every readback is still a Render-enum value, so clones still pass the CLI's check. The other option, an ADR018 divergence, would need a sign-off that parity does not ask for.
- **Render's behavior:** the provider's recordings answer `POST /v1/services` `region: "oregon"` with `oregon`. Render's Blueprint spec says of `region`, for services and databases: "You can't modify this value after creation" ([blueprint-spec](https://render.com/docs/blueprint-spec), read 2026-11-18). So the region is recorded only at create.

## Done — 2026-11-18

- **Code.** `resourcemeta.StampRegion` records a requested Render region on the new resource as the `app.bex.co/region` annotation. An omitted region or `BEX_REGION` records nothing. `Config.ResourceRegion` reads the recorded region back, else the D7 alias. Placement and `CheckRequestedRegion` are unchanged.
  - **Where it is recorded:** REST, GraphQL and MCP service create and its dry-run preview, build sources, Postgres and Key Value create, a Blueprint apply that creates a service, Postgres or Key Value (`bexService.Region`, `bexDatabase.Region`), and a Postgres recovery, which keeps its source's region.
  - **Where it is read:** the service, Postgres and Key Value views, so REST, GraphQL, MCP, list filters and dashboard metadata all follow. Also the Render service projection (`toRenderServiceWithMetadata` now prefers the view's region) and Blueprint export.
- **Tests.**
  - `TestResourceRegionReadsBackTheCreatedRegion`.
  - The create tables in `apps`, `postgres`, `keyvalue` and the composed server now check both the create's answer and the readback.
  - `TestBlueprintApplyReadsBackTheDeclaredRegion`: an apply with `region: oregon` reads `oregon` on services, Postgres and Key Value; a re-sync naming `virginia` leaves it; an entry with no region reads `frankfurt`.
  - `TestGenerateBlueprintExportsEachResourceRegion` and `TestRecoverReadsBackTheSourcesRegion`.
  - Mutation checks: removing the service, stack-database, Postgres or recovery stamp, or restoring the old projection precedence, fails the matching test.
  - The backend `go test ./...` and `make lint` pass.
- **Docs.** ADR049 D7 is amended. ADR018 (Blueprint contract, service region filter, Terraform row), ADR006 metadata, the CLI and Terraform checklists, and `lego/backend/AGENTS.md` (`BEX_REGION`) are updated.

  - `TestAccPostgresIPAllowListResource` **passes** production-shaped: create, update, import and destroy, with all 19 recorded `region` values reading `oregon`. In run A it failed on the region alone.
  - Recordings sha256: `48b491bd…` (webservice) and `09beceae…` (postgres). They were not uploaded; the harness re-creates them.
  - **Cleanup.** The workspace read empty on services, Postgres and Key Value. The API key was revoked (then 401), `agent-down` and `down` ran, and the four empty throwaway tenant namespaces were deleted.
