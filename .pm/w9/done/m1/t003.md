## Objective

Build the per-deploy page at `/services/$serviceId/deploys/$deployId` — bex's twin of Render's `dashboard.render.com/web/srv-…/deploys/dep-…` (inspected live 2026-07-14): a compact header (created date, status badge, trigger, image, pre-deploy outcome, started/finished) above a log viewer scoped to the deploy's time window, live-refreshing while the deploy is non-terminal.

## Context

- Route files pattern: `dashboard/src/routes/services.$serviceId.*.tsx`; the new route nests under the existing `services.$serviceId.tsx` shell so the service header + tab nav stay (Render keeps the service chrome on its deploy page too).
- Data: `deploy(serviceId, deployId)` (t001) for the header; `logs` with `startTime = deploy.createdAt`, `endTime = deploy.finishedAt ?? now` (t002). Query log types `build`, `predeploy`, and `app` — Render's page interleaves build lines (`==> …`) with instance-tagged runtime lines.
- Reuse `dashboard/src/features/logs/components/{log-viewer,log-line-list,log-filter-bar}.tsx` rather than a new log renderer; the deploy page needs search + follow, not the full filter bar.
- Poll the deploy while `status` is non-terminal (`update_in_progress`/`build_in_progress`… — terminal set per `lego/backend/internal/deploys/service.go`), then stop; the header badge and log window end must update on the terminal transition.
- New feature code lives in `dashboard/src/features/deploys/` (self-contained module per `dashboard/CLAUDE.md`), locale keys `deploys.*` in `locales/{en,zh}.ts` registered in `src/i18n/index.ts`.
- Every user-visible string through `useTranslations()`.

## Steps

1. Create `src/features/deploys/` (components + hooks + locales): `use-deploy.ts` (query + poll-until-terminal), `deploy-header.tsx` (status badge reusing the Events tab's status→badge mapping, trigger, image, pre-deploy status line, timestamps), `deploy-log-panel.tsx` (windowed logs query, type filter defaulting to all three, follow-to-bottom).
2. Add route `src/routes/services.$serviceId.deploys.$deployId.tsx` rendering them inside the service shell; page title `<name> · Deploy · bex dashboard`.
3. Register `deploys` locales (en + zh) in `src/i18n/index.ts`.
4. `yarn typecheck && yarn lint && yarn test`; verify visually against `yarn dev:local` (needs t005 for data).

## Acceptance criteria

- [ ] Navigating to `/services/<id>/deploys/<deployId>` renders the deploy's status, trigger, image, pre-deploy outcome, and timestamps.
- [ ] The log panel shows only lines inside the deploy's window, including `type=build` and `type=predeploy` lines, interleaved chronologically with `type=app`.
- [ ] While the deploy is in flight the page refreshes (logs + status) without a manual reload, and stops polling once terminal.
- [ ] Unknown deployId renders a not-found state (no crash, no phantom deploy).
- [ ] All strings translated (en + zh); `yarn typecheck && yarn lint && yarn test` pass.

## Out of scope

- A dedicated "Deploys" list tab (Render has one; bex's Events tab already lists deploy history — parity gap to note in t006, not build here).
- Render's `?r=<range>` URL time-range param and log maximize/options affordances.
- Commit hash/message display (no per-deploy commit metadata in bex yet — t001 out-of-scope note).
