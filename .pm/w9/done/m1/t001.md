## Objective

Expose the existing single-deploy core verb over GraphQL as `deploy(serviceId, deployId)`, so the dashboard's deploy detail page can fetch one deploy by id. REST (`GET /v1/services/{id}/deploys/{deployId}`) and MCP (`get_deploy`) already answer this via `deploys.Service.Get` (`lego/backend/internal/deploys/service.go:237`); GraphQL only has the `deploys(serviceId, …)` list — this closes that drift.

## Context

- `lego/backend/internal/deploys/graphql.go` — `deployGQLType` already models every field the page needs (`id status trigger image rollbackOf createdAt startedAt finishedAt preDeployStatus`); `GraphQLQuery()` returns only the list field today.
- `deployMutationArgs` in the same file is the `(serviceId, deployId)` argument shape to reuse.
- Error contract: unknown deployId → the same not-found the REST adapter maps (`core.ErrNotFound`); a deployId belonging to a different service must not resolve (see the service.go:237 doc comment).

## Steps

1. Add a `deploy` field to `GraphQLQuery()` in `graphql.go`: args `(serviceId String!, deployId String!)`, type `deployGQLType`, resolving through the same `s.Get(ctx, serviceId, deployId)` verb REST/MCP use.
2. Follow the existing resolver style (`gqlutil`, error passthrough — no adapter-side status mapping).
3. `cd lego/backend && go build ./... && go test ./internal/deploys/...`.

## Files

- `lego/backend/internal/deploys/graphql.go`

## Acceptance criteria

- [ ] `{ deploy(serviceId: "...", deployId: "...") { id status preDeployStatus } }` returns the same DeployView the REST detail endpoint serves.
- [ ] Unknown deployId (or a deployId owned by another service) errors as not-found, matching REST.
- [ ] `go test ./...` passes in `lego/backend`.
