## Objective

Verify the unified error shape is consistent across REST, GraphQL, and MCP, and compare against Render's documented error responses (`{"id","message"}` family) — flag any remaining drift as follow-up rather than silently diverging.

## Context

- docs/ADR006-bex-api.md — one core, thin adapters; error shapes listed as part of the compatibility contract.
- docs/cli-compatibility-checklist.md — the official CLI renders API `message` fields on failure; a login with a bad key is the cheapest live probe.

## Steps

1. Exercise representative error paths on each surface (REST 401/400/404/405; GraphQL decode + resolver error; MCP tool error) and record shapes.
2. Run `render` CLI with an invalid key against bex-api; confirm the failure output shows the message (not a raw body dump).
3. File follow-up notes for any drift found; update the CLI checklist row evidence if it changes.

## Results (2026-07-15)

**REST — one envelope, verified via `core.WriteErr` / `core.WriteErrStatus`** (both now share `statusErrID` for the `id` field, so their bodies are byte-identical):

| Path                       | Status | Content-Type       | Body                                                                                        |
| -------------------------- | ------ | ------------------ | ------------------------------------------------------------------------------------------- |
| auth gate, no credential   | 401    | `application/json` | `{"error":"unauthorized","id":"unauthorized","message":"unauthorized"}`                     |
| auth upstream down (Ory)   | 503    | `application/json` | `{"error":"auth upstream unavailable","id":"unavailable","message":"auth upstream unavailable"}` |
| GraphQL body decode        | 400    | `application/json` | `{"error":"bad request","id":"bad_request","message":"bad request"}`                        |
| metrics param invalid      | 400    | `application/json` | `{"error":"startTime: …","id":"bad_request","message":"startTime: …"}`                      |
| deploy-hook wrong method    | 405    | `application/json` | `{"error":"method not allowed","id":"method_not_allowed","message":"method not allowed"}` (+ `Allow: GET, POST`) |
| not found (`WriteErr`)     | 404    | `application/json` | `{"error":"app not found","id":"not_found","message":"app not found"}`                      |
| body too large (ratelimit) | 413    | `application/json` | `{"error":"request body exceeds N bytes","id":"payload_too_large","message":"…"}`           |

**GraphQL** keeps its spec-mandated envelope `{"data":…,"errors":[{"message":…}]}` — it cannot be `{"id","message"}` and stay a valid GraphQL response — but every error still carries a human `message`, the field Render clients key on. The pre-execution HTTP body-decode failure (not a GraphQL execution error) now returns the REST 400 above.

**MCP** keeps its JSON-RPC/tool-error protocol envelope; tool errors carry the message in the tool-result content, protocol errors in JSON-RPC `{code,message}`. Both surface `message`.

**Conclusion — no unexplained drift.** The REST/HTTP surface is fully unified on `{"error","message","id"}` + `application/json`. GraphQL and MCP each retain their own protocol-mandated error envelope, both of which include `message`; that is a protocol boundary, not a bex inconsistency.

**Render comparison.** Render's public error schema is `{"id","message"}` (per `render-oss/cli`'s generated client); bex is a superset (adds `error` for pre-existing bex tooling). The official CLI reports the API's `message` on failure — previously the 401 was `text/plain` with no `message`, so a bad-key login rendered a generic "unknown error"; it now carries `message":"unauthorized"`, which the CLI surfaces verbatim.

**CLI live probe.** The full-shape live probe (`scripts/cli-compat.sh verify` against a `.pm/w9/dev-9/` stack + a `render login` with a bad key) needs the dev-9 kind stack + a locally built `render` binary; not stood up in this session. The 401 body change is verified by `internal/api.TestErrorDialectIsRenderShaped` and the shape dump above; the CLI-rendering improvement follows deterministically from the CLI keying on `message`, now present. Recommended follow-up: run the live `render login` probe on the next dev-9 session and attach output to the `docs/cli-compatibility-checklist.md` login row.
