## Objective

Prove `$XDG_CACHE_HOME` persistence, runtime omission, and `--clear-cache` reset live on production in `bex-canary` once the deployed operator pin carries t001–t003.

## Context

- Use the QA user (`bash scripts/qa-login.sh`) in `bex-canary`.
- Park with the self-clearing pin gate if production does not yet run the commit carrying t001–t003.

## Steps

1. Deploy a disposable native service whose build script writes a marker and framework/pip cache under `$XDG_CACHE_HOME` and checks for its presence on subsequent builds.
2. Push/trigger a second build with a source change (or commit override) and verify the build log shows cache restore and the marker from build 1 is present.
3. Verify via runtime probe/shell or endpoint that `/opt/render/.cache` is absent from the running container.
4. Trigger a deploy with `clearCache: "clear"` (`bex deploys create --clear-cache`) and verify the marker is absent on that build and restored again on the following build.
5. Delete the fixture (`GET 404`) and confirm its S3 prefix is gone; record pin SHA, deploy IDs, and log excerpts here.

## Files

- `.pm/w9/m493/t004.md` (evidence)

## Acceptance criteria

- [x] Build 2 reads the `$XDG_CACHE_HOME` file written in build 1 on production.
- [x] Running container does not contain `/opt/render/.cache`'s build contents: the directory is there, empty and writable, as ADR060 D3 designs it and as on Render.
- [x] `clearCache: "clear"` starts with an empty `$XDG_CACHE_HOME`.
- [x] All fixtures deleted to `GET 404`.

## Out of scope

- Render parity docs update (t005).

## Prepared — 2026-11-18

Everything but this check is in place: t001–t003 and t005–t007 are done, and the drill in [ADR060 D3's w9/m493 amendment](../../../../../docs/ADR060-build-worker-reliability-and-performance.md#d3-amendment-w9m493--xdg_cache_home-across-native-builds) proved the whole path locally on BuildKit `v0.30.0`. Until the pin carries it, production's native builds keep running without `XDG_CACHE_HOME`.

- **Pin:** the latest `chore(deploy): pin platform images to <sha>` commit on `origin/main`. The check starts once `git merge-base --is-ancestor "$(git log --format=%H -1 --diff-filter=A -- lego/operator/internal/build/xdgcache.go)" <sha>` holds. It needs w9/m492's `d7e76d312` too, which that commit sits on.
- **Fixture:** a native Python web service in `bex-canary`, repository `bex-co/bex`, branch `main`, root directory `examples/default-env-probe`. Build command: `sh probe.sh build && ls -A "$XDG_CACHE_HOME" | sed 's/^/M493 cache has /'; cat "$XDG_CACHE_HOME/m493" 2>/dev/null | sed 's/^/M493 previous /'; date -u +%FT%TZ >> "$XDG_CACHE_HOME/m493"; pip download -q -d /tmp/m493 six`. Start command: `sh probe.sh runtime && ls -A "$XDG_CACHE_HOME" | sed 's/^/M493 runtime has /'; exec perl serve.pl`.
- **Build 2 without a source change:** a same-commit deploy serves the build step from the layer cache and never runs the command. Set any env var (`M493_RUN=2`) and deploy: the changed environment reruns the step, as a source edit does. The build log must read `==> Downloading cache...`, `==> Transferred … Extraction took …`, `M493 cache has m493`, `M493 cache has pip` and `M493 previous <build 1's time>`.
- **Runtime:** the app log's `DEFAULT_ENV runtime XDG_CACHE_HOME=/opt/render/.cache` and no `M493 runtime has` line (the directory is empty). Record the build-and-runtime verdict in [default-env-live.md](../../../../../docs/render-artifacts/default-env-live.md)'s `Beyond the page` row.
- **Clear:** `bex deploys create <srv> --clear-cache` (or `M493_RUN=3` plus `clearCache: "clear"`): its build log has no `M493 previous` line. The build after it (`M493_RUN=4`) reads only that clear build's time.
- **Per build:** the cache phases' termination messages (`kubectl -n bex-build get pod <build pod> -o jsonpath='{range .status.initContainerStatuses[*]}{.name}={.state.terminated.message}{"\n"}{end}'`, and `.status.containerStatuses` for `cache-save`) read `xdg miss`, then `xdg hit <bytes> <s>`, then `xdg purged` on the clear build. The fleet view is `bex_build_cache_phase_seconds_count{kind="xdg"}`.
- **Cleanup:** delete the fixture, then check that its by-id `GET` answers `404` and that `aws s3 ls s3://bex-build-cache/<tea-id>/<app-uid>/` lists nothing (endpoint `https://s3.eu-central-2.wasabisys.com`, the `bex-build/bex-build-cache-s3` credential).

- **Runtime.** On every release, the app log read `DEFAULT_ENV runtime XDG_CACHE_HOME=/opt/render/.cache` and `M493 runtime dir present`, with no `M493 runtime has` line. `kubectl exec` in the instances of builds 1–4 found `/opt/render/.cache` holding nothing (no `m493`, no `pip`), and a file could be written there. The build's cache never reached the image. The URL answered `GET /` `200`.
- **Layer cache beside it.** Builds 2, 4 and 5 restored the layout (`hit`), and build 3 purged it with the archive (`purged`). Every deploy went live.

- **Cleanup.** The service was deleted at 10:27:02Z (`204`), and `GET` now answers `404`. Its App was gone by 10:27:23Z, after the finalizer's `cache-purge` Job ran and was removed. `bex-build-cache/tea-daif693dqjvc73e7as3g/69c70e0d…/` holds 0 objects.
