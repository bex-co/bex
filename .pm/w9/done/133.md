# A Ruby service whose Gemfile pins an exact Ruby patch fails `bundle install`: bex builds on the line's patch and Bundler refuses it

Why: Render's own `render-examples/sidekiq` fails its build on bex with `Your Ruby version is 3.2.11, but your Gemfile specified 3.2.0`. Its Gemfile says `ruby '3.2.0'`, and the repository exists to deploy on Render.

- **Found by:** w9/m494 t004 on production, 2026-11-19. The fixture was `qa-20261119-m494-ruby` (`srv-dbvihrelkors73fpphag`), deleted afterwards. Its `Gemfile.lock` records `RUBY VERSION ruby 3.2.0p0` and its `Gemfile` pins `ruby '3.2.0'`. The build chose the 3.2 line's reviewed 3.2.11 from the lockfile, and `bundle install` exited 18 after the version check.
- **Where:** `exactRequest` (`lego/operator/internal/build/nativeversion.go`, "Only a plain version signal counts (an env var or a single-version file); a range, an alias or a lockfile keeps resolving to the line's reviewed patch"). `fromLockedRuby` and `fromGemfile` map onto the line, and ADR060's w8/175 amendment says "Ranges, aliases and lockfile signals keep the line's pin". For Ruby that choice is not a quiet divergence: Bundler enforces a Gemfile's exact `ruby` requirement, so the build fails.
- **Render:** [render.com/docs/ruby-version](https://render.com/docs/ruby-version) reads the Ruby from `Gemfile.lock`/`gems.locked` `RUBY VERSION` first, then `.ruby-version`, `.tool-versions` and the `Gemfile` `ruby` directive. The page does not say whether it installs the exact patch. Check that first, for example from a Render build log of this repository.
- **Done when:** a native Ruby service whose lockfile records `ruby 3.2.0p0` and whose Gemfile pins `ruby '3.2.0'` builds on Ruby 3.2.0, and the log names it (`==> Using Ruby 3.2.0 (from Gemfile.lock)`). A missing tag falls back with the same log line the other exact paths print. `nativeversion_test.go` covers the lockfile and Gemfile signals, and ADR060's plain-versions amendment and ADR018's runtime row are amended.

**Render checked first (2026-11-20):** Render installs the exact patch its first Ruby signal names, the lockfile's included. Its build logs read `==> Using Ruby version 3.4.1 via /opt/render/project/src/Gemfile.lock` (GoRails forum, January 2025) and `==> Using Ruby version 3.4.2 via /opt/render/project/src/.ruby-version`. It hands the detected string to ruby-install: a Gemfile `ruby file: ".tool-versions"` once reached it as the version `".tool-versions"` and failed to download `postmodern/ruby-versions` ([feedback.render.com](https://feedback.render.com/features/p/use-gemfilelock-or-tool-versions-instead-of-gemfile-for-ruby-version-detection), fixed 2024-04-04). Its [version-pinning guide](https://render.com/articles/pinning-nodejs-python-ruby-versions) says services "honor your exact version files" and stay "on the exact patch version you tested". `render-examples/sidekiq` itself moved to `ruby '3.3.14'` / `ruby 3.3.14p208` on 2026-11-20 (`680c18cfb`); `73f3ab4db` is the 3.2.0 commit m494 built.

**Fixed 2026-11-20 in `993593eeb` (loopx w9):** `exactRequest` now reads a fully qualified version from `Gemfile.lock`/`gems.locked` `RUBY VERSION` (patchlevel dropped), from `.tool-versions` `ruby` and from a single-requirement Gemfile `ruby "3.2.0"`, as it did from `.ruby-version`; a Gemfile range keeps the line's patch. Ruby's bookworm images start at 3.1.4 and 3.2.2 (`ruby:3.2.0-bookworm` is 404 on Docker Hub, `ruby:3.2.0-bullseye` exists), so a release before them takes its `/usr/local` tree from the `-bullseye` image onto the bookworm common base, which already carries bullseye's libssl1.1 and libffi7 for the 3.0 line; its source guard now admits any bullseye Ruby tree. The log reads `==> Using Ruby 3.2.0 (from Gemfile.lock)` and `==> ruby:3.2.0-bookworm does not exist; using Ruby 3.2.0 from ruby:3.2.0-bullseye`. With no image in either variant it keeps the reviewed patch and prints `==> No official image ruby:3.2.0-bookworm; using the reviewed Ruby 3.2 image`, as every exact path does. `TestRubyExactSignalsPinTheirPatch` (`nativeversion_test.go`) covers the lockfile, `gems.locked`, Gemfile and `.tool-versions` signals and the ranges that keep the line; `TestRubyReleaseOlderThanBookwormComesFromBullseye` and three new `TestExactVersionPinsTheRequestedPatch` rows cover the images. With the fix removed, all of them fail. The Ruby qualification profile has a `ruby320-locked-bullseye` case (Gemfile pin and lockfile, `bundle install --local`), which the next families run builds for real. ADR060's plain-versions amendment and ADR018's runtime row record it. Local Docker was unresponsive, so no real image was built here.

**Parked 2026-11-20:** the live check needs a pin carrying `993593eeb`; production runs `f797f525f5df`. **Next, once the pin carries it:** as the QA user in `bex-canary`, create a free native Ruby web service from `render-examples/sidekiq` with auto-deploy off, build `bundle install`, start `bundle exec ruby main.rb`.
