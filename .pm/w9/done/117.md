# An API key cannot create a Postgres credential, where Render's key can (`POST /v1/postgres/{id}/credentials`)

Why: Render serves its Postgres credentials routes to API keys; bex refuses every key on create because minting a database password is mint-class, so Terraform or a script cannot add a database user.

- **Render**: the pinned OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`) has `GET`/`POST /postgres/{postgresId}/credentials` and `DELETE /postgres/{postgresId}/credentials/{username}`.
- **bex**: `postgres.Service.CreateUser` (`lego/backend/internal/postgres/access.go`) calls `AuthorizeMintClass`, which refuses every machine caller (w9/m481 I4 kept it).
- **Done when:** a key whose creator may create Postgres users does so on REST, GraphQL and MCP (the relation still decides, capped by the creator since w9/m481); a delegated third-party token and a key with no recorded creator stay refused; the lineage records why a key may mint this credential (the w9/m481 webhook reasoning: a first-party credential revoked with its creator's membership).
- Filed by w9/m481 t009.

## Record (2026-11-19, `/loopx w9` worker)

**Shipped in `d3405541e`.** `postgres.Service.CreateUser` takes `AuthorizeExportClass` instead of `AuthorizeMintClass`: a session, a platform client or a bex API key with a recorded creator; a delegated third-party OAuth token, a key with no recorded creator (which I3 otherwise leaves `can_create`) and any other machine client are still refused. The key acts as its creator: `createUser`'s uncached `can_create` re-check is capped by the creator's own (`keyCeiling`), and the dispatch gate already required "Create and delete database credentials" in its grant. Recorded in [ADR024 § An API key creates Postgres logins as its creator](../../../docs/ADR024-members.md#an-api-key-creates-postgres-logins-as-its-creator-w9117) (I13), ADR012 § 7, ADR018's API keys and Postgres access rows, ADR117 and the security review [ADR121](../../../docs/ADR121-security-review-key-postgres-logins.md).

**The premise, corrected.** Render's own `POST /v1/postgres/{id}/credentials`, which this note's title names, was never refused to a key: `CreateCredential` reveals nothing and has had no class gate since w5/m265, and ADR018's API keys row wrongly said otherwise (now corrected). The refusal was on bex's native create, which returns the password: `POST /v1/postgres/{id}/users`, GraphQL `createDatabaseUser` and MCP `create_postgres_user`.

**Evidence.** `TestAKeyCreatesAPostgresUserAsItsCreator`, `TestAKeyCreatesNoPostgresUserItsCreatorMayNot` (a Contributor's key holding a stray developer tuple, a demoted and a removed creator), `TestCreateUserStillRefusesAnUnattributedCaller` (a key with no recorded creator, an operator-provisioned client, a delegated third-party token), `TestCreateUserFailsClosedWhenTheKeyRegistryCannotAnswer`, and the e2e `TestAPIKeyCreatesPostgresUsersAsItsCreatorE2E` (real Postgres and OpenFGA over REST, GraphQL, MCP and Render's credentials route: a Developer's key and a Postgres credentials Write key create logins and get the password, a Postgres instances Read & write key is `403 api_key_permission_denied`, a Contributor's key is 403, a key with no recorded creator and a delegated third-party token are 403 on the three native surfaces, the demoted Developer's key is refused at once and works again once they are promoted back, the removed Developer's key is refused). With `AuthorizeMintClass` restored, the unit tests and the e2e's Developer key failed; with no class gate, the unattributed callers created logins in both. No dev-9 run: the gate is the one w9/116 proved there with real Hydra keys, and the Postgres path below it is unchanged.

**Remaining: the production check.** Once a production pin carries `d3405541e` (`git merge-base --is-ancestor d3405541e <pin>`), sign in as the QA user (`bash scripts/qa-login.sh`) in `bex-canary` and create a free Postgres of your own. Mint a key with no `permissions` (All): its `POST /v1/postgres/{id}/users`, GraphQL `createDatabaseUser` and MCP `create_postgres_user` each create a login and return its password (before this change each answered 403). Mint a key granted only Postgres instances Read & write; its `POST …/users` answers 403 `api_key_permission_denied`. Then revoke both keys (401 on their next request), delete the database and log out. The demoted, removed, Contributor, unattributed and third-party cases need a second production identity or a forged key, so they ran in the e2e only. Record the result here and move the note to `done/`.
