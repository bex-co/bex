# 071 — Log levels are detected in JSON but not logfmt, so `--level` is dead for Go `slog`'s default output

Why: the shipper's own rationale is "parse the line's structured severity, never guess from substrings" — logfmt is structured, not a guess, and it is what `slog.NewTextHandler` emits, so the whole `--level` filter surface is unusable for a large class of ordinary Go services.

**Status:** done — fixed in `d41c5ac9e`, synced and verified in production on 2026-09-22 UTC.

Live, 2026-09-22 (sweep 5), production, `bex v0.2.1` / pin v2.27.0, workspace `bex-canary`. Fixture `qa-7a25346f-lvl`, free native-Go web service whose start command emitted one line in each of three shapes, then served. Created and deleted in-sweep.

| line emitted                                   | `level` label bex assigned |
| ---------------------------------------------- | -------------------------- |
| `{"level":"error","msg":"qa-lvl-…-json"}`       | **`error`** ✅              |
| `level=error msg=qa-lvl-…-logfmt`               | `unknown` ❌               |
| `ERROR qa-lvl-…-plain`                          | `unknown` ✅ (correct)     |

End-to-end the filter then behaves accordingly: `bex logs --resources <svc> --level error` returned **1** line (the JSON one) out of 16.

## This is not a request to reopen the design decision

`deploy/gitops/base/log-shipper.yaml:208-213` states it plainly:

> `level` on App logs, honestly: parsed from the line's own JSON severity field, NEVER guessed from substring matching (a line containing the word "error" is not an error). A non-JSON line — or JSON without a severity key — is labelled `unknown`, which is the truth: bex does not know.

That reasoning is right, and the plain-`ERROR` row above confirms it working as intended — substring guessing stays rejected.

**But logfmt is not a substring guess.** `level=error` is an unambiguous structured key/value, exactly as explicit as the JSON `"level":"error"` the pipeline already trusts. The stage that extracts it (`stage.json`, `:218-223`) simply has no logfmt counterpart, so the line never reaches the normalization template at `:229` and keeps the `unknown` seeded by `stage.static_labels` at `:244-249`.

## Why it matters more than it looks

`log/slog` is Go's standard structured logger, and `slog.NewTextHandler` — the default for anyone who does not explicitly choose JSON — emits logfmt:

```text
time=2026-09-22T00:41:37.000Z level=ERROR msg="request failed" path=/x
```

Those services get `level: unknown` on every line and cannot use `--level` at all. The same is true of logrus's default `TextFormatter` and anything else emitting logfmt. The README's advice ("tenants who want `level=error` log JSON") is a reasonable default, but it currently also excludes people who *are* logging structured severity, just not in JSON.

## Fix

Add a `stage.logfmt` beside the existing `stage.json` in `loki.process "app_logs"`, extracting the same two keys:

```river
stage.logfmt {
  mapping = { level = "", severity = "" }
}
```

Ordering matters: it must run before `stage.template` at `:229` so the normalization template sees the extracted value, and before `stage.labels` at `:251`. A stage whose source key was never extracted is skipped, so a JSON line is unaffected by the logfmt stage and vice versa.

The cardinality budget at `:26-32` is unchanged: the same template at `:229` still collapses everything to the same five buckets (`error|warn|info|debug|unknown`), so no new label values can be minted.

## Acceptance

- [x] A service logging `level=error msg=…` (logfmt) gets `level: error`, and `bex logs --level error` returns it.
- [x] A service logging `{"level":"error",…}` still gets `level: error` (no regression).
- [x] A plain `ERROR …` line still gets `level: unknown` — substring guessing stays rejected, and this should be asserted, not just left alone.
- [x] `list_log_label_values(label="level")` still returns only the five documented buckets.

~30-45m: one pipeline stage plus the three-shape assertion above. The shipper is gitops-deployed, so it needs a sync, not just a merge.
