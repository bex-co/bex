# A workspace delete that fails partway cannot be retried by its admin: the first attempt already revoked every member

Why: the delete is built to be retried after a purger failure, but the retry answers 403, so the workspace stays stuck half torn down until an operator finishes it.

- **Found by** w9/120, 2026-11-18. In `TestDeletingAWorkspaceRevokesItsAPIKeysE2E` (real Postgres and OpenFGA), the admin's first `deleteWorkspace` fails in a pre-cascade purger and their identical retry through `workspaces.Service.Delete` answers `forbidden`. The test now retries through `workspaces.AccountTeardown`, the account worker's path, which skips authorization.
- **Cause.** `workspaces.Service.deleteWorkspace` revokes every member's OpenFGA tuple before it runs the pre-cascade purgers (`lego/backend/internal/workspaces/service.go`, the `s.Revoker` loop above `runPurgers`). A failure in any purger then leaves the tenant row, but nobody holds `can_manage` on it any more, so `Delete`'s `AuthorizeWorkspace` and `AuthorizeFreshOn` refuse the retry. The w1/m61 retry tests (`TestDelete_RetryAfterPreCascadePurgerFailureCompletes`) run with allow-all authorization, so they cannot see this. A personal workspace may recover on the owner's next sign-in (`tenancy.ensureGranted`); a team workspace does not.
- **Constraint.** Revoking first is also what stops members creating resources (or minting API keys) while the purgers run, so do not just move the loop after the purgers. Options include keeping the revoke first and letting a retry by a subject the store still records as an Admin of the half-deleted workspace through, or marking the workspace as deleting so writes are refused while members keep `can_manage` until the cascade.
- **Paths:** `lego/backend/internal/workspaces/service.go` (`Delete`, `deleteWorkspace`), `lego/backend/internal/api/workspace_delete_apikeys_e2e_test.go`.
- **Done when:** an admin's retry of a delete whose purger failed completes the delete against real OpenFGA, with a test that drives the retry through the public verb; no member can create a resource or mint a key in the workspace once its first delete attempt has started.
- **Done 2026-11-19.** The delete now stamps `tenants.delete_started_at` (migration 0312, `store.StartTenantDelete`) after its settle and before the revoke, and `workspaces.Service.Delete` authorizes through `core.Base.AuthorizeWorkspaceOrRecorded`: when OpenFGA plainly refuses a person signed in directly (session or human OAuth, never an API key or a credential acting for someone), `store.DeletingTenantAdmin` admits a `kind = 'user'` admin row of a workspace whose delete has started. Capability, login requirements, the confirmation phrase and the audit row still apply. The mark also closes every re-grant path while the workspace is half deleted: `tenancy.ensureGranted` (the personal owner's next request used to hand the admin tuple straight back, so they could create resources there, which the new e2e test reproduced before the fix), login-time and link invites, org workspace joins, `UpdateMemberRole`, and the role outbox. Proof: `TestHalfDeletedWorkspaceE2E` (real Postgres and OpenFGA) has the admin and the developer refused at creating an env group and at minting a key after the failed first attempt, refuses the retry for the developer, a removed admin, another workspace's admin and a stranger, then completes the admin's and a personal owner's retries through the public verb. `TestDeletingAWorkspaceRevokesItsAPIKeysE2E` now retries through `Service.Delete` as well, and `TestWorkspaceDeleteStartedPG` covers the store half. With the recorded decision unwired, or the `ensureGranted` guard removed, the e2e test fails. ADR024 records it.
