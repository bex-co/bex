# 101 — The dashboard's Audit Log table names a deleted user `Deleted User ID#<usr- id>`, as the export does

Why: on production the table shows the stored marker `deleted:own-…`, an internal id no other surface shows, for a person REST answers as `usr-…` with `actorDeleted: true` and the CSV export as `Deleted User ID#usr-…` (w9/099), so the table and the export name one person two ways.

- **Source:** w9/m450 t008 (closeout walk on production, 2026-11-18). In `bex-canary` (`tea-daif693dqjvc73e7as3g`), the four rows of the identity w9/m449 deleted (`usr-dbum0qseoepc73dlkt9g`) read `deleted:own-dbum0qseoepc73dlkt…` in Workspace Settings → Audit Log. On REST `GET /v1/owners/tea-daif693dqjvc73e7as3g/audit-logs` they read `actor {type: user, id: usr-dbum0qseoepc73dlkt9g}` with `actorDeleted: true`, and the dashboard's own CSV export of 2026-11-18 reads `Deleted User ID#usr-dbum0qseoepc73dlkt9g`.
- **Today:** `dashboard/src/features/audit/components/audit-event-row.tsx` labels the actor with `useWorkspaceSubjectLabel(event.actor, event.actorEmail)`. With no email and no member to match, that hook falls back to the raw stored subject. `dashboard/src/features/audit/api/audit.graphql` does not select `actorDeleted`, though GraphQL serves it (non-null since w9/099). A person whose email lookup failed also shows the raw Kratos subject, not the `usr-` id that REST and the CSV show.
- **Do:** select `actorDeleted` and label the row the way `csvActor` (`dashboard/src/features/audit/lib/audit-csv.ts`) does: the email, else `Deleted User ID#<actorId>` for a deleted person, else `actorId`, else the subject. Keep the row's two-line height (w4/684).
- **Accept:** a dashboard test covers a deleted person, a person with a failed email lookup and a live member. On production, the table's actor cell for `usr-dbum0qseoepc73dlkt9g`'s rows in `bex-canary` matches the CSV's `actor` column.
