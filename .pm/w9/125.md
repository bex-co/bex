# An open shell, exec, file-transfer or agent-attach stream outlives a narrowing of its API key's grant

Why: w9/m496 holds a scoped API key to its grant on every request, but a stream the key opened before its grant was narrowed is revalidated by the SSH gateway against the key's role and revocation only, so it keeps running until the gateway's own session cap ([ADR118](../../docs/ADR118-security-review-scoped-api-keys.md), residual risk).

- **Found by:** w9/m496 t008, the security review of the scoped-key boundary, 2026-11-18.
- **Where:** the tickets are minted through the dispatch gate under their own actions (`services.jobs` for a service shell, `sandboxes.exec` and `sandboxes.files` for a sandbox, `agents.manage` for an agent attach), so a key without them cannot open a stream. Once open, `lego/backend/internal/sshgateway` revalidates it every `DefaultRevalidateInterval` (`webshell/websocket.go`, `nativessh/server.go`, `sandboxsse/sandboxsse.go`, `sandboxfiles/sandboxfiles.go`, `agentattach/agentattach.go`) with `ExecRevalidator` or `ResolveSSHSession`, which check the ticket subject's relations, not its grant. The ssh-gateway process has no Postgres, so it cannot read `tenant_members.key_permissions` itself.
- **Mitigation today:** revoking the key ends every stream at the next revalidation tick (its tuples are gone); a role change does too.
- **Render:** a scoped key's permissions are its whole authority ([render.com/docs/api-keys](https://render.com/docs/api-keys)); Render documents no live stream that survives a permission change.
- **Done when:**
  - The gateway's revalidation of a stream opened by an API key also asks bex-api, over the existing HMAC-signed internal verb pattern, whether the key's grant still covers the stream's action, failing closed when it cannot answer.
  - A test narrows a key's grant under an open exec stream and sees the stream end at the next tick; ADR118's residual is updated.
