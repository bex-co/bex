## Objective

Make the import-based launcher installable and document its safe interactive and CI authentication contracts without suggesting that a Bex OAuth client secret is a permanent bearer token.

## Context

- Upstream expects a bearer token in `RENDER_API_KEY`; the Bex bridge's analogous override therefore accepts only an already-issued short-lived access token.
- Headless Bex callers use a Hydra `client_credentials` exchange from a Bex API-key id/secret pair and should keep the issued access token in memory for the job.
- The CLI must describe its `~/.bex/cli.yaml` isolation and its retained upstream Render-branding limitations honestly.

## Steps

1. Add release/build packaging for the `bex` executable on supported platforms.
2. Document install, `bex login`, active-workspace selection, config/path overrides, local API override, and logout behavior.
3. Document CI's client-credentials exchange and the safe way to pass the resulting temporary bearer to the launcher.
4. Point users who need fully Bex-branded text or dedicated client identity to the explicitly deferred fork/extension decision.

## Files

- release/build workflow or Goreleaser configuration
- `README.md`
- `docs/` CLI documentation

## Acceptance criteria

- [ ] A documented supported-platform install path produces a runnable `bex` binary.
- [ ] Docs distinguish a Bex API-key client secret from a temporary bearer token.
- [ ] Docs name `~/.bex/cli.yaml` and all supported `BEX_*` controls.
- [ ] Docs do not promise full Bex branding or unsupported server capabilities.

## Out of scope

- Publishing a Homebrew formula or changing Render's upstream release channel unless a release decision explicitly authorizes it.
