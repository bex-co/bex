# 072 — An image web service whose process binds a port other than its `EXPOSE` never goes live

Why: Render detects the port a web service's process actually binds. In bex, a prebuilt image that declares `EXPOSE 80` but is told to listen on 3000 hangs in `update_in_progress` forever, so a working Render recipe never serves on bex.

## Repro (production, 2026-11-02, found during w9/m166 t005)

```sh
bex services create --name "$UNIQUE_QA_NAME" --type web_service \
  --runtime image --image docker.io/traefik/whoami:v1.11.0 \
  --plan free --region frankfurt --env-var WHOAMI_PORT_NUMBER=3000 \
  --auto-deploy=false --health-check-path /health \
  --max-shutdown-delay 5 --confirm -o json
```

What happened to fixture `srv-dbk591vksmps739gb5eg` in `bex-canary` (since deleted, with absence verified):

- The deploy `dep-dbk591vksmps739gb5f0` stayed `update_in_progress` for more than 10 minutes, and HTTPS returned 503 from the activator.
- The app logged `Starting up on port 3000`.
- The pod had `containerPort: 80`, and its startup probe ran `health-probe check --port 80 --path /health`, failing 32 times with `dial tcp …:80: connect: connection refused`.
- The same recipe went live on 2026-09-22 (w9/m166 t001), before w8/205 made new image web services `web-image-v1`.

## Root cause — first hypothesis disproved (2026-11-02, second repro)

The first diagnosis is **wrong**. It said that `explicitServingPort` (`port_detect.go:67`) skips detection for `web-image-v1`. That function only gates the non-image w8/177 path. Image web services choose their port in `selectWebImageHTTP` (`lego/operator/internal/controller/web_image_http.go:95`), and that function already handles this case:

1. It probes the declared ports for HTTP.
2. If none answers, it runs a full `portscan.Dialer.Scan` (512 workers, 400 ms per dial, inside `portDetectTimeout` = 15 s) and probes every open port it finds.

**Second repro**, on the current operator (`bex-controller-manager` image `sha256:e1b8dff…`, rolled about 10:05Z), with the same command (fixture `srv-dbk5udrh2q7s738ub8v0`, since deleted with absence verified):
- the App ended with `status.imageNetwork = {ports:[80], primaryPort:80, httpSelection:"fallback"}`;
- `Ready=False HealthCheckFailing … GET /health on port 80`;
- the deploy stayed `update_in_progress` and HTTPS returned 503;
- the app logged `Starting up on port 3000`.

So the bounded scan found no HTTP listener on 3000 within the 90 s discovery window.

**Ruled out:**
- **Network policy.** `allow-operator-probe-ingress` admits `bex-system` `control-plane=controller-manager` pods on all ports.
- **A missing scanner.** `cmd/manager/main.go:355` wires `portscan.Dialer{}`.

**Strongest remaining hypothesis.** `Dialer.Scan` returns `nil, ctx.Err()` when the 15 s deadline passes, discarding any ports already found. If, cross-node in production, closed-port dials time out (400 ms) instead of being refused, a 65535-port sweep cannot finish in 15 s. Every scan then errors, and selection falls back after the window.

ADR018's port row already says that hosted acceptance of the runtime detection "remains pending", so this path may never have worked in production.

**Side observation.** cert-manager hit an ACME `429` rate limit ordering this service's own certificate (`certificaterequest …-port3000-tls-1`). Serving was unaffected, because the wildcard serves `*.onbex.co`. This may deserve its own note if per-service orders keep failing.

## Expected (Render)

Render's [web-service port binding](https://render.com/docs/web-services#port-binding) detects the port the process binds. When the declared or selected port has no listener and exactly one other port answers, bex should record `status.detectedPort` and serve on it, as it already does for non-image web services.

An explicit port or an effective `PORT` must still win. A declared port that is actually listening must still be preferred.

## Next steps (once unblocked)

1. Measure one `Dialer.Scan` against a running pod from the operator's network position: duration, refused vs timed-out dials, and the error returned.
2. Then fix the actual cause. Candidates:
   - return the partial `open` set on deadline instead of `nil`;
   - order the scan so likely ports come first (common HTTP ports, then ascending);
   - give the scan its own longer budget than `portDetectTimeout`;
   - treat timeouts as a reachability verdict without sweeping every port.
3. Add an operator unit test with a scanner that times out on closed ports.
4. Acceptance: the repro command goes live and serves 200, and the ADR018 port row gets its hosted-acceptance evidence.

## Blocked (2026-11-02)

**Gate:** step 1 needs in-cluster access on production. Either `kubectl exec` into the `bex-system/bex-controller-manager` pod, or a short-lived debug pod in `bex-system` carrying the `control-plane=controller-manager` label so the probe policy admits it. That is privileged production-infra access, so this drain does not take it on its own authority.

An alternative is to reproduce on a local CAPD cluster with Cilium, if it matches production's datapath.

## Unblock review, 2026-11-04 (review conclusion, via `/unblock w9`)

**Conclusion.** No privileged production access is needed, so the in-cluster diagnosis gate is withdrawn. This is a technical choice, recorded as a review conclusion, not a user decision.

**Reference.** Render detects the port a web service's process actually binds ([web-service port binding](https://render.com/docs/web-services#port-binding)).

**Worker next steps.** Fix the most likely cause directly:
- `portscan.Dialer.Scan` returns `nil, ctx.Err()` on its deadline and so discards the open ports it already found. Make it return partial results.

- Give the web-image scan a budget that fits a full sweep.
