## Objective

Define and implement the compatibility-safe identity contract that makes Postgres names mutable: Kubernetes object identity stays immutable, the user-facing name becomes CR intent, and legacy Database CRs continue to read exactly as they do before backfill.

## Context

- `lego/types/v1alpha1/database_types.go` has no name field; `metadata.name` currently serves as API id, display name, CNPG Cluster name, Secret prefix, public hostname, backup prefix, and recovery source.
- `docs/ADR020-identifiers.md` says ids are stable and names mutable, but records managed datastores as a deliberate name-as-id exception.
- Kubernetes cannot rename `metadata.name`. Recreating a Database CR would cascade into CNPG/PVC/Secret ownership and is forbidden for this migration.
- Target contract: add an optional `Database.spec.name`; reads use `spec.name` with `metadata.name` as the legacy fallback. New API-created databases use `metadata.name = id.New(id.Postgres)` (`dpg-…`) and `spec.name = <user name>`. Existing CR metadata names remain their stable, grandfathered ids.

## Steps

1. Register `id.Postgres` with Render's `dpg` prefix in the closed id registry and extend its guard expectations through the existing registry-wide tests.
2. Add the optional mutable display-name field and validation markers to the Database CR contract; regenerate deepcopy/CRD manifests from `lego/operator/`.
3. Introduce one shared backend helper for the effective display name (`spec.name`, else `metadata.name`) so legacy fallback cannot drift between adapters.
4. Update ADR009/ADR020 design notes in the working change enough to pin the compatibility invariant before downstream call sites are rewritten.

## Acceptance criteria

- [ ] `id.New(id.Postgres)` produces a registered, DNS-safe `dpg-<20-char-xid>` through the only allowed mint path.
- [ ] A Database with `spec.name` exposes that value as its display name; an existing Database without it still exposes `metadata.name` with no behavior change.
- [ ] The CRD schema accepts the new field and generated files are current (`make manifests generate`).
- [ ] The design explicitly forbids deleting/recreating legacy Database or CNPG resources as a rename/migration mechanism.

## Out of scope

- KeyValue/`red-…` identity and KeyValue rename; ADR020 must keep that sibling gap explicit rather than silently claiming all datastore ids are fixed.
