## Objective

Run the standing user-surface parity gate: verify that the new rename semantics match Render where applicable and that bex's five surfaces do not disagree on identity, validation, or errors.

## Context

- The motivating client is the unmodified official Render CLI, whose generated contract sends an optional `name` in `PostgresPATCHInput` and resolves names to opaque ids.
- REST, GraphQL, MCP, and dashboard operations all sit over the same core; parity is behavioral, not merely that fields compile.
- Legacy Database ids are intentionally grandfathered while new ids are Render-shaped `dpg-…`; this compatibility distinction must be visible and tested, not hidden.

## Steps

1. Compare create/list/get/update output and rename error behavior with the pinned CLI/OpenAPI/observed Render contract.
2. Exercise REST, GraphQL, MCP, dashboard, and CLI rename paths against the same resource and compare id/name/error results.
3. Check mixed partial updates, dry-run, duplicate/invalid name, stale old-name resolution, cross-workspace access, pagination/cursors, and project/environment membership.
4. Confirm physical connection info and database data remain reachable and stable after the resource-name change.
5. Fix drift in scope; record genuinely adjacent gaps as follow-up PM work rather than silently diverging.

## Acceptance criteria

- [ ] All five surfaces return the same stable id and renamed display value for the same resource.
- [ ] Error statuses/shapes are consistent and the official CLI prints actionable messages.
- [ ] Rename does not change connection details, project/environment membership, pagination identity, or authorization target.
- [ ] Any accepted Render divergence is explicit in ADR/checklist evidence with an owner.
