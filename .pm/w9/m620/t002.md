## Objective

A Developer reads the workspace's billing details (usage, estimated and real cost, invoices, credit grants, billing readiness) and a Contributor or Viewer reads none of them, on every surface.

## Context

- `lego/backend/internal/usage/service.go:288` (`MonthToDate`, `AuditVerbMonthToDate`) on `can_view` today, so a Viewer and a Contributor read usage and the estimate; `:321-327` and `:381` attach the Stripe projection only for `can_manage_billing`, so a Developer gets no invoices.
- `lego/backend/internal/billing/service.go:262` (`Status`, billing readiness) on `can_manage_billing`; `:224` and `:241` (Checkout, Portal) stay.
- `lego/backend/internal/workspaces/pipeline.go:84` `SetPipelineSpendLimit` stays `can_manage_billing`.
- Surfaces: REST `GET /v1/usage`; GraphQL `usage`, `workspaceBillingReadiness`; MCP `get_usage`, `get_billing_readiness` (`lego/backend/internal/api/key_permission_ops.go` maps them to `KeyWorkspaceSettings`).

## Steps

1. Gate `MonthToDate` on `can_view_billing`, and attach the billing projection for `can_view_billing`.
2. Gate the readiness read on `can_view_billing`.
3. Check that the API key catalog level covering these reads caps a key at its creator's `can_view_billing`.

## Acceptance criteria

- [ ] A Developer's `GET /v1/usage` carries the billing projection; a Contributor's and a Viewer's answer 403 on REST, GraphQL and MCP.
- [ ] A Developer still cannot open Checkout or the Portal or change the spend limit.
