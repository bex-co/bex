## Objective

When an automation run settles, email the automation's creator if the setting asks for that outcome. A run fails when its session ends `failed`/`canceled` or the run is `failed_create`/`denied`; it succeeds when its session ends `succeeded`. Repeated failures are rate-limited the way Devin does it.

## Context

- Devin: failure notifications back off — sent after the 1st, 3rd, 9th… consecutive failure, resuming on the next success (Devin release notes, 'failure notification backoff').
- A session carries the automation that started it: `store.AgentSession.AutomationID` (`lego/backend/internal/store/agentsessions.go:208-210`).
- Run settling: `lego/backend/internal/agentsessions/automation_run.go`, `automation_scheduler.go`.
- Email delivery: `lego/backend/internal/notifications/alert_email_worker.go`, `delivery_policy.go`; session phases already feed push via `push_worker.go:466-512`.

## Steps

1. Track consecutive failed runs per automation (reuse the scheduler's failure count if it already counts session failures; otherwise add one, reset on success).
2. On a session reaching a terminal phase with a non-empty `AutomationID`, and on `failed_create`/`denied` runs, decide: `always` → send; `on_failure` → send only on failure and only when the consecutive-failure count is 1, 3, 9, 27…; `on_success` → send only on success; `never` → nothing.
3. Send through the existing email worker with an idempotency key per run so a retry or a second replica does not send twice. The email names the automation, the outcome, the fire time and links the session and the automation page.
4. en and zh email copy, following the existing alert-email templates.

## Files

- `lego/backend/internal/agentsessions/automation_run.go`, `automation_scheduler.go`
- `lego/backend/internal/notifications/alert_email_worker.go` (or a sibling `automation_email.go`), `delivery_policy.go`
- the email template files the alert worker already uses

## Acceptance criteria

- [ ] With `on_failure`, failures 1–9 send exactly three emails (1st, 3rd, 9th); a success resets the count.
- [ ] With `on_success`, a failed run sends nothing and a succeeded run sends one email.
- [ ] A redelivered settle (same run) sends no second email.
- [ ] Real-Postgres or service-level tests prove each of the above.

## Out of scope

- Push notifications for ordinary run outcomes (the session's own push already exists).
