### Producer → server → consumer

Line numbers below are at the diagnosis HEAD.

- Pinned upstream `cmd/serviceupdate.go:31-49` normalizes flags and runs the confirmed noninteractive update; `pkg/service/update.go:16-66,149-156` constructs one presence-aware request containing both settings, with no client-side health-prefix rejection.
- Pinned upstream `pkg/client/client_gen.go:20728-20754` builds `PATCH /services/{id}`; `pkg/service/repo.go:103-113` checks `client.ErrorFromResponse` before consuming JSON200. A 400 means command failure, not partial success output.
- `lego/backend/internal/apps/rest.go:952` calls `ApplyServicePatch`; `:974-1014` maps the nested request fields. There is no whole-request preparation phase.
- `lego/backend/internal/apps/settings.go:125-310` has **22 ordered rows**. Display name (`:127-130`) and shutdown delay (`:178-181`) execute before health validation (`:215-218`). `ApplyServicePatch` (`:322-338`) runs each setter immediately through `core.PatchOps`.
- `lego/backend/internal/core/patchops.go:46-58` stops at the first failing closure; earlier closures are already committed.
- `lego/backend/internal/apps/service.go:3924-3938` authorizes then rejects the relative health path. By then `SetMaxShutdownDelay` (`:3945-3955`) has persisted the new value through `recordedPatch`; `SetDisplayName` (`:4194-4202`) has updated store/CR for variant A.
- `service.go:4311-4330` applies the CR change and records its configuration audit. `settings.go:324-328` defers the rollout batch flush even on an error, so the successful early write produces a real deploy row. Removing this flush would only conceal the already-applied runtime change.
- The second production caller is MCP `update_service` at `lego/backend/internal/apps/mcp.go:867`. GraphQL/dashboard use the individual setters; they do not promise one transaction across independent mutations.

## Steps

1. Add a regression demonstrating both field pairs against real apps state/deploy storage, asserting the unchanged before/after state as well as the error.
2. Prepare the complete proposed patch and run all relevant validation, policy, confirmation, and permission checks before the first store/CR write. Reuse the setters' canonical validators rather than inventing REST-only rules. Account for proposed combined state, presence/clear semantics, source/registry credentials, and maintenance-before-free-downgrade behavior.
3. Apply only a prepared valid patch, keeping one appropriate rollout record and existing success/error envelopes. Do not downgrade a failure to success or hide earlier side effects from deployment history.
4. Explicitly document the remaining unexpected persistence-failure boundary. Do not claim that a preflight pass is a distributed database/Kubernetes transaction. Verify shared consumers in t002 before choosing any change to generic `PatchOps`.

## Acceptance criteria

- [ ] Invalid health combined with a valid name or shutdown delay returns the same 400 body/nonzero CLI result and leaves settings, revision, deployment count, and successful-change audit count unchanged.
- [ ] A later authorization/policy/type refusal cannot apply an earlier otherwise-permitted setting. Preserve existing unauthenticated 401 and non-disclosing missing/unauthorized behavior; do not introduce existence leaks.
- [ ] Valid combined updates still succeed, honor clears/omissions and coupled-state validation, and produce one config-change deployment when appropriate. A working HTTPS response after convergence is required, not merely an ID or 2xx response.
- [ ] Timeout/unavailable/persistence errors remain errors and do not claim successful application or certainty about an unobserved commit.
- [ ] Both real REST and MCP entry points are covered; single-field callers retain policy/permission behavior. No CLI fork, request repair, or launcher workaround.
