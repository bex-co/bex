## Objective

Prove the fix handles the shared mutation boundary, not only the demonstrated health/shutdown pair, without weakening existing callers' policies.

## Context

`ApplyServicePatch` has two production callers (REST and MCP) and a 22-row operation table. `core.PatchOps` has three production consumers: apps/settings, projects/MCP, and environments/MCP. The apps table serves web, private, worker, cron, and static services with different field eligibility; Postgres and Key Value use separate implementations.

## Steps

1. Recount call sites and aliases, enumerate all table fields and the validators/permission checks they use, and identify any side effect that still occurs during preparation.
2. Exercise failures late in representative field groups: invalid scalar, inapplicable service kind, plan eligibility, source/credential permission, and protected-environment confirmation. Check all earlier settings and side-effect counters remain unchanged.
3. Verify coupled valid state (maintenance disabled while downgrading; source and matching registry credential), empty patches, nil versus explicit clear, and no-op values. Use local fixtures for paid-plan policy coverage, never a paid production purchase.
4. Verify direct GraphQL/dashboard setters retain their guards. Leave projects/environments on their existing contract unless a deliberately shared change is proved safe and coordinated with w7/m152.

## Files

- `lego/backend/internal/apps/settings.go`, `service.go`, `graphql.go`, `rest.go`, `mcp.go` and their policy/patch tests
- `lego/backend/internal/core/patchops.go`, `internal/projects/mcp.go`, `internal/environments/mcp.go`
- `dashboard/src/` callers of the changed service-setting mutations (inventory actual paths)

## Acceptance criteria

- [x] A concrete caller/field/service-kind inventory accompanies results; no speculative claim that unrelated datastore APIs are affected.
- [x] Failure and success checks cover both adapters and shared direct setters, including unchanged authorization and nondisclosure behavior.
- [x] No generic rollback behavior is introduced without proving all three `PatchOps` consumers' contracts.

## Out of scope

- Expanding into the separately filed project/environment or disk row/CR bugs.

## Result (2026-09-22)

### Caller / consumer inventory (recounted, not assumed)

`ApplyServicePatch` has exactly **two** production callers, both unchanged in
shape: `rest.go:952` (`PATCH /v1/services/{id}`) and `mcp.go:868`
(`update_service`).

`core.PatchOps` has exactly **three** production consumers:
`apps/settings.go`, `projects/mcp.go:127`, `environments/mcp.go:149`.
**`patchops.go` was not modified**, so the projects/environments contracts are
untouched and w7/m152 needs no coordination.

GraphQL — and therefore the dashboard — does **not** go through the patch
table. It calls **24** setters one setting at a time (`SetAutoDeploy`,
`SetAutoscaling`, `SetBuildFilter`, `SetCommands`, `SetCronJob`,
`SetDisplayName`, `SetDockerfilePath`, `SetHeaders`, `SetHealthCheckPath`,
`SetIPAllowList`, `SetIdleTTL`, `SetMaintenanceMode`, `SetMaxShutdownDelay`,
`SetNotificationsToSend`, `SetNotifyOnFail`, `SetPlan`, `SetPort`,
`SetPreDeployCommand`, `SetPublishPath`, `SetRegistryCredential`, `SetRoutes`,
`SetRootDir`, `SetSourceAndRegistryCredential`, `SetSubdomainPolicy`). Those
keep their existing per-setting policy and error contracts: the setters were
refactored to CALL the extracted checks, not to lose them.

Service kinds: the table serves web, private, worker, cron and static. Postgres
and Key Value have separate implementations and are untouched.

### Side effects during preparation

The preflight is read-only. Verified by assertion, not by inspection:
`TestPreflightItselfWritesNothing` pins that a five-row preflight patches no CR
(resourceVersion stable) and writes no control-plane row (displayName, idleTTL
and deploy row counters all zero). The reads it performs —
`GetAppProtectedStatus`, `RequirePlanBilling` (payment-method + billing-mutation
checks), `validateExternalRegistryCredential`, `GitHub.ValidateRepo`,
`hostClaimedElsewhere` — are all non-mutating. The registry credential is
*validated*, never *materialized*: `TestRESTRegistryCredentialCreatePatchAndClear`
pins the materialization counter, and it still reads 1 (create's only).

The one real side effect is an authorization DENIAL audit row, which is
recorded once, by the preflight, instead of once by whichever setter used to
reach it first.

### Late-failure coverage across classes

`TestLateRefusalClassesApplyNoEarlierField` exercises five distinct refusal
classes, each paired with a valid earlier `displayName`, each asserting the
rename did not happen and the CR was not written:

| class | case |
| --- | --- |
| invalid scalar | health path without a leading `/` |
| inapplicable service kind | health path on a `cron_job` |
| plan policy | background worker downgraded to `free` |
| protected environment | root dir without the confirmation phrase |
| source validation | malformed repo URL |

All five were **mutation-checked**: with the preflight removed, all five fail.

### Coupled valid state, clears and no-ops

`TestPreflightValidatesCoupledStateAsProposedNotAsStored` (disable maintenance
+ downgrade to free, on the core verb) and the pre-existing
`TestMaintenanceMode{REST,MCP}PlanTransitions` confirm the preflight validates
the PROPOSED combined state. Source + matching registry credential is covered
by `TestRESTRegistryCredentialCreatePatchAndClear`; empty patch by
`TestPreflightLeavesEmptyPatchAReadOnlyNoOp` and
`TestRESTPatchEmptyBodyIsReadOnlyNoOp`; nil-vs-explicit-clear by
`TestUpdateServiceLeavesOmittedFieldsAlone`.

### Non-disclosure

`TestPreflightKeepsUnauthorizedAndMissingIndistinguishable` pins that the
up-front authorization did not turn the patch surface into an existence oracle:
a stranger gets a byte-identical error for a service that exists and one that
does not.
