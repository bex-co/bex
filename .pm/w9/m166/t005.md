## Boundary found on rebase — the store's name-conflict refusal (2026-09-27)

Rebasing onto main picked up w8/m47, which made `SetAppDisplayName` refuse a
name another service in the workspace already uses. That refusal is raised by
the **store, during the write** — not by a check the preflight can run — so it
is the one patch refusal that still lands mid-apply rather than up front.

It is harmless today **only because `displayName` owns the first table row**:
nothing can have been written before it, so a conflicted rename applies nothing
else and mints no deploy. `TestDisplayNameConflictAppliesNoOtherField` pins
that, and deliberately asserts the *later* field too, so it guards the table
order as much as the refusal.

Worth knowing rather than fixing: a uniqueness precheck would be TOCTOU (the
store constraint has to stay the real guard regardless), and moving the
displayName row would reintroduce the exposure. If a future row with a
store-raised refusal lands anywhere but first, it needs a preflight check or
the same row-order argument.

This also exposed a limit of the check/verb agreement guard: it skips rows whose
`check` is nil, so a verb that GAINS a refusal while its row has no check is not
flagged. That is how this arrived unnoticed.
