# Sign off, drop or widen the Admin's view of every member's API keys

Why: w9/m539 gave every role Render's own-keys list and kept one bex addition, an Admin's opt-in view of every member's keys with revoke; a divergence from Render stands only with the user's sign-off in ADR018 (AGENTS.md, Render parity first).

**What shipped (w9/m539, 2026-11-20).** Every role's API keys list on REST, GraphQL, MCP and the dashboard is the keys the caller minted, as on Render's Account Settings. An Admin may also ask for every key in the workspace (`GET /v1/api-keys?allMembers=true`, `apiKeys(allMembers: true)`, MCP `list_api_keys` with `allMembers`, the dashboard's "All members' keys" switch) and revoke any of them. Only a key's creator edits its grant. [ADR018](../../../docs/ADR018-render-parity.md)'s API keys row records the Admin view as a divergence pending your sign-off; [ADR024](../../../docs/ADR024-members.md#every-member-mints-and-manages-their-own-api-keys-w9m514) has the reasoning.

**Why bex kept it.** Render has no such view ([api-keys](https://render.com/docs/api-keys), [team-members](https://render.com/docs/team-members), re-read 2026-11-20; its only admin view of members' keys is the enforce-SSO report in [saml-sso](https://render.com/docs/saml-sso), which bex has as the login-requirement impact list). A departed member's keys need none, because every exit from a workspace revokes them (w2/m163). Two kinds of key would otherwise be unrevokable from the product: a demoted member's keys (a demotion ends no membership, so the key follows its creator down and nothing revokes it) and keys with no recorded creator (no one's own; production held 16 such `m35-*` fixtures on 2026-11-18, w9/119).

**The decision needed from the user** (pick one):

1. **Keep it.** Sign off the divergence in ADR018's API keys row; the worker turns "pending the user's sign-off" into the dated decision.
2. **Drop it (stricter, Render's exact behavior).** Remove `allMembers` from the three surfaces and the dashboard switch. A demoted member's keys are then revoked only by that member, and creator-less keys only by an operator; decide whether a demotion should revoke the member's keys instead.
3. **Widen it (looser).** Also let an Admin edit another member's key's grant (narrow it without revoking), which bex allowed until w9/m539 and Render does not show.

**Testable end state.** ADR018's API keys row names the user's dated decision instead of "pending the user's sign-off", and the code matches it: for 1, no change; for 2, `allMembers` answers 400 or is gone on every surface and the switch is gone; for 3, an Admin's `PATCH /v1/api-keys/{id}` on another member's key answers 200 within that creator's role on REST, GraphQL and MCP.
