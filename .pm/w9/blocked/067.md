# 067 — `bex ea sandboxes create --env-var` is refused by naming an internal JSON field

Why: two of the six documented flags on a supported command fail 100% of the time, and the refusal names a wire field the user never typed instead of the flag they did — bex already has a better pattern for this exact situation one field away.

Live, 2026-09-21, production, `bex v0.2.1` / pin v2.27.0, workspace `bex-canary`:

```text
$ bex ea sandboxes create --timeout 600 --env-var QA_MARKER=qa-4763a134 --confirm
Error: received response code 400: request body contains unknown field "env"

$ bex ea sandboxes create --timeout 300 --env-file ./envfile --confirm
Error: received response code 400: request body contains unknown field "env"

$ bex ea sandboxes create --timeout 300 --network-policy deny-all --confirm   # control
{ "id": "f757d6f9-…", "networkPolicy": {"default": "deny-all"}, "status": "running", … }
```

`--env-var` and `--env-file` are documented in `bex ea sandboxes create --help` and in its own examples (`bex ea sandboxes create --env-var FOO=bar --env-var BAZ=qux`). Neither can ever succeed.

## Mechanism

- The pinned client sends `env` as a first-class create field, and only when non-empty — which is why a create with no env vars succeeds: `pkg/sandbox/service.go:91-93`, `if len(input.Env) > 0 { body.Env = &input.Env }`.
- bex-api's create body struct has no `env` field — `lego/backend/internal/sandbox/rest.go:37-44` declares only `ownerId`, `plan`, `template`, `region`, `timeoutSeconds`, `networkPolicy` — and `rest.go:47` turns on strict decoding (`core.WithStrictJSONDecoding`), so any other key is a 400 from `core/http.go:222`.

## Two separable things

1. **The refusal is wrong regardless of scope.** bex already has the right pattern for a sandbox option it will not honor: `allow-all` is "a deliberate named 400 (`SANDBOX_NETWORK_POLICY_UNSUPPORTED`) because bex will not claim an unenforced policy" (`docs/cli-compatibility-checklist.md` row 271). `env` and `snapshotId` should refuse the same way — naming the feature and the flag — instead of leaking an internal field name. This part is ~30-45m and needs no scope decision.
2. **Whether to support sandbox env vars at all** is a real decision, not a bug fix. If the answer is yes, promote this to a milestone — plumbing env into the sandbox runtime is well over an hour.

Note `--snapshot-id` fails identically (`request body contains unknown field "snapshotId"`) but is **already graded `[-]`** in the checklist — "early-access sandbox surface outside the bex `ea` compat target" — so it is a documented non-goal and only item 1 applies to it. `--env-var`/`--env-file` are **not** graded anywhere, on a command whose siblings (`create`/`list`/`exec`/`stop`) are `[x]`.

## Not in this note

- `ea sandboxes exec` is healthy and was re-verified in the same sweep: `exec <id> -- sh -c 'exit 7'` exits 7, `-- true` exits 0, and an unknown id exits 1 with `received response code 404 (SANDBOX_NOT_FOUND): sandbox not found` — matching the `w7/m147` contract.
- The same sweep re-confirmed `w9/m94`'s deploy gate is still unmet: production still mints bare UUID sandbox ids (`bf642a94-e9ed-489f-a63e-35ad81932c7a`), not `sbx-<xid>`. That is m94 t004's existing blocker, not a new finding.

## Done 2026-09-21 (`/loopx w9`) — item 1 shipped; item 2 is yours

**Item 1 (the refusal) is fixed.** `env` and `snapshotId` are now declared on
the create body purely so they can be refused **by name**:
`SANDBOX_ENV_UNSUPPORTED` names `--env-var`/`--env-file`, and
`SANDBOX_SNAPSHOTS_UNSUPPORTED` names `--snapshot-id` — the same shape as the
existing `SANDBOX_NETWORK_POLICY_UNSUPPORTED`, instead of strict decoding's
`unknown field "env"`, which named an internal wire key the user never typed.
Declaring the fields costs nothing: neither is ever read into `CreateRequest`,
and a create without them is untouched (pinned by
`TestCreateWithoutUnsupportedOptionsStillSucceeds`, since the client only sends
`env` when non-empty). Guards in `internal/sandbox/publicid_test.go` assert the
code, that the message names the flag, and that it no longer leaks the wire key.
`docs/cli-compatibility-checklist.md` gains a `[~]` row for the two flags.

Not live-verified: dev-9 runs without `BEX_OPENSANDBOX_URL`, so the sandbox
routes are not mounted there at all (`404`), and the production token is expired
(the same gate as `w9/blocked/m94`). The unit tests drive the real REST handler.

**Item 2 — whether bex should support sandbox env vars at all — is untouched
and is yours.** It is a scope decision, not a defect: plumbing env into the
sandbox runtime is well over an hour and would be a milestone. Until then the
flags fail honestly instead of confusingly.
