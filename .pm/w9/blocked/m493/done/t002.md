## Objective

Persist `/opt/render/.cache` between native builds of the same App using w9/m492's S3 build-cache store while preserving BuildKit credential isolation and honoring `clearCache: "clear"`.

## Context

- Because native recipes execute `COPY . .` before the authored build command, BuildKit layer caching alone cannot retain `$XDG_CACHE_HOME` across source edits.
- Reuses w9/m492's S3 bucket and `<tea-id>/<app-uid>/` prefix (`<tea-id>/<app-uid>/xdg-cache.tar.zst`), still fetched/uploaded only by the credentialed `cache-restore`/`cache-save` phases so BuildKit holds no S3 credentials.
- Exported `/opt/render/.cache` must be bounded by a size cap so a runaway build cannot bloat cache transfer or pod ephemeral storage.

## Steps

1. In `cache-restore` (when `BEX_BUILD_CACHE=s3` and `!SkipCacheImport`), best-effort download and extract `<tea-id>/<app-uid>/xdg-cache.tar.zst` into a dedicated emptyDir mounted as a read-only named BuildKit build context (`--opt context:xdg-cache=...`).
2. In `native.go`, seed `/opt/render/.cache` from that build context before running the authored build command, and export the updated `/opt/render/.cache` to a dedicated build-output volume (or multi-output target) without copying it into the final runtime image.
3. In `cache-save`, compress and upload `/opt/render/.cache` to `<tea-id>/<app-uid>/xdg-cache.tar.zst` when within the size cap; in `cache-purge` (`SkipCacheImport`), delete `<tea-id>/<app-uid>/xdg-cache.tar.zst`.
4. Confirm App deletion in `app_controller.go` already removes the full `<tea-id>/<app-uid>/` prefix including `xdg-cache.tar.zst`.

## Acceptance criteria

- [x] A file written into `$XDG_CACHE_HOME` during build 1 is present in `$XDG_CACHE_HOME` at the start of build 2 after a source-only edit.
- [x] `SkipCacheImport` (`clearCache: "clear"`) purges `xdg-cache.tar.zst` and starts build 2 with an empty `/opt/render/.cache`.
- [x] BuildKit holds zero S3 credentials; missing, oversized, or corrupt archives never fail a build.

## Out of scope

- Per-runtime `/opt/render/project/...` dependency directories (w9/m494) and Node `node_modules` (w8/m161).

## Done — 2026-11-18

- `cache-restore` lists then downloads `<workspace>/<app-uid>/xdg-cache.tar.gz` into `/xdg-in` beside the layout, in parallel and under the phase's one deadline; `cache-save` uploads `/xdg-out/xdg-cache.tar.gz`; a clear-cache release's `cache-purge` deletes it (`lego/operator/internal/build/xdgcache.go`, `s3cache.go`). App deletion's `cache-purge-<app>` Job already deletes the whole `<workspace>/<app-uid>/` root (`CachePurgeJob`), archive included.
- **Deviation from the plan:** BuildKit gets no named context. Any input of the build command's step is part of its cache key, so an archive that changes every build would cost every build its "Reusing the cached result". The buildkit phase instead points `buildctl-daemonless.sh` (`$BUILDCTL`) at a wrapper that runs two solves of its own against the pod's one daemon (GC off): a seed solve before the image's and an export solve after it. Both run on the final stage's own base image. The archive is `.tar.gz`, not `.tar.zst`: it is made and unpacked inside BuildKit on the toolchain image, and Debian's base images ship gzip but no zstd.
- BuildKit still holds no credential; missing, oversized and corrupt archives build cold (t003).
- Proven on real BuildKit `v0.30.0` against an S3 endpoint (ADR060 D3 w9/m493 drill): build 2 read build 1's file after a source change, a same-source build stayed `CACHED`, a clear-cache build started empty.
