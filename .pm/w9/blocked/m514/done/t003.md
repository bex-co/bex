## Objective

Render manages keys on each person's Account Settings, so a Viewer, Contributor or Billing member sees and controls the keys they minted. Developer and Admin keep the workspace-wide list and revoke.

## Context

- `ListAPIKeys`, `RevokeAPIKey`, `UpdateAPIKeyPermissions`, `revokeScope` and `requireKeyIn` (`lego/backend/internal/apikeys/service.go`); the key's `createdBy` comes from Hydra's `bex.co/created-by` stamp and `tenant_members.created_by`.
- `UpdateAPIKeyPermissions` already admits the key's creator or a workspace Admin past `can_manage_keys`.
- A Developer demoted to Viewer keeps their keys, now at Viewer (m481); this task gives them back list and revoke.

## Steps

1. Gate the three verbs on t001's mint relation, then filter or refuse by ownership when the caller lacks `can_manage_keys`.
2. Keep the existing refusal shapes: another workspace's key `ErrNotInNamedWorkspace`, an unbound key 404, another member's key the shape t001 picks.
3. REST, GraphQL and MCP answer the same.

## Files

- `lego/backend/internal/apikeys/`, tests beside them

## Acceptance criteria

- [ ] A Viewer lists only their own keys in the workspace; a Developer and an Admin list every key there.
- [ ] A Viewer edits and revokes their own key and is refused another member's, on all three surfaces.
- [ ] Revoking a Viewer's key answers 401 on its next request.

## Out of scope

- Narrowing a Developer's or Admin's view to their own keys (t007 files it if Render's evidence calls for it).

## Record (2026-11-19)

- `ListAPIKeys` gates on `relOwnKeys`, then shows every key to a caller holding `can_manage_keys` (asked audit-silently through `Can`, failing closed to the own view) and the caller's own keys to anyone else.
- `RevokeAPIKey` and `UpdateAPIKeyPermissions` read the key first (`keyRelation`) and make their one `Authorize` with `relOwnKeys` for the caller's own key, `can_manage_keys` otherwise; `requireKeyIn` and the creator-or-Admin edit rule are unchanged. `UpdateAPIKeyPermissions` reuses that read instead of its own second Hydra GET.
- Shapes: another member's key 403 (audited once against `can_manage_keys`), another workspace's key `ErrNotInNamedWorkspace`, an unknown key as before. REST, GraphQL and MCP answer the same (e2e and dev-9).
- MCP tool descriptions for `create_api_key`, `list_api_keys` and `revoke_api_key` say who may do what.
- Tests: `TestABelowDeveloperMemberListsOnlyTheirOwnKeys`, `TestABelowDeveloperMemberEditsAndRevokesOnlyTheirOwnKeys`, `TestOwnKeysStayInTheirWorkspace`, `TestAKeyOwnsNoKey`, the e2e on three surfaces; a revoked Viewer key answers 401 on dev-9.
