## Objective

When a workspace's billing period closes, charge each cron job that owes the minimum the difference between $1 and its run charge for that period, exactly once.

## Context

- Cron run time is metered as `instance_seconds` from the cron job's runs (`lego/backend/internal/usage/service.go`, `queryCronRunSeconds`, w4/691) and priced by `pricing.Sheet` (`lego/backend/internal/pricing/`; `InstanceUSDPerMinute`, the per-tier `usdPerSecond` in `pricing.yaml`).
- Usage reaches Stripe through `usage_hourly` rows and the emitter (`lego/backend/internal/billing/emitter.go`), with deterministic identifiers and a seal horizon; period close and settlement live in `billing/settle.go` (`Settler.SettleWorkspace`, `Emitter.ExportWorkspace`).
- Precedent for a USD-denominated meter: `store.UsageKindAgentModelCostMicroUSD` (`store/agent_model_usage.go`), a micro-USD meter with a model-agnostic Stripe meter.
- The rule (who owes it, which period, proration) comes from t001's findings.

## Steps

1. Add a usage kind for the minimum (e.g. `cron_minimum_microusd`) beside the existing kinds in `store/usage.go`.
2. At the point the billing period's usage is sealed (before Stripe finalizes the period's invoice; follow how `settle.go` orders export vs. invoice), compute per cron service that existed in the period: run charge from its sealed `instance_seconds` × its tier rate (all tiers it ran on), then top-up = max(0, 1 000 000 − run charge in micro-USD).
3. Write one usage row per (service, period) with a deterministic identifier so a re-seal or a manual settle cannot double-charge; zero top-ups write nothing.
4. Respect the existing exclusions: workspaces exempt from export (comped, no payment method when required), cron jobs in workspaces before `BEX_STRIPE_EPOCH`.

## Files

- `lego/backend/internal/store/usage.go` (+ a migration if a new table or column is needed)
- `lego/backend/internal/billing/` (emitter / settle path)
- `lego/backend/internal/pricing/` (a helper to price a period's run seconds, if none exists)

## Acceptance criteria

- [x] A cron job with zero run seconds in a period yields exactly one $1.00 top-up row for that period.
- [x] A cron job whose run charge is ≥ $1 yields no row.
- [x] Re-running the seal for the same period writes nothing new.
- [x] Web services, workers, private services and static sites are unaffected.

## Out of scope

- The Stripe meter and price (t004); dashboard copy (t005).

**Done 2026-11-16.**

- New usage kind: `store.UsageKindCronMinimumMicroUSD` (`cron_minimum_microusd`).
- Migration `0284_cron_minimum` adds the kind to both CHECKs and creates the `cron_minimum_months` record, which cascades with the tenant.
- The hourly usage sweep (`usage/cron_minimum.go`, `chargeCronMinimums`) works in two steps:
  - It records the active cron jobs (created and not suspended) each hour.
  - 49 hours after a month ends, once `CatchupWindow` has passed, it writes one top-up row per cron job (`InsertCronMinimum`, `ON CONFLICT DO NOTHING`), in the month's last hour. The top-up is max(0, minimum − the month's exact run charge in micro-USD), priced by `pricing.Sheet.ServiceInstanceMicroUSD`.
  - The sweep has its own meter cursor, so each month is charged once.
- **Deviation:** the computation sits in the usage sweep, not at the Stripe seal. Stripe periods are anchored to each subscription's start, and the rule is per calendar month. The row then rides the ordinary outbox: seal, floor, exclusions and payment-method withholding.
