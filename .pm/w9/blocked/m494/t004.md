## Objective

Verify warm runtime-dependency cache reuse, version-bump invalidation, and `clearCache: "clear"` reset on production in `bex-canary`.

## Context

- Use the QA user (`bash scripts/qa-login.sh`) in `bex-canary`.
- Park with the self-clearing pin gate if production does not yet carry t001–t003.

## Steps

1. Deploy two disposable native fixtures (e.g., Ruby and Go or Rust) on production, record cold build durations, then trigger a source-only rebuild and confirm restored dependency cache + materially faster dependency install/compile in build logs.
2. Trigger `clearCache: "clear"` on one fixture and verify cold rebuild; delete all fixtures (`GET 404`) and confirm zero leftover S3 cache objects.
3. Record pin SHA, fixture IDs, timings, and cleanup evidence in this task.

## Prepared — 2026-11-19

Everything but this check is in place: t001–t003 and t005–t007 are done, and the drill in [ADR060 D3's w9/m494 amendment](../../../../docs/ADR060-build-worker-reliability-and-performance.md#d3-amendment-w9m494--native-dependency-directories-across-builds) proved the path on BuildKit `v0.30.0` for Ruby, Go and Rust. Until the pin carries it, production's native builds reinstall their dependencies on every source change.

- **Pin:** the latest `chore(deploy): pin platform images to <sha>` commit on `origin/main`. The check starts once `git merge-base --is-ancestor "$(git log --format=%H -1 --diff-filter=A -- lego/operator/internal/build/depscache.go)" <sha>` holds. That commit sits on w9/m492's `d7e76d312` and w9/m493's `7bfd497da`, so w9/m493 t004 can run on the same pin.
- **Fixtures,** in `bex-canary` as the QA user: a native Ruby web service and a native Go web service. Each needs a lockfile whose dependencies take visible time cold: for Ruby, a Gemfile with `bcrypt`, `puma` and `rack` (build `bundle install`, start `bundle exec puma -p $PORT`); for Go, a module requiring `github.com/google/uuid` (build `go build -o app .`, start `./app`). Prefix each build command with `TIMEFORMAT='M494 took %Rs'; time ` so the build log carries the install time.
- **Warm:** build 1 is cold: the log has Ruby's `Installing … with native extensions` lines and Go's `go: downloading` line. For build 2, change a source file (a commit, or a deploy with a changed env var such as `M494_RUN=2`, which reruns the step as a source edit does). Build 2's log must read `==> Downloading cache...` and `==> Transferred …`, then no `Installing` / `go: downloading` line, and a lower `M494 took`. The running service answers 200.
- **Clear:** `bex deploys create <srv> --clear-cache` on one fixture. Its log has no `Transferred` line and installs everything again; the build after it is warm again.
- **Per build:** the phases' termination messages read `xdg miss`, then `xdg hit <bytes> <s>`, then `xdg purged` on the clear build (`kubectl -n bex-build get pod <build pod> -o jsonpath='{range .status.initContainerStatuses[*]}{.name}={.state.terminated.message}{"\n"}{end}'`).
- **Cleanup:** delete both fixtures, then check that each by-id `GET` answers `404` and `aws s3 ls s3://bex-build-cache/<tea-id>/<app-uid>/` lists nothing (endpoint `https://s3.eu-central-2.wasabisys.com`, the `bex-build/bex-build-cache-s3` credential). Record the pin, fixture ids, timings and cleanup here.
