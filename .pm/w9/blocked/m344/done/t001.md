## Objective

Decide, in the ADRs, how PR feedback reaches a session before any code: which GitHub events steer, who is allowed to, how bots and loops are handled, how review comments batch, and what the agent posts back.

## Context

- Devin: replies to comments on PRs its sessions are working on while the session is not archived; the commenter needs write or admin on the repo and a GitHub account linked to their Devin account; bot comments are ignored by default, but CI failure comments are always processed ([GitHub integration](https://docs.devin.ai/integrations/gh), [PR bot comment settings](https://docs.devin.ai/product-guides/bot-comment-settings)).
- ADR047:114 ('a PR-comment loop (webhook → resume session) as a follow-on') and ADR090 D7:115 list this as follow-up.
- Steering already exists: `Service.Steer` (`lego/backend/internal/agentsessions/service.go:1668`); a session stores its PR (`store/agentsessions.go:175` `PRNumber`).
- bex members can sign in with GitHub (Kratos GitHub OIDC), which is the account link to check.

## Steps

1. Write a new decision in ADR047 (cross-referenced from ADR090): events `issue_comment` (on a PR), `pull_request_review`, `pull_request_review_comment` and a failed `check_suite` on the session's head.
2. Authorization, following Devin: the commenter has write or admin permission on the repo (GitHub collaborator-permission API, not `author_association` alone) and their GitHub account is linked to a member of the session's workspace who has `can_create`; the turn runs as the session creator and is billed to the session.
3. Bots: ignored by default; a failed check suite on the session's head always counts. Loop guard: at most N automatic steers per head SHA, none for comments the agent itself posted.
4. Batching: review comments in one review arrive as one steer; comments within a short window coalesce.
5. Canceled or archived sessions ignore feedback. Comment text is passed as quoted, untrusted data (ADR090 D2 layer 4).
