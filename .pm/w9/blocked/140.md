# A private Postgres answers no external connection string, where Render answers one for every database

Why: w9/134 found that Render answers `externalConnectionString` for every Key Value, even one created with `ipAllowList: []`, while bex answered an empty string for a private store. Its worker reported that bex's Postgres has the same private-database gap, so a client or Terraform config that copies Render's strings would find an empty one on a private bex database.

- **Found by:** w9/134's worker, 2026-11-21 (parked in 15120987b; its Key Value fix is in stash `loopx/w9/134`, unshipped until the host's Docker answers). Not verified by the orchestrator.

## Parked (2026-11-21): verified, implemented and tested; the pre-push gate cannot run on this host

- **Render's answer, verified.** Its OpenAPI `postgresConnectionInfo` requires `externalConnectionString` and `psqlCommand`. In the Terraform provider's cassettes at pin `06af456`, the four databases created with `ipAllowList: []` (`postgres_cassette.yaml` ×2, `postgres_parameter_overrides_cassette.yaml`, `postgres_datasource_cassette.yaml`; their reads answer `ipAllowList: null`) answer `postgresql://<user>:<password>@dpg-….oregon-postgres.render.com:5432/<db>` and `PGPASSWORD=… psql -h dpg-….oregon-postgres.render.com -p 5432 -U <user> <db>` on every read, and so does `postgres_allowlist_cassette.yaml`'s database after `PATCH ipAllowList: []`. The provider's own tests match `-p 543[2,4]`. No capture of Render's dashboard for a blocked Postgres exists in `docs/render-artifacts/`, and Render's docs do not say what it shows.
- **bex's answer, read from the code.** The operator set `status.externalHost` only for a `spec.public` database (`updateExternalAddressStatus`, `database_controller.go`), and connection info gated the external string on it (`PostgresConnectionInfo`, `lego/backend/internal/postgres/service.go`), so a private database answered `externalConnectionString: ""` and a psql command over its internal host on REST and GraphQL; `TestPrivatePostgresInternalAndPSQLHostsAgree` pinned the empty string, and `docs/render-artifacts/psql-cli.md` claimed Render gates it the same way. Every Render-shaped public `psqlCommand` also lacked Render's `-p 5432`. MCP has no connection-info tool, as Render's has none. The dashboard's Connections panel shows what the read answers.
- **Choice (parity-sufficient, w9/134's shape, no sign-off needed):** the operator records `status.reservedExternalHost` (`<id>.<BEX_DB_DOMAIN>`) for every database; `status.externalHost` is unchanged. Connection info answers a private database's Render-shaped URL and `psql -h <reserved> -p 5432 …` over it, with no `sslmode`, CA or `externalCertificate` (no endpoint presents a certificate; this is the shape production answers once public and issued). pg-sni-proxy routes only `spec.public`, so the edge refuses the host from every source, and no certificate is requested. Pooled and replica external strings stay empty while private and are now gated on `spec.public` too. Render-shaped public psql commands gain `-p 5432`. The dashboard needs no code change: it shows the answered strings, and Access Control already says external connections are disabled until a rule is saved.
