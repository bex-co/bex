## Objective

Settle whether the Key Value external endpoint has the same dual-stack allow-list trap the Postgres endpoint was proven to have. The code path and the DNS shape both say yes; the live control was inconclusive, so nothing is claimed yet.

## Context

- `lego/operator/cmd/kv-sni-proxy/main.go:145` calls the same `sniproxy.AllowedBy` as the Postgres proxy (`pg-sni-proxy/main.go:248`), over the same `ParseAllowList` output (`internal/sniproxy/allowlist.go:34-65`).
- `red-<id>.kv.bex.co` resolved to the same pair as the Postgres host on 2026-09-21: `A 49.12.20.236`, `AAAA 2a01:4f8:c01e:3d1f::1`.
- Why the 2026-09-21 sweep could not settle it: `bex kv-cli` at pin v2.27.0 is interactive-only (`Error: bex kv-cli can only be used in interactive mode`) with no `--command` flag, and driving it through a bounded PTY handed off to `redis-cli` before any PING/error could be captured.
- A free Key Value only gets an external endpoint once it is published; on 2026-09-21 a non-empty allow-list on `keyvalues update` published it (`public: true`, `externalHost` set) — the `w4/m116` t002 behavior, confirmed working live.

## Steps

1. Create a disposable free Key Value in a QA workspace, publish it with an allow list holding **only** the caller's IPv4 `/32`.
2. From a dual-stack client, connect to `externalHost:6379` over TLS by the supported route (`bex kv-cli` through a real PTY, or `redis-cli --tls` directly if the CLI cannot be driven non-interactively — say which was used).
3. Record the exact failure text and whether the peer address was the v6 or the v4 literal.
4. Repeat with the caller's IPv6 `/128` added. A pass here plus a fail above proves the trap; anything else disproves it.
5. Delete the fixture and record the result in this milestone's README (replace the "Unverified — Key Value half" bullet with the finding either way).

## Outcome 2026-09-21 — PROVEN. Key Value is affected, identically.

Live `/qa-find-bugs-cli` sweep 4, ~23:17–23:30 UTC against production. `bex v0.2.1` / pin v2.27.0, workspace `bex-canary` (`tea-daif693dqjvc73e7as3g`), human device-flow OAuth. Fixture `qa-3fc0a5a7-kv` (`red-daorlsbs0ils73bgpit0`), free plan — created, published, probed and deleted in-sweep; deletion confirmed (`keyvalues list` → `[]`), baseline `hello-go` untouched.

**Route used: `redis-cli --tls` directly**, which step 2 explicitly permits. `bex kv-cli` still could not be driven non-interactively: through a bounded PTY it does successfully hand off to `redis-cli` (that tool's own password warning appears), but then blocks waiting on a real terminal, so the bound kills it (rc 143) before any PING result. That is a harness limitation, not a product failure — recorded here so the next attempt does not spend time retrying it.

DNS — the same pair as the Postgres host:

```text
red-daorlsbs0ils73bgpit0.kv.bex.co   A     49.12.20.236
red-daorlsbs0ils73bgpit0.kv.bex.co   AAAA  2a01:4f8:c01e:3d1f::1
```

Probe form (the password was read from `connection-info` straight into the command and never printed):

```text
redis-cli --tls --sni red-daorlsbs0ils73bgpit0.kv.bex.co -h <literal> -p 6379 -a <redacted> --no-auth-warning PING
```

| allow list               | peer address used (literal)  | result                                                                                                     |
| ------------------------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| IPv4 `/32` only          | `2a01:4f8:c01e:3d1f::1` (v6) | **FAIL** — `Could not connect to Redis at 2a01:4f8:c01e:3d1f::1:6379: SSL_connect failed: unexpected eof while reading` |
| IPv4 `/32` only          | `49.12.20.236` (v4)          | **PONG**                                                                                                   |
| IPv4 `/32` + IPv6 `/128` | `2a01:4f8:c01e:3d1f::1` (v6) | **PONG**                                                                                                   |
| IPv4 `/32` + IPv6 `/128` | `49.12.20.236` (v4)          | **PONG**                                                                                                   |

Same symptom string as the Postgres half, same shape: an unlisted source gets a TLS EOF with nothing naming the allow list, a listed source works. Address family is the only variable between rows 1 and 3.

**The product hands the user the failing form.** `GET /v1/key-value/{id}/connection-info` returns (password redacted here):

```text
cliCommand: redis-cli --sni red-….kv.bex.co -u rediss://default:<redacted>@red-….kv.bex.co:6379
external  : rediss://default:<redacted>@red-….kv.bex.co:6379
```

Both target the **hostname**, which resolves AAAA-first on a dual-stack client. A user who allow-lists the IPv4 the product reports and then copy-pastes bex's own `cliCommand` gets the opaque EOF. This is the Key Value analogue of the Postgres CLI's IPv4-only `getUserIP` gate — and it means the trap is reachable with **no CLI involvement at all**, through a connection string the product itself emitted.

Consequences for the rest of the milestone:

- The README's "Unverified — Key Value half" bullet is replaced: Key Value is **confirmed affected**, not merely likely.
- **t003's scope stays both front doors** (`kv-sni-proxy/main.go:145` and `pg-sni-proxy/main.go:248`, one shared `sniproxy.AllowedBy`).
- **Carry into t002/t003:** whichever candidate is chosen, the `cliCommand` and `externalConnectionString` the product emits must land on a path the user's allow-list entry actually covers. Under candidate (a) that happens for free; under (c) the emitted string is the thing that has to change.
- **b′ applies to Key Value too, but differently.** The PostgreSQL SSLRequest pre-TLS `ErrorResponse` seam t002 found has no exact RESP analogue — a Redis client sends its ClientHello first with no plaintext round trip to hijack — so the legibility fix must be designed per protocol, not assumed portable.
