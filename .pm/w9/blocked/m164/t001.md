## Objective

Settle whether the Key Value external endpoint has the same dual-stack allow-list trap the Postgres endpoint was proven to have. The code path and the DNS shape both say yes; the live control was inconclusive, so nothing is claimed yet.

## Context

- `lego/operator/cmd/kv-sni-proxy/main.go:145` calls the same `sniproxy.AllowedBy` as the Postgres proxy (`pg-sni-proxy/main.go:248`), over the same `ParseAllowList` output (`internal/sniproxy/allowlist.go:34-65`).
- `red-<id>.kv.bex.co` resolved to the same pair as the Postgres host on 2026-09-21: `A 49.12.20.236`, `AAAA 2a01:4f8:c01e:3d1f::1`.
- Why the 2026-09-21 sweep could not settle it: `bex kv-cli` at pin v2.27.0 is interactive-only (`Error: bex kv-cli can only be used in interactive mode`) with no `--command` flag, and driving it through a bounded PTY handed off to `redis-cli` before any PING/error could be captured.
- A free Key Value only gets an external endpoint once it is published; on 2026-09-21 a non-empty allow-list on `keyvalues update` published it (`public: true`, `externalHost` set) — the `w4/m116` t002 behavior, confirmed working live.

## Steps

1. Create a disposable free Key Value in a QA workspace, publish it with an allow list holding **only** the caller's IPv4 `/32`.
2. From a dual-stack client, connect to `externalHost:6379` over TLS by the supported route (`bex kv-cli` through a real PTY, or `redis-cli --tls` directly if the CLI cannot be driven non-interactively — say which was used).
3. Record the exact failure text and whether the peer address was the v6 or the v4 literal.
4. Repeat with the caller's IPv6 `/128` added. A pass here plus a fail above proves the trap; anything else disproves it.
5. Delete the fixture and record the result in this milestone's README (replace the "Unverified — Key Value half" bullet with the finding either way).
