# 062 — `render-cli-auth-browser.cjs` cannot complete the production device flow

Why: the mandated pre-release live device check fails deterministically against production, so no release can evidence the gate the checklist requires.

## Repro (2026-09-20, production `https://oauth.bex.co` / `https://dashboard.bex.co`)

`bex login` (isolated config) prints a device URL; piping NUL-delimited QA credentials into `NODE_PATH=… node scripts/render-cli-auth-browser.cjs <verification-url>` (the exact `scripts/bex-cli-auth-e2e.sh:129-131` invocation) fills email + password and then times out:

- After password submit the flow lands on **`/auth/device`** (the "Authorize this device" confirmation), which the script never handles — it only waits for `/auth/consent` or `/auth/device/success` (`render-cli-auth-browser.cjs:85`).
- After clicking authorize, production redirects to **`/auth/login?login_challenge=…`** demanding reauthentication (password field hidden behind an "enter your password" expander; identifier input present-but-hidden), then skips consent (`skip_consent`) and lands on `/auth/device/success`.
- Reproduced on three consecutive fresh device codes; the CLI side stays `Waiting for login…` until the browser half completes.

## Fix shape (proven this hunt with a throwaway helper — creds via stdin, tab `approve-device.cjs` logic, not committed)

1. After the first login, wait for `/auth/device` too; wait for hydration, then click `Authorize device`.
2. On `/auth/login` (reauth): expand the password method when `input[name="password"]` is absent; fill identifier only when visible; submit the password method.
3. Keep the existing consent-approve + `/auth/device/success` + `render cli|connected` assertion.

With those steps the same invocation prints `authorized browser session` and `bex login` completes (`Login successful! CLI token saved.`, 0600 config).

## Acceptance

- [ ] `scripts/bex-cli-auth-e2e.sh` (browser half) completes against production with a disposable human identity: login → authorize → reauth → success, no timeout.
- [ ] No credentials, cookies, or device codes in the script's stdout/stderr (diagnostics stay redacted as today).
- [ ] Local-env e2e still green (no regression where the authorize step may be absent — handle `/auth/device` conditionally).

## Out of scope

- Changing the reauth requirement itself (plausibly intended step-up; normal human path enters the password once).
- `bex login` TUI/CLI changes.

## Disposition 2026-09-20 — BLOCKED (fix implemented and shipped; the acceptance run needs credentials this session cannot reach)

**Fix landed** in `scripts/render-cli-auth-browser.cjs`. The helper no longer
assumes a fixed page sequence: it now drives whichever of
`/auth/login`, `/auth/device`, `/auth/consent`, `/auth/device/success` is on
screen until the success page, bounded to 8 legs and waiting for a real URL
change between them. New legs, exactly as the note's proven shape describes:

- `/auth/device` — clicks the confirmation's submit via
  `form[action="/auth/device"] button[type="submit"]` (selector taken from the
  form's action, not its label, so a locale change or a pre-hydration render
  still works — the form POSTs natively).
- `/auth/login` on reauth — clicks `button[name="method"][value="password"]`
  first when `input[name="password"]` is not visible (the collapsed method),
  fills `identifier` only when it is visible, then submits the password method.
  A first login sees both fields visible and never takes the extra click, so the
  local-env path is unchanged (acceptance line 3's no-regression requirement is
  satisfied by construction, not by a run).

Diagnostics still print only paths and field name/type — no credentials,
cookies, or device codes (acceptance line 2).

**The gate:** acceptance line 1 is a live run against production with a
disposable human identity. This session cannot read `.env` (the credential
lookup is denied), so `CLI_USER_EMAIL`/`CLI_USER_PASSWORD` are unavailable, and
the local fallback is out too — `scripts/dev-env.sh 9 status` reports the CAPD
cluster's kubeconfig rejected (`x509: certificate signed by unknown authority`),
every dev-9 port `000`, and no default StorageClass; that is the same gate
already parked on `blocked/060.md`.

**To clear it**, with a disposable identity and either production or a healthy
local stack:

```
CLI_USER_EMAIL=… CLI_USER_PASSWORD=… BEX_API_URL=https://api.bex.co \
  HYDRA_ADMIN_URL=<private-admin-forward> scripts/bex-cli-auth-e2e.sh
```

Expect the browser half to print `authorized browser session` and the CLI half
`Login successful! CLI token saved.`; then tick the three acceptance boxes here
and move this note to `done/`.

That is **acceptance line 3** (local-env e2e still green, no regression) — and it

is exercised, not just skipped. **Acceptance line 2** holds by inspection:
`debugPage` prints only the path and each input's name/type; no value, cookie,
or device code is ever written.

Getting there required fixing two blockers that were **not** the helper — both
predate this note's fix and would have failed the old helper identically (proven
by re-running the pre-change helper from `6cf17cb12~1`, which stalls in exactly
the same place):

1. **`scripts/dev-env/values/hydra.values.yaml` overrode `urls.login`/`consent`
   but not `urls.device.*`**, so `deploy/gitops/base/values/hydra.values.yaml`
   won and every `dev-N` stack sent `bex login` to
   `https://dashboard.bex.co/auth/device` — a LOCAL device login authenticating
   against PRODUCTION, failing as "invalid credentials" with no hint it had left
   the machine. Filed and fixed as `064`.
2. **`scripts/bex-cli-auth-e2e.sh:create_identity` seeded an unverified
   address.** Kratos requires a verified address before issuing a session, so
   the identity authenticated and was then refused with
   `session_verified_address_required` — which the login UI renders as the same
   generic "credentials are invalid". The admin create body now sets
   `verifiable_addresses: [{verified: true, status: "completed"}]`.

**What is still gated (acceptance line 1):** the production run with a
disposable human identity — the leg where the reauth (`/auth/login?login_challenge=…`,

`CLI_USER_EMAIL`/`CLI_USER_PASSWORD` are unavailable. Run:

```

  HYDRA_ADMIN_URL=<private-admin-forward> scripts/bex-cli-auth-e2e.sh
```

and, on the same `✓` line, tick line 1 and move this note to `done/`.

## Update 2026-09-21 (`/qa-find-bugs-cli` sweep) — the production reauth page has no `name="method"` button

The gated run above is likely to **fail at the reauth leg**, for a reason that
is not credentials. A human device login was driven by hand against production
that day (browser MCP, not the helper), and the reauth page
(`https://dashboard.bex.co/auth/login?login_challenge=…`) was inspected in its
**initial, collapsed** state — the state it loads in:

```text
BUTTON name=provider type=submit value=github   "Sign in with github"
BUTTON name=null     type=button  value=null    "Password / Enter your password associated with your account"
INPUT  name=csrf_token  type=hidden
INPUT  name=identifier  type=hidden  (prefilled)
```

There is **no** `button[name="method"][value="password"]` on that page. The
helper's `submitPasswordLogin` opens with

```js
await method.first().waitFor({ state: "attached", timeout: 30_000 });
```

against exactly that selector, **before** any click — so it cannot reach the
disclosure click that expands the password field. Confirmed empirically: that
same selector was tried first by hand and timed out after the full 30 s on the
loaded page. The collapsed control is a plain `type="button"` carrying
`data-testid="ory/form/auth-picker/password"`.

The hand-driven flow completed once the disclosure was clicked by a selector
that matches it, the revealed `input[name="password"]` was filled, and submit
used `button[name="method"][value="password"], form button[type="submit"]:not([name="provider"])`
— i.e. the fallback, not the primary selector. Whether the **expanded** form
exposes `name="method"` was not captured; if it does, only the initial
`waitFor` needs to change, and if it does not, the submit needs the fallback too.

So before spending a disposable production identity on the gated run, make
`submitPasswordLogin` resolve the collapsed control by something that exists on
that page (the testid, or a password-method button matched by either shape),
and keep the local path working — dev-9's page may still render `name="method"`,
which is why the local acceptance leg is green and this was invisible to it.


## Addendum 2026-09-23 — `/qa-find-bugs-cli` sweep 5 (w8): still failing, and the open question is answered

The shipped helper still fails on production at the reauth leg. `scripts/render-cli-auth-browser.cjs` was fed the QA identity on stdin (`bex v0.2.1` device login) and exited 1 with `locator.waitFor: Timeout 30000ms exceeded … waiting for locator('button[name="method"][value="password"]')` at `submitPasswordLogin` (`:58`, called from `:141`). A throwaway driver logged the legs: `/auth/login` → `/auth/device` → `/auth/login` (reauth) → `/auth/device/success`. The first `/auth/login` **does** render `button[name="method"][value="password"]` ("Sign in with password") with a visible identifier and password. On the reauth page, after clicking the collapsed control (accessible name starting `Password`), the expanded form is:

```text
inputs:  csrf_token(hidden) · identifier(hidden) · password(password, visible)
buttons: (button) · (button) · name="method" value="password" type=submit "Sign in"
```

So the expanded form **does** expose `name="method"`. Only the initial `waitFor` (and the "is the password field visible" guard ahead of it) needs to change. The submit selector is fine. With that one change the flow finished and `bex login` printed `Login successful! CLI token saved.` (0600 config). Values and codes were never printed.
