# Static-site deploy fails post-build on prod (publish Job)

Filed by `w9/m44/t005` (sample lifecycle sweep, 2026-07-18). After the `.pm/w9/010` stopgap (a Dockerfile for `examples/static-site`) landed on `origin/main`, re-running the static-site lifecycle on **production** builds successfully but then fails to deploy:

```
#6 pushing manifest for zot.bex-registry.svc:5000/tea-…-static-site-x1:gen-1@sha256:a22a576… done
#6 DONE 0.3s
==> Deploy failed        (deploy dep-…, update_failed, ~3.5 min after create)
```

The build plane produces and pushes the image (the busybox image staging `index.html`); the failure is the **publish step** (ADR029: an in-cluster Job whose init container extracts `publishPath` from the built image → `aws s3 sync` to the object-store origin, then serve via the shared static-server). Reproduced with BOTH a re-used name and a unique name (`NAME_SUFFIX=-x1`), so it is **not** the `gen-1` tag-reuse issue (`.pm/w9/013`) — the static publish path itself is broken on prod.

**Not diagnosable from this session:** the publish Job runs in the build namespace and its pod logs are **not** surfaced by `render logs` (`--type app/deploy/request` all empty for a static site — no app pod). Root-causing needs the Hetzner prod kubeconfig to read the publish Job / init-container logs, which this laptop lacks.

**Leading hypotheses (to check with cluster access):**

1. **Publish Job image pull auth.** The extract initContainer pulls the just-built tenant image from Zot. m43 fixed per-App zot pull-credential activation for tenant Deployments/CronJobs (`registry.EnsureActive`, verify-then-bounce) — but the **publish Job** may not share that per-App pull-cred wiring, so its first-deploy pull 401s (the exact m43 failure mode, one plane over). Prod still runs the m43 operator (Argo sync suspended), so confirm the publish Job mounts a working pull secret.
2. **Extract/`cp` or s3-sync failure.** The extract runs `sh -c 'cp -a "$PUBLISH_PATH"/. /out/'` in the busybox image (validated locally: copies exactly `index.html`); or the `aws s3 sync` to `BEX_STATIC_S3_*` fails (creds/bucket/endpoint). The build succeeding proves `BEX_STATIC_S3_*` is at least set enough for reconcile to dispatch the build.

**Next step:** with the prod kubeconfig, `kubectl -n <build-ns> logs job/<publish-job> -c extract` (and the aws-sync container) on a fresh `services create --type static_site …`; fix the wiring, then re-run `scripts/samples-lifecycle.sh static-site` to green. The sample Dockerfile fix (`.pm/w9/010` stopgap) is correct and locally validated — this is a separate prod publish-plane defect.
