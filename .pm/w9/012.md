# Static-site on prod: a 5-bug chain — RESOLVED (static-site now GREEN)

Filed by `w9/m44/t005` (sample lifecycle sweep, 2026-07-18). Static sites were **comprehensively non-functional on production** — the first systematic prod exercise (via `scripts/samples-lifecycle.sh static-site`) uncovered a chain of five stacked bugs, each masking the next. All five are now fixed and the full lifecycle runs **GREEN on prod** (deploy → up `200 "Hello from bex"` → suspend → down → resume → up → delete → gone). Two fixes are durable code; three were manual prod interventions that still need codifying into infra/gitops.

## The chain (in the order they surfaced)

1. **No Dockerfile** (sample). `--type static_site` took the Docker build path and failed `no Dockerfile` — bex's static build plane is Dockerfile-only (ADR029). **Fixed + shipped** (`.pm/w9/010` stopgap: `examples/static-site/Dockerfile`; the no-Dockerfile flow is still the real follow-up in `010`).
2. **Publish Job pull credential** (operator code). The publish Job's extract initContainer pulled with `r.RegistryPullSecret` — an apps-namespace secret unreachable from the separate `BEX_BUILD_NAMESPACE` (bex-system), empty under per-App creds → the extract could not pull → `update_failed` post-build. **Fixed + shipped** (`dbb828ed`): `AppReconciler.buildJobPullSecret` + `RegistryBuildPullSecret` (env `BEX_REGISTRY_BUILD_PULL_SECRET`, default `bex-registry-pull`), unit-tested (`TestBuildJobPullSecret`).
3. **`bex-registry-pull` secret was stale** (prod infra). Even with (2), the pull 403'd: prod's `bex-registry-pull` authenticated as **`bex-puller`** — the old shared puller (w7/m8) that per-App mode (w7/m36) dropped from the Zot ACLs; only `bex-builder` (admin) and `app-<name>` (per-repo) have read. `scripts/registry-secrets.sh` *now* mints it with `bex-builder`, so prod's was pre-switch. **Applied on prod** (re-minted `bex-registry-pull` from the `bex-registry-push` `bex-builder` credential). **To codify:** re-run `registry-secrets.sh` against prod, or add `bex-registry-pull` to the out-of-band bootstrap so it can't drift.
4. **static-server RBAC** (operator code). The `bex-static-server` SA had a **namespaced Role** (`bex-system`) but the resolver lists Apps **cluster-wide** (`BEX_STATIC_NAMESPACE` empty) → `apps.app.bex.co is forbidden ... at the cluster scope` → the host→site snapshot was empty → 404 for every host. **Fixed** (this milestone, `lego/operator/config/staticserver/{role,rolebinding}.yaml` → `ClusterRole`/`ClusterRoleBinding`). **Also applied on prod** (`bex-static-server-apps-reader` ClusterRoleBinding covering both static-server SAs). Ships with the operator config.
5. **static-server deployment drift** (prod infra). The `default/bex-static-server` (which the Ingress targets — Ingress backends are same-namespace, and static-site Ingresses live in the App namespace) ran a **stale operator image** whose resolver returned empty, was **missing `BEX_BASE_DOMAIN`** (so it couldn't compute the Expose'd host `<subdomain>.onbex.co`), and there was a **second, unmanaged `bex-system/bex-static-server`** on a newer image that worked. None are Argo-managed. **Applied on prod:** set `BEX_BASE_DOMAIN=onbex.co` + updated the `default` static-server to the working image → the public URL served 200. **To codify (the real infra fix):** make the static-server(s) **Argo-managed** from `config/staticserver` so they track the current image + config automatically, and add `BEX_BASE_DOMAIN` to the `bex-static-config` ConfigMap (the design already `envFrom`s it — prod's ConfigMap just lacks the key). Consolidate to ONE static-server per the Ingress topology (in the App namespace, since the operator points the Ingress there).
