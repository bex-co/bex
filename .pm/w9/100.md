# 100 — Three audit-log actions Render may name that bex still records under its own verbs

Why: w9/m449 mapped every workspace event render.com/docs/audit-logs lists, but three bex actions sit next to Render events without a confirmed match, so they keep bex's names until a capture of Render's rows settles them.

- **Source:** w9/m449 t007 (Render parity), 2026-11-16; [render.com/docs/audit-logs](https://render.com/docs/audit-logs) read 2026-11-16.
- **Today:**
  - A service's branch change records `apps.SetSourceAndRegistryCredential`; Render's `UpdateAutoDeployTriggerEvent` is "trigger settings, such as branch or path filters". bex maps the build filter (`apps.SetBuildFilter`) to it, not the branch.
  - Giving a build-source-linked service its own repo or image unlinks it under `apps.SetSourceAndRegistryCredential`; the link itself is `UpdateServiceBuildSourceEvent` (`apps.LinkBuildSource`). Whether Render records an unlink as the same event is unknown.
  - Env group variable writes (`envgroups.PatchEnvironment` and siblings) keep bex's names: Render documents `CreateEnvVarsEvent`/`UpdateEnvVarsEvent`/`DeleteEnvVarsEvent` "for a service" and no env group variable event.
- **Do:** capture Render's audit rows for a branch change, a build source unlink and an env group variable edit (needs `RENDER_API_KEY` on a Pro reference workspace, as w10/blocked/002), then map each to what Render records, or record it as a non-goal in `renderWorkspaceEvents` and ADR018.
- **Accept:** each of the three actions answers Render's captured event on REST `GET /v1/owners/{ownerId}/audit-logs`, or ADR018's Audit logs row records why it keeps bex's name, with the capture as evidence.
