# Render's scoped API keys: a per-permission picker under the creator's role

Why: Render lets a key be granted a chosen subset of the creator's permissions ("Read" or "Read & write" per area, or "Enable all"); a bex key always gets the creator's whole role, so a least-privilege CI key is impossible.

- **Render** ([render.com/docs/api-keys](https://render.com/docs/api-keys), read 2026-11-18): "Your member role in the selected workspace determines which permissions you can grant an API key"; areas such as Workspaces ("View webhooks", "Create, update, and delete webhooks", "Update notification settings") and Projects ("Configure protected environments and cross-environment traffic blocking"), each Read or Read & write, plus "Enable all".
- **bex** (since w9/m481): a key acts with exactly its creator's current role (ADR024 § An API key acts with its creator's role). No per-permission grant exists on REST, GraphQL, MCP or the dashboard's API keys page.
- **Done when:** a key can be minted with a subset of the creator's permissions on every surface and the dashboard; each request is refused outside that subset even when the creator holds it; the subset never exceeds the creator's current role (the w9/m481 ceiling still applies); ADR018's API keys row records it.
