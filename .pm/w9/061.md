# 061 — Truthful cron schedule previews for oversized and non-divisor steps

Why: authors must be able to trust the schedule they confirm; oversized and non-divisor steps currently promise uniform intervals the scheduler does not run.

Transferred from `w4/099` to `w9/061` by user direction after the w4 brainstorm. Worker: **worker9**. Estimate: **45–60m**. Dependencies: none. Keep as an inbox note under the sizing rule; this replaces the original queue entry.

Found in the live `/qa-find-bugs` loop, 2026-09-17 pass 5, journey 10 (cron jobs). **Read-only — the create form was exercised but never submitted; no service was created, and nothing was deleted.**

## What it does

On `dashboard.bex.co/services/new?type=cron_job`, typing a schedule renders a human-readable preview under the field. Captured live, cycling values through the Schedule input:

| typed          | preview says          | cron actually runs         |
| -------------- | --------------------- | -------------------------- |
| `*/70 * * * *` | **Every 70 minutes**  | hourly, at minute 0        |
| `*/100 * * * *`| **Every 100 minutes** | hourly, at minute 0        |
| `0 */30 * * *` | **Every 30 hours**    | daily, at 00:00            |
| `*/30 * * * *` | Every 30 minutes      | every 30 minutes ✓         |
| `*/60 * * * *` | Every 60 minutes      | hourly ✓ (coincides)       |
| `0 */12 * * *` | Every 12 hours        | every 12 hours ✓           |

"Every 30 hours" is not merely wrong, it is unrepresentable — a drifting 30-hour period cannot be expressed in cron at all.

All three wrong inputs are **valid and saveable**: `internal/apps/testdata/cron-schedule-vectors.json` pins `*/100 * * * *` as `valid: true`, with the reason that names the real semantics — _"a step wider than the range still names its start"_. So the author is not stopped; they are told the wrong thing and allowed to proceed.

Day-of-month, month and day-of-week steps (`0 0 */40 * *`, `0 0 * */15 *`, `0 0 * * */9`) make no claim — they fall through to the generic "A 5-field crontab expression…" help text, which is honest. The defect is only in the minute and hour branches.

## Root cause

`dashboard/src/features/services/lib/cron.ts:144-150`:

```ts
const stepMinute = /^\*\/(\d+)$/.exec(minute);
if (stepMinute && hour === "*" && allDates) return `Every ${stepMinute[1]} minutes`;

const stepHour = /^\*\/(\d+)$/.exec(hour);
if (/^\d+$/.test(minute) && stepHour && allDates) return `Every ${stepHour[1]} hours`;
```

Both branches interpolate the captured step straight into a sentence without bounding it against the field's range. The same file already holds those bounds and already models robfig's behavior correctly: `validRange` (`cron.ts:71-90`) reads `spec.min`/`spec.max`, and the comment above it (`cron.ts:67-70`) documents the quirks the vector table pins. The checker learned the semantics; the preview never did.

## Why this is not a duplicate

- `w1/m145` (`8d35cff1d fix(dashboard): cron check matches bex-api`) aligned the dashboard's **validator** with bex-api's robfig parser — which is exactly why `*/70` is accepted and `0 0 * * 7` is refused. It did not touch `describeCron`.
- `w9/m91` t004 ("Schedule UX parity — human-readable preview + pre-fill + UTC note") built this preview. This is a gap it left, not a regression of it.
- `w4/098` recorded journey 10 working end to end; it exercised scheduling and run logs, not the preview's wording for over-range steps.

## Fix

Only claim a uniform interval when the schedule actually has one. A bounds-only fix is insufficient: source review during the brainstorm identified `*/40 * * * *` (minutes 0 and 40, alternating 40- and 20-minute gaps) and `0 */5 * * *` (hours 0, 5, 10, 15 and 20, with a four-hour gap at midnight). These additional cases are source-derived, not claimed as live QA observations. Use accurate field wording or the existing generic fallback for non-divisor steps.

When the step exceeds the field's max, the expression fires only at the field's start value — so either describe it truthfully (`*/70 * * * *` → "Every hour", `0 */30 * * *` → "Every day at 00:00") or fall through to the generic help text. Derive bounds and field width from the existing `FIELDS` specs. Keep the accepted schedule set aligned with the backend vector table.

`dashboard/src/features/services/lib/__tests__/cron.test.ts:34,37` only covers in-range steps (`*/5`, `*/2`), so no existing assertion encodes the wrong behavior — the fix adds cases rather than editing any. Cover both boundaries that coincidentally read correctly today (`*/60` minutes, `*/24` hours) so a future refactor cannot quietly break them.

Check both consumers of this helper: `dashboard/src/routes/services.new.tsx` and `dashboard/src/features/services/components/cron-deploy-section.tsx`, so Create and Settings agree.
