# A native Python build keeps its virtualenv's packages across source-only commits

Why: Render keeps `/opt/render/project/src/.venv` between builds, so a source-only commit's `pip install -r requirements.txt` finds every package installed. bex restores pip's wheel cache (`$XDG_CACHE_HOME`, w9/m493) but rebuilds the virtualenv from nothing on every build, so each one reinstalls every package.

- **Found by:** w9/m494, 2026-11-19. A Render staff answer on community.render.com lists the directories Render caches automatically: `/opt/render/project/.gems`, `/opt/render/project/nodes`, `/opt/render/project/src/.venv`, `/opt/render/project/.render`, `/opt/render/project/rubies` and `/opt/render/project/src/node_modules`.
- **Why w9/m494 left it out:** w9/m494 carries Ruby, Go, Rust and Elixir dependency directories (`nativeDependencyDirs`, `lego/operator/internal/build/depscache.go`). Its env-loader seed replaces only a directory that is missing or empty (`nativeDepsSeed`). The Python recipe makes the virtualenv before `COPY . .` (`nativeBuildDefaults`, `lego/operator/internal/build/native.go`), so the directory is already there and the seed leaves it alone. A Python row needs its own rule: replace the recipe's fresh virtualenv with the kept one when they were made by the same interpreter. The dependency key (the Dockerfile up to `COPY . .`, `xdgBuildctl` in `xdgcache.go`) already covers that. A repository that commits its own `.venv` still wins, as the recipe's `COPY . .` lets it win today.
- **Done when:** a native Python service rebuilt after a source-only commit has its `pip install -r requirements.txt` print `Requirement already satisfied` for every unchanged package; a Python version change or `clearCache: "clear"` installs them from nothing; and a test covers the replace rule and a committed `.venv`.
