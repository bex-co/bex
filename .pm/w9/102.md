# 102 — A sandbox exec over a connect token is audited as its API key (`rest_api`), not as `system`

Why: Render's `auditLogActor.type` tells a person, an API key and the platform apart (`user`, `rest_api`, `system`). On production, a workspace API key's sandbox commands read `system` while their other rows read `rest_api`, so a reader who filters out system rows misses that key's commands.

- **Source:** w9/m450 t008 (closeout walk on production, 2026-11-18). In `bex-canary` (`tea-daif693dqjvc73e7as3g`), REST `GET /v1/owners/tea-daif693dqjvc73e7as3g/audit-logs?startTime=2026-11-17T09:46:00Z` returns four `sandbox.StreamExec` rows (2026-11-17, 09:51–13:52Z) with `actor {type: system, id: c73bb20d-40ff-42df-8597-c9a428697d12}`. Each carries the client's `source_ip` and `user_agent` `Go-http-client/2.0`. The same id's 152 other rows in that window are all `rest_api`, among them the `sandbox.ConnectRun` rows that minted the tokens.
- **Today:** the connect stream re-enters with `core.Identity{Subject: claims.Subject, Method: "sandbox-connect"}` (`lego/backend/internal/sandbox/connect.go:286`), and the file stream with `"sandbox-file-connect"` (`file_connect.go:249`). `audit.actorType` (`lego/backend/internal/audit/rest.go:79`) maps every method it does not list to `system`. The command probe (`commands.go:135`, `"sandbox-command-probe"`) is the platform's own work, so `system` is correct for it.
- **Do:** give a connect-token row the actor type of the credential that minted the token: `rest_api` for an API key or an OAuth token, `user` for a session. For example, carry the minting method in the token claims, or map both methods in `actorType`. GraphQL `actorMethod` and the dashboard row follow. Amend ADR018's Audit logs row if the mapping is documented there.
- **Accept:** a backend test pins `sandbox.StreamExec` over a key-minted connect token to `rest_api` with the key's id, and the probe to `system`. On production, a `bex sandbox exec` with an API key writes a `rest_api` row.
