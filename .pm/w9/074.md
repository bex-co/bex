# 074 — Sandbox nodes join without gVisor: fail closed, catch template drift, stop calling it a capacity limit

Why: on 2026-11-04 every production agent session failed to start for ~2 days because the sandbox node joined the cluster without the gVisor runtime, and customers were told `SANDBOX_CAPACITY_LIMIT` (a plan limit) instead.

- **Incident (resolved 2026-11-04).** The live `bex-capi/bex-sandbox` KubeadmConfigTemplate was an old copy that downloaded gVisor from `releases/release/latest/` (now 404). The pinned, sha512-checked template committed in `2c17bea65` (security round 18) had never been applied. Each new sandbox node's `wget -q` failed silently and the node joined without `containerd-shim-runsc-v1`.
- **Remediation, with user authorization (surge first, then delete old).** Applied the repo template; surged a replacement cx33 node (`bex-sandbox-cgqq6-p8wcg`) and verified a gVisor pod (`uname` → `4.19.0-gvisor`); deleted the broken node. User rule recorded: when replacing a node, first create the new machine, then delete the old; if no capacity is available, find another way.
- **Fix 1: fail closed.** A sandbox node must not join (or must be tainted unschedulable) when runsc or the shim is missing. Make the install a hard gate, e.g. retry the download, then a final `test -x /usr/local/bin/containerd-shim-runsc-v1` whose failure aborts kubeadm join. Check how CAPI runs preKubeadmCommands.
- **Fix 2: drift guard.** A check, script or CI, that the live CAPI templates match `infra/clusterapi/overlays/hetzner-caph/*.yaml`. Also document that infra template changes must be applied (README).
- **Fix 3: honest error.** `FailedCreatePodSandBox`, or a missing runtime, must not map to `SANDBOX_CAPACITY_LIMIT`. Surface a platform-side "sandbox runtime unavailable" error (503-class).
- **Done when:** a test or dry-run shows a node without the shim does not become schedulable; the drift check reports a drifted template; the error mapping has a test.
