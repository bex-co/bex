# 063 — Re-grade the CLI checklist `psql` row for the verify-full era

Why: the row's evidence predates w4/m95's deliberate `sslmode=verify-full` switch, so it misleads anyone reproducing `bex psql` on a fresh machine (out-of-box failure looks like a regression).

## Evidence (live, 2026-09-20, bex v0.2.1 / pin v2.27.0, production)

- `bex psql <dpg-id> -c 'SELECT 1 AS bex_psql_probe;'` on a machine without `~/.postgresql/root.crt` fails: `root certificate file … does not exist`. `PGSSLROOTCERT=system` fails: `certificate verify failed` (private CNPG CA, by design).
- With the connection-info `serverCaCertificate` saved to a file and `PGSSLROOTCERT=<that file>`, the same command returns the probe row `1`. One transient `SSL error: unexpected eof` (IPv6) self-recovered on retry — single occurrence, not filed.
- The failure is intended behavior per w4/m95 (done): verify-full + in-dashboard CA download + `PGSSLROOTCERT` guidance, recorded as a deliberate bex extension (Render presents publicly-trusted certs and needs no counterpart). Not a product bug.

## Change

In `docs/cli-compatibility-checklist.md`, `psql [id|name]` row (and the `docs/render-artifacts/psql-cli.md` supplement if touched): note that since w4/m95 the external string pins `sslmode=verify-full`, the CLI passes it verbatim to psql (pinned `pkg/tui/views/psql.go:75,213` — no bex-side override possible without a fork), and the supported path is installing the connection-info CA (`PGSSLROOTCERT=/path/to/<id>-ca.pem`, per the dashboard Connections panel). Cite this note + the 2026-09-20 live probe as the verify-full-era evidence.
