## Objective

Establish exactly why the running zot rejects freshly written per-App credentials (both htpasswd user and ACL entry exist in the mounted Secrets but auth 401s until pod restart), and pick the activation mechanism t002 implements. Record the decision + evidence in this milestone's README.

## Context

- Prod evidence 2026-07-17 (memory `prod-zot-stale-creds-first-deploy.md`): `zot-htpasswd`/`zot-config` Secrets in `bex-registry` contained the new `app-<name>` user and repo ACL, Secret volume mounts are plain (no `subPath`, so files do propagate in-pod), yet a direct `curl -u` with the exact secret credentials returned 401 from zot-0 (up 21h). `rollout restart statefulset/zot` fixed it instantly — twice.
- `lego/operator/internal/registry/creds.go:31-33` claims htpasswd is re-read per auth request and config.json reloads on SIGHUP/restart — at least the htpasswd half is false for the deployed zot.
- Zot chart: `deploy/gitops/base/zot.yaml` (externalSecrets mounts; check deployed zot version + whether upstream supports config hot-reload and whether its fsnotify watcher survives the k8s Secret symlink swap).
- Reproduce locally on the mock cluster (`bash scripts/mock-cluster.sh`, `BEX_REGISTRY_NS` path) rather than experimenting on prod.

## Steps

1. On the mock cluster with per-App creds enabled, create App A (zot loads its creds at startup or has been restarted), then create App B and confirm B's pull 401s while A's works — the prod repro.
2. Determine the deployed zot version and read its auth/reload code or docs: is there a supported hot-reload (config watcher, SIGHUP handling in-container, an admin API)? Test whether updating the mounted Secret triggers any reload at all.
3. Enumerate candidate mechanisms with tradeoffs: (a) chart-side: enable a working zot hot-reload if one exists; (b) operator-side verify-then-bounce: after `EnsureCreds`, probe zot with the new credential and delete the zot pod when it 401s past the Secret-propagation grace; (c) sidecar/`shareProcessNamespace` SIGHUP. Respect the product-vs-GitOps boundary (`.pm/DO_NOT_DO.md`): the operator already owns the zot Secrets, so credential *activation* may live operator-side; chart changes belong in `deploy/gitops/`.
4. Write the decision (mechanism, blast radius of a zot bounce on concurrent pulls, propagation timing) into `w9/m43/README.md` and correct the `creds.go` package comment.
