## Objective

Thread the viewer capabilities from t001 through the dashboard as one context/hook the feature components read, so no component makes a bespoke one-off role check (the wrong shape called out in `.pm/w1/047.md`).

## Context

- A `grep` of `dashboard/src` for any client-side capability check (`canCreate`, `can_create`) finds nothing today.
- The dashboard queries GraphQL via Apollo; capabilities should ride an existing workspace-scoped query or a small dedicated one, cached like other viewer/workspace data.

## Steps

1. Add the GraphQL document for the t001 `viewer`/`capabilities` field and a `useCapabilities()` hook (or extend an existing workspace context) exposing the effective booleans.
2. Make it cache-friendly (cache-first on navigation, keyed on the active workspace) consistent with the m62/m68 fetch-policy patterns.
3. Provide a legible default while loading (treat as no-extra-permissions until known, or reuse the existing suspense/skeleton pattern) so controls never flicker enabled→disabled.

## Files

- `dashboard/src/features/**/graphql` (new capabilities document)
- a shared hook/context under `dashboard/src/common/` or the workspace feature

## Acceptance criteria

- [ ] `useCapabilities()` (or equivalent) returns typed effective booleans for the active workspace
- [ ] No per-control ad-hoc role logic — components read the shared context
- [ ] `yarn typecheck && yarn lint && yarn test` green
