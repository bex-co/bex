## Objective

Accept JSON `null` for the optional list fields Render's recorded requests send as `null`, treating each as omitted, as bex already does for `buildFilter`'s lists (`nullableBuildFilterLists`, w8/m54).

## Context

- Render accepted these nulls in the provider's recordings: `POST /services` with `"envVars":null`, `"secretFiles":null`, `"serviceDetails.routes":null`; `POST`/`PATCH /postgres` with `"readReplicas":null` (all answered 2xx).
- bex validates every Render request against the pinned schema (`api/render_openapi.go`), where these properties are not nullable, so kin-openapi refuses `null`; `applyRenderSchemaCompatibility` (`:487`) already widens `buildFilter` for the same reason.
- Whether the provider at tip still sends each of these as `null` is not confirmed statically (its request structs use pointer + `omitempty`); Render's acceptance is what makes this a parity item either way.

## Steps

1. Extend the schema compatibility pass to mark these properties nullable on create-service, update-service, create-postgres and update-postgres (clone the components, as `nullableBuildFilterLists` does, so responses stay non-null).
2. Confirm each domain decoder reads `null` as omitted (`*[]…` nil), not as a clear.
3. Test each null on its operation.

## Files

- `lego/backend/internal/api/render_openapi.go`, `lego/backend/internal/apps/rest.go`, `lego/backend/internal/postgres/rest.go`, tests

## Acceptance criteria

- [ ] Each of the four nulls is accepted and changes nothing.
- [ ] Responses keep their non-null lists (the shared response components are untouched).

## Out of scope

- Nulls Render's recordings do not show it accepting.
