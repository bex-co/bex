# 099 — A deleted user's audit export row reads `Deleted User ID#<id>`, as Render's does

Why: Render's audit-log export names a deleted user as `Deleted User ID#123123123` in its `actor` column; since w9/m450 bex writes the bare `usr-` id, so a CSV consumer matching Render's marker misses bex's deleted users.

- **Source:** w9/m450 t005 (Render parity), 2026-11-16; [render.com/docs/audit-logs](https://render.com/docs/audit-logs) § Export, read 2026-11-16: `actor` is "the email address of the existing Render user" or "the ID of the deleted Render user that performed the action (e.g., `Deleted User ID#123123123`)".
- **Today:** `dashboard/src/features/audit/lib/audit-csv.ts` `csvActor` writes `actorEmail`, else `actorId` (a deleted user's `usr-` id), else the subject. The dashboard cannot tell a deleted user from an email lookup that failed: both answer an id and no email. Account deletion rewrites the row's caller to `deleted:<own-id>` (`lego/backend/internal/store/accounts.go`, `CleanupAccountSubject`).
- **Do:** have bex-api say a person is deleted (e.g. GraphQL `actorDeleted`, from the `deleted:` marker, never parsed by the dashboard), and write `Deleted User ID#<usr- id>` in the export for it. REST `actor` keeps `{type: user, id}` (Render's schema has no deleted flag). Amend ADR018's Audit logs row.
- **Accept:** a deleted user's export row reads `Deleted User ID#usr-…`; a person whose email lookup failed still reads the `usr-` id; a dashboard test and a backend test cover both.
