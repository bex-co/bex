## Objective

Connection info answers `rediss://…@<externalHost>:6379` whenever the store is public and the operator has recorded its external host, whether or not its TLS listener has opened, as Render answers it while a store is `creating`. `externalCertificate` (`pending`/`failed`, a bex extension, w4/m357) keeps telling clients whether the endpoint accepts connections yet.

## Context

- `lego/backend/internal/keyvalue/service.go:1449-1456` blanks the external string while `!kv.Status.TLSListener` (w8/237). `service.go:1418-1421` refuses with 503 a public store that has no external host. `externalCertificateState` is at `service.go:1494`.
- `dashboard/src/features/keyvalue/components/connection-info-panel.tsx:168-185` hides the external field while it is empty and shows `keyvalue.connExternalPending`/`connExternalFailed` instead.
- w8/237's record is at ADR021, the bullet "Connection info (REST, the `/redis` alias, GraphQL and MCP) advertises the external `rediss://` URL … only while `status.tlsListener` is true". ADR018's Key Value row says "The external string stays empty until its TLS listener opens (w8/237)". Amend both: parity outranks the older choice (AGENTS.md Rules).
- Readiness (`updateKeyValueReadiness`) does not wait for the TLS listener today, so a store created public can read `available` up to about a minute before its external URL connects.

## Steps

1. Stop blanking the external string on the listener. Keep the external-host validation and the 503.
2. Decide what a store created public reads while its listener is still closed, and record it in ADR021. Render's `available` means every string it handed out connects. The Render-consistent option keeps such a store `creating` until its listener opens. A later first enable on an existing store keeps reading `available` with `externalCertificate: pending`. A failed certificate must not hold a store's internal clients hostage: say what it reads then.
3. Dashboard: show the external URL, and under it the pending or failed note taken from `externalCertificate`.
4. Amend ADR021 (w8/237) and ADR018's Key Value row.

## Done (2026-11-19)

- `KeyValueConnectionInfo` answers the external URL once `status.externalHost` is set, listener open or not, with `externalCertificate` pending, failed or publiclyTrusted.
- Status choice (ADR021 §3): a store created public reads `creating` until its listener opens (`keyValueFirstListenerWait`). The hold ends at the open listener, a failed certificate, or 5 minutes after the create, and never applies to a store that has been available (a later first enable reads `available` with `externalCertificate: pending`). Covered by `TestKeyValueFirstListenerWait`, `TestKeyValueCreatedPublicReadsCreatingUntilItsListenerOpens` and `TestKeyValueWithAFailedCertificateIsAvailable`.
- Dashboard: the Connect panel shows the URL with the pending or failed note under it, in all eight locales.
- dev-9 has no ClusterIssuer, so a public store's certificate never issues there. The store read `creating` ("waiting for the external TLS listener") and became `available` with `externalCertificate: pending` exactly 5:00 after its create.
- ADR021 (the w8/237 bullet) and ADR018's Key Value row are amended.
