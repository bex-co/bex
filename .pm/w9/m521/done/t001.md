## Objective

A store created after this change routes its stable `<id>` Service through its internal auth proxy from birth, and it sets `status.internalAuthOptional` in its first pass. Connection info and the compatibility Secret's `uri` then read `redis://<id>:6379` straight after the create, as Render's do. A running store's cutover is unchanged.

## Context

- `lego/operator/internal/controller/keyvalue_internal_proxy.go:318-331` (`reconcileKeyValueInternalRoute`): `intent.internalProxy = proxyReady || kv.Status.InternalAuthOptional`. `keyvalue_controller.go:785` (`reconcileKeyValueService`) switches the selector. `keyvalue_controller.go:567-571` writes the Secret's credential-free `uri`. `lego/backend/internal/keyvalue/service.go:1458` serves the credential-free string.
- **Why the wait exists.** w8/204 migrated running stores whose clients connected straight to Valkey, and their Service must not move to a proxy that is not serving. A store whose stable Service does not exist yet has no client to strand. Until its proxy is Ready, its Service has no endpoints, just as a store that is still creating has none today. `updateKeyValueReadiness` already waits for the proxy, so `available` still means the URL connects.
- **Security (record it in ADR021 with the change).** Nothing turns auth off: Valkey keeps its password and tenant ACL. The proxy supplies the restricted `default` user's `AUTH`, as it does for every cut-over store today (ADR021 § Internal authentication). Nothing widens reach: the same NetworkPolicies admit only the workspace and environment peers to the stable Service, and only the store's own proxy to its backend. The string carries no secret. The read stays `can_view_sensitive`, fresh, because the same answer carries the external credential.
- The manager always runs with `InternalProxyImage` set. A legacy embedding without it keeps the credentialed form.

## Steps

1. Choose "new" so that it cannot catch a store whose clients connect straight to Valkey. One option is the pass that creates the stable Service. Never use it for a store whose Service already selects the Valkey pod.
2. Set the selector and `status.internalAuthOptional` in that same pass. Check that the status write in the first pass (the one w9/108's 5 s wait reads) carries the flag.
3. A store created with `spec.internalAuth` set keeps the credentialed URL.
4. envtest: the first reconcile of a new store selects the proxy and sets the flag. An existing store whose Service selects Valkey, and whose proxy is not Ready, still waits. `spec.internalAuth` keeps the password in the URL.
5. dev-9, with the operator built from the tree (`bash scripts/mock-cluster.sh operator`):
   - create a store and read connection info at once: it answers `redis://<id>:6379`;
   - once the store is `available`, `valkey-cli -u redis://<id>:6379 PING` from a service in the same workspace answers `PONG`;
   - the same command from another workspace does not connect.

## Done (2026-11-19)

- `routeKeyValueFromBirth` (`lego/operator/internal/controller/keyvalue_internal_proxy.go`) runs before the credentials. A store whose stable Service is missing (confirmed by an uncached read) gets its Service on the proxy in the pass that creates it, and `status.internalAuthOptional` before the connection Secret is written, unless `spec.internalAuth` is set. An existing Service keeps the w8/204 wait.
- Envtest `A new Key Value's first reconcile (w9/m521)`, against the real API server through the whole Reconcile, records every write to the stable Service. Each one selects the proxy and comes after both proxy NetworkPolicies. The new store's NetworkPolicies equal a cut-over store's, uid and name aside. The first status write carries the flag, and the first Secret's `uri` is `redis://<id>:6379`. A store whose Service selects Valkey keeps it there, credentialed, until its proxy is Ready. A store created with internal auth is on the proxy from birth and keeps its credentialed URL. With `routeKeyValueFromBirth` disabled, the first spec fails.
- dev-9 (bex-api from the tree; operator from the tree on the shared mock cluster): a public store's first read at +310 ms and a private one's at +159 ms answered `redis://<id>:6379` on REST, `/v1/redis` and GraphQL. From a pod in the store's workspace, `valkey-cli -u redis://<id>:6379 PING` answered `PONG`. From another dev-9 workspace the short name did not resolve, and `<id>.<ns>.svc` timed out (NetworkPolicy).
- The security reasoning is ADR021 § Internal authentication, "From birth".
