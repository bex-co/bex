## Objective

Every credentialed string names the store's id as its user, as Render's do. The external URL reads `rediss://<id>:<password>@…`, the CLI command reads `--user <id>`, and the internal URL with internal authentication reads `redis://<id>:<password>@<id>:6379`. Valkey accepts that user with exactly the tenant's permissions and password, and no running store restarts to get it.

## Context

- Render: every credentialed string in the provider's cassettes names `red-…` as the user. Its internal-authentication URL is `redis://red-…:<password>@red-…:6379` ([render.com/docs/key-value](https://render.com/docs/key-value)).
- bex: `kvDefaultUser` (`lego/operator/internal/controller/keyvalue_controller.go:62`) and `valkeyDefaultUserRule` (`:262`) are the only tenant ACL user, set in the server's args. `keyValueConnectionSecretData` (`:301-315`) and the auth Secret's `username` write `default`. The backend's `keyValueURI` (`lego/backend/internal/keyvalue/service.go:1502`) also writes `default`. The internal proxy authenticates as `default` (`lego/operator/internal/kvinternalauth`).
- Adding a user to the server's args changes the pod template, which restarts the store, and a Persistence Off store loses its keys. Runtime switches already exist for this case: `CONFIG SET` as the platform user in `reconcileKeyValueMaxmemory` and `reconcileKeyValueMaxclients`, and the held templates in ADR021 § 10.

## Steps

1. Add a second tenant user named `<id>`, with `valkeyDefaultUserRule`'s permissions and the same password:
   - in the server args, wherever a store's template is rendered anew anyway;
   - with `ACL SETUSER` as the platform user on a running store whose template is held;
   - again after any restart that comes back without it.

   Keep the password out of every log and event.
2. Record in status when the user holds, and switch the strings to `<id>` only then. Until then keep `default`, so no string names a user the server does not know.
3. Keep `default` working: linked services' Secrets, the proxy's injected `AUTH`, the readiness probe. Decide whether the compatibility Secret's `uri`, `externalUri` and `username` move to `<id>`, and record the choice.
4. Check that `AUTH <id> <password>` works through the SNI edge (TLS pass-through) and through the internal proxy in client mode (`spec.internalAuth`).
5. Record the user in ADR021 (§ Internal authentication and the endpoint table).
