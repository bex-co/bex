## Objective

Stop the read shape from contradicting storage: a docker cron with a command must not report `dockerCommand: ""`.

## Context

- `lego/backend/internal/apps/render.go:489-505` — `envSpecificDetails(a AppView, svcType string)`; the docker map is built as `"dockerCommand": a.StartCommand`.
- A cron's command lives in `a.Command`, not `a.StartCommand`. The function already takes `svcType`, so it can tell a cron from a web service without new plumbing.
- Live proof (2026-09-21): one readout showing both halves at once —
  `serviceDetails.command: 'echo qa-root-level'` while
  `serviceDetails.envSpecificDetails.dockerCommand: ""`.
- This is what makes `services update --cron-command` look like a no-op: the write lands, the response renders through this projection, and the CLI prints the stale empty value.
- It also breaks cloning: `pkg/service/clone.go:143` reads `startCommandFromEnvDetails(details.EnvSpecificDetails)`.

## Steps

1. For a cron job, project the command from `a.Command` (falling back to `a.StartCommand` if both are ever populated — match whatever t003 decides is canonical).
2. Check the native projection in the same function for the mirror bug: does a native cron's `startCommand` read back from `a.Command` or `a.StartCommand`? The native path currently works live, so confirm rather than assume, and cover it either way.
3. Check `blueprint_generate.go:283,297`, which has its own `dockerCommand`/`Command` handling — make sure it agrees with this projection instead of being a second answer.
