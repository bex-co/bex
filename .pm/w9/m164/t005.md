## Objective

The existing allow-list-deny coverage cannot catch this bug, and quietly says PASS while it is live. Add a leg that exercises the **data path**, not the client-side gate.

## Context

- `scripts/psql-compat-verify.sh:395-417` is honest about what it tests: "the CLI's own client-side gate (`getUserIP` → `hasAccessToPostgres` over `pg.ipAllowList`) refuses BEFORE exec'ing psql". It sets the allow list to TEST-NET-1 so the gate trips, and asserts the refusal is named. Because the gate always trips first, the server's denial shape is never observed — the leg passed throughout the period this bug was live.
- The missing case is the asymmetric one: an allow list the client-side gate **accepts** (it contains the caller's IPv4) but the data path **rejects** (the connection arrives over IPv6).
- Key Value needs the equivalent (`scripts/keyvalue-cli-verify.sh`), subject to t001's finding.

## Steps

1. Add a data-path deny leg: allow-list only the caller's IPv4 `/32`, connect without forcing a family, and assert the outcome required by t002's decision — either success, or a refusal that names the allow list. Assert it is **not** a bare `unexpected eof`.
2. Keep a forced-IPv4 control in the same leg so a future regression can be localized to the family rather than to TLS.
3. Skip honestly when the runner has no IPv6 (the existing script's `curl`-probe gate is the precedent — a skip is honest, a silent pass is not).
4. Mirror into the Key Value verifier unless t001 disproved that half.
5. Confirm the new leg **fails** against the pre-t003 behavior before declaring it done — a deny leg that has never failed is not evidence.
