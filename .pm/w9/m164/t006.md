## Objective

Check that whatever t003 shipped is consistent across every surface it exposes, and that it does not drift from render.com behavior without the drift being recorded.

## Context

- If t002 chose candidate (c), the caller's reported address becomes a user-facing field and must appear with the same name, semantics and error shape on REST, GraphQL and MCP in `lego/backend/` (`docs/ADR006-bex-api.md`) and in the dashboard Access-control panel (`dashboard/AGENTS.md`).
- If t002 chose candidate (a), the parity question is the inverse: does Render publish AAAA for its datastore hosts? Dropping ours is parity if it does not, and a recorded divergence if it does.
- The region precedent is the model for recording a deliberate divergence: `docs/ADR018-render-parity.md` documents region as installation-selected and normalized to `BEX_REGION`, rather than pretending to match.

## Steps

1. Enumerate the surfaces t003 actually touched.
2. Compare each against the equivalent render.com behavior/API.
3. Record matches; file drift as follow-up work rather than silently diverging.
4. Update `docs/ADR018-render-parity.md` and `docs/cli-compatibility-checklist.md`.

## Files

- `docs/ADR018-render-parity.md`, `docs/cli-compatibility-checklist.md`
- `lego/backend/internal/` and `dashboard/` for any surface t003 changed

## Acceptance criteria

- [ ] Every surface t003 touched is checked on REST, GraphQL, MCP and UI, or explicitly listed as untouched.
