## Objective

Define and provision the dedicated Wasabi S3 build-cache bucket with a bucket-scoped IAM policy and 30-day expiry lifecycle rule, and amend ADR060 D3 and ADR019 to document the S3 build-cache backend and credential boundary.

## Context

- `BEX_BUILD_CACHE=registry` was rolled back on 2026-10-26 (`w7/done/047.md`) because `mode=max` adds ~422 MB/App onto Zot's single 100 GiB PVC.
- Existing Wasabi bucket + scoped IAM provisioning patterns live in `infra/wasabi/` and `scripts/agent-attachments-s3-credentials.sh` ([ADR095](../../../../docs/ADR095-agent-attachments.md), [ADR112](../../../../docs/ADR112-object-storage.md)).
- ADR060 D3's founding security invariant stands: BuildKit executes tenant code and must never hold S3 or registry credentials.

## Steps

1. Author the bucket-scoped IAM policy under `infra/wasabi/` granting object read/write/delete/list only on the build-cache bucket (never backups, tfstate, static-sites, attachments, or tenant object storage).
2. Add a repeatable provisioning/verification script (mirroring `scripts/agent-attachments-s3-credentials.sh`) with a 30-day object expiration lifecycle rule and negative checks proving no access to unrelated buckets.
3. Amend `docs/ADR060-build-worker-reliability-and-performance.md` (§ D3) and `docs/ADR019-infra-credentials.md` with the S3 cache key layout (`<tea-id>/<app-uid>/layer-cache/`), size cap (`8G`), expiry, and credential inventory.

## Acceptance criteria

- [x] Bucket-scoped IAM policy and lifecycle rule are checked in and validated against unrelated buckets (negative checks fail closed).
- [x] ADR060 D3 and ADR019 document `BEX_BUILD_CACHE=s3`, key layout, size cap, and credential ownership.

## Out of scope

- Migrating Zot image storage or kpack cache tags off Zot.

## Result — 2026-11-18

- `infra/wasabi/build-cache-s3-policy.json` grants list/get/put/delete (and multipart) on `bex-build-cache` only; `infra/wasabi/build-cache-lifecycle.json` expires every object after 30 days and aborts stale multipart uploads after one.
- `scripts/build-cache-s3-credentials.sh provision` created the `bex-build-cache` bucket (eu-central-2), applied the expiry, created IAM user `bex-build-cache` with the one inline policy `BexBuildCache`, and installed its key as `bex-build/bex-build-cache-s3` on production (labelled `app.bex.co/protected-from-tenant-mount`). Wasabi accepted the lifecycle rule.
- `verify` on production passed every row: the expiry rule is in force; put, read, list and delete of a probe under `.bex-security-probe/` succeed; account listing, `bex-tfstate` list and write, `bex-static` list and write, an unrelated bucket, and deleting the expiry rule are all refused with an access denial.
- `scripts/build-cache-s3-credentials.test.sh` (wired into `scripts.yml`) pins the refusals, the policy's bucket and actions, and the expiry.
- ADR060 gained the [D3 S3 amendment](../../../../docs/ADR060-build-worker-reliability-and-performance.md#d3-amendment-w9m492--the-s3-backend-off-zot) (key layout, 8 GB bound, expiry, credential boundary); ADR019 lists the credential and its custody.
- Deviation: the Secret is installed out of band, as every other S3 credential is (ADR019), rather than sealed into Git.
