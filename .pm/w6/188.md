# 188 — A service's first deploy reads an empty `fromService` `hostport` for a private service whose port is not detected yet

Why: Render's `redash` template builds `REDASH_REDIS_URL="redis://${REDIS_HOSTPORT}/0"` at start. On bex its first deploy runs with an empty value, so the web service and both workers start against no Redis (or localhost). A second deploy, triggered when the port is detected, fixes it, but only after the first one has gone live.

- **Source:** w6/m653 t003 (2026-11-26), the live run of the 49 remaining no-value `render-examples` templates ([render-examples-live.md](../../docs/render-artifacts/render-examples-live.md)).
- **Seen** on production pin `9b91284a4a2e`, in `bex-canary`, with `scripts/render-examples-live.sh redash` (render-examples/redash@347e2bd2ad98). The Blueprint has a web service and two workers, each with `REDIS_HOSTPORT` `fromService: {type: pserv, name: redash-redis, property: hostport}`, beside `redash-redis` (from `render-examples/redis`, listening on 10000). The sequence:
  - The first deploys went live with `REDIS_HOSTPORT` empty. The web service logged `ConnectionError: Error 111 connecting to None:6379` at 11:22:18 UTC, and `redash-worker` logged `transport: redis://localhost:6379/0` and `Cannot connect to redis://localhost:6379/0`.
  - `redash-redis`'s port was detected at 11:21:14, which started an `envUpdated` deploy of each reader.
  - The new `redash-worker` pod logged `Connected to redis://redash-redis:10000/0` at 11:22:11, and the env var then read `redash-redis:10000`.

  The fixtures were deleted by ID (404).
- **Inconsistent with bex's own model:** a private service's address reads `<slug>:10000` before its image's ports are discovered, "as Render's create answers" (w9/104, `lego/backend/internal/apps/render.go`). The same service's `hostport` is empty for the readers' first deploy instead.
- **Render:** the Blueprint spec documents `hostport` as the private service's host and port and says nothing about an empty value. Confirm what a Render reader sees on its first deploy (the `<slug>:10000` default, or a deploy held until the port is known) before choosing.
- **Do:** a reader's first deploy never gets an empty `hostport`, `host` or `port` for a private service in the same sync. Either resolve it as Render does, or hold the reader's release until the port is known, as w6/184 does for a database.
- **Acceptance:**
  - [ ] `bash scripts/render-examples-live.sh redash` on production shows no `None:6379` or `localhost:6379` line in the first deploy's logs.
  - [ ] A regression test: a sync that creates a private service and a reader of its `hostport` never renders the reader's env var empty.
- **Estimate:** ~1h, most of it confirming Render's behavior. A Render parity task applies if the deploy log or events change.
