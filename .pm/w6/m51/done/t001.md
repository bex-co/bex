## Objective

Determine precisely which `App.Spec`-patching `Service.SetXxx` verbs actually cause the operator to rebuild/redeploy without ever calling the `deploys` package's create-deploy path — the exact set the fix in t002 must cover, no more and no less.

## Context

- `lego/backend/internal/apps/service.go` has ~23 `SetXxx` verbs (grep `func (s \*Service) Set`); each ends in `s.patchFetched(ctx, a, func(a *appv1alpha1.App) { ... })` which patches the App CR spec and returns — none call `triggerDeploy` / the `deploys` package.
- `dashboard/src/features/services/components/manual-deploy-button.tsx:31-32` states "any spec change increments the generation and unconditionally re-enters the build path" — written in the context of the Restart action specifically; confirm whether this is literally true for every `App.Spec` field or only build-relevant ones (repo/branch/image, commands, root dir, runtime, dockerfile path) by reading the operator's reconcile diff logic, not by re-deriving it from this comment alone.
- Live-confirmed this run: `SetCommands`'s `startCommand` half (`service.go:3137-3160`) does force a real rebuild (build logs showed a genuine `go build`/image-push cycle) with zero `deploys` row created.
- **Live-confirmed by a later `/qa-find-bugs` iteration (2026-08-24), via the dashboard's Build Command control specifically:** the GraphQL `setBuildCommand` field (`apps/graphql.go:1384-1392`) is a thin projection that calls the identical `Service.SetCommands(ctx, id, &command, nil)` already confirmed broken for `startCommand` — so this is not a new backend verb, just independent confirmation that the SAME already-known-broken function reproduces through its second front-end entry point (the dashboard's separate `useBuildCommand`/`use-build-command.ts` hook, its own two-step confirm dialog reading "Service will redeploy with the new build command" — an explicit user-facing promise). Repro: on a fresh `qa-`-prefixed service, edited Build Command via Settings, confirmed via GraphQL that `buildCommand` persisted and `server.phase` transitioned `Building`→`Deploying`; polled `deploys(serviceId:)` across the whole transition and it never gained a new row (stayed at the 2 pre-existing ones), and the Events feed showed only the settings-audit entry ("Build and deploy settings changed") with zero corresponding Build/Deploy-started event for the rebuild. Confirms t002's fix to `SetCommands` will cover both the Start Command and Build Command dashboard controls in one place — no separate fix needed per GraphQL field.
- Candidate build-relevant verbs by field shape (not yet independently live-verified): `SetRootDir` (`:3034`), `SetDockerfilePath` (`:3060`), `SetPreDeployCommand` (`:3116`) — note: a Pre-Deploy Command change may or may not require an image rebuild, verify — `SetSourceAndRegistryCredential` (`:3189`, repo/branch/image change).
- `SetHealthCheckPath` is unresolved, not yet in either bucket: a separate iteration (recorded against `w6/037`) incidentally observed it also forcing `phase` to `Building`, but that observation wasn't isolated from adjacent edits on the same service and needs its own clean repro before it's added to the confirmed list.
- Candidate non-build verbs (should NOT need this fix, confirm they genuinely don't rebuild): `SetPlan`, `SetIdleTTL`, `SetDisplayName`, `SetAutoDeploy`, `SetNotifyOnFail`/`SetNotificationsToSend`, `SetIPAllowList`, `SetMaintenanceMode`, `SetMaxShutdownDelay`, `SetSubdomainPolicy`, `SetAutoscaling`, static-site-only `SetRoutes`/`SetHeaders`/`SetPublishPath`.

## Findings (2026-08-24)

**The enumeration is not a per-verb list — the operator already publishes an exhaustive one.** `lego/operator/internal/controller/release_identity.go` carries `appSpecIdentityClasses`, a map naming _every_ `AppSpec` field as one of:

- `identityArtifact` — changing it can produce different image bytes (a rebuild),
- `identityRelease` — changing it rewrites the pod template (a redeploy),
- `identityOperational` — reconciled against the running release; neither.

Two operator guard tests keep it honest: `TestAppSpecIdentityClassificationIsExhaustive` (fails when the CRD gains an unclassified field) and `TestEveryAppSpecFieldMatchesItsIdentityClass` (fails when a field's real fingerprint behavior stops matching its declared class). So the "does this force a rebuild" question has a single, already-tested answer — and re-deriving a second list in bex-api would be exactly the drift this milestone was filed for.

**Resolution:** the classification moved to the CRD contract module as `appv1alpha1.AppSpecIdentityClasses` + `appv1alpha1.SpecRollsRelease(before, after)` (`lego/types/v1alpha1/app_identity.go`), the operator now aliases it, and t002's gate calls `SpecRollsRelease`. A new operator test, `TestSpecRollsReleaseMatchesReleaseFingerprint`, asserts field-by-field that the backend's gate and the operator's release fingerprint agree — the cross-plane guard that makes drift a red test rather than an invisible rollout.

### Confirmed: forces a rollout (deploy row required)

| verb | field(s) | class |
| --- | --- | --- |
| `SetCommands` | `BuildCommand`, `StartCommand` | artifact+release (live-confirmed, both dashboard controls) |
| `SetRootDir` | `RootDir`, `RestartedAt` | artifact+release |
| `SetDockerfilePath` | `DockerfilePath`, `RestartedAt` | artifact+release |
| `SetSourceAndRegistryCredential` | `Repo`/`Image`/`Branch`/`RegistryCredentialID` | artifact+release |
| `SetPreDeployCommand` | `PreDeployCommand` | release (no rebuild — pre-deploy runs against the existing artifact) |
| `SetHealthCheckPath` | `HealthCheckPath` | release — **resolves t001's open question**; the `w6/037` observation of `phase: Building` was real |
| `SetMaxShutdownDelay` | `MaxShutdownDelaySeconds` | release |
| `SetPlan` | `Tier` | release (resizes the pod: new requests==limits) |
| `SetCronJob` | `Command` | release |
| `SetPublishPath` | `PublishPath` | release (static sites) |
| disk attach/detach/remount | `Disk` | release — disk **size** deliberately excluded: a grow is applied online, and rolling for it would turn a no-downtime resize into an outage |

### Confirmed: does NOT force a rollout (no deploy row, asserted by `TestOperationalVerbsOpenNoDeploy`)

`SetIdleTTL`, `SetDisplayName`, `SetAutoDeploy`, `SetNotifyOnFail`, `SetNotificationsToSend`, `SetIPAllowList`, `SetMaintenanceMode`, `SetSubdomainPolicy`, `SetAutoscaling`, `SetBuildFilter`, `SetRoutes`, `SetHeaders`, `Scale`, `Suspend`/`Resume` — every one patches a field the operator classifies `identityOperational` and reconciles against the _running_ release.

**Correction to the milestone's premise:** `manual-deploy-button.tsx`'s "any spec change … unconditionally re-enters the build path" is Restart-context-specific and is **not** literally true. Roughly half the `SetXxx` family is operational. Gating on `patchFetched` unconditionally would have minted a deploy for every scale and rename; gating on `SpecRollsRelease` is what makes the fix correct in both directions.
