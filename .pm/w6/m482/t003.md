## Objective

The gateway Deployment brings its new pods up first and gives an old pod the drain bound plus a margin before `SIGKILL`, and the production deploy step still finishes in minutes.

## Context

- `lego/operator/config/ssh/deployment.yaml`: `replicas: 2`, default strategy, default 30 s grace; requests `25m`/`64Mi`, limits `500m`/`512Mi`. `config/ssh/pdb.yaml` exists.
- `.github/workflows/deploy.yml:1376-1378`: `GRANTS_ONLY=1 bash scripts/ssh-gateway-db-role.sh`, then `rollout restart` and `rollout status --timeout=300s`. Terminating pods are not counted as replicas, so `rollout status` should return once the new pods are available; confirm it.
- The role sync installs this release's `dbrole.sql` before the restart, so a draining old pod runs for up to an hour against the new grants. Check that the grants only ever add privileges an older gateway uses, or record what an old pod could lose.
- Platform nodes run `bex.co/pool: platform`; two extra gateway pods for an hour must fit.

## Steps

1. Set `terminationGracePeriodSeconds` to the bound plus a margin (e.g. 3660) and a `RollingUpdate` with `maxUnavailable: 0`, `maxSurge: 1`.
2. Check `pdb.yaml` still allows the roll.
3. Confirm, on the local cluster, that `rollout status` returns while an old pod is still terminating.
4. Check the role sync against an old pod, and the platform pool's headroom.
5. Update any `scripts/gitops-validate.sh` assertion on these fields.
