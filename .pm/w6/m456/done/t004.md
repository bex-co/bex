## Objective

Existing stores adopt their limit, and an upgrade raises it at once, without restarting `valkey-server`.

## Context

- The maxmemory runtime pass (`keyvalue_maxmemory_runtime.go`) dials each running server as the platform user and `CONFIG SET`s the policy when it differs.
- Render cannot downgrade a Key Value ("It is not currently possible to downgrade a Key Value instance", render.com/docs/key-value), so in practice the limit only rises; the pass still handles any difference.

## Steps

1. Extend that pass, or add a sibling, to read `CONFIG GET maxclients` and set the plan's value when it differs.
2. Lowering the value below the current client count keeps existing clients and refuses new ones; confirm that and note it in the code.
3. Test against a real Valkey (the runtime tests' harness): the value follows a plan change with no pod restart.

## Files

- lego/operator/internal/controller/keyvalue_maxmemory_runtime.go (or a sibling)
- its tests

## Acceptance criteria

- [ ] A running store's `maxclients` follows its plan within one reconcile, with no restart
