## Objective

Add Render's connection limit to every Valkey tier as one table the operator, the proxies and bex-api read, and write down every path a connection takes to `valkey-server`, so t003–t005 bound the right ones.

## Context

- Render's table ([compute plans § Render Key Value plans](https://render.com/docs/compute-plans#render-key-value-plans), read 2026-11-17): `free` 50, `256mb` (Starter) 250, `1g` (Standard) 1,000, `3g` 3,000, `5g` (Pro) 5,000, `10g` (Pro Plus) 10,000, `20g` (Pro Max) 20,000, `40g` (Pro Ultra) 40,000, `50g` 50,000.
- bex ids: `lego/types/tiers/tiers.yaml` `valkey:` (`free`, `starter`, `standard`, `3g`, `pro`, `pro_plus`, `pro_max`, `pro_ultra`, `50g`); size aliases in `lego/types/tiers/aliases.go` (`256mb`→`starter`, `1g`→`standard`, `5g`→`pro`, `10g`→`pro_plus`, `20g`→`pro_max`, `40g`→`pro_ultra`).
- Paths to trace: the `<kv>-internal` proxy Deployment (`lego/operator/internal/controller/keyvalue_internal_proxy.go`, `lego/operator/cmd/kv-internal-proxy/main.go`): the plain `:6379` listener that injects the password, and the TLS passthrough listener (`BEX_KV_TLS_ADDR`) kv-sni-proxy forwards to; the `<kv>-backend` Service.
- Platform clients to count: redis_exporter as `kvPlatformUser` (`kvExporterEnv` in `keyvalue_controller.go`), the operator's runtime `CONFIG SET` client (`keyvalue_maxmemory_runtime.go`), and the persistence and TLS runtime dials.

## Steps

1. Add `connectionLimit` to each `valkey` tier in `tiers.yaml` and expose it from `tiers.go`.
2. Guard test in `tiers_test.go`: every id and alias resolves to Render's figure above, and a tier without one fails.
3. Trace every tenant path to `valkey-server` and every platform client that holds a connection; record them, with the connections each platform client holds, under a "Connection paths" heading in this milestone's README.
