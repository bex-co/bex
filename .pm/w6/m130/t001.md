## Objective

`POST /v1/services` and `PATCH /v1/services/{id}` reject `serviceDetails.renderSubdomainPolicy` with `400 bad request: request body contains unknown field "renderSubdomainPolicy"` — including for `web_service` and `static_site`, the two types Render's own schema declares the field on. Accept it at Render's documented nesting while keeping the existing top-level field working, mirroring the dual-accept pattern four adjacent fields in the same struct already use.

## Context

- `lego/backend/internal/apps/rest.go:40` — `patchServiceRequest` declares `RenderSubdomainPolicy *string` (tag `renderSubdomainPolicy`) at `:95-98`, top level.
- `serviceDetailsReq` (same file) lacks the field. Complete json-tag list: `plan`, `region`, `numInstances`, `healthCheckPath`, `maxShutdownDelaySeconds`, `runtime`, `env`, `envSpecificDetails`, `schedule`, `command`, `buildCommand`, `publishPath`, `preDeployCommand`, `previews`, `maintenanceMode`, `ipAllowList`, `disk`.
- The pattern to copy is in that struct's own comments: `schedule`, `command`, `publishPath` and `preDeployCommand` are each documented as "accepted here or at the top level (top level wins)". `preferTopLevel(...)` at `rest.go:471` is the existing helper.
- Render declares the field in `webServiceDetailsPOST`, `staticSiteDetailsPOST`, `webServiceDetailsPATCH`, `staticSiteDetailsPATCH` (`lego/backend/internal/api/openapi/render-public-api-1.json`).
- `ipAllowList` is the control: it decodes at the nested location today because `w6/m106` moved it.

## Steps

1. Add `RenderSubdomainPolicy` to `serviceDetailsReq` with the `renderSubdomainPolicy` json tag and a comment matching the four sibling dual-accept fields.
2. Wire it through create and patch with top-level-wins precedence, reusing `preferTopLevel` so the rule is the same one the siblings use. Mind the pointer semantics on patch: absent must stay distinct from an explicit value.
3. Keep the existing top-level request field. It is documented in `docs/ADR018-render-parity.md` row 117 and removing it is a breaking change this milestone is not making.
4. Re-run all four live probes from the milestone README plus the `ipAllowList` control, and record the new responses.
