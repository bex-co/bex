## Objective

Two decisions about the REST **response**, both to be written down rather than left implicit: (a) whether `renderSubdomainPolicy` stays a top-level field of the service object or moves into `serviceDetails` where Render's schema puts it; and (b) whether it is emitted at all for `private_service`, `background_worker` and `cron_job`, which have no platform subdomain. This subsumes the open question `.pm/w6/063.md` raised and never answered.

Name the target behaviour. "Make the surfaces consistent" is not a spec — it is satisfiable by normalizing everything onto the broken variant. Say which surface is correct and why.

## Context

- Render's top-level `service` schema has **no** `renderSubdomainPolicy`. Complete property list: `autoDeploy`, `branch`, `buildFilter`, `createdAt`, `dashboardUrl`, `environmentId`, `id`, `imagePath`, `name`, `notifyOnFail`, `ownerId`, `registryCredential`, `repo`, `rootDir`, `serviceDetails`, `slug`, `suspended`, `suspenders`, `type`, `updatedAt`.
- Render declares it in `webServiceDetails` and `staticSiteDetails` only.
- bex emits it in **both** places, for all five types — see the four-type live capture in the milestone README.
- `render.go:158` (declaration, comment claims "Always present and non-empty"), set at `:290`; `render.go:318` is the untyped details-table entry.
- `render.go:159-163` already states the rule for the sibling field: `ipAllowList` is web/static-only in Render's schema "so it is emitted from renderServiceDetails(), not here — see the ipAllowList block there (w6/m106)".
- Prior applications of the same pattern: `w1/m86` (Disk), `w6/m106` (ipAllowList).

**Consumer constraint — verified live, do not break it.** The dashboard reads this field from **GraphQL** as a flat top-level field, not from REST `serviceDetails`: `dashboard/src/features/services/types.ts:187` (`renderSubdomainPolicy: string | null`), consumed by `platform-subdomain-section.tsx:28`, which defaults absent to enabled — `(renderSubdomainPolicy ?? "enabled") === "enabled"`. bex's GraphQL has no `serviceDetails` nesting, so GraphQL's flat field is correct and must stay; only REST's placement is in question. Also verified live: a background worker's Settings page renders no subdomain control at all (accessibility-tree scan of `main` returned zero matches for `/subdomain/i`), so a per-type reporting change has no dashboard consequence today — but that default-to-enabled line is exactly why a null must be checked rather than assumed safe.

## Steps

1. Decide (a) and (b), and record the reasoning in `docs/ADR018-render-parity.md` row 117. If the top-level response field is deliberately retained as a bex superset field, row 117 must say so explicitly — today `render.go:155-158`'s comment asserts the opposite of the pinned spec, which is the thing a future reader will trust.
2. Implement the decision. If the field moves or becomes type-scoped, use the type-condition style already present in `renderServiceDetails` (`url` and `buildCommand` are both gated there).
3. Fix `render.go:155-158`'s comment so it describes what Render's schema actually says.
4. Re-run the four-type `GET /v1/services/{id}` capture and confirm REST and GraphQL agree on whatever value was named correct.
