# Large exec output that ends with the process is truncated in Kubernetes' exec path (gateway and kubectl alike)

Why: `ssh srv-…@ssh.bex.co 'pg_dump …' > dump` or any large `cat`/`head` through the Render-documented SSH path loses the tail of its output when the command exits right after writing it, so a data export silently comes out short.

- **Evidence (2026-10-29, production, pin `b63b8a1091d7`):** in `beancount-forum` (`srv-d9nqg9dcavls73fp8m2g`), `head -c 20000000 /dev/urandom` returned 17,178,624 and then 14,794,752 bytes through the gateway, and all 20,000,000 with `; sleep 40` appended. `kubectl exec … -- head -c 20000000 /dev/urandom` from a laptop with kubectl v1.37.0 returned 19,181,563 over WebSocket (`Copying stdout failed: read message: unexpected EOF`) and 14,393,344 over SPDY (`KUBECTL_REMOTE_COMMAND_WEBSOCKETS=false`). Outputs of 1 MB and 5 MB arrive whole.
- **Not the gateway:** client-go's SPDY v4 `stream()` waits for the stdout copy (`tools/remotecommand/v4.go:73-78`), and kubectl through the kube-API LB truncates without the gateway. Suspects, in order: containerd 2.3.3 exec IO not draining the pipe when the process exits, kubelet's CRI streaming proxy, and kube-apiserver's upgrade proxy.
- **Look at:** reproduce with `crictl exec` on the node (bypassing apiserver and kubelet). Then compare containerd's exec IO handling for a known fix. If upstream, pin the patched containerd in the node image (`infra/packer`).
- **Expected:** the exec stream delivers every byte the process wrote before its exit status.

## Bisect — 2026-10-29

- **containerd is clean:** on node `bex-tenant-0-tghbn-sc7vl` (containerd v2.3.3 `aad11006b869`), a short-lived privileged `kube-system` pod ran `ctr -n k8s.io task exec … head -c 20000000 /dev/urandom | wc -c` against the same `beancount-forum` container, three times. All three returned 20,000,000 bytes. The pod was then deleted. The node image has no `crictl`.
- **So the loss is above containerd's task IO:** in the CRI streaming server (containerd's CRI plugin `Exec` URL), kubelet's streaming proxy, or kube-apiserver's upgrade proxy. Both client protocols lose data (WebSocket and SPDY).
- **Next:** put a pinned `crictl` on the node (or into the debug pod) and run `crictl exec` to test the CRI streaming server alone. If clean, test kubelet's `/exec` with its client cert. Then match the failing layer to its upstream issue and fix (version bump in `infra/packer` or a kubelet/apiserver flag).
