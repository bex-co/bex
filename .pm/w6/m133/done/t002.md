## Objective

The editor is seeded from the live `pg_settings` read, so a brand-new database opens with 48 rows the tenant never set, and Save is a full replacement. Bind the editor to the declared overrides, and decide what the `pg_settings` view becomes.

Name the target behaviour. "Make them consistent" is not a spec: the fix must not be satisfied by making the declared read return the observed config.

## Context

- Today: `databases.graphql:364-370`'s `DatabaseParameterOverrides` (the `pg_settings` shape — `name setting unit source description`) → `use-database-insights.ts:74` → `insights-panel.tsx:299-307` → `<ParameterOverridesEditor overrides={…}>` (`parameter-overrides-editor.tsx:70`).
- The `pg_settings` read is a **legitimate read-only DBA insight** — "what differs from PostgreSQL defaults" — and should survive as one. It is the editability that is wrong, not the data.
- `save()` submits `rows.map(...)`, the whole table; the component's own comment says "The parameter map is a full replacement". `dirty` compares against `savedRows`, seeded identically, so removing one row enables Save and writes the other ~47.
- Decide and record: two sections, or one section with a read-only "effective" column beside the declared set? And what a brand-new database shows — an empty declared set, plus the read-only effective view if it is kept.
- `parameter-overrides-editor.tsx` already carries the ADR024 `can_operate` / `can_create` split (statement-logging parameters require `can_create`); that gate must survive the rebind.

## Steps

1. Point the editor at `t001`'s declared-overrides read.
2. Keep the `pg_settings` data as a read-only view, or remove it from this panel — decide, and write the decision down.
3. Verify a fresh database opens with an empty editor.
4. Confirm the ADR024 permission split still applies to the rebound editor.
