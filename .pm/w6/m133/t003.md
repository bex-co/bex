## Objective

`normalizeParameterOverrides` filters exactly one name. Every other parameter — including the operator's own WAL archive/restore commands and the TLS material paths — is passed straight through to `d.Spec.Parameters`. Decide the policy and enforce it in the **service layer**, so REST, GraphQL and MCP callers are bound by it too and the dashboard is not the only thing standing in the way.

## Context

- `normalizeParameterOverrides` (`lego/backend/internal/postgres/service.go:934-948`) drops only `shared_preload_libraries`; `service.go:867` assigns the result to `d.Spec.Parameters`.
- The concrete inventory to classify is the 48 names captured live on a fresh free database (full list in the milestone README). At minimum these are operator-owned: `archive_command`, `archive_mode`, `archive_timeout`, `restore_command`, `recovery_target_timeline`, `restart_after_crash`, `port`, `listen_addresses`, `cluster_name`, `ssl`, `ssl_ca_file`, `ssl_cert_file`, `ssl_key_file`, and the WAL/replication group (`wal_level`, `wal_keep_size`, `wal_log_hints`, `wal_receiver_timeout`, `wal_sender_timeout`, `max_replication_slots`, `hot_standby`).
- `archive_command` and `restore_command` hold the CloudNativePG operator's own binary path (`/controller/manager wal-archive|wal-restore …`) — they are the mechanism backups and PITR run on.
- The rows sourced `client` / `session` are not configuration at all: they exist only because of the API's own connection and are transient per-session values. They must never be persisted.
- **Precedent in the same file:** `sensitiveLoggingParameters` (`service.go:890`) already classifies parameter names for a policy decision — follow its shape rather than inventing a new mechanism.
- Allowlist vs denylist is a real decision: an allowlist is safe by default but needs maintaining as PostgreSQL versions add settings; a denylist is permissive by default and will miss the next operator-managed key. Record the reasoning.

## Steps

1. Decide allowlist or denylist, and write down why.
2. Implement it in the service layer, not in an adapter, so all three surfaces inherit it.
3. Decide the failure mode: silently filtered, or a named 400 telling the caller the parameter is managed. A named error is more honest, but check it cannot become an enumeration oracle for internals.
4. Verify by calling the API directly, bypassing the dashboard.

## Acceptance criteria

- [ ] Setting `restore_command` or `ssl_key_file` through the API does not land in `spec.parameters`.
- [ ] A `client`/`session`-sourced value can never be persisted.
- [ ] A legitimate tuning parameter (e.g. `statement_timeout`, `max_connections`) still works.
- [ ] `shared_preload_libraries` stays filtered.
- [ ] The policy lives in the service layer and binds REST, GraphQL and MCP alike.

## Out of scope

- Changing what CloudNativePG itself does with a conflicting parameter — see the milestone's Unverified list.
