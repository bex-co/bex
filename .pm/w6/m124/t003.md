## Objective

The service header renders "Service Failed" and "Latest deploy: Build Failed" side by side. The second is correct and sufficient; the first contradicts a service that answers 200. Make the badge describe the service.

## Context

- `dashboard/src/features/services/components/service-status-badge.tsx` renders `deriveStatus(service)` from `dashboard/src/features/services/lib/status.ts`.
- Its own doc: "suspension wins over phase … One component for every place a status shows — the list rows, the detail header, and the overview panel — so they can't drift." So one change covers all three placements — confirm that rather than editing three call sites.
- Much of this may fall out of `t002` for free: if the backend stops reporting `Failed`, the badge follows. Check what actually remains before changing UI code, and if nothing does, say so and close the task rather than inventing work.
- **Pre-settle state:** the list and detail are cache-first/polling surfaces, so they paint the previous phase before the query settles. Confirm a service that has just failed a build does not flash "Failed" and then correct itself.

## Steps

1. Re-check the header and list after `t002` lands; record what still misreports, if anything.
2. If the badge still needs work, change `deriveStatus`/the badge once, and verify list rows, detail header and overview panel together.
3. Keep the "Latest deploy: Build Failed" indicator — it is the correct signal and must remain prominent.
4. Check the sleeping/suspended states still win where they should (`w6/m116`–`m119` territory).
