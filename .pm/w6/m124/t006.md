## Objective

Pin the new rule and — more importantly — pin the cases that are correct today and that this change could break.

## Context

- The likeliest regression is the deploy row: `build_failed` is derived from the phase today, so a test must fail if it stops being reported once the phase changes.
- The second likeliest is over-correction: a first-deploy failure with no image must still report `Failed`, and a sleeping or suspended service must not be swept into "running".
- Envtest covers the operator's phase transitions; the backend's reconciler tests cover the deploy-status derivation.

## Steps

1. Operator: a build failure with `Status.Image` set leaves a running phase; with no image, `Failed`.
2. Operator: the Build condition is still written with release-generation attribution in both cases.
3. Backend: the deploy row reaches `build_failed` from the condition, including when the phase is running.
4. Backend: a stale condition does not settle a newer deploy.
5. Dashboard: badge shows running + a failed-deploy indicator; suspended and sleeping still take precedence.

## Files

- `lego/operator/internal/controller/*_test.go`
- `lego/backend/internal/store/*_test.go`
- `dashboard/src/features/services/**/__tests__/`

## Acceptance criteria

- [ ] `cd lego/operator && make test`, `cd lego/backend && go test ./...`, `cd dashboard && yarn test` all pass.
- [ ] A test fails if `build_failed` stops reaching the deploy row.
- [ ] A test fails if a first-deploy failure stops reporting `Failed`.
- [ ] A test fails if sleeping/suspended get swept into running.

## Out of scope

- Live production verification; that is the DoD.
