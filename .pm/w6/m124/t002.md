## Objective

`r.fail` stamps `PhaseFailed` unconditionally, so a service whose previous release is still deployed and serving 200 reports `Failed` on every surface. Apply the rule bex already documented and already implemented for the cancel path: a healthy release keeps serving, and the phase stays truthful.

## Context

- `lego/operator/internal/controller/app_controller.go:3913` — `app.Status.Phase = appv1alpha1.PhaseFailed`, with no check for an existing release.
- **The rule is already written down.** `lego/types/v1alpha1/app_types.go:1104-1111`: "Reusing `PhaseFailed` here made a service contradict its own deploy history … a healthy release never reaches this state: that release keeps serving and the phase stays Running."
- **The predicate already exists**, in the cancel path at `app_controller.go:577-579`: `if app.Status.Image != "" { return r.dispatchRuntime(...) }`. That is `w6/m52`'s fix for the identical contradiction.
- After a terminal build failure the reconcile deliberately quiesces (`:832-839`) — it returns nil with no requeue so it does not re-fail and re-meter ~20×/h. Whatever phase is written must therefore be correct on the **first** pass; nothing will come back to correct it.

## Steps

1. Mirror the cancel path's guard: when a prior release image is present, do not stamp a terminal failed phase.
2. Decide explicitly whether `Running` is the right value or a new state is warranted, and record the reasoning. The `PhaseCanceled` precedent argues for reusing the truthful running state and letting the deploy row carry the verdict.
3. Keep the Build condition write (`:3920-3926`) exactly as-is — it is the durable failure record `t001` now reads.
4. Confirm the first-deploy-failure case still reports `Failed`: no image, nothing serving, so `Failed` is truthful there.
5. Check the quiesce path still holds — the App must not start re-reconciling because its phase changed.
