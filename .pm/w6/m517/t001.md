## Objective

`reconcileKeyValueInternalProxy` keeps the existing pod template of a store's proxy Deployment exactly as it runs, unless something the customer did rolls it. The template moves only when:

- the Deployment is new;
- it runs no pod (suspended, or being resumed);
- the store's roll inputs changed since the template was written;
- the override (t002) asks for it.

When it moves, it takes the manager's image and the full current rendering in one write. The fields outside the template (replicas, strategy, selector) are rendered as always, so suspension and resume still work.

## Context

- `lego/operator/internal/controller/keyvalue_internal_proxy.go`: `reconcileKeyValueInternalProxy` renders the template, and `keyValueInternalProxyImage` / `carriesInternalProxyBinary` hold the image by binary hash (w6/m469).
- Existing holds: `holdDatastorePriority` (`datastore_priority.go`), `holdIsolationLabel` and `templateEqualIgnoringIsolation` (`keyvalue_isolation.go`). The isolation labels are relabelled in place on running pods (`syncKeyValuePodIsolation`, w8/220), so holding the template does not stop an isolation toggle from applying.
- The roll inputs, read from `keyValueIntent` and the CR:
  - the plan id (connection limit and memory limit);
  - `kv.Spec.InternalAuth`;
  - `intent.credentialRevision` and `intent.authSecretName`;
  - `intent.tlsForwarded()` and `intent.tlsSecretName`.
- w6/m512 t004's internal-auth cut lists terminating proxy pods and compares their `BEX_KV_INTERNAL_AUTH` with the store's mode. It must keep working: enabling internal auth changes an input, so it rolls.
- Render basis and the ceiling: see README § Findings.

## Steps

1. Record a digest of the roll inputs on the Deployment's own `metadata.annotations` (e.g. `app.bex.co/kv-internal-proxy-inputs`). Hash a stable encoding, not a Go `%v` of a struct.
2. In the mutate function, after rendering: if the Deployment existed, its recorded inputs equal the current ones, it runs a pod (`before` replicas > 0 and desired replicas > 0), and t002's override does not apply, restore `dep.Spec.Template` to `before`. Otherwise keep the rendering, with the manager's image, and record the inputs.
3. **Adoption.** A Deployment with no inputs record is recorded, keeping its template, when that template equals the current rendering (m469's image hold included). Otherwise it takes the rendering once, as today, and is recorded. A test covers both paths, including a pre-m512 template (no `BEX_KV_DRAIN_SECONDS`), which must roll once.
4. Keep `keyValueInternalDeploymentReady` and the readiness gating unchanged.
5. Log, once per held store and manager process, that a proxy holds a template other than the current rendering. The log names the store, not the diff.

## Acceptance criteria

- [ ] A settled Deployment's template is byte-identical after passes of a manager with a different `InternalProxyBinary`, a different `InternalProxyImage`, and a rendering that adds an env var.
- [ ] A plan change, enabling internal auth, a credential-revision change, and a TLS-forwarding change on a static-listener store each change the template once, onto the manager's image, with the full current rendering. A second pass changes nothing.
- [ ] Suspend then resume: the resumed template is the current rendering.
- [ ] Adoption: a matching template is recorded with no template change, and a pre-m512 template rolls once, then holds.
- [ ] The w6/m512 internal-auth cut tests and the w6/m484 fleet guard still pass.
- [ ] `make test` and `make lint` (from `lego/operator/`) pass.
