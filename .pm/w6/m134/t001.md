## Objective

Choose the service-event type and bounded detail shape for project/environment reassignment without reusing the misleading existing `service_environment_changed` env-var event.

## Context

- `lego/backend/internal/events/service.go` owns the service event vocabulary.
- `service_environment_changed` already means an env-var/config rollout.
- `.pm/w6/done/054.md` contains the live evidence and naming trap.

## Steps

1. Capture Render's equivalent behavior and decide whether the event is parity or a documented bex extension.
2. Define one stable type and details that distinguish project and environment moves and represent absent placement.
3. Document the vocabulary decision before emission code depends on it.

## Files

- `lego/backend/internal/events/service.go`
- `docs/ADR018-render-parity.md`

## Acceptance criteria

- [ ] The selected type cannot be confused with the existing env-var-change event.
- [ ] Details use public project/environment identifiers and cover assign, move, and unassign.
- [ ] The parity or extension decision is recorded with dated evidence.

## Out of scope

- Changing the runtime precedence or rollout behavior of environment variables.
