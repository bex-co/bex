# ADR026 §7a's "bex ahead" paragraph misdescribes Render's Public Git Repository

Why: the paragraph rests a parity judgement on a false premise about Render, and the next reader will trust it.

- **Where:** `docs/ADR026-github-integration.md` line 139 (the "**bex ahead** (w6/m99)" paragraph under §8) says "a Render service can only be created from a repo its connected credential already covers, so 'auto-deploy is on but nothing can deliver a push' cannot arise there".
- **What Render does:** its create form has a **Public Git Repository** option. Services created from it use no Git-provider credential, so Render does not support auto-deploys or PR previews for them, and its docs advise that method only for a public repository you don't belong to ([web services](https://render.com/docs/web-services), [deploys](https://render.com/docs/deploys)). The Render community also reports Auto-Deploy showing "Yes" on such a service while pushes never deploy ([forum](https://community.render.com/t/does-auto-deploy-on-public-repo-work/25963)). The recommended path is a deploy hook called from CI, which bex already serves (`lego/backend/internal/deploys/deployhook.go`, `ref`/`imgURL` supported).
- **Fix:** rewrite the premise. The state does arise on Render; Render just doesn't report it. bex's `pushDeliveryMethod: unavailable`, plus the dashboard hint that names the Deploy Hook (`dashboard/src/features/services/locales/en.ts:2766`), stays a bex-ahead disclosure, not a divergence. Keep the conclusion and the "internal parity" requirement. Run prettier.
- **Source:** this session's 2026-11-10 review of public-URL Blueprints against Render (`/pm-brainstorm for w6`, item 6).
