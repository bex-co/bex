## Objective

Close the remaining two lower-urgency corners of the same root cause: the attribute-only usage (lower severity, but still worth fixing for consistency and because a `title=` tooltip showing a wrong time on hover is still a real, if minor, defect), and the deploy-header path that is currently correct only by accident.

## Context

- `dashboard/src/routes/services.$serviceId.events.tsx:341,390` — `const exactTimestamp = formatDateTime(timestamp)`, used only as `<time dateTime={timestamp} title={exactTimestamp}>` (the visible child is a different, `formatRelativeAge`-based value already in `w6/m102`'s scope). React patches attribute mismatches during hydration (unlike text nodes), so this does not throw #418 and self-corrects almost immediately after mount — lower severity, but still shows a wrong tooltip for a brief window on a fresh load. Apply the primitive here too for consistency.
- `dashboard/src/features/deploys/lib/deploy-presentation.ts`'s `formatDeployTimestamp` (thin wrapper around `formatDateTime`), consumed by `dashboard/src/features/deploys/components/deploy-header.tsx:62-83`. This path is currently "correct" only because `DeployHeader` renders a loading `Skeleton` until its `deploy` prop resolves client-side (`:44-60`), so SSR never emits the real text — not a fix. Apply the primitive here defensively so a future change that makes the deploy query SSR-blocking (matching the pattern several other detail routes already use, per `dashboard/CLAUDE.md`'s "Navigation pending states" section) can't silently reintroduce this exact bug.

## Steps

1. Route `services.$serviceId.events.tsx`'s `exactTimestamp` through t001's primitive.
2. Route `deploy-presentation.ts`'s `formatDeployTimestamp` (or its `deploy-header.tsx` call sites) through the same primitive.
3. Confirm `deploy-header.tsx`'s existing skeleton-gate behavior is unaffected — this task adds defense-in-depth, it does not change the loading-state UX.
