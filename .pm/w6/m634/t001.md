## Objective

Decide and record how an instance's last health-check result travels from the kubelet to the App's status. Record Render's messages and the mapping from each check outcome to them.

## Context

- Probes (`lego/operator/internal/controller/health_probe.go`): a Health Check Path is an exec probe running the helper's `check` (`:64-68`); Render's default check is the helper's `open-port` (`:82-84`); some instances use the kubelet's TCP probe. The timeout is `healthCheckTimeoutSeconds` = 5 (`deployment_projection.go:99`).
- The kubelet records a failed probe as an `Unhealthy` event on the pod: an exec probe's message carries the command's output, a TCP probe's the dial error. When the command overruns, the kubelet reports a command timeout instead.
- The operator's RBAC on events is `create`/`patch`/`update` (`lego/operator/config/rbac/role.yaml`; kubebuilder marker in `database_controller.go:943`).
- Render's messages: `HTTP health check failed (timed out after 5 seconds)`, `HTTP health check failed with status code <N>`, and on restart `connection refused` or `i/o timeout` (render.com/docs/troubleshooting-deploys).

## Steps

1. Compare the recommended on-demand list of a failing pod's `Unhealthy` events (namespaced `get`/`list`, no watch) with a file the helper writes for a node-side reader. Write down the choice and why.
2. Name the App status field, its length bound and when it clears (the next passing check or the next release).
3. Map each outcome (status code, timeout, refused, unreachable, command timeout) to Render's message.
