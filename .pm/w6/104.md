# The runner host's Docker VM is far smaller than the 12 runners it serves

Why: since w6/m155 the native image builds (qemu-emulated, CPU-heavy) run on `bex-build` at the same time as production deploys, on one Docker Desktop VM. If they compete for CPU, a deploy build slows down even though it no longer waits for a runner.

- **Evidence (2026-11-02):** the Docker Desktop VM has 15 CPU / ~51 GB (`docker info`), while the host has 28 CPU / 96 GB. It runs 7 `bex-ci` + 2 `bex-build` + 3 `bex-production` runners, each with a 4 CPU / 8 GB burst limit (48 CPU / 96 GB at full burst) and 0.5 CPU / 512 MB reserved.
- **Do:** measure a deploy `build` job's duration with and without a concurrent native build (`docker stats` sampling plus job timings). If contention shows, write an action card for the user: Docker Desktop → Settings → Resources (CPUs/memory) to a recommended size, and how to confirm it took (`docker info`). Optionally lower `bex-build` burst limits so builds cannot starve the production pool's CPU.
- **Expected:** deploy builds keep their usual duration while image builds run, or the measurement shows there is no contention and the note closes.
