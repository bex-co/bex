## Objective

Lock in t001/t002's fix with tests that assert the JSON key is PRESENT (as `[]`) on a fixture with zero entries — not just that the value is correct when non-empty, which is what today's tests already cover and is exactly why this bug shipped unnoticed.

## Context

- Existing coverage only tests the non-empty case (mirrors how `w6/m106`'s own investigation found `TestRESTCreateWithIPAllowListAndReadBack` "passes today because it asserts the top-level field, encoding the bug rather than catching it" — same lesson applies here: a test that never constructs the EMPTY case can't catch an omitempty regression).
- Test packages: `lego/backend/internal/postgres/*_test.go`, `lego/backend/internal/keyvalue/*_test.go`.

## Steps

1. Postgres: add/extend a REST test that creates (or fixtures) a Postgres with no `ipAllowList` and no `readReplicas`, then asserts the raw JSON body of `GET`/list/create/PATCH responses contains the literal keys `"ipAllowList":[]` and `"readReplicas":[]` — decode into `map[string]json.RawMessage` (or equivalent) so a MISSING key fails the test, not just a wrong value.
2. Postgres: add an MCP test calling `get_postgres` (and ideally `list_postgres_instances`) on the same zero-entry fixture, asserting the same key-presence contract on the tool's structured output.
3. Key Value: same two tests (REST + MCP) for `ipAllowList` on a zero-entry fixture.
4. Regression control: re-run (or add if missing) the non-empty case for both resource types — a fixture WITH a saved CIDR entry (and, for Postgres, a named read replica) — asserting the value round-trips correctly through REST, GraphQL, and MCP alike. This must keep passing unchanged.
5. `cd lego/backend && go test ./internal/postgres/... ./internal/keyvalue/...` green.
