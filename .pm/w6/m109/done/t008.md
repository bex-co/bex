## Objective

The same `omitempty`-on-a-Render-required-field defect this milestone fixed for `ipAllowList`/`readReplicas`, on a third field family the original filing did not reach: `externalConnectionString` on the **connection-info** endpoints. `t001`/`t002` already established the fix pattern; this applies it one endpoint over.

## Context

Found live 2026-08-27, 54th `/qa-find-bugs` run, journey 12 (Key Value), on a `qa-` Key Value created and deleted in the same run plus a read of a pre-existing Postgres. **Key lists only — no values were captured.**

```
GET /v1/key-value/red-da880pfm2e9c73ft5u6g/connection-info
  -> keys: ["internalConnectionString", "cliCommand"]

GET /v1/postgres/dpg-d9nqg95cavls73fp8m20/connection-info
  -> keys: ["password", "internalConnectionString", "psqlCommand"]
```

Render's pinned spec (`lego/backend/internal/api/openapi/render-public-api-1.json`) marks the field **required** on all three connection-info schemas:

```
keyValueConnectionInfo   required: [internalConnectionString, externalConnectionString, cliCommand]
redisConnectionInfo      required: [internalConnectionString, externalConnectionString, redisCLICommand]
postgresConnectionInfo   required: [password, internalConnectionString, externalConnectionString, psqlCommand]
```

The cause is the same tag this milestone has been removing:

- `lego/backend/internal/keyvalue/service.go:136` — `ExternalConnectionString string \`json:"externalConnectionString,omitempty"\``
- `lego/backend/internal/postgres/service.go:183` — same
- `lego/backend/internal/postgres/service.go:199-200` — a second struct (the pooled variant) carries `omitempty` on **both** `InternalConnectionString` and `ExternalConnectionString`; check it against `postgresConnectionInfo`'s `internalConnectionPoolString`/`externalConnectionPoolString`, which Render does **not** list as required — so that struct may be correct as-is. Decide deliberately rather than sweeping it.

**The control is the neighbouring field.** `keyvalue/service.go:135` and `postgres/service.go:182` declare `InternalConnectionString` with **no** `omitempty` — the required-field treatment is already right there, one line up, which is why the internal string is always present and the external one vanishes.

**Difference from t001/t002:** those fields are arrays and were nil-coalesced to `[]T{}`. This is a **string**, so the fix is just dropping `omitempty` — an absent external endpoint is correctly the empty string, not a fabricated value. Do not invent a placeholder host.

## Why the original filing missed it

`m109`'s Source section states it "Exhaustively checked every other `required` field on **both schemas**" — that check covered the `postgres` and `keyValue` **resource** schemas. The `*ConnectionInfo` schemas are separate objects behind separate endpoints and were outside that sweep. The claim was correct for its scope; this is the scope's edge, not a contradiction of it.

## Steps

1. Drop `omitempty` from `ExternalConnectionString` in `keyvalue/service.go:136` and `postgres/service.go:183`.
2. Decide the pooled struct at `postgres/service.go:199-200` against Render's non-required pool fields; leave it alone if correct, and say so.
3. Confirm GraphQL is unaffected — `KeyValueConnectionInfo` already declares all three fields (`cliCommand`, `externalConnectionString`, `internalConnectionString`), so GraphQL returns the empty string today and REST is the only surface that drops the key. Check the Postgres GraphQL equivalent the same way.
4. Check MCP's connection-info tool output, which `t003` covered for the resource objects but not for this endpoint.
5. Extend `t003`'s regression tests: a **non-public** datastore's connection-info response has the key present as `""` on REST and MCP; a public one still carries a real value.
