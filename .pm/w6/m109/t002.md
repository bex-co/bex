## Objective

Key Value has the identical bug in TWO separate structs (unlike Postgres, REST does not embed `KeyValueView` directly): `KeyValueView.IPAllowList` (`lego/backend/internal/keyvalue/service.go:95`, used by MCP) and the REST-only `renderKeyValue.IPAllowList` (`lego/backend/internal/keyvalue/rest.go:66`, fed from `KeyValueView.IPAllowList` at `rest.go:89`). Both need `omitempty` dropped and the slice nil-coalesced to `[]core.IPAllowListEntry{}`, matching t001's Postgres fix and the existing `environments/rest.go` pattern.

## Context

- `lego/backend/internal/keyvalue/service.go:95` — `IPAllowList []core.IPAllowListEntry \`json:"ipAllowList,omitempty"\`` on `KeyValueView`, returned directly by 5 MCP handlers in `keyvalue/mcp.go` (`get_key_value`, `list_key_values` via `listKeyValueResult{KeyValues []KeyValueView}`, `create_key_value`, `suspend_key_value`, `update_key_value`).
- `lego/backend/internal/keyvalue/rest.go:66` — `IPAllowList []core.IPAllowListEntry \`json:"ipAllowList,omitempty"\`` on `renderKeyValue`; `toRenderKeyValue` (`rest.go:73-94`) copies `kv.IPAllowList` straight across at `rest.go:89` — fix needs to nil-coalesce here too since it doesn't re-derive from anything else.
- Live-verified bug (2026-08-26 hunt): `GET https://api.bex.co/v1/key-value/red-d9p49kdrtmes73c34ovg` has no `ipAllowList` key; `tools/call get_key_value {keyValueId:"red-d9p49kdrtmes73c34ovg"}` has no `ipAllowList` key; GraphQL `keyValue(id:...){ ipAllowListEntries{cidrBlock} }` returns `[]` correctly for the same resource.
- Reference fix pattern: `lego/backend/internal/environments/rest.go:72,80-84` (see t001's Context for the exact two-line shape).

## Steps

1. Remove `,omitempty` from `keyvalue/service.go:95` and `keyvalue/rest.go:66`.
2. Nil-coalesce `KeyValueView.IPAllowList` to `[]core.IPAllowListEntry{}` at whichever point(s) construct a `KeyValueView` for a response (grep `KeyValueView{` across `keyvalue/*.go` — cover create/get/list/update/suspend, not just the primary read path).
3. In `toRenderKeyValue` (`rest.go:73-94`), nil-coalesce `kv.IPAllowList` the same way before assigning to `renderKeyValue.IPAllowList` (do this even if step 2 already coalesces upstream — keep `toRenderKeyValue` defensive, matching how `toRenderEnvironment` does its own coalescing rather than trusting the view struct).

## Files

- `lego/backend/internal/keyvalue/service.go`
- `lego/backend/internal/keyvalue/rest.go`

## Acceptance criteria

- [ ] `KeyValueView.IPAllowList` and `renderKeyValue.IPAllowList` no longer have `omitempty`.
- [ ] Every code path that builds a `KeyValueView` or `renderKeyValue` for a response nil-coalesces `IPAllowList` to `[]core.IPAllowListEntry{}` when nil.
- [ ] A manual check against a Key Value instance with zero allowlist entries shows `"ipAllowList":[]` via both REST GET and MCP `get_key_value`.
- [ ] A Key Value instance with a real saved CIDR entry still shows the correct non-empty array (no regression).

## Out of scope

- `PostgresView` (covered by t001).
- Redis-specific routes — bex has no separate `/v1/redis` REST surface (confirmed: `grep -rln "\"/v1/redis" lego/backend/internal` returns nothing); `redis`'s Render schema is served identically through the KeyValue routes, so this fix covers it too.
