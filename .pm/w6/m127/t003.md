## Objective

Every free Key Value created through the dashboard before this milestone is running as a pure in-memory cache. `t002` gives them a way out; this task decides whether anyone takes it for them. This is a live-data question, not a code question — do not let `t002` ship as if it retroactively fixed them.

## Context

- Affected stores have `spec.persistenceMode: off` on a plan with a 1 GB disk, so they are losing data on every pod restart while a disk sits unused.
- **Whether any exist is unverified.** The hunt did not inspect the workspace's two pre-existing Key Value stores (`beancount-forum-redis`, `blockeden-forum-redis`) for plan or persistence, and only looked at one workspace. Establish the real population before deciding.
- Changing persistence restarts the store (`t002` establishes exactly what that costs), so a silent bulk migration is not obviously safe — an owner may be relying on cache semantics, and a restart is disruptive regardless.

## Steps

1. Enumerate free-plan Key Value stores with `persistenceMode: off` across workspaces.
2. Decide: migrate automatically, prompt the owner, or leave them and document how to change it.
3. If migrating, sequence it so the restart is expected rather than surprising.
4. Record the decision and the population count where the next person can find it.

## Files

- No code changes necessarily; an operational note plus whatever `t002` exposes

## Acceptance criteria

- [ ] The affected population is counted, not estimated.
- [ ] A recorded decision with reasoning.
- [ ] If left in place, the documented remedy actually works (it depends on `t002`).

## Out of scope

- Changing anything about paid stores, which were never locked.
