## Objective

Pin the parity between the two creation paths and the new update capability, and pin the neighbours that are correct today.

## Context

- The defect existed because nothing compared what the dashboard sends at create with what the API defaults to. A test that only exercises one path cannot catch it — assert on the value the form computes, not merely that the form renders.
- Interesting failure modes: the free lock returning under a different flag; `persistenceMode` accepted by create but silently dropped by patch (today's behaviour); underscore vs hyphenated input diverging between create and update; and `maxmemoryPolicy` regressing while attention is on its sibling.

## Steps

1. Dashboard: assert the free plan's submitted `persistenceMode` equals the API's free-plan default.
2. Dashboard: assert no locale string claims the free plan lacks a disk.
3. Backend: assert `PATCH` changes `persistenceMode`, in both spellings, and that `GET` reflects it.
4. Backend: assert `maxmemoryPolicy` patching is unchanged.
5. Backend: assert create and update reject the same invalid values, via the shared `validate()`.

## Files

- `dashboard/src/routes/__tests__/` (or the keyvalue feature's tests)
- `lego/backend/internal/keyvalue/*_test.go`

## Acceptance criteria

- [ ] `cd lego/backend && go test ./...` and `cd dashboard && yarn test` pass.
- [ ] A test fails if the free-plan persistence forcing returns.
- [ ] A test fails if `persistenceMode` stops being patchable.
- [ ] A test fails if create and update accept different values.

- Live production verification; that is the DoD.
