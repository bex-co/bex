# An unverified session on `/auth/verification` keeps polling `Workspaces` and `ViewerCapabilities`

Why: bex-api refuses every one of these requests with `EMAIL_VERIFICATION_REQUIRED` while the verification wall is up, so the page sends refused traffic every 30s for as long as it stays open. It is the same bug class as w6/078.

Found while reviewing the w6/078 fix (2026-10-19):

- `useWorkspaces` (`dashboard/src/features/workspaces/hooks/use-workspaces.ts:54-56`) and, through it, `WorkspaceProvider` gate on `useIsAuthenticated()`, which is `session != null`.
- An unverified session is non-null, so on `/auth/verification` the `Workspaces` query runs and polls. With a workspace cookie, `CapabilitiesProvider` then polls `ViewerCapabilities` too.
- `handleEmailVerificationRequired` deliberately skips `/auth/` paths (`common/apollo/auth-redirect.ts:80-81`), so nothing stops the loop.
- The UI never needs either answer for that session: `EmailVerificationGate` always blocks it.

To do (sub-hour):

1. Add a verified-session hook. It is `session != null && !emailVerificationRequired(session)`, the rule the root route already applies (`routes/__root.tsx:52`). Keep `useIsAuthenticated` unchanged: `authenticated.tsx` needs plain session semantics.
2. Gate `useWorkspaces` on the new hook.
3. Update the suites that mock `use-is-authenticated` for `useWorkspaces`, and add a test that an unverified session sends nothing.
