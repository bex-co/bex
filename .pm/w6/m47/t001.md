## Objective

A free-tier web service that auto-hibernates after its idle timeout — the dashboard correctly shows "Sleeping to save resources — wakes on the next request." — never actually wakes. Every request to its `.onbex.co` URL after hibernation returns a bare `404 page not found` (Traefik's own default-backend response, not the activator's expected `503` wake page) instead of triggering the wake flow, and the App's `phase` stays `Hibernated` indefinitely across repeated requests. This defeats the entire free-tier sleep/wake value proposition: a hibernated free service becomes permanently unreachable, not merely slow-to-wake.

## Context

- Live repro this run: created `qa-20260822-sleep2` (`web_service`, Docker runtime, repo `bex-co/bex` root `examples/hello-go`) on the Free plan, set Idle timeout to the minimum `5 min`, let it sit idle with zero requests to the app (only dashboard/GraphQL reads, which do not count as app traffic) for 5+ real minutes (verified via wall-clock, not the wait tool's own duration report — see Unverified below), then queried GraphQL directly (`{ server(id: "...") { phase } }`) and got `"Hibernated"`. Before hibernation, `curl -sSI https://qa-20260822-sleep2.onbex.co` had returned a clean `HTTP/2 200` (the app's own `hello-go listening on 3000: "OK"` response, 2-byte body).
- After hibernation, three separate `curl -D -` requests spaced 5–20s apart all returned identically:
  ```
  HTTP/2 404
  content-type: text/plain; charset=utf-8
  x-content-type-options: nosniff
  content-length: 19

  404 page not found
  ```
  This exact body/header shape is Traefik's own default-backend 404, not the activator's response. The activator's handler (`lego/operator/cmd/activator/main.go:134-160`) never returns this shape for any code path: a cache-miss host returns `503` + `"service unavailable"` (`main.go:147`), a live app returns `503` + either the JSON `{"error":"service hibernated","retryAfter":5}` or the HTML wake page (`writeWakeResponse`, `main.go:210-222`) — never a bare 404. A re-query of `{ server(id) { phase } }` immediately after each curl still returned `"Hibernated"` every time — the activator's `wake()` (`main.go:177-208`, which patches `annotLastActive` and scales the Deployment to 1 replica) never fired, meaning the request never reached the activator's handler at all.
- The operator's own Ingress-backend selection looks correct on read: `ingressBackend` (`app_controller.go:1767-1779`) returns `r.ActivatorService`/`r.ActivatorPort` whenever `autoHibernating` is true, and this is computed and passed to `reconcileIngressWithMiddlewares` (line 1678) *before* `parkKubernetes` is invoked (line 1682-1683) — so on paper the Ingress should already point at the activator Service by the time the App is marked Hibernated. Nothing in this run's static read explains the observed 404; the actual defect is unverified (see below).
- **Not a mislabeling artifact of the adjacent minor bug (t002 in this milestone):** t002 is about the *Events feed* wording ("Service suspended" vs a real hibernate-specific label) and does not touch `Spec.Suspended`, the Ingress, or the activator — confirmed via `grep -rn "\.Spec\.Suspended\s*=" lego/backend/internal/ lego/operator/internal/` returning zero operator-side writers. These are two independent findings; do not conflate their root causes.
- **Ruled out this run** (do not re-investigate): the operator never writes `.Spec.Expose`/`.Spec.Suspended` (grep-confirmed, see t002 and w6/m46/t001's sibling investigation); `applyClusterIPService` never sets a k8s Service `Type` (stays `ClusterIP`, so this isn't a LoadBalancer-bypass); the activator's own handler code has no 404 path for any input.

## Steps

1. Get cluster access (this run was browser-only QA against production with no `kubectl`) and, on a fresh repro (create a new Free service, set idle timeout to 5 min, let it hibernate), inspect the actual Ingress object for the hostname: `kubectl get ingress <app-name> -o yaml` — confirm whether `spec.rules[].http.paths[].backend.service.name` actually reads the activator Service name, or still points at the app's own (now-scaled-to-0) Service, or the Ingress is missing/stale entirely.
2. Check the activator pod's own logs (`kubectl logs -n <activator-ns> deploy/bex-activator`) during a wake attempt — confirm whether the request ever reaches it (a `"waking app"` log line, per `main.go:207`) or never arrives (pointing at an Ingress/routing problem, not an activator-logic problem).
3. If the Ingress backend is stale: bisect why `reconcileIngressWithMiddlewares`/`reconcileIngress` didn't re-patch it — check whether `reconcileIngress`'s own diff-before-write logic (or Traefik's own IngressRoute caching/re-index interval) has a case where a backend-service-name-only change is missed.
4. If the Ingress is correct but the activator never answers: check the activator Service's endpoint readiness (is the activator pod itself healthy?), and whether `BEX_ACTIVATOR_SERVICE`/`BEX_ACTIVATOR_PORT` are actually wired correctly in the production deployment (a misconfigured env var would make `ingressBackend` return an empty or wrong service name, which Traefik would then answer with its own default 404 — this matches the observed symptom shape closely and is the leading hypothesis, but is UNVERIFIED without cluster access).
5. Fix the actual defect once isolated, then live-verify: hibernate a fresh free service, request its URL, and confirm it wakes within the advertised window (dashboard's own wake page mentions `Retry-After: 5`) rather than 404ing.
