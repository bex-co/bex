## Objective

On a service's Logs tab, searching for a term that matches nothing shows a self-contradictory empty state: the title always reads **"No logs yet"** (implying the service has never produced any logs) while the body correctly reads **"No logs match these filters."** (implying logs exist but the filter excludes them). These two lines assert opposite things simultaneously whenever a filter is active and yields zero results.

## Context

- Live repro this run: on `qa-20260822-sleep2`'s Logs tab, with the service actively producing logs (a live-tailed startup line was visible), searching `zzz_no_such_term_xyz` in the "Search logs" box produced:
  ```
  No logs yet
  No logs match these filters.
  ```
  both rendered together in the same `EmptyState` component — confirmed via a fresh page snapshot, not inferred.
- Root cause pinned exactly: `dashboard/src/features/logs/components/log-viewer.tsx:179-188`:
  ```tsx
  } else if (lines.length === 0) {
    body = (
      <EmptyState
        iconName="ScrollText"
        title={t("logs.emptyTitle")}
        description={
          filtered ? t("logs.emptyFilteredBody") : t("logs.emptyBody")
        }
      />
    );
  ```
  The `description` prop correctly branches on `filtered`, but the `title` prop is hardcoded to `t("logs.emptyTitle")` unconditionally. The locale file (`dashboard/src/features/logs/locales/en.ts:129-140`) already has three related keys — `logs.emptyTitle` ("No logs yet", documented as "Empty-state title when the service has produced no logs"), `logs.emptyBody` ("This service hasn't produced any logs yet."), and `logs.emptyFilteredBody` ("No logs match these filters.") — but no `logs.emptyFilteredTitle` counterpart. The asymmetry (body branches on two keys, title only has one) is the bug: whoever added `emptyFilteredBody` did not add a matching filtered title.
- **Verified this is genuinely reachable, not a rare edge case:** any search term, log-type filter, or structured filter that narrows the visible set to zero rows hits this path — a routine action (typo in a search term, an overly specific filter) will trigger it, not just this contrived "type garbage" repro.
- **Blast radius:** `grep -n "emptyTitle" dashboard/src/features/logs/components/log-viewer.tsx` shows exactly one call site (line 183) — this is not a shared component instantiated elsewhere with the same bug, so the fix is single-site.

## Steps

1. Add a `logs.emptyFilteredTitle` locale key (e.g. "No matching logs") to `dashboard/src/features/logs/locales/en.ts` (and any other locale files under `dashboard/src/features/logs/locales/`, e.g. `zh.ts`).
2. In `log-viewer.tsx:183`, branch the title the same way the description already does: `title={filtered ? t("logs.emptyFilteredTitle") : t("logs.emptyTitle")}`.
3. Live-verify: search a non-matching term on a service with real log history and confirm the empty state now shows one internally-consistent message ("No matching logs" / "No logs match these filters."), not the current contradictory pair.
