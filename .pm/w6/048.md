# Cron schedule human-readable description doesn't handle named weekday/month cron fields

Why: a cron job creator who types `MON` instead of `1` gets no plain-English confirmation of what they're about to schedule, even though the exact same schedule typed numerically gets one — a silent, avoidable UX inconsistency on a field where getting the schedule wrong is easy to not notice until the job fires at the wrong time.

Live-verified on the New Cron Job form 2026-08-26 (not submitted — form-only test): typing `0 0 * * 1` shows the helper text "Every Monday at 00:00 · runs in UTC"; typing the semantically identical `0 0 * * MON` (a valid 5-field cron expression — accepted with no validation error) instead shows the generic fallback "A 5-field crontab expression (minute hour day month weekday). Runs in UTC." The backend (`lego/backend/internal/apps/service.go:3422`, `cron.ParseStandard` from `robfig/cron/v3`) accepts both forms identically, so this is a description-only gap, not a validity mismatch — the job would be created and run correctly either way.

Root cause: `dashboard/src/features/services/lib/cron.ts`. `isValidCron`/`resolveValue` (lines 50-56, 83-87) correctly resolve named weekdays/months via the `WEEKDAYS`/`MONTHS` lookup tables before validating, but `describeCron` (lines 99-129) re-parses the raw field strings with its own `/^\d+$/`-only regex tests (e.g. line 121 `/^\d+$/.test(dow)`) instead of reusing `resolveValue` — so a valid named token always falls through every phrase-building branch to `return null` (line 129), and the caller shows no preview.

Fix direction: have `describeCron` resolve `dow`/`month` through the same `resolveValue`/`WEEKDAYS`/`MONTHS` path `isValidCron` already uses before running its digit-based phrase checks, so `MON` and `1` (and `JAN` and `1`) produce the same human-readable description.
