# Runtime rollouts stuck Pending or ContainerCreating fail with no cause

Why: a deploy whose new pod never schedules (or never finishes creating) sits `update_in_progress` for the full 900s budget and then fails with only "rollout did not become healthy within the progress deadline". The user cannot tell a full node pool from a bad image or a broken health check.

- **Live, 2026-10-20 (w6/m148 t007).** Three new starter-plan worker pods never logged a line in 15 minutes: busybox in `bex-canary` and `bex`, then alpine. Over the same window, free-plan web pods started within seconds and existing starter pods kept running.
  - `dep-dbbgng19a20c7385rat0` ended `update_failed` with that generic reason.
  - The events feed and the dashboard showed nothing more.
  - The cause (capacity, image pull or something else) was not visible from any tenant surface.
- **Gap.** `stuckPodMessage` (`lego/operator/internal/controller/app_controller.go:5298`) diagnoses only these Waiting reasons: `CrashLoopBackOff`, image pull, `InvalidImageName` and `CreateContainerConfigError`. `probeStallMessage` covers Running-but-unready pods.
  - A pod with `PodScheduled=False` is not covered: the scheduler's message, e.g. `0/N nodes are available: Insufficient cpu`, never reaches the user.
  - A `ContainerCreating` pod is not covered either.
  - Builds already surface the unschedulable message (`lego/operator/internal/build/build.go:888`); runtime rollouts do not.
- **Fix.**
  - Add an unschedulable case that passes the scheduler's condition message through (pool and tier named, no node names).
  - Add a "still creating after N minutes" case.
  - Table-test both, alongside the existing stall cases.
- Also confirm with someone who has cluster access whether the starter pool was actually full at 06:35–07:20Z. If so, that is a capacity follow-up separate from this diagnosis.
