## Objective

A function builds, for a disk-bearing App and a node, the Job whose one pod holds the App's claim on that node and does nothing else. The operator-workload admission grammar admits it unchanged.

## Context

- **Pattern to follow:** the disk snapshot Job in `lego/operator/internal/controller/disk_backup.go` already mounts the claim beside a running service: the claim source is read-write and only the container mount is read-only (`:326`), and it tolerates the serving pool through `execution.TolerateServingPool`.
- **Admission (`deploy/gitops/base/operator-workload-admission.yaml`):**
  - no `nodeName`, so place the pod with a required node-affinity term `metadata.name In [<node>]` (`diskNodeField` in `disk.go`);
  - a serving-pool toleration only on an App-owned workload (`appOwnedWorkload`: a controller ownerReference to the App plus a pod label `app.bex.co/app` naming it);
  - restricted containers: no added capabilities, no privilege escalation, RuntimeDefault seccomp;
  - `automountServiceAccountToken: false` and the default ServiceAccount;
  - no priority class.
- **Quota and limits:** the namespace's `tenant-compute-quota` counts the pod's requests, limits and pod count, and `tenant-limits` fills in missing requests with 100m and 128Mi (`lego/backend/internal/store/namespaces.go`). Use explicit small values, with a zero CPU request as `diskSnapshotResources` does. A refused create is a fallback in t002, not an error.
- **The image must already be on the node**, because a pull here delays the deploy. Options:
  - the kubelet's sandbox `pause` image (`crictl info` on a tenant node gives its exact reference; tenant nodes run v1.34.9) with `IfNotPresent`;
  - bex's own image (`r.BackupHelperImage`), which a disk pod with a health-probe binary already pulled for its `bex-health-probe-install` init container (`deployment_projection.go:925`). It would need a command that blocks until `SIGTERM`.

  Pick one and record why.
- **Labels:** carry `app.bex.co/app` (admission, and `appPodRequests` then reconciles the App on the holder pod's events), plus a non-empty `app.bex.co/component` such as `disk-holder`. Never `app.bex.co/app-id`: the Services select `app.bex.co/app` plus `app.bex.co/app-id` (`privateServiceProjection`), so the holder must never match them.

## Steps

1. `diskHolderJob(app, node, …)`:
   - name `dskhld-<app>`, or a hash-bounded form within the name limit;
   - an App controller ownerReference;
   - `backoffLimit: 0`, an `activeDeadlineSeconds` just above the 15-minute startup budget as a backstop, and `ttlSecondsAfterFinished`;
   - one container that mounts the claim read-only and runs as non-root with a read-only root filesystem;
   - the serving-pool toleration;
   - `applyPodSpecServerDefaults`.
2. A unit test of the shape: the required node term, the read-only mount over a read-write source, no `app-id` label, the component label, the ownerReference and the deadline.
3. Check it against the admission grammar with the repo's existing policy test harness (`scripts/gitops-validate.sh` or the CEL tests beside `container_policy_test.go`). If none evaluates the workload policy, record how the shape was checked.
