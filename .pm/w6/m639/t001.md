## Objective

Find out whether, and by whom, a WebSocket through bex's edge is closed at 100 minutes. In `bex-canary` (disposable), deploy a paid (Starter) web service that runs a WebSocket echo server. From a client outside the cluster, hold two `wss://<slug>.onbex.co` connections that send a ping every 30 s for 2.5 h, and record when each one closes, how (close frame, FIN or RST) and from which side. As a control, hold one connection through a port-forward straight to a Traefik pod, past the Hetzner load balancer. If the dashboard's Shell reaches bex-api through the same entrypoints, also keep one Shell session open that prints a line every minute.

## Context

- Both tenant entrypoints set `transport.respondingTimeouts.readTimeout: 6000s` (`deploy/gitops/base/values/traefik.values.yaml` lines 91 and 100, w8/207; [ADR022 § Bounded request reading at the tenant edge](../../../docs/ADR022-tenant-isolation.md#bounded-request-reading-at-the-tenant-edge-w8207-2026-10-28)).
- [w6/149](../blocked/149.md) measured that "Traefik v3 sets that deadline on each accepted connection and keeps it through its first-byte peek".
- An outside report measured WebSockets through Traefik closed at exactly `readTimeout`, and kept open with `readTimeout: 0` (github.com/CryptoManufaktur-io/central-proxy-docker/pull/35); see also github.com/traefik/traefik/issues/13820. Nobody has measured it on bex yet.
- A paid service does not sleep, so the activator does not hold the connection. The edge cache passes a request with an `Upgrade` header straight through.
- The Hetzner load balancer closes a flow that carries no data for 1 h (w6/149). A 30 s ping keeps data flowing, so that close does not apply here.

## Steps

1. Create the fixture: a small echo server (any language) that answers pings, on a Starter web service in `bex-canary`.
2. Start the three connections and the Shell session, and timestamp every event.
3. Read the Traefik pod's logs around each close.
4. Delete the fixture.
