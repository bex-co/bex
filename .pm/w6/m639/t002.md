## Objective

Using t001's result and the source of the Traefik version production pins, choose the smallest change after which an upgraded (WebSocket) connection has no read deadline. Then amend ADR022 § "Bounded request reading at the tenant edge" with the choice, its evidence and what still bounds a slow client.

## Context

- The options, in order of preference:
- (a) A Traefik setting or behavior that clears the read deadline once a connection is upgraded, so plain requests keep w8/207's 100-minute bound. Check the pinned version's entrypoint and HTTP server code, and its release notes.
- (b) `readTimeout: 0` on both entrypoints. ADR022 then records the residual w8/207 weighed (a slow client keeps a connection longer), what still bounds it (the edge's resource limits), and that bex-api keeps its own 10 s header and 30 s read deadlines (`cmd/api/main.go:newHTTPServer`).
- **Recommendation, not a user decision:** (a) if the pinned Traefik offers it, otherwise (b), under ADR008 Render parity first. Render documents HTTP responses of up to 100 minutes but no WebSocket maximum. A stricter variant (a separate bound for slow request bodies) is its own follow-up, never a reason to park this.
