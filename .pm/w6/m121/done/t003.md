## Objective

`lego/backend/internal/logs/rest.go:159` reads `Last-Event-ID` to resume an SSE log stream, and the header is not advertised in `Access-Control-Allow-Headers`. Whether that actually breaks a cross-origin `EventSource` reconnect depends on browser behavior the 55th run did not test: the header is set by the browser itself on reconnect rather than by page script, and it is not on the CORS-safelist, so the two plausible outcomes disagree. Settle it by running it.

## Context

- The 55th run measured the advertised list (`Authorization, Content-Type, X-Session-Token`) and located the read, but explicitly did **not** test the reconnect. It is recorded as Unverified on the milestone; do not let it graduate to a fact without this task.
- Indirect evidence that it may not be broken: the dashboard's live log tail works (journey 7 of prior hunts), and the dashboard is cross-origin to `api.bex.co`. That is suggestive, not conclusive — the first connection carries no `Last-Event-ID`, so a working tail says nothing about the **reconnect** path.
- `t002` is blocked on this answer for one line of its change; the rest of `t002` does not depend on it.

## Steps

1. From `https://dashboard.bex.co`, open an `EventSource` against the cross-origin SSE log route with credentials.
2. Force a reconnect (kill the stream server-side, or drop the network in devtools) so the browser reissues with `Last-Event-ID`.
3. Record whether a preflight is sent, and whether it fails on the header. Capture the raw request/response, not the rendered console text.
4. Repeat on a second browser engine if convenient — this is a spec-interpretation area where engines have historically differed.
5. Write the answer into `t002`'s comment and onto the milestone, whichever way it lands.

## Completion evidence

- Live Google Chrome 152.0.7977.65 cross-origin `EventSource` probe, with the server deliberately omitting `Last-Event-ID` from `Allow-Headers`: first request `GET`, `Origin: http://127.0.0.1:<page-port>`, no cursor; server emitted `id: cursor-1` and closed; reconnect request `GET`, same Origin, `Last-Event-ID: cursor-1`; **zero `OPTIONS` requests**. Both messages arrived. Raw capture came from the receiving server, not browser console rendering.
- Answer consumed by t002: **EventSource's browser-owned `Last-Event-ID` reconnect header does not preflight in Chrome, so it need not be advertised. Resume is not degraded by the CORS header list.** This agrees with HTML's EventSource reconnect algorithm and Fetch's unset unsafe-request flag for the API.
- A signed-in run against the production log route was unavailable because `QA_EMAIL`/`QA_PASSWORD` are empty; this is recorded rather than presented as production observation. The real-engine cross-origin capture settles the browser behavior the task asks about; no second engine was run.
