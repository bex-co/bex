## Objective

`EnvGroupView.EnvironmentID` (and the identically-shaped `ProjectID`/`EnvironmentID` fields on `AppView`, `PostgresView`, `KeyValueView`) are bare Go `string` fields whose zero value, `""`, means "no relationship." REST already treats that correctly — `json:"environmentId,omitempty"` omits the key entirely. GraphQL does not: `gqlutil.StrField` resolves the raw Go string, so a workspace-scoped env group's `environmentId` comes back as `""` over GraphQL instead of `null`, and the two surfaces now disagree about the same underlying value for the same resource. Fix this at the shared resolver layer so every current and future optional-FK field inherits the correct behavior, the same way `w6/m44`'s `gqlutil.NilOnError` fixed the sibling "whole zero-value object" bug.

## Context

- Confirmed live today: `POST /graphql {"query":"{ envGroup(id:\"evg-da583mo09vvc73fbr2c0\"){ environmentId } }"}` → `{"data":{"envGroup":{"environmentId":""}}}`; `GET /v1/env-groups/evg-da583mo09vvc73fbr2c0` → response body has no `environmentId` key.
- Confirmed live today: `POST /graphql {"query":"{ service(id:\"srv-da583dg09vvc73fbr2ag\"){ projectId environmentId } }"}` → `{"data":{"service":{"environmentId":"","projectId":""}}}` for a service with no Environment and (despite a Project being selected in its create form) no actual Project association.
- `lego/backend/internal/envgroups/service.go:177` — `EnvironmentID string \`json:"environmentId,omitempty"\`` on `EnvGroupView`.
- `lego/backend/internal/envgroups/graphql.go:53` — `"environmentId": gqlutil.StrField(func(g EnvGroupView) any { return g.EnvironmentID })`.
- `lego/backend/internal/gqlutil/gqlutil.go:54-60` — `Typed`/`StrField`: generic field-resolver helpers, no empty-string-means-null convention today.
- Same shape, not yet independently reprobed this run — confirm each before migrating: `lego/backend/internal/apps/graphql.go:380-381` (`AppView.ProjectID`/`EnvironmentID`, struct at `lego/backend/internal/apps/service.go:417-418`); `lego/backend/internal/postgres/graphql.go:61-62` (`PostgresView.ProjectID`/`EnvironmentID`, struct at `lego/backend/internal/postgres/service.go:142,148`); `lego/backend/internal/keyvalue/graphql.go:51-52` (`KeyValueView.ProjectID`/`EnvironmentID`, struct at `lego/backend/internal/keyvalue/service.go:111,117`).
- **Independently confirmed live (2026-08-23), using pre-existing ungrouped resources, no mutation:** `POST /graphql {"query":"{ database(id:\"dpg-d9nqg95cavls73fp8m20\"){ projectId environmentId } keyValue(id:\"red-d9p49kdrtmes73c34ovg\"){ projectId environmentId } }"}` → `{"data":{"database":{"environmentId":"","projectId":""},"keyValue":{"environmentId":"","projectId":""}}}`; matched `GET /v1/postgres/dpg-d9nqg95cavls73fp8m20` and `GET /v1/key-value/red-d9p49kdrtmes73c34ovg` both have no `environmentId`/`projectId` keys in their response bodies. Same leak, both types — step 3 and acceptance criterion 2 below are satisfied for `postgres`/`keyValue`; only `apps`'s `service` leak remains previously-confirmed (see above) and `apps` still needs the same live check repeated post-migration.
- GraphQL's query field for Postgres is `database`, not `postgres` (see `lego/backend/internal/postgres/graphql.go:31-33` — deliberate Render-name split, REST stays `/v1/postgres`).
- `environments/graphql.go:35`'s `EnvironmentView.ProjectID` is a **different** case — every Environment has a required, non-optional Project (`environments/service.go:190` has no `omitempty`) — leave it untouched; migrating a genuinely-required field to nullable would be a regression, not a fix.
- `w6/m44` (shipped `bdad3db4` the same day) fixed a related but distinct bug: `gqlutil.NilOnError` nulls an entire resolved *object* when its resolver *returned an error* (dead-id lookups). This task is about one *field* inside a successfully-resolved object whose zero value is a legitimate "unset" state — `NilOnError` doesn't touch it, and shouldn't be reused for it.

## Steps

1. Add a shared helper in `lego/backend/internal/gqlutil/gqlutil.go` (e.g. `OptionalStrField`) that resolves a field to `nil` when the underlying Go string is `""`, and to the string otherwise — same signature shape as `StrField` so call sites are a one-line swap.
2. Migrate `envgroups/graphql.go:53`'s `environmentId` resolver to the new helper. Confirm via a fresh probe that `envGroup(id:<workspace-scoped>){environmentId}` now returns `null`.
3. Independently probe `postgres(id:)`/`keyValue(id:)`'s `projectId`/`environmentId` for a resource with no Project/no Environment (create one via the QA workspace or check an existing ungrouped resource) to confirm they exhibit the same `""` leak before migrating them. Migrate `apps/graphql.go:380-381`, `postgres/graphql.go:61-62`, `keyvalue/graphql.go:51-52` to the same helper once confirmed.
4. For any of the three that does *not* reproduce the leak (e.g. if some other code path already nulls it), leave it unmigrated and note why in this task's completion notes rather than changing working code.
5. Run `cd lego/backend && go test ./...` — confirm no existing test asserted the old `""` behavior as correct (a test doing so is itself evidence of the bug, not a reason to keep it; update it to expect `null`).
