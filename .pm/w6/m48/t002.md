## Objective

Once t001 makes GraphQL return `null` for a workspace-scoped env group's `environmentId`, the dashboard's own `?? null` normalization (which only ever caught `null`/`undefined`, never `""`) becomes correct by construction for the *new* wire shape — but it was silently covering for the bug, not actually handling it, so harden it defensively and verify the three broken UI consumers now behave correctly. This is the "belt and suspenders" half: a future resolver regression on any of these fields should not be able to silently reintroduce this exact class of bug.

## Context

- `dashboard/src/features/env-groups/hooks/use-env-groups.ts:51` — `environmentId: raw.environmentId ?? null`. After t001 this is already correct for the new wire shape, but change it to explicitly treat `""` as `null` too (`raw.environmentId || null`, or an explicit check) so it doesn't quietly regress if a future GraphQL change reintroduces an empty string anywhere in the chain.
- `dashboard/src/features/env-groups/components/linked-services-card.tsx:45-47` (`isCompatible`) and `:132-136` (the "Legacy link" warning render) and `:50-53`/`:99` (the `available` list gating the "Link Service" select+button).
- `dashboard/src/features/env-groups/components/env-group-actions.tsx:78-79,95` (`moveTarget` init) — apply the identical defensive normalization.
- Live-observed today (pre-fix): a workspace-scoped group linked to a workspace-scoped service showed "Legacy link outside this group's Environment" on that link; the same group's detail page had **no** "Select a service" / "Link Service" control visible at all, despite 5 other environment-less services existing unlinked in the same workspace; "Manage → Move group" showed the placeholder "Select an Environment" instead of "Workspace (no Environment)".

## Steps

1. Harden `use-env-groups.ts:51` and `env-group-actions.tsx:78-79,95` to treat `""` as `null`/`WORKSPACE_SCOPE` defensively (not just relying on t001's backend fix).
2. Manually verify against dev-6 or a QA workspace: a workspace-scoped Environment Group with a workspace-scoped linked service shows no "Legacy link" warning; the "Link Service" control is visible and lists other unlinked, environment-less services; "Move group" pre-selects "Workspace (no Environment)".
3. Verify the negative case still works: a service that genuinely *is* in a different Environment than the group still shows "Legacy link" and is still excluded from `available` — confirm `isCompatible`'s core comparison logic is unchanged, only its treatment of the "both sides unset" case.
