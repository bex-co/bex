# w6 · m48 — GraphQL leaks empty-string zero-values as real optional-FK data; Project-only create-form selection is a silent no-op

**Worker:** worker6 **Goal:** an unset optional relationship (a group's Environment, a service/database/key-value store's Project or Environment) is distinguishable from "the id is the empty string" by any GraphQL client — matching what REST already does via `omitempty` — so the dashboard's Environment Group page stops showing a false "Legacy link" warning, stops hiding its own "Link Service" control for the most common (no-Environment) configuration, and its "Move group" dialog stops rendering a blank placeholder over a real "Workspace" scope; and the shared create-form's Project/Environment hint stops implying that picking a Project alone does something it doesn't. **Status:** todo

## Definition of done

Verified on production (or dev-6) while signed in, and via a repeatable probe or click for each line:

- `POST /graphql {"query":"{ envGroup(id:\"<id-of-a-workspace-scoped-group>\") { environmentId } }"}` returns `"environmentId": null` — not `""` — for a group with no Environment. Confirmed today live: `GET /v1/env-groups/<id>` (REST) already omits the key entirely for the same group; GraphQL is the one surface still leaking the Go zero value.
- The identical live-verifiable null/omitted agreement holds for the other six call sites sharing the same `gqlutil.StrField(func(v T) any { return v.ProjectID/EnvironmentID })` pattern (`lego/backend/internal/apps/graphql.go:380-381`, `lego/backend/internal/postgres/graphql.go:61-62`, `lego/backend/internal/keyvalue/graphql.go:51-52`) — one probe per type (`service`, `postgres`, `keyValue`) against a resource with no Project/no Environment, each compared to its REST equivalent.
- On an Environment Group with no Environment ("Workspace (no Environment)") linked to a service that is *also* in no Environment: the group detail page shows **no** "Legacy link outside this group's Environment" warning on that link (today: it always shows, for every such link, in every workspace-scoped group).
- On that same group's detail page, with at least one other environment-less, unlinked service in the workspace: the "Select a service" dropdown + "Link Service" button are visible and that service is a selectable option (today: `available.length === 0` for a workspace-scoped group hides the entire control, functionally preventing linking a second service to a plain Environment Group through the UI).
- Opening "Move group" on a workspace-scoped group pre-selects "Workspace (no Environment)" in the Environment combobox (today: the combobox shows its placeholder, "Select an Environment", because `moveTarget`'s init (`group.environmentId ?? WORKSPACE_SCOPE`) never catches the empty-string sentinel).
- A cross-scope link (a service that genuinely *is* in a different Environment than the group, or vice versa) still shows the "Legacy link" warning and is still excluded from "available" — the fix narrows the false-positive case, it does not silence real mismatches. Confirm by linking (or inspecting) one such genuinely-incompatible pair.
- Creating a Web Service, Database, or Key Value store from its "New" form, selecting a Project and leaving Environment unset, no longer shows copy implying that choice already associated the resource with the project (current copy: "Optional. Selecting an environment also adds the resource to its project." — the word "also" implies the Project pick already did something; it did not, confirmed live: the created resource's `projectId` came back `""` over GraphQL and the resource never appeared on the chosen project's page). This is a **copy fix**, not a behavior change — Project membership flowing only through Environment assignment is confirmed intentional design (`w1/m32`, `w5/m25`: "assignment auto-joins the parent project"), out of scope to alter here.
- `cd lego/backend && go test ./...` + `make lint` green; `dashboard/`: `yarn typecheck && yarn lint && yarn test` green.

## Source + Goal linkage

- **Source:** live `/qa-find-bugs` hunt of `https://dashboard.bex.co`, 2026-08-22–23, signed in as the QA user, workspace `tea-d98210cbbpdc73dcrkvg`. Evidence: raw GraphQL/REST probes run from inside the authenticated page (`page.evaluate`/`fetch(..., {credentials:'include'})`), quoted in each task below; screenshot `.playwright-mcp/qa-domains-1.png` (an unrelated custom-domain probe run the same session, confirmed correct against `docs/render-artifacts/custom-domain-dns-instructions.md` and not filed).
  - `envGroup(id:"evg-da583mo09vvc73fbr2c0"){environmentId}` → `{"data":{"envGroup":{"environmentId":""}}}` while `GET /v1/env-groups/evg-da583mo09vvc73fbr2c0` → body has no `environmentId` key at all.
  - `service(id:"srv-da583dg09vvc73fbr2ag"){projectId environmentId}` → `{"data":{"service":{"environmentId":"","projectId":""}}}` for a service created via "+ New Service" from inside project `qa-20260822-hunt3`'s own page, with that project pre-selected in the create form — the service never appeared anywhere on the project's Overview page (`No environments yet.`, no ungrouped-within-project listing).
  - Live-observed consequences: the Environment Group detail page rendered "Legacy link outside this group's Environment" on a link that is not legacy by any accessible definition; its "Manage" → "Move group" dialog rendered the placeholder "Select an Environment" over a group whose Metadata panel, one scroll up, already read "Workspace (no Environment)"; its "Link Service" affordance was entirely absent despite 5 other environment-less services existing in the same workspace.
- **Root cause (traced):**
  - `lego/backend/internal/envgroups/service.go:177` — `EnvGroupView.EnvironmentID` is a bare `string` (zero value `""`), not a pointer/nullable type.
  - `lego/backend/internal/envgroups/graphql.go:53` — `gqlutil.StrField(func(g EnvGroupView) any { return g.EnvironmentID })` returns that raw `""` as the resolved GraphQL value instead of `nil`; `gqlutil.StrField`/`Typed` (`lego/backend/internal/gqlutil/gqlutil.go:54-60`) has no empty-means-null convention.
  - REST (`lego/backend/internal/envgroups/service.go:177`'s `json:"environmentId,omitempty"` tag, consumed by the plain-`encoding/json` REST handler) already omits the field for `""` — REST and GraphQL disagree today on the exact same underlying value.
  - `dashboard/src/features/env-groups/hooks/use-env-groups.ts:51` — `environmentId: raw.environmentId ?? null` only normalizes `null`/`undefined`, not `""`, so the dashboard's own `EnvGroupView.environmentId` inherits the wire bug as `""`.
  - `dashboard/src/features/env-groups/hooks/use-env-group-scope-index.ts:89-97` — `serviceEnvironmentById` is built only from real Environments' `serviceIds`, so an environment-less service is simply absent from the map, and `.get(id) ?? null` correctly yields `null` for it — the *service* side is correct; only the *group* side leaks `""`.
  - `dashboard/src/features/env-groups/components/linked-services-card.tsx:45-47` — `isCompatible` compares `null !== ""` and returns `false` for every environment-less service against an environment-less group, which both (a) drives the "Legacy link" warning at `:132-136` and (b) empties the `available` list at `:50-53`, hiding the entire link-a-service control (`:99` — `available.length > 0 ? (…) : null`).
  - `dashboard/src/features/env-groups/components/env-group-actions.tsx:78-79,95` — `moveTarget`'s init, `group.environmentId ?? WORKSPACE_SCOPE`, has the identical gap, so the "Move group" `<Select value={moveTarget}>` never matches its `WORKSPACE_SCOPE` (`"__workspace__"`) `SelectItem` and falls back to the unselected placeholder.
  - Blast radius (same anti-pattern, not yet confirmed to have a live UI consumer beyond the above — see t001/t004): `lego/backend/internal/apps/graphql.go:380-381` (`AppView.ProjectID`/`EnvironmentID`), `lego/backend/internal/postgres/graphql.go:61-62` (`PostgresView.ProjectID`/`EnvironmentID`), `lego/backend/internal/keyvalue/graphql.go:51-52` (`KeyValueView.ProjectID`/`EnvironmentID`) — all bare `string` fields (`lego/backend/internal/apps/service.go:417-418`, `lego/backend/internal/postgres/service.go:142,148`, `lego/backend/internal/keyvalue/service.go:111,117`) resolved through the identical `gqlutil.StrField` call shape. Confirmed live for `service`: `projectId`/`environmentId` both leak `""`. `postgres`/`keyValue` share the exact code shape but were not independently live-probed this run — t001 must confirm each before migrating it.
  - The Project-only-selection no-op: `dashboard/src/features/environments/components/project-environment-selector.tsx` (shared by `dashboard/src/routes/services.new.tsx`, `dashboard/src/routes/keyvalue.new.tsx`, `dashboard/src/features/databases/components/create-database-dialog.tsx`) — its own doc comment states the intended design plainly: "Project scopes the Environment list; only the Environment id is submitted because assignment auto-joins its parent Project." `dashboard/src/features/services/lib/create-service-input.ts:159-196` (`buildCreateServiceInput`) confirms: it emits `environmentId` (line 163) and never references `form.projectId` at all — matching the backend's `lego/backend/internal/apps/service.go:1428-1440` (`CreateRequest`), whose only membership field is `EnvironmentID` ("optionally assigns the new service to an existing environment (and therefore that environment's project)"). The mechanism is intentional and correct; only `dashboard/src/features/environments/locales/en.ts:318-322` (+ `zh.ts`)'s `environments.assignmentHint` message misdescribes it.
- **Precedent:** this is a sibling bug class to `w6/m44` ("a dead id resolves to GraphQL null, not a zero-value object", shipped `bdad3db4` earlier the same day) but a different mechanism and a different fix site — m44's `gqlutil.NilOnError` guard nulls an entire resolved object when its resolver function *returned an error* (a dead-id lookup); this milestone is about one *field inside a successfully-resolved object* whose own Go zero value is a legitimate "unset" state, which `NilOnError` does not and cannot touch. m44's own DoD language — "distinguishable by any client... without string-matching empty fields" — is the same guarantee this milestone extends to optional relationship fields.
- **Goal linkage:** [docs/ADR006-bex-api.md](../../../docs/ADR006-bex-api.md) — bex-api's REST/GraphQL/MCP surfaces are meant to agree; today REST and GraphQL disagree on the same field for the same resource. [docs/ADR008-vision.md](../../../docs/ADR008-vision.md)'s human surface: an Environment Groups page that warns about a "legacy" link that was never legacy, and hides its own primary action, is not telling the truth about the product's own state.
- **Expected outcome:** GraphQL clients (dashboard, CLI, SDK, MCP agents) can tell "no Project"/"no Environment" from "the id is an empty string" for every resource type that has one, the same way REST already lets them; the Environment Groups page's Link/Move/warning UI works correctly for the common no-Environment case; the create-form hint no longer promises an effect that doesn't happen.
- **Why now:** a delivered-looking feature (Environment Groups, shipped `w6/m24`) is silently broken in its most common configuration in production today, and the blast-radius grep shows the same defect shape reachable from three more resource types' GraphQL surfaces — left alone, every new optional-FK field built on `gqlutil.StrField` inherits it, exactly the failure mode `w6/m44` already fixed once for the "whole object" case that day.
- **Render parity task included:** the fix changes GraphQL null semantics on user-facing read paths for env groups (and potentially apps/postgres/keyvalue), so REST/GraphQL/MCP/UI must move together and be checked against render.com's equivalent (Render's API generally omits/nulls unset optional relationship fields rather than serializing them as empty strings).
