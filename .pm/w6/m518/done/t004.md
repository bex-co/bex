## Objective

Show on the local cluster that a binary-change roll of both SNI DaemonSets keeps an active external client past 30 s and up to the bound, while the deploy's wait and Argo's health pass as soon as each node's new pod is Ready.

## Context

- w6/m515 t004 is the harness: external TLS clients on `Local` NodePorts shaped like production's, a `BLPOP`, a `pg_sleep`, held idle clients and new-connection loops.
- A shorter bound (for example 300 s) set in the local overlay keeps the run short, as long as the production rendering keeps the chosen bound. Say which bound the run used.
- Egress: the `bex-kv-proxy` and `bex-pg-proxy` scrape jobs (`deploy/gitops/base/prometheus.yaml`), or the local equivalent.

## Steps

1. Hold a Key Value client that sends a command every few seconds and a `psql` session that runs a query every few seconds, through each proxy. Start a loop of new connections.
2. Roll both DaemonSets with a binary change. Run `scripts/operator-pins.sh wait` with the new images and time it against each new pod's Ready time. Read Argo's health of the DaemonSets, or the t002 mechanism's signal, throughout.
3. Record when each held client closed against its old pod's `SIGTERM`, the new-connection loop, and whether a stream that ended during the drain shows its bytes in the scrape.

## Files

- none (record the results in this task file)

## Acceptance criteria

- [x] The held clients kept their connections past 30 s and until the bound used, and closed then, not before.
- [x] The wait passed within seconds of the last new pod's Ready, while the old pods still drained. The t002 signal read Healthy at the same point.
- [x] No new connection failed, and the drained stream's egress was scraped.

## Result (2026-11-20, local CAPD cluster, bound 300 s)

**Setup.**

- **Builds.** `bex-operator:m518-b` is this tree with t003 (`BEX_OPERATOR_IMG=bex-operator:m518-b bash scripts/mock-cluster.sh operator`). `bex-operator:dev` was the node's earlier build of `main`, before `17e8848c0`. Their `/kv-sni-proxy` and `/pg-sni-proxy` hashes differ on the node (`13c9ef51…`/`12cbd5d3…` against `6eb1aa0c…`/`b318e6cd…`), so each `kubectl set image` between them is a binary-change roll, as a production pin is.
- **The bound.** A local-only patch set both drain variables to `300` and the grace period to `310` before the clients connected, so the old pods of each measured roll drained for 300 s. The repository renders 3,600 s and 3,610 s. Afterwards the patch was reverted, so both DaemonSets run `bex-operator:m518-b` with the repository's template.
- **Probes.** In dev-6's tenant namespace `tea-dbtf3l1jg4ra1r0m4ur0`: the public free KeyValue `red-m518probe` and the public free Database `dpg-m518probe` (Postgres 17), each with allowlist `0.0.0.0/0`. The store's public certificate cannot issue locally, so a self-signed `red-m518probe-kv-tls` Secret, labelled with the store's UID, stood in, and Key Value clients used `--insecure`. The two `config/prod` NodePorts (31892, 31056, `externalTrafficPolicy: Local`) were applied for the proof only.
- **Clients**, Docker containers on the CAPD `kind` network dialling the platform node `172.22.0.5`, every line timestamped:
  - `kv-busy`: on one `valkey-cli` connection, `BLPOP m518:busy 4` then `CLIENT ID` every 5 s. `pg-busy`: on one `psql` connection, `pg_sleep(4)` with `pg_backend_pid()` every 5 s.
  - `kv-idle`: a `SUBSCRIBE`. `pg-idle`: a `psql` session with a query every 20 s.
  - `kv-end` and `pg-end`: one connection each that read 256 KiB every 5 s until told to quit, which they did during the drain.
  - `kv-loop` and `pg-loop`: a new connection every 0.5 s (`PING`, `select 1`).
- **Sampling.** Every 2–3 s the DaemonSets and their pods. Every ~20 s each SNI pod's `bex_*_proxy_egress_bytes_total` for the probe, read from the pod's metrics port through the API server (the local Prometheus has no SNI scrape job, so this stands in for production's 15 s scrape). Also every ~25 s, each live DaemonSet through `argocd admin settings resource-overrides health` in the production Argo image, with and without `deploy/argocd/daemonset-health.lua`.

- **The health signal.** In all 12 samples between `SIGTERM` and the bound, Argo's built-in check read `Progressing … 0 out of 1 new pods have been updated` for both DaemonSets, and the Lua read `Healthy … All 1 nodes run a Ready pod of generation 55 (app.bex.co/new-pods-ready); old pods are still draining` (54 for Postgres). The DaemonSets' status read `updatedNumberScheduled` 0 of 1 throughout. After the old pods exited, both checks read Healthy with no message.
- **New connections.** No failure in either loop: 720 `PING`s and 600 `select 1`s.

Through the drain `kv-busy` kept client 98 and `pg-busy` backend 197, `kv-end` and `pg-end` quit at 05:45:22Z and 05:45:23Z, and the old pods' counters rose from 332,420 to 8,212,269 and from 301,923 to 8,186,884 at the 05:45:36Z read.
