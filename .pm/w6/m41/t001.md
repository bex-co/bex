## Objective

Write the failing test first: drive a stale (time-traveled) App condition through the store reconciler and show it still records a phantom `server_failed`/`server_available` pair despite `w3/m78`'s two mitigations. Without this, the fix in `t002` is unfalsifiable.

## Context

- `lego/backend/internal/store/reconciler.go:301` — `obs := debounceUnhealthy(observedServiceStateFor(d.ID, cur, hasOpenDeploy), r.unhealthyOnce)`.
- `debounceUnhealthy` (`:211`) suppresses a *single-tick* unhealthy observation; the second consecutive one records. Its state is per-process memory (`:188`).
- `observedServiceStateFor` (`:932`) derives availability from the App CR condition, excluding `Suspended` / `AutoHibernated` / `RolloutSettling` reasons (`:960-966`).
- The gap: both consecutive observations come from the operator's **cached** client. When the informer time-travels (apiserver/etcd stalls watch streams for minutes), a crash-era `Ready=False` can be re-concluded long after recovery — twice in a row — and the debounce passes it through.
- Existing coverage to model on and to keep green: `TestPGObservedCrashEdgeEmitsExactlyOnePair` (real-Postgres) and `TestPushWorkerEnqueuesObservedLifecycleFacts`.
- The condition already carries `LastTransitionTime` — the reproduction should make the stale-vs-fresh distinction visible on it, since that is what `t002` will key on.

## Steps

1. Read `w3/m78`'s existing observed-crash tests to reuse their harness shape.

3. Assert on the recorded edges, not on log output.
4. Confirm the test is red against HEAD, and that it is red for the right reason (the phantom pair), not an unrelated setup failure.
