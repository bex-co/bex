# 053 — Every service type's Build Command hint says it builds "your site's static output", including web services and workers

Why: the New Service form and the Settings tab describe a static-site build to users creating a Go/Node/Docker web service, so the field's one line of guidance is wrong for most of the service types it appears on.

## What's wrong

`dashboard/src/features/services/locales/en.ts:1894-1898`:

```ts
"services.buildCommandHint": {
  message:
    "The command that builds your site's static output (e.g., npm run build). Leave blank to use the runtime default.",
  description: "Build & Deploy: build-command help text",
},
```

It is rendered unconditionally on both surfaces that expose a Build Command:

- `dashboard/src/features/services/components/build-deploy-section.tsx:238` — the Build & Deploy section of every service type's Settings tab
- `dashboard/src/routes/services.new.tsx:333` — the New Service form, for every service type

Its sibling key gives the origin away — `services.buildCommandLabel`'s own `description` reads `"Build & Deploy: build-command field label (static_site settings)"` (`en.ts:1889-1893`). The pair was authored for static sites and then reused for everything.

`zh.ts:1858-1861` carries the same static-specific wording: `生成静态输出的命令（例如 npm run build）。留空则使用运行时默认值。`

## Live repro (2026-08-27)

`https://dashboard.bex.co/services/srv-d9bkcspg9s7c73d0n8ug/settings` — `agentmarketcap-1`, `type: web_service`, a Go/Docker service with no static publish path — renders under Build Command:

> The command that builds your site's static output (e.g., npm run build). Leave blank to use the runtime default.

## Fix sketch

Either make the hint generic ("the command that builds your service", with the runtime-default sentence kept) or branch it on service type so `static_site` keeps the static wording and the other four types get their own. Render's own copy for a web service's Build Command is generic. Both `en` and `zh` move together, and `services.buildCommandLabel`'s stale `(static_site settings)` description should be corrected in the same pass so the next reader is not misled about the key's scope.
