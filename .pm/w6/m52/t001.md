## Objective

Name the correct target state a service should report when its very first deploy is canceled before any image has ever been released — the decision every other task in this milestone builds on.

## Context

- Live-confirmed: `server(id:).phase` currently returns `"Failed"` for this case, while `deploy(...).status` correctly returns `"canceled"` — see `w6/m52/README.md`'s live-evidence section for the exact repro and root cause (`lego/operator/internal/controller/app_controller.go:552-573`, `settleCanceledRelease`).
- The operator's own Condition already carries the right semantics (`Reason: "BuildCanceled"`, `Message: "build canceled before a release became available"`) — the gap is purely that the coarse `Phase` enum has no distinct value for this state, so it reuses `PhaseFailed`.
- Check render.com's actual dashboard/API behavior for the equivalent case (cancel a service's very first deploy) before deciding — this determines whether the fix is closing a genuine Render-parity gap or just choosing bex's own new wording.
- Existing `Phase` vocabulary to choose among/extend: `Pending`, `Building`, `Deploying`, `Running`, `Hibernated`, `Failed` (grep `appv1alpha1.Phase` in `lego/types/` for the authoritative list before proposing a new one).

## Steps

1. Check render.com's behavior for canceling a first-ever deploy (docs, or a live test account if available) — record what it shows.
2. Decide: reuse an existing Phase value (if one already fits — e.g. does bex have anything like "Created"/"Canceled" at the service level today?), or add a new one.
3. Name the target dashboard-visible label and badge variant (non-destructive — this is not an error state).
4. Write the decision down in this task's own notes (or update the README) so t002–t004 implement a single agreed-on target, not three different guesses.
