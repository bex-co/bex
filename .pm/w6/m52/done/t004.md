## Objective

Make the dashboard's service header (and anywhere else the service-level status badge renders) show the new distinct, non-destructive status for a canceled first-ever deploy, instead of the red "Failed" badge.

## Context

- `dashboard/src/features/services/lib/status.ts`:
  - `toServiceView` (`:34-96`) projects the GraphQL `phase` string onto `ServiceView.phase` — currently drops any Condition Reason entirely; needs to also carry whatever t002 exposed.
  - `PHASE_STATUS` (`:179-190`) is the lower-cased-phase → `{key, variant}` lookup table; `failed: { key: "failed", variant: "destructive" }` is the line this milestone must not have blindly reuse for the new case.
  - `deriveStatus` (`:197-208`) is where suspension/hibernation-vs-sleeping special-casing already happens — the new signal's special case belongs here, following the same pattern.
- `dashboard/src/features/services/lib/labels.ts`: `STATUS_LABEL` maps `ServiceStatusKey` → i18n key; add the new key here.
- `dashboard/src/features/services/types.ts:361-372`: `ServiceStatusKey` union — add the new key.
- Locale files: `dashboard/src/features/services/locales/en.ts` and the `zh.ts` sibling — every user-visible string needs both (project convention, see `dashboard/CLAUDE.md` Internationalization section).
- Badge variant should NOT be `"destructive"` (red) — this isn't an error. Match whatever non-alarming variant fits the existing palette (e.g. `"secondary"`, the same as `suspended`/`sleeping`).

## Steps

1. Add the new `ServiceStatusKey` value and its `STATUS_LABEL` i18n key (en + zh).
2. Extend `ServiceView`/`toServiceView` to carry the new signal from GraphQL.
3. Extend `PHASE_STATUS`/`deriveStatus` to resolve to the new key for this specific case, without changing how a genuine `PhaseFailed` (no new signal present) resolves.
4. Manually verify in the dev/local environment (or against a live QA service once t003 has shipped) that the header badge renders correctly.

## Acceptance criteria

- [ ] A service in the new "canceled first-ever deploy" state shows a distinct, non-destructive badge and label, in both `en` and `zh`.
- [ ] A service with a genuine `PhaseFailed` (the new signal absent/false) still shows the existing red "Failed" badge, unchanged.

## Out of scope

- The backend/operator changes that produce the new signal (t002, t003).

## Implementation (2026-08-24)

- `types.ts`: `ServiceStatusKey` gained `"canceled"`.
- `lib/status.ts`: `PHASE_STATUS.canceled = { key: "canceled", variant: "secondary" }` — non-destructive, matching `suspended`/`sleeping`.
- `lib/labels.ts`: `canceled: "services.statusCanceled"`.
- Locales: `services.statusCanceled` = "Canceled" (en) / "已取消" (zh).

Two things deliberately **not** changed:

- `deriveStatus` needed no new special case. The suspension/hibernation branches exist because those states are derived from a combination of fields (`suspended` + phase + service type); `Canceled` is a plain phase, so the existing `PHASE_STATUS` lookup is the whole implementation. Adding a branch would have been code with nothing to decide.
- `CONVERGING_PHASES` (the detail header's polling set) correctly excludes `canceled` — it is terminal, so the header stops polling instead of spinning at the 3-second cadence forever.

`ServiceStatusKey`'s only exhaustive consumer is `STATUS_LABEL`, so `tsc --noEmit` is what proves nothing else needs the new key; there is no status-filter UI keyed on the union, and no component branches on `key === "failed"`.
