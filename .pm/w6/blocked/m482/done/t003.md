## Objective

The gateway Deployment brings its new pods up first and gives an old pod the drain bound plus a margin before `SIGKILL`, and the production deploy step still finishes in minutes.

## Context

- `lego/operator/config/ssh/deployment.yaml`: `replicas: 2`, default strategy, default 30 s grace; requests `25m`/`64Mi`, limits `500m`/`512Mi`. `config/ssh/pdb.yaml` exists.
- `.github/workflows/deploy.yml:1376-1378`: `GRANTS_ONLY=1 bash scripts/ssh-gateway-db-role.sh`, then `rollout restart` and `rollout status --timeout=300s`. Terminating pods are not counted as replicas, so `rollout status` should return once the new pods are available; confirm it.
- The role sync installs this release's `dbrole.sql` before the restart, so a draining old pod runs for up to an hour against the new grants. Check that the grants only ever add privileges an older gateway uses, or record what an old pod could lose.
- Platform nodes run `bex.co/pool: platform`; two extra gateway pods for an hour must fit.

## Steps

1. Set `terminationGracePeriodSeconds` to the bound plus a margin (e.g. 3660) and a `RollingUpdate` with `maxUnavailable: 0`, `maxSurge: 1`.
2. Check `pdb.yaml` still allows the roll.
3. Confirm, on the local cluster, that `rollout status` returns while an old pod is still terminating.
4. Check the role sync against an old pod, and the platform pool's headroom.
5. Update any `scripts/gitops-validate.sh` assertion on these fields.

## Files

## Record (2026-11-18)

Done. `lego/operator/config/ssh/deployment.yaml`: `strategy.rollingUpdate` `maxSurge: 1`, `maxUnavailable: 0`; `terminationGracePeriodSeconds: 3660`; `BEX_SSH_SHUTDOWN_TIMEOUT: 1h` set explicitly; readiness on `/readyz` (liveness stays `/healthz`). `pdb.yaml` (`minAvailable: 1`) is unchanged and does not affect `rollout restart` (the Deployment controller does not use the eviction API). `scripts/gitops-validate.sh` gained a lockstep check (grace ≥ timeout + 30 s, `maxUnavailable: 0`, readiness `/readyz`); it fails on grace 30, `maxUnavailable: 25%`, a `/healthz` readiness probe and a 2 h timeout, and the full script passes. `deploy.yml` got a comment only; its wait is unchanged.

- **Local cluster** (Kubernetes v1.36.1, kubectl v1.37.0, 2026-11-18): a scratch Deployment with this strategy and grace and a container that traps SIGTERM; `rollout restart` + `rollout status` returned in 3 s with both old pods still `Terminating` (`status.terminatingReplicas: 2`, `replicas: 2`). Their EndpointSlice entries read `ready=false serving=true terminating=true`, which is why readiness now fails while draining (a consumer that routes to serving-terminating endpoints, as Traefik 3.x may for fenced servers, would otherwise send new connections to a closed listener). Scratch namespace deleted.
- **Role sync**: `scripts/ssh-gateway-db-role.sh` (`GRANTS_ONLY=1`) runs `REVOKE ALL` then this release's `dbrole.sql` in one transaction, so a draining old pod sees no gap. Every change to `dbrole.sql` in its history added a grant (`git log -p`: de268e760 … f36247bc6), so an old pod keeps every privilege it uses. A future release that drops a grant or a column an older gateway reads must account for old pods draining up to an hour (ADR035 records it).
- **Headroom** (production, read-only, 2026-11-18): gateway pods use 21–24 MiB and 1m CPU; platform nodes run at 5–48 % of allocatable CPU requests, so two extra 25m/64Mi pods for an hour fit. Production is Kubernetes v1.34.9 with Traefik v3.7.17.
