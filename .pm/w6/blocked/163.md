# A Settings deploy followed within seconds by a Render-shaped save stays `created` until another deploy cancels it

Why: a dashboard (GraphQL) Settings save opens a deploy, but when a REST `PATCH /v1/services/{id}` or MCP `update_service` save lands before the operator starts that release, the deploy never runs. Its row says `created` with nothing to explain why, and the setting it was opened for never goes live. On Render a deploy that was triggered runs, and an Update Service save only waits for the next one.

- **Found by:** w6/m548 t007, production pin `7e481dece7ac`, 2026-11-21, workspace `bex-canary`. The fixture was `w6-m548-delay` (`srv-dc0sbfm0ri4c73c3vjh0`), a Starter image web service, since deleted.
- **Sequence (UTC):**
  1. 16:25:31: REST PATCH `maxShutdownDelaySeconds: 1`, a save-only write.
  2. 16:25:32: GraphQL `setMaxShutdownDelay(seconds: 300)` opened `dep-dc0sbv60ri4c73c3vjk0` (`service_updated`, `bexTrigger: settings_change`) and stamped `app.bex.co/release-generation: 3`.
  3. 16:25:34: MCP `update_service` `maxShutdownDelaySeconds: 120`, another save-only write, set `app.bex.co/pending-source-generation: 4`.
  4. The App's `status.releaseGeneration` stayed 1 and the rev-1 pod kept serving. The deploy row stayed `created` for six minutes, and the service's events showed `deploy_started` with no end.
  5. 16:31:32: a `POST /v1/services/{id}/deploys` request ran (`dep-dc0sepe0ri4c73c3vk7g`, queued, then live at 16:31:49). The stuck row turned `canceled`, so the 300 s it was opened for never went live.
- **Cause (read, not yet tested):** `sourceUpdatePending` (`lego/operator/internal/controller/release_identity.go`) holds the release while the stamped release generation (3) is below the pending-source generation (4). The save-only write (`rollout.WithSaveOnly`, `lego/backend/internal/rollout/rollout.go`) bumped the pending generation past a release that had been requested but not yet started. `firstReleaseReadsSavedSource` covers only a never-served service (w21/051). This App had served, so nothing released the hold.
- **Options:** let a release stamped before the save still run, with the settings it was requested with or the newest ones. Or have the save-only write leave a stamped, not-yet-started release alone, and mark only the settings after it as pending. Check how Render orders a queued deploy and a later Update Service, and pick the matching option.
- **Done when:** on production, a GraphQL Settings save followed within 2 s by a REST or MCP save reaches a terminal deploy state without another deploy being requested. The REST or MCP value then waits for the next deploy as before. An operator or rollout test covers the stamp-then-save order.
- **Implemented 2026-11-23 (w6 loopx):** the second option. On Render a triggered deploy is in progress at once, so a later Update Service save cannot reach it and waits for the next deploy (the w8/387 and w8/390 reading of Render's Wait policy). The cause held: the operator envtest reproduces the stranded deploy when the save lands before adoption, and the deploy reaches live when it lands after.
  - bex-api holds a change saved for the next deploy until the operator adopts the deploy ahead. This covers a save-only `Tracker` write (`Snapshot.pends` → `rollout.AwaitAdoptionBeforeHold`) and the source-pending marker (`apps.markSourcePending`: Update Source, build-source and repo holds). It is the w8/390 wait (at most 15 s), and it runs under either overlap policy, since a held save replaces nothing. A suspended service does not wait.
  - Tests: `rollout/adoption_test.go` `TestASavedOnlyWriteWaitsForTheDeployAheadToBeAdopted` and `TestAHeldWriteWithNothingToHoldDoesNotWait`; `apps/push_wait_test.go` `TestAnUpdateServiceSaveWaitsForTheDeployAheadToBeAdopted` (the REST/MCP `ApplyServicePatch` path, a setting and a source); and the operator envtest `save_only_settings_envtest_test.go` "runs a deploy adopted before a later save with its own settings, and holds the save (w6/163)". Each fails with its half of the fix reverted.
  - Recorded in [ADR004 § Settings saves wait for a deploy](../../../docs/ADR004-app-deployment.md#settings-saves-wait-for-a-deploy-w8m135-2026-10-29) and ADR018's w8/390 paragraph. Still to do: the live check in Done when, once production runs it.
