# A disk service's move pulls its image only after the volume reaches the new node

Why: when a disk service's volume moves (a cordoned or full node, or a plan that no longer fits), its new instance pulls an image the new node lacks only after Hetzner's detach and attach, so a large image adds its whole pull to a window already 30–35 s long.

- **Found by:** [w6/m595](../done/m595/README.md) t005 on production, 2026-11-23, in `bex-canary` (fixture `w6-m595-t005`, disposable, deleted).
  - P, a Starter → Standard plan change: Standard's 1 CPU did not fit on the volume's node, so the new pod was bound to another node at once. The volume then detached (9.35 s) and attached (16.02 s), and only then did containerd pull 311.0 MB the node lacked (13.00 s). Window 48.00 s.
  - C, a code deploy with the node cordoned: detach 9.38 s, attach 15.93 s, then a 305.1 MB pull (15.08 s). Window 47.76 s.
  - With a cached image, m547 t011 and m559 t005 measured moves of 33.25–39.75 s.
- **Cause.** The kubelet pulls a pod's images only after its volumes are mounted. The new pod is bound to its node within 0.3 s of the old pod's teardown, about 27 s before its volume arrives. w6/m595's pre-pull runs only on a held rollout, on the volume's own node (`prePullThroughHold`, `lego/operator/internal/controller/disk_prepull.go`).
- **Idea.** Once a `Recreate` disk rollout's new pod is bound to a node other than the volume's, start the same `dskpul-` Job there for the images that node may lack, so the pull overlaps the detach and attach. It needs no wait: the template is already written.
- **Done when:** on production, a cordoned code deploy of an image with at least 100 MB new to the destination node shows the destination's pull of the new digest ending before the new instance's `MountDevice`, the instance's own `PullImage` reading 0 bytes, and the window within 1 s of a cordoned run of a cached image. A test covers the bound-elsewhere path.

## 2026-11-23 — the fix shipped; the production measure waits for the pin

- **Fix (`b0420d7b61`).** Once a disk service's template is written and a new instance is bound to a node other than its volume's and has not mounted it, the operator starts the `dskpul-` Job on that node for every image the instance runs, since that node may lack any of them (`prePullOnMove`, `lego/operator/internal/controller/disk_prepull.go`). The volume's node is the holder's, or with no holder the node the template prefers, which is the one its instance ran on when the template was written. Nothing waits for the pull: it overlaps the detach and attach, and the kubelet runs the instance's own pull behind it. A held code deploy's pull still running on the node the volume leaves is ended there. A plan change that no longer fits the volume's node pre-pulls too (run P's case), though it keeps its images.
- **No second pull.** The move's Job stays, even once its pull has ended, until the instance has the volume, and then ends as any pre-pull does. It starts only within 60 s of the instance's binding, which is its TTL after it ends, so no pass finds it reaped and pulls again. `bex_disk_prepulls_total{result="moved"}` counts each one.
- **Pull policy.** Each pre-pull container now pulls its image with the policy the template's instance uses for it: `Always` for a tenant's image, as before, and `IfNotPresent` for bex's own helpers, such as the health-probe installer, which a move now pre-pulls too.
- **Tests.** `TestDiskPrePullOverlapsAMove` runs a cordoned code deploy and a plan change whose new instance is bound to node-b. The Job starts there with the instance's image, outlives its pull while the volume has not arrived, starts no second Job, and ends once the instance mounts. `TestDiskPrePullFollowsTheInstanceToTheNodeItsVolumeMovesTo`, `TestDiskPrePullReadsTheVolumesNodeFromItsHolder`, `TestDiskPrePullStartsNoneUnlessTheVolumeMoves` (an instance bound to the volume's node, one running where the volume moved, one bound past the bound: no Job and no write) and `TestDiskPrePullPullsEachImageAsTheInstanceDoes` cover the rest. Seven mutations of the change each fail one of them. `make test` and `make lint` passed.
- **Next.** Once production's pin carries `b0420d7b61`, measure as [m595 t005](../done/m595/done/t005.md) run C did, as the QA user in `bex-canary`: a disk-bearing Starter fixture (disposable) with its volume's node cordoned, a code deploy of an image with at least 100 MB of layers new to the destination node, and a cordoned run of a cached image. From the destination node's syslog, check that the pre-pull's pull of the new digest ends before the new instance's `MountDevice`, that the instance's own `PullImage` reads 0 bytes, and that the window is within 1 s of the cached run's. Record the windows in ADR082 § D3's table, ADR004 and ADR018, then close the note.
