## Objective

Before production, show the definition of done on a real cluster: a free store with internal authentication refuses its 51st authenticated client on both URLs, its platform clients still connect at the limit, and enabling internal auth restarts no Valkey pod.

## Context

- The local CAPD cluster (`bash scripts/mock-cluster.sh operator` builds and deploys the operator from the tree) or this workstream's `dev-6` stack (`.pm/w6/README.md` § Local dev environment).
- m456 verified its own limit the same way; reuse its probe approach (a pod holding N connections with `AUTH`, then one more).

## Steps

1. Create a free store, connect a client through the unauthenticated URL, then enable internal auth: the client's connection drops, the Valkey pod's restart count and `INFO server` `run_id` are unchanged.
2. Hold 50 authenticated connections on `<id>:6379`; the 51st reads `ERR max number of clients reached`. Repeat on the TLS port for a public store.
3. While 50 are held: the store stays Ready, `redis_connected_clients` keeps being scraped, a manual backup Job succeeds, and an operator pass (e.g. a maxmemory-policy change) applies.
4. Record the commands and the results (not raw output) in this task.

## Result — 2026-11-17 (local CAPD cluster)

Setup: `bash scripts/mock-cluster.sh operator` built `bex-operator:dev` from this tree (w6/m463 uncommitted on `4ecb6f004`) and rolled it onto the shared local cluster. Probes ran in dev-6's tenant namespace `tea-dbtf3l1jg4ra1r0m4ur0`. A `KeyValue` there needs `app.bex.co/workspace` equal to its namespace (the operator refuses any other, codex #11). Probe stores were `plan: free`, `persistenceMode: "off"`. The client was a `docker.io/valkey/valkey:8.1` pod in the same namespace, with the store's `<id>-auth` password as env `PW`, never printed. Clients are bash `/dev/tcp` connections that send `AUTH default $PW` then `PING`, or a bare `PING`. All probes were deleted afterwards.

1. **Enabling internal auth on a running store** (`red-m463probe2`, proxied, `internalAuthOptional` true):
   - Before the patch, an unauthenticated client through `<id>:6379` read `+PONG` and was held open.
   - Patch: `kubectl patch keyvalue <id> --type merge -p '{"spec":{"internalAuth":true}}'` at 23:06:30Z.
   - The proxy rolled. The new pod was Ready and the old one gone at 23:06:32.8Z, and at that moment the server closed the held client (read EOF).
   - New unauthenticated clients read `+PONG` until 23:06:32.8Z, one was refused while the old pod's listener closed, and from 23:06:34Z on they read `-NOAUTH Authentication required.`
   - The store read `Provisioning` for about a second (bex-api: `config_restart`), then `Ready`.
   - The Valkey pod was untouched: restart counts `0 0`, `INFO server` `run_id` the same before and after, StatefulSet generation 1 and its update revision unchanged.
   - `<id>` still selects `app.bex.co/keyvalue-internal-proxy`, and the proxy carries `BEX_KV_INTERNAL_AUTH=client` and `BEX_KV_MAX_CONNECTIONS=50`.
   - The first store (`red-m463probe`) showed the same restart-free switch.
2. **The limit** (`red-m463probe`, internal auth on): 50 authenticated clients on `<id>:6379` each read `+OK`, `+PONG`. The 51st read `-ERR max number of clients reached`, as did an unauthenticated client past the budget. The server ran `maxclients` 60 with `connected_clients` 51 (the 50 plus the reading client).
3. **Platform clients while the 50 were held:**
   - The store stayed `Ready`, its pod `Ready`, with no `Unhealthy` probe event.
   - The exporter answered three scrapes of `127.0.0.1:9121/metrics` inside its container with `redis_up 1`, `redis_connected_clients 51` and `redis_rejected_connections_total 0`. The local Prometheus does not scrape Key Value exporters, so this checks the scrape itself.
   - A snapshot Job ran the backup CronJob's own `snapshot` container (`valkey-cli -h <id>-backend --user bex --rdb`, with the backup pod's labels) and transferred the RDB. The local operator has no `BEX_KV_BACKUP_*`, so it renders no CronJob.
   - `spec.maxmemoryPolicy` changed to `volatile-lru`: the operator's `CONFIG SET` landed within a second (`CONFIG GET` and `status.maxmemoryPolicy` both `volatile-lru`), with the same `run_id`.

**Found along the way, filed as [w6/139](../../../done/139.md):** while the snapshot stand-in's main container ran, the `<id>-backend` EndpointSlice listed the backup pod as a ready endpoint, because backup pods carry `app.bex.co/keyvalue: <id>`. With a ready pod carrying those labels on the second store, 20 of 40 new clients through the proxy were reset. That is every proxied store's nightly upload window, since w8/204, and this milestone does not cause it.
