# A plan change after an `imageUrl` deploy redeploys the service's create-time image

Why: a Starter → Standard change rolled a live image service back from the tag its last deploy shipped to the tag it was created with. The customer gets back old code they never asked for.

- **Found by:** w6/m547 t001, on production, 2026-11-21, in `bex-canary`, on the service `w6-m547-disk` (`srv-dc0kcbl2b0us73dobm30`, deleted since).
- **Repro:**
  1. `POST /v1/services` creates an image service at `docker.io/traefik/whoami:v1.10.1`.
  2. Deploys go out with `POST /v1/services/{id}/deploys` `{"imageUrl":"docker.io/traefik/whoami:v1.11.0"}` (and earlier tags). Each goes live, and a restart afterwards keeps `v1.11.0` (deploy `dep-dc0kgbl26tvc739p1990`).
  3. `PATCH /v1/services/{id}` `{"serviceDetails":{"plan":"standard"}}` creates deploy `dep-dc0kgpl2b0us73dobm8g` (trigger `service_updated`), which ships `docker.io/traefik/whoami:v1.10.1` (`sha256:6956a30c…`).
- The App spec's `image` stayed `docker.io/traefik/whoami:v1.10.1` through every `imageUrl` deploy, so a settings change re-releases `spec.image`, not the image the serving release runs.
- **Check Render first:** does Render's deploy `imageUrl` change the service's configured image (`GET /v1/services/{id}` `image.imagePath`), or only that deploy's? Either way, a plan change on Render redeploys what is live, not an older image. Record the answer with its source.
- **Done when:** after an `imageUrl` deploy, a plan change, an env var change and a restart each keep serving the image the last deploy shipped. A regression test covers the plan-change path. `GET /v1/services/{id}` reports the image the way Render does.

## Loopx w6 verdict (2026-11-23)

**Work.** The premise held at `aa6a2a02d1`: a plan change opens its `settings_change` release through `rollout.Patch` (`apps.patchFetched`) with no image selection, so the operator ran `spec.image`, the tag the service was created with. w4/m418's `SelectServedImage` covered only environment saves and env-group rolls.

- **Render, recorded in [ADR018](../../../docs/ADR018-render-parity.md) (Trigger a deploy row):** a deploy's own image applies to that deploy only: "for future deploys, your service continues to use the tag or digest in its settings" ([render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image), read 2026-11-23). So `GET /v1/services/{id}` reports the configured tag as `imagePath`. bex already did (`apps/render.go`, `ImagePath` from `spec.image`), with the running override in the `servingImage` extension (w4/414). Render's [compute plans](https://render.com/docs/compute-plans) page does not say which image the dashboard's plan-change deploy runs. It does say its Update Service API does not deploy a plan change at all, which bex does: filed as [w6/172](../172.md).
- **Fix (`f5c781bbc8`):** `rollout.Patch` and `PatchLocked` keep the image the release in force selected for every `settings_change` of a prebuilt image: a plan change through the dashboard, REST or MCP, a dashboard Settings save that deploys, and a container-policy migration. That is the live deploy's digest once the selected release serves, the selected image while it is still rolling, and the live image when it ended without serving. A release in force that runs the saved image selects nothing, so a saved image held for the next deploy (w8/m135) still ships with the plan change. A compound PATCH's stage now keeps the live App's selection when another writer changed the spec between its read and its publish.
- **Tests:** `TestASettingsReleaseKeepsTheSelectedImage` (rollout, 12 cases through `Patch` and `PatchLocked`), `TestAPlanChangeAfterAnImageOverrideKeepsItsImage` (dashboard `updateServicePlan` and REST `PATCH`) and `TestAPlanChangeRacedByADeployKeepsTheDeploysImage`. Each fails with its fix reverted. The environment "Save and deploy" (w4/m418) and Restart (`restartSelection`) already kept the override.
- **Left:** the repro on production once the pin carries the fix. As the QA user in `bex-canary`, create an image web service on `docker.io/traefik/whoami:v1.10.1` (disposable), deploy `imageUrl` `docker.io/traefik/whoami:v1.11.0`, restart, and change the plan Starter → Standard with `PATCH /v1/services/{id}`. The plan change's deploy and the URL must serve v1.11.0. An environment "Save and deploy" and a Restart after it must keep v1.11.0, and `GET /v1/services/{id}` must still read `imagePath` v1.10.1. Then delete the service.
