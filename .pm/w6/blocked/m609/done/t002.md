## Objective

Prove with an operator envtest that a saved plan change waits for a deploy: the serving Deployment keeps the old plan's resources and serving pool, the App reads `undeployedChanges: true`, and the next deploy applies the plan in one release. Fix whatever the test finds.

## Context

- `Tier` is `IdentityRelease` (`lego/types/v1alpha1/app_identity.go`). `pendingReleaseView` (`lego/operator/internal/controller/release_view.go`) renders the adopted spec's release fields while `sourceUpdatePending` holds a save (`app_controller.go`, the `releaseDecision.sourcePending` branch).
- The pass reads `app.Spec.Tier` in `resourcesForTier` (`deployment_projection.go`, `app_controller.go`), `tiers.Compute.ServingPool`, `web_concurrency.go`, `autoscale.go` (`autoscaleDesired`), the instance cap (`app_controller.go`), `isFreeApp` (hibernation, `container_policy.go`) and `disk_backup.go`.
- The pattern to follow: `save_only_settings_envtest_test.go` (w8/m135 t006), which saves a shutdown delay, probe, command and pre-deploy and checks the serving template stays put.
- ADR004: Restart and rollback keep a pending save pending, and "A plan changed since the target is no change, as Render's rollback keeps the current plan."

## Steps

1. Add a case to `save_only_settings_envtest_test.go`: a Starter App with an adopted release saves `tier: standard` the way bex-api's save-only stamp does (pending-source-generation, no release generation).
2. Assert: the Deployment keeps Starter's requests and limits and its serving pool; `WEB_CONCURRENCY` is unchanged; `status.undeployedChanges` is true; no pre-deploy runs.
3. Stamp a deploy past the pending generation. Assert one rollout to Standard's resources and pool, and `undeployedChanges` false.
4. A Free → Starter save on a hibernating Free App keeps hibernating until the deploy; a canceled deploy keeps Starter's template and the pending state.
5. Check a Restart behind a pending plan: Render's restart keeps the running deploy, so the plan stays pending. Fix the operator if it does not.

## Done (2026-11-23)

- Two envtests in `save_only_settings_envtest_test.go`: a Starter service saved to Pro Plus keeps Starter's CPU and memory, stays off the `xl` pool, keeps `WEB_CONCURRENCY=1`, runs no pre-deploy, reads `undeployedChanges: true` and `status.servedTier: starter`, through a canceled deploy; the next deploy applies Pro Plus (4 CPUs, `xl`, `WEB_CONCURRENCY=4`) in one release. A hibernating Free service saved to Starter stays asleep on Free until the deploy, which wakes it on Starter. Both fail with `pendingReleaseView` disabled.
- The operator needed no change for the held plan itself. It now records `status.servedTier` from the template it writes (`recordServedTier`; a restored template's plan from its app container's CPU and memory, `templateTier`, guarded by `TestComputePlansDifferInCPUOrMemory`).
- **Restart (step 5):** a Restart applies a saved plan, and the envtest asserts it. Render's deploys page: "a service restart is actually a special form of manual deploy" that creates "a completely new instance", and the plan changes with "the first successful deploy after you update it". Restart keeps the live release's commit and recorded settings and runs the saved plan, as it did before (ADR004).
