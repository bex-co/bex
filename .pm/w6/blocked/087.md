# Deploys starve under steady manifest-touching pushes

Why: production went more than a day without a deploy (2026-10-20/21) while main was green, so finished work (w6/m149, m150, m151) could not reach its canary.

- **Mechanism:**
  - `deploy.yml` runs one at a time with a single pending slot, so each new push cancels the queued run.
  - `scripts/deploy-superseded.sh` makes the running run skip build and deploy when any newer commit changes a deploy manifest (`deploy/gitops`, `deploy/opensandbox`, `lego/operator/config`, `deploy.yml`).
  - A run takes 1–3h on the shared runners, so with several sessions pushing, the run that finishes has usually been superseded and the run that would build is cancelled while pending.
- **Evidence:**
  - 221b80f80 (run 39556825196) passed every test, then skipped build and deploy (superseded).
  - 65e0b19b5 (39560691355) was cancelled while pending.
  - The w1/116 note in `deploy-superseded.sh` already fixed the same starvation for image-source changes.
- **Fix candidates:**
  - deploy the superseded run's images when the newer manifest diff only touches resources those images do not read;
  - or build the pending run's tree instead of cancelling it;
  - or shorten the test stage with more runners.

  Keep the invariant that an image never meets manifests newer than its tree.

**BLOCKED (2026-10-21): needs a decision from the user.** Either relax the supersession invariant, letting an image deploy onto newer manifests that leave its resources untouched (needs a reviewed definition of "untouched"), or buy deploy throughput: more `bex-ci` runners, or a shorter test stage. The repo-side retry fixes (2d2b2c18e, d03cb0fa0, eaad82331) are already in; the starvation itself is structural.
