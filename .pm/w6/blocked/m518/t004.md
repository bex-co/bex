## Objective

Show on the local cluster that a binary-change roll of both SNI DaemonSets keeps an active external client past 30 s and up to the bound, while the deploy's wait and Argo's health pass as soon as each node's new pod is Ready.

## Context

- w6/m515 t004 is the harness: external TLS clients on `Local` NodePorts shaped like production's, a `BLPOP`, a `pg_sleep`, held idle clients and new-connection loops.
- A shorter bound (for example 300 s) set in the local overlay keeps the run short, as long as the production rendering keeps the chosen bound. Say which bound the run used.
- Egress: the `bex-kv-proxy` and `bex-pg-proxy` scrape jobs (`deploy/gitops/base/prometheus.yaml`), or the local equivalent.

## Steps

1. Hold a Key Value client that sends a command every few seconds and a `psql` session that runs a query every few seconds, through each proxy. Start a loop of new connections.
2. Roll both DaemonSets with a binary change. Run `scripts/operator-pins.sh wait` with the new images and time it against each new pod's Ready time. Read Argo's health of the DaemonSets, or the t002 mechanism's signal, throughout.
3. Record when each held client closed against its old pod's `SIGTERM`, the new-connection loop, and whether a stream that ended during the drain shows its bytes in the scrape.

## Acceptance criteria

- [ ] The held clients kept their connections past 30 s and until the bound used, and closed then, not before.
- [ ] The wait passed within seconds of the last new pod's Ready, while the old pods still drained. The t002 signal read Healthy at the same point.
- [ ] No new connection failed, and the drained stream's egress was scraped.
