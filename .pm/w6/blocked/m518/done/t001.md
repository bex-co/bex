## Objective

`scripts/operator-pins.sh wait` stops calling `kubectl rollout status` for the SNI DaemonSets. After the image wait, it passes once every node that should run the DaemonSet runs a Ready, non-terminating pod of the current template. A draining old pod no longer holds the deploy, and a new pod that never becomes Ready still fails it.

## Context

- `scripts/operator-pins.sh` `wait_for_proxies`: the image wait (`SNI_PROXY_WAIT_SECONDS`, default 600), then `rollout status … --timeout=300s` at line 123. `.github/workflows/deploy.yml` runs it at line 1400 (`timeout-minutes: 12`).
- `rollout status` and the DaemonSet controller's status read each node's oldest pod, terminating pods included (README § Findings). w6/m515 t003 measured 91.5 s for a 90 s drain.
- The current revision: pods carry `pod-template-generation` (the DaemonSet's `deprecated.daemonset.template.generation` annotation) and `controller-revision-hash`. Check `observedGeneration >= generation` first, so a template Argo just applied is not read against the old revision.
- `scripts/operator-pins.test.sh` fakes `kubectl` (`wait_case`, around line 152). It must be extended to fake the pod list.
- This task changes neither SNI binary nor either DaemonSet template, so it may ship before w6/m515 (README § Sequencing constraint).

## Steps

1. Replace the `rollout status` call with a poll. Read the DaemonSet's generation, `observedGeneration`, template generation and `desiredNumberScheduled`, then its pods by selector. Count the distinct nodes that have a Ready pod of the current template generation with no `deletionTimestamp`. Pass when that count reaches `desiredNumberScheduled`, and fail after 300 s with the DaemonSet, the count and the pods that are not Ready.
2. Update the script's header comment.
3. Extend `operator-pins.test.sh`. Cover: a node whose old pod is terminating while its new pod is Ready passes; a new pod that is not Ready fails at the bound; a stale `observedGeneration` waits; and two nodes where one still runs only the old pod wait.
4. Run it against the local cluster's SNI DaemonSets (`KV_SNI_PROXY_IMAGE` and `PG_SNI_PROXY_IMAGE` set to their running images), including during a roll.

## Result (2026-11-19)

- **The wait.** `wait_for_new_pods` in `scripts/operator-pins.sh` replaces `rollout status`, after the image wait. Each poll reads the DaemonSet and the pods its selector matches (`kubectl … -o json`, `jq`).
  - It passes once `observedGeneration` has reached `generation` and enough distinct nodes have a Ready pod that the DaemonSet controls, that is not terminating, and whose `pod-template-generation` equals the `deprecated.daemonset.template.generation` annotation. Enough means `desiredNumberScheduled`.
  - The bound stays 300 s (`SNI_PROXY_ROLLOUT_SECONDS`). A timeout names the count and every pod it did not count, with the reason.
  - `deploy.yml` changed only in the step's comment. The step still runs `operator-pins.sh wait`, and the job already uses `jq`. `scripts/gitops-validate.sh` now requires the new wait in place of the `rollout status` line.
- **Tests.** `scripts/operator-pins.test.sh`'s fake `kubectl` serves the DaemonSet and pod JSON, and answers `rollout status` from the DaemonSet's status as kubectl does. Eight new cases cover:
  - an old pod draining beside its node's Ready new pod;
  - a new pod that is never Ready;
  - a stale `observedGeneration`, with and without the controller catching up;
  - a node that still runs only its old pod, before and after its new pod is Ready;
  - a terminating current pod;
  - a pod another controller owns;
  - two pods on one node.
- **Mutation checks.** Reverting the poll to `rollout status` fails seven checks. Removing the terminating, Ready, `observedGeneration`, owner, per-node or template-generation filter each fails its case.
- **Local cluster** (CAPD, Kubernetes v1.36.1). The SNI DaemonSets run w6/m515's `bex-operator:m515-b`, which surges with `maxSurge: 1`.
  - Settled DaemonSets: the wait passed in 0.5 s.
  - A restart whose old pods had no open stream: the wait passed at +7 s, the moment the Key Value proxy's new pod was Ready (18:38:33Z). `rollout status` returned at +12 s, once the old pods had exited.
  - A restart whose old pods stayed for 90 s. A local-only 90 s `preStop` keeps each old pod Running and Ready after its deletion, which is what a drain looks like to the DaemonSet controller. The new pods were Ready at 18:39:36Z and the wait passed at 18:39:37Z (+7 s). `rollout status` returned at 18:41:06Z (+96 s). Through the drain the DaemonSet's status read `updatedNumberScheduled` 0 of 1.
