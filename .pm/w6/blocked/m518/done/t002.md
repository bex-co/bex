## Objective

A long drain must not turn the `bex-operator` Application Progressing for its whole length, and must not fire `PlatformGitOpsUnhealthy` on every deploy that moves an SNI pin. A roll that is really stuck must still read Progressing and still fire that alert. Choose the mechanism by evidence, implement it, and record the choice. That choice decides the bound t003 sets.

## Context

- Argo's DaemonSet health copies `kubectl rollout status`'s rule (`gitops-engine` `pkg/health/health_daemonset.go`), so a draining old pod reads Progressing. `PlatformGitOpsUnhealthy` fires after 15 m (`deploy/gitops/base/rules/alerting_rules.yml`), and `bex-operator` is expected (`deploy/gitops/base/prometheus.yaml`, `bex:platform_gitops_expected`). Its tests are in `deploy/gitops/base/rules/gitops_alerts_test.yml`.
- Argo CD comes from `deploy.yml` step 3 (a pinned `install.yaml`), which already patches `argocd-cmd-params-cm`. No `resource.customizations` exist yet.
- The Application syncs with `ServerSideApply=true` (`deploy/gitops/base/bex.yaml`).
- The operator can already `get`, `list`, `patch` and `watch` pods (`lego/operator/config/rbac/role.yaml`).
- The three options and their risks: README § Design. Never exclude the DaemonSets from the alert, and never widen its window.

## Steps

1. On the local cluster (Argo present, or a local Argo with the same pinned install), reproduce it. Roll a scratch `maxSurge: 1` DaemonSet whose old pod drains for several minutes, and read the Application's health throughout.
2. Weigh the options in README § Design.
   - For option 1: write the Lua, and prove it leaves every other DaemonSet's health unchanged. Prove the extra annotation does not make the Application OutOfSync.
   - For option 2: first prove on both kube-proxy and Cilium (production) that an established NodePort flow survives its backend's removal from the EndpointSlice. If either drops it, reject option 2.
3. Implement the chosen option. Keep it out of the SNI binaries and the DaemonSet templates if it is to ship before w6/m515 (README § Sequencing constraint).
4. Record the choice, the evidence and the resulting maximum bound in this task.

## Out of scope

- The bound itself (t003).

## Choice (2026-11-19): option 1, an Argo health check that reads a signal the operator writes

- **The premise holds.** Production runs Argo CD v3.4.6 (`quay.io/argoproj/argocd@sha256:6e9f4f1d…`). Its DaemonSet check is `kubectl rollout status`'s rule (`gitops-engine/pkg/health/health_daemonset.go` at `v3.4.6`), and the DaemonSet's status counts each node's oldest pod. So a draining old pod reads Progressing. A Lua override for `apps_DaemonSet` replaces the built-in check for every DaemonSet (`util/lua/lua.go`: a script that returns nothing gives an empty status, not the built-in one).
- **Option 2 rejected, with its variant that removes only the old pod's `ownerReference` and keeps its labels**, on the DaemonSet controller's code (`kubernetes` `release-1.36`, `pkg/controller/daemon`):
  - A pod released by its label also leaves the Services' EndpointSlices and the `bex-kv-proxy`/`bex-pg-proxy` scrape jobs, which select by that label. Those flows are the ones the drain exists to keep.
  - The controller does adopt no terminating orphan (`ClaimObject`: "Ignore if the object is being deleted"). But its `updatePod` hands a terminating pod to `deletePod`, which returns early for a pod with no controller ("No controller should care about orphans being deleted"). So releasing the pod queues no status update. After a roll's last node the status would stay stale until some unrelated event, and fixing that needs DaemonSet writes anyway.
  - A pod with no DaemonSet controller is an unmanaged pod to every drainer. `kubectl drain` refuses it without `--force`, and a node drain would wait out its drain, where today it skips DaemonSet pods.
  - The platform AppProject warns on orphaned resources (`orphanedResources.warn: true`), so each release would raise that warning.
  - These reject option 2 without the NodePort flow proof on Cilium.
- **Option 3 is not needed.** Option 1 keeps the Application Healthy for any drain length.
- **Implemented:**
  - `SNIProxyRolloutReconciler` (`lego/operator/internal/controller/sniproxy_rollout.go`, registered in `cmd/manager`) watches `bex-kv-sni-proxy` and `bex-pg-sni-proxy` in the operator's namespace and the pods they control. It keeps `app.bex.co/new-pods-ready: "<generation>/<desiredNumberScheduled>"` on each while every node runs a Ready, non-terminating pod of the current template, which is t001's rule, and removes the annotation otherwise. RBAC adds `get`/`list`/`watch` on DaemonSets, and `patch` on those two names only.
  - `deploy/argocd/daemonset-health.lua` is the built-in rule line for line, plus one branch. Where the built-in check would read Progressing on the pod counts, a DaemonSet whose annotation matches its generation and `desiredNumberScheduled` reads Healthy, with a message that old pods are still draining.
    - A stale value never matches a later generation or a node that joined.
    - Before the controller observes a generation, for `OnDelete`, and with complete counts, the answer is the built-in one.
  - `deploy.yml` step 3 installs the Lua as `argocd-cm`'s `resource.customizations.health.apps_DaemonSet`. Argo reloads `argocd-cm` without a restart: `controller/cache` `watchSettings` invalidates the cache when the settings change. `scripts/gitops-validate.sh` requires that patch.
  - Neither SNI binary nor either DaemonSet template changed. Neither binary links the new code (`go list -deps`), and `config/prod` renders both DaemonSets byte-identical to `3d8835416`. Only the ClusterRole changed.
- **Maximum bound: none from the health signal.** t003 can take the 3,600 s target.

## Evidence (2026-11-19)

- **The Lua in Argo's own image.** `scripts/argocd-daemonset-health.test.sh`, a new step in `gitops.yml`, runs Argo's own CLI (`argocd admin settings resource-overrides health`) in the production Argo image.
  - It matches the built-in check on 308 shapes the annotation must not decide: both strategies and none, every branch, wrong or malformed values, and matching values where the built-in check has already decided.
  - It reads Healthy on three draining shapes that the built-in check reads Progressing.
  - It fails when the image pin moves away from `deploy.yml`'s `ARGO_INSTALL_COMMIT`, or when the operator stops writing the key.
  - On all 12 live production DaemonSets, the Lua and the built-in check agree.
  - Each of these mutations fails it: dropping the branch, ignoring the node count, checking the annotation before the observed generation, `updated <= desired`, and ignoring `OnDelete`.
- **The operator.** `TestNewPodsReady` covers the rule. The envtest spec `SNI proxy rollout annotation` runs the reconciler in a manager and checks that the annotation is:
  - set while an old pod drains;
  - cleared by a new pod going NotReady, and set again when it is Ready;
  - cleared by a node joining, until that node's pod is Ready;
  - never written on another DaemonSet whose pods would qualify.
  Each of these mutations fails it: no pod watch, never removing, every DaemonSet, and terminating pods counting.
- **Local cluster, a drain past 15 minutes** (CAPD, Kubernetes v1.36.1, both SNI DaemonSets on w6/m515's surge image). There is no local Argo, so the two halves were checked together.
  - Setup. The reconciler ran from a throwaway main that registered only it, against the local cluster. A local-only 1,000 s `preStop` kept each old pod Running and Ready after its deletion, as a drain does. Each sample saved the live DaemonSet and evaluated it in the production Argo image, built-in and with the Lua.
  - From 19:06:00Z to 19:21:22Z both new pods were Ready, and both old pods were terminating but still Ready. The DaemonSet status read `updatedNumberScheduled` 0 of 1, and the operator held `46/1`. In all 13 samples the built-in check read Progressing and the Lua read Healthy, the last one 15 m 22 s into the drain.
  - One sample, at 19:10:18Z, could not read the cluster, because the local API server answered `EOF`.
  - The old pods were gone at 19:22:23Z. From then on both checks read Healthy with no message.
  - A new pod that never becomes Ready: at 19:25:42Z the Key Value DaemonSet moved to an image that does not exist. Its old pod kept serving, the operator removed the annotation, and both checks read `Progressing … 0 out of 1 new pods have been updated`.
  - Afterwards both DaemonSets were restored to w6/m515's template (5 s pause, 40 s grace), and the annotation and the throwaway main were removed.
- **Synced stays Synced.** Production's DaemonSets already carry `deprecated.daemonset.template.generation`, which is not in git, and `bex-operator` reads Synced. Argo's diff drops live-only map fields, and under server-side apply the operator's field manager owns the annotation.
- **The alert is unchanged.** `PlatformGitOpsUnhealthy`, its 15 m window and its rule tests (`gitops_alerts_test.yml`, run by `scripts/gitops-validate.sh`) are untouched.
