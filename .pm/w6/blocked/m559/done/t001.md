## Objective

A function builds, for a disk-bearing App and a node, the Job whose one pod holds the App's claim on that node and does nothing else. The operator-workload admission grammar admits it unchanged.

## Context

- **Pattern to follow:** the disk snapshot Job in `lego/operator/internal/controller/disk_backup.go` already mounts the claim beside a running service: the claim source is read-write and only the container mount is read-only (`:326`), and it tolerates the serving pool through `execution.TolerateServingPool`.
- **Admission (`deploy/gitops/base/operator-workload-admission.yaml`):**
  - no `nodeName`, so place the pod with a required node-affinity term `metadata.name In [<node>]` (`diskNodeField` in `disk.go`);
  - a serving-pool toleration only on an App-owned workload (`appOwnedWorkload`: a controller ownerReference to the App plus a pod label `app.bex.co/app` naming it);
  - restricted containers: no added capabilities, no privilege escalation, RuntimeDefault seccomp;
  - `automountServiceAccountToken: false` and the default ServiceAccount;
  - no priority class.
- **Quota and limits:** the namespace's `tenant-compute-quota` counts the pod's requests, limits and pod count, and `tenant-limits` fills in missing requests with 100m and 128Mi (`lego/backend/internal/store/namespaces.go`). Use explicit small values, with a zero CPU request as `diskSnapshotResources` does. A refused create is a fallback in t002, not an error.
- **The image must already be on the node**, because a pull here delays the deploy. Options:
  - the kubelet's sandbox `pause` image (`crictl info` on a tenant node gives its exact reference; tenant nodes run v1.34.9) with `IfNotPresent`;
  - bex's own image (`r.BackupHelperImage`), which a disk pod with a health-probe binary already pulled for its `bex-health-probe-install` init container (`deployment_projection.go:925`). It would need a command that blocks until `SIGTERM`.

  Pick one and record why.
- **Labels:** carry `app.bex.co/app` (admission, and `appPodRequests` then reconciles the App on the holder pod's events), plus a non-empty `app.bex.co/component` such as `disk-holder`. Never `app.bex.co/app-id`: the Services select `app.bex.co/app` plus `app.bex.co/app-id` (`privateServiceProjection`), so the holder must never match them.

## Steps

1. `diskHolderJob(app, node, …)`:
   - name `dskhld-<app>`, or a hash-bounded form within the name limit;
   - an App controller ownerReference;
   - `backoffLimit: 0`, an `activeDeadlineSeconds` just above the 15-minute startup budget as a backstop, and `ttlSecondsAfterFinished`;
   - one container that mounts the claim read-only and runs as non-root with a read-only root filesystem;
   - the serving-pool toleration;
   - `applyPodSpecServerDefaults`.
2. A unit test of the shape: the required node term, the read-only mount over a read-write source, no `app-id` label, the component label, the ownerReference and the deadline.
3. Check it against the admission grammar with the repo's existing policy test harness (`scripts/gitops-validate.sh` or the CEL tests beside `container_policy_test.go`). If none evaluates the workload policy, record how the shape was checked.

## Record (2026-11-21)

- **Built:** `diskHolderJob` in `lego/operator/internal/controller/disk_holder.go`. Its name is `dskhld-<app>`, through `appv1alpha1.DiskChildName`, so a long name is hash-bounded within 63 characters. It carries an App controller ownerReference, `backoffLimit: 0`, `activeDeadlineSeconds: 960` (the 900 s rollout budget plus 60) and `ttlSecondsAfterFinished: 60`. Its one container `hold` runs `/pause` with `IfNotPresent`, mounts the claim read-only over a read-write source, and runs restricted: non-root uid 65535, a read-only root filesystem, no escalation, drop ALL, RuntimeDefault. The pod has no token and the default ServiceAccount. A required node-affinity term on `metadata.name` places it, never `nodeName`. It tolerates the App's serving pool when the tier names one. Requests are an explicit 0 for CPU, memory and ephemeral storage, so tenant-limits adds nothing and a node packed to its last millicore still takes it. Limits are 10m, 32Mi and 16Mi. It goes through `applyPodSpecServerDefaults`.
- **Labels:** `app.bex.co/app`, `app.bex.co/app-uid` and `app.bex.co/component=disk-holder`, the new shared `appv1alpha1.ComponentDiskHolder`, which bex-api reads too (t003). It never carries `bex.co/app-id` (`renderenv.LabelAppID`, which the Services select on; the task text called it `app.bex.co/app-id`).
- **Image: the kubelet's sandbox image `registry.k8s.io/pause:3.10.2`, not bex's own image.** On 2026-11-21 every production node that listed its images had `registry.k8s.io/pause:3.10.2` (containerd 2.3.3's default). The nodes with an empty list had hit the kubelet's 50-image status cap. containerd pins the sandbox image, so it is never garbage-collected, and the holder pulls nothing. bex's image is on a disk node only when the pod has a health-probe binary: a disk worker never pulls it, and every operator upgrade changes its digest. `/pause` exits 0 on SIGTERM. A node on another sandbox version would pull the 300 KB image once, inside the 15 s mount bound, while the old instance still serves.
- **Shape test:** `TestDiskHolderJobIsTheAppsAndNoServiceSelectsIt, TestDiskHolderPodHoldsTheClaimOnTheVolumesNode and TestDiskHolderContainerRunsPauseRestrictedAndRequestsNothing` pins every field above, the long-name bound and the pooled toleration.
- **Admission check:** `container_policy_admission_test.go` loads the deployed `deploy/gitops/base/operator-workload-admission.yaml` into its own envtest API server and creates every workload as the operator's identity. `admissionTierWorkloads` now includes the holder Job. It is admitted under all four container-policy rows and at the `pro-plus` and `pro-ultra` tiers. The shared privilege mutations are all refused (an extra capability, escalation, privilege, a seccomp override, host namespaces, a host path, a token, a privileged ServiceAccount, init-container capability and seccomp, foreign priority classes). So are the pool mutations (unowned, a non-App owner, a forged app-uid, an uncataloged pool, any pool, the build-only toleration).
