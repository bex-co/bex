## Objective

In every workspace, new sandboxes land on the AX42-1 under Kata, and they land on the gVisor cloud node when the AX42-1 is full, cordoned or down. Scheduling does this alone, with no retry or new code path in bex-api. No sandbox can overcommit the AX42-1's memory.

## Context

- ADR105 § Decision steps 4 and 5.
- The scheduler uses `MostAllocated` scoring (`cluster.yaml` KubeSchedulerConfiguration). It and `ImageLocality` favour the cloud node, so a preferred affinity alone is not enough. A `PreferNoSchedule` taint on the cloud node adds TaintToleration (weight 3) on top of NodeAffinity (weight 2).
- `requestFor` (`lego/backend/internal/sandbox/meter.go`) requests a quarter of both limits today. At that memory request the scheduler would place about 40 agent sandboxes on the AX42-1, and a Kata guest keeps its page cache where the host cannot reclaim it. Memory request becomes equal to the limit for every sandbox, base sandboxes included, because they share the template. The CPU request stays at a quarter.
- The cap is allocatable memory: the memory limit plus the RuntimeClass `overhead`, against kubelet reservations set for 12 agent sandboxes.
- The two 512 GB disks do not hold 13 sandboxes at the 40 GB writable limit.
- `.pm/DO_NOT_DO.md`: no customer-facing capability behind an internal allowlist. There is none here; removing the trial taint opens the node to every workspace.
- Alert rules live in `deploy/gitops/base/rules/`, with tests in `alerts_test.yml`.

## Steps

1. Change `requestFor` so the memory request equals the limit, keep the CPU request at a quarter, and update its tests.
2. Add the preferred node affinity for `bex.co/sandbox-runtime=kata` to the BatchSandbox template, and the `PreferNoSchedule` taint to the cloud sandbox bootstrap. Roll the cloud node surge-first.
3. Set kubelet reservations on the AX42-1 so allocatable memory holds 12 agent sandboxes.
4. Add a disk-pressure alert for the node, with its test.
5. Remove the trial taint. Rollback is restoring it.
6. Remove the `gvisor` RuntimeClass and its admission branch once no Pod uses it.

## Acceptance criteria

- [ ] A new agent session in any workspace runs on the AX42-1 under Kata, even when the agent image is cached only on the cloud node.
- [ ] With the AX42-1 cordoned, a new session starts on the cloud node under gVisor.
- [ ] A new sandbox Pod's memory request equals its limit, and its CPU request is a quarter of its limit.
- [ ] A thirteenth concurrent agent sandbox lands on the cloud node.
- [ ] The disk-pressure alert fires in `alerts_test.yml`.

## Out of scope

- A second server or an EX63. File it when sustained use passes half the slots.
- Keeping the AX42-1 for agent sandboxes only. It needs a per-create scheduling knob in OpenSandbox (ADR105 § Decision step 4). File it as a w6 note if base sandboxes crowd agent sessions off the node.
