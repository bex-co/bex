## Objective

Serve the workspace's billing email (read: `can_view_billing`) and let Admins and Billing members set it (`can_manage_billing`) on GraphQL, REST and MCP, behind a new `billingEmail` plan feature with Pro as its minimum. A write updates the stored billing email and the Stripe Customer's email. On Hobby the read returns the owner's account email and the write answers `PLAN_FEATURE_REQUIRED`; a downgrade to Hobby sets the stored and Stripe emails back to the owner's account email.

## Context

- `tenants.billing_email` holds the address set at creation (`lego/backend/internal/store/workspace_creation.go`; `normalizeBillingEmail` in `lego/backend/internal/workspaces/service.go`).
- Plan gates: `planFeatures` in `lego/backend/internal/core/plan_gate.go` (`PLAN_FEATURE_REQUIRED` with `feature`, `requiredPlan`); ADR030 §9's table gets the row.
- The Stripe Customer is found through the workspace's billing mapping (`lego/backend/internal/billing/`).
- Check render.com/docs/audit-logs for an event Render records for a billing email change, and record it if one exists.

## Steps

1. Add the feature, the read and the write in the shared core, then the three adapters.
2. Write Stripe first, then the store, so a Stripe failure changes nothing.
3. Hook the plan change so a move to Hobby resets the email.

## Acceptance criteria

- [x] Tests: a Pro write updates both copies and reads back on every surface; a Hobby write is refused with `PLAN_FEATURE_REQUIRED` and changes nothing; a Developer cannot write; a downgrade resets the email; a Stripe failure leaves the stored email unchanged.

## Outcome (2026-11-25)

Done. `core.FeatureBillingEmail` (`billingEmail`, Pro) gates the write; `workspaces.Service.BillingEmail` (can_view_billing) and `SetBillingEmail` (can_manage_billing, re-asserted uncached) serve REST `GET`/`PUT /v1/workspaces/{workspaceId}/billing/email`, GraphQL `workspaceBillingEmail`/`setWorkspaceBillingEmail` and MCP `get_billing_email`/`update_billing_email`. The write sets the Stripe Customer's email first (`billing.StripeClient.SetCustomerEmail`), then `tenants.billing_email`. Every plan write (`store.updateTenantPlanTx`) clears the stored address on a move to Hobby, and `ChangePlan` then gives the Customer the owner's account email back (logged, not returned, if Stripe fails, since the plan has changed). Render's audit log has no billing email event; bex's lists the write under its own verb `workspaces.SetBillingEmail`. ADR030 §9 has the row. Tests: `internal/workspaces/billing_email_test.go`, `internal/billing/customer_email_test.go`, `internal/store/workspace_billing_email_pg_test.go`, and `internal/api/billing_email_e2e_test.go` (real Postgres and OpenFGA, every surface, every role, the Hobby refusal and the downgrade).
