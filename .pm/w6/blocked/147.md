# 147 — A live native SSH session ends every hour or two with no revocation, deploy or instance change

Why: Render closes an SSH session only when the user ends it, the service redeploys or restarts, or its SSH infrastructure goes into maintenance ([render.com/docs/ssh](https://render.com/docs/ssh)). On bex a plain `ssh <srv>@ssh.bex.co` session dropped three times in three hours with none of those, so a long-running SSH session dies under the user.

- **Source / severity / estimate:** w6/m482 t006 probes on production, 2026-11-19, pin `dff52c596d13`, before the next deploy; fixture `srv-dbvg5tm014qc73acud2g` in `bex-canary` (since deleted). **Major** for anyone holding a session; ~1h30m.
- **What the probes saw.** One instance, one SSH key, no gateway restart (the gateway pods `6cb8d858d7-*` ran from 11:36Z to 18:07Z) and no deploy step. Three OpenSSH sessions ended with `rc=255`, 7–9 s after their last 10 s tick:
  - opened 14:15:02Z, ended 16:59:02Z (after 9840 s);
  - opened 16:15:02Z, ended 17:17:03Z (after 3721 s);
  - opened 17:17:33Z, ended 18:03:33Z (after 2760 s; the deploy job was still checking out).
  - Each ended on a whole minute from its own open time, which is the 60 s revalidation tick (`core.DefaultStreamRevalidateInterval`). Each reconnect 30 s later succeeded with the same key, and the `fresh` probe's 163 short sessions every 2 min all answered.
  - Two dashboard Shell sessions held on the same instance over the same hours (14:14–18:14Z, 16:14–19:07Z) never dropped this way.
- **What the gateway counted.** `bex_ssh_gateway_channel_reauthorizations_total{result="rejected"}` and `bex_ssh_gateway_sessions_total{result="revoked"}` rose together with the 17:17 and 18:03 drops. Prometheus scrapes the gateway through its Service, so only one pod's counters show, and the 16:59 drop was on the other pod. The gateway logs nothing when it ends a session this way, so the failing check is unknown.
- **Mechanism (code).** `reauthorize` (`lego/backend/internal/sshgateway/nativessh/server.go:728-752`) runs on every tick through `sshgateway.WithRevalidation` (`:597`, `:657`), and `core.WithRevalidation` (`lego/backend/internal/core/revalidate.go:55-58`) ends the stream on any error. `reauthorize` counts three different failures as one `rejected` and returns an error for each, without telling a transient one apart:
  - `Store.SSHKeyByFingerprint` fails, including on a database error or its `HandshakeTimeout` (10 s) deadline;
  - `verifiedOwner` fails (`EmailVerified`, a Kratos call from the gateway, `cmd/ssh-gateway/main.go:288`);
  - `Apps.ResolveSSHSession` fails with anything but `ErrNotFound` (its authorization checks; compare w4/695, the reset OpenFGA connection fixed in bex-api).
  - Native SSH runs all three on every tick; the web shell's revalidation runs only `ResolveSSHSession` (`webshell/websocket.go:336-340`). That fits only native SSH dropping, though the Shell probe also authorized as an API key's machine identity rather than the user.
- **Fix direction:** log each rejection's cause (bounded, no subject or key). End the session at once only on a definite answer: the key is gone or bound to another subject, the owner is unverified, a deny (`ErrForbidden`), or the target is gone. Retry a transient error on the next tick, and still end the session after a few transient failures in a row so an outage cannot keep sessions open without checks. Never turn an error into an allow.
- **Done when:** a unit test where the key lookup, the email check or the resolver fails once with a transient error keeps the session open, and one where the key is deleted still ends it at the next tick. On production, a held `ssh <srv>@ssh.bex.co` loop runs to its 4 h cap with no `rc=255` between deploys, and the gateway logs the cause of any session it ends.

## Triage 2026-11-19 — fix shipped, the production hold waits for the pin

- **Premise held.** `reauthorize` returned an error for any failure of its three checks, and `core.WithRevalidation` ends the stream on the first error, so one failed tick of any check ended the session.
- **What production's logs say about the failing check.** Loki keeps the old gateway pods' lines. At the 16:59:02Z drop, pod `…-ndtdl` logged only `ssh gateway connection ended: context canceled`. Nothing in the window says `core: authorization unavailable` (OpenFGA) or `two-factor check unavailable` (the 2FA verb), and both log when they fail, so neither was the cause. bex-api answered `/v1/identity-email-verification` with 200 every time from 14:00Z to 18:10Z, all under 0.5 s (`bex_api_http_requests_total`, `bex_api_http_request_duration_seconds`). What is left: the gateway's key lookup in Postgres, a Kubernetes or store read inside `ResolveSSHSession`, or the gateway's HTTP call to bex-api failing before bex-api answered. The fix covers all of them, and the gateway now logs which one it was.
- **Also found.** bex-api answers 401 when the signed verb's 2 s nonce claim times out (`agentsession/http.go`), and the client turned that 401 into the same `ErrForbidden` as "unverified human". It is now `agentsession.ErrEmailUnverified` only for the real answer.
- **Shipped in `df12a997a`.**
  - A definite no still ends a live session at the next tick: the key deleted or bound to another subject, an unverified owner, a deny (login requirements and protected environments included), the service gone, or `suspended` / `ineligible` / `instance_gone`.
  - A check that gets no answer is retried, and three in a row end the session anyway, so an outage cannot keep sessions open without checks.
  - A channel never opens on an unanswered check. A multiplexed agent-session connection refuses only that channel. The App path records the session `failed`, not `revoked`.
  - `bex_ssh_gateway_channel_reauthorizations_total` gains `result="unavailable"`. Each failure logs `ssh gateway: reauthorization rejected: <cause>` or `ssh gateway: reauthorization unanswered: <cause>: <error>`, and the third unanswered tick also logs `ssh gateway: ending a session after 3 revalidations in a row without an answer`. None of these lines carries the subject or the key.
  - ADR035 § A check that gets no answer records the behavior.
- **Unit tests** (`nativessh/transient_reauth_test.go`), each run against all three checks: no answer keeps the session open; a deleted key, an unverified owner or a deny ends it at the first refused tick; three unanswered ticks in a row end it; an answered tick resets the count. Further tests cover the multi-channel and App-path channel opens, the logged causes (never the subject or the fingerprint) and a deleted instance through the real resolver. Mutation checks: removing the retry, the reset, the definite path or the multi-channel `continue` each turns a test red.
- **Next, once production's pin carries the fix.** In `bex-canary`, hold one plain `ssh <srv>@ssh.bex.co` loop with a 10 s tick, plus a fresh connection every 2 min (the w6/m482 t006 probe shape), for 4 h. Done when no session ends `rc=255` except at a gateway release's 1 h drain bound or at the 4 h cap. Then read the gateway's `reauthorization unanswered` lines (both pods, Loki `{namespace="bex-system", pod=~"bex-ssh-gateway.*"}`) and record which check was failing. Delete the fixture, keys and probes afterwards.
- **Not in scope.** The Web Shell's watchdog runs only `ResolveSSHSession` and still ends at its first unanswered tick, with the `unverified` reason. Its probes never dropped this way.
