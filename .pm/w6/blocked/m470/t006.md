## Objective

The deploy that ships this milestone leaves both SNI DaemonSets alone unless their binary changed. An external TLS client to a Key Value store and one to a Postgres database then survive a later deploy whose SNI binaries are byte-identical.

## Context

- At promotion both DaemonSets run `bex-operator@sha256:b4104643…` (producer `14eaa71b9`). `936b61bab` (w6/m467) changed `lego/types/v1alpha1` after it, so the next pin rolls them once whatever this milestone does (README § Findings). Compare against the pin that is live when this ships.
- Production deploys `main` at most once per 6 h (`deploy.yml` `changes` job). The write-back's log says `kept` or `moved` per proxy (t003).
- External paths go through the edge LB to the SNI proxies: Key Value on `<id>.kv.bex.co:6379` (TLS), Postgres on `<id>.db.bex.co:5432`. Each needs its IP allowlist to admit the client. Streams close after 1 h idle and 24 h total, so the probe pings every few minutes and starts less than 24 h before the deploy it watches.
- Production access: `scripts/fetch-app-kubeconfig.sh`, with `BEX_SSH_KNOWN_HOSTS_FILE` pointing at a temp file holding `* <key>` from `~/.ssh/bex_cp_host_ed25519.pub`. `~/.ssh/known_hosts` line 73 is stale; do not edit it. Signed-in API calls go through `bash scripts/qa-login.sh` (never read `.env` or `muse.env` yourself).
- Gate: a production pin whose producer contains the commit (`git log origin/main --grep "pin platform images"`, then `git merge-base --is-ancestor <commit> <producer>`).

## Steps

1. Before the shipping deploy, record each DaemonSet's image, generation, latest ControllerRevision, and pod names with start times. Hash the producer's `/kv-sni-proxy` and `/pg-sni-proxy` with t001's command. If they differ from the running image's, name the commit and expect one roll.
2. After the deploy, read the write-back's `kept`/`moved` lines and check the DaemonSets: the same pods and revision when kept, a completed rollout when moved.
3. Create a free Key Value store and a Postgres database in `bex-canary`, each with an allowlist that admits the probe's address. Hold one TLS client to each (note `CLIENT ID` and `pg_backend_pid()`, then `PING` / `SELECT 1` every few minutes) across the next deploy whose write-back keeps both pins. Afterwards check both answer on the same connection, and that both DaemonSets kept their pods and revision.
4. Record one deploy whose write-back moved a pin: the DaemonSet rolled to the new digest and the wait step waited for it.
5. Delete both probes by ID (each `GET` then answers 404) and any client pod.
