## Objective

The routines start with the bex repo's Go module, build and vet caches and the dashboard's yarn cache already in place (ADR105 § Alternatives considered: do it regardless). Today every session starts cold, and every cache sits on the gVisor rootfs (`overlay2=none`).

## Approach

- A routine-only agent template whose image is the agent image plus those caches, built at the paths a session uses (`/workspace`, `/home/bex`), so the build cache's keys match. The repo is public, so the caches expose nothing. Customers' `agent` template does not change.
- Built and pinned with the agent image in `deploy.yml`, so the driver in the cache image always matches the deployed agent image.

## Measured 2026-11-13 (local, native arm64, no gVisor; ratios, not sandbox times)

- A cold build of the four `lego/` modules took 35 s. With only the 2,036 third-party packages pre-built (the module list from `go list -deps -test`, built at the same `GOMODCACHE`/`GOCACHE` paths), the same build took 17 s and recompiled 1 third-party package. So a dependency-only cache halves the build.
- `go mod download` for the four modules took 50 s here; in the sandbox it took 137 to 436 s (ADR105 t001). A baked module cache removes it.
- Size: 4.5 GB of module cache (all four modules' graphs, the extracted trees and their zips) and 2.9 GB of build cache (dependencies, own packages and vet). The layer to bake is the module cache without its zips plus the dependency build cache.
- A dependency-only layer changes only when a `go.sum` or the third-party import set does, so its build can be cached across deploys and the sandbox node keeps it between pulls. Own packages still compile in each session.
