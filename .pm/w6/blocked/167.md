# Do the routines still need `agent-4c-8g`? Measure a week of their CPU and memory, then recommend a template per routine

Why: every `rt-*` automation runs on a 4 CPU / 8 GiB sandbox. That is twice the memory charge of `agent` (2 CPU / 4 GiB) once m566 bills on use, and no one has measured what the routines use since m354 chose it.

- **Background.** [m354](../done/m354/README.md) (user decision 2026-11-12) moved the routines to `agent-4c-8g` after five of eight died with their sandbox, some out of memory, on a `cx33`. The size was chosen for headroom, not from a measurement of each routine.
- **Start when** m566 t001 has recorded `sandbox_cpu_seconds` for agent sandboxes for 7 days. Until then park this note with a date gate.
- **Memory.** Check whether Prometheus keeps a pod memory series for `*-sandbox` namespaces (the cadvisor job in `deploy/gitops/base/prometheus.yaml` renames and keeps the pod CPU row). If it keeps none, file the relabel that keeps the pod's working-set peak; this note needs peak memory, not allocated memory.
- **Output.** Per routine (`agent_automations.name` joined through `agent_sessions.automation_id`): turns, p50/p95 CPU cores used during turns, peak memory, and turn duration. Recommend `agent` for a routine whose peak memory stays well under 4 GiB and `agent-4c-8g` otherwise. Record the table in [ADR105](../../../docs/ADR105-agent-sandbox-hetzner-bare-metal.md).
- **Decision.** Changing a routine's template reverses part of the user's m354 decision: present the recommendation to the user (`/unblock w6`), and do not change any automation without their decision.
- **Stakes.** Weighted today: $0.434 per hour for 4c-8g against $0.217 for 2c-4g. Billed on use (m566): memory $0.106 per hour against $0.053, plus the CPU actually used.

## Parked 2026-11-23 (date gate: 2026-12-01)

The measurement needs a week of both halves, and neither has one yet.

- **CPU.** Production's pin `cded300699` (2026-11-23T17:33Z) is the first to carry `506b9b40ef` (m566 t001), so agent sandboxes' `sandbox_cpu_seconds` rows start with that deploy. Those rows are hourly totals. p50/p95 cores during a turn come from Prometheus instead: `sandbox_pod_cpu_usage_seconds_total` has kept every `*-sandbox` pod's CPU, agent pods included, since w22/m314 (2026-11-17), and production keeps 30 days. Use `rate(...)` over each turn's window from `agent_session_turns`. The hourly rows are the cross-check.
- **Memory: Prometheus kept none, so the relabel shipped with this park.** On 2026-11-23, production Prometheus held no `container_memory_*` series for any `*-sandbox` namespace over two days, while `sandbox_pod_cpu_usage_seconds_total` held 106. Under gVisor the workload container's cgroup has no series. The pod cgroup's row (`container=""`, `name=""`) carries the sandbox's memory, sentry included: the sandbox node's raw cAdvisor reports it. But the `kubernetes-cadvisor` job dropped it. That job now keeps the row as `sandbox_pod_memory_working_set_bytes`, the same way it keeps the CPU row (`deploy/gitops/base/prometheus.yaml`, `scripts/test_platform_metrics.py` `verify_sandbox_pod_scrape`, ADR104 § Scrape). Argo CD applies it from `main`, so its first sample is the first agent sandbox after that sync. m566's `sandbox_memory_gb_seconds` is allocated memory, not a peak.
- **Peak.** Use `max_over_time(sandbox_pod_memory_working_set_bytes{namespace,pod}[turn window])`. It is sampled at the 15 s scrape interval, so a spike shorter than that can be missed: state that next to the table.
- **On resume.** Confirm that both series exist for agent sandbox pods and read each one's first sample. If either has less than 7 days, park again with the date 7 days after its first sample. Otherwise build the per-routine table (turns, p50/p95 cores, peak memory, turn duration) and record it in ADR105. Then present the recommendation through `/unblock w6`, and park on the user's decision. Change no automation without it.
