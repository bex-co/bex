## Objective

Pick how `wormhole` gets onto each native image so the selected primary Python never shadows or breaks it, and pin its version.

## Context

- `deploy/native-common/Dockerfile` (`sh /tmp/bex-native-install.sh python3-venv …`), `deploy/native-base/install.sh`, `deploy/native-base/Dockerfile`
- `lego/operator/internal/build/nativebases.go:33` (`nativeCommonBase`) and `:42+` (per-toolchain bases, Bullseye included)
- Primary runtimes install above the common layer under `/usr/local`; a Debian package installs under `/usr/bin` with the system `python3`.

## Steps

1. Recommendation: the Debian `magic-wormhole` package of each suite (Bookworm and Bullseye carry it), through `install.sh`; compare a vendored wheel set in the system Python if a suite lacks it.
2. Confirm `/usr/bin/wormhole` runs with the system interpreter after a primary Python is installed above (`#!/usr/bin/python3`).
3. Record the version per suite and the reason.

## Files

- deploy/native-common/Dockerfile, deploy/native-base/install.sh, deploy/native-base/Dockerfile

## Acceptance criteria

- [x] Each factory installs wormhole at a recorded version
- [x] A primary Python above it does not change which interpreter `wormhole` runs

## Out of scope

- Buildpack and Docker-runtime services (the tenant's own image)

## Record (2026-11-21)

- **Source: each suite's own Debian `magic-wormhole` package**, added to the shared package list in `deploy/native-base/install.sh`, so both factories install it: the common Bookworm image (`deploy/native-common/Dockerfile`, the only system layer production builds end on) and the per-toolchain bases (`deploy/native-base/Dockerfile`, manual publication only). Versions (Debian madison, 2026-11-21): Bookworm `0.12.0-1.1`, Bullseye `0.12.0-1`, Trixie `0.18.0-1`. Its server-side counterparts in the same suites are `python3-magic-wormhole-mailbox-server` `0.4.1-2` and `magic-wormhole-transit-relay` `0.2.1-1` (Bookworm), used only by the check (t002).
- **Why not a vendored wheel set:** every suite carries the package signed and SBOM-tracked like the rest of Render's tool table, with security updates through the normal Debian channel; a private wheel set would need its own manifest, freshness review and interpreter. The newer upstream line (0.18 in Trixie) is not needed for parity: the 0.12 client speaks the same mailbox and transit protocol as the public relay and current clients.
- **Interpreter:** `/usr/bin/wormhole`'s shebang is `/usr/bin/python3` (Debian's system 3.11 on Bookworm) and its modules live in `/usr/lib/python3/dist-packages`. A selected primary is copied into `/usr/local` and a Python service's virtualenv only prepends `PATH` and sets `VIRTUAL_ENV`, neither of which changes an absolute shebang or the system interpreter's `sys.path`. t002's checks assert it: the factory check requires `command -v wormhole` to be `/usr/bin/wormhole` with that shebang, and every family's generated image runs the same probe after its primary is copied in.
