## Objective

When a disk-bearing `Recreate` rollout's new template names an image the running template does not, the operator pulls that image onto the volume's node while the old instance still serves, and writes the template once the pull has ended or its bound has passed. It never stops a deploy.

## Context

- `holdDiskThroughRollout` / `startDiskHold` / `awaitDiskHolder` (`lego/operator/internal/controller/disk_holder.go`), called from `applyServingDeployment` (`release_config_snapshot.go`) before the Deployment write. `diskHoldNode` picks the node, or skips it when the volume must move.
- The kubelet posts a pod's status between pod syncs, and a sync includes its pulls. The pre-pull pod's container state therefore changes once the pull has ended:
  - it leaves `Waiting`/`ContainerCreating` and the pod ends (`StartError`): the image is on the node;
  - `ErrImagePull`, `ImagePullBackOff` or `InvalidImageName`: the pull failed, and the instance's own pull will report it as today.
- Pulls measured at promotion took up to 48.9 s (milestone README).

## Steps

1. Confirm the design note's premise on the mock cluster or production: a pod whose container pulls for many seconds reports `PodReadyToStartContainers` only after the pull. If it is wrong, carrying the pull in the holder pod may be simpler. Record which.
2. In `startDiskHold`, when the projected template names an image the stored one does not, start the pre-pull Job on the hold's node beside the holder. Wait for both: the holder mounted, and the pull ended, failed, or past its bound (choose it from the measured pulls, and record why). Skip the pre-pull when the hold is skipped. A refused or failed pre-pull is a rollout without one.
3. End the pre-pull Job once the template is written, without cancelling a pull still running in the kubelet: the new instance's pull then waits for it. Also end it on every path that ends the holder.
4. Count each rollout's pre-pull outcome in a metric next to `bex_disk_holds_total`.
5. Tests: a code deploy waits for the pull, a restart and a plan change start none, a cordoned node starts none, a failed pull and the bound both write the template, and no Job is left.

## Files

- `lego/operator/internal/controller/disk_holder.go` (and `disk_prepull.go` if t001 made one), `release_config_snapshot.go`, their tests and envtests

## Acceptance criteria

- [x] A code deploy's template is written only after the new image's pull has ended, failed, or passed its bound, and the old instance serves throughout
- [x] A restart, a plan change and a cordoned node start no pre-pull
- [x] `make test` and `make lint` pass

## Out of scope

- Rolling-update (diskless) services, which serve throughout their pull
- The restore of a served release after a failed rollout ([w6/165](../../../165.md))

## Record (2026-11-23)

**Step 1: the premise does not hold on the CAPD cluster.** A pod on `bex-tenant-0` of the mock cluster (Kubernetes 1.36.1) with two containers shaped as t001's, pulling `python:3.13-bookworm` (373 MB, 60.6 s) and then `node:22-bookworm-slim` (80 MB, 24.4 s), reported `PodReadyToStartContainers=True` 1 s after it was bound, before either pull. Both containers' `StartError` were posted only once the second pull had ended, 86 s later: the first container failed at 15:30:37 and its state reached the API at 15:31:02. Production's v1.34.9 had no pull over 4 s in its last hour of events, and was not probed. The pull still runs in a Job of its own, not in the holder:

- the holder ends as soon as the new instance has the volume, which would cancel a pull still running past the bound;
- the holder stays free of tenant images, their pull credentials and the signature webhook;
- the pull's end is read from container states, which the kubelet posts after the sync's last pull whichever way it posts `PodReadyToStartContainers`.

A second probe, with `activeDeadlineSeconds: 6` on a pod whose pull was running, finished its pull and its `StartError` before the kubelet marked it `DeadlineExceeded`.

**Steps 2–4.**

- `startDiskHold` starts the pre-pull beside the holder on the hold's node (`prePullThroughHold`), and only when the projected template names an image the stored one does not (`newTemplateImages`, init containers included). The template is written once the holder is mounted and the pull has ended, failed or passed `diskPrePullBound`.
- **Bound: 90 s.** The largest pull measured at promotion took 48.9 s, and the kubelet serializes pulls, so a pull can also wait behind another. The old instance serves while the rollout waits, so the bound costs deploy time only.
- **What reads as failed**, so the template is written at once:
  - the Job is refused;
  - its pod does not exist after 15 s: the pod quota, or the signature webhook;
  - a pull fails: `ErrImagePull`, `ImagePullBackOff`, `InvalidImageName` and the other pull reasons;
  - its pod is unschedulable or deleted;
  - a container ends without an image.
- A hold that falls back writes at once, and its pull goes on.
- **When the pre-pull ends.** `settleDiskPrePull` deletes it once the template is written and its pull is no longer running, never mid-pull. It is deleted at once on every path that frees the volume to move or stops the service: a first deploy, a suspend, a disk attach or detach, a skipped hold, `releaseDiskHold` (detach, restore), a later deploy of another image (`replaced`), and the rollout budget.
- `bex_disk_prepulls_total{result}` counts `pulled`, `failed`, `timeout` and `refused` per held rollout's write, next to `bex_disk_holds_total`.
- Tests: `TestDiskPrePullWritesACodeDeployOnlyOnceTheNewImageIsOnTheNode`, `TestDiskPrePullNeverStopsTheRollout`, `TestDiskPrePullPastItsBoundEndsOnceItsPullHas`, `TestDiskPrePullIsStartedOnlyForANewImageOnAHeldNode` (restart, plan change, cordoned node, other pool, no instance), `TestDiskPrePullEndsWhenItsRolloutDoes`, `TestDiskPrePullFollowsTheImageBeingDeployed`, `TestDiskPrePullDoesNotHoldARolloutWhoseHoldFellBack`, `TestDiskPrePullOfAnotherLifetimeIsLeftAlone`, `TestDiskPrePullStateReadsTheKubeletsPull`.
