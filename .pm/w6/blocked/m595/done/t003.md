## Objective

## Record (2026-11-23)

The pre-pull pod carries `app.bex.co/app`, `app.bex.co/app-uid`, `app.bex.co/component=disk-prepull` and, when the template has it, `app.bex.co/verify-image`. It has no `bex.co/app-id`, no `app.bex.co/revision`, no `pod-template-hash` and no `app` container: its containers are `pull-<n>`. It is controlled by a Job, its name starts with `dskpul-`, and it ends `Failed` with each container in `StartError` (exit 128). The kubelet emits a `Failed` Warning event per container.

**Fixed (the test seeds a pre-pull pod and fails without the fix):**

| reader | what it did with the pre-pull | fix | test |
| --- | --- | --- | --- |
| backend logs `ownPods` (store-less history, `appPodNames`, live tail) | dropped `component=disk-holder` only, so it read the `app` container on the pre-pull pod and the kubelet's refusal failed the whole read | drops `component=disk-prepull` too | `TestStoreLessLogReadsLeaveTheDiskHolderOut/disk-prepull` (red without the fix: "container app is not valid for pod dskpul-web-7fq2m") |

**Already excluded (verdict, evidence):**

- **Operator stall and node-loss diagnostics.** `stuckPodMessage`, `pendingPodMessage`, `probeStallMessage` and `nodeLossMessage` go through `instancePods`, which drops every component pod. `TestTheDiskPrePullIsNoInstanceOfTheRollout` seeds a pre-pull pod ended in `StartError`, backing off a pull, pulling for an hour, unschedulable and on a lost node; none sets a message. `diskNode` and `servingInstance` require a ReplicaSet owner (same test).
- **Instances, SSH, crash loop, metrics-server fallback.** `core.OwnAppPods` drops any component pod. `TestMetricsServerSnapshotShowsOnlyTheInstances` now seeds a pre-pull pod beside the holder.
- **Prometheus series and billing instance-seconds.** They match `pod=~PodNameRegex(<CR name>)`, anchored on the CR name, which a `dskpul-` name never matches.
- **Loki.** Reads select `container="app"`. The `pull-<n>` containers never start and write no log.
- **Rollout readers.** The exit, pull-failure and crash readers (`recordRolloutExit`, `permanentRolloutPullFailure`, `permanentRolloutCrash`), `instance_exits`, `serving_condition`, `release_rollout`, `image_digest`, port detection and private ports all require the revision label or the `app` container. So the pre-pull's `StartError` and exit code 128 are never a rollout failure or an instance exit.
- **Other operator readers.** `evacuatedNodeClear` and drain-guard require a ReplicaSet owner. `relabelAppPods` relabels only a Job pod with no component or `predeploy`. The cron Job lists (`cronRuns`, `preemptOtherCronRuns`) list Jobs by the app label, but a cron job cannot have a disk.
- **Egress meter, Services, `servingTargetPort`.** All attribute or select by `bex.co/app-id`, which the pre-pull does not carry.
- **Kubernetes Events.** Neither module reads Events (no `EventList` or `Events(` call outside tests), so the kubelet's `Failed` Warning events reach no deploy diagnosis, `stallDiagnosis` or service events feed. No platform alert rule matches a failed pod, a failed Job or a terminated reason.
- **Quota.** The pod requests nothing. Its CPU limit is 500m per image against `limits.cpu`, which instances cannot fill. A refused Job is a rollout without a pre-pull (`refused`), and a refused pod one with `failed` after 15 s.
