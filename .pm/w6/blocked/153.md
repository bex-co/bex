# The gateway's signed calls to bex-api fail at the transport about once in 150, and the log drops the cause

Why: each of these calls is a user's operation. A failed call refuses one agent git fetch or push, one GitHub read or write, or one model-usage report. It also costs one of the three tries native SSH allows its email check. The gateway logs only `agent credential broker unavailable`, so nobody can tell what failed.

- **Filed by** w6/147's production hold ([done/147.md](done/147.md), 2026-11-20).
  - The probe made about 700 email checks: two held native SSH sessions re-ran it on every 60 s revalidation tick for 4 h40m (about 560 ticks), and 141 fresh connections ran it once each. Five got no response, each logged as `ssh gateway: reauthorization unanswered: email_check_failed: email verification: agent credential broker unavailable`:
    - 06:33:33Z, 06:50:33Z, 08:52:33Z and 08:55:33Z on `bex-ssh-gateway-68877c47b6-qnw2n`;
    - 09:52:39Z on `-59bd49968c-zkq9n`.
  - Each failed within 0.3 s of its tick, so no 5 s client timeout was involved, and bex-api's pods logged nothing at those seconds.
  - w10/m522 saw the same string on the agent git proxy: two `mint failure (service=info/refs …): agent credential broker unavailable` at 08:28:22Z ([its README](../w10/done/m522/README.md), "Seen in passing").
- **Where.** `signedPost` (`lego/backend/internal/agentsession/http.go`) returns `fmt.Errorf("agent credential broker unavailable")` when `httpClient.Do` fails and drops `err`.
  - The email check's client is `&http.Client{Timeout: 5 * time.Second}` on the default transport (`cmd/ssh-gateway/main.go`, `EmailVerificationClient`). It POSTs to `http://bex-api.bex-system.svc:8091`.
  - bex-api's `:8091` server keeps idle connections for 120 s (`newHTTPServer`, `cmd/api/main.go`) and the transport for 90 s. Ticks reuse a connection every 60 s, so neither idle bound explains the failures on its face.
  - A POST is not replayable, so Go never retries it on a pooled connection that turned out dead.
- **Steps.**
  1. Wrap or log the transport error's class (dial, reset, EOF, timeout) at the gateway, never with the subject or the key. Keep the caller-facing message as it is.
  2. Read a day of production lines to find the cause.
  3. Fix that cause. One option: retry once when the request never reached bex-api (`httptrace` shows no bytes were written, or the connection was reused and died before the response). Keep the nonce's single use intact.
- **Done when:** the gateway's log names the transport cause of every `agent credential broker unavailable`, with a test that checks the line carries it. The production cause is recorded here. On production, held SSH sessions log no `email_check_failed` across 4 h, or the remaining rate is explained and accepted.

## Cause found, gateway fix shipped, parked for the production read (2026-11-20)

- **Every failure came from the operator's node.** All 11 `agent credential broker unavailable` lines in Loki since 2026-11-15 (git mints, a usage report, a two-factor check and the five email checks) came from a gateway pod on `bex-platform-k9wb4-dpjxh`. The gateway pods ran about as long on `jfc55` (107 pod-hours against 128 over the week, from `kube_pod_info`), which logged none. `bex-controller-manager` ran on `dpjxh` at every one of the 11, and a bex-api pod ran on `dpjxh` each time too.
- **The operator's port sweeps fill that node's conntrack table.** Read on production at about 12:50Z with `cilium-dbg` in the Cilium agents:
  - On `dpjxh`, `cilium_bpf_map_pressure{map_name="ct4_global"}` read 0.997 of its 131,072 entries. `cilium-dbg bpf ct list global` held 132,140 entries, 130,065 of them TCP connects from the operator's pod to three tenant pods, one port each: 65,535 to one pod, 60,598 and 3,932 to the other two. On `jfc55` the same map read 0.014.
  - From 01Z to 13Z the `dpjxh` agent logged 13 to 26 conntrack GC passes an hour that deleted at least half the table. The `jfc55` agent logged none. INGRESS `Policy denied` drops stood at 273,893 on `dpjxh` and 932 on `jfc55`.
  - The sweeps are `lego/operator/internal/portscan` (ports 1–65535, 512 workers), run for private-network port discovery (`private_ports.go`) and port detection (`port_detect.go`).
- **Mechanism.** Cilium's conntrack maps are LRU. A full table evicts the entries of idle connections, including the `SVC` entry that pins a pooled gateway→`10.97.99.11:8091` connection to one bex-api pod (`TCP SVC … -> 10.97.99.11:8091 … BackendID=…` in the same dump). The connection's next segment chooses a backend again, and with two bex-api pods it goes to the other pod about half the time. That pod has no such connection and resets it, which is a fast failure with nothing logged by bex-api. A POST is not replayable, so Go returned the error. The production log line shipped below names the class and should read `cause=reset (reused connection idle …)`.
- **Shipped in `dfcd4e23c`** (`lego/backend/internal/agentsession/http.go`):
  - Every failed attempt logs `agent credential broker: POST <verb path> attempt <n> failed: cause=<dial|reset|eof|timeout|canceled|other> (<new connection|reused connection idle …>); <retrying on a new connection|giving up>: <bounded error>`. The line never carries the body, so no subject or key. A replay logs `answered on retry (status …)` or `retry refused (401)`. The message callers relay is unchanged.
  - An attempt bex-api cannot have answered goes once more on a new connection with the same signed bytes. That is a failed dial, or a reused connection that died before any of the answer arrived. The nonce in the body keeps the replay single-use. A replay that bex-api refuses as seen (401) is still reported unavailable, never as a refusal. Timeouts, cancellations and fresh connections are not replayed.
  - `http_transport_test.go` resets pooled connections with an RST, as the other pod does. The tests cover the replay on a new connection, also with both pooled connections dead, a lost answer whose replay the real nonce claim refuses, and a reset fresh connection, a timeout and a failed dial. Each log line's cause is asserted. Mutation checks: removing the retry, the new-connection client, the 401 mapping, the fresh-connection or the timeout guard, or the reset class each turns a test red.
- **The table filling up is filed as [w6/156](../156.md).** It hits every pod on the operator's node (bex-api, bex-db, Kratos, Hydra, OpenFGA, Argo CD), not just the gateway. This item stays the gateway's.
