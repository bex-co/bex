## Objective

Reuse layers across runs: `cache-from`/`cache-to: type=registry,mode=max` on ghcr per image, written only from main, plus `RUN --mount=type=cache` for Go module/build and npm caches.

## Acceptance criteria

- [ ] A second run with unchanged inputs shows cached layers for every image and takes a fraction of the first.
- [ ] PR or non-main runs cannot write the cache.

## Done — 2026-11-06

- Registry layer cache (`<image>:buildcache`, `mode=max`, `ignore-error=true`) on the **operator** and **OpenSandbox controller** builds only. Their shipped layers install no OS packages. dashboard, opensandbox-server and agent-sandbox stay uncached on purpose: their shipped layers run apt/apk installs or upgrades, and a cached layer would stop picking up security fixes and then trip the CRITICAL CVE gate. Revisit with a dated cache epoch if those builds dominate.
- Every `go build` in `lego/Dockerfile` (16) and the controller build use `RUN --mount=type=cache,target=/root/.cache/go-build`, so exported layers carry binaries, not the compile cache. Registry cache does not export cache mounts, so Go compile reuse across runs would need persistent BuildKit state (not done).
- Writers: only main-only, reviewed workflows hold `packages: write` on these packages (deploy, pg-operand-image, hcloud-csi-image), so a cache layer has the same trust as the pinned image. Runs are serialized by `bex-production-deploy`.
- Not done: copying only `types/go.mod` before `go mod download` (the Dockerfile notes the source must be present).
