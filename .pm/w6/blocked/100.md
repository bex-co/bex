# Argo CD comparisons time out on git (60 s) intermittently, so deploy pins stall and the proxy gate fails

Why: a deploy whose pin Argo cannot compare in time fails its `wait for PROXY-compatible datastore proxies` gate, so a green main does not deploy (run 41401407222, 2026-11-02).

- **Evidence (2026-11-02 ~09:25 UTC):** every Argo application showed sync `Unknown`. `bex-operator` reported `ComparisonError: … rpc error: code = DeadlineExceeded`, and its last successful sync was 07:25. Controller logs showed `git_ms: 60002` / `compare_app_state_ms ≈ 60000` on `kpack`, `openbao-backup` and others while `log-shipper` compared in 583 ms. The repo-server's own `GenerateManifest` calls were all OK in 2 h (556 calls, max 13.9 s). `bex-pg-sni-proxy` stayed on `@f9ca5cd…` instead of `@e1b8dff…`. At the same time this laptop saw intermittent `api.github.com` connection errors, while githubstatus.com reported operational.
- **Likely cause:** git-over-SSH (`git@github.com:bex-co/bex.git`) ls-remote/fetch latency from the cluster spiking past the controller's 60 s repo-server timeout. Every new main commit invalidates the manifest cache for all git-sourced apps, so a slow fetch blocks every comparison at once.
- **Look at:** repo-server `--repo-cache-expiration` / `reposerver.git.request.timeout`, `controller.repo.server.timeout.seconds` (raise to 180 s), and whether the git-sourced apps can use one shared revision cache. A GitHub HTTPS read-only token instead of SSH is another option. Check the repo-server's network path (tenant-node egress policy) for SSH to github.com.
- **Expected:** a transient git slowdown delays one comparison, not every deploy gate.

## Root cause and interim fix — 2026-11-02

- **Not the network:** from the repo-server pod, an SSH handshake to `git@github.com` took 0.7–0.9 s three times out of three, and HTTPS `git ls-remote` took 0.74 s.
- **The checkout is the cost:** `.pm` holds **1,448 MB of the repo's 1,553 MB of tracked bytes (93%) and 37,178 of 43,127 files**, about 14k of them json/txt/log evidence. The pack is 749 MB. Every main commit invalidates ~30 git-sourced apps, and each re-checks-out the whole tree on the repo-server. The controller logged `git_ms` of 60002 under the stock 60 s timeout.
- **Interim fix, shipped `7bc6a62aa` and applied live ~09:31 UTC:** `controller/server.repo.server.timeout.seconds = 180` and 2 repo-server replicas, set by deploy.yml after the Argo install, with a restart only on change. Within 6 min, 31 of 32 apps were Synced (from 9), `bex-operator` synced at 09:36:50, and `bex-pg-sni-proxy` reached `@e1b8dff…`. **But** some git steps already take up to 180 s (`git_ms` 180008–180093), so the ceiling will be hit again as `.pm` grows.

## BLOCKED (2026-11-02): needs a user decision on what Argo checks out

- **(A) Move bulky `.pm` evidence out of the deploy repo (recommended):** json/log/tar/binary evidence goes to a separate `bex-pm-evidence` repo, or object storage, with links from the markdown. Board markdown stays where it is. The checkout shrinks ~90% for every consumer: Argo, CI checkouts and local clones. Cost: one migration plus a rule change for `/pm` and the QA skills on where evidence goes. History keeps the old blobs unless separately purged (a destructive rewrite, not proposed).
- **(B) Point Argo at a slim generated branch:** CI publishes only the deploy-relevant paths (`deploy/`, `lego/operator/config/`, `infra/clusterapi/`) to a `gitops` branch that Argo tracks. Repo content stays as is. Cost: a new publish step and a second source of truth that must stay consistent with main, plus changes to the app-of-apps and the supersession/pin checks that read `origin/main`.
- **(C) Keep raising timeouts:** no structural change, but every timeout raise only delays the next stall as `.pm` grows.
