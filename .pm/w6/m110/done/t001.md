## Objective

Decide, once, how bex identifies an App's pods in Prometheus, so t002 and t003 implement one selector instead of two opinions. Also settle the one open factual question the filing could not: whether production's autoscaler reads metrics-server (immune to this bug) or the Prometheus fallback (exposed to it).

## Context

- The current selector is a pod-**name shape** heuristic, documented at `lego/backend/internal/metrics/source.go:243-253` and in `docs/ADR010-observability.md`: `pod=~"<app>-[a-z0-9]+-[a-z0-9]{5}"`, chosen because "kubelet metrics carry pod NAMES but not pod labels (there is no `app.bex.co/app` to match on)".
- That statement is accurate for the scrape as configured: `deploy/gitops/base/prometheus.yaml:194-217`'s `kubernetes-cadvisor` job uses `kubernetes_sd_configs: [{role: node}]`, so no `__meta_kubernetes_pod_label_*` is available to relabel into a series label.
- But **kube-state-metrics is already scraped** — `deploy/gitops/base/prometheus.yaml`, `job_name: kube-state-metrics`, target `prometheus-kube-state-metrics.monitoring.svc:8080` — so `kube_pod_owner` / `kube_pod_labels` are available for a PromQL join today, with no new infra.
- Two candidate selectors:
  - **(a) shape tolerance** — `pod=~"<app>-[a-z0-9]+(-[a-z0-9]{5})?"`. Cheap, no new dependency. Safety argument to re-check and record: `[a-z0-9]+` cannot span a hyphen, so an App named `web` still cannot match a sibling App `web-api`'s pods in either the truncated (`web-api-<hash><5>`) or untruncated (`web-api-<hash>-<5>`) form.
  - **(b) label join** — select on the pod's owning workload via kube-state-metrics instead of on its name. Immune to name length, name shape, and future changes in Kubernetes' generator; costs a join and a dependency on kube-state-metrics staying scraped.
- Autoscale has two readers: `NewMetricsServerReader` (`lego/operator/internal/controller/autoscale.go:80-88`, `labelSelector=<labelApp>=<app>` — immune) and `NewPrometheusMetricsReader` (`:96-141`, the shape heuristic — exposed). Its own comment says the Prometheus one is "Used when metrics-server is unavailable (e.g. `BEX_PROM_URL` is set but metrics-server is not)".

## Steps

1. Read the reader-selection wiring in the operator's `main`/setup and the production operator env (`BEX_PROM_URL`, metrics-server presence) and record which reader production actually constructs. Write the answer into the milestone README's Unverified section, converting it to a fact or keeping it flagged.
2. Confirm the pod-name arithmetic against the pinned dependency rather than from memory: `k8s.io/apiserver@v0.35.0/pkg/storage/names/generate.go`, `MaxGeneratedNameLength = 63 - 5 = 58`, base truncated then a 5-char suffix appended. Derive the exact service-name threshold for each observed `podTemplateHash` length (6–10 chars seen live) and record the table.
3. Evaluate (a) vs (b) against: correctness at every name length, cross-App collision safety, cardinality/query cost, behavior when kube-state-metrics is down, and how each is tested without a live cluster.
4. Pick one. Record the decision and its rationale in the milestone README, and note whether `docs/ADR010-observability.md`'s heuristic paragraph needs rewriting (it does if (b) wins; it needs amending either way, since the current text asserts a shape guarantee Kubernetes does not make).
5. Decide whether the chosen selector becomes a **shared helper** used by all three call sites, or stays duplicated. Three copies of one PromQL fragment is what let this drift; state the choice so t003 implements it deliberately.
