## Objective

Make the App `instance_seconds` meter actually measure something. Today it selects pods by a name that no pod has ever had, so every App's compute has been metered as zero for the meter's whole life while Postgres and Key Value meter correctly.

## Context

- `lego/backend/internal/usage/service.go:808` passes `app.Name` from a `store.App`. Per `lego/backend/internal/store/store.go:96-102`, that field is the workspace-scoped public service name.
- The pods are named after the Kubernetes object: `core.CRName(tenantID, name)` = `tenant + "-" + name` (`lego/backend/internal/core/base.go:1379`), set at `lego/backend/internal/apps/service.go:1736`, and used verbatim as the Deployment name at `lego/operator/internal/controller/app_controller.go:1751`.
- The datastore sibling is the control that shows the fix's shape: `usage/service.go:573` passes `ds.Name`, a real CR name, into `queryInstanceSecondsStateful`, and Postgres/Key Value charge lines are correct live.
- Not every App is object-named with the prefix. `nameTaken`/`appCandidateNames` (`lego/backend/internal/apps/service.go:1809-1832`, `core/base.go:1388-1393`) document that Apps created before the w4/m19 scheme are still object-named **bare** and were never renamed in place, and that `tenantID == ""` skips the prefix entirely. A fix that assumes the prefix unconditionally will break exactly those rows — the same way the current code breaks the prefixed ones.
- The consumer is what makes this silent: `queryInstanceSecondsByMatcher` (`usage/service.go:933-950`) returns `(0, true)` when the query succeeds and matches nothing, and `processAppMeterWindowResult` (`:793-844`) persists that as a real row with `SourceHealth: healthy`.

## Steps

1. Resolve the App's real Kubernetes object name at the meter call site rather than guessing it — prefer reading the object name the same way the rest of the backend resolves an App (the `appCandidateNames` order), so a legacy bare-named App still meters.
2. Apply the selector chosen in t001.
3. Separate "matched nothing" from "genuinely zero" in `queryInstanceSecondsByMatcher`'s contract, so a selector that matches no pods can never again be persisted as a healthy zero. Decide where the distinction lives (an extra presence probe, or a source-health state) and keep `processAppMeterWindowResult`'s existing "a real zero is real coverage" behavior intact for an App actually scaled to zero.
4. Investigate — do not assume — why `build_seconds` is likewise absent from every service's charge tree. `queryBuildSeconds` (`usage/service.go:1103-1114`) selects build Jobs by the label `labelBuild: appName` in `s.Namespace`, a different mechanism from the pod-name matcher. Establish its own `file:line` cause. If it is the same "which name was passed" defect, fix it here; if it is something else, record it as its own finding rather than folding it in.
5. Re-probe live after deploy: the in-page `usage { estimatedCost { resources { serviceName resourceKind charges { kind quantity unit costUsd } } } }` query must show an `instance_seconds` line on a `resourceKind: "service"` row.

## Acceptance criteria

- [ ] A running paid-tier service produces a non-zero `instance_seconds` quantity whose hours match its actual uptime for the window.
- [ ] A legacy bare-object-named App (and the `tenantID == ""` path) still meters — covered by a test, since production may hold no such row to check.
- [ ] Postgres/Key Value metering is untouched and still correct.
- [ ] A selector matching no pods is no longer persisted as a healthy-zero `usage_hourly` row; an App at zero replicas still is.
- [ ] `build_seconds`' absence has its own established cause, recorded either as fixed here or as a separate finding with `file:line`.
