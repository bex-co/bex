## Objective

Check that this milestone's change is consistent across every surface it exposes, and that where bex differs from render.com the difference is recorded as a deliberate divergence rather than left as silent drift.

## Context

- Metrics reach callers through one funnel — `metrics/rest.go:92`, `metrics/graphql.go:298` and `metrics/mcp.go:88` all call `MetricsWithQuantiles` → `Metrics` → `promResourceQueryFor` — so a selector fix moves all three by construction. The parity question is whether they *report* the same thing, including the empty case: what each surface returns for a resource with genuinely no series.
- `instance_seconds` appearing in `estimatedCost.resources[].charges` changes what the dashboard's `/billing` charge tree renders (`dashboard/src/features/usage/components/charges-card.tsx`), including its per-resource expansion and the Services category subtotal.
- Render exposes both a metrics API and a billing/usage surface; ADR018's parity ledger is the record of where bex matches and where it deliberately does not.

## Steps

1. Exercise the same metric on all three surfaces for the same service — REST `/v1/metrics/{segment}`, GraphQL `metrics(name:)`, MCP's metrics tool — and confirm identical series, units and label vocabulary, for a service with data and for one without.
2. Confirm the empty case is reported the same way on all three (empty list vs null vs error), and that whatever it is, it is what the dashboard's "No data in range" state expects.
3. Open `/billing` and confirm the charge tree now shows compute per service, that the Services category subtotal includes it, and that the per-resource expansion is still readable with two charge kinds per service.
4. Compare against render.com's own metrics + usage surfaces for the same concepts and record any drift in `docs/ADR018-render-parity.md` as divergence, with a reason — not as a silent difference.
5. Note any follow-up the comparison surfaces as new board items rather than widening this milestone.
