# Decide: should Suspend require typed confirmation, matching Delete?

Why: bex currently claims Render lifecycle parity while using lighter confirmation for an action that immediately takes a service offline, so the difference should be explicitly accepted or closed instead of remaining accidental drift.

From the 2026-08-21 live bex-vs-Render Background Worker QA pass
(https://claude.ai/code/artifact/29934e6e-7bd8-4fa0-8a86-26327bb72932, finding
5). On bex, Suspend is a plain two-button dialog ("Suspend `<name>`?" ->
Cancel/Suspend). On Render, Suspend requires typing the exact phrase
`sudo suspend background worker <name>` before the button unlocks — the same
friction Render (and bex) both already apply to Delete.

Two reasonable positions, not an obvious bug either way:

- **Match Render:** consistency, and Suspend does take a paid service
  offline immediately (real, if reversible, impact).
- **Keep the lighter dialog:** Suspend is trivially reversible via Resume,
  unlike Delete — deliberately lighter friction for a reversible action is a
  defensible design choice, not an oversight.

Delete already matches Render exactly (typed-phrase confirmation on both
platforms) — this note is scoped to Suspend only. Whichever way this goes,
record the decision (a line in this note's resolution, or wherever bex
tracks UX-parity decisions) so it doesn't get re-discovered as a "bug" by a
future QA pass. If "match Render" wins, it's a small dashboard change to the
Suspend confirmation dialog (`dashboard/src/features/services/`, the same
component family Delete's typed-confirmation dialog already uses).
