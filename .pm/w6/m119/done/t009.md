## Objective

This milestone's two behavioural claims — that an auto-hibernated private service never wakes on its own, and that `resumeService` does not recover it — were established with samples **90 seconds or more apart**. A later run proved that sampling interval cannot distinguish "never wakes" from "wakes every 60–90 seconds". Re-establish both claims, or correct them, before anyone builds a fix on them.

## Context

- The 50th `/qa-find-bugs` run (2026-08-27) ran the same protocol on a free **web** service and read its `service_hibernated`/`service_woken` event feed. In ~6 minutes with **zero** HTTP requests to the service URL, it recorded **5 hibernations and 4 wakes**:

  ```
  service_hibernated@16:26:02
  suspender_removed@16:26:19    <- a resumeService call
  service_woken@16:26:32
  service_hibernated@16:27:32
  service_woken@16:27:45        <- no resume; self-driven
  service_hibernated@16:28:45
  service_woken@16:29:15
  service_hibernated@16:30:02
  service_woken@16:31:32
  service_hibernated@16:32:15
  ```

  The wake 13 seconds after that `resumeService` looked like Resume working — until the cycle continued without any further calls. So an apparent Resume effect on this surface is **not** evidence, in either direction.

- Applied to this milestone: the private-service samples were at `16:05:04`, `16:07:03`, `16:08:14` and `16:08:57`. If the private service flaps on a similar period, every one of those could have landed on a down-swing, and both claims would be artefacts of the sampling rate rather than of the type.
- What is **not** in doubt and does not need re-establishing: the private service **does** auto-hibernate (`phase: "Hibernated"`, `instances: 0`, observed), the **worker does not** (8 samples over 4m48s, all `Running`), and `app_controller.go:1710`'s `worker :=` predicate excludes only the worker type while its stated reason is about routing. The root-cause analysis stands on the code; only the two behavioural consequences need better evidence.

## Steps

1. Re-run the private-service probe with the **event feed** as the instrument, not polling: `GET /v1/services/{id}/events` and count `service_hibernated` vs `service_woken` over at least 10 minutes. Events are durable and immune to sample timing, which is exactly why the web run caught what polling missed.
2. If the private service records **zero** `service_woken` events while the web service records several under identical conditions, this milestone's premise is confirmed and sharpened — that contrast is a far stronger artifact than the original polling.
3. If it records wakes too, correct the milestone: the defect is then the flapping (`w6`'s separate filing), not a private-service-specific missing wake path, and `t001`'s decision changes shape.
4. Re-test `resumeService` against the event feed rather than a follow-up poll: look for a `service_woken` **caused by** the resume, distinguishable from the ambient cycle by its timing relative to `suspender_removed`.
5. Record the outcome here and amend `../README.md`'s Source section if either claim moves.

## Result (2026-08-27, 51st `/qa-find-bugs` run) — both claims CONFIRMED

Ran the two types **simultaneously**, in one window, so cluster conditions could not confound the contrast. Both free, both Go, both from the same repo, both armed at `16:55:05Z` with `setIdleTimeout(idleTTLSeconds: 60)`, and **neither service's URL was requested at any point** — every probe went to `api.bex.co`. Read at `17:06:01Z`, from `GET /v1/services/{id}/events`:

```
qa-20260827-fp   private_service   srv-da86mgfm2e9c73ft5qgg   final phase: Hibernated
  service_hibernated@16:56:15
  (service_woken: 0)

qa-20260827-fw   web_service       srv-da86mggueu1c7395ist0   final phase: Running
  service_hibernated@16:57:32   service_woken@16:58:15
  service_hibernated@16:59:02   service_woken@17:00:32
  service_hibernated@17:01:15   service_woken@17:02:15
  service_hibernated@17:03:15   service_woken@17:06:02
  (4 hibernations, 4 wakes)
```

**One hibernation and zero wakes for the private service across eleven minutes, against four and four for the web service under identical conditions.** So the original claim — an auto-hibernated private service does not come back on its own — holds, and now rests on the instrument that is immune to sample timing rather than on 90-second polling. The milestone's premise stands unchanged; no correction to `../README.md` was needed.

`resumeService` was deliberately **not** re-tested here. The 50th run showed a resume followed 13 seconds later by a `service_woken` that turned out to be one beat of the web service's ambient cycle, so on a flapping service the mutation cannot be isolated by timing. On the private service there is now no ambient cycle to confuse it — which makes a clean re-test possible, but it is `t003`'s to run alongside its fix rather than this task's.

## The mechanism this hands to `w6/m120/t001`

The contrast is not just evidence — it points at a cause, and the code says why the two types should differ:

- `holdHibernateForRouting` (`app_controller.go:1922-1934`) is the **only** path that puts a parked App's replica count back up: when an App is due to hibernate but its Ingress does not yet name the activator, it returns `clampReplicas(effectiveReplicas(app))` — 1 — with `hold=true`, and that value is what `CreateOrUpdate` writes to the Deployment at `:1751`. `parkKubernetes` then requeues after `hibernateRoutingGrace` (10s, `:1942`) **without** parking. This is `w6/m94`'s deliberate grace so a live endpoint never disappears before Traefik has ingested the activator route.
- `ingressRoutesToActivator` (`:1944-1956`) states the asymmetry outright: _"An App with no Ingress (private service, no resolvable host) has no public route to protect and answers **true**, so it hibernates without the extra pass."_

So a web service passes through the hold every time it parks, and a private service never does. That predicts exactly the measured contrast, and makes the hold path the first thing `t001` should open — specifically **whether it can re-enter after a successful park**, since one grace pass explains one Running→Hibernated transition but not four cycles.

**Still not observed:** the Ingress object itself across a cycle. This task had no cluster vantage point, so "the hold re-enters because the Ingress backend flaps" remains a hypothesis with a strong prediction behind it, not a finding. `w6/m120/t001` owns confirming it by watching `ingressRoutesToActivator`'s input directly.
