## Objective

Make the Postgres connection-info panel's "Internal connection string" reference the same canonical host as the "psql command" shown right next to it on the same panel — today they disagree.

## Context

- Live-reproduced 2026-08-25 (Free-plan Postgres `qa-20260825-pg`, `dpg-da6isn5inggs73dhbf20`): "Reveal connection info" showed
  - Internal connection string host: `dpg-da6isn5inggs73dhbf20-rw.tea-d98210cbbpdc73dcrkvg` (2-label, no `.svc`)
  - psql command host: `dpg-da6isn5inggs73dhbf20-rw.tea-d98210cbbpdc73dcrkvg.svc` (3-label, `.svc`-qualified)
  - Same database, same panel, two different host forms.
- Root cause: `lego/backend/internal/postgres/service.go:647` (`PostgresConnectionInfo`) sets `internal := string(sec.Data["uri"])` — CNPG's raw generated Secret, verbatim, un-normalized. `PSQLCommand` two lines below (`:655-656`) independently builds the `.svc`-qualified form from `d.Name`/`d.Namespace`. The operator's own `Status.Host` is set `.svc`-qualified at `lego/operator/internal/controller/database_controller.go:843` — that's the canonical value neither field is using for `internal`.
- Key Value has the equivalent surface (`lego/backend/internal/keyvalue/service.go:795-821`) and does **not** have this bug: both its connection-string fields derive from the single `kv.Status.Host` source (operator: `lego/operator/internal/controller/keyvalue_controller.go:526`). Use that as the reference pattern — one source of truth, not two independently-built strings.
- Two other readers of the raw `sec.Data["uri"]` exist — `query.go:170` and `insights.go:181` — but only for internal dial-out (SQL console execution), never displayed to a user. They work today via k8s DNS search-domain resolution of the 2-label form. **Do not change them** as part of this fix; they're a different concern (a working internal dial path, not a user-facing claim of canonicity).
- Existing test `lego/backend/internal/postgres/service_test.go` (~line 495) currently asserts the inconsistent 2-label form as the expected `InternalConnectionString` — it encodes the bug and must be updated, not preserved.
- Dedupe: this descends from `w7/m77/t005` (done) — that task's sibling `t003` reasoned about exactly this class of risk for `PSQLCommand` but never carried it to `InternalConnectionString`; `t008`'s Render-parity sweep confirmed REST/GraphQL/MCP agree with each other (they do) but never checked whether the two connection-string fields on the same response agree with each other.

## Steps

1. Change `PostgresConnectionInfo` (`service.go:647`) to build `InternalConnectionString` from `d.Status.Host` (the operator's canonical `.svc`-qualified host), matching how `PSQLCommand` and Key Value's equivalent already do it — not from `sec.Data["uri"]`.
2. Confirm the username/password/dbname portions of the connection string are unaffected — only the host component changes.
3. Update `service_test.go` (~line 495) to assert the `.svc`-qualified host.
4. Leave `query.go:170` and `insights.go:181` untouched.
