## Objective

Stand up kpack (the k8s-native Cloud Native Buildpacks controller) as a new day-1 GitOps dependency, with a `ClusterBuilder`/`ClusterStack` referencing `BEX_CNB_BUILDER`.

## Context

- `deploy/gitops/` is what Argo CD reconciles into the cluster (zot registry, opensandbox controller, CAPI, autoscaler, bex itself).
- `BEX_CNB_BUILDER` (default `paketobuildpacks/builder-jammy-base`) is already read at manager startup (`lego/operator/cmd/manager/main.go:225`) but nothing consumes it yet.
- kpack needs cluster-wide CRDs (`Image`, `Build`, `ClusterBuilder`, `ClusterStack`, `ClusterStore`) and its own controller Deployment.

## Steps

1. Add kpack's install manifests (CRDs + controller) under `deploy/gitops/`, following the existing pattern for other GitOps-managed components (zot, cert-manager, etc.).
2. Define a `ClusterBuilder` pointing at the image named by `BEX_CNB_BUILDER`.
3. Wire registry push credentials (reuse the existing `BEX_REGISTRY_PUSH_SECRET` pattern documented in root `CLAUDE.md`) so kpack can push built images to the same Zot registry as BuildKit builds.

## Files

- `deploy/gitops/` (new kpack manifests)

## Acceptance criteria

- [ ] kpack controller reconciles a test `ClusterBuilder` successfully in the local mock cluster.
- [ ] kpack can push to the same Zot registry BuildKit already uses.
