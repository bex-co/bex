# 064 — A blueprint apply creates env groups and reports that it did not; GraphQL's sync result also drops key values

Why: the planner counts an env group as a first-class action and the applier creates it, but every apply result omits it — so a CLI, CI job or agent that reads the response to learn what it just built is told nothing was built.

Filed 2026-08-27, 48th `/qa-find-bugs` run, journey 13 (Blueprints).

## Live repro

Manifest (one env group, two variables):

```yaml
envVarGroups:
  - name: qa-20260827-bpgrp
    envVars:
      - key: FOO
        value: bar
      - key: BAZ
        value: qux
```

**The plan says one action.** `POST /v1/blueprints/validate`, `multipart/form-data` with `ownerId` + `file` (Render's shape):

```json
{"valid":true,
 "plan":{"mode":"current_state","envGroups":["qa-20260827-bpgrp"],"totalActions":1,
         "actions":[{"operation":"create","kind":"env_var_group",
                     "name":"qa-20260827-bpgrp","sourcePath":"#/envVarGroups/0"}]},
 "estimatedPricing":{"totalUsd":"0.00","lines":[],"variable":[]}}
```

**The apply says nothing happened.** `POST /v1/blueprints/deploy` with the same manifest:

```
200 {"services":null,"databases":null,"keyValues":null}
```

**It did happen.** `GET /v1/env-groups?ownerId=…` immediately after:

```json
[{"envGroup":{"id":"evg-da85e7oueu1c7395iri0","name":"qa-20260827-bpgrp", …}}]
```

Both keys present on the detail read. Group deleted at end of run; the list is empty again.

## Root cause

`lego/backend/internal/apps/deploy.go:168-172` — `StackResult` has exactly three fields:

```go
type StackResult struct {
	Services  []AppView           `json:"services"`
	Databases []StackDatabaseView `json:"databases"`
	KeyValues []StackKeyValueView `json:"keyValues"`
}
```

There is no env-group field, so there is nowhere for the applier to record one. And it doesn't try: `applyStackEnvGroups` (`deploy.go:772-786`) returns only `error` and never receives the result —

```go
func (s *Service) applyStackEnvGroups(ctx context.Context, envGroups []parsedEnvGroup, assignments map[string]core.EnvironmentAssignment) error
```

**The control is the function immediately after it.** `applyStackDatastores` (`deploy.go:795`) takes `res *StackResult`, and its doc comment states the contract this one is missing: _"upserts the stack's databases and key values, **appending each applied view onto res** and recording its name → ID/CR-name…"_. Same file, same apply pass, one signature apart.

This is not "env groups aren't really part of blueprints" — the planner treats them as a first-class action kind (`"kind":"env_var_group"`, counted in `totalActions`), and `w1/m35` (field completeness: `envVarGroups`/`fromGroup`/`sync:false`/`fromService`) and `w2/m40` (environment-scoped groups) both shipped to make them one. Those milestones extended the input and the plan; the result was never extended to match.

## The three surfaces, and a second gap on one of them

| surface | shape | services | databases | keyValues | envGroups |
| --- | --- | --- | --- | --- | --- |
| REST `POST /v1/blueprints/deploy` | `StackResult` (`deploy.go:168-172`) | ✅ | ✅ | ✅ | **✖** |
| MCP `deploy` | `toRenderStack` (`mcp.go:329-331`), built from `StackResult` | ✅ | ✅ | ✅ | **✖** |
| GraphQL `syncBlueprint` | `syncBlueprintResultGQLType` (`graphql.go:927-941`) | ✅ | ✅ (names only) | **✖** | **✖** |

So all three drop env groups, and GraphQL additionally drops **key values**, which REST and MCP both report — a REST/GraphQL divergence on the same result object, independent of the env-group gap.

## Fix

Name the target behavior: **an apply result lists every resource kind the plan can act on.** The planner's action vocabulary is the contract — if `env_var_group` is a countable action, it is a reportable outcome.

- Add the env-group field to `StackResult` and give `applyStackEnvGroups` the `res *StackResult` parameter its sibling already takes, appending an id+name view (`StackDatabaseView`/`StackKeyValueView` are the shape precedent).
- Add `keyValues` and the new env-group field to `syncBlueprintResultGQLType`.
- MCP inherits from `StackResult` via `toRenderStack`, so it follows once the struct changes — confirm rather than assume.

**Adjacent, deliberately not folded in:** the deploy response returns `null` rather than `[]` for the kinds the manifest did not declare. That is the same shape `w6/m109` (open) filed for Postgres/KeyValue `ipAllowList`/`readReplicas`, but on a different struct and a different Render schema question, so it is its own claim — worth checking while here, not worth conflating.

## Estimate

~1h: one struct field plus one signature change, two GraphQL fields, and tests asserting a manifest of each kind reports that kind back. Sized as a note rather than a milestone because it is one mechanical change behind one decision — but it **is** a wire-shape change on three surfaces, so if the parity question below turns out contested it should be promoted.

## Also checked this run and NOT bugs — recorded so the next hunt does not re-investigate

- **`POST /v1/blueprints/validate` rejecting JSON** with `400 request body does not match the Render API schema` is correct, and my JSON body was my own bad input. Render's spec (`lego/backend/internal/api/openapi/render-public-api-1.json`, `/blueprints/validate`) accepts **only** `multipart/form-data` with `required: ["ownerId","file"]`, and the OpenAPI middleware enforces exactly that. bex's handler also has a JSON branch (`apps/rest.go:1344-1351`), reachable only when the router is mounted without the composition root's middleware — which its own comment at `:1354-1356` anticipates for "feature-level tests and embedders". The multipart form returns `200` with the full plan.
- **`ipAllowList` being required on a blueprint `type: keyvalue`** (`at '/services/0': missing property 'ipAllowList'`) is Render's own rule, not a bex addition: the shipped schema is `$id: https://render.com/schema/render.yaml.json` and its keyvalue entry carries `"required": ["type","name","ipAllowList"]`.
- **`keyValue:` / `redis:` as top-level manifest keys** are correctly rejected (`additional properties 'keyValue' not allowed`). The valid top-level keys are `services`, `databases`, `envVarGroups`, `previews`; a key value is `services: - type: keyvalue|redis`.
- **GraphQL `validateBlueprint` gives precise per-path errors** (`at '/services/0/type': value must be one of 'keyvalue', 'redis'`) where the REST validator gives a generic body-level message — different layers, both behaving as designed.
