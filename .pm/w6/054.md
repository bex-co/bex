# 054 — A service's Events feed never records a project/environment reassignment, though it records display-name changes and the audit log records the move

Why: the Events tab is the surface a user opens to answer "what changed on this service", and moving a service between projects/environments — one of the few changes that alters where the resource lives — leaves no trace there at all.

## What's wrong

Assigned `srv-da7o6ovvqdcc73bpn9hg` to a fresh environment via **Manage resources → Save** at `2026-08-27T02:55:04Z` (23rd `/qa-find-bugs` run). The service's Events tab and the REST events endpoint both show nothing for it.

REST, with an explicit window wide enough to include both the move and the service's whole history:

```
GET /v1/services/srv-da7o6ovvqdcc73bpn9hg/events?limit=50&startTime=<now-24h>
=> 14 events, newest 2026-08-27T00:33:15Z, types:
   deploy_ended · build_ended · build_started · deploy_started · service_environment_changed
   deploy_ended · build_ended · build_started · deploy_started · display_name_changed
   deploy_ended · build_ended · build_started · deploy_started
```

Nothing at `02:55`. Re-queried 8 seconds later and again at `02:57` — still 14, still nothing new. The dashboard Events tab agrees ("Activity 14 … You've reached the beginning of this service's history").

**The move was audited, just not evented.** The workspace audit log has it:

```
GET /v1/owners/tea-d98210cbbpdc73dcrkvg/audit-logs?startTime=<now-1h>
=> { "event": "environments.SetServices", "timestamp": "2026-08-27T02:55:04Z",
     "metadata": { "relation": "can_create",
                   "service": "tea-d98210cbbpdc73dcrkvg-qa-20260826-webhook-svc" } }
```

So the information exists; the service-scoped feed simply has no event type for it. And the feed is not restricted to deploys — it already carries `display_name_changed` (a rename) and `service_environment_changed`, so service-metadata changes are in scope for it.

## Naming trap for whoever picks this up

`service_environment_changed` sounds like this bug but is **not** it: per `.pm/w1/done/m81/README.md` t003 that event fires on an **environment-variable / config** change, a documented deliberate divergence (an env edit rolls the service and records an Event, opening no `dep-…` row). bex overloads "environment" for both env vars and project sub-groupings; a new event type here needs a name that does not collide with it.

## Not a duplicate of `w6/036`

`036` covers the **Move to project** flow orphaning a resource when the second of its two sequential mutations fails. This is the success path recording nothing. Different failure, different surface — though both live in the same move machinery and a fixer may want to read them together.

## Fix sketch

Add a service event for project/environment membership changes, emitted from wherever `environments.SetServices` / `setProjectServices` land the change, with the from/to project and environment in its details. Check `lego/backend/internal/events/vocabulary_test.go`'s guard before inventing a type name, and confirm whether render.com emits one for the equivalent move before choosing the shape — parity first, invention second.

## Repro

1. Open any service's Events tab and note the newest event.
2. Assign that service to a different project or environment (Manage resources, or the Actions → Move to project menu).
3. Reload the Events tab, and query `GET /v1/services/<id>/events?startTime=<now-1h>` — neither shows the move. Query `GET /v1/owners/<ws>/audit-logs?startTime=<now-1h>` and the `environments.SetServices` row is there.
