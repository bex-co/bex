# Pull a disk-bearing service's new image onto its node before Recreate stops the old instance

Why: under `Recreate`, a disk service is down for its whole image pull. For an image whose changed layers take many seconds to pull, that pull dominates the "few seconds" Render documents.

- **Source:** w6/m547 t001, 2026-11-21. Production pulled a new 3 MB whoami tag in 2.0–2.2 s. A cached one still took 0.6–0.7 s, because `imagePullPolicy: Always` re-checks the registry. A pre-pull would therefore save only about 1.5 s for m547's fixture, so m547 closed its t004 as not needed. In the same hour, production pulled `nginx` images of 26–64 MB in 3.4–3.7 s. Tenant-built images on the nodes have a median size of 967 MB (largest 2.6 GB), although a code deploy pulls only their changed layers.
- **Design (m547 t004's):** before the Deployment's template changes, run a short-lived pre-pull pod on the node the volume is on (`diskNode`, `lego/operator/internal/controller/disk.go`). It uses the same image and the same pull secrets, and it is bounded in time. Change the template once it completes or its bound passes, and never block a deploy on it.
- **Open questions to settle in the design:**
  - The tenant namespace's ResourceQuota may have no room for a second pod while the app runs.
  - Admission must treat the pre-pull pod like the app's own pod (`execution.LabelVerifyImage`).
  - Some images carry no binary that exits at once. A container that fails to start has still pulled its image.
- **Measure first:** pull times of real code deploys of built (`zot.bex-registry`) images, from their `Pulled` events. If they are tenths of a second, close this note as not needed.
- **Done when:** a disk service's code deploy of an image with at least 100 MB of new layers spends no pull time between SIGTERM and the new instance starting, measured as in m547 t001.
