## Objective

When a disk-bearing App's claim reaches `NodeResizePending` (or carries `FileSystemResizePending`), the operator patches an annotation onto the App's running pod once for that size, so the kubelet syncs the pod and expands the mounted volume within a second. The App controller also reconciles on the claim's status changes, so `DiskReady` returns as soon as the capacity reaches the request.

## Context

- w6/157's fourth grow: `kubectl annotate pod … w6-157/nudge=<ts>` at `NodeResizePending`, filesystem grown 0.35 s later. Any pod update makes the kubelet sync it (`HandlePodUpdates` → `syncPod` → `WaitForAttachAndMount` reprocesses the pod's volumes).
- `growDiskPVC` / `expandDiskPVC` in `lego/operator/internal/controller/disk.go`; `diskPVCName`; RBAC `pods: get;list;watch;patch` already granted (`app_controller.go:566`).
- `SetupWithManager` (`app_controller.go:8366`) has no claim watch. The claim is named `disk-<app>`; map it to its App.
- Comments that say the last step waits for a restart: `disk.go:403-407`, `lego/types/v1alpha1/app_types.go:213-216`.

## Steps

1. Watch the disk claim, filtered to status changes (`allocatedResourceStatuses`, conditions, capacity), and enqueue its App.
2. In `growDiskPVC`, when the claim waits for the node, patch an annotation such as `app.bex.co/disk-resize-requested: "<GB>"` onto each running pod of the App whose value differs. Patch the pod, never the Deployment template, so nothing rolls.
3. Rewrite the `DiskResizePending` message to say the filesystem is growing online, and keep a restart in the wording only for a node that reported a failed expansion. Fix the two comments.
4. `make test` and `make lint` from `lego/operator/`.

## Acceptance criteria

- [x] An envtest claim set to `NodeResizePending` gets its App's running pod annotated once with the requested size, and a second reconcile does not patch again.
- [x] A claim status change alone (capacity reaching the request) flips `DiskReady` True without an App change.
- [x] The Deployment's pod template is unchanged by a grow.

## Record (2026-11-21)

Done, with one step the task did not name: the `bex-operator-pod-labels` admission policy let the operator change no pod annotation, so on production the stamp would have been refused, as w3/m486's purge stamp once was.

- **Claim watch.** `SetupWithManager` owns the disk claim through `diskClaimStatusChanged` (`disk.go`): an update passes only when the claim's status changed (capacity, allocated size, `allocatedResourceStatuses`, conditions). The PVC informer was already running for the Key Value controller.
- **Nudge.** `growDiskPVC` calls `nudgeDiskPods` while the claim waits for the node (`allocatedResourceStatuses.storage: NodeResizePending`, or the older `FileSystemResizePending` condition). It stamps `app.bex.co/disk-resize-requested: <GB>` on each running, ReplicaSet-owned, non-terminating pod of the App that mounts the claim, only when the value differs. The value is the claim's `status.allocatedResources` (the request only when that is absent), so a grow asked for while the node still owes the previous one is not marked as handed over early. It patches the pod, never the template, and a failed patch is logged without failing the pass: the periodic sync still finishes the grow.
- **Admission.** `deploy/gitops/base/operator-pod-label-admission.yaml` admits that one annotation, set or changed, on a pod with a claim-backed volume named `disk`. Removing it, any other annotation and every spec rule stay denied.
- **Message.** `DiskResizePending` reads "growing the disk online to <N>GB; the filesystem reports <M>GB so far". Only a node that reported `NodeResizeError` (condition) or `NodeResizeInfeasible` gets "the node could not grow the filesystem online past <M>GB; it reaches <N>GB on the next restart". The comments in `disk.go` and on `ConditionDiskReady` (`lego/types/v1alpha1/app_types.go`) say the same.
- **Docs.** ADR082 § D4 records the operator side and ADR022's admission paragraph the new exception. The open-gap text in ADR018 and ADR082 stays until t003 measures production.
- Tests and the revert checks are in t006.
