## Objective

When a disk-bearing App's claim reaches `NodeResizePending` (or carries `FileSystemResizePending`), the operator patches an annotation onto the App's running pod once for that size, so the kubelet syncs the pod and expands the mounted volume within a second. The App controller also reconciles on the claim's status changes, so `DiskReady` returns as soon as the capacity reaches the request.

## Context

- w6/157's fourth grow: `kubectl annotate pod … w6-157/nudge=<ts>` at `NodeResizePending`, filesystem grown 0.35 s later. Any pod update makes the kubelet sync it (`HandlePodUpdates` → `syncPod` → `WaitForAttachAndMount` reprocesses the pod's volumes).
- `growDiskPVC` / `expandDiskPVC` in `lego/operator/internal/controller/disk.go`; `diskPVCName`; RBAC `pods: get;list;watch;patch` already granted (`app_controller.go:566`).
- `SetupWithManager` (`app_controller.go:8366`) has no claim watch. The claim is named `disk-<app>`; map it to its App.
- Comments that say the last step waits for a restart: `disk.go:403-407`, `lego/types/v1alpha1/app_types.go:213-216`.

## Steps

1. Watch the disk claim, filtered to status changes (`allocatedResourceStatuses`, conditions, capacity), and enqueue its App.
2. In `growDiskPVC`, when the claim waits for the node, patch an annotation such as `app.bex.co/disk-resize-requested: "<GB>"` onto each running pod of the App whose value differs. Patch the pod, never the Deployment template, so nothing rolls.
3. Rewrite the `DiskResizePending` message to say the filesystem is growing online, and keep a restart in the wording only for a node that reported a failed expansion. Fix the two comments.
4. `make test` and `make lint` from `lego/operator/`.
