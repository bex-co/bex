## Objective

Know where a disk service's downtime goes before changing anything.

## Context

- `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>`; `bash scripts/qa-login.sh`; fixtures in `bex-canary`.
- Phases: old pod `SIGTERM` → container exit → pod deleted → new pod scheduled (which node) → `VolumeAttachment` attached → image pulled → container started → startup probe passes → Ready → endpoint in Traefik → first 200 at the edge.

## Steps

1. Create a paid service with a 1 GB disk whose server listens at once (a small Go or Node app) in `bex-canary`.
2. Probe its public URL every 250 ms; run a code deploy that keeps the node, one that forces another node (cordon the current one), a restart and a plan change.
3. Read each phase from pod events, `VolumeAttachment` timestamps, kubelet events and the probe log; write the table here.
4. Decide which of t002–t004 the numbers need; mark the rest not needed with the reason.
