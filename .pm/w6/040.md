## The blocker: `deploy.yml` is failing on infrastructure, not on code

Every `deploy (bex via Argo)` run on recent commits is red:

| head                     | result                 |
| ------------------------ | ---------------------- |
| `91067653` (w6/m51 ship) | failure                |
| `096d0ddb`               | failure                |
| `8369fc1b`               | failure                |
| `c913fb5e`               | failure                |
| `666fe8ab`               | cancelled (superseded) |

The failing step is the **opensandbox controller image build**, and it is not a compile error:

```
#15 89.40 fatal error: fault
#15 ERROR: process "/bin/sh -c CGO_ENABLED=0 ... go build ... -o server ./cmd/controller"
          did not complete successfully: exit code: 1
```

`fatal error: fault` is a Go **runtime** crash (SIGSEGV/SIGBUS) inside the build container, not a diagnostic from the compiler about the source. The same run also logged

```
Error: Get "http://%2Fvar%2Frun%2Fdocker.sock/v1.55/containers/buildx_buildkit_builder-.../json":
       context deadline exceeded
```

Both point at the **self-hosted runner** (`/home/docker/actions-runner/...`) rather than at anything in the tree: memory pressure, a sick buildkit daemon, or failing storage on that host. Note every _test_ job on the same commits passes — `test-backend`, `test-operator`, `test-dashboard`, `test-opensandbox-controller`, `secret-scan` are all green. Only the image build on the deploy runner dies.

**First step is therefore an infrastructure check on the runner host, not a code change:** free memory/disk, buildkit/docker daemon health, and whether a `docker builder prune` + runner restart clears it. Only if a clean runner still reproduces the fault is this a toolchain/source problem worth bisecting.

## Pipeline update (2026-08-28) — three consecutive deploys, three unrelated flakes, nothing shipped

Escalating the section above: this is no longer one bad job, it is a pattern, and its practical effect is that **`main` has not shipped since `050d40e4` (2026-08-27T07:29)**.

| run | head | failing job | signature | real? |
| --- | --- | --- | --- | --- |
| (2026-08-24, original) | several | `build-and-deploy` | `fatal error: fault` in the opensandbox image build | no — runner |
| `33130207139` | `23c323f9` (w6/m110 fix) | `test-operator` | `timeout waiting for process etcd to start`, `Ran 0 of 151 Specs` | no — runner |
| `33131370255` | `344ead76` | `test-backend` | `TestSandboxAcceptsSFTPSubsystem`: `sftp exec argv = []string(nil), want [/bin/sh -c …]` | no — test race |

Each was verified locally against the same tree rather than assumed: `make test` passes the operator controller suite (`ok … 85.279s`), and `go test ./internal/sshgateway/nativessh/ -run TestSandboxAcceptsSFTPSubsystem -count=1` passes 3/3. `build-and-deploy` is `skipped` in every case, so no image is built and no milestone waiting on a live probe can advance.

Two distinct problems, worth separating before anyone "fixes the pipeline":

1. **The self-hosted runner intermittently fails to start heavy child processes** (buildkit, then etcd). Infrastructure: memory/disk headroom, docker/buildkit daemon health, a `docker builder prune` plus runner restart.
2. **`TestSandboxAcceptsSFTPSubsystem` was genuinely racy** — a `main`-blocking flake independent of the runner, and the one real in-repo bug in this table. **Fixed 2026-08-28.** `RequestSubsystem` returns as soon as the _server acknowledges_ the request, but the gateway dispatches to the executor on its own goroutine, so reading `exec.Command` straight after the ack had no happens-before edge against the write — `argv = []string(nil)` is that read landing first. The fix uses the affordance `FakeExecutor` already exposes and the package's other tests already use (`server_test.go:539,554`): a buffered `Started` channel, waited on with the same `select`/`time.After(time.Second)` idiom, before the argv assertions. Honest limit on the evidence: `-race -count=3` does **not** reproduce it on a dev machine, before or after the fix — the executor goroutine wins every time locally, so the detector never observes the interleaving. The CI failure itself is the proof the ordering can invert; the fix removes the possibility rather than relying on which goroutine happens to be faster.

Consequence for `w6/m110`: its fix is **still not live**, so `m110/t008`'s live sweep stays blocked on the deploy precondition as well as on credentials.
