# A failed disk deploy's return to the served release takes no disk hold, so its same-node swap can still detach the volume

Why: w6/m559's holder covers every Recreate swap that `applyServingDeployment` writes, but the swap back to the served release after a failed rollout is a Recreate too, and it can still pay Hetzner's detach and attach (about 25 s) on top of a failed deploy.

- **Where:** `restoreServedTemplate` (`lego/operator/internal/controller/release_config_snapshot.go`), called from `holdNewerRelease` for `actHoldVerdict` and `actHoldParked` (`release_plan.go`). It patches the Deployment's template directly with `r.Patch`, and never goes through `holdDiskThroughRollout` (`disk_holder.go`).
- **Effect:** on a disk service whose new instance failed its rollout, the served release's template replaces the failed one with no holder. The same-node gap w6/161 measured (0.3–0.6 s, one swap in ten at the 2 s node-status sync) applies to that swap.
- **Fix sketch:** run the same hold before the patch, with the restored template as the projection. The fallbacks and end rules stay as they are, and the end runs on the next serving pass.
- **Done when:** a unit test drives a failed rollout's restore on a disk App with a running instance on a schedulable node, and sees the holder created and mounted before the template is patched, then ended once the restored instance mounts the volume. ADR082 § D3's "Not covered" line is removed.
