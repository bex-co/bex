# cli-release-staleness.sh counts from the rewritten copy of an off-main release tag (#111)

Why: since the 2026-11-04 history rewrite `bex-cli/v0.4.0` points at `fb6098dd2`, which is not on main (its rewritten copy is `1a9a6c8f8`), so the Monday monitor lists 66 "unreleased" CLI commits back to a July merge-base instead of the 11 real ones, and #111 stays open with a misleading list.

## Fix

1. In `scripts/cli-release-staleness.sh`, when the newest `bex-cli/v*` tag is not an ancestor of `HEAD`, find main's equivalent commit (same patch-id, falling back to same subject + author date) and count from there; print which commit was used.
2. If no equivalent is found, report that explicitly instead of a merge-base count.
3. Add a test with a throwaway repo: tag a commit, rewrite it, assert only post-tag commits are listed.

## Not in scope

The 11 genuinely unreleased commits (`bex agent`, Render CLI v2.35.0 pin, cosign installer fixes, `bex docs`, …) need a release; that is the user's `/release cli` (v0.4.1), not this note.
