## Objective

Once t001 makes the rollout loop detect a since-deleted linked service (via `core.ErrNotFound`), remove that service's id from the group's persisted `meta.links` and persist the change, so `EnvGroupView.ServiceLinks` (REST/GraphQL/MCP) and the dashboard's "Linked Services" list stop showing a permanent dead entry.

## Context

- `meta.links []string` (`lego/backend/internal/envgroups/service.go`) is the group's own persisted link list, stored at `env-groups/{gid}/meta`, mutated only by `linkFetched` (add, `service.go:968`) and `UnlinkService` (remove, `service.go:1005`) today — nothing else ever prunes it.
- Live-confirmed this hunt: after deleting a linked service, the dashboard's env-group detail page shows it under "Linked Services" as a bare, unresolvable id (`srv-da7lkp29vh5c73aj90d0`) linking to a 404ing `/services/<id>` page, forever — because the dashboard resolves display names by cross-referencing `serviceLinks` against `services(ownerId)`, and a deleted service has no match.
- `DeleteEnvGroup`'s own detach loop (`service.go:711-716`) and `validateLinkedServiceEnvironments` (`service.go:1075+`) both already tolerate `ErrNotFound` via `detach`/`continue` — but neither of those paths ever removes the specific stale id from a **still-existing** group's `links`; they just don't error out.

## Steps

1. Decide where the prune should run: (a) opportunistically inside `patchEnvironmentAuthorized`, immediately after t001's loop identifies a stale id — remove it from `m.links` and persist via `s.touch` in the same call; and/or (b) a dedicated filter applied wherever `m.links` is read for display (`viewFromMeta`, `ListEnvGroupsFiltered`) so a group that never receives another `PatchEnvironment` call also eventually stops showing the dead entry. Prefer doing both if the cost is low — document the choice and the reasoning (a group that is never edited again but was linked to a deleted service should not show a dead link forever either).
2. Implement the prune, persisting via the existing `s.touch(ctx, gid, m)` pattern already used by `linkFetched`/`UnlinkService`.
3. Confirm the prune does not race the `PatchEnvironment` optimistic-concurrency (`expectedRevision`/CAS) machinery — read `patch.go`'s revision-handling code before touching `m.links` mid-patch.

## Files

- `lego/backend/internal/envgroups/service.go` (`meta`, `viewFromMeta`, `ListEnvGroupsFiltered`, `touch`)
- `lego/backend/internal/envgroups/patch.go` (if pruning inline with t001's loop)

## Acceptance criteria

- [ ] After a `PatchEnvironment` call that discovers a stale link, a subsequent `GetEnvGroup`/`envGroup(id)` no longer lists the deleted service in `serviceLinks`.
- [ ] The dashboard's "Linked Services" list for that group shows no dead-link entry after the prune.
- [ ] A group that is never patched again does not indefinitely show a dead-link entry either (state the mechanism that eventually resolves this — read-time filter, or note it as an accepted residual and justify why).
