# 186 — An image that runs as a non-root user cannot write to its disk, so Render's `minio` and `wordpress` templates fail their first deploy

Why: Render's templates run the Chainguard MinIO image (user `65532`) and a `www-data` WordPress image on a disk and go live there; on bex neither can create a file on its disk, and both exit.

- **Source:** w6/m644 t003 (2026-11-26), the live run of twenty `render-examples` templates ([render-examples-live.md](../../docs/render-artifacts/render-examples-live.md)).
- **Seen twice** on production pin `2bd6e1f415d3`, in `bex-canary`, with `scripts/render-examples-live.sh minio` (render-examples/minio@bf98c9604d0b): `minio-server`, an image web service running `cgr.dev/chainguard/minio` with a 10 GB disk at `/data`, ended `update_failed` about a minute in. Its app log reads `Error: unable to create (/data/.minio.sys/tmp) file access denied, drive may be faulty` and `FATAL Unable to initialize backend: file access denied`. The image's config sets `User: 65532`. The fixtures were deleted by ID (404), disk included.
- **Seen with `wordpress` too** (render-examples/wordpress@94c6a05f0f00, two runs): its Dockerfile ends `USER www-data:www-data`, and the official entrypoint's copy into the disk at `/var/www/html` fails with `tar: ./wp-includes: Cannot mkdir: Permission denied`, exit code 2. Its `mysql-wordpress` private service, which starts as root, went live. The template's PR #14 (2026-03-19) moved it to `wordpress:latest` because the pinned version "is not deploying successfully", so it was being deployed on Render then.
- **Render:** the minio template's PR #21 (2026-08-08) moved it to the Chainguard image and says the command "was tested on a Render Starter service with a 10 GB persistent disk. The service formatted the disk, passed `/minio/health/live`, and restarted successfully without reformatting the disk." Render's [disk docs](https://render.com/docs/disks) say nothing about ownership, so find out how Render makes the disk writable (the image's user owns the mount root, or the container runs as root) before choosing the fix.
- **Where:** the operator mounts the disk's PVC with no `fsGroup` and no ownership step for the service's own container (`disk_backup.go` explains why the backup Jobs run as root instead). A fresh ext4 root is owned by root, mode 755.
- **Do:** a service whose image runs as a non-root user can create files at its disk's mount path on the first deploy, as on Render, without a recursive chown of an existing disk's files on every start.
- **Acceptance:**
  - [ ] `bash scripts/render-examples-live.sh minio` and `… wordpress` print `live` on production.
  - [ ] A regression test for a non-root image with a disk, and an existing disk whose files carry other owners keeps them.
- **Estimate:** ~1h–1h30m. A Render parity task applies if the change shows in the deploy log or the disk's settings.
