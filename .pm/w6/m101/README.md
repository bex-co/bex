## Definition of done

- Renaming a service via `SetDisplayName` (REST `PATCH`, GraphQL `setDisplayName`, or the dashboard Settings page), then triggering any subscribed event (redeploy, restart, scale) causes the **next** webhook delivery's payload to carry `data.serviceName` equal to the new display label — verified by repeating this hunt's live probe: create a webhook subscribed to all events pointed at a real HTTPS sink (e.g. webhook.site), rename a test service, trigger a deploy, and inspect the delivered (signature-verified) payload.
- `go test ./lego/backend/internal/webhooks/... ./lego/backend/internal/store/...` includes a case with a renamed app (`display_name` set, differing from `name`) and asserts the dispatched/queried row's `ServiceName` equals the display label, not `apps.name`.
- `grep -c "AS service_name" lego/backend/internal/store/webhooks.go` — all matching arms resolve through the same display-label fallback (verified by re-reading the query, not just the count).
- `apps.name` itself is untouched and still returned as `AppView.Name` (the immutable id) on direct reads — this fix only changes what the **webhook feed** reports, not the resource's identity contract.

## Source + Goal linkage

- **Source:** live QA hunt of `dashboard.bex.co`, 2026-08-25/26 (10th hourly run), workspace "bex" (`tea-d98210cbbpdc73dcrkvg`). Reproduced against the real production service `eden-dash-v3` (`srv-d9ndt8hmcglc739fkp50`):
  - GraphQL probe (`page.evaluate` + `fetch(..., {credentials:'include'})` against `https://api.bex.co/graphql`, query `service(id:"srv-d9ndt8hmcglc739fkp50"){id name displayName type}`) returned `{"name":"block-eden-mono","displayName":"eden-dash-v3","type":"web_service"}` — the dashboard, breadcrumb, and page title all show `eden-dash-v3`.
  - A QA-created webhook (`whk-da78c6hgoibs73ah08u0`, deleted after the hunt) subscribed to all events and pointed at a webhook.site sink captured a live `commit_ignored` delivery with body `{"type":"commit_ignored","timestamp":"2026-08-26T06:24:05Z","data":{"id":"evt-o2hqo0s08ih9jc7mmhl3","serviceId":"srv-d9ndt8hmcglc739fkp50","serviceName":"block-eden-mono"}}` — the **pre-rename** name, wrong on the wire.
  - The webhook signature itself was independently verified spec-correct (Standard Webhooks HMAC-SHA256 over `{webhook-id}.{webhook-timestamp}.{body}`, secret `whsec_...` base64-decoded) — computed signature matched the delivered `webhook-signature: v1,pF1u90ymPjXW6MwJMWMS61Jo6KXvmhoDEQrqwl82Juc=` exactly, so signature verification is confirmed correct and NOT part of this bug.
  - Root cause: `lego/backend/internal/apps/service.go:3588-3598` (`SetDisplayName` — a direct k8s CR patch only; its own comment states "displayName is not owned by the control-plane row projector"). `lego/backend/internal/store/webhooks.go:700-808` (`webhookEventsQuery`): 4 of its 5 `UNION ALL` arms (deploy-started ~line 707, deploy-ended ~line 726, app-scoped audit ~line 745, `service_event_facts` ~line 790) select `a.name AS service_name` straight from the `apps` table, joined live at dispatch time — so the query itself isn't stale-caching, the underlying **column** is: an exhaustive grep of `lego/backend/internal/store/*.go` for `UPDATE apps SET` found zero statements touching `name`, and no `display_name` column exists in the schema at all. The drift is permanent and structural, not a caching lag.
- **Goal linkage:** [docs/ADR006-bex-api.md](../../docs/ADR006-bex-api.md) (webhooks contract) and the w8/m8 `displayName` feature's own stated goal ("a service can be renamed for humans ... reflected on reads across all three surfaces"). w8/m8's DoD proved only direct REST/GraphQL/MCP reads (`service.displayName`); the separately-instrumented outbound webhooks feature (w3/m11, built independently) was never exercised against a renamed service until this hunt.
- **Expected outcome:** any App-CR-backed resource (web service, private service, background worker, cron job, static site) that gets renamed keeps a correct `serviceName` in every subsequent webhook delivery, matching what the dashboard/REST/GraphQL already show.
- **Why now:** external integrations (Slack bridges, PagerDuty, custom on-call automations) key off `serviceName` to identify which service an alert is about; `eden-dash-v3` is 24 days old per the dashboard and has plausibly been emitting the wrong (pre-rename) name in every deploy/build/commit-ignored webhook the whole time — the kind of silent-wrong-data bug that gets worse (and more confusing during an actual incident) the longer it goes unfixed.
- **Render parity:** included (t004) — Render has no separate mutable/immutable name split, so its webhook payload's `service.name` always reflects the current name; bex's divergence is a bex-specific integration gap introduced by bex's own `displayName` extension, not a pre-existing parity gap. t004 confirms the fix doesn't change the wire field's name/shape, only which underlying value populates it, and that REST/GraphQL/MCP direct reads (already correct) are unaffected.
- **Blast radius:** exactly the 4 UNION arms named above, all reading the one shared `apps` table — every App-CR-backed type (web/private/worker/cron/static) is affected identically since they share this table. The 5th arm (datastore audit for Postgres/Key Value) is unaffected: those resource types have no `displayName`/rename feature at all (confirmed: no `display_name`/`DisplayName` symbol anywhere in `lego/backend/internal/postgres/` or `lego/backend/internal/keyvalue/`), so there is nothing to drift.
- **Adjacent classes:** n/a — a wrong wire-field *value*, not an error-taxonomy (not-found/forbidden/unauthenticated) surface.
- **Unverified:** whether the per-service in-dashboard Events tab has any analogous issue — grepped `lego/backend/internal/store/events.go` and found it carries no `ServiceName` field at all (the caller already knows which service they're viewing), so it's likely not applicable, but this was not independently reproduced against a renamed service's Events tab this run.
