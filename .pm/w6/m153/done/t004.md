## Objective

Across a control-plane roll, confirm that a deploy (or app-cluster) run and a disk-snapshot-drill run fetch the kubeconfig unaided. The user authorized a deliberate roll on 2026-10-29 (see README § Decision — 2026-10-29).

## Steps

1. Preflight: `kubectl -n bex-capi get kcp bex-control-plane` shows 3/3 Ready and up to date, not paused. No `deploy.yml` run is in its deploy step. Record the CP Machine names and IPs.
2. Trigger: `kubectl -n bex-capi patch kcp bex-control-plane --type merge -p '{"spec":{"rolloutAfter":"<now RFC3339>"}}'`.
3. While Machines are being replaced, dispatch `disk-snapshot-drill.yml` and `app-cluster.yml` (or let a pending `deploy.yml` run). Dispatch them again once the roll settles (3 new Machines Ready).
4. Collect the fetch lines from each run log (attempts, retry, stale-pin message if any). Record the run ids, the old→new Machine names and IPs, and the timings in the README.
5. Abort rule: if a new Machine is not Ready within 20 min, stop and record the state. Do not hand-edit `BEX_SSH_KNOWN_HOSTS`.

## Acceptance criteria

- [x] KCP rolled: 3 new CP Machines, 3/3 Ready afterwards.
- [x] At least one fetch from a workflow listed in the DoD succeeded mid-roll or right after it, and one after it settled, all with strict host-key checking and no pin edit. Run ids recorded in the README. **Result:** mid-roll fetches passed; the post-roll fetch failed with the named stale-pin error, so DoD 1 is not met. Follow-up is t008/t009.
- [x] Any failure is recorded with its log line; a stale pin after the roll settles keeps m153 open.
