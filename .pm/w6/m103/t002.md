## Objective

Stop the SSR render path from mutating one process-wide, module-level i18next singleton per request. Give each request its own isolated language state so a concurrent request's `changeLanguage` call can never affect another request's rendered HTML.

## Context

- `dashboard/src/i18n/init.ts:17-29` creates one module-level `i18n` instance shared by every request the server process handles (`i18n.use(initReactI18next).init(...)`, no per-request `createInstance()`/`cloneInstance()` anywhere in `dashboard/src` — confirmed by grep).
- `dashboard/src/routes/__root.tsx:19-36` (`beforeLoad`, runs server-side per request) does:
  ```ts
  const language = detectLanguage();
  if (i18n.language !== language) {
    await ensureLanguage(language);
    await i18n.changeLanguage(language);
  }
  ```
  This mutates the shared singleton. Under concurrent traffic, a second request's `changeLanguage("en")` can interleave between this request's `changeLanguage("zh")` and the moment React serializes this request's HTML, so the emitted markup can reflect the wrong request's language.
- `dashboard/src/i18n/detect-language/server.ts:28-41`'s `detectLanguageOnServer()` (URL → cookie `i18nextLng` via `dashboard/src/common/hooks/use-cookie-storage-state/cookie.ts` → `Accept-Language` → default) is itself correctly request-scoped (`getCookie`/`getRequestHeader` read the current request) — the request-scoped signal exists; only the mutable i18next instance it feeds into is shared.
- `dashboard/src/common/lib/document-head/index.ts:174-211`'s `globalMetadata()` and per-route `head()` resolvers (e.g. `dashboard/src/routes/services.new.tsx:63-67`) read off the same ambient singleton for titles/meta — blast radius is every route's SSR output, not just the root shell.
- There is no custom `entry-server.tsx`/`ssr.tsx` in this app — TanStack Start's default SSR handler is used. The fix must work within that default handler (no bespoke server entry to hook into) — likely `i18next`'s own `createInstance()`/`cloneInstance()` API, threaded through request context (TanStack Start's request-scoped context / React context provider) rather than the imported default-export singleton.

## Steps

1. Research TanStack Start's request-scoped state mechanism (server functions / router context) as the seam to hold a per-request i18next instance — confirm what's already available (the codebase already threads `language` through `beforeLoad` → loader → `head()`, so a similar per-request value can carry the instance or its resolved strings).
2. Replace the shared-singleton mutation in `__root.tsx`'s `beforeLoad` with a per-request instance: either (a) `i18n.cloneInstance({ lng: language })` scoped to the request and threaded through React context so every component under it reads the request's own instance, or (b) an equivalent isolation mechanism if TanStack Start's SSR model makes `cloneInstance` awkward — document whichever is chosen and why.
3. Ensure the client-side hydration path (still one process, one browser tab, genuinely single-consumer) keeps using the existing shared client instance — this fix is about the *server* render path specifically, where multiple concurrent requests share one process.
4. Update any other code reading the ambient `i18n` singleton during SSR (`document-head/index.ts`, per-route `head()` resolvers) to read from the request-scoped instance instead, so titles/meta don't reintroduce the same race through a side door.
5. Verify locally under simulated concurrency (see t003) that two overlapping requests with different `Accept-Language`/`i18nextLng` never cross-contaminate.
