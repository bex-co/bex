## Objective

Walk every surface a saved plan reaches and compare it with render.com.

## Steps

1. REST `PATCH /v1/services/{id}` and `GET /v1/services/{id}`: which plan `serviceDetails.plan` reads after a save and before the deploy, against Render's API reference.
2. MCP `update_service` (a bex extension; Render's MCP has no update tool) and `get_service`.
3. GraphQL and the dashboard: the Compute page and the service header while a plan is saved and not deployed, and the undeployed-changes banner. Render's dashboard deploys a plan change, so a pending plan reaches the dashboard only through the API.
4. The pinned CLI's `services update`, if it takes a plan.
5. File each drift as its own w6 inbox note.

## Acceptance criteria

- [ ] Each surface's behavior is recorded here with its Render source, and every drift is filed.
