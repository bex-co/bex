## Objective

`ApplyServicePatch` (REST `PATCH /v1/services/{id}`, the pinned CLI's `services update`, MCP `update_service`) saves a plan change under `rollout.WithSaveOnly`, like every other row: no deploy row, `app.bex.co/pending-source-generation` stamped, no release generation. The dashboard's GraphQL `updateServicePlan`, which calls `SetPlan` outside that context, keeps deploying at once.

## Context

- `lego/backend/internal/apps/settings.go`: `servicePatchOp.deploys` and the plan row's `deploys: true`; `ApplyServicePatch` picks `rowCtx` from it and wraps the table in `rollout.Batch`, whose only caller it is (`lego/backend/internal/rollout/rollout.go`).
- `lego/backend/internal/apps/service.go` `SetPlan`: `resumeFromBilling(ctx, a, core.AnnotFreeHoursSuspended)` for a paid target, `Store.SetAppTier`, and `RecordPlanChanged` with `planEdgeCacheToggle`'s `edge_cache_enabled` / `edge_cache_disabled`.
- A save-only write behind a deploy not adopted yet already waits for that adoption (`rollout.AwaitAdoptionBeforeHold`, w6/163), and a settings release of an image service keeps its selected image (`keepSelectedImage`, w6/159). Neither needs a change for the plan row, but t008 covers both with a plan.
- Tests that assert today's deploy: `TestCompoundPatchWithPlanDeploysEveryHeldChange` (`compound_publication_test.go`), `TestRESTPatchServicePlan` (`apps_test.go`), the REST case of `TestAPlanChangeAfterAnImageOverrideKeepsItsImage` and `TestAPlanChangeRacedByADeployKeepsTheDeploysImage` (`plan_image_override_test.go`), the free-downgrade cases in `predeploy_test.go`, and `TestSurfaceSaveSemantics` (`config_rollout_test.go`).

## Steps

1. Drop `deploys` from `servicePatchOp` and run every row under `rollout.WithSaveOnly`. Remove `rollout.Batch` if nothing calls it any more (`make lint`'s dead-code pass will say).
2. Decide each `SetPlan` side effect under a save, from Render's documentation, and record the source in the code comment and in t004's ADR text:
   - A service the Free instance hours suspended, upgraded to a paid plan. Render: [render.com/docs/free](https://render.com/docs/free) on what lifts the suspension, and whether a saved plan does. If the instances would come back on the Free plan the hours already ran out on, resume only with the deploy that applies the paid plan.
   - `plan_changed` and the edge-cache toggle. The operator keeps serving the edge cache on the running plan's tier (`AppSpec.ServesEdgeCache` under the view), so an `edge_cache_disabled` recorded at the save would be false until the deploy. Record each event when it becomes true, or record why not.
3. Update the MCP `update_service` description (`lego/backend/internal/apps/mcp.go`), which says "A plan change is the exception and applies at once", and the `SetPlan` and `servicePatchOp` comments.
4. Update the tests listed above to assert the saved plan: no deploy row, `pending-source-generation` stamped, the spec's tier saved, and a later `TriggerDeploy` covering it.

## Done (2026-11-23)

- `servicePatchOp.deploys` is gone: `ApplyServicePatch` runs every row under `rollout.WithSaveOnly` (`lego/backend/internal/apps/settings.go`). `rollout.Batch` had no other caller, so it went with the `Stage` refile/drop plumbing that served it (`lego/backend/internal/rollout/rollout.go`, `stage.go`); `rollout.SaveOnly(ctx)` is exported for `SetPlan`.
- `SetPlan` side effects under a save, from Render's docs:
  - **Free instance hours suspension:** not lifted at the save. render.com/docs/compute-plans: "your service's compute plan does not change until the first successful deploy after you update it"; render.com/docs/free: the suspension is lifted by moving the service "to any paid compute plan". The deploy that applies the saved paid plan lifts it instead: `core.DeployLiftsFreeHoursSuspension`, accepted by `deploys.validateTrigger`, written with the release stamp (store `SetAppSuspended(false)` + CR), and the deploy action capability reads ready. A manual resume stays refused and names that deploy.
  - **`plan_changed`:** recorded at the save, from the plan saved before, as every save-only write records its change (w8/m135).
  - **Edge-cache toggle:** not recorded under a save. Deviation from this task's Context: the operator did **not** keep the cache on the running plan (`updateAppPodsInPlace` converges the cache tier before the release view), so a saved Starter plan would have started a cache on a service still running Free. The cache now runs on the plan the instances run (`App.RunsEdgeCache`, operator `edgeCaches` / `edgeCacheProfileFor`, backend purge and profile toggles), so it moves with the deploy, which records no toggle.
- MCP `update_service` description: "a plan change included … Until that deploy the service keeps running, and being billed on, the plan it runs."
- Tests: `TestCompoundPatchWithPlanHoldsEveryChange`, `TestASavedPlanAfterAnImageOverrideLeavesItServing`, `TestAPlanChangeRacedByADeployKeepsTheDeploysImage` (held behind the racer), `TestSurfaceSaveSemantics` (GraphQL plan deploys, REST/MCP plan holds), the `plan` row of `TestServicePatchHoldsEveryReleaseField`, `TestASavedUpgradeLeavesTheFreeHoursSuspension`, `TestASavedPlanAcrossFreeMovesNoEdgeCacheYet`, `TestTriggerAppliesASavedPaidPlanOverTheFreeHoursSuspension` and the capability case; each fails with its fix reverted.
