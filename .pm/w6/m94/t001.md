## Objective

Before changing reconcile ordering, confirm how reliably the race reproduces, measure roughly how wide the window is, and enumerate every code path that could hit it — so t002 fixes the real mechanism instead of a guess.

## Context

- Live-reproduced 2026-08-25 (`qa-20260825-sleep`, Free tier, `idleTTLSeconds=45`): the first `curl` immediately after `server.phase` read `Hibernated` got a raw Traefik `503 no available server` (no `Retry-After`, `content-type: text/plain`) instead of bex's documented wake contract (`docs/render-artifacts/wake-interstitial.md`: `503 {"error":"service hibernated","retryAfter":5}` for a non-HTML `Accept`, with `Retry-After: 5`). Three follow-up requests ~20s later all got the real app's `200`.
- `grep -rn "no available server" lego/ deploy/ infra/` returns zero hits — confirmed this string is Traefik's own "zero ready endpoints" message, not bex's.
- Root cause candidate: `lego/operator/internal/controller/app_controller.go`'s `reconcileKubernetes` writes the Deployment (`CreateOrUpdate` at `:1611-1626`, already carrying `replicas: 0` for an auto-hibernating App, computed by `desiredReplicas` at `:1730`) **before** `ingressBackend` (`:1661`, which swaps the Ingress backend to the App-owned activator alias via `reconcileActivatorAlias` at `:2686`) and `reconcileIngressWithMiddlewares` (`:1666`, which actually applies the new Ingress backend). These are two separate, non-atomic Kubernetes API writes that Traefik's informers pick up independently and asynchronously — a request can land after the Deployment's pods have dropped out as ready endpoints but before Traefik's dynamic config has picked up the Ingress backend swap to the (always-ready) activator alias Service, hitting the App's own now-empty Service instead.
- **Confirmed distinct from `w6/m47`** (done 2026-08-23): that was a structural, always-reproducing 404 (`bex-activator` named directly instead of via a per-App alias, so the backend Service didn't exist in the tenant namespace at all — different Traefik error, "404 page not found", never self-resolved). This is a transient race that self-resolves on retry within the advertised window — the wake mechanism itself works, but the very first request can lose a timing race and see raw infra output instead of the documented contract.
- `desiredReplicas` (`:1730`) and `ingressBackend`/`parkKubernetes` (`:1710`, `:1755`) each have exactly one call site in `reconcileKubernetes` — confirm this holds (single reconcile path for every App type that can auto-hibernate; workers are excluded per `:1729`'s comment, cron/private services need checking).

## Steps

1. Grep every caller of `ingressBackend`, `parkKubernetes`, and `reconcileActivatorAlias` to confirm the single-call-site claim above; note if maintenance-mode routing (`maintenanceEnabled`, same function) shares the same non-atomic-write shape and whether it's already been hit by the same race (check `.pm` for a maintenance-mode wake/race finding).
2. Reproduce the race at least 3 more times (fresh `qa-` services) to get a rough hit rate — this run only observed it once.
3. Decide the fix shape: (a) reorder the two writes so the Ingress backend swap to the activator lands first, so pods only start terminating after Traefik can already route through the always-ready activator; and/or (b) add an explicit wait/requeue between the Ingress update and the Deployment scale-down so the reconcile doesn't race ahead of Traefik's config propagation. State which (or both) and why — reordering alone only helps if Traefik's Ingress-watch propagation is reliably faster than pod termination + endpoint removal, which needs to be argued, not assumed.
4. Check whether the same race can occur on the **resume** path (activator scaling the Deployment back up and the Ingress backend swapping back to the App's own Service) — same non-atomic-write shape, opposite direction; note whether it's in scope for t002 or a separate follow-up.
