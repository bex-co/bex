## Objective

Add a meaningful regression test for the fix — a race condition can't be reliably reproduced by timing alone in a test, so this needs to assert the actual mechanism the fix changes (write ordering, or an explicit propagation gate), not just re-run the live repro and hope.

## Context

- The bug is a timing race between two independent Kubernetes writes (Deployment scale-to-0, Ingress backend swap) and Traefik's asynchronous config propagation — not something `envtest` (no real Traefik) can reproduce end-to-end.
- Meaningful test options: (a) if the fix reorders writes, assert the order directly (e.g. a fake/recording client that captures write sequence, or splitting the two operations into separately-testable functions and asserting call order); (b) if the fix adds a propagation wait/requeue, assert that the reconcile actually waits/requeues rather than proceeding immediately; (c) a control-case test proving the non-auto-hibernating paths (manual suspend, maintenance mode) are unaffected by whatever changed.
- Do not write a test that merely re-asserts today's already-correct end states (Deployment has 0 replicas, Ingress points at the activator) without asserting the *ordering/timing* property the fix actually changes — that would pass against the pre-fix code too and prove nothing.

## Steps

1. Write a test that fails against the pre-fix code specifically on the ordering/gating property (not just the end state).
2. Write a control-case test for manual suspend and maintenance-mode routing, proving they're unaffected.
3. Run the full operator suite (`make test` from `lego/operator/`) to confirm nothing else broke.
