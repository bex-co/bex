# 184 — A Blueprint's image service starts before the database it reads is available, so Render's `umami` template fails its first deploy

Why: Render's README for the template says to log in "when the deploy is live"; on bex the first deploy fails in 30 seconds and the user has to find out that a manual deploy fixes it.

- **Source:** w6/m644 t003 (2026-11-26), the live run of twenty `render-examples` templates ([render-examples-live.md](../../docs/render-artifacts/render-examples-live.md)).
- **Seen twice** on production pin `2bd6e1f415d3`, in `bex-canary`, with `scripts/render-examples-live.sh umami` (render-examples/umami@058efe925af0: a `ghcr.io/umami-software/umami:3` web service, a Key Value instance and a `basic-256mb` Postgres in a project). The approved sync started the web service's deploy at 04:39:31 UTC, and it ended `update_failed` at 04:40:01: `failureReason` "container exited shortly after start and its instance has stopped (last exit code 1)", and the app log reads `Raw query failed. Code: N/A. Message: Can't reach database server at <ip>:5432`. The database read `creating` until 04:41:11. Umami runs its migrations at start and exits when the database does not answer.
- **Control:** on the kept fixture, a manual deploy at 04:43:06, after the database was `available`, went live at 04:44:09; `/api/heartbeat` answered 200 and the README's first login (`admin` / `umami`) returned a token. The fixture was deleted by ID (404).
- **Render:** the template (added 2026-11-22) says "Click **Deploy to Render** … When the deploy is live, open the service URL and log in right away", so its first deploy goes live there unchanged. Render's docs do not say how a Blueprint sync orders a service after the database it references (`fromDatabase`); confirm Render's behavior before choosing the fix (wait for the database, or retry the release while it is still provisioning).
- **Not affected in the same run:** `n8n` (image, free Postgres) went live, because n8n retries its database connection. Native services build for minutes, so their database is ready first.
- **Do:** a service whose environment reads a database or Key Value the same sync creates does not fail its first deploy because that datastore is still provisioning. Say in the deploy log what it waited for, in Render's words if Render prints any.
- **Acceptance:**
  - [ ] `bash scripts/render-examples-live.sh umami` prints `umami live` on production.
  - [ ] A regression test: a sync that creates a database and an image service reading it does not start the service's release (or does not fail it) while the database is not available.
- **Estimate:** ~1h–1h30m, most of it confirming Render's order. A Render parity task applies if the deploy log or events change.
