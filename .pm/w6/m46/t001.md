## Objective

A `private_service` App — explicitly documented and UI-advertised as "Accessible only within the platform network" — is currently reachable at its `.onbex.co` platform subdomain with a real, unauthenticated, live-serving Ingress route. Find the exact write path that leaves `spec.Expose` (or `spec.Host`) true/set for a private service, and fix it so a private service can never end up publicly routable again.

## Context

- Live repro this run: created `qa-20260822-private` (type `private_service`, Node runtime, repo `bex-co/bex` root `examples/hello-node`) via the dashboard's "New Service" form (GraphQL `createService` mutation). It reached `Live`.
  ```
  $ curl -sSI --max-time 10 https://qa-20260822-private.onbex.co
  HTTP/2 200
  content-type: text/plain

  $ curl -sS --max-time 10 https://qa-20260822-private.onbex.co
  hello from bex
  ```
- Raw GraphQL confirmation (fetched from inside the authenticated dashboard page):
  ```
  query { server(id: "srv-da56phoaj4rs73a8bnrg") { id name type url renderSubdomainPolicy phase } }
  {"data":{"server":{"id":"srv-da56phoaj4rs73a8bnrg","name":"qa-20260822-private","phase":"Running","renderSubdomainPolicy":"enabled","type":"private_service","url":"https://qa-20260822-private.onbex.co"}}}
  ```
  `url` is `a.Status.URL` (`lego/backend/internal/apps/service.go:796`) — the operator's OWN status field — so the operator itself independently confirms this App is publicly routed, not just a client display artifact. After deleting the service, the same hostname's TLS handshake failed (no cert), confirming the route only existed while the service did.
- The ONE place that decides `Expose` is `specFromCreate` (`lego/backend/internal/apps/service.go:2098`), and it is already correctly type-aware:
  ```go
  Expose: svcType == appv1alpha1.TypeWebService || svcType == appv1alpha1.TypeStaticSite,
  ```
  with an explicit comment: "private has no platform host." `GraphQL createService` (`lego/backend/internal/apps/graphql.go:1090-1197`) calls `s.Create` → `s.create` → `specFromCreate` → `applyCreateToSpec` (`service.go:2426-2461`, which just copies `want.Expose` from the same correctly-computed spec) → `a.Spec = desired` → `s.materializeNewApp`. Nothing read in that chain this run mutates `Expose` a second time.
- Exhaustive check: `grep -rn "\.Expose\s*=\|Expose:" lego/backend/internal/apps/*.go lego/operator/internal/controller/*.go lego/types/v1alpha1/*.go` (excluding tests) returns exactly **two** hits — `service.go:2098` (above) and `service.go:2458` (`dst.Expose = want.Expose` inside `applyCreateToSpec`). No legacy `req.Private`-style field remains in `rest.go` or `mcp.go`. The `Expose` computation itself is over a month old (commit `84e2216`, 2026-07-12) and long merged to `main` — this is not an undeployed fix; production is not expected to be behind on this line.
- **This is unverified, not re-guessed:** the exact write that produces the observed `Expose=true` (or a directly-set `Host`) was not isolated this run. Candidates not yet read: the blueprint/`render.yaml` stack-apply path (`lego/backend/internal/apps/deploy.go`'s `applyCreate`/`parseService`, described in `Create`'s own doc comment as "an idempotent upsert by design" — used for redeploys of an existing name, not applicable to THIS create, but worth ruling out explicitly), `provisionAppIdentity`/`materializeNewApp`'s full body past what this hunt read, and any operator-side spec-mutating write between App creation and the first status read (the CRD contract says the operator should only write `.status`, but that assumption needs to be verified, not assumed, given `EffectiveHosts`'s `add(s.Host)` fires unconditionally regardless of `Expose` too — a directly-set `Host` is an equally viable culprit as a flipped `Expose`).

## Steps

1. Write a store/integration-level test that calls `Service.Create` with `Type: "private_service"` and asserts `desired.Expose == false` immediately after `specFromCreate` (should already pass — a control case) AND asserts the persisted App CR's `Spec.Expose` and `Spec.Host`/`Spec.Hosts` are still false/empty after the full `create()` call returns (this is the one likely to fail — reproduce the bug in test form before touching any fix).
2. If step 1's post-`create()` assertion fails, bisect `materializeNewApp` line by line (clone-secret provisioning, registry-pull-secret provisioning, domain-claim replacement, store-row writes) for anything that re-reads or rebuilds the spec rather than mutating the already-correct `a.Spec` in place.
3. If step 1 passes (Expose is correctly false immediately post-create), the divergence happens on a LATER write — check whether the operator's own reconcile ever patches `.spec` (it should only patch `.status`; if it doesn't, add an explicit assertion/test proving that, then look at any bex-api background job — webhook redeploy, project/environment reassignment, a "sync" endpoint — that could touch this specific App shortly after creation).
4. Fix the actual divergent write once found.
5. Live-verify end to end: create a fresh `private_service` (any runtime) via the dashboard, wait for `Live`, and confirm `curl -sSI https://<name>.onbex.co` returns a routing/TLS failure — never the app's own response.
