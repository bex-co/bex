## Objective

`t001` fixes the one incident this hunt reproduced (via the dashboard's GraphQL `createService` mutation) and `t002` adds an operator-level backstop. Before calling the exposure class of bug closed, enumerate and test every OTHER surface that can create or update a service's `Expose`/`Host`/`Hosts`/`Type` fields, so a sibling entrypoint isn't left with the same gap.

## Context

- Known create entrypoints, all converging on `Service.Create`/`specFromCreate` per this hunt's read of `t001`: REST `createService` (`lego/backend/internal/apps/rest.go:936`, via `createServiceRequest.toCreateRequest` at `rest.go:409`), GraphQL `createService` (`lego/backend/internal/apps/graphql.go:1090`), MCP `create_private_service`/`create_web_service`/`create_background_worker`/`create_cron_job`/`create_static_site` tools (`lego/backend/internal/apps/mcp.go` — `createWebServiceArgs.toCreateRequest` at `mcp.go:218` and siblings). Confirm each MCP create-tool for a private/worker/cron type actually sets `Type` correctly and routes through the same `specFromCreate`, not a hand-rolled spec.
- `render.yaml` blueprint sync: `lego/backend/internal/apps/deploy.go`'s `parseService`/`applyCreate` path — described in `Service.Create`'s own doc comment as "an idempotent upsert" used for redeploys, separate from the plain create path this hunt exercised. Confirm it also produces the correct type-aware `Expose` for a `private_service` entry in a `bex.yml`/`render.yaml`, and that a redeploy of an EXISTING private service can never flip `Expose` true via `applyCreateToSpec`'s straight pass-through (`service.go:2458`).
- Any settings-UPDATE path (not just create) that could touch `Expose`/`Host`/`Hosts` post-creation — e.g. does changing a service's plan, moving it between projects/environments, or any other settings PATCH ever re-run spec construction with a stale/wrong type assumption?
- Re-run the exhaustive `grep -rn "\.Expose\s*=\|Expose:"` sweep across `lego/backend/internal/apps/*.go` after `t001` lands its fix — the count and call sites may have changed; restate the final count here.

## Steps

1. List every create/update code path in bex-api that can set or change a service's `Type`, `Expose`, `Host`, or `Hosts` — REST, GraphQL, MCP (one entry per tool), blueprint sync, and any settings-update mutation. State the count explicitly.
2. For each, write (or confirm an existing) integration test: create a `private_service` through that surface, assert the persisted App CR never carries `Expose=true`/a public `Host`/`Hosts` entry, and (where applicable) that the live `.onbex.co` URL never serves.
3. For the blueprint sync path specifically, also test a REDEPLOY of an already-existing `private_service` via `applyCreate` — confirm a second sync never flips `Expose`.
4. Any settings-update path found to also compute `Expose` (rather than just carrying it forward) gets the same type-aware treatment as `specFromCreate`.
