# Key Value lifecycle never fires an audit event, webhook, or notification

Why: a user who wires a webhook or notification to watch their workspace gets silently zero signal for every Key Value create/delete, unlike the identical Postgres flow — a trust gap in exactly the kind of automation these integrations exist for.

`lego/backend/internal/core/audit.go:183-184`'s `KeyValueAuditEffect` enum only has two members — `KeyValuePlanChanged`, `KeyValueUpdated` — versus `DatabaseAuditEffect` (`audit.go:160-166`)'s seven: `DatabaseCreated`, `DatabaseRestarted`, `DatabaseCredentialsCreated`, `DatabaseCredentialsDeleted`, `DatabaseBackupStarted`, `DatabasePlanChanged`, `DatabaseUpdated`. There is no `KeyValueCreated` equivalent at all.

Consequently `lego/backend/internal/keyvalue/service.go:369`'s `CreateKeyValue` (and `:448`'s `DeleteKeyValue`) never call any `Record*Effect` audit function — contrast `lego/backend/internal/postgres/service.go:459`'s `CreatePostgres`, which calls `s.RecordDatabaseEffect(ctx, d, core.DatabaseCreated)`. No audit event means no downstream signal: `lego/backend/internal/webhooks/service.go` only maps verbs that exist in the audit vocabulary (`TypePostgresCreated = eventvocab.TypePostgresCreated`, no Key Value counterpart), and `lego/backend/internal/notifications/subscriptions.go:386` consumes the same `core.RecordAuditEvent` stream — so both integrations are silently blind to Key Value's most fundamental lifecycle action.

(Key Value genuinely has no restart or per-credential concept the way Postgres does — `grep -n "Restart" lego/backend/internal/keyvalue/*.go` is empty — so `Created` is the one real, actionable gap here, not the full 5-verb Postgres set.)

**Verified live** 2026-08-23 during a `/qa-find-bugs` hunt (dashboard.bex.co): created a webhook subscribed to "All events" — confirmed via the Settings tab that all 32 leaf event checkboxes were individually checked, ruling out a UI-selection bug — then created `qa-20260823-webhook-kv` (a free-tier Key Value instance) and waited for it to reach `available`. Zero deliveries arrived, confirmed three independent ways: the webhook.site receiver's inbox stayed at `0/50`, the workspace's webhook list showed "Never sent", and the webhook's own Activity tab showed "No deliveries yet". Cleaned up both the webhook and the Key Value instance afterward; workspace verified back to baseline.

**Fix:** add a `KeyValueCreated` member to `KeyValueAuditEffect` (mirroring `AuditVerbPostgresCreated = "postgres.CreatePostgres"` → `TypePostgresCreated`), wire `CreateKeyValue` to call the new `RecordKeyValueEffect(ctx, kv, KeyValueCreated)`, and add the corresponding webhook event type + UI checkbox entry so it appears in the "Events to send" picker alongside the existing Postgres category. `DeleteKeyValue` firing nothing is consistent with `DeletePostgres` also firing nothing (deletion isn't audited for either resource type today) — not part of this gap, don't scope it in.

**Blast radius:** one enum addition, one new webhook event-type mapping, one call site in `CreateKeyValue`. Low risk — additive only, no existing behavior changes.

**Dedupe:** no `.pm` hit (open or `done/`) for `KeyValueCreated`, Key Value webhook/audit coverage, or this specific gap. Not listed in `.pm/DO_NOT_DO.md`. Distinct from `w6/m47/t002` (which is about auto-hibernate events being mislabeled as user-suspend, a labeling bug on an *existing* event — this is about an event that never fires at all).

Estimate: ~30-45 min (enum member + audit verb + webhook type mapping + `CreateKeyValue` call site + a regression test asserting the audit event fires, following `webhooks/service_test.go`'s existing Postgres-created test shape).
