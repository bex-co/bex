## Objective

Treat the Kratos courier as the hard availability dependency D8 makes it: a visible resend affordance on `/auth/verification` (a stuck user's only self-service exit) and a courier-health alert (an operator's only early warning that all new signups are blocked).

## Context

- Under D8 no session exists until the emailed code round-trips — a courier/SMTP outage silently blocks 100% of signups at a code-entry screen (ADR075 D8 edge 2).
- The courier runs as a separate `kratos courier watch` StatefulSet (`deploy/gitops/base/values/kratos.values.yaml` § courier); Kratos exposes courier message state via its admin API, and the existing Prometheus stack scrapes the auth namespace.
- Resend: re-initiating the verification flow for the address is the Kratos-native mechanism (unauthenticated by design).

## Steps

1. Verification page: add a resend affordance (re-trigger the verification flow for the entered email), with sensible cooldown copy; strings through `t()`.
2. Alerting: pick the cheapest reliable signal (courier queue/error metric or a probe on undelivered courier messages) and wire a Prometheus alert rule in the GitOps alerting config; document the response ("check SMTP relay / courier pod") next to the rule.
3. Verify on `dev-6` with Mailpit stopped: resend visibly fails/queues, alert condition fires; with Mailpit up: resend delivers a fresh code.

## Files

- `dashboard/src/features/auth/pages/verification-page/index.tsx` + locales
- `deploy/gitops/` alerting rules (wherever the existing Prometheus rules live)

## Acceptance criteria

- [x] A user on `/auth/verification` can request a fresh code without leaving the page.
- [x] A courier delivery stall raises a named alert an operator can act on.

## Out of scope

- SMTP provider changes; email template work.
