## Objective

Prove, on the deployed Kratos version, that the account-recovery flow cannot leak an unverified session — recovery mints a session **outside** login's after-hooks, so D8's invariant ("no unverified identity holds a session") depends on Kratos marking the recovered address verified.

## Context

- ADR075 D8 edge 1: completing recovery proves address ownership; Kratos is expected to mark the recovering address verified, but this must be verified empirically, not assumed — if it doesn't hold, the recovery flow must be hooked too (or D3's deleted "unverified" banner assumption breaks with no in-app surface).
- Recovery is live end-to-end since w4/m7 (`kratos.values.yaml` § recovery, code-based, `/auth/forgot-password`).

## Steps

1. On `dev-6` with t003 applied: create an identity, do **not** verify it, run the full recovery flow (code via Mailpit), and inspect the identity's `verifiable_addresses[].verified` via the Kratos admin API plus the session state.
2. If verified=true (expected): record the evidence (Kratos version + admin-API output) in this task and add a lightweight guard — a note pinned to the Kratos chart bump checklist or a scripted check — so a future Kratos upgrade re-runs the probe.
3. If verified=false: add the appropriate recovery after-hook (or `require_verified_address` equivalent) in t003's config files and re-verify; update ADR075 D8 edge 1 with the finding.

## Acceptance criteria

- [x] Empirical answer recorded with evidence: an unverified identity completing recovery either ends verified (invariant holds) or the config is amended so it cannot hold a usable unverified session.
- [x] A recurring guard exists so a Kratos upgrade can't silently regress this.

## Evidence (2026-08-20, dev-6, Kratos v26.2.0 / chart 0.62.1)

**The invariant HOLDS — no config amendment needed.** Probe: registered
`d8test1@example.com` (unverified, `verifiable_addresses[0].verified=false` at
registration), ran the full browser recovery flow (code via Mailpit :53060),
completed it, then read `GET /sessions/whoami` with the recovery session's
cookie jar:

```json
{ "active": true, "email": "d8test1@example.com", "verified": true }
```

Recovery proves address ownership and Kratos marks the recovering address
verified in the same step, so the session recovery mints belongs to a
now-verified identity — "no unverified session" survives the one mint that
bypasses login's after-hooks. Probe commands (rerun on every Kratos bump):
create recovery flow `GET /self-service/recovery/browser`, submit
`{method: code, email}`, fetch the 6-digit code from Mailpit
`/api/v1/search?query=to:<email>`, submit `{method: code, code}` (expect
`browser_location_change_required` → settings), then `GET /sessions/whoami`
with the jar and assert `.identity.verifiable_addresses[0].verified == true`.
The recurring guard is the RE-PROBE note pinned to the `require_verified_address`
hook comment in `deploy/gitops/base/values/kratos.values.yaml`, which a version
bump edit cannot miss.
