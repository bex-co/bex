## Objective

A platform operator can move one existing `strict-v1` or `image-v1` service onto the new policy deliberately, with a dry run. Nothing migrates implicitly: upgrade, Blueprint resync, redeploy and gate changes all leave existing services alone.

## Context

- ADR089 requires migrating existing services "only through a deliberate operation".
- The persisted policy lives in the `apps.container_policy` column (t004) and is projected to `App.spec.containerPolicy`.
- t002 decided whether a disk switched from host UID mapping to a user namespace needs an ownership step.
- t003 fixed the operation's unit, dry run and refusal states.

## Steps

1. Implement the operation in the shape t003 recorded. Recommended: a platform-admin bex-api operation or `scripts/` wrapper keyed by one `srv-` id. It defaults to dry run, prints the before/after policy and pod-security shape, and refuses while a deploy, suspend or disk operation is in flight.
2. Apply it in three steps:
   - persist the new policy;
   - let the reconciler roll the service once, using Recreate for disk services;
   - surface the outcome as a normal deploy/event.
3. Add the ownership step only if t002 showed one is needed.
4. Prove that a second run is a no-op and that a failure leaves the old policy in place.

## Files

- `lego/backend/internal/apps/` (operation + tests), and possibly `scripts/<name>.sh`
- `lego/backend/AGENTS.md` (operation documented, if it adds a command or flag)

## Acceptance criteria

- [ ] Dry run writes nothing. The real run rolls exactly once, and a rerun is a no-op.
- [ ] Refusal states are tested, and a failed migration leaves the persisted policy unchanged.
- [ ] Blueprint resync and redeploy never change an existing service's policy (test).

## Out of scope

- Bulk or automatic migration, and any tenant-facing control (Render exposes none).
