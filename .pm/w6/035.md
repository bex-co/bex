# Events feed's `build_started` fact fires at deploy-row creation, not actual BuildKit Job dispatch

Why: a Render-trained user/agent watching the Events tab, a `build_started` webhook payload, or a metrics build event-marker sees a timestamp that's wrong by the full queue-wait duration whenever a deploy sits behind another one — silently violating w7/m66's own shipped Definition of done, item 1 ("a `build_started` event when its BuildKit build Job begins").

## What's wrong

`buildLifecycleFacts` (`lego/backend/internal/store/reconciler.go:685-713`) unconditionally stamps the `build_started` `service_event_fact` at `open.CreatedAt`:

```go
facts := []ServiceEventFact{{
    SourceKey: "deploy:" + open.ID + ":build_started",
    ...
    At:        open.CreatedAt,
    ...
}}
```

`isBuildPhase` (reconciler.go:740-742) treats `DeployCreated`, `DeployQueued`, and `DeployBuildInProgress` as the same phase for build-fact purposes, so nothing gates this fact on the deploy having actually left the queue — it fires the instant the deploy row opens, whether or not its BuildKit Job has been dispatched yet.

## Live repro

Triggered "Deploy latest commit" on a fresh service (`qa-20260823-race`, `srv-da5qvp63sljc7396l58g`, now deleted) while its first deploy was still mid-build:

- The queued second deploy's `build_started` event (via `GET /v1/services/{id}/events`) landed at `2026-08-24T02:44:40Z` — exactly its `createdAt`.
- That same deploy's own row `startedAt` — correctly gated on the BuildKit Job actually dispatching — only landed at `2026-08-24T02:46:57.944954Z`, once the first deploy was canceled and the second's build genuinely began.
- Gap: 2m17s in this repro; scales with however long a deploy sits queued.

## Consumer check (who reads this, and who doesn't)

- **Affected:** the Events/Activity tab timeline row, the `build_started` webhook event payload, and the metrics chart's build event-marker — all three read the `service_event_facts` row per w7/m66's DoD item 5.
- **Confirmed unaffected:** the Deploys list "Duration" column (`dashboard/src/features/deploys/components/deploys-list-page.tsx:85`, `durationLabel`) uses the deploy row's own `startedAt`/`finishedAt`, which are correctly gated — not this fact. Do not conflate the two when fixing.

## Fix direction

Gate the `build_started` fact's `At` (or its emission entirely) on the deploy having actually transitioned out of `DeployQueued` into `DeployBuildInProgress` — `buildLifecycleFacts` needs the row's current status to distinguish "queued, not yet dispatched" from "BuildKit Job actually running," since `isBuildPhase` currently conflates them for this purpose. Likely a small, targeted change (sub-hour); add a regression test that reproduces a queued-then-superseded-or-continued deploy and asserts `build_started`'s timestamp matches the real dispatch point, not row creation.

## Dedupe

- Introduced by `w7/m66` (done 2026-07-31) — this is a regression against that milestone's own DoD item 1, not new-ground work.
- Distinct from `w6/m46/t004` (already fixed): that was a `ReleaseGeneration` race causing a false `Canceled` status; this is an event-fact timestamp accuracy bug on a deploy that completes correctly.
- No other `.pm` item (open or `done/`) touches `buildLifecycleFacts`/`isBuildPhase`/this fact's timing.
