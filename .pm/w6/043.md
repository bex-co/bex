# Blueprint detail's Sync History flashes "No syncs yet" during its own query's loading window

Why: a fresh visit to a blueprint's detail page can show "No syncs yet." even when real sync history exists, misleading anyone checking why an auto-sync failed.

Found live, `/qa-find-bugs` hunt of `dashboard.bex.co`, 6th run of the day, 2026-08-25/26, on the real production blueprint `blp-d9nqg95cavls73fp8m10` (`discourse_docker`, status "Error", "Last synced: 4d").

- **Repro:** fresh (uncached) navigation to `https://dashboard.bex.co/blueprints/blp-d9nqg95cavls73fp8m10` and inspect the "Sync History" card immediately after the page frame paints.
- **Expected:** the card distinguishes "still loading" from "genuinely has no history" — a skeleton/pending state while the query is in flight, the real table once data arrives, "No syncs yet." only once settled with truly zero results.
- **Actual:** the card unconditionally shows "No syncs yet." whenever `syncs.length === 0`, including during the query's own in-flight window — even though the same `BlueprintSyncs` GraphQL query returns 9 real historical sync runs moments later (most recent: `state: "error"`, `completedAt: "2026-08-21T07:54:03Z"`).
- **Root cause:** `dashboard/src/routes/blueprints.$blueprintId.tsx:190` — `const { syncs } = useBlueprintSyncs(blueprintId);` discards the `loading` flag that `useBlueprintSyncs` (`dashboard/src/features/blueprints/hooks/use-blueprint-syncs.ts:20-37`) already returns. The render at `blueprints.$blueprintId.tsx:424` (`syncs.length > 0 ? <Table> : <p>{t("blueprints.syncHistoryEmpty")}</p>`) has no loading branch. Unlike the page's own `blueprint` metadata query (awaited by the route's loader/pendingComponent before the frame renders), `useBlueprintSyncs` fires its own independent `useQuery` (`fetchPolicy: "cache-and-network"`, no `skip` guard) that is not gated by the page's pending state — so on any fresh/uncached load there's a real network-latency window where the empty state paints before the true data does.
- **Fix:** thread `loading` out of `useBlueprintSyncs` into the route, and gate the Sync History card: a loading/skeleton state while `loading && syncs.length === 0`, the table once populated, "No syncs yet." reserved for the settled-and-truly-empty case. Single call site, dashboard-display-layer only — no REST/GraphQL/MCP contract change.
- **Blast radius:** exactly one importer of `useBlueprintSyncs` (grep-confirmed). Not checked whether sibling detail routes (services/databases/keyvalue) have the same "un-awaited secondary query feeding a bare `length > 0` ternary" pattern — flagged as unverified, not assumed clean.
- **Not the same as `w6/done/m50`:** m50 (done, code-complete but live-verification blocked on the `w6/040` deploy freeze) added the `errorMessage` column content to this same table; it did not touch the loading-vs-empty gap this note describes — this is a distinct, narrower defect in the same component.
- **Evidence:** raw `BlueprintSyncs` GraphQL response captured via `page.on('response')` during a fresh `page.goto` (2026-08-25 run) — 9 sync records, most recent `bsr-da4086iii7bs73drbqgg` (error, 2026-08-21T07:54:03Z); `.playwright-mcp/page-2026-08-26T02-34-26-147Z.yml:104-105` shows the same page's initial snapshot reading "No syncs yet." at that moment.
- **Estimate:** ~20-30 minutes (single-file fix + a loading-state test).
