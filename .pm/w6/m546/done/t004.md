## Objective

Prove both halves before production: Render's documented setup keeps data, and an existing Go service's old mount still lands in its source tree.

## Context

- Disks on dev-6 use the local-path StorageClass; the mount is the App's `spec.disk.mountPath`.
- A container runtime resolves a mount path through symlinks inside the rootfs, so a mount at `/opt/render/project/src/data` should land in the new directory's `data`; confirm, do not assume.

## Steps

1. dev-6: a Go fixture with a disk at `/opt/render/project/go/src/github.com/<owner>/<repo>/data` writes `data/probe` by relative path; deploy again; the file is still there.
2. dev-6: a Go fixture built on the old layout, with a disk at `/opt/render/project/src/data`, redeployed on the new layout; its file is still there and readable at both paths.
3. Add envtest or build tests for what the cluster runs cannot cover.

## Record (2026-11-21)

- **Mount through the link, measured on production's runtime (06:22Z).** Pod `w6-m546-link-mount` ran `debian:bookworm-slim`, uid 999, read-only root, in `bex-canary` on `bex-tenant-0-wldb9-59ksr`. Its volume was mounted at `/lib/m546/data`, and the image's `/lib` is a link to `usr/lib`. `/proc/self/mountinfo` showed the mount at `/usr/lib/m546/data`, and a file written through the link read back at the real path. So containerd and runc resolve a mount path's links inside the image, and a disk mounted under `/opt/render/project/src/…` lands in the Go directory once `/opt/render/project/src` is a link. The pod was deleted afterwards.
- **Old-layout fixture on production, set up before the change rolls out:** `w6-m546-go-old` (`srv-dc0jho52b0us73dobktg`), a Starter native Go web service in `bex-canary` built from `https://github.com/render-examples/go-gin-web-server` `main`, with `autoDeploy: no`.
  - Disk `w6-m546-old` (`dsk-dc0jho52b0us73dobkug`), 1 GB, at `/opt/render/project/src/data`.
