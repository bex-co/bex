## Objective

`recovery-info` reports `backups: []` for three databases that `.pm/w7/039.md` proved had completed daily backups on 2026-08-21 — and proved it by restoring one and matching row counts. Establish which of the two explanations is true before writing any fix, because one of them is also an ops incident.

## Context

- The API cannot distinguish the two cases today; that inability is what `t002` fixes. This task needs cluster access, which the hunt that filed this did not have.
- Candidate (a) — bex-api cannot read them. Sub-cases: RBAC on `postgresql.cnpg.io` `Cluster`/`Backup` for bex-api's ServiceAccount; a namespace mismatch between the `Database` CR (`d.Namespace`, used at `recovery.go:128,134`) and where the CNPG `Cluster` and `Backup` objects actually live; or the CRD being absent from that client's scheme.
- Candidate (b) — the objects are genuinely gone: CNPG retention pruned them, or the `ScheduledBackup` stopped after 2026-08-21.
- Already ruled out, live: a by-name/by-id mismatch in the lookup key. `RecoveryInfo` uses the caller-supplied identifier for both the Cluster `Get` and the `cnpg.io/cluster` label selector, but `POST /v1/postgres/beancount-forum-db/recovery-info` returns `404 app not found`, so only the `dpg-…` id ever reaches it.
- The connection string places the CNPG Cluster at `dpg-<id>-rw.tea-d98210cbbpdc73dcrkvg.svc`, so the Cluster is named for the id and lives in the tenant namespace — compare that against `d.Namespace` for the same Database.

## Steps

1. `kubectl get backups.postgresql.cnpg.io -A -l cnpg.io/cluster=dpg-d9nqg95cavls73fp8m20` and the same for the other two ids. Record the count and the newest `creationTimestamp`.
2. `kubectl get cluster.postgresql.cnpg.io dpg-d9nqg95cavls73fp8m20 -n <ns> -o jsonpath='{.status.firstRecoverabilityPoint}'` — this is the field `recovery.go:129` reads and never got.
3. Compare the `Database` CR's namespace against the CNPG `Cluster`'s namespace.
4. Check bex-api's ServiceAccount can actually list both kinds: `kubectl auth can-i list backups.postgresql.cnpg.io --as=system:serviceaccount:<ns>:<bex-api-sa> -n <tenant-ns>`, same for `get cluster`.
5. `kubectl get scheduledbackups.postgresql.cnpg.io -A` — confirm the schedule still exists and when it last ran.
6. Write the answer into this task, and if it is (b), file the ops side separately rather than folding it in.
