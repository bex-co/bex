## Objective

Render t002's new state, and stop enabling a Restore button that would provision a billable database destined to fail.

## Context

- The card today (live capture, `2026-08-27`): `Earliest restore point: No backup yet` beside `Latest restore point: August 27, 2026 at 5:54 AM`, with `Backups: No backups yet.` below and `Restore to new instance` enabled.
- `recovery-panel.tsx:95-105`: the earliest field already has `fallback={t("databases.recoveryNoBackupYet")}`; the latest has no fallback because the backend never omits it. Once t002 can omit it, the panel needs the matching fallback and a copy string for the unreadable case (`en` and `zh` together).
- **Restore is the expensive half.** `Recover` (`recovery.go:199`) gates only on `!src.Status.BackupsEnabled`. With backups enabled but unreadable it passes name validation, passes `ensureDatabaseNameAvailable`, passes `RequirePlanBilling`, and creates a new paid Database that cannot bootstrap. Not executed during the hunt — doing so would have created a paid resource on a production workspace — so confirm this reading before relying on it.
- The panel's own copy ("Restore always creates a new database — this one is never modified") reasonably encourages a user to just try it, which makes the billable dead end more likely, not less.

## Steps

1. Render the unreadable state distinctly from "no backups yet" — a user must be able to tell "you have no backups" from "we could not check".
2. Give the latest field a fallback for the omitted case.
3. Gate `Restore to new instance` on there being a substantiated recovery window; when there is not, disable it with the reason rather than hiding it (the panel's existing convention: "recovery is unavailable, not broken").
4. Add the backend refusal too, so an API caller hits it as well — a disabled button is not a gate.
5. `en` and `zh` move together.
