## Objective

Make `server`, `service`, `database`, and `keyValue` resolve an id that names nothing to GraphQL `null` with a consistent not-found error envelope, instead of the all-empty object they return today. Sweep every other single-resource verb built on the same helper for the same defect, and confirm the REST and MCP surfaces answer 404/not-found rather than an empty resource.

## Context

- Measured live on 2026-08-22 (signed-in browser fetch against `https://api.bex.co/graphql`):
  - `{ server(id:"srv-d9ndt8hmcglc739fkp5X"){ id name slug phase } }` → `{"data":{"server":{"id":"","name":"","slug":"","displayName":"","type":"","phase":"","url":"","urls":null,"image":"","replicas":0,…}}}` — **no `errors` key**.
  - `database(id:"dpg-0000000000000000000000")` → same shape, no `errors`.
  - `keyValue(id:"red-0000000000000000000000")` → zero-value object **and** `errors:[{"message":"app not found","path":["keyValue"]}]`. Three verbs, two different contracts.
  - `deploys(serviceId:"<dead>")` → `{"data":{"deploys":null},"errors":[{"message":"app not found"}]}` — the correct shape, and the reason the ghost page renders the literal string "Deploys app not found".
- `gqlutil.KeyVerb` (`lego/backend/internal/gqlutil/gqlutil.go:114-122`) is the shared `(<key>: String!) -> fn(ctx, key)` shape for "every single-resource query". It returns `fn`'s `(T, error)` straight to graphql-go; when `T` is a value struct, the zero value marshals as an object, so the field is never `null`.
- `apps.Service.Get` (`lego/backend/internal/apps/service.go:1130-1136`) returns `AppView{}, err` when `AuthorizeApp` fails — the error exists at the Go level but does not reach the response for `server`/`database`.
- Wiring: `lego/backend/internal/apps/graphql.go:916-917` (`"server"` and `"service"` → `gqlutil.IDVerb(serviceGQLType, s.Get)`).
- `core.IsNotFound`-style predicates already exist for the REST layer; reuse the project's existing not-found classification rather than string-matching `"app not found"`.
- Do not "fix" this by having resolvers swallow errors: a genuine failure (authz outage, store error) must stay an error. Only a resolved-to-nothing id becomes `null` — the same distinction `dashboard/src/common/lib/document-head`'s `loadRouteResource` and `w9/m55` depend on.

## Steps

1. Decide the shape once: for a single-resource verb, not-found ⇒ `data.<field> = null` plus one not-found `errors` entry (matching what `deploys` already does), and keep real errors as errors.
2. Change the resolver plumbing so a value-typed `T` can express "absent" — e.g. have `KeyVerb` return `nil` (not `T{}`) when `fn` reports not-found, or give the affected verbs a pointer/`(T, bool, error)` form. Prefer the change that fixes every `KeyVerb`/`IDVerb` caller at once over patching three call sites.
3. Grep every `IDVerb`/`KeyVerb` caller and list which ones return value structs; fix them all, or explicitly note the ones already returning pointers/slices.
4. Check the REST twins (`GET /v1/services/<dead>`, `/v1/postgres/<dead>`, `/v1/redis/<dead>`) actually 404 with the Render error body, and the MCP tools for the same resources report not-found rather than an empty resource.
5. Re-run the live probes from Context against dev-6 and confirm all three verbs agree.
