## Objective

`ssh.bex.co:22` accepts TCP, writes `SSH-2.0-bex`, and then never sends `SSH_MSG_KEXINIT`. Find where that stops. The milestone establishes the symptom exhaustively but **not** the cause — nothing downstream may assume one.

## Context

- Reproduce with the raw-socket probe from the milestone README (connect, read banner, send a client version line, wait for packet type 20). Controls `github.com` and `gitlab.com` return 800 bytes with type 20 under the identical probe; bex returns 0.
- Already ruled out, do not re-chase: **eligibility** (paid, free and nonexistent targets all behave identically) and **algorithm negotiation** (four forced KEX/cipher sets, all identical; the server never sends its own proposal, which it would do before any "no common algorithm" outcome).
- Candidate stop points, read from config/docs and **not measured**:
  - **PROXY protocol mismatch between the LB and the gateway.** `BEX_SSH_PROXY_PROTOCOL_TRUSTED_CIDRS` gates whether the gateway accepts a PROXY v1/v2 header asserting the client IP. If the LB stopped sending it, started sending it, or no longer matches the trusted CIDR set, the gateway's first read consumes or awaits the wrong bytes — which matches "banner written on accept, then silence". A grep of `deploy/` and `infra/` for PROXY-protocol configuration returned **nothing**, so locating where this is configured is itself part of the task.
  - Pre-auth admission caps: `BEX_SSH_MAX_PREAUTH_CONNS` (256) / `…_PER_SOURCE` (32). Unlikely for a first connection from a cold source, and the failure reproduced across separated trials, but not excluded.
  - A gateway-side error or panic after the version write.
- `scripts/ssh-verify.sh` is the existing production acceptance script for exactly this surface and has apparently never been run on a schedule — run it here.

## Steps

1. Re-run the raw-socket probe and `scripts/ssh-verify.sh` against production; record complete output.
2. Read gateway logs around a probe connection — does it log an accept, a version write, then an error?
3. Check the LB → gateway PROXY-protocol contract in **both** directions (LB sending when the gateway does not expect it; gateway requiring it when the LB does not send it), and locate where that is configured.
4. Check the pre-auth admission counters.
5. Record the located cause. **`DO_NOT_DO.md` item 12:** if the fix belongs to the LB or GitOps, it stays there — locate and record rather than moving gateway responsibility into product code.

## Outcome (2026-08-28)

Located, not merely hypothesized. `w4/m82` (`9c111369`, 2026-08-16) enabled `proxyProtocol: version: 2` on `config/ssh/ingressroutetcp.yaml` but the gateway Deployment never got the matching `BEX_SSH_PROXY_PROTOCOL_TRUSTED_CIDRS`, so `proxyproto.Wrap` is a no-op and Traefik's un-stripped PROXY v2 header enters the SSH version exchange; `readVersion` discards it as non-`SSH-` preamble and blocks to the 10 s handshake deadline, so `KEXINIT` (sent only after the version exchange) never arrives. Eligibility and algorithm-negotiation stay excluded. Fix belongs to product config (operator gateway manifest), not the LB. Reproduced live with `ProbeKEXINIT`: controls (`github.com`/`gitlab.com`) send KEXINIT, `ssh.bex.co` times out.
