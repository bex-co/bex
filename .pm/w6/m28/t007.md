## Objective

Run the standing user-surface parity gate so REST-only Render nesting does not create contradictory ownership, placement, navigation, or freshness facts elsewhere.

## Context

- Render's nested owner object is specifically a public REST wire contract; GraphQL/MCP may represent the same fact as `ownerId` without copying the nesting.
- Dashboard detail links are only valid if their target routes exist and select the same workspace/resource.
- The official CLI is the fifth compatibility surface and motivated the milestone.

## Steps

1. Compare Service/Postgres/Key Value list/get metadata with Render's documented and observed behavior.
2. Exercise REST, GraphQL, MCP, dashboard, and CLI reads for the same resources and compare semantic values.
3. Verify owner resolution under multi-workspace callers, unset configuration, legacy unlabeled objects, and deleted/renamed workspaces.
4. Check dashboard links, timestamp time zones/precision, pagination envelopes, and error behavior.
5. Fix in-scope drift and file exact follow-up PM notes for adjacent gaps.

## Acceptance criteria

- [ ] All five surfaces agree on the resource workspace and freshness semantics.
- [ ] REST wire nesting remains adapter-local while GraphQL/MCP retain compatible neutral shapes.
- [ ] Every dashboard URL resolves to the intended tenant-scoped resource page.
- [ ] Any accepted Render divergence is explicit in ADR/checklist evidence with an owner.

## Out of scope

- Adding metadata fields to a non-REST surface solely for structural symmetry when it already exposes the same fact appropriately.
