## Objective

An env var set in the New Web Service creation form is baked into the App spec (and works) but never reaches the `internal/secrets` store the Environment tab / `envVars`/`envVar` GraphQL queries read — so it is permanently invisible to the UI: no reveal, no edit, no delete, omitted from Export. Seed it into that store at creation time so it behaves like any other env var.

## Context

- Live repro: created `qa-20260822-hello-py` with `MESSAGE=qa-20260822-marker-v1` via the New Web Service form's Environment Variables section.
  - The running instance correctly serves it: `curl https://qa-20260822-hello-py.onbex.co/` → `qa-20260822-marker-v1`. Survived a full manual redeploy (rev-3 → rev-4).
  - Direct GraphQL probe: `envVars(serviceId: "srv-da54p1moogrc73fp1i60")` → `[]`. Environment tab shows "No environment variables."
  - After adding a second var `QA_PROBE` through the Environment tab's own Edit UI and saving: `envVars` then returns **only** `QA_PROBE` — `MESSAGE` never appears, even though it's still live.
- Root cause: `lego/backend/internal/apps/service.go:1607` `Service.create` → `specFromCreate` assigns `Env: req.Env` directly onto the App CR spec at `service.go:2089`, and never calls into `lego/backend/internal/secrets` (the package backing `SetEnvVar`/`SetEnvVars`/`envVars`/`envVar` — e.g. `secrets/service.go:283` `SetEnvVars`). Compare the blueprint-apply path's `EnvSeeder.SeedEnvVars` (`lego/backend/internal/apps/deploy.go:840`), which does seed the secrets store — but only for a blueprint's `sync:false`/`generateValue` vars, not for an ordinary `Service.create` call's literal `EnvVars`.
- Blast radius: `lego/backend/internal/apps/deploy.go:2449` `applyCreateWithFields` (used by blueprint stack creates via `applyBlueprintCreate`) calls the **same** `specFromCreate` with the same `Env`-onto-spec assignment. Check whether a blueprint-created service's plain (non `sync:false`, non `generateValue`) `render.yaml` env vars have the identical visibility gap, or whether the existing `SeedEnvVars` call already covers them incidentally — cover both call sites or document why only one needs the fix.
- Adjacent classes: the fix must not change behavior for vars created via `SetEnvVar`/`SetEnvVars` (already correct) or blueprint `sync:false`/`generateValue` vars (already seeded via `EnvSeeder`) — only the creation-time literal-`Env` gap should move.

## Steps

1. In `Service.create` (or `specFromCreate`'s caller), after the App is created, write `req.EnvVars`'s literal entries into the `internal/secrets` store the same way `SetEnvVars` does — reusing that seam rather than duplicating its logic.
2. Verify the same gap in `applyCreateWithFields` (blueprint stack create path) and apply the equivalent fix there, or document why it's already covered.
3. Confirm `envVars(serviceId)` / the Environment tab lists a creation-time var immediately after creation — no follow-up Edit+Save required.
4. Confirm Export, "Show secret" reveal, edit, and delete all work on a creation-time var exactly as they do on one added later.
5. Confirm the var still reaches the running container (no behavior regression for the working case) and survives a redeploy.

## Acceptance criteria

- [ ] Creating a web service with an env var in the New Web Service form makes that var appear in `envVars(serviceId)` / the Environment tab immediately after creation.
- [ ] The var can be revealed, edited, exported, and deleted through the Environment tab like any other var.
- [ ] The var still reaches the running process and survives a redeploy (no regression).
- [ ] A blueprint-created service's literal `render.yaml` env vars are checked against the same gap and either fixed or explicitly documented as already covered.
- [ ] A regression test asserts `envVars(serviceId)` includes a creation-time literal var and fails on the pre-fix code.

## Out of scope

- Changing how blueprint `sync:false`/`generateValue` seeding works — that path is already correct.
