## Objective

`workspaces.Service.ChangePlan`'s downgrade guards (member-count + role checks) currently count rows in `tenant_members` only, so a Pro→Hobby downgrade with outstanding invites succeeds silently and those invites sit un-redeemable. Make the guards count pending `tenant_invites` too and refuse the downgrade with a reason naming the invites.

## Context

- `.pm/w6/011.md` — the source note. The accept-time invariant (`store.AcceptInvitesForEmail`'s `planAllowsJoin`) is already safe — this task is the downgrade-time UX/fail-early half.
- `lego/backend/internal/workspaces/service.go` — `ChangePlan` and its guards.
- `ListInvites` already exists on `PGStore` but needs adding to the `WorkspaceStore` interface + test fakes.

## Steps

1. Add `ListInvites` to the `WorkspaceStore` interface; update fakes.
2. Extend the member-count guard to include pending invites; extend the role guard to check invited roles.
3. Refuse the downgrade with a message naming the offending invites (consistent with the other guards' error shape), e.g. "workspace has 1 member + 2 pending invites, exceeds hobby plan's limit of 1; revoke them first."

## Files

- `lego/backend/internal/workspaces/service.go`
- `lego/backend/internal/workspaces/store.go` (or wherever `WorkspaceStore` is defined) + test fakes

## Acceptance criteria

- [ ] A downgrade that would put (members + pending invites) over the target plan's cap is refused, naming the invites.
- [ ] A downgrade with no over-cap invites is unaffected.

## Out of scope

- Any change to the already-closed accept-time invariant.
