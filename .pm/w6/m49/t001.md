## Objective

Every downstream task in this milestone (t002-t006) needs one shared, reliable way to ask "did this create mutation fail because the name is already taken?" — decide that mechanism here, first, so the fixes in t002-t006 aren't rebuilt per-type and don't drift from each other.

## Context

- Today's only working example, `dashboard/src/features/services/hooks/use-create-service.ts:131-135`, detects a conflict by lower-casing the GraphQL error message and checking `.includes("already in use")`. That string is backend prose (`lego/backend/internal/apps/service.go:1674,1885`: `"name %q is already in use"`) — it works for services only because services happens to say exactly that.
- The other two backend message shapes found live this run do NOT contain "already in use": keyvalue/postgres say `"a %s named %q already exists in this workspace"` (`lego/backend/internal/keyvalue/service.go:352`, `lego/backend/internal/postgres/service.go:451`); projects say just `"conflict: project: already exists"` (routed through the generic `store.ErrConflict = errors.New("already exists")`, `lego/backend/internal/store/store.go:56`, wrapped by `core.ErrConflict = errors.New("conflict")`, `lego/backend/internal/core/errors.go:97`). Three shapes, two sentinels, zero shared substring across all three.
- The codebase already has a working precedent for exactly this problem, in the same file that today's fragile check lives next to: `dashboard/src/common/lib/graphql-error.ts`'s `hasGraphQLErrorCode`/`planLimitExtensions` key on a structured GraphQL `extensions.code` (`"PLAN_LIMIT"`) rather than message text, with the doc comment explaining why: "Keying on the code (not a substring of the message) means backend copy changes have zero effect on whether the plan-limit CTA shows." `lego/backend/internal/api/ratelimit.go:151` sets `extensions: {"code": "RATE_LIMITED"}` the same way. Neither `core.ErrConflict` nor `store.ErrConflict` currently gets an `extensions.code` anywhere — `lego/backend/internal/core/http.go`'s `WriteErr`/`IsPublicError` only attach a `code` field when the error is wrapped as a `*core.CodedError` (see `errors.go:295`), which none of the conflict call sites use.
- Find where GraphQL errors get their `extensions` populated (likely near `graphqlHandler` in `lego/backend/internal/api/server.go`, or a shared error-formatting func referenced by `IsPublicError`) to see how `RATE_LIMITED`/`PLAN_LIMIT` get attached today, and whether the same mechanism can generically stamp `extensions.code = "CONFLICT"` for any error matching `errors.Is(err, core.ErrConflict)` (which already covers both `core.ErrConflict`-wrapped and, transitively, anything that also wraps `store.ErrConflict` underneath it — check that `errors.Is` unwraps far enough, or wrap `store.ErrConflict` results in `core.ErrConflict` at each call site if it doesn't).

## Steps

1. Trace the GraphQL error-formatting path from `lego/backend/internal/api/server.go`'s `graphqlHandler()` to find where `extensions.code` gets set today (`RATE_LIMITED`, `PLAN_LIMIT`).
2. Decide: (a) generically stamp `extensions.code = "CONFLICT"` for any GraphQL error satisfying `errors.Is(err, core.ErrConflict)`, at the same central point RATE_LIMITED/PLAN_LIMIT are stamped, or (b) keep per-type message matching (services' existing pattern) and just replicate it per hook. Prefer (a) — it matches the codebase's own documented preference and eliminates the exact fragility class this milestone exists to fix — but if tracing the error-formatting path surfaces a concrete reason (a)'s reachable code doesn't fit this call shape within the estimate, fall back to (b) and record why in this task's notes.
3. If (a): implement the generic `extensions.code = "CONFLICT"` stamp; add a `hasGraphQLErrorCode(err, "CONFLICT")`-based helper (reusing the existing `hasGraphQLErrorCode` in `dashboard/src/common/lib/graphql-error.ts`) that t002-t006 all call. Also confirm/update REST's `WriteErr` (`lego/backend/internal/core/http.go`) emits an equivalent `"code": "CONFLICT"` in its JSON body for parity between the two transports (checked properly in t007, but land the REST side here so t002-t006 aren't blocked on it later).
4. If (b): extract services' `.includes("already in use")` check into one shared function in `graphql-error.ts` (e.g. `isNameConflictError`) that also recognizes keyvalue/postgres's "already exists in this workspace" and projects/environments's generic "already exists" shapes, so t002-t006 call one function instead of five near-duplicate string checks.
5. Whichever path: keep `graphQLErrorMessage(err)`'s raw text available too (services still wants "is already in use" verbatim to show to the user; keyvalue/postgres/projects need their own specific text) — the new mechanism decides *whether* it's a conflict, the existing `graphQLErrorMessage` still supplies *what to say*.
6. `cd lego/backend && go test ./...` + `dashboard/`: `yarn typecheck && yarn lint` green before handing off to t002.
