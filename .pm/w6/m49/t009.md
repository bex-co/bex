## Objective

Add meaningful tests for every behavior this milestone changed, and — just as important — regression tests proving the two already-correct control cases (`use-create-service.ts`, `use-create-workspace.ts`) still behave exactly as they did before this milestone touched their shared error-handling infrastructure.

## Context

- `dashboard/src/features/keyvalue/hooks/__tests__/use-create-key-value.test.ts`, `dashboard/src/features/databases/hooks/__tests__/use-create-database.test.ts` (or equivalent paths) — check whether test files already exist for the hooks t002-t006 touched; extend them rather than duplicating.
- `use-create-service.ts` and `use-create-workspace.ts` are the control cases this milestone must not regress — they should already have tests covering their conflict/error paths (`use-create-service.test.ts` likely covers `setNameConflict`); if they don't, add them here rather than assuming coverage that doesn't exist.
- Tests must assert real behavior and failure modes, not tautological or snapshot-everything tests (repo-wide rule, `.pm/DO_NOT_DO.md`'s "minimum bar" section implicitly, and this file's own standing-task description).

## Steps

1. For each hook fixed in t002-t006: add a test asserting that a GraphQL error matching the conflict shape (using t001's mechanism) results in the specific conflict state/message being set, and a DIFFERENT test asserting that a non-conflict error (e.g. a network failure, or the cap-limit case) still falls through to its prior generic-toast/cap-limit behavior — the fix must be additive, not a blanket replacement of all error handling.
2. Add or extend a test for `use-create-service.ts` confirming `setNameConflict(true)` still fires correctly on t001's new shared mechanism (if t001 changed how conflicts are detected under the hood, even though services' outward behavior is unchanged).
3. Add or extend a test for `use-create-workspace.ts` confirming its passthrough-`error`-state behavior is unaffected.
4. If t001 added backend changes (a new `extensions.code`, or a REST `code` field): add a Go test in the relevant `lego/backend/internal/*` package(s) asserting the code is present on a conflict response.
5. If t005/t006 found environments/api-keys/registry-credentials NOT applicable: add a short test (or a comment pointing to the completion-notes evidence) documenting why, so a future reader doesn't rediscover the same investigation.

## Files

- Test files alongside every hook touched in t001-t006.
- `lego/backend/internal/*/graphql_test.go` or equivalent, if t001 touched the backend.

## Acceptance criteria

- [ ] Every hook fixed in t002-t006 has a test for both the conflict path and at least one non-conflict error path.
- [ ] `use-create-service.ts` and `use-create-workspace.ts` have passing regression tests confirming unchanged behavior.
- [ ] `dashboard/`: `yarn test` green; `cd lego/backend && go test ./...` green.
