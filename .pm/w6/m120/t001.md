## Objective

Find why a parked App comes back with no traffic. Everything else in this milestone waits on the answer, because "stop it waking" and "stop reporting the wake" are different fixes depending on the cause.

## Context

- Reproduction is cheap and the event feed is the instrument: free `web_service`, `setIdleTimeout(60)`, never touch the URL, then read `GET /v1/services/{id}/events`. This run recorded 5 `service_hibernated` and 4 `service_woken` in six minutes.
- `desiredReplicas` returns 0 only while `shouldAutoHibernate(app)` is true (`app_controller.go:1641-1650`), which requires `time.Since(lastActiveTime(app)) >= TTL`. For the App to un-park, that predicate must be flipping — so either the annotation is advancing or something bypasses the predicate.
- `app.bex.co/last-active` is re-stamped at `:2096-2102` **only when it is zero** (`if lastActiveTime(app).IsZero()`). So a cleared/lost annotation would restart the TTL from scratch — which matches an oscillation whose period is roughly the TTL.
- Candidates, in the order worth opening:
  1. Something clearing the annotation. Check whether `hibernated()` / `parkKubernetes` rewrite `ObjectMeta` in a way that drops it, and whether any patch replaces annotations wholesale rather than merging.
  2. `holdHibernateForRouting` (`:1729`) + `parkKubernetes`'s `routingHold` branch (`:1859-1861`), which return the pre-hibernate replica count and requeue after `hibernateRoutingGrace` (10s). Confirm this is a one-shot grace and cannot re-enter.
  3. The control-plane projector. `w6/m46`'s post-mortem found `applyOwnedSpec` re-stamping a field on every resync and bumping `metadata.generation`; an annotation-based timer is exactly the state a resync could disturb. `BEX_CP_RESYNC` sets that cadence — compare it against the observed period.

## Steps

1. Reproduce and capture the event feed; note the period between `service_hibernated` and the next `service_woken`.
2. Read the App CR across a cycle and watch `metadata.annotations["app.bex.co/last-active"]` and `metadata.generation`. Whichever moves is the mechanism.
3. Compare the cycle period against the TTL and against `BEX_CP_RESYNC` — matching one of them names the driver.
4. Write the mechanism here before anyone writes a fix.

## Prior work from the 51st `/qa-find-bugs` run (2026-08-27) — the search is already narrowed

A paired probe run for `w6/m119/t009` measured both auto-sleep-eligible types **simultaneously**, same window, same TTL (`60`), same repo and plan, neither URL ever requested:

```
private_service  srv-da86mgfm2e9c73ft5qgg   service_hibernated: 1   service_woken: 0   final: Hibernated
web_service      srv-da86mggueu1c7395ist0   service_hibernated: 4   service_woken: 4   final: Running
                   hib@16:57:32 woke@16:58:15 hib@16:59:02 woke@17:00:32
                   hib@17:01:15 woke@17:02:15 hib@17:03:15 woke@17:06:02
```

**Only the web service flaps.** That is a strong discriminator, because exactly one code path differs between the two types on the park route, and it is the only path that raises a parked App's replica count:

- `holdHibernateForRouting` (`app_controller.go:1922-1934`): when an App is due to hibernate but its Ingress does not yet name the activator, it returns `clampReplicas(effectiveReplicas(app))` — **1** — with `hold=true`. That value is written to the Deployment by `CreateOrUpdate` at `:1751`, and `parkKubernetes`'s `routingHold` branch (`:1859-1861`) then requeues after `hibernateRoutingGrace` (10s, `:1942`) **without** parking. It is `w6/m94`'s deliberate grace so a live endpoint never disappears before Traefik ingests the activator route.
- `ingressRoutesToActivator` (`:1944-1956`) says why a private service skips it: _"An App with no Ingress (private service, no resolvable host) has no public route to protect and answers **true**, so it hibernates without the extra pass."_

So: every web park goes through the hold; no private park does; only the web service comes back. **Start at the hold.**

The specific question it leaves is not "does the hold run" — it must, once per park, by design — but **why it appears to run repeatedly**. One grace pass explains one `Running → Hibernated` transition; it does not explain four `Hibernated → Running → Hibernated` cycles. Either `ingressRoutesToActivator` goes false again after a successful park, or the hold's replica write survives into a pass that should have parked.

Two supporting facts already established, so they need not be re-derived:

- `last-active` is **not** being cleared and re-stamped. `runningRequeue` (`:2094-2110`) stamps it only `if lastActiveTime(app).IsZero()`, and `hibernated()` (`:2120-2135`) writes `Status` only — it never touches `ObjectMeta`. So candidate 1 in the list above is unlikely, and candidate 2 is where the evidence points.
- `idleRequeueAfter` (`:1653-1659`) floors at 5 seconds once the TTL has elapsed, so a parked App is re-reconciled every ~5s — fast enough for a re-entrant hold to produce the observed ~45–90s cycle if it engages on some fraction of passes.

**Not observed, and the reason this is a lead rather than a finding:** the Ingress object itself across a cycle. Neither run had a cluster vantage point. Watch `ingressRoutesToActivator`'s actual input — the App's Ingress backend — across a full `Hibernated → Running → Hibernated` cycle, and the answer should fall out immediately.
