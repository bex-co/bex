# Static site: a request path over ~1000 chars returns 502 "origin error" instead of 404

Why: an operator or monitoring dashboard seeing 502 spikes on a static site will chase a false "origin down" alarm for what is actually a harmless (if pathological) client request for a path that never existed.

Live-verified on production 2026-08-26 against a QA static site (`octocat/Spoon-Knife` served from `qa-20260826-static.onbex.co`, deleted after the hunt): a `GET` for a nonexistent path under ~900 chars correctly SPA-falls-back to `index.html` (200); at ~1000+ chars of combined object-key length (client path + the site's internal bucket-key prefix) the response flips to `502 Bad Gateway`, body `origin error`, `content-type: text/plain; charset=utf-8`. Binary-searched the threshold with `curl` (see transcript): 900 chars → 200, 1000+ chars → 502, stable across repeated runs.

Root cause: `lego/operator/internal/staticserver/staticserver.go:208-209` — `ServeHTTP`'s `fetch` error handling recognizes only `ErrNotFound`/`ErrObjectTooLarge`/`ErrOverloaded` as classified outcomes; anything else falls into `else if err != nil { http.Error(w, "origin error", http.StatusBadGateway) }`. The S3-compatible object store's key-length limit (standard S3 caps object keys at 1024 bytes) is exceeded by the derived key (`site.keyFor(reqPath)`, `staticserver.go:113-122`) for an overly long request path, and the resulting client/API error isn't a shape `isNotFound` (`lego/operator/internal/staticserver/s3origin.go:121-135`) recognizes — so a client-caused "this key can never exist" condition is misreported as an origin/infra failure.

Fix direction: either (a) reject or truncate a request path before deriving the object key once it would exceed the store's key-length limit, answering `404 Not Found` (nothing could ever exist there) rather than attempting the S3 call, or (b) extend `isNotFound` to recognize the S3 "key too long"/400-class client error and map it to `ErrNotFound` like every other can-never-exist case. Either way the correct status is 404, not 502 — this is a client-input condition, not an origin outage.

Not a security issue: path traversal (`../../etc/passwd`, `..%2f` encodings) and unicode/space paths were also tested and all normalize safely to the SPA fallback with no escape — only the length case misbehaves.
