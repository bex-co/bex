## Objective

Render's `projectPOSTInput` requires `environments`; bex ignores the field and creates a project with none. Decide whether to honour it or to diverge deliberately, and make the chosen answer real.

## Context

- Render's schema: `projectPOSTInput` `required: ['name','ownerId','environments']`, with `projectPOSTEnvironmentInput` `required: ['name']` and optional `ipAllowList` / `networkIsolationEnabled` / `protectedStatus`.
- bex decodes only `{name, ownerId}` (`lego/backend/internal/projects/rest.go:102-105`) and returned 201 for a body with no `environments` at all.
- **Live consequence, observed:** the created project had zero environments — `GET /v1/environments?projectId=prj-da8al3vm2e9c73ft6710` returned `[]` — until one was created by hand. Under Render's model a project always has at least one.
- A project with no environments is not obviously broken in bex (resources were placed correctly once an environment existed), so this is a genuine product decision, not a self-evident bug. Treat it that way.

## Steps

1. Decide: honour `environments` on create (provisioning the named environments), or diverge deliberately.
2. If honouring: create the environments in the same request, and decide what an omitted `environments` means — reject as Render's schema implies, or default to a single environment.
3. If diverging: record it in `docs/ADR018-render-parity.md` with the reasoning, so it stops being an accident and becomes a documented position.
4. Either way, make sure the create response's `environmentIds` (from `t001`) reflects reality.

## Files

- `lego/backend/internal/projects/rest.go`, `lego/backend/internal/projects/service.go`
- `docs/ADR018-render-parity.md` if the divergence is kept

## Acceptance criteria

- [ ] A written decision with reasoning, in code comment and ADR018 as appropriate.
- [ ] The implemented behaviour matches the decision.
- [ ] The create response's `environmentIds` is truthful under that behaviour.
