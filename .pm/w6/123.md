# A brand-new service's first minutes of egress are undercounted

Why: in w6/m333's production probe, the free service `qa-m333-egress` (`srv-dbqmev0rcnqs73dmd100`, `bex-canary`) served exactly 10,000,000 bytes between 07:15 and 07:17 UTC on 2026-11-12, then was deleted. Its hour metered `egress_bytes` 4,571,645, with every source healthy. The likely cause: the Traefik router counter is a new series, and Prometheus `increase()` does not count a series' first sample. So bytes served before the router's first scrape are lost. Every new service would undercount the same way, and a short-lived one mostly.

- **Do:**
  1. Confirm the cause. Check the router series' first sample against the curl timeline, and check whether `egressquery`'s exact-delta path is meant to cover a series that starts inside the window.
  2. If it is the first-sample gap, count a series that starts inside the window from 0. Treat that as an explicit, tested rule, since a reset-inflated sample must still never be invented.
  3. Re-run the probe.
- **Source:** w6/m333 t005, 2026-11-12.

## Cause confirmed — 2026-11-12

- **The arithmetic.** Traefik keeps one `traefik_router_responses_bytes_total` series per router × status code × method × protocol. The probe's `code="200"` series first appeared at 07:16:38 already reading **6,000,570**: three of the five 2 MB downloads finished before its first scrape. `increase()` counts only growth after a series' first sample in the range, so it read (10,000,570 − 6,000,570) × (105 s + 7.5 + 7.5) / 105 s = 4,571,428.57. Adding the `code="503"` series' ~216 bytes gives exactly the billed 4,571,644.57; `sum(increase(…[3600s]))` at 08:00Z reproduces it.
- **Scope.** Every series that first appears inside an hour loses what it counted before its first scrape. That covers a new service's first responses, and the first response with a status code a router has never returned. Up to one scrape interval (15 s) of traffic is lost per new series.
- **Fix direction.** Count a series that starts inside the window from zero. One option is, per series, `max_over_time(x[3600s]) − (last_over_time(x[5m] offset 3600s) or …×0)`, guarded like today by the existing `resets() == 0` health term so a reset never invents bytes. `ExactDelta` already treats a missing series as zero, but it reads only the instant, so a series gone stale by the hour's end (a deleted service) would vanish from it.
- **Prove it before switching billing.** Run old against new on recorded production windows, with a test in Prometheus's engine (the backend suite already runs `TestInstanceSecondsQueryOnPrometheus` that way). This changes billing arithmetic, so the rollout needs that comparison first.
