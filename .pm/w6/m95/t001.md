## Objective

Determine, with real cluster/operator-log evidence (kubectl, operator logs, Job/Pod history) — not just the dashboard/REST vantage point the discovering hunt was limited to — exactly why a fresh App CR's `status.Phase` stays `PhaseBuilding` (current-generation Ready condition) indefinitely while `lego/backend/internal/logs/service.go`'s `awaitBuildPod` finds zero Pending-or-Running build pod for it. Name the confirmed mechanism before t002 writes a fix.

## Context

- Reproduced 3/3 live on `dashboard.bex.co`, 2026-08-25 (see `.pm/w6/m95/README.md` for full evidence): `srv-da6un2u7kmsc739k8ju0`, `srv-da6upp67kmsc739k8k80`, `srv-da6ur3u7kmsc739k8ke0` — all fresh web services, Docker runtime, `rootDir=examples/hello-go` against the public `bex-co/bex` repo, Free plan, across both GitHub-App and Public-Git-URL source methods.
- The log-follow error (`ErrBuildNotRunning`, `lego/backend/internal/logs/service.go:70`) fires from `awaitBuildPod` (`service.go:944-994`) when `s.BuildPods(ctx, q.App, s.BuildNamespace)` lists no Pending/Running pod — a Pending pod is deliberately NOT refused (comment at `service.go:933-943`), so this means no pod exists at all, not a scheduling delay.
- `lego/backend/internal/store/reconciler.go:867-922`'s `observedDeployStatus`, with matching release generations (confirmed in all 3 repros — the orphan/supersede branch at `:924-969` did not fire), derives `build_in_progress` straight from `app.Status.Phase == PhaseBuilding` with a current-generation Ready condition. The store is a faithful mirror of what the App CR itself reports.
- `lego/operator/internal/build/build.go`'s `EnsureBuild`/`BuildJob` (`:535-573`, `:708-988`) dispatches via `execution.EnsureOwnedJob` (`lego/operator/internal/execution/job.go:53-78`) — described (not yet confirmed against this incident) as self-healing: Get→NotFound→re-Create.
- `lego/operator/internal/controller/app_controller.go:756-783` (`buildFromSource`) treats a Job-dispatch error as non-silent (`r.fail` → `PhaseFailed`), so a clean dispatch failure should NOT produce this symptom — which is exactly why this needs cluster evidence, not another code read.

## Steps

1. Reproduce live again (fresh `qa-<yyyymmdd>-` service, same repo/rootDir/runtime/plan) against a cluster where you can `kubectl get jobs,pods -n <build-namespace> -l app=<app-name>` and read operator logs directly.
2. At the moment the deploy log-follow first returns `ErrBuildNotRunning`, check: does a build Job object exist for this App at all? If yes, what does its `.status` say, and does it have zero pods, or pods that already terminated?
3. Tail operator logs for this App's reconcile loop across the same window — is `EnsureBuild` being called repeatedly (normal steady-state reconcile), or did the loop stop being invoked for this App entirely after the initial `PhaseBuilding` write?
4. If the Job never existed, trace why `buildFromSource`'s call to `EnsureBuild` didn't produce one, or produced one that was immediately garbage-collected/deleted by something else (check `TTLSecondsAfterFinished`, any prune/cleanup sweep, admission webhooks).
5. Name the confirmed mechanism plainly in this task's closing note (or a short addendum file) — this becomes t002's spec.
