## Objective

The store reconciler goroutine (`lego/backend/cmd/api/main.go:1252`, `go rec.Run(ctx)`) drives `core.PollWake`'s loop (`lego/backend/internal/core/poll.go:73-84`), which calls `step(ctx)` (→ `ReconcileOnce`) with no `recover()`. A panic anywhere in that call graph — a nil dereference on one malformed App/deploy row — crashes the whole `bex-api` process; during a crash-loop or slow restart, no gate-timeout evaluation runs for *any* app, not just the one that panicked. Add a `recover()` so one bad row degrades to a logged skip, not a process-wide outage of the exact watchdog this milestone depends on.

## Context

- This is a contributing-risk hardening task, not a confirmed cause of this hunt's incident — do not claim it explains the reproduced hang unless t001's cluster evidence says so.
- `core.PollWake` / `pollLoop`: `lego/backend/internal/core/poll.go:73-84`.
- Reconciler start site: `lego/backend/cmd/api/main.go:1252`.

## Steps

1. Add a `recover()` at the appropriate boundary (per-tick in `pollLoop`, or wrapping `ReconcileOnce` itself) that logs the panic (with enough context to identify which app/row triggered it, if determinable) and lets the poll loop continue on its next tick rather than crashing the process.
2. Add a test that panics deliberately inside one row's processing and asserts the loop survives and continues processing subsequent apps/ticks.
3. Confirm no existing test relied on a panic propagating out of the reconciler (unlikely, but check).
