## Objective

`lego/backend/internal/store/reconciler.go`'s `supersededDeployStatus` (`:924-969`) only closes an orphaned `build_in_progress`/queued row as `Canceled` past its gate timeout when `app.Status.ReleaseGeneration > 0` (`:965-968`). That guard was added by `2da39122` and `2f9db5d4` specifically so a legacy operator's metadata-generation churn (e.g. manual scale) wouldn't wrongly cancel a live rollout. Determine whether this guard can also strand a row when `ReleaseGeneration` is legitimately `0` or the App CR is briefly/permanently absent from the reconciler's `List` pass (`reconciler.go:511-517`), and close that gap without reopening the legacy-operator false-cancel risk the guard exists to prevent.

## Context

- This hunt's 3 repros all had matching release generations (the normal `PhaseBuilding` switch branch fired, not this orphan branch) — so t001 may confirm this guard is unrelated to the discovered incident. If so, this task still stands as a hardening pass against the documented, currently-live gap; do not skip it on that basis, but do not overstate it as "the" root cause if t001 found a different mechanism.
- `appReleaseGeneration` (`reconciler.go:984-989`) already falls back to `app.Generation` (the k8s metadata generation) when `ReleaseGeneration == 0` — a real k8s object's metadata generation starts at 1, not 0, so the literal `generation == 0` branch at `:941` is close to unreachable in practice; the practical gap is the `ReleaseGeneration > 0` guards at `:965`, `:985`, `:992` specifically privileging the release-generation-aware signal over the always-available metadata-generation fallback for the *timeout* decision, while using the fallback freely elsewhere.
- Also check `reconciler.go:511-517` (the `!ok → Create; continue` branch): if the App CR is missing from one `List` pass entirely, `recordObservations`/`recordDeploy` — and therefore the whole timeout check — does not run for that App that pass at all.

## Steps

1. Write (or locate) a test that puts a `build_in_progress` row on an App with `ReleaseGeneration == 0` past `BuildGateTimeout`, and confirm today it is NOT closed (red).
2. Change the guard so the gate-timeout closure fires even when release-generation evidence is entirely absent, while preserving the original fix's guarantee: a legacy operator's operational metadata-generation churn (manual scale) must still NOT be treated as a supersede/orphan.
3. Confirm `2da39122`'s and `2f9db5d4`'s own regression tests (`TestObservedDeployStatusCancelsOrphanedRowAfterTimeout` and siblings) still pass unchanged.
