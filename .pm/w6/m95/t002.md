## Objective

Using t001's confirmed mechanism, make it structurally impossible for a deploy row to sit at `build_in_progress` indefinitely with no backing BuildKit Job/Pod — either by restoring real build progress (self-heal the missing Job) or by failing the row out within `BuildGateTimeout` in every case, not only the `ReleaseGeneration > 0` branch.

## Context

- t001's finding is the spec for this task — do not re-derive it, read it.
- `lego/backend/internal/store/reconciler.go:971-982` (`timedOutDeployStatus`) already fails a `DeployQueued`/`DeployBuildInProgress` row to `DeployBuildFailed` once `deployTimedOut` (`:842-860`) is true — the fix may be as narrow as ensuring that timeout check is actually reached and evaluated for this scenario, or as broad as an operator-side self-heal that recreates the missing Job so the row makes real progress instead of failing.
- Whichever layer changes, the row must still eventually reach a terminal, honest status (`build_failed` or a real `live`) — never stay `build_in_progress` past `BuildGateTimeout` (35m).

## Steps

1. Implement the fix at the layer t001 identified.
2. Add a targeted regression test that simulates the exact confirmed mechanism (e.g. an envtest that deletes/never-creates the build Job/Pod behind an App already at `PhaseBuilding`) and asserts the deploy row reaches a terminal state within the gate timeout — proven red against pre-fix code.
3. Re-run the original live repro (fresh `qa-<yyyymmdd>-` service, same config) once deployed, and confirm it either builds successfully or fails cleanly within the gate timeout — never hangs.

## Files

- Per t001's finding — likely `lego/operator/internal/build/build.go`, `lego/operator/internal/controller/app_controller.go`, and/or `lego/backend/internal/store/reconciler.go`.
