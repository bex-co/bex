# 180 — Customers Checkout created before w6/m628 still bill the cardholder's name, not the workspace's

Why: w6/m628 names every new Stripe Customer after its workspace, but 9 of bex's 13 live Customers were created by Checkout before it, and Checkout named each after the cardholder, so their invoices still bill a person's name, and a workspace rename does not change it.

- **Evidence (2026-11-25, w6/m628 t001):** a read-only count over bex's live Customers (tagged `bex_workspace`, retired ones left out) found 9 whose name equals their default card's cardholder name, each with the card's billing address, 2 renamed to their workspace's name by `scripts/stripe-customer-names.py --live --apply`, and 2 whose workspace's only name is its `tea-` id. No name was printed ([billing-info.md](../../docs/render-artifacts/billing-info.md)).
- **Why m628 left them:** a cardholder's name may be the name the member wants billed, and nothing tells it apart from a name typed into the Stripe portal. `FollowWorkspaceRename` (`lego/backend/internal/billing/customer_billing_info.go`) therefore treats it as the member's and keeps it on a rename, and the backfill script renames only Customers still named by their `tea-` id.
- **Open decision (user):** move these 9 to their workspace's name, the Bill-to m628 recommends for every workspace, or keep the cardholder's. Render's own default Bill-to is unverified.
- **Do, if moved:** extend `scripts/stripe-customer-names.py` with a mode that also renames a Customer whose name equals its default card's `billing_details.name`, dry-run it live, then apply. A member can still set a company name in Billing info afterwards.
- **Acceptance:** the live dry run lists no Customer billing a cardholder's name, or this note records the user's decision to keep them.
- **Estimate:** ~30m.
