## Objective

Confirm the change is consistent wherever a resource count is reported, and record the surface's bex-only status rather than inventing a Render row for something Render does not expose.

## Context

- `workspaceLimits` is a **bex extension**: Render publishes no equivalent resource-cap query, so there is no Render behaviour to match. The parity task here is narrow and mostly about not creating a false ledger entry.
- What does need checking is internal consistency: whether any REST or MCP surface reports a resource count that would now disagree with the corrected one.
- The dashboard consumer chain is `use-resource-limits.ts` → `resource-caps.tsx`; its near-limit warning fires at a 0.8 ratio, which did not trigger at 11/100 during the hunt and so has never been seen in this context.

## Steps

1. Grep for any other surface reporting a resource count or cap; confirm none contradicts the corrected number.
2. Confirm the cap-hit error path (`mapServiceCapError`) still produces its named error unchanged.
3. Record in `docs/ADR018-render-parity.md` that the resource-cap surface is bex-only — or confirm an existing row already says so — rather than adding a divergence against a Render feature that does not exist.
4. Exercise the near-limit warning once at a ratio ≥ 0.8 so its behaviour under the new rule is known.
