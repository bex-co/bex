# 067 — The Environment page shows a key twice — as a service variable and under a linked env group — with no sign that the group's value is shadowed

Why: a user whose service variable and linked env group both define the same key sees it listed in both places with nothing indicating which one the process actually gets, on the page whose stated job is to "Manage service-specific variables, secret files, and linked environment groups".

Found 2026-08-27, 63rd `/qa-find-bugs` run, journey 4. **Minor** — nothing displayed is false, but the page under-informs on exactly the case where it matters.

## Live repro

A throwaway service and an env group deliberately colliding on one key, then linked:

```
POST /v1/services   name=qa-20260827-env2, envVars: SHARED_KEY=from-service, SVC_ONLY=svc-1
POST /v1/env-groups name=qa-20260827-eg,   envVars: SHARED_KEY=from-group,   GROUP_ONLY=grp-1
GraphQL mutation { linkEnvGroup(id:"evg-…", serviceId:"srv-…") }  ->  true
```

`https://dashboard.bex.co/services/srv-da8bvavm2e9c73ft6bd0/env`, from the accessibility tree:

```
Environment Variables …
  code: SHARED_KEY   code: •••••••  [Reveal] [Copy env vars]
  code: SVC_ONLY     code: •••••••  [Reveal] [Copy env vars]
Linked Environment Groups …
  Linked (1)
    link "qa-20260827-eg"  ->  /env-groups/evg-da8bve0ueu1c7395jd4g
    text: Linked GROUP_ONLY SHARED_KEY
    [Unlink]
```

`SHARED_KEY` appears twice — once as a service variable, once among the linked group's keys — with no marker, ordering hint, or tooltip saying the group's copy is overridden.

## The runtime precedence is correct; only the display is silent

`lego/operator/internal/controller/app_controller.go:3466-3487` (`envFromSources`) appends every `spec.envFromSecrets` entry (the linked **groups**) first, then `runtimeEnvSecret(app)` — the service's own env Secret (`:3542-3543`) — **last**. Kubernetes resolves duplicate keys across `envFrom` sources by last-source-wins, so the **service** variable wins, matching Render's documented "service-level overrides env group" behaviour. This is a display gap, **not** a precedence bug — do not "fix" it by changing the merge order.

Note for whoever picks this up: two nearby reads of this ordering are misleading. `app_controller.go:4412` (`knownBuildSecretNames`) ends in `sort.Strings`, and `app_controller.go:1295` builds a `map[string]bool` — neither preserves order, so neither can be used to reason about precedence. `envFromSources` is the only site that determines it.

## Fix sketch

Mark the shadowed key where it is already shown. The linked-group row renders the group's key list (`Linked GROUP_ONLY SHARED_KEY`), so the smallest honest change is to flag any key there that a service variable overrides — and/or note on the service variable that it overrides a linked group. `dashboard/src/features/services/` renders both sections on the same page, so both key sets are already in hand; en and zh move together.
