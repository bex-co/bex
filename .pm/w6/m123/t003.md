## Objective

A build that fails inside buildkit produces **no** buildkit output in the tenant's build log — not the error, not even buildkit's usual progress lines. This task owns the untraced cause and the fix.

## Context

**Observed, cause not traced.** For a free `web_service` on the public repo `github.com/render-examples/express-hello-world` with `dockerfilePath: ./NoSuchDockerfile`, the complete build log (`GET /v1/logs?resource=…&type=build&limit=30&startTime=…&endTime=…`) was 11 lines:

```
==> Build queued                                        (x2 — a superseded first deploy, then the manual one)
From https://github.com/render-examples/express-hello-world
 * branch            main       -> FETCH_HEAD
 * [new branch]      main       -> origin/main           (x2, one per deploy — the clone SUCCEEDED)
==> Deploy canceled                                      (the superseded deploy's banner)
==> Building from https://github.com/render-examples/express-hello-world@main
==> Build failed
```

- **The log pipeline works** — the clone phase's own git output is present, and in a separate fixture a clone *failure*'s stderr (`fatal: Authentication failed for …`) shipped correctly. So this is specific to the buildkit container, which is the lead worth chasing: whatever differs between those two containers.
- Candidate explanations, none confirmed: buildkit's container output is not collected by the log shipper; it failed before producing output; or its output went only to the pod termination message that `t001` shows nothing reads.
- Watch for a `limit` cap when re-probing — `limit=200` returns `400 invalid query parameter "limit"`, which can look like an empty log if the response shape is not checked.

## Steps

1. Reproduce the fixture and inspect where buildkit's stdout/stderr actually goes — pod logs, the shipper, Loki.
2. Identify the divergence from the clone container, which does ship.
3. Fix it so the failing phase's error is in the log the dashboard shows.
4. Confirm the fix on a **succeeding** build too: buildkit progress output should be present there as well, and its absence today may mean this was never working rather than failing only on error.

## Files

- `lego/operator/internal/build/build.go` (container/stream wiring)
- `lego/backend/internal/logs/` (query + progress synthesis)
- wherever build pod logs are shipped

## Acceptance criteria

- [ ] The missing-Dockerfile fixture's build log contains buildkit's own error naming the Dockerfile.
- [ ] A successful build's log contains buildkit's progress output.
- [ ] The cause is written down — this task exists because it was observed but not explained.

## Out of scope

- The `failureReason` composition (`t001`), which must work even when the log is empty; the two are deliberately independent channels.
