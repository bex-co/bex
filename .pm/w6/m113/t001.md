## Objective

Settle the semantics before touching code. `phase` currently answers "Failed" for a service returning 200, and there is no upstream behavior to copy — `w6/m52` recorded that "Render has no service-level status at all (its header renders the latest deploy)", which is why bex's `phase` was free to drift here.

## Context

- The two defensible answers are `Running` (phase describes what is serving; the failed attempt is already fully described by `deploy.status` and the header's `Latest deploy` badge) or a new distinct value such as `Degraded` (phase describes the service *and* flags that the newest attempt did not land).
- `app_types.go:1094` pins the enum: `+kubebuilder:validation:Enum=Pending;Building;Deploying;Running;Hibernated;Canceled;Failed`. A new value is a CRD change plus codegen, and `dashboard/src/features/services/lib/status.ts` carries only the raw phase — `w6/m52` found it never carried the Condition Reason, so a new value is the only way the dashboard can render a new distinction.
- The invariant is already written for the sibling case at `app_types.go:1104-1112`: "A cancel with an earlier healthy release never reaches this state: that release keeps serving and the phase stays Running." Generalizing that sentence to build failures is the cheapest coherent answer; adding `Degraded` is the more expressive one.
- Place `Hibernated` explicitly: a sleeping free-tier service has nothing running **by design** and must not collapse into whatever is chosen.

## Steps

1. Write the decision and its rationale into this milestone's README, then into `app_types.go`'s enum comment so the next reader finds it where `PhaseCanceled`'s rationale already lives.
2. If a new enum value is chosen, cost it out: CRD regeneration, `dashboard/.../status.ts`, the header badge's colour/label mapping, and every consumer that switches on phase.
3. Confirm the chosen value cannot collide with `Hibernated` or `Canceled`, and say where each of the four lands.
4. Check what the operator should do on the *next* successful deploy — does the service leave the new state automatically? The filing could not observe recovery because the fixture's builds kept failing.
