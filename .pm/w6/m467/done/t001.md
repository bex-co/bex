## Objective

Pick the mechanism that gives each named replica its own instance, URL and PgBouncer on the CNPG bex runs, prove it with raw manifests on dev-6, and write the choice down before code.

## Context

- CNPG 1.30.1 (`deploy/gitops/base/cnpg-operator.yaml`). Its `Pooler` targets `type` `rw`, `ro` or `r` only; its `Cluster` has `spec.replica` for replica clusters. Check CNPG v1.30.1's source and docs for anything newer before deciding.
- **Option A, bind instances in the one Cluster.** Each name is bound to one non-primary instance (`cnpg.io/instanceName`), recorded in the replica's status so later reconciles keep it. A Service per name selects that instance and `cnpg.io/instanceRole: replica`. The non-primary instance left unbound is the HA standby. A failover can promote a bound instance: CNPG's automatic failover picks the most advanced standby, and `triggerCNPGSwitchover` (`database_controller.go:2051`) picks any non-primary one. The name then moves to a standby, and the planned switchover must target the HA standby. The per-replica pool needs a PgBouncer Deployment bex owns: CNPG's PgBouncer image, the `cnpg_pooler_pgbouncer` auth query and its secret, server and client TLS, `pgbouncerParameters`, `pgbouncerRunCommand`, resources, `bex-datastore`, and NetworkPolicy reach. Everything keyed on `cnpg.io/cluster=<id>` keeps working.
- **Option B, one replica cluster per name.** A one-instance `Cluster` with `spec.replica.enabled` streams from the primary (`externalClusters`). It is never the primary's failover target, as Render's replicas are separate instances. Its `-rw` Service reaches its designated primary, which is read-only, and a CNPG `Pooler` `type: rw` on it gives a CNPG-owned PgBouncer. Costs: its Pods carry another `cnpg.io/cluster`, so every reader of `core.PodLabelCNPGCluster` (`lego/backend/internal/core/base.go:68`: metrics, logs, shell, disk usage, recovery) and the operator's readiness, instance count, storage quota and billing must follow. Check CNPG's cluster-name length limit against the 63-character `<id>-ro-<name>`, and whether the auth-query function exists on a replica cluster (it replicates from the primary only once the primary has had a Pooler).
- **Names.** `<id>-ro-<name>` already fills one DNS label for the longest names (`readReplicaNameMaxLength`), so a per-replica pooler cannot be `<id>-ro-<name>-pool` (ADR009 § Named read replicas). Render's pooled URL is the direct host on port 6432.
- dev-6 shares the cluster's bex operator, so the spike applies raw manifests in `dev-6`, as m458 t002 and t004 did.

## Steps

1. Read CNPG v1.30.1's Pooler and replica-cluster code and docs. List what each option needs from bex.
2. On dev-6, build each option by hand on one HA database with two replicas: the replica Service or cluster, and one PgBouncer per replica. For each one, check:
   - each replica URL reads only its instance (`inet_server_addr()`), never the primary or the HA standby;
   - after a switchover and after deleting the primary Pod, where each name points;
   - each replica's PgBouncer authenticates and holds 90 server connections.
3. Record what each option restarts or replaces on an existing database with in-cluster readers. The primary's Pods must not roll.
4. Choose the option whose replicas behave as Render's: own instance, own URL, own pool, never the HA standby or a failover target. This is a parity choice, not a user decision. Choose names for the per-replica Service, pooler and public pooled label. Write the decision, the evidence and the restarts into ADR009 § Named read replicas. If neither option can reach Render's behavior, record why and park the milestone for ADR018's sign-off.
5. Delete the spike's resources on dev-6.
