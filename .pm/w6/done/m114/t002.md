## Objective

The name is the *first* error the validator returns. Fixing it may only reveal the next one. This task establishes whether the exporter's output is actually appliable, per kind, rather than assuming one fix finished the job.

## Context

- `validateBlueprint` returns `errors` as a list but the filing only ever saw one entry, because the name failed first. Nothing yet establishes what is behind it.
- All five App-typed kinds (web · private · worker · cron · static) flow through `generateServiceEntry`; only `web` was exercised live.
- Fields worth suspecting, because they are kind-specific and the generator emits them conditionally (`blueprint_generate.go:180-224`): `runtime: image` + `image.url`, `runtime: static` + a publish path, cron `schedule`, `healthCheckPath`, `branch` (emitted only when non-default), disks, and `dockerCommand` (the compiler rejects it for `runtime: image` per `blueprint_plan_test.go:271`).
- The blueprint compiler's own refusals live in `blueprint_compiler.go:184-259` (`blueprintServiceRuntimeProblems`, `blueprintNativeRuntime`) — read those to know what the exporter must not emit.

## Steps

1. For each of the five kinds, generate a manifest from a real service of that kind and feed it verbatim to `validateBlueprint`. Create `qa-`-prefixed fixtures where the workspace has no service of that kind, and delete them afterwards.
2. Record, per kind, `valid` and the full `errors` list.
3. Fix what the exporter emits wrongly; for anything that is a genuine gap in the compiler rather than the exporter, file it separately rather than widening this milestone.
4. Also round-trip a datastore-referencing service (`fromDatabase` / `fromService`) — `datastoreReference` (`:320-348`) only emits the reference when the target is in the same selection, so a partial selection is a case worth validating.
