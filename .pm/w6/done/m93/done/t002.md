## Objective

Stop a live-tail reconnect from replaying a pod's log from the start — implement the backend SSE resume cursor that `w9/053` (done) shipped a partial mitigation for and explicitly deferred.

## Context

- Live-reproduced 2026-08-25 (Cron Job `qa-20260825-cron`): with Live tail ON, a single log line from one scheduled run rendered **twice**, identical timestamp/pod/message. Control check: the same run with Live tail OFF (pure historical GraphQL query) rendered the line **once** — proves this is a live-tail-only rendering issue, not a double execution or a backend double-write.
- **This is not a new bug and not a regression.** `.pm/w9/done/053.md` shipped the client-side ms-precision dedupe fix (`dashboard/src/features/logs/lib/map.ts:25-32`, `logLineKey`, commit `6e35aa9a`, 2026-08-22) and its own resolution note explicitly named the remaining gap: _"the real replay-window eliminator is backend SSE resume (`id:` + `Last-Event-ID` → k8s `SinceTime`), which would still need this ms-dedupe for the boundary second."_ Confirmed via git history: nothing has touched the relevant dedupe/replay logic in `map.ts`, `use-live-logs.ts`, or `service.go`'s `FollowLogs`/`streamPodLogs` since that fix landed — this is the same never-closed gap, reproduced live, not a reintroduction.
- Root cause: `lego/backend/internal/logs/podlogs.go:45-50` (`NewPodLogStream`) sets `Follow: true` with no `SinceTime`/`SinceSeconds`/`TailLines`. Every fresh subscribe — including the browser `EventSource`'s built-in auto-reconnect, invisible to the React hook — calls a brand-new `FollowLogs`/`streamPodLogs` (`service.go:740-834`, `:1180-1203`), which replays the pod's entire log from offset 0. A replayed line can land in the same millisecond bucket as the still-buffered original, which `map.ts`'s ms-precision `logLineKey` structurally cannot distinguish — exactly the "boundary second" case `w9/053` named.
- Alternate cause ruled out: duplicate concurrent pod streams. `appPodNames` (`service.go:1111-1123`, via `AppPodsIn`, `internal/core/base.go:1615-1623`) does one k8s `List` call returning each pod once; the per-pod goroutine fan-out (`service.go:806-814`) cannot double-stream a single pod within one `FollowLogs` call.
- Related, unverified this hunt: 9 repeated `GET /v1/logs/subscribe?type=build` reconnects were observed during one deploy's build-log tail, with the UI's "reconnecting" banner persisting throughout — possibly the same replay mechanism surfacing on the build-log path too. Investigate as part of step 1 below; don't assume it's the same bug without checking.

## Triage + fix (2026-08-25)

**Verdict: the symptom's diagnosis is wrong; the mechanism it names cannot produce a duplicate line. A different, real defect sits at the same call site and is fixed.**

### Why the stated cause is not the cause

The task says a replayed line "can land in the same millisecond bucket as the still-buffered original, which `map.ts`'s ms-precision `logLineKey` structurally cannot distinguish." That is backwards. `logLineKey` is `(Date.parse(timestamp), instance, message)` — so two records in the same millisecond, from the same pod, with the same message produce an **identical** key, and an identical key is exactly what the dedupe drops. Same ms ⇒ deduped, not duplicated. A duplicate can only render when the two keys **differ**.

And a replay cannot make them differ. Both the live tail and the historical query parse the same kubelet bytes through the same `parseContainerLogLine` (`service.go:1221`) and list pods through the same `AppPodsIn`, so a replayed line is byte-identical in all three key components. Two independent dedupes then stand in its way:

- `use-live-logs.ts:163-193` — a `Set` of keys kept in sync with the ring buffer, keyed on subscription identity (`epoch`), so it deliberately **survives a stream retry**; its own comment says "survives and dedupe absorbs any replayed lines."
- `log-viewer.tsx:145` → `mergeLogLines` → `dedupeLogLines` (`map.ts:119-133`) — dedupes across the history/live boundary too, keeping the first occurrence.

A "stale client" explanation is also out: `6e35aa9a` (the `w9/053` ms-dedupe fix) is an ancestor of `717143ae`, which deployed successfully 2026-08-24 21:43 — before the 2026-08-25 hunt.

### Why the evidence doesn't establish a bug either

The control ("Live tail OFF shows the line once") does not isolate a rendering defect. The two views are different result sets by construction: the historical query is a bounded window (`useLiveRange(range)`), while the live buffer **accumulates for the whole session**. On a cron job ticking on a schedule, live-on legitimately shows lines from more runs than a narrow historical window does. Reproducing this properly needs the two rendered rows' actual `timestamp`/`instance`/`message` values captured — which the hunt did not record (it notes "no screenshots were captured this cycle").

**No duplicate-line fix was made, because none is warranted on this evidence.** If it recurs, capture the two rows' three key fields; that immediately says which component diverged, and the fix follows from that rather than from a guess.

### The real defect at the same call site, now fixed

`NewPodLogStream` set `Follow: true` with no `SinceTime`/`TailLines`, so **every** subscribe re-read the pod's entire log from offset 0. `LogQuery.Since` already existed and was already honored — but only by `keep()` discarding lines _after_ kubelet had shipped the whole history into bex-api. So `GET /v1/logs/subscribe?startTime=…` was silently paying the full cost of a bound it then threw away, and a browser `EventSource`'s own invisible reconnect paid it again on every drop. That is the plausible mechanism behind the "9 repeated reconnects" noted in step 4.

Fixed by pushing the bound down and making the reconnect resumable:

1. `PodLogStream` takes a `since time.Time`; `NewPodLogStream` sets `PodLogOptions.SinceTime`.
2. `FollowLogs` and the build-log path pass `q.Since` through `streamPodLogs`/`streamContainerLogs`.
3. SSE frames now carry `id: <line timestamp>`, and `subscribeStream` reads `Last-Event-ID` back into `q.Since` (`resumeFrom`). An explicit `startTime` wins; an unparseable cursor is ignored, never refused.

**No dashboard change was needed for the reported path.** The browser's native `EventSource` replays `Last-Event-ID` on its own reconnect with no client code involved — which is precisely the "invisible to the React hook" case. The hook's _other_ reconnect path (a terminal `event: error` frame → `setAttempt` → a brand-new `EventSource`, `use-live-logs.ts:217-231`) starts with no cursor and still reads unbounded; left alone deliberately, since closing it means threading cursor state into the URL and the reported symptom came from the automatic path.

A formatting hazard the `id:` change introduced was caught by test and fixed: the emit closure now passes a second argument, and the NDJSON format's unindexed `%s` would have appended `%!(EXTRA string=…)` to every line — corrupting JSON for CLI clients while SSE looked fine. Both formats now use explicit `%[1]s`.

`w9/053`'s ms-dedupe is untouched, as the acceptance criteria require.
