## Objective

A pooled database's PgBouncer can open a descriptor for each of Render's 30,000 clients and its server connections on production's tenant nodes.

## Context

- Filed by t005's production check, 2026-11-17: production's containerd 2.3.3 starts containers at an open-file soft limit of 1,024 (hard 524,288). CNPG's Go manager restores that soft limit for PgBouncer, which logs `kernel file descriptor limit: 1024 (hard: 524288)` and never raises it. t003 read the hard limit and kind's 1,073,741,816 soft limit, so dev-6 did not show it.
- On the operator's `basic-1gb` pooler, 1,000 `pgbench` clients left PgBouncer `accept() failed: Too many open files` (11 times) and `sbuf_connect … Too many open files`, holding 10 server connections of its 90 at 63 transactions per second.
- CNPG 1.30.1 (`pkg/specs/pgbouncer/deployments.go`) sets the `pgbouncer` container's command to `/controller/manager pgbouncer run` only when the Pooler template has none (`WithContainerCommand(…, false)`).

## Steps

1. `poolerTemplate` sets the `pgbouncer` container's command to `/bin/sh -c` `pgbouncerRunCommand`: raise the soft limit to the hard one, then `exec` CNPG's manager.
2. A test pins the template command for both Pooler types and runs the command under a soft limit of 256 and a hard limit of 4,096 with a stand-in manager, which must start at 4,096 with `pgbouncer run`.
3. Check the exact command in a production Pooler; record it in ADR009 and ADR018.

## Result — 2026-11-17

- `pgbouncerRunCommand` in `datastore_priority.go`; `TestPgBouncerStartsWithTheHardFileLimit` failed with the command removed from the template (`ro pooler pgbouncer container = map[name:pgbouncer resources:…]`) and with the raise removed (`CNPG's manager started with "256 pgbouncer run"`).
- On production, a standalone CNPG Pooler `m458-nofile-test` against the probe, with the operator's settings and a command that raised the limit, ran PgBouncer and its manager at 524,288 (`kernel file descriptor limit: 524288 (hard: 524288)`). The same 1,000 clients connected in 6.2 s and held 87 server connections with 913 waiting, 412 transactions per second, 0 failed; the database's other 10 tenant slots were the two poolers' `auth_query` sessions. A second Pooler, `m458-nofile-test2`, with the exact shipped command, ran at 524,288 with the manager as PID 1 and answered a query. Both deleted; each `kubectl get` reads `NotFound`.
