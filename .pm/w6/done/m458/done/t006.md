## Result — 2026-11-17

Read on production (pin `e36296ae8`) as the QA user, for the `bex-canary` probe `dpg-dbucp4g8vt4s73a1ougg` (`basic_1gb`, pooled, public with this host allowlisted, replica `r1`). Passwords were compared, never printed.

- **REST** `GET /v1/postgres/{id}/connection-info`: `internalConnectionPoolString` on `<id>-pooler.<ns>.svc:6432`, `externalConnectionPoolString` on `<id>-pool.db.bex.co:5432`, and `readReplicaConnectionStrings[r1]` with the direct strings plus `<id>-pooler-ro.<ns>.svc:6432` and `<id>-pool-ro.db.bex.co:5432`. The probe's certificate was refused by Let's Encrypt's weekly limit for `bex.co` (`externalCertificate: failed`, the reason says so), so the external strings carried `sslmode=verify-full` and `serverCaCertificate`, as ADR009's private-CA fallback specifies. `GET /v1/postgres/{id}` lists `r1` with `connectionInfo` `internalPoolHost` / `externalPoolHost`.
- **GraphQL** `databaseConnectionInfo` returns the same strings and the same password; `database.readReplicas[].connectionInfo` the same pool hosts.
- **MCP** `get_postgres` returns `connectionPool: pgbouncer` and the same replica pool hosts.
- **Dashboard** Access control → Connection pooling → Reveal pooled strings lists the internal and external pooled strings and both for read replica `r1`, as REST does.
- **Connects.** From this host both external pooled names answered with `verify-full` against the connection info's CA: `-pool` on the primary, `-pool-ro` on the replica (`pg_is_in_recovery()` true).
- **Against Render.** Render's `postgresConnectionInfo` carries the two pooled strings and its `readReplica` is `{id, name}`; bex's per-replica pooled strings are the extension t004 recorded. No new drift. The open differences stay as filed: one pool shared by every replica (w6/137) and the external pooled URL on 5432 (signed off, ADR018).
