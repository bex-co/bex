## Objective

Confirm the fix changes only which value populates the webhook payload's `serviceName` field, not its name/shape, and that direct REST/GraphQL/MCP reads of `service.name`/`service.displayName` are unaffected — matching Render's behavior (no mutable/immutable name split, so its webhook payload's service name is always current).

## Context

- `docs/ADR006-bex-api.md` — bex-api's Render-compatibility contract.
- `docs/ADR018-render-parity.md` — the parity ledger; this fix doesn't add a new divergence row, it closes a bex-specific integration gap (bex's own `displayName` extension not reaching bex's own webhooks feature).

## Steps

1. Re-run this hunt's live probe (or the new regression test's assertions) against REST `GET /v1/services/{id}`, GraphQL `service(id:...)`, and the MCP service-read tool — confirm `name`/`displayName` fields are byte-identical to before this milestone.
2. Confirm the webhook JSON payload shape (`{type, timestamp, data:{id, serviceId, serviceName, status?}}`) is unchanged — only the `serviceName` value's source changed.
3. Note in this task's completion evidence whether ADR018/ADR006 need any wording update (expected: no, since this is a bug fix, not a new feature or contract change).

## Files

- No code changes expected; verification only.

## Acceptance criteria

- [ ] REST/GraphQL/MCP direct service reads are unchanged.
- [ ] Webhook payload shape (keys, types) is unchanged; only the `serviceName` value differs for renamed services.

## Result

**No wire-shape drift; webhooks are the only surface whose value changed.**

- **REST/GraphQL/MCP direct reads unchanged.** `TestRESTDisplayNamePatchRoundTripAndOmission`, `TestGraphQLDisplayNameRoundTrip` and `TestMCPDisplayNameRoundTrip` were not touched by this milestone and pass unchanged — `name` (immutable id) and `displayName` are byte-identical to before, including the empty-value clear.
- **Payload shape unchanged.** `payload`/`payloadData` (`webhooks/worker.go:340-353`) are untouched: `{type, timestamp, data:{id, serviceId, serviceName, status?}}`, same keys, same types. Only which column populates `serviceName` changed. `data.serviceId` still carries the immutable id a receiver calls the API back with.
- **No new parity divergence.** Render has no mutable/immutable name split, so its webhook service name is always current; this closes a bex-specific gap rather than opening one.
- **Docs did need a wording update** (t004 expected none): the omission is what let the drift persist. ADR018's w8/m8 rename row enumerated the three read surfaces and stopped there — it now states the webhook half, why w8/m8's DoD missed it, and the `COALESCE(NULLIF(display_name,''), name)` mechanism. ADR006's payload line now defines `serviceName` as the current human label (`displayName` when set, else `name`) against `serviceId`'s immutability.
- **Blast radius, confirmed wider than filed — in bex's favour.** `notifications/push_worker.go:610` tails the same `ListWebhookEvents` feed and builds push titles from `ServiceName` (`"<name> deploy started."`), so renamed services had stale push notifications too. Same one-line SQL fix covers both; no push-side change needed.
