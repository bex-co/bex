# 076 — A deploy made while a free service sleeps never runs, then closes update_failed with the generic health-gate line

Why: a free service that is asleep when its owner deploys gets a failed deploy that no rollout ever attempted, with the reason "the deploy did not become healthy within the health-gate window; check the service logs". There are no logs to check, and the new release is silently never tried.

**Estimate:** ~1h; inbox-sized (operator wake-on-deploy or an honest close reason, plus tests). **Worker:** worker6. Filed 2026-10-04 during the `/loopx w6` drain of m147.

## Evidence

- **w1/m172 live round 1, 2026-10-04** (`.pm/w1/done/m172/README.md`, "Deploy while asleep, no traffic"): `srv-db0vi0em0lvc73av9r9g`, `dep-db11c6klp43c73cufipg` started 09:02:18Z while hibernated. Nothing woke it and the rollout never ran. bex-api closed the row at its 18-minute gate (09:20:24Z) with the generic health-gate line.
- Since `e13afdd59` (w1/m172 part 2), `holdUnservedRelease` keeps the served template on a parked Deployment by design. A deploy to a sleeping service therefore waits for a wake. With no traffic, no wake comes, and the backend gate (`lego/backend/internal/store/reconciler.go` `deployTimedOut` → `timedOutDeployReason`) fires first.
- Not covered by w6/m147: m147 defers a park while a rollout is **in flight on an awake Deployment** (`rolloutAwaitingVerdict`). A deploy that starts while the service is **already parked** never reaches the Deployment.

## Decide, then fix

1. Check Render: a deploy to a spun-down free service builds and starts the new instance (expected; confirm from Render docs). If so, the operator should treat a newly requested release as activity on a parked free App: stamp `app.bex.co/last-active` once per release generation. The wake then starts the served pod first, rolls the new release over it (w1/m172), and m147's deferral holds the park until the verdict.
2. If the decision is instead to keep the service asleep, the row must not close as a health-gate failure. Give it an honest terminal state and reason ("the service was asleep; the release will roll out on its next request").

## Acceptance

- [x] Deploying a failing release to a hibernated free service with no traffic ends with that release's real diagnosis (or the honest reason chosen in step 2), never the generic health-gate line.
- [x] Deploying a healthy release to a hibernated free service ends `live` without needing an external request (if step 1 is chosen).
- [x] Operator envtest plus backend reconciler test; red with the fix reverted.

## Completed — 2026-10-04

**Verdict: worked (step 1, wake on deploy).** Render's free-tier page documents spin-down and request wake but says nothing about deploys. A Render deploy is `live` only once the new instance passes its health check, so a deploy is activity.

- `wakeForRelease` (`lego/operator/internal/controller/app_controller.go`, first step of `holdNewerRelease`) stamps `app.bex.co/last-active` on an auto-hibernated App with a newer release that has not served. It records the generation in `app.bex.co/release-wake-generation`, so each release wakes the service once. `stampLastActive` (`activity.go`) carries the extra annotation in the same optimistic-lock patch.
- No wake for: a suspended App, a release whose rollout already failed (`failedRolloutOverServed`) or whose pre-deploy failed (`preDeployFailedFor`), or a release that already woke it. The single wake is a documented bound (ADR004): a pre-deploy or served-pod start that outlasts the idle window parks again and waits for a request.
- After the wake, w1/m172 starts the served pod first and rolls the release over it, and w6/m147's `rolloutAwaitingVerdict` holds the park until the verdict. The deploy row then closes `live` or with the real diagnosis.
- Tests: `wake_for_release_test.go` (goes live with no request; suspended stays parked; once per release, and the next release wakes it again). The goes-live and once-per-release tests fail with the wake disabled; the suspended test passes either way, as it should. Two m172 tests rewritten to the new flow, where the deploy itself wakes the service: `TestParkedPendingPreDeployServesPriorReleaseUntilTheStepPasses` and `TestFailedRolloutStartedWhileParkedServesPriorRelease`. `TestWakeOverFailedPreDeployRestoresPriorRelease` pins the failed-pre-deploy exclusion (it failed before that check). Operator `make test` and `make lint` (four modules) pass; `/simplify` (two reviewers) applied.
- Live: covered by w6/m147 t004's deploy-while-asleep scenario on production.
