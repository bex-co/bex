- **Mechanism (unchanged from w6/087):**
  - `deploy.yml` keeps one running run and one pending slot, so each push cancels the pending run.
  - A run that finishes its tests skips build and deploy whenever a newer commit touched a deploy manifest (`scripts/deploy-superseded.sh`, rule 4).
  - Runs took 1.5–4h today. Several sessions pushed every 10–20 min, many of them manifest-touching. So the only runs that reached the end were always superseded, and the run that would build was always cancelled while pending.
- **Fix — target behavior:** a green main pins within a bounded time (proposal: ≤3h after the first deployable commit) however steadily sessions push. Options, any one of which meets the target:
  1. After N consecutive superseded or cancelled runs, or past a wall-clock bound since the last pin, a run that passed tests pins its own tree even if newer manifests exist. The newer tree follows in the next run. w4/439 already lets a run that is past the check pin on rule 4.
  2. Stop cancelling the pending run when the running one will be superseded: let the newest commit take the single slot without killing a run that is about to finish.
  3. Batch manifest-touching pushes, so the supersession check compares against a settled tree rather than every intermediate commit.
  - w6/m158 (in progress: shorter runs) reduces the window but does not bound it. With runs at ~1h and pushes every 10–20 min, rule 4 still starves.
- **Blast radius:** `deploy.yml` concurrency and `scripts/deploy-superseded.sh` rules 0–4. `scripts/deploy_latency.py` and the m156 watchdog read the same states, so a new "forced pin" outcome needs a state there too. Rule 4 exists so a pin never deploys a tree older than one already queued. Any option must keep "never roll production backward" (the pinned tree must contain the previous pin).

  - The runner queue time per run (how much of the 1.5–4h was waiting for runners) was not broken out.
