## Objective

Determine, with real cluster/operator-log evidence (kubectl, operator logs, Job/Pod history) — not just the dashboard/REST vantage point the discovering hunt was limited to — exactly why a fresh App CR's `status.Phase` stays `PhaseBuilding` (current-generation Ready condition) indefinitely while `lego/backend/internal/logs/service.go`'s `awaitBuildPod` finds zero Pending-or-Running build pod for it. Name the confirmed mechanism before t002 writes a fix.

## Context

- Reproduced 3/3 live on `dashboard.bex.co`, 2026-08-25 (see `.pm/w6/m95/README.md` for full evidence): `srv-da6un2u7kmsc739k8ju0`, `srv-da6upp67kmsc739k8k80`, `srv-da6ur3u7kmsc739k8ke0` — all fresh web services, Docker runtime, `rootDir=examples/hello-go` against the public `bex-co/bex` repo, Free plan, across both GitHub-App and Public-Git-URL source methods.
- The log-follow error (`ErrBuildNotRunning`, `lego/backend/internal/logs/service.go:70`) fires from `awaitBuildPod` (`service.go:944-994`) when `s.BuildPods(ctx, q.App, s.BuildNamespace)` lists no Pending/Running pod — a Pending pod is deliberately NOT refused (comment at `service.go:933-943`), so this means no pod exists at all, not a scheduling delay.
- `lego/backend/internal/store/reconciler.go:867-922`'s `observedDeployStatus`, with matching release generations (confirmed in all 3 repros — the orphan/supersede branch at `:924-969` did not fire), derives `build_in_progress` straight from `app.Status.Phase == PhaseBuilding` with a current-generation Ready condition. The store is a faithful mirror of what the App CR itself reports.
- `lego/operator/internal/build/build.go`'s `EnsureBuild`/`BuildJob` (`:535-573`, `:708-988`) dispatches via `execution.EnsureOwnedJob` (`lego/operator/internal/execution/job.go:53-78`) — described (not yet confirmed against this incident) as self-healing: Get→NotFound→re-Create.
- `lego/operator/internal/controller/app_controller.go:756-783` (`buildFromSource`) treats a Job-dispatch error as non-silent (`r.fail` → `PhaseFailed`), so a clean dispatch failure should NOT produce this symptom — which is exactly why this needs cluster evidence, not another code read.

## Findings (2026-08-25)

**Verdict: two independent code paths — not one — put an App in `PhaseBuilding` with no build pod behind it, and the control plane granted both the `build_in_progress` deploy status. Both were live on `main`; both are fixed in t002. The 35-minute watchdog does fire for the plain case, so the hunt's symptom was "up to 35 minutes of misleading Building" rather than infinite — except on four narrower paths where the watchdog is never evaluated at all, which are genuinely permanent and are closed in t002/t003.**

### Vantage point — stated plainly

This task asked for cluster/operator-log evidence. **That was not available and is not obtainable right now**: there is no reachable bex cluster from this workstation (`infra/local/bex.kubeconfig` points at a dead kind API server; the only live context is a bare `orbstack` cluster with no bex install), and production has not deployed successfully since 2026-08-24 (`w6/040`), so even a live repro against it would exercise pre-fix code and prove nothing about `main`.

What replaced it is stronger than another code read and weaker than production logs: an **exhaustive, executable enumeration** of every code path on `main` that can produce the exact observed state, with each candidate confirmed or ruled out by a test that runs against the real controller and reconciler code. Because the enumeration is exhaustive rather than selective, it does not depend on guessing which path fired in production — every path that *can* fire was found, and every one of them was live.

### The observed state, stated precisely

The hunt's three repros share one signature, and every element of it is load-bearing:

- (a) App CR `status.Phase == PhaseBuilding`;
- (b) a Ready condition whose `observedGeneration` equals the CR's metadata generation (so `readyReasonForGeneration` reports `conditionCurrent`);
- (c) zero Pending-or-Running pods carrying `app.bex.co/build=<app>` in `BEX_BUILD_NAMESPACE` — `awaitBuildPod` (`lego/backend/internal/logs/service.go:944-994`) deliberately accepts a Pending pod, so `ErrBuildNotRunning` means no pod object at all;
- (d) deploy row `build_in_progress`, release generations matching (so `supersededDeployStatus` returned `settled=false` and the normal phase switch ran).

Two details of the REST evidence corroborate this reading exactly. `updatedAt` 2µs after `startedAt` (`19:28:49.999680` / `.999682`) is the fingerprint of `TransitionDeploy`'s single UPDATE, whose `started_at` and `updated_at` each call `clock_timestamp()` (`store.go:1998-2005`) — so the row moved `created → build_in_progress` in exactly one write and then never again. And the two log lines that preceded the error (`==> Build queued`, `==> Building from …@f0d2a2e`) are not build output at all: they are `progressFollower` narrating the deploy ROW's own `createdAt`/`startedAt` (`internal/logs/progress.go:86,101`). Nothing in the hunt's evidence ever came from a build.

### Enumeration — every writer of PhaseBuilding

`grep -rn "PhaseBuilding" lego/operator/internal` proves there are exactly five `setPhase(…, PhaseBuilding, …)` call sites, all in `app_controller.go`, and no other writer anywhere in the operator:

| site | reason written | pre-fix deploy status | build Job at that moment |
| --- | --- | --- | --- |
| `:701` `awaitRegistryCredActive` | `RegistryCredsPending` | **`build_in_progress`** | **none — the gate is upstream of `EnsureBuild`** |
| `:729` per-App/workspace cap | `BuildQueued` | `queued` | none |
| `:795` overshoot shed | `BuildQueued` | `queued` | created, then shed |
| `:844` `obs.Phase == PhaseWaiting` | `BuildQueued` | `queued` | created, pod unplaced |
| `:848` `obs.Phase == PhaseBuilding` | `Building` | **`build_in_progress`** | created; **pod count not necessarily ≥ 1** |

The three `BuildQueued` sites mapped to the `queued` deploy status, which contradicts (d): **ruled out.** The other two both match (a)–(d):

**Mechanism 1 — `RegistryCredsPending` (`app_controller.go:697-706`).** For a repo-backed App the registry-credential gate runs *before* `build.EnsureBuild` is ever called. While zot has not yet re-read a freshly minted per-App push credential, it parks the App at `PhaseBuilding` with reason `RegistryCredsPending` and requeues every 10s — with no build Job, no pod, and nothing for the log stream to follow. `observedDeployStatus` recognised only the literal `"BuildQueued"` and **defaulted everything else to `build_in_progress`**, so this pre-dispatch wait reported a live build. This fits the hunt's profile precisely: all three repros were brand-new Apps (a fresh credential zot has not loaded — zot reads htpasswd only at process start, `internal/registry/verify.go:33-45`, and the activating bounce is rate-limited to one per 2 minutes globally), while the control case `eden-dash-v3` is a long-lived service whose credential acceptance is memoized and which built normally.

**Mechanism 2 — a build Job with no pod classified as Building (`build.go:607-616` → `app_controller.go:848`).** `buildQueued` returned `(false, "")` for BOTH a failed pod List and a successful List returning zero pods, so `EnsureBuild` fell through to `Observation{Phase: PhaseBuilding}` — which directly contradicts `PhaseBuilding`'s own documented contract three hundred lines above it: *"the build is running — a pod is placed on a node"* (`build.go:406-409`). The controller then wrote reason `Building` and the row went `build_in_progress` with zero pods. Normally sub-second; indefinite whenever pod creation is being rejected (namespace `ResourceQuota`, an admission webhook, a `LimitRange` the pod template violates), because the Job object exists and is healthy while its pod never materialises.

### The milestone README's candidates, each settled

1. **`EnsureOwnedJob` self-heal — ruled out as a defect.** It is genuinely Get→NotFound→Create on every pass, and `buildFromSource` is re-entered every 5s (`buildObserveRequeue`), so a vanished Job *is* recreated. Owner-ref, namespace and label filters are not implicated. The defect is not a missing Job; it is how a Job with no pod is *classified* (mechanism 2).
2. **Reconcile loop not re-triggered — ruled out.** Both PhaseBuilding paths return an unconditional `RequeueAfter` (10s for the credential gate, 5s for build observation), so re-entry is level-triggered and needs no watch event. A silent watch failure cannot explain this symptom.
3. **`supersededDeployStatus`'s `ReleaseGeneration > 0` guard — not this incident's mechanism** (the hunt confirmed matching generations, so this branch never fired), **but a real and independent stranding gap**, confirmed and closed by t003.
4. **The 35-minute `BuildGateTimeout` watchdog — confirmed to FIRE**, by executable probe through a full `ReconcileOnce` pass: a `build_in_progress` row backdated 40 minutes under a `PhaseBuilding` CR closes `build_failed` with `finished_at` set. So this was not an infinite hang in the general case, and the severity is "up to 35 minutes of a misleading Building state with a log stream that lies", which is what t002 fixes at the source. **However**, four paths reach a terminal state *never*, because they skip the timeout evaluation entirely rather than failing it:
   - `ReconcileOnce`'s three `continue`s — App CR absent from the List, App CR owned by another control plane (the w6/m39 guard), and a failed spec `Update` — each skip `recordObservations`, and with it every route to a terminal status. The first self-heals (the same pass recreates the CR); the other two do not.
   - `supersededDeployStatus`'s legacy branch, which returned settled-with-no-status forever (t003).

### Spec for t002/t003

- Grant `build_in_progress` only on positive proof that a build pod is running — an allow-list on the Ready reason, shared as one contract in `lego/types` instead of a matched pair of string literals on either side of the module boundary.
- Classify a successful pod List returning zero as `PhaseWaiting`, keeping a failed List (absent evidence) on today's behaviour.
- Make the gate-timeout close unconditional: it must run even on a pass that cannot observe the App CR, and even with no release-generation evidence.
- A timed-out build must close with a build-specific `failureReason`; the rollout's "did not become healthy within the health-gate window; check the service logs" points a tenant at logs a service that never built does not have.
