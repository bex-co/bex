## Outcome (2026-08-25)

**No wire-semantics change, and parity is structural rather than checked-by-hand.** REST (`rest.go:108`), GraphQL (`graphql.go:37`), and MCP (which shares REST's `renderDeploy`) all read the same `DeployView.Status` verbatim from `deploys/service.go:129` — one value, three encodings — so a deploy cannot read differently across them by construction. The dashboard consumes that same string through `dashboard/src/features/deploys/lib/deploy-status.ts`, which already carries `queued` in all three of its maps: `deployStatusKey` → `deploys.statusQueued`, `deployStatusVariant` → the in-progress badge, and `CANCELABLE_STATUSES` → the Cancel action stays offered. Nothing in the dashboard needed changing.

**Render comparison.** Render surfaces a build that cannot be scheduled as a queued and then failed deploy, never an indefinite in-progress spinner. That is now bex's behaviour on both mechanisms: a pre-dispatch wait reads `queued`, and the build gate closes it `build_failed` with a build-specific reason. Recorded in `docs/ADR018-render-parity.md` under Deploys, noting explicitly that the eleven-value vocabulary is unchanged (`queued` and `build_in_progress` are both already in it), so no filter, client, or migration is affected.

**One visible consequence, recorded rather than hidden:** `startedAt` is now stamped on the queued→build_in_progress edge instead of at the pre-dispatch wait. That is the honest moment, and it is also what stops the build-log stream emitting `==> Building from <repo>@<sha>` (`internal/logs/progress.go:101`, which reads `StartedAt`) before any build exists — the exact misleading line the hunt captured.

**Known pre-existing inconsistency, not introduced here and deliberately not widened:** the service header derives from the App CR's `status.Phase`, which stays `Building` during a queued build, so a service can read "Building" while its deploy row reads "Queued". That was already true for the `BuildQueued` reason before this milestone and is unchanged by it.
