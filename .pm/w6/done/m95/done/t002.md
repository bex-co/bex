## Objective

Using t001's confirmed mechanism, make it structurally impossible for a deploy row to sit at `build_in_progress` indefinitely with no backing BuildKit Job/Pod — either by restoring real build progress (self-heal the missing Job) or by failing the row out within `BuildGateTimeout` in every case, not only the `ReleaseGeneration > 0` branch.

## Context

- t001's finding is the spec for this task — do not re-derive it, read it.
- `lego/backend/internal/store/reconciler.go:971-982` (`timedOutDeployStatus`) already fails a `DeployQueued`/`DeployBuildInProgress` row to `DeployBuildFailed` once `deployTimedOut` (`:842-860`) is true — the fix may be as narrow as ensuring that timeout check is actually reached and evaluated for this scenario, or as broad as an operator-side self-heal that recreates the missing Job so the row makes real progress instead of failing.
- Whichever layer changes, the row must still eventually reach a terminal, honest status (`build_failed` or a real `live`) — never stay `build_in_progress` past `BuildGateTimeout` (35m).

## Steps

1. Implement the fix at the layer t001 identified.
2. Add a targeted regression test that simulates the exact confirmed mechanism (e.g. an envtest that deletes/never-creates the build Job/Pod behind an App already at `PhaseBuilding`) and asserts the deploy row reaches a terminal state within the gate timeout — proven red against pre-fix code.
3. Re-run the original live repro (fresh `qa-<yyyymmdd>-` service, same config) once deployed, and confirm it either builds successfully or fails cleanly within the gate timeout — never hangs.

## Outcome (2026-08-25)

Both mechanisms t001 confirmed are fixed at their source, and the gate-timeout backstop is now unconditional.

**`build_in_progress` is granted only on proof of a running build.** `lego/types/v1alpha1/app_types.go` gains `ReasonBuilding`/`ReasonBuildQueued`/`ReasonRegistryCredsPending` and the `BuildIsRunningReason` predicate on the CRD contract — the same place `IsBuildFailureReason` already lives, and for the same stated reason: before this, the operator wrote `"Building"`/`"BuildQueued"` as local literals (`app_controller.go:88-89`) and bex-api compared against its own copy (`reconciler.go:934`), with the reader **defaulting to build_in_progress**. So every reason the operator invented for a pre-dispatch wait silently claimed a live build. The predicate is an allow-list, not a deny-list: an operator newer than its control plane can add a wait reason, and it can never add a running one without changing the shared contract.

**A dispatched Job with no pod is Waiting, not Building.** `build.go`'s `buildQueued` treated a failed pod List and a successful List returning zero pods identically. They are opposites — one is absent evidence, the other is positive proof that nothing is running — and lumping them together produced `PhaseBuilding` in flat contradiction of that phase's own documented contract ("a pod is placed on a node"). Only the empty-result case changed; a List error keeps today's behaviour with its original rationale intact. The reason string names the real state ("build job dispatched; waiting for its build pod to be created") rather than borrowing the scheduler-capacity wording.

**The gate timeout can no longer be skipped.** `ReconcileOnce`'s three `continue`s — App CR absent, App CR owned by another control plane, spec `Update` failed — now call `settleAbandonedDeploys`, which closes only rows already past their gate timeout and never advances a phase (with no CR read this pass there is no live evidence to project). Sub-timeout rows are untouched, so a brief transient still costs nothing. The close notifies on the same terms as `recordDeploy`'s, since a failure nobody is told about is barely better than a row that never closes.

**An honest terminal message.** A timed-out build closed with the rollout's "did not become healthy within the health-gate window; check the service logs" — wrong twice for a service that never built. `timedOutDeployReason` now names the budget that actually expired, and `failureReasonFor` surfaces the operator's own wait message for `BuildQueued`/`RegistryCredsPending` ("the build never started: Waiting for the registry to accept this app's build credential"), which is the same w7/m79 gap this function's comment already documents twice.

### Tests (each proven red pre-fix by reverting only the source hunks)

`lego/backend/internal/store/build_backing_test.go`:

- `TestBuildInProgressRequiresProofOfARunningBuild` — table over `Building` / `BuildQueued` / `RegistryCredsPending` / an invented future reason. Red pre-fix on the last two.
- `TestFirstDeployWithNoBackingBuildReachesATerminalStateWithinTheGateTimeout` — the DoD end to end: fresh repo-backed service, App parked at `RegistryCredsPending`, row reports `queued` with no `startedAt`, then closes `build_failed` past the gate with `updatedAt` advanced and the registry message carried. Red pre-fix.
- `TestBuildGateTimeoutFailsARowWhoseBuildPodVanished` — the milestone's named regression: a legitimately `build_in_progress` row whose backing Job/Pod is gone reaches a terminal state on the build gate.
- `TestDeployIsSettledWhenTheAppCRCannotBeObserved` — both permanently-skipping passes (foreign control plane; an `Update` that keeps failing), including that nothing closes while still inside the budget, and that the close notifies.

`lego/operator/internal/build/build_test.go`: `TestDispatchedJobWithNoPodObservesAsWaitingNotBuilding` plus the two reworked `buildQueued` subtests (zero pods ⇒ queued; List error ⇒ not queued).

One existing envtest assertion was narrowed rather than deleted: `build_admission_envtest_test.go`'s self-deadlock guard asserted `Reason != BuildQueued`, which after this change also matches the legitimate no-pod-yet report (envtest runs no Job controller, so a Job there never gets a pod). It now asserts on the cap's own **message**, which is the invariant it actually guards.
