## Objective

`use-create-api-key.ts` and `use-create-registry-credential.ts` share the same bare-`catch {}` shape as the confirmed-broken hooks, but a grep of `lego/backend/internal/apikeys/` and `lego/backend/internal/registrycreds/` found **no** `ErrConflict`/uniqueness handling at all — unlike projects/environments, there isn't even circumstantial evidence these two resource types enforce workspace-unique names. Determine that first; a bare `catch {}` swallowing a conflict message that never exists is not a bug worth fixing.

## Context

- `dashboard/src/features/api-keys/hooks/use-create-api-key.ts:39,53-54` and `dashboard/src/features/registry-credentials/hooks/use-create-registry-credential.ts:52-53` both use unconditional `toast.error(t("<type>.createError", ...))` on any failure, with no message extraction.
- API keys are commonly not name-unique in comparable products (multiple keys can share a display label, distinguished by id/prefix instead) — this is a real possibility, not just an oversight, and would mean there is nothing to fix here.
- Registry credentials (container registry auth) may or may not enforce unique names per registry host — unconfirmed.

## Live probe result (2026-08-23, live QA hunt, `/loop 30m` session)

Confirmed live — **neither resource type enforces name uniqueness; not applicable, no fix needed.**

1. **API keys**: created `qa-20260823-dup` via the dashboard's Create API key dialog, then created a second API key with the identical name. Both succeeded with distinct key values (`0wVv1nr1-G~XS8TU9KGLx4fR.v` and `bGzPkag9CyH294mI5a.GboDvyt`) and both rows coexist in the API Keys table, distinguished only by creation time — confirming API keys are not name-unique, matching this task's stated hypothesis that comparable products commonly key on id/prefix rather than display name.
2. **Registry credentials**: created two credentials, both with Display name `qa-20260823-dup` but distinct registry hosts (`registry.qa-20260823-example.invalid`, `registry.qa-20260823-example2.invalid`) and distinct dummy (non-real) usernames/tokens. Both succeeded with no conflict and both rows coexist in the Registry Credentials table. Note: this confirms display-name-only duplication is harmless: it does not independently confirm behavior when both display name *and* host are identical, which remains untested and is left as a genuine open edge case for a future run, not assumed either way.

All four test resources (2 API keys, 2 registry credentials) were deleted via the UI's Revoke/Delete flow immediately after and confirmed gone from both list tables.
