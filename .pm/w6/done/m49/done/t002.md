## Objective

`use-create-key-value.ts` already extracts the GraphQL error message but throws it away for every case except the unrelated cap-limit check. Wire it to t001's shared conflict mechanism so a duplicate-name create shows the backend's actual reason.

## Context

- Live-confirmed today: creating `qa-20260823-duptest` twice → second call's GraphQL response: `{"data":{"createKeyValue":null},"errors":[{"message":"conflict: a key-value store named \"qa-20260823-duptest\" already exists in this workspace","path":["createKeyValue"]}]}`. The dashboard's actual UI toast for the same action: "Couldn't create qa-20260823-duptest. Please try again." (locale `dashboard/src/features/keyvalue/locales/en.ts:227-230`).
- `dashboard/src/features/keyvalue/hooks/use-create-key-value.ts:81-89`:
  ```
  } catch (err) {
    if (isPaymentOnboardingCancelled(err)) return null;
    const msg = graphQLErrorMessage(err) ?? "";
    if (msg.toLowerCase().includes("workspace is limited")) {
      setCapLimit(msg);
    } else {
      toast.error(t("keyvalue.createError", { name: input.name }));
    }
    return null;
  }
  ```
- Backend message source: `lego/backend/internal/keyvalue/service.go:352`.
- Look at `use-create-service.ts:125-138`'s `setNameConflict(true)` pattern for the shape of "dedicated inline state, not a toast" — decide whether Key Value's create form has (or should get) an equivalent inline slot, or whether a toast carrying the *specific* message (instead of the generic one) is an acceptable interim step for this resource type. Either is fine as long as the specific reason reaches the user; prefer inline if the form already has a natural place for it, don't invent new UI surface just to match services exactly.

## Steps

1. Add a branch using t001's shared conflict-detection helper, alongside the existing cap-limit branch.
2. On conflict, either set a new `nameConflict`-shaped state the create form renders inline, or call `toast.error()` with the specific extracted message rather than the generic `keyvalue.createError` string — pick based on what the New Key Value form's layout supports without disruptive rework.
3. Reproduce live: create a Key Value, then attempt the same name again from the UI, confirm the specific reason is now shown (not "Please try again").
4. Clean up any `qa-`-prefixed resources created for this check.

## Files

## Decision

A specific toast (not a new inline state): the New Key Value form has no natural inline slot next to Name the way services' wizard does, and a toast carrying the real message is a near-zero-cost fix that fully satisfies the DoD ("shows the backend's specific reason") without inventing new UI surface for a single resource type.

## Live probe result (2026-08-24, dev-7)

Created `m49-dup` via the dashboard's New Key Value form, then attempted the identical name again from the same form. Toast changed from the old generic "Please try again" to: **"A key-value store named "m49-dup" already exists in this workspace"** — the backend's actual reason, capitalized via `refusalReason`. GraphQL probe backing it: `extensions.code: "CONFLICT"`. Test resource deleted after.
