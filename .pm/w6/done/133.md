# Public datastore and WebSocket egress lose what a new series counted before its first scrape

Why: w6/m455 recovered this gap for HTTP only. A public Postgres or Key Value, and an App's WebSocket frames, still bill nothing for the bytes their counter recorded before its first scrape, so a short-lived public database connection or a first WebSocket session undercounts the same way a new service's first responses did.

- **Where.** The SNI proxies create `bex_pg_proxy_egress_bytes_total` / `bex_kv_proxy_egress_bytes_total` lazily on a resource's first copied bytes and never delete a series (`lego/operator/internal/sniproxy/meter.go`). The WebSocket plugin keeps per-App counters in a process-local map (`deploy/gitops/charts/traefik-plugins/websocketegress/websocketegress.go`). All three bill through `egressquery.Increase` (`lego/backend/internal/egressquery/query.go`), which drops a series' first sample.
- **Do:**
  1. Confirm, from each exporter's code, that a series absent from a successful scrape cannot later come back with an older value (the SNI proxies look safe: process-local, created at zero, never deleted; a restart is already rejected by the process-start health term).
  2. Set `NewSeriesFromZero` on each spec that passes, so `egressquery.Billed` counts its new series from zero behind the same scrape guard.
  3. Before billing switches, compare old against new on recorded production hours with `TestBilledAgainstIncreaseOnRecordedHours` pointed at those counters, as m455 t003 did for Traefik.
- **Done when:** a `promtool` case per source shows a new series billed from zero, the recorded-hours comparison differs only on new series, and ADR023 § New series count from zero lists the sources it covers.
- **Source:** w6/m455 t006, 2026-11-17.

## Done 2026-11-17

- **Exporters (step 1).** Both are process-local and never delete a series. The SNI proxies register one `CounterVec` in a process-local registry, create a resource's series when its first public connection closes, and serve every series on every scrape (`promhttp`, a failed gather is a 500). The WebSocket plugin creates an App's counter at zero in `New`, keeps it across middleware rebuilds (`LoadOrStore`), and writes every counter it holds (`metricsBody`). Every target is scraped per pod. `TestByteMeterSeriesAppearsAtFirstBytesAndStays` and `TestAppCounterStartsAtZeroAndSurvivesMiddlewareRebuilds` pin that side; each failed with the behavior it covers broken. `websocketegress.go` is unchanged, because any edit renames its ConfigMap and rolls Traefik.
- **Rule (step 2).** `NewSeriesFromZero` is set on the WebSocket, Postgres and Key Value specs (`lego/backend/internal/egressquery/query.go`). `TestBilledOnPrometheus` runs per source in Prometheus's engine. A session first scraped at its final 52,000 bytes bills 52,000 where `increase()` bills 0. A series missing at the start because its target was not scraped, or the scrapes failed, keeps `increase()`. Without the flag, three cases per source fail. Without the guard, the two missing-at-start cases fail per source.
- **Old against new (step 3).** `TestBilledAgainstIncreaseOnRecordedHours` now replays every source with the rule. On production Prometheus (104 hours ending 2026-11-13T08:00Z..2026-11-17T15:00Z, run twice, same figures), every hour of every source differs only on the new series, and none of them had been present earlier in retention.
  - WebSocket: 998 new series, all first scraped at 0. 2,792 → 2,790 B, because a new series bills its exact value where `increase()` extrapolated it.
  - Postgres: 25 new series, 100,350 → 215,696 B; in the 68 hours the gate passes, 91,121 → 184,775 B.
  - Key Value: 11 new series, 82,113 → 149,956 B, all of it in the 68 hours the gate passes.
  - The guard kept series on `increase()` in five hours, and the health gate skips all five.
- **ADR023** § New series count from zero lists the sources it covers and records the above.
- Production access: `~/.ssh/known_hosts` was stale, so the kubeconfig was fetched through ADR019's recovery flow. `Verify production SSH trust` run 43877180814 reported `SHA256:W/o3ED3/…VRyU`, all three running control planes matched it on a fresh keyscan, and the fetch used a temporary wildcard pin. `.env`, `~/.ssh/known_hosts` and the pin files were not changed.
