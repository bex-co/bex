# A store's proxy still closes its held clients on every deploy that changes the proxy's code

Why: w6/m512's 30 s drain lets short commands finish, but pools, pub/sub subscribers and long blocking commands still meet a close, without notice, on each deploy that changes `/kv-internal-proxy`, where Render breaks a store's connections for its own reasons only in announced maintenance.

- **Filed by** w6/m512 t006 (2026-11-19), as the stricter variant ADR021 § 10 names.
- **Today.** A proxy rolls when its binary changes (w6/m469), and the old pod drains for `BEX_KV_DRAIN_SECONDS` (30), then closes what is left (w6/m512, ADR021 § 10). The binary changed in 2 of the 11 production deploys on 2026-11-17.
- **Render:** a store's connections break when the customer changes it ("Render restarts your Key Value instance", [Key Value](https://render.com/docs/key-value)), and for Render's own infrastructure in service-affecting maintenance that "usually occur[s] no more than once every three months", announced by email and reschedulable for paid services ([platform maintenance](https://render.com/docs/platform-maintenance), both read 2026-11-19). No ADR018 row signs off bex's unannounced closes.
- **Direction:** defer a proxy-code roll to the store's next roll the customer causes (a plan change, enabling internal authentication, a resume), so the new binary rides on a restart the customer already accepted. Keep an override that rolls at once for a security fix. The held image is already safe to keep, since m469 records each proxy's binary hash.
- **Weigh before building:** a store the customer never changes would run the old binary indefinitely, so the deferral needs a ceiling (for example, roll in the store's nightly backup window after N days) or the override. `.pm/DO_NOT_DO.md` lists Render's maintenance runs as a non-goal: that is the customer-facing maintenance-window surface, not this deferral, which adds none.
- **Done when:** a deploy that changes `/kv-internal-proxy` rolls no store's proxy, a client held through `<id>:6379` keeps its `CLIENT ID` across it, the store's next plan change or internal-auth enable rolls its proxy onto the new binary, and a security override rolls every proxy at once.

Promoted to [m517](../m517/README.md) on 2026-11-19 by `/loopx w6`. The premise holds at `2df9359a5`. `keyValueInternalProxyImage` moves a proxy onto the manager's image as soon as its `/kv-internal-proxy` hash differs, and every other pod-template field is rendered fresh on each pass, so a deploy that changes either rolls every store's proxy. Each of this month's three binary changes (`0eed45bcb` m456, `ef091b640` m463, `d6d29f9a7` m512) also changed the rendering in the same commit. The hold therefore covers the whole template, not just the image: it is keyed on the store's own roll inputs (plan, internal auth, credential revision, TLS forwarding, resume), with a code-reviewed revision constant as the security override. No time ceiling: Render gives paid stores advance email notice and bex has no notice surface (`.pm/DO_NOT_DO.md`, maintenance runs), so a ceiling would bring the unannounced close back. The work is more than an hour across several tasks (8 in all): the hold, the override with a rendering guard, a local proof, ADR021 § 10, a production check, and the closing tasks. It ships only once production's pin carries `d6d29f9a7` and w6/m512 t007 has recorded its roll.
