## Objective

Pin the create/update distinction, and pin the datastore siblings that are correct today and that a refactor of this loop would break.

## Context

- The defect survived because no test planned a manifest against a workspace where the service already existed under a tenant-prefixed CR name. That fixture shape is what the tests need.
- Build the App fixture with a tenant-prefixed object name **and** a `LabelServiceName` label, or the test will pass for the wrong reason — a fixture whose object name happens to equal the public name cannot detect this bug at all.
- Also cover the legacy App with no label, whose object name legitimately is the public name.

## Steps

1. Plan a manifest against an existing tenant-prefixed App and assert the action is not `create`.
2. Assert a changed manifest and an unchanged one produce different plans.
3. Assert a genuinely new service still plans `create`.
4. Assert the legacy no-label App resolves via the fallback.
5. Assert an App in another workspace does not match.
6. Assert databases and key-values still plan correctly, and that duplicates conflict for all three kinds.
