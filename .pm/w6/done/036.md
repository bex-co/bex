# "Move to project" silently orphans a resource on partial mutation failure

Why: a transient failure on the second of two sequential mutations silently detaches a resource from its project with no rollback and no accurate error — the user sees "Failed to move" but the resource has actually lost its project membership entirely.

`dashboard/src/features/projects/hooks/use-move-to-project.ts:109-140`'s `moveTo` runs two independent full-list-replace GraphQL mutations sequentially with no rollback: first `runSet(from.id, ...)` removes the resource from its current project, then `runSet(to.id, ...)` adds it to the target. If the second call fails after the first succeeds, the `catch` shows a generic `"Failed to move \"{name}\"."` toast (`locales/en.ts:317-320`) implying nothing happened — but the resource is now unassigned from **both** projects.

**Live-reproduced end to end via the real dashboard UI** (2026-08-24): created `qa-20260824-moveA`/`moveB` projects and a Key Value in moveA, used route interception to fail only the second `SetProjectKeyValues` call, triggered the move via Actions menu → Move to project → moveB in the browser, and confirmed via three independent GraphQL queries afterward that `moveA.keyValueIds=[]`, `moveB.keyValueIds=[]`, and the KeyValue's own `projectId=""` — it's orphaned, not moved and not unmoved, while the UI told the user the move "Failed."

Same shared hook drives services and databases identically (`idsOf()` branches on `kind`, `runSet()` calls `SetProjectServices`/`SetProjectDatabases`/`SetProjectKeyValues`), so the same failure mode applies to all three resource kinds by code-path identity — not independently re-tested this run.

**Fix direction:** either reorder to add-then-remove (a failure leaves the resource in both projects — safe and recoverable — rather than in neither), or roll back the first mutation on second-call failure, and have the error toast/message reflect the actual resulting state rather than a generic "failed" that implies a no-op.

**Estimate:** 20-30 min.

## Closed 2026-08-27 — the failure mode is now unreachable by construction (37th `/qa-find-bugs` run)

`d247d210`: *"Membership is single-valued server-side (`apps.project_id`, one `LabelProject`), so the target write alone completes the move — one mutation, all-or-nothing."*

**Why this verification did not use route interception.** The filed repro forced a failure on the *second* of two mutations. The fix removes the second mutation, so there is no longer a second call to fail — the orphaning window is gone by construction, not by better error handling. Verifying that means proving two things instead: that exactly one mutation fires, and that the premise making one mutation sufficient is actually true.

**1. Exactly one mutation.** Built `qa-20260827-movea` / `qa-20260827-moveb` and a free Key Value `qa-20260827-movekv` in A, then moved it to B through the real UI (Actions → Move to project → `qa-20260827-moveb`), recording every GraphQL operation by name from the click:

```
operations issued by the move:  ["SetProjectKeyValues", "Projects"]
  SetProject* count: 1
```

One write plus `refreshProjects`' `Projects` refetch. The filed bug issued two `SetProjectKeyValues` — remove-then-add.

**2. The premise, checked rather than taken on trust.** "Assigning to the target already unassigns from the old project" is the whole load-bearing claim; if it were false the resource would end in *both* projects — a different bug, not a fix. Three independent reads after the move:

```
query { projects(ownerId: "tea-…") { name keyValueIds } }
  qa-20260827-movea  keyValueIds: []                                ← source cleared by the target write
  qa-20260827-moveb  keyValueIds: ["red-da80hnoueu1c7395ilrg"]

GET /v1/key-value/red-da80hnoueu1c7395ilrg
  projectId: "prj-da80hnoueu1c7395ilr0"                             ← = moveb
```

All three agree, so one write is a complete move.

**The shipped code says the same thing and cites this note** (`projects/hooks/use-move-to-project.ts`, in `moveTo`): a single `await runSet(to.id, [...idsOf(kind, to), resourceId])` under a comment explaining that a second call clearing the source *"is pure redundancy. It was also the bug… With one call the move is all-or-nothing."*

**Kinds:** exercised live with a key-value. Services and databases go through the same `moveTo` with `idsOf`/`runSet` branching on `kind`, exactly as this note observed, so they inherit the single-call shape — recorded as inherited, **not** separately observed.

Closed against the same bar as `029`/`030`/`041`, `035`, `031`, `028`, `027`, `037` and `033`: fixed, deployed, and re-probed live. All three `qa-` fixtures were deleted (`deleteKeyValue` → `true`, `GET` → 404; both projects deleted; the workspace's project list is back to its three originals).
