# New Service page's browser tab title never updates when the Service Type radio changes after load

Why: `w6/m43` (done) made the tab title and `<h1>` agree on initial load, but the same drift it fixed is still live for the one interaction most users actually use to pick a type — clicking the radio button — so the fix's promise ("tab title and `<h1>` always agree") doesn't hold post-load.

Live-reproduced on `/services/new`: loading the page shows `<h1>New Web Service</h1>` and `document.title = "New Web Service ・ bex Dashboard"` (agree, per `w6/m43`). Clicking the **Private Service** (or Background Worker / Cron Job / Static Site) radio updates the `<h1>` to `New Private Service` immediately, but `document.title` stays frozen at `"New Web Service ・ bex Dashboard"` — reproduced for every non-default type, confirmed via `browser_evaluate(() => ({title: document.title, heading: document.querySelector('h1')?.textContent}))` returning `{"title":"New Web Service ・ bex Dashboard","heading":"New Private Service"}`.

Root cause: `dashboard/src/routes/services.new.tsx:63-67`'s `head()` resolver computes the title from `serviceTypeCreateCopy(match.search?.type)` — the **URL search param**, evaluated once per route match — while the live `<h1>` at the same file's component body reads `serviceTypeCreateCopy(form.serviceType)`, live client React state from `dashboard/src/features/services/hooks/use-new-service-form.ts:52-58` (`useState`, initialized once from `search.type ?? DEFAULT_SERVICE_TYPE`, updated only via the in-memory `set()` setter — never written back to the URL). Clicking a Service Type radio calls `set({ serviceType: ... })`, which never touches `match.search`, so TanStack Router never re-runs `head()`. Not a regression of `w6/m43` — its own Definition of done and tests (`services.new.test.tsx:800-810`, `route-heads.test.ts`) only assert the *initial* route-load title for a given `?type=`/default; changing the radio post-load without a URL param change was never in that milestone's scope.

Fix shape: either (a) have the radio's `onChange` also update the URL search param (`navigate({ search: { type: ... } })`) so `head()` re-runs naturally, or (b) set `document.title` directly from an effect keyed on `form.serviceType`, mirroring what the `<h1>` already does. (a) keeps title/heading/URL all agreeing and is probably the smaller, more consistent fix given `parseNewServiceSearch` already round-trips `?type=`.

Evidence: `.playwright-mcp/qa-services-title-mismatch-1.png`.

## Resolution (2026-09-03)

Fixed via the note's option (a): the Service Type radio's onChange also writes `?type=` (`navigate` with functional search updater + `replace: true`), so `head()` re-runs and URL/title/<h1> agree; other params kept, no history entry, form state survives (no remount). 3 tests added under a real `head()`+`HeadContent` harness in `services.new.test.tsx` (61/61 pass).
