# An invalid `?type=` query param on `/services/new` crashes the whole page

Why: a malformed or unrecognized `type` deep-link value (e.g. a bookmark, external integration, or future internal caller passing anything other than the 5 exact `ServiceType` strings) hard-crashes the New Service page with "Something went wrong" instead of falling back to the default type — a real, reachable defect just off the primary create-service journey.

## Repro

1. Navigate to `https://dashboard.bex.co/services/new?type=web` (any value that isn't exactly one of `web_service` / `private_service` / `background_worker` / `cron_job` / `static_site`).
2. Page renders a full "Something went wrong" error-boundary crash.

Control cases (both correct):

- `?type=web_service` (a valid enum value) → renders "New Web Service" fine.
- bare `/services/new` (no `type` param) → falls back to the default fine.

Console error on crash:

```
TypeError: Cannot read properties of undefined (reading 'titleKey')
    at Object.head (.../index-C6c_TJYg.js:55:68831)
```

## Root cause

`dashboard/src/routes/services.new.tsx:63` computes the document title via `serviceTypeCreateCopy(match.search?.type).titleKey`. `serviceTypeCreateCopy` (`dashboard/src/features/services/lib/create-context.ts:76-79`) does `SERVICE_TYPE_CREATE_COPY[type ?? DEFAULT_SERVICE_TYPE]` with no guard — if `type` is a truthy string that isn't one of the 5 valid `ServiceType` keys, the lookup returns `undefined` and `.titleKey` throws.

The route already has a sanitizer for exactly this case — `parseNewServiceSearch` (same file, lines 90-100) calls `isServiceType()` and drops any unrecognized `type` before it reaches the rest of the app. But this route's `head()` callback receives `match.search?.type` as the **raw, pre-validation** value on a direct/hard navigation (confirmed empirically: a full `page.goto()` to `?type=web` crashes). TanStack Router's `head()` runs during the SSR/initial-load pipeline in `@tanstack/router-core@1.170.25`'s `projectLane`, and the crash only reproduces this way — not independently verified whether an in-app client-side navigation to the same malformed URL also crashes, since by then `validateSearch` has typically already run. So `head()` is the one call site in this file bypassing the sanitizer that every other reader of `type` in this route (the form's `serviceType` state, line 77) correctly goes through.

**Blast radius:** grepped every `head: ({ match })` callback across `dashboard/src/routes/` (18 routes) — `services.new.tsx` is the **only** one that derives its title from a search-parsed value via a keyed lookup; every other route's `head()` uses a hardcoded literal title-key string. Not a systemic pattern needing a sweep — isolated to this one file.

## Fix

Make `serviceTypeCreateCopy` defensive regardless of the framework-level cause: `SERVICE_TYPE_CREATE_COPY[type ?? DEFAULT_SERVICE_TYPE] ?? SERVICE_TYPE_CREATE_COPY[DEFAULT_SERVICE_TYPE]`, so any unrecognized type value (now or from a future caller) falls back to the default title instead of throwing. Add a regression test hitting `/services/new?type=web` (or calling `serviceTypeCreateCopy` directly with a bogus string) asserting it resolves to the default web-service title instead of throwing.

## Dedupe

Grepped `.pm` (open + `done/`) for `titleKey` / `serviceTypeCreateCopy` / `parseNewServiceSearch` — only unrelated hits in `w5/done/m47` and `w6/done/m43` (same file, different already-shipped feature, not this crash). Not in `DO_NOT_DO.md`. `git log -S"serviceTypeCreateCopy"` shows only the original commit that built this system — no existing fix.

## Resolved (verified 2026-08-25)

Fixed by `ca14cb59` ("feat(dashboard): deep-linkable service create wizard + per-type New menu"), which rewrote this route's search handling. `parseNewServiceSearch` (`features/services/lib/create-context.ts:91-103`) now admits `type` only when `isServiceType(search.type)` holds and **drops** it otherwise — its own docstring says "Unknown values dropped" — so an unrecognized value can no longer reach the picker. The downstream consumer is safe on the same path: `serviceTypeCreateCopy` takes `ServiceType | undefined` and falls back to `DEFAULT_SERVICE_TYPE`. An invalid `?type=` therefore renders the default wizard instead of crashing the page. Closed without further work.
