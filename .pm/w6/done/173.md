# A disk service's move pulls its image only after the volume reaches the new node

Why: when a disk service's volume moves (a cordoned or full node, or a plan that no longer fits), its new instance pulls an image the new node lacks only after Hetzner's detach and attach, so a large image adds its whole pull to a window already 30–35 s long.

- **Found by:** [w6/m595](m595/README.md) t005 on production, 2026-11-23, in `bex-canary` (fixture `w6-m595-t005`, disposable, deleted).
  - P, a Starter → Standard plan change: Standard's 1 CPU did not fit on the volume's node, so the new pod was bound to another node at once. The volume then detached (9.35 s) and attached (16.02 s), and only then did containerd pull 311.0 MB the node lacked (13.00 s). Window 48.00 s.
  - C, a code deploy with the node cordoned: detach 9.38 s, attach 15.93 s, then a 305.1 MB pull (15.08 s). Window 47.76 s.
  - With a cached image, m547 t011 and m559 t005 measured moves of 33.25–39.75 s.
- **Cause.** The kubelet pulls a pod's images only after its volumes are mounted. The new pod is bound to its node within 0.3 s of the old pod's teardown, about 27 s before its volume arrives. w6/m595's pre-pull runs only on a held rollout, on the volume's own node (`prePullThroughHold`, `lego/operator/internal/controller/disk_prepull.go`).
- **Idea.** Once a `Recreate` disk rollout's new pod is bound to a node other than the volume's, start the same `dskpul-` Job there for the images that node may lack, so the pull overlaps the detach and attach. It needs no wait: the template is already written.
- **Done when:** on production, a cordoned code deploy of an image with at least 100 MB new to the destination node shows the destination's pull of the new digest ending before the new instance's `MountDevice`, the instance's own `PullImage` reading 0 bytes, and the window within 1 s of a cordoned run of a cached image. A test covers the bound-elsewhere path.

## 2026-11-23 — the fix shipped; the production measure waits for the pin

- **Fix (`b0420d7b61`).** Once a disk service's template is written and a new instance is bound to a node other than its volume's and has not mounted it, the operator starts the `dskpul-` Job on that node for every image the instance runs, since that node may lack any of them (`prePullOnMove`, `lego/operator/internal/controller/disk_prepull.go`). The volume's node is the holder's, or with no holder the node the template prefers, which is the one its instance ran on when the template was written. Nothing waits for the pull: it overlaps the detach and attach, and the kubelet runs the instance's own pull behind it. A held code deploy's pull still running on the node the volume leaves is ended there. A plan change that no longer fits the volume's node pre-pulls too (run P's case), though it keeps its images.
- **No second pull.** The move's Job stays, even once its pull has ended, until the instance has the volume, and then ends as any pre-pull does. It starts only within 60 s of the instance's binding, which is its TTL after it ends, so no pass finds it reaped and pulls again. `bex_disk_prepulls_total{result="moved"}` counts each one.
- **Pull policy.** Each pre-pull container now pulls its image with the policy the template's instance uses for it: `Always` for a tenant's image, as before, and `IfNotPresent` for bex's own helpers, such as the health-probe installer, which a move now pre-pulls too.
- **Tests.** `TestDiskPrePullOverlapsAMove` runs a cordoned code deploy and a plan change whose new instance is bound to node-b. The Job starts there with the instance's image, outlives its pull while the volume has not arrived, starts no second Job, and ends once the instance mounts. `TestDiskPrePullFollowsTheInstanceToTheNodeItsVolumeMovesTo`, `TestDiskPrePullReadsTheVolumesNodeFromItsHolder`, `TestDiskPrePullStartsNoneUnlessTheVolumeMoves` (an instance bound to the volume's node, one running where the volume moved, one bound past the bound: no Job and no write) and `TestDiskPrePullPullsEachImageAsTheInstanceDoes` cover the rest. Seven mutations of the change each fail one of them. `make test` and `make lint` passed.
- **Next.** Once production's pin carries `b0420d7b61`, measure as [m595 t005](m595/done/t005.md) run C did, as the QA user in `bex-canary`: a disk-bearing Starter fixture (disposable) with its volume's node cordoned, a code deploy of an image with at least 100 MB of layers new to the destination node, and a cordoned run of a cached image. From the destination node's syslog, check that the pre-pull's pull of the new digest ends before the new instance's `MountDevice`, that the instance's own `PullImage` reads 0 bytes, and that the window is within 1 s of the cached run's. Record the windows in ADR082 § D3's table, ADR004 and ADR018, then close the note.

**The new image was on the destination before the volume.**

- **The pre-pull started at the binding.** In every run the operator logged `pulling the instance's images onto the node its disk moves to` for `dskpul-tea-daif693dqjvc73e7as3g-w6-173` within 0.05 s of the new instance's binding, and containerd's `PullImage` of the new digest began 0.28–0.32 s later. `bex_disk_prepulls_total{result="moved"}` and `bex_disk_holds_total{result="skipped_unschedulable"}` each counted once per run.
- **It ended before `MountDevice`.** C2 read 330.3 MB in 12.74 s and C4 316.6 MB in 15.43 s, and each pull ended 13.82 and 10.73 s before the new instance's `MountVolume.MountDevice succeeded`.
- **Nothing was fetched after the attach.** Each instance's own `PullImage` of the digest read 0 bytes in 0.59–0.65 s, the `imagePullPolicy: Always` re-check alone. Each destination pulled the digest exactly twice, the pre-pull's and the instance's, so no pass started a second pre-pull.
- **The Job ended once the instance had the volume.** The operator logged `ended the disk rollout Job` with reason `finished` on the pass that saw the new instance running, after its pull.

**The window: within 0.75 s of the cached run.**

- C2 and C4 took 32.75 s each, against 32.00 s for C5, a cached image moved with the same Hetzner timings (detach 9.33–9.39 s, attach 15.98–16.20 s). Before the fix, m595 t005's C took 47.76 s with the same detach and attach (9.38 and 15.93 s), 15.08 s of it a 305.1 MB pull after the attach.
- What is left of the 0.75 s comes after the attach, not from the pull. The new-image runs' sandboxes came 2.82–2.93 s after `MountDevice` (cached: 2.45–2.56 s), and their app ran 1.67–1.75 s after the sandbox (cached: 0.97–1.44 s), the first start from a freshly unpacked image.
- **C1 and C3 are Hetzner's.** In C3, the CSI detach call hit its deadline after 16.01 s (`DeadlineExceeded`), and the attach then took 16.06 s. In C1 the detach took 16.12 s, and Hetzner reported the attach at 10:01:52.6Z, but the disk appeared in `85xrs`'s kernel only at 10:02:01.6Z (`sd 0:0:0:3: [sdd] Attached SCSI disk`). The kubelet's publish failed three times until then, so its sandbox came 11.45 s after `MountDevice`. Neither pulled any bytes. m547 t011 measured the same 16 s detach.

**No surface showed a pre-pull.**

- No `dskpul-` Job or pod was left after any run, or at the end.
- `GET /v1/services/{id}/instances`, polled every second, never listed more than one instance or a `dskpul-` id.
- `GET /v1/services/{id}/events` held 12 events (6 `deploy_started`, 6 `deploy_ended`), none naming a pre-pull. 4,084 log lines read through `GET /v1/logs` from 09:59 to 10:10Z named neither `dskpul`, `pull-0`, `StartError` nor `exec: "/"`.
- After C5 the counters read `moved` 5 and `skipped_unschedulable` 5, with `held`, `mounted` and `pulled` unchanged, and nothing counted `failed`, `timeout` or `refused`.

**Against the definition of done.** On production, cordoned code deploys of images with 330.3 and 316.6 MB new to the destination node pulled the new digest there 13.82 and 10.73 s before the new instance's `MountDevice`. The instance's own `PullImage` read 0 bytes. Both windows, 32.75 s, are within 0.75 s of a cordoned run of a cached image (32.00 s). `TestDiskPrePullOverlapsAMove` and `TestDiskPrePullStartsNoneUnlessTheVolumeMoves` cover the bound-elsewhere path (`b0420d7b61`). ADR082 § D3, ADR004 and ADR018 record the measure. Closed 2026-11-24.
