# 055 — Custom-domain DNS instructions tell you to create "this exact TXT record" at one host, once per domain, with a different value each time

Why: bex auto-adds the `www` sibling when you add an apex, so the very first custom domain a user adds produces two panels demanding two different TXT values at the same host name — and following either one literally, in the single-value edit box most DNS providers give you, destroys the other's proof.

## What's wrong — instructions, not architecture

The design is deliberate and documented. `docs/ADR005-custom-domain.md:16` specifies the ownership record as `TXT _bex-challenge.<registrable-domain>` with a "Durable random `bex-domain-verification=…` challenge", and `:53` states that "each row has its own durable challenge and must verify independently". `systemDomainOwnershipVerifier.VerifyTXT` (`lego/backend/internal/apps/domains.go:62-73`) accordingly does `slices.Contains(values, value)`, so several TXT records **can** coexist at that one name and each row verifies against its own. That part is fine and should not be changed.

What is missing is any instruction saying so. Each panel reads, in isolation:

> **First, create this exact TXT record to prove ownership.** The domain is not routed until verification succeeds.

Nothing says "keep the records already at this host", and nothing warns that the host is shared across every domain you add under the same registrable domain.

## Live repro (2026-08-27, 24th `/qa-find-bugs` run)

Added `qa-20260827.invalid` to `srv-da7o6ovvqdcc73bpn9hg`. bex auto-created the `www` sibling. Then added `sub.qa-20260827.invalid`. All three claims, read straight from REST:

```
GET /v1/services/srv-da7o6ovvqdcc73bpn9hg/custom-domains

qa-20260827.invalid       apex       ownershipDnsRecord: TXT _bex-challenge.qa-20260827.invalid
                                     = bex-domain-verification=GjyWKaFV_t659J7REHQBzoHQwfPqSrP4
www.qa-20260827.invalid   subdomain  ownershipDnsRecord: TXT _bex-challenge.qa-20260827.invalid
                                     = bex-domain-verification=a2_VKEVFsStMPcWIimBqzaMY5hkdtEnu
sub.qa-20260827.invalid   subdomain  ownershipDnsRecord: TXT _bex-challenge.qa-20260827.invalid
                                     = bex-domain-verification=6ptrPZoR_qm6o-EjBJo2POwBkoqgp41K
```

Same host, three values. The dashboard renders all three panels stacked on `/services/<id>/settings`, each with the "this exact TXT record" wording — confirmed on a fresh page load, in the accessibility tree, not just innerText. All three claims were deleted at the end of the run.

The values are minted per claim by `newDomainChallenge()` (`lego/backend/internal/store/store.go:957-963`, 24 random bytes base64url), called from `AddDomainClaim` (`:968`), while the record **name** comes from `ownershipDNSRecordName` (`domains.go:83-85`) = `"_bex-challenge." + registrableDomain(host)`. Per-claim value, per-registrable-domain name — as designed.

## Fix sketch

Copy, not mechanism. The TXT panel needs to say that this host holds one record per domain and that existing values must be preserved — ideally rendering the sibling values together when more than one claim shares the host, so the user sees the full required set rather than one row at a time. `dashboard/src/features/services/` renders `ownershipDnsRecord` per row today; grouping by `ownershipDnsRecord.name` is the natural shape. Both `en` and `zh` move together.

## Not a bug (checked, recorded so the next hunt does not re-file it)

- The shared challenge host is intended (`ADR005:16,53`), and the verifier tolerates multiple values.
- The **deterministic** `sha256(appID + "\x00" + root)` challenge in `domains.go:87-102`, used by `requireDomainOwnership` (`:807`, `:933`), is not a competing scheme by accident — `ADR005:36` documents it as the storeless bex-api's fail-closed path.
- `qa-20260827-hijack.onbex.co` is correctly refused: "is a reserved platform hostname". The platform-suffix guard works.

## Resolution (2026-09-03)

Both halves done — copy and grouping: `domainOwnershipGuidance` now says the shared `_bex-challenge` host holds one TXT record per domain and existing values must be kept (en+zh), and a new `ownershipSiblings()` helper lists sibling claims sharing `ownershipDnsRecord.name` inside each panel (and each half of the post-add dialog) under a keep-their-records note — the user sees the full required record set, not one row at a time. Tests: paired claims each show both values + the note; a lone claim shows neither.
