# `git push` from Zed works in a sandbox resume started for an editor

Why: since w6/m564 (ADR054 D8) opening a closed session in Zed starts its sandbox, but once the start settles the session is `completed`/`failed` again, and the gateway's Git mint refuses every non-live phase, so a person who edits in Zed and pushes from its terminal gets `remote: forbidden`. A Devin machine opened from its workspace pushes.

- **Where.** `credentialMintPhases` in `lego/backend/internal/agentsession/mint.go` (`creating`/`running`/`resuming`/`redispatching` only) gates `CurrentSandboxCaller`, which every gateway verb shares (Git, model, share, `gh`). The same refusal already applies in a finished turn's idle window, editor or not.
- **Candidate.** Admit the Git mint, and only it, for a finished session whose `sandbox_id` equals `editor_sandbox_id` (the sandbox resume started or kept for a person, `store.AgentSession.EditorSandbox`), still bound by the exact Pod UID and the `bex-agent/*` branch rule. Keep the model mint and every other verb on the live-phase allowlist: no agent runs there.
- **Security.** This widens a credential window that codex F12 closed on purpose. Write the reasoning into ADR054 D8 (who holds a shell there: `can_view_sensitive` only; how long: the idle timeout or an open editor, 4 h at most) and add the negative tests for the non-editor finished sandbox and for the model route.
- **Done when** a real-Postgres mint test grants a Git token to the editor's sandbox of a completed session and refuses it to a finished turn's own sandbox, and the production check of w6/m564 t004 pushes a commit from the Zed terminal.
