## Objective

Use the CR's effective physical database and owner-role names in the actual CloudNativePG data plane, with explicit, tested behavior for fresh bootstrap, legacy CRs, and recovery-created clusters.

## Context

- `lego/operator/internal/controller/database_controller.go` currently computes `dbname := normalizeIdent(db.Name)` and `owner := dbname + "_user"` before building `bootstrap.initdb`.
- This is the mechanism that must change for custom names to be real; changing only API readback would produce unusable connection strings.
- Recovery uses `bootstrap.recovery`, not `bootstrap.initdb`. A recovered cluster must expose the database/owner names that actually exist in the restored archive; it must not invent incompatible defaults.
- Existing clusters with empty fields must render byte-identical CNPG specs so reconciliation does not restart or replace them.

## Steps

1. Replace controller-local name derivation with t001's effective-name helpers.
2. Project the names into `bootstrap.initdb.database` and `.owner`, and ensure related generated resources/credentials refer to the same owner.
3. Define and implement recovery semantics: propagate the source's effective physical names onto the recovery target (or reject an incompatible custom override) before creating the target CR.
4. Add pure projection and reconciliation tests for both custom and legacy/default cases.

## Acceptance criteria

- [x] A custom-name CR projects the exact requested database and owner into CNPG `bootstrap.initdb`.
- [x] An old/empty-field CR produces the same CNPG spec as before this milestone.
- [x] Recovery never returns connection info naming a database/owner absent from the restored archive.
- [x] Reconciliation cannot mutate physical identity after the cluster is initialized.

## Out of scope

- In-place `ALTER DATABASE ... RENAME` or role renames.
