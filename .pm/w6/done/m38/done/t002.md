## Objective

Make the Render-shaped `POST /v1/postgres` request's `databaseName` and `databaseUser` fields real core create intent, and make every backend read/connection path use the effective persisted values rather than re-deriving them ad hoc.

## Context

- `lego/backend/internal/postgres/service.go`'s `CreatePostgresRequest` has neither field today; `pgView` always derives both from `Database.metadata.name`.
- The REST decoder therefore accepts the official CLI payload but silently drops the two keys.
- Connection-info, secret-loading, pooler strings, read replicas, recovery, and webhook projections must agree with the view; a cosmetic readback change without a matching real database would be false parity.
- `dryRun` must run identical validation/default resolution without creating the CR.

## Steps

1. Add optional `databaseName`/`databaseUser` request fields and validate them through t001's shared contract.
2. Persist them into `Database.spec` on create; keep each omitted value empty/defaulted so legacy/default behavior remains byte-compatible.
3. Replace backend-local derivations with t001's effective-name helpers in `pgView`, connection-info, pooler/read-replica URLs, recovery creation, and any secret/query path that names the database or owner.
4. Ensure dry-run returns the exact resolved names and performs no Kubernetes writes.
5. Pin the Render REST request/response casing and 400 error dialect.

## Acceptance criteria

- [x] REST create with both fields stores both values and returns them unchanged in `databaseName`/`databaseUser`.
- [x] Supplying only one custom field defaults only the omitted field; omitting both is byte-identical to the current behavior.
- [x] Connection strings and SQL-query/user-management paths use the effective persisted database and owner rather than a newly derived value.
- [x] Invalid identifiers fail with Render-shaped 400 before a CR or Secret is created.
- [x] Dry-run resolves the same values with zero side effects.
