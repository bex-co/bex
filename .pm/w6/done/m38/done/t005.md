## Objective

Eliminate false-success behavior for the official CLI's `--datadog-api-key` and `--datadog-site` flags without implementing the external Datadog agent/metrics-drain integration excluded by the roadmap guardrails.

## Context

- The checklist records that create and update currently return success while silently dropping `datadogAPIKey`/`datadogSite`.
- Render's official docs describe these fields as an organization API credential plus site that starts an agent alongside Postgres and forwards database/host/disk metrics.
- `.pm/DO_NOT_DO.md` excludes external log/metric-drain integrations. This user request did not explicitly reopen that product decision, so this milestone must not deploy an agent, store the credential, or claim functional Datadog parity.
- The API should nevertheless recognize the known Render fields and fail clearly; generic JSON unknown-field rejection would risk breaking forward compatibility for unrelated clients.

## Steps

1. Add presence-sensitive request/patch fields for `datadogAPIKey` and `datadogSite` only where the Render REST/CLI payload can send them.
2. Return a named `core.ErrBadRequest` explaining that Postgres Datadog monitoring is unsupported before any CR mutation, including empty-string update/removal requests.
3. Add create and update tests proving no success/no-op and no credential leakage in logs/errors/audit details.
4. Record the deliberate non-goal in the checklist/ADR rather than marking these flags complete.

## Acceptance criteria

- [x] Create/update with either Datadog field returns a stable, named 400 and performs no mutation.
- [x] The API key value is never echoed, audited, or logged.
- [x] Requests omitting both fields behave byte-identically to today.
- [x] Docs keep Datadog functional support open/non-goal while removing the inaccurate “accepted with success” behavior.

## Out of scope

- Storing a Datadog key, deploying a Datadog agent, or forwarding any metric/log.
