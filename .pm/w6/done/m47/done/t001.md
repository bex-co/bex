## Objective

A free-tier web service that auto-hibernates after its idle timeout — the dashboard correctly shows "Sleeping to save resources — wakes on the next request." — never actually wakes. Every request to its `.onbex.co` URL after hibernation returns a bare `404 page not found` (Traefik's own default-backend response, not the activator's expected `503` wake page) and the App's `phase` stays `Hibernated` indefinitely. This defeats the entire free-tier sleep/wake value proposition: a hibernated free service becomes permanently unreachable, not merely slow-to-wake.

## Root cause — CONFIRMED (2026-08-23, static)

**An Ingress backend resolves only within the Ingress's own namespace, and the auto-hibernate branch named a Service in a different one.**

`ingressBackend` (`lego/operator/internal/controller/app_controller.go`) returned `r.ActivatorService` — the bare name `bex-activator` — as the public backend for an auto-hibernating App. That Service lives in `bex-system` (`lego/operator/config/activator/service.yaml`, plus the `bex-` `namePrefix` from `config/default`), while under ADR043 every tenant App's Ingress lives in its own `tea-<xid>` workspace namespace. The named backend therefore does not exist in the Ingress's namespace, Traefik has no backend to route to, and it answers with its own default 404 — matching the observed body/header shape exactly, and explaining why the activator never logged the request and the phase never moved.

Three things corroborate this over the original "misconfigured env var" hypothesis:

1. **The same function already does it correctly for maintenance.** `reconcileMaintenanceAlias`, forty lines away, carries the comment _"Ingress backends must live in the Ingress namespace. When the shared responder is in the platform namespace, create an App-owned ExternalName alias…"_ — and the hibernate branch simply never got one.
2. **ADR043 D7 enumerated only two alias shapes** ("static-server and maintenance routing"), as did `operator-alias-admission.yaml` and `verify-static-site-security.sh`. The wake path was overlooked in every one of them, consistently.
3. **The test gap is exactly shaped like the bug.** `TestCrossNamespaceMaintenanceUsesOwnedExternalNameAlias` existed for maintenance; nothing equivalent existed for hibernation, and every hibernate test ran in namespace `default` — where a cross-namespace alias is unnecessary and the defect is invisible.

Ruled out (do not re-investigate): the activator's handler has no 404 path for any input; the operator never writes `.Spec.Suspended`; `applyClusterIPService` never sets a Service `Type`. The env var was wired correctly all along — the value was right, the _namespace_ was unreachable.

## Fix — SHIPPED

- `ingressBackend` now routes an auto-hibernating App through `reconcileActivatorAlias`, which creates an App-owned `bex-activator-<app>` ExternalName alias in the App's own namespace targeting `bex-activator.bex-system.svc.cluster.local:8888` (short-circuiting when the App already shares the activator's namespace). New `ActivatorNamespace` field, wired from `POD_NAMESPACE` in `cmd/manager`.
- The alias reuses `reconcilePlatformAlias`, so its labels, owner reference, port shape, and 63-char name cap match the existing static/maintenance aliases exactly.
- **Admission, verifier, and docs updated in lockstep** — the fail-closed `ValidatingAdmissionPolicy` admits exactly three alias shapes now, so shipping the operator without this would have had the API server deny every wake alias: `deploy/gitops/base/operator-alias-admission.yaml` (new `exactActivatorAlias`, sync-wave `-3` still precedes the operator), `scripts/verify-static-site-security.sh` (live inventory would otherwise flag every wake alias as noncanonical), ADR029, ADR043 D7, `lego/operator/CLAUDE.md`.
- Regression tests: `lego/operator/internal/controller/auto_hibernate_wake_test.go` — see t006.

## Live verification — DONE (2026-08-23, dev-7 / shared CAPD cluster)

Verified as a **before/after on one live App**, `m47-sleep` (free tier, `idleTTLSeconds`, image `traefik/whoami`) in the real tenant namespace `tea-da4cvia9086ufe1pmhf0` — the cross-namespace shape the bug needs. Deleted afterwards; the alias was garbage-collected with it via its owner reference.

**Before (operator `bex-operator:dev`, the pre-fix build already deployed):**

```
phase=Running   backend=m47-sleep:80         # serving normally
… idle TTL elapses …
phase=Hibernated backend=bex-activator:8888  # scaled to 0
$ kubectl get svc bex-activator -n tea-da4cvia9086ufe1pmhf0
Error from server (NotFound): services "bex-activator" not found
```

That is the defect exactly as predicted: the public Ingress points at a Service that **does not exist in its own namespace**, which is why Traefik answers with its default 404 and the activator never sees the request.

**After (operator rolled to a build of this fix):**

```
backend=bex-activator-m47-sleep              # flipped within one reconcile
$ kubectl get svc bex-activator-m47-sleep -n tea-da4cvia9086ufe1pmhf0
TYPE=ExternalName  EXTERNALNAME=bex-activator.bex-system.svc.cluster.local  PORT=8888
labels={"app.bex.co/app":"m47-sleep","app.bex.co/platform-alias":"activator",
        "app.kubernetes.io/managed-by":"bex-operator"}   owner=App/m47-sleep controller=true
```

The labels/owner match `exactActivatorAlias` in `operator-alias-admission.yaml` field for field.

**The full wake cycle, end to end:**

1. DNS — the tenant-namespace backend resolves the whole chain (this is what Traefik does): `bex-activator-m47-sleep.tea-….svc.cluster.local` → CNAME → `bex-activator.bex-system.svc.cluster.local` → `10.135.37.22`.
2. Request through that backend with the app's Host header, while hibernated — **the wake page, not a 404**:
   ```
   HTTP/1.1 503 Service Unavailable
   Retry-After: 5
   Cache-Control: no-store
   {"error":"service hibernated","retryAfter":5}
   ```
   and in the activator log: `"waking app" app=m47-sleep host=m47-sleep.onbex.co`.
3. Within one reconcile (~6s): `phase=Running backend=m47-sleep replicas=1 ready=1` — the Ingress flips back off the alias to the App's own Service.
4. The retry serves the **real application response**: `HTTP 200` with whoami's own body (`Hostname: m47-sleep-7fd5cd767d-mxjkc`, `Host: m47-sleep.onbex.co`).

**Environment repairs needed to run the leg** (local-cluster drift, none of it product defects, none committed): the CAPD LB port had been remapped so `infra/local/bex.kubeconfig` pointed at a dead port; the Traefik `Middleware` CRD was absent (installed the copy the repo already vendors for envtest); the activator pod could not reach the API server from its worker node (`10.128.0.1:443 i/o timeout`) so it was pinned to the control-plane node; and the cluster's `bex-manager-role` lacked `replicasets`, which blocked the operator's cache sync entirely. That last one is a **real latent gap in `config/rbac`** — filed as inbox note `w6/032`.
