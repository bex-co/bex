## Objective

Check that t001–t003's fixes are consistent across every surface bex-api exposes (REST, GraphQL, MCP) and the dashboard UI, and compare against render.com's documented free-tier sleep/wake and event/audit-log behavior — flagging any divergence as follow-up rather than silently diverging (`docs/ADR006-bex-api.md`).

## Steps

1. Confirm the wake fix (t001) is observable identically from REST `GET /v1/services/:id`, GraphQL `server(id)`, and MCP's service-read tool — all three should agree on `phase`/status once a wake succeeds, with no surface stuck reporting stale `Hibernated` state after the others have updated.
2. Confirm the new hibernate/wake event types (t002) are surfaced consistently: the REST events endpoint, the GraphQL events field, and the MCP events tool should all expose the new distinct type(s), not just the dashboard's Events tab.
3. Confirm the Logs empty-state fix (t003) has no equivalent server-side contract to check (UI-only) — note this explicitly rather than silently skipping it.
4. Compare against render.com's own behavior: does Render's dashboard/API distinguish an auto-slept free service from a manually suspended one in its own event/activity log? Record the comparison; if bex's new distinction has no Render equivalent, note it as a deliberate improvement, not a gap.

## Files

- `lego/backend/internal/apps/rest.go`, `graphql.go`, `mcp.go`

## Acceptance criteria

- [x] REST, GraphQL, and MCP reads of a woken service's phase agree with each other and with the dashboard.
- [x] REST, GraphQL, and MCP reads of the new hibernate/wake event types agree with each other and with the dashboard's Events tab.
- [x] The render.com divergence is written down explicitly rather than silently absorbed.

## Outcome

Parity holds **by construction** rather than by three parallel edits, which is worth recording:

- **Phase** is read from the same `App.status.phase` projection on all three surfaces, so t001's routing fix cannot desynchronize them — no surface caches a phase of its own.
- **Event types**: the events feed sets `ev.Type = r.FactType` (`events/service.go`), so a new fact type reaches REST, GraphQL, and MCP the moment it joins `allFactTypes`. There is no GraphQL enum for event types to extend.
- **Webhook subscribability**: `EventTypes` is derived from the `verbEvents` + `factEvents` key sets, so adding to `factEvents` automatically extends the GraphQL `webhookEventTypes` query and the MCP `list_webhook_endpoints` vocabulary that feed the dashboard's picker.
- **t003 is UI-only** — the Logs empty-state title has no server-side contract. Noted here rather than skipped silently, as the task asked.

**Render divergence (deliberate improvement, not a gap):** Render's own webhook vocabulary has no equivalent of `service_hibernated` / `service_woken` — it reports a slept free service through the same suspend/resume vocabulary bex used to. Both new types are therefore recorded as `bexExtensions` in `docs/render-artifacts/fixtures/render-webhook-vocabulary-2026-08-17.json`, which is the gate `TestBexWebhookVocabularyHasOneTruthfulDispositionPerValue` enforces: no bex value can enter the served picker without an explicit disposition.
