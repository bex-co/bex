## Objective

The Events tab (and, transitively, any audit-log/webhook/notification consumer of the same event fact) reports a service's transition into `Hibernated` phase as **"Service suspended"** — the identical label and event type used for an explicit user-initiated Suspend. This directly contradicts an existing, explicit invariant documented elsewhere in the same codebase: `lego/backend/internal/apps/service.go:856-857`'s `suspenders` doc comment states "The user-driven suspend verb is the only way an App becomes suspended in bex, so a suspended App always reports exactly `["user"]`." The Events feed breaks that invariant's spirit by using the _same word_ for a mechanism (free-tier auto-idle-hibernate) that is explicitly not user-driven suspension.

## Context

- Live repro this run: `qa-20260822-sleep2` auto-hibernated after its 5-minute idle timeout (confirmed via GraphQL `phase: "Hibernated"`, not `Spec.Suspended`). Its Events tab (`/services/<id>/events`) showed, as the top-most/most-recent entry: `"Service suspended"` timestamped exactly to when the idle window elapsed — with no distinguishing text indicating this was an automatic idle-sleep rather than someone clicking Suspend.
- Root cause pinned exactly: `lego/backend/internal/store/event_facts.go:387-390`:
  ```go
  if obs.ServicePhase != previousPhase {
      switch obs.ServicePhase {
      case "Hibernated":
          facts = append(facts, makeFact("suspended", EventFactServiceSuspended))
  ```
  This fires on _any_ transition to the `"Hibernated"` observed phase — which is exactly what auto-idle-hibernate produces (confirmed: `Spec.Suspended` was never written; only `Status.Phase` changed, per the grep in the sibling task t001 finding zero operator-side writers of `.Spec.Suspended`). There is no separate fact/event type for "auto-hibernated due to idle timeout" anywhere in the vocabulary — `grep -n "Type.*=.*\"" lego/backend/internal/events/service.go` lists every event type constant and none of them distinguish the two.
- **Consumer impact, not just cosmetic display:** `EventFactServiceSuspended` also feeds `lego/backend/internal/webhooks/service.go:98,143` (webhook payload `type: "service_suspended"`) and `lego/backend/internal/notifications/push_worker.go` (push notification wording) — so this is not confined to the dashboard Events tab; every downstream consumer of this event type currently cannot distinguish "a human suspended this service" from "this free service went to sleep as designed." A user relying on webhooks/notifications to detect an unexpected suspend would get a false positive on every normal free-tier sleep cycle.
- **Control case verified:** the `service_resumed` fact (`event_facts.go:391-394`) has the _same_ conflation in reverse — waking from `Hibernated` back to `Running` fires `EventFactServiceResumed`, identical to a manual Resume. This task should fix both directions symmetrically, not just the sleep side.

## Steps

1. Add a new event fact type (and corresponding events/webhooks/notifications vocabulary entries) for auto-hibernate/auto-wake, e.g. `EventFactServiceHibernated`/`EventFactServiceWoken`, distinct from the user-driven `EventFactServiceSuspended`/`EventFactServiceResumed`.
2. In `observedStateFacts` (`event_facts.go:375-406`), distinguish which fact to emit based on _why_ the phase changed — the free-tier auto-hibernate path is identifiable (the App has `Spec.IdleTTLSeconds > 0` and is on a free/eligible plan, per `lego/operator/internal/controller/app_controller.go:1838`'s own gate `r.ActivatorService != "" && app.Spec.IdleTTLSeconds > 0 && isFreeApp(app)`) versus an explicit `Spec.Suspended` write from the user-driven `Suspend()` verb (`service.go:2757`). Read whichever signal is actually available to `observedStateFacts` at the point it runs (it may need a new field on `ObservedServiceState`, e.g. carrying `app.Spec.Suspended` alongside the observed phase, since phase alone conflates the two).
3. Update the dashboard/webhook/notification copy for the new event types (e.g. "Service went to sleep" / "Service woke up") — keep the existing `service_suspended`/`service_resumed` wording exclusively for the user-driven case, matching the `suspenders()` invariant.
4. Live-verify: hibernate a fresh free service via idle timeout and confirm its Events entry reads distinctly from a manually-Suspended service's Events entry.

## Outcome

`spec.suspended` is the discriminator — the operator never writes it, only the user-driven Suspend verb does — so `ObservedServiceState` now carries it and `observedStateFacts` branches on it.

- New facts `service_hibernated` / `service_woken` (migration `0097_hibernate_wake_event_facts`), distinct from `service_suspended` / `service_resumed`.
- The wake direction cannot read `spec.suspended` (it is false either way by the time `Running` is observed), so `service_event_checkpoints` gained a `suspended` column recording _why_ the service went down; `checkpointServiceSuspended` pins it to whatever phase `checkpointServicePhase` retains, and the column joined the UPDATE's `IS DISTINCT FROM` guard so suspending an already-sleeping service is not a lost write.
- Webhooks expose both new types (opt-in, additive). **Push notifications deliberately do not** — paging an owner on every routine idle cycle is the very false positive this task exists to remove; the split is what makes the surviving `service_suspended` push trustworthy.
- Dashboard: distinct labels ("Service went to sleep" / "Service woke up", en + zh) and distinct icons (Moon / Sunrise) rather than the suspend pause/play pair.
- Tests: `TestAutoHibernateFactsStayApartFromSuspend` (three branches: idle cycle, user cycle, and a user suspend layered on top of an existing sleep), proven red before the fix.
