# 062 — No pluralization convention: four ad-hoc schemes, and ~9 strings still render "1 variable operations"

Why: react-i18next's native plural support is available with zero configuration for English and is used **zero** times, so every feature that needs a count invents its own answer — three have, badly or verbosely, and the rest just print the plural noun.

Filed 2026-08-27, 44th `/qa-find-bugs` run, journey 4 (env vars).

## Live repro

On `qa-20260827-env` (`srv-da83k18ueu1c7395ipg0`, deleted at end of run). Service Settings → Environment → **Edit**, change one variable's value, and the unsaved-changes bar reads:

```
Unsaved environment changes
1 variable operations · 0 file operations
```

Read from the live accessibility tree, not innerText. Source: `dashboard/src/features/services/locales/en.ts:3874` — `"{variables} variable operations · {files} file operations"`, one template, no branch.

## Four schemes, none shared

1. **Hand-rolled One/Many + caller branch** — `deploys.listCountOne`/`listCountMany` and `deploys.listCountLoadedOne`/`listCountLoadedMany` (`deploys/locales/en.ts:253-270`). Four keys for two counts. This is why the Deploys tab correctly shows "1 deploy" and "20 deploys loaded".
2. **Hand-rolled singular/plural pair** — `agentSessions.metaTurn` / `agentSessions.metaTurns` (`agent-sessions/locales/en.ts:393-400`), added by `w9/m92/t006` to fix "1 turns". That task's own Steps say: _"use whatever pattern this codebase already uses elsewhere for pluralization (**if none exists yet**, a simple ternary is acceptable)"_ — so the absence of a convention was noticed, and another one-off was accepted rather than establishing one.
3. **The `(s)` escape hatch** — `projects/locales/en.ts:75`, `"{count} resource(s) in progress"`.
4. **No handling at all** — the rest.

`grep -rho '"[a-zA-Z.]*_\(one\|other\)"' dashboard/src --include="*.ts" | wc -l` returns **0**: react-i18next's built-in plural resolution (`key_one` / `key_other` with a `count` param, no config needed for English) is not used anywhere, even though `use-translations.ts` is a thin wrapper over `react-i18next`'s `useTranslation` and passes params straight through.

## Fix

Adopt react-i18next's native plurals as the one convention — `key_one` / `key_other` with `t(key, { count })` — then migrate the table above and retire the three ad-hoc schemes so the next feature has something to copy.

Two things to settle while doing it, because they are why the wrapper does not already make this obvious:

- `useTranslations`' `t` is typed `key: keyof typeof en` and its dev-mode guard warns when `!(key in en)`. With native plurals the base key does not exist in the catalog — only `key_one`/`key_other` — so both the type and the warning need to accommodate that, or the convention will look broken in dev the first time someone tries it.
- `zh` has no plural distinction, so its catalog needs only the `_other` form; do not mechanically double it.

## Resolution (2026-09-03)

Adopted i18next-native `_one`/`_other` plurals as the one convention (numeric `count`; zh gets `_other` only — one cardinal category; a two-count sentence is two pluralized keys composed at the call site; a formatted count passes a second `{formatted}` display param). Wrapper dev-guard now accepts plural base keys and instead warns when one is called without a numeric count; locale-parity + keys-exist tests enforce the en pairing and the zh single-form shape; `src/i18n/__tests__/plurals.test.ts` is the copyable reference and the convention is documented in dashboard/CLAUDE.md §i18n. All ~9 wrong strings migrated (incl. the live '1 variable operations' bar, split into two composed keys), and all the ad-hoc schemes retired: deploys' 4-key One/Many pairs, agentSessions.metaTurn/metaTurns, metrics' post-note requestCount pair, and the '(s)' hatch in projects + environments. 781 tests / 73 files green.
