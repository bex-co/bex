## Objective

Give `blueprint_syncs` a place to record why a sync errored, and thread it through the store layer that already writes the row's terminal `state`.

## Context

- `lego/backend/internal/store/blueprints.go:48-55` — the `BlueprintSync` struct has `ID, BlueprintID, CommitID, State, StartedAt, CompletedAt, CreatedAt` and no error/message field at all.
- `lego/backend/internal/store/blueprints.go:229-241` — `UpdateBlueprintSync(ctx, id, state string, completedAt *time.Time)` takes no error parameter; its `UPDATE blueprint_syncs SET state = $2, completed_at = $3` never touches such a column because none exists.
- Confirmed via live GraphQL introspection (`__type(name: "BlueprintSync")`) that the API schema has no error field either — this is a store-layer gap, not a resolver oversight.
- Both write call sites already compute the real error and then throw it away before calling `UpdateBlueprintSync`:
  - `lego/backend/internal/apps/blueprint.go` inside `CreateBlueprint` (~line 447-459): `applyErr` from `s.deployParsedStack(...)` is used only to pick `syncState`/`finalStatus`, then `_, _ = s.Blueprints.UpdateBlueprintSync(ctx, run.ID, syncState, &completedAt)` discards it.
  - `lego/backend/internal/apps/blueprint.go` inside `runSync` (~line 655-676), reached by both `SyncBlueprint` (manual REST/GraphQL/MCP sync) and `triggerBlueprintSync` (webhook auto-sync, `blueprint.go:686-700` — its own comment says "Errors are intentionally dropped (webhook already responded)", conflating "don't block the webhook response" with "never persist it anywhere"): identical `applyErr` → `syncState` → discard pattern.
- Existing migrations for this table: `0016_blueprints.up.sql` (creation), `0059_blueprint_git_connection.up.sql`, `0068_blueprint_render_yaml_default.up.sql` — none add an error column.

## Steps

1. Add a migration (next free number after `0068`) adding a nullable `error_message TEXT` column to `blueprint_syncs`.
2. Add `ErrorMessage *string` (or `sql.NullString`, matching this file's existing convention) to the `BlueprintSync` struct.
3. Change `UpdateBlueprintSync`'s signature to accept an optional error string (e.g. `errMsg *string`) and include it in the `UPDATE` statement and `RETURNING` scan.
4. Update both call sites in `blueprint.go` to pass `applyErr.Error()` (as a pointer, or `nil` on success) instead of discarding it. For `triggerBlueprintSync`, this is the one place the error becomes durably visible at all — it must still not block or fail the webhook's HTTP response, only persist alongside the state write that already happens there.
