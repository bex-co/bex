## Objective

Make the workspace's Cmd+K global search actually narrow results for a realistic short query, instead of returning most/all of the workspace's resources because cmdk's bundled fuzzy scorer treats a subsequence match against a resource's semi-random ID as relevant.

## Context

- `dashboard/src/common/components/dashboard-layout/global-search-dialog.tsx:146-259` — every `CommandItem` (projects, services, databases, keyValues, envGroups) sets `value={`${name} ${id} ${type}`}`. `CommandDialog`/`Command` (`dashboard/src/common/components/ui/command.tsx:9-34`) pass all props through to cmdk's `CommandPrimitive` with no `filter` override and no `shouldFilter={false}` — so cmdk applies its default `command-score` fuzzy/subsequence scorer against that full composite string.
- **Root cause, confirmed live** in the real production workspace: because the composite `value` includes each resource's ~20-character near-random ID (e.g. `prj-d9dgeo0bd9nc73a0vh1g`), a short query has a high statistical chance of subsequence-matching _some_ resource's ID even when it has nothing to do with that resource — measured directly:
  - `redis` (5 chars, low collision odds) → 2/2 correct results.
  - `forum-db` (8 chars, hyphenated) → 3 correct + 2 false positives (`blockeden-forum-redis`, `forums` Project).
  - `cms` (3 chars) → 2 correct (`beancount-cms-v2`, `eden-cms-v2`) drowned in 7 unrelated results (`tianpan-forum-db`, `beancount-forum-redis`, `blockeden-forum-redis`, `beancount-forum-db`, `blockeden-forum-db`, plus 2 more).
  - `db` (2 chars) → 3 correct drowned in 9 total, including two Projects (`bex.co`, `beancount.io`) and a Key Value with `db` nowhere in their name/id/type.
  - `eden` (4 chars, a real word appearing in two service names) → returned literally every resource in the workspace (6/6), including `bex.co`/`beancount.io` Projects whose name+id+type contain no `d` at all in a position that could plausibly subsequence-match.
  - Control: `zzznonexistentxyz999` (nonsense, no real subsequence anywhere) correctly returned zero results — confirming the filter _runs_, it's just far too permissive for realistic short/common queries.
- **Existing correct precedent in this exact codebase** — `dashboard/src/common/components/ui/combobox.tsx:244` sets `<Command shouldFilter={false}>` and does its own explicit case-insensitive substring match at lines 63-71 (`option.label.toLowerCase().includes(search) || option.value.toLowerCase().includes(search)`). This is the pattern to mirror, not new design.
- **Prior art, same symptom, different mechanism**: `w9/m92/t002` (`.pm/w9/done/m92/`) already fixed the Agents sidebar session search for the identical "search doesn't narrow" complaint — but that box uses a hand-rolled `fuzzyMatch`/`matchQuality` (`dashboard/src/features/agent-sessions/lib/mention.ts:77-93`), not cmdk. Confirmed via `grep`: cmdk's `Command`/`cmdk` import is used in exactly one place in the dashboard — `global-search-dialog.tsx`. This is not a regression of `w9/m92` and does not touch its files; it's an independent, never-audited instance of the same lesson at a different code layer.
- **Consumer check**: the ID is baked into `value` for a real reason — a user who has a resource's raw id (from a log line, CLI output, etc.) can currently find it by pasting the id fragment. The fix must preserve that, not just strip id/type out of `value`.

## Steps

1. Set `shouldFilter={false}` on the `Command`/`CommandDialog` in `global-search-dialog.tsx` (or pass a custom `filter` prop doing the equivalent), matching `combobox.tsx`'s pattern.
2. Compute filtered result lists explicitly with case-insensitive substring matching against the same composite text already used (`name`/`id`/`type`), preserving id-search.
3. Verify `CommandEmpty` (`common.topbarSearchEmpty`) still renders correctly when a substring genuinely matches nothing.
