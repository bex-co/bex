## Objective

A brand-new service's very first deploy can be closed as `Canceled` by bex-api even though nothing ever superseded it and no user clicked Cancel — the build never even starts. Find and fix the mechanism so a first-ever deploy only reaches `Canceled` when something genuinely superseded it.

## Context

- Live repro: created `qa-20260822-worker` (`background_worker`, Node runtime, repo `bex-co/bex` root `examples/hello-node`) via the dashboard, no env vars/secrets set, single "Deploy Service" click. Its only deploy `dep-da56pr0aj4rs73a8bnu0`:
  - Deploy log: `08:45:48 PM ==> Build queued` then `08:46:31 PM ==> Deploy canceled` — no build ever started, no compile output between those two lines.
  - Events tab: `Deploy started (First build)` → `Build started` → `Build ended: Canceled` → `Deploy ended: Canceled`, all ~43 seconds apart, all `now`/`1m` timestamps (i.e. genuinely this run, not stale data).
  - I never clicked Cancel, never triggered a second deploy, never pushed to the repo.
- Confirmed this is a BACKEND-persisted inconsistency, not client cache staleness: after a genuine full-page reload (`page.goto`, fresh Apollo cache), a direct GraphQL probe still returned:
  ```
  query Server($id: String!) { server(id: $id) { phase ... } }
  {"data":{"server":{"phase":"Building", ...}}}
  ```
  — `phase: "Building"` persisted well past the deploy's own `finishedAt`, even though the deploy list for the same service showed `status: "Canceled"` with a real `finishedAt`.
- Code: `lego/backend/internal/store/reconciler.go:917-929` (`supersededDeployStatus`):
  ```go
  if app.Status.ReleaseGeneration > 0 && open.Generation != 0 && app.Status.ReleaseGeneration > open.Generation {
      return DeployCanceled, true
  }
  ```
  This closes an open deploy row `Canceled` whenever the App's reported `ReleaseGeneration` has moved PAST the row's own stamped generation — the row-supersedes-row bookkeeping for a genuinely newer trigger (a push, an env-var redeploy). `lego/operator/internal/controller/release_identity.go:301-302`:
  ```go
  if app.Status.ReleaseGeneration == 0 {
      app.Status.ReleaseGeneration = app.Generation
  }
  ```
  initializes `ReleaseGeneration` from the CURRENT `app.Generation` (Kubernetes' built-in spec-generation counter, bumped by ANY spec-mutating write) the first time it's read as zero — not necessarily the generation the deploy row itself was opened against. If any spec-mutating write touches the App between the deploy row's creation (bex-api, generation N) and this initialization (operator, possibly reading generation N+1 or later), `ReleaseGeneration` ends up ahead of `open.Generation` and the row above fires — manufacturing a "supersede" for a release that was never actually replaced.
- **Unverified this run** — do not re-guess, reproduce first: which specific second spec-mutating write bumps `app.Generation` between deploy-row creation and this initialization, for a bare first-time create with zero env vars/secrets/settings touched. Candidates not yet read: does the operator itself ever write back to `.spec` (e.g. stamping a resolved image tag) as part of normal reconciliation before `ReleaseGeneration` is first set? Does bex-api's own create flow issue more than one spec-mutating write (`materializeNewApp`'s clone-secret/registry-secret provisioning steps modify `a.Spec.CloneSecret`/similar BEFORE the initial k8s object create — if the App is created once with a placeholder and PATCHed with the resolved secret name, that's a second generation right there)?

## Steps

1. Write an integration test: create a service via `Service.Create`, capture the returned App's `Generation` immediately (call it N), then drive the store's reconciler/projector through a simulated first reconcile and assert `app.Status.ReleaseGeneration` never exceeds N (or whatever the deploy row's own stamped `Generation` is) — reproduce the bug in test form.
2. Once reproduced, log or step through exactly which write bumps `app.Generation` between create and the operator's first `ReleaseGeneration` read. Check `materializeNewApp`'s clone-secret (`ensureCloneSecret`, `service.go:1872-1878`) and registry-pull-secret provisioning steps specifically — if either PATCHes the App's `.spec` (not just creates a Secret object) after the initial `a.Spec = desired; ...Create(a)`, that is a second generation for a request that looks like one create to the caller.
3. Fix by either (a) not issuing a second spec-mutating write before the first reconcile settles, or (b) making the deploy row's `Generation` stamp and `ReleaseGeneration`'s first-read snapshot share the same atomic point of truth, so a legitimate pre-first-reconcile spec patch is never mistaken for a user-triggered supersede.
4. Confirm the existing, deliberate supersede case (`w2/done/018.md`'s "Resolved 2026-08-16" push-cadence-faster-than-build scenario) still works correctly after the fix — that regression must not regress.
