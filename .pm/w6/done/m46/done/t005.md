## Objective

The dashboard's Service header status/phase pill can get stuck indefinitely — observed stuck on "Building" for 10+ minutes past when the deploy actually closed as `Canceled` — because the client only refreshes that query in response to a LOCAL user-triggered mutation. `w6/m45` t003 already fixed this for the Cancel/Rollback BUTTON case (`deploy-actions.tsx`'s `refetchQueries` now includes `"Server"`), but a server-driven status change — this milestone's `t004` bug, or any other backend-initiated transition — never triggers a refetch at all, because no local mutation ever fires.

## Context

- Live repro (`t004`'s incident): the deploy closed itself (`Deploy ended: Canceled`) with zero local user action — no button click, nothing in the browser triggered a GraphQL mutation. The `Server` query (`operationName: "Server"`, requested fields include `phase`) is only re-fetched by Apollo when something in the app calls `refetchQueries` or the query's own poll interval elapses. Confirmed via a genuine full-page reload (fresh Apollo cache, not just a stale in-memory cache) that the API itself — not just the client — kept returning `phase: "Building"` well after the deploy's `finishedAt`. Once `t004` fixes the backend to stop reporting the wrong terminal phase, THIS bug is still live for any other timing gap between a deploy's real status change and the next time something causes the Service header to refetch.
- This is broader than `w6/m45` t003's fix: that one is scoped to the Cancel/Rollback button's own mutation call. This bug has no local mutation to hook a refetch onto at all — it needs either a shorter/active poll interval on the `Server` query while a deploy is in a non-terminal state, or a subscription/live-update mechanism, or at minimum a refetch keyed off the `Deploys` query's own poll noticing a status change (the deploys list DOES update correctly and promptly — only the header pill lags).

## Steps

1. Locate the `Server` query's current fetch policy on the service detail page (dashboard route showing the header) — confirm whether it polls at all today, and at what interval, versus `Deploys`'s polling.
2. Add either: (a) a poll interval on `Server` while any deploy for the service is in a non-terminal status, stopped once terminal; or (b) a refetch of `Server` triggered whenever the `Deploys` query (which does poll/update promptly) observes the latest deploy's status change to a terminal value — whichever fits the existing data-fetching architecture with the least duplication.
3. Write a test (component/integration level, mocking a deploy transitioning to a terminal status with no local mutation involved) asserting the header status renders the new terminal state within one poll cycle, with no manual reload.
4. Live-verify: create a service, force it into the `t004` scenario (or any other server-driven terminal transition available in a test/staging path) and confirm the header updates without a reload.
