Proof: the local cluster's own `kratos-public`/`hydra-public` Ingress objects are bound to `auth.bex.local`/`oauth.bex.local` only (`kubectl -n auth get ingress` on `infra/local/bex.kubeconfig`), yet `curl https://auth.bex.co/self-service/registration/api` returns a live, valid Kratos flow — that traffic is not reaching this cluster's Traefik at all. The real `dashboard.bex.co` is a **separate production deployment** this session has no `kubectl` access to. This matches `w6/done/m5/t003.md`'s own 2026-07-11 retarget note ("target the rebuilt live prod stack... at dashboard.bex.co ... Kratos/Hydra/OpenFGA/control-plane Postgres are live and verified there") — t002/t003/t004 below follow that same established precedent and verify against real prod over HTTPS (browser + REST), not via `kubectl`.

The local mock cluster was still useful this session: it's where the `BEX_KRATOS_ADMIN_URL` bug (below) was diagnosed and where the fix was validated end-to-end before being written back to source.

## t001 evidence — local stack + bug found and fixed

- Regenerated `infra/local/bex.kubeconfig` (`clusterctl get kubeconfig bex`, gitignored, not committed) — the CAPD cluster's containers were already up (6+ days uptime) but the kubeconfig file was absent from this checkout.
- Confirmed all backing services reachable from `bex-api`'s own namespace via a throwaway debug pod (`curlimages/curl`, deleted after use): OpenFGA `:8080/healthz` → 200, OpenBao `:8200/v1/sys/health` → 200, Hydra admin `:4445/health/alive` → 200, CP Postgres (`bex-db-rw`) reachable via `psql`.
- **Bug found:** `curl kratos-admin.auth.svc:4434` (bex-api's actual configured `BEX_KRATOS_ADMIN_URL`) **timed out** (curl exit 28) — the `kratos-admin` Service only exposes port **80** (→ `targetPort: http-admin`, container port 4434), not 4434 directly. `kratos-public`'s equivalent env var (`BEX_KRATOS_URL=http://kratos-public.auth.svc:80`) correctly uses port 80, proving the repo's own convention — `BEX_KRATOS_ADMIN_URL` broke it. Root-caused to commit `e6c74046` ("owners/members identity lookup", Jul 9) — **broken since the day the env var was introduced**, never exercised/noticed until this session's debug-pod test. This silently disables Kratos email enrichment everywhere it's used (the owners API and, per m10, the Team page) whenever `BEX_KRATOS_ADMIN_URL` is set — despite requests looking "configured", every one fails closed with an empty/omitted email, indistinguishable from `BEX_KRATOS_ADMIN_URL` being unset at all.
  - **Fixed in source:** `lego/operator/config/api/deployment.yaml` — `http://kratos-admin.auth.svc:4434` → `http://kratos-admin.auth.svc:80`.
  - **Live-validated on the local cluster:** `kubectl -n bex-system set env deploy/bex-api BEX_KRATOS_ADMIN_URL=http://kratos-admin.auth.svc:80` + rollout; confirmed the pod restarts healthy and the URL now resolves (debug-pod curl → 200).
  - **Not yet deployed to real prod** — no push/deploy credentials this session; see the residual note below.
- **Second bug found** (surfaced by t002's live delete test, root-caused here): the `bex-api` ClusterRole (`lego/operator/config/api/rbac.yaml`, `api-role`) has RBAC rules for `apps` and `databases` but was **never granted `keyvalues`** when w6/m4 added the `KeyValue` CRD/purger — `keyvalue.WorkspacePurger.PurgeWorkspace` calls `Client.List` on `keyvalues.app.bex.co`, which 403s for the `bex-api` ServiceAccount. Since `workspaces.Service.Delete`'s purger loop (`lego/backend/internal/workspaces/service.go:480`) aborts and surfaces the first purger error, and `keyvalue.WorkspacePurger` is wired **last** in `cmd/api/main.go`'s `WorkspacePurgers` slice (after `secrets` and `postgres`), a workspace delete on real prod today reports a hard failure to the user even though the tenant row, OpenFGA tuples, and OpenBao secrets are *already* correctly torn down by the time the error fires.
  - **Fixed in source:** added matching `keyvalues`/`keyvalues/status` rules to `api-role`, mirroring the existing `databases` rules exactly.
  - **Live-validated on the local cluster:** `kubectl auth can-i list/delete keyvalues.app.bex.co --as=system:serviceaccount:bex-system:bex-api` → `yes` (was implicitly `no` before the patch — 403 confirmed live by t002's real-prod delete, see below).
  - **Not yet deployed to real prod.**

## t003 evidence — OpenBao tenant-secrets purge (real prod)

Driven via `curl` directly against `https://api.bex.co`/`https://auth.bex.co` (no browser needed) — two fresh scratch Kratos identities (`m11-openbao-verify-a-*@example.com`, `-b-*`), each auto-provisioned into its own single workspace (renamed `m11-openbao-a` / `m11-openbao-b`), avoiding a real ambiguity found along the way: `tenantService.Tenant()` resolves an identity's current workspace via a plain `tenant_members` join with no `ORDER BY`/deterministic tie-break, so one identity with two workspaces has no reliable way to target the second one over REST. (`Authorization: Bearer` is Hydra-OAuth2-only on this API — a Kratos session must go over `X-Session-Token`, not `Bearer`; noted since the original task brief assumed otherwise.)

1. **Created `m11-purge-test`** (`private_service`, `nginx:alpine`) in workspace A — `POST /v1/services` → 201, `ownerId` correctly stamped to A's tenant id.
2. **Set + read back an env var:** `PUT .../env-vars {"PURGE_CHECK":"leaked-if-not-purged-<random>"}` → 200; `GET .../env-vars` → 200, value present.
3. **Deleted workspace A** (`sudo delete workspace m11-openbao-a`) — hit the same known `keyvalues.app.bex.co is forbidden` error from t001/t002 (expected — real prod doesn't have the RBAC fix yet). Confirmed the tenant row itself was gone regardless: `GET /v1/owners/{id}` as A → 403.
4. **Attempted the literal black-box re-read** (create the same-named service in workspace B, read its env vars — if the old value leaked through, the purge hadn't fired): blocked by a **second, separate, real bug** — see below. `POST /v1/services` (same name, workspace B) → 403 forbidden, not 201.

**PASS, via strong indirect evidence**, even though the literal re-creation step was blocked: `workspaces.Service.Delete`'s purger loop (`service.go:480`) aborts and returns on the **first** purger error; the composition root (`cmd/api/main.go:224`, pre-fix ordering) wires `Purgers` as **`secrets` (OpenBao) → `postgres` → `keyvalue`**; and the error actually returned both times was specifically about `keyvalues.app.bex.co` — the **last** purger in that list. Since the loop is strictly sequential and stops at the first failure, seeing the keyvalue-stage error is direct evidence the secrets (OpenBao) and postgres purgers upstream of it both returned `nil` — the OpenBao purge genuinely ran and succeeded on real prod before the (separately-tracked) keyvalue RBAC gap aborted the chain.

**Third bug found (serious) — orphaned Apps from the public create path never get cleaned up:** `apps.Service.create()` (`lego/backend/internal/apps/service.go:452-456`, the single code path `POST /v1/services`/GraphQL `createService`/MCP `create_web_service` all share) stamps a created App CR with `core.LabelTenant` only — **never** `store.LabelManagedBy`. The control-plane reconciler's orphan-prune sweep (`internal/store/reconciler.go:134-136`) lists prune candidates filtered **by `LabelManagedBy`**, so a publicly-created App is structurally invisible to it; when its owning workspace is deleted, nothing ever prunes the CR. It survives — still running (billable Deployment/Service/pod) — and becomes **permanently unreachable**: `core.Base`'s tenant gate (`base.go:255`) now forbids everyone, including its own creator, because its `LabelTenant` names a tenant that no longer exists. It also permanently squats its name platform-wide (all Apps share one k8s namespace). Confirmed live: `m11-purge-test` (created in step 1 above) is now stuck in exactly this state — `GET .../env-vars` as A → 403, as B → 403, `GET /v1/services/m11-purge-test` as A → 403, `DELETE` as A → 403. **This resource is still live on real prod and could not be cleaned up from this session (no API path grants access to it anymore, and no `kubectl` access to real prod). A maintainer needs to `kubectl delete app m11-purge-test -n default` (or the real tenant-apps namespace) directly against the production cluster.**
  - **Fixed in source:** added `lego/backend/internal/apps/purger.go` (`apps.WorkspacePurger`, mirroring the existing `postgres`/`keyvalue`/`secrets` purgers exactly — lists+deletes App CRs by `core.LabelTenant`) and wired it into `cmd/api/main.go`'s `WorkspacePurgers` slice. Safe to run alongside the existing row-backed cascade/reconciler path for row-backed Apps (deleting an already-pruned object is a no-op); its only observable effect is catching the Apps that path never reached.
  - **Tested:** `lego/backend/internal/apps/purger_test.go` — deletes only the given tenant's Apps, explicitly covers an App with no `LabelManagedBy` (the exact regression case), no-op on an unowned/already-purged tenant. `go build ./... && go vet ./... && go test ./...` all green.
  - **Not yet deployed to real prod** — same as the other two fixes below; needs `/ship`.

**Cleanup state:** both workspaces A and B confirmed deleted (`GET /v1/owners/{id}` → 403 for both identities post-delete). The orphaned `m11-purge-test` App/Deployment/pod is **not** cleaned up — flagged above, needs cluster-admin action.
