## Objective

Walk every surface a saved plan reaches and compare it with render.com.

## Steps

1. REST `PATCH /v1/services/{id}` and `GET /v1/services/{id}`: which plan `serviceDetails.plan` reads after a save and before the deploy, against Render's API reference.
2. MCP `update_service` (a bex extension; Render's MCP has no update tool) and `get_service`.
3. GraphQL and the dashboard: the Compute page and the service header while a plan is saved and not deployed, and the undeployed-changes banner. Render's dashboard deploys a plan change, so a pending plan reaches the dashboard only through the API.
4. The pinned CLI's `services update`, if it takes a plan.
5. File each drift as its own w6 inbox note.

## Acceptance criteria

- [x] Each surface's behavior is recorded here with its Render source, and every drift is filed.

## Done (2026-11-24)

Walked on production (pin `ff5de0a130e6`) as the QA user in `bex-canary`, on `w6-m609-plan` (`srv-dc2j64sb6mms7391k8ug`, disposable) with Standard saved over a running Starter (t005 step 3):

1. **REST.** `PATCH /v1/services/{id}` answers 200 with `serviceDetails.plan: standard`, and `GET` reads `plan: standard`, `undeployedChanges: true`, `undeployedChangesReason: saved`. No deploy opens and the service's events record `plan_changed` starter → standard at the save. Render: "The Update service endpoint does _not_ trigger a new deploy", and "your service's compute plan does not change until the first successful deploy after you update it" ([render.com/docs/compute-plans](https://render.com/docs/compute-plans)). The `plan` field is the setting the PATCH wrote, as every saved Update Service field reads back (ADR018's w8/m135 paragraph); Render documents no separate running-plan field, and bex keeps the running plan internal (`status.servedTier`, read by billing). No drift.
2. **MCP.** `update_service` is a bex extension that follows REST: Render's MCP server has no update tool (`lego/backend/internal/api/openapi/render-mcp-tools.json`). `get_service` reads `plan: standard`, `undeployedChanges: true`, reason `saved`, as REST does. No drift.
3. **GraphQL and the dashboard.** `service { plan undeployedChanges }` reads `standard` / `true`. The service header and the Compute section show "1c-2g Standard", under the banner "Saved changes aren't live yet. Use a standard deploy to apply them." Render's dashboard deploys a plan change at once (compute-plans, Dashboard tab: "Render automatically triggers a deploy to apply the new compute plan"), so it has no pending-plan state of its own; the banner is bex's undeployed-changes notice for every saved field (w8/m135). Unverified: what Render's dashboard shows for a plan saved through its API before the deploy, which needs a Render account this run did not have. No drift filed.
4. **The pinned CLI.** `services update --plan` sends `PATCH /v1/services/{id}` with `serviceDetails.plan` and prints "Updated this service" with the PATCH's answer (`render-oss/cli` `cmd/serviceupdate.go`, pinned in `lego/cli/go.mod`), so it saves the plan with no deploy, as REST does and as Render's API does. No drift.
5. No drift found, so nothing filed.
