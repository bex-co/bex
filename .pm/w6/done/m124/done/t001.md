## Objective

The deploy row's terminal `build_failed` status is derived from the App reaching `PhaseFailed`. `t002` stops a serving service from reaching that phase, so this derivation must move to the Build condition first — otherwise `t002` trades a wrong service status for a wrong deploy status.

## Context

- `lego/backend/internal/store/reconciler.go:1027-1031`:

  ```go
  case appv1alpha1.PhaseRunning:
      if releaseIsActive(open, app) { return DeployLive }
  case appv1alpha1.PhaseFailed:
      if conditionCurrent {
          switch {
          case appv1alpha1.IsBuildFailureReason(reason): return DeployBuildFailed
  ```

- The right source already exists and is durable: `r.fail` sets `ConditionBuild` separately at `lego/operator/internal/controller/app_controller.go:3920-3926`, attributed to the **release** generation that actually built rather than `metadata.generation` (`w6/m100` — read that milestone's reasoning before touching generation handling).
- `reconciler.go:1209` also keys off the phase (`if app.Status.Phase == appv1alpha1.PhaseFailed && c.Message != ""`) to source the failure message; it needs the same treatment or the message disappears when the phase changes.
- `reconciler.go:81` notes an existing precedent that the phase is not the whole story: an ImagePullBackOff "never makes the App CR's own phase machine reach PhaseFailed — it polls PhaseDeploying".

## Steps

1. Derive the terminal build verdict from `ConditionBuild` (+ its `ObservedGeneration`) rather than from `Status.Phase`.
2. Keep the existing generation-currency check — a stale condition must not settle a newer deploy (that is what `conditionCurrent` guards today).
3. Do the same for the failure-message lookup at `:1209`.
4. Verify the deploy row still reaches `build_failed` **before** `t002` lands, so the two changes can be reasoned about independently.

## Files

## Acceptance criteria

- [ ] A failed build still produces `build_failed` on the deploy row, with the phase unchanged (pre-`t002` state).
- [ ] The failure message still resolves.
- [ ] A stale Build condition does not settle a newer deploy.
- [ ] `live` / `canceled` / `deactivated` derivations are untouched.

## Out of scope

- Changing the phase itself — that is `t002`, and it depends on this landing first.
