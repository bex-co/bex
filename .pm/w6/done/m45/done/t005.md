## Objective

Check that t001-t004's fixes are consistent across every surface they touch: REST, GraphQL, and MCP in `lego/backend/` (same fields, semantics, error shapes) and the `dashboard/` UI. Compare against render.com's equivalent behavior and flag any drift as follow-up work rather than silently diverging.

## Context

- t002 changes env-var visibility, which is read/written identically across REST, GraphQL, and MCP (`docs/ADR006-bex-api.md`) — confirm all three now see a creation-time env var, not just the GraphQL path this hunt exercised.
- t001 (native build PATH) and t003/t004 (dashboard-only) have a narrower surface — confirm whether they need REST/GraphQL/MCP checks at all and note why if not.

## Steps

1. For t002: verify REST `GET /v1/services/{id}/env-vars` (or equivalent) and MCP's env-var read tool also see a creation-time var, not just GraphQL `envVars`.
2. For t001: confirm the CLI / REST create-service path (not just the dashboard form) produces the same fixed Dockerfile behavior.
3. Record any Render-behavior divergence found along the way in `docs/ADR018-render-parity.md`.

## Outcome

1. **t002 — REST, GraphQL and MCP all see a creation-time env var.** Verified by construction and by test. All three read surfaces delegate to the same `secrets.Service` methods — REST `GET /v1/services/{id}/env-vars` → `ListEnvVarsPage`/`ListEnvVars` (`secrets/rest.go:80`), GraphQL `envVars` → `ListEnvVarsPage` (`secrets/graphql.go:171`), MCP `list_env_vars` → `ListEnvVarsPage` (`secrets/mcp.go:121`) — reading the same OpenBao path the new create-time seeder writes. `TestCreationTimeEnvVarIsVisibleOnEverySecretsReadSurface` (`secrets/files_test.go`) drives all three against a store seeded only by `PrepareCreateSecrets` and asserts each returns the var. The **write** side is covered symmetrically: `TestCreationTimeEnvVarsReachTheSecretsStoreOnEverySurface` (`apps/create_payload_test.go`) proves the REST, GraphQL and MCP create payloads all hand their literals to the seeder.

2. **t001 — the CLI/REST create path produces the identical Dockerfile.** No per-surface work needed, and none was done. The Dockerfile is generated by the **operator** from the App CR (`build.nativeDockerfile`, keyed on `spec.builder`/`spec.runtime`), never by an API adapter — every create surface (dashboard form, REST, GraphQL, MCP, official CLI, blueprint) converges on the same CR, so `shellJSON`'s login-shell fix reaches all of them through one code path. `TestNativeDockerfileKeepsToolchainPATH` iterates every runtime in `nativeRuntimeImages` rather than the one the dashboard happened to select.

3. **t003/t004 — dashboard-only, no API surface.** `refetchQueries` and the deploy-header separator are Apollo/JSX concerns with no REST/GraphQL/MCP counterpart; the queries they refetch (`Server`, `Deploys`, `ServiceEvents`) are unchanged.

4. **Divergence recorded in `docs/ADR018-render-parity.md`:** a new **Gap backlog** row for the missing New-Service-wizard runtime auto-detect (t004 item 2 — Render infers the repo's language, bex statically defaults to Node), and the § Environment & config "Env vars" row now documents the creation-time fix plus the deliberate Blueprint carve-out (manifest-owned `envVars:` stay on `spec.Env` because a sync re-applies them; that is what `sync: false` exists to opt out of).
