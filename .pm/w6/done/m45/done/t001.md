## Objective

Native-runtime builds (`spec.builder` native, selected via the New Web Service form's Runtime picker) fail for Go with `go: command not found`, despite pulling the official `golang:1.24-bookworm` image whose `ENV PATH` includes the Go toolchain. Fix the wrapper that is discarding that `PATH` so Go (and Rust, which shares the same class of bug) actually build.

## Context

- Live repro: created `qa-20260822-hello-go` (Runtime=Go, root dir `examples/hello-go`, repo `bex-co/bex`) via the dashboard. Build log (`dep-da54mplau1bs73c6rpt0`):
  ```
  #10 [stage-0 4/4] RUN --mount=type=secret,id=render-env,... ["/bin/bash","-lc","... go build -o app ."]
  #10 0.081 /bin/bash: line 5: go: command not found
  #10 ERROR: process ... did not complete successfully: exit code: 127
  ```
- Root cause: `lego/operator/internal/build/native.go:110-116` (`shellJSON`) wraps both the build `RUN` step (`native.go:92-97`) and the start-command `CMD` (`native.go:104-107`) in `["/bin/bash","-lc", command]`. `-lc` makes bash a **login shell**, which sources Debian's `/etc/profile` — this resets `PATH` to the fixed system default (`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`), discarding the toolchain image's `ENV`-configured `PATH` (`golang:1.24-bookworm` adds `/usr/local/go/bin`; `rust:1-bookworm` adds `/usr/local/cargo/bin` — neither is on the Debian default).
- Control case, live-verified: `qa-20260822-hello-py` (Runtime=Python 3, same repo/mechanism) built and deployed successfully; `curl https://qa-20260822-hello-py.onbex.co/` returned the expected body. Python (and node, ruby) survive only because their interpreter binary lives at `/usr/local/bin/...`, which **is** on the reset default `PATH` — coincidence, not design.
- `nativeRuntimeImages` (`native.go:46-53`): `elixir`, `go`, `node`, `python`, `ruby`, `rust` all share the one `shellJSON` wrapper.
- Unverified this run: Rust was not independently deployed (no example app in this repo) — reasoned broken by the same PATH-outside-default-profile argument, not empirically confirmed. Elixir is reasoned as likely unaffected (official image symlinks `erl`/`elixir`/`mix` into `/usr/local/bin`) but also not empirically confirmed.

## Steps

1. Change `shellJSON` (`native.go:114`) to a non-login shell (`/bin/bash -c`) — or, if login-shell semantics are needed for some other reason, re-export `PATH` after `/etc/profile` runs — so the RUN and CMD steps keep the toolchain image's PATH.
2. Deploy a Go service from a public repo (reuse `examples/hello-go`) end to end: build succeeds, reaches Live, `.onbex.co` URL serves (curl-verify, not just dashboard status).
3. Deploy a Rust service end to end the same way (add a minimal `examples/hello-rust` if none exists, or use an existing public Rust hello-world with an explicit root dir) — confirm it also now builds and serves.
4. Deploy or re-verify Elixir, Node, Python, Ruby native builds still succeed after the change (regression — they must not have been relying on login-shell-only behavior).

## Verification (2026-08-22)

The fix is one character (`-lc` → `-c`, `native.go` `shellJSON`), so the evidence
that matters is that the operator's own generated Dockerfile now builds. Both
runtimes were driven through real Docker/BuildKit against the digest-pinned
toolchain images, using the exact bytes `nativeDockerfile` emits:

| runtime | pre-fix (`-lc`) | post-fix (`-c`) |
| --- | --- | --- |
| go (`examples/hello-go`) | `/bin/bash: line 5: go: command not found`, exit 127 — byte-identical to the production build log in Context | image built; `curl` → `qa-m45-marker` (the `MESSAGE` env var), container log `hello-go listening on 10000` |
| rust (`examples/hello-rust`) | `/bin/bash: line 5: cargo: command not found`, exit 127 | image built; `curl` → `qa-m45-rust`, container log `hello-rust listening on 10000` |

Rust was only *reasoned* broken when this task was filed — now empirically
confirmed, with the same error and exit code as Go. The `CMD` wrapper is
exercised too: both containers were started by the generated
`CMD ["/bin/bash","-c",...]`, so the fix is proven on the start-command path,
not just the build one.
