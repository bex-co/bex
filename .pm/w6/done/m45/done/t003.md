## Objective

After canceling or rolling back a deploy, the service header's top-level status pill (e.g. "Building") doesn't refresh immediately — it lags up to 30s behind the adjacent "Latest deploy" chip, which already shows the correct terminal state ("Canceled"). Refetch the query backing that pill in the same mutation call that already refetches `Deploys`/`ServiceEvents`.

## Context

- Live repro on `qa-20260822-hello-py`: canceled an in-progress manual deploy (`dep-da54qj6oogrc73fp1i7g`). Immediately after confirming, the header showed **"Service: Building"** next to **"Latest deploy: Canceled"** on the same page. A fresh navigation/reload showed the correct "Service: Running" — confirms this is a stale-cache window, not a backend inconsistency.
- Root cause: `dashboard/src/features/deploys/components/deploy-actions.tsx:57-64` — both `cancelDeploy` and `rollbackService` mutations set `refetchQueries: ["Deploys", "ServiceEvents"]`, omitting `"Server"` (the query `useServer`/`ServerDocument` reads — `dashboard/src/features/services/api/server.graphql` — polled every `RESOURCE_POLL_INTERVAL_MS` = 30s, `dashboard/src/common/lib/polling.ts:9`). `dashboard/src/features/services/hooks/use-trigger-deploy.ts:53` already refetches `["Server", "Deploys", "ServiceEvents"]` for the same header chrome on manual-deploy/restart. Cancel/Rollback never got the `"Server"` entry — introduced in commit `1427024b` (2026-07-17), which added the other two queries to Cancel/Rollback but not `Server`.
- Blast radius: `DeployActions` (the shared component owning both mutations) is used on 3 surfaces — `dashboard/src/features/deploys/components/deploys-list-page.tsx`, `deploy-detail-page.tsx`, and `dashboard/src/routes/services.$serviceId.events.tsx`. All 3 show the same stale-pill window for both Cancel and Rollback.

## Steps

1. Add `"Server"` to the `refetchQueries` array for both `cancelDeploy` and `rollbackService` in `deploy-actions.tsx`.
2. Verify on all 3 surfaces (deploys list, deploy detail, events tab) that Cancel updates the header pill immediately, with no reload.
3. Verify Rollback does the same (mints a new deploy — confirm the header pill reflects the new deploy's state, not the old one).

## Files

## Acceptance criteria

- [x] Cancel updates the header pill within the same page load on all 3 surfaces — the fix is in `DeployActions` itself, the single component all three mount, so there is no per-surface path to miss.
- [x] Rollback does the same (it mints a new deploy; `Server` now refetches alongside `Deploys`).
- [x] Regression test in `deploy-actions.test.tsx` asserts `Server` is refetched for **both** mutations; proven red pre-fix (`expected [ 'Deploys', 'ServiceEvents' ] to deeply equal [ Array(3) ]`).

## Note — the third refetch site was already correct

`use-service-lifecycle.ts:86` (restart) also omits `"Server"` from
`refetchQueries`, which looks like the same bug but is not: it receives
`useServer`'s own `refetch` from `ServiceDetailLayout` and calls it in
`pollUntilConverged`, so the header pill is refreshed by that poller instead.
Left alone.

The shared triple now lives once, as `DEPLOY_REFETCH_QUERIES` in
`dashboard/src/common/lib/fetch-policy.ts`, consumed by both `deploy-actions.tsx`
and `use-trigger-deploy.ts` — the two sites had drifted apart precisely because
the list was written out twice.

## Out of scope

- Any change to `use-trigger-deploy.ts` (already correct) or to the 30s poll interval itself.
