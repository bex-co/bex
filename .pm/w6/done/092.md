# Blueprint numbers past the unsigned 64-bit limit are accepted as decimals

Why: an out-of-range whole number should be refused as an invalid integer everywhere, but bex accepts it past the u64 limit while refusing the value just below it.

- **Reported by the w6/081 CMS port (2026-10-21), from running bex's compiler. Not yet reproduced in a bex test.**
  - `numInstances: 18446744073709551616` (2^64) is accepted.
  - `numInstances: 18446744073709551615` is refused as an invalid integer.
- **Likely cause:** after the u64 change (`809472bdc`), the parse falls back to a float for a whole number outside the integer range.
- **Fix:** refuse an integer-shaped scalar outside the integer range. Add a compiler test at both boundaries, then mirror it in the CMS checker.
- **Also seen in the same port:** an alias to an unknown anchor is reported at line 0, column 0. A second finding, the cron plan-list wording, is filed as w6/093.

**Done 2026-10-21.**
- **Numbers:** `blueprintScalarValue` refuses an integer-shaped `!!float` (a whole number too wide for 64 bits) as an invalid integer. At an `envVars[].value` pointer it keeps the exact digits, consistent with w8/104.
- **Anchors:** `yamlSyntaxLocation` places an unknown-anchor error at its `*name` token.
- **Tests:** `TestBlueprintWholeNumberPastUnsigned64` and `TestBlueprintUnknownAnchorIsLocated` both fail on the old compiler and pass now.
- **Gates:** Blueprint tests, vet and backend golangci-lint pass.
- **CMS checker:** it must mirror the number refusal. This is noted on w6/081's branch follow-up.
