# A control-plane roll stalls on a Hetzner capacity error until someone deletes the Machine

Why: a routine CP roll (or MHC replacement) must finish without a human. On 2026-10-29 one cx33 placement failure in fsn1 parked the roll for ~16 min, until the Machine was deleted by hand.

- **Evidence:** Machine `bex-control-plane-r2nmn` (07:43 UTC) got HCloudMachine `ServerCreateFailedIrrecoverableError`: `error during placement (resource_unavailable …) … delete the Machine to trigger a new creation attempt`. KCP waited and did not retry. The CP MHC `bex-control-plane-unhealthy-5m` (`nodeStartupTimeout` 900s) remediates through `HCloudRemediationTemplate` (a reboot), which cannot help when no server exists. After a manual `kubectl delete machine`, replacement `sdffv` was Ready in <2 min (w6/m153 t004 record).
- **Look at:** whether KCP remediation, or an MHC whose remediation is a plain Machine delete, can cover CP Machines that never get a `providerID`. Alternatives: a fallback placement (another server type or location in the HCloudMachineTemplate), or a small controller or CronJob that deletes Machines stuck in `ServerCreateFailedIrrecoverableError` with a `resource_unavailable` reason. Check etcd-quorum safety with KCP's maxSurge 1: the failed Machine never joined etcd.
- **Recurred the same day:** the w6/m153 t009 roll's Machine `bex-control-plane-zrv5d` (08:54 UTC) got the same `resource_unavailable` error for cx33 in fsn1. It was deleted by hand after ~12 min, and its replacement `kh4bq` joined. So 2 of 6 CP replacements on 2026-10-29 needed a human.
- **Expected:** a capacity blip delays a roll by minutes, then the roll completes on its own.

## Resolution — 2026-10-29

- **Premise partly wrong:** the roll does not wait for a human forever. CAPH v1.1.7 `pkg/services/hcloud/remediation/remediation.go:63-80, 229-252`: when the HCloudMachine has no providerID (the server was never created), remediation skips the reboot and sets `MachineOwnerRemediated=False` ("machine will be deleted"), so KCP deletes and recreates the Machine. The CP MHC marks such a Machine unhealthy only after `nodeStartupTimeout` (15m). Both manual deletes on 2026-10-29 came at 12–16 min, before or at that point.
- **Change:** CP `nodeStartupTimeout` 15m → 8m (`cluster.yaml`, with the reason inline). Healthy CP joins reached a Node in under 2 minutes on 2026-10-29 (`sdffv`, `kh4bq`), so 8m bounds a capacity stall at ~8–9 min without remediating a slow but healthy join. Workers keep 10m. Server-side dry-run: MHC configured, KCP unchanged (no roll).
- **Timer start (CAPI v1.13.2 `internal/controllers/machinehealthcheck/machinehealthcheck_targets.go:224-255`):** the node-startup clock runs from the latest of Machine creation, cluster infra-ready, CP-initialized and the Machine's own InfrastructureReady, the last only once it is True. A server that is never created therefore times out 8m after Machine creation. A healthy join's clock starts only at infra-ready, so 8m is generous for it.
- **Not verified live:** a Hetzner capacity failure cannot be provoked. The self-remediation path is read from CAPH source, not observed. If the next `ServerCreateFailedIrrecoverableError` on a CP Machine is not replaced within ~10 min, reopen with the Machine and HCloudRemediation events.
- **Not done:** a fallback server type or location. Placement stays fsn1/cx33, consistent with the control-plane placement group.
