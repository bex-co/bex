## Objective

Before the operator writes a pod template that rolls a disk-bearing App, it makes sure a holder pod is running on the volume's node. It removes the holder as soon as the new instance has mounted the volume there, or at once when the new instance goes to another node. Any failure to hold falls back to today's rollout, so a holder can delay a deploy by a few seconds, never block it.

## Context

- `applyServingDeployment` (`lego/operator/internal/controller/release_config_snapshot.go:736`) projects the template inside `CreateOrUpdate` and compares it with the stored one afterwards (`changed`, `:784`). A deploy, a restart (`spec.restartedAt`), a plan change and a cancel restore all go through it. The holder check needs the projected template before the write, so compute it first, then decide.
- `diskNode` (`disk.go:309`) finds the node of the serving instance (ReplicaSet-owned pods only, so the holder's Job pod is never mistaken for it). `preferDiskNode` makes the new pod prefer that node, but only as a preference.
- The App reconciles on its pods' events (`appPodRequests`), the holder's included once it carries `app.bex.co/app`.
- **When `PodReadyToStartContainers` is true, the volumes are mounted:** the kubelet waits for attach and mount before it creates the sandbox. Deleting the holder at binding alone would be safe from a detach, but the kubelet could tear the mount down before it adds the new pod. Waiting for the mount keeps the mapping and the in-use report.

## Steps

1. **Start the hold.** The App has a disk, the stored strategy is `Recreate`, the projected template differs from the stored one, and a serving instance runs on a node that is schedulable and that the new template can land on. That means the same serving pool and required terms; a plan change onto another pool skips the hold. Then:
   - create the holder Job for that node unless it exists;
   - hold the template write and requeue on the holder pod's events, plus a short `RequeueAfter`;
   - write the template once the holder pod has `PodReadyToStartContainers` on that node.
2. **Fall back.** If the holder pod is not mounted within a bound (about 10–15 s), or its create is refused (quota, admission), or the node turns unschedulable, delete the holder and write the template as today. Log the reason and count it, for example `bex_operator_disk_holds_total{result="held|fallback_timeout|fallback_refused|skipped_unschedulable|…"}`.
3. **End the hold.** Delete the holder once:
   - the new ReplicaSet's pod has `PodReadyToStartContainers` on the holder's node;
   - or the new pod is bound to another node, at once, because the volume must move and a holder there would hold it hostage;
   - or no rollout is in progress any more: the template is unchanged, the App is suspended or scaled to zero, or the App is being deleted;
   - or the holder outlived its bound. This covers an operator restart in mid-rollout. The Job's `activeDeadlineSeconds` is the last backstop.
4. **Tests.** Use fake-client or envtest tests with pod status set by hand, because envtest runs no kubelet or scheduler. Cover:
   - the hold before the write;
   - each fallback;
   - the end on the same node;
   - the immediate end on another node;
   - the cleanup when no rollout is in progress;
   - no holder for an App without a disk, for a rolling App, for an unchanged template, and for a first deploy with no instance.

   Prove the ordering test is real: write the template before the holder is mounted, and watch it fail.

## Record (2026-11-21)

- **The hook.** `applyServingDeployment` (`release_config_snapshot.go`) now keeps its write in one closure, `project`. `holdDiskThroughRollout` (`disk_holder.go`) first runs that closure on a copy of the stored Deployment and compares the templates, before `CreateOrUpdate` writes anything. A wait > 0 returns `(wait, nil)` with nothing written. `reconcileKubernetesRuntime` then requeues after it and persists the pass's status, and the holder pod's own events wake it sooner. The signature is now `(time.Duration, error)`, and its 15 test call sites changed with it.
- **Start.** A hold starts when the App has a disk, the stored strategy is `Recreate` and both templates mount the claim, the template would change, replicas > 0, and the replaced instance runs (`servingInstance`: ReplicaSet-owned, Running, not deleting). Its node must take new pods: not cordoned or being deleted, and no NoSchedule or NoExecute taint that the holder or the new template does not tolerate, `ToBeDeletedByClusterAutoscaler` included. The new template's node selector and required terms must match it (`nodeMatchesPod`). A plan change onto another pool fails that and skips the hold. The Node read goes through `APIReader`, so the manager starts no Node informer. The template is written in the pass that finds the holder pod on the node with `PodReadyToStartContainers` (or Running). A holder that already holds the volume carries a rollout that follows another (a restart during a deploy's start).
- **Fallbacks (all write the template in the same pass and delete the holder):** a refused create (`fallback_refused`), a failed, deleted or misplaced holder pod or Job (`fallback_failed`), no mount within `diskHoldMountBound` = 15 s (`fallback_timeout`), a node that is gone, cordoned or tainted (`skipped_unschedulable`), and a new template that cannot land there (`skipped_other_pool`). No running instance is `skipped_no_instance`. A read error is logged and rolls without a hold.
- **End.** On passes whose template is already written, `diskHoldEnd` deletes the holder (background propagation, with a UID precondition) on each of these:
  - a pod of the ReplicaSet whose template is the Deployment's current one has its volumes mounted on the holder's node (`mounted`);
  - such a pod is bound to another node, at once (`moved`);
  - the Deployment has settled (`settled`);
  - replicas are 0 or the template mounts no disk (`stopped`);
  - the Job finished (`finished`);
  - the holder is older than the 15-minute rollout budget (`expired`).

  `currentInstances` finds the new instance the way the Deployment controller does: by template, with `pod-template-hash` set aside. A pod of a template that a later deploy replaced never ends that deploy's hold. `cleanupDisk` (disk detached) and a restore's scale-to-zero also release the holder. An App's deletion garbage-collects it.
- **Metrics:** `bex_disk_holds_total{result}` and `bex_disk_hold_ends_total{reason}`. They are named without the task's `bex_operator_` prefix, which no operator metric uses.
- **Tests (fake client, pod status set by hand):** `TestDiskHoldWritesTheTemplateOnlyOnceTheHolderHasTheVolume`, `…EndsOnceTheNewInstanceHasTheVolumeOnItsNode`, `…EndsAtOnceWhenTheNewInstanceIsBoundElsewhere`, `…CarriesThroughARolloutThatFollowsAnother`, `…FallsBackWithoutBlockingTheRollout` (refused, timeout, failed pod, cordoned before and during, the autoscaler's taint, a gone node, another pool), `…EndsWithNoRolloutInProgress` (settled, suspended, finished, expired) and `…IsNeverStartedWithoutASameNodeSwapToCover` (a steady pass makes zero writes and starts no Job, a first deploy, no running instance, a diskless rolling service).
- **Mutations, each run against its test (all red):**
  - M1: the template is written right after the holder is created. Red: "wait = 0s, want the rollout held for its holder".
  - M2: the holder ends at the new pod's binding. Red: "the holder ended before the new instance had the volume mounted".
  - M3: no immediate end when the new pod is bound elsewhere. Red.
  - M4: any ReplicaSet's pod reads as the new instance. Red: "the first rollout's instance mounting the volume ended the second rollout's hold".
  - M5: no mount bound. Red: "a holder is left".
  - M8: no `settled` end. Red: "the holder is left with no rollout to hold for".
- **Not covered:** `restoreServedTemplate`, the restore of a served release after a failed rollout, patches the Deployment directly and takes no hold. ADR082 records it, and [w6/165](../../../165.md) files it.
