## Objective

Give every identity a stable, opaque `own-<xid>` id. Register the `own` kind in
`internal/id`, persist a subject⇄own-id mapping in the control-plane store (so
the same subject always resolves to the same `own-` id and an `own-` id reverse-
maps to its subject), and expose a small resolver the owners/members code calls.

## Context

- `lego/backend/internal/id/id.go` — registered kinds today: `tea`/`srv`/`cdm`/`evg`/`dep`/`inv`/`exp`/`aud`. No `own`. A new kind is added here (and nowhere else); the guard test then holds it to the `<prefix>-<xid>` DNS-safe format (docs/identifiers.md).
- Kratos subjects are UUIDs, not xids — so `own-<xid>` must be **minted + stored**, not derived. Precedent for a control-plane table + migration: `lego/backend/internal/store/migrations/` (0001–0007) + `internal/store` queries.
- `docs/render-artifacts/owners-api.md` pins the prefix as `own-` (not `usr-`).

## Steps

1. Add `Owner = id.Kind{prefix: "own", desc: "user/identity (Render own-)"}` to `internal/id/id.go`; the guard test picks it up.
2. New migration `internal/store/migrations/0009_owner_ids.up.sql` / `.down.sql`: a table mapping `subject` (unique) ⇄ `own_id` (unique).
3. `internal/store`: `OwnerIDForSubject(ctx, subject) (ownID string, error)` — get-or-create, mint via `id.New(id.Owner)` on first sight (race-safe upsert). (No reverse `own-→subject` lookup: it existed only for peer-resolve, a dropped non-goal — YAGNI.)
4. Surface it on the workspaces service's `WorkspaceStore` interface (satisfied by the store), so t002 has one source of truth.
