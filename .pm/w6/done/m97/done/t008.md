## Objective

t001/t002 fix and prove the guard-rejection behavior for a **fresh App create**. This task fixes the same guard's behavior on a **redeploy of an already-Live App** — confirmed this run (16th `/qa-find-bugs` hunt, code trace, not a new live repro) to be a distinct, second defect: the rejected Deploy row never reaches `update_failed`. It instead sits at `queued` forever, or — once a 35-minute timeout elapses — resolves to `canceled`, which is the wrong terminal state and misrepresents what actually happened (a guard rejection, not a genuine cancel or an indefinitely pending build).

## Context

- **Mechanism, traced to file:line this run.** `rejectProtectedSecretRefs` fires at `lego/operator/internal/controller/app_controller.go:499-501` and, on rejection, calls `r.fail(ctx, &app, "ProtectedSecretReference", err)` (`app_controller.go:3811-3814`), which sets `Status.Phase = PhaseFailed` and stamps a Ready=False condition — and **returns before `prepareAppReleaseDecision` (`app_controller.go:521`) ever runs**, so `Status.ReleaseGeneration` is never updated to the generation the rejected release was trying to reach.
- **Why create is fine:** a brand-new App has never had `Status.ReleaseGeneration` set (zero), so `appReleaseGeneration()` (`lego/backend/internal/store/reconciler.go:1104-1109`) falls back to `app.Generation` (its first-ever generation, `=1`), which trivially equals the Deploy row's `Generation` (`store.FirstDeployGeneration = 1`, `store.go:751`). `observedDeployStatus`'s `PhaseFailed` branch (`reconciler.go:1014-1024`) then resolves straight to `DeployUpdateFailed` — the instant failure this milestone's own repro observed.
- **Why redeploy is not:** `redeployFetched` (`lego/backend/internal/apps/service.go:2665`), blueprint-sync `patchChangedStackService` (`lego/backend/internal/apps/deploy.go:2652`), and `triggerFetched` (`lego/backend/internal/deploys/service.go:477`) all bump `AnnotationReleaseGeneration` to `previousGeneration+1`, Patch the existing App CR (bumping `metadata.generation`), and open a new Deploy row with `Generation = previousGeneration+1`. When the operator's guard rejects this reconcile, `Status.ReleaseGeneration` stays pinned at the last successful release `G` (non-zero — the early return in `r.fail` never lets it advance). `observedDeployStatus` → `supersededDeployStatus` (`reconciler.go:1036-1089`) then sees `appReleaseGeneration()==G != open.Generation==G+1`, is not the queued-overlap case (`reconciler.go:1058`), and hits `if !timedOut { return "", true }` (`reconciler.go:1074-1076`) — `recordDeploy` (`reconciler.go:629,664-666`) reads `status==""` and writes nothing, so the row sits exactly where `CreateDeploy` left it. Only once `deployTimedOut`'s 35-minute `BuildGateTimeout` (`reconciler.go:84,942-960`) trips does the same function's tail return `DeployCanceled` (`reconciler.go:1077-1079`).
- **Live symptom this explains (15th run, read-only observation, not re-probed this run):** `eden-cms-v2` (`srv-d9e40ei9086p3l1jri30`) stuck `queued` indefinitely; `block-eden-mono` (`srv-d9ndt8hmcglc739fkp50`) resolved to `canceled` after ~35 minutes. **Both are standing production services outside the QA sandbox — do not restart, redeploy, or otherwise touch them.** Verify any fix against a fresh `qa-`-prefixed fixture instead, using a guard-rejection reason other than the self-secret case (see Out of scope).
- This is a **distinct** defect from t001's: t001 stops the guard from firing on an App's own self-minted secret. This task fixes what happens to the Deploy-status state machine on **any** `r.fail`-driven rejection that occurs on a redeploy rather than a create — it is not automatically fixed by t001 landing, since t001 only removes one specific trigger, not the generation-staleness mechanism itself.
- **New live data (17th `/qa-find-bugs` run, read-only, nothing touched) — re-check against this before considering the fix complete:** (1) `eden-cms-v2`'s stuck-`queued` row (`dep-da74dkb7o1fc73av6org`) has now sat `queued` for ~18.5 hours (since 2026-08-26T01:52:17Z) without flipping to `canceled` — this outlives the 35-minute `BuildGateTimeout` this task's own mechanism predicts, so either the timeout only fires on active reconcile traffic this App isn't currently getting, or a second mechanism is holding it `queued` indefinitely that this trace hasn't captured yet. (2) Two services (`beancount-cms-v2`'s `dep-da7k9qfkh5kc73fbqu3g`, and a fresh `block-eden-mono` attempt `dep-da7kh8vkh5kc73fbquqg`) were observed stuck at status **`created`** (not yet `queued`) — a state this task's write-up never discusses; both were too fresh (<30min) at observation to tell whether they progress normally or represent a third stuck-state variant. Re-verify all three against whatever fix lands here, not just the `queued`→`canceled` case already traced.

## Steps

1. Ensure a guard rejection (`r.fail` at the `rejectProtectedSecretRefs` call site, and ideally the sibling early `r.fail` sites t007 already names) advances `Status.ReleaseGeneration` to the generation it was attempting to reach, even though the release itself failed — so `supersededDeployStatus`'s generation-match predicate can see the outcome immediately instead of waiting on a timeout. (Alternative valid fix: have `recordDeploy`/`observedDeployStatus` recognize a Ready=False condition whose `ObservedGeneration` already reflects the open deploy's target generation as a terminal failure signal in its own right, independent of `Status.ReleaseGeneration` bookkeeping — pick whichever keeps `prepareAppReleaseDecision`'s existing contract intact for the success path.)
2. Confirm `observedDeployStatus`'s `PhaseFailed` branch (`reconciler.go:1014-1024`) is reached for the redeploy case once the generation match holds, exactly as it already is for `CreateApp`.
3. Add a regression test that rejects a **redeploy** (not a create) via the guard and asserts the Deploy row reaches `update_failed` well inside the 35-minute `BuildGateTimeout` window — not `queued` forever, not `canceled` only after timeout.
4. Re-verify all 4 blast-radius call sites (`CreateApp`, `redeployFetched`, blueprint `patchChangedStackService`, `triggerFetched`) agree on instant `update_failed` for a guard rejection.
