## Objective

The API server admits the t005 projection for App-owned new-policy workloads, and nothing broader. This repeats the w4/m142 lesson: ADR089 shipped `image-v1` without its admission change, and every Docker deploy in the canary failed.

## Context

- `deploy/gitops/base/operator-workload-admission.yaml`:
  - `imageCompatibilityWorkload` keys on the label, the App controller ownerRef UID/name match, a single `app` or `predeploy` container, and the `deployments`/`cronjobs`/`jobs` resources (`:96-110`);
  - the restricted grammar applies outside execution namespaces (`:163-193`);
  - `hostUsers` is required only in isolated execution namespaces (`:155-161`).
- w4/m142's fix `d95d017ba` added the image-v1 branch and an API-server regression test. Find it and extend the same test.

## Re-scope — 2026-10-20

The `hostUsers == false` requirement is out of scope (w6/086). The `containerPolicyCaps` admission map and its envtest dry runs shipped in 67aa2bf35. What remains is checking the other acceptance cases (forged label without owner, `render-v1` caps on a datastore or backup workload) and `gitops-validate`.

## Steps

1. Add a new-policy variable with the same ownership predicate as `image-v1`, plus its capability list. Keep `image-v1` admitted for existing services.
2. For the new policy, require all of the following:
   - drop `ALL`;
   - `add` ⊆ the t003 set;
   - the t003 `allowPrivilegeEscalation` value;
   - RuntimeDefault seccomp;
   - `hostUsers == false` on the paths where t003 adopted it.

   Init containers get no capability exception.
3. Server-side dry-run regressions must cover:
   - acceptance of the exact projection;
   - rejection of one capability beyond the set;
   - rejection of a missing `hostUsers` (if adopted);
   - rejection of a forged label without the matching App owner;
   - rejection of the new set on a datastore or backup workload.
