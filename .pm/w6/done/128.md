# The loopx guard charges a workflow's old red streak to this loop when its earlier runs fall outside the run window

Why: a CI-fix dispatch went to `postgres operand image (build + verify)`, a workflow that has never passed on main, because the guard sees only the newest 400 runs across the whole repository.

## What happened

- Run [43841677012](https://github.com/bex-co/bex/actions/runs/43841677012) ran on `e9f27399b` (w6/m422). In the workflow's `paths`, that commit changed only a comment in `scripts/install-syft.py`.
- `pg-operand-image.yml` has failed on every push run since its first, `3f38f03bf` on 2026-10-31: 15 runs, none green. The run before this one, 43576648124 (2026-11-14), was already red, but it was older than the guard's 400-run listing. So the streak looked as if it began on our push.

## Why the workflow is red (not w6's to fix)

1. **Deliberate gate.** Every major stops at `deploy/pg-operand/check.sh`'s fatal `ordinary-owner complete Timescale/IMMV logical restore remains unsupported` (`permission denied to set parameter "timescaledb.restoring"`). This is w8/m92's BLOCKED gate, which waits on an upstream raw owner-restore capability. The gate is left fatal on purpose (see "CI sweep — 2026-11-05" in the [m92 README](../../w8/blocked/m92/README.md)). Nothing in w6 can turn it green.
2. **PGDG drift, fixed alongside this note.** After PGDG's November minor release (first seen in run 43576648124), PG14–18 failed earlier, at `apt-get install`. The newest extension builds depend on `postgresql-NN (>> 14.25 / 15.20 / 16.16 / 17.12 / 18.7)`, but `deploy/pg-operand/matrix.json` held 14.24 / 15.19 / 16.15 / 17.11 / 18.6. The `fix(ci)` commit shipped with this note moves those bases to CNPG's matching `system-bookworm` digests, so all six majors reach the gate again.
3. The fix's own run is expected to stay red at (1). The guard will report it as attempt 2. That red belongs to w8/m92, not to this loop: do not file another note for it.

## The w6 work: the guard

- In `scripts/loopx-guard.py`, `ci_status` (around line 849) owns a workflow when `streak[0]` is on one of our commits. But `gh_runs()` lists only the newest `CI_RUNS` = 400 runs repo-wide. For a path-filtered workflow that runs rarely, the listing can hold no success and no earlier red run, so a streak that started weeks ago looks as if it started on our push.
- **Fix:** when no settled success comes before the streak in the listing, read that workflow's own push-on-main history before taking ownership: `gh run list --workflow <name> --limit 50`, filtered for branch and event in code, not with `--branch` (see the `gh_runs` docstring). A workflow whose first-ever run is ours and red stays ours.
- **Test** (in `CITest`, `scripts/test_loopx_guard.py:1251`): when earlier red runs appear only in the per-workflow listing, the streak is someone else's and is not reported. A workflow whose only runs are ours and red is still reported.
