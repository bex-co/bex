## Objective

If t001 shows the image pull in the downtime, pull the new image onto the target node before the Deployment's template changes, so `Recreate` starts from a local image.

## Context

- Needed only when t001 marks it so; otherwise close with t001's numbers.
- The operator's release path for a disk App; image pull secrets in the tenant namespace.

## Steps

1. Before the template change, run a short-lived pre-pull pod (same image, same pull secret, `nodeName` of t002's target, command that exits at once), bounded in time.
2. Change the template once it completes or its bound passes; never block a deploy on it.
3. Tests for success, timeout and a node that is gone.

## Files

- lego/operator/internal/controller (release path) and tests

## Acceptance criteria

- [ ] A disk App's new image is local on the target node before the old pod stops, or the bound is recorded
- [ ] `make test` and `make lint` pass

## Out of scope

- Pre-pulling for rolling-update Apps

## Record (2026-11-21)

Closed as not needed, with t001's numbers. The fixture's new tags pulled in 2.0–2.2 s. A cached image still took 0.6–0.7 s, because `imagePullPolicy: Always` re-checks the registry. A pre-pull would therefore save about 1.5 s on a code deploy, and nothing on a restart or plan change. The larger terms were the node move, the 10 s startup period and the kubelet's 10 s sync, which t002, t003 and t010 shorten. The variant for images whose changed layers take many seconds to pull is filed as [w6/m595](../../m595/README.md), with this task's design and its open questions: tenant quota, admission, and images with no binary that exits at once.
