## Objective

Know where a disk service's downtime goes before changing anything.

## Context

- `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>`; `bash scripts/qa-login.sh`; fixtures in `bex-canary`.
- Phases: old pod `SIGTERM` → container exit → pod deleted → new pod scheduled (which node) → `VolumeAttachment` attached → image pulled → container started → startup probe passes → Ready → endpoint in Traefik → first 200 at the edge.

## Steps

1. Create a paid service with a 1 GB disk whose server listens at once (a small Go or Node app) in `bex-canary`.
2. Probe its public URL every 250 ms; run a code deploy that keeps the node, one that forces another node (cordon the current one), a restart and a plan change.
3. Read each phase from pod events, `VolumeAttachment` timestamps, kubelet events and the probe log; write the table here.
4. Decide which of t002–t004 the numbers need; mark the rest not needed with the reason.

**Method.** A fresh-TLS `GET /` through `https://w6-m547-disk.onbex.co` every 250 ms (send time logged; about 0.3 s from the edge's reply). Locally stamped `kubectl --watch` streams of the App's pods, the namespace's events, the PV's `VolumeAttachment`s, the EndpointSlice and every node's `volumesInUse`/`volumesAttached`, plus the hcloud CSI node logs and the node's kubelet syslog (`/api/v1/nodes/<node>/proxy/logs/syslog`). A window runs from the first failing probe to the first 200. Every failure was a 503 (C and E also one 502). Isolated client timeouts at 07:22:12Z were local network noise and are excluded.

**Where the time goes**

- **The scheduler moves the volume in 3 of 6 unforced runs (C, D, E).** It picks the best-scoring node in the volume's location, not the volume's node. A move adds 27–32 s: the old node's kubelet must first report the volume free, then Hetzner takes 9.1 s to detach and 15 s to attach.
- **The startup probe costs 7.1–9.1 s in every run.** whoami listens within milliseconds of starting. The 10 s startup period (`deployment_projection.go` `healthCheckPeriodSeconds`) is the single largest term on a node that keeps its volume. Readiness is not a term: the kubelet runs the readiness probe as soon as startup passes, and Ready followed in 0.2–0.6 s.
- **On the same node, the volume costs 4.6–11.7 s.** The CSI driver closes LUKS on unpublish, and the new pod opens it again: `cryptsetup open` takes 2.1–2.3 s (its default 2 s key-derivation time), and publish → `Pulling` takes another 0.7–0.9 s. The rest, 1.7–8.6 s, is the kubelet waiting before it mounts. In A2, the kubelet syslog has the new pod's `VerifyControllerAttachedVolume` start only at 07:25:32.4, 8.6 s after the pod reached the node, with no other volume activity in between. The kubelet mounts an attachable volume only after its node-status sync has reported the volume in use (`reportedInUse`), and production's kubelets sync every 10 s (`nodeStatusUpdateFrequency: 10s` in `/configz`). The same sync gates a move: the attach/detach controller detaches only after the old node's next sync drops the volume from `volumesInUse` (1.0–8.1 s above). This term is not in t002–t004. It is t010.
- **The pull costs 0.6–2.2 s for this 3 MB image.** That is docker.io round trips: `imagePullPolicy: Always` re-checks a cached image (0.6 s), and a new tag pulls (2.0–2.2 s). In the same hour, production pulled `nginx` images of 26–64 MB in 3.4–3.7 s. Tenant-built images on the nodes have a median size of 967 MB (85 images; largest 2.6 GB), although a code deploy pulls only their changed layers.
- **Stop is 0.4–1.3 s.** whoami exits on SIGTERM at once, and the 0 s preStop for disk Apps holds (`drainSecondsFor`).

**Decisions**

- **t002 needed:** the move costs 27–32 s, and half the unforced runs moved.
- **t003 needed for the startup probe:** 7.1–9.1 s → about 1 s. Its readiness half is **not needed**: Ready followed startup by 0.2–0.6 s in all seven runs, so a 1 s readiness period would add probe load without shortening the window. Readiness keeps 5 s × 3.
- **t004 not needed for this bound:** a pre-pull would save only about 1.5 s, and only on a code deploy. A new tag pulled in 2.0–2.2 s, but a cached image still took 0.6–0.7 s (C, D, E), because `imagePullPolicy: Always` re-checks the registry. A restart or plan change pulls nothing new, so it saves nothing there. It matters for an image whose changed layers take many seconds to pull, which is filed as [w6/m595](../../m595/README.md).
- **New t010:** the kubelet's 10 s node-status sync adds 0–10 s on the same node and delays a move's detach. Without t010, the definition of done's bound cannot hold.
- **Found on the way:** after deploys with `imageUrl` `v1.11.0`, run D's plan change rolled the service back to its create-time image `v1.10.1`. The App spec's `image` still read `v1.10.1`, and deploy `dep-dc0kgpl2b0us73dobm8g` (`service_updated`) shipped `sha256:6956a30c…`. It is filed as [w6/159](../../../blocked/159.md).
