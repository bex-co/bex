# Docker-runtime source builds do not bind `registryCredentialId`

Filed by `w6/m31` (2026-07-15), from its Render-contract parity check.

Render's current service create/update contract exposes `registryCredentialId` in two source contexts: `image.registryCredentialId` for a prebuilt image and `serviceDetails.envSpecificDetails.registryCredentialId` for a repository-backed Docker build. `w6/m31` implements the former end to end across REST, GraphQL, MCP, and the dashboard because bex already had the safe runtime mechanism: materialize a workspace-scoped `dockerconfigjson` Secret and reference it from the App workload.

The Docker-build variant needs a different mechanism. Its credential must be available to BuildKit while resolving private `FROM` images without becoming a Docker build arg, a tenant-readable BuildKit secret, or a long-lived credential in the resulting image. The current build Job has no service-credential mount/auth path, so accepting the nested field would silently ignore requested authentication. bex therefore returns a named 400 when an explicit credential is supplied for a repo-backed service.

A future milestone should design the BuildKit-side credential boundary, thread the persisted binding through the build Job, add foreign/unknown credential isolation tests, and live-verify an authenticated private base-image pull. This is larger than a sub-hour inbox fix and should be promoted before implementation.
