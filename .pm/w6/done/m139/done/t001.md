## Objective

Represent stable shell presentation separately from the fresh affirmative grants needed to read protected content or dispatch actions.

## Context

- The capability provider's lastResolved fallback can continue enabling work after a failed refresh with no freshness expiry.
- downgradeDetected currently treats allowed → unavailable as confirmed loss; ADR087 distinguishes unavailability from denial.

## Steps

1. Keep snapshots in memory and bind them to identity/session, workspace, and access generation; record client last-check time without inventing a server membership version.
2. Use the ADR087 30-second client policy to expire affirmative action/read eligibility while preserving stable navigation where appropriate.
3. Make explicit denied and unavailable outcomes distinct; unknown vocabulary remains restrictive and reason-unknown.

## Acceptance criteria

- [x] A grant that is stale, checking, unavailable, or from another generation never enables a protected operation.
- [x] Transient failures do not remove tabs merely because a fetch failed and never announce a role change.
- [x] Allowed → denied triggers the confirmed-loss path; allowed → unavailable blocks work with neutral copy.

## Out of scope

- Backend permission changes or a new role-to-permission mapping.
- Resource-specific lifecycle eligibility, owned by m141.
