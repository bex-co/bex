## Objective

Make foreground/reconnect a membership-and-access barrier before screens restore protected work, including recovery from workspace membership removal.

## Context

- CapabilitiesProvider polls every 30 seconds but does not participate in the existing app/network recovery transition.
- WorkspaceProvider loads membership at bootstrap; a removed selected workspace must not remain the active context.
- The small auth-link recovery defect is tracked separately as w6/071 and is first in the handoff priority order.

## Steps

1. Reuse the existing recovery utilities to single-flight membership and capability checks on foreground/reconnect and relevant navigation return.
2. Pause protected recovery until the current context is verified; use fresh evaluation for recovery while retaining the ordinary background/cache policy.
3. Clear a removed selection and use the verified chooser or existing empty state. Treat a resource 403 separately from global auth failure.

## Acceptance criteria

- [x] Concurrent foreground/reconnect triggers produce one current-context recovery and no protected request before access resolves.
- [x] Removal of the selected membership clears selection and reaches a usable chooser or empty/logout state.
- [x] Offline and failed checks cannot fall back to stale affirmative grants or force logout for a resource-level refusal.

## Out of scope

- Changing native PKCE/credential storage or dashboard session authentication.
- Creating new workspace-management screens.

Mounted concurrent recovery, startup-error retry, explicit workspace removal/selection and empty-state cases pass; native foreground request order is recorded. See [verification record](../../../../../mobile/e2e/m139-access-recovery.md).
