## Objective

Stop `internal/api/render_openapi.go`'s Render-compatibility validator from unconditionally 400ing every REST request to a blueprint-id-scoped route, while keeping the rest of the Render-compat guarantee intact (bex-native routes, every other id kind, and body/query validation all stay exactly as strict as they are today).

## Context

- Root cause: `internal/api/openapi/render-public-api-1.json`'s `blueprintId` path parameter is pinned to Render's own historical shape (`pattern: "^exs-[0-9a-z]{20}$"`, at `/blueprints/{blueprintId}` and `/blueprints/{blueprintId}/syncs`). bex mints Blueprint ids as `blp-…` (`internal/id/id.go:79`) and always will — `id.New`/`id.Kind` is a closed, compile-time registry (`docs/ADR020-identifiers.md` § Enforcement), so there is no code path that could ever produce an `exs-…` id.
- `internal/api/render_openapi.go` already has a precedent for exactly this kind of targeted, operation-scoped override:
  - `renderRequiredCompatibility` (relaxes required body fields per operation)
  - `renderOptionalParameterCompatibility` (relaxes a named parameter's `Required`)
  - `renderQueryExtensions` (allowlists bex-only query params per operation)
  - `applyRenderCompatibility` is where all three are applied to the loaded `*openapi3.T` before the router is built (`loadRenderOpenAPIContractData`, ~line 151-172).
- None of the three existing maps touch a path parameter's `schema.pattern`. This task adds that fourth knob, scoped as narrowly as the others (by operationId + parameter name), not a global "ignore all path patterns" escape hatch.
- The four affected operationIds (confirmed exhaustively — see the milestone README's table): `retrieve-blueprint`, `update-blueprint`, `disconnect-blueprint`, `list-blueprint-syncs`. All four parameters are the SAME `blueprintId` path-level parameter (`$ref`'d from `/blueprints/{blueprintId}`'s `parameters[0]` into `/blueprints/{blueprintId}/syncs`), so one mutation covers all four operations — but assert that in the test (t002), don't assume it.

## Steps

1. In `applyRenderCompatibility` (or a small new sibling function called from the same place), add a targeted mutation that replaces (or removes) the `blueprintId` path parameter's `Schema.Value.Pattern` for the `/blueprints/{blueprintId}` and `/blueprints/{blueprintId}/syncs` path items, so it accepts bex's actual id shape. Prefer replacing the pattern with something that validates bex's real shape (`^blp-[0-9a-v]{20}$` — note bex's xid alphabet is base32-hex `0-9a-v`, narrower than Render's `0-9a-z`; a real bex id already satisfies `[0-9a-z]{20}`, so either charset works, but match bex's own actual alphabet for a validator that means something) over blanket-deleting the pattern, so the parameter still rejects garbage — just not bex's own real ids.
2. Do this as a new small map (e.g. `renderPathParameterPatternOverrides map[string]map[string]string` keyed by operationId → parameter name → replacement pattern) applied inside `applyRenderCompatibility`'s existing loop, mirroring how `renderRequiredCompatibility`/`renderOptionalParameterCompatibility` are looked up and applied — do not hand-edit the parsed doc ad hoc outside that established mechanism.
3. Do NOT touch `internal/id/id.go`'s `Blueprint` prefix, any stored blueprint id, or any dashboard/GraphQL/MCP code — this is purely a compatibility-layer correction for the REST validator's copy of Render's spec.
4. Confirm `TestRenderOpenAPIPinGuards` / the SHA-256 pin check (`renderOpenAPISHA256`) still passes — this mutation runs on the loaded `*openapi3.T` in memory, not on the embedded JSON file, so the file's hash is untouched. If the pin guard test hashes something else (the post-mutation document), read it before assuming this is safe.

## Acceptance criteria

- [ ] `GET /v1/blueprints/{a real blp-… id}` no longer 400s at the validator layer (it may still 403/404 for the wrong caller/id — that's t002's job to assert correctly).
- [ ] `PATCH`/`DELETE /v1/blueprints/{id}` and `GET /v1/blueprints/{id}/syncs` likewise no longer 400 on a syntactically valid `blp-…` id.
- [ ] An `exs-…`-shaped id (Render's own shape, which bex will never issue but a copy-pasted Render example might be pasted by a confused user) is still correctly rejected as not-found (404) rather than accepted as if it existed — i.e. the fix widens the accepted *syntax*, it does not disable the id-not-found check downstream.
- [ ] Every other operation's validation (body schema, required fields, query allowlist, the other 4 pattern-constrained path params) is unchanged — no regression in `TestRenderRequestValidatorRejectsBeforeSideEffects` / `TestRenderRequestValidatorAcceptsExtensionsAndPreservesInput`.

## Out of scope

- Changing bex's Blueprint id prefix itself, or any stored data.
- Fixing GraphQL/MCP (already correct — not wrapped by this validator).
- The `blueprintsync` id (`bsr-…` vs Render's `exe-…`) — not confirmed pattern-constrained in the current spec; leave as noted-unverified for t003 to record, not fixed here.

## Outcome (2026-08-26)

`renderPathParameterPatternCompatibility` added to `internal/api/render_openapi.go` as the fourth compatibility map, keyed `operationId → parameter name → replacement pattern` and applied inside `applyRenderCompatibility`'s existing loop alongside `renderOptionalParameterCompatibility` — same lookup, same place, no ad-hoc mutation of the parsed document.

**The pattern widens rather than replaces**: `^(?:blp|exs)-[0-9a-z]{20}$`, not `^blp-…`. This task's own acceptance criteria required an `exs-…` id to reach the store and 404 rather than 400, and that is also the right call on principle — every existing knob in this file relaxes Render's contract (drop a required field, un-require a parameter, allow an extra query name) and none narrows it. Swapping bex's shape in for Render's would fix bex clients by breaking Render-shaped ones, so `TestRenderPathParameterOverridesOnlyWiden` now pins "an override must accept everything the upstream pattern accepted" as a checked invariant of the map itself, not just of this one entry. The character class stays Render's `[0-9a-z]` rather than narrowing to xid's actual `[0-9a-v]` for the same reason — a real bex id satisfies both.

Safe against the pin guard as the task suspected: the mutation runs on the loaded `*openapi3.T`, never on the embedded JSON, so `renderOpenAPISHA256` is untouched. kin-openapi v0.144.0 compiles patterns lazily into a package-level `sync.Map` keyed by the pattern string (`openapi3/schema.go:2655`), and `applyRenderCompatibility` runs before any request is validated, so rewriting `Schema.Value.Pattern` takes effect with no cache to invalidate.

Confirmed rather than assumed, per this task's own instruction: `/blueprints/{blueprintId}/syncs` `$ref`s the parameter out of `/blueprints/{blueprintId}`'s `parameters[0]`, so all four operations do share one object — but the map lists all four operationIds explicitly anyway, so the override does not silently depend on that aliasing.

**Two further defects on the same routes, found by t002's tests and fixed here** — see t002's notes. Neither was visible to a code read: both needed a request driven through the real composed server.
