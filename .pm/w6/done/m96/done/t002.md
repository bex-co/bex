## Objective

Close the actual coverage gap that let this ship as "done" under `w2/m62`: prove the four blueprint-id REST routes work **through the real composed server** (auth + rate limit + `renderRequestValidator`), not through the bare-mux shortcut the existing test uses. Also lock in the four id/pattern pairs that already happen to be correct today, so a future Render spec refresh can't silently reintroduce this class of bug on any of the five without failing CI.

- Because the composed-server harness in that file appears to use a mocked/counting backend (`mutations` counter, `http.StatusNoContent` responses) rather than the real `apps.Service`, check whether it's wired to a real or fake blueprint backend before assuming a 200 body proves anything beyond "the validator let it through." If the harness can't easily exercise a full round-trip to a real blueprint through Blueprints service (fake store, etc.), it's fine to assert "validator passed it through to the inner handler" there and add a SEPARATE full-stack test (real `apps.Service` + `fakeBlueprintStore` + the validator wrapper) that proves an actual 200/403/404 comes back — don't let "the validator didn't 400" quietly stand in for "the endpoint actually works."

## Outcome (2026-08-26)

`internal/api/render_openapi_blueprint_test.go`: a real `apps.Service` (backed by a tenant-scoping `blueprintFixtureStore`) behind the real `newRenderRequestValidator`. **Writing it found two more live defects that the milestone's own exhaustive spec grep could not have seen**, because both live past the path-parameter check that was rejecting every request before them:

1. **`ownerId` was rejected on all four routes.** Render's `retrieve-blueprint`/`update-blueprint`/`disconnect-blueprint`/`list-blueprint-syncs` declare no `ownerId` query parameter (verified against the embedded spec), but all four bex handlers read `r.URL.Query().Get("ownerId")` (`internal/apps/rest.go:1172-1198`), so the strict-query gate answered `400 request contains an unsupported query parameter` for any call naming a workspace. This is the identical concession `renderQueryExtensions` already makes for `retrieve-webhook`/`update-webhook`/`delete-webhook`/`retrieve-event` — with the identical rationale already written above it — simply never extended to blueprints. Fixing only the path pattern would have moved the failure one line down, not fixed it.
2. **A missing or other-workspace blueprint returned `500 internal error`, not 404 — on REST, GraphQL and MCP alike.** Every blueprint verb returned the raw `store.ErrNotFound`-wrapped error, which `core.WriteErr` does not classify (it matches `core.ErrNotFound`; the two are distinct sentinels), so it fell through to the unclassified-error branch and was redacted. `internal/apps/disks.go` already routes store errors through `store.MapError`; the blueprint verbs never did. Fixed at the six call sites in `internal/apps/blueprint.go`. Without this the milestone's third DoD bullet would have been satisfied only in the letter — "not 400 any more" would have meant "500 instead", which is not a correct distinct outcome.

### Tests

`TestBlueprintIDRoutesPassTheRenderOpenAPIGate` — GET by id (200 **with the right body**, not merely a 200), GET syncs, PATCH (asserted to have reached the store), DELETE (asserted to have reached the store), and the three formerly-indistinguishable outcomes as three genuinely different scenarios: a nonexistent id → 404, another workspace's blueprint read as your own workspace → 404 (tenant-scoped store read), and asking *as* a workspace you are not a member of → 403 (refused by `Authorize` before any store read). Different ids and different caller-workspaces, not one fixture asserted twice.

Two guards on the fix's own shape: garbage in the id position is still 400 **and asserted on the `invalid path parameter` reason** — those requests also carry `ownerId`, so a bare status check would pass on the unrelated query rejection — and a Render-shaped `exs-` id still reaches the store for an honest 404.

`TestEveryConstrainedIDPathParameterAcceptsItsBexID` — derives the set from the real spec crossed with `NewServer(...).restHandler()`, the same real mux `TestRenderRouteIntersectionInventory` uses, rather than a hand-listed route set (my first attempt hand-listed them and got `jobId`'s path wrong, which is exactly the drift this guards against). For each pattern-constrained id parameter on a bex-served route it mints **real** ids via `ids.New(kind)` and asserts they satisfy the pattern the validator will apply. It is completeness-checked in both directions: an unclassified parameter fails, and a stale entry fails. The spec has seven such parameters; `maintenanceRunID` and `userId` sit on operations bex does not serve, which is why the milestone's count of five in the intersected surface was right.

`TestRenderPathParameterOverridesOnlyWiden` — see t001.

### Existing tests

`TestRESTListBlueprintSyncsIncludesErrorMessage` is untouched, as instructed — it tests real error-message plumbing and keeps doing so. One assertion in `TestSyncBlueprintNotFound` changed from `store.ErrNotFound` to `core.ErrNotFound`, which is the point of defect 2: `store.MapError` deliberately keeps the store error in the message (`%v`) rather than the chain, so the core sentinel is the one every surface maps to a status.
