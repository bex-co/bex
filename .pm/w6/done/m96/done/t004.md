## Outcome (2026-08-26)

**Parity confirmed with a test, not an assumption — and the assumption in this task's framing turned out to be wrong.** The task states GraphQL and MCP "were already correct (never wrapped by the REST validator)". That is true of the *validator*, and false of the surfaces: t002 found that every blueprint verb returned its raw store error, so a missing or other-workspace blueprint came back as a redacted internal failure on **all three** surfaces, not just REST. The fix therefore landed in the shared service layer (`internal/apps/blueprint.go`), which is why all three move together and none drifted.

`TestBlueprintByIDNotFoundIsIdenticalAcrossSurfaces` (`internal/apps/blueprint_test.go`) is the evidence:

- the five shared verbs (`GetBlueprintByID`, `ListBlueprintSyncs`, `UpdateBlueprint`, `DisconnectBlueprint`, `SyncBlueprint`) each return `core.ErrNotFound` for a missing id, and each is asserted `core.IsPublicError` — the property that decides whether the message survives to the caller or is redacted to "internal error", which is what made not-found indistinguishable from a server fault;
- REST returns 404 with a body;
- GraphQL returns exactly one error that is not the redacted internal one;
- MCP's `get_blueprint` returns a tool error;
- and a control case proves the blueprint that DOES exist still reads successfully, so the mapping did not turn a working read into a failure.

`UpdateBlueprint` needed a real field in that table: an empty patch is a bad request *before* the lookup, so asserting not-found on an empty patch would have proved nothing. Caught while writing it.

**Render comparison.** The embedded spec is the reference for these four operations. Render declares no `ownerId` on any of them; bex accepts one, recorded as a labeled query extension in `renderQueryExtensions` beside the identical webhook and event concessions — a superset, so a Render-shaped client is unaffected. Response shapes are unchanged by this milestone. The `blp-`/`exs-` id-shape divergence is recorded in ADR020 (t003) with the compatibility mechanism that resolves it.

**No drift found, so nothing filed as follow-up.**
