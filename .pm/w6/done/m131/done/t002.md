## Objective

Today a `type=request` query against a live store returns `200 {"logs":[],"hasMore":false}` — byte-identical to a service that genuinely received no traffic. Decide what, if anything, should distinguish those two, and write the decision down.

Name the target behaviour. "Make the empty state honest" is not a spec — it is satisfiable by any change that alters the response shape without helping the caller.

## Context

- `docs/ADR018-render-parity.md:182` already defines the vocabulary this extends: "**Nothing accepted is ignored:** without the store (`BEX_LOKI_URL` unset) `type=request`, `type=build`, and the store-only filters return 503." That path keys on **store presence only**.
- Here the store is present and healthy — app logs (100 lines) and build logs (100 lines) come from it in the same window — so the request query takes the success path.
- The honest question is whether bex can even distinguish the two cases. "No rows for this stream" and "no traffic" look identical from Loki unless something else asserts the stream should exist.
- A legitimate outcome is **"the pipeline fix alone is sufficient; no new state"** — provided that is recorded as a decision with its reasoning, not left unexamined.

## Steps

1. Establish whether the distinction is knowable from the API's vantage point at all, given `t001`'s finding.
2. If it is, decide what carries it — a distinct status, a response field, or a UI-level affordance — and which of REST/GraphQL/MCP/dashboard change.
3. If it is not, record that explicitly in ADR018 row 182 so the next reader does not re-open it.
4. Preserve the existing store-absent 503 behaviour either way.

## Outcome (2026-08-28)

**Decision: the distinction is NOT knowable per-resource, and is deliberately not represented in the API.**

A `type=request` read against a live store returns `200 {"logs":[]}` whether the service was genuinely quiet or the pipeline had stopped producing. Loki's label index is empty in both cases, so from one App's vantage point there is nothing to key on — step 1's question answers itself. Manufacturing an error would misreport every quiet service, so the honest empty stays and the store-absent 503 path is untouched.

What was NOT accepted is leaving the gap unguarded. The distinction *is* decidable in aggregate — across every tenant app, over hours, zero request lines means the pipeline, not the traffic — so it moved out-of-band to `scripts/request-logs-liveness.sh` on the existing 6h schedule (`t004`). Recorded in `docs/ADR018-render-parity.md` row 182 (per step 3) and `docs/ADR010-observability.md` § Log filters, and pinned by `TestRequestStreamStatesAgreeAcrossRESTGraphQLAndMCP` + `TestQuietServiceAndDarkPipelineAreTheSameResponse`.
