# 057 — Secret Files' empty state tells you to add a file but shows no control, and the file-name field shows its validation hint before you type

Why: two small gaps in the same panel, both found while running journey 4 — the first makes the feature look broken to anyone who hasn't discovered that a differently-titled section's Edit button unlocks it.

## 1. Empty state with no affordance

On `/services/<id>/env` in read mode, the **Secret Files** panel renders:

> **No secret files**
> Add a file to mount secret contents into this service.

with **no add control anywhere in the panel**. The accessibility tree for the section contains no button at all — the only buttons in that region belong to the **Environment Variables** panel above it (`Export`, `Edit`). Pressing that panel's `Edit` is what reveals `Add secret file` and `Upload files` inside the Secret Files panel.

So the copy issues an instruction the current mode cannot satisfy, and the control that enables it lives under a different section's heading. Compare Environment Variables, whose own actions sit in its own header.

Fix shape: either give the Secret Files panel its own affordance in the empty state (an `Add secret file` button that enters edit mode), or reword the empty state to point at the actual control. Verified live 2026-08-27 on `srv-da7o6ovvqdcc73bpn9hg`.

## 2. Validation hint on an untouched empty field

Clicking `Add secret file` inserts a row whose `File name` input is empty and unfocused, and the hint is **already** displayed beneath it:

> Use letters, digits, dot, dash and underscore; not '.' or '..'.

The user is told they got it wrong before typing a character. The conventional shape is to render the rule as neutral helper text, or to defer the error state until blur or submit.

Both live on the shared environment editor (`dashboard/src/features/services/components/service-environment-editor.tsx` — the same file `w6/044` cites for the per-row Copy button's wrong label), so they are one visit for whoever picks it up. Both `en` and `zh` move together if the copy changes.

## Verified working in the same journey (recorded so it isn't re-probed)

- Adding a secret file persists: `GET /v1/services/<id>/secret-files` → `[{"secretFile":{"name":"qa-20260827-secret.txt"}}]`, and the row survives a reload.
- Deleting it persists too: the same endpoint returns `[]`.
- The contents dialog states the mount point — "This file is mounted read-only at `/etc/secrets` after the next deploy" — matching Render's `/etc/secrets/<filename>`. **Not verified** that the file actually appears there: the config-change deploy that would have mounted it failed at clone, so the running process was never re-rolled with the file.
- REST's secret-file list returns only `{name}`, never `content`. Render's own list returns content; bex withholding it is a plausible deliberate security divergence, **not checked** against `docs/ADR018-render-parity.md` this run — worth a look before anyone "fixes" it.

## Resolution (2026-09-03)

(a) The Secret Files read-mode empty state now carries its own "Add secret file" affordance (permission-gated like the header Edit) that enters the draft with a blank file row — the copy's instruction is satisfiable in place. (b) `FileDraftItem` shows the file-name rule as neutral helper text until typed-in/blur, then real error styling (no premature `role=alert`/aria-invalid). Tests added for both.
