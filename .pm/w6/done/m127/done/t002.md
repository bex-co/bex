## Objective

`persistenceMode` is settable at create and changeable nowhere, while Render's `keyValuePATCHInput` includes it. That is what makes a wrong default permanent. Add it to the patch path, mirroring how `maxmemoryPolicy` already works.

## Context

- Missing in three places that must move together:
  - `lego/backend/internal/keyvalue/service.go:683-694` — `KeyValuePatch{Name, Plan, MaxmemoryPolicy, IPAllowList}`
  - `lego/backend/internal/keyvalue/rest.go:336-341` — the PATCH decoder
  - `lego/backend/internal/keyvalue/mcp.go:163` — `patch := KeyValuePatch{...}`
  - plus GraphQL (`keyvalue/graphql.go`, which already carries `setKeyValueMaxmemoryPolicy` and the `maxmemoryPolicy` field at `:48`)
- **`w7/m45` is the template** — it did exactly this for `maxmemoryPolicy` through the shared `UpdateKeyValue`. Copy its shape, including normalization: `renderToCRD`/`crdToRender` (`service.go:189-190`) convert Render's underscore wire form to the CRD's hyphenated form and back. `validPersistenceModes` (`service.go:178`) is `{"journal-snapshot","snapshot","off"}` in CRD spelling.
- `UpdateKeyValue` and `PreviewUpdateKeyValue` share `KeyValuePatch.validate()` (`service.go:699`) "so the two paths can never accept different inputs" — preserve that.
- **State the runtime consequence.** The operator builds valkey flags from `spec.persistenceMode` (`keyvalue_controller.go:171-190`), so a change implies a StatefulSet rollout. Say explicitly what happens to data in each direction — `off` → `journal_snapshot` (nothing to restore from; persistence starts now) and `journal_snapshot` → `off` (the AOF/RDB stop being written; existing files' fate). Do not leave this to be discovered by a user.

## Steps

1. Add `PersistenceMode *string` to `KeyValuePatch` and validate it in `validate()` alongside `MaxmemoryPolicy`.
2. Thread it through the REST decoder, GraphQL, and MCP `update_key_value`, all via `UpdateKeyValue`.
3. Keep `dryRun` working for the new field on every surface that already supports it.
4. Determine and document the data behaviour across a mode change in both directions.
5. Add the dashboard control if it belongs here — or state that it is deliberately deferred, as ADR018 already does for post-create eviction-policy editing.

## Files

- `lego/backend/internal/keyvalue/{service.go,rest.go,graphql.go,mcp.go}`

## Acceptance criteria

- [ ] `PATCH /v1/key-value/{id}` with `persistenceMode` changes it, visible on the next `GET`.
- [ ] GraphQL and MCP `update_key_value` do the same.
- [ ] Underscore and hyphenated inputs are both accepted, as create already allows.
- [ ] `validate()` stays shared, so create and update cannot diverge.
- [ ] `maxmemoryPolicy` update behaviour is untouched.
- [ ] The data consequence of a mode change is documented.

## Out of scope

- Migrating existing stores (`t003`).

## Outcome

`KeyValuePatch` gained `PersistenceMode *string` with `validate`/`apply` mirroring `maxmemoryPolicy`, and a shared `persistenceModeKnown` helper reused by `CreateKeyValue` so create and update validate identically. Wired through REST `PATCH /v1/key-value/{id}` (decode + patch), GraphQL `setKeyValuePersistenceMode` (registered in the authz scope matrix), and MCP `update_key_value(persistenceMode:)` — all via the shared `UpdateKeyValue`/`PreviewUpdateKeyValue`, normalizing underscore/hyphen like create. The operator's `valkeyArgs` re-derives AOF/RDB on the changed spec and rolls the pod, untouched.
