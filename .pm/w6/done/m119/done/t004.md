## Objective

The Settings page renders the idle-timeout control on a private service under a sentence promising it wakes on the next request. Gate the control on what the type can actually do.

## Context

Live capture, free `private_service` Settings page:

```
Idle timeout   Free services sleep after this idle window, then wake on the next request.
               [ Platform default ]
```

- `dashboard/src/routes/services.$serviceId.settings.tsx:168` gates the row on `{!cron && !staticSite && …}` — by type, but only excluding the two types that have no Deployment. `IdleTimeoutRow` then gates on `planSleeps(plan)` (`features/services/lib/idle-timeout.ts`), which checks the **plan** (`free`/null) and not the type.
- So the gating is split across two files and neither asks the question that matters: can this type be woken?
- `SetIdleTTL`'s own doc comment (`lego/backend/internal/apps/service.go:3050-3052`) says "Only free-tier Apps ever sleep, but the value is stored regardless … **the dashboard is what gates the control per tier**" — the backend explicitly delegates gating to the dashboard, and the dashboard gates tier but not type. That handoff is where this fell through.
- Related but distinct: `w6/m116` (open) is about what the value `0` means and the "Platform default" label. This task is about whether the control appears at all. They touch the same component; coordinate rather than duplicate.

## Steps

1. Gate the control on auto-sleep eligibility as t001 defined it, not on plan alone — and put the predicate in one place rather than splitting it across the route and the row.
2. If t001 excluded private services, the control should not render for them at all (the route already omits Custom Domains for that type, so there is a precedent for type-gated sections).
3. If t001 gave them a wake path, the hint's wake sentence needs to describe it accurately for a private service — "the next request" means something different in-cluster.
4. `en` and `zh` together.
