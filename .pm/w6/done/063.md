Two more things hold, checked rather than assumed:

- Custom domains are refused with a **type-specific** reason: `POST …/custom-domains {"name":"qa-priv-20260827.example.com"}` → `400 bad request: a private_service has no ingress and cannot have custom domains`. Built once in `apps/domains.go:627-631` (`errNoPublicIngress`) and used from 2 call sites — the create path (`apps/service.go:2332`, gated `!TypePubliclyRoutable(svcType) && len(req.Hosts) > 0`) and the add-domain verb (`apps/domains.go:863`, gated `!app.Spec.PubliclyRoutable()`).

## Part 2 — the residue: `setSubdomainPolicy` tells a non-routable service to do something the product forbids

On that same live private service:

```
mutation { setSubdomainPolicy(id:"srv-da84g6oueu1c7395iqkg", policy:"disabled"){ id renderSubdomainPolicy } }
=> {"data":{"setSubdomainPolicy":null},
    "errors":[{"message":"bad request: renderSubdomainPolicy cannot be disabled without at least one custom domain"}]}
```

A caller who follows that instruction hits the Part 1 refusal — `a private_service has no ingress and cannot have custom domains`. The two guards send them in a circle.

**Root cause:** `lego/backend/internal/apps/service.go:3560-3577` (`SetSubdomainPolicy`) has **no type gate at all**. Its guard is `a.Spec.Host == "" && len(a.Spec.Hosts) == 0`, and its doc comment states the rationale — _"that would leave the service silently unreachable"_ — which only makes sense for a publicly-routable type. A private service, background worker or cron job has no platform subdomain to disable (`EffectiveHosts` returns `nil` before the policy is even consulted) and cannot acquire the custom domain the message asks for.

Same file, same concern, correct instinct: `SetIPAllowList` (`:3579-3583`) carries the comment _"Only meaningful for web_service and static_site"_ — it also has no gate, but a no-op allowlist write is harmless, whereas this one emits a misleading instruction.

**Target behavior:** refuse with a type-specific reason, reusing `errNoPublicIngress`'s shape so the two guards word the same fact the same way — and decide whether `renderSubdomainPolicy` should be reported at all for a non-routable type. It currently reads `"enabled"` on a private service (both in this run's capture and in m46's 2026-08-22 one), which is what makes the mutation look available in the first place. REST, GraphQL and MCP move together; the dashboard needs no change, since it already omits the control for these types.

**Blast radius:** one verb, one call site per surface. The family is the complement of `TypePubliclyRoutable`'s allowlist — `private_service`, `background_worker`, `cron_job`. Verified live for `private_service` only; the other two share the identical type-agnostic guard by inspection (the function references no type), which is why they are stated here as reasoned rather than probed.

**Severity: minor.** The outcome is correct — the mutation *should* be refused — only the reason is wrong, and the dashboard never exposes the control for these types, so this is an API/MCP-caller defect. It is worth fixing on the `w7/m80` precedent: that milestone treated an MCP description promising _"restore the platform default /"_ as _"the contract an agent reads, so a stale one is a live defect, not a typo"_. An agent told to add a custom domain here will loop.

## Estimate

~45m: add the type gate with a type-specific message, decide the reporting question for `renderSubdomainPolicy` on non-routable types, one regression test per affected type.
