## Objective

Show that a request held through a cold start survives the activator pod being replaced, and record how often the activator holds requests.

## Context

- Gate: a production pin whose producer contains this milestone's commit.
- Production access: `scripts/fetch-app-kubeconfig.sh` with `BEX_SSH_KNOWN_HOSTS_FILE` pointing at a temp file holding `* <key>` from `~/.ssh/bex_cp_host_ed25519.pub` (w3/m472). Signed-in API calls go through `bash scripts/qa-login.sh`.
- Lining a held request up with a production deploy is timing-sensitive; the local cluster (`bash scripts/mock-cluster.sh operator`, then `kubectl rollout restart` of the activator) is an accepted substitute, recorded as such.

## Steps

1. Read the activator's held-request volume over a recent day (logs or metrics), read-only.
2. Hibernate a free fixture web service in `bex-canary` (or on the local cluster) and send a non-HTML request; while it is held, replace the activator pod that holds it.
3. Record the response (status, time) and the pod events.
4. Delete the fixture by id (`GET` answers 404).

## Record

Ran on the **local cluster** 2026-11-19 (no production deploy lines up with a held request; the accepted substitute). Production's first deploy carrying this commit still replaces activator pods that run the old binary, so it is the second such deploy that drains on production.

- **Held-request volume (production, read-only, Prometheus `traefik_service_request_duration_seconds` on the `tea-*-bex-activator-*` aliases).** Last 24 h to 2026-11-19 04:20Z: 166 requests to sleeping or not-ready Apps, all answered `503` in under 0.5 s, none held. Last 7 days: 5,172 requests; about 41 took over 1 s (held through a wake), about 12 ended `200`, 42 `499` (the client gave up first) and 1 `502`. The unclaimed-host fallback (`bex-system-bex-activator-8888`) took about 40,600 requests a day, almost all `404`.
- **Setup.** Image `bex-operator:m485` built from this tree and imported on every node; only `bex-system/bex-activator` was pointed at it, with grace 150 and `maxUnavailable: 0`, `maxSurge: 1`. Fixture App `default/m485-held` (`busybox:1.36`, `sleep 15; exec httpd -f -p 8080 -h /etc`, host `m485-held.onbex.co`, `idleTTLSeconds: 120`) left to auto-hibernate; then `GET /hostname` with `Accept: application/json` through Traefik's `websecure` entrypoint, and `kubectl rollout restart deploy/bex-activator` 2 s later.
- **Result (m485 image).** `200` after 20.5 s with the App's own body (`m485-held-k6fbq7fadj1bmhbiue4v`) and no `X-Render-Routing`; Traefik logged `DownstreamStatus 200`. The pod holding it (`bex-activator-5c4b46b688-jrwjb`) logged `waking app` at 04:35:30, got `Killing` and logged `draining` at 04:35:44, and logged `drained` at 04:35:54, the end of its window. An earlier run (`POST`, which busybox httpd answers `501`) was answered by the App 5 s after its pod's window ended, so the request also survives the listener closing; another, whose wake the fixture's then 30 s idle window cut short, held its request through SIGTERM to the 90 s hold bound and answered the activator's `504`, with `drained` logged at that moment.
- **Control (pre-m485 image, same procedure).** `502 Bad Gateway` after 13.5 s: the holding pod `bex-activator-f7d746f84-rxjrc` logged `waking app` at 04:38:45 and got `Killing` at 04:38:49, when Traefik answered `502`.
- **Cleanup.** The local activator was put back on `bex-operator:dev`, grace 30 and its old strategy. Fixture deleted: `kubectl -n default get apps.app.bex.co m485-held` answers `NotFound`.
