## Three new bugs this verification found — all fixed + regression-tested here

**BUG 1 (serious) — plan limits were bypassable through the pending-invite window.** Proved on real prod: a **hobby** workspace (member cap 1) ended up with **2 accepted members**. Invite on Pro → downgrade to Hobby (`ChangePlan`'s guards count only *accepted* members, never pending `tenant_invites`) → the invitee joins on first login, and `store.AcceptInvitesForEmail` redeemed the invite with **no plan check at all** — no member cap, no `RoleAllowedOnPlan`. A pending `developer` invite would likewise land a role Hobby forbids.
**Fix:** enforce the plan at **accept time** (`lego/backend/internal/store/members.go` — `planAllowsJoin`), the one point every path to a `tenant_members` row passes through; a violating invite is left **pending** (fails closed without ever blocking a login) and self-heals if the workspace upgrades again. Regression test `TestAcceptInviteRespectsPlanLimits` **fails before the fix** (`hobby workspace redeemed a 2nd member: accepted 1, want 0`) and passes after. `planAllowsJoin`'s member-count query reuses `store.CountTenantMembers` (given a small `queryRower` seam so it works inside `planAllowsJoin`'s transaction too) rather than a second copy of the same SQL — caught and fixed by this milestone's own `/simplify` pass.

**BUG 2 — bex-api cannot list `jobs.batch`; usage build-seconds metering is silently broken on prod.** `kubectl -n bex-system logs deploy/bex-api` loops on `usage: build_seconds list jobs …: jobs.batch is forbidden`, and `kubectl auth can-i list jobs.batch --as=…:bex-api` → **no**. Same species as m11's missing `keyvalues` grant: `usage.queryBuildSeconds` lists build Jobs in the apps namespace, so the rollup fails closed on every reconcile and build seconds are under-reported platform-wide.
**Fix:** a read-only `batch/jobs` rule on the namespace-scoped Role (`deploy/gitops/base/bex-api-apps-rbac.yaml`), where the other apps-namespace grants deliberately live.

**BUG 3 — a stale positive-TTL cache 403'd the workspace switcher for up to 30s after a self-delete.** Proved live: delete a workspace, and the very next `query Workspaces { ... }` call (the switcher's own list query) came back `{"errors":[{"message":"forbidden"}]}` — even though the account still owned a second, untouched workspace. Root cause: `api.tenantService.Tenant` (`internal/api/tenancy.go`) caches a caller's resolved "current workspace" for `core.PositiveTTL` (30s); `workspaces.Service.Delete` revoked the OpenFGA tuple on the deleted tenant but never evicted that cache entry, so `core.Base.Authorize` — which every verb, including `List`, gates through — kept resolving the caller (and every other revoked member) to the now-deleted, now-tuple-less tenant and 403'd. Waiting out the 30s TTL and retrying confirmed the theory (the switcher recovered on its own once the cache entry expired).
**Fix:** `TTLCache.Delete` (`internal/core/http.go`, the cache had no eviction primitive before this) + `tenantService.InvalidateTenant` (`internal/api/tenancy.go`, evicts both possible `core.Identity.Method` cache-key variants since the caller only knows the subject) + a new optional `TenantResolutionInvalidator` seam (`internal/workspaces/service.go`, type-asserted off `Base.Workspace`, mirroring the existing `WorkspaceGranter`/`WorkspaceRevoker` pattern) that `Delete` calls for every member it revokes. Regression tests: `TestInvalidateTenantEvictsStaleCachedResolution` (api package, proves both cache-key variants evict), `TestDelete_InvalidatesEveryMemberTenantResolution` (workspaces package, proves every revoked member — not just the deleting caller — gets invalidated) and `TestDelete_ToleratesResolverWithoutInvalidation` (the seam is optional). A 4-agent `/simplify` pass (reuse/simplification/efficiency/altitude) confirmed the fix sits at the right layer — protecting every `Authorize`-gated verb uniformly (`Create`, `GetWorkspace`'s `own-` path, and `List` all resolve through the same cache) rather than special-casing `List` alone, which would have left `Create` still riding the stale cache post-delete.
