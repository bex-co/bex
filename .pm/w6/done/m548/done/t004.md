## Objective

Every way to attach a disk leaves the service at the default delay, recorded as a setting change, and the operator never projects a custom grace for a disk-bearing App.

## Context

- Attach paths: REST `POST /v1/disks` and GraphQL `addDisk` and MCP `add_disk` (`lego/backend/internal/apps/disks.go:104,619,722`), a create with `serviceDetails.disk`, a Blueprint adding a disk.
- Operator grace: `terminationGracePeriodSeconds(shutdownDelay, drain)` in `lego/operator/internal/controller/deployment_projection.go`.
- t001's production count of Apps holding both.

## Steps

1. On attach, clear a custom `maxShutdownDelaySeconds` in the same write, with the setting-change event the other settings record.
2. The operator uses the default for a disk-bearing App whatever the spec holds.
3. Return the Apps t001 counted to 30 s through the same path, once, and record their ids here.
4. Tests for each attach path and the operator projection.

## Files

- lego/backend/internal/apps/disks.go, deploy.go, blueprint_plan.go, lego/operator/internal/controller/deployment_projection.go and tests

## Acceptance criteria

- [x] Each attach path reads back 30 s and records the change; the projected grace is 30 for a disk App with a custom spec value
- [x] The production Apps holding both are back at 30 s, ids recorded
- [x] Backend and operator suites and `make lint` pass

## Out of scope

- Restoring a delay on detach

## Record (2026-11-21)

Steps 1, 2 and 4 done; **step 3 waits for the production pin.**

- `AddDisk` (`disks.go`), behind REST `POST /v1/disks`, GraphQL `addDisk` and MCP `add_disk`, clears `maxShutdownDelaySeconds` in the write that attaches the disk, and records `max_shutdown_delay_changed` when the delay it ran with changes (a custom one; an explicit 30 is cleared silently). A Blueprint `disk` applier does the same (`blueprint_plan.go`), and the sync records the change through its setting events. A create carrying both takes only 30 and stores nothing (t002).
- `AppSpec.ShutdownDelaySeconds` (`lego/types`) is nil for a disk App. The operator projects the grace from it (`deployment_projection.go`), so a disk App's `terminationGracePeriodSeconds` is 30 whatever its spec or a rolled-back release holds, and so does every bex-api read and the Blueprint export.
- Tests: `TestAttachingADiskReturnsACustomShutdownDelayToTheDefault` (REST, GraphQL, MCP × custom, explicit 30, none: spec cleared, reads 30, events), `TestBlueprintDiskSyncRecordsTheShutdownDelayReset`, `TestGenerateBlueprintOmitsADiskServicesShutdownDelay`, and the operator's `TestTerminationGracePeriod/a_disk_App_keeps_the_default_delay_whatever_its_spec_holds` (web and worker params, spec 300). `make test` and `make lint` pass.
- **Step 3, open:** t001 counted one App, `srv-dbnun74vg1gs7387qojg` (twenty-crm, workspace `bex`, 120 s). It goes through the new path once the pin carries this change: the operator then runs it at 30 s (one `Recreate` roll on the upgrade, the only disk App whose template changes), and `PATCH /v1/services/srv-dbnun74vg1gs7387qojg` with `{"serviceDetails":{"maxShutdownDelaySeconds":30}}` as the QA user, an admin in `bex`, clears the stored 120 and records `max_shutdown_delay_changed`. Doing it before the pin would only store an explicit 30 that the running release ignores until its next deploy.
