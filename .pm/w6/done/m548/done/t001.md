## Record (2026-11-21)

**Render's rule, read 2026-11-21:**

- [Persistent Disks](https://render.com/docs/disks), "Disk limitations and considerations": "You can't change the shutdown delay for a service with a persistent disk."
- [Deploys](https://render.com/docs/deploys), "Setting a shutdown delay": "You can't customize the shutdown delay for a service with a persistent disk." The same section documents setting the delay through the API's Update service endpoint and `render.yaml` only. It documents no dashboard field.
- [Blueprint spec](https://render.com/docs/blueprint-spec): `maxShutdownDelaySeconds` is "an integer between `1` and `300`, inclusive", default `30`. Neither it nor the `disk` section mentions the rule.
- The pinned spec (`render-public-api-1.json`) types `maxShutdownDelaySeconds` 1–300, default 30, on the web, private and worker details, POST and PATCH. It says nothing about disks.

**Render's error wording (verified through third-party quotes, not reproduced against Render):** Render's Blueprint validator answers `services[0].maxShutdownDelaySeconds`: "max shutdown delay is not supported for services with a disk". Public `render.yaml` fixes quote it: [quangshuynh/flipper#51](https://github.com/quangshuynh/flipper/pull/51) (2026-09-27) removed `maxShutdownDelaySeconds: 30` beside a disk, and [drwatson93/ThetaBot#3](https://github.com/drwatson93/ThetaBot/pull/3) (2026-09-26) removed `60`. So the validator refuses the field at any value, the default included. No API error text or dashboard copy for the rule was found: **unverified**.

**What bex does:**

| case | rule | evidence |
| --- | --- | --- |
| Blueprint declares `disk` and `maxShutdownDelaySeconds` | refused at `services[i].maxShutdownDelaySeconds` with Render's sentence, at any value | verified (the quotes above) |
| REST, GraphQL, MCP set a delay other than 30 on a disk service, or create carries both | `400` with the same sentence | Render's rule verified; its API wording **unverified** |
| the same surfaces set exactly 30 on a disk service | accepted, stores nothing (a no-op, or clears a value left from before the rule). bex reads 30 back for a disk service, so a client writing back what it read is not refused | bex's choice, **unverified** |
| attaching a disk to a service with a custom delay | the delay returns to 30 s in the attach write, recorded as `max_shutdown_delay_changed` | bex's choice, **unverified** (Render documents only the rule) |
| detaching a disk | restores nothing; the delay stays 30 s | bex's choice, **unverified** |
| reads, the operator's pod grace, Blueprint export | 30 for a disk App whatever its spec or a rolled-back release holds; the export omits the field | follows from the rule |
| dashboard | Max shutdown delay reads 30, read-only, with Render's docs sentence and a link to the Disk tab | Render documents no dashboard field for the delay, so its copy is unverified |

**Production, 2026-11-21** (`kubectl get apps.app.bex.co -A -o json` on the app cluster through `scripts/fetch-app-kubeconfig.sh`): 28 Apps, 7 with a disk, 2 with a custom delay, **1 with both**: `srv-dbnun74vg1gs7387qojg` (twenty-crm, workspace `bex` `tea-d98210cbbpdc73dcrkvg`, Standard, `maxShutdownDelaySeconds: 120`, Deployment `Recreate` with `terminationGracePeriodSeconds: 120`). t004 returns it to 30 s.
