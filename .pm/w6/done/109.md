# 109 — pg-operand verifies its image before pushing it

Why: every failed pg-operand gate leaves an unsigned, unverified `bex-operator:<ver>-postgres-<sha>` tag in GHCR.

- **Evidence:** `.github/workflows/pg-operand-image.yml` builds with `push: true` (line ~114) and only then runs "verify the allowlist on the pushed digest" (~130); the gate has failed on every run since 2026-10-31 (w8/m92, w8/234). `bexOperandImages` is empty, so production does not use them, but a stray tag can be picked up by hand.
- **Do:** build and verify locally first (`--load`, or an OCI layout per platform), run `deploy/pg-operand/check.sh` against it, and push + sign only after it passes; if the multi-arch build cannot load, push to a scratch tag and delete it on failure.
- **Done when:** a failing gate run leaves no new `-postgres-` tag in GHCR.

- **Done 2026-11-08:** `9790e9e45` builds to an OCI layout, gates each platform from a job-local `registry:3` (dockerd shares the runner netns), and only then publishes the same layout with `oras cp`, refusing a GHCR digest that differs from the gated one. Run `42456500246`: all six majors failed `check.sh` (the known w8/m92 Timescale/IMMV restore), and GHCR gained no `-postgres-` tag (57 before and after, 0 for `9790e9e45`). The publish step itself first runs when w8/m92's gate passes; watch that run's "publish the gated image" step.
