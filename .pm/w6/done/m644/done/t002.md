## Objective

A script that takes one `render-examples` repo, deploys its `render.yaml` unchanged into `bex-canary` through bex-api, waits for every resource's first deploy, runs the template's check, prints one result line, and deletes everything it created.

## Context

- Use the repo-connected Blueprint path, as Render's one-click deploy does: REST `POST /v1/blueprints` with the repo, then approve the first plan (the calls `bex ea blueprints create --repo https://github.com/render-examples/<repo>` makes). A template's services usually name no `repo:`, because Render takes the Blueprint's own repo. `scripts/app-apply.sh` sends a local file, so it is not the right path here.
- Authentication: `BEX_API_URL` plus an API key for `bex-canary`, the QA user's workspace (`scripts/lib/first_party_workspaces.txt`; the QA credentials are in `.env`). Never print or commit the key.
- Create the Blueprint's resources in a new project of their own named `render-examples-live-<repo>` and marked `(disposable)` wherever the board names it. Deleting the project and the Blueprint must leave nothing behind, Postgres, Key Value and disks included.
- The repository rule on evidence: no `json`/`log`/`stdout` file under `.pm/`, and no raw output committed anywhere. The script writes to stdout only.

## Steps

1. Create the Blueprint from the repo and approve its plan. A refused create or plan is stage `validate` or `plan`, reported with bex's error.
2. Poll each created resource until its first deploy is live or failed. The stages are `build`, `deploy` and, for datastores, `provision`. Cap the wait (build 120 min and pre-deploy 30 min are Render's own limits; a lower cap for the whole run is fine) and report a timeout as its own outcome.
3. Run the check from t001's table: an HTTPS request to the service's `onbex.co` URL for a web service; for a worker or cron job, the log line it names (through `GET /v1/logs`).
4. Print one line: `<repo> <outcome> <stage> <detail>`. The outcome is `live` or `failed`; the detail is the first error line, with other tenants' ids hashed (`scripts/lib/public_log.py`).
5. Delete the Blueprint's resources and project, even after a failure (`trap`), and confirm that none remain.
6. Support `--keep` to leave a failed template's resources up for triage, and say in the output that they must be deleted by hand.

## Acceptance criteria

- [x] One known-good template (for example `render-examples/express-hello-world`) prints `live` against production, and `bex-canary` holds nothing afterwards.
- [x] A template whose check fails prints `failed` with the stage, and still cleans up.
- [x] `shellcheck scripts/render-examples-live.sh` is clean.
