# Large exec output that ends with the process is truncated in Kubernetes' exec path (gateway and kubectl alike)

Why: `ssh srv-…@ssh.bex.co 'pg_dump …' > dump` or any large `cat`/`head` through the Render-documented SSH path loses the tail of its output when the command exits right after writing it, so a data export silently comes out short.

- **Evidence (2026-10-29, production, pin `b63b8a1091d7`):** in `beancount-forum` (`srv-d9nqg9dcavls73fp8m2g`), `head -c 20000000 /dev/urandom` returned 17,178,624 and then 14,794,752 bytes through the gateway, and all 20,000,000 with `; sleep 40` appended. `kubectl exec … -- head -c 20000000 /dev/urandom` from a laptop with kubectl v1.37.0 returned 19,181,563 over WebSocket (`Copying stdout failed: read message: unexpected EOF`) and 14,393,344 over SPDY (`KUBECTL_REMOTE_COMMAND_WEBSOCKETS=false`). Outputs of 1 MB and 5 MB arrive whole.
- **Not the gateway:** client-go's SPDY v4 `stream()` waits for the stdout copy (`tools/remotecommand/v4.go:73-78`), and kubectl through the kube-API LB truncates without the gateway. Suspects, in order: containerd 2.3.3 exec IO not draining the pipe when the process exits, kubelet's CRI streaming proxy, and kube-apiserver's upgrade proxy.
- **Look at:** reproduce with `crictl exec` on the node (bypassing apiserver and kubelet). Then compare containerd's exec IO handling for a known fix. If upstream, pin the patched containerd in the node image (`infra/packer`).
- **Expected:** the exec stream delivers every byte the process wrote before its exit status.

## Bisect — 2026-10-29

- **containerd is clean:** on node `bex-tenant-0-tghbn-sc7vl` (containerd v2.3.3 `aad11006b869`), a short-lived privileged `kube-system` pod ran `ctr -n k8s.io task exec … head -c 20000000 /dev/urandom | wc -c` against the same `beancount-forum` container, three times. All three returned 20,000,000 bytes. The pod was then deleted. The node image has no `crictl`.
- **So the loss is above containerd's task IO:** in the CRI streaming server (containerd's CRI plugin `Exec` URL), kubelet's streaming proxy, or kube-apiserver's upgrade proxy. Both client protocols lose data (WebSocket and SPDY).
- **Next:** put a pinned `crictl` on the node (or into the debug pod) and run `crictl exec` to test the CRI streaming server alone. If clean, test kubelet's `/exec` with its client cert. Then match the failing layer to its upstream issue and fix (version bump in `infra/packer` or a kubelet/apiserver flag).

## Root cause — 2026-10-29 (kube-apiserver's upgrade proxy drops the tail for a slow reader)

Layer-by-layer, `head -c 20000000 /dev/urandom` in `beancount-forum` (node `bex-tenant-0-tghbn-sc7vl`):

| Path | Result |
| --- | --- |
| `ctr task exec` (containerd) | 3/3 × 20,000,000 |
| `crictl exec` (CRI streaming, hostNetwork debug pod) | 5/5 × 20,000,000 |
| SPDY straight to kubelet `/exec` (apiserver-kubelet-client cert, from a CP node) | 3/3 whole, and 2/2 whole with a reader that stalls 10 s |
| kubectl → local kube-apiserver `10.10.0.13:6443`, fast reader | 6/6 whole (SPDY and WebSocket) |
| kubectl → local kube-apiserver, reader stalls 10 s | **4/4 short**: SPDY 19,980,288 / 19,820,544, WebSocket 12,386,304 / 10,625,024 |
| laptop kubectl, ssh gateway (slow readers via the API LB / in-cluster) | short (see above) |

**Mechanism:** `k8s.io/apimachinery/pkg/util/proxy/upgradeaware.go:413-452` (unchanged in v0.37.1; production apiserver v1.34.9) copies each direction in a goroutine and returns as soon as either finishes, and its defer then closes the other half. When the process exits, kubelet closes the backend. A slow client is still sending flow-control frames, so the client→backend copy fails first and the proxy returns. The backend→client copy, still draining buffered stdout, is cut off. A fast reader drains before that happens.

Every debug pod (`w6-099-ctr`, `-crictl*`, `-kexec`) and the temporary `crictl` binary were removed.

**BLOCKED (2026-10-29): needs a user decision.** A fix in kube-apiserver itself would mean a fork, which is out of bounds.

- **(a) Gateway drain buffer (recommended now):** the SSH gateway reads exec stdout/stderr from the apiserver as fast as it arrives, into a bounded per-channel buffer (memory first, then spilling to the pod's ephemeral disk), and forwards it at the client's pace. Customer `ssh` exports become whole up to the bound. Cost: gateway memory/ephemeral storage, which needs a chosen cap (e.g. 64 MiB RAM + 2 GiB disk per channel, under the channel limiter). Web Shell and `kubectl` stay affected.
- **(b) Upstream report (also recommended):** file an issue and patch at kubernetes/kubernetes (the proxy should keep copying backend→client after the client→backend half fails, until the backend EOF drains), then take it with an apiserver bump. This is an external publication and needs the user's OK.
- **(c) Exec straight to kubelet from the gateway:** rejected. It needs kubelet client credentials in the gateway, a privilege escalation.

## Decision — 2026-10-29

- **IDs:** w6/099. **Source:** explicit user decisions in `/unblock w6`: D5 = memory-only gateway buffer, 64 MiB; D6 = file upstream directly.
- **D5, gateway drain buffer, memory only:** the SSH gateway's exec path (`internal/sshgateway/nativessh/session.go` `runExec` → `KubeExecutor.Execute`) puts a bounded in-memory buffer of at most 64 MiB per channel between the apiserver stream and the SSH channel, for stdout and stderr together. The apiserver stream is read at full speed until the buffer is full, then backpressure applies as today. There is no disk spill (option rejected by the user). Acceptance:
  - Live on production after deploy: `ssh srv-…@ssh.bex.co 'head -c 50000000 /dev/urandom' | wc -c` returns exactly 50,000,000 three times out of three from a laptop.
  - Unit test: a stalled SSH reader does not slow the executor's writes until the cap is reached, and exit status still follows the drained output.
  - Gateway memory: the per-channel cap stays under the existing channel limiter. Check the gateway pod memory limit and raise it if `maxChannels × 64 MiB` would exceed it. Record the arithmetic.
  - Outputs beyond ~64 MiB plus in-flight can still lose their tail until upstream is fixed. Document this in ADR035 (SSH).
- **D6, upstream:** file an issue at kubernetes/kubernetes with the layer-by-layer repro above (slow reader through kube-apiserver vs. direct kubelet) and the `upgradeaware.go:413-452` mechanism, using the user's `gh` identity (authorized). Open a PR making the proxy keep copying backend→client after the client→backend half ends, until the backend copy finishes (with a bounded grace), plus a unit test. The PR needs the CNCF CLA for the account. If the CLA check fails, leave the PR open, record the link, and name "user signs the CNCF CLA" as the remaining gate. Record both links here.
- **Next (worker):** implement D5, ship it, verify it live, then file D6. 099 closes when D5 is verified live and both upstream links are recorded. The upstream merge and an apiserver bump are a separate follow-up.

## D5 implementation — 2026-10-29

- `internal/sshgateway/drain.go`: `DrainingExecutor` wraps the `KubeExecutor` for every gateway exec path (native SSH, Web Shell, agent attach). Exec stdout/stderr go into a `golang.org/x/sync/semaphore` budget, 64 MiB per channel (blocking that channel only) and 128 MiB per process (non-blocking: when it is spent a channel writes straight through). Close waits for the drain, or discards on context end. A panic still returns the budget. Env: `BEX_SSH_DRAIN_BUFFER_PER_CHANNEL` and `BEX_SSH_DRAIN_BUFFER_TOTAL` (`0` disables), recorded in lego/backend/AGENTS.md. Gateway memory limit raised from 256Mi to 512Mi to hold the 128 MiB process budget (2 replicas).
- Tests (`-race`): read-ahead of a stalled client with exact ordered bytes and the exit code after the drain; backpressure at the per-channel cap; a spent global budget falls back to direct writes; cancel with a stalled client returns; panic returns the budget; forwarding errors surface; disabled budget passes through. ADR035 § SSH protocol and exec behavior updated.
- **Remaining:** live 50 MB check after deploy, then D6 upstream issue and PR.

## D6 outcome — 2026-10-29

- **Already filed upstream, so no duplicate:** kubernetes/kubernetes#142376 "Exec drops end of stdout when client reads slowly" (opened 2026-09-24, `triage/accepted`, assigned to seans3) reports the same loss. The fix is in flight: PR #142461 "exec/attach: let the client close the connection so no output is lost", now being split into a client-go change, then translator + wsstream, then cri-streaming behind a KEP. A second issue and PR would only have duplicated it.
- **Done instead (within the user's authorization to submit):** a comment with this cluster's layer-by-layer matrix (v1.34.9, containerd 2.3.3) and the gateway-buffer mitigation: https://github.com/kubernetes/kubernetes/issues/142376#issuecomment-6510332127. It was edited the same minute to say the mitigation is unit-tested and rolling out, not yet verified live.
- **Follow-up:** once #142461 or its client-go part ships in a release, bump the apiserver/kubelet (and client-go in the gateway) and re-run the 20 MB slow-reader check. Not a w6 gate.
