# An SNI-proxy roll could hold its external clients for up to an hour, once the deploy's wait stops counting draining pods

Why: w6/m515 drains `bex-kv-sni-proxy` and `bex-pg-sni-proxy` for 30 s, so a held external Key Value or Postgres client (a pool, a pub/sub subscriber, an idle `psql` session) is still closed without notice on each deploy that changes an SNI binary, up to about 40% of production deploys. Render breaks such connections only in announced maintenance. A bound up to the proxies' 1 h idle timeout would close only clients that stay active for an hour after the roll.

- **Filed by** w6/m515 t005 (2026-11-19), as the longer-bound variant its Design weighed. It applies once w6/m515 has shipped: that milestone is parked in [`m515`](../m515/README.md), its code in stash `loopx/w6/m515`.
- **Render:** see [platform maintenance](https://render.com/docs/platform-maintenance) (read 2026-11-19), and w6/145 for the per-store proxy's version of the same gap. w6/145's per-store deferral cannot apply here, because one SNI pod serves every store and database on its node.
- **What blocks a longer bound today.** `kubectl rollout status daemonset/…` reads each node's oldest pod (the DaemonSet controller's `updatedNumberScheduled`), so it waits until every draining pod is gone. On the local cluster on 2026-11-19, a `maxSurge: 1` DaemonSet whose old pod took 90 s to stop took 91.5 s to report `successfully rolled out`. `scripts/operator-pins.sh wait` gives each SNI DaemonSet 300 s after its image wait, so a bound near 300 s or more fails the deploy. The wait must instead pass once every node runs a Ready pod of the new revision (`controller-revision-hash` or `pod-template-generation`), and ignore terminating pods.
- **Weigh before building:**
  - Memory: two pods of up to 512 Mi each share a node per proxy while one drains. The old pod's footprint shrinks as its streams end.
  - A deploy that lands within the bound: three pods per node.
  - Egress metering: `ByteMeter.Add` counts a stream's bytes only when it closes, so a stream that closes less than one scrape interval (15 s) before its process exits is never billed. That holds for any bound and predates w6/m515, which already bills more than before: until then a roll lost every open stream's bytes.
  - The grace period becomes the 5 s `preStop` pause plus the bound plus a margin. Kubernetes evicts no DaemonSet pod in a node drain, so a node drain does not wait for it.
- **Done when:** both DaemonSets drain for the chosen bound, the deploy's wait passes as soon as each node's new pod is Ready, ADR021 § 10 states the new bound, and on production a client kept active across an SNI-moving deploy keeps its connection until the bound.
