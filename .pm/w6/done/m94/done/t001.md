## Objective

Before changing reconcile ordering, confirm how reliably the race reproduces, measure roughly how wide the window is, and enumerate every code path that could hit it — so t002 fixes the real mechanism instead of a guess.

## Context

- Live-reproduced 2026-08-25 (`qa-20260825-sleep`, Free tier, `idleTTLSeconds=45`): the first `curl` immediately after `server.phase` read `Hibernated` got a raw Traefik `503 no available server` (no `Retry-After`, `content-type: text/plain`) instead of bex's documented wake contract (`docs/render-artifacts/wake-interstitial.md`: `503 {"error":"service hibernated","retryAfter":5}` for a non-HTML `Accept`, with `Retry-After: 5`). Three follow-up requests ~20s later all got the real app's `200`.
- `grep -rn "no available server" lego/ deploy/ infra/` returns zero hits — confirmed this string is Traefik's own "zero ready endpoints" message, not bex's.
- Root cause candidate: `lego/operator/internal/controller/app_controller.go`'s `reconcileKubernetes` writes the Deployment (`CreateOrUpdate` at `:1611-1626`, already carrying `replicas: 0` for an auto-hibernating App, computed by `desiredReplicas` at `:1730`) **before** `ingressBackend` (`:1661`, which swaps the Ingress backend to the App-owned activator alias via `reconcileActivatorAlias` at `:2686`) and `reconcileIngressWithMiddlewares` (`:1666`, which actually applies the new Ingress backend). These are two separate, non-atomic Kubernetes API writes that Traefik's informers pick up independently and asynchronously — a request can land after the Deployment's pods have dropped out as ready endpoints but before Traefik's dynamic config has picked up the Ingress backend swap to the (always-ready) activator alias Service, hitting the App's own now-empty Service instead.
- **Confirmed distinct from `w6/m47`** (done 2026-08-23): that was a structural, always-reproducing 404 (`bex-activator` named directly instead of via a per-App alias, so the backend Service didn't exist in the tenant namespace at all — different Traefik error, "404 page not found", never self-resolved). This is a transient race that self-resolves on retry within the advertised window — the wake mechanism itself works, but the very first request can lose a timing race and see raw infra output instead of the documented contract.
- `desiredReplicas` (`:1730`) and `ingressBackend`/`parkKubernetes` (`:1710`, `:1755`) each have exactly one call site in `reconcileKubernetes` — confirm this holds (single reconcile path for every App type that can auto-hibernate; workers are excluded per `:1729`'s comment, cron/private services need checking).

## Findings (2026-08-25)

**Verdict: the race is real, the root cause is confirmed, and it has a second, worse sibling on the resume path that the filing listed only as a question.**

**Call-site claims confirmed by grep** — `ingressBackend`, `parkKubernetes`, `reconcileActivatorAlias` and `desiredReplicas` each report 2 hits, being one definition plus exactly one call. Single reconcile path, as assumed. `grep -rn "no available server" lego/ deploy/ infra/` returns zero hits, confirming the string is Traefik's own.

**Ordering confirmed by reading `reconcileKubernetes`:** the Deployment `CreateOrUpdate` (already carrying `replicas: 0`) is at `:1611`; `ingressBackend` is at `:1661` and `reconcileIngressWithMiddlewares` at `:1665`. So the scale-down write genuinely precedes the route swap, and the two are separate non-atomic API writes Traefik ingests independently. The window is real.

**Reproduction rate: not measured, and deliberately not pursued.** The DoD's live trials need `dashboard.bex.co`, and the deploy pipeline has been red since 2026-08-24 (`w6/040`), so no rate could be gathered this session and no fix could be live-verified. The code-level confirmation above is what this task rests on instead; the live leg moves to `w6/040`.

### The resume race (step 4) — in scope, and the more serious of the two

Walking the wake path settles the question the task left open. The activator does **not** proxy: it returns `503 {"error":"service hibernated","retryAfter":5}` with `Retry-After: 5` (`cmd/activator/main.go:199-208`) and stamps `lastActive`. That stamp makes `shouldAutoHibernate` false on the very next reconcile, so `ingressBackend` immediately hands the route back to the App's own Service (`:1755`, the `return app.Name` branch) — while the Deployment has only just been scaled up and no pod is ready.

The client then retries at exactly the second bex told it to and hits an Ingress pointing at a Service with zero ready endpoints: the same raw `no available server`. That is not a narrow timing race like the hibernate side — it is close to deterministic for any app that takes longer than ~5s to become ready, and it happens on the path the user is actively waiting on. **Folded into t002.**

### Decided fix (both directions)

1. **Readiness-gated routing.** `ingressBackend` routes through the activator whenever the App has no ready endpoint _and_ the activator is its wake path — not only once the idle TTL has elapsed. This is the structural fix: the public Ingress never names a Service that has nothing to serve. `shouldAutoHibernate`'s non-time conditions are split out as `autoSleepEligible` for it to reuse.
2. **Route-before-drain, with a grace.** On the pass that decides to hibernate, write the activator route and keep the pods, then requeue after `hibernateRoutingGrace` (10s) and scale down on the next pass. Reordering alone was rejected for exactly the reason this task flagged — it only narrows the window, since Traefik's propagation is asynchronous and the operator cannot observe it. Buying a bounded amount of time is the honest way to cover an unobservable dependency, and the App has already been idle for its whole TTL so the wait costs nothing.

**Maintenance mode is exempt from (2)** — caught by an existing test rather than by inspection. Its own alias owns the public route, so draining the App's Service cannot surface a raw 503; worse, holding there would never resolve (the Ingress will never name the activator while maintenance owns it) and the workload would stop hibernating entirely, breaking the routing/replica independence `ingressBackend` documents.
