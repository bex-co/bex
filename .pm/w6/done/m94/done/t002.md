## Implementation (2026-08-25)

Both directions closed, per t001's decision.

**Readiness-gated routing (`ingressBackend`).** The activator now holds the public route whenever the App has no ready endpoint and the activator is its wake path — `autoHibernating || (!serving && r.ActivatorService != "" && autoSleepEligible(app))`. `serving` is `dep.Status.ReadyReplicas > 0`, read off the Deployment `CreateOrUpdate` already fetched, so it costs no extra API call. `autoSleepEligible` is `shouldAutoHibernate` minus the idle-time check, factored out so the routing question ("can the activator serve for this App right now?") and the scheduling question ("should it sleep yet?") stop sharing one predicate — they legitimately disagree while an App is waking.

This is what closes the resume race, and it also improves an unrelated case for free: a free-tier App whose pods are not ready for any reason (a fresh deploy, a crash loop) now answers with the documented interstitial instead of raw Traefik text.

**Route-before-drain (`holdHibernateForRouting` + `hibernateRoutingGrace`).** On the pass that decides to hibernate, if the Ingress does not yet name the activator, the App keeps its normal replica count and `parkKubernetes` requeues after 10s instead of parking. The next pass sees the activator route already written, and scales to 0 then. `ingressRoutesToActivator` reads the live Ingress rather than tracking state on the App, so there is nothing to expire or reconcile; an App with no Ingress at all (private service, no resolvable host) answers true and hibernates without the extra pass.

**Why a grace and not just a reorder,** restating t001's call because it is the load-bearing decision: the operator cannot observe Traefik's config propagation — there is no readiness signal for "I have ingested this Ingress" — so no ordering of two non-atomic writes can _close_ the window, only narrow it. A bounded wait is the honest way to cover an unobservable dependency. 10s is deliberately generous: the App has already been idle for its entire TTL, so waiting costs nothing, while being too short reintroduces the very window it exists to close.

### Verified not to disturb the neighbours

- **Maintenance mode** is exempt from the hold, and this was caught by an existing test (`maintenance takes routing precedence over an already auto-hibernated workload`) rather than by inspection — my first cut held unconditionally, which pinned replicas at 2 forever, because the Ingress will never name the activator while maintenance owns the route. Now covered by a dedicated test too.
- **Manual suspend** is untouched: `autoSleepEligible` returns false for a suspended App, so neither the readiness gate nor the hold applies, and `parkKubernetes` parks it exactly as before.
- **Workers** are excluded from both (no Ingress, nothing to route).
- The **full operator suite** (145 specs + the package's plain tests) passes, including every pre-existing hibernate/wake/maintenance test.

### A test that encoded the bug

`TestWakeRestoresAppServiceAsIngressBackend` asserted the route returns to the App's own Service on the first post-wake reconcile — i.e. exactly the racy behavior, since the fake client leaves `ReadyReplicas` at 0. Its stated intent ("the alias is a sleeping-state detail, not a permanent indirection") is right and is preserved; it now asserts the swap-back happens **once a pod is ready**, plus the new negative case that it does not happen before. The concern that this could strand an App on the activator was checked and dismissed: `SetupWithManager` uses `Owns(&appsv1.Deployment{}, ResourceVersionChangedPredicate{})` and watches Pods directly, precisely so status-only changes re-reconcile.
