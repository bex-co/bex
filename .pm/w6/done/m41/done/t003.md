## Objective

Count rejected time-traveled conclusions so informer staleness becomes a readable signal rather than an invisible suppression. A guard that silently drops conclusions is one incident away from being blamed for a missed outage.

## Context

- Without a counter, `t002` is indistinguishable from a bug that drops real edges — exactly the ambiguity that made the original phantom pairs hard to diagnose.
- `.pm/w3/016.md`'s framing: staleness is normal in milliseconds on a healthy control plane and pathological in minutes during an incident. A counter that stays at zero in steady state and climbs during a control-plane incident is the useful shape.
- bex-api already exposes Prometheus metrics; follow the existing naming and registration conventions in the backend rather than inventing a new surface.

## Steps

1. Add a counter incremented whenever `t002`'s guard rejects a conclusion.
2. Label it so the reason is legible (service and/or rejection cause) without unbounded cardinality — do not label with anything tenant-unbounded.
3. Register it alongside bex-api's existing collectors.
4. Sanity-check cardinality against the number of services.

## Files

- `lego/backend/internal/store/reconciler.go` and the backend's metric registration site

## Acceptance criteria

- [ ] A rejected time-traveled conclusion increments the counter.
- [ ] A normal healthy/unhealthy transition does not.
- [ ] Label cardinality is bounded and does not grow with tenant-controlled input.
- [ ] Metric follows the existing backend naming convention.

## Out of scope

- Alerting rules on the new series.
- Dashboard visualization.
