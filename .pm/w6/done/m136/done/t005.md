## Objective

Document and expose whether a capability response used cached checks, and support a fresh (cache-skipping) evaluation for recovery after an access change — without inventing a security guarantee from a timestamp.

## Context

- ADR087 requirement 4. `lego/backend/internal/authz/authz.go:64-80` — positive-only check cache; `core.PositiveTTL = 30s` defined in `lego/backend/internal/core/http.go:503`, wired in `cmd/api/main.go`. Revocation evicts positives only on the processing replica; others retain until expiry.
- Write-relation gates (`can_operate`, `can_create`) already use fresh checks via `core/base.go`; the capability read path may not.
- Client receipt time is "last checked", not proof of membership version.

## Steps

1. Add a fresh-evaluation option (or dedicated field) to the capability query for recovery flows; default stays cached.
2. Surface a `cached` indicator (or documented equivalent) in the response.
3. Document the end-to-end consistency boundary (positive TTL, per-replica eviction, FGA reconciliation) in the contract's doc comment / ADR pointer.

## Files

- `lego/backend/internal/members/service.go`
- `lego/backend/internal/authz/authz.go` (bypass hook if needed)
- `lego/backend/internal/core/base.go`

## Acceptance criteria

- [ ] A fresh evaluation after a revocation observes the denial even while a stale positive sits in another cache path (test with the TTL cache primed).
- [ ] Cached-vs-fresh is distinguishable by the caller.
- [ ] No claim of instantaneous cross-replica revocation appears anywhere in the contract docs.

## Out of scope

- Changing the TTL or the checker's caching architecture; measuring production propagation (m138 telemetry).
