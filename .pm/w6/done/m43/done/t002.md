## Objective

Suspending then resuming a `background_worker` transiently shows the service
status badge as **Sleeping**, with the hint "Sleeping to save resources —
wakes on the next request." A worker has no Ingress and no HTTP endpoint, so
nothing can ever send it a "next request" to wake it on — the operator's own
design comment says as much ("A worker never auto-hibernates — it has no
Ingress, so a request could never wake it," `app_controller.go`). The status
badge derivation doesn't know the service's type, so it shows this anyway
during the brief window where a resuming worker's phase still reads
`Hibernated`. Gate the "sleeping" mapping on service types that can actually
auto-sleep.

## Context

- Root cause: `PHASE_STATUS` in
  `dashboard/src/features/services/lib/status.ts:169-183` maps phase
  `hibernated` to `{ key: "sleeping", variant: "secondary" }`
  unconditionally. `deriveStatus()` (same file, ~line 189) looks up this
  table by `s.phase` alone — it never consults `s.type`.
- The comment already on that table entry
  (`status.ts:178-181`) states the intent precisely: "sleeping" is meant only
  for the free-tier auto-sleep case, "a bex extension over Render" tied to
  `idleTTLSeconds`. `types.ts:349-357`'s `ServiceStatusKey` doc comment says
  the same thing another way.
- Only `web_service`/`private_service` have `idleTTLSeconds`-driven
  auto-sleep at all (per `ServiceView.idleTTLSeconds`,
  `dashboard/src/features/services/types.ts:64` and the operator's
  `autoHibernating = !worker && ...` gate). `background_worker` and
  `cron_job` can reach phase `Hibernated` only via manual suspend/resume, not
  auto-sleep — and manual-suspend is already handled by the earlier
  `if (s.suspended) return {key: "suspended", ...}` branch in
  `deriveStatus()`, so the only way a non-sleep-eligible type shows
  `hibernated` is the transient window on the way back from a resume, which
  is exactly what was observed live.
- Locale strings: `services.statusSleeping` /
  `services.statusSleepingHint` (`dashboard/src/features/services/locales/en.ts:235-244`).
- `service-status-badge.tsx:19` reads `status.key === "sleeping"` to decide
  whether to show the hint — no type-gating needed there once `deriveStatus`
  stops emitting `"sleeping"` for ineligible types.

## Steps

1. In `deriveStatus()` (`status.ts`), branch the `hibernated` phase mapping
   on whether the service type is auto-sleep-eligible
   (`web_service`/`private_service`) instead of using the flat
   `PHASE_STATUS` table lookup for that one phase.
2. For an ineligible type (`background_worker`, `cron_job`, `static_site`)
   reaching phase `Hibernated` outside of manual suspend, pick an accurate
   transitional status instead — most likely reuse `"deploying"` or
   `"pending"`'s variant, or introduce a distinct key (e.g. `"resuming"`) if
   the existing ones read wrong; whichever reads correctly against a real
   resume, verified live.
3. Update `isSleeping()` (`status.ts:203`) if its contract changes.
4. Leave the free-tier web/private sleeping behavior byte-identical — this
   task narrows an over-broad mapping, it doesn't touch the real auto-sleep
   feature.

## Acceptance criteria

- [ ] A `background_worker` moving from Suspended → Running via Resume never
      shows the "Sleeping" badge or "wakes on the next request" copy at any
      point in the transition.
- [ ] A `web_service`/`private_service` on the Free tier still shows
      "Sleeping" / "wakes on the next request" exactly as before after an
      idle-timeout auto-sleep.
- [ ] `isSleeping()` and any other caller of `deriveStatus()` compiles and
      behaves correctly with the narrowed mapping.

## Out of scope

- The Free-tier auto-sleep feature itself, or whether Background Worker
  should offer a Free tier at all (that's `w6/025.md`).
