## Result

**Every new test confirmed red against pre-fix code by actually reverting the fix, not by inspection** — and re-confirmed after t004's refactor, since that changed the gate's shape:

- Operator, with `recordedBuildVerdict`'s Build-condition branch removed (pure pre-w6/m100 semantics): `Ran 3 of 151 Specs … 1 Passed | 2 Failed`. The race spec fails on `releaseGeneration` staying at 1 with no gen-2 Job; the operational-churn spec fails because the old `metadata.generation` comparison re-dispatched the doomed build. The w2/m82 quiescence spec passes in both — as it must.
- Backend, with the `supersededDeployStatus` verdict branch removed: three tests go red on `first deploy = "canceled", want "build_failed"` (plus the empty `failureReason`).
- With the fix in place: all green on both sides.

**No test asserts a mock was called.** Every assertion is on real outcome state — the App CR's `Status.ReleaseGeneration`/`Status.Phase`/conditions and the actual existence of a build Job on the envtest API server; the stored deploy row's `status`/`failure_reason`/`started_at`/`overlap_pending` after driving the real `Reconciler.recordObservations`.

**Cheap extra coverage for the milestone's "Unverified" call sites, without live-hunting each:** the envtest's `trigger()` bumps `spec.restartedAt`, which is *literally* what webhook auto-deploy (`redeployFetched`), `Restart`, `secrets.bumpRestart`, Blueprint sync (`patchChangedStackService`), and `rollout.Snapshot.Stamp` all do — so the operator-side mechanism is covered for all of them by construction, and the test says so. The backend fixture is parameterized on how the second row is opened, covering `CreateDeploy` (manual/webhook/restart shape) and `CreateRollbackDeploy`. What remains genuinely unverified is only the *live* end-to-end for those triggers, which the milestone deliberately carries forward.

**Residual found and documented, not hidden:** `ConditionBuild` is a single slot keyed by condition type, so a *later* generation's build failure replaces an earlier one's — exactly the bound `status.preDeploy` has always had. If two consecutive builds fail faster than one bex-api resync (possible for a clone failure, which fails in seconds), the first row's own verdict is gone before it is read and it falls back to the superseded-row inference (`canceled`). Still strictly better than the permanent strand it replaces, and now stated in the `ConditionBuild` doc comment rather than assumed.
