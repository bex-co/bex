## Objective

`lego/operator/internal/controller/app_controller.go:3761-3765` (`setNotReadyCondition`, the shared body behind `r.fail` at lines 3805-3809) stamps the Ready condition's `ObservedGeneration` from `obj.GetGeneration()` — the App's raw current `metadata.generation` — instead of the release generation the failing build was actually pinned to (`app.Status.ReleaseGeneration` at the moment of failure). When a second deploy's spec patch has already bumped `metadata.generation` before the first deploy's build fails (an ordinary race — see the milestone's Background), this mis-attributes the terminal-failure marker to the *newer* generation. `terminalBuildFailureRecorded` (`app_controller.go:881-886`), gating re-dispatch at line 681, then incorrectly concludes the newer generation already failed terminally and halts the reconcile before `app.Status.ReleaseGeneration` can ever be persisted forward to the newer (queued) generation — stranding it at `queued` forever with no further reconcile ever scheduled for that App.

Fix this so a queued/pending release generation can still advance once the blocking generation's build failure is durably recorded, without reopening the w2/m82 bug this exact code exists to prevent (an already-recorded terminal failure being re-attempted/re-metered on every reconcile, which caused ~20 `Reconciler error` log lines/hour per stuck App before that fix).

- Candidate fix directions (pick and justify one, or another that satisfies the acceptance criteria):
  1. Stamp the Ready condition's `ObservedGeneration` from the generation the build attempt was actually pinned to (e.g. the release generation being observed when `r.fail` is called from the build-failure path) rather than unconditionally from `obj.GetGeneration()` — while auditing every other `r.fail` call site (not just the build path) for the same unconditional stamp, since `setNotReadyCondition` is shared.

## Result

**Chosen direction: (1) with a dedicated carrier — the terminal build verdict now rides its own condition, attributed to the release generation that actually built.**

Direction (1) as literally written (re-stamp Ready's `ObservedGeneration` from the release generation) is not viable on its own: bex-api's `readyReasonForGeneration`/`failureReasonFor` compare Ready against `metadata.generation`, so re-stamping it would have broken the *failed* deploy's own close-out. Direction (2) (fold the release advance into the failure write) does not work either — whatever generation the marker carries, the gate would still match it on the next pass. So:

- `lego/types/v1alpha1/app_types.go` — new `ConditionBuild = "Build"` on the CR contract. Written only on a terminal build failure, `Status=False`, `Reason` = the same build-failure class Ready carries, `ObservedGeneration` = `status.releaseGeneration` (the generation whose build actually ran). No CRD schema change: `status.conditions` is already a free-form `[]metav1.Condition`, so `make manifests` produced no diff.
- `app_controller.go` `r.fail` — writes that condition whenever `IsBuildFailureReason(reason)`, in the **same** status update as Ready, so the two halves can never be observed apart. One place, so every build-failure `r.fail` site in `buildFromSource` (dispatch errors, cap failures, credential failures, and the observed `PhaseFailed` branch) is covered without call-site churn.
- `terminalBuildFailureRecorded` / `buildOutcomeAlreadyRecorded` — read the Build condition and compare against `releaseGeneration(app)`, which `prepareAppReleaseDecision` has already advanced in memory by the time `buildFromSource` runs. A generation whose failure is recorded still matches its own record, so w2/m82 t006 (never re-create a doomed build's Job after its TTL reap) is intact; a *different*, newer, pending generation no longer matches and proceeds.
- `legacyReadyBuildFailure` — upgrade fallback. An App whose build failed under the previous operator has no Build condition, so both gates fall back to the old Ready/`metadata.generation` reading. Without it, every currently-failed App in the estate would re-dispatch its doomed build once on operator rollout.

**Consumer half (needed to avoid regressing the failed deploy, done here rather than deferred):** the operator now adopts the pending generation ~5ms after recording the failure, while bex-api resyncs every 30s (`defaultResyncPeriod`) — so this pass almost always observes the CR only *after* the advance, where a bare generation comparison reads "superseded" and would have closed the deploy that actually failed as `canceled`, with no `failureReason`. `store/reconciler.go` `supersededDeployStatus` now checks the durable verdict for the row's own generation first, and `recordDeploy` sources that row's `failureReason` from it.

## Step-5 audit: other `r.fail` call sites

`setNotReadyCondition`'s unconditional `obj.GetGeneration()` stamp is **left as-is for every non-build caller, deliberately** — it is correct there, not a latent copy of this bug:

- **Rollout/operational failures** (`ServiceFailed`, `IngressFailed`, `DeployFailed`, `NetworkPolicyFailed`, `DiskFailed`, `PublishFailed`, `Cron*Failed`, `Middleware*`, `BadSpec`, …) have **no re-dispatch gate at all** — they retry by design on the next reconcile, so no gate can mis-read them. And bex-api's readers of those reasons (`readyReasonForGeneration`, `failureReasonFor`, `observedImagePullFailure`) all compare against `app.Generation`, so the current stamp is the one they need.
- **Pre-deploy** (`ReasonPreDeployFailed`, `app_controller.go` `failPreDeploy`) is already release-generation-scoped through its own record, not the Ready condition: the operator writes `status.preDeploy.Generation = releaseGeneration(app)` and bex-api's `preDeployStatusFor` compares `pd.Generation != appReleaseGeneration(app)`. Verified by reading both sides — no analogous exposure, no follow-up filed.
- `dbFail`/`kvFail` (Database/KeyValue) have no release-generation concept at all.
