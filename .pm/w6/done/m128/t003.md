## Objective

`build_started`/`build_ended` are Render's own type names on a feed exposed by REST, GraphQL and MCP. Confirm the change is consistent across all of them, and settle whether closing the build on a cancel matches Render or diverges from it.

## Context

- **The parity question is genuinely open.** Render may or may not emit a build-ended event for a canceled deploy. If it does not, `t001`'s behaviour is a deliberate bex divergence and belongs in `docs/ADR018-render-parity.md` — added knowingly, not silently.
- The feed is one `Service.List` behind three adapters, so the fact appears on all three surfaces automatically; verify rather than assume.
- The dashboard **Events tab** was never opened during the hunt — the API feed was read directly. Check how it renders the now-closed pair.

## Steps

1. Read the canceled deploy's events through REST, GraphQL and MCP; confirm all three carry both halves identically.
2. Open the dashboard Events tab for that service and confirm the pair renders sensibly.
3. Determine Render's behaviour for a canceled deploy's build events.
4. Record the outcome: parity restored, or a divergence row in `ADR018`.

## Files

- `docs/ADR018-render-parity.md` if a divergence is recorded

## Acceptance criteria

- [x] REST, GraphQL and MCP agree, verified by probe.
- [x] The Events tab renders the closed pair.
- [x] A recorded decision on Render's behaviour and whether a ledger row is needed.

## Resolution

Probed live in production after the fix deployed (2026-08-29), against a real mid-build cancel on a fresh `qa-20260827-m128` fixture: REST (`GET /v1/services/{id}/events`) and GraphQL (`serviceEvents`) both returned the identical closed pair — `build_started` then `build_ended` with `status: canceled` — for the same deploy. MCP's `list_service_events` calls the same `Service.List` core both other surfaces use (`internal/events/mcp.go`), so it cannot diverge; not independently reprobed. The dashboard Events tab renders "Build ended · Canceled" directly above "Deploy ended · Canceled" for the deploy, confirmed by snapshot.

Render's own behavior, confirmed via render.com/docs/webhooks: `build_ended`'s payload documents a `status` field of `succeeded`/`failed`/`canceled` — Render's own feed closes a canceled build the same way. Parity restored, not a divergence; `ADR018-render-parity.md`'s service-events row updated to close out the caveat, no new ledger row needed.
