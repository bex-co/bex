## Resolution

Ran the fixture on production twice (2026-08-29), once against the pre-fix
image and once post-deploy, on `qa-20260827-m128`
(`github.com/render-examples/express-hello-world`): free `web_service`,
deploy #1 to `live`, `POST .../deploys`, confirmed `build_in_progress` by
reading the deploy first, then `POST .../deploys/{id}/cancel`.

- **Pre-fix run** (before `daf84f6e`/`0ce43b99` reached production):
  reproduced the exact reported bug — `deploy_started` + `build_started` +
  `deploy_ended(canceled)`, no `build_ended`.
- **Blocking discovery:** shipping the fix exposed a live, unrelated CI
  incident — `test (backend)`'s self-hosted ARM64 runner had been failing on
  every push since 2026-08-28T04:57Z (12 consecutive commits, none touching
  this milestone) because GitHub Actions' `services:` container pull could
  not reliably resolve the pinned multi-arch `postgres:17` index to the
  runner's own platform. Fixed by re-pinning `backend-test.yml`'s postgres
  service to its `linux/arm64/v8` manifest digest directly (verified locally
  before pinning); `deploy.yml`'s `build-and-deploy` was gated on this and
  could not have shipped anything, not just this fix, until it was resolved.
- **Post-fix run:** cancel returned 200/`canceled` with a real ~7s duration;
  the events feed now carries `build_started` → `build_ended(canceled)` for
  the same deploy, confirmed identically on REST, GraphQL and the dashboard
  Events tab (see `t003`).
- **Webhook/supersede items (`t002`):** stated as code-level (not live)
  verification — the outbound pipeline is fact-source-agnostic and
  idempotent by `source_key`, so a Cancel-inserted fact is indistinguishable
  from a reconciler-inserted one; push omits build lifecycle by design. The
  supersede path is pinned by a new reconciler test
  (`TestRecordDeploySupersededMidBuildEmitsBuildEndedCanceled`) rather than a
  live trigger.
- Fixture deleted via the dashboard's own Danger Zone confirm flow, which
  worked cleanly; `GET` on the deleted service id then returned 404. (Aside,
  not filed: a same-origin `fetch(..., {method:'DELETE'})` issued directly
  from the page console against `api.bex.co` was CORS-rejected —
  `Method DELETE is not allowed by Access-Control-Allow-Methods in preflight
  response` — while the dashboard's own delete button succeeded regardless,
  so the dashboard evidently does not route this mutation through a plain
  browser-side `DELETE` fetch. Not reproduced as a user-facing defect.)
