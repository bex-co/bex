## Objective

Project `RollingUpdate` with `maxSurge: 25%` and `maxUnavailable: 0` on every App Deployment that is neither held nor disk-bearing, existing ones included, without rolling any pod.

## Context

- `lego/operator/internal/controller/deployment_projection.go`: `defaultRollingUpdateStrategy` (`:941`) returns `25%`/`25%`. `projectRolloutHold` (`:956`) writes it only when a Deployment leaves the held strategy, so every other Deployment keeps what the API server defaulted (`25%`/`25%`).
- `projectDeployment` calls `projectRolloutHold` (`:979`), then `applyDiskProjection` (`:1001`). With a disk, `applyDiskProjection` sets `Recreate`. When a disk is detached it resets the strategy to the empty value (`disk.go:121`), which the API server defaults back to `25%`/`25%`.
- `image_network.go:560` also calls `projectRolloutHold`.
- The strategy is not part of the pod template, so writing it changes no `pod-template-hash` and rolls nothing.
- `maxSurge: 25%` rounds up to at least 1, which `maxUnavailable: 0` requires.

## Steps

1. Change `defaultRollingUpdateStrategy` to `maxSurge: 25%`, `maxUnavailable: 0`, and have `projectRolloutHold` write it whenever the release is not held.
2. Make a disk detach land on the same strategy instead of the empty one, so the order of the two projections cannot bring `25%` back.
3. Check every other place that compares or resets the strategy (`disk_prepull.go`, `disk_holder.go`, `platform_redeploy.go`, `web_image_http.go`) still reads `Recreate` and the held strategy correctly.
4. Update the comments that describe the API-server default.
