# A muse turn ends as soon as the agent starts a background workflow, so the routine does nothing

Why: three of the bex workspace's eleven `rt-*` routine runs on muse that got a sandbox ended 2.5 minutes in, marked completed, with no work done. Each had just started a `workflow` whose subagents were still running. On Devin, a session keeps working until its work is done.

- **Seen on production (w6/m354 t007, 2026-11-16).** Every muse session that called the `workflow` tool ended its turn 2 to 3 s later. Every `rt-*` run on muse that never called it went on to open its PR or report that it had nothing to change. Of the 19 muse sessions created from 2026-11-15 22:41 to 12:30 UTC on 2026-11-16, three called it:
  - `rt-simplify-logic`, `ags-dbt4732jclac73969pf0` (2026-11-15 23:43 UTC)
  - `rt-simplify-logic`, `ags-dbt7hh5hdqoc73dn7glg` (2026-11-16 03:30)
  - `rt-prune-useless-tests`, `ags-dbtcq6m004dc73ajmfg0` (2026-11-16 09:30)
- **What the transcripts show.** Each ends with a `workflow` part in `output-available`, then `workflow: inProgress` and two `subagent: inProgress` parts in `input-available`, then `finish`. For example, `ags-dbtcq6m004dc73ajmfg0` ends with seq 23–27, 09:33:56.805 to 09:33:59.735. The agent's last text announces more work, such as "I'll fan out parallel discovery before making any edits." The sessions read `phase=completed` with no pull request, and their turns ran 2 min 21 s to 2 min 30 s.
- **Where the turn ends.** `lego/agent-image/driver/src/session.ts` (~350) closes the turn when `provider.prompt()` returns, which is the ACP `session/prompt` response. muse returns that response while its workflow keeps running, and nothing waits for the workflow or carries its result into a turn.
- **Fix, to choose from the evidence.** Either the driver keeps the turn open while the agent reports tool calls still `inProgress`, with the turn bound still applying. Or muse's profile makes `workflow` wait for its result, if muse has such a setting. Check how muse signals that background work has finished before picking.
- **Done when:** a muse session that starts a `workflow` keeps its turn open until the workflow's result reaches the agent and the agent finishes. Prove it with a driver test that has the agent end its prompt while a workflow tool call is `inProgress`, and with one production routine run that calls `workflow` and opens its PR or reports that it has nothing to change.

## Verdict, 2026-11-16 (`/loopx` worker): fixed by turning Muse workflows off, parked for the production check

- **How Muse reports finished background work.** It wakes the agent with a turn of its own, after the turn that launched the work has ended. Muse 1.4.14's `workflow` launch result says: "the workflow runs in the background and its completion is delivered to this conversation … Do not poll for completion: the result is delivered automatically and wakes you even after you end the turn." No setting makes the tool wait. `run.workflow_trigger_mode` (`auto`, `explicit` or `off`) only decides whether the model is offered the tool.
- **Why the driver cannot wait for it.** muse-code-acp 0.11.0 keeps the Muse host for 60 s after it answers `session/prompt`, then closes it and reports every unresolved card as `failed` with an unknown outcome. It never streams the turn Muse starts to deliver the result, and it refuses a prompt while that turn runs (the adapter's `src/muse-sdk-host.ts` `release()`, `src/sdk-prompt-turn.ts` ~251 and `docs/async-tasks.md`). A driver that held the turn open would see the workflow killed about a minute in. That rules out the first option, and Muse offers the second only as `off`.
- **Shipped.** Before the adapter starts, the driver writes `run.workflow_trigger_mode: "off"` to Muse's settings together with the model (`writeMuseSettings` in `lego/agent-image/driver/src/acp.ts`; [ADR108 D8](../../../docs/ADR108-muse-code-agent.md)).
  - **Probe.** Muse 1.4.14-R7309.1 (the pinned SHA-256) ran under muse-code-acp 0.11.0, driven over ACP with the profile's session config. By default the first model request offered 26 tools, including `muse.workflow`. With the setting it offered 25 and no `muse.workflow`.
  - **Tests.** `test/muse.test.ts` checks three things: the settings the adapter starts with (the model, workflows off, other keys kept); a muse profile with no model; and that other profiles leave Muse's settings alone. With the setting line removed, the first two fail.
- **Definition of done, amended.** The driver test that keeps a prompt open across an in-progress workflow now belongs to the adapter fix that would turn workflows back on, filed as w6/130. For this item, done means that no Muse session can start a workflow, so all of its work stays in the turn the driver waits on.
- **Gate (clears by itself).** First, the production deploy that carries this commit and rebuilds the agent image. Then the next Muse `rt-*` routine runs: read their transcripts as w6/m354 t007 did. None may contain a `workflow` tool call, and each must open its PR or report that it has nothing to change.
