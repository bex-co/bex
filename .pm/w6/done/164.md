# A Traefik roll ends every native SSH session within seconds, though Render gives its SSH infrastructure's connections an hour

Why: every change to the edge's values or plugins rolls Traefik, which sits on the native SSH path, so each one cuts every open `ssh <srv>@ssh.bex.co` session at once. Render says that when it maintains "underlying infrastructure that enables SSH connections", it "gives existing connections one hour before automatically closing them" ([render.com/docs/ssh](https://render.com/docs/ssh), read 2026-11-21). The ssh-gateway already gives that hour on its own release ([ADR035](../../../docs/ADR035-ssh.md), w6/m482), but the Traefik hop in front of it does not.

- **Filed by** w6/153's held-session probe ([done/153.md](153.md), 2026-11-21). Two plain `ssh` sessions were held from 18:13Z 2026-11-20 to 10:27Z 2026-11-21. Two of their seven ends came from Traefik rolls:
  - **21:02:16Z 2026-11-20.** One session on each gateway pod (`bex-ssh-gateway-898bc5cf6-mwjgw` and `-t8csw`), after 10,109 s and 10,018 s. Both ended in the same second with `Connection to ssh.bex.co closed by remote host.`.
    - Traefik rolled `775c7dc785` → `5fd98c5cdd` then. The new pods started at 21:01:41Z and 21:01:54Z, and the old pods' `kube_pod_info` ends at 21:02Z. That roll was w8/357's edge plugin change ([done/357.md](../../w8/done/357.md): "2026-11-20 21:02Z … the edge rolled onto it").
    - No gateway release, instance change or reauthorization happened at that second.
  - **02:27:04Z and 02:27:17Z 2026-11-21.** Both sessions were on `859b9f67d5-s8cgj`, 2 min into its 1 h drain. They ended 13 s apart in the same way, so the edge cut the gateway's drain short.
    - Traefik rolled `5fd98c5cdd` → `578d4844d9`, with the new pods starting at 02:26:51Z and 02:27:05Z. That roll was w8/363's (`1d9af0ece8`, committed 02:23Z, which edits `traefik.values.yaml`).
  - At each end the gateway logged `ssh gateway connection ended: context canceled`. That is its client side, the Traefik connection, closing. It logged no reauthorization line.
- **The path.** The Hetzner `:22` listener (PROXY protocol, `infra/terraform/main.tf`) goes to NodePort `32207`. That port is Traefik's `ssh` entrypoint (`--entryPoints.ssh.address=:2222/tcp`, `deploy/gitops/base/values/traefik.values.yaml`). It uses `IngressRouteTCP bex-system/bex-ssh-gateway` and ends at the gateway's `:2222`.
  - Production's Traefik Deployment rolls `maxSurge: 1`, `maxUnavailable: 0` with `terminationGracePeriodSeconds: 60`. The `ssh` entrypoint sets no `transport.lifeCycle`.
  - So an old Traefik pod closes the TCP streams it proxies within seconds of its `SIGTERM`.
  - Traefik rolled twice in these 6 h. Three commits this week edited `traefik.values.yaml`: w21/113's `fe52cf2b6`, w8/357's `845a178c1` and w8/363's `1d9af0ece`.
- **Not explained, seen in the same probe.** At 10:24:32Z 2026-11-21 both sessions, then on `794544567b-rk97m`, ended the same way after 1,125 s. No Traefik roll, gateway release or instance change happened then.
  - m547's roll of `bex-tenant-0` was under way. Its first old node, `wldb9-4pxsp`, left between 10:24Z and 10:26Z, and the probe's own node `wldb9-59ksr` left by 10:31Z.
  - But with `externalTrafficPolicy: Local` the load balancer carries `:22` only to the nodes running Traefik (`dpjxh`, `m82n5`), so `4pxsp` was not on the path.
- **Options.** Pick the one that gives an open session Render's hour:
  1. Give the `ssh` entrypoint a long `transport.lifeCycle.graceTimeOut` and raise Traefik's grace period to match. Check what that does to edge rolls: two replicas with `maxSurge: 1`, and HTTP on the same pods.
  2. Take `:22` off Traefik. The Hetzner `:22` service would go to a NodePort on the gateway itself, which already reads PROXY v2 (`lego/backend/internal/sshgateway/nativessh/proxyv2_test.go`). Then only the gateway's own 1 h drain governs, as the SNI proxies own their ports.
- **Seen in passing.** The gateway also ends every native SSH session at 4 h (`BEX_SSH_SESSION_TIMEOUT`, `lego/backend/AGENTS.md`). [render.com/docs/ssh](https://render.com/docs/ssh) states no maximum session length, and [ADR018](../../../docs/ADR018-render-parity.md) records no such divergence. Check how Render behaves before choosing, and file that separately if it differs.
- **Done when:** on production, a plain `ssh <srv>@ssh.bex.co` session held through a Traefik roll stays open until the roll's old pods finish the hour, with a regression check that renders the chosen setting. ADR035 records the edge's part of the hour.

## Fix shipped, parked for the production check (2026-11-23)

- **Option 1, with its effect on edge rolls handled.** Option 2 would put every gateway release behind the load balancer's health check. A gateway pod's node would keep getting new `:22` connections from the load balancer for up to 45 s (three 15 s checks) with no Ready gateway on it, several times a day, and w6/152's accept window assumes Traefik in front. It also needs a Terraform apply. Traefik rolls only on an edge change, so the edge's hop drains instead.
- **Shipped in `bca73171bb`:**
  - `deploy/gitops/overlays/prod/values/traefik.values.yaml`: the `ssh` entrypoint sets `transport.lifeCycle.graceTimeOut: 3600s`, and the pod grace is `3660` s. The base hostNetwork edge keeps the default, because its `Recreate` roll would have no pod at all during a drain.
  - The same file spreads the two pods with `topologySpreadConstraints` (hostname, `maxSkew: 1`, `DoNotSchedule`) instead of required pod anti-affinity. kube-scheduler v1.34 counts a terminating pod for inter-pod anti-affinity: `interpodaffinity` has no terminating-pod bypass, while `podtopologyspread/common.go` skips one ("Bypass terminating Pod (see #87621)"). Production has three platform nodes and two edge pods. With required anti-affinity, the roll's second new pod would wait `Pending` for up to the hour behind the first draining pod, the Deployment would pass its 600 s progress deadline, and Argo's `PlatformGitOpsUnhealthy` would fire after 15 min.
  - `deploy/gitops/base/prometheus.yaml`: the `traefik` and `traefik-websocket-meter` jobs keep Ready pods only, as the `bex-api` job already does. A draining pod's metrics entrypoint (`:9100`) closes at `SIGTERM`, while the WebSocket plugin's `:9101` listener lives as long as the process. If Prometheus still scraped the pod, its `up` of 0, or its series ending mid-hour, would fail the next hour's HTTP and WebSocket egress windows in `egressquery.Health` for every service, and the usage rollup skips a failed window. The roll's own hour fails both windows anyway (new process start), as before.
  - `scripts/edge-ssh-drain-validate.sh` checks all of this over the rendered releases, run by `scripts/gitops-validate.sh`. `check_request_path_ha` accepts a `DoNotSchedule` hostname spread. `scripts/edge-ssh-drain-validate.test.sh` covers 12 cases and runs in `scripts.yml`. [ADR035 § Sessions across an edge roll](../../../docs/ADR035-ssh.md#sessions-across-an-edge-roll-w6164) records the design.
- **Checked locally.**
  - `traefik:v3.7.17` in Docker with a raw TCP route to an echo backend and a client writing every second. Today's flags: the stream closed 10 s after `SIGTERM` (`closed by remote after 13.1s`, connected 3 s before), which is the probe's symptom. With `graceTimeOut=20s` it held to the bound (23.1 s), and Traefik logged `Waiting 20s seconds before killing connections entryPointName=ssh` beside `10s` for `web`. With `graceTimeOut=60s` and a client that left 15 s into the drain, Traefik exited at 15 s. A new connection made inside the drain from the same network was refused (`ConnectionRefusedError`).
  - The validator fails today's production render on five counts: no `graceTimeOut`, the required anti-affinity, no spread, and both scrape jobs. It passes the change. `bash scripts/gitops-validate.sh` passes in full (helm v4.2.3 locally; CI pins v3.19.0).
- **Not yet verified: production.** The deploy that carries this rolls Traefik under the old 10 s, so sessions open then still end. The check needs the next roll after it.
- **Unknown until that check: the load balancer.** At the end of a roll, the node of the second old pod has no Ready edge pod, so its `:22` health check fails and the load balancer marks it unhealthy. Hetzner does not document whether an established connection to an unhealthy target survives (AWS NLB resets them by default). The first old pod's node gets the second new pod and stays healthy.
- **The 4 h cap seen in passing is filed as [w6/174](../174.md).** Render's page names no time limit among its closure reasons, and bex has no Render account to hold a session past 4 h, so that item starts by finding out.
- **Next, once production's pin carries `bca73171bb`:**
  1. `kubectl -n traefik get deploy traefik -o yaml` shows `terminationGracePeriodSeconds: 3660`, the arg `--entryPoints.ssh.transport.lifeCycle.graceTimeOut=3600s`, the topology spread and no `affinity`, with its two pods on two platform nodes. Prometheus `up{job="traefik"}` lists only Ready pods.
  2. Hold plain `ssh <srv>@ssh.bex.co` sessions in the w6/153 shape (probe pod in `bex-canary`, 10 s tick) until each Traefik pod carries at least one. `traefik_open_connections{entrypoint="ssh"}` per pod shows which pods carry them.
  3. Let Traefik roll: the next edge values or plugin change, or `kubectl -n traefik rollout restart deploy/traefik`. Note each old pod's `SIGTERM` time and node, and which old pod's node received a new pod.
  4. Pass when every held session keeps ticking through the roll and ends only on its own, at its 4 h cap, or about 3600 s after its old pod's `SIGTERM`. The second new pod must start within a minute of the first old pod's `SIGTERM` (not `Pending`), the Argo `traefik` Application must return to Healthy within minutes, and the hour after the roll must have healthy HTTP and WebSocket egress windows.
  5. If sessions on the old pod whose node received no new pod end about 45 s after its `SIGTERM`, while those beside a new pod survive, then the load balancer cuts established flows to an unhealthy target. Record that in ADR035 and file the follow-up (for example, keep a Ready edge pod on every draining node).
  6. Delete the probe, the fixture service and the key.
