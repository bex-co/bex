## Result — 2026-11-17

Read on production (pin `fc4fbf28a`) as the QA user, against `bex-canary`'s `starter` store `red-dbpf5q5me2kc73f2l0og` and t006's probes:

- **The figure per plan matches Render.** Render documents free 50, `256mb` 250, `1g` 1,000 and so on up to `50g` 50,000 ([compute plans](https://render.com/docs/compute-plans#render-key-value-plans), read 2026-11-17). On production, free admitted exactly 50, `starter` 250 and `standard` 1,000, each through the store's internal URL, and free admitted 50 on its external TLS URL too (t006). `TestValkeyConnectionLimitsMatchRender` pins every plan id and alias.
- **The refusal matches Render's.** Render's Key Value is Valkey, so a client past the limit reads Valkey's own `-ERR max number of clients reached`. bex returns those exact bytes on the plain listener and inside TLS on the external one.
- **REST** `GET /v1/key-value/{id}` and **MCP** `get_key_value` carry no connection field, and neither do Render's Key Value schemas. Nothing in the 2026-11-17 MCP tool list states a connection limit (searched for `1024`, `max connections`, `connection limit` and `maxclients`).
- **GraphQL** `KeyValue` and `KeyValueInstanceType` on production carry no connection field yet. **The dashboard** at the deployed `db48cde2bae9` states no limit: its Active Connections chart plots the count with no limit line. Render shows the limit on each plan card and beside Active Connections. bex shows it with w6/m459 (`64200b09c`, `connectionLimit` read from the same `lego/types/tiers` table the operator enforces), which is not in this pin and is already parked for the deploy that carries it.

No new drift, and nothing on any surface contradicts the limit. The one missing display is w6/m459's, already filed and in flight.
