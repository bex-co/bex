## Objective

Make the in-cluster BuildKit build Job use `App.Spec.DockerfilePath` when set, instead of always defaulting to `<context>/Dockerfile`.

## Context

- `lego/operator/internal/build/build.go:216-264` — the BuildKit Job's `--opt context=<repo>.git#<branch>[:<rootDir>]` construction has no `--opt filename=` override today (defaults to `Dockerfile` at the context root).
- `docs/ADR004-deployment.md` documents the current build-from-git flow.

## Steps

1. When `App.Spec.DockerfilePath` is set, add `--opt filename=<path>` to the buildctl invocation.
2. Validate the path is relative (reject absolute paths / `..` escapes) before passing it through.

## Files

- `lego/operator/internal/build/build.go`

## Acceptance criteria

- [x] A build with `DockerfilePath: docker/Dockerfile.prod` uses that file instead of the root `Dockerfile`.
- [x] Unset `DockerfilePath` behaves exactly as today (byte-identical build args).
- [x] Path traversal attempts are rejected.

## Out of scope

- StartCommand (t003).

## Resolution

Found already shipped by an earlier, unrelated commit — `build.go`'s `BuildJob` already
appends `--opt filename=<DockerfilePath>` when set (`build.go:266-267`), with existing
coverage in `TestBuildJobCustomDockerfilePath` (build_test.go). Traversal is rejected the
same way `RootDir` is (the operator trusts the CR; bex-api's `store.ValidRootDir` rejects
`..`/absolute paths at `service.go:864` before the CR is ever written) — the operator
never re-validates `RootDir` either, so this follows the established pattern rather than
introducing a new one. No changes made.
