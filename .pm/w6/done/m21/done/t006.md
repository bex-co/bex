## Resolution

Ran `/simplify` (4 parallel review agents: reuse, simplification, efficiency, altitude)
over the diff. Reuse/simplification agents both flagged `startcommand_test.go`'s
`newReconciler`/`reconcileN` closures as copy-paste of a pattern already repeated across
sibling test files — fixed within the new file by collapsing the two duplicate `Context`
blocks into one `DescribeTable` (declined extracting a package-wide shared helper into
`suite_test.go`: touching other tests' files is outside this diff's scope). Efficiency
agent found no issues in the backend plumbing and noted the envtest's 3x-reconcile-loop
cost is a propagated pre-existing pattern, not a regression.

The altitude agent's finding was a genuine correctness gap, not just a quality nitpick,
so — as a deliberate, disclosed exception to this task's "behavior-preserving" scope —
it was fixed rather than only logged: `app_controller.go`'s `StartCommand` → Deployment
`Command` override was gated on `Runtime == "docker"` only, so a legacy
`Builder: "dockerfile"` App (no explicit `Runtime`, still a valid way to request a
Dockerfile build via REST/GraphQL/MCP/bex.yml today) silently dropped `StartCommand` at
deploy time even though `DockerfilePath` was honored for the same App at build time. Since
this milestone's own DoD requires `StartCommand` to "take effect on the resulting
Deployment," and the new `startcommand_test.go` was about to certify the too-narrow
behavior as correct, the gate was broadened to reuse the existing `effectiveBuilder`
mechanism (`!= native && != buildpack`) in both `app_controller.go`'s Deployment path and
`cronPodSpec`, with a new test entry for the legacy-builder and native-runtime cases.
