## Objective

Expose `dockerfilePath`/`startCommand` on App create/update across bex.yml ingestion, REST, GraphQL, and MCP.

## Context

- `lego/backend/internal/apps/deploy.go` (~line 416) handles bex.yml/render.yaml-shaped manifest ingestion.
- `lego/backend/internal/apps/mcp.go:106` has the comment flagging this exact gap — remove/update it once implemented.

## Steps

1. Add `dockerfilePath`/`startCommand` fields to the bex.yml schema and App create/update REST/GraphQL/MCP request types.
2. Thread through to `App.Spec.DockerfilePath`/`StartCommand` on CR create/update.
3. Update the `mcp.go:106` comment to reflect the new support (or remove it).

## Files

- `lego/backend/internal/apps/deploy.go`
- `lego/backend/internal/apps/rest.go`, `graphql.go`, `mcp.go` (or equivalent app-surface files)

## Acceptance criteria

- [x] Creating/updating an App with `dockerfilePath`/`startCommand` via bex.yml, REST, GraphQL, and MCP all set the corresponding CR fields.
- [x] Omitting the fields is fully backward compatible.

## Out of scope

- Dashboard UI for these fields (covered by t005's parity check, not new UI build).

## Resolution

`startCommand` was already threaded through every surface (REST, GraphQL, MCP, bex.yml)
by an earlier, unrelated commit. `dockerfilePath` was only threaded through REST
(`rest.go`'s `envSpecificDetails.dockerfilePath`, matching Render's create shape) and the
`CreateRequest`/`applyCreateToSpec` core — GraphQL (`serviceGQLType` read field +
`createService` mutation arg), MCP (`createWebServiceArgs`/`createCronJobArgs`), and
bex.yml ingestion (`bexService.DockerfilePath` → `parseService`) were missing it. Added all
three (`graphql.go`, `mcp.go`, `deploy.go`). The `mcp.go:106`-area comment no longer
describes a gap (already rewritten by the earlier commit that shipped `startCommand`); no
further comment change needed.
