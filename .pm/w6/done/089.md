# Verify a nightly disk snapshot and restore of a userns render-v1 service

Why: w6/m151 put render-v1 pods with disks in pod user namespaces. The snapshot/restore round trip was proven only on the local cluster, because production has no on-demand snapshot.

- **Steps:**
  1. Keep (or create) a disk-backed render-v1 service, such as unchanged ClickHouse, past one nightly `dskbak-` run.
  2. Confirm `GET /v1/disks/{id}/snapshots` lists the snapshot.
  3. `POST /v1/disks/{id}/snapshots/restore` into a fresh service and read a sentinel row back.
- **Expected:** passes. On-disk UIDs are unshifted under idmapped mounts, and the snapshot Job runs as host root with `DAC_OVERRIDE`/`CHOWN`/`FOWNER`.
- **If it fails:** remove `BEX_RENDER_V1_USER_NAMESPACES` from `lego/operator/config/prod/kustomization.yaml`. No data migration is needed.

- **Fixture kept (2026-10-21):** unchanged ClickHouse `srv-dbcd1t4iimkc73f6l0m0` in `bex-canary` (`tea-daif693dqjvc73e7as3g`), with the sentinel row `m151-customer` in table `sentinel`. Delete it after the check.

**Result 2026-10-22: no snapshot was taken.** `GET /v1/disks/dsk-dbcd1t4iimkc73f6l0n0/snapshots` still returned `[]` at 05:15 UTC, after the whole 02:00–02:59 UTC window. Polling every 5–10 minutes found nothing; one poll got a transient empty body.
- **Ruled out through the API and repo:**
  - The listing returns storage errors as errors, so it isn't hiding a failure.
  - The operator's `diskSnapshotWorkspace` and bex-api's `diskSnapshotPrefix` both key on the workspace id and App name.
  - The production manager is configured for snapshots (`config/manager/manager.yaml` `BEX_DISK_SNAPSHOT_*`).
  - The QA user has no other disk to compare against, so it's unknown whether every disk missed its run or only this userns render-v1 one.
- **Not observable without the cluster:**
  - whether `dskbak-*` exists in `tea-daif693dqjvc73e7as3g` and at which minute;
  - its Job and pod outcome (for example a CreateContainerConfigError, or a mount failure beside an idmapped service pod);
  - the App's `DiskReady` condition, which bex-api never surfaces (w6/094);
  - the `silent_failure_alerts` firing.

**Root cause found, 2026-10-24 21:03 UTC** (`disk-snapshot-drill` snapshot run 40132266076; access worked again once the roll settled). All three attempts failed in the snapshot walker with `statat <path>: no such file or directory`, each on a different path: `store/021/…/202610_35567_37352_357/CurrentMetric_Merge.bin`, then `202610_37358_37358_0`, then `202610_37368_37368_0`. ClickHouse merges and drops data parts continuously, and `walkTree` treated an entry deleted between the directory listing and its read as fatal. Not user namespaces and not placement: the pod ran beside the service on `bex-tenant-0-tghbn-vgmd7`.
- **Fix:** `lego/operator/internal/disksnapshot` skips a vanished entry, as GNU tar does. An escaping symlink still fails.
- **Test:** `TestBackupSkipsEntriesThatVanishMidWalk` reproduces the exact production error before the fix.
- **Remaining:** after the deploy, take one snapshot with `disk-snapshot-drill`, restore it into a fresh service, read the sentinel, then delete the fixture.

**Backup verified, restore bug found and fixed (2026-10-24, 22:39–23:10 UTC):**
- **Backup:** after `bc09a5fea` deployed (pin `bc09a5fea76b`), `disk-snapshot-drill` snapshot run 40139347320 completed on its first attempt in 4.5 minutes. The API lists the snapshot (22:39:24Z) and `diskSnapshotHealth` reports `ok`, due 2026-10-25T10:00Z.
- **Restore race:** a peer (`m089-peer`, `srv-dbej9smnvu5c73f911p0`) wrote `post-snapshot` after the snapshot, then `POST /v1/disks/dsk-dbcd1t4iimkc73f6l0n0/snapshots/restore` returned 200. The operator scaled ClickHouse to 0 (22:45:40) and started `dskrst-` (22:45:41). Then, at 22:45:43, the Deployment scaled back to 1 while the Job ran. The Job failed at 22:45:49, `DiskReady` read healthy, and ClickHouse answered `UNKNOWN_TABLE` (Code 60). The disk was half-restored and the failure was hidden (diagnose run 40140661690).
- **Cause:** bex-api's projector rebuilt `spec.disk` from the row and dropped the CR-only `restoreSnapshot`. The operator then saw no pending restore.
- **Fix:** `23750eda6` (`applyOwnedSpec` keeps it; `TestApplyOwnedSpecKeepsAPendingDiskRestore` fails before the fix).
- **Remaining:**
  1. After `23750eda6` deploys, take a fresh snapshot. The fixture's table is gone, so first recreate the sentinel through the peer. Then write `post-snapshot`, restore, and expect the sentinel present and `post-snapshot` absent. If the `dskrst-` Job itself still fails, read its reason with the drill; that failure was masked by the race.
  2. Delete `m089-peer` and the ClickHouse fixture.
