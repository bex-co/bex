# A plan change through `PATCH /v1/services/{id}` deploys at once, where Render's Update Service saves it for the next deploy

Why: Render's API saves a compute plan change and applies it with the next deploy. bex resizes and redeploys the service the moment a Render-shaped client saves the plan, so a client that follows Render's documented "update, then deploy" sequence gets two deploys, and one that only saves gets a restart it did not ask for.

- **Found by:** w6/159's Render check, 2026-11-23.
- **Render:** [render.com/docs/compute-plans](https://render.com/docs/compute-plans) § Changing a service's compute plan, read 2026-11-23:
  - API: "For Update service, follow up with a request to the Trigger deploy endpoint to apply the new compute plan." "The Update service endpoint does not trigger a new deploy."
  - "Your service's compute plan does not change until the first successful deploy after you update it."
  - Dashboard: "Render automatically triggers a deploy to apply the new compute plan." Blueprint: "The next time you sync your Blueprint, Render triggers a deploy to apply the new compute plan."
- **bex:** `servicePatchTable`'s plan row is the one row marked `deploys: true` (`lego/backend/internal/apps/settings.go`), so `ApplyServicePatch` (REST `PATCH /v1/services/{id}`, MCP `update_service`) runs it outside `rollout.WithSaveOnly` and opens a `settings_change` deploy (`service_updated` on REST). [ADR018](../../../docs/ADR018-render-parity.md) (the w8/m135 paragraph, "Settings saves through the API save only") says "A plan change still deploys at once, as a resize does on Render". w8/m135 listed that claim as unverified.
- **Check first:**
  - Whether the operator can hold a saved plan: w8/m135's notes say the runtime record did not capture plan or disks, so the pods would roll from `spec` without a deploy row. Its settings fingerprint may cover plan since then (`recordedSettingsMatch`).
  - When billing switches to the new plan, given that Render's plan "does not change until the first successful deploy".
  - Whether Render's MCP server can change a plan at all (a search summary said its MCP "doesn't modify scaling settings").
- **Done when:**
  - `PATCH /v1/services/{id}` `{"serviceDetails":{"plan":"standard"}}` opens no deploy. The service keeps running on its old plan and reads `undeployedChanges: true`, and the next deploy applies the plan.
  - MCP `update_service` behaves the same way, or follows whatever Render's MCP does.
  - The dashboard's Compute page (GraphQL `updateServicePlan`) still deploys at once.
  - ADR018 and ADR004 § Settings saves wait for a deploy are amended, and the w8/m135 plan tests are updated.

**Promoted 2026-11-23 to [w6/m609](../m609/README.md)** by `/loopx w6`. The "Check first" answers make it more than an hour across several tasks. The operator can already hold a saved plan (`Tier` is a release field, so `pendingReleaseView` keeps the running tier), but no test proves it. Billing cannot: the hourly meter bills `instance_seconds` at the store's tier, which `SetPlan` writes at the save, and the Free instance hours enforcer reads the saved spec's tier, so a saved plan would be billed and exempted before it runs. Render's MCP server has no update tool (`render-mcp-tools.json`), so bex's `update_service` follows REST. The milestone covers the save-only plan row and `SetPlan`'s side effects, an operator envtest, billing by the running plan, the ADRs, a production check, Render parity, Simplify, Test coverage and Closeout.
