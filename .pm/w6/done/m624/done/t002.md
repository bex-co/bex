## Objective

On the local CAPD cluster (Kubernetes v1.36.1, containerd 2.3.1), show that an App whose pod mounts the helper from an image volume passes its exec probes and runs its preStop drain. Show that the kubelet starts its app in the pass that starts the pod.

## Context

- `bash scripts/mock-cluster.sh`, then `bash scripts/mock-cluster.sh operator`. Both are pre-approved. The host needs the inotify limits in [infra/local/README.md](../../../../../infra/local/README.md#host-requirement-inotify-limits).
- The open questions are what the code cannot settle:
  - whether a file `subPath` mounts from an image volume;
  - whether the binary runs under the app's non-root UID with user namespaces on (`appHostUsers`; containerd sets up idmap for image volumes);
  - whether a shell-less image is fine;
  - whether the tenant namespace's Pod Security level and `operator-workload-admission.yaml` admit the template.

## Steps

1. Deploy a web image service with a Health Check Path, and one that names no port, each with a disk. Use a shell-less image such as `traefik/whoami`, with t001's setting on.
2. Check that each pod has no init container and that its startup, readiness and liveness probes pass. Delete a pod and check that the preStop drain ran.
3. From the node's containerd and kubelet logs, compare the time from the pod's sandbox to the app's `StartContainer` with a named-port twin's, over several restarts.
4. Record the results in this task. If the volume cannot carry the probe, record why, and go to the definition of done's fallback.

## Acceptance criteria

- [ ] Both services become Ready through the exec probe from the image volume, and the drain runs.
- [ ] Each instance's time to start is within 0.2 s of the twin's.

## Out of scope

- Production (t003–t005).

## Done (2026-11-24)

Local CAPD cluster (Kubernetes v1.36.1, containerd 2.3.1), operator `bex-operator:dev` built from the tree with the setting on. Fixtures in a namespace `w6-m624` (disposable) with a tenant namespace's labels, RoleBindings, LimitRange and NetworkPolicies (Pod Security enforce `baseline`, warn and audit `restricted`), all on `bex-worker-0`, all `traefik/whoami` (shell-less), Starter, `render-v1`: **a** (web image, no port, 1 GB disk), **h** (port 80, Health Check Path `/`, disk), **t** (port 80, no path, disk: the twin, no helper) and **d** (port 80, no path, no disk: the TCP check with the health-checked drain). The namespace is deleted.

- **A file `subPath` does not mount.** The first pod read `failed to mount image volume: ImageVolumeMountFailed: … only directory subpath is supported, subpath: "health-probe"` and never started. t001 moved the helper into a directory of its own in bex's image (`/bex-health`), mounted with `subPath: bex-health`. With that, every pod started.
- **Shape.** a, h and d had no init container and the `bex-health` image volume (`bex-operator:dev`, `IfNotPresent`); t had neither. Their startup probes were `/bex-health/health-probe open-port …` (a), `… check --port 80 --path / … --host w6-m624-h.onbex.co` (h) and the TCP check with `/bex-health/health-probe drain --seconds 60` as preStop (d). Admission took each template.
- **The probes pass.** All four Apps went `Running`; `kubectl exec` of the helper's `check` in h and `open-port` in a exited 0, and `/bex-health/manager` does not exist in the app container: only the helper is visible.
- **The drain runs.** Deleting d's healthy pod took 61 s, with no `FailedPreStopHook`.
- **User namespaces.** With `BEX_RENDER_V1_USER_NAMESPACES=w6-m624`, d ran `hostUsers: false` and went Ready through the helper. The disk fixtures could not run in a user namespace here at all, the twin included (`failed to set MOUNT_ATTR_IDMAP on /opt/local-path-provisioner/…`): local-path's directory on the CAPD node cannot be idmapped, which is this cluster's limit and not the image volume's (production's `hcloud-volumes` can, w6/m151). They were measured with user namespaces off.
- **Time to start.** From containerd's `RunPodSandbox … returns sandbox id` to the app's `StartContainer … returns successfully`, over five or six restarts each in alternating rounds: a 0.61–0.81 s, h 0.64–0.79 s, t 0.64–0.84 s. In each round a and h were within 0.18 s of t. With the setting turned off and the same restarts, h ran the installer and took 2.62–4.05 s against t's 1.34–2.90 s; one breakdown shows the installer's `StartContainer` returning at 11:08:37.33 and the app's `PullImage` starting at 11:08:38.45, the relist wait the image volume removes. (Starts where the node pulled an image, the first deploys and one restart of a that pulled `pause` and `traefik/whoami`, took 1.0–2.2 s and are left out.)
