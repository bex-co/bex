## Objective

Implement `core.Base.AuthorizeApp(ctx, relation, name) (*App, error)`: fetch the resource, derive its workspace from `core.LabelTenant`, authorize `relation` there once, audit there once (target = resource name) — collapsing the current two independent gates (`Authorize` against the caller's default workspace, then `GetApp` against the resource's actual workspace) into one correct seam.

## Context

- `.pm/w6/done/013.md` (or `w6/013.md` if not yet moved) — the full diagnosis and designed fix this task implements verbatim.
- `lego/backend/internal/core/base.go` — `Authorize`, `GetApp`, `AuthorizeLabeled` (added by `w6/m14`) — `AuthorizeApp` builds on `AuthorizeLabeled`.
- **Critical invariant to preserve:** 403-before-404. Today `Authorize` runs before the fetch, so an unauthorized caller gets `ErrForbidden` for a name that doesn't exist. `TestAuthzGuardsEveryVerb` sweeps verbs against an empty fake client and expects `ErrForbidden` — a naive fetch-first `AuthorizeApp` returns `ErrNotFound` and fails that sweep. The fix: authorize against the caller's **acting** workspace first when the fetch would 404 (i.e., attempt the fetch, and on a not-found, fall back to authorizing against the acting/default workspace to preserve the existing "forbidden beats not-found" ordering for a truly nonexistent resource).

## Steps

1. Implement `AuthorizeApp` per the design in `w6/013`.
2. Verify the 403-before-404 ordering is preserved for both "resource exists, caller lacks access" and "resource doesn't exist at all" cases.
3. Verify `core.Base.AuthorizeTarget`'s audit vocabulary still names the same event for calls that route through the new seam.
