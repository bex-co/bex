## Objective

Replace Kratos's sketchy default verification/recovery emails ("Verify your
account with the following code: … or clicking the following link: …") with
templates rendered in bex's standard branded email layout, generated from the
same source as every other bex transactional email so the two can never drift.

## Context

- The standard: `lego/backend/internal/email/layout.html.tmpl` — table-based,
  fully-inlined HTML whose palette is generated from the dashboard's own
  style.css (`brand_gen.go` + `dashboard/scripts/generate-email-brand.mjs`);
  invites/deploy/webhook notices already use it. Kratos courier must join it.
- Kratos supports template overrides: `courier.templates.
  {verification_code,recovery_code}.{valid,invalid}.email.{subject,body.html,
  body.plaintext}` as Go-template URIs (`file://`, `base64://`), variables
  `{{ .VerificationCode }}` / `{{ .VerificationURL }}` / `{{ .RecoveryCode }}`.
- Gotcha: rendering Kratos placeholders THROUGH html/template's URL context
  yields `#ZgotmplZ` — generate with sentinels and post-replace, the same
  pattern as the brand-token Replacer.
- dev-6 (Mailpit :53060) is the live verification bench.

## Steps

1. Generator in `lego/backend/internal/email` (the `TestDumpGraphQLSchema`
   pattern: env-gated test writes files) rendering the bex layout into Kratos
   template files for verification_code + recovery_code, valid + invalid,
   html + plaintext + subject; code-carrying subjects ("<code> is your bex
   verification code"). Plaintext stays information-equivalent.
2. Drift guard test: committed template files must equal generated output.
3. Wire the templates into the Kratos deployment (chart `emailTemplates` values
   or ConfigMap mount + `courier.templates.*` config in
   `deploy/gitops/base/values/kratos.values.yaml`).
4. Apply to dev-6, register a fresh user, verify the Mailpit HTML body renders
   the bex card (brand palette, code prominent, button to the verification URL)
   and the plaintext part carries code + link.

## Files

- `lego/backend/internal/email/` (generator + guard test)
- `deploy/gitops/base/values/kratos.values.yaml` (+ template files wherever
  the delivery mechanism wants them)

## Acceptance criteria

- [x] Fresh signup's verification email in Mailpit is the bex-branded card
      (HTML) with an equivalent plaintext part; recovery email likewise.
- [x] Subjects carry the code; `.invalid` variants are branded too.
- [x] Drift test fails if the committed templates stop matching the generator.

## Out of scope

- SMTP/courier infrastructure changes; localizing the emails; the bex-side
  mailer (invites etc.) which already uses the layout.
