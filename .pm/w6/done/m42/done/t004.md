## Objective

Make the dashboard's auth pages present the D8 restructure coherently: sign-up follows `continue_with` into verification instead of navigating to `/`, login renders the verification-required refusal, verification success continues to login — with the guarded `next` param surviving all three hops.

## Context

- `dashboard/src/features/auth/pages/register-page/index.tsx:47` navigates to `/` on success today — under D8 there is no session to land with; the registration response carries `continue_with` (`show_verification_ui`).
- `useOryConfig` already sets `verification_enabled: true` / `verification_ui_url: /auth/verification` (`src/common/lib/ory/config.ts:48-53`), so Ory Elements can follow the flow; verify the deployed `@ory/elements-react` actually presents the login hook's verification-required state and handle it explicitly if not (implementation risk flagged in the ADR review).
- D3 (as corrected): `next` is threaded **client-side as a query param** — sign-up → `/auth/verification?next=…` → `/auth/login?next=…` — re-validated by the same guard login already uses; no Kratos `return_to` dependency.
- Repo rule: don't hand-roll auth forms; use Ory Elements flow components (`dashboard/CLAUDE.md`).

## Steps

1. Register page: on success, follow `continue_with` to `/auth/verification` (carrying validated `next`); honor the same guarded `next` semantics as login on entry.
2. Login page: render the `require_verified_address` refusal state — Ory Elements' presentation if it handles the flow error, else an explicit branch into the verification flow with the same messaging.
3. Verification page: on success, navigate to `/auth/login` (+ validated `next`); keep the flow usable when reached directly/unauthenticated (it must be — no session exists yet).
4. Exercise the full loop against the t003 `dev-6` Kratos (Mailpit for codes): sign-up → code → login → deep link honored.
