# Postgres `max_connections` follows Render's plan table, set explicitly

Why: every bex Postgres plan has 4 GB or less today, so PostgreSQL's default of 100 matches Render by accident; nothing pins it, so the 8 GB and 16 GB plans [w6/m332](blocked/m332/README.md) adds (Render: 200 and 400) would silently stay at 100, and w6/m457, w6/m458 and w6/m459 need the figure from one table.

- **Render** ([compute plans § Render Postgres plans](https://render.com/docs/compute-plans), read 2026-11-17): 100 connections up to 4 GB (`free`, `0.1c-256mb`, `0.5c-1g`, `1c-2g`, `1c-4g`, `2c-4g`), 200 for `2c-8g`, 400 for `2c-16g` and `4c-16g`, and 500 for every plan with 32 GB or more. "The compute plan only determines your database instance's RAM, CPU, and connection limit."
- **bex** sets no `max_connections`: `pgExtensionParameters` (`lego/operator/internal/controller/database_operand.go`) sets `shared_buffers` and the extension settings only, so CNPG runs PostgreSQL's default 100. The tiers (`lego/types/tiers/tiers.yaml` `postgres:`) are `free`, `basic-256mb`, `basic-1gb`, `1c-2g`, `pro-4gb` and `basic-4gb`, with Render's spec ids aliased in `lego/types/tiers/aliases.go`.
- **Do:**
  1. Add `maxConnections` to each `postgres` tier, with an accessor in `tiers.go`. A guard test pins every id and alias bex accepts to Render's figure, and carries Render's whole table so a tier added later (w6/m332) must match it.
  2. Set `max_connections` from the plan as a platform-owned parameter beside `shared_buffers`, so `Spec.Parameters` cannot change it.
  3. On dev-6, confirm an existing cluster does not restart: the value stays 100, so `pg_settings.pending_restart` stays false after CNPG rewrites the configuration.
  4. Add a line to w6/m332's README pointing at the table, so its new plans take 200 and 400.
- **Done when:** `SHOW max_connections` reads 100 on a database of each current plan on dev-6, no running cluster restarted, and the guard test fails for a tier whose figure differs from Render's.
- **Source:** `/pm-brainstorm one aspect of render parity for w6` 2026-11-17, item 2, filed by the user's `/pm them to w6`.

**Done 2026-11-17.** Step 1 had landed with w6/m457 (`e2e85ac52`): every tier's `maxConnections` and `TestPostgresMaxConnectionsMatchRender`, which fails a tier off Render's figure (checked again: `basic-1gb` at 200 fails it). Step 2: `cnpgClusterSpec` sets `max_connections` from the plan after the tenant's parameters on every operand, not only beside `shared_buffers`. That block is only projected with an adopted bex operand, and no major has one. A declared `max_connections` in any spelling is dropped, and recovery strips one (`operatorManagedParameters`). Step 3, on dev-6 (CNPG 1.30.1, PostgreSQL 18): one probe Cluster per current plan was created from the previous spec and then given the new one. Each read `max_connections` 100 from CNPG's `custom.conf`, with `pending_restart` false and the same Pod UID, restart count 0 and postmaster start time a minute later. In a contrast run, 101 on one probe restarted PostgreSQL in place. The probes were deleted. Production on 2026-11-17 has four tenant databases, all at 100 with none declaring the setting, so the deploy restarts none. Step 4: w6/m332's README points at the table. Recorded in ADR009 § Server connection limit and ADR018.
