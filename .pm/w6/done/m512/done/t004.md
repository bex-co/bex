## Objective

Enabling internal authentication closes every connection the old, unauthenticated proxy pod relays within seconds, even though that pod now drains on `SIGTERM`. This keeps the w6/m463 guarantee and Render's "existing connections that use your unauthenticated URL will break" ([Key Value](https://render.com/docs/key-value)). Decide, with evidence, whether a credential rotation and making a store private must also cut at once, and give them the same treatment if so.

## Context

- The old pod's env and grace period are fixed when it is created, so it cannot learn the reason for its own `SIGTERM`.
- The operator has no pod `delete` RBAC, only `get`, `list`, `patch` and `watch`. It does dial each store's Valkey as `kvPlatformUser` (`+@all`), so `CLIENT LIST` and `CLIENT KILL ID` are available. The proxy's upstream connections arrive from its pod IP.
- Candidate mechanisms:
  - (a) While a pod of an older template revision still exists and the current template differs from it in a field that must cut access, the operator kills that pod's upstream clients in Valkey. Match on the pod IP in `CLIENT LIST`, and repeat until the pod is gone, because the pod accepts until it gets `SIGTERM`.
  - (b) A short-grace delete of the old pod. This needs new RBAC and a pod watch.
  - Prefer (a), unless the evidence says otherwise.
- The template already distinguishes the change: `BEX_KV_INTERNAL_AUTH`, `credentialRevisionAnnotation` and the TLS env. The current pod's ReplicaSet carries its template.
- Making a store private: check whether `kv-sni-proxy` already closes a removed route's streams. If it does, the internal proxy's TLS listener drains nothing reachable.

## Steps

1. Pick the mechanism and the list of changes that cut at once. Write both down in this task's progress section.
2. Implement them in the operator, reusing the existing platform-user dial.
3. Test them: an envtest or unit test with a fake Valkey, or the engine tests' real Valkey (`keyvalue_internal_auth_engine_test.go`).

## Progress — 2026-11-19: mechanism and decisions

- **Mechanism (a), with no new RBAC.** `cutStaleKeyValueProxyClients` (`keyvalue_internal_proxy_cut.go`) runs on each KeyValue pass after the internal route. It lists the store's proxy pods from the cache. For each pod that is terminating and whose `BEX_KV_INTERNAL_AUTH` differs from the store's mode, it runs `CLIENT LIST` against the store's Valkey (`<id>-0`) as the platform user and `CLIENT KILL ID` for every client whose address is that pod's IP. While such a pod remains, the store is polled every second (`kvProxyCutRequeue`), and proxy pod events now enqueue the store (`keyValuePodRequests`).
- **Why only once the pod is terminating.** Until then the old pod serves as it did in w6/m463, so the store keeps an endpoint while the new pod starts. A stale pod that accepts until its `SIGTERM` is caught by the next one-second pass.
- **Enabling internal authentication cuts at once.** It is the only roll whose old pod's connections must close, because they were authenticated by the proxy.
- **Credential rotation: no cut needed.** `credentialRevisionAnnotation` is on Valkey's template as well as the proxy's (`keyvalue_controller.go`, `applyKeyValueStatefulSet`), so a rotation restarts Valkey. That closes every upstream connection and ends the old pod's drain. The password is also not user-rotatable (ADR021 § 6).
- **Plan change and suspension: no cut needed.** Both change Valkey's template too.
- **Making a store private: no cut needed.** It changes no proxy template: `tlsForwarded()` stays true while the store's server can listen (§ 3), so the proxy does not roll. `kv-sni-proxy` drops the route for new connections and has never closed a removed route's open streams (`cmd/kv-sni-proxy`, `kvRouter.delete`). This milestone changes neither.
- **Tests:**
  - `TestKeyValueCutsOnlyATerminatingProxyOfTheOldMode` checks five cases: enabling, a binary-only roll, a roll after enabling, an old pod still serving, and no pod IP yet. It also checks the 1 s requeue and that a proxy pod's event reaches the store.
  - `TestEnablingInternalAuthCutsADrainingProxysClients` (the Valkey 7 and 8 engine tests, which run when `BEX_TEST_VALKEY` is 1): a held unauthenticated client through a proxy draining for 30 s is closed within 5 s of the operator's pass, and the old proxy's `Serve` then returns. With the mode unchanged nothing is cut, and the held client still answers `PING` a second later.
