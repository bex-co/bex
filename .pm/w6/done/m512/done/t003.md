## Objective

`reconcileKeyValueInternalProxy` sets `BEX_KV_DRAIN_SECONDS` and a `terminationGracePeriodSeconds` that covers it, in the same template write as the image change, so no store rolls twice. A drain must not let a store's tenants take Valkey's platform reserve of 10.

## Context

- `lego/operator/internal/controller/keyvalue_internal_proxy.go` builds the template.
- w6/m469's hold keeps the image while the binary is byte-identical. This milestone changes the binary, so the env and grace period ride on the roll the binary already causes.
- ADR021 § 9: Valkey runs `--maxclients` at the plan's limit plus 10, and each proxy pod's budget is the plan's limit.
- `deploymentRolloutReady` (`app_controller.go`) counts no terminating pod, so a draining old pod does not hold the store's readiness.

## Steps

1. Choose the bound and justify it in ADR021 (t006). Weigh in-flight commands, how long the reserve is exposed, and node drains, which respect the grace period. Short commands finish in milliseconds, while a blocking command waits as long as its client asked. Something in the 30–60 s range is the expected answer. Render documents no figure for Key Value.
2. Set the env and `terminationGracePeriodSeconds`. Make the grace period the drain plus a few seconds' margin, so the process closes its streams itself before `SIGKILL`.
3. Measure the reserve risk and bound it. While an old pod drains, the old and new pods together can admit up to twice the limit. Find whether a client can actually push the upstream past `--maxclients` during a drain (pools keep their old connections, so growth needs new dials). Then fix it. Options:
   - make the new pod's `--check` treat Valkey's maxclients refusal as "up";
   - have a draining pod stop counting toward the budget;
   - shorten the drain.
   Record the choice in t006.

## Result — 2026-11-19

- **Bound: 30 s drain, `terminationGracePeriodSeconds: 35`** (`kvInternalProxyDrainSeconds`, `kvInternalProxyGraceSeconds` in `keyvalue_internal_proxy.go`). 30 s is Render's default shutdown delay for its own instances ([deploys](https://render.com/docs/deploys), read 2026-11-19: "If your app's process doesn't exit within its specified shutdown delay (default 30 seconds)"). Render documents no figure for Key Value. A command in flight takes milliseconds and the pod exits once idle, so the bound decides only when a held client is closed, and how long a node drain waits for a proxy. The 5 s margin lets the process close the rest itself before `SIGKILL`. The env and grace period go in the same template write as the image, so the deploy whose binary change carries them rolls each proxy once.
- **The reserve risk is real.** With the fix reverted, `TestADrainingProxyLeavesTheReserveToThePlatform` fails on both pinned images. A free store's tenants held 50 clients through the old pod and reconnected 50 through the new one, and a platform-user dial during the drain read `EOF`: Valkey's 60 slots were full.
- **Fix: the draining pod gives its streams back** (`kvinternalauth.KeepReserve`). While it drains, the old pod reads `INFO clients` every 100 ms over one connection, as the default user, with the password it already holds for `--check`. While the store has more clients than the plan's limit besides that connection, it closes that many of its own draining streams. If the upstream already refuses it, it closes one per tick. Platform clients count toward the limit here, so a tenant at its limit can lose a draining stream a few seconds early. Rejected:
  - `--check` treating Valkey's refusal as ready: Valkey's own probe, the exporter and the operator would still be refused.
  - A shorter drain: a tenant can open 10 connections inside any window.
  - Raising `--maxclients`: Valkey lowers its open-files hard limit to the start value, so every store would restart (ADR021 § 9).
- **Tests:**
  - `TestKeyValueInternalProxyDrainsWithinItsGracePeriod` fails without the env or when the grace period does not exceed it.
  - The m469 hold envtest (`keeps the proxy's image and generation …`) still sees no new template for an unchanged binary, now with the drain env and grace period in it.
  - `TestADrainingProxyLeavesTheReserveToThePlatform` (the Valkey 7 and 8 engine tests, which run when `BEX_TEST_VALKEY` is 1): all 50 tenants reconnect through the new pod, then a fresh platform-user dial and `kvinternalauth.Check` both succeed.
  - `TestKeepReserveGivesTheNewPodsClientsTheDrainingStreams`, `TestKeepReserveClosesNothingBelowTheLimit`, `TestKeepReserveShedsWhenTheUpstreamIsFull` and `TestConnectedClientsRefusesAnUnexpectedReply` run without Docker.
