## Objective

Ensure a confirmation cannot outlive the context or permission under which it was opened.

## Context

- Service and deploy controls hold local confirmation state; identity/workspace/target changes can make it obsolete.
- Existing server mutations remain the final authority and already support protected-resource confirmation where applicable.

## Steps

1. Capture the workspace, resource, optional deploy ID, and action when opening a confirmation.
2. Before dispatch, verify that context is current and refresh the needed permission/precondition; discard any check result whose context changed while awaiting it.
3. Clear obsolete confirmations on context or confirmed access loss; compose the existing protected-confirmation flow without bypassing it.
4. Keep retry of a failed read separate from mutation submission; never replay an ambiguous or offline mutation automatically.

## Acceptance criteria

- [ ] Changing workspace/service/deploy during an open confirmation results in zero dispatch against the stale target.
- [ ] A permission loss or unavailable recheck prevents dispatch and presents the correct explanation.
- [ ] Double submission, protected confirmation, and ambiguous transport results preserve existing safe mutation behavior.
