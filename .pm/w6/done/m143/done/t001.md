## Objective

Expose serverActions and deployActions to dashboard consumers with typed target binding and distinct permission/precondition states.

## Context

- The backend projections live in `lego/backend/internal/apps/actioncaps.go` and `lego/backend/internal/deploys/actioncaps.go`.
- The generated dashboard schema contains these fields, but no dashboard query currently consumes them.

## Steps

1. Add the GraphQL documents with explicit acting-workspace and service identity using the existing request-context convention; regenerate relevant types.
2. Normalize allowed/denied/unavailable, missing actions, and precondition codes without introducing another authorization engine.
3. Reuse permission tooltip/menu primitives and provide bounded English/Chinese reasons.

## Files

- dashboard/src/features/capabilities/api/ (new action documents)
- dashboard/src/features/capabilities/hooks/
- dashboard/src/features/capabilities/locales/en.ts
- dashboard/src/features/capabilities/locales/zh.ts
- dashboard/src/graphql/definitions.ts
- dashboard/src/graphql/schema-types.ts
- lego/backend/internal/apps/actioncaps.go (contract reference)
- lego/backend/internal/deploys/actioncaps.go (contract reference)

## Acceptance criteria

- [ ] An action result is associated with the exact requesting workspace/service; obsolete results cannot enable another target.
- [ ] Unknown action/outcome/precondition values render unavailable rather than permissively enabling dispatch.
- [ ] Generated documents use the existing backend contract and explanations distinguish denial from unavailable checks.
