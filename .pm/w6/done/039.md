# 039 — Scheduled cron execution can run concurrently with an active manually-triggered run, violating the documented "single concurrent execution" guarantee

Why: bex's own contract doc (`docs/render-artifacts/cron-runs.md`) promises "a single concurrent cron execution," stricter than Render's cancel-and-replace — but the guarantee silently breaks whenever a schedule tick lands during an active manual Trigger Run, risking duplicate side effects for any non-idempotent cron command.

**Severity:** major

**Repro** (on a fresh `cron_job` service, schedule `*/5 * * * *`):

1. Create the service; wait for its first deploy to reach `Running`.
2. Before the next scheduled tick, trigger a manual run via Events → Recent Runs → Trigger Run → confirm. A run starts (`crr-...`, status maps to "pending"/displays "Running"); the Trigger Run button correctly disables while it's active.
3. Let the manual run keep executing (used a long-lived process — a Go HTTP server binary — as the Start Command so it wouldn't self-terminate) until the schedule's next tick passes.
4. Query `cronJobRuns(serviceId)` again, or reload Events → Recent Runs.

**Expected:** at most one active run at a time (per `docs/render-artifacts/cron-runs.md`: "Render documents a single concurrent cron execution... bex applies `ForbidConcurrent` to scheduled Kubernetes CronJobs").

**Actual:** a SECOND run starts at the scheduled tick while the manual run is still active. Confirmed via GraphQL (two distinct `crr-` ids, both `startedAt` set, both `finishedAt` empty, both status "pending"/"Running") AND via live log streaming showing two genuinely separate pod instances running concurrently (`<app>-run-<hash>-<suffix>` from the manual trigger, `<app>-<cronjob-hash>-<suffix>` from the schedule).

**Root cause:** `lego/operator/internal/controller/app_controller.go`'s `reconcileCronJob` (~line 2706) sets `cj.Spec.ConcurrencyPolicy = batchv1.ForbidConcurrent` on the `batchv1.CronJob` object, but Kubernetes' own ConcurrencyPolicy only inspects Jobs that CronJob object's controller created itself — it has no visibility into the separate one-off `batchv1.Job` `ensureManualRun` (~line 2940) creates directly, owned by the App CR rather than the CronJob. Nothing suspends the CronJob's own schedule while a manual run is active: `cj.Spec.Suspend` (~line 2730) is driven only by `app.Spec.Suspended` (the user-facing Suspend action), never by "a manual run is currently in flight." `TriggerCronRun` (`lego/backend/internal/apps/service.go:2738`) does cancel an existing *pending* run before starting a new manual one (so manual-vs-manual overlap is prevented), but nothing in either direction accounts for manual-vs-scheduled overlap.

**Fix direction:** have the operator suspend the underlying `batchv1.CronJob`'s own schedule (`cj.Spec.Suspend = true`) whenever a manual run (from `app.Spec.RunAt`) is active, mirroring the existing `app.Spec.Suspended` → `cj.Spec.Suspend` toggle already in `reconcileCronJob`, and un-suspend once that run reaches a terminal state. Alternatively/additionally, `ensureManualRun` could check for an active scheduled Job (via the `labelApp` selector) before creating the manual one, matching `TriggerCronRun`'s existing manual-vs-manual cancel logic.

**Blast radius:** single mechanism (`reconcileCronJob`/`ensureManualRun`), one CRD field (`app.Spec.RunAt`) — affects every `cron_job` service that has both a real recurring schedule and ever uses the manual Trigger Run action; doesn't affect cron jobs that are never manually triggered.

**Adjacent classes:** manual-trigger-while-manual-run-active is correctly rejected (disabled button + backend `ForbidConcurrent`-style rejection, per `w5/029`'s verified walk); scheduled-tick-while-scheduled-run-still-active is correctly forbidden by k8s's own `ConcurrencyPolicy: Forbid` (same CronJob object, so k8s sees both). Only the scheduled-vs-manual cross-mechanism case is unguarded.

**Unverified:** whether the reverse ordering (schedule fires first, then a manual trigger is attempted while the scheduled Job is still active) is also unguarded — `TriggerCronRun`'s cancel-existing-pending-run logic reads `a.Status.Runs`, which is populated uniformly for both scheduled and manual Jobs via `cronRuns()`/`toCronRun()`, so it likely *would* correctly cancel an active scheduled run before starting a manual one — but this specific ordering wasn't live-tested this session.

**Render:** Render's own contract (per the same artifact doc) uses "cancel active, then start replacement" rather than bex's stricter "reject/suspend while active" — so Render itself has no scheduled-vs-manual gap by construction (a manual trigger there always cancels whatever's running first). bex's design is intentionally stricter but the scheduled-run path was never updated to honor that stricter guarantee.

**Estimate:** tens of minutes (the suspend-while-active pattern already exists in the same function for `app.Spec.Suspended`; extending it needs a way to track "manual run active" distinctly from "user requested Suspend").

Deduped: confirmed distinct from `w5/029` (that note verified manual-vs-manual rejection, never covers this scheduled-vs-manual case) and from all other open w6 cron-related items; not in `.pm/DO_NOT_DO.md`. Verified live 2026-08-24.

## Closed 2026-08-27 — live-verified across three schedule ticks, plus the resume and this note's own Unverified case (38th `/qa-find-bugs` run)

`d247d210`: *"`reconcileCronJob` now pauses the CronJob's own schedule for the manual run's duration, reusing the mechanism `spec.suspended` already drives, and requeues at 10s so it resumes promptly."*

**The shipped code**, in `reconcileCronJob` (`lego/operator/internal/controller/app_controller.go`):

```go
manualRunActive, err := r.manualCronRunActive(ctx, app, cancelPending)   // :3008
scheduleSuspended := suspended || manualRunActive                         // :3012
cj.Spec.Suspend = &scheduleSuspended                                      // :3023
…
if manualRunActive { return ctrl.Result{RequeueAfter: 10 * time.Second}, nil }   // :3074-3079
```

with a comment naming this note and the exact mechanism — that a manual run is an App-owned one-off Job which `ConcurrencyPolicy` structurally cannot see. `manualCronRunActive` (`:3122-3135`) returns true while the manual Job exists-and-is-unsettled, and conservatively true in the not-yet-created window.

**Fixture:** `qa-20260827-cronrace2`, `cron_job`, Go runtime, schedule `* * * * *` (every minute), command `sleep 200` — a run long enough to span three tick boundaries. Live at `10:27:37Z`.

**1. The filed case: a schedule tick during an active manual run.** Triggered manually, then sampled `cronJobRuns` every ~9 s from `10:28:22Z` to `10:31:58Z`, spanning the **10:29:00, 10:30:00 and 10:31:00** ticks:

```
maxConcurrent across the whole window: 1
active run throughout:  crr-a36cq6jmlplhu0koo56f   (the manual one)
```

No second `crr-` ever appeared. Under the filed bug a scheduled run started at the first tick, giving two concurrently-active runs with two separate pods.

**2. The resume — the control a suspend-only fix would fail.** Pausing the schedule and never lifting it would pass test 1 while silently killing the cron. After the manual run finished, a **new** run appeared without any trigger from me:

```
10:32:20Z   total runs 2 → 3,  active: crr-8tfgm6f4…   ← scheduled, so the schedule un-suspended
```

**3. This note's own `Unverified` line, now closed.** The note predicted but never tested the reverse ordering — a manual trigger arriving while a *scheduled* run is active. It happened by chance here: at `10:28:00Z` a scheduled run `crr-4opvthisvvc4fbs0vgpa` was already active when the manual trigger fired, and it was **canceled** rather than left to run alongside:

```
before trigger:  crr-4opvthisvvc4fbs0vgpa  status "pending"   startedAt 10:28:00Z  finishedAt ""
after  trigger:  crr-4opvthisvvc4fbs0vgpa  status "canceled"  finishedAt 10:28:03.458Z
```

Exactly what the note reasoned `TriggerCronRun`'s cancel-existing-pending-run logic would do, since `a.Status.Runs` is populated uniformly for scheduled and manual Jobs. Recorded here so the `Unverified` line does not outlive the note.

So all three orderings now hold the documented single-concurrent-execution guarantee: scheduled-vs-scheduled (k8s `ForbidConcurrent`), manual-vs-manual (`TriggerCronRun`'s cancel, per `w5/029`), and both directions of scheduled-vs-manual — the last being the gap this note found.
