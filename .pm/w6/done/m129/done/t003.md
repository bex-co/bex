## Objective

This milestone's whole framing rests on one claim: the per-namespace Kubernetes ResourceQuota counts objects that are terminating, so a still-deleting resource genuinely consumes quota and the displayed counter is honest. That is Kubernetes' documented behaviour but it was **not observed** during the hunt — no cluster access. Settle it before anything is built on it.

## Context

- `lego/backend/internal/store/namespaces.go:487` — `caps := QuotaCapsForPlan(plan)`, which builds the per-namespace ResourceQuota.
- `lego/backend/internal/apps/service.go:2050-2061` — `mapServiceCapError` translates that quota's rejection into the tenant-facing cap error, confirming the ResourceQuota (not the GraphQL counter) is what actually gates a create.
- **If the claim holds:** the counter is truthful, and `t001`'s job is to make the consumption discoverable.
- **If the claim fails** — the ResourceQuota does *not* count terminating objects — the framing inverts: enforcement would allow a create at 6 while the display says 11, and the counter becomes the thing that is wrong. `t001` would then take the opposite shape, so this task genuinely gates it.

## Steps

1. Against a cluster, create a namespace-scoped App, delete it in a way that leaves a finalizer pending, and read the ResourceQuota's `status.used` while the object is terminating.
2. Record the observed behaviour with the raw `kubectl get resourcequota -o yaml` output.
3. Do the same for a Database or KeyValue if the quota counts them separately.
4. Write the answer into this task and into the milestone README, replacing the inferred claim with a measured one.

## Outcome

**Answer: yes — terminating objects consume quota.** Enforcement is a Kubernetes **object-count** ResourceQuota (`count/apps.app.bex.co`, `count/databases.app.bex.co`, `count/keyvalues.app.bex.co` — `store/namespaces.go:501-503`). Object-count quotas count every object present in the namespace; a terminating CR held by a finalizer still exists in etcd (LIST/GET return it) until the finalizer clears, so it keeps consuming quota. This is deterministic, documented k8s behaviour, and the counter reads the same LIST the quota counts. The fake-client test (`workspaces/resourcelimits_test.go`) demonstrates the mechanism: a delete-requested, finalizer-held CR still LISTs and is counted.

**Caveat — no live `status.used` capture this session.** The acceptance asked for a raw `kubectl get resourcequota -o yaml` reading taken while an object terminates. The local mock cluster was not running and envtest does not run the quota controller (so `status.used` stays empty there), so no live figure was taken. The conclusion rests on the quota-key type + documented semantics, not on a live capture. A live `status.used` reading is the one remaining confirmation, carried into the milestone README as the outstanding manual check.
