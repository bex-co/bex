## Objective

Only services exhibits the divergence today, but all three counters share the missing filter. Fixing services alone leaves the identical latent defect on the two resource kinds whose Hobby cap is 1 — where a single terminating object consumes the entire quota.

## Context

- `lego/backend/internal/workspaces/service.go:953-955`:

  ```go
  out.Services.Used  = len(apps.Items)
  out.Postgres.Used  = len(dbs.Items)
  out.KeyValues.Used = len(kvs.Items)
  ```

  None filters on `DeletionTimestamp`. Postgres (3) and Key Value (2) matched reality during the hunt only because neither happened to be mid-delete.
- `store/plans.go:107` — Hobby is `Postgres: 1, KeyValues: 1`. The blast radius of one lingering datastore CR on that plan is total.
- Datastore teardown has its own history: `w3/m46/t009`'s control table measured Key Value deleting in ~1s and Postgres in ~1s, so the window is normally short — which is exactly why this is latent rather than visible, and why a test must force the state rather than wait for it.

## Steps

1. Apply `t001`'s chosen rule to the Database and KeyValue counters.
2. Exercise each with a datastore genuinely mid-delete — force the state rather than relying on catching it.
3. Confirm the Hobby caps behave correctly at the boundary (1 of 1 used, one terminating).
