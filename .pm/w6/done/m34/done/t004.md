## Objective

End-to-end proof on a live stack: a repo-backed Docker service whose Dockerfile `FROM`s a private image builds and deploys green when a credential is bound, and fails with a pull auth error when it isn't (negative control).

## Context

- `w6/m31`'s closeout ran the equivalent live check for the image context against an auth-enabled private registry with an anonymous negative control — mirror that recipe (see `w6/done/m31/`).
- dev stack: `.pm/w6/dev-6/` (this workstream's isolated stack).

## Steps

1. Push a private base image to the auth-enabled registry from the m31 recipe; create a repo-backed Docker service whose Dockerfile uses it.
2. Bind the credential → build green; unbind → build fails on pull auth (negative control).
3. Capture evidence (build log excerpts) in the task file on completion.

## Files

- `.pm/w6/dev-6/` stack; no product code expected

## Acceptance criteria

- [x] Positive and negative controls both observed and recorded.

## Evidence

On 2026-07-15, the local CAPD app cluster ran an authenticated disposable `registry:2` and a Git repository whose Dockerfile began with `FROM zot.bex-registry.svc:5000/private-base:latest`.

- Valid bound credential: BuildKit logged credential sharing, resolved the private manifest, pushed `m34-positive:gen-4`, and the generated background-worker pod reached `1/1 Running`; App phase was `Running` / reason `Deployed`.
- Wrong bound credential: the same private manifest `HEAD` returned `401 Unauthorized`; App phase was `Failed` / reason `BuildFailed`.
- The positive Job referenced only `bld-m34-positive-registry-auth` at `/docker-config`. Both Apps, both credential Secrets, the registry namespace, host Git/port-forward processes, temporary repo, and local registry tag were removed afterward.
