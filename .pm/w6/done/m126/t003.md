## Objective

The conformance suite validates ten read operations and nothing else, which is why a non-conformant create response shipped unnoticed. Bring projects under it and extend it to write responses, so this stops the class rather than the instance.

## Context

- `internal/api/conformance_test.go`'s `operationPath` map (its own comment at `:360`: "maps an operationId to the bex REST path under test") covers exactly these ten, all reads:

  `list-services · retrieve-service · list-postgres · retrieve-postgres · retrieve-redis · list-secret-files-for-service · list-custom-domains · list-events · retrieve-event · list-redis`

- No project operation appears, and no `POST`/`PATCH`/`PUT` response of any resource is validated.
- There is **no** allowlist entry for any project operation in `conformance_allowlist_test.go` — unlike the `serviceDetails` union, which is a deliberate documented divergence. Projects are unexamined, not waived.
- **Expect this to find siblings.** Other resources may have the same write-path mistake; projects are simply where it was caught. Newly surfaced offenders are follow-up filings, not scope creep here — record them, fix what is cheap, file the rest.

## Steps

1. Add the project operations to `operationPath`.
2. Extend the suite to validate create/update/replace response bodies against their Render schemas, not just reads.
3. Run it and record every violation it surfaces across all resources.
4. Fix what belongs to this milestone (projects); file the rest with their own evidence.
5. Where a violation is a deliberate divergence, add a narrow allowlist entry citing the ADR018 row — never a broad one.
