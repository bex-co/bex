## Objective

Retain a valid initial notification response until authentication, workspace selection, and destination access are ready, then consume it exactly once.

## Context

- The mount effect clears the binding before inspectAndRepair and immediately clears/handles the last response.
- The notification response callback rejects when notificationMatchesBinding has no current binding.

## Steps

1. Capture a bounded pending initial response and coordinate it with restored identity/workspace/access rather than consuming it during unresolved startup.
2. Dedupe initial-response and live-listener paths; clear the response after successful consumption or explicit terminal rejection.
3. Revalidate the closed envelope, current binding, and destination permission before routing; handle offline/unconfigured registration honestly without inventing navigation authority.

## Acceptance criteria

- [x] A cold-start response observed before auth/workspace readiness is not silently lost and opens once after validation.
- [x] The same response delivered by both initial lookup and a listener does not navigate twice.
- [x] Wrong session/workspace, malformed routes, and denied destinations never expose destination details or silently switch workspaces.

## Out of scope

- Changing the notification envelope's security boundaries.
- Automatic execution of resource actions from a push.

## Completion evidence — 2026-09-07

Mounted provider and native initial-response fixtures wait for restored workspace/access and navigate exactly once; duplicate, foreign and denied responses cannot route. The OS initial response is cleared only on consumption or terminal rejection. See [verification and platform evidence](../../../../../mobile/e2e/m140-notifications.md).
