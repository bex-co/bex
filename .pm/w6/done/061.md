# 061 — A rollback emits `build_started`/`build_ended: succeeded` although it runs no build

Why: the Events timeline, the `build_started`/`build_ended` webhook payloads and the metrics build marker all report a build that never happened, on the one operation whose whole point is that it reuses an already-built image — and the discriminator the fix needs is already sitting in the same function.

Filed 2026-08-27, 42nd `/qa-find-bugs` run, journey 3 (Deploys: rollback leg).

## Live repro

On `qa-20260827-shell` (`srv-da82ntnm2e9c73ft5lk0`, free web service, repo `bex-co/bex-hello-go-live`, deleted at end of run). Rolled back to the deactivated first deploy:

```
POST /v1/services/srv-da82ntnm2e9c73ft5lk0/rollback   {"deployId":"dep-da82ntnm2e9c73ft5lkg"}
=> 201 {"id":"dep-da82r28ueu1c7395iong","status":"created","trigger":"rollback",
        "image":{"ref":"zot.bex-registry.svc:5000/tea-.../...-qa-20260827-shell:gen-1@sha256:c0dd2e65ed39…"},
        "rollbackOf":"dep-da82ntnm2e9c73ft5lkg", …}
```

The creation response already carries the final pinned digest — there is nothing left to build. The events feed nevertheless reports a build:

build_started@2026-08-27T12:28:57Z  {"deployId":"dep-da82r28ueu1c7395iong","image":"zot.bex-registry.svc:5000/tea-…"}

## The control is in the same capture, and it is what names the mechanism

The non-rollback deploy on the same service, same minute — a real repo build:

```
build_started@2026-08-27T12:27:02Z  {"deployId":"dep-da82plnm2e9c73ft5lm0"}
build_ended@2026-08-27T12:28:15Z    {"deployId":"dep-da82plnm2e9c73ft5lm0","status":"succeeded"}
```

Two differences, both diagnostic: the real build took **73 seconds** and the rollback's "build" took **5**; and the rollback's facts carry an `image` field the real build's do not. That extra field is not noise — it is `Image: open.Image` (`reconciler.go:771,780`), populated because the rollback row was **born** with a resolved image, which is exactly the signal that says "this deploy has no build to run".

## Root cause

`lego/backend/internal/store/reconciler.go:740-742`:

```go
if d.Repo != "" {
    facts = append(facts, buildLifecycleFacts(open, newStatus)...)
}
```

The guard tests **the service's** repo. The function's own doc comment (`:731-738`) states the intended rule per **deploy**: "build_started/build_ended for a repo-backed deploy … an image-backed deploy (no build phase) and a deploy with no pre-deploy step each emit neither." A rollback on a repo-backed service *is* an image-backed deploy — `Rollback` requires `target.ResolvedImage != ""` and sets it with `SetAppImage` (`deploys/service.go:758,765`) — but the service carries a `Repo`, so the guard passes and the facts are emitted anyway. `buildEndedStatus`'s own doc says it reports "the outcome to stamp on a **repo-backed deploy's** build_ended fact", so the whole file is written to the per-deploy rule and only this one line implements the per-service one.

## Fix

Discriminate per deploy, not per service. `open.Image` is already in scope in `buildLifecycleFacts` and is non-empty exactly for deploys that skip the build. Target behavior: a deploy that runs no BuildKit Job emits neither `build_started` nor `build_ended` — the same silence an image-backed service's deploy already gets. Do **not** instead relabel the events; the timeline should not claim a build phase that has no Job behind it, which is the same standard `w7/m66` set when it corrected `service.go:88`'s "no source" claim on the grounds that ADR034's BuildKit Jobs are a real source.

## Blast radius

- `recordLifecycleFacts` has 1 call site (`recordDeploy`, `reconciler.go:653`), and `buildLifecycleFacts` has 2 (`recordLifecycleFacts:741` and the superseded-row path at `:659`, which is guarded by `d.Repo != ""` in the same shape at `:654` — check both, the second one closes rows that were genuinely building).
- **The sibling no-build path does not exist**, checked rather than assumed: an `imgURL` override on a repo-backed service is rejected outright (`deploys/service.go:437`, `p.ImageURL != "" && a.Spec.Repo != ""`), so rollback is the only way a repo-backed service produces a build-less deploy.
- Consumers that must be re-checked, not just the Events tab: the `build_started`/`build_ended` **webhook** payloads and the **metrics build marker**, both named as consumers of these facts by `buildStartedAt`'s comment (`reconciler.go:794-796`). A phantom build reaches all three.
- Facts are idempotent by `source_key`, so historical rows already written for past rollbacks stay — decide whether to leave them or backfill, and say which.

## Checked, and correct — recorded so the next hunt does not re-investigate

The rest of journey 3 passed cleanly on the same fixture:

- **Deploy hook.** `GET` on the hook URL is mutating — and that is deliberate parity, not a bug: `deploys/deployhook.go:332-345` says "accepts GET and POST like Render" and "GET is deliberately mutating for Render/curl compatibility", with `Cache-Control: no-store` and `Referrer-Policy: no-referrer` set for exactly the caching/referrer-leak hazards. Verified live that the mitigations actually ship: `PUT` → `405` + `allow: GET, POST`, and both `no-store` and `no-referrer` present on the 405 and on a bad-key 404. A bad key returns `404 app not found` — no oracle distinguishing "no such hook" from "wrong key".
- **Newest-wins.** Two hook deploys 2s apart: the older settled `canceled`, the newer went `live`, and the previously-live deploy became `deactivated`. `rev-1` → `rev-3`.
- **Rollback state machine.** Converged in ~42s to `live` with `trigger: "rollback"` and `rollbackOf` naming the restored deploy; REST detail, GraphQL `deploy(...)`, and the Events ledger all agree; the previously-live row went `deactivated`; `curl` on the public URL returned `200 OK — pushed v3`.
- **Shell (journey 8).** Not a bug and not testable here: `sshEligible` (`apps/service.go:981-995`) requires a **paid**, non-suspended web/private/worker, so the free-tier page correctly reads "Shell access isn't available — Shell access requires a running paid web, private, or background service and an active SSH gateway." Positive control observed read-only on paid running services (`beancount-forum`, `agentmarketcap-1` → `sshAddress: srv-…@ssh.bex.co`); free services return `""`. Plan-gated, so out of scope.

## Unverified

- That an **image-backed service's** deploy really emits neither fact — that is the control the code comment claims and this run did not create an image-backed service to observe it. Worth one probe before the fix, since it is the behavior the fix normalizes rollback onto.
- Whether the dashboard Events tab renders these two facts with build-specific copy/icons (it has a catalog per `w7/m66`), and what a phantom `build_ended: succeeded` looks like there — the API feed was read directly this run, not the tab.
- Whether past rollbacks in this workspace already carry the phantom facts (not queried).

## Resolution (2026-09-03)

One guard covers all call sites: `buildLifecycleFacts` early-returns when the deploy row was born with an image (`open.Image != ""` — rollback's stable discriminator), so no build facts are emitted; events are not relabeled, matching the note's target behavior. Triage found a third call site added after filing (`CanceledBuildLifecycleFacts`, w6/m128) with the same hole — covered by the same guard. Historical phantom facts left in place (idempotent by source_key; backfill deliberately out of scope). 4 red/green-proven regression tests incl. genuinely-building controls; test fixtures that impossibly carried a born image on repo builds corrected.
