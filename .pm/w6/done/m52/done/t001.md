## Objective

Name the correct target state a service should report when its very first deploy is canceled before any image has ever been released — the decision every other task in this milestone builds on.

## Context

- Live-confirmed: `server(id:).phase` currently returns `"Failed"` for this case, while `deploy(...).status` correctly returns `"canceled"` — see `w6/m52/README.md`'s live-evidence section for the exact repro and root cause (`lego/operator/internal/controller/app_controller.go:552-573`, `settleCanceledRelease`).
- The operator's own Condition already carries the right semantics (`Reason: "BuildCanceled"`, `Message: "build canceled before a release became available"`) — the gap is purely that the coarse `Phase` enum has no distinct value for this state, so it reuses `PhaseFailed`.
- Check render.com's actual dashboard/API behavior for the equivalent case (cancel a service's very first deploy) before deciding — this determines whether the fix is closing a genuine Render-parity gap or just choosing bex's own new wording.
- Existing `Phase` vocabulary to choose among/extend: `Pending`, `Building`, `Deploying`, `Running`, `Hibernated`, `Failed` (grep `appv1alpha1.Phase` in `lego/types/` for the authoritative list before proposing a new one).

## Steps

## Decision (2026-08-24)

**Render parity finding — the decisive one:** Render has **no service-level status field at all**. Its public `Service` object exposes `suspended`/`suspenders` and nothing else about lifecycle; the dashboard's service header simply renders the **latest deploy's** status. So on Render, canceling a first deploy shows "Canceled" in the header, because the header _is_ the deploy. bex's `phase` is a documented bex-only extra (`docs/ADR018-render-parity.md` line 54: "bex extras `phase`/`replicas`/`revision` (superset Render clients ignore)"), which is exactly why it was free to drift out of agreement with the deploy record — nothing on the Render side pins it.

That makes this a genuine parity gap, not a wording choice: bex should show what Render shows.

**Decision: add `PhaseCanceled AppPhase = "Canceled"`.**

Rejected alternatives:

- _Reuse `PhasePending`._ Accurate about "nothing running" but loses the fact that a user did this on purpose, and a service that sits at "Pending" forever after a cancel is its own confusion.
- _Thread the Condition `Reason` through to GraphQL instead of adding a Phase value._ More plumbing (new field on `AppView`, three surfaces, dashboard projection) for a distinction the phase enum is already the right shape to carry — and every consumer already reads `phase`.

Because `phase` is bex-only, adding a value cannot break a Render client, and the dashboard's `PHASE_STATUS` lookup already falls back to `"unknown"` for an unrecognized phase, so an older dashboard degrades gracefully rather than crashing.

|  | value |
| --- | --- |
| CRD phase | `Canceled` (kubebuilder enum extended) |
| dashboard status key | `canceled` |
| badge variant | `secondary` — non-destructive, matching `suspended`/`sleeping` |
| en / zh label | "Canceled" / "已取消" |

Scope: the `app.Status.Image == ""` branch only — a cancel with a live prior release keeps serving it and stays `Running`, which is what the Cancel dialog already promises.
