## Objective

`GET`/`POST`/`PATCH` `/v1/services` currently emit a service's `ipAllowList` as a top-level sibling of `serviceDetails` on the wire (`renderService.IPAllowList`, `lego/backend/internal/apps/render.go:150-157`, populated at `render.go:286`). Render's own pinned OpenAPI spec (`lego/backend/internal/api/openapi/render-public-api-1.json`) declares `ipAllowList` as a property of `webServiceDetails`/`staticSiteDetails` — nested inside `serviceDetails`, not beside it. Move the value into `renderServiceDetails()`'s map, exactly mirroring the `disk` fix already shipped in the same function (`render.go:346-353`, `w1/m86`).

## Context

- REST's write side already reads `serviceDetails.ipAllowList` correctly (`rest.go:501-504` on create, `rest.go:792-797` on PATCH) — this is a **read/response-rendering bug only**, not a store or write-path issue.
- Confirmed live this hunt: a POST create with `serviceDetails.ipAllowList: [{cidrBlock, description}]` is accepted and applied (enforcement works — a real Traefik `Middleware` blocks out-of-list traffic with `403`), but the create response and every subsequent GET show the value at the JSON root, not inside `serviceDetails`.
- Render's schema scopes `ipAllowList` to exactly `webServiceDetails` and `staticSiteDetails` — confirmed absent from `privateServiceDetails`/`backgroundWorkerDetails`/`cronJobDetails` in the same pinned spec file. This matches the existing create-time rejection for non-ingress types (`lego/backend/internal/apps/deploy.go:2025-2026`).
- `renderServiceDetails()` (`render.go:293-360`) already gates several fields by `svcType` (e.g. `maintenanceMode` to `renderWebService` only, `buildCommand` to static sites only) — follow the same pattern rather than inventing a new one.
- `toRenderServiceWithMetadata` (`render.go:220-286`) is the single call site that populates the top-level field via `cloneIPAllowEntries(a.IPAllowList)`; `renderService`/`serviceWithCursor`/`serviceAndDeploy` all wrap this one function, so create, PATCH, get, and list responses are all fixed by touching this one path.

## Steps

1. Add an `ipAllowList` key to the map built in `renderServiceDetails()`, populated from `a.IPAllowList` via `cloneIPAllowEntries`, gated to `svcType == renderWebService || svcType == appv1alpha1.TypeStaticSite` (match the existing type-comparison idiom used a few lines above for `maintenanceMode`/`buildCommand`), omitted entirely when the list is empty (matching the current `omitempty` behavior and Render's "empty = open to all" semantics).
2. Remove the top-level `IPAllowList` field from the `renderService` struct (`render.go:150-157`) and its population at `render.go:286`, **or** keep it as an explicitly-commented deprecated alias for one release — decide based on whether any other in-repo consumer (dashboard, CLI-compat scripts, `scripts/cli-compat.sh`) reads the root-level field; grep before deciding, and record the decision in this task's outcome, not silently.
3. Confirm `cloneIPAllowEntries` (`rest.go:394-400`) is reusable as-is for building the map value (it currently returns `[]core.IPAllowListEntry`, which needs to serialize to `[{cidrBlock, description}]` — check the JSON tags on `core.IPAllowListEntry`/`ipAllowEntry` match Render's field names exactly).

## Files

## Acceptance criteria

- [ ] `GET /v1/services/{id}` for a web service or static site with a saved `ipAllowList` shows `serviceDetails.ipAllowList: [{cidrBlock, description}]`.
- [ ] The same shape appears on the `POST /v1/services` create response and the `PATCH /v1/services/{id}` response — no divergence between create/update/read.
- [ ] `GET /v1/services/{id}` for a `private_service`/`background_worker`/`cron_job` never has an `ipAllowList` key in `serviceDetails`, even when the App CR carries a (rejected-at-create-time, so normally impossible) non-empty list.
- [ ] Decision on the root-level field (dropped vs. deprecated alias) is explicit and recorded, not silently one or the other.

## Out of scope

- Any change to the write path (`rest.go`'s decode functions), GraphQL, MCP, the dashboard, or the operator's Traefik middleware — all already correct and unaffected.
