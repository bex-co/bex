## Objective

A deploy that fails its build before any reconcile pass observes it mid-build gets `started_at` stamped on the `queued → build_failed` transition, so start and finish land on the same instant and the build reports a zero duration. Make a failed build's recorded duration match the time it actually ran.

## Context

- `lego/backend/internal/store/deploy_lifecycle.go:61-63` — `DeployStatusStartsExecution` excludes only `queued`, `canceled` and `deactivated`, so `build_failed` counts as "executing" and `TransitionDeploy` stamps `started_at = clock_timestamp()` on that transition.
- Measured live: a build that ran **68 seconds** (`createdAt 19:56:07.854793Z`) recorded `startedAt 19:57:15.720548Z` / `finishedAt 19:57:15.720549Z` — one microsecond.
- **Control, from the same responses:** every `live`/`deactivated` deploy has a distinct `startedAt`, on two unrelated services; `canceled` (excluded by the predicate) has **no** `startedAt` at all. The predicate explains both, so the mechanism is confirmed rather than merely correlated.
- **The real duration already exists.** `Observation.RunSeconds` (`build/build.go:431`, computed `:559`/`:564`) is the Job's own run duration. Its only consumer is a Prometheus histogram (`app_controller.go:819,843` → `build_metrics.go:157-164`). It never reaches the App status or the deploy row.
- `CanTransitionDeploy`'s doc (`deploy_lifecycle.go:70-74`) explains that forward phase skips are expected, "because the backend samples Kubernetes state rather than receiving every operator edge" — so the skip is by design and the stamp must cope with it.

## Steps

1. Choose the approach and record why: either exclude terminal-failure statuses from the "executing" set, or project `RunSeconds` onto the App status so the deploy row can derive a true start.
2. **Re-read `reconciler.go:790-802` first.** `buildStartedAt` (`:803`) reads `open.StartedAt`, so this also moves the `build_started` event and its webhook payload — `w6/035` deliberately tuned that timing and its reasoning must not be undone by accident.
3. Make `progress.go:101`'s `==> Building from` banner sort before the build's own output rather than after it.
4. Decide what a failed build with no known start records — a null `startedAt` (like `canceled`) is honest; a fabricated one is not.

## Acceptance criteria

- [ ] A failed build's `startedAt` precedes its `finishedAt` by roughly its real runtime, or is honestly absent.
- [ ] The Events tab stops rendering `0s` for it.
- [ ] `==> Building from` sorts before the failing phase's output.
- [ ] `live`, `deactivated` and `canceled` deploys are unchanged — regression-tested, since they are correct today.
- [ ] The `build_started` event's timing still satisfies `w6/035`.
