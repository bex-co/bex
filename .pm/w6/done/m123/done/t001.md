## Objective

The tenant-facing build failure reason is the curated class sentence concatenated with Kubernetes' own Job condition text, so a failed build reports bex's internal namespace, Job/pod naming, a bare exit code, and its own PodFailurePolicy rule index. Replace the appended half with the failing container's captured output tail — a capture the build already creates and nothing reads.

## Context

- `lego/operator/internal/controller/app_controller.go:849`:

  ```go
  return halt(r.fail(ctx, app, view.reason, fmt.Errorf("%s: %s", view.message, obs.Message)))
  ```

- `view.message` comes from `buildFaultViews` (`build_failure.go:36-51`) and is the half worth keeping. `obs.Message` is `execution.JobFailureMessage(...)` (`build/build.go:563`) — Kubernetes' text.
- **The capture already exists and is unused.** `captureFailureTail` (`build/build.go:1249-1259`) sets `TerminationMessagePolicy = FallbackToLogsOnError` on every build init- and app-container precisely "so a failing container's output is retrievable from the pod status". `grep -rn "TerminationMessage\|Terminated.Message\|LastTerminationState" lego/operator lego/backend --include='*.go' | grep -v _test` finds only setters plus the unrelated CrashLoopBackOff reader.
- **Model the tone on the runtime path**, `app_controller.go:3635-3645`, which already does this well: names the symptom, tells the tenant where to look, and adds the one hint that usually explains it. No internals.
- Note `faultFromJob`'s doc (`build/build.go:464-468`): reading the Job's *reason* needs no pod listing. Reading the *tail* does require touching the pod — weigh that cost and say what happens when the pod is already reaped.

## Steps

1. Read the failing container's termination message from the build pod's status; identify which phase failed (clone / buildkit / push) so the message can name it.
2. Compose: curated class sentence + the failing phase + a bounded tail of its output. Cap the tail's length and strip anything that would re-leak internal identifiers.
3. Decide the fallback when no tail is available — a reaped pod, a timeout with no failing container, the kpack path, `unclassifiedBuildFailure` (`build_failure.go:57-62`).
4. Keep the internal Job/pod name flowing to **operator** logs; it is useful there. Only the tenant-facing string changes.
5. Grep every caller of `r.fail` before changing the composition — a non-build caller may depend on the current shape.

## Acceptance criteria

- [ ] A missing-Dockerfile build's `failureReason` names the missing Dockerfile.
- [ ] It contains none of `PodFailurePolicy`, `bex-build/`, `bld-tea-`, `FailJob rule`, or a bare `exit code 90`.
- [ ] Each fault class (`FaultTenant`/`FaultInfra`/`FaultTimeout`/unclassified) has a defined message with and without a tail.
- [ ] `w7/m82/t003`'s class distinction still holds — tenant vs infra still differ.
- [ ] Operator logs still carry the internal Job identity.

## Out of scope

- Getting buildkit's output into the *log stream* — that is `t003`. This task uses the pod-status tail, which is a different channel and works even when the log is empty.
