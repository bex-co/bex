## Objective

Pin the three behaviours this milestone shipped, and — just as importantly — pin the cases that are correct today and would be easy to break.

## Context

- The regression risk is concentrated in `DeployStatusStartsExecution`: `live`, `deactivated` and `canceled` all behave correctly today *because* of the current predicate, so they need tests as much as `build_failed` does.
- `buildStartedAt` (`reconciler.go:803`) feeds the `build_started` event and its webhook payload; `w6/035` tuned that timing deliberately.
- Assert real failure modes, not string equality against a fixture: a test that pins the exact new sentence will fail on every copy edit and teaches nothing.

## Steps

1. Assert a tenant-fault build failure's message names the failing phase and contains none of the internal markers (`PodFailurePolicy`, `bex-build/`, `bld-tea-`, `FailJob rule`).
2. Assert each fault class with and without an available tail.
3. Assert a `queued → build_failed` skip records a duration matching the Job's run time, or an honestly absent start.
4. Assert `live`/`deactivated`/`canceled` timestamp behaviour is unchanged.
5. Assert the `build_started` event timing still satisfies `w6/035`.

## Files

- `lego/operator/internal/controller/*_test.go`, `lego/operator/internal/build/build_test.go`
- `lego/backend/internal/store/*_test.go`, `lego/backend/internal/logs/*_test.go`

## Acceptance criteria

- [ ] `cd lego/operator && make test` and `cd lego/backend && go test ./...` pass.
- [ ] A test fails if the raw Job message is reintroduced into the tenant-facing string.
- [ ] A test fails if a successful deploy's timestamps change.
- [ ] No test asserts an exact user-facing sentence as its only claim.

## Out of scope

- Live production verification; that is the DoD.
