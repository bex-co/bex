## Objective

`lego/backend/internal/apps/graphql.go:299` reads `AppView.Name` raw while REST and MCP serialize `renderServiceName(a)`. Route GraphQL through the same helper so a renamed service reports the same `name` on all four read surfaces.

## Context

- The divergence, captured live 2026-08-27 (full probe in `../README.md`): `srv-d9ndt8hmcglc739fkp50` reads `name:"eden-dash-v3"` on REST and `name:"block-eden-mono"` on GraphQL, same instant, same session.
- `mcp.go:36-39` claims "the three surfaces cannot drift" because every tool delegates to the same `Service` method. True of the method, false of the serializer — REST/MCP share `renderService`, GraphQL builds its own field map.
- The dashboard will not notice: `dashboard/src/features/services/lib/status.ts:35-39` computes `displayName ?? immutableName` itself, and `immutableName` has exactly two references, both in that file. Confirm this before shipping — it is the reason the bug was invisible through the browser for as long as it was.

## Steps

1. Change `graphql.go:299` to resolve through the same helper REST uses, so there is one implementation rather than a second copy of the fallback.
2. Confirm the change reaches every alias of the type, not just the one that was probed: `server(id:)` and `service(id:)` (both bound to `s.Get`, `graphql.go:974-975`), `services(ownerId:)` (`:960`), and `SyncBlueprintResult.services` (`:932`). They share `serviceGQLType`, so one edit should cover all four — verify by reading, and note anything that builds a Service payload outside that type.
3. Re-run the live probe from `../README.md` against a renamed service and confirm REST and GraphQL now return the same `name`.
4. Check whether any mutation return payload also selects `name` (e.g. `createService`, `suspendService`) and would now echo the label — expected and correct, but confirm nothing keys off it.
