## Objective

`GET /v1/services/eden-dash-v3` returns `404 app not found` for the value REST itself returns as that service's `name`. After t002, GraphQL inherits the same hole. Close it in whichever direction t001 chose, and place the neighbouring error classes while doing so.

## Context

- Live, 2026-08-27 (`../README.md`, Probe 2): `GET /v1/services/eden-dash-v3` → 404; `GET /v1/services/block-eden-mono` → 200 returning `name: eden-dash-v3`. GraphQL `server(id:)` behaves identically for both strings.
- Cause: `core.Base.GetApp` (`core/base.go:1453-1495`) resolves `LabelAppID` (the `srv-…` id), then `LabelServiceName` (the immutable name). `displayName` is not a resolution key anywhere in `core`.
- The codebase already handles the dual-name case **in one place**: `apps/rest.go:663`'s `?name=` list filter accepts `a.Name` **or** `renderServiceName(a)`. The by-id path never got the same treatment. Whatever this task does must not narrow that filter.
- Render resolves services by `srv-…` id only — so "no name resolves" is a defensible, parity-correct answer, provided t003 has given the immutable name a home so a caller can still construct one where bex's extension supports it.

## Steps

1. Implement t001's decision. If by-name reads stay: add the display label as a resolution key and handle the consequences in step 2. If they become id-only: keep `LabelServiceName` working for legacy CRs (`w1/m46`) and document the boundary.
2. If the display label becomes a resolution key, settle **ambiguity**: nothing constrains two services in one workspace to distinct display names, unlike `LabelServiceName`. Define and test the answer for a duplicate — 409, deterministic first-match, or refusal. Do not leave it to map iteration order; `core/base.go:1642` already had to make a similar loop deterministic.
3. Place the adjacent classes explicitly. A caller who lacks access to a service must get the same answer as a caller naming a service that does not exist — do not let a new resolution key turn the 404 into an existence oracle. `core/audit.go:539` describes the existing per-candidate authorize-and-skip loop; follow it.
4. Confirm `?name=` list filtering still matches both spellings after the change.
5. Re-run Probe 2 from `../README.md` and paste the result.

## Acceptance criteria

- [ ] Every `name` a read surface returns either resolves on a by-name read, or no name does and that is documented in ADR006 with the id-only rule stated.
- [ ] A duplicate display name has a defined, tested outcome — not iteration order.
- [ ] A forbidden service and a nonexistent one are indistinguishable to the caller, with a test asserting it.
- [ ] `GET /v1/services?name=<display label>` and `?name=<immutable name>` both still match.
- [ ] Probe 2 re-run and pasted into the task's completion evidence.

## Out of scope

- Changing how `srv-…` ids are minted or resolved.
- Making display names unique — that is a product decision, not this fix; step 2 handles duplicates as they are.
