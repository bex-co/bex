# A disk-bearing web image service that names no port is down 25 s longer on each image deploy, while bex rediscovers its HTTP port

Why: under `Recreate` no earlier release serves while the new one starts, so the operator's wait before it looks for the image's HTTP port is pure downtime. Render detects the port of a service that binds one other than `PORT` as the instance starts.

- **Found by:** w6/m547 t005, production, 2026-11-21, runs A1 and A2 (code deploys `v1.10.2` and `v1.10.3` of `docker.io/traefik/whoami` with no `PORT` and no configured port, fixture `srv-dc0nm80n82tc73dukib0` in `bex-canary`, deleted since). The windows were 44.0 s and 37.0 s. With `PORT=80` set, the same deploys took 7.25–9.0 s.
- **Sequence (A2):** the new instance passed its startup probe at 11:14:51 and was Ready at 11:14:52. The operator logged `Detected HTTP on port 80; serving it` at 11:15:12 and rewrote both port-bearing Services at 11:15:17. Their EndpointSlices and Traefik picked up the instance the same second, 25 s after Ready. Until then the edge answered 503 with no backend.
- **Where:** `imageNetwork.image` is the release's digest. `retainableWebHTTPSelection` (`lego/operator/internal/controller/web_image_http.go:116`) keeps an earlier HTTP choice only for the same digest, so every new tag is rediscovered. `selectWebImageHTTP` (`:129`) waits `portDetectGrace` (20 s from container start, `port_detect.go:75`) before it probes. `webImageReleaseHeld` (`:72`) keeps the Services pinned to the serving release until then, and under `Recreate` that release has no pods left.
- **Also measured:** such a service's pod runs the `bex-health-probe-install` init container (`health_probe.go:47`) for its exec startup probe. It added about 3.3 s per start (2.1 s from `Created` to `Started`), which a service with a named port does not pay.
- **Done when:** on production, an image deploy of a disk-bearing web image service that names no port, whose server listens within 2 s, reaches the edge within 1 s of its instance turning Ready, measured as in m547 t005. Rolling (diskless) services keep today's hold, so no candidate takes traffic before its port is known.

- **Premise held** on `9454368e6b`. `selectWebImageHTTP` waited `portDetectGrace` (20 s from the container's start) before it probed any pending candidate, `Recreate` included. `reportWebHTTPSelection` then requeued 5 s after the pass that chose the port, and the Services moved on the pass after that. - **`30fa205aa7`:** a `Recreate` candidate is probed as soon as it is Ready (`detectsAtReady`, `web_image_http.go`). Its open-port probe passing means it listens, and the lowest port answering HTTP then wins. The pass after any port choice runs 100 ms later (`webHTTPChosenRequeue`), not 5 s. A rolling release keeps the grace, and its hold is unchanged.

A start command with Rails on 5000 and a client on 10000 was served on whichever bound first, and Render's answer was to delay the second listener ([community.render.com/t/19379](https://community.render.com/t/render-disobeying-port-or-other-issue/19379), read 2026-11-21).
