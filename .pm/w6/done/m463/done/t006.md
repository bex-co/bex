## Result — 2026-11-18

Read on production (pin `359aee37d`, producer `14eaa71b98e5`) as the QA user, against t005's free probe `red-dbuhar5e7qgs73b3481g` in `bex-canary` after internal authentication was enabled on it.

- **The limit matches Render's.** Render sells free with 50 connections, `256mb` 250 and so on up to `50g` 50,000. Its compute-plans page says nothing about internal authentication changing the limit ([compute plans](https://render.com/docs/compute-plans#render-key-value-plans), read 2026-11-18). On production, the probe with internal authentication admitted exactly 50 authenticated clients on its internal URL (t005). Before this milestone its tenants met only Valkey's `--maxclients` 60.
- **The refusal matches Render's.** Render's Key Value is Valkey, so the client past the limit reads Valkey's own `-ERR max number of clients reached`. The probe's 51st client read those bytes, with or without `AUTH` (t005).
- **What enabling breaks matches Render's.** Render: "Any existing connections that use your unauthenticated URL will break!", then "Render restarts your Key Value instance (it will be unavailable for a few seconds)", and the internal URL then carries a username and password ([Key Value](https://render.com/docs/key-value), read 2026-11-18). On production the held unauthenticated client was closed 4 s after the enable. New unauthenticated clients read `-NOAUTH` from then on, and the store read `config_restart` before `available`. bex rolls the proxy instead of restarting Valkey, so the keyspace survives even with no persistence. ADR021 § 2 already records that, and it contradicts nothing Render tells the customer.
- **Every surface agrees and states nothing contrary:**
  - REST `POST /v1/key-value/{id}/internal-auth` answered 202 with `internalAuth: true` and `status: config_restart`, and `GET /v1/key-value/{id}` answered `internalAuth: true`.
  - GraphQL `keyValue { internalAuth }` read `true`, and a repeated `enableKeyValueInternalAuth` answered `internalAuth: true`, `available`.
  - MCP `get_key_value` read `internalAuth: true`, and `enable_keyvalue_internal_auth` was idempotent. Its description ("open unauthenticated internal connections drop, the internal connection string then carries the password, and linked services pick it up on their next deploy") is accurate. No MCP tool description states a connection limit (searched for `connection limit`, `max connections`, `maxclients`, `1024`).
  - The deployed dashboard bundle (`index-CQQ2i9KQ.js`, served since 01:16Z) carries the confirmation "Every internal connection will need the password. Existing connections that use the unauthenticated URL will break, … This can't be undone." It also carries the enabled state, "Internal connections require the password." Neither mentions a limit change, and none happens.
- **No drift to fix or file** on these surfaces. While checking t005, a separate divergence turned up: every operator deploy rolls every store's proxy and closes its clients. It is filed as [w6/140](../../140.md).
