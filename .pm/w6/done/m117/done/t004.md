## Objective

Confirm the new `RecoveryInfoView` shape is consistent across REST, GraphQL, MCP and the dashboard, and record the unknown state as a deliberate bex extension.

## Context

- Render's Recovery tab shows a backup list and a PITR window; bex's `earliest`/`latest`/list mirrors it. An explicit "could not read" state has no Render counterpart, so it is an extension and belongs in the parity ledger rather than arriving unannounced.
- All three API surfaces project the same view type, so a field addition must appear on all three or the surfaces drift — the failure mode `w6/m115` was filed for on a different field.

## Steps

1. Read `recovery-info` for one database through REST, GraphQL and MCP; confirm identical fields and identical meaning for each state (healthy-with-backups, healthy-empty, unreadable, disabled).
2. Add the unknown-state row to `docs/ADR018-render-parity.md` as a deliberate extension.
3. Check `docs/ADR009-postgresql-management.md` describes what the recovery surface now reports.

## Files

- `docs/ADR018-render-parity.md`, `docs/ADR009-postgresql-management.md`
- verification only otherwise

## Progress (corrected 2026-09-01)

Steps 1–3 are done. REST, GraphQL and MCP all project the single `RecoveryInfoView` off the same `Service.RecoveryInfo` (`gqlutil.IDVerb(databaseRecoveryInfoGQLType, s.RecoveryInfo)`; MCP returns the view verbatim), so the four states cannot drift per surface. The honest-unknown extension is recorded in `docs/ADR018-render-parity.md`, and `docs/ADR009-postgresql-management.md` now identifies the Barman ObjectStore entry — not native CNPG Cluster status — as the source of both bounds.
