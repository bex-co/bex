## Objective

Make `RecoveryInfo` able to say "I could not read this". A failed recovery-source read and a genuinely empty result previously produced byte-identical responses, which is why a database with proven daily backups reported none.

## Context

Three fields, three sources, and only the one that cannot fail survives (`lego/backend/internal/postgres/recovery.go`):

- `:128` `if err := s.Client.Get(…, cluster); err == nil { … }` — a failed Get is discarded, so `EarliestRecoveryTime` is never set.
- `:145-147` `if err := s.Client.List(…); err != nil { return []BackupView{} }` — a failed List is indistinguishable from an empty one.
- `:133` `info.LatestRecoveryTime = s.Now().UTC()…` — pure clock, always succeeds.

`enabled:true` comes from `d.Status.BackupsEnabled` on the Database CR, which also needs no CNPG access — so the whole response can be produced with every CNPG read failing, which is exactly the shape observed in production.

`listBackups`' doc comment blesses the swallow as "best-effort … an unavailable CNPG CRD (e.g. envtest) yields an empty list". That is a test convenience that became the production failure mode; keep envtest working by making the state explicit, not by hiding it.

## Steps

1. Add an explicit unknown/error state to the recovery response contract. It must be representable on REST, GraphQL and MCP.
2. Return it when the authoritative ObjectStore `Get` fails and when the Backup `List` fails, distinguishing "read failed" from "read succeeded, nothing there".
3. Withhold `LatestRecoveryTime` when the evidence for the window could not be read. It currently asserts a restore point in exactly the case where nothing else could be established.
4. Keep the `enabled:false` path byte-identical — a plan without backups is a different, already-correct state.
5. Preserve the authz ordering: `fetchDatabase` must still refuse before any CNPG read, so the new state can never reveal whether a database exists to a caller who cannot see it.

## Files

## Acceptance criteria

- [x] A failed ObjectStore Get and a failed Backup List each produce a response distinguishable from the empty-but-healthy one.

- [x] Authz still precedes every recovery-source read.

## Completion correction (2026-09-01)

Production inspection showed that the original implementation chose the wrong successful-read source: plugin-backed clusters do not populate the native CNPG Cluster recovery fields. `RecoveryInfo` now reads the Barman `ObjectStore.status.serverRecoveryWindow` entry keyed by the Database's exact `status.backupServerName`, returns both authoritative bounds only as a pair, and propagates ObjectStore Get and Backup List failures. A missing shared ObjectStore is also an explicit source error—not “no window”—because every tenant namespace must contain that projected object; only a readable ObjectStore with an absent/incomplete server entry represents an unestablished window. The no-backup-plan and Database-authz ordering remain unchanged.
