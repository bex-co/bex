## Objective

Run real proxies on the local CAPD cluster through operator upgrades. An operator rebuilt with an unrelated change rolls no proxy, and a client held through the proxy keeps its connection. A proxy code change still rolls it, and so does enabling internal authentication, which still closes the unauthenticated client.

## Context

- `bash scripts/mock-cluster.sh operator` builds and imports `bex-operator:dev`. One fixed tag never changes the template's `image` string, which hides both the roll and the hold. Tag each build distinctly (for example `bex-operator:dev-<n>`), as production's digests are, and say how in the task record.
- Use a free probe store in dev-6's tenant namespace, as w6/139 and w6/m463 t003 did.
- A held client is one connection: `CLIENT ID` before and after proves it is the same. `valkey-cli` reconnects by itself, so a `PONG` alone proves nothing.

## Steps

1. Deploy build A. Create the probe store and wait for its proxy. Open one client through `<id>:6379` and note its `CLIENT ID`.
2. Deploy build B, which changes only something outside the proxy (a log line in the manager). Check that the proxy Deployment's ReplicaSets, pod name and image are unchanged, the annotation records the hash, and the held client answers `PING` with the same `CLIENT ID`.
3. Deploy build C, which changes the proxy binary (a throwaway local change, never committed). Check that the proxy rolls once onto C.
4. Enable internal authentication on the store. Check that the proxy rolls on the held image and the held unauthenticated client is closed (w6/m463).
5. Delete the probe store and every probe object.

## Files

- none committed beyond the task record (the build C change is discarded)

## Acceptance criteria

- [x] Build B: no new ReplicaSet, same pod, same `CLIENT ID`, `PING` answered
- [x] Build C: the proxy rolls once
- [x] Internal auth: the proxy rolls and the unauthenticated client is closed; no Valkey pod restarts
- [x] The probes are deleted

## Out of scope

- The adoption path through a registry: t002's unit tests cover it, and t005 sees it on production

Builds were tagged distinctly with `BEX_OPERATOR_IMG=bex-operator:m469-<x> bash scripts/mock-cluster.sh operator`. The held client was a restricted `valkey/valkey:8.1` pod that opens one bash `/dev/tcp` connection to `red-m469probe:6379` and sends `CLIENT ID` + `PING` on it every 2 s.

- **Build A** (this tree, before `/simplify`'s registry move, which this path does not exercise): the proxy ran `m469-a` with the record `a15db4ab…` (the arm64 binary), ReplicaSet `-56f6d95b99`, pod `-ssp4w`. The client read `id=:17 +PONG`.
- **Build B** (a throwaway manager-only log line): the manager ran `m469-b`, and its log showed the line and a `keyvalue reconciled` pass for the probe. The proxy kept `m469-a`, generation 1, ReplicaSet `-56f6d95b99`, pod `-ssp4w` started at 05:15:16Z. The client kept reading `id=:17 +PONG` with no gap.
- **Build C** (a throwaway log line in `cmd/kv-internal-proxy`): the proxy rolled once onto `m469-c` (ReplicaSet `-5789448f` at 05:20:55Z, generation 2, record `11196197…`), and the held client's connection closed as the old pod left. - **Build D** (the tree again, so the binary is back to `a15db4ab…`) rolled the proxy onto `m469-d`, as a changed binary should. **Build E** (identical to D, another tag): the manager ran `m469-e`, the proxy kept `m469-d`, and a new held client kept `id=:215` with no gap.

- The probe store and the client pod were deleted, and no `m469` object is left in the namespace. The shared cluster's operator was left on `bex-operator:m469-e`, this milestone's code, until the next `mock-cluster.sh operator`.
