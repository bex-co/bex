## Objective

The deploy that ships this milestone finds every production proxy Deployment without t001's annotation. Instead of rolling them all once, the operator reads `/kv-internal-proxy` out of the Deployment's current image from its registry. When it is byte-identical to the manager's, the operator keeps the image and records the hash. Any doubt rolls the proxy as today.

## Context

- Production's proxies run `ghcr.io/bex-co/bex-operator@sha256:b4104643…`, whose `/kv-internal-proxy` hashes to `d1a7d7d0e8ecc328…` (README § Findings). A build that leaves the proxy code alone produces the same bytes.
- The path, checked by hand at promotion: GHCR anonymous token (`https://ghcr.io/token?scope=repository:bex-co/bex-operator:pull`, or the generic `401` `WWW-Authenticate: Bearer` challenge). Then the image index (OCI, with provenance) → the `linux/<GOARCH>` manifest → its config. Then the non-empty `history` entry whose `created_by` is `COPY /workspace/kv-internal-proxy /kv-internal-proxy # buildkit`, which is layer 19 on all six images sampled. That layer is a 4.2 MB gzip tar with one entry, `kv-internal-proxy`.
- `internal/imagecheck` already speaks the Distribution API (`parseRef`, `resolveDigest`, `fetchBlob`) over `internal/httpclient`. Reuse its parsing and bounded client, not its signature logic.
- Production runs `linux/amd64` only (`deploy.yml` `platforms: linux/amd64`). Local images (`bex-operator:dev`) are not in any registry.

## Steps

1. Add a small resolver: given a digest-pinned image reference, return the sha256 of its `/kv-internal-proxy`, or an error. Bound it: a timeout, a size cap on the manifest, config and layer, and digest references only. Cache results in memory per image digest.
2. In t001's hold, when the Deployment has no recorded hash, ask the resolver about its current image. Keep the image and record the hash only on an exact match. On an error or a mismatch, set `InternalProxyImage` and record the manager's hash (today's roll).
3. Make sure no registry call blocks a reconcile for long: a failure falls through to the roll, and a successful match is never asked twice.
4. Check that the manager can reach `ghcr.io` (no egress NetworkPolicy selects it at promotion), and say so in the task record.

## Result — 2026-11-18

- `registry.ImageFileSHA256` (`internal/registry/image_file.go`) builds on the existing digest-verified `readImageConfigDocument` that `ReadImageConfig` uses. Of `imagecheck` it reuses only the idea: `imagecheck` has no index or platform handling, and `registry` already has Bearer realm validation (R25-03), the blob-redirect policy and error classification. The `/simplify` pass moved it there from a first draft in `imagecheck`.
  - It reads the `linux/<GOARCH>` manifest and config, then the layer of the history entry `COPY /workspace/kv-internal-proxy /kv-internal-proxy # buildkit`.
  - Limits: digest references only, a layer of at most 64 MiB declared before the download, 30 s for it, a file of at most 128 MiB, and the layer checked against its digest.
- `controller.InternalProxyBinaryFromRegistry` caches results per digest. It refuses a tag or local image before any request (`TestInternalProxyBinaryFromRegistryNeedsADigest`).
- `carriesInternalProxyBinary` asks the registry only when the Deployment has no record. It keeps the image and records the hash only on an exact match. An error or a mismatch rolls the proxy. A recorded match is never asked again (the envtest counts the calls).
- Unit tests (`image_file_test.go`, an `httptest` registry behind a Bearer challenge, serving an index with this architecture, a decoy architecture carrying another binary and an attestation) cover the match and seven refusals: a tag, no build step, the step twice, history and layers disagreeing, an oversized layer, a 503, and a substituted layer.
- envtest: a Deployment written without the hash, whose image resolves to the manager's hash, keeps its template. Recording the hash bumps the Deployment's generation, because the API server copies a Deployment's annotations to its ReplicaSet, but creates no new ReplicaSet.
- **Against production's registry:** `ImageFileSHA256` on `ghcr.io/bex-co/bex-operator@sha256:b4104643…` (the running proxies' image), run as linux/amd64, returned `d1a7d7d0e8ecc328…` in 1.8 s, the hash in README § Findings. **The binary this milestone ships is the same:** `go build ./cmd/kv-internal-proxy` for linux/amd64 from this tree in the Dockerfile's pinned `golang:1.26.11` builder, at `/workspace/operator`, hashes to `d1a7d7d0e8ecc328…`. So the shipping deploy should adopt every proxy and roll none.
- **Egress:** no NetworkPolicy or CiliumNetworkPolicy in `deploy/gitops` or `lego/operator/config` selects the manager for egress (`network-policies.yaml` restricts only ingress in `bex-system`), so the manager reaches `ghcr.io` as it reaches other registries. t005 confirms it on production: an adopted proxy records the hash, while a failed lookup logs "rolling the Key Value proxy onto the operator's image" and rolls.
