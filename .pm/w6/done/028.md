# 028 — Metrics page: "1 requests" + 10 unbatched Metrics queries per load (sub-hour)

Why: the Total Requests card says "1 requests" to every user whose service served exactly one request in the window — the same pluralization class `w9/m92` t006 fixed for "N turns" — and the same page fires ten separate `Metrics` GraphQL operations per load, which is the kind of self-inflicted request fan-out `w9/m92` t008 trimmed for the sessions poll.

From the live `/qa-find-bugs` hunt of `dashboard.bex.co`, 2026-08-22.

- **"1 requests"** — `/services/<id>/metrics`, Network Metrics → Total Requests summary. Reproduced on `srv-d9ndt8hmcglc739fkp50` with a 12-hour window. Needs the same singular/plural handling the rest of the dashboard uses (i18n plural forms, not a hand-rolled `+ "s"`). Owner file: `dashboard/src/features/metrics/components/network-metrics-card.tsx`.
- **10 `Metrics` operations per page load** — `application-metrics-card.tsx:61-76` issues seven (`cpu`, `memory`, `cpu_limit`, `memory_limit`, `cpu_target`, `memory_target`, `instance_count`) and `network-metrics-card.tsx:121-131` three more (`http_requests`, `http_latency`, `bandwidth`), each its own HTTP POST — Apollo is wired with a plain `HttpLink` (`dashboard/src/common/apollo/factory.client.ts:20`), no batching. Measured: 20 GraphQL requests for one Metrics page load, and each `useMetrics` re-polls every 30s (`use-metrics.ts:106`). GraphQL aliases or a batch link would collapse these into one round trip. Not a bug on its own — steady-state polling stays well under the 500/min `BEX_RATE_LIMIT` — so this is efficiency, not correctness.

Not filed as bugs from the same hunt (recorded so a later pass doesn't re-litigate them): the 429s seen mid-hunt were self-inflicted by the sweep's own navigation rate, not reachable by a real user's pace; `/services/<id>/headers` and `/redirects` redirecting to `/settings` is correct for a web service (those tabs are static-site surfaces); the `/notifications` switches all have proper accessible names via `label[for]` (an initial heuristic flagged them, the accessibility tree cleared them); and `api.bex.co` answering `403` to a `Python-urllib/*` User-Agent is Cloudflare bot protection — curl with a normal UA gets a proper `401`.

## Closed 2026-08-27 — correctness half live-verified; efficiency half unchanged and out of scope by this note's own text (33rd `/qa-find-bugs` run)

**Bullet 1 — "1 requests" — fixed, and verified on all three branches.** `d247d210` describes it as *"singular key pair plus a call-site ternary, following the agentSessions.metaTurn precedent"*, which is exactly what the note asked for. Live on production:

| branch | how it was produced | rendered |
| --- | --- | --- |
| exactly 1 | one `curl` to `qa-20260826-webhook-svc.onbex.co` at `07:52:24Z`, then `/metrics?range=30m` | **`1 request`** |
| many | `beancount-forum` (`srv-d9nqg9dcavls73fp8m2g`), `/metrics?range=12h` | **`162 requests`** |
| zero | `eden-dash-v3` (`srv-d9ndt8hmcglc739fkp50`), `/metrics?range=12h` | summary line **omitted** |

The singular branch is the one the note filed; the plural branch is the control, checked so "it renders 1 request" could not be a fix that broke the common case. The zero branch is deliberate, not a third bug — `network-metrics-card.tsx:269-278` gates the whole summary on `requestCount > 0` before choosing between the keys:

```tsx
{requestCount > 0 && (
  <span …>
    {t(requestCount === 1 ? "metrics.requestCount" : "metrics.requestsCount",
       { count: requestCount.toLocaleString() })}
  </span>
)}
```

with `metrics.requestCount` = `"{count} request"` and `metrics.requestsCount` = `"{count} requests"` (`metrics/locales/en.ts:161-170`). Real i18n keys, not a hand-rolled `+ "s"` — the thing the note specifically asked for.

**Bullet 2 — the 10 unbatched `Metrics` operations — unchanged, and deliberately so.** Re-measured this run: **17 GraphQL POSTs** for a single Metrics page load (the note recorded ~20; the exact count moves with what else the route fetches). Apollo is still on a plain `HttpLink` with no batch link. `d247d210` never claimed to touch it, and **this note's own text already classifies it**: *"Not a bug on its own — steady-state polling stays well under the 500/min `BEX_RATE_LIMIT` — so this is efficiency, not correctness."*

No successor item is filed for it, because filing one would contradict the note's own judgment that it is not a defect. Anyone who later wants the round trips collapsed has the measurement and the two call sites (`application-metrics-card.tsx:61-76`, `network-metrics-card.tsx:121-131`) recorded here to start from.
