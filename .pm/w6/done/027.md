# Health-check section gate open-codes `servesHttp` — convert, but decide the loading case

Surfaced by `w6/m43`'s `/simplify` pass (2026-08-21) and deliberately left out
of that milestone.

`routes/services.$serviceId.settings.tsx` spells the same predicate twice by
exclusion:

- `:86` — `if (!cron && !worker && !staticSite) navigationSections.push("health-checks");`
- `:327` — `{!cron && !worker && !staticSite && (` … the Health Checks section itself

Its own comment at `:324-326` says what it means in words: "web_service /
private_service only — never cron/worker/static (no HTTP readiness)". That is
exactly `servesHttp(type)`, which `w6/m43` added to
`features/services/lib/service-type.ts` beside `isCron`/`isWorker`/etc. The
backend agrees — `lego/backend/internal/apps/service.go` rejects
`SetHealthCheckPath` for cron/worker.

**Why it wasn't done in m43:** it is not a behavior-preserving swap. `cron`,
`worker`, and `staticSite` are each `service ? isX(service) : false`
(`:63-65`), so while the service is still loading all three are `false` and the
health-check section **renders**. `servesHttp(service.type)` on an absent
service would be `false` and **hide** it. The two also disagree for an unknown
or legacy wire type: the current expression shows health checks, `servesHttp`
hides them.

So this needs a decision, not just a substitution: should the section render
optimistically while loading (today's behavior, preserved by
`service ? servesHttp(service.type) : true`) or stay hidden until the type is
known? Pick one, convert both sites, and cover the loading case with a test.
Sub-hour once decided.

## Closed 2026-08-27 — converted, decided, and live-verified (34th `/qa-find-bugs` run)

`d247d210` describes it as *"the health-check section gate open-coded servesHttp by exclusion. Converted both sites, keeping today's render-while-loading behavior explicitly rather than by accident."* That is exactly what this note asked for: a decision, not a substitution.

**The conversion, at HEAD.** One predicate now, consumed by both former sites:

```
routes/services.$serviceId.settings.tsx:78    const healthChecks = service ? servesHttp(service.type) : true;
routes/services.$serviceId.settings.tsx:101   if (healthChecks) navigationSections.push("health-checks");
routes/services.$serviceId.settings.tsx:346   {healthChecks && ( … the Health Checks section … )}

features/services/lib/service-type.ts:110-112 servesHttp(type) => type === "web_service" || type === "private_service"
```

The `: true` is the decision the note demanded, written down rather than inherited by accident.

**Live verification of both type branches.**

| branch | service | result |
| --- | --- | --- |
| serves HTTP | `qa-20260826-webhook-svc` (`web_service`) | `#health-checks` **present** |
| does not | `qa-20260827-cron` (`cron_job`, created and deleted for this check) | `#health-checks` **absent**; rendered sections were exactly `general · deploy · build · notifications · deploy-hook · suspend · danger-zone`, and no "Health Check" string appeared anywhere on the page |

`worker` and `static_site` follow from the same single boolean over the type string — read at `service-type.ts:110-112`, **not separately probed live**. One predicate, one mechanism; recorded as read rather than claimed as observed.

**The loading branch is unreachable on this route — worth recording so nobody hunts a flash that cannot happen.** The note worried about what renders "while the service is still loading". Sampled it two ways on the cron (the only type where the two branches differ visibly):

- client-side nav from `/deploys` → `/settings`, 14 samples at ~120 ms: `#health-checks` false in every one, including frames before `#general` existed;
- a cold load in a fresh tab with `waitUntil: 'commit'`, 16 samples at ~90 ms: `#general` was already present in the first successful sample and `#health-checks` never appeared.

In both cases `service` is defined at first paint — from the Apollo cache on the client nav, and from SSR on the cold load — so the `: true` arm never evaluates in production on this route. It is correct defensive code, and the "does it flash?" question the note raised is **not observable here**. Stated as a limit of the verification rather than as "no flash occurs".

**One behavior change the note predicted, and it is the right direction:** an unknown or legacy wire type now **hides** health checks where the old exclusion expression showed them. `servesHttp` is an allowlist (`web_service || private_service`), so a type bex does not recognise no longer gets a section whose backend refuses it — `lego/backend/internal/apps/service.go` rejects `SetHealthCheckPath` for cron/worker, which the note already cited as the backend agreeing.
