# 068 — bex spells three disk event types differently from Render, so its own `?type=` filter cannot select two of them

Why: two emitted disk events cannot be selected through the Render-shaped filter at all, and the parity evidence still claims disk events do not exist, so the wire vocabulary needs an explicit compatibility decision.

**Found:** 2026-08-27, while running `w6/m122/t004`'s parity check (the milestone that made the dashboard Events tab fail-open). Not a `m122` defect — `m122` is dashboard-only and its fix is complete — but the parity probe it required surfaced this, and `t004` says a needed API change is a new finding rather than a silent fix.

## What

bex emits four persistent-disk event types (`lego/backend/internal/events/service.go:216-219`, from the `apps.AddDisk` / `apps.UpdateDisk` / `apps.DeleteDisk` / `apps.RestoreDiskSnapshot` audit verbs):

```
disk_attached   disk_updated   disk_detached   disk_restored
```

Render's pinned public OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`, `components.parameters.eventTypeParam`, a 39-value enum captured 2026-07-20) spells the same family:

```
disk_created    disk_updated   disk_deleted
```

So of bex's four, exactly **one** (`disk_updated`) matches Render. `disk_attached` and `disk_detached` are bex spellings of concepts Render already names `disk_created` and `disk_deleted`; `disk_restored` has no Render equivalent at all.

## Why it matters

`renderRequestValidator` (`lego/backend/internal/api/render_openapi.go:357`) validates `?type=` against that enum before the handler runs. Verified by probe in `TestServiceEventSurfaceCarriesDriftedTypes` (`lego/backend/internal/api/events_surface_test.go`):

- `GET /v1/services/{id}/events?type=disk_updated` → **200**, narrows correctly.
- `GET /v1/services/{id}/events?type=disk_attached` → **400**, and there is no spelling a Render-trained client could send that would reach those rows.

The events themselves are returned fine on all three surfaces (REST, GraphQL and MCP all carry `disk_attached` — that half is proven in the same test). It is only selection by type that is unreachable, and only for the two divergent spellings.

This is the same class as `docs/render-artifacts/service-events.md`'s treatment of the family, which is now **stale**: its "Still non-goals" section says `disk_*` is omitted "(no persistent disks)". bex has had them since ADR082, and emits four types.

## The decision this needs

Three options, none obviously right — hence a note, not a milestone:

1. **Rename to Render's spelling** (`disk_attached` → `disk_created`, `disk_detached` → `disk_deleted`). Restores filterability for free and matches the vocabulary's stated house rule ("Render's event types … spelled exactly as its list-events enum spells them"). Costs a wire-visible rename of two already-emitted types, plus the dashboard catalog, `LABEL_KEYS`, icons and both locales moving with it.
2. **Keep bex's spelling** and record the divergence as an ADR018 row, accepting that the two types are unfilterable through the Render-shaped parameter. Cheapest, and consistent with how every other bex-named type (`env_vars_changed`, `custom_domain_added`, `custom_domain_verified`, …) already behaves — all are refused 400 by the same enum.
3. **Widen the validator** for bex-named types on this one parameter. Largest blast radius: it weakens the pinned-contract guarantee that `w6/m96` and the OpenAPI gate exist to protect.

Option 2 is the status quo and is defensible; the reason to look at option 1 is that `disk_attached`/`disk_detached` are not bex-original concepts the way `env_vars_changed` is — Render already named them, and bex chose different words for the same thing.

## Also owed

`docs/render-artifacts/service-events.md`'s "Still non-goals" line listing `disk_*` as omitted for want of persistent disks is factually stale and should be corrected whichever option wins.

## Triage (2026-09-03)

The "Also owed" doc staleness is already fixed — `docs/render-artifacts/service-events.md:110`
now records that `disk_*` is no longer a non-goal and names this note as the open
decision. What remains is exactly the wire-vocabulary decision (options 1–3
above); no code change is safe to make ahead of it, so the note stays open.
Recommendation on record: option 1 (rename to Render's `disk_created`/`disk_deleted`)
— Render already named these concepts, the divergence buys nothing, and the two
types are currently unfilterable through the Render-shaped `?type=` parameter;
the rename cost is bounded (two event types + dashboard catalog/labels/locales).

## Resolution (2026-09-07)

Option 1 ratified — rename to Render's `disk_created`/`disk_deleted` — via `/pm-brainstorm for w8` #2, approved the same day. Promoted to **[`w8/m34`](../../w8/m34/README.md)** (rename + history/subscription compatibility + dashboard catalog + parity-positive filter guard + docs closure). Note moved to `done/068.md`.
