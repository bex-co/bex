# Static site publish failures surface a generic Kubernetes Job error instead of the actual reason

Why: a wrong or missing Publish Directory — likely the single most common first-time-setup mistake on this surface — leaves the user with zero actionable information about what to fix.

**Live-repro:** created a Static Site (`bex-co/frontend-onefx-boilerplate`) with Publish Directory deliberately set to a nonexistent path (`totally-nonexistent-output-dir-xyz`), 2026-08-24 QA workspace (`srv-da6ci36f35us73c4og50`, deploy `dep-da6ci36f35us73c4og5g`). The build itself correctly succeeded (Events: "Build ended Succeeded"), and the deploy correctly failed rather than falsely reporting Live — good — but the only reason shown anywhere (deploy detail page, Events, logs) was:

```
BackoffLimitExceeded: Job has reached the specified backoff limit
```

with no mention of the missing/empty publish directory anywhere.

**Root cause:** `lego/operator/internal/publish/publish.go:216`'s `publish.Ensure` calls `execution.JobFailureMessage(cur, "unknown publish failure")` (`lego/operator/internal/execution/job.go:108-115`), which reads **only** the Kubernetes `Job`'s own `JobFailed` condition `Reason`/`Message` — never the failing pod/container's actual termination reason or log output. The `extract` initContainer's script (`publish.go:356-364`, `extractContainer`) is `set -e; cp -a "$PUBLISH_PATH"/. /out/` — when `PUBLISH_PATH` doesn't exist in the built image, `cp` fails with a specific, useful stderr message (`cp: can't stat '.../.': No such file or directory`) and a non-zero exit, but that detail is discarded. The publish Job carries no `PodFailurePolicy` (unlike the BUILD Job's `buildPodFailurePolicy`, which fails fast on a tenant-classified exit code specifically so the failure can be attributed and explained — see `build.go`'s `faultFromJob`), so it simply retries (`backoff := int32(1)` at `publish.go:266`, whose own comment already says *"a failed publish is a user/config error, not a flake"* — underscoring that this should already be a specific message) and then reports the generic Job-level `BackoffLimitExceeded` reason once the single retry is exhausted.

Same shape applies to the direct-publish/clone path (`cloneContainer`, `publish.go` ~369-410) and to any non-directory failure (e.g. a bad clone), since both share the same `Ensure`/`JobFailureMessage` seam.

**Fix direction:** capture the failing container's actual termination reason (exit code + tail of stderr — e.g. via `terminationMessagePolicy: FallbackToLogsOnError`, or by listing the Job's pod and reading container statuses) and surface that as `Observation.Message` instead of, or prefixed onto, the generic Job condition reason — mirroring how the build plane already treats a Job's specific failure class as worth explaining rather than defaulting to Kubernetes' own generic wording.

**Distinct from `w6/037`:** that note is a dashboard-layer bug (a generic toast swallows an already-specific backend GraphQL error). This one is upstream of that — the operator/backend layer here never had a specific message to relay in the first place, so there's nothing for a dashboard-layer fix to surface.

**Render:** not independently checked against Render's own behavior for this same failure case this run.

**Cleanup:** the test static site (`srv-da6ci36f35us73c4og50`) deleted via the dashboard's Danger Zone flow; workspace confirmed back to baseline.

## Resolution (2026-08-25)

**Partly already fixed, and the half that was left is the half this note explicitly called out.**

The extract path — the note's own live repro (a built image whose Publish Directory does not exist) — was closed by `d247d210`'s inbox triage: `publish.Ensure` now calls `failureMessage`, which reads the failing container's terminated state and quotes it, with `extract` carrying `terminationMessagePolicy: FallbackToLogsOnError` so its `cp: can't stat …` reaches the user. That triage deliberately excluded `clone` and `upload` from the log-echo policy, with a sound reason recorded in the code: `clone` holds `GIT_AUTH_TOKEN` and `upload` takes the object-store keys via `envFrom`, and a log tail is the wrong place to bet on what a third-party CLI prints on an error path.

The consequence was that this note's own second paragraph — *"Same shape applies to the direct-publish/clone path … and to any non-directory failure"* — stayed open. A direct-publish static site (no Dockerfile, the `w9/010` path) has the **same** wrong-Publish-Directory mistake available to it, at `cd "/work/$SRC_DIR"`, and it produced `clone: Error (exit 1)` — Kubernetes' bare word, no better than the `BackoffLimitExceeded` this note was filed about.

**Fix.** The credential objection is against echoing the container's *output*; it is not an objection to the container *speaking*. So `clone` now writes its own line to `/dev/termination-log` under the default `ReadFile` policy — text this operator authored, nothing git printed, so no token can ride out on it — one per step that can fail on the tenant's own input:

- fetch → `could not fetch "$REF" from this service's repository — check that the branch or commit exists and that bex still has access to the repo`
- checkout → `fetched "$REF" but could not check it out`
- **`cd $SRC_DIR` → `the publish directory "$SRC_DIR" does not exist in the repository at "$REF"`** — this note's mistake, on the path that has no built image
- cp → `the publish directory "$SRC_DIR" exists but its contents could not be staged for upload`

Exit codes are preserved (`cmd || fail $? "…"`), and nothing tenant-controlled is interpolated into the script text — `SRC_DIR`/`REF`/`REPO` still reach it only as environment variables, so the no-shell-injection property the file guards throughout is unchanged.

Second, `failedContainerDetail` stopped quoting `term.Reason`, which for the ordinary case is literally `"Error"` and for a SIGKILL/OOM is empty. It now names the step: `clone` → the repository could not be staged, `extract` → the built image's publish directory could not be staged, `upload` → *"could not be uploaded to the static-site store; this is a platform fault, not a problem with your site"*. That last one matters — an upload failure is never the user's fault and should not read as though it might be.

**Deliberately not done: the `PodFailurePolicy`.** The note names its absence, but as diagnosis of *why* the generic message appeared rather than as the fix — and the note's own "Fix direction" points at the message layer, which is now closed. Adding fail-fast would trade the single retry that absorbs a transient staging failure for roughly forty seconds of latency on an already-broken config, so the attribution it was cited for is achieved without changing retry semantics.

**Tests** (`lego/operator/internal/publish/publish_test.go`, both red pre-fix):

- `TestCloneStepsExplainTheirOwnFailures` — every failing step routes through `fail()`, the publish-directory message names both the directory and the ref, `clone` stays off the log-echo policy, and the repo URL is not interpolated into the script.
- `TestFailedPublishNeverQuotesKubernetesBareError` — drives the unrecorded case through `Ensure` and pins that it no longer produces `clone: Error (exit 137)`.
- `TestUnrecordedContainerFailureNamesTheStep` — the per-container wording, including that none of it says "Error".

Plus `app_controller_staticsite_test.go`'s new `explains a failed publish in the failing container's own words` envtest, which pins the **whole seam** end to end — container termination detail → App `Ready` condition (`PublishFailed` + the message) → what bex-api stamps as the deploy's `failureReason`. Stated honestly: this one is green both before and after this change, because it exercises the `term.Message` path `d247d210` already added; it closes an untested seam rather than guarding this delta.
