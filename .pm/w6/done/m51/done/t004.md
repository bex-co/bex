## Objective

Confirm t002's fix is visible identically across every surface that exposes the affected `SetXxx` verbs, and matches Render's own equivalent behavior (a Render Settings change also opens a deploy).

## Context

- `docs/ADR006-bex-api.md` — bex-api is meant to be Render-compatible across REST/GraphQL/MCP; `Service.SetXxx` verbs are shared by all three fragments, so t002's fix should apply uniformly, but this task is the check, not an assumption.
- Dashboard Settings pages call these verbs via GraphQL; confirm the resulting deploy row surfaces correctly in the Deploys tab and Events feed UI, not just in a raw API query.

## Steps

1. For each verb t001/t002 covered, exercise it via REST PATCH, GraphQL mutation, and the MCP tool equivalent; confirm each creates a visible deploy row identically.
2. Exercise the Dashboard Settings UI path for at least Start Command; confirm the Deploys tab and Events feed show the new row without a manual refresh being required to see it start (initial appearance), though polling-driven updates during the build are fine.
3. Compare against Render's actual documented/observed behavior for the equivalent settings change (does render.com's dashboard show a new deploy when you edit Start Command?) and note any deliberate divergence.

- [ ] REST, GraphQL, and MCP all produce an identical, visible deploy row for the same underlying edit.
- [ ] Dashboard Settings → edit → Save shows the resulting rollout in Deploys/Events without requiring a separate Manual Deploy click.

## Out of scope

## Findings (2026-08-24)

All three API surfaces converge on the same `apps.Service` verbs, so the gate in `patchFetched` covers them by construction — verified rather than assumed by `TestSurfacesAgreeOnDeployHistory`, which drives the same Start Command edit through the GraphQL verb (`SetCommands`, behind `setStartCommand`/`setBuildCommand`) and through `ApplyServicePatch` (the single ordered op table behind REST `PATCH /v1/services/{id}` and the `update_service` MCP tool) and asserts each opens exactly one `config_change` row.

Dashboard: `deployTriggerKey` gained a `config_change` case and both locales gained `deploys.triggerConfigChange` ("config change" / "配置变更"), so the new rows render with a real label instead of falling through to the null/unknown branch in the Deploys tab. No other dashboard change was needed — the Deploys tab and Events feed already poll the same queries.

Render parity: Render also opens a deploy for a settings change, and its deploy-trigger object carries an `envUpdated` flag for configuration-driven rollouts — which is what `config_change` maps to in the events feed. `manual` stays false, matching Render's meaning (a clicked deploy). No deliberate divergence.
