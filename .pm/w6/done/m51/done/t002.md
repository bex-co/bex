## Objective

Every verb t001 confirms forces a rebuild must create a real, visible `deploys` row for that rollout — the same guarantee `w2/m30` already gave the Restart action — instead of silently patching the App CR spec and leaving the operator's resulting rebuild untracked.

## Context

- `w2/m30` (done 2026-07-14, `.pm/w2/done/m30/`) solved this exact problem for Restart specifically: "dashboard restart → `triggerDeploy`" — read that milestone's implementation for the established pattern (likely `internal/deploys/graphql.go`'s `triggerDeploy` resolver / equivalent REST-side verb) before designing a new mechanism.
- The target shape: each t001-confirmed `SetXxx` verb (or a shared wrapper all of them call through) creates a deploy row scoped to the resulting rebuild, the same way `triggerDeploy` does, so `deploys(serviceId:)` / `GET /v1/services/{id}/deploys` and the Events feed see it.
- Must preserve today's actual mutation semantics — the field still needs to persist immediately (so `service(id).startCommand` etc. still reflect the new value right away) — this is additive tracking, not a behavior change to the setter's return value.

## Steps

1. Read `w2/m30`'s implementation of the Restart→`triggerDeploy` consolidation as the template.
2. Design the tracking hook: likely each t001-confirmed verb, after `patchFetched` succeeds, calls the same deploy-creation helper `triggerDeploy` uses (factored out if not already shared) so a new `deploys` row is opened for that rebuild.
3. Ensure the created deploy's `trigger` field accurately reflects the cause (e.g. `"settings_change"` or similar — distinct from `"api"`/`"create"`/manual-deploy triggers already in use, so users can tell a Settings edit from an explicit deploy in history).
4. Confirm the deploy row's status genuinely tracks the resulting build/deploy through to a terminal state (`live`/`deactivated`/`failed`/`canceled`) — not left permanently `building` if the operator's build fails, which is the second half of this milestone's DoD (a failed rebuild must reach a terminal status, not hang).
5. Apply to REST, GraphQL, and MCP call sites of each affected verb (they share `Service.SetXxx`, so this should be automatic — verify in t004).

## Acceptance criteria

- [ ] Editing a t001-confirmed field (e.g. Start Command) via GraphQL creates a new `deploys` row immediately, queryable via `deploys(serviceId:)`.
- [ ] The same holds via REST PATCH and the MCP tool equivalent.
- [ ] A deliberately-broken value (e.g. a start command referencing a nonexistent flag) produces a deploy row that reaches a terminal `failed`/`canceled` status within the normal build-timeout window — not stuck `building` indefinitely.
- [ ] A subsequent valid correction to the same field produces its own new tracked deploy that reaches `live`, with no separate Manual Deploy/Restart click required.

## Out of scope

- Verbs t001 determines are genuinely non-build (no change needed there).

## Implementation (2026-08-24)

One shared seam, `lego/backend/internal/rollout`:

- `rollout.Before(app)` snapshots the App's spec, `metadata.generation`, and control-plane row id.
- `Snapshot.Stamp(app)` asks `appv1alpha1.SpecRollsRelease(before, after)` whether the pending mutation rolls a release and, when it does, stamps `AnnotationReleaseGeneration` so the row and the operator's release decision name the same generation (the same guard `deploys.triggerFetched` uses against an operational mutation racing in between).
- `Tracker.Patch(ctx, client, app, trigger, mutate)` does the whole dance and opens the row; `Tracker.Open` is the lower-level form for a caller that owns its own merge-patch.
- The row's trigger is `store.TriggerConfigChange` (`"config_change"`), distinct from `create`/`api`/`deploy_hook`/`rollback`/`new_commit`. The Events feed maps it to Render's `envUpdated` trigger flag (previously never set) — deliberately not `manual`: nobody clicked Deploy.

Wired at: `apps.patchFetched` (the chokepoint all 33 `SetXxx`/disk call sites share), `envgroups.rollLinkedService` (link/unlink/roll/group-value change), `secrets.rollApp` + `finalizeEnvironmentPatch` (env vars, secret files, batch saves).

Two decisions worth flagging:

- **A multi-field PATCH is one rollout, not one per field.** `ApplyServicePatch` (shared by REST `PATCH /v1/services/{id}` and the `update_service` MCP tool) applies each present field as its own setter. Without coalescing, a four-field save would have opened four rows — three immediately canceled by the store's overlap handling. `rollout.Batch` scopes the request so only the final release generation is recorded. The dashboard is unaffected either way (it saves one field per mutation, each behind its own confirm dialog).
- **A failed row write does not fail the edit.** By the time the row is written the spec patch has landed and the rebuild is already rolling, so a store error is logged rather than returned — reporting a failure that did not happen would push the user into a retry that redeploys again. Same trade-off the git-webhook redeploy path already makes.

Terminal status (acceptance criterion 3) needs no new mechanism: once a row exists, `store.Reconciler.recordDeploy` drives it through the operator's observed phase to `live` / `build_failed` / `update_failed` / `canceled`, bounded by the operator's 15-minute `progressDeadlineSeconds` and the control plane's 18-minute `DeployGateTimeout`. See t003.
