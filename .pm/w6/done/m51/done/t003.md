## Verification (2026-08-24)

**Root cause of the observed "stuck Building", restated precisely:** the phase was never unbounded — the operator bounds a rollout with `progressDeadlineSeconds = 900s` (15 min, `deployment_projection.go`) and bex-api observes it with `DeployGateTimeout = 18m` (`store/reconciler.go`). The 2-minute observation window in the milestone's live evidence was mid-rollout. What was genuinely broken was that the rollout was **unobservable**: no deploy row meant nothing to inspect, cancel, or retry, and no terminal status ever appeared anywhere the user could see. "Stuck" was the honest reading of a rollout with no visible state, not a hung state machine.

**Structurally verified** by `TestConfigChangeFailsTerminallyThenSelfHeals` (`lego/backend/internal/store/config_rollout_journey_test.go`), which replays the exact live journey against the reconciler:

1. First deploy reaches `live`.
2. A broken Start Command opens a `config_change` row; the App sits in `Deploying` and never becomes healthy → the row closes **`update_failed`** with a non-empty `failure_reason`, asserted through `IsTerminalDeployStatus`.
3. The correction alone — no Manual Deploy, no Restart — opens its own row (asserted _not_ to be swallowed as superseded) which reaches **`live`** once the operator reports Running under that release.

Why the correction self-heals now: each edit is its own release generation with its own row, and `prepareAppReleaseDecision`'s pending slot adopts the newer spec as soon as the running build resolves. Before, the correction bumped the generation with nothing recording it, so there was no row to move and nothing in the UI changed.

Post-deploy, run the same repro on a fresh `qa-<yyyymmdd>-` service and confirm the two rows appear with the statuses above.
