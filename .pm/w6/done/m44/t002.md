## Objective

Make `/services/<dead-id>` stop rendering a fully-chromed ghost service page and follow `w9/m55`'s contract: redirect to `/` with the not-found toast. The service detail route is the only id-bearing detail route that never calls `useNotFoundRedirect`.

## Context

- Measured live 2026-08-22, `/services/srv-d9ndt8hmcglc739fkp5X`: `document.title` is "Page not found ・ bex Dashboard" while the body renders the full service shell — `SERVICE / Service Unknown`, an enabled **Connect** and an enabled **Manual Deploy** button, all 9 tabs (Deploys, Settings, Events, Logs, Metrics, Environment, Shell, Scaling, Plan) as live links, `Service ID:` blank, `Slug —`, `Instances 0`, `Revision —`, and the raw string `Deploys app not found`. It stays there indefinitely (sampled for 8s). The title and the body contradict each other.
- `dashboard/src/routes/services.$serviceId.tsx` contains no `useNotFoundRedirect` call. Its siblings all do: `project.$projectId.tsx:71`, `databases.$databaseId.tsx:123`, `blueprints.$blueprintId.tsx:216`.
- `w9/m55` t003 was titled "Apply to shell routes: services layout, project, webhook, workspace alias" and is marked DONE, so this is a regression or an incomplete application — check the history before rewriting, and match whatever the sibling routes do rather than inventing a second pattern.
- The hook only fires on a **settled not-found** and never on an error (`dashboard/src/common/hooks/use-not-found-redirect.ts`); t001 is what makes that state reachable for a service.
- Independently of the redirect, an action button pointed at a resource the page could not load should not be enabled — a dead-id page must never offer **Manual Deploy**.

## Steps

1. Find how the service route settles its resource (loader `loadRouteResource` state and/or the `Server` query result) and derive a real not-found boolean from t001's `null`.
2. Call `useNotFoundRedirect(...)` the way the sibling detail routes do.
3. Verify the error branch: a failed query must keep the inline error/retry UI, not redirect.
4. Confirm the ghost header/actions cannot render for an unresolved service (guard the action buttons on a loaded service, if the redirect leaves any frame where they'd paint).
5. Re-check every service tab path (`/services/<dead>/logs`, `/metrics`, `/settings`, …) — `w9/m55`'s DoD says "any tab".

## Files

- `dashboard/src/routes/services.$serviceId.tsx` (+ the tab routes if they resolve independently)

## Acceptance criteria

- [ ] `/services/<dead>` and each of its tab URLs redirect to `/` with the `common.resourceNotFoundToast` toast.

## Outcome (2026-08-22)

Done, but the title's premise is wrong: the route was never missing the escape hatch. `service-detail-layout.tsx`
already called `useNotFoundRedirect` — its predicate was defeated. `!service` never fired against the truthy
zero-value object, and once the backend answered `null`, `!error` never fired either, because bex-api reports a dead
id AS an error. Fixed by replacing the hand-rolled `!loading && !x && !error` with the shared `resourceNotFound` /
`resourceFailed` pair, which tests both halves. Pinned by
`dashboard/src/features/services/components/__tests__/service-detail-dead-id.test.tsx` (redirect on a not-found error,
redirect on a bare empty settle, and no redirect on a genuine outage).
