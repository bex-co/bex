## Objective

Give a dead blueprint id the same not-found treatment as every other dead resource id, instead of the generic failure page it shows today.

## Context

- Measured live 2026-08-22, `/blueprints/bpt-000000000000000000000`: `document.title` is "Something went wrong ・ bex Dashboard" and the page's `h1` is the raw id `bpt-000000000000000000000`. Sibling dead ids (`/services/<x>`, `/databases/<x>`) title themselves "Page not found ・ bex Dashboard".
- `dashboard/src/routes/blueprints.$blueprintId.tsx:216` already calls `useNotFoundRedirect(!loading && !blueprint && !error)`, so the page is landing in the **error** branch rather than the not-found branch — most likely because the backend answers a dead blueprint id with an error instead of an absent resource. Confirm which, and fix it on the side that is wrong; do not force a redirect on a genuine error (that would undo `w9/m55`'s central distinction).
- `w9/m55` t002 covered blueprints, so treat this as a regression and check what changed.

## Steps

1. Capture the actual GraphQL response for a dead blueprint id (signed-in browser fetch, as in t001's Context).
2. If the backend reports a dead id as an error, align it with t001's not-found contract; if it already reports absence, fix the route's classification.
3. Make sure a real blueprint-loading failure still renders the inline error state.
4. Check that no page uses a raw `bpt-…`/`srv-…` id as its `h1` when the resource did not load.

## Files

- `dashboard/src/routes/blueprints.$blueprintId.tsx`
- the blueprint resolver in `lego/backend/internal/apps/blueprint.go` (`GetBlueprintByID`, `lego/backend/internal/apps/blueprint.go:470`) if the error originates there

## Acceptance criteria

- [ ] `/blueprints/<dead>` redirects to `/` with the not-found toast (or otherwise matches sibling dead-id behavior), and no longer titles itself "Something went wrong".
- [ ] No raw resource id is used as a page heading for a resource that failed to load.
- [ ] A genuine blueprint query failure still shows the inline error/retry UI.
- [ ] `yarn typecheck && yarn lint && yarn test` green.

## Out of scope

- Blueprint sync/apply behavior — this is only the dead-id read path.


## Outcome (2026-08-22)

Done. The symptom was real; the cause is the same predicate as t002, not a missing hatch. `use-blueprint.ts` already
carried a zero-object workaround (`data?.blueprint?.id ? … : null`), so `blueprint` was null — but the accompanying
`app not found` error drove `showError`, producing the "Something went wrong" title over the raw `bpt-…` id. Both the
redirect predicate and `showError` now go through the shared pair. `blueprint(id, ownerId)` is also covered on the
backend by `TestDeadIDBlueprintResolvesToNull` — it is the verb that proves the fix had to live in the schema rather
than in `gqlutil`'s verb helpers.
