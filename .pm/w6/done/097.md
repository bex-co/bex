# `bex ea objects` returns 404 in every region — Render's early-access object storage is not served

Why: the CLI ships the Render EA object-storage commands (`list/put/get/delete`), but bex answers 404 for `oregon`, `frankfurt` and `fsn1`. A user who follows Render's docs to stage a data import hits a dead end. The crypto-price migration had to use a temporary tunnel instead (2026-10-27).

- **Decide:** implement the EA objects API (bex already runs S3-compatible stores for disk snapshots), or make the CLI say plainly that bex does not offer it yet.

## Triage — 2026-10-29 (BLOCKED: needs a product decision from the user)

- **Contract (render-oss/cli pinned `af9bdd180e90`, `pkg/storage/repo.go` + `client_gen.go`):** `GET /v1/objects/{ownerId}/{region}` lists objects (cursor, limit). `PUT /v1/objects/{ownerId}/{region}/{key}` takes `{sizeBytes}` and returns a presigned upload URL. `GET …/{key}` returns a presigned download URL (404 when missing). `DELETE …/{key}` returns 204. The client then PUTs or GETs the presigned S3 URL directly, with no chunked encoding.
- **Not in Render's public OpenAPI:** the pinned `render-public-api-1.json` has no `/objects` path. The commands sit under `render ea` ("early access … subject to change"), so Render's own exposure is gated and unstable.
- **What implementing means:** a new storage product. That needs a per-region bucket and credential custody (bex already presigns S3 for Postgres exports, `postgres/export_signer.go`, and runs S3 stores for disk snapshots), per-workspace prefixes and quotas, metering and billing for stored bytes and egress, and four authz-checked REST handlers plus docs. Estimate ~1.5–2 days as a milestone.
- **Decision needed (user):** (A) build it as a milestone for Render parity, including whether it is free during early access or metered; or (B) record a signed ADR018 divergence ("Render early-access object storage not offered") and have the CLI and the API answer with a plain "not offered on bex" message instead of a bare 404.
- **Recommendation:** (A) if migrations onto bex keep needing a staging bucket, as the crypto-price import did. Otherwise (B) now, re-opened when Render takes the feature GA.

## Decision and implementation — 2026-10-29 (option B)

- **Source:** explicit user decision (D4 = B, "先记偏差"). Render's early-access object storage is not offered on bex. This is a signed ADR018 divergence (Other datastores & storage → "Object storage (`render ea objects`, early access)"), to be re-opened when Render takes it GA or a migration needs a staging bucket. Option A stays on file as recorded above.
- **API:** `GET /v1/objects/{ownerId}/{region}`, and `PUT|GET|DELETE …/{key...}`, answer 404 `bex does not offer Render's early-access object storage yet`. Classified read/write in the scope matrix. `TestObjectStorageAnswersNotOffered`.
- **CLI:** `bex ea objects list|put|get|delete` refuses with the same sentence before any request. `--local` is passed through to upstream. `TestEaObjectsSaysObjectStorageIsNotOffered`.
- **Remaining:** after deploy, `bex ea objects list --region oregon` against production shows the message once the next bex-cli release carries the launcher change. Until then the API's 404 message shows for list/put through the Render CLI client.

## Closed — 2026-10-29 (API live; CLI on the next release)

- **API, live:** production pin `2ac6fd95402e` carries `e8d1df424`. As the QA user in `bex-canary`, `GET /v1/objects/{owner}/oregon`, `PUT …/oregon/a.txt`, `GET …/frankfurt/a.txt` and `DELETE …/fsn1/a.txt` each answered 404 `{"code":"NOT_FOUND","message":"bex does not offer Render's early-access object storage yet"}`. The QA session was logged out.
- **CLI, merged and tested, not yet released:** the launcher refusal reaches users with the next `bex-cli/v*` release (latest is `v0.3.3`, 2026-10-16, before `e8d1df424`). Releasing is the `/release cli` workflow and was not run here. Until then, Render-CLI-based `bex` builds show the API's message on `list` and `put`.
