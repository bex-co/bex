# An agent session's Go build temp files live in gVisor's memory-backed /tmp, so a routine was OOM-killed at its 8 GiB limit

Why: the first routine timed on the new setup (`rt-unify-duplicates`, `ags-dbrbbtgv8soc73b22mkg`, `agent-4c-8g`, warm cache, 30Gi disk) ran 68 min 24 s and then failed with "the sandbox ran out of memory" (2026-11-13 08:11:59 UTC): its memory reached 7.5 GiB of 8 at 08:08 while a second routine shared the cpx42.

- Under gVisor `/tmp` is an internal tmpfs, so it counts against the sandbox's memory limit (ADR042, ADR105). The Go toolchain writes its work directory (`$WORK`: compiled packages, link outputs, test binaries) under `$TMPDIR`, which defaults to `/tmp`.
- Fix: set `GOTMPDIR` (and `TMPDIR` for other tools) in the agent image to a rootfs directory such as `/var/tmp`, which counts against the 30Gi ephemeral storage instead (`lego/agent-image/Dockerfile` ENV block), and check how much memory the next routine run uses.
- From w6/blocked/m354 (routines timed on the cpx42); ~30m.

**Done 2026-11-13.** `9964b42d2` sets `GOTMPDIR=/var/tmp/go-tmp` in the agent image (deployed with `5de3d5bcc`). The next `rt-unify-duplicates` run (`ags-dbrdpfgk58is73aunnmg`, `agent-4c-8g`) completed in 61 min 56 s with the go command's work directory under `/var/tmp/go-tmp`; its memory peaked at 6.2 of 8 GiB and its disk at 4.9 of 30 GiB (ADR105 § What the routines did on the interim setup).
