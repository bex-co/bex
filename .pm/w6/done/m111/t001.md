## Objective

Stop the live tail from delivering lines the user's range excluded, and stop every first connect from re-reading a pod's whole log from kubelet's offset 0.

## Context

- `dashboard/src/features/logs/hooks/use-live-logs.ts:45-56` (`subscribeUrl`) builds `/v1/logs/subscribe?resource=…[&type][&text][&instance]` — no `startTime`.
- `dashboard/src/features/logs/components/log-viewer.tsx:134-143` computes `historyWindow = useLiveRange(range)` and hands it to `useLogHistory` only; `useLiveLogs` receives `type`/`text`/`instance` and nothing about the window.
- Server side: `lego/backend/internal/logs/rest.go:442` already parses `startTime`/`endTime`, and `:151-156` documents that an explicit `startTime` wins over the `Last-Event-ID` fallback. A browser `EventSource` sends `Last-Event-ID` only on **re**connect, so the first connect of every page load has neither.
- With `q.Since` zero, `NewPodLogStream` (`lego/backend/internal/logs/podlogs.go:56-66`) omits `PodLogOptions.SinceTime`; its own comment states the consequence: _"Without it kubelet replays the pod's ENTIRE log from offset 0 on every subscribe."_
- `w6/m93` added that `since` plumbing but scoped its claim to reconnects. This task closes the first-connect half. Read `.pm/w6/done/m93/README.md` before touching `podlogs.go` so the two fixes do not fight.
- **Boundary the fix must handle, not discover in production:** `rest.go:61` runs `core.CheckQueryWindow(s.MaxQueryHours, …)`; `BEX_MAX_QUERY_HOURS` defaults to `720` (`lego/backend/cmd/api/main.go:523`) and `core/pagination.go:82` rejects `end.Sub(start) > 720h`. The widest preset is exactly `30d` = 720h, so it sits on the boundary and a custom range past it returns `400`.

## Steps

1. Thread the resolved window from `log-viewer.tsx` into `useLiveLogs` and into `subscribeUrl` as `startTime`.
2. Clamp what is sent so a 30d preset or a wide custom range cannot trip `CheckQueryWindow`. Decide explicitly whether the clamp lives client-side, server-side, or both, and say which in the milestone README.
3. Confirm the window change reopens the stream (it is a new subscription) without duplicating lines against `mergeLogLines`' cross-source dedupe — a range change already refetches history, so both sources move together.
4. Check the interaction with `Last-Event-ID` resume: an explicit `startTime` must not defeat a mid-session resume into a narrower window than the client already has.
5. Re-probe live: the Network panel shows `startTime` on the subscribe request; a service whose only lines are older than the range shows nothing with Live on.
