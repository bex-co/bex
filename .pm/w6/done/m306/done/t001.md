## Objective

A release held by the admission gate or by a datastore wait has no Job yet, so nothing measures its wait: `bex_build_queue_seconds` starts at Job creation. Record when the current release first entered the hold, restart-safe in App status, and observe a histogram from that moment to Job creation, labelled by the wait's cause.

## Context

- `lego/operator/internal/controller/app_controller.go:1105-1130`: cap hold, `BuildQueued`, 30 s requeue
- `app_controller.go:1146`: datastore wait, `buildDatastoreWaitRequeue` (10 s)
- `lego/operator/internal/controller/build_metrics.go:75-77`: `bex_build_queue_seconds` = Job creation → pod placement
- docs/ADR060 §D5 "Queue time starts at the trigger (amended 2026-11-10)"

## Steps

1. Add an App status field holding the moment the current release generation first entered a hold; clear it when the release's Job is created, reset it when a newer generation is adopted. Run codegen (`make manifests generate` in `lego/operator/`).
2. On Job creation, observe a new histogram (for example `bex_build_admission_wait_seconds{cause}`, cause `admission` or `datastore`, the last cause seen).
3. Envtest: a manager restart during a hold keeps the original timestamp; a new generation resets it; a release that never waits observes ~0.

## Acceptance criteria

- [ ] A release held N seconds then dispatched observes ≈N in the histogram, with the right cause
- [ ] The held-since timestamp survives a manager restart
- [ ] ADR060 §D5 names the shipped series

## Out of scope

- Changing the semantics of `bex_build_queue_seconds` (it keeps measuring the node wait)
