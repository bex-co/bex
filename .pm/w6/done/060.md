# 060 — CORS preflight advertises only `GET, POST, OPTIONS`, so every mutating REST route is unreachable from the allowlisted browser origin

Why: `withCORS` hardcodes the method list, and it has drifted from a router that registers 53 routes on `DELETE`/`PATCH`/`PUT` — so bex's Render-compatible REST API is read-only to any browser client on the origin bex itself allowlists, while `POST /graphql` on that same origin mutates everything.

Filed 2026-08-27, 41st `/qa-find-bugs` run, journey 5 (custom domains). Found while trying to clean up throwaway domain claims over REST.

## Live repro

From `https://dashboard.bex.co` (the allowlisted origin), authenticated with the session cookie, `page.evaluate` + `fetch(..., {credentials:'include'})`:

```
DELETE https://api.bex.co/v1/services/srv-da7o6ovvqdcc73bpn9hg/custom-domains/qa-20260827.example.com
=> TypeError: Failed to fetch

console:
Access to fetch at 'https://api.bex.co/v1/services/srv-.../custom-domains/qa-20260827.example.com'
from origin 'https://dashboard.bex.co' has been blocked by CORS policy:
Method DELETE is not allowed by Access-Control-Allow-Methods in preflight response.
```

Reproduced identically for all three domain names tried. `GET` on the same collection, same origin, same session, succeeds — so the origin allowlist itself is working; only the method list refuses.

## The control kills the security rationale

The same browser, same origin, same cookie, deleting the same three resources through GraphQL instead:

```
POST https://api.bex.co/graphql
mutation($id:String!,$name:String!){ deleteCustomDomain(id:$id, name:$name) }
=> {"data":{"deleteCustomDomain":true}}   x3
GET  /v1/services/srv-da7o6ovvqdcc73bpn9hg/custom-domains  =>  []
```

So the restriction blocks nothing an attacker on that origin could not already do — every mutation in the product is reachable as `POST /graphql`, which the list permits. It only removes REST parity. (Same session also ran `deleteService` mutations over `POST /graphql` repeatedly across this hunt, so the cross-origin mutate path is proven, not assumed.)

## Root cause

`lego/backend/internal/api/auth.go:725`:

```go
w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
```

A literal, inside `withCORS` (`:708-734`). The function's own doc comment explains the origin allowlist and why `Allow-Credentials` is needed for the Kratos cookie; it says nothing about restricting methods, so this reads as a stale default rather than a decision.

The router it fronts disagrees. Distinct route patterns registered on verbs the preflight omits (`grep -rho '"<VERB> /[^"]*"' internal/ --include='*.go' | grep -v _test | sort -u | wc -l`):

| verb | distinct REST routes |
| --- | --- |
| `DELETE` | 26 |
| `PATCH` | 17 |
| `PUT` | 10 |

53 in total, across services, custom domains, env vars, env groups, environments, registry credentials, ssh keys, Postgres, Key Value. Examples: `DELETE /v1/services/{id}/custom-domains/{name}`, `PATCH /v1/environments/{id}`, `PUT /v1/environments/{id}/service-links`.

## Fix

Advertise the verbs the router actually serves. Prefer deriving the list from the registered patterns over a second hand-maintained literal — a literal is what drifted. If a hand-written list is kept, the regression test below is what stops it drifting again.

`Access-Control-Allow-Headers` is a literal in the same block (`Authorization, Content-Type, X-Session-Token`) and has the same drift exposure; check it against what the handlers actually read while here. No `Access-Control-Max-Age` is set, so every preflight is a round trip — worth adding, but that is polish, not the defect.

## Test

Assert the preflight response's `Access-Control-Allow-Methods` is a superset of every verb the mux registers, enumerated from the router rather than restated — so adding a route on a new verb fails the test instead of silently 404-ing browsers.

## Checked

- **Not the dashboard's problem today**, which is why it survived: the dashboard mutates through `POST /graphql`, covered by the existing list. This breaks third-party browser clients of the REST surface, and bex advertises that surface as Render-compatible (`docs/ADR006-bex-api.md`).
- **Not a duplicate.** `.pm` mentions of CORS are `w3/m43` (agent-session gateway stream endpoint, done) and `w4/dev-4/README.md` (a local `http://localhost:5173` origin setup note). Neither touches the method list.
- **Not deploy lag.** `git log -S"Access-Control-Allow-Methods" -- lego/backend` returns only `764d22ec` (the w3/m43 gateway CORS) and `8a86a28b` (the lego/ workspace move).
- **Render:** Render's REST API is documented as server-to-server and does not invite browser clients, so bex is not restoring a Render behavior here — it is making its own allowlisted origin coherent with its own router. Worth a line in the parity ledger only if the fix changes the advertised surface.

## Unverified

- Whether a browser client of the REST API actually exists today, or whether the CORS origin allowlist is set to anything besides the dashboard in production (`BEX_API_CORS_ORIGIN` was not read).
- Whether `Access-Control-Allow-Headers` is likewise short — noted as adjacent, not measured.
