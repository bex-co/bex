## Objective

Confirm that canceling an in-flight deploy of an image-backed service that already has a prior successful release actually reverts the running workload to the previous image — not just the deploy row's `status` — matching the Cancel dialog's existing promise "The last successful deploy remains live." This branch was reasoned from code in this milestone's evidence, never live-reproduced — this task is where it gets verified for real.

## Context

- `lego/operator/internal/controller/app_controller.go:577-579` (`settleCanceledRelease`): `if app.Status.Image != "" { return r.dispatchRuntime(ctx, app, app.Status.Image, port) }` — re-dispatches the PREVIOUS successful image. For a repo-backed App this is a no-op in practice (the live Deployment was never touched during an unfinished build). For an image-backed App, by the time Cancel is called the Deployment may have ALREADY been patched to the new (bad) image mid-rollout — this is the structurally different, harder case flagged as unverified in the milestone record.
- ADR004 (`docs/ADR004-app-deployment.md`): "The default RollingUpdate starts the new pod before terminating the old one... A pod joins the Service's endpoints only once its ReadinessProbe passes" — so a slow-but-not-yet-ready new pod means the OLD pod is still serving when Cancel is called; confirm `dispatchRuntime` reverting `spec` back to the old image causes Kubernetes to converge back to the old ReplicaSet cleanly (no split-brain between two ReplicaSets both wanting to be active).

## Steps

1. Create a live (or envtest) image-backed service, let its first deploy succeed (`Status.Image` set, `Running`).
2. Trigger a second deploy to a new image that will take a while to become ready (or use a crash-looping image, as in this milestone's original repro, but on the SECOND deploy instead of the first).
3. While the new pod is not yet ready (old pod still serving), call Cancel on the second deploy.
4. Assert: the deploy row closes `canceled`; `service(id:){phase}` settles to `"Running"` (not stuck `"Deploying"`); the running pod's image matches the FIRST (previous successful) image, not the second (canceled) one.
5. Confirm no orphaned ReplicaSet/pod from the canceled second deploy lingers after the revert.
