## Objective

Cover the behavior this milestone shipped with tests that assert the real failure modes — including the ones that look fine today and are only fine by accident.

## Context

- The existing test at `lego/backend/internal/metrics/range_test.go:174-178` asserts the current two-segment matcher string verbatim, so it encodes the bug rather than catching it — the same pattern `w6/m106` found with `TestRESTCreateWithIPAllowListAndReadBack`. It must be rewritten, not merely updated to a new literal.
- The bug's trigger is a **length**, so a fixture with a short name proves nothing. Tests need pod names at and past the 58-character generateName boundary, with both a 6-char and a 10-char `podTemplateHash`, since the threshold moves with hash length.
- Short-named services behave correctly today *because* the current assumption happens to hold. They are the regression surface, not the control.
- Defect A was invisible because a matcher that matched nothing was persisted as a healthy zero — that path needs its own assertion.

## Steps

1. Replace the string-equality matcher test with tests that assert **which pod names the selector accepts and rejects**: truncated one-segment, untruncated two-segment, both hash lengths, and an adversarial sibling App (`web` must not match `web-api`'s pods in either shape).
2. Test the usage meter's identity: an App whose object name is tenant-prefixed, a legacy bare-object-named App, and the `tenantID == ""` path all select their own pods.
3. Test that a selector matching no pods is not recorded as a healthy zero, while an App genuinely at zero replicas still is.
4. Cover the autoscale Prometheus fallback reader with the same name-length cases.
5. Add a dashboard-side test only if the charge tree's rendering changed shape with a second charge kind per service.
