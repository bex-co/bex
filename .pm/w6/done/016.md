Postgres/KeyValue/Service REST objects never populate Render's `owner` (nested `{id,name,email,type}`), `region`, `dashboardUrl`, or `updatedAt` fields — found 2026-07-15 running the real `render-oss/cli` (`./cli`) against a live bex-api (dev-9 harness) as part of checking postgres CLI compatibility (`docs/cli-compatibility-checklist.md`).

`render postgres get <name>` in the CLI's default text/interactive mode (`cli/pkg/text/postgres.go`) shows a blank `Region:` line and **omits** the `Workspace: <name> (<id>)` line entirely (via `workspaceLine`, silently skipped when `Owner.Name`/`Owner.Id` are both empty) — real, user-visible output, not a JSON-only cosmetic gap. Confirmed via raw `GET /v1/postgres/{id}`: the response has no `owner`/`region`/`dashboardUrl`/ `updatedAt` keys at all — `lego/backend/internal/postgres/service.go`'s `PostgresView` struct (~line 61) doesn't define them.

`apps.ServiceView` and `keyvalue.KeyValueView` have the identical omission (grepped both, zero hits for `Owner`/`Region`/`DashboardUrl`) — this is systemic across all three resource types, not postgres-specific.

**Update 2026-07-15 (same day, a parallel session):** KeyValue's `owner` slice of this is now fixed — `lego/backend/internal/keyvalue/rest.go` gained a REST-boundary-only `renderKeyValue`/`keyValueOwner` wire type nesting `owner: {id,name,type}` (email omitted; no `workspaces.Service` wiring was added, so it stays out of scope here too — this fix mirrors `workspaces.renderOwner`'s shape by hand rather than depending on it, which is why the reorder problem below didn't need solving to ship it). `region`/ `dashboardUrl`/`updatedAt` are still not populated for KeyValue, matching this note's remaining scope. Postgres and Service still have the full `owner`/`region`/`dashboardUrl`/`updatedAt` gap described below untouched. See `docs/cli-compatibility-checklist.md` RC13/RC14 for the full account.

bex already has the building blocks: `workspaces.renderOwner` + `toRenderOwner` (`lego/backend/internal/workspaces/render.go:33-61`) build exactly the `{id,name,email,type}` shape Render's `owner` schema wants, used today by `GET /v1/owners`. But they're unexported, and none of `postgres.Service`/`apps.Service`/`keyvalue.Service` carry a `workspaces.Service` (or narrower owner-lookup interface) dependency — and in `lego/backend/internal/api/server.go`'s `NewServer`, `workspaces.Service` is constructed (`Workspaces: &workspaces.Service{...}`, ~line 399) _after_ `pg`/`kv` (~line 319/324), so wiring it in means reordering construction too.

Region/dashboardUrl are smaller: bex has no per-Database region concept at all today (single-region deployments) — decide whether to hardcode a configured value or leave genuinely unset (and get the CLI to degrade gracefully) before touching that part; don't fabricate a region string with no backing data. `BEX_DASHBOARD_URL` (docs/ADR026, root CLAUDE.md env table) already gives a real base for a `dashboardUrl` link if a route exists in `dashboard/` for a given resource type.

Sizing: cross-cutting (3 backend packages + wiring reorder + a design call on region), not a quick fix — needs a real milestone if promoted, not a `/pm add-task` under an existing one.
