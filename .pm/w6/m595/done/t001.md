## Objective

The operator can build an App-owned Job whose one pod pulls a set of images onto one node and runs none of them: the pre-pull a disk service's code deploy starts beside its holder (t002).

## Context

- The holder Job is the model: `diskHolderJob` in `lego/operator/internal/controller/disk_holder.go` (App-owned, required node affinity on the node's name because admission refuses `nodeName`, zero requests, serving-pool toleration, `BackoffLimit` 0, deadline, TTL). [ADR082 § D3](../../../../docs/ADR082-persistent-disks.md) describes it.
- `operator-workload-admission.yaml` (`deploy/gitops/base/`) admits an App-owned Job (`appOwnedWorkload`) whose containers have the strict shape. The verify-image webhook (`lego/operator/config/webhook/manifests.yaml`, `internal/webhook/pod_admit.go`) checks only pods labeled `app.bex.co/verify-image: enabled`.
- `tenantImagePullPolicy` is `Always` (`app_controller.go`): with `IfNotPresent` a cached image skips the registry's credential check (w4/426).
- The milestone README's design notes cover the command, the user, the CPU limit, the labels and the quota.

## Steps

1. Add the Job builder next to the holder's: a `dskpul-` name through `appv1alpha1.DiskChildName`, the App's app label and a component label, one container per image to pull, `ImagePullPolicy: Always`, the projected template's `imagePullSecrets` and its `app.bex.co/verify-image` label when it carries one.
2. Make sure no container can run tenant code: a `command` no image can execute (e.g. `/`), an explicit non-root `runAsUser`, `RestrictedContainerSecurityContext`, a read-only root filesystem, no volumes and no service-account token.
3. Size it: zero requests, limits at which runc's init fails within about a second (the holder's 500m CPU), and a deadline and TTL.
4. Unit tests for the shape, and a test that the admission policy's CEL admits it, or an envtest create if the repository tests that policy another way.

## Files

- `lego/operator/internal/controller/disk_holder.go` or a new `disk_prepull.go`, and their tests
- `lego/types/v1alpha1/labels.go` if a new component value is needed

## Acceptance criteria

- [x] The Job's pod pulls each image with the template's credentials and verify-image label, and runs no tenant code
- [x] `make test` and `make lint` pass

## Out of scope

- The rollout hook (t002)

## Record (2026-11-23)

- `diskPrePullJob` in `lego/operator/internal/controller/disk_prepull.go`: the App-owned Job `dskpul-<app>` (`appv1alpha1.DiskChildName`), labels `app.bex.co/app`, `app.bex.co/app-uid`, `app.bex.co/component=disk-prepull` (`appv1alpha1.ComponentDiskPrePull`) and the template's `app.bex.co/verify-image` when it carries one. One container `pull-<n>` per image, `imagePullPolicy: Always`, the template's `imagePullSecrets`, command `/`.
- Shared with the holder: the required node-affinity term (`diskNodeAffinity`), the container hardening (`diskHolderSecurityContext`: restricted, uid/gid 65535, `runAsNonRoot`, read-only root) and `diskHolderResources` (zero requests, 500m CPU). No volumes, no service-account token, `BackoffLimit` 0, the holder's 16-minute deadline and 60 s TTL.
- The command was checked on the CAPD cluster (Kubernetes 1.36.1, containerd 2.3.1) with a pod of this shape: each container ended `terminated`, exit 128, reason `StartError`, message `exec: "/": is a directory`, with its `imageID` set, and the pod went `Failed`.
- Tests: `TestDiskPrePullJobIsTheAppsAndNoInstance`, `TestDiskPrePullPodPullsEachImageOnTheNodeAndRunsNone`. The deployed `bex-operator-workloads` policy admits the Job and refuses each privilege mutation of it (`admissionTierWorkloads` in `container_policy_admission_test.go`, every tier).
