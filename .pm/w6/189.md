# 189 — A Blueprint service that reads another service's address starts before that service is up, so Render's `temporal` template fails its first deploy

Why: Render's `temporal` template adds a `fromService` variable whose only job is ordering. Its comment reads "The worker service needs to wait for the history service to be up first, otherwise it will fail". On bex the worker starts at once and its first deploy fails.

- **Source:** w6/m653 t003 (2026-11-26), the live run of the 49 remaining no-value `render-examples` templates ([render-examples-live.md](../../docs/render-artifacts/render-examples-live.md)).
- **Seen** on production pin `9b91284a4a2e`, in `bex-canary`, with `scripts/render-examples-live.sh temporal` (render-examples/temporal@9594ec21757c: six private services, a web service, a worker and a `basic-256mb` Postgres). The approved sync started every service at once. `temporal-frontend` runs Temporal's `auto-setup`, which creates the schema. `temporal-worker`, which reads `temporal-frontend`'s and `temporal-history`'s `host`, started first and exited: `sql schema version compatibility check failed: … relation "schema_version" does not exist`. Its deploy ended `update_failed` at 11:55:09 UTC, while `temporal-frontend` was still `update_in_progress`; `temporal-history` and `temporal-matching` went live two minutes later. The fixtures were deleted by ID (404).
- **Render:** `render.yaml` gives `temporal-worker` a variable `DEPENDS_ON_HISTORY` (`fromService: {name: temporal-history, type: pserv, property: host}`), which Temporal never reads. The comment above it says the worker must wait for history. So on Render a service that references another service through `fromService` is deployed after it. Render's docs do not state this order.
- **Sibling:** [w6/184](184.md) is the same gap for a database or Key Value the service reads (`umami`, and `langfuse4-template` in this run). Fix them together: a reader's first release waits for every resource of the same sync that its `fromService` and `fromDatabase` references name.
- **Do:** in a Blueprint sync, a service whose environment references another service of the same sync (`fromService` with `host`, `hostport`, `port` or `envVarKey`) starts its first release after that service's first deploy is live. Say in the deploy log what it waited for, in Render's words if Render prints any.
- **Acceptance:**
  - [ ] `bash scripts/render-examples-live.sh temporal` gets past `temporal-worker` on production. Its `temporal-elasticsearch` still needs [w6/186](186.md).
  - [ ] A regression test: a sync that creates two services, one reading the other's `host`, does not start the reader's release before the other is live.
- **Estimate:** ~1h on top of w6/184's ordering. A Render parity task applies if the deploy log or events change.
