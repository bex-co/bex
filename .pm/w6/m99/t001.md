## Objective

Expose, as an explicit checkable field on the service read path, whether THIS App's `spec.repo` actually belongs to the workspace's connected GitHub App installation — reusing the grant-match signal `mintCloneSecret` already computes on every deploy trigger, rather than inventing a second lookup. The stored `autoDeploy` boolean's default-true behavior for any repo-backed create stays unchanged (see the milestone README's Adjacent classes); this task only adds a way to check push **deliverability**, distinct from the on/off **setting**.

## Context

- `lego/backend/internal/apps/clonesecret.go:106-121` `mintCloneSecret(ctx, namespace, appName, workspaceID, repo)` calls `s.GitHub.CloneToken(ctx, workspaceID, repo)`, whose `ok` bool is exactly "does `repo` belong to `workspaceID`'s GitHub connection." Today this only runs at deploy-trigger time (create, redeploy, manual deploy, deploy hook, rollback, blueprint sync — see `w6/m97`'s enumerated call sites) and its result is discarded except to decide whether to mint `spec.cloneSecret`.
- `lego/backend/internal/apps/render.go:130-141,207-219,280-281` defines `AutoDeploy`/`AutoDeployTrigger` on the Render-shaped response and maps bex's stored `a.AutoDeploy` bool onto them via `yesNoEnum`/`triggerEnum` — this is the shared REST+GraphQL mapper.
- `lego/backend/internal/apps/service.go:2342` `autoDeploy = req.Repo != ""` (create-time default) — leave unchanged.
- GraphQL schema and MCP `get_service`/`list_services` structured content both derive from the same underlying service-read path — confirm the exact call chain before adding a field so it reaches all three surfaces from one change.

## Steps

1. Add a read-only, computed field to the service's Render-shaped response — e.g. `autoDeployCapable: bool` or a richer `pushDeliveryMethod: "github_app" | "manual_webhook" | "none"` (pick whichever the existing enum conventions in `render.go` favor; prefer reusing `CloneTokenSource.CloneToken`'s `ok` semantics over introducing a new grant-check code path).
2. Wire it through the one shared REST+GraphQL response mapper (`render.go`) so both surfaces gain it identically, and through the MCP `get_service`/`list_services` tool schemas (`lego/backend/internal/apps/mcp.go`) so their structured content includes it too.
3. Compute it on read (not cached from create time) — a workspace's GitHub grant can change after the App was created (installation edited on GitHub's side), so a stale create-time snapshot would reintroduce a staler version of this same bug.
4. Handle `s.GitHub == nil` (GitHub integration off) and `a.Spec.Repo == ""` (image-backed) cleanly — both should report "not applicable," not "no."

## Files

- `lego/backend/internal/apps/render.go`
- `lego/backend/internal/apps/clonesecret.go` (read-only reuse, or extract the check into a small shared helper if `mintCloneSecret`'s side effects — writing the Secret — make it unsuitable to call from a pure read path)
- `lego/backend/internal/apps/mcp.go` (or wherever `get_service`/`list_services` structured output is assembled)
- `lego/backend/internal/apps/graphql.go` (schema field, if GraphQL needs an explicit resolver beyond the shared struct)

## Acceptance criteria

- [ ] `GET /v1/services/{id}` for a service whose repo is NOT in the workspace's GitHub grant returns the new field indicating no GitHub-app delivery, while `autoDeploy`/`autoDeployTrigger` keep reporting the stored on/off setting unchanged (default-on behavior preserved).
- [ ] The same service's GraphQL `server(id){...}` and MCP `get_service` responses carry the identical value for the new field — no REST/GraphQL/MCP divergence introduced.
- [ ] A service whose repo IS in the grant (the `w2/m9` control case) reports the new field as GitHub-app-deliverable, unchanged from today's implicit assumption.
- [ ] An image-backed service (no repo) and a GitHub-integration-off deployment both report the field as not-applicable, not as a false "no."

## Out of scope

- Changing the stored `autoDeploy` boolean's default-on create-time behavior.
- The dashboard hint (t002) and regression tests (t003) — this task is backend-only.
