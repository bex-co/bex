# The session page keeps a started sandbox's live conversation stream open after the start settles, holding one of the person's five gateway sessions for up to 4 hours

Why: w6/m564 t004's production run (2026-11-23) found that after Connect > Start the sandbox, the session page's conversation stream that attached while the session read `resuming` stays open once the start settles, until the tab leaves the page. Since m564 t009 it no longer keeps the sandbox, but the gateway counts it against the person's concurrent sessions (`BEX_SSH_MAX_SESSIONS_PER_IDENTITY`, 5, one limiter shared by SSH, web shell and agent attach), so a few started sessions left open in tabs can refuse the person's own Zed with `session limit reached` for up to the 4-hour cap.

- **Evidence.** Session `ags-dc22jkehv52s73bqmmt0` in the `bex` workspace (disposable). Three starts from the dashboard each left one `ssh_sessions` row of the agent attach open from the `resuming` phase on: `ssn-dc22ompknr1s73a6bkog` (12:06:51Z, ended 12:07:36Z only when the tab navigated away, gateway log `agent attach: live splice ended … context canceled`) and `ssn-dc22s9hknr1s73a6bld0` (12:14:30Z to the navigation at 12:22:15Z). The re-attach after the settle wrote its own row, which closed within milliseconds (12:06:56Z, 12:14:35Z), so the first stream is never aborted.
- **Where.** The dashboard's in-place re-attach (`session-conversation-impl.tsx`, the `attachSignal` effect calls `resumeStream()` without ending the stream it replaces), or the gateway's live splice to a sandbox resume started for an editor (`lego/backend/internal/sshgateway/agentattach`), whose driver runs no turn and so never ends the stream (ADR054 D8). Find which one holds it before fixing; ending the replaced stream in the dashboard is the likely one.
- **Done when** a dashboard test shows the re-attach ends the stream it replaces, and on production a start from Connect, with the tab left on the session page, leaves no open agent-attach row once the start has settled.
