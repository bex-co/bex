## Objective

Prove the fix live against production (or a staging equivalent), not just in unit tests — hydration mismatches are a runtime SSR-vs-client timing phenomenon that a component test can assert but not fully substitute for.

## Context

- Original repro: `page.goto('https://dashboard.bex.co/webhook/<id>')` immediately after a delivery landed ~55s earlier logged React error #418 (`.playwright-mcp/qa-webhook-react418-console.log` from the 2026-08-25/26 hunt).
- Sign in via `scripts/qa-login.sh` per the standard QA procedure (never read `.env` directly, never type the password into a tool call).

## Steps

1. Sign in as the QA user.
2. Create a short-lived QA webhook (`qa-<date>-...` prefix), trigger an event, and load `/webhook/<id>` within the first ~60 seconds of the delivery landing — repeat 3x to increase the odds of crossing the exact "now"→"1m" boundary during page load. Check `browser_console_messages` each time.
3. Repeat against 2 more of the newly-guarded routes with a naturally recent timestamp (e.g. a cron job's service header showing `lastSuccessfulRunAt`, or a database/keyvalue detail page loaded right after creation).
4. Delete the QA webhook and any other QA-created resources afterward.

## Files

- No code changes; verification only.

## Acceptance criteria

- [ ] Zero React error #418 across all repro attempts.
- [ ] QA resources cleaned up.

## Out of scope

- Exhaustively verifying all 22 sites live (t002's proximity-check script plus this spot-check across 3 routes is sufficient evidence for closeout).

## Status — blocked on deployment, not on code

**Cannot be run yet, and not for lack of trying: production serves the pre-fix bundle.** `deploy.yml` builds on push to `main`, so `dashboard.bex.co` cannot exhibit the fixed behaviour until this milestone ships. Probing it now would only re-confirm the bug the hunt already captured (`.playwright-mcp/qa-webhook-react418-console.log`), at the cost of creating and deleting real resources in production.

**What was done instead — a deterministic equivalent that is strictly stronger than the live probe, and permanent:** the live repro depended on *luck* (a page load happening to straddle a bucket boundary), which is why the DoD asks for 3 repeats. `dashboard/src/test/hydration.ts`'s `hydrateAcrossBoundary` forces the boundary crossing instead: it server-renders at one clock and hydrates the same markup at another, so the mismatch is guaranteed to be attempted every run. It is applied to three surfaces (`webhook-deliveries-card`, `api-key-row`, `relative-time` itself), each asserting zero recoverable React errors, and the `relative-time` case carries a negative control proving the probe still detects an unguarded formatter. This runs in CI on every commit, forever — the live probe runs once.

The honest DoD reading for m102 is **zero #418 attributable to a relative age**; a literal zero on that route needs m107 too.
