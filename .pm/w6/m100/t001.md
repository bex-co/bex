## Objective

`lego/operator/internal/controller/app_controller.go:3761-3765` (`setNotReadyCondition`, the shared body behind `r.fail` at lines 3805-3809) stamps the Ready condition's `ObservedGeneration` from `obj.GetGeneration()` — the App's raw current `metadata.generation` — instead of the release generation the failing build was actually pinned to (`app.Status.ReleaseGeneration` at the moment of failure). When a second deploy's spec patch has already bumped `metadata.generation` before the first deploy's build fails (an ordinary race — see the milestone's Background), this mis-attributes the terminal-failure marker to the *newer* generation. `terminalBuildFailureRecorded` (`app_controller.go:881-886`), gating re-dispatch at line 681, then incorrectly concludes the newer generation already failed terminally and halts the reconcile before `app.Status.ReleaseGeneration` can ever be persisted forward to the newer (queued) generation — stranding it at `queued` forever with no further reconcile ever scheduled for that App.

Fix this so a queued/pending release generation can still advance once the blocking generation's build failure is durably recorded, without reopening the w2/m82 bug this exact code exists to prevent (an already-recorded terminal failure being re-attempted/re-metered on every reconcile, which caused ~20 `Reconciler error` log lines/hour per stuck App before that fix).

## Context

- `lego/operator/internal/controller/app_controller.go:670-683` — the gate + its rationale comment (re-dispatch halt, TTL-reap re-run prevention).
- `lego/operator/internal/controller/app_controller.go:855-886` — `buildOutcomeAlreadyRecorded` (metering gate, correctly reason-scoped) vs `terminalBuildFailureRecorded` (re-dispatch gate, generation-scoped — the one that's wrong).
- `lego/operator/internal/controller/app_controller.go:3750-3809` — `setNotReadyCondition` + `r.fail`. The conflict-retry loop here (`statusWriteAttempts`, re-read/re-apply) is unrelated to this bug and must not be disturbed.
- `lego/operator/internal/controller/release_identity.go:190-268` — `buildRunning`/`prepareAppReleaseDecision`: the pin-while-building branch (220-247, ADR060 §D1a, correct) vs the non-pin branch that advances `Status.ReleaseGeneration` (248-262) — this advance is computed in memory but never persisted when `terminalBuildFailureRecorded` halts first.
- `lego/backend/internal/store/reconciler.go:1036-1089` — `supersededDeployStatus`: the consumer that trusts `app.Status.ReleaseGeneration` as the sole "which row is active" signal (its `OverlapPending` branch at 1058-1060 waits forever on the assumption this fix restores).
- Candidate fix directions (pick and justify one, or another that satisfies the acceptance criteria):
  1. Stamp the Ready condition's `ObservedGeneration` from the generation the build attempt was actually pinned to (e.g. the release generation being observed when `r.fail` is called from the build-failure path) rather than unconditionally from `obj.GetGeneration()` — while auditing every other `r.fail` call site (not just the build path) for the same unconditional stamp, since `setNotReadyCondition` is shared.
  2. Persist `app.Status.ReleaseGeneration`'s advance to the pending generation as part of (or immediately before) recording the terminal build failure, so the "already failed" gate and "release generation advanced" fact land in the same status write and can never observe each other's stale half.
  3. Any other approach — but it must keep `terminalBuildFailureRecorded`'s original purpose intact (never re-create/re-run a Job for a generation whose failure is already durably recorded) while letting a *different*, newer, still-pending generation proceed.

## Steps

1. Reproduce locally/in envtest: an App with `Status.Phase=PhaseBuilding`, `Status.ReleaseGeneration=G1`, `Status.PendingReleaseGeneration=G2`, `metadata.generation=G2` (i.e., a second spec patch already landed); drive the build Job to a `PodFailurePolicy`/`FailJob` failure; assert the App gets stuck (`terminalBuildFailureRecorded` wrongly true for G2) — this should be RED before the fix.
2. Apply the chosen fix.
3. Re-run the repro: assert the next reconcile now dispatches G2's build (or, if desired, at minimum advances `Status.ReleaseGeneration` to G2 and lets the following reconcile dispatch it) instead of halting.
4. Re-run the existing w2/m82 regression tests (`lego/operator/internal/controller/` — search for `buildOutcomeAlreadyRecorded`/`TestReconcilerError` or equivalent) unmodified and confirm they still pass: a generation whose failure is already recorded must never be re-failed/re-metered.
5. Audit every other `r.fail(...)` call site in `app_controller.go` for the same unconditional `obj.GetGeneration()` stamp pattern and note (in this task or a follow-up) whether pre-deploy/rollout failure paths share the same exposure even though `terminalBuildFailureRecorded` itself doesn't gate them (a *different* gate might).
