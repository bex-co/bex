## Objective

t001-t002 prove the fix for a **fresh deploy**. This task proves (and, if still broken post-t001, fixes) a second, more insidious angle live-confirmed on production during the 2026-08-26 14th `/qa-find-bugs` run: an **already-Live, already-stable** service with a GitHub-connected repo gets bounced to `phase: "Failed"` the next time the operator reconciles it for **any** reason (not a new deploy) — and the dashboard Events feed then reports a plausible-sounding but **wrong** cause ("A running instance stopped passing readiness checks"), actively misleading whoever investigates.

## Context

- **Live evidence (this run, not reasoned from code alone):** `beancount-forum` (`srv-d9nqg9dcavls73fp8m2g`, `bex-co/discourse_docker`, workspace `tea-d98210cbbpdc73dcrkvg`) shows `phase: "Failed"` via both `GET /v1/services/srv-d9nqg9dcavls73fp8m2g` (REST) and the dashboard header pill, while its **Latest deploy reads "Live"** (`dep-da4c61pahdqc73f1j9n0`, deployed 2026-08-21, revision `rev-112`, `updatedAt: "2026-08-26T00:53:54Z"` — i.e. flipped to Failed ~9h before this was observed, with no new deploy in between). This is `spec.CloneSecret` remaining permanently set on the App CR after the last successful build (nothing clears it once minted — see `lego/backend/internal/apps/service.go:3267`'s comment, which only clears it on a repo change) combined with `Reconcile`'s level-triggered nature (`lego/operator/internal/controller/app_controller.go:499`, `rejectProtectedSecretRefs` runs unconditionally on **every** reconcile, not gated on a new generation) — so any resync/watch-triggered reconcile of this App (cert renewal check, operator restart, unrelated config sync) re-evaluates the guard against the same self-referencing `CloneSecret` and re-fails it, indefinitely, even though nothing about the actual running Deployment changed.
- **The misleading Events entry, root-caused:** the dashboard's Events feed showed, for this exact service, `"Instance failed" / "A running instance stopped passing readiness checks."` (9h old) — the `services.eventsTypeInstanceFailed` / `services.eventsReason.readiness_failed` locale pair (`dashboard/src/features/services/locales/en.ts:3427-3429`, `:3552-3555`). The backend event this renders comes from `observedServiceStateFor` (`lego/backend/internal/store/reconciler.go:1232-1281`): when the Ready condition is `False`, `hasOpenDeploy` is `false` (true here — the last deploy is closed/Live), and `condition.Reason` is not one of the three explicitly excluded values (`"Suspended"`, `"AutoHibernated"`, `"RolloutSettling"`, checked at line 1270-1271), the function sets `obs.ReasonCode = EventReasonReadinessFailed` (line 1274) **unconditionally** — it never inspects what `condition.Reason` actually is otherwise. So `"ProtectedSecretReference"` (this bug's Ready-condition reason, set by `r.fail` at `app_controller.go:499`) collapses into the exact same generic "readiness check failed" story a real `CrashLoopBackOff`/`ImagePullBackOff` produces — even though nothing about the pod's readiness was ever evaluated.
- This is not limited to `ProtectedSecretReference`: `Reconcile`'s other early `r.fail` call sites that run **before** any pod/container is ever inspected (`"PerAppRegistryCredsFailed"` at line ~497, `"RegistryPullSecretFailed"` at line ~500 — see `convergeRegistryCredentials`, `app_controller.go:487-503`) hit the identical generic-fallback path in `observedServiceStateFor` once `hasOpenDeploy` is false. This task's fix should close the whole class, not just the one reason this hunt happened to reproduce.

## Steps

1. Confirm (after t001 lands) that `beancount-forum`'s exact scenario is actually fixed: force a reconcile of an App whose `spec.CloneSecret` is already set to its own deterministic self-name (no new deploy triggered) and assert `rejectProtectedSecretRefs` no longer fails it — add this as an operator-level regression test distinct from t002's "new deploy" framing (a **standing** App, generation unchanged, reconciled again).
2. Independently of t001, fix `observedServiceStateFor` (`lego/backend/internal/store/reconciler.go:1232-1281`) so a Ready=False condition whose `Reason` reflects a pre-pod-evaluation refusal (`"ProtectedSecretReference"`, `"PerAppRegistryCredsFailed"`, `"RegistryPullSecretFailed"`, and any other `r.fail` reason set before `dispatchRuntime`/pod reconciliation ever runs) does **not** get labeled `readiness_failed`. Either add a small denylist/allowlist of "these reasons mean a real pod-level readiness failure" (inverse of the existing three-item exclusion list) or thread a coarser signal (e.g. a reason-prefix or a new bounded `ReasonCode`) so the dashboard can render an honest, distinct message for a pre-pod-evaluation refusal versus an actual unhealthy running instance.
3. Add the new bounded reason code's dashboard copy (en + zh, `dashboard/src/features/services/locales/`) if step 2 introduces one — follow the existing `services.eventsReason.*` naming convention.
4. Live-verify once deployed: re-check `beancount-forum` (or an equivalent standing GitHub-connected service) shows `phase` agreeing with its Latest deploy's actual status, and that if the guard ever misfires again for a genuinely different reason, the Events feed names that reason honestly instead of defaulting to "readiness checks."
