# tenant-view probe detects an activator-held wake and polls for `service_woken` (#134)

Why: the production canary raised a false tenant-view-down (#134, run 42455673421) because the probe cannot tell its own request woke the service; a probe that cries wolf trains everyone to ignore the next real outage.

## Evidence (checked at `460c283a6`)

- `scripts/tenant-view-liveness.sh:153` sets `wake_seconds=$waited`, which only counts 3 s retries after a non-200 (`:140-146`). An activator-held wake is a single curl blocking ~14 s (w4/517 measured 13.7 s) and is reported as "200 in 0s".
- With `wake_seconds=0` the script takes the "already awake" branch (`:297-320`): one `fetch_events`, no poll; the `WOKEN_BUDGET=120` loop (`:277-286`) only runs in the wake branch. `service_woken` lands on the backend's ~30 s observation pass, so the single read raced it.
- Green runs 42419769275 / 42180336461 / 42377288041 saw their own wake 27–175 s old: the canary does sleep and wake; not a production regression.
- Events are queried from `WINDOW_START` = now − 10 min (`:124`, `:267`), so the documented 3600 s `EVENT_WINDOW` never applies. The failure text at `:302-309` repeats the old w1/m173 "never sleeps" diagnosis.

## Fix

1. Measure stage 1 by elapsed time (curl `%{time_total}` or `date +%s` around the loop); > ~3 s means a wake.
2. Poll for a `service_woken` at or after the wake start for up to `WOKEN_BUDGET` in both branches before failing.
3. Align the events query window with `EVENT_WINDOW` (or drop the 3600 s claim) and rewrite the misleading message.
4. Add a test for "held 14 s response ⇒ wake branch" if a harness exists; dispatch `ssh-edge-liveness.yml` and let the green run close #134 (`.github/workflows/ssh-edge-liveness.yml:449`).
