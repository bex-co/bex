# SSH gateway exec runs at ~43 KB/s and drops a quiet session after ~2 minutes

Why: piping a database into a service over `ssh srv-…@ssh.bex.co` (the Render-documented way to move data in) is unusable for anything over a few MB, and a long INSERT that prints nothing is cut mid-write.

- **Throughput:** 20 MB of random data through `ssh srv-dbg4lfdn83uc738uug70@ssh.bex.co wc -c` took 461 s (~43 KB/s) on 2026-10-27. A 13.7 MB ClickHouse Native stream took 384 s.
- **Idle cut:** an `INSERT … SELECT FROM url()` that printed nothing ended at ~128 s with exit 255. ClickHouse cancelled the query mid-insert and left a partial table. Detached (`setsid nohup`) inserts finished normally.
- **Look at:** channel window and packet sizes in `internal/sshgateway` (a tiny flow-control window would give exactly this bandwidth), the k8s exec stream path, and `BEX_SSH_SESSION_TIMEOUT` versus idle handling for exec sessions with an open stdin.
- **Expected:** throughput bound by the link, and no idle cut while a command runs.

## Progress — 2026-10-29

- **New, more serious finding (fixed):** exec output was truncated whenever the command exited before the client had received it all. `ssh srv-d9nqg9dcavls73fp8m2g@ssh.bex.co 'head -c 1000000 /dev/urandom' | wc -c` returned 368,689 bytes, and 5 MB returned 3,309,568 followed by `Connection … closed by remote host`. With `; sleep 30` appended, all 5,000,000 bytes arrived. Cause: `nativessh.Server` closed the transport as soon as the single-session exec returned. The tail still in flight (in the socket send buffer and the edge proxy's) was reset away. Fix: wait for the client to close the transport, as sshd does, bounded by `clientCloseGrace` (30 s) and the session context. Regression test `TestGatewayWaitsForTheClientToCloseAfterExec` (red with a zero grace, green with the fix).
- **Idle cut, not reproduced:** `sleep 200 | ssh … 'sleep 150; echo alive'` printed `alive`, rc 0, after 200 s. The gateway's own session limit is 4 h (`SessionTimeout`). The 10-27 cut at ~128 s is unexplained; a gateway pod roll during that day's deploys is plausible but unverified. Re-test after deploy with a 10-minute quiet exec.
- **Throughput, improved but not root-caused:** on 2026-10-29, 5 MB went up in 15 s (~333 KB/s, against 43 KB/s on 10-27) and down in ~30 s. A direct `kubectl exec -i … wc -c` of 20 MB from the same laptop took 21.7 s (~920 KB/s), so the gateway path is still ~3× slower than the API path. Not yet located (Traefik TCP entrypoint, SPDY executor, or the SSH channel).
- **Follow-up spotted, not changed:** `webshell/websocket.go` also closes after its close frame without waiting for the browser's close (lower risk, an interactive TTY).
- **Remaining:** after deploy, re-run the 1 MB/5 MB truncation checks (expect the exact byte counts), the 10-minute quiet exec, and a throughput profile of the gateway path.
