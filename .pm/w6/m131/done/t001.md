## Objective

Discharge the production verification `w3/m8` left owed, and determine where Traefik's access-log stream stops before it becomes `type=request` in Loki. This is the diagnosis task: the milestone establishes the symptom exhaustively but **not** the cause, and nothing downstream should assume one.

## Context

- `scripts/logs-verify.sh` already exists (20 KB, executable) and was written for exactly this gate. `w3/m8`'s status line records why it never ran: it "inherits m5/t005's gate — it needs a Loki-synced cluster (prod), which the CAPD mock is not."
- Symptom, live 2026-08-28: `type=request` returns 0 rows for all five web services in the workspace over 24h, and `GET /v1/logs/values?label=method` / `?label=statusCode` return `[]` for all five. Loki's label index is the source for those, so the labels were never shipped.
- **Already ruled out — do not re-chase.** The `w3/m13` frozen-ConfigMap failure (Argo CD `ComparisonError` → live ConfigMap stuck pre-`w3/m8`, documented at `deploy/gitops/base/log-shipper.yaml:66-89`) is **not** the cause: that frozen state also lacks level normalization, and `label=level` on `beancount-cms-v2` returns `["error","unknown"]` live. App logs and build logs also flow from the same store.
- Candidate stop points, read from config and **not measured**:
  - Traefik's own access log (`traefik.values.yaml` `logs.access`) — is it enabled and JSON?
  - the shipper's traefik discovery/relabel (`deploy/gitops/base/log-shipper.yaml:463-490`), whose relabel regex is `traefik/traefik`;
  - the `ServiceName` drop stage (`:493-504`), which drops every line not carrying `ServiceName` — if the access-line format changed, this drops everything.
- Node-scoped discovery: the config's single `discovery.kubernetes.pods` block is client-side `keep`-filtered by node (`:60-63`), so a Traefik pod on an unexpected node would be invisible to that Alloy instance.

## Steps

1. Run `scripts/logs-verify.sh` against production and record its complete output in this task.
2. Query Loki directly for `{job="traefik"}` to establish whether Traefik lines arrive at all, versus arriving and being dropped by the `ServiceName` stage.
3. If they arrive, check the access line's shape against what the drop stage and the `ServiceName`→App attribution expect.
4. If they do not, check Traefik's access-log setting and the discovery relabel in that order.
5. Record the located cause. **`DO_NOT_DO.md` item 12:** if the fix belongs in Helm/GitOps, it stays there — this task locates and records it rather than moving shipper responsibility into product code.

## Outcome (2026-08-28)

**Cause located, fixed, and verified working in production.**

Cause (from code, then confirmed live): the shipper's `ServiceName` attribution regex was anchored to the literal `default` namespace, so every ADR043 `tea-<xid>` tenant access line was dropped as `not_a_tenant_app`. Fixed in `4c66473b`.

Verified 2026-08-28 by direct read-only probes of production Loki (prod kubeconfig via `scripts/fetch-app-kubeconfig.sh`; nothing deployed, modified or deleted):

- `scripts/request-logs-liveness.sh 24h` → PASS; tenant namespaces `tea-d98210cbbpdc73dcrkvg` (the hunt's own) and `tea-da2isimlm39c739m4ofg` are producing `type=request`.
- `agentmarketcap-1`: `type=request` → 5 lines/1h (was 0/24h); `label=method` → `["GET","HEAD","POST"]` and `label=status` → `["200","307","404","499","500"]` (both were `[]` from Loki's label index — the decisive evidence, now flipped); `method=GET` narrows; the `host` filter matches both values discovery offers.

**`scripts/logs-verify.sh` was deliberately not run against prod.** It deploys two fixture Apps into the live customer-serving cluster and deletes pods, and it fixtures into `APP_NS=default` — the one namespace the bug never broke — so it proves strictly less than the probes above. Its new tenant-attribution phase (t004) is the part that carries real signal, and that assertion was verified directly instead.
