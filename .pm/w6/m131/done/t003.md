## Objective

Discovery and filtering read different sources, so they can disagree permanently — and today they do. Decide whether what a surface offers as a filter value must be something the filter can actually match.

## Context

- `lego/backend/internal/logs/service.go:657-661` answers `label=host` from `app.Status.URLs`, deliberately: the code comment says `host` "is not a stream label (the cardinality budget keeps it in the line), so its values come from the App itself — which is why it resolves even with no store wired."
- `host` **filtering** is a Loki line filter over the access line's `RequestHost` (`logs/loki.go:273-286`), so it can only ever match request logs.
- Live consequence: `label=host` returns real hostnames (e.g. `["agentmarketcap-1.onbex.co","agentmarketcap.ai"]`) while a `host` filter matches nothing on any service.
- The dashboard repeats the pattern independently: with `label=method` returning `[]`, the Method dropdown still offers `GET · POST · PUT · PATCH · DELETE` from a **static fallback** list. `ADR018:182` describes these as "dropdowns fed by `logLabelValues` discovery with static fallbacks" — the fallback is intentional, but it currently presents values discovery says do not exist.
- Both halves are defensible in isolation; together they guarantee a user can pick an offered value and get nothing.

## Steps

1. Decide whether `host` discovery should reflect filterability, keep its current App-derived behaviour, or signal the difference.
2. Apply the same question to the dashboard's static Method / Status-code fallbacks: when discovery returns empty, should the fallback list still render?
3. Implement the decision and record it alongside ADR018 row 182's existing description of the fallbacks.

## Files

- `lego/backend/internal/logs/service.go` (`LogLabelValues`)
- `dashboard/src/features/logs/` (Filters popover and its fallback lists)
- `docs/ADR018-render-parity.md` (row 182)

## Acceptance criteria

- [ ] A `host` value returned by discovery, used as a `host` filter, returns rows — or discovery no longer offers values the filter cannot match, per the recorded decision.
- [ ] The static Method/Status-code fallback behaviour when discovery is empty is decided and recorded.
- [ ] `host` discovery still resolves with no store wired, or the change to that is deliberate and noted.

## Out of scope

- Making the request pipeline produce data (`t001`).

## Outcome (2026-08-28)

**`host` discovery keeps its App-derived source; the dashboard's static fallbacks are narrowed.**

- `host` stays answered from `app.Status.URLs`: it is the right answer to "which hosts does this service serve", it resolves with no store wired, and with the attribution fix the `host` line filter matches exactly those values — so a host with no traffic in the window is an ordinary honest empty, not a guaranteed one. t003's first acceptance branch.
- The static Method/Status-code/Level fallbacks now stand in for *"we could not ask"* only. Once `logLabelValues` **answers** with an empty set they are dropped, so the Filters popover no longer offers `GET·POST·PUT·PATCH·DELETE` on a service whose store says it has produced no request lines. They still carry the UI while loading and when discovery is unavailable (no store => 503).
- `useLogLabelValues` gained a sibling `useLogLabelDiscovery` returning `{values, resolved}` — the three other callers keep the plain-array hook unchanged.

Recorded in ADR018 row 182 + ADR010; covered by three new `log-filter-bar.test.tsx` cases (answered-empty drops fallbacks, unavailable keeps them, answered-with-values merges).
