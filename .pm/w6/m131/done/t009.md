## Objective

This milestone's `Unverified` section flagged the metrics consequence as "a code-read inference and its own claim; if it holds it may deserve a separate finding". **It holds, and it is more user-visible than the logs symptom this milestone was filed for:** the unfiltered request graph shows real traffic, and applying the host filter the product itself offers empties it. It lives here rather than in its own milestone because `t001`'s pipeline fix is the shared root cause — but it is a different surface, a different code path, and it needs its own DoD bullet, because m131 as filed could be closed with this still broken.

Found live 2026-08-28, 70th `/qa-find-bugs` run, journey 7 (metrics half). Read-only — nothing was created, modified or deleted.

## Context

### Live evidence — API

Service `srv-d9bkcspg9s7c73d0n8ug` (`agentmarketcap-1`, real production traffic), 1h window, `fetch` from inside the authenticated dashboard page with `credentials:'include'`:

```
GET /v1/metrics/http-requests?resource=srv-d9bkcspg9s7c73d0n8ug&startTime=<1h ago>&endTime=<now>
  -> 200   1 series, 61 points, total 24.33
GET /v1/metrics/http-requests?...&host=agentmarketcap-1.onbex.co
  -> 200   0 series,  0 points, total 0
GET /v1/metrics/http-requests?...&path=/
  -> 200   0 series,  0 points, total 0
GET /v1/metrics/http-latency?...
  -> 200   1 series, 61 points, total 137.66
GET /v1/metrics/http-latency?...&host=agentmarketcap-1.onbex.co
  -> 200   0 series,  0 points, total 0
```

Controls from the same batch: `GET /v1/metrics/cpu` unfiltered → 200, 1 series, 61 points (so the window and resource are right); `GET /v1/metrics/bandwidth?...&host=...` → `400 request contains an unsupported query parameter`, which is **correct and must stay** — bandwidth carries no per-request host/path axis.

The filtered host is the service's **own hostname**, the only host it serves, so the correct filtered answer is essentially the unfiltered one — not zero.

### Live evidence — dashboard, which is what makes this major

On `https://dashboard.bex.co/services/srv-d9bkcspg9s7c73d0n8ug/metrics` the Network Metrics card renders **"Total Requests — 38 requests"** with a 145-point bar chart, plus a "Response Times" p90 chart. The Host dropdown offers exactly:

```
All · agentmarketcap-1.onbex.co · agentmarketcap.ai
```

Selecting `agentmarketcap-1.onbex.co` changes both charts to **"No data in range"**. The dropdown offers precisely the values that empty the graph, and the empty state reads as "you had no traffic" when 38 requests were visible one click earlier.

### Root cause — the same absent stream, reached by a different path

- `lego/backend/internal/metrics/service.go:755-759` (`requestMetric`): when `q.Host != "" || q.Path != ""` the read is served from `s.RequestLogMetrics` instead of Prometheus — by design (`w5/m58`), since Traefik's Prometheus counters carry no per-request host/path axis.
- `lego/backend/internal/metrics/lokisource.go:49` (`NewLokiRequestMetricsSource`) builds that query, extracting `request_host="RequestHost"` and `request_path="RequestPath"` at `:126` from the Traefik access line.
- That access-log stream has **no data** — established exhaustively in this milestone's background: `type=request` returns 0 rows for all five services, and `label=method`/`label=statusCode` return `[]` from Loki's own label index.
- The `s.RequestLogMetrics == nil` guard only fires when the source is **unwired**. It is wired, so the query runs against an empty stream and succeeds into an empty series. `metrics/service.go:137-142` states the intent — "with the Loki source unwired they surface `core.ErrLogStoreUnavailable`, never a silently-unfiltered Prometheus result" — and that intent is met. What neither guard covers is **source wired + stream not produced**: the same gap `t002` owns, on a second surface.

### Scope

- **Not** a `w5/m58` regression. Routing host/path to the log store is correct and is not re-litigated; it simply cannot work while the stream is empty.
- The host-discovery asymmetry `t003` owns for logs reappears here verbatim and should be settled together: `ADR018:190` records that the Metrics tab's "Host values are discovered from the logs label-values read (App URLs)" — the same App-derived source as `logs/service.go:657-661`. On both surfaces the offered values come from the App while the filter matches only access-log lines.

## Outcome (2026-08-28)

**Confirmed downstream of t001's fix, and verified in production.**

The metrics read path for a host-filtered `http_requests` — `count_over_time` over `request_host` extracted from the access line, which is exactly what `requestMetric` issues when `q.Host != ""` — returns **1 series / 12 points** for `agentmarketcap-1` filtered to its own hostname, against **0 series / 0 points** at filing. The dashboard's "38 requests" → "No data in range" collapse is resolved, because the stream it reads now exists.

Code half (step 3): `requestMetric` carries an explicit note that its `RequestLogMetrics == nil` guard covers "source unwired", not "source wired but stream not produced" — that second state is deliberately unrepresented for the reason `t002` recorded, and is caught out-of-band by the scheduled liveness probe. `docs/ADR018-render-parity.md` row 190 records the shared fate with the request-log stream.

Not re-probed through the authenticated REST/GraphQL/MCP surfaces or the dashboard Host dropdown (no QA credentials); verified at the Loki layer those surfaces read from. `bandwidth` + host/path still returning its named 400 is unchanged by this milestone — no code path touched it.
