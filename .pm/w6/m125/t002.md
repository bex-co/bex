## Objective

Because the service lookup always missed, `PlanBlueprintResource`'s update branch has effectively never executed for a service in production. `t001` makes it run for the first time. Confirm what it reports is true, rather than assuming the branch is correct because it compiles.

## Context

- `lego/backend/internal/apps/blueprint_state_plan.go:148-156` — `PlanBlueprintResource`; `:150-152` is the create path, and the `BlueprintResourceService` case at `:154-156` calls `parsedBlueprintService(r.parsed, resource.Name)`.
- That call keys by `resource.Name` — the **manifest** name — so check it is not repeating `t001`'s confusion one level down, in the opposite direction.
- The live evidence to reproduce: an unchanged manifest and one differing only in `buildCommand` (`npm install` → `npm ci`) currently produce byte-identical plans. After the fix they must differ, and the difference must describe the real change.
- The documented convention for env groups (`:30-33`) is that an existing group is "conservatively an update because a no-op cannot be proved without revealing its values". Decide whether services follow the same conservative rule or can report a true no-op, and write the decision down.

## Steps

1. Re-plan the unchanged manifest and record the operation.
2. Re-plan the `npm ci` variant and confirm the plans differ.
3. Apply the changed manifest and confirm the plan predicted the outcome — same id, field updated in place, no duplicate.
4. Exercise a manifest mixing a new service with an existing one and confirm both actions are correct in the same plan.
5. Check the three error-gate call sites (`deploy.go:581`, `blueprint.go:419`, `blueprint.go:572`) still behave sensibly now that they see update actions rather than only creates.

- [ ] A changed manifest and an unchanged one produce different plans.
- [ ] The update action describes what actually changes.

- [ ] The no-op-versus-conservative-update decision is recorded.
