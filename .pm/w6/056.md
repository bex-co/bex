# 056 — Deleting an apex custom domain leaves its auto-added `www` sibling behind, silently stripped of its redirect

Why: bex creates the `www` row on the user's behalf, so a user who adds one domain and later removes it is left holding a second domain they never asked for, now pointing straight at the service instead of redirecting — and the delete confirmation never mentions the pair in either direction.

## Live repro (2026-08-27, 24th `/qa-find-bugs` run)

1. Add `qa-20260827.invalid` to a service. bex auto-adds `www.qa-20260827.invalid` with `redirectForName: "qa-20260827.invalid"` (confirmed via `GET /v1/services/<id>/custom-domains`), and the dashboard row reads "www.qa-20260827.invalid redirects here".
2. Delete the apex through the row's Actions → Delete. The confirmation reads, in full:

   > **Delete qa-20260827.invalid?** The service stops serving this domain. Its Ingress rule is removed and the TLS certificate is left to expire. This can't be undone.

   No mention of the sibling.
3. Re-read the list:

   ```
   GET /v1/services/srv-da7o6ovvqdcc73bpn9hg/custom-domains
   => [ { "name": "www.qa-20260827.invalid" } ]     ← survives, and redirectForName is now absent
   ```

   Before the delete that same row carried `"redirectForName": "qa-20260827.invalid"`. After it, the key is gone — the row changed meaning from "redirects to the apex" to "serves this service directly", without the user asking.

## Expected

Either the pair is deleted as a pair, or the surviving row's new meaning is disclosed before the delete and reflected afterwards. Silently converting a redirect into a direct-serving domain is the one outcome that should not happen — a domain the user never added is now a domain the user is serving.

## Where it sits against `w6/m30`

`w6/m30` (done, 2026-07-15) shipped the www↔apex pairing and its redirect, and its DoD says "**deleting the pairing removes the redirect cleanly**", with the outcome noting "the mock-cluster matrix verified … delete cleanup with trusted TLS". The **redirect mechanism** does go away with the apex, so that half holds. What m30's wording does not cover is the paired **claim row's** own lifecycle — and that is what leaks here. Filed as a new gap rather than a regression, because the DoD sentence is about the redirect, not the row. Whoever picks this up should re-read m30's DoD item by item before deciding which of the two it really promised.

## Fix sketch

Decide the intended semantics first, then implement one of them:

- **Cascade** — deleting either half of an auto-created pair deletes both, and the confirmation says so ("This also removes www.example.com").
- **Promote with disclosure** — the sibling survives as a direct-serving domain, but the confirmation says that explicitly and the row's own copy updates from "Redirects to …" to whatever it now is.

The auto-pairing is created in the claim path (`AddDomainClaim(ctx, appID, host, redirectForName)`, `lego/backend/internal/store/store.go:968`) — whichever branch creates the sibling is where the delete counterpart belongs. REST/GraphQL/MCP all expose `redirectForName` (per m30), so the semantics must move on all three, plus the dashboard's confirmation copy in `en` and `zh`.

## Unverified

- The reverse direction: adding `www.example.com` first (does bex auto-add the apex, and what does deleting the `www` do to it?) — not exercised this run.
- Whether a **verified** pair behaves the same as the two `pending` claims tested here; `.invalid` can never resolve, so both rows stayed `pending` throughout.
