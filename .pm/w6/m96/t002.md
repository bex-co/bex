## Objective

Close the actual coverage gap that let this ship as "done" under `w2/m62`: prove the four blueprint-id REST routes work **through the real composed server** (auth + rate limit + `renderRequestValidator`), not through the bare-mux shortcut the existing test uses. Also lock in the four id/pattern pairs that already happen to be correct today, so a future Render spec refresh can't silently reintroduce this class of bug on any of the five without failing CI.

## Context

- The existing, misleadingly-reassuring test: `internal/apps/blueprint_test.go:1365` (`TestRESTListBlueprintSyncsIncludesErrorMessage`) builds `mux := http.NewServeMux(); svc.RegisterREST(mux)` directly — this never passes through `newRenderRequestValidator`, so it could not have caught t001's bug and still won't catch a regression of it. Do not "fix" this test in place and call it done — it tests something real (error message plumbing) and should keep doing that; the new coverage is additive, through a different harness.
- `internal/api/render_openapi_test.go` already has the right harness shape to copy: `newOpenAPITestHandler` (builds a handler with the validator wired in) and `requestOpenAPITest` (fires a request through it), used by `TestRenderRequestValidatorAcceptsExtensionsAndPreservesInput` (~line 343) for exactly this "does a realistic request pass the gate" pattern — e.g. its existing webhook assertions at lines 362-380 (`GET /v1/webhooks/whk-00000000000000000000?ownerId=tea-bravo` → 204) are the template to follow for blueprints.
- Because the composed-server harness in that file appears to use a mocked/counting backend (`mutations` counter, `http.StatusNoContent` responses) rather than the real `apps.Service`, check whether it's wired to a real or fake blueprint backend before assuming a 200 body proves anything beyond "the validator let it through." If the harness can't easily exercise a full round-trip to a real blueprint through Blueprints service (fake store, etc.), it's fine to assert "validator passed it through to the inner handler" there and add a SEPARATE full-stack test (real `apps.Service` + `fakeBlueprintStore` + the validator wrapper) that proves an actual 200/403/404 comes back — don't let "the validator didn't 400" quietly stand in for "the endpoint actually works."
- Adjacent-classes requirement (from the milestone README): assert a real `blp-…` id in the caller's own workspace → 200/204 with real data; a real-shaped `blp-…` id that does not exist → 404; a real `blp-…` id belonging to a different workspace → 403 (or bex's equivalent not-found-for-non-members convention — check `AuthorizeApp`'s sibling for Blueprints in `internal/apps/blueprint.go` for which one it actually returns, and assert exactly that, don't guess). These three cases must be **distinguishable**, not all collapsing to the same status.
- Table test for the other 4 pairs: enumerate `{diskId: "dsk", webhookId: "whk", eventId: "evt", jobId: "job", blueprintId: "blp"}` against the corresponding pattern pulled from the loaded spec (or hardcode the expected patterns with a comment pointing at the spec paths, if reading them back out of `*openapi3.T` in a test is awkward) and assert each bex prefix satisfies its Render pattern. This is the guard that makes "no other kind has this bug" a checked fact forever, not a one-time grep in a PM record.

## Steps

1. Add the full-stack blueprint-id tests (see Context) covering: GET by-id (own workspace, success), GET by-id (nonexistent id, 404), GET by-id (other workspace's id, 403-or-bex's-actual-equivalent), PATCH by-id (success), DELETE by-id (success), GET .../syncs (success).
2. Add the cross-kind pattern table test.
3. Run `cd lego/backend && go test ./internal/api/... ./internal/apps/...` and confirm everything is green, including the pre-existing tests in both files (no regressions).
