## Objective

Confirm the fix reaches every resource type that can carry `spec.Image`, and resolve whether `static_site` is actually part of that family or excluded by construction.

## Context

- The reconcile path (`settleCanceledRelease`) is shared across all App-typed resources — `w6/m52` verified this shape by spot-checking two types (web service, cron job), not all five. This milestone should do the same spot-check shape for the image dimension: web + private + worker + cron are the types confirmed to offer "Existing Image" in the create flow.
- **Open question surfaced this run:** the "New Service" create form (`/services/new?type=static_site`) DOES render an "Existing Image" tab for Static Site (confirmed live), which is surprising given static sites build-and-publish to S3 rather than run a container (ADR029). Check `lego/backend/internal/apps/service.go`'s `validateTypeSpecificCreate`/`validateCreateSource` and the static-site publish pipeline to determine whether the backend actually accepts `spec.Image` for `static_site`, or silently ignores/rejects it. If it's reachable, static_site needs its own regression test here; if not (e.g. the backend 400s on the combination, or the operator's static-site codepath never looks at `spec.Image`), record that explicitly as a UI/backend mismatch worth its own follow-up note (a static site's create form offering a source kind the backend can't use is a separate, smaller finding — do not silently drop it, file a `w6/NNN.md` inbox note for it if confirmed).
