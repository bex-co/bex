## Objective

Have the used-CPU meter read agent sandboxes' pods too, recording `sandbox_cpu_seconds` for them at $0, without changing what they are billed. Memory (`sandbox_memory_gb_seconds`) is already recorded for them.

## Context

- `meterObservation` sets `UsageBilled: idleTracked(raw)`, and `idleTracked` is false for a sandbox carrying `bex.co/agent-session` (`lego/backend/internal/sandbox/meter.go`, `idle.go:174`). CPU intervals are opened only for usage-billed sandboxes.
- The CPU meter: `lego/backend/internal/sandbox/cpu_meter.go` (Prometheus `SandboxPodCPUMetric`, pod cgroup counter for `*-sandbox` namespaces, `deploy/gitops/base/prometheus.yaml`). Agent sandboxes run in `<workspace>-sandbox` too.
- November on production: `sandbox_memory_gb_seconds` rows exist for 174 agent sandboxes; `sandbox_cpu_seconds` for none.

## Steps

1. Separate "record CPU" from "billed on use" in the meter state, so agent sandboxes record CPU and keep the weighted charge.
2. Show the recorded CPU as an unbilled line, as `/v1/sandboxes` CPU before 2026-11-18 was.

## Files

- `lego/backend/internal/sandbox/meter.go`, `cpu_meter.go`, `lego/backend/internal/store/sandbox_meter.go`

## Acceptance criteria

- [x] A real-Postgres test: an agent sandbox accrues `sandbox_cpu_seconds` and its weighted charge is unchanged.
- [x] On production, a day after the deploy, agent sandboxes have `sandbox_cpu_seconds` rows.

## Progress (2026-11-23)

The code is shipped; the production check above is read with t002, a day after production carries it.

- **Premise corrected.** Memory was not recorded for agent sandboxes after 2026-11-18: `accrueSandboxInterval` stopped writing their `sandbox_memory_gb_seconds` at `sandboxUsage.billedFrom` (the `memoryEnd = billedFrom` branch), so their memory rows end at that instant. Agent memory is now recorded again, beside CPU, so t006 and w6/167 have both halves.
- **Mark per row, not per hour.** Until now a CPU or memory row was unbilled only by its hour (before `billedFrom`). Agent rows after it share kind and hour with billed `/v1/sandboxes` rows, so migration 0338 adds `usage_hourly.unbilled`. The meter sets it on an agent sandbox's CPU and memory, from the interval's and the cursor's `usage_billed`, and every read that prices, exports, settles or compacts leaves a marked row out, as it leaves out a row from before the switch. The estimate shows them as the existing `Sandbox CPU (included in compute)` and `Sandbox memory (included in compute)` lines at $0; the weighted `sandbox_compute_seconds` charge and the session's `compute_milli_seconds` are unchanged. t003 needs only the meter's side: from its instant, write agent rows unmarked and stop the weighted meter.
- **CPU meter.** An agent sandbox's running interval now opens unsettled, so the CPU meter reads its pod like any other.
- **Tests.** `TestSandboxRunningIntervalsPG` and `TestSandboxUsageSwitchPG` (real Postgres): an agent sandbox running across the switch has its CPU window read, two hours of CPU and memory marked unbilled, its two weighted hours billed, the outbox hands the export only its CPU and memory marked, settle and compaction leave them out. `TestStripeMeterEventMapping` and `TestToEventMapping`: a marked row is carried to the export and never sent. Each of eight mutations (the interval settled at open, CPU or memory written unmarked, the month-to-date read, compaction, settle or the outbox ignoring the mark, the export sending it) fails a test.
- **Production pre-check.** Production's Prometheus already keeps `sandbox_pod_cpu_usage_seconds_total` for agent sandbox pods under the name the meter reads: a `bex` workspace pod on `agent-4c-8g` ran as `<substrate id>-0` in `<workspace>-sandbox` and its series read 254.77 CPU-seconds 28 minutes after it started.
