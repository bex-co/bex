# 050 — "Projected total for `<month>`" extrapolates a Stripe subscription-period total using calendar-month elapsed time

Why: the number a user budgets against is understated roughly 2.4× on the QA workspace right now, and it is understated by construction — not by the accepted estimate-vs-rated skew — because two different time windows are divided into each other.

## What's wrong

`dashboard/src/features/usage/components/charges-card.tsx:228` picks the headline total:

```ts
const total = rated ?? categories.reduce((sum, c) => sum + c.totalUsd, 0);
```

and line 237 projects it:

```ts
const projected = isCurrentMonth ? projectMonthEnd(total, now) : null;
```

`projectMonthEnd` (`dashboard/src/features/usage/lib/charges.ts:82-89`) assumes `spentUsd` accrued **from the 1st of the calendar month**:

```ts
const start = new Date(now.getFullYear(), now.getMonth(), 1).getTime();
const end   = new Date(now.getFullYear(), now.getMonth() + 1, 1).getTime();
const elapsed = now.getTime() - start;
return (spentUsd * (end - start)) / elapsed;
```

But when `rated` is non-null the numerator is Stripe's `billing.currentCost.amountUsd`, which covers the **subscription period**, not the calendar month. Live capture (in-page authenticated `fetch`, 2026-08-27):

```
query { usage { period estimatedCost { totalUsd } billing { currentCost { amountUsd periodStart periodEnd } } } }
=> period                       = "2026-08"
   estimatedCost.totalUsd       = "79.10"
   billing.currentCost.amountUsd = "30.01"
   billing.currentCost.periodStart = "2026-08-16T00:00:00Z"
   billing.currentCost.periodEnd   = "2026-09-16T00:00:00Z"
```

So $30.01 covers Aug 16 → Aug 27 (~11 days) but is divided by the fraction of Aug 1 → Aug 27 (~26 days) elapsed. The page rendered **"Projected total for August $36.07"**; a period-correct projection from the same $30.01 is ~$84. The card also sits directly above a charge tree summing to $79.10, so the projection reads as lower than what is already shown accrued.

## Not the already-accepted skew

`w6/m98/done/t007.md` explicitly triaged the *tree-vs-total gap* as expected ADR040 seal-window behavior and asked future hunts not to re-file it. That disposition stands and this note does not reopen it. This is a different defect: even granting that `rated` and the tree legitimately differ, `projectMonthEnd`'s arithmetic is wrong regardless, because it divides a subscription-period numerator by a calendar-month denominator. t007's analysis attributed the whole gap to meter-emission lag and never noticed that the two figures also cover different windows.

## Fix sketch

`billing.currentCost.periodStart`/`periodEnd` are already selected by the `Usage` query (`dashboard/src/features/usage/api/usage.graphql:48-49`) but are not passed into `ChargesCard`. Thread them through and project over the window the total actually covers; when the total falls back to the category sum (`rated == null`), the calendar month is the right window and today's math is already correct — so the fix is window-aware, not a formula swap. Decide explicitly what a subscription period spanning two calendar months should even be labelled — "Projected total for August" may be the wrong sentence, not just the wrong number.

## Repro

1. Sign in to `https://dashboard.bex.co/billing` on a workspace whose Stripe subscription period does not start on the 1st.
2. Read "Projected total for `<month>`" and compare it with the Charges tree's own subtotals directly above it.
3. Confirm the window mismatch with the `Usage` GraphQL probe above.
