## Objective

`build_ended` is not only a UI row — it reaches outbound webhooks and push notifications. Confirm a subscriber now receives a closed pair for a canceled deploy, and that the new emission does not double-fire.

## Context

- Lifecycle facts reach the Events tab and outbound **webhooks** via the `factEvents` map (`lego/backend/internal/webhooks/service.go`), and a subset also reach **push notifications** via `projectedPush` (`lego/backend/internal/notifications/push_worker.go`). Push is **selective, not universal**: `push_worker.go:661-667` deliberately drops `service_hibernated`/`service_woken` (w6/m47). So this task must confirm `build_ended(canceled)` is actually in the pushed set, not assume it — the webhook path is the broad one, push is opt-in per type.
- **This was never observed during the hunt** — no webhook was subscribed. So this task must actually exercise the path rather than inherit the claim.
- The risk specific to `t001` is duplication: the fact is now emitted from a second place, so a subscriber could receive `build_ended` twice if the `source_key` idempotency does not hold across the two paths.

## Steps

1. Subscribe a webhook endpoint in the QA workspace.
2. Run the canceled-mid-build fixture and capture what the endpoint receives.
3. Assert exactly one `build_started` and exactly one `build_ended` for the canceled deploy.
4. Check the push-notification path carries the same, or record why it legitimately differs.
5. Remove the webhook subscription afterwards.

## Files

- No production code expected; this validates `t001`. If a gap appears, it is its own finding.

## Acceptance criteria

- [ ] A subscriber receives both halves for a canceled deploy, each exactly once.
- [ ] The successful and build-failed paths still deliver exactly one `build_ended` each.
- [ ] The webhook fixture is removed.

## Out of scope

- Broader webhook-delivery work; this task only asks whether these two facts arrive correctly.
