## Definition of done

On **production** (`https://dashboard.bex.co` / `api.bex.co`), for a disk-bearing paid service:

- The GraphQL query `diskSnapshots(id: "<dsk-id>")` returns `{"data":{"diskSnapshots":[...]}, "errors": null}` — no top-level GraphQL error — even for a disk with zero snapshots yet (an empty array, not an error). Re-run the exact probe this hunt captured: `query DiskSnapshots($id: String!) { diskSnapshots(id: $id) { createdAt snapshotKey instanceId } }` against a real disk id, and confirm it no longer returns `{"errors":[{"message":"internal error","path":["diskSnapshots"]}]}`.
- The dashboard's Disk → Snapshots card (`dashboard/src/features/services/components/disk-section.tsx`'s `SnapshotsCard`) renders either the honest empty state ("No snapshots yet") or a real snapshot list — never the generic "Snapshots are unavailable / internal error" state — for this correctly configured production deployment.
- At least one real snapshot object exists under the disk's bucket prefix (via the operator's nightly CronJob or a manually triggered run) and is listed identically by `GET /v1/disks/{diskId}/snapshots` (REST), the `diskSnapshots` GraphQL query, and the `list_disk_snapshots` MCP tool.
- A restore-from-snapshot round trip on a scratch disk returns the pre-snapshot bytes (mirrors the sequence `w1/m87`'s own t004 ran, but against production instead of the CAPD cluster).
- Deleting the disk purges its snapshot objects (the bucket listing for that prefix goes to zero).
- The two failure modes stay distinguishable in server logs: "feature not configured" (`DISK_SNAPSHOTS_NOT_CONFIGURED`) vs. a genuine, ongoing S3-layer failure — an on-call engineer reading `bex-api` logs can tell them apart without guessing which secret or region is wrong.

## Source + Goal linkage

- **Source:** live QA hunt of `https://dashboard.bex.co`, 2026-08-26 (this session). Created a real Starter-tier Existing-Image service (`srv-da7b0bnkh5kc73fbq5t0`, deleted after the hunt), attached a 10 GB disk at `/var/data` (`dsk-da7b0lapjh2s73adl6dg`, deleted after the hunt), and opened its Disk tab. The Snapshots card showed "Snapshots are unavailable / internal error" on a fresh page load, reproduced twice. Captured the raw GraphQL exchange directly from the browser's network log:
  - Request: `operationName: "DiskSnapshots"`, `variables: {"id":"dsk-da7b0lapjh2s73adl6dg"}`, query `query DiskSnapshots($id: String!) { diskSnapshots(id: $id) { createdAt snapshotKey instanceId __typename } }`.
  - Response: `{"data":{"diskSnapshots":null},"errors":[{"message":"internal error","locations":[{"line":2,"column":3}],"path":["diskSnapshots"]}]}`.
  - Screenshot: `.playwright-mcp/qa-disk-1-snapshots-internal-error.png`.
- **Root cause (traced, not fully diagnosed — see t001):** `lego/backend/internal/apps/disk_snapshots.go`'s `ListDiskSnapshots` (line 105) returns the CodedError `errDiskSnapshotsNotConfigured()` (line 89, `DISK_SNAPSHOTS_NOT_CONFIGURED`, public/un-sanitized) only when `s.DiskSnapshots == nil || len(s.SnapshotSecret) == 0` — i.e. when the deployment never wired the feature. Getting the generic "internal error" instead means the feature **is** wired (`s.DiskSnapshots` is non-nil) but the actual S3 call — `S3Origin`-equivalent `ListSnapshots` in `NewS3DiskSnapshotLister` (line 346) hitting Wasabi at `s3.eu-central-2.wasabisys.com`/`bex-disk-snapshots` (`lego/operator/config/manager/manager.yaml:279-298`, `lego/operator/config/api/deployment.yaml:465-500`) — returned an error `isNotFound`-style classification never recognizes (unlike `s3origin.go`'s `isNotFound`, `disk_snapshots.go` has no not-found carve-out at all; `fmt.Errorf("list snapshots: %w", err)` at line 115 always falls through to `sanitizeGraphQLErrors`'s generic "internal error" via `core.IsPublicError`, `lego/backend/internal/api/server.go:1259-1270`). The exact upstream cause (wrong region on the **read** secret, wrong bucket, expired/rotated credential, or a genuine outage) is unconfirmed — that's t001.
- **This is a regression against `w1/m87`** (`.pm/w1/done/m87/README.md`, done 2026-08-25), whose own Definition of Done requires this to work "on production" and whose own code comment (`lego/backend/internal/core/errors.go:298-310`, `NewUnavailableError`) names this exact failure mode as the thing it fixed: _"a sanitized message ('internal error') tells the tenant their service is broken when nothing is (w1/m87/t005 — this is exactly what the Disk tab's Snapshots card did on production, 2026-08-24)."_ The dashboard-side fix (t005, distinguishing "not configured" from "a real outage" via the `DISK_SNAPSHOTS_NOT_CONFIGURED` code) is **still correct and not regressed** — verified this run that the card does show the distinct "Snapshots are unavailable" title, not the old bare crash. What regressed (or was never actually true) is the **production infrastructure**: `m87`'s own progress notes record its end-to-end drill (t004) as run "on the CAPD cluster" — a local kind dev cluster — not the real Hetzner cluster serving `dashboard.bex.co`, even though the milestone's Definition of Done and its "arm ADR082 snapshots" commit (`c194333d`) describe provisioning real Wasabi credentials. Walking `w1/m87`'s DoD item by item against this run: "GET /v1/disks/{diskId}/snapshots lists it" — **fails** on production (this finding); "a restore on a scratch disk returns the pre-snapshot bytes" and "deleting that disk purges its objects" — **unverified this run** (no existing snapshot to restore from, and creating one requires either waiting for the nightly CronJob or triggering it manually, which this hunt did not have cluster access to do); "The Snapshots card never renders 'internal error' for an unconfigured store, and a genuine failure stays visibly distinct from 'never configured'" — **holds** (dashboard side correct), but a genuine failure IS occurring in production right now, which the milestone's own record treats as a closed, non-recurring risk.
- **Goal linkage:** [docs/ADR082-persistent-disks.md](../../../docs/ADR082-persistent-disks.md) D5 (snapshot promise) and [docs/ADR018-render-parity.md](../../../docs/ADR018-render-parity.md) ledger truthfulness — the disk row claims daily snapshots with 7-day retention; that is currently false of the running production system for at least one real disk.
- **Expected outcome:** a tenant who attaches a disk on production actually gets backups they can list and restore, matching what render.com's own Disks feature promises and what bex bills $0.175/GB/month for.
- **Why now:** disks are a paid feature already live and billing on production (Pro-plan-and-up); every hour this stays broken is an hour a paying tenant's disk has no working recovery path if their disk-bearing service corrupts its own data. The mechanism is freshly understood (this session traced it to file:line), which makes the fix cheap now and more expensive to re-derive later.
- **Render parity — included** (t005): the disk-snapshot verb is a REST + GraphQL + MCP surface (`/v1/disks/{diskId}/snapshots`, `diskSnapshots`, `list_disk_snapshots`); confirm all three agree once the production fix lands, and confirm the dashboard's existing not-configured/real-outage distinction (`disk-section.tsx`) is unaffected.

- The exact upstream S3/Wasabi failure mode (wrong region on the read secret vs. wrong bucket vs. expired credential vs. a genuine Wasabi-side outage) — traced to "the S3 call fails with something `isNotFound`-equivalent logic never classifies," not further, because this hunt has no access to production `bex-api` logs or the `bex-disk-snapshot-read` Secret's actual contents.
