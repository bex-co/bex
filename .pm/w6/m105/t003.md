## Objective

Independent of the production fix (t002), close the code-level gap: today `ListDiskSnapshots` has exactly
two outcomes — success, or a blanket "internal error" for anything that isn't the specific
`s.DiskSnapshots == nil` not-configured case. A genuine, ongoing S3-layer failure (bad credential, wrong
region, bucket gone) should be classified distinctly from a one-off transient blip, and from
"never configured," so an operator reading logs or a future dashboard iteration can tell them apart.

## Context

- `lego/backend/internal/apps/disk_snapshots.go:113-116`: `s.DiskSnapshots.ListSnapshots(...)` errors are
  wrapped with bare `fmt.Errorf("list snapshots: %w", err)` and nothing else — no `CodedError`, so
  `core.IsPublicError` (`lego/backend/internal/core/http.go:294`) rejects it and
  `sanitizeGraphQLErrors`/`WriteErr` both flatten it to "internal error."
- `lego/operator/internal/staticserver/s3origin.go:121-135`'s `isNotFound` is the sibling pattern this
  package should follow for its own S3 error triage (though that one only distinguishes not-found; this
  task is about distinguishing "backend broken" from "not configured," not adding a not-found case here —
  a missing prefix legitimately means zero snapshots, not an error).
- Do NOT invent a new not-found semantic for an empty listing — `ListObjectsV2` on an empty/non-existent
  prefix returns zero objects successfully, not an error; the loop at `disk_snapshots.go:117-131` already
  handles that correctly (empty `views` slice). This task is only about the case where the S3 call itself
  errors.

## Steps

1. Add a `CodedError` (e.g. `DISK_SNAPSHOTS_UNAVAILABLE`, `core.NewUnavailableError`-shaped but wrapping a
   distinct code from `DISK_SNAPSHOTS_NOT_CONFIGURED`) for the case where `s.DiskSnapshots` is configured
   but the S3 call itself fails — so REST/GraphQL/MCP all carry a stable code a client can branch on,
   matching the existing `DISK_SNAPSHOTS_NOT_CONFIGURED` pattern.
2. Keep the raw error logged server-side (as today) — the new code changes only what crosses the trust
   boundary, not what an on-call engineer can see in logs.
3. Decide (and document in this task's closeout) whether the dashboard's `SnapshotsCard`
   (`dashboard/src/features/services/components/disk-section.tsx:582-587`) should show a different message
   for this new code vs. the generic `error.message` fallback it uses today — at minimum confirm the
   existing fallback (`title={t("services.diskSnapshotsUnavailableTitle")}, body={error.message}`) does not
   regress; a nicer body copy is a bonus, not required for this task's acceptance.
4. Add a unit test on `ListDiskSnapshots` with a fake `DiskSnapshotLister` that returns a raw (non-coded)
   error, asserting the new code is present in the returned error's `Extensions()`/`Code`.
