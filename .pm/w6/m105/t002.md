## Objective

Correct whatever t001 identified — re-provision or rotate the `bex-disk-snapshot-read` (and, if the
write side is also implicated, `bex-disk-snapshot`) Secret against the real production Wasabi account, and
confirm the fix from outside bex-api (a raw S3 call), not just by re-reading config.

## Context

- `scripts/disk-snapshot-secret.sh provision` / `install` is the existing, tested provisioner
  (`scripts/disk-snapshot-secret.test.sh`, 22 CI-wired guards) — reuse it rather than hand-editing
  Secrets, so the two-identity separation (operator writes+deletes, bex-api only lists) stays intact.
- If t001 found a region/endpoint mismatch instead of a bad credential, the fix is a config value change
  in the `bex-disk-snapshot-read` Secret (or the deployment manifest default), not a rotation.
- `docs/runbooks/disk-snapshot-setup.md` has the rollback procedure if a rotation goes wrong — the age
  keypair rotation hazard in particular (rotating without keeping the old key makes existing snapshots
  permanently unreadable) does not apply here since t002 only touches the read-side S3 credential, not the
  age keypair — confirm this task does not touch `BEX_DISK_SNAPSHOT_AGE_SECRET`.

## Steps

1. Apply the fix identified in t001 (re-provision credential, fix region/endpoint, or escalate if it's a
   genuine Wasabi-side outage with no client-side fix).
2. Redeploy bex-api so the corrected Secret is picked up (a Secret value change alone does not restart
   pods that already read it into env — confirm whether a rollout restart is needed).
3. Re-run the exact failing probe from this hunt (GraphQL `diskSnapshots(id: "<a real dsk- id>")`) and
   confirm it returns `{"data":{"diskSnapshots":[]},"errors":null}` (empty list, no error) for a disk with
   no snapshots yet.
