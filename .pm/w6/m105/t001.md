## Objective

Find the exact reason `ListDiskSnapshots` fails on production with an unclassified error (surfaced to
clients as generic "internal error") instead of either succeeding or returning the coded
`DISK_SNAPSHOTS_NOT_CONFIGURED` refusal.

## Context

- Reproduced live on `https://dashboard.bex.co` 2026-08-26: GraphQL `diskSnapshots(id: "dsk-…")` on a
  freshly created disk returned `{"data":{"diskSnapshots":null},"errors":[{"message":"internal
  error","path":["diskSnapshots"]}]}`.
- `lego/backend/internal/apps/disk_snapshots.go:105-116` (`ListDiskSnapshots`): the
  `DISK_SNAPSHOTS_NOT_CONFIGURED` branch only fires when `s.DiskSnapshots == nil ||
  len(s.SnapshotSecret) == 0`. Getting "internal error" instead means the feature IS wired but the
  underlying `s.DiskSnapshots.ListSnapshots(ctx, prefix)` call (line 113,
  `S3DiskSnapshotLister.ListSnapshots` at `disk_snapshots.go:364`) returned an error that isn't
  `ErrNotFound`/`ErrObjectTooLarge`/`ErrOverloaded` — i.e. a raw, unclassified S3 SDK error.
- Production config: `lego/operator/config/api/deployment.yaml:465-500` wires
  `BEX_DISK_SNAPSHOT_ENDPOINT`/`_BUCKET`/`_REGION`/`_PREFIX`/`_ACCESS_KEY`/`_SECRET_KEY` from the
  `bex-disk-snapshot-read` Secret (all `optional: true`); `lego/operator/config/manager/manager.yaml:279-298`
  is the operator's write-side config pointing at `https://s3.eu-central-2.wasabisys.com` /
  `bex-disk-snapshots` / region `eu-central-2`.
- `w1/m87`'s own progress notes (`.pm/w1/done/m87/README.md`) record its end-to-end drill as run "on the
  CAPD cluster" (a local kind dev cluster), not the real Hetzner production cluster — so the production
  `bex-disk-snapshot-read` Secret may never have actually been verified against the real Wasabi account,
  despite the milestone's "arm ADR082 snapshots" commit (`c194333d`) describing the provisioning script.

## Steps

1. Check whether the `bex-disk-snapshot-read` Secret exists in the production `bex-system` namespace and
   whether its keys (`BEX_DISK_SNAPSHOT_ENDPOINT`/`_BUCKET`/`_REGION`/`_ACCESS_KEY`/`_SECRET_KEY`) are
   non-empty and internally consistent (region matches the endpoint's `s3.<region>.wasabisys.com` host).
2. Run `scripts/disk-snapshot-secret.sh verify` (or the closest equivalent read-side check it offers)
   against production credentials to confirm the two-identity separation still holds and the read
   identity can actually `ListObjectsV2`/`GetObject` on `bex-disk-snapshots`.
3. If credentials look right, reproduce the exact failing call locally (a small Go snippet or `aws-cli`
   invocation with path-style addressing against the same endpoint/bucket/region/prefix) to capture the
   real AWS SDK error text — region mismatch (`PermanentRedirect`), `AccessDenied`, `NoSuchBucket`, or a
   Wasabi-side outage all look different once unwrapped.
4. Check bex-api's own logs (`log.Printf("bex-api graphql: internal error: %v", resolverErr)` at
   `lego/backend/internal/api/server.go:1266`) if production log access is available this session; that
   line prints the real, unsanitized error server-side even though the client only sees "internal error".
5. Record which of the four hypotheses (wrong region, wrong bucket, expired/rotated credential, genuine
   outage) is confirmed, with the literal error text as evidence.
