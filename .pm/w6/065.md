# 065 — The Metrics time range (and both datastore log viewers') is lost on reload and cannot be shared; the service Logs page persists its own

Why: the shared range module is written for URL persistence and one of the four surfaces uses it, so a custom absolute window a user just spent a minute entering survives on the Logs page and evaporates everywhere else.

Filed 2026-08-27, 52nd `/qa-find-bugs` run, journey 7 (Metrics). Read-only throughout — nothing created, modified or deleted.

## Live repro

On `beancount-forum` (`srv-d9nqg9dcavls73fp8m2g`), `/services/<id>/metrics`:

1. The `Time range` combobox offers `Last 30 minutes … Last 30 days` plus `Custom…`. Default is `Last 12 hours`.
2. Pick **Last 30 days** → the combobox reads `Last 30 days` and the charts redraw (`Line chart with 13 data points`, down from `145`). **The URL does not change**: `https://dashboard.bex.co/services/srv-d9nqg9dcavls73fp8m2g/metrics`, no query string.
3. Reload → combobox is back to `Last 12 hours`, charts back to `145 data points`.

The same URL therefore renders a different view depending on what the previous visitor clicked, and a metrics view cannot be linked to a teammate.

## The inconsistency, enumerated

`grep -rn "useState<RangeSelection>" dashboard/src --include="*.tsx" | grep -v test` returns **exactly 3** surfaces that keep the range in component state only:

| surface | file:line |
| --- | --- |
| Service **Metrics** | `dashboard/src/routes/services.$serviceId.metrics.tsx:38` |
| **Postgres** log viewer | `dashboard/src/features/databases/components/postgres-log-viewer.tsx:28` |
| **Key Value** log viewer | `dashboard/src/features/keyvalue/components/key-value-log-viewer.tsx:28` |

Against **1** that persists to the URL: the service **Logs** page, via `dashboard/src/features/logs/lib/log-search.ts` — which reads `search.range`, a Render-compatible alias `search.r` (`RENDER_RANGE_ALIASES`, `:86`), and `search.rangeStart`/`rangeEnd` for custom windows (`:105`, `:140`).

So it is not "metrics behaves differently from logs" — **two of the three log surfaces don't persist either**, which is the sharper statement and the one a fix should be scoped against.

## Root cause

The capability exists and is documented for exactly this: `dashboard/src/features/metrics/lib/range.ts` exports `parseRangePreset` — _"Returns the supported relative range named by a **URL value**, or null"_ — and `parseCustomRange` — _"Reconstructs a stored custom range from ISO start/end"_. Both are consumed by `log-search.ts`; the metrics route never reads the URL at all (no `validateSearch`, no `useSearch`), it just initialises `useState(DEFAULT_RANGE_PRESET)`.

Nothing in the metrics route comments says the range is deliberately session-scoped, so this reads as three surfaces that were built before the persistence pattern existed, or beside it, rather than as a decision.

## Fix

Reuse the pattern that already works: give the three surfaces a URL search-param schema in the shape `log-search.ts` uses (`range`, plus `rangeStart`/`rangeEnd` for custom), and read it through the existing `parseRangePreset`/`parseCustomRange` helpers rather than a fourth spelling. The `r` Render alias is a Logs-specific compatibility shim and need not spread.

Note the datastore log viewers are components, not routes, so their persistence has to come from whichever route hosts them — that is the only part of this that is not a copy of the Logs page.

## Estimate

~1h: one search-param schema reused across three surfaces, plus tests asserting a picked range survives a reload.

## Checked, and NOT bugs — recorded so the next hunt does not re-investigate journey 7's Metrics half

The rest of the surface is in good shape and this run verified it:

- **Ranges shift correctly.** `GET /v1/metrics/cpu?resource=…&startTime=…&endTime=…` returned 31 / 361 / 1441 points for 30m / 6h / 24h, with `first`/`last` timestamps matching the requested window exactly.
- **The over-wide-window guard is a model error message.** A 30-day window with no `resolutionSeconds` returns `400 bad request: window ÷ resolution yields 43200 samples per series; the limit is 11000 — raise resolutionSeconds` — it names the computed value, the limit, and the remedy.
- **No UI path can trigger that 400.** Every entry in `RANGE_PRESETS` (`metrics/lib/range.ts:16-26`) pairs its span with a resolution yielding ~120 points (30m/15, 1h/30, 4h/120, 12h/300, 24h/720, 2d/1440, 7d/5040, 14d/10080, 30d/21600), and custom windows go through `resolutionForSpan(span) = max(1, round(span/120))` with a `MAX_CUSTOM_RANGE_HOURS = 720` client guard that matches `BEX_MAX_QUERY_HOURS`.
- **A 30-day chart showing ~3 days of data is retention, reported honestly.** `deploy/gitops/base/prometheus.yaml:128` sets `retention: 3d`. Probed the boundary: 72h returns a full 73 points; 96h returns 78 starting at `2026-08-24T12:23Z`; 720h returns 13 starting at `2026-08-24T17:23Z`. The API returns what is retained with correct timestamps rather than padding, and `range.ts`'s own comment documents this as deliberate — _"Ranges beyond Prometheus's retention simply show the retained window — same as Render past its own horizon."_
- **`?range=30d` in the URL being ignored was my own bad input**, not a deep-link bug — the metrics route has no search-param schema at all, which is what this note is about.

## Unverified

- Whether render.com persists its metrics range in the URL. Not checked; the argument here rests on bex's own internal inconsistency and on the helpers' documented intent, not on parity.
- Whether the 3-day Prometheus retention is intended to stay that short given the UI offers a 30-day range — a capacity question (`retention: 3d` on an 8Gi PV), not a defect, and out of scope for this note.
