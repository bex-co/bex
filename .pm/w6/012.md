## Note

w6/m14 gave **writes** a membership-checked workspace target (`ownerId` → `core.WithWorkspace` → `core.Base`). Three read/bind surfaces still resolve the caller's workspace implicitly through `Base.Tenant(ctx)` and so, for a multi-workspace caller, answer for their **default** workspace only:

- **usage** (`usage/service.go:118`) — `GET /v1/usage`, GraphQL `usage`, MCP `get_usage`.
- **api-keys** (`apikeys/service.go:107`) — list scoping and, more importantly, which workspace a newly minted key **binds** to.
- **GitHub connections** (`github/service.go:79`).

They already inherit m14's override for free (they call `Base.Tenant`, which honors it) — what is missing is the **adapter plumbing**: a REST `ownerId` query/body param, a GraphQL arg, and the MCP `core.SelectedWorkspace` precedence, plus the dashboard threading `currentWorkspaceId` into the usage and API-keys pages. Also: `dashboard/src/features/team/hooks/use-current-workspace.ts` returns `workspaces[0]` (the account's FIRST workspace, not the switcher's) and `team-panel.tsx` still uses it — the same class of bug m14/t006 fixed in the audit log.

**Render-consistency:** Render has no usage API and its keys are user-scoped/dashboard-only, so both are bex extensions — the target is Render's `ownerId` *vocabulary* plus bex's own cross-surface consistency, not a Render shape. Whether Render binds GitHub-App installs at user or workspace level is unverified.

**Source:** surfaced while implementing w6/m14 (2026-07-13) — not from a `/pm-brainstorm` pass. Sized at roughly one 45m backend task + one 30m dashboard task; promote with `/pm` when it comes up.
