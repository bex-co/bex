## Objective

Make App deletion purge the same path the write path used. `apps.Service.Delete` passes `a.Name` to `PurgeApp`, but a store-managed App's `metadata.name` is the tenant-prefixed `CRName(tenant, publicName)`, while the live secrets live under the public `LabelServiceName` — so purge deletes `services/<tenant>-<name>/` and leaves `services/<name>/` behind, leaking the prior tenant's values on name recreation (codex-security #15, medium).

## Context

- `lego/backend/internal/apps/service.go` Delete (~:1843/:1875) calls `PurgeApp(ctx, a.Name)`.
- `lego/backend/internal/secrets/purger.go:73-77` — `PurgeApp` passes the name straight into `envPath(name)`/`filesPath(name)` with no `storeServiceName` resolution, unlike every read/write verb.
- `lego/backend/internal/core/base.go:820` — `CRName` = `tenant+"-"+name`.
- After t001 the path is also tenant-scoped, so purge must resolve **both** the public name (via `storeServiceName`) and the tenant.

## Steps

1. Change `PurgeApp` to accept the App CR (or its `LabelServiceName` + tenant label) instead of a bare name, and resolve the storage identity the same way the write path does.
2. Update `apps.Service.Delete` to pass the resolved identity.
3. Confirm the fake-backed `PurgeApp` test still asserts "deletes exactly the supplied path" against the new resolved path.

## Files

- `lego/backend/internal/secrets/purger.go`
- `lego/backend/internal/apps/service.go`

## Acceptance criteria

- [ ] Deleting a store-managed App removes the path its env/secret-files were actually written to.
- [ ] A same-public-name recreation does not surface the deleted App's secret material.
