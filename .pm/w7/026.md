# `BEX_BASE_DOMAIN` is two independent env vars that must agree, and nothing checks

**Source:** found by `w7/m78/t001` (2026-08-09) while root-causing the missing-Ingress symptom.

The platform hosting suffix is read by **three** separately-configured Deployments:

- the **operator** (`config/manager/manager.yaml`) — decides whether `EffectiveHosts` yields a platform host, i.e. whether an Ingress is created at all;
- **bex-api** (`config/api/deployment.yaml`) — decides whether `pendingPublicURL` can report a URL before the first successful deploy (w5/m48);
- the **static-server** (`config/staticserver/deployment.yaml`) — resolves host → site.

They are conceptually one setting. Nothing enforces that they agree, and CLAUDE.md actively documents them as movable apart: bex-api's entry says "keep unset **until the operator's shared-hosting PSL gate accepts the same value**". Today all three are unset, so they agree by coincidence.

**The failure mode when they diverge is silent and confusing in both directions:**

- operator set, bex-api unset → services route correctly, but the API reports `url: null` for every service that has not yet reached Running (the w5/m48 "show the URL from creation" behavior is inert). This is the state the guidance above literally prescribes as an intermediate step.
- operator unset, bex-api set → the API advertises a platform URL that nothing serves.

**Also worth noting while here:** the static-server carries an explicit `BEX_BASE_DOMAIN: ""` as an SSA tombstone ("for production Deployments that previously carried the unsafe onbex.co value"), while the operator and bex-api rely on the field simply being **absent** from their manifests. Absence removes a previously-set value only if the same field manager owns it; an explicit empty value is unconditional. That asymmetry is either deliberate and undocumented, or an oversight — worth confirming against the live Deployments, since the whole `w7/m54` security decision rests on the value actually being gone everywhere.

**Candidate fixes** (either is small):

- Derive all three from one source — a ConfigMap the three Deployments consume — so they cannot drift.
- Or add a `gitops-validate.sh` structural guard asserting the three render identically, in the spirit of the existing platform-shape guards.

**Sizing:** likely sub-hour either way, so an inbox note rather than a milestone. Promote if the live check shows the values already disagree in production.

**First step regardless — needs cluster access:**

```
kubectl -n bex-system get deploy bex-controller-manager bex-api \
  -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.template.spec.containers[0].env[?(@.name=="BEX_BASE_DOMAIN")].value}{"\n"}{end}'
```
