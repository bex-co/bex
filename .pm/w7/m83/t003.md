## Objective

Put the BuildKit prewarm DaemonSet back on the nodes that actually run builds, and add a guard so the next taint does not silently strand it again.

## Context

- **Measured on hetzner-prod 2026-08-17:** `build-image-prewarm` reports `DESIRED 2 / READY 2`, and both pods sit on `bex-tenant-0-*` — the **serving** nodes. `bex-tenant-lg-4wvlk-s5z8z`, the only node that runs builds, has no prewarm pod.
- Cause: `deploy/gitops/base/build-image-prewarm.yaml` sets `nodeSelector: bex.co/pool=tenant` and carries **no `tolerations` block**. ADR060 D8 (2026-08-15) registered `bex.co/build-only=true:NoSchedule` on `bex-tenant-lg` / `bex-tenant-burst`; both still carry the `bex.co/pool=tenant` label, so the selector matches but the taint is not tolerated.
- **Scope is narrower than it first looks:** the live build's events showed `Container image ... already present on machine`, because the lg node has been up since 2026-08-16 and kubelet's own image cache covers warm nodes. The defect bites on **cold** nodes — a burst scale-from-zero, or lg being replaced — which is exactly when a build is most latency-sensitive. The original evidence for this DaemonSet (`w1/030`) was a ~2-minute silent `ContainerCreating` window on a cold node.
- `egress-meter` (`lego/operator/config/egress-meter/daemonset.yaml:31`) is the sibling case, but its exclusion is probably **correct** — build nodes host no serving Apps. That decision is inbox note `029`, not this task.

## Steps

1. Add the `bex.co/build-only=true:NoSchedule` toleration to `build-image-prewarm`.
2. Add a fail-closed guard to the gitops validation path: every MachineDeployment registering the build taint must have a matching prewarm toleration.
3. Give the guard a red/green self-test (the `w7/m58` universal-guard and `w7/m65` pinning-guard shape).
4. Confirm the image ref still matches `build.go`'s `defaultBuildkitImage` — the file's own header warns that a drifted ref silently warms the wrong image.
