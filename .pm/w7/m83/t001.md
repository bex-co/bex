## Objective

Emit the one build series the platform does not have: how long a build waits between admission and its pod being scheduled. ADR060 D5 calls this "the capacity/platform signal", and its absence is why every incident in this class has presented as silence.

## Context

- `w2/m72` already shipped `bex_build_outcomes_total{outcome}` and `bex_build_run_seconds` in `lego/operator/internal/controller/build_metrics.go` — extend that file, do not start a second metrics surface.
- **Queue time is the platform's SLI; run time is mostly the tenant's.** Conflating them was the 2026-08-11 misattribution, where a build sat `Pending` 22 minutes and the deploy was failed by the control-plane gate while the build itself was healthy.
- Admission timestamp: the build Job's creation. Scheduled timestamp: the pod's `PodScheduled` condition transition. Both are observable from the operator's existing watches.
- Metrics land on the manager's existing metrics endpoint.

## Steps

1. Add `bex_build_queue_seconds` (histogram): Job admission → build pod scheduled.
2. Add `bex_builds_active` and `bex_builds_queued` gauges for the live admission picture.
3. Pick bucket boundaries that resolve both the healthy case (seconds, warm node) and the pathological one (tens of minutes, cold scale-from-zero) — justify them in a comment rather than copying a default.
4. Make sure a restart does not double-count or strand a gauge (the observation path is non-blocking since D1/`w2/m72`).

## Acceptance criteria

- [ ] `bex_build_queue_seconds` distinguishes a warm-node build (seconds) from a cold scale-from-zero (minutes) in its buckets.

- [ ] An operator restart does not corrupt the gauges.
