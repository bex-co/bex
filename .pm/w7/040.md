# 040 — A migrated managed Postgres silently stops backing up, and deleting the old one would erase the new one's archive

Why: both halves are fixed and prod is mitigated, but retiring the old default-namespace instances (runbook Step 9) is still held for the agreed soak — this note is the record of why that retirement is now safe with respect to the archive collision.

**Live production defect, silent, found by executing it.** 2026-08-21, while finishing `w7/m77`'s datastore cutover on hetzner-prod. Both halves fixed in the repo; production mitigated in place.

## How it surfaced

`w7/m77` moves each tenant datastore from the shared `default` namespace into its workspace namespace, keeping the CR name — that is what makes it a move rather than a new database. After all three forum databases were cut over and serving, their CNPG clusters read:

```
ContinuousArchiving=False/ContinuousArchivingFailing
  barman-cloud-check-wal-archive:
  ERROR: WAL archive check failed for server dpg-d9nqg95cavls73fp8m20: Expected empty archive
```

Three production databases were running with **zero archived WAL and no base backup**, while every signal anyone looks at stayed green: `Database` phase `Ready`, CNPG `Ready`, the `ScheduledBackup`s present, the sites serving 200. WAL accumulated instead — 1.3 GB, 913 MB and 353 MB against 9.8 GB volumes, so this had a countdown attached.

## Root cause — one line, two consequences

The barman archive identity is derived from the CR name alone:

```go
current = db.Status.BackupServerName
if current == "" {
    current = db.Name          // <- no namespace
}
```

A `Database` name is unique only **within a workspace**. Two namespaces holding the same name therefore resolve to one archive prefix under the shared destination, and that single fact produces two distinct defects:

**1. The migrated database never backs up.** barman refuses to archive into an occupied prefix — `Expected empty archive`. It fails _closed_, so nothing was corrupted, but nothing was written either. Any bex migration that preserves the CR name hits this, which is exactly what the namespace cutover is.

**2. Deleting the old database would erase the new one's archive.** The delete-time purge Job walks prefixes, not objects, keyed on the bare name:

```sh
for suffix in '' -pg13 … -pg18; do
  aws s3 rm "${DESTINATION}/${DATABASE}${suffix}/" --recursive …
done
```

Retiring the old `default/dpg-X` — the last step of the very runbook that creates the collision — would have recursively deleted `dpg-X*`, which is also the live tenant database's archive. Here it happened to be empty because of defect 1. Had archiving worked, the runbook's final step would have destroyed the surviving database's backups.

Note the shape: defect 1 masked defect 2. The failure that looked like the problem was the only reason the worse one did no damage.

## Why nothing caught it

`Database` readiness is provisioning state, not backup state. `bex_datastore_ready` (added in `w7/036`) reports `Ready` for a database archiving nothing, and `w7/039` had just established that a green `Backup` row is not proof of a restorable archive — this is the same lesson from the other end: a green _cluster_ is not proof of a _backup_. No test covered two Databases sharing a name across namespaces, because before ADR043 there was only one namespace.

## Fix

Namespace-scope the archive identity, extending [ADR074](../../docs/ADR074-workspace-scoped-artifact-identity.md)'s workspace-scoped artifact identity from Zot repos and static S3 prefixes to the Postgres archive plane:

- `databaseArchiveBase(namespace, name)` — the bare name in the legacy shared apps namespace (byte-identical, so no existing database's history moves), `<namespace>-<name>` everywhere else.
- `status.backupServerName` still wins when set: it is where a database demonstrably has history, including an already-versioned `-pgNN` generation, which must not double-suffix.
- The recovery `externalCluster` default resolves the source through the same base, or a tenant-namespace restore would repeat `w7/039`'s "no target backup found".
- The purge Job takes an explicit prefix list — this database's base, every per-major generation of it, and its current pin — instead of building prefixes from the bare name.

Four regression tests, each proven red against the unfixed derivation: scoping, the pin/upgrade interaction, the recovery default, and a purge set that both excludes the bare name and leaves legacy behaviour byte-identical.

## Production mitigation, applied before the fix could ship

The three live databases were repointed at workspace-scoped prefixes through the existing `status.backupServerName` field — the same values the fixed derivation produces, so the deploy is a no-op for them:

```
tea-d98210cbbpdc73dcrkvg-dpg-d9nqg95cavls73fp8m20   (and the two multisite databases)
```

A status-only write does not trigger a reconcile (the `Database` watch is generation-based), so the owned CNPG Cluster was touched to drive one. All three then reported `ContinuousArchiving=True`, a fresh base backup completed on each, and WAL began draining (1.3 GB → 641 MB, 913 MB → 593 MB). The three forums served 200 throughout.

## Observability — added in the same pass

Readiness could not have caught this, so it got its own signal. `w7/036` added `bex_datastore_ready` after a Database that never provisioned went unnoticed; this is the opposite failure — a Database that provisions, serves, and backs up nothing — and it needed its own series rather than an inference:

- `bex_datastore_wal_archiving{namespace,name}` — 1 when a backup-enabled Database's CNPG cluster reports `ContinuousArchiving=True`, 0 otherwise, read at scrape time from the cluster's own condition. Emitted only for databases whose plan has backups, so a backup-less plan raises no noise.
- Alert `DatabaseNotArchivingWAL` (critical, 15m), whose description names the exact `Expected empty archive` case and points at Step 5 of the cutover runbook.

The listing shares `bex_datastore_observe_errors_total`, so a failed CNPG listing is counted rather than silently dropping the series — the same reasoning `w7/036` applied, and the same reason an alert on `== 0` must never be the only guard.

A regression test asserts a non-archiving database reads 0, an archiving one reads 1, and a backup-less one emits nothing; proven red against the collector without the metric.

## Follow-ups

- The three mitigated databases now archive under a prefix the purge derives identically, so their eventual deletion is correct. No orphan is left behind.
- Retiring the old `default` instances (runbook Step 9) is now safe with respect to this defect — the prefixes no longer overlap — but is still held for the agreed soak.
