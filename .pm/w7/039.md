# 039 — Managed-Postgres restore-from-backup never worked; every recovery failed "no target backup found"

Why: the restore fix is live and proven, but the follow-ups keep the class from recurring — ADR031's drills never covered tenant Postgres via spec.recovery, and a green Backup row was proven to be no evidence of a restorable archive.

**Live defect on the disaster-recovery path.** Found 2026-08-21 by executing `w7/m77`'s runbook Step 1 against hetzner-prod. Fixed in the repo, not yet deployed.

## How it surfaced

The cutover runbook's first step says, in its own words: _"Take a backup and **prove it restores** — do not accept 'a backup object exists'."_ That instruction earned its keep.

Backup objects looked perfect. All three tenant databases have `ScheduledBackup`s and completed daily `Backup` rows, the most recent from that morning:

```
dpg-d9nqg95cavls73fp8m20-backup-20260821030000  completed
dpg-d9rrkoc4h4mc73edurp0-backup-20260821030000  completed
dpg-d9rs3ee0ccis738kc7c0-backup-20260821030000  completed
```

Restoring one into a scratch Database (`spec.recovery.sourceDatabase`) failed instead of provisioning. Every recovery pod errored, in a loop:

```
full-recovery: "Error while restoring a backup"
  error: "rpc error: code = Unknown desc = no target backup found"
```

## Root cause

`serverName` selects the source's archive prefix inside the shared destination (`s3://bex-tfstate/postgres`). The source cluster writes under its own:

```
plugins: [{ barmanObjectName: bex-tenant-postgres, serverName: dpg-d9rrkoc4h4mc73edurp0, isWALArchiver: true }]
```

The recovery `externalCluster` bex projected carried no `serverName` at all:

```
externalClusters: [{ name: source, plugin: { barmanObjectName: bex-tenant-postgres } }]
```

Without it the barman plugin defaults to the **new** cluster's own name (`dpg-m77restoretest`), where nothing has ever been written — hence "no target backup found".

`database_controller.go` passed only the **optional** field:

```go
"plugin": barmanCloudPlugin(p.recovery.SourceBackupServerName, false),
```

`SourceBackupServerName` exists solely to pin a specific PostgreSQL-major generation. On an ordinary restore it is empty, so `serverName` was omitted every time. `SourceDatabase` is the source Database's CR name and _is_ its serverName — the CRD comment says so, and `Database.status.backupServerName` confirms it — so it is the correct default.

## Why nothing caught it

`TestCnpgClusterSpecRecovery` covers only the case where `SourceBackupServerName` **is** set (`"src-pg16"`). The ordinary path — `sourceDatabase` alone, which is what the API and every user produce — had no test. The suite was green throughout.

## Fix

Default `serverName` to `SourceDatabase` when no explicit generation is pinned; an explicit one still wins. Two regression tests: the ordinary path (proven red against the unfixed projection) and the override.

## Impact, stated plainly

Every managed Postgres has been accumulating backups that could not be restored through the platform's own recovery path. The data is intact and the archives are real — this is a restore-path defect, not data loss — but the recovery feature (`spec.recovery`, PITR, Render's restore) has never worked on any tenant database.

Nothing on the backup side is wrong: the `ScheduledBackup`s, the WAL archiving, and the object store are all healthy. That is precisely what made this invisible — every signal a dashboard or alert would look at was green.

## Verified fixed on hetzner-prod

Re-ran the restore after the fix deployed. The scratch Database reached **`Ready`**, and the recovered data matches the source exactly:

|  | posts | topics | users | last post |
| --- | --- | --- | --- | --- |
| source `dpg-d9rrkoc4h4mc73edurp0` | 18,324 | 4,168 | 190 | 2026-07-05 |
| restored copy | **18,324** | **4,168** | **190** | **2026-07-05** |

The restored instance carries the source's own database name (`dpg_d9rrkoc4h4mc73edurp0`), so the archive prefix resolved correctly — which is precisely what was broken. Scratch instance deleted; the three forums served 200 throughout.

**`w7/m77` Step 1 is therefore satisfied**: the restore point is proven, not assumed.

## Follow-ups

- **ADR031's restore drills should have caught this.** `w7/m29` recorded drills for etcd, OpenBao and bex-db — but not for a _tenant_ Postgres through `spec.recovery`. Add one, and put it on the same re-drill cadence.
- Consider whether a completed `Backup` should be verified rather than merely recorded; a green backup that cannot restore is worse than a red one.
