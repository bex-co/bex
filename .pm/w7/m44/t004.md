## Objective

Extend the sweep to the three samples whose lifecycle differs from a plain web service, adapting each leg's "verify up/down" to the type's observable behavior.

## Context

- `examples/static-site` (`static_site`): CLI `services create --type static_site --publish-directory …`; up = `https://<name>.onbex.co` serves the built content from the shared static-server (ADR029); suspend/resume/delete semantics per ADR029 — pin what prod actually does and compare with Render's static-site suspend behavior.
- `examples/cron-demo` (`cron`): no URL — up = CronJob exists and a run fires (5-min schedule; trigger a manual run instead of waiting where the surface allows), suspend = no new runs, resume = runs again, delete = CronJob + runs gone. CLI: `services create --type cron_job --cron-schedule … --cron-command …` as supported; note gaps.
- `examples/stack-demo`: a Blueprint (web + worker + postgres via `fromDatabase`). The official CLI has no blueprint apply — compose it as the CLI can (postgres create + two services create + explicit env wiring) or use the documented blueprint path (ADR017) for create and the CLI/REST for the lifecycle verbs; document which. Postgres suspend/resume via CLI **is** supported (`docs/cli-compatibility-checklist.md:82`).
- Free-tier caps (`BEX_MAX_*`): delete as you go.

## Steps

1. Add the three specs (with type-specific verify functions) to the harness.
2. Run each on prod; record evidence; triage failures (inline vs t005).

## Evidence (prod sweep 2026-07-17, `scripts/samples-lifecycle.sh`, api.bex.co)

- **static-site** — ◐ two problems: one fixed, one filed (build ✅, publish ✖ on
  prod). First failure: `--type static_site --publish-directory .` went down the
  **Docker build path** and failed `no Dockerfile` (bex's static build plane is
  Dockerfile-only, ADR029; the publish Job extracts `publishPath` from a *built
  image*, `publish.go:232`), while the sample had no Dockerfile and its `bex.yml`
  over-promised "no Dockerfile needed". Stopgap fixed + shipped (`61a18797`): a
  minimal `examples/static-site/Dockerfile` (`FROM busybox; COPY index.html`) +
  honest `bex.yml`; validated locally by simulating the extract (`cp -a
  "$PUBLISH_PATH"/. /out` → exactly `index.html`). Real no-Dockerfile-publish fix
  filed **`.pm/w9/010`**. Post-`/ship` prod re-run (both same-name and unique
  `static-site-x1`): the build now **succeeds** (image pushed) but the deploy fails
  post-build — `==> Deploy failed`, deploy `update_failed`. The failing step is the
  **publish Job** (extract → S3), whose logs `render logs` doesn't surface (no app
  pod); root-causing needs the prod kubeconfig. Filed **`.pm/w9/012`** with repro +
  hypotheses (likely a publish-Job image-pull-cred gap, the m43 failure mode one
  plane over). So static-site is **not GREEN**; the two problems are fixed/filed
  per the "fix or file" mandate, none skipped.
- **cron-demo** — ❌ found a harness gap → **fixed** → ✅ GREEN (proven via runs, not
  URL). First create failed: the Render CLI requires **both** `--cron-schedule` AND
  `--cron-command` (client-side), even though the image has its own ENTRYPOINT
  (`/cron-demo`) — a documented CLI gap. Added `--cron-command "/cron-demo"`.
  `srv-d9dc8lc…` (run with a `* * * * *` schedule to observe runs fast): deploy →
  **a run emitted its MESSAGE to logs** (verify-up via `render logs`, not a URL) →
  suspend → **no new run for one window** (1→1) → resume → **a run fired again** →
  delete → gone. Full cron semantics proven through runs.
- **stack-demo** — ✅ GREEN (all three resources; DB wiring works). Composed as the
  CLI can (the CLI has no blueprint apply): `postgres create` (`dpg-d9dccc…`), read
  its **internal** connectionString via `GET /v1/postgres/{id}/connection-info`, then
  two `services create` with `DATABASE_URL` wired explicitly (`stack-web`,
  `stack-worker` type `background_worker`). web served **`db ok: SELECT 1 = 1`**
  (200) — the injected DATABASE_URL reaches CNPG and `SELECT 1` runs. suspend
  (web+worker via REST, postgres via CLI `postgres suspend`) → sustained-down →
  resume → served DB data again → delete all three → gone. Documented divergence
  from the blueprint path: DATABASE_URL is injected as a plain env var (the
  blueprint's `fromDatabase` keeps it in the CNPG Secret via a secretRef).

CLI gaps documented for the checklist: service suspend/resume are dashboard-only
(REST fallback per leg); cron create needs `--cron-command` even for an
image-entrypoint job; no blueprint apply (stack composed leg-by-leg).
