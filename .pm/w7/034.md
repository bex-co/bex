# 034 — Cron and manual-run containers pull `IfNotPresent` where the Deployment path deliberately pulls `Always`

Why: a cron run can silently execute a stale cached image against a mutable gen-N tag — the exact staleness failure (codex-security #29) the Deployment path was deliberately hardened against, with no serving URL to make it visible.

Surfaced by `w7/m84/t005`'s reuse review, 2026-08-19. **Pre-existing, not introduced by m84** — m84 is byte-identical here, which is the only reason it is a note and not a fix.

`deployment_projection.go` sets the tenant container's pull policy through `pullPolicyFor`, which returns `Always` for anything not digest-pinned. The comment at `app_controller.go` says why: a mutable `gen-N` tag means a node can reuse a previous App lifetime's cached image and run stale code (codex-security #29).

`cronPodSpec` never sets `ImagePullPolicy` at all, so the API server defaults it — and its rule is tag-based: anything not `:latest` gets **`IfNotPresent`**. So a `cron_job`, and the one-off Jobs `spec.runAt` materializes from the same template, carry exactly the policy the Deployment path rejects, against exactly the same mutable `gen-N` tags. m84 made that explicit in the projection (`applyPodSpecServerDefaults` now writes what the server was already storing) but deliberately did not change it: the fix is `pullPolicyFor(image)`, and that changes the stored template.

**Impact if real:** a cron run scheduled onto a node that still has `…/app:gen-7` cached from a previous deploy executes the old image. Same failure mode the Deployment path was hardened against; less likely to be noticed, because a cron run leaves no serving URL to look wrong.

**Cost of the fix:** one CronJob template update per cron App (no pod rollout — a CronJob has none; the next scheduled run picks it up). Check whether the buildpack/native path's baked CMD interacts, and whether any test pins `IfNotPresent` for cron.

Sub-hour. Promote only if the security reasoning survives a second look — the counter-case is that a cron image is pulled fresh on most runs anyway because the pod is short-lived and lands on a random node.
