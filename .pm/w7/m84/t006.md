## Objective

Cover what the t004 invariant does not: that a **real** change still produces a write, and that each fixed field is individually pinned.

## Context

- The invariant proves "no write when nothing changed". The complementary risk is over-correcting into "no write **ever**" — a projection that silently stops applying changes would pass the invariant and break deploys. That direction needs its own tests.
- Per-field regression tests matter because the fix depends on matching specific API-server defaults; a Kubernetes upgrade that changes one default should fail loudly here rather than silently resume churning.

## Steps

1. Test that changing the App spec (image, env, replicas, probe path) **does** produce an update and the expected object.
2. Pin each defaulted field the fix now sets, individually, so a changed upstream default fails a named test.
3. Test the no-rollout property explicitly (template hash stability across the fix).
4. Confirm `make test` is green.

## Files

- `lego/operator/internal/controller/deployment_projection_test.go` and sibling controller tests

## Acceptance criteria

- [ ] A real spec change still produces exactly one update.
- [ ] Each defaulted field is individually pinned by a named test.
- [ ] Template-hash stability is asserted, not assumed.
- [ ] No trivial or tautological tests; `make test` green.

## Out of scope

- Measuring the apiserver write-rate reduction in production — desirable but not a merge gate.
