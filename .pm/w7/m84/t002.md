## Objective

Make the mutate function's output equal what the API server stores, so `CreateOrUpdate` returns `OperationResultNone` for an unchanged App — without rolling a single production pod.

## Context

- `028`'s fix sketch: set `TerminationMessagePath`/`TerminationMessagePolicy` on the container, `SuccessThreshold: 1` on all three probes, set readiness `PeriodSeconds`/`FailureThreshold` explicitly, and preserve the fetched `TerminationGracePeriodSeconds` when `MaxShutdownDelaySeconds` is unset — **or** switch the seam to `CreateOrPatch`.
- Choose deliberately between "match the defaults" and "switch to `CreateOrPatch`" and record why; matching defaults is more explicit but must be re-checked on Kubernetes upgrades, while `CreateOrPatch` is more robust but changes the seam's semantics.
- `w9/m57` fixed the Service equivalent by matching the server default (`Protocol`) — the precedent leans toward matching, but the probe field count here is larger.
- **Rollout safety is the hard constraint:** the Deployment template hash is computed post-defaulting, which is why nothing rolls today. Any change that alters the pre-defaulting template in a way the hash sees would roll every App in production at once.
- `m80` and `m81` set probe fields deliberately (5s timeouts, derived thresholds, `startupProbe`, `livenessProbe`) — do not disturb those values while adding the defaulted ones.

## Steps

1. Pick the approach and record the rationale in a code comment.
2. Implement it so the second reconcile is a no-op.
3. Prove no rollout: assert the resulting pod-template hash is unchanged versus the pre-fix projection for a representative App.
4. Confirm t001's Deployment assertion now passes.
