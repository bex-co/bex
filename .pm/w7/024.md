# Build pods cannot schedule on tenant nodes despite real headroom (autoscaler/capacity, not QoS)

**Source:** production bug report 2026-08-08 §5 (`tianpan-forum` / `blockeden-forum` deploy), triaged the same day.

Deploying from a repo requires a build pod whose `buildkit` init container requests **7Gi + 2 CPU**. On hetzner-prod the tenant nodes were **85–97% committed on requests** while only **11–52% actually used** (Guaranteed-QoS workloads, request == limit), so the build pod — and even a trivial 100m/128Mi pod — stayed `Pending` with "Insufficient cpu/memory". Earlier this looked like builds "wedging": status `Building`, zero logs. Worked around by importing an already-built image per tenant (`runtime: image`), skipping the build entirely.

**The reporter suggested Burstable QoS (request < limit) for build/app pods. Reject that framing** — the sizing is deliberate. `lego/operator/internal/build/build.go:75-86`:

> Build execution resources match Render's Starter pipeline tier (2 CPU, 8 GB RAM) while remaining schedulable on the baseline 8 GB tenant nodes. The 7 GiB memory request leaves allocatable headroom for kubelet and DaemonSets but still **makes a builder effectively node-exclusive, so Cluster Autoscaler adds a node instead of co-locating** a memory-hungry build with serving workloads.

So the request size is the mechanism, not the bug. Under-requesting would reintroduce exactly the noisy-neighbor eviction risk the constants were chosen to avoid, and would fight `docs/ADR034-scalable-build-pipeline.md`'s Pod-versus-machine capacity model.

**The actual question is why Cluster Autoscaler did not add a node.** Candidates, in order:

- autoscaler max-node / node-group bounds reached (`deploy/gitops` autoscaler config, `infra/` node pools);
- the node group cannot provision a machine type that fits a 7Gi+2CPU pod, so the pod is unschedulable-but-not-scale-up-triggering;
- autoscaler not actually reconciling the tenant pool, or scale-up blocked by a pending-pod predicate;
- baseline node size drifted below what the constants assume ("the baseline 8 GB tenant nodes").

Check the autoscaler's own events/logs for the pending build pod first — it records why it declined to scale up, which picks the branch without guessing.

**Sizing:** kept as an inbox note rather than a milestone because the fix may well be a bounded config change (a node-group max, a machine type) — sub-hour. Promote to a milestone if the investigation shows the capacity model itself needs revisiting (e.g. a dedicated build node pool, which `docs/ADR034` would own).
