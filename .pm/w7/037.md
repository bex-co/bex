# 037 — The official Render CLI is 403 on every operation in production

**Live regression on a shipped surface.** Found 2026-08-20 while trying to use the CLI's
stored credentials. Not fixed — this note is the evidence and the narrowing.

## Symptom

Every CLI action fails:

```
$ render services -o json --confirm
Error: you are not allowed to take this action
```

Direct API call with the same credential:

```
GET https://api.bex.co/v1/services -> 403
{"code":"INSUFFICIENT_SCOPE","error":"insufficient OAuth scope",
 "params":{"required":"bex.read"}}
```

## What was verified

| fact | value |
| --- | --- |
| stored access token | expired 2026-08-17; refresh via `POST /v1/token/refresh/` returns **200** |
| refreshed token, introspected at Hydra | `active: true`, `client_id: 429024F5…`, `scope: openid offline_access`, `aud: []` |
| CLI client registration in Hydra | `scope: openid offline_access bex.read bex.write bex.sensitive` |
| CLI client metadata | `{"bex.co/platform-client": true}` — **marker present** |

So the credential is valid and the client is correctly marked. The refused capability is
`bex.read`, introduced by the operation-level scope matrix (`11b73d5e`, w2/m78), which is
deployed.

## Root cause — found, and it was deliberate

`9081fbdb fix(security): close repository audit findings` **removed** the platform-client
branch from `core.CapabilityExempt` on purpose, rewriting the doc comment to "Human OAuth
delegations are never exempt, including first-party public clients":

```diff
 func (id Identity) CapabilityExempt() bool {
 	if id.Method != "oauth2" || !id.Human {
 		return true
 	}
-	if id.PlatformClient && !HasGranularCapability(id.CanonicalScopes) {
-		return true
-	}
 	return false
 }
```

The hardening is right. What was missed is that the CLI's authority *depended* on that
exemption, and the other half of the migration never happened: `cliauth/service.go` still
requested `openid offline_access` alone. The Hydra client registration had already been
moved to the granular vocabulary — so the client was entitled to `bex.read`/`bex.write`/
`bex.sensitive` and simply never asked for them.

Nothing covered the pairing. The one test that touched it pinned the old literal
(`scope != "openid offline_access"`), so it protected the broken behavior.

## Fix

The device flow now requests the capabilities the client is registered for, keeping the
hardening intact — no blanket exemption, the grant is explicit and shows up in audit
provenance, and Hydra still narrows it to the client's registered set so the CLI cannot
request more than it is entitled to.

Regression test `TestDeviceAuthRequestsGranularCapabilities`, proven red against the old
value; the pre-existing assertion was updated to the shared `cliRequestedScope` constant so
the request and its test cannot drift apart again.

**Existing CLI sessions must re-login** (`render login`). A refresh preserves the original
grant, so a token minted before this fix stays identity-only — that is inherent to OAuth,
not a further bug.

## Original narrowing (kept for the record)

`Identity.CapabilityExempt()` exempts a platform-marked client that has not requested a
granular capability:

```go
if id.PlatformClient && !HasGranularCapability(id.CanonicalScopes) {
    return true
}
```

The token's scopes are `openid offline_access` — no granular capability — and the client
carries the platform marker. The exemption should fire and the request should be allowed.
It is not, which means `id.PlatformClient` is resolving **false** at the REST seam despite
Hydra holding the marker.

## The likely second half

`cliauth/service.go:244` — the device-authorization request hardcodes:

```go
"scope": {"openid offline_access"},
```

The Hydra client registration was updated to the granular vocabulary
(`bex.read bex.write bex.sensitive`), but the flow that actually requests scopes was not.
So **re-logging in does not fix this** — a fresh device login receives the same
identity-only grant as the refreshed token. That is worth confirming before anyone
recommends `render login` as the workaround; it is the obvious advice and it appears to be
wrong.

## Narrowing left to do

1. Determine why `PlatformClient` is false — is the resolver erroring (its failure is
   indistinguishable from a negative), or is the exemption not consulted on this path?
   `platformClient()` consults a cache first; the bex-api pods restarted an hour before
   this test, so a stale negative is unlikely but not excluded.
2. Decide the intended contract: either the device flow requests the granular scopes it is
   now registered for, or the platform-client exemption must work. Today neither does.
3. Add a test that exercises a platform-client token with identity-only scopes against a
   read operation. Nothing covers this or the regression could not have shipped.

## Impact

The CLI is one of bex's five surfaces and `docs/cli-compatibility-checklist.md` treats
running the unmodified upstream CLI against bex-api as a first-class guarantee. Right now
every row in that checklist would fail. The dashboard is unaffected: a Kratos session is
`Method: "session"`, which `CapabilityExempt` short-circuits before any scope check.
