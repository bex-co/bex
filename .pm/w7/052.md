# 052 — GraphQL serializes Project, Environment and Blueprint timestamps in Go's `time.String()` format, while REST returns RFC3339 for the same field (five fields as of 2026-09-16 — a fifth shipped after filing)

Why: the same instant on the same resource comes back as `2026-09-16 01:51:44.60528 +0000 UTC` from GraphQL and `2026-09-16T01:51:44.60528Z` from REST. Anything that parses a date strictly — a non-Chrome browser, an SDK, an MCP agent, `time.Parse(time.RFC3339, …)` — gets a valid value from one surface and a parse error from the other, for a field ADR006 says the three adapters project from one core.

**Estimate:** 35m · **Severity:** minor (no data loss; Chrome's lenient parser hides it in today's UI) · **Attribution:** bex-api (GraphQL adapter) · **Worker:** worker7

## Root cause

`gqlutil.StrField` is `Typed(graphql.String, …)` (`lego/backend/internal/gqlutil/gqlutil.go:60`), so graphql-go coerces whatever Go value it is handed into a string. Sibling views hand it a **pre-formatted string**; these three hand it a **`time.Time`**, which stringifies as Go's `2006-01-02 15:04:05.999999999 -0700 MST` layout:

| view | field type | GraphQL resolver |
| --- | --- | --- |
| `ProjectView.CreatedAt` | `time.Time` (`projects/service.go:169`) | `projects/graphql.go:33` |
| `ProjectView.UpdatedAt` | `time.Time` (`projects/service.go:170`) | `projects/graphql.go:34` — **added after filing by `w4/m109` (`b3cd31e3f`), deployed 2026-09-16 09:19:31Z** |
| `EnvironmentView.CreatedAt` | `time.Time` (`environments/service.go:193`) | `environments/graphql.go:38` |
| `BlueprintView.CreatedAt/UpdatedAt` | `time.Time` (`apps/blueprint.go:402-403`) | `apps/graphql.go:829-830` |
| `AppView.CreatedAt` / `AppView.UpdatedAt` | `string` (`apps/service.go:443-444`) | correct today |
| `KeyValueView.CreatedAt` | `string` (`keyvalue/service.go:84`) | correct today |
| `EnvGroupView.CreatedAt` | `string` (`envgroups/service.go:191`) | correct today |
| `ServiceInstanceView.CreatedAt` | `time.Time`, but formatted at the resolver: `.UTC().Format(time.RFC3339)` (`apps/graphql.go:576`) | correct today, and the pattern to copy |
| `DeployView.CreatedAt/UpdatedAt` | `time.Time`, formatted at the resolver by a **package-private** `formatTime`/`formatTimePtr` (`deploys/graphql.go:47-48`) | correct today — and the reason the helper should be shared rather than re-invented |

REST and MCP are unaffected because both marshal the struct with `encoding/json`, which renders `time.Time` as RFC3339 (`projects/rest.go:45-46`; `projects/mcp.go:61`, `environments/mcp.go:73` return the views directly).

## Three private re-inventions of the same helper, at two precisions

This is new, and it sharpens the fix below. The codebase now formats GraphQL timestamps three separate ways:

| helper | precision | sites |
| --- | --- | --- |
| `gqlTime` (`agentsessions/graphql.go:35`) | `time.RFC3339Nano` | agentsessions, 9 fields |
| `formatTime` / `formatTimePtr` (`deploys/graphql.go:47-48`) | `time.RFC3339` | deploys, 5 fields |
| inline `.UTC().Format(...)` | both — RFC3339 in `jobs`/`apps:576`/`sshkeys`, RFC3339Nano in `notifications` | 8 fields |

So a shared `gqlutil.TimeField` is not purely additive: it must **pick a precision**, and whichever it picks changes the wire output of fields that are correct today. That trade belongs in the fix, not discovered during it.

## Fix

Format at the point of projection the way `apps/graphql.go:576` already does — `b.CreatedAt.UTC().Format(time.RFC3339)` — across the **five** affected fields, which live in three files (`projects/graphql.go:33-34`, `environments/graphql.go:38`, `apps/graphql.go:829-830`).

Better, add a `gqlutil.TimeField` helper that does it once, so the sixth field cannot inherit the broken spelling by default — which is exactly how `Project.updatedAt` arrived. **But that helper has to decide a precision first**, and the decision is not free: three private helpers exist today at two precisions (see the table above), so adopting one shared helper changes the wire output of whichever group does not match it. Recommended: make `TimeField` emit `time.RFC3339`, migrate the five broken fields to it immediately, and leave the correct-today `RFC3339Nano` sites alone until someone decides whether sub-second precision is part of the contract. Migrating them silently would be a second wire-format change dressed as a refactor.

Keep the REST/MCP structs as `time.Time`; only the GraphQL projection changes. A zero `time.Time` should serialize as `""`/null rather than `0001-01-01T00:00:00Z`, matching how the string-typed siblings behave when empty — `jobs/graphql.go:40-51` is the existing nil-guard pattern to copy.

## Observed impact today, stated precisely

The Blueprints table's **Last Updated** column renders **`20d`**, not `—`: Chrome's `Date.parse` accepts the Go format leniently, so the current UI looks correct. Measured in the page (Chrome 537.36):

```text
Date.parse("2026-08-26 10:26:53.507942 +0000 UTC") → 2026-08-26T10:26:53.507Z
Date.parse("2026-08-26T10:26:53.507942Z")          → 2026-08-26T10:26:53.507Z   (same instant)
Date.parse("2026-08-26 10:26:53")                  → 2026-08-26T17:26:53.000Z   (no zone ⇒ local time)
```

The third line is the warning: V8's leniency is doing the work here, and a variant that loses the offset silently shifts by the viewer's UTC offset instead of failing. `formatRelativeAge` (`features/services/lib/format.ts:25-31`) returns `—` only when `Date.parse` yields `NaN`, which is what a stricter engine would produce — ECMAScript only guarantees the ISO-8601 Date Time String Format, and anything else is implementation-defined. So the damage is not "the dashboard is broken in Chrome" but "the GraphQL contract is wrong, and every non-lenient consumer breaks on it."
