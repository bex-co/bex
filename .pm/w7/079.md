# A person signed in at the dashboard must retype their password the first time a browser connects an agent or approves `bex login`; Render asks for nothing

Why: Render parity (ADR008): a signed-in Render user approving the CLI or an app is not asked to sign in again, while bex asks every browser to confirm its password at its first OAuth grant, which is the first thing a new user does when connecting Claude Code or running `bex login`.

- Found by w7/073, 2026-11-17. Kratos (v26.2.0 and v1.3.1 alike, `selfservice/flow/login/handler.go` `createBrowserLoginFlow`) rewrites a login-challenge flow to `refresh=true` whenever Hydra's login request has `skip: false`. Hydra sets `skip` only for a browser that holds its own remembered login (`ory_hydra_session`; Hydra v26.2.0 `consent/strategy_default.go` `forwardAuthenticationRequest`). A dashboard sign-in never goes through Hydra, so the first grant from every browser gets the re-authentication form (message `1010003`, "confirm this action by verifying that it is you"). Kratos then accepts the challenge with `remember` for the session lifespan (168h in production), so later grants from that browser pass with no UI ([ADR012 §7](../../docs/ADR012-auth.md)).
- Production: w4/m116 t005 (2026-10-03, `bex login` device approval: password at sign-in, then again at the challenge) and w4/m454 t004 (2026-11-17, an MCP client's authorize after `qa-login.sh`).
- Kratos has no switch for it: `oauth2_provider` takes only `url`, `headers` and `override_return_to`, and `session.cookie.persistent` (what makes Kratos ask Hydra to remember) is already on.
- What reaches Render's behavior: when the login page gets a refresh flow for a login challenge while the browser holds a live Kratos session at its required AAL, the dashboard's server accepts the challenge at Hydra's admin API itself (subject the identity, `identity_provider_session_id` the session, `amr` from the session, `remember` for the session lifespan) and leaves a request with `prompt=login` or an exceeded `max_age` to Kratos's form. The consent page and the device page's Authorize click still gate the grant, as they already do for a browser Hydra remembers, which today grants with no password at all.
- **Needs a user decision:** that accept contradicts `.pm/DO_NOT_DO.md` "Do not hand-build a Hydra login/consent provider" (the login UI only passes `login_challenge` through). Either amend that line to allow a session-backed accept, or sign the divergence off as an ADR018 row.
- Done when: a browser signed in at the dashboard only connects an agent and approves `bex login` with no password form, `scripts/auth-oauth21-e2e.sh` has a leg that proves it (a session from a plain browser login, then an authorize), and ADR012 §7, ADR025 and DO_NOT_DO agree; or ADR018 records the signed-off divergence and ADR012 §7 and ADR025 link it.
