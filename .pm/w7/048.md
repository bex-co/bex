# 048 — The Scaling page offers autoscaling on a free service, then the save fails: the autoscaling card ignores the plan instance cap its sibling card applies

Why: a free-plan user can fill in an autoscaling range of up to 100 instances, press Save, and only then learn from a red toast that the free plan caps them at 1 — while the Manual Scaling card six lines below already says so up front. Render does not offer horizontal scaling on free instance types at all.

**Estimate:** 40m · **Severity:** minor (misleading UI; the platform enforces the cap correctly, nothing is lost) · **Attribution:** dashboard · **Worker:** worker7

## Repro (every step was run)

1. Create a **free** web service (any eligible type: web, private, background worker — workers are paid-only, so in practice web and private).
2. Open `/services/<srv-id>/scaling`. The page shows the Autoscaling card and, below it, the Manual Scaling card reading _"Free services run a single instance. Upgrade to a paid plan to run multiple load-balanced instances."_ with its own slider pinned to 1 and Save disabled.
3. Turn the **Autoscaling** switch on. The full editor appears: Minimum/Maximum instances, Target CPU, Target Memory.
4. Set **Maximum instances = 3** (the control accepts up to 100) and enable Target CPU. Press **Save Changes**.

Accessibility-tree evidence that the control is not capped, read live on the free fixture:

```text
spinbutton "Maximum instances": min="1" max="100" value="1"   → after fill("100") value="100"
slider     "Maximum":           aria-valuemin="1" aria-valuemax="100"
…on the same page: "Manual Scaling  Free services run a single instance. Upgrade to a paid plan…"
```

**Actual** — the mutation is sent and refused; the card keeps showing "Autoscaling on" until a reload, after which it is off again:

```text
POST https://api.bex.co/graphql   operationName: SetAutoscaling
  variables: {id: "srv-daktdlgb3bfc73eq7ubg", minInstances: 1, maxInstances: 3, targetCPUPercent: 60}
→ HTTP 200
  [{"data":{"setAutoscaling":null},
    "errors":[{"message":"bad request: the free plan is limited to 1 instance(s) and cannot scale to 3",

toast: "The free plan is limited to 1 instance(s) and cannot scale to 3"
after reload: switch "Autoscaling off"
```

**Expected** — the same thing the Manual Scaling card does on a free plan: do not offer a range the plan cannot run. Either replace the Autoscaling card with the free-plan upgrade copy, or render it disabled with that copy, so the refusal is never reached from the UI.

The client-side validation that does exist works: saving with no utilization target shows the inline _"At least one utilization target (CPU…"_ message and sends nothing. The gap is specifically the plan cap.

## Root cause

- `dashboard/src/routes/services.$serviceId.scaling.tsx:70` renders `<AutoscalingSection autoscaling={autoscaling} />` whenever `scalable` — a **type** gate (`supportsScaling`: web/private/worker, `features/services/lib/service-type.ts:145-152`). It passes `plan={service.plan}` only to `ManualScalingSection` (`:74-80`).
- `dashboard/src/features/services/components/manual-scaling-section.tsx:43-46` is the sibling that gets it right: `const isFree = plan === "free"; const maxInstances = isFree ? 1 : INSTANCE_MAX;` plus the `services.scalingManualDescriptionFree` copy.
- `dashboard/src/features/services/components/autoscaling-section.tsx` takes no `plan` prop at all. `INSTANCE_MIN = 1` / `INSTANCE_MAX = 100` (`:23-24`) bound both instance controls (`:317-320`) and the load-time clamp (`:198-199`), and `validate()` (`:46-52`) checks only min ≤ max and "at least one target". Nothing consults the plan.
- The server is right and already says so: `lego/backend/internal/apps/service.go:4439` (`autoscalingSpec`, doc comment at `:4431`) calls `checkInstanceCap(tier, req.MaxInstances)` at `:4460` and the same for `MinInstances` at `:4463`; `checkInstanceCap` (`:3246`, comment `:3241`) reads `tiers.Compute.InstanceCap(tier)`, and `lego/types/tiers/tiers.yaml:41-46` gives compute `free` `maxInstances: 1` (`:46`) — with the comment "matching Render — its free instance types offer no horizontal scaling" (`:43-44`). **Line numbers corrected sweep 36**; the note originally cited `:4407-4448`, `:3214-3224` and `:43-46`, and the first of those did not even span the `checkInstanceCap` calls it described.

## Control case — the correct pattern, verified live on the same free service (2026-09-16, sweep 15)

A second free web service (`qa-20260916-e2ccd0-mnt`, `srv-dal4m7lfht5c7389ld90`, created and deleted inside that sweep) shows **three** plan-gated controls behaving three different ways in one session — so the right shape is not hypothetical, it already ships two doors down:

| control                                     | on a free plan                                                                                              | verdict          |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------- |
| **Maintenance Mode** (Settings)             | `switch "Maintenance…"` reads **disabled**, `aria-checked=false`, with a paid-only hint beside it              | gated up front ✅ |
| **Manual Scaling** (Scaling)                | _"Free services run a single instance. Upgrade to a paid plan…"_, slider pinned to 1, `Save Changes [disabled]` | gated up front ✅ |
| **Autoscaling** (Scaling, same page)        | `switch "Autoscaling off"` reads **enabled** — the editor opens and the refusal arrives only after Save        | this defect ❌    |

`maintenance-mode-section.tsx:20,43` is the reference implementation: it takes a `plan` prop, computes `const eligible = plan !== "free"`, disables the control, and swaps in `services.maintenanceModePaidOnly` copy — the exact three moves `AutoscalingSection` is missing. Prefer copying that shape rather than inventing a new one.

## Fix

Give `AutoscalingSection` the same plan awareness the manual card has: pass `plan={service.plan}` from the route, and on `plan === "free"` render the card in its unavailable state — the existing `services.scalingManualDescriptionFree` copy (or a sibling key) instead of the editor. Clamping the max control to 1 would technically stop the failed save, but it would still advertise an autoscaler that cannot do anything on that plan, so prefer not offering it. Paid tiers omit `maxInstances` in `tiers.yaml`, so they keep the full 1–100 range.
