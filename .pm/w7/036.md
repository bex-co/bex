# 036 — No new managed Postgres can provision anywhere; an RBAC hardening patch broke it

Why: the RBAC fix and observability shipped, but the open follow-ups (a runtime provision-to-Ready smoke check, and re-checking the other least-privilege GitOps patches for the same delegation mistake) are what cover the defect class rather than this one instance.

**Live production defect, silent, platform-wide.** Found 2026-08-19 by `w7/m77/t007`'s cutover rehearsal. Fix written (uncommitted); this note is the record.

## Symptom

Any `Database` created today — in **any** namespace — hangs in `Provisioning` forever with no CNPG pod. The CNPG Cluster reports:

```
Cluster cannot proceed to reconciliation due to an error while interacting with plugins:
roles.rbac.authorization.k8s.io "<cluster>-barman-cloud" is forbidden: user
"system:serviceaccount:cnpg-system:plugin-barman-cloud" is attempting to grant RBAC
permissions not currently held: {APIGroups:[""], Resources:["secrets"],
ResourceNames:["bex-db-backup-s3"], Verbs:["get" "watch" "list"]}
```

Verified in both `tea-d98210cbbpdc73dcrkvg` and `default`, so it is not namespace-specific.

## Root cause

`deploy/gitops/charts/barman-cloud-plugin/kustomization.yaml` patched the upstream `plugin-barman-cloud` ClusterRole with `op: remove, path: /rules/0`, deleting its cluster-wide Secret grant. The stated reasoning was sound as far as it went — the ObjectStore reconciler genuinely never reads or mutates a Secret — but it missed Kubernetes' **privilege-escalation prevention**: whoever _creates_ a Role granting X must themselves hold X (or hold `escalate`).

The controller's job is to create a per-cluster Role granting `get/watch/list` on that cluster's backup credential, which the CNPG instance sidecar then uses. Removing its own Secret access removed its ability to create the very Roles the patch comment cites as the reason removal is safe.

**Why it stayed invisible:** per-cluster Roles created _before_ the patch keep working, so every existing database (`default`, `auth`, `bex-system`) is completely unaffected. Only new ones fail, and they fail as a hang rather than an error a tenant would see. Nothing alerts on "Database stuck in Provisioning".

## Fix

Narrow rather than remove: `secrets: [get, list, watch]` — exactly the verbs the delegated Roles grant, which is what escalation prevention checks against. `create`/`delete` stay dropped, so most of the hardening intent survives. Rendered output verified; `scripts/gitops-validate.sh` passes.

## The guard that should have caught it was blind

`gitops-validate.sh` already had a check here — and it asserted the **wrong direction** (fail if the Secret rule exists), so it was enforcing the outage rather than preventing it.

Worse, it never ran at all. It used jq's `index("secrets")`, which this `yq` does not implement; the expression errored, `>/dev/null 2>&1` swallowed the message, and the non-zero exit was read as "no match". **The guard silently passed for its entire life** — it would never have caught a regression in either direction. It was the only `index(` in the script.

Replaced with a verb-set pin that fails both ways, proven red against each:

| tree | result |
| --- | --- |
| rule removed (this outage) | `FAIL: Barman controller Secret verbs are '', want exactly 'get,list,watch'` |
| upstream create/delete restored | `FAIL: ... are 'create,delete,get,list,watch', want ...` |
| correct | PASS |

Lesson worth generalizing: a guard whose expression errors is indistinguishable from a guard that passes, whenever stderr is discarded and exit status is the only signal. Any check written as `if cmd >/dev/null 2>&1` deserves a red-test before it is trusted.

## Follow-ups worth considering

- **A runtime smoke check.** The static guard above covers this specific regression, but RBAC delegation in general is only exercised on a live cluster. A check that provisions a throwaway Database and asserts it reaches `Ready` — plus the five artifacts the runbook now lists — would cover the class rather than the instance. **Still open.**

## Observability — done, and live

Verified on hetzner-prod 2026-08-21: the operator metrics endpoint serves **17 `bex_datastore*` series**, and the running image digest matches the GitOps pin built from `0ac1b6b5` (which carries the collector). The RBAC fix itself was verified earlier by a Database reaching `Ready` in a tenant namespace with all five D8.4 artifacts.

## What was added

The deeper problem was not the RBAC bug but that **nothing could see it**. A Database that never provisions produced no signal at all: CNPG's metrics come from instance pods, so a Cluster that never got a pod exports nothing, and "nothing" is exactly the state worth paging on. The operator exported build metrics and no datastore metrics whatsoever.

Added:

- `bex_datastore_ready{kind,namespace,name,phase}` — 1 when the CR reports its ready phase, 0 otherwise, sourced from the CR status rather than from a pod that may not exist. The phase rides as a label so an alert can say _why_.
- `bex_datastore_age_seconds{kind,namespace,name}` — paired with readiness to distinguish "still coming up" from "never arrived".
- `bex_datastore_observe_errors_total` — because a failed listing makes the readiness series vanish, and an alert on `== 0` would otherwise go quiet exactly when it is blind.
- Alerts `DatastoreStuckProvisioning` (critical, not-ready and older than 15m) and `DatastoreObservationFailing` (warning).

Collection is scrape-time and uncached, like the ClusterBuilder collector, so it cannot block a reconcile. Regression tests assert a stuck Database reads 0 with its phase, that a failed listing is counted and emits no readiness series, and that age advances — each proven able to fail.

- **An alert.** A `Database` in `Provisioning` past a few minutes should page; today it is silent forever.
- Re-check the other least-privilege RBAC patches in `deploy/gitops` for the same delegation-versus-direct-use mistake.
