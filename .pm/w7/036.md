# 036 — No new managed Postgres can provision anywhere; an RBAC hardening patch broke it

**Live production defect, silent, platform-wide.** Found 2026-08-19 by `w7/m77/t007`'s
cutover rehearsal. Fix written (uncommitted); this note is the record.

## Symptom

Any `Database` created today — in **any** namespace — hangs in `Provisioning` forever with no
CNPG pod. The CNPG Cluster reports:

```
Cluster cannot proceed to reconciliation due to an error while interacting with plugins:
roles.rbac.authorization.k8s.io "<cluster>-barman-cloud" is forbidden: user
"system:serviceaccount:cnpg-system:plugin-barman-cloud" is attempting to grant RBAC
permissions not currently held: {APIGroups:[""], Resources:["secrets"],
ResourceNames:["bex-db-backup-s3"], Verbs:["get" "watch" "list"]}
```

Verified in both `tea-d98210cbbpdc73dcrkvg` and `default`, so it is not namespace-specific.

## Root cause

`deploy/gitops/charts/barman-cloud-plugin/kustomization.yaml` patched the upstream
`plugin-barman-cloud` ClusterRole with `op: remove, path: /rules/0`, deleting its cluster-wide
Secret grant. The stated reasoning was sound as far as it went — the ObjectStore reconciler
genuinely never reads or mutates a Secret — but it missed Kubernetes' **privilege-escalation
prevention**: whoever *creates* a Role granting X must themselves hold X (or hold `escalate`).

The controller's job is to create a per-cluster Role granting `get/watch/list` on that
cluster's backup credential, which the CNPG instance sidecar then uses. Removing its own
Secret access removed its ability to create the very Roles the patch comment cites as the
reason removal is safe.

**Why it stayed invisible:** per-cluster Roles created *before* the patch keep working, so
every existing database (`default`, `auth`, `bex-system`) is completely unaffected. Only new
ones fail, and they fail as a hang rather than an error a tenant would see. Nothing alerts on
"Database stuck in Provisioning".

## Fix

Narrow rather than remove: `secrets: [get, list, watch]` — exactly the verbs the delegated
Roles grant, which is what escalation prevention checks against. `create`/`delete` stay
dropped, so most of the hardening intent survives. Rendered output verified;
`scripts/gitops-validate.sh` passes.

## Follow-ups worth considering

- **A guard.** This class — a least-privilege patch that removes a permission needed for
  *delegation* rather than for direct use — is invisible to review and to every test, because
  RBAC is not exercised anywhere but a live cluster. The cheap version is a smoke check that
  provisions a throwaway Database and asserts it reaches Ready.
- **An alert.** A `Database` in `Provisioning` past a few minutes should page; today it is
  silent forever.
- Re-check the other least-privilege RBAC patches in `deploy/gitops` for the same
  delegation-versus-direct-use mistake.
