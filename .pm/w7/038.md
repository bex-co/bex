# 038 — Two findings on the forum service: credentials baked into its image, and `autoDeploy` that never fires

Both found 2026-08-20/21 while finishing `w7/m77`'s multisite work. Neither is fixed.

## 1. Tenant database credentials are baked into a registry image

`config/multisite.yml` **is** in the `beancount-forum` image (verified from a throwaway
container running the same digest, so nothing could have been copied in), and it carries
**real credentials** — 0 placeholder tokens, 2 live database passwords, plus both database
FQDNs:

```
placeholders: 0
real-looking password lines: 2
  host: dpg-d9rrkoc4h4mc73edurp0-rw.default.svc.cluster.local
  host: dpg-d9rs3ee0ccis738kc7c0-rw.default.svc.cluster.local
```

The repo's own template says `# NOTE: passwords below are placeholders … Do NOT commit real
credentials.` The intent was right; the image does not honour it.

Anyone able to pull that image — any holder of the per-App registry credential, anyone with
registry access, and anything that mirrors or caches layers — obtains two tenant Postgres
passwords. Rotating those passwords does not invalidate the copy in older image layers.

How they got there is unresolved: no version of `_infra/docker/Dockerfile` in the fork's
history copies the file (checked every revision), yet the layer contains it with an mtime
matching build time. Establish that before assuming a fix is complete — the same path may
be baking other files in.

**`b6cbd62` on `bex-co/discourse_docker` is the fix** and should be kept: it ships a
placeholder-only template and resolves it at boot from platform-injected env, so the image
carries no credential. It is pushed but **not yet built** (see finding 2), so today's image
is still the credential-bearing one.

## 2. `autoDeploy: true` on a service whose CR has no `repo` — push-to-deploy silently never fires

| App | namespace | `spec.repo` | autoDeploy |
| --- | --- | --- | --- |
| `tea-d98210cbbpdc73dcrkvg-beancount-forum` (**live**) | tenant | **`<UNSET>`** | true |
| `beancount-forum` (legacy, phase Failed) | `default` | `…/discourse_docker.git` | true |
| every other tenant App | tenant | set | — |

The git webhook matches a push against `App.spec.repo`. With that field empty the live
service can never match, so a push to its repository redeploys nothing. Confirmed: a
correctly signed push webhook for the right repo and branch returned `200 {"redeployed":[]}`.

The service is therefore **not** on push-to-deploy despite reporting that it is, and has
presumably not auto-deployed since the ADR043 namespace migration — the legacy App in
`default` kept the repo binding and the tenant-namespace projection did not. Its builder is
still `dockerfile` with a `dockerfilePath`, so the repo is genuinely how it is meant to
build.

Two things worth deciding together: whether the projection should carry `repo` (it looks
like a migration gap, and `w7/m77` is exactly the migration), and whether `autoDeploy: true`
with an empty `repo` should be refused or surfaced rather than silently inert. The second is
the general defect — the field claims a behaviour the resource cannot perform, and nothing
reports it.

## Related, already handled

A deploy can still be triggered without the API: the App carries a
`bex.co/deploy-hook-token` annotation, and `POST /v1/deploy-hooks?key=…` returns a deploy id
and rolls the pod. That redeploys the **current image** — it does not rebuild — which is why
it did not pick up `b6cbd62`.
