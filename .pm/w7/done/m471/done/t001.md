## Objective

Give `twofactor.Gate` a way to answer, for a member who is not making a request, whether they and each of their keys would meet a login requirement. It must use the same rules and caches `Check` uses, so the confirmation list and the enforcement cannot disagree.

## Context

- `lego/backend/internal/twofactor/gate.go`: `checkTwoFactor` (lines 286-312) and `checkGoogle` (332-368) decide per principal; `enrollmentOf`, `googleAccountOf` and `keyCreatorOf` are the 60 s caches.
- 2FA rules: a member counts when Kratos reports an enrolled factor. A subject Kratos does not know is a platform principal, exempt for a member and refused for a key (`unattributed`). An API key with no creator is refused.
- Google rules for a member with no request: the account check of `checkGoogle`'s default branch, a linked Google account matching the member's email. For a key: an unrecorded stamp is exempt; a recorded stamp that is not Google, or a creator whose account does not match, is refused (`refuseKey`).
- API keys carry `CreatedBy` and `CreatedSignIn` (`apikeys.APIKey`, read from Hydra metadata in `apiKeyFromHydra`). SSH keys carry `Subject` and `CreatedSignIn` (`store.SSHKey`).

## Steps

1. Add an exported assessment beside `Check`, for example `AssessMember(ctx, required, subject) (meets bool, err error)` and `AssessKey(ctx, required, creator string, signIn core.SignIn) (meets bool, err error)`. Build both from the existing check helpers so no rule is copied. Turn `core.ErrForbidden`-class refusals into `meets=false`, and pass lookup failures through as errors.
2. An assessment is not a refusal. It must not increment `bex_workspace_two_factor_refusals_total`. Separate the counting from the decision if needed.
3. Add a table test for both requirements and their combination in `gate_test.go` or a new `gate_assess_test.go`: enrolled, unenrolled, non-human, no creator, Google stamp with a matching and a non-matching account, other stamp, unrecorded stamp, and lookup failure.

## Acceptance criteria

- [x] For every case in the table, the assessment agrees with what `Check` decides for the same principal.
- [x] The refusal counter does not move during an assessment.
- [x] `cd lego/backend && go test ./internal/twofactor/` passes.

## Out of scope

- Live sessions: a member's current sign-in method is not read.

## Outcome (2026-11-17)

`twofactor.Gate.AssessMember`, `AssessAPIKey` and `AssessSSHKey` (`gate.go`) run `Check`'s own decision (`decide`, split out of `check`) over its caches. An SSH key is its own entry point because the gate treats it unlike an API key under 2FA: a subject Kratos does not know is exempt for an SSH key and refused for an API key. Refusals are counted through the scope (`scope.metrics`), which only `Check` and `CheckOrganization` set, so assessments and the lock-out guard `SignedInWithGoogle` count nothing. `gate_assess_test.go` pins the truth table and runs every row through `Check` too.
