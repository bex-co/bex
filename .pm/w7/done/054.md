# 054 — The tenant-view canary's metrics stage is the only stage with no retry budget, and it has opened four "Tenant view is broken" issues in five days

Why: an alert that fires when nothing is wrong trains people to ignore it, which is the opposite of what `w3/m83` built this canary for — "a silent regression … surfaces as a GitHub issue within six hours". Issue **#71 was open for 9h41m** asserting production's tenant view is broken (opened 2026-09-16T12:00:25Z, auto-closed 21:41:21Z when the next run passed), and the cause is the probe's own query shape rather than a product defect — established in sweep 32, after this note's original timing explanation was falsified by its own control case.

**Estimate:** 45m (the budget, splitting the cpu/memory assertions, and an explicit `startTime`) · **Severity:** minor (alerting reliability, not tenant-facing) · **Attribution:** synthetics/CI · **Worker:** worker7

## Root cause: cpu is a `rate()`, and a just-woken pod cannot fill its lookback

Established 2026-09-16 (sweep 32) by reading the query builder and six consecutive production runs. **This supersedes the "2–4 second" timing argument this note was filed with — see "What this corrects" below.**

- **cpu and memory are not the same kind of query.** `promResourceQueryFor` (`lego/backend/internal/metrics/source.go:262-284`) builds memory as a plain gauge — `sum by (pod) (max by (pod, container) (container_memory_working_set_bytes{…}))` (line 273) — but cpu as a **rate**: `sum by (pod) (max by (pod, container) (rate(container_cpu_usage_seconds_total{…}[60s])))` (line 282), where the lookback is `stepSeconds(req.Resolution)` (line 204-209) and the probe sends `resolutionSeconds=60`.
- **A rate needs two samples in its lookback; a gauge needs one.** `kubernetes-cadvisor` scrapes every **15s** (`deploy/gitops/base/prometheus.yaml:256`). A pod that has existed ~12s has **0 or 1** samples inside the 60s lookback, so `rate()` yields no points at all. Memory over the same instant would return a value from a single scrape.
- **The probe can never report that asymmetry**, because `for metric in cpu memory` checks cpu first and `exit 5`s immediately (`scripts/tenant-view-liveness.sh:194-208`). Every failure therefore names `/v1/metrics/cpu` and **memory is never queried** — so the log cannot distinguish "cpu's rate is cold" from "the whole metrics pipeline is blank".
- **Stage 3 is still the only stage with no budget.** Stage 1 waits `BEX_CANARY_WAKE_BUDGET` (60s); stage 2 waits `BEX_CANARY_LOG_BUDGET` (180s); stage 4 accepts an event up to `BEX_CANARY_EVENT_WINDOW` (3600s) old. Stage 3 queries once and fails on an empty series.
- **Stage 3 also sends no window at all.** Stages 2 and 4 pass an explicit `startTime=$WINDOW_START` (lines 150, 167, 215); stage 3 sends only `resource` and `resolutionSeconds`, falling back to `defaultMetricSpan = time.Hour` (`metrics/service.go:73,183`). The script's own comment (lines 191-192) states the assumption that breaks: _"Defaulted window is the last hour … which a service that just served a request **always populates**."_ A one-hour window does not help when the series is a rate whose lookback is empty.

| 35153705860   | 2026-09-16T21:40:48Z | 9s   | **pass** (run green)     |

**Wake duration does not discriminate**: across seven runs a 9s wake produced **three passes and two failures**, while both 12s wakes failed. The variable that matters is how long the pod had already been alive when the query ran — i.e. whether ≥2 cAdvisor scrapes had landed — which the wake time does not measure, because the activator may have started the pod before the probe's own request completed.

### What this mechanism does NOT explain, stated plainly

The rate-lookback account above explains every **failure**: a pod alive ~12s cannot put two cpu samples inside a 60s lookback, so the series is empty. It does **not** explain the **passes**. With a 9s wake and stage 3 querying seconds later, the pod is ~12s old — so by this note's own mechanism run `35153705860` should have failed, and it passed cleanly (cpu *and* memory carrying samples, events 8s old).

So something had already started that pod before the probe's request, in at least three runs, and **this note does not know what.** Candidates, none probed: unrelated traffic to `hello-go.onbex.co` inside the preceding hour; the activator holding the pod longer than the 15m idle TTL under some conditions; or the 1-hour default query window catching a still-recent earlier wake. The decisive measurement is the **pod's age at stage-3 query time**, which no run currently records.

This is recorded rather than smoothed over because sweep 32 replaced one overconfident explanation (the "2–4 second" timing story) with another that is correct about the failures and silent about the passes. The fix below does not depend on resolving it — a budget longer than two scrape intervals makes the stage pass in either case — but any claim that the mechanism is fully understood would be premature.

The failure history still fits a racing probe rather than one outage: tracking issues at **three different stages** (#63, #68 at `2/4 logs`; #70 at `4/4 events`; #71 at `3/4 metrics`), #68 auto-closed **six minutes** after opening, and runs pass and fail in succession with no related deploy.

## What this corrects

Filed, this note argued stage 3 fails because it queries "roughly 2–4 seconds" after the first 200, citing a throwaway fixture (`qa-20260916-f8c156-met`) that showed 1 cpu sample at ~30s, 2 at +45s, 3 at +90s. That measurement was real but I read the wrong cause from it: the samples were sparse **because cpu is a rate needing two scrapes**, not because "metrics take ~30s to start". The 05:11 run then falsified the timing framing outright — same 9s wake, stage 3 passed. The mechanism above explains both the passes and the failures; the original framing explained only the failures.

## Explicitly NOT established

- **The owed 0–3s fixture test is no longer needed, and is withdrawn.** It was the right test for the wrong theory. The question it was meant to settle — does a just-woken pod return zero cpu samples — is answered deterministically by the query builder (`rate(...[60s])`, source.go:282) against the scrape interval (15s, prometheus.yaml:256): two samples cannot exist in a window the pod has not been alive for. No fixture can make that false. What a fixture would still add is the exact pod-age threshold where cpu starts returning points; that is a nice-to-have, not a blocker on the fix.
- **`w6/m110` is excluded for this canary specifically.** That bug was a pod-name selector that only matched the two-segment `<app>-<hash>-<suffix>` form, blanking cpu **and** memory for services whose object name crossed the 58-char `generateName` truncation (source.go:247-255). The canary's app is `hello-go` — far under the threshold, so its pod name is the matched form. A recurrence of that class would also blank memory, which this probe never reaches.
- **A different genuine metrics regression is not excluded.** Because the loop exits on cpu, no run in the table ever queried memory. If memory is also empty, something larger is wrong and this note's mechanism is only part of it — which is exactly why the fix below must query both and report them separately.
- **The canary itself was not reproduced.** Its service lives in the `bex-canary` workspace behind a scoped key this run does not hold and did not request, so the measurements above cover the _class_ on an equivalent free service, not the canary.

## Fix

Three changes, in this order — the first two are the correctness fix, the third is what makes the stage diagnostic:

1. **Give stage 3 a budget, sized off the rate lookback, not off a guess.** Poll for up to `BEX_CANARY_METRIC_BUDGET` before failing. The floor is **strictly greater than two cAdvisor scrape intervals** (2 × 15s = 30s) so the `[60s]` rate can hold two points; 90–120s gives margin for a slow first scrape. A budget shorter than 30s cannot fix this no matter how it is spelled.
2. **Query memory independently of cpu, and report both.** Replace the `for metric in cpu memory` early-exit with one that evaluates both and prints each result. Target behavior: the stage passes when **both** carry samples, and when it fails the log says _which_ — `cpu empty / memory ok` is a cold rate, `cpu empty / memory empty` is a pipeline failure worth paging about. Today both print the same line.
3. **Send an explicit `startTime`, as stages 2 and 4 do.** Relying on `defaultMetricSpan` couples the probe to a server default it does not control; the comment at lines 191-192 already asserts a window the request never actually names.

**Do not** weaken the assertion to "a 200 is enough" — an empty series behind a 200 is precisely the `w6/m110` failure this canary exists to catch. The budget must expire before the stage passes.

If stage 3 still fails **with** a ≥30s budget and memory empty alongside cpu, that is a real pipeline regression and deserves its own filing.

## Resolved 2026-09-17 (`/loopx w7`)

Stage 3 now polls to a budget instead of asserting once, and reports cpu and memory separately. All three changes this note specified are in `scripts/tenant-view-liveness.sh`:

1. **`BEX_CANARY_METRIC_BUDGET`, default 120s.** Sized off the mechanism, not a guess: cpu is `rate(container_cpu_usage_seconds_total[60s])` and a rate yields nothing until two samples land inside its lookback, while cAdvisor scrapes every 15s. A budget under 30s cannot work however it is spelled; the comment in the script says so, so the next person does not shrink it.
2. **cpu and memory polled independently, both reported.** The old `for metric in cpu memory` loop exited on cpu and never asked memory, so a cold rate and a dead pipeline printed the same line. The failure output now distinguishes them and says which reading means what — `cpu EMPTY / memory present` points at the budget, `both EMPTY` points at the `w6/m110` selector class.
3. **Explicit `startTime=$WINDOW_START`**, matching stages 2 and 4, instead of relying on the server's `defaultMetricSpan`.

The assertion was **not** weakened: the stage still fails when the budget expires with either series empty, so an empty series behind a 200 — the `w6/m110` failure this canary exists to catch — still fails the run.

Verified: `bash -n` clean, and CI's own gate (`shellcheck --severity=warning scripts/lib/canary-api.sh scripts/tenant-view-liveness.sh`, `.github/workflows/scripts.yml:140`) passes. The workflow sets no budget env, so the 120s default applies with no workflow change.

**Still open, and deliberately not closed by this fix:** the question this note recorded in sweep 37 — the rate-lookback mechanism explains every observed failure but **none of the three passes**, since a 9s wake leaves the pod ~12s old and it passed anyway. Something warmed that pod before the probe's request and no run records pod age at query time. The budget makes the stage correct either way, which is why it did not need settling first; it remains worth knowing.
