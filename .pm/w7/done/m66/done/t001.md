## Objective

Emit `build_started` and `build_ended` as distinct service events — the single largest bex↔Render events gap. Render's timeline shows Build and Deploy as two separate event pairs; bex today folds the build into `deploy_started`/`deploy_ended` and `internal/events/service.go:88` still claims build events "have no accepted bex mechanism or durable source." That rationale is stale: ADR034's in-cluster BuildKit build Jobs (`bld-<name>-gen-<generation>`) are a durable, observable lifecycle. Surface it through the same control-plane-reconciler → `service_event_facts` path that already produces `image_pull_failed`/`server_failed`/`server_available`.

## Context

- Fact emitter (the precedent path): `lego/backend/internal/store/reconciler.go` observes `App.status` transitions and writes `service_event_facts` rows; fact type constants live in `lego/backend/internal/store/event_facts.go:33-43` (`EventFactImagePullFailed`, `EventFactServerFailed`, …).
- Events vocabulary: `lego/backend/internal/events/service.go` — Render-named type constants (`service.go:121-181`), the package-doc vocabulary table (`service.go:33-95`), and the `## Omissions` note at `service.go:86-94`.
- Build Jobs are named `bld-<name>-gen-<generation>` in `BEX_BUILD_NAMESPACE` (see root `CLAUDE.md` and ADR034); the operator already tracks build progress in the `App` phase/revision — confirm exactly which `App.status` field(s) mark build start and build terminal status.
- The operator is DB-free, so the **operator must expose** build start/end in `App.status` (add fields to `lego/types/v1alpha1` + operator status writes only if not already present); the **reconciler reads status and writes the fact**.
- Details shape: reuse the existing typed, structurally-redacted detail columns — `build_ended` carries `details.status` (succeeded|failed|canceled) like `deploy_ended`; associate to the deploy via the existing `deployId` linkage where available.

## Steps

1. Trace how the operator surfaces build lifecycle in `App.status` today; if build start/terminal aren't observable, add minimal status fields (`types/v1alpha1` + operator) — no new controller, just status.
2. Add `EventFactBuildStarted = "build_started"` / `EventFactBuildEnded = "build_ended"` to `event_facts.go`; add `TypeBuildStarted`/`TypeBuildEnded` to the Render-named block in `service.go` and to the package-doc vocabulary table.
3. In `reconciler.go`, observe the build-phase transition and insert the two facts idempotently (one `build_started` per build, one `build_ended` with status), mirroring the `image_pull_failed` emission (dedupe key + no double-emit on resync).
4. Confirm the composed read (`internal/store/events.go`) and `events/service.go` pass the new types through unchanged (generic type + typed details).

## Acceptance criteria

- [ ] A repo/Dockerfile-backed deploy yields exactly one `build_started` and one `build_ended` (with `details.status`) event, distinct from the deploy pair; image-backed services with no build phase emit neither.
- [ ] Facts are idempotent across reconciler resyncs (no duplicate rows).
- [ ] The new types carry no arbitrary value — only typed scalar detail columns (redaction discipline preserved).
- [ ] `service.go:88`'s "build_started/build_ended … have no accepted bex mechanism or durable source" claim is removed/corrected (full doc reconciliation is t006).
