## Objective

Emit `job_run_ended` when a one-off job finishes, with `details.status`. Render's events include `job_run_ended` ("one-off job execution completed", carries a status); bex today emits only `job_started` (`jobs.Create`) and `job_canceled` (`jobs.Cancel`) — both audit-verb-derived — and never records the job's own terminal outcome. Close the completion beat.

## Context

- Existing job event mappings: `internal/events/service.go` `eventTypes` map — `"jobs.Create": TypeJobStarted`, `"jobs.Cancel": TypeJobCanceled` (`service.go:215-216`); constants `TypeJobStarted`/`TypeJobCanceled` in the bex-named block.
- `job_started`/`job_canceled` come from `audit_events` (a caller action); `job_run_ended` is an **observed** terminal outcome, so it belongs on the `service_event_facts` reconciler path (t001), not the audit map — unless a one-off job's completion is already recorded in `App.status`/a jobs table the store reads.
- Confirm where one-off job runs are tracked (jobs feature `internal/apps`/`internal/store`) and which signal marks terminal success/failure.

## Steps

1. Determine the durable terminal signal for a one-off job run (App.status jobs/run record vs. Job object phase).
2. Add `job_run_ended` as a fact type + vocabulary entry; emit it idempotently from the reconciler with `details.status` (succeeded|failed).
3. Verify it composes into the feed and filters via `type=job_run_ended`.
