## Objective

Surface `pre_deploy_started` and `pre_deploy_ended` as standalone events, matching Render. bex already runs a pre-deploy Job (`predeploy-<name>-gen-<generation>`, w1/m33, ADR004 § Pre-deploy command) and already computes its outcome as `details.preDeployStatus` (running|succeeded|failed) — but only ever attached to the single `deploy_ended` event, never as its own timeline entries. Promote the same observed signal to two distinct events via the reconciler-fact path built in t001, while keeping the existing `preDeployStatus` on `deploy_ended` for back-compat.

## Context

- The pre-deploy status is already threaded into `deploy_ended` details: `internal/events/service.go` `Details.PreDeployStatus` (added w1/m33) and the GraphQL/REST detail field `preDeployStatus`.
- Pre-deploy Jobs run in `BEX_BUILD_NAMESPACE` as `predeploy-<name>-gen-<generation>` (root `CLAUDE.md`).
- Emission path + fact-type registration follow the t001 pattern exactly (`event_facts.go` constants, `reconciler.go` observation, `service.go` vocabulary).
- Render treats these as deploy-lifecycle events (`pre_deploy_started`, `pre_deploy_ended` with a status), sequenced before `deploy_ended`.

## Steps

1. Add `EventFactPreDeployStarted`/`EventFactPreDeployEnded` (`= "pre_deploy_started"`/`"pre_deploy_ended"`) and the `TypePreDeploy*` vocabulary entries.
2. In `reconciler.go`, observe the pre-deploy Job phase (or the `App.status` field that reflects it) and emit the two facts idempotently, with `build_ended`-style `details.status` on the ended event.
3. Keep `deploy_ended.details.preDeployStatus` populated (no removal) so existing clients/tests don't regress.
4. Ensure services with no pre-deploy command emit neither event.

## Files

- `lego/backend/internal/store/event_facts.go`
- `lego/backend/internal/store/reconciler.go`
- `lego/backend/internal/events/service.go`
- `lego/types/v1alpha1/*` / `lego/operator/**` only if the pre-deploy phase isn't already observable in `App.status`

## Acceptance criteria

- [ ] A service with a pre-deploy command produces one `pre_deploy_started` and one `pre_deploy_ended` (with `details.status`) per deploy; a service without one produces neither.
- [ ] `deploy_ended.details.preDeployStatus` still populated (back-compat intact).
- [ ] Facts idempotent across resyncs; redaction discipline preserved.
