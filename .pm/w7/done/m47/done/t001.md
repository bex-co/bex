## Objective

Stand up the Metronome-side configuration the emitter targets, and capture it as a repeatable runbook. Metronome separates metering from rating: bex sends events, Metronome aggregates them into billable metrics and rates them via rate cards. This task creates those objects (in the Metronome dashboard/API) and documents the exact steps so the setup is reproducible for a fresh Metronome org.

## Context

- `docs/ADR040-billing-metronome.md` §5 (event/metric mapping) + §8 Phase 0.
- One `event_type` per meter kind: `instance_seconds`, `egress_bytes`, `build_seconds`, `storage_gb_seconds`. Numeric quantity travels as string `properties.value`; dims `tier`, `resource_kind`, `service_id`.
- Billable metric = `sum(properties.value)` filtered by `event_type`, grouped by `tier` / `resource_kind`.
- Price seed: `lego/backend/internal/pricing/pricing.yaml` — every `usdPerSecond` / `usdPerByte` / build / storage rate becomes a rate on the matching metric, preserving ADR030's discount policy (30% off Render; bandwidth 90% off).
- No bex code in this task — Metronome config + a docs runbook only.

## Steps

1. Create a Metronome org/sandbox; generate an API key (bearer) → hand to ops as the out-of-band `BEX_METRONOME_TOKEN` (do not commit).
2. Create the four billable metrics (sum over `properties.value`, grouped by `tier`/`resource_kind`).
3. Create products (one line item per meter family) + a rate card mirroring `pricing.yaml`'s tiers/rates exactly.
4. Write the runbook (new file under `docs/`, e.g. `docs/runbooks/metronome-billing-setup.md`) with the exact objects, field mappings, and how to re-derive rates from `pricing.yaml`.
5. Cross-link the runbook from `docs/ADR040-billing-metronome.md` §8 Phase 0.
