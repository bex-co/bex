## Objective

Make the operator notice that a pod cannot start because an env var references a Secret that is not resolvable in its namespace, and say so on the App's status — instead of leaving the deploy to fail an unexplained health check minutes later.

## Context

- The production symptom was pod `CreateContainerConfigError: secret "dpg-<id>-app" not found`, with no status condition, no event, and no error beyond an eventual health-check failure. Kubernetes already reports the reason on the pod; nothing surfaced it upward.
- `lego/operator/internal/controller/app_controller.go` already has the status/condition vocabulary — `r.fail(ctx, app, "<Reason>", err)` plus `meta.SetStatusCondition` on `Ready` — so this is a new reason, not new machinery.
- The controller already inspects child health elsewhere (`app_child_health_envtest_test.go`, `stuck_pod_test.go` are the nearest existing patterns) — reuse that path rather than adding a second pod-watching mechanism.
- Distinguish transient from terminal: a Secret that has not been created *yet* during a normal rollout is not the same as one that will never exist. The condition should not flap on a healthy deploy.

## Steps

1. Find where child-pod state is already read and extend it to recognize the unresolvable-config class (missing Secret/ConfigMap key or object).
2. Set a specific `Ready=False` reason naming the missing object, distinct from a generic health-check failure.
3. Debounce so a normal rollout does not transiently report it — follow the existing single-tick debounce precedent in `store/reconciler.go` (`debounceUnhealthy`, w3/m78) rather than inventing another.
4. Confirm the condition clears once the dependency resolves.

## Files

- `lego/operator/internal/controller/app_controller.go`
- `lego/types/v1alpha1/app_types.go` (if a status field is added)

## Acceptance criteria

- [x] An App whose pod cannot resolve a referenced Secret reports a specific condition naming it.
- [x] The condition does not fire during a normal healthy rollout.
- [x] The condition clears when the dependency becomes resolvable.
- [x] `make test` green.

### Outcome (2026-08-09)

The machinery already existed and the class was simply missing from it. `stuckPodMessage` (w9/011) recognised `CrashLoopBackOff` and `ImagePullBackOff`/`ErrImagePull` — but not `CreateContainerConfigError`, which is the one state where the pod **never starts at all**, so it neither crash-loops nor fails a pull. That is why the incident's first leg had no signal: the two existing diagnoses are both about a container that ran or tried to.

One `case` added to the existing switch, passing the kubelet's own message through (it already names the object exactly — `secret "dpg-…-app" not found`) plus the actionable cause. No new pod-watching path, exactly as the task asked.

**On step 3's debounce.** Not added here, deliberately. The condition is explanatory and lives inside a branch where the App is *already* not-ready; it is recomputed from live pod state every 5s, so a Secret that materialises a moment later is corrected on the next pass. Debouncing would delay the explanation for no benefit and add reconciler state. Where transience genuinely matters is the *projection* layer — an event or a page for a momentary blip is real noise — and `debounceUnhealthy` already sits exactly there, wrapping the single observation site (`reconciler.go:318`). t002 relies on it and pins it with a test rather than adding a second mechanism.

## Out of scope
