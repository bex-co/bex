## Objective

Carry t001's reason to where users and agents actually look: the deploy's failure reason and the service event feed — so "Update Failed" becomes "could not start: linked database Secret … is not available".

## Context

- `docs/ADR052-notifications.md` describes the composed feed (`deploys` + `audit_events` + `service_event_facts`) — the existing carrier, so no new bus is needed.
- `lego/backend/internal/store/reconciler.go` already observes App state and closes deploys with a reason (`recordDeploy`, `ObservedServiceState`, `reasonCode`) — the seam to extend.
- `w7/m66` shipped the lifecycle-fact vocabulary (build / pre-deploy / `job_run_ended` / `branch_deleted`) and `w3/m78` pushed observed-lifecycle facts end to end; follow those shapes rather than inventing a parallel one.
- The deploy-failure email (`w7/m44`) already names the failing commit and links to logs — a specific reason improves it for free, so check the composed text still reads correctly.

## Steps

1. Thread t001's reason through the observed-state seam into the deploy's recorded failure reason.
2. Emit the corresponding service-event fact using the existing vocabulary.
3. Verify the reason reaches REST, GraphQL, and MCP through the shared core, and that the dashboard renders it.
4. Check the deploy-failure email still composes correctly with the more specific reason.

### Outcome (2026-08-09)

The carrier already existed and already reached every surface; the diagnosis was being dropped one step before it. `failureReasonFor` switches on the Ready reason and had no case for `CreateContainerConfigError`, so a config-error deploy fell through to the literal string **"the deploy did not become healthy within the health-gate window; check the service logs"** — the generic line the incident reported — while the operator already held the exact missing object. Adding the case makes `deploys.failure_reason` carry it, and from there it rides an existing, fully-wired path: REST + MCP share `renderDeploy.FailureReason`, GraphQL has `failureReason`, and the dashboard renders it in `deploy-header.tsx`. Verified all four rather than assumed.

`observedServiceStateFor` had the same omission with a different consequence: during an open deploy only `ImagePullBackOff` and `CrashLoopBackOff` counted as concrete container failures, so an unresolvable config was treated as ordinary rollout progress and the instance went **unobserved for the whole health-gate window**. Extracted the list into `concreteContainerFailure` and added the case, with the classification pinned in both directions — too narrow loses the observation, too wide reports a failure on every ordinary rollout and trains people to ignore the signal.

**No new service-event fact type.** `service_event_facts.reason_code` is a CHECKed closed vocabulary (migration 0043) and the fact types have their own CHECK, so a new kind costs a migration. It would carry no signal the deploy row does not already carry to the same surfaces, so the deploy's free-text `failure_reason` is the right home and the vocabulary stays closed.

**Beyond the task, because the check found it empty:** step 4 asked whether the failure email still composes. It did — because it never referenced the reason at all. w7/m44 enriched that email with the commit message and a logs link, and it still could not say what went wrong. Since this is the first thing most people read when a deploy breaks, the reason is now threaded through `DeployNotification` → `deployDetails` → the failed-path body, ahead of the commit block. Byte-identical when the reason is empty (pinned by test), and failure-only, so a "started"/"succeeded" mail can never carry it. Recorded in `docs/render-artifacts/notify-on-fail.md` as a deliberate extension over Render's captured email.
