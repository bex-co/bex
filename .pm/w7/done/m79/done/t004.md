## Objective

Check the new signals are consistent across REST, GraphQL, MCP, and the dashboard, and reasonable against render.com's deploy-failure vocabulary.

## Context

- Render exposes deploy status/reason and service events; bex mirrors that surface (`docs/ADR006-bex-api.md`, ledger in `docs/ADR018-render-parity.md`).
- New reason codes are a compatibility surface: an added value must not break a client that switches on the documented set. Check how the existing codes handle unknown values before adding to them.

## Steps

1. Compare the new reasons/events across REST, GraphQL, and MCP for the same failing service.
2. Confirm the dashboard presents them usefully — the reason should be readable without opening logs.
3. Compare with Render's vocabulary; where bex is more specific, record it as a deliberate extension rather than drift.
4. Update `docs/ADR018-render-parity.md` and `docs/ADR052-notifications.md`'s gap register where evidence changed.

## Acceptance criteria

- [x] Reasons and events agree across all three API surfaces.
- [x] The dashboard presents the reason without requiring a log dive.
- [x] Extensions beyond Render's vocabulary are recorded deliberately.

### Outcome (2026-08-09)

Both signals are consistent across the three surfaces by construction rather than by coincidence: `failureReason` rides `renderDeploy` (shared REST + MCP) plus a GraphQL field, and `publicRoutingNotice` rides `renderService` (shared REST + MCP) plus a GraphQL field. Checked all six rather than inferred from the one-core/thin-adapters rule.

Dashboard: the deploy header already rendered `failureReason`, so t002's change lands there for free; the service-detail header now renders `publicRoutingNotice`.

**Render comparison.** Neither field exists on Render, and for opposite reasons. `failureReason` was already recorded as a bex extra in w9/011 — Render surfaces the cause through its own UI rather than the deploy object. `publicRoutingNotice` describes a state Render **cannot reach**: it always has a platform host to hand out, so "exposed but no derivable public host" is a bex-only condition created by the `w7/m54` PSL decision. Both stay `omitempty`, so a Render-shaped client sees no new keys unless the state applies. Recorded in `docs/ADR018-render-parity.md` (a new Services row) and `docs/render-artifacts/notify-on-fail.md` (the email extension).

**No new reason codes were added**, so the compatibility concern this task flagged — a client switching on the documented `reason_code` set — does not arise. See t002 for why the closed vocabulary stayed closed.
