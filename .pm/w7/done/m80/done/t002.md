## Objective

Three independent timers bound how long a rollout may take to become healthy, they disagree, and the tightest one silently wins. Make all three read 15 minutes — Render's documented deploy window — and assert they agree so they cannot drift apart again.

## Context

Today:

| timer                                    | value                      | set where                                       |
| ---------------------------------------- | -------------------------- | ----------------------------------------------- |
| `startupProbe` budget                    | none (does not exist)      | —                                               |
| `Deployment.spec.progressDeadlineSeconds` | unset → **600s** (k8s default) | never set by the operator                    |
| bex-api `DeployGateTimeout`              | **180s**                   | `lego/backend/internal/store/reconciler.go:72`  |

So the effective budget is **3 minutes** — a number that is the accidental minimum of three unrelated choices, against Render's "If this condition is not met within 15 minutes, Render cancels the deploy and continues routing traffic to your service's existing instances."

Grounding for why 3 minutes is genuinely tight: in the `gen-78` production deploy, the image pull alone took **51.7s** (498 MB image) before the container even started.

Note the two values live in different modules — the operator (`lego/operator`) and bex-api (`lego/backend`) — which is how they drifted. They must move together.

## Steps

1. Set `ProgressDeadlineSeconds: 900` on the projected Deployment spec.
2. Raise `defaultDeployGateTimeout` from `3 * time.Minute` to **`18 * time.Minute`**.
3. Add a comment at each site naming the other two timers, so the next person to touch one finds the others.

> **Corrected while implementing.** The task originally said to set the deploy gate to 15m so all three timers were equal. That is wrong, and the new test caught it. The sibling gates already encode the real rule: a control-plane budget must be strictly **longer** than the mechanism it observes (build Jobs 30m → gate 35m; pre-deploy Jobs 10m → gate 12m). `DeployGateTimeout` observes the rollout, whose budget is 15m, so it must exceed it — an equal gate races the Deployment's own `ProgressDeadlineExceeded` and can win, reporting the generic "did not become healthy within the health-gate window" in place of the specific verdict, which is precisely the vagueness w7/m79 set out to remove. 18m carries the same ~20% margin the other two gates use.
>
> So the invariant is **not** "three equal numbers": the two mechanism timers (`startupProbe` budget, `progressDeadlineSeconds`) are equal to each other at 15m; the observer sits above them.
