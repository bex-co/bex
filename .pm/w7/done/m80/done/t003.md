## Objective

Render has one health-check concept carrying three consequences: gate the deploy, remove from rotation, restart. Kubernetes has three probes. bex currently loads all of it onto `readinessProbe`, which is why boot behavior and steady-state behavior cannot be tuned independently. Add the `startupProbe` that owns the boot phase, so a slow-starting service gets Render's full 15 minutes while steady-state checks stay strict.

## Context

- While a `startupProbe` is running, kubelet **suspends both readiness and liveness**. That is the property that makes the boot budget real, and it is also the precondition that later makes a `livenessProbe` safe to add (`w7/027.md`).
- 15 minutes at a 10s period = `failureThreshold: 90`.
- Render documents no explicit grace period; its 15-minute deploy window is the equivalent, which is why t002's number and this one must match.
- Probe kind must track `healthCheckPath` the same way readiness does — after t004 that means TCP when unset, HTTP when set. Build this so t004 changes one shared constructor, not three call sites.

## Steps

1. Factor the probe construction into one helper that returns a `corev1.Probe` for a given handler + timing, so readiness and startup cannot drift in kind or target.
2. Add `StartupProbe` with the same handler as readiness, `TimeoutSeconds: 5`, `PeriodSeconds: 10`, `FailureThreshold: 90`.
3. Assert in a test that the startup budget (`PeriodSeconds × FailureThreshold`) equals `progressDeadlineSeconds` from t002 — derive both from one named constant rather than repeating `900`.
4. Confirm the worker/cron path still carries no probes at all.
