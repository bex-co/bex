## Objective

Give the readiness probe the same budget Render gives a health check: five seconds. Today the operator constructs the probe with only `HTTPGet` set, so every unspecified field takes the Kubernetes default — including `timeoutSeconds: 1`. Render's documented rule is that an instance is healthy if it answers `2xx`/`3xx` **within five seconds**, so bex is five times stricter than the platform it mirrors, and it is strict against a number nobody chose.

## Context

- `lego/operator/internal/controller/deployment_projection.go:110-116` — the whole probe: `HTTPGet` with path + port, no timing fields.
- Inherited defaults today: `timeoutSeconds: 1`, `periodSeconds: 10`, `failureThreshold: 3`, `successThreshold: 1`, `initialDelaySeconds: 0`.
- Observed on production `beancount-cms-v2`: `Readiness probe failed: Get "http://10.244.40.62:3000/": context deadline exceeded (Client.Timeout exceeded while awaiting headers)` on a live pod. Its `/` serves in 1.3–2.9s — every probe is a full SSR render, so the 1s budget can never hold.
- Render: "Render considers a check successful if the instance responds with a `2xx` or `3xx` status code within five seconds."

## Steps

1. Set `TimeoutSeconds: 5` on the readiness probe in `buildContainer`.
2. Leave `periodSeconds`/`failureThreshold` at the Kubernetes defaults (10s × 3 = 30s to leave rotation). Do **not** shorten the period to match Render's 15s: bex probes a tenant-supplied path that may be an expensive render, so halving the interval doubles that cost, and with `replicas: 1` leaving rotation sooner buys nothing — there is no second pod to take the traffic. Record this reasoning in the code comment so it is not "corrected" later.
3. Extend the existing probe assertions in `app_controller_test.go` to pin the timeout, so a future edit cannot silently drop back to 1s.
