# 041 — The three image-pinning residuals `w7/m85` deliberately left open

Why: settling "where does an image bex runs stop" once, for all three residuals together, ends the boundary re-litigation that caused this lineage to be re-reported six times.

Filed by `w7/m85` t006 (2026-08-21) while closing the ADR055 F7 digest-pinning lineage. That milestone's claim is precise: **every image bex builds from, runs, or ships resolves by digest**, and `scripts/image-pin-validate.sh` keeps it that way across four syntaxes. These three sit outside that sentence on purpose. None is a regression; each is a deliberate boundary worth revisiting once, together.

## 1. The static backup CronJobs still fetch `age` at run time

`w7/m85` removed the runtime download from the **managed Key Value** backup path: its encrypt stage now runs `/backup-encrypt`, a first-party entrypoint of the bex image (`filippo.io/age` compiled in), because the operator is in the loop and can resolve its own image off its Pod.

The **etcd** and **OpenBao** CronJobs (`deploy/gitops/charts/{etcd,openbao}-backup/cronjob.yaml`) are plain Helm-templated manifests with no operator in the loop, so they keep w1/m66 F16's mitigation: download the pinned `age` v1.3.1 release, verify it against a SHA-256 committed in the chart, and fail the Job on mismatch — no upload rather than an unencrypted one. That is a real mitigation, not a gap, but it is a weaker one than the KeyValue path now has, and it runs in a stage holding a plaintext etcd/OpenBao snapshot.

Closing it needs one of: a published first-party helper image (the artifact ADR068 #9 named and `w7/m85` argued against for the operator-mediated path), or wiring the operator to render these two CronJobs so they inherit the same self-image mechanism. Prefer the second if the CronJobs are moving under operator management anyway; the first otherwise. Cross-reference [ADR050](../../docs/ADR050-encrypted-platform-backups.md), which now records both halves.

## 2. Developer and e2e shell harnesses start containers by tag

`scripts/auth-mail-e2e.sh`, `auth-oidc-e2e.sh`, `agent-snapshot-secret.sh`, `backup-s3-credentials.sh` and friends `docker run` images by tag. The guard covers workflow `docker run` (CI is part of the supply chain that produces a shipped artifact) but deliberately not these: they run on a laptop against local fixtures and never touch a published image.

The argument for pinning them anyway is that a developer's machine holding production-adjacent credentials is a target too — `backup-s3-credentials.sh` and `agent-snapshot-secret.sh` in particular handle real secrets. The argument against is churn: a dozen more digests to refresh for images no tenant ever reaches. Decide once, then either pin them and widen the guard's fifth syntax, or write the exclusion into the guard's header as a reviewed decision rather than an omission. Sub-hour either way.

## 3. Digests that live outside the guard's four syntaxes

`lego/operator/internal/build/toolchain-freshness.json` carries a `committed:` digest per toolchain entry — JSON, so the guard does not read it. It is currently safe by a different mechanism: `TestToolchainInventoryMatchesCommittedPins` cross-checks each entry against the Go source the guard _does_ read, so the two cannot drift. Worth knowing the coupling exists, since deleting that test would silently create a second unguarded home for image digests.

## Why one note rather than three

They share a question — where does "an image bex runs" stop? — and answering it once is cheaper than three separate triages. The evidence that this matters: the lineage this milestone closed was re-reported six times precisely because each round re-litigated that boundary from scratch.

## Disposition — reviewed and retired, 2026-09-05

1. **Static backup binary download: retain the existing mitigation.** Both charts verify the committed SHA-256 before running age, and `scripts/gitops-validate.sh` guards that verification. A mutable upstream asset cannot execute without matching the reviewed bytes. Download failure stops the backup; it does not permit plaintext upload. Moving these Helm-owned jobs into the operator solely to resolve a self-image introduces ownership coupling without fixing an observed failure. A separate helper image is not required for this inventory finding. Revisit packaging if a measured availability problem or an independently planned backup-job migration warrants it.
2. **Custody scripts: already fixed.** Both `agent-snapshot-secret.sh` and `backup-s3-credentials.sh` use the pinned AWS CLI digest and reject tag-only overrides before invoking Docker. Local fixture-only auth/e2e harnesses remain outside the shipped-image guard as a reviewed boundary. The guard header now distinguishes fixture harnesses from credential-custody helpers, instead of claiming every script only handles local fixtures.
3. **JSON inventory: already guarded.** `TestToolchainInventoryMatchesCommittedPins` couples the inventory to the source pins; it passed during this review. No second parser is needed for the same invariant.

This note is retired as a mixture of implemented fixes and reviewed exclusions, not a claim that runtime binary downloads or fixture tags were removed. The four syntaxes and the separate protections are now documented together in `scripts/image-pin-validate.sh`.
