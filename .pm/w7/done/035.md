# 035 — The operator envtest suite has an intra-spec ordering coupling (`-ginkgo.randomize-all` fails)

Why: a suite that only passes in one spec order will eventually fail for a reason nobody can reproduce; fixing it now, while the failing seed is known, is cheap — and adding randomize-all afterwards keeps the coupling from returning.


## Disposition — done, 2026-09-05

Reproduced the original 1 GiB-versus-5 GiB failure with seed 4242. envtest never garbage-collects children, so deleting `smoke-kv` left its StatefulSet for the next sibling spec. Each spec now uses a distinct KeyValue name and child resource set. Running the whole suite also exposed the same defect in cron history: a completed Job from a sibling leaked into the expected one-run list. Cron fixtures now use distinct names too. `TestControllers` enables `RandomizeAllSpecs` by default, so normal `make test` and CI exercise this contract. All 152 controller specs passed with seed 4242 after both fixture fixes; assertions were preserved.

Found while checking whether `w7/m84`'s new specs introduced ordering coupling, 2026-08-19. They did not — **this reproduces on a pristine tree**, verified by stashing the milestone's changes and re-running the same seed:

```
KUBEBUILDER_ASSETS=… go test ./internal/controller/ -args -ginkgo.randomize-all -ginkgo.seed=4242
→ KeyValue Controller [It] reconciles a tier-sized StatefulSet + headless Service +
  credentials Secret, owner-referenced — FAILED "standard storage floor"
  (keyvalue_test.go:507)
```

86/87 pass; the one failure is a spec inside `Describe("KeyValue Controller")` whose PVC storage assertion depends on a sibling `It` having run first (or not having run first). Ginkgo randomizes only top-level containers by default, so `make test` and CI are green and this is latent, not broken.

It is still worth fixing: a suite that only passes in one order will eventually fail for a reason nobody can reproduce, and the fix is normally per-spec fixtures rather than a shared `smoke-kv` object. Sub-hour to diagnose (run with `-ginkgo.randomize-all` and read which sibling mutates the shared KeyValue), possibly more to unpick if several specs share it.

Consider adding `-ginkgo.randomize-all` to `make test` once it passes, so the coupling cannot come back.
