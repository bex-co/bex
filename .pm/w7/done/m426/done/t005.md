## Objective

Non-interactive use of the `bex` CLI is one environment variable holding an API key, as `RENDER_API_KEY` is for Render's CLI, and the skills pack stops generating a token-exchange step.

## Context

- `lego/cli/internal/bridge/bridge.go:21,62` maps `BEX_ACCESS_TOKEN` to upstream's `RENDER_API_KEY`. Upstream sends `RENDER_API_KEY` as a bearer, so a bex key works there once t002 ships.
- `lego/cli/internal/skills/packgen/packgen.go:72-75` rewrites Render's CI deploy step into a curl + jq `client_credentials` exchange, and `:125` renames `RENDER_API_KEY` to `BEX_ACCESS_TOKEN`.
- `lego/cli/internal/branding/runtime.go:78` rewrites upstream's messages about the variable.
- `docs/bex-cli.md` documents CI authentication as an exchange.

## Steps

1. Add `BEX_API_KEY` as the documented variable for a key, mapped to upstream's `RENDER_API_KEY` when that is unset. Keep `BEX_ACCESS_TOKEN` working.
2. Skills pack: generated CI snippets set `BEX_API_KEY` from a secret and have no exchange step.
3. `docs/bex-cli.md` and `lego/cli/README.md`: non-interactive use is one variable. Keep a short note on the exchange for callers who want short-lived tokens, and say that the released binary gains `BEX_API_KEY` at the next CLI release.
4. Tests: the bridge mapping and its precedence; the packgen output; branding messages name the variable the user set.

## Files

- `lego/cli/internal/bridge/`
- `lego/cli/internal/skills/packgen/`
- `lego/cli/internal/branding/`

## Acceptance criteria

- [ ] `BEX_API_KEY=<key> bex services list -o json` works against a dev stack with no login and no exchange.
- [ ] Generated skills contain no token-exchange recipe.
- [ ] `cd lego/cli && go test ./...` passes.

## Out of scope

- Releasing the CLI: `/release cli` is the user's call.
- `w3/m404` (device-login token refresh in long-running `bex agent` commands).
