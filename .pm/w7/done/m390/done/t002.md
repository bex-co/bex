## Objective

Install Meta's native `muse` binary in the agent image at a pinned version, verified by SHA-256 at build, and make the profile manifest able to declare and verify a native binary alongside the npm adapter.

## Context

- `lego/agent-image/driver/src/install-profiles.ts` installs only `npmPackage` entries and checks each `executable` belongs to its package at the pinned version.
- `lego/backend/internal/agentsession/profiles.go` validates `agent-profiles.json`; the driver loads the same file (`lego/agent-image/driver/src/profiles.ts`).
- Muse's launcher removes superseded binaries, and the latest installer may pull another version: keep the verified binary at a fixed path and point `MUSE_CODE_EXECUTABLE` at it.
- No downloaded artifact is committed (DO_NOT_DO `#NO-ARTIFACTS-IN-GIT`); the binary is fetched at image build.

## Steps

1. Add an optional `nativeBinary {url, version, sha256, path}` field to the manifest schema (Go and TS validators).
2. Teach `install-profiles.ts` (or a Dockerfile stage it drives) to download, verify the SHA-256, install to `path`, and run `<path> --version` to check the version; fail the build otherwise.
3. Make sure no Muse self-update can replace it at runtime (config or read-only path), per the t001 ADR.
4. Keep the Trivy gate and SBOM covering the binary.

## Files

- `lego/agent-image/Dockerfile`, `lego/agent-image/driver/src/install-profiles.ts`, `lego/agent-image/driver/src/profiles.ts`, `lego/backend/internal/agentsession/profiles.go`, `lego/agent-image/README.md`

## Acceptance criteria

- [ ] A build with a wrong SHA-256 or version fails.
- [ ] `profiles_test.go` and the driver profile tests cover a valid and an invalid `nativeBinary`.

## Out of scope

- Adding the `muse` profile entry itself (t003).
