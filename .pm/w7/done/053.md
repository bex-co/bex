# Destructive typed-phrase delete confirms announce as `role=dialog`, not `alertdialog`

Why: four of the most destructive confirmations in the product announce with weaker semantics than their siblings on the same page, and the shared component that fixes it is already in use next door — so this is a call-site change, not a design question.

## A second axis — the phrase convention (sweep 25, corrected sweep 34)

> Originally titled "a second axis of the **same** inconsistency". It is a separate one: the role split and the phrase split have different causes and different fixes, as the closing paragraph of this section now explains.

The ARIA role is not the only thing that differs between destructive confirms. The **webhook endpoint** delete (on `/webhook/<whk-id>/settings`) uses a different typed-phrase convention — ~~and a different implementation~~, which sweep 34 disproved (see the corrected bullet below):

```text
Delete qa-20260916-af104e-wui? No further events will be sent to this endpoint,
and its delivery history will be removed.
To continue, type  delete webhook qa-20260916-af104e-wui
```

- The required phrase is **`delete webhook <name>`** — no `sudo` prefix — where every `SudoCommandField` consumer uses `sudo delete <type> <name>` (`sudo delete web service …`, `sudo delete static site …`, `sudo delete env group …`).
- The phrase is **not** rendered in a `<strong>`; the dialog contains no such element, while `SudoCommandField` renders one. ~~So this confirm is a separate implementation~~ — **wrong, corrected sweep 34.** The absent `<strong>` is simply how `ConfirmDialog` renders its own phrase input rather than evidence of a hand-rolled dialog. `webhook-settings-card.tsx:314` renders `ConfirmDialog`, and its comment says so outright: the typed gate "is the primitive's now — this card had hand-rolled it with its own state and comparison before ConfirmDialog existed." Webhooks are absent from the `SudoCommandField` list because they use the **better** primitive, not a worse one.
- Both halves were observed: typing the sibling convention's phrase leaves **Delete** disabled and nothing happens; typing the dialog's own phrase completes the delete (`webhookEndpoints: []`, no API fallback).
- **Corroborated from another family (sweep 26).** The managed-Postgres delete confirm reads _"Type **sudo delete postgres &lt;name&gt;** below to confirm"_ and renders the phrase in a `<strong>` — the `SudoCommandField` shape. So the `sudo delete <type> <name>` convention holds across services, static sites, env groups and Postgres.
- **The webhook confirm is an outlier on the phrase axis only, not on role (corrected sweep 34).** Its phrase really is `delete webhook <name>` with no `sudo` prefix — that inconsistency stands, and it was observed live. But its role was **never measured**; this note inferred a weaker role from the missing `<strong>`, and the code says the opposite. Since it renders `ConfirmDialog`, it is already an `alertdialog`.
- **The disk confirms use a third phrase convention**, unexamined until sweep 34: `diskSudoPhrase(verb, disk)` (`disk-section.tsx:52`) builds phrases for both `delete` and `restore`. Whoever settles the convention should read that helper too.

These are **not** the same root cause. The role split is four call sites using the wrong primitive; the phrase split is a copy/convention disagreement that exists *within* the correct primitive as well. Fixing the first does not fix the second, and this note previously implied it would.

## Root cause

`dashboard/src/features/services/components/delete-service-card.tsx:105` renders `DialogContent` from `@/common/components/ui/dialog` instead of the shared confirm dialog. The same shape appears at `dashboard/src/features/env-groups/components/env-group-actions.tsx:176,201`, `dashboard/src/features/databases/components/database-confirm-dialogs.tsx:49`, and — found in sweep 34 — `dashboard/src/features/keyvalue/components/key-value-confirm-dialogs.tsx:44-45`, whose `DeleteKeyValueDialog` is a plain `Dialog` wrapping a `SudoCommandField` (`:52-58`), exactly like the other three.

## Target behavior

These four render through `dashboard/src/common/components/confirm-dialog.tsx`, which is built on Radix `AlertDialog` (imports at `:4-13`) and **already supports this exact interaction** via its `phrase` prop — "Phrase-gated — additionally pass `phrase`; confirm stays disabled until the user types it exactly. For actions that destroy data and leave no second signal that they happened." (`confirm-dialog.tsx:37-39`, implemented at `:124-141` — both citations re-verified at HEAD `1331e6203`).

**The controls are in-tree, but not the one this note first named.** Four phrase-gated destructive confirms already render through `ConfirmDialog`, and they demonstrate *two different valid compositions*:

- **The primitive owns the gate** — pass `phrase` directly and let `ConfirmDialog` render the input: `webhooks/components/webhook-settings-card.tsx:314` (phrase `:325`), `services/components/disk-section.tsx:528` (delete, phrase `:533`) and `:615` (restore, phrase `:620`).
- **The caller owns the gate** — wrap a `SudoCommandField` as a child and drive `confirmDisabled`: `keyvalue/components/key-value-confirm-dialogs.tsx:108` (`SuspendKeyValueDialog`, field at `:129`). Its own comment explains the choice: the `SudoCommandField` "is the house sudo control, used identically by the datastore suspend flows — so the gate is the caller's and rides confirmDisabled."

The second composition is the one the four broken sites should probably adopt, since it keeps the existing `SudoCommandField` look and only swaps the surrounding primitive. That makes the fix smaller than "port to the `phrase` prop" — and it is a decision the fix must state, not discover.

## Why it matters

`alertdialog` makes assistive technology announce the dialog's description as an alert; a plain `dialog` does not. Radix `AlertDialog` additionally refuses outside-click dismissal, so a stray click cannot discard a half-typed sudo phrase.

## Not a regression

`w1/m89`'s definition of done was "`grep -rl AlertDialogCancel dashboard/src/features dashboard/src/common` returns only the shared primitive and the shadcn kit" — it consolidated hand-rolled **AlertDialogs** and never covered components that were already plain `Dialog`s. This is the residual left outside that scope, not a backslide.

## What this corrects

Two claims in this note were wrong, and they failed in opposite directions — which is why neither looked suspicious:

1. **The control was misattributed.** The note cited `key-value-confirm-dialogs.tsx` as proof that a sudo-phrase confirm works as an `alertdialog`. That file's **delete** is a plain `Dialog` — a fourth instance of the defect. Its **suspend** is the `ConfirmDialog` one. Reading the file's imports (both primitives are imported) rather than its behaviour is what made the wrong half look like the right one.
2. **A correct example was filed as the defect.** The sweep-25 "second axis" concluded the webhook confirm was "a separate implementation" and "the single outlier on both axes" from an absent `<strong>` element. It renders `ConfirmDialog` and is already correct on role; only its phrase convention diverges.

The common cause is enumerating by `SudoCommandField` — a *helper*, not the behaviour — so every confirm that reaches the same behaviour through `ConfirmDialog` fell outside the search and got reasoned about from symptoms instead. This is the same failure mode sweep 33 found in `052`, which enumerated by `StrField` and missed 15 fields resolved another way. Enumerate by the behaviour, then check which helper each site uses.

Severity: minor. Estimate ~50m — four call sites, the composition decision named under Target behavior, plus any test asserting the current role.

## Resolved 2026-09-17 (`/loopx w7`) — role split fixed; phrase axis split out as `057`

All four plain-`Dialog` confirms now render through `ConfirmDialog`, so each announces as `alertdialog` and refuses outside-click dismissal — a stray click can no longer discard a half-typed sudo phrase. The composition is the one sweep 34 recommended (**caller owns the gate**): each site keeps its existing `SudoCommandField` as `children` and drives `confirmDisabled`, so the look is unchanged and only the surrounding primitive moved.

- `services/components/delete-service-card.tsx`
- `env-groups/components/env-group-actions.tsx` — **the delete dialog**
- `databases/components/database-confirm-dialogs.tsx`
- `keyvalue/components/key-value-confirm-dialogs.tsx` — the delete, joining the suspend that was already correct

**A citation in this note's own Blast radius was wrong.** It listed `env-group-actions.tsx:176,201` as the plain-`Dialog` sites to change. Those are the **rename** and **move** dialogs — ordinary forms, correctly plain `Dialog`s — and there is a **clone** dialog too. The destructive typed-phrase confirm is a fourth dialog in that file. Converting the cited lines would have changed three forms that were never the defect and missed the one that was.

**Implementing it surfaced a defect in the shared primitive, now fixed.** Radix closes on `AlertDialogAction`, so routing the service delete through `ConfirmDialog` silently broke the protected-environment retry: a protected env answers `confirmation_required` with a server-issued phrase the user must type **in that same dialog**, and the dialog was closing before they could. `ConfirmDialog` gains `closeOnConfirm` (default `true`, so no existing caller changes); `delete-service-card` passes `false` and owns closing, which is exactly what its plain `Button` did before. Caught only because a pre-existing test asserted the retry flow — without it this ships as a silent regression in the one delete that most needs the guard.

**Test updates were scoped, not blanket.** Fourteen role assertions moved `dialog` -> `alertdialog`, only for the converted confirms. Left untouched: the rename/move/clone dialogs, suspend/restart, the "nothing is open yet" `queryByRole("dialog")` assertions, and every `ProtectedConfirmationDialog` assertion — that component stays a plain `Dialog` by design, since its phrase is an API handshake rather than a local are-you-sure.

Verified: dashboard suite 425 files / 3471 tests green; `tsc --noEmit` and `yarn lint` clean.

**The second axis is not fixed and is now [`057`](057.md).** The phrase convention still disagrees — webhooks require `delete webhook <name>` with no `sudo` while every `SudoCommandField` sibling uses `sudo delete <type> <name>`, and disks build theirs from `diskSudoPhrase(verb, disk)`. As this note argued, that is a different root cause with a different fix, and settling it is a convention decision rather than a mechanical change. Filed separately so closing the role split does not bury it.
