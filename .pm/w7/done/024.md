# Build pods cannot schedule on tenant nodes despite real headroom (autoscaler/capacity, not QoS)

**Source:** production bug report 2026-08-08 §5 (`tianpan-forum` / `blockeden-forum` deploy), triaged the same day.

Deploying from a repo requires a build pod whose `buildkit` init container requests **7Gi + 2 CPU**. On hetzner-prod the tenant nodes were **85–97% committed on requests** while only **11–52% actually used** (Guaranteed-QoS workloads, request == limit), so the build pod — and even a trivial 100m/128Mi pod — stayed `Pending` with "Insufficient cpu/memory". Earlier this looked like builds "wedging": status `Building`, zero logs. Worked around by importing an already-built image per tenant (`runtime: image`), skipping the build entirely.

**The reporter suggested Burstable QoS (request < limit) for build/app pods. Reject that framing** — the sizing is deliberate. `lego/operator/internal/build/build.go:75-86`:

> Build execution resources match Render's Starter pipeline tier (2 CPU, 8 GB RAM) while remaining schedulable on the baseline 8 GB tenant nodes. The 7 GiB memory request leaves allocatable headroom for kubelet and DaemonSets but still **makes a builder effectively node-exclusive, so Cluster Autoscaler adds a node instead of co-locating** a memory-hungry build with serving workloads.

So the request size is the mechanism, not the bug. Under-requesting would reintroduce exactly the noisy-neighbor eviction risk the constants were chosen to avoid, and would fight `docs/ADR034-scalable-build-pipeline.md`'s Pod-versus-machine capacity model.

**The actual question is why Cluster Autoscaler did not add a node.** Candidates, in order:

- autoscaler max-node / node-group bounds reached (`deploy/gitops` autoscaler config, `infra/` node pools);
- the node group cannot provision a machine type that fits a 7Gi+2CPU pod, so the pod is unschedulable-but-not-scale-up-triggering;
- autoscaler not actually reconciling the tenant pool, or scale-up blocked by a pending-pod predicate;
- baseline node size drifted below what the constants assume ("the baseline 8 GB tenant nodes").

Check the autoscaler's own events/logs for the pending build pod first — it records why it declined to scale up, which picks the branch without guessing.

**Sizing:** kept as an inbox note rather than a milestone because the fix may well be a bounded config change (a node-group max, a machine type) — sub-hour. Promote to a milestone if the investigation shows the capacity model itself needs revisiting (e.g. a dedicated build node pool, which `docs/ADR034` would own).

Related: `w7/m77` (the datastore-link root cause from the same incident), `w7/m78` (missing Ingress), `w7/m79` (no user-visible signal — note that this one also presented as silence: `Building` with zero logs).

**Repo-side findings (2026-08-09, w7 board review — live check still needed):** every branch checkable without cluster access was checked; the candidates narrow to two.

1. **`bex-tenant-0` is pinned min=1/max=1** (`infra/clusterapi/overlays/hetzner-caph/cluster.yaml:190`) — the baseline tenant pool can *never* scale up. All build scale-out capacity is `bex-tenant-burst` (min 0 / max 2, scale-from-zero).
2. **Ruled out:** the Cilium startup-taint scale-from-zero blocker — fixed 2026-07-27 (`7260c8a8`, with a `clusterapi-validate.sh` guard), before the 2026-08-08 incident.
3. **Prime suspect — the burst pool's scale-from-zero simulation is razor-thin:** capacity hint `memory: "8G"` (decimal, = 7629Mi) minus the build pod's 7Gi (7168Mi) leaves **461Mi** for every DaemonSet CA simulates onto the template node (log-shipper alone requests 128Mi, plus Cilium, node-exporter, egress-meter). If their sum exceeds 461Mi, CA correctly concludes "won't fit on a new node" and declines *silently* — the observed symptom — and a real fresh cx33's allocatable would likely reject the pod too (`build.go`'s "fits the baseline 8 GB node" claim needs re-verifying against live allocatable).
4. **Remaining alternative:** the burst pool was simply at max 2 during the incident (nodes "85–97% committed" was plural, so ≥2 tenant nodes existed).

**The live check picks between 3 and 4** (needs a hetzner-prod kubeconfig, unavailable this session): autoscaler logs/events for a pending build pod, `kubectl get machinedeployment bex-tenant-burst`, and `kubectl describe node <tenant-node>` → Allocatable. If branch 3, the fix is capacity-model territory (shrink the build request a notch vs. raise the hint to true capacity — ADR034 owns that trade-off) ⇒ promote to a milestone per this note's own sizing rule.

## RETIRED 2026-08-17 — branch 3 refuted by measurement, residue carried by `w7/m83`

The live check this note asked for was finally run (hetzner-prod admin kubeconfig, 2026-08-17). **The note's prime suspect — branch 3, "the burst pool's scale-from-zero simulation is razor-thin" — is refuted.**

Measured:

| quantity | value |
| --- | --- |
| cx33 allocatable memory | **7,834,836Ki (7.47 GiB)** |
| build pod effective request | `max(initContainers)` = **7Gi = 7,340,032Ki** |
| free after the build pod | **483 MiB** |
| DaemonSet requests on a tainted build node | **log-shipper only: 128Mi + 50Mi = 178Mi** |
| cilium · cilium-envoy · hcloud-csi-node · kube-proxy | **0Mi each** |
| **spare** | **305 MiB — it fits** |

This note (and a first draft of `builder-issues.md`) assumed cilium and its siblings carried meaningful memory requests. They request **zero**. The CA hint (`8G` = 7,812,500Ki) is also slightly *below* real allocatable, so the scale-from-zero simulation is conservative rather than optimistic and reaches the same "fits" verdict with ~283 MiB spare.

Branch 4 (the pool was simply at max during the incident) or an unrelated cause is what remains. Also measured: `bex-tenant-burst` sits at `replicas 0` with a single active build on lg (47% of allocatable) — **the warm tier has never been exhausted, so there is no evidence of a build capacity shortage at all.** No pool rotation or machine-type change is justified; that recommendation was made and withdrawn (`builder-issues.md` §4).

**Surviving residue → `w7/m83/t004`:** 305 MiB is thin enough to be fragile. If log-shipper's request grows, another DaemonSet gains the build toleration, or the build request rises, a cx33 stops fitting and cluster-autoscaler declines to scale up **without emitting an error**. The arithmetic guard is that failure mode's tripwire.

Note 3's separate observation — `bex-tenant-0` pinned min=1/max=1 — is also stale: D8 raised its max to 2, and it now sits at 2/2. That is tracked as `w7/031.md`.

Full record: [`builder-issues.md`](../builder-issues.md) §3.5, §4.

**Shipped 2026-08-18 (`w7/m83/t004`).** The arithmetic guard is live in `scripts/clusterapi-validate.sh`: the floor is computed from `build.go`'s own memory request plus every repository-declared DaemonSet that tolerates the build taint, and any build pool whose CA hint drops below it — or rises above measured allocatable — turns CI red, with `scripts/clusterapi-validate.test.sh` proving both directions. The measured allocatable figures above are recorded in [docs/ADR060](../../../docs/ADR060-build-worker-reliability-and-performance.md) § Measured node arithmetic so the next reader does not have to re-measure a live cluster.
