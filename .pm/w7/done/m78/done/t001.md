## Objective

Pick the real branch from evidence before writing a fix. The reconcile has several `r.fail()` returns between the Deployment apply and the Ingress apply; each produces the same outward symptom, and guessing would likely fix the wrong one.

## Context

Reconcile order in `lego/operator/internal/controller/app_controller.go` for a web service:

- ~1015 — per-App registry pull credential: requeues with "Waiting for the registry to accept this app's pull credential"
- ~1030 — `reconcileSlugService` → `r.fail(..., "ServiceFailed")`
- ~1082 — pre-deploy gate: `reconcilePreDeploy` can halt the reconcile before the Deployment
- **1088 — Deployment applied** (this is why pods exist)
- 1105 — `reconcileNetworkPolicy` → `r.fail(..., "NetworkPolicyFailed")` — deletes any pre-ADR043 per-App NetworkPolicy; a permissions or API error here returns before routing
- 1116 — `applyClusterIPService` → `r.fail(..., "ServiceFailed")`
- 1155 — `reconcileIngress` → `r.fail(..., "IngressFailed")`

Observed production state: pods running, no ClusterIP Service, no Ingress, `serviceDetails.url: null`, deploy shows "Update Failed", `bex-controller-manager` healthy throughout, and forcing re-reconcile by annotating the CRs produced no routing work. That combination points at a `fail()` between 1088 and 1116 — line 1105 is the leading candidate — but the App's status condition and the operator log line will say which.

Note the operator's RBAC does grant `networkpolicies` delete (`lego/operator/config/rbac/role.yaml:136-146`), so if 1105 is the culprit the question is whether the binding actually reaches the tenant namespace, not whether the verb exists.

### Outcome (2026-08-09) — the premise was wrong; nothing failed

**No cluster access this session** (local kind is down, no prod context, `.env` is permission-gated), so I took step 3's sanctioned path — reproduce rather than infer — which is the better evidence anyway: the affected Apps had already been mutated by the manual workaround.

`internal/controller/tenant_namespace_routing_envtest_test.go` reconciles the exact production shape — a store-projected web service (`CRName(tenant, slug)`, tenant namespace, `Expose: true`, `Subdomain: slug`, no custom domain) — under both configurations:

| Base domain | Result |
| --- | --- |
| `onbex.co` | ClusterIP Service + slug alias + Ingress at `forum.onbex.co` |
| **unset (production)** | Service created, **no Ingress, no URL, phase NOT Failed, reconcile returns no error** |
| unset + a custom domain | Ingress created at the custom host |

**The cause.** `AppSpec.EffectiveHosts` contributes the platform host only when `baseDomain != ""`. With it unset, a service that brought no custom domain of its own has **zero** effective hosts, so `reconcileIngress` takes its `len(hosts) == 0` branch — which deletes any stale Ingress and returns `nil`. Nothing fails, so no status reason ever names a cause. `status.URL` is then never written, because it is only set on the Running path.

**Production runs it unset by deliberate decision**, stated in three places: `config/manager/manager.yaml:151` ("intentionally unset: onbex.co is a registrable domain, so tenant JavaScript could set parent cookies received by a sibling tenant"), `config/api/deployment.yaml:68`, and — decisively — `config/staticserver/deployment.yaml:53`, which sets an **explicit `""` as an SSA tombstone** to strip "the unsafe onbex.co value" from Deployments that previously carried it. So platform hosts were live once and were deliberately turned off.

**Every reported observation now fits, and two of them dissolve:**

- _"no Ingress for the new tenants"_ — correct behavior, not a failure.
- _"`serviceDetails.url: null`"_ — the operator writes `status.URL` only when Running, and bex-api's `pendingPublicURL` fallback (w5/m48, "Render shows a service's URL from the moment it's created") depends on **bex-api's own** `BEX_BASE_DOMAIN`, which is likewise unset. Both sources are empty, so the field is null regardless of health.
- _"the reference tenant `beancount-forum` works"_ — it carries an explicit host, which routes with or without a platform subdomain. The third spec pins exactly this. It is also why the reporter could model a hand-made Ingress "on beancount's".
- _"annotating the CRs forced no re-reconcile"_ — the App controller uses `generationOrDeletionPredicate`, and an annotation does not bump `metadata.generation`. The update was filtered; nothing was stuck.
- _"Deploy 'Update Failed'"_ — the health-check failure from the crashlooping pods (w7/m77's root cause), not a routing error.

**Not confirmed against the live cluster:** whether the manager Deployment's env actually carries the value today. Git's desired state is unset, and the fleet-wide behavior above is consistent with every observation, but one `kubectl -n bex-system get deploy bex-controller-manager -o jsonpath='{..env}'` would settle it. Worth doing when cluster access returns.

### The real defect this exposed

The behavior is correct; the **silence** is not. Two related states, neither of which surfaces anywhere:

1. A web service created today gets **no public URL at all** unless the user attaches a custom domain, and nothing says so — not at create, not on the service page, not in the deploy. On a Render-compatible platform that is a startling default to discover by inspection.
2. When `BEX_BASE_DOMAIN` was removed, `reconcileIngress`'s zero-host branch **deleted the public route of every service that had only a platform host** — silently, fleet-wide. Deleting is the right security behavior (that was m54's whole point); doing it without a trace is not.

Both reduce to the same missing signal: _expose is set, yet no public host is derivable._ That is precisely `w7/m79/t003`, so m78 folds there rather than building the same condition twice.
