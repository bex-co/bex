## Objective

Check the fix is consistent across REST, GraphQL, MCP, and the dashboard, and against render.com's behavior for a service that deployed but is not routable.

## Context

- The defect's visible symptom was `serviceDetails.url: null` on a service whose pods were running — a Render-compatible field (`docs/ADR006-bex-api.md`).
- `docs/ADR041-service-addresses.md` owns the internal/public address contract; `lego/backend/internal/apps/domains.go` derives the reported URL.
- Render's own behavior for a deployed-but-unroutable service is the comparison point: does it report a null URL silently, or surface the deploy as failed?

## Steps

1. Confirm the URL/routing fields agree across REST, GraphQL, and MCP for the same service.
2. Confirm the dashboard reflects the corrected state.
3. Compare with render.com's behavior and flag drift as follow-up rather than diverging silently.
4. Update `docs/ADR018-render-parity.md` where evidence changed.

### Disposition (2026-08-09)

**MOVED to `w7/m79` 2026-08-09.** The `serviceDetails.url` question is real but its cause is not a routing abort: the operator writes `status.URL` only on the Running path, and bex-api's `pendingPublicURL` fallback depends on bex-api's own `BEX_BASE_DOMAIN`, which production leaves unset. Both are the same missing-signal problem m79 owns, and its parity task covers the surfaces.
