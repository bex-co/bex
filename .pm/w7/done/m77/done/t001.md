## Objective

Decide and record exactly which namespace a `Database`/`KeyValue` CR and its Secrets live in, what happens to the already-provisioned `default`-namespace datastores on hetzner-prod, and which dependent subsystems must move with them — before any code changes. The migration touches subsystems that already shipped (logs, metrics, authz, backups, SNI proxies, purge), so the contract has to be settled once rather than discovered per-caller.

## Context

- `docs/ADR043-tenant-namespace-isolation.md:38` already states the intended contract: "Hosting workloads (App / Database / KeyValue) land in `<ws>`". Only the App half was implemented (`aca23a05`, `db7d95fc`).
- `lego/backend/internal/core/base.go:264-274` records the divergence in a doc comment: `AppNamespace` returns the per-tenant namespace, and "Only Apps live in the per-tenant namespace; Databases/KeyValues/Secrets stay in `b.Namespace`."
- Creation sites to move: `lego/backend/internal/postgres/service.go:493`, `lego/backend/internal/keyvalue/service.go:402`.
- Already namespace-agnostic (verify, do not change): `lego/operator/cmd/pg-sni-proxy/main.go:120` routes from `db.Namespace` off the `Database` CR, so the public SNI front door follows the CR wherever it lives.
- Hard dependency: the Barman Cloud `ObjectStore` is **namespaced** and GitOps-installed as a single object (`deploy/gitops/charts/barman-cloud-objectstores/tenant-postgres.yaml`; referenced by name at `lego/operator/internal/controller/database_controller.go:77,217`). GitOps cannot enumerate dynamically created tenant namespaces, so per-tenant backups need an owner — decide operator-created vs. a namespace-scoped default.
- Legacy set: hetzner-prod has live datastores in `default` serving real tenants (`beancount-forum` and siblings). A flag-day rename is not available — CRs are not movable in place.

## Steps

1. Enumerate every reader/writer keyed on `core.Base.Namespace` for datastore CRs and Secrets (bex-api services, logs, metrics, recovery, exports, purgers, authz object ids, workspace purge) and classify each as must-move / already-namespace-agnostic / legacy-tolerant.
2. Choose the legacy strategy: dual-read (resolve tenant namespace first, fall back to `b.Namespace`) versus a one-shot migration with no fallback. Record the reasoning, including how long any fallback lives and what removes it.
3. Choose the ObjectStore owner for per-tenant backups and confirm the S3 destination-prefix contract still holds per namespace.
4. Write the ordered cutover plan for hetzner-prod, including how a live Discourse tenant's connection is re-pointed without data loss and what the rollback is at each step.
5. Amend `docs/ADR043-tenant-namespace-isolation.md` with the decision, and add a short lineage note that the App-only implementation was the defect.
