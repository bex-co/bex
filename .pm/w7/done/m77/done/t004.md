## Objective

Keep managed-Postgres backups/PITR and paid-plan Key Value RDB backups working once datastores live in per-tenant namespaces. The Barman Cloud `ObjectStore` is a namespaced object referenced by name, and it is installed by GitOps as a single instance — which cannot cover namespaces that are created dynamically at workspace-create time.

## Context

- `lego/operator/internal/controller/database_controller.go:74-77` — `tenantBackupObjectStoreName = "bex-tenant-postgres"`, with the comment "ObjectStore is installed by GitOps before the operator starts projecting"; line 217 references it by name (`barmanObjectName`), and line 325 notes the destination/retention/transport live on the namespaced ObjectStore.
- `deploy/gitops/charts/barman-cloud-objectstores/tenant-postgres.yaml` — the single GitOps-installed instance.
- `BEX_DB_BACKUP_DESTINATION` / `_ENDPOINT` / `_S3_SECRET` (CLAUDE.md) are the non-secret contract that "must match the namespaced `bex-tenant-postgres` ObjectStore"; any variable unset ⇒ backups disabled for every plan.
- Key Value: `BEX_KV_BACKUP_*` drives per-instance nightly RDB CronJobs plus a delete-time prefix purge and a finalizer — these run in the datastore's namespace and need the apps-namespace S3 Secret reachable there.
- The S3 credential Secrets are likewise namespaced; a tenant namespace has no copy today.

## Steps

1. Implement the ObjectStore ownership decision from t001 so every tenant namespace hosting a Database has a valid ObjectStore before the first backup is scheduled.
2. Make the S3 credential Secret the ObjectStore and the KV backup CronJobs reference available in the tenant namespace, without widening what a tenant workload can read (the tenant's own pods must not gain the platform backup credential).
3. Verify the KeyValue backup CronJob, retention, delete-time purge, and finalizer all still resolve in the new namespace.
4. Confirm the fail-closed behavior is preserved: any backup variable unset ⇒ backups disabled, no half-configured ObjectStore left behind.

### Outcome (2026-08-08)

`DatabaseReconciler.reconcileTenantBackupStore` projects both halves of the transport into the Database's own namespace before the Cluster is written: the S3 credential Secret, and the Barman `ObjectStore` the Cluster references by name. `KeyValueReconciler.reconcileTenantBackupCredential` does the credential half for the RDB CronJob (that path talks to S3 directly, with no ObjectStore). Both are wired from the new `BackupSourceNamespace` (= `BEX_APPS_NAMESPACE`) and are **no-ops** when the datastore is already in the source namespace or the field is empty, so the pre-D8 topology and single-namespace deployments stay byte-identical.

Two decisions worth keeping:

- **The ObjectStore spec is copied from the GitOps original, not rebuilt from env.** Destination, retention, compression, and SSE therefore stay single-sourced in Git. Rebuilding them in Go would create a second place for backup policy to drift, and that drift would only be discovered at restore time.
- **The projected ObjectStore carries no ownerReference.** It is shared by every Database in the namespace, so binding it to one would delete it the moment that one went away and silently break every sibling's archiving. Pinned by test.

Failure is loud: a missing source ObjectStore or credential fails the Database with `BackupStoreUnavailable` rather than letting the Cluster come up with a dangling `barmanObjectName`, which CNPG reports as "backups not configured" rather than as an error — a Postgres that looks healthy and archives nothing.

The credential in a tenant namespace is not tenant-readable: tenant workloads have no Kubernetes API access and run with `automountServiceAccountToken: false` (w7/m2).
