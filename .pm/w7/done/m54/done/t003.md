## Objective

Make the safety invariant behind Traefik's global ExternalName support enforceable: only trusted platform controllers may create or retarget the aliases used for static-site and maintenance routing.

## Context

- `allowExternalNameServices: true` is cluster-wide, while safe behavior currently depends on tenants having no Kubernetes Service/Ingress write access.
- Operator aliases are deterministic, App-owned, and target fixed Services in `bex-system`.
- If a tenant identity could mutate an alias or Ingress, Traefik could become an internal routing primitive.

## Steps

1. Enumerate every tenant-facing identity and prove its effective Service/Ingress permissions with impersonation checks.
2. Add the narrow RBAC/admission and structural CI guards needed to reject tenant-created Ingresses and tenant-retargeted ExternalName Services while admitting operator reconciliation.
3. Add negative tests for internal targets such as bex-api, registry, OpenBao, tenant databases, and arbitrary external DNS names.
4. Verify static-site and maintenance-mode routing still work through operator-owned aliases.

## Acceptance criteria

- [x] Tenant-facing identities receive `no` from `kubectl auth can-i` for Service and Ingress create/update/patch/delete.
- [x] Admission rejects retargeting an operator alias to an unapproved internal or external destination.
- [x] The operator can create/update/delete both static-server and maintenance aliases.
- [x] CI fails if tenant RBAC gains alias/Ingress mutation or if the admission guard is removed.
- [x] Production probes show public static and maintenance routes work while tenant-to-platform ingress remains blocked.

## Out of scope
