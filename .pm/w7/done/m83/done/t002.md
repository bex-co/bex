## Objective

Turn t001's series into a page, so the next queueing incident announces itself instead of being discovered by hand-descending through Traefik → bex-api → controller logs.

## Context

- Two prior incidents were diagnosed manually because nothing alerted: 2026-08-08 (build wedged in `Building`, zero logs) and 2026-08-11 (22 minutes `Pending`, deploy failed by the control-plane gate while the build was healthy).
- bex-api's `DeployGateTimeout` is 18m (`m80` settled the three-timer relationship), so an alert must fire meaningfully **before** the gate fails the deploy — otherwise it reports history.
- Existing Prometheus rules live in the gitops path alongside the other platform alerts.

## Steps

1. Add an alert on `bex_build_queue_seconds` p95 breaching a threshold, and one on any single build `Pending` beyond N minutes.
2. Choose N to fire before the 18m deploy gate, and justify the number in a comment against `m80`'s timer table.
3. Verify the rules load and evaluate (rule-unit test or the existing alerts-verification path).

## Files

- `deploy/gitops/base/` Prometheus rules
- `scripts/alerts-verify.sh` if it is the existing verification path

## Acceptance criteria

- [ ] A build queued beyond the threshold fires an alert before the deploy gate would fail it.
