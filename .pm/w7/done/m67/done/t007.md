## Objective

Prevent the gap from reopening: CI fails if any CNPG Cluster manifest under `deploy/gitops/` lacks a Barman Cloud plugin block, so the *next* platform Postgres added without backups is caught at PR time.

## Context

- Precedent: the repo's fail-closed gitops CI guards (w7/m8's registry guard in `gitops-validate.sh`, w7/m58's universal securityContext guard). Follow that shape: structural scan over rendered/raw manifests, explicit allowlist for genuine exceptions (none expected today — bex-db, tenant template, and the three auth DBs all carry plugins after t002), and a red/green self-test so the guard can't silently rot.
- Guard should also assert serverName uniqueness within each ObjectStore destination (the Barman correctness invariant).

## Steps

1. Extend the gitops validation script with the CNPG-plugin guard + self-test.
2. Verify red (temporarily strip a plugin block locally) and green.

## Files

- `scripts/gitops-validate.sh` (or the repo's current gitops CI guard location)
- `.github/workflows/` (only if the guard isn't already wired into CI)

## Acceptance criteria

- [x] Guard fails on a Cluster without a plugin block; passes on current tree.
- [x] serverName-uniqueness assertion covered.
- [x] Self-test proves the guard actually scans (anti-tautology).

## Out of scope

- Guarding tenant Databases created at runtime (operator-owned, covered by ADR009's plan gating, not gitops).
