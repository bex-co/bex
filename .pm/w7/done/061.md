## Result — 2026-09-28 (worker7): recovery verified, no residual

Read-only, production `secrets/openbao-{0,1,2}`, 72h of logs (2026-09-26T03:45Z → 07:40Z on 28th). Lease ids were compared only as SHA-256 prefixes; no token, lease id or secret value was printed or stored.

- **No failover in the window.** `bao status` on all three members names `openbao-0` as leader, `active_time` 2026-09-22T18:40:16Z; no leadership log lines in the window.
- **Every failure is a standby write.** 71 `failed to revoke lease … cannot write to readonly storage` (with the paired `failed to mark token as revoked`) occurred only on the standbys `openbao-1` / `openbao-2`. The active `openbao-0` logged **0** errors and 61 `revoked lease` lines.
- **Every failed lease was revoked.** All 71 failed lease ids hash-match a `revoked lease` line on the active node, 0.15–0.6s later (e.g. standby fail 06:15:38.553Z → active revoked 06:15:38.750Z). The scheduled `next_attempt` retry on the standby is moot; the lease is already gone.
- The `error rotating OIDC keys … readonly storage` warnings are the same class: standby-only (3 each on openbao-1/2, 0 on the active).

Conclusion: normal HA behaviour (standbys observe the expiry and attempt a write they cannot perform; the active performs it), not incomplete cleanup. No repair needed; no collection was expanded and no component upgraded. The residual is log noise only (~1 error line per standby per hour).
