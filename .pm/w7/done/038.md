# 038 — Two findings on the forum service: credentials baked into its image, and `autoDeploy` that never fires

Why: verify retirement of historical credential-bearing forum images; the current image template and auto-deploy reporting are now verified fixed.

**Current disposition (2026-09-06): closed.** Current images and auto-deploy reporting are fixed; the two historical passwords are invalid; after verified backups, the exact legacy gen-54 manifest, credential layer and five inactive ReplicaSets were retired. See the final outcome and drill record below.

The following two findings describe the original 2026-08-20/21 incident while finishing `w7/m77`; their image, credential-validity and service-configuration statements are historical.

## Original finding 1 — credentials baked into a registry image

`config/multisite.yml` **is** in the `beancount-forum` image (verified from a throwaway container running the same digest, so nothing could have been copied in), and it carries **real credentials** — 0 placeholder tokens, 2 live database passwords, plus both database FQDNs:

```
placeholders: 0
real-looking password lines: 2
  host: dpg-d9rrkoc4h4mc73edurp0-rw.default.svc.cluster.local
  host: dpg-d9rs3ee0ccis738kc7c0-rw.default.svc.cluster.local
```

The repo's own template says `# NOTE: passwords below are placeholders … Do NOT commit real credentials.` The intent was right; the image does not honour it.

Anyone able to pull that image — any holder of the per-App registry credential, anyone with registry access, and anything that mirrors or caches layers — obtains two tenant Postgres passwords. Rotating those passwords does not invalidate the copy in older image layers.

How they got there is unresolved: no version of `_infra/docker/Dockerfile` in the fork's history copies the file (checked every revision), yet the layer contains it with an mtime matching build time. Establish that before assuming a fix is complete — the same path may be baking other files in.

**`b6cbd62` on `bex-co/discourse_docker` is the fix** and should be kept: it ships a placeholder-only template and resolves it at boot from platform-injected env, so the image carries no credential. It is pushed but **not yet built** (see finding 2), so today's image is still the credential-bearing one.

## Original finding 2 — `autoDeploy: true` without a repository

| App | namespace | `spec.repo` | autoDeploy |
| --- | --- | --- | --- |
| `tea-d98210cbbpdc73dcrkvg-beancount-forum` (**live**) | tenant | **`<UNSET>`** | true |
| `beancount-forum` (legacy, phase Failed) | `default` | `…/discourse_docker.git` | true |
| every other tenant App | tenant | set | — |

The git webhook matches a push against `App.spec.repo`. With that field empty the live service can never match, so a push to its repository redeploys nothing. Confirmed: a correctly signed push webhook for the right repo and branch returned `200 {"redeployed":[]}`.

The service is therefore **not** on push-to-deploy despite reporting that it is.

**It is not a projection defect** — checked before assuming, because the obvious repair (write `repo` onto the CR) would have been wrong. `applyOwnedSpec` sets `Repo` on **every resync**, not only at create:

```go
set(&dst.Repo, want.Repo)   // reconciler.go, applyOwnedSpec
```

So a non-empty control-plane row would have back-filled the CR on the next resync. The CR is still empty after many, which means **the row itself carries no repo**. The projector is faithfully reflecting the desired state it was given.

That fits the rest of the evidence: `_infra/bex/bex-forums-multisite.yaml` describes this service as `runtime: image` against a pinned `gen-53`, i.e. deploying a prebuilt image rather than building from the repo. Clearing the repo binding is what that switch does.

So the repo binding is **service configuration, not corruption**, and restoring it is a product decision (go back to building from the repo) that has to go through the API — not something to patch onto the CR.

What remains a real defect is narrower and general: **`autoDeploy: true` alongside an empty `repo` is silently inert.** The field claims a behaviour the resource cannot perform, no surface reports the contradiction, and the only symptom is pushes that quietly do nothing. Either refuse the combination or surface it.

## Related, already handled

A deploy can still be triggered without the API: the App carries a `bex.co/deploy-hook-token` annotation, and `POST /v1/deploy-hooks?key=…` returns a deploy id and rolls the pod. That redeploys the **current image** — it does not rebuild — which is why it did not pick up `b6cbd62`.

## Verified — 2026-09-05: exact historical artifact and credential validity

The separate legacy repository `tea-d98210cbbpdc73dcrkvg-beancount-forum` still retains gen-51, gen-52, gen-53, gen-64, and gen-54. Its image configs contain no password/secret/token/database-URL environment keys. The completed layer scan found one `multisite.yml` with two non-placeholder password fields, in **gen-54**, not the currently retained gen-53.

Exact affected artifacts:

- Repository: `tea-d98210cbbpdc73dcrkvg-beancount-forum` (legacy, no workspace path prefix).
- Tag: `gen-54`.
- Manifest: `sha256:f9f1e8de18d77743c78d73bafbe05faa73e64647f5f40681f92c362f2248c029`.

No registry artifacts, ACLs, database credentials, or workload controllers were modified by this inspection. Temporary inspector pods were deleted.

## Outcome — 2026-09-06: backed up, verified and retired

The user's migration/closeout request authorized the remaining cleanup. Live inspection showed migration to clean gen-112 was already complete; no traffic or database cutover was needed. Three logical database backups were restored in a network-isolated local PostgreSQL container: all 882 public-table counts matched their export snapshots and all tables belonged to the application role. The forum pull credential now receives HTTP 404 for the old tag, digest and layer; a read-only volume scan found no file with that layer digest anywhere in the registry volume. Other legacy/current tags were unchanged. Current Deployment remains 1/1 Ready and all three site APIs return 200.

The old image had no uploads either. This closes the credential-artifact and auto-deploy findings, not the newly discovered upload recovery work.
