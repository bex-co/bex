# A blocked org downgrade names members by their sign-in id, and on Hobby tells the Owner to make a Developer a Developer

Why: when Render's downgrade preconditions do not hold, the Owner is told which members to change, but bex lists each one as a Kratos subject (`6cfb0006-…:viewer`), not their email. On a Hobby target it also tells the Owner to change a Developer "to Developer or Admin", which does not unblock the downgrade.

- **Found by:** w7/m464 t013, on production, 2026-11-17 (pin `14eaa71b98e5`), org `org-dbugoqde7qgs73b346ag` (fixture, since deleted).
- **Probe, primary on Scale, target Hobby:** first a Viewer member, a Contributor invite, two secondaries and a workspace IP rule. GraphQL `changeWorkspacePlan(id, plan: "hobby")` answered `ORGANIZATION_DOWNGRADE_BLOCKED` with `preconditions[1] = {kind: "member_roles", items: ["6cfb0006-9fe9-434d-a481-ad10799247d0:viewer"]}`. The Settings → Change plan dialog read "Change these members' roles to Developer or Admin: 6cfb0006-9fe9-434d-a481-ad10799247d0 (Viewer)". The invite line names its email ("qa-…-pending@example.com (Contributor)").
- **Probe, the same member as Developer:** after `changeWorkspaceMemberRole(role: "developer")`, the retry answered `member_roles` with `["6cfb0006-…:developer"]`, and the dialog read "Change these members' roles to Developer or Admin: 6cfb0006-… (Developer)". Removing the member let the downgrade through.
- **Cause:**
  - `lego/backend/internal/workspaces/service.go:1542-1550` `rolesOutsidePlan` writes `m.Subject+":"+m.Role`. `internal/workspaces/organizations.go:534` uses it for the org preconditions.
  - `store.LimitsFor(hobby)` (`internal/store/plans.go:77`) allows only `admin` and one member. So on a Hobby target every non-admin member lands in `member_roles`, under copy written for Render's Billing/Viewer/Contributor rule (`dashboard/src/features/workspaces/locales/en.ts` `workspaces.orgDowngradeMemberRoles`; `change-plan-dialog.tsx:51-60` `personWithRole`).
  - The standalone downgrade checks the member count first ("exceeds hobby plan's limit of 1", `service.go:1480`). The org path never does.
- **Adjacent, same class:** GraphQL `changeOrganizationMemberRole` returns `email: ""` for the member it changed, while `organizationMembers` lists that email (`internal/members/organizations.go:522` builds the view without `Email`/`UserID`). The dashboard does not read it, but an API client does.
- **Fix:**
  - `member_roles` names each person by their email (`Identities.LookupEmails`, subject only when none resolves) and keeps Render's meaning: Billing, Viewer and Contributor members.
  - A Hobby target also names, under its own kind, every member beyond the one admin it seats, with copy that says to remove them.
  - `changeOrganizationMemberRole` (and MCP's equivalent) returns the member's email and user id, as the list does.
- **Done when:** on a primary with a Viewer and a Developer besides the Owner, a Hobby downgrade is refused naming the Viewer by email under "change their role" and both non-admins by email under "remove them (Hobby has one member)"; a Pro downgrade names only the Viewer. A role change's response carries the email. Backend and dialog tests cover each.
- **Render:** the downgrade lists "team members … with the Billing, Viewer, or Contributor role" (render.com/docs/organizations); Render's Hobby is a single-member plan. ~1h.
- **Done 2026-11-18:** `member_roles` and `invite_roles` keep Render's meaning (Billing, Viewer and Contributor, judged against Pro on either target), and name each member by email through `Identities.LookupEmails` (`workspaces.Service.memberRoles`, the subject only when none resolves). A Hobby target adds `member_limit`: every member past the one seat, which the Owner making the change keeps, and every pending invite. The dialog words it "Remove these members and pending invites (Hobby has one member)", and its warning gains a Hobby line. `changeOrganizationMemberRole` and MCP `change_organization_member_role` return the member's email and user id. Proved by `TestOrganizationDowngradeNamesPeopleE2E` (real Postgres and OpenFGA: Viewer, Developer and a Developer invite beside the Owner; Pro names only the Viewer, Hobby names the Viewer under both kinds and everyone else under `member_limit`, and the downgrade goes through once they are gone), the role-change read-back in `TestOrganizationsE2E`, `TestUnseatedKeepsTheCallerThenAdmins`, `TestMemberRolesNamesByEmailElseSubject` and the change-plan dialog tests; each fails with the fix reverted.
