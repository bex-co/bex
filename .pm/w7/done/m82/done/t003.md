## Objective

Turn t001/t002's classification into something a tenant and an operator can both read: split today's flat `BuildFailed` into `succeeded | user_failed | infra_failed | canceled | timeout` and carry that class to all three sinks ADR060 D2 names.

## Context

- The App CR condition reason is flat `BuildFailed` today, so "your git ref is wrong" and "a node went away" are the same string.
- `w2/m72` already ships `bex_build_outcomes_total{outcome}` (splitting `superseded`/`canceled`/`failed`/`timeout`/`succeeded`) and `bex_build_run_seconds` in `lego/operator/internal/controller/build_metrics.go` — **extend** that vocabulary, do not introduce a second one. `failed` must split into `user_failed` / `infra_failed` without breaking existing series consumers.
- `m79` shipped the `failure_reason` path from the operator through the deploy record to REST/GraphQL/MCP, the dashboard, and the failure email — reuse it; do not build a parallel channel.
- ADR060 D5: the infra/user split "is what makes a build SLO definable at all".

## Steps

1. Extend the outcome vocabulary in the operator's build observation to carry the classified result.
2. Split the App condition reason so `BuildFailed` distinguishes the tenant class from the infra class, with a message saying which and why.
3. Thread the class into the bex-api deploy record over the existing `m79` `failure_reason` seam.
4. Extend `bex_build_outcomes_total{outcome}` with the new classes; add `bex_build_retries_total{reason}` (`disruption`, `transient`).
5. Check whether the closed event vocabulary needs a new value or reuses an existing one — `m79` deliberately kept it closed and needed no migration; do the same if possible, and say so explicitly if not.

## Files

- `lego/operator/internal/build/`, `lego/operator/internal/controller/build_metrics.go`
- `lego/operator/internal/controller/app_controller.go`
- `lego/backend/internal/deploys/`

## Acceptance criteria

- [ ] A tenant-caused build failure and an infra-caused one produce different condition reasons and different deploy `failure_reason` values.
- [ ] `bex_build_outcomes_total` distinguishes `user_failed` from `infra_failed`; existing series consumers still work.
- [ ] `bex_build_retries_total{reason}` counts automatic retries by cause.
- [ ] No second, parallel failure-reporting channel was introduced alongside `m79`'s.
