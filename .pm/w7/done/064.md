# bex-api without the control-plane store crashes at start once Hydra holds an API key

Why: a store-off bex-api (`BEX_CP_DB_URI` unset, the DB-free mode `lego/backend/AGENTS.md` documents) that restarts after anyone has created an API key panics before it listens, so a self-hosted or local DB-free install stops starting the moment it has a key.

- Found by w7/m426, 2026-11-16, while running a DB-free bex-api against a Hydra v26.2.0 that held API-key clients.
- `lego/backend/cmd/api/main.go` calls `backfillMachineMemberships(ctx, st, deps.APIKeys)` with `st` a nil `*store.PGStore`. Passed as `any`, it is a non-nil interface holding a nil pointer, so the `st.(machineMembershipStore)` assertion succeeds and `(*PGStore).MarkMachineMemberships` dereferences `s.Pool` (`lego/backend/internal/store/members.go`). The function's own comment says "a DB-less run leaves it nil and the reconcile is skipped"; it is not skipped. With zero keys `MarkMachineMemberships` returns before the dereference, which is why an empty Hydra hides it. Since `fa07982b9` (w5/m103, 2026-09-17).
- Repro: start a Hydra, `POST /admin/clients` one client with `"metadata":{"bex.co/api-key":true}`, then start bex-api with `BEX_HYDRA_ADMIN_URL` set and `BEX_CP_DB_URI` unset. It exits with `panic: runtime error: invalid memory address or nil pointer dereference` in `store.(*PGStore).MarkMachineMemberships`.
- Fix: skip the backfill when the store is off (pass a typed interface, or guard the nil pointer at the call), with a test that calls `backfillMachineMemberships` with a nil `*store.PGStore` and a key store holding one key and expects no panic and no call.
- Done when: the repro starts and serves `/healthz`, and the test fails on the old code.

**Done 2026-11-16:** `backfillMachineMemberships` takes `st *store.PGStore`, not `any`, and returns before listing keys when it is nil; the `machineMembershipStore` interface it was asserted through is gone (`lego/backend/cmd/api/main.go`). Tests in `lego/backend/cmd/api/machine_membership_backfill_test.go`: a nil store with one listed key does not panic and never lists keys (on the old code it panics in `(*PGStore).MarkMachineMemberships(0x0, …)`), and with a real Postgres a listed key's legacy binding becomes `machine` while the human stays a member. The repro, run against a throwaway Hydra v26.2.0 holding one `bex.co/api-key` client and a throwaway kind cluster with the bex CRDs: the old binary exits 2 with that panic, the fixed one answers `/healthz` 200 and keeps running.
