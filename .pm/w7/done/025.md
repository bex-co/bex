# App-side metrics still query the shared namespace on two fallback paths

**Source:** found while auditing namespace resolution for `w7/m77/t003` (2026-08-08). Left unfixed deliberately — m77 is scoped to datastores, and this is the App side.

Two App-scoped metrics paths still pass `s.Namespace` where the App CR's own `<ws>` namespace is what holds the data (ADR043):

- `lego/backend/internal/metrics/service.go:455` — `s.ResourceMetrics(ctx, s.Namespace, appName)`, the metrics-server snapshot used when `ResourceMetricsRange` (Prometheus) is unavailable, i.e. when `BEX_PROM_URL` is unset.
- `lego/backend/internal/metrics/service.go:879` — `filterValuesOrEmpty` → `s.MetricsFilterValuesSource(ctx, s.Namespace, app, label)`.

The neighbouring request-metrics path already does this correctly and says why (`readRequestSeries`: "The App CR is in hand — its namespace is the per-tenant `<ws>` namespace under ADR043; use it directly rather than the shared s.Namespace"), so these two look like misses from that pass rather than intent.

**Why it matters and why it is easy to miss:** the failure mode is an empty series, not an error. Same family as the still-open `project_logs_tenant_namespace_bug` (dashboard logs empty because the read queried `default`) and the same class m77/t003 fixed for datastore logs/metrics/usage.

**Before fixing, verify the impact honestly:** production sets `BEX_PROM_URL`, so path 1 may be dead in prod and live only in dev/degraded mode. Check that first — if so this is a low-severity dev-only gap and should be sized accordingly, not promoted.

**Sizing:** likely sub-hour (both call sites hold the App CR already, so it is `app.Namespace` at each). Kept as a note. Promote only if the verification shows a live production impact or if it turns out the App-side has more of these.

Related: `w7/m77` (the datastore half, fixed), `w7/m79` (the "no user-visible signal" milestone — a silently-empty metric series is exactly its subject matter).

---

**Disposition (2026-08-09, w7 board review): implemented.** Impact verified honestly first, then both call sites fixed:

- `resourceMetric` (the metrics-server snapshot fallback) now resolves the namespace via `s.AppNamespaceByName`, the same seam its ranged sibling already used. Verified impact: prod sets `BEX_PROM_URL`, so this path is live only in dev/degraded mode — but there it silently returned empty series for every tenant-namespace App.
- `filterValuesOrEmpty` now threads `app.Namespace` from the App CR its caller (`MetricsFilters`) already holds. Verified impact: zero in prod today — the production `NewPrometheusFilterValuesSource` **ignores its namespace argument entirely** (`source.go`, `func(ctx, _, app, label)`) — but the interface contract now carries the right value for any source that honors it.
- Regression test `TestMetricsSnapshotAndFilterDiscoveryUseAppNamespace` pins both: App in `ws-tenant` with shared namespace `default`, asserting each source receives `ws-tenant`. Backend build + full test suite green.
- The "does the App side have more of these" check: these two were the last `s.Namespace` uses in `internal/metrics`, and `internal/logs` already threads `app.Namespace` everywhere (fixed + deployed 2026-07-31, `cd3b5f72`). One adjacent dev-only edge observed, not fixed: the build-log paths fall back `BuildNamespace → s.Namespace`, while an unset `BEX_BUILD_NAMESPACE` actually puts builds in the App's own namespace — prod sets the var, so noting it here is the record.
