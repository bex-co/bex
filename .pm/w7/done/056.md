# 056 — The `gitops (render)` gate has been red for 5.5 days because its own assertion miscounts under the yq version CI pins — the manifest it guards is correct

Why: `gitops (render)` is the guard that stops broken Kubernetes manifests from reaching Argo CD ("Catches broken manifests/values before Argo CD ever sees them" — `.github/workflows/gitops.yml:3-5`). It has failed **every run since 2026-09-12**, not because anything is wrong with the GitOps tree, but because one assertion returns a two-line string under the pinned `yq`. **22 commits touching the guarded paths have merged since**, none with a passing validation, and anyone who genuinely broke a manifest in that window could not have distinguished their breakage from the standing red.

**Estimate:** 20m · **Severity:** minor (no tenant-facing impact; nothing was blocked — `main` is not branch-protected) · **Attribution:** CI/platform · **Worker:** worker7

## Source

Live `/qa-find-bugs` loop of `https://dashboard.bex.co`, 2026-09-17 (thirty-ninth sweep), filed to w7 by request. Found from CI rather than the product: `origin/main` moved for the first time in fourteen sweeps, and checking what landed surfaced a workflow that had been failing since long before those commits.

## What was seen

Run `35167303015` of **gitops (render)** on `2f2a057db`, 2026-09-17T00:37Z. Every preceding check in the script passes; the job produces exactly **two** `FAIL:` lines:

```text
==> tenant rollout headroom stays preemptible, pool-scoped, and tier-sized
FAIL: tenant-headroom tolerates bex.co/build-only — that holds an elastic BUILD node (ADR060 D8) warm for serving rollouts that may not schedule there
FAIL: see errors above
##[error]Process completed with exit code 1.
```

**The breaking commit is `d82cc98cd`** ("fix(hosting): reserve rollout headroom so a deploy stops minting the node that evicts it", 2026-09-12T05:06:46Z). Its very first gitops run failed at 05:06:53Z. The last green run was `1ec6bac1e` at 2026-09-11T21:35:31Z. The gate has been red continuously since — 19 failures in the last 30 runs.

## Root cause — the check, not the tree (measured under both yq versions)

`scripts/gitops-validate.sh:2628`:

```sh
headroom_build_tol="$(yq -N "$headroom_pod | (.tolerations // []) | map(select(.key==\"bex.co/build-only\")) | length" "$headroom_yaml")"
```

`deploy/gitops/base/tenant-headroom.yaml` holds **two documents** (a `PriorityClass` at `:45` and the `Deployment` at `:62`). Under the yq version CI pins, the `//` alternative operator **materializes for the document `select` already filtered out**, so the expression emits one line per document.

Measured on the identical file (`git diff 1331e6203..2f2a057db` confirms `gitops-validate.sh` and `tenant-headroom.yaml` are byte-identical across the range):

```text
yq v4.44.6 (pinned by .github/workflows/gitops.yml:122):
  output = "0\n0"   (od -c: 0 \n 0)   ->  [ "0\n0" != 0 ]  ->  FAIL
yq v4.47.1 (current release):
  output = "0"      (od -c: 0)        ->  [ "0" != 0 ]     ->  PASS
```

The three sibling assertions in the same block use the same `select(...) | .spec.template.spec` prefix against the same two-document file and **pass**, because their expressions emit nothing for the non-matching document: `.priorityClassName` -> `bex-tenant-headroom`, `.terminationGracePeriodSeconds` -> `0`, `.nodeSelector."bex.co/pool"` -> `tenant`, each a single line. The only structural difference in the failing one is `(.tolerations // [])`.

**The author already hit this pitfall class once, and the fix introduced the second instance.** The comment directly above the failing line (`:2625-2627`) reads: _"`(.tolerations // [])` and not `[.tolerations[]? | ...]`: the array collector materializes even for the documents `select` filtered out, so the bracket form answers '0' once per document in the file and never compares equal."_ That diagnosis is exactly right — and `// []` has the same behaviour under the pinned version.

## The manifest is correct and must not be "fixed"

`deploy/gitops/base/tenant-headroom.yaml` has **no `tolerations` block at all**, deliberately. Its own comment at `:94-98` states the intent the check enforces:

```text
# The serving pool only. bex-tenant-lg and bex-tenant-burst also carry
# bex.co/pool=tenant but are tainted bex.co/build-only (ADR060 D8), and
# this deliberately does NOT tolerate it: reserving capacity on a build
# pool would hold an elastic build node warm for a rollout that is not
# allowed to schedule there anyway.
```

Author intent, check intent and ADR060 D8 all agree. **Do not add or remove anything in the manifest to make the gate green** — that would satisfy the error message while breaking the reservation the manifest exists to provide.

## Fix — and the one that looks right but does not work

Target behavior: the assertion reads a single scalar regardless of how many documents the file holds.

- **`| head -1`** — verified under yq 4.44.6: output becomes `0`, the check passes.
- **`| tr -d '\n'` does NOT work here, despite being the in-tree idiom elsewhere.** Verified under 4.44.6: it concatenates to `"00"`, which still compares unequal to `0` and still FAILs. It works at `:1050`, `:1246`, `:1259`, `:1269`, `:1444` because those expressions emit nothing for non-matching documents, so there is nothing to concatenate. Anyone applying the familiar idiom here ships a fix that does not fix it.
- **Alternative worth considering:** bump `YQ_VERSION` (`.github/workflows/gitops.yml:122-123`, currently `4.44.6` with a pinned arm64 sha256). 4.47.1 does not exhibit the behaviour. This silently repairs the assertion but leaves the fragile expression in place for the next version bump, so prefer fixing the expression; bumping as well is fine.

## Blast radius — counted, not estimated

`grep -c '// \[\]' scripts/gitops-validate.sh` -> **10 occurrences**. Classified:

- **One is the defect:** `:2628`.
- **Two are path-scoped, with no document-level `select`** (`:1204`, `:1218` — `(.initContainers // [])` / `(.containers // [])` inside an already-resolved `.spec.jobTemplate...` path), and are consumed by a `while read` loop that skips empty lines.
- **The rest pair a doc-level `select` with `// {}` / `// []` but every one ends in `| tr -d '\n'`** (`:1245`, `:1267-1268`, `:1444`; guards at `:1246`, `:1259`, `:1269`, `:1272`, `:1275`, `:1445`) and **all pass in CI today** — the run produced only the two FAIL lines above, so they are empirically unaffected.

**Failure direction matters and is favourable:** this class produces _visible red_, not false green. A "must-exist" guard fed a multi-line value would use `-eq` and throw a bash integer error rather than passing quietly; the only `-eq 0` sites are `:879` and the final aggregator `:2668`.

## Resolved 2026-09-17

Fixed by `f69e2c52c` — `scripts/gitops-validate.sh` now reads `yq -N ea "[$headroom_pod | .tolerations[]? | select(.key==\"bex.co/build-only\")] | length"`, evaluating all documents as one stream so the collector materializes once. The commit's own comment records both forms that failed (`select(...) | (.tolerations // []) | map(...) | length` and `select(...) | [.tolerations[]? | ...] | length`, each answering `"0\n0"`), matching this note's measurement exactly.

**The shipped fix is better than the one proposed here, in two ways.** It does not rely on `head -1` trimming a symptom — it removes the multi-document materialization itself. And it adds a guard loop over every captured value (`headroom_priority`, `headroom_preemption`, `headroom_class`, `headroom_grace`, `headroom_pool`, `headroom_build_tol`) that fails loudly if any contains a newline, so the next assertion written in this shape cannot silently miscompare. That closes the class rather than the instance — what this note's "Blast radius" section argued for but did not itself specify.

`gitops (render)` is green again (`4763a5e53`, `94246d5b9`) after failing every run since 2026-09-12.

**The follow-up this note recommended also shipped.** `6775f4f90` added `scripts/ci-red-streak.sh` and `.github/workflows/ci-red-streak.yml`, alerting when a workflow goes persistently red on `main` — the "nothing currently watches the watcher" gap named above. Its commit message reaches the same conclusion independently: _"A permanently-red check is worse than no check: it guards nothing and it teaches people that red is the normal colour."_

**Not closed by the fix**, and carried forward from Unverified: whether any manifest merged during the 5.5-day window is actually broken. The 22 commits that merged unvalidated were counted, never individually validated — the gate passing now proves only that the tree is valid today.
