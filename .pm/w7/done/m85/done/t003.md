## Objective

Stop installing a package at runtime in the stage that handles unencrypted tenant backup data, and pin the rest of the backup Job's stages while there.

## Context

- [ADR067](../../../docs/ADR067-security-review-round12.md) finding 8 names this specifically: the Key Value backup pipeline "installs `age` at runtime via `apk add` in a stage that reads the plaintext RDB". A compromised or hijacked package feed therefore executes code with the plaintext backup in reach.
- ADR050 Tier A is what introduced the `age` step (`BEX_BACKUP_AGE_PUBLIC_KEY`; the private half stays out of band in `.env`/CI for `scripts/restore-*.sh`).
- ADR067 notes the durable fix is "the reviewed first-party backup helper ADR061 already scoped" — that is a larger piece of work. This task takes the bounded version: eliminate the runtime install.
- **[ADR068](../../../docs/ADR068-security-review-round13.md) #9 has effectively settled the choice**: it names the durable fix as "a first-party reviewed backup helper image containing `valkey-cli` + `gzip` + `age`, digest-pinned". Build that unless a concrete reason not to emerges — record the reason if so.
- ADR068 #9 also widens the scope beyond the encrypt stage: the **snapshot** stage runs `valkey:<version>` and the **compress** stage runs `busybox:1.37`, both tag-addressed over plaintext backup material. The upload image is already pinned. One helper image covers all three.
- The same finding notes snapshot-stage `REDISCLI_AUTH` exposure is bounded by the same supply-chain prerequisite — mention it, but it is not in scope here.

## Steps

1. Build the first-party helper image (`valkey-cli` + `gzip` + `age`), digest-pinned, per ADR068 #9 — or record why not.
2. Move the snapshot, compress and encrypt stages onto it so **no** stage performs a network package install and none is tag-addressed.
3. Verify a backup still encrypts and — critically — that `scripts/restore-*.sh` can still decrypt an object produced the new way.
4. Confirm the unset-`BEX_BACKUP_AGE_PUBLIC_KEY` path is still byte-identical (plain `.gz`).

## Files

- `lego/operator/internal/controller/keyvalue_backup.go`
- `scripts/restore-*.sh` if the decrypt path needs a matching change

## Acceptance criteria

- [x] No `apk add` (or equivalent) runs in any stage that touches plaintext backup material.
- [x] The snapshot, compress and encrypt stages are all digest-pinned (ADR068 #9's full scope, not just the encrypt stage).
- [x] A produced `.rdb.gz.age` still decrypts with the existing restore script.
- [x] Backups disabled / no age key remains byte-identical.
- [x] The chosen approach and its trade-off are recorded.

## Out of scope

- The full first-party backup helper ADR061 scoped — that is a separate milestone.
- `REDISCLI_AUTH` exposure in the snapshot stage.

## Outcome (2026-08-21)

**Done, and deliberately not the way ADR068 #9 named it.** Recorded in [ADR050](../../../docs/ADR050-encrypted-platform-backups.md), [ADR067 finding 8](../../../docs/ADR067-security-review-round12.md) and [ADR068 finding 9](../../../docs/ADR068-security-review-round13.md).

Two of the three defects this task inherited were already closed when it ran: snapshot and compress were digest-pinned by round-14 #5, and `apk add age` had become a checksum-verified release download in round-16 #11. What was genuinely open was that download — still a network fetch inside the stage holding the plaintext RDB.

**What shipped:** `lego/operator/cmd/backup-encrypt`, `filippo.io/age` v1.3.1 compiled into the bex image as a `/backup-encrypt` entrypoint. The encrypt stage runs it with plain file arguments — no shell, no package manager, no download, nothing resolved at run time. The operator resolves its own image off its Pod (`internal/selfimage`, `POD_NAME` downward API), so the stage always matches the digest the operator was rolled out with.

**Why not the separate `valkey-cli` + `gzip` + `age` helper image:** the bex image is already the reviewed, cosign-signed, SBOM-attested, digest-pinned first-party artifact. A second published image would add a registry artifact to scan and sign, a sixth generated digest to the deploy write-back transaction, and a bootstrap fallback path — to run a stage the bex image can run itself. The trade-off accepted: the encrypt stage now depends on the operator knowing its own image, so **encryption configured + image unresolved fails the reconcile closed** rather than uploading plaintext (`TestKeyValueBackupEncryptionFailsClosedWithoutHelperImage`).

**Verified:** a `.rdb.gz.age` produced by `/backup-encrypt` decrypts byte-identically with the upstream `age` v1.3.1 CLI — the exact binary `scripts/lib/restore.sh` invokes — so no restore-script change was needed. Backups with no age key remain byte-identical (`TestKeyValueBackupEncryptStepDisabledByDefault`, unchanged, plus the second half of the fail-closed test).

`REDISCLI_AUTH` exposure in the snapshot stage stays out of scope, as filed.
