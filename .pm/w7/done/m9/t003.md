## Objective

Bound how many build Jobs a single workspace can run concurrently (git-push-triggered or manual-deploy builds), queueing or rejecting past the cap — so one workspace's rebuild storm can't starve the shared build namespace/nodes.

## Context

- `BEX_BUILD_NAMESPACE` — the namespace build Jobs run in (shared across tenants per `CLAUDE.md`'s env-var table).
- `w1/m26` found a live incident class where a runaway rebuild loop (51 generations on one App) filled shared registry storage — this task closes the sibling concurrency-side risk.
- Build-trigger paths: manual deploy trigger (`w2/m5`), push-to-deploy webhook (`w2/m9`).

## Steps

1. Decide queue-vs-reject semantics for a workspace at its build-concurrency cap (reject is simpler and matches this milestone's "clean rejection" DoD; document the choice).
2. Count the workspace's currently-running build Jobs (label-selector query in `BEX_BUILD_NAMESPACE`) before admitting a new build.
3. Wire the check into both the manual-deploy trigger and the push-to-deploy webhook path.

## Files

- `lego/backend/internal/deploys/` (build-trigger paths)

## Acceptance criteria

- [ ] A workspace at its build-concurrency cap gets a clean rejection on a new build trigger, from both manual and webhook paths.
- [ ] Builds under the cap are unaffected.

## Out of scope

- Cross-workspace fair-scheduling of the shared build namespace — this task only bounds one workspace's own concurrency, not global scheduling fairness.
