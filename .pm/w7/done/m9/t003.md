## Objective

Bound build concurrency in the operator: per App, at most one active build Job — a newer revision's build supersedes and cancels the in-progress one (Render's documented behavior verbatim); across a workspace, at most the t001-configured number of concurrent build Jobs (bex extension — a superseding build waits/requeues rather than erroring when the workspace is at its cap). Env knob per t001; unset ⇒ current behavior.

## Context

- Build Job creation: `lego/operator/internal/build/build.go` (Jobs already carry `ActiveDeadlineSeconds` + TTL from m2); the reconcile trigger lives in `lego/operator/internal/controller/app_controller.go`.
- Render anchor: "Each Render service can have only one active build at a time … Render cancels any in-progress build for the same service" (render.com/docs/build-pipeline, 2026-07-12).
- Workspace attribution: build Jobs/Apps carry the `app.bex.co/workspace` label (m1 contract) — count active build Jobs by that label for the cap.
- Cancellation = delete the superseded Job (propagation foreground) so BuildKit stops burning the shared quota; the reconcile loop's requeue machinery handles the at-cap wait (no busy loop).
- The git webhook stays rate-limit-exempt (m3) — this task bounds the damage instead of touching the exemption.

## Steps

1. Per-App: before creating a build Job for a new revision, find an active Job for the same App and older revision — delete it (newest wins); never run two builds for one App.
2. Per-workspace: count active build Jobs with the App's workspace label; at the cap, requeue the reconcile rather than creating the Job.
3. Verify on the local mock: rapid revision bumps on one App leave exactly one active Job; N+1 concurrent Apps' builds in one workspace hold at N with the (N+1)th starting after a slot frees.
