## Objective

Enforce the t001 creation caps in bex-api's core create verbs for services, databases, and key-value instances: one count-against-cap check in the core layer (`lego/backend/internal/core` or the owning service packages), so the REST, GraphQL, and MCP adapters inherit identical behavior per the ADR006 one-core/thin-adapters pattern. Env knobs per t001; `0`/unset ⇒ no cap (byte-identical today).

## Context

- Create paths: apps (`lego/backend/internal/apps` — `specFromCreate`/`appFromRequest` are the m-w6 validator precedent for where create-time gates live), postgres (`lego/backend/internal/postgres`), keyvalue (`lego/backend/internal/keyvalue`).
- The count is per **workspace** (owner) — count existing live resources for the caller's workspace; deleted/suspended semantics per t001 (Render counts *active* free datastores).
- Error shape from t001 — follow the m6 pattern of surfacing it identically on all three surfaces (`TestAuditSurfaceParity`-style parity tests exist as precedent; t006 covers tests).
- New env vars ⇒ CLAUDE.md env table + `.env.example`/`.env.template` sync (repo rule).

## Steps

1. Plumb the t001 knobs into config (`lego/backend/internal/core/config.go` pattern).
2. Add the count check at each create verb's core entry point; return the t001 error.
3. Verify manually on the local mock: cap=1, second create refused on REST + GraphQL + MCP, second workspace unaffected.
4. Update the CLAUDE.md env table + example/template envs.

## Files

- `lego/backend/internal/core/` (config + shared check)
- `lego/backend/internal/apps/`, `lego/backend/internal/postgres/`, `lego/backend/internal/keyvalue/` (create verbs)
- `CLAUDE.md`, `.env.example`, `.env.template`

## Acceptance criteria

- [ ] With a cap configured, the (N+1)th create for a workspace is refused with the documented error on REST, GraphQL, and MCP; another workspace can still create.
- [ ] All knobs unset ⇒ no behavior change (existing tests stay green).
