## Objective

Decide the full limit vocabulary before implementation: which caps exist (services / databases / key-value instances per workspace; concurrent builds per App and per workspace), their env-var names and defaults (`0` = disabled; unset ⇒ current behavior), and the error shape returned on all three surfaces. Anchor on Render's documented numbers and record the conscious divergences, then write it into `docs/ADR006-bex-api.md` as a sibling of § Rate limits.

## Context

- Render anchors (verified against render.com docs 2026-07-12, cited in the milestone README): Hobby = 25 total services per workspace (natural default for the service cap); free tier = 1 active free Postgres + 1 active free Key Value per workspace (bex caps are tunable counts — no 30-day expiry copy); builds = one active build per service, newest wins, in-progress build cancelled.
- Divergences to record: per-workspace concurrent-build cap is a bex extension (Render bounds via billed pipeline minutes — bex has no billing, per the FUTURE-MAYBE pricing entry); Render publishes no API error shape for its service cap, so bex picks its own consistent shape (the m6 precedent: pick, document, cross-reference in the parity ledger).
- Existing knob style to follow: `BEX_RATE_LIMIT`/`BEX_RATE_BURST` (m3) — env-tunable, `0`/unset disables, documented in the CLAUDE.md env table.
- Error-shape precedents: m3's `{"id":"rate_limited","message":…}` + GraphQL `extensions.code` envelope; m6's 409/400 collision guards.

## Steps

1. Fix the cap list, env names (e.g. `BEX_MAX_SERVICES_PER_WORKSPACE`, `BEX_MAX_DATABASES_PER_WORKSPACE`, `BEX_MAX_KEYVALUES_PER_WORKSPACE`, `BEX_MAX_BUILDS_PER_WORKSPACE`), and defaults.
2. Pick the error: status code + REST body id + GraphQL extensions code + MCP mapping, consistent with the m3/m6 vocabulary.
3. Write the § into `docs/ADR006-bex-api.md` (anchors, defaults, divergences); note the CLAUDE.md env-table rows t002/t003 will add.
