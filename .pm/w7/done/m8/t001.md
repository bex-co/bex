## Objective

Decide and document how Zot access control works before any implementation: htpasswd authentication + Zot `accessControl` policies; a shared push credential (held in the build pod's filesystem, unreadable from tenant `RUN` steps) vs per-App credentials; and whether reads stay anonymous (kubelet pulls unchanged, but tenant builds can still pull cross-tenant images) or become authenticated (needs t004's `imagePullSecrets`). Write the decision down so t002–t004 execute without re-litigating.

## Context

- `deploy/gitops/base/zot.yaml:16` — "local/dev defaults"; the "TLS + auth" intent is a comment, not config. Chart values have `mountConfig: false`; a custom Zot config (auth + accessControl) likely requires flipping that.
- `lego/operator/internal/build/build.go:184` — push is `--output type=image,name=<image>,push=true,registry.insecure=true`, no credential anywhere.
- `deploy/gitops/base/network-policies.yaml:64-68` — pods labeled `app.bex.co/component: build` may reach Zot :5000; those pods run tenant-authored Dockerfile/CNB steps in the pod's network namespace. Lines 71-84: kubelet pulls arrive from node identity (host/remote-node), currently anonymous.
- Threat model nuance: tenant `RUN` steps can mount any **declared** BuildKit secret (the `GIT_AUTH_TOKEN` precedent) and see build-args, but cannot read the pod filesystem — so a docker-config credential mounted into the buildkitd container is safe from them. This is why shared-cred-first still closes the anonymous hole.
- Zot htpasswd/accessControl is static-file config — per-App dynamic credentials mean regenerating the htpasswd file on every App create/delete; weigh that operational cost against what per-App scoping actually buys (protection if buildkitd itself is exploited).
- `registry.insecure=true` is TLS-off, not auth-off — with auth on, credentials cross the cluster network in plaintext HTTP; document that residual or decide TLS is in scope.
- Check for other registry clients before deciding: operator, bex-api, opensandbox — anything else that reads/writes Zot.

## Steps

1. Enumerate every Zot access path (build push, kubelet pull, cosign signing container from w6/006, anything else) and what credential each would need.
2. Decide: shared vs per-App push credential; anonymous-read vs authenticated-read; TLS or documented plaintext-HTTP residual.
3. Write the design into `docs/ADR022-tenant-isolation.md` (new § Registry access control) with the residual risks of the chosen scheme; cross-reference from `docs/ADR028-security-review.md` if touched.
