Why: the serving pool is at its autoscaler ceiling and can no longer spill onto the tainted build pools, so the next tenant growth spurt hits an unschedulable wall — and the measurement decides between opposite fixes (add a node vs right-size requests).

**What is true:**

| ------------------ | ----- | ---------------------- | ------------------- |
| `bex-tenant-0`     | cx33  | **2 / 1 / 2 — at max** | none                |

The serving pool has no headroom, and since ADR060 D8 tainted the other two pools, serving workloads can no longer spill onto them. D8 anticipated this and raised tenant-0's max from 1 to 2 — it is now at that new ceiling.

**No harm observed:** a cluster-wide `--field-selector status.phase=Pending` query returned only the one live build pod, so nothing is currently unschedulable. This is a headroom risk, not an incident.

**Do this first, before any proposal:** read actual-versus-requested utilisation on both `bex-tenant-0` nodes. Requests are what the scheduler enforces, and the 2026-08-08 incident showed nodes 85–97% committed on requests while only 11–52% used — so "at max" may mean genuinely full or merely over-requested, and those have opposite fixes (add a node vs. right-size requests).

Note this is a **serving** question, not a build question. Do not let it fold into the build-plane milestones (`m82`–`m86`), whose capacity thread is closed (`builder-issues.md` §4).
