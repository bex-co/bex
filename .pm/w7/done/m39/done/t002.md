## Objective

Make the pull-Secret reclamation story truthful and regression-guarded: the comment claims owner-reference garbage collection that doesn't exist (and can't — the Secret and the App CR live in different namespaces), while actual reclamation rides an explicit delete. If a future refactor trusts the comment and drops that delete, Secrets leak per deleted App.

## Context

- `lego/operator/internal/registry/creds.go:136` — "The per-App pull Secret is garbage-collected via owner references." No `SetControllerReference`/`OwnerReferences` call exists anywhere in the file.
- Actual reclamation: the explicit `r.Delete(...)` in `lego/operator/internal/controller/app_controller.go:2306-2309` (alongside `RevokeCreds` for the htpasswd/ACL half at `:2302`).
- Cross-namespace owner references are not permitted in Kubernetes, so the comment's mechanism is impossible as-is — correcting the comment (not adding owner refs) is the fix.

## Steps

1. Rewrite the comment to state the real mechanism (explicit delete on App deletion) and why owner refs can't apply (cross-namespace).
2. Add a regression test: reconcile an App to mint creds, delete the App, assert the `reg-pull-<name>` Secret, htpasswd entry, and ACL entry are all gone (envtest or the existing per-App-registry envtest file).

## Files

- lego/operator/internal/registry/creds.go
- lego/operator/internal/controller/per_app_registry_envtest_test.go

## Acceptance criteria

- [ ] No comment claims owner-reference GC for the pull Secret.
- [ ] A test fails if the explicit delete in `app_controller.go` is removed.

## Out of scope

- Restructuring where the Secret lives to make owner refs possible — the explicit delete is the accepted mechanism; this task makes it truthful and guarded.
