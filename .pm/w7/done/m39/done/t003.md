## Objective

Stop htpasswd/config write contention from failing reconciles. Every App reconcile patches the same two singleton Secrets (`zot-htpasswd`, `zot-config`) under optimistic locking with a hard cap of 5 attempts, then returns an error — under bulk onboarding or a mass resync, the two Secrets serialize all writers and can exhaust the cap, failing Apps that did nothing wrong.

## Context

- `lego/operator/internal/registry/creds.go:153-303` — four `for range 5` loops (`ensureHTPasswdEntry`, ACL add, and their revoke counterparts) ending in `fmt.Errorf("too many conflicts updating htpasswd for %s", username)`.
- controller-runtime treats a returned error as requeue-with-backoff anyway, but the error is logged as a failure and counts against reconcile-error metrics/alerts; a conflict is expected contention, not a failure.
- Options: return a typed transient/conflict result that requeues quietly (`ctrl.Result{RequeueAfter: …}` on `apierrors.IsConflict`), or use `retry.RetryOnConflict` with a fresh GET per attempt (which it already does) plus jitter and treat final conflict as requeue-not-error.

## Steps

1. Pick the mechanism (typed conflict ⇒ requeue quietly is the least invasive) and apply it to all four loops.
2. Add a test that runs N goroutines minting distinct users against one htpasswd Secret through a conflict-injecting fake client and asserts every user lands without a hard error.
3. Confirm reconcile-error metrics no longer count pure-conflict outcomes (inspect how the controller surfaces the result).
