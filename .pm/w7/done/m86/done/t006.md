## Objective

Produce the number that justifies the feature, against the D5 series rather than a stopwatch impression.

## Context

- The milestone's why-now is explicitly the weakest of its batch, so it owes an honest measurement — including an honest negative result if the win is small.
- `bex_build_run_seconds` (`w2/m72`) is the series to read; m83's `bex_build_queue_seconds` separates queue time out, which matters because a slow build and a queued build were previously conflated.
- ADR060 records the alternative if this underdelivers: "per-workspace persistent cache volumes are the intermediate step if D3's hit rate proves insufficient." So a weak result has a defined next move rather than being a dead end.
- Use a repo whose dependency install genuinely dominates (a JS or Rust build), not a trivial one that would flatter the result.

## Steps

1. Pick a representative repo where dependency install dominates the build.
2. Record cold-cache and warm-cache `bex_build_run_seconds` for the same commit.
3. Record the added push cost (the second artifact) and the registry storage growth.
4. Write the result into `docs/ADR060` — including the honest verdict if the delta is small, plus whether the persistent-cache-volume escalation should be triggered.

## Outcome — measured, but NOT from the metric

Measured on a faithful local harness (the pinned `moby/buildkit:v0.30.0` and `quay.io/skopeo/stable:v1.22.2` the build plane runs, against a real Zot) with a multi-stage Node service whose `npm install` dominates:

| | cold | warm |
| --- | --- | --- |
| build | 55.2s | **20.5s**, every dependency step `CACHED` |
| cache restore | — | 1.2s |
| cache store | 1.5s | 1.5s (beside the 0.8s image push, not before it) |
| net wall clock | 56.7s | **23.2s (−59%)** |

Added push cost and storage growth, both quantified as the task required: the cache is **512 MB against a 90 MB image**, taking the App's registry footprint from 90 MB to 512 MB (**+422 MB per App** after dedupe). That is inherent to `mode=max` — `min` would discard exactly the dependency layers that produced the win — but it is a 5.7× multiplier on per-App registry storage against a single-replica Zot PVC. Escalation call: the hit rate is excellent, so ADR060's persistent-cache-volume escalation is **not** triggered.

## Outcome — on-cluster D5 measurement, 2026-09-05

Completed two real same-commit pairs: dashboard Dockerfile **179s → 38s (−78.8%)** and dependency-focused native Node API **75s → 64s (−14.7%)**. All four queue samples were zero. Warm dependency steps were cached and image digests matched. Cache-save phases were 4s/1s and 3s/1s; incremental deduplicated registry content was 173,078,026 bytes and 5,825 bytes respectively. The latter still restores about 517 MB, explaining why a hit need not produce a large total gain.

Full fixtures, histogram method, footprint semantics, failure exclusions, cleanup and verdict are in `docs/drills/2026-09-05-build-cache.md` and ADR060 D3. No persistent-volume escalation: hits worked. Keep the gate opt-in pending an estate-wide capacity decision. Both pairs' disposable Jobs, Pods and repository tags were removed; production manager configuration was unchanged.
