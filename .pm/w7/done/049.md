# 049 — A service URL opened directly leaves every capability-gated control dead for ~30 seconds, and Settings says "Permissions could not be refreshed"

**Promoted to [w7/m149](../m149/README.md)** by `$pm all for w7` after the five-item brainstorm. This archives the source note, not a completed implementation. The approved milestone supersedes the historical blocked status and undecided options below.

## Historical source evidence

Why: anyone who opens a service link in a new tab — from a notification, a deploy email, a teammate's message, or a bookmark — lands on a page whose Environment editor is disabled and whose Settings page claims their permissions failed, with no way to act until a 30-second poll quietly fixes it. Nothing is wrong with their role: the workspace capability check is simply never evaluated for that page load.

**Estimate:** 1h30m (diagnosis is half of it) · **Severity:** major (misleading permission error; blocks the env-var journey on that page load) · **Attribution:** dashboard · **Worker:** worker7

## Repro (every step was run, three independent fresh-browser runs)

1. Open a **fresh browser** with a valid dashboard session (no prior dashboard page visited in it).
2. Go straight to `https://dashboard.bex.co/services/<srv-id>/env`.
3. Watch the "Edit" and "Export" buttons on the Environment Variables card, and the Settings page's Source card.

Sampled once per 2s, with every GraphQL request logged:

```text
2s  edit=disabled   30s edit=disabled
…   (disabled at every sample from 2s through 30s)
32s edit=enabled

requests:
 0.0s GET  dashboard.bex.co/services/<srv-id>/env
 2.1s POST api.bex.co/graphql [Workspaces,InstanceTypes,Deploys]   → 200, three workspaces, no errors
 2.2s POST api.bex.co/graphql [EnvVarKeys,SecretFileNames]
 2.7s GET  auth.bex.co/sessions/whoami
 2.7s POST api.bex.co/graphql [Services,Projects,BillingReadiness,DeployActions,EnvGroups]
32.2s POST api.bex.co/graphql [Workspaces]          ← the 30s poll
32.7s POST api.bex.co/graphql [ViewerCapabilities]  ← the FIRST capability evaluation of this page load
```

The first `Workspaces` response (2.0s) is a clean `200` carrying all three workspaces and no `errors` key — the stall is not an API failure.

On `/services/<srv-id>/settings` opened the same way, the phrase **"Permissions could not be refreshed. Try again — this is not a role change."** renders **5 times** (once per gated card). Clicking through to Environment from that page (client-side navigation, no reload) leaves Edit **disabled**, and going back leaves the banner in place: only the 30s poll, a reload, or a window focus/visibility event clears it. Dispatching `focus` at 30s produced `ViewerCapabilities` within 800ms and enabled the controls immediately.

**Control (passes):** the same service reached by clicking from the dashboard home — `ViewerCapabilities` fires at 7.5s and Edit is enabled at every sample. The env-var journey then completes normally: `patchServiceEnvironment` → `{envVarKeys:["MESSAGE"], rolledOut:true}`, and `https://<slug>.onbex.co/` served the new value.

**Expected:** a deep-linked page evaluates capabilities as soon as the workspace is known (seconds, not 30), and until that answer exists the controls render a *pending* state — never the failure copy, which should appear only when a capability check actually failed.

**A second, harsher symptom of the same unresolved workspace (observed 2026-09-16, sweep 8).** `/agents` is guarded by `requireAgentsFeature()` (`dashboard/src/common/lib/growthbook/require-agents-feature.ts:8-13`), which calls `isAgentsDashboardEnabled(context.workspaceId)` (`config/growthbook.ts:89-95` — the note first cited `:77-83`, which has since drifted) and **throws `redirect({to:"/"})` when it answers false**. Opened as a cold deep link in a fresh browser, `https://dashboard.bex.co/agents` lands on the Projects overview and never issues an `AgentSessions` query at all — the whole route is unreachable. Reached warm (home first, then `/agents`) the same URL renders normally and its loader's `AgentSessions` query returns 20 sessions. So where the env editor merely sits disabled for ~30s, a flag-gated route disappears outright; both follow from `context.workspaceId` being null on the first paint. Any fix must make the gate wait for a resolved workspace rather than treating "not yet known" as "not entitled" — add that to the acceptance list.

## Root cause (partly traced; the stall itself is unverified)

Verified by reading:

- `dashboard/src/features/capabilities/context/capabilities-provider.tsx:136-145` — `refresh()` returns early when `workspaceRef.current` is null, leaving the state at `checkingCapabilities`. The effect that calls it (`:242-249`) re-runs only on `[currentWorkspaceId, generation]`, and the poll/focus/online listeners (`:250-275`) are registered only `if (currentWorkspaceId)`.
- `dashboard/src/features/workspaces/context/index.tsx:39-46` — `selectedId` is `preferredId` (the server cookie, null on a first visit) until `ready`, then the first workspace.
- `dashboard/src/features/workspaces/hooks/use-workspaces.ts:55-66` — `ready = authenticated && !loading && data !== undefined && error == null`, `fetchPolicy: "cache-first"`, `pollInterval: RESOURCE_POLL_INTERVAL_MS` (the 30s that matches the observed recovery).
- The user-visible copy: gated controls read `capabilities.reasonKey("can_create")` → `grantReasonKey` (`features/capabilities/lib/capability-policy.ts:156-182`), which returns **undefined while `status === "checking"`** ("disable without claiming a role change") and `capabilities.grantUnavailable` only when `status === "unavailable"` or a ready snapshot's grant is `unavailable`. The copy is `features/capabilities/locales/en.ts:85` (key; message text at `:86-87`). Consumers — **corrected sweep 35**: `features/services/components/service-environment-editor.tsx:222` (`useCapabilities`), `:226-227` (`reasonKey("can_create")` and `("can_view_sensitive")`), with the gated controls at `:674-677` (Edit, `disabled={loading || Boolean(errorKind) || createDenied}`), `:640-652` (Export) and `:740-743` (Add secret file). ~~`env-vars-panel.tsx:137-166` and `secret-files-panel.tsx`~~ — those files **were dead code when this note was filed and no longer exist**; see "What this corrects".
- **So the observed page was in the `unavailable` state, not merely pending** — which the provider sets only in `refresh()`'s catch (`capabilities-provider.tsx:227-233`, and that catch explicitly ignores its own aborts). Yet no `ViewerCapabilities` request reached the wire in 30 seconds, and the server-rendered HTML contains neither the copy nor the page body (`curl` of `/services/<id>/settings` with the session cookie: 241,617 bytes, zero matches for the phrase and for "Custom Domains"), so the state was produced client-side without a visible request. A query that rejects before dispatch is the shape that fits; proving it is the first task.

**Unverified — the fix task must settle this first:** why `currentWorkspaceId` stays null for ~30s even though the first `Workspaces` response arrives clean at 2.0s. Two candidates, both testable by instrumenting `ready`/`selectedId`/`refresh(reason)` in a dev build against a deep link: (a) the first response is delivered as part of an Apollo **batch** issued by another consumer, and the provider's own `cache-first` query never resolves until the poll; (b) `authenticated` (from `useRootContext().session`, `routes/__root.tsx:22-57`) is false during hydration, so the query is `skip`ped, and the un-skip does not deliver the cached value. Do not write the fix against either until one is proven.

## Fix

1. **Separate pending from failed.** While no capability answer exists yet, gated controls must show a pending/checking state (disabled with "Checking permissions…" or a skeleton), never `grantUnavailable`. Today the same copy covers "never asked" and "asked and failed".
2. **Ask as soon as the workspace is known** on a deep link — and, once proven, fix the root stall so the first evaluation happens in the same second as the workspace list rather than at the poll boundary.
3. Keep the fail-closed rule from `w6/m144`: an unknown answer must still not enable actions.

## What this corrects (sweep 35)

The live observation stands — three fresh-browser runs, re-confirmed on the post-deploy build in sweep 22 with the count of 5 and the ~30s recovery matching exactly. What was wrong is where the note pointed in the code.

1. **The consumer citation named dead code, and did so at the moment of filing — not through later drift.** At this note's own revision `7099fc707`, `env-vars-panel.tsx` was imported only by two test files and by `secret-files-panel.tsx`, which in turn was imported only by its own test. Neither was reachable from the running app. `service-environment-editor.tsx` — the component that actually renders the Edit/Export/Add-secret-file controls and actually calls `useCapabilities` — existed at that same revision. Commit `3f6b44a32` ("delete **dead** env components", 2026-09-15 23:22) removed the pair about six hours after `7099fc707`, and sweep 22's re-confirmation did not notice the citation had become unresolvable.
2. **The consumer count was wrong and the method overstated it** — see Blast radius. 33 → 32 raw, ~29 real.
3. **Two line citations had drifted**: `growthbook.ts:77-83` → `:89-95`, and `en.ts:87` → `:85`.

**What survived verification, checked line by line at HEAD `1331e6203`:** `capabilities-provider.tsx:136-145` (the early return on a null workspace), `:227-233` (the catch that sets `unavailable` and ignores its own aborts), `:242-249` (the effect keyed on `[currentWorkspaceId, generation]`) and `:250-275` (poll and focus/online listeners registered only `if (currentWorkspaceId)`); `workspaces/context/index.tsx:39-46`; `use-workspaces.ts:55-66`; `capability-policy.ts` `grantReasonKey` falling through to `return undefined` for `status === "checking"`; the copy quoted verbatim; and `RESOURCE_POLL_INTERVAL_MS = 30_000` (`common/lib/polling.ts:11`), which is what makes the ~30-second recovery the poll boundary rather than a coincidence.

**The one universal claim in this note was checked and holds.** The inference above depends on `unavailable` being reachable *only* through `refresh()`'s catch — otherwise the page could have arrived there some other way and the "no request on the wire" argument would not follow. `unavailableCapabilities` occurs at exactly three lines in the provider: `:34` (the import), `:230` and `:233`, both inside that catch. There is no other assignment site, so the inference stands. (Recorded explicitly because the equivalent claim failed in `052` and `053`; this one survived.) The `capability-policy.ts` span was `:155-181` and is `:156-182`.

The lesson is narrower than sweeps 33 and 34's. Those failed by enumerating on the wrong axis; this one failed by **not checking that a cited file is reachable from the running app**. A `file:line` that resolves is not the same as a `file:line` that executes — and a dead file can match the symptom's shape perfectly, because it usually *was* the code that produced that shape before it was replaced.

## Triage 2026-09-17 (`/loopx w7`) — BLOCKED on a live instrumented reproduction

Premise re-verified against current code: `capabilities-provider.tsx:136-144` still early-returns on a null workspace, and its effect still keys on `[currentWorkspaceId, generation]`. The defect stands. Two parts of this note's own diagnosis were advanced, and one was disproved:

- **Candidate (b) is falsified.** The note offered "`authenticated` (from `useRootContext().session`) is false during hydration, so the query is `skip`ped". It is not: `routes/__root.tsx` `beforeLoad` **awaits** `sessionPromise` and returns `session` in the route context, so `useIsAuthenticated()` is already true on the first render. `useWorkspaces` is never skipped for this reason. Do not spend time here.
- **Candidate (a) is still live but unproven.** `factory.client.ts:21-28` does use `BatchHttpLink` (`batchMax: 32`, `batchInterval: 10`), so queries are genuinely batched — but a 10 ms batch window cannot by itself explain a ~30 s stall, and nothing in source shows the provider's own query being starved.
- **Fix step 1 is already satisfied and should be dropped from the fix.** It claims "Today the same copy covers 'never asked' and 'asked and failed'". It does not: `capabilities.grantUnavailable` has exactly two sources, both in `capability-policy.ts` (`:166` `state.status === "unavailable"`, `:179` a ready snapshot whose grant is `unavailable`). A `checking` state returns `undefined`, so a pending page renders no reason copy at all. Pending and failed are already distinct in code.

**This sharpens the contradiction the note already recorded rather than resolving it.** For Settings to render the refresh-failure copy 5×, the provider must have reached `unavailable` — which `refresh()` sets only in its catch (`:227-233`), and that catch explicitly ignores its own aborts. So a `ViewerCapabilities` query must have *rejected*, while the network log shows no such request for 30 s. The shape that fits is a query that rejects before dispatch (`client.query` is called with `context.fetchOptions.signal`; an already-aborted signal rejects with no request), but nothing in source proves it happens on this path.

**The gate:** settling this needs a live cold deep link with `ready` / `selectedId` / `refresh(reason)` / the abort signal instrumented in a dev build — the note said so when filed ("both testable by instrumenting … in a dev build against a deep link"), and a further source pass has not substituted for it. Writing the fix without that measurement would be guessing at which of two mechanisms to repair, and the wrong guess ships a no-op — the failure mode this board has already seen twice (`054`'s budget, `056`'s `tr -d`).

**Not blocked on credentials.** Whoever picks this up can reproduce it with `scripts/qa-login.sh`; what it needs is an instrumented build and a focused live session, not access.
