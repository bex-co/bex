## Objective

Make the mutate function's output equal what the API server stores, so `CreateOrUpdate` returns `OperationResultNone` for an unchanged App — without rolling a single production pod.

## Context

- `028`'s fix sketch: set `TerminationMessagePath`/`TerminationMessagePolicy` on the container, `SuccessThreshold: 1` on all three probes, set readiness `PeriodSeconds`/`FailureThreshold` explicitly, and preserve the fetched `TerminationGracePeriodSeconds` when `MaxShutdownDelaySeconds` is unset — **or** switch the seam to `CreateOrPatch`.
- Choose deliberately between "match the defaults" and "switch to `CreateOrPatch`" and record why; matching defaults is more explicit but must be re-checked on Kubernetes upgrades, while `CreateOrPatch` is more robust but changes the seam's semantics.
- `w9/m57` fixed the Service equivalent by matching the server default (`Protocol`) — the precedent leans toward matching, but the probe field count here is larger.
- **Rollout safety is the hard constraint:** the Deployment template hash is computed post-defaulting, which is why nothing rolls today. Any change that alters the pre-defaulting template in a way the hash sees would roll every App in production at once.
- `m80` and `m81` set probe fields deliberately (5s timeouts, derived thresholds, `startupProbe`, `livenessProbe`) — do not disturb those values while adding the defaulted ones.

## Steps

1. Pick the approach and record the rationale in a code comment.
2. Implement it so the second reconcile is a no-op.
3. Prove no rollout: assert the resulting pod-template hash is unchanged versus the pre-fix projection for a representative App.
4. Confirm t001's Deployment assertion now passes.

## Result

**Approach: match the defaults**, in one shared place — `server_defaults.go`'s
`applyPodSpecServerDefaults`, called as the last line of `applyDeploymentSpec`. The
projection keeps saying what bex chooses; the helper says what Kubernetes would have
chosen for everything else.

The two alternatives were rejected on evidence, not taste, and the reasoning is in the
file's head comment:

- **`CreateOrPatch`** does not fix this. It diffs the same in-memory object before and
  after the mutate, so a mutate that drops a server-defaulted field still registers as a
  change and still sends a request. It changes the verb, not the request count.
- **Server-side apply** removes the need to know the defaults but sends a request on
  every reconcile by construction — which is the thing being removed.

So the cost of the chosen approach is that the constants must track the API server, and
that cost is paid by the test rather than by vigilance: `server_defaults_envtest_test.go`
re-derives every one of them from the live envtest API server, field by named field, and
asserts the whole defaulted PodSpec equals what the helper produces. A Kubernetes release
that moves a default fails a named line.

**No rollout, proven not argued.** `stores byte-identical bytes before and after the fix`
builds the Deployment from the pre-w7/m84 projection, stores it, then applies today's
projection to the stored object: the stored pod template is `Equal` and the
`resourceVersion` does not even move. The pod-template hash is a pure function of the
stored template, so an unchanged template is an unchanged hash.

**m80/m81 semantics untouched**: every value the helper writes for a probe is the
Kubernetes default the probe already inherited (readiness period 10s, failureThreshold 3,
successThreshold 1, `httpGet.scheme` HTTP). The deliberate bex values — 5s timeouts, the
derived startup/liveness thresholds — are set before the helper runs and it only fills
zeros. `TerminationGracePeriodSeconds` is the one visible change: nil-when-unset becomes
an explicit 30, which is exactly what the server had already stored.
