## Objective

Run `$simplify` over the OpenAPI boundary and remove accidental machinery while preserving all validation and compatibility behavior.

## Context

- The intended shape is one pin, one loader, one thin request wrapper, one strict JSON helper, and a small operation-keyed query-extension map.
- Likely complexity traps: parallel specs/routers, copying kin's middleware, a general overlay generator, per-handler error mappers, repeated body buffering, or retaining m30's custom schema walker after kin replaces it.

## Steps

1. Run `$simplify` over the milestone diff.
2. Consolidate shared loading/routing/error/decoding code and remove dead compatibility adapters.
3. Confirm the request path still buffers only under the existing body cap and production never validates responses.
4. Re-run focused tests after accepted simplifications.

## Acceptance criteria

- [ ] `$simplify` findings are applied or explicitly rejected with a concrete compatibility/security reason.

## Out of scope

- Relaxing validation to reduce code or refactoring unrelated feature adapters.

## Resolution

Simplification review retained one pin, one cached loader/router, one thin middleware, and one strict JSON helper. It removed the duplicate spec-operation traversal and the nested decoder's temporary `http.Request`, deleted the old spec/walker, and kept compatibility policy as small operation-keyed maps. A context-aware structural pass remains intentionally because `encoding/json` custom unmarshalers otherwise bypass `DisallowUnknownFields`; its regression test proves the security reason. Focused tests and lint remained green.
