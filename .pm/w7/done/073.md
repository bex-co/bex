# Under production's Kratos v26.2.0, a signed-in browser connecting an agent is asked for its password again

Why: w4/m17 made "already signed in → no login form" the commonest connect-an-agent path, and `scripts/auth-oauth21-e2e.sh` leg 13 proves it only against Kratos v1.3.1; production runs v26.2.0, where that path answers differently, so the script pins a Kratos that production does not run.

- Found by w7/065, 2026-11-16, when it moved the script's pins to production's versions. Hydra moved to v26.2.0. Kratos stayed on v1.3.1 because leg 13 fails under v26.2.0: a fresh password form is submitted where the script expects the signed-in shortcut.
- Probe (throwaway Hydra v26.2.0 and Kratos v26.2.0, both in memory, the script's `oauth2_provider` config with `override_return_to: true`): sign in once through the browser login flow, then authorize again with the same cookie jar. Kratos v26.2.0 answers the dashboard's AJAX call `GET /self-service/login/browser?login_challenge=…` (`Accept: application/json`) with 200 and a login flow that has `refresh: true`, `state: choose_method`. The same request as a browser 303s to `<dashboard>/auth/login?flow=<id>`, not to Hydra. Kratos v1.3.1 answers `null`, and `bootstrapViaKratos` in `dashboard/src/common/hooks/use-ory-flow.ts` handles that by sending the browser straight to Hydra (ADR012 §7 line 87).
- Hydra's login request has `skip: false` on every authorize, because Kratos accepts the challenge without asking Hydra to remember the login (the script's leg 11 and 13 comments). So under v26.2.0 a signed-in person is probably asked to re-enter a password each time an agent connects. Not yet checked on production: production's Kratos config (`deploy/gitops/base/values/kratos.values.yaml`) also differs in session and AAL settings.
- Fix: check on production (`dashboard.bex.co` as the QA user, sign in, then run an agent's authorize) what a signed-in person sees. If it asks for the password again, decide with Render's own OAuth flow as the reference (a signed-in Render user approving an app is not asked to sign in again) whether Kratos should be told to remember the login, or the dashboard should treat a `refresh` flow under a live session as the shortcut. Then move the script's Kratos pin to v26.2.0 and update leg 13 and ADR012 §7.
- Done when: `scripts/auth-oauth21-e2e.sh` pins Kratos v26.2.0 and exits 0 twice in a row, and leg 13 still asserts that a signed-in browser submits no password.

**Done 2026-11-17:** the script was wrong, not the product, and the version bump changed nothing a person sees. Kratos asks Hydra to remember every login it accepts (`session.cookie.persistent`, on by default), so a browser that signed in through a challenge is skippable at its next authorize. Kratos v26.2.0 then accepts the challenge and answers the AJAX call `400 session_already_available` (v1.3.1 answered `200 null`). The dashboard already hands both back to Kratos as a browser request (`use-ory-flow.ts`), and production answers the same way (w8/124 on 2026-10-19, w4/m454 t004 today). `kratos_login` read the 400 as a password form; it now classifies it as the signed-in shortcut. The script pins Kratos v26.2.0, leg 13 still requires that path (it fails on the old classification under v26.2.0), and it exited 0 twice in a row on a throwaway kind cluster with nothing left listening. The refresh flow the probe above saw is a browser Hydra does not remember yet: a person signed in only at the dashboard confirms their password at their first grant, under both versions (w4/m116 t005). Removing that is a Render parity gap that needs a user decision against DO_NOT_DO, filed as [w7/079](079.md). ADR012 §7 and ADR025 no longer claim Kratos skips the remember.
