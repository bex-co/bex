# `scripts/auth-obs-e2e.sh` fails at its ALLOW leg: the consent route's verified-email gate refuses the ops operator

Why: the script is ADR088 §4-5's end-to-end proof that the Grafana consent gate admits an ops-workspace admin and refuses everyone else, and it cannot pass on main, so the allow half of that gate is unproven against real components.

- Found by w7/065, 2026-11-16, which fixed the same break in `scripts/auth-oauth21-e2e.sh`. Run on a throwaway kind cluster with the bex CRDs (`FGA_PORT=28080`, since another session held 18080): legs 1–7 pass, then leg 8 ends at `https://obs.bex.co/login/generic_oauth?error=access_denied&error_description=Verify+your+email+address+before+signing+in+to+other+apps&state=state-allow`.
- Cause: since w2/m168 the dashboard's consent route runs the verified-email gate before any accept (`resolveSubjectGate` in `dashboard/src/common/server-fn/hydra-consent.ts`). The script starts the dashboard without `BEX_IDENTITY_CLAIMS_URL` and without `BEX_REQUIRE_VERIFIED_EMAIL=0`, so the gate is on, the claims lookup has no URL, and every subject counts as unverified.
- Fix, two options: set `BEX_REQUIRE_VERIFIED_EMAIL=0` on the dashboard, as `auth-oauth21-e2e.sh` now does; or, closer to production, point `BEX_IDENTITY_CLAIMS_URL` at the script's bex-api (`http://localhost:$CP_PORT/internal/identity-claims`, same bearer `BEX_OPS_ROLE_TOKEN`), mark the schema's email `verification: { via: email }`, and create both identities with a verified address, so the gate runs and passes. The second also proves the gate on the ops path.
- Done when: `scripts/auth-obs-e2e.sh` exits 0 twice in a row on a clean machine, and nothing listens on its ports afterwards.

**Done 2026-11-17:** the second option. The dashboard now runs the verified-email gate as production does (`BEX_REQUIRE_VERIFIED_EMAIL=1`, `BEX_IDENTITY_CLAIMS_URL` at the decoupled listener's `/internal/identity-claims`, same bearer). The schema's email carries production's `verification: { via: email }` marker, and A and B are created with a verified address through Kratos' admin API. B's two denials are therefore the ops gate's alone, and they still assert its own description. A new leg 13 adds C, an ops-workspace admin with an unverified address, who bounces with the gate's "Verify your email address…" description, so the role never outranks the gate. Leg 10 also asserts the identity-claims verb's answers (A verified, C not) and its 401 on a wrong bearer. Each server now starts as its own process group, and cleanup TERMs, TERMs again and KILLs the group, as in `auth-oauth21-e2e.sh`. On a throwaway kind cluster with the bex CRDs (`FGA_PORT=28080`), the script exited 0 twice back to back, and after each run nothing listened on 4433, 4434, 4444, 4445, 28080, 8290, 8191 or 5197. Dropping `BEX_IDENTITY_CLAIMS_URL` reproduces this note's exact leg-8 failure. Turning the gate off (`=0`) fails leg 13 with a code issued to C.
