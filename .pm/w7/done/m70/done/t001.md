## Objective

Make every OpenBao env-var and secret-file key include an immutable workspace (tenant) identifier, so two same-named Apps in different workspaces can never resolve to the same store path. Today `NewOpenBaoStore` fixes tenant to the constant `default` and `envPath`/`filesPath` key only on the public service name (codex-security #1, high).

## Context

- `lego/backend/internal/secrets/store.go:41-44` — `baoTenant = "default"` ("single tenant until w1/m2"); `NewOpenBaoStore` at ~:82 hard-codes `tenant=baoTenant`; `dataURL`/`metadataURL` prepend that single tenant.
- `lego/backend/internal/secrets/service.go:76-88` — `envPath(service)`/`filesPath(service)` build `services/<service>/{env,files}` with no tenant segment; `storeServiceName(a, fallback)` returns `a.Labels[core.LabelServiceName]` (public name) only.
- `AuthorizeApp` already verifies the caller owns the App; the gap is the storage key, not the authz gate.
- Tenant id is available on the App CR — `a.Labels[core.LabelTenant]` (verify the exact label key in `lego/types`/`core`).

## Steps

1. Resolve the canonical tenant identifier available on the App CR (label or spec) and confirm it is set on both CRD-projected and store-managed Apps.
2. Change the store key derivation so the tenant is part of the path: e.g. `envPath`/`filesPath` take a tenant and `dataURL` prepends `s.tenant` sourced per-request from the App (not the `default` constant). Keep `storeServiceName` for the public-name half.
3. Update every read/write verb (`ListEnvVars`, `SetEnvVars`, `GetSecretFile`, `PutSecretFile`, `DeleteSecretFile`, etc.) to pass the resolved tenant through.
4. Update the OpenBao KV policy / path prefix expectations to match the new `<tenant>/services/<name>/...` layout.
