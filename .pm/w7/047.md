# Start the bounded production build-cache trial (the guardrail is built; this is a flag flip and a date)

Why: the shipped registry build cache (ADR060 D3, correctness fixed in m87 + m88) has never been on in production, and the measured win is the largest customer-visible build-latency improvement on the board — Dockerfile 179s→38s class. `m89` closed held because starting the trial meant a named human watching a dashboard for 48–72 hours and running a rollback command at the right moment. That requirement is gone: the operator now enforces the stop rules itself.

**Worker:** worker7. **Estimate:** 30m to start, 30m to read the result. **Status:** in progress — repairing and deploying the trial alerts before enabling the already conditionally approved trial.

## What changed 2026-09-16

The trial breaker (`lego/operator/internal/controller/build_cache_trial.go`) withdraws the cache with no human in the loop, on three rules:

| Stop rule | Effect |
| --- | --- |
| `BEX_BUILD_CACHE_TRIAL_DEADLINE` (absolute RFC3339) | the 72h hard stop, immune to manager restarts |
| push p95 > 60s over ≥5 samples in 15m | cache withdrawn, `reason="push_latency"` |
| ≥3 push failures in 15m | cache withdrawn, `reason="push_errors"` |

Visible as `bex_build_cache_enabled` (1/0) and `bex_build_cache_withdrawals_total{reason}`, alerting through `BuildCacheTrialWithdrawn`, with the previously-missing `BuildPushTimeHigh` covering the latency rule for the fleet. A trip never re-arms — re-enabling is a deploy.

**The failure mode of inattention is now "no cache", not "unbounded cache".** If nobody watches, the deadline ends the trial and production returns to today's behavior on its own.

## To start

1. Add to the `controller-manager` JSON patch in `lego/operator/config/prod/kustomization.yaml`:

   - `BEX_BUILD_CACHE_TRIAL_DEADLINE=<now + 72h, RFC3339>`
2. Ship; wait for the manager rollout.
3. Trigger one build (a disposable QA App is enough) and confirm the Job carries the `cache-restore`/`cache-save` phases. Bounce Zot if the per-App cache ACL grants need a process restart.
4. Record the start here. No vigil required — check back at the end.

## To close

Read `bex_build_cache_enabled`, `bex_build_cache_withdrawals_total`, the push histogram and Zot's PVC over the window, then record a dated retain-or-rollback. Retain = drop the deadline (leaving the latency and failure rules armed). Rollback = remove both variables. The decision is deliberately not automated: withdrawing is safe, but *keeping* a feature is a judgement about measured benefit.

## The one gap worth naming

The **Zot PVC >70%-for-10m rule is not auto-actioned** — the operator does not observe the registry's filesystem, and reaching for Prometheus from a DB-free mechanism-layer manager would be a worse trade than the `ZotRegistryFillingUp` alert that already pages. The push-failure rule is a partial backstop (a filling registry fails pushes, and three inside the window trip the breaker), not a substitute.
