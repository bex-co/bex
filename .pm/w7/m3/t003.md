## Objective

Bound the expensive request shapes rate-limiting alone doesn't catch: a global request body-size cap, bounds on log and metrics query ranges (time window + line/point counts), and a per-caller cap on concurrent SSE live-tail connections.

## Context

- Body cap: `http.MaxBytesReader` at the same mux as t002's middleware (`lego/backend/internal/api`).
- Log queries + `/v1/logs/subscribe` SSE live in `lego/backend/internal/logs`; metrics ranges in `lego/backend/internal/metrics` (Prometheus-backed since w3/m4 — an unbounded range is a Prometheus-sized query).
- Refusals need clear, Render-consistent 4xx errors (400/413), not silent truncation — except where Render itself silently caps (check t001's capture; follow it).
- Existing dashboards (w5/m6 logs, w3/m3+ metrics) must stay within the caps — pick bounds above what the UI requests.

## Steps

1. Add the body cap at the router; audit multipart/webhook paths for a compatible limit.
2. Clamp/reject out-of-bounds log + metrics ranges; cap SSE connections per caller with a clean close on excess.
3. Click through the dashboard's Logs + Metrics tabs against the capped API to confirm no regression.

## Files

- `lego/backend/internal/api/` (body cap)
- `lego/backend/internal/logs/` (range bounds + SSE cap)
- `lego/backend/internal/metrics/` (range bounds)

## Acceptance criteria

- [ ] Oversized body → 413; out-of-range log/metrics query → 400 (or documented clamp); N+1th SSE stream refused cleanly
- [ ] Dashboard Logs + Metrics tabs work unchanged under the caps
- [ ] Caps enumerated in docs/bex-api.md §Rate limits
