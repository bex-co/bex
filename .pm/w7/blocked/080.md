# 080 — Create the live custom-domain Price, then release the held meter

Why: since w7/m429, custom domains above a workspace plan's included count (2 Hobby, 15 Pro, 25 Scale) are metered as `custom_domain_seconds` and shown in every usage estimate, but no card is charged for them until the live Stripe Price exists and bex-api stops holding the meter, so bex still gives away what Render charges $0.25 a domain-month for.

- **Today:** `lego/operator/config/api/deployment.yaml` sets `BEX_STRIPE_CUSTOM_DOMAIN_METER` to `"0"`, so `internal/billing/stripe.go` keeps `custom_domain_hours` off every Subscription and its rows pending in the outbox. `docs/runbooks/stripe-billing-setup.md` says the Price is "not created on any account yet". Production metered its first row on 2026-11-17 (w7/m429 t006).
- **The user's step (gate):** run `python3 scripts/stripe-billing-setup.py --live`. It adds the `custom_domain_hours` Price ($0.175 a domain-month, `unit_amount_decimal` 0.02397260274 cents per domain-hour) and reports every other dimension `exists`. The classifier denies the agent live Stripe writes (`w2/blocked/070`), so the agent cannot run it.
- **Then the worker:** confirm the live Price exists (a second `--live` run reports `custom_domain_hours` `exists`), set `BEX_STRIPE_CUSTOM_DOMAIN_METER` to `"1"` in `lego/operator/config/api/deployment.yaml`, update the runbook line and `lego/backend/AGENTS.md`'s row, and ship. Held rows inside the 34-day backfill window then ship to Stripe.
- **Acceptance:** after the pin carries the flag, a live Subscription of a workspace over its included count carries a `custom_domain_hours` item, and the outbox holds no `custom_domain_seconds` row older than its seal.
- **Note:** this brings the catalog to 20 items, Stripe's maximum per Subscription, so the next metered item needs a design change first ([ADR030 §16](../../../docs/ADR030-pricing.md)).
