## Objective

Deploy Dex the way t002 decided, so Kratos has an OIDC issuer for Bitbucket on production and on the local cluster.

## Context

- Platform components are Argo CD Applications under `deploy/gitops/base/` with values in `deploy/gitops/base/values/`. Charts are pinned with their digests in `deploy/helm-artifacts.lock`.
- Auth secrets are written out of band by `scripts/auth-secrets.sh` on every deploy (`deploy.yml`'s auth-secrets step), never committed.
- Traefik serves `auth.<base-domain>`; `deploy/gitops/base/network-policies.yaml` holds the auth namespace's policies (m465 added `allow-kratos-settings-guard-to-cp-api`).
- Workloads in `auth` are pinned to `bex.co/pool=platform`.

## Steps

1. Add a Dex Application (chart or vendored manifests, pinned), on the platform pool, with the storage t002 chose.
2. Configure one `bitbucketcloud` connector from `BEX_BITBUCKET_OIDC_CLIENT_ID`/`_SECRET`, and one static client for Kratos whose redirect URI is `https://auth.<base-domain>/self-service/methods/oidc/callback/bitbucket`. Put both secrets in an out-of-band Secret that `scripts/auth-secrets.sh` writes; the static client's secret is minted once and kept.
3. Route the public issuer path through Traefik, and add the NetworkPolicy that lets Kratos reach Dex's token and discovery endpoints in-cluster if it does not use the public URL.
4. Leave Dex off (no pod) while the Bitbucket pair is unset, so installations without Bitbucket run nothing new.
5. Bring it up on the local cluster (`bash scripts/mock-cluster.sh` or `scripts/dev-env.sh 7 up`) and check the discovery document answers at the issuer.
6. Add `.env.example` entries, and update `scripts/gitops-validate.sh` coverage and any workflow `paths` (`scripts/ci_test_inputs.py`) the new files need.

## Files

## Acceptance criteria

- [x] On the local cluster with a Bitbucket pair set, `<issuer>/.well-known/openid-configuration` answers with Dex's endpoints, and Kratos can reach its token endpoint.
- [x] With the pair unset, no Dex pod runs.
- [x] `scripts/gitops-validate.sh` passes.

## Out of scope

- The Kratos provider entry (t004).

## Result (2026-11-17)

Done. `deploy/gitops/charts/dex/` (vendored manifests: Deployment at `replicas: 0`, `Recreate`, platform pool, read-only and non-root, the image pinned by digest, config from the `dex` Secret's `config.yaml` only; Service; `/dex` Ingress on `auth.bex.co` with Kratos's certificate) and the `dex` Application (`deploy/gitops/base/dex.yaml`, wave 3, `ignoreDifferences` on `/spec/replicas` with `RespectIgnoreDifferences`), added to both expected-Application inventories. `allow-dex-public-edge` admits Traefik to port 5556 only. `scripts/auth-secrets.sh` writes `auth/dex` from `dex_bitbucket_config`, keeps Kratos's client secret, scales Dex to one (restarting it on a changed config) and waits before Kratos gets the button; without the pair it writes the fragment first, then scales Dex to zero and deletes the Secret. `scripts/gitops-validate.sh` pins the Deployment, hardening, Application, route-equals-the-fragment's-issuer and the NetworkPolicy (mutation-checked).

Local check, 2026-11-17, in `dev-7-auth` (the shared `auth` namespace syncs from main, so the manifests were applied to this workstream's own namespace, without the Ingress): `auth-secrets.sh`'s own Dex steps with a placeholder pair and the in-cluster issuer brought the pod up from ghcr; `/.well-known/openid-configuration` answered with Dex's endpoints and its token endpoint accepted Kratos's client (`invalid_grant` for a made-up code). A rerun with the same config left the pod alone; a changed config restarted it; with the pair unset the Deployment went to zero, no pod ran, and the Secret was gone. Removed from `dev-7-auth` afterwards.

Deviation: vendored manifests, not a mirrored Helm chart, so `deploy/helm-artifacts.lock` and `gitops.yml`'s paths (already `deploy/gitops/**`) needed no change.
