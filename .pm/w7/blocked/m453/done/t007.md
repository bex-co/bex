## Objective

Check that the window and its refusals are the same on REST, GraphQL, MCP and the dashboard: same start, same refusal codes and details, same error shape. Compare them with render.com's documented behavior, and file any drift as follow-up work.

## Context

- Render's contract: `GET /postgres/{postgresId}/recovery` → `recoveryStatus` (`AVAILABLE|BACKUP_NOT_READY|NOT_AVAILABLE`) + `startsAt`. `POST` takes `restoreName`/`restoreTime` (`lego/backend/internal/api/openapi/render-public-api-1.json`). Docs: render.com/docs/postgresql-backups (3 days on Hobby, 7 on Pro or higher, no backfill, nothing within ten minutes of now).
- bex's REST responses must still validate against the pinned OpenAPI response schema.

## Steps

1. Walk the three API surfaces and the panel on `dev-7`, on a Hobby and a Pro workspace.
2. Confirm REST adds no non-Render field. GraphQL/MCP may carry the native hint fields.
3. File every difference as an inbox note in w7. That includes `recoveryStatus` during the stalled-backup edge, and an error message wording Render documents differently.
