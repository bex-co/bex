## Objective

Check that a bearer API key behaves the same on REST, GraphQL and MCP (same identity, same 401 and 429 bodies, same revocation latency), that the dashboard's key dialog matches what the API returns, and that this matches Render's documented API-key behavior.

## Context

- REST, GraphQL and MCP in `lego/backend/` share one auth middleware; the dashboard consumes GraphQL (`dashboard/AGENTS.md`).
- Render reference: render.com/docs/api and api-docs.render.com/reference/authentication.

## Steps

1. Compare each surface's behavior and wording for this milestone's change against Render and against each other.
2. File any drift as follow-up work through `/pm`; record the outcome here.

## Files

- `lego/backend/internal/api/`, `lego/backend/internal/apikeys/`
- `dashboard/src/features/api-keys/`
- `docs/ADR012-auth.md`, `docs/ADR018-render-parity.md`

## Acceptance criteria

- [x] Every surface behaves and reads the same, and matches Render's documented behavior, or the drift is filed.

**Done 2026-11-17, checked live on production at pin `db48cde2bae9` as the QA user in `bex-canary`.** No drift to file.

- **Identity.** One key reads the same services on REST, GraphQL and MCP, and its writes are audited as `rest_api` with the key's id. `whoami` through the Render CLI names the key's creator, as Render's `GET /v1/users` names a key's owner.
- **Create on every surface.** A key created over REST, one over GraphQL `createApiKey` and one over MCP `create_api_key` each answered `key` equal to `bex_<id>_<secret>`. Each worked as a bearer on another surface: the GraphQL key on REST, the MCP key on GraphQL. No list carries the key or the secret: REST omits both, GraphQL returns empty strings, and MCP's text has neither. Revoke over REST, GraphQL `revokeApiKey` and MCP `revoke_api_key` each refused the key at the next request.
- **401.** One body (`{"error":"unauthorized","id":"unauthorized","message":"unauthorized"}`, identical bytes) and one `WWW-Authenticate` challenge on all three surfaces, for a wrong secret, an unknown id, a malformed key, random text and a revoked key. Render's clients only read the status: the CLI printed its own 401 message, and Terraform printed `unauthorized`.
- **429.** REST and MCP answer `{"id":"auth_overloaded",…}` and GraphQL its `errors` envelope with `AUTH_OVERLOADED`, all with `Retry-After`. Two shapes by design: ADR006's shed-class table gives each surface its own envelope, as for every other credential since w4/m100. Render documents no 429 for a bad key, so there is nothing to diverge from. The repeated-wrong-key 429 that did not fire is t006's, fixed and pending the pin.
- **Revocation.** The first request after `DELETE /v1/api-keys/{id}` was refused on every surface, which matches Render's "Revoking an API key takes effect immediately" (render.com/docs/api).
- **Dashboard.** The production bundle (`index-B6CrZzVe.js` at the pin) runs `createApiKey` selecting `key`, carries the "Example request" curl copy and the collapsed "OAuth client credentials" detail, and no locale says "not a bearer". A browser check of the dialog was not possible here: the Playwright MCP server did not connect. t003 checked the dialog's layout in a browser at 1280 and 375 px.
