## Objective

Let people sign up, sign in and link their account with Google, the way GitHub works today. Without it, nobody could meet the requirement.

## Context

- `scripts/auth-secrets.sh` `oidc_fragment` writes the Kratos `oidc.yaml` fragment. It emits the GitHub provider only when both `BEX_GITHUB_OIDC_*` are set, and otherwise `enabled: false`. Its login and registration hooks mirror the password flow, so keep them in lockstep.
- `.env.example:515-521` documents the GitHub pair. `scripts/gh-secrets.sh` pushes `.env` to GitHub secrets.
- `scripts/auth-oidc-e2e.sh` proves the OIDC mechanism against Dex, a stand-in for the real provider.
- The dashboard renders provider buttons from the flow's `oidc` nodes through Ory Elements (`dashboard/src/features/auth/`).
- The callback is `https://auth.<base-domain>/self-service/methods/oidc/callback/google`.

## Steps

1. Make `oidc_fragment` emit each provider on its own: `github` when its pair is set, and `google` (`provider: google`, scopes `openid email profile`) when `BEX_GOOGLE_OIDC_CLIENT_ID` and `BEX_GOOGLE_OIDC_CLIENT_SECRET` are set. Keep `enabled: false` when neither is set. Map `email`, and `name` when present.
2. Add both names to `.env.example`, with the callback URL and where to create the client. Check `DRY_RUN=1` output for each of the four combinations.
3. Extend `scripts/auth-oidc-e2e.sh`, or its test, so a two-provider fragment is proven. At minimum, the fragment must parse, list both ids and keep the hooks.
4. Check the dashboard's login, sign-up and account settings pages render a Google button with a proper label and icon in every locale. Add the icon if Ory Elements does not.
5. Update ADR012 § Social login and ADR027 §1.

## Files

## Acceptance criteria

- [x] With only the Google pair set, the fragment enables only `google`. With both pairs, it enables both. With neither, it is `enabled: false`.
- [x] On `dev-7`, a stand-in provider registered under id `google` signs a new person up and back in, and the dashboard shows its button.
- [x] `.env.example` mirrors the new names, with no values.

## Out of scope

- Creating production's Google OAuth client. That is done in bex's Google Cloud project; t008 checks it exists.
- GitLab and Bitbucket sign-in.

## Result (2026-11-17)

- `scripts/lib/kratos-oidc-fragment.sh` is the one generator of the Kratos `oidc.yaml` fragment: `github` and `google` (Kratos's built-in `provider: google`, scopes `openid email profile`) each on their own pair, `enabled: false` with neither, the login and registration hooks kept in lockstep with the password flow, Google's mapper marking a Google-verified email verified, and a `label` on each provider so the buttons read "Sign in with Google" and "Sign in with GitHub" (Kratos had labelled GitHub's with its bare id, `github`, on every page in every language). `scripts/auth-secrets.sh` calls it, and its DRY_RUN names the enabled providers for each combination.
- `.env.example` documents `BEX_GOOGLE_OIDC_CLIENT_ID` and `BEX_GOOGLE_OIDC_CLIENT_SECRET` with the callback URL and where to create the client; `deploy.yml` passes them to `auth-secrets.sh`; `scripts/auth-oidc-verify.sh` lists every provider and checks the guard.
- `scripts/kratos-oidc-fragment.test.sh` (42 checks, run by `scripts/gitops-validate.sh` in the gitops workflow) pins the four combinations, both ids, the hooks and the mappers.
- `scripts/auth-oidc-e2e.sh` now runs the generated fragment on Kratos v26.2.0 (production's version, was v1.3.1) with Dex registered as `google`: the login flow offers both buttons with those labels, a new person signs up with the stand-in Google (email verified, session method `oidc`/`google`) and a fresh browser signs back in as the same identity. Passed 2026-11-17.
- **Deviation:** the stand-in ran in that e2e harness, not on `dev-7`. dev-N's Kratos runs in the cluster while its bex-api runs on the host, and no stand-in provider is reachable from both the browser and the Kratos pod there; `scripts/dev-env/values/kratos.values.yaml` says so. The dashboard's provider button is t007's.
