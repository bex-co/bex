## Objective

Enforce the setting at the one point the 2FA requirement already uses, so every surface refuses the same way and none can drift.

## Context

- `core.Base.requireTwoFactor` (`lego/backend/internal/core/twofactor.go`) calls `core.TwoFactorGate.Check` after every positive OpenFGA decision. `WithTwoFactorExempt` marks the reads a blocked member still needs. `CheckTwoFactor` covers workspace configuration.
- `twofactor.Gate` (`internal/twofactor/gate.go`) resolves the principal: a session, a human token, or an API key's creator. It caches the setting and the facts for 60 s and fails closed.
- The SSH gateway asks bex-api over an HMAC verb (`internal/agentsession/two_factor.go`, `internal/sshgateway/twofactor.go`) for native SSH, the web shell, agent attach and sandbox exec and files. `cmd/ssh-gateway/twofactor_test.go` covers it.
- `internal/api/twofactor_surfaces_test.go` proves one refusal on every surface.

## Steps

1. Extend the gate so one `Check` answers both requirements. A workspace that requires neither still costs no lookup. A caller who fails both gets one refusal, in an order t001 fixes.
2. Refuse with 403 `WORKSPACE_GOOGLE_LOGIN_REQUIRED` and the workspace id when the caller's sign-in (from t003) is not Google. An API key or SSH key fails when it was not created in a Google session, unless t001's exemption applies.
3. Carry the answer through the SSH gateway verb, so every SSH path refuses a non-Google key in an enforcing workspace.
4. Count refusals in the existing metric under a new closed reason.
5. Extend `twofactor_surfaces_test.go` and the gateway tests to the new requirement.

## Files

- `lego/backend/internal/twofactor/gate.go`, `internal/core/twofactor.go`, `internal/agentsession/two_factor.go`, `internal/sshgateway/twofactor.go`, `cmd/api/main.go`, and the tests named above

## Acceptance criteria

- [x] In an enforcing workspace, a password-session member, a token from a password session, and an API key and SSH key created in one all get the coded 403 on REST, GraphQL, MCP and SSH. The same callers signed in with Google pass.
- [x] The exempt reads still answer a blocked member: the workspaces list, `currentUser` and leave.
- [x] A lookup that cannot answer fails closed. A workspace that requires neither setting makes no lookup.

## Out of scope

- The dashboard's blocked page. That is t007.

## Result (2026-11-17)

- `twofactor.Gate` answers both requirements in one `Check`: one cached settings row per workspace (a workspace that requires neither costs no lookup), the Google check first, then 2FA. Keys follow their creation stamp (unstamped keys are exempt), interactive sign-ins their own sign-in, tickets and background work the member's linked Google account; every Google pass also needs that account to match the member's email (`KratosIdentities.GoogleAccountMatches`, the stored ID token). Lookups fail closed. Refusals count under the closed reasons `not_google` and `key_not_google`.
- The SSH verb carries a native key's stamp (`signIn`, refused outside the vocabulary or on a ticket method) and answers the refusal's `code`; the gateway caches per workspace, subject, method and sign-in, answers the same coded 403, and native SSH prints a Google banner (`rejected_google_login`).
- Tests: `twofactor/gate_google_test.go` (the principal-by-sign-in matrix, order against 2FA, fail-closed, cache, metrics), `api/google_login_surfaces_test.go` (REST, GraphQL and MCP give the same coded 403 to a password session, a password token and a password key; Google ones pass; exempt reads work), the verb and gateway tests, and a native SSH test over a real SSH handshake.
- On dev-7 (2026-11-17), with the requirement on: a password session and an API key made in it got `403 WORKSPACE_GOOGLE_LOGIN_REQUIRED` with the workspace id on REST, GraphQL and MCP (the key with the "create a new key" message), while `/v1/owners`, `/v1/users`, GraphQL `workspaces` and MCP `list_workspaces` answered. SSH paths are covered by the gateway tests; dev-7 runs no gateway.
