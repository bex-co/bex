## Objective

Render says members "can't change their Render account's associated email address" and "can't disconnect" Google while they belong to an enforcing workspace. bex must refuse both where they actually happen: in Kratos's settings flow, not only in the dashboard.

## Context

- The account settings page posts Kratos's own settings flow (`dashboard/src/features/auth/pages/settings-page/index.tsx`, Ory Elements). A client can call `/self-service/settings` directly, so hiding a control is not enough.
- Kratos is configured in `deploy/gitops/base/values/kratos.values.yaml`, with `flows.settings` at about line 189. The local overlay is `deploy/gitops/overlays/local/values/kratos.values.yaml`, and dev-env has `scripts/dev-env/values/kratos.values.yaml`. Production runs Kratos v26.2.0.
- Kratos's `web_hook` action can interrupt a flow when its response is parsed (`response.parse: true`). Probe which settings methods (`profile`, `oidc`) it runs before the change is saved.

## Steps

1. Probe on `dev-7` whether a parsed `web_hook` on `settings.after.profile` and `settings.after.oidc` can refuse a change with a message the UI shows. If it cannot, record the alternative t001 chose (for example, a `before` hook plus a re-check, or reverting through the admin API) and its limits.
2. Add an internal, authenticated bex-api endpoint the hook calls. It answers "refuse" when the identity belongs to a workspace that requires Google login and the change alters the email trait or removes the `google` OIDC credential. Its message names the workspaces to leave first.
3. Wire the hook in all three Kratos values files, with the shared secret out of git as the OIDC secrets are.
4. Make the dashboard show the refusal clearly in every locale.

## Result (2026-11-17)

- Probed on Kratos v26.2.0 (2026-11-17): a `web_hook` with `response.parse: true` on `settings.after.profile` and `settings.after.oidc` runs before the change is saved, and a 4xx body in Kratos's message shape refuses it with the message on the field (`#/traits/email`) or the form (`#/`). The payload carries the identity as it would be saved (new traits) but no credentials; a link runs the hook on the provider's callback URL, an unlink on the settings POST. An unreachable hook fails the flow, so the guard fails closed.
- `internal/settingsguard` serves `POST /internal/kratos/settings-guard?method=profile|oidc` on :8091 behind `BEX_KRATOS_SETTINGS_GUARD_TOKEN`: it refuses an email change (message 4100001) and, while Google is linked, any unlink (4100002), for a member of an enforcing workspace, naming the workspaces to leave; a link, a non-email profile change and a member of no enforcing workspace pass. Kratos cannot say which provider an unlink removes, so a GitHub unlink is refused too: filed as w7/085.
- Wiring: the hooks ride the `oidc.yaml` fragment (`scripts/lib/kratos-oidc-fragment.sh`); `scripts/auth-secrets.sh` mints the bearer once into `bex-system/bex-kratos-settings-guard`, which bex-api's Deployment reads; NetworkPolicy `allow-kratos-settings-guard-to-cp-api` lets Kratos reach :8091. The three Kratos values files explain where the hooks live (Kratos arrays merge whole, so they cannot sit in git beside the bearer). dev-N runs no guard (its bex-api is on the host, out of the Kratos pod's reach).
- Tests: `settingsguard_test.go` (the decision table, pointers, bearer, store and Kratos outages fail closed, mounting), `workspaces` (`SettingsFacts`), `store` (`GoogleLoginWorkspaces`), and `scripts/auth-oidc-e2e.sh` against Kratos v26.2.0: an email change and an unlink are refused and nothing changes, a name change saves, and with the guard gone the change is refused.
- **Deviation:** the dev-7 acceptance ran in that e2e harness with a stub guard, not on dev-7 (see above); "after leaving the workspace, they can" is the guard's no-enforcing-workspace case. The dashboard's localized refusal is t007's.
