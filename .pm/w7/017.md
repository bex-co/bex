# ssh-gateway DB role — optional RLS defense-in-depth

**Type:** optional hardening / residual-risk record. **Not a milestone** (prod-mitigated, w7/m56 already shipped the least-privilege role).

codex-security scan #23 (low): `lego/backend/internal/sshgateway/dbrole.sql` grants table-wide `SELECT/INSERT/UPDATE` on `ssh_sessions` and `SELECT/INSERT/DELETE` on `shell_ticket_nonces`, with no RLS / ownership predicate — exactly as w7/m56 designed it (the gateway owns the whole table; row-scoping lives in application SQL `WHERE id=$1`/`WHERE nonce=$1`, enforced by `dbrole_integration_test.go`). The residual risk: a *stolen* gateway DB credential could rewrite any tenant's SSH session audit row or delete cross-replica ticket claims.

**Largely mitigated already:** the credential is scoped, rotated (w7/m56), and reachable only from the gateway pods; the application SQL bounds normal operation.

**Trigger to promote:** a compliance/audit requirement lands, or the threat model for a stolen gateway credential rises. Then add PostgreSQL RLS: `ALTER TABLE ssh_sessions ENABLE ROW LEVEL SECURITY` + a gateway-role policy scoping rows to gateway-originated sessions, and revoke unrestricted `UPDATE`/`DELETE`. Until then: recorded, not built.

Source: codex-security scan `codex-security-bex-azfRGv`, finding #23.
