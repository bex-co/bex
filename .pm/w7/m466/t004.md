## Objective

A person, an API key or an SSH key that does not meet the org's requirement is refused in every workspace of the org and on the org's own objects, through the hook that already enforces the workspace settings.

## Context

- `core.Base.requireTwoFactor` (`lego/backend/internal/core/twofactor.go`) runs after every positive OpenFGA decision. It names a workspace from a `workspace:` object or through `TwoFactorObjectResolver`, and an object it cannot place is not enforced. `org:<id>` objects are not placed today.
- `twofactor.Gate.Check` (`internal/twofactor/gate.go:198`) reads `LoginRequirements`, which returns the effective requirement since t002. So org workspaces are covered once the cache is right. What is new is the org objects and the refusal details.
- The SSH gateway asks bex-api over an HMAC verb that runs the same gate (`internal/agentsession/two_factor.go`, `internal/sshgateway/twofactor.go`) and caches the answer for about 150 s in a live session.
- The exempt verbs (`core.WithTwoFactorExempt`) are the workspace list, `currentUser` and leaving a workspace. t001 decides the org equivalents: listing orgs and `organization(id)`'s name, so a blocked person sees why.

## Steps

1. Teach the gate's resolver about `org:<id>`. An org object is enforced against the org's own requirement, with no workspace involved. Settle that in the gate, not in each org verb.
2. When the org's setting is what refused, carry `organizationId` (and the org name, if t001 chose it) in the coded 403's details, so the dashboard can name the org.
3. Mark the org reads a blocked person still needs as exempt, matching the workspace exemptions.
4. Check the API-key and SSH-key rules (the key's creator, the creator's sign-in method, the May 2024 exemption for Google) against an org requirement: they read the effective requirement, with no new branch.
