## Objective

Give the gate a fact to read. Every principal the 2FA gate already resolves must also say whether it was signed in with Google.

## Context

- `lego/backend/internal/core/identity.go`: `Identity` has `Method` (`session`, `oauth2`, gateway tickets) but no sign-in method.
- Kratos's `/sessions/whoami` returns `authentication_methods`. bex-api resolves dashboard sessions through it.
- Human OAuth tokens (`bex login`, MCP clients) come from Hydra, through bex's Kratos login-challenge bridge (ADR012 §7). Hydra's accept-login body takes `amr`, which then appears in the token's claims.
- An API key is a Hydra client with a created-by stamp (`twofactor.KeyCreators`). SSH keys are stored per user.

## Steps

1. Add the sign-in method to `core.Identity`, filled from the Kratos session on the session path. Make it a closed value such as `password` or `oidc:google`, never free text.
2. Pass it through the login-challenge bridge as Hydra `amr`, and read it back on the OAuth path.
3. When an API key is created, stamp whether its creator was signed in with Google, next to the created-by stamp. Do the same for SSH keys. Keys that existed before follow t001's exemption rule.
4. Keep background identities (agent sessions, automation) honest. They act as the member who started them, so record what that member's sign-in was when they started, or refuse them as t001 decides.

## Files

- `lego/backend/internal/core/identity.go`, the session and OAuth middleware, the login-challenge bridge, the API key and SSH key stores, and a migration if a key stamp needs a column

## Acceptance criteria

- [ ] Unit tests show a password session, a Google session, a token minted from each, and keys created from each carrying the right value.
- [ ] A key created before this change reads as t001 says.

## Out of scope

- Refusing anything. That is t005.
