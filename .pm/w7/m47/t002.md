## Objective

Add a thin, env-gated client wrapper around the official Metronome Go SDK that the emitter and provisioning code call. It owns bearer auth, batching (≤100 events per ingest call), and the retry/backoff policy — so the emitter loop (t005) stays about mapping rows to events, not HTTP mechanics.

## Context

- SDK: `github.com/Metronome-Industries/metronome-go/v3` (`client.V1.Usage.Ingest(...)`, Go 1.22+) — added to `lego/backend/go.mod`.
- New package, e.g. `lego/backend/internal/billing` (or `usage/metronome.go`) — backend only; the operator never imports it (ADR040 §Consequences).
- Env gate: `BEX_METRONOME_TOKEN` (unset ⇒ client is nil / disabled, feature off, byte-identical), `BEX_METRONOME_URL` (default `https://api.metronome.com`).
- Retry policy (ADR040 §4, Metronome guidance): exponential backoff on `429`, retry `5xx` until success, route non-429 `4xx` to a dead-letter log rather than blocking.

## Steps

1. Add the SDK dependency to `lego/backend/go.mod`; `go mod tidy`.
2. Create the client wrapper: constructor reads `BEX_METRONOME_TOKEN`/`BEX_METRONOME_URL`; returns nil (disabled) when the token is unset.
3. Implement `IngestBatch([]Event)` chunking into ≤100-event calls with the retry/backoff + DLQ-log policy.
4. Implement `EnsureCustomer(tenantID)` (used by t004) — thin pass-through to `POST /v1/customers`.
5. Unit-test the batching + retry classification (429/5xx retry, non-429 4xx → DLQ) with a stub transport.

## Acceptance criteria

- [ ] With `BEX_METRONOME_TOKEN` unset the constructor returns a disabled client and no network calls happen.
- [ ] Batches of >100 events split into ≤100-event ingest calls.
- [ ] 429 → backoff+retry; 5xx → retry; non-429 4xx → DLQ log, loop not blocked (unit-tested with a stub transport).

## Out of scope

- Customer-provisioning business logic + `billing_excluded` (t004).
