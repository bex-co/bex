## Objective

Offer "Sign in with Bitbucket" wherever the installation sets a Bitbucket OAuth consumer.

## Context

- t003 runs Dex with a static client for Kratos. Kratos's `generic` provider builds itself from `issuer_url` discovery and reads claims from the ID token by default.
- `scripts/lib/kratos-oidc-fragment.sh` and its test are shaped by t001.

## Steps

1. Add `kratos_oidc_bitbucket_provider`: `id: bitbucket`, `provider: generic`, `issuer_url` Dex's, `label: Bitbucket`, scopes `openid email profile`, the Dex static client's id and secret, and a mapper that marks the email verified only when Dex's ID token says so. Enable it on `BEX_BITBUCKET_OIDC_CLIENT_ID` + `BEX_BITBUCKET_OIDC_CLIENT_SECRET`.
2. Add a test-only issuer override, as for Google and GitLab, so the e2e can point `bitbucket` at a stand-in.
3. Add the pair to `deploy.yml`, `scripts/auth-secrets.sh`'s header and `DRY_RUN` line, and `scripts/auth-oidc-verify.sh`.
4. Extend `scripts/kratos-oidc-fragment.test.sh` for Bitbucket alone, all four providers, a half pair, the provider shape, label and mapper.
5. Update ADR012 §10 and ADR027.

## Files

- `scripts/lib/kratos-oidc-fragment.sh`, `scripts/kratos-oidc-fragment.test.sh`, `scripts/auth-secrets.sh`, `scripts/auth-oidc-verify.sh`, `.github/workflows/deploy.yml`, `docs/ADR012-auth.md`, `docs/ADR027-sso.md`

## Acceptance criteria

- [ ] With only the Bitbucket pair set, the fragment enables only `bitbucket`, a `generic` provider at Dex's issuer; with every pair, all four; with none, `enabled: false`.
- [ ] `bash scripts/kratos-oidc-fragment.test.sh` passes, and the dry run names `bitbucket` without printing a secret.

## Out of scope

- Creating production's Bitbucket OAuth consumer (t007).
