# 055 — The production liveness schedule runs 3–5.5 hours late, so `w3/m83`'s "within six hours" guarantee is not delivered

Why: `w3/m83` exists so that "a silent regression … surfaces as a GitHub issue **within six hours**". Measured over nine consecutive scheduled runs, the workflow fires **3h04m–5h27m** after its cron slot and the gap between runs reaches **7h28m** — so a regression can go unreported for longer than the guarantee promises, and nobody would notice because each individual run looks fine.

**Estimate:** 30m to decide · **Severity:** minor (detection latency, not a tenant-facing defect) · **Attribution:** CI/synthetics · **Worker:** worker7

Consecutive gaps, all eight between the nine runs above: **7h16m** · 6h47m · 5h10m · 4h29m · 7h28m · 6h48m · 5h16m · 4h25m.

**Corrected sweep 37.** This list previously began at 6h47m and silently omitted the first gap (2026-09-14T22:00:54 → 2026-09-15T05:17:16 = **7h16m**), which is itself over the six-hour guarantee. The omission understated the note's own case.

**The 12:37 (09-16) slot was delayed, not dropped.** At 14:03:51Z it had not fired; it landed at 17:15:38Z, 4h38m late. This matters because GitHub may either defer *or* skip a scheduled run, and the two have different fixes — a skipped slot means a missed detection window outright, a delayed one means a late detection. Every slot measured so far has eventually run, so the observed failure mode is **latency, not loss**. That keeps the eight rows above a drift measurement rather than a gap measurement.

Every row above is `event: schedule`; the one `workflow_dispatch` run in the window (2026-09-14T22:01:48Z) is excluded.

## Why it matters

- `w3/m83`'s goal sentence is the guarantee: _"surfaces as a GitHub issue **within six hours**"_, and its definition of done lists the tenant-view canary as `(6h)`.
- **Four of the eight** observed gaps exceed six hours (7h16m, 6h47m, 7h28m, 6h48m) — half of them, not the "two of five" this note originally claimed. A regression appearing just after a run therefore waits up to ~7.5 hours for its issue, not ≤6.
- The drift is invisible from any single run: each one passes or fails on its own merits, and only the sequence shows the guarantee is not being met. That is the same shape as the lineage this canary came from — a guard that exists and does not do what it claims.

## Cause is NOT established, deliberately

GitHub documents scheduled workflows as best-effort: they can be delayed under load and skipped entirely, and the delay is not part of any SLA. So the cause may be entirely outside bex. Two candidates, neither probed here:

1. **GitHub-side dispatch delay** — the documented best-effort behaviour, which would make this a wrong *claim* rather than a broken mechanism.
2. **Runner availability** — the fleet runs on a single self-hosted Mac ([`DO_NOT_DO.md` `#RUNNER-HOSTS`](../DO_NOT_DO.md)), so a queued or offline runner would also defer a dispatched run. Worth checking queue wait times on these runs before concluding.

Distinguishing them is the first step of any fix; do not assume either.

## Fix (decide, then do one)

- **Restate the guarantee honestly.** If GitHub-side delay is the cause and is accepted, change `w3/m83`'s six-hour wording (and ADR088 §6's coverage table, if it repeats it) to the cadence actually delivered — a guarantee nobody can keep is worse than a slower one that is true.
- **Or move the trigger to something bex controls.** A scheduler inside the cluster invoking the same scripts, or a `repository_dispatch` from one, removes the dependency on best-effort cron.
- Either way, add the cheap check that would have caught this: assert the gap between consecutive runs of each liveness workflow stays under its advertised window, and open an issue when it does not. The canaries watch production; nothing watches the canaries.

## Blast radius

- The same cron governs all three jobs in this workflow (`public-edge-liveness`, `request-logs-liveness`, `tenant-view-liveness`), so the latency applies to every surface they cover, not just the tenant view.
- Other scheduled probes on the same fleet plausibly drift too (the isolation matrix, the deploy canary's weekly run); this note measures only this workflow, and the others are **unverified**.

## Dedupe

Distinct from [`054`](054.md), which is about the tenant-view canary's stage 3 having no retry budget (false positives). This note is about detection latency (delayed reporting) — different mechanism, different fix, same workflow. `w3/m83` is **done** and its DoD does not mention schedule drift. No open board item mentions scheduled-workflow latency or the six-hour guarantee. Nothing in `.pm/DO_NOT_DO.md` applies; `#RUNNER-HOSTS` forbids splitting the runner fleet across hosts, which this note does not propose.

## Unverified

- Queue wait time per run was not read, so runner contention versus GitHub dispatch delay is undecided.
- Only this workflow was measured. Whether the other scheduled probes drift equally is not checked.
- Whether any regression was actually missed because of the drift is not established — this records that the guarantee is unmet, not that it has already cost something.
