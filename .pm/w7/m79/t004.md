## Objective

Check the new signals are consistent across REST, GraphQL, MCP, and the dashboard, and reasonable against render.com's deploy-failure vocabulary.

## Context

- Render exposes deploy status/reason and service events; bex mirrors that surface (`docs/ADR006-bex-api.md`, ledger in `docs/ADR018-render-parity.md`).
- New reason codes are a compatibility surface: an added value must not break a client that switches on the documented set. Check how the existing codes handle unknown values before adding to them.

## Steps

1. Compare the new reasons/events across REST, GraphQL, and MCP for the same failing service.
2. Confirm the dashboard presents them usefully — the reason should be readable without opening logs.
3. Compare with Render's vocabulary; where bex is more specific, record it as a deliberate extension rather than drift.
4. Update `docs/ADR018-render-parity.md` and `docs/ADR052-notifications.md`'s gap register where evidence changed.

## Files

- `lego/backend/internal/deploys/`, `lego/backend/internal/events/`

## Acceptance criteria

- [ ] Reasons and events agree across all three API surfaces.
- [ ] The dashboard presents the reason without requiring a log dive.
- [ ] Extensions beyond Render's vocabulary are recorded deliberately.

## Out of scope

- New notification channels.
