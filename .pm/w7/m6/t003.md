## Objective

Stop `AddDomain` from routing an unverified host. Today it patches the hostname straight into `App.spec.hosts[]`, which makes the operator build an Ingress rule and cert-manager request an ACME cert for a domain the tenant may not own. Change the flow so an added domain is recorded in the store as `pending` and is **not** written into `spec.hosts[]` until it reaches `verified` (t002); once verified, the host is promoted into `spec.hosts[]` (⇒ Ingress + cert). Removing a domain still cleans up the store row and any promoted host.

## Context

- `lego/backend/internal/apps/domains.go:207-235` — `AddDomain` currently appends to `spec.hosts[]` unconditionally (store write, then CR patch).
- The operator projects `spec.hosts[]` → Ingress + cert-manager Certificate (`effectiveHosts` in `app_controller.go`); nothing routes a host that is not in `spec.hosts[]`.
- The store row is the source of truth for pending/unverified domains; the CR only ever carries verified hosts.
- Coordinate with t002's verify transition — the natural place to promote the host into `spec.hosts[]` is the moment the store status flips to `verified`.

## Steps

1. `AddDomain`: write the store row as `pending` (with challenge token from t001) and return the pending view + challenge record; do **not** patch `spec.hosts[]`.
2. On successful verification (t002), promote the host into `App.spec.hosts[]` (the existing CR patch), so Ingress + cert issuance happen only for owned hosts.
3. `DeleteDomain`: remove the store row and, if the host was promoted, remove it from `spec.hosts[]` (keep idempotent).

## Files

- `lego/backend/internal/apps/domains.go` — `AddDomain`, `VerifyDomain` (promotion), `DeleteDomain`.

## Acceptance criteria

- [ ] Adding a domain does not put it in `spec.hosts[]` and does not trigger an Ingress rule or cert request; the store shows it `pending`.
- [ ] After a passing verify, the host appears in `spec.hosts[]` (Ingress + cert follow); before that, it does not.
- [ ] Deleting a pending or verified domain removes the store row and any promoted host; both paths are idempotent.
