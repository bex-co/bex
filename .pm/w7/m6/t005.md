## Objective

Expose the new verification lifecycle on every surface a caller uses to manage domains: the domain view carries its `status` (pending/verifying/verified) and the DNS **challenge record** (the `TXT _bex-challenge.<host>` the tenant must publish) alongside the existing `dnsRecord` (CNAME/ALIAS). The verify verb returns the transitioned state; add/verify collision + reserved-host rejections surface as validation errors, not 500s. The dashboard DNS-instructions panel shows the challenge record + a status chip + a re-check that reflects pending → verified.

## Context

- REST: `lego/backend/internal/apps/rest.go` (custom-domain routes) — `POST …/custom-domains`, `POST …/custom-domains/{name}/verify`.
- GraphQL: the `customDomains`/`verifyCustomDomain` schema + resolvers in `lego/backend/internal/` (mirror the DomainView fields).
- MCP: the custom-domain tools (`verify_custom_domain` etc.).
- Dashboard: the DNS-instructions panel (w5/m10) that already renders `dnsRecord` + a re-check button — add the challenge record + status chip.
- `docs/ADR018-render-parity.md:59` — the Verify/DNS row this makes truthful; `docs/render-artifacts/custom-domain-dns-instructions.md`.

## Steps

1. Add `status` + `challengeRecord` to the DomainView returned by REST, GraphQL, and MCP (same field names/semantics across all three).
2. Ensure verify returns the post-transition state and that collision/reserved rejections return the typed validation error on each adapter.
3. Dashboard: render the challenge record (copyable) + a status chip (pending/verifying/verified); wire the existing re-check to the verify verb and reflect the new state; call out that an unverified domain is not yet serving.
