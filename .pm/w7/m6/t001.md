## Objective

Give each custom domain a persisted verification lifecycle in the control-plane store: a status (`pending` → `verifying` → `verified`) and a per-domain challenge token the tenant publishes in DNS to prove ownership. This is the state the verify verb (t002) checks and the routing gate (t003) reads. Domains added before this migration default to `pending` (they will require a verify pass to become routed) unless a back-compat decision marks pre-existing rows `verified` — decide and document that in the migration.

## Context

- `lego/backend/internal/store/reconciler.go:267` and the `Domain` type — the existing store representation of a custom domain (today just the hostname, no status/token).
- `docs/ADR005-custom-domain.md:50` — the deferred `pending → verifying → active, owned-by-tenant` state machine this task begins.
- `docs/ADR003-control-plane.md` — the Postgres store is the source of truth; migrations live alongside the other store migrations (grep for the migration directory / numbering used by `owner_ids`/`git_connections`).
- Mint any new id via `lego/backend/internal/id` if a domain row gains its own id (ADR020); the challenge token is a random secret, not a resource id.

## Steps

1. Add `status` (enum: pending/verifying/verified) and `challenge_token` (random, minted once on add) columns to the domains store table; write the next-numbered migration. Decide + document the back-compat default for existing rows.
2. Extend the store's Domain read/write methods (and the fake store used in tests) to carry status + token.
3. Generate the token on domain add (crypto/rand); expose status + token on the store's Domain read path for t002/t005 to consume.
