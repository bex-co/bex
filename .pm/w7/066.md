# The local Go format gates use whichever gofmt is first on PATH, not the toolchain CI formats with

Why: on a machine whose PATH `gofmt` is older than the workspace's pinned Go, `scripts/ship-gates.sh` refuses a correctly formatted file, and "fixing" it locally turns `go lint` red on main, which has already happened once.

- Found by w7/m427, 2026-11-16, shipping a one-line addition to `lego/backend/internal/api/scope_matrix_ops.go`.
- CI's `go lint` takes Go from `lego/cli/go.mod` (1.27.3, `.github/workflows/go-lint.yml`). `scripts/ship-gates.sh` (`xargs gofmt -l`) and `make fmt-check` in `lego/operator/Makefile` call plain `gofmt`. On this machine that is Homebrew's Go 1.26.5.
- The two versions align the REST block of `scope_matrix_ops.go` differently. `7eddb23c4` formatted it with the local one and `go lint` went red on every push until `a0266464a` reformatted it with 1.27.3. Since then the local gate rejects any push that touches the file: `gofmt would change these files`.
- The same PATH mismatch breaks `make lint`'s dead-code step here: an analyzer built by Go 1.26.5 cannot load dependencies that need Go 1.27's standard library (`crypto/mldsa`).
- Repro: `gofmt -l lego/backend/internal/api/scope_matrix_ops.go` prints the file with Go 1.26.5 first on PATH; `"$(cd lego && go env GOROOT)/bin/gofmt" -l` on the same file prints nothing.
- What w7/m427 did: ran the unchanged gate with a PATH entry holding only the pinned toolchain's `gofmt`. That is a workaround each worker has to rediscover.
- Fix: have `ship-gates.sh` and `fmt-check` take `gofmt` from the workspace toolchain (`$(cd lego && go env GOROOT)/bin/gofmt`), and build the dead-code analyzer with it, so local gates and CI format with one version.
- Done when: with an older Go first on PATH, `bash scripts/ship-gates.sh origin/main` passes a push that touches `scope_matrix_ops.go` unchanged from CI's formatting, `make lint` passes, and a test or a comment in the gate pins where `gofmt` comes from.
