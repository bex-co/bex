# Deployment `CreateOrUpdate` PUTs every reconcile and self-retriggers

Found by the m81/t005 efficiency review (verified link-by-link, not observed end-to-end). Pre-existing, unrelated to m81.

**Chain:** the API server defaults embedded pod-template fields on the stored Deployment (container `terminationMessagePath`/`terminationMessagePolicy`, pod `dnsPolicy`/`restartPolicy`/`schedulerName`/`terminationGracePeriodSeconds: 30`, probe `successThreshold: 1`, readiness `periodSeconds`/`failureThreshold`). `applyDeploymentSpec` rebuilds `Containers` wholesale and forces `TerminationGracePeriodSeconds` to nil when unset, so the mutated object can never `DeepEqual` the fetched, defaulted one. `controllerutil.CreateOrUpdate` therefore returns `Updated` (a PUT) on **every** reconcile; the call site discards the result, and `Owns(&appsv1.Deployment{}, ResourceVersionChangedPredicate{})` feeds the operator's own PUT back into the queue — a silent self-sustaining reconcile loop per App. Pods never roll (template hash is computed post-defaulting), so it is pure API-server/operator churn.

w9/m57 fixed this exact mechanism for Services by matching the server default (`Protocol`). The Deployment path is the same bug, unspotted.

**Fix sketch:** make the mutate output match the server-defaulted object — set `TerminationMessagePath`/`TerminationMessagePolicy` on the container, `SuccessThreshold: 1` on all three probes, set readiness `PeriodSeconds: 10`/`FailureThreshold: 3` explicitly, preserve the fetched `TerminationGracePeriodSeconds` when `MaxShutdownDelaySeconds` is unset (or switch the seam to `CreateOrPatch`). Add an envtest asserting a second reconcile returns `OperationResultNone` / unchanged Deployment RV, mirroring `registry_pull_secret_envtest_test.go:193-198`.

Sizing: likely >1h (multiple defaulted fields + envtest + verifying no rollout churn on existing prod Deployments) — promote to a milestone per the sizing rule if the probe-list grows.
