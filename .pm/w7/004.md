# Production CNPG bootstrap cannot reach the Kubernetes API through the tenant egress deny

Production verification for `w9/m3` on 2026-07-15 proved the managed-Postgres rename path, then exposed an independent runtime failure: both the pre-existing legacy Database and a fresh `dpg-…` smoke Database stalled in CNPG init because the init pod could not reach `https://10.96.0.1:443` (`dial tcp ... i/o timeout`). The fresh resource reached `Setting up primary`; its init container then exhausted `wait-for-get-cluster` retries. The Database, CNPG Cluster, PVC, credential Secret, and Services were all created, and the official CLI rename preserved their identities before the readiness gate failed.

The live Cilium policy `default/deny-tenant-node-and-metadata-egress` selects every pod with `app.bex.co/workspace`. The operator deliberately propagates that label onto CNPG pods for same-workspace isolation, so the policy's `egressDeny` to `host` and `remote-node` also catches CNPG's Kubernetes-API traffic. All Cilium, kube-proxy, and hcloud-csi DaemonSet pods were Ready on the affected tenant node; this is policy behavior, not a missing node agent.

Fix this without reopening node-local or cloud-metadata access:

1. Reproduce with a managed Database on a tenant node and a direct API-service probe from its CNPG init/instance identity.
2. Split or narrow the Cilium selectors so tenant application workloads retain the node/metadata deny while platform-managed CNPG pods can reach only the Kubernetes API paths they require. Account for deny-overrides-allow semantics; a broad allow rule cannot override the current `remote-node` deny.
3. Add a policy-render/unit regression plus a live bootstrap test that requires a Database to reach `Ready` and execute `SELECT 1` from a fresh tenant node.
4. Repair or explicitly retire `default/biliblilitest` only with separate approval: it was already `Cluster is unrecoverable and needs manual intervention` before the rename rollout, has no ready instance or completed backup, and destructive recreation is outside this note.

Source: production `w9/m3` rollout verification, 2026-07-15. The rename feature and non-destructive legacy backfill shipped successfully; this note owns only the pre-existing CNPG bootstrap/networking defect.
