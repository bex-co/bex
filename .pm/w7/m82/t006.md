## Objective

Check that the new failure classification is consistent everywhere it is exposed, and compare against render.com's equivalent behavior rather than silently diverging.

## Context

- bex-api is meant to be Render-compatible ([docs/ADR006-bex-api.md](../../../docs/ADR006-bex-api.md)); the same fields, semantics and error shapes must hold across REST, GraphQL and MCP in `lego/backend/`, plus the `dashboard/` UI ([dashboard/CLAUDE.md](../../../dashboard/CLAUDE.md)).
- `m80`'s parity sweep is the cautionary precedent: it found that milestone's change was **inert** because all four surfaces coerced the value back to the old default. Check that the new classes actually reach each surface; do not just check that a field exists.
- `m79` shipped `failure_reason` to REST/GraphQL/MCP + dashboard + the failure email — the email is a fifth consumer and must not be forgotten.
- [docs/ADR018-render-parity.md](../../../docs/ADR018-render-parity.md) records the deploy/events rows; update the affected cells with evidence.

## Steps

1. Enumerate every surface that exposes a build/deploy failure reason, including the failure email.
2. Verify each renders the new classes with consistent vocabulary and error shape — end to end, not by field presence.
3. Compare against Render's documented build/deploy failure reporting; record any deliberate divergence.
4. Update the relevant `docs/ADR018-render-parity.md` rows; file any drift as follow-up work rather than fixing it inline.

## Files

- `lego/backend/internal/deploys/`, the REST/GraphQL/MCP adapters
- `dashboard/src/features/`
- `docs/ADR018-render-parity.md`

## Acceptance criteria

- [ ] All five consumers (REST, GraphQL, MCP, dashboard, failure email) show the same class with the same vocabulary.
- [ ] The change is proven non-inert on each surface.
- [ ] Divergence from Render is recorded, not silently introduced.
- [ ] The parity ledger rows are updated with evidence.

## Out of scope

- Fixing unrelated parity gaps the sweep surfaces — file them.
