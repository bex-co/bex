## Objective

Define the build SLO the classification makes possible, and alert on the signature that distinguishes a platform incident from a bad day of tenant commits.

## Context

- ADR060 D5: the SLO is on **infrastructure success rate** — the fraction of terminal builds that are not `infra_failed`, initial target **99.5%**. `user_failed` builds are excluded; a tenant's broken Dockerfile is not a platform failure.
- Track p50/p95 durations, never averages, and exclude failures from duration series.
- The flake-vs-user discriminator: infra causes manifest as **synchronized** failures across independent Apps and workspaces (clustered by node or registry); user errors are isolated and deterministic per commit. The alert is therefore on the `infra_failed` rate across ≥N distinct workspaces in a short window.
- Existing Prometheus rules live in the gitops path alongside the other platform alerts.

## Steps

1. Add the infra-success-rate recording rule and its 99.5% SLO threshold.
2. Add the correlated-failure alert (`infra_failed` spanning ≥N distinct workspaces within a window), with N and the window chosen and justified in a comment.
3. Add p50/p95 duration rules that exclude failed builds.
4. Verify the rules load and evaluate (rule-unit test or the equivalent check in the existing alerts verification path).

## Files

- `deploy/gitops/base/` Prometheus rules
- `scripts/alerts-verify.sh` if it is the existing verification path

## Acceptance criteria

- [ ] Infra-success rate is a recorded series with an explicit 99.5% target.
- [ ] A synthetic burst of `infra_failed` across several workspaces fires the alert; the same count within one workspace does not.
- [ ] Duration series exclude failures and report quantiles, not averages.
- [ ] The rules are proven to load, not assumed to.

## Out of scope

- Paging policy / routing — the alert is defined here, its destination is operational configuration.
