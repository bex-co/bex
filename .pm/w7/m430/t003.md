## Objective

bex can count, per database and per time bucket, the queries that completed after waiting at least one second on a lock, which is what Render's Lock-Delayed Queries graph shows.

## Context

- Render: "The number of recently completed database queries that were delayed by another operation holding a lock for one second or longer. Queries appear on this graph after they've completed. They do not appear while they're still waiting on a lock."
- PostgreSQL's `log_lock_waits` logs a line when a session has waited longer than `deadlock_timeout` (one second by default) and another when it acquires the lock. The second line is "completed after a wait of at least one second".
- The operator sets CNPG parameters in `lego/operator/internal/controller/database_controller.go` (`pg_stat_statements.track` at `:618`; legacy tenant-declared `spec.parameters` at `:954`). `log_lock_waits` takes effect on a reload, with no restart.
- Tenant Postgres logs reach Loki under `{namespace, database=<dpg-id>}` (w3/m28). Request metrics filtered by host or path are already served from Loki and answer `LOG_STORE_UNAVAILABLE` without it (w5/m58).

## Steps

1. Choose the source. Recommended: turn `log_lock_waits` on for every tenant database and count the "acquired … after" lines per bucket from the log store. The alternative, sampling `pg_locks` from the exporter, misses waits that start and end between scrapes and counts waiting queries, not completed ones.
2. Set the parameter in the operator without overriding a value a database's legacy `spec.parameters` declares, and confirm on a live cluster that existing databases adopt it by reload with no restart.
3. Check the extra log lines do not include statement text beyond what the database already logs, and that they count toward the tenant's log volume like any other line. Record both in ADR009.
4. Add the count as a metric source next to the Loki request-metrics source, clipped to the query window, answering the existing log-store-unavailable error when the store is not wired.
5. Tests: the operator projection (set, legacy value kept); the LogQL builder against the pinned Loki with real `log_lock_waits` lines, including a wait that is still in progress (not counted).
