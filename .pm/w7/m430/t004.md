## Objective

The datastore metrics verb serves network activity, transaction volume, lock-delayed queries, disk activity and disk operations, and REST, GraphQL and MCP return the same series for the same query.

## Context

- `lego/backend/internal/metrics/datastore.go` (metric names at `:61-77`, the per-kind refusals), `graphql.go` (`datastoreMetrics(query: {kind, resource, name})`), `rest.go`, `mcp.go` (`get_datastore_metrics`).
- Render's REST API has no path for these five, so REST and MCP names are bex extensions (the milestone README's decision state). `lego/backend/internal/api/render_metrics_contract_test.go` walks every Render `/metrics` path and must stay green.
- Counts are per bucket, as `http_requests` has been since w4/m108, so a series sums to the total in the window.
- The disk tab of a service already uses the datastore metrics panel (`dashboard/src/features/services/components/disk-section.tsx`), so a service with a disk is a resource kind here.
- `w7/m427`'s per-plan floor is applied in the core verbs and covers these metrics with no extra work.

## Steps

1. Add the metric names: network in and out, transactions, lock-delayed queries, disk read and written bytes, disk read and write operations. Bytes and counts are per-bucket sums.
2. Applicability: Postgres serves all; Key Value serves disk activity (and its existing metrics); a service with a disk serves disk activity and disk operations. Anything else is a coded 400 naming the metric and the kind, after the resource is authorized.
3. Expose them on GraphQL, on REST as bex-extension paths beside the existing datastore paths, and on MCP `get_datastore_metrics`. Empty windows answer an empty list, not `null` (w6/m110).
4. Tests: each metric on each kind; the refusals; REST, GraphQL and MCP parity for one populated and one empty query; cross-workspace isolation; the PromQL and LogQL run through `promtool` and the pinned Loki as the existing metrics tests do.

## Out of scope
