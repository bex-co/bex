## Objective

Decide how a registry cache export can happen without handing BuildKit a registry credential, and record the decision before any code is written. ADR060 D3 explicitly defers this "implementation detail to be settled in the milestone" — it is the milestone's real design risk.

## Context

- The current pipeline keeps credentials away from BuildKit **by construction**: BuildKit writes an OCI archive to an emptyDir (`lego/operator/internal/build/build.go:437`, `--output type=oci,dest=…/image.tar`) and a separate `skopeo` container does the authenticated push (`:543`). The code comment at `:485` states it outright: BuildKit "has no clone, platform push, or signing credential."
- A naive `--export-cache type=registry` requires BuildKit to authenticate to Zot, which **inverts that invariant** — and BuildKit is the one container running tenant-authored Dockerfile `RUN` steps, i.e. the least trusted process in the pipeline.
- ADR060 D3 names two candidate shapes: Skopeo copies the cache artifact too, or the cache export is granted through the same push-phase container.
- Related constraint: cache scope is **per-App repository** (`<app-repo>-cache`), reusing the per-App Zot ACL and credential machinery from `w7/m36`, so a workspace can never read another workspace's cache layers — ADR034 §6's isolation requirement with zero new authz surface.
- `--mount=type=cache` package-manager caches do **not** export to registry caches; that needs persistent local state and is explicitly deferred by ADR060, not half-solved here.

## Steps

1. Enumerate the candidate shapes, including a local cache export that a credentialed container copies afterwards.
2. Evaluate each against the invariant: does the tenant-code-executing container ever hold a credential that can write to the registry?
3. Pick one, state the residual risk, and note what would invalidate the choice.
4. Amend `docs/ADR060-build-worker-reliability-and-performance.md` D3 with the decision so t002–t004 implement one settled design.
