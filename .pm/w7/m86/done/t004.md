## Objective

Keep the two retention concerns from colliding: image retention must never delete a hot cache, and cache growth must never evict a deployable image generation.

## Context

- Today the operator writes a per-App Zot retention policy driven by `BEX_ZOT_RETENTION_COUNT` (`mostRecentlyPushedCount`, default 5).
- ADR060 D3: `-cache` repositories are **exempt** from that policy and get their own — most-recent-1 plus a time bound. Without the exemption, a busy App's cache pushes would consume the retention window and silently delete deployable image tags; without a cache-specific policy, cache repos grow unbounded.
- This is the failure mode most likely to be discovered in production rather than in review, because it only manifests after N builds.

## Steps

1. Exempt `-cache` repositories from the image retention policy.
2. Add the cache-specific policy (most-recent-1 plus a time bound), with the time bound chosen and justified.
3. Verify the generated Zot config expresses both policies correctly for an App that has both repositories.
4. Test the interaction after enough simulated pushes that a naive shared policy would have evicted a deployable tag.

## Files

- the operator's Zot retention/config management (`lego/operator/internal/controller/`)

## Acceptance criteria

- [ ] Cache pushes never reduce the retained count of deployable image tags.
- [ ] Cache repositories are bounded by their own policy.
- [ ] The interaction is proven by a test with enough pushes to trigger a naive-policy eviction.

## Out of scope

- Zot GC tuning — that is m82 t004 (ADR060 D4).

## Outcome

Corrected by measurement, see docs/ADR060 D3 amendment. The exemption D3 asked for is unnecessary (Zot applies retention per REPOSITORY, and the cache is a different repository from the image, so cache pushes cannot consume the image's window). The tightening policy D3 asked for is NOT EXPRESSIBLE: with a global `**` policy present, a more specific `**-cache` policy failed to tighten it in BOTH orderings — measured against a real Zot, which logged the surviving tags as `retained by mostRecentlyPushedCount:5`. Adding a provably inert policy was rejected. What bounds growth instead is structural and stronger: the cache occupies exactly one constant tag, rewritten per build, so a cache repo holds one manifest regardless of build count.
