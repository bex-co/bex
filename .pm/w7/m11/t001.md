## Objective

Choose the admission mechanism that will verify a tenant image's cosign signature before a pod using it is admitted, keyed to the same signing key material `w6/006` uses to sign.

## Context

- `w6/006` (`.pm/w6/done/006.md`) — opt-in cosign signing via `BEX_TENANT_SIGNING_KEY_SECRET` (a Secret with `cosign.key`+`cosign.password`, in the build namespace); the build Job cosign-signs each pushed tenant image.
- `docs/ADR028-security-review.md` — records verification as "out of scope" for the original security review.
- Candidate mechanisms: a Kubernetes `ValidatingAdmissionPolicy` with a CEL expression calling out to a verification helper (k8s 1.30+ built-in, no extra controller), a lightweight custom admission webhook doing the cosign verify call directly, or an existing policy engine if one is already in the cluster (check `deploy/gitops/` for Kyverno/OPA — likely none, given the codebase sweep found nothing).
- The **public** half of the signing key pair is what verification needs — decide where it's read from (the same Secret, a ConfigMap, or embedded at deploy time).

## Steps

1. Survey what's already in-cluster (any admission-control mechanism) to avoid introducing a new one unnecessarily.
2. Decide: `ValidatingAdmissionPolicy` (simplest, no new controller, but CEL's cosign-verify capability needs checking) vs. a small custom webhook (more control, more to operate).
3. Document the decision and how the public key material reaches the verifier.
