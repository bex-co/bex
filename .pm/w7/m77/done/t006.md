## Objective

Close the knowingly-accepted gap that Postgres and Key Value creation is uncapped per workspace. `w3/m34` deleted the app-code `BEX_MAX_POSTGRES`/`BEX_MAX_KEYVALUES` caps on the premise that the per-tenant `ResourceQuota` replaces them — a premise that only held for Apps, because the datastore CRs were never in the namespace being charged. t003 makes the premise true; this task verifies it actually bites.

## Context

- `.pm/w3/010.md` records the gap in full: the `count/databases.app.bex.co` and `count/keyvalues.app.bex.co` dimensions "are never actually charged" because the CRs are created in the shared apps namespace. The user was informed before m34 proceeded and explicitly accepted the interim, documented in `docs/ADR006-bex-api.md` § Per-workspace resource caps and `store.quotaForPlan`'s doc comment.
- `lego/backend/internal/store/namespaces.go` — `quotaForPlan` and the `ResourceQuota` the `NamespaceReconciler` applies per workspace.
- ADR043 D3's stated intent was to eliminate the dual-enforcement-path ambiguity, so the fix is to make the quota real — not to reintroduce app-code caps.

## Steps

1. Confirm the quota dimensions match the CR kinds now landing in the namespace.
2. Verify a create past the plan's cap is rejected by the quota, and that the rejection surfaces as a clean API error rather than an opaque 500 or a silently-stuck CR.
3. Confirm a quota set below current usage still never evicts existing datastores (ADR043's non-disruptive rollout property) — existing tenants must not be broken by the newly-charged dimensions.
4. Update the honest-gap notes in `docs/ADR006-bex-api.md` and `quotaForPlan`'s doc comment now that the gap is closed.

### Outcome (2026-08-08)

The dimensions were already in `quotaForPlan` — they simply counted nothing, because the objects they count were created somewhere else. t003 fixed that, so this task's work was to make the rejection *usable* and to pin that it stays real.

`DatabasesQuotaCountKey` / `KeyValuesQuotaCountKey` are now named constants beside `AppsQuotaCountKey`, and `CreatePostgres` / `CreateKeyValue` route the API server's Forbidden through the same `core.QuotaCapError` helper the service cap uses. Without that mapping the caller gets a raw 403 quoting a Kubernetes ResourceQuota — an object a Render-compatible client has no concept of. All three caps now return the identical Render-shaped 400 across REST/GraphQL/MCP.

Tests: `TestQuotaChargesEveryKindThatLandsInTheNamespace` asserts the invariant that made this gap possible in the first place — a cap is only a cap if the object it counts lands where the quota applies — across every plan. `TestFreePlanDatastoreCapsAreTighterThanPaid` stops the dimensions from being present but meaningless (equal caps everywhere would pass the first test while capping nothing, which is close to the state being fixed). `TestQuotaCapError_MapsDatastoreDimensions` covers both messages, and `..._DoesNotCrossDatastoreDimensions` guards the silent failure where a Postgres rejection mapped with the Key Value key falls through to a raw 403.

Non-disruption holds unchanged: a `ResourceQuota` set below current usage never evicts — Kubernetes only rejects new or increased requests — so newly-charged dimensions do not disturb workspaces already over the line (ADR043's converge-on-reconcile property, unchanged by this task).

`docs/ADR006-bex-api.md` § Per-workspace resource caps no longer carries a known-gap paragraph, and its cap table names the real mechanism for all three rows. `.pm/w3/010.md` is marked closed.
