## Objective

Write the tests that prove the bug before fixing it, so the fix is verified rather than assumed and the three legs can never silently regress. Each leg failed independently and only became visible after the previous one was fixed by hand — a single end-to-end test would have hidden two of them, so each gets its own assertion.

## Context

The three legs, all verified against the code on 2026-08-08:

1. **Secret resolution** — `lego/backend/internal/apps/deploy.go:1732` `resolveDatabaseRef` emits a bare `SecretKeyRef{Name: "<dpg-id>-app"}`. Kubernetes resolves `secretKeyRef` **same-namespace only**, and no mirroring code exists anywhere in `postgres/`, `keyvalue/`, or `apps/`. Symptom: pod `CreateContainerConfigError: secret "dpg-<id>-app" not found`.
2. **Network reachability** — `lego/backend/internal/store/namespaces.go:448` `allowNetworkPolicies` layers exactly four allows on the tenant default-deny: same-namespace, kube-system DNS, traefik ingress, and `allow-internet-egress` — which excepts `10/8`, `172.16/12`, `192.168/16` (line ~550). Datastore ClusterIPs are RFC1918, so they are denied. Symptom: `Redis::CannotConnectError: Connection timed out`.
3. **Hostname resolution** — `lego/backend/internal/apps/deploy.go:455` `dbPropertyKey` maps the `host` property onto CNPG's `host` key, which holds the bare service name `dpg-<id>-rw` — resolvable only in-namespace. Symptom: `PG::ConnectionBad: could not translate host name "dpg-<id>-rw"`.

## Steps

1. Add a test asserting that a `fromDatabase`/`fromService` env reference resolves to a Secret that exists **in the App's own namespace** — not merely that the `secretKeyRef` name is right.
2. Add a policy test asserting the tenant namespace's generated allow set actually permits egress from an App pod to its own workspace's Postgres `:5432` and Valkey `:6379` endpoints, evaluating the real `allowNetworkPolicies` output rather than restating it.
3. Add a test asserting the injected hostname is resolvable from the App's namespace (co-located short name, or an FQDN) — a value-shape assertion, not a string-equality snapshot.
4. Confirm all three fail against current `main`, and record the failure output in the task notes so the fix has a before/after.

## Files

- `lego/backend/internal/apps/` (link-resolution tests)
- `lego/backend/internal/store/namespaces_test.go` (reachability of the generated allow set)
- `lego/backend/internal/postgres/`, `lego/backend/internal/keyvalue/` (namespace placement)

## Acceptance criteria

- [x] Three independent tests, one per leg, each failing on current `main` for the documented reason.
- [x] No test asserts a hardcoded namespace literal that the fix would merely rename — each asserts the relationship (same namespace as the App / reachable / resolvable).
- [x] `cd lego/backend && go test ./...` shows exactly these three as the new failures.

### Outcome (2026-08-08)

`internal/apps/datastore_namespace_test.go` — three tests, all failing on `main` with the incident's exact symptoms (`secret "dpg-…-app" not found`, unresolvable `secretKeyRef`, bare-name host in the wrong namespace). `go test ./...` across the backend module is otherwise green, so these are precisely the new failures.

**Correction to this task's premise:** leg 2 (network reachability) has **no independent failing unit test**. It is a consequence of placement, not a separate code path — once the datastore is co-located, `allow-same-namespace` covers it, and before co-location the denial happens in the kernel, not in code this layer can exercise. Pretending otherwise would have meant a test that encodes the *old* topology and has to be rewritten by the fix, which is not a regression guard.

What leg 2 needs instead is a guard that co-location stays **sufficient** — the fix rests entirely on that, and a future narrowing of `allow-same-namespace` would silently reopen the bug. `internal/store/datastore_reachability_test.go` provides it: a small evaluator over the real generated policy set asserting a co-located datastore is reachable on 5432/6379/6380/6432, that an out-of-namespace one is not (so nobody "fixes" this by punching a cross-namespace hole, which would undo ADR043 D3), and that the RFC1918 exceptions the second assertion depends on still function. These pass today by design. Leg 2's runtime proof is t013.
