## Objective

Close ADR043 D8.2 — the structural blocker t001 found. The manager's Secret informer is scoped to exactly one namespace, and both datastore reconcilers touch Secrets through the cached client. Move them to the uncached client (the precedent the App path already set) so a `Database`/`KeyValue` in `<ws>` can be reconciled at all.

## Context

- `lego/operator/internal/controller/secret_cache.go` — `NamespacedSecretCacheOptions(namespace)` pins the Secret informer to one namespace, wired from `BEX_APPS_NAMESPACE` at `lego/operator/cmd/manager/main.go:193-196`.
- Its doc comment states the constraint that rules out the obvious fix: "The operator's ClusterRole deliberately cannot read Secrets… Without this per-kind scope, an `Owns(Secret)` watch asks for a cluster-wide list and **prevents the entire shared cache (including the App controller) from starting**." So widening the informer cluster-wide is not available — that would trade this bug for a total operator outage.
- Cached Secret touchpoints that break once the CR moves:
  - `keyvalue_controller.go:296` (connection Secret) and `:302` (auth Secret) — created in `kv.Namespace`
  - `keyvalue_controller.go:938` — `Owns(&corev1.Secret{})`, a cache-backed watch
  - `database_controller.go:640-663` — pooler Secret read + copy in `db.Namespace`
- The escape hatch already exists and is already used for exactly this reason: `app_controller.go:938` `buildPlaneClient()` returns the uncached client, described at `main.go:226` as "Secrets outside BEX_APPS_NAMESPACE are deliberately absent from the manager cache. Keep one direct client for build-plane resources and other explicitly RBAC-scoped namespaces."
- Authority is already granted: `deploy/gitops/base/tenant-namespace-clusterroles.yaml`'s `bex-tenant-operator` (secrets + serviceaccounts) is bound per-`<ws>` by the NamespaceReconciler.

## Steps

1. Route the Database and KeyValue reconcilers' Secret reads/writes through the uncached client. Consider whether `buildPlaneClient()` is the right name once it serves tenant namespaces too, or whether the seam should be renamed for what it is.
2. Replace the KeyValue `Owns(&corev1.Secret{})` watch. Decide deliberately: drop it (the reconciler creates these Secrets itself, so the watch mainly guards manual edits), or re-express it in a form that needs no cluster-wide Secret informer — and record which and why.
3. Verify no remaining cached Secret access can be reached with a CR outside `BEX_APPS_NAMESPACE`; a missed one fails only at runtime, in a tenant namespace, which is the hardest place to notice.
4. Confirm the manager still starts with its Secret cache scoped as before — the failure mode being avoided is the whole cache refusing to start.

### Outcome (2026-08-08)

Both reconcilers gained a `SecretClient` field (nil ⇒ falls back to the cached client, so existing tests and embedders are byte-identical) wired to the manager's existing `uncachedClient` in `cmd/manager/main.go`. Every datastore Secret read/write/delete now runs on it: the KeyValue connection + auth Secrets, and the Database pooler Secret's source read, projection, and delete. The informer scope itself is untouched, which was the point — widening it is what breaks the whole cache.

**`Owns(&corev1.Secret{})` removed from the KeyValue controller.** The deciding fact is that it is cache-backed, so it could never fire for a KeyValue in a tenant namespace: keeping it would make drift healing work in one namespace and silently not in the others, which is a worse contract than not having it. Nothing load-bearing is lost — the auth Secret is `Immutable: true` (the API server rejects data edits outright), the connection Secret is derived and re-converged every pass, and a Ready KeyValue already requeues every `childHealthRequeue` (30s). So healing goes from near-instant-in-one-namespace to ~30s everywhere. The reasoning is in the code at the removal site.

`internal/controller/datastore_secret_plane_test.go` pins it by handing the reconciler two **distinct** clients and asserting which one the Secrets landed in — the production regression is silent (a cached read just does not see the namespace), so an assertion that a Secret merely exists would not catch it. Verified anti-tautologically: reverting one call site to `r.Client` turns the test red with both the "not written through SecretClient" and "reached the CACHED client" messages, and restoring it turns it green.

`secret_cache.go`'s doc comment now records the datastore exemption, so the next reader meets the constraint before the workaround.
