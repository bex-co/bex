## Objective

Close ADR043 D8.3. The tenant namespace's default-deny allow set was written for application pods; datastore workloads need paths none of the four existing allows grant. Omitting any one reproduces w7/m33's failure mode — CNPG stalling in bootstrap because a policy blocked its control traffic — this time inside every tenant namespace.

## Context

- `lego/backend/internal/store/namespaces.go:448` `allowNetworkPolicies` (hosting regime) installs exactly four: `allow-same-namespace`, `allow-dns-egress` (kube-system), `allow-traefik-ingress` (traefik), `allow-internet-egress` (0.0.0.0/0 **minus** `10/8`, `172.16/12`, `192.168/16`, `100.64/10`, `169.254/16`).
- Every in-cluster peer a datastore needs is RFC1918, so `allow-internet-egress` grants none of them, and `allow-same-namespace` covers only pods already in `<ws>`.
- Required additions (ADR043 D8.3): egress to the kube-apiserver (CNPG instance manager); ingress from `cnpg-system` (CNPG operator), from the pg-/kv-sni-proxies (public `<name>.<BEX_DB_DOMAIN>` / `<BEX_KV_DOMAIN>`), from monitoring (Prometheus scrape), and from `bex-system` (bex-api's direct query path, `postgres/query.go:157`).
- Prior art for the failure being avoided: `w7/m33` fixed CNPG bootstrap stalling against the ADR022 egress deny by splitting selectors. Same class, new location — the lesson is that CNPG's control traffic is easy to forget because it is not the traffic anyone is thinking about.
- Counter-constraint: ADR043 D6 confines what the namespace reconciler may create in a tenant namespace via admission. New allows must be permitted by that gate, or they will be rejected at apply time.
- Platform side: `deploy/gitops/base/network-policies.yaml` gives each platform namespace default-deny **ingress**. The SNI proxies now dial *into* tenant namespaces, so check whether their namespace also carries egress restrictions that need the matching allow.

## Steps

1. Add the D8.3 allows to the hosting regime only — the sandbox regime deliberately gets no same-namespace or label-only allow and must stay untouched.
2. Keep each allow as narrow as its purpose: a peer plus the ports that peer actually needs, not a namespace-wide opening.
3. Verify against D6's admission confinement that each new policy is accepted.
4. Verify the reverse direction for the SNI proxies and for Prometheus.
5. Confirm the tenant-to-tenant and hosting-to-sandbox denials are unchanged — this task widens what a datastore can talk to, and must not widen what a tenant workload can reach.

### Outcome (2026-08-08)

Two mechanisms, deliberately split by who is allowed to grant what:

- **`allow-datastore-control-ingress`** — a fifth hosting-regime k8s NetworkPolicy admitting `cnpg-system`, `bex-system`, and `monitoring`. Peer-scoped, not port-scoped: those are platform namespaces already under their own default-deny ingress, so a port list adds little security while a wrong one fails silently as a stalled bootstrap or an empty metrics series. Port-narrowing is a reasonable follow-up once live traffic confirms the exact set.
- **`allow-cnpg-apiserver-egress`** — a `CiliumClusterwideNetworkPolicy` in `deploy/gitops/base/datastore-control-egress.yaml`. The apiserver has no portable k8s NetworkPolicy representation, and D6's admission confines bex-api's CNP authority to `<ws>-sandbox`, so this cannot be (and should not be) bex-api's to create. Same GitOps split the sandbox regime already uses.

**The `obsolete_platform_allows` guard in `gitops-validate.sh` caught a footgun before it shipped.** It records that an earlier `allow-cnpg-kube-apiserver` was deleted once `deny-metadata-egress-all-pods` stopped enabling default-deny — which is the tell that in Cilium *any* policy with a positive egress rule turns on default-deny egress for every endpoint it selects. This policy selects CNPG pods **cluster-wide**, including un-migrated clusters in the shared namespace where there is no default-deny. Shipped without `enableDefaultDeny.egress: false`, it would have restricted those clusters to the single apiserver rule — cutting DNS and S3 backups, and breaking exactly the tenants the cutover had not reached yet. The flag is set, a new `gitops-validate.sh` guard pins the whole shape, and both the guard and the policy tests were verified anti-tautologically (removing the flag fails the guard; removing the allow fails the D8.3 test with the w7/m33 message).

Tests: `TestHostingAdmitsDatastoreControlPlanes` (each peer named with why), `TestHostingDoesNotAdmitArbitraryNamespaces` (another tenant, sandbox, `default`, `bex-build`, `kube-system` all still denied — the counterweight that proves the widening was bounded), `TestSandboxRegimeGainsNoDatastoreAllow`, plus the existing allow-set enumeration extended in both its positive and its sandbox-negative list.
