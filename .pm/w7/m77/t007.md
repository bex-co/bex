## Objective

Execute t001's cutover plan against hetzner-prod so the real tenants stop depending on hand-built reconcile artifacts, and prove the platform path now does what a human did by hand on 2026-08-08.

## Context

- Affected production tenants (workspace `tea-d98210cbbpdc73dcrkvg`): `tianpan-forum` and `blockeden-forum` (currently running **only** because of manual artifacts), plus `beancount-forum` (`srv-d9nqg9dcavls73fp8m2g`) and `beancount-cms-v2`, whose datastores also live in `default`.
- Manual artifacts to retire, per tenant, from the incident report §7:
  1. Hand-copied `dpg-<id>-app` + `red-<id>` Secrets in the tenant namespace, with a hand-patched `host` key set to the FQDN.
  2. A hand-written `CiliumNetworkPolicy` allowing the forum pods egress to `app.bex.co/keyvalue=<red-id>:6379` and `cnpg.io/cluster=<dpg-id>:5432`.
  3. A hand-made traefik `Ingress` for `<svc>.onbex.co` with cert-manager `letsencrypt-prod` — **KEEP, see the correction below**.
- These are live forums serving real data at `https://tianpan-forum.onbex.co/forum/` and `https://blockeden-forum.onbex.co/forum/` — downtime is a real user impact, and the Postgres holds real content.
- Do not commit or print `.env` / `*.kubeconfig` contents (repo rule).

## Steps

1. Take a verified backup of each affected tenant's Postgres before touching anything, and confirm it is restorable — not merely that a backup object exists.
2. Execute [`docs/runbooks/datastore-namespace-cutover.md`](../../../docs/runbooks/datastore-namespace-cutover.md) one tenant at a time, starting with a tenant that is not a live forum if one exists. Rehearse the whole procedure on a scratch workspace first — the runbook requires it.
3. After each tenant: confirm the pod mounts platform-created Secrets (not the hand-copied ones), reaches Postgres and Valkey, and serves its site.
4. Remove the manual artifacts for that tenant and confirm nothing regresses — the removal is the proof the platform path works.
5. Record the executed cutover, per-tenant results, and any deviation from the plan.

## Live-state re-derivation (2026-08-19, before touching anything)

The brief above is 11 days old and **the affected set has changed shape**. Verified against
hetzner-prod with the admin kubeconfig; every claim below is a `kubectl` read, not an
inference from the board.

**`tianpan-forum` and `blockeden-forum` no longer exist as Apps.** No App by either name
exists in any namespace. What survives them in `tea-d98210cbbpdc73dcrkvg` is debris:
Ingresses, TLS Secrets, `reg-pull-*` Secrets, and two hand-written CiliumNetworkPolicies.

**They became sites inside one Discourse multisite instance.** All three orphan-looking
Ingresses — `…-tianpan-forum`, `…-blockeden-forum`, `…-beancount-forum-ms` — route to the
same backend, `tea-d98210cbbpdc73dcrkvg-beancount-forum:3000`. So four public hostnames
(`tianpan-forum.onbex.co`, `blockeden-forum.onbex.co`, `beancount-forum.onbex.co`,
`beancount.io`) are served by **one** App.

**That one App consumes all four datastores**, which are all still in `default`:

| datastore | how the App reaches it | evidence |
| --- | --- | --- |
| `dpg-d9nqg95cavls73fp8m20` | declared: `DISCOURSE_DB_*` env → `dpg-…-app` Secret | App CR `spec.env` |

**What this changes about the plan.** The brief's "one tenant at a time, starting with a

### Addendum — all three forums ARE serving; they live at `/forum`, on one multisite App

**Correction (2026-08-19).** An earlier revision of this section claimed two forums were
offline. That was wrong, and the mistake is worth recording because it nearly redirected the
milestone: the check was `GET /` against a Discourse running with
`DISCOURSE_RELATIVE_URL_ROOT=/forum`, where a 404 at `/` is correct behaviour. The brief at
the top of this file already gave the real path (`…onbex.co/forum/`).

Verified through the public edge:

| URL | HTTP | title |
| --- | --- | --- |
| `https://beancount.io/forum/` | 200 | Beancount and Plain-Text Accounting Forum |
| `https://tianpan-forum.onbex.co/forum/` | 200 | 10x.pub |
| `https://blockeden-forum.onbex.co/forum/` | 200 | Web3 Developer Forum |
| `https://tianpan.co/forum/` | 200 | 10x.pub |
| `https://blockeden.xyz/forum/` | 200 | Web3 Developer Forum |

**The real topology.** One App (`…-beancount-forum`) runs Discourse in **multisite** mode
serving three live sites, each with its own database and its own hostnames:

| site | database | hostnames |
| --- | --- | --- |
| beancount (primary, `DISCOURSE_HOSTNAME`) | `dpg-d9nqg95cavls73fp8m20` | `beancount.io` |
| tianpan | `dpg-d9rrkoc4h4mc73edurp0` | `tianpan-forum.onbex.co`, `tianpan.co` |
| blockeden | `dpg-d9rs3ee0ccis738kc7c0` | `blockeden-forum.onbex.co`, `blockeden.xyz` |

All three databases are **live and in use**, sizes and post counts as measured above. One
shared Valkey (`red-d9p49kdrtmes73c34ovg`) backs all sites, which is standard Discourse
multisite and explains why the other two `red-…` connection Secrets were minted but never
provisioned.

**The cutover constraint this exposes — and it is the important finding.**
`config/multisite.yml` is **baked into the tenant's image** (present in the pod, mtime
predating the pod by 10 days, no volume mounts on the Deployment), and it hardcodes the two
secondary databases by FQDN:

```
host: dpg-d9rrkoc4h4mc73edurp0-rw.default.svc.cluster.local
host: dpg-d9rs3ee0ccis738kc7c0-rw.default.svc.cluster.local
```

The `beancount-multisite-yml` Secret holds the same content but is **not mounted**, so it is
inert. Consequence: the runbook's Step 7 claim — "because the CR name is unchanged, the
App's env references need no edit" — holds only for the primary database, which is wired
through platform-injected `secretKeyRef` env. The two secondary databases are wired through
a file **inside the tenant's own image**, which the platform cannot rewrite. Moving them to
`<ws>` changes the namespace segment of both FQDNs and breaks two live sites until that file
is updated and the image redeployed.

So the cutover for this tenant needs a step the runbook does not have: update `multisite.yml`
(to the new namespace, or to the short `dpg-…-rw` name that resolves in-namespace once
co-located) and redeploy, inside the same window as the database move. Mounting the existing
Secret over the baked-in file would make this platform-manageable in future and is worth
considering as part of the same change.

### Rehearsal result — it found a production defect on the first try

Ran 2026-08-19, in the tenant's own namespace with a **scratch** Database
(`dpg-m77rehearsal`, same `basic-256mb` plan as the live one, so D8.4 was genuinely
exercised). Highest fidelity available — the exact target environment — at the lowest blast
radius: a new CR, no tenant data touched, deleted afterwards. Quota had ample headroom
(`count/databases 0/25`; it reads 0 precisely because the real ones are still in `default`,
which is the `w3/010` gap t006 closes).

**It never provisioned.** Phase `Failed`, zero CNPG pods, immediately:

```
Ready=False reason=BackupStoreUnavailable
  reading ObjectStore default/bex-tenant-postgres: objectstores.barmancloud.cnpg.io
  "bex-tenant-postgres" is forbidden: User "system:serviceaccount:bex-system:bex-controller-manager"
  cannot get resource "objectstores" in API group "barmancloud.cnpg.io" in the namespace "default"
```

Confirmed with `kubectl auth can-i`: the operator's ServiceAccount has **no verb on
`objectstores` in any namespace**. Root cause: `reconcileTenantBackupStore` (the ADR043 D8.4
projection, t004) reads the GitOps ObjectStore and `CreateOrUpdate`s a copy per tenant
namespace, but no `+kubebuilder:rbac` marker for `barmancloud.cnpg.io` was ever written, so
the generated ClusterRole omitted the resource entirely.

**This is bigger than the cutover.** It is not a migration problem — it means **every
backup-enabled Database created in a tenant namespace fails today**, which is m77's whole
premise. Step 5 of the runbook would have hit it with a tenant mid-cutover and the old
instance already quiesced.

**Fixed in the repo** (needs a ship + deploy before the cutover can proceed):

- `database_controller.go` gains the marker, least-privilege per `w7/m7`:
  `get;create;update;patch` — no `list`/`watch` (unstructured reads bypass the informer
  cache and go direct), no `delete` (the projected store is deliberately unowned and shared
  by every Database in the namespace).
- `config/rbac/role.yaml` regenerated.
- **Durable half:** `rbac_gvk_coverage_test.go`. The existing `rbac_test.go` only guards
  against OVER-granting; nothing checked the other direction, which is why this was
  invisible. The new guard scans the package's own sources for
  `…GVK = schema.GroupVersionKind{…}` declarations and asserts the ClusterRole grants each
  one — so a kind added later is covered without anyone remembering a list. Out-of-tree
  kinds reached through the dynamic client are exactly where the compiler cannot help, and
  envtest runs without RBAC, so no other test in the repo can catch this class. Proven red
  against the pre-fix `role.yaml` and green with it; carries an anti-tautology assertion so
  an empty or drifted scan fails loudly.

**Rehearsal verdict: not yet passed.** It reproduced a blocker instead, which is the gate
working as designed. Re-run it after the fix deploys, and only then schedule the cutover.

### Cutover sequence, revised (2026-08-19)

Two blockers were found and fixed in working trees; neither is committed.

**Blocker 1 — the operator cannot provision a datastore in a tenant namespace.** RBAC gap,
fixed in `bex7` (marker + regenerated ClusterRole + `rbac_gvk_coverage_test.go`). Verified
safe to ship: a server dry-run against production's own 1.34.9 API server returns every
default identical to the constants the projection now writes, and the live forum Deployment
and Valkey StatefulSet already store exactly those values — so no tenant pod rolls. The
grant itself is inert until a datastore actually lives in a tenant namespace
(`BEX_APPS_NAMESPACE=default`, so `reconcileTenantBackupStore` early-returns today).

**Blocker 2 — the multisite config is a hand-placed file inside the running container.**
`config/multisite.yml` has never been in the image (no Dockerfile version copies it) and is
not mounted; it was copied into the live pod by hand, with the checked-in template's
`__…_DB_PASSWORD__` placeholders replaced by real values. So **any** pod restart — redeploy,
node drain, eviction, OOM — drops the two non-default forums to single-site and their four
hostnames stop resolving. This is a standing production fragility that predates the
milestone and is not in the Step 8 inventory.

Fixed in `discourse_docker` (branch `bex-main`, uncommitted): `start.rb` now materializes
`config/multisite.yml` from a mounted secret before `db:migrate`, substituting any
`__NAME__` placeholder from the environment and **aborting** rather than writing a
half-substituted config. Absent source ⇒ single-site, the correct default. Exercised
against the real config and both failure paths.

**Do not push `discourse_docker` before the App is wired.** The forum App has
`autoDeploy=true` on `main`, so a push rebuilds and restarts the pod — which discards the
hand-placed file and takes the two forums down, while delivering nothing (the Dockerfile
still does not ship the file, and the namespace edit points where the databases are not
yet).

Order that keeps every site up:

1. Ship `bex7`. No tenant pod rolls; unblocks datastore creation in `<ws>`.
2. Re-run the rehearsal; a scratch Database in `<ws>` must reach Ready.
3. Add `filesFromSecrets: [beancount-multisite-yml]` to the forum App. **This rolls the
   pod** (it adds a volume+mount), so it needs the window — and it must land together with
   the `start.rb` push, so the restart it causes is the one that starts reading the mounted
   file instead of losing the hand-placed one.
4. Then the datastore move itself (Steps 1–7), with the namespace edit to `multisite.yml`
   already in the Secret.
5. Steps 8–10 as written, minus the Ingresses (keep, per the 2026-08-09 correction).

Steps 3 and 4 are one window. After it, the config survives restarts and the tenant
namespace holds its own datastores.
