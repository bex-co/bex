# 006 — A Blueprint's estimate and paid-intent check price an existing resource whose file omits `plan` at the create default, not at the plan the sync keeps

Why: w33/m436 t005 found that the review step can show a price the apply never charges. A sync or adopt keeps an existing resource's plan when `plan` is omitted, but the estimate and the payment-method check read the parse's create default. That has been true for services since w1/122 and for databases, and it is now true for Key Value.

Evidence (read against the tree carrying w33/m436, 2026-11-16):

- `ValidateBlueprint` returns `EstimatedPricing: blueprintEstimatedPricing(st)` (`lego/backend/internal/apps/blueprint.go:863`). `blueprintEstimatedPricing` (`blueprint_pricing.go:39`) prices every parsed entry and never reads the workspace snapshot. A plan-less entry is therefore priced at `starter` (service, Key Value) or `basic-256mb` (database) even when the action plan for it is `noop` against an existing free resource. The plan's actions are correct: `TestASyncThatOmitsPlanLeavesAFreeKeyValueAlone` shows `noop` and no write.
- `stackHasPaidPlan` (`deploy.go:1664`) reads the same parsed plans, so `requireStackBilling` treats such a sync as paid intent (`blueprint.go:1385`, `:1660`, `deploy.go:971`). Production runs `BEX_REQUIRE_PAYMENT_METHOD=all` (ADR075 D7), so every apply needs a card there anyway. Under `1`, a cardless workspace's sync of a file that only keeps free resources is refused with `PAYMENT_REQUIRED`.
- Render documents the create default and "Render retains the current compute plan for an existing service" (render.com/docs/blueprint-spec § `plan`, read 2026-11-16). It does not say what its Estimated pricing panel shows for a resource it already has.

Fix: price and gate each resource at the plan the apply would leave it on. That is the parsed plan for a create or for a declared `plan`, and the live plan for an existing resource whose entry omits `plan`. The resolver already has both (`blueprint_state_plan.go`). Keep the agreement test (`blueprint_pricing_agreement_test.go`) true for both sides.

Done when: validating a file whose only entry is an existing free web service, Postgres or Key Value with `plan` omitted shows no paid line, and under `BEX_REQUIRE_PAYMENT_METHOD=1` its sync does not ask for a payment method. A create in the same file is still priced and gated at the default. There is a test per kind that fails on today's code.
