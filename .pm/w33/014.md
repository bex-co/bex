# w33/014 — Prefer the 16 GB build node (`bex-tenant-lg`) for build pods and bound memory-pressure eviction retries

Why: `bex-tenant-burst` (`cx33`, ~6.77 GiB usable after DaemonSets) cannot hold the full `8G` (7.45 GiB) build container limit without node memory-pressure eviction, and `DisruptionTarget: Ignore` turns repeated memory-pressure evictions into an unbounded retry loop; preferring `bex-tenant-lg` (`cx43`, 16 GB) and bounding memory-pressure eviction retries fixes the loop in pure operator code with zero manual ops or node-pool changes.

## Context

- `infra/clusterapi/overlays/hetzner-caph/cluster.yaml:840-960`: both `bex-tenant-lg` (1× `cx43`, 16 GB, ~15.1 GiB allocatable, label `nodepool: bex-tenant-lg`) and `bex-tenant-burst` (2× `cx33`, 8 GB, ~7.47 GiB allocatable, label `nodepool: bex-tenant-burst`) carry the same taint `bex.co/build-only=true:NoSchedule` and label `bex.co/pool=tenant`.
- Today build pods have no scheduling preference between them, so Kubernetes `LeastAllocated` sends builds onto `cx33` burst nodes as soon as `bex-tenant-lg` holds one build (or randomly on ties), where a 6.8–7.45 GiB build triggers kubelet node memory-pressure eviction (`Evicted` + `DisruptionTarget=True`) instead of a clean cgroup OOMKill.
- Because `buildPodFailurePolicy` ignores `DisruptionTarget=True`, a build repeatedly evicted for node memory pressure loops freely until `BuildTimeout` (2h) or GitHub clone-token expiry.
- Swapping `bex-tenant-burst` from `cx33` to `cx43` is intentionally deferred: `fsn1` has intermittent `cx43` stockouts (`docs/ADR053-node-instance-types.md:96`), and adding `cx43` dependency to `burst` increases manual ops friction during CAPI rolls.

## Steps

1. In `lego/operator/internal/build/build.go` (`BuildJob`), add a soft `preferredDuringSchedulingIgnoredDuringExecution` node affinity preferring `nodepool=bex-tenant-lg` (weight 100) so solo/heavy builds land on the 16 GB `cx43` node whenever a slot is free, while still scheduling cleanly onto `bex-tenant-burst` (and local kind/CAPD clusters where that label is absent) when full.
2. Inspect how Kubernetes / kubelet marks a memory-pressure eviction on a build pod (`pod.Status.Reason == "Evicted"` and `pod.Status.Message` mentioning memory / `DisruptionTarget` condition message) vs a voluntary node drain/preemption. In `EnsureBuild` (or via a bounded retry cap in the controller when observing repeated `Evicted` memory-pressure pods on a Job), stop an unbounded memory-pressure eviction loop after a small cap (e.g., 2 memory-pressure evictions) and fail the build with a clear memory-limit / eviction verdict instead of looping for 1–2 hours.
3. Document the scheduling preference and eviction-loop guard in `docs/ADR060-build-worker-reliability-and-performance.md`.
4. Add unit/envtest coverage in `lego/operator/internal/build/` and `lego/operator/internal/controller/`.

## Acceptance criteria

- [ ] `BuildJob` carries a soft preference for `nodepool=bex-tenant-lg` without requiring it (so clusters without `nodepool` labels still schedule builds unchanged).
- [ ] A build Job whose pods are repeatedly evicted for node memory pressure stops looping at the bounded cap instead of retrying until `BuildTimeout`, while genuine node drains/preemptions remain absorbed.
- [ ] `make test` and `make lint` pass in `lego/operator/`, and `bash scripts/docs-links-validate.sh` passes.
