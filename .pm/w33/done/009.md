# 009 — Walk the deploy button's referrer fallback on production in a real browser

Why: w33/003 was checked only on `vite dev` with hand-set `Referer` headers. Nobody has yet seen `https://dashboard.bex.co/deploy` with no `repo` pick up the referring repository in a browser, through the production ingress and the sign-in bounce.

Production already carries `8f7f06824` (pin `ad799a7cf32b`, 2026-11-21), so this is a walk, not a code change. Nothing is created until Deploy is clicked, so the walk leaves no fixtures. Use playwright-core with headless Chrome. On this host the Playwright MCP fails because `npx` is not on PATH. Sign in with the QA user (`QA_EMAIL` / `QA_PASSWORD` from `.env`).

Walk, with `page.goto("https://dashboard.bex.co/deploy", { referer })` and a public repository such as `https://github.com/render-examples/express-hello-world`:

1. Signed in, `referer` `…/<owner>/<repo>` → the new-Blueprint wizard opens with that repository filled in.
2. Signed in, `referer` `…/<owner>/<repo>/tree/<branch>` → the repository and that branch are filled in.
3. Signed out, same referrer → the sign-in page's `next` carries the repository; after signing in, the wizard opens filled in.
4. `referer` `https://github.com/` (origin only, which is what github.com really sends) → the empty wizard, as before.
5. One real click from a page that sends its full URL (an `<a referrerpolicy="unsafe-url">` on a local page whose path is `/<owner>/<repo>`), so the client's `document.referrer` path is exercised as well as the server's header.

Done when: each step behaves as described, recorded in this note with the URL each one landed on. A step that differs is fixed under this note if the fix fits in under an hour, or filed as a follow-up.

Source: follow-up from w33/003's open live check, listed in the w33 drain report, 2026-11-21. ~30m.

**Done 2026-11-22:** walked on production pin `19fdb46f1758` (carries `8f7f06824`) with playwright-core 1.49.1 and headless Chromium, signed in as the QA user in the first-party `bex` workspace; nothing was clicked past the wizard, so nothing was created. Every step behaves as described:

1. `Referer: https://github.com/render-examples/express-hello-world` → `307 /deploy` → `https://dashboard.bex.co/blueprint/new?repo=https%3A%2F%2Fgithub.com%2Frender-examples%2Fexpress-hello-world`; the Public Git URL tab holds the repository, the name `express-hello-world`, Blueprint Path `render.yaml`, and Branch `main` once the preview resolved the default branch.
2. `Referer: …/express-hello-world/tree/main` → `…/blueprint/new?repo=…%2Fexpress-hello-world&branch=main`, the same fields with Branch `main` from the link.
3. Signed out, `Referer: …/express-hello-world` → `307 /deploy` → `307 /blueprint/new?repo=…` → `https://dashboard.bex.co/auth/login?next=%2Fblueprint%2Fnew%3Frepo%3Dhttps%253A%252F%252Fgithub.com%252Frender-examples%252Fexpress-hello-world` ("Welcome back"). After signing in, the same login URL forwarded to `…/blueprint/new?repo=…%2Fexpress-hello-world` with the wizard filled as in step 1. The session came from `scripts/qa-login.sh` (the password never passes through the agent), so the login page's `session_already_available` branch, not the form's `onSuccess`, did the forward; both navigate to the same `safeNext(next)`.
4. `Referer: https://github.com/` → `307 /deploy` → `https://dashboard.bex.co/blueprint/new`, the empty wizard (Blueprint Path `render.yaml` only).
5. A real click on `<a referrerpolicy="unsafe-url" href="https://dashboard.bex.co/deploy">` on a local page served at `https://github.com/render-examples/express-hello-world` (a Playwright route): the browser sent that full URL as `Referer`, and it landed on `…/blueprint/new?repo=…%2Fexpress-hello-world`, filled. The client path: the same click to `/blueprint/new` instead, then an in-app `router.navigate({ to: "/deploy" })` with no document request, landed on `…/blueprint/new?repo=…%2Fexpress-hello-world` from `document.referrer`; with an origin-only `document.referrer` the same navigation stays on the empty wizard.

The first try at step 5 served the page at `http://127.0.0.1:<port>/render-examples/express-hello-world` and landed on the empty wizard. That is intended, not a bug: the referrer only names a repository bex can clone, and `isValidGitUrl` (`dashboard/src/common/lib/utils/git-url.ts`) accepts `https://` and GitHub's SSH spellings, not `http://`. Reproduce with the walk above; no follow-up filed.
