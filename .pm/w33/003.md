# 003 — The deploy button falls back to the referring page when `repo` is absent, as Render documents

Why: ADR018's Blueprint row records "Not implemented: Render's Referer fallback when `repo` is absent" with no user sign-off, and a button copied from a Render README without `repo` lands on an empty wizard on bex.

Render (render.com/docs/deploy-to-render, read 2026-11-16): "By default, Render uses the **referrer of the page** containing the Deploy to Render button to detect the repository to deploy." and, of the `repo` parameter, "Without it, the Git repository URL is determined from the `Referer` header, however many browsers no longer include the full URL in the `Referer` header due to privacy and security concerns."

bex today: `dashboard/src/routes/deploy.tsx` reads only the `repo` and `path` search parameters and hands `repo` to `parseDeployRepo` (`dashboard/src/features/blueprints/lib/deploy-link`); with no usable `repo` it opens the empty `/blueprints/new` wizard.

Do: when `repo` is absent, try `document.referrer` through the same `parseDeployRepo` (it already understands `…/tree/<branch>`), and carry the result through the sign-in redirect so a signed-out visitor keeps it. A referrer that is only an origin, or names no repository, behaves as today. Nothing is created until the user clicks Deploy, as now. Add the two cases to the route's tests, and replace the ADR018 sentence.

Expect a small effect: a page on github.com sends only its origin to another site, which is the limit Render's own sentence describes. The alternative that closes the unsigned gap without code is the user's one-line sign-off in ADR018; that is a divergence and is the user's call, so this note implements the fallback unless such a sign-off is recorded first.
