## Objective

A hook on a service with a disk can read and write the disk at the service's mount path, which is the use Render names ("downloading files to a persistent disk").

## Context

- `spec.disk {name, mountPath, sizeGB}` (ADR082); a disk-bearing service runs one instance and deploys with `Recreate`.
- The pre-deploy Job receives only the `/etc/secrets` projection (`lego/operator/internal/predeploy/predeploy.go:138`, `Volumes`/`VolumeMounts`), so a Job built the same way has no disk.
- Disk provisioning, snapshots and restore live in `lego/operator/internal/controller/app_controller.go` (`annotDiskProvisioned`) and `disk_backup.go`.

## Steps

1. Read how the Deployment mounts the claim and which access mode the claim has.
2. If the claim can be mounted by a second pod on the same node, schedule the hook Job onto the instance's node and mount the claim at `spec.disk.mountPath`. If it cannot, run the hook inside the live instance instead, as t001 allows, and record which was chosen in ADR004.
3. Keep the hook off the disk while a restore or a purge is pending.
4. A service without a disk runs the hook exactly as t002 built it.

## Files

- `lego/operator/internal/controller/app_controller.go`
- `lego/operator/internal/predeploy/predeploy.go`
- `docs/ADR004-app-deployment.md`, `docs/ADR082-persistent-disks.md` (one sentence each)

## Acceptance criteria

- [ ] A file the hook writes under the mount path is readable by the running service.
- [ ] The hook never runs against a disk with a pending restore or purge.
- [ ] `make test` passes from `lego/operator/`, with an envtest for the disk case.

## Out of scope

- Giving the pre-deploy command disk access (Render's pre-deploy command has none).

## Outcome (2026-11-16)

- The claim is `ReadWriteOnce` (lego/operator/internal/controller/disk.go `createDiskPVC`), so the first option was taken: the hook Job mounts the claim at `spec.disk.mountPath` with a required pod affinity to the service's instance on `kubernetes.io/hostname`. Running inside the live instance was rejected (it needs `pods/exec` on the operator and leaves no Job to bound or read). ADR004 and ADR082 record it.
- Three things the steps did not name, each needed for the mount to work: the pod takes the instance template's `hostUsers` (the local `local-path` class refuses the idmapped mount a pod user namespace needs), it drops the tenant-pool node selector (the instance's node is the only one that can mount the volume), and it keeps the tier's limits over near-zero requests (CPU 0, memory 64Mi), the disk snapshot Job's rule, because that one node is bin-packed and no autoscaler can add room to it.
- The hook does not start while a requested restore is unserved or a snapshot purge is pending (`diskBusy`), and a restore waits for a hook that still mounts the volume (`initialDeployHookHoldsDisk` in `reconcileDiskRestore`).
- Tests: `TestInitialDeployHookMountsTheServiceDisk`, `TestInitialDeployHookStaysOffADiskWithAPendingRestore`, `TestRestoreWaitsForARunningInitialDeployHook`, the envtest "Initial deploy hook (kubernetes runtime)", and the admission envtest, which now submits the disk-sharing hook Job to the deployed `bex-operator-workloads` policy under every container policy and both serving-pool tiers.
- Not observed: a kubelet mounting the volume twice on one node and the service reading the hook's file. That needs a cluster (t007, the production replay).
