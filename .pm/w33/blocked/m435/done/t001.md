## Objective

Write down, before any code, how bex runs a Blueprint's `initialDeployHook` after this milestone: once, after the service's first release is live, beside `preDeployCommand`, with the service's disk, and without failing the deploy when it fails.

## Context

- Render (render.com/docs/blueprint-spec, read 2026-11-16): "Render runs this command after a service's _first_ successful deploy. Useful for one-time initialization tasks such as seeding a database or downloading files to a persistent disk." "This command runs only once per service instance (including in preview environments). For commands that should run before _every_ deploy, use `preDeployCommand` instead." Web services, private services and background workers only.
- Render documents no failure rule for the hook, no timeout and no log wording.
- bex today: the hook is the pre-deploy step until it succeeds (`lego/types/v1alpha1/predeploy.go:28`, `lego/types/v1alpha1/app_types.go` `InitialDeployHook`), from w2/m45 and w8/m63. ADR018's gap-backlog row for `initialDeployHook` states the timing difference; `docs/ADR006-bex-api.md` (capability registry row) says only "`initialDeployHook` runs once on first deploy".
- A disk-bearing service is single-instance with `Recreate` deploys (ADR082).
- `.pm/DO_NOT_DO.md`: one-off jobs stay a non-goal. The hook is an existing Blueprint field, not a way to run arbitrary commands on demand.

## Steps

1. If a Render workspace is available, capture what Render does when the hook exits non-zero (deploy status, retry, log lines) into `docs/render-artifacts/`; otherwise say in the ADR that the rule below is bex's choice.
2. In ADR004, next to the pre-deploy section, record: the hook runs as a one-time Job on the live release's image with the app pod's env, secrets and pull secrets; it starts only after the first release is live; `preDeployCommand` runs on every release including the first; a failed hook leaves the deploy live, is recorded, and is retried after the next release goes live; success sets `status.initialDeployHookCompleted` and nothing selects the hook again.
3. Record how the hook reaches the disk (t003 chooses between a Job co-scheduled with the instance and mounting the same claim, and running inside the live instance) and the constraint that decides it (the claim's access mode).
4. Record the edge cases: a suspended service, a canceled or rolled-back first release, a service scaled past one instance (once per service), and that cron jobs and static sites keep refusing the field.
5. Update ADR049 (the registry's `initialDeployHook` entry text) and the ADR018 gap-backlog row so neither still says the hook precedes the rollout.
