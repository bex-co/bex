## Objective

Know, and record, what each non-Blueprint Key Value create does with an omitted plan, and align any that Render's pinned contract defines differently.

## Context

- Render's pinned OpenAPI requires `plan` on `keyValuePOSTInput` (`lego/backend/internal/api/openapi/render-public-api-1.json`), so REST has no default to match.
- Render's MCP `create_key_value` arguments are pinned in `lego/backend/internal/api/openapi/render-mcp-tools.json`.
- bex's own creates: REST `POST /v1/key-value` (`lego/backend/internal/keyvalue/rest.go`), GraphQL, MCP (`lego/backend/internal/keyvalue/mcp.go`), and the dashboard's New Key Value form.

## Steps

1. For REST, GraphQL, MCP and the dashboard form, read what an omitted plan does today.
2. Compare REST with the pinned `keyValuePOSTInput` and MCP with the pinned `create_key_value` arguments (required, default, enum).
3. Align a surface only where the pinned contract says something different from what bex does; where Render defines nothing (GraphQL, the dashboard's preselected plan), leave it and record why.
4. Write the result as one short table in ADR021.

## Files

- `lego/backend/internal/keyvalue/` (only if a surface must change)
- `docs/ADR021-keyvalue-management.md`

## Acceptance criteria

- [ ] ADR021 states the omitted-plan behavior per surface with its Render basis.
- [ ] Any surface that changed has a test.

## Out of scope

- Changing the CRD default, which self-hosted and storeless creates rely on.
