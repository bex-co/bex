## Objective

A tenant can see that the hook ran and how it ended, and no surface reports a deploy as waiting on, or failed by, the hook.

## Context

- bex-api tells a release still awaiting its pre-deploy step from one whose rollout has begun through `PreDeployStepCommand` (`lego/backend/internal/store/reconciler.go:2630`, w4/670; tests in `lego/backend/internal/store/awaiting_predeploy_test.go`). After t002 the hook is no longer that step.
- Event types on REST must stay inside Render's enum (ADR018 Service events row); do not add a bex-named event type for the hook.
- Pre-deploy output already reaches the deploy's log; the hook's Job output needs the same path.

## Steps

1. Route the hook Job's output into the first deploy's log, after the lines that mark it live, in the style of the pre-deploy lines. A non-zero exit ends with a line that names the hook and its exit code.
2. Make bex-api's deploy status independent of the hook: a deploy is `live` before the hook starts and stays `live` whatever the hook does.
3. Remove the hook from the awaiting-pre-deploy read and its tests; a release with only a hook owed is not awaiting pre-deploy.
4. Blueprint reads keep echoing `initialDeployHook` (`lego/backend/internal/apps/render.go:511`).

## Files

- `lego/backend/internal/store/reconciler.go`, `lego/backend/internal/store/awaiting_predeploy_test.go`
- `lego/operator/internal/controller/app_controller.go` (log routing)
- `lego/backend/internal/logs/` (only if the hook's lines need a label)

## Acceptance criteria

- [ ] REST `GET /v1/logs`, GraphQL `logs`, MCP `list_logs` and the dashboard deploy log show the hook's output after the deploy went live.
- [ ] A failed hook changes no deploy's status on any surface.
- [ ] `cd lego/backend && go test ./...` passes.

## Out of scope

- A new event type or notification for the hook.
