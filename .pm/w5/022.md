# Fix metrics lookup for opaque service IDs

Production diagnosis on 2026-07-17 confirmed that both the service Metrics tab
and Scaling → Recent Metrics send the public `srv-…` service ID to the shared
metrics verb. `metrics.Service.Metrics` resolves that ID to the correct App for
authorization, but downstream pod, cAdvisor, and Traefik selectors continue to
use the unresolved request value. Store-managed Apps use tenant-prefixed
Kubernetes names, so the selectors return successful empty series.

For `srv-d9dd16roviqs738quds0`, the live App is
`tea-d98210cbbpdc73dcrkvg-bex`: production Prometheus returned no CPU, memory,
or Traefik series for the `srv-…` selector, while the resolved App-name selector
returned one CPU series, one memory series, and seven Traefik series. Prometheus,
cAdvisor, the App, and its pod were healthy.

Fix `lego/backend/internal/metrics` so operational lookups use the resolved
`app.Name`, while response labels retain the public/requested resource identity
and bandwidth keeps using the stable App ID plus exact router identities. Add a
store-managed regression fixture whose metadata name, public service name, and
`bex.co/app-id` differ; query it by `srv-…` and cover CPU, memory, resource
limits, instance count, HTTP requests/latency, and the shared REST/GraphQL/MCP
behavior. Preserve name-based and legacy label-less compatibility.

Acceptance: both production dashboard pages render real metrics for the
affected service; typed-ID and legacy-name tests pass; empty series still mean
genuine absence rather than an identity mismatch. Estimate: 45m.
