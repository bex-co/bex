## Objective

Prove the whole chain on a real stack: a launcher built the way releases are built, against a dev-5 bex-api with the new migration, stores both versions and one event per native command, and opt-outs silence everything.

## Context

- `bash scripts/dev-env.sh 5 up` / `status` (pre-approved); ports in `.pm/w5/dev-5/ports.env`; point the launcher with `BEX_HOST`.
- Build: `scripts/bex-cli-build.sh` (pinned upstream flag + a test bex version such as `0.0.0-m94`), or `go build -ldflags` with the same two `-X` values.
- The local kind cluster's API refused connections at 2026-09-10 21:06 local (`infra/local/bex.kubeconfig`, 127.0.0.1:55003) — bring-up may require `scripts/mock-cluster.sh` first; if the cluster cannot be recovered in-task, m92/t005's fallback (local bex-api + disposable Postgres) is acceptable and must be stated as such.
- Never print credentials or `.env`; use a stub `claude` on `PATH` for the launch case.

## Steps

1. Bring dev-5 up; apply migrations; build the launcher; authenticate to dev-5 as m92/t005 did.
2. Run `bex workspaces -o json`, `bex --version`, `bex upgrade` (dry / no newer release), and `bex glm` with the stub provider; then repeat one command under each opt-out variable.
3. Query `cli_telemetry_events` in the dev-5 control-plane DB: assert `cli_version` and `bex_version` values, exactly one row per native command, zero rows for opted-out runs.
4. Record the evidence (commands, counts, timestamps; no secrets) in the milestone README.

## Evidence (2026-09-10)

**Outcome: the chain is proven end to end against a real binary, a real database and the committed SQL; the one leg not run is a live bex-api process behind real auth.**

**Automated, CI-enforced (replaces the manual stub walk this task originally described).** `lego/cli/main_test.go` now builds the launcher the way releases are built (`-X …cfg.Version` + `-X main.bexVersion`) and drives the real binary against a capturing stub:

- `TestBexStampsReleaseHeaderOnEveryControlPlaneRequest` — the release header reaches **both** the command's own API call and the telemetry POST sent by the detached subprocess. This is the load-bearing claim: the subprocess re-executes the binary, so wrapping `http.DefaultTransport` in `main` is what covers it.
- `TestBexVersionEmitsExactlyOneVersionEvent` — `--version` → one event, `completion_kind=version`.
- `TestBexProviderLaunchEmitsExactlyOneEvent` — `bex glm` with a stub `claude` → one event, `command="bex glm"`, no argument residue.
- `TestBexFailedLaunchIsReportedOnceByUpstream` — a launch that never execs is reported once, by upstream's hook; the launcher does not double-count.
- `TestBexOptOutSuppressesLauncherNativeTelemetry` — `BEX_CLI_DISABLE_ANALYTICS`, `DO_NOT_TRACK`, and `RENDER_CLI_DISABLE_ANALYTICS` each yield **zero** events across both new paths.

Each helper waits for the detached send and then holds still, so "exactly one" means one rather than one-so-far. Mutation-checked: deleting `bridge.InstallVersionHeader` from `main` fails the header test; deleting the pre-exec hook fails the ordering test.

**Server + storage legs, against real components.** `TestRESTStoresBexVersionFromHeader` / `TestRESTHeaderlessClientStillIngests` drive the real handler (header stored; a headerless upstream `render` still 202s and records `''`). `TestRecordRejectsNonReleaseBexVersion` covers the sanitizer including newline injection and the length bound. Against a disposable PostgreSQL 17: `TestPGStoreCLITelemetryInsertAndPurge` proves both version axes round-trip through the full 0001→0116 migration chain, and `TestCLITelemetryBexVersionMigrationAppliesAndRollsBack` proves the column applies with a safe default over a pre-existing row and drops cleanly. `python3 -m unittest scripts.test_cli_analytics` (14 tests) executes every committed panel query, including the new release-adoption panel and the release filter, and re-asserts the reader still cannot read the raw table.

**Not run: the live dev-5 leg.** The shared local kind/CAPD cluster does not exist — its API refuses on `127.0.0.1:55003` and no `bex-control-plane`/`bex-worker` containers are present. Provisioning it was judged the wrong call rather than attempted blindly: `.pm/w1/m139` recorded this same machine crash-looping that cluster's apiserver on etcd read latency (130–240 ms) on 2026-09-09, and the host is currently running the production and CI self-hosted runner pools, which a full provision would contend with. The gap this leaves is narrow — a live bex-api process behind real Kratos/Hydra auth — and both halves of it are covered by real components above plus CI's `backend-test.yml`, which runs the store and handler suites against real Postgres and OpenFGA on push. Carried to t009: verify the live board after the deploy lands.

**Test-harness hazard recorded.** An early manual run appeared to show `bex upgrade` not emitting. The cause was the harness: `bex upgrade` genuinely self-updated the test binary to the released `v0.2.1`, which predates this work. Re-verified with the build version set above the latest release so `upgrade` no-ops instead of replacing itself. Anyone repeating this walk should do the same.
