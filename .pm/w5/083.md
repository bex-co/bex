# A crash under an open deploy can be dated from the rollout start

Why: w5/m113 lets a debounced pass keep the edge floor, so a confirmed failure is stamped at its Ready transition. Under an open deploy, the unhealthy conclusion (a concrete container failure with nothing serving) carries Ready's `LastTransitionTime`, which is the rollout's start, not the failure's. When the first pass to see the rollout is already that debounced crash, `server_failed` is dated from the rollout start.

That is accurate for a Recreate rollout (disk-backed services), whose old pod stops first. It is early for a RollingUpdate whose old pods died later in the rollout. Before m113 the same edge was a resync or two late in both cases.

Source: w5/m113's `/simplify` quality review, 2026-10-05 (`observedServiceStateFor`'s open-deploy branch, `lego/backend/internal/store/reconciler.go`; Ready written at `lego/operator/internal/controller/app_controller.go` `reportRolloutProgress`).

## Fix (~45m)

1. In that branch, back the conclusion with the `Serving` condition's transition when it is False for the current generation. That is when the serving revision actually stopped. With no such condition, carry no transition, so the edge stays at the observation.
2. Keep Ready's time for `rejectStaleUnhealthy`'s ordering, or move that guard to the same source. Either way, write down which.
3. PG replay through `guardServiceObservation`: a RollingUpdate whose old pod dies mid-rollout is dated at the `Serving` flip, and a Recreate rollout at the rollout start.
