## Objective

Make the REST adapter faithfully accept the official CLI's nested image owner while binding it to the same authorized workspace as the created or updated service, without weakening strict JSON validation.

## Context

- Top-level create `ownerId` already selects a membership-checked workspace through `w6/m14`.
- On create, nested `image.ownerId` must not silently disagree with the effective top-level/default workspace; on PATCH it must not retarget an existing service into another workspace.
- `image.registryCredentialId` already has omission-versus-clear semantics that must remain byte-compatible.

## Steps

1. Extend the REST-only image wire model with `ownerId`; do not add a duplicate ownership concept to the core App CR.
2. On create, resolve the effective workspace once and validate nested image ownership against it using the existing membership/authorization mechanism.
3. On PATCH, validate nested ownership against the target App's own workspace before applying any source change.
4. Return a field-named error for inconsistent owner fields and preserve the existing forbidden behavior for a workspace the caller cannot access.
5. Re-run exact POST/PATCH cases with and without `registryCredentialId`, plus omission and unknown-field controls.

## Acceptance criteria

- [x] Exact official-CLI image create and image update payloads decode and persist the intended image path.
- [x] A matching nested owner succeeds; conflicting top-level/resource ownership gets a named `image.ownerId` 400, and unauthorized workspace selection remains 403 with no mutation.
- [x] `registryCredentialId` set/clear/omitted behavior is unchanged on both POST and PATCH.
- [x] Unrecognized image keys are still rejected by the strict decoder; the fix does not replace it with permissive decoding.

## Out of scope

- Changing Render's pinned OpenAPI schema, introducing image ownership into GraphQL/MCP, or supporting cross-workspace service moves.
