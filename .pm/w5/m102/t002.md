## Objective

Implement Leave as one core verb in `members/service.go`, acting only on the caller's own subject, guarded by the owner and last-admin rules, using the same fail-closed revoke-then-delete order as `Remove`.

## Objective detail / Context

- `Remove`'s ordering rationale is load-bearing (`lego/backend/internal/members/service.go:981-994`): revoke the OpenFGA tuple **before** deleting the row, so a partial failure leaves a fail-closed intermediate a retry converges. Leave must copy it, not re-derive it.
- Authorization per t001's decision — self-scoped, not `can_manage`; the caller's subject comes from `core.IdentityFrom`, never from an argument.
- Guards: owner refusal (`OWNER_CANNOT_LEAVE`), last-admin refusal (reuse `guardLastAdmin` with the caller's current role).
- Audit: its own verb name with the workspace as the object, so the events feed distinguishes "left" from "was removed" (`core.AuthorizeOnTarget` / the member-target vocabulary, `lego/backend/internal/api/CLAUDE.md`).

## Steps

1. Add `LeaveWorkspace(ctx, workspaceID) error` to `members.Service`.
2. Resolve the caller's subject from context; take no subject argument at all.
3. Run the membership fetch, owner guard, last-admin guard; then revoke tuple, then delete row.
4. Record the audit row under a distinct verb name and confirm it appears in the events feed.
5. Invalidate the caller's resolver cache entry (t003 wires the seam if it is not already reachable here).

## Acceptance criteria

- [ ] `LeaveWorkspace` removes only the caller's own membership; there is no argument by which it could remove another subject.
- [ ] Owner and last-admin refusals fire with coded errors.
- [ ] Tuple is revoked before the row is deleted; a forced revoke failure leaves the member row present and no live tuple.
- [ ] The audit row names its own verb, distinct from `members.Remove`.
