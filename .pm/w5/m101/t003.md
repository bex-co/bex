## Objective

Separate "manage a teammate" from "act on yourself": `members.Remove` and `members.ChangeRole` refuse when the target subject is the caller's own subject. Removing yourself becomes `m102`'s explicit Leave verb; changing your own role becomes something another admin must do — matching Render, where neither is possible from the members surface.

## Context

- `Remove` (`lego/backend/internal/members/service.go:956`) and `ChangeRole` (`:793`) both take a `subject` argument and never compare it with the caller.
- The caller identity is already on the context (`core.IdentityFrom`), and both verbs already run `AuthorizeOnTarget` + `AuthorizeFreshOn` + `guardCallerRoleSettled` — the new check belongs next to those, before any store read.
- Machine callers (API-key client ids) are subjects too: an API key removing its own binding row must hit the same refusal.
- `AccountOffboarder.Remove` (`service.go:1014`) is the trusted background path and must stay exempt — it is not an authenticated self-service action.

## Steps

1. Add `guardSelf(ctx, subject)` to `members.Service`; call it from `Remove` and `ChangeRole` after authorization, before the store read.
2. Return distinct coded errors for the two verbs so the UI can say the right thing: `CANNOT_REMOVE_SELF` (point at Leave workspace) and `CANNOT_CHANGE_OWN_ROLE` (point at another admin).
3. Confirm the audit trail still records the attempt with the `member:<subject>` target (the deny path records immediately — verify, don't assume).
4. Assert the exemption: `AccountOffboarder.Remove` and invite acceptance are unaffected.
