## Objective

Make the subject named by `tenants.owner_identity_id` unremovable through the member verbs, guarded in both places the last-admin rule is already guarded: a friendly service-level refusal, and a hard recheck inside the store transaction that already holds the workspace advisory lock — so a second adapter or a race cannot bypass it.

## Context

- Owner binding is set only by onboarding's `CreateTenantWithMember` (`lego/backend/internal/store/store.go:736`); workspaces created through `CreateWorkspace` (`internal/store/workspaces.go:44`) have a NULL binding, so this guard is a no-op for them — the last-admin rule keeps covering those.
- The precedent to mirror exactly: `guardLastAdmin` (`internal/members/service.go:1076`) plus the in-transaction recheck in `PGStore.RemoveMember` (`internal/store/members.go:190`, `pg_advisory_xact_lock` + `FOR UPDATE`).
- ADR086's `RemoveAccountMember` (`internal/store/accounts.go:349`) is the one path that legitimately clears the binding — it must keep working unchanged.
- Coded errors: follow `core.ErrBadRequest` / `core.NewPlanLimitError` shapes already used in this package (`guardPlanRole`).

## Steps

1. Add a store read for the owner subject (e.g. `TenantOwnerSubject(ctx, tenantID)`) and a typed `ErrOwnerMember` sentinel.
2. Add `guardOwner` to `members.Service`, called from `Remove` before the write (and from `ChangeRole` only if the role change would drop the owner below `admin` — decide and document which, in the ADR task t006).
3. Recheck inside `PGStore.RemoveMember`'s existing transaction: if the row being deleted is the owner binding's subject, return `ErrOwnerMember`.
4. Map the sentinel to a coded refusal in `mapStoreErr` so every adapter sees the same error.
5. Leave `RemoveAccountMember` untouched and assert in a test that the ADR086 offboarding path still removes an owner (it clears the binding in the same transaction).

## Acceptance criteria

- [ ] `members.Remove` on the owner subject returns a coded refusal and leaves the `tenant_members` row intact.
- [ ] The refusal also fires when the service-level guard is bypassed (direct `PGStore.RemoveMember` call in a test).
- [ ] `AccountOffboarder` / `RemoveAccountMember` (ADR086) still removes a deleting owner and clears the binding; its existing tests pass unmodified.
- [ ] The t001 resurrection assertion flips to the refusal outcome.

## Out of scope

- Self-removal and self role change (t003).
- Letting the owner leave by transferring ownership (deferred, `.pm/FUTURE-MAYBE.md`).
