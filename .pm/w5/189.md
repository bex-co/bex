# 189 — Sandbox image imports: a platform-wide budget sized to the registry, fair import workers, and no foreign layer URLs

Why: round 24's S-3 fix counts in-flight imports against each workspace's cap, but the per-workspace cap (500 GB default) is larger than the shared Zot registry, so several workspaces together can still fill it and break every tenant's builds.

- **Source:** security review round 24 (w5/m371, ADR107), S-3 remainder and sandbox hardening notes.
- **Budget:** a platform-wide limit on imported sandbox image bytes (in flight and stored), well below the registry volume (`deploy/gitops/base/zot.yaml`), refusing with a named 429. Needs the operator's capacity number: check the production PVC size first, since it may have been grown out of band.
- **Workers:** the import worker pool is shared across tenants (2 per replica, `lego/backend/internal/sandbox/images.go`); a slow source holds a slot for up to 30 minutes. Bound per-workspace concurrency in the pool.
- **Foreign URLs:** layers that carry `urls` are copied into imported manifests, and containerd on the sandbox node tries those URLs from the host network (a blind GET). Strip or refuse such layers (needs a deployment test to confirm containerd's behavior).
- **Zot dedupe:** check whether Zot v2.1.22's cross-repo mount lets an import link another tenant's layer by digest; restrict mounts to the importer's own repositories if so.
- **Size:** more than 1h; promote to a milestone.
