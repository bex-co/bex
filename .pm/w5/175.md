# A WAL archive that hangs, instead of failing, is never reported

Why: m141's live walk showed that when the object store silently drops packets, `barman-cloud-wal-archive` blocks for more than 20 minutes without failing. CNPG keeps `ContinuousArchiving=True` throughout, so `postgres_wal_archive_failed` never fires, even though nothing has been archived since the stall and the recovery window keeps growing.

- **Evidence (2026-10-27, production `bex-canary`):**
  - A `CiliumNetworkPolicy` `egressDeny toEntities: world` was applied to one QA database's pods.
  - `pg_switch_wal()` ran at 04:34:40, and the plugin logged "Executing barman-cloud-wal-archive" for segment 5.
  - At 04:57, `pg_stat_archiver` still showed `failed_count=0`, `last_archived_time=04:21`, and the condition said "Continuous archiving is working".
  - Only denying DNS as well (a fast failure) flipped the condition.
- **Shape of a fix:** have the operator compare `pg_stat_archiver.last_archived_time` (or the oldest `.ready` segment in `pg_wal/archive_status`) with the time since the last WAL switch. Report a stall past a threshold (for example, 15 minutes with segments waiting) as `WALArchiving=failed` with a stalled reason, so the existing `postgres_wal_archive_failed` edge fires. Check what Render reports for a stalled archive first.
- **Size:** about 1 to 2 hours (operator probe, condition, and tests), so this probably becomes a milestone.
