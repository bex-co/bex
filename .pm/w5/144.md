# An App without a service-name label still reaches a Blueprint apply's env and maintenance verbs by name

Why: w5/m133 made the apply address the service it wrote by its public id. An App without a service-name label (pre-w4/m19 bare-named, or created with no workspace) keeps its object name, because the secrets store keys its path by that name. `AuthorizeApp` then resolves the name through its displayed-name lookup, which searches every workspace the caller belongs to when the deploy names none.

- **Where:** `lego/backend/internal/apps/deploy.go` `stackServiceRef` returns `app.Name` when `LabelServiceName` is empty. `LinkEnvGroup`, `SeedEnvVars` and `ConfigureMaintenanceMode` resolve it through `core.Base.AuthorizeApp`.
- **Fix:** either name the App's own workspace in the context for those calls (`core.WithWorkspace(ctx, app.Labels[core.LabelTenant])`), or have the secrets store's key fall back to `a.Name` rather than the passed string, so the public id always works.
- **Test:** a label-less App in workspace A, plus an App displayed under its name in workspace B the caller also belongs to. An ownerless deploy's link, seed and maintenance change reach the App in A.
- Found by w5/m133's quality review (2026-10-07). It is rare: the projector stamps the label on managed Apps.
