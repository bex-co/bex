# 059 — Cobra's usage/error path prints unbranded `render …` examples; the branding overlay only re-walks on the help path

Why: the first thing a `bex` user sees after a typo is upstream's usage block, and for four supported commands it tells them to run `render …` — a binary they do not have — even though `--help` for the same command is correctly Bex-branded.

- **Severity:** minor (cosmetic, but it is exactly the guarantee `lego/cli/internal/branding` exists to make, and it is the most-hit error surface).
- **Attribution:** Bex launcher (`lego/cli/internal/branding`). Not upstream: the strings are ordinary cobra metadata the overlay already owns and already rewrites on the help path.
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-15 UTC, workspace `bex` / `tea-d98210cbbpdc73dcrkvg`.

## Versions and context

- Installed customer binary `bex v0.2.1` (`/opt/homebrew/bin/bex`, "compatible with Render CLI v2.27.0") **and** a private checkout build of `main` at `710ebe07e` (`go build -o … ./lego/cli`) — the leak reproduces identically on both, so this is not release lag.
- Upstream pin: Render CLI **v2.27.0** / `a764810a768202704e7206eb7b87a47211fcd98e`.
- Isolated 0700 temp dir, private `BEX_CLI_CONFIG_PATH`, inherited `RENDER_*`/`BEX_*` removed, `BEX_HOST=https://api.bex.co/v1/`, `BEX_NO_UPDATE_NOTIFIER=1`, non-TTY. No network call is needed to reproduce — flag parsing fails before any request.

## Reproduction

```text
$ bex services update --bogus-xyz
Error: unknown flag: --bogus-xyz
Usage:
  bex services update <service> [flags]

Examples:
  # Rename a service
  render services update my-service --name my-new-name --output json

  # Change a service plan
  render services update srv-abc123 --plan 2c-4g --output json
```

Same shape, same run, `grep -cE '^[[:space:]]+render '` over the full stderr of `<cmd> --bogus-xyz`:

| command            | unbranded lines | what leaks                                                      |
| ------------------ | --------------- | --------------------------------------------------------------- |
| `services update`  | 2               | both examples                                                     |
| `logs`             | 3               | all three examples                                                |
| `keyvalues create` | 7               | six examples **and** `--workspace … (set via 'render workspace set').` |
| `workflows list`   | 1               | the example                                                       |

Control — the same commands on the help path are clean:

```text
$ bex logs --help | grep -c 'render '
0
```

`postgres create`, `services create`, `deploys *`, `projects`, `environments`, `ssh`, `psql`, `blueprints validate`, `restart`, `jobs *`, `whoami`, `workspaces` are all clean on both paths.

## Root cause

- `branding.Apply` (`lego/cli/internal/branding/branding.go:45-70`) calls `brandTree(root)` once, then installs a `root.SetHelpFunc` wrapper that calls `brandTree(root)` again before delegating. Its own comment states why: "upstream setupCommands adds more children during Execute (after this returns), so HelpFunc re-walks the tree before any help output."
- That re-walk is the **only** thing that brands late-added commands, and it is reachable exclusively through cobra's help path.
- The four affected commands are exactly the ones constructed inside upstream `setupCommands()` (`cmd/root.go:189-216`, called from `execute()` at `cmd/root.go:404` — i.e. after `branding.Apply` has already run): `setupLogCommands` → `NewLogsCmd` (`cmd/root.go:149-153`, `Example` set at `cmd/logs.go:29`), `setupServiceCommands` (`cmd/serviceupdate.go:24`), `setupKVCommands` (`cmd/kvcreate.go:29` + the flag usage at `cmd/kvcreate.go:51`), `setupWorkflowCommands`.
- On a flag/arg error cobra prints `c.UsageString()`, which renders the **usage** template and never invokes `HelpFunc`. `RewriteText` itself is fine — fed the leaking `--workspace` usage string directly it returns the `'bex workspace set'` form (verified with a throwaway test in `internal/branding`).

## Fix (~45m)

Wrap the usage path the same way `Apply` already wraps the help path:

```go
prevUsage := root.UsageFunc()
root.SetUsageFunc(func(c *cobra.Command) error {
    brandTree(root)
    overrideDocs(root)
    return prevUsage(c)
})
```

Cobra resolves `UsageFunc` for descendants by walking to the root, so one wrapper covers the tree — the same property the existing `HelpFunc` wrapper relies on.

- **Safe against upstream:** upstream never calls `SetUsageFunc` (only `SetHelpTemplate` at `cmd/root.go:84` and two `SetHelpFunc` calls — `cmd/execution.go:242`, `cmd/workflowinit.go:322`), so nothing clobbers it. Do **not** use `SetFlagErrorFunc` for this: upstream's `observeCobraValidationAndHelp` (`cmd/execution.go:248`) replaces it during `Execute` **without** delegating to a previous one, so a branding hook there would be silently dropped. This ordering must be re-diffed on every pin bump.
- Record the seam in `lego/cli/UPSTREAM_RENDER_CLI.md` step 4 beside the existing `CustomHelpTemplate` / `SetupCommands` re-diff instructions.

## Blast radius

Launcher-only; no REST/GraphQL/MCP/dashboard surface and no wire change. `brandTree` is idempotent (it rewrites already-Bex text to itself) and the extra walk runs only when usage is rendered, i.e. on an error, so there is no hot-path cost. The four commands above are the current population, but the fix is general — any future upstream command constructed in `setupCommands` is covered automatically.

## Regression checks

- New test in `lego/cli/internal/branding/branding_test.go`: build a root with a **late-added** child whose `Example` contains `render …`, call `Apply`, then assert `child.UsageString()` contains `bex ` and not `render ` — today this fails, and it fails for the right reason (the existing help-path assertions at `branding_test.go:97` and `:134` already pass).
- Extend `scripts/bex-cli-validate.sh` to run `bex <cmd> --bogus-xyz` for `services update`, `logs`, `keyvalues create`, `workflows list` and fail closed on any `^[[:space:]]+render ` line, so a pin bump that late-adds another command cannot reintroduce this silently.
- Control that must stay green: `bex logs --help` and `bex keyvalues create --help` remain 0 `render ` hits, and `render.yaml` / `bex.yml` / `render.com` hostnames stay byte-identical.

## Unverified

- Only the four commands above were swept (29 command paths tested). `bex help <cmd>` and a bare non-runnable group were not re-checked after a hypothetical fix.
- Whether `Args`-validation failures (wrong positional count) take the same `UsageString` path was reasoned from cobra's source, not exercised.
