## Objective

Make the Prometheus resource source answer CPU with MIN and MAX as t001 decided, for services and managed datastores alike. Keep a named refusal only where the capability really is absent (the metrics-server fallback).

## Context

- Production CPU query: `lego/backend/internal/metrics/source.go:328` — `sum by (pod) (max by (pod, container) (rate(container_cpu_usage_seconds_total{…}[Ns])))`, with the lookback `max(step, minRateLookback)` at `source.go:223`. `main.go` wires `NewPrometheusResourceSource` in production; the metrics-server snapshot source is the fallback.
- Interval meaning (t001 option a): wrap the rate in a subquery, `max_over_time((…)[<step>s:<scrape>s])` / `min_over_time(...)`. At a step ≤ the rate lookback MAX ≈ AVG; that's expected, so document it.
- Cross-series meaning (t001 option b): route through the existing replica aggregate (`MetricQuery.ReplicaAggregate`/`AggregateMax`, `parseReplicaAggregate` in `select.go:73`) instead of new PromQL.
- Datastore CPU reads go through the same source (`datastore.go`); keep their series shape unchanged for AVG.

## Steps

1. Add the aggregation to `MetricQuery` (or reuse the replica-aggregate fields under option b) and thread it to the resource source.
2. Build the MIN/MAX query (option a) or map onto the replica aggregate (option b). AVG and omitted stay byte-identical to today's query.
3. When the active resource source cannot honor MIN/MAX (the metrics-server fallback), return the named 400, now worded as that source's limit and not a general bex one.
