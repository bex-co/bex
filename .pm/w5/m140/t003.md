## Objective

Replace the AVG-only `cpuAggregation` rule with one parser all three surfaces share, so REST `aggregationMethod`, MCP `cpuUsageAggregationMethod` and GraphQL `aggregationMethod` reach t002's implementation with the same semantics and the same refusals. Close GraphQL's silent drop.

## Context

- `cpuAggregation` (`lego/backend/internal/metrics/mcp.go:111-123`) is called from REST (`rest.go:402`) and MCP (`mcp.go:178`); MAX/MIN currently return 400 "metrics-server snapshot".
- GraphQL declares `aggregationMethod` (`graphql.go:116`) but `metricsQueryInputFromArgs` (`graphql.go:381-454`) never reads it, so MAX is accepted and ignored.
- The MCP field's description (`mcp.go:57-60`) still says "bex CPU is a metrics-server snapshot, so MAX/MIN are rejected".

## Steps

1. Turn `cpuAggregation` into a parser returning the aggregation (or the named 400 for an unknown value, or for any non-CPU metric). Call it from REST, MCP and GraphQL.
2. Read `aggregationMethod` in `metricsQueryInputFromArgs`.
3. Rewrite the MCP field description and REST/GraphQL docs to the shipped semantics from t001.

- lego/backend/internal/metrics/mcp.go

## Acceptance criteria

- [ ] The same MAX request returns the same series on REST, MCP and GraphQL (one table-driven test across the three adapters).

- [ ] GraphQL no longer accepts `aggregationMethod` without effect.
