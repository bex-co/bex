## Objective

Serve Render's request-count host breakdown — REST `aggregateBy=host`, MCP `aggregateHttpRequestCountsBy: "host"`, GraphQL `aggregateBy: ["HOST"]` — from the Loki request-log store. Each series is labelled `host`. When that store can't answer, refuse with 503 and never fall back to a counter that has no host.

## Context

- `requestGroupBy` (`lego/backend/internal/metrics/mcp.go:129-145`) refuses `host` on the premise that neither source has a host axis.
- The Loki pipeline already extracts `request_host` (`lokisource.go:154-161`) and already emits `sum by (<label>)` (`lokisource.go:143`). `lokiGroupLabel` (`lokisource.go:205-214`) maps only status and method.
- Unfiltered `http_requests` reads Loki first and falls back to the Traefik counter on a Loki error (`service.go:1046-1056`). That fallback is right for an ungrouped count but wrong for a host breakdown: the counter has no host and would return one unlabelled series as if it were the breakdown. The host/path *filter* branch already refuses rather than fall back, so follow it.
- GraphQL's `aggregateBy` loop (`graphql.go:444-450`) drops HOST silently.

## Steps

1. Map `host` → `GroupBy="host"` in `requestGroupBy`, `lokiGroupLabel` → `request_host`, and relabel the result to `host` after the read, as status is relabelled to `code`.
2. In `service.go`, make a host-grouped read Loki-only: a Loki error or an unwired `RequestLogMetrics` answers `ErrMetricsUnavailable` (503 `METRICS_UNAVAILABLE`).
3. Map GraphQL `HOST` onto the same `GroupBy`.
