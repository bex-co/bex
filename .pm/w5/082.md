# ci-red-streak reads main through the runs API's branch search, which can return stale pages

Why: `scripts/ci-red-streak.sh:56` lists each workflow's runs with `gh run list --branch main`. A branch filter turns GitHub's run listing into a search, and that search can answer with a page of only old runs (cli/cli#7341, max-sixty/tend#1443). On 2026-10-05 the same call made w5/m112's ship gate block a green main on a failure from 2026-09-12. The daily red-streak report can misread a streak the same way.

Source: w5/m112's `/simplify` efficiency review, 2026-10-05. The ship gate (`scripts/ship-gates.sh`) was fixed in the same push; this note is its sibling.

## Fix (~30m)

1. Drop `--branch main`, add `headBranch` to `--json`, and keep only `headBranch == "main"` in the jq, as `scripts/ship-gates.sh` does.
2. Workflows that also run on pull requests then list PR runs too. Either raise the per-workflow `--limit` until main's streak still fits, or check whether `--event push` avoids the search path. Measure before choosing.
3. The fake `gh` in `scripts/ci-red-streak.test.sh` re-sorts runs newest-first (`:163`), which hides listing order from the detector. Stop re-sorting, and add a case where a stale run is listed first.
