## Objective

A concurrent re-plan by another developer cannot replace what an approval applies.

## Context

- `lego/backend/internal/apps/blueprint_onboarding.go` `ApproveBlueprint` (`LatestBlueprintPlan`), its REST handler, the GraphQL `approveBlueprint` field and the MCP `approve_blueprint` tool (`approveBlueprintArgs`, `planningGuidance`).

## Steps

1. Accept an optional sync id on every surface; when given and it is not the newest planned sync, answer 409 with a named code and apply nothing.
2. Have the MCP tool's guidance and schema carry the plan step's sync id.

## Acceptance criteria

- [x] Test: approving a stale sync id is refused and applies nothing; the newest one applies; an omitted id behaves as before.

## Outcome (2026-11-13)

`ApproveBlueprint` takes an optional sync id (REST body `syncId`, GraphQL `syncId`, MCP `syncId`, either spelling); once the newest plan is approvable, a different id answers 409 `BLUEPRINT_PLAN_CHANGED` (`details.syncId` the newest sync, `reviewedSyncId` the caller's) and nothing applies. The MCP tool's description asks agents to pass the reviewed plan's id; the dashboard passes the plan on screen and, on that refusal, shows the newest plan. MCP parity: `approve_blueprint` moved from 1:1 to superset (test and ADR018 updated). Tests: `TestBlueprintSyncPublicIDs…` (stale id refused, newest applies in the durable spelling), `use-planned-sync.test.ts`.
