# 193 — Check that the build pushers cannot link another workspace's layer into the shared registry by mount

Why: Zot links a mounted digest from any repository the pusher can read, whatever the `from` (w5/192, ADR107 S-4), and `bex-builder`, the credential kpack and BuildKit push with, can read every repository. If either pusher asks to mount a layer whose digest a tenant chose, the tenant's built image could carry another workspace's layer.

- **Source:** w5/192 /simplify review (2026-11-13).
- **Check:** for a Dockerfile build whose `FROM` image a tenant controls (its manifest naming a digest it does not hold), and for a kpack build, does the pusher send `?mount=<digest>` to Zot for a base layer it did not read the bytes of? kpack's lifecycle pushes with go-containerregistry, which asks to mount every layer it read from another registry; BuildKit's containerd pusher mounts only within one registry host.
- **Fix if so:** give the build pushers a credential that reads only the repositories a build may mount from (the build's own and the platform's run images), or have them upload rather than mount.
- **Size:** ~1h with a local Zot and a crafted base image.
- **Triage 2026-11-13 (`/loopx w5`): parked on the local cluster.** Reading the pushers' code suggests neither mounts a digest a tenant chose, but that is unverified. kpack's lifecycle mounts only run-image layers, which the platform's stack supplies, and uploads the app layers it built. BuildKit's containerd pusher mounts only within one registry host, and a layer it never read from a tenant's `FROM` registry cannot be exported without its bytes. Verifying it needs the build stack (kpack, BuildKit) against the deployed Zot, which runs on the local kind/CAPD cluster, blocked by the host's inotify limits (the w5/m370 gate).
