## Objective

Measure, on the local cluster, what makes an App change wait in the operator's queue, before choosing a fix.

## Context

- Local cluster: `bash scripts/mock-cluster.sh` (and `operator` to deploy `bex-operator:dev`); this worker's stack is `dev-5` (`bash scripts/dev-env.sh 5 up`).
- `BEX_APP_RECONCILE_WORKERS` (production `2`), `BEX_MAX_ACTIVE_BUILDS`, the 5 s build re-observe and the requeue sites in `lego/operator/internal/controller/app_controller.go`.
- The symptom to reproduce: a maintenance-mode toggle's Ingress repoint (w4/603) and a deploy's `queued` wait (w21/012).

## Steps

1. Create about 100 Apps on dev-5 (image web services, a few source builds in flight, some Free services hibernating).
2. Read queue wait, depth and pass time from t001's metrics; time a maintenance-mode toggle until the Ingress points back.
3. Find which passes are slow or frequent: per-pass duration by kind (build observe, rollout, hibernation, datastore), the requeue fan-out, and API reads per pass (a CPU profile or per-pass timing logs).
4. Record the numbers and the cause(s) in the milestone README under `## Findings`.
