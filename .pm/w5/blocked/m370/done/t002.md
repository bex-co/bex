## Objective

Measure what makes an App change wait in the operator's queue, before choosing a fix. Since 2026-11-19 (§ Findings, unblock record) this reads production's queue, at production's fleet, instead of the local cluster, which cannot run on this host; any load generated lives in `bex-canary` and is deleted.

## Context

- Production: `scripts/fetch-app-kubeconfig.sh <path outside the repo>`, `kubectl -n monitoring port-forward svc/prometheus-server` (3 days of retention) and `svc/loki` (30 days of logs). Read-only.
- Local cluster (not usable here: the host's inotify limits need the user's sudo): `bash scripts/mock-cluster.sh`.
- `BEX_APP_RECONCILE_WORKERS` (production `2`), `BEX_MAX_ACTIVE_BUILDS`, the 5 s build re-observe and the requeue sites in `lego/operator/internal/controller/app_controller.go`.
- The symptom to reproduce: a maintenance-mode toggle's Ingress repoint (w4/603) and a deploy's `queued` wait (w21/012).

## Steps

1. Read production's fleet (28 to 29 Apps of every kind). Generate load only in `bex-canary`, and delete it.
2. Read queue wait, depth and pass time from t001's metrics; time a maintenance-mode toggle until the Ingress points back.
3. Find which passes are slow or frequent: per-pass duration by kind (build observe, rollout, hibernation, datastore), the requeue fan-out, and API reads per pass (a CPU profile or per-pass timing logs).
4. Record the numbers and the cause(s) in the milestone README under `## Findings`.
