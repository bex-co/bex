# Render templates with free-form resource names or dotted env keys validate (needs a naming decision)

Why: Render's Blueprint spec puts no rule on a resource `name` beyond uniqueness, and its templates use dotted env keys, but bex refuses both. So templates like `pgadmin` (`name: pgAdmin`), `gitpod-openvscode-server` (a 31+ character name), `vibe-code-demo-apps`, `postgresql-missing-trigger-index`, and `elasticsearch`/`forem` (`discovery.type`) fail on bex while deploying on Render.

- **Names:** bex applies ADR020's resource-name rule (lowercase, digits, hyphens, at most 30 characters) to a Blueprint `name` (`RESOURCE_NAME_INVALID`). Render's spec says only "provide a unique name for each resource" (render.com/docs/blueprint-spec, fetched 2026-10-20). This overlaps the open naming decision in blocked w5/m118 (should resource names refuse id-shaped values), so it needs the same user decision. A likely shape: keep the slug rule for the generated resource id, and let the Blueprint `name` be a display name mapped onto it, as the dashboard's display names already are.
- **Dotted env keys** (`discovery.type`): bex refuses anything outside `[A-Za-z_][A-Za-z0-9_]*` (`core/config.go:129`). Kubernetes accepts dotted names in container `env`, and Elasticsearch reads them, so it may be safe to accept, but this needs checking against `envFrom` Secret projection and every consumer.
- **Guard:** `knownBlueprintGaps` in `lego/backend/internal/apps/blueprint_render_examples_corpus_test.go` lists both. Remove each entry when it ships, and the corpus test then holds the line.
- Source: w5/m143's corpus run (2026-10-20). Sizing: once decided, each half is about an hour; the naming half may promote to a milestone.
