## Objective

Postgres and Key Value names use one function and one max length, and every entry point calls it.

## Context

- `ValidDatabaseName`, `ValidKeyValueName` and `store.nameRE` encode the same rule.
- `lego/backend/internal/apps/deploy.go:2544` `parseKeyValue` never calls `ValidKeyValueName`; `parseDatabase` does (`:2464`). A Blueprint Key Value named `Cache_1` passes validate, then fails at CR create with an apiserver Invalid error that comes back as a 500.
- Service names accept ID-shaped names like `dpg-<20 chars>` (`specFromCreate`, `apps/service.go:2656`), and `AuthorizeApp` resolves by id first. So w8/049's name/ID ambiguity remains for services; refusing such names is a behavior change.
- A helper that also needs `internal/id` can't live in `core`, which is documented to import only CRD types. Use a small package such as `internal/resourcename` for the ID-shaped check.

## Steps

1. Add one `ValidResourceName` and an exported `MaxResourceNameLength` in `lego/types/v1alpha1`, replacing the three copies.
2. Call it from Blueprint `parseKeyValue`.
3. Decide on ID-shaped service names. Refusing them for new names only is a behavior change: ask the user first and record the decision.
