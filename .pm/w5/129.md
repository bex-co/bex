# Every kpack release leaves its Image behind for the App's lifetime

Why: a buildpack service gets one kpack `Image` per release revision. It is deleted only with the App (`build.ReclaimAppArtifacts`), while build Jobs expire an hour after they finish (`TTLSecondsAfterFinished: 3600`). So every list that counts builds grows with release history, and kpack rebuilds every live Image when the ClusterBuilder changes.

- **Costs:**
  - `build.ObservingAppBuild` lists the App's Images on every queued pass, every 30s;
  - `countActiveBuilds`, the census and `TrimOvershoot` list Images namespace-wide;
  - a ClusterBuilder update rebuilds every leftover Image. While those rebuild they count as active builds: they take cap slots, and `ObservingAppBuild` reports any App with one as observing.
- **Where:** `lego/operator/internal/build/kpack.go` (`kpackImageName` hashes the UID and revision) and `artifacts.go` (`ReclaimAppArtifacts`).
- **Fix:** once a release's Image has finished and its artifact is stored (the w5/108 success pass), delete this App's Images with any other `app.bex.co/build-revision`. Keep the one the release still needs, and do not delete an Image that is still building.
- **Test:**
  - after release 2's Image succeeds and its artifact is stored, release 1's Image is gone, and release 2's stays;
  - an Image of another App, or of a release still building, is left alone.
- Found by w5/119's efficiency review (2026-10-07).
