# Two more writes lose a reconcile pass's unsaved status

Why: w5/096 fixed the App metadata patches that discarded a pass's in-memory status. Two writes of the same kind remain.

- **Patches that land on a copy of the App.** `desiredReplicas` receives `effectiveApp`, a copy whenever a release config is selected or pending sources are kept (`lego/operator/internal/controller/release_config_selection.go`, `saved_configuration.go`). Its last-active stamp and autoscale patches land on that copy.
  - The pass's own `app` keeps the old resourceVersion, so its status write conflicts and the pass retries.
  - The `Status.Autoscaling` "Started" record set on the copy is lost.
  - Fix: patch and record on the pass's `app`, and only read from `effectiveApp`.
- **The Database major-upgrade-failed spec revert.** `database_controller.go` patches `spec.version` back on `db` itself, so the server's object overwrites status the pass has not written yet: `CurrentVersion` just read from the cluster, connection fields, exports, last backup. The Failed status write after it then saves the server's values. It heals on the next pass, and the branch is rare.
  - Fix: patch a copy under the read resourceVersion, as `patchAppMeta` does.
- Test: an App with a selected release config whose autoscaler stamps a scale-down keeps its status write. A failed major upgrade records the cluster's current version in its Failed status.
- Found by w5/096's reviews (2026-10-06).
