## Objective

Give every sandbox an enforced maximum lifetime, so that even when every session-side teardown path fails, a sandbox stops on its own. Decide and record what `timeoutSeconds: 0` means, because bex and the pinned client currently disagree.

## Context

- `validateCreateMetadata` (`lego/backend/internal/sandbox/service.go:160-173`) rejects out-of-range values with the message "sandbox timeoutSeconds must be 0 (no expiry) or between 60 and 86400". `minSandboxTimeout = 60`, `maxSandboxTimeout = 86400` (`service.go:48-49`).
- The value is stored as OpenSandbox metadata `bex.co/timeout-seconds` (`service.go:197`) and read back only for display (`service.go:321`). Nothing enforces it — `rg` over `lego/operator/internal` finds no consumer.
- The pinned Render CLI v2.27.0 documents the opposite default: `cmd/sandboxcreate.go:104` — "Maximum sandbox lifetime in seconds. 0 uses the default and maximum of 86400 (24 hours)" — and `pkg/sandbox/service.go:83-84` omits `timeoutSeconds` from the create body unless it is `> 0`. So the CLI's default path asks for the 24-hour cap and bex grants immortality.
- Live proof that nothing expires: sandbox `271ec9ce-a32b-4128-bb43-02a9e57b01b6` has `timeoutSeconds: 0` and has been `running` for 403 hours.

## Steps

1. Decide the semantics with the user's pricing intent in mind: either (a) `0` means the 86400 default/maximum, matching the pinned client and Render, or (b) `0` keeps meaning "no expiry" and becomes an explicit, documented bex divergence with a separate platform-wide ceiling.
2. Enforce whichever bound is chosen. Prefer a single enforcement point the reconcile in `t003` also reads, rather than trusting OpenSandbox metadata.
3. Return the **effective** bound (never a bare `0`) from the sandbox read shape on REST, GraphQL, and MCP so a caller can see when its sandbox will stop.
4. Record the outcome in `docs/ADR018-render-parity.md` and `docs/cli-compatibility-checklist.md` (the `ea sandbox create` row at line 270), and in `docs/ADR014-sandboxes.md`.

## Acceptance criteria

- [ ] A sandbox created with no `timeoutSeconds` stops automatically at the documented bound; a test drives the clock and asserts termination.
- [ ] The sandbox read shape returns the effective bound identically on REST, GraphQL, and MCP — never `0` as "unbounded".
- [ ] `bex ea sandboxes create` (no `--timeout`) against the fixed server produces a sandbox whose reported bound matches what the CLI's own `--timeout` help promises, or the divergence is written down in both docs with the reason.
- [ ] `SANDBOX_TIMEOUT_INVALID` still rejects negative and out-of-range values with its current coded 400.

## Out of scope

- Changing the `minSandboxTimeout`/`maxSandboxTimeout` bounds themselves.
- Sandbox snapshot and hibernation retention (ADR059 D5), which has its own window.
