# A write that empties the files map can drop the mount a later write added

Why: the App's files reference is not ordered by revision, so a write that empties the files map and stalls before its App patch removes the reference a later write patched in, and the pod stops mounting files the store and Secret both hold.

- The single-key verbs patch through `rollApp` (`rollout.Tracker.Patch`), and the batch through `finalizeEnvironmentPatch`. Both use `client.MergeFrom` with no optimistic lock, so a patch replaces `spec.filesFromSecrets` with the list computed from the App the writer read.
- The order:
  1. A deploying batch deletes the last file. It commits `{}` at 2, projects the empty Secret at 2, then stalls before its App patch.
  2. `SetSecretFile(g)` commits `{g}` at 3, projects it and patches the reference in.
  3. The batch's patch lands with the list it computed, without `<service>-files`.
- The store and the Secret then hold `{g}` at 3 while the pod mounts nothing, until the next files write. w5/106 closed the Secret's side of this order, not the reference's.
- A possible fix: the secrets writers patch with `client.MergeFromWithOptimisticLock` and re-run the mutate, projection included, on a conflict. `Tracker.Patch` is shared by every App-spec writer, so either scope the lock to these writers or check the others tolerate a retry.
- Test: the order above, with the App referencing the files Secret afterwards.
- Found by w5/106's quality review (2026-10-07).
