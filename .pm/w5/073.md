# MCP create drops `dockerCommand` for image services

Why: an MCP create with `runtime: "image"` and a `dockerCommand` silently creates the service without its command, so an image that needs one crash-loops. That is the failure REST was fixed for on 2026-10-04 (w4/188).

Source: Last-24h code review, 2026-10-05 (user handed all fixes to w5). REST fixed in `4fe79515b` (w4/188); MCP not. Code-verified.

## Mechanism

- `lego/backend/internal/apps/mcp.go:360` `resolveMCPDockerArgs` returns early unless `isDockerRuntime(runtime)`. For `image`, `dockerCommand` is neither applied nor refused.
- Its doc comment (`mcp.go:350`, "maps dockerCommand/dockerContext the way REST does") has been false since w4/188.
- The MCP schema says `startCommand` is "refused for runtime image" (`mcp.go:201`, `:292`), but `specFromCreate` accepts it (`apps/image_create_test.go:118`). So MCP documents no way to set an image service's command at all.

## Fix

1. Apply REST's w4/188 rule for `runtime: "image"` in `resolveMCPDockerArgs`: `dockerCommand` becomes the image's command. Keep `checkMCPDockerArgs`' refusal of ambiguous combinations.
2. Correct the `startCommand`/`dockerCommand` jsonschema descriptions for the image runtime, in both the web-service and cron tool inputs.
3. Tests: an MCP image create with `dockerCommand` stores the command; ambiguous combinations are still refused.

Done: the same image service created through REST and MCP yields identical spec commands.

Follow-up (not here): a guard that every create field reaches the service through every transport is [w5/m117](m117/README.md).
