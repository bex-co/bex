# 060 — `GET /v1/key-value?suspended=` is rejected by the OpenAPI validator, so the filter ADR018 documents is unreachable and its handler code is dead

Why: ADR018 claims Key Value list-filter parity that production does not have — the parameter 400s at the edge before the handler runs — so anyone trusting the ledger (or reading the handler) believes a filter exists that no client can use.

- **Severity:** minor (a documented capability is absent; no data or availability impact).
- **Attribution:** server (bex-api request-validation layer + an incorrect parity claim).
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-15 UTC, sweep 3. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, human device-login token, `render-cli/2.27.0` User-Agent.

## Reproduction

```text
$ GET https://api.bex.co/v1/key-value?ownerId=tea-…&suspended=suspended
HTTP/2 400
{"error":"request contains an unsupported query parameter","id":"bad_request","message":"request contains an unsupported query parameter"}

$ GET https://api.bex.co/v1/key-value?ownerId=tea-…&suspended=bogus
HTTP/2 400
{"error":"request contains an unsupported query parameter","id":"bad_request","message":"request contains an unsupported query parameter"}
```

Both values produce the **same** validator message, so the handler's own named 400 is never reached. Controls from the same run, same token, same host:

| request                                          | result                                                             |
| ------------------------------------------------ | ------------------------------------------------------------------ |
| `/v1/key-value?…&limit=2`                        | `200`                                                               |
| `/v1/key-value?…&environmentId=env-…`            | `200`, `[]`                                                         |
| `/v1/key-value?…&name=qa-20260915-4ce6fd-kv`     | `200`, one row                                                      |
| `/v1/postgres?…&suspended=suspended`             | `200`, `[]`                                                         |
| `/v1/postgres?…&suspended=bogus`                 | `400` `{"error":"invalid query parameter \"suspended\""}` — validator, schema-enum violation |

The Postgres pair is the discriminator: `/v1/postgres?…&suspended=suspended` returns `200`, so the parameter is admitted there and the filter runs; on Key Value **no** value is admitted.

Note on the two validator messages — they distinguish *kinds of schema violation*, not validator-vs-handler: `unsupported query parameter` means the parameter is absent from the path's schema, `invalid query parameter "x"` means it is present but the value violates its schema (`/postgres`'s `suspended` is `{"type":"array","items":{"enum":["suspended","not_suspended"]}}`). Neither reaches bex's handler. The handler's own `core.ParseEnum` message (`unknown suspended "bogus" (want suspended|not_suspended)`) is therefore unreachable for this parameter — tracked separately as `w5/063`.

## Root cause

The enforced request validator is pinned to Render's public OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`, refreshed by `w6/073`). Render's document lists `suspended` on `GET /postgres` but **not** on `GET /key-value`:

```text
/key-value  ['name','region','createdBefore','createdAfter','updatedBefore','updatedAfter','ownerId','environmentId','cursor','limit']
/postgres   ['name','region','suspended','createdBefore','createdAfter','updatedBefore','updatedAfter','ownerId','environmentId','includeReplicas','cursor','limit']
```

So the validator is behaving correctly and the divergence is on bex's side:

- `lego/backend/internal/keyvalue/rest.go:236` parses `suspended` via `core.ParseEnum("suspended", q.Get("suspended"), core.RenderSuspended, core.RenderNotSuspended)` and `:254` filters on it — **unreachable in production**.
- `docs/ADR018-render-parity.md:159` states: "**REST list filter parity (w2/m53):** `GET /v1/key-value` now supports `?environmentId=` (OR'd), `?suspended=suspended`|`not_suspended` (named 400 on unknown value) …". The `environmentId` and time-window half of that claim is true; the `suspended` half is not.

## Fix (~40m) — a decision, then one of two paths

Render genuinely does not offer this filter on Key Value, so parity and the claim cannot both stand.

- **(a) Keep it as a deliberate extension.** Add `suspended` to the bex-side allowlist the validator consults for `/v1/key-value` (the same seam that must already permit any other bex-only parameter), keep the handler, and relabel the ADR018 sentence as a bex **extension** rather than parity — the same framing the row already uses for the GraphQL/MCP string-list allowlist arguments. Confirm the intersection-enforcement gate from `w6/m96`/`w6/073` still holds for every other path.
- **(b) Drop it.** Delete the parse+filter at `rest.go:236,254`, correct the ADR018 sentence, and let an unknown parameter keep 400ing. GraphQL/MCP/dashboard callers must be checked first — if any of them relies on this filter, (a) is forced.

Check the same class on the sibling paths before choosing: any other query parameter bex parses but Render's document omits is dead the same way.

## Blast radius

`rg` for `core.ParseEnum("suspended"` and for query parameters parsed in `internal/*/rest.go` that are absent from the pinned document. GraphQL (`keyValues`) and MCP (`list_key_value`) do not go through the REST validator, so they may expose a filter REST cannot — worth asserting either way.

- Keep `/v1/postgres?suspended=bogus` → handler-named 400 as the control.
- Whichever path is chosen, `docs/ADR018-render-parity.md:159` matches reality.

## Dedupe

`rg` over open and `done/` `.pm` for `unsupported query parameter` and the key-value suspended filter returns no match. `w6/073` (validator pin refresh) and `w6/m96` (Blueprint-ID guards) touch the validator but not this parameter. The CLI compatibility checklist grades `keyvalues suspend` (line 105) as the **verb**, not the list filter.
