# Creating a service whose deleted namesake's Secrets await garbage collection answers 500

Why: create-time preparation creates the new service's `<service>-env` / `<service>-files` Secret before the App exists. When a deleted service of the same name left its Secret for garbage collection, `prepareProjection`'s `Create` meets `AlreadyExists` and rolls the store write back. The create then fails with the raw Kubernetes error, which bex-api answers as a 500 "internal error", until GC catches up.

- **Where:** `lego/backend/internal/secrets/files.go` `prepareProjection`, and `adoptPreparedSecret` after it.
- **Fix:** on `AlreadyExists`, take the name over only when the existing Secret is controlled by an App that no longer exists:
  - read the App by name, and replace the Secret only if it is absent or has another UID;
  - rewrite it ownerless with this create's map and revision, for adoption as today.
  - Leave anything else alone: a live App's Secret, or another create's prepared, ownerless one. That create must still fail, with a coded conflict rather than a 500.
- **Context:** w5/118 made post-create writes replace a predecessor's Secret (`controlledByAnother` in `projection.go`). This is the create-time half.
- **Test:**
  - a create that carries files, while the deleted namesake's Secret is still present, succeeds, mounts only its own files, and owns the Secret;
  - a Secret controlled by a live App, or an ownerless one, still refuses the create, with a 409.
- **Related:** `apps` `writeNewApp` returns on a prepare failure without aborting. When the env leg fails after the files leg, the prepared ownerless `-files` Secret and its store map are left behind. Run `AbortCreateSecrets` on that path too.
