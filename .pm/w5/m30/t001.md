## Objective

Provide narrow, authorized GraphQL mutations that the dashboard can use to change or clear `startCommand` and `dockerfilePath` without replaying the broad `createService` create-or-update mutation.

## Context

- `lego/backend/internal/apps/service.go` already has authorized `SetCommands`; reuse its `startCommand` path rather than duplicating command semantics.
- There is no equivalent narrow setter for `DockerfilePath`; add one using `AuthorizeApp`, `store.ValidRootDir`, and `patchFetched`, with repo/Docker-runtime applicability checks.
- `lego/backend/internal/apps/graphql.go` exposes both fields for reads and `createService`, but currently exposes no safe dashboard setting mutation for either field.
- Match the error and scalar-argument conventions of `setRootDir` and `setPreDeployCommand`.

## Steps

1. Add a service-layer Dockerfile-path setter with authorization, trimming/validation, clear semantics, and explicit rejection for inapplicable services; preserve legacy `builder: dockerfile` Apps whose runtime is empty.
2. Expose `setStartCommand` and `setDockerfilePath` GraphQL mutations that delegate to the shared service methods.
3. Add resolver/service tests for set, clear, unauthorized, invalid-path, and wrong-runtime cases.

## Files

- `lego/backend/internal/apps/service.go`
- `lego/backend/internal/apps/graphql.go`
- `lego/backend/internal/apps/*_test.go`

## Acceptance criteria

- [ ] Both mutations set and clear the intended `App.Spec` field and return the updated service.
- [ ] A caller lacking `can_operate` cannot mutate either field.
- [ ] Dockerfile paths containing absolute or `..` components are rejected, and the Dockerfile mutation rejects non-repo/non-Dockerfile-built services while accepting legacy `builder: dockerfile` Apps.
- [ ] Existing REST, MCP, and create-service behavior remains green.

## Out of scope

- Adding a general-purpose `updateService` mutation or changing operator build/command behavior already shipped by `w6/m21`.
