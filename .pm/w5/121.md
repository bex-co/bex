# Two cron status patches replace a pass's unsaved release decision

Why: w5/096 and w5/110 stopped writes from replacing status a pass had set but not yet written. Two cron paths still `Status().Patch` the pass's own App, and the server's stored status replaces the release decision the pass holds in memory.

- `acknowledgeManualRun` (`lego/operator/internal/controller/cron_manual_intent.go`) and `preemptOtherCronRuns` (`app_controller.go`) call `r.Status().Patch(ctx, app, client.MergeFromWithOptions(before, client.MergeFromWithOptimisticLock{}))` inside `reconcileCronJob`.
- By then the pass holds unsaved status:
  - the release decision from `prepareAppReleaseDecision`: `ReleaseFingerprint`, `ReleaseArtifactFingerprint`, `ReleaseGeneration` and `PendingReleaseGeneration`;
  - the artifact identity `resolveDeployImage` set.
- Each `before` snapshot is taken just before its patch, so those fields are not in the patch, and decoding the response puts the stored values back into `app`.
- Fix: patch a copy, as `patchAppMeta` does for metadata, and carry back only the fields the patch changed plus the resourceVersion.
- Guard: `TestPassesPatchTheirAppOnlyThroughPatchAppMeta` (`metadata_patch_test.go`) skips `Status().Patch` and matches only the identifier `app`. Extend it to status patches, and to `db` and `kv`, so the next one fails the build.
- Test: a cron pass with a new release decision acknowledges a manual run, and the release decision is stored at the end of the pass.
- Found by w5/110's reuse review (2026-10-07).
