## Objective

Implement the canonical mapping used by live and historical instance consumers, with explicit compatibility for already-issued live IDs and existing raw-name log filters.

## Context

- apps.ListInstances and SSH targets call id.DeriveServiceInstance with podInstanceIdentity, which prefers pod UID.
- Metric and log history exposes pod names without a live Pod object; datastore ordinal names can be reused after replacement.
- The approved scope absorbs both w4 notes and must establish one shared rule before either package changes.

## Steps

1. Trace the live, historical, and input-resolution identity requirements for App, Postgres, and Key Value resources.
2. Implement the smallest shared mapping in internal/id or an appropriate leaf seam; preserve resource scoping and document the chosen UID/name compatibility.
3. Define deterministic behavior for deleted pods, reused names, ambiguous inputs, and legacy selectors; bounded resource-scoped lookup is required if translation needs discovery.

## Files

- `lego/backend/internal/id/id.go`
- `lego/backend/internal/apps/service.go`
- `docs/ADR020-identifiers.md`
- `docs/ADR010-observability.md`

## Acceptance criteria

- [ ] A live pod and its retained history can resolve to a stable public identity under the documented mapping.
- [ ] Existing live IDs have an explicit compatible resolution path; ambiguous or foreign selectors cannot choose another pod.
- [ ] All resource IDs continue to use internal/id; no operator/backend dependency violation is introduced.

## Out of scope

- A new resource-identity product or global cross-tenant lookup service.
- Blindly replacing UID hashing with name hashing without handling compatibility and pod-name reuse.
