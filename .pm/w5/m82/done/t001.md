## Objective

The gateway's Git smart-HTTP proxy forwards a gzip-compressed `git-upload-pack` request body to GitHub intact **with** its `Content-Encoding: gzip` header, so clone/fetch negotiation bodies over git's 1 KiB gzip threshold (any repo with ~20+ refs) stop failing 400-upstream → 502 "git upstream refused request".

## Context

- Root cause of production session `ags-da9l9e5a801s739cb2ig` failing: `lego/backend/internal/sshgateway/agentcred/agentcred.go:243` forwards only `Accept`, `Content-Type`, `Git-Protocol` upstream; git gzips any smart-HTTP RPC body > 1 KiB (`remote-curl.c` `post_rpc`), so the pack-fetch POST arrives at GitHub as gzip bytes labeled plain → GitHub 400 → gateway 502 (`agentcred.go:257`) → git `RPC failed; HTTP 502 … expected 'packfile'`.
- Verified: POSTing a gzipped upload-pack body to `github.com/<repo>.git/git-upload-pack` without the header returns 400; with `Content-Encoding: gzip` returns 200. `bex-co/bex-security` clone fetch body: ~40 KiB raw (887 refs), sent gzipped; `bex-co/bex`: 574 bytes, sent plain (why it worked).
- Scope the header forward to `git-upload-pack` POSTs (and harmless on `info/refs` GETs, which carry no body). Do **not** blindly forward it for `git-receive-pack` — `validateReceivePack` parses the raw body; t002 owns that path.
- `request.ContentLength = r.ContentLength` (`agentcred.go:240`) already carries the compressed length correctly.

## Steps

1. In `serveGit`, forward the client's `Content-Encoding` header upstream for the upload-pack service (extend the allowlist conditionally on `service != "git-receive-pack"`, or handle receive-pack in t002's decompression seam).
2. Ensure Go's transport doesn't transparently interfere (body is passed as an opaque reader; no decompression happens on request bodies — confirm with the test).
3. Unit test against a stub upstream (`UpstreamOrigin` test seam): gzipped POST with `Content-Encoding: gzip` reaches the upstream with the header and byte-identical body; plain POST unchanged.
