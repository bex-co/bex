# Listing members rewrites each member's owner-id row

Why: the Team page polls `workspaceMembers` every 30s, and each poll writes one Postgres row version per member, only to read ids that already exist — the same no-op upsert w5/087 removed from the sandbox key.

- `store.PGStore.OwnerIDForSubject` (`lego/backend/internal/store/workspaces.go:276`) mints a candidate `own-` id and runs `INSERT … ON CONFLICT (subject) DO UPDATE SET subject = EXCLUDED.subject RETURNING own_id`. The no-op `DO UPDATE` is what returns the stored id, and it writes.
- It runs once per member inside two list loops: GraphQL `workspaceMembers` (`internal/members/service.go:504`, polled by the dashboard's Team page every 30s, `dashboard/src/features/team/hooks/use-team.ts`) and REST `GET /v1/owners/{ownerId}/members` (`internal/workspaces/service.go:854`). So each list is N round trips and N row versions.
- Fix: read first and upsert only a miss, as w5/087 did. Better, resolve a whole list with one `SELECT … WHERE subject = ANY($1)` and mint only the misses.
- Test: a Postgres test that listing twice leaves the `owner_ids` rows' `xmin` unchanged.
- Found by the reuse review of w5/087.
