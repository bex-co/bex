# Pick one answer for a named workspace that does not hold the id

Why: a member who names the wrong workspace gets 403 from some by-id families and 404 from others, so ADR072's by-id matrix carries a split row where w5/m115 promised one rule.

- **Today.** Apps, Postgres and Key Value refuse the cross-workspace reach with 403, audited in the named workspace (`core.Base.resourceWorkspaceFor`, `lego/backend/internal/core/base.go:1613`, w6/m14). API keys do the same (`apikeys.RevokeAPIKey`). Both are locked by `TestReadSideOwnerIDTargetingE2E` and `TestActionCapabilitiesGraphQLWorkspaceSelection`. The store-backed families (env groups, registry credentials, webhooks, Blueprints, environments) look only in the named workspace and answer 404.
- **A third answer: ignore the named workspace.** `environments.List` (`lego/backend/internal/environments/service.go:438`, via `requireProject`) and `projects.authorizedProject` (`lego/backend/internal/projects/service.go:273`) read the project by id and authorize on its own workspace. Naming `tea-a` for a `tea-b` project lists `tea-b`'s environments (200), where the matrix's by-parent-id row says 404. A caller still needs the relation in `tea-b`, so this isn't an escalation, but it's the same question. Found by w5/m115's review.
- **The same split, unresolved upstream.** w4/m172's DoD says a mismatched `ownerId` "answers like the non-member case" (403); its workstream README line says 404. Its live probes run on store-backed families, which answer 404.
- **Decide.** 403 everywhere follows ADR072 #8's reasoning (a member of several workspaces learns that access, not existence, is the problem), but each store-backed verb then needs an unscoped existence read. 404 everywhere changes w6/m14's gate and its e2e. Record the choice in the ADR072 matrix row and in w4/m172's probe expectations.
