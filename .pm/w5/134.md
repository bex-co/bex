# A refused service create overwrites, then deletes, its namesake's secrets store map

Why: create-time preparation writes the new service's env and files maps into the store at the service's path before it creates the projection Secret, and deletes the path when that Secret is refused. The path is keyed by workspace and service name, so in a concurrent create of the same name, the refused request first overwrites the other's store map and then deletes it, leaving the surviving service's Secret without its source of truth.

- **Where:** `lego/backend/internal/secrets/files.go` `prepareProjection`: `updateMapCAS` (clear + copy) runs before `createPreparedSecret`; on `errSecretNameHeld` the store path is deleted. `storeServiceName` keys the path by the service name label, so namesakes share it.
- **Reach:** two creates of the same service name in one workspace within the prepare window; the store's name check normally refuses the second create earlier (w5/128 found this while scoping the abort).
- **Fix:** check the Secret's holder before the store write (refuse a held name without touching the store), or make the store write conditional on the path being absent or a purge's leftover.
- **Test:** a create refused because another create holds the Secret leaves the other's store map exactly as it was.
- Found while closing w5/128 (2026-10-07).
