# Deleting an App deletes the images of a workspace sibling named `<app>-cache`

Why: an App's build-cache repository is `<repo>-cache`, which is also the image repository of an App named `<name>-cache` in the same workspace. Deleting App `web` deletes every image App `web-cache` pushed, so `web-cache` can neither pull its image on the next pod start nor roll back.

- **Where:** `lego/operator/internal/identity/identity.go` `CacheRepo` (`Repo() + "-cache"`, w7/m86). `controller/app_controller.go` `deleteRegistryRepo` deletes `id.CacheRepo()` unconditionally. `registry/creds.go` grants each App's Zot user exclusive access to `Repo()` and `CacheRepo()`, so the two Apps keep taking that repository from each other. With `BEX_BUILD_CACHE` on, `web`'s BuildKit cache lands in `web-cache`'s image repository and uses up its retention.
- **Fix:** name cache repositories so no App name can produce them, e.g. with a character or path segment App names cannot contain. Existing caches may go cold rather than stay shared. Until then, deletion skips a cache repository another App owns as its image repository. Refusing App names that end in `-cache` is a naming-rule decision (see m118).
- **Test:** deleting App `web` leaves App `web-cache`'s image repository and its Zot grant alone.
- Found by w5/m134's quality review (2026-10-07). w5/m134 keeps kpack's cache in the image repository partly because of this.
