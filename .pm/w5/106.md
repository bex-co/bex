# A deleted secret-files Secret records no revision, so a late projection can recreate it

Why: w5/m127 orders every projection by store revision, but deleting a service's last secret file deletes its `<service>-files` Secret, and a Secret that no longer exists records nothing for a late projection to lose to.

- The order:
  1. The store holds `{f}` at version 1.
  2. `SetSecretFile(f, x)` commits `{f: x}` at version 2, then stalls before it projects.
  3. `DeleteSecretFile(f)` reads version 2. It deletes the Secret, drops `spec.filesFromSecrets` and commits `{}` at version 3.
  4. The stalled write finds no Secret. It creates `{f: x}` at version 2 and adds the reference back.
- The pod then mounts a file the store no longer holds, after the delete answered success.
- The window predates m127. m127 closes it for every Secret that still exists.
- A possible fix:
  - Keep an emptied files Secret as an empty Secret stamped with its revision, still unreferenced, so no empty `/etc/secrets` mount appears.
  - Have `projectFiles` leave the App reference to the later write when its projection is superseded.
- That changes a pinned contract: `TestSecretFiles_RoundTripAndProjection` expects the Secret gone after the last delete, and ADR013 says it is "deleted when the last file goes away".
- Test: the four-step order above, with the pod's Secret and reference matching the store afterwards.
- Found by w5/m127 (2026-10-06).
