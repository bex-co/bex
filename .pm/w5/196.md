# The deploy job restarts the operator a second time after Argo already rolled it to the new digest

Why: every deploy that changes the operator image restarts it twice, two leader handovers and two fleet sweeps where one would do (w5/m370 t002 counted 50 operator pod creations in 71 h, in 25 pairs one to three minutes apart).

- **Evidence (production, 2026-11-16 to 2026-11-19, read by w5/m370 t002):** the two ReplicaSets of each pair differ only in `kubectl.kubernetes.io/restartedAt`. The second comes from `.github/workflows/deploy.yml`, step "roll bex onto the freshly-pushed image": `kubectl -n bex-system rollout restart deploy/bex-controller-manager deploy/bex-api`. Its comment says the Deployment runs a mutable `:latest`, but `deploy/gitops/base/bex.yaml` pins `controller=ghcr.io/bex-co/bex-operator@sha256:…`, so Argo already rolls the operator on every pin commit; the restart then re-pulls the same digest. w8/248 found and removed the same redundant restart for OpenSandbox's server (deploy.yml `opensandbox_converged`).
- **Cost once w5/m370 t003 is deployed:** each restart is a handover of about 2 s with no App reconciled and a sweep of the whole fleet (about 75 s at 29 Apps) that a tenant's change now jumps; the first sweep is cut off by the second restart. Before t003 each restart cost 14 to 21 s with no leader plus that sweep.
- **Check before removing it:** whether anything relies on the restart to reach the operator. A Secret or ConfigMap the manager reads only at start (an `env` `secretKeyRef` or `envFrom` in `lego/operator/config/manager/manager.yaml` or the prod overlay) that an earlier deploy step writes would stop reaching it. Then either restart only when such an input changed, or only when the Deployment has not converged on the pinned digest, as the OpenSandbox step does. bex-api's restart is out of scope here unless the same reasoning holds for it.
- **Paths:** `.github/workflows/deploy.yml` (the roll step), `deploy/gitops/base/bex.yaml`, `lego/operator/config/manager/manager.yaml`, `lego/operator/config/prod/`.
- **Done when:** over a day of deploys that change the operator image, production shows one operator pod creation per deploy (`kube_pod_created{namespace="bex-system",pod=~"bex-controller-manager-.*"}`), the deploy job still waits for the operator to run the pinned digest, and a deploy step that rewrites an operator-read Secret still reaches the running manager.
