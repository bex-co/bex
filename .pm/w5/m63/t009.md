## Objective

Fix the correctness bug ADR050 §Recovery flow identifies: `restore-postgres.sh` currently clones the source ObjectStore's own Secret verbatim into the recovery namespace, which breaks the moment that Secret becomes write-only (t007). Point it at the new `<store>-backup-reader` credential instead.

## Context

- `docs/ADR031-platform-data-backup.md` §Restore runbooks: "It clones the source ObjectStore and only its referenced credentials into a new namespace, creates a one-instance recovery Cluster without a backup/WAL-writer plugin…"
- SSE-S3 (t005) decrypts transparently on `GetObject`, so this task needs no decrypt step — only a credential-source change.
- This is a **required** change, not optional: once t007 lands, an unmodified `restore-postgres.sh` will fail every Postgres restore with 403, silently breaking a previously-working script.
- Applies uniformly to all `restore-postgres.sh` invocations: `bex-db`, tenant Postgres Databases, and the three auth DBs (`kratos-db`, `hydra-db`, `openfga-db`) all share this one script.

## Steps

1. Locate where `restore-postgres.sh` builds the recovery Cluster's `externalClusters[].plugin` Secret (currently cloning the source ObjectStore's Secret).
2. Change it to source the `<store>-backup-reader` credential (from `.env`, per t007's naming) instead of cloning the in-cluster writer Secret.
3. Re-run the script's existing `DRY_RUN=1` path against a real ObjectStore to confirm the recovery Cluster can `GetObject`/`ListBucket` its base backups and WAL with only the reader credential.

## Files

- `scripts/restore-postgres.sh`

## Acceptance criteria

- [ ] `restore-postgres.sh` no longer reads or clones any `*-backup-s3` writer Secret.
- [ ] A confirmed restore (`--confirm …`) succeeds for at least one tenant Database and for `bex-db`, using only the reader credential.
- [ ] Re-running the auth-DB restore example from `docs/ADR031-platform-data-backup.md` (`kratos-db`) succeeds unchanged in outcome (same row count / marker present).

## Out of scope

- Any change to CNPG's own recovery mechanics (`bootstrap.recovery`, `externalClusters`) beyond the credential source.
- The live cross-store drill (t010).
