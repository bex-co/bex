## Objective

Replace the shared `TF_STATE_ACCESS_KEY`/`TF_STATE_SECRET_KEY` currently installed in `etcd-backup-s3`, `openbao-backup-s3`, `bex-db-backup-s3`, `auth-dbs-backup-s3`, and `bex-kv-backup-s3` with each store's new write-only credential from t006, and install the five read-only credentials out-of-band for restore scripts to consume.

## Context

- `docs/ADR031-platform-data-backup.md` §One-time setup per cluster lists exactly these five Secret-creation commands, all currently sourcing `$TF_STATE_ACCESS_KEY`/`$TF_STATE_SECRET_KEY`.
- This is the task that actually closes the credential-sharing gap ADR050 exists to fix — t002-t005 (encryption) are defense-in-depth on top of this, not a substitute for it.
- Do this store by store, verifying each CronJob/plugin still succeeds with the new writer credential, before moving to the next — a broad simultaneous swap risks silently breaking all five backup paths at once with no single clear failure signal.

## Steps

1. For each store, run `scripts/backup-s3-credentials.sh provision` (t006) to mint the writer/reader pair if not already done.
2. Replace the Secret's `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` with the new writer credential's values (`kubectl create secret generic … --dry-run=client -o yaml | kubectl apply -f -`, or delete+recreate — never leave the old and new values both live in etcd for that Secret).
3. Trigger a manual backup run for that store (`kubectl create job --from=cronjob/…`, or an on-demand CNPG `Backup`) and confirm success before moving to the next store.
4. Record each store's reader credential in the operator's `.env` (out-of-band, never installed as a cluster Secret) under a clearly-named variable per store.
5. Once all five are confirmed on writer credentials, run `scripts/backup-s3-credentials.sh revoke-legacy` to confirm no live Secret still references `TF_STATE_ACCESS_KEY`/`TF_STATE_SECRET_KEY`.

## Files

- No new files; mutates the five in-cluster Secrets and the operator's `.env`.

## Acceptance criteria

- [ ] All five Secrets (`etcd-backup-s3`, `openbao-backup-s3`, `bex-db-backup-s3`, `auth-dbs-backup-s3`, `bex-kv-backup-s3`) hold their own store-scoped writer credential, not the TF-state root credential.
- [ ] A manual backup trigger succeeds for every one of the five stores post-migration.
- [ ] Five reader credentials exist in `.env`, none installed as in-cluster Secrets.
- [ ] `scripts/backup-s3-credentials.sh verify` passes for all five stores.

## Out of scope

- Wiring the reader credentials into the restore scripts (t008/t009) — this task only provisions and records them.
