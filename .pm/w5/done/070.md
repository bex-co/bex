# The cron schedule editor hangs the browser tab on a zero step (`*/0`)

Why: editing an existing schedule from `*/30` to `*/15` passes through `*/0 * * * *`, and the never-fires check loops forever on it: the tab freezes, then crashes, and the edit is lost.

Source: Last-24h code review, 2026-10-05 (user handed all fixes to w5). Regression from `299767929` (w4/197). Reproduced in Node: `cronNeverFires("*/0 * * * *")` used ~2.4 GB, then threw `RangeError`; `0 0 1-99999999 * *` took 4.7 s.

## Mechanism

- `dashboard/src/features/services/lib/cron.ts:117` `expandRange` loops `for (let v = start; v <= end; v += step)`. `parseUint("0")` returns `0`, so a zero step never advances. Huge ranges (`1-99999999`) and integers ≥ 2^53 have the same unbounded shape.
- `cronNeverFires` (`cron.ts:143`) expands fields without validating them. Both callers pass unvalidated text:
  - `features/services/components/cron-deploy-section.tsx:83` calls it _before_ `isValidCron`, inside a `validate` that `features/services/components/editable-field-row.tsx:153` runs on every render while editing (every keystroke).
  - `routes/services.new.tsx:350` calls it exactly when the schedule failed `isValidCron`.
- Same cause, second symptom: `* * 32 * *`, `* * * 13 *`, `5-2 * * * *` and `0 0 99 2 *` show "This schedule never fires" instead of the format error.
- `lego/backend/internal/apps/testdata/cron-schedule-vectors.json` already has a `*/0 * * * *` row, but `cron.test.ts` only runs rows through `isValidCron`, which rejects them before any expansion.

## Fix

1. Replace `cronNeverFires` with `cronScheduleProblem(s): "format" | "never_fires" | null`. It parses every field first (`validRange`) and only expands validated, bounded input.
2. Switch both call sites on the result (format copy vs never-fires copy).
3. Tests: every vector row goes through `cronScheduleProblem`, not only `isValidCron`; explicit `*/0`, huge-range and out-of-range-field cases assert the format verdict and finish promptly.

Done: typing `*/0 * * * *` in the Settings schedule editor and the create wizard shows the format error without freezing; the four mislabeled inputs show the format error; `yarn test` green.

Follow-up (not here): the shared vectors gain a `code` column asserted by Go and TS in [w5/m118](m118/README.md) t001.

**Done 2026-10-05.** `cronScheduleProblem` (`dashboard/src/features/services/lib/cron.ts`) parses every field before expanding any, returning `"format"`, `"never_fires"` or null. `isValidCron` wraps it, and both the Settings editor and the create wizard switch on it, so `*/0 * * * *` and the four mislabeled inputs show the format error without freezing. `parseUint` also no longer backtracks quadratically on pasted zero runs.
