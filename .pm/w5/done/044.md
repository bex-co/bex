# Bug: Key Value metrics page passes display name, not typed id — all charts empty

Symptom: `/keyvalue/red-…` disk/memory/connections charts all render "No data in range" (reported on prod `red-d9p49kdrtmes73c34ovg`, 2026-08-17).

Root cause: `dashboard/src/routes/keyvalue.$keyValueId.tsx:155` passes `resource={keyValue.name}` (the human display name, GraphQL `Name: kv.Spec.Name`) to `DatastoreMetricsPanel`, but bex-api resolves `datastoreMetrics.query.resource` as the KeyValue **CR name** = the typed id (`red-…`): `findKeyValue` matches only `metadata.name` (`lego/backend/internal/core/base.go:1097`). The lookup misses → NotFound → GraphQL error → the panel's `errorPolicy: "all"` swallows every error except the exact `"metrics source not configured"` into the empty-chart state. Every sibling uses the id: the Postgres page passes `database.id` (`databases.$databaseId.tsx:166`), and this page's own log viewer passes `keyValue.id` (`:138`). REST/MCP surfaces are unaffected (they take the id). Broken since the panel was introduced in `a5cf1f75` (w3/m10) — never worked.

Fix: one line — `resource={keyValue.id}`. Optional hardening (separate small change): in `lego/backend/internal/metrics/datastore.go`, after `AuthorizeKeyValue` resolves the CR, use `kv.Name` (not the raw `q.Resource`) for the PromQL pod/PVC matchers, so a name-shaped input can never silently produce empty series again.

Verify: devtools on a keyvalue page → `DatastoreMetrics` responses currently carry `keyvalues.app.bex.co "<name>" not found` with `data: null`; after the fix the same queries return series. Add a route test asserting the panel receives `keyValue.id` (mirrors the Postgres page).
