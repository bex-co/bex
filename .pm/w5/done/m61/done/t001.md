## FINDING (2026-07-30): the panels already exist — milestone already-satisfied

The design probe reveals the premise is stale: **both datastore detail pages already ship a mounted, feature-complete Logs panel.** No new panel is warranted.

- **Databases page** — `databases.$databaseId.tsx:142` renders `<PostgresLogViewer resource={database.id} />` on the `?tab=logs` tab.
- **Key Value page** — `keyvalue.$keyValueId.tsx:127` renders `<KeyValueLogViewer resource={keyValue.id} />` on the `?tab=logs` tab.
- Each viewer (`features/databases/components/postgres-log-viewer.tsx`, `features/keyvalue/components/key-value-log-viewer.tsx`) has: a range select (1h/6h/24h), an instance filter (from `useLogLabelValues`), a debounced text search, `LogLineList` row rendering, and every honest non-happy state — **store-unavailable** (`result.unavailable` → EmptyState), unauthorized, error, loading, and empty (with filtered-vs-unfiltered copy). This meets and exceeds the DoD.

**Why `databaseLogs`/`keyValueLogs` are (correctly) unconsumed:** the viewers use the shared service `Logs` operation (`usePostgresLogs`/`useKeyValueLogs` → `LogsDocument`), and the backend `logs` verb **routes `dpg-`/`red-` ids** to `queryDatabaseLogs`/`queryKeyValueLogs` internally (`internal/logs/service.go:434-438`) — the **same service code** the dedicated `databaseLogs`/`keyValueLogs` GraphQL fields call. So the panels already render true database/keyvalue log lines with identical data + store-gating; the dedicated GraphQL fields are redundant parallel reads. Consuming them would be pure churn (identical data, more code, splice work, zero user benefit) — a regression in effort/risk. Same class of stale-miner finding as `w5/m60` t003 (`setNotifyOnFail`).

**Decision:** close the milestone as already-satisfied; write no code. One minor, non-blocking consistency observation filed as inbox note `030` (the datastore viewers' 1h/6h/24h presets predate the shared m56 range ladder the service Logs tab uses).
