# Env group `serviceLinks` are Render's `{id, name, type}` objects on REST and MCP

Why: Render's env group returns `serviceLinks` as `envGroupLink` objects, while bex returns bare id strings. A Render client that decodes the documented shape fails on bex's.

- **Render:** `envGroupMeta.serviceLinks` is an array of `envGroupLink` with required `id`, `name` and `type` (`serviceTypeShort`) ([retrieve env group](https://api-docs.render.com/reference/retrieve-env-group), checked 2026-10-06).
- **bex:** `EnvGroupView.ServiceLinks []string` (`lego/backend/internal/envgroups/service.go`). Since w5/m120 every entry is a `srv-` id on REST, GraphQL and MCP, so the objects can be built from the linked Apps.
- **Fix:** the REST and MCP views return `{id, name, type}` per link, resolving each id to its App once per read and dropping a link whose service is gone. GraphQL stays the dashboard's contract (ids, names rendered client-side) unless the dashboard moves to the objects. The create and patch results' `pendingServiceIds`, `affectedServiceIds` and `failedServiceIds` stay ids, which Render has no counterpart for.
- **Test:** a REST GET of a linked group decodes into Render's schema (`id`, `name`, `type` present), and MCP matches it.
- **Size:** about an hour (view, REST, MCP, tests); found in w5/m120's Render parity check.

## Done (2026-10-06)

- REST and MCP answer `serviceLinks` as Render's `envGroupLink` objects. That covers get, list, create, rename, move and clone, plus the MCP tools.
- Each object holds the service's id, the name its own view shows (its display name when set), and Render's short type. The short type comes from `resourcemeta.ServiceTypeShort`, the table Render's dashboard routes already used; it spells a static site `static`.
- GraphQL still lists the stored ids, and `EnvGroupView` no longer serializes them.
- A link whose service is gone, or is being deleted, is left out.
- Only a linked group lists the workspace's services.
  - A read whose list fails fails.
  - A write has already committed by then, so it answers its links empty and logs the failure. A create would otherwise report a failure that a retry cannot repeat.
- Found on the way: the pinned Render CLI decodes `serviceLinks` as `[]EnvGroupLink`, so a linked group used to break it.
- `core.AppPublicName` and `core.DisplayedAppName` replace four copies of the same name fallback.
- Tests:
  - every group-returning REST route and MCP tool is checked against Render's pinned `envGroupLink` schema;
  - the read/write failure split;
  - an unlinked group renders without listing services;
  - the wired-server unlink test reads the stored ids through GraphQL, so it can fail again.
- 11 mutants, each killed.
