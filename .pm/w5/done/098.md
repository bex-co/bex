# A Blueprint resource conflict names its kind in display text, not the manifest kind

Why: the takeover dialog maps the conflict's kind to a localized label, and today it must accept bex-api's display spelling `"key value"` as a lookup key, so rewording that text would leave zh users an untranslated kind again.

- **Where:** `lego/backend/internal/apps/blueprint_ownership.go` records the claim kind as `"key value"` (~`:121`) and maps `key_value` to it (~`:218`) before it reaches GraphQL `extensions.kind`. The dashboard accepts both spellings in `dashboard/src/features/blueprints/lib/kind-labels.ts` (`KIND_LABEL`), and `"database"` likewise.
- **Fix:** put the manifest kind (`service`, `postgres`, `key_value`, `env_var_group`) in `extensions.kind` and keep the display wording in the message only; then drop the display-text keys from `KIND_LABEL`. Check REST and MCP carry the same field.
- **Size:** about 30 minutes. Found by w5/m125's quality review.

**Result (2026-10-07):**

- `BLUEPRINT_RESOURCE_CONFLICT`'s `kind` param is now the manifest kind plan actions use: `service`, `postgres` or `key_value`. REST carries it in `params.kind` and GraphQL in `extensions.kind`; MCP carries the message only.
- The message keeps its wording, as in `key value "cache"` and `database "orders"`.
- Every refusing path records the claim kind and maps it in one place, `blueprintClaimResourceKind`, which also replaces detach's inline copy.
- The claim-or-conflict step is one helper, shared by the apply's claim and the post-apply stamp. The stamp's message used to read `key_value "cache"`.
- The dashboard's `KIND_LABEL` drops its display-text keys.
- **Tests:** `TestBlueprintResourceConflictNamesTheManifestKind` pins the kind and wording on the ownership scan, the durable claim and the stamp; six mutants each fail it. Dashboard lint and tests pass: 481 files, 4348 tests.
- **Docs:** ADR049 records the params.
- **Follow-ups:** w5/114, w5/115.
