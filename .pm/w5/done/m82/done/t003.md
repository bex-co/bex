## Objective

Every 502-returning path in the Git proxy's `serveGit` logs an attributable one-line reason (session, repo, service, upstream status / error class — never the token or Authorization header), so the next upstream failure is diagnosable from `kubectl logs` instead of requiring a DB audit-trail reconstruction.

## Context

- All five `StatusBadGateway` sites in `lego/backend/internal/sshgateway/agentcred/agentcred.go` (mint failure :227, upstream URL :232, request build :237, `Do` error :250, upstream non-200 :257) emit nothing; during the `ags-da9l9e5a801s739cb2ig` diagnosis the gateway pods' only line was the startup banner. bex-api's mint log (`mint.go:99`) exists precisely because the same opacity hid a w3/m43 failure — extend that lesson to the gateway side.
- The `sshgateway.Metrics` seam already carries counters (`Authentication`, `LimitRejected`); add an upstream-outcome counter (e.g. labeled `do_error` / `non_200`) alongside the logs if it fits the existing metrics shape — follow the conventions in `lego/backend/internal/sshgateway/`.
- Never log credentials, the mint response, or raw request bodies. Upstream status code + `service` + verified session/repo identifiers are safe (they're already in audit_events).

## Steps

1. Add `log.Printf` lines at the five 502 sites carrying: session id, repository, service, and the upstream status code or error class.
2. Add/extend a gateway metric for upstream git-proxy failures if the `Metrics` type has a natural home for it.
3. Unit-assert the non-200 path produces the log line (capture via `log.SetOutput` or the package's existing test pattern).
