# Blueprint ownership checks query one resource at a time, and an apply lists datastores twice

Why: every Blueprint read and apply pays one Postgres round trip per declared resource for ownership, and an apply lists the workspace's datastores twice. The dashboard polls a Blueprint's detail, so the read side runs continuously while the page is open.

- **One owner query per resource.**
  - `blueprintOwnershipConflicts` (`lego/backend/internal/apps/blueprint_ownership.go`, its `ownerOf`) calls `GetBlueprintResourceOwner` once per declared service, Postgres and Key Value on every apply preflight and validate.
  - `resourceOwnedByBlueprint` (`apps/blueprint.go`) does the same for every resource on each Blueprint read, which `use-blueprint.ts` polls at `RESOURCE_POLL_INTERVAL_MS`.
  - Fix: one store read of the workspace's claims into a `kind/name → owner` map, keeping the CR-label fallback.
- **Datastores listed twice per apply.** `blueprintOwnershipConflicts` lists the workspace's Databases and Key Values, then `deployParsedStack` lists them again through `stackDatastoreSnapshots` (`apps/deploy.go`). bex-api's Kubernetes client is uncached, so each list is an API-server round trip returning every datastore in the workspace.
  - Fix: take the snapshots once, before the preflight, which writes nothing, and pass them in.
- **Test:** an apply and a Blueprint read each make one claims query, counted by a fake store, and the apply lists each datastore kind once.
- Found by w5/098's efficiency review (2026-10-07). Both costs date from w8/m40.

**Result (2026-10-07):**

- **One claims read.** `store.PGStore.BlueprintResourceOwners(ctx, tenantID)` maps every claimed resource in a workspace to its owner (`BlueprintResourceKey{Kind, Name}`). It is one query, served by the claims table's `(tenant_id, kind, name)` primary key.
  - The apply preflight, the validate preview (`blueprintOwnershipConflicts`) and the Blueprint read (`resolveBlueprintResourcesFromIR`) each read it once, through `blueprintResourceOwners` and `blueprintResourceOwner`. Before, each queried once per declared resource.
  - The claim still outranks the CR label. A failed read leaves the labels to decide, as the per-resource reads did, and the claim each write takes still enforces ownership.
  - `GetBlueprintResourceOwner` stays only for a failed claim's refusal, which needs a fresh read.
- **One pre-write datastore list per kind.** `deployParsedStack` takes its datastore snapshots before the ownership preflight, which writes nothing, and passes them in. `blueprintOwnershipConflicts` follows the "nil means fetch here" convention, so the preview passes nil.
  - The refusal order is unchanged: ownership, then billing.
  - The post-write ownership stamp still lists the kinds it stamps, since it must see the CRs the apply created. It no longer lists a kind the manifest does not declare, so a services-only apply lists no datastores.
  - An apply declaring both kinds lists each twice, down from three times.
- **Tests.**
  - `TestABlueprintApplyAndReadEachReadTheClaimsOnce`:
    - an apply and a read each make one claims read and no per-resource lookups;
    - the apply lists each datastore kind at most twice;
    - after another Blueprint takes over the Postgres, the read drops it and the preflight refuses the re-apply.
  - `TestAServicesOnlyApplyListsNoDatastores` pins the stamp's guard.
  - Five mutants each fail these tests: per-resource lookups in the preflight or in the read, the preflight's own lists, ignoring the claim, and an unguarded stamp.
  - `TestPGClaimBlueprintResource` covers the workspace-scoped map against real Postgres.
  - The apps, api and store suites pass, also under `-race`, and `make lint` is clean.
- **Not done here:**
  - The action plan and the validate preview still take their own datastore lists. Filed as w5/124.
  - The Blueprint read lists only the workspace's own namespace, so it may miss un-migrated resources. Filed as w5/125.
  - The `kind/name` string keys elsewhere in apps are left for w5/115, which owns claim-kind typing.
