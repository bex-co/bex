## Objective

Apply the post-create contract to embedded child resources and secret-bearing flows without forcing detail redirects that would discard essential context or one-time credentials.

## Context

- Webhook creation intentionally shows the mint-once signing secret before the user chooses to open `/webhook/$webhookId`.
- API-key and managed-Postgres-user creation expose secrets that cannot be recovered later.
- Environments, registry credentials, SSH keys, workspace invitations, custom domains, and database exports/users are created inside an owning Project, settings page, service, or database context and do not all have independent detail routes.
- A cross-resource navigation policy must distinguish these cases from standalone resource creation.

## Steps

1. Compare every contextual and secret-bearing row from t001 with its current success and failure behavior.
2. Correct only proven mismatches: retain or restore the owning context, refresh the relevant list, and keep one-time values visible until explicit acknowledgement.
3. Ensure any subsequent View/Open affordance uses the returned immutable id and leads to the correct detail route when one exists.
4. Verify failed mutations neither close the interaction nor lose entered non-secret context unnecessarily.

## Acceptance criteria

- [x] One-time API-key, webhook, and database-user credentials remain visible until acknowledged and are never discarded by automatic navigation.
- [x] Embedded resources refresh and remain in their owning context unless the matrix documents a specific detail destination.
- [x] Returned ids, not names, drive every optional View/Open link.
- [x] Failure behavior is non-navigating and preserves a recoverable interaction state.

## Out of scope

- Making one-time secrets retrievable later or inventing standalone routes for child records.
