# Reserved Postgres roles miss CNPG's `cnpg_` prefix

Why: a database user named `cnpg_<anything>` passes bex-api, but CNPG's webhook rejects it as reserved for operator use. That recreates the reconcile wedge w4/m170 just fixed, and the operator's self-heal uses the same predicate, so it never recovers.

Source: Last-24h code review, 2026-10-05 (user handed all fixes to w5). Gap in `faf2ca1f6` (w4/m170). Checked against CNPG source, `pkg/postgres/roles.go` `IsRoleReserved` (main): reserved are `postgres`, `streaming_replica`, the operator prefix `cnpg_` and the PostgreSQL prefix `pg_`.

## Where

- `lego/types/v1alpha1/database_types.go:64` `ReservedPostgresRole` checks `postgres`, `streaming_replica` and `pg_*`, not `cnpg_*`.
- Same gap in the dashboard copy, `dashboard/src/features/databases/lib/identifiers.ts:11-17`.
- Consumers: bex-api create/add-user (`lego/backend/internal/postgres/access.go:141`) and the operator's managed-roles projection and heal (`lego/operator/internal/controller/database_controller.go:372-378`).

## Fix

1. Add the `cnpg_` prefix to `ReservedPostgresRole` and the dashboard twin; cite CNPG's `IsRoleReserved` in the doc comment.
2. Check how CNPG's managed-roles reconcile handles the role names `public` and `none` (PostgreSQL refuses both); add them if they wedge it too.
3. Tests: the types predicate; `TestManagedRolesNeverProjectReservedRoles` (`lego/operator/internal/controller/database_test.go:379`) with a `cnpg_reader` user; bex-api refusal with the existing `POSTGRES_IDENTIFIER_RESERVED` code; the dashboard identifier test.

Done: adding Postgres user `cnpg_reader` through REST, GraphQL, MCP or the dashboard is refused before it reaches CNPG; a CR that already carries one has it filtered from managed roles and the database reconciles.
