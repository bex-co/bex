# 061 — A suspended Key Value is indistinguishable from a running one in the CLI: bex reports suspension only in a field the pinned client drops

Why: a user who suspends a store, then runs `bex kv get` to check, is told `Status: available` — so the datastore their app can no longer reach looks healthy on the surface they were given to inspect it with.

- **Severity:** major (the CLI misreports a resource's operational state; no data loss).
- **Attribution:** server (status vocabulary), surfaced only on the CLI. The client-side half is upstream and cannot be fixed in the launcher.
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-15 UTC, sweep 3. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, human device login, `bex v0.2.1` (upstream pin v2.27.0). Fixtures `qa-20260915-4ce6fd-kv` (`red-daks9a831mas7389obi0`) and `qa-20260915-4ce6fd-pg` (`dpg-daksavg31mas7389obk0`), both created and deleted inside the run.

## Reproduction

```text
$ bex keyvalues suspend red-daks9a831mas7389obi0 --confirm -o json   # exit 0
$ sleep 30

$ bex keyvalues get red-daks9a831mas7389obi0 -o json
{"data":{ "id":"red-…","status":"available",
          "maxmemoryPolicy":"allkeys_lru","persistenceMode":"snapshot", … }}
# keys: createdAt environmentId id ipAllowList maxmemoryPolicy name ownerId
#       ownerType persistenceMode plan projectId region status updatedAt version
# -> no `suspended` key at all

$ bex keyvalues get red-daks9a831mas7389obi0 -o text
Status: available            # and nothing else mentions suspension

$ GET https://api.bex.co/v1/key-value/red-daks9a831mas7389obi0
{"id":"red-…","status":"available","suspended":"suspended", …}
```

Postgres is half-affected — the field survives the projection but the text renderer omits it:

```text
$ bex postgres get dpg-daksavg31mas7389obk0 -o json
status= available   suspended= suspended

$ bex postgres get dpg-daksavg31mas7389obk0 -o text
Status: available            # `suspended` never printed
```

The suspension is real, not a stale read: the subsequent `keyvalues resume` returned `status: "creating"`, i.e. the instance had genuinely been scaled down.

## Root cause

- **bex keeps suspension out of `status` by design.** `kvStatus` (`lego/backend/internal/keyvalue/service.go`) maps the CR phase to exactly `available | unavailable | creating`, plus `deleting` from a deletion timestamp (`kvView`); suspension is reported separately as `Suspended: core.SuspendedEnum(kv.Spec.Suspended)`. `.pm/w1/085.md` records this as deliberate — "the wire `status` deliberately stays `available` while suspended (the backend reports readiness separately from suspension)" — and fixes the **dashboard** presentation by deriving a combined label client-side.
- **Render does not split them.** The pinned client's generated `DatabaseStatus` enum (`pkg/client/types_gen.go:481-491`) includes `DatabaseStatusSuspended = "suspended"` alongside `available`/`creating`/`unavailable`, so on Render the suspended state arrives in `status` itself.
- **The pinned client therefore has nowhere to read it from on bex.** Upstream projects the API object into its own output type before rendering, and `KeyValueOut` (`pkg/keyvalue/output.go:10-30`) carries `Status` but **no** `Suspended` field — so for Key Value the CLI structurally cannot show suspension. `PostgresOut` keeps the field, but `text.PostgresDetail` does not print it.
- Net: the dashboard has a derived view and the REST consumer has two fields to combine, while the CLI — the surface with neither — is left with a `status` that is wrong by Render's own vocabulary.

## Fix (~50m)

The clean fix is server-side, and it is one decision shared with `w1/085`: **make `status` carry `suspended`**, matching Render's enum, for both Key Value and Postgres.

- `kvStatus` / its Postgres twin return `"suspended"` when `spec.suspended` is set (suspension outranks readiness; `deleting` still wins).
- Keep the separate `suspended` field — it is Render's shape too and REST/GraphQL/MCP consumers already read it.
- Coordinate with `w1/085`: once `status` is truthful, the dashboard's `deriveStatus` (`dashboard/src/features/keyvalue/lib/status.ts:79-85` and the databases twin) becomes a passthrough and that note's "Status row reads available" symptom disappears at the source rather than being patched per-card. Land them together or sequence 085 after this.
- Record the resolved behavior in `docs/ADR018-render-parity.md` (the Key Value and Postgres rows) and in `docs/cli-compatibility-checklist.md` beside the `keyvalues suspend` / `postgres suspend` rows.

If the readiness/suspension split must be preserved instead, then this is a deliberate divergence and it needs writing down in both docs plus an explicit note that the CLI cannot represent a suspended Key Value — but that leaves a user-visible wrong answer on a supported command, so prefer the fix.

## Blast radius

Every consumer of the datastore `status` string: REST `GET /v1/key-value{,/id}` and `/v1/postgres{,/id}`, GraphQL `keyValues`/`keyValue`/`postgres*`, MCP `list_key_value`/`get_key_value`/`list_postgres`/`get_postgres`, the dashboard list/detail status chips (via `deriveStatus`), and `datastore_event_facts`' availability arming — `docs/render-artifacts/webhooks-api.md:148` states "a suspended datastore is never reported unavailable", so check that adding a `suspended` status does not make the fact writer emit a spurious `key_value_unhealthy`/`postgres_unavailable` edge.

## Regression checks

- Backend: suspending a Key Value and a Postgres makes `status` read `suspended` on REST, GraphQL, and MCP alike (cross-surface assertion, not one adapter).
- `deleting` still outranks `suspended`; `creating` on resume is unchanged.
- Datastore event facts: a suspend emits no availability edge (the existing guard stays green).
- Dashboard: the status chip and the Details Status row agree — the `w1/085` assertion, now satisfiable from the wire.
- Live CLI control: `bex kv get -o text` on a suspended store prints `Status: suspended`.

## Unverified

- Render's live API was not called; that `status` can be `suspended` there is taken from the pinned client's generated enum, which is derived from Render's published OpenAPI.
- Whether `text.PostgresDetail` should additionally print the `suspended` field is an upstream rendering question and is not part of this fix.

## Dedupe

`.pm/w1/085.md` is the **dashboard** sibling of the same underlying split and is cited above; it does not cover the CLI, and its proposed fix (derive the label in two dashboard cards) would leave the CLI wrong. `rg` over open and `done/` `.pm` for `DatabaseStatusSuspended` / `kvStatus` returns nothing else. `docs/cli-compatibility-checklist.md:105,160` grade `keyvalues suspend` / `postgres suspend` as working verbs — true, and unaffected; what is wrong is the subsequent read.
