# The api test suite builds the MCP server twice per test server

Why: about 6.6 s of the api package's 7.65 s of test CPU goes to building the MCP server: once inside `Handler()`, and again in every test MCP session.

- `Server.Handler()` builds one MCP server through `mcpHTTPHandler` (`lego/backend/internal/api/server.go`).
- `MCPServer()` builds a second, which the test helpers `mcpSession` / `mcpSessionIdentity` use. Each build re-registers every tool and re-resolves its JSON schemas.
- Fix: build the MCP server once per `Server` and return that one instance from both `MCPServer()` and `mcpHTTPHandler`. Production keeps one shared instance, as the doc comment already says.
- Don't defer the build to the first `/mcp` request: a broken tool schema should still fail at startup.
- Test: the suite stays green and `go test ./internal/api/` gets faster. Optionally add a check that `MCPServer()` returns the same instance on repeat calls.
- Found by w5/093's efficiency review (2026-10-06).

**Result (2026-10-07):**

- **One server per `Server`.** `Server.MCPServer()` builds the MCP server once, on first use, through `sync.Once`; the registration body moved to `buildMCPServer`. `Handler` still makes that first call at startup, so a broken tool schema still fails there. Stdio, the `/mcp` handler and the tests' in-memory sessions share the one instance.
- **One schema cache per process.** Every server is built with a shared `mcp.SchemaCache`, the go-sdk v1.6.1 option, because a tool's inferred and resolved schemas depend only on its Go types. The api suite builds one server per test server, about 280 per run, and resolution was most of its CPU after the first fix. Nothing mutates a registered schema: `toolsWithWorkspaceID` re-encodes a copy. The two `AddExactJSONTool` tools build a fresh output schema each time, so they miss the cache, which costs nothing that matters.
- **Measured** on the api test binary:

  | Change                | Wall    | User CPU |
  | --------------------- | ------- | -------- |
  | Before                | ~16 s   | ~27 s    |
  | One server per Server | ~13 s   | ~22 s    |
  | Plus the schema cache | ~4–5 s  | ~6.6 s   |

  All tests pass, and the suite passes under `-race`.
- **Test.** `TestHandlerBuildsTheOneMCPServerAtStartup` uses the standard `serverWith` fixture. It checks that `Handler` leaves the server built and that `MCPServer()` returns that same instance. Two mutants fail it: building on every call, and a `/mcp` handler that resolves the server per request.
- **The contract**, now in `MCPServer`'s doc comment: a Server's fields must be final by its first MCP build. Production sets `OriginMetrics` before `Handler` and `RunStdio`, and no test writes a captured field after a build.
- **Next biggest test cost:** `fakeClient` builds a fresh client-go scheme per call, about 1.8 s of the remaining CPU. Not filed: it's minor and test-only.
