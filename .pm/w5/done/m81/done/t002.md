## Objective

Capture the two latency phases that dominate perceived startup and are today entirely uninstrumented: sandbox provisioning (dispatch→running, observed 3–10s warm) and agent readiness / time-to-first-model-call (agent-ready to the first upstream vendor call, the gap where a cold or misconfigured turn stalls).

## Context

- `dev-5`: create ~100ms → sandbox running 3–10s (pod schedule + image + execd) → agent ready <1s (`initialize` 132ms, `session/new` 736ms) → first model call. None of this is timed in-product.
- Provisioning is driven asynchronously in `runDispatch`/`dispatch` (`lego/backend/internal/agentsessions/service.go` ~475) via `Sandbox.CreateAgentSessionSandbox`/`AgentSessionLifecycle` (`lego/backend/internal/sandbox/service.go`) and recorded by `RecordAgentSessionDispatch`.
- The first upstream model call is observable at the gateway model proxy (`lego/backend/internal/sshgateway/modelproxy/modelproxy.go`) — the first proxied request per session marks agent-ready→first-call.

## Steps

1. Emit a **sandbox-provision latency** signal (dispatch/schedule → running) from the dispatch path, labelled by outcome (running vs failed-to-provision).
2. Emit a **time-to-first-model-call** signal: mark the first proxied model request per session at the gateway (or persist a `firstModelCallAt` the Completer can diff against session create) — pick the lower-friction of a metric vs a persisted timestamp, threaded through the async dispatch/gateway boundary.
3. Keep the signals cheap and non-blocking on the hot path (no added PostgreSQL round-trip per request; a once-per-session mark).

## Files
