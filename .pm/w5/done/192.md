# 192 — Confirm whether Zot's dedupe links a blob another repository holds when an import checks for it, and close it if so

Why: an attacker-controlled source registry can serve a manifest naming a layer digest it does not have. If the sandbox registry answers the importer's existence check for that digest from its global dedupe store (Zot runs with `Dedupe: true`), `remote.Write` skips the upload and the attacker's imported image then holds another workspace's private layer, readable from their sandbox.

- **Source:** w5/m383 /simplify review (2026-11-13), carrying the "Zot dedupe" item of w5/189. m383 closed the same-host cross-repo mount (a source on the registry's own host is refused) but not this.
- **Check:** run Zot v2.1.22 locally with the deployed config (`deploy/gitops/base/zot.yaml`, `lego/operator/.../zotconfig.go`), push a blob into repository A, then `HEAD /v2/B/blobs/<digest>` as the importer: does it answer 200 and link the blob into B?
- **Fix if it does:** make the importer prove the source serves every layer before writing (read each layer through go-containerregistry's verifying reader, or upload unconditionally), or turn off Zot's cross-repository dedupe linking for the snapshot prefix.
- **Size:** ~1h with the local Zot check and a test.
- **Done 2026-11-13 — the exposure was real, and fixed.** Checked against Zot v2.1.22 run locally with the deployed storage settings (`dedupe: true`): HEAD and GET never link a blob across repositories, but **any** mount request (`POST …/blobs/uploads/?mount=<digest>`) links it from whichever repository holds it, with no `from`, with a `from` naming another repository, or one that lacks it. And go-containerregistry's `remote.Write` sends such a mount for **every** layer of an import (`?mount=…&from=<source repo>&origin=<source host>`, the OCI 1.1 cross-origin mount), whatever the source registry; `TestImportNeverAsksTheSandboxRegistryToMount` caught three on an ordinary import. So an attacker serving a manifest that names another workspace's layer digest would have had that layer linked into their imported image, readable from their sandbox (gated on knowing the digest). Fix: the copy hands go-containerregistry plain layers (`sandbox.uploadOnly` unwraps `remote.MountableLayer`), so it never asks to mount and every blob is uploaded from bytes the source served; the cost is bandwidth for layers Zot already holds. A HEAD stays safe while Zot's `storage.hydrateBlobOnRead` is off, which `TestZotNeverHydratesBlobsAcrossRepositoriesOnRead` (operator) pins. The importer is the only bex code that writes to a registry; the build pushers (kpack, BuildKit) are filed as w5/193. Recorded in ADR107 as finding S-4.
