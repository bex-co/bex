# A crash under an open deploy can be dated from the rollout start

Why: w5/m113 lets a debounced pass keep the edge floor, so a confirmed failure is stamped at its Ready transition. Under an open deploy, the unhealthy conclusion (a concrete container failure with nothing serving) carries Ready's `LastTransitionTime`, which is the rollout's start, not the failure's. When the first pass to see the rollout is already that debounced crash, `server_failed` is dated from the rollout start.

That is accurate for a Recreate rollout (disk-backed services), whose old pod stops first. It is early for a RollingUpdate whose old pods died later in the rollout. Before m113 the same edge was a resync or two late in both cases.

Source: w5/m113's `/simplify` quality review, 2026-10-05 (`observedServiceStateFor`'s open-deploy branch, `lego/backend/internal/store/reconciler.go`; Ready written at `lego/operator/internal/controller/app_controller.go` `reportRolloutProgress`).

## Fix (~45m)

1. In that branch, back the conclusion with the `Serving` condition's transition when it is False for the current generation. That is when the serving revision actually stopped. With no such condition, carry no transition, so the edge stays at the observation.
2. Keep Ready's time for `rejectStaleUnhealthy`'s ordering, or move that guard to the same source. Either way, write down which.
3. PG replay through `guardServiceObservation`: a RollingUpdate whose old pod dies mid-rollout is dated at the `Serving` flip, and a Recreate rollout at the rollout start.

## Outcome (2026-10-06)

Done, with two changes to the plan.
1. **The signal did not exist.** The operator wrote `Serving` as True or Unknown only: when no active-revision pod was ready it wrote Unknown, the same as a failed list. So "Serving False for the current generation" never happened, and the first version of this fix dated every open-deploy crash at the observation. The operator now writes `False` (`ReasonServingRevisionUnavailable`) when the list succeeded and no active-revision pod is ready, and keeps Unknown (`ReasonServingUnobserved`) for "not observed". `lego/types/v1alpha1/serving_condition.go` documents the three statuses. The backend's healthy-under-deploy check, the only other consumer, keys on True and is unchanged.
2. **The later of the two clocks, not "no transition".** Under an open deploy the unhealthy conclusion carries Serving's stop (`servingStoppedAt`: False, for this generation) when it is later than Ready's transition (the rollout start). A RollingUpdate crash is therefore dated when serving stopped and a Recreate at the rollout start. A stop carried over from before the rollout never dates the crash earlier than the rollout. With no stop recorded, Ready's time keeps `rejectStaleUnhealthy` a real clock (step 2: the guard and the edge share this value, documented on `ReadyTransitionAt`). "No transition" would have turned the m41 stale guard off for every open-deploy crash, and dated a Recreate late.

Step 3: `TestPGOpenDeployCrashIsDatedWhenServingStopped` replays through `guardServiceObservation` on real Postgres. Rolling update → Serving's stop; Recreate → the rollout start; no stop, a stop from an older generation, or a stop carried over from before the rollout (older than the healthy checkpoint, which alone the stale guard would refuse) → the rollout start. Mutants (Ready only, Serving alone, generation ignored) each fail exactly their cases. The operator's `TestServingRevisionIgnoresFailingReplacement` now expects False for a crashed serving release. Store suite (real deps), operator `make test` and `make lint` green.
