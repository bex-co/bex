# Catch-block errors outside the shared helpers stop showing raw "Failed to fetch"

Why: w5/164 fixed the shared GraphQL error helpers, but eleven catch-block calls still show a caught error's raw `.message`, so a network failure shows the browser's untranslated English ("Failed to fetch"), even in the Chinese UI.

- **Where:** these are the `ALLOWED_RAW_MESSAGE` entries in `dashboard/src/common/lib/__tests__/mutation-error-toast-invariant.test.ts`.
  - **Raw text inside a translated sentence** ("Couldn't save the allowlist: Failed to fetch"):
    - `features/databases/hooks/use-access-control.ts:83` and `:102`
    - `features/databases/hooks/use-recovery.ts:175`
    - `features/keyvalue/hooks/use-key-value-networking.ts:77`
    - `features/services/hooks/use-service-networking.ts:28`
  - **env-groups:** in `features/env-groups/hooks/use-env-groups.ts:232/258/357/397`, the toast `description` is `error.message`, under a translated title.
  - **agent-sessions:** in `features/agent-sessions/components/session-detail-header.tsx:137/173`, the whole toast is `err.message`. `agentSessionErrorMessage`'s last fallback (`features/agent-sessions/lib/errors.ts:60`) returns raw text, and so does `new-session-composer.tsx:205`.
  - **SQL console:** `features/databases/components/sql-console.tsx:89` shows Postgres's own error for the user's SQL. Keep that, but use `t("databases.sqlUnknownError")` for a transport failure.
- **Fix:**
  - Interpolated sites: pass `refusalReason(e)` and use a reason-less variant of the copy when it is empty, or show `mutationErrorMessage(e, t(…generic))`.
  - env-groups: `description: refusalReason(error) || undefined`.
  - agent-sessions: when the error is neither an `AgentSessionError` nor a GraphQL error, fall back to a translated generic (a new `agentSessions.errors.generic`). Routing the header's toasts through `agentSessionErrorMessage` alone would only move the raw text.
  - sql-console: show the raw text only for a GraphQL error.
  - Then drop each entry from `ALLOWED_RAW_MESSAGE`.
- **Test:** for each site, a network `TypeError("Failed to fetch")` shows the translated copy in en and zh, and a server refusal still shows its message. The invariant's stale-entry check proves the allowlist is empty.
- Source: found while working w5/164 on 2026-10-20 (the raw-message scan that test added). Sizing: about an hour of small call-site swaps, so an inbox note. If it runs over, promote it.

**Done 2026-10-20.** The 11 catch-block calls no longer show raw text:

- The five "Couldn't X: {error}" toasts (Postgres allowlist and create-user, restore, the Key Value and service IP allowlists) now call `mutationErrorMessage(e, t(…))`, as their neighboring catch sites already did. Their keys now read as reason-less copy.
- The env-group descriptions use the newly exported `relayableReason`, as does the Postgres parameter editor's save error.
- `agentSessionErrorMessage` falls back to `mutationErrorMessage(err, t("common.errorDefaultMessage"))`. The session header's pin/cancel toasts and the composer's non-coded branch now route through it, which also covers the steering composer and the archive toggle.
- The SQL console relays Postgres's error and otherwise shows "Couldn't run the query. Please try again.", which no longer blames the statement for a network failure.
- `ALLOWED_RAW_MESSAGE` is gone: the invariant now requires no raw reads at all.
- **Tests:** each site covers a network failure (en + zh for create-user) and a server refusal; `relayableReason` has its own transport and throttling cases. Dashboard tsc, eslint and vitest are green.
