# The sandbox-files endpoint answers an executor failure with the executor's text

Why: w5/123 stopped bex-api's refusals from carrying a dependency's error text, but the ssh-gateway's sandbox-files endpoint still writes any error's text to the client, so a Kubernetes exec failure can name the API server, the pod and the node.

- `lego/backend/internal/sshgateway/sandboxfiles/sandboxfiles.go` `writeError` answers `http.Error(w, err.Error(), status)` for every error, and `executionError` returns the executor's own error unchanged when `Executor.Execute` fails.
- The coded refusals beside it (`statusError`'s fixed sentences, `errTooLarge`, `errBadArchive`, `ErrTargetTerminated`, a timeout) are bex's own text and can stay.
- Fix: answer an executor failure with the fixed "sandbox file operation failed" (503) and log the cause, as `core.HideCause` does in bex-api.
- Test: an executor that fails with an error naming an internal address answers 503 with the fixed sentence, and the address is absent from the body.
- Found by w5/123's reuse review (2026-10-07).

**Result (2026-10-07):**

- **An executor's failure is hidden at its source.** `execute` answers any executor error other than a terminated target with `sandbox file operation failed` (503). The cause is logged with the sandbox's id by the gateway's own `hideCause`, because `core.HideCause` would log as bex-api.
  - The executor's failure is hidden whatever it wraps. A dropped exec stream (`io.ErrUnexpectedEOF`) used to answer 400 as if the client's upload were bad, and an exec deadline answered 504, both carrying the API server's exec URL with namespace and pod.
  - A terminated target keeps its own 404.
- **Anything else unclassified is hidden too.** `writeError`'s fallback answers the same 503 and logs the cause, for example a failed read of the upload naming the gateway's addresses. bex's own refusals keep their sentences.
- **Archive errors are classified by kind.** Simplify found that a failed body read inside a tar or gzip upload was still wrapped into a 400 carrying the network error's text, and that corrupt gzip now answered a logged 503.
  - `archiveError` marks only format errors (gzip header or checksum, corrupt deflate data, tar header, truncation) as the client's bad archive, a 400 with their detail. Anything else passes through to the hidden 503.
  - A corrupt gzip checksum now answers 400, where it answered 503 before.
- **Logs.**
  - The stage cleanup calls the executor directly, so one failed upload no longer logs its cause twice.
  - A bad download marker logs the refusal itself, not the cancel the gateway caused.
- **Tests.** `TestAnExecutorFailureAnswersWithoutItsText`:
  - a dropped stream and an exec deadline each answer the fixed 503, with the cause logged, on upload and download;
  - a terminated target answers 404;
  - an unreadable raw upload and an unreadable tar upload answer the fixed 503, and the cause is logged;
  - a bad download marker logs its refusal.

  A corrupt-checksum row joins the upload validation table. Eight mutants each fail a test. The gateway suites pass with `-race` (apart from agentcred's existing race, w5/140), and `make lint` is clean. ADR006 lists the endpoint under its refusal rule.
- **Follow-ups.**
  - w5/139: a transfer revoked mid-stream answers 503, while the exec stream answers 403. This is pre-existing.
  - w5/140: two git-proxy tests race their own log capture. This is pre-existing.
