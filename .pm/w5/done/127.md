# Identity lookups fetch every member's TOTP secret just to learn whether MFA is on

Why: `KratosIdentities.Lookup` and `LookupMany` ask Kratos for `include_credential=totp` so that `MFAEnabled` can see a TOTP credential. That include returns the credential's config, which holds the TOTP secret, for every member on every Team-page poll. Only the credential's presence is read.

- **Evidence** (Kratos v26.2.0 on dev-5, 2026-10-07): once any `include_credential` is given, the list endpoint lists every credential type, with config only for the included ones. A single GET lists them all without config. So `include_credential=webauthn` alone should still show a TOTP credential's presence. The webauthn config is still needed, because its stub entry only counts with registered keys (w4/020).
- **First, check the premise** with an identity that has TOTP enrolled. No dev-5 identity had one, so the presence of an unrequested `totp` entry was not observed directly.
- **Fix:** drop `include_credential=totp` from both reads in `lego/backend/internal/workspaces/kratos.go`, and keep the presence check.
- **Test:**
  - the fake Kratos in `kratos_test.go` lists a TOTP credential without config and is never asked for it;
  - `MFAEnabled` stays true;
  - a live check on a stack where an identity has TOTP enrolled.
- Found by w5/116's efficiency review (2026-10-07).

**Result (2026-10-07):**

- **Premise checked live on dev-5 (Kratos v26.2.0, chart 0.62.1).** A throwaway identity enrolled TOTP through the settings flow, then was read back through the admin API:

  | read | credentials listed | config returned for |
  | --- | --- | --- |
  | list, no include | none | — |
  | list, `include_credential=webauthn` | password, totp, webauthn | webauthn |
  | list, `webauthn` + `totp` | password, totp, webauthn | totp, webauthn |
  | single GET, `webauthn` | password, totp, webauthn | webauthn |

  **Probe**, for the re-probe the Kratos values file now asks for on a version bump:
  1. `POST /admin/identities` with a password credential and a verified address.
  2. Log in with the password through the login API flow.
  3. Open the settings API flow, compute a code from its `totp_secret_key` node, and submit it with `method: totp`.
  4. Read the identity with each include, and record which credential types carry `config`.
  5. `DELETE` the identity.
- **Fix.** `Lookup` and `LookupMany` include only webauthn. Its config is still needed, because its stub entry counts only with registered keys (w4/020). TOTP shows by presence, without the config that holds its secret. Every caller goes through these two reads: members, owners, the auth gate's identity lookup, opsrole and identityclaims. So no path fetches a TOTP secret any more.
- **Verified live after the change.** A temporary test ran the changed reader against dev-5's Kratos with a TOTP-enrolled identity. `Lookup` and `LookupMany` both reported MFA on. The identity and the test were removed.
- **Simplify.** A dedicated fake was dropped. The existing `Lookup` fake now pins its include to exactly webauthn, as `fakeKratosList` already did for `LookupMany`. That also catches a `password` include, which would drop webauthn's config, and which the dropped fake missed.
  - The docs name the Kratos version the behavior was checked on.
  - `kratos.values.yaml` carries a RE-PROBE note at the TOTP method.
- **Tests.** Five mutants each fail a test: `Lookup` asking for totp, dropping its include, or switching to password; `LookupMany` asking for totp or dropping its include. The workspaces suite, `make lint` and `gitops-validate.sh` pass.
- **Follow-up:** w5/133. Email-only batch reads still make Kratos load credentials.
