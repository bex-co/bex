## Objective

Decide, with live evidence, which store serves each Network-card section (requests count, status codes, response times) under a Host filter and under a Path filter, and record the decision so t002–t005 implement one pinned design instead of discovering constraints mid-build.

## Context

- Traefik's Prometheus series (`BEX_PROM_URL`) have no per-path label; bex already attributes Traefik series per App via its Ingress routers (the w5/m48 static-site precedent), and multiple hosts on one App mean multiple routers — so a Host filter can plausibly ride router-level label matching.
- The Loki request-log store (`BEX_LOKI_URL`) already carries `host`/`path` labels — the w5/m23 Logs-tab filters and `list_log_label_values` prove the labels exist end to end. Response-time aggregation from Loki depends on what the request-log lines record (Traefik access logs carry duration).
- The metrics core is `lego/backend/internal/metrics/` (`service.go`, `source.go`); w3/m12 is where the API's current filter rejection lives.
- The m56 multi-quantile read shows the current PromQL query shapes.

## Steps

1. Against dev-5 (or prod, read-only), list the label sets of the Traefik request series bex queries today; confirm whether router labels give a usable per-host axis and confirm no path axis exists.
2. Query Loki for the request-log labels/fields available per line (host, path, status, duration) and check cardinality/rate feasibility for range aggregation over the metrics page's presets (30m–30d).
3. Decide per section × filter: Prometheus-served, Loki-served, or unsupported-with-explicit-reject. Decide the behavior when only `BEX_PROM_URL` is set (Path filter ⇒ store-unavailable, mirroring the Logs-tab 503 pattern).

## DECISION (pinned 2026-07-30)

Evidence gathered from the code (dev-5/prod read-only unavailable — stack down; label facts confirmed from the shipped, production-verified query builders instead):

- **Prometheus/Traefik has no host or path axis.** `traefik_service_requests_total` / `traefik_service_request_duration_seconds_bucket` carry `service`/`code`/`method`/`le` only. `addRoutersLabels` adds a router **name**, not the matched `Host()`/`Path()` (`source.go:250-255`, `service.go:107-115`). So **neither** Host nor Path can be Prometheus-served — the m58 README's "Host can ride router labels" hypothesis is refuted; both filters are Loki-served.
- **The Loki request-log store carries both.** `type=request` streams (Traefik access log) expose `RequestHost`/`RequestPath` as JSON line fields (already parsed at `logs/loki.go:278`), `status`/`method` as stream labels (`logs/loki.go:408-414`), and `Duration` (Traefik's standard JSON field, nanoseconds) for latency. Loki's `/loki/api/v1/query_range` accepts LogQL **metric** expressions and returns a `resultType:"matrix"` body **structurally identical to Prometheus**, so `metrics.parsePromMatrix` parses it unchanged.

### Pinned matrix (Network-card section × filter × source)

| Section | Host | Path | Query |
| --- | --- | --- | --- |
| Total Requests (count) | Loki | Loki | `sum(rate({namespace,app,type="request"[,status]} \| json request_host="RequestHost", request_path="RequestPath" \| <host/path eq filters> [<step>s]))` |
| Status/Method group-by | Loki | Loki | same, `sum by (code\|method) (...)` (Loki `status`→relabelled `code` to match the Prometheus vocabulary) |
| Response Times (quantile) | Loki | Loki | `quantile_over_time(<q>, {…type="request"} \| json latency_ns="Duration", request_host=…, request_path=… \| <filters> \| unwrap latency_ns [<step>s]) / 1000000000` (ns→s) |
| Outbound Bandwidth | **reject** | **reject** | `ErrBadRequest` — egress (L3/L7) has no per-request host/path axis |

Count uses LogQL `rate` (matched-lines/second) to match the Prometheus path's `sum(rate(...))` req/s semantics, so toggling a filter never rescales the Y-axis.

### Store-unavailable behavior (pinned)

- Host/Path filters apply **only** to `http_requests`/`http_latency`; any other metric + host/path ⇒ `ErrBadRequest` (named, at `Metrics()` up front).
- Host/Path set + `BEX_LOKI_URL` unset (Loki request-metrics source nil) ⇒ `core.ErrLogStoreUnavailable` (the Logs-tab 503 pattern) — **never** a silently-unfiltered Prometheus result.
- Unfiltered reads (no host/path) ⇒ unchanged Prometheus path, byte-identical.
- **Discovery** reuses the existing logs `LogLabelValues` (w5/m23) for **Host only**: `host` resolves from the App's own URLs (works even with no store — the Host dropdown always populates). **Path is NOT discoverable** — `DiscoverableLabels` deliberately omits it because `path` is a high-cardinality line field, not a Loki stream label (Loki's label-values API can't enumerate it). So the metrics UI mirrors the **Logs tab**: **Host = dropdown** (`useLogLabelValues(resource, "host")`), **Path = free-text input** whose value becomes the Loki `request_path` line filter. This is the honest degrade — no fabricated Path dropdown. No new discovery verb needed.
