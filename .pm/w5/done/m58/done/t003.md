## Objective

Give the metrics page real Host and Path values to offer in its filter dropdowns: reuse (or minimally extend) the existing Loki label-values discovery so the dashboard can populate both filters scoped to the service and time range, instead of the empty discovery m42 recorded.

## Context

- `list_log_label_values` / the GraphQL `logLabelValues` read (w5/m23, `lego/backend/internal/logs/service.go` + adapters) already discovers `host` and `path` values from Loki — the metrics UI may be able to consume it as-is.
- If Host is Prometheus-served per t001, decide whether host values still come from Loki discovery (one source of truth for the dropdown) or from the router label set; pin one and note it.
- Discovery must degrade honestly: no Loki ⇒ the discovery read reports store-unavailable (existing behavior), and the UI falls back per t005.

## Steps

1. Confirm the existing label-values read covers both labels scoped by service + time range; extend only if a gap is proven (e.g. a missing label or scope).
2. If any extension is needed, make it in the logs core and mirror it across its REST/GraphQL/MCP adapters (same-fields rule).
3. Add/extend tests for the discovery path the metrics UI will call.

## Files

- `lego/backend/internal/logs/service.go` (+ `rest.go` / `graphql.go` / `mcp.go` only if extended)
- `lego/backend/internal/logs/logs_test.go`

## Acceptance criteria

- [ ] A documented discovery call returns the host values and path values for a service over a time range, suitable for the two dropdowns.
- [ ] No-Loki deployments get the existing explicit store-unavailable response from discovery, not an empty-success.
- [ ] `cd lego/backend && go test ./internal/logs/...` passes.

## Out of scope

- The dropdown UI itself (t005).
