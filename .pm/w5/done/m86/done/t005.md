## Objective

Teach the dashboard consent acceptor an ops-gated client class: for client ids in `OAUTH_OPS_CLIENTS`, resolve `consent.subject`'s ops-workspace role via t004's verb **before any accept** — including the trusted/skip headless path — stamp `email`/`name`/`ops_role` id_token claims on accept, and reject non-qualifying subjects with `access_denied` (ADR088 §4).

## Context

- `dashboard/src/common/server-fn/hydra-consent.ts`: the gate must run before `acceptConsent` in **both** `handleConsent` (headless GET) and `handleConsentDecision` (human POST), preserving the "headless and human paths grant identically" invariant.
- The headless path has no dashboard session — use `consent.subject` (the Kratos identity id Hydra bound at login), never the request cookie.
- Role→claim mapping: `admin` → `GrafanaAdmin`, `developer` → `Editor`, `viewer` → `Viewer` (as `ops_role`); `contributor`, `billing`, non-member ⇒ `rejectConsent` with `access_denied`. `email`/`name` come from the same bex-api response (extend t004's verb to include them from the control-plane identity data if not already available — one round trip).
- Claims ride `acceptOAuth2ConsentRequest`'s `session.id_token`; only for ops-gated clients — every other client's accept body stays byte-identical.
- New SSR env (server-only, not `VITE_`): `OAUTH_OPS_CLIENTS`, plus the verb's URL + `BEX_OPS_ROLE_TOKEN`; verb URL should reuse the in-cluster bex-api base the SSR runtime already knows where possible.
- Fail closed: verb unreachable/misconfigured ⇒ reject for ops-gated clients (never accept ungated); non-ops clients unaffected.

## Steps

1. Add the ops-gate branch + claim stamping in `hydra-consent.ts`; keep the check in one function shared by both entry points (the `pkceSatisfied` precedent).
2. Wire env parsing beside `platformClients()`/`trustedClients()`.
3. Unit tests in `__tests__/hydra-consent.test.ts`: member roles accepted with correct claims (headless + POST), contributor/billing/non-member rejected, verb failure rejects, non-ops clients byte-identical.
4. Document the env vars in `dashboard/CLAUDE.md` SSR table.
