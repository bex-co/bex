## Objective

A release stamped for a clear-cache rebuild builds on a new kpack cache tag, and the ordinary releases after it keep using that tag, so the cleared cache is never restored again.

## Context

- `AnnotationClearCacheReleaseGeneration` (`lego/types/v1alpha1/app_types.go`) binds a clear to one release generation. bex-api deletes it on the next ordinary deploy (`deploys/service.go`), and the operator consumes it after the clear release builds (`consumeClearCacheAnnotation`).
- `clearCacheApplies` (`controller/release_identity.go`) feeds `Options.SkipCacheImport`, which only BuildKit honors.
- kpack reads and writes one tag, so it cannot skip a restore. A new tag is the only clear, and the operator must remember it in status.

## Steps

1. Add an App status field recording the release generation of the latest clear, then regenerate the CRD.
2. Set it when a clear release dispatches its build, and pass it to the build options.
3. Derive the kpack cache tag from it (the t001 tag before any clear).
4. Controller tests: a clear release dispatches with a fresh tag; the next ordinary release, with the marker gone, reuses it.

## Files

- `lego/types/v1alpha1/app_types.go`, generated CRD
- `lego/operator/internal/controller/{app_controller.go,release_identity.go,*_test.go}`
- `lego/operator/internal/build/{build.go,kpack.go}`

## Acceptance criteria

- [ ] A clear release's kpack Image uses a tag no earlier release used.
- [ ] The following ordinary release uses the same tag as the clear release.

## Out of scope

- Purging old cache tags from the registry; Zot's retention ages them out.
