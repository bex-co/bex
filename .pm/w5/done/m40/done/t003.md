## Objective

Use the Web Service facts already queried by the dashboard to show runtime in the service header and resolve the observed contradiction where the service banner said `Building` while the latest deploy was terminal `Build Failed`.

## Context

- `server.graphql` and `ServiceView` already carry `runtime`; `service-detail-header.tsx` does not display it.
- The service badge represents operator/App `phase`, while deploy rows represent control-plane deploy status. They are related but not interchangeable and must remain explicitly labeled if both are shown.
- The dev-5 comparison is evidence of a coherence bug, not proof that the dashboard should overwrite the upstream App phase with the latest deploy status.

## Steps

1. Add a compact runtime fact/badge when `service.runtime` is non-empty, using the service type as the fallback context rather than inventing a language.
2. Reproduce the `Building` + terminal `Build Failed` state and trace whether the stale fact originates in dashboard polling/cache, the API projection, or the App status.
3. Fix the owning layer if it falls within the dashboard contract; if the upstream phase is genuinely stale, render service phase and latest-deploy status as separately named facts and file the exact cross-layer owner instead of silently relabeling it.
4. Ensure a live service still presents its existing public URL and revision facts without claiming an internal address the current API does not expose.
5. Add locale and component coverage for native runtime, Docker, absent runtime, and divergent service/deploy state.

## Acceptance criteria

- [ ] Native-language and Docker runtimes render when present; missing runtime produces no fake label.
- [ ] The same screen does not describe one terminal failed deploy as actively building.
- [ ] Any simultaneous service phase and latest-deploy result are visibly named as different facts and covered by a regression test.
- [ ] Existing URL, revision, lifecycle actions, and responsive header behavior do not regress.

## Out of scope

- Adding an API-only internal hostname, implementing browser Shell, or taking over w2/m39's running-instance SSH work.
