## Objective

Polish the existing deploy-detail header and log panel so the available status, commit, trigger, timestamps/duration, pre-deploy outcome, and build-log availability answer “what happened?” without implying a root cause the API did not provide.

## Context

- w5/m29 and w9/m1 already shipped this page, its timeline, actions, navigation, search, and build-log pane. This task is a hierarchy/state pass, not a rewrite.
- w7/m28 intentionally makes store-backed `type=build` reads return 503 when `BEX_LOKI_URL` is unset. The dev-5 screenshot's “log store unavailable” message is therefore a truthful environment state, not missing ingestion code.
- Full metadata is optional: image-backed deploys and unresolved GitHub commits must continue to omit commit facts rather than fabricate them.

## Steps

1. Reuse the list's timestamp/duration presentation so list and detail cannot disagree.
2. Make status + commit/message + trigger the primary hierarchy; retain deploy id, image, pre-deploy result, and exact timestamps as secondary facts.
3. Audit log-panel branches so loading, successful empty range, store unavailable, query error, and live-tail disconnection remain visually and semantically distinct.
4. Give the store-unavailable and successful-empty states actionable, accurate copy; do not point users to unsupported drains or claim retention when the API did not say so.
5. Cover full-metadata, sparse-metadata, failed, live, and storeless fixtures in component tests/locales.

## Acceptance criteria

- [ ] A complete repo-backed fixture clearly shows status, short SHA/message, trigger, duration, and exact timestamps; a sparse fixture has no invented placeholders.
- [ ] The detail and list derive duration and status labels through shared helpers.
- [ ] A 503 log-store response cannot be mistaken for “this deploy emitted no logs,” and a successful empty query cannot be mistaken for a store outage.
- [ ] Terminal failure copy reports the known phase/status only; it never invents a cause from missing logs.

## Out of scope

- Rebuilding the detail route/timeline, implementing Loki ingestion, external log drains, or adding an unsupported structured failure-reason field.
