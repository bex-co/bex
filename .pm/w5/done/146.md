# The projects list reads each project's environments separately

Why: `renderProjects` (`lego/backend/internal/projects/rest.go`) resolves owners in one batch, then calls `environmentIDs` once per project, so a page of N projects makes N store reads for its `environmentIds`.

- **Where:** `projects/rest.go` `renderProjects`, around :101; `environmentIDs` reads one project's environments.
- **Fix:** read every listed project's environment ids in one store query keyed by project id (an `EnvironmentIDsForProjects` returning a map), and render from it.
- **Test:** listing three projects makes one environment read, and each project keeps its own `environmentIds`.
- Found by w5/133's efficiency review (2026-10-07).

## Result (2026-10-07)

- A page of projects reads its environments in one query: `store.ListEnvironmentsForProjects` (`project_id = ANY($1)`, served by the `(project_id, name)` index). `renderProjects` groups them by project, and `renderProject` renders through it, so the per-project `environmentIDs` path and its fallback are gone. An empty page makes no read.
- One `queryEnvironments` now serves all three environment reads: per project, per page and per workspace. They share one order, creation then id.
- Tests:
  - `TestAProjectPageReadsItsEnvironmentsOnce`: one read of exactly the page's ids, including a `limit=2` page; each project's public ids; `[]` for an empty project; no read for an empty page.
  - The real-DB `assertProjectsEnvironmentsRead`: filtering, grouping and order.
- Mutants: five in the projects package (per-project reads, misgrouping, first project only, storage ids, empty-page read) and three in the store against the real DB (reversed order, no filter, first id only). All fail the tests.
- Follow-ups: w5/154 (`environments` has no `tenant_id` index) and w5/155 (the projects list reads every project's services before it pages).
