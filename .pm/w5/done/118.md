# A recreated service inherits its predecessor's uncollected projection Secrets

Why: a service deleted and recreated under the same name, before Kubernetes garbage-collects the old App's `<service>-env` / `<service>-files` Secrets, finds them still stamped with the old service's store revisions, which outrank the new service's, so its first writes lose to the dead service's data.

- App names are deterministic (`core.CRName` is `tenant-name`), so the new App's Secrets have the old ones' names. The purge deletes the store paths' metadata, so the new service's versions restart at 1.
- With a leftover files Secret that holds files, the new service's first `SetSecretFile` is superseded. It mounts the Secret that won, the predecessor's files. That predates w5/106: the old rule mounted for any non-empty write.
- With an empty leftover, which w5/106 now keeps, the new service's first file is superseded and not mounted until a write outranks the old revision.
- Create-time preparation fails loudly instead: `prepareProjection`'s `Create` meets `AlreadyExists`, and the store write rolls back.
- A possible fix: `projectSource` trusts a recorded revision only when the Secret's controller owner UID is `a.UID`. Otherwise it replaces the Secret and owns it.
- Test: an App deleted with its owned files Secret left behind (the fake client runs no garbage collection), then recreated. Its first file write leaves the Secret holding only that file, mounted.
- Found by w5/106's quality review (2026-10-07).

**Result (2026-10-07):**

- **A predecessor's Secret no longer outranks a recreated service.** `projectSource` treats a projection Secret controlled by another App, a deleted namesake's that garbage collection has not reached, as not its own:
  - its recorded revision is ignored;
  - the write replaces the Secret;
  - `SetControllerReference`, which matches owners by group, kind and name, re-points the owner to the new App's UID.

  An ownerless Secret, one create-time preparation wrote ahead of its App, keeps revision ordering. Replacing a predecessor's Secret counts as creating one, so a failed CAS save removes it rather than restoring it.
- **A request that spans a delete and a recreate cannot take the new service's Secret over.** Before replacing, a re-read confirms the writer's App is still the one at its name. If not, the write answers 409 `CONFLICT` ("the service changed since this request read it"), and its compensation leaves the projection to the new service.
- **Deletes converge.** A delete that met a predecessor's higher revision used to run out of retries.
- **Tests.**
  - env and files: a recreated service's first write replaces the leftover, and so does a delete, which converges; the new App owns the Secret;
  - a stale request is refused with only the coded conflict, leaving the new Secret untouched;
  - a failed CAS save removes the replaced Secret.
  - The secrets fixtures' `sampleApp` now carries a UID, so ten existing tests pin the UID comparison.
  - Five mutants fail: no guard, `ExistedBefore` kept, no live-App check, any owner counted, and compensation re-projecting for a replaced App.
  - The secrets, apps, api and envgroups suites pass, and `make lint` is clean.
- **Docs:** ADR013 states the one exception to revision ordering.
- **Follow-up:** w5/128. Create-time preparation still meets the predecessor's Secret with a raw `AlreadyExists`, answered as a 500, and a failed env leg leaves the prepared files Secret behind.
