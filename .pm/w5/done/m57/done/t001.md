## Objective

Make `/static/<serviceId>` the canonical dashboard URL for static-typed services (matching Render's `/static/<id>` scheme), while keeping `/services/<serviceId>` working as a redirect for existing links. Non-static service types stay canonical on `/services/`.

## Context

- Today every service type is unified under `/services/$serviceId` and `/static/*` is a thin redirect **onto** `/services/` — `dashboard/src/common/lib/render-alias.ts` `RENDER_ALIAS_TARGETS.static = "/services"` (line ~16), consumed by `dashboard/src/routes/static.$.tsx`. This was m48's deliberate choice (static direct URLs redirect to `/services`).
- **Design tension (read before implementing):** the unified-`/services/` decision is intentional and documented — render-alias.ts's header comment notes the official Render CLI "falls back to `web` for unknown service types, so segment↔type validation would break its links." Reversing the alias for static must **not** break `/web|worker|pserv|cron/<id>` CLI deep-links, nor the create landings (`RENDER_CREATE_LANDINGS`). Pick the least-invasive approach: e.g. render the same detail page under `/static/$serviceId`, and redirect `/services/<id>` → `/static/<id>` only when the loaded service is static-typed (type is known only after fetch), while `/static/*` no longer collapses to `/services/`.
- Sidebar nav item `to:` paths are all `/services/$serviceId/...` (`dashboard/src/features/services/components/service-nav.tsx` lines 37-91) and must resolve under the new canonical base for a static service.
- Breadcrumb / deep-link generation in `dashboard/src/features/services/components/service-detail-header.tsx` must emit `/static/<id>` for static services.

## Steps

1. Decide the canonical-base mechanism (a real `/static/$serviceId` route tree vs a type-aware redirect) that keeps other types on `/services/` and doesn't regress CLI alias deep-links or create landings.
2. Update `render-alias.ts` so `static` no longer targets `/services` and a reverse `/services/<static-id>` → `/static/<id>` redirect exists; keep web/worker/pserv/cron alias behavior byte-identical.
3. Point static-service nav `to:` paths, sidebar links, and breadcrumbs at the `/static/<id>` base for static-typed services only.
4. Verify `/static/<id>` and every sub-route (`/events /settings /metrics /env /redirects /headers`) load, and `/services/<static-id>` redirects to the `/static` equivalent (path + sub-path + query preserved).

## Acceptance criteria

- [ ] A static-typed service's canonical URL and sub-routes are under `/static/<serviceId>`.
- [ ] `/services/<serviceId>` for a static service redirects to the `/static/<serviceId>` equivalent (path + sub-path + query preserved).
- [ ] Non-static services are unchanged: still canonical on `/services/`, and `/web|worker|pserv|cron/<id>` CLI-style aliases still redirect to `/services/<id>`.
- [ ] Create landings (`RENDER_CREATE_LANDINGS`) still resolve.
- [ ] `yarn typecheck && yarn lint` green.
