# 184 — Top queries still lists Insights' own statements on a database that ran Insights before w4/557, until its statistics reset

Why: w21/026's goal is that Postgres Insights' Top queries shows the customer's queries, as Render's does. Every database that opened Insights before w4/557 still shows the panel's own statements there, and on a low-traffic database they never leave.

- **Source / severity / estimate:** `/pm-brainstorm for 残留问题 for w5` (2026-11-12), item 4; residual recorded in w4/557's done record and in `lego/backend/internal/postgres/insights.go:318-323`. **Minor.** ~30m.
- **Root cause:**
  - w4/557 tags Insights' statements `SELECT /* bex:insights */ …` and leaves tagged rows out.
  - pg_stat_statements keeps the first text it saw for a query id, and the id ignores comments. A database that ran the statements untagged keeps the untagged text.
  - The statistics survive restarts (`pg_stat_statements.save`) and leave only past `pg_stat_statements.max`, so on a quiet database the rows stay indefinitely.
- **Fix (target behavior):** Insights' statements are fixed constants in `insights.go`. Leave out rows whose stored text equals one of them without the tag, as well as tagged rows. A customer statement is never matched.
- **Tests:** in real Postgres, run an Insights statement untagged first, then confirm Top queries leaves it out while a customer statement with similar text stays.
- **Render parity:** Render's Insights shows the customer's queries only.
- **Dedupe:** w4/557 (done; the tag), w21/058 (done; the `begin read only`/`rollback` envelope).

- **2026-11-12 (loopx w5):** done, with a different mechanism than the note proposed. PostgreSQL 18's pg_stat_statements stores normalized text: literals become `$n` and IN lists are squashed to `$1 /*, ... */` (checked on a local postgres:18 with the module preloaded). So the stored text cannot be matched to Insights' Go constants. What the untagged and tagged runs share is the query id: the tag is a comment, and the id ignores it. `EXPLAIN (VERBOSE)` reports that id ("Query Identifier") to a non-superuser. Top queries therefore asks EXPLAIN for the query id of each Insights statement (`insightStatements`), caches the ids per database for an hour (`insightQueryIDCache`), and adds `queryid NOT IN (…)` (`insightQueryIDSQL` in `postgres/insights.go`). The EXPLAIN statements are tagged, so the existing tag filter leaves out their own rows. A database without pg_stat_statements reports no ids and keeps today's query. Test: `TestTopQueriesLeavesInsightsQueryIDsOut` (real Postgres with `compute_query_id = on` and a stand-in view) leaves out an untagged row filed under the table-sizes insight's id and keeps the customer's. Residual: rows of Insights statements whose SQL itself changed before w4/557 (the earlier Top queries and Active processes texts) no longer match any current statement. They stop growing, since nothing runs them now, and leave when pg_stat_statements evicts them.
