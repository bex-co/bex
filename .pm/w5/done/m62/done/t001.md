## Objective

Make `dev-5/up.sh` independent of the broken shared-cluster assumption: diagnose why the CNPG CRDs are missing from the shared kind cluster, then change `up.sh` to install or verify the CNPG operator itself (idempotently) and to fail fast with an actionable message on any precondition it genuinely cannot meet (kind cluster absent, tools missing).

## Context

- `up.sh`'s header (`.pm/w5/dev-5/up.sh:2-8`) documents the assumption: it reuses "that cluster's CNPG operator and the bex operator (already watching all namespaces)". The m58 closeout recorded the reality: "dev-5 unraisable — missing CNPG CRDs".
- The script is already idempotent by design (`helm upgrade --install`, `kubectl apply`, PID re-checks) — the CNPG install must follow the same pattern (e.g. `helm upgrade --install cnpg` into its own namespace, or a pinned `kubectl apply` of the CNPG release manifest, matching however the shared cluster originally got it — check `scripts/mock-cluster.sh` / `deploy/gitops/` for the canonical CNPG version to pin).
- The bex-operator reuse assumption may be equally stale — verify it in the same diagnosis and give it the same install-or-fail-fast treatment if so.

## Steps

1. Raise the current shared cluster state and record what is actually missing (CNPG CRDs? the operator deployment? the bex operator too?).
2. Find the canonical CNPG install source/version the platform uses (GitOps/`mock-cluster.sh`) and add an idempotent install/verify step to `up.sh` before the "CNPG Clusters" phase.
3. Add a preflight block: required tools, kind cluster reachable, and each reused-component check with a one-line actionable failure message.
4. Run `up.sh` from the broken state to completion; re-run to prove idempotency.
