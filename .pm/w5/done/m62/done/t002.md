## Objective

Give dev-5 a working log store so store-gated features stop being locally unprovable: a minimal single-binary Loki in a dev-5 namespace, a lightweight shipper getting dev-5 pod logs into it, and the dev-5 bex-api launched with `BEX_LOKI_URL` pointing at it.

## Context

- Loki was never part of dev-5; every store-gated surface (w5/m23 log filters, m58 Host/Path metrics, the datastore log viewers) can only show its 503 state locally today.
- Match production's label vocabulary where cheap: check how the platform's collection pipeline labels streams (`deploy/gitops/` observability config — the labels `host`/`path`/`level`/`instance` that `logLabelValues` discovers) so dev-5 verification exercises the same read paths. Request-log (`type=request`) streams come from Traefik access logs in prod — t001/t005 decide whether dev-5 can produce those or whether that's the prod-only residue.
- Keep it dev-cheap: Loki monolithic mode, filesystem storage, one small shipper (promtail or Alloy) scoped to dev-5 namespaces; ports from `dev-5/ports.env` conventions (N=5-derived, no collisions).
- `up.sh` wires env for the locally-built bex-api — add `BEX_LOKI_URL` there; `down.sh` must tear the new pieces down.

## Steps

1. Add idempotent Loki + shipper install to `up.sh` (own dev-5 namespace), following the script's existing helm/apply idiom; add teardown to `down.sh`.
2. Export `BEX_LOKI_URL` into the dev-5 bex-api launch env.
3. Verify end to end: generate app-pod log lines, confirm they land in Loki (direct query) and read back through bex-api's log verbs with labels populating discovery.
4. Record in the dev-5 README section what the local pipeline covers vs prod (input to t005's 028 scoping).
