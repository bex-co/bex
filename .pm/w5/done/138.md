# A new service's first build follows its branch, not the commit its deploy records

Why: creating a repo-backed service resolves the branch tip for the first deploy row's provenance, but never pins it as the build input. The build clones whatever the branch holds when it starts, so a push in between leaves the deploy row naming a commit that was never built. Every later trigger pins its commit ("never let the operator silently follow a moving branch"). For a buildpack service the first kpack Image also tracks the branch, so kpack rebuilds it on each push until the next stored build prunes it (w5/129).

- **Where:** `lego/backend/internal/apps/service.go` CreateApp records `FirstDeployCommit: s.resolveDeployCommit(...)` but leaves `a.Spec.BuildCommit` empty. The webhook path (same file, `a.Spec.BuildCommit = commit.Hash`) and the deploy API (`lego/backend/internal/deploys/service.go`) both pin it. The operator builds `effectiveDeployRef`: `BuildCommit`, else `Branch`.
- **Fix:** when the resolver returns a commit, stamp it as the new App's `spec.BuildCommit` as well, so the clone verifies it (`EXPECTED_COMMIT`) and kpack builds exactly that commit. An unresolved commit keeps today's branch build.
- **Test:** a create whose resolver answers a SHA writes it to both the App's `BuildCommit` and the first deploy row; one it cannot resolve leaves `BuildCommit` empty.
- Found by w5/129's efficiency review (2026-10-07).

## Result (2026-10-07)

- **Create:** `apps.provisionAppIdentity` resolves the branch tip once and pins it as the new App's `spec.BuildCommit` as well as the first deploy row's commit. The first build clones that commit, verified by `EXPECTED_COMMIT`, and a buildpack service's first kpack Image builds it instead of tracking the branch. An unresolved tip still builds the branch.
- **Found by the reviews, fixed with it:**
  - A Blueprint redeploy recorded the branch tip on its row but built whatever commit an earlier deploy had pinned. `patchChangedStackService` now pins the tip it records, or builds the branch when unresolved.
  - A saved repo or branch change (Update Source) kept the old pin, so the next rollout built the old commit against the new source. `applySourceChange` now clears it.
  - `github.resolveCommit` matched any host's `owner/repo` to a connected GitHub account. Only github.com repositories resolve now, so a GitLab repository is never pinned to a GitHub SHA.
- **Docs:** the `AppSpec.BuildCommit` doc (CRD regenerated) and the operator's `effectiveDeployRef` now name every writer. ADR018's commit-metadata note says what create, Blueprint redeploys and source changes pin.
- **Tests:**
  - `TestCreatePinsTheFirstBuildToTheCommitItsDeployRecords`: resolved and unresolved.
  - `TestABlueprintRedeployBuildsTheCommitItRecords`: resolved and unresolved, over an earlier pin.
  - `TestSourceUpdateClearsTheBuildPin`: repository and branch changes.
  - `TestResolveCommit`: a GitLab repository whose owner matches the connected account.
  - Five mutants fail them, including the shipped create and Blueprint code.
- **Gates:** backend `go test ./...`; operator `make test`; `make lint`.
- **Follow-up:** w5/152, the public resolver's five-minute cache can now pin a stale tip.
