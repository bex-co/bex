## Objective

Make the static-site Metrics tab show what a static site actually has — requests and bandwidth — instead of CPU/memory charts for pods that don't exist (static sites are served by the shared static-server, docs/ADR029-static-sites.md). Render's static Metrics page is usage/bandwidth-oriented.

## Context

- First verify current behavior on a static site: the Metrics tab (w5/m42/m43 shape) likely queries cAdvisor CPU/mem for the App's pods and renders empty charts.
- Request metrics per host exist via Traefik (`BEX_PROM_URL`, docs/ADR010-observability.md — the Network card w5/m42 built); egress metering exists (docs/ADR023-usage-metering.md). Reuse those series keyed by the static site's host(s), not pod labels.
- Keep the shared range dropdown/event-marker framework (m42/m43) — this is a per-type panel-set change, not a new page.
- Note w5 `022.md` (done): typed `srv-…` metrics requests resolve the k8s App name for Traefik lookups — the plumbing for host-keyed request metrics should already work for static sites; verify.

## Steps

1. Reproduce: open Metrics on a static site; record which panels render and which are empty.
2. Gate the Application (CPU/mem/instances) card off for `static_site`; keep/expand the Network card (requests, status codes, bandwidth if derivable from existing series).
3. Verify the request series actually match a static site's host (Traefik router labels for the shared static-server vs per-App).
4. If bandwidth per static site isn't attributable from existing series, ship requests-only and record the gap as ADR018 drift — do not build a new meter.
