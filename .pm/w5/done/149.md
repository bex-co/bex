# A build the cancel's one delete misses runs to the end: the operator's settle never stops it

Why: bex-api stops a canceled release's build with one best-effort delete after the stamp lands, and nothing retries it. A build the operator creates after that delete's list, or one whose delete failed, runs to the end and holds a workspace build-cap slot, though it can never promote.

- **Where:** `lego/operator/internal/controller/app_controller.go` `settleCanceledRelease` reverts or settles the App but stops no build. `lego/backend/internal/store/release_cancel.go` `deleteReleaseBuild` runs once per cancel, after `markReleaseCanceled`. An operator pass that read the App just before the stamp can still create the release's Job or kpack Image after it.
- **Fix:** have the operator's canceled branch delete the canceled release's build Job and kpack Image itself. It derives both names, and it is level-triggered, so it retries. bex-api's delete stays as the fast path. Check `builder=auto` and the active build recorded in status.
- **Test:** a canceled release whose Job or kpack Image exists when the operator settles the cancel is gone after the settle; a newer release's build stays.
- Found by w5/136's reviews (2026-10-07).

## Result (2026-10-07)

- **The operator stops the canceled build.** Its canceled branch (`settleCanceledRelease`) calls `build.StopRevision` for the canceled release's revision of a repo-backed service. That deletes the build Job while it runs, a Job between retries included, and the revision's kpack Image, both selected by the App's UID so a namesake's build of the same revision stays.
- **Retries until a stop succeeds.** A failed stop is logged and requeued after 30s. Once a stop succeeds, the generation is remembered per App UID, so later canceled passes skip the build plane's uncached reads. No canceled pass dispatches, so the build cannot start again. bex-api's one delete stays the fast path.
- **One definition of a running build.** `build.StopBuildJob` decides it by the Job's finished condition, not its Failed count. `deleteSiblingBuildJobs` uses it too, so a retrying sibling's cache save no longer outlives a clear-cache rebuild.
- **Tests:**
  - build `TestStopRevision` stops the running and retrying Jobs and the canceled revision's Image, and keeps the finished Job, the namesake's Job, and the later and namesake Images;
  - the envtest "Canceling a config_change mid-build" now checks that generation 2's Job is gone after the cancel, that later canceled passes read it once in total, and that a later deploy's generation-3 build runs.
- **Mutants:** six fail the tests: no stop, finished Jobs stopped, the old Succeeded/Failed counts, any owner's Job stopped, no Images stopped, and no record of the stop.
- `TestDeleteSiblingBuildJobsKeepsCurrentClearsActivePeers`' finished Job now carries the `JobComplete` condition a real finished Job has, since a running build is judged by that condition.
- **Docs and comments:** ADR060's cancel paragraph and bex-api's cancel comments no longer say nothing retries a cancel.
