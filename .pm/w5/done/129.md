# Every kpack release leaves its Image behind for the App's lifetime

Why: a buildpack service gets one kpack `Image` per release revision. It is deleted only with the App (`build.ReclaimAppArtifacts`), while build Jobs expire an hour after they finish (`TTLSecondsAfterFinished: 3600`). So every list that counts builds grows with release history, and kpack rebuilds every live Image when the ClusterBuilder changes.

- **Costs:**
  - `build.ObservingAppBuild` lists the App's Images on every queued pass, every 30s;
  - `countActiveBuilds`, the census and `TrimOvershoot` list Images namespace-wide;
  - a ClusterBuilder update rebuilds every leftover Image. While those rebuild they count as active builds: they take cap slots, and `ObservingAppBuild` reports any App with one as observing.
- **Where:** `lego/operator/internal/build/kpack.go` (`kpackImageName` hashes the UID and revision) and `artifacts.go` (`ReclaimAppArtifacts`).
- **Fix:** once a release's Image has finished and its artifact is stored (the w5/108 success pass), delete this App's Images with any other `app.bex.co/build-revision`. Keep the one the release still needs, and do not delete an Image that is still building.
- **Test:**
  - after release 2's Image succeeds and its artifact is stored, release 1's Image is gone, and release 2's stays;
  - an Image of another App, or of a release still building, is left alone.
- Found by w5/119's efficiency review (2026-10-07).

**Result (2026-10-07):**

- **Prune on store.** `build.PruneKpackRevisions` deletes an App's kpack Images, service accounts and credential Secrets from every build revision except the one just stored. `storeBuiltArtifact`, the w5/108 pass that stores a succeeded build's artifact, runs it best-effort. Release 2's stored build removes release 1's Image. A failed prune is retried by the next stored build, and anything left is swept with the App.
- **No exemption for a build still running.** The note asked to spare an Image that is still building. Under ADR060 §D1a, a build runs to completion before the next release dispatches, so once a release stores, every other revision is spent. Sparing running builds would only have kept waste:
  - an Image kpack rebuilds on its own (a service's first Image tracks its branch, w5/138);
  - a canceled release's build (w5/136).

  Deleting an in-flight Image costs at most a restarted build, because `ensureBuildpack` recreates a missing Image.
- **Scope.**
  - The App's name and UID labels select the objects, and `appArtifactOwned` checks them, so a same-named App in another workspace is untouched.
  - kpack's Builds go with their Image, their controller owner, so they are not listed.
  - `ObservingAppBuild` and `deleteSiblingBuildJobs` now share the selector (`build.AppBuildSelector`). `ReclaimAppArtifacts` shares the delete step (`deleteArtifact`).
  - `listKpackImages` no longer calls its failure "list kpack builds".
- **Simplify.**
  - Review found that the still-building rule kept exactly the Images this item exists to remove.
  - It also found that the controller test could not catch a wrong `keep`: it only checked that release 1's Image went. Both are fixed.
  - `keep` is now matched as the labels spell it, and an empty UID is refused. The ADR text moved to D1a.
- **Tests.**
  - Build-level: once gen-4 stores, gen-3 (finished), gen-2 (kpack rebuilding) and gen-1 (first build) lose their Image, service account and Secret. gen-4's and a namesake App's stay.
  - Controller: a buildpack release 2 stores its artifact; release 1's Image is gone and release 2's own survives.
  - Seven mutants each fail a test.
  - `make test` and `make lint` pass. ADR060 §D1a documents the rule.
- **Follow-ups.** All three predate this item.
  - w5/136: cancelling a buildpack release never stops its kpack build. The Image names have differed since 815e003b0.
  - w5/137: every buildpack release builds with an empty cache, because the cache tag is per revision.
  - w5/138: a new service's first build follows its branch, not the commit its deploy records.
