# Cancelling a buildpack release never stops its kpack build

Why: Cancel is one of the two preemptions ADR060 §D1a keeps for a running build, but for a buildpack service the backend deletes a kpack Image that does not exist. The build runs to the end: it holds a build-cap slot and pushes an image no release will use.

- **Where:** `lego/backend/internal/store/release_cancel.go` `deleteReleaseBuild` names the Image `appv1alpha1.BuildJobName(name, gen-N)` = `bld-<app>-gen-N`. Since 815e003b0 the operator names it `bld-<app>-gen-N-<12hex>` (`lego/operator/internal/build/kpack.go` `kpackImageName` hashes the App UID and revision), so the delete answers NotFound, which `deleteBuildArtifact` treats as already gone. The operator's `settleCanceledRelease` assumes the backend deleted the build and stops nothing itself.
- **Fix:** delete the canceled release's kpack Image by the labels the operator stamps (`app.bex.co/build`, `app.bex.co/app-uid`, `app.bex.co/build-revision=gen-N`) rather than by a name derived in a second module, or have the operator stop it when it settles the cancel.
- **Test:** cancelling a buildpack release deletes the Image the operator created for it, named as the operator names it; another App's Image of the same revision stays.
- Found by w5/129's quality review (2026-10-07).

## Result (2026-10-07)

- **Contract:** the label keys the operator stamps on build artifacts (`LabelBuild`, `LabelAppUID`, `LabelBuildRevision`) and `ReleaseBuildLabels(app, uid, revision)` live in `lego/types/v1alpha1/jobnames.go`. The operator's Jobs, kpack artifacts and `execution.LabelAppUID` use them. The Job and the kpack Image take their labels from `buildLabels`/`kpackArtifactLabels` instead of hand-built copies, and the `kpackRevisionLabel` alias is gone. bex-api's `core.PodLabelBuild` and usage's `labelBuild` copies were removed in favor of the contract.
- **Cancel:** `store.deleteReleaseBuild` lists the canceled release's kpack Images in the build namespace by `ReleaseBuildLabels`, with the UID `markReleaseCanceled` re-reads, and deletes each; a cluster without kpack has nothing to stop. It tries the Job and the Image both and joins their errors, since nothing retries a cancel once its stamp lands.
- **Tests:** `build.TestKpackImageReleaseLabelsCrossModuleContract` pins the keys' literals and that release 3's Image matches its selector while release 4's does not. `store.TestCancelReleaseStopsItsBuild` runs through `CancelRelease` with a UID-less caller copy: the Job and the hashed-name Image go; a recreated namesake's gen-7 Image and the App's gen-8 Image stay; the list stays in the build namespace; a failed Job delete still stops the Image and is reported; no kpack reports nothing. `deploys.TestCancelDeletesInFlightKpackImage` had encoded the bug (an unlabeled Image named like the Job) and now builds the operator's shape. 15 mutants fail the tests, including the shipped by-name delete.
- **Docs:** ADR060 §D1a "Cancel reaches buildpack builds"; ADR018's Cancel-deploy row names both build shapes.
- **Residual, filed as w5/149:** an operator pass that read the App before the stamp can create the Image after the cancel's list, and the operator's settle stops nothing, so that build runs to the end in a build-cap slot. It can never promote, and the next stored build's w5/129 prune removes it.
