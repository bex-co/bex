## Objective

Add Render-shaped alias routes to the dashboard that redirect `/{web|worker|pserv|static|cron}/$serviceId` (and any sub-path, e.g. `/web/srv-x/deploys/dep-x`) to the canonical `/services/$serviceId/...` routes, preserving the remainder of the path and the query string.

## Context

- Canonical routes: `dashboard/src/routes/services.$serviceId.tsx` + tab children (`index`, `deploys.index`, `deploys.$deployId`, `env`, `events`, `logs`, `metrics`, `plan`, `scaling`, `settings`).
- All five segments accept any `srv-` id — do not validate segment↔service-type (Render's CLI falls back to `web` for unknown types; strict validation breaks its links).
- TanStack Start file-based routing; a catch-all `dashboard/src/routes/$.tsx` already exists — aliases must win over it. A splat child under each alias (e.g. `web.$serviceId.$.tsx` or a shared loader doing `redirect()`) keeps sub-paths.
- Sub-tab names that differ between Render and bex (per t001's table) get an explicit segment-mapping in the redirect; unknown sub-paths fall through to the service root.

## Steps

1. Implement the five alias route families with a shared redirect helper (one module, five thin route files — or a single dynamic segment route if TanStack matching allows constraining to the five values).
2. Preserve sub-path + search params in the redirect; map any differing tab segment names from t001.
3. Route-tree test: `/web/srv-x` → `/services/srv-x`, `/cron/srv-x/deploys/dep-y` → `/services/srv-x/deploys/dep-y`, unknown segment still 404s via `$.tsx`.

## Files

- `dashboard/src/routes/` (new alias route files)
- `dashboard/src/routes/__tests__/` (redirect tests)

## Acceptance criteria

- [ ] All five segments redirect to the canonical service routes, sub-paths and query preserved.
- [ ] `yarn test` passes; no existing route behavior changes.

## Out of scope
