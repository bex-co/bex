## Objective

Carry the authoritative metadata needed by the populated Project table through GraphQL list operations and the dashboard's service/database/key-value view models.

## Context

- `AppView` already has `Runtime`, `Region`, and `UpdatedAt`; the GraphQL Service type exposes `runtime` and `updatedAt` but not `region`.
- `PostgresView` and `KeyValueView` already expose `region` and `updatedAt` in GraphQL.
- Dashboard list documents currently omit these fields: `Services` omits runtime/updatedAt and cannot query region; `Databases` and `KeyValues` omit region/updatedAt. Their list view models therefore cannot normalize the facts for `ResourceRow`.
- `w6/m28` and `w9/m42` established `resourcemeta` and datastore GraphQL metadata. Reuse those sources; do not derive timestamps in the browser.

## Steps

1. Add `region` to the backend GraphQL Service type, resolved from `AppView.Region`, with parity coverage alongside `updatedAt`.
2. Select runtime/region/updatedAt in the dashboard resource list operations as applicable.
3. Extend `ServiceView`, `DatabaseView`, and `KeyValueView` plus their projection helpers with nullable metadata.
4. Regenerate dashboard GraphQL definitions through the repository's codegen path.
5. Cover configured and omitted region, missing runtime, and independent created/updated timestamps.

## Acceptance criteria

- [ ] Every supported project resource row receives nullable runtime/region/updatedAt from server truth.
- [ ] Service `region` is present in GraphQL and uses the same explicit `BEX_REGION` source as REST; unset stays null/empty.
- [ ] `updatedAt` remains distinct from `createdAt`; no client-side approximation is introduced.
- [ ] Backend and dashboard projection tests cover populated and omitted values.

## Out of scope

- Making region user-selectable; per-resource placement is not a bex capability.
- Rendering the fields (t005).
