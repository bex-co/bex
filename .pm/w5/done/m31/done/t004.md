## Objective

Repair the dead end: deleting, suspending, or deploy-overriding a service in a protected environment currently fails with a raw backend error because the dashboard never sends `ProtectedConfirmation`. Detect the named error (or pre-check the service's environment `protectedStatus`), show a typed-confirmation dialog (the `workspaces.DeleteConfirmation` UX pattern, wording per t001's capture), and re-issue the verb with the confirmation.

## Context

- Backend guard: w6/m19's `apps` destructive-verb guard (`protection.go`) — Delete/Suspend(not Resume)/existing-service deploy-override require the echoed confirmation.
- Dashboard flows to touch: danger-zone delete (w5/m14), suspend control, and the create/deploy override path if reachable in UI.

## Files

- `dashboard/src/features/services/` (delete/suspend flows) + shared confirmation dialog component

## Acceptance criteria

- [x] A protected service is deletable/suspendable in a real browser via the typed confirmation; an unprotected service's flows are unchanged; the raw-error dead end is gone; tests cover both paths.

## Out of scope

- Changing the backend guard's semantics.

## Resolution

Added one server-phrase parser and shared typed retry dialog, then threaded `confirm` through suspend, delete, and Blueprint sync. Blueprint sync gained adapter parity on REST/GraphQL/MCP. Real-browser retries succeeded only for `sudo suspend service m31-suspend`, `sudo delete service m31-delete`, and `sudo deploy service m31-blueprint`; unit/component tests cover wrong, correct, protected, and ordinary paths.
