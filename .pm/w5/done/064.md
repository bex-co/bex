# 064 — A failed deploy's reason never reaches the CLI: the build-log narration closes with a bare `==> Deploy failed` while the actionable cause sits only in the events feed

Why: bex computes an excellent, specific reason for every deploy failure and then publishes it to the one surface the CLI has no command for — so the terminal narration a CLI user actually reads says only that something failed.

- **Severity:** major (a supported, routine failure path is undiagnosable from the primary automation surface; no data loss).
- **Attribution:** server (log narration omits a field it already has durably).
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-15 UTC, sweep 6. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, human device login, `bex v0.2.1` / upstream pin v2.27.0, `https://api.bex.co/v1/`. Fixture `qa-20260915-46a2ca-static` (`srv-daktj30b3bfc73eq7upg`), created and deleted inside the run.

## Reproduction

A static site pointed at a publish directory that does not exist in the repo:

```text
$ bex services create --name qa-…-static --type static_site \
    --repo https://github.com/bex-co/bex --branch main \
    --root-directory examples/static-site --publish-directory public --confirm -o json
# exit 0

$ bex deploys list srv-daktj30b3bfc73eq7upg -o json
[{"id":"dep-daktj30b3bfc73eq7uq0","status":"update_failed", …}]     # no reason field

$ bex logs --resources srv-daktj30b3bfc73eq7upg --type build --limit 20 -o text
2026-09-15 23:49:32  ==> Build queued
2026-09-15 23:49:36  ==> Building from https://github.com/bex-co/bex@11d96a5
2026-09-15 23:50:06  ==> Deploy failed
```

That is the complete CLI-visible account. The reason exists and is precise — `GET /v1/services/{id}/events`, same run:

```json
{
  "type": "deploy_ended",
  "details": {
    "deployStatus": "failed",
    "fullDeployStatus": "update_failed",
    "failureReason": "clone: the publish directory \"examples/static-site/public\" does not exist in the repository at \"main\" (exit 2)"
  }
}
```

The pinned CLI has **no events command** (neither does Render's), so nothing a CLI user can type reaches that string.

Second instance, same sweep family (sweep 4, `srv-dakss49cin2c7382cj9g`): a failed pre-deploy closes with `==> Pre-deploy failed` in the build log while `failureReason` reads `"the pre-deploy command exited with code 128; check the pre-deploy logs"`.

Contrast a failure that *is* diagnosable (sweep 5, bad branch): the build log carried `fatal: couldn't find remote ref does-not-exist-qa088e01` — but only because git's own stderr leaked into the build stream. Wherever the failing check is **bex's own**, nothing leaks and the narration stays bare.

## Root cause

`lego/backend/internal/logs/progress.go` synthesizes the platform narration lines the CLI reads (`type=build`, container `platform`):

- `terminalLine(status, serviceType)` maps a terminal status to a fixed string — `"==> Build failed"`, `"==> Pre-deploy failed"`, `"==> Deploy failed"`, `"==> Deploy canceled"` — with no parameter for a reason.
- Its input struct `DeployProgress` carries `ID / Status / Image / Commit / CreatedAt / StartedAt / FinishedAt` and **no failure-reason field**, so the narration layer structurally cannot include one.
- The reason is durable and already modelled: `store.EventFact.FailureReason`, documented in `lego/backend/internal/store/events.go:87-90` as "the human-actionable cause stamped when the reconciler…", surfaced by `w1/m138` in `deploy_ended.details.failureReason` alongside `fullDeployStatus`.
- `docs/ADR018-render-parity.md` records that placement deliberately, noting "Render's own `deploy_ended.details` has no failure reason, so the check is consistent extras across the three adapters" — i.e. the field was added as a bex extension on the **events** surface only, and the log narration was never revisited.

## Fix (~40m)

Carry the reason into the line the CLI already reads:

- Add `FailureReason string` to `logs.DeployProgress` and populate it in the composition root that adapts `store.Deploy` (the same place `Status`/`Commit` are filled).
- Have `terminalLine` append it when present: `==> Deploy failed: clone: the publish directory "examples/static-site/public" does not exist in the repository at "main" (exit 2)`. Keep the bare line when the reason is empty, so no status loses its current text.
- This is parity-improving, not a divergence: Render's deploy log stream carries failure detail; bex's narration contract lives in `docs/render-artifacts/live-deploy-following.md` § Platform progress-line contract and must be updated in the same change.
- Multi-line reasons (the clone-step reason embeds a newline) need a decision — either one line per segment or a flattened single line. Prefer segments, since the stream is line-oriented and the deploy id is already the `instance` label.

This also substantially closes `w5/062` from the CLI side: a pre-deploy failure would narrate its exit code and cause even though the step's own stdout stays behind the `predeploy` log type. The two are complementary — `062` is about the command's output, this is about the platform's reason — and `062` should cite this note.

## Blast radius

`logs/progress.go` and its composition root; the deploy-detail log viewer in the dashboard, which renders the same synthesized lines and would now show the reason twice (it already displays `failureReason` beside the row — check for duplication); the `w1/m138` events contract is untouched. Line ids derive from `logID(instance+timestamp+message)`, so changing the message text changes the id — confirm the live-tail dedupe against store reads still holds, since that dedupe is exactly what the narration comment relies on.

## Regression checks

- A static site whose publish directory is missing: `bex logs --type build` contains the publish-directory reason; the test asserts the rendered line, not just that a field is populated.
- A failed pre-deploy narrates its reason; a failed clone narrates its reason without losing git's own stderr line.
- A successful deploy still narrates exactly `==> Your service is live 🎉`, and a cron job still gets `==> Cron job deployed — runs on schedule 🎉`.
- A terminal status with an empty reason still emits the current bare line.
- Live-tail/store dedupe: the same deploy read twice produces identical ids for the narration lines.
