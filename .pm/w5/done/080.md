# The Blueprint compiler refuses `dockerCommand` on `runtime: image`

Why: REST, MCP and GraphQL can set an image service's command (`dockerCommand` becomes the start command; w4/188, w5/073), but a `render.yaml` image service with `dockerCommand` is refused. So the same service can't be declared as a Blueprint.

Source: found in w5/073's `/simplify` review, 2026-10-05.

## Where

- `lego/backend/internal/apps/deploy.go:2343` (`manifestStartAndAutoDeploy`): `dockerCommand requires runtime: docker`.
- `lego/backend/internal/apps/blueprint_compiler.go:298-301` repeats the docker-only rule.
- Render's Blueprint spec defines `dockerCommand` as "the command to run when starting the Docker-based service" but documents it under "Building from a Dockerfile". So whether Render accepts it with `runtime: image` is unverified.

## Fix (~45m)

1. Research Render's behavior first: does a `render.yaml` with `runtime: image` plus `dockerCommand` validate and apply on Render? If Render refuses it, close this note as matching Render and record that in ADR049.
2. If Render accepts it: map `dockerCommand` to the start command for `runtime: image` in both compiler paths, and keep the both-spellings refusal.
3. Generate Blueprint should then export an image service's command as `dockerCommand`.
4. Tests: a Blueprint image service with `dockerCommand` stores `spec.startCommand`; the generate → parse round-trip keeps it.

Done: a `render.yaml` image service can declare its command the same way the API can, or the divergence is recorded as matching Render.

## Outcome (2026-10-06)

Done.
1. **Render research.** Render's own render.yaml schema (vendored at `lego/backend/internal/apps/schema/render.yaml.json`) puts `dockerCommand` on `serverService` and `cronService` with no runtime condition, so Render validates `runtime: image` with `dockerCommand`. bex's REST, GraphQL and MCP already set an image service's command this way (w4/188, w5/073), and the dashboard edits it as the image's Docker Command (w5/m124).
2. The compiler (`blueprint_compiler.go`) and the apply path (`deploy.go` `manifestStartAndAutoDeploy`) accept `dockerCommand` for `runtime: docker` or `image`; it becomes `spec.startCommand`. A native runtime is still refused, and so is declaring both spellings.
3. Generate exports a service's (and a cron's) command as `dockerCommand` when its build reads one. That uses `readsDockerCommand(buildStrategy(spec))`, the same rule `dockerDetails.commandApplies` applies to a create.
4. Tests: an image service's `dockerCommand` stores `startCommand`, re-plans as noop and is generated back as `dockerCommand`; both spellings are refused; the compiler accepts web and cron image commands with zero problems and refuses a native one; there is a round-trip shape; and the two tests that pinned the old refusal now pin the new rule. ADR049 records the rule, and the `StartCommand` CRD doc says docker or a prebuilt image (CRD regenerated).

Mutants each fail a test (compiler, apply, export spelling). `make lint`, operator `make test` and the apps package green. Follow-up: w5/102, a buildpack build's dockerCommand, which the API ignores but a Blueprint takes.
