# Route search validators that omit a rejected key leak its raw value to readers

Why: TanStack sets `match.search = {...raw, ...validated}` (`router-core/dist/esm/router.js:688-691`), so a validator that omits a bad key hands its raw value to every reader. w5/078 fixed the create route and the two crashes (deploy `?r=12h`, project `?q=123`); four other routes still leak real bad values.

- **Logs `?type=`** (`dashboard/src/features/logs/lib/log-search.ts`): `?type=bogus` reaches bex-api and gets a 400 "unknown log type", and `write({...search})` (`routes/services.$serviceId.logs.tsx`) writes the junk back to the URL. Start the parsed object from the file's own `CLEARED_LOG_SEARCH`, which also covers the `t`/`r` placeholder keys.
- **Agents `?phase=`** (`routes/agents.tsx`): `?phase=bogus` switches the page to list mode, and the list query fails with "unknown phase filter". `fromPhase` (`routes/agents_.$agentSessionId.tsx`) carries it into the Back link.
- **`/settings`** (`routes/settings.tsx`, read with `useSearch({strict:false})`): `?git_error=1` shows a spurious GitHub error, `?addKey=1` opens the dialog, and `?returnTo=123` falls back to `/`. `safeNext` checks the type, so this is not an open redirect.
- **Key Value `?tab=`** (`routes/keyvalue.$keyValueId.tsx`): `?tab=bogus` leaves no tab highlighted.
- **Latent:** today's readers re-check these values: `parseRangeSearch` (`features/metrics/lib/range.ts`), `index.tsx` `new`, `workspace.settings.tsx` `plan`, and agents `view`.
- **Fix:** add a helper in `dashboard/src/common/lib/search-params/` that sets every declared key to undefined before applying the parsed result, and use it in each validator. A validator annotated `{ k?: T }` may return `k: undefined`; the key stays optional for navigation (`exactOptionalPropertyTypes` is off). Test each route with its bad value, as `src/routes/__tests__/deploy-log-range-search.test.ts` does.
- **Size:** about 1h. Found by w5/078's reuse review.

**Result (2026-10-07):**

- **Validators.** Nine validators now return every key they own, `undefined` when rejected:
  - logs: `parseLogSearch`, which now reads its range through `parseRangeSearch`;
  - agents: `phase`, `view` and `archived`;
  - agent detail: `fromPhase` and `fromArchived`;
  - `/settings`;
  - Key Value and Postgres: `tab`;
  - `/`: `new`;
  - `/workspace/settings`: `plan`;
  - `parseRangeSearch`, used by metrics, Key Value and Postgres.
- **No new helper.** I used the explicit-`undefined` idiom the auth routes and w5/078 already use, not the suggested helper, and added the rule to `dashboard/AGENTS.md`'s code standards.
- **Settings readers.** They read the route's own validated type (`getRouteApi("/settings")`) instead of a cast whose `addKey?: boolean` hid the raw number 1.
- **Home-page test.** `index.test.tsx` ran a copy of the old validator; it now runs the route's own.
- **Redirect.** A link carrying a rejected value now redirects once to its canonical URL. Verified live on dev-5:
  - `/services/<id>/logs?type=bogus&live=yes`: one document load, the canonical URL, the logs view rendered, and no 400;
  - `/settings?git_error=1&addKey=1`: no GitHub error and no form;
  - `?addKey=true` still opens the form.
- **Tests.**
  - `src/routes/__tests__/search-validators.test.ts` pins eleven validators with `toStrictEqual`: these nine plus w5/078's two deploy routes, whose test it absorbs. The older rejection assertions moved to `toStrictEqual`.
  - Mutants restoring the omit form fail them.
  - Dashboard lint and tests pass: 481 files, 4356 tests.
