# Generate Blueprint exports a service's registry credential

Why: a service bound to a private registry credential exports without its `registryCredential`, so the service a sync creates from the file falls back to the newest credential for the image host, or to none, and a private pull can fail.

- **Today:** `generateServiceEntry` (`lego/backend/internal/apps/blueprint_generate.go`) never emits `registryCredential` or `image.creds`, though the parse resolves both by name (`fromRegistryCreds: {name}`, w8/m19 t005).
- **Fix:** resolve `spec.registryCredentialId` to the credential's name through the `RegistryCreds` seam and emit `registryCredential: {fromRegistryCreds: {name}}`; an explicit empty binding (no credential) has no render.yaml spelling, so list it as not exported.
- **Test:** add a bound credential to `TestGenerateBlueprintRoundTripsRealCreates` with a fake credential store; its create probes clear `RegistryCredentialID` today because the test runs without one.

Source: w5/m117's round trip (2026-10-05).

## Outcome (2026-10-06)

Done.
1. `generateServiceEntry` exports a bound credential by its workspace name (`exportedRegistryCredential`): on `image.creds` for a prebuilt image, as Render spells it, else on `registryCredential`. The parse already resolves both by name.
2. An export carries only a credential that would sync. It omits one in each of these cases:
   - an explicit binding to none, which render.yaml cannot spell;
   - a binding the build no longer reads (a Dockerfile build since moved to a native runtime keeps it);
   - a credential since deleted;
   - a name another credential shares. Names are not unique, since an unnamed credential is named for its host, and the parse refuses an ambiguous name, so exporting it made the file unsyncable. The name must resolve back to the same id.

   A store error from that check fails the export. A failed id→name lookup still reads as a deleted credential, because `ResolveCredentialNames` reports none; the doc comment says so.
3. Tests:
   - `TestGenerateBlueprintRoundTripsRealCreates` now runs with a credential store. Its parse resolves names as a sync does, and its creates include a bound image, a bound Dockerfile build, and an explicit binding to none. The last is listed in `blueprintNotExported`.
   - `TestGenerateBlueprintNamesTheBoundRegistryCredential` pins the spelling and the four omissions.
   - Mutants are caught: export off, applicability ignored, ambiguity propagated, no resolve-back.
4. ADR018's Blueprint row no longer lists the binding as not exported.
