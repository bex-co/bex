# Two more writes lose a reconcile pass's unsaved status

Why: w5/096 fixed the App metadata patches that discarded a pass's in-memory status. Two writes of the same kind remain.

- **Patches that land on a copy of the App.** `desiredReplicas` receives `effectiveApp`, a copy whenever a release config is selected or pending sources are kept (`lego/operator/internal/controller/release_config_selection.go`, `saved_configuration.go`). Its last-active stamp and autoscale patches land on that copy.
  - The pass's own `app` keeps the old resourceVersion, so its status write conflicts and the pass retries.
  - The `Status.Autoscaling` "Started" record set on the copy is lost.
  - Fix: patch and record on the pass's `app`, and only read from `effectiveApp`.
- **The Database major-upgrade-failed spec revert.** `database_controller.go` patches `spec.version` back on `db` itself, so the server's object overwrites status the pass has not written yet: `CurrentVersion` just read from the cluster, connection fields, exports, last backup. The Failed status write after it then saves the server's values. It heals on the next pass, and the branch is rare.
  - Fix: patch a copy under the read resourceVersion, as `patchAppMeta` does.
- Test: an App with a selected release config whose autoscaler stamps a scale-down keeps its status write. A failed major upgrade records the cluster's current version in its Failed status.
- Found by w5/096's reviews (2026-10-06).

**Result (2026-10-07):**

- **Writes land on the pass's App.**
  - `desiredReplicas` now takes the pass's own App and the configured replica count, `desiredReplicas(ctx, app, configured, obs)`, instead of the projected runtime copy. `planReplicas` passes `effectiveReplicas(effectiveApp)`.
  - The last-active stamp and the autoscaler's patch and `Started` record now land on the pass's App. Before, on the copy, the App kept its old resourceVersion: a status write in the same pass could conflict, and the lost `Started` record let every 5 s rollout poll re-read metrics and decide again.
  - No App copy reaches `desiredReplicas`, so the bug cannot come back through it.
- **The Database revert patches a copy.** The failed-major-upgrade revert patches a copy under the read resourceVersion (`MergeFromWithOptimisticLock`, as `patchAppMeta` does) and carries back only the metadata and `spec.version`.
  - Patching `db` itself had decoded the server's object over the status the pass had set but not yet written: the cluster's `currentVersion`, connection fields and the rest. The Failed write then saved the stale values.
  - A concurrent edit now conflicts and requeues instead of being overwritten.
- **Tests.**
  - `TestASelectedConfigsAutoscalerWritesThePassApp` uses an App on release 1's selected config: 2 replicas against a spec of 3. A scale-up to 3 records `Started 2→3` on the pass's App, and its status write succeeds. Passing the copy as the App, or the App's own count, each fails it.
  - `TestAFailedMajorUpgradeRecordsTheClustersVersion`: the stored version is 15 and the cluster is on 16, so the Failed status must record 16. HEAD's code stores 15.
  - `make test` and lint pass.
- **Follow-up:** w5/121. Two cron `Status().Patch` calls still replace the pass's unsaved release decision, and the `patchAppMeta` AST guard does not cover status patches or `db`/`kv`.
