# A crashed create's other projection leg outlives the service that takes its name

Why: since w5/135 a create takes over the abandoned prepared Secret of the leg it seeds (env or files). A crashed create may have prepared both legs, and the leg the new create does not seed stays behind:
- its store map persists (store-off), so the new service inherits the crashed create's keys on its first write;
- or, once the maps are purged, its ownerless Secret keeps the crashed data at a higher revision, and `projectSource` treats an ownerless Secret as the App's own. A later `SetEnvVar` answers OK while the projection stays the stale one.

A create that seeds nothing proceeds past both legs.

- **Where:** `lego/backend/internal/secrets/projection.go` around :154–168 (`projectSource` takes an ownerless Secret as the App's own) and `files.go` `PrepareCreateSecrets` (only seeded legs are touched).
- **Fix:**
  - In `projectSource`, treat an ownerless Secret that `abandonedPreparation` flags as a predecessor and replace it, as w5/118 does for a deleted App's.
  - In `PrepareCreateSecrets`, `abortProjection` an unseeded leg whose Secret is vacated, so the new service starts clean.
- **Test:** a crashed create with both legs, followed by a create seeding only files. The env leg's stale Secret and map are gone, and a later env write projects.
- Found by w5/135's quality review (2026-10-07). Store-on deployments are covered by the apps row's UNIQUE (tenant, name), which holds the name while the create's row exists.

## Result (2026-10-07)

- **Unseeded legs are released.** A create now claims, and at once releases, each leg it does not seed whose Secret exists (`secrets.releaseUnseededLegs`, first in `PrepareCreateSecrets`). The claim is the one a seeded leg makes, so it takes over a crashed create's abandoned preparation or a deleted namesake's Secret, and refuses with 409 a leg anybody still holds. The release removes the store map, then the Secret, detached from the request. The new service inherits neither the leftover's keys nor its revision.
- **Creates that seed nothing release too.** When the seeder is wired, a create seeding nothing goes through it (`apps.writeNewApp`). It costs one Secret read per unseeded leg, and the commit makes no call for such a create.
- **A failed store delete keeps the name.** `abortProjection` no longer removes the Secret when the store delete failed. The Secret keeps holding the name until a later create takes the abandoned claim over, and that create removes the map. Before, the map outlived a vanished Secret and passed to the next service.
- **Existing services replace the leftover.** A service created beside an abandoned preparation before this fix replaces it on its first write, whatever revision it records. A failed CAS save still restores that Secret as the service's own (`ExistedBefore` counts only another App's Secret as replaced), because the service may have adopted nothing after a crash past its App create.
- **Tests:**
  - `TestACreateReleasesTheLegsItDoesNotSeed`, for a create seeding only files and one seeding nothing;
  - `TestACreateLeavesAHeldUnseededLegAlone`;
  - `TestAServiceReplacesAnAbandonedPreparationAtItsName`;
  - `TestACASRollbackRestoresAServicesOwnUnadoptedSecret`;
  - `TestAReleaseThatCannotRemoveTheMapKeepsTheName`;
  - apps `TestACreateWithoutSecretsStillPrepares`.
- **Mutants:** ten fail the tests:
  - no release;
  - files never released;
  - release without a claim;
  - the claim's refusal ignored;
  - inverted legs;
  - no abandoned predecessor;
  - owner references ignored;
  - HEAD's direct empty-seed create;
  - `ExistedBefore` counting the abandoned preparation;
  - the Secret deleted after a failed store delete.

  The release's detached context has no test, because the fakes ignore cancellation. It mirrors `prepareProjection`'s rollback.
- **Docs:** ADR013.
