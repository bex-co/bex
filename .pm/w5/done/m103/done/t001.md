Establish the facts before changing anything: bind an API key to a workspace, then observe what the member list, seat usage, the Team page and the member mutations actually do with that row. The premise of this milestone is a code read, not a live observation — if it is already handled, the milestone re-scopes to t004 and closes.

## Context

- `PGStore.BindClient` (`lego/backend/internal/store/store.go:800`) inserts a `tenant_members` row with the client id as subject and role `developer`.
- `ListTenantMembers` (`internal/store/workspaces.go:209`) selects every row for the tenant with no subject filter.
- `members.List` enriches via Kratos (`members/service.go:411`) — a client id will miss, producing `identityResolved: false`, which w4/070 defined as "a human whose identity no longer resolves" (ADR024 § Member identity).
- Seat math: `store.CanAddMember` and `SeatUsage` (`members/service.go:450`, `:472`) — Render's `owner.usage.users`.
- Subject kinds are distinguishable: Kratos identity ids vs Hydra client ids; check `internal/id` and how `Identity.Method` is derived before inventing a heuristic.
