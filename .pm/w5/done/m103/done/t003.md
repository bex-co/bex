## Objective

Close the write side of the same confusion: `ChangeRole` and `Remove` refuse a machine subject with a coded error that names where the credential is actually managed, so a key's workspace binding cannot be half-severed from a surface that does not own it.

## Context

- A key's binding is `apikeys`' business: it is written by `BindClient` and cleared by `UnbindKey` (`lego/backend/internal/api/tenancy.go:472`), alongside the key's own FGA grant. A `members.Remove` against it deletes the row from underneath that feature.
- The guard belongs next to `m101`'s `guardSelf` / `guardOwner` in `members/service.go`, using the discriminator from t002.
- Error code should follow the same vocabulary as m101's: coded, identical on REST/GraphQL/MCP.

## Steps

1. Add the machine-subject guard to `Remove` and `ChangeRole`.
2. Carry the code across the three adapters.
3. Assert the key keeps working after a refused attempt.
4. Confirm the `apikeys` surface remains the one place a binding is created or cleared.

## Files

- `lego/backend/internal/members/service.go`, `rest.go`, `graphql.go`, `mcp.go`
- `lego/backend/internal/members/members_test.go`

## Acceptance criteria

- [ ] Member mutations against a machine subject are refused with one coded error on all three surfaces.
- [ ] The key's binding and function are unchanged after the refusal.
- [ ] Human members are unaffected.

## Out of scope

- Changing how API keys are bound or revoked.
