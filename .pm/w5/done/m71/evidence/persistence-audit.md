# Agent-session persistence audit — 2026-08-17

## Incident

Production session `ags-da1m1ah0htvc73dtrkug` accepted two turns and produced assistant output for both, but a refresh showed no submitted chat message. The durable transcript contained 478 assistant stream parts (turn 1: local parts 0–355; turn 2: 0–121) and no user-role event. The follow-up existed only in the dashboard's optimistic React state and the fresh sandbox's `BEX_AGENT_PROMPT`; terminal reconciliation then removed the optimistic bubble because `session.turns` had advanced.

The core contract error was treating an AI SDK **response** stream as a complete conversation record. A response stream represents assistant output; it does not durably recreate the submitted user message. AI SDK's own persistence guidance stores the complete `UIMessage[]`, reloads those messages into `useChat`, and treats `UIMessage.role` as source-of-truth ([message persistence](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence), [resume streams](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams), [`UIMessage`](https://ai-sdk.dev/docs/reference/ai-sdk-core/ui-message), [`useChat`](https://ai-sdk.dev/docs/reference/ai-sdk-ui/use-chat)). Bex instead had neither durable user messages nor a role-correct replay adapter.

## Historical contract drift

- `.pm/w3/done/m43/done/t001.md` promised that each turn's prompt would be recoverable from transcript alone, but only assistant response parts were stored.
- ADR047 D9 described a globally ordinal-keyed, byte-transparent tee and made live `POST` the prompt-turn authority; those claims did not survive redispatch or durable-role requirements.
- ADR051's “skip a turn when any part exists” optimization contradicted partial live tee recovery, and its 4 MiB/parts-cap wording did not match the driver's 16 MiB recorder.
- ADR059 did not distinguish workspace-only Resume from a new prompt turn.
- ADR065 made durable transcript reads first-class but omitted user intent and completeness.

## Resulting contract

1. `agent_session_turns` is the accepted user-intent ledger. `turns` is its accepted-turn count, not a sandbox-dispatch count.
2. `agent_session_transcripts` is assistant output. `(session, turn, part_index)` is idempotent identity; `seq` is only the stable global replay cursor.
3. A settled turn states whether assistant history is complete and why it is not. Retained prefixes remain readable.
4. Stream replay is an adapter: stored assistant payloads remain verbatim, while the gateway adds the minimum role/turn framing required to form a valid durable conversation.
5. Existing sessions recover only the initial task that still exists in `agent_config`. Historical follow-up text was never stored and remains explicitly unrecoverable.
