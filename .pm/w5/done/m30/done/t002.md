## Objective

Make the service-detail data model carry `runtime`, `builder`, `startCommand`, and `dockerfilePath`, so Settings renders persisted values and can gate Docker-only controls from backend truth without breaking legacy Dockerfile-built Apps.

## Context

- The backend GraphQL `Service` type already resolves all four fields.
- `dashboard/src/features/services/api/server.graphql` does not select them today.
- `ServiceView` and `toServiceView` likewise omit them, so a component-only change would show empty values and guess applicability.

## Steps

1. Select the four fields in the detail query and regenerate GraphQL definitions.
2. Add nullable fields and documentation to `ServiceView` and map them in `toServiceView` without changing list-query behavior.
3. Extend projection tests for populated and absent values.

## Acceptance criteria

- [x] A detail response with all four values maps them exactly into `ServiceView`.
- [x] A list response or unset field maps to `null` without inventing a runtime or default path/command.

Projected `runtime`, `builder`, `startCommand`, and `dockerfilePath` through the detail query and `ServiceView`, regenerated the combined GraphQL definitions, and covered populated and absent values.
