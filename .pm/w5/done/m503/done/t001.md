## Objective

Find which request shapes are slow and why, before changing anything.

## Context

- The handler builds a LogQL `query_range` per read (`lego/backend/internal/logs/loki_streams.go`, `loki.go`); `lokiFetchLimit` caps lines per request.
- Production Loki is reachable read-only with the production kubeconfig (`scripts/fetch-app-kubeconfig.sh`, then `kubectl -n monitoring port-forward`).

## Steps

1. Write a small harness (a Go test behind a build tag, or a script) that prints the LogQL and parameters the handler sends for representative requests: windows of 1h, 24h, 7d and 30d; `type` app, request and build; with and without a text or status filter; both directions; `limit` 100 and 1000.
2. Time each against production Loki for a busy service and an idle one.
3. Record the table and the dominant cause (for example a wide window scanned whole before `limit` applies, a line filter Loki cannot push down, or JSON parsing of every request line) under `## Findings`.

## Files

- A harness file under `lego/backend/internal/logs/` or `scripts/`
- .pm/w5/m503/README.md (Findings)

## Acceptance criteria

- [ ] The Findings table names the shapes that take over 10 s and why.

## Out of scope

- Changing the query (t002).

## Outcome (2026-11-19)

Done: the harness is `lego/backend/internal/logs/loki_timing_test.go` (build tag `lokitiming`), and the table and causes are in the milestone README's Findings. `limit` 1000 was not timed apart: the API clamps it to 100 (`maxLogLimit`).
