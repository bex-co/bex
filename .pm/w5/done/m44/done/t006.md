## Objective

Wire the combined draft to Render's split save action: Save only, Save and deploy, or Save, rebuild, and deploy. Each path must have truthful progress/result UX, cause no duplicate rollout, and leave a recoverable draft when a later step fails.

## Context

- `save_only`: t002 batch patch with no rollout.
- `deploy`: t002 batch patch with one rollout of the current image and no build.
- `rebuild`: save-only batch patch followed by the existing `triggerDeploy` full build. The initial patch must not roll; if the deploy trigger fails, configuration remains saved and the UI must say exactly that.
- Current `useTriggerDeploy` already refetches deploy history/events and returns the new deploy id. Repo-backed `deploy_only` is deliberately unsupported and is not needed for the env rollout path.

## Steps

1. Add the split save menu and type-appropriate labels/disabled states.
2. Compose the batch mutation and deploy trigger without an intermediate pod roll; navigate/link to the new deploy when available.
3. Preserve the draft and identify which phase failed; offer Retry without duplicating the successful phase.
4. Guard tab close/navigation while dirty, and make Cancel/Discard explicit but non-destructive to server state.
5. Refetch keys/names/service/deploys/events after success and show one concise toast.

## Acceptance criteria

- [ ] Save only causes no immediate rollout; Save and deploy causes exactly one no-build rollout; rebuild causes one source build/deploy and no preliminary rollout.
- [ ] Cancel and navigation-discard never write; dirty navigation warns accessibly.
- [ ] A save-success/deploy-failure state says config was saved, keeps a retryable action, and never repeats the patch silently.
- [ ] No-op drafts cannot submit.

## Out of scope

- Adding cached-artifact `deploy_only` support for repo services.
- Changing header Manual Deploy semantics.
