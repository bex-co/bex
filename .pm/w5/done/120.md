# The autoscaler's scale-down window has three more gaps

Why: w5/109 voids a pending scale-down when the signal recovers, but the stabilization stamp still records only when a dip began. It also survives readings it never sees, and an unreadable stamp freezes it, so a scale-down can still commit on one low reading, or never commit.

- `lego/operator/internal/controller/autoscale.go` `applyAutoscaling`:
  - **An unreadable stamp holds forever.** A stamp that fails to parse holds every dip and is never re-stamped, so a sustained dip never scales down. w5/109 at least clears it on the next decision at or above the current count. Fix: treat a parse error as no stamp, then re-stamp and hold.
  - **Depth is not tracked.** A shallow dip (want 4 of 5) stamps the window, and one deep reading after it (want 1) commits the deep count at once. HPA instead commits the highest recommendation seen within the window. Fix: record the highest desired count while the window runs, alongside the stamp, and commit that.
  - **The stamp outlives passes that skip autoscaling.** `desiredReplicas` (`app_controller.go`) calls `applyAutoscaling` only while autoscaling is on and the App is not suspended. A stamp from before a suspend, or before autoscaling was turned off, therefore survives. Once the App resumes after the window, one low reading commits. Fix: clear the stamp whenever autoscaling does not run for the App, or record when it last ran.
- Test: each case holds a dip for a full window from its own start.
- Found by w5/109's quality review (2026-10-07).

**Result (2026-10-07):**

- **An unreadable stamp restarts the window.** A stamp that does not parse counts as no stamp: the pass stamps anew, records its reading, and holds a full window. Before, it held every dip forever.
- **Depth.** A new annotation, `app.bex.co/autoscale-scale-down-to`, records the highest count any reading asked for while the window runs. It is written only when that count rises. Once the window elapses it commits that record, like HPA's stabilization, so one deep reading at the end of a shallow dip no longer scales past what the whole window supports. A continuing dip then starts a fresh window from the committed count. The commit is held within the current max, so lowering max mid-window cannot commit above it.
- **Pauses clear the window.** `desiredReplicas` clears the stamp and its record (`dropScaleDownWindow`) on any pass where autoscaling does not run: suspended, disabled, unset, or no metrics reader. A dip after the pause waits a full window again. The commit and the drop clear both annotations through one helper, `clearScaleDownWindow`.
- **Accepted:**
  - a failed write of the record loses only that reading's rise, as a failed stamp loses only one pass's hold;
  - a metrics outage keeps the window, so the first reading after it may commit at once, as HPA would.
- **Tests.**
  - an unreadable stamp restarts the window and records its first reading;
  - the window commits the highest count, and a shallower reading raises the record;
  - a lowered max binds the commit;
  - suspend, disable, unset and unwired metrics each clear the window.
  - Six mutants fail them.
  - `make test` (operator) and `make lint` pass.
- **Docs:** ADR018's autoscaling row describes the window.
- **Follow-up:** w5/130. Re-enabling autoscaling resumes from the count it last chose rather than the service's own.
