# A text search over many hours of a busy service still spends its whole 18 s scan budget

Why: after w5/m503 a `text` search reads every raw line of its window into bex-api to match it there, about 1 s per hour of the busiest service, so a search over a day or a week of it still answers at the 18 s budget with a partial page; w5/m503's definition of done names this the shape left above 5 s.

- **Measured (w5/m503 Findings, production Loki, 2026-11-19):** on the busiest service (about 20,000 request lines an hour) one hour of raw lines is about 0.4 to 0.5 s of Loki time and 12 to 14 MB of answers to decode. A one-hour search finishes in about 1 s in the cluster; a day's search covers about four hours before the budget, and a week's the same four, each a partial page with `hasMore` and the cursor at the scan's edge.
- **Why it reads everything:** `NewLokiSource` matches `text` in Go (`lokiTextScanPage`, `textScanPage` in `lego/backend/internal/logs/loki.go`) because Loki's case-insensitive regexp simplifier is not a safe Unicode superset of the API's literal match, and a request line's message is rendered from its stored JSON (`requestLine`), so a term can match the message and not the stored bytes (`responseTimeMS=12`).
- **Directions to weigh:** a LogQL prefilter that is a superset of the Go match for the lines whose message is a prefix of the stored line (app, build, Postgres and Key Value lines, raw `textMode`, literal terms: ASCII-only terms can use `|= ` per case variant, or `|~ "(?i)…"` where it is proven a superset), keeping the Go match as the decision; request lines rendered in LogQL (`| json | line_format`) only if it can be shown to be a superset of `requestLine`'s output; reading a wave of whole buckets in parallel once a scan is busy, which cuts the latency but not the bytes.
- **Done when:** a no-match `text` search over a day of the busiest service answers under 5 s in production (`bex_api_logs_page_duration_seconds{filter="text"}` p95 on the bex-api-gateways dashboard), returns exactly the matches the Go matcher finds today (a test with Unicode case folding, escapes and a rendered request line), and `BexApiLogsReadSlow` stays quiet over a day of production traffic.
- **Promoted 2026-11-19** to [w5/m520](../m520/README.md) by `/loopx w5`: a superset prefilter for app, build, Postgres and Key Value lines, a separate rule for rendered request lines, timing against production Loki, Render parity, tests and a 24 h production reading are more than one sitting. Triage on `e0dc599d3` confirmed the premise: `localTextSearch()` (`lego/backend/internal/logs/service.go:850`) is true for any `text` term and `lokiPipelineFor` (`loki.go:582`) adds no line filter for it, so Loki returns raw 1,000-line pages that `textScanPage` (`loki.go:257`) matches in Go; w5/197 changed only the no-`startTime` default.
