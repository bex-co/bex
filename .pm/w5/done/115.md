# Blueprint claim kinds are bare strings at about twenty call sites

Why: the claim kinds `service`, `database` and `key_value` are typed out at each call site, and only migration 0112's `CHECK` guards them. A typo passed to `GetBlueprintResourceOwner` reads as "unclaimed" rather than failing.

- **Where:** `lego/backend/internal/apps/blueprint_ownership.go`, `apps/blueprint.go` (`resourceOwnedByBlueprint`'s callers) and `apps/deploy.go`. `store.BlueprintResourceClaim.Kind` is a plain `string`.
- **Fix:** declare the claim kinds as constants beside `store.BlueprintResourceClaim`, use them at every site and in `blueprintClaimResourceKind`, and add a test that keeps the constants equal to the migration's `CHECK` set.
- **Also:** the detach path drops a resource's kind into `BlueprintResource.Type`, and `blueprint_state_plan.go` rebuilds it with an if-chain. Return the kind with each detached resource instead.
- Found by w5/098's reuse and quality reviews (2026-10-07).

**Result (2026-10-07):**

- **Typed kinds.** `store.BlueprintClaimKind` names a claim's kind, with the constants `BlueprintClaimService`, `BlueprintClaimDatabase` and `BlueprintClaimKeyValue` and the list `BlueprintClaimKinds()`. The claim, its key (`BlueprintResourceKey`, with `BlueprintResourceClaim.Key()`), the store methods, the apps `BlueprintStore` interface and every apps call site use them.
  - A `string` or manifest-kind variable can no longer reach a claim API unconverted. That would have been "postgres", which a claim calls "database".
  - The `"kind/name"` map keys for declared, released and detached claims became typed keys.
  - `blueprintClaimResourceKind` is an explicit switch. An unknown kind passes through verbatim, so no resolver finds it.
- **The detach path returns each resource's kind.** `blueprintDetachments` returns `blueprintDetachment{BlueprintResource, kind}`, so the plan no longer rebuilds the kind from the wire `Type` with an if-chain. The sync's public `DetachedResources` is unchanged.
- **Tests.**
  - `TestBlueprintClaimKindsMatchTheMigrationsCheck` (store, no database) compares `BlueprintClaimKinds()` with the latest migration's `blueprint_resource_claims_kind_chk`, through the existing `latestMatchingSQL`/`quotedList` helpers.
  - `TestEveryClaimKindHasItsOwnManifestKind` (apps) requires every claim kind to map to a distinct manifest kind. A new kind therefore fails one or the other until it has both its migration and its mapping.
  - The detach tests now pin each detachment's kind, including a detached static site, which is a `service` in the plan on every surface.
  - The claim tests use the constants. The apps fake keys claims by struct, which also ends its string splitting.
  - Mutants fail the tests: a constant drifting from the `CHECK`, a kind without a migration, a new kind without a mapping, a database mapped as a service, and a wrong detach kind.
  - The apps, store and api suites pass, and `make lint` is clean.
