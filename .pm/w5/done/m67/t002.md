## Objective

Confirm the routes that reuse their `component` as `pendingComponent` still resolve to one shared code-split chunk after the export removal, so none throws a `ReferenceError` at import.

## Context

- `dashboard/CLAUDE.md` § Navigation pending states warns: the component-as-pending pattern requires `component` + `pendingComponent` to share a chunk, grouped by `codeSplittingOptions.defaultBehavior` in **both** `vite.config.ts` and `vitest.config.ts`. If the shared identifier is stripped, the route module throws `ReferenceError` at import.
- Two route modules use `pendingComponent: RouteComponent` (`grep "pendingComponent: RouteComponent" dashboard/src/routes/*.tsx`); ~9 detail routes set `pendingMs: 0`.
- Dropping the `export` (t001) should not change chunk grouping, but this must be proven, not assumed.

## Steps

1. Identify the `pendingComponent: RouteComponent` routes and the detail routes with `pendingMs: 0`.
2. `yarn build` then load each such route in the app (or run its route test) and confirm no `ReferenceError`/blank import.
3. Spot-check the built output that `component` and `pendingComponent` for those routes resolve to the same chunk.

## Files

- `dashboard/src/routes/services.$serviceId.tsx`, `static.$serviceId.tsx`, and the other detail routes using `pendingComponent`/`pendingMs: 0`
- `dashboard/vite.config.ts`, `dashboard/vitest.config.ts` (read-only reference for `codeSplittingOptions`)

## Acceptance criteria

- [ ] Every component-as-pending route imports and renders without `ReferenceError`.
- [ ] `component` + `pendingComponent` share one chunk for those routes.

## Out of scope

- Rationalizing whether those pending configs are still needed post-persistent-shell — that's w5/m69.
