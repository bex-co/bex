# A Blueprint dockerCommand on a buildpack build becomes the start command, while the API ignores it

Why: `runtime: docker` with `x-bex.builder: buildpack` and `dockerCommand: x` passes the Blueprint compiler and parse, and `x` becomes the start command. A create through REST, GraphQL or MCP ignores dockerCommand on a buildpack build (`dockerDetails.commandApplies`, `create_transport_guard_test.go:197`), so the same declaration means two things.

- **Where:** `lego/backend/internal/apps/blueprint_compiler.go` `blueprintServiceRuntimeProblems` and `deploy.go` `manifestStartAndAutoDeploy` judge dockerCommand by the declared runtime only. The build-strategy-adjusted runtime is at `deploy.go` ~`:2224-2227`.
- **Fix:** judge the field by the build strategy (`readsDockerCommand(buildStrategy(...))`, `build_strategy.go`), and refuse it as `BLUEPRINT_CAPABILITY_INCOMPATIBLE` like the compiler's other inert-field rules (a Dockerfile build's `buildCommand`). Test that the buildpack declaration is refused and that docker and image builds still accept it.
- **Size:** about 30 minutes. Found by w5/080's reuse review.

**Result (2026-10-07):**

- **The rule.** A Blueprint `dockerCommand` is judged by the build: runtime image, or runtime docker that is not the schema's spelling of a buildpack build (`blueprintReadsDockerCommand`, `build_strategy.go`).
- **Both gates.** The compiler and the parse share that one predicate. The compiler refuses with `BLUEPRINT_CAPABILITY_INCOMPATIBLE` at the field, and the parse refuses with a bad request; both point a native or buildpack build to `startCommand`.
- **Before.** A buildpack build's `dockerCommand` silently became its start command, while a create ignored it.
- **Not taken.** Judging by `buildStrategy` itself, the note's suggestion, was tried and reverted after review. It widened what was accepted: `runtime: static` beside a dockerfile builder or a worker type, and a native runtime beside an image block. The declared-runtime predicate keeps every other verdict unchanged.
- **Tests.** `TestBlueprintDockerCommandCompilerAndParseAgree` runs the compiler and the parse on the same eight services and requires them to agree: Dockerfile, the auto builder, image, image cron, buildpack, buildpack cron, native, and a static site (which Render's schema refuses). Three mutants each fail it, including treating any builder as a buildpack.
- **Docs.** ADR006 records the rule.
