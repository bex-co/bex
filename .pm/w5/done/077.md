# Native build failure text: drop the legacy loader branch and unescape the step-header path

Why: w8/052's error rewrite carries three problems: a branch for builds generated before w8/052, a `(:?)` that reads like a typo of `(?:`, and a step-header path that leaves JSON escapes in the user's command while the verdict path unescapes them.

Source: Last-24h code review, 2026-10-05 (user handed all fixes to w5). Follow-up to `8f58b933d` (w8/052). No secret risk found: env values arrive only through the secret mount, and `$VAR` stays unexpanded in the quoted command. The exit code is regex-parsed from BuildKit's text and fails safe (text left unchanged).

## Fix

1. `lego/operator/internal/build/build.go:711`: settle `(:?)` (decide whether an optional literal colon was intended) and cover it with a test either way.
2. Delete the pre-w8/052 inline-loader branch (`build.go:717-733`). It only matters for Jobs that failed during the rollout window, which have aged out.
3. Unescape JSON in the step-header path the same way the verdict path does.
4. Optional, decide here: `ARG BASH_ENV=/opt/bex/load-env`, with the loader ending in `unset BASH_ENV` (`build/native.go:224-250`). BuildKit's own message would then name only `/bin/bash -c <cmd>` and the exit code, and both regexes could go. Only do this if build semantics are unchanged.

Done: a failed native build names the user's unescaped command and its exit code on both paths; build tests green.

## Outcome (2026-10-06)

Done (`lego/operator/internal/build/build.go`), with step 3 resolved differently from how it was filed.

1. `(:?)` was intended: it keeps the colon BuildKit's error summary puts after the step header (` > [stage-0 5/5] RUN …:`), which the progress log omits. It is now written `(:)?`, with a comment.
2. The pre-w8/052 inline-loader branch is deleted, along with its test case.
3. **Premise false; the header is left as BuildKit prints it.** The step header is not JSON. The pinned `docker/dockerfile:1.7` frontend prints the exec form after its own unquoting: quotes and backslashes come out bare, and a newline stays a literal `\n`, exactly as a `\n` written inside the command does. A real run of the pinned BuildKit captured `["/bin/bash","-c",". /opt/bex/load-env\necho "done" && echo 'a\b' …\nexit 3"]`. JSON-decoding the header (tried first) left the loader and secret mount showing for any command containing a quote, and turned `\b` into a control character, so it was reverted. The verdict line quotes the process with Go `%q` and names the exact command; the header names it as printed. The comments now say so, and the test asserts the real captured header/verdict lines, both header forms, against those two renderings.
4. Declined `BASH_ENV`. It would let the regexes go, but it changes how the RUN gets its environment (an ARG recorded in image history, and bash sourcing it for the top-level shell), and proving that equivalent needs a BuildKit run of its own.

Mutants (colon form not matched, colon dropped, verdict keeping the loader) each fail the test. Operator `make test` and `make lint` green.
