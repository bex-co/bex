# A deleted service's write can commit over its namesake's store map once a purge restarts versions

Why: a service's purge deletes its store paths' metadata, so the next write there starts again at version 1. A write in flight for the deleted service can have read version 1 of its own map. A namesake's create that commits version 1 of its seeded map lets that stale compare-and-set succeed over it. The dead write's projection is refused since w5/147, but its compensation then restores the dead service's prior map there. The new service's Secret is right, while its store holds the dead service's values, and its next write deploys them.

- **Where:**
  - `lego/backend/internal/secrets/store.go` `openBaoStore.Delete` (:268), a KV v2 metadata DELETE that restarts versions.
  - The forward compare-and-set: `service.go` `updateMapCAS` (PutCAS around :919).
  - The compensations: `restoreMap` (:954, via `batch.go` `compensateEnvironment`) and `batch.go` `compensateCASEnvironment` (:567). Both PutCAS on the version alone.
  - `rollbackCASEnvProjection` (:592) also matches the Secret by version number alone. It can delete the new service's Secret (:599), or re-stamp it with the dead App as controller (:604), after which garbage collection deletes it.
- **Fix:** keep versions monotonic across a purge, so a namesake's first write lands past any version a dead write read: destroy versions and keep the metadata, then remove the metadata only once it is safe. Or tie each store write to the App's identity, e.g. its UID in the path's custom metadata, checked before every compare-and-set and restore. A liveness check before PutCAS only narrows the window.
- **CAS path:** `batch.go` `safeCASProjectionError` (:418) maps `core.ErrServiceReplaced` to the coded env revision conflict. So w5/157's skip, where `compensateEnvironment` restores nothing for a replaced service, never fires for a CAS write, and `compensateCASEnvironment` still restores. Route a replaced CAS write past that compensation while keeping the CAS surface's coded answer.
- **Test:** the dead write reads version 1, then the purge and the namesake create's `prepareProjection` commit version 1. The dead write refuses, and the namesake's store and Secret still hold the create's map. The reproduction is w5/147's review probe `TestProbeDeadWriteStoreABA`, kept at `/tmp/w5-156/probe_test.go` for this session.
- Found by w5/147's quality review (2026-10-07). Likely more than an hour, since purge and existing paths change. Promote it if so.

**Done 2026-10-08.** A deleted service's purge, and a failed create's release, now retire the store paths instead of deleting their metadata. `openBaoStore.Retire` commits an empty map as a new version and destroys every older version, so versions keep counting. A write that read the dead service's map now conflicts instead of compare-and-setting over the namesake's, and no compensation or Secret rollback can match a namesake's revision. A workspace purge sweeps every `services/*` path the tenant's store lists, retired ones included, and still deletes them outright. A revision-checked save whose service was replaced takes back its source change while it is the latest, leaves the namesake's Secret alone, and answers `ENVIRONMENT_REVISION_CONFLICT` (previously `ENVIRONMENT_RESTORATION_FAILED`). `scripts/delete-audit.sh` now reads the tenant-prefixed `tenants/data/<ws>/…` path and counts an empty retired map as gone. Its old `secret/data/…` check could never find anything. Tests: `TestADeadWriteCannotCommitOverItsNamesakeAfterAPurge` (the review probe, now driving the real `PurgeApp`), `TestAReplacedCASWriteTakesBackItsChangeAndLeavesTheSecret`, plus real-OpenBao `TestRetireKeepsCountingAndDestroysTheOldValues` and `TestAWorkspacePurgeSweepsItsRetiredPaths`. Both fixes were mutation-checked. ADR013 updated.
