## Objective

Make the official Render CLI service verifier permanently exercise the two paths this production run exposed, then run a cleanup-safe acceptance pass against the deployed API.

## Context

- The existing verifier covers repo-backed service families but did not exercise the official CLI's nested image owner field.
- Its delete checks accept the immediate CLI acknowledgement; they do not require GET 404 plus list absence, allowing a stuck finalizer to pass.
- Service names must stay within the existing 30-character DNS-label contract; the first manual long-name probe correctly failed that independent validation.

## Steps

1. Add an image-backed create → read → image update → readback → delete leg driven only by unmodified CLI v2.21.0.
2. Add a repo-backed create followed promptly by delete while its first build is pending or active.
3. Poll both immutable-id GET and `render services` until 404/list absence, with an explicit five-minute deadline and a diagnostic failure naming the last phase.
4. Make traps clean every verifier-created service on success, failure, timeout, or interruption and reject production unless an explicit disposable-fixture gate is set.
5. After the normal ship/deploy path is authorized and complete, run the exact production acceptance and record sanitized results.

## Acceptance criteria

- [x] The verifier fails on the pre-fix nested-owner 400 and on a DELETE that stays visible through GET or list after the deadline.
- [x] Image create/update and delete-during-first-build both pass against the deployed production API with the unmodified pinned CLI.
- [x] Every verifier fixture is absent by id and list after the run; when cluster access is available, the delete audit also proves zero UID-scoped residue.
- [x] Output/evidence includes versions, redacted ids/names, phases, deadlines, and pass/fail only—never tokens, credentials, kubeconfigs, or raw authenticated bodies.

## Out of scope

- Running destructive probes without an explicit disposable-fixture gate, modifying the CLI, or treating DELETE acknowledgement alone as cleanup success.
