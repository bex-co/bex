# A finished build's artifact lives only in memory until the pass's first status write

Why: a pass that ends before its first App status write — now including a write conflict (w5/095) — loses the artifact a just-finished build resolved, so the next pass re-enters `buildFromSource` for a build that already succeeded.

- On the pass that first sees a build succeed, `ArtifactImage` / `ArtifactFingerprint` exist only in memory (`lego/operator/internal/controller/app_controller.go`, the build-success branch of `buildFromSource`). For a web service, private service or worker with no pre-deploy command, the first App status write is the config-snapshot record.
- Before w5/095, a conflict there went to `r.fail`. Its retried failure write persisted the artifact, but also closed the deploy as failed. Now nothing is written, and the next pass sees a finished build again:
  - the admission caps run again: a finished Job is not active, so a full workspace or cluster scope parks the already-built release as `BuildQueued`, with a 30 s requeue;
  - the build outcome, run-seconds and queue-wait metrics are counted a second time;
  - the registry digest lookup repeats, along with about 6–10 uncached API calls.
- Fix, from w5/095's efficiency review:
  - persist the artifact once, when `buildFromSource` first returns a fresh image and `ArtifactFingerprint` changed: one status write per build;
  - and/or skip the admission caps when this revision's Job already exists, which is observation rather than a new dispatch. That also covers the early returns that already end a pass before any status write.
- Test: a build-success pass whose snapshot write conflicts. The next pass deploys the built image without parking it as queued or metering the build twice.
- Found by w5/095's efficiency review (2026-10-06).

**Result (2026-10-07):**

- **The artifact is stored first.**
  - `buildFromSource` now takes the release's artifact fingerprint. On success, its new `storeBuiltArtifact` sets `ArtifactFingerprint`/`ArtifactImage` and writes status before anything else can end the pass, and meters the build only after that write. A later pass reuses the artifact through `reusableArtifactImage`: no re-admission, no repeated digest lookup, no second metering.
  - The write is an unconditional `Status().Update`, not `updateStatusIfChanged`. A requeued pass whose informer cache has not seen the artifact must conflict there; a skipped "unchanged" write would let it meter again.
- **The caps gate only a new dispatch.** `build.ActiveAppBuilds` became `build.ObservingAppBuild`. From the same single List, it reports an active build or the release's own Job once it finished, owned by this App lifetime.
  - Before, a finished Job was not active, so even the pass that first saw a build finish parked the release as `BuildQueued` whenever other builds held every slot: a succeeded build waited for a slot, and a failed one went unrecorded.
  - kpack builds count only while active (w5/119). Correction, w5/119: the kpack Image is per revision, not shared across releases, so the release's own finished Image now counts like its Job.
- **Tests.**
  - `TestAFinishedBuildIsSettledWhileOtherBuildsHoldEverySlot`, with every slot held: a succeeded build rolls out its own image, not release 1's, and a failed build records release 2's Build failure.
  - `TestABuildSuccessPassStoresItsArtifactFirst` makes the snapshot write conflict in one case and the artifact write in the other. Each meters once and deploys the built image.
  - `TestAPassBehindTheArtifactWriteMetersNothing`: a pass that reads a stale App conflicts instead of metering again.
  - `TestObservingAppBuild` in `internal/build` covers which builds count.
  - Five mutants each fail the suite: skipping the write as unchanged, no early write, metering before the write, ignoring the release's Job, and counting only succeeded Jobs.
  - `make test` and `make lint` pass. The e2e build-cache drill compiles against the new signature.
- **Doc.** ADR060 D6 records that admission gates only a new dispatch and that the success pass stores the artifact before metering.
- **Follow-up:** w5/119, a finished kpack build still waits for a slot.
