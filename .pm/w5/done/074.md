# A reconcile pass compares its final status against a cache that hasn't seen its own write

Why: `setPhase` writes immediately, but the pass's final `updateStatusIfChanged` compares against the informer cache. When the final status equals the cached pre-pass status it skips the write, leaving the intermediate phase stored. `c33c9e7d6` (w6/m147 t003) fixed one caller; the shape remains for others.

Source: Last-24h code review, 2026-10-05 (user handed all fixes to w5). Medium confidence: timing-dependent, and the fake client has no cache lag, so existing tests can't show it.

## Mechanism

- `lego/operator/internal/controller/status_update.go:30` `updateStatusIfChanged` compares the desired status with the cached object (`:61`, `bytes.Equal(want, have)`).
- Example: on a suspended cron job's one-minute poll, the pass writes Deploying through `setPhase`. Its final compare sees Hibernated == Hibernated in the stale cache and never restores it, so the phase flaps.

## Fix

1. First prove it: a test client whose cache returns the pre-pass object shows the skipped restore.
2. In `updateStatusIfChanged`, don't trust the cache once this pass has written. After an in-pass write `obj` holds the newer resourceVersion, so `if stored.GetResourceVersion() != obj.GetResourceVersion()` means write.
3. Keep the existing parked-pass guards in `app_controller.go` as belt-and-braces.

Done: with a lagging cache, a pass that writes an intermediate phase always ends with its final phase stored; suspended cron jobs don't flap; operator `make test` green.

Needed before [w5/m123](m123/README.md) (release planner).

## Closed 2026-10-06

- **Repro:** `status_update_test.go` `TestStatusRestoreLandsDespiteALaggingCache` serves a frozen pre-pass App from `Get`. The pass writes Deploying, then sets Hibernated and calls `updateStatusIfChanged`. Before the fix, Deploying stayed stored.
- **Fix:** `status_update.go:52` `statusUnchanged` writes whenever the cache's resourceVersion is older than `obj`'s (`resourceversion.CompareResourceVersion`), since such a cache has not seen the pass's own write. A cache at or ahead of `obj` is still trusted. The first draft used `!=`, which would have turned a cache-ahead pass into a 409 that three callers record as `DeployFailed` (filed as [w5/095](../095.md)).
- **Cron flap:** `app_controller.go:3942` stamps Deploying only when the cron has not settled. Settled means Running, or Hibernated when suspended, at the current generation and image. Previously the one-minute run-history poll of every settled cron wrote Deploying and then restored the final phase.
- **Tests:** `TestUnchangedStatusIsNotWritten` checks that a cache at the pass's version, or ahead of it, writes nothing. The envtest case `converge-cron-suspended` (`reconcile_convergence_envtest_test.go:301`) proves a suspended cron converges with no status writes on its settled pass. Three mutations each fail the suite as intended: dropping the version check, using `!=`, and dropping the cron gate.
