# Listing members looks up each member's identity in Kratos one request at a time

Why: since w5/104 a members list resolves its owner ids in one read. Its remaining per-member cost is one sequential Kratos admin request each, with a 5s timeout. The Team page polls the list every 30s, so a 20-member workspace makes 20 serial HTTP calls per poll.

- **Where:**
  - `internal/members/service.go` `List`, via `LookupIdentity`, which the Team page's GraphQL `workspaceMembers` reaches.
  - `internal/workspaces/service.go` `ListMembers`, via `Lookup`, which the REST `GET /v1/owners/{ownerId}/members` reaches.
  - Both resolve through `internal/workspaces/kratos.go` `KratosIdentities.Lookup`: `GET /admin/identities/{id}?include_credential=totp&include_credential=webauthn`.
- **Fix:** batch the lookups. Use Kratos's `GET /admin/identities?ids=…` if the deployed version supports it with the credential includes the MFA flag needs. Otherwise run them concurrently with a small cap. Keep the honest-omit contract: a failed lookup leaves that member's fields empty and doesn't fail the list.
- **Test:** a 20-member list makes one batched request, or at most N concurrent ones within the cap, and one failing identity leaves only its own fields empty.
- Found by w5/104's efficiency review (2026-10-07).

**Result (2026-10-07):**

- **One request per 100 members.** `KratosIdentities.LookupMany` sends `GET /admin/identities?ids=…&include_credential=totp&include_credential=webauthn&page_size=N` for each batch of 100 ids. It decodes each identity exactly as `Lookup` does, through the shared `kratosIdentity.attrs()`. The members list goes through `workspaces.IdentityReader.LookupMany` (REST `GET /v1/owners/{ownerId}/members`) and through `members.IdentityLookup.LookupIdentities`, which the api adapter bridges (the Team page's GraphQL `workspaceMembers` and the invite's already-a-member check). A 20-member workspace now makes one Kratos request per poll, where it made 20 in sequence.
- **Kratos v26.2.0, the deployed chart 0.62.1, probed live on dev-5:**
  - `ids` and `include_credential` work on the list endpoint, and an unknown id is simply absent.
  - One id that is not a UUID makes Kratos refuse the whole batch with 400. So only UUID subjects are sent, and a named platform client such as `bex-bootstrap` stays unresolved, as its single lookup already did.
  - Results are keyed by the subject as asked, through the canonical UUID, so only asked subjects come back.
  - A throwaway test against the live Kratos found the batch and the single lookups resolve the same identities with the same attributes.
- **Honest omit kept.** A failed batch leaves only its own subjects without identity fields, and the list still succeeds. The reader now goes through `core.DoJSON` on the shared `core.OryTransport` pool. That drains each response, so a non-200 answer no longer discards its connection.
- **Tests.**
  - `TestListMembersResolvesItsIdentitiesInOneRequest` uses 21 members, including `bex-bootstrap` and an unknown UUID. They take one Kratos request, and email and MFA are set per member.
  - `TestKratosIdentitiesLookupManyChunksAndFailsPerBatch`: 250 ids go out as batches of 100, 100 and 50, and a 500 leaves only that batch unresolved.
  - `TestKratosIdentitiesLookupManyAnswersTheSubjectsAsked`.
  - `TestListAndTheMemberCheckResolveMembersInOneRead`: one batch read per members verb and no single lookups.
  - Mutants fail the tests: a per-member lookup in each of the three callers, no UUID filter, no chunking, aborting after a failed batch, and keying by Kratos' id. The suites pass under `-race`, and `make lint` is clean.

  - w5/127: the lookups fetch each member's TOTP secret only to learn whether MFA is on.
