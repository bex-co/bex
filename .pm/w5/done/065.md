# 065 — `postgres update --high-availability` works, but always reports `diff: {}` and a stale value, so the user is told nothing changed

Why: the write lands, yet the command's own before/after diff — the feature that exists to tell you what it did — is empty for this field every time, so the only honest reading of the output is "that did nothing".

- **Severity:** minor (reporting only; the mutation itself is correct and converges).
- **Attribution:** server (the PATCH response echoes an observed field where every sibling field echoes desired state).
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-16 UTC, sweep 8. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, human device login, `bex v0.2.1` / upstream pin v2.27.0. Fixture `qa-20260915-391a64-pg` (`dpg-dakup23joeps73deje40`), free plan, created and deleted inside the run.

## Reproduction

```text
$ bex postgres update dpg-dakup23joeps73deje40 --high-availability --confirm -o json
  data.highAvailabilityEnabled = False
  diff = {}                                  # exit 0

# ~70 s later
$ bex postgres get dpg-dakup23joeps73deje40 -o json
  status = available   highAvailabilityEnabled = True      ←  it DID work
```

The reverse direction behaves identically:

```text
$ bex postgres update dpg-… --high-availability=false --confirm -o json
  data.highAvailabilityEnabled = True        # stale — still the pre-change value
  diff = {}                                  # exit 0

# 20 s later
$ bex postgres get dpg-… -o json
  highAvailabilityEnabled = False            ←  it DID work
```

Sibling fields in the **same** `postgres update` invocation do not behave this way — they echo the new value immediately and populate the diff:

```text
--disk-size-gb 5           -> data.diskSizeGB = 5,            applied
--connection-pool pgbouncer-> data.connectionPool = pgbouncer, applied
--disk-autoscaling         -> data.diskAutoscalingEnabled = true, applied
--disk-size-gb 3           -> refused client-side: "must be 1 or a multiple of 5"
```

So within one command, four flags report their change and one reports nothing.

## Root cause

- `highAvailabilityEnabled` is deliberately an **observed** field: `lego/backend/internal/postgres/service.go:103-105` — "HighAvailabilityEnabled reflects the operator's **observed state (≥2 ready instances)**. Render's highAvailabilityEnabled read field."
- The PATCH does write the intent: `service.go:998-999` — `if patch.EnableHighAvailability != nil { d.Spec.HighAvailability = *patch.EnableHighAvailability }`, and the operator honors it (`database_controller.go`: `if db.Spec.HighAvailability && desiredInstances < 2 { … }`, with `Status.HighAvailabilityEnabled` set only once ≥2 instances are ready).
- Upstream computes the diff by comparing a **read before** against a **read after** the PATCH (`pkg/postgres/output.go:158-159`). Since the after-read still reports the pre-convergence observed value, `HighAvailabilityEnabled` can never differ, so `diff` is `{}` by construction.
- Every other PATCH-able field is desired state and flips in the same transaction, which is why only this one is affected.

Not a plan-eligibility problem: HA converged to `true` on the **free** plan, so bex provisions the replicated cluster regardless of tier — the CLI's own flag help ("available for plans with at least 1 CPU") is a Render statement bex does not enforce, which is worth a deliberate decision but is a separate question from this note.

## Fix (~20m) — pick one

- **(a) Echo the requested value on the PATCH response** for `highAvailabilityEnabled`, consistent with `diskSizeGB` / `connectionPool` / `diskAutoscalingEnabled`, and let `GET` keep reporting observed state. Smallest change; makes the diff meaningful; slight cost is that the PATCH response briefly disagrees with a `GET` issued immediately after.
- **(b) Keep the response observed and add a distinct requested field** (e.g. `highAvailabilityRequested`) so both the intent and the reality are readable, and so the diff has something to compare. Truthful but adds a field Render does not have — check ADR018 before choosing.
- **(c) Accept and document.** Record in `docs/ADR018-render-parity.md`'s Postgres row and `docs/cli-compatibility-checklist.md` that `--high-availability` is eventually consistent and its diff is always empty, so nobody re-reports it.

Prefer (a) unless Render's own PATCH response is known to echo observed state, in which case (c).

## Blast radius

`internal/postgres/rest.go`'s `handleUpdatePostgres` response mapping and whatever GraphQL/MCP update paths share it — check that all three agree after the change, since `postgres` has a cross-surface parity test. The `GET` read shape must not change. Confirm no dashboard panel keys off the PATCH response's `highAvailabilityEnabled` as "current truth".

## Regression checks

- `postgres update --high-availability` on a fixture reports the requested value (option a) or a documented stale value (option c) — asserted against the wire, not the handler.
- A follow-up `GET` after convergence reports `true`; before convergence it reports `false`. Both are correct and the test should pin both.
- `--disk-size-gb` / `--connection-pool` / `--disk-autoscaling` keep echoing their new values and populating the diff.
- `--high-availability=false` turns HA off and reports symmetrically.

## Unverified

- Render's own PATCH response semantics for `highAvailabilityEnabled` were not captured live; the parity question in option (c) rests on that.
- Whether the dashboard's Postgres detail page reads the PATCH response or re-fetches was not checked.
- HA on free converged once, in ~70 s; no claim is made about whether free-tier HA is *intended*.
