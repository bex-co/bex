# A logs read with no `startTime` reads the last hour, as Render documents, not the last seven days

Why: Render's List logs defaults `startTime` to `now() - 1 hour`, and bex reads back seven days instead, a divergence ADR018 does not record; on a busy service that week is also the slowest default shape left after w5/m503 (a type the service logs little of walks a week of Loki splits: about 6 s of Loki time for the newest 101 app lines).

- **Render's contract:** the pinned client (`github.com/render-oss/cli` `pkg/client/types_gen.go`, `ListLogsParams.StartTime`, from `render-public-api-1.json`) documents "Epoch/Unix timestamp of start of time range to return. Defaults to `now() - 1 hour`", and `EndTime` "Defaults to `now()`".
- **bex today:** an absent start reads back `lokiLookback` (`core.ShortestLogRetention()`, seven days) in `lego/backend/internal/logs/loki.go` `lokiRange`, and the paging cursors name that window (`render.go` `resolveCursorWindow`, w8/125). `docs/ADR010-observability.md` (w9/m389) says "The default lookback with no `startTime` stays seven days"; ADR018 has no row for it, so under ADR008's parity rule the ADR is amended, not kept.
- **Measured (w5/m503 Findings, production Loki, 2026-11-19):** on the busiest service a default-window `type=app` read cost 5.9 s of Loki time, `type=build` 1.6 to 2.6 s and a no-match `level=error` read 1.5 to 1.7 s; the same shapes over one hour cost under 0.1 s.
- **Check before changing it:** the pinned Render MCP server's `list_logs` default (it should take the same hour), every bex surface that omits the start (REST `GET /v1/logs`, `GET /v1/logs/values`, GraphQL `logs` and `logLabelValues`, MCP `list_logs`, the CLI's `render logs` without `--start`), and whether the dashboard ever omits it (it sends a start today). `Service.Logs` (the unfiltered tail-N read) has no Render counterpart and can keep its own lookback.
- **Done when:** with no `startTime`, REST, GraphQL and MCP return only lines from the last hour, `nextStartTime`/`nextEndTime` name that hour, a backward page that reaches the hour's start ends `hasMore: false`, ADR010 is amended, and tests pin the default on each surface.

**Done (2026-11-19):** REST `/v1/logs` and `/v1/logs/values`, GraphQL `logs` (project views too) and `logLabelValues`, and MCP `list_logs` and `list_log_label_values` read the hour before the earlier of `endTime` and now when no `startTime` is given (`renderWindow`, `lego/backend/internal/logs/rest.go`), so the store, the pod-log fallback and the cursors name that hour; `render logs` without `--start` sends no start (pinned `render-oss/cli` `cmd/logs.go`) and gets it too. The pinned Render MCP server's `list_logs` and `list_log_label_values` document the same "Defaults to 1 hour ago". `TestEveryRenderSurfaceReadsTheLastHourWithoutAStart`, `TestThePodLogFallbackReadsTheLastHourWithoutAStart` and the rewritten `TestBackwardPagesWithoutAStartFollowTheirCursorsToTheEnd` (cursors name the hour, the last page ends `hasMore: false`) fail with the default removed. The dashboard's `logs` reads always send a start; its filter-value discovery sent none, so it now asks for seven days rounded up to the hour (`discoveryStartTime`) and its dropdowns are unchanged. `Service.Logs` and the per-datastore log endpoints keep the seven-day store default. ADR010 (and ADR006's logs parameters) amended.
