# A refused service create overwrites, then deletes, its namesake's secrets store map

Why: create-time preparation writes the new service's env and files maps into the store at the service's path before it creates the projection Secret, and deletes the path when that Secret is refused. The path is keyed by workspace and service name, so in a concurrent create of the same name, the refused request first overwrites the other's store map and then deletes it, leaving the surviving service's Secret without its source of truth.

- **Where:** `lego/backend/internal/secrets/files.go` `prepareProjection`: `updateMapCAS` (clear + copy) runs before `createPreparedSecret`; on `errSecretNameHeld` the store path is deleted. `storeServiceName` keys the path by the service name label, so namesakes share it.
- **Reach:** two creates of the same service name in one workspace within the prepare window; the store's name check normally refuses the second create earlier (w5/128 found this while scoping the abort).
- **Fix:** check the Secret's holder before the store write (refuse a held name without touching the store), or make the store write conditional on the path being absent or a purge's leftover.
- **Test:** a create refused because another create holds the Secret leaves the other's store map exactly as it was.
- Found while closing w5/128 (2026-10-07).

**Result (2026-10-07):**

- **The Secret is the claim.**
  - `prepareProjection` now creates the ownerless projection Secret first, or takes over a deleted namesake's, before writing the store map, then stamps the committed store revision onto it.
  - A create refused because another holds the name (a live App, another create, a namesake still deleting) never touches the store map at that path, which is the holder's. It used to overwrite it and then delete it.
  - Refused creates make no OpenBao calls, down from three.
- **The stamp.** It is a metadata-only merge patch under the claim's resourceVersion, so a Secret changed since the claim fails the create instead of adopting a changed Secret. A takeover keeps the server's view of the Secret it claimed. The version cannot be predicted before the write: a CAS retry moves it, and stamping "committed" before commit would break `committedAt`.
- **Aborts.** A failure after the claim removes both halves. Simplify's quality review found that `abortProjection` released the name before deleting the store map, so a create claiming the name in between could lose its fresh map (reproduced). The map now goes first, while the Secret still holds the name.
- **Tests.**
  - The w5/128 refusal test seeds each holder's store map and asserts it is unchanged. HEAD fails it for every holder.
  - `TestAFailedPrepareReleasesTheName` covers a failed store write (plain and versioned) and a failed stamp; each leaves neither Secret nor map.
  - `TestAnAbortDeletesTheMapWhileStillHoldingTheName` pins the abort order.
  - The rollback-hiding test now triggers a real rollback (files leg, then a refused env leg).
  - Six mutants, including HEAD's own file, each fail a test. The secrets, api and apps suites and `make lint` pass.
- **Follow-up.** w5/147: a deleted namesake's in-flight write can take over a prepared Secret. It predates this change.
