# A status-write conflict is recorded as a deploy failure at three operator call sites

Why: a 409 from a status write means "reconcile again from current state", but three call sites hand it to `r.fail(ctx, app, "DeployFailed", err)`, which stores phase Failed and lets bex-api close the open deploy row as `DeployUpdateFailed`, a terminal state.

- **Where:** `lego/operator/internal/controller/app_controller.go`, the `ensureSelectedConfigBeforePlanning` failure (~`:2315`, every pass of an App on a selected release config), a second at ~`:2347`, and the cron path's `ensureReleaseConfigSnapshot` at ~`:3954`. Each error can be a status-write conflict from `updateStatusIfChanged` (`release_config_selection.go:154`).
- **The rule already exists:** `failStep` (~`:5270`) returns a conflict instead of recording it ("Recording a failure with a stale status retry could overwrite another pass's durable acknowledgement").
- **Fix:** route the three sites through the same rule (return `apierrors.IsConflict(err)` errors as they are), or have them return a `stepFailure` and call `failStep`.
- **Test:** a conflicting status write during config selection requeues without storing Failed or a `DeployFailed` condition.
- **Size:** about 30 minutes. Found by w5/074's quality review; w5/074 keeps such conflicts rare (it writes against a cache that is ahead only when obj's status changed).

## Done (2026-10-06)

- `r.fail` now returns a write conflict without recording it, so the next pass retries from current state. `failStep` loses its own copy of that check.
- The three named sites, all writing App status, are covered, and so is every other `r.fail` whose error can be a lost race:
  - the Deployment, Service and Ingress `CreateOrUpdate` writes, which the reuse review reproduced storing `ServiceFailed` and `IngressFailed`;
  - the build sites, where a recorded conflict stood as a terminal build failure that no pass retries.
- A failed config-snapshot record now rolls back to the generation the stored status still records, not 0. A failure written after it used to drop the served release's snapshot.
- Tests through `Reconcile`, each failing when its rule is reverted:
  - a snapshot-record conflict, on the cron and the web path;
  - a Deployment update conflict during release 2's rollout;
  - a conflict on the selected-config record;
  - `r.fail` with a conflict for deploy, service and build reasons, and a real failure still stored;
  - a failed snapshot record keeping the served snapshot.
- Operator `make test` and `make lint` are green.
- Known gaps:
  - A stale-cache `CreateOrUpdate` can return AlreadyExists, a different 409 that `IsConflict` does not match. Low likelihood.
  - A build-success pass that ends on a conflict loses its in-memory artifact (w5/108).
