## Objective

Prove, in an isolated driver branch, that Vercel's AI SDK harness layer (`HarnessAgent` + `@ai-sdk/harness-acp`) can drive the existing `claude-code-acp` ACP agent and project its built-ins (plans, file diffs/edits, terminal output, tool calls) as **typed** UI-message parts — the thing `@mcpc-tech/acp-ai-provider` + `toUIMessageStream()` cannot do today without the lossy `data-acp` re-wrap. This is a **hard gate**: if typed parts do not arrive cleanly (Vercel's own caveat is that ACP can under-expose some harness internals), stop here and record findings rather than proceeding to t002.

## Context

- Driver today: `lego/agent-image/driver/src/acp.ts` — `createACPProvider(@mcpc-tech/acp-ai-provider)` → `LanguageModelV3`; `session.ts:182` `streamText(model).toUIMessageStream()`; `session.ts:195` `.fullStream` raw-drain re-wrapped as `data-acp` (`rawUIMessagePart`).
- New packages: `@ai-sdk/harness-acp` (meta-adapter, `createACP({harnessId, source, executable, forwardEnv, permissionModeMapping, authentication})`) + `HarnessAgent` (`generate()`/`stream()`), on the same `ai` SDK (`6.0.237`) already in `package.json`.
- ACP agent binary installed in the image: `@zed-industries/claude-code-acp@0.16.2` (`lego/agent-image/Dockerfile`), invoked as `claude-code-acp`.
- Vercel guidance: prefer direct `@ai-sdk/harness-claude-code`/`-codex` where available; use `@ai-sdk/harness-acp` for the uniform path first (that is this milestone's scope; direct adapters are an out-of-scope follow-up).
- Do NOT adopt the harness layer's session/resume or `createVercelSandbox` lifecycle — we run OpenSandbox on our own k8s with the ADR051 Completer + Postgres transcript. Take only the adapter + `HarnessAgent` stream.

## Steps

1. In a driver branch, add `@ai-sdk/harness-acp` + the `HarnessAgent` entrypoint, wiring `createACP` to spawn `claude-code-acp` with the same env/forwarding the current provider uses.
2. Run one headless turn against a real (or locally spawned) `claude-code-acp` and capture the emitted UI-message parts (log part `type`s + `state`s).
3. Confirm plans, file diffs/edits, terminal output, and tool calls surface as typed parts (`tool-*` / `dynamic-tool` like `fileChange`, with `part.state` transitions) — NOT dropped raw chunks.
4. Verify the stream still carries the `x-vercel-ai-ui-message-stream: v1` shape (byte-transparency upstream is unaffected).
5. Record the exact part-type inventory + any gaps (anything ACP under-exposes) in the milestone README / this task's notes. Decide gate: proceed to t002, or stop with findings.

## Gate findings (2026-08-14, desk half)

- **Packages exist and install.** `@ai-sdk/harness-acp@1.0.9` (published 2026-08-14), on `@ai-sdk/harness@1.0.72` + `@ai-sdk/provider-utils@5.0.27`; siblings `@ai-sdk/harness-claude-code@1.0.75` / `-codex` present.
- **BLOCKER — forces an AI SDK v6→v7 major upgrade, not a driver-local swap.** `@ai-sdk/harness@1.0.72` depends on **`ai@7.0.66`** / `@ai-sdk/provider@4.0.7` / `provider-utils@5.0.27`. Current stack is on **v6**: driver `ai@6.0.237`; dashboard `ai@6.0.241` + `@ai-sdk/react@3.0.243`. The driver's UI-message stream must stay wire-compatible with the dashboard's `useChat`, so the version bump cascades to the client (and mobile) — contradicting this milestone's "driver-only, byte-transparency trivially preserved" premise.
- **Maturity risk.** `harness-acp` is 1.0.9, published the same day this was scoped (~hours old).
- **BLOCKER 2 (decisive) — the harness layer is a sandbox-ORCHESTRATION framework, architecturally opposite to bex's in-sandbox driver.** `HarnessAgent` runs on a *host* and per session calls `HarnessV1SandboxProvider.createSession()` → a `HarnessV1NetworkSandboxSession` (`getPortEndpoint`/`getPublicUrl`/`stop`/`destroy`/`setNetworkPolicy`/snapshot `onFirstCreate`/`resumeSession`); the bridge-backed ACP adapter installs a **bridge process inside the sandbox** and opens a **WebSocket to it** via `getPortEndpoint`. Only `@ai-sdk/sandbox-vercel` is published (no `@ai-sdk/sandbox-local|node|process|docker|e2b`). bex already owns this layer (OpenSandbox + gateway single-hop + ADR042/047), where the **driver runs _inside_ the pod** and just spawns `claude-code-acp` as a local child (today's `@mcpc-tech/acp-ai-provider` fits that exactly). Adopting the harness layer requires either (a) making bex-api/gateway a HarnessAgent host that provisions sandboxes — **violates ADR047** (bex-api never connects to the driver's network path) and duplicates OpenSandbox — or (b) running `HarnessAgent` inside the driver pod behind a **bespoke `HarnessV1SandboxProvider` ("this-pod")** + a bridge child + a loopback WebSocket. Both **add** architecture (+ the v7 cascade), the opposite of the simplification goal.
- **Gate decision: HALT — recommend pivot away from the harness layer.** The valuable outcome the user wants (typed plan/diff/terminal parts instead of the lossy `data-acp` round-trip) is achievable **without** the harness layer: in the driver, replace the `.fullStream` raw-drain + generic `data-acp` re-wrap (`session.ts:84`/`:195`) with a small deterministic map from ACP `session/update` → typed data parts (`data-acp-plan`/`-diff`/`-terminal`/`-tool`), and simplify the client `acp-parts.ts` classifier to switch on those explicit types. That deletes the round-trip's ambiguity with **no framework import, no v7 upgrade, no bespoke sandbox provider** — a genuine simplification that keeps byte-transparency and the whole gateway/bex-api/transcript path unchanged. Live verification (a real `claude-code-acp` turn) still needs a cluster + model key regardless of path.
