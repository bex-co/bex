## Objective

Guarantee that every terminal-failure class carries a non-empty, actionable `failureReason` at the API source and that the dashboard renders it — so no failed session shows a blank card. Closes inbox note `w5/048` (sandbox-create capacity/timeout failures showed an empty `failureReason` while bex-api logged the real cause), and extends the guarantee to the model-auth and turn-timeout classes this milestone touches.

## Context

- `w5/048`: session `ags-da51u99jg4reds94nrv0` showed **Failed / sandbox create failed** with an **empty** `failureReason` in the dashboard while bex-api logged `sandbox did not become ready … plan limit`.
- Failure classes to cover: sandbox-create capacity/timeout (048), model-auth 401/403 (t003), turn-timeout (t002), lost-sandbox. Model-auth already populates a reason today (observed on `dev-5`); sandbox-create does not.

- The `failureReason` field is exposed on REST/GraphQL/MCP (`AgentSessionView`) and rendered in the dashboard header/detail (`deploy-header`-style callout).

## Steps

1. Audit each terminal-failure class for whether `failureReason` is populated at source; map OpenSandbox capacity/timeout errors into a `failureReason` at fail time where empty (048's root cause if it is empty at source).

3. Ensure the message is actionable (capacity/plan-limit → what to do; auth → bad/expired key; timeout → turn exceeded the bound) with a generic fallback when the class is unknown.
4. Verify on `dev-5` across the classes: a capacity-blocked create, an invalid-key session (t003), and a timed-out turn (t002) each show a non-empty reason on a fresh API read and in the dashboard.
