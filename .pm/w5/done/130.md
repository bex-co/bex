# Re-enabling autoscaling resumes from the count it last chose, not the service's own

Why: the autoscaler keeps its last decided count in `app.bex.co/autoscale-replicas` and seeds every autoscaled pass from it, but nothing clears it when autoscaling is turned off. Turning autoscaling back on later starts from that stale count. A service set to 1 replica whose autoscaler last chose 4 jumps to 4, and the scale-down window then holds it there for about five minutes.

- **Where:**
  - written by `applyAutoscaling` (`lego/operator/internal/controller/autoscale.go`);
  - read by `desiredReplicas` (`app_controller.go`) to seed `current`;
  - nothing else reads it, in the operator, bex-api or the dashboard.
- **Decide first:** suspend takes the same non-autoscaling path in `desiredReplicas`. Today a resumed service restarts at its last autoscaled count, which is probably right for resume. Clear the annotation only when autoscaling itself is turned off, not on suspend.
- **Fix:** when `desiredReplicas` runs for an App whose autoscaling is disabled or unset, clear `app.bex.co/autoscale-replicas` along with the scale-down window (w5/120's `dropScaleDownWindow` path), through `patchAppMeta`.
- **Test:**
  - an App whose autoscaler chose 4, with autoscaling turned off and then back on, resumes from its configured count;
  - a suspended and resumed App keeps 4.
- Found by w5/120's reuse review (2026-10-07).

**Result (2026-10-07):**

- **Forget on turn-off.** `skipAutoscaling` (formerly `dropScaleDownWindow`) settles the autoscaler's state on a pass it does not run. When autoscaling is turned off or unset, it now also deletes `app.bex.co/autoscale-replicas`, in the same write that clears the window, so turning autoscaling back on seeds from the service's own count. As the note decided, a suspended service keeps the count and resumes where it was. So does one whose operator has no metrics reader.
- **A transition still under way was a second copy of the count.** The quality review found that a scale-up still under way (`Status.Autoscaling` Started) also held at its target after autoscaling came back on. With the count forgotten, the pass after it would then drop at once, with no window and no record.
  - Turning autoscaling off now also ends that transition. The activity feed pairs its "Autoscaling started" with an "Autoscaling ended" at turn-off, and re-enabling starts clean.
  - An "abandoned" state would need a CRD and backend change, so I didn't add one.
- **One write path.**
  - `settleAutoscaler` records a count ("" for none) and clears the window in one patch. Both the autoscaler's commit and the skip path use it, and a pass with nothing to change writes nothing.
  - `autoscalingEnabled` replaces the inline checks.
  - `endAutoscalingTransition` is shared with `completeAutoscalingTransition`.
- **Efficiency.** The review counted patches:
  - Apps without autoscaling write nothing.
  - Forgetting the count is one write, then none.
  - A conflict is ignored and retried on the next pass.
  - The annotation write neither bumps generation nor queues a pass.
- **Tests.** `TestTurningAutoscalingBackOnStartsFromTheServicesOwnCount`:
  - off, off mid-scale and unset resume at the spec's 1, and the mid-scale case ends its transition;
  - suspended and metrics-unwired resume at 4.

  Seven mutants each fail a test, and the suspend and unwired rows kill theirs on their own. `make test` and `make lint` pass. ADR018's autoscaling row documents the rule.
- **Left alone.** The backend repeats `Autoscaling != nil && Enabled` about seven times. A shared `AppSpec` method in `lego/types` belongs with the duplicate-unification routine, because a types change runs the whole backend suite.
