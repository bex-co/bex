# Two cron status patches replace a pass's unsaved release decision

Why: w5/096 and w5/110 stopped writes from replacing status a pass had set but not yet written. Two cron paths still `Status().Patch` the pass's own App, and the server's stored status replaces the release decision the pass holds in memory.

- `acknowledgeManualRun` (`lego/operator/internal/controller/cron_manual_intent.go`) and `preemptOtherCronRuns` (`app_controller.go`) call `r.Status().Patch(ctx, app, client.MergeFromWithOptions(before, client.MergeFromWithOptimisticLock{}))` inside `reconcileCronJob`.
- By then the pass holds unsaved status:
  - the release decision from `prepareAppReleaseDecision`: `ReleaseFingerprint`, `ReleaseArtifactFingerprint`, `ReleaseGeneration` and `PendingReleaseGeneration`;
  - the artifact identity `resolveDeployImage` set.
- Each `before` snapshot is taken just before its patch, so those fields are not in the patch, and decoding the response puts the stored values back into `app`.
- Fix: patch a copy, as `patchAppMeta` does for metadata, and carry back only the fields the patch changed plus the resourceVersion.
- Guard: `TestPassesPatchTheirAppOnlyThroughPatchAppMeta` (`metadata_patch_test.go`) skips `Status().Patch` and matches only the identifier `app`. Extend it to status patches, and to `db` and `kv`, so the next one fails the build.
- Test: a cron pass with a new release decision acknowledges a manual run, and the release decision is stored at the end of the pass.
- Found by w5/110's reuse review (2026-10-07).

**Result (2026-10-07):**

- **Status patches go through a copy.** `patchAppStatus` (`metadata_patch.go`) sits beside `patchAppMeta`. It patches the change `mutate` makes to a copy of the App, under the App's resourceVersion, then gives the App the status it sent and the new resourceVersion. The server's status is never decoded into the pass's App.
  - `acknowledgeManualRun` and `preemptOtherCronRuns` use it, so the release decision and artifact the pass has not written yet survive both patches.
  - `reconcileSavedConfigurationStatus` hand-rolled the same locked patch and now uses it too.
  - `preemptOtherCronRuns` records the cancellation with one scan of the run history, and still sends nothing for a run already recorded canceled.
- **The guard covers every write that decodes the server's object.** `TestPassesPatchTheirAppOnlyThroughPatchAppMeta` is now `TestPassesWriteTheObjectTheyHoldThroughACopy`.
  - It flags a `Patch` through any client, status included, and a main-resource `Update`, of `app`, `db`, `kv` or a cleanup Job's `parent`, with or without `&`. A status `Update` writes the pass's status instead of losing it, so it is not flagged.
  - Every allowlisted function sits under a comment giving its reason. They are the deletion passes, the Database disk autoscaler and the KeyValue TLS finalizer and certificate writes. The last two run before their pass sets any status.
  - A probe file with `&app`, `r.Client.Patch`, `r.Update(ctx, kv)` and `cl.Patch(ctx, parent, …)` fails it; a status `Update` in the same file does not.
- **Tests.**
  - `TestAStatusPatchKeepsThePassUnsavedStatus`: a cron pass holding an unsaved release generation acknowledges a manual run, and the generation reaches the stored status at the pass's end.
  - `TestCronPreemptionWaitsForEveryActiveRun` holds an unsaved release generation through the preemption.
  - `TestARecordedCancellationKeepsItsFinishTime`: a run already recorded canceled keeps its finish time while its Pods go.
  - Five mutants each fail a test: decoding the server's status, dropping the resourceVersion carry-back, a direct status patch on either path, and re-recording a canceled run.
  - `make test` and `make lint` pass.
