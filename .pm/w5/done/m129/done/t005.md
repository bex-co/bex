## Objective

## Acceptance criteria

- [x] Findings fixed or recorded.

## Result (2026-10-07)

Three review agents (reuse, quality, efficiency) read the whole diff. Fixed:

- **The inventory is guarded.**
  - `appv1alpha1.KeyValueFailedReasons` lists every reason the operator fails a store with.
  - The operator's `TestKeyValueReasonsAreClassified` requires every reason the Key Value controller writes to be a constant, classified as failed or as a non-failure. A literal reason, or one in neither list, fails it.
  - bex-api's `TestEveryFailedReasonHasASentence` walks the list.
- **Missed reasons.** `PVCResizePending` and `FileSystemResizePending` (converging) are now constants. So is `StorageProvisioned`, the storage condition's ready reason.
- **Sentences now say what the operator does:**
  - `PersistenceTransitionFailed` fires on any start, not only a mode change.
  - `BackupCronJobFailed` covers removing a leftover schedule too.
  - The workload and volume "read" failures are status checks, not data reads.
  - The quota sentence is reworded.
  - The certificate and issuer sentences say "public access", as the UI does.
- **Scope.** The App controller's literal swaps are reverted, and the Key Value reason block no longer claims App meanings.
- **A stale reason.** Both cards show a reason only beside Unavailable. The list query refreshes a cached status without the reason, so a recovered store could still hold an old one. Postgres had the same gap.
- **Duplication:**
  - `core.DatastoreStatusReason` serves Postgres and Key Value.
  - A shared `StatusWithReason` cell serves both cards.
  - `ownValue` (`common/lib/own-value.ts`) serves both `statusReasonLabel`s.
  - `src/test/go-source.ts` serves both vocabulary tests, reading reasons from every types file.
- **Comments.** Stale comments in `keyvalue.graphql` and `status.ts` are fixed.

Recorded, not fixed:

- The cross-surface test mirrors Postgres's, but its setup uses each package's private helpers; revisit if a third datastore arrives.
- The operator's storage-outcome mapping is shared in shape with the App's disk, but their messages, failure flags and requeues differ.
- Efficiency was clean: a reason is computed only for an unavailable store, and only the detail query fetches it.
