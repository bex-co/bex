## Objective

An unavailable Key Value's view carries `statusReasonCode` (its Ready reason) and `statusReason` (a fixed sentence for that reason, never the raw condition message) on REST, GraphQL and MCP. A healthy one omits both.

## Context

- `lego/backend/internal/keyvalue/service.go`: `KeyValueView` (~`:78`) and `kvStatus` (~`:217`).
- The Postgres precedent: `postgres/service.go`'s statusReason mapping, GraphQL `OptionalStrField`, and `status_reason_cross_surface_test.go`.

## Acceptance criteria

- [x] Both fields appear on all three surfaces for an unavailable Key Value and are omitted, or null on GraphQL, for a healthy one.
- [x] An unknown reason gets a generic sentence and still carries its code.

## Result (2026-10-07)

- `KeyValueView` carries `statusReason` and `statusReasonCode` when the status is `unavailable`.
  - The sentences live in `internal/keyvalue/status_reason.go` (`unavailableReasons`), one fixed sentence for each of the 20 failed reasons.
  - `StorageShrinkRejected` passes the operator's own message through, as Postgres does.
  - An unknown reason gets "The Key Value failed to reconcile (Reason)." and keeps its code.
  - A suspended or deleting store carries no reason.
- **Surfaces:**
  - GraphQL uses `OptionalStrField`, so a healthy store returns null.
  - MCP returns the view.
  - REST needed its own `renderKeyValue` fields. The cross-surface test caught their absence: REST had dropped both.
