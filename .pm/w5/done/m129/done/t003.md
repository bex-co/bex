## Objective

The dashboard's Key Value Details card shows an unavailable Key Value's reason, translated by `statusReasonCode` in en and zh, and falls back to bex-api's sentence for a code it does not know.

## Context

- The Postgres precedent: `features/databases/components/database-metadata-card.tsx`, `features/databases/lib/labels.ts`, and `lib/__tests__/status-reason-vocabulary.test.ts`, which reads the reasons and sentences from the Go source.

## Acceptance criteria

- [x] en and zh translations for every reason bex-api explains; a vocabulary test fails if one is missing.
- [x] The skeleton still matches the ready card (dashboard/AGENTS.md).

## Result (2026-10-07)

- The Key Value detail query fetches both fields; types were regenerated offline from `TestDumpGraphQLSchema`, touching only this query's hunk.
- `KeyValueView` gains `statusReason` and `statusReasonCode`. The list maps them to null.
- The Details card's Status row shows the reason under the status label, translated through `STATUS_REASON_LABEL` (`features/keyvalue/lib/labels.ts`). It falls back to bex-api's sentence for an unknown code.
- en and zh carry 21 keys: the 20 sentences, plus the dashboard's own shrink copy, which doesn't name a size because the view fetches none.
- `features/keyvalue/lib/__tests__/status-reason-vocabulary.test.ts` reads the reasons from the Go source, across the Key Value and Database types files, and their sentences from bex-api. The en copy must equal bex-api's sentence.
- The card's skeleton is unchanged: a healthy store, the common ready state, has no reason line.
