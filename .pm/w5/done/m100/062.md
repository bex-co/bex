# 062 — `pre_deploy_failed` is undiagnosable from the CLI: bex tells the user to "check the pre-deploy logs", which no Render-compatible client can request

Why: the platform's own failure message names a next step the CLI cannot take — the pre-deploy step's output lives behind a bex-only log type the pinned client's closed `--type` enum rejects, so a failed migration is a dead end for every CLI and automation user.

- **Severity:** major (a supported deploy path fails with actionable server-side detail that the primary automation surface cannot reach; no data loss).
- **Attribution:** server + docs. The client-side half is upstream and correct for Render, so the launcher cannot fix it.
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-15 UTC, sweep 4. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, human device login, `bex v0.2.1` (upstream pin v2.27.0), `https://api.bex.co/v1/`. Fixtures `qa-20260915-f29821-n3` (`srv-daksr21cin2c7382cj80`) and `qa-20260915-f29821-pd` (`srv-dakss49cin2c7382cj9g`), both created and deleted inside the run.

## Reproduction

A free web service whose pre-deploy command prints a marker and exits non-zero:

```text
$ bex services create --name qa-…-pd --type web_service --runtime image \
    --image docker.io/library/busybox --plan free --region frankfurt \
    --pre-deploy-command "echo QA_PREDEPLOY_MARKER_f29821; exit 7" --confirm -o json
# exit 0 -> srv-dakss49cin2c7382cj9g   (preDeployCommand round-trips on read)

$ bex deploys list srv-dakss49cin2c7382cj9g -o json
[{"id":"dep-…","status":"pre_deploy_failed","startedAt":"…","finishedAt":"…", …}]
```

The output exists and the server will serve it — but only under the bex-only type:

```text
$ GET /v1/logs?ownerId=tea-…&resource=srv-dakss49cin2c7382cj9g&type=predeploy&limit=20
HTTP/2 200 -> 1 record, message "QA_PREDEPLOY_MARKER_f29821"
```

No request the pinned CLI can construct reaches it:

| command                                             | result                                                                     |
| --------------------------------------------------- | -------------------------------------------------------------------------- |
| `bex logs --resources <srv> --limit 30 -o text`     | 0 lines                                                                     |
| `bex logs --resources <srv> --type app`             | 0 lines                                                                     |
| `bex logs --resources <srv> --type request`         | 0 lines                                                                     |
| `bex logs --resources <srv> --type build`           | 3 lines — `==> Deploy queued`, `==> Deploying image …`, `==> Pre-deploy failed` |
| `bex logs --resources <srv> --type app,request,build` | 0 matches for the marker                                                   |
| `bex logs --resources <srv> --type predeploy`       | **exit 1**, client-side: `invalid argument "predeploy" for "--type" flag: must be one of "app", "request", "build"` |

And the guidance the platform itself emits (`GET /v1/services/{id}/events`, same run):

```json
{
  "type": "deploy_ended",
  "details": {
    "deployStatus": "failed",
    "preDeployStatus": "failed",
    "fullDeployStatus": "pre_deploy_failed",
    "failureReason": "the pre-deploy command exited with code 128; check the pre-deploy logs"
  }
}
```

A CLI user is told to check logs the CLI refuses to ask for. The `build` stream tells them the step failed but never why.

## Root cause

- `LogTypePreDeploy = "predeploy"` (`lego/backend/internal/logs/service.go:58`) is a deliberate bex extension, documented in `docs/ADR010-observability.md:127-134`: a **live** read of the `predeploy` container on the `app.bex.co/predeploy=<name>` Job pod, never Loki, and it must be requested **on its own** — mixing it with `app`/`request`/`build` is a named 400 (`logs/service.go:250-256`). `docs/ADR018-render-parity.md:71` records the same: "an untyped log query still does not include them — `predeploy` is a live Job-pod read requested on its own."
- The pinned client's `--type` is a closed enum over Render's three values, validated before any request is built, because Render has no fourth log type — its deploy log stream simply contains the pre-deploy output.
- So the extension is, by construction, unreachable from the one surface Render users arrive with. The two facts are each documented; **their intersection — that `pre_deploy_failed` cannot be diagnosed via the CLI — is not**, and `docs/cli-compatibility-checklist.md:119` grades `--type <types>` a plain `[x]` on the strength of the `app`/`request` split alone.
- Secondary: the pre-deploy Job pod is TTL-reaped (ADR010: "a Job pod TTL-reaped after its hour is simply gone"), so even a dashboard user has roughly a one-hour window to read why a migration failed.

## Fix — pick one, then record it

**(a) Make the output reachable by Render-compatible clients (~2h, promote to a milestone).** Ship the pre-deploy Job pod's stdout/stderr into the `build` stream as well, which already narrates `==> Pre-deploy failed` in the same window — matching Render, whose deploy log stream carries pre-deploy output. Keep `type=predeploy` as the precise bex extension. This needs the operator's log shipper to label the pre-deploy Job pod the way build pods are labelled (`app.bex.co/build=<name>` → Loki `type=build`), plus the backend type mapping, tests, and the ADR010/ADR018 updates. It also fixes the TTL problem, since the durable store then holds the output.

**(b) Stop pointing at an unreachable surface (~30m).** Leave the architecture alone; change `failureReason` so it names a surface the reader can actually use (the dashboard deploy detail, or `type=predeploy` over REST/GraphQL/MCP), and write the CLI gap into `docs/cli-compatibility-checklist.md:119` and the ADR018 pre-deploy row. This is honest but leaves CLI users without the output.

Prefer (a); (b) is the correct fallback if the shipping change is not wanted now. Either way the checklist row must stop reading as unqualified support.

## Blast radius

`logs/service.go`'s type validation and every adapter that exposes it (REST `/v1/logs`, GraphQL `logs(type:)`, MCP `list_logs`); the operator's log-shipper pod labelling if (a); the deploy-detail log viewer, which already interleaves `build`/`predeploy`/`app` (`docs/render-artifacts/deploy-detail-page.md:20`) and must not double-render the same lines if they start arriving under both types; `failureReason` producers in `internal/predeploy` / the deploy reconciler if (b).

## Regression checks

- A pre-deploy command that prints a marker and exits non-zero: the marker is retrievable through a request the pinned CLI can actually make (option a), asserted end to end rather than only against the backend handler.
- `bex logs --type build` on that deploy still contains the `==> Pre-deploy failed` narration and does not duplicate lines.
- The mixed-type 400 (`build`/`predeploy` with others) stays a named refusal — `.pm/w3/done/006.md` closed on exactly that behavior.
- Deploy-detail interleaving shows each line once.

## Unverified

- Whether the dashboard deploy-detail viewer currently renders the pre-deploy marker was not checked this run (the CLI was the subject).
- The TTL window was not measured; it is quoted from ADR010.
- Exit code 128 vs 7: the shell-less `traefik/whoami` fixture produced 128 with no output; the busybox fixture produced the marker. The `failureReason` text was captured from the 128 case.
