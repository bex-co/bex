## Objective

Now that SSR queries actually authenticate (t002), any route-guard/loader logic that was written around or compensating for the previously-broken SSR auth (e.g. always treating SSR as unauthenticated and deferring to client-side redirects) needs to be checked for correctness and fixed if it double-guards or mishandles the now-real SSR auth state.

## Context

- `dashboard/src/routes/__root.tsx` — the most likely place for a root-level auth gate.
- t001's survey of SSR-dependent routes/loaders.

## Steps

1. For each route/loader from t001's survey, check whether its logic assumed SSR auth never succeeds.
2. Fix any logic that would now behave incorrectly (e.g. a redirect loop, or missing a legitimate SSR-authenticated fast path).

## Files

- `dashboard/src/routes/__root.tsx` and any other routes flagged by t001

## Acceptance criteria

- [ ] No route exhibits a redirect loop or incorrect gate behavior post-fix.

## Out of scope

- Public-route behavior — t004.
