# A deleted secret-files Secret records no revision, so a late projection can recreate it

Why: w5/m127 orders every projection by store revision, but deleting a service's last secret file deletes its `<service>-files` Secret, and a Secret that no longer exists records nothing for a late projection to lose to.

- The order:
  1. The store holds `{f}` at version 1.
  2. `SetSecretFile(f, x)` commits `{f: x}` at version 2, then stalls before it projects.
  3. `DeleteSecretFile(f)` reads version 2. It deletes the Secret, drops `spec.filesFromSecrets` and commits `{}` at version 3.
  4. The stalled write finds no Secret. It creates `{f: x}` at version 2 and adds the reference back.
- The pod then mounts a file the store no longer holds, after the delete answered success.
- The window predates m127. m127 closes it for every Secret that still exists.
- A possible fix:
  - Keep an emptied files Secret as an empty Secret stamped with its revision, still unreferenced, so no empty `/etc/secrets` mount appears.
  - Have `projectFiles` leave the App reference to the later write when its projection is superseded.
- That changes a pinned contract: `TestSecretFiles_RoundTripAndProjection` expects the Secret gone after the last delete, and ADR013 says it is "deleted when the last file goes away".
- Test: the four-step order above, with the pod's Secret and reference matching the store afterwards.
- Found by w5/m127 (2026-10-06).

**Result (2026-10-07):**

- **The record.** Emptying a map no longer deletes its projection Secret. `projectSource` dropped its `remove` mode, so an emptied map is projected like any other map: the Secret stays empty, stamped with the store revision, and is created if it was missing. A stalled write's late projection of an earlier revision is now superseded instead of recreating the Secret with a file the store no longer holds.
- **Compensation.** `compensateEnvironment` no longer deletes a Secret restored over an empty map. That path reopened the same window behind a delete.
- **The mount follows the Secret.** `sourceProjection.HoldsData` reports whether the Secret, as the call left it, holds any key: the winning write's data when superseded.
  - `projectFiles` mounts by it, and only a projection that was not superseded removes the mount. The old rule mounted whenever the late write's own map was non-empty. Because App writes are merge patches, that re-added the mount whenever the stalled write was the service's first file.
  - Removing the mount also clears a mount a save-only write staged.
  - The save-only path stages the mount `projectFiles` decided, instead of re-deriving it from the write's own map.
- **Left alone on purpose.**
  - Create-time `abortProjection` still deletes, because no App exists to own a kept Secret.
  - The CAS env rollback still deletes, because it removes only the Secret its own write just created.
- **Tests.**
  - New tests cover the four-step order and the same window through a failed write's compensation. Each runs from two starts, a mounted map and the service's first write, for env and files.
  - A late first write must mount the map a restore kept.
  - A late save-only first write must stage no mount.
  - Two deletes that together empty the Secret must leave no files mount.
  - Emptying through the single-key delete and through a deploying batch must clear a staged mount.
  - The `projectSource` table gained rows for an emptied map: created when missing, kept when it was there, left alone at the same revision, and left to a later revision. It also asserts `HoldsData` on every row.
  - `TestSecretFiles_RoundTripAndProjection` and the compensation test over empty maps now expect the Secret kept, empty.
  - Eight mutants each fail the suite, including the old mount rule, deleting on empty, a restore that deletes, staging from the write's own map, and `HoldsData` taken from the caller's data.
- **Doc.** ADR013's compensation and revision-owned projection paragraphs describe the kept Secret and the mount rule. They also correct two stale claims: that a delete carries a UID precondition, and that create-time preparation projects through the shared primitive.
- **Follow-ups:**
  - w5/117: the App reference is still not ordered by revision. Its merge patch has no precondition, so a stalled emptying write can drop a reference a later write added.
  - w5/118: a service recreated before garbage collection inherits its predecessor's projection Secrets.
