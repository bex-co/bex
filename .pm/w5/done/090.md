# Create refuses build settings its build never reads

Why: create stores settings the build ignores, and update refuses the same settings, so a service can hold configuration that does nothing and that the user cannot change back through the setter.

- **Found by** w5/m117's round trip (2026-10-05), which only checks that an export reproduces what create stored:
  - a `builder` on a prebuilt image (`image` + `builder: dockerfile` or `buildpack` creates, and the builder is never used);
  - `dockerfilePath`/`dockerContext` on a native runtime or a buildpack build, which `SetDockerfilePath` refuses ("dockerfile path only applies to a Dockerfile-built service", `settings_check.go`);
  - a `startCommand` on a static site, which serves files and runs nothing.
- **Fix:** refuse each in `specFromCreate` with update's wording, and keep Render's inertness at the transports. REST already drops docker details on a native runtime or a prebuilt image (`buildsDockerfile`, ADR006); MCP's `dockerfilePath`, upstream's docker argument, should follow its `dockerContext` there. Then only bex's own surfaces (GraphQL, the Blueprint parse) meet the refusal, and `TestCreateWireFieldsReachTheRequest`'s MCP rule for `dockerfilePath` becomes `dockerfileBuildOnly`.
- **Test:** a create per case answers the setter's 400.

## Outcome (2026-10-06)

Done.

1. **Create refuses settings its build never reads,** with update's answer where update has one (`errDockerfileBuildOnly`, and `startCommandApplies` in the shared per-type block):
   - a `builder` other than auto on a prebuilt image, a new create-only entry in `prebuiltImageSourceFields`; `runtime: docker` beside an image, which stored the same inert builder, is refused too;
   - a `dockerfilePath` or `dockerContext` where `buildStrategy` builds no Dockerfile: a native runtime, buildpacks, a prebuilt image, or a static site that only publishes;
   - a static site's `startCommand`.
2. **Render's inertness stays at the transports.** `dockerDetails.dockerfileOnly` drops a Dockerfile setting from a non-Dockerfile create on REST and on both MCP create tools (`dockerfilePath` now follows `dockerContext`), and the transport guard's MCP rule became `dockerfileBuildOnly`. The dashboard never sends these settings.
3. **A static site's native runtime now needs only its build command.** It used to also require a start command that nothing runs, which (1) now refuses.
4. **The Blueprint path, from the review:**
   - The compiler refuses the same fields at their own paths with `BLUEPRINT_CAPABILITY_INCOMPATIBLE`.
   - An export leaves the Dockerfile settings out unless the service builds a Dockerfile, so a service created before this change still exports a file that validates.
   - A sync that moves a service off a Dockerfile build clears the settings the file omits.
5. **One premise correction.** The operator's native build did read `dockerContext`, as its BuildKit context. Create now refuses it there, as Render reads it for Docker builds only. Services created before keep it, their builds keep using it, and ADR006 says so.
6. **Tests:**
   - `TestCreateRefusesBuildSettingsItsBuildNeverReads` has nine cases. Each create refusal equals the setter's refusal where a setter exists, and the Dockerfile and static-native creates still pass.
   - Also added: `TestALegacyInertBuildSettingStaysSyncable`, `TestBlueprintRefusesDockerfileSettingsBesideAnotherBuild`, `TestBlueprintSyncOffADockerfileBuildClearsItsSettings`, and a `runtime docker with an image` row in `TestResolveBuildStrategy`.
   - Mutants are caught: each refusal off, the old static-blind predicate, the export ungated, the sync not clearing, and static-native still needing a start command.
   - The probes and round trip moved accordingly. The static start-command gap left `blueprintNotExported`, since create no longer accepts it.
