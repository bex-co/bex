# 063 — The OpenAPI validator's bare `invalid query parameter "x"` pre-empts bex's own actionable 400s, so a list request never learns the bound it violated

Why: bex deliberately built one actionable 400 vocabulary for list filters (`core.ParseEnum`: "one vocabulary and one 400 message serve every surface"), and the request validator sits in front of it and answers with a message that names neither the accepted values nor the numeric bound — so the designed message is unreachable for every parameter Render's schema constrains.

- **Severity:** minor (polish, but it is a support cost on the most common client mistake and it is inconsistent with bex's own error conventions).
- **Attribution:** server (request-validation layer).
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-15 UTC, sweep 5. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, human device login, `render-cli/2.27.0` User-Agent, `https://api.bex.co/v1/`.

## Reproduction

Through the CLI (exit 1 in every case — the failure is loud, only the reason is missing):

```text
$ bex logs --resources srv-… --type build --limit 150
Error: error listing logs: received response code 400: invalid query parameter "limit"
```

Direct, across endpoints:

| request | response body |
| --- | --- |
| `/v1/logs?…&limit=150` | `{"error":"invalid query parameter \"limit\"", …}` |
| `/v1/logs?…&limit=0` | `{"error":"invalid query parameter \"limit\"", …}` |
| `/v1/logs?…&direction=sideways` | `{"error":"invalid query parameter \"direction\"", …}` |
| `/v1/services?…&limit=500` | `{"error":"invalid query parameter \"limit\"", …}` |
| `/v1/postgres?…&limit=500` | `{"error":"invalid query parameter \"limit\"", …}` |
| `/v1/key-value?…&limit=500` | `{"error":"invalid query parameter \"limit\"", …}` |
| `/v1/postgres?…&suspended=bogus` | `{"error":"invalid query parameter \"suspended\"", …}` |

`limit=0` and `limit=500` — opposite violations of opposite bounds — are indistinguishable. Contrast the one parameter that _does_ reach bex's handler, on the very same endpoint:

```text
$ /v1/logs?…&type=pre_deploy
{"error":"bad request: unknown log type \"pre_deploy\" (want app|request|build|predeploy)", …}
```

Same request, same user, one actionable message and one opaque one.

## Root cause

- The enforced validator is pinned to Render's OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`). It owns these constraints: `/logs` and `/postgres` declare `limit` as `{"type":"integer","default":20,"minimum":1,"maximum":100}`, `/logs` declares `direction` as `{"type":"string","enum":["forward","backward"]}`, `/postgres` declares `suspended` as `{"type":"array","items":{"enum":["suspended","not_suspended"]}}`.
- A value violating any of those is refused at the edge with the generic `invalid query parameter "<name>"`, so the handler never runs.
- bex's handler layer has a purpose-built message for exactly this class — `core.ParseEnum` (`lego/backend/internal/core/pagination.go:145-151`) returns `unknown %s %q (want %s)`, and its doc comment states the intent: "Adapters with typed arguments (GraphQL/MCP) share it with REST so one vocabulary and one 400 message serve every surface." `ParseDirection` carries the same comment ("one vocabulary and one 400 message for every surface, so a second direction-honoring list can't drift from the first").
- Wherever Render's schema constrains a value, that message is dead code on REST. `type` is the exception only because bex widened its schema for the `predeploy` extension, letting the value through to the handler.
- Consequence for GraphQL/MCP: those adapters do **not** pass through the REST validator, so the same bad value produces the good message there and the bare one on REST — the cross-surface consistency `ParseEnum` exists to guarantee is broken in practice.

## Fix (~40m)

Make the validator's refusal carry the violated constraint, which it already knows (it is doing schema validation and has the failing keyword, the bound, and the enum in hand):

- Map the validation error into bex's error envelope with the constraint named — e.g. `limit must be an integer between 1 and 100`, `direction must be one of forward|backward`, `suspended must be one of suspended|not_suspended` — keeping `id: bad_request` and the existing status code so no client contract changes.
- Prefer deriving the text from the schema rather than a hand-maintained per-parameter table, so a pin refresh cannot make it stale.
- Then assert REST and GraphQL/MCP produce the same vocabulary for the same bad value, which is what `ParseEnum`'s comment already promises.

Leave `unsupported query parameter` (parameter absent from the schema) as its own distinct message — that one is correct and is the subject of `w5/060`.

## Blast radius

Every REST list endpoint behind the validator: `/v1/logs`, `/v1/services`, `/v1/postgres`, `/v1/key-value`, `/v1/projects`, `/v1/environments`, events, audit logs. Error **codes** and statuses must not change — only the human message — so existing clients and the dashboard's error handling are unaffected. Check that no test asserts the exact current string.

## Regression checks

- `limit=0` and `limit=500` produce **different**, bound-naming messages on at least `/v1/logs` and `/v1/services`.
- `direction=sideways` names both accepted values.
- A valid `limit=100` still returns `200` with exactly 100 records (verified this run: `limit=10/50/100` → `10/50/100` lines).
- REST and GraphQL/MCP agree on the message for the same invalid enum value.
- `w5/060`'s `unsupported query parameter` case keeps its own distinct wording.

## Unverified

- Whether Render's own API returns a richer message was not checked; this note argues from bex's **internal** inconsistency, not from Render parity.
- The full list of endpoints behind the validator was not enumerated; six were probed.
