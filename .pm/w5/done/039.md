# Pre-existing: paid KeyValue backup fails at the snapshot step (Valkey connectivity)

Surfaced 2026-08-04 while enabling ADR050 Tier A encryption in prod. **Not an ADR050 regression** — the encrypt step is downstream of the failure and never runs.

Symptom: a manual `kvbak-red-d9p49kdrtmes73c34ovg` Job (and the never-yet-run scheduled one) fails in the **`snapshot`** initContainer with:

```
Could not connect to Valkey at red-d9p49kdrtmes73c34ovg:6379: Try again
```

Evidence it predates ADR050:

- the KeyValue instance is `Ready` (pod `red-…-0` 2/2 Running), yet
- the scheduled `kvbak` CronJob has no `lastSuccessfulTime`/`lastScheduleTime`, and
- `s3://bex-tfstate/keyvalue/red-d9p49kdrtmes73c34ovg/` has **0 objects** — no KV backup has ever succeeded for this instance.

`Try again` is a DNS temporary-resolution failure, so the likely cause is the backup Job pod not resolving/reaching the Valkey Service — a NetworkPolicy (ADR043 tenant isolation) or Service-name/DNS issue, owned by ADR021 KeyValue backups, not ADR050.

## Root cause — CONFIRMED live (2026-08-07)

Read-only prod inspection (`hetzner-prod` context) traced this end to end. It is **not** a DNS/infra flake and **not** a Service-name bug — it is a missing operator-managed egress allow:

1. The KeyValue `red-d9p49kdrtmes73c34ovg` lives in the **`default`** apps namespace (Apps have migrated to per-workspace `tea-<xid>` namespaces; stateful KeyValue has not). Its Service endpoint **is** published (`10.244.67.229:6379`), so targeting/DNS records are fine.
2. `default` carries the Cilium `deny-tenant-node-and-metadata-egress` CiliumNetworkPolicy (`deploy/gitops/base/tenant-node-egress.yaml`). It selects **every `app.bex.co/workspace`-labelled pod that is not a CNPG pod** and — by design (see its header comment) — flips them into egress **default-deny**, expecting each tenant workload's own operator-managed allow to restore DNS/in-namespace/internet egress.
3. Apps get that allow from their hosting namespace's namespace-wide policies; **tenant Postgres is carved out** via `cnpg.io/cluster`. The **KeyValue backup/purge Jobs** carry `app.bex.co/workspace` (→ selected) but are **not** Apps and have **no** CNPG carve-out and **no** companion allow — so they are default-denied with nothing granting DNS.
4. Empirically confirmed: from the running Valkey pod (same Cilium selector as the Job), `nslookup` of the nameserver `10.96.0.10` **times out** and `getent hosts <kv>` fails. valkey-cli surfaces that resolver failure as `Try again`. There are **zero** k8s `NetworkPolicy` objects and no egress-allow CNP in `default`.

So KeyValue is the only tenant workload that is default-denied yet lacks an allow — which is exactly why **no** KV backup has ever succeeded, while Apps and tenant Postgres back up fine.

## Fix — LANDED in code (2026-08-07), live-green pending

`lego/operator/internal/controller/keyvalue_controller.go`: new `reconcileKeyValueBackupNetworkPolicy` emits a per-KeyValue `<name>-backup-egress` k8s `NetworkPolicy` (owned by the KeyValue, wired into `Reconcile` + `Owns`). It is **egress-only** and **scoped to the backup/purge Job pods** (`app.bex.co/component in {keyvalue-backup, keyvalue-backup-purge}`), granting exactly: DNS to kube-system CoreDNS (53 UDP/TCP), the Valkey Service (6379/6380 to `app.bex.co/keyvalue=<name>` pods), and public internet minus in-cluster/private + metadata ranges (S3 upload). It is **additive** — the Cilium node/metadata deny still wins — and a no-op where a namespace-wide allow already covers the pods (the eventual `<ws>`-namespace topology). The Valkey server pods, which never dial out, keep their default-deny egress untouched. Covered by `TestKeyValueBackupNetworkPolicyRestoresJobEgress`; operator build/vet/gofmt + all KeyValue tests green.
