## Objective

An authorization refusal answers a stable code on GraphQL, REST and MCP, without changing the 403 or the message. A refusal that already carries a more specific code (for example `INSUFFICIENT_SCOPE`) keeps it.

## Acceptance criteria

- [x] A bare `ErrForbidden` refusal carries the forbidden code on all three surfaces, and specific codes are untouched.

## Result (2026-10-06)

- `core.ErrForbidden` is itself a `CodedError` carrying `FORBIDDEN`; its 403 and message `forbidden` are unchanged.
- Every `fmt.Errorf("%w: …", core.ErrForbidden)` resolves to the code through `errors.As`. A `NewForbiddenError` refusal stays outermost, so its own code wins: `INSUFFICIENT_SCOPE`, `EMAIL_VERIFICATION_REQUIRED` and `ACCOUNT_DELETION_SESSION_REQUIRED`.
- Updated tests:
  - `core/scope_test.go` asserts that a denial's code is exactly `FORBIDDEN`;
  - `core/http_helpers_test.go` pins the 403 body.
- Evidence:
  - `TestTheDashboardsRefusalsAreCodedOnEverySurface/forbidden` covers REST, GraphQL and MCP;
  - `TestErrorDialectIsRenderShaped/insufficient_scope_403` still answers `INSUFFICIENT_SCOPE`;
  - an uncoded-`ErrForbidden` mutant fails.
- Side effect, verified safe: the dashboard's invite classifier already listed `FORBIDDEN` as terminal. `members.AcceptInvite` refuses as forbidden only before `AcceptInviteByToken`, so a forbidden redemption committed nothing and terminal is accurate.
