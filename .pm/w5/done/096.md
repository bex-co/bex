# A metadata patch mid-pass discards the pass's unsaved status changes

Why: `stampLastActive` and the disk annotation patches decode the full server response into `app`, replacing in-memory status the pass set earlier but has not written yet, so a release identity or artifact image recorded in memory can be lost.

- **Where:** `lego/operator/internal/controller/activity.go` `stampLastActive` (`r.Patch(ctx, app, …)` with the App itself as the target) and the disk paths (`disk.go` ~`:341`, `:356`). controller-runtime decodes the patch response into the object, status included.
- **At risk:** status the pass sets in memory and persists "later in the reconcile", e.g. the release identity (~`app_controller.go:572`) and `ArtifactImage` (~`:769`); `recentlyActive` runs after both (via ~`:2685`).
- **Fix:** patch a copy and copy back only the new resourceVersion and metadata, or move the patch before the status mutations; first prove it with a test that sets a status field, stamps last-active, and checks the field survives to the final status write.
- **Size:** about 45 minutes. Found by w5/074's efficiency review (not yet reproduced).

## Done (2026-10-06)

- Reproduced first. A test that set `ArtifactImage` and `ReleaseGeneration` in memory, stamped last-active and checked them failed on the old code: both fields were reset to the stored, empty values.
- Fix: `patchAppMeta` in `internal/controller/metadata_patch.go`.
  - It patches a deep copy, under `MergeFromWithOptimisticLock`, against the resourceVersion the pass holds, and brings back only metadata.
  - If the App changed since the read, the patch conflicts and the pass retries (w5/095). The pass's later status write therefore cannot overwrite status another controller wrote, such as `UndeployedChanges`. An unlocked first version of the helper could, as w5/096's quality review showed on envtest.
- Converted: last-active stamping, the four autoscale annotation patches, the disk restored and provisioned markers, the clear-cache annotation, the TLS secret history and the registry-credential rotation clear. The rotation clear also never adopted its resourceVersion, so the pass's next write conflicted with its own patch.
- The deletion path's registry-purge patch is left as it is: that pass holds no unsaved status, and its finalizer `Update` needs the server's spec with the server's resourceVersion.
- Tests:
  - the unsaved status survives a stamp, and the exact stamp and the status both land;
  - a patch over an App changed since the read conflicts and leaves the pass's App untouched;
  - an AST guard fails if any non-deletion function patches the pass's `app` directly.
  - 3 mutants, each killed.
