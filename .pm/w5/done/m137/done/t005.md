## Objective

The bex-only surfaces mirror the same one-step model: GraphQL and MCP expose the traffic `dnsRecord` and a `verificationStatus` with t004's meaning, and `ownershipStatus`/`ownershipDnsRecord` disappear from the schema, the tool descriptions, and the shared `DomainView`.

## Context

- `customDomainGQLType` (`lego/backend/internal/apps/graphql.go`) exposes `ownershipStatus`, `verificationStatus`, `serverStatus`, `dnsRecord`, `ownershipDnsRecord`; the dashboard's `useCustomDomains` maps `ownershipStatus → ownershipVerified` and `verificationStatus → verified` (TLS). After t004 the core view's verification field changes meaning — rename/repurpose deliberately so no adapter can keep reading TLS out of it, and give the dashboard's certificate column its own explicit field rather than a repurposed one.
- MCP `verify_custom_domain` etc. (`mcp.go`) describe filters as `unverified|pending|verified` — descriptions must match the new semantics and the tool must return the fresh (possibly still unverified) view instead of the old `DOMAIN_OWNERSHIP_PENDING` conflict.
- GraphQL schema is a public contract for the dashboard only; field removal is a coordinated dashboard change (t006) — land schema + dashboard reads so neither is broken at any pushed commit (order with t006 as needed).

## Acceptance criteria

- [ ] The cross-surface coded/semantics tables assert identical verification meaning and traffic record on REST, GraphQL, and MCP for apex, subdomain, and the auto-paired sibling.
- [ ] `grep -rn "ownership" lego/backend/internal/apps` returns nothing on domain surfaces; MCP tool text no longer mentions TXT/ownership.
- [ ] `verifyCustomDomain` on an unpointed domain returns the unverified view (no error); on a pointed one, verified.
