## Objective

REST custom domains speak Render's OpenAPI semantics exactly: `verificationStatus` is `unverified | verified` meaning traffic-DNS verification, add returns `201` with the array of created domains (pair included), verify returns `202` with no body, and no ownership field exists.

## Context

- Today `renderCustomDomain` (`lego/backend/internal/apps/domains.go`) carries `ownershipStatus`, `ownershipDnsRecord`, and a `verificationStatus` that reports **TLS issuance** (`pending|verified`), while `filterDomains` filters on that TLS value — so Render's `?verificationStatus=verified` silently means "certificate issued" on bex. The amendment corrects the semantics, not just the spelling: `pending` (internal) → `unverified` (wire), and the filter matches DNS verification, keeping `pending` accepted as the established alias.
- Add currently returns the single requested object (`addDomain` in `rest.go`); Render's OpenAPI declares an array and its generated CLI client decodes one. Returning the pair means `AddDomain`'s core result (or a list read at the adapter) must expose both rows in Render's order.
- Certificate progress stays available without overloading Render's field: additive `certificateReason` (existing) and the dashboard's GraphQL certificate status (t005/t006). Decide `serverStatus`'s fate in this task against the OpenAPI schema and record it; additive-and-inert is the bar for anything kept.
