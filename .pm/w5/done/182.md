# 182 — A header rule that changes a static file's Content-Type leaves its ETag unchanged, so a browser that revalidates keeps the old type

Why: an owner who saves a header rule to correct a file's type (a `.wasm`, a font) expects visitors to get it. A browser that cached the file revalidates with its old ETag, gets a 304 without a Content-Type, and keeps using the wrong type.

- **Source / severity / estimate:** `/pm-brainstorm for 残留问题 for w5` (2026-11-12), item 2; residual of w4/581. **Minor.** ~30m.
- **Root cause:**
  - `lego/operator/internal/staticserver/staticserver.go:690` caches `obj.etag = contentETag(obj.Body, contentType(reqPath, obj.ContentType))`, the type before header rules.
  - The rules apply afterwards, in `applyHeaders` (near `:507`).
  - Go's `http.ServeContent` drops Content-Type from a 304, so a rule change never reaches a revalidating browser.
- **Fix (target behavior):**
  - After the header rules apply, fold the response's final Content-Type into the tag: hash the cached tag with the final type. The body is not hashed again.
  - A rule that sets `ETag` itself still wins (w4/272).
  - With no rule touching Content-Type, the tag stays what it is today, so no cache is invalidated by this change alone.
- **Tests:**
  - adding a Content-Type rule changes the ETag;
  - `If-None-Match` with the old tag answers 200 with the new type;
  - with no rule the ETag is unchanged;
  - a saved ETag rule still answers 304 to its own tag.
- **Render parity:** Render's static-site header rules apply to the response; standard HTTP validators must follow the representation.
- **Dedupe:** w4/581 (done; served type in the tag), w4/272 (done; saved ETag rules), w4/341 (done; validators).

- **2026-11-12 (loopx w5):** done. After the header rules apply, a rule that changed the served Content-Type now also changes the generated tag (`retypedETag` in `staticserver.go`). It hashes the cached content tag together with the final type, so the body is not hashed again. A browser that revalidates with the old tag therefore gets 200 with the new type, not a 304, which carries no Content-Type. A saved ETag rule still wins (w4/272), and with no Content-Type rule the tag is the content tag, as before. Test: `TestAContentTypeRuleChangesTheGeneratedETag` checks the new strong tag, a 200 with the new type for the old tag, a 304 for the new tag, and the saved-ETag precedence.
