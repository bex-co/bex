# A Blueprint apply and preview still list the workspace's datastores two or three times

Why: w5/114 made the apply's ownership preflight share `deployParsedStack`'s datastore snapshots. The action plan that runs just before still takes its own identical lists, and so does the validate preview. bex-api's Kubernetes client is uncached, so each list is an API-server round trip returning every datastore in the workspace.

- **Apply** (create, sync, `DeployStack`): `blueprintActionPlan` → `newBlueprintActionResolver` (`lego/backend/internal/apps/blueprint_state_plan.go:118,132`) lists Databases and Key Values. `deployParsedStack` then lists them again in `stackDatastoreSnapshots`, with no cluster write in between. A create also lists all three kinds once more for the view it returns (`blueprint.go` `CreateBlueprint` → `resolveBlueprintResources`).
- **Preview** (`blueprintValidationFor`): the lists happen in `previewOwnershipConflicts` and again in the action plan. `validateWorkspaceReferences` lists a third time when the manifest references a datastore it does not declare.
- **Fix:** take `stackDatastoreSnapshots` once per request and pass it down, using the existing "nil means fetch here" convention (`resolveExistingBlueprintReferences`, `blueprintOwnershipConflicts`). The post-write ownership stamp keeps its own lists, because it must see the CRs the apply creates.
- **Test:** count the lists, as `TestABlueprintApplyAndReadEachReadTheClaimsOnce` does. A sync and a preview list each datastore kind once before any write.
- Found by w5/114's efficiency and reuse reviews (2026-10-07).

**Result (2026-10-07):**

- **One snapshot per request.** `datastoreSnapshot` (`lego/backend/internal/apps/datastore_snapshot.go`) lists each datastore kind on first use and serves every read before the request writes a Database or Key Value:
  - the action plan's resolver, and the ownership check;
  - reference resolution, and the apply's display-name lookups.
  - It replaces w5/114's nil-means-fetch `(databases, keyValues)` pairs and `stackDatastoreSnapshots`. The ownership check reads the snapshot's tenant instead of taking its own.
- **Where snapshots start.**
  - `deployStack`.
  - `runSync`, right after admission. Staging writes only the store.
  - The validate preview, which writes nothing.
  - The create's plan reads one snapshot, and its apply reads a fresh one after admission. Admission serializes the Blueprint's applies, and an apply admitted first may have created a datastore since the plan's read. The simplify review found that reusing the plan's snapshot reopened that window.
  - The post-write ownership stamp and the create's returned view still list for themselves.
- **Lists of each kind before the first write.**
  - A sync that drops a resource: 3 → 1.
  - A preview: 3 Databases and 2 Key Values → 1 of each.
  - DeployStack: 2 → 1.
  - A create stays at 2, by design.
- **Simplify.**
  - The parallel `prefetch` was dropped. In production the plan always fills the snapshot first, so it never ran; the datastore apply now reads through the getters.
  - `blueprintDetachments` takes a lazily built resolver instead of a resolver plus a snapshot.
  - Comments that still described the nil contract were fixed.
- **Test.** `TestABlueprintRequestListsEachDatastoreKindOnceBeforeItWrites` counts lists before the first cluster write:
  - a create lists each kind twice;
  - a preview with an undeclared `fromDatabase` reference lists each once;
  - a sync that adds a service and detaches the Postgres lists each once.
  - Seven mutants each fail it, including one that reuses the plan's snapshot after the create's admission.
  - The apps suite passes, and `make lint` is clean.
