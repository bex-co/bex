## Objective

Separate the lifetime of rollback runtime selection from the saved inputs used for subsequent deployment.

## Context

- Saved Settings must remain B while A is serving; the next normal deploy must consume B.
- Operator reconciliation, pod replacement and standard deploy dispatch can expose an incorrectly persisted override.

## Steps

1. Trace standard deploy, restart and reconcile paths; retain or clear release selection according to t001 rather than accidentally restoring saved state.
2. Ensure service reads and Settings display saved values, and existing deploy history truthfully identifies the running rollback. Explicitly disposition `UndeployedChanges`, currently limited to canceled releases, for rollback divergence.
3. Preserve dashboard/API auto-deploy options and update affected UI copy or projections only where needed. Verify same-image/config-only rollback and already-running-target capability guards against the selected release, not just saved image fields.

## Acceptance criteria

- [x] After rollback, all saved-setting reads still report B and the next standard deploy runs B.
- [x] Reconciliation, pod replacement and explicit Restart retain A while saved configuration remains B; the next standard deploy intentionally replaces it with B.
- [x] Same-image/config-only targets and already-running-target refusals are covered without stale action capabilities.
- [x] UI behavior distinguishes saved settings from the selected deployment without inventing a new configuration workflow.

## Out of scope

- New configuration-history UI; changing unrelated Settings save semantics.
