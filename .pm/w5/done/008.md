# Logs-tab structured filter UI — UNBLOCKED (w3/m8 landed 2026-07-12)

UI half of the parity ledger's "Request / HTTP logs + structured filters" row: filter controls on the service Logs tab (type, level, statusCode, method, path, instance — Render's filter vocabulary), with dropdown values fed by the label-values discovery `w3/m8` shipped. Before building, capture Render's live Logs filter UI via Playwright (→ `docs/render-artifacts/`) so controls/labels/placement are render.com-consistent, not guessed.

## What w3/m8 shipped for the UI to consume (2026-07-12)

The backend half is done — REST/GraphQL/MCP all honor the full filter set (docs/ADR010-observability.md § Log filters). The GraphQL surface the dashboard already talks to now offers:

- `logs(resource, type, text, level, instance, host, statusCode, method, path, direction, limit)` — `type`/`text` stay single-valued strings (the shape the dashboard already sends, unchanged); the request filters are `[String]` lists.
- `LogEntry { timestamp message type instance level method statusCode }` — the row gained `level`/`method`/`statusCode`, and `type` is now **truthful per line** (`app` vs `request`) instead of the hardcoded `"app"` it used to be.
- `logLabelValues(label, resource, …filters)` → `[String]` — the dropdown feed (labels: `host`|`instance`|`level`|`method`|`statusCode`|`type`), scoped to the service.

## Observed UI drift (filed here, not fixed in w3/m8)

1. **The Request type option now returns real lines.** `log-filter-bar.tsx`'s type dropdown already offers `all`/`app`/`request`; picking Request used to return an empty page and now returns Traefik access lines. The **message is the raw JSON access line** — the viewer renders it as-is, which is honest but ugly. A request line probably wants its own rendering (method/status/path chips from the labels, JSON collapsed), not the app-line treatment.
2. **No filter controls for the newly-honored filters** — level, statusCode, method, path, instance. That's the substance of this note.
3. **Stale comments corrected in place** (2026-07-12, w3/m8): `log-filter-bar.tsx` and `logs.graphql` claimed the API "can't honor" these filters over raw pod logs. It can now; the comments no longer say otherwise. No behavior change.
4. **New empty/error state to handle:** without the durable store (`BEX_LOKI_URL` unset — local dev), `type=request` and the store-only filters now return **503** rather than an empty page (the honesty rule). The Logs tab should show an explanatory state ("request logs need the log store") instead of a generic error toast. Prod has Loki wired, so this is a dev-mode state.

Promote as milestone-sized (filter state + URL sync + label-value queries + request-line rendering + the 503 state + capture comparison + tests).
