# ci-schedule-drift lists runs through the runs API's event search, the same lagging path as a branch filter

Why: `scripts/ci-schedule-drift.sh` lists runs with `gh run list --event schedule`, and GitHub serves an `event` filter by searching runs, as it does `branch`. That search can lag (cli/cli#7341), the failure w5/082 fixed in ci-red-streak and the ship gate, so a drift report could be computed from stale runs.

- **Where:** `scripts/ci-schedule-drift.sh` ~`:145`.
- **Fix:** measure first, as w5/082 did. List the workflow's newest runs without `--event`, keep `.event == "schedule"` in jq, and size `--limit` so the inspected schedule history still fits. Teach its self-test's fake `gh` to answer `--event` with a stale page, so a regression fails there.
- **Size:** about 30 minutes. Found by w5/082's quality review (not yet reproduced).

**Result (2026-10-07):**

- **The listing.** `ci-schedule-drift.sh` lists each scheduled workflow's newest runs, one API page of 100, with no `--event` filter. Its jq keeps the scheduled ones. This is how w5/082 fixed `--branch`.
- **Measured 2026-10-07:**
  - infra's newest 100 runs are the most mixed: 81 scheduled, 18 pushes.
  - The weekly workflows have 12 runs or fewer in all.
  - The check needs about 10 scheduled verdicts at most.
  - Calls are unchanged at two per workflow, and a run takes about 10s instead of 7s.
- **Review fix.** The "in the N inspected" count was counting every event. It now counts scheduled runs only, so "never fired" still reads 0 beside a manual run.
- **Tests.**
  - New case (o) goes through the real fetch path with a stub `gh`. The stub answers `--event`, or `-e`, with a stale page and rejects any unknown flag.
  - New case "never fired beside a manual run".
  - Both fail on the old code, as two mutants confirmed.
  - The live run reports OK.
