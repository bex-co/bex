# A database's unavailable reason should travel as a code the dashboard can translate

Why: `dashboard/src/features/databases/components/database-metadata-card.tsx:40-44` renders `statusReason`, a fixed English sentence built in the backend, so zh users see English. The same reason strings are also copied as literals in a second package.

Source: Last-24h code review, 2026-10-05 (user handed all fixes to w5). Follow-up to `faf2ca1f6` (w4/m170, "explain unavailable databases").

## Where

- `lego/backend/internal/postgres/service.go:97-100` (`StatusReason` field) and `:436-437` (`statusReason()` from the Ready condition).
- Exposed on GraphQL at `postgres/graphql.go:43`.
- The Ready reasons are repeated as string literals in `lego/backend/internal/store/datastore_observations.go`.

## Fix

1. Put the Database Ready reasons in `lego/types/v1alpha1` as constants, and use them from `postgres/service.go` and `store/datastore_observations.go` instead of literals.
2. Expose a reason code next to `statusReason` on REST, GraphQL and MCP; keep the sentence for API clients.
3. Dashboard: translate by code (en and zh), falling back to the sentence for unknown codes.

Done: the zh database page shows a translated reason; REST, GraphQL and MCP carry the same code; no reason literal is duplicated.

## Outcome (2026-10-06)

Done.

The shrink refusal names the allocated size from `diskSizeGB`. `status-reason-vocabulary.test.ts` reads the reasons and sentences from the Go source: every reason bex-api explains must have a translation whose en copy is that sentence.
