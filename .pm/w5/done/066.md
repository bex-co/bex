# 066 — A Postgres read replica is returned without the `id` Render's schema requires, so `bex postgres get` prints `"id": ""`

Why: the repo's own pinned Render schema marks `readReplica.id` **required**, the pinned client decodes it into a non-pointer string, and bex never sends it — so every Render-compatible consumer that resolves a replica by id gets an empty string.

- **Severity:** minor (a replica is still usable by name and its hosts are correct; the broken field is the identifier).
- **Attribution:** server (response shape violates the pinned consumer's requirement).
- **Found:** live `/qa-find-bugs-cli` hunt, 2026-09-16 UTC, sweep 9. Workspace `bex` / `tea-d98210cbbpdc73dcrkvg`, human device login, `bex v0.2.1` / upstream pin v2.27.0. Fixture `qa-20260916-8cd143-pgrr` (`dpg-dakvgsish60c73ao4m80`), free plan, created and deleted inside the run.

## Reproduction

```text
$ bex postgres create --name qa-…-pgrr --plan free --region frankfurt \
    --read-replica qa-replica --confirm -o json
# exit 0

$ bex postgres get dpg-dakvgsish60c73ao4m80 -o json
  readReplicas = [{"id": "", "name": "qa-replica"}]        ← id is the empty string
```

The wire response omits the key entirely:

```text
$ GET /v1/postgres/dpg-dakvgsish60c73ao4m80
"readReplicas":[{"name":"qa-replica",
                 "connectionInfo":{"internalHost":"dpg-…-ro.tea-….svc",
                                   "externalHost":"dpg-…-ro-qa-replica.db.bex.co"}}]
```

The `""` the CLI prints is the pinned client's zero value, not something bex sent.

## Root cause

Two divergences in one struct, and a code comment that asserts the opposite of the pinned schema.

- **bex's view** — `lego/backend/internal/postgres/service.go:172-178`:

  ```go
  // ReadReplicaView is one named read replica as returned in the Render-shaped
  // postgres object. Maps to Render's readReplicas[{name, connectionInfo}].
  type ReadReplicaView struct {
      Name           string                     `json:"name"`
      ConnectionInfo *ReadReplicaConnectionInfo `json:"connectionInfo,omitempty"`
  }
  ```

- **The pinned Render schema** — `lego/backend/internal/api/openapi/render-public-api-1.json`, `components.schemas.readReplica`:

  ```json
  {
    "type": "object",
    "properties": {
      "id": { "type": "string", "description": "The replica instance identifier." },
      "name": { "type": "string" },
      "parameterOverrides": { "$ref": "#/components/schemas/postgresParameterOverrides" }
    },
    "required": ["id", "name"]
  }
  ```

- **The pinned consumer** — `pkg/client/types_gen.go:2973-2980`: `type ReadReplica struct { Id string \`json:"id"\`; Name string \`json:"name"\`; ParameterOverrides *PostgresParameterOverrides }`. `Id` is a non-pointer with no `omitempty`, so a missing key decodes to `""` and prints as `""`.

So bex **omits a required field** (`id`), **omits an optional one** (`parameterOverrides` — present in bex's PATCH decoder at `internal/postgres/rest.go`, so the concept exists), and **adds a field Render's `readReplica` does not have** (`connectionInfo`). The comment's claim that Render's shape is `[{name, connectionInfo}]` is the origin of the mismatch — it is simply wrong against the document checked into this repo.

The OpenAPI validator did not catch this because it validates **requests**, not responses.

## Fix (~40m)

1. Add `ID string \`json:"id"\`` to `ReadReplicaView` and populate it. bex does not model a replica as its own `dpg-` resource today — the hosts are derived (`<primary>-ro…`) — so this needs a deliberate choice:
   - **(a) A stable derived id**, e.g. `<primaryID>-ro-<name>`, minted the same way for every read and never re-derived differently. Cheapest, no migration, and satisfies the required field.
   - **(b) A real minted `dpg-` id** persisted with the replica, if replicas are ever to become addressable resources (Render's field is described as "the replica instance identifier").
   Prefer (a) unless there is a plan to make replicas addressable; record whichever in `docs/ADR009-postgresql-management.md`.
2. Add `parameterOverrides` to the read view for parity with the PATCH input.
3. Keep `connectionInfo` — it is genuinely useful — but label it in `docs/ADR018-render-parity.md` as a **bex extension** on `readReplica`, and fix the `service.go:172-173` comment so the next reader is not misled again.
4. Mirror on GraphQL (`readReplicaViewGQLType`, `graphql.go:48,79`) and MCP so the three surfaces keep agreeing.

## Blast radius

`internal/postgres/service.go` (`ReadReplicaView`), `rest.go`, `graphql.go`, `mcp.go`, and the Postgres cross-surface parity test. Anything that already persists or displays a replica identity — check the dashboard's Postgres detail page before choosing (a) vs (b), since a derived id that later changes to a minted one is a second break.

## Regression checks

- A Postgres created with `--read-replica <name>` returns a non-empty `id` on REST, GraphQL and MCP, and `bex postgres get -o json` prints it.
- The id is **stable** across two reads and across a primary update (assert equality, not just non-emptiness) — the property that makes (a) safe.
- `name` and `connectionInfo.{internalHost,externalHost}` keep their current values.
- A response-shape test asserts `readReplica` carries every field the pinned document marks required — the gap class the request-only validator cannot see.

## Unverified

- Whether the replica is actually serving reads was not tested (no `psql` against the `-ro` host this run); only the returned metadata was checked.
- **Open policy question, deliberately not claimed here:** bex accepted a read replica on the **free** plan. Render offers replicas only on paid tiers. That is the same class as HA-on-free from `w5/065` and deserves one decision covering both, rather than being asserted as a bug in this note.
- Render's live response was not called; the contract above is the document pinned in this repo.
