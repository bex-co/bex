## Objective

Fix the Kubernetes OpenSandbox substrate so a BatchSandbox and the server API report a terminal error when their owned sandbox Pod/container terminates unsuccessfully, instead of remaining `Pending` forever.

## Context

- Production Pod `3b34b8f2-55a9-42b0-a117-f94f5477d6e5-0` is `Failed`, exit 1, while its BatchSandbox remains `Pending` with no failed task count.
- The OpenSandbox server therefore returns Pending/Creating to bex-api indefinitely, bypassing the existing terminal-state fail-closed check.
- The controller is built from pinned upstream source plus repository patches under `deploy/opensandbox/patches/`; the fix must survive image rebuilds and remain compatible with retained/snapshotted sandboxes.

## Steps

1. Reproduce an owned Pod `Failed` transition against the pinned controller and identify why status aggregation omits it.
2. Patch the controller to project terminal phase, reason, task failure count, observed generation, and condition without confusing deliberate suspend/hibernate/terminate flows.
3. Verify the OpenSandbox server maps that BatchSandbox state to its terminal/errored API status.
4. Add a real-controller regression using the same image/CRD/template shape deployed in production.

## Acceptance criteria

- [x] A sandbox container exiting non-zero makes its BatchSandbox and server response terminal within two reconciliation intervals.
- [x] Failure reason and exit signal are bounded/non-secret and usable by the control plane.
- [x] Successful, suspended, hibernated, explicitly canceled, and retained-resource paths preserve their existing semantics.
- [x] The regression runs against the pinned controller patch/build path, not only a mocked OpenSandbox client.

## Out of scope

- Replacing OpenSandbox or redesigning its full status API.
- General workload-Pod lifecycle changes outside BatchSandbox ownership.
