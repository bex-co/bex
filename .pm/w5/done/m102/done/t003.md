## Objective

Make Leave race-safe and immediately visible: the delete and its last-admin/owner recheck happen inside the same `pg_advisory_xact_lock` transaction the other member writes use, and the caller's cached workspace resolution is evicted so the next request does not ride a stale positive.

## Context

- `PGStore.RemoveMember` (`lego/backend/internal/store/members.go:190`) already takes the workspace advisory lock, re-reads the row `FOR UPDATE`, and rechecks the last-admin count — reuse it rather than adding a parallel path, extending it with the owner recheck from `w5/m101/t002`.
- Cache: `tenantService.InvalidateTenant` (`lego/backend/internal/api/tenancy.go:413`) exists precisely for this, added after the w5/m13 finding that a self-delete blanked the workspace switcher for up to 30 s. `workspaces.Service.Delete` is the existing caller to copy.
- Positive membership entries are cached separately (`tenantService.IsMember`, `:384`) — check whether that cache also needs eviction for the workspace just left, and say so either way.

## Steps

1. Route Leave's write through the existing locked store path (adding a `subject`-is-caller variant only if the guard set genuinely differs).
2. Wire `InvalidateTenant` for the leaving subject.
3. Audit the `members` positive cache for a stale-access window after leaving; evict if one exists.
4. Add a concurrency test: two of three admins leaving simultaneously cannot land the workspace at zero admins.

## Acceptance criteria

- [ ] Leave's delete and its rechecks are in one locked transaction.
- [ ] After leaving, the caller's very next request no longer resolves to that workspace (no stale-TTL window).
- [ ] Concurrent leaves cannot drop a workspace below one admin.
- [ ] Any remaining cache window is documented if it is deliberately kept.
