# Sandbox verbs rewrite the workspace's tenant-key row on every call

Why: every sandbox read, lifecycle call, exec and file transfer pays a Postgres write (a new row version and its WAL) plus a fresh random key it then throws away, only to read a key that already exists.

- `store.PGStore.SandboxKeyForWorkspace` (`lego/backend/internal/store/sandboxtenants.go:54`) mints a candidate key, then runs `INSERT … ON CONFLICT (workspace_id) DO UPDATE SET workspace_id = EXCLUDED.workspace_id RETURNING api_key`. The no-op `DO UPDATE` is what makes the conflict arm return the stored key, but it still writes.
- Fix: read first (`SandboxKeyLookup` already exists), and fall back to the minting upsert only when no key is stored. The upsert keeps concurrent first mints collapsing to one key.
- Test: a Postgres test that a second call returns the same key without changing the row's `xmin`.
- Found by the efficiency review of w5/m115. The same review noted that `ownedSandbox` re-reads the sandbox the routing probe just read (`lego/backend/internal/sandbox/service.go:384`); that is worth fixing in the same pass if it's cheap.

## Outcome (2026-10-06)

Done.
1. `SandboxKeyForWorkspace` reads a stored key first, through the existing `SandboxKeyLookup` (an index lookup on `UNIQUE(workspace_id)`). It mints a key and runs the upsert only when none is stored, so concurrent first mints still collapse to one key through `ON CONFLICT … RETURNING`. The biggest beneficiary is the agent-session completer, which fetched every running session's key every 15s and so wrote one row version per session per tick.
2. `TestSandboxKeyMintIdempotentAndResolves` asserts a repeat call leaves the row's `xmin` unchanged. A mutant that always upserts fails it (`xmin 1180 → 1181`). Passes on real Postgres.
3. Not done: `ownedSandbox`'s re-read of the sandbox the routing probe just read. Only callers who belong to more than one workspace and name no owner pay it, as one in-cluster OpenSandbox read. Reusing the probe's read would also move the ownership check onto data read before the verb authorizes, rather than after. The reviews advised against it.
4. The same no-op upsert sits on a hot path in `OwnerIDForSubject`, which the Team page's 30s poll runs once per member. Filed as w5/104.
