# A finished kpack build still waits for a build slot

Why: since w5/108 the build caps skip a pass that only observes the App's own build, but that check finds this release's build Job, and a buildpack (kpack) build has no Job. A finished kpack build in a workspace whose other builds hold every slot is still parked as `BuildQueued` until a slot frees.

- `build.ObservingAppBuild` (`lego/operator/internal/build/build.go`) lists the App's build Jobs and kpack Images. It counts an active one, or this release's Job once it finished. A kpack build is one long-lived `kpack.io` Image per App (`build.KpackImage`), reused across releases, so it counts only while it is not terminal.
- So on the pass that finds a kpack build Ready, nothing counts. The caps apply, and with the workspace or cluster scope full, the built release waits `30s` at a time.
- The artifact itself is safe: w5/108 stores it on the success pass, so only that first pass is held.
- A possible fix: count the kpack Image as this release's dispatched build when its source revision is the release's. `checkKpackArtifact` already reads the Image's identity, so the revision check belongs beside it in `internal/build`.
- Test: a Ready kpack Image for the release, with every workspace slot held by other builds. The pass deploys the built image instead of reporting `BuildQueued`.
- Found by w5/108 (2026-10-07). kpack runs only for services that set `builder: buildpack`.

**Result (2026-10-07):**

- **The premise was half wrong.** The kpack Image is not one long-lived Image per App: `kpackImageName` hashes the App UID and the release revision, so each release gets its own Image, as each gets its own Job. The bug held anyway, because `ObservingAppBuild` counted an Image only while it was running.
- **Fix.** `build.ObservingAppBuild` takes the release revision. It derives the Job name from it, and counts the release's own finished kpack Image through `checkKpackArtifact`, the same check `ensureBuildpack` uses when it takes over that Image. So a pass that finds this release's Image Ready or Failed is no longer parked as `BuildQueued` while other builds hold every slot. `listKpackImages` keeps the no-kpack-CRDs tolerance (`missingKpack`) for both counters.
- **Tests.** `TestObservingAppBuild` gains five kpack cases: a running Image, the release's own built Image, the release's own failed Image, another release's finished Image, and a same-named App's running Image elsewhere. Three mutants fail them: active-only, any revision, and no UID filter.
- **Not added:** a controller-level kpack replay. No controller fixture drives a kpack build through `Reconcile`. The w5/108 Job-path controller test pins the shared call site, which would park the release if passed the wrong revision.
- **Checks:** `make test` (operator) and `make lint` pass.
- **Docs:** ADR060 no longer says a kpack Image is reused across releases, and w5/108's record carries the correction.
- **Follow-up:** w5/129. Every kpack release leaves its Image for the App's lifetime, so the build lists grow, and a ClusterBuilder update rebuilds them all.
