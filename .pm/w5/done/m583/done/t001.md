## Objective

Replace the codeless `core.WriteErrStatus` call in `GET /v1/metrics/bandwidth-sources` with a coded `core.NewBadRequestError("too_many_resources", …)` so clients receive `"code": "too_many_resources"` structurally in the JSON error envelope.

## Context

- `lego/backend/internal/metrics/bandwidth_sources.go:46-47` defines `maxBandwidthSourceResources = 30` with comment `(error code too_many_resources)`.
- `lego/backend/internal/metrics/bandwidth_sources.go:97-101` calls `core.WriteErrStatus(w, http.StatusBadRequest, fmt.Sprintf("too_many_resources: the breakdown supports at most %d resources", maxBandwidthSourceResources))`, which writes `{"error": ..., "message": ..., "id": ...}` with no `"code"` key.
- `withRenderErrorCodes` (`lego/backend/internal/api/render_openapi.go:997-1011`, `w8/411`) preserves `"too_many_resources"` because it is in the pinned `components.schemas.errorCode` enum.

## Steps

1. Define a constant for `too_many_resources` in `lego/backend/internal/metrics/` and replace `core.WriteErrStatus` at `bandwidth_sources.go:98-100` with `core.WriteErr(w, core.NewBadRequestError("too_many_resources", …))` (keeping a clear human message and `maxResources` param if helpful).
2. Check if GraphQL or MCP exposes bandwidth-sources and align the error code if they share the cap.
3. Add a composed-server test in `lego/backend/internal/api/` (e.g., alongside `render_error_codes_test.go` or `render_metrics_contract_test.go`) asserting `GET /v1/metrics/bandwidth-sources` with 31 resources returns HTTP 400 with `"code": "too_many_resources"`.
