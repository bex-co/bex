# A refused resource name carries a code on every surface

Why: an invalid service, Postgres or Key Value name answers a 400 with no `code`. Clients cannot branch on it, unlike every other naming refusal w5/m118 coded. The w4 QA loop69 live check found it through a Blueprint deploy.

- **Evidence:** `POST /v1/blueprints/deploy` with a Key Value named `Cache_1` answers 400 `{"error":"key-value \"Cache_1\": bad request: …","id":"bad_request"}` with no `code` (recorded in `blocked/m118/README.md`, live check 2026-10-06).
- **Cause:** `resourcename.CheckDatastore` (`lego/backend/internal/resourcename/resourcename.go`) refuses `!appv1alpha1.ValidResourceName(name)` with a plain `fmt.Errorf("%w: name %s", core.ErrBadRequest, core.ResourceNameRule)`; only the resource-id-shaped case is coded (`core.NameResourceIDReservedError`). The service create (`specFromCreate`), `NameAvailable` and rename paths do the same.
- **Fix:** one coded refusal beside `NameResourceIDReservedError` (for example `RESOURCE_NAME_INVALID`, params `field` and `maxLength`), used by every `ValidResourceName` check. The Blueprint wrap (`apps/deploy.go` `parseKeyValue`/`parseDatabase`) must keep the code, as GraphQL's sanitizer already does for a wrapped `CodedError`.
- **Test:** a table over service create, Postgres create, Key Value create and Blueprint deploy asserting the same code on REST, GraphQL and MCP.
- **Size:** about an hour.

## Done (2026-10-06)

- An invalid name now answers 400 `RESOURCE_NAME_INVALID`, with params `field` and `maxLength`, from one check, `core.CheckResourceName`. That check covers:
  - service create and the name-availability check;
  - Postgres and Key Value create, rename and recovery (through `resourcename.CheckDatastore`);
  - a Blueprint's service, database and Key Value declarations;
  - workspace create and rename.
- REST carries `code` and `params`, GraphQL its extensions, and MCP the `RESOURCE_NAME_INVALID:` text prefix. A Blueprint deploy keeps the code through the error that names the resource.
- Blueprint validation now places a coded refusal at the declared field its `field` param names. A Key Value named `Plan_Cache` used to be reported at its `plan`.
- The dashboard's database and Key Value rename hooks branch on the code instead of the message text.
- The internal tenant API (`store/api.go`, port 8091, operator scripts only) keeps its own `ErrInvalid`. Its errors never reach REST, GraphQL or MCP.
- Known nit, not fixed: on Render's Postgres `/recovery` route the request field is `restoreName`, but the refusal says `field: "name"`. `NAME_RESOURCE_ID_RESERVED` has had the same mismatch since w8/049.
- Tests and verification:
  - a REST, GraphQL and MCP table over service, Postgres and Key Value creates;
  - Blueprint REST deploy, MCP `deploy` and GraphQL validate, which also checks the located path;
  - the datastore name rule, the name-availability check, workspace create and rename, and the m118 Blueprint test with `Plan_Cache`;
  - dashboard hook tests in both directions;
  - every mutant killed;
  - backend suite, `make lint-backend`, dashboard `yarn lint` and `yarn test` (4342 tests) all green.
