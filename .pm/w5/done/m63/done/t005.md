## Objective

Set `configuration.data.encryption: AES256` and `configuration.wal.encryption: AES256` on all three Barman Cloud plugin `ObjectStore` CRs, per ADR050 §2 Tier B.

## Context

- `deploy/gitops/charts/barman-cloud-objectstores/{bex-db,tenant-postgres,auth-dbs}.yaml`.
- Plugin CRD support confirmed at `deploy/gitops/charts/barman-cloud-plugin/upstream/manifest-0.13.0.yaml:153-162,367-376` — enum `AES256 | aws:kms`.
- This is explicitly weaker than Tier A (SSE decrypts transparently on any authenticated `GetObject`) — §3/t006-t007 is what actually protects Tier B's confidentiality against a leaked credential. Do not present this task as closing the confidentiality gap on its own.
- Confirm Wasabi accepts the `AES256` SSE header before relying on it (its S3 API docs / a manual `PutObject` with the header, checked against a test bucket) — flag in this task's notes if it doesn't, since the ADR assumed it would.

## Steps

1. Add `configuration.data.encryption: AES256` and `configuration.wal.encryption: AES256` to `bex-db.yaml`.
2. Same two fields in `tenant-postgres.yaml` (object store `default/bex-tenant-postgres`).
3. Same two fields in `auth-dbs.yaml`.
4. Sync via Argo, trigger an on-demand `Backup` for one cluster, and confirm the uploaded object carries `x-amz-server-side-encryption: AES256` (`aws s3api head-object`).

## Files

- `deploy/gitops/charts/barman-cloud-objectstores/bex-db.yaml`
- `deploy/gitops/charts/barman-cloud-objectstores/tenant-postgres.yaml`
- `deploy/gitops/charts/barman-cloud-objectstores/auth-dbs.yaml`

## Acceptance criteria

- [ ] All three `ObjectStore` CRs show `encryption: AES256` under both `data` and `wal`.
- [ ] A fresh on-demand backup for at least one cluster per ObjectStore shows the SSE header on its uploaded object(s).
- [ ] No existing backup/restore/PITR drill regresses (re-run the relevant `scripts/restore-postgres.sh` `DRY_RUN=1` path).

## Out of scope

- Write-only credential scoping for these three ObjectStores (t006/t007) — this task alone does not close the credential-leak threat model; say so explicitly wherever this is reported as done.
- SSE-C / customer-managed keys (ADR050 Follow-ups, upstream plugin limitation).
