## Objective

Build the two-policy-per-store IAM shape ADR050 §3 specifies, mirroring the static-site reader/publisher precedent, as reusable templates plus one provisioning script for all five backup stores.

## Context

- Precedent: `infra/wasabi/static-s3-publish-policy.json`, `infra/wasabi/static-s3-read-policy.json`, `scripts/static-s3-credentials.sh` (`provision` / `verify` / `revoke-legacy` subcommands, idempotent, never prints secret values, uses a pinned `amazon/aws-cli` Docker image against Wasabi's IAM-compatible API).
- Five stores to parameterize over: `etcd` (`s3://bex-tfstate/etcd-snapshots`), `openbao` (`openbao-snapshots`), `bex-kv` (`keyvalue`), `bex-db` (`bex-db`), `auth-dbs` (`auth-dbs`) — plus `tenant-postgres` (`postgres`) if it's meant to get its own writer/reader pair distinct from `bex-db`'s (check ADR031's table: `default/bex-tenant-postgres` currently shares credential naming with `bex-db-backup-s3`; decide during implementation whether tenant-postgres needs its own identity or can share `bex-db`'s, and record the decision in the script's header comment).
- `docs/ADR050-encrypted-platform-backups.md` §3's permission table: writer = `PutObject`+`DeleteObject`+`ListBucket`, no `GetObject`; reader = `GetObject`+`ListBucket` only.

## Steps

1. Write `infra/wasabi/backup-writer-policy.json` and `infra/wasabi/backup-reader-policy.json` as parameterized templates (placeholder bucket/prefix, substituted by the script — same approach `static-s3-*-policy.json` uses for `bex-static`).
2. Write `scripts/backup-s3-credentials.sh` with `provision` (idempotent: create missing IAM users/keys per store, apply the two policies scoped to that store's prefix, install the writer Secret in-cluster, leave the reader credential un-installed/printed only into `.env`-style output the operator captures out of band), `verify` (positive/negative access matrix: writer denied `GetObject`, reader denied `PutObject`, using a random probe object), and `revoke-legacy` (refuses until `verify` passes and no live Secret still references the shared `TF_STATE_*` root credential).
3. Follow `static-s3-credentials.sh`'s conventions exactly: secret values never touch argv/stdout/git, pinned `amazon/aws-cli` image, sourced from `.env` for the root bootstrap credential used only to create the new scoped IAM users.

## Files

- `infra/wasabi/backup-writer-policy.json`
- `infra/wasabi/backup-reader-policy.json`
- `scripts/backup-s3-credentials.sh`

## Acceptance criteria

- [ ] `scripts/backup-s3-credentials.sh provision` is idempotent (a second run changes nothing) and creates one writer + one reader IAM identity per store, each scoped to that store's own prefix only.
- [ ] `scripts/backup-s3-credentials.sh verify` proves the writer cannot `GetObject` and the reader cannot `PutObject`, against a real Wasabi probe object, and exits non-zero on any deviation.
- [ ] No secret value appears in script output, `kubectl` argv, or git.
- [ ] The tenant-postgres-vs-bex-db credential-sharing decision from Context is recorded in the script's header comment.

## Out of scope

- Actually swapping the five backup Secrets to the new writer credentials (t007).
- `revoke-legacy`'s actual invocation against production (that's a t007/t010-adjacent live step, not this task).
