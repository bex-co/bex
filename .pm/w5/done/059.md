# w5/059 — Workspace settings: the Name field keeps the previous workspace's name after a switch

Observed live on `dev-5` during the `w5/m102` closeout walk (2026-09-17), incidental to that milestone and **not caused by it**.

## What happens

On `/workspace/settings`, switching workspaces with the sidebar switcher updates everything in the General card **except the Name input**, which keeps showing the previously selected workspace's name:

| Field        | After switching to `tea-dalov79jg4r9du1omc20` |
| ------------ | --------------------------------------------- |
| Name (input) | `tea-dalov21jg4r9du1omc00` ← stale            |
| Plan         | `Hobby` ← correct (was `Pro`)                 |
| Workspace ID | `tea-dalov79jg4r9du1omc20` ← correct          |
| Created      | correct                                       |

Reproduced twice in the same session (switching to the personal workspace, and again to `m102-shared`, whose ID rendered as `tea-dalpkt1jg4r0s26thrp0` while the Name input still read `tea-dalov21jg4r9du1omc00`).

## Why it matters

The Name field is an editable input with a live **Save** button next to it. Pressing Save while it is stale would rename the newly-selected workspace to the *previous* workspace's name — a silent wrong-target write, the same class of bug as the pre-w6/m14 "Team page manages the wrong workspace" defect. The read-only fields being correct makes it worse: the card looks coherent.

## Likely cause

`WorkspaceDetailsCard` (`dashboard/src/features/workspaces/components/workspace-details-card.tsx`) seeds the input's state from `workspace.name` on mount. The component is not remounted on a switch (same route, changed prop), so the `useState` initializer never re-runs. The read-only rows render straight from the prop, which is why only the input drifts.

Check the same pattern in the other edit-in-place cards that seed state from a prop on a route that swaps the underlying resource without remounting.

## Suggested fix

Either key the card on `workspace.id` so a switch remounts it, or sync the input when the workspace id changes (and only when the field is not dirty, so an in-progress edit is not clobbered). A test should switch the workspace prop and assert the input follows.

## Evidence

- `.playwright-mcp/` captures from the m102 walk (`m102-owner-disabled`, `m102-leave-confirm`) show the mismatch between the Name input and the Workspace ID row.
- Not in scope for `w5/m102` (leave workspace), which is why it is filed rather than fixed there.

## Resolution (2026-09-17) — DONE

Fixed in `WorkspaceDetailsCard`: the draft name re-seeds when the card is pointed at a **different** workspace id, using the render-phase state-reset pattern (`seededFor !== workspace.id`) rather than an effect, so there is no flash of the stale value.

Keyed on the **id, not the name**, deliberately: the rename flow refetches on success and re-renders this card with the same workspace, and a name-keyed reset would wipe an in-progress edit. Both behaviors are covered — `re-seeds the name input when pointed at a different workspace` and `does not clobber an in-progress edit of the same workspace` — and the first fails without the fix (mutation-checked).

Dashboard typecheck + lint + 3,499 tests green.

**Scope note:** the "check the same pattern in other edit-in-place cards" suggestion above was **not** swept. This note's own defect is fixed; a systematic audit of prop-seeded drafts across the settings surfaces is a separate piece of work and was not performed here.
