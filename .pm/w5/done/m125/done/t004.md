## Objective

Scaling's utilization chart and the Metrics tab choose their empty state with one function, and a sleeping service is never labeled limitless.

## Context

- `dashboard/src/features/services/components/scaling-recent-metrics.tsx` repeats the Metrics tab's no-data / no-limit / unavailable logic; w4/192 was exactly that copy drifting.
- It makes four extra queries (the absolutes and both `*_limit`) only to choose its empty text. "No limit configured" still reads the current pod, so a sleeping service whose percentages didn't survive is called limitless.

## Steps

1. Extract `utilizationEmptyReason()` and use it in both views.
2. Drop the extra queries if the reason can come from the percentage read.
3. Fix the sleeping case.

## Files

- dashboard/src/features/services/components/scaling-recent-metrics.tsx
- The Metrics tab component

## Acceptance criteria

- [ ] A sleeping service never shows "No limit configured", both views share the function, and the scaling test asserts the chart renders (`role="img"`).

## Out of scope

- Work owned by other w5 items in the 2026-10-05 queue.

## Outcome (2026-10-06)

- `utilizationEmptyReason()` (`dashboard/src/features/metrics/lib/utilization.ts`) decides both views' empty state.
- Step 2: the extra reads stay. The percentage read alone cannot tell no usage (absolute read empty) from a lost limit history, nor a limitless service (limit read empty).
- Step 3: "awake" is `runsInstances(service)`: not suspended and phase not Hibernated, from the service both routes already load. The `instance_count` series cannot say it: bex-api's Prometheus `count(...)` returns no point while zero pods run, so its last point is the count from before the service slept.
- Tests: a literal reason table, the sleeping case in both components and both routes, and `role="img"` chart assertions. All 9 mutants (each input of the reason, both halves of `runsInstances`, each route and component ignoring `awake`) fail a test.
