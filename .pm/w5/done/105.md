# Two new services in one Blueprint can declare the same host

Why: a manifest whose two new services both declare `shop.example.com` validates and previews clean, then the apply creates the first and refuses the second, leaving the Blueprint half-applied.

- Each service's host checks (`validateBlueprintServices` → `previewBlueprintHosts`, and w5/m126's `planNewApp` in preview) compare its hosts with existing services' claims, never with the other services the same manifest declares.
- The apply meets the conflict only at the second service's claim write, after the first service exists.
- Fix: a cross-resource check in the compiler's semantic validation (or `validateBlueprintServices`) that refuses a host two declarations share, located at the second declaration's `domains[i]`. It needs no List, and it runs before any write.
- Test: validate and apply both refuse a two-service manifest sharing a host, with the same message, and the apply creates nothing.
- Found by the efficiency review of w5/m126.

**Result (2026-10-07):**

- **The check.** The compiler's `NormalizeBlueprintIR` runs `blueprintDuplicateHostProblems` after its duplicate-name check. A host that two services declare is refused as `BLUEPRINT_DUPLICATE_HOST` at the second declaration's `domains[i]` (or `domain`), citing the first. So is a host whose www or apex sibling another service declares, because a claim reserves its sibling too (`hostClaims.claimedElsewhere`).
- **What still passes.**
  - One service may list its own apex and www.
  - A `domain` beside a non-empty `domains` claims nothing, because `parseService` reads `domain` only when `domains` is empty.
- **Where it applies.** Validate, preview, sync and apply all compile the manifest, so the refusal comes before any write. An apply no longer creates the first service and then refuses the second.
- **Tests.**
  - `TestBlueprintRefusesAHostTwoServicesShare` covers four refusals: the same host spelled differently, an apex and its www, a host its first claimant lists beside its sibling, and the singular `domain`. Each pins the problem's path and the pointer it cites. Each also checks that the apply returns the same message and leaves no Apps.
  - The test service verifies domain ownership. Without the check, its apply creates the first App, so that assertion catches the half-applied Blueprint.
  - Two cases must be allowed, and are: a service's own apex and www, and a `domain` beside `domains`.
  - Six mutants fail it: no call, no sibling lookup, no own-service exemption, no normalization, always reading `domain`, and never reading `domain`.
- **Doc.** ADR005 now has a paragraph next to the `domains.host` uniqueness rule.
- **Accepted consequence.** A Blueprint stored before this change with such a manifest no longer compiles, so its detail page lists no resources until the manifest is fixed. Every tightened compile rule has that effect. The next sync names the host, and the durable claims keep the resources owned in the meantime.
