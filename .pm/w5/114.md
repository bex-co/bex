# Blueprint ownership checks query one resource at a time, and an apply lists datastores twice

Why: every Blueprint read and apply pays one Postgres round trip per declared resource for ownership, and an apply lists the workspace's datastores twice. The dashboard polls a Blueprint's detail, so the read side runs continuously while the page is open.

- **One owner query per resource.**
  - `blueprintOwnershipConflicts` (`lego/backend/internal/apps/blueprint_ownership.go`, its `ownerOf`) calls `GetBlueprintResourceOwner` once per declared service, Postgres and Key Value on every apply preflight and validate.
  - `resourceOwnedByBlueprint` (`apps/blueprint.go`) does the same for every resource on each Blueprint read, which `use-blueprint.ts` polls at `RESOURCE_POLL_INTERVAL_MS`.
  - Fix: one store read of the workspace's claims into a `kind/name → owner` map, keeping the CR-label fallback.
- **Datastores listed twice per apply.** `blueprintOwnershipConflicts` lists the workspace's Databases and Key Values, then `deployParsedStack` lists them again through `stackDatastoreSnapshots` (`apps/deploy.go`). bex-api's Kubernetes client is uncached, so each list is an API-server round trip returning every datastore in the workspace.
  - Fix: take the snapshots once, before the preflight, which writes nothing, and pass them in.
- **Test:** an apply and a Blueprint read each make one claims query, counted by a fake store, and the apply lists each datastore kind once.
- Found by w5/098's efficiency review (2026-10-07). Both costs date from w8/m40.
