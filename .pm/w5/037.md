# Object Lock / WORM retention on bex-tfstate backup prefixes (ADR050 follow-up)

ADR050 §3's write-only per-store credentials stop a leaked backup credential from *reading* backups, but a `<store>-backup-writer` identity still holds `PutObject`/`DeleteObject` on its prefix (the retention prune needs delete). So a compromised writer credential could still overwrite or delete existing backups — an integrity/availability risk distinct from ADR050's confidentiality scope.

Mitigation: enable S3 Object Lock / WORM retention (or a versioning + MFA-delete equivalent, per what Wasabi supports) on the relevant `bex-tfstate` backup prefixes so existing objects cannot be overwritten or deleted within the retention window even with the writer credential. Reconcile with the Jobs' own rolling-N prune (Object Lock retention must be ≥ the keep window, or the prune must move to lifecycle rules).

Scope: `infra/` / bucket-side configuration, out-of-band (bex-tfstate is the manually-created "bottom turtle"). Verify a drill where a writer credential is denied an overwrite/delete of a locked object.
