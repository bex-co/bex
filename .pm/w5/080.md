# The Blueprint compiler refuses `dockerCommand` on `runtime: image`

Why: REST, MCP and GraphQL can set an image service's command (`dockerCommand` becomes the start command; w4/188, w5/073), but a `render.yaml` image service with `dockerCommand` is refused. So the same service can't be declared as a Blueprint.

Source: found in w5/073's `/simplify` review, 2026-10-05.

## Where

- `lego/backend/internal/apps/deploy.go:2343` (`manifestStartAndAutoDeploy`): `dockerCommand requires runtime: docker`.
- `lego/backend/internal/apps/blueprint_compiler.go:298-301` repeats the docker-only rule.
- Render's Blueprint spec defines `dockerCommand` as "the command to run when starting the Docker-based service" but documents it under "Building from a Dockerfile". So whether Render accepts it with `runtime: image` is unverified.

## Fix (~45m)

1. Research Render's behavior first: does a `render.yaml` with `runtime: image` plus `dockerCommand` validate and apply on Render? If Render refuses it, close this note as matching Render and record that in ADR049.
2. If Render accepts it: map `dockerCommand` to the start command for `runtime: image` in both compiler paths, and keep the both-spellings refusal.
3. Generate Blueprint should then export an image service's command as `dockerCommand`.
4. Tests: a Blueprint image service with `dockerCommand` stores `spec.startCommand`; the generate → parse round-trip keeps it.

Done: a `render.yaml` image service can declare its command the same way the API can, or the divergence is recorded as matching Render.
