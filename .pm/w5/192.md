# 192 — Confirm whether Zot's dedupe links a blob another repository holds when an import checks for it, and close it if so

Why: an attacker-controlled source registry can serve a manifest naming a layer digest it does not have. If the sandbox registry answers the importer's existence check for that digest from its global dedupe store (Zot runs with `Dedupe: true`), `remote.Write` skips the upload and the attacker's imported image then holds another workspace's private layer, readable from their sandbox.

- **Source:** w5/m383 /simplify review (2026-11-13), carrying the "Zot dedupe" item of w5/189. m383 closed the same-host cross-repo mount (a source on the registry's own host is refused) but not this.
- **Check:** run Zot v2.1.22 locally with the deployed config (`deploy/gitops/base/zot.yaml`, `lego/operator/.../zotconfig.go`), push a blob into repository A, then `HEAD /v2/B/blobs/<digest>` as the importer: does it answer 200 and link the blob into B?
- **Fix if it does:** make the importer prove the source serves every layer before writing (read each layer through go-containerregistry's verifying reader, or upload unconditionally), or turn off Zot's cross-repository dedupe linking for the snapshot prefix.
- **Size:** ~1h with the local Zot check and a test.
