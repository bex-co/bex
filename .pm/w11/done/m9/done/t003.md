## Objective

Resolve the signed-in person's display name/email for the drawer through bex-api's existing Render-compatible current-user endpoint, with bounded authenticated networking and no persistent profile cache.

## Context

- `GET /v1/users` is the backend's intentional REST-only "who am I" endpoint and returns `{name,email}` for a user-consented OAuth subject via the existing Kratos identity lookup.
- Mobile's OAuth scopes are deliberately only `openid offline_access`; adding `profile`/`email` scopes would change the reviewed auth contract and is unnecessary.
- `authManager.getAccessToken()` handles freshness; `features/logs/rest-transport.ts` is the existing pattern for bounded Bearer REST calls and testable credential injection.
- Name/email are personal data: keep only current in-memory UI state, never AsyncStorage/SecureStore/analytics/logs/crash output.

## Steps

1. Add a small typed current-user REST client with injected credentials/fetch, HTTPS-configured origin, timeout/abort, exact response validation, and normalized `{name,email}` output.
2. Add a focused hook/provider state for loading, ready, unavailable, offline, and retry without automatic unbounded retries.
3. Reset/abort the status read at the identity boundary and ensure late responses from a signed-out/replaced session cannot render.
4. Use honest name/email fallbacks (for example, email-only or translated "Signed in") without showing the raw OAuth subject as a friendly identity.

## Acceptance criteria

- [ ] A signed-in OAuth caller sees the validated name/email returned by `GET /v1/users`; email-only and empty honest-subset responses render safely.
- [ ] The request is bounded, authenticated via `authManager`, abortable, and never persists or logs name/email/tokens.
- [ ] Sign-out or identity replacement makes every in-flight old-user response unrenderable.
- [ ] Offline/unavailable profile status is distinct from "no name" and offers an explicit retry without blocking workspace/resource supervision.

## Out of scope

- Adding OAuth `profile`/`email` scopes, querying Kratos directly, adding a GraphQL/MCP current-user twin, or building mobile profile editing/settings.
