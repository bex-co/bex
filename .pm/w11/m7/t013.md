## Objective

Use Expo MCP to view, interact with, and polish the shipped mobile agent-session experience on representative phone viewports before tests and closeout claim the UI is complete.

## Context

- This is an interactive visual and behavior gate, not a snapshot or code-review exercise.
- Exercise the real native render tree and controls. Unit tests, static bundle output, and dashboard behavior do not prove mobile layout quality.
- If Expo MCP cannot run the app or reach a required state, this task remains open with the exact missing setup recorded; do not substitute indirect evidence.

## Steps

1. Launch/reload the app through Expo MCP, authenticate with an approved test identity, and navigate the affected list/detail/deep-link routes.
2. View and interact with first attach, history replay, live streaming, large plan/diff/tool/terminal parts, composer submit, pending/failed turn, needs-decision, background/foreground resume, completion, and phase-1 fallback states.
3. Repeat at representative compact and large phone sizes in light and dark themes, including the on-screen keyboard, safe areas, scrolling, text scaling/truncation, touch targets, and English/Chinese content.
4. Fix every material visual, accessibility, or interaction defect found; rerun the Expo MCP walkthrough until clean and record the viewed routes/states and final evidence in this task before marking it done.

## Acceptance criteria

- [ ] Expo MCP has interactively rendered and exercised every affected agent-session flow and state; the evidence names the viewed routes, device sizes, themes, and locales.
- [ ] Conversation rows remain readable and stable during streaming, expansion, long output, and unknown parts with no overlap, clipping, unsafe-area loss, or unintended scroll jumps.
- [ ] Composer and decision controls remain visible and operable with the keyboard open; loading, offline, reconnecting, error, disabled, and fallback states are visually distinct and actionable.
- [ ] Light/dark themes, compact/large phones, text scaling, touch targets, and English/Chinese copy were viewed; material defects were fixed and the polished result was re-viewed through Expo MCP.
- [ ] No screenshot, snapshot, static export, or code inspection is presented as a substitute for the Expo MCP pass.

### Expo MCP live create → run → PR pass (2026-08-16, real prod)

An authorized Expo MCP pass on the signed-in iPhone 17 Pro (iOS 26.5, 402×874 pt)
drove the real create path against prod `api.bex.co` and uncovered a genuine
create-blocking defect plus a backend blocker.

- **Create was failing for every submit.** Submitting the composer surfaced only
  the generic "Couldn't create the session." overlay. Instrumenting the mutation
  caught the real backend error: `branch must start with bex-agent/`
  (`AGENT_SESSION_INPUT_INVALID`). The composer collected the repo's **base**
  branch (`main`) and sent it as the create mutation's `branch`, but that field
  is the agent **work** branch and the backend rejects anything outside the
  mandated `bex-agent/` namespace (ADR047 push confinement). The mobile client
  had therefore never been able to create a session.
- **Fix.** `composer/compose.ts` now resolves a valid work branch exactly like
  the dashboard consumer: an empty branch derives `bex-agent/<slug(prompt)>`, an
  in-namespace override is kept verbatim, and any other entry (e.g. `main`) is
  slugged into the namespace — a phone entry can no longer produce the rejection.
  The repo picker no longer pre-fills the misleading base branch, and the branch
  chip placeholder now shows the honest derived `bex-agent/…` name. (This
  supersedes the earlier "fills its default branch" evidence above, which was
  built against the wrong branch contract.) `canSubmit` no longer requires a
  typed branch because the prompt drives the default. Targeted tests updated.
- **Verified live via Expo MCP.** After the fix, two real sessions were created
  from the composer and both returned "Session assigned." — `bex-agent/main` on
  `bex-co/bex`, and `bex-agent/add-a-single-one-line-comment-…` on
  `bex-co/web-beancount` (branch correctly derived from the prompt). The second
  reached the `running` phase with a live sandbox, confirming the mobile
  create → provision → running path end to end.
- **Also viewed on real data:** the Sessions list with mixed Running/Failed/
  Canceled/Completed phases and the `#52` PR number; the completed-session detail
  with the "Pull request #52 / Open in GitHub" card; the running-session detail
  with the live-unavailable fallback banner, the Follow-up steer composer, and the
  uncertain-turn recovery notice. The failed-session detail now surfaces the
  descriptive lifecycle status ("Sandbox create failed") instead of the opaque
  generic fallback (`detail/failure-reason.ts` `failureStatusText`).
- **Backend blocker (out of mobile scope), recorded not fixed.** A fresh
  end-to-end run to a draft PR could not be completed: the deployed agent driver
  currently crashes on startup inside the sandbox with
  `Internal error: API Error: Unexpected token … is not valid JSON (code -32603)`.
  Both the pre-existing running session and the new one hit the identical error
  and stalled in `running` with a live sandbox but zero transcript rows and no
  progress — the documented "known crash-path gap" (see the
  `agent-session-verify-harness` note). This affects every client (dashboard
  included), not the mobile code, and the mobile UI correctly degrades to the
  phase-1 fallback while it persists. The single `bex-sandbox` node was also at
  capacity (one stranded sandbox blocks all new creates with "sandbox create
  failed"); freeing it let the mobile create provision immediately.
- **Text-entry limitation of the harness.** The bundled Expo MCP XCTest driver
  exposes only tap/screenshot/find (no type or scroll), and macOS Accessibility
  blocks AppleScript keystrokes, so an unseeded fresh prompt cannot be typed
  through automation. The live create above used a temporarily seeded initial
  prompt (reverted) to work around this; below-fold controls (e.g. Cancel) could
  not be reached by scrolling.

Gate after this pass is green: full `yarn test`, `git diff --check`, and fresh
iOS plus Android Expo exports. The mobile create defect is fixed and verified
live.

### Backend `-32603` root cause + full create→PR verified (2026-08-17)

The run→PR blocker was root-caused: the ADR062 gateway **model proxy** forwarded
the agent SDK's `Accept-Encoding: gzip` to the vendor (so Go's Transport returned
the raw gzip body) but `copyResponseHeaders` **dropped `Content-Encoding`**,
shipping gzip labeled as plain JSON — the in-sandbox ACP agent JSON-parsed the
gzip magic and every turn died with `Unexpected token '\x1f' … -32603`. A
secondary bug wrote that binary error into Postgres (`invalid byte sequence
0x00`), stranding the session in `running`. The identical fix was already merged
upstream (`e9dff2ec` relay Content-Encoding + `4295ff79` stop losing the reason)
and, once its platform image rolled to prod (gateway digest
`…83e10605` → `…261b2531`), the **full workflow was verified live via Expo MCP**:
a mobile-created session on `bex-co/web-beancount` went
`creating → running → completed` in ~3 min and opened draft **PR #1701**, with
the mobile detail rendering Completed + the PR card. No `-32603`. This is a
backend/deploy fix, not a mobile change; the mobile slice (create, list, detail,
steer composer, uncertain-turn recovery, live-unavailable fallback, PR display)
is verified against real prod data. Physical push and background/foreground
live-stream recovery remain owned by the m5/m6 push gate and a live-attach pass.
