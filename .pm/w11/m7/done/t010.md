## Objective

Make the shipped conversation endpoint safe for mobile and repeated multi-client resume by separating read/turn tickets, exposing a durable replay cursor, and keeping transcript sequence allocation monotonic across sandbox reconnect, hibernation, and redispatch.

## Context

- The gateway rejects a `read` ticket on POST and a `turn` ticket on GET, while the dashboard transport currently mints one generic/default ticket for both request types.
- GET currently begins durable replay at sequence `-1`; client-side duplicate collapsing is not a resume protocol.
- The gateway live splice numbers a driver's stream from zero while the transcript primary key is session-global; redispatch behavior needs a pinned conformance test and correction if it collides.

## Steps

1. Add action-specific ticket preparation to the dashboard/reference transport, define and implement an authenticated `afterSeq`/cursor resume contract, allocate or translate live sequences in the session-global space, and document the external AI SDK client contract.

## Acceptance criteria

- [ ] Each GET connection mints/accepts only a one-time `read` ticket and each POST only a one-time `turn` ticket across REST/GraphQL/MCP and the dashboard reference client.
- [ ] Reconnect after an acknowledged cursor sends only later parts, with an explicit full-history path for first attach.
- [ ] Transcript sequences remain monotonic and collision-free across reconnect, hibernation/rehydration, and redispatch; a test fails with sandbox-local sequence reuse.
- [ ] Ticket, cursor, and transcript limits remain fail-closed and bounded.

## Out of scope

- Persisting user prompts and turn status (t011).
- Mobile UI implementation.
