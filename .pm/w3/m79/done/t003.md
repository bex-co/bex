## Objective

Run an in-cluster OpenSandbox server in **kubernetes runtime**, in **multi-tenant** mode so sandbox pods land in the `<ws>-sandbox` namespace the gateway derives.

## Context

- Multi-tenant mode is flipped by a `[tenants]` block (`deploy/opensandbox/sandbox-cluster.toml:84`) whose `endpoint` bex-api serves at `GET /v1/sandbox-tenants` on `BEX_CP_ADDR` (`internal/store/api.go:139,548`), returning `{"namespace": "<ws>-sandbox"}` (`store/namespaces.go:86`). bex-api stamps the per-workspace `OPEN-SANDBOX-API-KEY` (`internal/sandbox/client.go:34`), wired when the store is on (`cmd/api/main.go:1056`).
- Single-tenant/insecure mode lands pods in one fixed namespace (`opensandbox`), which the gateway's derived `<ws>-sandbox` won't match — so multi-tenant is required.
- Omit the `[secure_runtime]` block locally (no gVisor). Point `batchsandbox_template_file` at t002's relaxed template.
- The host server uses the CAPD admin kubeconfig, so it needs no per-namespace RBAC; the `<ws>-sandbox` namespace is created by bex-api's `NamespaceReconciler` (`store/namespaces.go:150-155`).

## Steps

1. Render a local multi-tenant k8s TOML: `[runtime] type=kubernetes`, `[kubernetes] kubeconfig_path=<CAPD kubeconfig>`, `batchsandbox_template_file=<relaxed>`, `[tenants] provider=http`, `endpoint=http://<host>:<BEX_CP_PORT>/v1/sandbox-tenants` (+ `Bearer <BEX_CP_TOKEN>` or rely on `BEX_CP_INSECURE=1`). No `OPENSANDBOX_INSECURE_SERVER`.
2. Start `uvx --from opensandbox-server==0.2.2 opensandbox-server --config <rendered.toml>` under the dev-env pid/log supervision; health-check.
3. Expose `BEX_OPENSANDBOX_URL` for bex-api.

## Completion note

The planned host process could create workloads but could not reach their pod IPs under CAPD. The shipped server is therefore an in-cluster Deployment using a ServiceAccount; its tenant callback reaches the host bex-api through t006's `kube-system` bridge. Live create and agent-session runs both landed in the correct `<ws>-sandbox` namespace.
