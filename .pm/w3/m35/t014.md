## Objective

Prevent a compromised OpenSandbox server/controller from using its legitimate tenant-namespace Pod/Job mutation authority to create an ordinary runc Pod that bypasses gVisor, sandbox placement, identity labels, or ServiceAccount-token suppression.

## Context

- The checked-in BatchSandbox template requests gVisor but is trusted application input, not an API-server authorization boundary.
- The controller must create Pods/Jobs in each `<ws>-sandbox`; namespace-scoped RBAC contains where it can write but not what Pod shape it can submit.
- Namespace default-deny contains network reachability but does not restore the missing host/kernel boundary.

## Steps

1. Add a fail-closed ValidatingAdmissionPolicy selected by the trusted sandbox namespace regime label.
2. Require every sandbox Pod to retain the sandbox regime label, `runtimeClassName: gvisor`, scheduler-enforced sandbox-node placement (no create-time `nodeName` bypass), and `automountServiceAccountToken: false`.
3. Add static guards and impersonated controller dry-runs that deny runc and admit the exact gVisor shape.

## Acceptance criteria

- [ ] A server/controller identity authorized to create Pods in `<ws>-sandbox` is denied when it omits gVisor, bypasses sandbox placement, omits regime identity, or enables token mounting.
- [ ] The exact production BatchSandbox Pod shape still passes admission and reaches Running under gVisor.
- [ ] CI fails if the policy/binding, fail-closed mode, sync ordering, or any required Pod invariant drifts.

## Out of scope

- Claiming gVisor is a microVM; a future hardware-isolated tier still requires KVM-capable nodes and Kata/Firecracker.
