## Objective

Make the reviewed security state reproducible from Git: Argo owns the lifecycle server, config, RuntimeClass, RBAC, and policies, and every OpenSandbox component version is deliberately pinned.

## Context

- m32 recorded that the server Deployment and tenant-config Secret were manually applied rather than GitOps-durable.
- `server.Dockerfile` defaults to an unpinned PyPI version and the Deployment references an internal `:latest` tag.
- The checked-in BatchSandbox template does not fully encode the live gVisor placement/hardening described by ADR042.

## Steps

1. Add the server/config/RuntimeClass/policy resources to the correct GitOps application with secret material represented through the repository's sealed/out-of-band pattern.
2. Pin server, execd, and any retained egress image by reviewed version/digest; remove mutable `latest` behavior.
3. Ensure the checked-in BatchSandbox template carries gVisor placement, token, security-context, and identity labels required by t002-t006.
4. Serialize digest write-back and refuse to attach images built from an older production input tree to newer manifests.

## Files

- `deploy/opensandbox/`
- `deploy/gitops/base/`
- `deploy/gitops/overlays/prod/`
- `.github/workflows/deploy.yml`
- `scripts/gitops-validate.sh`

## Acceptance criteria

- [ ] A from-scratch GitOps render contains the same hardened resources and immutable images validated live.
- [ ] Argo reports no unmanaged/manual OpenSandbox security resource drift.
- [ ] Rebuilding the server image resolves a fixed OpenSandbox version rather than the newest package at build time.
- [ ] Digest write-back validates every digest and fails instead of deploying a stale, missing, or all-zero reference.

## Out of scope

- OpenSandbox pause/resume snapshot redesign.
