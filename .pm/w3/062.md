# Terminated and errored sandboxes stay readable, as on Render

Why: Render keeps a terminated or errored sandbox readable (`status`, `terminatedAt`) and answers a connect-token mint for it with 409, which the v2.36 CLI turns into "sandbox … was terminated at …"; bex forgets the sandbox the moment it ends, so every read answers 404 and the explanation never shows.

- **Evidence (production, 2026-11-10, `bex-canary`, QA account):** `POST /v1/sandboxes` → 201 `sbx-dbpfd5lme2kc73f2l15g`; `POST …/terminate` → 204; then `GET /v1/sandboxes/sbx-dbpfd5lme2kc73f2l15g` and `POST …/runs/stream/token` both answer `404 SANDBOX_NOT_FOUND`.
- **Render:** the pinned OpenAPI `sandbox` object carries `status` (enum includes `terminated`, `errored`) and `terminatedAt`; both connect-token operations document a `409`. CLI v2.36 `pkg/sandbox/repo.go` `explainConflict` reads exactly those on a 409.
- **bex today:** OpenSandbox deletes the pod on terminate and bex keeps no sandbox record with an end time (`lego/backend/internal/store/sandbox_*.go`: meter, activity, names, executions — no tombstone), so `ownedSandbox` reports not-found.
- **Likely shape:** a durable sandbox record written at create and closed at terminate/reap (status + `terminatedAt`), read by GET/list (`status=terminated` filter) and by the token mints (409 for an ended sandbox); a retention window to match Render's (verify how long Render lists an ended sandbox before choosing). REST, GraphQL `sandboxes`/`sandbox`, MCP `list_sandboxes` share the service path. Execution history (`/execs`, w32/m298) of an ended sandbox should then stay readable too.
- **Size:** more than an hour (store migration + service + three surfaces + reconcile path) — promote to a milestone.
- Source: w3/m303 t004 (2026-11-10), found while checking what the v2.36 CLI reads on an ended sandbox. ADR018 records the divergence pending this item.
