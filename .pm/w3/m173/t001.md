## Objective

Produce a complete, names-only map of which workflow job reads which secret, which environment (if any) that job runs under, and whether each secret is production-class, so t002 can decide the gate shape from evidence and t003/t005 can move secrets without breaking a workflow.

## Context

- 37 repository-scope secrets (names in the milestone README Evidence); environment secrets only `BEX_ONBEX_TLS_CERT`/`_KEY` (`production-deploy`) and `EXPO_TOKEN` (`production-release`).
- Workflow trees: `.github/workflows/` and `lego/operator/.github/workflows/`.
- Jobs with an `environment:` today: `app-cluster.yml:58`, `cli-release.yml:46`, `deploy.yml:438`, `infra.yml:84`, `mobile-release.yml:59`, `openbao-restore-drill.yml:45`, `keyvalue-restore-drill.yml:51`, `snapshot.yml:37`.
- `deploy.yml` alone references secrets 35 times across several jobs; only one job carries an environment.

## Steps

1. For every job in both workflow trees, list each `secrets.X` reference (job `env:`, step `env:`/`with:`, `secrets: inherit`, reusable-workflow `secrets:` passthrough) and the job's `environment:` and trigger (`push`, `schedule`, `workflow_dispatch`, `pull_request`).
2. Classify each secret: production-class (cluster, infra, identity, backup, signing, registry push credentials) vs non-production (e.g. a Stripe test-mode webhook secret). Record the reason for each borderline case.
3. Mark scheduled jobs that need a production credential (edge liveness, canary, isolation matrix): required reviewers would block them, which t002 must account for.
4. Record the table (names only) in this task file's Evidence section; count-check it against `grep -c 'secrets\.'` per file.
