## Objective

The dashboard reads and writes the account's theme through GraphQL, in Render's own names, and a REST client can do the same through a bex extension.

## Context

- Render's documents (README § Render's Appearance): `user { id … themeSetting logThemeSetting }`, `updateUserThemeSetting(id: String!, themeSetting: ThemeSetting!) { id themeSetting }`, `updateUserLogThemeSetting(id: String!, logThemeSetting: LogThemeSetting!) { id logThemeSetting }`.
- bex-api's GraphQL has no `user` query today. Its self-service settings precedent is `notificationSettings` (`internal/notifications/graphql.go`, `rest.go`), which also shows strict partial JSON decoding for PATCH.
- `GET /v1/users` (`internal/workspaces/rest.go`) is Render's whoami and keeps Render's `{name, email}` shape; `GET /v1/users/deletion-preview` (`internal/accounts/rest.go`) is the bex-extension precedent under `/v1/users`.
- The schema snapshot: `lego/backend/internal/api/testdata/schema.graphql`; the router's contract: `lego/backend/internal/router/contract.graphql` if it lists the operations.

## Steps

1. A small service (its own package or `internal/accounts`, whichever keeps the import DAG and depguard happy) with `Get` and the two updates, on the caller's own subject from `core.IdentityFrom`. No workspace is involved.
2. GraphQL: `ThemeSetting` and `LogThemeSetting` enums, `User { id themeSetting logThemeSetting }`, the `user` query, and the two mutations. `id` must be the caller's own user id (what `user.id` returns); any other id is refused the way bex refuses another subject's data.
3. REST (bex extension): `GET /v1/users/theme-settings` → `{themeSetting, logThemeSetting}` and `PATCH` with either field, strict decoding, an unknown field or value is a 400.
4. Wire it in `internal/serve`, regenerate the schema snapshot, and add tests for both surfaces: defaults, each write, another user's id refused, unknown values refused, unauthenticated refused.
