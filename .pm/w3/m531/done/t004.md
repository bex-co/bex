## Objective

Dashboard Theme stops being a per-browser choice. Signed in, the dashboard reads the account's `themeSetting` and applies it, and a change in Appearance or the account menu writes it to the account, as Render's `updateThemeSetting` does.

## Context

- `ThemeProvider` (`dashboard/src/common/providers/theme-provider/index.tsx`) keeps `system`/`light`/`dark` in `localStorage` (`vite-ui-theme`) and a cookie, and `?theme=` wins. The pre-paint script `src/common/components/document/theme-script.js.txt` reads the same key.
- Writers: `AppearanceCard` (`src/features/auth/pages/settings-page/appearance-card.tsx`) and the account menu's theme submenu (`src/common/components/user-nav.tsx`).
- Render previews the new setting at once, sends the mutation, then commits the server's value; its provider follows other tabs through `storage` events (README § Render's Appearance).

## Steps

1. Add the GraphQL operations and run codegen.
2. In the signed-in shell, read `user { id themeSetting logThemeSetting }` and apply the theme part. Keep the browser copy (localStorage + cookie) in step, so the pre-paint script and SSR agree on the next load. Map Render's enum onto bex's `Theme` plus a high-contrast flag (t005 uses the flag).
3. Both writers set the theme at once and send `updateUserThemeSetting`. On failure, put the previous theme back and show a toast saying it was not saved.
4. A `storage` listener lets another open tab follow a change.
5. Signed-out pages keep the browser's choice. `?theme=` still wins. Update `AppearanceCard`'s comment, which says the theme is kept in the browser.
6. Tests: a stored account theme is applied over the browser's, both writers send the mutation, a failed write reverts, another tab follows.

## Done (2026-11-20)

- The provider keeps Render's enums (`settings.ts`), the browser copy in `bex-user-settings` (plus `vite-ui-theme` for older copies), and is bound to the account by `AccountThemeSync` in the signed-in shell (`root-component.tsx`), which reads `user` and writes the two mutations. Writes go one at a time, later changes folded into the next, so two answers can never land out of order (found by the hook's own test against Apollo's MockLink); a refused write toasts `common.themeNotSaved` (the server's reason when it gave one) and puts the previous value back.
- The provider no longer applies a class before the stored theme is read, which removed a one-frame light flash the old provider had on a dark reload (`account-theme.test.tsx` pins it).
