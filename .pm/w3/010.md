# Postgres and Key Value creation is currently uncapped (no per-workspace enforcement)

**Type:** correctness / cost-abuse gap, surfaced by w3/m34 (retiring ADR043's transitional `BEX_MAX_*` flags).

w3/m34 deleted the app-code `BEX_MAX_SERVICES`/`BEX_MAX_POSTGRES`/`BEX_MAX_KEYVALUES` per-workspace creation caps on the premise that the per-tenant-namespace `ResourceQuota` (`count/apps.app.bex.co`/`count/databases.app.bex.co`/`count/keyvalues.app.bex.co`, `store.quotaForPlan`) replaces all three. That premise only holds for **Services (Apps)**: managed Postgres and KeyValue CRs are **not** namespaced under ADR043 — `postgres.Service.CreatePostgres` and `keyvalue.Service.CreateKeyValue` both create their CRs in the shared apps namespace (`s.Namespace`, `BEX_API_NAMESPACE`), never a workspace's own `<ws>` namespace — so the `count/databases.app.bex.co`/`count/keyvalues.app.bex.co` dimensions on every workspace's `ResourceQuota` are never actually charged.

The user was informed of this gap before m34 proceeded and explicitly chose to delete all three caps as originally specified, accepting that Postgres/Key Value creation is uncapped in the interim (documented in `docs/ADR006-bex-api.md` § Per-workspace resource caps and `lego/backend/internal/store/namespaces.go`'s `quotaForPlan` doc comment — this is an honest, recorded gap, not a silent one).

A workspace can currently create unlimited managed Postgres/Key Value instances — a real cost and abuse-surface risk (each provisions real CNPG/Valkey compute + storage).

Two ways to close it, either promotable to a milestone:

1. **Namespace Postgres/KeyValue under `<ws>` too** (extend ADR043's scope beyond Apps) — the deeper fix, but per m36's own note it's "a coordinated change across create/authz/pods/logs" affecting multiple already-shipped features (logs, metrics, authz, SNI proxies). Bigger lift.
2. **Restore app-code enforcement for Postgres/KeyValue specifically** (mirroring the deleted `BEX_MAX_POSTGRES`/`BEX_MAX_KEYVALUES` checks, or a plan-tier-driven equivalent using `store.QuotaCapsForPlan`) — smaller, faster, but keeps the dual-enforcement-path ambiguity ADR043 D3 was written to eliminate for Services.

Promote to a milestone when there's real usage/cost pressure, or as part of any future work that already touches Postgres/KeyValue namespace placement.

Source: w3/m34 (2026-08-01), t001 gating decision.
