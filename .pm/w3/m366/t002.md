## Objective

The service layer serves history beyond the status window without losing the live detail only status has.

## Context

- `ListCronRuns` / `GetCronRun`: `lego/backend/internal/apps/service.go:4322-4346`. `cronRunsOf` (`service.go:1360`) adds the unmaterialized canceled run and the pending manual run. `lastSuccessfulCronRunAt`: `service.go:1444`, used at `service.go:1192`.
- w4/m300 (blocked) owns the acknowledged-trigger and canceled-run semantics in these functions; w5/m108's no-resurrection rule reads `Status.CancelRunRecorded`.

## Steps

1. Merge: status entries win for any run id they carry (live phase, trigger details); facts supply runs status no longer holds. Keep newest-first order and the existing cursor semantics.
2. `GetCronRun`: status first, then the facts; the same 404 shape for unknown or foreign ids.
3. `lastSuccessfulRunAt`: the newer of the status scan and `LatestSucceededCronRun`.
4. A run whose terminal state is in status but not yet recorded as a fact shows its status state, never a regressed one.
5. A store-off backend (no Postgres) falls back to today's status-only behavior.
