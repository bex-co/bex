## Objective

Check that the change is consistent across every surface it exposes: REST, GraphQL and MCP in `lego/backend/` (same fields, semantics, error shapes; `docs/ADR006-bex-api.md`) and the `dashboard/` Runs page (w2/m360). Compare against render.com's Runs page and `cronJobDetails.lastSuccessfulRunAt`, and file any drift as follow-up work rather than silently diverging.

## Acceptance criteria

- [ ] Every surface shows the same history and last success; drift is fixed or filed.

## Result (2026-11-13)

- REST, GraphQL and MCP share `ListCronRuns`/`GetCronRun`/`CancelCronRun`. `TestCronRunSurfacesReachEvictedRuns` shows the three agree on the evicted runs' count, ids, status and times, and on the terminal 409. `serviceDetails.lastSuccessfulRunAt` (REST), GraphQL `lastSuccessfulRunAt` and MCP `get_service` all read the same `view(a)` field.
- Dashboard: the Runs page (w2/m360, `dashboard/src/features/services/hooks/use-cron-runs.ts`) already pages `cronJobRuns` with a cursor and Load more, so it pages past the tenth run with no change. Its 5-row poll stays inside the status window and never reaches the store. The header's "Last run" reads `lastSuccessfulRunAt`.
- Render: `cronJobDetails.lastSuccessfulRunAt` (pinned OpenAPI, optional date-time) now reports the last success after any number of failures. Render's Runs page "shows run history and logs for each run" with no documented ten-run limit. The list, get and per-run cancel routes remain the documented bex extensions (w2/m36). No drift was found to file.
