## Objective

Make `scripts/alerting-heartbeat.sh` succeed against the live cluster, so issue #99 closes on its own and the hourly heartbeat means something again.

## Context

- Filed by `/unblock w3` 2026-10-29. Every scheduled run since 2026-10-21 prints `FAIL: cluster API or Alertmanager unreachable` and `FAIL: Prometheus unreachable through the API server` (e.g. run `40955985179`) and updates #99; the job itself shows success.
- Local reproduction: `kubectl get --raw /api/v1/namespaces/monitoring/services/prometheus-server:80/proxy/...` times out, while `kubectl -n monitoring port-forward svc/prometheus-server` answers. The kubeconfig fetch works.
- Production read-only access: see the milestone README's D1 record.

## Steps

1. Find out why the apiserver service proxy cannot reach monitoring Pods: CP host network → Pod CIDR routing, or a NetworkPolicy / CiliumNetworkPolicy in `monitoring` denying `kube-apiserver` / host entities. Read-only diagnosis only.
2. Fix it in the repo: either allow apiserver ingress in the policy (the narrowest rule that works), or have the heartbeat use `kubectl port-forward` (it goes through the kubelet). Prefer the fix that does not widen tenant reachability.
3. Stop swallowing stderr in `kubectl_raw` (`scripts/alerting-heartbeat.sh:47`): put the first error line into the FAIL message.
4. Add or extend a test (heartbeat self-test / script test) that catches this kind of regression.

## Acceptance criteria

- [x] After the release rolls out, one `alerting-heartbeat.yml` run has `down=false` in its log and #99 is closed by the workflow (run id recorded).
- [x] The FAIL message includes the underlying error.

## Done (2026-10-30, loopx w3)

- Cause: the apiserver service proxy dials Pods from the control-plane host network; `monitoring`'s `deny-tenant-ingress` only admits the `monitoring` and `bex-system` namespaces, and Cilium classifies the apiserver as `remote-node`, so every proxied read timed out (the `bex-system` service proxy times out the same way).
- Fix `32aa6e75f`: the heartbeat reads through `kubectl port-forward` (kubelet → Pod netns; no NetworkPolicy widening), every FAIL line carries the underlying error, forwards are stopped on exit; the self-test gained a stub kubectl/curl live path (no service proxy, errors named, no leaked forward; mutation-checked by disabling the exit trap). ADR010 § Alerting heartbeat updated.
- Live: dispatched run `40979918674` on `32aa6e75f` → `OK: Watchdog active, no failed notifications in 1h, https://api.bex.co and https://dashboard.bex.co answering`; the workflow closed #99.
