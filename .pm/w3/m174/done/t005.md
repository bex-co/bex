## Objective

Make "tenant capacity ran out" visible before tenants see deploys stuck in Deploying: alert on tenant pods unschedulable for >10m, and on requested resources near allocatable while the serving pool is at its maximum size.

## Context

- Only builds have a queue alert (`BuildQueuedTooLong`); no rule reads `kube_pod_status_unschedulable` / Pending phase or requested-vs-allocatable.
- Serving pool autoscaler bounds: `infra/clusterapi/overlays/hetzner-caph/cluster.yaml:373-378` (max 3; the comment records rollout pods that went unschedulable on two serving nodes).
- kube-state-metrics is scraped (`prometheus.yaml:424`).

## Steps

1. Add `TenantPodUnschedulable` (tenant namespaces, `PodScheduled=false` reason `Unschedulable` for >10m, excluding build pools already covered).
2. Add `TenantServingPoolSaturated` (CPU or memory requests >85% of allocatable on the serving pool while its node count equals the configured max).
3. Rule tests for both, including a build pod that must not trigger the tenant alert.

## Files

- `deploy/gitops/base/prometheus.yaml`
- the rule-test harness

## Acceptance criteria

- [ ] Both rules fire on fixture series and stay quiet on healthy ones; build pods are excluded.

## Out of scope

- Raising pool limits or Hetzner quota (`.pm/FUTURE-MAYBE.md`).

## Done (2026-10-20)

`TenantPodUnschedulable` (critical, 10m): `kube_pod_status_unschedulable` in `tea-*` joined to `kube_pod_owner{owner_kind=~"ReplicaSet|StatefulSet|Cluster"}`, so Job pods (builds, pre-deploy, backups — co-located in tenant namespaces per ADR043 D8) are excluded. The planned pool-saturation rule was **dropped**: an unschedulable serving pod for 10m already means the pool is at its autoscaler maximum or scale-up failed, and a saturation threshold would hard-code `cluster.yaml`'s node counts into PromQL.
