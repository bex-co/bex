## Objective

Resuming a suspended service opens a deploy, as Render's does, with trigger `service_resumed`, so it shows in Deploys and Events; GraphQL `resumeService` answers the deploy it opened, so the dashboard can open it.

## Context

- Render: the REST `deploy.trigger` enum carries `service_resumed` (`lego/backend/internal/api/openapi/render-public-api-1.json`); the dashboard's `resumeService` (`service-*.js`) selects `... on Server { deploy }` and `... on CronJob { build }` and opens it. `POST /v1/services/{id}/resume` answers 202 with no body.
- bex: `setSuspended` (`lego/backend/internal/apps/service.go`) flips `Spec.Suspended` and opens no deploy. A restart opens a deploy on the live release with `store.TriggerRestart` (`lego/backend/internal/deploys/service.go`, `restart_wait.go`); `SetPlan` returns the deploy it opened as `LatestDeployID` through `rollout.WithOpenedDeploy` (w3/105), and GraphQL reads it in `lego/backend/internal/apps/graphql.go`.
- An idle (scale-to-zero) wake is not a resume and must open no deploy.

## Steps

1. Verify first: confirm from Render's API reference or changelog what a `service_resumed` deploy is (which commit or image, and whether a cron job's resume builds), and record it in `docs/render-artifacts/cron-dashboard.md`. If Render's resume turns out to open nothing, record that and reduce t005 to the toasts.
2. Add `TriggerServiceResumed = "service_resumed"` and open a restart-shaped deploy on the live release when a resume is accepted, in the same write order as restart; a resume refused by its guards opens none.
3. Return it as `LatestDeployID` from `Resume`, select `latestDeployId` in the dashboard's `ResumeService` mutation, and check REST and MCP deploy reads report `trigger: "service_resumed"` (MCP `list_deploys`, REST `GET /v1/services/{id}/deploys`).
4. Events and webhooks: `deploy_started`/`deploy_ended` carry the trigger the way Render's do.
