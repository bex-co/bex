# A fresh upgrade clone's Upgrade button waits for the server's backup guard instead of being refused by it

Why: the guided page enables "Upgrade to PostgreSQL 18" on an upgrade clone as soon as it is available, because Render's page needs no PITR wait for a clone, but bex-api refuses the upgrade with 409 `POSTGRES_UPGRADE_BACKUP_REQUIRED` until the clone's own first backup completes, so the recommended first step can answer with an error.

Found by w3/m676 t007's production walk on 2026-11-27 (pin `546d61ac7343`, `bex-canary`, a paid 16 and its clone, both disposable).

- **Seen:** the clone `qa-20261127-m676-src-upgrade-clone-g9mg` (disposable) read `available` at 17:13:28Z. Upgrade, clicked at about 17:14:25Z, answered inline "A completed physical backup is required before upgrading this durable Postgres instance". The clone's first backup completed at 17:14:32Z, and the same click at 17:15Z started the run, which ended `SUCCEEDED`. So the window is about a minute.
- **Why:** `dashboard/src/features/databases/components/database-version-upgrade.tsx:454` counts a clone as ready without PITR (`isUpgradeClone(database.name)`), as Render's page does. `lego/backend/internal/postgres/service.go:2138` still requires a completed backup in the current generation for every durable plan, clones included. That guard is bex's recorded stricter-than-Render rule (`docs/render-artifacts/postgres-version-upgrade.md` § bex parity and deliberate extensions).
- **Done when:** a fresh clone's page does not offer an upgrade the server refuses. Either the button waits, with Render's "not ready" tooltip, until the server would accept (for example by reading the clone's `databaseRecoveryInfo` the way the source's page does), or the server accepts a clone whose source had a completed backup. Pick the option closer to Render's behavior (Render upgrades a clone with no wait) and record it in ADR018's "Postgres major-version upgrade" row. A dashboard test pins the fresh-clone state.
