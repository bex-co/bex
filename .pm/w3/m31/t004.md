## Objective

Enforce plan-tier caps (services / postgres / keyvalues / cpu / memory / pods) via per-namespace `ResourceQuota`/`LimitRange` at the API server, replacing the `BEX_MAX_*` counting done in bex-api code (ADR043 D3).

## Context

- Today: `BEX_MAX_SERVICES` / `BEX_MAX_POSTGRES` / `BEX_MAX_KEYVALUES` are per-workspace caps enforced in bex-api code; plus one shared cluster `tenant-apps-quota`.
- ADR043 D3: push enforcement to the lowest layer — API server `ResourceQuota` is not bypassable by an app bug.

## Steps

1. Derive per-tenant `ResourceQuota`/`LimitRange` from the workspace's plan tier at namespace create (t001) and on plan change.
2. Remove/adapt the `BEX_MAX_*` enforcement to defer to quota (or keep as a fast pre-flight that matches the quota).
3. Retire the shared-namespace manifests once per-tenant quotas are live: `deploy/gitops/base/tenant-quotas.yaml` (the one `tenant-apps-quota`) and `deploy/gitops/base/tenant-namespace.yaml` both hardcode `namespace: default`.

## Files

- `lego/backend/internal/` (where `BEX_MAX_*` is enforced), namespace reconciler (t001)
- plan-tier map: `lego/types/tiers/`
- `deploy/gitops/base/tenant-quotas.yaml`, `deploy/gitops/base/tenant-namespace.yaml` (retire)

## Acceptance criteria

- [ ] A workspace at its plan cap cannot create more services/DBs/KVs (denied by the API server, not just bex-api code — needs t002's placement of CRs into `<ws>`, hence the t002 dependency).
- [ ] One tenant can no longer starve a shared quota.

## Out of scope

- The namespace lifecycle itself (t001), NetworkPolicy (t005).
