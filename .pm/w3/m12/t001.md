## Objective

Return a clear 400 error when a caller passes `host` or `path` to a metrics query for `http-requests`, `http-latency`, or `bandwidth`, instead of silently accepting and ignoring the filter.

## Context

- `docs/ADR006-bex-api.md:322` — "`host`/`path` filters are accepted but not yet applied (Traefik service counters lack those labels)."
- `lego/backend/internal/metrics/source.go:207-209` — `promQueryFor` comment confirms host/path have no Traefik service-level label to filter on.
- `lego/backend/internal/metrics/rest.go:201-202` — parses `host`/`path` from the query string but nothing downstream consumes them.
- Mirror the existing "refuse rather than silently drop" pattern used for store-only log filters (`BEX_LOKI_URL` unset ⇒ 503, root `CLAUDE.md`).

## Steps

1. In the metrics query handler(s) (REST/GraphQL/MCP entry points), check for a non-empty `host`/`path` filter on the affected metric types and return 400 with a clear message ("host/path filtering is not supported for this metric") before querying Prometheus.
2. Apply consistently across REST, GraphQL, and MCP — same error semantics.

## Files

- `lego/backend/internal/metrics/rest.go`
- `lego/backend/internal/metrics/graphql.go`
- `lego/backend/internal/metrics/mcp.go`

## Acceptance criteria

- [ ] `GET /v1/metrics/http-requests?path=/x` returns 400.
- [ ] Same for `host` filter, and for `http-latency`/`bandwidth`.
- [ ] Queries without `host`/`path` are unaffected.
- [ ] GraphQL and MCP equivalents behave identically.

## Out of scope

- Adding host/path as real Prometheus labels (deliberately rejected — cardinality risk).
