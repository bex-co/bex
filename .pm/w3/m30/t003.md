## Objective

Give `lego/backend` a KeyValue log query path: a typed KeyValue resource id routes through the same durable log core Postgres uses (`logs.Service.QueryLogs`), authorized via `core.Base.AuthorizeKeyValue`, with the honest degraded fallback when Loki is unset.

## Context

- Mirror `lego/backend/internal/postgres/logs.go` (`QueryDatabaseLogs` — delegates typed `dpg-` names to the shared core, exact-pod fallback otherwise); the keyvalue sibling lives in `lego/backend/internal/keyvalue/`.
- The generic logs entry point resolves resource kinds in `lego/backend/internal/logs/` (m28 taught it `dpg-`); teach it the KeyValue id kind the same way.
- Store-only filters must 503/400 honestly, never silently ignore (the standing log-surface rule, CLAUDE.md `BEX_LOKI_URL` row).

## Steps

1. Add `QueryKeyValueLogs` (or equivalent) in `internal/keyvalue`, delegating to the shared core with the keyvalue label selector from t002.
2. Teach the generic `resource=` resolution to accept KeyValue ids with `AuthorizeKeyValue` authorization.
3. Unit-test authorization (cross-tenant 403/404 discipline) and the Loki-unset fallback.

## Files

- `lego/backend/internal/keyvalue/logs.go` (new)
- `lego/backend/internal/logs/service.go` / resolution seam

## Acceptance criteria

- [ ] A KeyValue id queries logs through the durable core when Loki is wired; unset falls back honestly (or 503s where the store is required), never silently empty.
- [ ] A caller without keyvalue access cannot read its logs (existing 403/404 discipline).
