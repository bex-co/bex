## Objective

Add Render's three storage fields to GraphQL's `Database`, resolved only when a query asks for them, from the fullest instance's used bytes and the database's logical size.

## Context

- `lego/backend/internal/postgres/graphql.go` builds `Database` (`PostgresView`). The metrics package has the Prometheus clients (`lego/backend/internal/metrics/source.go`: `promQueryRange`, `NewPrometheusDiskUsageSource`; `datastore.go`: the PVC pattern for a database's instances).
- The operator's `DatabaseDiskUsage` (`database_autoscale.go`) picks the fullest PVC with instant queries. The backend cannot import the operator; write its own instant query in `lego/backend/internal/metrics`.
- Render types: `storageUsedPercent` a number, `storageUsed` and `storageTotal` byte counts as strings (Render's rule calls `Number(...)` on them). t001 records the exact types; match them.

## Steps

1. Add an instant-query source for a database's used bytes across its instance PVCs, returning the fullest.
2. Resolve the three fields lazily on `Database`. `storageTotal` is the logical size in bytes (the Metrics page's capacity), `storageUsed` the fullest PVC's used bytes, `storageUsedPercent` their ratio.
3. When Prometheus fails, times out or has no sample, return null for all three and log once. The rest of the read is unaffected.
4. A list query that does not select the fields makes no Prometheus call.

## Files

- `lego/backend/internal/metrics/` (new instant-query source)
- `lego/backend/internal/postgres/graphql.go`, its wiring in `lego/backend/internal/api/`
- `dashboard/src/features/databases/graphql/` (the database query and its generated types)

## Acceptance criteria

- [ ] Tests cover a single instance, an HA pair and replicas (fullest wins), no sample, a Prometheus error, and a list query that does not select the fields.
- [ ] REST's and MCP's Postgres responses are byte-for-byte unchanged in their contract tests.

## Out of scope

- A REST or MCP usage field: Render's public API has none.
