# A failed Blueprint sync's page says which of its actions applied and which failed, as Render's does

Why: on Render each action of a failed sync carries its own state and reason ("deploy failed" links the failed deploy); bex records a sync's state and one error, so a failed sync's page shows its actions with no state at all.

Filed by w3/m678 t009 on 2026-11-27.

- **Render:** the sync's read carries `actionStates { state message }`, parallel to the plan's actions (`iacExecution`, `iac-D9RnC10j.js`), and each row of the sync page draws its own state's icon and, for an errored action, its reason (`hL` in `index-D5V4ZgbE.js`; "deploy failed" becomes a Failed deploy link) ([blueprint-pages.md § A sync's page](../../docs/render-artifacts/blueprint-pages.md#a-syncs-page-syncs-and-the-sync-card-w3m678)). A sync that is not settled subscribes to its action states.
- **bex:** `blueprintSyncActionState` (`lego/backend/internal/apps/blueprint_sync_page.go`) gives every action the sync's own state while it waits, runs or has succeeded, and none once it failed: `runSync` records the sync's error (`blueprint_syncs.error_message`), not which action met it or which applied before it. The page polls the sync every 3 seconds while it applies.
- **Done when:** `deployParsedStack` records each planned action's result as it applies it (a jsonb beside `plan_actions`, with the reason of the one that failed and the ones it never reached left as planned), `blueprintSync` returns them as `actionStates`, and the sync page draws each row's own icon and reason; a real-Postgres test fails a sync at its second action and reads success, error with the reason, then not applied.
