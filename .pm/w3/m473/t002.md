## Objective

With `limit` 101–1000 now admitted, the REST answer serves at most 100 lines (the milestone's recorded recommendation) and still says there is more. The CLI's scroll then keeps loading.

## Context

- `lego/backend/internal/logs/service.go:128-134`: `maxLogLimit = 100`. `normalized` (`:394-405`) clamps `q.Limit` to it.
- `lego/backend/internal/logs/rest.go:598` parses `limit` with `core.QueryLimit64`. The REST log list fills `hasMore` and `nextStartTime`/`nextEndTime`; w4/m107 made the cursors followable.
- Check: does `hasMore` compare against the requested limit (1000) or the clamped one (100)? A page of exactly 100 lines with `limit=1000` must still report `hasMore: true` when older lines exist.

## Steps

1. Trace `limit=1000` through `normalized`, the probe (`:342`, one line past the caller's clamped limit) and the REST `hasMore`/cursor computation.
2. Fix any place that uses the unclamped value.
3. Add a service or REST test with 250 seeded lines. `limit=1000` answers 100 lines, `hasMore: true` and cursors. Following the cursors twice reaches the oldest line, and the last page has `hasMore: false`.
4. Record the page-size decision in a code comment beside `maxLogLimit`, pointing at this milestone's README.
