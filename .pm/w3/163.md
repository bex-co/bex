# Postgres and Key Value Logs read Render's `l`, `q` and custom `r` log keys

Why: Render's log viewers share one URL grammar, so a Render-shaped link into a database's or Key Value instance's logs carries `l` (label filters), `q` (search text) and a custom `r` window; bex reads them on a service's Logs only (w3/m707), and a datastore's Logs open unfiltered.

Filed by w3/m707 t007 on 2026-11-27, from Render's dashboard bundle read the same day (the `log-filters-*.js` chunk: `logType` `t`, `searchValue` `q`, `labels` `l`, `timeRange` `r`, custom windows `YYYY-MM-DD@HH:mm:ss~YYYY-MM-DD@HH:mm:ss`).

- **Render:** one parser (`Ie`) reads the keys for every log viewer; a datastore's labels are `LEVEL` and `INSTANCE`. [dashboard-routes.md § Render's deep-link queries](../../docs/render-artifacts/dashboard-routes.md#renders-deep-link-queries).
- **bex:** `parseLogSearch` (`dashboard/src/features/logs/lib/log-search.ts`) reads them for `/services/<id>/logs`; the datastore Logs routes validate through `datastore-log-search.ts`, which reads bex's keys alone.
- **Done when:** `/databases/<id>/logs` and `/keyvalue/<id>/logs` read `l` (`LEVEL`, `INSTANCE`), `q` and a custom `r` as the service Logs do, bex's keys win, Render's leave the URL at the first write, and the search-validator test covers both routes.
