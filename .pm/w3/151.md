# After an in-place major upgrade, bex leaves extensions at their old versions where Render runs `ALTER EXTENSION … UPDATE`

Why: Render updates each extension with `ALTER EXTENSION UPDATE` as part of a major upgrade. bex leaves them at their old versions, and the upgrade's log tells the user to run a file in PGDATA, which a bex user cannot reach.

Found by w3/m676 t007's production walk on 2026-11-27 (pin `546d61ac7343`, `bex-canary`, a paid 16 clone upgraded to 18, disposable).

- **Seen:** after the run ended `SUCCEEDED` on PostgreSQL 18.7, `pg_available_extensions` read `pg_stat_statements` installed at 1.10, with 1.12 as the default. The guided page's logs end with pg_upgrade's "Your installation contains extensions that should be updated with the ALTER EXTENSION command" and CloudNativePG's "pg_upgrade emitted update_extensions.sql in PGDATA on the primary. Once the cluster is back online, review the script and apply extension updates as needed."
- **Render:** the guided page lists "each extension updated with `ALTER EXTENSION UPDATE`" among the changes it makes even if the upgrade fails (`docs/render-artifacts/postgres-version-upgrade.md`, the Irreversible changes row). w3/m676 recorded this as one of bex's own differences on the page, but ADR018 has no user sign-off for it as a divergence.
- **Done when:** after a successful in-place upgrade, every installed extension that the target can update is updated, as on Render. For example, the operator runs the generated `update_extensions.sql`, or the equivalent `ALTER EXTENSION … UPDATE` for each extension, as the superuser once the cluster is healthy. The guided page's irreversible-changes list and ADR018's "Postgres major-version upgrade" row say so. A local upgrade from 16 shows `pg_stat_statements` at the target's default version. If an extension cannot be updated, the run's log says which one and why, in words a user can act on.
