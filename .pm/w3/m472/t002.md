## Objective

Retry host-key failures only when they can heal. Pinned verification failing mid-roll can heal. A stale `~/.ssh/known_hosts` entry under `accept-new` never does, so it must fail on the first pass with the fix spelled out, not after about five minutes of retries.

## Context

- `scripts/fetch-app-kubeconfig.sh:66-125`: `ATTEMPTS` (default 6) × `RETRY_SECONDS` (default 60) applies to every "Host key verification failed", whatever the trust tier. The final message talks only about "the pinned BEX_SSH_KNOWN_HOSTS".
- The retry exists for w6/m153: a control-plane roll briefly leaves every candidate failing strict pinned checks.

## Steps

1. Have `bex_ssh_hostkey_args` export which tier it chose (for example `BEX_SSH_HOSTKEY_TIER=pinned|derived|tofu`).
2. In `fetch-app-kubeconfig.sh`, retry host-key failures only for the pinned and derived tiers. Under `tofu`, stop after the first pass. Print that the local known-hosts entry for `<ip>` does not match, how to supply `BEX_SSH_KNOWN_HOSTS_FILE` or `BEX_CP_SSH_HOST_KEY_FILE`, and the ADR019 recovery workflow (`Verify production SSH trust`). Do not suggest `ssh-keygen -R`: removing the entry and accepting the next key is trust on first use again.
3. Apply the same rule to `verify-substrate.sh` if it retries.

## Files

- `scripts/fetch-app-kubeconfig.sh`, `scripts/verify-substrate.sh`, `scripts/lib/ssh-hostkey.sh`
- `scripts/fetch-app-kubeconfig.test.sh`

## Acceptance criteria

- [ ] Under `tofu` with a failing stub `ssh`, the script exits non-zero without sleeping. The test runs with `RETRY_SECONDS` left at its default and finishes in under 5 s.
- [ ] Under a pinned tier the existing bounded retry still happens (the existing test stays green).
- [ ] The `tofu` failure message names both variables and ADR019, and contains no key material.

## Out of scope

- Changing the retry bounds for pinned runs.
