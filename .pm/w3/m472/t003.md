## Objective

The Hetzner API token never appears in a process's command line, where any local user's `ps` and process-accounting logs can read it.

## Context

- `scripts/fetch-app-kubeconfig.sh:77`: `curl -sf -H "Authorization: Bearer $HCLOUD_TOKEN" "https://api.hetzner.cloud/v1/servers?…"`
- `scripts/verify-substrate.sh:178`: `hc() { curl --fail --silent --show-error -H "Authorization: Bearer $HCLOUD_TOKEN" "https://api.hetzner.cloud/v1$1"; }`
- `scripts/qa-login.sh` already keeps credentials off argv ("Credentials go to curl by file, never in argv (ps leaks argv)").
- The w3/m302 worker observed the token in `ps` during its 2026-11-17 run.

## Steps

1. Add a small shared helper, for example `scripts/lib/curl-auth.sh` `bex_curl_bearer <VAR_NAME> <curl args…>`. It feeds `header = "Authorization: Bearer <value>"` to `curl --config -` on stdin (or `-H @-`, curl ≥ 7.55), so the value lives only in the shell's memory and the pipe.
2. Use it in `discover` and `hc`. Keep `set -euo pipefail` semantics and curl's exit status.
3. Check the other scripts that send a production token on the command line (`scripts/agent-session-verify.sh`, `scripts/auth-obs-e2e.sh`, and any reading a name from `scripts/production-secrets.txt`). Move the production-class ones to the helper. Dev-only tokens (`CP_TOKEN` against a local stack) may stay, with t004's validator scoped accordingly.

## Files

- `scripts/lib/curl-auth.sh` (new), `scripts/fetch-app-kubeconfig.sh`, `scripts/verify-substrate.sh`, and the production-token scripts step 3 finds
- `scripts/fetch-app-kubeconfig.test.sh`
