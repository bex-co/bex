## Objective

Add an auto-deploy predicate to the events store filter so the discrimination that `events/service.go` currently performs only at view time (enabled / disabled / legacy-changed, from the stored `AutoDeployEnabled` boolean) can be pushed into the SQL `WHERE` clause, keeping pagination correct.

## Context

- `lego/backend/internal/events/service.go:490-503` — view-time discrimination: `auto_deploy_enabled` when the stored boolean is true, `auto_deploy_disabled` when false, `auto_deploy_changed` for legacy rows without the boolean.
- `lego/backend/internal/store/events.go` — the events SELECT; migration 0037 already persists the audit `details` columns including the auto-deploy boolean, so no new migration.
- The `pushDown` doc comment in `events/service.go` explains why filtering must stay in SQL: a Go-side drop produces short pages.

## Steps

1. Add an auto-deploy predicate field to `ServiceEventFilter` (three-state: want-true, want-false, want-NULL/legacy — e.g. an enum or `*bool` + legacy flag).
2. Extend the store's WHERE builder to emit the predicate against the persisted boolean column (NULL for legacy rows).
3. Unit-test the store layer: seed true/false/NULL rows, assert each predicate returns only its rows and cursors stay stable.

## Files

- `lego/backend/internal/store/events.go`
- `lego/backend/internal/events/service.go` (filter struct if it lives there)
- store tests alongside

## Acceptance criteria

- [ ] `ServiceEventFilter` can express enabled-only, disabled-only, and legacy-only auto-deploy queries
- [ ] The predicate is applied in SQL, not in Go post-processing
- [ ] Store tests cover all three predicate states plus the unset (no-predicate) case
