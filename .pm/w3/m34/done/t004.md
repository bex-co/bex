## Objective

Ensure removing the bex-api code caps does not regress the caller-visible error when a workspace hits a plan limit. With `BEX_MAX_*` gone, the limit is enforced by the per-namespace `ResourceQuota`, which fails a create with an API-server `403 exceeded quota` instead of bex-api's `ErrConflict`/"limited to N services" message. Verify (and, if needed, translate) so REST, GraphQL, and MCP still return a Render-compatible cap error.

## Context

- Prior behavior: `apps/service.go` returned `ErrBadRequest`/`ErrConflict` "workspace is limited to N services; delete an existing service to create another" (Render-shaped).
- New behavior: the App CR create (or the projector's create) hits the namespace `ResourceQuota` `count/apps.app.bex.co`; the error surfaces from the Kubernetes client as a `Forbidden`/`exceeded quota` API error.
- Render parity contract: `docs/ADR006-bex-api.md`, `docs/ADR018-render-parity.md` — same fields/semantics/error shape across REST/GraphQL/MCP.

## Steps

1. Reproduce a create-past-cap on a capped plan; capture the raw error across all three surfaces.
2. If it is not Render-shaped, map the quota-exceeded API error to the existing `ErrBadRequest`/`ErrConflict` cap message in the create path.
3. Confirm the dashboard surfaces it the same as before.

## Files

- `lego/backend/internal/apps/service.go` (create error mapping), postgres/keyvalue equivalents
- REST/GraphQL/MCP fragments if the mapping needs a surface-specific shape

## Acceptance criteria

- [ ] Create-past-cap returns a Render-compatible error (message + status) on REST, GraphQL, and MCP — no raw `exceeded quota` leak.
- [ ] Dashboard cap UX unchanged.

## Out of scope

- New cap semantics; per-resource quota tuning.
