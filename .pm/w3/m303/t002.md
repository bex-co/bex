## Objective

`timeoutSeconds` follows Render's current contract on every plan: omitted means 86400 s, `0` means no timeout, positive values from 60 to 2,592,000 s are honored, and anything else answers `400 SANDBOX_TIMEOUT_INVALID`. Hobby is no longer capped at 86400 s, and 1–59 s is refused as Render refuses it.

## Context

- `lego/backend/internal/sandbox/lifetime.go`:33-75 (`hobbySandboxMaxTimeout`, `0` held to 86400 on Hobby, `osMinTimeout` floor enforced by the reconcile).
- Render: CLI commit `c280b0b66` (INF-7261, "remove the 24-hour sandbox lifetime limit for Hobby"), v2.36.0 notes, render.com/docs/sandboxes-limits (no plan difference).
- Pinned OpenAPI `POST /sandboxes` `timeoutSeconds`: "Use 0 for no timeout. Positive values must be at least 60."
- ADR018:489 and ADR014 § Lifetime bound record today's Hobby cap under user decision w2/m263 D3=A, which chose to match Render; Render has since changed.
- Recommendation in place of an open decision: follow Render (D3=A's basis, ADR008). Keeping the Hobby cap would need a signed ADR018 divergence.

## Steps

1. Drop the Hobby branch from `resolveTimeout`; refuse `1..59` with the existing code and a message naming the 60 s minimum.
2. Keep legacy metadata semantics (`"0"` = 86400 s default, `none` = no timeout) unchanged.
3. Amend ADR014 § Lifetime bound and ADR018:489 (cite c280b0b66 and the docs page).
