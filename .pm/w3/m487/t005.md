## Objective

Check that CPU and memory usage and limits for an edge-cached service is consistent across every surface it exposes and with Render, and flag any drift as follow-up work rather than silently diverging.

## Context

- Surfaces: REST `/v1/metrics/cpu`, `/memory`, `/cpu-limit`, `/memory-limit`; GraphQL `metrics`; MCP `get_metrics`; the dashboard Metrics page; autoscaling as seen on the service.
- Reference: [render.com/docs/web-service-caching](https://render.com/docs/web-service-caching) (fetched 2026-11-18): the cache is "powered by the same global CDN as Render static sites", Render purges it on each successful deploy and on a manual purge, failed deploys do not purge, and responses carry `CF-Cache-Status`.
- Ledger: `docs/ADR018-render-parity.md` rows "Edge caching" and "Cache purge".

## Steps

1. Compare the shipped behavior on each surface above (same values, semantics and error shapes).
2. Compare with Render's documented behavior; mark anything Render does not document as unverified, not as matched.
3. File any drift with `/pm add w3 …`, or record it in ADR018 with its date.

## Files

- the milestone README (parity table)
- docs/ADR018-render-parity.md (only if a cell or note changes)

## Acceptance criteria

- [ ] A short parity table is in the milestone README; every difference is fixed, filed, or recorded in ADR018

## Out of scope

- Fixing drift found here (it is filed, not fixed in this task)
