## Objective

Pin today's behavior with tests that fail until the fix lands: the autoscaler and bex-api's usage and limit-history queries include the `edge-cache` sidecar's CPU and memory, while the pod-spec limit reader already excludes it.

## Context

- `lego/types/podmetrics` `Parse` sums every container in each pod (the shared decoder for the autoscaler and bex-api's current usage).
- `lego/operator/internal/controller/autoscale.go:219-260`: `autoscaleDesired` compares that sum with the plan's `tierLimits(tier)`. The sidecar's limit is 160Mi (`edge_cache.go`), so enabling caching can push a service over its `targetMemoryPercent` and scale it out.
- `lego/backend/internal/egressquery/podname.go:125`: `PodNameMatcher` is `container!=""`, used by the service usage query (`lego/backend/internal/metrics/source.go`, `resourceUsageQuery` ~318-360) and by the limit history (`resourceLimitQuery` ~455-460, summing `kube_pod_container_resource_limits` by pod).
- `lego/backend/internal/metrics/service.go:1238-1262`: `podResourceLimits` skips the `edge-cache` container ("its resources are the platform's, never counted against the plan"), so the fallback and the Prometheus history disagree by 160Mi.
- Render: the cache is "powered by the same global CDN as Render static sites", outside the instances, so caching does not change instance metrics.

## Steps

1. `autoscaleDesired` test: a pod whose usage includes an `edge-cache` container must yield the same desired count as the app container alone.
2. PromQL tests: the service usage and limit-history queries must exclude `container="edge-cache"`.
3. Confirm both fail on the current code.
