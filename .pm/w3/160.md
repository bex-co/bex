# A service's Events filter keeps Render's `?et=` in the URL as it changes

Why: Render's Events page writes the types it shows to its URL, so a filtered Events view survives a reload and can be shared; bex reads `et` only on entry (w3/m707) and keeps the filter in component state, so the URL drops it at the first change and a reload shows every type.

Filed by w3/m707 t007 on 2026-11-27, from Render's dashboard bundle read the same day (`serviceEventsPicker-*.js`; find the code by `eventTypes`).

- **Render:** the picker's state is `{eventTypes}` under the URL key `et`, comma-separated GraphQL type names; choosing every type deletes the key, and any other choice writes the chosen list (`et=DeployEnded,ServerFailed`). [dashboard-routes.md § Render's deep-link queries](../../docs/render-artifacts/dashboard-routes.md#renders-deep-link-queries).
- **bex:** `routes/services.$serviceId.events.tsx` seeds `hiddenTypes` from `et` through `eventTypesHiddenBy` (`dashboard/src/features/events/service-event-catalog.ts`) and the routes drop `et` on the first change. The filter tracks hidden types on purpose (w6/m122), so writing Render's shown list needs a reverse of `bexEventType` and a rule for bex's own types Render has no name for.
- **Done when:** a filter change writes `et` in Render's spelling (bex's snake_case name where Render has none), every type selected removes it, a reload restores the filter, and the route test covers the round trip.
