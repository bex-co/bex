# A Blueprint plan says when its file no longer declares an environment group the Blueprint manages

Why: a plan that drops an environment group from the file lists nothing for it, and the approved sync's detachment note leaves it out, yet the Blueprint stops listing it among its resources: the group leaves the Blueprint and nobody is told.

Filed by w3/m678 t008 on 2026-11-27.

- **Seen on production** (pin `546d61ac7343`, `bex-canary`, the Blueprint `qa-20261127-m678` (disposable)): the Blueprint managed `blueprint-refs-group-cx4p` (disposable) and three services from `examples/blueprint-refs/render.yaml`. After `bex ea blueprints update --path examples/retained-env/render.yaml`, the plan read Create Service `retained-env-cx4p` and Stop managing for the three services, with no row for the group. The approved sync's note named the three services only. Then `GET /v1/blueprints/<id>` listed `retained-env-cx4p` alone, while `GET /v1/env-groups/<evg-id>` still answered 200 with the group linked to a detached service.
- **Cause:** `blueprintDetachments` (`lego/backend/internal/apps/blueprint_detach.go`) finds what the file stopped declaring in `blueprint_resource_claims`, whose kinds are `service`, `database`, `key_value` and `build_source` (migration 0191). A Blueprint remembers its environment groups in `blueprint_env_group_claims` instead (migration 0323, w8/382), which the detachments never read, so an environment group is never a detachment.
- **Render:** check what Render's plan and sync page show for an environment group the file stops declaring (the sync page's action kinds, `blueprint-pages.md` § A sync's page) before choosing the row's wording, as bex's Stop managing rows for services follow Render's.
- **Done when:** a plan whose file no longer declares a managed environment group lists Stop managing Environment group `<name>` (REST, GraphQL and MCP, and the sync page's row), the approved sync's note names it, and a real-Postgres test plans and approves that change and reads the action and the note.
