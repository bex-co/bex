# While a Blueprint's read loads, its sidebar names it by its `exs-` id beside a header of skeleton bars

Why: a click from the Blueprints list paints a frame whose header and breadcrumb are skeleton bars while the sidebar's title already reads `exs-…`; the ready page then renames it, so the one word the frame commits to is the wrong one, where a skeleton should preview the ready state exactly (`AGENTS.md`).

- **Seen** on production pin `486e3f4afbf6` (2026-11-27, w3/m677 t007) in Chrome at 1440, as the QA user in `bex-canary`, with the GraphQL `Blueprint` read held after a click on a Blueprint (disposable) in the Blueprints list: the header's name, status and Manual sync slots and the breadcrumb's last crumb were skeleton bars, and the sidebar's title read `exs-dc4nl7fs6bbs739rm7r0`. Released, the title read the Blueprint's name. The entries below it did not move.
- **Where:** `dashboard/src/common/components/dashboard-layout/blueprint-sidebar.tsx` passes `name={blueprint?.name ?? blueprintId}` to `ResourceSidebar` (`resource-sidebar.tsx`, which draws it as plain text). `database-sidebar.tsx`, `key-value-sidebar.tsx` and `sandbox-group-sidebar.tsx` use the same fallback. [w3/119](119.md) covers the service sidebar, whose header frame already shows the cached name.
- **Done when** with the `Blueprint` read held after a click from the Blueprints list, the sidebar's title is never the id: either a skeleton line where the header frame draws one, or the list cache's name in both the sidebar and the header frame. This holds at 1440 and in the 390 drawer, and the Postgres, Key Value and sandbox group sidebars behave the same way. A test pins it.
