# 044 — Correlate and fix the api.bex.co dropped-mutation race

Why: QA keeps seeing `ERR_CONNECTION_CLOSED` (and a CORS error) on `api.bex.co/graphql` amid hundreds of 200s, and because the dashboard never retries a mutation, a dropped one reads to the user as "did nothing" — the FUTURE-MAYBE "any recurrence" trigger has fired and the correlation was never run.

**Estimate:** ~1h. **Promoted from:** [FUTURE-MAYBE](../FUTURE-MAYBE.md) "Intermittent `ERR_CONNECTION_CLOSED` on api.bex.co mutations" (first seen `w1/071`, 2026-08-19), by `/pm-brainstorm for w3` 2026-10-19 item 2.

## Recurrences

- `w4/done/138.md:114,154` (2026-09-22): one read failed with `ERR_CONNECTION_CLOSED` between two good reads.
- `w4/done/293.md:66` (2026-10-17): four transient GraphQL `ERR_CONNECTION_CLOSED` console errors, not attributed.
- `w4/done/368.md:39` (2026-10-19 UTC, loop runs 1–2): "Recurring `ERR_CONNECTION_CLOSED` / one CORS console error on `api.bex.co/graphql` amid hundreds of 200s"; preflight CORS headers are correct; watch-list only.

## Lead (unproven)

- `newHTTPServer` (`lego/backend/cmd/api/main.go:1430-1436`) sets `ReadTimeout: 30s` and **no** `IdleTimeout`; Go then uses `ReadTimeout` as the keep-alive idle timeout, so bex-api closes an idle upstream connection after 30s.
- Nothing in `deploy/gitops` sets a Traefik `ServersTransport` (`forwardingTimeouts.idleConnTimeout`), so Traefik keeps idle upstream connections in its pool for its default 90s.
- A request Traefik sends on a connection bex-api has just closed fails; Go's transport retries that only for idempotent requests, and GraphQL is always `POST`, so Traefik answers a 502 — with no CORS headers, which the browser reports as a CORS/network error.
- The dashboard's `shouldRetry` (`dashboard/src/common/apollo/retry-link.ts:33-35`) retries queries only, so reads self-heal and mutations surface — matching "mutations failed, reads were fine" from `w1/071`.

## Steps

1. **Within Prometheus's 3-day retention** (`deploy/gitops/base/prometheus.yaml:230`), take a sighting window from the running w4 QA loop (or reproduce one) and run the FUTURE-MAYBE correlation recipe: `sum by (code) (increase(traefik_service_requests_total{service=~"bex-system-bex-api-.*"}[1m]))` (edge) against `sum by (status) (increase(bex_api_http_requests_total{surface="graphql"}[1m]))` (origin), plus `bex_api_graphql_operation_duration_seconds_count` for the failing operation.
2. **Edge 502 with no matching origin request** ⇒ the idle race above: give `newHTTPServer` an explicit `IdleTimeout` longer than Traefik's upstream pool idle (or add a Traefik `ServersTransport` whose `idleConnTimeout` is below bex-api's), with a test that idles an upstream connection past 30s and then sends a `POST` through the same transport configuration.
3. **Origin completed 2xx under a closed browser connection** ⇒ the edge/LB keep-alive race the FUTURE-MAYBE entry describes; record the evidence and promote to a milestone (idempotency keys become a question).
4. **Anything else** ⇒ record the evidence here and promote.
5. Update the FUTURE-MAYBE entry with the result.
