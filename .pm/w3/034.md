# Datastore deleting-read parity: fold Postgres/Key Value onto consistent-absence (adjacent m81 gap)

**Type:** parity follow-up (filed by w3/m81/t005, not folded in). **Touches:** `lego/backend/internal/postgres/`, `lego/backend/internal/keyvalue/`, ADR006/ADR009/ADR021/ADR018. **Blast radius:** small — the same by-id read gate m81 added for services, applied to the two datastore families.

## Problem

w3/m81 gave **services** one coherent deleting-read contract: the instant an App carries a `DeletionTimestamp`, every by-id surface (`GET /v1/services/{id}` + `/routes`/`/headers`/`/deploys`, GraphQL `server`/`service`, MCP `get_service`) returns `not found`, matching `List` (which already omits deleting rows) and Render's `GET 404`. The dead-URL and finalizer-overrun halves were the service-specific driver.

The **datastore** families were deliberately scoped out. Postgres (`Database`) and Key Value (`KeyValue`) still carry the w2/m61 by-id `deleting` projection while their `List` drops the row (w6/m129's `terminating` reconciliation covers all three families) — the **same list-drops-but-by-id-shows-deleting incoherence** m81 fixed for services. It is defensible-but-not-decided: neither datastore advertises a platform serving URL that can go stale, so the "dead URL" symptom does not apply, and a longer visible `deleting` window during irreversible data destruction is arguably more honest. But it is a **cross-family inconsistency** (services 404, datastores `deleting`) that a tenant can observe, so it should be a recorded decision, not an accident.

## Options

1. **Fold onto consistent-absence** — add `core.NotFoundIfDeleting(a)` after `AuthorizeApp` in the Postgres/Key Value by-id read verbs (get + connection-info), so all three families answer `not found` uniformly. Smallest change; matches Render's own datastore delete → 404.
2. **Keep `deleting` deliberately for datastores** — document the split in ADR006/ADR018 as an intentional divergence: services (URL-bearing, edge-served) go absent immediately; datastores show a bounded `deleting` because their teardown (CNPG cluster + Barman purge Job / Valkey RDB purge) is a longer, data-destroying operation worth surfacing. Requires the same finalizer-overrun bound (`DeletionStalled`-equivalent) m81 added, or the `deleting` state can hang unbounded exactly as the service one did.

## Recommendation

Verify Render's live datastore delete behavior (does a deleted Postgres/Key Value reach `GET 404`, and how fast?), then pick option 1 if Render 404s (parity) or option 2 with an explicit divergence note + a datastore finalizer bound if a visible `deleting` is genuinely wanted. Do **not** leave the current unbounded, undocumented `deleting`-by-id + list-drop split standing — that is the same shape as the m81 incident, just on a different noun.
