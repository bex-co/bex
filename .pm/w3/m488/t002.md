## Objective

The request that fills the cache (MISS or EXPIRED) gets a 304 when its validator matches the upstream's response, while the cache still stores the full body; waiters on the same fill go through t001's path.

## Context

- `fetch` (`edgecache.go` ~278-333) strips `If-None-Match` and `If-Modified-Since` before going upstream (`:321-322`, so the stored body suits every client) and tees the upstream response straight to the leader's client.
- `decide` (the ReverseProxy's `ModifyResponse`, ~340) sees the upstream headers before the body.
- So today, turning caching on turns an app's own 304s into full 200s on every cacheable path; those bytes leave through the pod's eth0, which the bandwidth meter counts against the plan's included bandwidth (w6/m319, `docs/ADR030-pricing.md` §14).

## Steps

1. In `decide`, when the leader's original request carried a validator that matches the upstream response, write 304 to the client and send the body only into the store.
2. Keep `CF-Cache-Status: MISS` / `EXPIRED` on that response.
3. Unit tests for both statuses, for a non-matching validator (full 200), and for an upstream that is not storable (no change from today).
