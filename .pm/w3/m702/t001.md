## Objective

Make `pg_duckdb.so` in every operand that carries it (16, 17, 18) find `libduckdb.so` in its own directory. Then the copy CloudNativePG's major-upgrade Job makes under `/controller/old/usr/lib/postgresql/<major>/lib/` starts with `pg_duckdb` preloaded on the target image, and the image gate proves it.

## Context

- `deploy/pg-operand/Dockerfile`, stage `duckdb`, copies `pg_duckdb.so` and `libduckdb*.so*` into the pkglibdir as upstream's `pgduckdb/pgduckdb:<major>-v1.1.1` built them. pg_duckdb's `Makefile` links with `-Wl,-rpath,$(PG_LIB)/`, an absolute `/usr/lib/postgresql/<major>/lib/` (milestone README § Three causes).
- CloudNativePG 1.30.1's `instance upgrade prepare` runs `cp -a` on bindir, pkglibdir and sharedir into `/controller/old/<same path>`, so `libduckdb.so` sits beside the copied `pg_duckdb.so`. Only the lookup is wrong.
- `$ORIGIN` is shorter than the absolute path, so either `patchelf --set-rpath '$ORIGIN'` or `chrpath -r '$ORIGIN'` works. Install the tool in the throwaway `duckdb` stage only, never in the final image.
- The final stage already runs `ldd "/usr/lib/postgresql/${PG_MAJOR}/lib"/*.so | { ! grep 'not found'; }`, which cannot see this bug: there the absolute path exists.
- `deploy/pg-operand/check.sh` / `gate.sh` hold the per-extension gate that `pg-operand-image.yml` runs on arm64 and natively on amd64. `operand_test.py` holds the recipe's unit tests.

## Steps

1. In the `duckdb` stage, set `pg_duckdb.so`'s RUNPATH to `$ORIGIN` before the `chown`/`chmod`. Explain why in a comment that cites CloudNativePG's `prepare` copy.
2. Add a build-time check in the final stage that relocates the library. Copy the pkglibdir to a scratch prefix and require that `ldd <scratch>/pg_duckdb.so` resolves `libduckdb.so` to `<scratch>/libduckdb.so`. A plain `ldd` of the original is not enough. Do it on majors that carry `pg_duckdb` only, and remove the scratch copy.
3. Better still, in `gate.sh`: copy bindir, pkglibdir and sharedir under `/tmp/old` as `prepare` does, and start the copied server on a scratch data directory with `shared_preload_libraries = 'pg_duckdb'`. Then hide the original path, the way the target image lacks it, and check the server starts. Use this if the gate's harness allows it; otherwise step 2 alone.
4. Record in `deploy/pg-operand/README.md` why the RUNPATH is `$ORIGIN`.
5. Build one major locally (`docker build` with the 16 row of `matrix.json`, arm64 is enough). Confirm the relocation check fails without step 1 and passes with it.

## Acceptance criteria

- [ ] On a local 16 build, `readelf -d` (or the relocation check) shows `pg_duckdb.so`'s RUNPATH as `$ORIGIN`. A relocated copy resolves `libduckdb.so` beside itself.
- [ ] The build fails when the RUNPATH step is removed (verified once locally).
- [ ] `python3 -B -m unittest discover -s deploy/pg-operand -p '*_test.py'` passes, and `bash -n` passes on the edited scripts.
