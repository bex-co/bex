## Objective

While a Database's major upgrade is pending, project the bex operand's extension settings of the major the cluster still runs. That means the preload, `output_plugin_libraries`, `duckdb.*` and the allowlist. Project the target's once the target is observed. The old server that `pg_upgrade` starts then reads only settings it knows.

## Context

- `cnpgClusterSpec` (`lego/operator/internal/controller/database_controller.go`, near `extensionsMajor`) takes the extension major from `p.version` for a versioned Database. That is the target as soon as bex-api accepts an upgrade, so the source's instance manager rewrites its `custom.conf` with the target's preload (milestone README § How CloudNativePG 1.30.1 runs the upgrade).
- `majorUpgradePending(desired, observed)` (`database_controller.go`) already defines "accepted, not running yet". `db.Status.CurrentVersion` moves to the target only once the upgraded cluster is healthy, and a failed run returns `spec.version` to the source. So `majorUpgradePending(p.version, p.runningVersion)` holds from acceptance to a healthy target.
- The logical-replication settings already follow the running major (`runningMajor`, `database_subscription.go`; `syncsLogicalSlots`, `database_publication.go`). This task gives the extension settings the same rule.
- What each source gets while pending:
  - 13: no `pg_duckdb`, no `duckdb.*` and no `output_plugin_libraries`;
  - 14 and 15: no `pg_duckdb` and no `duckdb.*`;
  - 16 and 17: the same as 18, so nothing changes.
  - The image stays the target's. `pgExtensionPreloadLibraries` and `pgExtensionParameters` are already keyed by major.
- After the upgrade from 13–15, `pg_duckdb` joins `shared_preload_libraries`, and CloudNativePG restarts the instance for it. `lastUpgradeRun` reads `SUCCEEDED` as soon as `status.currentVersion` reaches the target (`upgradeRunState`, `lego/backend/internal/postgres/upgrade_run.go`), so that restart can come after the run reads succeeded. Keep the Database out of Ready while that restart rolls (see how `restartPending` and `resourcesPending` hold it), or record why not.
- Read replicas copy the primary's `parameters` and `shared_preload_libraries` (`database_replicas.go`), and wait while an upgrade is pending (`readReplicaSourceOf`). Check that they follow, and add a case if they do not.
- On a failed run, `spec.version` returns to the source, and the projection is what the cluster ran before, so no extra restart.

## Steps

1. Derive the extension major as the observed one while `majorUpgradePending(p.version, p.runningVersion)` holds, and keep the image the target's. Keep the unversioned-Database path (`unversionedOperandImage`, `unobservedOperandPostgresql`) unchanged.
2. Table test over every source 13–17 and every target above it, with an observed source and a pending target. The projected `shared_preload_libraries` is a subset of what `pgExtensionPreloadLibraries(source)` names (the libraries that source's operand carries). `output_plugin_libraries` is absent for source 13. With `runningVersion` equal to the target, the projection equals a fresh target's.
3. A case for a failed run (`spec.version` back to the source): the projection equals the pre-upgrade one.
4. Handle the post-upgrade restart from 13–15 as above, with a test.
5. Amend ADR092 D4 (a preload change after an upgrade from 13–15 is one more restart) and ADR009 § Major-version upgrades (the rule).
6. `make test` and `make lint` from `lego/operator/`.

## Acceptance criteria

- [ ] The table test fails before the change (15 → 18 preloads `pg_duckdb`; 13 → 18 sets `output_plugin_libraries`) and passes after.
- [ ] A 16 → 18 or 17 → 18 projection while pending equals 18's, so it adds no restart.
- [ ] `make test` and `make lint` pass.

## Out of scope
