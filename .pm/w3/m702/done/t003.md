## Objective

While a Database's major upgrade is pending, project the bex operand's extension settings of the major the cluster still runs. That means the preload, `output_plugin_libraries`, `duckdb.*` and the allowlist. Project the target's once the target is observed. The old server that `pg_upgrade` starts then reads only settings it knows.

## Context

- `cnpgClusterSpec` (`lego/operator/internal/controller/database_controller.go`, near `extensionsMajor`) takes the extension major from `p.version` for a versioned Database. That is the target as soon as bex-api accepts an upgrade, so the source's instance manager rewrites its `custom.conf` with the target's preload (milestone README § How CloudNativePG 1.30.1 runs the upgrade).
- `majorUpgradePending(desired, observed)` (`database_controller.go`) already defines "accepted, not running yet". `db.Status.CurrentVersion` moves to the target only once the upgraded cluster is healthy, and a failed run returns `spec.version` to the source. So `majorUpgradePending(p.version, p.runningVersion)` holds from acceptance to a healthy target.
- The logical-replication settings already follow the running major (`runningMajor`, `database_subscription.go`; `syncsLogicalSlots`, `database_publication.go`). This task gives the extension settings the same rule.
- What each source gets while pending:
  - 13: no `pg_duckdb`, no `duckdb.*` and no `output_plugin_libraries`;
  - 14 and 15: no `pg_duckdb` and no `duckdb.*`;
  - 16 and 17: the same as 18, so nothing changes.
  - The image stays the target's. `pgExtensionPreloadLibraries` and `pgExtensionParameters` are already keyed by major.
- After the upgrade from 13–15, `pg_duckdb` joins `shared_preload_libraries`, and CloudNativePG restarts the instance for it. `lastUpgradeRun` reads `SUCCEEDED` as soon as `status.currentVersion` reaches the target (`upgradeRunState`, `lego/backend/internal/postgres/upgrade_run.go`), so that restart can come after the run reads succeeded. Keep the Database out of Ready while that restart rolls (see how `restartPending` and `resourcesPending` hold it), or record why not.
- Read replicas copy the primary's `parameters` and `shared_preload_libraries` (`database_replicas.go`), and wait while an upgrade is pending (`readReplicaSourceOf`). Check that they follow, and add a case if they do not.
- On a failed run, `spec.version` returns to the source, and the projection is what the cluster ran before, so no extra restart.

## Steps

1. Derive the extension major as the observed one while `majorUpgradePending(p.version, p.runningVersion)` holds, and keep the image the target's. Keep the unversioned-Database path (`unversionedOperandImage`, `unobservedOperandPostgresql`) unchanged.
2. Table test over every source 13–17 and every target above it, with an observed source and a pending target. The projected `shared_preload_libraries` is a subset of what `pgExtensionPreloadLibraries(source)` names (the libraries that source's operand carries). `output_plugin_libraries` is absent for source 13. With `runningVersion` equal to the target, the projection equals a fresh target's.
3. A case for a failed run (`spec.version` back to the source): the projection equals the pre-upgrade one.
4. Handle the post-upgrade restart from 13–15 as above, with a test.
5. Amend ADR092 D4 (a preload change after an upgrade from 13–15 is one more restart) and ADR009 § Major-version upgrades (the rule).
6. `make test` and `make lint` from `lego/operator/`.

## Record (2026-11-27)

- **The rule:** `pendingUpgradeSource` (`database_controller.go`) takes the source as the major CNPG reports the data directory holds, `status.pgDataImageInfo.majorVersion` (read into `clusterParams.dataVersion` from the live Cluster), falling back to `status.currentVersion`. While `majorUpgradePending(spec.version, source)` holds, `clusterOperand` keeps the target's image and projects the source's operand settings: preload, `output_plugin_libraries`, `duckdb.*` and allowlist, or none of them when the source runs an upstream image. The unversioned path is unchanged, only moved into `clusterOperand` (`cnpgClusterSpec` passed gocyclo's limit of 30 otherwise). `clusterDataMajor` now serves the readiness read and the read replicas too.
- **Deviation from step 1, and why step 4 needs no hold:** the data directory's major, not `status.currentVersion`, decides when the target's settings return. CNPG 1.30.1's `majorVersionUpgradeHandleCompletion` (`pkg/reconciler/majorupgrade/reconciler.go`) patches `pgDataImageInfo` to the target as soon as the Job succeeds, then deletes the Job with foreground propagation and only afterwards creates the target's instance Pod, whose instance manager writes `custom.conf` from the Cluster at start. The Cluster watch (`ResourceVersionChangedPredicate`) lands the target's settings in that gap, so the instance starts with `pg_duckdb` preloaded and there is no second restart to hold Ready through. `status.currentVersion` moves only once the instance is ready, so switching on it would have made that restart certain. t004's 13 → 18 and 15 → 18 runs on dev-3 show it: the Cluster gained `pg_duckdb` in the same 2 s sample in which `pgDataImageInfo` read 18 and the new Pod was `Pending`, the postmaster started 2 s after the container (`pg_postmaster_start_time` 11:35:12 / 11:41:01) with 0 container restarts, and it had not restarted a minute later. Were the Pod ever to start first, CloudNativePG applies the preload with one in-place restart.
- **Read replicas follow without a case of their own:** `readReplicaSourceOf` leaves them alone while an upgrade is accepted or running (`TestReadReplicaSourceSettles` rows "upgrade accepted, not started" and "upgrade running") and copies the primary's live spec once it is settled, which is then the target's.
- **Tests:** `TestPendingMajorUpgradeCarriesTheSourcesOperandSettings` (every source 13–17 and target above it: the pending projection is the source's own settings with the target's image, preloads only what the source's operand carries, no `output_plugin_libraries` on 13, no `duckdb.*` below 16, 16/17 differing from 18 only in the allowlist; the target's own settings once the data directory reports it; the fallback; an upstream source) and `TestReconcileKeepsTheSourcesPreloadUntilPgUpgradeSucceeds` (15 → 18 through the reconcile, succeeding and failing). With the rule reverted both fail (15 → 18 pending sets `duckdb.threads` and preloads `pg_duckdb`, 13 → 18 sets `output_plugin_libraries`). `make test` and `make lint` pass.
- **Docs:** ADR009 § Major-version upgrades (The old server runs the source's settings) and ADR092 D4 (An upgrade adds no restart).
- **Addendum (2026-11-27, found by t004):** a 16 database with `pg_duckdb` installed still failed in `pg_upgrade`'s schema restore, `ALTER SEQUENCE duckdb.extensions_table_seq OWNER TO postgres` → `(PGDuckDB/DuckdbUtilityHook_Cpp) Not implemented Error: Writing to DuckDB and Postgres tables in the same transaction block is not supported` (`pg_upgrade_dump_<oid>.log`). That is pg_duckdb 1.1.1 taking the extension's sequence for a DuckDB table before its access method is restored (duckdb/pg_duckdb#1074, open, no fix in 1.2.2). While an upgrade from a source that carries `pg_duckdb` is pending, the Cluster now also sets `duckdb.unsafe_allow_mixed_transactions = true` (`pgUpgradeMixedTransactions`, `database_operand.go`). It is `PGC_USERSET`, so it gives no role anything it could not already set for its own session, and the target's own settings drop it before the target's instance starts. The table test holds it on every 16+ source and its absence from every target's own settings; `carriesPgDuckdb` replaces the two copies of the 16/17/18 check.
