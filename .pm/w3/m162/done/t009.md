## Objective

When the services inventory collector fails to list App CRs from Kubernetes, it still writes a snapshot stamped `complete=true`. The resource **count** stays correct because existence comes from Postgres, but every **state** degrades to `unknown` while the batch claims to be authoritative. A future reader cannot tell a collector outage from a real platform outage. Record the failure honestly.

## Context

- `lego/backend/internal/store/product_inventory.go:81-91` — the `complete=false` failure-marker branch explicitly excludes `source == "services"`; the code falls through to `items = nil` and a normal record.
- `:254-255` — `recordProductInventory` writes `complete=true` unconditionally.
- `:310-314` — for services the sample is built from the `apps` table LEFT JOINed against the payload, so a nil payload yields correct ids with `COALESCE(x.state,'unknown')` for every row.
- The split is deliberate and correct ("Postgres owns App existence even when Kubernetes cannot report readiness") — existence and state have different sources and different trust. The defect is that one `complete` flag is used to describe both.
- **Latent, not firing.** Historical check across all `source='services'` buckets: `unknown` appears once, for a single resource; there is no all-`unknown` bucket. This is a pre-emptive fix.

## Steps

1. Decide the representation and apply it consistently: either write `complete=false` for the batch when the list failed, or add a separate marker (e.g. a `state_source` column on `product_inventory_batches`) recording that the state dimension is untrusted while existence is fine. Prefer the second if any consumer relies on `complete=true` for count continuity.
2. Whichever is chosen, make sure the count series stays unbroken — the point is to label state as untrusted, not to drop the snapshot.
3. Make the distinction visible to readers by exposing it through `product_analytics.inventory_batches`.
