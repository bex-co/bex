## Objective

Deleting a workspace makes its final Stripe lifecycle webhook fail forever. `deleteWorkspace` cancels the Stripe subscription first (which makes Stripe emit `customer.subscription.deleted`) and then drops the tenant row, cascading `billing_provider_mappings` away. When Stripe delivers the event, the handler tries to write a mapping whose foreign-key target no longer exists, returns 503, and Stripe retries for up to three days. Treat a billing event for a workspace that no longer exists as benign and acknowledge it.

## Context

- Live failure, production, 2026-09-16 23:27:34:
  `billing: Stripe lifecycle handler event=evt_1UGSEjEqsEqs2tLVTHfQYNzv type=customer.subscription.deleted: verify billing mapping: ERROR: insert or update on table "billing_provider_mappings" violates foreign key constraint "billing_provider_mappings_workspace_id_fkey" (SQLSTATE 23503)`
- Metrics confirm it: `bex_api_http_requests_total{route="POST /v1/webhooks/stripe",status="503"} 1` and `bex_billing_operations_total{operation="webhook_handler",result="error"} 1`; the Stripe event still reports `pending_webhooks=1`.
- Ordering that causes it: `lego/backend/internal/workspaces/service.go:1199-1202` — `PreCascadePurgers` (which include `CancelContract`) run, then `DeleteTenant`.
- `lego/backend/internal/billing/contracts.go:127-150` — `CancelContract` is what triggers the Stripe event.
- The benign-ignore precedent already exists: `lego/backend/internal/billing/lifecycle.go:70-73` returns `nil` for `errNotBexBillingContract`.
- Same pattern already happened on 2026-09-05 for `tea-dadkqjrr12dc73ba2hg0`.
- **Risk this closes:** Stripe disables endpoints that fail persistently. A disabled endpoint silently drops `checkout.session.completed`, which is the sole writer of `payment_method_bound_at` (`billing/sessions.go:228-232`) — real customers would be locked out with no trace.

## Steps

1. In `store.RecordStripeBillingEvent`, detect the foreign-key violation on `billing_provider_mappings_workspace_id_fkey` (pgx `*pgconn.PgError` with `Code == "23503"`) and translate it to `ErrNotFound` rather than letting the raw error escape. Do not broaden this to every 23503 — match the constraint name so an unrelated FK bug stays loud.
2. In `Lifecycle.HandleStripeEvent` (`billing/lifecycle.go:56-78`), treat that `ErrNotFound` the same way `errNotBexBillingContract` is treated: `return nil` so the webhook answers 204.
3. Make sure the ignore is only for a genuinely absent workspace — an existing workspace whose write fails for any other reason must still return an error so Stripe retries.
4. Verify the stuck event converges: watch `bex_api_http_requests_total{route="POST /v1/webhooks/stripe"}` and confirm the Stripe event's `pending_webhooks` reaches 0.

## Out of scope

- Reordering `deleteWorkspace` so cancellation happens after the cascade — the event would still race delivery, and the pre-cascade ordering is load-bearing (`service.go:1193-1198` explains why the purgers need the rows to still exist).
- The Stripe-side cleanup that deletion also misses — that is t002.
