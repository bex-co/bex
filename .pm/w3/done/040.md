# 040 — The tenant-view canary's unexplained stage-3 passes

Why: the stage-3 budget shipped (`w7/054`, `BEX_CANARY_METRIC_BUDGET`, default 120s), which makes the probe correct — and also makes the one thing nobody understands about it permanently unobservable, so it should survive the fix with a trigger instead of dying inside a closed note.

## What is established

A pod alive ~12s cannot put two cpu samples inside a `[60s]` rate lookback (`rate()` at `lego/backend/internal/metrics/source.go:282`, cAdvisor scraping every 15s at `deploy/gitops/base/prometheus.yaml:256`). That explains every stage-3 **failure**.

## What is not

It does not explain the **passes**. Three of seven consecutive production runs passed stage 3 at what should have been the same pod age — run `35153705860` (2026-09-16T21:40:48Z) had a 9s wake and passed cleanly, cpu _and_ memory carrying samples. By the mechanism above it should have failed. Something had already started that pod before the probe's request, in at least three runs, and nobody knows what.

Wake duration does not discriminate: across seven runs a 9s wake produced three passes and two failures, while both 12s wakes failed.

Candidates, none probed:

- unrelated inbound traffic to `hello-go.onbex.co` inside the preceding hour (a public host attracts scanners);
- the activator holding the pod past its 15m idle TTL under some condition;
- the 1-hour default query window catching a still-recent earlier wake.

The decisive measurement is **the pod's age at stage-3 query time**, which no run records.

## Trigger

Stage 3 fails again **with** the 120s budget in place, **or** any work next touches activator idle/TTL behavior. Then record pod age at query time and settle it.

## Explicitly not

The 0–3s fixture test the original note owed was withdrawn there and stays withdrawn — it was the right test for a theory that was already falsified. What a fixture would still add is the exact pod-age threshold where cpu starts returning points: a nice-to-have, not a blocker.
