# A log explorer's range picker lists Render's log ranges, without Last 30 minutes and Last 12 hours

Why: Render's log explorers offer Live tail, Last hour, Last 4 hours, Last 24 hours, Last 2 days, Last 7 days, Last 14 days, Last 30 days and Custom; bex's log explorers share Metrics' ladder and add Last 30 minutes and Last 12 hours, so a Render user sees two ranges Render's Logs never lists.

Found by w3/m537 t007's parity check (2026-11-20). Render's dashboard bundle (`log-filters-1FeMUC1z.js`, read 2026-11-20) lists the log explorer's ranges as `logTimeRangeIntervals: ["live","1h","4h","24h","2d","7d","14d","30d"]`, and the capture's [§ The view page](../../docs/render-artifacts/project-observability.md#the-view-page) records the same list. Render's Metrics page keeps its own ladder with `30m` and `12h` (`metrics-*.js`, `"30m": "Last 30 min"` … `"30d"`), which is the one bex's `RANGE_PRESETS` (`dashboard/src/features/metrics/lib/range.ts`) follows for both.

The log explorers draw their picker through `LogRangeSelect` (`dashboard/src/features/logs/components/log-range-select.tsx`), which wraps the shared `RangeSelect` (`features/metrics/components/range-select.tsx`).

Done when the service Logs tab, a Postgres or Key Value Logs tab and a project's Application Logs and Request Logs views list exactly Render's log ranges (Live tail, the seven presets from Last hour to Last 30 days, Custom), Metrics keeps its own ladder, an old link naming `30m` or `12h` on a log explorer opens on the nearest Render range (as `15m` and `6h` already do through `RENDER_RANGE_ALIASES` in `features/logs/lib/log-search.ts`), and a test pins both lists.

**Done 2026-11-25.** Every log explorer's picker (the service Logs tab's `LogFilterBar`, the Postgres and Key Value `DatastoreLogViewer`, a project's `ProjectLogViewer`) draws through `LogRangeSelect`, which now passes `LOG_RANGE_PRESETS` (`features/logs/lib/log-range.ts`: `1h`, `4h`, `24h`, `2d`, `7d`, `14d`, `30d`, Render's `logTimeRangeIntervals` after `live`) to `RangeSelect`'s new `presets` prop; Metrics keeps `RANGE_PRESETS`. `toLogRange` reads Metrics' `30m` as Last hour and `12h` as Last 24 hours (nearest on the ladder's ratio scale, and covering the window the link named), applied where a log explorer reads its range (`logRangeFromSearch` for the service and datastore tabs, `projectLogRange` for a project view, its saved `timeRange.relative` included), so an old `range=30m`/`range=12h`/`r=12h` link opens on a listed range, and Render's `r=15m` now lands on Last hour. The URL keys still accept `30m` and `12h` because a Key Value's Metrics tab and a project's Service Metrics view share them. Render's Edit view lists the same ranges (`value !== "live" && value !== "custom"`), so a log view's Time Range offers the seven, a stored `30m`/`12h` shows as itself, and a Service Metrics view keeps the nine; bex-api still accepts all nine for every view type (`internal/savedsearch/document.go`). Pinned by `log-range.test.ts` (both lists and the mapping), `log-filter-bar.test.tsx`, `datastore-log-viewer.test.tsx` and `project-log-viewer.test.tsx` (each picker's exact options), `log-search.test.ts`, `project-log-search.test.ts` and `edit-view-dialog.test.tsx`; every new assertion fails with the old ladder and an identity `toLogRange`.
