## Objective

Gate every move whose source or target environment is protected on a fresh workspace-manage check, including environment `Set*` membership changes that pull a resource out of a protected environment into another one or into Unassigned.

## Context

- `setResourceMembers` checks only the target (`internal/environments/service.go:1209-1225`)
- Per-resource `SetEnvironmentID` checks `RelCanCreate` (`internal/postgres/service.go:1948`, `internal/keyvalue/service.go:890`, `internal/envgroups/service.go:678`)
- Project moves drop the environment (`SetProjectID`)
- **Result (2026-11-07):** move-out was already gated on every writer by `loadExitGuard` (w4/m232). It now answers the placement code when the source is protected, and keeps plain `FORBIDDEN` for an environment that is only isolated or allow-listed. Move-in on the environment `Set*` verbs was already gated by `authorizeACLBearingMutation` on an ACL-bearing target. It now goes through `authorizeMembershipChange`, which also uses the placement code for a protected target. The one ungated move-in, `envgroups.MoveEnvGroup`'s target, now resolves through the create resolver; a group that stays put skips the check. Project moves leave through the exit guard. Per-resource `SetEnvironmentID` is reached only from the environments feature, so a second gate there was not added. Tests: `TestMovingAServiceIntoOrOutOfAProtectedEnvironmentNeedsAnAdmin`, `TestMovingADatastoreIntoAProtectedEnvironmentNeedsAnAdmin`, `TestLeavingAnIsolatedButUnprotectedEnvironmentKeepsItsPlainRefusal`, and the PG surface test (REST `POST/DELETE /v1/environments/{id}/resources`, GraphQL `moveEnvGroup`/`setEnvironmentServices`, MCP `move_env_group`).

## Steps

1. Add a `move` restricted verb.
2. In `setResourceMembers` and `SetServices`, check each changed member's source environment as well as the target.
3. Cover project moves that detach a resource from a protected environment.
