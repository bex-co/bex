## Objective

Check the change is consistent on every surface it exposes — REST, GraphQL and MCP in `lego/backend/` (same fields, semantics and error shapes) and the `dashboard/` UI — against render.com's behavior, and file any drift as follow-up work rather than silently diverging.

## Context

- Placement surfaces: REST create routes with `environmentId`, GraphQL `create*`/`set*` mutations, MCP create tools, dashboard wizards and move dialogs
- `docs/ADR006-bex-api.md`, `docs/ADR018-render-parity.md`, `dashboard/AGENTS.md`
- **Result (2026-11-07):** REST, GraphQL and MCP return the same coded 403. The params are `{environmentId}` on REST and in the GraphQL extensions; MCP's text starts with `PROTECTED_ENVIRONMENT_ADMIN_REQUIRED: `. All three are exercised by `TestProtectedEnvironmentPlacementNeedsAnAdminOnEverySurfacePG`. The dashboard disables the same placements by the same relation (`can_manage`) and maps the code to the same reason. Render (render.com/docs/projects, fetched 2026-11-07) restricts create in, and move into or out of, a protected environment to Admins, with the Blueprint exception for updates to existing resources. Drift found and not fixed here (no `.pm` filing per this run's limits; reported to the caller):
  1. ADR018 row 225's older w4/m127 sentence ("Render's own protected environments gate deletion and suspension only") and its w5/m31 "typed retry" sentence are stale since w8/187.
  2. A Blueprint auto-sync that would add a resource to a protected environment now fails until an Admin syncs manually. Render's behavior for a push-triggered sync is undocumented.
  3. A create URL that preselects a protected environment keeps it selected, shown disabled, for a non-Admin. The submit then shows the reason.

## Steps

1. Exercise each surface for the behavior this milestone changed.
2. Compare against Render's documented behavior and the pinned schema.
3. Record the result in ADR018 and file any drift as a w3 inbox note.
