## Objective

Check that the changed exit is consistent across every surface it touches, and compare against Render's equivalent behavior, flagging drift as follow-up rather than diverging silently.

## Context

- The change is dashboard-only, but it invokes account deletion, which has REST/GraphQL/MCP surfaces that must agree on semantics and error shape (`docs/ADR006-bex-api.md`).
- Render has no self-host exit at all — bex being open source is a genuine divergence, not a parity gap. The parity question is narrower: does account deletion behave and report consistently across surfaces.

## Steps

1. Confirm the deletion verb the wall calls has the same semantics and error shape on REST, GraphQL, and MCP.
2. Compare account deletion against Render's equivalent and note any real drift.
3. File anything found as follow-up work; do not silently diverge.

## Files

- `lego/backend/internal/accounts/`
- `docs/ADR018-render-parity.md` if a row needs updating

## Acceptance criteria

- [x] Deletion semantics and error shapes agree across REST, GraphQL, and MCP.
- [x] Drift against Render is recorded, with the self-host exit noted as a deliberate bex-only path.

## Out of scope

- Changing the deletion verb's contract.

## Outcome

No drift. This milestone changed no API surface — the wall calls the existing
`deleteAccount` mutation and nothing in `internal/accounts/` or `internal/api/` was
touched (`git diff --name-only` confirms).

Worth recording for the parity ledger: `deleteAccount` exists **only** on GraphQL —
there is no REST route and no MCP tool for it. That matches Render, whose public API
likewise exposes no account-deletion endpoint; account deletion is a dashboard-only
operation on both platforms. So the single-surface shape is a deliberate match, not a
gap, and needs no follow-up.

The self-host exit itself has no Render counterpart at all — bex being open source is
the divergence, and it is the whole point of ADR075 § Positioning.
