# 042 — Nothing watches whether the watchers ran on time

Why: `ci-red-streak.sh` catches a workflow that is persistently red, but a scheduled probe that is **green and ran four hours late** is invisible to it — and that is exactly the failure `w7/055` measured, where nine consecutive runs drifted 3h04m–5h27m and half the gaps blew past the advertised window.

## The gap, precisely

Two watchers exist and neither covers this:

- `scripts/ci-red-streak.sh` (`6775f4f90`) counts **consecutive failures** per workflow on main. A late run that passes resets nothing and triggers nothing.
- `scripts/cli-release-staleness.sh` and `scripts/build-toolchain-freshness.sh` watch the age of a specific artifact, not a workflow's own cadence.

The drift is invisible from any single run — each passes or fails on its own merits, and only the sequence shows the advertised window is not met. It took a manual read of run history to find it once; nothing stops that from being the detection method next time.

## Shape

`scripts/ci-schedule-drift.sh`, a sibling of `ci-red-streak.sh` and following its conventions exactly:

- per workflow with a `schedule` trigger, fetch recent `event: schedule` runs, compute consecutive-run gaps, compare against a declared window;
- declare the windows in **one** place, so adding a scheduled probe without a window is visible rather than silently unwatched;
- one tracking issue, opened / updated / closed, as `ci-red-streak.yml` does;
- deliberately **not** a required gate — binding releases to an advisory checker is a worse trade than the problem, the same call `ci-red-streak` made;
- `scripts/ci-schedule-drift.test.sh` wired into `scripts (test)`, covering the cases that decide whether it reports anything at all: a workflow with one scheduled run (no gap computable), a workflow with **zero** scheduled runs (never fired — the worst case, and the one a naive gap computation reads as healthy), and a `workflow_dispatch` run that must not be counted as a scheduled one.

Nine scheduled workflows exist today (`ssh-edge-liveness`, `deploy-canary`, `isolation-matrix`, `infra`, `ci-red-streak`, `cli-release-staleness`, `build-toolchain-freshness`, `render-schema-drift`, plus the drill workflows); `w7/055` measured only the first and said so.

## Parked 2026-09-16 by `/loopx w3` — blocked on `w7/055`

The gate is the **number**, not the code. This checker's whole job is to compare a scheduled workflow's observed inter-run gap against an accepted window, and `w7/055` is the item that sets that window (ADR088 §6 plus the workflow/script headers). It is unblocked — the owner chose "restate honestly" on 2026-09-16 — but not yet applied.

Two shapes were weighed here and one was rejected:

- **Derive the window from each workflow's own cron period × a tolerance**, which would make this independent of `055`. Rejected: `ssh-edge-liveness` declares `37 */6 * * *` and observed gaps reach 7h28m, so a cron-derived window fires immediately against drift that `055` measured and **accepted** as GitHub-side dispatch (queue wait zero on all ten runs). That ships a checker whose first act is to contradict a decision already made.
- **Compare against the accepted window `055` publishes.** Correct, and it needs `055` to land first.

**Unblocks when:** `w7/055` publishes the window. Then this is ~60m: script, self-test, daily workflow, following `scripts/ci-red-streak.sh`'s conventions exactly.

## Done 2026-09-23 — unblocked by `w7/055`, shipped

`w7/055` closed on 2026-09-17 and published the number this was waiting on — a **12h** freshness-alert threshold for `ssh-edge-liveness.yml` — with the instruction that every other workflow needs its own sample. The block was therefore stale; picked up in a review of every `blocked/*` item.

**Shipped**, following `scripts/ci-red-streak.sh`'s conventions:

- `scripts/ci-schedule-drift.sh` — per scheduled workflow, reports **no verdict in the runs inspected** (never fired), **no verdict for longer than the window** (overdue now), or **two consecutive verdicts further apart than the window where the later one is inside a 48h lookback** (late, since recovered — a daily checker otherwise never sees a gap that closed between two of its own runs). Exit 0/1/2 like its sibling; `validate` mode fails when a scheduled workflow has no window, a window names no scheduled workflow, or a workflow is declared twice.
- The windows live in **one** table at the top of the script, each set above that workflow's own measured worst gap (2026-09-23, up to 100 `event: schedule` runs each): `ssh-edge-liveness` **12h** (055; 4h25m–9h30m since 09-05), daily `infra`/`ci-red-streak` **40h** (worst 34h24m; a skipped day still trips), weekly five **216h** (worst 178h30m; a skipped week still trips). The checker exempts itself: it cannot observe its own absence.
- `scripts/ci-schedule-drift.test.sh` — 20 cases, including the three this note named (one run, **zero** runs, `workflow_dispatch` not counted) plus cancelled and in-progress runs, the lookback edge, exempt entries, unusable input, and `validate`. Mutation spot-checked: dropping the cancelled filter or the `event == "schedule"` filter each turns a case red.
- `.github/workflows/ci-schedule-drift.yml` — daily, self-test first, one `ci-schedule-drift` issue opened/updated/closed; **not** a gate.
- `scripts (test)` runs `validate` + the self-test on every push, and shellchecks both scripts.
- `docs/ADR088-platform-observability-ui.md` §6 records the checker and the two departures below.

**Two deliberate departures from the handoff's wording, both evidence-driven:**

1. **A run counts once it reaches a verdict** (success or failure, mirroring ci-red-streak's filter), not only on success. `ssh-edge-liveness`'s gaps between *successes* reach **65h** because its probes fail often; a literal "12h without a success" fires constantly and duplicates ci-red-streak's report.
2. **Cancelled runs do not count.** The measurement found `infra (terraform)`'s daily drift schedule fired every day **2026-08-30 → 2026-09-09 and every run was cancelled** — eleven days with nothing looking, invisible to both existing watchers. Replayed against that history as of 2026-09-08, the checker reports `infra.yml` with no verdict for 239h18m. (Recovered on 09-10; recorded here, not re-filed.)

Live check against real history on 2026-09-23: `OK`, every workflow inside its window.
