## Objective

Delete the in-code per-workspace resource caps (`BEX_MAX_SERVICES`, `BEX_MAX_POSTGRES`, `BEX_MAX_KEYVALUES`) now that the per-namespace `ResourceQuota` (`count/apps.app.bex.co`, `count/databases.app.bex.co`, `count/keyvalues.app.bex.co`) provisioned per workspace enforces the same plan-tier ceilings one layer down, at the API server.

## Context

- ADR043 §82: "Per-tenant `ResourceQuota`/`LimitRange` replace the `BEX_MAX_SERVICES`/`BEX_MAX_POSTGRES`/`BEX_MAX_KEYVALUES` app-code caps — same intent, enforced one layer down."
- `lego/backend/internal/store/namespaces.go:275,311-314` — `quotaForPlan` already stamps the `count/*.app.bex.co` caps; comment: "the count/<resource> caps that retire `BEX_MAX_*`". Shipped in w3/m31.
- In-code enforcement to remove: `lego/backend/internal/apps/service.go:1523` (`if s.MaxServices > 0 …`), the postgres + keyvalue equivalents, the `apps.Service.MaxServices` field (`service.go:124`), `internal/api/server.go` `MaxServices`/`MaxPostgres`/`MaxKeyValues` deps fields (`:303`), the wiring in `cmd/api/main.go:580-582`, and `internal/store/api.go:446-452` (`LimitsFor(t.Plan).MaxServices` count query) if it becomes dead.
- Prod: these env vars are already unset (ResourceQuota does the work).

## Steps

1. Remove the `BEX_MAX_*` reads in `cmd/api/main.go` and the `MaxServices`/`MaxPostgres`/`MaxKeyValues` deps plumbing.
2. Remove the count-check blocks in `apps`/`postgres`/`keyvalue` `service.go`.
3. Delete any now-dead store helpers (`LimitsFor`-based count queries) if nothing else uses them.
4. `go build ./... && go test ./...` from `lego/backend`.
