## Objective

Make the three new push events (`server_available`, `service_suspended`, `service_resumed`) selectable in the dashboard push-policy editor and renderable/deep-linkable in the mobile client's inbox, preserving w11/m5's closed-vocabulary discipline.

## Context

- Dashboard event list: `dashboard/src/features/notifications/lib/push-policy.ts` (~8–17, currently 8 events) + client-side validation (`validatePushSettings`); panel `dashboard/src/features/notifications/components/push-notification-settings-panel.tsx`; copy in `dashboard/src/locales/en.ts`.
- Mobile: `mobile/src/features/notifications/` — the inbound envelope vocabulary is deliberately closed (ADR048 D2, w11/m5/t008 parity audit: `usage_threshold` omitted because no mobile route). The three new events deep-link to the **existing service route**, which is allowlisted — so they belong in the mobile vocabulary, unlike `usage_threshold`.
- The GraphQL enum extension lands in t001; the shared policy model must stay byte-identical across REST/GraphQL/dashboard/mobile (ADR048's one-core rule).

## Steps

1. Add the three events to `push-policy.ts` (labels via locales, e.g. "Service recovered", "Service suspended", "Service resumed") and to any per-service-override event validation.
2. Extend the mobile inbound-envelope vocabulary + inbox rendering for the three events; verify the deep-link route validates against the existing allowlist.
3. Update the w11/m5 parity-audit record (`mobile-scope-policy` test / t008 notes) so the vocabulary delta is deliberate, not drift.
4. Dashboard + mobile tests for select/persist/render.
