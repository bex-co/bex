## Live crash leg — RUN 2026-08-08 (evidence below)

Runbook: against a live cluster with a store-managed web service, a member whose push policy enables the four lifecycle events, and a registered device: (1) baseline `server_failed`/`server_available` counts on `GET /v1/services/{id}/events`; (2) break the service (image → `busybox:1.36`) via the Render-compatible image PATCH, hold ≥3 resyncs; (3) assert exactly **one** new `server_failed`; (4) restore, assert exactly **one** new `server_available` + inbox rows in `GET /v1/notifications`.

**Harness actually used** (the shared CAPD mock cluster was unusable — see findings): a dedicated single-node kind cluster (`m78-live`), host-run m78 bex-api (`BEX_CP_RESYNC=5s`, disposable docker Postgres 16 + Hydra `--dev`, allow-all authz) + host-run operator, real push transport pointed at a loopback fake Expo (`BEX_EXPO_PUSH_URL=http://127.0.0.1:19876`, the runbook's loopback affordance), device registered through the real gated REST verb, service `srv-d9re3opjg4rfgoo89tg0` (`traefik/whoami`, tier starter) in its `tea-d9re3mpjg4rfgoo89teg` namespace.

**Evidence (final clean cycle, #4):** baseline 11/11 → image→busybox PATCH 200 at 08:43:34Z → `server_failed` +1 (12/11) within one debounced resync, **held exactly 12/11 through the sustained ~2-min crash-loop** → restore PATCH 200 at 08:45:23Z → `server_available` +1 (12/12 at 08:55:42Z; recovery was honestly delayed by a real KCM outage on the harness host, correctly held as an open deploy rather than faked). Suspend/resume leg: `POST …/suspend` then `/resume` (202/202) → exactly **one** `service_suspended` + **one** `service_resumed` inbox row. Final member inbox: all four event types present; the fake Expo received 29 real sends with valid ticket/receipt round-trips (`title "Service unavailable"/"Service recovered"`, route `/services/srv-…`).

**Two platform bugs found and fixed by this leg** (the phantom-pair storm: 5 pairs in ~10 min on the flaky harness host before the fixes):

1. **Phantom Critical pages during old-ReplicaSet reaping.** A reconcile landing on stale Deployment status (KCM catch-up) reported `Ready=False`/`RolloutProgressing` for a service whose current-revision pods were all Ready; with the deploy closed, the reconciler counted any `Ready=False` as an outage → phantom `server_failed`+`server_available` pair (a real Critical push once the channel releases; also fired into outbound webhooks since w7/m66). Fixed twice over: the operator now writes reason **`RolloutSettling`** when its live pod scan shows the full current-revision complement Ready while only Deployment bookkeeping lags (`currentRevisionFullyReady`, `app_controller.go`), and `observedServiceStateFor` excludes that reason like `Suspended`/`AutoHibernated`; plus a **single-tick unhealthy debounce** in the store reconciler (`debounceUnhealthy` — first unhealthy observation is remembered but unrecorded; a second consecutive one records; recovery immediate). Both unit-tested (`TestObservedServiceStateExcludesRolloutSettling`, `TestDebounceUnhealthySuppressesSingleTickBlips`).
2. **Residual (recorded as inbox note `w3/016`):** on a host whose apiserver/etcd stall watch streams for **minutes**, the operator's cached clients (dep status + pod list) can time-travel far enough that even the fixed discrimination misfires (pairs 3s apart kept appearing between cycles on the sick harness host, never during the induced-outage windows). Healthy control planes bound informer staleness to milliseconds; further hardening (quorum-read confirmation before an unhealthy record) is follow-up, not an m78 gate.

**Environment findings** (recorded as inbox note `w3/017`): the shared CAPD mock cluster could not host the leg — its control plane was lease-thrashing under host disk latency, and more fundamentally **two dev-N control planes on one cluster mutually prune each other's `tea-*` namespaces** (each `NamespaceReconciler` deletes managed namespaces absent from its own DB — my tenant's namespace was deleted within 60s of creation by the dev-5 session's bex-api, and vice versa). The dev-N harness and ADR043's pruner are incompatible on a shared cluster.

## Definition of done

A member whose push policy enables the new events receives (as durable `push_notifications` inbox rows + `push_deliveries`, and as live pushes where the Expo transport is configured) a notification for an observed recovery (`server_available`), suspension (`service_suspended`), and resumption (`service_resumed`); the default policy's event set is **unchanged** (additive opt-in — no migration). The dashboard push-policy editor lists and persists the three new events; the mobile client renders their inbox rows and deep-links to the existing service route; MCP remains deliberately push-verb-free. A store-level E2E drives a service through Running → crash → recovery and asserts **exactly one** `server_failed` fact and **exactly one** `server_available` fact for the outage (checkpoint edge dedup across resync ticks), with the corresponding push rows enqueued. ADR052's gap-register items 1–2 are updated to point here as resolved.
