## Outcome (verified no-op)

**No code change required.** Investigation showed managed datastores are NOT namespaced under ADR043 — only App workloads move to `<ws>`:

- `internal/postgres/service.go:500` and `internal/keyvalue/service.go:409` create the Database/KeyValue CR with `Namespace: s.Namespace` (the shared `default`), with no tenant-namespace awareness.
- `internal/core/base.go` `AuthorizeDatabase` (line 687) / `AuthorizeKeyValue` Get the CR from `b.Namespace` only (not cluster-wide like `AuthorizeApp`'s `AppListScope`). If datastores lived in `<ws>`, datastore authz would 404 entirely — which no one reported.
- `DatabasePods`/`KeyValuePods` (base.go:1102/1116) list in `b.Namespace`.
- Prod check (2026-07-31): no managed tenant Database/KeyValue CRs exist; the only CNPG pods are platform ones in `auth`/`bex-system` (excluded from tenant logs).

So the datastore log reads (`queryPostgresLogs`/`queryKeyValueLogs` → `s.History(ctx, s.Namespace, q)`, and the pod paths) are already consistent with where datastore pods and Loki streams live (the shared namespace). Changing them to a `<ws>` namespace would point at an empty namespace and BREAK working behavior. Recorded the reasoning in the milestone DoD. Namespacing datastores, if ever wanted, is a coordinated create/authz/pods/logs change = a separate milestone.

## Objective

The managed-datastore log reads have the same hardcoded-`s.Namespace` bug as the App path. Under ADR043, managed Postgres (CNPG) and Key Value (Valkey) workloads live in the tenant `<ws>` namespace, and the Alloy shipper stamps their Loki streams (`type=postgres`/`type=keyvalue`) with that namespace. Fix `queryPostgresLogs` and `queryKeyValueLogs` to query the datastore's actual namespace.

## Context

- `lego/backend/internal/logs/service.go:506` (`queryPostgresLogs`) and `:553` (`queryKeyValueLogs`) call `s.History(ctx, s.Namespace, q)`.
- Live pod-log reads for datastores: `:983` (Postgres, `core.CNPGPostgresContainer`) and `:1006` (Key Value, `core.ValkeyContainer`) also pass `s.Namespace` to `readContainerLogs`.
- These verbs authorize + fetch the CR via `AuthorizeDatabase`/`AuthorizeKeyValue`, so the CR (and its `.Namespace`) should be in hand — pass that, analogous to t001's App path. Confirm managed Database/KeyValue CRs are projected into `<ws>` under tenant namespaces (they are tenant resources); if a name→namespace resolver is needed, mirror `AppNamespaceByName`.
- Datastore-log surfaces shipped in m28 (Postgres) and m30 (Key Value) — the shipper labels (`postgres=<dpg-id>` / `keyvalue=<red-id>`) are in `deploy/gitops/base/log-shipper.yaml`.

## Steps

1. In `queryPostgresLogs`/`queryKeyValueLogs`, pass the CR's namespace (from the `AuthorizeDatabase`/`AuthorizeKeyValue` result) to `s.History` instead of `s.Namespace`.
2. Do the same for the datastore live pod-log reads (`:983`, `:1006`).
3. Keep `TenantNamespaces=false` byte-identical.
