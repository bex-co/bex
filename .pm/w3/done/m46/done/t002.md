## Objective

After a `static_site` is deleted, its Overview / "Ungrouped Resources" row keeps rendering with status **Unknown** even though the public URL and the service detail page both already `404`. Make delete remove the row promptly (matching Render, which drops the service from the list immediately).

## Context

- Verified live 2026-08-21: post-delete, `curl` on the URL → `404` and the detail route → "Page not found", but the Overview table still showed `parity-static-site` as `Unknown` ≥40s later across reloads.
- Likely a list-projection issue: the services list still returns a record (or resolves phase from a now-absent App CR → `Unknown`) after the backing App is deleted. Determine whether the backend list still emits the row or the dashboard caches it.

## Steps

1. Reproduce and pin the source: inspect the `services` list response (REST + GraphQL) right after a static-site delete — does the deleted service still appear? Is status `Unknown` from a missing App phase?
2. Fix so a deleted static site is excluded from the list once delete completes (backend projection and/or dashboard cache invalidation on delete).
3. Confirm no regression for still-live services and for genuinely-unknown transient states.

## Files

- `lego/backend/internal/apps/` (services list projection / delete path)
- `dashboard/src/features/services/` + `dashboard/src/routes/index.tsx` (list query + post-delete cache handling)

## Acceptance criteria

- [ ] After deleting a static site, it disappears from the Overview list without a lingering `Unknown` row (backend excludes it and/or the dashboard invalidates on delete).
- [ ] Live services and legitimate transient states are unaffected.
- [ ] A regression test covers the delete→absent-from-list transition.

## Out of scope

- Broader resource-list status vocabulary changes beyond the delete case.
