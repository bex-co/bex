## Objective

Expose `secret` on the GraphQL webhook type and the MCP webhook view with the same authorization as webhook management, so every surface agrees with REST.

## Context

- GraphQL webhook type: `lego/backend/internal/webhooks/graphql.go:42`
- MCP webhook view in `internal/webhooks/` (mint-once today)

## Steps

1. Add the field to GraphQL and MCP.
2. Authorize it with the webhook-manage relation; a caller who can only read gets no secret.
3. Update the MCP parity pin if the tool output schema changes.

## Files

- lego/backend/internal/webhooks/graphql.go
- lego/backend/internal/webhooks/mcp.go
- lego/backend/internal/mcp parity pin

## Acceptance criteria

- [x] GraphQL and MCP return the secret for a manager
- [x] A non-manager does not receive it

## Out of scope

- New webhook features

## Result (2026-11-08, loopx w3)

GraphQL `secret` resolves for a caller with can_manage on the workspace and `null` otherwise (`gqlutil.OptionalStrField`); MCP list/create render the same `endpointWire`. `TestGraphQLWebhookSecretFollowsTheManagerBoundary`, `TestDestinationURLRedactedForNonAdminReaders` and `TestDestinationURLRedactedForReadOnlyOAuthAdmin` cover manager, member, read-only and write OAuth tokens. The secret follows the exact-URL boundary rather than the mint class: bex API keys (what Render clients use) fail the mint class, and a manager may already repoint the destination.
