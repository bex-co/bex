## Objective

Prove definition of done items 1 and 2 on the local cluster, with the adopted operands and the operator built from the tree.

## Context

- dev-3's bex-api is on `:54030` (`bash scripts/dev-env.sh 3 status`). The bex operator and CloudNativePG 1.30.1 are the shared cluster's, and serve every `dev-N`. `bash scripts/mock-cluster.sh operator` rebuilds `bex-operator:dev` from this tree, imports it on every node and deploys it. It is pre-approved; walk promptly after it, because another workstream's redeploy replaces it.
- The verb: REST `PATCH /v1/postgres/{id}` with `version`, GraphQL `upgradeDatabaseVersion`, MCP `update_postgres`. The result: GraphQL `lastUpgradeRun` (`SUCCEEDED`, `FAILED`, `IN_PROGRESS`).
- A failing run leaves its reason in `pg_upgrade_server.log` under `pgdata-new/pg_upgrade_output.d/*/log/`, in the Job pod (it goes with the Job). The Job's `major-upgrade` container log points there.
- On 2026-11-27 dev-3 still had a 16 database, `dpg-dc0bh0hjg4r72d0uh3b0`, stuck on the upstream image since 2026-11-21 (pod 0/1, `Instance Status Extraction Error`). It is not a fixture for this walk; delete it or leave it.
- w3/m676's walk (`../../m676/README.md` § Local walk) shows the shape of a run on dev-3.

## Steps

1. Deploy the operator from a tree carrying t002 and t003.
2. In a dev-3 workspace, create Free databases on 13, 15 and 16, and insert one row in each. On a second 16, run `CREATE EXTENSION pg_duckdb` as the owner and create a small table.
3. Upgrade each to 18 through the verb, one at a time. For each, record:
   - the run's state and duration;
   - the row;
   - `SHOW shared_preload_libraries` and `SHOW local_preload_libraries`;
   - the server version;
   - for the 13 and 15 databases, the post-upgrade restart that t003 adds, and what the Database showed during it.
4. On the `pg_duckdb` database, `SET duckdb.force_execution = true;` and query the table on 18.
5. Record the results in this task, with the operator image and the digests. Delete the databases.

So the 13 and 15 databases had no post-upgrade restart for `pg_duckdb` to join the preload, and the Database went `Upgrading` → `Ready` once, as the run read `SUCCEEDED` (t003 § Record).
- **Earlier runs:** 13 → 18 (`pgu-dc4mlbhjg4r62fancohg`, 74 s) and 15 → 18 (`pgu-dc4mo39jg4r62fancp7g`, 75 s) also succeeded before t002, with the 2026-11-23 18 as the target.
- **The one failure, and its fix:** the first `pg_duckdb` run (`pgu-dc4muqhjg4r62fancpcg`, 11:54:18) ended `FAILED` after 56 s, CNPG rolled it back, and the database came back on 16 with its rows and DuckDB query intact. `pg_upgrade_internal.log` stopped at "Restoring database schemas in the new cluster *failure*", and `pg_upgrade_dump_<oid>.log` ended with `pg_restore: error: could not execute query: ERROR: (PGDuckDB/DuckdbUtilityHook_Cpp) Not implemented Error: Writing to DuckDB and Postgres tables in the same transaction block is not supported` / `Command was: ALTER SEQUENCE duckdb.extensions_table_seq OWNER TO postgres;` (`pg_upgrade_server.log` held nothing past the server starts).
