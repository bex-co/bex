# App log levels: the shipper stores four buckets, so a `notice` line reads `info` and a `critical` line `error`; check whether Render keeps its eight levels

Why: w3/m509 drew a level gutter for Render's eight documented levels (render.com/docs/logging), with a blue mark for `notice` and the line's own word as the mark's title, but on production no app line ever carries `notice`, `critical`, `alert` or `emergency`.

Found by w3/m509 t006's production walk (2026-11-20, pin `3e53abbe3bc3`). A web service printed logfmt lines at `info`, `warn`, `error`, `critical`, `debug` and `notice`. `GET /v1/logs` labeled them `level=info`, `warning`, `error`, `error`, `debug` and `info`, so the dashboard showed `notice` as a plain `info` line (no blue mark) and titled the `critical` row's ✕ "error". The mapping is the shipper's `stage.template` (`deploy/gitops/base/log-shipper.yaml`, `loki.process "app_logs"`), mirrored by `shipperLevelBuckets` in `lego/backend/internal/logs/applevel.go:46` (`notice` → `info`; `critical`, `crit`, `alert`, `emergency` → `error`), and the MCP `level` filter documents only `debug|info|warn|error|unknown` (`lego/backend/internal/logs/mcp.go:47`).

First check, in a Render workspace, which `level` label value Render's `GET /v1/logs` and log explorer give a line logged at `notice` and at `critical`. If Render keeps the eight levels: store them (the shipper's template, `applevel.go`, the `level` filter values on REST, GraphQL and MCP, the dashboard's Level filter), keep every stored `warn`/`warning` line findable by the same filter, and record it in ADR018's Logs table. If Render buckets them too: record that in ADR018 and drop the unreachable `notice` mark's claim from the m509 parity row.

Done when ADR018 records Render's observed level values for `notice` and `critical` lines, and bex's stored label, filters and gutter match them, with a shipper-config test.

**Render's answer (2026-11-20).** Render keeps the eight levels. Read-only, in the signed-in reference workspace: its dashboard GraphQL `logValues(label: LEVEL)` answered `debug`, `info`, `notice`, `warning`, `error`, `critical`, `alert`, `emergency` for the app and the request logs of two projects, a JSON `"level":"warn"` line read `warning`, and the dashboard bundle draws each of the eight (a value outside them reads as `info`). [render.com/docs/logging](https://render.com/docs/logging) lists the same eight for the level mark and the `level` filter. No line in that workspace was logged at `notice` or `critical`, so a line at each was not observed directly, and no service was created there to log one. The capture is [project-observability.md § Levels](../../../docs/render-artifacts/project-observability.md#levels-re-read-2026-11-20-w3086).

**Done 2026-11-20.** The shipper's `app_logs` template and `applevel.go` store each of Render's eight under its own name (`crit` → `critical`, `emerg` → `emergency`; `fatal`, `panic`, 50 and 60 stay `error`). An App's `level` filter on REST, GraphQL, MCP and the CLI selects that level's lines alone, with `warning` still matching the `warn` streams stored before w8/031; Postgres and Key Value keep their four buckets and their mapping. The MCP `level` description names the eight. The service Logs tab offers the eight in Render's order, and the gutter shows the `debug` and `notice` marks on hover only, `notice` in the muted grey, as Render's does. Tests: `TestAppLineLevelMatchesShipper` runs the real template over the whole vocabulary, `TestShipperStoresEachRenderLevel`, the tail and Loki selector cases, `scripts/test_log_shipper.py` (nine-value budget), and the dashboard's Level options and gutter marks. Recorded in [ADR018](../../../docs/ADR018-render-parity.md) (Application logs and Log explorer rows) and [ADR010](../../../docs/ADR010-observability.md).
