## Objective

Derive, for one host on one App, the reason cert-manager has not issued its TLS certificate — and expose it on `DomainView` as a nullable `CertificateReason`.

## Context

- `domainCertificateReady` (`lego/backend/internal/apps/domains.go:331`) answers only "is the TLS Secret present with a `tls.crt`". Everything about *why* it is absent lives in the ACME objects cert-manager owns.
- Precedence, most specific first: the `Challenge`'s `status.reason` (the field that carried `Waiting for HTTP-01 challenge propagation: wrong status code '404'`), then the `Order`'s `status.state`/`status.reason` when it failed, then the `Certificate`'s `Ready` condition message.
- cert-manager types are absent from the backend scheme; read them unstructured, as `internal/postgres/recovery.go` reads CNPG objects.
- Challenges/Orders are labelled and owned by the Certificate but carry generated names, so select by listing in the App's namespace and matching `spec.dnsName` (Challenge) / the Certificate's own name (Order owner refs).

## Steps

1. Add `CertificateReason string` to `DomainView` with a comment stating it is populated only while the cert is NOT issued.
2. Add a `domainCertificateReason` helper next to `domainCertificateReady` that reads Challenge → Order → Certificate in that precedence and returns the first non-empty reason.
3. Wire it into `domainView` and `domainClaimView` so both the storeless and managed-claim projections carry it, and only when `VerificationStatus` is still `pending`.
4. Treat every cluster error (no CRD, RBAC denial, not found) as "no reason available" — never propagate it as a read failure.
