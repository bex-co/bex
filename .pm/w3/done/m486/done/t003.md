## Objective

A purge or a profile switch patches each live pod's `app.bex.co/cache-purged-at` / `app.bex.co/cache-profile` annotations instead of the pod template; a pod created later starts empty with the profile its template names. The template stops carrying the purge stamp, and the operator release that ships this rolls no existing caching service.

## Context

- `lego/operator/internal/controller/deployment_projection.go:815-826` (sidecar append and the purge-stamp copy); `edgeCacheContainer` in `edge_cache.go`.
- The operator already holds `pods: patch` (`lego/operator/config/rbac/role.yaml:39-46`).
- `w6/m484` (todo) changes the same block so a stored template keeps its sidecar image. Rebase onto it if it has landed; otherwise keep its stored-template rule intact.
- Pods from a template that predates the downward-API volume cannot read the file; they keep today's roll-based purge until their template changes for another reason (a deploy).
- Residual, owned by `w3/m489`: turning caching on from `no-cache` still adds the sidecar, so it rolls once.

## Steps

1. New templates mount the downward-API annotations volume into the sidecar and stop copying `cache-purged-at` into the template; a stored template keeps its existing annotation and env unchanged.
2. Reconcile: when the App's `cache-purged-at` or `cacheProfile` differs from a live pod's annotation, patch that pod.
3. Turning caching off keeps the sidecar as a pass-through until the next deploy, with no roll.
4. Make t001 pass; add a test that an old-shape template is not rolled by the upgrade.
