# 041 — Should `/v1/metrics/cpu` distinguish "pod too young to fill a rate lookback" from an empty series?

Why: the canary's false alarm has a tenant-facing twin — a free service just woken by a request has a blank Metrics page for ~30s, and the API cannot tell the tenant which of "no data yet" or "the query is wrong" they are looking at, any better than the probe could.

## The behavior

`promResourceQueryFor` builds cpu as `rate(container_cpu_usage_seconds_total{…}[Ns])` (`lego/backend/internal/metrics/source.go:282`) where `N = stepSeconds(resolution)`. cAdvisor scrapes every 15s (`deploy/gitops/base/prometheus.yaml:256`), so a pod that has existed less than two scrape intervals yields no cpu points at all. Memory, a plain gauge (`:273`), returns a value from a single scrape over the same instant.

A tenant who wakes a hibernated free service and opens Metrics therefore sees a cpu chart that is empty while the memory chart has data — with no explanation. [`w7/054`](../w7/done/054.md) fixed the probe that trips over this by giving it a budget; it deliberately did not touch what the API says, so the tenant-facing half is untouched.

## The question, which is product not engineering

Is an empty series the right answer here, or should the response carry something a client can render as "warming up"? Both have real costs:

- Answering "too young" means the API knows the pod's age — a new input to the metrics path, and a new field on a Render-compatible response, which is parity surface.
- Leaving it empty keeps the wire shape exactly Render's, and an empty chart for 30 seconds after a cold start is arguably honest.

Render's own behavior on a just-woken free service is **not checked** and should be, first — this may be a divergence or may be exactly what Render does.

## Trigger

A tenant asks why their metrics are blank after a wake, or Render is checked and answers differently from bex. Then decide; do not build speculatively.
