# A service's Logs type dropdown is Render's: none for a one-type service, and Request logs disabled on a plan without them

Why: Render draws no log type dropdown for a private service, worker or cron job, and disables Request logs behind an upgrade tooltip on a plan without request logs; bex draws All logs and Application logs for a one-type service, and offers Request logs on every plan, answering with a plan notice once it is picked.

Found by w3/101 (2026-11-25), read from Render's dashboard bundle (`Logs-B1PgKi0H.js`, `log-filters-B4QxydRn.js`; the capture's [§ The opening log type](../../docs/render-artifacts/project-observability.md#the-view-page)). Render's dropdown builds its options as `availableLogTypes.length > 1 ? [{logType: "all"}, ...availableLogTypes] : [...availableLogTypes]` and returns `null` when one option is left. A service's types come from its `userFacingTypeSlug`: `web` offers `app` and `request` (`restrictedTiers: tiersRequestOnly`, the two paid tiers above Hobby), every other slug `app` alone. A restricted option is disabled, with an upgrade tooltip (`Requires … plan or higher`, Upgrade your plan), and the URL parser and the initial selection skip a disabled type, so `t=request` on such a plan opens Application logs.

bex: `LogFilterBar` (`dashboard/src/features/logs/components/log-filter-bar.tsx`) always draws the type `Select`, listing `LOG_TYPE_FILTERS` without Request logs when `servesRequests` is false. Request logs on Hobby is refused by bex-api and drawn as the plan notice in `LogViewer` (`planFeatureRequired(history.error, "requestLogs")`, w8/m138).

Done when a private service's, worker's or cron job's Logs tab draws no type dropdown, a web service's on a plan without request logs shows Request logs disabled with Render's upgrade tooltip and opens a `type=request` link on Application logs, and tests pin both. Verify the tooltip's words and the plan bex reads it from (the workspace plan behind `requestLogs`) before building.
