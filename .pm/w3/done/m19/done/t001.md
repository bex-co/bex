## Objective

Stop the Events and Metrics pages from silently inheriting the backend's Render-compatible one-hour REST default. Make the shared dashboard read accept an explicit range and accumulate cursor pages without duplicate rows.

## Context

- `dashboard/src/features/services/api/events.graphql` declares only `serviceId`, `cursor`, and `limit`, even though the backend GraphQL field accepts `startTime` and `endTime`.
- `dashboard/src/features/events/hooks/use-service-events.ts` passes no range and exposes no `fetchMore`; the Events route asks for 20 rows and ignores each event cursor.
- `dashboard/src/routes/services.$serviceId.metrics.tsx` and `EventTimeline` use the same hook for ranges wider than one hour.

## Steps

1. Add `startTime`/`endTime` variables to the GraphQL operation and redesign the hook around explicit range + cursor inputs.
2. Give the Events route a retained-history window and cursor accumulation; when a `BEX_MAX_QUERY_HOURS`-sized window is exhausted, continue into the preceding window rather than issuing an over-wide request.
3. Pass the Metrics toolbar's exact selected range into its event read and retain stable id-based deduplication across cache/network/fetch-more results.
4. Preserve refetch semantics and loading/error behavior for both consumers.

## Acceptance criteria

- [ ] A service with events older than one hour shows them on the Events page without changing the backend REST default.
- [ ] Metrics requests and renders events across the selected range.
- [ ] Two cursor pages concatenate newest-first with no duplicate event ids; refetch does not append stale rows.
- [ ] A query window never exceeds the configured backend maximum.
