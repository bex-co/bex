## Objective

Use the existing evidence-backed deploy lifecycle and actionable failure reasons to add truthful intermediate/failure activity without inventing events from the latest row state.

## Context

- `TransitionDeploy` observes build, pre-deploy, rollout, and terminal states but currently overwrites `updated_at`; only `deploy_started` and `deploy_ended` survive as events.
- `PreDeployStatus` already has started/finished timestamps on the App CR.
- `failureReasonFor` distinguishes image-pull and runtime failures; Render's image-pull event requires a message and image URL.
- Initial Deploy Hooks belong to Render preview-environment initialization, which `.pm/DO_NOT_DO.md` excludes; pipeline-minutes exhaustion has no bex billing source.

## Steps

1. Journal accepted deploy/pre-deploy transitions transactionally with their deploy-row changes, keyed so retries do not duplicate them.
2. Emit `image_pull_failed` only for a typed image-pull reason, with a bounded public reason and the validated image reference; never expose raw Kubernetes messages that may drift or contain credentials.
3. Keep existing `deploy_started`/`deploy_ended` ids and cursor behavior compatible; do not double-emit a deploy edge from both the old projection and the new facts.
4. Assess Render's current build/pre-deploy event enum against the captured facts and add only fields with exact durable timestamps/statuses; record any remaining omission.

## Acceptance criteria

- [ ] An image-backed rollout that reaches `ImagePullBackOff` produces one `image_pull_failed` and one failed deploy end with the same deploy identity.
- [ ] Reconciler polling and process restart do not duplicate phase events.
- [ ] Existing deploy event ids and links remain stable.
- [ ] Initial-deploy-hook and pipeline-minutes labels remain absent with explicit reasons.
