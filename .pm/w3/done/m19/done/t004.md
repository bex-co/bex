## Objective

Separate accepted user intent from observed service convergence, matching Render's paired suspension/resumption entries and adding durable instance-failed/recovered activity.

## Context

- `apps.Suspend`/`Resume` already produce `suspender_added`/`suspender_removed` audit events at request acceptance.
- The operator later reports Hibernated/Running and a typed Ready condition; that observed edge is the source for `service_suspended`/`service_resumed`.
- The captured Render feed shows both entries at the same transition and shows `Instance failed` followed by `Service recovered` when health returns.

## Steps

1. Define a typed readiness/availability checkpoint from App phase + Ready condition; ignore Pending/Building/Deploying states that belong to an open deploy.
2. Persist service suspended/resumed only when the operator converges to the requested phase, without replacing the existing intent events.
3. Persist `server_failed` on a real running-instance readiness failure and `server_available` only on its subsequent healthy edge; carry an instance id and bounded reason code only when sourced.
4. Ensure a deploy replacement, restart, scale, and ordinary resync do not manufacture failure/recovery pairs.

## Acceptance criteria

- [ ] Suspend and resume each show one intent event and one later observed-state event.
- [ ] A real unhealthy→healthy edge shows exactly one failure and one recovery.
- [ ] A steady unhealthy or healthy status across repeated resyncs produces no additional rows.
- [ ] User-visible failure details contain no pod log, env value, or unbounded Kubernetes message.

## Out of scope

- Provider hardware-failure classification without a source that can distinguish it.
