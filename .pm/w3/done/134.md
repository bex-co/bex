# Every in-place major upgrade fails on bex's Postgres operands: pg_upgrade cannot start the old server

Why: since the operands were adopted on 2026-11-23 (w21/m584), CloudNativePG's major-upgrade Job cannot start the source server, so every upgrade a customer starts ends `FAILED` after its downtime, from every major, on REST, GraphQL, MCP and the dashboard's guided page (w3/m676). Render upgrades in place to its latest major from any supported version.

- **Found:** by w3/m676's local walk on 2026-11-26 (dev-3, CloudNativePG 1.30.1, the adopted digests in `bexOperandImages`, `lego/operator/internal/controller/database_operand.go`). Two free databases with a seeded row, each upgraded to 18 through the verb: 16 → 18 three times and 15 → 18 twice, every run `FAILED` within 30 s, the Job `BackoffLimitExceeded` and CloudNativePG's `MajorUpgradeRollback`. The rows survived each rollback. 13, 14 and 17 were not run; the two causes below cover them.
- **Cause, from 16 or 17:** `pg_upgrade` starts the old server from `/controller/old` (the binaries the Job's `prepare` init container copies from the source image), and it stops at `FATAL: could not load library "/controller/old/usr/lib/postgresql/16/lib/pg_duckdb.so": libduckdb.so: cannot open shared object file`. The copy carries `pg_duckdb.so`, not the `libduckdb.so` it links. The operator preloads `pg_duckdb` on 16, 17 and 18 (`pgExtensionPreloadLibraries`).
- **Cause, from 13 to 15:** the old server reads the configuration CloudNativePG writes for the target, whose `shared_preload_libraries` names `pg_duckdb`, and stops at `FATAL: could not access file "pg_duckdb": No such file or directory`, because the 15 operand has no `pg_duckdb`.
- **Seen in:** `pg_upgrade_server.log` under `pgdata-new/pg_upgrade_output.d/*/log/` in the running Job pod (it goes with the Job); the Job's `major-upgrade` container log names the failure and points there.
- **Ways to look at:** keep `pg_duckdb` (and any other library only some majors carry) out of the preload while a major upgrade runs, and put it back once the new major is healthy; or make the copied old binaries find `libduckdb.so` (copy it beside `pg_duckdb.so`, or an rpath); or check whether CloudNativePG 1.30 offers a hook for the old server's settings. ADR092 D4 records how a preload change rolls.
- **Done when:** on the local cluster, a PostgreSQL 15 and a PostgreSQL 16 database on the adopted operands, each with a seeded row, upgrade to 18 through the verb, end `SUCCEEDED` in `lastUpgradeRun`, and keep the row; a test holds the preload rule; and production repeats it on a disposable database before w3/m676's walk.
- Promoted to [w3/m702](../blocked/m702/README.md) on 2026-11-27 by `/loopx w3`. Triage confirmed both causes and found a third: a 13 server does not know the target's `output_plugin_libraries`. It also found that no single "way to look at" fixes all three. A 16 or 17 source needs the operand's `pg_duckdb.so` to find `libduckdb.so` beside it (`$ORIGIN`; pg_duckdb's `Makefile` links an absolute `$(PG_LIB)/` RUNPATH). Dropping `pg_duckdb` from the preload instead would fail every database with `pg_duckdb` installed, because pg_upgrade `LOAD`s each C library on the new server and pg_duckdb's `_PG_init` refuses a load outside the preload. A 13–15 source needs the operator to project the source major's extension settings while the upgrade is pending, as it already does for the logical-replication settings. CloudNativePG 1.30.1 offers no hook for the old server's settings. The work needs an operand recipe, a published and adopted 16/17/18, an operator rule, local walks and a production repeat behind a pin, which is more than one sitting.
