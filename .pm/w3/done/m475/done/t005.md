## Objective

Prove the fix on production with Render's own CLI, as a customer would run it.

## Context

- This waited for a production pin (`chore(deploy): pin platform images to <sha>` on origin/main) that contains t001's commit, `de181cfc4`. The gate cleared on 2026-11-18: pin `1ec5007be0fa` (`c7f44bd87`) contains it (`git merge-base --is-ancestor de181cfc4 1ec5007be0fa`), found by the w3 routine `pin-gated-recheck`.
- Use the QA user in `bex-canary` (`scripts/qa-login.sh`, never printing secrets). Device-approve a `render login` the way `.claude/skills/qa-find-bugs/SKILL.md` describes, or use an API key from the QA workspace, and revoke it afterwards.

## Steps

1. Download the stock Render CLI release binary matching the pin (or v2.37.0 once w22/m444 lands), verify its checksum, and point it at `https://api.bex.co`.
2. Run `render logs -r <a qa service with more than 100 lines> --limit 1000 -o json`. Expect exit 0 and lines.
3. Open `render logs -r <same>` interactively, scroll up past the first page (a pty-driven `script`/`expect` session is fine), and confirm older lines load with no error banner.
4. Record the commands and outcomes in the milestone README (no tokens). Clean up any key or session created.
5. In `docs/cli-compatibility-checklist.md`, flip the `logs` "interactive viewer, scroll up to load older lines" row from `[~]` to `[x]` and drop its "Pending" sentence.

## Acceptance criteria

- [x] Both checks pass on the production pin that carries the fix.

## Result (2026-11-18, production, pin `1ec5007be0fa`)

- **Binary:** the unmodified Render CLI v2.36.0 release, `cli_2.36.0_darwin_arm64.zip` from `render-oss/cli`, checked against the release's `cli_2.36.0_SHA256SUMS`. It ran with `RENDER_HOST=https://api.bex.co/v1/`, `RENDER_API_KEY` set to a key minted for this check, and an isolated `RENDER_CLI_CONFIG_DIR`/`RENDER_CLI_CONFIG_PATH`. The key was minted over REST as the QA user in `bex-canary` (`tea-daif693dqjvc73e7as3g`). `workspace set` selected `bex-canary`.
- **Deployed revision:** both `bex-api` replicas ran `bex-operator@sha256:b3f35c93…`, the digest pin `c7f44bd87` sets, so production carried `de181cfc4`.
- **Fixture:** `hello-go` (`srv-dbkq3hdhhjfs73eiahe0`), about 20 lines a minute. `GET /v1/logs?limit=100` answered `hasMore: true`.
- **Step 2 passes.** `render logs -r srv-dbkq3hdhhjfs73eiahe0 --limit 1000 -o json` exited 0 with empty stderr. It printed 100 JSON log objects, newest first, the server's page cap.
- **Step 3 passes.** `render logs -r srv-dbkq3hdhhjfs73eiahe0` ran in a pty (160x45) and loaded its first page. Pressing PgUp and Up past the top loaded older lines with no error banner, and the viewer stayed open until it was closed, exiting 0. The first page covered 15:24:55–15:29:51 UTC. After the first scroll, the viewer showed lines back to 15:09:55. Further scrolling reached 14:29:55, an hour back.
- **The scroll's own requests:** a second pty run went through a loopback recorder in front of `api.bex.co`. The recorder logged method, path and status, and never headers. The viewer sent the first page as `limit=100` and then twelve older pages as `limit=1000` with the previous page's `startTime`/`endTime` cursors. All thirteen answered 200 with about 100 lines (about 40 KB) each, stepping back about 5 minutes a page.
- **Bounds on production:** a direct REST probe of `limit=1000` answered 200 with 100 lines, `hasMore` and both cursors. `limit=0` and `limit=1001` answered 400 `limit must be an integer between 1 and 1000`. `limit=abc` answered 400 `invalid query parameter "limit"`.
- **Cleanup:** `DELETE /v1/api-keys/{id}` answered 204. The CLI's next call with the key failed `your token is expired`. `bex-canary` again holds only its two `bex-canary-probes` keys. The QA Kratos session was logged out (`qa-login.sh --logout`), and its cookie then answered 401. The jar, the storage state, the CLI config and the fetched kubeconfig were deleted. `~/.render` was not touched.
