## Objective

Widen the declared `limit` bound on `list-logs` (`GET /v1/logs`) from 1–100 to 1–1000. Keep every other operation's bounds as pinned.

## Context

- `lego/backend/internal/api/render_openapi.go` keeps operation-keyed relaxation maps: `renderRequiredCompatibility`, `renderCommaListQueryCompatibility`, `renderOptionalParameterCompatibility` and `renderPathParameterPatternCompatibility`. Each one may only widen, enforced by tests such as `TestRenderPathParameterOverridesOnlyWiden`.
- No map widens a numeric bound today.
- Pinned spec: `/logs` `limit` is `{"type":"integer","default":20,"minimum":1,"maximum":100}`.
- Error text comes from `parameterConstraintMessage` (`render_openapi.go:1047-1090`).
- Production today answers `400 limit must be an integer between 1 and 100` for `limit=1000` (checked 2026-11-18).

## Steps

1. Add an operation-keyed numeric-bound widening, for example `renderQueryBoundCompatibility = map[string]map[string]float64{"list-logs": {"limit": 1000}}`. Apply it to the parameter schema at load time, beside the other compatibility maps.
2. Add an invariant test: every entry only raises a maximum or lowers a minimum relative to the pinned spec.
3. Check whether the logs stream/subscribe routes (`/v1/logs/subscribe`) declare the same parameter, and widen them only if the CLI sends 1000 there.

## Files

- `lego/backend/internal/api/render_openapi.go`, `render_openapi_test.go` (or the existing gate test file)

## Acceptance criteria

- [x] Through the gate: `limit=1000` passes, `limit=1001` → 400 "limit must be an integer between 1 and 1000", `limit=0` → 400, `limit=abc` → 400 (tests).
- [x] The widen-only invariant test fails if an entry narrows a bound.

## Out of scope

- Other list endpoints. The pinned CLI sends at most 100 elsewhere (`grep` of `pkg/` on 2026-11-18).

## Result (2026-11-18)

`renderQueryMaximumCompatibility` (`render_openapi.go`) raises `list-logs`' `limit` to 1000 on a copy of the shared `limitParam`, so every other operation keeps 100. Step 3: `/logs/subscribe` and `/logs/values` are not widened. The CLI's own code sends 1000 only on the list scroll; a user's own `--tail --limit 1000` stays the pinned 400 (see the milestone's parity table). A non-integer `limit` answers the gate's generic `400 invalid query parameter "limit"`, as on every operation, since it fails the parse before any bound. Tests: `TestRenderListLogsAdmitsTheCLIPageLimit`, `TestRenderQueryMaximumsOnlyWiden` (`render_openapi_logs_limit_test.go`).
