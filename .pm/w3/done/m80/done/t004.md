## Objective

Stop reacting to expiry only after a request fails. Surface the Kratos session `expires_at` into client session state and use it two ways: (1) the 60s client session memo must never report "authenticated" past `expires_at` (today it can mask a just-expired session and show authenticated chrome until the first 401); (2) when a navigation happens near/after expiry, re-check the session at the route boundary so the user gets the clean `beforeLoad` redirect instead of a mid-page failure.

## Context

- `SessionState` today carries only `{ session, aal2Required }`: `dashboard/src/common/server-fn/session.ts:31-35`; Kratos whoami already returns `expires_at` — it is just dropped.
- Client memo: `SESSION_CACHE_TTL_MS = 60_000`, invalidated only on explicit login/logout: `session.ts:45-91`; t001 adds invalidation on 401.
- Route-boundary check that already redirects correctly: `dashboard/src/routes/__root.tsx:20-48` + `requireAuth` (`dashboard/src/common/lib/auth/auth.ts:40-59`).
- `kratos-sessions.ts:42-43` reads session timestamps for the devices panel only — no expiry logic anywhere.

## Steps

1. Add `expiresAt` to `SessionState` (parsed from whoami) on both server and client paths.
2. Memo guard: treat a cached session whose `expiresAt` has passed as a miss (re-fetch instead of returning stale "authenticated").
3. Route boundary: in the root `beforeLoad`, when `expiresAt` is past or within a small skew window, bypass the memo and re-validate before rendering authenticated chrome.
4. Keep it timer-free: no countdown UI, no background interval — checks ride existing request/navigation moments (with t003's sliding sessions, an active user's `expiresAt` keeps moving forward anyway).

- [ ] With a session expiring in <60s, navigating after expiry produces the `beforeLoad` login redirect (no flash of authenticated chrome, no error card).
- [ ] The client memo never returns an authenticated state whose `expiresAt` is in the past.
- [ ] No new polling/timers introduced.
