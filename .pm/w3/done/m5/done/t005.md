## 2026-07-14 — live-verified, on the mock cluster via dev-3, not prod

Prod's `bex-controller-manager` was still unstable (rechecked live: flapping `Running` ⇄ `CrashLoopBackOff` on a cache-sync timeout over a 5-minute poll, even though the `MachineHealthCheck` remediation loop that caused it had separately resolved). Rather than wait on an unrelated incident, proved the milestone's point on workstream w3's own isolated environment (`.pm/w3/dev-3`) instead:

- Manually `helm install`ed Loki + log-shipper (Alloy) into the shared mock cluster's `monitoring` namespace, using the **exact** values `deploy/gitops/base/loki.yaml`/`log-shipper.yaml` + the `local` overlay's patches render to (`kubectl kustomize deploy/gitops/overlays/local`, extracted with `yq`, templated with `helm template` first to catch the River-config Helm-tpl-escaping trap before installing for real) — byte-identical to what ArgoCD would sync, just without ArgoCD itself (the mock cluster runs no GitOps, ArgoCD or otherwise).
- Brought up `.pm/w3/dev-3` (`bash .pm/w3/dev-3/up.sh`) for its Hydra — `BEX_HYDRA_ADMIN_URL` turned out to be a **hard** startup requirement for bex-api now (unconditional, not gated by `BEX_OPENFGA_URL`), so `GET /v1/logs` 401s without a real bearer. Seeded the `bex-bootstrap` OAuth2 client on dev-3's own Hydra (`scripts/auth-bootstrap-client.sh`) and minted a token via `oauth2/token` client-credentials.
- Deployed a throwaway `whoami-logs-m5check` App into `dev-3`'s own namespace, killed its pod, and queried the pre-restart window over REST with Loki wired: the deleted pod's lines came back. A pre-run time range returned 0 lines (real bounds). Re-querying with `BEX_LOKI_URL` unset returned 0 lines from the deleted pod (honest live-only fallback), and every store-only filter 503'd. Cleaned up the test App; uninstalled the ad hoc Loki/log-shipper release afterward (outside dev-3's own documented scope — didn't want to leave undocumented infra on the shared cluster for other workstreams).

**Four real bugs found in `scripts/logs-verify.sh` itself — fixed upstream in this pass**, not just worked around in a scratch copy:
1. `go run ./lego/backend/cmd/api` from the repo root has no Go workspace context (`lego/go.work` isn't found walking up from repo root) — fixed with `export GOWORK="$(pwd)/lego/go.work"`.
2. `go run`'s wrapper PID is not its compiled child's PID — `kill "$API_PID"` on a `go run`-backgrounded process orphans the real server holding the port; the next `start_api` call's healthz check then passes against the **stale** (wrong-`BEX_LOKI_URL`) orphan, silently invalidating the fallback assertion. Confirmed empirically (orphaned `api` processes still bound to the test ports after `kill`). Fixed: build once to `$BINDIR/bex-api` and run that instead (the pattern the script's own header comment already claimed it used, and `secrets-verify.sh` actually does).
3. `mcp="$(... | go run ... mcp-stdio 2>/dev/null)"` under the script's own `set -euo pipefail`: a non-zero exit from the piped `go run` aborts the whole script at that assignment, before ever reaching the `|| info "MCP check inconclusive"` soft-fail branch below it — so that branch had likely never actually been reached in any prior run. Fixed with `|| true` on both `mcp=`/`mcpv=` assignments.
4. `BEX_HYDRA_ADMIN_URL` is now a **hard, unconditional** bex-api startup requirement (independent of `BEX_OPENFGA_URL`/authz), so `GET /v1/logs` 401s without a real bearer — this would have blocked the **prod** run too, even once the operator stabilizes. Fixed by seeding the `bex-bootstrap` OAuth2 client on the target cluster's Hydra (`AUTH_NS=auth`, `scripts/auth-bootstrap-client.sh`, the same pattern `secrets-verify.sh` already uses) and minting a token via `oauth2/token` client-credentials, threaded as `${AUTH[@]}` on every `curl` to bex-api.

Re-ran the **actual patched `scripts/logs-verify.sh`** (not a scratch copy) against the mock cluster with a fresh ad hoc Loki/log-shipper install: DURABLE (REST), BOUNDED, FALLBACK, and FALLBACK HONESTY all pass. It fails, as expected and unrelated to these fixes, at the w3/m8 REQUEST phase — no Traefik on this mock cluster (`mock-cluster.sh` never installs it; a separate, already-closed milestone's phase bundled into the same script). Cleaned up (test Apps, ad hoc Loki/log-shipper release, monitoring namespace) after both runs.
