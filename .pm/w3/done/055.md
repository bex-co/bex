# Key Value fails with "network policy could not be applied" after moving into an environment

Why: assigning a Key Value to a project environment leaves it `Failed`/Unavailable in the dashboard and stops its reconcile, although Valkey keeps serving.

## Observed (2026-11-08, hetzner-prod)

- Key Value `red-dbnukk1ngmjs739tgulg` (`twenty-redis`, workspace `tea-d98210cbbpdc73dcrkvg`) was assigned in the dashboard to project `CRM` (`prj-dbo052cvg1gs7387qong`), environment `Production` (`evm-dbo052cvg1gs7387qoo0`) at 05:03:50Z. `bex kv get` reports `status: unavailable` from that moment; the dashboard shows "The Key Value's network policy could not be applied."
- The `KeyValue` CR is `PHASE Failed`, condition `Ready=False reason=NetworkPolicyFailed`: `pods "red-dbnukk1ngmjs739tgulg-0" is forbidden: ValidatingAdmissionPolicy 'bex-operator-pod-labels' with binding 'bex-operator-pod-labels' denied request: the operator may change only the app.bex.co/network-isolation label on a pod`.
- The pod is still `Running` with only `app.bex.co/keyvalue` and `app.bex.co/workspace` labels; the CR carries `app.bex.co/environment-id`. Clients still connect (Twenty registered BullMQ cron jobs on it at 05:07Z). The Postgres `twenty-postgres` moved in the same save stayed `available`.

## Cause

- `syncKeyValuePodIsolation` → `relabelIsolation` patches every key in `inPlacePodLabels = []string{labelNetworkIsolation, labelEnvironment}` (`lego/operator/internal/controller/keyvalue_isolation.go:58`) onto the running Valkey and internal-proxy pods.
- `deploy/gitops/base/operator-pod-label-admission.yaml` (w8/m136) lets the operator's service account change only `app.bex.co/network-isolation` on a pod, so the `app.bex.co/environment-id` patch is denied and the reconcile returns `ReasonNetworkPolicyFailed` (`keyvalue_controller.go`, after `reconcileEnvironmentPeerPolicy`).
- Regression from `abaaa3b49` (w4/451, 2026-10-31), which added `labelEnvironment` to the in-place relabel without widening the policy. Still present at `origin/main` `9df11b619`.

## Fix options

1. Allow `app.bex.co/environment-id` in the policy's label expression (keep spec/annotations/owners/finalizers locked), and update the policy comment and ADR032 §Datastores.
2. Or stop relabelling `environment-id` in place: carry it on the StatefulSet/Deployment templates only, and make sure nothing that selects running pods depends on it before they roll.

Either way, a failed relabel should not mark a serving Key Value `Failed`; also check `Postgres` for the same relabel path.

## Acceptance

- Assigning an existing Key Value to an environment (and moving it between environments) leaves it `available` without restarting the Valkey pod, and the pod gains the environment label.
- An envtest or admission-policy test covers the operator relabel against `bex-operator-pod-labels`.
- `red-dbnukk1ngmjs739tgulg` returns to `available` after the fix reconciles.

## Outcome (2026-11-07)

- **Done** — fix option 1. `bex-operator-pod-labels` now admits exactly the operator's `inPlacePodLabels` (`app.bex.co/network-isolation` and `app.bex.co/environment-id`); spec, annotations, owners, finalizers and every other label stay locked. `keyvalue_isolation.go` names the policy as the contract its key list must match; ADR032 §Datastores and the kustomization comment are updated.
- Regression: `lego/operator/internal/controller/pod_label_admission_test.go` loads the production manifest into its own envtest API server and runs the real `syncKeyValuePodIsolation` as the operator's service account through join → isolate → move → leave, plus denials for another label, a dropped label, image, annotation, finalizer and owner changes. Against the old manifest it fails with the exact production denial; `GOWORK=off make test` is green.
- Postgres has no equivalent path: CNPG applies `inheritedMetadata` to live pods with its own service account, which the policy does not match.
- Not changed: a relabel that is still denied keeps marking the store `Failed`. The isolation label is a security boundary, so a silent partial relabel would be worse than a loud failure; with the policy matching the key list, a store that is serving no longer reaches that path.
- `red-dbnukk1ngmjs739tgulg` returns to `available` on its next reconcile once Argo CD syncs the policy (no operator image change is needed).
