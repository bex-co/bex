# 069 — A Blueprint service linked to a Docker or image build source can set `dockerCommand`, as Render's schema allows

Why: Render's Blueprint schema lets a cron job or web service with `buildSource` set `dockerCommand`, the command its container runs. bex refuses `dockerCommand` there, and it also refuses `startCommand` beside a Docker or image source. So a Blueprint service linked to such a source cannot run any command but the image's default.

- **Source:** the w3/m367 closeout, 2026-11-17, on production in `bex-canary` via `POST /v1/blueprints/validate`. The test Blueprint declared `buildSources: [{name: s, image: {url: docker.io/library/busybox:1.36.1}}]` and a service with `buildSource: s`.
  - `type: web` with `dockerCommand: httpd -f -p 10000` → `BLUEPRINT_CAPABILITY_INCOMPATIBLE` at `services[0].dockerCommand`: "dockerCommand requires a Dockerfile build or a prebuilt image".
  - `type: cron` with `dockerCommand: echo hi`, linked to a `git` source with `runtime: docker`, gets the same refusal.
  - `type: cron` with `startCommand:` → "build source s uses a Docker or image runtime, which takes no startCommand". That follows Render's REST rule for `startCommand` (`servicePATCH.buildSourceId`: "Linking to a Build Source with a Docker or image runtime rejects a start command").
  - With no command at all it validates, syncs and runs the image's default command. m367 closed on that path.
- **Render:** the pinned `lego/backend/internal/apps/schema/render.yaml.json` lists `dockerCommand` in both `cronService` and `serverService`. The `allOf` that applies beside `buildSource` forbids only `runtime, repo, branch, image, registryCredential, buildCommand, buildFilter, dockerContext, dockerfilePath, rootDir`.
- **Cause:** the rule judges the service's own `runtime`, which is empty beside `buildSource`. The two sites are `lego/backend/internal/apps/blueprint_compiler.go:371-374` (the capability rule) and `deploy.go:3350` (`manifestStartAndAutoDeploy`). It should judge the linked build source's runtime, as `sourceForImageRules` (`build_sources.go`) already does for the image rules.
- **Steps:**
  1. Check render.com's Blueprint and build-source docs for `dockerCommand` on a linked service, and cite what they say.
  2. Judge `dockerCommand` against the linked source. A Docker or image source accepts it, and a native source still refuses it, wanting `startCommand`.
  3. The apply sets the linked service's container command, and the export writes `dockerCommand` back. Check that REST `envSpecificDetails.dockerCommand` on a linked service agrees.
- **Done when:** both Blueprints above validate, plan and sync, and the container runs the given command. The export re-validates as a no-op plan. A native source with `dockerCommand` is still refused, with its schema path. ~1h.

**Done 2026-11-17 (w3/069, `/loopx w3`).** Render's docs say Docker-based services set the optional `dockerCommand` in place of `startCommand` ([blueprint-spec](https://render.com/docs/blueprint-spec)), and the pinned schema allows it beside `buildSource`. The docs say nothing more about build sources: they are still a private beta. The rule now judges the linked source's runtime. The capability compiler and `manifestStartAndAutoDeploy` leave `dockerCommand` beside `buildSource` to the link. `buildSourceStartRule` (`build_sources.go`) then refuses a native source's `dockerCommand` and a Docker or image source's `startCommand` as `BUILD_SOURCE_COMMAND_INCOMPATIBLE`, at the field at fault, and accepts a Docker or image source's `dockerCommand`. The plan runs the same check for an existing service linking a workspace source, so validate refuses what sync would. REST create beside `buildSourceId` judges `envSpecificDetails.dockerCommand` the same way, and the export writes `dockerCommand` for a Docker or image source. Tests:

- `TestBlueprintLinkedServiceTakesADockerCommand`: both Blueprints validate and sync, store the command, and export as a no-op plan.
- `TestBlueprintLinkedCommandRefusalsNameTheirField`: the refusals land at `services[0].dockerCommand` or `startCommand`.
- `TestServiceCreateLinkedDockerCommand`: the REST create.
- Operator `TestServiceLinkedToADockerSourceRunsItsDockerCommand`: the web and cron containers run it through the shell.

Each backend test fails with the fix reverted. A REST PATCH of a linked service's `envSpecificDetails.dockerCommand` already set the command. A REST read of a linked service omits Render's required `runtime`/`env` for every source kind, which is older than this change; that is filed as [070](070.md). The production check of the two Blueprints waits for the deploy of this commit.
