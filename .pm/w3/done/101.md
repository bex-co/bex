# A web service's Logs tab opens on Application logs, as Render's does

Why: Render's Logs page for a web service opens on its application logs, where bex's opens on all log types, so a Render user's first view of a busy web service is buried in request lines.

Found by w3/m537 t007's parity check (2026-11-20), read from Render's dashboard bundle (`Logs-CxB-g50N.js`, 2026-11-20). The explorer's initial filters pass through `n = e => !t && xe && e.logType === "all" ? { ...e, logType: "app" } : e`, where `xe` is true when the resource offers both `app` and `request` logs (a web service: `log-filters-*.js` `Fe("web")` gives `[{logType: "app"}, {logType: "request"}]`) and `t` is `URLSearchParams.has("logType")`, a key Render's own URL writer never sets (it writes the type as `t`). So a web service's Logs opens on `app` whatever its `t` says, unless the link spells `logType`. Verify on a signed-in Render web service before building: open its Logs page, and a link with `?t=all`, and note which type each shows and what the type dropdown lists.

bex: `EMPTY_LOG_FILTERS.type` is `all` (`dashboard/src/features/logs/types.ts`), and `logFiltersFromSearch` (`features/logs/lib/log-search.ts`) keeps it for a URL with no `type`.

Done when what Render's web service Logs page opens on is recorded in the capture, a web service's Logs tab in bex opens on the same log type (a worker, cron job or private service, which offers no request logs, keeps its single type), a link naming a type still opens on it if Render's does, and a test pins the default.

**Done 2026-11-25.** Render's bundle (`Logs-B1PgKi0H.js`, `log-filters-B4QxydRn.js`, `ServerLogs-BfHfeFcl.js`, read 2026-11-25) still runs the same opening rule, and its URL writer deletes `t` for All logs, so a web service's Logs on Render opens on Application logs with no `t` or `t=all`, on Request logs with `t=request`, and back on Application logs after All logs is picked and the page reloaded. The capture records it in [§ The opening log type](../../../docs/render-artifacts/project-observability.md#the-view-page); no signed-in Render session was available, so it was read from the bundle, not walked. `LogViewer` (`dashboard/src/features/logs/components/log-viewer.tsx`) now opens a URL naming no type on Application logs when the service serves requests (`withOpeningLogType` in `features/logs/types.ts`), applied only where it adopts a URL, never to the URL's echo key, so All logs, which writes no type, stays picked until a reload; a worker, private service or cron job keeps All logs, and `type=`/`t=` naming `app` or `request` open on it. The empty state now counts only a search or a structured filter as a search (`hasLogSearch`), as Render's No matching logs does, so a quiet web service reads as an empty range with no Clear filters that would clear nothing. Pinned by `log-viewer.test.tsx` (LogViewer opening log type, the empty-state cases) and `service-log-navigation.test.tsx` (each link through the real route, All logs through a reload, the three one-type services); every new assertion fails with an identity `withOpeningLogType`, the All-logs cases fail when the opening type reaches the URL key, and the empty-state cases fail with the old `filtered`.
