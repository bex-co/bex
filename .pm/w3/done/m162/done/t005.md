## Objective

bex's Stripe webhook endpoint is currently configured exactly right, and nothing enforces it. If someone adds a handled event type in Go without subscribing to it in Stripe, those events never arrive and nothing reports it. Add a check that compares the live endpoint's configuration against the code's whitelist.

## Context

- Verified live 2026-09-16, endpoint `we_1U50YHEqsEqs2tLVSFK88Ldl` → `https://api.bex.co/v1/webhooks/stripe`, status `enabled`, `api_version=2026-06-24.dahlia`, 10 `enabled_events` matching the code exactly.
- Code-side whitelist: `isLifecycleEvent` (9 types, `lego/backend/internal/billing/lifecycle.go:176-188`) plus `checkout.session.completed` (`webhook.go:84`).
- The account hosts five other endpoints (beancount ×2, blockeden, cuckoo, tianpan). **The check must identify bex's endpoint by URL and must never read from, report on, or modify the others.**
- Stripe endpoints are account-wide: subscribing to a type means receiving that type from every product on the account. Type filtering therefore cannot isolate products, and is not expected to — ownership is already enforced by `bex_workspace` metadata (`sessions.go:263-281`, `lifecycle.go:70-73`). This check is about drift, not isolation.
- Pattern to follow: `scripts/stripe-billing-verify.sh` already exists as the billing verification entry point.

## Steps

1. Add a verification step that fetches the bex endpoint by URL and asserts: `status=enabled`, `api_version` equals the SDK's `stripe.APIVersion`, and `enabled_events` equals the code's whitelist set exactly (no missing, no extra).
2. Source the expected set from the code rather than a duplicated literal, so adding a handled type updates the expectation automatically.
3. Fail with a message naming the specific difference (missing types, extra types, version mismatch) — not a bare "mismatch".
4. Make it read-only. The check reports drift; a human fixes Stripe.

## Files

- `scripts/stripe-billing-verify.sh`
- `lego/backend/internal/billing/` (export the whitelist set if it is not already reachable)

## Acceptance criteria

- [x] The check passes against the current production configuration.
- [x] Removing a type from the expected set (or simulating an endpoint missing one) makes it fail with a message naming that type.
- [x] The check touches only the endpoint whose URL is bex's; the other five are never read into output or modified.
- [x] The check performs no writes against Stripe.

## Out of scope

- Narrowing the `rk_live_*` restricted key's permissions. That is real and worth doing — the key can currently read and write every product on the shared account — but it must be done by a human in the Stripe Dashboard after enumerating exactly which resources bex uses; a wrong scoping breaks the billing path. Track separately.
- Migrating bex to its own Stripe account.
