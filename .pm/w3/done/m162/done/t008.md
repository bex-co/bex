## Objective

Every product-analytics view exposes an `audience` column, and exactly one workspace out of 31 is classified. Every grouped read is therefore "one known value plus a large `unclassified` bucket" — the dimension exists but cannot be used. Populate it and keep it populated.

## Context

- `product_analytics_audiences` allows `customer` / `internal` / `qa` / `canary` (CHECK constraint, verified live).
- Current contents: one row — `tea-daif693dqjvc73e7as3g` = `canary`.
- All eight views coalesce to `'unclassified'` when a row is absent: `scripts/product-analytics.sql:23,39,46,56,76,84`.
- The QA/ops workspace `tea-d98210cbbpdc73dcrkvg` is unclassified, so its churn (71 web-service create/deletes in the week of 2026-09-14) reads as ordinary activity. It inflated `product_hosting_daily` to 30 live web services on 2026-09-14 against a true standing count of 8.
- **Classification is not exclusion.** QA activity is wanted signal; the point is to be able to read the QA series and the customer series separately, not to discard either.
- The table has `ON DELETE CASCADE` to `tenants`, so rows disappear with their workspace — the guard must tolerate that.

## Steps

1. Classify the known workspaces: `tea-d98210cbbpdc73dcrkvg` → `qa`; keep the existing `canary`; default the remainder to `customer`.
2. Confirm with the user whether any of the remaining workspaces are their own test accounts (those should be `internal`, not `customer`) — only they can tell those apart.
3. Add a guard test asserting that every workspace id referenced by the QA skill configuration carries a non-`unclassified` audience, so a newly created QA workspace cannot silently blank the dimension again.
4. Leave the views alone — they already expose the column correctly; the defect was the empty table, not the SQL.

- [x] A test fails if a QA-configured workspace has no audience row.
- [x] Nothing filters QA data out of the views.

## Out of scope
