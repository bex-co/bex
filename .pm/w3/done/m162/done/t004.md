## Objective

`bex_billing_webhook_last_success_timestamp_seconds` already records when a signature-, version-, and mode-valid Stripe webhook last succeeded. Nothing watches it. Add an alert so a stalled or misconfigured webhook receiver surfaces on its own instead of being discovered during an unrelated investigation.

## Context

- Metric is published today (confirmed live on both bex-api pods): `bex_billing_webhook_last_success_timestamp_seconds 1.789550895e+09`.
- Existing alerting machinery: `w3/m6` shipped Alertmanager + rules; `scripts/alerts-verify.sh` is the verification entry point.
- Volume is genuinely low — 3 deliveries on 2026-09-16 across both pods — so the window must tolerate quiet periods without crying wolf. Pick it from observed inter-event gaps, not from a round number.
- Both replicas serve the endpoint, so the rule must consider the max across pods, not any single instance.

## Steps

1. Add a rule that fires when `time() - max(bex_billing_webhook_last_success_timestamp_seconds)` exceeds the chosen window.
2. Choose the window from the real inter-delivery gap distribution; document the reasoning in the rule's annotation so the next person does not have to re-derive it.
3. Add the rule to whatever `scripts/alerts-verify.sh` asserts so it cannot silently disappear.
4. Guard against a false positive on a fresh deploy: a just-started pod that has never received a webhook publishes 0. Either seed from process start or exclude the untouched series.

## Files

- `deploy/gitops/` alert rules (follow the `w3/m6` layout)
- `scripts/alerts-verify.sh`

## Acceptance criteria

- [x] The rule fires when no webhook has succeeded within the window.
- [x] A freshly restarted pod that has never received a webhook does not trigger the alert.
- [x] `scripts/alerts-verify.sh` covers the new rule.
- [x] The rule's annotation states why the window has the value it does.

## Out of scope

- Alerting on billing export/outbox health — separate concern, already has its own metrics.
