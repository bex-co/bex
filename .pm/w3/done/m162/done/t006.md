## Objective

`CreateCheckoutSession` provisions the Stripe Customer and Subscription **before** the user reaches the payment page. A `billing_provider_mappings` row with a live `subscription_id` therefore proves only that someone opened checkout — but it reads exactly like a bound customer, and the reconciler compounds it by marking those workspaces `healthy` / `payment_succeeded`. Record the two facts separately.

## Context

- `lego/backend/internal/billing/sessions.go:116` calls `EnsureContract` before returning the hosted session URL; `contracts.go:37-81` creates the Customer and Subscription there.
- Production state 2026-09-16: 12 workspaces carry a livemode `customer_id` **and** `subscription_id` with `payment_method_bound_at IS NULL`. Stripe confirms zero attached payment methods for all 12. Their `billing_lifecycles.status` is `healthy` and their latest reconcile outcome is `payment_succeeded`.
- This actively misled the 2026-09-16 investigation — the presence of live subscriptions was initially read as "cards were bound but the webhook lost them", and only a per-customer Stripe API check disproved it.
- `payment_method_bound_at` is and must remain the single source of truth (`store/billing.go:30` already says so).

## Steps

1. Add `checkout_started_at timestamptz` to `billing_provider_mappings` via a migration, and stamp it where the mapping is first created for a checkout.
2. Tag the pre-payment Stripe Subscription with metadata `bex_pending_setup=true` at creation, and clear it when `SetPaymentMethodBound` succeeds, so the ambiguity is resolved on the Stripe side too.
3. Backfill `checkout_started_at` for existing rows from the best available signal, or leave it null and document that null means "predates this column" — do not invent a timestamp.
4. Audit existing readers for anything that infers payment state from `subscription_id` or `billing_lifecycles.status` and point them at `payment_method_bound_at`.

## Acceptance criteria

- [x] `checkout_started_at` is set when a checkout session is created and is independent of `payment_method_bound_at`.
- [x] A subscription created ahead of payment carries `bex_pending_setup=true`; the flag is cleared once the card is bound.
- [x] A test asserts a workspace with a subscription but no bound card is reported as not-bound by every payment-state reader.
- [x] The migration's down leg is exercised.

## Out of scope

- Changing when the Customer/Subscription is created. Creating it before checkout is deliberate — the subscription id is embedded in the checkout metadata and used for the ownership proof in `verifiedCheckout`.
- Reconciler semantics for `healthy`/`payment_succeeded` on a cardless subscription — those are accurate descriptions of the Stripe objects; the fix is not to misreport them but to stop reading them as payment state.
