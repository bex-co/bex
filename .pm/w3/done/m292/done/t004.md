## Objective

An Admin's Blueprint sync runs a fresh can_manage check in the whole-manifest pre-check and again per protected create, and validation/apply list environments twice with one query per project. Do each once.

## Context

- lego/backend/internal/apps/blueprint_protected_placement.go (ListProjects + ListEnvironments per project)
- lego/backend/internal/apps/blueprint_plan_limits.go, deploy.go applyBlueprintGroupingsWith
- store.PGStore.ListWorkspaceEnvironments (lego/backend/internal/store/environments.go) already lists in one query; loadExitGuard uses it
- m281 /simplify findings (w3/059)

## Steps

1. Load the workspace's environments once per validate/apply and pass them through.
2. Carry the passed pre-check in the request so per-create placement does not re-run the fresh check.

## Files

- lego/backend/internal/apps/
- lego/backend/internal/core/environment.go

## Acceptance criteria

- [x] A Blueprint apply issues one environment listing and one fresh manage check (asserted with a counting fake)

## Result (2026-11-08, loopx w3)

An Admin's passed pre-check marks the request (`core.WithPlacementCleared`, scoped to that workspace), so the apply's protected creates skip the repeated fresh check: `TestBlueprintPlacementIntoAProtectedEnvironmentNeedsAnAdminPG` pins one `can_manage` decision per Admin apply (2 with the mark removed). The placement read uses one workspace-wide `ListWorkspaceEnvironments` when the store offers it instead of one query per project (`TestBlueprintEnvironmentPlacementsUseOneWorkspaceListing`). Scope note: `blueprintPlanLimitErrors` and `applyBlueprintGroupingsWith` keep their own listings; they predate m281 and were not part of the duplication m281 added.
