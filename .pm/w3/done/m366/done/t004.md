## Objective

Be honest at the edges, then prove the definition of done where users are.

## Context

- Cron facts start at migration 0075 (2026-08-16); earlier runs have none and are simply absent.
- Run logs come from Loki and age out with its retention; the Runs page (w2/m360) opens a run's logs.

## Steps

1. Runs older than the facts are omitted, never invented. Document it.
2. A run whose logs are past retention opens with the page's existing "no logs" state; confirm on dev-3 or with a fake Loki that it is not an error.
3. After deploy, on production in `bex-canary`, create a `*/5` QA cron, wait for at least twelve runs, and check REST paging, the eleventh-newest run's read, and the Runs page past the tenth. Delete the fixture.

## Result (2026-11-17, `/loopx w3`)

**Steps 1 and 2.**

- Runs older than the facts are omitted, never invented. ADR038's "History past the status window" bullet says so (t005).
- A run window past log retention is not an error.
  - `bex-canary` is on the Scale plan, with 30 days of logs (GraphQL `logRetention`).
  - REST `GET /v1/logs` over 2026-10-01 11:59:55–12:00:25Z answers 200 with `logs: []`. The backend clamps the start to the plan's floor and returns no lines when that inverts the range (`logs/loki.go` `lokiRange` and its `start.After(end)` guard).
  - The dashboard Logs page with the Runs page's link shape (`range=custom&rangeStart=…&rangeEnd=…`) over that window shows "No logs in this time range", with no alert and no failed API response.

**Step 3, production check.** Production pin `db48cde2bae9`. Signed in as the QA user (session cookie) in `bex-canary` (`tea-daif693dqjvc73e7as3g`).

- **Fixture:** cron `srv-dbu5tjeggh5s73emef30` (`qa-20261117-8661-m366`), created 14:03:57Z on starter. It runs `busybox:1.36.1` on `* * * * *`, logs a line, sleeps 15 s, and succeeds only in epoch minutes ≡ 9 (mod 15), so 14:09Z is its one success.
- **Just triggered and in progress:**
  - At 14:04:07, `POST …/runs` answered 200 `pending` with `crr-h4so4li2efqni85vp4es`. The list right after it showed that run once, beside the in-progress scheduled run `crr-t05ugkuhorbhmfpjp9kn` (started 14:04:00), also shown once.
  - `POST …/runs/crr-h4so4li2efqni85vp4es/cancel` answered 200 `canceled`, finished 14:04:08.31Z, never started.
  - An every-10 s poll from 14:05 to 14:20 never listed an id twice.
- **One success followed by ten failures:**
  - At 14:20:06, `App.status.runs` held 14:11–14:20, ten entries, so the 14:09 success and the 14:10 failure had been evicted.
  - `status.lastSuccessfulRunAt` read 14:09:19Z. REST `serviceDetails.lastSuccessfulRunAt`, GraphQL `service { lastSuccessfulRunAt }` and MCP `get_service` all read `2026-11-17T14:09:19Z`.
- **Paging past the window:**
  - At 14:22:29 the status window held 14:13–14:22.
  - REST `GET /v1/cron-jobs/{id}/runs?limit=5`, followed by cursor, returned 4 full pages and then an empty one. That is 20 runs, 20 unique, in the same order as `limit=100`: 14:22 back to 14:04, then the canceled run.
  - GraphQL `cronJobRuns` and MCP `list_cron_job_runs` (paged by 5) list the same 20 ids, in that order, behind the newer 14:23 run.
- **The eleventh-newest run:**
  - `crr-qdi1898ond97vdbc4fpu` (14:12:00–14:12:18Z) is outside the window. `GET …/runs/{runId}` answers 200 `unsuccessful` with both times, and GraphQL `cronJobRun` and MCP `get_cron_job_run` read it identically.
  - Render's `cronJobRun` has no reason field (pinned spec: `id`, `status`, `startedAt`, `finishedAt`, `triggeredBy`, `canceledBy`). The run's failure reason is on its `cron_job_run_ended` event `evt-0v56aunm0tejpor7o97n`: `reasonCode: non_zero_exit`, `reason: {nonZeroExit: 1}`.
- **Other evicted runs:**
  - The success `crr-9m93q8eqbgobfvhonp9r` reads 200 `successful`, 14:09:00–14:09:19Z.
  - The canceled-before-start run reads 200 `canceled`, with no `startedAt`, on REST, GraphQL and MCP (w5/m108's rule). Its `finishedAt` now has microsecond precision (14:04:08.310919Z), as `cronRunRecordView` documents.
- **Cancel and unknown ids:** cancelling the evicted 14:12 run answers 409 `CRON_RUN_TERMINAL`, and an unknown `crr-` id answers 404 `CRON_RUN_NOT_FOUND`. Both are unchanged.
- **Dashboard Runs page:**
  - Load more went from 5 rows to 10, 15, 20 and then 21, all 21 runs, and then disappeared. Row 15 is the 14:09 success, and row 21 is the canceled run ("never started").
  - The evicted 14:12 run's detail links "View logs" to its 14:11:55–14:12:23 window, which shows its line `qa-m366 minute-mod=12`.
- **One ordering edge, not a DoD failure:**
  - The canceled-before-start manual run overlapped the 14:04:00 scheduled run. In the window it listed above that run, in trigger order. After eviction it lists below it, because the facts order by the ended fact's time.
  - Paging across the boundary still had no gap and no repeat. This happens only when a manual run is canceled before it starts while a scheduled run is active.
- **Cleanup:**
  - `DELETE` answered 204 at 14:24:29, then `GET` answered 404. The fixture's App, Jobs and Pods are gone.
  - `bex-canary` lists only its baseline service `hello-go`. This run's Kratos session was revoked: `--logout` succeeded, and the API answered 401 afterwards.
