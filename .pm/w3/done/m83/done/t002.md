## Objective

Close the `w3/m36` blind spot: extend the six-hourly Loki label-index probe so it fails when no `type=app` stream exists for any `tea-<xid>` tenant namespace in the window — the exact shape of the outage where every tenant's logs were silently empty for days after the ADR043 migration.

## Context

- `scripts/request-logs-liveness.sh` queries `/loki/api/v1/label/namespace/values` scoped to `{type="request"}` and asserts LIVE + TENANT (`TENANT_RE='^tea-[a-z0-9]{20}$'`). Same index call with `{type="app"}` gives the app-log answer; a quiet tenant is not a dark pipeline only in aggregate — across all tenants over 6h, zero app streams means the shipper, not the traffic (ADR010 §"what closes the gap").
- Workflow job `request-logs-liveness` in `.github/workflows/ssh-edge-liveness.yml` (~218–304): fetches the app-cluster kubeconfig with the pinned host key, port-forwards Loki, runs the probe, opens/closes the `request-logs-down` issue, scrubs the kubeconfig. Either add a second assertion in the same script (one job, one issue label per stream type) or a sibling script + step; prefer one script with `STREAM_TYPES="request app"` to keep the job simple.
- Make the failure message name the stream type so the issue is actionable (`app-logs-down` vs `request-logs-down`).

## Steps

1. Parameterise the probe by stream type; add `app` to the default set; keep exit codes distinct per failed type.
2. Add the `app-logs-down` label + issue open/close steps mirroring the request-log ones.
3. Local dry run against dev-3's Loki (`bash scripts/dev-env.sh 3 up`), then a manual `workflow_dispatch` on prod.

## Files

- `scripts/request-logs-liveness.sh`, `.github/workflows/ssh-edge-liveness.yml`, `docs/ADR010-observability.md`

## Acceptance criteria

- [ ] A dispatch run against prod reports both `request` and `app` tenant streams live.
- [ ] Forcing `TENANT_RE` to an impossible pattern makes the `app` assertion fail and opens `app-logs-down` (red-path, recorded in t007).
