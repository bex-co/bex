## Objective

Exercise the product's core promise end to end on a schedule — a repo becomes a running HTTPS service and then disappears cleanly — and discharge the two live probes still owed on the record (`w3/m46` t008 static-site behaviours, `w3/m81` t004 delete timing) by running them weekly instead of "in a future QA run".

## Context

- Web variant: `POST /v1/services` (public Git URL of this repo + `rootDir: examples/hello-go`, free plan, canary workspace) → poll deploys until `live` (bounded by the build SLO) → `GET https://<slug>.onbex.co/` 200 → `DELETE` → by-id reads 404 and list absence within the w5/m49 five-minute window (the m81 contract) → public host returns the intentional 404.
- Static variant: `scripts/static-delete-timing-verify.sh` already does create-with-route-and-header → serve → delete → poll list/REST/GraphQL/public host to absence, always tears down, never prints the bearer; it takes `API`, `BEARER`, `REPO`. Confirm the static fixture repo it expects and use the canary key (t003) as `BEARER`.
- Cadence weekly (a build + two deploys per week is cheap); label `deploy-canary-red`; on failure the issue body carries the deploy id and the failing stage so it is actionable.
- Cleanup must be unconditional (`trap`), and the probe must refuse to run outside the canary workspace (guard on the key's workspace id) so a mis-set secret cannot touch a real tenant.
