## Objective

A guard that has never been seen red is not known to work. For each new probe, run it once with a deliberately impossible expectation via `workflow_dispatch` inputs, confirm the tracking issue opens with an actionable body, then run it green and confirm the issue closes — and record run ids on the milestone README the way m131/m132 did.

## Context

- Break levers (no production change needed): app-logs → impossible `TENANT_RE`; tenant-view → nonexistent service id input; deploy canary → wrong expected status code input; isolation matrix → an input that flips one expected-deny to expected-allow.
- Each workflow needs the corresponding `workflow_dispatch` input so the red path is reproducible without editing the workflow.
- Evidence: workflow run URLs + issue numbers, no secrets.

## Steps

1. Add the dispatch inputs where missing.
2. Red run → issue opened (check body names the stage and the fix pointer); green run → issue closed with the recovery comment.
3. Record the matrix (probe × red run × green run × issue) in the milestone README.
