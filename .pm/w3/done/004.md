# Log-shipper ships every stream N× (cluster-wide pod discovery on every node)

`deploy/gitops/base/log-shipper.yaml` runs Alloy as a **DaemonSet**, but its `discovery.kubernetes "pods"` has **no node scoping** — so every node's replica discovers every pod in the cluster and opens a log-follow stream against each. Each log line is therefore parsed, relabelled and pushed to Loki **N times** (N = node count).

Loki dedupes identical `(timestamp, line)` within a stream, so this is invisible to users — the cost is pure waste: N× shipper CPU on the process stages, N× push bandwidth, and N× log-follow streams against the apiserver.

**Why now:** the flaw pre-dates `w3/m8` (m5's `app_pods` block has the same shape), but m8 pointed the same discovery at **Traefik's access log** — the highest-volume stream in the cluster — which is where a constant factor of N actually starts to hurt.

**Fix (unverified — this is why it wasn't done inline):** scope discovery to the local node, e.g. a `keep` relabel on `__meta_kubernetes_pod_node_name` matched against a `NODE_NAME` injected via the downward API (`controller.extraEnv`), or `discovery.kubernetes`'s `selectors { field = "spec.nodeName=..." }`. **The failure mode of getting this wrong is that the shipper matches nothing and the platform silently loses all logs**, so it wants a live Loki-synced cluster to verify — not a blind config edit. Pair it with the m5/t005 + m8/t005 live runs, which need the same cluster.

Source: `/simplify` efficiency agent during `w3/m8` (2026-07-12); deferred out of that milestone deliberately, with the reason above.
