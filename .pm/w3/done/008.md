# Add content-aware controls for sandbox egress to approved writable APIs

Why: Destination allowlists cannot stop a sandbox from uploading data to an attacker-controlled account on an approved writable service, so they are not a data-loss-prevention boundary.

**Type:** residual-risk record / future hardening. **Not an m35 gate**: m35 controls destination reachability and does not claim data-loss prevention.

Cilium DNS/FQDN/SNI policy can authenticate an approved HTTPS destination but cannot identify the remote account or inspect encrypted request content. A sandbox may therefore send data to an attacker-controlled account on an approved writable service such as GitHub or an LLM API. This is materially narrower than arbitrary internet/DNS exfiltration, but it remains an exfiltration channel.

The original credential-brokering half is no longer pending: m38 keeps GitHub installation tokens outside the guest at rest and m37/m40 route model credentials through the gateway/OpenBao path. Those controls reduce credential exposure but do not constrain the destination account, HTTP operation, or uploaded content, so the remaining work is the content-aware egress boundary.

Promote before bex offers an enterprise DLP claim or a tenant requires preventive controls over approved writable destinations. Evaluate:

1. Extending the existing credential brokers with destination-account and action constraints where provider APIs support them.
2. Separate allowlists for read-only package/bootstrap traffic versus writable APIs; remove writable destinations from the default where product behavior permits.
3. An authenticated outbound proxy with account/method/path/size policy and auditable request metadata; treat TLS interception, certificate trust, privacy, and prompt/source-code sensitivity as explicit design costs.
4. Per-workspace egress budgets and anomaly signals as detection, not a substitute for prevention.

Completion evidence must prove data cannot be uploaded to an attacker-owned account on each supported destination while legitimate package/model workflows still work. A DNS/FQDN allowlist alone is not that evidence.

Source: m35 Cilium policy review, 2026-07-28; documented in ADR042 D4 and ADR043 D3.
