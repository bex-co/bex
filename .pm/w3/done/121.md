# A Postgres database's Recovery page draws a loading frame 76 px shorter than the ready card at a 390 phone

Why: the Recovery page's pending frame is meant to be a structural preview of the ready card at the same width (the repository's skeleton rule, w3/m641's definition of done 5), but at 390 its header and two rows are shorter than the card that replaces them, so the page jumps when the read lands.

- **Seen** on production pin `cdaa0a248615` (2026-11-25, w3/m641 t006) as the QA user in `bex-canary`, on a Basic 256MB Postgres (disposable) with one completed backup. The `Database` read was held after a client navigation from `/`:
  - At 1440 the pending card equalled the ready one (399/399 px).
  - At 390 it drew 590 against 666. The header was 40 against 80, because the description ("Point-in-time recovery and backups. Restore always creates a new database — this one is never modified.") takes three lines. The backup row was 50 against 66, and the export scope line 60 against 80 (four lines).
  - Locally `local-bex` answers no backups, so the local walk never compared this card.
- **Where:** `RecoveryPanelSkeleton` and `RecoveryContentSkeleton` in `dashboard/src/features/databases/components/recovery-panel-skeleton.tsx`, drawn by `DatabaseRecoverySkeleton` in `dashboard/src/common/components/route-skeletons.tsx`. The header is an `h-5` bar where the ready `CardDescription` wraps. Below `sm` the backup row is `h-[3.125rem]` and the export scope `h-[3.75rem]`, both measured at 375 px for w7/m453.
- **Done when** a held `Database` read draws a Recovery card equal to the ready one (within 2 px) at 1440 and 390 for a database with a backup. The header carries the real title and description text, so it wraps as the ready one does, and a test pins the shape.
- Filed 2026-11-25 by w3/m641 t006.

**Done 2026-11-27.** Held `Database` and `DatabaseRecoveryInfo` reads and the lazy panel's Suspense fallback each drew the ready card's height, measured in headless Chrome against `local-bex` with one completed backup mocked in, at 1440 (399/399 px) and 390 (640/640 for a database whose name is the default, 620/620 for one with its own name):

- The header lays out the ready title and description invisibly under its bars, so it wraps as the ready one does (80 px at 390). So do the actions, the list headings, the export scope line, the empty exports line and the disabled line (a database without backups: 60/60 at 390, 20 against 60 before).
- The 66 px backup row came from the ready card, not the skeleton: the age (`35m`) shrank to one character per line at 390, so the row's height followed the age's length (50 px for `3h`). The age and status no longer shrink, the id truncates instead, and the row is 40 px at every width, as its skeleton now is.
- The scope line names the database's own name when the layout or the open page knows it. On a cold load it names the one a create that names none gets, from the id in the URL (`dpg_…`, four lines at 390, as production's 80 px line was). A database with a name of its own can then differ by a line on a cold load until the read lands.
- Tests: `route-skeletons.test.tsx` § database recovery pending frame (w3/121) and `recovery-panel.test.tsx` (the scope line while loading, the backup row's age group); all six fail with the fix reverted.
