# MCP `get_metrics` refuses a host breakdown when the call also asks for CPU or memory

Why: Render's MCP server applies `aggregateHttpRequestCountsBy` to the request-count read only, so an agent that asks for `cpu_usage` and `http_request_count` by host in one call gets both from Render and a 400 from bex.

Found by w3/087 (2026-11-20) while pinning MCP's label names. `get_metrics` with `metricTypes: ["cpu_usage", "http_request_count"]` and `aggregateHttpRequestCountsBy: "host"` fails with `bad request: aggregateBy=host applies only to http_requests`: `RegisterMCP` (`lego/backend/internal/metrics/mcp.go`) sets one `MetricQuery.GroupBy` for every metric type in the call, and `Service.Metrics` (`service.go`, the `groupByHost` check) refuses it on cpu. Render's server sends `aggregateBy` only on its request-count read (`render-oss/render-mcp-server` `pkg/metrics/repo.go`, commit `c6b8bb1`; [metrics-page.md](../../docs/render-artifacts/metrics-page.md), the aggregation section), and bex already does the same for `cpuUsageAggregationMethod` (`cpuAggregationFor`). A `statusCode` breakdown beside cpu is not refused; check that it leaves the cpu series as they are.

Done when an MCP `get_metrics` call breaks down only its `http_request_count` read by host or status code and reads every other metric type as it would alone, REST's per-metric refusal (`/v1/metrics/cpu?aggregateBy=host` is a 400) is unchanged, and a test covers the mixed call for both breakdowns.

**DONE 2026-11-20.** Checked Render's server first: `pkg/metrics/repo.go` at `c6b8bb1` builds each metric type's REST read on its own and sends `aggregateBy` only from `getHttpRequestCount`, `host`/`path` only from `getHttpRequestCount` and `getHttpLatency`, and `aggregationMethod` only from `getCpuUsage`. bex's `get_metrics` set one `GroupBy`, `Hosts` and `Paths` for every type in the call, so the host breakdown beside cpu was the 400 this note names, a `statusCode` breakdown also split `http_latency` by code (Render's latency read stays whole), and an `httpHost` or `httpPath` beside cpu was the same kind of 400. `mcpReadScope.forMetric` (`lego/backend/internal/metrics/mcp.go`) now sends each argument only to the reads Render's server sends it to, cpu aggregation included, so every other type reads as it would alone. REST is unchanged: `/v1/metrics/cpu?aggregateBy=host`, `?host=` and `?path=` and `/v1/metrics/http-latency?aggregateBy=host` stay 400s. `TestMCPGetMetricsScopesEachArgumentToRendersReads` covers both breakdowns and the filters on a call mixing cpu, memory, request count and latency, checks each entry against the same type read alone and the request count against REST's breakdown, and failed on all three cases before the fix. Recorded in [metrics-page.md § Aggregation](../../../docs/render-artifacts/metrics-page.md#aggregation-w5m140-2026-10-20) and ADR018's core-metrics row. The `httpHost`/`httpPath` scoping goes past the note's wording; it is the same Render rule in the same loop.
