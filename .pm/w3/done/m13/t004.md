## Objective

Add a signal (metric, alert, or CI check) that would catch a future accidental re-introduction of unscoped, cluster-wide pod discovery.

## Context

- This flaw pre-dated `w3/m8` silently (m5's `app_pods` block had the same shape); a regression guard prevents it recurring unnoticed.

## Steps

1. Add a config-level check (e.g. a CI lint/test asserting `log-shipper.yaml`'s discovery blocks include a node-scoping selector) or a runtime metric comparing discovered-target count against expected per-node pod count.
2. Wire it into the same test/CI surface `w3/m8`'s guards use, if applicable.

## Files

- `deploy/gitops/base/log-shipper.yaml`
- CI config or test files, as appropriate

## Acceptance criteria

- [x] Removing the node-scope selector from `log-shipper.yaml` fails the new check.

## Out of scope

- Full observability dashboarding for shipper health.

## Resolution

Added a structural CI guard to `scripts/gitops-validate.sh` ("log-shipper node-scope guard") asserting the committed Alloy River config carries the `spec.nodeName=` + `sys.env("K8S_NODE_NAME")` field-selector expression — the same grep-the-committed-values-string pattern as the existing zot/RBAC/network-policy/bex-db-backup guards already in that script, so no chart render is needed to catch a regression at the source. Wired into the same CI surface (`scripts/gitops-validate.sh`, run by `.github/workflows/gitops.yml` on every push/PR touching `deploy/gitops/**`) that `w3/m8`'s and other guards use. Verified in t006 that the check genuinely fails when the selector is removed.
