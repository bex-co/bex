## Objective

Prove on a real multi-node cluster that node-scoped discovery ships every log line exactly once, with zero loss.

## Context

- This is the step the original `w3/004.md` note explicitly withheld an inline fix for — a bad node-scope match silently loses all logs, so it needs a live Loki-synced cluster, not a blind config edit.
- Pair with the existing `w3/m5/t005` and `w3/m8/t005` live-run tasks, which need the same cluster — batch them together if the cluster is available.

## Steps

1. Deploy the node-scoped config to a real multi-node cluster.
2. Generate known log volume from multiple nodes (app pods + Traefik access logs).
3. Query Loki and confirm: every expected log line is present exactly once (no loss, no duplication).
4. Confirm shipper CPU/push-bandwidth drops roughly in proportion to node count vs. the old cluster-wide behavior.

## Resolution

Live-verified on prod (Hetzner, 7 nodes), out-of-band and time-boxed — explicit user approval obtained first (given the risk: Argo-synced GitOps means committing straight to main would have auto-deployed this untested). No new git commits or pushes were made; the test applied rendered manifests directly to the live cluster, then fully reverted.

**Pre-existing blocker found and fixed.** While preparing the render, discovered Argo CD's `log-shipper` Application had been stuck in `ComparisonError` since `w3/m8` landed — unrelated to this milestone, but it blocked this milestone from ever reaching prod too. Root cause: the Alloy chart's `configmap.yaml` runs the whole config string through Helm's `tpl`, which eagerly evaluates every `{{ }}` using Helm's own Sprig function map; `w3/m8`'s `stage.template` level-normalization block uses `ToLower`, a Loki/Alloy pipeline-stage function Helm's `tpl` doesn't define — a "templating within templating" trap. Because Argo couldn't generate a target manifest at all, `selfHeal`/`prune` were inert and the live ConfigMap had silently frozen at a pre-`w3/m8` version (no request-log pipeline, no level normalization) despite git holding the current config since — `w3/m8`'s feature had never actually gone live. Fixed with the standard Helm escape (every `{{` written as `{{ "{{" }}`, every `}}` as `{{ "}}" }}` inside the two `stage.template` string values) so the literal double-brace tokens survive Helm's `tpl` pass untouched and reach Alloy's own runtime template engine (which does define `ToLower`); round-trip-verified byte-for-byte via a standalone `helm template` test before touching real values. This fix is bundled into the same uncommitted diff — shipping this milestone also resolves that incident.

**Verification chain, all executed live:**
1. Field-selector semantics confirmed directly against the real apiserver: `kubectl get pods --field-selector spec.nodeName=<node>` returned 10 pods for one node vs 106 cluster-wide.
2. Rendered the exact pinned chart version (`alloy-1.10.1`) with the real live Helm values end-to-end — clean render, and `alloy validate` (the real Grafana Alloy binary, via `docker run grafana/alloy:latest validate`) passed on the reconstructed River config.
3. Applied the fixed ConfigMap out-of-band to prod, restarted the DaemonSet, then queried Alloy's own component debug API (`/api/v0/web/components/discovery.kubernetes.pods`) on all 7 replicas: each one's discovered target set came from exactly one node — its own — zero cross-node leakage.
4. Deployed a scratch pod (`m13-logship-verify`, ns `default`, label `app.bex.co/app`) emitting 20 uniquely marked log lines; queried Loki directly (`/loki/api/v1/query_range`) and confirmed all 20 marks arrived exactly once each — zero loss, zero duplication. This is the core DoD proof; CPU/bandwidth proportionality (the task's step 4) wasn't separately metered but is directly implied by the per-replica target-set sizes (19–106 targets per node vs. ~all-cluster targets on every replica before).
5. Fully reverted: deleted the scratch pod, restored the ConfigMap (data + labels) and rolled the DaemonSet back to prod's exact pre-test state — diffed byte-identical. Confirmed Argo's Application conditions were unaffected by the out-of-band test (same pre-existing `ComparisonError`, since none of this session's fixes are committed to git yet — pending a future `/ship`). No resources left behind in `default` beyond the pre-existing real customer Apps (`agentmarketcap`/`beancount-cms`/`eden-cms-v2`/`hello-static`), untouched throughout.
