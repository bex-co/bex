# 070 — A REST read of a service linked to a build source states Render's required `serviceDetails.runtime` and `env`

Why: Render's `serviceDetails` schema requires `runtime` and `env`, but bex omits both for every service linked to a build source, so `POST /v1/services` with `buildSourceId` and each later read of that service answer a body that fails Render's response schema.

- **Source:** w3/069, 2026-11-17. `TestServiceCreateLinkedDockerCommand` (`lego/backend/internal/apps/build_sources_test.go`) creates linked services through REST. Behind `validated()` (the pinned-schema conformance wrapper), every create answers 201 and then fails with `/service/serviceDetails/env: property "env" is missing` and `/service/serviceDetails/runtime: property "runtime" is missing`. That happens for a native source with `startCommand` too, so it is older than w3/069. The test calls the mux directly for now.
- **Cause:** `linkBuildSourceSpec` (`build_sources.go`) clears the service's own `runtime`, `core.EffectiveRuntime` then reads `""`, and `renderService` (`render.go`, the `if a.Runtime != ""` block) writes neither field. With no runtime, `envSpecificDetails` is also absent, so REST never shows a linked service's `startCommand` or `dockerCommand`.
- **Steps:**
  1. Find what Render reports for a linked service's `runtime`, `env` and `envSpecificDetails`. This is probably the build source's runtime. Cite the evidence, or record the choice in ADR097 if Render's contract does not say.
  2. Project it in `restServices` from the carrier (`sourceForImageRules` already reads the carrier's runtime for the image rules), cached per build source for a list.
  3. Put `validated()` back in `TestServiceCreateLinkedDockerCommand`, and add a GET and list check for a native, a Docker and an image source.
- **Done when:** REST create, get and list of a service linked to each kind of build source pass the pinned Render response schema. `envSpecificDetails` reports the linked service's command in the field the link rule takes: `startCommand` for a native source, `dockerCommand` for a Docker or image one. ~1h.

## Done 2026-11-17

Render's pinned `webServiceDetailsPOST.runtime` reads "Required unless `buildSourceId` is set, since the build source provides its own runtime", and every read member of `serviceDetails` requires `runtime` and `env`. So a REST read of a linked service now states its build source's runtime (`restServices` → `linkedBuildView`, `lego/backend/internal/apps/build_sources.go`). Its `envSpecificDetails` takes that runtime's shape: the source's build settings (`buildCommand`, or `dockerContext` and `dockerfilePath`) around the service's own command. A list reads each build source once. The choice of build settings is recorded in [ADR097 § Links](../../../docs/ADR097-build-sources.md).

- `TestServiceCreateLinkedDockerCommand` runs through `validated()` again.
- `TestLinkedServiceReadsItsBuildSourceRuntime` checks create, get and list through `validated()` for a native web service and cron job (`startCommand`), a Docker web service (`dockerCommand` and the source's paths), and an image web service (`dockerCommand`). It also counts the build-source reads in a list.
- Both tests fail with the fix reverted, and so does `TestServicePatchLinksABuildSource` once its `update-service` allowlist entry is gone.
- Deviation: a cron job on an image source reads its command as `startCommand` only, like every image cron. The pinned CLI clones a cron's command from that field, and `lego/cli/testdata/image-cron-clone-source.json` pins that shape.
- The `update-service` `env`/`runtime` allowlist entry existed only for the linked PATCH, so it is gone (`allowlistSize` 32 → 30). ADR018's row now keeps only the `buildpack` case.
- MCP's service results project without a context and still omit the runtime: follow-up [071](071.md).
