# 072 — Ratio panels on obs.bex.co draw a 0–10000% axis when every value is 0

Why: an operator glancing at "Ingest rejection share" on 2026-11-17 saw an axis up to 10000%. A healthy all-zero ratio reads as broken, and that is exactly the panel meant to tell a broken pipeline from a quiet one (ADR113 D8).

- **Source:** the `/loopx w3` drained report of 2026-11-17, finding 2. Screenshot taken on `obs.bex.co/d/bex-cli-usage` (30 days, audience all) in that session; not committed. Filed by `/pmx 1,2,3,5 to w3` on 2026-11-18.
- **Cause:** these panels set `"unit": "percentunit"` and `"min": 0` but no `"max"`. When every point is 0, Grafana falls back to a 0–100 raw range, which `percentunit` renders as 0–10000%. The ingest rejection query itself is right, a ratio in [0, 1] (`deploy/gitops/base/values/grafana.values.yaml`, the "Ingest rejection share" panel, around line 9751).
- **Affected:** a scan of every board in `grafana.values.yaml` on `origin/main` `d41bbb9c2` found seven `percentunit` timeseries with no `max`.
  - Bounded ratios that get `"max": 1`:
    - `bex-cli-usage`: "Ingest rejection share", "Agent and CI signals per day", "CLI faults vs reported outcomes".
    - `bex-platform-availability`: "Edge 5xx ratio", "Platform service 5xx ratio".
  - Leave alone, because they can exceed 100% by design (overcommit): `bex-cluster-capacity` "CPU commitment by node (requests / allocatable)" and "Saturation vs allocatable by node".
- **Fix:** add `"max": 1` to the five bounded-ratio panels' `fieldConfig.defaults`. Add a test in `scripts/test_cli_analytics.py`, which already loads `grafana.values.yaml` and runs in `gitops.yml`. It walks every dashboard and fails on a `percentunit` timeseries that has neither `max` nor a place on an explicit may-exceed-100% list holding the two capacity panels.
- **Done when:** `python3 -m unittest scripts/test_cli_analytics.py` passes, and fails if `"max": 1` is removed from any of the five. After the Grafana sync, the rejection-share panel on `obs.bex.co` with all-zero data shows a 0–100% axis.

## Done 2026-11-18 (`4a4f107b0`)

- The five bounded ratios carry `"max": 1`. A sixth panel the filing's scan missed, bex-cli-usage "Stored events by completion kind", takes `percentunit` on its right axis from overrides B and C (the 30-minute execution_error share and its alert line). Its share and alert line read 0 on production on 2026-11-16 (w3/m438 t005), so it drew the same 0–10000% axis. It gets `custom.axisSoftMax: 1` instead of a hard cap, because the alert line (3x the 7-day share) can pass 100% and a cap would clip it.
- `RatioAxisTest` in `scripts/test_cli_analytics.py` walks all eight boards, overrides included. It fails on any `percentunit` timeseries field with neither `max` nor `custom.axisSoftMax`, unless the panel is one of the two capacity panels. It needs no database. With any one of the five `max` lines or either soft max removed, it fails and names that panel. The full file passed, 67 tests with `scripts/test_product_analytics.py`, against a disposable `postgres:17`.
- Cause confirmed in Grafana 13.2.1, the version production runs: `UPlotScaleBuilder.ts` replaces a degenerate range with `[0, 100]` unless a hard max applies. A local `grafana/grafana:13.2.1` drew all-zero TestData series as 0–10000% before the change and 0–100% after, on the left axis and on the right override axis alike. The soft max grew to 150% for a 1.4 point.
- Production: Argo's `grafana` app synced `4a4f107b0` at 09:14:56 UTC. The `grafana-dashboards-platform` ConfigMap carries all seven bounds, and a new Grafana pod rolled out on it. "Ingest rejection share" read exactly 0 for every one of 103 hourly points over the past 7 days, NaN where there was no traffic. So the provisioned panel now draws 0–100%. obs.bex.co itself needs an ops-workspace sign-in, so this worker did not open the panel in a browser.
