## Objective

Contain an OpenSandbox lifecycle-server compromise to provisioned tenant sandbox namespaces and make the network claim “only bex-api can reach port 8077” true at pod identity level.

## Context

- `deploy/opensandbox/server-in-cluster.yaml` binds pod/service/ConfigMap and sandbox-CR mutation cluster-wide.
- The NamespaceReconciler already stamps `bex-tenant-sandbox-server` RoleBindings per `<ws>-sandbox`.
- `admit-only-bex-api` currently selects only the `bex-system` namespace, admitting every pod there.

## Steps

1. Remove the mutation-capable ClusterRoleBinding; retain only per-tenant RoleBindings.
2. If informers require cluster scope, split a minimal read-only ClusterRole/Binding with no create/update/patch/delete verbs.
3. Add the exact bex-api identity to lifecycle-server ingress and the m33 exec-gateway listener, then re-check the server→control-plane callback rule.
4. Default-deny component egress: the server may resolve only its fixed in-cluster tenant resolver, and the controller gets no DNS path at all.

## Acceptance criteria

- [ ] The server SA cannot mutate pods/services/configmaps/CRs outside `<ws>-sandbox` namespaces.
- [ ] It can still create/list/delete a sandbox in an authorized tenant namespace.
- [ ] A non-bex-api pod in `bex-system` cannot reach port 8077.
- [ ] A non-bex-api pod in `bex-system`, Traefik, or monitoring cannot reach the exec gateway on port 8081; the signed bex-api path still works.
- [ ] Server/controller identities cannot use raw DNS as a bearer-exfiltration channel; required API/tenant-resolver/execd paths still work.

## Out of scope

- Replacing OpenSandbox's lifecycle server implementation.
- Per-workspace lifecycle-server/controller identities; the shared components remain a cross-sandbox trusted computing base even though their Kubernetes authority is contained to provisioned sandbox namespaces.
