## Objective

Check that tightened network-policy, visibility, ownership, and error semantics stay coherent across REST, GraphQL, MCP, and the unmodified Render CLI, recording intentional divergences rather than silently changing a surface.

## Context

- `networkPolicy` is a Render-visible create/response field.
- bex also exposes sandbox lifecycle through GraphQL and MCP; the concurrently landed m33 CLI/MCP exec path must use the same core owner authorization.
- Security refusals must not vary by adapter or leak another sandbox's existence.

## Steps

1. Compare current Render CLI/API field and error behavior for supported sandbox network settings and resource visibility.
2. Exercise all bex adapters against the same allowed/denied cases.
3. Update parity/checklist/ADR divergence notes for every deliberate difference.

## Acceptance criteria

- [ ] REST, GraphQL, MCP, and CLI agree on effective policy, visibility, and named refusal semantics.
- [ ] Unauthorized cross-owner/cross-tenant lookups do not reveal resource existence.
- [ ] Every intentional Render divergence is documented with evidence.

## Out of scope

- Reworking the already shipped m33 exec transport beyond applying the shared owner authorization boundary.
