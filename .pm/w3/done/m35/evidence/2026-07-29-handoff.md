## Security problem found during live verification

The checked-in `bex-sandbox-pods` ValidatingAdmissionPolicy existed in
production, but its CEL `matchConditions` expression based on
`namespaceObject` did not select a controller-submitted Pod in a namespace
labelled `app.bex.co/regime=sandbox`. A server/controller identity with valid
namespace-scoped Pod authority could therefore submit an ordinary runc Pod and
bypass the claimed gVisor host boundary.

The fix replaces that CEL namespace match with the admission API's native
`spec.matchConstraints.namespaceSelector`. The policy remains fail-closed and
requires:

- `runtimeClassName: gvisor`;
- `bex.co/pool=sandbox` scheduler placement and no create-time `nodeName`;
- `app.bex.co/regime=sandbox` workload identity;
- `automountServiceAccountToken: false`.

The production policy now reports the native sandbox namespace selector,
`failurePolicy: Fail`, and a binding with `Deny` plus `Audit`. An impersonated
controller server-side dry run denies a Pod with no gVisor runtime and admits
the exact gVisor shape.
