# Harden the observed-availability edge against long operator-cache staleness

Found by w3/m78's live crash leg (2026-08-08). The operator concludes App `Ready` from its controller-runtime **cached** clients (Deployment status get + pod list). When apiserver/etcd stall watch streams for minutes (observed on the overloaded local harness host; plausible on prod only during control-plane incidents), the cache time-travels: a pass can re-conclude a crash-era `Ready=False` long after recovery, and the m78 mitigations (`RolloutSettling` discrimination + the reconciler's 2-tick `debounceUnhealthy`) both read the same stale world, so phantom `server_failed`/`server_available` pairs (3s apart) can still slip through — each one a Critical push page + webhook delivery.

Candidate hardening (pick one, small):

- Before recording an unhealthy edge, the store reconciler re-fetches the App CR with its **direct quorum client** after a short delay (it already has one — `client.New`, uncached) and only records if the condition still holds — a confirm-read debounce instead of a tick debounce.
- Or: the operator condition carries `LastTransitionTime`; the reconciler refuses to record an unhealthy edge whose condition transition is **older than the previous healthy checkpoint** (a time-traveled conclusion, not a new one).

Either keeps real outages (which persist and re-transition) intact. Not urgent: healthy control planes bound informer staleness to milliseconds; the m78 fixes already killed the common single-tick case (old-pod reap).
