## Objective

Check that the new datastore events are consistent across every surface they touch — REST, GraphQL, MCP, dashboard, mobile — and against Render's own behaviour, flagging drift as follow-up notes rather than diverging silently.

## Context

- Surfaces: REST `/v1/webhooks` event-type validation + `GET /v1/events/{id}`; GraphQL `serviceEvent` / webhook mutations; MCP `get_service_event` / webhook tools; dashboard picker + push-policy editor; mobile catalog.
- Render references: `docs/render-artifacts/webhooks-api.md` (pinned 67-value enum, picker set of 64 with the six API-only / three picker-only values — check which of the new names Render's picker actually shows), the pinned OpenAPI event schema in `lego/backend/internal/api/openapi/` (field name for the datastore subject), and Render's Postgres / Key Value dashboard pages: **verify first** whether they expose an activity/events list; if yes, mirror it from the same facts as a follow-up note, if no, record the decision in ADR018.
- Notification parity: Render emails on datastore unavailability? Check `docs/render-artifacts/notify-on-fail.md`; if it does, that is the `w2/028` email item — note it there, do not build it here.

## Steps

1. Walk each surface with the same fact id; confirm identical names, timestamps, and details.
2. Compare against the pinned artifacts and Render's live docs; record ✅/◐ per surface in the ADR018 row.
3. File any drift as inbox notes with a `Why:` line.
