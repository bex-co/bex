## Objective

Pin today's behavior with projection tests that fail until the fix lands: a manual purge and a switch between `origin-controlled` and `origin-controlled-all` each change the projected Deployment's pod template, so every instance rolls. For a service with a disk (Recreate strategy) that roll is an outage.

## Context

- `lego/backend/internal/apps/edge_cache.go:99-117`: `PurgeCache` stamps `app.bex.co/cache-purged-at` on the App.
- `lego/operator/internal/controller/deployment_projection.go:821-826` copies that annotation into `dep.Spec.Template.Annotations`, which rolls the Deployment.
- `lego/operator/internal/controller/edge_cache.go` (`edgeCacheContainer`) passes the profile as the env var `BEX_EDGE_CACHE_PROFILE`, so a profile switch changes the template too.
- `lego/operator/internal/controller/disk.go:96-102`: a disk forces `Recreate`. Neither `checkCacheProfile` (`lego/backend/internal/apps/edge_cache.go:52-69`) nor the App CEL rules (`lego/types/v1alpha1/app_types.go:501-505`) refuse caching on a disk-bearing web service.
- Render: the cache is "powered by the same global CDN as Render static sites" and a purge is triggered "from its Settings page" ([web-service-caching](https://render.com/docs/web-service-caching)); nothing in it touches instances.

## Steps

1. Add tests that re-project the same caching App before and after a purge stamp, and before and after a static↔all profile switch, and assert the pod template is unchanged.
2. Add one with `spec.disk` set, asserting the same.
3. Confirm all fail on the current code with a diff naming the annotation or the env var.
