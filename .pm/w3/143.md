# A Blueprint whose repository bex cannot reach says so on its Resources page, as Render's does

Why: when Render cannot read a Blueprint's repository, its Resources page says "Render cannot access the following repo:" with the repository's URL and how to fix it; bex's, since w3/m680, keeps drawing the resource tables, and the reader finds the cause only on the failed sync's page.

Filed by w3/m680 t007 on 2026-11-27.

- **Render:** a `not found` error on the page's `executionSourceResources` read draws `AN`: the heading "Render cannot access the following repo:", the repository's URL as a link, "Please make sure the repository exists, or if this is a private repository, connect your Git provider to Render." and the Git connect control (`index-D5V4ZgbE.js`, [blueprint-pages.md § Resources](../../docs/render-artifacts/blueprint-pages.md#resources-w3m680)).
- **bex:** a fetch failure records a failed sync whose one error has no line or field (`lego/backend/internal/apps/blueprint_onboarding.go` `PlanBlueprint` → `recordFailedPlan`; `failSync` for an automatic sync), so `blueprint-resources-page.tsx` cannot tell it from a failed deploy and shows the tables. `classifyBlueprintFetchError` knows the reason but the sync does not keep it.
- **Done when:** a Blueprint whose newest sync failed because its repository is gone or unreadable shows Render's notice in Render's words (all eight locales) with bex's GitHub connect action, in place of the tables; the sync keeps a code for that reason (GraphQL only unless Render's API has one); a backend test and a dashboard test pin it; `blueprint-pages.md` § Still apart loses the line.
