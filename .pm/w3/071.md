# 071 — An MCP read of a service linked to a build source states its build source's runtime, as REST does

Why: since w3/070, REST reads of a linked service state Render's required `serviceDetails.runtime` and `env` (the build source's runtime), but MCP's service results still omit both. Render's MCP server returns the same service object as its API, so an agent cannot tell how a linked service is built.

- **Source:** w3/070, 2026-11-17. REST resolves the carrier in `restServices` (`linkedBuildView`, `lego/backend/internal/apps/build_sources.go`). MCP projects through `toRenderService(app)`, which has no context: `renderServiceResult`, `createdServiceResult` and `toRenderServices` in `lego/backend/internal/apps/mcp.go`, plus `link_build_source` in `build_sources_graphql.go`. So `get_service`, `list_services`, the create tools, `update_service`, scale, suspend/resume and restart answer a linked service with no `runtime`, `env` or `envSpecificDetails`.
- **Steps:** route every MCP service result through `linkedBuildView`, one carrier read per build source on a list. These helpers take `(AppView, error)` straight from a verb call, so they need a context-carrying shape: for example, a method that takes the context and returns the adapter.
- **Done when:** MCP `get_service`, `list_services` and a create tool, for services linked to a native, a Docker and an image build source, answer the same `serviceDetails.runtime`, `env` and `envSpecificDetails` as REST `GET /v1/services/{id}`. A test compares the two surfaces. ~1h.
