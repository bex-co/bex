## Objective

Answer one log query for a whole project or environment, as Render's `logs(query: {project, filterDocument, …})` does: resolve the project's resources the caller may read, apply the view's filters, and label each line with its resource.

## Context

- `lego/backend/internal/logs/graphql.go` (today `resource` is required and single), `rest.go` (multi-resource history), `filterpattern.go` (text and wildcard/regex terms), the per-plan retention floor (w9/m389).
- Labels per line, in Render's order: `SERVICE` (the resource id; the dashboard needs its name too), `DEPLOY`, `INSTANCE`, `LEVEL`, `LOG_TYPE`.
- Resource types: Services, Cron jobs, Postgres, Key Value (Postgres and Key Value logs come from the datastore log readers).

## Steps

1. Add `project` and `filterDocument` to the query input; keep the single-`resource` form unchanged.
2. Resolve membership server-side (environment filter, Resource, Resource Type), check `can_view_logs` per resource, drop the unreadable ones silently.
3. Merge the per-resource streams in time order, 50 lines a page, with `nextStartTime`/`nextEndTime`/`hasMore`, inside the existing time box.
4. Request Logs scope: `LOG_TYPE` request over the project's web services only.

## Files

- lego/backend/internal/logs/graphql.go
- lego/backend/internal/logs/ (scope resolution, merge)

## Acceptance criteria

- [ ] A project with a web service, a cron job and a Postgres returns their lines interleaved by time, each labeled with its resource
- [ ] An environment filter narrows to that environment's resources
- [ ] A resource the caller cannot read contributes no line and no label
