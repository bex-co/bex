# 077 — A bare GET after a HEAD-first fill reads the stored page, not `MISS`

Why: when a HEAD is the first request for a cacheable path (uptime monitors and link checkers often go first), the edge fills its cache with a GET but a client's next bare GET still goes to the app. Cloudflare, Render's CDN, caches one object for that URL, so the GET reads `HIT` there.

- **Source:** w3/075's production check, 2026-11-19, pin `dff52c596d13` ([record](done/075.md#production-record-2026-11-19)). On a new key, a bare `curl -sI` read `200 MISS` and filled the cache with a GET. The next bare HEAD read `HIT`, but the next bare `curl -s` read `200 MISS`, and nginx logged a second `GET`.
- **Cause:** a HEAD fill stores the page under the HEAD's own encoding preference, which is identity for a bare client. Traefik adds `Accept-Encoding: gzip` to a GET that carries none, so the bare GET looks up the gzip key. `serve` (`lego/operator/internal/edgecache/edgecache.go`) reads the other key's page (`unencodedVariant`) only for a HEAD.
- **Constraint:** a GET that accepts gzip may read the identity key's page when that page states no `Content-Encoding` beyond `identity`, unless the client refused identity (`identity;q=0` or `*;q=0`). A GET that does not accept gzip must never read a gzip-encoded page.
- **Done when:** a unit test fills a key with a bare HEAD and then sends a GET with `Accept-Encoding: gzip`. The GET reads `HIT` with the full body and `Age`, and the origin sees one GET. A gzip-encoded page under the gzip key never answers a bare GET. On production, a bare `curl -sI` then a bare `curl -s` of a new cacheable path read `MISS`, then `HIT`. ~45m.
