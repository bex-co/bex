## Objective

Remove one imported sandbox image without deleting its group, as Render's `delete-sandbox-build` does.

## Context

- Render: "The build no longer appears in lists and cannot be retrieved or used to create sandboxes, including by image name. Repeated requests to delete the build return HTTP 204." Responses include 404 and 409. Read the pinned schema for when 409 applies (for example a build still importing).
- Builds service: `lego/backend/internal/sandbox/images.go` (`GetImage` `:432`, `ListImages` `:452`, `createImage` `:478`); routes `sandbox/images_surfaces.go:36-64`. Registry delete: `RegistryReaper.DeleteImportedImage` (`sandbox/snapshot_size.go:332`), already used by group delete (`images.go:598`, w2/m359).
- Builds are rows in the store (`store.SandboxBuild`); storage accounting in the workspace sandbox-storage gauge (w22/m313).

## Steps

1. Service `DeleteImage(ctx, groupID, buildID)`: authorize like the other write verbs, mark the build deleted, delete its registry tag, release its storage accounting. An already-deleted build answers 204; an unknown id 404; a state Render answers 409 for answers 409 with a named code.
2. Lists, get-by-id and sandbox create by `buildId` or `buildName` exclude deleted builds.
3. REST route, GraphQL mutation and MCP tool beside the existing build verbs; scope matrix write row.
4. If the pinned Render CLI has an images delete command, walk it on dev-3.

## Files

- `lego/backend/internal/sandbox/images.go`, `images_surfaces.go`, the store build queries, GraphQL and MCP registrations, `api/scope_matrix_ops.go`

## Acceptance criteria

- [ ] Delete then list/get/create-by-name behave as Render documents; repeat delete answers 204.
- [ ] The registry tag is gone and the storage gauge drops.

## Out of scope

- Deleting a running sandbox started from the build (it keeps running, as with group delete).
