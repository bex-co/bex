# 153 — After Disconnect Blueprint, the Blueprints list still shows the Blueprint until a reload

Why: Render's list drops a disconnected Blueprint at once. bex's keeps listing it, so the user reads the disconnect as failed and opens a Blueprint that is gone.

- **Source:** w3/m679 t005 step 2, the production walk of 2026-11-27 ([README](done/m679/README.md#production-walk-2026-11-27-t005-step-2)).
- **Seen:** on production pin `546d61ac7343`, as the QA user in `bex-canary`, Disconnect Blueprint on `qa-20261127-m679-b` (disposable) at 1440 and on `qa-20261127-m679` (disposable) at 390. The mutation answered, the toast read "Blueprint disconnected" and `/blueprints` opened, still listing the disconnected Blueprint with its Paused badge. `GET /v1/blueprints/<id>` answered 404, `GET /v1/blueprints` no longer had it, and a reload dropped the row.
- **Where:** `/blueprints` (`dashboard/src/routes/blueprints.tsx`) is the parent route of every `/blueprints/<id>/…` page, so its loader read the list when Settings opened. Coming back to it is a `stay`, which `titleLoaderFetchPolicy` (`dashboard/src/common/lib/document-head/index.ts`) reads cache-first, and `useBlueprints` is cache-first too. `useDisconnectBlueprint` (`dashboard/src/features/blueprints/hooks/use-disconnect-blueprint.ts`) leaves the cache as it was. The dialog before w3/m679 navigated the same way. The local walk's stateful proxy did not show it.
- **Do:** after a disconnect succeeds, evict the Blueprint and `ROOT_QUERY`'s `blueprints` field from the Apollo cache, as `use-env-groups.ts` does for a deleted group, so `/blueprints` reads the list from bex-api.
- **Acceptance:**
  - [ ] A test disconnects from Settings with the list cached, then `/blueprints` lists only the other Blueprints. It fails without the eviction.
  - [ ] On production, a disconnect from Settings opens `/blueprints` without that Blueprint, at 1440 and 390, with a Blueprint created for the check (disposable).
- **Estimate:** ~45m. The dashboard alone changes, toward the list Render shows, so there is no Render parity task.
