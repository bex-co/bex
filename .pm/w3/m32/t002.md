## Objective

Deploy `opensandbox-server` in-cluster (Deployment + Service + ConfigMap + PVC + SA/Role in `opensandbox-system`) configured for the kubernetes runtime backend, so `BEX_OPENSANDBOX_URL` points at an in-cluster Service instead of host `:8077` (ADR042 D1).

## Context

- The vendored chart (`deploy/gitops/charts/opensandbox-controller/`) deploys only the controller manager — no Service/ConfigMap/Secret templates.
- `deploy/opensandbox/sandbox-k8s.toml` hardcodes `/Users/tianpan/...` paths and `kubeconfig_path`; in-cluster it must use the pod ServiceAccount.

## Steps

1. Extend the chart (or sibling chart) with Deployment + Service + ConfigMap + PVC (sqlite) + SA/Role mirroring the controller's ClusterRole verbs on the BatchSandbox/Pool/SandboxSnapshot CRDs.
2. New cluster TOML: `[runtime] type=kubernetes workload_provider=batchsandbox`, drop `kubeconfig_path`, `batchsandbox_template_file` → mounted ConfigMap, `[store] type=sqlite path=/data/bex.db`, `host=0.0.0.0`.
3. Argo Application references it; `BEX_OPENSANDBOX_URL=http://<svc>.opensandbox-system.svc:<port>`.

## Files

- `deploy/gitops/charts/opensandbox-controller/` (extend) or new chart
- `deploy/opensandbox/sandbox-cluster.toml`
- `deploy/gitops/base/opensandbox-controller.yaml`

## Acceptance criteria

- [ ] Server pod runs in-cluster and reaches the controller via its SA.
- [ ] `BEX_OPENSANDBOX_URL` resolves to the in-cluster Service.

## Out of scope

- Snapshot registry config (t003), Kata (t004), security hardening (t006).
