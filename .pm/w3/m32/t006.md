## Objective

Make the bex-api↔OpenSandbox link a single trusted hop with defense in depth: NetworkPolicy admitting only bex-api, OpenSandbox multi-tenant mode (per-workspace API key → `<ws>-sandbox` via an HTTP tenant-lookup provider backed by bex IAM), and `INSECURE_SERVER` dropped (ADR042 D4).

## Context

- Today: server is loopback + no `api_key` + `OPENSANDBOX_INSECURE_SERVER=YES`; OpenSandbox's lifecycle API does no per-tenant authz.
- OpenSandbox multi-tenancy: `[[tenants]]` (file) or HTTP provider — server sends `OPEN-SANDBOX-API-KEY`, endpoint returns `{namespace, ttl}` or 401; lifecycle ops auto-scoped to the tenant namespace.
- NetworkPolicy model: `deploy/gitops/base/network-policies.yaml` (`deny-tenant-ingress` admits only `bex-system`).

## Steps

1. NetworkPolicy on `opensandbox-system` admitting only bex-api (`bex-system`); deny tenant + sandbox pods.
2. Enable OpenSandbox multi-tenant HTTP provider → bex-api tenant-lookup endpoint; bex mints per-workspace OpenSandbox keys mapped to `<ws>-sandbox`.
3. Set `[server].api_key`/multi-tenant config; drop `INSECURE_SERVER`.

## Files

- `deploy/gitops/base/network-policies.yaml`, `deploy/opensandbox/sandbox-cluster.toml` (`[tenants]`)
- `lego/backend/internal/` (tenant-lookup endpoint + key minting)

## Acceptance criteria

- [ ] Only bex-api can reach the OpenSandbox server; tenant/sandbox pods cannot.
- [ ] A per-workspace key's ops are scoped to `<ws>-sandbox`; a stolen key can't cross tenants; OpenSandbox itself rejects cross-tenant ops even if bex-api bugs.

## Out of scope

- The lifecycle validation (t007), the bex-api sandbox feature surface (t009).
