## Done (validated on prod 2026-07-29)

Implemented, shipped, and validated end-to-end on prod (Hetzner cluster):

- **Key store** — `sandbox_tenant_keys` (migration 0054): one opaque high-entropy
  key per workspace, idempotent/race-safe mint (`SandboxKeyForWorkspace`) +
  reverse lookup (`WorkspaceForSandboxKey`). `internal/store/sandboxtenants.go`.
- **Tenant-lookup endpoint** — `GET /v1/sandbox-tenants` on the CP internal API
  behind the CP bearer, matching `opensandbox_server/tenants/http_provider.py`
  (200 `{namespace,ttl}` | 401 `{code:UNAUTHORIZED}`). bex-api stamps each
  request's `OPEN-SANDBOX-API-KEY` via the store-backed `KeyProvider`.
- **Per-`<ws>-sandbox` RBAC** — `bex-tenant-sandbox-server` ClusterRole bound by
  the NamespaceReconciler to the OpenSandbox server SA per sandbox namespace
  (never cluster-wide for the tenant-scoped grant); bex-api granted `bind` on it.
- **Server multi-tenant** — `[tenants]` HTTP provider config (rendered from a
  Secret with the CP bearer), `OPENSANDBOX_INSECURE_SERVER` dropped;
  `allow-opensandbox-to-cp-api` NetworkPolicy admits only the server pod to
  bex-api :8091; the admit-only-bex-api NetworkPolicy fronts the server.

**Acceptance evidence:** key A → sandbox in `tea-d98210…-sandbox`, key B → sandbox
in `tea-d9a2ka1…-sandbox` (each server-scoped to its own namespace, gVisor);
invalid key → 401 `INVALID_API_KEY`; key A gets 404 listing/deleting key B's
sandbox (scoped list); nothing leaks to the shared `bex-sandbox`. Commits
`a0e23811`, the bind-grant fix, `6716579a`.

**Follow-ups (not blocking the guarantee, which is server-enforced scoping):** the
server retains a cluster-wide ClusterRoleBinding from `server-in-cluster.yaml`
(the per-`<ws>-sandbox` RBAC is defense-in-depth; narrow the cluster grant to
read/informer-only as hardening); the server Deployment + tenant-config Secret
are prod-applied, not yet gitops-durable; the server→bex-api tenant lookup is
in-cluster HTTP (cleartext key over the pod network — move to HTTPS).

## Objective

Make the bex-api↔OpenSandbox link a single trusted hop with defense in depth: NetworkPolicy admitting only bex-api, OpenSandbox multi-tenant mode (per-workspace API key → `<ws>-sandbox` via an HTTP tenant-lookup provider backed by bex IAM), and `INSECURE_SERVER` dropped (ADR042 D4).

## Context

- Today: server is loopback + no `api_key` + `OPENSANDBOX_INSECURE_SERVER=YES`; without multi-tenant mode, any reachable caller can drive any sandbox.
- OpenSandbox multi-tenancy (OSEP-0014): `[[tenants]]` (file) or HTTP provider — server sends `OPEN-SANDBOX-API-KEY`, endpoint returns `{namespace, ttl}` or 401; lifecycle ops auto-scoped to the tenant namespace.
- NetworkPolicy model: `deploy/gitops/base/network-policies.yaml` (`deny-tenant-ingress` pattern — admits `bex-system` plus each namespace's own platform peers like `kpack`/`bex-build`, never tenant pods; here the admit list is bex-api alone).
- This task **owns** the bex-api side of the key plumbing: the internal tenant-lookup endpoint + per-workspace key minting/store. t009's sandbox feature package **consumes** those keys; it does not re-implement them.

## Steps

1. NetworkPolicy on `opensandbox-system` admitting only bex-api (`bex-system`); deny tenant + sandbox pods.
2. Enable OpenSandbox multi-tenant HTTP provider → bex-api tenant-lookup endpoint; bex mints per-workspace OpenSandbox keys mapped to `<ws>-sandbox`.
3. Set `[server].api_key`/multi-tenant config; drop `INSECURE_SERVER`.

## Files

- [x] Only bex-api can reach the OpenSandbox server; tenant/sandbox pods cannot.
- [x] A per-workspace key's ops are scoped to `<ws>-sandbox`; a stolen key can't cross tenants; OpenSandbox itself rejects cross-tenant ops even if bex-api bugs.
