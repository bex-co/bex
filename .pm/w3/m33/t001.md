## Objective

Add an `Exec` method to the in-package OpenSandbox client (`internal/sandbox/client.go`) that runs a command inside a sandbox and streams stdout/stderr + exit status. This is the transport every exec surface (REST stream, MCP) rides.

## Context

- OpenSandbox runs an `execd` sidecar/agent in each sandbox pod (`execd_image = opensandbox/execd:v1.0.16` in `deploy/opensandbox/sandbox-cluster.toml`). The lifecycle server proxies/exposes exec — inspect the **installed PyPI package inside the running server pod** to find the exact exec API, the same way the tenant-provider contract was found for m32 t006: `kubectl -n opensandbox-system exec <server-pod> -c server -- ls /usr/local/lib/python3.12/site-packages/opensandbox_server/` then grep for `exec`/`proxy`/`runs`/`stream` (see `api/proxy.py`, `services/sandbox_service.py`).
- The client already sends `OPEN-SANDBOX-API-KEY: <per-workspace key>` on every call (m32 t006); exec must carry it too so the server scopes to the caller's `<ws>-sandbox`.
- bex-api must NOT gain `pods/exec` — exec goes through the OpenSandbox server/execd, exactly as create/list/stop do.

## Steps

1. Inspect the running server's package to nail the exec wire shape (path, method, request body — command/args/tty, streaming framing: chunked, WS, or SSE).
2. Add `Client.Exec(ctx, tenantKey, id string, cmd []string, stdout, stderr io.Writer) (exitCode int, err error)` (or a streaming variant returning an `io.ReadCloser`) matching that shape.
3. Map OpenSandbox exec errors (sandbox not running, not found) onto the client's error conventions.
