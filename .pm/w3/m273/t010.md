## Objective

Make the DoD's first bullet true for the case it names: a private image service whose process binds a port its image does not declare. Today the readiness probe targets the image's declared primary, and port discovery only scans a Ready pod. A process bound elsewhere therefore never becomes Ready and is never scanned, and its first deploy stays `update_in_progress` indefinitely.

## Context (live, production pin `cc3c51e12952`, which contains `c6bcb8741` and `dd31fbdef`; 2026-11-05 QA run 87, `bex-canary`)

- Failing case:
  - `POST /v1/services` created `{type:"private_service", name:"qa-20261105-pserv87", image:{imagePath:"docker.io/traefik/whoami:v1.10"}, serviceDetails:{plan:"starter", runtime:"image", envSpecificDetails:{dockerCommand:"/whoami --port 8080"}}, envVars:[{key:"PORT",value:"8080"}]}` → 201 `srv-dbmblckrv9ic73d23e70`.
  - The log shows `Starting up on port 8080` at 17:19:58Z.
  - The deploy `dep-dbmblckrv9ic73d23e7g` was still `update_in_progress` at 17:32:31Z, more than 12 minutes later. REST and GraphQL read `port: 80`, `openPorts: [80]`. `GET …/env-vars` returns `PORT=8080`.
  - The deploy page says: "a TCP connect to port 80 … Nothing accepted a TCP connection on port 80, the primary port selected from the image's declared TCP ports (80)".
- Control (same image, command and `PORT`, `type: web_service`, free): `srv-dbmbprsrv9ic73d23e90` was Live within ~30s with `port: 8080`, and `curl https://qa-20261105-web87.onbex.co/` → 200. A web image service honors an effective `PORT` (`ConfiguredImagePort`); a private one does not.
- Causes:
  - `lego/operator/internal/controller/private_ports.go:173-196`: `readyPodIP` requires `podReady`, and `scanPrivatePorts` (`:105`) returns nil without one. Discovery cannot rescue a release that its own readiness probe holds back.
  - `lego/operator/internal/controller/app_controller.go:678-680`: `if app.Spec.UsesImagePorts() { app.Status.EnvPort = 0 }` discards `PORT` for image-port private services.
  - `lego/types/v1alpha1/image_network.go:195-203`: `ConfiguredImagePort` honors `EnvPort` only when `UsesWebImagePorts()`. The same web-only gate appears at `image_network.go:284` and in the stall hint at `app_controller.go:5785`.
  - ADR018's `PORT` row ("an effective `PORT` … wins") and `docs/ADR089-*.md` D3 phase 2 promise otherwise.
- Render: a private service must bind at least one listener, and Render detects its open ports (render.com/docs/private-services). A process listening on 8080 deploys and is reachable on 8080 whatever the image declares.

## Steps

1. Choose the primary port for a private image-port service in this order:
   - an effective `PORT`;
   - otherwise an explicit configured port;
   - otherwise the first declared port.
   Make it the probe target and the network primary, as for web.
   - Widen `ConfiguredImagePort` and `image_network.go:284` to `HasImagePorts()`.
   - Drop the `EnvPort = 0` branch at `app_controller.go:679`.
   - Make the stall hint name `PORT` for both types.
2. For a private service with no `PORT` whose declared primary never accepts a connection, the first rollout must not wait forever. Scan Running-but-not-Ready pods of the candidate revision. When the scan finds a listener and the declared primary has none, select that listener as the primary. Otherwise stall with the existing hint.
3. Envtest cases:
   - Image declares 80, process binds 8080 with `PORT=8080` → Ready on 8080, `openPorts` contains 8080.
   - The same without `PORT` → discovered 8080 becomes the primary.
   - Regression: ClickHouse `[8123, 9000, 9009]` unchanged; a web image with `PORT` unchanged.
4. Live: rerun the failing case above in `bex-canary`. Reach `qa-…-pserv:8080` from a peer worker, then fold the result into t005.
