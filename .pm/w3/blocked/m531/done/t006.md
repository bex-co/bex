## Objective

Appearance gains Render's **Log Explorer Theme** choice: Match Dashboard (Default), Light, Dark, stored as `logThemeSetting` through `updateUserLogThemeSetting`. With Light or Dark, every log explorer renders in that theme whatever the dashboard's, in its high-contrast twin while High Contrast Mode is on.

## Context

- The stylesheet's dark variant is `@custom-variant dark (&:is(.dark *))` and the dark tokens sit on `.dark` (`dashboard/src/style.css`). A light subtree inside a dark page still matches `.dark *`, so forcing an explorer light on a dark dashboard needs the variant and the tokens to respect the nearest theme class.
- The explorers: `LogExplorer` (`dashboard/src/features/logs/components/log-explorer.tsx`) as used by `log-viewer.tsx` (service Logs tab), `datastore-log-viewer.tsx` (Postgres and Key Value), `project-log-viewer.tsx` (project Application and Request Logs) and `src/features/deploys/components/deploy-log-panel.tsx`.
- Render: `effectiveLogViewerTheme` is nothing for `MATCH_APP`, else the light or dark theme in its high-contrast twin when the mode is on. t001 records whether menus and tooltips opened inside the explorer follow its theme.

## Steps

1. Make the theme scope nestable in `style.css`: the `dark` variant and the token sets apply by the nearest `.light`/`.dark` ancestor, so a forced subtree can go either way. Check nothing outside the explorer changes (the page sweep and `theme-contrast.test.ts` stay green).
2. One hook gives the effective log theme; the explorer root carries its class. Portalled menus and tooltips from inside the explorer follow t001's finding.
3. Appearance: the Log Explorer Theme select with Render's three options, translated into all eight languages. Its skeleton gains the row at the ready size.
4. Tests: each setting puts the right class on each explorer's root, Match Dashboard puts none, High Contrast Mode reaches the explorer, and the select writes the mutation.
