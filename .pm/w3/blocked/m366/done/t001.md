## Objective

A store query that rebuilds run records from the durable facts, so history no longer depends on the operator's ten-entry status.

## Context

- `cronRunFacts` (`lego/backend/internal/store/reconciler.go:578-620`): started fact (`At` = StartedAt, `RunID` = `ids.Derive(ids.CronRun, run.Name)`), ended fact (`At` = FinishedAt, `Status` succeeded/failed/canceled, `ReasonCode`, `ExitCode`). Source keys `cron:<appID>:<runName>:started|ended` (`cronRunSourceKey`).
- Table `service_event_facts` (`store/migrations/0043_service_event_facts.up.sql`; index `service_event_facts_app_at_idx`). Cron facts exist from migration 0075 (2026-08-16); failure reasons from 0141.

## Steps

1. `ListCronRunFacts(ctx, appID, cursor, limit)`: one row per run id, joining started and ended, ordered by start time then run id descending; cursor = (startedAt, runID).
2. `LatestSucceededCronRun(ctx, appID)`: the newest ended fact with status succeeded.
3. Check both with `EXPLAIN` on a seeded table; add a partial index on `(app_id, type, at DESC)` for the two cron types only if the plan needs it.
4. Real-Postgres tests: more than ten runs, cursor paging, a started-only run, an ended-without-started run (a run older than the start fact).

## Files

- `lego/backend/internal/store/` (new query file + test), a migration only if the index is needed

## Acceptance criteria

- [ ] Paging returns every seeded run once, in order, across pages.
- [ ] The latest success is found behind ten newer failures.

## Out of scope

- Changing what the reconciler records.

## Result (2026-11-13)

- `lego/backend/internal/store/cron_run_history.go`:
  - `CronRunHistory` interface, with `ListCronRunRecords(appID, after, exclude, limit)` and `CronRunRecord(appID, runID)`, implemented by `PGStore`.
  - A run is its single `cron_job_run_ended` fact, ordered `(at, source_key) DESC`. A cron job never runs concurrently, so that is also start order. Its start joins by primary key on the sibling `…:started` key.
  - The cursor is a run id resolved to its position. An unknown id gives an empty tail.
  - Only runs with a recorded outcome are returned.
- Migration `0245_cron_run_history`:
  - Backfills `run_id` on cron facts from before 0141 (2026-10-05) with the same derivation as `id.Derive(id.CronRun, <job>)`: sha256, the first 100 bits, lowercase base32hex.
  - Adds the partial index `(app_id, run_id) WHERE run_id <> ''`.
- EXPLAIN on 3,000 seeded runs: an index scan on `service_event_facts_app_at_idx`, with the cursor row comparison inside the index condition, plus primary-key lookups. The cursor lookup uses the new partial index.
  - The first draft anchored canceled-before-start runs with a `NOT EXISTS`. The planner turned it into a hashed subplan that seq-scanned the whole table. Anchoring on the ended fact removed it.
- Real-Postgres tests (`cron_run_history_pg_test.go`):
  - 14 finished runs, a canceled-first run and a started-only run, paged by 5 with two excluded.
  - Every finished run appears once, in order. The orphan is absent. The unknown cursor and another app give nothing.
  - By-id reads, including the canceled-first run with no start.
  - The SQL backfill equals `id.Derive` for four job names, and never rewrites a recorded id.
