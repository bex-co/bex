## Objective

The service layer serves history beyond the status window without losing the live detail only status has.

## Context

- `ListCronRuns` / `GetCronRun`: `lego/backend/internal/apps/service.go:4322-4346`. `cronRunsOf` (`service.go:1360`) adds the unmaterialized canceled run and the pending manual run. `lastSuccessfulCronRunAt`: `service.go:1444`, used at `service.go:1192`.
- w4/m300 (blocked) owns the acknowledged-trigger and canceled-run semantics in these functions; w5/m108's no-resurrection rule reads `Status.CancelRunRecorded`.

## Steps

1. Merge: status entries win for any run id they carry (live phase, trigger details); facts supply runs status no longer holds. Keep newest-first order and the existing cursor semantics.
2. `GetCronRun`: status first, then the facts; the same 404 shape for unknown or foreign ids.
3. `lastSuccessfulRunAt`: the newer of the status scan and `LatestSucceededCronRun`.
4. A run whose terminal state is in status but not yet recorded as a fact shows its status state, never a regressed one.
5. A store-off backend (no Postgres) falls back to today's status-only behavior.

## Files

- `lego/backend/internal/apps/service.go` (and a focused helper file if clearer)

## Acceptance criteria

- [ ] Unit tests: eviction (11+ runs), a duplicate id in both sources, a pending manual run, a canceled-before-start run after eviction, ten failures after a success.
- [ ] w4/m300's existing tests pass unchanged.

## Out of scope

- Operator changes to `maxCronRuns`.

## Result (2026-11-13)

- `apps.Service.CronRunHistory` (nil in store-less mode) is wired from `cmd/api/main.go` through `api.Deps`.
- `cronRunPage`: the status window first (`cronRunsOf`, so live runs and triggers not yet in status keep their place), then `ListCronRunRecords` excluding the window's ids. A page the window fills never asks the store. A cursor outside the window pages the facts.
- `findCronRun`: status first, then the facts. Both `GetCronRun` and `CancelCronRun` use it.
- **Design change from this task's step 3 (worker's call):** `lastSuccessfulRunAt` comes from a durable operator status field, `App.status.lastSuccessfulRunAt`, not from a fact query. The reasons:
  - The service view is built by the pure `view(a)` on every REST, GraphQL and MCP path, lists included.
  - A per-cron fact query there would be N+1 on list. Doing it only on some paths would make mutation replies disagree with reads.
  - The operator already owns run status, and a status field reaches every surface at once.
  - The backend still takes the newer of the field and a scan of `status.runs`, so it is right against an older operator too.
- The w4/m300 and w5/m108 semantics are unchanged. The existing `cron_runs_test.go` cases pass untouched, and a canceled-first run stays canceled after eviction.
