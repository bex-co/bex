# 077 — A bare GET after a HEAD-first fill reads the stored page, not `MISS`

Why: when a HEAD is the first request for a cacheable path (uptime monitors and link checkers often go first), the edge fills its cache with a GET but a client's next bare GET still goes to the app. Cloudflare, Render's CDN, caches one object for that URL, so the GET reads `HIT` there.

- **Source:** w3/075's production check, 2026-11-19, pin `dff52c596d13` ([record](done/075.md#production-record-2026-11-19)). On a new key, a bare `curl -sI` read `200 MISS` and filled the cache with a GET. The next bare HEAD read `HIT`, but the next bare `curl -s` read `200 MISS`, and nginx logged a second `GET`.
- **Cause:** a HEAD fill stores the page under the HEAD's own encoding preference, which is identity for a bare client. Traefik adds `Accept-Encoding: gzip` to a GET that carries none, so the bare GET looks up the gzip key. `serve` (`lego/operator/internal/edgecache/edgecache.go`) reads the other key's page (`unencodedVariant`) only for a HEAD.
- **Constraint:** a GET that accepts gzip may read the identity key's page when that page states no `Content-Encoding` beyond `identity`, unless the client refused identity (`identity;q=0` or `*;q=0`). A GET that does not accept gzip must never read a gzip-encoded page.
- **Done when:** a unit test fills a key with a bare HEAD and then sends a GET with `Accept-Encoding: gzip`. The GET reads `HIT` with the full body and `Age`, and the origin sees one GET. A gzip-encoded page under the gzip key never answers a bare GET. On production, a bare `curl -sI` then a bare `curl -s` of a new cacheable path read `MISS`, then `HIT`. ~45m.

## Work record (2026-11-20)

- **Reference.** Cloudflare, Render's CDN, caches one object for a URL whatever its client's `Accept-Encoding`, so a GET after a HEAD-first fill reads `HIT` there.
- **Fix** (`8386c9f7c`, `lego/operator/internal/edgecache/edgecache.go`): `serve` reads the other encoding preference's page (`unencodedVariant`) on any miss of its own key, GET as well as HEAD. That page must name no `Content-Encoding` beyond `identity`, and the client must not refuse identity (`identity;q=0`, or `*;q=0` with no `identity` member of its own, RFC 9110 §12.5.3, `acceptsIdentity`). A gzip page still never answers a client that does not take gzip.
- **Tests** (`edgecache_head_test.go`):
  - `TestTheEdgesGzipGetReadsThePageABareHeadFilled`: a bare HEAD fills (`MISS`), then a GET with `Accept-Encoding: gzip` reads `HIT` with the full body, `Age: 7` and no `Content-Encoding`, a conditional one reads `304 HIT`, and the app sees one `GET identity`. The app gzips for a gzip client, so a GET that reached it would show.
  - `TestABareGetNeverReadsAGzipPage`: after the edge's GET stored a gzip page, a GET with no `Accept-Encoding` reads `MISS` and the identity body, and an `identity` and a `br` GET then read `HIT`, all without `Content-Encoding`.
  - `TestAClientThatRefusesIdentityNeverReadsTheIdentityPage` and `TestAcceptsIdentity`: `gzip, identity;q=0` and `gzip, *;q=0` miss and get the app's gzip page; `gzip, identity;q=0.1, *;q=0` and `gzip;q=0.5` read `HIT`.
  - `TestTheEdgesGzipGetReadsABareHeadsFillThroughEitherReplica`: on a two-replica tier, 16 paths are filled by a bare HEAD each, and the gzip GET reads `HIT` at either replica.
- **Proof the tests are real.** Restoring the HEAD-only condition fails the first, third and fifth tests. Dropping the identity check fails the refusal test. Dropping the `unencoded` check fails both gzip-page guards. `make test` and `make lint` pass.
- **Docs.** [ADR004](../../../docs/ADR004-app-deployment.md) § Edge caching has a paragraph on it, and the [ADR018](../../../docs/ADR018-render-parity.md) "Edge caching" row has one sentence.
