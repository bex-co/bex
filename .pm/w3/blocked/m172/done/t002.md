## Objective

Choose between (a) lazy minting — setup-mode Checkout without a pre-made Customer/Subscription, minted on `checkout.session.completed` — and (b) keep eager Customer minting but defer the Subscription to completion and reclaim abandoned Customers; record the rule in ADR040.

## Context

- `CreateCheckoutSession` passes `Customer` and, when tax is configured, `CustomerUpdate{Address,Name: auto}` + tax-id collection (`lego/backend/internal/billing/sessions.go:140-161`) — `customer_update` requires an existing Customer, which constrains option (a). Verify the current Stripe setup-mode Checkout contract (stripe-docs skill) before deciding.
- `verifiedCheckout` (`sessions.go:259`) proves ownership via the pre-existing Customer + `checkoutSubscriptionMetadataKey`; option (a) needs a new ownership proof (workspace metadata + `ClientReferenceID` + server-side session re-read).
- Legitimate eager owners: comped (`admin.go` comp), admin `provision` (`admin.go:62`), gate-off emitter (`emitter.go:303`).

## Steps

1. Verify the Stripe constraints for each option.
2. Pick one; t004's reclaimer stays either way as the backstop for Customers that do exist.
3. Write the rule ("who may own a Stripe Customer, and when it is reclaimed") into ADR040 §2.

## Outcome (2026-10-02)

Done — option (a), verified against Stripe docs: setup-mode Checkout supports `customer_creation=always` (Customer created only on a submit attempt; tax ids saved to it), while `customer_update` requires a pre-existing Customer.
