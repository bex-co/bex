## Objective

Render's sandbox build object (create, list and get) gained `failureCode`: "A machine-readable reason the build failed. Null unless the status is `failed` … Treat unrecognized codes as `internal_error`" (example `image_pull_failed`). bex's builds already end `failed` with a reason (w2/m358). Expose it as Render's code.

## Context

- `lego/backend/internal/sandbox/images.go` (`buildView`, `:280`) and the store's `SandboxBuild` failure reason.
- Map bex's failure reasons (pull failure, platform, size cap) to Render's codes where they match. Anything else maps to `internal_error`. Read the live schema for any published code list.

## Acceptance criteria

- [ ] A failed build reads its `failureCode` on REST, GraphQL and MCP. Every other build reads `null`. Response conformance against the new pin passes.

## Result (2026-11-13)

- Render's codes come from its SDK's `SandboxBuildFailureCode` enum (render-oss/sdk, 2026-11-13). The live spec only references it.
- Failures are recorded at fail time (`failure_code`):
  - the source registry's 401/403 → `image_access_denied`, its 404 → `image_not_found`, any other source failure → `image_pull_failed`;
  - the import timeout → `deadline_exceeded`;
  - bex's own registry, a lost credential, the stale sweeper or a group delete → `internal_error`.
- From simplify: a source layer read inside the write counts as a source failure (`fromOtherHost`), because the source image is lazy.
- Platform and size problems are 400s before an import starts, so they never become codes.
- Builds that failed before the code existed read `internal_error`. Every other status reads `null`. Exposed on REST, GraphQL `failureCode` and MCP.
- `TestBuildFailureCode`, plus the PG test's recorded code.
