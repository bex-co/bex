## Objective

On production, purging an edge-cached service and switching its caching profile leave its instances running and its cache behaving as on Render.

## Context

- Production pin: wait for a `chore(deploy): pin platform images to <sha>` commit that contains this milestone's commits (`git merge-base --is-ancestor`).
- QA user in `bex-canary` (`QA_EMAIL`/`QA_PASSWORD` in `.env`); production kubeconfig via `bash scripts/fetch-app-kubeconfig.sh <path outside the repo>`.

## Steps

1. On an edge-cached web service fixture in `bex-canary`, request a cacheable path twice and record `CF-Cache-Status: HIT`.
2. Record pod UIDs and `restartCount`, purge with REST `POST /v1/services/{id}/cache/purge`, and time how long until the path reads `MISS`, then `HIT` again. Record UIDs and `restartCount` again.
3. Switch the profile between `origin-controlled` and `origin-controlled-all` from the dashboard and record the UIDs.
4. Record how many production services have caching on, and how many of those have a disk.
5. Write the record into the milestone README.

- [ ] Pod UIDs and restart counts are unchanged across the purge and the profile switch
- [ ] The path reads MISS after the purge and HIT after that
