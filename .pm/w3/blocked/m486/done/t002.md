## Objective

The edge-cache proxy reads its purge generation and its profile from a downward-API annotations file it polls, instead of from its start-up environment. A new purge generation drops every stored entry; a profile change applies from the next request; `no-cache` turns it into a pass-through that answers `CF-Cache-Status: DYNAMIC`.

## Context

- `lego/operator/internal/edgecache/edgecache.go`: `Config.Profile`, `requestEligible` (~222), `store` / `removeLocked` (~435-470), the in-flight `fetch` (~278-333).
- `lego/operator/cmd/edge-cache/main.go` reads `BEX_EDGE_CACHE_PROFILE` once at start.
- A downward-API volume item for `metadata.annotations` is refreshed by the kubelet when the pod's annotations change; no restart.
- Design recommendation (from the brainstorm, not a user decision): a downward-API file rather than an admin endpoint, because it adds no listener reachable through the Service's port 19099, needs no credential, and finishes asynchronously like Render's `202`.

## Steps

1. Add an env var (e.g. `BEX_EDGE_CACHE_CONTROL`) naming the annotations file; parse `app.bex.co/cache-purged-at` and `app.bex.co/cache-profile` from it.
2. Poll it every few seconds. On a new purge value, clear the LRU and do not store a fill that started before the purge. On a new profile, swap it atomically.
3. With no file (a pod from an older template), keep using the env profile and today's behavior.
4. Unit tests: purge during an in-flight fill, profile switch, `no-cache` pass-through, missing file.
