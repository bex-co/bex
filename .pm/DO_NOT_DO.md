# DO NOT DO — roadmap anti-goals and guardrails

Use this file as a hard constraint when running `/pm-brainstorm` and `/pm`. If a proposed milestone/task conflicts with any item below, reject it.

## Anti-goals

- Do not propose roadmap work that is not clearly tied to bex's project goals/pillars (`docs/ADR008-vision.md`) or current platform roadmap intent.
- Do not create milestones that are vague, non-testable, or missing observable outcomes.
- Do not create milestones for sub-hour work; keep those as inbox notes (`wN/NNN.md`).
- Do not add "nice-to-have" work that has no clear sequence/dependency/risk rationale for why it must happen now.
- Do not duplicate existing milestones/tasks without a clear gap analysis and replacement intent.
- Do not propose work that conflicts with established architectural boundaries (bex product code vs platform GitOps responsibilities).
- Do not include tasks that cannot define concrete files/resources/systems they touch.
- Do not treat speculative ideas as committed roadmap items without explicit source context.
- **Do not OAuth2-ize the first-party dashboard.** The dashboard authenticates with its Kratos session (HttpOnly cookie, same-site) — never make it a Hydra OAuth2 client, and never store OAuth access/refresh tokens (or Kratos session tokens) in browser-readable storage. IETF `draft-ietf-oauth-browser-based-apps` ranks browser-held tokens last (BFF/cookie-session first); Ory's own guidance is "first-party apps use Kratos sessions; Hydra is for third-party/machine clients". Local-dev cross-origin is a dev-workflow problem — solve it with the Vite dev proxy (`dashboard/.env.example`, same-origin tunnel), not by changing the production auth architecture. (Learned from a reverted, never-committed dashboard-as-OAuth2-client attempt, 2026-07-07; the corrected **provider-side** work is `w4/m9`, which keeps the dashboard on sessions.)
- **Do not hand-build a Hydra login/consent provider.** Kratos's native `oauth2_provider.url` integration accepts Hydra login challenges itself (the login UI only passes `login_challenge` through); at most a headless consent acceptor is needed. A custom provider app (in bex-api or the dashboard) re-implements what Kratos ships. (Same lesson from the reverted 2026-07-07 attempt; `w4/m9` is the corrected design.)
- **Do not build a "Link database to service" picker in the dashboard** (an "Add from database" env-var flow that inserts a managed database's connection string into a service's environment). Render has no such dashboard feature — its env editor offers only **+ Add Environment Variable** and **Add from .env** (verified against render.com/docs/configure-environment-variables, 2026-07-08); the Render flow is copy the Internal Database URL from the database page, paste it into the service's env vars, and the m8 Databases page (connection-info reveal + copy buttons) plus the existing Environment tab already cover that. Render's only first-class DB→service linkage is the Blueprint `fromDatabase` field (IaC) — if bex ever mirrors that, it's `bex.yml`/backend spec work (w1), not a dashboard picker. (Withdrawn from `/pm-brainstorm for w5`, 2026-07-08.)
- **Do not build hosted agent sandboxes (E2B-compatible execution environments) for now — pillar 5 is off the roadmap.** User decision 2026-07-08 (follow-up to `/pm-brainstorm for w2`): the Render-alternative core — in-cluster builds (w1/m5), tenancy + enforced authz (w1/m9), elasticity (w1/m3), Render parity (w1/m13, w2/m4–m5) — is unfinished, and sandboxes are a second product surface competing for the same worker capacity; the mechanism is also single-host-only today (opensandbox Docker runtime `:8077`; the k8s snapshot path is blocked — docs/ADR014-sandboxes.md D5/D6). Do not propose sandbox milestones, tasks, or adjacent UX/pricing work (e.g. the GitHub-premium-request consumption model discussed 2026-07-08) unless the user explicitly re-opens pillar 5. `w2/m3` removed 2026-07-08; the design record stays in docs/ADR014-sandboxes.md (ADR, status: proposed) so a future re-open starts from the settled architecture, not from scratch. **Narrow carveout:** interactive SSH into an already-running service instance is not a hosted sandbox and was explicitly reopened by the user on 2026-07-14; it is tracked as `w2/m39` and does not reopen ephemeral shells or the rest of pillar 5. **Re-opened 2026-07-27** by explicit user decision: pillar 5 is back on the roadmap. The single-host mechanism blocker that motivated the 2026-07-08 pause is removed by the in-cluster multi-node OpenSandbox Kubernetes-runtime substrate + Kata isolation ([docs/ADR042-sandbox-cluster-substrate.md](../docs/ADR042-sandbox-cluster-substrate.md)); the gateway design stays in [docs/ADR014-sandboxes.md](../docs/ADR014-sandboxes.md). Tracked as `w3/m32` (per user direction, placed in w3 alongside the related `w3/m31` tenant-namespace-isolation work — both are cross-theme for the Observability workstream, recorded here so the placement is intentional, not drift).
- **Do not firewall `:22`/`:6443` with a static source-IP allowlist (the w1/m7 t001 `bex-app` firewall).** Removed 2026-07-09 (Terraform `hcloud_firewall.app` + `app_cluster_name` var deleted from `infra/terraform/`). A static `allowed_ssh_cidrs` fits neither the operator (dynamic residential IP — locks himself out on the next lease) nor CI (GitHub-hosted runners use large dynamic egress ranges — locks out `deploy.yml`/`app-cluster.yml`). So `:22`/`:6443` stay **authentication-only** (key-only SSH gated by the `bex` key + kube TLS/RBAC), an accepted single-layer baseline recorded in [docs/ADR019-infra-credentials.md](../docs/ADR019-infra-credentials.md) §Decisions. If a network second layer is ever wanted, the correct form is **Tailscale/WireGuard** (lock to a stable tailnet, with a tailnet-joined self-hosted CI runner) — _not_ a static CIDR. Do not re-propose the static-allowlist firewall. (User decision 2026-07-09, after the t005 LB outage post-mortem surfaced that none of t001 had ever applied to prod anyway.)
- **Do not build the Render capabilities the parity audit marked deliberate non-goals** (the `—` rows in [docs/ADR018-render-parity.md](../docs/ADR018-render-parity.md); recorded here 2026-07-09 so `/pm-brainstorm`/`/pm` reject them — the ledger rows stay as the evidence map):
  - **Persistent disks** (Render `/disks` + Disks tab) — bex is stateless-first (managed Postgres/Key Value hold state); disks disable multi-instance + zero-downtime deploys, which fights the dense bin-pack + free-tier-sleep economics.
  - **One-off jobs (`/services/{id}/jobs`) and ephemeral shell instances** — execution products beyond connecting to an already-running service remain off-roadmap with pillar 5. Interactive SSH into a running service, plus the user public keys required to authenticate it, was explicitly reopened on 2026-07-14 and is tracked in `w2/m39`. The **browser-hosted Shell terminal** (Render's in-dashboard Web Shell attached to an already-running instance) was explicitly reopened by the user on 2026-07-17 and is tracked in `w2/m55` — it rides `w2/m39`'s isolated-gateway exec mechanism, keeps `pods/exec` off bex-api, and streams the terminal only over an authenticated gateway WebSocket (the ADR035 §non-goal rewrite is `w2/m55` t001). Do **not** expand either milestone into the still-excluded surfaces: one-off jobs, ephemeral/`--ephemeral` shells, cron shells, hosted sandboxes, SFTP/SCP, or forwarding.
  - **Static-site CDN cache purge** — Render's `POST …/cache/purge`. bex's static-server caches immutable per-revision objects (a deploy is a new revision ⇒ a new prefix, so there is nothing stale to purge), so an explicit purge API has no job to do — non-goal. (Header rules + redirects/rewrites were the other half of this row; they **shipped** in `w1/m21` once `w1/012` was promoted — see [render-parity.md](../docs/ADR018-render-parity.md) and [docs/ADR029-static-sites.md](../docs/ADR029-static-sites.md).)
  - **External log/metric drains** (Render `owner-log-stream`/`resource-log-streams`/`owner-metrics-stream`) — third-party observability-drain integrations, non-goal.
  - **Enterprise/managed-infra surfaces: SSO/SAML · SCIM, maintenance runs, dedicated outbound IPs** — non-goal for now (Ory can add SSO later if it ever matters).
  - **Workflows & tasks** (Render's `/workflows`/`/tasks`/`/task-runs` orchestration product) — an orchestration surface, not a hosting primitive; off-roadmap.
- **Do not build PR preview environments** (Render `POST …/previews` + Previews tab — spin up a temp App per pull request, tear down on close/merge). Proposed as `w2/m11` during `/pm-brainstorm more` 2026-07-12 (unblocked by w2/m8–m9's GitHub App integration) and rejected by user decision the same day. Do not re-propose unless the user explicitly re-opens it.
- **Do not use vcluster (or any per-tenant virtual control plane) as a tenant isolation tier.** It only isolates the control-plane/API axis — a surface bex's Render-style product never exposes to tenants (they never touch Kubernetes) — while workloads still share the host kernel and network, so NetworkPolicy + a sandboxed runtime are still required regardless. It is **not** a security boundary. Per-tenant control planes also multiply operational surface (upgrade/backup/monitor N apiservers) and carry always-on overhead that fights bex's dense bin-pack + free-tier-sleep economics. The isolation ladder is **namespace (default) → microVM (Kata/Firecracker/gVisor, hard)**; "tenant wants their own kubectl/CRDs" is a niche BYO-Kubernetes product feature, not an isolation strategy. (Rejected w1/m6, 2026-07-07.)
- **Do not materialize or start an OpenChoreo/Korifi substrate spike now.** User decision 2026-07-19: both remain uncommitted future candidates documented in `docs/ADR039-operator-audit-and-platform-reuse.md`, not work that automatically follows `w2/m59`–`w2/m61`. Completing those operator-fix milestones is necessary evidence but does not authorize a PoC, adapter, migration, or new engine abstraction. Re-open only on an explicit future user decision, then materialize a separate milestone with a fresh current-version/code/licensing review and the ADR039 compatibility/isolation gates.
- **Do not build Bitbucket git-provider integration** (connect + repo listing + private deploy + push-to-deploy, mirroring the GitHub App shape). Proposed during `/pm-brainstorm more milestones to work on` 2026-07-13 and rejected by user decision the same day. `docs/ADR018-render-parity.md`'s Git connections row still records Bitbucket as an untracked `◐` divergence — that's accurate and stays as-is, it just isn't roadmap work. Do not re-propose unless the user explicitly re-opens it.
- **Do not develop a first-party bex CLI from scratch.** User decision 2026-07-14, resolving the standing "bex CLI" scope question flagged in every `/pm-brainstorm` round since round 3: Render's fifth surface (the `render` CLI) is covered by pointing **Render's own official CLI** ([render.com/docs/cli](https://render.com/docs/cli), open-source `render-oss/cli`) at bex-api — bex is Render-API-compatible, so the CLI is a _client to verify_, not a product to build. Compatibility is tracked in `docs/cli-compatibility-checklist.md` (owned by `w9/m2`); gaps the checklist surfaces become work against **bex-api** (or upstream-documented workarounds), never a bespoke/forked CLI codebase. Do not propose writing, forking, or vendoring a CLI unless the user explicitly re-opens this.
- **Do not build Slack deploy-notification delivery** (Render's owner-level `slackEnabled` on `PATCH /notification-settings/owners/{ownerId}` plus a Slack-app/OAuth integration). Surfaced by `/pm-brainstorm` round 14 (2026-07-15) from `docs/render-artifacts/notify-on-fail.md:49-50` and declared a non-goal on the round's recommendation (user approved "materialize them all"): it is the same external-integration class as the already-rejected log/metric drains, and bex's composition answer already exists — point an outbound event webhook (`/v1/webhooks`, w3/m11 + w3/m27) at a Slack bridge. The `notify-on-fail.md` divergence note stays accurate as-is. Re-propose only if the user explicitly re-opens third-party notification integrations.
- **Do not build GitLab git-provider integration** (connect + repo listing + private deploy + push-to-deploy, mirroring the GitHub App shape). Proposed during `/pm-brainstorm more for w2` 2026-07-13 and rejected by user decision the same day. Combined with the Bitbucket rejection above, bex's git-connection surface stays GitHub-only by deliberate choice — `docs/ADR018-render-parity.md`'s Git connections row's "GitLab/Bitbucket providers remain ◐ (out of scope)" note is accurate and stays as-is. Do not re-propose unless the user explicitly re-opens it.

## Minimum bar for a meaningful milestone

Every proposed milestone must include:

- goal linkage (which project goal/pillar it advances),
- expected outcome (observable impact),
- why now (dependency/risk/sequence rationale),
- definition of done with testable end state.
