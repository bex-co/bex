# Serve Postgres `replication_lag` for read replicas on non-HA databases, excluding the primary pod's fake zero

Why: Render monitors replication lag for every Postgres database with read replicas regardless of whether High Availability is enabled (`render.com/docs/postgresql-read-replicas`, `GET /v1/metrics/replication-lag`), whereas bex returns empty `replication_lag` on REST, GraphQL, MCP, and shows N/A on the dashboard whenever `highAvailabilityEnabled` is false.

## Evidence

- `lego/types/v1alpha1/database_types.go:277-292`: `ReadReplicas` is explicitly independent of `EnableHighAvailability`.
- `lego/backend/internal/metrics/datastore.go:332,455-461`: gates `MetricReplicationLag` strictly on `db.Status.HighAvailabilityEnabled`, returning `nil` for a non-HA database that has read replicas.
- `lego/backend/internal/metrics/source.go:831-835`: `NewPrometheusReplicationLagSource` already matches replica clusters via `appv1alpha1.DatabaseClustersPattern(req.Cluster)`, and `deploy/gitops/base/prometheus.yaml:968` already scrapes `cnpg_pg_replication_.*` (which includes `cnpg_pg_replication_in_recovery`). Without constraining to recovery pods, CNPG's primary pod exports `cnpg_pg_replication_lag = 0`.
- `dashboard/src/features/metrics/components/datastore-metrics-panel.tsx:186-187,460` and `dashboard/src/routes/databases.$databaseId.tsx:464`: skip querying `replication_lag` and show the N/A state based solely on `!highAvailabilityEnabled`, ignoring `database.readReplicas.length > 0`.

## Fix

1. In `lego/backend/internal/metrics/datastore.go`, gate `MetricReplicationLag` on `db.Status.HighAvailabilityEnabled || len(db.Spec.ReadReplicas) > 0` (leaving lone non-HA primaries with no read replicas returning empty `nil`, never a fake zero).
2. In `lego/backend/internal/metrics/source.go`, constrain `NewPrometheusReplicationLagSource` to standby/replica pods (`max by (pod) (cnpg_pg_replication_lag{namespace=...,cnpg_io_cluster=~...} and on (pod) cnpg_pg_replication_in_recovery{namespace=...,cnpg_io_cluster=~...} == 1)`), so the primary pod's `0` is never emitted alongside read replicas or standbys.
3. In `dashboard/src/features/metrics/components/datastore-metrics-panel.tsx` and `dashboard/src/routes/databases.$databaseId.tsx`, pass `hasReadReplicas` (or `replicationLagEnabled = highAvailabilityEnabled || readReplicas.length > 0`) so the Replication Lag chart renders for databases with read replicas even when HA is off.
4. Update `docs/ADR018-render-parity.md` (`Extended metrics`) and add regression tests in `lego/backend/internal/metrics/datastore_test.go` and `dashboard/src/features/metrics/components/__tests__/datastore-metrics-panel.test.tsx`.

## Acceptance criteria

- [x] A non-HA Postgres with one or more `spec.readReplicas` returns real per-replica `replication_lag` series on REST `/v1/metrics/replication-lag`, GraphQL `datastoreMetrics(name: REPLICATION_LAG)`, and MCP `get_datastore_metrics`.
- [x] A non-HA Postgres with no read replicas still returns empty (no fake zero), and the primary pod's `cnpg_pg_replication_lag = 0` is excluded by the `cnpg_pg_replication_in_recovery == 1` filter.
- [x] The dashboard Postgres Metrics panel queries and renders Replication Lag when `highAvailabilityEnabled` is true **or** `readReplicas.length > 0`, and keeps its N/A state when neither is set.
