# 009 — A database whose first backup completes beside another's can read no recovery window for up to 30 minutes

Why: the upgrade gate (since `29d664572`) and point-in-time recovery read a workspace database's completed backup from the Barman Cloud plugin's recovery window in the shared ObjectStore. The plugin drops that write when it conflicts with another database's write, so a paid database with a completed backup is refused a major-version upgrade (409 `POSTGRES_UPGRADE_BACKUP_REQUIRED`) and offers no recovery (`BACKUP_NOT_READY`) until the plugin's next retention pass. On Render, both are available once the first backup completes.

## Evidence (production pin `ad799a7cf32b`, 2026-11-21, found by w34/m543's second replay)

- `bex-canary` (`tea-daif693dqjvc73e7as3g`) had two 10 GB `basic_256mb` databases created within seconds of each other: `dpg-dc11h4k6t83c738ncud0` (PostgreSQL 16) and `dpg-dc11h4k6t83c738ncue0` (17). Their first plugin Backups completed at 22:19:50Z and 22:19:53Z.
- The 17 instance's `plugin-barman-cloud` sidecar logged `Refreshing the recovery window`. It then logged `Error while updating the recovery window in the ObjectStore status stanza. Skipping.` with `Operation cannot be fulfilled on objectstores.barmancloud.cnpg.io …`: an optimistic-concurrency conflict on `bex-tenant-postgres`, the one ObjectStore every database in the namespace writes its window to.
- `status.serverRecoveryWindow` held `tea-daif693dqjvc73e7as3g-dpg-dc11h4k6t83c738ncud0` but no key for `…-dpg-dc11h4k6t83c738ncue0`. So `GET /v1/postgres/dpg-dc11h4k6t83c738ncue0/recovery` read `BACKUP_NOT_READY`, and `PATCH {"version":"18","dryRun":true}` answered 409 `POSTGRES_UPGRADE_BACKUP_REQUIRED`.
- The plugin's retention pass (`retentionPolicyIntervalSeconds: 1800` on the ObjectStore, `Applying backup retention policy` at 22:48:50Z) wrote the window 29 minutes after the backup. Then the recovery read `AVAILABLE` from 22:19:53Z, and the dry run answered 200. Across production's six tenant ObjectStores, no other database with a completed backup was missing a window at 22:35Z.
- bex's readers: `hasCompletedBackup` and `recoveryWindow` (`lego/backend/internal/postgres/service.go`, `recovery.go`). The ObjectStore: `deploy/gitops/charts/barman-cloud-objectstores/tenant-postgres.yaml`. The plugin: `deploy/gitops/charts/barman-cloud-plugin/upstream/manifest-0.13.0.yaml` (v0.13.0).

## Done when

- Two paid databases created together in one workspace both read `recoveryStatus` `AVAILABLE` within a minute or two of their first backups completing, and both accept an upgrade dry run. Possible routes: a shorter retention pass, a bex-side refresh of a missing window, a plugin release that retries the status write, or a gate that trusts a completed Backup of the database's only archive generation. Never let a backup from an earlier generation authorize an upgrade.
- A regression test covers the window a dropped write leaves missing, for the gate and for recovery.

## Fixed (2026-11-21, `c6ad07748`, `/loopx w34`)

- **Route:** a bex-side read of a missing window. Plugin v0.16.0 (the newest, 2026-11-09) and its `main` still write the window with one `Status().Update` from the ObjectStore read before the backup, with no retry (`internal/cnpgi/instance/recovery_window.go`), so no plugin release fixes it. A shorter retention pass would add a write per database to the same contended object, and a bex write to the plugin's status would make its own writes conflict more.
- **Change:** while the ObjectStore has no window for the generation, `recoveryWindow` (`lego/backend/internal/postgres/recovery.go`) reads the window the generation's completed CNPG `Backup`s span, from the first `status.stoppedAt` to the last, which is how the plugin computes its window from the catalog. Recovery info, `recover` and the upgrade gate (`hasCompletedBackup`) all read it. A `Backup` belongs to the generation by its `serverName`, or, as the plugin leaves that empty, by CloudNativePG's `status.majorVersion` (each generation is one major), so a backup from before the last upgrade authorizes neither. ADR009 and the ADR018 recovery row say so.
- **Checked on production (read-only, 2026-11-21):** all 145 plugin `Backup`s carry `majorVersion`, and for every database with backups enabled the window the `Backup`s span equals the ObjectStore's to the second.
- **Tests:** `TestTheGenerationsBackupAuthorizesUpgradeAndRecovery` (REST recovery status and the upgrade dry run, for a dropped write, a running or failed backup, another database's backup, the generation before the last upgrade, and the post-upgrade backup) and `TestTwoDatabasesBackedUpTogetherBothReadTheirWindow` (the production pair on REST, GraphQL, MCP and `recover`). Both fail with the old code.
- **Left:** the live check. Once the pin carries `c6ad07748`, as the QA user in `bex-canary`, create two 10 GB `basic_256mb` databases within seconds of each other. Within a minute or two of each first plugin `Backup` completing, both `GET /v1/postgres/{id}/recovery` must read `AVAILABLE` and both `PATCH {"version":"18","dryRun":true}` must answer 200. Record whether a sidecar logged `Error while updating the recovery window` (the drop is a race, so the pair may not lose a write this time). Delete both fixtures, check each by-id `GET` answers 404, and close.
