## Objective

An abandoned or stalled slot keeps WAL forever when `max_slot_wal_keep_size` is `-1`, PostgreSQL's default, which CNPG keeps. On an enabled database the operator sets a bound sized from the disk, so a slot that falls too far behind is invalidated instead of filling the volume or growing it through disk autoscaling.

## Context

- CNPG v1.30.1 `docs/src/replication.md` recommends setting it explicitly ("e.g. `max_slot_wal_keep_size: \"10GB\"`").
- Tenant parameter writes are refused for operator-managed names (`lego/backend/internal/postgres/service.go:1654` `operatorManagedParameters`); add this name there so a tenant cannot lift the bound.
- Disk autoscaling grows storage as it fills ([ADR009](../../../docs/ADR009-postgresql-management.md) § disk autoscaling); the bound must sit below the autoscaling trigger.
- Render's value is unknown; [w34/001](../001.md) captures it. Pick a value, state it in ADR009 as bex's choice, and say how it scales with `storageGB`.

## Steps

1. Set `max_slot_wal_keep_size` on the CNPG Cluster while `spec.logicalReplication` is present; leave it unset otherwise.
2. Add it to `operatorManagedParameters`.
3. Document the value and the invalidation behavior (the slot's `wal_status` becomes `lost`; the subscriber must resync).

## Acceptance criteria

- [ ] `SHOW max_slot_wal_keep_size` reads the bound on an enabled database and `-1` on one that is not enabled.
- [ ] A tenant parameter write naming it is refused like the other operator-managed names.

## Out of scope

- A notification when a slot is invalidated: Render has no such event type.
