## Objective

bex's operators play Render's support team: one verb, reachable only on bex-api's cluster-internal listener, takes Render's request inputs (database id, publisher role, schemas, all tables or not), checks Render's prerequisites, writes `spec.logicalReplication`, grants the role read access to the named schemas, and records an audit event. A second form disables.

## Context

- The internal mux: `opsrole.Register(internalRoot, …)` in `lego/backend/cmd/api/main.go:1487`; the ADR088 §4 pattern (static bearer, never the public `:8090` mux).
- Plan gate: add a `FeatureLogicalReplication` with `minimum: planPro` beside `FeatureNetworkIsolation` (`lego/backend/internal/core/plan_gate.go:82`).
- Storage: the database's effective storage is at least 10 GB (`Database.spec.storageGB`, else the plan's default).
- The role must be one of the database's credentials (the owner or a `spec.users` entry), per t003's decision.
- Schema grants (`GRANT USAGE ON SCHEMA …`, `GRANT SELECT ON ALL TABLES IN SCHEMA …`, `ALTER DEFAULT PRIVILEGES … GRANT SELECT`) run as the owner through bex-api's direct query path (`lego/backend/internal/postgres/query.go`). Render's form asks for the schemas, which implies it grants them; if t001 decides otherwise, the runbook tells the user to grant.

## Steps

1. Add the verb and its refusals: `LOGICAL_REPLICATION_PLAN_REQUIRED` (below Pro), `LOGICAL_REPLICATION_STORAGE_TOO_SMALL` (under 10 GB), `LOGICAL_REPLICATION_ROLE_UNKNOWN`, a free plan, a suspended or deleting database. Each refuses before any write.
2. Write the spec field, run the grants, wait for the operator's convergence (role attribute, publication), and answer with the outcome.
3. Record an audit event for enable and disable.
4. Write `docs/runbooks/postgres-logical-replication.md`: the request inputs, the call, how to check the result, how to disable.
