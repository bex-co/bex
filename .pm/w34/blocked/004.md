# A Postgres user's password Secret outlives its database

Why: deleting a database on Render removes everything that belongs to it, but on bex the password Secret of every user added with `POST /v1/postgres/{id}/users` stays in the workspace namespace after the database is gone. Production had 18 such Secrets on 2026-11-21 (found by w34/m542's production replay).

- **Premise.** `CreateUser` (`lego/backend/internal/postgres/access.go:209-219`) creates `<db>-user-<digest>` with no owner reference and no label. `DeleteUser` deletes it (`access.go:267`), but nothing deletes it when the database is deleted. The operator's `db-finalizer` and the Cluster's garbage collection only reach objects the Database owns.
- **Evidence (2026-11-21, pin `cce6c749f6ff`).** Every `dpg-*-user-*` Secret on production belonged to a database that no longer exists: 18 before this replay's own one was deleted by hand, 17 after. Among them is `dpg-dc0me40n82tc73dukfq0-user-…` in `tea-daif693dqjvc73e7as3g`, left by w34/m541's replay (created 09:45Z, database deleted 09:50Z). Each still holds the username and password of a role whose cluster is gone.
- **Paths:** `lego/backend/internal/postgres/access.go` (`CreateUser`, `postgresUserSecretName`), and the operator's Database deletion (`lego/operator/internal/controller/database_controller.go`, the `app.bex.co/db-finalizer` teardown). A recovered copy does not reuse its source's `spec.users` (`recovery.go:464` carries only the retirements), so an owner reference to the issuing Database is safe.
- **End state:** a user Secret is owned by its Database (or removed by the finalizer), so deleting a database leaves no `<db>-user-*` Secret. A test covers it, and the existing orphans on production are removed once, by an operator, after the fix ships.

**Fixed 2026-11-21 in `74c5c00b8`; parked for the live check.** bex-api owner-references each new user Secret to its Database (`access.go`, `createUser`), and the operator's finalizer deletes every `spec.users` Secret named `<db>-user-…` once the Cluster is gone, holding the Database until it can (`database_controller.go`, `deleteUserSecrets`), so a Secret created before the owner reference goes too. `TestUsersCRUD` and `TestDatabaseDeletionRemovesAddedUsersSecrets` cover both halves, and each fails with its half reverted. Re-read on production the same day, still on the old pin: 17 `dpg-*-user-*` Secrets in three workspace namespaces, none with an owner, none of their databases among the 6 live ones. They are left until the deploy, so one sweep also catches any made in between. **Next, once the pin carries `74c5c00b8`:** in `bex-canary`, create a fixture Postgres, add a user, delete the database and confirm that no `<db>-user-*` Secret remains. Then delete each pre-fix orphan once, after checking that no Database of that name exists in its namespace and that no live `spec.users` names it (names only, never the contents). Then close.
