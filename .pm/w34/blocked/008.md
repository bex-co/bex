# 008 — An old primary that rejoins after a clean failover keeps stale logical slots, and slot synchronization stops on it

Why: on an HA publisher on PostgreSQL 17 or later, the next failover or switchover onto that instance no longer carries a `failover = true` subscription's slot as synchronized. It reuses a stale copy, which holds back WAL on the standby until `max_slot_wal_keep_size` invalidates it, and the subscription then has to be re-created.

## Evidence (production pin `7e481dece7ac`, 2026-11-21, found by w34/m543's replay)

HA PostgreSQL 18.6 publisher `dpg-dc0s50i5r8pc73e308p0`, slot synchronization on (w34/m543 t001), an outside PostgreSQL 18 subscriber with `s_ha` (`failover = true`) and `s_nofo` (without):

- Before: the standby listed `s_ha` with `synced = t`; `s_nofo` was not on it.
- `kubectl delete pod <primary>` (smart shutdown, about three minutes while a writer stayed connected) promoted the standby. The old primary rejoined without `pg_rewind` and kept both slots with `synced = f`, at the position it stopped. Its log repeated `exiting from slot synchronization because same name slot "s_ha" already exists on the standby` for as long as it was the standby.
- A switchover back to it (`POST /v1/postgres/{id}/failover`) streamed `s_ha` from that stale copy (`logical decoding found consistent point at 0/708D198`). Nothing was lost or duplicated in this run, only because the copy still held all the WAL. `s_nofo`, which had read `replication slot "s_nofo" does not exist` on the other primary, resumed as well.
- After a forced Pod deletion (`--grace-period=0 --force`), `pg_rewind` ran on the old primary, its slots were gone, and it logged `newly created replication slot "s_ha" is sync-ready now`. So only a clean rejoin keeps the stale slots.

## Direction

- PostgreSQL's slot sync worker never replaces a slot it did not create (`synced = f`). The rejoined standby's logical slots with `synced = false` have to be dropped once it runs as a standby of an HA publisher with `synchronizeLogicalDecoding`: by CloudNativePG (check releases after 1.30.1 and its issue tracker) or by bex's operator through a superuser connection to the replica.
- Record the outcome in ADR009 § Lifecycle › Failover and switchover.

## Done when

- After a Pod-deletion failover on an HA 17+ publisher, the rejoined standby lists every failover-enabled slot with `synced = t` within the sync interval and holds no logical slot with `synced = f`.
- A second failover or switchover back loses and duplicates no row on a `failover = true` subscriber, on a real cluster.

## Fixed 2026-11-21 (`/loopx w34`, `44d7d8d5b`); the production replay waits for the pin

- **Upstream first.** CloudNativePG v1.30.2 (2026-11-17), the newest release, does not drop them: [cloudnative-pg#9969](https://github.com/cloudnative-pg/cloudnative-pg/issues/9969) describes exactly this and is open (reopened after going stale), and its two fixes, [#9998](https://github.com/cloudnative-pg/cloudnative-pg/pull/9998) and [#10006](https://github.com/cloudnative-pg/cloudnative-pg/pull/10006), wait for review. So bex does it.
- **Where.** The operator is the DB-free manager (`lego/operator/AGENTS.md`, `lego/backend/.golangci.yml`), so the sweep is bex-api's, beside its other tenant-database connections: `StandbySlotSweeper` (`lego/backend/internal/postgres/standby_slots.go`, every 30 s, started in `cmd/api/main.go`).
- **What it drops.** On each Running instance of an HA publisher's own Cluster labelled `cnpg.io/instanceRole: replica` (never a read-replica Cluster, which users reach), when it runs 17 or later and is in recovery: every logical slot that is not `synced`, not active and not temporary, re-checking both in the drop statement. `failover = false` copies go too, so the standby holds no `synced = f` slot (Done when 1), and their `catalog_xmin` stops reaching the primary through `hot_standby_feedback`.
- **How it connects.** As CloudNativePG's `streaming_replica` (`REPLICATION`, which dropping a slot takes), into the `postgres` database, the only one CloudNativePG's `pg_hba` admits it to by certificate; a logical slot can be dropped from another database of the instance (checked on 18.7). Client certificate `<id>-replication`, server chain verified against `<id>-ca` and `<id>-public-ca` (verify-ca, as CloudNativePG's replication), no plaintext fallback. No RBAC change: bex-api already reads every Secret of a tenant namespace.
- **Checked locally (PostgreSQL 17.11 and 18.7 containers, shaped as CloudNativePG shapes them: `sync_replication_slots`, `hot_standby_feedback`, `synchronized_standby_slots`, TLS, `streaming_replica` by certificate).** A clean shutdown of the primary and a promotion reproduced the production log: the rejoined instance kept `s_ha` (`failover`) and `s_nofo` at `0/3000060`, both `synced = f`, and its sync worker exited every 10 s on `s_ha`. bex-api's sweep, run through its real code against that instance, dropped both; 12 s later the sync worker logged `newly created replication slot "s_ha" is sync-ready now`, `s_ha` read `synced = t` at the primary's position, and no further error followed. Against the primary it dropped nothing, and a server certificate from another CA was refused.
- **Tests.** `TestStandbySlotSweepLeavesAPrimarysSlots` (real PostgreSQL 17 in CI) fails with the recovery check removed; `TestStandbySlotSweepReachesOnlyAnHAPublishersStandby` fails with the role label dropped; `TestStandbySlotSweepVerifiesTheServerAgainstTheDatabasesCAs` and `TestStandbySlotSweepReportsEachFailingStandby` cover the TLS trust and a failing standby. The backend suite and `make lint` pass. ADR009 § Lifecycle › Failover and switchover, the ADR018 "Logical replication (lifecycle)" row and the runbook record the rule.
