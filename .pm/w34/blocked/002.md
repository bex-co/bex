# 002 — Decide how a workspace asks for logical replication: a request channel bex does not have yet, or self-service as a signed-off divergence

Why: Render enables logical replication only through its support team, and w34/m541 matches that with an ops-only verb, but bex has no support channel, so a workspace has no way to make the request the verb answers.

- **Render** (render.com/docs/postgresql-logical-replication, read 2026-11-20): "To enable logical replication, please reach out to our support team in the Render Dashboard", with the database ids, the subscriber role, the schemas and the all-tables choice.
- **bex today:** the dashboard has nine "contact support" strings (`dashboard/src/features/*/locales/en.ts`) and no support address, form or chat behind them (no `mailto:` or support URL in `dashboard/src` or `lego/backend/internal`, checked 2026-11-20).
- **Options:**
  1. **Recommended (matches Render):** keep enablement an operator action and name the channel a workspace uses to ask (a support address, or a request form that files the four inputs for the operators). The user picks the channel. w34/m541 t007's dashboard note then names it.
  2. **Divergence, needs the user's sign-off in ADR018:** a workspace Admin turns it on in the database's Settings (REST, GraphQL, MCP and the dashboard, as a bex extension), with the same prerequisites the verb checks. This removes the manual operator step but adds a public field Render does not have.
- The recommendation rests on ADR008 § Render parity first; it is not a recorded user decision.

End state: the user's choice is recorded here, in ADR009 § Logical replication and (for option 2) in ADR018 with their sign-off, and the dashboard note names the channel or the control. Implementation of option 2 would be its own milestone. ~45m once decided; needs the user's decision, so it starts in `blocked/` until then.

Source: `/pm-brainstorm` for one aspect of render parity (Postgres logical replication), 2026-11-20, item 5.
