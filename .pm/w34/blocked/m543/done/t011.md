## Objective

Let a paid database in a workspace namespace start a major-version upgrade once its first backup completes, so DoD 4 can be walked on production.

## Context

- Found by the production replay (2026-11-21, pin `7e481dece7ac`): a `basic_256mb` and a `1c-2g` PostgreSQL 16 database in `bex-canary`, each with a completed backup (`recoveryStatus` `AVAILABLE`), were refused on REST `PATCH version` (dry run included) and MCP `update_postgres` with 409 `POSTGRES_UPGRADE_BACKUP_REQUIRED`. The gate runs before the logical-slot check, so neither the refusal by slot name nor the `upgradeNotice` could be reached.
- `hasCompletedBackup` (`lego/backend/internal/postgres/service.go`) counted only a CNPG `Backup` whose `status.serverName` named the database's generation, or an empty one when the generation is the bare cluster name. Every Barman Cloud plugin `Backup` on production (147 completed) has an empty `serverName`, and a workspace database's generation is namespace-scoped (`tea-…-dpg-…`), so none matched: no paid database in a workspace namespace could upgrade.

## Acceptance criteria

- [x] A completed plugin backup in the current generation authorizes the upgrade; a pending one, or one only in the generation before the last upgrade, does not.
- [x] A test that fails without the fix.

## Done (2026-11-21, `29d664572`)

The gate also accepts the `ObjectStore`'s recovery window for the generation's name, which the plugin writes when a backup completes and recovery info already reads (`recoveryWindow`). `TestBackupGuardReadsThePluginsRecoveryWindow` covers the three cases and fails with the old code. ADR009 § Major-version upgrades says where the backup is read. The live replay of DoD 4 waits for the pin to carry it (t006, t010).
