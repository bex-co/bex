# 006 — A recovery that names its plan the way Render's API spells it fails with 500

Why: Render's recovery request takes the database's plan in the API's own spelling (`basic_256mb`, `pro_4gb`), and bex answers `500 internal error` instead of restoring.

## Evidence (production pin `7e481dece7ac`, 2026-11-21, found by w34/m543's replay)

- `POST /v1/postgres/dpg-dc0s4uu0ri4c73c3vi90/recovery` with `{"restoreName":"qa-20261121-m543-pitr","restoreTime":"2026-11-21T16:16:00Z","plan":"basic_256mb"}` answered `500` `internal error`. bex-api logged `Database.app.bex.co "dpg-dc0sci60ri4c73c3vjqg" is invalid: [spec.plan: Unsupported value: "basic_256mb": supported values: "free", "basic-256mb", …]`. The same request with `basic-256mb` answered 200 and restored. Nothing was left behind (by-id `GET` 404, no CR).
- Cause: `lego/backend/internal/postgres/recovery.go:419` takes `plan := req.Plan` before `:440` canonicalizes `req.Plan` with `tiers.Postgres.CanonicalID`, so the validation passes on the canonical id while the CR is written with the raw alias. Create and update canonicalize before use (`service.go:935`, `:1578`). Every recovery surface goes through `Recover`: REST `POST /v1/postgres/{id}/recovery` and `/recover`, GraphQL and MCP.

## Done when

- A recovery naming `basic_256mb`, `pro_4gb` or `1c-4g` creates a copy whose `spec.plan` is the canonical id, on REST, GraphQL and MCP; an unknown plan is still a 400.
- A regression test that fails without the fix covers an aliased plan.
