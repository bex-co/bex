# 007 — A recovered copy's connection info opens CNPG's empty `app` database, not the restored one

Why: after a point-in-time recovery, the copy's connection strings reach an empty database as a user the copy's own view does not name, so the restored data looks lost.

## Evidence (production pin `7e481dece7ac`, 2026-11-21, found by w34/m543's replay)

- `qa-20261121-m543-pitr` (`dpg-dc0scp60ri4c73c3vjrg`) was recovered from `dpg-dc0s4uu0ri4c73c3vi90` to 16:16:00Z. REST and GraphQL read `databaseName` `dpg_dc0s4uu0ri4c73c3vi90` and `databaseUser` `dpg_dc0s4uu0ri4c73c3vi90_user`, and the restored rows (2,680 in `stream`) are in that database.
- `GET /v1/postgres/dpg-dc0scp60ri4c73c3vjrg/connection-info` named the user `app` and the database `app`. That login works and opens a database holding only the `pg_stat_statements` views. The copy's `<id>-app` Secret is for `app`/`app`; the source's is for `dpg_…_user`/`dpg_…`.
- Cause: the operator's recovery bootstrap (`lego/operator/internal/controller/database_controller.go:581`, `rec := map[string]any{"source": recoverySource}` plus `recoveryTarget`) sets no `database` or `owner`, so CloudNativePG defaults both to `app`, creates them and writes `<id>-app` for that role. The `initdb` branch passes both (`:610`). `PostgresConnectionInfo` (`lego/backend/internal/postgres/service.go:1112`) reads `<id>-app`. The shape dates from w1/m17 (`918f7b5f1`); the only recovered database on production was this fixture.
- Render: a recovery creates a new database that holds the data as of the chosen time, and its connection info reaches that data like any database's.

## Done when

- A recovered copy's internal and external connection strings and psql command (REST, GraphQL, MCP, the dashboard) connect to the restored database as a login that can read the source's tables, and its view's `databaseName`/`databaseUser` agree with them.
- Check first what CloudNativePG does with an existing owner named in `bootstrap.recovery` (whether it resets its password to the generated Secret's), and keep ADR009 § Lifecycle › Recovery's credential retirements (w34/m543 t005) intact.
- A projection test and a production replay with a fixture recovered in `bex-canary`, deleted afterwards.
