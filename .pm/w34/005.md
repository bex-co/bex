# An HA subscriber could opt into a synchronous standby, so an automatic failover loses no row it applied (stricter than Render)

Why: bex's HA standby is asynchronous, as Render's is, so an automatic failover can lose what a subscriber applied in its last seconds, and unlike a client's lost write the publisher never sends it again: the subscriber silently stops matching its publisher (found by w34/003, 2026-11-21).

- **Premise.** [w34/003](done/003.md) closed the loss as Render's documented HA ("changes to your primary instance in the last few seconds before the failover will be lost", [render.com/docs/postgresql-high-availability](https://render.com/docs/postgresql-high-availability), read 2026-11-21), and the verb's answer now warns an HA subscriber. Preventing it would be stricter than Render, so it is optional.
- **What it takes, checked locally on PostgreSQL 18.7** ([ADR009 § Lifecycle](../../docs/ADR009-postgresql-management.md#lifecycle-w34m543)): both of these. A synchronous standby alone (CNPG `postgresql.synchronous`, `method: any`, `number: 1`) lost the same 1,000 rows, because a subscription's `synchronous_commit` defaults to `off` and overrides the server's setting, so its commits skip the wait. With the subscription's `synchronous_commit = on` as well, no row was lost or duplicated.
- **Costs to weigh:** with `dataDurability: required`, every write that waits for the standby pauses while it is down (CNPG v1.30.1 `docs/src/replication.md`); `preferred` keeps writing and reopens the gap while the standby is away. Setting the cluster's own `synchronous_commit` to `local` would keep the user's other writes as fast as today, and make only the subscriptions created with `synchronous_commit = on` wait. On 16 and later the user creates the subscriptions, so they would have to set it themselves; bex could set it on the 13–15 ones it creates.
- **Paths:** `lego/operator/internal/controller/database_controller.go` (`cnpgClusterSpec`), `lego/operator/internal/controller/database_subscription.go` (`subscriptionSpec`), `lego/backend/internal/postgres/logical_replication.go` (`failoverWarnings`), `docs/ADR009-postgresql-management.md`, `docs/ADR018-render-parity.md`, `docs/runbooks/postgres-logical-replication.md`.
- **Decision needed:** a behavior stricter than Render that costs write latency or availability is the user's call: whether to build it, and whether as the default for HA subscribers or on request.
- **End state:** either the user declines it and this note closes, or an HA PostgreSQL 18 subscriber that has it takes a counted stream from an outside publisher through a forced failover with no row lost or duplicated, and the ADR018 "Logical replication (lifecycle)" row records the difference from Render with the user's sign-off.
