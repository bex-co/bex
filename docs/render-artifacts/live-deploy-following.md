# Render live deploy following

**Captured:** 2026-07-15

**Method:** Render's public documentation (no authenticated production service was mutated for this capture).

## Observed contract

- Creating a service kicks off its first deploy and opens the new service's deploy-progress log explorer. Render tells users to “open your new service's page” and follow the build and start commands as they run.
- The deploy log feed updates in real time. A successful deploy changes its displayed status to **Live**; a failed deploy changes to **Failed** while leaving its log feed available for diagnosis.
- A dashboard Manual Deploy starts immediately from the service's Events page. An individual deploy is opened by selecting **Deploy** in its event entry; that page is the deploy-specific log explorer and is also where an in-progress deploy can be canceled.
- Render's general log explorer exposes **Live tail** as a time-range mode, and the deploy-specific explorer is documented as the place to follow build/start progress.

These sources establish the observable outcome—remain on the deploy-specific progress view while logs and status advance—but do not publish the dashboard's private navigation implementation. bex therefore treats the landing URL itself as UI behavior and keeps its public wire contract unchanged.

## Terminal behavior

- Success: status becomes **Live** and the accumulated deploy log remains visible.
- Failure: status becomes **Failed** and the accumulated log remains visible for troubleshooting.
- Cancellation: the deploy details page exposes **Cancel deploy** while the deploy is in progress.

## bex comparison (before w3/m14)

- Deploy detail already polled all non-terminal statuses every three seconds and stopped at every terminal status.
- Manual Deploy already navigated to the returned deploy id.
- The detail log pane polled Loki history; `GET /v1/logs/subscribe?type=build` refused build logs as store-only.
- Create navigated to the service overview even though store-managed create opened its first deploy row transactionally.

w3/m14 closes the last two gaps: build SSE follows the active build pod, and create returns/navigates to the first deploy with an honest service-page fallback when no deploy id is available.

## bex live verification (2026-07-15)

Verified on the local CAPD cluster through w3's isolated `dev-3` identity/API stack and a real headless Chrome session against the dashboard:

- a create-triggered git build produced 128 `type=build` SSE frames and transitioned `build_in_progress` → `live`; the App reached `Running`;
- the dashboard Manual Deploy confirmation navigated directly to `/services/<service>/deploys/<deploy>`; its build panel visibly appended BuildKit lines while Chrome remained on that page;
- the same open page updated its deploy header, timestamps, and timeline to terminal `Build Failed` without a refresh when exercised once without the temporary registry;
- a subscription after the build had ended emitted the named terminal `no running build is available to follow` error instead of hanging. (Still true of the dashboard's SSE build tail. Since w8/m159 the Render CLI's WebSocket build tail instead waits for the next build, as Render's subscription does; ADR010 § The live tail.)

The temporary test services, registry, pull/push Secrets, and browser profile were removed after verification. No production service was mutated.

## 2026-07-17 production incident + Render deploy-page recheck

A real production deploy (`dep-d9d8r3h07a5s73dj32ag`) showed only old-revision app lines while its build ran. Three compounding causes, verified against prod Loki and the deploy row:

- The build pod stayed Pending for ~2 minutes (cold buildkit image pull), emitting nothing; `followBuildLogs` answered the deploy page's one SSE subscription with the terminal `no running build` event, and the client never retried — the tail was dead before the build's first line.
- The build then failed within seconds; the deploy closed its window and the page stopped polling immediately, racing Loki ingest for the few in-window build lines.
- The still-running previous revision kept logging into the open window — correct interleaving, but the only visible content.

An authenticated dashboard.render.com walk (`/web/srv-…/deploys/dep-…`) confirmed the deploy page is Render's general log explorer scoped to the deploy's absolute window (`?r=start~end`) with an **All logs** default filter offering **All logs / Application logs / Build logs** — bex's interleaving is parity-correct. Render additionally synthesizes platform progress lines (`==> Cloning from…`, `==> Checking out commit…`, `==> Running build command…`), so its feed is never silent during scheduling; bex emits no platform lines (open parity gap).

Fixes shipped with this recheck: `followBuildLogs` now waits for a Pending build pod to start instead of terminating (completed-only or no pods remains the immediate named terminal outcome), the dashboard build tail reopens a terminated subscription every 5s while the deploy is still `build_in_progress`, and the deploy page's windowed queries keep polling 15s past `finishedAt` to absorb store ingest lag.

## Platform progress-line contract (w1/m48/t001)

Render's platform narrates a deploy inside the log feed itself. From [Your First Render Deploy](https://render.com/docs/your-first-deploy) and public build-log excerpts, the canonical lines are `==> Cloning from https://github.com/…`, `==> Checking out commit <sha> in branch <branch>`, `==> Running build command '<cmd>'…`, `==> Build successful 🎉`, `==> Deploying…`, and `==> Your service is live 🎉`. Render's docs do not publish which API log `type` carries them or their label/id shape (the reference workspace's retained logs had expired, so this could not be captured live — recorded uncertainty; bex needs only a compatible _reading experience_, not byte equality).

bex synthesizes from what its control plane actually observes — the deploy row's three timestamps plus terminal status — never inventing clone/checkout moments it cannot see (those arrive as real BuildKit stdout once the pod runs):

**The rollout (w32/m560).** Render's deploy log narrates the rollout between a build's last line and its verdict. In thirty public GitHub issues from 2025-12 to 2026-11 that quote Render deploy logs, `==> Deploying...` opens the rollout of every built service, native or Docker, between 0.1 s and 34 s after the build's last line (DerekSopok/EMS-Kahoot#3, frayel/devagent#62, darthjee/ward#109, Collective-Intelligence-Labs/omnichain-payments-evm#46). `==> Setting WEB_CONCURRENCY=N by default, based on available CPUs in the instance` follows about 0.1 s later. On a native runtime only, `==> Running '<start command>'` comes 9–12 s after that, quoted as configured, and again each time the command starts again (after `==> Exited with status 1`, after `==> Timed Out`). A Dockerfile service prints no `Running` line, with or without a Docker Command (HKUDS/nanobot#6607). The operator records each release's rollout in `status.releaseRollout`: when it first wrote the release's serving template (microseconds, so the line sorts after the build pod's own nanosecond-stamped `==> Build successful 🎉`), the app container's starts on the release's pods while the rollout runs (the current run's start and, after a restart, the one before; at most ten), the start command a native image runs through native-init, and the `WEB_CONCURRENCY` default the container got. A resync, a cancel's revert and a survivor's redispatch never move the start, and nothing is added once the release serves, fails or is canceled. The control plane copies the record onto the release's own deploy row while the row is open, so a newer release never rewrites an older deploy's log. A static site and a cron job run no instance at deploy and get none of the three lines; neither do a build that failed or a deploy canceled before its rollout. The `WEB_CONCURRENCY` line follows bex's rule (`webConcurrencyCutoff`, 2026-10-21), since it reports what the container got, and it follows an image deploy's own `==> Deploying image <image>` line too. The CLI's build tail (Render's WebSocket subscription, which follows every build) sends each line once on its next pass after the row records it, the way it sends the verdict; the dashboard's deploy page reads them from its windowed history poll, as it reads the verdict. Not observed in Render's logs, and kept as bex's own: a private service's rollout (assumed to match a web service's), a background worker's (assumed the same, though two 2025 worker logs put `==> Your service is live 🎉` before `==> Running`), and a prebuilt image's and a rollback's (bex keeps `==> Deploying image <image>`). A pre-deploy command's lines come before any `==> Deploying...` in Render's logs, as bex's do, since bex writes the template after the step passes. Render opens the step with `==> Starting pre-deploy: <command>` and closes it with `==> Pre-deploy complete!`, or with `==> Pre-deploy has failed`, `==> Exited with status N` and the troubleshooting line, as bex does since w32/m572 (below). Render's log API labels these lines `type: app` in the two public captures, and its messages carry ANSI colour codes, which bex's carry too since w32/m576 (below). Both captures and the public logs behind them are in [ADR018](../ADR018-render-parity.md) § Logs, Build logs.

**The instance's own `Running` line (w32/m575).** On Render `==> Running '<command>'` is the instance's line: ivanseibel/tretta's capture of Render's log API (a free native Node web service, 2026-10-18) has it at each free spin-up, when no deploy runs, and inside a deploy, each copy with the instance's `instance` and `level` labels and a UUID id, where the platform's lines carry neither. A native cron run writes it too (Lizo-RoadTown/hcs-coordination, a `runtime: python` cron). bex's native-init writes it to the container's stdout each time it starts a `<shell> -c <command>` launch, before the command's own output and quoted as configured: a service's start command at every start (a deploy, a restart after a crash, a free instance's spin-up), a cron run and the initial deploy hook. It reaches every app read (`bex logs -r <srv>`, REST, the subscribe stream, GraphQL, MCP, the Logs page) with the pod's labels. A Dockerfile or prebuilt image writes none. native-init is copied into each image at build, so the narration's copy in the table above stays for a release whose image predates it: a native build labels its image `co.bex.native-init.announces=true`, and the operator records on the release's rollout whether its instance writes the line (`status.releaseRollout.instanceAnnounces`, `rollout_instance_announces`), once with its start. A row an older control plane wrote reads as an older image. Each start is then named once on the deploy page and the CLI's type-less deploy tail, which interleave the app's lines. A pre-deploy step keeps the narration's line: the operator sets `BEX_NATIVE_INIT_QUIET` on a step whose image carries the label, and native-init writes nothing and removes the variable from the command's environment. A new release's start-command line is therefore in the type-less read with `type=app`, not in `bex logs --type build`; what Render's `type=build` read returns stays with w32/085. Render's start-time Bun lines are w32/093's.

**The pre-deploy step (w32/m572).** Render's deploy log narrates a pre-deploy command between the build's last line and the rollout. `==> Starting pre-deploy: <command>` comes about 4 s after `==> Build successful 🎉`, quoted as configured. On a native runtime `==> Running '<command>'` follows when the step's container starts, about 12 s later, and the command runs under bash. The command's output comes next. A step that passes ends `==> Pre-deploy complete!` (BerriAI/litellm#9549, ganjasan/mapsurvey#73). One that fails ends `==> Pre-deploy has failed`, and its deploy closes with `==> Exited with status N` and the troubleshooting line within a second, with no `==> Deploying...` anywhere (Unwrenchable/ATOMIC-FIZZ-CAPS-VAULT-77-WASTELAND-GPS#82 with timestamps; dukens11-create/Flupflap#206; stranske/learning-management-system#191; healthkey-ai/promop#1636). A Dockerfile or prebuilt image's step prints no `Running` line: its output follows the start line (ClipFarmVB/ClipFarm#173 and ganjasan/mapsurvey#72, Docker, exit statuses 127 and 2; BerriAI/litellm#9549 and briankeane/alloy-client-portal#8, image, the second with exit status 128 and no output). The operator records the step in `status.preDeploy`: the command and whether a native image's entrypoint ran it, and its launch in microseconds, all stamped by the pass that creates the step's Job, so the start line sorts after the build pod's nanosecond-stamped last line. It also records the container's start as the kubelet reports it, the moment it settled the step's verdict (microseconds, after the command's last output line and before the rollout's start), and the container's exit status when the command ended on its own or the kernel killed it for memory. A requeue, a manager restart and a re-check of the verdict never move them, and a newer release replaces them. The control plane copies the record onto the release's own deploy row while the row is open: the launch, command and launch kind once, the container's start, then the end with its exit status, on the pass that closes a failed step's row too. Each line comes from those moments, held just after the line before it where a whole-second start would read first, and a closed row's lines stay at or before its close. `==> Pre-deploy complete!` comes before the rollout's `==> Deploying...`, which follows it. Failures no Render log shows keep bex's `==> Pre-deploy failed: <reason>` close: an out-of-memory kill, an image that cannot be pulled, no build minutes left, an infrastructure fault, and a row an older operator recorded. So does a program the runtime could not launch, as w32/m572 chose, though briankeane/alloy-client-portal#8 shows Render closing an image's missing program with `==> Exited with status 128` (w32/091). So does the 30-minute limit: jdegreef/open-word-bible#1023 paraphrases its log as "Pre-deploy has failed / Timed out" and quotes none, and MalaysiaKaki/astrail-webmcp#10 (Docker, 2026-10-03) shows `==> Pre-deploy timed out` with nothing after it (w32/091). A step refused before its Job existed gets no start line. A deploy canceled while its step runs keeps the step's lines up to `==> Deploy canceled`. The CLI's build tail sends each line once on its next pass after the row records it, and the dashboard's deploy page reads them from its windowed history poll. The tail does not yet carry the step's own output, which it reads only from build pods (w32/092). Not observed in Render's logs: what follows `==> Pre-deploy complete!` (ganjasan/mapsurvey#73 quotes only selected lines; w32/085), and an out-of-memory kill.

**The primary URL block (w32/m567).** Render follows a web service's `==> Your service is live 🎉` with six lines: `==> ` (a blank marker that keeps its trailing space), a rule of `==> ` and 59 slashes, `==> `, `==> Available at your primary URL https://<service>.onrender.com`, `==> `, and the rule again. Twelve public GitHub issue logs from 2025-09 to 2026-11 carry the whole block, every rule 59 slashes (falcon-Z/z0-auth#12, lelewithheart/Pixel-Breach#10, lss233/kirara-ai#1498, Jeanajsja/SGSDev#1 and eight more; [ADR018](../ADR018-render-parity.md) § Logs, Build logs). Each is a line of its own: the first 30 to 240 ms after the live line, the rest 3 to 110 ms apart (falcon-Z/z0-auth#12: live at `17.712`, the block from `17.947` to `17.965`), and the app's own request lines can fall between them. Logs read through Render's API end the URL at the host (`https://z0-auth.onrender.com`); only logs copied from the dashboard's viewer, which links the URL, show a trailing slash. Once the service has a custom domain, that domain is the primary and the line counts the service's other domains (barouu78-wq/teranga-ai#417 and mvryhan-web/video-variator-android#233, `+ 2 more domains`; bookorbit/bookorbit#31, `+ 1 more domain`). A static site's log ends at `==> Your site is live 🎉` with no block (muppetbrown/mana_meeples_singles_market#226). bex writes the same six lines a millisecond apart from `finished_at`, so each has its own id even where the text repeats. The URLs come from the deploy's own row: when the control plane closes a web service's deploy `live`, it records the URLs the operator serves the service at (`status.urls`, wildcards dropped) in `live_urls`, once, with the primary first. The primary is the first custom domain served (`spec.host`, then `spec.hosts` in the order they were added) that is not the redirecting side of a www/apex pair, else `status.url`. Every other URL counts, the `<slug>.onbex.co` host and the www redirect included, which matches Render's count of two for a root domain if Render counts its own redirect and `onrender.com` host the same way (an inference from the three logs; w32/085's capture can confirm it). A domain added later changes the next live deploy's block, never an older deploy's, and a row that went live before the record existed has no block. A static site, a private service, a background worker and a cron job record nothing. The live tail sends the block with the live line, after the build's last line, and a history read whose window opens inside the block keeps the lines after its start. The initial deploy hook's lines follow the block (w33/m435). The dashboard's deploy page closes a live deploy's log window 7 ms past `finished_at` (`deployWindowEnd`) so the pane carries the block. Not observed in Render's logs: a private service or a worker with the block (neither has a public URL, and bex writes none), a wildcard custom domain (bex never names or counts one), and the count when the `onrender.com` subdomain is disabled (bex counts only the hosts it serves).

**The port scan (w8/385).** Render's deploy log narrates its port scan while a web service has no open port, about once a minute, five times, each followed by the docs line, then `==> Port scan timeout reached, no open ports detected. Bind your service to at least one port. If you don't need to receive traffic on any port, create a background worker instead.` and the docs line about five minutes in, while the deploy runs on to its 15-minute budget (wording, count and timing from deploy logs quoted in GitHub issues; [ADR018](../ADR018-render-parity.md) § Logs, Build logs). The control plane stamps `port_scan_since` when the open rollout's stall first says no port is open (the operator's no-open-port hint, a stalled any-open-port check, or an image's HTTP discovery that finds nothing) and `port_scan_until` when a later stall says the scan is over (a port answers, the check passes, or the stall is about something else). The scan lines run from the first to the end of the scan or the deploy, and an open scan's up to the read; each carries the docs line. The timeout line and the docs line come a minute after the fifth scan line (w8/389), and nothing more until the deploy ends. A deploy that fails still scanning before then gets them at `finished_at`, before `==> Deploy failed`. A port that opens after the timeout line still goes live: the startup probe spends the whole 15-minute budget.

**What the scan found (w8/388).** Render words two cases apart from "no open ports": a listener only on localhost (`==> No open ports detected on 0.0.0.0, continuing to scan...`, then `==> Port scan timeout reached, no open ports detected on 0.0.0.0. Detected open ports on localhost -- did you mean to bind one of these to 0.0.0.0?`, each with the docs line) and open ports that answer no HTTP (`==> No open HTTP ports detected on 0.0.0.0, continuing to scan...`, then `==> Port scan timeout reached, no open HTTP ports detected. If you don't need to receive public HTTP traffic, create a private service instead.`, with no docs line). The node's listener reader now answers a pod's loopback-only ports apart from its reachable ones, so the operator's stall names the localhost case (`hint_no_open_port_localhost`, or `http_port_localhost_only` during an image's HTTP discovery) and the no-HTTP case (`hint_no_open_http_port`, `http_port_none_http`, and a listener that accepts discovery's connection and stays silent while no other port answers). The first of those a running scan reports is stamped on the row as `port_scan_found` with `port_scan_found_at`, from the same clock reading as `port_scan_since` when the scan starts with it, and never changes. Lines from that moment on, the timeout line included, carry its wording; earlier lines keep the plain text, so a line a tail already sent never rewords. A node without a reader is swept from outside and cannot see loopback, so it keeps the plain wording.

**A web service that sets `PORT` (w8/416).** Render scans that port alone and names it: `==> Continuing to scan for open port 8080 (from PORT environment variable)...` on the same cadence, then `==> Port scan timeout reached, failed to detect open port 8080 from PORT environment variable. Bind your service to port 8080 or update the PORT environment variable to the correct port.`, with no docs line. The operator's stall for such a service whose TCP check finds `PORT` closed carries `hint_env_port_closed`. The row records the finding with its port as `port_scan_found` `env_port:<port>` at the scan's first line, so every line of that scan carries this wording.

Failure statuses append the deploy row's `failureReason` when present (`==> Deploy failed: …`, w5/064) so the CLI's `type=build` narration carries the same cause as `deploy_ended.details.failureReason`; multi-line reasons become one stream line per segment. Empty reasons keep the bare historical line. A deploy that ran out its 15-minute rollout budget (the row's `end_timed_out_seconds`, the budget its close recorded) closes as Render's has since May 2026 instead, with `==> Timed Out` and the troubleshooting line and no cause; the cause stays on the deploy's `failureReason` (w8/391, [ADR018](../ADR018-render-parity.md) § Logs, Build logs). A build whose own work failed (the operator's `build failed …` sentence, `appv1alpha1.IsBuildFailed`) closes with `==> Build failed 😞` and the troubleshooting line, and a start command that exited (no memory kill, no timeout) with `==> Exited with status N` and the troubleshooting line, as Render's logs in 2026 do; neither names a cause, which stays on the deploy's `failureReason` (w8/393). Since w32/m591, the operator records the earliest non-OOM exit of the release's app container while the rollout ran (`status.releaseRollout.firstExit`, whole seconds as the kubelet reports them, never overwritten by later restarts), and the control plane copies it onto the open deploy row (`rollout_first_exit_at`, `rollout_first_exit_code`, preserving exit code `0`). When the deploy settles `update_failed` (not timed out, not OOM-killed), bex places its single `==> Exited with status N` (red, `PlatformFailure`) and troubleshooting line (blue, `PlatformStep`) right after run 1's exit — held at the close of that whole second (`.999999999`) and clamped to `finished_at` (and after run 1's narrated `Running` line on pre-w32/m575 native images) so run 1's nanosecond app output sorts before the pair and later restarts follow it, with nothing more at `finished_at` — matching public Render logs (DerekSopok/EMS-Kahoot#3, rkendel1/freq#187 and #191, darthjee/ward#109, muppetbrown/mana_meeples_singles_market#63, omkarwarik02/DevLens#1; muppetbrown/mana_meeples_singles_market#84 is the one observed exception after run 2). The pair is never emitted while the deploy is still `update_in_progress`, an eventually-live deploy (`live`/`deactivated`) keeps today's lines until w32/085 settles whether Render sets `finishedAt` at the first exit, and older `update_failed` rows with no recorded first exit keep the pair at `finished_at` using `end_exit_code`. A static site's publish Job that finds no publish directory, with no build command or after a build that left none, reads as the build's own failure too, and its log closes with Render's `==> Publish directory <dir> does not exist!` (the path as configured), then `==> Build failed 😞` and the troubleshooting line. The publish Job's output never reaches the build log, so bex writes that line from the failure reason, which keeps it (w8/395). A pre-deploy command that exited with status N closes with `==> Pre-deploy has failed` at the step's end, then `==> Exited with status N` and the troubleshooting line (w32/m572). A build that timed out, hit an infrastructure fault or never ran, a no-build static site's other clone failures, a pre-deploy step whose command did not exit on its own, an image pull failure and an out-of-memory kill keep bex's line, since no Render log shows theirs.

**Render's colour codes (w32/m576).** Render's log API, its CLI's `-o json` and `-o yaml` and its MCP server's `list_logs` return each `==>` line with ANSI codes, and its CLI shows them coloured on a terminal. bex writes the lines Render's captures show in Render's exact bytes, from one table (`lego/types/renderlog`) that the control plane, the build pod's scripts, native-resolve and native-init share:

| --- | --- | --- |

The forms come from ivanseibel/tretta's, kush252/Sentry-AI's and Ishan2036924/upmyrank-poc's captures ([ADR018](../ADR018-render-parity.md) § Logs, Build logs). Every other line in the table above, Render's lines no capture shows with their codes as well as bex's own, stays plain until w32/085's capture shows Render's; w32/m576's t001 table lists each line with its form and source. Each line shows the words it showed before: REST, the subscribe stream, GraphQL and MCP return the stored bytes, the dashboard draws the marker coloured and the text bold and copies the words, and `textMode=display` finds a line by those words while the raw `text` default matches the stored bytes (w4/m189).

**A native build's own lines (w4/m324).** A native-runtime build (Node, Python, Ruby, Go, Rust, Elixir, and a static site's native build) runs BuildKit on a Dockerfile bex generates, and BuildKit's plain transcript of it is mostly bex's recipe: toolchain and tool layers, the env loader, the secret mount, `#N` step numbers, elapsed seconds and digests. The build pod's log therefore carries Render's lines instead, written by the BuildKit container itself so the live tail and the Loki history read the same stream: `==> Running build command '<cmd>'...` (the command as configured; omitted when there is none), the command's own output with no `#N` or elapsed-time prefix, then `==> Uploading build...` as soon as the command's step is done or served from the cache (w33/m570), or `error: build command '<cmd>' exited with code N` when the command fails. Everything BuildKit does after the command's step runs under that line, as on Render, where `==> Uploading build...` directly follows the command's output: the image's remaining steps, its export and compression, the layer cache's export and the `$XDG_CACHE_HOME` archive. On a 1.4 GB Node image that is about 7 minutes, which the log used to pass in silence. The BuildKit container leaves the line's moment in the build's output volume, and the push phase, which prints no second line, counts `==> Uploaded in Ns` from it, export and push together, then prints `==> Build successful 🎉` once the image is pushed (w4/582). That Render's upload also covers compressing the image is bex's reading, not verified: Render shows only the order of the lines. A BuildKit container that cannot leave the moment prints no line, and the push phase prints it as it starts, as before w33/m570. A BuildKit phase that fails after the line ends with `==> Uploading build failed` and shows nothing of BuildKit's error. A failing step before the command's reaches the log as `==> Preparing the build failed: <BuildKit's error>` and BuildKit's closing `error:` line, and anything buildctl prints before BuildKit's first step (a daemon that never started) passes through. On failure the container writes the raw transcript's tail to its termination message, so the transient/tenant classifier, the failure reason (which for a native build names the `build command` or `build environment` step and quotes the command's output without elapsed stamps) and the platform-fetch reason (w8/m148) still read BuildKit's own words. A build command step BuildKit served from its cache adds `==> Reusing the cached result: nothing the build command reads has changed since an earlier build` after its narration (w4/582); the live tail attaches the short push phase too, so it carries the verdict. Since w32/046 only a retried release can be served that step: every release carries its own build revision and runs the command, as on Render. A Dockerfile build keeps BuildKit's plain output, as Render shows it.

Labels: `type=build`, `instance=<dep-… id>`, `container=platform`. Ids come from the existing `logID` derivation (instance + timestamp + message hash, `internal/logs/render.go`), so identical lines are deterministic across reads and dedupe against the SSE tail for free. Synthesis applies only when a query explicitly asks for `type=build` (matching which streams the store selector includes), is additive (a missing Loki still reports `buildStoreUnavailable`; platform lines never masquerade as a successful empty build history), and `deactivated` deploys keep their `live` closing line — deactivation is a later replacement event outside the deploy's own window.
