# Service environment revisions

The optional service environment CAS protocol is a bex extension. Render's [single-variable update](https://api-docs.render.com/reference/update-env-var), checked 2026-09-21, accepts a value without a caller-supplied revision. Its [dashboard save modes](https://render.com/docs/configure-environment-variables) distinguish save only, deploy, and rebuild/deploy. No authenticated Render concurrency experiment was performed.

Bex exposes the same service patch through REST `PATCH /v1/services/{id}/environment`, GraphQL `patchServiceEnvironment`, and MCP `patch_service_environment`. An `expectedEnvRevision` permits exactly one ordinary existing variable update. Successful CAS responses include a nullable `revision` that can be passed unchanged into the next save, including when the value was unchanged. Sparse patches return `revision: null`: a later source read could observe another writer, so it cannot supply a reliable revision for that patch.

`ENVIRONMENT_REVISION_CONFLICT` means this request was refused before its source write was accepted. Concurrent independent writers may of course change the service. A successful source write followed by projection failure remains an error: successful compensation returns `ENVIRONMENT_UPDATE_RESTORED`; incomplete compensation, including a newer writer preventing safe rollback, returns `ENVIRONMENT_RESTORATION_FAILED`. These errors must not be interpreted as unchanged-state refusals or automatically retried. Responses preserve the existing named-code contracts (REST HTTP409, GraphQL extensions, MCP structured errors), without exposing secret values or internal paths.

The dashboard's shared Environment editor currently submits sparse patches without `expectedEnvRevision` (`env-vars.graphql`, `use-environment-draft-save.ts`). It retains a failed draft and displays the server error; it does not automatically retry a secret write. Its deployment follow-up retry is separate. This change does not claim the editor itself gains CAS protection.

Local regression coverage exercises response token chaining on all three surfaces and both save modes, stale-state refusal, and post-write compensation ownership. Real OpenBao tests use fake Kubernetes resources to control interleavings; they do not establish production deployment or explain the original unattended failure frequency. The original live report and owed deployed verification remain tracked in w4/m130.

The optional local KV integration tests take `BEX_TEST_OPENBAO_KV_URL` and `BEX_TEST_OPENBAO_KV_TOKEN` pointing to a disposable OpenBao dev instance; run `go test ./internal/secrets -run TestPatchEnvironmentRealOpenBao -v` from `lego/backend`. Each test creates and deletes an isolated KV-v2 mount. Backend CI supplies both variables. These are separate from the existing `BEX_TEST_OPENBAO_URL` workspace lifecycle test, which requires Kubernetes authentication.
