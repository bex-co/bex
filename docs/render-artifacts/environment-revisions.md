# Service environment revisions

The optional service environment CAS protocol is a bex extension. Render's [single-variable update](https://api-docs.render.com/reference/update-env-var), checked 2026-09-21, accepts a value without a caller-supplied revision. Its [dashboard save modes](https://render.com/docs/configure-environment-variables) distinguish save only, deploy, and rebuild/deploy. No authenticated Render concurrency experiment was performed.

Bex exposes the same service patch through REST `PATCH /v1/services/{id}/environment`, GraphQL `patchServiceEnvironment`, and MCP `patch_service_environment`. An `expectedEnvRevision` permits exactly one ordinary existing variable update. Successful CAS responses include a nullable `revision` that can be passed unchanged into the next save, including when the value was unchanged. Sparse patches return `revision: null`: a later source read could observe another writer, so it cannot supply a reliable revision for that patch.

A variable a Blueprint's manifest dropped stays on the service as a literal and lists as an ordinary variable at the store's revision, although the store does not hold it yet ([ADR018](../ADR018-render-parity.md), w21/m421). A revision-checked save that names one moves it inside its own compare-and-set write: the store takes the literal with the edit as one new revision, checked against the revision the caller listed, and the same App patch removes the literal, so the first save lands and the returned revision chains. A revision another writer really advanced still answers `ENVIRONMENT_REVISION_CONFLICT`, and nothing is written. Save only holds the literal's removal for the next deploy. The single-variable verbs and the bulk replace check no revision: they move the literal inside their own write (w21/108), the store write taking the retained name as its edit and the same App patch removing the literal, so a write the API refuses (a `value` with `generateValue`, a breach of the aggregate quota, a `DELETE` of a name that does not exist) moves nothing and saves nothing for a deploy, and each verb makes one store write and one App patch. A `DELETE` of a name that does not exist answers 404 and changes nothing, on every service and not only one a Blueprint synced (w21/109, 2026-11-17): Render documents the 404 for [delete environment variable](https://api-docs.render.com/reference/delete-env-var) and no other effect, so the call makes no App patch, opens no deploy over GraphQL or MCP and leaves no saved change over REST (no `app.bex.co/saved-config-revision`, no `app.bex.co/pending-env-secret`). Before w21/109 it re-projected the reduced set before it knew the name existed, which patched the App and, over GraphQL and MCP, bumped `restartedAt`, set `spec.envFromSecret`, stamped a release generation and opened a `config_change` deploy. The one exception is a name the derived Secret still carries after the store lost it, which a delete an older release left half done (it committed its source write before the projection): that retry projects the reduced set and rolls the workload, and still answers 404. A `DELETE` of a secret file that does not exist behaves the same. A `PUT` that stores nothing new (the same single variable, the same whole set, the same secret file) answers as before and changes nothing (w21/110, 2026-11-17): no App patch, no deploy over GraphQL or MCP, no `app.bex.co/saved-config-revision` over REST, no Secret write and no event, since Render documents no effect for a write of the saved value (its env-var and secret-file PUTs deploy nothing). A retained literal's move and the clearing of invalid-name debris from `spec.Env` are still changes, and a store map an earlier attempt committed before its projection is still projected by the retry of the same `PUT` (once, when the derived Secret is not the store's map or the App does not refer to it). A staged write holds the removal for the next deploy as well (REST opens no deploy, as Render's env-var REST writes deploy nothing; GraphQL and MCP open exactly one, in that same patch), and a sync that re-declares the name meanwhile refuses the verb and rolls the store write back (w21/106).

`ENVIRONMENT_REVISION_CONFLICT` means this request was refused before its source write was accepted. Concurrent independent writers may of course change the service. A successful source write followed by projection failure remains an error: successful compensation returns `ENVIRONMENT_UPDATE_RESTORED`; incomplete compensation, including a newer writer preventing safe rollback, returns `ENVIRONMENT_RESTORATION_FAILED`. These errors must not be interpreted as unchanged-state refusals or automatically retried. Responses preserve the existing named-code contracts (REST HTTP409, GraphQL extensions, MCP structured errors), without exposing secret values or internal paths.

The dashboard's shared Environment editor currently submits sparse patches without `expectedEnvRevision` (`env-vars.graphql`, `use-environment-draft-save.ts`). It retains a failed draft and displays the server error; it does not automatically retry a secret write. Its deployment follow-up retry is separate. This change does not claim the editor itself gains CAS protection.

Local regression coverage exercises response token chaining on all three surfaces and both save modes, stale-state refusal, and post-write compensation ownership. Real OpenBao tests use fake Kubernetes resources to control interleavings; they do not establish production deployment or explain the original unattended failure frequency. The original live report and owed deployed verification remain tracked in w4/m130.

The optional local KV integration tests take `BEX_TEST_OPENBAO_KV_URL` and `BEX_TEST_OPENBAO_KV_TOKEN` pointing to a disposable OpenBao dev instance; run `go test ./internal/secrets -run TestPatchEnvironmentRealOpenBao -v` from `lego/backend`. Each test creates and deletes an isolated KV-v2 mount. Backend CI supplies both variables. These are separate from the existing `BEX_TEST_OPENBAO_URL` workspace lifecycle test, which requires Kubernetes authentication.
