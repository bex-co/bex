# Render CLI `ea sandbox` wire shape (w3/m32 t008)

Captured from the official `render-oss/cli` source and verified with v2.21.0, so bex-api's `/v1/sandboxes*` adapter (m32/m33, ADR042 D2) matches the real wire behavior and `render ea sandbox create/exec/list/stop` works unmodified. Rows 238–241 of [cli-compatibility-checklist.md](../cli-compatibility-checklist.md) are green.

All requests carry the workspace as an `ownerId` query parameter (Render's team id, `tea-…`); the server base path is `/v1/`.

## Endpoints

| CLI command | Method + path | Request | Response |
| --- | --- | --- | --- |
| `ea sandbox create` | `POST /v1/sandboxes?ownerId=` | `{ "plan": <plan>, "image"?: <ref>, "networkPolicy"?: {…} }` | `Sandbox` |
| `ea sandbox list` | `GET /v1/sandboxes?ownerId=&cursor=&status=` | — (repeat `status=` per filter; `--all` sends every status) | `[{ sandbox, cursor }]` newest first, as Render lists them (w32/015; cursor pagination over that order) |
| (get by id) | `GET /v1/sandboxes/{sandboxId}?ownerId=` | — | `Sandbox` |
| `ea sandbox exec` (v2.24.0+, step 1) | `POST /v1/sandboxes/{sandboxId}/runs/{operation}/token?ownerId=` (`operation` = `stream`) | `{ "command": "…" }` | `201` `SandboxConnectResponse` `{ executionId: "exe-…", expiresAt, method: "POST", token, uri }` |
| `ea sandbox exec` (v2.24.0+, step 2) | `POST <uri>` = `/v1/sandboxes/{sandboxId}/runs/{executionId}/stream`, `Authorization: Bearer <token>`, `Accept: text/event-stream` | `{ "command": "…" }` (must equal the minted command) | `200` SSE `output` events followed by `exit` with `exit_code`, or `error` with `{status, message}` |
| `ea sandbox exec` (≤ v2.21.0, legacy) | `POST /v1/sandboxes/{sandboxId}/exec?ownerId=` | `{ "command": "…" }` | same SSE stream, single step |
| execution history (SDK, no CLI command; w32/m298) | `GET /v1/sandboxes/{sandboxId}/execs?cursor=&limit=` · `GET /v1/sandboxes/{sandboxId}/execs/{execId}` | — | `200` `[{execution, cursor}]` newest first · one `execution` (`id, sandboxId, type, operation, command, userId, startedAt, stoppedAt?, exitCode?`) |
| `ea sandbox stop` | `POST /v1/sandboxes/{sandboxId}/terminate?ownerId=` | — | 200/204 |
| (logs) | `GET /v1/sandboxes/{sandboxId}/logs?ownerId=` | — | log events |
| (files, `ea sandboxes copy`) | `POST /v1/sandboxes/{sandboxId}/files/{operation}/token` (`upload`/`download`) then the returned `uri` | **none** — `ownerId` and `path` are query parameters (corrected w7/m150 t001; the mint sends no body) | 201 connect token; PUT upload / GET download on the returned URI — bounded subset implemented by w7/m150; live pinned-CLI roundtrip verified on dev-7 2026-10-03 |

Since v2.24.0 the CLI flow is two requests (`pkg/sandbox/repo.go` `connect` + `ExecSandboxStream`): the mint returns a connect token and the `uri` to redeem it at, and the redeem's response body is the SSE stream. The connect token is not an OAuth credential — bex signs it with a key derived from the gateway exec secret, binds it to the workspace, sandbox, `executionId`, operation, and the exact command bytes, expires it within 60 s, and consumes it once across replicas — so the redeem route is served outside the OAuth gate (classified in the always-public inventory) and re-applies the exec gate under the token's minter at redeem time. Refusals there are JSON `{"message"}` bodies with a precise status: 401 not a connect token, 403 wrong sandbox/execution/command, 409 already used, 410 expired, 404 `SANDBOX_NOT_FOUND` if the sandbox vanished, 429 from the IP limiter. Each `event: output` carries `{"stream":"stdout|stderr","data":"…"}`; the terminal `event: exit` carries `{"exit_code":N}` (the key `pkg/sandbox/sse.go` has decoded at every pin — bex emitted `exitCode` before w7/m147, which the CLI read as 0), and `event: error` carries `{"status":N,"message":"…"}` (404 terminated target, 403 access revoked mid-stream, 503 target not ready — code `target_unavailable`, a sandbox Pod on a NotReady or unreachable node — or exec failed to start), which the CLI prints as `sandbox exec stream error status N: message`. bex adds the internal `exitCode`/`error`/`code` keys beside them for one release so a bex-api reader that rolls out apart from the gateway decodes either; a terminated target's event may also carry `terminatedReason` and `terminatedExitCode` (how its container ended, w9/m349), which the CLI ignores. A missing exit event is a CLI error. bex-api performs workspace plus durable owner/admin authorization, signs a short-lived single-use ticket binding the exact command and sandbox namespace, and reverse-proxies the isolated ssh-gateway's stream. Only that gateway holds namespace-scoped `pods/exec`. MCP `sandbox_exec` consumes the same SSE path and returns buffered stdout/stderr/exit code.

**How the command runs (w32/m348, 2026-11-12).** The CLI shell-quotes its argv into the one `command` string; the server runs that string under `bash -c` in a new shell in the sandbox user's home directory, as Render does (Render SDK 1.8.0 `SandboxClient.exec`: "command is passed to `bash -c` in the sandbox"; render.com/docs/sandboxes-executing: "Each command starts in a new shell in your sandbox's home directory"). The page's advice to "Use `sh -c` to interpret operators such as `&&`, pipes, and redirection" is about the CLI's quoting, not the server's shell. bex falls back to `/bin/sh -c` on a root filesystem without bash, and an agent-session sandbox starts in its checkout ([ADR104 D2](../ADR104-sandbox-render-parity.md#d2--lifecycle-timeouts-and-suspension)).

## Bounded file transfers (w7/m150)

The pinned launcher (`v1.1.3-0.20260909214233-a764810a7682`) uploads a single file as `application/octet-stream` with its exact Content-Length (the empty-file case may be chunked), or streams a directory as `application/x-tar` with gzip encoding and unknown length. Downloads retain those content types and use gzip for both shapes. The gateway closes the gzip trailer only after validation and successful sandbox execution, so a late failure cannot become a successful truncated copy. The API preserves the compressed bytes end to end.

The file mint and transfer routes reuse sandbox exec's workspace create permission, durable owner/admin boundary, and sensitive agent-session permission. Minting requires the API write scope even for downloads. The public file token and internal gateway ticket use separate signing keys derived from the existing exec secret; neither authorizes OAuth, shell, or run routes. Tokens expire within 60 seconds, bind the exact operation and path, and are single-use through the shared nonce store. Missing durable replay protection makes file transfer unavailable. The gateway rechecks permissions when a transfer begins and during its lifetime.

Supported remote paths are clean absolute paths below `/`, or clean relative paths that resolve under the sandbox user's home directory as Render resolves them (w32/m299; no `..`). `.` is the home directory itself (w32/022), so the CLI help's own example `bex sandboxes cp <sbx>:. ./sandbox-home` downloads it, while an upload to `.` is refused as an existing directory. Paths are at most 4096 bytes and 64 levels, without traversal or control characters; existing symlink ancestors are refused. Transfers allow at most 256 MiB in each of the wire and decoded streams, 10,000 archive entries, and five minutes. Archives need unique names and parents preceding children; duplicate entries, missing end markers, and damaged gzip trailers are refused. **Links (w32/m380, 2026-11-14), as on Render** (render.com/docs/sandboxes-files: "Symlinks are preserved, and sockets, FIFOs, and other special files are skipped"): the same rule holds for uploads and downloads. A symlink is kept with its target byte for byte, whether relative, absolute or dangling, since the tenant is root in its own sandbox and can `ln -s` anything through exec. A symlink is never a parent, so no later entry is written through it. A hard link is kept only when it names a file earlier in the same archive, so it cannot reach outside the tree; tar archives the first name it reads for an inode and each later one as a link to it. A hard link to a symlink, which BusyBox writes for a second name of a symlink, arrives as a copy of that symlink. Sockets, FIFOs and devices are skipped, and so is a hard link to one. Link entries carry no body and count toward the 10,000-entry cap. The pinned client stores symlinks without following them and restores both link types inside an `os.Root`, which refuses any later write through an outward link. Before w32/m380 every link was refused, so one link anywhere in a tree, such as a Python virtualenv's `bin/python -> python3` or `node_modules/.bin`, failed the whole copy. The destination-path rule above is separate and unchanged: it is about the path the caller names, which must not pass through an existing symlink, so a transfer cannot be redirected outside the path it was authorized for.

A directory destination must not already exist; merging an existing tree is unsupported. Single files may replace a regular file. The destination parent must exist. The gateway checks the destination in a stdin-less exec before any of the upload is sent, so a refused one answers `409` or `404 file_not_found` at once, whatever the upload's size (w8/313). Before that fix, an upload over about 512 KB often stalled two minutes and then answered `503`: the staging exec exited without reading its stdin, and a pods/exec stdin stream the remote stops reading stalls rather than ends. The staging script still reads the rest of the upload before any later refusal, for a destination that changed after the check. Uploads stream into a private staging path and publish only after the complete input and sandbox execution succeed. **Metadata (w32/018, 2026-11-12):** an archive entry keeps its modification time (whole seconds, clamped to what a USTAR header holds), as extracting a tar does, and its permission bits without owners or special bits; the published directory takes the archive root's (`.`) mode, 0755 when the archive has none, instead of the staging directory's 0700, and a single uploaded file is published 0644, a plain create under the default umask, which is also the mode the pinned client gives a downloaded file. Render documents neither; downloads keep the sandbox's mtimes the same way. Cancellation attempts bounded cleanup; if the sandbox disappears, a hidden `.bex-copy-*` staging directory can remain, but no incomplete upload is published at the requested destination. Download errors after the first byte end with an incomplete gzip stream; the CLI reports failure rather than silently accepting the partial body. A download refused before its first byte answers its cause as a JSON error with its own status (w32/m380). The gateway used to abort it, which reached the client as `503 sandbox file gateway unavailable`, or as `409 file ticket already used` when Go's transport replayed the body-less GET on a reused connection after the gateway had spent the ticket. bex-api's hop to the gateway is never replayed now, and a hop dropped before any response answers `503 the sandbox file transfer ended before a response`, while an unreachable gateway still answers `503 sandbox file gateway unavailable`.

The shared contract and real handler/launcher tests live in `lego/cli/testdata/sandbox-file-contract.json`, `lego/cli/sandbox_contract_test.go`, and `lego/backend/internal/sandbox/file_roundtrip_test.go`. Those are local transport checks. **Live verification (2026-10-03, dev-7):** the pinned launcher built from `lego/cli` uploaded and downloaded a 3 MiB random file, an empty file and a nested directory through a real OpenSandbox sandbox via the in-cluster gateway's Kubernetes Executor; all were byte-identical (sha256 inside the sandbox and `cmp`/`diff -r` locally). Live refusals: traversal and relative paths `400`, foreign workspace `403`, another identity's sandbox `404 SANDBOX_NOT_FOUND`, replayed token `409`, wrong path or method `403`, an OAuth token on the transfer URI `401`, a declared 256 MiB + 1 byte upload `413`, chunked nonempty raw upload `411`, missing source or parent `404`, existing directory destination `409`. Killing the CLI mid-upload of 150 MiB published nothing and left no staging directory or transfer process in the sandbox. The dev-7 mock runs runc, not gVisor; the production gVisor path was exercised the same day by w9/m94 t004 (`copy` upload and download roundtrip on `bex-canary`). Sandbox groups, snapshots, and App SSH file access remain outside this work.

## Models

**Sandbox** — `{ id: <SandboxId>, plan: <SandboxPlan>, networkPolicy: <SandboxNetworkPolicy>, status: <SandboxStatus> }` (plus timestamps).

**SandboxPlan** (compute size): `1c-2g` · `2c-4g` · `4c-8g` · `8c-16g`, plus the deprecated `starter` · `standard` · `pro` (sized like the Workflow plans of the same name). Since w2/m263 each plan sets the sandbox container's CPU/memory limit (`starter` 0.5 CPU/512 MiB, `standard` = `1c-2g`, `pro` = `2c-4g`); see [ADR018 § Sandbox create flags](../ADR018-render-parity.md#sandbox-create-flags-w2m263) for `idleTimeoutSeconds`, `timeoutSeconds: 0`, groups and images.

**SandboxStatus**: `creating` · `running` · `suspending` · `suspended` · `resuming` · `errored` · `terminated`.

Note: Render's sandbox lifecycle has a `suspending`/`suspended`/`resuming` set (idle suspension and wake-on-exec) distinct from `terminated`. bex maps OpenSandbox `Pausing` ⇄ `suspending`, `Paused` ⇄ `suspended`, `Resuming` ⇄ `resuming` (rootfs-only on the k8s substrate, ADR042 D5) and delete ⇄ `terminated`. Since w2/m278 bex suspends a sandbox after `idleTimeoutSeconds` (default 900) with no exec or file transfer, and the next exec or file transfer resumes it ([ADR014 D4](../ADR014-sandboxes.md#d4--idle-hibernate--gateway-observed-autopause)).

## Deliberate bex divergences

- **`plan` → size**: each accepted plan maps to a fixed sandbox CPU/memory limit (w2/m263); an unknown plan is Render's `invalid_sandbox_plan` (`SANDBOX_PLAN_INVALID` until w8/312). The value is echoed back on `Sandbox`, and billing follows the resources through the weighted compute meter.
- **`networkPolicy`**: matches Render since w32/m283 ([ADR042 § Sandbox network policies](../ADR042-sandbox-cluster-substrate.md#sandbox-network-policies-w32m283)). An omitted policy is `allow-all`; `type` (or its deprecated alias `default`) is `allow-all`, `deny-all` or `allow-list`, and `allow-list` takes `rules` of `{domain, protocol: "https"}`. Invalid input — rules on a non-allow-list policy, an allow-list without rules, a domain with a scheme/port/path, uppercase, an inner wildcard, an IP literal, a cluster-local name, a duplicate or more than 100 rules — fails before any runtime call with `SANDBOX_NETWORK_POLICY_INVALID` across REST, GraphQL, MCP and the CLI. Cilium enforces each posture outside gVisor, above a platform floor (nodes, the Kubernetes API, metadata, private ranges, other Pods) that no policy opens.
- **Visibility/ownership**: Render's `ownerId` is a team boundary. bex adds a per-caller boundary inside that workspace: ordinary members list/get/exec/stop only sandboxes whose reserved owner/workspace metadata matches their resolved identity and whose sandbox-regime plus enforced-policy stamps are intact; an explicit workspace admin may operate all fully hardened owned sandboxes in the workspace. Foreign, ownerless, and incompletely hardened objects are indistinguishable from missing ones (`SANDBOX_NOT_FOUND`).
- **`image`**: bex's `Create` is template-based (ADR014 D2 / ADR042 D2) — the image is fixed at template registration, not taken from an arbitrary request ref.
