# Render sandbox groups: delete, default set and the project environment

Captured 2026-11-12 for w2/m359 from the pinned Render CLI v2.36 (`render-oss/cli` at `4fd34231b637`). Neither operation is in Render's public OpenAPI, so the CLI's generated client and commands are the contract. The group create, list, retrieve and update operations are in the OpenAPI and were served by w22/m311. The design bex chose is [ADR104 § D7](../ADR104-sandbox-render-parity.md#d7--groups-plans-limits-and-regions).

## Operations

| CLI | Route | Success | Refusals |
| --- | --- | --- | --- |
| `render sandbox-groups delete <sbg-id> [--confirm]` | `DELETE /v1/sandbox-groups/{sandboxGroupId}` | `204`, no body (`ParseDeleteSandboxGroupResponse`) | `409 default_sandbox_group_not_deletable`, `409 sandbox_group_suspended` (`pkg/sandboxgroup/repo.go`) |
| `render sandbox-groups default set <sbg-id>` | `POST /v1/sandbox-groups/{sandboxGroupId}/set-default`, no body | `200` with the group (`ParseSetDefaultSandboxGroupResponse`) | `409 sandbox_group_suspended` |

## Behavior the CLI states

- `cmd/sandboxgroupsdelete.go`: "Delete a sandbox group. This action is irreversible. Deleting a group terminates its sandboxes and deletes its snapshots and credentials shortly after. Suspended groups cannot be deleted. The workspace's default group cannot be deleted; make another group the default with "render sandbox-groups default set <sandboxGroupId>" first. Without --confirm, show the group that would be deleted without making changes."
- Before calling `DELETE`, the command reads the group (`GET /v1/sandbox-groups/{id}`) and refuses a default group itself with `ErrDefaultGroupNotDeletable`. Without `--confirm` it stops after that read.
- `cmd/sandboxgroupsdefaultset.go`: "Make a sandbox group the default for its workspace."
- `pkg/sandboxgroup/repo.go` maps the 409 codes to: "the workspace's default sandbox group cannot be deleted; …", "the sandbox group is suspended and cannot be deleted", and "the sandbox group is suspended and cannot be made the default".

## The dashboard

render.com/docs/sandboxes-creating (read 2026-11-12, 2026-11-14 and 2026-11-26) mentions the dashboard only for creating a group ("You can also create groups from the + New > Sandbox Group menu in the Render Dashboard. In the Dashboard, you can optionally place a group in a project environment."). Render's dashboard bundle (read 2026-11-26) does more than the docs say: it lists the workspace's groups (`sandboxGroupsForOwner`), renames one (`updateSandboxGroupName`), sets the default (`setDefaultSandboxGroup`), deletes one (`deleteSandboxGroup`), and gives each group the pages below. It imports nothing: images are imported with the CLI and the SDKs only.

### Render's group pages (bundle read 2026-11-26, w1/m658)

- **Routes and navigation.** A group is `/sandbox-group/<sbg-id>`. Its index and `sandboxes/*` are the Sandboxes list; a sandbox's drawer is `sandboxes/<sbx-id>/<tab>` with the tabs `events`, `configurations` (Details), `snapshots`, `logs` and `shell`. It also has `snapshots/*`, `builds/*` (Custom images) and `settings`; its `urls` chunk links a snapshot as `snapshots/<snp-id>` and an image as `builds/<name>?version=<version>`, and `/sandbox-group/new` is the create page (bundle read 2026-11-27, w3/m705). Every route's loader sends the browser away unless the frontend flag `sandboxes` is on; the sidebar's **Custom images** entry shows only with `sandbox_builds`, and the drawer's Shell tab only with `sandbox_shell`. The group's delete confirmation lists what goes with it: Sandboxes, Snapshots, Custom images (with `sandbox_builds`) and Brokered credentials ("This sandbox group, <name>, will be permanently deleted, along with its run history, logs, and settings:", "Anything using this group via SDK, CLI, or API will stop working."). A default group's delete first asks for the new default.
- **Sandboxes list.** `sandboxesForGroup(input: SandboxesForGroupFilterInput!)` answers `cursor hasMore sandboxes sortField sortDirection`; the input carries `statuses`, `search`, `createdAfter`, `createdBefore`, `cursor`, `limit` and the sort (`STARTED_AT`). The time range opens on the last 7 days and offers All time. Search reads "Search by name, sandbox ID, or status", and a status word becomes a status filter. Above the rows: **Total** and **Errored** over the range ("Share of sandboxes in the time range that ended in an error.", `<0.1%` for a small share), from the metrics query `SANDBOX_RUNS_COMPLETED_TOTAL` split by `sandbox_state` (succeeded, errored) into the chart ("Couldn't load sandbox runs"), and **Running** from `SandboxGroupRunningCount` (`sandboxGroup { runningSandboxCount }`, polled every minute: "Creating, running, resuming, or suspending now, whatever the time range. These count against the concurrency limit."). Rows update over `sandboxesForGroupUpdated` and `sandboxUpdated` with **Pause live updates** / **Resume live updates**; columns can be shown or hidden ("Show or hide columns"); selected sandboxes terminate together ("Failed to terminate N sandboxes. Please try again."). Empty states: "Create your first sandbox" ("Spin up a sandbox from the CLI, or set up your code to create sandboxes programmatically with the TypeScript and Python SDKs.", CLI steps "Install or update to the latest CLI", "Log in and use this workspace", `render sandboxes create --group <id> --wait`, and SDK steps "Set your API key", "Set up a project and install the SDK", "Initialize your first sandbox", "Run your code locally"), "No matching sandboxes" ("Try another search, or widen the time range.", Clear filters) and "Couldn't load sandboxes" (Try again).
- **The sandbox** (`sandboxListFields`): `id name status createdAt startedAt endedAt errorReason networkPolicy allowedDomains timeoutSeconds timeoutAt idleTimeoutSeconds sourceSnapshotId sourceBuildId sourceBuild { id name } source { … on SandboxEmailSource { email } … on SandboxTemplateSource { templateId } } region { id description } image { name registryUrl } plan { name cpus memoryGb storageGb }`. `errorReason` is one of `CONTAINER_CONFIG_INVALID HOST_LOST IMAGE_PULL_FAILED PROCESS_EXITED START_TIMEOUT TIMED_OUT UNKNOWN UNSCHEDULABLE`, each with its sentence ("Render couldn't tell why this sandbox errored. When the list shows only running sandboxes and the open one stops: "Your selected sandbox stopped. Switched to a running one."
- **Events.** `sandboxEvents(sandboxId, before: Time, beforeId, limit)` answers `hasMore events`, newest first (by timestamp, then id); `sandboxEventsSubscription` streams new ones. - **Snapshots page.** `SandboxSnapshots(input: SandboxSnapshotsFilterInput!)` answers `cursor hasMore snapshots` (`id sandboxGroupId name kind status sourceSandboxId plan { name cpus memoryGb } sizeBytes failureCode requestedAt capturedAt expiresAt`), with "Search snapshots" and the time range; `SandboxSnapshotsForGroupUpdated` keeps it live. ### What bex does (w1/m658)

Each choice the bundle and the docs leave open, with its basis:

| Question | bex | Basis |
| --- | --- | --- |
| Which sandboxes a group lists | Every sandbox of the group, live and ended (an ended one stays readable for 30 days, as its record does), created in the time range; no status named lists every status, ended ones included. Agent-session sandboxes belong to no group and are not listed. | Render's summary counts ended runs and its client-side filter keeps any status when none is named; REST `list-sandboxes` with `sandboxGroupId` already leaves agent sandboxes out (w22/m311). |
| Search | A status word (bex's or its label in the reader's language) becomes a status filter; anything else matches an id exactly or a name in part, ignoring case. | Render's search box and its client-side match. |
| Run summary | GraphQL `sandboxGroupRuns(sandboxGroupId, endedAfter, endedBefore)`: Total, Errored and Succeeded over the range and 30 buckets for the chart. A terminated sandbox counts where it ended; an errored one where it was created, since bex records no time it errored. | Render's `SANDBOX_RUNS_COMPLETED_TOTAL` is a metric bex does not keep; the same counts read from the group's sandboxes. |
| Events | A new table, `sandbox_lifecycle_events` (migration 0350), records created and ready at create, suspended by the verb or the idle sweeper (`IDLE_TIMEOUT`), resuming by the verb or for a command (`CONNECTION`), and terminated by the verb or a group delete (`SYSTEM`). A sandbox created before it reads its created event from its record and, once ended, its terminated event (`SYSTEM`). Executions and snapshots come from their own stores. Errored is not reported: bex does not observe the transition. Events are kept 35 days. | Render's `sandboxEvents` shape; bex had `sandbox_activity`, executions and snapshots but no lifecycle record. |
| Trigger and who started it | The created event's trigger is the surface the request came through (`core.ProductSurface`: Dashboard, CLI, API, SDK by its user agent, else bex's `SYSTEM`), and its user is the signed-in person's email; an API key's create has no user. The drawer's Details read both (`Sandbox.trigger`, `source`). bex has no templates, so no `SandboxTemplateSource`. | Render's created event and `source`. |
| Cost and Duration | Duration only (from the sandbox's start, or creation, to its end or now). | Logs tab | Left out until the logs API serves Render's `sandbox` filter, which it refuses by name today (`unsupportedLogFilters`); filed as w1/162. | The DoD's alternative. |
| Live updates | bex has no GraphQL subscriptions, so the dashboard polls: the list, its summary and the running count every 5 s while live, and **Pause live updates** stops all three; an open sandbox's drawer and its events every 5 s while the sandbox is creating, running, resuming or suspending; the Snapshots and Custom images pages every 10 s while a capture or an import is in flight. | Render's subscriptions; the cadences stay clear of the QUIC idle band (`poll-cadence-invariant.test.ts`). |
| Paths | `/sandbox-groups/<sbg-id>` stays, with Sandboxes as its index and `snapshots`, `images` and `settings` below it; a drawer is a search parameter of its page (`?sandbox=<sbx-id>&tab=snapshots`, `?snapshot=<snp-id>`, `?image=<name>&tab=details`). `/sandboxes/<sbx-id>` and `/sandbox-snapshots/<snp-id>` resolve a bare id. ## The project environment

The pinned OpenAPI's `create-sandbox-group` body has `ownerId`, `name` and `region` only. Its response, and the retrieve and list shapes, carry a nullable `environmentId` ("The ID of the environment this sandbox group belongs to, if any"). Render's own clients go further. They are the contract here, as [ADR104 § D9](../ADR104-sandbox-render-parity.md#d9--the-sdk-is-part-of-the-contract) makes the SDK:

- **Create:** SDK v1.10.0's `createGroup({environmentId})` and CLI v2.38.0's `sandbox-groups create --environment <id or name>` send `environmentId` in the create body.
- **Move:** both clients put a group in an environment, or move it to another one, with Render's environment-resources routes. The SDK's verb is `setGroupEnvironment(group, environment)`; the CLI's is `sandbox-groups environment set <group> <environment>`, which "relies on the API to move the group out of any environment it was in". Both send `POST /environments/{id}/resources` with `{resourceIds: [group]}`.
- **Clear:** `setGroupEnvironment(group, null)` and `sandbox-groups environment remove <group>` read the group and, when it is in an environment, send `DELETE /environments/{that id}/resources?resourceIds=<group>`.
- **Read back:** both clients read the group again afterwards.

The requests and the statuses each client accepts are recorded in `lego/backend/internal/sandbox/testdata/group-environment-contract.json` (w22/m603). Render's public docs (render.com/docs/sandboxes-creating, read 2026-11-23) still name only the dashboard's placement at create, and the public OpenAPI's `resourceIds` description lists "env group, service, Postgres, or Redis".

Placement is membership only: who can see or use the group does not change (w22/m412, [ADR104 § D7](../ADR104-sandbox-render-parity.md#d7--groups-plans-limits-and-regions)).

|  | bex |
| --- | --- |
| REST create body | the pinned fields, plus an optional `environmentId` (a string or `null`), which SDK v1.10.0 and CLI v2.38.0 send |
| Response | `environmentId` is the environment's public `evm-` id, `null` for a group in none |
| `POST /v1/environments/{id}/resources` with an `sbg-` id | `201` with the environment: the group is in it, moved out of any other |
| `DELETE /v1/environments/{id}/resources?resourceIds=<sbg->` | `204`: the group is in no environment; a group that is not in this one is left where it is, as for every other kind |
| An `sbg-` id that names no group of the workspace, on either route | `404 SANDBOX_GROUP_NOT_FOUND`, "sandbox group not found" (the CLI's own reading), the same for another workspace's group; nothing in the request changes |
| A create in another workspace's environment, or one that does not exist | `404 NOT_FOUND`, one answer for both |
| A protected environment on either side of a create or a move, for a non-Admin | `403 PROTECTED_ENVIRONMENT_ADMIN_REQUIRED` ("Moving a group into or out of a protected environment requires an admin", CLI v2.38.0) |
| The environment object | lists no groups, as Render's does not |
| The environment is deleted | the group stays and reads `environmentId: null` (unknown on Render, not enforced; see below) |

Placement and moves are the only group verbs gated by environment protection. Deleting, editing or reading a group in a protected environment is not restricted: Render documents none of it (unknown, not enforced).

GraphQL `setSandboxGroupEnvironment` and MCP `set_sandbox_group_environment` take the SDK's shape (an environment, or null to clear) and go through the same verb as REST.

### Render's dashboard (bundle read 2026-11-23)

- **The group's own page** shows no environment and offers no move.
- **The project page** lists an environment's groups among its resources. Selected groups move with the bulk **Move** control, into another environment or out to the workspace, through the generic `changeEnvironmentForResources` mutation.
- **Other lists:** the environment's "Move Services" dialog lists the workspace's groups as candidates, and the home page's ungrouped table lists groups that are in no environment.
- **Deleting an environment or project that holds the default group** is refused there: "This … contains the default sandbox group. Make another group the default first." Whether Render's API refuses it too is not known (w22/030).

### bex's dashboard (w22/m603)

- **The project page.** Each environment's card lists its sandbox groups among its resources: type "Sandbox Group", status "Ready", the Default badge, and the group's region. They are counted under "All" but have no type filter of their own, so the card's pills stay the ones its skeleton previews, and a group row has no row menu.
- **Moving and removing.** Selected groups move with the card's bulk **Move**. The environment's **Manage resources** dialog has a Sandbox Groups tab, where a group is checked to put it in the environment and unchecked to take it out. Both write `setSandboxGroupEnvironment`.
- **The group's own page** is unchanged, as Render's.
- **Not yet as on Render (w22/031):** the Overview's ungrouped list does not list groups that are in no environment, and bulk Move has no workspace item that takes a selection out of its environment.

## What bex answers where Render is silent

- `sandbox_group_suspended` is never produced: bex has no suspended sandbox groups.
- A repeated `DELETE`, or one for a group whose delete is still finishing, answers `404 SANDBOX_GROUP_NOT_FOUND`: the group leaves every read the moment its delete starts.
- `set-default` on the group that is already the default answers `200` with it.
