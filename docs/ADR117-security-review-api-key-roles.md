# ADR117: Security review — an API key acts with its creator's role

- **Status**: Accepted (2026-11-18, w9/m481)
- **Trigger**: w9/m481 changes what a credential may do. Until then every bex API key was bound as a Developer; now a key acts with its creator's current member role in the workspace it was minted in, as on Render ([ADR024 § An API key acts with its creator's role](ADR024-members.md#an-api-key-acts-with-its-creators-role-w9m481)). An Admin's key can now manage members' notification settings, registry credentials, protected environments and webhooks. The milestone's boundary (I1–I5) was its acceptance floor; this is the adversarial pass over the implementation before it reached production.
- **Lineage**: a focused pass after [ADR110](ADR110-security-review-round25.md), like [ADR103](ADR103-security-review-static-rewrite-proxy.md). It re-confirms ADR072's mint-class rule (codex round-7 F3) and w4/079 for every caller but an attributed key on webhook create and repoint.

## Scope

`lego/backend/internal/core/keyrole.go` (`keyCeiling`, `AuthorizeExportClass`, `AttributedAPIKey`, `HoldsFresh`) and its two call sites in `core/base.go` (`checkAuthz`, `checkAuthzFresh`); `twofactor.Gate.APIKeyCreator` and its wiring in `cmd/api/main.go`; the mint (`tenancy.BindKey`, `store.BindClientForCreator`), the follow (`store.enqueueRoleReconciliation`, `members.Service.reconcileCreatorKeys`, `store.RecordKeyCreators`) and the revoke (`tenancy.UnbindKey`); the webhook verbs' class gate; the three projections moved to `HoldsFresh` (webhook secrets, usage billing figures, the sandbox admin view). Attacker: a workspace member with any role, a holder of a stolen or stale key, a delegated third-party OAuth client, and anyone who can register a Hydra client through public dynamic client registration.

## Verdicts

| # | Attack | Verdict | Evidence |
| --- | --- | --- | --- |
| 1 | An Admin is demoted; their key keeps acting as Admin because its tuple did not move (a failed or still-queued revoke) | Blocked | every decision for an API key also requires its creator's decision on the same relation and object through the same check (`keyCeiling`): uncached for a write, cached for a read exactly as the creator's own is. `TestKeyIsRefusedWhatItsDemotedCreatorMayNotDo`, `TestKeyCeilingChecksTheCreatorAsFreshlyAsTheKey`; against real Postgres and OpenFGA with the key's revoke made to fail, all four Admin writes are refused on REST, GraphQL and MCP at the next request (`TestAPIKeyActsWithItsCreatorsRoleE2E`) |
| 2 | A key is used in another workspace where its creator is an Admin | Blocked | a key has a row and tuples only in its own workspace; naming another is refused by membership; the ceiling refuses any other workspace object even against a stray hand-written tuple. `TestKeyActsOnlyInItsOwnWorkspace`, the e2e's cross-workspace list |
| 3 | A key with no recorded creator acts above a Developer (a pre-stamp key, a hand-written Admin grant) | Blocked | never re-seated (its `created_by` stays NULL) and the ceiling refuses it every relation a Developer lacks, whatever it holds. `TestUnattributedKeyNeverPassesAnAdminRelation`. The isolation fixture that relied on such a grant now names its bootstrap client as creator (`scripts/verify-sandbox-isolation-live.sh`) |
| 4 | A key is re-roled through the member verbs | Blocked | `guardMachine` refuses a machine target (`MEMBER_IS_MACHINE`), and `ChangeRole` is mint-class, so a key cannot call it either. The e2e asserts both |
| 5 | A key mints a key, enrolls an SSH key, invites or re-roles a member, creates an org or workspace | Blocked | `AuthorizeMintClass` is unchanged and refuses every machine caller; `TestAuthorizeExportClassAdmitsOnlyAttributedKeysBeyondTheMintClass` asserts it for an attributed key; the e2e asserts the key mint, the invite and the role change |
| 6 | A delegated third-party OAuth token, or a non-key `client_credentials` client, creates or repoints a webhook | Blocked | `AuthorizeExportClass` admits a key only when Hydra's registry names it a bex API key with a creator; everything else falls to `AuthorizeMintClass`. `TestAuthorizeExportClassAdmitsOnlyAttributedKeysBeyondTheMintClass`, `TestCreateRequiresMintCredentialClass`, `TestAnAdminsAPIKeyManagesWebhooksAsTheAdminDoes` |
| 7 | The creator lookup cannot answer (Hydra down) | Blocked, fails closed | `ErrAuthzUnavailable` (503) for every key decision and the export-class gate; never a pass. `TestKeyCeilingFailsClosedAndLeavesOtherClientsAlone`. A store that cannot name creators is reported at startup (`TestWireTwoFactorWarnsWhenTheAPIKeyStoreCannotNameACreator`) |
| 8 | A key bound before this change stays a Developer while its creator is an Admin | Not a gap: under-privileged until the startup backfill seats it (`store.RecordKeyCreators`, `TestRecordKeyCreatorsSeatsLegacyKeysOnce`), and capped by its creator meanwhile |
| 9 | A mint racing its creator's role change seats the key at the old role | Blocked | the mint holds the workspace advisory lock `UpdateMemberRole` takes, reads the creator's row inside it, and refuses while the creator's own intent is queued (`ErrRoleUnsettled`). `TestBindClientForCreatorSeatsTheCreatorsRole` |
| 10 | A forged creator stamp: a client registered through Hydra's public dynamic registration claiming `bex.co/api-key` and an Admin's `bex.co/created-by` | Blocked twice | Hydra refuses `metadata` on `POST /oauth2/register` (`invalid_client_metadata`, "'metadata' cannot be set for dynamic client registration", checked on dev-9 on 2026-11-18). And the stamp only ever restricts (the ceiling is an AND, and the export-class gate is followed by `RelCanManage`). Authority comes from the binding row and tuple only `BindKey` writes, under the mint-class gate; a registered client has neither, so it is refused on every workspace object, its own home check included |
| 11 | A key minted by another key (possible before codex round-7 F3) inherits a higher tuple | Blocked | the ceiling walks the creator chain, each link capped by the next, at most three; a longer or cyclic chain fails closed. `TestKeyMintedByAKeyIsCappedThroughTheChain`. Production holds none |
| 12 | A projection that asks OpenFGA directly (who sees a webhook's secret, billing figures, every sandbox) answers from a key's stale tuple | Fixed | the three that did now ask `Base.HoldsFresh`, which carries the ceiling. The remaining direct checks are tuple management (`members.checkRoleFresh`, `tenancy.revokeOtherRoles`) and the operator-only ops-console role read, none of which decides what a caller may do |
| 13 | A revoked key keeps a role tuple other than `developer` | Fixed | `UnbindKey` revokes every role, idempotently, before the row (`TestUnbindKeyRemovesBindingAndRevokesMembership`, and the e2e checks every role after a revoke) |
| 14 | Over random histories of role changes, partial and failed tuple writes and stray grants, a key exceeds its creator or acts outside its workspace | Blocked | `TestKeyNeverExceedsItsCreatorOverRandomHistories` (200 histories of 30 steps, every relation in two workspaces) |

Every guard was reverted once and a test above failed: the ceiling in either check path, the home-workspace check, the unattributed ceiling, the chain bound, the export-class attribution, and the keys-first convergence in `ChangeRole`.

## Residual risks

- **A read on another replica can use a positive cached up to 30 s** after a demotion, for the key exactly as for its creator's own session ([ADR012 §8d](ADR012-auth.md#8d-revocation-latency-w21085)). Writes are uncached. Owner: the ADR012 cache budget, unchanged.
- **Leaked production fixtures (found during this review). Closed 2026-11-18 (w9/119).** On 2026-11-18 production's Hydra held 16 `m35-*` API keys `scripts/verify-sandbox-isolation-live.sh` minted on 2026-11-15 and never deleted, 4 of them bound as Admin, plus 4 bootstrap clients bound as Admin of the 8 leftover fixture workspaces (8 rows) and of `workspace:default`. Their secrets lived only in the run's deleted fixture directory, and since this change the 16 keys cannot act above a Developer, but they were still live credentials.
  - **Cause.** Four `sandbox-measure.yml` legs failed 17–28 minutes into their run, after the bootstrap's 15-minute access token had expired. The cleanup trap's API calls were refused, and `graphql_call`'s `fail` exited the trap before its Hydra and OpenFGA deletes ran.
  - **Removal.** The 8 workspaces went through `deleteWorkspace`, which revoked the bootstraps' 8 workspace tuples. Then the 20 Hydra clients and the remaining 20 tuples that named them (the keys' 16 and the 4 on `workspace:default`) were deleted. Hydra, `tenant_members` and OpenFGA now answer zero for `m35-%`.
  - **Prevention.** The trap now mints a fresh token and survives a refused call. Every run also sweeps `m35-*` fixtures older than six hours before it provisions. `scripts/verify-sandbox-isolation-live.test.sh` covers both.
  - **Open follow-up.** `deleteWorkspace` revokes only the people in a workspace, so a deleted workspace's API keys keep their Hydra client and tuples. Filed as w9/120.
- **Render's other key forms are not offered**: classic keys that act in every workspace, per-permission scoped keys, and a Viewer or Contributor minting a key capped at their role. Each is a parity variant filed separately (w9/118, w9/114, w9/115); none widens what a bex key can do today. Two verbs Render serves to keys stay mint-class for keys until their own review: a member role change (w9/116) and a Postgres credential (w9/117). The member role change was reviewed and opened to an attributed key on 2026-11-19 ([ADR120](ADR120-security-review-key-member-management.md)); verdicts 4 and 5's "`ChangeRole` is mint-class" no longer holds for such a key, and `guardMachine` still refuses a key's binding.
