# ADR: GitHub↔workspace connection model — workspace-owned, many-to-many

_Renumbered from ADR075 to ADR078 (2026-08-20): ADR075 was concurrently claimed by [ADR075-user-onboarding.md](ADR075-user-onboarding.md); per the w6/m40 convention the number stays with the more-cited document (29 vs 11 citing files). Bare “ADR075” references to THIS document across `lego/backend/internal/github/`, `internal/agentsession/`, and `.pm/w5/` were rewritten to ADR078 in the same change._

**Status:** accepted — 2026-08-19, implemented by [w5/m74](../.pm/w5/done/m74/README.md); **revised 2026-09-16** — the cardinality decision in §2 is reversed from **N:1** to **N:N**: an installation may now be bound to several workspaces, each binding independently proved. The trigger was a live report that the one behaviour Render has and bex did not is the plain one — _the same GitHub account serving more than one workspace_ — and that bex offered no completable path to it: the install URL dead-ends silently (GitHub strips `state` for an already-installed account), the claim flow filtered the installation out as "bound elsewhere" and reported `no_claimable_installation` ("install the App first"), and a direct github.com install is a no-op. Three dead ends, none of which named the real cause. §2 records why the original rejection reasoning does not survive the three-proof claim flow, §4a restates the push webhook's fail-closed invariant for fan-out, and §1's rejection of Render's per-user credential model is _reaffirmed and strengthened_ — the parity target is Render's **observable behaviour**, never its mechanism. Also **revised 2026-08-20** after the live production walk (w5/046) failed and exposed three defects §3 had missed — the wrong assumption that GitHub preserves `state` for already-installed accounts (it does not; §3a's claim flow is the correction), the dashboard's GitHub surfaces ignoring the workspace switcher (§6), and the connect flow failing only at the callback when the OAuth verifier is unconfigured (§7). The revision is implemented by [w5/m75](../.pm/w5/done/m75/README.md) and **verified live on production 2026-08-20**: the claim flow bound the already-installed `puncsky` installation to a second workspace through GitHub OAuth with no reinstall. Amends [ADR026-github-integration.md](ADR026-github-integration.md) §4 (the one-connection-per-workspace data model) and closes its "multi-workspace connection routing is w6" deferral with an explicit decision. Records a deliberate Render-parity divergence for [ADR018-render-parity.md](ADR018-render-parity.md).

## Context

### The incident that forced the question

A workspace admin installed the bex GitHub App on their **personal** GitHub account directly from `github.com/apps/<slug>/installations/new` (installation `154851602`), then opened `services/new` and saw no repos. Diagnosis against production:

1. A direct GitHub-side install is a deliberate **no-op** in bex — the `installation` webhook event is answered 200 and discarded (`lego/backend/internal/apps/webhook.go`), because binding requires the three-proof connect flow ([ADR026 §4](ADR026-github-integration.md), w1/m67 F3). Working as designed, but the user had no way to know.
2. The `services/new` "Connect GitHub" prompt links the **bare** install URL from the `gitConnection` query (`dashboard/src/features/services/components/service-source-picker.tsx`) — no signed state, so even a user who dutifully follows the product's own CTA ends in `missing_state`. Only the Settings card's `connectGit` mutation mints a state-bearing URL. A product bug, not a design decision.
3. Even after fixing 1–2 by re-running connect from Settings, the deeper limit remains: `git_connections` is keyed `PRIMARY KEY (workspace_id)` — **one connection per workspace**. The workspace was already bound to the `bex-co` org installation, so connecting the personal account would silently **replace** the org binding rather than add to it. A team that keeps some repos under an org and some under members' personal accounts cannot deploy both from one workspace.

### What the 2026-08-20 live walk added (the revision's evidence)

Attempting verification point 3 against production — connecting the already-installed `puncsky` installation to a second workspace, driven through a real browser — failed three independent ways, each a defect this ADR's first version missed:

1. **GitHub strips `state` for already-installed accounts.** The original §3 asserted "GitHub preserves `state` through the configure flow as well as first install". Observed: the install URL's account picker shows plain **Configure** links (`github.com/settings/installations/<id>`) for any account that already has the app — the signed `state` is dropped; even `installations/new/permissions?state=…&target_id=<user>` redirects to the same settings page. There is **no state-preserving GitHub-side path for an already-installed account**, so m74's `missing_state` recovery page sends the user in a circle: its "try the stateful connect" CTA hits the same wall. The only flow GitHub always carries `state` through is **OAuth user authorization** (`/login/oauth/authorize`) — which is what §3a's claim flow builds on.
2. **The dashboard's GitHub surfaces ignore the workspace switcher.** Every git hook (`useGitConnection(s)`, `useRepos`, `useConnectGit`, `useDisconnectGit`, `RepoBranches`) omits `ownerId`, so the backend resolves the caller's **default** (oldest) workspace regardless of the selected one — verified live: with `tian-personal` selected and the page fully reloaded, the Settings card still showed the `bex` workspace's connection, and the same probe against the API with an explicit `ownerId` returned the correct (empty) set. Consequence: "Connect (another) account" while a non-default workspace is selected would silently bind the installation to the **wrong tenant**. The services/databases hooks already pass `ownerId: currentWorkspaceId`; the git feature simply never did.
3. **A missing OAuth verifier fails at the worst possible moment.** Production's `bex-github-app` Secret lacked the `client-id`/`client-secret` keys (the env refs are `optional: true`), so the installation-admin `Verifier` was nil — and per the fail-closed design every binding 503s **at the callback**, after the user has walked the entire GitHub flow. `StartConnect` happily minted install URLs it knew could never complete, and nothing at startup or connect time surfaced the misconfiguration.

### What Render actually does — the full granularity model (deep-researched 2026-08-21)

Researched from [render.com/docs/github](https://render.com/docs/github), [login-settings](https://render.com/docs/login-settings), [your-first-deploy](https://render.com/docs/your-first-deploy), [team-members](https://render.com/docs/team-members), [deploys](https://render.com/docs/deploys), [monorepo-support](https://render.com/docs/monorepo-support), the [Dec-2024 multi-account changelog](https://render.com/changelog/add-your-git-deployment-credentials-to-multiple-render-accounts), the [May-2026 Update-Source changelog](https://render.com/changelog/change-your-services-backing-repo-or-image-in-the-render-dashboard), and archived staff answers from the (since-sunset) community forum.

Render has **exactly three durable objects and no workspace-level git object at all**. Repo access at deploy time is a chain: **service → (points at) a member's user credential → (authorized as) that member's GitHub account → (which can see) a GitHub App installation → (whose grant includes) the repo.** Break any link and deploys stop; running instances keep serving.

| Layer | Object | Managed where | Who can change it | Disconnect ⇒ what breaks |
| --- | --- | --- | --- | --- |
| **User** | "Git deployment credential" — the OAuth link between one Render user and one GitHub account | Render → Account Settings → Account Security | only that user | every service _pointing at_ this credential stops deploying |
| **Installation** | The Render GitHub App on a personal account or org, "All repositories" vs "Only select repositories" grant | **github.com only** — Render hosts no grant-editing UI, just the deep link `github.com/apps/render/installations/new` | whoever holds GitHub-side power (org owners can restrict installs to owners-only, with member-initiated installs becoming approval requests) | uninstalling removes repo access for **everyone** deploying through that installation |
| **Service** | Two pointers: which member's _credential_ deploys it, and which _repo+branch_ backs it | Service → Settings | any member whose role can edit services | credential swappable to another member (the documented creator-left fix); since May 2026 the backing **repo is swappable too**, incl. repo→Docker-image (fully detaching the service from git) |
| **Repo** | _(nothing)_ — no repo-scoped Render object beyond installation-grant membership; monorepo root-dir/build filters scope **triggers**, not access | — | — | — |

Layer-level rules and edges the docs + staff answers pin down:

- **User cardinality:** one GitHub account per Render user, ever ("A given Render account can have up to one connected account from each Git provider"). Since Dec 2024 the _same_ GitHub account may be a **deploy** credential on multiple Render accounts (the agency case), but may **log in** to only one. Login+deploy on one Render account must be the same GitHub account.
- **Repo picker in a team workspace:** resolves through the **creating user's** GitHub identity — what you see is (your connected account's reachable repos) ∩ (repos granted to installations of the app). A teammate's grants never appear; a collaborator needs both halves to hold for _themselves_.
- **Two different GitHub-side revokes** (a recurring confusion Render staff had to spell out): revoking under _Authorized GitHub Apps_ kills one **user's** OAuth link (their credential + login); uninstalling under _Installed GitHub Apps_ kills the **installation** for everyone. Render's own cleanup recipe enumerates three surfaces: `github.com/settings/installations`, `…/apps/authorizations`, `…/applications`.
- **Grant staleness:** grant edits happen after the fact on github.com and Render promises no event-driven picker refresh — the documented remedies for a stale repo list are reconfigure-the-grant or disconnect-and-reconnect the user credential.
- **Documented failure mode:** "if the creator of a Render service loses access to that service's connected GitHub repository, it can disrupt deploys" — remediated by manually re-pointing the service at another member's credential.

In one sentence: **on Render, people connect and workspaces borrow; on bex, workspaces connect and people prove.** Render's "direct github.com install just works" is a corollary of never _binding_ installations — it _reads_ them through whoever is looking, and pays for that with the per-person coupling above.

### The inconsistency, named

| Dimension | Render | bex today |
| --- | --- | --- |
| Connection owner | user (member) | workspace |
| Installations reachable per workspace | unbounded (union of members' identities) | exactly 1 |
| Installation → workspace binding | none (workspace-agnostic) | strict, unique (w1/m65 F2) |
| Repo picker enumerates | creating user's GitHub identity, all installations | the workspace's single installation |
| Direct github.com install | supported, documented | silent no-op |
| Creator leaves the team | service deploys **break** until credential re-pointed | no effect (workspace owns the connection) |
| Deploy credential | the pointing member's user token | fresh installation token per deploy trigger |

Two of these divergences are bex **strengths** (rows 6–7): workspace ownership means no member-departure breakage and no per-service credential pointer to babysit, and it is what lets the identity-less push webhook, agent-session token mint, and blueprint sync resolve a workspace without any user in the loop. Three are real **gaps** (rows 2, 4, 5): a workspace is capped at one GitHub account, the picker can never show a second account's repos, and the GitHub-side install path every GitHub user already knows is a dead end.

The table reads "bex today" as of 2026-08-19. Rows 2, 4 and 5 were closed by m74 + m75; **row 3 is closed by the 2026-09-16 revision** (§2), leaving only rows 1, 6 and 7 — the deliberate ownership divergence and the two strengths that follow from it.

### Granularity mapping after this ADR (m74 + m75 shipped)

Where each of Render's control surfaces lands in bex's model — the connect/disconnect answer at every level:

| Render control surface | bex equivalent |
| --- | --- |
| User credential (per member, Account Security) | **absent by design** (§1) — no per-member layer exists to connect, revoke, or leak; members prove installation admin at bind time instead of holding standing credentials |
| Installation, workspace-agnostic, read through user OAuth at query time | installation **bound to one or more workspaces**, each binding separately proved (§2, 2026-09-16); bound via the three-proof install flow (first install) or the **claim flow** (§3a, already installed) — the claim flow is the workspace-bound model's replacement for Render's read-through-whoever-is-looking trick, and N:N is what makes it reach Render's observable outcome |
| Per-service credential pointer (swap when the creator leaves) | not needed — every deploy mints a fresh installation token from the connection whose `account_login` owns the repo (§4) |
| Disconnects: user-level OAuth revoke / GitHub uninstall / service repoint | workspace-level per-installation disconnect (`DELETE /v1/git/connections/{installationId}`, §5) + the same GitHub-side uninstall; nothing per-member to revoke |
| Repo grants: edited on github.com, deep-linked from the product | identical — bex's "Manage repo access on GitHub" is the same deep link; grants live in the installation on both platforms, and **neither platform has a product-side per-repo allow/deny** |
| Grant-staleness handling (no promised auto-refresh) | same class — bex fetches repo lists on demand per connection |
| Per-service **source swap** (change backing repo, or repo→image, Settings → Update Source) | **not shipped** — the one Render granularity bex lacks; it is service-config granularity, not access granularity (tracked as a gap in Consequences) |

## Decision

### 1. Connections stay workspace-owned — Render's user-bound model is rejected

The connection remains an object of the **workspace**, minted by an admin, visible to and usable by every member per their role. We do not adopt per-user Git deployment credentials or per-service credential pointers.

Rationale, in order of weight:

- **No member-departure breakage.** Render documents the failure and a manual remediation; bex simply doesn't have the failure. A deploy credential that dies when a human leaves is the wrong shape for a team product.
- **Headless consumers need workspace resolution.** The push webhook (no identity), the agent-session token mint (sandbox, not a browser user), blueprint auto-sync, and deploy-time clone-secret refresh all resolve `workspace → installation` with no user in the call path. A user-bound model would force every one of them to pick _some member's_ credential — reintroducing the pointer problem everywhere.
- **Tenancy alignment.** [ADR043](ADR043-tenant-namespace-isolation.md) makes the workspace the isolation unit; repo access is a workspace capability like its namespaces, quotas, and secrets, not a property of whichever member clicked first.
- **Auditability.** One workspace-scoped binding set, admin-gated mutations, is a smaller and more legible trust surface than N members × M providers of personal credentials.

This is a **deliberate, recorded parity divergence**: [ADR018](ADR018-render-parity.md) gets a divergence note on the git-integration rows (the REST/GraphQL/MCP repo surface is a bex extension anyway — Render lists repos only through its private dashboard API).

**Reaffirmed 2026-09-16, against the strongest argument for adopting it.** The case for per-user credentials is usually made as a _confidentiality_ claim: on Render, member A picks from A's own private repos, and teammate B never sees A's private repo list. That is true, and it is the one thing the per-user layer buys. It does not survive scrutiny as a reason to build it here:

- **It protects the picker, not the code.** Once A creates a service from a private repo, every teammate whose role can operate that service sees its repo URL, reads its build logs, redeploys it, and — at developer and above — reaches its source through a shell. On Render too. The per-user layer hides a _list_, while the workspace exposes the _contents_ of everything already on that list.
- **The confidentiality is GitHub's, not the platform's.** Render's picker resolves to (your GitHub account's reachable repos) ∩ (the App's grants). The first term is GitHub's own account boundary; Render adds no boundary, it merely declines to remove one. "Per-user makes sense" is an argument that _GitHub accounts_ make sense — which they do — not that bex should mint a second credential layer.
- **The real control surface is the installation grant, and it is strictly finer.** "All repositories" vs "Only select repositories" is a per-repo decision made by whoever holds GitHub-side authority; bex honours it unchanged. Per-user is all-or-nothing by identity: a Render user has exactly one GitHub account, so a member whose single identity spans personal **and** org repos cannot expose only the org half. The grant can. The coarser control is not the one to build.
- **It would be the only sub-workspace confidentiality boundary in bex.** Env vars, OpenBao-backed secrets, database credentials, build logs, deploy history, artifacts and shell access are all workspace-scoped, per [ADR043](ADR043-tenant-namespace-isolation.md) and the [ADR024](ADR024-members.md) role matrix — none of them is per-member. A single per-member boundary that every neighbouring surface declines to honour is not a security control; it is a UI filter that manufactures false confidence.
- **bex already has a stronger answer to the stated want.** "B must not see A's private repos" is satisfied by a **separate workspace** — a real isolation boundary where B is not a member and therefore sees no repo list, no service, no logs and no shell. What used to block that answer was the N:1 cardinality (A's personal account could not be in both A's own workspace and the team's); §2 removes it. The scenario offered as an argument _for_ per-user is in fact an argument for N:N.

What per-user genuinely buys and N:N does not: deploying one personal private repo into a **shared** workspace without exposing that account's whole grant to the workspace. That is a narrow, real capability. Its price here would be a per-member refreshable credential store, Render's documented creator-leaves breakage, and the false boundary above. If the need is ever demonstrated, the cheaper and strictly stronger shape is a **per-connection repo allowlist chosen at bind time** — workspace-owned, no per-user credentials, and something neither platform has today. Recorded in Alternatives; not scheduled.

### 2. A workspace holds **many** installations; an installation may serve **many** workspaces (revised 2026-09-16)

The cardinality is **N:N**. A workspace connects many installations (m74); an installation may be bound by many workspaces, **each binding independently proved** by the §3/§3a flows.

- **`git_connections` is re-keyed** from `PRIMARY KEY (installation_id)` to the composite `PRIMARY KEY (workspace_id, installation_id)`, keeping the non-unique `workspace_id` index and adding a non-unique `installation_id` index for the webhook's reverse lookup. Columns are unchanged (`workspace_id`, `installation_id`, `account_login`, `created_at`). The new key is a strict **relaxation** of the old one, so every existing row already satisfies it: the migration is a constraint swap with **no dedup, no backfill, and no row rewrite**, and it is backward-compatible with the pre-revision binary (which simply never inserts a second row for an installation).
- **`GitConnectionByInstallation` becomes `GitConnectionsByInstallation`** (plural). It had exactly two non-test callers: the claim-flow candidate filter, which this revision deletes, and `WorkspaceForInstallation`, which §4a makes plural.
- **Within a workspace the model is unchanged.** `(workspace_id, installation_id)` is still unique, so a workspace cannot hold two rows for one installation and reconnect stays idempotent. `account_login` remains unique within a workspace by construction (GitHub allows one installation of a given App per account), so **repo owner → connection** resolution inside a workspace is still unambiguous, and `account_login` is still refreshed from the app-JWT lookup whenever the row is touched.
- **Quotas, now symmetric.** `BEX_MAX_GIT_CONNECTIONS_PER_WORKSPACE` (default `10`, `0` disables) bounds a tenant's connection fan-**in** as before, refusing with coded `GIT_CONNECTION_LIMIT` (409) identically across REST/GraphQL/MCP. N:N adds the mirror bound `BEX_MAX_WORKSPACES_PER_GIT_INSTALLATION` (default `10`, `0` disables), which caps how many workspaces one installation may serve and therefore the webhook's fan-**out** (§4a); it refuses with coded `GIT_INSTALLATION_WORKSPACE_LIMIT` (409) on all three surfaces. Both are admitted inside the same store transaction as the insert, for the reason the existing cap already is: a standalone count lets two concurrent callbacks at limit−1 both pass.

#### Why the original rejection does not survive

The 2026-08-19 text rejected sharing on two grounds. Re-examined, the first was a mechanism constraint mistaken for a security property, and the second assumed a weaker flow than the one that shipped.

1. _"`WorkspaceForInstallation` must stay a function (ADR057 round-6 #9 fail-closed)."_ — This is a statement about a Go signature, not an invariant. What round-6 #9 actually requires is that an app-signed delivery **never widens to workspaces that have not been proved**, and that an unresolvable installation act on **nothing** rather than fall back to a global match. A function returning one workspace satisfies that; so does a function returning the proved binding set, provided the empty set still means act-on-nothing. §4a restates the invariant in the form that carries the requirement rather than the arity.
2. _"Cross-workspace sharing would let one workspace's admin grant another workspace's repos by side effect."_ — This is only true if a binding can happen **without** proof. It cannot. Every binding, on both the install and the claim path, requires the full three-proof sequence ([ADR026 §4](ADR026-github-integration.md), w1/m67 F3): a signed nonce-only state naming a server-side single-use transaction, the initiating bex subject matching at callback, a fresh `can_manage` on the target workspace, and an OAuth proof that the human at the browser **administers the exact installation being bound**. Two workspaces holding the same installation therefore means the same GitHub administrator asserted it twice, deliberately, once per workspace. There is no side effect: workspace A's admin gains nothing in workspace B, and cannot bind anything in a workspace where they lack `can_manage`.

What the original text was protecting against is the **unproved** attach — auto-binding from the `installation` webhook, or binding off a `missing_state` callback. Both remain rejected (§3, Alternatives), and w1/m65 F2's protection is preserved in the form that matters: an installation is attached to a workspace only by someone who proved, at that moment, that they administer both.

The residual risk N:N does change is **proof staleness**, and it is a multiplier rather than a new class: an admin who was an org owner at bind time and is later demoted leaves a live binding behind. That is already true at N=1; N:N makes it true N times. It is accepted here for the same reason it was accepted there — the binding is admin-visible and one `DELETE /v1/git/connections/{installationId}` away — and a periodic re-proof or binding TTL is recorded as future work rather than pretended away.

#### Rollback is a one-way door once a second binding exists

The migration is safe to apply ahead of the binary, but the reverse is not symmetric. A pre-revision binary reads `GitConnectionByInstallation` as a single-row query; with two rows for one installation it fails or returns an arbitrary workspace. The down migration therefore **refuses** — `RAISE EXCEPTION`, in the style `0091_git_connections_multi.down.sql` already uses — while any installation is bound to more than one workspace, naming them so the operator can disconnect the extras first. Reverting is an operational procedure, not a rollback; that is recorded here because it must not be rediscovered during an incident.

### 3. The connect flow is unchanged; every entry point must use it

The three-proof, one-principal connect flow ([ADR026 §4](ADR026-github-integration.md): signed nonce-only state + server-side single-use transaction + initiator-subject match + OAuth installation-admin proof + fresh `can_manage` at callback) is untouched — it is the security core of this feature. It covers **first installs**: GitHub carries `state` through `installations/new` when the target account does not yet have the app. ~~It also covers "the app is installed, bind it"~~ — **corrected 2026-08-20**: for an already-installed account GitHub strips the `state` (Configure links go to `github.com/settings/installations/<id>`), so the install URL can never bind one; that case is §3a's claim flow.

What changes is that **every Connect CTA goes through a bindable flow**:

- The `services/new` source picker's "Connect GitHub" button switches from the `gitConnection` query's bare `installUrl` to the `connectGit` **mutation** (StartConnect → stateful URL), exactly like the Settings card. The bare install URL **stops being advertised**: `GetConnection`/`gitConnection` drop `installUrl` from the not-connected view (the field stays for connected rows as a "configure repo grants on GitHub" deep link, where statelessness is fine because configuration edits don't bind anything).
- Direct GitHub-side installs remain a **no-op for binding** (auto-bind from the `installation` webhook is rejected again — the webhook proves the installation exists, not that any bex principal may attach it to any workspace). The `missing_state` recovery affordance points at the **claim flow** (§3a), which is the path that actually completes for an already-present installation — not at the install URL, which GitHub would strip the state from again.

### 3a. Claiming an already-installed installation — the OAuth-authorize flow (2026-08-20 revision)

An installation that already exists on GitHub (the direct-install case, and any account the app was ever installed on) cannot be bound through the install URL — GitHub drops the `state`. The **claim flow** binds it through the one GitHub flow that always preserves `state`, OAuth user authorization, while keeping all three proofs:

1. **Start:** a new admin-only verb (`claimGit` / `POST /v1/git/claim`) mints the same server-side single-use transaction (`github_connect_transactions`: nonce + workspace + initiating subject, 15-min TTL) and returns a **claim URL**: `github.com/login/oauth/authorize?client_id=<app client id>&state=<signed nonce-only state>`. Refused up front when the OAuth verifier is unconfigured (§7). Since 2026-09-16 it accepts an **optional `installationId`**, recorded on the transaction row and used to disambiguate at step 3 — see "The claim selector is not optional" below.
2. **Callback:** GitHub redirects to the existing `GET /v1/git/callback` with `code` + `state` and **no `installation_id`** — which is exactly how the callback distinguishes a claim from an install. It runs the same proof sequence: verify state → consume nonce → initiator == caller → fresh `can_manage`.
3. **Installation resolution replaces the missing query param:** the callback exchanges the single-use `code` for a user token and asks GitHub `GET /user/installations` — which lists only **this app's** installations the authorizing user can reach. Candidates are filtered to those the user **administers** (the same admin proof `VerifyInstallationAdmin` applies today: personal-account owner, or org membership `role=admin`). **Revised 2026-09-16:** the additional filter "and not already bound to any workspace" is **deleted** — being bound elsewhere no longer disqualifies an installation, because §2 permits N:N and this callback carries a full, independent proof. What remains is scoped to the transaction's own workspace: an installation already bound to **this** workspace stays a candidate and re-binding it is idempotent. When the transaction carries an `installationId` (step 1), candidates are narrowed to it, and an id the user does not administer is not a candidate — a client-supplied id can only ever **narrow** a server-proved set, never add to it. Exactly one candidate ⇒ bind it (same quota gates and `account_login` refresh as §2). Zero ⇒ bounded `no_claimable_installation`. Several ⇒ bounded `ambiguous_installation`, never a guess.

The three proofs are preserved and one is strengthened: the state/nonce transaction and initiator match are identical, and the admin proof is evaluated against the exact installation being bound — including when an `installationId` was supplied at start, since that id is used only to intersect the set GitHub and the admin check already proved. A claimed binding is indistinguishable in the store from an installed one.

#### The claim selector is not optional (2026-09-16)

Dropping the bound-elsewhere filter **enlarges the candidate set**, and the size of that set is exactly what `ambiguous_installation` trips on. Before this revision, an admin who administers several installations usually saw them filtered down to one because the others were already bound. After it, every installation they administer is a candidate, so ambiguity becomes the common case rather than the rare one — precisely for the multi-workspace users this revision exists to serve. Shipping N:N without the selector would replace one dead end (`no_claimable_installation` on an installation bound elsewhere) with another (`ambiguous_installation` with no way to choose), which is not a fix.

The selector is therefore in scope with the cardinality change. It cannot be a start-time parameter alone: **the dashboard does not know any installation id before the OAuth round trip** — the candidate set is only discoverable with the user token minted from the single-use `code` at step 3. So the mechanism is a **deferred selection**, with the start-time `installationId` as an optimisation for the case where an id is already in hand:

- On ambiguity the callback has already completed **every** proof for **every** candidate: state, nonce, initiator, fresh `can_manage`, and `VerifyInstallationAdmin` per installation. Rather than discard that work, it persists the proved set (`installation_id` + `account_login`) as a `github_claim_selections` row keyed by a fresh single-use selection nonce, carrying the transaction's workspace and initiating subject, with a short TTL (5 min), and redirects to the dashboard with the selection id as `git_claim_selection` — deliberately **not** on the `git_error` channel the dashboard renders as a failure alert, because this is a success continuation.
- The dashboard renders an account picker from `GET /v1/git/claim/selections/{id}` and completes with `selectGitClaim(selectionId, installationId)`, which consumes the row atomically (`DELETE … RETURNING`, so a replay finds nothing) and binds **only** an installation drawn from the stored set. Both verbs carry `ownerId` and are **admin-gated on that workspace** exactly like `connectGit`/`claimGit` — so `can_manage` is re-evaluated at selection time (a demotion inside the window must not still bind) and the denial is audited through the ordinary authorize seam. On top of that gate the selection's own workspace must equal the authorized one and its subject must equal the caller.
- **This grants no authority the callback had not already proved.** The selection row is a memo of a completed proof, not a substitute for one: it is subject-bound, workspace-bound, single-use, short-lived, and closed — an `installationId` outside the stored set is refused, so the client can choose among proved options but can never introduce a new one. The OAuth `code` is not stored or replayed. Unknown, expired, already-consumed, foreign-subject and foreign-workspace selections all fail identically, so a selection id cannot be probed.
- The row is **subject-bearing state**, so it joins the [ADR086](ADR086-account-deletion.md) cleanup inventory in the same class as the connect transaction: deleted on account deletion, never anonymized — an orphaned selection must not remain completable.
- Expiry or an unknown/consumed selection id fails closed to the ordinary `ambiguous_installation` message, whose remedy becomes "start the claim again", never "temporarily uninstall the extras".

### 4. Consumption resolves by repo owner within the workspace's connection set

Every consumer that today does `GetGitConnection(workspace)` moves to owner-scoped resolution against the workspace's set:

- **`ListRepos`** aggregates across all of the workspace's connections — one fresh installation token per connection, fetched concurrently, each repo annotated with its `accountLogin`/`installationId` so the picker can group by account (Render-parity UX: personal + org repos in one list). Fan-out is bounded by the §2 quota.
- **`ListBranches`, deploy-time clone-token mint, blueprint fetch, commit resolution:** parse `owner` from the repo URL via the existing structural `githubOwnerRepo` gate (unchanged — w1/m65 F1), then select the workspace connection whose `account_login == owner`; no match ⇒ exactly today's no-connection behavior (public fetch or clear failure, never a wrong-installation token). `RepoAccessible` stays as the post-mint grant check.
- **Push webhook:** `WorkspaceForInstallation` becomes `WorkspacesForInstallation`, returning the delivery's **proved binding set** — see §4a.
- **Agent-session token mint:** the owner-equals-`account_login` guard becomes owner-in-connection-set (still exact-match, still one repository, still `contents:write` least privilege). Unchanged by N:N: the mint starts from a caller-authorized workspace and looks **outward** to that workspace's connections, so a second workspace binding the same installation gains nothing it had not separately proved.

**Direction matters, and it is what keeps the blast radius small.** Only the push webhook resolves `installation → workspace`; every other consumer resolves `workspace → connections`. The deploy-time clone-token mint in particular reads the workspace from the App CR's `bex.co/tenant` label and then matches by repo owner ([ADR026 §6](ADR026-github-integration.md)) — the opposite direction — so it is unaffected by this revision. The reverse lookup has exactly one call site, which is the whole of §4a.

### 4a. The push webhook's fail-closed invariant, restated for fan-out (2026-09-16)

`GitWebhook.scopeFor` returns `scopes []string` instead of `scope string`, and each accepted delivery is matched once per scope. The invariant [ADR057](ADR057-security-review-round6.md) round-6 #9 established is **preserved in substance and restated in a form that does not depend on arity**:

- An app-signed delivery may reach **only** workspaces that hold a proved binding for the delivering installation — never a workspace that has not bound it, and never a global scan.
- **Empty means act on nothing.** An unknown installation, an unbound one, a missing installation id, a resolver that is unwired, or a lookup error all yield an empty scope set, which must not degrade into the manual key's deliberately global scope. This is the original codex #7 / round-6 #9 requirement verbatim; N:N changes how many non-empty scopes there can be, not what an empty one means.
- The manual `BEX_WEBHOOK_SECRET` key keeps its existing global behaviour and is still rejected outright in multitenant operation at verify time. Fan-out applies to the GitHub App key only.
- **Replay de-duplication is already per-scope** (`replayClaim`'s claim key includes the scope), so N scopes take N independent claims: one workspace's processing cannot swallow another's delivery, and a redelivery is still refused per workspace.
- Fan-out width is bounded by `BEX_MAX_WORKSPACES_PER_GIT_INSTALLATION` (§2), so a single push cannot fan into an unbounded number of tenants.
- The resulting behaviour is the intended one: a push to a repo tracked by services in two workspaces that both bound the installation deploys in both. Each of those workspaces had an administrator of that installation prove the binding, so this is the outcome they asked for, not leakage.

Because this changes a security invariant rather than a feature, it lands as its own reviewable commit with its own tests — a one-shot change is not an excuse for an unreviewable diff.

### 5. Surfaces

- **REST:** `GET /v1/git/connections` (list), `DELETE /v1/git/connections/{installationId}` (admin-only, per-connection disconnect). The singular `GET`/`DELETE /v1/git/connection` remain as compatibility aliases over the first/only connection and are documented deprecated (this whole surface is a bex extension, so the deprecation is ours to schedule).
- **GraphQL:** `gitConnections: [GitConnection!]!` alongside the existing singular (deprecated directive); `disconnectGit(installationId)` gains the argument (omitted ⇒ sole connection, error when ambiguous).
- **MCP:** `get_git_connection` → `list_git_connections`; `list_repos` returns the aggregated, account-annotated list.
- **Dashboard:** the Settings card lists all connections with per-row disconnect + "Connect another account"; the `services/new` picker groups repos by account and uses the stateful connect (§3). The claim flow (§3a) adds `claimGit` (GraphQL) / `POST /v1/git/claim` (REST) returning `{claimUrl}`, surfaced wherever the recovery affordance appears.
- **Claim selection (2026-09-16, §3a):** `claimGit`/`POST /v1/git/claim` take an optional `installationId`; the deferred picker adds an authenticated `GET /v1/git/claim/selections/{id}` read and a `selectGitClaim(selectionId, installationId)` mutation (REST: `POST /v1/git/claim/selections/{id}`), with the dashboard account picker rendered from it. Both stay **absent from MCP** for the reason connect and claim already are: they are halves of a browser ceremony an agent cannot complete.

### 6. Every dashboard GitHub surface is workspace-scoped (2026-08-20 revision)

The git feature's hooks pass `ownerId: currentWorkspaceId` — the same pattern `use-services`/`use-databases` already follow — on **every** operation: `gitConnections`/`gitConnection`, `repos`, `repoBranches`, `connectGit`, `claimGit`, `disconnectGit`. A null (still-resolving) workspace id defers the query rather than issuing an unscoped one, so no GitHub read or mutation can ever act on the caller's default workspace by accident. This is a correctness requirement, not polish: with the switcher on workspace B, an unscoped `connectGit` binds the installation to workspace A — a wrong-tenant write performed with the user's own authority.

### 7. Fail at start, not at the callback (2026-08-20 revision)

`StartConnect` and the claim verb refuse **up front** (bounded, actionable error) when the installation-admin verifier is unconfigured (`BEX_GITHUB_APP_CLIENT_ID`/`_SECRET` unset), instead of minting an install URL whose callback is guaranteed to 503 after the user walks the whole GitHub flow. bex-api additionally logs a startup warning when the GitHub App is configured but the verifier is not — the half-configured state is a deployment mistake (production ran in it undetected: the Secret simply lacked the two keys, and `optional: true` env refs made it silent), never a meaningful configuration.

## Alternatives considered

- **Adopt Render's user-bound credentials wholesale** — rejected. It imports Render's documented member-departure failure mode and per-service credential pointer, and it breaks every headless consumer (webhook routing, agent mint, blueprint sync) that must resolve a workspace without a user present. Render's shape is a consequence of Render's history (login OAuth first, App later), not a design to copy.
- **Hybrid: workspace connections + per-user connections merged in the picker** — rejected for now. It doubles the credential model (two ownership classes, two revocation stories, precedence rules) to serve one marginal case — a member who wants to deploy from repos the workspace admins have not connected — which is arguably a feature, not a gap: workspace admins _should_ control the deployable repo universe.
- ~~**Share one installation across workspaces (drop one-workspace-per-installation)** — rejected. Webhook scoping stops being a function, w1/m65 F2's cross-tenant attach protection erodes, and the legitimate need ("my personal account serves my two workspaces") is better served by GitHub's own model — install the App per-org, or accept the 1-workspace bind for a personal account.~~ — **reversed 2026-09-16, now §2.** All three clauses were wrong. "Stops being a function" describes a Go signature, not the fail-closed property (§4a restates the property without the arity). The attach protection does not erode, because every binding still carries the full three-proof sequence — what F2 guards is the **unproved** attach, which stays rejected. And "install the App per-org" is not available to the case that actually occurs: GitHub permits exactly one installation of an App per account, so a **personal** account genuinely cannot be split across two workspaces by any GitHub-side means. The suggested fallback — "accept the 1-workspace bind" — was the dead end users hit.
- **Per-connection repo allowlist chosen at bind time** — deferred, not rejected (§1). It would let an admin bind an account while exposing only chosen repos to that workspace, covering the one thing per-user credentials buy that N:N does not, and neither Render nor bex has it. Out of scope here because nothing in the N:N model blocks adding it later, and no demonstrated need has arrived; file it as its own milestone if one does.
- **Periodic re-proof or a TTL on bindings** — deferred (§2, proof staleness). N:N multiplies an accepted N=1 risk rather than introducing a new one, and the mitigation is orthogonal to cardinality.
- **Auto-bind on the `installation` webhook** — rejected again, as in ADR026: the webhook proves existence, not authority. Binding without the three proofs reopens the exact cross-tenant installation-attach the transaction flow closed (w1/m67 F3).
- **Keep 1:1 and just fix the dashboard CTAs** — rejected as insufficient: it fixes the trap but leaves the incident's real want (org **and** personal repos in one workspace) impossible, and leaves us inconsistent with Render on the one dimension where Render's UX is strictly better.
- **Uninstall + reinstall as the already-installed answer** (instead of §3a's claim flow) — rejected as the product answer: it works (a fresh install carries `state`) and remains the documented manual fallback, but it destroys the installation's repo grants, requires GitHub-side admin action for what is a bex-side binding, and cannot be offered as a button. Render never hits this case because its user-bound OAuth model reads installations instead of binding them; the claim flow is the workspace-bound model's equivalent affordance.
- **Auto-bind the sole claimable installation at `missing_state` time** (skip the explicit claim round trip) — rejected: the `missing_state` callback arrives with no usable proof (its nonce was never minted, or was consumed), so binding anything from it would bypass the transaction flow entirely — exactly the w1/m67 F3 hole again.

## Consequences

- The incident's desired end state becomes real: one workspace connected to both the `bex-co` org installation and the `puncsky` personal installation, both accounts' repos in one picker, each deploy minting a token from the right installation.
- The migration is a key swap on a table whose production contents are one row; no data movement, no dual-read window, no runbook — deliberately unlike [ADR074](ADR074-workspace-scoped-artifact-identity.md)'s identity migration. The 2026-09-16 N:N key swap has the same shape and one extra property: it only **relaxes** a constraint, so it is forward-compatible with the running binary and may land ahead of it.
- **Reverting N:N is an operational procedure, not a rollback** (§2): once any installation serves two workspaces, the pre-revision binary's single-row `GitConnectionByInstallation` is unsafe, and the down migration refuses until the extra bindings are disconnected. Deploy ordering is migration-then-binary; un-deploy ordering is disconnect-then-binary-then-migration.
- **The one behaviour that made users conclude "GitHub connect is broken" disappears.** Every path that previously dead-ended for an already-bound account now completes: the same GitHub account serves as many workspaces as its administrators bind it to, which is the Render-observable outcome (Render reaches it by never binding; bex by proving each binding).
- **A push can now deploy in more than one workspace.** This is intended and bounded (§4a), but it is a genuine behaviour change for anyone who binds an installation twice, and it is the thing to check first if a workspace reports an unexpected deploy.
- Every security invariant of ADR026 and the review lineage is preserved by construction: the three-proof connect, fresh `can_manage` at callback (ADR073 #3), unique installation→workspace (w1/m65 F2), fail-closed multitenant webhook scoping (ADR057), structural repo-origin gating before any mint (w1/m65 F1), token least-privilege and narrowing (ADR047/ADR056 F14 unchanged). New attack surface is limited to the connection **count**, which the quota bounds.
- `ListRepos` latency grows with connection count (one GitHub round trip per connection, concurrent); acceptable under the default cap of 10 and pageable per account if it ever isn't.
- The bare install URL disappearing from the disconnected view is a small API-shape change to a bex-extension surface; the dashboard is its only known consumer.
- Render-parity ledger and [docs/ADR018](ADR018-render-parity.md) gain the recorded divergence: bex is **workspace-bound by design** (superset UX: multi-account picker; subset: no per-member credentials).
- **Remaining Render granularity bex lacks — per-service source swap.** Render (May 2026) lets a service's backing repo be changed, or the service switched from repo-backed to Docker-image-backed, from Settings → Update Source. That is service-configuration granularity, not access granularity — nothing in this ADR's connection model blocks it — and it is deliberately out of scope here; file it as its own milestone if wanted. Every _access_ granularity Render exposes (user, installation, service-credential, repo-grant) now has a bex answer per the mapping table above.

## Verification

1. **Multi-connection connect** — with an org installation already bound: Settings → Connect another account → GitHub account picker → choose a personal account → callback binds a **second** row; `GET /v1/git/connections` lists both; `services/new` shows both accounts' repos grouped; creating a service from each account clones with that account's installation token (assert distinct `installation_id` in the mint audit).
2. **Cardinality + both quotas (revised 2026-09-16)** — connecting an installation already bound to **another** workspace now **succeeds**, given its own full proof sequence, and both workspaces list it; re-binding it to a workspace that already holds it is idempotent (one row, no duplicate). A caller without `can_manage` on the target workspace is still refused, and a callback whose OAuth user does not administer the installation still binds nothing. The N+1th connection over `BEX_MAX_GIT_CONNECTIONS_PER_WORKSPACE` returns `GIT_CONNECTION_LIMIT`, and the N+1th **workspace** for one installation returns `GIT_INSTALLATION_WORKSPACE_LIMIT`, on REST, GraphQL, and MCP identically.
3. **Entry-point consistency** — the `services/new` connect button round-trips GitHub and binds successfully for a **first install** (no `missing_state`); an already-present installation binds through the **claim flow** (§3a) without re-installing — verified live: the claim URL round-trips GitHub OAuth, the callback resolves the sole claimable installation, and the binding lands in the transaction's workspace.
4. **Owner-scoped consumption** — with two connections, a push webhook from each installation redeploys only its own workspace's matching Apps; agent-session mint refuses a repo whose owner matches **no** workspace connection; deploy of a repo from account B never receives account A's token (assert in the clone-secret refresh path).
5. **Compatibility** — a workspace with exactly one connection sees byte-identical behavior on the singular REST/GraphQL surfaces; the migration up/down round-trips the current production row unchanged.
6. **Workspace scoping (§6)** — with workspace B selected in the dashboard, the Settings GitHub card, the repo picker, and connect/claim/disconnect all read and write **B's** connection set (assert the request carries B's `ownerId`); switching workspaces refetches.
7. **Fail-at-start (§7)** — with the OAuth verifier unconfigured, `connectGit`/`claimGit` return an actionable error immediately (no install URL is minted), and bex-api logs the half-configured warning at startup.
8. **Shared-installation fan-out (§4a, 2026-09-16)** — with one installation bound to workspaces A and B, each running a service tracking the same repo+branch: one `git push` produces **one deploy in each**, with independent replay claims (a redelivery is refused in both). Disconnecting B leaves A's deploy working and B receiving nothing. An installation bound to **no** workspace, a delivery with no installation id, and an unwired resolver each act on **nothing** in multitenant operation — never a global match.
9. **Claim selection (§3a, 2026-09-16)** — an admin who administers two installations starts a claim, authorizes on GitHub, and lands on a dashboard **account picker** rather than `ambiguous_installation`; choosing one binds it, and the selection id is then spent (replay binds nothing). A `selectGitClaim` naming an installation outside the stored set is refused, as is one presented by a different subject or after the 5-minute TTL. Supplying `installationId` at start skips the picker and binds directly; an id the OAuth user does not administer binds nothing.
10. **Rollback guard (§2)** — the down migration succeeds while every installation serves one workspace, and **refuses with a named exception** once any serves two; disconnecting the extras lets it proceed.
