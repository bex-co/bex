# ADR112 — bex object storage: Render's `ea objects` contract and an S3-compatible API over Wasabi

**Status:** proposed (2026-11-14); amended 2026-11-19: the Cloudflare-shaped contract that `wrangler r2` calls ("Contract B") is replaced by an S3-compatible API and a `bex s3` command. Filed 2026-11-15 as [w21/m415](../.pm/w21/done/m415/README.md), [m416](../.pm/w21/done/m416/README.md) and [m417](../.pm/w21/done/m417/README.md), all done; the S3 amendment is filed as [w21/m498](../.pm/w21/done/m498/README.md) (the S3 core, on production and walked there on 2026-11-19), [m499](../.pm/w21/done/m499/README.md) (`bex s3`, the contract suite and the docs) and [m500](../.pm/w21/m500/README.md) (the full production walk, then Contract B's removal) (§ Tasks).

**Implemented 2026-11-15, amended 2026-11-19.** Contract A (Render's four routes), the store, the sweep and public buckets (objectgw) are on production and were walked there (Contract A on 2026-11-15, public buckets on 2026-11-16, § Not verified). Contract B, the Cloudflare-shaped routes, shipped with them on 2026-11-15 (w21/m416) and is **removed by this amendment**: its code stays until the S3 API replaces it on production (D3, the Removal of Contract B bullet), and nothing below describes it as a design. Where the code differs from the text below, § D3, § D4 and § Not verified say so with the date.

**Source:** user request 2026-11-14: an ADR to support Render's early-access object store with Wasabi S3, then the goal restated as "rw cli contract + wasabi wrapper": serve the contract of Render's CLI and a second, Cloudflare-shaped one, each as a thin layer over one Wasabi-backed store. **Amended by the user on 2026-11-19:** after a review of what `wrangler r2` can do (no object listing, three object commands, 300 MiB, the bytes inside the REST call), the user chose the S3 protocol instead, with bex verifying SigV4 itself and keeping the bytes behind its own gateway ("option A" of D3's two designs, so that quota, metering and audit stay in one place), and asked for this ADR to be rewritten with the R2 CLI approach removed entirely, so that the customer's command is `bex s3 <…>`.

**Rewritten 2026-11-14 and 2026-11-19.** The first version served only Render's four routes; it had no bucket, no public access, no CORS and no lifecycle, so the second version added `wrangler r2`'s contract. This version drops that contract for the S3 protocol, which every object-storage client already speaks and which lists, copies, syncs and uploads in parts, none of which `wrangler r2 object` does.

**Amended 2026-11-19 (this version).** D3 is now the S3 API (SigV4 verified by bex, bytes streamed through `bex-s3`, a Deployment of its own, access keys held in OpenBao) and the `bex s3` command; D4's public toggle is `bex s3 public`, not an S3 call; D6, D7, D8 and D9 follow; D10 and D11 are rewritten; Contract B and everything that served it are removed once the S3 API is on production (D3's Removal of Contract B bullet, § Tasks).

**Amended 2026-11-15 (w21/m417 t001, D4 and D9).** objectgw authenticates to bex-api with one more credential, `BEX_OBJECT_STORAGE_GATEWAY_TOKEN`, a static bearer on bex-api's cluster-internal listener, and reports its bytes through the same listener. It is the fifth credential variable and still no configuration: endpoints, ports, the bex-api URL and every cap stay constants. A service named like a bucket host keeps its name and takes a suffixed slug, instead of the bare `pub-` prefix being refused (parity: Render refuses no service name for its host).

**Amended 2026-11-15.** Tenant data shares the platform's existing Wasabi account instead of a dedicated one (user decision, D1), so there is no second account to create and no new root credential. D9 now names the identities and the four credential variables, and fixes the rule that environment variables carry credentials only: endpoints, buckets, regions and caps are code constants, and the objectgw kill switch is a scale to zero (D4).

**Amended 2026-11-16 (w21/095, D4, D5 and D8).** Wasabi counts what a LIST reads as egress (its documentation says so; D8 has the quotes), so the hourly sweep's listings are part of the shared account's fair-use ratio. A region is now listed again only after a gap that grows with the objects it held (one hour per 100, at most 72), the sweep's estimated listing bytes are a metric with an alert, and the egress alert's notes name the sweep as the part of the ratio its meter does not hold. How many bytes Wasabi counts for a listing could not be measured: the account's own counter did not hold the test's requests (D8, read 2026-11-19), so the rule and the budget stand as shipped, on the safe side.

**Amended 2026-11-16 (w21/096, D8).** The sweep's own health is watched: `ObjectStorageSweepStale` warns when no pass has completed in three hours and `ObjectStorageSweepCutOff` when the 50-minute pass is cut off twice in three hours, with three panels on the Billing and metering dashboard and a runbook ([runbooks/object-storage-sweep.md](runbooks/object-storage-sweep.md)) that names the first log line to read and what raises `sweepWorkers`. Every replica now exports each of the sweep's series at zero, so `increase()` counts a pod's first cut-off.

### Contract A: what the pinned Render CLI and the SDKs enforce

The sources are `render-oss/cli@v1.1.3-0.20261106232710-4fd34231b637` (`pkg/storage/repo.go`, `pkg/client/storage/storage_gen.go`, `cmd/object*.go`) and the Python and TypeScript object clients in `render-oss/sdk`. All call the same four routes:

| Route | Request | Response |
| --- | --- | --- |
| `GET /v1/objects/{ownerId}/{region}` | `cursor`, `limit` | `{items:[{cursor, object:{key, sizeBytes, lastModified}}], hasNext, nextCursor?}` |
| `PUT /v1/objects/{ownerId}/{region}/{key}` | `{sizeBytes}` | `{url, expiresAt, maxSizeBytes}` |
| `GET /v1/objects/{ownerId}/{region}/{key}` | none | `{url, expiresAt}`; the CLI maps 404 to "object not found" |
| `DELETE /v1/objects/{ownerId}/{region}/{key}` | none | 200 or 204; the CLI maps 404 to "object not found" |

- **There is no bucket in the contract.** `ownerId` is the workspace id (`tea-…`) and `--region` is mandatory, so a tenant sees one namespace per workspace per region.
- The client PUTs or GETs the returned URL itself. A zero-byte upload sends `http.NoBody`, because "presigned S3 URLs do not support chunked encoding" (`repo.go`).
- **`maxSizeBytes` equals the requested `sizeBytes`.** Both SDKs refuse an upload whose size differs from the response's `maxSizeBytes`, so the URL signs that exact length. They send the caller's `Content-Type` and `Content-Length`, read the response's `ETag`, and on a GET read `size` and `content-type`.
- `ea objects list` reads the first page only, with `--limit` defaulting to 100; its help example uses `--limit=200`. Python's `list` docstring gives a default of 20. The generated `Region` type lists `frankfurt`, `ohio`, `oregon`, `singapore`, `virginia`.

### The S3 protocol: what clients send and what bex serves

S3 is the contract that aws-cli, rclone, boto3, the AWS SDKs, s5cmd and Terraform's AWS provider all speak, and the only one that gives a customer listing, copy, sync and uploads in parts. The AWS CLI facts below were read on 2026-11-19 from docs.aws.amazon.com/cli (`cli-configure-envvars`, `topic/s3-config`). The wire facts about streaming payloads are from memory of AWS's SigV4 documentation, which I could not read page for page on 2026-11-19, so D11's known-answer tests are what pin them, not this text.

| Group | S3 operations bex serves (v1) |
| --- | --- |
| Buckets | `ListBuckets`, `CreateBucket`, `HeadBucket`, `DeleteBucket`, `GetBucketLocation` |
| Objects | `PutObject`, `GetObject` (with `Range` and the conditional headers), `HeadObject`, `DeleteObject`, `DeleteObjects`, `CopyObject` (one workspace, one region, up to 5 GiB), `GetObjectTagging` (always an empty set) |
| Listing | `ListObjectsV2`, `ListObjects` |
| Multipart | `CreateMultipartUpload`, `UploadPart`, `UploadPartCopy`, `CompleteMultipartUpload`, `AbortMultipartUpload`, `ListParts`, `ListMultipartUploads` |
| Bucket configuration | `Get/Put/DeleteBucketCors`, `Get/Put/DeleteBucketLifecycleConfiguration` |
| Everything else | 501 `NotImplemented`: versioning, ACLs, bucket policies (publishing is `bex s3 public`, D4), tag writes, object lock, encryption, replication, notifications, website, accelerate, select, SigV2, and any header or subresource bex does not implement (D3) |

Facts that shape the design:

- **What `aws s3` does by default (read 2026-11-19).** `multipart_threshold` and `multipart_chunksize` are 8 MB (a part is at least 5 MB), `max_concurrent_requests` is 10, and `addressing_style` is `auto`: virtual-hosted where possible, path style as the fallback. Request payload checksums are calculated by default (`AWS_REQUEST_CHECKSUM_CALCULATION` is `when_supported`), and a streaming upload over HTTPS is sent with an unsigned payload (`payload_signing_enabled`). So a stock `aws s3 cp` of a file over 8 MB is a multipart upload with up to ten requests in flight, a smaller one is a single `PutObject` that carries a checksum, and a server without multipart cannot serve the commonest command.
- **Which addressing style `auto` picks for a custom endpoint is not settled by those pages.** A virtual-hosted request goes to `<bucket>.objects.onbex.co`, which has two labels under the base domain and so is covered by no certificate or route (D3). bex serves path style only, and `bex s3` sets it explicitly; the production walk reads what each stock client does without help (§ Not verified).
- **Endpoint and credentials by environment.** The CLI reads `AWS_ENDPOINT_URL_<SERVICE>` (so `AWS_ENDPOINT_URL_S3`), `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE`, and an environment variable overrides the same setting from a profile. That is all `bex s3` has to set (D3).
- **SigV4 payload modes** a client may send in `x-amz-content-sha256`: `UNSIGNED-PAYLOAD`; the body's hex SHA-256; `STREAMING-UNSIGNED-PAYLOAD-TRAILER` (`Content-Encoding: aws-chunked`, `x-amz-decoded-content-length`, `x-amz-trailer`, chunks of `<hex size>\r\n<data>\r\n`, a final `0\r\n` and the trailing checksum header); and `STREAMING-AWS4-HMAC-SHA256-PAYLOAD`, with or without `-TRAILER`, whose chunks each carry a chained signature. bex serves the first three. The signed-chunk modes answer 501 (D10): over HTTPS the CLI and the current SDKs send the unsigned ones.
- **Errors are XML**, `<Error><Code/><Message/><Resource/><RequestId/></Error>` with an `x-amz-request-id` header, and clients retry on 5xx and on `SlowDown` (503) but not on 4xx.

## Decision

### D1 — One store: virtual buckets over one shared Wasabi bucket per region

- **Layout.** A bucket per region on Wasabi, `bex-objects-<region>` (final names are settled at provisioning, since Wasabi bucket names are global). The object key is `<tea-id>/<obk-id>/<key>`, the prefix idea of [ADR074](ADR074-workspace-scoped-artifact-identity.md).
- **Buckets are rows.** `object_buckets(id, workspace_id, name, region, system, public, cors, lifecycle, created_at)` with `(workspace_id, name)` unique. `id` is a new typed id, `obk-<xid>`, minted through `internal/id` ([ADR020](ADR020-identifiers.md)). A name is 3 to 63 characters of lowercase letters, digits and hyphens that starts and ends with a letter or digit (`^[a-z0-9][a-z0-9-]{1,61}[a-z0-9]$`), a strict subset of S3's rule (S3 also allows dots, which break the certificate of a virtual-hosted name and which bex does not need), and never changes. **The Wasabi key embeds the id, not the name**, so a bucket that is deleted and recreated under the same name never sees the old objects. A bucket must be empty to be deleted, and no upload may land between the emptiness check and the row's removal (w4/678, 2026-11-15): the delete marks the row (`deleting_since`) and lists holding the row `FOR UPDATE`, a streamed put refuses a marked bucket before its first byte (409 `OperationAborted`), and a finished put confirms its row `FOR SHARE`, removing its object and answering 404 `NoSuchBucket` when the row is gone.
- **Why virtual.** Wasabi allows 1000 buckets per account by default, and a tenant never holds a Wasabi credential, so a physical bucket per customer bucket isolates nothing a key prefix does not.
- **Contract A's namespace is a system bucket.** Render's `{ownerId}/{region}` resolves to the workspace's bucket `render-<region>`, created on first use (`system = true`, outside the bucket cap, and the `render-` prefix is reserved). An object put with the Render CLI is therefore readable with any S3 client and the other way round, and `ListBuckets` lists `render-<region>` among the workspace's buckets. A system bucket cannot be deleted (403 `AccessDenied`, w4/678, 2026-11-15): Render has no way to delete the namespace, and a deleted one came back under a new id on the next Render call while a URL minted before the delete still uploaded under the old one, where nothing could list, read or delete the object.
- **Regions at launch.** `CreateBucket`'s `LocationConstraint` takes `oregon`, `us-west-1` or `us-west-2` for Oregon and `frankfurt`, `eu-central-1` or `eu-central-2` for Frankfurt; an absent one goes to `oregon`, a constant (D9). Any other value, and Render's other regions (`ohio`, `virginia`, `singapore`), answers 400 `InvalidLocationConstraint`, recorded in ADR018 as a dated divergence. bex does not compare the signing region of a request with the bucket's: one endpoint serves both regions, the bucket's row decides, and `GetBucketLocation` answers the bex name.
- **Account (user decision 2026-11-15: shared).** Tenant data goes on the platform's existing Wasabi account, the one that holds `bex-tfstate` and every backup and drilled restore path ([ADR031](ADR031-platform-data-backup.md), `.pm/FUTURE-MAYBE.md:23`), in buckets and under IAM users of its own (D9). The first draft used a separate account so that a Wasabi limit could not reach the backups; sharing gives that up. Wasabi may limit a service whose egress regularly exceeds its storage, public buckets (D4) make that likelier, and I assume Wasabi would act on the account, not on one bucket (unverified). What sharing saves is a second 1 TB minimum, about $8 a month at today's page, and a second root credential to guard. The first response to a Wasabi warning is objectgw's kill switch (D4); the second is moving tenant data to a separate account, which changes only the values in D9, not the code, and must not block D2 or D3.
- **Posture.** Private, no versioning (it would double the Wasabi bill), no CORS and no ACLs at Wasabi; CORS and public access are bex's (D4). Encryption at rest is Wasabi's automatic AES-256.

### D2 — Contract A: the four Render routes, served as the pinned CLI and SDKs call them

Remove the four entries from `notOfferedRefusals` and the `objectStorageNotOffered` constant. Add `lego/backend/internal/objectstorage`, a core service with the REST handlers as a thin adapter ([ADR006](ADR006-bex-api.md)). Errors keep Render's shape.

- **list.** The service reads Wasabi directly over `<tea-id>/<obk-id of render-region>/`, with no database mirror. `limit` is honored up to 1000, the S3 page size; the CLI never follows `nextCursor`, and its own help example asks for 200, so capping at 100 would truncate silently. The cursor is the base64 of the last key, fed to `StartAfter`. The default is 20, from the Python docstring; Render's default and cap are unverified.
- **put.** Mint a presigned PUT that signs `Content-Length` equal to `sizeBytes`, so an upload cannot exceed what the quota gate reserved, and return `maxSizeBytes` equal to `sizeBytes`, which the SDKs require. Do not sign `Content-Type`: the request carries only `sizeBytes`, the client's header is stored as sent, and the SDKs read it back. The PUT response must expose the object's `ETag`. A size above the per-object cap is `413`.
- **get and delete.** `HeadObject` first, and a missing key answers `404`: S3's `DeleteObject` answers 204 for a missing key, while the CLI treats 404 as "object not found".
- **get URL.** Pin `response-content-disposition: attachment`, as [ADR095](ADR095-agent-attachments.md) D7 does for anything that is not a raster image, so a browser opening the URL does not render tenant HTML on Wasabi's origin. Do not pin `response-content-type`.
- **Metering.** The bytes bypass bex, so egress is a shadow estimate from the size `HeadObject` returns when a GET URL is minted: exact for a complete download, an upper bound for a ranged one.

### D3 — The S3-compatible API: SigV4 verified by bex, the bytes streamed through `bex-s3`, and `bex s3` as the command

bex serves the S3 REST API at `https://objects.<BEX_BASE_DOMAIN>` (`objects.onbex.co`), path style, from a Deployment of its own, so any S3 client works with an endpoint, an access key and its secret. The customer's command is `bex s3 <…>`, which runs the AWS CLI with those already set. Contract B (Cloudflare-shaped routes for `wrangler r2`) is not part of this design; the last bullet of this decision says what goes.

```sh
bex s3 mb s3://photos --region frankfurt
bex s3 cp cat.jpg s3://photos/cat.jpg
bex s3 ls s3://photos/
bex s3 sync ./site s3://photos/site
bex s3api put-bucket-cors --bucket photos --cors-configuration file://cors.json
```

- **Why bex terminates S3 (the user's choice, 2026-11-19).** The other design was one Wasabi IAM user per tenant, scoped to a prefix, with the client talking to Wasabi directly. That takes the quota gate (D8), the shadow meters, the audit rows (D6), the rate caps and the egress kill switch out of bex's path, on an account whose fair-use allowance measured 67 GB (D4), and it rests on Wasabi enforcing prefix-scoped policies, which was never verified. With bex in the path every byte is metered, every request is authorized against a workspace role, and a tenant never holds a Wasabi credential (D1, D9).
- **Where it runs: `bex-s3`, a Deployment of its own** (the bex-api image started with the S3 surface only, so it has the core service, Postgres, OpenFGA, OpenBao and the read-write Wasabi pair of D9), two replicas. A stream of up to 5 GiB for up to 30 minutes does not belong on the pods that serve REST, GraphQL and MCP: bex-api's limits are 200m CPU and 512Mi (`lego/operator/config/api/deployment.yaml`, where a comment records both replicas OOM-killed together once), its drain window is 15 seconds (`cmd/api/main.go`), and a rollout would cut every upload in flight. `bex-s3` sets `terminationGracePeriodSeconds` above the stream deadline (2,100 seconds), stops taking new requests on SIGTERM and lets its streams finish, and has resource limits sized by t109's measurement. It mounts no REST, GraphQL, MCP or OAuth route, so a bucket named `graphql`, `mcp` or `v1` cannot collide with one. objectgw stays separate: it holds no database credential.
- **Host and routing.** Two IngressRoutes serve `objects.<domain>`, both DNS-only to Traefik. The existing one (priority 10000, `PathPrefix(/cloudflare/client/v4/)`, to bex-api) stays until t111; a new one for the rest of the host, at a lower priority, sends everything to `bex-s3`. The new route ships with the S3 core, together with `scripts/gitops-validate.sh`, which today pins the old route's exact match (`:3322`) and must pin both, so t109 runs on the final route before Contract B goes and t111 only deletes the old one. While both exist, a key under `client/v4/` of a bucket named `cloudflare` would reach the old route, so the S3 surface refuses that bucket name until t111. The host is `objects.`, not `api.`, because `api.bex.co` is behind Cloudflare's proxy, which refuses a request body over 100 MiB with its own HTML `413` (measured 2026-11-15, § Not verified), and an S3 object goes to 5 GiB; `*.onbex.co` is DNS-only and resolves straight to Traefik. `objects` stays a reserved service slug (`publichost.APILabel`). The surface takes no cookie and no OAuth token, only SigV4, and has its own gate that writes S3's XML errors for everything that fails before a route runs. The host gives up Cloudflare's DDoS and WAF layer, as every other `*.onbex.co` host does, and Traefik cleans request paths by default, so `//` and dot segments are rewritten before bex sees them and would break a signature (D7 refuses those keys). An unauthenticated request must cost little: a key id is checked against the `s3k-<xid>` shape before any lookup, an unknown id is one database lookup whose miss is cached for 30 seconds in a bounded cache, a known key's secret is read from OpenBao at most once per 15 minutes on each replica whatever is sent, and failed authentications are rate-limited per client address (an IPv6 address by its /64; a constant, D8), after which the address's failing requests are refused from the in-memory caches alone. **Path style only:** `<bucket>.objects.onbex.co` has two labels under the base domain and the wildcard certificate covers one ([ADR093](ADR093-onbex-wildcard-tls.md)); D10 lists virtual-hosted style, which needs a second certificate name.
- **Access keys.** A row `object_access_keys(id, workspace_id, created_by, name, permission, created_at, expires_at, last_used_at, revoked_at)` with a typed id `s3k-<xid>` ([ADR020](ADR020-identifiers.md)); the id is the access key id. The secret, 40 random characters, is shown once at creation and kept in OpenBao through `core.SecretKV` at `object-storage/keys/<id>` ([ADR013](ADR013-secrets.md)), because SigV4 needs the secret itself to verify a request and an API key's hash would not do (registry credentials are kept the same way). `permission` is `read` or `readwrite`.
  - **Authorization: the creator's relation on one fixed object.** `core.Base` authorizes an S3 request as the key's creator on exactly `workspace:<key.workspace_id>`, never on anything the request names, with the key's `permission` as a ceiling: `read` is `can_view` and `can_view_sensitive` (list and get), `readwrite` adds `can_create` (put, copy, delete, multipart, bucket create and delete, CORS, lifecycle). **No key ever holds `can_manage`**, so a leaked key cannot publish a bucket (D4). [ADR024](ADR024-members.md) rules out evaluating a key's request as its creator because the creator's tuples reach other workspaces; here the object is fixed by the key's own row, so they cannot be reached. Demoting or removing the creator takes effect on the next request that misses the 30-second cache of key records and the 30-second OpenFGA read cache, as for people. The audit row names the key id as the actor, so the holder of a presigned URL is distinguishable from its creator.
  - **A key is disposed with the person's other keys.** S3 keys join the disposal of API keys when a member leaves a workspace (ADR024, w2/m163) and when an account is deleted ([ADR086](ADR086-account-deletion.md)), the workspace-enforced 2FA and sign-in gates that cover a member's API and SSH keys ([ADR012](ADR012-auth.md) § 9a), and the enumeration of `TestEveryMembershipEndingVerbDisposesKeys`; a disposal deletes the row and its OpenBao secret, and re-adding the creator does not revive it.
  - **Creating a key is a `mint`-class verb** ([ADR012](ADR012-auth.md) § 7, the scope-class table's `mint` row, with API-key create and SSH-key enroll): human only, `bex.write` and the mint class, so an API key cannot create one and a delegated third-party token cannot either. A key is **persistent** (no expiry, for CI, rclone and Terraform) or **ephemeral** (`expires_at` at most 12 hours, which is what `bex s3` mints). At most 100 live persistent keys per workspace and 20 live ephemeral keys per creator (`bex s3` reuses its cached key, so one person on a few machines stays under it). Revoked and expired keys, with their OpenBao secrets, are deleted after 7 days by the sweep. Per-bucket and per-prefix keys are D10.
  - **The secret store.** The secret is read and written at `object-storage/keys/<id>` under `secrets.WithTenant(ctx, row.workspace_id)`, because the store prepends the context's tenant and falls back to `default`. A secret never changes, so a replica caches it for 15 minutes; revocation travels with the 30-second cache of the row, which is read first. Create writes OpenBao first and rolls it back if the row fails; revoke marks the row first and deletes the secret after, and a row whose secret is missing (OpenBao restored from an older snapshot) is revoked and listed as broken. **An OpenBao error is 503 `ServiceUnavailable`, never 403**, because SDKs retry the one and not the other, and an alert watches it (t112).
  - REST `/v1/object-storage/{ownerId}/access-keys` (create, list, revoke) and `/v1/object-storage/{ownerId}/buckets/{bucket}` (a bucket's region, public host, objects and bytes from the last sweep, which S3 cannot answer) are bex-only routes, thin adapters of the core service with GraphQL beside them ([ADR006](ADR006-bex-api.md)). They are not in Render's OpenAPI, so [ADR018](ADR018-render-parity.md)'s strict request gate does not cover them, bex validates their input, and each gets a `REST <METHOD> <pattern>` entry in `classifiedOps` (`scope_matrix_ops.go`, regenerated by `GENERATE_SCOPE_MATRIX=1 go test ./internal/api -run TestGenerateScopeMatrix`).
- **Verification.** The `Authorization: AWS4-HMAC-SHA256` header and the presigned query form (at most 7 days) are verified over the canonical request with the key's secret. The region and service come from the credential scope as the client sent them (the service must be `s3`, the region is compared with nothing, D1), the clock may differ by 15 minutes (403 `RequestTimeTooSkewed`), signatures are compared in constant time, and an unknown, revoked or expired key answers 403 `InvalidAccessKeyId` and a wrong signature `SignatureDoesNotMatch`, so existence leaks no more than it does on S3. SigV2 answers 501.
  - **Every `x-amz-*` header and `host` must be in `SignedHeaders`**, in both forms, as S3 requires. A presigned URL is a bearer credential: an unsigned `x-amz-copy-source` added by its holder would otherwise copy any object of the workspace into a public key.
  - **The router matches subresource query parameters first** (`?tagging`, `?acl`, `?retention`, `?versioning`, `?policy`, `?uploads` and the rest). An unrecognised one, and a `POST /<bucket>` form upload, answers 501 before any object or bucket handler runs, so `PUT /b/k?tagging` can never overwrite an object and `DELETE /b/k?tagging` can never delete one.
  - **A header whose semantics bex does not implement answers 501 and is never ignored**: `If-None-Match` and `If-Match` on a put (Terraform's state lock uses one), `x-amz-tagging`, `x-amz-storage-class` other than `STANDARD`, `x-amz-server-side-encryption*` and a non-private `x-amz-acl`. The `x-amz-copy-source-if-*` conditions are not refused: a copy evaluates them (see Multipart upload).
  - **Payload modes.** `UNSIGNED-PAYLOAD`, an explicit SHA-256 and `STREAMING-UNSIGNED-PAYLOAD-TRAILER`. The trailer path, which the AWS CLI v2, boto3 and the Go, Java and JS SDKs take by default (read on 2026-11-19 in botocore's `httpchecksum.py` and AWS's SDK data-integrity page; the CLI's default algorithm is CRC64NVME and the others' is CRC32), sends `Transfer-Encoding: chunked` with no `Content-Length`, `x-amz-decoded-content-length` for the real size, `Content-Encoding: aws-chunked` and `x-amz-trailer`. So **the length of a body is `Content-Length`, or `x-amz-decoded-content-length` for `aws-chunked`, and 411 `MissingContentLength` is for neither**; the `aws-chunked` token is removed from the `Content-Encoding` that is stored (any other encoding stays); and the decoded length is the `Content-Length` of the Wasabi request.
  - **Integrity is verified before the commit.** bex verifies CRC32, CRC32C, CRC64NVME, SHA1 and SHA256 trailers, `Content-MD5` and an explicit SHA-256 (Go's `hash/crc64` has no NVMe polynomial, so t102 carries one with the published test vector), and answers 501 for any other `x-amz-trailer`, so integrity is never skipped silently. Puts and parts echo the `x-amz-checksum-*` they verified. bex **withholds the body's last byte from the Wasabi request until the digest or trailer verifies**; on a mismatch it ends the upstream request short of its signed `Content-Length`, which Wasabi refuses (§ Not verified, settled 2026-11-15), so nothing is stored, a previous object is untouched and the corrupt bytes are never readable. The answer is 400 `BadDigest` (`XAmzContentSHA256Mismatch` for an explicit SHA-256). The two signed-chunk modes answer 501 (D10). A `CompleteMultipartUpload` body that carries per-part checksums is rebuilt for Wasabi from `PartNumber` and `ETag` alone.
  - **Everything that can refuse runs before the body is read** (authentication, authorization, name and key validation, the quota gate and the stream slot), so a client that sent `Expect: 100-continue`, as `aws s3 cp` does, is refused before it sends a byte when the edge passes the expectation on. Traefik's transport gives `100-continue` a short timeout, so this is a saving and not a guarantee, and nothing in front of `bex-s3` may read the body.
- **Objects stream.** The handler extends the per-request read and write deadlines with `http.NewResponseController` (the 30 s server timeouts would otherwise cut a large upload), refuses above 5 GiB (400 `EntityTooLarge`), and streams to Wasabi on a server-signed presigned PUT that signs `content-length` and the `x-amz-meta-*` headers the request carried, so there is no spooling. `Content-Type`, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language`, `Expires` and `x-amz-meta-*` are stored as sent and returned by `GetObject` and `HeadObject` (rclone keeps an object's modification time in `x-amz-meta-mtime`, and without it every sync copies everything again). A put overwrites. Wasabi enforces the signed length and refuses a chunked body (§ Not verified, settled 2026-11-15), so the handler always passes a real length on. Every put or get is bounded to 30 minutes on the Wasabi side too, and an error from the Wasabi call never carries its URL, whose query is a signature valid for 15 minutes. **bex rebuilds every XML answer** (the `Location` and `Key` of a completed upload, `ListParts`, listings) and forwards no Wasabi body, so the physical key `<tea-id>/<obk-id>/…` never leaves; `CopyObject` and `CompleteMultipartUpload` can answer 200 with an `<Error>` body, which bex reads and turns into the error.
  - **A get opens the object once** (`GetObject` at Wasabi answers the headers and the body together, and `NoSuchKey` for a missing one) and streams it back with `Range`, `If-Match`, `If-None-Match`, `If-Modified-Since` and `If-Unmodified-Since` passed on, the stored headers, `ETag` and `Last-Modified`. It is served with `Content-Disposition: attachment` unless the object stored one, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox`, and is exempt from response compression: without them a browser that followed a link would run a tenant's HTML on bex's origin, which [ADR095](ADR095-agent-attachments.md) D7 forbids for attachments. A `Range` is checked against the size Wasabi reports and one past the end is 416 `InvalidRange`: Wasabi answered a presigned `Range` past the end with the whole object and a 200 (§ Not verified), so a resume at `bytes=<size>-` would otherwise download everything again. A `HEAD` is a Wasabi `HEAD`, holds no stream slot and meters nothing. A delete of a missing key succeeds, as on S3 (Render's route answers 404, D2).
  - **Concurrency, pacing and rates.** At most 16 streams per workspace on each replica (Contract B's cap was 8, sized for wrangler's one stream, and `aws s3 cp` runs 10 requests at a time), within the replica-wide cap of 64 (`MaxConcurrentStreamsPerReplica`, `limits.go`) and 100 open multipart uploads per workspace. A refusal is 503 `SlowDown`, which S3 clients retry, never 429. **Reads are paced, not charged as debt**: response bodies leave through a rate-limited writer at 8 MiB/s per workspace on each replica. D4's debt-and-429 scheme was built for anonymous readers and would fail the ten parallel 8 MiB ranges of a 1 GiB `aws s3 cp` against its 64 MiB burst, and 429 is not a throttle S3 clients retry. Uploads take 16 MiB/s per workspace on each replica, and requests are capped at 100 a second per workspace (burst 200) and 50 a second per access key. All are constants (D8).
  - **Egress is the exposure here too, and a rate does not bound a month.** An authenticated S3 download streams from the same shared Wasabi account, with its 67 GB allowance, as a public read does, and a workspace at the pacing above would use the whole allowance in about an hour. So **S3 reads are refused with 403 `QuotaExceeded` once the workspace's month-to-date egress passes the larger of the bytes it stores and 5 GiB** (Wasabi's own rule is egress at or below storage), a bex-owned constant like the others. Budgets and rates bound one workspace, not the sum: the sum is watched by the egress alerts (D4), which already read the meter that now holds the S3 bytes (D8), and stopped by the kill switch, which gains a second step: the `objects.` route is pointed at a static 503 in GitOps (t112 writes it into `docs/runbooks/objectgw-kill-switch.md` and `gitops-validate.sh`). Contract A's presigned reads and public reads keep their own bounds (D2, D4); a budget for them is D10.
  - **What watches it.** Counters by operation and S3 error code, by authentication failure reason, streams in flight against the cap, and bytes in and out. Built 2026-11-19 (w21/m498 t014) as `bex_s3gw_requests_total{operation,code,status}`, `bex_s3gw_auth_failures_total{reason}` (unknown*key, bad_signature, clock_skew, expired, malformed, denied, throttled, internal and `secret_store`, which is OpenBao failing on the key path), `bex_s3gw_bytes_total{direction}`, `bex_s3gw_streams_in_flight` and `_stream_limit`, `bex_s3gw_egress_budget_refusals_total` and `bex_s3gw_listing_response_bytes_total`, scraped per pod by the `bex-s3gw` job whose keep-list is `bex_s3gw*.\*`(a test reads the live list and the registry, and`scripts/obs-scrape-keep-check.sh` reads the alerts against it). Every alert has a firing test (`deploy/gitops/base/rules/s3_gateway_alerts_test.yml`) and a panel on the Billing and metering board: `S3GatewayServerErrors`(5xx other than the SlowDown throttle above 5% of requests for ten minutes),`S3GatewayAuthFailuresHigh`, `S3SecretStoreErrors`(critical),`S3StreamSlotsSaturated`(a replica above 80% of its 64 slots),`S3EgressBudgetRefusals`and`S3ListingBytesHigh`(over 1 GB of listing answers in a day). **The S3 kill switch is the same mechanism as objectgw's**, a reviewed replica count in`lego/operator/config/prod/kustomization.yaml` (`bex-s3gw`, normally 2), after which Traefik answers 503 on `objects.`; `scripts/gitops-validate.sh` pins that the patch exists and that the runbook (`docs/runbooks/objectgw-kill-switch.md`, "The S3 API switch") shows it. The first draft proposed a static 503 route; scaling to zero needs no new mechanism and no component to keep running during the incident it is for.
- **`CopyObject` and `UploadPartCopy`.** Both buckets are bex buckets of the key's workspace in one region, and bex runs a server-side Wasabi copy between the two physical keys, with the metadata directive `COPY` or `REPLACE`, up to 5 GiB; `UploadPartCopy` takes a range of such a source. The AWS CLI copies an object of 8 MiB or more with `UploadPartCopy`, so `aws s3 mv` and a bucket-to-bucket `sync` fail without it. The CLI also asks for tags while it copies, and Wasabi's `NoSuchTagSetError` is what breaks `mv` and `sync` under CLI v2, so `GetObjectTagging` answers 200 with an empty `TagSet` and a `PutObjectTagging` that carries tags answers 501. A copy needs the read of the source (`can_view_sensitive`) and the write of the destination (`can_create`), the quota gate adds the source's size, and a copy across regions or workspaces answers 501.
- **Multipart upload.** `CreateMultipartUpload` starts the Wasabi upload and writes a row `object_multipart_uploads(id, workspace_id, bucket_id, region, key, wasabi_upload_id, created_by, created_at, last_part_at)` (`region` is the bucket's, copied so the quota read, the sweep and a purge reach the right Wasabi bucket after the bucket row is gone; `created_by` is the access key id); the upload id bex hands out is the row's typed id (`mpu-`). Its parts are rows `object_multipart_parts(upload_id, part_number, size, etag, uploaded_at)`, so a part number sent again replaces the earlier one and the upload's `bytes` is their sum. Each `UploadPart` is streamed to a presigned `UploadPart` URL that signs `content-length`, after the quota gate reserved its declared length; parts follow S3's published limits (5 MiB to 5 GiB, the last one smaller, at most 10,000), which Wasabi's own are not verified against (§ Not verified). **The parts' bytes count against the workspace's quota until the upload completes or is aborted**, because the sweep's object listing does not see them, and a part that would take the upload past 5 GiB is refused with `EntityTooLarge` when it starts, not at the end (so a larger `aws s3 cp` fails at its 5 GiB mark, which the docs say). `CompleteMultipartUpload`, `CreateMultipartUpload` and a copy confirm the bucket row `FOR SHARE` as D1 describes for puts. `CompleteMultipartUpload` passes the part list to Wasabi, rebuilt from `PartNumber` and `ETag` alone and checked against the rows first (ascending, each part uploaded with that ETag, each but the last at least 5 MiB, the total at most 5 GiB; parts uploaded and not listed are dropped, as on S3); `AbortMultipartUpload`, `ListParts` and `ListMultipartUploads` are served from the rows, and an abort also reaches Wasabi (`ListMultipartUploads` takes no `delimiter` in v1: 501). A part writes no allowed audit row, however many a large upload has (a 1 GiB `aws s3 cp` is 128): the upload's create, complete and abort rows are its record, and a denied part is recorded once per key, verb and bucket per window. An unfinished upload keeps its bucket from being deleted (`BucketNotEmpty`, as on S3), and a deleted workspace's uploads are aborted at Wasabi before its prefix is emptied. **`UploadPartCopy` and `CopyObject` honor the four `x-amz-copy-source-if-*` conditions** against the source they already HEAD (412 `PreconditionFailed` when one fails, including `if-none-match` and `if-modified-since`, which S3 also answers 412 on a copy): `aws s3 cp` between buckets sends `if-match` on every part so a source that changes mid-copy is not stitched together, and answering 501 to it (as the first draft of D3 did for every conditional header) made every copy of 8 MiB or more fail. Settled 2026-11-19, w21/m498 t013, with stock aws-cli. **The sweep aborts an upload with no part for 7 days** (`last_part_at`), a constant that a lifecycle `AbortIncompleteMultipartUpload` rule can shorten, because the parts Wasabi holds are billed there and are in no object listing bex can read.
- **Listing.** `ListObjectsV2` and `ListObjects` list Wasabi under `<tea-id>/<obk-id>/` plus the client's prefix and strip that prefix from the keys they return, with `delimiter`, `max-keys` (at most 1000), `encoding-type=url` and `start-after`; `fetch-owner` is ignored. **The V2 continuation token is the base64url, without padding, of the last client key it returned**, fed to Wasabi as `StartAfter` after the server adds the prefix back; it is never Wasabi's own opaque token, so a forged token can start a listing at another point of the same bucket and nowhere else. **V1's `marker` and `NextMarker` are raw client keys**, as S3 defines them (a client may send any key), so nothing is decoded. With a `delimiter`, a page that ends in a common prefix `p` is continued from `p` followed by U+10FFFF, which sorts after every key under `p`, and a V1 `marker` that is one segment past the request prefix and ends in the delimiter is treated the same way (a key equal to the prefix is a key, not a common prefix); a continuation from the bare prefix would return that prefix's keys again. (The first draft of this decision incremented the last byte of `p`, `/` to `0`; `StartAfter` is exclusive, so that skipped a key named `dir0`. A key that sorts after `p` and under it is dropped from the first page of the continuation, so a Wasabi that orders differently cannot repeat the prefix. Settled 2026-11-19, w21/m498 t012.) The V2 token carries one byte that says whether its last entry was a key or a common prefix, because the two continue differently and a V2 client never sends a marker. The delimiter is one ASCII byte in v1 (so the increment stays valid UTF-8) and any other answers 501 `NotImplemented`. Tests cover a page that ends on a prefix, a key that equals a prefix and a prefix with a multi-byte character before the delimiter. Wasabi counts what a listing reads as egress (D8), so a listing adds its estimated response bytes (the sweep's `listResponseBytes` estimate) to the workspace's `object_storage_egress_bytes`, and listings are capped per workspace and per replica at 5 a second, a constant (D8).
- **Buckets.** `CreateBucket` writes a row and makes no Wasabi call; a name is unique within a workspace, and the same name in another workspace is a different bucket, so S3's global-namespace `BucketAlreadyExists` never occurs and an existing name is 409 `BucketAlreadyOwnedByYou`. `ListBuckets` lists every bucket of the workspace in both regions, the `render-<region>` system buckets included. `DeleteBucket` checks emptiness with a one-key listing and the absence of multipart uploads (409 `BucketNotEmpty`). `HeadBucket` answers 200 with `x-amz-bucket-region`; `GetBucketLocation` answers the bex region name. A bucket is limited to 1,000 per workspace (400 `TooManyBuckets`). A preflight cannot name its workspace, so it resolves its bucket only from the `X-Amz-Credential` key id of a presigned URL's query; an unknown or revoked id, a missing bucket and a refused origin all answer the same 403 with no CORS header (D4).
- **Bucket configuration.** CORS is the rules of `PutBucketCors` (`AllowedOrigin`, `AllowedMethod` of GET, PUT, POST, DELETE and HEAD, `AllowedHeader`, `ExposeHeader`, `MaxAgeSeconds`), at most 100 rules and 64 KiB, stored on the bucket row. Lifecycle is `PutBucketLifecycleConfiguration` with `Filter.Prefix` (or the legacy `Prefix`), `Status`, `Expiration` (`Days` from 1 to 36,500, or a `Date` at 00:00 UTC) and `AbortIncompleteMultipartUpload.DaysAfterInitiation`, at most 1,000 rules; `Transition`, `NoncurrentVersionExpiration` and the tag and size filters answer 501. Publishing a bucket is not an S3 call (D4): `GetBucketPolicy`, `PutBucketPolicy` and `DeleteBucketPolicy` answer 501. Both rule sets are validated by the code the hourly sweep runs them with (`objectstorage.ValidateLifecycle`, `ValidateCORS`), inside the service, so no route can store a rule the sweep would not run. `Days` is capped at 36,500 (`MaxLifecycleAgeSeconds`, 100 years): a larger value, a "never expire" idiom, would overflow a `time.Duration` and delete every object. A bucket with no rules answers `NoSuchCORSConfiguration` or `NoSuchLifecycleConfiguration` (404). Both are stored in the JSON shape the sweep already runs (`lifecycle.go` and `cors.go`, written for Cloudflare's API and kept): `Days` is `maxAge` in seconds, `Date` is the `Date` type, `Status` is `enabled`, `Filter.Prefix` is the condition's prefix, and `AbortIncompleteMultipartUpload` is the abort transition, which now runs; CORS maps one to one, and `ID`s are kept so a `Get` returns what a `Put` sent. Rules written through Contract B are read the same way, and none are known beyond the QA buckets.
- **Errors.** S3's XML with S3's published codes where S3 has one: `AccessDenied`, `InvalidAccessKeyId`, `SignatureDoesNotMatch`, `RequestTimeTooSkewed`, `NoSuchBucket`, `NoSuchKey`, `NoSuchUpload`, `BucketAlreadyOwnedByYou`, `BucketNotEmpty`, `InvalidBucketName`, `TooManyBuckets`, `InvalidArgument`, `KeyTooLongError`, `EntityTooLarge`, `EntityTooSmall`, `InvalidPart`, `MissingContentLength`, `InvalidLocationConstraint`, `BadDigest`, `XAmzContentSHA256Mismatch`, `NotImplemented`, `SlowDown` and `ServiceUnavailable`. `QuotaExceeded` (403) is bex's own, for a D8 cap, and its message says which. `InvalidRange` (416), `PreconditionFailed`, `MalformedXML`, `IncompleteBody`, `AuthorizationHeaderMalformed` and `AuthorizationQueryParametersError` are S3's and bex uses them as S3 does. A bucket name is resolved inside the key's own workspace, so another workspace's bucket is simply `NoSuchBucket` and nothing about other workspaces can be probed.
- **The command: `bex s3`.** A launcher in `lego/cli`, which imports nothing from the backend, in the shape of `bex ea objects`'s pass-through and the launcher's other commands that run a local tool.
  - `bex s3 <args>` runs `aws s3 <args>` and `bex s3api <args>` runs `aws s3api <args>`, with the environment set: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` of a key minted for the signed-in person in the current workspace (ephemeral, twelve hours, cached in the CLI's state directory with mode 0600 and replaced when under one hour remains; a command that outlives its key fails with a 403 the CLI does not retry, so a very long transfer uses a persistent key), `--endpoint-url https://objects.<base domain>` on the command line (the `AWS_ENDPOINT_URL_S3` variable needs a recent CLI, and an older one would send the request to AWS), `AWS_REGION=oregon` (`--region` overrides it), and `AWS_CONFIG_FILE` and `AWS_SHARED_CREDENTIALS_FILE` pointed at files bex owns, the config carrying `s3 = addressing_style = path`. The child never sees the user's `AWS_PROFILE` or `AWS_SESSION_TOKEN`, so the user's own AWS credentials are not sent to bex and bex's key never lands in `~/.aws`.
  - `bex s3 env` prints the same variables for other tools (rclone, boto3, s5cmd, Terraform's AWS provider with `s3_use_path_style`), `bex s3 keys create|list|revoke` manages persistent keys (the secret is printed once), `bex s3 public <bucket> enable|disable|status` publishes or unpublishes a bucket (D4; it calls bex's bucket route with the person's own token, so it needs the admin role), and `bex s3 info <bucket>` reads the bucket route above (region, public host, objects and bytes). A URL made with `bex s3 presign` stops working when its ephemeral key expires (twelve hours at most), whatever `--expires-in` says; a long-lived URL needs a persistent key (`bex s3 keys create`, then `bex s3 env`), and the docs say so. Those five names are bex's; everything else is passed to `aws` as typed.
  - **Why it runs `aws` instead of speaking S3 itself.** The AWS CLI v2 already has `sync`, multipart, retries and progress, and a native client would re-implement them in the launcher for no customer gain. ### D4 — Public access: `bex s3 public` enables a read-only gateway at `pub-<obk-id>.onbex.co`

`bex s3 public <bucket> enable` (REST `PUT /v1/object-storage/{ownerId}/buckets/{bucket}/public`, with a GraphQL mutation beside it, thin adapters of the core service's `SetBucketPublic`) sets `public` on the bucket, `disable` stops serving, and `status` reports the host. The public host is `pub-<obk-xid>.<BEX_BASE_DOMAIN>`; it is in the answer and in `bex s3 info <bucket>`. Private is the default for every bucket. **Publishing is not an S3 call.** It needs `can_manage` (a workspace admin), which no access key holds (D3), so a leaked key cannot publish customer data, and S3's bucket-policy calls answer 501. A policy-based toggle for the tools that expect one is D10. A public bucket is read on `pub-` hosts only: an unsigned request to `objects.` cannot name a workspace.

- **objectgw.** A new binary in the backend image, deployed like the static-server ([ADR029](ADR029-static-sites.md)): `GET` and `HEAD` only, `Range` and conditional requests passed to Wasabi, no listing (the root answers 404), a **read-only** Wasabi identity, a cache. It resolves `Host` to a bucket by asking bex-api (cached 30 s, misses cached too, authenticated by a bearer: see As built), so the gateway holds no database credential. A private, deleted or unknown host answers 404.
- **Host.** `pub-<obk-xid>` is a single label under `BEX_BASE_DOMAIN`, so the existing wildcard certificate covers it with no per-host order ([ADR093](ADR093-onbex-wildcard-tls.md) w4/650). The `pub-` prefix is reserved in service-slug validation so a service cannot take a bucket's host. Routing `pub-*` hosts to objectgw is an infrastructure task (t006).
- **Trust.** Public bucket content is served from the same registrable domain as tenant apps and static sites, so it carries the same risk class: tenant-controlled HTML and script on a sibling host ([ADR103](ADR103-security-review-static-rewrite-proxy.md) is the model). objectgw sets `X-Content-Type-Options: nosniff` and serves the stored `Content-Type` and `Cache-Control`; it does not claim stronger isolation than static sites have.
- **CORS.** `PutBucketCors` stores the rules on the bucket row, and objectgw applies them, including preflight. The S3 host is reached by a browser only with a presigned URL, and the same rules apply there: a preflight to `objects.<domain>/<bucket>/…` is answered from the bucket's rules, with no credentials, resolving its bucket from the presigned query's `X-Amz-Credential` key id alone (an unverified routing hint: an unknown or revoked id, a missing bucket and a refused origin all answer the same 403 with no CORS header), and a response to a presigned request carries the rule's headers. A header-signed browser SDK cannot be served, because its preflight carries no key id. Wasabi's own CORS stays off. The bex cap is 100 rules and 64 KiB per bucket.
- **Authorization.** Enabling or disabling needs `can_manage` (workspace admin), because it publishes customer data. Reads need nothing. A system bucket (`render-<region>`) can be made public by the same call; the Render CLI has no way to know.
- **Egress is the exposure.** Wasabi's free egress is a fair-use ratio, and public reads are the case most likely to break it. objectgw counts every byte out, enforces per-bucket and per-workspace rate and bandwidth caps (set from the production walk of 2026-11-16, § As built), and has a kill switch: scale objectgw to zero replicas in GitOps. That needs no new mechanism and no environment variable. A stopped `pub-` host then gets Traefik's no-backend answer, measured on production on 2026-11-16 as `503` with the plain body `no available server` (and `502 Bad Gateway` for the first seconds, while the pods are still terminating), instead of objectgw's 404; an exact 404 would need a runtime flag store, which the backend does not have today (a search of `lego/backend/internal` for one found none) and which is a separate decision. The account is shared with the platform's backups (D1), so a Wasabi limit would reach the restore paths too; t006 adds an operator alert on month-to-date public egress, its thresholds set from measurement like the caps, ahead of the kill switch. Wasabi also counts what a listing reads, so the hourly sweep's listings (D8) are part of the same ratio; they are budgeted at 10 GB a month and watched by `ObjectStorageSweepListingHigh` (w21/095, 2026-11-16). Cloudflare labels r2.dev non-production; bex's host is rate-limited and cached but not a CDN, and the docs must say so.
- **Not here:** custom domains, a CDN, signed public URLs.
- **As built, 2026-11-15 (w21/m417).** What the code does where this section was silent or chose differently:
  - **How objectgw authenticates (decided in t001).** The gateway sends `Authorization: Bearer <BEX_OBJECT_STORAGE_GATEWAY_TOKEN>` to two verbs on bex-api's cluster-internal `:8091` listener (`internal/objectgw/verbs.go`; never on the public `:8090` mux, which a test pins): `GET /internal/object-gateway/public-bucket?host=<host>` answers `{bucketId, workspaceId, region, cors}` for a public, live bucket of a served region, and one answer, `404`, for everything else (private, deleted, unknown, malformed, another domain, the apex), so the gateway and a visitor cannot tell a private bucket from one that never existed; `POST /internal/object-gateway/egress` takes `{bytes: {<tea-id>: n}}`. It is the shape of the ops-role and identity-claims verbs: a static bearer, compared in constant time before any database work. It is **not** the SSH gateway's `BEX_SANDBOX_EXEC_SECRET` HMAC: that secret also signs the agent credential mints, so an internet-facing server must not hold it. A lookup of public data needs no replay guard (the HMAC verbs spend a database write per request on one). The token is at least 32 characters (startup refuses a shorter one); unset, the verbs are not mounted and every `pub-` host answers `503`. `scripts/object-storage-s3-credentials.sh provision` mints it once (64 hex characters) and `install` puts the same value in `bex-object-storage` and `bex-object-storage-read`.
  - **The host** is `publichost.Label` (`internal/objectstorage/publichost`, a leaf): `pub-<xid>` for `obk-<xid>`, one label under `BEX_BASE_DOMAIN`. The publish route answers 501 on a deployment with no hosting domain. The as-built toggle, `dev-url` in `internal/api/cloudflare_r2_domains.go`, goes with Contract B (D3) and the publish route replaces it.
  - **The slug reservation is narrower than the text above.** A service slug is its host's label, so a service called `pub-<20 xid characters>` would take a bucket's host. The refusal the first draft implied (every name that starts `pub-`) would be a parity divergence, since Render refuses no service name for its host. `store.CreateApp` instead treats exactly that shape as a taken subdomain, as Render does for a taken one: the service keeps its name and gets a `-xxxx` suffix. `pub-site` is untouched. The slug is minted only in `CreateApp` (`internal/store/store.go`); the operator and the CRD never validate one, and a tenant cannot apply an App CR. Traefik's route for `pub-` hosts has a higher priority than any service route, so a collision could not expose another tenant's bytes either.
  - **Reads go to Wasabi as the visitor asked.** The gateway signs a one-minute GET or HEAD URL with the read-only identity and sends the visitor's `Range`, `If-Match`, `If-None-Match`, `If-Modified-Since` and `If-Unmodified-Since` with `net/http` (compression off), so partial content, `304` and `412` are Wasabi's own and the bytes are those stored. Wasabi's `412` and `416` bodies are XML with a request id, so the visitor gets the status and a plain line. `If-Range` is not an S3 header: a request that carries it gets the whole object, which the standard allows, since a ranged answer for a changed object would corrupt a resumed download. The query string is ignored, so no `versionId`, listing or response override is passed on. The root and every key that fails the D7 validation (a `.` or `..` segment after decoding, a leading `/`, a backslash, a control character) answer `404`.
  - **The cache** holds whole objects of at most 1 MiB, 64 MiB and 8192 entries per replica, for 60 seconds, filled by a plain GET (at most 32 fills at once; a bigger object or a ranged read streams). A hit costs no Wasabi request: `http.ServeContent` evaluates `Range`, `If-Range` and the conditional headers and answers `HEAD`. An overwritten object reaches visitors within 60 seconds. Disabling public access is bounded by the lookup cache, 30 seconds with misses cached too, because the bucket is looked up before the object cache is read: a test drives disable, the window and the `404`. The lookup of a host not known to be a bucket is rate-limited (50 a second, burst 100) and concurrent lookups of a host share one call, so guessing hosts costs bex-api at most that rate; a bucket that was served is renewed under a limiter of its own (200 a second), so a flood of guesses cannot make real buckets answer `503` as their entries expire; a failed lookup is `503`, never a cached `404`.
  - **CORS** is `cors.go`: the first rule whose origin (`*`, an exact origin, or `https://*.example.com`), method and headers admit the request wins; an allowed origin gets `Access-Control-Allow-Origin` (`*` for a `*` rule, the origin otherwise), the rule's expose headers, and `Vary: Origin` on every answer of a bucket that has rules; a preflight answers `204` with the methods, the requested headers, the max age and `Vary`, and `403` with no CORS header when no rule admits it. `Access-Control-Allow-Credentials` is never sent. Every answer carries `X-Content-Type-Options: nosniff`; the stored `Content-Type`, `Cache-Control`, `Content-Disposition`, `Content-Encoding`, `Content-Language`, `Expires`, `ETag` and `Last-Modified` are served and nothing else of Wasabi's.
  - **Caps** (`limits.go`, bex's own, unverified, per replica; ADR018; reset from the production walk of 2026-11-16, below): 50 requests a second per bucket (burst 100) and 100 per workspace (burst 200); 2 MiB a second per bucket (burst 64 MiB) and 4 MiB a second per workspace (burst 128 MiB); at most 32 responses open per bucket, 64 per workspace and 256 per replica, so a few slow readers of one bucket cannot hold every place. A response is charged as it starts, so one large object can take a bucket into debt and is served whole; the next request answers `429` with `Retry-After` until the debt is repaid. A bandwidth cap bounds a rate, not a month. The first values were 10 and 20 MiB a second with bursts of 256 and 512 MiB: a replica can relay about 240 MiB/s, so no replica limit asked for a change, but 20 MiB/s from each of two replicas spends the shared Wasabi account's whole free-egress allowance (67 GB) in 27 minutes, so the bandwidth caps are now sized to move a workspace under half of it in an hour (`TestTheBandwidthCapsLeaveTheAllowanceAnHourOfWarning`).
  - **Streams.** A streamed response keeps its write deadline a minute ahead of its reader and never past 30 minutes: the server's own 120 s timeout would cut a large object, and a flat 30 minutes would let a stalled reader hold its place that long.
  - **Counting.** objectgw counts the object bytes each response sends (not the text of an error) per workspace, exports `bex_objectgw_response_bytes_total{origin="wasabi"|"cache"}` and `bex_objectgw_requests_total{result}`, and every minute posts the per-workspace sums to the egress verb, which adds them to `object_storage_egress_bytes` (D8), the shadow meter shown at $0. A gateway that dies loses at most a minute.
  - **The alert reads the meter, not objectgw.** Prometheus keeps three days, so a month cannot be summed there. bex-api exports `bex_usage_object_storage_egress_month_bytes`, the sum of the meter over the current UTC month for every workspace and all three paths (presigned reads, streamed reads, public reads), which is the quantity Wasabi's fair-use rule is about. It is an upper bound of what Wasabi served: bytes objectgw sent from its own cache count too, since the meter is per workspace and the gateway reports what it sent, not where it came from (the gateway's own `bex_objectgw_response_bytes_total{origin}` separates them). `ObjectStoragePublicEgressHigh` (30 GB, warning) and `...Critical` (50 GB, critical), both after five minutes, read it. Wasabi's free egress is monthly egress at or below the account's active storage, which measured 67 GB on 2026-11-16 for the whole shared account, so the thresholds are about 45% and 75% of that allowance (the first values, 500 GB and 900 GB, assumed the 1 TB minimum plan counts, which Wasabi's policy text does not say, and would have fired only after the account was over). The meter does not hold the sweep's listings, which Wasabi counts too (D8, w21/095): the sweep's own budget is 10 GB a month, `ObjectStorageSweepListingHigh` watches it, the critical threshold plus the budget (60 GB) is still under the allowance, and both alert descriptions say that the total they read is only what bex serves to tenants. The panel is on the Billing and metering dashboard. The gateway's own counters are scraped per pod (`kubernetes_sd`), because a scrape of the Service read one replica's series only.
  - **Deployment.** objectgw is `bex-objectgw` (`lego/operator/config/objectgw`): two replicas, same image as the manager, hardened like the static-server, no Kubernetes API access, `envFrom` the optional `bex-object-storage-read` Secret. Without the Secret it stays Ready and answers `503`. Traefik reaches it through two IngressRoutes (a Kubernetes Ingress cannot match `pub-*`) at priority 10000 with the default wildcard certificate. The kill switch is the replica count in `lego/operator/config/prod/kustomization.yaml` (`docs/runbooks/objectgw-kill-switch.md`); Argo CD's self-heal reverts a `kubectl scale`.

### D5 — Lifecycle rules run in the sweep

`PutBucketLifecycleConfiguration` stores the rules on the bucket row (in bex's own shape, a `Days` kept as a `maxAge` in seconds). The hourly sweep (D8) deletes objects matching a rule's prefix whose `LastModified` is older than `maxAge` (or past `date`), at most 10,000 per rule per sweep, so one sweep stays inside its hour. A rule runs when its region is next listed, which is every hour only up to 100 objects (D8, w21/095: Wasabi counts what a listing reads as egress): about a day at 2,400 objects, which is Cloudflare's "typically within 24 hours of the expiration" (read 2026-11-16), and up to 72 hours from 7,101 objects. A rule with `Transition` answers 501. An `AbortIncompleteMultipartUpload` rule runs in the same sweep (D3), which also aborts an upload that has had no part for 7 days whether or not a rule says so. The cap is 1000 rules per bucket (bex's own). Wasabi's 90-day minimum storage duration bills an object deleted earlier; whether it bills the remainder for a deleted object is unverified, and the docs must warn that a short rule saves nothing on storage.

### D6 — Authorization is workspace-level, in two layers, for Contract A and the S3 API

Render has no bucket-level access control that I could find: access is the workspace role plus the API key, and a key today carries every permission of the account ([fine-grained keys](https://render.com/changelog/scope-access-to-a-workspace-s-resources-with-api-keys) are a private beta). bex mirrors Render's roles ([ADR024](ADR024-members.md), `deploy/gitops/authz/model.fga`), so access is by workspace and needs no new FGA type.

- **OpenFGA**, through `Base.AuthorizeWorkspaceAs` (`lego/backend/internal/core/base.go`) on `ownerId` (Contract A) or on the access key's workspace (S3):

  | Operation | Relation |
  | --- | --- |
  | list objects (A and S3), `HeadObject`, `ListBuckets`, `HeadBucket`, `GetBucketLocation`, `GetBucketCors`, `GetBucketLifecycleConfiguration`, `ListParts`, `ListMultipartUploads`, the bucket route of D3, `ListAccessKeys` | `can_view` |
  | get an object (A and S3, and the source of a copy) | `can_view_sensitive` |
  | put, copy or delete an object, a multipart upload, bucket create or delete, `PutBucketCors`, `DeleteBucketCors`, `PutBucketLifecycleConfiguration`, `DeleteBucketLifecycleConfiguration` | `can_create` |
  | publish or unpublish a bucket (the bucket route of D3 and `bex s3 public`, not an S3 call) | `can_manage` |
  | create or revoke an access key | the `mint` class (below), then `can_create` |

  Object bytes are customer data, as Postgres exports are, so get is sensitive, matching [ADR095](ADR095-agent-attachments.md).

  **Audit verbs (w21/087).** The routes authorize in their HTTP adapters, where `core.Base` would derive the audit verb from the calling closure; the audit log named them `api.route.func1`, `api.RegisterREST.func2` and the like. Each route names its verb through `AuthorizeWorkspaceAs`, spelled `objectstorage.<Action>` (`lego/backend/internal/objectstorage/audit.go`): `PutObject`, `GetObject`, `DeleteObject`, `DeleteObjects`, `CopyObject`, `ListObjects`, `CreateBucket`, `DeleteBucket`, `GetBucket`, `ListBuckets`, `GetBucketUsage`, `Get/Set/DeleteBucketCORS`, `Get/Set/DeleteBucketLifecycle`, `Get/SetBucketPublic`, `CreateMultipartUpload`, `CompleteMultipartUpload`, `AbortMultipartUpload`, `ListMultipartUploads`, `CreateAccessKey`, `ListAccessKeys`, `RevokeAccessKey` and `NotOffered` (the refusals, and the S3 operations bex answers 501). Contract A and the S3 API share a verb for the same action, and `UploadPart` and `ListParts` write no row of their own. A write relation records the allowed and the denied call, a read relation only the denied one, so a successful list or info leaves no row (a get is the one exception, below). Render's audit-log enum has no object or bucket event, so none maps onto one: REST reports the verb as bex's own `<feature>.<Action>` value ([audit-logs-api.md](render-artifacts/audit-logs-api.md)). `TestEveryRegisteredRouteRecordsANamedVerb` drives every route and fails a verb that is not `<feature>.<Action>`.

  **Audit targets and the download row (w21/094, 2026-11-16).** A row read `objectstorage.PutObject` on `workspace:tea-…` and named nothing else, and a successful get wrote no row, so a reader could tell neither which bucket or key a put or a delete touched nor that customer bytes had been downloaded. Render's audit-log enum has no object or bucket event (render.com/docs/audit-logs lists no event with object, bucket or storage in its name, read 2026-11-16), so both decisions are bex's own and not parity ones.

  - _Decision 1: the target names the bucket, and an object row its key._ It is `bucket:<name>` for a route that acts on a bucket and `object:<bucket>/<key>` for one that acts on an object, on the allowed and the denied row alike (`core.BucketTarget`, `core.ObjectTarget`, recorded through `Base.AuthorizeWorkspaceTargetAs`). Render's routes carry no bucket, so they name the workspace's system bucket, `render-oregon`: Contract A and the S3 API read alike, and the key a put through one wrote is the key a get through the other names. REST's audit `metadata` carries `bucket` and `key` (two keys, as the neighbouring kinds key `service` or `database`), and GraphQL's `resource` is the target. The name is the route's path value and is never resolved against a bucket row first, so the authorization order is unchanged: authorize, and the row carries what the path named. The target is built from the path alone, so no query string, header, body field, presigned URL or credential can enter it. The key is the one field a caller fills, and a refused caller's is not validated yet, so it is bounded to 256 bytes after escaping (a longer one is cut on a character boundary and ends `…[truncated, N bytes]`), is valid UTF-8, has every control, format or line-separating character (a newline, a bidirectional override) and every backslash written as an escape (`\u000a`, `\xff`), and has a signed query that a caller pasted into a key (`?X-Amz-Signature=…`) replaced by `?[redacted]`. One S3 route has no bucket in its path: `ListBuckets` names none. `CreateBucket` carries its bucket in the path like every other bucket route, so its denied row names it, and the allowed row is still written once the bucket exists (the create precedent of w4/m321), so a create that failed (an invalid name, a name taken, the workspace at its limit) records no allowed row. The residual: a caller refused on a workspace that is not theirs leaves a row on that workspace's trail, as every denial does, and its key is now up to 256 bytes of text of their choosing there. It is bounded and escaped, and it is what an admin needs to see when someone probed `secrets/prod.env`.
  - _Decision 2: a successful get records once per request._ `objectstorage.GetObject` is written when bex-api hands out the bytes: an S3 get once the object opened and before its first byte (a presigned S3 URL is verified by bex when it is used, so its use is the get), Contract A's mint of a presigned GET once it was minted (the mint is the download's one request to bex-api; the bytes go to Wasabi and bex never sees them). It is one row per request and never one per chunk. A ranged request is one request, but a client that downloads a large object in parts (`aws s3 cp` reads in 8 MB ranges, ten at a time, by default) would write a row for each part, so **a get writes a row at most once per access key, bucket and key in 15 minutes on a replica** (an in-memory window, so two replicas may write two). A HEAD sends headers and no bytes, a get that found no bucket or no object, or that the mint rate limiter or the stream limiter refused, handed out nothing, and a list or a bucket read is metadata: none of these records a success, and a refusal of any of them still records, as before. A public read at `pub-<id>.onbex.co` is anonymous, so there is no caller to record; enabling one is the audited act (`SetBucketPublic`) and its egress is metered. _Why record it:_ object bytes are customer data, bex already gates a get at `can_view_sensitive`, the class of a Postgres export, and Render audits the downloads of customer data it has once per request (`DownloadDatabaseBackupEvent` for a Postgres logical backup, `DocumentDownloadEvent`) beside `ViewEnvVarValuesEvent` and `ViewConnectionInfoEvent`, so a download that is invisible unless it was refused is the wrong default for this class. _What bounds the volume:_ a get is one row for one request, as a put is. Contract A's mints are limited to 5 a second per workspace (burst 30), shared with the puts, and the S3 streams to 16 in flight per workspace on each replica, so a workspace cannot write more rows a second for gets than the puts' rows already allow. What remains is that a workspace whose app mints a URL for every page view writes a row for each, in a log whose API has no event filter; if production shows that, the looser variant is one row per caller, bucket and hour, a decision for then. **S3 writes are bounded the same way:** a denied row is written at most once per access key, verb and bucket in the same 15-minute window (a leaked `read` key cannot fill the log with denied puts), `CopyObject` records its source bucket and key as well as its destination, `DeleteObjects` records one row naming the bucket, the count and the first key, and `UploadPart` and `ListParts` write none.
  - _The override is closed._ `core.readRelations` still records a refusal only, and a get's authorization still does (the denied row above). The success row is written by the route once the read succeeded (`Base.RecordObjectViewed`), not by the authorization, so a missing object or a refused mint leaves none. The verbs that may do this are one closed set, `core.auditedViews`: `secrets.ViewEnvVarValues`, `datastores.ViewConnectionInfo` and `objectstorage.GetObject`. `core.recordView` enforces it for every writer (any other verb is refused and logged), `TestOnlyTheAuditedViewsRecordASuccessfulRead` pins it by name, and `TestTheAuditedReadAllowlistIsPinned` with the route, tool and field sweeps (`checkReadRecordsNoSuccess`) fail an allowed read that records a success under any other verb.
  - _Tests._ `audit_object_test.go` (core) covers the target's escaping, bound and signed-query cut and the closed set; `audit_object_targets_test.go` and `audit_verbs_test.go` (api) drive Contract A and the S3 API as an allowed and as a refused caller (every route's refusal names its target; a get is one row for a streamed, a ranged and five concurrent requests, none for a HEAD, a missing object or a refused mint; a signed query, headers and a minted URL never reach a row); `audit_verbs_pg_test.go` reads the rows back through the REST audit log on Postgres.

- **OAuth scope class**, for a human OAuth token only: `bex.read`, `bex.write` or `bex.sensitive` (`lego/backend/internal/core/scope.go:217-232`). Machine API keys carry no scope and skip this layer ([ADR012](ADR012-auth.md)); an API key acts with its creator's current role in its own workspace (ADR024, w9/m481), so it reaches every object of that workspace, as a Render key does. The matrix row for Contract A's `GET …/{key...}` is `OpClassSensitive` (`scope_matrix_ops.go:873`, beside the Postgres export), as t002 made it; had it stayed read, a developer's token that consented to `bex.read` only could mint a presigned GET for the bytes. **An S3 request carries no OAuth token at all**: a SigV4 request is authorized as the key's creator on its own workspace (D3) with the key's permission, so the scope class applies where the key is minted. Creating an S3 access key is a `mint`-class verb ([ADR012](ADR012-auth.md) § 7, the scope-class table's `mint` row, beside API-key create and SSH-key enroll), so a human token needs `bex.write` and the mint class and an API key cannot create one. t002 adds a test for Contract A's row; t101 adds one for the mint.
- **Out of scope:** per-bucket or per-prefix keys (D10). An S3 access key in v1 reaches every bucket of its workspace, with its creator's role as the ceiling.

### D7 — Names and keys are validated by bex and default closed

- **Bucket names:** the rule of D1, plus the reserved `render-` prefix, answered with S3's `InvalidBucketName`.
- **Keys:** reject an empty key, one over 1024 bytes, one that starts with `/`, one with a `.` or `..` segment or a doubled slash (Traefik's path cleaning rewrites both before bex sees them, which breaks a SigV4 signature), and one with a backslash or a control character, on every route.
  - Reason: "Wasabi's handling of `..` in S3 keys" is unproven on a live deployment ([m394](../.pm/w21/done/m394/README.md)). A `..` segment is the one input that could step out of `<tea-id>/<obk-id>/`.
  - `http.ServeMux` cleans and redirects such paths, but the check runs on the decoded value regardless, with cases for `%2e%2e`, doubled slashes and Unicode.
  - Render's key rules are not fully known, and S3 itself accepts a key with a `.` or `..` segment and a leading `/`, so this is a bex rule, recorded in ADR018, answered with `InvalidArgument` (`KeyTooLongError` above 1024 bytes). A client that syncs a directory tree does not produce those keys.

### D8 — Usage, quotas and billing: the bucket is the truth, the gate is at write, v1 is a shadow meter

- **Gate.** A put is refused (`429` on A, 403 `QuotaExceeded` on S3) when the last observed usage, plus what bex has itself written since that observation (a write-through counter of the bytes and objects of completed S3 puts, copies and multipart completions, kept per workspace and region; `quota.go` reserves nothing today), plus the declared length of this replica's puts and parts in flight, plus the `bytes` of the workspace's unfinished multipart uploads, plus its own size, would pass a cap. On A the size is `sizeBytes` and the bytes bypass bex, so a per-workspace mint rate limit bounds the overshoot. On S3 bex sees the length first and the bytes after, so the overshoot is what the other replica has in flight, up to 16 streams of 5 GiB on each of two replicas; the counter and the ingress pacing of D3 bound how fast a workspace gets there. **Deletes and overwrites free quota only at the next observation**, up to 72 hours for a large region, so a `sync --delete` that frees space and refills it inside that window is refused; counting them incrementally, which bex can now do for what passes through it, is D10.
- **Sweep.** Hourly, per workspace and region, list `<tea-id>/`, attribute bytes and objects to a bucket by the second path segment, and write `object_storage_usage(workspace, bucket, region, bytes, objects, observed_at)`. A region is listed only once its gap since the last observation has passed: an hour for up to 100 objects, one more hour for each further 100, at most 72 hours (w21/095, below). The same pass runs the lifecycle rules (D5) and retries purges (D9). It feeds the shadow meter `object_storage_gb_seconds`, following [ADR023 § Sandbox snapshot storage](ADR023-usage-metering.md#sandbox-snapshot-storage-w22m313-adr104-d8) and [ADR104 D8](ADR104-sandbox-render-parity.md)'s precedent.
- **Sweep concurrency, deadline and resume (w21/088, measured on production 2026-11-15).** The first sweep walked the workspaces one at a time inside a 50-minute pass, so one workspace with many objects held every workspace behind it, and a pass that ran out of time left the tail unlisted: the next pass listed in id order, so it swept the head again first and the tail starved.
  - **A pool of 4.** `Sweeper.Pass` sweeps `sweepWorkers = 4` workspaces at once, the `errgroup.SetLimit` shape of `core.PatchEach` and the agent PR-state poll. One workspace's regions and pages stay sequential, so 4 is also the most listing requests in flight. It is a constant, not an environment variable (D9). A panic in one workspace fails that workspace only (a worker goroutine is outside `core.Poll`'s recover).
  - **Why 4.** Measured from a pod in the production cluster to Wasabi with the platform credential (curl, a fresh connection each, read-only): a list of an empty prefix takes 0.64 to 0.68 s to Oregon (0.16 s to connect and 0.31 s more for TLS, so about 0.19 s once the connection is warm) and 0.08 to 0.10 s to Frankfurt; a full page of 1,000 keys from Oregon is 215,226 bytes and took 1.26 to 1.28 s (about 0.8 s warm), the only page measured. Four workers therefore send at most about 21 list requests a second if every workspace is empty and about 5 a second when they are paging full lists. I found no published limit for S3 requests: Wasabi's rate-limiting page, read 2026-11-15, covers the Account Control API only (1,000 GET, 100 PUT, 100 POST and 10 DELETE a minute), and one forum report names a 403 `RequestRateLimitExceeded` from the data API (unverified). The account is shared with the platform's backups (D1), and Wasabi's fair-use rule is about egress, not requests, so the bound is meant to take a few slots of a vendor that publishes no limit, not to be the fastest that works. A failed listing is logged and retried by the next pass, and raising the constant is a reviewed change with a new measurement.
  - **What it buys.** Sequentially a pass is the sum of its workspaces; with the pool it is closer to the sum divided by 4, and a workspace that takes minutes holds one worker, not the pass. A workspace at the 1,000,000-object cap in one region is 1,000 pages, about 13 minutes from Oregon at 0.8 s a page, so a sequential 50-minute pass cannot hold more than three of them and the pool holds about fifteen (the 2,000,000 listing stop, `MaxSweepListedObjects`, is about 27 minutes, inside the 30-minute `RegionTimeout`). Small workspaces cost one request a region, about 0.2 s from Oregon, so request count, not time, is what the object cap bounds.
  - **The deadline.** A pass ends at `min(PassTimeout = 50 min, the interval)`: `Run` gives each pass a context that ends at the interval. It stops starting workspaces, abandons the listings in flight (a listing is recorded only when it finished, so nothing is half-written), and returns "pass cut off: n of m workspaces not reached". Those are counted as not reached, not as failures, and logged once. `core.Poll` runs a pass to its end before it reads the ticker, which holds one tick, so a tick that falls inside a pass is skipped, never queued, and two passes never overlap on a replica; the advisory lock does the same across replicas.
  - **The resume.** The pass sorts live workspaces by their oldest observation, a workspace never recorded first (`store.ObjectStorageWorkspace.LastObserved`), after the deleted ones (purges keep the store's order, the attempt longest ago first). A cut-off pass leaves exactly the workspaces it did not reach with the oldest observations, so the next one starts with them. `MinGap` still lets a second replica's tick skip what the first just swept.
  - **What it reports.** One log line a pass (`pass over N workspaces took T with 4 workers: a swept, b fresh, c failed, d not reached`) and `bex_usage_object_storage_sweep_pass_duration_seconds{result="complete|failures|cut_off"}`, `bex_usage_object_storage_sweep_workspace_duration_seconds`, `bex_usage_object_storage_sweep_workspaces_total{result="swept|fresh|failed|not_reached"}` and `bex_usage_object_storage_sweep_last_complete_timestamp_seconds`. They carry the `bex_usage_` prefix because the bex-api scrape job keeps only the families its keep-list names (`deploy/gitops/base/prometheus.yaml`): the first names, `bex_object_storage_sweep_*`, were exported by the pods and found in no Prometheus query on production. Only the replica that holds the lock records.
  - **What watches it (w21/096).** Both alerts read how a pass ended, not how much work it did: since w21/095 a pass over regions that are not yet due is `fresh` and takes a second, which is healthy. `ObjectStorageSweepStale` fires when `time() - max(max_over_time(bex_usage_object_storage_sweep_last_complete_timestamp_seconds[3h]))` passes three hours for 30 minutes (a pass that reached every workspace without a failure sets the gauge; a cut-off pass or one with a failed workspace does not), or when bex-api exports the egress gauge and none of the sweep's series. The gauge is process-local and reads 0 in a new pod, so the three-hour look-back, which keeps the newest value any pod reported, is what stops a deploy alone from reading as the whole epoch. `ObjectStorageSweepCutOff` fires on `sum(increase(..._pass_duration_seconds_count{result="cut_off"}[3h])) > 1.5` for 10 minutes (`increase()` extrapolates, so one cut-off reads about 1.0). Every replica exports every series at zero from its start (`NewSweepMetrics`, `TestEveryReplicaExportsEverySweepSeriesAtZero`), because only the replica that holds the lock records a pass and a series born at its first event is one `increase()` cannot count. Panels: "Object storage sweep: pass duration by result" (against the 50-minute limit), "workspaces by result" and "age of the last complete pass". ### D9 — Credentials and rollout reuse the ADR095 and ADR029 recipes

- **Identities.** The platform's existing Wasabi account (D1) gets two IAM users of its own, the split [ADR029](ADR029-static-sites.md) uses: `infra/wasabi/object-storage-s3-policy.json` (get, put, delete and list on `bex-objects-oregon` and `bex-objects-frankfurt`, held by bex-api and bex-s3; the S3 surface also needs `s3:AbortMultipartUpload`, `s3:ListMultipartUploadParts` and `s3:ListBucketMultipartUploads`, which w21/m498 t001 added and `verify` proved on production on 2026-11-19: it opens a real multipart upload, uploads a part, lists the parts and the bucket's uploads and aborts it, in both regions, with the denied probe on `bex-tfstate` still failing) and `infra/wasabi/object-storage-read-s3-policy.json` (get and list on the same two, held by objectgw).   - bex-api and bex-s3, from `bex-system/bex-object-storage`: `BEX_OBJECT_STORAGE_ACCESS_KEY` and `BEX_OBJECT_STORAGE_SECRET_KEY`. An IAM user belongs to the account, so one pair serves both regions.
  - objectgw, from `bex-system/bex-object-storage-read`: `BEX_OBJECT_STORAGE_READ_ACCESS_KEY` and `BEX_OBJECT_STORAGE_READ_SECRET_KEY`, one read-only pair for both regions. objectgw never receives the read-write pair.
  - Both sides, the same value in both Secrets (amended 2026-11-15, w21/m417 t001): `BEX_OBJECT_STORAGE_GATEWAY_TOKEN`, the bearer objectgw presents on bex-api's internal listener (D4, As built). It is not a Wasabi key and not the SSH gateway's secret. `provision` mints it once; `install` writes it to both Secrets.
  - Reused, already set: `BEX_BASE_DOMAIN`, and the OpenBao connection the env-vars feature uses. An S3 access key's secret is a KV entry at `object-storage/keys/<id>` (D3), so SigV4 needs no key-encryption variable.
  - Tests reach a fake S3 by injecting the endpoint through the config struct. A local S3 for development would be its own decision, not an environment override.
- Without the credential pair, both regions keep answering today's `404` "not offered" on Contract A and 503 `ServiceUnavailable` on the S3 surface. Without the gateway token bex-api does not mount the gateway's verbs, and objectgw (which then has no token either) answers `503`. The code ships before any bucket exists and nothing changes until the user installs the credential, the shape of [ADR095](ADR095-agent-attachments.md)'s 503-when-unconfigured path.
- **Deleting a workspace or account purges `<tea-id>/`** in both regions and drops its bucket rows, access keys (rows and OpenBao secrets) and multipart uploads (aborted at Wasabi), so no `pub-` host keeps answering and no key outlives its workspace ([ADR086](ADR086-account-deletion.md)). An unavailable bucket is retried by the sweep, as ADR095 D7 does for attachments. Without it, a deleted workspace's objects keep accruing Wasabi's 90-day minimum for nothing.

### D10 — Not in this decision

Each is its own follow-up, per the rule that parity-sufficient work ships and wider variants are filed separately:

- **Virtual-hosted-style addressing** (`<bucket>.objects.<base domain>`): it needs a second certificate name, `*.objects.<base domain>`, ordered over DNS-01 as ADR093's is, and a route. Until then every client uses path style, which `bex s3` sets.
- **Per-bucket and per-prefix access keys**, IAM-style policies, and session tokens other than the expiring keys of D3.
- **Signed-chunk payloads** (`STREAMING-AWS4-HMAC-SHA256-PAYLOAD`, with and without a trailer), SigV2, and copies across regions or workspaces.
- Versioning, object lock, tagging, ACLs, SSE-C and KMS, replication, event notifications, S3 Select, website hosting, accelerate, storage classes, Sippy migration, and custom domains for public buckets.
- **A native `bex s3` client** with no AWS CLI dependency, and conveniences beyond `info` and `public` (a `bex s3 usage`).
- **A bucket-policy toggle** for the tools that expect one (S3's `PutBucketPolicy` for a public-read document, answered only for an admin's token, never for an access key).
- **Incremental quota counting for deletes and overwrites**, which bex can do for what passes through it, and a monthly egress budget for Contract A's presigned reads and for public reads.
- A dashboard UI for browsing objects, GraphQL and MCP adapters for them (D1's core service makes them thin), and anything specific to the Render SDK clients beyond D11's test.

## Alternatives considered

- **Keep option B (not offered).** It contradicts the parity rule and the user's instruction.
- **Serve only Render's four routes (this ADR's first version).** It has no bucket, no public access, no CORS and no lifecycle; Render itself calls the feature early access.
- **Keep wrangler's contract (Contract B) beside S3.** It is shipped, and it would keep `wrangler r2` users. The user rejected it on 2026-11-19: it has no listing, three object commands and a 300 MiB cap, and it is a second internet-facing surface to secure, test against a third party's releases and document, for a tool whose useful part S3 already covers.
- **`bex r2 …`, a launcher over wrangler.** It would hide the three variables and `--remote`, and fix none of what is missing: no listing, no copy or sync, one request per object.
- **One Wasabi IAM user per tenant, with S3 straight to Wasabi (the other design of D3).** It keeps the bytes off bex-api. It also takes quota, metering, audit, rate caps and the kill switch out of bex's path on an account with 67 GB of free egress, and it depends on Wasabi enforcing prefix-scoped policies, which is unverified (§ Not verified). The user chose bex verifying SigV4 on 2026-11-19.
- **A native Go S3 client in `bex s3`.** It needs no `aws`, and it re-implements `sync`, multipart, retries and progress in the launcher. D3 runs `aws`; D10 keeps this open.
- **Redirecting S3 requests to presigned Wasabi URLs** (what Contract A does for Render). It would keep the bytes off bex-api, but S3 clients are not written to follow a redirect to a differently signed URL, I did not test it, and quota, metering and audit would be left to a guess.
- **Virtual-hosted addressing first.** It needs a second certificate name and a route, and path style is enough for every client that can set it (D10).
- **Cloudflare R2 as the backend.** Its native public domains, CORS, lifecycle, bucket-scoped tokens and free egress would make D3's S3 API, D4 and D5 almost free, and it allows 100,000 buckets per account. The user chose a Wasabi wrapper. R2's costs are location hints that are only best effort (only jurisdictions guarantee placement), at most one write per second to the same key, a second vendor with no infrastructure in this repository, and storage at nearly twice Wasabi's floor. **Reassess it if Wasabi's fair-use limit stops public buckets.**
- **A separate Wasabi account for tenant data (this ADR's first draft).** It keeps a Wasabi egress action away from the backups and restore paths, for a second 1 TB minimum (about $8 a month) and a second root credential to guard. The user chose the shared account on 2026-11-15. Revisit it at the first Wasabi warning or at the egress alert (D1, D4).
- **A physical Wasabi bucket per customer bucket.** It hits the 1000-bucket default and isolates nothing a key prefix does not.
- **Extend the static-server for public buckets.** It learns hosts from App custom resources and has no database access by design; a bucket has no CR. objectgw copies its shape instead.
- **MinIO or Hetzner Object Storage.** MinIO adds a PVC and an operations surface ([ADR082](ADR082-persistent-disks.md)). `s3client.go` notes Hetzner works too, but the user chose Wasabi and its account, IAM scripts and presign path are in place.
- **A Stripe item each for storage, transfer and requests.** The 20-item Subscription cap leaves no room (D8).

## Consequences

- **`bex-s3` is a data plane.** Streamed uploads, downloads and multipart parts cost connections, bandwidth and long-lived goroutines, at up to 5 GiB an object and 16 streams a workspace on each replica. They run on a Deployment of their own (D3), so a stream does not share pods with REST, GraphQL and MCP, and a rollout waits for them; the cost is a third kind of pod to run, size and roll, and the caps and the deadline extension bound the rest.
- **A new external cost surface.** Wasabi's 1 TB minimum, 90-day minimum storage duration and egress fair-use all respond to tenant behavior, and bex's invoice has no meter to push them back. Public buckets sharpen the egress risk, and the account is shared with the backups, so a limit would reach the restore paths too (D1). The shadow meters, the caps and the kill switch keep it bounded until pricing exists.
- **Provider concentration.** Tenant data inherits the single-provider, single-region exposure `.pm/FUTURE-MAYBE.md:23` records for backups. v1 has no replica, and the docs must say so.
- **Two third-party wire shapes to chase.** Render's `ea` namespace is "subject to change", and S3 clients change their defaults in their releases (checksums, payload framing, addressing). The contract tests (D11) are the only early warning.
- **The listing gap is closed, at a price.** A customer can list a named bucket, and every listing is Wasabi egress (D8), so a workspace that lists a million objects in a loop spends the shared allowance; the listing rate cap and the egress meter bound and show it.
- **A presigned URL is a bearer credential** for one key until it expires, and a public bucket's objects are readable by anyone.
- **Recoverable secrets.** SigV4 needs the secret to verify a request, so bex keeps each access key's secret in OpenBao instead of a hash, as it does for registry credentials; API keys keep a hash. A leak of that KV path would expose them. A key is workspace-wide in v1, so the reach of a leaked one is a workspace's objects until it is revoked (30 seconds to reach every replica), and per-bucket keys (D10) would narrow it.
- **An internet-facing S3 parser.** Canonical requests, `aws-chunked` framing and trailers are parsed in Go on bex-api before any authorization finishes. D11's known-answer tests and fuzzing are the check, and the surface belongs in the next security review round ([ADR110](ADR110-security-review-round25.md) is the latest).
- **Using AWS's names.** The surface is "S3-compatible". bex may refer to Amazon S3 to explain compatibility and may not claim to be it; the host says `objects` and no answer names Amazon.
- **Quota is eventually consistent.** Gating at write plus rate limits bounds the overshoot but does not remove it. Since w21/095 the observation a gate reads is up to 72 hours old for a region of more than 7,100 objects (D8), so the overshoot window of such a region is that long.
- **A new Stripe dimension is scarce.** One cost-denominated dimension (D8) is all the catalog can afford.
