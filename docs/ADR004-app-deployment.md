# Deploying / replacing an App (Hetzner, prebuilt-image path)

> **Status: the manual runbook for the prebuilt-image path.** The **`App` CR is the only interface**: you never touch the Deployment; the operator rewrites it. This laptop-build-and-import runbook is for pushing a **prebuilt image** by hand (`spec.image`).
>
> **Retired on production (2026-11-16).** Steps ⓪–⑥ below no longer deploy anything on the production cluster, and the `/deploy-app-from-local` skill that ran them is removed. The operator sets `imagePullPolicy: Always` on every tenant container (w4/426), so the kubelet resolves each image against a registry on every container start and never starts an image that exists only in a node's containerd. bex-api also creates each App in its workspace's namespace ([ADR043](ADR043-tenant-namespace-isolation.md)), not `default`. To run code that is not on the tracked branch, push the commit and let the in-cluster build deploy it, or push the image to a registry and deploy an image-backed service (`runtime: image`). The steps stay as the record of the original path; importing an image into a node still applies to platform images on the local kind/CAPD cluster (`scripts/mock-cluster.sh operator`).
>
> **Build-from-git is in-cluster.** Render-native runtimes (`spec.runtime` plus build/start commands) and Dockerfile builds run as BuildKit Jobs confined by Pod user namespaces; the explicit bex `spec.builder: buildpack` extension runs as a kpack Image. The pipeline pushes release-generation-tagged images to Zot and pins the resolved digest — no docker daemon, laptop build, or `ctr` import. A signed git push redeploys them ([ADR017-deploy-from-chat.md](ADR017-deploy-from-chat.md), gated on `spec.autoDeploy`). See **[In-cluster builds](#in-cluster-builds-buildkit-kpack--zot)** below.
>
> Build concurrency, queueing, and Pod-versus-machine scaling are decided in [ADR034](ADR034-scalable-build-pipeline.md).

The examples below use a placeholder App `my-app` (container port 3000); substitute your App's name, port, and host. Three places are involved — keep them straight:

| place | role in a deploy |
| --- | --- |
| **laptop** | builds the image, smoke-tests it, runs `kubectl`/`ssh` |
| **a CP node** (via hcloud API + SSH) | serves `/etc/kubernetes/admin.conf` — `scripts/fetch-app-kubeconfig.sh`, touched once, for access (self-managed since w1/m19.1; no mgmt cluster) |
| **app cluster** | containerd stores the image; apiserver holds the `App` CR; the **operator** turns the CR change into a rollout |

## Steps

### ⓪ Get the app-cluster kubeconfig — _laptop → infra cluster_

Cluster API stores the workload ("app") cluster's kubeconfig as a secret on the management ("infra") cluster:

```sh
ssh -i <ssh-key> root@<infra-ip> \
  'kubectl -n bex-capi get secret bex-kubeconfig -o jsonpath="{.data.value}" | base64 -d' \
  > bex-app.kubeconfig
export KUBECONFIG=$PWD/bex-app.kubeconfig
kubectl get app my-app -o yaml   # current image / port / host — your baseline
```

### ① Build amd64 with a **fresh** tag — _laptop_

```sh
cd <project>
docker build --platform linux/amd64 -t my-app:$(git rev-parse --short HEAD) .
```

- **`--platform linux/amd64`** — the Hetzner node is x86_64; an arm64 build won't run.
- **Fresh, non-`:latest` tag (git sha)** — when this runbook was written the operator set no `imagePullPolicy`, so k8s defaulted to `IfNotPresent` and a reused tag silently served the node's _cached_ image. The operator now sets `Always` (see the retirement note above), which is why a node-local image no longer starts.

### ② Smoke-test locally — _laptop_

Cheap insurance before shipping ~800 MB:

```sh
docker run -d --rm --name smoke -p 127.0.0.1:3999:3000 my-app:<sha>
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3999/   # expect 200
docker stop smoke
```

### ③ Import into the node's containerd — _laptop → app node_

No app-image registry yet, so stream the image straight into containerd's **`k8s.io` namespace** (the one the kubelet reads) — one pipe, no temp file:

```sh
docker save my-app:<sha> \
  | ssh -i <ssh-key> root@<app-node-ip> 'ctr -n k8s.io images import -'
```

### ④ Patch the App CR — _laptop → apiserver → operator_

```sh
kubectl patch app my-app --type merge \
  -p '{"spec":{"image":"my-app:<sha>"}}'
```

This is the actual "deploy". The spec change bumps `metadata.generation` — **required**, because the controller watches with `GenerationChangedPredicate`: generation-changing updates are delivered to the reconciler (the reconcile itself is level-triggered and deliberately has no early-return — it re-applies desired state on every pass). The operator then classifies the change by artifact/release identity; changing `spec.image` changes both and therefore rewrites the owned Deployment's image. The default RollingUpdate starts the new pod **before** terminating the old one, so the single node serves without a gap. A pod joins the Service's endpoints (and receives traffic) only once its **`ReadinessProbe`** passes. Workers and cron jobs expose no HTTP port, so they carry no probe at all. What "healthy" means has two modes, matching Render:

| `spec.healthCheckPath` | probe | meaning |
| --- | --- | --- |
| unset | `TCPSocket` on the container port | the platform was not told what healthy looks like, so it asks only whether the process is listening |
| set | `HTTPGet` of the path; 2xx/3xx is ready | the opt-in to a stricter check |

The empty case deliberately does **not** fall back to `GET /`. Kubernetes scores an HTTP probe healthy only on `200 ≤ code < 400`, so that fallback made a service whose root is a legitimate 404 — an API with no root route — permanently un-Ready and impossible to deploy, while the same service deploys on Render (whose default is likewise a TCP socket probe) untouched. The CRD therefore carries no default for the field. The two modes are also distinct **release** inputs: switching between unset and `/` is a configuration deploy of its own — a new release generation and revision on the same artifact — exactly like any other path change (w4/m191). The operator's `release-v2` identity encodes the path verbatim; `release-v1` folded unset into `/`, so such a switch re-rolled pods under the old revision and its deploy row could never go Live. A `release-v1` status is adopted in place on first reconcile (no rollout) when the served release — per its release record or, before records, its live probe — matches the saved mode; a backend-stamped or direct-edit switch still rolls.

**Probe Host (w4/m190).** An HTTP probe still connects to the pod's own IP and port — `HTTPGet.Host` stays empty, because setting it would move the connection to the public route and test the release already serving there — but it sends a `Host` header naming the service, Render's rule ("If your service has any verified custom domains, Render sets one of those domains as the value of the `Host` header … Otherwise, Render uses the service's `onrender.com` subdomain", [render.com/docs/health-checks](https://render.com/docs/health-checks), rechecked 2026-10-10). Selection is custom-first: `spec.host`, then the first `spec.hosts` entry (bex-api admits only verified claims there, so a pending domain is never chosen; a `hostRedirects` source is skipped), else the canonical platform host from `EffectiveHosts` (`spec.subdomain`, not the display name). Private services, workers, unexposed web services and TCP mode send no header — Render's private services have no HTTP check at all, so bex's private HTTP extension keeps kubelet's pod-IP Host. Without the header, an app that allowlists its own hostnames answered the probe 421 and could never finish an HTTP-health deploy.

The Host is **chosen once per release**: domains are operational fields (`AppSpecIdentityClasses`), so adding, verifying or removing one opens no deploy and must not roll pods either. The operator keeps the header (or its absence) from the live template while it carries the same release label, and selects from current domains when a release is first projected — a normal deploy, Restart, or rollback (which pairs the target's historical health path with today's domains). Cancel and failed-rollout restoration reapply the served template verbatim, Host included. The same freeze means an operator upgrade does not roll running services: a template projected before the header existed adopts it on its next real release. Render does not document when its Host reselects after a domain edit; this per-release timing is bex behavior, not an observed Render contract.

> **Migration.** Kubernetes applies CRD defaults at write time, so every App stored before this change has `healthCheckPath: "/"` persisted and keeps the HTTP check. Clearing the field is how an owner opts into the TCP default; nothing is rewritten automatically, because silently changing the health semantics of a running service is not a decision the platform should make on an owner's behalf.

All three probes — startup, readiness, and the `livenessProbe` below — share one handler and get Render's five-second budget (`timeoutSeconds: 5`) rather than Kubernetes' one-second default, which no server-side-rendered page reliably meets — the result there is a permanently flapping pod rather than an honest failure. **Point `healthCheckPath` at a cheap endpoint** (a `/healthz` that does no rendering or database work), not at an expensive server-side-rendered route: the path is probed every 10s for the life of the service, and 60s of consecutive failures restarts the instance, so probing a slow route turns ordinary load into a restart. Render's health-check docs give the same advice.

A `StartupProbe` with the same handler owns the boot phase and carries the full rollout budget; while it runs, kubelet suspends readiness and liveness, so a slow start cannot be mistaken for a sick instance. **Three timers bound a rollout and their relationship is the contract:** the startup budget and the Deployment's `progressDeadlineSeconds` are the mechanism and derive from one constant (15 minutes, Render's window), while bex-api's `DeployGateTimeout` _observes_ that mechanism and is deliberately longer (18 minutes) — the same rule the build (30m Job → 35m gate) and pre-deploy (10m → 12m) budgets follow, so the mechanism's own specific verdict lands before the generic health-gate message. **Service phase follows the mechanism (w4/m103):** when the Deployment reports `Progressing=False` / `ProgressDeadlineExceeded` and no earlier release ever succeeded (`Status.ActiveRevision` empty), the operator settles `phase: Failed` with the stuck-pod diagnosis (crash-loop / image-pull / …) on Ready — so the service header agrees with the deploy row instead of reading `Deploying` forever. A failed rollout over a prior release keeps `Running` / `Hibernated` (deploy fact only), matching the build-failure rule from w6/m124. The 18-minute observer remains the backstop when the CR has not yet observed the deadline; it does not retune either budget. Mid-rollout image-pull diagnosis already rides the Ready condition (`ImagePullBackOff`); surfacing that string on an still-open deploy row's `failureReason` is a deliberate follow-up, not a timer change.

**A startup crash settles early (w4/454).** A process that exits during startup fails the deploy as soon as the kubelet's own CrashLoopBackOff verdict is in (two restarts, about 30–40 s) instead of holding `update_in_progress` for the full progress deadline, as Render does ("Exited with status N … exited or crashed during startup"). Only current-revision pods that were never Ready count, and every one of them must be crash-looping; the settle is the same terminal path and wording as the permanent image-pull failure, for web, private and worker services alike. A process that served and later died, a running pod whose health check fails, and `CreateContainerConfigError` (a linked datastore's Secret can still arrive) keep the 15-minute budget. Over nothing served, the early settle (crash or permanent pull) also stops the release at zero, as the deadline does (w1/m179, w4/m351): the deploy that reads failed is never the one that later serves.

**Queueing is not building.** A build Job requests 2 CPU + 7Gi and is node-exclusive by design, so it can sit unschedulable for many minutes waiting for capacity. That wait is reported as a distinct state — the operator holds the Ready reason at `BuildQueued` until a pod is actually **placed on a node**, then flips it to `Building` — and the control plane maps those onto the deploy row's `queued` and `build_in_progress`. Because phase budgets are measured from the row's last transition, the queued→building edge **restarts the build budget**, so a build that waited 20 minutes for a node still gets its full window to run.

Placement, not pod phase, is the dividing line: the build executes in initContainers, so a pod actively compiling reports phase `Pending` for most of its life. Before this (fixed 2026-08-11) a dispatched build reported `Building` immediately, the wait was spent from the build's own budget, and a build that queued 22 minutes was closed `build_failed` while still running — it then succeeded and shipped, leaving the deploy record contradicting the revision actually serving. Buildpack/kpack builds are exempt: they resolve down a path that reports no waiting, so they still open at `Building`.

Render drops an instance from rotation after 15s of consecutive failures, and so does bex: readiness runs every 5s with 3 failures (w8/189; until then it took 30s, a recorded divergence that w8/189 retired). Render's second steady-state stage — **restarting** an instance after 60s of consecutive failures — ships as a `livenessProbe` (w7/m81: same handler and 5s budget as readiness, 10s period × 6 failures). A wedged instance — process alive, event loop blocked, deadlocked — self-heals in about a minute instead of staying out of rotation until someone notices. That holds again since w4/m353: Kubernetes runs a container's preStop hook before a liveness restart too, and the 60s rollout drain (§ Rollout headroom) was a plain `sleep`, so the restart landed about two minutes after the checks started failing (round 229 measured 114s for whoami with a failing `/health`). The drain now runs the instance's own health check first and skips the wait when it fails, so SIGTERM follows the kubelet's restart decision at once. The contract is unconditional parity, Render's own rule with the same absence of per-service control. The restart-spiral hazard that deferred it from m80 (restarting a service that merely slowed under load produces a cold start that makes the next probe slower still) is bounded two ways: kubelet suspends liveness while the `StartupProbe` runs, so a slow boot gets the full 15 minutes rather than a kill chain; and in TCP mode the probe is a kernel-level connect that never invokes the tenant's handler, so an expensive SSR route cannot fail it — in HTTP mode the hazard is Render's own documented behavior, carried as parity. The rejected alternative — liveness only on an explicit `healthCheckPath` — would deny TCP-mode services the restart Render gives them to avoid a hazard that mode does not have, at the price of a mode distinction Render users never have to learn.

Preferred over a raw patch: declare the App in the project's `render.yaml` and apply that (see below) — same effect, but the spec lives in the app repo.

### ⑤ Watch the rollout — _laptop_

```sh
kubectl rollout status deployment/my-app
kubectl get app my-app   # PHASE Running, REVISION bumped (rev-N → rev-N+1)
```

### ⑥ Verify the edge serves the new version — _laptop → node's traefik_

```sh
curl -s -o /dev/null -w '%{http_code}\n' https://my-app.<node-ip>.sslip.io/
curl -s https://my-app.<node-ip>.sslip.io/ | grep -i '<something only in the new version>'
```

Grep for content that **only exists in the new build** — a 200 alone can't distinguish new pod from old.

## `render.yaml` — declaring the App in its own repo

Rather than hand-writing `kubectl patch`, a project can carry a `render.yaml` at its root declaring how it runs on bex. `bex.yml` remains a deprecated filename-only alias:

```yaml
# render.yaml
services:
  - name: my-app
    type: web # public; use pserv for a private service
    runtime: image
    image: { url: my-app:<sha> }
    # For a git build, use runtime: docker plus repo/branch instead of image.
    numInstances: 1
    healthCheckPath: /healthz # optional. Set => one HTTP GET that follows no redirect, 2xx/3xx is ready (w8/m133). Omit => TCP probe on the port (no default path)

    envVars: # literal (non-secret) config -> App.spec.env (PORT is operator-owned)
      - key: LOG_LEVEL
        value: info
    domains: # custom domains on top of the platform hostname
      - my-app.example.com # first entry -> App.spec.host (canonical URL)
      - www.customer.com # rest -> App.spec.hosts (each gets its own TLS cert)
```

`envVars` are **literal, non-secret** configuration: they map to `App.spec.env` and are set on the container in order, with `PORT` appended last. **Since w5/m149, `PORT` is the service's to set, as on Render** (replacing w2/m95's reservation). The operator resolves the service's effective `PORT` in Kubernetes' own precedence: a `spec.env` literal, then the `envFrom` Secrets, where the service's own set beats a linked group's. A valid value becomes the serving port: container port, Service port, probes and the injected `PORT` all use it, and the operator records it as `status.envPort`, which `App.ServingPort()` (and so `ServicePort`, `OpenPorts`, `InternalAddress`) prefers over `spec.port`. An unusable value (not a number, out of range, or a reserved platform port) is ignored, and `spec.port` applies. Image-port private services keep their image-discovered ports.

**Web services on their image's port (w4/615, 2026-11-14).** A web service created without a port from a Docker build or a prebuilt image (`web-image-v1`) has no `PORT` of its own, so its process gets Render's default, `PORT=10000`, whatever port its image declares with `EXPOSE` or HTTP discovery selects: "The default value of `PORT` is `10000` for all Render web services". Only the routing, the Services, the container ports and the health check follow the selected port, as they do for a detected listener on a native service (w8/267). Until w4/615 the selected port was written into `PORT`, so a process with a public listener on a fixed port and an internal one on `$PORT` bound the same port twice on its second start and never went live, and a crash hint told it to listen on `$PORT` at a port it already used. A crash hint on such a service names no `$PORT`. The rule is recorded per release (`status.imageNetwork.processPort`): a release resolved before w4/615 keeps the `PORT` it started with, so the operator upgrade restarts nothing, and its next release resolves afresh and discovers its HTTP port again under `PORT=10000` rather than keeping a listener chosen under another `PORT`. An explicit port or the service's own `PORT` still sets both.

**A first web image release rolls once (w4/m350, 2026-11-14).** HTTP port discovery on a web service's first release changes only the Services and the route, never the pod template, as Render's port scan routes to the port it finds without restarting the instance. Until w4/m350 an image that declared one port and served HTTP on another (`traefik/whoami` with `EXPOSE 80` listening on 10000) rolled a second ReplicaSet about a minute in: discovery moved the TCP probe's port and the container ports from 80 to 10000, and the first instance could never become Ready on a port nothing listened on. Now, while such a release has no Health Check Path and nothing serves before it, its three probes run Render's default check, "TCP socket probes to one of your service's open ports": an exec of bex's health-probe helper (`health-probe open-port`) that passes when the pod address accepts a connection on any port its network namespace listens on, skipping bex's reserved sidecar ports (`ReservedImagePorts`). Its app container declares no container ports (they are informational, and no Service reads them for an image-port service), and `PORT` is 10000 throughout (w4/615). That template is kept for the release once stored, so going live does not roll it. Unchanged: a service with a Health Check Path keeps its HTTP check on the chosen port; a release over a serving one keeps w4/m320's HTTP guard and hold; every later release probes TCP on its known port; an edge-cached first release keeps the port-bound shape, because its sidecar fronts the primary discovery moves; and an operator that cannot resolve its own image keeps the TCP probe.

**Image-port private services (w6/m148, 2026-10-20).** The paragraph above is the configured-port contract. It still holds for web services, native private services, and every private service created before w6/m148 (prebuilt-image private services before w6/095, 2026-10-29).

- **The exception.** A new Docker private service — Git-built, or prebuilt from an `image:` (w6/095; read anonymously, or with the registry credential the service selected; w4/m301) — created **without** a port (the dashboard leaves the field blank for that shape) publishes every TCP port its image declares with `EXPOSE`, under its stable hostname.
- **`PORT`** is the resolved **primary**, which is also the TCP health-checked port and the `internalAddress` suffix:
  - an explicit port wins;
  - otherwise 3000, if the image declares it;
  - otherwise the lowest declared TCP port;
  - otherwise 3000.
- **Divergence from Render.** This is declared-port discovery, not Render's runtime scan of the ports the process actually opens.
- **References.** A blueprint-created service of that shape takes its ports from the image too, and `fromService` `port`/`hostport` references follow its serving port.

Details: [ADR089 § Port slice decisions](ADR089-render-container-compatibility.md), and the Open ports row of [ADR018](ADR018-render-parity.md).

An environment **value** containing a NUL byte is refused the same way (**w8/m62**): a process environment string ends at its first NUL, so the container runtime would refuse the variable and the native build loader would silently drop the byte. Every write path — service and Environment Group writes, the create payload, Blueprint literals, `sync:false` seeds and prompt answers — returns `400 ENVIRONMENT_VARIABLE_VALUE_INVALID` (Blueprint validation: `valid:false` with the entry's location), naming the key but never the value. Only newly supplied values are checked, so a value stored earlier stays replaceable and deletable. Binary content belongs in a secret file, whose bytes are kept exactly.

**Blueprint deliberately still has no `port` key (w4/m121 t004).** Two reasons, and the second is the load-bearing one. Render's own `render.yaml` has no port field, so adding one would be a bex-only extension to a manifest format bex tracks for parity. And a manifest is **re-applied on every sync**: a `port` declared there would fight the dashboard control on each sync, recreating for the port exactly the two-writers problem `w4/m120` had to solve for manifest `envVars` — where the manifest silently won and the API reported success for a write the process never saw. A blueprint-created service keeps the platform default and is repointed through the update verb like any other, which leaves exactly one writer. Re-open only with a writership rule (a `sync: false` equivalent) designed first, not as an afterthought. Ports below 1024 are bindable (unprivileged ports are enabled on every pod, w6/m149, [ADR022-tenant-isolation.md](ADR022-tenant-isolation.md)), so a stock image that defaults to `:80` (nginx, httpd, whoami) can keep it once the service port is set to 80. **Container privileges (w6/m149, 2026-10-20; native runtimes since w32/m462, 2026-11-17):** new Docker/image and native runtime services run the `render-v1` policy (drop all plus Render's measured `CHOWN, DAC_OVERRIDE, FOWNER, SETGID, SETUID, SYS_CHROOT`), so an image whose entrypoint switches user or chowns its data directory starts unchanged; existing services keep `strict-v1`/`image-v1` ([ADR089](ADR089-render-container-compatibility.md) D2). A rollout stuck because the process listens somewhere other than the configured port surfaces the diagnosis on the failed deploy itself: the operator inspects crash-looping/unpullable pods and stamps an actionable message that closes the deploy as its `failureReason` (w9/011, REST/GraphQL/MCP + the dashboard's deploy page). **The complete set of platform-injected variables (w4/m123).** A tenant container receives the variables the user configured — literals, its own Secret, and any linked environment groups — plus exactly one bex-injected variable, `PORT`, and the eight the Kubernetes kubelet always adds for the API server's own Service: `KUBERNETES_SERVICE_HOST`, `KUBERNETES_SERVICE_PORT`, `KUBERNETES_SERVICE_PORT_HTTPS`, `KUBERNETES_PORT`, `KUBERNETES_PORT_443_TCP`, `KUBERNETES_PORT_443_TCP_ADDR`, `KUBERNETES_PORT_443_TCP_PORT`, and `KUBERNETES_PORT_443_TCP_PROTO` (the full Docker-link set, counted live in `/qa-find-bugs` pass 193, w4/153). Variables the image itself defines (`PATH`, `HOME`, runtime versions) pass through unchanged. Nothing else is added.

That was not true until w4/m123. Kubernetes defaults `enableServiceLinks` to **true**, which makes the kubelet inject a legacy Docker-link set — `<NAME>_SERVICE_HOST`, `<NAME>_SERVICE_PORT`, `<NAME>_PORT_<n>_TCP_*` — for **every Service in the pod's namespace**. Live on 2026-09-21 a web service with four configured variables received **185**, of which **174** were these: every sibling resource in the workspace, three managed Postgres primaries addressed by id, and cert-manager's own ACME solver Service. The count is not the problem. A `<NAME>_PORT` variable **shadows the name an application expects to configure itself with**, so a process reading `REDIS_PORT` or `API_PORT` is handed `tcp://10.x.x.x:6379` by the platform and fails in a way that looks like its own bug. Every pod bex creates — the app Deployment, builds, pre-deploy, cron runs, backups, exports, publish — now sets `enableServiceLinks: false`, and a source-level guard fails if a new pod-producing projection forgets.

**The eight Kubernetes variables cannot be removed this way, and that is worth stating plainly.** The kubelet injects the `kubernetes` Service's own link variables regardless of `enableServiceLinks` (`getServiceEnvVarMap` treats the master Service in the `default` namespace as unconditional), so a bullet claiming they disappear would be wrong. They name the API server, which tenant pods cannot reach anyway — `automountServiceAccountToken` is false, so there is no credential, and NetworkPolicy governs the path.

**Reaching a sibling stays exactly where it was documented.** The supported address is the private one, `<slug>:<port>` ([ADR041](ADR041-service-addresses.md) D4) — surfaced as `internalAddress` on the service object. That never depended on service links, so removing them removes no supported path.

**Credentials** (a database URL, an API key) don't belong in `render.yaml` — set them through the env-vars API ([ADR006-bex-api.md](ADR006-bex-api.md#env-vars--tenant-secrets-render-env-vars-compatible)), which stores them in OpenBao and materializes a `<name>-env` Secret consumed via `App.spec.envFromSecret` ([ADR013-secrets.md](ADR013-secrets.md#product-usage-w4m6-the-env-vars-api)).

Like render.yaml, **the service `type` decides exposure** — a `web` service is public by definition and its platform hostname is mandatory (there is no opt-out flag); `pserv` services are reachable only in-cluster at `<name>.<namespace>.svc:<port>`.

The workload type is immutable after creation. Render's [Blueprint specification](https://render.com/docs/blueprint-spec) says an existing resource's `type` cannot be modified, and the public [Update service API](https://api-docs.render.com/reference/update-service) has no type field. bex enforces that contract twice: CRD CEL admission compares the effective old/new `App.spec.type`, and Blueprint sync returns the same named bad request before it mutates an existing App. The legacy empty type is semantically `web_service`, so empty ↔ explicit web normalization remains valid. Changing between web, private, worker, cron, or static requires deleting and recreating the service; this prevents an old Deployment/Service/Ingress or CronJob from surviving beside a different workload kind.

Apply it from the bex repo — this renders each `.services[]` entry into an App CR and `kubectl apply`s it (respects `$KUBECONFIG`; `DRY_RUN=1` prints the CRs instead):

```sh
scripts/app-apply.sh <project-dir | path/to/render.yaml>
```

Changing `domains[0]` and re-applying is how an App moves to a real domain: the operator rewrites the Ingress to the new host and cert-manager issues a fresh certificate for it (DNS for the host must already point at the edge, or sit behind a proxy such as Cloudflare that forwards HTTP to it — otherwise the ACME HTTP-01 challenge cannot pass). Additional entries serve the App at extra hostnames — typically customers' custom domains CNAME'd to the platform hostname; see [ADR005-custom-domain.md](ADR005-custom-domain.md) for that flow (edge registration + per-host cert isolation).

## Reconcile generation, artifact identity, and release identity

`App.metadata.generation` is a Kubernetes change/acknowledgement counter, not a deploy id. Every spec update increments it and wakes the controller, including updates that must reconcile in place. The operator computes two versioned SHA-256 identities from the desired spec and persists only their one-way digests:

- `status.artifactFingerprint` covers source/build inputs or the selected prebuilt image. Its resolved OCI reference is persisted separately in `status.artifactImage`, so a candidate can survive pre-deploy requeues while `status.image` continues to name the active healthy release. A fingerprint match lets a repo-backed App reuse that resolved artifact without reading `spec.cloneSecret` or consuming build capacity.
- `status.releaseFingerprint` covers the artifact plus pod/static-publish inputs that require pre-deploy or rollout. `status.releaseGeneration` records the metadata generation that initiated that release and remains stable if later operational generations arrive while it is building or rolling. Backend deploy verbs stamp `app.bex.co/release-generation` in the same spec patch; the operator consumes a newer stamp so an operational mutation racing ahead of the first reconcile cannot detach the build, pre-deploy Job, or deploy-history row from its release.
- `status.conditions[Build]` is the terminal build verdict for one release generation, stamped with `status.releaseGeneration` rather than `metadata.generation` (w6/m100). The Ready condition cannot serve as that record: a second deploy's spec patch can bump `metadata.generation` before the running build resolves, so a Ready-stamped verdict is filed against the wrong generation — which used to make the operator's re-dispatch gate treat the queued deploy as already failed and never build it, stranding the row at `queued` with no automatic recovery. Ready is also overwritten by the next release's progress within milliseconds, so it cannot still explain a resync later why the previous release's deploy row ended. The Build condition is written only on a terminal build failure, in the same status update as Ready, and is what closes that row `build_failed` with its build error rather than `canceled`.
- Operational fields—replicas, suspension, autoscaling policy, cron run/cancel intent, display/notification/auto-deploy/build-filter settings, and routing/allowlist/maintenance configuration—change neither identity. They reconcile against the active image/revision without a build, pre-deploy Job, pod-template change, or deploy-history row.

The classification is exhaustive and test-guarded: adding an `AppSpec` field without assigning deploy semantics fails the operator suite. Build inputs such as repo/ref/runtime/build command change the artifact and release; runtime inputs such as port, health check, tier resources, and pre-deploy command change the release (native builder inputs also change its artifact). `spec.restartedAt` deliberately changes both for a repo-backed standard deploy. A snapshot-backed restart selects the **live artifact and recorded runtime configuration** without rebuilding or applying newer saved command/environment settings (w5/m107). A legacy release without a resolved artifact retains the commit-pinned rebuild fallback from w1/m148; that fallback cannot promise full configuration parity. Secret _contents_ never enter either fingerprint.

Every retained App was normalized to carry artifact and release fingerprints during the w1/m56 fleet migration. A missing fingerprint is now treated like any other missing desired-state identity and enters normal artifact/release reconciliation; the operator no longer infers an identity from an active revision. Operational edits such as replica changes remain no-op releases because their stored canonical fingerprints continue to match.

## Per-release configuration snapshots (w1/m152)

A release's identity is a fingerprint — proof that inputs changed, never a restorable value. Its _configuration_ lived only in mutable objects: one `<name>-env` / `<name>-files` Secret per service, rewritten in place on every save, plus each linked env group's shared `<evg-id>-env` / `<evg-id>-files`, rewritten for every service linked to it. The pod template referenced those by **name**, and kubelet resolved contents at pod creation. So a save changed what a _running_ release would serve on its next pod creation, and canceling the deploy that carried the save could not put the old values back — there were none to put back. A crash-restarted pod of the old release came up with the new values for the same reason.

**Each dispatched release now writes an immutable copy of every configuration source it reads, and its pod template references those copies instead.**

- **One snapshot per source, never flattened.** For release generation _N_: `<name>-env-rN` and `<name>-files-rN` for the service's own maps, plus `<name>-<evg-id>-env-rN` / `<name>-<evg-id>-files-rN` per linked group (`AppReleaseSnapshotName`). The `envFrom` list and the projected-volume source list keep their existing order with snapshot names substituted, so **precedence is unchanged and never re-derived** — it remains a property of list order (groups first, the service's own last, which is what makes a service's own key and file win).
- **Why not one flattened Secret per release.** bex-api's map quotas are **per map**: 512 KiB of env vars (`maxSecretMapBytes`) and 1 MiB of secret-file contents (`maxSecretFilesBytes` = `corev1.MaxSecretSize`, w4/m363). Each sits within Kubernetes' 1 MiB Secret limit, so "a map that passes the quota can always materialize". Flattening a full service map with two full group maps reaches 1.5–3 MiB while every input passed its own quota — recreating the source/projection divergence that quota was introduced to stop. A per-source copy inherits its source's guarantee by construction. The one place sources do merge, a native or Dockerfile build's secret files, is packed into as many `bld-…-native-files` Secrets as its contents need, each within the limit (w4/m363).
- **Retention: a 20-generation window.** This shares the numeric bound of `deploys.eligibilityScanLimit`, but a recent-deploy scan is not proof that every offered target still has a configuration record. The rollback verb accepts an explicitly named target outside that scan. A selected rollback or restart gets its own source copies and record under its new generation, so serving it does not depend on retaining the original target forever. The window is counted back from the release being rolled, which is not the serving one until it serves: the served release's record and copies are exempt until a newer release serves, because a failed or canceled rollout goes back to them and operational edits can put the served release any number of generations behind (w1/123).
- **Missing historical configuration is an explicit limitation.** A target predating snapshots or whose record was reclaimed selects its image only and leaves saved configuration untouched. The dashboard discloses this possibility; the API logs the missing record. This existing Bex fallback is not full Render configuration parity, and no history age or guessed value can reconstruct missing metadata.
- **A shared source is scoped by the reading service.** A group's Secret lives in the workspace namespace and is read by every linked service, while release generations are counted **per App**. The first build named group copies `<evg-id>-env-rN`, which was the _same object_ for every linked service at its own generation _N_. Copy-once then gave the second service the first one's copy — values from a different moment, owned and garbage-collected by the other service (found by t004). The service's own sources cannot collide and keep their names, which bex-api's rollback also reads. An App still projecting a legacy unscoped copy **keeps projecting it**, because switching names would roll it with no deploy. `status.unscopedSnapshotGeneration` marks that generation, and the App becomes a non-controller co-owner of the copy. The service that created the copy then neither garbage-collects nor cascade-deletes it while another service reads it. The App's next release uses scoped names.
- **Lazy migration; nothing rolls on upgrade.** An App serving a release from before snapshots keeps projecting its mutable Secrets until a **new** release rolls out, and snapshotting then rides a rollout that happens anyway (`servingWithoutSnapshots`). A cancel over such a release has no snapshot to restore to, and it stays put too. The first build snapshotted on every pass, which would have flipped and rolled every service. In production it failed instead (t011, below): services in workspace namespaces with any config source failed their reconciles without rolling, and the lazy rule keeps the fix from turning into a fleet-wide roll. Cancel and rollback fall back to prior behaviour for any release with no snapshot.
- **Snapshot Secret I/O is uncached.** The manager caches Secrets for one namespace only (`NamespacedSecretCacheOptions`), and tenant Apps live in workspace namespaces (ADR043). Every snapshot, record and GC call therefore goes through `uncachedSecretClient()`. Through the cache, a new service's first release failed with `unknown namespace for the cache` (w4/171, t011). envtest could not see it, because its Apps live in the cached namespace. The regression test fakes production's cache instead.
- **A standard deploy's build and pre-deploy steps read the saved sources, not snapshots.** They run before that release is snapshotted, while the projection still points at the _served_ generation's copies. Projecting the App as-is handed release N+1's migration release N's `DATABASE_URL`, and a native build release N's build-time env (found by t004). They read the mutable sources, exactly as before snapshots; only serving pods read copies.
- **A first release that never served and failed stops at zero (w1/m179).** Render cancels a deploy whose instances never pass their health check; with no earlier release there is nothing to keep serving. Whichever settle fails it with no ready pod of the current release — the progress deadline (Render's 15-minute window), the startup-crash settle or the permanent image-pull settle — records the failure in the release-scoped `Rollout` condition as well as Ready, and a cached read still on the previous template never stops the new one. Until w4/m351 only the deadline stopped: a crash-settled first deploy read `update_failed` at about 40 s yet kept restarting for 15 minutes, and a crash that cleared went live under the failed row (round 214). **The early pull-failure settle stops too (w4/m351 t002, decision (a)).** Keeping a missing-tag or denied pull retrying after its row closed is the same defect: a pull that clears would serve under a failed deploy, and `update_failed` admits no move out. Render pulls a prebuilt image as part of its deploy and fails that deploy when the pull fails ([Deploy a prebuilt Docker image](https://render.com/docs/deploying-an-image)); a failed deploy is final, and the service runs again only through a new deploy ([Deploys](https://render.com/docs/deploys)). The pre-deploy step already treats the same pull answers as final (its Job is deleted, w8/m49), and `PermanentPullFailure` only matches answers that "arrive with a new deploy" (a fixed tag or credential) after its 90-second grace; transient registry errors keep the deadline. The next pass's plan is `stopped`: the Deployment goes to zero replicas, the phase stays Failed and is never marked Running (a drained Deployment reads as a complete rollout), and the activator answers its host with a plain 503 instead of waking the failed pod. A newer release moves the release generation past the record and rolls. A suspend parks it as usual, and a resume returns it to the stopped Failed state, because there is no successful release to resume. Before this, the pod restarted until the service was deleted (a startup-probe kill every 15 minutes, w8/039). A `ProgressDeadlineExceeded` condition now counts only once the deployment controller has observed the current template: the pass that writes a new release used to read the previous rollout's verdict.
- **A Dockerfile build receives the service's env and secret files, as on Render (w1/m178).** The same saved-source projection a native build mounts reaches a Dockerfile build: each env var as a build arg (`--opt build-arg:K=V`, assembled inside the BuildKit container from the build's own Secret so no value enters the Job spec; literals override Secret keys, as at runtime) and each secret file as a BuildKit build secret under Render's id (`.env` → `_env`, at `/run/secrets/_env`). The env Secret names are deliberately not Dockerfile artifact identity: a new value reaches the build on a rebuild request (`spec.restartedAt`), matching Render's "Save, rebuild, and deploy" versus "Save and deploy", and counting them would have rebuilt every Dockerfile service on the operator upgrade. Contract: [render-artifacts/docker-build-env.md](render-artifacts/docker-build-env.md).
- **Cron jobs follow the same rules.** A run is a pod created from the CronJob's template. The cron path therefore snapshots, records and restores exactly as the Deployment path does. A canceled change used to reach the next run, scheduled or manual (t004).
- **A cancel never runs the canceled release's pre-deploy command.** The served release already passed its own gate. Gating on the spec's command ran the canceled deploy's migration against the served image and held the service in Deploying (t004).

- **A cancel restores the served release's recorded pod template, not just its configuration.** Configuration Secrets are not the only thing a `config_change` alters: the save bumps `spec.restartedAt`, which reaches the template as the `app.bex.co/restarted-at` annotation, and the same deploy can carry a start command, health-check path or plan. Re-projecting the current spec on cancel therefore changed the template — and rolled a pod — even once the Secrets had been reverted; an envtest reproduced exactly that. So every normal pass records the template it applied as `<name>-podtemplate-r<generation>` (same labels, same 20-generation GC, same owner), and a pass settling a cancel over a served release applies that record verbatim. When the Deployment already holds it, nothing is written and nothing rolls. With no record (a release that predates this, or one reclaimed beyond the window) the pass re-projects as before. The record tracks the template the release actually serves; cancellation never overwrites the prior served record with the canceled configuration.

Snapshots are owned by their App (owner reference) so a service delete reclaims them, and they are never written by the control plane — the operator is DB-free, so a release must be restorable from cluster state alone.

### Ordinary Save-only differences (w4/m145)

Service-local Save only preserves the serving release while updating saved variables and files, including the contents of sources the App already references. `undeployedChanges` compares those saved sources and their membership with the active release's recorded configuration. It becomes true when they differ and clears when a successful standard deploy applies the saved values or an ordinary Save-only edit reverts them to the running values. Cancellation retains its broader pending state for plan and pre-deploy settings outside that record until the next successful deploy. A successful save alone is not proof of a difference: no-op writes must not invent pending changes.

This comparison runs separately from runtime reconciliation. An opaque save notification and active-revision changes wake the status controller; configured or pending supported Apps also get a 60-second recheck. The periodic check repairs a save/projection/status race even when a failed write compensates its Secret data without another App event. Status reconciliation does not dispatch a build, change the serving template, or open a deploy record. Read errors retry conservatively, and a post-save legacy release with no retained configuration record remains pending because its original values cannot be reconstructed. No migration rollout is used to manufacture that evidence.

The new comparison covers Deployment-backed web services, private services and background workers, plus CronJob templates. Static sites have a separate publication path without equivalent retained build-configuration records; this change does not establish their pending-status correctness. Postgres and Key Value use separate handlers. Linked-group sources participate in the recorded-source comparison during periodic checks, but group writers gain no new notification path here, and their transaction and rollout guarantees are not re-certified by this fix.

Both dashboard notices read the same authoritative `Server.undeployedChanges` field. Saving refetches that document and the editor's name lists, but the first response can precede reconciliation; success feedback therefore states that the environment was saved without a deploy and explains how to apply any pending changes. The client does not optimistically set the flag, which would misreport no-op and revert saves. An accepted save followed by a failed refresh ends the committed draft and asks the user to reload; it does not invite replaying the patch as a failed write.

Render's [environment-variable documentation](https://render.com/docs/configure-environment-variables#setting-environment-variables), rechecked 2026-10-02, distinguishes saving without deployment, deploying the existing build with saved variables, and rebuilding before deployment. Its [Restart contract](https://render.com/docs/deploys#restarting-a-service) preserves the running configuration, and its [rollback contract](https://render.com/docs/rollbacks#service-specific-config) preserves saved settings for the next standard deploy. `undeployedChanges` and these notices are Bex extensions, not documented Render wire fields. Render's secret-file section documents Save Changes triggering a deploy; the shared three-choice file editor is a Bex extension rather than a published secret-file Save-only requirement.

### Saved settings and selected runtime configuration (w5/m107)

The m152 decision to restore historical environment values and commands into saved state misread Render's rollback matrix. [Render's rollback documentation](https://render.com/docs/rollbacks), researched 2026-10-01, explicitly preserves current settings for the next standard deploy. A rollback selects historical inputs only for the new running release; Settings and environment/secret-file reads continue showing the saved values. The dashboard disables auto-deploy, while API rollback leaves it unchanged.

| Input | Rollback selection |
| --- | --- |
| Build artifact, start/Docker command, health-check path, instance count, service environment | Target deploy |
| Environment groups | Target associations with current values; deleted groups are omitted and shared sources are never rewritten |
| Port (and its port mode), shutdown delay, pre-deploy command | Target deploy (w4/m433). Render's rollback page does not list them; bex selects the target's recorded values, as for the start command. A rollback runs the target's pre-deploy command: whether Render runs one on a rollback is unverified, so this is bex's choice |
| Compute plan, disks, domains, static routes and headers | Current settings |
| External registry image | The target deploy's own reference, as on Render: a tag is pulled again (the operator resolves it as the rollback's release, and the rollback deploy records that digest); a digest runs that exact image; a tag that no longer resolves fails the rollback while the live release serves (w4/m432) |
| External registry credential | Target deploy (w8/m529): the credential that pulled it before, or none when it pulled anonymously. Render's rollback page ([§ Registry-hosted Docker images](https://render.com/docs/rollbacks), read 2026-11-20) says Render "pulls the image again" but not with which credential, so bex keeps the one the target went live with. bex-api refreshes that credential's pull Secret from its stored token first, so a rotated token is used; a credential deleted since leaves nothing to pull with, and the pull is anonymous |

The backend stamps a generation-scoped `spec.releaseConfig` selection instead of rewriting saved image, command or secret data. The operator materializes the selected configuration into the new release's own snapshots and projects it on each reconcile. A normal deploy clears the selection and uses saved settings. `undeployedChanges` reports a saved/runtime difference without attributing it solely to cancellation; a rollback followed by Restart can retain that difference.

New release records include the source membership, literal environment, start and cron commands, health path and replica count alongside the pod template. Since w4/m433 they also keep the port, port mode, shutdown delay and pre-deploy command (`ReleaseRecordSpec.Runtime`). bex-api copies those into `spec.releaseConfig.runtime`, so the operator serves the selected port and runs the selected pre-deploy step from the first pass, and `App.RuntimeSpec` gives every reader the running port. A port mode applies only within its family: a selection never moves a service between configured and image ports. A record written before w4/m433 carries none of the four. A Restart or rollback to it runs the saved values, and bex-api logs that fallback. Older records can recover commands, environment references and probes from their template, but not historical replicas: that field lives outside the pod template. Missing metadata remains unknown rather than becoming an invented default. Secret-file restoration follows the service-owned configuration rule as Bex correctness; Render's published matrix does not specify secret files or pre-deploy-command behavior.

[Render Restart](https://render.com/docs/deploys#restarting-a-service) preserves the running commit and configuration. A snapshot-backed restart therefore selects the live artifact and its recorded configuration, including the group values already running. It does not apply newly saved B settings after an A rollback. Only the next standard deploy applies B in that flow. The running port, shutdown delay and pre-deploy command are kept too (w4/m433): a Restart reruns the running release's pre-deploy command, never a saved one. Render's Restart page does not say whether a restart runs the pre-deploy command at all, so running it is bex's unverified choice. So is the registry credential (w8/m529): a Restart pulls the serving release with the credential it went live with, or anonymously when it had none, whatever the service binds now, since the credential is part of the running configuration. The release record keeps the binding (`ReleaseRecordSpec.Registry`; a record written before it reads the binding from its adopted spec, and one with neither pulls with the saved binding), bex-api carries it in `spec.releaseConfig.registry`, and `App.ReleasePullSecret` gives the Deployment, the pre-deploy step and the image metadata read the same Secret. Each credential materializes into its own per-App Secret, `<app>-registry-pull-<credential id>`, so a later switch, failed or only saved, never rewrites the one a serving release pulls with: a reschedule, eviction or wake of the serving release keeps pulling with its own credential too. On production a failed switch to a bad Docker Hub credential used to leave Restart failing on Docker Hub's 401 until the binding was cleared by hand (w8/353). Historical autoscaling settings, and Restart after canceled plan/disk changes, are not established by this milestone; do not extend the claim beyond the recorded fields. Cancellation continues to restore the prior served template; rollback must not blindly restore that entire template because doing so would also revert current plan and disk settings.

### Settings saves wait for a deploy (w8/m135, 2026-10-29)

[Render's Update Service API](https://api-docs.render.com/reference/update-service) saves and deploys nothing: "Changes will not be deployed automatically. Instead you must call the deploy API to have changes pushed out to your service, irrespective of the `autoDeploy` option." bex now matches it. This replaces the w6/m51 rule that every release-relevant settings write rolls a tracked deploy at once, which had no ADR018 sign-off.

- **REST `PATCH /v1/services/{id}` (and the pinned CLI's `services update`) and MCP `update_service` save only.** Every release-relevant row of the shared op table (`ApplyServicePatch`) runs under `rollout.WithSaveOnly`. That covers health check path, shutdown delay, pre-deploy command, start/Docker/build commands, root dir, Dockerfile path and context, runtime, port, cron command and publish path. The edge-cache profile is not among them: it is operational since w3/m486, so a save applies at once on every surface and opens no deploy ([§ Edge caching](#edge-caching-w5m151)). `rollout.Snapshot.Stamp` then holds the change the way it holds a write on a suspended service. It sets `app.bex.co/pending-source-generation`, stamps no release generation and opens no deploy row. Source changes were already held this way (`SetSourceAndRegistryCredential`), and env vars too (w8/186). The audit/config-changed event is still recorded. **The first release consumes a save made before its source is fixed (w21/051).** A service that has served nothing has no active release to keep rendering, and its creation already requested a deploy. A save made after that request but before the build starts (a branch, a health check path, a Docker command, created then patched within seconds, the standard IaC, CLI and agent sequence) is the deploy the hold was waiting for: the operator does not hold it (`firstReleaseReadsSavedSource`), the first release builds from the saved spec, and its deploy row reaches a terminal state. Holding it left the App with no phase, no build and the first deploy row "created" until another deploy was requested. Once the build starts, the release keeps its own source, and a service that has served or failed keeps the contract above.
- **Plan is the exception and deploys at once,** as a plan change does on Render (a resize). When a PATCH carries a plan with other fields, the one release the plan opens carries every field saved so far. Its row is a `settings_change` deploy and its stamp reaches the pending generation. Name, `autoDeploy` and the other operational fields stay operational: no deploy either way.
- **The operator keeps serving the release it runs.** While a saved change is pending, the pass runs on `pendingReleaseView`: the current release's adopted spec, viewed through the saved spec's operational fields. Template, Service port, probe, shutdown delay and command stay the release's own, and no pre-deploy runs. Each release record now keeps the spec the release was adopted with (`adoptedSpec`, written once while the saved spec is still that release's, w8/m121's key). A release with no recorded spec, one that predates this change and has had no template write since, falls back to projecting the saved spec as before.
- **`undeployedChanges` reads true until the caller deploys.** The status comparison now checks the served record's settings fingerprint whenever the record carries one. Fields outside the record's selected values (plan, pre-deploy command, shutdown delay, build settings) therefore count as well as the recorded probe, command and environment. Saving the running value again leaves nothing pending.
- **The next deploy applies everything together.** A manual deploy, deploy hook, autodeploy commit, or a Blueprint sync that changes the service stamps a release generation at or past the pending one. The operator then adopts the saved spec in one release, which runs the saved pre-deploy command and rolls the new template. A cancel of that deploy restores the served template and leaves the settings pending. Restart and rollback keep their w5/m107 selection: they run the selected release's recorded settings, so a pending save stays pending through them.
- **A failed build changes none of this (w8/289, 2026-11-12).** A failed build leaves `status.releaseGeneration` on its generation, and a save skips `buildFromSource` and its failed-build hold. The pass then dispatched the serving image under the failed generation's revision. For a web, private or worker service that was a new pod template: the save replaced the serving instance with no deploy, raised a false `server_failed`, and on a pre-deploy service ran the failed release's pre-deploy step. `resolveDeployImage` now sends a pending save whose release revision is not the active one to `holdPendingArtifact` whenever the latest build failed, for every service type, as w32/003 already did for static sites. The serving pods stay byte-identical until a deploy, and that deploy builds the saved spec as usual.
- **Dashboard Settings keep saving and deploying,** explicitly. The GraphQL setters behind the Settings page are not save-only: each save opens one `settings_change` deploy, and the rows that say so ("Saving starts a new deploy") stay true. Adding Render's per-save "Save only" choice to the Settings page is a separate follow-up. It does not change the API contract.
- **Restart and rollback leave a pending save pending (w4/m433).** Their selected record supplies the start command, health path, environment, instance count, port, shutdown delay and pre-deploy command, so a saved but undeployed value does not go live through them, and `undeployedChanges` keeps reporting it (reason `historical_release`) until a standard deploy. Before w4/m433 the shutdown delay, pre-deploy command and port came from the saved spec, so a Restart shipped a saved port.

Static sites restore the target's retained publication (w4/m197): the operator records each successful publish's object-store prefix per generation, and rollback copies that prefix into the new revision. The target's image is not re-extracted through today's publish directory, and nothing is rebuilt from today's build command. A target with no recorded publication is refused with a named 409 before dispatch. Current static routes/headers and saved settings remain intact, and dashboard rollback still disables auto-deploy. Details are in [ADR029](ADR029-static-sites.md).

## In-cluster builds (BuildKit/kpack → Zot)

Setting `App.spec.repo` builds the image **on the cluster**, so there is no laptop step and no docker daemon (app nodes run containerd). When the operator reconciles a repo-backed App whose revision changed, it:

1. Names the build `bld-<name>-gen-<release-generation>` in `BEX_BUILD_NAMESPACE` and selects the mechanism from `spec.builder`.
2. A Render-native language runtime (`node`, `python`, `go`, `ruby`, `rust`, or `elixir`) selects the internal `native` strategy. The operator generates a language-toolchain Dockerfile, runs the exact `buildCommand`, and records the exact `startCommand` as the image command. Literal and OpenBao-backed service env is available to the build through a BuildKit secret and is not retained in image metadata.
3. `docker`, `auto`, and `dockerfile` dispatch a Kubernetes Job with serial clone, BuildKit, Skopeo-push, and optional Cosign phases. Clone stages the selected branch into an `emptyDir`; BuildKit consumes that local context, keeps its default process sandbox inside `hostUsers: false`, and exports an OCI archive without the output credential. Render's optional Docker Context, Dockerfile Path, and Docker Command map to `rootDir`, `dockerfilePath`, and the workload command override.
4. The explicit bex `buildpack` extension creates a `kpack.io/v1alpha2` Image using the GitOps-managed Paketo `ClusterBuilder` (`bex`). kpack clones `repo`/`branch`, honors `spec.rootDir` as `source.subPath`, and receives literal `BP_*`/`BPE_*` App env vars as build-time configuration. Secret-backed runtime env is never copied into the Image CR.
5. The selected pipeline pushes the release-generation tag to Zot. BuildKit output is pushed by credential-isolated Skopeo; kpack pushes through its Image controller. The App-scoped Zot identity can write only its own output repository and read the shared, platform-owned `bex-cnb-builder` repository; only `bex-builder` can write that builder repository. In local HTTP clusters kpack uses `BEX_KPACK_REGISTRY=zot.local:5000`, an alias for canonical `BEX_REGISTRY=zot.bex-registry.svc:5000`; the operator rewrites the successful digest back to the canonical name before workload rollout.
6. The operator waits for Job completion or kpack's Ready condition, records the resolved digest in App status, and runs that immutable image. Failure conditions include the underlying Build reason/message.

The tag is the App's **release generation**, so a genuine deploy—including a webhook redeploy that stamps `spec.restartedAt`—gets a new build and re-pull, while manual scale and other operational changes retain the current tag and image. The tag alone is **mutable across incarnations**—delete + recreate of the same App name resets to release generation 1 and re-pushes `gen-1`—so after every successful build the operator resolves the tag it just pushed to its immutable manifest digest (`HEAD /v2/<repo>/manifests/<tag>`, with the App's own per-App registry credential) and records `<repo>:<tag>@<digest>` in `status.artifactImage`. The candidate reference is used by pre-deploy and rollout; only after the release is healthy does `status.image` advance to it (w9/013). A node's stale tag cache can then never serve a previous incarnation's bytes, and rollback's `resolvedImage` restore target pins the exact build. Resolution failure logs and falls back to the tag (dev clusters where the operator can't reach the registry). Config: `BEX_REGISTRY` (canonical Zot host), optional `BEX_KPACK_REGISTRY` (kpack-only endpoint alias), `BEX_CNB_BUILDER` (the builder imported into the `ClusterStore`/`ClusterBuilder`), and `BEX_BUILD_NAMESPACE` (production: dedicated `bex-build`; unset: the App namespace). The operator has `batch/jobs`, `kpack.io` Image/Build, and namespaced build-credential RBAC. `scripts/registry-secrets.sh` creates the bootstrap docker config; the operator mints App-repository credentials, while BuildKit receives only an explicitly selected private-base credential.

## Pre-deploy command (gate a rollout on a migration) — w1/m33

Setting `App.spec.preDeployCommand` makes the operator run that command **to completion against the new revision's image before the Deployment rolls to it** (Render's Pre-Deploy Command — typically a database migration). This is real health-gating, not a cosmetic field: the rollout waits on the step, and a non-zero exit **fails the deploy and leaves the previous revision live and serving**.

Mechanism (`internal/predeploy`, dispatched from `reconcileKubernetes`'s `reconcilePreDeploy`), mirroring the build plane's Job-and-poll shape but with deploy-safe differences:

1. The operator runs the command as a Kubernetes **Job** (`predeploy-<name>-gen-<release-generation>`, in `BEX_BUILD_NAMESPACE`) whose single container **is the new image**, launched by the same rule as the service's Docker Command (`shellCommand`, w8/172: `sh -c <script>` runs its script, a plain command is exec'd so a shell-less image can pre-deploy, shell syntax keeps `/bin/sh -c`), and a native or buildpack service keeps the absolute platform shell (`/bin/sh -c <command>` — absolute because the runtime resolves a bare program against the app's own PATH, which may be empty or narrow; w8/m61); a program the runtime cannot start fails the step naming it (`StartError`), with the **same env, envFrom (the `<name>-env` Secret a migration reads `DATABASE_URL` from), image-pull secrets, security context, tier resources, and `/etc/secrets` volume** as the app pod — so a migration runs against exactly what will serve. When `BEX_BUILD_NAMESPACE` differs from the App namespace, the operator first relocates what the pod references there (w9/012): the env/secret-file Secrets are mirrored beside the Job, a platform-registry image pulls with the build-namespace credential (`BEX_REGISTRY_BUILD_PULL_SECRET`), and a foreign image's external pull secret is copied across.
2. It **never retries** (`BackoffLimit 0`): re-running a partially applied migration can corrupt data, so a failed pre-deploy is terminal until the user pushes a new revision. A bounded `activeDeadlineSeconds` reaps a hung migration as failed.
3. The operator observes the Job **non-blocking** — one `Get` per reconcile, then `RequeueAfter` — so the App CR reports the step `Running`/`Succeeded`/`Failed` on `status.preDeploy` while it runs; the Deployment is **not created or updated** until the step succeeds, which is what keeps the old revision live.
4. The step is gated **per release generation**, so it runs once per rollout, exactly like Render, and never runs for scale/routing/suspension or re-runs a migration that already passed or failed for the same revision (which also guards against re-creating the Job after its TTL reap).

Skipped when there is no rollout to gate (suspended / auto-hibernating, both scaling to 0) and for `cron_job`/`static_site` (a cron runs its own `command`; a static site has no running container). Unset `preDeployCommand` is byte-identical to prior behavior — no Job, no gate. It runs on every release, the first included: a Blueprint's one-time `initialDeployHook` is a separate command that runs after the first release is live and never in the step's place (w33/m435, [§ Initial deploy hook](#initial-deploy-hook-once-after-the-first-release-is-live--w33m435)).

The step's outcome and logs are visible on the deploy record: `preDeployStatus` (`internal/store`/`internal/deploys`) distinguishes a migration failure from a health-check failure, and the `predeploy` log type ([ADR006](ADR006-bex-api.md), [ADR010](ADR010-observability.md)) reads the Job pod's logs, each record labelled `type: predeploy`.

**Malformed image references (w8/m49).** Public create/update/Blueprint/deploy inputs are rejected by the shared image grammar and registry-policy validator before mutation. For legacy or directly applied CRs, kubelet `InvalidImageName` fails a rollout or pre-deploy step immediately with the kubelet's reason; retrying cannot repair the reference. Rollout diagnosis only considers the desired revision's non-deleting app pods, and pre-deploy diagnosis requires the exact Job owner UID and command container. A failed pre-deploy Job is deleted before failure is recorded, preserving the serving release and preventing a late command execution. Missing-image and denied-authentication pull errors still get their 90-second grace, while transient network/registry failures retain their existing deadlines.

**A failed step is a deploy fact, not an outage (w1/m149).** The step runs before the rollout, so when it fails over a released image the previous release never stopped serving: the phase stays Running (Hibernated when parked) with Ready describing the serving release, exactly as w6/m124 settles a failed build. Only a first release whose step fails reads Failed. `status.preDeploy` is the durable, release-generation-scoped verdict, and its message — built from the Job pod's terminated container ("exited with code N", an out-of-memory kill, or the 30-minute deadline, each pointing at the pre-deploy logs) — is what bex-api closes the `pre_deploy_failed` row with. Reading it from `status.preDeploy` rather than the Ready condition keeps the reason correct when `metadata.generation` has moved past the condition, and when Ready describes the prior release.

**The step never receives traffic (w4/m181).** Both stable serving Services, the CR-named one and the slug alias, select `app.bex.co/app` **and** `bex.co/app-id`. Only the runtime pod template carries the second label; pre-deploy, build and disk-backup Job pods carry only the first. Before this, a ready pre-deploy pod with no listener joined the EndpointSlice, and while a migration ran, a share of public requests to the still-serving previous release answered 502 (live 2026-10-08: six of twelve). The Deployment's immutable selector is unchanged, and image-port Services keep their revision constraint while a port change rolls; a same-port rollout selects every runtime pod so the replacement is an endpoint before the old pod drains (w4/m243 t012, ADR089). Every runtime pod has carried `bex.co/app-id` since 2026-07-16; a read-only production check on 2026-10-08 found only a finished build pod without it. Render runs pre-deploy before starting the replacement and documents a zero-downtime handoff; its selector internals are not claimed.

**A cancel lets a running step finish, and the deploy records how it ended (w5/085).** Canceling a release does not stop a pre-deploy Job that is already running. That covers both the user's Cancel and a suspend that ends the rollout (w5/m114). A migration stopped halfway is worse than one that finishes, which is also why the step never retries. Nothing gates on the step any more, but the operator keeps reading its Job until it ends. It records the verdict on `status.preDeploy` under the canceled release's generation, and the verdict neither fails the service nor rolls the release. bex-api then replaces the `canceled` that the deploy's close settled onto the still-running step with that verdict, and records the step's `pre_deploy_ended` event. The deploy still reads canceled, while its pre-deploy step reads succeeded or failed. A step keeps `canceled` only when it was stopped (a newer release's step supersedes it) or when its Job was gone before anyone read it.

**The deploy page's log window follows that step to its end (w4/m198).** The step's last success or error line lands after the deploy's `finishedAt`, so the dashboard's default deploy window for a canceled deploy whose step reads succeeded or failed runs from `createdAt` to the later of `finishedAt` and that deploy's own `pre_deploy_ended` fact (matched on `details.deployId` through the typed, cursor-paged `serviceEvents` read, inclusive of the fact's whole second). `finishedAt`, duration and every API adapter keep meaning the cancellation. While a canceled step may still be running, the detail page keeps polling the deploy for the Job's bounded lifetime so the window widens when the verdict lands. A missing fact or a failed read keeps the cancellation bound and says so, with the relative ranges as the escape hatch. Render documents no equivalent post-cancel window, so this is bex's own policy rather than a parity claim.

**A held release does not freeze the serving one (w1/m156).** "Not created or updated until the step succeeds" applies to the pod template, not to the prior release's runtime.

- **The invariant.** While a prior release serves, the template advances only to a release whose pre-deploy step passed. A newer release is held while its step is pending, running or failed.
- **While it is held**, the pre-deploy hold (`actGate`, or `actHoldStep` once the step failed or while the pass parks) and `convergeServingRuntime` keep the prior release converging:
  - a replicas-only patch of the existing Deployment, so a wake, hibernation, suspend, resume, manual scale or autoscale still lands;
  - the Ingress routed to the activator or to the prior release's Service, on the port that Service exposes, rewritten only when the scale changed or the live route differs;
  - for a failed step, the phase settled from the scale that pass wrote: Running once awake, Hibernated while parked.
- **Parking.** A suspended or auto-hibernating pass still does not run the step, and it no longer writes the held release's template onto the parked Deployment either.
- **Before m156** the gate returned before every runtime write:
  - a free service parked over a failed pre-deploy answered `503 service hibernated` indefinitely while reading Running;
  - a parking pass baked the unmigrated release into the template, so the next wake would have started it.
- **Unchanged:**
  - a first release (nothing serves yet);
  - a fresh step failure, which still returns its reconcile error.

**A failed rollout goes back to the served release's template (w1/m172).** A release whose step passed does reach the pod template, and its rollout can still fail (a crash, a failing health check, an image that cannot be pulled).

- **Why the template cannot stay.** Awake, the Deployment keeps the old ReplicaSet's pods, so the prior release serves. Parked, both ReplicaSets sit at 0, and the next wake, resume or scale starts the newest template: the failed one. Nothing becomes ready, the route stays on the activator (`503 service hibernated`), and the phase used to read Running from the desired scale.
- **At the verdict** (`ConditionRollout` false for the release generation, over a release that served), `settleFailedRolloutMessage` restores the served release's pod template: its recorded template (the w1/m152 release record), or the template of the ReplicaSet the Deployment still retains for it when there is no record.
- **Afterwards** the failed-rollout hold (`actHoldVerdict`) keeps the failed release off the template and `convergeServingRuntime` keeps the served release's replicas and routing following the App, exactly as for a held pre-deploy step. A background worker is held the same way.
- **The hold ends** when a newer release is requested: the release generation moves past the verdict and that release rolls normally. The failed deploy stays `update_failed`; waking never retries it.
- **Nothing to restore from** (no record and no retained ReplicaSet): the phase settles Failed with the rollout's own reason, never Running.
- **Unchanged:** a rollout that fails within the served release's own generation (its record is the template that failed), and a first release.

**A release that has not served is never started alone from zero (w1/m172).** Scaling a Deployment up is not a rollout: Kubernetes raises `ProgressDeadlineExceeded` only for a template change in progress. With a newer template already on a parked Deployment, a wake starts only that template's pods, and one that cannot become ready leaves the service on the activator with no deadline and no verdict to restore from (live: `503 service hibernated` for 22 minutes and counting, phase Deploying).

- **Parked**, `actHoldParked` keeps the served release's template on the Deployment: a deploy made while the service sleeps does not reach it, and a park that lands mid-rollout puts the served template back.
- **Waking** (or resuming), the served release's pod starts first, behind the activator, with the phase Deploying.
- **Once that pod is ready** the normal path rolls the newer release over it as a rolling update: the served pod keeps serving until the new one is ready, and a failure reaches the progress deadline and the restore above.
- **A served release that can no longer start** does not block the release that might fix it: once it has been unavailable for `servedWakeBudget` (5 minutes) the newer release rolls anyway.
  - **The clock is the Deployment's `Available` condition, not pod age (w5/m123).** Pods its ReplicaSet cannot create (the workspace quota, the image-signature webhook after a key rotation) never exist to age, so a pod-age clock never started and the newer release, possibly the fix, was held indefinitely.
  - **The cause is named.** While the Deployment reports `ReplicaFailure`, Ready reads `ServedReleaseCannotStart` with its message, and bex-api shows it as the deploy's stall reason instead of ordinary progress.
  - **The same bound holds awake.** A paid service whose only pod is unready holds a newer release, perhaps the hotfix, at most 5 minutes after it lost availability. A pod that was just replaced does not restart the clock.

**A rollout in flight is not idle (w6/m147).** The free idle window equals the rollout budget (15 minutes), and a deploy is not traffic, so with no requests a park used to land before the progress deadline. It overwrote Ready with `AutoHibernated` and nothing settled the rollout, so the deploy closed with the generic health-gate line although the operator had named the crash (`exit code 127`) or the failing probe.

- **Deferred park.** `awaitingVerdict` keeps an idle App awake while the current release, newer than the served one, is on its awake Deployment without a `Rollout` verdict. The rollout goes live, or `settleFailedRollout` records the diagnosis on `Rollout` and the served template returns before the App parks. Bounded by the progress deadline plus `rolloutVerdictGrace` (2 minutes). A manual suspend still parks immediately and puts the served template back.
- **The deploy row keeps its diagnosis.** bex-api does not clear an open row's `stallReason` while Ready carries a park reason (`AutoHibernated`, `Suspended`). An `update_failed` close reads the `Rollout` verdict, then a current Ready diagnosis, then the row's last `stallReason`, and only then the generic line.

**A program that never started is not a crash (w4/m177).** A crash loop whose last termination is the runtime's `StartError` means the container's program could not be launched at all: it never ran, wrote no logs, and its exit code 128 is the runtime's. The stall reason keeps the `CrashLoopBackOff` condition reason that bex-api's consumers admit, but its message says the container could not start. It names the program when runc's `exec: "<program>": …` shape identifies it (missing, not executable), and it never passes the raw OCI text through. A missing `/bin/sh` points at the Docker Command, which bex runs as `/bin/sh -c` on Dockerfile and prebuilt-image services, and tells the user to clear it or pick an image with a shell. Ordinary crashes keep the exit-code, logs and `$PORT` guidance. The same message reaches the open deploy's `stallReason` and a terminal `failureReason` on REST, GraphQL, MCP and the dashboard. Render documents command overrides but not this failure's wording, so no Render copy is claimed.

**The Docker Command is exec'd the way Render runs it (w6/077, 2026-10-19; w8/164, 2026-10-21).** Render uses no shell: it splits words shell-style, removes quotes, and rewrites `$VAR` to Kubernetes' `$(VAR)`; for `<program> -c <rest>` it passes the rest verbatim. bex's `shellCommand` (`shell_command.go`) follows that for every Docker Command, pre-deploy and cron command: a command that begins with a shell and `-c` runs that shell with everything after `-c` as its one script (Render's documented `/bin/sh -c python manage.py migrate && gunicorn …` form, which the old extra wrapper silently broke by making `python` the inner script; a script that is one quoted word is unquoted, which Render does not do); a plain command (no unquoted shell syntax) is exec'd directly, so shell-less images (`scratch`, distroless, `traefik/whoami`) start; and a command that needs a shell (`&&`, `|`, `;`, `$VAR`, redirection, globs, a leading `NAME=value`, an unbalanced quote) keeps running through `/bin/sh -c`, so existing services keep their meaning. Divergence that remains: a bare chained command without an explicit shell works on bex and not on Render. Release records written before w8/164 hold the old `/bin/sh -c <command>` form and are still recognized. Evidence and the comparison table: [docker-command.md](render-artifacts/docker-command.md).

**A prebuilt image runs its Docker Command whatever build settings it retains (w4/m202).** Switching a native or buildpack service to Existing Image keeps its runtime, builder and root directory for a later switch back (ADR026), and the operator used to read that retained builder as "native", leaving the saved Docker Command out of both the Deployment and the cron fallback: the image's default process ran instead (BusyBox exited 0 in a loop, HTTP 503). One decision (`shellRunsStartCommand`) now serves both projections. When the saved source is a prebuilt image and that image is what the release runs, the command is the `/bin/sh -c` override. A native or buildpack artifact still served while an image switch is only staged keeps its baked command. A selected release (Restart, rollback, environment reuse), and the served artifact a staged source switch keeps running, keep the launch their recorded app container shows: no override for a native artifact, the shell override for an image one, whichever way the saved source has since moved. A record that cannot show it falls back to the saved source. That includes a command-less record of the saved prebuilt image, which pre-fix operators wrote for exactly this bug. Cron's explicit `command` still wins. The launch travels as a typed projection parameter, never an App annotation, so a CR edit cannot steer it.

**A switch to a prebuilt image keeps only a command that already was a Docker Command (w8/m461, 2026-11-17).** The native Start Command and the Docker Command share `spec.startCommand`, so the operator cannot tell them apart; w4/m202 runs whatever the field holds. A native Node service switched to an image therefore ran `node app.js` as the image's command, and the deploy failed with `the startup program "node" does not exist in this image`. The source writer (`sourceFields.applyTo` → `settleSourceSwitch`, shared by REST `PATCH image`, GraphQL `setImage` and MCP `update_service`) now drops, on a switch from a build to a prebuilt image:

- the build command, which an image service refuses (w4/418);
- a start command the build baked into its image: a native or buildpack build's, a native cron's, and a native build source's, with a linked cron's `command`. The source writer reads the carrier to tell (`linksNativeBuildSource`); one it cannot read counts as native.

A Dockerfile build's start command is already its Docker Command (`envSpecificDetails.dockerCommand` on both sources) and carries over, as does a Docker or image build source's `dockerCommand` (w3/069), and so does a cron's explicit `command` override, which already ran through the shell. A command sent with the switch (`--image … --start-command …`, or `dockerCommand`) is written after the source and runs as the Docker Command. A Blueprint switch follows the same rule for a service that builds itself (w8/m70). A Blueprint that moves a linked service to an image keeps its command, since a sync does not read the carrier. The runtime, builder and root directory stay for a switch back, but the dropped commands are not kept: a switch back to Git needs its start command again, as a fresh native service does. The reads follow the source: a service whose saved source is a prebuilt image reports runtime `image` on REST, GraphQL and MCP whatever runtime it retains (`core.EffectiveRuntime`), and a switch back reports the retained runtime again.

**An update cannot leave a native build without the commands it needs (w32/052, 2026-11-20).** A native build needs its build command and, unless it is a static site or a build source, its start command. Create refuses a native runtime without them (`400 native runtime <rt> requires buildCommand and startCommand`, w2/m254 t016), and the operator fails every build of such a service at dispatch (`validateNativeOptions`). An update used to save that state: clearing either command (`bex services update --build-command ''`), or switching an image service back to a repo its kept native runtime builds, after the switch to the image dropped the commands (above). Every later deploy then failed one second after it was queued. An update now gets create's answer when it leaves a native build missing a command it had (`checkNativeCommandsKept`). REST `PATCH` and MCP `update_service` judge the finished patch once, after every row, so a switch back that sends the repo and both commands in one update saves (REST `repo` with `serviceDetails.envSpecificDetails.buildCommand` and `startCommand`). The pinned Render CLI cannot send that update: it refuses `--build-command` and `--start-command` on a service whose runtime reads `image` before any request (`pkg/service/update.go`), so `bex services update` has no route back to Git for such a service yet (w32/056, seen on production 2026-11-20). GraphQL `setBuildCommand`, `setStartCommand`, `setRepo` and the other source setters judge their own change, and `setRepo` takes `buildCommand` and `startCommand` for the switch back, which the dashboard's Update Source dialog asks for when an image service's builder is native. A gap the update finds and leaves refuses nothing, so a service saved missing a command before this check still takes its other settings, and each command one save at a time. A native cron's blank start command still drops only its command override (w8/m69), and a static site with no runtime still publishes its files as they are when its build command is cleared (w8/m59); one pinned to a native runtime builds natively and keeps its command.

**A switched service serves the port its image binds (w8/m504, 2026-11-19).** The switch keeps the service's port mode, `configured-v1` for a native service, and the stored default port 10000. Stamping an image port mode when the switch is saved would re-project the native release that still serves, since the operator reads the mode from the saved spec, and the mode is release identity ([ADR089 § Port slice decisions](ADR089-render-container-compatibility.md), item 7). The switched release's first deploy finds its port instead: its check of 10000 fails, the operator scans the unready instance, and after two scans that agree it records the listener as `status.detectedPort` and serves, routes and probes on it, `PORT` staying 10000. A web service takes its lone HTTP listener (w8/177, `nginx` on 80); a private service takes any listener, 3000 if open, else the lowest (`redis` on 6379). `port` and `openPorts` then read as an image-created service's; before that deploy they read the native release's 10000.

**A port edit follows readiness (w4/m182).** A configured-port App's container port is named `bex-http`, and both stable Services (CR-named and slug) target that name rather than a number. A numeric `targetPort` moved to an edited port the moment the Service was written, while the ready old pods still listened only on the old port. Live, each port edit gave more than 12 seconds of public 404/502. By name, kube-proxy and the ingress resolve each pod's own listener: old pods keep serving on the old port until the new ones are ready, then traffic follows readiness. Pods projected before the name existed would drop out of a named Service, so while any live pod lacks the name, the Service keeps that pod's numeric port; the next rollout adopts the name. The Service port number is still the configured port, so `<slug>:<port>` internal addresses and Ingress backends behave as before. Image-port private services (`portMode: image-v1`) already use named ports with a revision constraint and are unchanged. Local replay on 2026-10-08 (kube-proxy, a 120-sample port edit): numeric target had 41 failures, named had none. The Traefik path is covered by the live closeout. Render's documented handoff keeps the old instance serving until the new one is ready; a mutable port field is a bex extension.

**A deploy wakes a sleeping service (w6/076).** Parked, the holds keep a newer release off the Deployment until a wake. With no traffic no wake came, and bex-api closed the deploy at its gate with the health-gate line though nothing had rolled. A Render deploy is live only once the new instance passes its health check, so a deploy is activity. The wake (`actWake`) stamps `last-active` on an auto-hibernated App with a newer release that has not served, and records the generation in `app.bex.co/release-wake-generation`, so each release wakes the service at most once. A suspended App, a release whose rollout or pre-deploy already failed, and a release that already woke it stay parked. The single wake is a deliberate bound: a release whose pre-deploy step or served-pod start outlasts the idle window parks again and waits for a request, as before.

**The lifecycle is one decision per pass (w5/m123).** The fixes above each added a branch, and each branch re-derived the same answers: whether the pass parks, which release the Deployment carries, whether the served release's runtime is still there.

- **One read, one decision.** `observeRelease` reads the Deployment and the Service once. `planRelease` decides from those facts alone whether the pass parks, whether it may stamp Deploying, and its act: roll, wake, run the pre-deploy step, hold on a failed step, a failed rollout or a parked Deployment, or start the served release first.
- **The holds execute the plan.** An executor that learns a fact mid-pass, a step that passed on this pass or a served template with nothing to restore from, records it and carries out the act planned from it.
- **Every invariant is checked.** `release_plan_test.go` runs `planRelease` over every combination of facts and checks the rule each fix established. Reverting any one of them inside `planRelease` fails the rule it names.

**Background workers are held the same way (w1/m158).** A worker has no Service, Ingress or auto-sleep, but its replicas follow resume, manual scale and autoscale.

- **Both holds now apply.** The pre-deploy hold and the build hold below both move a held worker's replicas on the prior release's template.
- **Before m158,** a resume or a scale over a pending, running or failed pre-deploy step or build waited for a new release. Suspend still parked a worker, because the gate is skipped while suspended, but that pass also wrote the held release onto the worker's pod template.

**A release without an image does not freeze the serving one either (w1/m157).** A build halts the pass before the runtime, so the same gap existed one stage earlier. While a newer release's build was queued, running, waiting on a registry credential or failed, the prior release could not wake, sleep, resume or scale. On production a resume over a failed build answered `503 service hibernated` for minutes while the service read Running.

- **The hold.** `resolveDeployImage` hands a build halt to `holdPendingArtifact`. It runs `planReplicas` (the replica plan, then the disk lifecycle, so a restore still wins) and then `convergeServingRoute`: the same replicas-only patch and Ingress convergence as above.
- **A recorded build failure** settles the phase from that scale (Running or Hibernated). The Build condition stays the verdict.
- **A build in flight** keeps its Building phase and its own poll. A parked pass scales and routes, then returns the build's requeue, because nothing watches build Jobs. That phase pins the release to its build (ADR060 §D1a). A pass observing a build therefore returns a routing or disk error without recording Failed, which would release the pin and let a newer push start a second build.
- **Polls stay cheap.**
  - **Awake.** A held pass on a build's or pre-deploy step's few-second poll runs only the disk-restore gate. It rewrites the Ingress only when the scale changed or the route differs.
  - **Asleep.** A service already asleep skips the replica plan entirely, including the traffic query, until a request stamps last-active.
  - **Every other held pass** (a recorded failure, a suspended App, an event) converges the slug Service and the execution-policy removal, and rewrites the Ingress with its middlewares. Custom domains and IP allow-list edits made while a release is held therefore apply, including over a failed pre-deploy step.
- **Suspended.** A suspended App reuses its serving image instead of building. That pass now parks through the hold, and no longer writes the unbuilt release's config onto the parked template.
- **An image refused before dispatch (w32/m419).** An image-port service reads its release's image metadata before it dispatches anything. When the registry refuses that read (a tag that does not exist, a refused credential, an image without the hosting platform) over a release that served, `failBeforeDispatch` records the Rollout verdict (w4/533) and then holds through `holdPendingArtifact`, so the serving release keeps following the App like a held build.
  - Before, every later pass re-read the refused image (`reusableArtifactImage` returns the release's per-deploy image, or the saved one) and stopped at the refusal. An IP allow-list, a suspend or a workspace rule saved after a typo'd tag was never enforced until the next deploy went live.
  - That verdict makes the release final: a dispatch would only hold it off the pod template (`actHoldVerdict`). So a later pass that finds it recorded (`imageReadFailureRecorded`) goes straight to the hold, without reading the registry again. A save after the refusal holds as well, as w8/289 holds one after a failed build. The next deploy is a new release and reads its image afresh.
- **An image read waiting on the registry (w32/031).** A 429, a 5xx or a failed request is not a refusal: the deploy waits and retries (`imageRegistryWait`, w4/m243 t008), from 30 s up to 5 minutes a pass, for up to 15 minutes (the rollout budget) from the wait's first failed or turned-away read, recorded in `status.registryWait` so a manager restart does not restart it. Past that the release fails as `ImagePullFailed` with `image_registry_unreachable` ("the registry {host} did not answer the read of the image {image} for 15 minutes…") while the previous release keeps serving, as Render fails a deploy whose image "is no longer available or reachable" (w4/692). The bound counts from the wait, not the release: a git-built image's release starts before its build. Render documents no registry timeout of its own. That wait used to return before the hold above, so a setting saved meanwhile did not reach the serving release until the registry answered.
  - Over a served release, the wait now holds that release like a build in flight (`holdServingRelease` with `open`). Each pass converges the shared children, the Ingress with its middlewares, and the replicas, so a suspend parks the service. The phase stays Deploying with the wait's stall message, which pins the release (ADR060 §D1a). No verdict is recorded, so the deploy row stays `update_in_progress` and the release still rolls once the registry answers. A suspend still ends that deploy, as it ends any rollout (w4/m171).
  - The pass comes back at the wait's cadence, not the serving release's, so the registry is read no sooner than before. A save comes back at once through the watch.
  - A read the gate turned away (`registryBusyError`) keeps a rate-limited wait's own reason and message, so the stall stays `ImageRegistryRateLimited` on a save's pass, not the generic wait.
- **Unchanged:**
  - a first release;
  - cron jobs and static sites;
  - a build failure recorded only in the legacy Ready marker (written before w6/m100). It stays on the halt, so no status write can erase the marker and dispatch the build again.

## Initial deploy hook (once, after the first release is live) — w33/m435

A Blueprint's `initialDeployHook` (`App.spec.initialDeployHook`) is Render's one-time command. Render's Blueprint spec ([render.com/docs/blueprint-spec](https://render.com/docs/blueprint-spec#initialdeployhook), read 2026-11-16) says: "Web services, private services, and background workers only. Render runs this command after a service's _first_ successful deploy. Useful for one-time initialization tasks such as seeding a database or downloading files to a persistent disk." and "This command runs only once per service instance (including in preview environments). For commands that should run before _every_ deploy, use `preDeployCommand` instead."

Before w33/m435 bex ran the hook **as** the pre-deploy step until one release completed it (w2/m45, then w8/m63). Three things followed, none of them Render's:

- the hook ran before the first rollout, not after it;
- the first release never ran its own `preDeployCommand`, so a seed ran in place of the migration it depends on;
- a failing hook failed the first deploy.

**What runs when.** `App.PreDeployStepCommand` is the release's `preDeployCommand` and nothing else, so every release runs it before its rollout, the first included. `App.OwedInitialDeployHook` selects the hook while it is owed: it is set, and neither `status.initialDeployHookCompleted` nor the older `bex.co/initial-deploy-hook-ran` annotation marks it done. The operator starts an owed hook in the pass that finds the current release live (`reconcileInitialDeployHook`, called after the web and worker paths mark the release Running) and at no other point.

**Mechanism.**

1. The hook is a Job of the pre-deploy plane, `predeploy-<name>-gen-<release-generation>-hook` (`appv1alpha1.InitialDeployHookJobName`), in the App's own namespace. It keeps what the cluster keys on for a pre-deploy Job: the `predeploy-` name prefix and the single `predeploy` container the workload admission policy admits a widened container policy for, the `app.bex.co/component=predeploy` and `app.bex.co/predeploy=<name>` labels the log shipper, the environment boundary and the build-minutes meter select, and the release's revision label. `app.bex.co/predeploy-step` tells the two apart: `initial-deploy-hook` here, `pre-deploy` on the step's Job. No Service selects either (w4/m181).
2. Its container is copied from the pod template the Deployment serves the release with: the same image, env, `envFrom`, image-pull secrets, security context and resources, the `/etc/secrets` projection, and the service's disk (below). The command is launched by the pre-deploy step's rule (`preDeployArgv`). Reading the live template, not the saved spec, is what makes "the app pod's env" true for a release running a selected or held configuration.
3. It runs once per release generation and never retries (`BackoffLimit 0`), under the pre-deploy step's 30-minute deadline. Render documents no timeout for the hook. The bound is bex's, a difference from Render that the user signed off on 2026-11-17 ([ADR018](ADR018-render-parity.md#deployment-sources--iac), w33/004).
4. The run is recorded in `status.initialDeployHook` (Job, release generation, `Running`/`Succeeded`/`Failed`, start, end, message), apart from `status.preDeploy`, which stays the step's own verdict. The operator reads a running hook's Job on every pass, live or not (`observeInitialDeployHook`), so a hook left running through a suspend or a newer release's build has its end read before the Job's one-hour TTL reaps it.
5. One success sets `status.initialDeployHookCompleted`, and nothing selects the hook again: not a later deploy, a Blueprint re-sync, a restart or a rollback.

**A failed hook never fails the deploy (a signed-off difference).** Render documents no failure rule for the hook, and no Render workspace was available to capture one. The user signed off on bex's rule as a difference from Render on 2026-11-17 ([ADR018](ADR018-render-parity.md#deployment-sources--iac), w33/004). bex's rule: the release is live before the hook starts and stays live whatever the hook does. The phase, the `Ready` condition and the deploy's status do not change; the failure is recorded on `status.initialDeployHook` with the pod's own cause ("the initial deploy hook exited with code 3", an out-of-memory kill, the 30-minute window, a program the image does not have, an image that cannot be pulled). The hook stays owed and runs again after the **next** release goes live. A hook that ended for a release is never started again for that release, even after its Job is reaped. Only a run whose Job is gone before its end was ever read (an operator down for the Job's whole one-hour TTL) is started again, as an unread pre-deploy step is. Two more endings are failures of the same kind: a workspace out of build minutes starts no hook that month, as it starts no pre-deploy command (ADR030 §13), and a Job the API server refuses is recorded with the platform-error sentence (w9/090) instead of being retried every few seconds.

**The hook sees the service's disk.** A disk-bearing service's claim is `ReadWriteOnce` (ADR082), and that access mode decides the design: a second pod can mount the volume only on the node it is already attached to. So the hook Job mounts the same claim at `spec.disk.mountPath` and carries a **required** pod affinity to the service's own instance on `kubernetes.io/hostname` (the selector takes the app label plus the revision label only instances carry, so it never matches the hook's own pod or another Job's). It also mounts the volume the way the instance does: the pod takes the instance template's `hostUsers` instead of the pre-deploy plane's pod user namespace, and drops the tenant-pool node selector, because the instance's node is the only one that can mount the volume and the local `local-path` class refuses an idmapped mount ([container-privileges.md](render-artifacts/container-privileges.md)). A file the hook writes under the mount path is therefore owned as the service would own it and is there for the running instance to read. Because that one node is bin-packed like any other and no autoscaler can add room to it, a disk-sharing hook keeps the tier's limits but requests next to nothing (CPU 0, memory 64Mi), the disk snapshot Job's rule: it runs on the node's spare capacity instead of waiting out its deadline unscheduled. The alternative, running the hook inside the live instance, was rejected: it needs `pods/exec` on the operator, and it leaves no Job to bound, record or read logs from. A service without a disk runs the hook in the pre-deploy pod shape unchanged. The pre-deploy command still mounts no disk, as on Render.

The hook stays off a disk that something else owns: it does not start while a restore the owner requested is unserved or a snapshot purge is pending (`diskBusy`), and a restore waits for a hook that still mounts the volume, as it waits for an earlier restore (`initialDeployHookHoldsDisk`).

**Edge cases.**

- **Suspended.** A suspended service starts no hook. It starts once the resumed release is live. A hook already running when the service is suspended is left to finish.
- **Canceled first release.** A release canceled before it went live never reaches the hook. A cancel that settles back onto a served release starts none either: no release went live.
- **Rollback, restart.** Each is a release. If the hook is still owed when it goes live, it runs then, on that release's image.
- **A newer release while the hook runs.** The newer release's pre-deploy step cancels an older step still in flight (newest wins) but never the hook: a one-time seed stopped halfway is worse than one that finishes. No second hook starts beside a running one. When it ends, a success completes the hook, and a failure lets the release that is live by then run it.
- **Scale.** Once per service, whatever its instance count. bex reads Render's "once per service instance" as once per service; preview environments, where that sentence would matter, are a recorded non-goal.
- **Cron jobs, static sites, build sources.** They run neither command, and the Blueprint compiler refuses the field on a cron job or a static site.
- **A hook added to a service that has already deployed** is owed like any other and runs after the next release goes live. Render's sentence reads as "never" for that case. The user signed this rule off as a difference from Render on 2026-11-17, together with the failure rule ([ADR018](ADR018-render-parity.md#deployment-sources--iac), w33/004).

**Tenant surfaces.**

- **Deploy log.** The hook pod's output is shipped as `type=build` and read live as `type=predeploy`, like a pre-deploy command's ([ADR010](ADR010-observability.md)). bex-api adds the platform lines from `status.initialDeployHook` on the deploy that went live under the run's release: `==> Running the initial deploy hook` after `==> Your service is live 🎉`, then `==> Initial deploy hook succeeded`, or `==> Initial deploy hook failed: <cause>` and a line saying the deploy stays live and the hook runs again after the next deploy. A deploy-scoped read drops the other deploys' hook pods, since a hook runs inside the next deploy's window.
- **Deploy record.** `initialDeployHookStatus` (`running`, `succeeded`, `failed`) and `initialDeployHookFinishedAt` on REST, GraphQL and MCP, both bex extras, read from the App's status for the deploy that went live under the run's release. They never change `status`: a deploy with a failed hook is `live`. The dashboard's deploy page keeps its log window open while the hook runs and closes it where the hook ended. The App keeps the latest run only, so once a later deploy retries a failed hook the earlier deploy reads no hook status; its output stays in the log store.
- **No event, no notification.** REST event types stay inside Render's enum (ADR018, Service events), so the hook records none.
- **bex-api's awaiting-pre-deploy read** (w4/670) follows `PreDeployStepCommand`: a release that owes only a hook is not awaiting a pre-deploy step and reads `update_in_progress`.

**Services from before w33/m435.** No stored App needs an edit.

- A hook already completed, by either marker, never runs again.
- A first release that failed on the hook as its pre-deploy step keeps that verdict (`legacyHookStep`): an operator upgrade does not roll a failed release. Its next release runs its own `preDeployCommand`, goes live, then runs the hook.
- A release whose hook an older operator is still running as its step is watched to the end. The older operator stamped no `app.bex.co/predeploy-step` label, which is how its Job is recognized (`ranHookAsStep`): no second run starts, and its success counts as the hook's completion. If that Job is gone unread, the release rolls and the hook, still owed, runs once it is live.

## Deploy commit provenance (w9/001, public-repo fallbacks w4/m108 t004 + w8/209)

Repo-backed deploy rows are stamped with commit provenance **at deploy-open time** — before the build runs — so REST/GraphQL/MCP and the dashboard Deploys tab can name the code being shipped (`commit.id` / `commit.message` / `commit.createdAt`). Resolution goes through one seam (`github.Service.resolveCommit` → `deploys` Trigger, `apps` create-path first deploy, and blueprint redeploy):

1. **GitHub App installation for the repo owner** — mint an installation token and `GET /repos/{owner}/{repo}/commits/{ref}`. This is the connected-repo path (w9/001).
2. **GitHub without an installation (Public Git URL)** — unauthenticated `GET /repos/{owner}/{repo}/commits/{ref}`, preserving the message and author time (w4/m108 t004).
3. **Other public HTTPS Git URLs** — anonymous smart-HTTP `info/refs?service=git-upload-pack` discovery resolves an advertised branch, tag (peeled for annotated tags), `HEAD`, or full advertised SHA (w8/209). This works with the GitHub App disabled and needs no provider integration. The deploy row carries the verified SHA and the build pins that SHA through the existing seam. Discovery follows Git's [smart-HTTP advertisement](https://git-scm.com/docs/http-protocol#_smart_server_response) and [reference discovery](https://git-scm.com/docs/pack-protocol#_reference_discovery) contracts. It does not fetch commit objects, so message and author time remain empty on this path. An explicit full SHA (`deploys create --commit <40/64 hex>`) that the advertisement does not list — any historical commit, or a lookup that missed — is recorded as requested (2026-10-29 fix after the w8/209 hosted run found `commit: null` and `Building from …@main`). That SHA is the build pin: the clone fetches it and fails the deploy unless the checkout matches `EXPECTED_COMMIT`, so a `live` deploy proves the recorded commit, and echoing the caller's own SHA reveals nothing about the repository. Abbreviated SHAs are not expanded and stay misses.

Both public paths share positive (~10s) and miss (~2m) TTLs and a 5s request deadline. A positive entry only absorbs a burst, such as a Blueprint's services built from one repository. The earlier five-minute entry built a commit from before the latest push (w5/152). Smart-HTTP reads are bounded at 1 MiB. Past the bound only the default branch (or `HEAD`) resolves, from the first record's `symref=HEAD:` capability: gitlab-org/gitlab advertises 82 MB with `refs/heads/master` 13 MB in, behind `refs/environments`, and would otherwise miss even its default branch (w8/209 follow-up). HTTPS redirects stay bounded and pass the same public-IP dial guard at every hop, with no ambient proxy, credentials, or cookies.

**Why not report the SHA back from the build?** Resolving before build reuses the existing seam and reaches every deploy-opening caller. The exact returned SHA pins the checkout, so a branch moving after resolution cannot change the build's code. No new operator→backend write path is needed.

**Honest omission, never fabrication.** Non-HTTPS generic URLs, private repos without a connection, unadvertised refs other than an explicit full SHA on a generic host, malformed advertisements, and provider failures leave `commit` omitted (`ok=false`). All public lookup failures collapse to the same miss, so the path does not distinguish private from missing repositories. Callers still open the deploy; an unresolved branch remains unpinned.

## Render's default environment variables (w5/m148)

Every service gets Render's documented default variables (`RENDER`, `RENDER_*`, `IS_PULL_REQUEST`; the full list and values are in [ADR018](ADR018-render-parity.md)). One package, `lego/types/renderenv`, computes the values that follow from the App alone, for both the operator and bex-api's Blueprint resolver. The operator adds them to the app container (and cron runs) just before `PORT`, as platform-owned entries. It also adds the pod name as `RENDER_INSTANCE_ID`, and `RENDER_GIT_COMMIT` from the serving image's OCI revision label. BuildKit stamps that label from the clone step's `git rev-parse HEAD`, so a commit always travels with its image. Each web, private and worker service also gets a headless `<slug>-discovery` Service for `RENDER_DISCOVERY_SERVICE`. The operator never adopts a same-named object it does not control.

## Edge caching (w5/m151)

A web service on a paid plan whose `spec.cacheProfile` is `origin-controlled` or `origin-controlled-all` gets Render's edge caching ([ADR018](ADR018-render-parity.md) row "Edge caching"). Render's cache is "powered by the same global CDN as Render static sites" ([render.com/docs/web-service-caching](https://render.com/docs/web-service-caching)): it lives outside the instances, every instance is behind it, and only "each time you successfully deploy" and a manual purge empty it; "failed deploys do not trigger a purge". bex's cache lives in a **per-service tier** outside the service's instances (w3/m489). Until then it was an in-memory sidecar in each pod, which a Restart, a scale-out, an eviction, a node drain and turning caching on each emptied or started cold, and which filled each key once per instance.

**The tier (w3/m489).** This is the recommendation under [ADR008 § Render parity first](ADR008-vision.md#render-parity-first) (option A). The alternative, keeping the per-pod sidecar and recording its effects in ADR018 as a divergence (option B), would need the user's sign-off; the cost below lets that be revisited with numbers.

- **Topology.** Each caching App gets a Deployment `bex-edge-cache-<app>` of bex's `edge-cache` proxy (`lego/operator/internal/edgecache`, `/edge-cache` in bex's own image) and a headless Service of the same name. Both are owned by the App and live in its own namespace, so nothing is shared across tenants, the reason the sidecar lived in the pods. Tier pods carry `app.bex.co/edge-cache: <app>` and no `app.bex.co/app`, so no Service of the App, instance list, metric, log stream, shell or bill counts them.
- **Upstream.** The tier forwards misses to port 10000 of the App's own Service (`http://<app>:10000`). That port targets the primary listener on every port path and through a port change (`withPrivateNetworkPorts`), so the tier never follows a port and a port change rolls no tier pod. The App's own Services target the app itself, never a cache, so private-network traffic is not cached, as Render's CDN fronts only the public URL.
- **Route switch.** `ingressBackend` keeps its precedence (maintenance, suspension, sleep and first deploy) and then routes to the tier while one of its pods is Ready (`edgeCacheTierServing`), and to the App's Service otherwise. Turning caching on keeps the route on the Service until a tier pod is Ready. A tier that cannot start, or the loss of every tier pod at once, returns the route to the Service at the next pass, where requests are served uncached. Turning caching off moves the route back first; the next pass, which the Ingress write brings, removes the tier once no Ingress of the App names it (`retireEdgeCacheTier`).
- **Replicas and fail-open.** Two replicas, rolled with `maxUnavailable: 0` and `maxSurge: 1` and spread across nodes by preferred anti-affinity. One replica cannot fail open: Traefik v3.7 sends no new request to a terminating endpoint ("fenced", `pkg/server/service/loadbalancer/wrr`) and answers 503 when a Service has only fenced endpoints. With two, a deleted, evicted, OOM-killed or drained pod leaves the other serving, and a terminating proxy keeps serving its in-flight and peer requests for 10 seconds before it shuts down. The local drill (w3/m489 t006) measures it.
- **One fill per key.** Each replica resolves the headless Service to its Ready peers every 5 seconds (`BEX_EDGE_CACHE_PEERS`). A cache-eligible request whose key another replica owns, by rendezvous hashing over those peers, is forwarded to it once with `X-Bex-Edge-Cache-Hop`. The header is honored only from a current peer, never forwarded further and never sent to the app. A forward that fails before any response is served locally. So a key reaches the app once whatever the replica and instance counts, and a lost replica's keys move to the other. The app sees the same `X-Forwarded-For`, `-Host` and `-Proto` with or without the hop.
- **Capacity.** Bodies live on a 1792 MiB `emptyDir` (`sizeLimit`): up to 1 GiB per replica, so 2 GiB per service since each key lives on one replica, and 128 MiB per object. The sidecar held 48 MiB in memory per instance and 6 MiB per object. Fills stream to temp files, at most four at once (512 MiB), and the limit keeps 256 MiB beyond them for files a purge is still removing. Each body is charged in whole 4 KiB blocks, as the kubelet measures the volume, and the in-memory index is bounded at a thirty-second of the store. A restarted proxy starts empty, because it cannot know which purges it missed. Render documents no object cap; Cloudflare's default cacheable file limit is 512 MB.
- **Network policy.** None is added. Tier pods carry the App's workspace and environment labels, which the namespace's own policies select: `allow-traefik-ingress` admits the edge, and `allow-same-namespace` (or an isolated environment's `isolate-<env>`) admits peer traffic and the tier's requests to the app, beside `allow-dns-egress`. The environment labels move on running tier pods in place (`relabelPodsInPlace`), and the template holds its own (`holdIsolationLabel`), as for the App's pods, so an isolation toggle rolls no tier pod.
- **Resources and cost.** Each tier pod requests 100m CPU, 192 MiB memory and 256 MiB ephemeral storage, with limits of 1 CPU, 192 MiB and 2 GiB, so a caching service costs about 0.2 vCPU and 384 MiB requested. Render includes edge caching with every paid web service, so bex pays for the tier: its pods count against the workspace namespace's compute quota (58 CPU of requests) and appear on no bill. On production, 0 of 27 Apps had caching on (2026-11-19, read through `scripts/fetch-app-kubeconfig.sh`), so the tier costs nothing there today.
- **Image.** The tier keeps the image it runs while nothing else about its template changes, so an operator release alone restarts no tier pod, which is the rule w6/m484 sets for the App's own pods. The pass that records a successful deploy moves it to the operator's image, since that deploy empties the cache anyway (`edgeCacheTierImage`). One guard covers the whole class (w6/m484): `TestANewOperatorImageChangesNoLongLivedTenantPodTemplate` (`operator_upgrade_test.go`) drives a web service in each helper shape, a private service, a background worker and a Key Value store through their reconcilers under two operator images. It fails when any Deployment or StatefulSet in the namespace changes its pod template, so the next helper wired to the operator's image fails there too.

**What empties the cache (w3/m486, w3/m489).** The operator patches three annotations on each running tier pod every pass (`annotateEdgeCacheTierPods`). Each tier pod reads them every 2 seconds from its downward-API annotations file (`BEX_EDGE_CACHE_CONTROL`). Neither the tier's template nor the App's carries them, so none of them rolls a pod.

- **`app.bex.co/cache-purged-at`** is the App's manual purge stamp. A tier pod created after the purge started empty and is not handed it.
- **`app.bex.co/cache-revision`** is the release whose successful deploy last emptied the cache (`edgeCacheRevision`), recorded on the tier Deployment's own metadata. It moves to `status.activeRevision` once three things hold: that revision is the App's current release, the release is no Restart, and the App's own Deployment has no old non-terminating pod left. bex-api runs a Restart as a new release of the serving one (`spec.releaseConfig.preserveGroupValues`), so it is no new version. Waiting for the old pods means no fill can reach the replaced version after the purge. It also waits while bex-api has stamped a newer release the operator has not adopted yet (`releaseUnadopted`): the tier converges at the top of a pass, so until the adoption `spec.releaseConfig` is the new request's and no longer marks the serving release as a Restart. Before that guard, on production (w3/m489 t007), a deploy requested after a Restart recorded the Restart's release and emptied the cache before the deploy began, even a deploy that then failed. So a failed or still-rolling deploy, a Restart, a scale change, a crash, a node drain, a suspension and an operator release empty nothing. A Rollback, an environment save that reuses the served build, and a plan change are deploys on Render, and each empties it.
- **`app.bex.co/cache-profile`** is the saved profile, or `no-cache`, a pass-through, once caching is off. A new value applies from the next request and empties the cache as well.
- **Reading them.** After a proxy's first read of the file, a new purge stamp or revision empties it, and a fill that started before that is not stored. A purge lands within the kubelet's refresh of the file after the patch, and the App watch passes a stamp change at once, although it bumps no generation.
- **Admission.** The `bex-operator-pod-labels` admission policy admits exactly these three annotations, set or changed, on a pod running an `edge-cache` container. Until that exception (2026-11-19) it admitted no pod annotation, so on production every such patch would have been refused (`pod_label_admission_test.go`).
- **Residual.** A Restart of a release recorded before release snapshots, which bex-api still runs as a plain redeploy of its commit, empties the cache as a deploy does.

**The profile is operational (w3/m486).** `spec.cacheProfile` is no release input (`AppSpecIdentityClasses`), as Render's CDN setting opens no deploy, so a switch on REST, GraphQL or the dashboard opens no deploy row and mints no release generation. The tier's template carries no profile: a new tier pod passes every request through until its first pass annotates it, within seconds of its creation. A release fingerprinted with the profile in it, as every caching service's was before w3/m486, is adopted as the same release (`adoptCacheProfileReleaseIdentity`).

**Migration from the sidecar (w3/m489).** The operator release that ships the tier creates one for every caching service and moves its route once a tier pod is Ready. The App's Services stop targeting the sidecar on the first pass, so for those few seconds requests reach the app directly and uncached, and the tier starts empty, once. A pod template stored with the sidecar keeps it, with its control volume and any purge stamp of a template from before w3/m486, exactly as stored, while nothing else about the template changes (`keptEdgeCache`). So the upgrade, a purge, a switch, turning caching off and a new helper image roll no instance. The sidecar receives no request meanwhile. The next change for another reason, such as a deploy or a restart, drops it. Turning caching on adds nothing to an App's pods, so it rolls no instance either.

**Image-port services (w9/087).** A web service on its image's port (`web-image-v1` / `web-image-configured-v1`, every new web service since w4/m243) caches the same way. The tier reaches the image network's resolved primary through port 10000, as a provisional primary while HTTP discovery is still choosing, and the new primary once a port change is promoted. The proxy's listener, 19099, is one of the three ports Render reserves (18012, 18013 and 19099; `IsReservedImagePort`) because it was the sidecar's inside the app's pods, which a kept template may still run (w21/076). An image that exposes 19099 is refused when its metadata is read, a `PORT` of 19099 is ignored, an explicit port of 19099 is refused, and HTTP and listener scans skip it and any pod running the sidecar.

**Metrics and autoscaling leave the cache out (w3/m487).** Render's cache runs on its CDN, outside the instance, so turning caching on changes no instance metric. The tier's pods are no pods of the App's, so no Metrics chart, limit line or autoscaling decision reads them. A kept sidecar is skipped by its container name, one constant, `appv1alpha1.EdgeCacheContainer`, which the shared metrics-server decoder (`podmetrics.Parse`, read by the autoscaler and bex-api), bex-api's Prometheus reads and its pod-spec limit reader all skip ([ADR010 § Metrics](ADR010-observability.md#metrics)).

**Tests.** `edge_cache_test.go` covers the tier's routing through readiness, caching off, purge, switch, scale and a successful deploy in envtest, plus `TestTheCacheEmptiesOnlyOnASuccessfulDeploy`, `TestTheTierKeepsItsImageUntilASuccessfulDeploy`, `TestAnUpgradeKeepsAStoredEdgeCacheSidecarUntilTheTemplateChanges`, `TestTurningCachingOnRollsNoInstance` and `TestTheRouteFollowsTheTiersReadiness`. `container_policy_admission_test.go` admits the tier and kept sidecar Deployments under the production workload policy. `internal/edgecache` covers the disk store, the peer fill and the revision purge.

**Conditional requests answer 304, and a stored answer carries its Age (w3/m488).** Caching must not turn an app's 304s into full 200s: those bytes are the service's outbound bandwidth, which the meter bills past the plan's included amount (w6/m319, [ADR030 §14](ADR030-pricing.md)). The cache therefore answers a client's validators itself:

- **A stored page** answers a GET or HEAD with `304 Not Modified` and `CF-Cache-Status: HIT` when the request's `If-None-Match` is `*` or names the page's `ETag` by weak comparison. Without an `If-None-Match`, it does the same when the request's `If-Modified-Since` is at or after the page's `Last-Modified` (RFC 9110 §13.1 and §13.2.2, RFC 9111 §4.3.2). Only a stored 2xx is replaced, so a stored 404 or redirect answers as itself (§13.2.1). The 304 carries the 200's headers less its representation metadata: `Content-Type`, `Content-Length`, `Content-Encoding`, and `Last-Modified` when an `ETag` is present. This is how Go's file server shapes one (§15.4.5).
- **The fill.** The upstream still sees no validators, so the body it sends suits every client the key covers; Cloudflare, Render's CDN, likewise sends no ETag to the origin on a cacheable miss ([etag-headers](https://developers.cloudflare.com/cache/reference/etag-headers/)). When the leader's own validators match the upstream's response, the leader gets a 304 with `MISS` or `EXPIRED` and the body goes only into the store. A body past the object cap is not read to its end. A page the cache does not keep answers a matching validator with a 304 the same way, under its `BYPASS` or `DYNAMIC` status: a `private` or `no-cache` page such as Rails' default, one with `Set-Cookie`, or a stream. That is the 304 the app would have sent had it seen the validator. Requests waiting on a fill answer their own validators from the stored page.
- **Age.** Every answer from a stored page carries one `Age`, in place of any it was stored with: the upstream's own `Age` at store time plus the whole seconds since (RFC 9111 §4, §5.1). A fill is generated by the app for that request, so it passes the upstream's response through as is, with no `Age` of the cache's own.
- **Evidence boundary.** Neither Render's caching page nor Cloudflare's ETag page says whether the edge answers a conditional request from cache, or what `Age` it sends. A capture from a Render workspace needs `w10/blocked/002`. So this behavior rests on the RFCs and on not regressing the app's own 304s. `Range` requests and `stale-while-revalidate` stay out: neither is documented for Render's edge cache.

**A HEAD reads the stored GET, and a HEAD miss fills with a GET (w3/075).** Cloudflare, Render's CDN, answers a HEAD for a cached resource at the edge. On a miss it "will send a GET request to your origin, cache the full response and return the response headers only" ([cache-behavior](https://developers.cloudflare.com/cache/concepts/cache-behavior)). Until w3/075, bex proxied a HEAD miss as a HEAD and stored nothing. Every bare HEAD also missed: Traefik adds `Accept-Encoding: gzip` to a GET that came without one (Go's transport does so for every method but HEAD) and passes a HEAD as it came. The proxy keys a page by whether its client takes gzip, so a client's bare GET filled the gzip key, and its bare HEAD looked up the other, which no public GET fills. On production pin `7af50a28168d`, `curl -sI` of a cached path read `MISS` every time.

- A HEAD whose own key has no page reads the page stored for the same URL under the other encoding preference, provided that page names no `Content-Encoding` beyond `identity`. It then gets the header fields a GET of its own preference would carry (RFC 9110 §9.3.2). A gzip page never answers a HEAD that did not accept gzip, because Traefik decompresses only the GETs it added gzip to.
- A HEAD miss goes to the app as a GET with the HEAD's own encoding preference. The page is stored, and the HEAD gets its header fields with `MISS` (or a `304 MISS` for a matching validator), so the next HEAD reads `HIT`. A page the cache does not keep (a `Set-Cookie`, a `private` page, one past the object cap) is answered with its header fields, and its body is not read.
- The tier routes a request to its owner by host and target, not by encoding preference, so both of a URL's pages live on one replica and a HEAD at either replica finds the GET's page.

**A GET reads the page a HEAD filled (w3/077).** Cloudflare keeps one object per URL, so after a HEAD-first fill a client's next GET reads `HIT`. bex's HEAD fill stores the page under the HEAD's own encoding preference, which is identity for a bare client, and Traefik turns that client's next bare GET into a gzip one. Until w3/077 only a HEAD read the other key's page, so that GET went to the app. On production pin `dff52c596d13`, a bare `curl -sI` then a bare `curl -s` of a new path read `MISS`, then `MISS`, and nginx logged a second `GET`. On pin `11b1e8f85f06`, which carries the fix, the same pair read `MISS`, then `HIT`, and nginx logged one `GET`.

- A GET or HEAD whose own key has no page reads the page stored for the same URL under the other encoding preference, provided that page names no `Content-Encoding` beyond `identity` and the client did not refuse identity (`identity;q=0`, or `*;q=0` with no `identity` member of its own, RFC 9110 §12.5.3).
- A gzip page never answers a client that does not take gzip, GET or HEAD, because Traefik decompresses only the GETs it added gzip to.

## Deploy image digest (w8/m122)

An image deploy reports Render's `image.sha`, "the SHA that the image reference was resolved to", on REST and MCP (`image.sha`), GraphQL (`Deploy.imageSha`) and the dashboard deploy header (short form, full value on hover, copy). Render's pinned CLI prints it after `SHA:` in its deploy list.

**Source.** The operator records `status.imageDigest {generation, digest}` when a release first serves, from one of two sources (`operator/internal/controller/image_digest.go`):

1. A digest-pinned `status.image` (`…@sha256:…`, every in-cluster build, or a service created by digest) is its own evidence; no pod is read.
2. Otherwise the digest comes from the kubelet: `containerStatuses[app].imageID` of the earliest-created Ready, non-terminating pod of the release's own revision. A bare `sha256:…` imageID is a local image's config id, not a registry digest, and is ignored.

**When.** It records the digest in the status write that first names the release in `activeRevision`. That is either `markRunning` (the shared web/private/worker path, once the Deployment converges) or the earlier `RolloutSettling` pass (w4/405), which fires once every pod of the release is Ready while the Deployment is still converging. bex-api can close the row live on that earlier write, so the digest has to be in it. Before w4/m320 t011 it was not, and every held image change went live without `image.sha`.

Once a generation has a digest, it keeps it. A pod that later re-pulls a moved tag never rewrites what the release first ran. A record for another generation is dropped, never carried forward. bex-api stamps the row's `image_sha` beside `resolved_image` on the row's **live** close, and only from a record of that row's own generation. A failed, canceled or superseded deploy has no digest, and neither does a live deploy whose release recorded none. It is never shown with the previous release's digest. A rollback row takes the digest its own release records when it goes live, not one copied from its target.

**Which digest (corrected w8/208, 2026-10-28).** Image-port metadata discovery retains both the verified top-level reference digest and the Linux/amd64 platform-manifest digest. Its release reference pins the top-level digest: an OCI index for a multi-architecture tag, a manifest for a single-architecture tag, and the exact requested digest for a by-digest create. The kubelet chooses its node platform from the pinned index; config/port validation still reads the selected Linux/amd64 manifest. `recordImageDigest` therefore records the same index that a user can pin, rather than its child manifest. Cache identity and once-per-release tag resolution use that top-level reference too. Existing historical deploy rows retain the digest they recorded.

"Linux/amd64" is the hosting node pool's platform, the operator's `BEX_IMAGE_PLATFORM` default (w2/m293 t007, 2026-11-08). Index selection and the config check both use that one setting. The arm64 local CAPD mock sets `linux/arm64` (from `scripts/mock-cluster.sh operator`), because BuildKit there builds arm64 images; production leaves it unset. A config for another platform is refused as `image config is not Linux/<arch>`, and an index with no entry for it as `image has no Linux/<arch> manifest`.

Observed on containerd (kind v1.36.1, arm64, 2026-10-20): a pod running `docker.io/ealen/echo-server:0.9.2` reported `imageID` `docker.io/ealen/echo-server@sha256:006b92e1…`. That is the tag's OCI **index** digest (`docker buildx imagetools inspect`), not the linux/arm64 manifest (`sha256:74afa5ff…`). So for a multi-arch tag, `image.sha` is the platform-independent digest the tag resolved to. It is what a registry `HEAD` on the tag returns, and it is what `ref@<sha>` pulls on any node.

**Limits.**

- A Git-backed deploy's built image has a digest too, but Render reports no `image` object for a Git-backed deploy. No surface reports it.
- A cron job has no long-running pod at convergence, so it records a digest only for a digest-pinned image. A cron job on a tag reports none.
- A static site has no runtime container and records nothing.
- The pod read goes through the informer cache. If the cache has not yet seen the Ready pod's image id when the release is first named active, that release records no digest and its row stays without one. Nothing is backfilled after the live close.
- `image.registryCredential` is not reported.

**Remaining tag-based runs.** Image-port web services now resolve and pin each release before rollout (w4/m243, corrected to the top-level digest by w8/208). Source-built private image-port services likewise pin their build reference. Other configured-port/tag paths still run the tag with `imagePullPolicy: Always`. A restart, scale-out or reschedule of the same release can therefore pull a moved tag and run bytes other than its recorded `image.sha`. Pinning each release to `ref@digest` would close that gap, but at a cost: digest resolution against tenant registries, with their credentials, before the rollout, instead of reading the kubelet afterwards. Render's docs are ambiguous about restarts, and its rollback re-pulls the tag. This is a separate product decision; it is not implemented.

## Control-plane deploy lifecycle

For store-managed Apps, bex-api projects the operator's current-release facts into Render's deploy vocabulary without adding an operator-to-database dependency. A deploy row begins `created`; `BuildQueued` and `Building` evidence yield `queued` and `build_in_progress`; a release-generation-scoped pre-deploy Job yields `pre_deploy_in_progress`; rollout reconciliation yields `update_in_progress`; and the corresponding failure or convergence facts yield `build_failed`, `pre_deploy_failed`, `update_failed`, or `live`. A later operational metadata generation does not detach the open row: the projector matches it to `status.releaseGeneration` and the active `rev-<release-generation>`. A row whose own release generation carries a terminal `status.conditions[Build]` verdict closes `build_failed` with that verdict's message even once the release has advanced past it — otherwise the deploy that actually failed would report the `canceled` a bare generation comparison infers (w6/m100). Fast phases may be skipped when the polling control plane never observes them. Invalid regressions are rejected.

The control-plane fallback gate is phase-specific and resets at each stored transition: builds receive 125 minutes (longer than the BuildKit Job's 120-minute active deadline, Render's build limit), pre-deploy commands receive 35 minutes (longer than their 30-minute Job deadline, Render's pre-deploy limit), and workload rollout receives 18 minutes (longer than the 15-minute rollout budget). This prevents a healthy long build from being falsely closed as `build_failed` while retaining a bounded failure for rollout states such as `ImagePullBackOff` that do not make the App phase machine fail on their own.

`updatedAt` advances only on a real stored transition, `startedAt` records the first executing phase (a phase the observer skipped contributes its operator-recorded, generation-attributed start — the build window, or for a fast `pre_deploy_failed` the failed step's Job start — and stays unknown without one), and `finishedAt` records the first terminal result. A newer trigger cancels an older open deploy; a newer live deploy atomically marks the former live revision `deactivated`, retaining its original `finishedAt` and using `updatedAt` for the replacement instant. See [ADR006](ADR006-bex-api.md#deploy-history--trigger-w2m5-render-deploys-compatible) for adapter/filter semantics.

### Saves on a suspended service (w4/m234)

A suspended service deploys nothing: Trigger, Rollback and `deployActions` already refuse it with precondition `suspended`. The configuration writers now agree.

- **Environment "Save and deploy" and "Save, rebuild, and deploy"** (REST `PATCH /v1/services/{id}/environment`, GraphQL `patchServiceEnvironment`, MCP `patch_service_environment`) stage like Save only on a suspended service. They answer `rolledOut: false` with `rolloutError`: "Saved. This service is suspended, so nothing was deployed. Resume it, then deploy to apply the changes." The locked write re-checks the App it writes, so a suspend that lands between the read and the write stages too, and a rebuild refused by a racing suspend gets the same sentence. A compound Settings patch whose publish races a suspend re-decides against the App it writes, so it is held, not stamped.
- **Every other release-rolling write** that lands on a suspended App (a legacy `PUT /env-vars/{key}`, a Settings field such as `healthCheckPath`, an environment-group roll) opens no deploy row. `rollout.Snapshot.Stamp` marks it pending (`AnnotationPendingSourceGeneration`, the source-update hold) instead of stamping a release and filing a `config_change` row that the reconciler would only close `canceled`. Rows opened before the suspend still close "Canceled: the service was suspended" (w4/m171).
- **Env groups.** A deploying group save leaves a suspended linked service in `pendingServiceIds`, like an Auto-Deploy-off one, and rolls only the running services. An owner's link to a suspended service is held the same way, and a create with `serviceIds` names that service in `pendingServiceIds`. An unlink, a group delete or a Blueprint sync's link on an Auto-Deploy-off service is staged in an annotation and folded into the spec by the owner's next release (ADR013 § Precedence and redeploy, w4/m239), so every release the operator adopts has a deploy row; the one writer that bare-patched release-identity fields without a row was `envgroups.rollLinked`. An owner's link deploys an Auto-Deploy-off service at once, with its own row, as Render documents (w32/m423).
- **Resume, then deploy.** Resume opens no row, and the operator keeps the prior release serving, so the revision is unchanged. Staged environment values stay pending and `undeployedChanges` reads true. The next deploy (Manual Deploy, a git push, a running-service save) stamps a newer release and rolls the saved changes with exactly one row. The dashboard's notice says "Resume the service, then deploy". Its environment editor makes Save only the primary action while the service is suspended, and disables the two deploying items with the Manual Deploy reason.
- **Residual (narrowed by w8/m135).** A spec field saved while suspended (a probe path, a command, the shutdown delay) is held like a save-only PATCH. The operator keeps rendering the held release's own settings through Resume until a deploy (`pendingReleaseView`, § Settings saves wait for a deploy). A release whose record carries no adopted spec still projects the saved field onto the parked Deployment's template, as before, and it takes effect when the service resumes. A Blueprint sync is a deploy of its own (it resolves a commit and files a `blueprint` row) and does not go through `Stamp`, so on a suspended service it still files that row, which the reconciler closes canceled as before (w4/366).

## Deletion finalization window (w3/m81)

A `DELETE` (REST `DELETE /v1/services/{id}`, or the equivalent GraphQL/MCP/dashboard verb) is accepted at once and the App CR is marked for deletion; the operator's `app.bex.co/finalizer` then tears down what ownerRefs cannot cascade. From that instant the **tenant read contract is consistent absence** — every by-id surface returns `not found`, matching `List` and Render's `GET 404` ([ADR006 § Reads while a deletion finalizes](ADR006-bex-api.md#reads-while-a-deletion-finalizes-w3m81)) — so a by-id read can never advertise a serving URL whose route and certificate the ownerRef cascade has already withdrawn.

Finalization is **bounded**. The ordinary controls (private service, worker, cron, Key Value) clear in 1–15 seconds; the one long pole — a static site's object-prefix purge — runs as a Job with a 15-minute `activeDeadlineSeconds` and `BackoffLimit` 3 ([ADR029 § Deletion and finalizer bound](ADR029-static-sites.md#deletion-and-finalizer-bound-w3m81)). If finalization has not completed within 15 minutes of the deletion request, the operator stamps a `DeletionStalled` condition on the App and backs its requeue off from 2s to 30s. The finalizer is **retained** on overrun — nothing is force-removed, so no object prefix is silently orphaned and `scripts/delete-audit.sh` remains the residue gate — while the resource stays absent from every tenant read and keeps counting against the workspace's `terminating` quota (w6/m129) until cleanup succeeds. The rejected alternative — force-removing the finalizer after the deadline to free the quota faster — would strand exactly the leaked static prefix the delete-audit gate exists to prove absent, so a genuinely unrecoverable purge is an operator action, not a silent finalizer drop.

## Rollout headroom — why a deploy must not mint a node (2026-09-12)

A rolling update is zero-downtime only with two halves. **Readiness gating:** `replicas: 1` gives `maxUnavailable: 25% → 0` and `maxSurge: 25% → 1`, so Kubernetes starts the new Pod and waits for `PodReady` before the old one is torn down. **A drain on the way out (w1/m154):** deleting a Pod sends `SIGTERM` at once, while its endpoint leaves Traefik (and kube-proxy) a moment later, so an app that exits on `SIGTERM` failed the requests still routed to it — production saw one `502` on every config-change roll of a free web service. Web and private services' pods therefore carry a **60 s** preStop drain (no shell needed in the tenant image) and a `terminationGracePeriodSeconds` of 60 s plus `maxShutdownDelaySeconds` (default 30), so the user's delay still counts from `SIGTERM`. **The drain applies only to an instance that is still serving (w4/m353).** Kubernetes runs preStop before every container stop, a liveness restart included ("a liveness/startup probe failure"), and by then readiness has had the instance out of rotation for about 45 s, so a drain protects nothing and only doubles Render's 60 s restart. The preStop is therefore an exec of the `health-probe` helper (`health-probe drain --seconds 60 <check>`), whose check is the liveness probe's own (the no-redirect HTTP check for a Health Check Path, `tcp --port N` for a TCP-checked service, `open-port` while a first image release discovers its port): it waits 60 s when the check passes and returns at once when it fails, and it always exits 0 so a hook error never blocks termination. A deleted healthy instance (a deploy, a restart, a scale-in, a node evacuation) drains exactly as before. **Every drained pod carries the helper (t002 option (a)):** TCP-checked services gain the `bex-health-probe-install` init container and the `/bex-health` volume (§ Health checks answer 3xx) only for their drain; their probes stay the kubelet's TCP check. The cost is what path-checked services already pay: the installer's copy at pod start and, on a node that has not run it yet, a pull of bex's own image. Verified on kind v1.36.1 (2026-11-14) with the helper on a hostPath: whoami flipped to a failing `/health` was restarted 51 s after the flip with the checked drain and 121 s with the plain sleep, a busybox listener killed under a TCP check was restarted at 61 s, and deleting either healthy pod still took 61 s. The rejected option, keeping the plain sleep for TCP-checked services, would have kept their restart at two minutes, a parity gap with no user sign-off. A probe-level `livenessProbe.terminationGracePeriodSeconds` cannot do this alone: Kubernetes counts preStop inside the grace period, so a shorter one would cut the sleep and leave the app only the 2 s extension between SIGTERM and SIGKILL. **With the checked drain, the liveness probe carries its own grace (w4/m353 t007):** `maxShutdownDelaySeconds` (default 30) plus the drain's one check (5 s). The kubelet uses it for the kill it decides, preStop included, so an instance that ignores SIGTERM (`sh` as PID 1) is SIGKILLed Render's delay after SIGTERM instead of waiting out the 60 s the drain had skipped too: round 398's busybox fixture restarted 145–150 s after its listener died. The pod's grace stays drain + delay, so a deletion still drains a healthy instance. The trade-off: an instance that recovers in the instant between its sixth failed liveness check and the drain's check drains only until the probe grace runs out, then gets the kubelet's 2 s minimum before SIGKILL; it is restarted either way. A plain-sleep drain keeps the pod's grace, which a shorter one would cut. An operator that does not know its own image (`make run`) keeps the plain sleep. 60 s is Render's (w8/180: a 70 s request was cut with `502` by the previous 10 s drain; w1/m154 had measured ~3 s of 502s per roll without any drain). Workers take no traffic and disk-attached services roll with `Recreate`, so neither drains. **The drain is adopted on each service's next roll, not on upgrade:** a Deployment stored without it (or with the 10 s of before w8/180, with the plain sleep of before w4/m353, or with the checked drain but no liveness grace of before w4/m353 t007) keeps its template until the template changes for its own reason (a deploy, a config change, a restart), and a new Deployment gets it at creation. Adding it to every stored template at once would roll every web and private service on the same operator upgrade, and the surge Pods would outrun the headroom slot below. Even with both halves, production proved readiness is not sufficient, because of what the **surge Pod does to the node pool**.

Observed twice in one hour on `beancount-cms-v2` (`hetzner-prod`, tenant pool at ~80% requested): the surge Pod (1 CPU / 2Gi, Guaranteed) did not fit → `FailedScheduling` → Cluster Autoscaler grew `bex-tenant-0` 2→3 → the surge Pod landed **on the new node** → the old replica was retired → that node now held one 1-CPU Pod on a 4-vCPU machine (28.9%, under `--scale-down-utilization-threshold`) whose Pod was reschedulable elsewhere → after `scale-down-delay-after-add` + `scale-down-unneeded-time` (5m + 5m) the autoscaler logged `Scale-down: removing node … pods to reschedule: <the tenant's only replica>` and evicted it. Rescheduling re-pulled a 633 MB image (72s measured), the Service held zero ready endpoints, and Traefik served 503. **The deploy manufactured the node that later evicted it.**

Lengthening `scale-down-unneeded-time` does not fix this. The node is still under-utilized and the Pod is still movable, so the same eviction lands later — decoupled from the deploy that caused it, therefore harder to diagnose, and at the price of delaying every legitimate consolidation cluster-wide. It is a cost knob, not an availability knob.

The fix is to make the surge fit on a node that already exists: `deploy/gitops/base/tenant-headroom.yaml` runs a `pause` Deployment holding one **standard-tier** reservation (1 CPU / 2Gi / 4Gi ephemeral, requests == limits) on `bex.co/pool=tenant` at priority **-1**. Tenant Pods carry no priority class (0), so the scheduler preempts the placeholder and takes its slot immediately — no scale-up, no new node, no consolidation eviction. The placeholder's `terminationGracePeriodSeconds: 0` means the slot is yielded instantly, `preemptionPolicy: Never` means it can never displace real work, and -1 sits deliberately **above** the autoscaler's `--expendable-pods-priority-cutoff` default of -10 (below it, CA would ignore the placeholder for scale-up and assume it deletable during scale-down, so the reservation would stop reserving). The displaced placeholder goes Pending and reclaims a slot as soon as the rollout retires the old replica; at `max-size: 3` it simply waits, which costs nothing and churns no nodes. `scripts/gitops-validate.sh` pins every one of those invariants, including a drift guard against the `standard` row of `lego/types/tiers/tiers.yaml`.

Scope, stated plainly: this removes the **deploy-correlated** eviction. It does not make a single-replica service highly available. A hardware failure still takes `replicas: 1` down, because one replica has no disruption budget to spend; that needs `replicas >= 2` and is the tenant's cost decision. A planned CAPI machine roll no longer does (next section).

## Node rolls hand single-instance services over before the drain (w1/m186)

A CAPI drain evicts each pod at once. For a one-instance service, that pod is the only one, so every `bex-tenant-0` roll cost those services their restart time. If the replacement could not schedule, the outage lasted hours: on 2026-10-24 beancount.io answered `no available server` for that reason (w1/138). A zero-disruption PodDisruptionBudget is not the answer, because it kept nodes undrainable for six days (ADR060 D8).

`drain-guard` (`lego/operator/cmd/drain-guard`, `internal/drainguard`) puts a CAPI **pre-drain hook** on every `bex-tenant-0` Machine. CAPI neither cordons nor drains a deleting Machine while the hook remains. When such a Machine is deleted, drain-guard:

1. cordons its node;
2. finds each App Deployment whose only Ready pods are on that node and sets `drain-guard.bex.co/evacuated-from=<node>` on its pod template;
3. lets the rolling update do the rest: the replacement starts on another node, becomes Ready, and only then is the old pod retired, so its preStop drain above still applies;
4. releases the hook once no App is left at risk, and CAPI's drain finds nothing serving.

Some cases release the hook at once:

- **Nothing to protect.** The Machine has no node, or its node is gone or not Ready.
- **Disk-attached services.** They roll with `Recreate` and cannot overlap two pods, so they get today's behavior.
- **The hold is bounded.** It never lasts more than 10 minutes from the Machine's deletion, so a replacement that never becomes Ready only delays the roll and never pins it.

drain-guard runs as its own ServiceAccount, never the operator's. It is the only bex identity with a grant in `bex-capi`: Machines, no Secrets. A fail-closed admission policy (`deploy/gitops/base/drain-guard-admission.yaml`) limits its writes to the hook, a cordon, and the evacuation annotation. Operations are in [runbooks/drain-guard.md](runbooks/drain-guard.md).

**Cluster Autoscaler scale-downs (w1/m187).** CA removes a node another way. It taints the node `ToBeDeletedByClusterAutoscaler` (`NoSchedule`), evicts its pods itself, and deletes the Machine only once the node is empty. The pre-drain hook therefore finds nothing at risk and releases at once. Between the taint and its drain, CA sleeps `--node-delete-delay-after-taint` (CA 1.34 `actuator.go` `deleteNodesAsync`), and bex raises that delay from upstream's 5s to **5 minutes** (`infra/clusterapi/autoscaler-values.yaml`, floor held by `scripts/clusterapi-validate.sh`).

drain-guard watches the workload cluster's Nodes. When the taint lands on a guarded Machine's node, it applies the same evacuation annotation and rechecks until no App there is at risk. It does not cordon, because CA's taint already keeps the replacement off the node. A replacement that is not Ready by the end of the delay is evicted as before, so the delay can slow a consolidation but never stop one. This is the path that evicted `beancount-cms-v2` in the section above, now with a Ready replacement waiting.

**Tenant visibility (`w4/m504`, 2026-11-19).** When a non-`Recreate` App Deployment gains a new `drain-guard.bex.co/evacuated-from` value, the App reconciler records the transition on `App.status.platformRedeploy` (keyed by node and Deployment generation; trigger `node_replacement` for a CAPI Machine roll or `node_consolidation` when the node carries `ToBeDeletedByClusterAutoscaler`), and ends it once that generation's rollout completes or the old pod is gone after hold expiry. The control-plane reconciler projects it into idempotent `zero_downtime_redeploy_started` and `zero_downtime_redeploy_ended` service events on REST, GraphQL, MCP, outbound webhooks and the dashboard. Disk-attached (`Recreate`) services record neither.

## Gotchas

- **Apps are imperative by design** — the `App` CR lives only in the app cluster's etcd, _not_ in git and not in `deploy/gitops/` (that's platform-only). Losing the node loses the CR; see [`docs/ADR003-control-plane.md`](ADR003-control-plane.md) for the planned Postgres source of truth.
- **Monorepo support applies to both mechanisms** — `App.spec.rootDir` scopes BuildKit's local checkout context or kpack `source.subPath`, and scopes the git-push webhook so changes only outside that directory do not redeploy the App.
- **The edge IP is the node IP** (traefik on hostNetwork) — the `*.sslip.io` host is tied to it and changes if the node is replaced.
- **Server IPs drift** — reread them from `hcloud`/the kubeconfig rather than trusting old notes; the kubeconfig's API endpoint is also distinct from the node IP.
- Day-0 cluster creation lives in [`infra/`](../infra/README.md); Argo-reconciled platform apps in [`deploy/gitops/`](../deploy/gitops/README.md). This doc is day-N **app**-level deployment only.

## Health checks answer 3xx without following it (w8/m133)

Render: "a check is successful if the instance responds with a `2xx` or `3xx` status code within five seconds" ([render.com/docs/health-checks](https://render.com/docs/health-checks)). The kubelet's `HTTPGetAction` follows every same-host redirect (every relative `Location`) up to ten hops and scores the final response, with no field to stop it; a health path that answered `302 → /login` (or `/elsewhere` → 500) never became Ready, and the stall reason told the user the 3xx they returned was acceptable.

**Decision (spike on kind v1.36, 2026-10-23):** a service with a Health Check Path probes by **exec of bex's static `health-probe` binary** (`lego/operator/cmd/health-probe`, `internal/healthprobe`) on the startup, readiness and liveness probes, keeping the periods, thresholds and 5 s timeout. It makes one GET to the pod's address on the service port with the Render `Host` header, never follows a redirect, and exits 0 for 200–399. An init container (`bex-health-probe-install`, bex's own image, non-root, read-only root, 20m/32Mi) copies the binary into a 32 MiB `emptyDir` mounted read-only at `/bex-health` in the app container, so the check works for any tenant image, shell-less and distroless ones included. The spike ran a hardened `hostUsers: false` pod: the exec probe made the `302 → 500` path Ready with no `/elsewhere` request and the app saw `Host: app.onbex.co`, a plain `500` stayed unready, and the same path under an `HTTPGet` probe stayed unready while the kubelet requested `/elsewhere` eight times. A service with no path keeps the TCP probe; a worker has no probe.

**Adoption.** Like the preStop drain, the probe is adopted lazily: a running release keeps its `HTTPGet` probe, or the helper image it was installed from, until its pod template changes for another reason (a deploy, a config change, a restart). An operator upgrade never rolls the fleet and a new operator image never re-rolls installed helpers. When the operator does not know its own image (`BackupHelperImage` empty, as under `make run`) services keep the `HTTPGet` probe. Rejected: a platform-side checker driving a readiness gate (liveness semantics would be reimplemented), and rewriting the user's path or proxying through a sidecar (changes what the app sees).

## A live release failing its health check is not a deploy (w4/m327, 2026-11-11)

Render removes an instance that fails its health check from rotation and restarts it ([render.com/docs/health-checks](https://render.com/docs/health-checks)). That is an instance event: the deploy list and the service keep describing the live deploy. bex reported it as a rollout. A served pod's lost readiness made `reportRolloutProgress` stamp phase `Deploying` on every surface. The saved-changes notice, reading that phase, said the settings would "go live when the current deploy finishes", though no deploy existed and none would apply them.

- **The phase stays Running** when the Deployment runs the active revision, which is the release, and the App was Running (`servedReleaseOutage`). Ready stays False with the diagnosis (`HealthCheckFailing`, a crash, quota or node loss). The outage is reported by `server_failed` / `server_available` and their notifications, as before: with no ready instance bex-api reads it as `readiness_failed`, and with one still serving, as healthy.
- **Unchanged:** a newer release rolling, a pre-deploy step, a first release, and the live release starting after a wake or a resume (it was Hibernated, so it reads Deploying, above).
- **Saved changes apply only with a release.** `undeployedChangesApplying` is true while a newer release is requested (its stamp) or rolling (Deploying a release other than the active one), never for a phase alone. During the outage, or a wake, the notice is "Use a standard deploy to apply them".
- **The Events reason** reads "A running instance failed its health check.", naming the check the service's Settings configure, where it said "readiness checks".
- **Not verified on Render:** its header and services-list badge during an instance failure. Its docs describe the failure as an instance event only.

## A platform refusal reads as a support reference (w9/090, 2026-11-12)

Render reports a failure on its own side as an internal error and asks the customer to contact support. bex copied the API server's refusal of the operator's own write verbatim. On 2026-11-12 a failed deploy and its Events entry read `deployments.apps "…" is forbidden: ValidatingAdmissionPolicy 'bex-operator-workloads' with binding 'bex-operator-workloads' denied request: …`. That names an internal policy and the tenant namespace, and the customer can do nothing about it.

- **What is replaced.** The API server can refuse a request the operator makes for an App: an admission policy or webhook denial, a webhook it could not call (`failed calling webhook`, which names the webhook's Service), RBAC (`Forbidden`), or a schema check (`Invalid`). The App's status then records the `platform_error` sentence in place of the refusal: "bex could not apply this release because of a platform error, not a problem with your code or settings. Contact support with reference `g<generation>-<8 hex>`". This applies to every message `fail` records: `Ready=False` under every reason it is given (`DeployFailed`, `ServiceFailed`, `IngressFailed`, `NetworkPolicyFailed`, …) and a build failure's `Build` verdict. It also applies to the `Rollout` verdict of a release refused before dispatch and to the verdict of a pre-deploy step that could not start (`status.preDeploy`). bex-api copies these into the deploy's `failureReason` and the Events feed unchanged, so REST, GraphQL and MCP return the sentence, and the dashboard words it by its code.
- **Pods the served release cannot create.** While a newer release waits for the served one to start, `Ready=ServedReleaseCannotStart` quotes the ReplicaSet's `FailedCreate` text, which is the API server refusing the pod. A refusal other than a quota now reads "the previously deployed release cannot create its pods because of a platform error, not a problem with your code or settings (contact support with reference …)". The wait budget sentence follows it unchanged.
- **The reference** is the release's generation (`status.releaseGeneration`, not `metadata.generation`) and the first 8 hex digits of a SHA-256 over the App's UID and the raw text. A retry that meets the same refusal gives the same reference, even across a settings save, so the condition does not churn and one refusal reads the same on Ready and on its verdict. The operator logs the raw refusal at error level with `reference`, `app`, `namespace`, `generation`, `releaseGeneration` and `reason` when the status does not show that reference yet. A retry whose status already shows it logs at V(1), so a refusal is one error line, not one per backoff retry. The pass still returns the raw error, so controller-runtime requeues with backoff.
- **What keeps its text.** A ResourceQuota refusal (`exceeded quota`) names the workspace plan's limit, which the customer can raise. Every diagnosis the operator writes itself keeps its text too (image pull, health check, crash, build output, pre-deploy exit), as do API errors that are not refusals, such as not found. Database and Key Value conditions are unchanged.
- **Customer input never reaches a refusal.** An Invalid that a customer setting caused would now read as a platform error, so bex-api must refuse that setting first. A disk mounted at `/bex-health` duplicated the health-probe volume's mount and made the Deployment Invalid; that path is now a reserved disk mount path ([ADR082](ADR082-persistent-disks.md)).
- **Rejected: replacing the text in bex-api.** bex-api sees only text. Only the operator knows which failures were refusals, and only its log holds the line support needs.
- **History:** deploy rows closed before this change keep the text they were stored with.

## Literal commands and environment carriers (w8/206, 2026-10-28)

The kubelet expands `$(NAME)` and collapses `$$` in literal `env[].value`, `command` and `args` before starting a container. Bex protects authored text at each Kubernetes projection boundary with `execution.KubernetesLiteral`: each dollar becomes two dollars for that one pass. The shell or executable then receives the original text. This covers start/cron/pre-deploy argv, direct runtime env values, platform Git metadata, native Dockerfiles, indexed build env/file lists, builder paths and Bex's clone inputs. Secret/FieldRef values and platform scripts that deliberately reference Kubernetes env variables retain their existing transport. kpack build env is protected before kpack copies it into its build Pod; its Git source CRD URL/ref remains raw intent consumed by the upstream source resolver.

Release records retain raw authored specs and recorded PodTemplates. Raw specs pass through projection once; launch recognition accepts current protected argv and historical raw argv; cancel restores its recorded template verbatim. Affected runtime templates roll once to adopt the corrected command/env bytes. Native artifacts already built with altered command bytes adopt the correction on a requested rebuild, whose normal rebuild nonce already invalidates artifact reuse.
