# ADR090 — Agent-owned delivery: the coding agent commits, pushes and opens its draft PR

**Status:** Accepted, 2026-10-22. Implementation is tracked in `w10/m13`. This ADR supersedes the driver-owned half of [ADR047](ADR047-cloud-coding-agent-sessions.md) D4 ("delivery is deterministic and enforced outside the agent") and the evidence digest that ADR047 D4 kept on the wire. It retires [ADR062](ADR062-sandbox-credential-vault.md) D7, which kept the scrub machinery as defense in depth, and the standalone real-key driver mode. ADR051, ADR054 and ADR059 carry matching amendments.

**Source:** user request 2026-10-22: the agent, not a program, should commit the code. The follow-up asked why the platform interferes at all. The answer is that the driver-owned path's main justification, scanning for a real model key before push, has been void since ADR062.

**Related decisions:** [ADR047](ADR047-cloud-coding-agent-sessions.md) (session product, Git proxy, Completer), [ADR051](ADR051-agent-session-transcript.md) (durable transcript), [ADR059](ADR059-agent-sandbox-hibernation.md) (hibernation and dirty-tree retention; superseded 2026-10-25), [ADR062](ADR062-sandbox-credential-vault.md) (placeholder-only sandbox, model proxy), [ADR084](ADR084-security-review-round22.md) #17 (pre-push scan bypass rejected).

## Context

### What ships today

After each headless turn the in-sandbox driver stops the agent, scrubs persisted state for credential bytes, runs `git add -A`, writes one `bex agent: <prompt first line>` commit, scans every new Git object for credential needles, pushes `bex-agent/<id>` and writes `{delivery, evidence, scrubbedFiles}` into its status file. The bex-api Completer reads that file through the gateway exec boundary, opens a draft PR through the GitHub App with a metadata-only body, and records `headSha`/`prUrl`/`prNumber`/`evidence`.

So the deliverable is one squash commit with a template message and a PR body that says nothing about the change. Agents already write better commits and PR descriptions than this. Users of Devin, Copilot coding agent, Open SWE and Claude Code on the web expect them to.

### Why the driver-owned path existed, and why that reason is gone

The driver commit was the only place the platform could guarantee a credential scan ran before anything left the sandbox. That mattered when the sandbox held the tenant's real model key ([ADR056](ADR056-security-review-round5.md) #6, [ADR063](ADR063-security-review-round9.md) #1). It no longer does:

- **Placeholder-only sandbox.** Since ADR062 and ADR064, hosted sandboxes hold only `ModelKeyPlaceholder` (`lego/backend/internal/agentsession/model.go`). The real key is injected by the gateway model proxy on its upstream hop. The sandbox lifecycle admits nothing else.
- **Branch-pinned Git proxy.** The GitHub token never enters the sandbox either. The gateway parses every receive-pack and refuses any ref other than the session's bound branch (`lego/backend/internal/sshgateway/agentcred/agentcred.go` `validateReceivePack`).
- **The bypass was already accepted.** [ADR084](ADR084-security-review-round22.md) #17 rejected "agent can bypass the driver's pre-push credential scan" for exactly these two reasons. The agent can push mid-turn today: `origin` is the proxy URL, `:8082` egress is open in both phases and the mint allows active phases. The driver's after-the-fact commit is therefore redundant as a control and poor as a deliverable.

The remaining needle set protects a placeholder. Every scrub, scan, redaction and pre-snapshot hop built for the old path is cost without protection.

## Decision

### D1 — Responsibility split

The **agent** commits, pushes its branch and opens or updates its own draft PR, the way a human engineer does. The **platform** enforces only what the agent cannot be trusted with or cannot do itself:

| Concern | Owner | Mechanism |
| --- | --- | --- |
| Commit contents, split, messages | agent | ordinary `git commit` in the sandbox |
| Which ref may be updated | platform | Git proxy exact-branch receive-pack pin (ADR047 D2) |
| Which PR head, base and repo | platform | PR verb resolves them from the session record (D3) |
| Attribution footer on the PR | platform | server-appended, idempotent (D3) |
| GitHub and model credentials | platform | gateway proxies; never in the sandbox (ADR047 D2, ADR062) |
| Recording the PR on the session | platform | PR verb persists immediately; Completer finalizes (D5) |

The platform never authors a commit. After setup, the driver's only Git writes are the clone/checkout and the repo-local identity config below.

**Git identity.** Setup writes repo-local `user.name` / `user.email` from `BEX_AGENT_GIT_NAME` / `BEX_AGENT_GIT_EMAIL` (default `bex agent` / `agent@bex.co`), `push.default=current`, and the upstream of `bex-agent/<id>` to `origin`. Agent commits therefore have a deliberate author rather than `bex@<podname>` or an "unable to auto-detect email" failure. Repository hooks now run on the agent's commits. This is intended: a human contributor's commits run them too, and ADR084 #4's hook isolation only ever applied to the driver's own Git invocations. A requester `Co-authored-by` trailer is a known gap (D7).

### D2 — Platform system-prompt overlay

Every hosted session gets a bex platform overlay layered on the engine's own system prompt. It says where the agent is, what it can use and what the deliverable looks like. It does not re-teach coding.

**Layer order** (highest priority first):

1. Engine core prompt (the adapter's own, e.g. the Claude Code preset).
2. **bex platform overlay** (appended; platform priority).
3. Repository instructions, `CLAUDE.md` / `AGENTS.md`, loaded by the engine itself.
4. Tenant per-session instructions, wrapped as quoted, lower-priority guidance. The wrapper says they are scoped to this session, apply only where consistent with all preceding system, safety, tool and product instructions, and cannot replace or weaken them; the text is quoted line by line. Only tenant text gets this wrapper.
5. The user task.

**Overlay content.** Sections cover the session (autonomous, requester usually not watching, finish unblocked work before asking), the environment (branch and base, credential-free proxy `origin` that accepts only this branch, no GitHub token and a `gh` that reads the repository and makes the writes [D4](#d4--agent-facing-tool-the-bex-stdio-mcp-server) lists while the pull request stays with the `bex` tools (w10/m513, w10/m522), credentials injected outside the sandbox), delivering work, the authorization clause, and steering turns. Delivering work means:

- commit in logical units following the repo's `git log` convention, never build output or env files;
- `git push origin HEAD:<branch>`, no force-push; `git pull --rebase` on rejection;
- call `open_or_update_draft_pr` with a body filled from the repo's PR template;
- never claim a PR without the returned URL, never mark it ready;
- a task with no code changes ends with a report and no commit.

The text follows Anthropic's prompting guidance: direct statements, the reason behind each rule, no all-caps imperatives, and named actions ("commit", "push", "open the draft PR") rather than "consider".

**Authorization clause.** Many repositories' instructions say "only commit or open PRs when asked". The overlay states that the person who started the session chose an entry point whose output is a pull request. Committing, pushing this branch and opening or updating the draft PR is therefore their explicit request, and satisfies such rules. Repo rules about commit style, tests and formatting still apply. Without this clause, a well-behaved agent obeying `CLAUDE.md` would finish the task and deliver nothing.

**Channel per adapter.**

- **ACP `systemPrompt`.** When `initialize` advertises `agentCapabilities.sessionCapabilities.systemPrompt`, the driver sends `systemPrompt: {mode: "append", content: [{type: "text", text}]}` on `session/new` **and** `session/load`, re-sent on every lifecycle call as the RFD requires. claude-agent-acp supports this from 0.92; bex pins 0.94.0. An `invalid_params` reply fails the turn with a named reason; there is no silent retry without the overlay.
- **Codex.** codex-acp 1.4.0 has no ACP field. The overlay goes through Codex `developer_instructions` if that channel is verified in the pinned adapter; otherwise the preamble below.
- **Fallback.** Any other adapter gets the overlay as a first-prompt preamble through the existing continuity path (ADR047 D3 continuity amendment). It is never published into the stream.

**Claude settings.** Through `_meta.claudeCode.options` the driver disables Claude Code's built-in git/PR instructions (`includeGitInstructions: false` / `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1`) and blanks `attribution.pr` and `attribution.commit`. The built-in instructions say "only commit when asked" and use `gh pr create`; both contradict the overlay. With them off, the overlay is the single delivery contract and the server footer the single attribution. `excludeDynamicSections: true` keeps the system prompt identical across sandboxes for cache reuse.

### D3 — The `pull-request` verb

The PR-side twin of the Git proxy's exact-branch rule: one narrowly-scoped, credential-free way for the sandbox to open or update its own draft PR.

- **Gateway.** On the `:8082` mux, at the Git proxy path plus `/pull-request`. `POST` with JSON `{title, body}`. `title` is a single line of at most 256 runes; `body` is at most 60000 bytes. It reuses the Git proxy's chain unchanged: Pod source-IP resolution, `agentsession.AuthorizePod` label digests, limiter and budgets, audit.
- **Internal hop.** The gateway calls bex-api's internal listener (`:8091`) at `/v1/agent-session-pull-requests` over the existing HMAC hop. bex-api re-checks the live sandbox generation and phase, as the Git mint does.
- **Server-filled fields.** Owner, repo and base come from the session record. Head is pinned to the bound `bex-agent/<id>` branch. The agent cannot name any of them.
- **Typed refusals.** `branch_not_pushed`, `not_ahead`, `invalid_request`, `too_large`, `forbidden`, `upstream_error`.
- **Semantics.** It creates a **draft** PR, or updates the title and body of the existing open PR for that head. It never undrafts. bex-api appends a server-side footer behind a `<!-- bex-agent-footer -->` marker; an update replaces anything after an existing marker, so the footer is idempotent and always present. `prUrl`, `prNumber` and `headSha` are persisted on the session immediately, so REST, GraphQL and MCP show the PR mid-turn.
- **A taken-over PR (w9/m348).** A session that a `/bex` comment started on a person's PR still pushes only its own `bex-agent/<id>` branch, started from that PR's head ([ADR094 D3](ADR094-coding-agent-mcp.md#d3--create_agent_session-input)). For it the verb opens no PR and never touches the title, body or draft state. It reads the session branch's head on GitHub and fast-forwards the PR's head branch to it (`PATCH …/git/refs/heads/<head>`, `force: false`); it compares the two first, so behind or diverged is `pr_branch_diverged` with the merge to run, a write GitHub refuses anyway is a branch rule (`pr_branch_protected`, not retried), and a closed PR is `pull_request_closed`. It records the new head and answers `{url, number, created: false, headSha, takenOver: true}`. The overlay replaces the draft-PR delivery steps with "push your branch, bring the PR up to date with the tool, merge on divergence, reply with `reply_on_pull_request`", and the delivery check nudges a turn whose PR lacks its pushed head.

### D4 — Agent-facing tool: the `bex` stdio MCP server

The agent image ships a stdio MCP server named `bex` with one tool, `open_or_update_draft_pr({title, body})`, which calls the D3 verb. The driver registers it in `mcpServers` on `session/new` and `session/load`. Stdio is the one MCP transport every ACP agent must support; HTTP/SSE MCP is optional. A tool is a first-class, schema-validated affordance in every engine, unlike a curl recipe in the prompt. `gh` is not installed, so there is no second PR path to guard.

_Amended 2026-11-19 (w10/m513): `gh` is installed and reads; it never writes._ An agent that cannot read its repository's CI cannot reproduce a red run or check the PR it delivered, and the bex-co/beancount-io automation runs of 2026-11-15..18 said so. Devin's machine "can carry a GitHub CLI (`gh`) token that lets Devin use GitHub features directly through the GitHub API", which a security profile can remove ([Security profiles](https://docs.devin.ai/product-guides/security-profiles), read 2026-11-19). bex gives the same working `gh` with no token in the sandbox, as [ADR047 D2](ADR047-cloud-coding-agent-sessions.md#gh-reads-amendment-w10m513-2026-11-19) describes:

- **Wiring.** gh's `http_unix_socket` setting sends every call over a Unix socket the driver serves, as plain HTTP with the GitHub host in the `Host` header (verified with gh 2.105.0, the pinned version). The driver forwards `api.github.com` calls to the gateway's `github-api` route, `<Git proxy URL>/github-api/<path>`, and refuses any other host. `GH_TOKEN` is a placeholder gh needs before it calls anything; `GH_REPO` names the session's repository, because `origin` is the Git proxy.
- **What it admits.** REST `GET` and `HEAD` on `/repos/<owner>/<repo>` and below, for the session's repository only, and `POST /graphql` when every operation is a query whose top-level fields are `repository` with that owner and name (literal or variable), `node`/`nodes`, `rateLimit` or the schema. That covers `gh run list`, `gh run view --log-failed`, `gh pr view`, `gh pr checks` and `gh api repos/{owner}/{repo}/…`. A `node` lookup by id is scoped by the token below, which GitHub enforces. Paths with `..`, `.`, `//` or encoded separators, other repositories, `/repositories/<id>`, `/user`, `/search` and the rest of the API are refused.
- **The token.** bex-api mints it per call through a new internal verb (`/v1/agent-session-github-read-credentials`, the mint's HMAC and checks), narrowed to the one repository with `actions`, `checks`, `statuses`, `pull_requests` and `contents` read and `metadata` read. An installation that has not granted Actions or Commit statuses gets `checks`, `contents` and `pull_requests` read, so `gh run` then answers with GitHub's own 403. The gateway injects it on the upstream hop only. GitHub's redirects to its log and archive storage are followed by the gateway itself with a fresh request that carries no token, and only to GitHub's and Azure Blob's hosts over HTTPS. Token scopes and expiry headers are not relayed.
- **Writes stay refused.** _Superseded by the w10/m522 amendment below, which admits comments, reviews, labels, issues and CI re-runs._ Any other method, and any GraphQL mutation, answers `403` in GitHub's error shape, which gh prints: "bex: gh in this session only reads <repo> (CI runs and logs, checks, pull requests and contents). Open or update the pull request with the open_or_update_draft_pr tool of the bex MCP server, and reply on it with reply_on_pull_request." The D3 verb therefore stays the one pull-request path, and Claude Code's built-in `gh pr create` instructions stay off (D2).
- **Budget.** The route counts calls per session (`BEX_AGENT_GITHUB_API_MAX_REQUESTS_PER_SESSION`, default 1000) and per workspace (10000), separately from the Git budget, so reads can never spend the exchanges a session needs to push. GitHub's installation rate limit is shared with every other use of the App.
- **The overlay** says that `gh` reads the repository's CI runs, checks, pull requests and contents, that it cannot write, and that pull requests stay with the `bex` tools.

_Amended 2026-11-19 (w10/m522): `gh` writes on the session's repository what Devin's `gh` writes, except the pull request itself and code._ An agent that finds a flaky failure should re-run it, answer a reviewer in the thread where the question was asked, and open an issue for what it found but did not fix, without a person or a new `bex` tool. Devin's machine "can carry a GitHub CLI (`gh`) token that lets Devin use GitHub features directly through the GitHub API" ([Security profiles](https://docs.devin.ai/product-guides/security-profiles)), and its App holds pull requests write ("create new PRs"), Actions write ("rerun workflows"), issues write ("open new issues"), commit statuses write and contents write ([GitHub integration](https://docs.devin.ai/integrations/gh), both read 2026-11-19). bex admits those writes on the session's repository with two hardenings Devin does not document: the pull request is opened and changed only by the D3 verb, which records it and its footer, and code and refs move only through the Git proxy, which accepts only the session branch. The requests below were recorded from the pinned gh 2.105.0 through a socket that forwarded reads to GitHub and answered every write itself; the command-by-command table is in [w10/m522](../.pm/w10/done/m522/README.md#design-record-t001-2026-11-19), and `lego/backend/internal/sshgateway/agentcred/testdata/gh-2.105.0-requests.json` replays it in a test.

- **Admitted REST writes**, under `/repos/<the session's repository>/` only, with no query string:
  - Comments: `POST issues/{n}/comments`, `PATCH`/`DELETE issues/comments/{id}`; review comments `POST pulls/{n}/comments`, replies `POST pulls/{n}/comments/{id}/replies`, `PATCH`/`DELETE pulls/comments/{id}`; reactions on issues, issue comments and review comments.
  - Reviews: `POST pulls/{n}/reviews` and `POST pulls/{n}/reviews/{id}/events` whose `event` is not `APPROVE`, `PUT`/`DELETE pulls/{n}/reviews/{id}`; requested reviewers `POST`/`DELETE pulls/{n}/requested_reviewers`.
  - Issues and their labels and assignees: `POST issues`, `POST`/`PUT`/`DELETE issues/{n}/labels[/{name}]`, `POST`/`DELETE issues/{n}/assignees`.
  - Actions: `POST actions/runs/{id}/rerun` (`gh run rerun`, with `{"enable_debug_logging":true}` for `--debug`), `…/rerun-failed-jobs` (`--failed`), `…/cancel` and `…/force-cancel` (`gh run cancel [--force]`), and `POST actions/jobs/{id}/rerun` (`--job`).
- **Admitted GraphQL mutations**, when every top-level field of the document is one: `addComment`, `updateIssueComment`, `deleteIssueComment` (`gh pr comment`, `--edit-last`, `--delete-last`, `gh issue comment`); `addPullRequestReview` and `submitPullRequestReview` whose `event` is not `APPROVE` (`gh pr review --comment`/`--request-changes`), `updatePullRequestReview`, `deletePullRequestReview`, `addPullRequestReviewComment`, `addPullRequestReviewThread`, `addPullRequestReviewThreadReply`, `updatePullRequestReviewComment`, `deletePullRequestReviewComment`; `addReaction`, `removeReaction`; `addLabelsToLabelable`, `removeLabelsFromLabelable`; `requestReviews`, `requestReviewsByLogin`; `addAssigneesToAssignable`, `removeAssigneesFromAssignable`, `replaceActorsForAssignable` (`gh pr edit --add-label/--add-assignee/--add-reviewer`); `createIssue`, `updateIssue`, `closeIssue`, `reopenIssue` (`gh issue create/edit/close/reopen`); and `updatePullRequest` only when its input sets nothing but labels, assignees or the milestone. gh's `pr edit --add-reviewer` sends an `updatePullRequest` that names only the pull request before `requestReviewsByLogin`. A node id is scoped by the token's one-repository narrowing, which GitHub enforces, and GitHub resolves each id as its own type: `updateIssue` or `closeIssue` with a pull request's id answers "Could not resolve to Issue node" (checked 2026-11-19). `gh issue close <n>` on a pull request's number sends `closePullRequest` instead, which stays refused.
- **Refused, and why.** Every other write answers `403` in GitHub's error shape before anything reaches GitHub, and a GraphQL document that holds any refused mutation, subscription or query field is refused whole:
  - The pull request itself: `POST pulls`, `PATCH pulls/{n}`, and `createPullRequest`, `updatePullRequest` with a title, body, base, state or `maintainerCanModify`, `markPullRequestReadyForReview`, `convertPullRequestToDraft`, `mergePullRequest`, the auto-merge mutations, `closePullRequest` and `reopenPullRequest` (`gh pr create`, `pr edit --title/--body/--base`, `pr ready`, `pr merge`, `pr close`, `pr reopen`). D3 opens it as a draft and records it with its footer, and a person decides when it is ready and merged. REST `PATCH issues/{n}` is refused too, because GitHub treats a pull request as an issue there; gh's own issue edits use GraphQL.
  - Approvals: an `APPROVE` review event, REST or GraphQL, literal or from variables. GitHub counts an approval by an App installation that has write access toward a branch's required reviews, as a person's, so an agent could approve a person's pull request into a protected branch. Dismissing a review and `resolveReviewThread` are refused for the same reason: they can satisfy "dismiss stale reviews" and "require conversation resolution".
  - Code and refs: contents, git data, refs, `PUT pulls/{n}/update-branch` and `updatePullRequestBranch` (it merges the base into the head), `createLinkedBranch` (`gh issue develop`), `createCommitOnBranch`, releases. Code reaches GitHub only through the Git proxy, which accepts only the session branch.
  - Workflow dispatch (`gh workflow run`): a dispatch starts a new run on any ref with chosen inputs and the repository's secrets, while a re-run repeats a run that already ran, with its original actor's privileges. Approving a fork's pending run and deleting runs or their logs are refused.
  - Commit statuses and check runs, which branch protection can require.
  - Settings and administration: labels and milestones of the repository (`gh label create/edit/delete`), locks (`gh issue lock`, `gh pr lock`), transfers and deletion of issues, hooks, secrets, variables, environments, deployments, collaborators and the repository itself.
  - Every other repository, and every path outside `/repos/<repository>/`.
- **The refusal** says what `gh` can write here and names the tools: "bex: gh in this session reads <repo> and writes to it only to comment and reply, review without approving, label, assign, request reviewers, open, edit and close issues, and re-run or cancel Actions runs. Open or update the pull request with the open_or_update_draft_pr tool of the bex MCP server, reply on it with reply_on_pull_request, and change code only by pushing your session branch."
- **The write token.** bex-api mints one per admitted write through its own internal verb (`/v1/agent-session-github-write-credentials`, the read verb's HMAC, Pod, lifecycle, branch and owner checks, never for a repository environment build), audited as `agentsessions.MintGitHubWriteCredential`, allowed or denied, with the repository. It is narrowed to the one repository with `pull_requests`, `issues` and `actions` write, the read token's `checks`, `contents` and `statuses` read, and `metadata` read. It never holds `contents`, `workflows`, `statuses`, `checks`, `administration` or any other write. An installation that has not granted the whole set refuses it with 422; the mint then reads the installation's permissions (`GET /app/installations/{id}`) and asks for the intersection, so a write the installation lacks (for example Issues on an App from the older manifest) answers GitHub's own 403 while the others work. Reads keep the read-only token of the w10/m513 amendment.
- **Bodies.** A write's body and every GraphQL body are read after admission, up to 1 MiB, and must be one JSON value that repeats no key, so the gateway reads them as GitHub will. A write carries its parameters in its body: a query string on a write is refused. GitHub's redirect of a write is not followed.
- **Accountable.** Writes count against the route's per-session (1000) and per-workspace (10000) budgets with the reads. They post as the App's bot, and PR feedback ignores every author that is not a `User` ([ADR047 D11](ADR047-cloud-coding-agent-sessions.md#d11--pr-feedback-steers-the-session-w9m344-2026-11-12)), so a session's own comment never steers it. A re-run that fails again completes the same check suite, whose feedback row the session already has (`ON CONFLICT (session_id, source_key)`), so it does not steer the session a second time.
- **The overlay** says that `gh` reads the repository and makes these writes, that it cannot open, edit, approve, merge or close a pull request, dispatch a workflow or change code, branches or settings, and that the pull request itself stays with the `bex` tools. Claude Code's built-in git and PR instructions stay off (D2).

_Amended 2026-11-19 (w10/m524): a workspace admin can turn `gh` off._ As a Devin security profile can remove the `gh` token while sessions keep their Git integration, the agent environment's `githubCliEnabled` (on by default) turns every write and read above off for the workspace's sessions. While it is off, the read and write credential verbs refuse with the named refusal `github-cli-off` before any token is minted, audited as denied, and the route answers each call `403` in GitHub's error shape: "bex: gh is turned off for this workspace's agent sessions (the agent environment's GitHub CLI setting, githubCliEnabled). A workspace admin turns it back on in Settings → Agents or with `bex agent env set --github-cli on`. Pushes to your session branch and the bex MCP tools open*or_update_draft_pr and reply_on_pull_request still work." This refusal holds from a running session's next call. A turn dispatched while it is off also gets `BEX_AGENT_GITHUB_CLI=0`: the driver configures no socket, config or `GH*\*`variables, and the overlay says`gh`is off for the workspace and that the pull request still goes through the`bex` tools and code through pushes to the session branch. The D3 verb, the PR-comment verb and the Git proxy never read the setting. [ADR047 D2](ADR047-cloud-coding-agent-sessions.md#a-workspace-can-turn-gh-off-amendment-w10m524-2026-11-19) has the setting's surfaces, storage and timing.

_Amended 2026-11-20 (w10/027): `gh` works in the session's terminals too._ Devin's `gh` token is on the machine for every shell, so a person who opens a session's web Shell, `ssh` session or Zed and runs `gh run list` gets an answer there. The driver writes the agent's `GH_*` settings to a shell file beside its status file once the socket serves, and the image's profile script, which the web Shell's and SSH's `/bin/sh` reads through `ENV` and login shells and bash read as before, exports them. A terminal's `gh` therefore takes the same socket and the same gateway route: the same admitted writes, the same refusals naming the `bex` tools, the same budget and audit. It obeys the setting above: a turn dispatched with `gh` off removes the file, and the route refuses a running session's call naming the setting. The terminal runs as the agent's uid and could reach the socket already, so the file adds no access, and the sandbox still holds no token.

### D5 — Turn end: observe, nudge once, never commit

When the agent ends its turn, the driver computes read-only Git facts: `{dirty, unpushedCommits, remoteHead, baseBranch, prRecorded}`. If the work is undelivered (a dirty tree, unpushed commits, or a pushed branch ahead of base with no PR recorded), the driver sends the agent **one** follow-up prompt asking it to finish delivery, then recomputes the facts. The driver never commits or pushes.

The status file's `git{}` object replaces `delivery{}` and `evidence{}`. The Completer never opens or edits a pull request. It finalizes from the PR record the D3 verb already wrote. _Amended 2026-11-13 (w5/m382): its one GitHub access is a read of the session branch's head, through a one-method interface (`Completer.Heads`, served by `agentsession.BranchHeads`), so the head it records, and CI-failure steering keys on, is GitHub's rather than the sandbox's own report._ Work still undelivered after the nudge finalizes as **succeeded with a delivery note**, not failed: the agent's turn did succeed. _Amended 2026-10-25 (w10/m15): ADR059 hibernation and its dirty-git retention are retired. The tree stays only while the finished session's sandbox is alive, which is at most `BEX_AGENT_SANDBOX_IDLE_TTL` (2h) of idle time. After that the sandbox is terminated and undelivered work is lost. The post-turn nudge is the only guard, and the delivery note tells the user what was left behind._

### D6 — Deletions

These go away, end to end:

| Removed | Why it is dead |
| --- | --- |
| Evidence surface: REST/GraphQL/MCP `evidence` field and the `evidence` column (down-migratable drop) | No renderer since w5/m65. The ADR051 transcript carries the narrative; the digest was lossy and mislabelled. |
| Driver credential scrub, Git-object scan, secret-form (encoded) needles, redaction | Protects only the ADR062 placeholder. The agent can push mid-turn regardless (ADR084 #17). |
| Standalone real-key driver mode (no model proxy) | The model proxy is mandatory (ADR062/ADR064). The mode existed only for a verify script. |
| `POST /snapshot/scrub`, `bex-pre-snapshot`, the single-use snapshot grant | The OpenSandbox tenant key is never injected (ADR047 D2), and the Git and model credentials live in gateway proxies. The snapshot holds no live secret to scrub. |
| `credential-scrub-test.sh` CI step | Tests the removed machinery. |

The controls that still bound a sandbox are unchanged: default-deny egress, the placeholder-only model key, the branch-pinned Git proxy and the head-pinned PR verb.

### D7 — Out of scope and follow-ups

- Gateway-side non-fast-forward rejection, so a force-push is refused by the proxy and not only by the overlay. A `/bex` takeover does not depend on it: it never pushes the person's PR branch, which only moves by GitHub's fast-forward-only ref update.

## Platform OpenRouter route for an allowlisted workspace (2026-10-23)

**User decision 2026-10-23** (tracked in `w10/m14`): ship agent sessions on a bex-owned OpenRouter key now, but only for workspace `tea-d98210cbbpdc73dcrkvg`, and keep every other tenant off it until the economics are in place.

- **Scope.** bex-api's `BEX_AGENT_PLATFORM_MODEL_ROUTE=openrouter` applies to every workspace that has not set its own model key, and only to the claude profile. Until 2026-11-16 it covered only the `tea-` ids in an allowlist, `BEX_AGENT_PLATFORM_MODEL_WORKSPACES`; the user removed that allowlist on 2026-11-16 (w10/m14 t007). Unlike the dev route it runs on the production control plane. The route is resolved per workspace at create, steer and mint time, not from the endpoint a session stored, so an existing session moves onto it on its next dispatch. A workspace with its own key stays on `api.anthropic.com` with that key. With the route off, an explicit OpenRouter endpoint is refused. Workspaces on the route report `modelKeyReady` through the platform key. Because only the claude profile is routed, each capabilities profile also carries its own `modelKeyReady`, and a create or steer for a profile with neither the route nor the workspace's own key is refused `400 AGENT_SESSION_MODEL_KEY_REQUIRED` instead of failing minutes later on the model proxy (2026-11-06, w9/076). An unreadable key store still defers to the proxy.
- **Key custody.** The key lives in the `bex-system` Secret `bex-agent-platform-model` and flows to bex-api's env, then to the internal mint, then to the gateway's upstream hop. It never enters the sandbox, which still holds only `ModelKeyPlaceholder`, nor any API response, log, audit event or error. A missing Secret disables the route with a loud startup log rather than crash-looping bex-api.
- **Model pin.** The mint returns `pinnedModel`. The gateway refuses with 403 any request whose JSON top-level `model` is not exactly that id, appears twice, or carries OpenRouter's `models` fallback list or paid `plugins`. A tenant sandbox therefore cannot spend the platform key on a different model. Workspace BYO routes are not pinned. _Amended 2026-10-27 (w10/m17 t002):_ the pin is enforced before the gateway too. A session create that names a different `agentConfig.model` for the claude profile is refused with a typed 400 `AGENT_SESSION_MODEL_PINNED` (params `field`, `pinnedModel`) instead of failing mid-turn with the gateway's 403; an omitted or equal model records the pinned id. A steer always runs the pinned model, even for a session whose stored model predates the allowlist. The workspace agent environment reports `modelPinned`/`pinnedModel` and refuses a different `defaultModel` (`AGENT_ENVIRONMENT_MODEL_PINNED`).
  - _Amended 2026-11-19 (w10/m516): the pin is per session, inside a platform model catalog._ The one-model-per-workspace pin above existed so a sandbox could not spend the platform key on a more expensive model while nothing was priced. [ADR091](ADR091-agent-model-pricing.md) D1 now prices every platform request at its own reported cost × 1.3 under per-workspace spend caps, so a person chooses the model, as Devin's agent selector lets them ([Your First Session](https://docs.devin.ai/get-started/first-run), read 2026-11-19). The security property stays: the mint pins the session's choice, so the sandbox still cannot pick another model.
    - **Catalog source.** `BEX_AGENT_PLATFORM_MODEL` is the default and the catalog's first model. `BEX_AGENT_PLATFORM_MODELS` is a comma-separated list of further OpenRouter ids, in the order pickers show them. It is deploy configuration (`lego/operator/config/api/deployment.yaml`), not code, so changing it needs no image release. A malformed or repeated entry refuses startup. There are no aliases: an Anthropic-style id such as `claude-opus-5-5` is refused with the catalog's own ids listed, so a name never maps to a model the person did not see. Labels are the ids themselves.
    - **Initial catalog (production, 2026-11-19).** `deepseek/deepseek-v4.1-flash-1017` (default), `anthropic/claude-haiku-5.5` (cheaper per token), `anthropic/claude-sonnet-5.5` and `anthropic/claude-opus-5.5` (stronger). Each answered a live probe on 2026-11-19 at 14:31Z, made with the platform key (never logged) on `https://openrouter.ai/api/v1/messages`: a tool-use request with `"tool_choice":{"type":"auto"}` and `"provider":{"data_collection":"deny"}` returned 200 with `stop_reason: tool_use` and the model's own `usage.cost`, and a streamed request carried `usage.cost` on `message_delta`, which the gateway meters. The 5.5 Sonnet and Opus refuse a forced `tool_choice` (`any`/`tool`); Claude Code sends `auto`. A model added later must pass the same probe first, and the probe is recorded here.
    - **Resolution.** On a workspace without its own key, a claude session's model is the request's catalog model, else the workspace default when the catalog offers it, else the catalog's first model. The session records it in `agentConfig.model`. The sandbox gets it as `ANTHROPIC_MODEL` and the three `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL` slots. The mint returns it as `pinnedModel`, and the gateway refuses any other request model with a 403. A stored model that left the catalog runs the default and never strands a session: on a steer, at the mint, in an automation run (whose run record says so). A session created on the route before its workspace set its own key drops its catalog model for the workspace default on its next turn.
    - **Errors.** A model outside the catalog is refused before anything runs. `400 AGENT_SESSION_MODEL_NOT_OFFERED` covers a session create, a message, and an automation's template (params `field`: `agentConfig.model`, or `model` on a message; `model`; `models`, the offered ids). `400 AGENT_ENVIRONMENT_MODEL_NOT_OFFERED` covers the workspace default (`field: defaultModel`). `AGENT_SESSION_MODEL_PINNED` stays for the profiles with one fixed model (`muse`, ADR108 D4; `deepseek`, ADR114). `AGENT_ENVIRONMENT_MODEL_PINNED` is retired. The environment keeps `modelPinned` (true on the route: each session is pinned) and `pinnedModel` (now the catalog default) for older clients, and adds `models`.
    - **The switch on a message.** A message (REST `model`, GraphQL `model`, MCP `model`, `bex agent send --model`, chat `/model`) may name a model. Every turn runs in a fresh sandbox ([ADR047](ADR047-cloud-coding-agent-sessions.md) D8 phase 1; a kept disk boots a new pod too), so the new model needs no ACP model call and no agent restart: the turn's begin records it as `agentConfig.model` in the same transaction that starts the turn, the new pod reads it from its env, and the mint pins it. A queued message switches the model when it is delivered, not when it is queued. A model that left the catalog while the message waited runs the default rather than failing the message. A message without a model keeps the session's model. The pinned `@agentclientprotocol/claude-agent-acp` is never asked to change models in place.
    - **A workspace narrows the catalog** _(amended 2026-11-20, w10/m527)_. A workspace admin may turn catalog models off (`enabledModels` on the agent environment, stored as the opt-out `agent_environments.disabled_models`), as Devin's admins allowlist models. The catalog default can never be turned off, and a model added to the catalog later starts on. Resolution above then reads "the request's offered model, else the workspace default while it is offered, else the catalog's first model", where offered means in the catalog and not turned off. A model turned off is refused up front exactly as one outside the catalog (`AGENT_SESSION_MODEL_NOT_OFFERED`, `AGENT_ENVIRONMENT_MODEL_NOT_OFFERED`, listing only the offered models), and a write leaving the default off or naming a non-catalog model is `AGENT_ENVIRONMENT_MODELS_INVALID`. The mint is unchanged: it pins the model the session recorded, so a turn in flight keeps it, and the session's next dispatch runs the fallback. A workspace default an admin turns off stops taking effect and the catalog default runs, as Devin's pinned default does outside its allowlist. The full record is [ADR047](ADR047-cloud-coding-agent-sessions.md) D7's w10/m527 amendment.
- **Follow-ups (not in this step).** Per-workspace token metering and pricing, plan quotas plus an OpenRouter-side spend cap, and a data policy for platform-key traffic. Widening the route to every workspace is dated in `w10/m14` t007.

### Metering, price/quota mechanism and data policy (2026-10-27, w10/m14 t003–t006)

- **Metering.** For a platform-key `/v1/messages` exchange (the mint returned `pinnedModel`), the gateway tees the relayed response and never buffers or alters it. It reads Anthropic usage from a JSON body or from the SSE `message_start` and `message_delta` events. It then reports `{requestId (amr-…), session, workspace, model, input/output/cache-read/cache-write tokens}` to bex-api's internal `POST /v1/agent-session-model-credentials/usage` over the same HMAC and nonce as the mint. A bounded queue, retries under one request id, and a dropped report is logged and counted in `bex_ssh_gateway_model_proxy_usage_reports_total{result}`; metering never fails a model response. bex-api records each request id once (`agent_model_usage_events`) into `usage_hourly`. The rows are `resource_kind=agent_session`, `service_id=<ags-…>`, `tier=<model>`, with kinds `agent_model_{input,output,cache_read,cache_write}_tokens`. BYO-key traffic is never metered.
- _Superseded for billing by [ADR091](ADR091-agent-model-pricing.md) (2026-10-30): price = provider cost × 1.30 via one `agent_model_cost_microusd` meter, a monthly USD spend cap (`AGENT_MODEL_SPEND_CAP_REACHED`) replacing the token quota, threshold billing and settle-before-delete. The token meters below remain for display._
- **Price and quota mechanism, shipped disabled** (superseded by [ADR091](ADR091-agent-model-pricing.md): cost-based pricing, and D5 monthly USD spend caps with code `AGENT_MODEL_SPEND_CAP_REACHED` replaced the token quota in w10/m14 t005). `pricing.yaml` `agentModel.models[]` prices each model in USD per 1M tokens per kind. Each priced kind becomes a Stripe lookup key `agent_model_<kind>_tokens.<model>`. `agentModel.monthlyTokenQuota[]` caps a plan's month-to-date total of all four kinds; the mint checks it and refuses with HTTP 429, refusal header `model-quota-exceeded`. The gateway then answers the agent with an Anthropic-shaped 429 whose `error.code` is `AGENT_MODEL_QUOTA_EXCEEDED`, and fails the session with a readable reason and `failureReasonCode`. Both lists ship empty: tokens are metered and shown but nothing is charged or capped until the user sets numbers. The OpenRouter key's credit limit remains the spend backstop.
  - Superseded by [ADR091](ADR091-agent-model-pricing.md): each request is now priced at its upstream cost × `agentModel.markup` and billed on one model-agnostic `agent_model_cost_microusd` meter; the per-model token prices and meters above are gone.
- **Data policy.** The gateway JSON-merges `"provider":{"data_collection":"deny"}` into every platform-route Messages request, so OpenRouter routes only to providers that neither store prompts non-transiently nor train on them. A client-supplied `provider` object is refused with 403 alongside `models`/`plugins`, so the policy cannot be weakened. A live check on 2026-10-27 confirmed that `/api/v1/messages` validates this field (a bad value returns 400 naming `provider.data_collection`). With `deny`, `deepseek/deepseek-v4.1-flash-1017` still answered 200. `count_tokens` is not rewritten. The customer-facing terms disclosure is a pending user/legal decision.

## Prior art

Paraphrased from public documentation and source; no leaked or GPL prompt text is copied.

- **ACP client-provided system prompt RFD** ([agentclientprotocol.com/rfds/client-system-prompt](https://agentclientprotocol.com/rfds/client-system-prompt)). The client may send `systemPrompt` with `append` or `override` mode on session new/load/resume/fork. Support is advertised as a session capability. An unsupported request is an `invalid_params` error, not a silent fallback. The RFD is still unstable.
- **claude-agent-acp PR #1366.** Maps `append` to the Claude Code preset plus appended text. It keeps the user/project/local setting sources, so `CLAUDE.md` / `AGENTS.md` still load, and accepts `_meta.claudeCode.options` overrides.
- **codex-acp PR #653.** Append-only support through Codex developer instructions, in preview tags only.
- **Claude Agent SDK, modifying system prompts** ([code.claude.com/docs/en/agent-sdk/modifying-system-prompts](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts)). Describes preset-plus-append, the switch for the built-in git instructions, attribution settings and excluding dynamic sections.
- **Open SWE** ([github.com/langchain-ai/open-swe](https://github.com/langchain-ai/open-swe)). The agent commits and pushes itself. An `open_pull_request` tool appends the platform footer, and a guard blocks other PR-creation paths.
- **GitHub Copilot coding agent** ([risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)). Pushes to a single branch only; the platform opens a draft PR.
- **Devin PR templates** ([docs.devin.ai/integrations/pr-templates](https://docs.devin.ai/integrations/pr-templates)). PR bodies follow the repo's template, found by a documented lookup order.
- **Claude Code on the web** ([code.claude.com/docs/en/cloud-environments](https://code.claude.com/docs/en/cloud-environments)). A cloud environment where the agent works on a branch and delivers through Git.
- **Anthropic prompting best practices.** Be direct, explain why, avoid over-emphatic imperatives that make current models over-trigger.

## Consequences

- Agent PRs read like a teammate's: a reviewable commit history, a templated description, and a bex footer.
- About 1,000 lines of driver and backend delivery, evidence and scrub code, plus a CI script, are deleted.
- The PR appears on the session as soon as it exists, not only at finalize.
- Delivery now depends on the agent following the overlay. The one-nudge check and the delivery note make a miss visible without the platform authoring code. Since 2026-10-25 nothing keeps undelivered work past the 2h idle close: the nudge is the only guard.
- `evidence` disappears from REST, GraphQL and MCP. This is a bex-only surface with no Render equivalent; `w10/m13` t012 checks the three surfaces, the dashboard and mobile agree.
