# ADR090 — Agent-owned delivery: the coding agent commits, pushes and opens its pull request

**Status:** Accepted, 2026-10-22. Implementation is tracked in `w10/m13`. This ADR supersedes the driver-owned half of [ADR047](ADR047-cloud-coding-agent-sessions.md) D4 ("delivery is deterministic and enforced outside the agent") and the evidence digest that ADR047 D4 kept on the wire. It retires [ADR062](ADR062-sandbox-credential-vault.md) D7, which kept the scrub machinery as defense in depth, and the standalone real-key driver mode. ADR051, ADR054 and ADR059 carry matching amendments.

**Source:** user request 2026-10-22: the agent, not a program, should commit the code. The follow-up asked why the platform interferes at all. The answer is that the driver-owned path's main justification, scanning for a real model key before push, has been void since ADR062.

**Related decisions:** [ADR047](ADR047-cloud-coding-agent-sessions.md) (session product, Git proxy, Completer), [ADR051](ADR051-agent-session-transcript.md) (durable transcript), [ADR059](ADR059-agent-sandbox-hibernation.md) (hibernation and dirty-tree retention; superseded 2026-10-25), [ADR062](ADR062-sandbox-credential-vault.md) (placeholder-only sandbox, model proxy), [ADR084](ADR084-security-review-round22.md) #17 (pre-push scan bypass rejected).

## Context

### What ships today

After each headless turn the in-sandbox driver stops the agent, scrubs persisted state for credential bytes, runs `git add -A`, writes one `bex agent: <prompt first line>` commit, scans every new Git object for credential needles, pushes `bex-agent/<id>` and writes `{delivery, evidence, scrubbedFiles}` into its status file. The bex-api Completer reads that file through the gateway exec boundary, opens a draft PR through the GitHub App with a metadata-only body, and records `headSha`/`prUrl`/`prNumber`/`evidence`.

So the deliverable is one squash commit with a template message and a PR body that says nothing about the change. Agents already write better commits and PR descriptions than this. Users of Devin, Copilot coding agent, Open SWE and Claude Code on the web expect them to.

### Why the driver-owned path existed, and why that reason is gone

The driver commit was the only place the platform could guarantee a credential scan ran before anything left the sandbox. That mattered when the sandbox held the tenant's real model key ([ADR056](ADR056-security-review-round5.md) #6, [ADR063](ADR063-security-review-round9.md) #1). It no longer does:

- **Placeholder-only sandbox.** Since ADR062 and ADR064, hosted sandboxes hold only `ModelKeyPlaceholder` (`lego/backend/internal/agentsession/model.go`). The real key is injected by the gateway model proxy on its upstream hop. The sandbox lifecycle admits nothing else.
- **Branch-pinned Git proxy.** The GitHub token never enters the sandbox either. The gateway parses every receive-pack and refuses any ref other than the session's bound branch (`lego/backend/internal/sshgateway/agentcred/agentcred.go` `validateReceivePack`).
- **The bypass was already accepted.** [ADR084](ADR084-security-review-round22.md) #17 rejected "agent can bypass the driver's pre-push credential scan" for exactly these two reasons. The agent can push mid-turn today: `origin` is the proxy URL, `:8082` egress is open in both phases and the mint allows active phases. The driver's after-the-fact commit is therefore redundant as a control and poor as a deliverable.

The remaining needle set protects a placeholder. Every scrub, scan, redaction and pre-snapshot hop built for the old path is cost without protection.

## Decision

### D1 — Responsibility split

The **agent** commits, pushes its branch and opens or updates its own PR, the way a human engineer does. The **platform** enforces only what the agent cannot be trusted with or cannot do itself:

| Concern | Owner | Mechanism |
| --- | --- | --- |
| Commit contents, split, messages | agent | ordinary `git commit` in the sandbox |
| Which ref may be updated | platform | Git proxy exact-branch receive-pack pin (ADR047 D2) |
| Which PR head, base and repo | platform | PR verb resolves them from the session record (D3) |
| Attribution footer on the PR | platform | server-appended, idempotent (D3) |
| GitHub and model credentials | platform | gateway proxies; never in the sandbox (ADR047 D2, ADR062) |
| Recording the PR on the session | platform | PR verb persists immediately; Completer finalizes (D5) |

The platform never authors a commit. After setup, the driver's only Git writes are the clone/checkout and the repo-local identity config below.

**Git identity.** Setup writes repo-local `user.name` / `user.email` from `BEX_AGENT_GIT_NAME` / `BEX_AGENT_GIT_EMAIL` (default `bex agent` / `agent@bex.co`), `push.default=current`, and the upstream of `bex-agent/<id>` to `origin`. Agent commits therefore have a deliberate author rather than `bex@<podname>` or an "unable to auto-detect email" failure. Repository hooks now run on the agent's commits. This is intended: a human contributor's commits run them too, and ADR084 #4's hook isolation only ever applied to the driver's own Git invocations. A requester `Co-authored-by` trailer is a known gap (D7).

### D2 — Platform system-prompt overlay

Every hosted session gets a bex platform overlay layered on the engine's own system prompt. It says where the agent is, what it can use and what the deliverable looks like. It does not re-teach coding.

**Layer order** (highest priority first):

1. Engine core prompt (the adapter's own, e.g. the Claude Code preset).
2. **bex platform overlay** (appended; platform priority).
3. Repository instructions, `CLAUDE.md` / `AGENTS.md`, loaded by the engine itself.
4. Tenant per-session instructions, wrapped as quoted, lower-priority guidance. The wrapper says they are scoped to this session, apply only where consistent with all preceding system, safety, tool and product instructions, and cannot replace or weaken them; the text is quoted line by line. Only tenant text gets this wrapper.
5. The user task.

**Overlay content.** Sections cover the session (autonomous, requester usually not watching, finish unblocked work before asking), the environment (branch and base, credential-free proxy `origin` that accepts only this branch, no GitHub token and a `gh` that reads the repository and makes the writes [D4](#d4--agent-facing-tool-the-bex-stdio-mcp-server) lists while the pull request stays with the `bex` tools (w10/m513, w10/m522), credentials injected outside the sandbox), delivering work, the authorization clause, and steering turns. Delivering work means:

- commit in logical units following the repo's `git log` convention, never build output or env files;
- `git push origin HEAD:<branch>`, no force-push; `git pull --rebase` on rejection;
- call `open_or_update_draft_pr` with a body filled from the repo's PR template; it opens the PR ready for review, and `draft: true` asks for a draft only when the task, a person's message or the repository's instructions ask for one (_amended 2026-11-22, w10/040; every PR was a draft before_);
- never claim a PR without the returned URL;
- merge it, or mark a draft ready, only when the task or a person's message asks, and otherwise leave both to the requester (_amended 2026-11-20, w10/m538; it read "never mark it ready" before_);
- a task with no code changes ends with a report and no commit.

The text follows Anthropic's prompting guidance: direct statements, the reason behind each rule, no all-caps imperatives, and named actions ("commit", "push", "open the PR") rather than "consider".

**Authorization clause.** Many repositories' instructions say "only commit or open PRs when asked". The overlay states that the person who started the session chose an entry point whose output is a pull request. Committing, pushing this branch and opening or updating the PR is therefore their explicit request, and satisfies such rules. Repo rules about commit style, tests and formatting still apply. Without this clause, a well-behaved agent obeying `CLAUDE.md` would finish the task and deliver nothing.

**Channel per adapter.**

- **ACP `systemPrompt`.** When `initialize` advertises `agentCapabilities.sessionCapabilities.systemPrompt`, the driver sends `systemPrompt: {mode: "append", content: [{type: "text", text}]}` on `session/new` **and** `session/load`, re-sent on every lifecycle call as the RFD requires. claude-agent-acp supports this from 0.92; bex pins 0.94.0. An `invalid_params` reply fails the turn with a named reason; there is no silent retry without the overlay.
- **Codex.** codex-acp 1.4.0 has no ACP field. The overlay goes through Codex `developer_instructions` if that channel is verified in the pinned adapter; otherwise the preamble below.
- **Fallback.** Any other adapter gets the overlay as a first-prompt preamble through the existing continuity path (ADR047 D3 continuity amendment). It is never published into the stream.

**Claude settings.** Through `_meta.claudeCode.options` the driver disables Claude Code's built-in git/PR instructions (`includeGitInstructions: false` / `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1`) and blanks `attribution.pr` and `attribution.commit`. The built-in instructions say "only commit when asked" and use `gh pr create`; both contradict the overlay. With them off, the overlay is the single delivery contract and the server footer the single attribution. `excludeDynamicSections: true` keeps the system prompt identical across sandboxes for cache reuse.

### D3 — The `pull-request` verb

The PR-side twin of the Git proxy's exact-branch rule: one narrowly-scoped, credential-free way for the sandbox to open or update its own PR.

- **Gateway.** On the `:8082` mux, at the Git proxy path plus `/pull-request`. `POST` with JSON `{title, body}` and an optional boolean `draft` (w10/040). `title` is a single line of at most 256 runes; `body` is at most 60000 bytes. It reuses the Git proxy's chain unchanged: Pod source-IP resolution, `agentsession.AuthorizePod` label digests, limiter and budgets, audit.
- **Internal hop.** The gateway calls bex-api's internal listener (`:8091`) at `/v1/agent-session-pull-requests` over the existing HMAC hop. bex-api re-checks the live sandbox generation and phase, as the Git mint does.
- **Server-filled fields.** Owner, repo and base come from the session record. Head is pinned to the bound `bex-agent/<id>` branch. The agent cannot name any of them.
- **Typed refusals.** `branch_not_pushed`, `not_ahead`, `invalid_request`, `too_large`, `forbidden`, `upstream_error`, and `draft_not_supported` (w10/040).
- **Semantics.** It opens a PR ready for review, or a draft when the request says `draft: true` (_amended 2026-11-22, w10/040, below; it always created a draft before_), or updates the title and body of the existing open PR for that head. It never changes an existing PR's draft state: since w10/m538 two sibling verbs mark the session's PR ready and merge it, when the task asks (the amendment below). bex-api appends a server-side footer behind a `<!-- bex-agent-footer -->` marker; an update replaces anything after an existing marker, so the footer is idempotent and always present. `prUrl`, `prNumber` and `headSha` are persisted on the session immediately, so REST, GraphQL and MCP show the PR mid-turn.
- **A taken-over PR (w9/m348).** A session that a `/bex` comment started on a person's PR still pushes only its own `bex-agent/<id>` branch, started from that PR's head ([ADR094 D3](ADR094-coding-agent-mcp.md#d3--create_agent_session-input)). For it the verb opens no PR and never touches the title, body or draft state. It reads the session branch's head on GitHub and fast-forwards the PR's head branch to it (`PATCH …/git/refs/heads/<head>`, `force: false`); it compares the two first, so behind or diverged is `pr_branch_diverged` with the merge to run, a write GitHub refuses anyway is a branch rule (`pr_branch_protected`, not retried), and a closed PR is `pull_request_closed`. It records the new head and answers `{url, number, created: false, headSha, takenOver: true}`. The overlay replaces the draft-PR delivery steps with "push your branch, bring the PR up to date with the tool, merge on divergence, reply with `reply_on_pull_request`", and the delivery check nudges a turn whose PR lacks its pushed head.

_Amended 2026-11-20 (w10/m538): the session marks its own pull request ready and merges it when asked, as Devin does._ A task such as "fix the flaky test and merge once CI is green" used to end with a draft a person had to undraft and merge. Devin's App holds Pull requests and Contents write, its setup tip recommends branch protection "to ensure all required checks pass before Devin can merge changes" ([GitHub integration](https://docs.devin.ai/integrations/gh)), and Devin "is subject to the exact same branch protections and SDLC policies as any human engineer" ([SDLC integration](https://docs.devin.ai/essential-guidelines/sdlc-integration), both read 2026-11-20). Devin merges its own pull requests (35 of the 60 most recently updated merged pull requests by `app/devin-ai-integration` were merged by `devin-ai-integration[bot]`, for example [gateweavehq/track#365](https://github.com/gateweavehq/track/pull/365)), undrafts before it merges ([TeddyJubu/cal-scheduling#1](https://github.com/TeddyJubu/cal-scheduling/pull/1): `ready_for_review` 22:33:11Z, `merged` 22:33:18Z by the same bot), and merges "only on explicit request" ([Al-does/alex-rl-experiments#149](https://github.com/Al-does/alex-rl-experiments/pull/149)). The [w10/m538 design record](../.pm/w10/done/m538/README.md#design-record-t001-2026-11-20) has the evidence for each choice below.

- **Two verbs, two tools.** `POST <Git proxy URL>/pull-request/ready` with `{}` and `POST <Git proxy URL>/pull-request/merge` with at most `{method, commitTitle, commitMessage, auto}`, or `{disableAuto}` alone (`method` one of `merge`, `squash`, `rebase`; a one-line title of at most 256 runes; a message of at most 60000 bytes; `auto` and `disableAuto` since w10/m577, below; both take an optional `number` since w10/041, below). They run the PR verb's gateway chain unchanged (Pod source-IP resolution, label digests, limiter, the Git budget) and reach bex-api's `:8091` at `/v1/agent-session-pull-request-ready` and `/v1/agent-session-pull-request-merges`, kind-tagged under the `pull-request-ready` and `pull-request-merge` MAC domains with a single-use nonce, as the comment verb is. The D4 server lists them as `mark_pull_request_ready` and `merge_pull_request` in repo sessions only. Neither takes an owner, repository or head: an envelope or a gateway body naming one is refused. _Amended 2026-11-22 (w10/041): both take the number of another pull request of the session's repository; before, a number was refused too._
- **The pull request.** Without a `number`, both act on the session's recorded `prNumber` (`no_pull_request` before there is one); with one, on that pull request of the session's repository (w10/041, below). bex-api re-runs the live-generation check, reads the pull request back from GitHub and refuses unless its number, head branch (the session branch, or a takeover's `takeoverHeadRef`), head repository and base repository are the session's own; closed or merged is `pull_request_closed` (a merged one is recorded as merged).
- **Undrafting** is GraphQL-only: REST `PATCH …/pulls/{n}` takes no `draft` field, and `gh pr ready` sends the same `markPullRequestReadyForReview` with the pull request's node id. A pull request that is already ready answers `alreadyReady: true` without a call.
- **The merge call** is the synchronous REST merge, `PUT …/pulls/{n}/merge`, whose answer is final: 200 merged, 405 not mergeable, 409 the head moved, 422 invalid, 403 not permitted. GitHub now recommends `PUT …/pulls/{n}/merge-async`, which answers 202 with a UUID to poll; the parity-sufficient choice is the call that answers in the request. A base branch that requires a merge queue, and a merge asked for once the checks pass, take GitHub auto-merge instead (_amended 2026-11-22, w10/m577, below; before, a merge-queue repository got GitHub's refusal_).
- **The head pin.** `sha` is the session's recorded `headSha`, the head `open_or_update_draft_pr` last recorded (or the Completer at turn end, or a takeover's fast-forward). bex-api refuses with `head_changed` before calling GitHub when the pull request's head differs, and GitHub's 409 maps to the same code, so a commit pushed later is never merged unchecked. The hint says to push, call `open_or_update_draft_pr` and try once more, with `auto: true` to let GitHub merge it once its checks pass. An armed pull request follows GitHub's rule for a later head instead (w10/m577, below).
- **The method.** The agent may name one. Otherwise the first of merge, squash and rebase that the repository's settings allow (`allow_merge_commit`, `allow_squash_merge`, `allow_rebase_merge`, which `GET /repos/{owner}/{repo}` shows only to a token with Contents write) and that the base branch's active rules allow (`GET …/rules/branches/{base}`: a `pull_request` rule's `allowed_merge_methods`, and `required_linear_history`, which refuses a merge commit). A named method they refuse is `merge_method_not_allowed` naming the allowed ones, before any merge. Classic branch protection's linear-history setting needs Administration read to see, so GitHub's own refusal reports it.
- **The tokens.** Each call mints its own, narrowed to the one repository, and none enters the sandbox. Reading the pull request uses Pull requests read. Undrafting uses Pull requests and Contents write: GitHub names no permission for the mutation, and installations with Pull requests write alone have been refused it ("Resource not accessible by integration"). Merging uses Contents, Pull requests and Workflows write, which GitHub lists for the merge endpoint plus the Workflows write a merge of a pull request that changes `.github/workflows/` needs; an installation that has not granted Workflows refuses that set with 422, so the mint retries without it, as the session's push token does (w10/014). An installation without Contents or Pull requests write is `not_permitted`.
- **GitHub decides, and says why.** GitHub's refusal reaches the agent as GitHub states it: the `message` of its error body and its `errors` entries, on one line, at most 1000 characters, prefixed `GitHub: `, under a typed code whose hint says what to wait for or fix and not to retry in a loop. `merge_blocked` (405, or a 422 that is not about the method) covers required checks pending or failing, a required review, a conflict, a branch behind its base and any other rule; its hint says to call again with `auto: true` and end the turn (since w10/m577) or wait with `gh pr checks <number> --watch` (the number, since w10/042: gh finds no pull request for the current branch through the Git proxy), fix and push, stop and tell the user when a review is required, or merge the base branch. `head_changed` (409), `merge_method_not_allowed` (GitHub's "… are not allowed" words, or the pre-check), `not_permitted` (403), `pull_request_draft` (a merge of a draft: mark it ready first), `rate_limited` and `upstream_error` complete the set. Relaying GitHub's text is deliberate here, unlike the other verbs (w6/005): it describes the agent's own pull request in a repository the session's `gh` already reads.
- **Required reviews stay a person's.** An `APPROVE` review stays refused on every path (D4), so a session cannot satisfy required reviews by itself, and neither verb bypasses a rule (`bypass_rules` is never sent).
- **The state shows at once.** A merge records `prState: merged` on the session in the same request (`RecordAgentSessionPRState`, never read again), so REST, GraphQL, MCP and the dashboard read it without the PR-state poller or a webhook. A failed write is only logged; the poller records it later. An armed or queued pull request is not merged yet and records nothing: the poller (every five minutes in its first week) or a `pull_request` delivery (ADR094 D7) records `merged` once GitHub merges it (w10/m577).
- **Accountable.** Each call is audited on both hops as `agentsessions.PullRequestReady` or `agentsessions.PullRequestMerge`, allowed or denied, with the repository.
- **A taken-over pull request (w9/m348).** Its recorded `prNumber` is the person's pull request. A takeover session may mark it ready or merge it, at the head its fast-forward recorded, when the `/bex` comment or a later message asks: the commenter has write access and could merge it themselves, as Devin's `/devin` session on a pull request can. The overlay says the pull request's state belongs to the person who opened it unless asked.
- **Only when asked.** No gate can read intent, so "only when the task or a person's message asks" lives in the overlay (D2) and in both tools' descriptions, as Devin's behavior does. The authorization clause says that marking ready or merging is not part of the request to deliver a pull request. A workspace that wants agents never to merge has a stricter variant to file (w10/m538 t006); the workspace's `gh` switch does not reach these tools.
- **Delivery check.** The merge tool marks the driver's pull request record merged at the merged head. When GitHub deletes the merged branch, the D5 check counts local commits from that head instead of the setup-time base, so merged work is not called unpushed. An armed, queued or disarmed answer leaves the record as it is.

_Amended 2026-11-22 (w10/m577): a session told to merge once CI is green arms GitHub auto-merge or the merge queue and ends its turn, as Devin can._ Before, such a session had to stay in its turn watching the checks, which a session with `gh` off could not do at all, and a repository whose base branch requires a merge queue refused its merge. Devin Review can "Enable or disable GitHub auto-merge from the merge button dropdown. When enabled, the PR will merge automatically once all required checks pass", its `m` will "Merge the PR, add or remove it from the merge queue, or enable auto-merge when offered" ([Devin Review](https://docs.devin.ai/work-with-devin/devin-review), read 2026-11-22), and Devin's own `gh` token runs `gh pr merge --auto`. The [w10/m577 design record](../.pm/w10/blocked/m577/README.md#design-record-t001-2026-11-22) has the evidence for each choice below.

- **The option.** `merge_pull_request({auto: true})`, after `gh pr merge --auto`, has GitHub merge the pull request once its required checks pass; `{disableAuto: true}`, alone, after `--disable-auto`, undoes it. The tool still takes no pull request number, owner, repository or head.
- **The state read.** bex-api reads the pull request's `isMergeQueueEnabled`, `isInMergeQueue`, `mergeStateStatus` and `autoMergeRequest` (GraphQL, Pull requests read), the fields gh reads before it chooses. A plain merge whose read fails merges as before.
- **The merge queue.** Where the base branch requires a merge queue, the pull request goes into it with or without `auto`, as gh and GitHub's merge button do: `enablePullRequestAutoMerge({pullRequestId, expectedHeadOid})` ("Merge when ready", which queues a ready pull request and one whose checks are pending once they pass), or `enqueuePullRequest` with the same pin where GitHub refuses that with "Auto merge is not allowed" or "is in clean status". The queue sets the method and the commit text, so none is sent and the answer names none. The answer is `{merged: false, mergeQueue: true, headSha}`; a pull request already queued answers the same with no call.
- **Auto-merge.** Without a queue, `auto` sends `enablePullRequestAutoMerge` with `expectedHeadOid` = the recorded head, the method rule above as `mergeMethod`, and the commit text as `commitHeadline` and `commitBody`. The answer is `{merged: false, autoMerge: true, method, headSha}`, within the call. A pull request already armed answers the same with its armed method and no call. One GitHub would merge now (`mergeStateStatus` `CLEAN`, `HAS_HOOKS` or `UNSTABLE`, or GitHub's "Pull request is in clean status" refusal of the arm) is merged now with the synchronous call, as gh does.
- **The head pin after arming.** The arm is pinned as the merge is (`head_changed` before any call, and `expectedHeadOid`). GitHub keeps auto-merge on after a push by anyone with write access, which the session's push is, and merges that later head only once its own required checks pass. bex does not disarm it, as Devin's `gh pr merge --auto` does not, so for an armed pull request "a commit pushed later is never merged unchecked" reads "a later head merges only after its own required checks pass". The overlay says so and names `disableAuto`.
- **The undo.** `disableAuto` sends `dequeuePullRequest` for a queued pull request and `disablePullRequestAutoMerge` for an armed one, unpinned and on a draft too, and answers `{merged: false, autoMergeDisabled: true}`, also when nothing was armed.
- **Refusals.** A repository whose "Allow auto-merge" is off (`allow_auto_merge: false`, read with the method settings, on a branch without a queue; or GitHub's "Auto merge is not allowed for this repository") is `auto_merge_not_allowed` (409). Its hint says to wait for the checks (`gh pr checks <number> --watch`) and call without `auto`, or to tell the user. A draft stays `pull_request_draft`, a head that is not the recorded one `head_changed` (also GraphQL's "… does not match"), and every other refusal of GitHub's comes back in GitHub's words under the codes above.
- **Tokens.** The arm and the queue call use the merge's token. GitHub makes the later merge as the actor who armed it, so Workflows write matters there too, and GitHub documents an App token for the queue. The undo uses the mark-ready token.
- **The answer and the audit.** The gateway client and the driver accept an answer that names the pull request with exactly one outcome (`merged` with its commit, `autoMerge`, `mergeQueue` or `autoMergeDisabled`), and the audit stays `agentsessions.PullRequestMerge` on both hops.
- **Shown at once (w10/047, 2026-11-23).** An armed, queued or disarmed answer records the pull request's `prAutoMerge` and `prMergeQueued` (ADR094 D7) on every session of the workspace that recorded it, as a merge records `prState: merged`. After an arm, a queue or an undo bex-api reads the merge state back, so the record names who armed it and when as GitHub does; where that read fails it records what the answer says (armed now, by nobody named; queued; nothing), which the PR-state poller corrects on its next read. A pull request already armed or queued records the state the verb read. A failed write is only logged.
- **Said everywhere.** The overlay's merge step (D2) and the tool's description say that when the task or a person asks to merge once the checks pass or CI is green, the agent marks the pull request ready, calls the tool with `auto: true` as soon as it is ready, reports that GitHub will merge it, and ends its turn rather than waiting for or watching the checks, before or after the call. The overlay's `gh` line says `gh pr checks <number> --watch` is not needed for that. _Amended 2026-11-23 (w10/m577 t010):_ on production the default model armed auto-merge and then watched the checks anyway, and in a later turn watched them and merged without `auto` (t005). So the driver adds `next` to an armed or queued answer, which tells the agent at that very step to end its turn and to report auto-merge armed or the pull request queued, not merged; an undo or a merge carries none.

_Amended 2026-11-22 (w10/040): a session opens a regular pull request unless a draft is asked for, as Devin does._ Every session pull request used to be a draft, which a requester who wanted Devin's default had to undraft (or ask the session to), and which reviewers whose notifications skip drafts did not see. Devin's docs name no setting that makes the pull requests it opens drafts: its pull request settings (Settings > Devin > Pull requests) choose only whose identity opens them ([GitHub integration](https://docs.devin.ai/integrations/gh), [release notes](https://docs.devin.ai/release-notes/overview), both read 2026-11-22). Port's tracking guide says "Devin usually opens a regular PR (not draft, no WIP)" ([Track AI-driven pull requests](https://docs.port.io/guides/all/track-ai-driven-pull-requests/), read 2026-11-22). And of the 200 most recent pull requests `app/devin-ai-integration` created since 2026-11-13, 6 were drafts on 2026-11-20 ([w10/m538 design record](../.pm/w10/done/m538/README.md#design-record-t001-2026-11-20)): Devin opens a draft when it is asked for one.

- **The default.** `createPull` sends `draft: false`. A pull request opens ready for review, and a merge needs no `mark_pull_request_ready` first.
- **The option.** `open_or_update_draft_pr({title, body, draft: true})` opens it as a draft. The overlay and the tool's description say to pass it only when the task, a person's message or the repository's instructions (an `AGENTS.md` asking for draft pull requests, say) ask for a draft. Devin has no workspace or automation switch for this, so bex adds none: a repository that wants drafts says so in its instructions.
- **Read only on open.** `draft` applies only when the call opens the pull request. An update sends only the title and body, as before, so a later call never drafts or undrafts it. Undrafting stays `mark_pull_request_ready`. A takeover session's call ignores `draft`, since that pull request's state belongs to the person who opened it.
- **The answer** carries `draft`, the pull request's state as GitHub returned it, so the agent can say which kind it opened. The driver and the gateway send `draft` only when it is true, so a request that does not ask for a draft is the same `{title, body}` as before the option, on both hops.
- **A plan without drafts.** GitHub offers drafts in private repositories only on GitHub Team and Enterprise Cloud ([Pulls](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request), read 2026-11-22), and refuses a draft elsewhere, such as in a private repository on GitHub Free or Pro, with 422 "Draft pull requests are not supported in this repository." That is `draft_not_supported`, and its hint says to call again without `draft` and tell the user. The refusal is checked before the 422 fallback for a concurrent create. The old always-draft verb could not open a pull request on such a repository at all; the default now can.
- **The tool keeps its name.** `open_or_update_draft_pr` predates the option. Tasks, automations and repository instructions can name it, and the gateway's hints name it to sandboxes on older images, so a rename would break them for a word. Its title and description say what it does.

- **The option.** Both tools take an optional `number`, a positive integer. _Amended 2026-11-23 (w10/048): `auto` on a pull request in a GitHub stack arms the stack, as Devin Review's auto-merge on a stacked pull request does._ A `/bex` takeover session, or one given a `number` (w10/041), may be asked to merge a person's pull request that sits in a GitHub stack, where each pull request targets the branch of the one below it. GitHub says that endpoint "does not support stacked pull requests" and that a stack lands only through `PUT …/pulls/{n}/merge-async` ([Pulls](https://docs.github.com/en/rest/pulls/pulls), read 2026-11-23). ### D4 — Agent-facing tool: the `bex` stdio MCP server

The agent image ships a stdio MCP server named `bex` with one tool, `open_or_update_draft_pr({title, body})` (`draft` added by the w10/040 amendment to D3), which calls the D3 verb. _Amended 2026-11-19 (w10/m513): `gh` is installed and reads; it never writes._ An agent that cannot read its repository's CI cannot reproduce a red run or check the PR it delivered, and the bex-co/beancount-io automation runs of 2026-11-15..18 said so. - **Wiring.** gh's `http_unix_socket` setting sends every call over a Unix socket the driver serves, as plain HTTP with the GitHub host in the `Host` header (verified with gh 2.105.0, the pinned version). The driver forwards `api.github.com` calls to the gateway's `github-api` route, `<Git proxy URL>/github-api/<path>`, and refuses any other host. `GH_TOKEN` is a placeholder gh needs before it calls anything; `GH_REPO` names the session's repository, because `origin` is the Git proxy. gh still cannot map the current branch to its pull request through that remote (`could not resolve remote "origin"`), so the overlay says to pass the pull request's number to every `gh pr` command and names the session's own once it has one (w10/042).

- **The overlay** names the command with the session's branch: "runs a workflow on your branch (`gh workflow run <workflow> --ref <branch>`), never on another ref".

### D5 — Turn end: observe, nudge once, never commit

When the agent ends its turn, the driver computes read-only Git facts: `{dirty, unpushedCommits, remoteHead, baseBranch, prRecorded}`. If the work is undelivered (a dirty tree, unpushed commits, or a pushed branch ahead of base with no PR recorded), the driver sends the agent **one** follow-up prompt asking it to finish delivery, then recomputes the facts. The driver never commits or pushes.

The status file's `git{}` object replaces `delivery{}` and `evidence{}`. The Completer never opens or edits a pull request. It finalizes from the PR record the D3 verb already wrote. _Amended 2026-11-13 (w5/m382): its one GitHub access is a read of the session branch's head, through a one-method interface (`Completer.Heads`, served by `agentsession.BranchHeads`), so the head it records, and CI-failure steering keys on, is GitHub's rather than the sandbox's own report._ Work still undelivered after the nudge finalizes as **succeeded with a delivery note**, not failed: the agent's turn did succeed. _Amended 2026-10-25 (w10/m15): ADR059 hibernation and its dirty-git retention are retired. The tree stays only while the finished session's sandbox is alive, which is at most `BEX_AGENT_SANDBOX_IDLE_TTL` (2h then; 5 minutes since 2026-11-22, [ADR059](ADR059-agent-sandbox-hibernation.md#2026-11-22--idle-close-follows-devin-5-minutes-automations-at-once)) of idle time. After that the sandbox is terminated and undelivered work is lost. The post-turn nudge is the only guard, and the delivery note tells the user what was left behind._

### D6 — Deletions

These go away, end to end:

| `credential-scrub-test.sh` CI step | Tests the removed machinery. |

The controls that still bound a sandbox are unchanged: default-deny egress, the placeholder-only model key, the branch-pinned Git proxy and the head-pinned PR verb.

### D7 — Out of scope and follow-ups

- Gateway-side non-fast-forward rejection, so a force-push is refused by the proxy and not only by the overlay. A `/bex` takeover does not depend on it: it never pushes the person's PR branch, which only moves by GitHub's fast-forward-only ref update.
- A PR-comment steering loop (webhook → steer the session), with the AI footer also on comments the agent posts. _Decided in [ADR047 D11](ADR047-cloud-coding-agent-sessions.md#d11--pr-feedback-steers-the-session-w9m344-2026-11-12) (w9/m344)._
- A tenant per-session instruction field, with the D2 layer-4 wrapper (not yet implemented).
- Requester `Co-authored-by` on agent commits.
- Override-mode system prompts (`mode: "override"`).
- Making OpenRouter a customer-selectable provider (see the dev route and the allowlisted platform route below).

## Platform OpenRouter route for an allowlisted workspace (2026-10-23)

**User decision 2026-10-23** (tracked in `w10/m14`): ship agent sessions on a bex-owned OpenRouter key now, but only for workspace `tea-d98210cbbpdc73dcrkvg`, and keep every other tenant off it until the economics are in place.

- **Scope.** bex-api's `BEX_AGENT_PLATFORM_MODEL_ROUTE=openrouter` applies to every workspace that has not set its own model key, and only to the claude profile. Until 2026-11-16 it covered only the `tea-` ids in an allowlist, `BEX_AGENT_PLATFORM_MODEL_WORKSPACES`; the user removed that allowlist on 2026-11-16 (w10/m14 t007). Unlike the dev route it runs on the production control plane. The route is resolved per workspace at create, steer and mint time, not from the endpoint a session stored, so an existing session moves onto it on its next dispatch. A workspace with its own key stays on `api.anthropic.com` with that key. With the route off, an explicit OpenRouter endpoint is refused. Workspaces on the route report `modelKeyReady` through the platform key. Because only the claude profile is routed, each capabilities profile also carries its own `modelKeyReady`, and a create or steer for a profile with neither the route nor the workspace's own key is refused `400 AGENT_SESSION_MODEL_KEY_REQUIRED` instead of failing minutes later on the model proxy (2026-11-06, w9/076). An unreadable key store still defers to the proxy.
- **Key custody.** The key lives in the `bex-system` Secret `bex-agent-platform-model` and flows to bex-api's env, then to the internal mint, then to the gateway's upstream hop. It never enters the sandbox, which still holds only `ModelKeyPlaceholder`, nor any API response, log, audit event or error. A missing Secret disables the route with a loud startup log rather than crash-looping bex-api.
- **Model pin.** The mint returns `pinnedModel`. The gateway refuses with 403 any request whose JSON top-level `model` is not exactly that id, appears twice, or carries OpenRouter's `models` fallback list or paid `plugins`. A tenant sandbox therefore cannot spend the platform key on a different model. Workspace BYO routes are not pinned. _Amended 2026-10-27 (w10/m17 t002):_ the pin is enforced before the gateway too. A session create that names a different `agentConfig.model` for the claude profile is refused with a typed 400 `AGENT_SESSION_MODEL_PINNED` (params `field`, `pinnedModel`) instead of failing mid-turn with the gateway's 403; an omitted or equal model records the pinned id. A steer always runs the pinned model, even for a session whose stored model predates the allowlist. The workspace agent environment reports `modelPinned`/`pinnedModel` and refuses a different `defaultModel` (`AGENT_ENVIRONMENT_MODEL_PINNED`).
  - _Amended 2026-11-19 (w10/m516): the pin is per session, inside a platform model catalog._ The one-model-per-workspace pin above existed so a sandbox could not spend the platform key on a more expensive model while nothing was priced. [ADR091](ADR091-agent-model-pricing.md) D1 now prices every platform request at its own reported cost × 1.3 under per-workspace spend caps, so a person chooses the model, as Devin's agent selector lets them ([Your First Session](https://docs.devin.ai/get-started/first-run), read 2026-11-19). The security property stays: the mint pins the session's choice, so the sandbox still cannot pick another model.
    - **Catalog source.** `BEX_AGENT_PLATFORM_MODEL` is the default and the catalog's first model. `BEX_AGENT_PLATFORM_MODELS` is a comma-separated list of further OpenRouter ids, in the order pickers show them. It is deploy configuration (`lego/operator/config/api/deployment.yaml`), not code, so changing it needs no image release. A malformed or repeated entry refuses startup. There are no aliases: an Anthropic-style id such as `claude-opus-5-5` is refused with the catalog's own ids listed, so a name never maps to a model the person did not see. Labels are the ids themselves.
    - **Initial catalog (production, 2026-11-19).** `deepseek/deepseek-v4.1-flash-1017` (default), `anthropic/claude-haiku-5.5` (cheaper per token), `anthropic/claude-sonnet-5.5` and `anthropic/claude-opus-5.5` (stronger). Each answered a live probe on 2026-11-19 at 14:31Z, made with the platform key (never logged) on `https://openrouter.ai/api/v1/messages`: a tool-use request with `"tool_choice":{"type":"auto"}` and `"provider":{"data_collection":"deny"}` returned 200 with `stop_reason: tool_use` and the model's own `usage.cost`, and a streamed request carried `usage.cost` on `message_delta`, which the gateway meters. The 5.5 Sonnet and Opus refuse a forced `tool_choice` (`any`/`tool`); Claude Code sends `auto`. A model added later must pass the same probe first, and the probe is recorded here.
    - **Resolution.** On a workspace without its own key, a claude session's model is the request's catalog model, else the workspace default when the catalog offers it, else the catalog's first model. The session records it in `agentConfig.model`. The sandbox gets it as `ANTHROPIC_MODEL` and the three `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL` slots. The mint returns it as `pinnedModel`, and the gateway refuses any other request model with a 403. A stored model that left the catalog runs the default and never strands a session: on a steer, at the mint, in an automation run (whose run record says so). A session created on the route before its workspace set its own key drops its catalog model for the workspace default on its next turn.
    - **Errors.** A model outside the catalog is refused before anything runs. `400 AGENT_SESSION_MODEL_NOT_OFFERED` covers a session create, a message, and an automation's template (params `field`: `agentConfig.model`, or `model` on a message; `model`; `models`, the offered ids). `400 AGENT_ENVIRONMENT_MODEL_NOT_OFFERED` covers the workspace default (`field: defaultModel`). `AGENT_SESSION_MODEL_PINNED` stays for the profiles with one fixed model (`muse`, ADR108 D4; `deepseek`, ADR114). `AGENT_ENVIRONMENT_MODEL_PINNED` is retired. The environment keeps `modelPinned` (true on the route: each session is pinned) and `pinnedModel` (now the catalog default) for older clients, and adds `models`.
    - **The switch on a message.** A message (REST `model`, GraphQL `model`, MCP `model`, `bex agent send --model`, chat `/model`) may name a model. Every turn runs in a fresh sandbox ([ADR047](ADR047-cloud-coding-agent-sessions.md) D8 phase 1; a kept disk boots a new pod too), so the new model needs no ACP model call and no agent restart: the turn's begin records it as `agentConfig.model` in the same transaction that starts the turn, the new pod reads it from its env, and the mint pins it. A queued message switches the model when it is delivered, not when it is queued. A model that left the catalog while the message waited runs the default rather than failing the message. A message without a model keeps the session's model. The pinned `@agentclientprotocol/claude-agent-acp` is never asked to change models in place.
    - **A workspace narrows the catalog** _(amended 2026-11-20, w10/m527)_. A workspace admin may turn catalog models off (`enabledModels` on the agent environment, stored as the opt-out `agent_environments.disabled_models`), as Devin's admins allowlist models. The catalog default can never be turned off. _(Amended 2026-11-22, w10/m568.)_ The list has Devin's two modes: every catalog model is on, a model added to the catalog later included, until an admin turns one off; from then on it is an allowlist ("A model is allowed when its UID is listed", Devin's [List Models](https://docs.devin.ai/desktop/accounts/api-reference/list-models)), and a model added to the catalog later is off there, read as `newModels`, until an admin turns it on. The allowlist is stored as `agent_environments.known_models`, the catalog the narrowing write saw, less `disabled_models`. _(Amended 2026-11-23, w10/m592.)_ The mode is explicit, as on Devin's settings page: `allowAllModels: true` allows all again, and an allowlist stays one even while it lists every current catalog model, so the next model is off there. Editing `enabledModels` keeps the mode (no longer "every model back on allows all again"), and `allowAllModels: false` alone keeps the models on now as the allowlist. "Allow all" is `known_models` NULL, so no migration was needed. _(Amended 2026-11-22, w10/m573.)_ An admin may instead filter by provider, Devin's other filter type ("Filter by specific models or by provider (one filter type at a time)", [Devin Desktop admin controls](https://docs.devin.ai/desktop/controls)). `enabledProviders` lists providers, a model's provider being its id's prefix before `/`, and the workspace offers every catalog model of a listed provider, one added to the catalog later included, plus the catalog default. It is stored as `agent_environments.enabled_providers` beside an exact `disabled_models`, so a previous-release Pod offers the same set. An `enabledModels` write returns to the by-model list. Resolution above then reads "the request's offered model, else the workspace default while it is offered, else the catalog's first model", where offered means in the catalog and not turned off. A model turned off is refused up front exactly as one outside the catalog (`AGENT_SESSION_MODEL_NOT_OFFERED`, `AGENT_ENVIRONMENT_MODEL_NOT_OFFERED`, listing only the offered models), and a write leaving the default off or naming a non-catalog model is `AGENT_ENVIRONMENT_MODELS_INVALID`. The mint is unchanged: it pins the model the session recorded, so a turn in flight keeps it, and the session's next dispatch runs the fallback. A workspace default an admin turns off stops taking effect and the catalog default runs, as Devin's pinned default does outside its allowlist. The full record is [ADR047](ADR047-cloud-coding-agent-sessions.md) D7's w10/m527 amendment.

### Metering, price/quota mechanism and data policy (2026-10-27, w10/m14 t003–t006)

- **Metering.** For a platform-key `/v1/messages` exchange (the mint returned `pinnedModel`), the gateway tees the relayed response and never buffers or alters it. It reads Anthropic usage from a JSON body or from the SSE `message_start` and `message_delta` events. It then reports `{requestId (amr-…), session, workspace, model, input/output/cache-read/cache-write tokens}` to bex-api's internal `POST /v1/agent-session-model-credentials/usage` over the same HMAC and nonce as the mint. A bounded queue, retries under one request id, and a dropped report is logged and counted in `bex_ssh_gateway_model_proxy_usage_reports_total{result}`; metering never fails a model response. bex-api records each request id once (`agent_model_usage_events`) into `usage_hourly`. The rows are `resource_kind=agent_session`, `service_id=<ags-…>`, `tier=<model>`, with kinds `agent_model_{input,output,cache_read,cache_write}_tokens`. BYO-key traffic is never metered.
- _Superseded for billing by [ADR091](ADR091-agent-model-pricing.md) (2026-10-30): price = provider cost × 1.30 via one `agent_model_cost_microusd` meter, a monthly USD spend cap (`AGENT_MODEL_SPEND_CAP_REACHED`) replacing the token quota, threshold billing and settle-before-delete. The token meters below remain for display._
- **Price and quota mechanism, shipped disabled** (superseded by [ADR091](ADR091-agent-model-pricing.md): cost-based pricing, and D5 monthly USD spend caps with code `AGENT_MODEL_SPEND_CAP_REACHED` replaced the token quota in w10/m14 t005). `pricing.yaml` `agentModel.models[]` prices each model in USD per 1M tokens per kind. Each priced kind becomes a Stripe lookup key `agent_model_<kind>_tokens.<model>`. `agentModel.monthlyTokenQuota[]` caps a plan's month-to-date total of all four kinds; the mint checks it and refuses with HTTP 429, refusal header `model-quota-exceeded`. The gateway then answers the agent with an Anthropic-shaped 429 whose `error.code` is `AGENT_MODEL_QUOTA_EXCEEDED`, and fails the session with a readable reason and `failureReasonCode`. Both lists ship empty: tokens are metered and shown but nothing is charged or capped until the user sets numbers. The OpenRouter key's credit limit remains the spend backstop.
  - Superseded by [ADR091](ADR091-agent-model-pricing.md): each request is now priced at its upstream cost × `agentModel.markup` and billed on one model-agnostic `agent_model_cost_microusd` meter; the per-model token prices and meters above are gone.
- **Data policy.** The gateway JSON-merges `"provider":{"data_collection":"deny"}` into every platform-route Messages request, so OpenRouter routes only to providers that neither store prompts non-transiently nor train on them. A client-supplied `provider` object is refused with 403 alongside `models`/`plugins`, so the policy cannot be weakened. A live check on 2026-10-27 confirmed that `/api/v1/messages` validates this field (a bad value returns 400 naming `provider.data_collection`). With `deny`, `deepseek/deepseek-v4.1-flash-1017` still answered 200. `count_tokens` is not rewritten. The customer-facing terms disclosure is a pending user/legal decision.

## Prior art

Paraphrased from public documentation and source; no leaked or GPL prompt text is copied.

- **ACP client-provided system prompt RFD** ([agentclientprotocol.com/rfds/client-system-prompt](https://agentclientprotocol.com/rfds/client-system-prompt)). The client may send `systemPrompt` with `append` or `override` mode on session new/load/resume/fork. Support is advertised as a session capability. An unsupported request is an `invalid_params` error, not a silent fallback. The RFD is still unstable.
- **claude-agent-acp PR #1366.** Maps `append` to the Claude Code preset plus appended text. It keeps the user/project/local setting sources, so `CLAUDE.md` / `AGENTS.md` still load, and accepts `_meta.claudeCode.options` overrides.
- **codex-acp PR #653.** Append-only support through Codex developer instructions, in preview tags only.
- **Claude Agent SDK, modifying system prompts** ([code.claude.com/docs/en/agent-sdk/modifying-system-prompts](https://code.claude.com/docs/en/agent-sdk/modifying-system-prompts)). Describes preset-plus-append, the switch for the built-in git instructions, attribution settings and excluding dynamic sections.
- **Open SWE** ([github.com/langchain-ai/open-swe](https://github.com/langchain-ai/open-swe)). The agent commits and pushes itself. An `open_pull_request` tool appends the platform footer, and a guard blocks other PR-creation paths.
- **GitHub Copilot coding agent** ([risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/coding-agent/risks-and-mitigations)). Pushes to a single branch only; the platform opens a draft PR.
- **Devin PR templates** ([docs.devin.ai/integrations/pr-templates](https://docs.devin.ai/integrations/pr-templates)). PR bodies follow the repo's template, found by a documented lookup order.
- **Claude Code on the web** ([code.claude.com/docs/en/cloud-environments](https://code.claude.com/docs/en/cloud-environments)). A cloud environment where the agent works on a branch and delivers through Git.
- **Anthropic prompting best practices.** Be direct, explain why, avoid over-emphatic imperatives that make current models over-trigger.

## Consequences

- Agent PRs read like a teammate's: a reviewable commit history, a templated description, and a bex footer.
- About 1,000 lines of driver and backend delivery, evidence and scrub code, plus a CI script, are deleted.
- The PR appears on the session as soon as it exists, not only at finalize.
- Delivery now depends on the agent following the overlay. The one-nudge check and the delivery note make a miss visible without the platform authoring code. From 2026-10-25 nothing kept undelivered work past the idle close, so the nudge was the only guard; since 2026-11-18 (w10/m491) the close keeps a checkout's undelivered work on disk for the next message, and since 2026-11-22 the close comes 5 minutes after a person's turn (ADR059 § 2026-11-22).
- `evidence` disappears from REST, GraphQL and MCP. This is a bex-only surface with no Render equivalent; `w10/m13` t012 checks the three surfaces, the dashboard and mobile agree.
