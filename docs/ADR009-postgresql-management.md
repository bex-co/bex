# ADR: managed PostgreSQL for tenants (CNPG, plans, internal/external URLs)

**Status:** accepted and implemented — the `Database` CRD (`lego/types/v1alpha1/database_types.go`), the CNPG-projecting controller (`lego/operator/internal/controller/database_controller.go`), the `postgres` tier family (`lego/types/tiers/tiers.yaml`), and the bex-api surface (`lego/backend/internal/postgres/`, [ADR006-bex-api.md](ADR006-bex-api.md#managed-postgres-render-v1postgres-compatible)) all ship. The CloudNativePG (CNPG) operator and the control-plane's own DB `bex-db` run on the cluster. Grounded in a live study of Render Postgres (create → connect → delete driven through the dashboard).

## Context

bex is an open-source Render. Render sells **managed Postgres** as a first-class product, and we want parity. Two Postgres concerns must not be conflated:

1. **The control plane's own DB (`bex-db`, exists)** — platform infra, the source of truth for tenants/apps/domains. Internally multi-tenant (a `tenant_id` column). Not a tenant resource.
2. **Tenant databases (this ADR)** — a Render-style "add a Postgres" that a tenant provisions, connects to, and deletes.

What Render actually does (confirmed by creating a real Free instance and connecting to it): a Postgres is a **standalone resource** with a create form (name, database, user, region, **version 13–18**, plan Free/Basic/Pro/Accelerated, storage, HA), and its **Connections** panel exposes two URLs that are the whole product:

- **Internal:** `postgresql://user:pass@dpg-<id>-a/db` — private network, same region, no SSL. For services _inside_ the platform.
- **External:** `postgresql://user:pass@dpg-<id>-a.<region>-postgres.render.com:5432/db` (Render documents `EXTERNAL_HOST:PORT/DATABASE`, https://render.com/docs/postgresql-creating-connecting) — public FQDN, **SSL required**, plus an IP allowlist. For anything _outside_.

## Decision

### 1. Operator: CloudNativePG (CNPG)

Already deployed, and validated over the alternatives:

- **Governance** — Apache 2.0, CNCF. Rules out KubeDB (freemium) and StackGres (AGPL).
- **Architecture** — native HA via the Kubernetes API (no Patroni/StatefulSet), less to operate than Zalando/Crunchy.
- **Fit** — every axis of the plan design maps to a built-in CNPG feature (below). When the product spec maps 1:1 onto the operator's CRDs, it's the right operator.

The operator is only the _executor_. Plans, per-tenant provisioning, connection-URL assembly, lifecycle, and metering live in **bex's control plane** on top of CNPG — that is the actual build, and it's the same for any operator.

### 2. A standalone `Database` resource → a CNPG `Cluster` in the tenant namespace

Render Postgres is standalone (created independently; multiple services connect to it; it outlives any one app). So model it as a standalone **`Database`** (control-plane row + CR), _not_ `App.spec.database`. The control plane projects it to a CNPG `Cluster` in the **tenant's namespace**, so it inherits that namespace's isolation for free — NetworkPolicy, ResourceQuota, RBAC, and namespace-scoped credential Secret.

### 3. Two URLs = two network paths (the core of the product)

|  | Render | bex (CNPG) |
| --- | --- | --- |
| **Internal URL** | `dpg-<id>-a` private host | the CNPG **`<cluster>-rw` ClusterIP Service**: `postgresql://user:pass@<cluster>-rw.<tenant-ns>.svc:5432/db` — in-cluster only, for the tenant's Apps. Free; CNPG creates the Service. |
| **External URL** | `<id>.<region>-postgres.render.com` + SSL (Let's Encrypt certificate) | the **`bex-pg-sni-proxy` DaemonSet** on `:5432`, routing by SNI to the right CNPG `<id>-rw` ClusterIP Service after handling the PostgreSQL SSLRequest preamble. **Production (w2/m245):** each public database serves a Let's Encrypt certificate for its public names, so connection-info returns Render's exact `postgresql://user:pass@<id>.db.bex.co:5432/db` (no `sslmode`, no `serverCaCertificate`) and a stock client connects with no downloaded CA — see [§ Publicly trusted server certificates](#publicly-trusted-server-certificates-w2m245). **Private-CA fallback** (`BEX_DB_CLUSTER_ISSUER` unset, or the certificate still issuing): CNPG's generated server certificate carries every public SNI alias, and the strings pin `:5432/db?sslmode=verify-full`. The client must then trust the database's server CA, which the authenticated connection-info read (REST `GET /v1/postgres/{id}/connection-info` + GraphQL `databaseConnectionInfo`) carries as an additive `serverCaCertificate` PEM field (w4/m95; certificate blocks only, never the key; the whole read answers an actionable 503 while that CA is unprovisioned rather than handing out a verify-full URL that cannot connect). The dashboard Connections panel offers it as a download plus `PGSSLROOTCERT` instructions. One CA covers the primary, pooler, and replica public endpoints. CNPG rotates it about every 90 days, and each rotation means re-downloading it. One wildcard `*.db.bex.co` fans out to every DB — no per-DB LoadBalancer. Opt-in per DB via `spec.public`. |

The external route is created by the operator only when `spec.public: true` and `BEX_DB_DOMAIN` is set (private by default). Key constraints:

- **DNS-only (gray-cloud) wildcard.** `*.db.bex.co` must be plain A records to the Terraform-owned edge load balancer, **not** Cloudflare-proxied ones — Cloudflare's proxy is HTTP(S) only; it cannot carry raw TCP `:5432` (that needs Spectrum, an enterprise feature). This differs from the App/API domains, which are proxied.
- **Production DNS reconciliation.** [`scripts/datastore-dns-cloudflare.sh`](../scripts/datastore-dns-cloudflare.sh) reconciles both `*.$BEX_DB_DOMAIN` and `*.$BEX_KV_DOMAIN` to the Terraform-owned `bex-traefik` load balancer's IPv4 address with `proxied:false`, removes stale, duplicate and AAAA records at those two wildcard names, and refuses CNAME/NS collisions. **IPv4 only (w9/m164, user decision 2026-11-04):** Render's datastore hosts publish A records only, and so do bex's. A published AAAA sent dual-stack clients over IPv6, where an allow list holding only their IPv4 refused them with a bare `SSL error: unexpected eof while reading` — including the product's own copied connection string. The shared reconciler takes `BEX_EDGE_DNS_FAMILIES=A` from this wrapper; the SSH edge keeps both families. Run it with an ephemeral zone-scoped Cloudflare DNS/Edit token; `--check` is read-only and must pass before external datastore acceptance. The App/API/custom-domain records remain Cloudflare-proxied and are outside this script's targets.
- **Postgres SSLRequest preamble (solved — w1/m29).** libpq's default negotiation sends a cleartext `SSLRequest` **before** the TLS `ClientHello`. The `bex-pg-sni-proxy` handles this: it receives the SSLRequest, replies `S`, reads the TLS `ClientHello` to extract the SNI hostname, connects to the appropriate CNPG backend, replays the SSLRequest/S exchange with it, then splices the connection bidirectionally. The proxy is not a TLS terminator — the TLS session is end-to-end between the client and CNPG. Direct-TLS clients (PG 17+ `sslnegotiation=direct`) are also handled transparently (no SSLRequest → the proxy reads the TLS `ClientHello` directly). The Traefik `postgres` entrypoint is removed; the proxy replaces it.

### Publicly trusted server certificates (w2/m245)

Render's Postgres hosts present Let's Encrypt certificates (`oregon-postgres.render.com`, `frankfurt-postgres.render.com`: issuer `Let's Encrypt YR1`, verify OK, checked 2026-10-29), so a copied external URL connects with no CA file. bex matches that when the operator's `BEX_DB_CLUSTER_ISSUER` names a cert-manager ClusterIssuer. Production sets `letsencrypt-prod`. Local and dev clusters leave it unset, because they cannot answer HTTP-01 for production names; they keep the private-CA contract in §3. Code: `lego/operator/internal/controller/database_public_tls.go`, `lego/backend/internal/postgres/service.go` (`externalURL`).

- **Issuance.** Each public Database gets a `<db>-public-tls` Certificate covering all of its public SNI names (primary, `-pool`, `-ro-<name>`). It is issued over HTTP-01 through Traefik: `dpg-*.db.bex.co` answers ACME on port 80, and the `allow-traefik-ingress` NetworkPolicy already admits the solver. The Secret is labeled `cnpg.io/reload` and stamped with the Database UID.
- **Wiring.** The operator changes the CNPG Cluster only once the Certificate is Ready for its current generation and the chain verifies (trusted root, primary hostname, unexpired). It then sets `spec.certificates.serverTLSSecret: <db>-public-tls` and `serverCASecret: <db>-public-ca`. The CA Secret has no key; it holds only the root(s) that anchor the issued chain, so replication trusts only the issuer that signed this database. `serverAltDNSNames` is dropped, because CNPG rejects it beside `serverTLSSecret`. CNPG keeps generating its own client CA and `streaming_replica` certificate. In-cluster names need not be on the public certificate: replication and PgBouncer connect with `verify-ca`, CNPG's status client ignores the DNS name, and pg-sni-proxy never terminates TLS. PostgreSQL hot-reloads a changed certificate (`cnpg.io/reload`), but PgBouncer reads it only at start: the Pooler's Pod template therefore carries a digest of the served certificate (`app.bex.co/served-certificate`), so enabling the pooler on an existing public database (which re-issues the certificate with the pooler's name) and every renewal roll PgBouncer onto the new certificate (w8/245). On production (2026-10-30) an HA database's replica streamed over TLS with the new certificate, and after a failover the former primary rejoined as a streaming replica.
- **Status.** `status.externalCertificate` is `Pending` while the certificate is issuing or being withdrawn. It becomes `PubliclyTrusted` only once CNPG's own status reports serving the Secret. The `PublicCertificateReady` condition gives the reason when it is not ready; it never affects the Database's Ready condition. Since w4/m357 the condition names a failed cert-manager attempt instead of reading `Issuing` throughout: `RateLimited` when the ACME error is Let's Encrypt's rate limit, `IssuanceFailed` for any other failure (cert-manager's `Issuing=False/Failed` for the Certificate's current generation; the raw message stays on the CR). A public Key Value carries the same condition for its `<id>-kv-tls` Certificate ([ADR021](ADR021-keyvalue-management.md)).
- **Pending and failed are visible (w4/m357).** The REST read, GraphQL `Database`, MCP `get_postgres` and connection info (REST + GraphQL `databaseConnectionInfo`) carry the bex extension `externalCertificate`: `publiclyTrusted`, `pending` or `failed`, absent with no external endpoint or no managed certificate, plus `externalCertificateReason`, a fixed sentence for `failed` (never the ACME text). The dashboard Connections card says the certificate is being issued, or failed, and that the CA below or `sslmode=require` connects meanwhile; it says nothing once trusted. Key Value carries the same fields.
- **Pending-too-long alert.** The operator's datastore collector exports `bex_datastore_public_certificate_pending_seconds{kind,namespace,name,reason}` (seconds since `PublicCertificateReady` turned False) and `PublicCertificatePendingTooLong` (`deploy/gitops/base/rules/alerting_rules.yml`) fires past 10 minutes.
- **Connection info.** With `PubliclyTrusted`, every external string (primary, pooler, replicas) is Render's `postgresql://user:pass@host/db`, and `psqlCommand` is Render's `PGPASSWORD=… psql -h host -U user db`. `serverCaCertificate` is omitted on REST and `""` on GraphQL, because system roots verify the chain. The URL has no `sslmode`: libpq's default (`prefer`) negotiates TLS, and the proxy accepts nothing else, so the session is always encrypted. `sslmode=verify-full` alone would make libpq demand `~/.postgresql/root.crt`, and `sslrootcert=system` breaks libpq < 16, node-postgres, pgjdbc and Prisma. A client that wants hostname verification adds `sslmode=verify-full&sslrootcert=system` (or its driver's equivalent) itself, and the certificate satisfies it. Without `PubliclyTrusted`, the private-CA contract in §3 applies unchanged.
- **Renewal.** cert-manager renews the certificate before expiry. The `cnpg.io/reload` label makes CNPG serve the new serial within about 40 seconds with no Pod restart. This was proven on dev-2 (CNPG 1.27) and by a forced renewal on production (2026-10-30, CNPG 1.30.1), after which the same URL connected unchanged. A served Secret stays served while it is valid, even while the Certificate re-issues for a changed name set. An expired or untrusted Secret is unwired.
- **Withdrawal.** Turning public access off reverts the Cluster to CNPG's certificate and deletes the Certificate at once. The two Secrets are deleted only after CNPG's status stops naming them, and only when they carry this Database's UID label or owner reference. Deleting the Database removes the Certificate before its Secret, so cert-manager never orders a replacement.
- **Let's Encrypt budget.** Let's Encrypt allows 50 new certificates per rolling week per registered domain (`bex.co`), refilled at about one per 202 minutes, shared with every other `*.bex.co` certificate (platform hosts such as `api`, `dashboard`, `status`); renewals are exempt. Each public database or Key Value is one certificate whatever its SAN count, and any change to its name set (pooler on or off, a replica added or removed, public access off and on) orders a new one.
  - **It bound on 2026-11-13 (w4/m357 t001).** Certificate Transparency (certspotter) shows 95 Let's Encrypt `bex.co` certificates in the 168 h before 02:23 UTC, almost all `dpg-*.db.bex.co` and `red-*.kv.bex.co` from QA rounds that create a public datastore each, then one issuance per refill (issued about 04:33, 08:09, 10:43, 13:58, 17:23, 20:18). A database created into the empty bucket kept CNPG's private CA, so its copied URL carried `sslmode=verify-full` and failed on a stock client, and a Key Value had no external listener at all. cert-manager then backs the failed Certificate off 1 h, 2 h, 4 h … up to 32 h, so the stall outlasts the refill. `onbex.co`'s own 50/week budget was exhausted the same week by per-host App certificates (w4/650).
  - **Lasting fix (gated on a credential).** One `*.db.bex.co` and one `*.kv.bex.co` wildcard, issued over DNS-01 by a namespaced Issuer like ADR093's `traefik/onbex-dns01`, copied by the operator into each public datastore's namespace as `<db>-public-tls` / `<id>-kv-tls`, so creating a datastore orders nothing. It needs a Cloudflare API token with Zone:DNS:Edit + Zone:Read on the `bex.co` zone only (the existing `BEX_CLOUDFLARE_DNS_TOKEN` is scoped to `onbex.co`), stored as `BEX_DATASTORE_DNS_TOKEN` in `.env` and the `production-deploy` environment and installed as a Secret beside that Issuer. Until it exists, QA rounds create private datastores unless they probe this path, and the alert above reports a recurrence.
- **Known limit, same as Render.** A client machine with a stale `~/.postgresql/root.crt` still verifies against that file.

### TLS passthrough and query cancellation (w8/m87, user decision 2026-11-01)

The SNI proxy routes each external connection by its TLS server name and relays the encrypted stream unchanged: it holds no tenant database private key and never sees SQL. PostgreSQL's legacy cancel request (`PQcancel`, what psql sends on Ctrl+C) is a separate plaintext connection carrying only the backend PID and secret key, with no server name, so the proxy cannot route it, and the running statement continues. The alternative — terminate TLS at the shared proxy with every database's serving key to observe `BackendKeyData` and route cancels ([design](../.pm/w8/done/m87/design.md) history in w8/m87) — was declined by the user: the passthrough trust boundary is kept. libpq 17+'s TLS cancel (`PQcancelCreate`) carries SNI and works; so does `pg_cancel_backend()` from a second session. ADR018 records the difference; `docs/bex-cli.md` tells psql users.

### Postgres SNI proxy — deployment (w1/m29)

The proxy binary (`/pg-sni-proxy`) lives in the same image as the operator. A `DaemonSet` (`bex-pg-sni-proxy`) runs on platform nodes, listening on container port 5432, and watches `Database` CRs cluster-wide to maintain its routing table. It needs a `ClusterRole` to `list/watch` databases.

**When it rolls (w6/m470).** The DaemonSet takes the operator image under its own kustomize pin, and `deploy.yml` keeps that pin while the new image's `/pg-sni-proxy` is byte-identical to the pinned one's. A platform deploy that leaves the proxy's code alone therefore replaces no proxy pod and closes no external connection, as on Render; a code or DaemonSet template change still rolls it. The rule, shared with `bex-kv-sni-proxy`, is [ADR021 § 10](ADR021-keyvalue-management.md#10-a-platform-deploy-rolls-no-stores-proxy-w6m469-w6m470-2026-11-18).

**A roll that changes it drains (w6/m515).** The DaemonSet asks for no `hostPort` and rolls with `maxSurge: 1`, `maxUnavailable: 0`, so each node's new pod is the Local NodePort's endpoint, Ready, before the old pod is told to stop. The old pod keeps accepting through a 5 s `preStop` pause while its endpoint leaves the nodes' service rules. On `SIGTERM` it stops accepting, and a query in flight gets its result: open streams relay until they end or `BEX_PROXY_DRAIN_SECONDS` passes, within the grace period. The bound is 3,600 s under a 3,645 s grace period (w6/m518 and w6/151; 30 s from w6/m515 until then), so a session that ends within the hour is never cut by a roll. Once its last stream has ended, the old pod waits up to 35 s for a Prometheus scrape to read the bytes it counted, and it counts each stream's bytes as it delivers them (w6/151). That scrape reads its drained gauge at 1, so the egress meter bills the hour the pod exits in (w6/155, ADR023). Neither the deploy's wait nor `bex-operator`'s Argo health waits for the draining pod: both read each node's new pod. A session held busy for longer is still closed once, at the bound, on each deploy that changes the binary, the gap ADR021 § 10 records with the rule, the rejected directions and the local and production measurements.

**Dev:** the proxy has no host port. A local client reaches it through a NodePort (`config/prod`'s, applied by hand) or `kubectl port-forward` (`scripts/psql-compat-verify.sh`). The `hostPort: 5432` dev edge was removed in w6/m515: it kept the surge pod off the node, and PodSecurity `baseline` refused it.

**Prod (Hetzner LoadBalancer):** port `5432` is absent from Traefik's Service. The prod kustomization creates a fixed NodePort selecting the proxy DaemonSet; Terraform owns the shared edge LB's `5432 → 31056` listener and TCP health check:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: bex-pg-sni-proxy-public
  namespace: bex-system
spec:
  type: NodePort
  externalTrafficPolicy: Local
  selector:
    app.bex.co/component: pg-sni-proxy
  ports:
    - name: postgres
      port: 5432
      targetPort: 5432
      nodePort: 31056
      protocol: TCP
```

The kustomization applies this object with the rest of the operator; it is not a manual post-deploy step. `externalTrafficPolicy: Local` ensures the Hetzner health check and traffic reach only platform workers with a local proxy pod, but a TCP load balancer still replaces the application-visible client address. Terraform therefore enables PROXY protocol on only the PostgreSQL and Valkey listeners. Before reading the PostgreSQL preamble, each proxy accepts a bounded v1/v2 header only when the immediate peer is the load balancer's fixed `10.10.0.7/32` private address; the asserted original address drives both allowlist layers. Headerless direct/dev connections retain their socket source, while a header from any other peer fails closed. **`BEX_PROXY_PROTOCOL_TRUSTED_CIDRS` must stay this narrow — the immediate edge/LB peer only (a single `/32` here).** Whatever it trusts can assert an arbitrary original client address, so widening it to a shared range (notably the tenant pod CIDR) would let a tenant workload spoof its source IP and defeat the per-Database `ip-allow-list` that keys on it; the DB password remains the second layer, but the allowlist must not be silently bypassable. The Valkey/`kv-sni-proxy` mirror (ADR021) carries the identical constraint. The rollout is compatibility-first: when a saved Terraform plan would enable either datastore listener, `infra.yml` waits for the same commit's `deploy.yml` run; that deploy succeeds only after both proxy DaemonSets run the digest its write-back pinned for them, the freshly built one or a held one with a byte-identical binary. A failed or missing deploy leaves the load balancer unchanged. The production `allow-production-edge-proxies` NetworkPolicy admits public traffic only to the PostgreSQL/Valkey proxy pods on their two public ports; every other `bex-system` workload remains under the namespace default deny.

### Server connection limit (w6/134, 2026-11-17)

Each plan's PostgreSQL runs Render's connection limit for the plan ([compute plans § Render Postgres plans](https://render.com/docs/compute-plans), read 2026-11-17): 100 up to 4 GB, 200 for `2c-8g`, 400 for `2c-16g` and `4c-16g`, and 500 from 32 GB. `connlimit.Postgres` (`lego/types/tiers/connlimit`) carries the figure for each plan, `tiers` copies it into each tier's `MaxConnections` (w6/154, [ADR021 § 10](ADR021-keyvalue-management.md#10-a-platform-deploy-rolls-no-stores-proxy-w6m469-w6m470-2026-11-18)), and `TestPostgresMaxConnectionsMatchRender` pins every id and alias bex accepts to Render's table, so a tier added later (w6/m332) must carry Render's figure. The SNI proxies' route admission (below) and the PgBouncer pool ([§ Managed PgBouncer settings](#managed-pgbouncer-settings-w6m458-2026-11-17)) are sized from the same figure.

- **Set explicitly.** `cnpgClusterSpec` puts `max_connections` into the Cluster's `spec.postgresql.parameters` from the plan, after the tenant's legacy `spec.parameters`. A declared `max_connections` in any spelling is dropped, so the server can never run a figure the pool and the proxies were not sized for. Recovery strips a source's declared value too (`operatorManagedParameters`). Before this the operator set nothing and every cluster ran PostgreSQL's default 100, Render's figure for every current plan only by accident.
- **No restart for existing databases.** Changing `max_connections` needs a PostgreSQL restart, but CNPG reloads the configuration and restarts only when `pg_settings.pending_restart` turns true. Every current plan's 100 equals the running value, so it never does. On dev-6 (CNPG 1.30.1, PostgreSQL 18), one probe Cluster per current plan was created from the previous spec and then given the new one: each read `max_connections` 100 from CNPG's `custom.conf` within 5 s, with `pending_restart` false, the same Pod UID, restart count 0 and the same `pg_postmaster_start_time()` a minute later. In a contrast run, setting 101 on one probe restarted its PostgreSQL in place within 10 s. Production on 2026-11-17 had four tenant databases (two `basic-256mb`, two `basic-1gb`; PostgreSQL 18.4 and 16.15), none declaring `max_connections`, each running 100 from initdb's `postgresql.conf`, so the deploy carrying this change rolls none of them.
- **A plan with another limit.** A plan change to a plan with another figure (w6/m332's 200 or 400) changes the value, and CNPG restarts PostgreSQL to apply it, as in the contrast run.
- **Shown beside the Metrics chart (w6/138, 2026-11-18).** As on Render's dashboard ([render-artifacts/postgres-connection-limit.md](render-artifacts/postgres-connection-limit.md#the-active-connections-chart-w6138-2026-11-18)), the Active Connections chart reads "Limit N" beside its title, from GraphQL `databaseInstanceTypes.maxConnections`. Render's plan cards show no limit, so bex's do not.

### External connection admission (w6/m457, 2026-11-17)

An allowlisted client outside the cluster gets its datastore's own connection limit, as on Render: Render documents one connection limit per plan ([compute plans](https://render.com/docs/compute-plans), read 2026-11-17) and no separate cap for external connections. Past the limit the client reads the server's own refusal, never a dropped connection. The same rule holds for `kv-sni-proxy` ([ADR021 § 9](ADR021-keyvalue-management.md#9-connection-limits-w6m456-2026-11-17)).

**What it replaced.** `91a24194f` (2026-08-16, "remediate repository security review", findings 6 and 19) gave both SNI proxies 1,024 connections per process, 128 per source, 256 per workspace and 64 per resource, recorded in no ADR. One bucket held a database's primary, pooled and replica hostnames together. Every external Postgres client stopped at 64, against Render's 100, and the proxy closed the 65th after the TLS ClientHello. `psql` read that as `SSL error: unexpected eof while reading`. ADR008 § Render parity first amends that hardening choice.

**The rule.** The proxy relays TLS end to end, so it cannot write PostgreSQL's error itself: any client it sheds sees a closed connection. Each cap is therefore either the server's limit with room above it, or process protection that no tenant within its plan reaches.

| cap | before | now | reason |
| --- | --- | --- | --- |
| per route (one public hostname of one datastore) | 64 per resource | twice the server's limit (`sniproxy.RouteCapacity`): the plan's `max_connections` for the primary and each `-ro-<replica>` (Render limits each replica like its primary), `connlimit.PostgresPoolerMaxClientConn` (30,000, Render's PgBouncer `max_client_conn`) for `-pool` and each replica's own `-rp-<replica>` (w6/m467) | Up to twice the limit, the client past it still reaches PostgreSQL and reads its refusal, even when as many arrive at once as the plan holds. A refused connection leaves once the server has answered it. |
| per workspace | 256 | none | With every route bounded, a workspace's total is the sum of its routes' caps, so a workspace cap either repeats that sum or refuses a tenant within its plans. |
| per source (`BEX_PROXY_MAX_CONNS_PER_SOURCE`) | 128 | off (`0`), kept as an incident lever | One client host is entitled to its datastores' whole limits. The largest (Key Value `pro_max`'s 20,000, the pooler's 30,000) exceed a whole process, so any per-source cap either refuses a host within its plan or repeats the global cap. |
| handshake, per IPv4 /24 or IPv6 /64 (`BEX_PROXY_MAX_HANDSHAKES_PER_NETWORK`) | 32 | 128 | It counts only connections still between their PROXY header and their SNI, never held ones. It keeps R25-12's ratio: 32 networks are still needed to fill a process ([ADR110](ADR110-security-review-round25.md)). One host opening 128 connections at once into one replica, about 384 across three, is still admitted. |
| global per process (`BEX_PROXY_MAX_CONNS`) | 1,024 | 4,096, memory limit 96 Mi → 512 Mi, `GOMEMLIMIT` 400 MiB | The edge load balancer (Hetzner `lb11`, `max_connections` 10,000 for all five listeners, `round_robin`) spreads connections over the three platform replicas, at most about 3,334 each. 4,096 idle routed connections measured 412 MB in the proxy's cgroup on linux/arm64 (374 MB anonymous, 36 MB kernel), about 95 KB each. |

The route's capacity is computed from the `Database` CR on every watch event, so a plan change reaches the proxy without a restart. `tiers.Postgres.Resolve` is the same resolution the operator sizes the server from. A shed past a route's capacity is still metered as `reason="resource"`.

**What the client reads.** PostgreSQL keeps `superuser_reserved_connections` (3) of its 100. A tenant role past the remaining slots reads `FATAL: remaining connection slots are reserved for roles with the SUPERUSER attribute` (SQLSTATE 53300; PostgreSQL 16+). `sorry, too many clients already` is what a client reads once every slot is held. Verified locally on 2026-11-17 against PostgreSQL 18.6 with TLS, through `handleConn` with the shipped caps: 110 concurrent `psql` sessions as a non-superuser to a `basic-256mb` route admitted 97, and the other 13 read that FATAL. The same run with the old 64 admitted 64, and the other 6 read `SSL error: unexpected eof while reading`. CNPG's own superuser sessions use ordinary slots, so on a live cluster a tenant sees a few fewer than 97. Verified on production on 2026-11-17 (pin `e36296ae8`): from a host on the probe's allowlist, 110 concurrent external `psql` sessions as the tenant role to a `basic-256mb` database (PostgreSQL 18.6) held 96, and the other 14 read that FATAL. None read an EOF or an SSL error, and no proxy replica counted a rejection.

**No idle or lifetime bound in the proxies (w6/149, 2026-11-20).** A routed stream stays open in the proxy however long it is silent and however old, as a direct connection does: PostgreSQL closes no idle session by default, Valkey's `timeout` is `0` by default and "does not apply to Pub/Sub clients" ([valkey.io/topics/clients](https://valkey.io/topics/clients/)), and Render documents no such close ([Key Value](https://render.com/docs/key-value), read 2026-11-20). `BEX_PROXY_IDLE_TIMEOUT` and `BEX_PROXY_MAX_LIFETIME` (`kv-sni-proxy`: the `BEX_KV_PROXY_*` pair) are unset, read by `sniproxy.StreamBounds`, and stay as incident levers: set, a stream closes once neither direction has moved a byte for the idle bound (w6/148), and at the lifetime however busy. `TestByDefaultASilentStreamStaysOpenUntilEitherSideCloses` holds an unbounded stream silent, relays after the silence, and closes it as soon as either side closes.

- **What it replaced.** F6 of the 2026-08-16 repository security review (w1/m65 t008) gave every routed stream a 1 h idle and a 24 h lifetime bound: a routed copy could idle forever after auth, and the proxies had no admission caps then. Until w6/148 each direction counted alone, so a client that only received was closed an hour after its last command while its messages kept arriving (on production, w6/m515 t006's subscriber, five hours in a row). w6/148 made bytes either way hold the stream open, and a stream silent both ways for an hour, and every stream at 24 h, were still closed. ADR008 § Render parity first amends that hardening choice. A busy stream now lives past 24 h.
- **Why the process needs neither.** Since w6/m457 the admission caps hold it: each route admits twice its server's limit and each process 4,096 streams (above), so an idle stream holds a slot its datastore's own limit already counts. 4,096 idle routed streams measured 412 MB in the proxy's cgroup, under its 512 Mi limit. The idle bound never kept a client from holding a slot either: one byte an hour kept a stream open.
- **The edge load balancer still closes a stream that carries no data for an hour (measured on production, 2026-11-20, w6/149).** Every external stream crosses one of the Hetzner load balancer's TCP services (PROXY protocol), and Hetzner exposes no idle setting on a TCP service (`http.timeout_idle` exists only on HTTP services). A silent TCP connection through its HTTP listener, where Traefik's own read deadline is 6,000 s, got the load balancer's FIN exactly 3,600 s after it opened, and so did one whose client had vanished, while the same silent connection straight to a Traefik pod stayed open past the hour. Two silent TLS clients through the Key Value listener closed at the same 1 h mark. In that hour the load balancer sent no keepalive probe, and Traefik's 3 min TCP keepalive on the load balancer's leg did not hold the flow. So an external `LISTEN` or `SUBSCRIBE` client that gets nothing for an hour, or an idle pool or `psql` session, is still closed at 1 h, by the load balancer. [ADR018](ADR018-render-parity.md#other-datastores--storage) records it as a divergence that needs the user's decision.
- **Dead peers.** Go keeps TCP keepalive on both of the proxy's sockets (15 s idle, then a probe every 15 s, 9 probes), so a dead load-balancer leg or backend leg closes within about 2.5 min, and the other leg with it. Behind the load balancer the client socket's peer is the load balancer, not the client, so a client that vanishes without a FIN or RST is reaped when the load balancer closes its leg, at its 1 h idle timeout, as the vanished client above was.
- **On a roll** an old pod's drain closes every stream still open at its bound (§ A roll that changes it drains above, ADR021 § 10).

**Residual exposure.**

- **One source.** With no per-source cap, one address can hold as many connections as the routes that admit it allow, each route up to twice its limit. To fill a process it needs routes whose allowlists admit it, for example ones open to `0.0.0.0/0`, adding up to 4,096. `DatastoreProxyShedding` alerts on sustained `reason="global"`, and `BEX_PROXY_MAX_CONNS_PER_SOURCE` can be set during an incident.
- **The edge.** The edge load balancer admits 10,000 connections across HTTP, HTTPS, SSH, PostgreSQL and Valkey together. That is less than a Key Value `pro_plus` or `pro_max` store's limit, or the pooler's 30,000. Raising it is a load-balancer type decision (`lb21` 20,000, `lb31` 40,000), filed as [w6/136](../.pm/w6/blocked/136.md).

### Managed PgBouncer settings (w6/m458, 2026-11-17)

A pooled database's PgBouncer runs Render's settings ([connection pooling](https://render.com/docs/postgresql-connection-pooling), read 2026-11-17), set per plan by `pgbouncerParameters` in the CNPG `Pooler`'s `spec.pgbouncer.parameters`. Before this the Pooler set only `poolMode`, so PgBouncer ran its own defaults, read with `SHOW CONFIG` on a dev-6 `basic-1gb` pooler (PgBouncer 1.25.2, CNPG 1.30.1): a pooled database refused its 101st client where Render accepts 30,000.

| setting | Render | before (PgBouncer default) | now |
| --- | --- | --- | --- |
| `max_client_conn` | 30000 | 100 | 30000 (`connlimit.PostgresPoolerMaxClientConn`) |
| `default_pool_size` | `max_connections` − 10 | 20 | the plan's `maxConnections` − 10 (`PostgresTier.PoolerPoolSize`): 90 on every current plan |
| `max_db_connections` | `max_connections` − 10 | 0 (unlimited) | as `default_pool_size` |
| `client_idle_timeout` | 86400 | 0 (never) | 86400 |
| `server_login_retry` | 2 | 15 | 2 |

- **Accepted and reloaded.** All five are on CNPG 1.30.1's PgBouncer parameter allowlist and are reloadable. A change rewrites `pgbouncer.ini` and CNPG issues `RELOAD`, so the PgBouncer Pod does not roll. On dev-6, 1,000 `pgbench` clients through a Render-configured pooler held 90 server connections with 910 clients waiting. A pool resize mid-run (90 → 50) reloaded without a restart, and the run finished with 0 failed transactions. PgBouncer closes only idle server connections, so a smaller pool takes effect as the busy ones free up. Every current plan has Render's 100 connections, so today a plan change leaves the pool at 90. A plan with another limit (w6/m332's 200) gets its own pool on its next reconcile.
- **Reserved connections.** The 10 Render reserves cover direct connections and the pooler's own login lookups. CNPG's PgBouncer authenticates each new client with `auth_query` over a separate `cnpg_pooler_pgbouncer` pool on the `postgres` database: 4 server connections during a 1,000-client login burst. `max_db_connections` limits each database, so a tenant using additional databases (w8/m155) gets a pool for each, as Render's PgBouncer does.
- **Capacity for 30,000 clients.** PgBouncer needs a file descriptor per client and per server connection, and PgBouncer logs `max expected fd use: 30012`. **The open-file soft limit (corrected 2026-11-17 by the production check).** Production's tenant nodes (containerd 2.3.3) start a container at a soft limit of 1,024 under a hard limit of 524,288, and CNPG's Go manager hands PgBouncer that soft 1,024 (PgBouncer logs `kernel file descriptor limit: 1024 (hard: 524288)`); kind's 1,073,741,816 hid it on dev-6. PgBouncer never raises its own limit, so on production 1,000 `pgbench` clients through a `basic-1gb` pooler left it `accept() failed: Too many open files`, holding 10 server connections of its 90 at 63 transactions per second. `poolerTemplate` therefore sets the container's command to `pgbouncerRunCommand`, which raises the soft limit to the hard one (no privilege needed) and then `exec`s CNPG's own `/controller/manager pgbouncer run`; CNPG keeps a command its template sets. A Pooler with that command on production read `kernel file descriptor limit: 524288`, and the same 1,000 clients held 87 server connections (the other 10 of the database's 97 tenant slots went to two poolers' `auth_query` sessions) with 913 waiting, at 412 transactions per second and none failed. Measured on dev-6 with TLS clients: 23 MiB of cgroup memory idle, 143 MiB with 3,000 connected (about 42 KB each), so about 1.2 GiB at 30,000. `poolerTemplate` sets the container's resources explicitly instead of inheriting `tenant-limits`' defaults (100m / 128 Mi, 2 / 4 Gi). The request is 100m / 256 Mi, about 5,000 clients, which is what a quiet pooler reserves on its node. The limit is 2 CPU / 2 Gi; PgBouncer is single-threaded, so it uses at most one core. Pooler Pods carry the `bex-datastore` class, which `tenant-compute-quota` excludes, so the larger request takes nothing from a workspace's service quota. Production had no Pooler on 2026-11-17, so no PgBouncer rolls for the new template or for the command.
- **Each read replica has its own pool (w6/m467).** Render: "Render automatically enables it for all of that database's read replicas", and "Each read replica has its own independent connection pool." Each replica of a pooled database gets its own CNPG `Pooler`, `<id>-rp-<name>`, `type: rw` on its own replica cluster (whose read-write Service is its designated primary, read only), with the same settings and template. Its pool is `maxConnections` − 10 on its own instance, so two replicas hold two pools, as Render's do ([§ Per-replica readers and pools](#per-replica-readers-and-pools-one-replica-cluster-per-name-w6m467-decided-2026-11-18)). A replica's pooler goes away with pooling or with the replica. From w6/m458 until w6/m467 one `Pooler` `type: ro`, `<id>-pooler-ro`, fronted the primary Cluster's `-ro` Service for every name, so several replicas shared one replica's pool.
- **Production check (2026-11-17, pin `e36296ae8`).** A `basic-1gb` probe with pooling and one replica in `bex-canary`: both PgBouncers' `SHOW CONFIG` read `max_client_conn` 30000, `default_pool_size` and `max_db_connections` 90, `client_idle_timeout` 86400 and `server_login_retry` 2 (PgBouncer 1.25.2). Through `<id>-pooler-ro:6432` a client read the replica (`pg_is_in_recovery()` true, the replica Pod's address) and a row written through the primary's pooler, and an `INSERT` was refused as read-only; both external pooled names (`-pool`, `-pool-ro`) connected with `verify-full`. 1,000 clients on the operator's pooler hit the open-file limit above. **Re-run (2026-11-18, pin `359aee37d`, which carries `pgbouncerRunCommand`).** On a new `basic-1gb` pooled probe in `bex-canary`, the operator's own Pooler and its Pod ran the command, and PgBouncer logged `kernel file descriptor limit: 524288 (hard: 524288)`. `pgbench -c 1000 -j 10 -T 60` with a 0.2 s query on the internal pooled URL: all 1,000 clients connected (in 5.1 s), `SHOW POOLS` held exactly 90 server connections (`sv_active` 90) with 910 clients waiting throughout, plus 5 `cnpg_pooler_pgbouncer` lookup connections, at 434 transactions per second (the pool's ceiling is 450) with 0 failed, and PgBouncer logged no `Too many open files`. The probe was deleted by ID (`DELETE` 204, then `GET` 404).

### 4. Naming convention (copy Render's reasoning, not its strings)

Render's URL is engineered for three constraints at once; bex should satisfy the same:

- **Identity and display name are separate.** Every resource mints `Database.metadata.name = dpg-<xid>` through `internal/id`; this immutable value is the REST/GraphQL/MCP id and the root of every physical object name. The required `Database.spec.name` is the mutable, user-facing DNS-label name. The production and maintained-dev fleets were verified to contain no old name-as-id or missing-name objects before the legacy reader was removed (w1/m56 t009).
- **Explicit or defaulted physical identity** — create may set optional `spec.databaseName` and `spec.databaseUser`, matching Render's `databaseName` / `databaseUser` contract. Each is validated independently as a lowercase PostgreSQL unquoted identifier (`[a-z_][a-z0-9_]{0,62}`) and is immutable after creation. Omission independently defaults the database to the immutable id with hyphens replaced by underscores (`dpg-…` → `dpg_…`) and the owner to `<default-database>_user`; supplying only one field does not change the other's default.
- **Rename-safe** — the operator, connection-info view, CNPG bootstrap, and recovery flow all consume that effective physical identity. Changing mutable `spec.name` therefore cannot change credentials or SQL identifiers, and recovery copies the source's effective database/user pair into the new CR so the restored archive opens under the same SQL identity.
- **Typed opaque ID in the SNI hostname** — the immutable ID (not the mutable name) lives in `<id>.db.bex.co`, so a **rename never breaks a connection string**, the ID is unique/non-guessable, and one wildcard endpoint routes by SNI to the right backend. (Render: `dpg-<id>-a` where `-a` is the primary-instance address.)
- **Brand domain** — external endpoint on `db.bex.co` (the brand), not the app-hosting `onbex.co` — same rule as `api.bex.co` vs `onrender.com`.

### 5. Plans — three axes, not one size knob

Reading Render's pricing carefully: Free and Basic-256mb are _identical specs_ ($0 vs $6 — the difference is backups/persistence), and Pro-4gb ($55, 1 CPU) is cheaper than Basic-4gb ($75, 2 CPU) — because **Pro sells availability + PITR, not raw compute**. So a plan decomposes into three axes, each a distinct CNPG field:

| axis | CNPG field | Free | Basic | Pro |
| --- | --- | --- | --- | --- |
| compute (RAM/CPU) | `spec.resources.requests==limits` | 256Mi/0.1 | 256Mi–4Gi / 0.1–2 | 4–16Gi / 1–4 |
| availability | `spec.instances` (+ sync replica, anti-affinity) | 1 | 1 | **3, failover** |
| durability | Barman Cloud `spec.plugins[]` + plugin `ScheduledBackup` | none, expires | daily | **WAL → PITR** |
| storage | `spec.storage.size` (expand-only) | 1Gi bundled | bundled | metered |
| version | `spec.imageName` / `ImageCatalog` (per-cluster) | any of 13–18 |  |  |
| tuning | `spec.postgresql.parameters` (shared_buffers ~25% RAM; `max_connections` the plan's, [§ Server connection limit](#server-connection-limit-w6134-2026-11-17)) | per plan |  |  |

Every Render Postgres feature (per-tenant version, daily backup, PITR, HA, pooling, hibernation) maps to a CNPG mechanism — so CNPG is sufficient for Render parity, and there is no case for switching to Crunchy (pgBackRest only wins at extreme scale) or a multi-engine strategy (Redis etc. is a _separate operator_, not a CNPG gap).

### Capacity admission (w8/m50)

The existing catalog now owns capability metadata as well as resource sizes. [Free Postgres has fixed 1 GB storage](https://render.com/docs/free), so free creates and storage growth cannot exceed that size and free disk autoscaling is unsupported. Paid storage retains the catalog's 16,384 GB ceiling. [Managed pooling requires a paid plan](https://render.com/docs/postgresql-connection-pooling). [Read replicas require 0.5 CPU, 10 GB effective storage and a maximum of five](https://render.com/docs/postgresql-read-replicas); `basic-1gb` with 10 GB qualifies, independently of HA's 1-CPU rule. Primary documentation checked 2026-10-02; no plan or price is added.

One admission helper checks creates and merged updates, including dry runs, plan changes and Blueprint sync. The allocated-storage high-water mark participates, so a downgrade cannot disguise an existing larger volume. Refusals precede writes. Existing unsupported settings survive unrelated edits and can be disabled; storage and replicas are never silently shrunk or removed. The operator skips automatic growth on free even when an older database still has autoscaling enabled. Dashboard controls consume server metadata rather than duplicating plan policy.

Each eligible named replica is a one-instance CNPG replica cluster of its own ([§ Per-replica readers and pools](#per-replica-readers-and-pools-one-replica-cluster-per-name-w6m467-decided-2026-11-18), w6/m467), beside the primary Cluster's plan/HA instances; readiness waits for the primary and every replica's instance. Autoscale quota uses the change in aggregate provisioned storage across the primary Cluster and the replica clusters, including replicas that become eligible when storage grows to 10 GB. Ineligible legacy declarations keep their names and get no instance and no host. Until w6/m467 the eligible names added instances to the primary Cluster and shared its `-ro` Service; before w8/m50 they were aliases with no reader at all when HA was off.

**Shipped plan ladder (w2/m171, 2026-10-29).** `lego/types/tiers/tiers.yaml` carries `free`, `basic-256mb` (0.1 CPU), `basic-1gb` (0.5 CPU), `1c-2g` (1 CPU / 2 GiB, $28.00/mo), `pro-4gb` (alias `1c-4g`, `pro_4gb`; 1 CPU / 4 GiB, $38.50) and `basic-4gb` (alias `2c-4g`, `basic_4gb`; 2 CPU / 4 GiB, $52.50), priced at Render × 0.70 (small tiers corrected to $4.20 / $13.30; [ADR030](ADR030-pricing.md)). High availability is available only on plans with at least 1 CPU, so on the last three; see [HA](#high-availability). Live Stripe catalog provisioning for the new prices is still pending.

### 6. Lifecycle (create → URLs → connect → delete)

1. **Create** `Database{metadata.name: dpg-<xid>, spec: {name, plan, version, storage, databaseName?, databaseUser?}}`; the API validates explicit physical identifiers and the CRD makes them immutable.
2. **Provision** → CNPG `Cluster` in the tenant namespace from the plan catalog; CNPG creates the effective database/owner pair and stores the generated password in a namespace Secret.
3. **Surface connection info** → the control plane assembles both URLs + host/port/db/user/password/psql-command from the Secret and the `-rw` Service (the Connections panel).
4. **Delete** → deleting the `Database` deletes the Cluster + Service + Secret + PVC and drops the external SNI route. (Optionally a final backup first.) While the `app.bex.co/db-finalizer` holds the CR (`DeletionTimestamp` set), tenant **by-id reads** return the same `not found` as an absent id (`core.NotFoundIfDeleting`, w8/m35) — REST get/connection-info and siblings, GraphQL, MCP — and List omits the row; workspace-limits still counts it under `terminating` (w6/m129). The internal `pgView` may still project `status: deleting` for operator-facing code paths that bypass the read gate. A finalization that overruns its 15-minute bound stamps `DeletionStalled` on the Database (w8/012; same condition name as Apps) and backs the requeue off while retaining the finalizer.

### Rename and normalized identity

`PATCH /v1/postgres/{id}` changes only `spec.name`. The `Database` metadata name/UID, CNPG Cluster, PVC, credential Secret, Services, pooler, routes, backup server/prefix, exports, recovery references, project/environment membership, connection strings, SQL database, and owner role remain attached to the immutable id. The same core mutation backs REST, GraphQL `renameDatabase`, MCP `update_postgres(name:)`, and the dashboard; `dryRun=true` runs identical validation without writing.

The original rollout expanded the CRD, backfilled `spec.name`, and proved identity preservation before enabling rename traffic. On 2026-07-28, production and the maintained local cluster both reported zero missing names and zero non-typed ids; `spec.name` then became required and the one-time migration script plus metadata-name fallback were retired. A rollback restores the preceding code/CRD commit without reversing canonical object data.

For a live rename, capture identities with `scripts/postgres-rename-verify.sh snapshot`; run the official-CLI smoke (`scripts/postgres-rename-cli-smoke.sh`), which resolves the new name back to the same id; compare the snapshot afterward. The 2026-07-15 production proof preserved all 11 recorded object UIDs while renaming a fresh `dpg-…` resource.

### Create-time physical identity proof (w6/m38)

REST, GraphQL `createDatabase`, MCP `create_postgres`, Blueprint `databaseName`/`user`, and the dashboard create dialog all reach the same core create contract. Invalid or overlength identifiers return a named 400 before any CR is written. Unsupported Render Datadog create/update fields also return a named 400; bex never stores the API key or pretends monitoring was configured.

[`scripts/postgres-create-cli-smoke.sh`](../scripts/postgres-create-cli-smoke.sh) is the live acceptance verifier. On 2026-07-18 it drove the unmodified Render CLI v2.21.0 against isolated dev-6, created both-custom, database-only, and user-only cases, waited for real CNPG readiness, and asserted the CR, generated Secret, `current_database()`, and `current_user` without printing credentials. It then proved both Datadog create and update fail closed and removed every disposable resource.

### 7. Security floor (not optional, even in MVP)

- **Internal path** — the tenant's default-deny NetworkPolicy already isolates the `-rw` Service to the tenant's own pods.
- **External path** — a public Postgres port. **Require TLS** and a per-DB **IP allowlist** (Render exposes exactly this). Without it you're publishing an open Postgres. The SNI proxy accepts nothing but TLS, so even Render's URL shape, which carries no `sslmode`, always connects encrypted.

## MVP scope

Ship only what fits the current single `cx33` (8 GB) node — single-instance plans differing by resources + backup:

- **free** — 256Mi/0.1CPU/1Gi, `instances:1`, no backup, **30-day TTL** (a control-plane sweeper — else "free forever" eats the cluster, which is why Render expires them). The contract is [§Free-plan expiry](#free-plan-expiry-w8m126).
- **basic-256mb** — 256Mi/0.1CPU, `instances:1`, daily `ScheduledBackup`.
- **basic-1gb** — 1Gi/0.5CPU, `instances:1`, daily backup.

The first cut included the external URL because it is central to the Render experience; the original Traefik TCP route was later replaced by the protocol-aware metered proxy in §3.

### Free-plan expiry (w8/m126)

Render's rules, from [render.com/docs/free](https://render.com/docs/free) (read 2026-10-20) and the pinned spec's `postgres.expiresAt` / `postgresDetail.expiresAt` ("The time at which the database will be expire. Applies to free tier databases only."):

| Rule | Render | bex |
| --- | --- | --- |
| Clock | "Free Render Postgres databases expire 30 days after creation." | `expiresAt` = the free clock's start + 30 days. The start is the creation time, or the time of a change to `free` (`bex.co/free-since`). |
| `expiresAt` field | Free databases only. | RFC 3339 UTC on REST, GraphQL and MCP for a `free` database; omitted for every paid plan. |
| At expiry | "An expired Free database is inaccessible unless you upgrade it to a paid compute plan." | The sweeper suspends it (CNPG hibernation: compute stops, PVC and credentials kept). It reads `suspended` with suspenders `["billing"]` and a `statusReason`. Resume is refused (`POSTGRES_FREE_EXPIRED`) until the plan is paid. |
| Grace | 14 days to upgrade, then Render deletes the database and its data. | Deleted at `expiresAt` + 14 days through the same path as a user delete: usage retirement recorded first, the CR delete cascades the cluster, PVC and Secret. |
| Notifications | Email as expiry approaches and as the grace period's end approaches. | Workspace owners are emailed 7 days before `expiresAt`, at expiry, and 3 days before deletion. |
| Upgrade | Any paid plan removes the expiry. | A change to a paid plan drops `expiresAt` and the expiry state, and resumes a database the expiry suspended. A database the user suspended stays suspended. |
| Suspension | Not stated for databases. | A user suspension does not pause the clock. |

**Once only.** Every stage (`warned`, `expired`, `final-warned`, `deleted`) is claimed by writing `bex.co/free-expiry: <stage>@<expiresAt>` with an optimistic-concurrency `Update` of the CR, then performed. A replica whose write conflicts skips the database, so a warning is mailed once and a delete runs once across bex-api replicas. The value names the `expiresAt` it belongs to, so a database whose clock restarts (a later change back to `free`) starts its stages again. Each stage writes an audit row (`postgres.FreeExpiry{Warned,Expired,FinalWarned,Deleted}`, caller `free-expiry-sweeper`).

**Rollout window.** Free databases created before this rule existed are not expired early: the clock's start is clamped to the rollout date `2026-10-27T00:00:00Z`, so none expires before 2026-11-26 or is deleted before 2026-12-10. The 7-day warning is the announcement.

## Alternatives considered

- **Operators** — Zalando (older Patroni/StatefulSet architecture), Crunchy PGO (pgBackRest, heavier, only wins at extreme backup scale), StackGres (AGPL + heavy), KubeDB (freemium). CNPG chosen; see §1.
- **Isolation model** — shared cluster + row-level (weakest; that's how the _control plane_ stores its own tenants, not tenant DBs) and database-per-tenant on a shared cluster (noisy neighbor, shared blast radius) both rejected in favor of **instance-per-tenant-DB** (matches the namespace compute model).
- **Attach DB to App (`App.spec.database`)** — rejected; a DB shouldn't die with one app or be un-shareable. Standalone `Database` is Render-faithful.
- **Per-DB LoadBalancer for the external endpoint** — rejected; a Hetzner LB per DB is costly and doesn't scale. One protocol-aware SNI proxy on a wildcard endpoint preserves the region-proxy shape while handling PostgreSQL's preamble and per-resource metering.

## Advanced: data protection, lifecycle, access (w1/m17)

Built on the same CNPG-is-the-executor principle — every advanced capability maps to a CNPG mechanism the operator projects and bex-api drives (three adapters: REST/GraphQL/MCP, see [ADR006-bex-api.md](ADR006-bex-api.md#managed-postgres-render-v1postgres-compatible)).

### Backups + point-in-time recovery

> Backup-bucket encryption (SSE-S3 via the plugin's `encryption: AES256` field) and write-only backup credentials are specified in [ADR050-encrypted-platform-backups.md](ADR050-encrypted-platform-backups.md) (Tier B), not here.

- **Durability is a plan axis** (`lego/types/tiers` `postgres[].backup`): Free is ephemeral (no backups, as on Render); `basic-*` opt in. When a backed-up plan runs and the operator's backup-store contract is configured (`BEX_DB_BACKUP_DESTINATION` / `BEX_DB_BACKUP_ENDPOINT` / `BEX_DB_BACKUP_S3_SECRET`), the controller loads `barman-cloud.cloudnative-pg.io` as the Cluster's sole WAL archiver and points it at the namespaced `bex-tenant-postgres` `ObjectStore`; the daily `ScheduledBackup` uses `method: plugin`. The ObjectStore owns the Wasabi/S3 destination, gzip policy, credential references, and `30d` retention without placing credential values in Git. The three environment variables must match it because logical-export and finalizer-purge Jobs consume those same non-secret coordinates directly; any unset value disables backups and recovery. WAL archiving is what makes PITR possible; the base backup pins the window. CNPG scopes each cluster's first backup generation through plugin parameter `serverName=<database>`; after a major upgrade the operator uses `<database>-pg<major>` because `pg_upgrade` changes PostgreSQL's system ID/timeline. One bucket therefore fans out safely to every database and major generation.
- **Logical exports are portable `pg_dump` artifacts**, separate from CNPG's physical PITR backups. bex-api appends an `exp-…` request to `Database.spec.exports`; the operator runs a resource-limited, version-compatible `pg_dump --format=directory`, packages `<timestamp>/<database>/` as Render's `.dir.tar.gz`, and uploads it beneath `<destination>/logical-exports/<database>/<export-id>/`. The operator reports `created` → `running` → `available|failed` in `Database.status.exports`. Available artifacts expire seven days after creation: an object-delete Job must succeed before the record becomes `expired`. An authorized list read (`can_view_sensitive`) mints a fresh S3-compatible URL for at most 15 minutes; URLs are never stored and dump bytes never enter bex-api. A list that returned at least one URL records one audit row, Render's `DownloadDatabaseBackupEvent` (w21/105, [ADR006](ADR006-bex-api.md) § Audit log), and GraphQL mints and records only for a query that selects `url`. Contract capture: [render-artifacts/postgres-exports.md](render-artifacts/postgres-exports.md).
- **`recovery-info`** reports whether recovery is available (`Status.BackupsEnabled`), the backup list, and the Barman Cloud plugin's authoritative restorable window. The window comes from the namespace's `ObjectStore/bex-tenant-postgres` at `status.serverRecoveryWindow[Database.status.backupServerName]`: `firstRecoverabilityPoint` is the earliest bound and `lastSuccessfulBackupTime` is the latest. Both are reported only when the pair is established; bex-api never synthesizes a “latest = now” point. A no-backup plan returns `{enabled:false}`, never an error; an ObjectStore or CNPG Backup read that fails (RBAC, CRD unavailable, transient) is an explicit API error, never an empty window or list — an empty result always means “verified none” (w6/m117).
- **`recover` always restores to a NEW `Database`** (never in place — matching Render): bex-api creates a Database with `spec.recovery{sourceDatabase, targetTime}`, which the controller bootstraps via CNPG `bootstrap.recovery` plus an `externalClusters[].plugin` reference carrying the shared ObjectStore name and the source's exact `serverName`. The source instance is untouched. Recovery requires both bounds of the source server's ObjectStore recovery window; without them the request is refused (400) before any billing gate or resource creation, so an unsubstantiated restore can never provision a paid instance that cannot bootstrap (w6/m117). The production plugin path recovered a pre-target marker, excluded a post-target marker, and cleaned up without residue in the [2026-07-28 PITR drill](drills/2026-07-28-barman-plugin-pitr.md). **The recovery stays inside the source's boundary (w4/356, 2026-10-19).** A recovery is the source's data, so it lands where the source sits. It joins the source's environment, inheriting its project and inbound-IP layer through the same resolver a create uses, or, with no environment, the source's project. It always copies the source's `public` flag and its own IP allow-list. Render documents the allow-list half: "the recovery instance _always_ copies the IP address allow list from the original instance" (render.com/docs/postgresql-backups, fetched 2026-10-19). A source environment that cannot be resolved refuses the recovery rather than landing it outside. Before this, a `can_create` caller could materialize a protected environment's database as a workspace-scoped instance with none of those controls. **The restore fits its data (w4/360).** The new instance's disk is floored at the source's storage high-water mark, and it carries the source's parameter overrides (minus the platform-managed names, which the platform sets for the restore itself), so an archive from a grown disk never restores into the plan's default volume. It passes the same admission check a create does, before the billing gate, so a plan that cannot hold the data (Free's fixed volume) is refused before anything is created. An inherited plan since retired from the catalog is not re-validated. HA, the pooler, read replicas and disk autoscaling change cost and stay an explicit choice.
- **The recovery window follows the workspace plan (w7/m453, 2026-11-16).** Render offers point-in-time recovery for the "Past 3 days" on Hobby and the "Past 7 days" on Pro or higher (render.com/docs/postgresql-backups and render.com/pricing, read 2026-11-16). bex applies the same window, `core.pitrRetention`, on every surface:
  - **The start.** The plan floor is now minus 3 days on Hobby, now minus 7 days on Pro, Scale and Enterprise, rounded up to the second. Where it cuts the ObjectStore's window, `recovery-info` starts at the newest base backup completed at or before the floor (CNPG `Backup` `status.stoppedAt`, or the ObjectStore's `lastSuccessfulBackupTime`), never before `firstRecoverabilityPoint`; with no such backup known it starts at the floor. That is Render's start, captured on 2026-11-17 ([render-artifacts/postgres-recovery-window.md](render-artifacts/postgres-recovery-window.md), w7/075): Render reports the first of the base backups it keeps for the window, 7 days 20 hours back on a Pro workspace, so the start can lie up to a day before the floor. A database younger than the window keeps its own first point. The latest bound stays `lastSuccessfulBackupTime`. This covers REST `startsAt`, GraphQL and MCP `earliestRecoveryTime`, and the dashboard picker. A workspace where no plan applies (no store, the default tenant) keeps the ObjectStore's window. GraphQL and MCP also return `retention { plan days upgradePlan upgradeDays }`, the hint the dashboard shows. REST keeps Render's two fields.
  - **No backfill on upgrade.** Render: "Upgrading from Hobby does not retroactively "backfill" your recovery window. Instead, your existing 3-day window extends to 7 days going forward." `store.UpdateTenantPlan` stores the old plan's floor in `tenants.pitr_visible_from` (migration 0290), next to the log floor, and the window takes the later of the two until Pro's own floor passes it, four days after the upgrade. A downgrade narrows the window at once, as the log floor does. Render's page does not say what a downgrade does.
  - **Refusals.** `recover` refuses a target before that start with `RECOVERY_TARGET_BEFORE_WINDOW` naming it. It refuses a target within ten minutes of now with `RECOVERY_TARGET_TOO_RECENT` and the latest allowed time (Render: "You can't restore to a time that's within ten minutes of the current time"). A target in the future is still `RECOVERY_TARGET_IN_FUTURE`. An empty target still means the latest point. All of these happen before any billing gate or `Database` create.
  - **Stopped backups.** If the last base backup is older than the plan floor (nightly backups stalled, or the database is suspended), that backup is the newest one at or before the floor, so the window starts there and stays `AVAILABLE`, and `recover` takes a target after it. Render does the same: a database suspended in August still answered `AVAILABLE` in November (w7/075). This replaces w7/m453's `BACKUP_NOT_READY` and refusal, which Render does not give. One difference remains open in w7/075: Render keeps a suspended database's window as it was at the suspension, and bex, which does not record when a database was suspended, counts the floor back from now.
  - **The stored retention stays `30d`.** The floor alone gives Render's behavior. The 23 days past the longest window are an operator margin: ADR031's tenant-Postgres policy and `scripts/restore-postgres.sh` restore from them. Wasabi bills a 90-day minimum storage duration ([ADR112](ADR112-object-storage.md)), so a shorter policy would save nothing on storage and would permanently delete that margin. `TestTenantBackupStoreKeepsTheLongestRecoveryWindow` reads the chart's `retentionPolicy` and fails if it is ever shorter than `core.LongestPITRRetention()`, so change the two together.
- **`export`** triggers/lists the logical artifacts above on Render's singular REST path; GraphQL and MCP expose the same lifecycle fields and authorization. The retired plural `/exports` REST path returns 404.

### Lifecycle (suspend / resume / restart)

Mirrors the compute and KeyValue lifecycle verbs, writing intent to the `Database` CR the operator converges (see [ADR007-restart-suspend-and-resume.md](ADR007-restart-suspend-and-resume.md)):

- **suspend / resume** → `spec.suspended`, mapped to CNPG **hibernation** (`cnpg.io/hibernation=on`/removed). Postgres can't scale-to-zero, but hibernation stops compute and keeps the PVC (data), credentials, and any external route, preserving the sleep=free promise; a suspended DB settles `Ready`/`Suspended` immediately rather than waiting on ready instances.
- **restart** → `spec.restartedAt` (verb-as-timestamp), stamped onto CNPG's `kubectl.kubernetes.io/restartedAt` annotation for a rolling restart of the primary.

### Readiness under load (w8/298)

A busy Postgres serves new connections slowly; it does not refuse them. CNPG's default readiness check runs `pg_isready`, which gives up after its own 3 s connect timeout (CNPG 1.30.1 `PgIsReady`, no `-t`). On a CPU-saturated 100m instance, starting the probe's backend took longer than that. The lone Pod went NotReady, so the `-rw` Service had no endpoint: every new connection was refused, and the database read `config_restart` while its running queries finished.

- **A single-instance Cluster** sets `spec.probes.readiness` to `type: query` with `timeoutSeconds: 30`. The query strategy connects from the instance manager and is bounded only by the kubelet's timeout. A stopped server still fails at once, because its socket refuses the connection.
- **Clusters with standbys** (HA or readers) keep CNPG's defaults: there, readiness picks which instances serve.
- **Rollout without restarts:** the strategy is read from the Cluster at each check, so it applies at once. The timeout is part of the instance Pod's spec, and CNPG applies a change to it by restarting the Pod. An existing Cluster therefore adopts the timeout only when its Pods roll anyway, under the same rule as the datastore priority class (`clusterPodsRoll`): a plan change, an image update, a restart, or hibernation. A restart counts because CNPG 1.30.1 deletes and recreates the Pod for it rather than restarting Postgres in place: only `PendingRestart` is an in-place rollout (`cluster_upgrade.go`).

### Major-version upgrades (w8/m12)

- `Database.spec.version` is desired intent; changing it upward updates CNPG's `Cluster.spec.imageName`. CNPG performs its offline in-place `pg_upgrade`, so every database instance is unavailable during the operation.
- `Database.status.currentVersion` comes from CNPG's `status.pgDataImageInfo.majorVersion`, not from desired spec. It remains the source version while `spec.version` is already the target, then advances once the upgraded cluster is healthy. CNPG's `Upgrading Postgres major version` phase maps to `Database.status.phase=Upgrading`; an upgrade failure maps to `Failed` with the CNPG condition message. The API maps those phases to `upgrading` and `unavailable`, never a stale `available` mid-upgrade. **Before and after CNPG's phase (w4/m215):** CNPG patches its upgrade phase only after resolving the new image, and the old major's instance stays healthy in between, so a known `spec.version` ahead of the recorded major also holds `Upgrading`. That interval used to read `available` and stop the dashboard's fast polling. A new major is recorded only once its cluster is healthy (or its upgrade failed, for the revert). Recording CNPG's target major before its instances were ready used to hide the change from the healthy pass: it took no post-upgrade base backup and re-pointed archiving at the source generation. The failed-upgrade revert runs first, so a reverted target never sticks at `Upgrading`. Empty desired versions and unobserved clusters keep provisioning semantics.

**Restart is not creation (w4/m137).** The controller reuses the `Provisioning` phase for a first provision and for every later restart (a manual restart, a resume, a CNPG instance recovering). It therefore records `Database.status.provisioned=true` on the first Ready (or suspended) settle and never clears it. The API maps a not-ready phase to `creating` only before that flag is set, and to Render's `config_restart` afterward. A `Ready` phase is `available` only while its Ready condition is true, not the suspended placeholder, and observed at the current generation. Otherwise the same `config_restart` covers a resume whose stale suspended Ready would have read `available` with nothing serving. The dashboard labels it **Restarting** and keeps polling. `upgrading` is **not** in Render's `databaseStatus` enum; it stays as recorded parity drift. Render's value for a user-initiated restart was not observed, so `config_restart` is the closest documented value (the alternative, `unavailable`, reads as a failure).

- One guarded backend verb fans out to REST `PATCH /v1/postgres/{id}` with a `version` field, GraphQL `updateDatabaseVersion`, and MCP `update_postgres(version:)`. Targets must be known versions, strictly newer than the observed version, and **16 or newer** (w4/308): CNPG 1.30's admission webhook rejects an in-place major upgrade to a lower target, so accepting 13→14/15 would leave the Database `Failed` on its old major. Creation still offers 13–18; the dashboard's upgrade picker applies the same floor. Errors are machine-readable: `POSTGRES_VERSION_UNKNOWN`, `POSTGRES_VERSION_NOT_NEWER`, `POSTGRES_UPGRADE_TARGET_UNSUPPORTED` (400, before any write, real or dry-run), `POSTGRES_VERSION_NOT_OBSERVED`, and `POSTGRES_UPGRADE_IN_PROGRESS`.
- A plan with the durability bit (`basic-*`) must have backup projection enabled **and** a completed CNPG `Backup` object in its current archive generation before the verb patches intent; otherwise it returns 409 `POSTGRES_UPGRADE_BACKUP_REQUIRED`. A stale backup from an older major cannot authorize another upgrade. Free is intentionally exempt because its contract has no physical backups.
- The image and new per-major Barman Cloud plugin `serverName` move together when an upgrade starts. Once CNPG reports the new major healthy, the operator creates a plugin-method on-demand base backup for that generation; recovery intent records the exact source `serverName`, so PITR never guesses across an incompatible `pg_upgrade` boundary.
- The dashboard's version row opens a target selector with only newer catalog versions, an explicit offline/downtime warning, and inline guard errors. The detail query polls through `upgrading` until the operator reports the new current version.
- Render comparison and the live CNPG 16→17/data-intact proof are captured in [render-artifacts/postgres-version-upgrade.md](render-artifacts/postgres-version-upgrade.md).
- **A logical-replication publisher's slots (w34/m543).** The verb reads a publisher's logical slots last, after every other check. From a 17 or later source, `pg_upgrade` carries the slots but fails the whole upgrade while one is invalidated or has not consumed all WAL, so bex refuses first with 409 `POSTGRES_UPGRADE_LOGICAL_SLOTS_BEHIND`, naming each slot and why. From a 13–16 source, `pg_upgrade` drops every slot without a word, so bex accepts and answers `upgradeNotice` naming the slots. A slot that cannot be read refuses with 503 `POSTGRES_UPGRADE_LOGICAL_SLOTS_UNREADABLE`. A database that does not publish is not read. Details: [§ Lifecycle › Major-version upgrades](#major-version-upgrades).

### Grow-only storage across plan changes (w2/m60)

Storage capacity is independent from compute-plan selection and is monotonic. On every reconcile, the operator projects the maximum of the selected plan floor, `spec.storageGB`, `status.allocatedStorageGB`, and the live CNPG Cluster storage request. `status.observedStorageGB` records which explicit intent produced the accepted high-water mark, so an unchanged legacy zero/below-plan value remains valid while a newly submitted lower value is rejected. A plan downgrade can reduce CPU/memory but can never render a smaller CNPG PVC request.

The Render-compatible REST update path, including the official CLI's `postgres update --disk-size-gb`, rejects a nonpositive or smaller explicit size with a named 400 before mutating the Database. Blueprint sync applies the same high-water rule. Reads return the effective accepted size from one shared `PostgresView`, so REST, GraphQL, MCP, the CLI, and dashboard do not show a stale plan floor while expansion is converging. Render documents the same separation: changing compute does not change storage, and storage [can be increased but not reduced](https://render.com/docs/postgresql-refresh); its PostgreSQL guide exposes the same [`diskSizeGB` increase-only field](https://render.com/docs/postgresql-creating-connecting).

This is deliberately separate from automatic growth below. Manual and plan-driven growth establish the same persisted high-water mark that disk autoscaling consumes; neither path can erase the other. Controller tests prove `5 GiB + plan downgrade -> 5 GiB`, explicit `10 GiB` growth, and a later shrink rejection that leaves the live CNPG request untouched.

### Render's storage sizes and 6-hour wait (w2/m317)

Render's storage contract ([creating & connecting § storage](https://render.com/docs/postgresql-creating-connecting)): a new database takes "1 GB or any multiple of 5 GB", an increase is "any multiple of 5 GB greater than the current storage capacity", and "after you increase a database's storage, you can't increase it again for 6 hours". bex applies all three on every surface:

- **Create:** an explicit `diskSizeGB` other than 1 or a multiple of 5 is a 400 `POSTGRES_STORAGE_STEP_INVALID`, on REST/GraphQL/MCP (`postgres.CheckNewDatabase`) and on a Blueprint database create. A restore keeps its source's size whatever it is, because recovery is not a caller-chosen size.
- **Increase:**
  - An off-step size is the same 400. It applies only to an increase, so an unchanged legacy size keeps syncing.
  - A second increase within 6 hours of the later of `app.bex.co/storage-increased-at` (stamped by bex-api and Blueprint sync when they apply a manual increase) and `app.bex.co/disk-autoscale-at` (the operator's autoscale stamp) is a 409 `POSTGRES_STORAGE_INCREASE_TOO_SOON`, whose params name `nextIncreaseAt`.
  - A dry run does not stamp. Blueprint reports both refusals as `diskSizeGB` field conflicts.
- The dashboard Storage edit (w2/m307) enforces the step client-side and shows the server's refusal as is.

### Disk autoscaling (w8/m14)

- `Database.spec.diskAutoscaling` is desired intent. When enabled, the operator samples the existing Prometheus `kubelet_volume_stats_{used,capacity}_bytes` series once a minute and uses the fullest CNPG instance PVC. It is independent of the optional control-plane database (`BEX_CP_DB_URI`); unset `BEX_PROM_URL` disables the loop without changing API round-trip behavior.
- Render's captured rule is applied exactly: at 90% full, grow the current `spec.storageGB` by 50%, round upward to the next 5 GB, cap at 16 TB, wait 12 hours before another increase, and never shrink. The last resize annotation is persisted atomically with the new desired size, preventing a stale kubelet sample or slow CNPG expansion from causing a second bump.
- Every resize emits a Kubernetes Event (`DiskAutoscaled`) and appends a bounded `status.diskResizeHistory` entry with timestamp, old/new size, and the triggering used/capacity sample. Render does not publish a notification contract; this is bex's explicit auditability extension.
- A Ready database whose Prometheus/PVC sample fails three consecutive one-minute reconciles emits one `Warning DiskAutoscalingSampleUnavailable` Event, visible in `kubectl describe database`. The debounce count lives in `app.bex.co/disk-autoscale-sample-failures`, survives manager restarts, resets on a successful sample, and does not accrue before the Database is Ready (so initial no-PVC noise stays quiet). The count caps at the threshold to prevent event spam during a sustained outage.
- The Render field asymmetry is preserved: `enableDiskAutoscaling` on REST, GraphQL, and MCP create inputs / REST PATCH; `diskAutoscalingEnabled` on every returned Postgres object. GraphQL `updateDatabaseDiskAutoscaling` and MCP `update_postgres(enableDiskAutoscaling:)` are thin adapters over the same guarded core mutation. The detail page places the toggle beside the disk chart and displays the current size and 16 TB cap.
- The 16,384 GB cap is sourced from the shared `lego/types/tiers/tiers.yaml` Postgres catalog for both the operator and backend MCP description; the dashboard's TypeScript mirror has a build test that reads and compares the same catalog field. Public evidence and the deliberate notification/status divergence are pinned in [render-artifacts/postgres-disk-autoscaling.md](render-artifacts/postgres-disk-autoscaling.md).
- Live CAPD/CNPG verification grew a threshold-crossing 1 GiB database to 5 GiB, observed the status audit entry and Kubernetes Event, and confirmed the PVC's requested and reported capacity converged after CSI filesystem expansion. The exact samples and mock-substrate setup are recorded in the capture above.

### Access & connection

- **Render REST create default (w2/038).** On `POST /v1/postgres`, omitted `ipAllowList` defaults to public intent and explicit unrestricted rules unless `public:false` overrides it; an explicit empty array instead creates a private database unless `public:true` overrides it. Explicit `null` for either `ipAllowList` or `public` is rejected by public API schema validation. Render documents [public access by default with `0.0.0.0/0`](https://render.com/docs/postgresql-creating-connecting#restricting-external-access). Bex stores that rule plus `::/0` to preserve its existing unrestricted IPv6 behavior, so default-create readback no longer looks blocked to the CLI. The [create state matrix](#postgres-create-access-intent-w2038) below is REST's; GraphQL, MCP and the dashboard resolve the same way (w4/553), apart from its `null` rows. Existing resources are not migrated. If public intent exists but the operator has not published `status.externalHost` (for example, `BEX_DB_DOMAIN` is unset), connection-info returns a named 503 before exposing credentials, so the official CLI never invokes local `psql` with an empty target.
- **IP allowlist** (`spec.ipAllowList`) gates the **external** SNI endpoint only: every metered proxy replica watches the Database CR and checks the original source address from the trusted edge PROXY header (or the socket source on a direct connection) before dialing a backend. The environment-projected allowlist is an additional AND layer. An explicit empty allowlist update disables external access by setting `spec.public=false`; a nonempty update sets it true, and omission keeps intent unchanged. An explicit `public` field in the same update wins, so `public:true` with `[]` deliberately retains Bex's unrestricted resource layer, subject to environment rules. The proxy's empty-layer-as-unrestricted predicate stays unchanged for absent environment rules and existing public/empty CRs; those resources are not force-migrated. Internal `-rw` access is never gated. The [shared datastore update state matrix](ADR021-keyvalue-management.md#datastore-allowlist-update-intent-w2m166) applies to REST PATCH, dedicated PUT, GraphQL, MCP, the dashboard, and Blueprint datastore writes; primary, pooler, and read-replica external routes all follow public intent. This corrects the prior sticky-public behavior to match Render's [clear-to-disable contract](https://render.com/docs/postgresql-creating-connecting#restricting-external-access); the create omission defaults above are retained. Entries are `{cidr, description}` pairs (w4/m24): the description is operator-facing metadata that persists on the CR and never affects enforcement. Pre-m24 bare-string CR/store entries were normalized fleet-wide and are rejected by both admission and structured REST decoding. The separately named GraphQL/MCP string-list compatibility arguments remain supported; adapters lift them explicitly into structured entries.
- **Any-IP rule covers IPv6 (w8/140).** Render's "allow any IP" rule `0.0.0.0/0` also admits IPv6 sources at the datastore SNI front doors (w8/140): `sniproxy.ParseAllowList` treats a rule that masks to `0.0.0.0/0` as `0.0.0.0/0` plus `::/0` in either layer. Render's datastore endpoints are IPv4-only, so there the rule admits everyone; ours also publish AAAA and dual-stack clients try IPv6 first. The equivalence is enforcement-only (the saved rule and every readback stay as authored), and narrower IPv4 rules are not widened ([w9/m164](../.pm/w9/done/m164/README.md)).
- **Create-time allowlist validation (w8/m16).** REST `ipAllowList`, GraphQL `ipAllowList`/`ipAllowListEntries`, and MCP `ipAllowList`/`ipAllowListEntries` all feed the same `CreatePostgresRequest.IPAllowList` validation and persistence path, after each adapter resolves its create defaults. The object-form argument wins when both are present, preserving descriptions; invalid CIDRs fail before any Database is created.

- **Blueprint access intent and export (w2/m166).** A sync that omits `ipAllowList` preserves the saved list and public intent; explicit `[]` disables external access and a nonempty list enables matching sources. Explicit lists have the same effect at Blueprint create, while omission on a new Postgres is Render's documented default — public with `0.0.0.0/0` and `::/0`, credentials still required (w8/157; Key Value requires the field, so its `[]` stays private). `GenerateBlueprint` / `generateDatabaseEntry` emit `[]` for a private database, both `0.0.0.0/0` and `::/0` for a public database with no rules, or the existing rules and descriptions for a restricted public database. Render YAML cannot encode inactive saved rules separately from publication. Export/reapply therefore preserves effective resource access while normalizing those first two representations; the initial plan reports the change and subsequent plans are no-ops. Environment restrictions remain separate. See the [shared Blueprint state and export contract](ADR021-keyvalue-management.md#datastore-allowlist-update-intent-w2m166).
- **PgBouncer pooler** (`spec.pooler`) projects a CNPG `Pooler` (transaction mode) whose `<id>-pooler` Service backs the pooled connection strings `connection-info` now returns (internal always; external when `public`, resolved by the proxy from `<id>-pool.<domain>`). This fills the previously-stubbed `internalConnectionPoolString`/`externalConnectionPoolString`. **Port 6432, as on Render (w2/m316, 2026-11-10).** Render's pooled URLs "use PgBouncer's port 6432 instead of the standard PostgreSQL port 5432" ([connection pooling](https://render.com/docs/postgresql-connection-pooling)), internal and external alike. bex's internal pooled string and the operator's `<id>-pooler-app` Secret `uri` (behind Blueprint `connectionPoolString`) name 6432. The Pooler's `serviceTemplate` adds a `pgbouncer-pooled` ServicePort onto PgBouncer's named container port. CNPG keeps its default `pgbouncer`/5432 port, because it drops that only for a template port named `pgbouncer`, so the Service serves both. PgBouncer still listens on container port 5432, so NetworkPolicies are unchanged. **The external pooled string stays on 5432 (signed-off difference, user decision 2026-11-10).** bex marks the pooled endpoint by host (`<id>-pool.<domain>`, routed by SNI), so the external URL works on 5432. The edge load balancer (Hetzner `lb11`) is also at its five-listener limit (22, 80, 443, 5432, 6379): a 6432 listener's apply was refused (`resource_limit_exceeded`). Serving it would need a larger LB type (+€14/month) and still would not reproduce Render's same-host, port-selects-pooler rule, so it was not pursued (ADR018). Every pooled URI handed out on 5432 keeps connecting.
- **Postgres users** (`spec.users`) are additional managed PostgreSQL login roles projected to CNPG `spec.managed.roles`; bex-api generates each credential issuance into a distinct per-user basic-auth Secret referenced by CNPG's `passwordSecret` and reveals its password once on creation — never logged. Delete/re-create is an explicit rotation: the old Secret is removed before revocation commits, same-name recreation clears the deletion tombstone, and concurrent or abandoned issuance attempts cannot replace the referenced credential. **Deletion retires, it does not drop (w4/m179):** a deleted additional role stays in `spec.deletedUsers` and the operator projects it `ensure: present, login: false, disablePassword: true`, so CNPG sets it `NOLOGIN` with a `NULL` password. CNPG executes `ensure: absent` as a bare `DROP ROLE`, which PostgreSQL refuses while any grant or owned object references the role. That refusal left a deleted login authenticating and reading data after the API reported success. Retirement never depends on the role's objects, keeps tenant tables and grants intact, and may leave the role visible in `pg_roles`; the native user/credential lists omit it. Every delete surface (REST `/users/{user}` and `/credentials/{user}`, GraphQL `deleteDatabaseUser`, MCP `delete_postgres_user`) reports **accepted** revocation intent, applied on the next reconcile, not an observed SQL change. Retirement blocks new authentication; it does not terminate already-established sessions. Verified against real CNPG 1.27 (2026-10-08): the old shape reproduced `cannotReconcile` with a fresh login still reading the granted table; the new shape refused fresh logins, kept the grant and an owned table, and same-name reissue accepted the new password and refused the old one (`scripts/pg-role-retirement-check.sh`). The immutable effective owner role (`spec.databaseUser` or the stable-id-derived default) stays CNPG bootstrap-managed.
- **Credential rotation (w5/m265).** Render's model is that every credential added through `POST /postgres/{id}/credentials` becomes the database's default ([render.com/docs/postgresql-credentials](https://render.com/docs/postgresql-credentials)). bex records it as a `spec.users` entry with `ownerPrivileges: true` and points `spec.defaultUser` at it. Such a credential is projected `inRoles: [<owner>, every retired login, every earlier owner-privileged credential]`: whichever credential ran a migration owns its tables, so the next default must keep reaching them after that credential is deleted, and joining only earlier ones keeps the membership graph acyclic. The operator then builds `<id>-default-app` — CNPG's `-app` key set with the default's username, password and URIs; a key it does not know is dropped if it carries the owner's password — and moves `status.secretName` to it once that Secret is current, never back to the owner mid-rotation. Connection info, the SQL query and Insights paths, logical exports, the pooler Secret and Blueprint `fromDatabase` references (re-pointed on the next sync) all read `status.secretName`. The default cannot be deleted. "Deleting" the original owner adds it to `spec.deletedUsers`, which retires the owner like any login (`login: false`, `disablePassword: true`) while it keeps owning its objects and its `pg_monitor` membership; it is then omitted from the credential list. Retiring the owner is refused as a retryable conflict until `status.secretName` has moved to the new default, so consumers are never left on a retired login. Native auxiliary users (`POST …/users`) keep `ownerPrivileges` off and their one-time password. Verified on real CNPG 1.30.1 with `scripts/pg-credential-rotation-check.sh`.

### Postgres create access intent (w2/038)

The public REST API validates the body before the adapter resolves public intent and fills an omitted list. These are the values persisted and returned by valid creates; dry runs return the same resolved intent without creating a Database:

| REST `ipAllowList` | Explicit `public` | Resulting `public` | Stored/readback rules |
| --- | --- | --- | --- |
| Omitted | Omitted or `true` | `true` | `0.0.0.0/0` and `::/0`, with empty descriptions |
| `null` | Any | Rejected with HTTP 400 | No Database created |
| Any | `null` | Rejected with HTTP 400 | No Database created |
| `[]` | Omitted | `false` | `[]` |
| Nonempty | Omitted | `true` | Supplied entries and descriptions |
| Omitted or an array | `false` | `false` | Supplied entries stored, inactive; reads `[]` |
| `[]` | `true` | `true` | `[]` stored, an intentional unrestricted resource layer; reads `0.0.0.0/0` and `::/0` |
| Nonempty | `true` | `true` | Supplied entries and descriptions |

The [embedded public schema](../lego/backend/internal/api/openapi/render-public-api-1.json) defines `postgresPOSTInput.ipAllowList` as an optional, non-nullable array. The composed API's [request validator](../lego/backend/internal/api/render_openapi.go) rejects `null` before calling the Postgres adapter. The Bex `public` extension is likewise a non-nullable boolean: omit it or send `true`/`false`. Direct-fragment tests bypass that validator, so their Go decoder treats `null` like omission for these fields; this internal behavior is not accepted public API input.

The rules gate external connections after reconciliation, with environment restrictions still applied as an independent AND layer. Internal access is unchanged. The IPv6 rule preserves Bex's prior behavior; it is not an assertion that Render's documented default contains that second entry. Existing public/empty databases retain their saved representation, and [m166's update semantics](ADR021-keyvalue-management.md#datastore-allowlist-update-intent-w2m166) remain unchanged.

**Reads report effective access (w4/m315).** Render has no separate public toggle, and its clients read an empty list as externally blocked. Every read therefore reports what the external endpoint admits, by the rule the Blueprint export already used (`core.EffectiveAllowList`): a public database with no saved rules reads `0.0.0.0/0` and `::/0` with empty descriptions, a private database reads `[]` whatever inactive rules it keeps, and any other database reads its saved rules. This covers REST get, list, `PATCH` responses and `GET …/ip-allow-list`, GraphQL `database`/`databaseIpAllowList`, MCP `get_postgres`/`get_postgres_ip_allow_list`, the dashboard Access control panel and the Blueprint export. Writes are unchanged, so writing back what was read keeps access as it is. Saved data is not migrated.

**Native creates resolve the same way (w4/553).** GraphQL `createDatabase`, MCP `create_postgres` and the dashboard resolve an omitted `public` by the REST rule (`postgres.CreateExposure`), so the matrix above applies to them too. An omitted flag publishes unless the list is explicitly empty, and a published create that sends no list saves `0.0.0.0/0` and `::/0`; explicit `public:false` stays private. Their flat `ipAllowList` and description-carrying `ipAllowListEntries` forms both count as the list. They have no `null` rejection: GraphQL drops a `null` variable and MCP decodes `null` as omitted, so either reads as omission. The dashboard's Public access switch starts on; switching it off creates a private database. This replaces the earlier private-by-omission rule for native creates, which predated the Render-parity-first decision. Direct CRs keep the CRD's `public:false` default. Blueprint Postgres creates already followed Render (w8/157), and explicit empty/nonempty lists follow the [Blueprint contract](ADR021-keyvalue-management.md#datastore-allowlist-update-intent-w2m166). Key Value keeps its private default, which is Render's (ADR021).

**Pinned CLI implications.** At Render CLI v2.27.0 (`a764810a768202704e7206eb7b87a47211fcd98e`), [`BuildCreateRequest`](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/postgres/create.go#L123) sets the allowlist only for nonempty input: both nil and empty CLI input omit the JSON key. An explicit REST `[]` is therefore distinct from the ordinary CLI create. The pinned [text renderer](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/text/ipallowlist.go#L17) describes an empty list as externally blocked; its [`psql`/`pgcli` guard](https://github.com/render-oss/cli/blob/a764810a768202704e7206eb7b87a47211fcd98e/pkg/tui/views/psql.go#L195) checks whether the detected client IP matches a rule, and skips that check if IP discovery fails. The CLI does not understand Bex's separate `public` override; since w4/m315 the public/empty states read as the unrestricted pair, so it no longer describes them as blocked. Default-create rules repair the same contradiction at create time; they do not prove endpoint readiness, TLS trust or successful SQL connectivity.

### Parameter overrides: retired, two read-only views remain (w6/m133 → w2/066)

`Database.spec.parameters` is the tenant's **declared** override set. The operator merges it straight on top of its own CNPG parameter map, so a tenant key of the same name wins and nothing downstream re-asserts the platform's value.

**Retired to match Render (2026-11-04, user decision D2=A, w2/066).** Render's 2026-11-02 OpenAPI dropped `parameterOverrides` from Postgres create/update/detail and the `postgresParameterOverrides` schema, and render.com documents no customer-editable server parameters. bex followed: REST `POST`/`PATCH /v1/postgres` and MCP `update_postgres` refuse the field by name (400, `{}` and dry-run included) with guidance toward standard SQL session defaults — `ALTER DATABASE <name> SET <parameter> = <value>` or `ALTER ROLE <role> SET …`, which the database owner can run over a regular connection or from the dashboard SQL console (MCP `query_render_postgres` is read-only). The bex-only `PUT /v1/postgres/{id}/parameter-overrides`, GraphQL `setDatabaseParameterOverrides`, and the dashboard editor are removed, and the Postgres object no longer carries `parameterOverrides`. Existing `spec.parameters` are deliberately left in place: the operator keeps applying them (zero disruption), except `max_connections`, which is always the plan's ([§ Server connection limit](#server-connection-limit-w6134-2026-11-17)), and recovery still carries a source's set minus the platform-owned names (`tenantParameters` filters through `operatorManagedParameterNames`, w4/360).

**Two read-only views remain.**

|  | source | contains |
| --- | --- | --- |
| **declared** | `Database.spec.parameters` | what this database set before the retirement — empty for almost every database |
| **observed** | `pg_settings` where `source <> 'default'` | the whole effective configuration, ~48 rows on a fresh free database, mostly the operator's |

The declared set is readable on all three surfaces (`GET /v1/postgres/{id}/parameters`, GraphQL `databaseParameterSpec`, MCP `list_postgres_parameters`); the dashboard shows it read-only, and only when a database declares something. The observed view is `GET /v1/postgres/{id}/parameter-overrides`, GraphQL `databaseParameterOverrides`, MCP `list_postgres_parameter_overrides`. Before w6/m133 the declared set had no read at all, and the editor seeded from the observed view wrote the operator's ~48 rows in as tenant config on a single save; the platform-owned name table (`operatorManagedParameters`: WAL archival and recovery, TLS material, replication/HA/pod control, log shipping, `allow_alter_system`, `pg_stat_statements.track`, the extension allowlist) dates from that fix and now serves recovery.

### Declared parameter observations (w4/m132)

The declared parameter list now includes `observationStatus`, nullable `observedSetting`, and nullable `observedUnit` on REST, GraphQL and MCP. The dashboard's read-only declared-parameter table displays these beside the declared values. The diagnostic reads the same non-default `pg_settings` rows as the existing observed-configuration endpoint:

- `observed`: a row with this name is present; its current value and unit are shown. Names match case-insensitively, as in PostgreSQL itself, so a declared `timezone` is corroborated by the runtime's `TimeZone`; the declaration keeps its own spelling (w4/317). This does **not** assert that the requested value was applied.
- `not_observed`: the name is absent from that non-default view. The override may still be pending or may be invalid; it is not confirmed as applied.
- `unavailable`: runtime observation failed. The declared value stays readable so users can inspect and repair configuration during a database outage.

Declared names and values pass through to Postgres as they were set before the w2/066 retirement. This diagnostic deliberately reports runtime evidence instead of implementing another Postgres parameter validator. For example, declared `work_mem: 8MB` can correctly appear as observed `8192` with unit `kB`; raw string inequality is not a failed-application signal. A previous non-default value can also remain visible after an invalid write. The UI does not label either case “applied”. The dashboard refreshes observations every 15 seconds while visible. Empty declared sets do not query the runtime. The diagnostic is a point-in-time read, not a reconciliation acknowledgment or a guarantee of later health.

[PostgreSQL documents](https://www.postgresql.org/docs/17/view-pg-settings.html) `setting` as the current value and `unit` as its implicit unit. Render no longer exposes `parameterOverrides` (w2/066); these per-entry observations are a bex extension. Key Value's fixed policy/persistence enums remain strictly validated; the Postgres setting catalogue is version- and extension-dependent.

### pgvector in every application database (w8/m84)

Render lists pgvector among its PostgreSQL 13+ extensions under the SQL name `vector`; the CloudNativePG images bex pins for every major (13–18) package it (0.8.1 on 13, 0.8.6 on 18), but `CREATE EXTENSION vector` needs a superuser, so an ordinary embedding migration's `CREATE EXTENSION IF NOT EXISTS vector` failed for the application owner with `permission denied`. Every reconcile now applies an owned `postgresql.cnpg.io/v1` **Database** child, `<db>-app` (distinct from bex's own `app.bex.co` Database), that adopts the application database — the default or custom name and owner a create or restore (which copies the source's) wrote, never a second database — with `extensions: [{name: vector, ensure: present}]`, `ensure: present` and `databaseReclaimPolicy: retain`. CNPG installs vector as the superuser in the default schema, so the migration becomes a no-op and the owner can use the type, its operators and its indexes (HNSW verified); existing databases get it on their next reconcile. No version is pinned, so CNPG never alters an installed extension, and withdrawing the child keeps the database and its rows. CNPG's verdict projects onto the Database's `ExtensionsReady` condition (`Pending` / `Applied` / `ApplyFailed` with CNPG's message, read whatever generation it names because CNPG advances `observedGeneration` only on success); a suspended database keeps its last verdict. The child is optional to serving: a write error is `ApplyError` on that condition and the rest of the reconcile carries on, and a database PostgreSQL itself owns (a legacy `template1`, w4/m170), which CNPG's Database CRD refuses, gets no child and `ReservedDatabaseName`. pg_stat_statements keeps its own management (below), and other extensions are untouched. Policy difference from Render: vector is pre-installed rather than created on demand by a bare `CREATE EXTENSION`, which an application role still cannot run for other superuser-only extensions. Verified on CloudNativePG 1.30.0 with every pinned major by `TestApplicationDatabaseVectorOnCNPG` (opt-in, `BEX_CNPG_KUBECONFIG`): refused before, a no-op after, real vector values/distance/HNSW, hstore and pg_stat_statements beside it, rows retained when the child is deleted and unchanged when it is reapplied, and a child naming a missing owner role reported as CNPG's refusal. A one-off CNPG in-place major upgrade (PG17 → PG18) with vector, rows and an HNSW index kept the extension (0.8.6), the rows and the nearest-neighbour answer, with the child still applied.

**First Available includes vector (w4/m223).** The CNPG Database child applies seconds after the cluster turns healthy, so a new database used to report its first `Ready`/`available` 8–18 s before vector was installed, and a migration run at that moment failed. A database that has never served now stays `Provisioning` (`creating`, Ready reason `InitializingExtensions`) until `ExtensionsReady` is true for the current generation; an initial `ApplyFailed`/`ApplyError` is `Failed` with Ready reason `ExtensionsFailed` (`unavailable`, a fixed sentence and translated code) and is retried. Once `status.provisioned` is set, the child is optional again: a later extension or backfill problem only degrades `ExtensionsReady`. The PostgreSQL-owned database CNPG cannot manage keeps its no-extensions treatment, and suspending a never-served database no longer sets `provisioned`, so its first `Ready` after resume still waits for vector.

### Legacy query-insights convergence (w8/m16)

Every reconcile projects `pg_stat_statements.track=all` plus CNPG's dedicated `shared_preload_libraries: [pg_stat_statements]`, including onto clusters created before the insights surface. CloudNativePG recognizes the `pg_stat_statements.*` parameter as its managed-extension switch: it performs the required rolling restart for preload changes and runs `CREATE EXTENSION IF NOT EXISTS pg_stat_statements` in each connectable database. The operator does not launch a competing SQL Job. A projection test starts from a legacy CNPG spec with neither setting, proves one reconcile adds both, and proves the next reconcile is byte-identical (no restart churn). Single-instance plans have a brief interruption during the one-time CNPG restart; HA plans roll through replicas.

Production-equivalent proof on 2026-07-16 used a disposable `dev-8-m16/m16-pgstat-proof` CNPG cluster created with the old spec: `pg_extension` initially returned zero `pg_stat_statements` rows. Creating the matching bex `Database` caused an ordinary reconcile to add `track=all` and the preload library; CNPG rolled the one instance, created the extension, returned the Database to `Ready`, and `pg_stat_statements` contained 30 query rows. The Database and proof namespace were then deleted successfully.

### Lock waits are logged (w7/m430)

Every reconcile projects `log_lock_waits=on` beside `pg_stat_statements.track=all`, under the tenant's legacy `spec.parameters`, so a database that declared its own value keeps it (`TestClusterSpecLogsLockWaits`). It is the source of the Metrics page's Lock-Delayed Queries graph ([ADR010 § Database activity and disk graphs](ADR010-observability.md#database-activity-and-disk-graphs-w7m430-2026-11-16)). The setting is reloadable: on CNPG 1.30.1 with PostgreSQL 18.4 an existing cluster adopted it with no restart (same postmaster start time and pod, restart count 0), checked on the local CAPD cluster on 2026-11-16.

With it on, a session that waits longer than `deadlock_timeout` (one second unless a legacy parameter changed it) logs one `LOG` line then, `process N still waiting for <lock> on <object> after N ms` with the holding and waiting pids, and a second when the lock is granted, `process N acquired <lock> on <object> after N ms`. A wait that ends in a deadlock or a cancel logs the deadlock or cancel error instead. Neither line carries statement text where bex stores or shows it: CNPG's JSON record adds the statement (`query`) and the tuple being updated (`context`), but the log shipper and the direct pod reads keep only the time, pid, severity, message, detail and hint (both proven on these lines by `lego/backend/internal/logs/testdata/tenant-log-lines.json`). The lines are ordinary entries in the database's Logs tab and count toward the tenant's log volume like any other; a database with no lock contention writes none.

### Insights visibility: the owner holds `pg_monitor` (w4/m115)

Loading `pg_stat_statements` is not enough to make Insights readable. PostgreSQL masks `pg_stat_activity.query` and `pg_stat_statements.query` as the literal `<insufficient privilege>` for every backend owned by a _different_ role unless the reader holds `pg_monitor` (or is superuser). The insights path dials the tenant database as the database **owner** — the unprivileged app user from the CNPG `<cluster>-app` Secret's `uri` — so on 2026-09-19 a live database with recent SQL-console activity rendered 9 process rows and 25 top-query rows with all 34 Query cells masked, while Storage, Table scans and Parameters on the same page were fine.

**Decision: the operator projects the database owner into CNPG `spec.managed.roles` as a member of `pg_monitor`.** `pg_monitor` is a read-only predefined role — it widens what the owner can _see_ in the statistics views and confers no DDL/DML power — and the insights connection keeps its own envelope regardless (`default_transaction_read_only=on` plus the statement timeout pinned at session startup, asserted by test). Because it is declarative and re-projected on every reconcile, it converges on **existing** databases with no separate backfill pass.

Two deliberate details. The owner role carries **no `passwordSecret`**: CNPG only assigns a NULL password to roles it _creates_ without one, and the owner always already exists (`bootstrap.initdb` creates it, or a restored base backup carries it), so tenant credentials are untouched — whereas naming the `-app` Secret would make the projection depend on a Secret the recovery bootstrap does not always produce. And because CNPG revokes memberships not listed in `inRoles`, the owner's role memberships are bex-owned from here on; a membership granted out of band inside the database will be revoked at the next reconcile.

Honest degradation is the second half. `<insufficient privilege>` is never republished as query text: the API blanks the field and sets `masked: true` on the process/top-query object (REST, GraphQL and MCP all carry it), and the dashboard renders a "Hidden" cell plus one per-section explanation, keeping unmasked rows and every real statistic beside them visible. The dashboard also still treats the bare literal as masked, so an older bex-api cannot leak it either.

### Additional databases: the default users hold `CREATEDB` (w8/m155)

Render: "You can create additional databases in your Render Postgres instance", by running `CREATE DATABASE <name>` in a psql session, and "Use your instance's same internal and external URLs to connect, except substitute your new database's name as the final component" ([render.com/docs/postgresql-creating-connecting § Adding multiple databases to a single instance](https://render.com/docs/postgresql-creating-connecting), read 2026-11-11; no plan restriction is stated). On bex the statement answered `ERROR: permission denied to create database` on every plan: `managedRoles` projected no `createdb`, a managed role's omitted attribute is false, and CloudNativePG reverts a manual `ALTER ROLE`.

**Decision: the operator projects `createdb: true` onto the database's default users.** The role attributes are:

| Role | `LOGIN` | `CREATEDB` | `CREATEROLE` | `SUPERUSER` |
| --- | --- | --- | --- | --- |
| The owner (`bootstrap.initdb`'s user, the first default) | yes | yes | no | no |
| A default credential (`POST /postgres/{id}/credentials`, `OwnerPrivileges`) | yes | yes | no | no |
| An auxiliary user (`POST …/users`), "granted nothing" by design | yes | no | no | no |
| A retired user, the tombstoned owner included | no | no | no | no |

- A role attribute is not inherited through membership, so each default credential carries `createdb` itself; joining the owner would not give it.
- A retired login is no longer a default user, so the attribute is withdrawn with its login. A database it created stays reachable: later defaults are members of every retired login.
- The projection is declarative, so existing and restored databases gain the attribute at their next reconcile. A spike on kind with CloudNativePG 1.30.1 (2026-11-11) showed `rolcreatedb` change within two seconds of the `spec.managed.roles` edit, with the postmaster start time and the pod unchanged and a session opened before the edit still running; withdrawing it works the same way.
- Tenant isolation is unaffected: each instance is its own CloudNativePG cluster, and `CREATEDB` grants nothing outside it. Storage metering, the free plan's storage limit, physical backups, point-in-time recovery, suspend and resume are cluster-wide and cover a second database.
- With `CREATEDB` the owner can also rename its primary database (`ALTER DATABASE … RENAME` needs the attribute). bex's connection strings, exports and Insights name the primary database, so they fail until it is renamed back. This is self-inflicted and reversible, and Render's default user has the same power.

**`CREATE USER` stays refused; an open divergence, not signed off (w8/257, re-examined 2026-11-11).** Render's credentials page says "Users created directly with the `CREATE USER` command are _not_ managed by Render", which implies its default user can create roles; no page lists the user's attributes. bex refuses the statement on every version, and users are added through bex. Giving the default users `CREATEROLE` was built and withdrawn before it shipped, for two reasons.

- **PostgreSQL 16 and later: CloudNativePG takes the created role back.** PostgreSQL makes a role's creator an `ADMIN`-only member of it; that membership is what lets the creator alter, drop and grant the role. CloudNativePG's role sync counts every membership of a managed role and revokes each one not listed in `inRoles` (`internal/management/controller/roles/postgres.go` in 1.30.1, the pinned version; the rule this section's `inRoles` projection already relies on). Reproduced on PostgreSQL 16 with the sync's own statement: after `REVOKE <role> FROM <owner>` the owner's `ALTER ROLE … PASSWORD`, `DROP ROLE` and `GRANT <role> TO …` all answer `permission denied`, and nobody but a superuser can remove the role. Once the owner has granted the role onward, the `REVOKE` itself fails with `dependent privileges exist`, and that role's membership sync fails from then on. Upstream: [cloudnative-pg#11448](https://github.com/cloudnative-pg/cloudnative-pg/issues/11448) (open).
- **PostgreSQL 13, 14 and 15: it is not safe.** Before 16 a role with `CREATEROLE` can alter any non-superuser role and grant itself `pg_execute_server_program`, `pg_read_server_files` and `pg_write_server_files`: programs and files in the database pod, which holds the instance's server keys and replication certificate and which no tenant can reach today.

When it is granted, the version that counts is the major the cluster runs (`status.currentVersion`), not the one requested: during an upgrade from 15 it stays 15 until the upgraded cluster is healthy. The ways forward (wait for the upstream fix, carry a patched instance manager, or sign the divergence off) are w8/257's. **What a second database is not covered by (w8/258, 2026-11-11).** A logical export dumps the instance's primary database (`databaseName`) only, and says so: the dashboard's Recovery panel and the MCP export tools name the database an export contains. Every surface shows one `databaseName`. Continuous backups and point-in-time recovery cover the whole instance, every database in it. **Decided (w8/278, 2026-11-12):** the export stays the primary database, as Render's does. Render's dashboard export is a `.dir.tar.gz`, PostgreSQL's directory format, which `pg_dump` writes for one database (`pg_dumpall` writes plain SQL only), and its [backup docs](https://render.com/docs/postgresql-backups) ("Exporting with `pg_dump`") tell a user with several databases to repeat `pg_dump` for each one or use `pg_dumpall`. Insights connects to the primary database: **Processes** (`pg_stat_activity`) and **Top queries** (`pg_stat_statements`) are instance-wide views, so they list every database's backends and statements; **Storage**, **Table sizes** and **Table scans** read the primary database only (`current_database()`, `pg_tables`, `pg_stat_user_tables`). Render's Top Queries tab is on the database's Metrics page and says nothing about a second database.

### Logical replication (w34/m541)

Render: "Render Postgres databases do not enable logical replication by default." The prerequisites are "Your workspace must be on a **Pro** plan or higher" and "Your database must have at least 10 GB of storage". Enabling is not self-service: "To enable logical replication, please reach out to our support team in the Render Dashboard", naming each database's `dpg-` id, the role subscribers will use (Render recommends "a dedicated read-only user for this purpose"), the schemas subscribers read, and whether to publish all tables. "The command `CREATE PUBLICATION [name] FOR ALL TABLES` requires superuser privileges and must be executed by our support team", while "Commands of the form `CREATE PUBLICATION [name] FOR TABLE…` can be executed by you", and subscribers "do not need to be Render-managed" ([render.com/docs/postgresql-logical-replication](https://render.com/docs/postgresql-logical-replication), read 2026-11-20). Render's pinned OpenAPI has no logical-replication field.

**bex before w34/m541 (checked 2026-11-21 on a PostgreSQL 18 publisher shaped like a bex tenant: a non-superuser owner, `wal_level=logical`, TLS; the shared mock cluster could not run, see the milestone):** `SHOW wal_level` reads `logical`, CloudNativePG's default; the default user's `CREATE PUBLICATION mine FOR TABLE public.orders` succeeds and its `FOR ALL TABLES` answers `must be superuser to create FOR ALL TABLES publication`; an external PostgreSQL 18 subscriber's `CREATE SUBSCRIPTION … PUBLICATION mine` as the default user is refused with `permission denied to start WAL sender` (DETAIL `Only roles with the REPLICATION attribute may start a WAL sender process.`). PostgreSQL 15 and older word the refusal `must be superuser or replication role to start walsender`; both are SQLSTATE 42501. No bex role holds `REPLICATION`, and `max_slot_wal_keep_size` reads `-1`.

**Decision: bex's operators play Render's support team.** One verb on bex-api's cluster-internal `:8091` listener, behind the control-plane bearer like the fleet rebuild, never on the public `:8090` mux: `/api postgres-logical-replication enable --database dpg-… --role <credential> --schema <name>… [--all-tables]` and `… disable --database dpg-…` inside the bex-api pod ([runbook](runbooks/postgres-logical-replication.md)). No REST, GraphQL or MCP field exists, as on Render. How a workspace asks is [w34/002](../.pm/w34/002.md); this decision does not wait on it.

- **Prerequisites, each refused by name before any write:** a workspace below Pro, or whose plan cannot be read, is `LOGICAL_REPLICATION_PLAN_REQUIRED`; a free database `LOGICAL_REPLICATION_FREE_PLAN`; less than 10 GB of effective storage (`tiers.PostgresLogicalReplicationMinStorageGB`, the larger of the plan's, the requested and the allocated size) `LOGICAL_REPLICATION_STORAGE_TOO_SMALL`; a role that is not a live credential of the database `LOGICAL_REPLICATION_ROLE_UNKNOWN`; a schema the database does not have `LOGICAL_REPLICATION_SCHEMA_UNKNOWN`; a suspended, deleting or unavailable database `LOGICAL_REPLICATION_DATABASE_UNAVAILABLE`; an existing publication named `bex_all_tables` that is not `FOR ALL TABLES` `LOGICAL_REPLICATION_PUBLICATION_NAME_IN_USE` (CloudNativePG would adopt the user's publication and drop it on disable).
- **The intent is `Database.spec.logicalReplication`** (`publisherRole`, `schemas`, `allTables`). Absent, the CR and every projection are what they were.
- **The publisher role gets `REPLICATION`, and no other role.** Any live credential qualifies: the owner, a default credential or an auxiliary user from `POST …/users`, which is Render's recommended dedicated reader. The owner needs no special case: it is already projected onto `spec.managed.roles` (§ Additional databases), so the operator adds CloudNativePG's `replication: true` to that one entry. A retired login never gets it. Removing the field, or naming another role, takes it back off, because the projection is declarative.
- **`FOR ALL TABLES` is a CloudNativePG `Publication`.** The operator declares `<id>-all-tables`, publication `bex_all_tables` in the primary database, reclaim policy `delete`, owned by the Database, while `allTables` is set, and removes it when it is cleared. CloudNativePG creates it as the superuser, which is the step Render's support performs. Its verdict is the `LogicalReplication` condition on the Database (never Ready). A second database made with `CREATE DATABASE` gets no all-tables publication; `REPLICATION` is instance-wide, so the user's own `FOR TABLE` publications there work.
- **Schema grants.** Render's form asks for the schemas, so its support grants them. The verb runs, as the database's default user, `GRANT USAGE ON SCHEMA`, `GRANT SELECT ON ALL TABLES IN SCHEMA` and `ALTER DEFAULT PRIVILEGES FOR ROLE <the owner and each owner-privileged credential the default user belongs to> IN SCHEMA … GRANT SELECT ON TABLES` to the publisher role, in one transaction. A table no such role owns is left to its owner. The grants are ordinary SQL the user could have run, so disable keeps them.
- **Retained WAL is bounded.** PostgreSQL's `max_slot_wal_keep_size` default is `-1`, unbounded, and CloudNativePG keeps it. While a database publishes, the operator sets it to a fifth of the database's storage, 2048 MB at Render's 10 GB floor, following the disk as it grows, so retained WAL alone stays far below the 90% disk-autoscaling trigger. The value is set after the tenant parameters and the name is operator-managed, so nothing lifts it. A slot that falls further behind is invalidated (`pg_replication_slots.wal_status` becomes `lost`) and its subscriber must be re-created. This value is bex's choice until [w34/001](../.pm/w34/001.md) captures Render's. A database that does not publish keeps `-1`.
- **Disable stops publishing and leaves nothing holding WAL.** It drops the database's logical slots first, connected as the publisher while it still holds `REPLICATION`: a subscriber's apply worker reconnects about a second after its walsender ends, so each slot is taken in a loop that ends the walsender, waits for the slot's release and drops it at once. It then clears the spec (`REPLICATION`, the all-tables publication and the WAL bound go) and ends any walsender left, so the subscriber's next connection is refused. The answer lists the dropped slots and any it could not drop.
- **The verb waits for PostgreSQL itself**, reading `pg_roles.rolreplication` and `pg_publication` as the default user, for up to two minutes, and answers `converged` with what it read, or the operator's condition if it did not converge. Re-running the same request writes nothing and records nothing new. Enable and disable each record one audit row on the database (`postgres.EnableLogicalReplication`, `postgres.DisableLogicalReplication`, caller `bex-operations`).
- **What stays the user's:** `CREATE PUBLICATION … FOR TABLE` as the default user, the subscriber side, and connecting subscribers to the external URL `<id>.<domain>:5432`. The SNI proxy never terminates TLS (§ TLS passthrough), so a replication connection reaches the instance unchanged and `pg_hba` matches it on the ordinary database rules. Never the pooled URL: PgBouncer cannot carry a replication connection.
- **Later milestones:** bex as a subscriber is [w34/m542](../.pm/w34/blocked/m542/README.md), [below](#subscribers-w34m542); failover, switchover, restarts, suspend, major upgrades and recovery are [w34/m543](../.pm/w34/blocked/m543/README.md), [§ Lifecycle](#lifecycle-w34m543).

**Verification.** `lego/backend/internal/postgres/logical_replication_pg_test.go` runs the verb against real PostgreSQL (17 in CI, 18 locally on 2026-11-21) with the operator played by a superuser loop: the refusals write nothing; enable grants the schemas, including a table created afterwards; a real subscription as the publisher role copies the existing rows and receives inserts, updates and deletes; the default user's `FOR TABLE` publication decodes for the publisher role; disable drops both slots while the subscription keeps reconnecting, the walsender is refused again and nothing streams on. The operator's projection is covered by `database_publication_test.go`. On a local PostgreSQL 18 pair over TLS (`sslmode=require`), an external subscriber connected as the reader copied the existing rows and received every change through `bex_all_tables`, a second subscription received the default user's `FOR TABLE` publication, and after the disable its reconnects were refused with `permission denied to start WAL sender`. That run is also where a one-shot terminate-then-drop lost both slots to the reconnecting apply workers, which is why the disable drops each slot in a loop. The replay on a real cluster and on production is the milestone's t008 and t012.

#### Subscribers (w34/m542)

Render's request names each database "you want to enable logical replication for (both publishers _and_ subscribers)", and afterwards the user creates "a subscription on each subscriber" ([render.com/docs/postgresql-logical-replication](https://render.com/docs/postgresql-logical-replication), read 2026-11-20). The page names no PostgreSQL major and no role attribute for a subscriber.

**bex before w34/m542 (checked 2026-11-21 on PostgreSQL 15, 17 and 18 shaped like a bex tenant: a non-superuser owner of its database and tables):** no role can create a subscription. The owner's `CREATE SUBSCRIPTION` answers `permission denied to create subscription` (DETAIL `Only roles with privileges of the "pg_create_subscription" role may create subscriptions.`) on 17 and 18, and `must be superuser to create subscriptions` on 15, both SQLSTATE 42501. The managed-roles projection grants no `pg_create_subscription` membership.

**Decision: the same verb enables a subscriber, in the form the database's major allows.**

- **PostgreSQL 16 and later: a subscriber role (`--subscriber-role`).** `spec.logicalReplication.subscriberRole` names a live credential, as the publisher role does. The operator adds `pg_create_subscription` to that role's CloudNativePG `inRoles`, beside the memberships it already has, only while it is named and only once the cluster runs 16 or later. The running major counts first: a cluster still upgrading from 15 has no such role, and CNPG would fail every managed role while one names it. The verb grants the role `CREATE` on the primary database when it lacks it, as the default user, since PostgreSQL needs both (`permission denied for database` otherwise). The owner and owner-privileged credentials have it already. The user then runs `CREATE SUBSCRIPTION`, as Render's page says, and PostgreSQL's own rules apply. A non-superuser's subscription must authenticate with its password (`password is required`), which every bex and Render URL carries. Changes are applied as each table's owner, so the subscription's owner must be able to `SET ROLE` to it; the runbook therefore recommends the database's default user, which owns the tables it created. Taking the field away, or naming another role, removes the membership; the `CREATE` grant is ordinary SQL the user could have run, and stays.
- **PostgreSQL 13–15: bex creates the subscription (`--subscription`).** These majors let only a superuser create or own a subscription, and no bex role is one. Render's support team, which already runs `FOR ALL TABLES` as a superuser, can create one there, so bex's operators do. The verb takes the subscription's name, the publisher's `postgresql://` URL (on stdin, so its password is on no command line) and the publication. It puts the password in a Secret of its own, owned by the Database, and writes the rest of the connection to `spec.logicalReplication.subscriptions[]`. A new password gets a new Secret, so the Cluster spec changes and CNPG rewrites the passfile. The operator projects each subscription as an `externalClusters` entry, whose password CNPG's instance manager writes to a passfile that the connection string names, so no password reaches the Cluster spec or `pg_subscription`. It also declares a CloudNativePG `Subscription` `<id>-sub-<hash>` in the primary database, reclaim policy `delete`, which CNPG creates as the superuser. At most four per database (`LogicalSubscriptionsMax`, PostgreSQL's default `max_logical_replication_workers`). The user cannot alter or drop a superuser's subscription (`must be owner of subscription`, checked on 15), so removing one is the verb's `disable --subscription <name>`, which drops it and its slot on the publisher. The verb refuses each form on the other majors by name (`LOGICAL_REPLICATION_SUBSCRIBER_FORM`). This path rests on ADR008 § Render parity first; what Render does on its own 13–15 databases is uncaptured ([w34/001](../.pm/w34/001.md)).
- **Prerequisites** are the publisher's (Pro, a paid plan, 10 GB, an available database), each refused by name before any write. One database may be both: an enable sets the halves it names and keeps the others, and `disable` takes `--publisher`, `--subscriber` or `--subscription <name>` to remove one part.
- **Disable is refused while the role owns subscriptions** (`LOGICAL_REPLICATION_SUBSCRIPTIONS_EXIST`), naming each `<database>.<subscription>` from `pg_subscription`, which every role can read apart from its connection string. PostgreSQL keeps a subscription whose owner loses `pg_create_subscription`, and keeps applying it: on 17 the owner could still disable, alter and drop it afterwards, only not create another. A disable that left one running would leave the database receiving changes that bex reports as not enabled, so the user drops them first. Naming another subscriber role is refused the same way.
- **Egress: none added.** Checked on production on 2026-11-21 from a CNPG instance pod in a hosting namespace (`bex-canary`). It opened TCP 5432 and a TLS PostgreSQL session to a database's external URL `<id>.db.bex.co` through the edge load balancer and `pg-sni-proxy` (PostgreSQL itself answered, refusing a probe user's password). It also opened a session to a PostgreSQL outside bex (EBI's public server), which saw the connection come from the instance's node ExternalIP. Both ride `allow-internet-egress` ([ADR043](ADR043-tenant-namespace-isolation.md) D3: the internet minus private ranges, for every hosting pod), and a same-workspace database's `-rw` Service rides `allow-same-namespace`. Cilium's `deny-tenant-node-and-metadata-egress` excludes CNPG pods. So a subscriber reaches all three kinds of publisher, and nothing new opens for any database. A publisher with inbound IP rules must admit the tenant nodes' addresses: bex has no NAT gateway ([ADR018](ADR018-render-parity.md) § Service outbound IPs). A database in a network-isolated environment reaches another environment's database only through its external URL.
- **Restarts.** A subscription lives in the catalog, and its apply worker starts again with the server. A local PostgreSQL 17 subscriber stopped while its publisher took 1,000 inserts came back with every row exactly once. CNPG's restarts (a plan change, a storage resize, suspend's hibernation, which keeps the volume) are that restart; the replay on a real cluster is the milestone's t010. Meanwhile the publisher's slot retains WAL, bounded by the rule above when the publisher is a bex database.
- **What stays the user's:** the subscriber's tables, since DDL is not replicated; `CREATE SUBSCRIPTION` on 16 and later; the sequences at cutover, which are not replicated (`setval` from the publisher's values); and waiting for `pg_stat_subscription` to catch up before cutting over.

**Verification.** `lego/backend/internal/postgres/logical_subscription_pg_test.go` runs the verb against real PostgreSQL (17 in CI; 15, 17 and 18 locally on 2026-11-21), with the operator played by a superuser loop. On 16 and later: the owner's `CREATE SUBSCRIPTION` is refused before enabling; enabled, it subscribes and receives the copy, inserts, updates and deletes; disable is refused naming the subscription and goes through once the user drops it, after which the refusal is PostgreSQL's again; a dedicated credential gets `CREATE` on the database; the 13–15 form is refused, writing nothing. On 15: the role form is refused, and a subscription bex creates is written with its password in a Secret and removed with that Secret. On a local PostgreSQL 15 instance, a superuser subscription whose connection string names a passfile, as CNPG builds it, copied every row of a PostgreSQL 18 publisher; the same drop with the passfile gone fails with `could not connect to publisher when attempting to drop replication slot`, which is the runbook's recovery case. The operator's projection is covered by `database_subscription_test.go`. The replay on production is the milestone's t010.

#### Lifecycle (w34/m543)

Render's logical-replication page says nothing about failover, major-version upgrades or recovery ([render.com/docs/postgresql-logical-replication](https://render.com/docs/postgresql-logical-replication), read 2026-11-20). Render documents all three for every paid Postgres, and bex has each at ✅ in ADR018. These rules keep them correct for a database that publishes or subscribes. What Render does in each case is uncaptured ([w34/001](../.pm/w34/001.md)).

##### Failover and switchover

- **PostgreSQL 17 and later: the slots follow.** A publisher with a standby (`spec.highAvailability`) running 17 or later gets CloudNativePG's logical decoding slot synchronization: `replicationSlots.highAvailability.synchronizeLogicalDecoding: true`, and `hot_standby_feedback` and `sync_replication_slots` on, which CNPG's webhook requires beside it (CNPG v1.30.1 `docs/src/replication.md` § Logical Decoding Slot Synchronization). The running major counts first, as for `pg_create_subscription`: a 16 server refuses to start with `sync_replication_slots` in its configuration. Both settings reload without a restart, and both are operator-managed while the rule holds. Turning it off withdraws the stanza, and CNPG's webhook defaults it again.
- **The subscriber's part:** a slot follows only if the subscription was created `WITH (failover = true)`, which needs a 17 or later subscriber (`ALTER SUBSCRIPTION … SET (failover = true)` on an existing one). An older subscriber or a CDC tool can create the slot itself with `pg_create_logical_replication_slot('<name>', 'pgoutput', false, false, true)` as the publisher role and subscribe with `create_slot = false`. The verb's answer carries this as a warning for an HA publisher.
- **Cost:** CNPG names the standby's HA slot in `synchronized_standby_slots`, so a change is sent to a failover-enabled subscription only once the standby has it. While the standby is down, those subscriptions wait, and the primary logs a warning. A subscription without `failover` is not held back, and not kept through a failover either.
- **PostgreSQL 13–16: a failover loses every slot.** CNPG keeps them there only through the `pg_failover_slots` extension, which bex's PostgreSQL image does not carry ([w8/m92](../.pm/w8/blocked/m92/README.md), [w8/276](../.pm/w8/blocked/276.md)). After a failover or switchover, every subscriber's next connection finds no slot (`replication slot "…" does not exist`), and the subscription has to be re-created, which copies the tables again. The verb's answer to an enable on such a database says so, as does the runbook. The ADR018 row records the gap with w8/m92 as its owner.
- **A subscriber with a standby** keeps its subscriptions through a failover, since they and their replication origins are WAL-logged. bex's standbys are asynchronous, though: one promoted before receiving the last transactions the old primary applied resumes from its own origin, while the publisher's slot may already have confirmed past it, so those transactions are skipped. This gap is recorded in ADR018 and filed as [w34/003](../.pm/w34/003.md).

##### Major-version upgrades

CNPG upgrades in place with `pg_upgrade --link` from a new data directory whose configuration comes from the Cluster, `wal_level = logical` included (CNPG v1.30.1 `internal/cmd/manager/instance/upgrade/execute/cmd.go`). A failed `pg_upgrade` leaves the Job failed and the database offline until bex returns `spec.version` to the source major ([§ Major-version upgrades](#major-version-upgrades-w8m12)). Checked locally on 2026-11-21 with PostgreSQL 16.15, 17.11 and 18.7 binaries and a real external subscriber:

| Source | Slot at shutdown | `pg_upgrade` |
| --- | --- | --- |
| 17 | subscriber paused, 50 rows behind | fails: `The slot "s" has not consumed the WAL yet` |
| 17 | subscriber paused, only a checkpoint behind | passes (it decodes the WAL to tell) |
| 17 | subscriber streaming until shutdown | passes, `Restoring logical replication slots in the new cluster`; the subscriber resumed with every row exactly once |
| 16 | any | passes, and the slot is gone: the subscriber stopped receiving |

So the shared verb (REST `PATCH /v1/postgres/{id}` `version`, GraphQL `updateDatabaseVersion`, MCP `update_postgres`, dry runs included) reads a publisher's slots, every database's, as the default user:

- **From 17 or later:** it notes `pg_current_wal_lsn()` and refuses while a slot is invalidated (`wal_status = 'lost'` or an `invalidation_reason`) or has not confirmed that position, with 409 `POSTGRES_UPGRADE_LOGICAL_SLOTS_BEHIND` naming each slot as invalidated, as not followed by any subscriber, or as followed but behind. A slot a subscriber is streaming from gets ten seconds to confirm; a caught-up one does within a second or two. One nobody follows cannot move, so the wait ends at once. A slot with only a checkpoint behind it would pass `pg_upgrade` but not this check: its subscriber has to connect once. Accepted, the upgrade keeps the slots.
- **From 13–16:** it accepts and answers `upgradeNotice`, naming the slots the upgrade drops and saying to re-create their subscriptions afterwards. REST carries it as a bex field of the PATCH answer, GraphQL as `Database.upgradeNotice`, MCP as a second text beside the result, and the dashboard as a warning toast that stays until dismissed. A dry run answers it too, so a caller can read it before committing. Refusing instead would hold the upgrade on a step Render's documentation does not describe. The notice keeps ADR009's rule that an upgrade never loses data silently.
- A slot read that fails refuses with 503 `POSTGRES_UPGRADE_LOGICAL_SLOTS_UNREADABLE`, the cause logged and not answered. A database that does not publish is not read and upgrades as before: no role of it can create a logical slot.

##### Restarts, suspend, plan changes and storage resizes

A logical slot lives in `pg_replslot` on the volume, and a subscription in the catalog. None of these operations replaces the primary's volume: suspend is CNPG hibernation, which keeps the PVC; a restart or a plan change recreates the primary's Pod on the same volume (CNPG's `primaryUpdateMethod` default is `restart`, which bex keeps, so no switchover happens); a storage resize grows the PVC. So the slots, the publications and the role attributes survive, and the subscriber resumes from its confirmed position. While the publisher is down, the subscriber's connection fails and retries. While it is hibernated nothing writes WAL, and the `max_slot_wal_keep_size` bound applies again once it runs. A plan change on an HA database still restarts the primary in place. No code change was needed; the replay on a real cluster is the milestone's t006.

##### Recovery

A recovery creates a new database with a new `dpg-` id ([§ Backups](#backups--point-in-time-recovery)). Render enables logical replication per database id, so the copy starts not enabled, whatever its source was:

- **The spec is not carried.** `Recover` builds the copy's spec afresh, and `spec.logicalReplication` is not part of it, so the copy has no `REPLICATION` projection, no all-tables `Publication` child and no WAL bound. The source's `max_slot_wal_keep_size`, `hot_standby_feedback`, `sync_replication_slots` and `max_logical_replication_workers` are operator-managed, so none of them reaches the copy. That rule used to drop only the canonical spelling of a name; it now drops every spelling.
- **The roles.** The backup restores the publisher role's `REPLICATION` and the subscriber role's `pg_create_subscription`. CNPG takes both from the owner, which the copy manages, because its spec enables nothing. A publisher or subscriber role that is another credential is retired on the copy, like the source's retired logins (§ Backups, w5/m384): NOLOGIN, no password, no membership. The source's other added users are not carried, as before. A role the source named before the restore target and no longer names is outside this rule.
- **Subscriptions.** The backup also restores the source's subscriptions, enabled, with their connection strings and slot names. Started, one would connect to the source's publisher and compete with the source for its slot; whichever holds it consumes the changes, and the source's subscriber silently misses them. So the operator runs a copy with `max_logical_replication_workers = 0` from its Cluster's creation until the copy is enabled as a subscriber, and keeps the setting while the live Cluster carries it. A copy recovered before this rule is not restarted for it. The verb refuses the copy's first subscriber enable while `pg_subscription` holds any subscription, naming each (`LOGICAL_REPLICATION_SUBSCRIPTIONS_EXIST`). The user detaches and drops each one (`ALTER SUBSCRIPTION … DISABLE`, `… SET (slot_name = NONE)`, `DROP SUBSCRIPTION …`), and an operator does the same as the superuser for one a superuser owns (a 13–15 subscription bex created). Detached, the drop leaves the publisher's slot to the source.
- **What stays in the catalog:** the user's own `FOR TABLE` publications, and `bex_all_tables` if the source published all tables. With no role holding `REPLICATION`, nothing can stream from them. Enabling the copy as a publisher with `--all-tables` adopts `bex_all_tables`, and disabling it drops it.

**Verification.** `lego/backend/internal/postgres/logical_slots_pg_test.go` runs on real PostgreSQL (17 in CI and locally on 2026-11-21). A publisher whose subscriber is paused with rows behind is refused on REST, GraphQL and MCP alike, by the slot's name, and nothing is written. Once the subscriber streams and confirms, all three accept with no notice. A source observed at 16 is accepted on all three with the same notice. A recovered copy holding its source's subscription is refused a subscriber enable, naming it, and accepted once it is dropped. An HA publisher's enable answers its major's failover warning. `logical_replication_lifecycle_test.go` covers recovery (nothing enabled, the logical-replication credentials retired, the managed settings in any spelling dropped) and an unreadable publisher's refusal; `database_logical_lifecycle_test.go` covers the operator's slot synchronization (only for an HA publisher running 17 or later, withdrawn cleanly) and the copy's worker guard. The failover drill and the production replay are the milestone's t006 and t010.

## HA · failover · read replicas (w1/m22)

Shipped 2026-07-12. All three Render fields verified against the live API ([render-artifacts/postgres-ha.md](render-artifacts/postgres-ha.md)):

### High availability

- `spec.highAvailability` (Render's `enableHighAvailability`) provisions a replicated CNPG cluster. When `true`, the operator raises `spec.instances` to `max(plan.Instances, 2)` and adds **required** pod anti-affinity (`enablePodAntiAffinity: true, podAntiAffinityType: required, topologyKey: kubernetes.io/hostname`) so primary and standby always land on different nodes; with no free node the standby stays Pending until the autoscaler adds one rather than sharing the primary's node (w2/m171). The ready-gate waits for both instances before reporting `Ready`.
- The wire field `highAvailabilityEnabled` (REST, GraphQL, MCP, the CLI) is the **configured** value, `spec.highAvailability`, as on Render, whose create response already says `true` while the database is `creating` (checked live 2026-11-01, w2/059). The operator's observed state, `status.highAvailabilityEnabled` (HA on _and_ ≥2 instances ready), stays internal: it gates replication-lag metrics and is exposed only as GraphQL's bex extension `highAvailabilityReady`, which the dashboard uses to show a standby still being added or removed.
- Available only on plans with ≥1 CPU (`1c-2g`, `pro-4gb`, `basic-4gb`); the standby is billed like the primary (two instances metered). A plan change to a <1-CPU plan while HA stays on is refused with `POSTGRES_HA_PLAN_UNSUPPORTED` unless the same request disables HA (w2/m171).
- HA can be toggled on an existing database: REST `PATCH /v1/postgres/{id}` `enableHighAvailability`, GraphQL `updateDatabaseHighAvailability`, MCP `update_postgres.enableHighAvailability`, and the dashboard create dialog + HA panel (w2/m171).
- Each promotion emits one `postgres_cluster_leader_changed` event (`{"leaderId": ...}`, webhook-subscribable). Live acceptance on dev-2 (2026-10-30): failover ~5s, internal URL unchanged.
- Independent of `readReplicas`: a DB can have read replicas without HA and vice versa (Render's documented independence).
- **Available in every workspace plan (w2/m247).** Render gates HA only on a ≥1-CPU plan, not on the workspace plan. Datastore Pods (CNPG instances, poolers, Key Value) carry PriorityClass `bex-datastore`, and the services' compute quota (`tenant-compute-quota`) is scoped `PriorityClass NotIn [bex-datastore]`, so a Hobby workspace's 3-CPU service budget never refuses a database instance. Datastores are bounded by their count caps and per-instance billing instead (ADR043 § Per-plan quota dimensions). Verified on production 2026-10-31 in a Hobby workspace that already ran services: `1c-2g` and `2c-4g` HA pairs each reached two healthy instances on distinct nodes with no `exceeded quota`, while a 4-CPU service there was still refused by `tenant-compute-quota`.

### Failover

- `spec.failoverAt` (verb-as-timestamp, like `restartedAt`) triggers a CNPG **planned switchover**: the operator reads the cluster's `status.instanceNames`, finds a non-primary instance, and patches `cluster.status.targetPrimary` to it. Read replicas are clusters of their own (w6/m467), so the primary Cluster's only non-primary instance is the HA standby: a planned or automatic failover promotes it and never a replica. CNPG then fences the old primary and promotes the target. The operator records the timestamp in `status.lastFailoverAt` so it only acts once per request.
- API surfaces: REST `POST /v1/postgres/{id}/failover → 202` (no body, matching Render exactly); GraphQL `failoverDatabase(id) → Boolean`; MCP `failover_postgres`. All three write `spec.failoverAt` through `Failover()` in `lifecycle.go`.
- Requires `// +kubebuilder:rbac:groups=postgresql.cnpg.io,resources=clusters/status,verbs=patch`.

### Named read replicas

- `spec.readReplicas: [{name}]` (Render's `readReplicas` create field) declares named read replicas. Each is its own one-instance CNPG replica cluster (`appv1alpha1.ReadReplicaClusterName`) streaming from the primary, with its own Service `<id>-ro-<name>` on its instance: the internal host, and under `<BEX_DB_DOMAIN>` the external one, which the proxy routes to that Service (w6/m467, [§ Per-replica readers and pools](#per-replica-readers-and-pools-one-replica-cluster-per-name-w6m467-decided-2026-11-18)). No replica URL reaches the primary or the HA standby.
- `status.readReplicaStatuses: [{name, internalHost, externalHost}]` tracks the resolved hosts. API `readReplicas[].id` is the stable derived id `<primary>-ro-<name>` (w5/066) — not a separately minted `dpg-` resource; `connectionInfo` on the view is a bex host-only extension beside Render's required `id`/`name`. The proxy rebuilds its exact route table from current CR intent; the operator removes any pre-m15 Traefik routes during reconciliation.
- Connection strings (with password) are in `connection-info` as `readReplicaConnectionStrings: [{name, internalConnectionString, externalConnectionString}]` — host-only info (without password) is also in the view.
- **Pooled replica connections (w6/m458, per replica since w6/m467).** When the database is pooled, each replica has its own PgBouncer, a CNPG `Pooler` `<id>-rp-<name>` on its replica cluster, and its status carries `poolerHost` (`<id>-rp-<name>.<ns>.svc`) and, when public, `poolerExternalHost` (`<id>-rp-<name>.<BEX_DB_DOMAIN>`), which the proxy routes to that PgBouncer and the server certificate names. `readReplicaConnectionStrings[]` adds `internalConnectionPoolString` (port 6432) and `externalConnectionPoolString` (port 5432, as the primary's), and the view's `connectionInfo` adds `internalPoolHost`/`externalPoolHost`. `-rp-` is as long as `-ro-`, so the pooled label fits one DNS label for every name admission accepts. From w6/m458 until w6/m467 one `<id>-pooler-ro` (`<id>-pool-ro` outside) served every replica.

### Per-replica readers and pools: one replica cluster per name (w6/m467, decided 2026-11-18)

Render: "Each read replica has its own independent connection pool", a replica is reached "just like you do your primary instance, using its internal or external connection URL", and its HA standby is a separate instance from its read replicas ([read replicas](https://render.com/docs/postgresql-read-replicas), [connection pooling](https://render.com/docs/postgresql-connection-pooling), read 2026-11-17). Two mechanisms on CNPG 1.30.1 were built by hand on dev-6 (PostgreSQL 18) on 2026-11-18. This is a parity choice, not a user decision.

**Option A, each name bound to an instance of the one Cluster.** A four-instance Cluster with Services `<id>-ro-a` and `<id>-ro-b` selecting `cnpg.io/instanceName` and `cnpg.io/instanceRole: replica`. Each Service read its own instance. Two things fail:

- **A replica can be promoted.** With the HA standby's WAL receiver lagging (received `0/A002F28` against `0/AC7C770` on the bound instances), deleting the primary Pod made CNPG fail over to `-3`, replica `a`'s instance. `<id>-ro-a` lost its endpoint, and a session already open through it was now on the primary. CNPG elects the most advanced standby: received LSN, then replay LSN (`PostgresqlStatusList.Less`, `reconcileTargetPrimaryForNonReplicaCluster`). Nothing marks an instance as not promotable, and a fenced instance is shut down.
- **Removing one replica drops another.** After `a` was rebound to `-1`, lowering `spec.instances` from 4 to 3 removed `-4`, replica `b`'s instance (`ScaleDown … removing instance -4`). CNPG removes the highest-serial ready non-primary (`findDeletableInstance`). It cannot remove a chosen instance.
- **Pool.** CNPG's `Pooler` takes `type` `rw`, `ro` or `r` and no instance, so each replica's PgBouncer would be a Deployment bex owns: image, `auth_query` role and secret, server and client TLS, configuration. It was not built, because A already fails the two points above.

**Option B, one replica cluster per name (chosen).** Next to the primary `Cluster` (two instances, HA) and its `Pooler`, each replica got:

- a one-instance `Cluster` with `replica.enabled`, `bootstrap.pg_basebackup`, and an `externalClusters` entry that streams from `<id>-rw` as `streaming_replica`, using the primary's `-replication` client certificate with `sslmode: verify-ca` against the primary's server CA (CNPG's "standalone replica cluster");
- a CNPG `managed.services.additional` Service `<id>-ro-<name>`, `selectorType: rw`, which selects the replica's designated primary;
- a CNPG `Pooler` `<id>-rp-<name>`, `type: rw`, on that cluster.

Each replica was healthy about 65 s after it was created. On that setup:

- **Each URL reads its own instance.** `<id>-ro-a:5432` and `<id>-rp-a:6432` read `a`'s Pod with `pg_is_in_recovery()` true, and `b`'s URLs read `b`'s Pod. Neither the primary nor the HA standby served any replica URL.
- **Certificates.** A replica cluster signs its own server certificate with the primary's `<id>-ca` (`certificates.serverCASecret`) and lists its own public hosts (`serverAltDNSNames`). `verify-full` against that CA, the one bex serves (`serverCACertificate`), passed for `<id>-ro-a.<domain>` and `<id>-rp-a.<domain>`. With a user-provided certificate (a cert-manager CA issuer standing in for Let's Encrypt), the replica cluster served the primary's `-public-tls` and `-public-ca`, and `verify-full` passed again once its pooler rolled, since PgBouncer reads its certificate only at start (w8/245).
- **Pool.** PgBouncer authenticated with CNPG's `auth_query`. The `cnpg_pooler_pgbouncer` role and `user_search` function replicate from the primary, whose own Pooler created them; CNPG's instance manager creates them only on a primary. With 1,000 `pgbench -S` clients through each replica's pooler at once, `SHOW POOLS` read 90 `sv_active` on each. Each replica instance held 90 `app` backends, and the primary and the HA standby held none.
- **Failover.** After a switchover to the HA standby and then the deletion of the new primary's Pod, both replicas kept streaming from `<id>-rw` (`pg_stat_wal_receiver` `streaming`) and read the rows written after each. Every URL stayed on its own instance.
- **Removal.** Deleting `b`'s Cluster and Pooler mid-run left `a`'s 1,000 clients running: 902,257 transactions, none failed. The primary's Pods kept their UIDs throughout; the demoted primary restarted once, for the switchover itself.
- **Connection slots.** At saturation a replica held 90 pooled connections plus 7 `cnpg_pooler_pgbouncer` lookup sessions, all 97 tenant slots, so a direct connection to that replica read `remaining connection slots are reserved`. m458 saw the same on the primary.

**Why B.** Render's replicas are separate instances that are never a failover target, and B gets that from CNPG's own primitives, with CNPG owning the Services and the PgBouncer. A needs a PgBouncer bex owns and works against CNPG's failover and scale-down.

**Names.** A replica cluster is `<id>-r-<first 10 hex of sha256(name)>`. CNPG caps a cluster name at 50 characters (`validateName`), and `<id>-ro-<name>` reaches 63. The replica's direct Service is `<id>-ro-<name>`, and its PgBouncer is the Pooler (and Service) `<id>-rp-<name>`, published as `<id>-rp-<name>.<BEX_DB_DOMAIN>`. `-rp-` is as long as `-ro-`, so every name admission accepts fits one DNS label and `readReplicaNameMaxLength` is unchanged. A name that cannot form a DNS label (possible only before the 2026-10-19 admission rule) uses the cluster's hash in place of the name. `<id>-pooler-ro` and `<id>-pool-ro` go away.

**What changes on an existing database with replicas.**

- **Primary Pods: none roll.** The primary Cluster's `spec.instances` falls back to the plan and HA count, and CNPG removes the in-cluster readers, the highest-serial non-primary first and never the primary. When that leaves one instance, the live readiness timeout is kept (`holdReadinessTiming`), so only the PodDisruptionBudget goes.
- **Readers are rebuilt.** Each reader is recreated as a replica cluster with a new `pg_basebackup`. Its clients reconnect, and its internal host moves from `<id>-ro` to `<id>-ro-<name>`; the external `<id>-ro-<name>` does not change.
- **Pooled readers move.** `<id>-pooler-ro` is deleted, and each replica's pooled host is `<id>-rp-<name>`, inside and outside.
- **Production restarts nothing.** Its 5 databases have no replica, HA or pooling (read 2026-11-18 00:05Z).

**Costs B carries.**

- **Labels.** A replica's Pods carry their own `cnpg.io/cluster`, so whatever reads the primary's label (logs, metrics, readiness, the disk-growth quota check) must include `<id>-r-*`.
- **No replication slot.** CNPG writes no `primary_slot_name` for a replica cluster's designated primary, so a replica more than `wal_keep_size` (CNPG's 512 MB) behind needs the WAL archive or a new clone. In-cluster standbys keep HA slots.
- **Major upgrades.** A physical standby cannot cross a PostgreSQL major, so a major upgrade of the primary recreates its replicas.

**Shipped (t002–t005, 2026-11-18).** `reconcileReadReplicas` (`database_replicas.go`) builds each replica cluster from the primary's live spec: image, plan resources, storage, PostgreSQL parameters and preloaded libraries, and labels.

- **Cloned from a settled primary only.** A replica is cloned from a primary that serves, runs the major its spec names and is not suspended. A replica cloned at another major is deleted and cloned again. Hibernation and restarts follow the Database's at all times.
- **Placement and pool.** A replica prefers a node without the primary's instances. A pooled replica's `Pooler` follows once its cluster exists.
- **Routing.** pg-sni-proxy routes `<id>-ro-<name>` and `<id>-rp-<name>` to the Services of the same names, each with its own admission bucket.
- **Observability, billing and quota.** Logs, metrics, disk usage and disk autoscaling read the primary's and every replica cluster's Pods and PVCs (`appv1alpha1.DatabaseClustersPattern`, `<id>(-r-<hash>)?`). Instance-seconds and storage metering count each replica's instance and PVC, as they counted in-cluster readers, so a replica is billed like its primary, as on Render. The tenant quota room counts a PgBouncer and a clone Job for each cluster.

**What each change restarts or replaces.**

| change | what happens |
| --- | --- |
| add a replica | its cluster, Service and pooler are created; the primary Cluster's spec and every other replica are untouched |
| remove a replica | its cluster and pooler are deleted; the primary and every other replica keep their Pods and clients |
| pooling on or off | each replica's pooler, and the primary's, is created or deleted; no instance restarts |
| plan change | every pool is rewritten by `RELOAD`, no PgBouncer rolls; CNPG restarts the primary's and each replica's instance for new resources, as before |
| certificate issued or renewed | a replica cluster reloads it, and its pooler rolls on the served-certificate digest (w8/245), as the primary's |
| PostgreSQL major upgrade | each replica is deleted and cloned again once the primary runs the new major |
| suspend or resume | each replica hibernates or resumes with the primary |
| an existing database with in-cluster readers | see above: the readers are rebuilt as replica clusters, the primary does not roll |

**Stale read-replica detection (`postgres_read_replica_stale`, w4/m511).** A read replica cluster whose WAL streaming from the primary stops keeps serving stale reads while CNPG still reports the replica `Cluster` `phase: "Cluster in healthy state"` and `Ready=True`. CNPG's `:9187/metrics` `pg_replication` queries also do not emit for replica clusters (`bootstrap.pg_basebackup` defaults `GetApplicationDatabaseName()` to `"app"`, which does not exist on bex's `dpg_…` databases, so Prometheus receives neither `cnpg_pg_replication_lag` nor `cnpg_pg_replication_is_wal_receiver_up` from a read replica).

- **Signal:** The operator polls each ready replica instance's CNPG instance-manager HTTPS endpoint (`https://<pod-ip>:8000/pg/status`, Pod IP from `Cluster.status.instancesReportedState`, admitted by every tenant namespace's `allow-operator-probe-ingress` / `allow-datastore-control-ingress`, TLS verified against `Cluster.status.certificates.serverCASecret` with no Prometheus or SQL dependency). A standby (`isPrimary: false`) is syncing iff `isWalReceiverActive && !replayPaused`.
- **Threshold and hysteresis:** On a settled, non-suspended primary (`readyInstances > 0`, not major-upgrading) and a ready replica (`readyInstances > 0`), the operator polls every **30 s**. On the first non-syncing sample it stamps `syncStoppedAt` on that entry of `Database.status.readReplicaStatuses` while keeping `syncing: true`. Only once non-syncing has persisted continuously for **2 minutes (`120 s`)** does `syncing` flip to `false`, pinning `syncStoppedAt` to the episode's start. Transient probe errors preserve the previous `(syncing, syncStoppedAt)` so a brief scrape timeout neither false-alarms nor flaps a stale episode back to healthy.
- **Recovery and re-arming:** The first syncing sample (`isPrimary == false && isWalReceiverActive && !replayPaused`) sets `syncing: true` and clears `syncStoppedAt`. The control-plane reconciler records one `postgres_read_replica_stale` fact per `(replica, syncStoppedAt)` episode when `syncing` becomes `false`, records nothing on recovery (Render has no recovery event), and re-arms on recovery so a subsequent stale episode records a new event.
- **False-alarm exclusions:** During initial sync (`pg_basebackup`), `readyInstances == 0` so probing does not start until the replica is ready and streaming. During suspension or major upgrade (`!src.settled`), `syncStoppedAt` is cleared (and `syncing` cleared while suspended). During a primary HA failover, the replica's walreceiver reconnects in ~10–15 s, well under the 2-minute threshold.
- **dev-4 observations (2026-11-19, CNPG 1.30.1, PostgreSQL 17, `1c-2g` HA + replica `reader`):**
  - **Initial sync:** replica `Cluster` reported `phase: "Setting up primary"`, `readyInstances: 0` during `pg_basebackup`; once `readyInstances: 1`, `/pg/status` reported `isWalReceiverActive: true`, `replayPaused: false`, `isPrimary: false`.
  - **Broken streaming (Calico `Deny` NetworkPolicy blocking replica → primary `:5432` + terminating the replica's walsender):** within <1 s `isWalReceiverActive` flipped to `false` and `receivedLsn`/`replayLsn` froze at `0/50506C0` while the primary advanced from 9 to 17 rows over 95 s; `Cluster.status` stayed `phase: "Cluster in healthy state"`, `Ready=True` throughout.
  - **Recovery (NetworkPolicy deleted):** reconnected at `T+28s`, immediately flipping `isWalReceiverActive` back to `true` and catching up to all 22 rows (`0/6000A18`).
  - **Primary HA failover (`POST /v1/postgres/{id}/failover`):** primary switched in ~5.7 s; `isWalReceiverActive` dipped to `false` at `T+3.1s..10.8s` (~10.6 s total) and returned to `true` by `T+13.7s`, never approaching the 2-minute threshold.

## SQL console error mapping (w4/071)

The dashboard SQL console, REST `POST /v1/postgres/{id}/query`, and MCP `query_render_postgres` share `mapPGError`. Schema and syntax SQLSTATEs (`42601`, `42703`, `42P01`, `42883`, `42P02`, `3D000`, `3F000`) return the Postgres `Message` (and `Position` when set) to the authenticated caller — those strings only quote the caller's own SQL or catalog identifiers. Multi-statement input (still `42601`, but with Postgres's "multiple commands" message) returns the product sentence `only one statement per query`, matching the console's single-statement copy. Write/DDL refusals and statement timeouts keep their fixed prose. Integrity and cast failures (`23505`, `23503`, `22P02`, …) stay collapsed to `bad request (SQLSTATE …)` so stored/literal values never leave the DB response. Neither class is written to logs, metrics, or audit events.

## SQL result values (w4/m157)

The same three surfaces share one conversion from pgx's decoded cells (`lego/backend/internal/postgres/query_values.go`), applied before the encoded-result budget so the cap measures what is emitted. REST and MCP carry JSON values; GraphQL carries each cell as a nullable string. Where pgx's default decoding is not truthful, the cell becomes:

- **float/numeric NaN and ±Infinity** — the strings `NaN`, `Infinity`, `-Infinity`.
- **date/timestamp/timestamptz ±infinity** — `infinity` / `-infinity`.
- **uuid** — the canonical lowercase hyphenated string.
- **arrays** — nested to their dimensions, matching PostgreSQL's `to_json`.
- **json/jsonb** — the server's JSON text, kept by codecs registered only on the query's own connection. Numbers keep every digit. On GraphQL a JSON `null` is the string `"null"` and a JSON string keeps its quotes, both distinct from SQL NULL's null cell. On REST/MCP, JSON null and SQL NULL both encode as `null`, and object key order and whitespace follow PostgreSQL's output, compacted.
- **finite dates/timestamps outside years 0–9999** — Bex's ISO 8601 expanded-year string: a sign and at least six astronomical-year digits, then the usual RFC 3339 remainder with its fraction and offset. Examples: `+010000-01-01T00:00:00Z`, and `-000001-01-01T00:00:00Z` for PostgreSQL's `0002-01-01 BC`. RFC 3339 cannot carry those years, and before this conversion one such value failed the whole result. Years 0–9999 keep their RFC 3339 form.

Every other value — finite numbers including exact numeric digits, integers, text, bytea (base64), year 0–9999 times and NULL — keeps its existing encoding.

## Consequences

- Deferred: the Accelerated tier and payment collection. Backups + PITR + lifecycle + access shipped in **w1/m17**; HA/replicas/failover in **w1/m22**; disk autoscaling in **w8/m14**.
- **`bex-db` (the control plane's own DB) runs two cross-node instances plus continuous WAL archiving and nightly backups** — required pod anti-affinity and CNPG switchover cover one platform-node drain (w1/m38); the off-cluster backup/PITR path covers correlated loss (w2/m27, [ADR031-platform-data-backup.md](ADR031-platform-data-backup.md)).
- The external-endpoint IP allowlist, pooler, and read-replica names ride the same metered `*.db.bex.co` SNI proxy (§3) — no per-DB LoadBalancer; every backend→client byte rolls up to the parent Database.

- **bex MVP verification (when built):** apply a `Database` CR → CNPG `Cluster` reaches healthy → install the deployment's server CA and connect via the **internal** URL from an in-cluster pod and via the **external** URL (`<id>.db.bex.co`, `sslmode=verify-full`) with `psql` → delete the `Database` → Cluster/Service/Secret/PVC gone and the external route removed.
