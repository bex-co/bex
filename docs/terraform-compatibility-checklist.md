# Render Terraform provider compatibility checklist

Render's official Terraform provider ([render.com/docs/terraform-provider](https://render.com/docs/terraform-provider), registry `render-oss/render`, source `render-oss/terraform-provider-render`) graded against bex with **its own acceptance suite**, unmodified, re-recorded against a bex API. It is a client bex must serve, like the [Render CLI](cli-compatibility-checklist.md); [ADR018](ADR018-render-parity.md) points here from its "Terraform provider" row.

Legend: `[x]` passes against bex · `[~]` passes in part · `[ ]` fails, with the board item that owns each bex-side cause · `[-]` a recorded omission or non-goal ([ADR018 § Render operation omissions](ADR018-render-parity.md#render-operation-omissions), `.pm/DO_NOT_DO.md`).

## Pins and harness

- **Provider:** `render-oss/terraform-provider-render` at `06af456d9bdb1b839f29923ac7e435c4a1f01f3c` (tip on 2026-11-16, after release v1.9.1).
- **Terraform:** 1.17.2. The harness checks the release zip against a sha256 pinned per platform.
- **Harness:** `scripts/terraform-provider-verify.sh <package>... | all` with `BEX_API_URL`, `RENDER_API_KEY` (a bex API key) and `RENDER_OWNER_ID` (the workspace `tea-` id). Optional: `TF_VERIFY_RUN` (a test-name filter), `TF_VERIFY_WORKDIR` and `TF_VERIFY_TIMEOUT`.
  - **Clone.** It clones the pinned commit into a work directory outside the repository; it refuses one inside. Nothing from the clone runs except `go test` on the named package.
  - **Record mode.** It runs one test per `go test`, with `TF_ACC=1` and `UPDATE_RECORDINGS=true`. The provider's go-vcr helper then talks to `RENDER_HOST` and writes a fresh cassette over Render's own.
  - **Results.** It prints one row per test: target `bex` (the test uses the recording provider) or `offline` (an `httptest` fake or a unit test), the result, and the first error.
  - **Sweep.** After each test, it deletes every resource that appeared in the workspace while the test ran, then confirms none is still listed. A test that fails after bex created something leaves it out of Terraform's state, so this is what keeps the next test's names free. Use a workspace no one else is creating resources in.
  - **Run output.** Re-recorded cassettes and logs stay in the work directory. It prints a recordings tarball's sha256 and the `git -C <work>/terraform-provider-render diff` that compares bex's answers with Render's.
- **Workspace:** the tests assume Render's test workspace, which is on a plan with webhooks, autoscaling, network isolation and inbound IP rules, so the graded workspace was upgraded to Scale (`changeWorkspacePlan`).
- **Tests:** `scripts/terraform-provider-verify.test.sh` (offline: argument and work-directory refusals, the result table, the sweep against a fake API), run in `scripts.yml`.

## Failure classes

Each class names the request, Render's recorded answer and bex's answer. "Render" is the provider's own cassette at the pin; "bex" is the re-recording.

1. **The requested region was read back as bex's own** (w9/105, fixed 2026-11-18). For example, `POST /v1/services` with `serviceDetails.region: "oregon"` got Render's 201 with `oregon`, and bex's 201 with `frankfurt`. The provider stores the response's `region`, a required `RequiresReplace` attribute, so Terraform aborted the apply with _Provider produced inconsistent result after apply: .region: was "oregon", but now "frankfurt"_. This hit every service, Postgres and Key Value configuration that names a region other than `frankfurt`; Render's suite names `oregon` in 50 configurations and `ohio` in 5. A resource now reads back the Render region it was created with and still runs in `BEX_REGION` ([ADR049](ADR049-render-yaml-parity.md) D7, amended). **Rechecked on dev-9 with `BEX_REGION=fsn1`** (main `1ec5007be` plus the fix): `TestAccPostgresIPAllowListResource` passes (create, update, import, destroy; every recorded answer reads `oregon`), and `TestWebServiceResource_Autoscaling` gets past the region to class 7's memory percentage (w9/111).
2. **An environment that names the defaults needed Admin** (w9/106, fixed 2026-11-18). The provider always sends `protectedStatus` (`"unprotected"` unless configured) and `networkIsolationEnabled: false` for each environment, on project create, environment create and the environment `PATCH` of every update. bex required `can_manage` whenever either field was present, so a Developer, and so every API key, got 403 even for `unprotected`. Now only a value that restricts access needs Admin: `protected`, isolation on, or an allow list that keeps some source out (`core.EnvironmentACLBearing`, the w4/355 definition). An update also needs Admin when the environment already restricts access. **Rechecked on dev-9** (main `018004cd3` plus the fix, OpenFGA on) with a Developer API key and the provider built from the pin. A `render_project` with an unprotected environment applied and planned clean. It then took a rename and a second unprotected environment, planned clean again and was destroyed. One with a `protected` environment was still refused with 403. The item's raw probe, `POST /v1/projects` with `unprotected` and isolation off, answered 201. The seven tests this class stopped do not pass yet: every fixture also declares a `protected` prod environment, which is Admin-only on Render too, so they now stop at class 3.
3. **An API key acted as a Developer, never as its creator's role** (w9/107, fixed 2026-11-18 by w9/m481). Render's key permissions go up to "every permission your member role allows" ([render.com/docs/api-keys](https://render.com/docs/api-keys)), and "Your key's access adjusts to match your new member role". bex bound every key as a Developer (`BindKey`), so its Admin-only writes were 403 for any key: `PATCH /v1/notification-settings/owners/{id}`, `POST /v1/registrycredentials` and a protected environment. `POST /v1/webhooks` was refused even for an Admin key, because only a human caller could mint a signing secret (`AuthorizeMintClass`, w4/079). Now a key acts with its creator's current role in its own workspace and follows it, capped at request time by its creator's own decision, and webhook create and repoint admit a key a person minted ([ADR024](ADR024-members.md#an-api-key-acts-with-its-creators-role-w9m481), [ADR117](ADR117-security-review-api-key-roles.md)). **Rechecked in run C:** with an Admin's key as minted, `render_webhook` and `render_project` pass, `render_notification_setting` gets past its first step to the previews divergence, and the supplementary `render_registry_credential` apply passes. Every test this class stopped now stops where run B did, which had the Admin grant this change makes unnecessary. **Live on production pin `4b2cebd0bd03` (2026-11-19):** a key the QA user minted in `bex-canary` with no permissions named created a webhook (201) and a registry credential (200) and patched owner notification settings (200); each was then deleted or restored and the key revoked (w9/m481 t008).

4. **Key Value connection info `409` right after create** (w9/108, fixed 2026-11-18). Render answers `GET /v1/key-value/{id}/connection-info` 200 with its strings while the store is still `creating`. bex answered `409 "key value credentials are still converging"` until the operator recorded the credential revision. Each Key Value and Redis test reads it right after create, and so does the provider's create. Now the unchanging password is served from the operator's first reconcile, and a read that arrives before that pass waits up to 5 s for it. **Rechecked on dev-9** (main `158b31565` plus the fix): both data source tests apply and pass checks 1–10, then stop at class 10. Both resource tests get past connection info to `log_stream_override` (`404`), a recorded omission.
5. **`PUT …/env-vars` and `…/secret-files` with a `null` body** (w9/109, fixed 2026-11-18). The provider sends `null` to clear a service's variables and files, and Render answers 200 `[]`. Render's cassettes hold 66 such requests (32 env-vars, 34 secret-files), all answered 200. bex's Render request gate refused them with `400 request body does not match the Render API schema`, because w9/m472 had made the lists nullable inside a create body only. Both PUTs' bodies now accept `null` as the empty list (`renderNullableBodyOperations`), on a copy of the schema that the build-source PUT and the create bodies keep sharing non-null. **Rechecked in run D:** the re-recordings hold 22 such PUTs, 20 with `null`, all answered 200, and `TestBackgroundWorkerDockerResource` passes. Run B counted nine tests stopped by this class. In run D eight tests pass, and `TestWebServiceResource_RuntimeUpdate` reaches step 4 of 4, where class 9 stops it. The rest stop at classes 6, 7, 8 and 9 and at the preview non-goals.
6. **`imagePath` is read back as written** (w9/110, fixed 2026-11-18). A create with `image.imagePath: "nginx"` gets Render's `imagePath: "docker.io/library/nginx:latest"` and bex's `"nginx"`. The provider takes `image_url` and the tag from `imagePath` only when it has a `:` or `@`, so `image_url` reads null. Terraform then aborts every image-service create that names a bare image. Now REST, GraphQL and MCP read the configured image in Render's form (`store.RenderImagePath`: Docker Hub's short names expand, a missing tag reads `latest`, an explicit tag or digest is kept), while the App keeps and runs the image as written. **Rechecked in run E:** every bex answer in the re-recordings reads the qualified form, and a bare `nginx` appears only in the provider's own request bodies. Webservice's `TestEnvVarsResource` passes its first step and stops at step 2 on class 9.
7. **A disabled autoscaling criterion loses its percentage** (w9/111, fixed 2026-11-18). A create with `criteria.memory: {enabled: false, percentage: 70}` gets 70 back from Render and 0 from bex. The provider stores the answer, so Terraform aborted with _Provider produced inconsistent result after apply: .autoscaling.criteria.memory.percentage_. Now `spec.autoscaling` keeps a turned-off criterion's percentage (`disabledCPUPercent`/`disabledMemoryPercent`), which every REST read, MCP and GraphQL read back and scaling never uses. **Rechecked in run F:** every bex answer in the three scaling recordings reads `memory: {enabled: false, percentage: 70}`. `TestWebServiceResource_Autoscaling`, `TestBackgroundWorkerScalingResource` and `TestPrivateServiceScalingResource` pass their first step and stop at step 2 on class 9.
8. **A service notification override with `previewNotificationsEnabled: "false"`** (w9/112, fixed 2026-11-18). Render answers 200 and reads `"false"` back. bex answered `400 … use default`. Now the override keeps `"false"` in `spec.previewNotificationsEnabled` and every read answers it back: the override `GET`, `PATCH` and list, the service object (an extension, omitted at `default`), GraphQL and MCP. `"true"` stays refused, as `400 NOTIFICATION_PREVIEWS_UNSUPPORTED`: preview notifications belong to PR previews, a non-goal. **Rechecked in run G:** the recorded `PATCH` answers 200 with `"false"`, and `TestWebServiceResource` stops at the next request, `PUT /v1/logs/streams/resource/{id}` (`log_stream_override`, an omission).
9. **A `PATCH` of an image service carrying `rootDir: ""`** (w9/113, fixed 2026-11-18). The provider sends every service's `rootDir` on each update, `""` for an image service, and Render answers 200. bex answered `400 has no repo to build (root directory only applies to build-from-git)`, though the value was the service's own empty root directory.
