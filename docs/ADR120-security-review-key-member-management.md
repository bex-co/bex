# ADR120: Security review — an API key changes member roles and removes members

- **Status**: Accepted (2026-11-19, w9/116)
- **Trigger**: w9/116 relaxes a gate round 24 closed. [ADR107](ADR107-security-review-round24.md) H-1 made a member role change mint class (`AuthorizeMintClass`), which refuses every machine caller, so Render's `PATCH /v1/owners/{ownerId}/members/{userId}` refused every API key where Render's key with "Update member roles and remove members" succeeds. A bex API key with a recorded creator now changes a member's role and removes a member, acting for its creator ([ADR024 § An API key manages members as its creator](ADR024-members.md#an-api-key-manages-members-as-its-creator-w9116)). Render parity comes first, and AGENTS.md says to amend the older decision rather than keep the divergence; this review is what makes the amendment safe.
- **Lineage**: a focused pass after [ADR117](ADR117-security-review-api-key-roles.md), [ADR118](ADR118-security-review-scoped-api-keys.md) and [ADR119](ADR119-security-review-member-api-keys.md), whose invariants I1–I10 it keeps, except that I4 no longer covers a role change. It amends ADR107's H-1 decision for attributed keys only, and adds I11 (a key manages members only as its creator could, now) and I12 (a key never acts on its creator).

## Scope

`lego/backend/internal/members/service.go` (`ChangeRole`, `Remove`, `keyCreatorRole`, `guardKeyCreatorRole`, `RoleWithin`); `core.Base.KeyCreator`, `AttributedAPIKey` and `AuthorizeExportClass` (`internal/core/keyrole.go`); the unchanged paths a key's member verb now reaches: `core.keyCeiling`, the verbs' uncached `can_manage` re-check, `guardCallerRoleSettled`, `guardSelf`, `guardMachine`, `guardLastAdmin`, `endMembership`'s key and session teardown, the dispatch gate's `keyPermissionOps` (all six member operations need `workspace.members.manage`) and the audit row. Reviewed as an attacker holding a leaked API key of each member role, with All and with a scoped grant.

## Verdicts

| # | Attack | Verdict | Evidence |
| --- | --- | --- | --- |
| 1 | A key promotes a member above its creator's role (Admin from a Developer's key, Billing from a Developer's or Contributor's) | Blocked | only an Admin holds `can_manage`, and the ceiling asks the creator the same relation uncached; beside it `guardKeyCreatorRole` refuses a target role, or a member, its creator's current row does not cover (`403 ROLE_ABOVE_KEY_CREATOR`). `TestAKeyNeverReachesAboveItsCreatorsRole` takes the model out of the way (every subject holds every relation) and the rule alone refuses; `TestRoleWithinMatchesTheModel` pins the role order to `model.fga` |
| 2 | A key changes its creator's role, or removes its creator (a self-promotion back after a demotion, a self-removal) | Fixed in the change | `guardSelf` compared only the caller's subject, and `Remove` has no class gate, so before this change an Admin's key could remove its own creator; with the guard reverted the e2e's key demoted its own creator. `keyCreatorRole` now refuses the creator as target with `CANNOT_CHANGE_OWN_ROLE` / `CANNOT_REMOVE_SELF` (409), in both directions and whatever role is named. `TestAKeyCannotActOnItsCreatorOrAnyKeyBinding`, the e2e on REST's two routes, GraphQL and MCP |
| 3 | A key re-roles or removes its own binding, or another key's | Blocked (I5) | `guardSelf` on the key's subject and `guardMachine` (`MEMBER_IS_MACHINE`) are unchanged. Same tests |
| 4 | A Developer's, Contributor's, Viewer's or Billing member's key changes a role or removes a member | Blocked | none of them holds `can_manage`, and the ceiling refuses whatever the key's tuple says. `TestBelowAdminKeysCannotManageMembers`; the e2e's Developer key gets 403 on every surface, and m514's e2e still refuses a Viewer's key |
| 5 | An Admin's key whose grant lacks "Update member roles and remove members" changes a role or removes a member | Blocked (I6) | the dispatch gate maps `PATCH`/`DELETE` on both REST routes, `changeWorkspaceMemberRole`, `removeWorkspaceMember`, `change_workspace_member_role` and `remove_workspace_member` to `workspace.members.manage`, which only Workspaces Read & write grants. The e2e's Workspaces Read key under an Admin creator gets `403 api_key_permission_denied` on every surface |
| 6 | An Admin is demoted; their key keeps managing members | Blocked (I1) | both verbs re-check `can_manage` uncached and the ceiling asks the creator at the same freshness, so the key is refused on its next request. `TestADemotedCreatorsKeyLosesMemberManagementAtOnce`; the e2e demotes the creator, the key is refused on every surface, and promoted back it works again |
| 7 | The creator's demotion is still queued, so their tuple and the key's still say Admin | Blocked | `keyCreatorRole` refuses while the creator's role reconciliation is pending (round-19 #3, as `guardCallerRoleSettled` does for the caller), and the role guard reads the creator's row, not the tuple. `TestAKeyWaitsForItsCreatorsRoleChange` (with stale admin tuples it is refused, and once the queue clears it still cannot promote above the row's Developer) |
| 8 | A key with no recorded creator, a key minted by a key, or a key whose creator left the workspace | Blocked | `AuthorizeExportClass` refuses an unattributed key a role change; `keyCreatorRole` needs the creator to be a person row in the workspace; the ceiling's I3 refuses an unattributed key `can_manage` anyway. `TestAKeyWithNoPersonBehindItCannotManageMembers` |
| 9 | A delegated third-party OAuth token, or a `client_credentials` client that is not a bex API key, changes a role | Blocked (H-1 holds) | `AuthorizeExportClass` admits a machine caller only when Hydra names it a bex API key with a creator, and falls to `AuthorizeMintClass` for everything else. `TestRoleChangesStillRefuseADelegatedThirdPartyToken`, `TestMembershipIssuanceRefusesADelegatedThirdPartyToken`, `TestAuthorizeExportClassAdmitsOnlyAttributedKeysBeyondTheMintClass`, and the operator client case in `TestAKeyWithNoPersonBehindItCannotManageMembers` |
| 10 | A key invites an outside account, then promotes it | Blocked (I4) | `Invite` and `ResendInvite` keep `AuthorizeMintClass`; Render's public API has no invite endpoint and no key permission names one. m481's e2e still asserts a key's invite is refused |
| 11 | A key manages members of another workspace where its creator is an Admin | Blocked (I2) | a key has a row and tuples only in its own workspace, and the ceiling refuses any other workspace object |
| 12 | The creator lookup cannot answer (Hydra down) | Blocked, fails closed | `KeyCreator` returns `ErrAuthzUnavailable` (503), as the ceiling does |
| 13 | A key demotes or removes every other Admin, or the last one | Not a gap | the last-admin rule applies to a key unchanged, and the key's creator, an Admin, is out of its reach, so the workspace keeps at least that Admin |
| 14 | A key's change is not attributable | Not a gap | the success row (`members.ChangeRole`, `members.Remove`) is built from the request identity, so it names the key's client id as the caller, as every key write does (ADR012 §8e) |

Every new guard was reverted once and a test above failed: the class gate (the unit tests and the e2e), the creator guard (the e2e's key then demoted its own creator), the role guard, the pending-creator check and the machine-creator check. A key with no recorded creator is refused three times over (the export-class gate, the creator lookup finding no person row, and the ceiling's I3).

## Accepted, by design

- **What a key changes outlives the key.** A promotion a key makes stays after the key is revoked, as one its Admin makes stays after their session ends. That is what H-1 refused for a delegated token, whose consent is not the member's own authority; a bex API key is the member's own credential, revoked with their membership (w2/m163), and Render's keys work this way.
- **A key is refused its creator's own row with 409**, the code a person gets for their own row, because the key acts for that person. Another Admin's key may change the creator's role, as another Admin may.

## Residual risk

- **A leaked Admin key with the permission can re-role or remove every existing member but its creator.** It cannot bring an outside account in (verdict 10), so a durable foothold needs an existing member to promote. Owner: the workspace Admin. The audit log names the key on every change, revoking the key ends it, and a key for automation that does not manage the team can be minted without "Update member roles and remove members" (Workspaces Read, w9/m496).
- **A change racing its creator's demotion.** The fresh `can_manage` check and the creator's row are read before the write, so a demotion that commits between them lets one change land, the same window a request from the creator's own session has.
- **ADR117's, ADR118's and ADR119's residuals stand** for these keys.
