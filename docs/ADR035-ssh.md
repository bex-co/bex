# ADR035 — SSH into running service instances

**Status:** accepted; running-instance SSH implemented behind production activation and live verification (2026-07-14); in-dashboard Browser Web Shell over that same running instance added (w2/m55, 2026-07-17) and **production-activated 2026-09-08 (w2/m90)**. **Amended by [ADR054](ADR054-open-in-zed.md) (w2/m65): a second target kind — the agent-session sandbox (`ags-…@ssh.bex.co`) — resolves through this same gateway with a per-connection multi-channel exception and an sftp-server subsystem bridge, both scoped to sandbox targets only; `srv-…` App targets keep the single-channel / no-subsystem / no-forwarding contract unchanged. The inline corrections below fold that amendment in.** **Regression + fix (w6/m132, 2026-08-28): the public handshake silently stopped sending `KEXINIT` after w4/m82 enabled Traefik's PROXY protocol without the gateway's matching `BEX_SSH_PROXY_PROTOCOL_TRUSTED_CIDRS`; see [Regression](#regression-the-proxy-protocol-receiver-half-was-never-deployed-w6m132). It is now guarded by a manifest lockstep check and an always-on KEXINIT liveness synthetic.**

## Context

Render supports public-key SSH into paid web services, private services, and background workers. Its current CLI reads `serviceDetails.sshAddress`, verifies a live deploy, optionally lists `GET /v1/services/{id}/instances`, and invokes the user's local OpenSSH binary. This is narrower than an ephemeral shell product: it attaches to one container that is already serving the App.

bex previously grouped every exec-shaped feature under the hosted-execution non-goal. The user reopened running-instance SSH (2026-07-14) and, later, the in-dashboard Browser Web Shell over that same already-running instance (2026-07-17 — see [Browser Web Shell](#browser-web-shell)). Ephemeral instances, one-off jobs, and hosted sandboxes remain excluded in [`.pm/DO_NOT_DO.md`](../.pm/DO_NOT_DO.md).

The security constraint is stronger than ordinary API reads: Kubernetes `pods/exec` can read the complete runtime environment and act with the workload's identity. bex-api must not inherit that permission.

## Decision

bex runs `/ssh-gateway` as a third backend entrypoint in the shared lego image and as its own Deployment and ServiceAccount. It accepts SSH on container port 2222. Traefik's dedicated `ssh` TCP entrypoint exposes it on public port 22 in production.

The connection path is:

1. OpenSSH connects to `<service-id>@ssh.bex.co`, or `<instance-id>@ssh.bex.co` for a selected replica.
2. The gateway accepts public-key authentication only. It hashes the presented key with OpenSSH SHA-256 and resolves that globally unique fingerprint in `ssh_keys`.
3. After the client proves key possession, the gateway attaches the stored subject as a `core.Identity` with method `ssh`.
4. A composite resolver routes by id kind (ADR054 D1). A `srv-…` username goes to `apps.Service.ResolveSSHSession`, which resolves the App through its stable id and calls the resource-scoped `AuthorizeApp(can_view_sensitive)` seam — the SINK's relation, since a shell reads the pod's env vars and mounted secrets (codex round-4 #8; the weaker `can_operate` an earlier draft named would let a contributor `printenv` around the boundary). An `ags-…` username goes to the agent-session resolver, which authorizes `can_view_sensitive` on the `agent_session:<id>` object and derives the session's sandbox pod. Authorization therefore targets the resource's own workspace, not whichever workspace happens to be the caller's default.
5. For an App target the resolver selects a Running, Ready pod whose revision label and `app` container image equal the App's active status. A bare service id selects a random eligible replica, matching Render. A specific instance id selects exactly the pod returned by the instances endpoint. For an agent-session target it derives the live sandbox pod (`<sandbox_id>-0` in `<workspace_id>-sandbox`, container `sandbox`) — refused unless the session's phase implies a running sandbox.
6. One SSH `session` channel maps to one Kubernetes `pods/exec` stream in the target container. EXCEPTION (ADR054 D3): an agent-session sandbox target may open several concurrent `session` channels over one connection — what Zed's ControlMaster remoting multiplexes — each its own `pods/exec` stream, bounded by `BEX_SSH_MAX_CHANNELS_PER_CONN`; App targets stay single-channel. No sshd or sidecar is injected into tenant images.

## Public contract

### SSH keys

Keys are identity-scoped. One person can use the same key in every workspace where that identity has `can_operate`; a key is not copied into workspace membership or Kubernetes Secrets.

- REST: `GET/POST /v1/ssh-keys`, `DELETE /v1/ssh-keys/{id}`
- GraphQL: `sshKeys`, `createSSHKey`, `deleteSSHKey`
- MCP: `list_ssh_keys`, `add_ssh_key`, `delete_ssh_key`
- Dashboard: Account Settings → SSH Public Keys

Eligible service pages expose the command through a Connect → SSH menu and a left-nav Shell page, matching Render's information architecture. The Shell page shows the copy-ready running-instance SSH command **and** hosts an in-browser terminal (see [Browser Web Shell](#browser-web-shell)); unavailable services explain the missing address without inventing one. Private keys never enter the browser — the in-browser terminal authenticates with the caller's dashboard session, not an SSH key.

The store contains typed `ssk-…` id, subject, display name, canonical public key, SHA-256 fingerprint, and creation time. It never accepts or stores private material. Supported key types match Render's documented set: Ed25519, RSA (minimum 2048 bits, authenticated only with SHA-2 signatures), ECDSA P-256/P-384/P-521, and OpenSSH security-key Ed25519/ECDSA. Comments are discarded. Multiple records, `authorized_keys` options, trailing payloads, oversized input, malformed text, and duplicate key material are rejected. Options are rejected rather than silently stripped because a user might otherwise believe an option such as `command=` still restricts the registered account key.

Render documents RSA support but no minimum size. The 2048-bit registration floor is bex's explicit security policy; it rejects obsolete weak RSA material instead of advertising a key that the gateway should not trust.

Any workspace member may manage their own public keys through `can_manage_ssh_keys`; only contributor/developer/admin identities can open sessions because target authorization separately requires `can_operate`. Deleting a key prevents every new handshake using it. Existing sessions are not retroactively killed by key deletion.

### Service and instance shape

When `BEX_SSH_HOST` is set and the SSH-key store is available, an eligible service returns:

```json
{
  "serviceDetails": {
    "sshAddress": "srv-d5t5d4v8g3c73f5m9peg@ssh.bex.co"
  }
}
```

The field is omitted for free, suspended, cron, static, or unsupported service types and when no public host is configured. Web, private, and background-worker services on a paid plan are eligible to advertise an address; the gateway still requires an active revision (a release that went live) and a Ready current-image pod of it before authenticating. The App phase is not part of the gate (w4/m352): it tracks the latest deploy, so a deploy's build, pre-deploy and rollout leave the serving instance reachable — see § Sessions across a deploy.

`GET /v1/services/{id}/instances` returns Render's array of `{id,createdAt}` objects. Public instance ids are `<service-id>-<opaque-suffix>`, stably derived from the Pod **name** so live listing, metrics, and logs agree without a live UID lookup (historical Prom/Loki retain only names). Pre-m87 SSH selectors hashed the Pod UID; the resolver still accepts those legacy ids for the same Ready pod and fails closed on ambiguity. Raw pod names, UIDs, or Kubernetes credentials are never exposed on the wire. The general instances surface follows Render's rollout-observability contract: it includes non-terminating Pending, Running, and Unknown Deployment pods and excludes terminating, terminal, cron, and static pods. The SSH resolver then re-lists the service pods and narrows a requested id to a Running+Ready pod whose `app.bex.co/revision` label equals `App.status.activeRevision` and whose app-container image equals `App.status.image`. Build, pre-deploy, stale-revision, stale-image, and non-Ready pods therefore remain visible where appropriate for instance inspection but fail closed as SSH targets. The operator stamps the revision label on every app Deployment pod template, so a same-image restart cannot make the old ReplicaSet look current.

## SSH protocol and exec behavior

The server permits only:

- one `session` channel per SSH connection (EXCEPTION: an agent-session sandbox target may open up to `BEX_SSH_MAX_CHANNELS_PER_CONN` concurrent `session` channels, each its own exec stream — ADR054 D3);
- `pty-req` before execution;
- `window-change` while a PTY session runs;
- one `shell` request, executed as `/bin/sh`; or
- one `exec` request, executed as `/bin/sh -lc <client-command>`; or
- the `sftp` subsystem, executed as the fixed `sftp-server` binary — ONLY on an agent-session sandbox target, so Zed can upload its remote-server when the sandbox's closed egress blocks a direct download (ADR054 D4). App targets reject every subsystem.

The command is one argv value, not interpolated into a Kubernetes URL or host command. It intentionally receives normal shell semantics inside the app container. The gateway does not log or persist it.

stdin, stdout, stderr, TTY state, and resize events bridge through client-go `remotecommand`. Kubernetes exit codes become SSH `exit-status`. Client disconnect, restart, redeploy, or pod deletion cancels the stream; a gateway release does so only an hour after its pod began draining (§ Sessions across a gateway release). A service session has no time limit (§ How long a session lasts). An image without executable `/bin/sh` fails with exit 126 and a bounded shell-unavailable message; bex never installs a shell into the image.

**Output reaches the client whole (w6/096, w6/099, 2026-10-29).** A finished single-session exec leaves the transport for the client to close (`clientCloseGrace`, 30 s), so the server never resets the tail of the output away. Separately, kube-apiserver's upgrade proxy (`k8s.io/apimachinery/pkg/util/proxy/upgradeaware.go`) closes an exec stream as soon as its client→backend half fails, which a slow reader triggers once the process exits, and output still in flight is lost. kubectl hits the same loss. The gateway therefore reads exec stdout/stderr from the apiserver at full speed into an in-memory buffer (`BEX_SSH_DRAIN_BUFFER_PER_CHANNEL`, 64 MiB per channel; `BEX_SSH_DRAIN_BUFFER_TOTAL`, 128 MiB per process, user decision 2026-10-29) and forwards it at the client's pace; `exit-status` follows the drained output. Only a channel's own cap ever blocks it: once the process-wide budget is spent, a channel writes straight through (the old backpressure), so stalled clients cannot freeze other sessions, and a cancelled or revoked session discards what is left instead of waiting on a client that stopped reading. A burst that outruns the client by more than the buffer can still lose its tail until the upstream proxy is fixed (w6/099).

The following never reach Kubernetes: `direct-tcpip`, forwarding, agent forwarding, X11, SCP protocol handling, and environment requests — on every target. Subsystems and extra session channels are likewise banned EXCEPT the two ADR054 D3/D4 carve-outs above (multiple `session` channels and the `sftp` subsystem), which apply to agent-session sandbox targets only.

## Isolation and RBAC

The gateway ServiceAccount has one Role in the configured tenant App namespace: `get,list` on `apps.app.bex.co` and `pods`, plus `create` on `pods/exec`. It has no ClusterRole or ClusterRoleBinding.

It cannot read Secrets, logs, Jobs, platform/auth namespaces, or arbitrary tenant namespaces. bex-api's separate Role remains read-only for pods and has no `pods/exec` rule. A structural manifest test guards this split and rejects any future cluster-wide gateway grant.

The gateway runs non-root with all capabilities dropped, a read-only root filesystem, resource limits, two replicas, a PodDisruptionBudget, and SSH ingress restricted to the Traefik namespace. A separate internal HTTP listener supplies health probes and Prometheus metrics; only the monitoring namespace may reach it. Metrics contain bounded authentication/session outcome and limit-scope labels—never subjects, service or instance ids, addresses, commands, environment values, or terminal content. Global and per-identity session caps default to 100 and 5 and cover native SSH, the web shell and agent attach. Sandbox exec and file streams hold a limiter of their own, with no per-identity bound below its pool, because Render documents no concurrency limit on sandbox commands ([ADR104 D7 § Concurrent commands and transfers](ADR104-sandbox-render-parity.md#concurrent-commands-and-transfers-w22m623), w22/m623). Handshakes default to 10 seconds. An agent-session connection, and a service connection that has not opened its shell yet, last at most four hours (`BEX_SSH_SESSION_TIMEOUT`); a service shell has no time limit (§ How long a session lasts).

The `bex_ssh_gateway_authentications_total{result}` counter is also the **server-side proxy for the dashboard SSH-key onboarding funnel** (w2/m66's `RequiresSshKey` gate): `result="rejected_key"` is an offered key not found in `ssh_keys` (the caller has not registered it — the dominant first-run failure the gate exists to pre-empt), versus `result="accepted"`. The gate reduces the former, so "the gate is working" reads as `rejected_key`'s share falling as `accepted` rises — e.g. `sum(rate(bex_ssh_gateway_authentications_total{result="rejected_key"}[1h])) / sum(rate(bex_ssh_gateway_authentications_total[1h]))` trending down. This exact metric root-caused the w2/m65 "Open in Zed" dead-end (a `rejected_key`-only spike with zero `rejected_target`).

## Host-key custody and network exposure

The gateway host key is unrelated to the `~/.ssh/bex` node-admin key described in [ADR019](ADR019-infra-credentials.md). It is a dedicated, stable Ed25519 key installed out of band as `bex-system/bex-ssh-host-key` by [`scripts/ssh-host-key-secret.sh`](../scripts/ssh-host-key-secret.sh). The Deployment refuses to start when the Secret is absent or malformed.

The local hostNetwork Traefik baseline binds its SSH entrypoint on 2222, avoiding node sshd on port 22. The production Hetzner LoadBalancer exposes that entrypoint on 22. The `ssh.bex.co` A/AAAA records must be DNS-only and point directly at the Traefik LoadBalancer; an ordinary Cloudflare-proxied record cannot carry this raw SSH endpoint. [`scripts/ssh-dns-cloudflare.sh`](../scripts/ssh-dns-cloudflare.sh) reconciles that exact DNS-only A/AAAA set and removes stale or duplicate address records. Its Cloudflare token needs zone-specific `Zone / DNS / Edit`; zone discovery additionally needs `Zone / Zone / Read`, which can be avoided by supplying `CLOUDFLARE_ZONE_ID`. The token is an ephemeral operator credential and must not be written to `.env` or a checked-in file. `--check` is read-only and rejects proxied, missing, stale, or duplicate address records.

**The client's address through the edge (w9/m451 t010, 2026-11-18).** A native SSH connection crosses two PROXY-protocol hops. The Hetzner `:22` listener sends its header to Traefik's `ssh` entrypoint, which believes it only from the load balancer's private address `10.10.0.7/32`. Traefik then sends its own v2 header to the gateway, which believes it only from the pod CIDR (`BEX_SSH_PROXY_PROTOCOL_TRUSTED_CIDRS`, w6/m132). The gateway records the resulting client address as the session's `remote_address` and as `metadata.source_ip` on `StartShellEvent`/`EndShellEvent`. Until w9/m451 the first hop was missing: w1/m150 kept `:22` plain on the belief that the second hop carried the client, but that hop carries only what Traefik knows, so every native SSH row recorded `10.10.0.7`. The web shell arrives through `:443`, whose listener already sent the header, and recorded the client. The two halves roll out in w1/m150's order: Traefik's trust first, then the listener. The reverse order puts the load balancer's header into the SSH version exchange. While Traefik trusts a peer that sent no header, it holds the server's banner until the client speaks. OpenSSH and the Render CLI send their identification at once, and `ProbeKEXINIT` now does too. Once the listener sends its header, a client-written PROXY line is not believed. It arrives after the load balancer's header and reaches the gateway as ordinary pre-banner text. `scripts/edge-proxyprotocol-validate.sh` pins both halves.

[`scripts/ssh-activate.sh`](../scripts/ssh-activate.sh) `--check` is a separate read-only preflight that requires the complete public A/AAAA set to equal the Terraform-owned Hetzner edge's public address set and verifies TCP/22 presents the mounted key's published fingerprint. Both SSH edge scripts query that exact named object with `HCLOUD_TOKEN`; they no longer depend on Kubernetes `LoadBalancer` status because the production Traefik Service is intentionally a `NodePort`. Running activation without `--check` performs the same gates before creating the activation ConfigMap and restarting bex-api. `BEX_SSH_HOST` must not be set before those checks pass.

Rotation is deliberate: create a new key, publish its fingerprint and maintenance window, replace the Secret with `scripts/ssh-host-key-secret.sh` (which rolls and waits for both gateway replicas), and tell clients to replace the known-host entry. Routine deploys never regenerate the key.

## Audit contract

`AuthorizeApp(can_view_sensitive)` (App target) or `AuthorizeOn(can_view_sensitive, agent_session:<id>)` (sandbox target, ADR054 D2) records the allowed or denied connection authorization through the shared audit seam. A successful handshake additionally creates an `ssn-…` row in `ssh_sessions`, then closes it with end time and result. The table contains only subject, workspace, service id, instance id, remote address, start/end times, and result. The daily audit sweep deletes these rows after `BEX_AUDIT_RETENTION_DAYS` (default 90), the same boundary as `audit_events`.

**Workspace audit log (w9/m451, 2026-11-16).** A service shell session, native SSH or the dashboard Shell, also writes Render's `StartShellEvent` when it opens and `EndShellEvent` when it closes into the workspace audit log (`audit_events`, verbs `shell.StartShell`/`shell.EndShell`, `sshgateway.RecordShellEvent`): the person, the service (`metadata.service`, the `srv-` id), the instance (`metadata.instance`, column `instance_id`, migration 0289), the client address (`metadata.source_ip`) and, for the web shell, the browser's user agent (`metadata.user_agent`; native SSH has none, Render says "when available"). Each row's id derives from the `ssn-` id and the phase, so a retried write records once; a failed write is logged and never blocks or ends the session. A refusal after the caller is identified (a denied `can_view_sensitive`, a workspace two-factor requirement) is the denied authorization row the resolver already records (`apps.ResolveSSHSession` at the gateway, `apps.CreateShellSession` at web shell ticket mint), which the audit log reports as `StartShellEvent` with `status: error`, now carrying the client address; an unknown key records nothing. Two refusals record no row, as everywhere in bex: the uncached re-check after a cached positive and the protected-environment admin gate. A watchdog or per-channel re-check that refuses mid-session records the same `error` row. An agent-session sandbox (`ags-…`, ADR054) is a cloud-agent surface whose reference product is Devin, not a service shell: it records neither event.

**Write path and residual.** The gateway writes these rows through its existing `INSERT`-only grant on `audit_events` (`dbrole.sql`; no `SELECT`, `UPDATE` or `DELETE`, tested by `TestGatewayScopedRoleAllowsOwnSurfaceDeniesTheRest`), chosen over merging `ssh_sessions` into the audit log at read time, which would have broken its single keyset cursor, the CSV export and one-table retention. The per-service event index trigger skips the two shell verbs (migration 0289): shell sessions are not service events, and the trigger reads `apps` and `tenants`, which the gateway role must never be granted. Residual: a stolen gateway credential can insert forged audit rows into any workspace's log, but cannot read, alter or delete any row, so it can add noise but cannot hide what happened; the per-row RLS that would bind inserts to the gateway's own sessions stays the `.pm/FUTURE-MAYBE.md` ssh-gateway RLS entry.

The audit type and schema have no command, argv, environment, stdin, stdout, stderr, or terminal-content field. This structural omission is the privacy boundary; operators must not add ad hoc stream logging around it.

## Fail-closed behavior

Authentication fails without revealing whether the cause was an unknown/deleted key, malformed username, missing/foreign service, insufficient role, unsupported/free/suspended service, missing live revision, or missing/non-Ready/stale instance. No session channel opens and no `pods/exec` request occurs.

One refusal is told to the client, because it can only follow a positive authorization decision (w22/m402, [ADR012 §9a](ADR012-auth.md#9a-workspace-enforced-two-factor-authentication-w22m402)): a member of a workspace that requires two-factor authentication who has no second factor. The funnel asks the gateway's two-factor gate (an HMAC question to bex-api, cached 30 s, failing closed) after OpenFGA allows, so a key that is not a member with access never reaches it. The SSH client prints an authentication banner saying the workspace requires two-factor authentication; a channel refused on a live connection carries the same reason in its open-failure description. An outage of that check is refused without the message.

**An agent session with no sandbox to open wakes, or is told (w10/043 and w10/m597, 2026-11-23).** `ssh ags-…@ssh.bex.co` into a session whose sandbox closed (completed or failed, not archived) starts it, and into one whose sandbox is starting waits for it: the login is admitted with the session as its target, every session channel is held with progress on stderr, and the command runs once the sandbox is up, as SSH into a sleeping Devin session "wakes the machine and completes the request instead of showing 'not running'" ([release notes](https://docs.devin.ai/release-notes/2026), 2026-09-25, read 2026-11-23). The start is bex-api's `Service.Resume`, run as the key's owner through a signed internal verb, so it is refused to a caller who may view the session but not start it ([ADR054 D9](ADR054-open-in-zed.md#d9--an-ssh-login-wakes-a-closed-session-w10m597-2026-11-23), reviewed in [ADR124](ADR124-security-review-ssh-session-wake.md)). Everything else that keeps a session from opening is told in an authentication banner with the resolver's `AGENT_SESSION_NOT_ATTACHABLE` message: a canceled or archived session, a caller who may not start it, a start bex-api refused (with its reason: payment method, billing, the live-sandbox cap), and a wake bex-api did not answer. The resolver refuses that way only after `can_view_sensitive` passed, cached and fresh. A key enrolled by an API key is told, and may wake a session, only when its grant covers sandbox execution (and, for the start, managing agent sessions). So a caller who may not view the session, or who names one that does not exist, still gets the bare `Permission denied (publickey)`. A banner is counted as `authentications_total{result="rejected_no_sandbox"}`, a wake as `session_wakes_total{result}`, and a channel refused later keeps the generic reason. A start that ends without a sandbox is told on each waiting channel's stderr with exit status 1.

After authorization, Kubernetes errors remain bounded. A pod disappearing during restart/redeploy closes the stream. The gateway never retries against another replica, because silently switching a specific session target would violate instance selection and could cross a deploy boundary.

### Sessions across a deploy (w4/m352)

A session lives as long as the instance it is attached to. Both transports re-run `ResolveSSHSession` at connect and every `BEX_SSH_REVALIDATE_INTERVAL` (default one minute; codex round-9 #6), and that gate reads the serving release — `Status.ActiveRevision` and `Status.Image`, which keep describing it while a newer deploy builds, runs pre-deploy, or waits on rollout health — never the App phase. So during a deploy an open shell keeps running and a new one opens on the serving instance (REST `POST /v1/services/{id}/shell-ticket`, GraphQL `createShellSession`, the Web Shell, raw `ssh` and `render ssh` alike). Build and pre-deploy pods, and the new revision's pods before it goes live, are never targets. With zero-downtime deploys the old instance stops only after the new release is live; its exec stream then breaks, and the stream is never moved to another replica. A first deploy that never went live still refuses with "the service has no running instance yet; wait for the current deploy to go live".

Render parity: Render "automatically closes a service's active SSH sessions" when "the service is redeployed or restarted for any reason", and "you cannot SSH into an instance that is no longer running" ([render.com/docs/ssh § Automatic session closure](https://render.com/docs/ssh), checked 2026-11-14). Its zero-downtime deploys keep the old instance serving until the new one is healthy, and its CLI "verifies a live deploy" before connecting (§ Context) — a live deploy that a deploy in progress does not remove. bex therefore closes a session when its instance is replaced (the redeploy taking effect), not when a deploy starts. The phase-based gate this replaces cut every session at the first tick after any deploy started, with a false "no running instance yet", while its instance kept serving (round 226). A live comparison against a Render account during a deploy's build phase was not available; the closure point is read from Render's documentation.

**Why a session ended.** A server-ended Web Shell session gets an error frame with a stable `reason` beside the English `message` (the `code` field stays the exit status of an `exit` frame): `revoked` (an authorization failure — a removed member, a role change, a newly protected environment, a deleted service and an API key whose grant no longer includes one-off jobs (w9/125, [ADR118](ADR118-security-review-scoped-api-keys.md) verdict 20) all read only "your access to this service ended"), `suspended`, `ineligible` (Free plan or a type without instances), `instance_gone` (the attached pod stopped, or no Ready pod of the serving release remains), `timeout` (the gateway's drain bound, § Sessions across a gateway release), and `unverified` (the resolver failing closed on an unreachable store). The runtime reasons are reachable only after a fresh authorization passes, so they disclose no more than the caller's own `GET /v1/services/{id}`. The dashboard shows each under "Session ended" in the reader's language, falling back to the message for a reason it does not know; a transport failure stays "Connection error". Native SSH has no such channel beyond the exit status and the closed connection, so an SSH client still sees only the connection end — a known gap.

### A check that gets no answer (w6/147)

Native SSH re-runs three checks at each channel open and each revalidation tick: the key lookup, the owner's email check (bex-api's internal verb) and `ResolveSSHSession`. Only a definite answer ends a live session at that tick: the key deleted or bound to another subject, an unverified owner, a deny (a login requirement and a protected environment included), the service gone, or a runtime refusal (`suspended`, `ineligible`, `instance_gone`). A check that gets no answer (a database error or timeout, bex-api, OpenFGA or Kubernetes unreachable, an internal request bex-api refused, such as a 401 from a nonce claim that timed out) is retried at the next tick, and three in a row end the session anyway (three minutes at the default interval), so an outage cannot keep sessions open without checks. A new channel never opens on an unanswered check; on a multiplexed agent-session connection only that channel is refused. Each failure is counted in `bex_ssh_gateway_channel_reauthorizations_total` (`result="rejected"` or `"unavailable"`) and logged with its cause (`ssh gateway: reauthorization rejected: key_gone`, `ssh gateway: reauthorization unanswered: resolve_failed: …`), never the subject or the key.

Render parity: Render closes a session only when the user ends it, the service redeploys or restarts, or its SSH infrastructure goes into maintenance ([render.com/docs/ssh § Automatic session closure](https://render.com/docs/ssh)). Before this, any failed check ended the session, and on production plain `ssh` sessions ended every one to three hours with none of those (w6/147). The Web Shell's revalidation runs only `ResolveSSHSession` and still ends at its first unanswered tick, with the `unverified` reason.

### How long a session lasts (w6/174)

A service shell, native SSH or the Web Shell, has no time limit. It ends when its client ends it, when its access ends (§ A check that gets no answer), when its instance stops (§ Sessions across a deploy), or an hour after the gateway or edge pod carrying it began draining (§ Sessions across a gateway release, § Sessions across an edge roll). Until w6/174 every one also ended at `BEX_SSH_SESSION_TIMEOUT` (4 h): each held probe of w6/147 and w6/153 ended there, with `END rc=255 after=14401s`.

`BEX_SSH_SESSION_TIMEOUT` (default and production `4h`) still bounds what is not a service shell: an agent-session connection (ADR054 D6, whose Completer treats an older open SSH row as leaked), an agent attach stream, a sandbox exec, and a service connection that authenticated but has not opened its shell yet.

**A client that went away.** A session with no time limit must not outlive a client that vanished without closing its connection, such as a laptop that slept and woke on another network. Such a connection would hold one of its owner's five session slots until the next gateway release. Native SSH therefore asks the client every minute whether it is still there (`keepalive@openssh.com`, as sshd's `ClientAliveInterval 60` with `ClientAliveCountMax 3`), and closes the connection when one has gone unanswered for three minutes. A client answers a request it does not know with a failure ([RFC 4254 § 4](https://www.rfc-editor.org/rfc/rfc4254#section-4)), which counts as an answer, so a live client never notices. The Web Shell already pings the browser every 50 s and closes the shell after 60 s without an answer.

Render parity: Render "automatically closes a service's active SSH sessions" when "the service is redeployed or restarted for any reason", and when it maintains the "underlying infrastructure that enables SSH connections", giving existing connections an hour ([render.com/docs/ssh § Automatic session closure](https://render.com/docs/ssh), read 2026-11-23). It names no session length, and for "long-running commands" it suggests a one-off job, not a limit. bex follows that list. A session held past 4 h on Render could not be measured, because bex has no Render account (w10/002's gate), so the absence of a cap is read from Render's documentation, as the closure point of § Sessions across a deploy is.

### Sessions across a gateway release (w6/m482)

A release of `bex-ssh-gateway` itself (every production deploy runs `kubectl rollout restart deploy/bex-ssh-gateway`, several times a day) no longer cuts the sessions it carries. The gateway runs two lifetimes:

- **SIGTERM turns readiness off, and the listeners close a window later** (w6/152). `/readyz` turns 503 at once so the terminating pod leaves every Service endpoint (`serving=false`, not only `ready=false`), while native SSH (`:2222`), the Web Shell (`:8080`) and the internal listeners (sandbox exec `:8081`, agent Git `:8082`, agent attach `:8083`, model proxy `:8084`, egress proxy `:8085`) keep accepting for `BEX_SSH_ACCEPT_WINDOW` (default and production `10s`), then stop. Traefik (`IngressRouteTCP` routes only to `ready` endpoints) and the nodes' Service load balancing keep sending new connections to the old pod until they have seen its endpoint leave, which takes a few seconds; a listener closed at SIGTERM failed those before the SSH banner (`kex_exchange_identification: Connection closed by remote host`, one of 141 probe connections across pin `4e37ec03f`'s roll). A connection made in the window is served by the old pod and drains with the rest; after it, a new `ssh`, `bex ssh` or Shell connection, and a new shell ticket's WebSocket (REST `POST /v1/services/{id}/shell-ticket`, GraphQL `createShellSession`), lands on a new pod. It follows Render's order for a deploy: the new instance gets the traffic, Render waits 60 s, then sends the old one `SIGTERM` ([render.com/docs/deploys](https://render.com/docs/deploys), read 2026-11-20). Kubernetes switches the traffic and sends `SIGTERM` at the same moment, so the gateway holds its listeners open itself (rather than with a `preStop` pause, so any supervisor gets the same order).
- **Open sessions keep running** until they end on their own, their access is revoked, their instance stops, an agent session's 4 h cap passes, or `BEX_SSH_SHUTDOWN_TIMEOUT` (default and production `1h`) has passed since the listeners closed. Revalidation keeps ticking on a draining pod, so § Sessions across a deploy and the revocation rules apply unchanged. In-flight agent streams (model-proxy answers, Git exchanges, attach streams, exec, egress tunnels) drain within the same bound; hijacked connections (the Web Shell, `CONNECT` tunnels) are counted by the gateway itself, because `http.Server.Shutdown` does not wait for them.
- **At the bound** the remaining sessions end with `sshgateway.ErrGatewayShutdown`: a Web Shell gets the `timeout` end reason ("the session reached its time limit"), native SSH a closed connection, and both an audit end row (`failed`). They get 10 s to say so; a stream that ignores its context (an egress `CONNECT` splice) dies with the process. A second SIGTERM ends every session at once (inside the accept window too, which it also ends), and a listener that fails ends the process at once, as before.

The process exits as soon as the window has passed and the last session has ended, so a pod with no open session leaves 10 s after its SIGTERM. The Deployment rolls `maxSurge: 1`, `maxUnavailable: 0` with `terminationGracePeriodSeconds: 3660` (the window plus the bound plus a margin; `scripts/gitops-validate.sh` keeps them in lockstep and refuses a missing window). Terminating pods are not counted in `status.replicas`, so `deploy.yml`'s `rollout status` returns once the new pods are available while the old ones drain (checked on the local cluster, Kubernetes 1.36, 2026-11-18: 3 s with two old pods still terminating). Each release can therefore leave up to two old pods for up to an hour beside the two new ones (about 25 MiB each in production). A platform node drain waits for a draining gateway pod in the same way, for at most the grace period.

A draining old pod runs against the new release's database grants and schema for up to an hour. `scripts/ssh-gateway-db-role.sh` replaces the role's grants with the release's `dbrole.sql` in one transaction; every change to that file so far added privileges, so an old pod keeps everything it uses. A release that removes a grant or a column an older gateway reads must wait for the old pods to finish (or accept that their audit end rows may fail).

Render parity: Render closes a service's SSH sessions when "Render is scheduled to perform maintenance on underlying infrastructure that enables SSH connections. In this case, Render gives existing connections one hour before automatically closing them" ([render.com/docs/ssh § Automatic session closure](https://render.com/docs/ssh), read 2026-11-17). The ssh-gateway is that infrastructure, so its release gives open sessions the same hour. Moving a session to another gateway pod is not attempted; it ends at the bound, as on Render.

### Sessions across an edge roll (w6/164)

Native SSH reaches the gateway through Traefik's `ssh` entrypoint, and every change to the edge's values or plugins rolls Traefik. Until w6/164 an old Traefik pod closed every SSH stream it carried 10 s after its `SIGTERM` (Traefik's default `transport.lifeCycle.graceTimeOut`), and the client printed `Connection to ssh.bex.co closed by remote host.`. That included sessions already inside a gateway pod's hour: w6/153's held sessions ended this way at the rolls of 21:02Z 2026-11-20 and 02:27Z 2026-11-21. Production now gives the edge's hop the same hour:

- **The `ssh` entrypoint drains for an hour.** The production Traefik values set `ports.ssh.transport.lifeCycle.graceTimeOut: 3600s` and `deployment.terminationGracePeriodSeconds: 3660`. At `SIGTERM` Traefik closes every listener at once, so a draining pod serves no new connection. Its HTTP entrypoints keep their default 10 s. The SSH streams it already carries run until they end or the hour passes, and the process exits as soon as the last one ends, so a pod with no open SSH stream still leaves about 10 s after its `SIGTERM`. This was checked against `traefik:v3.7.17` with a raw TCP route on 2026-11-23. Without the setting, a held stream closed 10 s after `SIGTERM`. With it, the stream ran to the bound, a new connection during the drain was refused, and the process exited the moment the held stream closed.
- **The pods spread by a topology spread, not by required anti-affinity.** kube-scheduler counts a terminating pod for inter-pod anti-affinity, but not for a topology spread (`pkg/scheduler/framework/plugins/podtopologyspread/common.go`, "Bypass terminating Pod"). Under the old required anti-affinity, a roll on the three-node platform pool would start its first new pod on the spare node. Its second would wait `Pending` behind the first draining pod for up to the hour, and the edge would serve two releases meanwhile. `topologySpreadConstraints` (hostname, `maxSkew: 1`, `DoNotSchedule`) still keeps one live pod per node, and the second new pod starts beside the draining one.
- **Prometheus scrapes Ready Traefik pods only.** A draining pod's metrics entrypoint is closed. If it were still scraped, its `up` of 0 (job `traefik`), or its series ending inside the next hour (both Traefik jobs), would fail that next hour's HTTP and WebSocket egress windows in `egressquery.Health` for every service, and the usage rollup skips a failed window. The roll's own hour fails both windows anyway, as it did before.
- **The local hostNetwork edge keeps the default.** It rolls with `Recreate`, which starts the new pod only after the old one exits, so an hour's drain there would be an hour with no edge.

`scripts/edge-ssh-drain-validate.sh` keeps all four over the rendered releases (run by `scripts/gitops-validate.sh`; `scripts/edge-ssh-drain-validate.test.sh` proves each failure).

A roll leaves a draining pod's node without a Ready edge pod: the second new pod starts beside the first draining one, so the second draining pod's node has none. The load balancer's `:22` health check then marks that node unhealthy (with `:80` and `:443`). Hetzner does not document what happens to an established connection to an unhealthy target, so w6/164 checked it on production on 2026-11-24. The load balancer sends that node no new connection but keeps the ones it already carries. Two sessions were held on each old pod through a `rollout restart`. The two on the pod whose node stayed unhealthy for its whole drain ticked every 10 s for the hour, like the two beside a new pod. Each session ended 3600 s after its own pod's `SIGTERM`. So the edge needs no Ready pod on every draining node.

Render parity: Render's hour covers the "underlying infrastructure that enables SSH connections" ([render.com/docs/ssh § Automatic session closure](https://render.com/docs/ssh), read 2026-11-21). The edge's `:22` hop is part of that infrastructure, so its roll gives open sessions the same hour as a gateway release.

### Pre-authentication faults are distinguishable from authorization refusals (w6/m132)

The paragraph above governs failures **at and after** authentication, and its non-disclosure is a deliberate security boundary. A **pre-authentication** fault — the connection never completing the version exchange and key exchange, so the client never receives a `KEXINIT` — is a different case, and it is **not** a security boundary: it leaks nothing about a key, a service, or a role because it happens before any of those are consulted. Conflating the two is what let the w6/m132 regression (a Traefik PROXY header the gateway was misconfigured to not strip, fed into the version exchange) look like every other quiet refusal for weeks.

The honest-failure decision is therefore: **the two are kept structurally distinguishable, and the pipeline fix plus observability — not a new in-band SSH message — carries it.** A client that reaches authentication and is refused sees the transport succeed and the auth attempt fail (`Permission denied (publickey)`); a client hitting an infrastructure fault never gets a `KEXINIT` and its handshake dies before authentication. There is no protocol-legitimate way to say more before `KEXINIT`: SSH forbids application messages (a `SSH_MSG_DISCONNECT` reason, a banner) until the transport is established, and inventing one would mean forking the handshake. Server-side, the `bex_ssh_gateway_handshakes_total{result}` counter separates `established` from `failed` with no subject, address, or cause — so a dead edge is loud in metrics and the always-on liveness synthetic below fails, while `authentications_total` (which `ADR035:106` governs) stays untouched and its opacity unchanged.

## Threat model

- **Cross-workspace target guessing:** stable service ids resolve through `AuthorizeApp`; the resource's tenant label determines the OpenFGA object.
- **Key ambiguity:** fingerprint uniqueness permits exactly one subject per public key.
- **Deleted key races:** every new handshake reads the database before accepting the offered key and rechecks it after signature verification, before target authorization; no key cache survives deletion.
- **Pod-name confusion:** clients receive a derived instance id, and resolution re-lists label-selected Ready pods rather than accepting a raw pod name.
- **Stale rollout target:** pod container image must match observed active image and the pod must be Ready and non-terminating.
- **Command injection into gateway/Kubernetes:** the SSH command is passed as one `/bin/sh -lc` argv element; it is never evaluated by the gateway host or embedded into a URL.
- **Session exhaustion:** bounded handshake/session durations and global/per-identity counters reject excess connections. Sandbox exec and file streams are counted apart (w22/m623), so a burst of sandbox commands cannot take native SSH's 100 slots; their own pool bounds what one replica holds.
- **Compromised gateway:** namespaced pod/exec RBAC limits the Kubernetes blast radius to the configured App namespace; it cannot read platform Secrets. This remains a powerful tenant-workload privilege, which is why the binary and ServiceAccount are isolated. **Database blast radius (w7/m56):** the gateway no longer shares bex-api's full-privilege `bex-db-app` credential. It connects as the scoped `bex_ssh_gateway` Postgres role — `SELECT` on `ssh_keys`/`tenants`/`tenant_members` (authenticate the caller + resolve their workspace/membership), `INSERT`/`UPDATE` on its own `ssh_sessions`, `SELECT`/`INSERT`/`DELETE` on `shell_ticket_nonces`, and `INSERT` on `audit_events` — and **nothing else**. A stolen gateway credential therefore cannot read billing/usage (`stripe_billing_events`, `usage_hourly`), tenant credentials (`registry_credentials`, `git_connections`, `sandbox_tenant_keys`), or app/domain/deploy rows: those tables are never granted, and a fresh role has no default table access. This is enforced by Postgres, not by the narrow Go `Store` interface — verified negatively (a `SELECT` on the sensitive tables is refused with SQLSTATE `42501`) by the CI-run `TestGatewayScopedRoleAllowsOwnSurfaceDeniesTheRest` (`internal/sshgateway/dbrole/dbrole_integration_test.go`), which provisions the role from the same `internal/sshgateway/dbrole/dbrole.sql` the production `scripts/ssh-gateway-db-role.sh` applies (one DDL source, so the tested and shipped boundaries cannot drift). The gateway is a least-privilege _consumer_ of the control-plane store: it never runs migrations or the ownership check (those stay with bex-api on `bex-db-app`), which is what lets it run under a role with no DDL privilege. Note that resolving SSH authorization legitimately needs tenant/membership reads, so those are granted (not denied) — the boundary is money + credentials + resource data, which the gateway never touches.
- **Host-key substitution:** stable out-of-band custody and published fingerprints make unexpected replacement visible to OpenSSH.

## Browser Web Shell

Render's Shell page hosts an in-browser terminal alongside the copy-ready `ssh` command. bex matches this (w2/m55) without weakening the isolation above: the browser terminal rides the **same** isolated gateway, `KubeExecutor`, Render-compatible instance targeting, `AuthorizeApp(can_operate)`, session caps, and content-free audit as native SSH. It adds only a browser transport and a session-authenticated ticket path. It does **not** give bex-api `pods/exec`, and it never puts an SSH private key in the browser.

### Connection path

1. In the dashboard Shell page the authenticated caller (a Kratos session, HttpOnly cookie) requests a short-lived **exec ticket** from bex-api: `POST /v1/services/{id}/shell-ticket` (GraphQL `createShellSession`). bex-api runs `AuthorizeApp(can_operate)` and the same eligibility gate as `sshAddress` (paid, non-suspended web/private/worker) plus a live release (an active revision and its image, whatever the latest deploy is doing; w4/m352), then returns `{ticket, url, expiresAt}`. The mint does not list pods: whether a Ready pod of the serving release exists is decided once, by the gateway's connect-time `ResolveSSHSession`. Every refusal is a `409` naming its own blocker (w4/506), and the dashboard shows that sentence.
2. The ticket is an HMAC-SHA256-signed token over `{subject, serviceId, instanceId?, issuedAt, expiresAt, nonce}`, signed with `BEX_SHELL_TICKET_SECRET` — a secret shared only between bex-api and the gateway. bex-api can mint it; it cannot exec. The TTL is short (seconds) and the nonce makes it single-use **across every gateway replica** (w1/042 L7): each redemption atomically claims the nonce in the shared control-plane store (`shell_ticket_nonces`, `INSERT … ON CONFLICT` — exactly one replica wins; expired rows are pruned by the next claim), backed by a per-process map as the cheap same-replica first line. A store error refuses the ticket — the session-audit write requires the same database, so this adds no availability dependency.
3. The browser opens a WebSocket to the gateway at `url` (`wss://…/shell`, Traefik-terminated to the gateway's plain-HTTP `BEX_SHELL_WS_ADDR`), carrying the ticket exclusively in a `Sec-WebSocket-Protocol` entry (`bex.ticket.<ticket>` alongside the `bex.shell` marker, which is the only protocol the gateway ever selects) — never in the URL, whose `RequestPath` Traefik's access log keeps while headers are dropped (w1/042 L8). Query-string tickets are rejected. The gateway verifies the ticket signature, expiry, and single-use, attaches `core.Identity{Subject}`, and calls the same `ResolveSSHSession` used by native SSH — so the gateway **re-authorizes** `can_operate` against the App's workspace and re-selects a Ready, current-image, current-revision pod. bex-api's authorization is not trusted transitively.
4. One WebSocket maps to one `pods/exec` stream in the `app` container (`/bin/sh`, TTY). Browser stdin/stdout are binary WebSocket frames; JSON text frames carry terminal resize (mapped to the same `TerminalSizeQueue`) and the terminal exit/error. The gateway never logs or persists the stream.

### Boundary and audit

The re-drawn boundary is: **terminal bytes reach the browser, but only over an authenticated, `can_operate`-gated gateway WebSocket, and only for an already-running instance.** `pods/exec` stays confined to the gateway ServiceAccount; bex-api gains no exec permission (the structural RBAC test still guards this). A browser session counts against the same global/per-identity caps and writes the same `ssn-…` `ssh_sessions` audit row (subject, workspace, service, instance, remote address, start/end, result) — with **no** command, argv, or terminal-content field. Metrics stay bounded exactly as for SSH.

Unset `BEX_SHELL_TICKET_SECRET` (on bex-api or the gateway) disables the Web Shell: bex-api returns 503 for the ticket verb and the gateway does not start its WebSocket listener. That is the byte-identical default; native `ssh` is unaffected.

### A second target: an agent session's sandbox (w10/m615)

The ticket names one of two targets, never both: a service (`ServiceID`, optionally `InstanceID`), or an agent session (`SessionID`, an `ags-…` id), the session page's Terminal ([ADR054 D10](ADR054-open-in-zed.md#d10--the-session-pages-terminal-wakes-a-closed-session-w10m615-2026-11-23)). The gateway routes a ticket by the field it names, never by an id's prefix: a service ticket reaches `apps.Service.ResolveSSHSession` exactly as above, and a session ticket the agent-session resolver native SSH uses for `ags-…` logins (`can_view_sensitive` on the session, ADR054 D2). bex-api mints a session ticket through `POST /v1/agent-sessions/{id}/shell-ticket` (GraphQL `createAgentSessionShellSession`), starting a closed sandbox as the caller through `Service.Resume`; the gateway holds the WebSocket while the sandbox starts (`starting` and `ready` control frames), up to the start's own 16-minute ceiling, then bridges `/bin/sh` in the sandbox container. A session's Terminal is capped like an SSH connection to a session (`BEX_SSH_SESSION_TIMEOUT`), and its open `web_shell` row keeps the sandbox from its idle close as an editor's SSH row does. Nothing on the service path changed: same frames, same refusals, no cap.

### Production activation

The Web Shell rides the same isolated gateway as native SSH, so it inherits that fail-closed sequence and adds one edge route and one shared secret. In order: deploy the image and manifests (they already wire `BEX_SHELL_TICKET_SECRET` into **both** bex-api and the gateway as an _optional_ Secret ref, set the gateway's `BEX_SHELL_WS_ADDR` to `:8080`, and set bex-api's `BEX_SHELL_WS_URL` to `wss://ssh.bex.co/shell`); confirm the gateway Service exposes the plain-HTTP shell port (8080), the `ssh-shell` Ingress publishes `wss://ssh.bex.co/shell` with a valid cert-manager TLS cert, and the gateway NetworkPolicy admits Traefik → 8080; and only then install the shared HMAC key with [`scripts/shell-ticket-secret.sh`](../scripts/shell-ticket-secret.sh) (the same `bex-shell-ticket` Secret both Deployments mount). Installing that Secret is the single activation flip: before it, `createShellSession` honestly 503s ("web shell transport not configured") and the gateway starts no WebSocket listener; after it, the script rolls both Deployments and the dashboard terminal connects. `BEX_SHELL_WS_URL` is static — the Secret, not the URL, gates the feature — so the URL may be present before the edge is reachable without ever minting a redeemable-nowhere ticket.

**Activated 2026-09-08 (w2/m90).** Production already had the Secret, the `:8080` listener, and Ingress `bex-ssh-shell`; this milestone verified the public refusal shape, recorded a live `dashboard.bex.co` Web Shell session plus the fail-closed matrix, and added the always-on ticketless WS probe (`scripts/shell-ws-probe.sh` on `ssh-edge-liveness.yml`) plus a `gitops-validate.sh` lockstep check so the edge cannot die silently again. Sanitized evidence: `.pm/w2/done/m90/evidence/2026-09-08-production-activation.md` (w2/m90 evidence, purged 2026-11-04).

## Explicit non-goals

This ADR does not authorize ephemeral shell instances, `--ephemeral`, one-off jobs, cron shell access, hosted sandboxes, SFTP/SCP, forwarding, agent forwarding, direct TCP/Unix-socket channels, shell installation, or an sshd sidecar. The in-dashboard [Browser Web Shell](#browser-web-shell) attaches to an already-running instance and is in scope; ephemeral and hosted execution remain excluded. A refused feature refuses by name: `POST /v1/services/{id}/ephemeral-shell`, the route the pinned CLI's `ssh --ephemeral` calls on a paid service, answers 410 `EPHEMERAL_SHELLS_UNSUPPORTED` after the same authorization as `jobs create`, and its message points to plain `bex ssh <service>` (w8/304). Until then the route did not exist, and the CLI printed "failed to create ephemeral shell: not found".

Deterministic tests cover parsing, canonical fingerprints, duplicate/foreign ownership, REST/GraphQL/MCP parity, service eligibility, stale-revision/non-Ready filtering, any/specific-instance resolution, a real in-process SSH handshake, PTY resize, exit status, deleted-key and forbidden-target denial, forwarding rejection, session caps, authenticated-idle timeout/release, a service shell outliving the session timeout, the keepalive closing a silent client, and content-free audit writes.

### Regression: the PROXY-protocol receiver half was never deployed (w6/m132)

That 2026-07-17/18 acceptance was real, and then nothing re-checked it — so a regression six weeks later went unnoticed until the 71st `/qa-find-bugs` run (2026-08-28) found `ssh.bex.co:22` writing its `SSH-2.0-bex` banner and then never sending `KEXINIT`, for **every** target alike. The cause was a half-completed change: w4/m82 (2026-08-16) turned on `proxyProtocol: version: 2` on the ssh `IngressRouteTCP` so Traefik forwards the real client address, but shipped the gateway Deployment **without** the matching `BEX_SSH_PROXY_PROTOCOL_TRUSTED_CIDRS`. With no trusted CIDR, `proxyproto.Wrap` is a no-op, so the un-stripped binary PROXY v2 header is fed straight into the SSH version exchange; Go's `readVersion` discards it as non-`SSH-` preamble and then blocks waiting for a valid version line until the 10 s `BEX_SSH_HANDSHAKE_TIMEOUT` closes the socket. `KEXINIT` is only sent **after** a completed version exchange, so it never arrives — the exact reported symptom. The sibling `pg-sni-proxy`/`kv-sni-proxy` never regressed because they set their `BEX_PROXY_PROTOCOL_TRUSTED_CIDRS`; only the SSH gateway's half was missing.

The fix sets `BEX_SSH_PROXY_PROTOCOL_TRUSTED_CIDRS` to the cluster pod CIDR on the gateway Deployment (Traefik is its only admitted `:2222` peer per `networkpolicy.yaml`, so trusting the pod range is safe), and a `scripts/gitops-validate.sh` check now fails CI whenever the route sends a PROXY header without the Deployment setting the matching trust — the two halves can no longer drift silently. Two guards make the class detectable rather than silent: the manifest lockstep check above, and an always-on liveness synthetic — the credential-free KEXINIT probe (`internal/sshgateway/nativessh.ProbeKEXINIT`, driven by `scripts/ssh-kexinit-probe.sh` on the scheduled `ssh-edge-liveness.yml`) — that fails within hours of a dead edge instead of on the next human's manual check. Reproduced live under that probe on 2026-08-28: `github.com` and `gitlab.com` sent `KEXINIT`, `ssh.bex.co` sent its banner then timed out. Live re-verification after the fix's production rollout (the raw probe and the full `scripts/ssh-verify.sh` matrix) is owed on deploy.

The verifier requires the API URL/token, a disposable private-key file, and the published host-key fingerprint. By default it creates and cleans up a paid, shell-capable two-replica service; an explicitly supplied existing service must be disposable because the matrix restarts, suspends, resizes, and temporarily rolls it to a shell-less image. The default fixture uses one healthy port for both its shell-capable BusyBox server and the shell-less whoami rollout, so a real Ready redeploy must replace the attached pod before the exit-126 check. Readiness also requires a live deploy and retries transient edge errors within its deadline. The matrix registers only the derived public key, pins the observed TCP/22 host key, checks runtime environment, PTY resize, any- and specific-instance raw SSH, exit status, stale-instance denial, separate restart- and redeploy-driven stream closure, suspended/free/shell-less behavior, and unknown/deleted keys. `BEX_RENDER_CLI_VERIFY=1` adds interactive CLI checks by service name, service id with the **Any instance** picker option, and direct complete instance id; the three-selector supplement passed against production on 2026-07-18. `BEX_RENDER_CLI_BIN` can pin an exact downloaded release binary instead of relying on `PATH`. The script supplies `RENDER_HOST`, `RENDER_API_KEY`, `RENDER_WORKSPACE`, and an isolated `RENDER_CLI_CONFIG_PATH` to the unmodified binary without persisting their values, pins the OpenSSH host key/private key explicitly, and asserts the destination the CLI selected. The current official release, `render-oss/cli` v2.21.0 at `c398207`, still has an upstream defect in both instance-picker callbacks (they drop the selected instance id), so exact-replica acceptance uses the CLI's supported full-instance-id argument instead of claiming that broken menu path works. `BEX_SSH_VERIFY_FULL_MATRIX=1` additionally requires out-of-band viewer, foreign-workspace, static, and cron fixtures, because the primary acceptance identity must not be able to manufacture its own weaker role or foreign workspace.
