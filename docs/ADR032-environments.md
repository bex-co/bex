# Environments: named subsets of a Project's services

`internal/environments` is the second half of Render's Projects & Environments grouping feature, layered on top of `internal/projects` (w1/m31, which shipped named Projects — a workspace-scoped label services opt into — but deliberately scoped out Environments as "a much larger architectural change" for a later milestone). This is that later milestone: a Project's services can now be further grouped into named **Environments** (e.g. staging/production), readable and filterable over REST, GraphQL, and MCP.

## The shape

One feature package, three thin adapters, deliberately mirroring `internal/projects`' own shape field-for-field so the two grouping features read as one consistent system rather than two independently-designed ones:

- **`lego/backend/internal/environments`** — the verbs (`service.go`): `List(projectID)`, `Get(id)`, `Create(projectID, name)`, `Rename(id, name)`, `Delete(id)`, `SetServices(id, serviceNames)` (full-replace, not incremental add/remove — the same PUT-replace-all shape `projects.Service.SetServices` chose). Every verb starts with `s.Authorize` (satisfying `TestAuthzGuardsEveryVerb`'s reflection sweep — `internal/projects` itself is not in that sweep, an existing gap this feature doesn't inherit) before a `requireProject`/`requireEnvironment` fetch-then-`AuthorizeOn` step resolves the actual tenant to check against, the two-gate pattern `apps.Service.Get`+`GetApp` established for k8s-CR resources, adapted here for Postgres rows.
- **`rest.go` / `graphql.go` / `mcp.go`** — REST `GET/POST /v1/environments` (required `?projectId=` filter, matching Projects' required `?ownerId=`) + `GET/PATCH/DELETE /v1/environments/{id}` + `PUT /v1/environments/{id}/service-links`; GraphQL `environments(projectId:)`/`environment(id:)` queries + `create/rename/deleteEnvironment`/`setEnvironmentServices` mutations; MCP six tools (`list_/get_/create_/rename_/delete_environment`, `set_environment_services`) — **full read+write**, not read-only: Projects' own MCP surface ships full CRUD (create/rename/delete/set-services), so Environments matches that precedent rather than the originally-scoped "read-only MCP" plan, for consistency between the two sibling features.
- **`lego/backend/internal/store/environments.go`** — the control-plane Postgres table (`0019_environments.up.sql`): a nullable `environment_id` FK column added to `apps`, the exact shape `0014_projects.up.sql` set for `project_id` (not a join table — a service belongs to at most one environment at a time, reassigning it just moves the column).

## Assigning to an environment also joins the project

Render's own model treats "in an environment" as "in that project" — an environment is scoped _inside_ a project, not a parallel grouping. So `SetEnvironmentServices` stamps **both** `apps.environment_id` and `apps.project_id` in the same update; a caller doesn't need two calls (`setProjectServices` then `setEnvironmentServices`) to get a service showing up in both the project's and the environment's service lists. Verified live: assigning a service to an environment makes it appear in `GET /v1/projects/{id}`'s `serviceIds` too, with no separate project-assignment call.

The reverse isn't automatic: removing a service from its project via the independent `setProjectServices` verb (which knows nothing about environments) can leave a stale `apps.environment_id` pointing at an environment of a project the service is no longer in. `ListEnvironmentServices` defends against this by filtering on **both** `environment_id` and `project_id` together, so a drifted row never surfaces as a false membership — but the `apps.environment_id` column itself isn't proactively cleared by `setProjectServices` (that would mean threading environments-package knowledge into the already-shipped, independently-authored projects package). Documented here as a known, narrow edge case rather than silently left unexplained.

## Why not read/write forward pointers on `AppView`

A service's own view (`list_services`, `GET /v1/services/{id}`) does not carry `projectId`/`environmentId` fields. This mirrors `internal/projects`' own precedent exactly (it never added `projectId` to `AppView` either) — `internal/apps`'s reads come entirely from the Kubernetes App CR, while project/environment membership lives only in the control-plane Postgres `apps` table (never projected onto the CR). Adding a forward pointer would mean wiring a NEW kind of Postgres-store lookup into `apps.Service`'s otherwise CR-only read path, keyed by the CR's `store.LabelAppID` label back to the control-plane row — a real, first-of-its-kind integration this milestone deliberately did not take on, to keep the change composable with (not a rework of) the already-shipped Projects code. The dashboard already works around this by joining `services` + `projects[].serviceIds` client-side (`dashboard/src/routes/index.tsx`); an Environments-aware version of that same join is the natural follow-on, not a regression introduced here.

## REST's `ErrEnvironmentsUnavailable` → 503 mapping

`environments.ErrEnvironmentsUnavailable` (returned when `BEX_CP_DB_URI` is unset) is a package-local sentinel, not one of `core`'s registered `Err*Unavailable` values — `core` is the leaf kernel every feature imports and cannot import a feature package back to register one directly (the same reason every other `…Unavailable` sentinel, e.g. `core.ErrWorkspacesUnavailable`, lives IN `core` instead). `internal/projects` has this exact same local-sentinel shape (`projects.ErrProjectsUnavailable`) and, on inspection, its REST fragment passes it straight to `core.WriteErr` — which doesn't recognize it, so it currently falls through to a bare 500 rather than the documented 503-for-unavailable convention. `internal/environments/rest.go` adds a small local `writeErr` wrapper that checks for `ErrEnvironmentsUnavailable` first and maps it to 503 before delegating to `core.WriteErr` — fixed for this feature's own REST surface only; `internal/projects`' equivalent gap was left alone (out of scope for a change layered on top of already-shipped code) but is flagged here for whoever picks it up.

## Enforcement (the definition of done)

Verified live against the CAPD mock cluster (`scripts/environments-verify.sh`, mirroring `events-verify.sh`'s harness — bex-api on the host against the real cluster's App CRD + operator, a throwaway local Postgres for the control-plane store so it never touches the shared `bex-db`'s live workspace state): three services created in one workspace, grouped into a project with two environments (two services in staging, one in production), then read back and cross-checked on all three surfaces — REST (`GET /v1/environments/{id}` lists its assigned service names, `GET /v1/environments?projectId=` scopes the list, `GET /v1/projects/{id}` shows the auto-joined membership), GraphQL (`environments(projectId:)`, `environment(id:)`), and MCP (`list_environments`, `get_environment`, `get_project`, via a real streamable-HTTP client session) — all agreeing, plus the corrected store-less 503 case.

## Known divergence from Render / deliberate scope

- **No dashboard UX.** REST/GraphQL/MCP only, matching Projects' own scope boundary and this milestone's.
- **No forward pointer on a service's own view** — see above; a follow-on, not an oversight.
- **Full-CRUD MCP, not read-only** — a deliberate consistency choice with the already-shipped Projects MCP surface, diverging from this feature's own original "read-only" plan.
- **No protected-environment ACLs** (Render's `protectedStatus`/`networkIsolationEnabled`/`ipAllowList`) — out of scope, same boundary Projects itself drew.
