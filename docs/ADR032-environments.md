# Environments: named subsets of a Project's resources

`internal/environments` is the second half of Render's Projects & Environments grouping feature, layered on top of `internal/projects` (w1/m31, which shipped named Projects — a workspace-scoped label resources opt into — but deliberately scoped out Environments as "a much larger architectural change" for a later milestone). This is that later milestone: a Project's services, managed Postgres databases, Key Value instances, and environment groups can now be further grouped into named **Environments** (e.g. staging/production), readable and filterable over REST, GraphQL, and MCP.

## The shape

One feature package, three thin adapters, deliberately mirroring `internal/projects`' own shape field-for-field so the two grouping features read as one consistent system rather than two independently-designed ones:

- **`lego/backend/internal/environments`** — the verbs (`service.go`): `List(projectID)`, `Get(id)`, `Create(projectID, name)`, `Rename(id, name)`, `Delete(id)`, plus full-replace membership verbs for services, databases, Key Value instances, and env groups (`SetServices`, `SetDatabases`, `SetKeyValues`, `SetEnvGroups`). Every verb starts with `s.Authorize` (satisfying `TestAuthzGuardsEveryVerb`'s reflection sweep); w4/m22 added `internal/projects` to that same shared inventory with a store fixture that lets its fetch-then-authorize verbs reach the authorization gate, closing the pre-existing exclusion this ADR originally called out. A `requireProject`/`requireEnvironment` fetch-then-`AuthorizeOn` step resolves the actual tenant to check against, the two-gate pattern `apps.Service.Get`+`GetApp` established for k8s-CR resources, adapted here for Postgres rows.
- **`rest.go` / `graphql.go` / `mcp.go`** — REST `GET/POST /v1/environments` (required `?projectId=` filter, matching Projects' required `?ownerId=`) + `GET/PATCH/DELETE /v1/environments/{id}` + full-replace `service-links`, `database-links`, `keyvalue-links`, and `env-group-links` routes; GraphQL has the corresponding queries and `setEnvironment*` mutations; MCP has matching `set_environment_*` tools — **full read+write**, not read-only. The REST list uses Render's `[{environment, cursor}]` pagination envelope and honors `name`, `projectId`, created-time, `ownerId`, and `environmentId`; `updatedBefore`/`updatedAfter` are named 400s because the current Environment contract has no `updatedAt`. REST objects additionally expose Render's `databasesIds`/`redisIds` spellings alongside bex's cross-surface `databaseIds`/`keyValueIds` names so the unmodified official CLI and existing bex clients both decode correctly. Render's object has no `ownerId` or timestamps; GraphQL's `ownerId`/`createdAt` are documented bex extensions, not REST omissions.
- **`lego/backend/internal/store/environments.go`** — the control-plane Postgres table (`0019_environments.up.sql`): a nullable `environment_id` FK column added to `apps`, the exact shape `0014_projects.up.sql` set for `project_id` (not a join table — a service belongs to at most one environment at a time, reassigning it just moves the column).

## Assigning to an environment also joins the project

Render's own model treats "in an environment" as "in that project" — an environment is scoped _inside_ a project, not a parallel grouping. So `SetEnvironmentServices` stamps **both** `apps.environment_id` and `apps.project_id` in the same update; a caller doesn't need two calls (`setProjectServices` then `setEnvironmentServices`) to get a service showing up in both the project's and the environment's service lists. Verified live: assigning a service to an environment makes it appear in `GET /v1/projects/{id}`'s `serviceIds` too, with no separate project-assignment call.

Project departures now clear incompatible environment state. The App store path clears `environment_id` and the environment projection (w4/m32). Postgres and Key Value clear their environment label and inherited IP layer in the same optimistic-lock patch as the project change (w7/m151). Their resource-owned allowlists are preserved. Assigning the same membership after authorization performs no write. Environment assignment joins the project first, then assigns the environment and its inherited rules.

## Datastore deletion and stale placement (w7/m151, 2026-09-21)

Deleting an environment detaches its Postgres and Key Value members while preserving their parent-project membership and resource-owned IP rules. Deleting a project leaves its surviving datastores unassigned. Cleanup finishes before deleting the grouping row; a failed cleanup leaves that row available for retry. Each datastore cleanup compares the expected grouping id against the current resource and uses an optimistic-lock patch, so retry cannot erase a concurrent valid reassignment or its inherited rules. Environment IP-rule fan-out checks the expected environment in the same way, so a stale fan-out cannot reapply policy after a departure. These operations are not distributed transactions: earlier members can already be detached when a later operation fails.

The existing control-plane reconciliation pass also repairs provably stale datastore references: a missing project clears project/environment labels and inherited rules; a missing or incompatible environment clears only environment membership and its inherited rules. Repairs are idempotent and preserve the resource-owned allowlist. They require a canonical workspace namespace, matching datastore ownership labels, a local tenant record and the current control plane's managed hosting namespace. Foreign groupings, shared legacy namespaces, ambiguous ownership and lookup failures are retained and reported for operator investigation; this does not adopt foreign resources. Each pass bounds and caches its grouping lookups, and concurrent changes conflict instead of being overwritten.

**Parity boundary:** bex's preserve-and-detach deletion behavior is intentional. Render's REST API requires an [empty environment](https://api-docs.render.com/reference/delete-environment) and [empty project environments](https://api-docs.render.com/reference/delete-project), returning 409 otherwise; its [dashboard deletion](https://render.com/docs/projects#modify-a-project) also deletes contained services. bex's per-kind full-replacement membership routes also differ from Render's [add](https://api-docs.render.com/reference/add-resources-to-environment)/[remove](https://api-docs.render.com/reference/remove-resources-from-environment) resource routes. These are explicit differences, not full Render lifecycle parity.

Local regressions cover both datastore kinds, retry/interruption/concurrent reassignment, and REST/GraphQL/MCP mutation and read consistency. Dashboard grouping views consume those GraphQL fields. The dated live dev-7 walkthrough remains blocked on shared VM capacity; no new live UI or cluster acceptance is claimed here.

## Create-time assignment and forward pointers (w2/m37)

Service, managed-Postgres, and Key Value creation now accept Render's optional `environmentId` on REST, GraphQL, and MCP. All nine adapter paths delegate to one `core.EnvironmentResolver` implementation in `internal/environments`: it resolves the Environment before creating anything, returns 404 for an unknown id and 403 for a known Environment in another workspace, and returns the parent Project id with the Environment policy. Omission preserves the previous ungrouped behavior. Assignment automatically joins the parent Project, matching the bulk membership verbs above.

Services stamp `bex.co/project` and `bex.co/environment` onto the App CR at birth and persist both ids on the control-plane row. `AppView` therefore reports `projectId` and `environmentId` directly on REST, GraphQL, and MCP without a second membership-list lookup. The same first-write rule stamps the project/environment labels on Database and KeyValue CRs. A network-isolated environment additionally stamps the App's `app.bex.co/network-isolation` label before the first pod can be reconciled.

The dashboard service, Postgres, and Key Value create flows share one Project/Environment selector. Choosing an Environment supplies its id and implicitly joins its parent Project; the server remains authoritative and rejects stale or foreign ids. An empty selection preserves ungrouped creation.

Blueprints use Render's separate YAML vocabulary: resources nested directly under `projects[].environments[]` receive the same first-write assignment, and resources under root `ungrouped:` receive none. A direct `environmentId` inside a Blueprint resource is rejected because it is not part of Render's Blueprint schema. Project/Environment rows declared by name are created or resolved before resource convergence; reapplying the stack preserves idempotence.

## Package-local unavailable errors → 503

`environments.ErrEnvironmentsUnavailable` and `projects.ErrProjectsUnavailable` (returned when `BEX_CP_DB_URI` is unset) are package-local sentinels, not `core` errors — `core` is the leaf kernel every feature imports and cannot import feature packages back to register them directly. Each REST fragment therefore has a local `writeErr` wrapper that checks its sentinel first and returns a Render-shaped 503 unavailable response before delegating every other error to `core.WriteErr`; w4/m22 added the Projects wrapper and closed the old bare-500 fallthrough this ADR originally flagged. GraphQL naturally carries the same sentinel as a resolver error and MCP as a tool error, rather than inventing HTTP status semantics for those transports. `TestUnavailableStoreAcrossAdapters` pins all three Projects paths.

## Enforcement (the definition of done)

Verified live against the CAPD mock cluster (`scripts/environments-verify.sh`, mirroring `events-verify.sh`'s harness — bex-api on the host against the real cluster's App CRD + operator, a throwaway local Postgres for the control-plane store so it never touches the shared `bex-db`'s live workspace state): three services created in one workspace, grouped into a project with two environments (two services in staging, one in production), then read back and cross-checked on all three surfaces — REST (`GET /v1/environments/{id}` lists its assigned public stable `srv-…` ids, `GET /v1/environments?projectId=` scopes the list, `GET /v1/projects/{id}` shows the auto-joined membership), GraphQL (`environments(projectId:)`, `environment(id:)`), and MCP (`list_environments`, `get_environment`, `get_project`, via a real streamable-HTTP client session) — all agreeing, plus the corrected store-less 503 case. Membership writes accept those public ids and retain legacy service-name compatibility; reads are canonical ids. w4/m22 separately drove the unmodified official Render CLI against dev-4 with a real seeded Project and Environment: `render environments <project-id> -o json` returned the populated Environment instead of a zero-valued record, while an unknown Project remained a specific nonzero-exit 404.

## Protected-environment ACLs (w6/m19)

Render's `protectedStatus`/`networkIsolationEnabled`/`ipAllowList` — deferred at this feature's original scope (see below) — shipped as a follow-on milestone, `w6/m19`, closing the gap `docs/ADR018-render-parity.md`'s Environments row flagged. Full-replace, not partial-patch (`SetACL(id, protectedStatus, networkIsolationEnabled, ipAllowList)` — the same convention `SetServices`/postgres's `SetIPAllowList` already use), over REST (`PATCH /v1/environments/{id}/acl`), GraphQL (`setEnvironmentACL`), and MCP (`update_environment`, which w1/m71 folded `set_environment_acl` into).

`w4/017` then aligned the **standard** REST create/update wire shape with Render's: `POST /v1/environments` and `PATCH /v1/environments/{id}` accept the ACL triple directly, with `ipAllowList` as Render's `[{cidrBlock, description}]` objects, reads echoing the object form. Since `w4/m24` the `description` **persists** (the `environments.ip_allow_list` column is a jsonb array of `{cidrBlock, description}` entries — migration 0034), and the ACL fan-out onto member Database/KeyValue CRs carries descriptions along. Migration 0053 normalized the last pre-m24 JSON strings and added a structured-row constraint before w1/m56 retired the compatibility decoder. The PATCH is per-field partial (absent fields untouched, `networkIsolationEnabled: false` appliable — pointer-decoded), merged by the handler into the full-replace `SetACL` core; a bad ACL on POST is validated before the row is created, so a 400 never leaves an orphan environment. `w6/m33` lifted create into one neutral `CreateWithACL` service verb: GraphQL `createEnvironment` and MCP `create_environment` now accept the same ACL triple and object-form allowlist, so every adapter validates before create and an invalid CIDR leaves no orphan. The bex-native `/acl` route accepts the same structured entries; the standalone GraphQL/MCP Set-ACL operations retain their product-neutral string-list `ipAllowList` plus the description-carrying `ipAllowListEntries` sibling (extension, not replacement). `w4/m30` moved the partial-update merge (name rename + the ACL-triple merge, including the pre-migration empty-`protectedStatus`-defaults-to-`unprotected` rule) out of the REST handler and into one core `Update(ctx, id, patch)` verb in `environments/service.go`, so it exists exactly once instead of being reimplementable per adapter; REST `PATCH /v1/environments/{id}` now just decodes and calls it, and GraphQL `updateEnvironment` / MCP `update_environment` ride the same verb as new partial-update siblings to the existing full-replace `setEnvironmentACL` (whose MCP half, `set_environment_acl`, w1/m71 folded into `update_environment`) (all three surfaces proven to merge identically by `TestUpdateAcrossRESTGraphQLAndMCPProduceIdenticalMerges`).

- **`protectedStatus`** (`protected`/`unprotected`, default `unprotected`) arms `internal/apps`' own destructive-verb guard (`apps/protection.go`): `Delete`, `Suspend` (not `Resume` — a protected environment blocks taking availability away, not restoring it), and an existing service's stack-apply override (`applyCreate`, reached via `DeployStack`/the MCP `deploy` tool — never the git-push auto-deploy pipeline's webhook-triggered `redeploy`, which stays unauthenticated-by-webhook-signature and ungated by design) all refuse on a protected member unless the caller echoes back `apps.ProtectedConfirmation(verb, name)` — the exact confirm-phrase shape `workspaces.DeleteConfirmation` established. The phrase rides the request context (`core.WithConfirm`/`core.ConfirmFrom`, package-local to `apps`) rather than a new parameter, since these verbs are reached through REST/GraphQL/MCP forwarding helpers shared with ungated verbs (Restart, Resume) that all share a fixed `func(ctx, name string)` shape.
- **`networkIsolationEnabled`** is projected onto every member App CR as a NEW label, `core.LabelNetworkIsolation` (`app.bex.co/network-isolation`) — present only while isolation is on, written/cleared by `environments.Service` itself (`SetServices` on membership change, `SetACL` on the flag's own toggle, `Delete` on environment teardown) via the same `AuthorizeApp`-then-merge-patch seam `apps.Service` uses, not the control-plane reconciler. **Not** `core.LabelEnvironment` — the concurrently-shipped `w6/m20` (below) landed that name first for a DIFFERENT, unconditional purpose (Database/KeyValue environment membership); this label needed its own name since its semantics differ (conditional on a policy flag, App-only). The operator's `reconcileNetworkPolicy` (`app_controller.go`) scopes that App's ingress/egress "same-scope" peer selector to `core.LabelNetworkIsolation` instead of `app.bex.co/workspace` when the label is present — denying traffic to/from the rest of the workspace, not just outside it. DNS, Traefik ingress, and public-internet egress are unaffected either way (infrastructural, not "other Apps").
- **`ipAllowList`** fans out to every Database/KeyValue whose `core.LabelEnvironment` (the `w6/m20` label, below) names this environment (`propagateIPAllowList`, via each's `SetEnvironmentIPAllowList`) — the same membership `SetDatabases`/`SetKeyValues` manage. The inherited layer is separate from each resource's own allowlist; both layers remain enforced, and an environment-level change never overwrites resource-owned rules (w4/m28).

### What `protectedStatus` covers — the data plane too (w4/m127, 2026-09-21)

`w6/m19` built the guard for services and `w6/m37` extended it to Postgres and Key Value. Both asked only **which resources** it covers. A live matrix against a free Postgres and a free Key Value created into a fresh protected environment asked, for the first time, **which operations** — and found the answer incoherent:

```
suspendDatabase / suspendKeyValue / deleteDatabase / deleteKeyValue  → REFUSED   (the control: the guard was armed)
executeDatabaseQuery(allowWrites) CREATE TABLE / INSERT / DROP TABLE → ACCEPTED
setKeyValuePersistenceMode("off") · setKeyValueMaxmemoryPolicy(…)    → ACCEPTED
failoverDatabase · renameDatabase                                    → ACCEPTED
```

A protected environment refused to pause the database and permitted `DROP TABLE` inside it.

**Decision: protection covers what can destroy data, break identity, or interrupt availability — not merely the two verbs that stop the object.** The guarded set is now delete, suspend, **writable SQL through the console**, failover, rename, major-version upgrade, durability (`persistenceMode`), and eviction (`maxmemoryPolicy`). Resume stays exempt, as it always has: protection blocks taking availability away, not restoring it. A read-only query is never gated — protection has no reason to stop the one console use that cannot lose anything.

The rule, so the next field is placed without another live matrix: **if the verb can lose data, change what the resource IS, or take it offline, it needs the phrase.** A plan change is billing, an allow-list edit is a firewall — neither qualifies.

**The confirmation on the data plane is an accident guard, not a security boundary, and is documented as one.** Writable SQL is already gated on a strictly stronger authorization pair than anything else in the product — both `can_create` and `can_view_sensitive`, re-asserted uncached at the sink (`postgres/query.go`, codex rounds 9 and 18) — so this adds no authority check. What it adds is a deliberate pause. A caller holding those two relations can read the connection string and run the same `DROP TABLE` over the wire, where no bex-api guard exists and none can: protection is a control-plane mechanism and the data plane is reachable without it. That makes the confirmation worth having, because the dominant failure is a mis-aimed console tab rather than a determined attacker — and worth describing accurately rather than implying a containment it cannot deliver.

Mechanically it is the same shape as every other guarded verb: the phrase rides `core.WithConfirm` on the request context, `confirm` is an **optional** argument on the affected REST routes, GraphQL mutations and MCP tools (no verb gained a required one), and an unprotected resource is untouched. `gqlutil.PatchMutation`/`ArgMutation` thread it for every single-field setter, so a newly-guarded setter cannot ship without a way to confirm it.

### What `protectedStatus` covers on a service — the verbs, not just the resource (w4/m126, 2026-09-21)

`w4/m127` (above) settled _which operations_ the guard covers on a datastore. The same live hunt asked it of a service and found the mirror gap:

```
suspendService / deleteService                     → REFUSED   (the control: the guard was armed)
setImage / setRepo / setBranch                      → ACCEPTED
setStartCommand / setBuildCommand / setRootDir      → ACCEPTED
setDockerfilePath / setPreDeployCommand             → ACCEPTED
updateCronJob(command:)                             → ACCEPTED
```

A protected environment refused to pause the service and permitted anyone to replace the executable it runs. Worse than it reads: `setImage` mints **no** deploy — the image is staged and the documented "next deploy uses it" contract applies it later — so the change sits invisible in `imagePath` until an ungated `restartServer` or an automatic deploy rolls it out. And none of these verbs had a `confirm` argument at all, so the guard was not merely absent, it was unreachable.

**Decision: the same rule as the data plane — if the verb can lose data, change what the resource IS, or take it offline, it needs the phrase.** For a service, "what it is" is the code it runs. Three confirmation verbs join `delete`, `suspend` and the direct-deploy override:

| verb | covers |
| --- | --- |
| `repoint` | `image`, `repo`, `branch`, `registryCredentialId` — which code runs |
| `redefine` | build/start/pre-deploy commands, a cron's `command`, `dockerfilePath`, `rootDir` — how it is built and what it executes |
| `take offline` | **enabling** maintenance mode, which 503s every host |

One phrase per class, not per setter. The per-verb design exists so a confirm typed for a cheap verb cannot arm an expensive one; within a class the stakes are identical, and eleven near-identical phrases would be a worse UI without being a stronger control.

**The rule considered and rejected: "guard every verb that mints a release."** It is more mechanical — `patchFetched` already enumerates that set — and it fails on the finding that opened the milestone, because `setImage` mints no release. It would have missed the headline bug while gating a health-check-path edit that cannot hurt anyone.

**Deliberately left out, with reasons, so the omissions are decisions:**

- **`Resume`, `restartServer`, webhook auto-deploy** — unchanged, for the reasons already recorded above.
- **Disabling maintenance mode, and a URI-only edit** — restoring availability, the same reason `Resume` is exempt.
- **A cron `schedule`-only change** — _when_ the job runs, not _what_ it runs. The service layer already splits these two (`LifecycleOrCreate(command != nil)`), and the guard follows the same split.
- **`scaleService`** — the minimum is 1 replica, so scaling can never take the service offline. It is capacity, and capacity is billing.
- **`setPlan`, `setIdleTimeout`** — billing and an operational timer; neither redefines the service nor removes it.
- **`healthCheckPath`, `port`, `ipAllowList`, `renderSubdomainPolicy`, `autoDeploy`, `buildFilter`, `displayName`, notification settings** — reversible configuration with nothing to lose. A firewall edit is a firewall, per the datastore rule above.
- **Environment variables and secret files** — the honest borderline. They change the service's _configuration_, not its identity, and they are the single most-edited control in the product; gating them would mean a typed phrase on nearly every save in a protected environment, which trains people to type the phrase without reading it. Revisit only with evidence of a real incident, not on symmetry.

Mechanically identical to every other guarded verb: the phrase rides `core.WithConfirm` on the request context, `confirm` is an **optional** argument on the GraphQL mutations, the REST `PATCH /v1/services/{id}` query string, and MCP `update_service`, and an unprotected service is byte-identical to before. The guard fails **closed** — a protection-lookup failure refuses the verb rather than waving it through, matching delete and suspend.

**Dashboard.** The retry handshake `w5/m31` described for delete and suspend now lives in one mount (`common/providers/protected-retry-provider.tsx`) that every single-field Settings save reaches through `useFieldMutation`, plus the four hooks with their own bodies (registry credential, cron, maintenance mode). The constraint from `w5/m31` is unchanged and is the reason this is safe: the dashboard parses the phrase out of the server's error and never precomputes it, so adding or renaming a verb word cannot desynchronize the UI.

## w6/m20 extension: Databases and KeyValues join too

The original scope above (and the dashboard UX added afterward, w5/m25) covered services only — the same services-only asymmetry `internal/projects` had before its own `w1/m31` extension added `DatabaseIndex`/`KeyValueIndex`. `w6/m20` closes the same gap here: `postgres.Service`/`keyvalue.Service` gained a `SetEnvironmentID` verb (mirroring `SetProjectID`) that stamps a new `core.LabelEnvironment` label on the Database/KeyValue CR — the same CR-label mechanism `LabelProject` already used, since these CRs have no control-plane row for `SetEnvironmentServices`' bulk-column approach to apply to. `environments.Service` gained `SetDatabases`/`SetKeyValues` (full-replace-by-name, diffing the label state like `projects.Service`'s own `SetDatabases`/`SetKeyValues`) and `EnvironmentView` now carries `databaseIds`/`keyValueIds` alongside `serviceIds`, surfaced identically over REST (`PUT /v1/environments/{id}/database-links`+`/keyvalue-links`), GraphQL (`setEnvironmentDatabases`/`setEnvironmentKeyValues` mutations, `databaseIds`/`keyValueIds` fields), and MCP (`update_environment`'s `databaseIds`/`keyValueIds` arguments, w1/m71's fold of the `set_environment_databases`/`set_environment_keyvalues` tools). Assigning a Database/KeyValue to an environment also joins it to the environment's project (mirroring `SetEnvironmentServices`' `apps.project_id` stamp); removing it from the environment does not unjoin the project, the same asymmetry `SetEnvironmentServices` already has for services. The dashboard's environment card and its "Manage resources" dialog (`dashboard/src/features/environments/`) were extended the same way Projects' own page already merges all three resource kinds (`use-grouped-resources.ts`).

`w6/m19`'s protected-environment ACLs (above) and `w6/m20` shipped the same week and both independently needed "an environment id on a label" — `w6/m20`'s landed first as `core.LabelEnvironment` (unconditional Database/KeyValue membership); `w6/m19` renamed its own, semantically-different App-only/isolation-conditional label to `core.LabelNetworkIsolation` to avoid the collision, and its `ipAllowList` fan-out was upgraded from an earlier "environment's project members" draft to `w6/m20`'s precise `EnvironmentID`-based membership once it landed.

## w6/m24 extension: Environment groups join too

Environment groups now carry an optional `environmentId` in their KV-stored metadata and API object. `EnvironmentView.envGroupIds` is assembled by listing only the Environment's owning workspace, and `SetEnvGroups` full-replaces membership with an explicit same-workspace check before any mutation. A foreign group id is `403`, never silently ignored or moved across tenants. The adapters expose the same operation as REST `PUT /v1/environments/{id}/env-group-links`, GraphQL `setEnvironmentEnvGroups`, and MCP `update_environment(envGroupIds:)`; Render-shaped env-group creation also accepts `environmentId` across the three adapters. Deleting an Environment clears its groups' association so no dangling forward pointer remains. `w5/m31` added a fourth **Env Groups** tab to the dashboard's existing **Manage resources** dialog, using workspace-scoped candidates and the same full-replace semantics.

## Dashboard operations catch-up (w5/m31)

The Environment card's **All settings** action now edits `protectedStatus`, `networkIsolationEnabled`, and the complete `ipAllowList` in one `setEnvironmentACL` mutation. Protection and isolation are switches; CIDRs use an add/remove list. The card displays a protected badge. The existing membership dialog now full-replaces `envGroupIds` alongside services, databases, and Key Value instances.

Protected service actions no longer terminate at a raw GraphQL error. Delete, suspend, and the reachable direct-deploy override path (Blueprint **Sync**) parse only the backend's named protected-environment error, display its exact `apps.ProtectedConfirmation` phrase, and retry with `confirm`. Blueprint sync gained the same optional confirmation field on REST, GraphQL, and MCP so all three adapters can reach the already-existing `DeployStack` guard. The dashboard does not precompute the phrase. Resume, restart, webhook auto-deploy, and ordinary unprotected flows remain unchanged.

The implementation is reconciled against the dated live Render capture in [render-artifacts/protected-environments.md](render-artifacts/protected-environments.md). Render uses role enforcement for protected Environments, whereas bex's current backend uses an explicit typed retry for an authorized caller; the dashboard represents that real contract rather than claiming the models are identical.

## Inbound IP rules: real enforcement semantics (w4/m28)

The design decision (t001, 2026-07-15), verified against the dated capture in [render-artifacts/protected-environments.md](render-artifacts/protected-environments.md) (Render: rules apply to eligible public web services/static sites + datastores; a source must pass **every** applicable workspace/Environment/service rule; deleting every rule = deny-all; the dashboard seeds `0.0.0.0/0`; IPv4 only):

- **Eligible targets.** An environment's `ipAllowList` applies to every member resource with a public entry point: web services and static sites (their HTTP Ingress) **and** Databases/Key Values (their public SNI route) — no longer datastores only. Private services, background workers, and cron jobs have no public ingress and are unaffected, matching Render's "eligible" qualifier.
- **Layer composition = middleware chaining, not list rewriting.** Each layer keeps its own field and its own Traefik middleware; the layers compose by **chaining** on the same router (Traefik middlewares AND together — a request must pass each), which yields Render's "pass every applicable rule" intersection without bex ever computing CIDR-set intersections. Concretely: the resource's own `spec.ipAllowList` keeps rendering its existing middleware (`<name>-ip-allow` HTTP, or the datastore MiddlewareTCP), and the environment layer projects onto a **new, operator-owned CR field** `spec.environmentIPAllowList` (flat CIDR `[]string` on App, Database, and KeyValue) rendered as a second chained middleware (`<name>-env-ip-allow`). This **retires the clobber**: `propagateIPAllowList` previously full-replaced each member datastore's own `spec.ipAllowList`, silently destroying service-level rules on every environment ACL write; now the two layers coexist. (At switchover the effective reachability is unchanged: previously-clobbered datastores hold an identical copy of the environment list in their service-level field, and identical-list ∩ identical-list = the same list.)
- **Workspace layer: explicit deferral.** bex has no workspace-level inbound-IP surface anywhere (verified by inventory); Render's workspace rules are recorded as out of scope here. When one is added it joins the same chain as a third middleware — the composition mechanism is already layer-count-agnostic.
- **Empty means deny-all, migrated seeded-open.** Render's semantics (zero rules = deny-all) are adopted with a no-lockout migration: a store migration seeds every existing environment whose `ip_allow_list` is empty with `{cidrBlock: "0.0.0.0/0", description: "Allow all (migration seed)"}` + `{cidrBlock: "::/0", …}` — the IPv6 twin is a deliberate bex extension (bex accepts IPv6 CIDRs everywhere; Render is IPv4-only): before migration an empty list projected **no** middleware, so IPv6 sources were reachable, and seeding only `0.0.0.0/0` would have silently cut them off. Creates that omit `ipAllowList` are seeded the same way (Render's own dashboard seeds `0.0.0.0/0`; an API caller who explicitly sends `[]` gets honored deny-all). An **explicitly empty** environment list projects the deny-all placeholder `255.255.255.255/32` onto member `environmentIPAllowList` fields — Traefik rejects an empty `sourceRange`, so deny-all must be a real, unmatchable range; the placeholder is projected by the backend fan-out (the operator stays mechanism-only: non-empty field ⇒ chained middleware, empty ⇒ none).
- **Membership sync, all writers.** The fan-out runs on environment `SetACL`/`CreateWithACL` (list changes), `SetServices`/`SetDatabases`/`SetKeyValues` (membership changes: joiners get the current list, leavers get cleared), per-resource environment assignment (`SetEnvironmentID` on Postgres/Key Value, project/environment assignment on services), and environment `Delete` (clear every member — the same never-leave-a-dangling-projection rule `LabelNetworkIsolation` follows). Member Apps are found via the store's `apps.environment_id` (the same set `ListEnvironmentServices` serves); datastores via their `EnvironmentID` view field as today.
- **Known bounded gaps, documented not silent:** the host-redirect Ingress (auto-paired sibling hosts) carries only the redirect middleware — a blocked source can still receive a 3xx to the canonical host it cannot fetch (same exposure the service-level allowlist already has); descriptions never reach enforcement (CIDRs only project onto CRs; descriptions live in the `environments` row). The three cross-feature lifecycle edges filed as `.pm/w4/025.md` — `projects.SetServices`' stale `environment_id`, `projects.Delete`'s environment cascade bypassing the member-clear fan-out, and the absence of a pre-m28 member backfill — are closed by w4/m32, below.

## Environment IP-layer lifecycle correctness (w4/m32)

The three edges w4/m28's own consistency review filed (`.pm/w4/025.md`) as enforcement-bearing the moment m28 shipped:

- **`projects.SetProjectServices` clears `environment_id` on departure.** A service pulled out of its project (not its environment) used to keep a stale `apps.environment_id` — invisible to `ListEnvironmentServices` (which filters on both columns), but its App CR's `spec.environmentIPAllowList` stayed frozen forever, since nothing re-triggered a clear. The store now NULLs `environment_id` in the SAME transaction as `project_id`, and `projects.Service.SetServices` fans the App CR clear out via a new narrow `environments.EnvironmentIndex` interface (`ClearServiceEnvironmentLayer`) — mirroring the `DatabaseIndex`/`KeyValueIndex` cross-feature-index shape this codebase already uses, so `projects` stays ignorant of `environments` internals beyond this one seam.
- **`projects.Delete` fans the clear out to every child environment's members.** The DB cascade (`environments.project_id ON DELETE CASCADE`, then `apps.environment_id ON DELETE SET NULL` transitively) already leaves the store rows consistent; nothing else re-synced the already-existing App/Database/KeyValue CRs. `projects.Service.Delete` now calls `EnvironmentIndex.ClearMembersForProject` — which enumerates every child environment and re-runs the same member-clear fan-out `environments.Service.Delete` itself uses — BEFORE the project row (and its cascaded environment rows) disappear.
- **Migration closeout (w1/m56).** The former `api environments-backfill` one-shot repaired pre-w4/m32 store drift and re-applied rules that predated the write-time fan-out. Production reported zero Environment rows and the maintained local cluster had no control-plane store at the retirement gate, so there was no remaining state for that command to repair; the subcommand, `Backfiller`, store repair methods, and migration-only tests are now removed. Current membership and ACL writers maintain the invariant directly.
- **Authorization shape:** `ClearServiceEnvironmentLayer`/`ClearMembersForProject` never call `s.Authorize`/`s.AuthorizeOn` themselves — they're internal system operations invoked after the calling verb (`projects.Service.SetServices`/`Delete`) already authorized. To keep them out of the reflection-based authz-completeness sweep (`internal/api/server_test.go`, which treats every exported `(ctx, ...) error` method on a swept feature service as an independently-authorized verb) without bolting on a redundant `Authorize` call, the actual logic lives in unexported `Service` methods and is exposed only through the thin `environments.ProjectMemberClearer` wrapper (satisfying `projects.EnvironmentIndex`), mirroring `apps.WorkspacePurger`'s established shape.
- **Render parity:** no wire-shape change — these are lifecycle-correctness fixes to bex's own store/CR consistency, not a REST/GraphQL/MCP surface Render's docs describe at this granularity. REST/GraphQL/MCP and the dashboard already observe identical post-lifecycle state (they all read the same `EnvironmentView`/CR-projected fields); no drift to file.

## Known divergence from Render / deliberate scope

- **Environment-scoped Blueprint env-var groups are not yet applied.** Root `envVarGroups` remain supported, while a group nested under `projects[].environments[]` returns a named validation error rather than silently losing membership.
- **Protected-action model differs.** Render protection removes destructive permissions from non-Admins; bex accepts the exact server-issued typed retry from an otherwise-authorized caller. See the capture above.
- ~~Environment inbound-IP enforcement differs~~ — closed by `w4/m28`, see § Inbound IP rules above (layered middleware chaining over eligible public services + datastores, empty-means-deny-all with a seeded no-lockout migration; the workspace layer remains an explicit deferral).
- **Full-CRUD MCP, not read-only** — a deliberate consistency choice with the already-shipped Projects MCP surface, diverging from this feature's own original "read-only" plan.
