# Render parity matrix — REST · GraphQL · MCP · UI

A single, evidence-based map of how far bex actually matches [render.com](https://render.com), one row per Render capability across the four surfaces bex mirrors. It replaces scattered "Render-compatible" assertions with a checkable ledger: what has parity, what diverges, what is missing, and what is a deliberate non-goal — each cell backed by a pointer to code (bex side) or Render's own spec/docs (Render side).

**Method.** Four API-focused passes from 2026-07-08, re-verified against Render's live API/docs through 2026-07-27, plus an authenticated page-by-page dashboard walk on 2026-07-15: bex's public REST vs Render's OpenAPI spec; bex's GraphQL vs Render's captured dashboard operations; bex's MCP tools vs the current `render-oss/render-mcp-server`; and bex's dashboard vs Render's live dashboard. The design record for bex's side is [ADR006-bex-api.md](ADR006-bex-api.md) ("one Core, three adapters"); this doc is the parity ledger over it. [Dashboard-walk evidence](render-artifacts/dashboard-walk/README.md).

**MCP parity is pinned and measured (w1/m70, 2026-08-18).** The MCP column above was, until now, backed by hand-written comments in the feature packages carrying manual check dates — not by anything checkable. It is now pinned the way REST is: `lego/backend/internal/api/openapi/render-mcp-tools.json` records what `render-oss/render-mcp-server` **actually registers** (captured by building it and reading its own `tools/list`), hash-pinned by `renderMCPToolsSHA256`, guarded by `TestMCPParity*`, and watched weekly by `scripts/render-mcp-drift.sh`. Measured against `main@89c1f01b`, where upstream registers **22** tools, bex registers **185**: 10 `Parity1to1`, 2 `Superset`, 7 `Divergent`, 166 `Extension`. (**w5/m74** added `list_git_connections`, the multi-account connection surface — ADR075. **w3/m46** wired `clearCache` into `trigger_deploy`, moving it from `Divergent` to `Superset` — an agent written against Render's `trigger_deploy` now calls it unchanged. **w2/023** added `get_service_outbound_ips`, the Render-shaped shared-egress read Render's own MCP does not ship. **w6/m133** added `list_postgres_parameters`, the tenant's DECLARED Postgres parameter set — distinct from `list_postgres_parameter_overrides`, which reports the observed `pg_settings` configuration and is mostly the platform's, not the tenant's.) (It was 213 at m70; **w1/m71** folded 30 `Extension` `set_*` setters into five patch-shaped `update_*` tools, and **w1/m74** folded the 12 remaining per-field `update_*`/`rename_*` tools into those same tools on the rule _fold what REST carries in the resource's `PATCH` body, keep what REST puts behind its own route_. −38 net across the two, losing no ✅ cell in this ledger, because the MCP column scores whether a capability is reachable over MCP, not whether a particular tool name still exists.) Full inventory and the per-tool reasons: [ADR006 § MCP parity is pinned](ADR006-bex-api.md#mcp-parity-is-pinned-w1m70).

**What the MCP column scores.** A `✅` in the MCP column means the **capability is reachable over MCP** — it has never meant bex ships a tool with Render's name for it, and the Legend's "Render capability = a noun/verb Render exposes on _any_ of its surfaces" already implies this. Stating it explicitly because it is load-bearing for `w1/m71`: consolidating bex-invented tools (folding per-field `set_*` setters into a resource's `update_*`) preserves every `✅` in this column, because the capability stays reachable. Renaming or removing a `Parity1to1` tool does **not** preserve parity, because an agent written against Render's official server calls it by name. The 10 `Parity1to1` tools are the contract; the 194 `Extension` tools are bex's to reshape.

**Parity gaps the pin surfaced (w1/m70; `trigger_deploy` closed w3/m46).** Seven bex tools share an upstream tool's name while breaking its contract. Four are genuine bex/Render differences (no caller-chosen `region` on the four create tools; no PR preview environments behind `list_services`' `includePreviews`). Three are unintended and are filed for repair rather than accepted on merit: `create_postgres` spells Render's `diskSizeGb` as `diskSizeGB`; `create_static_site` omits `autoDeploy` and `buildCommand` while requiring `publishPath`; and `get_metrics` renames `resourceId`/`httpLatencyQuantile`/`resolution` to `resource`/`quantile`/`resolutionSeconds`. (A fourth — `trigger_deploy` omitting `clearCache` — was **repaired in w3/m46**: the arg is now accepted on MCP as an enum-validated no-op, moving the tool from `Divergent` to `Superset`.) Upstream also ships `update_environment_variables`, which bex covers under the different name `update_env_vars` — so the long-standing "Render's official MCP has no env-var tools" note in `internal/secrets/mcp.go` was stale and has been corrected.

**Canonical-surface re-verification (w1/m55, 2026-07-27).** Render's current MCP source adds optional per-call `workspaceId` to every resource tool and treats session selection as transitional. bex adopts the request-scoped contract, removes its selection tools/table and the bex-only `list_key_value_instances`, and rejects MCP `ownerId`. Public REST now registers only `/v1/services`, `/v1/postgres`, `/v1/registrycredentials`, `/v1/webhooks` with `eventFilter`, and singular Postgres `/export`; its internal port-8091 `/v1/apps` contract is unchanged. Blueprints use `services`, object-form `image`, `plan`, `numInstances`, and `staticPublishPath`. The complete caller migration and the Render compatibility forms intentionally retained are recorded in [deprecated-surface-removal-2026-07-27.md](render-artifacts/deprecated-surface-removal-2026-07-27.md).

**Operator-correctness re-verification (w2/m60, 2026-07-19).** Current Render primary sources were rechecked for the four tenant-visible lifecycle rules repaired here: Blueprint [`type` is immutable](https://render.com/docs/blueprint-spec), the public [service update schema](https://api-docs.render.com/reference/update-service) has no type transition, PostgreSQL storage [can increase but not decrease and remains independent from compute](https://render.com/docs/postgresql-refresh), and the official CLI exposes `postgres update --disk-size-gb` but no `services update --type`. bex regression evidence is unit/envtest rather than a post-deploy live claim: all 20 ordered cross-type pairs are rejected by both Blueprint Core and CRD admission; a plan downgrade retains accepted Postgres capacity; explicit shrink is a named 400 with no mutation; Valkey expands the bound PVC and waits for real capacity/current revision; and App/KeyValue leave Ready on current-child failure. Applicable REST, GraphQL, MCP, CLI, and dashboard reads all consume the corrected shared views/status mapping; no new public Kubernetes-resize condition was invented.

**Upstream drift re-baseline (w2/m79, 2026-08-19).** Diffed Render's live OpenAPI (`api-docs.render.com`, 208 ops; sole new path `GET /services/{serviceId}/outbound-ips`), the public changelog (Managed OIDC for Anthropic/OpenAI + AWS GA, MCP OAuth for Claude Code/Codex/Cursor, MCP `trigger_deploy`, Postgres PgBouncer pooling, Key Value persistence modes, dedicated outbound IPs), and `render-oss/render-mcp-server` tip (`86a9c6f6`; contractual tool set still matches the 2026-08-18 pin — `trigger_deploy` already present). Rows re-verified as unchanged where bex already covered the surface (Key Value `persistenceMode` — true at **create**, but the **post-create** PATCH surface Render's changelog highlighted was still missing and only landed in w6/m127; Postgres pooler mechanism, MCP OAuth/connect recipe, MCP deploy trigger). Updated/added rows below: service outbound-IP read (✖), Managed OIDC for AI providers (✖), Postgres `connectionPool` OpenAPI enum vs bex `pooler` bool (recorded divergence on the existing pooler row), dedicated-outbound-IPs evidence refresh (status stays `—`). DO_NOT_DO `—` rows were not reopened. CLI pin moved v2.22.0 → **v2.24.0** (`fe8a6188119e`); checklist re-run recorded separately.

**Post-create landing audit (w5/m45, 2026-07-17).** Every resource-create action reachable in the dashboard is classified in the [cross-resource contract](render-artifacts/post-create-landings.md). Standalone Service, Postgres, PITR recovery, Key Value, Project, Environment Group, rollback-deploy, and Workspace outcomes consume the successful response's immutable id; missing-id and rejected responses do not navigate. Contextual Environments, service-side Environment Groups, registry/SSH credentials, invitations, exports, custom domains, and environment contents stay with their owner, while webhook/API-key/database-user one-time secrets remain visible until acknowledgement. Blueprint auto-registration and top-level types without a direct dashboard create action are recorded separately instead of being counted as redirect coverage. Desktop and narrow Chrome evidence exercised all three outcome classes.

**Durable deletion and credential consistency correction (w2/m61, 2026-07-19).** Service/static/Postgres/Key Value delete acknowledgement shapes are unchanged across REST, GraphQL, MCP, dashboard, and the official CLI. While Kubernetes finalizers still hold an App/Database/KeyValue, shared views report `Deleting`/`deleting` instead of Ready/available; required cleanup failure is therefore never presented as success. App finalization now proves an exact-UID execution inventory, historical TLS private keys, Zot manifests, and static-object prefixes absent; Database finalization terminally observes and removes its backup-purge Job. Key Value uses an immutable controller-owned password authority and withholds connection info unless the Ready rollout's one-way credential revision matches. The updated `scripts/delete-audit.sh` is the residue gate; deterministic restart/transient-failure/deadline tests are the cluster-independent regression evidence.

**Official-CLI image and deletion production correction (w5/m49, 2026-07-21 UTC).** The Render-declared nested `image.ownerId` emitted by unmodified CLI v2.21.0 now passes both OpenAPI and the strict REST decoder while resolving to the same authorized workspace; GraphQL/MCP/UI keep the one shared core owner rather than gaining a REST-wire duplicate. Deleting during a first repository build interrupts the synchronous wait, repairs scoped registry cleanup authority, revokes credentials only after repository absence, and quiesces Ingress/cert-manager producers before TLS Secret removal. The production CLI passed image create/update/delete and immediate first-build delete to GET 404 plus CLI-list absence within five minutes. The original stuck fixture and the final acceptance prefix had zero App/workload/build/TLS/credential objects and zero Zot htpasswd/ACL/catalog matches. [Sanitized evidence](../.pm/w5/done/m49/evidence/2026-07-20-diagnosis.md).

**Strict Render REST input contract (w7/m49, 2026-07-20).** Authenticated REST operations in the live bex-mux ∩ pinned-Render-spec intersection now validate against one complete offline OpenAPI snapshot before side effects. Declared constraints, undeclared query names, unknown typed JSON fields, trailing JSON, wrong media types, and stray bodies return the shared Render-shaped 400 without values or schema dumps; valid handler bodies remain byte-identical and defaults are not injected. The official CLI/API shapes and documented bex `dryRun`/`confirm`/service/datastore extensions remain accepted. This is a deliberate bex security strengthening over Render's mostly open object schemas, not a claim about render.com's live unknown-field policy. Bex extensions, public device/HMAC/deploy hooks, GraphQL, MCP, and production response streams are outside the gate; retired public aliases are rejected before dispatch. The exact 119-operation inventory and refresh contract are in [openapi-request-validation.md](render-artifacts/openapi-request-validation.md); response conformance remains CI-only and now uses that same complete pin plus the ADR018-cited stale-checked divergence allowlist.

**Private-service network isolation re-verified (w6/m46, 2026-08-22).** A live private service was reachable at its `.onbex.co` platform host, serving unauthenticated traffic. Cause was one write: the control-plane projector rebuilt each App's spec from an `apps` row that carried no service type, so `projectSpec` stamped `expose: true` on every service it converged, overwriting the type-aware value the create path computed. The type is now a column (migration 0095) and the projector derives exposure from it; `expose` also left the projector's owned-field set, since nothing in the row or any lifecycle verb ever changes it. Two independent gates now stand behind that: `AppSpec.PubliclyRoutable` drops every host inside the CRD contract's `EffectiveHosts`, and the operator repeats the check where the Ingress is actually created. Custom domains follow the same rule on every surface — the Blueprint path already refused them for a non-routable type; REST/GraphQL/MCP create named only `background_worker`/`cron_job` (letting `private_service` through) and the add-domain verb checked nothing, so both were aligned onto the shared predicate, and the dashboard stops offering the Custom Domains card and the platform-subdomain toggle to a type that can never have either. **No divergence was added:** the recorded w9/m58 split — REST/MCP omit `serviceDetails.url` for a private service, GraphQL retains `url` as a bex-shaped surface — was re-verified and left standing; what all four surfaces now agree on is that none ever reports a public host for a private service. The deploy-status vocabulary is unchanged (no new value; the same eleven states).

**Legend.** ✅ parity (evidence pointer) · ◐ partial (divergence documented) · ✖ missing (gap — see backlog) · — deliberate non-goal (rationale inline). "Render capability" = a noun/verb Render exposes on _any_ of its surfaces; a `—` on the REST column can still be a `✅` elsewhere (Render itself splits work across surfaces — e.g. read-only SQL is MCP-only on both sides).

**A fifth surface.** REST/GraphQL/MCP/UI above are bex's own adapters; Render's _official CLI_ (`render-oss/cli`) is a fifth, external surface bex never builds its own competitor to (`.pm/DO_NOT_DO.md`) — [docs/cli-compatibility-checklist.md](cli-compatibility-checklist.md) runs it unmodified against bex-api and tracks the result the same way this ledger does. It surfaced several REST wire-format bugs this matrix's capability-level rows don't catch. Its fixed-client browser login is implemented through Hydra device authorization and locally verified with two real users, refresh rotation, and scoped logout (`w4/m27`); production rollout evidence is still pending.

**Native mobile is a client, not a sixth adapter (w11/m2).** The first-party Expo app consumes the existing GraphQL schema through generated typed documents and the same human identity/OpenFGA checks as the dashboard and CLI; it adds no Core verb, field, error code, workspace fallback, or mobile-only authorization rule. Its initial workspace read is the existing caller-scoped `workspaces` query. Later tenant reads must pass the selected Render-shaped `ownerId` where GraphQL already accepts one, and omission retains the documented deterministic-default behavior rather than becoming hidden native state. HTTP 401 causes one serialized refresh and then logout; 429/502/503/504 query retries are bounded, while mutations are never transport-retried. Workspace or identity changes abort pending requests and clear Apollo state before the new boundary renders. The UI differences are deliberately presentation-only: supervision tabs and validated deep-link placeholders omit configuration/destructive actions under [ADR048](ADR048-mobile.md), while server semantics remain those recorded in this matrix.

**Mobile supervision consumes the existing evidence contracts (w11/m3).** The project-grouped status home reads caller-scoped `projects`, `services`, `databases`, and `keyValues`; the service evidence screen uses the same keyset-paged `deploys` and per-event-cursor `serviceEvents` shapes as the dashboard, including unknown-event fallback rather than inventing a mobile vocabulary. CPU, memory, and bandwidth snapshots use the existing Render-shaped `metrics(query:)` field and preserve empty, partial, reset, and degraded-source meaning in a compact presentation. Log catch-up uses `GET /v1/logs` and freezes one timestamp before opening credentialed `/v1/logs/subscribe`; stable row ids deduplicate the inclusive history/live boundary, the mobile buffer is capped at 500 lines, and Loki-only filters remain explicitly history-only or surface the existing 503 rather than widening silently. Polls and tails stop outside an active, online app and recover through bounded single-flight backoff on foreground/reconnect; cached observations cross a visible fresh/stale boundary. This adds no mutation, configuration route, shell, or new server contract.

**Native push is a deliberate bex delivery-channel extension (w11/m5), with browser web push added as a second transport of the same extension (w2/m76).** Render's captured dashboard notification settings and bex's existing email toggles remain unchanged. Render has no push notifications (email + Slack-via-integrations only); this is never a “parity fix.” bex adds one caller-scoped push policy and secret-free destination metadata through REST and GraphQL, backed by the same authenticated workspace/member boundary and event vocabulary; the dashboard edits the complete shared policy while the native app owns Expo installation-token registration and the dashboard owns VAPID `PushManager` subscribe. Provider tokens, tickets, endpoints, and p256dh/auth keys never enter a caller **read** response. MCP deliberately has no device-registration, web-push, or push-policy tools because an installation- or browser-bound human notification channel is not an agent capability; this is documented surface scope rather than semantic drift. Each optional transport reports unavailable when its Secret is absent and makes no provider call. Native physical iOS/Android delivery evidence is still pending; browser push has no Apple/Google/app-store dependency.

**Mobile safe actions reuse the existing lifecycle contracts (w11/m4).** Native exposes only the pre-parameterized action allowlist from ADR048: deploy trigger/cancel/known-target rollback; service restart/suspend/resume; Postgres restart/suspend/resume; and Key Value suspend/resume. Each generated document calls the same GraphQL mutation used by the dashboard or its existing compatibility alias, so OpenFGA authorization, protected-environment confirmation, audit recording, conflict rules, and deploy-history effects remain in the shared server core. The client never supplies build parameters, images, commands, scaling, plans, settings, PITR, failover, deletion, or other consequence-heavy input. Confirmation binds the exact action and opaque target, one controller single-flights double taps, and mutations are never transport-retried. A lost response is reported as possibly committed and requires a server refresh before a new confirmation; visible success follows an accepted mutation plus refreshed resource/deploy state, not an optimistic patch. An AST/GraphQL inventory test fails if any unapproved mutation, direct write method, action registration, or route enters the native product surface.

**Role-aware dashboard controls (w9/m84 + w2/m74, 2026-08-18).** The dashboard consumes the same effective OpenFGA relations as REST/GraphQL/MCP and disables definitive denials with a localized, keyboard-reachable reason instead of letting a user edit and then receive 403. Service/environment-group variables and secret files plus datastore delete use `can_create`; sensitive reveal/export independently use `can_view_sensitive`; Postgres/Key Value plan and suspend/resume/restart use `can_operate`. Unknown capability reads remain permissive and the server remains authoritative. Render's current [workspace role matrix](https://render.com/docs/team-members#role-permissions) likewise denies Contributors sensitive fields and most create/modify/delete operations while allowing deploy/rollback triggers. Bex deliberately keeps its documented broader Contributor lifecycle boundary—including datastore plan/lifecycle verbs—rather than silently narrowing `can_operate`; protected-resource and billing gates still compose independently. Render does not document whether each denied dashboard placement is hidden or disabled, so Bex's explicit reason is an intentional legibility improvement, not a claimed pixel-level match. No public API shape changed in m74.

> **Headline.** bex has real parity on the **service lifecycle, env vars, environment groups, secret files, custom domains, managed Postgres lifecycle/data protection/logs, managed Key Value, service logs, metrics, and autoscaling config** core across all four surfaces, and is _ahead_ of Render on several AI-native verbs (API-key management over the API, deploy-from-chat, inbound push webhooks, and GraphQL/MCP webhook management — [§ bex ahead of Render](#bex-ahead-of-render)). The remaining wire-format and UI-depth gaps are mapped to owning milestones/notes in the [§ Gap backlog](#gap-backlog). (Background-worker and cron-job service types shipped in w1/m15; environment groups + secret files in w1/m16; managed Key Value landed on REST/GraphQL/MCP in w2/m7 and the dashboard in w5/m12; autoscaling config shipped in w1/m20; static sites — build → object-store origin + redirects/rewrites/headers — shipped in w1/m21; deploys as first-class objects — list/get/trigger in w2/m5, cancel/rollback in w2/m10, deploy-body params (commitId/clearCache/deployMode) + restart consolidation in w2/m30 — shipped across REST/GraphQL/MCP.)

**A build_in_progress deploy always has a build behind it (w6/m95, 2026-08-25):** a live hunt reproduced 3/3 fresh web services whose first deploy sat at `build_in_progress` with `updatedAt` byte-identical to `startedAt` while `GET /v1/logs/subscribe?type=build` answered `{"error":"no running build is available to follow"}` in under 20ms — no BuildKit pod existed. Render's behaviour is the parity target: a build that cannot be scheduled surfaces as a queued deploy and then a failed one, never an in-progress spinner over nothing. Two readings were granting `build_in_progress` without evidence. The operator classified a build Job that had not yet produced a pod as `PhaseBuilding` (whose own contract is "a pod is placed on a node"), and bex-api treated every `PhaseBuilding` Ready reason except the one literal it recognised as "building" — so `RegistryCredsPending`, which parks a brand-new App _before_ its build Job is created while zot re-reads its freshly minted push credential, reported a live build. Both now report the honest `queued`, via one shared contract (`ReasonBuilding`/`ReasonBuildQueued` + `BuildIsRunningReason` in `lego/types`) rather than a matched pair of string literals, and the reader is an allow-list so an unrecognised future reason can never claim running infrastructure. **The eleven-value wire vocabulary is unchanged** — `queued` and `build_in_progress` are both already in it, REST/GraphQL/MCP read the one `DeployView.Status` verbatim, and the dashboard already renders, labels, and offers Cancel on `queued` — so no surface, filter, or client needs a migration. One visible consequence: `startedAt` is now stamped on the queued→build_in_progress edge rather than at the pre-dispatch wait, so the build-log stream's `==> Building from <repo>@<sha>` line is emitted only once a build really exists. Separately, the gate-timeout close was made unconditional (a row whose App CR the reconcile pass cannot read at all, and a legacy operator's generation-mismatched row, both previously stayed open forever), and a timed-out build now closes with a build-specific `failureReason` instead of the rollout's "did not become healthy within the health-gate window; check the service logs", which pointed at logs a service that never built does not have.

**A deploy queued behind a failed build always runs (w6/m100, 2026-08-26):** a live hunt triggered a second deploy while the first was still building, the first failed its build (wrong branch → clone exit 90 → `PodFailurePolicy`), and the second stayed at `status:"queued"` with empty `startedAt`/`finishedAt`/`failureReason` and a frozen `updatedAt` for 185+ seconds — indefinitely, in fact: only a human clicking Cancel closed it. Render's behaviour is the parity target — a deploy queued behind a sibling that fails takes the build slot the failure freed. The cause was generation bookkeeping, not the wire contract: the operator stamped a build failure's durable marker with `metadata.generation`, which the queued deploy's own spec patch had already bumped, so the re-dispatch gate read the first deploy's verdict as the second's and halted before ever building it. The terminal build verdict now rides its own `status.conditions[Build]`, attributed to the release generation that actually built, and both the operator's re-dispatch gate and bex-api's deploy projection read it there. **No wire-shape change:** the eleven-value status vocabulary, `renderDeploy`'s fields, the GraphQL/MCP projections (MCP literally reuses REST's `toRenderDeploy`), and the dashboard's status/label/polling logic are all untouched — this is a liveness fix, so the same row simply now reaches `build_in_progress` → `live`/`build_failed` instead of never leaving `queued`. One consequence worth naming: the deploy whose build failed still closes `build_failed` **with its build error**, not `canceled`. It would have become `canceled` under the plain generation comparison, because the operator adopts the queued generation milliseconds after recording the failure while bex-api resyncs every 30s — the durable condition is what keeps the verdict readable that late. Regression coverage: `build_failed_pending_release_envtest_test.go` (operator), `queued_behind_failure_test.go` (bex-api, including the Rollback call site).

**Blueprint wire-shape divergences (2026-08-16).** Bex creates and immediately syncs a Git-connected Blueprint, so the stored Blueprint never rests in Render's `created` status; it transitions through `syncing` to `in_sync` or `error`. ## Resource-object metadata parity (w6/m28)

Service, Postgres, and Key Value REST responses now carry truthful Render-compatible metadata from one shared backend contract: tenant-store `owner` objects, configured `BEX_REGION`, configured `BEX_DASHBOARD_URL` routes, and authoritative `updatedAt` values. Owner lookup is caller-scoped and batched; unresolved or unauthorized workspaces are omitted rather than guessed. Region and dashboard URL are also omitted when unconfigured. Dashboard links resolve to the existing `/services/{id}`, `/databases/{id}`, and `/keyvalue/{id}` pages. API writes stamp `app.bex.co/updated-at`; legacy reconciled resources may use Kubernetes managed-field time, and resources with neither source omit `updatedAt` instead of copying creation time.

**w6/m28** enriched REST only; GraphQL/MCP carried flat `ownerId` but not `region`/`dashboardUrl`/`updatedAt`. **w2/m46** extended all three to GraphQL (`Database`/`KeyValue` types) and MCP (tool structured outputs) via shared `PostgresView`/`KeyValueView` fields populated in the same `view()` path REST uses. **w9/m42/t003** added `TestGraphQLPostgresMetadataParity`, `TestMCPPostgresMetadataParity`, `TestGraphQLKeyValueMetadataParity`, and `TestMCPKeyValueMetadataParity` to lock the fields cross-surface; all pass. The pinned official CLI renders workspace and region in Postgres and Key Value text output. Its generated Service text type exposes owner ID and dashboard URL but has no workspace-name or region fields, so the live verifier checks the complete Service metadata directly on the raw REST response after the unmodified CLI has decoded and created the resource. ## bex ahead of Render

Verbs where bex's AI-native posture exposes _more_ than Render does — tracked here so they read as deliberate supersets, not accidental drift:

- **API-key management over the API** — `POST/GET/DELETE /v1/api-keys` + GraphQL + MCP. Render mints keys in the dashboard only (account-scoped, non-expiring); bex makes them a first-class, workspace-scoped, revocable OAuth2-client resource an agent can rotate itself ([ADR012-auth.md](ADR012-auth.md)).
- **Deploy-from-chat** — MCP `deploy {repo, bexYaml}` retains its wire argument but rides the same Blueprint compiler and `Create` verb (no bespoke endpoint): one call takes a repo plus a `render.yaml` manifest to a live URL ([ADR017-deploy-from-chat.md](ADR017-deploy-from-chat.md)).
- **Inbound push-to-deploy webhook** — `POST /v1/webhooks/git` (HMAC-SHA256, outside the OAuth gate). Render's public `/webhooks` are _outbound_; bex additionally accepts the git host's push.
- **Webhook management beyond Render REST** — Render publishes `/v1/webhooks` CRUD and keyset-paged `/events` history plus the global `GET /v1/events/{eventId}` hydration route, so bex’s corresponding REST family is compatibility work, not a product lead. bex remains ahead on GraphQL and MCP management (`list_webhook_endpoints`, `list_webhook_deliveries`, and create/update/delete endpoint tools) and adds `serviceEvent(id:)` / `get_service_event` over the shared global lookup, because Render’s official MCP server has no webhook or event tools; those dialects and the dashboard also expose richer retry diagnostics. bex deliberately treats the signing secret as mint-once instead of returning it on later reads. The dated correction and remaining product/source divergences are in [webhooks-api.md](render-artifacts/webhooks-api.md) (`w2/m70`, `w8/m24`).
- **Usage metering** — `GET /v1/usage` + GraphQL `usage(period: $period)` + MCP `get_usage` tool return month-to-date or historical-month usage (instance-seconds per tier, egress bytes, build seconds, storage GB-seconds, and weighted sandbox compute seconds) for the caller's workspace — including managed Postgres and Key Value instances (`resourceKind: "postgres"` / `"key_value"`) and hosted sandboxes (`resourceKind: "sandbox"`). **Coverage contract (w11/m8):** every adapter returns the same `coverage {state, through, degradedSources}` beside the totals. Current-month `complete` means durable healthy evidence for every applicable hourly source through the latest closed UTC hour; a late start, gap, degraded/unavailable source, or lagging stream is `partial`; historical and pre-contract totals are always `unknown`, never inferred complete. `through` is the common contiguous watermark and `degradedSources` is bounded and presentation-safe. **Outbound completeness (w8/m15):** App `egress_bytes` atomically sums exact HTTP responses, downstream WebSocket frames, and direct public TCP/UDP L3 bytes; public datastore rows contain encrypted backend→client proxy bytes, while private datastore traffic is explicit zero. Same-cluster/private, cluster DNS, denied, control-plane, and backup traffic are excluded. All three adapters read the same durable rows and therefore cannot disagree. All three surfaces accept the same `period: YYYY-MM` argument with identical semantics — including its validation: a malformed period is a named 400 on every surface, never a silent fall-back to the current month and echo it in the response body. **Workspace targeting (w6/m18, w1/m55):** REST and GraphQL accept `ownerId`; MCP accepts per-call `workspaceId` alongside `period`, and the dashboard's Usage page follows the switcher. **Dashboard** (**w8/m6 + w8/m9 + w8/m15**): month picker on the Usage page lets users select any of the last 6 months; a 3-month trend view shows totals over the last three calendar months; storage has its own GB-hours table; bandwidth copy names the complete public-egress basis. **Render comparison (re-verified 2026-07-27):** Render's [pricing page](https://render.com/pricing) lists Postgres and Key Value as plan-priced compute and outbound bandwidth as a usage dimension; its [Postgres flexible-plan documentation](https://render.com/docs/postgresql-refresh) sets Postgres storage at `$0.30/GB-month`, prorated by the second. Render's [dashboard documentation](https://render.com/docs/render-dashboard) exposes payment-method updates, accrued charges, included-usage counters, and invoice history only in the Billing UI, with no public REST/GraphQL/MCP billing endpoint. **Verdict:** parity on the public-outbound category intent, compute, and the Postgres storage rate dimension; deliberate bex extension on raw quantities and API access. **Documented drift:** bex publishes its precise byte basis (including direct L3 headers and encrypted datastore proxy bytes), while Render does not expose an invoice-level byte-boundary contract; Render prices provisioned Postgres capacity and has no separate Key Value storage line, while bex prices actual used PVC bytes for both datastore kinds. See [docs/ADR023-usage-metering.md](ADR023-usage-metering.md). **Real billing surface (w7/m48, direct Stripe pivot w7/m50, [ADR040](ADR040-billing-metronome.md)):** beside the advisory `estimatedCost`, the same usage read on all three surfaces carries a `billing` object — Stripe's current Subscription invoice preview + finalized invoices — with identical field names/semantics across REST (`billing` in the `/v1/usage` envelope), GraphQL (`usage.billing { currentCost, invoices }`), MCP (`get_usage`), and the dashboard's distinct "Current Spend" card (an _Invoice_ badge, not the estimate). `billing` is `null`/absent (estimate-only, never a 500) when no bex Stripe Subscription exists, the workspace is structurally excluded, billing is off (`BEX_STRIPE_SECRET_KEY` unset), or the Stripe read degrades. A Mode-B comped Subscription can still expose rated net-zero invoice data. Still a **bex-ahead extension** — Render exposes no billing API, so this is internal cross-surface consistency, not a Render-parity claim. **Credits (w5/m70):** the same `billing` object carries a `credits` block — `{availableUsd, currency, grants[{name, remainingUsd, expiresAt}]}` from Stripe's `credit_balance_summary`/`credit_grants` reads (never derived from the invoice preview, whose total is unreliable for credit under flexible billing mode) — identical on REST/GraphQL/MCP (guarded by `TestBillingCrossSurfaceParity`), absent (not zeroed) at zero balance or on a degraded/permission-denied credit read. Dashboard: a "Credits remaining" card (hidden entirely at zero, mirroring Render's own billing-page presentation of promotional credit), a credit-adjusted "Credits applied −$X → amount due $Y" line under the invoice preview, an earliest-expiry note, and the ADR046 clarification that a payment method is still required. The dashboard page itself was renamed `/usage` → `/billing` in the same milestone (Render's workspace IA; `/usage` redirects, the usage API keeps its ADR023 names).
- **Billing onboarding, dunning, and self-service** — w7/m51–m52 provide one contract — gated on `can_manage_billing` (billing role or admin) since **w1/m60**, so Render's **Billing** role manages billing without full workspace-admin — across REST (`/v1/workspaces/{id}/billing` and hosted-session POSTs), GraphQL (`workspaceBillingReadiness`, `createBilling*Session`), MCP (`get_billing_readiness`, `create_billing_*_session`), and the dashboard. Setup-mode Checkout binds a test payment method to the existing metered contract; Portal is Customer-scoped; Tax reports unconfigured until an operator-confirmed catalog and active same-mode registration pass. Signed failed/action-required/success invoice and Subscription events now converge through the same durable lifecycle as the polling backstop: visible grace, reversible test-mode enforcement, exact-marker recovery, owner notifications, and a 409 billable-mutation gate while enforced/recovering. This is a **bex-ahead extension**, not a Render-parity claim: Render publicly documents billing UI and broad failed-payment suspension rights, but not a grace schedule, ownership/recovery algorithm, or billing-lifecycle API. The **billing-role authorization** now matches Render's role split (w1/m60); bex leaves static sites/data untouched and refuses live enforcement. See the [dated comparison](render-artifacts/billing-onboarding.md).
- **In-app Audit Log viewer** — dashboard Settings → **Security & Compliance** → Audit Log (`w4/m14`, regrouped `w4/m15`) is a live, paginated, in-app table. Render's dashboard has no in-app audit-log table at all — only a date-range CSV export under Workspace Settings → Compliance (render.com/docs/audit-logs, checked 2026-07-11); bex places its richer table under the analogous Security & Compliance grouping.
- **GitHub repo listing & connection status over the API** — `GET /v1/repos` + MCP `list_repos`/`list_git_connections` return the workspace's connected installations' repositories (private included, each annotated with the owning GitHub account) and the connections' account/install URLs, so "which of my repos can you deploy?" is one agent call. Render lists repos only through its private dashboard API and its MCP has no repo tools (w2/m8, [ADR026-github-integration.md](ADR026-github-integration.md)). **Workspace targeting (w6/m18, w1/m55):** connect/list-connections/disconnect/repo-list use `ownerId` on REST/GraphQL and per-call `workspaceId` on the MCP `list_repos`/`list_git_connections` tools, so a multi-workspace caller can check or list a **non-default** workspace's GitHub connections explicitly rather than only ever resolving their default one. **Multi-account (w5/m74, [ADR075](ADR078-github-workspace-connections.md)):** a workspace holds several connections; `GET /v1/git/connections` / `gitConnections` / `list_git_connections` list them all, and `DELETE /v1/git/connections/{installationId}` disconnects one. The singular `get_git_connection` / `GET /v1/git/connection` remain as deprecated single-connection aliases. **Claim flow (w5/m75, ADR075 §3a):** `POST /v1/git/claim` / `claimGit` return `{claimUrl}` — the OAuth-authorize round trip that binds an installation **already present** on GitHub (where GitHub strips the install URL's signed state); this is the workspace-bound model's answer to Render's "direct github.com install just works" (Render's user-bound OAuth model _reads_ installations, so it never needs a binding ceremony). Deliberately absent from MCP: the claim is a browser OAuth ceremony an agent cannot complete, matching connect's existing MCP absence.
- **A user-consented OAuth 2.1 provider for third-party agents** — an MCP client self-registers (DCR), sends its user through bex's own login, and the user grants it on a real **consent screen**; the agent then holds its own revocable, scoped token (w4/m9 + w4/m16, [ADR012-auth.md §7](ADR012-auth.md#7-oauth-21-provider-for-agents-one-dashboard-login-first-party-sessions--third-party-clients-w4m9)). Render has **no OAuth2 provider or consent surface at all** — agents and CI use dashboard-minted API keys, so there is no Render shape to mirror here (re-checked against api-docs.render.com + render.com/docs 2026-07-12: the only credential is an account-scoped API key). No operator blessing is required: `skip_consent`/`OAUTH_TRUSTED_CLIENTS` only _skips_ the screen for first-party clients. **Cross-surface consistency:** bex-api never distinguishes a consented client from a blessed one — it introspects the bearer and checks the audience, with no trusted-client branch anywhere in `lego/backend`, so both tokens authorize identically at `/mcp`, REST, and GraphQL (evidence: [scripts/auth-oauth21-e2e.sh](../scripts/auth-oauth21-e2e.sh) legs 8 and 10 assert the same 200 for each). **Granular capabilities (w8/m27):** a third-party human token for the API audience must carry `bex.read` / `bex.write` / `bex.sensitive` (independent, advertised in RFC 9728 `scopes_supported`); missing or near-match scopes fail closed with one coded `INSUFFICIENT_SCOPE` across REST, GraphQL, and MCP. Dashboard Kratos sessions and machine API keys stay scope-exempt. The unmodified official Render CLI launcher and the platform-marked mobile client keep the legacy `bex.api` compatibility alias until those clients request the granular vocabulary; `bex.api` is never an umbrella grant for anyone else. This remains a Bex security extension, not a Render OAuth-parity claim. **Both login states (w4/m17):** the recipe works whether or not the user is already signed into the dashboard — the signed-in path (the commonest one: Kratos accepts the login challenge outright and answers the page's AJAX call with `200 null`) is asserted by leg 13, which drives a second authorization from a reused, already-signed-in cookie jar and fails if the browser is made to re-authenticate. **Revocable in practice, not just in theory (w4/m18):** "revocable, scoped token" was only half true from m16 to m18 — remembered consent shipped with no UI to undo it. Agent terminal states (`completed`+PR / `failed`) also project into the existing push channel as the `agent_pr_ready`/`agent_failed` delivery events, deep-linking to the session; still bex's own cross-surface discipline, no Render counterpart.
- **Agent-session durable conversation history and terminal convergence** (`w5/m71` + `w5/m72` + **`w4/m87`**, [ADR047](ADR047-cloud-coding-agent-sessions.md) + [ADR051](ADR051-agent-session-transcript.md)) — Render has no coding-agent conversation product, so this is not endpoint parity. - **Viewer capability projection** (`w9/m84`, [ADR024](ADR024-members.md)) — the caller's own effective workspace permissions (`role` + `canView`/`canViewLogs`/`canOperate`/`canCreate`/`canViewSensitive`/`canManageKeys`/`canManage`/`canManageBilling`) as one read-only projection on all three surfaces: REST `GET /v1/viewer/capabilities`, GraphQL `viewerCapabilities(ownerId)`, MCP `get_viewer_capabilities`. The dashboard consumes it to **disable-with-reason** the create-gated build/deploy config, cron command, and statement-logging parameter controls (`w9/m84`); service/environment-group writes, leftover `EnvVarsEditor` writes, datastore delete, and `can_view_sensitive` reveal (`w2/m74` + leftover `EnvVarsEditor` in `w9/m87`); plus `can_manage_billing`. `SetBuildFilter` is `can_operate` — viewers disabled-with-reason, contributors keep the editor (`w9/m87`; `w2/m74` left Build Filters out of scope). Datastore `SetPlan` and suspend/resume/restart stay `can_operate` (`w2/m74`). Member-management stays on its existing Render-consistent hide. Disable-with-reason vs Render's hide remains the deliberate m84 choice; no REST/GraphQL/MCP wire change.
- **Denied-read audit trail** (`w4/m20/t001`) — a denied `can_view`/`can_view_logs`/`can_view_sensitive` check now leaves a `status: denied` `audit_events` row (successful reads still don't, by volume). Render's documented audit-log event vocabulary (render.com/docs/audit-logs) covers privileged account/team/service-lifecycle actions only — member added/removed, service created/deleted, and the like — with no "someone tried to view X and was refused" event class at all; bex's binary allowed/denied `Outcome` already covers this uniformly (same field, same rendering, `internal/audit`/`internal/events`) so no new vocabulary or schema was needed, just widening which relations reach the sink.
- **MCP `update_service` routing vs REST PATCH** (`w1/073`, 2026-08-19) — REST `PATCH /v1/services/{id}` matches Render's PATCH field set, including the `repo`/`image` source object. MCP `update_service` is a bex fold (Render's official MCP has no update-service tool): it carries the settings PATCH plus two fields Render keeps on dedicated REST routes (`notificationsToSend` on `PATCH /v1/notification-settings/overrides/services/{id}`, `autoscaling` on `PUT /v1/services/{id}/autoscaling`). Those REST routes stay; MCP does not grow a source-kind switch (`repo`/`image` — create-like, REST-only). The three remaining differences are this routing, not missing verbs.

- **Push-deliverability disclosure** (`w6/m99`, [ADR026 §7a](ADR026-github-integration.md)) — the service object carries `pushDeliveryMethod` (`github_app` | `manual_webhook` | `none` | `unknown`) beside Render's `autoDeploy`/`autoDeployTrigger`, answering whether a push to the tracked branch can REACH bex for that specific repo rather than only whether the setting is on. Render has no counterpart and needs none: a Render service can only be created from a repo its connected credential already covers, so "auto-deploy is on and no push can ever arrive" is unreachable there. bex's Public Git URL tab accepts any github.com URL — including one outside every installation's grant, which is also the documented `w6/m97` workaround — so bex owes the disclosure. Parity here is therefore **internal**, not upstream: REST, GraphQL, MCP, and the dashboard's Build & Deploy hint report the one server-computed value, asserted together rather than in three drifting per-surface tests. The value comes from the same per-repo grant predicate a deploy trigger applies, computed on read (a GitHub-side grant edit takes effect immediately, no create-time snapshot) by the by-id read alone; the service list omits it rather than pay a GitHub round-trip per repo on a polled path.

The MCP `query_render_postgres` tool itself remains parity, not a superset — it is read-only on both platforms. The dashboard console and its explicitly confirmed write mode are a deliberate bex extension; no write flag was added to the agent tool.
