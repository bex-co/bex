# Render parity matrix — REST · GraphQL · MCP · UI

A single, evidence-based map of how far bex actually matches [render.com](https://render.com), one row per Render capability across the four surfaces bex mirrors. It replaces scattered "Render-compatible" assertions with a checkable ledger: what has parity, what diverges, what is missing, and what is a deliberate non-goal — each cell backed by a pointer to code (bex side) or Render's own spec/docs (Render side).

**Method.** Four API-focused passes from 2026-07-08, re-verified against Render's live API/docs 2026-07-09 (and the official MCP SQL tool again 2026-07-14), plus an authenticated page-by-page dashboard walk on 2026-07-15: bex's public REST vs Render's OpenAPI spec; bex's GraphQL vs Render's captured dashboard operations; bex's MCP tools vs `render-oss/render-mcp-server` v0.3.0 (24 tools — incl. three non-functional `update_{web_service,static_site,cron_job}` stubs that return "use the dashboard/API"; Render's only functional MCP write is the single env-var tool `update_environment_variables`); and bex's dashboard vs Render's live dashboard. The design record for bex's side is [ADR006-bex-api.md](ADR006-bex-api.md) ("one Core, three adapters"); this doc is the parity ledger over it. [Dashboard-walk evidence](render-artifacts/dashboard-walk/README.md).

**Legend.** ✅ parity (evidence pointer) · ◐ partial (divergence documented) · ✖ missing (gap — see backlog) · — deliberate non-goal (rationale inline). "Render capability" = a noun/verb Render exposes on _any_ of its surfaces; a `—` on the REST column can still be a `✅` elsewhere (Render itself splits work across surfaces — e.g. read-only SQL is MCP-only on both sides).

**A fifth surface.** REST/GraphQL/MCP/UI above are bex's own adapters; Render's _official CLI_ (`render-oss/cli`) is a fifth, external surface bex never builds its own competitor to (`.pm/DO_NOT_DO.md`) — [docs/cli-compatibility-checklist.md](cli-compatibility-checklist.md) runs it unmodified against bex-api and tracks the result the same way this ledger does. It surfaced several REST wire-format bugs this matrix's capability-level rows don't catch. Its fixed-client browser login is implemented through Hydra device authorization and locally verified with two real users, refresh rotation, and scoped logout (`w4/m27`); production rollout evidence is still pending.

> **Headline.** bex has real parity on the **service lifecycle, env vars, environment groups, secret files, custom domains, managed Postgres lifecycle/data protection, managed Key Value, service logs, metrics, and autoscaling config** core across all four surfaces, and is _ahead_ of Render on several AI-native verbs (API-key management over the API, deploy-from-chat, webhooks in both directions over the API — [§ bex ahead of Render](#bex-ahead-of-render)). The remaining wire-format, UI-depth, and managed-Postgres-log gaps are mapped to owning milestones/notes in the [§ Gap backlog](#gap-backlog). (Background-worker and cron-job service types shipped in w1/m15; environment groups + secret files in w1/m16; managed Key Value landed on REST/GraphQL/MCP in w2/m7 and the dashboard in w5/m12; autoscaling config shipped in w1/m20; static sites — build → object-store origin + redirects/rewrites/headers — shipped in w1/m21; deploys as first-class objects — list/get/trigger in w2/m5, cancel/rollback in w2/m10, deploy-body params (commitId/clearCache/deployMode) + restart consolidation in w2/m30 — shipped across REST/GraphQL/MCP.)

## Resource-object metadata parity (w6/m28)

Service, Postgres, and Key Value REST responses now carry truthful Render-compatible metadata from one shared backend contract: tenant-store `owner` objects, configured `BEX_REGION`, configured `BEX_DASHBOARD_URL` routes, and authoritative `updatedAt` values. Owner lookup is caller-scoped and batched; unresolved or unauthorized workspaces are omitted rather than guessed. Region and dashboard URL are also omitted when unconfigured. Dashboard links resolve to the existing `/services/{id}`, `/databases/{id}`, and `/keyvalue/{id}` pages. API writes stamp `app.bex.co/updated-at`; legacy reconciled resources may use Kubernetes managed-field time, and resources with neither source omit `updatedAt` instead of copying creation time.

This is a REST-boundary enrichment. Existing ids, list cursor envelopes, Core/GraphQL/MCP `ownerId`, and authorization behavior remain unchanged. The pinned official CLI renders workspace and region in Postgres and Key Value text output. Its generated Service text type exposes owner ID and dashboard URL but has no workspace-name or region fields, so the live verifier checks the complete Service metadata directly on the raw REST response after the unmodified CLI has decoded and created the resource. See [ADR006 § Resource metadata contract](ADR006-bex-api.md#resource-metadata-contract-w6m28) and the [CLI compatibility checklist](cli-compatibility-checklist.md#systemic-root-causes).

## bex ahead of Render

Verbs where bex's AI-native posture exposes _more_ than Render does — tracked here so they read as deliberate supersets, not accidental drift:

- **API-key management over the API** — `POST/GET/DELETE /v1/api-keys` + GraphQL + MCP. Render mints keys in the dashboard only (account-scoped, non-expiring); bex makes them a first-class, workspace-scoped, revocable OAuth2-client resource an agent can rotate itself ([ADR012-auth.md](ADR012-auth.md)).
- **Deploy-from-chat** — MCP `deploy {repo, bexYaml}` rides the same `Create` verb (no bespoke endpoint): one call takes a repo + `bex.yml` to a live URL ([ADR017-deploy-from-chat.md](ADR017-deploy-from-chat.md)).
- **Inbound push-to-deploy webhook** — `POST /v1/webhooks/git` (HMAC-SHA256, outside the OAuth gate). Render's public `/webhooks` are _outbound_; bex additionally accepts the git host's push.
- **Webhook management over the API** — outbound webhook endpoints are a full REST/GraphQL/MCP resource (`/v1/webhooks/endpoints` CRUD + enabled toggle + keyset-paged delivery history + the served event-type vocabulary), where Render's public docs manage webhooks from the dashboard only and its official MCP server (render-oss/render-mcp-server v0.3.0, checked 2026-07-12) ships **no webhook tools at all** — an agent can wire up its own integrations against bex (`list_/create_/delete_webhook_endpoint`, w3/m11) with the signing secret returned exactly once at creation.
- **Usage metering** — `GET /v1/usage` + GraphQL `usage(period: $period)` + MCP `get_usage` tool return month-to-date or historical-month usage (instance-seconds per tier, egress bytes, build seconds, storage GB-seconds) for the caller's workspace — including managed Postgres and Key Value instances (`resourceKind: "postgres"` / `"key_value"`). All three surfaces accept the same `period: YYYY-MM` argument with identical semantics and echo it in the response body. **`ownerId` workspace targeting (w6/m18):** all three surfaces also accept `ownerId` (REST query param, GraphQL arg, MCP `core.SelectedWorkspace` precedence) alongside `period`, and the dashboard's Usage page follows the switcher — a multi-workspace caller previously always got their default workspace's usage regardless of which workspace they meant. **Dashboard** (**w8/m6 + w8/m9**): month picker on the Usage page lets users select any of the last 6 months; a 3-month trend view (one SvgLineChart per meter) shows totals over the last three calendar months; storage has its own GB-hours table. **Render comparison (re-verified 2026-07-14):** Render's [pricing page](https://render.com/pricing) lists Postgres and Key Value as plan-priced compute and says compute is prorated by the second; its [Postgres flexible-plan documentation](https://render.com/docs/postgresql-refresh) sets Postgres storage at `$0.30/GB-month`, prorated by the second. Render's [dashboard documentation](https://render.com/docs/render-dashboard) exposes accrued charges and included-usage counters only in the Billing UI, with no public REST/GraphQL/MCP billing endpoint. **Verdict:** parity on compute and on the Postgres storage rate dimension; deliberate bex extension on raw quantities and API access. **Documented drift:** Render prices provisioned Postgres capacity and has no separate Key Value storage line; bex prices actual used PVC bytes at 30% below Render for both datastore kinds. See [docs/ADR023-usage-metering.md](ADR023-usage-metering.md).
- **In-app Audit Log viewer** — dashboard Settings → **Security & Compliance** → Audit Log (`w4/m14`, regrouped `w4/m15`) is a live, paginated, in-app table. Render's dashboard has no in-app audit-log table at all — only a date-range CSV export under Workspace Settings → Compliance (render.com/docs/audit-logs, checked 2026-07-11); bex places its richer table under the analogous Security & Compliance grouping.
- **GitHub repo listing & connection status over the API** — `GET /v1/repos` + MCP `list_repos`/`get_git_connection` return the connected installation's repositories (private included) and the connection's account/install URL, so "which of my repos can you deploy?" is one agent call. Render lists repos only through its private dashboard API and its MCP has no repo tools (w2/m8, [ADR026-github-integration.md](ADR026-github-integration.md)). **`ownerId` workspace targeting (w6/m18):** connect/get-connection/disconnect/repo-list all accept `ownerId` (REST query param, GraphQL arg; MCP on the two read tools — `list_repos`/`get_git_connection` — via `core.SelectedWorkspace`), so a multi-workspace caller can check or list a **non-default** workspace's GitHub connection explicitly rather than only ever resolving their default one.
- **A user-consented OAuth 2.1 provider for third-party agents** — an MCP client self-registers (DCR), sends its user through bex's own login, and the user grants it on a real **consent screen**; the agent then holds its own revocable, scoped token (w4/m9 + w4/m16, [ADR012-auth.md §7](ADR012-auth.md#7-oauth-21-provider-for-agents-one-dashboard-login-first-party-sessions--third-party-clients-w4m9)). Render has **no OAuth2 provider or consent surface at all** — agents and CI use dashboard-minted API keys, so there is no Render shape to mirror here (re-checked against api-docs.render.com + render.com/docs 2026-07-12: the only credential is an account-scoped API key). No operator blessing is required: `skip_consent`/`OAUTH_TRUSTED_CLIENTS` only _skips_ the screen for first-party clients. **Cross-surface consistency:** bex-api never distinguishes a consented client from a blessed one — it introspects the bearer and checks the audience, with no trusted-client branch anywhere in `lego/backend`, so both tokens authorize identically at `/mcp`, REST, and GraphQL (evidence: [scripts/auth-oauth21-e2e.sh](../scripts/auth-oauth21-e2e.sh) legs 8 and 10 assert the same 200 for each). **Both login states (w4/m17):** the recipe works whether or not the user is already signed into the dashboard — the signed-in path (the commonest one: Kratos accepts the login challenge outright and answers the page's AJAX call with `200 null`) is asserted by leg 13, which drives a second authorization from a reused, already-signed-in cookie jar and fails if the browser is made to re-authenticate. **Revocable in practice, not just in theory (w4/m18):** "revocable, scoped token" was only half true from m16 to m18 — remembered consent shipped with no UI to undo it. Settings → Security & Compliance → **Connected agents** now lists every client the user has authorized (name, scopes, grant date, from Hydra's `listOAuth2ConsentSessions`) and revokes one with `revokeOAuth2ConsentSessions(subject, client)`, which invalidates every access token that client holds immediately — proven end-to-end by leg 14, which lists the client, revokes it, and asserts the still-live token from leg 13 now 401s at `/mcp`. No bex-api surface exists for this by design (dashboard SSR only, over Hydra's admin API directly — the same pattern `hydra-consent.ts` already established); Render has nothing to compare against here either, since it has no OAuth provider to begin with.
- **Account-level session management** — Settings → Security & Compliance → **Active sessions** (w4/006, folded into w4/m18) lists every browser/device Kratos currently recognizes as the signed-in user (via the self-service `FrontendApi.listMySessions`) and offers per-session sign-out plus a one-click "sign out other sessions" (`disableMySession`/`disableMyOtherSessions`) — the browser-session counterpart of Connected Agents' OAuth-grant revocation. Not a Render mirror: session/device management sits with whatever identity provider a Render-hosted app happens to use, not with Render's own dashboard (Render is not itself an identity provider for its users' end customers the way Kratos is bex's own login backend), so there is no Render capability row this compares against — it is bex's own account-security surface, Kratos-owned like login and MFA.
- **Denied-read audit trail** (`w4/m20/t001`) — a denied `can_view`/`can_view_logs`/`can_view_sensitive` check now leaves a `status: denied` `audit_events` row (successful reads still don't, by volume). Render's documented audit-log event vocabulary (render.com/docs/audit-logs) covers privileged account/team/service-lifecycle actions only — member added/removed, service created/deleted, and the like — with no "someone tried to view X and was refused" event class at all; bex's binary allowed/denied `Outcome` already covers this uniformly (same field, same rendering, `internal/audit`/`internal/events`) so no new vocabulary or schema was needed, just widening which relations reach the sink.

The MCP `query_render_postgres` tool itself remains parity, not a superset — it is read-only on both platforms. The dashboard console and its explicitly confirmed write mode are a deliberate bex extension; no write flag was added to the agent tool.
