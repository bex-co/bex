# Render parity matrix — REST · GraphQL · MCP · UI

A single, evidence-based map of how far bex actually matches [render.com](https://render.com), one row per Render capability across the four surfaces bex mirrors. It replaces scattered "Render-compatible" assertions with a checkable ledger: what has parity, what diverges, what is missing, and what is a deliberate non-goal — each cell backed by a pointer to code (bex side) or Render's own spec/docs (Render side).

**Ledger layout (2026-11-23, w10/m607).** This file is the index of the parity ledger. Each section's rows live in their own file under [ADR018/](ADR018/), which the section's heading below points at: amend a row there, not here. The headings stay here so every `ADR018-render-parity.md#…` link still resolves; a new section gets a file of its own and a pointer heading here. The MCP pins, the upstream drift re-baseline rounds, the mobile scope notes and the dated cross-cutting corrections that used to open this file are in [ADR018/surface-pins-and-corrections.md](ADR018/surface-pins-and-corrections.md). The split keeps every file far below the 1 MiB blob limit `scripts/repo-artifact-guard.sh` enforces.

**Method.** Four API-focused passes from 2026-07-08, re-verified against Render's live API/docs through 2026-07-27, plus an authenticated page-by-page dashboard walk on 2026-07-15: bex's public REST vs Render's OpenAPI spec; bex's GraphQL vs Render's captured dashboard operations; bex's MCP tools vs the current `render-oss/render-mcp-server`; and bex's dashboard vs Render's live dashboard. The design record for bex's side is [ADR006-bex-api.md](ADR006-bex-api.md) ("one Core, three adapters"); this doc is the parity ledger over it. [Dashboard-walk evidence](render-artifacts/dashboard-walk/README.md). Render's changelog covers what no API pin sees, such as a feature Render ships only in its dashboard (w4/m553, 2026-11-22). Every entry since its first (2023-03-31) has one row in [render-changelog.md](render-artifacts/render-changelog.md): matched, partial, a gap with the board item that owns it, a non-goal, or n/a with the reason. The weekly `render-changelog` job in `.github/workflows/render-schema-drift.yml` runs `scripts/render-changelog-drift.sh`, which reads Render's Atom feed and changelog page and fails on an entry with no row or a row whose entry is gone.

**What the MCP column scores.** A `✅` in the MCP column means the **capability is reachable over MCP** — it has never meant bex ships a tool with Render's name for it, and the Legend's "Render capability = a noun/verb Render exposes on _any_ of its surfaces" already implies this. Stating it explicitly because it is load-bearing for `w1/m71`: consolidating bex-invented tools (folding per-field `set_*` setters into a resource's `update_*`) preserves every `✅` in this column, because the capability stays reachable. Renaming or removing a `Parity1to1` tool does **not** preserve parity, because an agent written against Render's official server calls it by name. The 15 `Parity1to1` tools, and the upstream arguments of the 9 `Superset` ones, are the contract; the 223 `Extension` tools are bex's to reshape.

**Legend.** ✅ parity (evidence pointer) · ◐ partial (divergence documented) · ✖ missing (gap — see backlog) · — deliberate non-goal (rationale inline). "Render capability" = a noun/verb Render exposes on _any_ of its surfaces; a `—` on the REST column can still be a `✅` elsewhere (Render itself splits work across surfaces — e.g. read-only SQL is MCP-only on both sides).

**A fifth surface.** REST/GraphQL/MCP/UI above are bex's own adapters; Render's _official CLI_ (`render-oss/cli`) is a fifth, external surface bex never builds its own competitor to (`.pm/DO_NOT_DO.md`) — [docs/cli-compatibility-checklist.md](cli-compatibility-checklist.md) runs it unmodified against bex-api and tracks the result the same way this ledger does. It surfaced several REST wire-format bugs this matrix's capability-level rows don't catch. Its fixed-client browser login is implemented through Hydra device authorization and locally verified with two real users, refresh rotation, and scoped logout (`w4/m27`); production rollout evidence is still pending. **Agent skills (w8/m143):** Render's `render skills install` gives an agent skills for the platform the user is on. The `bex` launcher therefore replaces upstream's `skills` tree, which installed Render's skills, with an embedded bex pack under the same subcommands and flags. That is parity of behavior, not a divergence ([bex-cli.md](bex-cli.md), checklist `skills` row).

> **Headline.** bex has real parity on the **service lifecycle, env vars, environment groups, secret files, custom domains, managed Postgres lifecycle/data protection/logs, managed Key Value, service logs, metrics, and autoscaling config** core across all four surfaces, and is _ahead_ of Render on several AI-native verbs (API-key management over the API, deploy-from-chat, inbound push webhooks, and GraphQL/MCP webhook management — [§ bex ahead of Render](ADR018/bex-ahead-of-render.md#bex-ahead-of-render)). The remaining wire-format and UI-depth gaps are mapped to owning milestones/notes in the [§ Gap backlog](ADR018/gap-backlog.md#gap-backlog). (Background-worker and cron-job service types shipped in w1/m15; environment groups + secret files in w1/m16; managed Key Value landed on REST/GraphQL/MCP in w2/m7 and the dashboard in w5/m12; autoscaling config shipped in w1/m20; static sites — build → object-store origin + redirects/rewrites/headers — shipped in w1/m21; deploys as first-class objects — list/get/trigger in w2/m5, cancel/rollback in w2/m10, deploy-body params (commitId/clearCache/deployMode) + restart consolidation in w2/m30 — shipped across REST/GraphQL/MCP.)

## API contract

**Workspace-scoped credential and event details (w4/m134, 2026-09-22).** Registry credential by-ID reads, updates, and deletes accept optional REST query / GraphQL `ownerId`; GraphQL `serviceEvent` now accepts the same selector already honored by REST event detail. MCP uses its existing per-call `workspaceId`. The dashboard passes its selected workspace for credential details and mutations. Omission preserves the default-workspace behavior, and membership/role checks still precede workspace-scoped store access. These selectors are a bex addition: Render's [credential retrieval](https://api-docs.render.com/reference/retrieve-registry-credential) and [event retrieval](https://api-docs.render.com/reference/retrieve-event) references declare only the resource ID, with [API keys covering member workspaces](https://api-docs.render.com/reference/authentication). Bex retains the documented default-workspace lookup instead of introducing a global ID lookup.

### Allowlisted response-schema divergences (w3/m272)

**Every Render-shaped response in the test suites is validated (w3/m272, 2026-11-05; closed across all served operations in w5/m581, 2026-11-23).** The `internal/api` handler every API test builds (`buildHandler`) and the `internal/apps` httptest muxes (`validated`) run each `/v1` response that matches an operation in the pinned spec through `internal/rendertest`. A response must use a status the operation documents and match that status's schema: enums, formats, unions and required keys. HTTP `204 No Content` responses must carry an empty body and no `Content-Type` header (`w5/m581` caught and fixed `DELETE /v1/build-sources/{buildSourceId}` sending `core.HandleJSON`'s `null\n`, and also switched `POST`/`PATCH /v1/build-sources` from `core.DecodeJSON` to `core.DecodeBody` so unknown-field or malformed JSON returns 400 instead of 500). A service's `serviceDetails` is checked against the union member its `type` selects, field by field. An error status the operation does not list (Render's per-operation lists are incomplete; none lists 405) must still carry Render's `error` body. A success status the operation does not list fails. The production gate decides which routes are Render operations, so bex-native routes are not validated. A violation fails the test that served it unless `rendertest.Allowlist` excuses it. That list only shrinks: `TestAllowlistOnlyShrinks` pins its size, 22 since w4/710 (2026-11-19; it was 109 before w10/m373 and 23 after w9/m473). A full run with the test database fails any entry that no response reproduces. Each entry cites one row below. Since `w5/m581`, `internal/api`'s `TestMain` also fails any full package run (`rendertest.FullPackageRun()`) that leaves any served non-streaming Render operation (pinned spec minus `renderOperationOmissions`) without a validated 2xx response (`conformanceExemptions` exempts only `subscribe-logs`, which is an SSE stream; `conformanceRefusalOnly` allows `post-job` to validate against Render's 410 error envelope per `.pm/DO_NOT_DO.md`). The temporary `dropUndefinedMetricValueUnit` workaround for Render's earlier `values.items.required` typo was retired in round 9 (`w4/m596`, 2026-11-23) once Render fixed `values.items.required` to `["timestamp","value"]`.

**Unpaged REST lists answer Render's first page (user decision 2026-11-13, w22/007, w10/m377).** Every list operation in the pinned contract that bex serves, called with neither `cursor` nor `limit`, answers Render's `limitParam` default of 20 with the cursor that continues it (the audit log's `auditLogLimitParam`, 20 up to 1000). The last six that did not (sandboxes, static-site routes and headers, which returned everything; deploys and jobs, which returned the newest 100; log label values, which ignored `limit`) were switched; `TestEveryServedRenderListIsClassified` (`internal/api/render_list_paging_test.go`) walks every pinned list operation and fails on one with no recorded evidence. **Scope (the proposal's recommendation, not yet confirmed by the user):** REST only. GraphQL is bex's own API, read by the dashboard and the mobile app, with no Render counterpart, and keeps returning whole lists; MCP follows Render's MCP server, whose pinned list tools take no paging arguments, and is unchanged.

**Production-shaped fixtures (w10/m373).** These omissions are fixture gaps, not divergences, and no longer have entries. The fake API server stamps `managedFields` and returns them as a real one does (`rendertest.Stamped`, `WithReturnManagedFields`), so every fixture has the `updatedAt` production always serves. A field a server lacks the source for (`region` without `BEX_REGION`, `dashboardUrl` without `BEX_DASHBOARD_URL`, `owner`/`ownerId` without the workspace store, `owner.email` without the identity reader) is excused by `rendertest.Wrap`'s `Source` list only when the server under test really lacks that source, so a production-configured server is held to the full schema: `TestRenderConformance` runs with a region and dashboard URL, and `TestResourceRESTMetadataUsesOwnWorkspaceAndAuthoritativeSources` with every source. A disk's `id` comes from the control-plane row a create writes only for a workspace's service, so it belongs to the workspace source. Fixture objects also carry what every bex-api write does: `Stamped` gives a seeded App bex-api wrote the tier its create sets when no plan is asked for (`starter`, so `plan` is present; objects a test creates through the fake client get none, so a create that stopped setting one still fails), and `rendertest.KubectlApplied` marks the hand-applied CR that may lack one. Static-site fixtures carry the `publishPath` every create path requires.

Responses fixed when the check first ran: `POST /v1/registrycredentials` answers Render's documented `200`, not `201`. `GET /v1/blueprints/{id}` always carries Render's required `resources`, `[]` for a Blueprint that declares none (GraphQL and MCP unchanged). REST log lines no longer carry the `container` label, which is outside Render's closed label-name enum. GraphQL never exposed it; MCP `list_logs` still returns it in its `labels` map. The `/v1/key-value` conformance cases now validate against the current `list-key-value`/`retrieve-key-value` operations. Their `keyValue` envelope conforms, which retired the old `list-redis` entry.
