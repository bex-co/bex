# Deployment sources & IaC

This is the Deployment sources & IaC part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), moved out of it on 2026-11-23 (w10/m607) to keep the ledger under the 1 MiB blob limit. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

**Blueprint automatic correctness repair (w1/m182, 2026-10-20):** automatic sync consumes an immutable snapshot of the current authoritative branch, rechecks it before apply, and fences claims/reclaimed workers through existing execution authority. Accepted and consumed commits remain distinguishable in existing intent evidence and sync-history notes. Manual reviewed-commit pins retain their behavior. Ordering, coalescing, recovery and force-push rules are bex choices; Render documents automatic syncing but not those guarantees. See [ADR049's source-ordering record](../ADR049-render-yaml-parity.md#automatic-source-ordering-and-recovery-w1m182-2026-10-20). Existing partial assessments below remain applicable.

**Initial Blueprint group composition (w4/m148, 2026-10-02).** New App creation prepares authorized group references and membership before publishing its first CR; a durable initialization gate prevents the database projector from dispatching a partial configuration. The returned first deploy keeps its identity. Existing group auto-deploy policy is unchanged. Real-Postgres lifecycle/compensation tests cover this protocol; hosted build/HTTP and first-deploy acceptance remain open. See [ADR049](../ADR049-render-yaml-parity.md#initial-environment-group-composition-w4m148) for failure and recovery boundaries.

**Blueprint wire-shape divergences (2026-08-16).** Bex creates and immediately syncs a Git-connected Blueprint, so the stored Blueprint never rests in Render's `created` status; it transitions through `syncing` to `in_sync` or `error`. This is deliberate immediate feedback, not an unreachable state to emulate. **Update (w4/368, 2026-10-19):** `created` does have one reachable path — a Blueprint that has genuinely never applied (deploy-auto-registered before its first recorded sync, pre-m62 `active` rows) projects as `created` until its first recorded sync stamps `lastSyncAt`; deploy auto-registration itself now records that first success run, so the state is transient there rather than permanent. Blueprint `resources[]` emits the canonical current `key_value` type only, never Render's deprecated `redis` alias; the deprecated spelling is intentionally read-compatible but not emitted. Environment groups are included as `environment_group` resources, and current-state plans represent an absent group as `create`, and an existing group as `update` only when the sync would write one of its variables, without exposing values (w8/376).

**Blueprint-by-id REST routes were unreachable until w6/m96 (2026-08-26).** `w2/m62`'s Definition of done said `GET/PATCH/DELETE /v1/blueprints/{id}` and `GET /v1/blueprints/{id}/syncs` "behave per Render's OpenAPI", and it shipped closed — but nothing ever exercised those routes through the composed server. The only REST test built a bare `http.NewServeMux()`, which never crosses `internal/api/render_openapi.go`'s validator, so CI could not see that **every** call to all four operations was rejected before authz or lookup: Render's spec pins `blueprintId` to `^exs-[0-9a-z]{20}$` and bex mints `blp-` (`docs/ADR020-identifiers.md`, Known deviations). Since w2/m269 (2026-11-05) every surface answers with Render's `exs-` spelling and accepts both; `blp-` is only the durable storage key (ADR020 "Blueprint public aliases"). Found live on `api.bex.co` against a real blueprint, 2026-08-26. Driving those routes through the real validator then exposed two more defects on the same path — Render's four blueprint operations declare no `ownerId`, so the strict-query gate 400'd any call naming a workspace (the same concession the webhook and event routes already carry, never extended here), and every blueprint verb returned its raw store error, so a missing or other-workspace id came back `500 internal error` rather than 404 on **all three** surfaces, not just REST. All three are fixed; the by-id verbs now return 200/404/403 as distinct outcomes, identically across REST, GraphQL and MCP (`TestBlueprintByIDNotFoundIsIdenticalAcrossSurfaces`). The coverage gap itself is closed by `TestBlueprintIDRoutesPassTheRenderOpenAPIGate` (real `apps.Service` behind the real validator) and `TestEveryConstrainedIDPathParameterAcceptsItsBexID`, which checks every pattern-constrained id path parameter on a bex-served route against the id prefix that addresses it, so a future spec refresh cannot silently reintroduce the class on any kind. **The two blueprint lists now use Render's envelope (w4/157, 2026-09-27).** `GET /v1/blueprints` and `GET /v1/blueprints/{id}/syncs` returned bare rows with no `cursor`, flattening a sync's `commit.id` to `commitId`, so a Render client decoding `blueprintWithCursor`/`syncWithCursor` got empty objects and could not page. Both now return `[{blueprint|sync, cursor}]`, like every other bex list. The blueprint list pages with `limit`/`cursor` via `core.StablePage`, and its rows drop the whole manifest, which stays on the by-id read. Sync rows nest `commit: {id}`, and a run with no resolved commit reports an empty id rather than a fabricated one. Both are validated against the pinned schemas (`TestBlueprintIDRoutesPassTheRenderOpenAPIGate`). Sync ids answer as Render's `exe-` since w2/m288 (2026-11-08), so the sync rows conform in full (ADR020). GraphQL and MCP keep their bex-native shapes.

**Current Blueprint contract (ADR049 / w1/m63, 2026-08-02).** `render.yaml` is canonical; `bex.yml` is an identical-grammar, warning-emitting filename alias only. Every validation, preview, deploy, sync, REST, GraphQL, MCP, dashboard, and helper path enters the pinned-schema compiler before a write. Unknown fields are closed-world errors; unsupported Render capabilities (including previews) are explicit pre-write refusals. Per-resource `region` is no longer one: since w8/152 (2026-10-29) it is accepted and normalized to `BEX_REGION`, as on create, and since w9/105 (2026-11-18) a resource the file creates reads its declared region back. Validation reports source code/path/line/column and, when current non-secret state is readable, a `current_state` action plan. Secret-backed env groups stay value-safe without suppressing that plan: absent is `create`, and existing is `update` of `envVars` only when the sync would write a declared variable, else `noop` (w8/376, 2026-11-21); a caller who may not read the group's values gets the `update` with a message instead of the answer. A `structural` plan remains only when the env-group resolver itself is unavailable. The historical detail in the row below predates this correction and is context, not the current contract. See [ADR049](../ADR049-render-yaml-parity.md), [ADR006](../ADR006-bex-api.md#renderyaml--the-blueprint-manifest-w1m24), and the capability registry at `lego/backend/internal/apps/schema/capabilities.json`.

Each rule as bex ships it ([ADR004 § Initial deploy hook](../ADR004-app-deployment.md#initial-deploy-hook-once-after-the-first-release-is-live--w33m435)):

1. **A failed hook leaves the deploy live and runs again after the next deploy.** The release is live before the hook starts, and it stays live. A hook that exits non-zero, is killed out of memory, outruns its window or cannot start changes neither the service's phase nor the deploy's `status`, which stays `live`. The deploy's log reads `==> Initial deploy hook failed: <cause>` (for example "the initial deploy hook exited with code 1"), then `==> The deploy stays live. The hook runs again after the next deploy goes live.` (`lego/backend/internal/logs/progress.go`). The deploy record's `initialDeployHookStatus` is `failed`. The hook stays owed (`App.OwedInitialDeployHook`, `lego/types/v1alpha1/predeploy.go`), but it is never started again for the release it failed on. The next release to go live runs it (`reconcileInitialDeployHook`, `lego/operator/internal/controller/initial_deploy_hook.go`), and so on until one run succeeds.
2. **A hook added late runs.** A hook that a Blueprint sync adds to a service that has already deployed is owed like any other. It runs once, after the service's next deploy goes live; normally that is the deploy the sync's change opens. Render's "after a service's _first_ successful deploy" reads as "never" for this case.
3. **The bound is the pre-deploy command's: 30 minutes, one attempt.** The hook's Job has the pre-deploy step's 30-minute `activeDeadlineSeconds` (`predeployTimeout`, `lego/operator/internal/predeploy/predeploy.go`) and `BackoffLimit 0`, and each release gets at most one Job. A hook still running at 30 minutes is ended, and it fails under rule 1 with "the initial deploy hook did not finish within its 30-minute window".
