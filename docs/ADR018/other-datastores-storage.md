# Other datastores & storage

This is the Other datastores & storage part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), moved out of it on 2026-11-23 (w10/m607) to keep the ledger under the 1 MiB blob limit. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

**Key Value persistence handoff (w4/m153, 2026-10-02).** Changes between Snapshot only and Journal + Snapshot use an offline init conversion before the new server can become Ready, preventing reuse of an old journal when enabling AOF. Reads on REST/GraphQL/MCP retain the desired mode and expose `config_restart` during conversion/restart; the dashboard reports an update accepted, not data-plane completion. Switching to or from Off intentionally discards data, with English/Chinese warnings and a typed dashboard confirmation. [Render's official documentation](https://render.com/docs/key-value#data-persistence) documents Off-transition loss and a restart on mode changes; its paid-only persistence remains an intentional difference from bex's durable Free default. The Render comparison is documentation-only, with no observed paid mutation or confirmation-dialog behavior. Hosted data-survival acceptance is tracked separately from source/local tests in w4/m153; see [ADR021](../ADR021-keyvalue-management.md) for the handoff and restore precedent.

**Key Value list pagination (w8/m13):** ✅ with the same REST/GraphQL semantics as Postgres. Render's current official MCP spelling is `list_key_value` with the shared optional `workspaceId`; bex exposes that tool and no longer registers the bex-only `list_key_value_instances`. It returns the complete per-call workspace list and exposes no cursor/limit arguments.

**Protected Environment destructive-verb parity (w6/m37, 2026-07-17):** Key Value delete and suspend now resolve the CR's Environment label and require the exact server-issued `sudo <verb> key value <name>` phrase for protected members across REST, GraphQL, MCP suspend, and the dashboard. Resume and environment-less/unprotected resources are unchanged. Render's official MCP server has no datastore delete or suspend tools: bex adds no delete tool, while `suspend_keyvalue` / `resume_keyvalue` are deliberate lifecycle/safety extensions carrying the same guard (and restore path) as the other surfaces.

**Grow-only PVC and health correction (w2/m60):** a Key Value plan increase now patches the bound `data-<red-id>-0` PVC when its StorageClass allows expansion, exposes pending/failed convergence through internal CR conditions, and withholds Ready until both capacity and the current StatefulSet revision converge. Shrink and non-expandable classes leave the PVC untouched with actionable status and bounded retry. REST/GraphQL/MCP/UI continue to expose Render's plan/status fields from the shared resource view; the internal `StorageReady` detail is deliberately not promoted into a new Render-facing API. Existing dashboard `unavailable`/creating states therefore remain truthful during resize or failed rollout.

**External datastore connections: the 1 h idle close (w6/148, w6/149, 2026-11-20) — ⚠️ divergence, awaiting the user's decision ([w6/149](../../.pm/w6/blocked/149.md)).** Render documents no close of an idle or long-lived external Key Value or Postgres connection ([Key Value](https://render.com/docs/key-value), read 2026-11-20), Valkey's own `timeout` "does not apply to Pub/Sub clients" ([valkey.io/topics/clients](https://valkey.io/topics/clients/)), and PostgreSQL closes no idle session by default. bex's SNI proxies closed a relayed stream after 1 h idle, and 24 h after it was routed however busy (F6). w6/148 made bytes in either direction count, so the proxies no longer close a subscriber that only receives, and w6/149 removed both bounds from the proxies (`BEX_PROXY_IDLE_TIMEOUT`, `BEX_KV_PROXY_IDLE_TIMEOUT` and their `_MAX_LIFETIME` pair stay as unset incident levers), so a busy stream lives past 24 h. **The gap that remains is the edge load balancer's.** Every external stream crosses one of the Hetzner load balancer's TCP services, which closes a flow that has carried no data for an hour, and Hetzner exposes no idle setting on a TCP service. Measured on production on 2026-11-20: a silent TCP flow through its HTTP listener, where Traefik's own read deadline is 6,000 s, got the load balancer's FIN exactly 3,600 s after it opened, while the same flow straight to a Traefik pod stayed open past the hour. Probes through both datastore listeners showed the same rule later that day, once the proxies ran with no bounds (pin `11b1e8f85f06`). A client that sent and received nothing was closed 3,600 s after its last byte, although it sent a TCP keepalive every 15 s. A `SUBSCRIBE` or `LISTEN` client that sent nothing after subscribing, but got a message every 10 min, stayed open past the hour. So the load balancer counts bytes in either direction, and TCP keepalive probes do not count. A `LISTEN` or `SUBSCRIBE` client that gets nothing for an hour, and an idle pool or `psql` session, are therefore still closed at 1 h without notice. Closing the gap needs the datastore ports off that load balancer or Hetzner raising its timeout; otherwise it stands only with the user's sign-off here. An SNI-proxy roll also closes a long-lived stream, 1 h after the old pod's `SIGTERM` ([ADR021 § 10](../ADR021-keyvalue-management.md#10-a-platform-deploy-rolls-no-stores-proxy-w6m469-w6m470-2026-11-18)). In-cluster clients are unaffected ([ADR009 § External connection admission](../ADR009-postgresql-management.md#external-connection-admission-w6m457-2026-11-17)).
