# Services & lifecycle

This is the Services & lifecycle part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), moved out of it on 2026-11-23 (w10/054) to keep the ledger under the 1 MiB blob limit. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

**CI-gated dispatch recovery (w1/m181, 2026-10-20).** Render documents `checksPass` and the success/neutral/skipped, zero-check and failure rules. Bex's source-bound pending acceptance, atomic release receipt, idempotent deploy-history recovery and latest-branch fencing repair its own failure windows; **Render's corresponding ordering, crash-recovery and exactly-once guarantees are undocumented and unmeasured**. The REST/GraphQL/MCP/dashboard gate fields are unchanged. **Live (2026-10-26):** once the production App subscribed to Check suite, a real GitHub Actions repository behaved as Render documents. A failing check did not deploy. A passing check deployed about 4s after the check run completed. Of two back-to-back pushes, only the newer one deployed. Other Apps' queued suites with no check runs did not block the deploy (`w1/m181` t006). [Evidence and explicit bex choices](../render-artifacts/auto-deploy-checks-pass.md#dispatch-recovery-w1m181-correctness-extension-2026-10-20).

**Service display-name validation (w8/034, 2026-10-02).** The shared rename path rejects control characters and Unicode line separators before trimming, labels longer than 100 Unicode code points after trimming. REST `PATCH name` / `displayName`, GraphQL `setDisplayName`, and MCP `update_service(displayName:)` return the same actionable refusal; the dashboard Settings row displays the GraphQL error and retains a rejected draft. Ordinary edge spaces still trim and an empty value still clears the label. Authorization, deletion checks, workspace uniqueness, immutable IDs, routing, and deploy behavior stay intact. **Bex policy, Render limit unverified:** Render's [update-service schema](https://api-docs.render.com/reference/update-service) declares `name` as a string without a published maximum or pattern; 100 code points is an explicit Bex limit. **ID-shaped names accepted (w5/m118, 2026-10-24):** the reservation of names shaped like a resource ID (w8/034, extended to Postgres and Key Value by w8/049) is withdrawn on every surface, as Render sets no such limit. bex-api addresses a datastore only by its id and resolves a service id before its name, so an ID-shaped label cannot shadow another resource; `NAME_RESOURCE_ID_RESERVED` is retired. The pinned CLI and dashboard normalize edge whitespace before submitting, so raw edge-control rejection is an API-input contract. The CLI cannot express an empty clear; direct REST/GraphQL/MCP and the dashboard preserve clearing. Existing stored labels are not rewritten.

**Service rename publication (w4/m225, 2026-10-17).** After `setDisplayName` commits, the dashboard settles every active Server and Services read that started before the write, then re-reads the service with a fresh, non-deduplicated request and only then refreshes the route, so an older response can no longer put the previous label back over the saved one. A failed re-read after a committed rename is a warning with a read-only Try again, never a second rename. The API contract is unchanged.

**Image deploy input validation (w8/m49, 2026-10-02).** Create, source update, Blueprint validation/apply, and deploy overrides share OCI reference validation: repository paths must be lowercase, tags may contain uppercase characters, and digests must match their algorithm's hexadecimal length. Errors distinguish malformed references from private/reserved addresses and non-public registry hosts. **Since w5/171 (2026-10-23) any public registry is accepted, as on Render** ([render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image): public images from any reachable registry). The fixed allowlist is gone, and names of the platform's own networks (`.svc`, `.cluster.local`, `.local`, `.internal`, single-label) are refused. Node bootstraps deny containerd's cgroup any link-local destination, so a registry name that rebinds to the metadata service gets nothing ([ADR022](../ADR022-tenant-isolation.md) § Image pulls from the node network). Render's Blueprint templates on `cgr.dev` (minio, langfuse) now validate, and render-examples is at 92 of 170 valid. **Rollout (w5/174, 2026-10-24):** every node pool was rolled onto the new bootstrap; the rule was verified on a replaced node, and production then dropped its `BEX_PUBLIC_IMAGE_REGISTRIES=false` pin. Any public registry is now accepted in every workspace. REST, GraphQL, and MCP reject caller `commitId` on image-backed services before changing settings or creating a deploy. Use `imageUrl` with a tag or digest instead. The dashboard already offers specific-commit deployment only for repository-backed non-cron services and displays the shared GraphQL error. Render's [CLI documentation](https://render.com/docs/cli) documents this source split; its [create-deploy reference](https://api-docs.render.com/reference/create-deploy) additionally restricts image overrides to the configured host/repository/name. Since w8/042 (2026-10-03) bex enforces that restriction too: a per-deploy image must keep the saved image's registry host, repository and image name (Docker Hub short forms normalized), and only the tag or digest changes, without changing the saved image. Any other image is a named 400 on REST, GraphQL, MCP and the deploy hook. The exact live Render response to an image-service `commitId` is unverified; Bex's named 400 is not presented as an observed Render response. Legacy malformed references already in Kubernetes receive an immediate `InvalidImageName` diagnosis on rollout and pre-deploy paths. **Registry rate limits (w5/176, 2026-11-04):** Render pulls from the registry on every deploy and restart and documents a 429 with three remedies: wait for the limit to reset, use a credential for an account with a higher limit, or mirror the image ([render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image)). bex matches the first two. A 429 or 5xx on the image metadata read keeps the deploy open as `ImageRegistryRateLimited` and retries it (w4/m243 t008, `e3e0f9eea`), and a workspace `docker.io` registry credential authenticates both the metadata read and the pull. Authenticating anonymous Docker Hub reads with a platform account is bex-specific hardening for the shared egress quota, tracked in w5/177; it is not a parity gap.

> **Shared-hosting security update (corrected 2026-08-18, amended 2026-11-21; supersedes the 2026-08-08 "disabled" wording).** Shared platform hosting remains **enabled**: production configures `onbex.co` as `BEX_BASE_DOMAIN`. The cross-tenant cookie risk is real (`onbex.co` is not on the Public Suffix List, so a tenant can set a parent-scoped cookie a sibling receives) and is **accepted**, through open signup too. This is a parity divergence, since `onrender.com` is on the PSL, and the user signed it off on 2026-11-21: a PSL submission needs a user count bex cannot reach without staying open. Interim tenant guidance is host-only / `__Host-` cookies. Neither unsetting `BEX_BASE_DOMAIN` nor submitting `onbex.co` to the PSL is currently authorized — unsetting caused the second production outage; `scripts/gitops-validate.sh` now rejects an empty production hosting suffix. Canonical decision and reopening trigger: [`.pm/DO_NOT_DO.md` `#PSL`](../../.pm/DO_NOT_DO.md). Manager/static-server still refuse an _ordinary registrable replacement_ that is not a browser-recognized private Public Suffix; that gate does not authorize emptying the configured base domain.
