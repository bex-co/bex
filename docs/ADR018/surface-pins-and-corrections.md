**MCP result shapes are pinned too (w4/m378, 2026-11-14).** The tools pin above records names, arguments, types and hints; it never recorded what a tool _answers_, and sixteen shared tools had drifted into bex's own shapes: lists wrapped in objects (`{"services":[…]}`), `list_deploys`' cursor moved into a field, `list_logs` lines with a label map keyed `service` and no `id`, `get_metrics` as `{series:[{labels:{…}, points}]}`, the creates without `deployId`, datastores with flat `ownerId`/`maxmemoryPolicy`/`persistenceMode`, and `query_render_postgres` as `{columns, rows, rowCount, truncated}`. Each now answers the text Render's server sends for the same call (`render-oss/render-mcp-server@23fb336`):

- `list_services`, `list_workspaces`, `list_log_label_values`: a bare JSON array (`list_workspaces` items are REST's owner objects, `GET /v1/owners` items); `list_postgres_instances` and `list_key_value` the same, or Render's sentence (`No Postgres instances found`, `No Key Value instances found`) for an empty workspace. `list_deploys` and `list_events`: the array, then `\n\n cursor: <id>` (`""` on an empty page). An empty array is `[]`, as upstream's own `list_events` writes it, where upstream's `list_services`/`list_deploys` would marshal a nil slice as `null`.
- `list_logs`: REST's `GET /v1/logs` envelope, byte-identical lines. `get_metrics`: Render's `MetricsResponse` (`resourceId`, `timeRange` echoing the call's bounds, `metrics[{type, data}]`), each `data` the REST series for that type with REST's `statusCode` label; bex's legacy multi-id `resource` array answers one such object per resource, in a JSON array.
- `create_web_service`/`create_static_site`/`create_cron_job`: Render's `{service, deployId}`, the REST create envelope (a dry run has no `deployId`). `get_key_value`/`create_key_value`/`get_postgres`/`create_postgres` and the list items: the REST objects, `owner` and Key Value's `options` included.
- `query_render_postgres`: a JSON array of row objects keyed by column name (a repeated name keeps its last column), at most 5 MB of it; past that the rows that fit, then Render's `Results truncated: …` notice as a second text item, never `isError`. There is no row cap and no per-cell or per-row refusal; a row too large for the 5 MB budget on its own answers `[]` and the first-row notice. bex keeps its 10 s statement timeout, the read-only envelope and its exact value encoding (w4/m157, w4/m158). The console (REST `POST /v1/postgres/{id}/query`, GraphQL `executeDatabaseQuery`) keeps `QueryResult` and its 500-row cap: it is bex's own extension.
- `trigger_deploy`: the deploy object, or, for a deploy that waits behind the one in progress (REST's `202`), Render's sentence `The deploy request was accepted, but the deploy has not been created yet. Use list_deploys to check on the service's deploys.` with the queued deploy as `structuredContent` (w8/378).
- Tools whose answer is an array, `arrayCursor`, plain text, or empty-list sentence carry no `structuredContent`, as Render's server sends none; `get_metrics` is likewise text-only (`structuredContent == nil`) because its legacy multi-`resource` array mode returns a JSON array while single `resourceId` returns a JSON object (`metrics/mcp_render_test.go`). Every other shared `object` tool keeps the JSON-equal object in `structuredContent` beside `Content[0].Text` (and `trigger_deploy`'s queued `emptyText` keeps the queued `Deploy` in `structuredContent`, w8/378).
- `update_blueprint` appends Render's no-op sentence (`The Blueprint already has the supplied settings. No update was needed, and planning was skipped.`) as a second text block when every supplied setting already matches (w5/m601; `pkg/blueprint/tools.go:179-181`).
