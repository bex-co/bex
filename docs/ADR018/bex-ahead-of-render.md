# bex ahead of Render

This is the bex ahead of Render part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), moved out of it on 2026-11-23 (w10/m607) to keep the ledger under the 1 MiB blob limit. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

Verbs where bex's AI-native posture exposes _more_ than Render does — tracked here so they read as deliberate supersets, not accidental drift:

- **S3-compatible object storage API and `bex s3` (w21/m498, w21/m499 and w21/m500, [ADR112](../ADR112-object-storage.md) D3; extension, reference product Amazon S3, not Render, which has no S3 API or access keys; user decision 2026-11-19).** The user decided on 2026-11-19 to serve the S3 protocol instead of `wrangler r2`'s contract, with bex verifying SigV4 itself and streaming the bytes ("option A"), and `bex s3 <…>` as the customer's command. bex serves path-style S3 at `https://objects.onbex.co` from `bex-s3`, a Deployment of its own: buckets, objects (`Range`, conditional reads, metadata), `CopyObject`, listings, the multipart family, CORS and lifecycle, with access keys (`s3k-` ids, secrets in OpenBao, persistent or ephemeral, acting as their creator with a `read` or `readwrite` ceiling), and `bex s3`, bex's own client (`ls`, `cp`, `mv`, `rm`, `sync`, `mb`, `rb`, `presign`, `cors`, `lifecycle`, `info`, and `env`, `keys` and `public` beside them) that signs and sends its own requests with the endpoint and a twelve-hour key set, needs nothing else installed and reads none of the user's own credentials or configuration (made native on 2026-11-20, w21/m540, and released as `bex-cli` v0.9.0); the bex-only REST routes `/v1/object-storage/{ownerId}/access-keys` and `.../buckets/{bucket}[/public]` have GraphQL beside them, and MCP and the dashboard have no object surface (ADR112 D10). Render's four `/v1/objects` routes and `render ea objects` are unchanged and share the store: an object put either way is listed and read the other way (`render_interop_test.go`, 2026-11-19). Verified on production on 2026-11-19 with stock aws-cli 1.44.87 (w21/m498 t019, ADR112 § Not verified) and pinned weekly by `scripts/s3-contract.sh` (aws-cli 2.39.5, rclone v1.75.2 and boto3 1.43.125 with their own defaults against the real gateway; the first run found that rclone's `x-amz-bucket-object-lock-enabled: false` was refused, now served). **Recommendations of the ADR, adopted by the worker and not user decisions** (the milestone's decision state; each can be changed in a reviewed code change): `bex-s3` as its own Deployment, no access key holding `can_manage` so publishing is `bex s3 public`, path-style addressing only, `bex s3` built on the AWS SDK for Go v2 with its generally available upload and download managers, and 12-hour ephemeral keys. **Divergences from S3, dated 2026-11-19, each bex's own and none signed off, with their reason:** buckets live in two regions only (`oregon`, `frankfurt`, and S3's names for them) because those are the Wasabi buckets bex holds, any other `LocationConstraint` answers `InvalidLocationConstraint` (D1); a bucket name is unique per workspace and never global (`BucketAlreadyOwnedByYou`, never `BucketAlreadyExists`), is 3 to 63 lowercase letters, digits and hyphens (no dots, which break the wildcard certificate of virtual-hosted style), reserves `render-*` for Render's namespace and `cloudflare` until the old routes go (D1, D7); keys are 1 to 1024 bytes with no `.` or `..` segment, doubled or leading slash, backslash or control character, because Traefik cleans paths before bex sees them (D7); versioning, ACLs, bucket policies, object lock (`false` is accepted), encryption settings, tag writes, website, replication, notifications, accelerate, Select, storage classes other than `STANDARD`, conditional writes, signed-chunk payloads and SigV2 answer 501 and are never silently ignored, `GetObjectTagging` is an empty set, a bucket with an unfinished upload cannot be deleted, copies stay in one workspace and region, the listing delimiter is one ASCII character and `ListMultipartUploads` takes none (D3, D10); path-style addressing only, since `<bucket>.objects.onbex.co` has two labels under the wildcard certificate (D3, D10); `x-amz-copy-source-if-*` are honored (412) because the AWS CLI sends them on every copy part; a listing continues after a prefix followed by U+10FFFF; a part writes no allowed audit row and a successful get at most one per key and bucket in 15 minutes (D6); downloads are served as `attachment` with `nosniff` and a sandboxing CSP (ADR095 D7); and publishing a bucket is `bex s3 public`, not a bucket policy (D4). **Not a divergence any more: user metadata names (w21/113, 2026-11-19).** bex first sent them capitalised (`X-Amz-Meta-Mtime`), so boto3 and the AWS CLI read `{'Mtime': 'v'}` where S3 returns `{'mtime': 'v'}` and `head['Metadata']['mtime']` was a `KeyError` (rclone was unaffected). Traefik canonicalises every header name it relays, which no setting turns off, so the S3 route runs a Traefik local plugin that writes `x-amz-meta-*` names in lowercase just before the head goes out; stock aws-cli 2.39.5, boto3 1.43.125 and rclone v1.75.2 read S3's answer on production, and `scripts/s3-contract.sh` pins it through the same edge (ADR112 D3). **Not a divergence any more: the confirmation of a delete (w21/115 and w21/116, 2026-11-20).** `rm` (one object, or `--recursive`), `rb --force` and `sync --delete` (not with `--dryrun`) ask `Are you sure you want to delete …? This cannot be undone. [y/N]:` before any request, in `bex ea objects delete`'s words (`object '<key>'` for one object, which `rm` fills with the object's `s3://bucket/key` since `ea objects` has no buckets), and go on only for `y` or `yes`; any other answer or an end of input prints `Delete canceled.` and exits 0 having done nothing. `--yes` (`-y`, the flag `ea objects delete` has) and the root `--confirm` ("Skip all confirmation prompts") skip the question. What a terminal is comes from the root command, as for `ea objects delete`: stdin, stdout and stderr all terminals, `TERM` not `dumb`, no `CI`, and neither `-o` nor `RENDER_OUTPUT` chosen, so a pipe, a script or CI never asks. One observation, checked against the pinned CLI on 2026-11-20: `ea objects delete` reads `--yes` only and still asks under `--confirm`, so `--confirm` skipping the question is `bex s3`'s own reading of the flag's help. The source delete of `mv` does not ask, since its bytes survive at the destination. **Divergences of `bex s3`'s own conventions, dated 2026-11-20, each bex's own and none signed off (awaiting the user's sign-off; the reference product is the familiar S3 command-line tools, since Render has no S3 command):** a recursive `cp`, `mv`, `rm` or `sync` reads `s3://b/photos` as the folder `photos/` and never touches `photos-old/` (the common tools match by characters, which makes `rm --recursive s3://b/photos` delete `photos2/` too; `ls` still matches by characters); 8 requests in flight by default, at most 10 (`--concurrency`), counted over the whole command, because the gateway admits 16 streams per workspace on each replica; a symbolic link, device or socket is skipped with a warning where the common tools follow links; `sync` compares times in whole seconds and gives a downloaded file its object's time, and a directory it cannot read stops it before any delete; one file failing is reported and the rest go on with exit `1`, while an expired key, a quota or a refused operation stops the command; `cors` and `lifecycle` are `bex s3` verbs over the S3 API's JSON documents and `bex s3api` does not exist; a persistent key reaches the command through `BEX_S3_ACCESS_KEY_ID` and `BEX_S3_SECRET_ACCESS_KEY`, and `AWS_*` variables and `~/.aws` are never read; a file over 5 GiB is refused before any request; `ls` prints UTC times; the `-o json` shape uses S3's field names (`size`, `lastModified`, `etag`) where `bex ea objects list` prints Render's (`sizeBytes`), and `--region` is optional (default `oregon`) where `ea objects` requires it. Compared 2026-11-20 with `bex ea objects` and `bex agent`: the `-o` flag and its text fallback off a terminal, exit `1` for a failure and `2` for a wrong command line, the active workspace and no per-command `--workspace`, and the REST and GraphQL routes of the key and bucket commands match; MCP and the dashboard have no object surface (ADR112 D10). **Constants, dated 2026-11-19, bex's own and unverified (Render, S3 and Wasabi publish none to match; changing one is a reviewed code change with a new dated entry here):** 100 GB and 1,000,000 objects per workspace per region; 1,000 buckets per workspace; 5 GiB per object, 10,000 parts, 100 open multipart uploads per workspace and an abort after 7 days without a part; 16 concurrent streams per workspace on each replica within a replica-wide 64; reads paced at 8 MiB/s and uploads at 16 MiB/s per workspace per replica; 100 requests a second per workspace (burst 200) and 50 per key (burst 100); 5 listings a second per workspace per replica; a monthly S3 egress budget of the larger of the stored bytes and 5 GiB (403 `QuotaExceeded`); 100 live persistent and 20 live ephemeral keys per workspace and creator, ephemeral keys at most 12 hours, revoked and expired keys deleted after 7 days; 20 failed authentications a minute per client address; a clock skew of 15 minutes. **Measured on production, 2026-11-19 (w21/m500 t001, ADR112 § Not verified):** the 16-stream cap admitted 32 of 40 slow uploads (16 on each of two replicas) and refused 8 with 503 `SlowDown`; the 100 GB gate refused a 5 GiB put with 403 `QuotaExceeded` while 15 held streams and 15 GiB stored stood on one replica; the egress budget refused every read of a workspace past 5 GiB (403 `QuotaExceeded`, the other verbs unaffected); a real 5 GiB single `PutObject` completed to `frankfurt`; a single 2 GiB `PutObject` to `oregon` ran at 15.3 MiB/s, the 16 MiB/s pace, so a 5 GiB request fits the 30-minute stream deadline for any client link above about 3 MiB/s (the 1 MiB/s read once from one `oregon` stream did not reproduce, and one connection to Wasabi's `us-west-1` tops out near 17 MiB/s on Wasabi's receive window; w21/114). Wasabi's own limits were measured as well: S3's 10,000 parts and 5 GiB per part hold, and Wasabi supports `If-None-Match` and `If-Match` on a put, which bex still answers 501 (a follow-up, not a parity item). A key whose creator lost the role was not observed live (tests cover it), and Terraform's AWS provider is not tested.
- **Public buckets: `bex s3 public` and the `pub-` host (w21/m417, rewritten for the S3 API in w21/m499 on 2026-11-19; [ADR112](../ADR112-object-storage.md) D4; extension, reference product Cloudflare R2's `r2.dev` public development URL, not Render, which has no public buckets).** `bex s3 public <bucket> enable|disable|status` calls `PUT|GET /v1/object-storage/{ownerId}/buckets/{bucket}/public` (body `{enabled}`, answer `{public, host}`, GraphQL `setObjectBucketPublic` beside it; not in Render's OpenAPI), with the person's own token: it needs the workspace admin (`can_manage`), which no S3 access key ever holds, and S3's bucket-policy calls answer 501, so a leaked key or a tool that sets a policy cannot publish customer data. The first version of this row described the toggle as wrangler's `bucket dev-url` on the Cloudflare-shaped routes, which the S3 API replaced (the routes were removed on 2026-11-19, w21/m500); with a bucket public, anyone can read the bucket's objects, read-only, at `https://pub-<xid>.<BEX_BASE_DOMAIN>`, with `Range`, conditional requests, the bucket's CORS rules and no listing at the root; private is the default. REST and GraphQL, as for the rest of the surface; the gateway was walked on production on 2026-11-16 through the earlier toggle (stock wrangler 4.162.0 enabled it; `Range`, conditional requests, browser CORS with a real preflight, disable and the kill switch's answer were read there, ADR112 § Not verified), and the S3-era toggle's route and its admin-only refusal are covered by tests (`object_storage_admin_test.go`) and `bex s3 public` by the CLI's tests. Compared with R2's documentation on 2026-11-15 (the public-buckets page and the API schema): both are non-production by statement (bex says the same: the host is rate-limited and cached, and is not a CDN), both refuse a listing at the root, both leave caching rules, WAF and access control to a custom domain that bex does not offer, and both let the setting be turned off without touching anything else. **Divergences from Cloudflare, dated 2026-11-15, each bex's own and none signed off:** the host is a single label under the platform's shared suffix (`pub-<xid>.onbex.co`), not Cloudflare's own `r2.dev`, so public bucket content shares a registrable domain with tenant apps and static sites (the same risk class as [ADR103](../ADR103-security-review-static-rewrite-proxy.md), unmitigated beyond `X-Content-Type-Options: nosniff`; ADR112 D4 records it as user-changeable); publishing needs the workspace admin (`can_manage`) and a person's own login, where Cloudflare's token needs write access to the bucket, and a deployment with no hosting domain refuses to publish (503); turning it off reaches every visitor within 30 seconds (the gateway caches which bucket a host names; 24.5 s measured on production on 2026-11-16), where Cloudflare's propagation time is not published; an object overwritten while public reaches visitors within 60 seconds (the gateway's cache; Cloudflare's r2.dev page documents none, because it says caching is not available there); the rate and bandwidth caps are bex's own, unverified and per gateway replica, because Cloudflare publishes no r2.dev limit (50 requests a second per bucket and 100 per workspace, 2 MiB a second per bucket and 4 per workspace, reset on 2026-11-16 from the production walk to keep a workspace under half of the shared Wasabi account's 67 GB free-egress allowance per hour; at most 32 open responses per bucket, 64 per workspace and 256 per replica, a refusal is 429 with `Retry-After` or 503 for the replica's own); `If-Range` is not honored (the whole object is served); `OPTIONS` that is not a CORS preflight is 405; an answer to a request the gateway cannot serve is a short plain-text body, never the store's XML; and Cloudflare's page says nothing about CORS on `r2.dev` that bex could compare with, so bex applies the bucket's own rules and never allows credentials. The `pub-` prefix is reserved only in the exact shape of a bucket host (`pub-` and a 20-character xid), so a service may still be called `pub-site`, as on Render; such a name gets a suffixed slug, as a taken subdomain does. No custom domains, CDN or signed public URLs (ADR112 D10).

- **Webhook management beyond Render REST** — Render publishes `/v1/webhooks` CRUD and keyset-paged `/events` history plus the global `GET /v1/events/{eventId}` hydration route, so bex’s corresponding REST family is compatibility work, not a product lead. bex remains ahead on GraphQL and MCP management (`list_webhook_endpoints`, `list_webhook_deliveries`, and create/update/delete endpoint tools) and adds `serviceEvent(id:)` / `get_service_event` over the shared global lookup, because Render’s official MCP server has no webhook tools and no single-event retrieval tool (it gained a service-event **list** tool, `list_events`, which bex implements to its contract as of w1/m165); those dialects and the dashboard also expose richer retry diagnostics. bex deliberately treats the signing secret as mint-once instead of returning it on later reads. The dated correction and remaining product/source divergences are in [webhooks-api.md](../render-artifacts/webhooks-api.md) (`w2/m70`, `w8/m24`).
- **Usage metering** — `GET /v1/usage` + GraphQL `usage(period: $period)` + MCP `get_usage` tool return month-to-date or historical-month usage (instance-seconds per tier, egress bytes, build seconds, storage GB-seconds, weighted sandbox compute seconds, a sandbox's used CPU as `sandbox_cpu_seconds` and its allocated memory as `sandbox_memory_gb_seconds` (billed from 2026-11-18T00:00:00Z as Render bills a running sandbox, w22/m314; rows and charge lines recorded before that instant carry `unbilled`, and `estimatedCost.sandboxUsageBilledFrom` gives the instant), and the image a suspended sandbox retains as `sandbox_snapshot_gb_seconds`, w22/m313) for the caller's workspace — including managed Postgres and Key Value instances (`resourceKind: "postgres"` / `"key_value"`) and hosted sandboxes (`resourceKind: "sandbox"`). **Coverage contract (w11/m8):** every adapter returns the same `coverage {state, through, degradedSources}` beside the totals. Current-month `complete` means durable healthy evidence for every applicable hourly source through the latest closed UTC hour; a late start, gap, degraded/unavailable source, or lagging stream is `partial`; historical and pre-contract totals are always `unknown`, never inferred complete. `through` is the common contiguous watermark and `degradedSources` is bounded and presentation-safe. **Outbound completeness (w8/m15):** App `egress_bytes` atomically sums exact HTTP responses, downstream WebSocket frames, and direct public TCP/UDP L3 bytes; public datastore rows contain encrypted backend→client proxy bytes, while private datastore traffic is explicit zero. Same-cluster/private, cluster DNS, denied, control-plane, and backup traffic are excluded. All three adapters read the same durable rows and therefore cannot disagree. All three surfaces accept the same `period: YYYY-MM` argument with identical semantics — including its validation: a malformed period is a named 400 on every surface, never a silent fall-back to the current month and echo it in the response body. **Workspace targeting (w6/m18, w1/m55):** REST and GraphQL accept `ownerId`; MCP accepts per-call `workspaceId` alongside `period`, and the dashboard's Usage page follows the switcher. **Dashboard** (**w8/m6 + w8/m9 + w8/m15**): month picker on the Usage page lets users select any of the last 6 months; a 3-month trend view shows totals over the last three calendar months; storage has its own GB-hours table; bandwidth copy names the complete public-egress basis. **Render comparison (re-verified 2026-07-27):** Render's [pricing page](https://render.com/pricing) lists Postgres and Key Value as plan-priced compute and outbound bandwidth as a usage dimension; its [Postgres flexible-plan documentation](https://render.com/docs/postgresql-refresh) sets Postgres storage at `$0.30/GB-month`, prorated by the second. Render's [dashboard documentation](https://render.com/docs/render-dashboard) exposes payment-method updates, accrued charges, included-usage counters, and invoice history only in the Billing UI, with no public REST/GraphQL/MCP billing endpoint. **Verdict:** parity on the public-outbound category intent, compute, and the Postgres storage rate dimension; deliberate bex extension on raw quantities and API access. **Documented drift:** bex publishes its precise byte basis (including direct L3 headers and encrypted datastore proxy bytes), while Render does not expose an invoice-level byte-boundary contract; Render prices provisioned Postgres capacity and has no separate Key Value storage line, while bex prices actual used PVC bytes for both datastore kinds. See [docs/ADR023-usage-metering.md](../ADR023-usage-metering.md). **Real billing surface (w7/m48, direct Stripe pivot w7/m50, [ADR040](../ADR040-billing-metronome.md)):** beside the advisory `estimatedCost`, the same usage read on all three surfaces carries a `billing` object — Stripe's current Subscription invoice preview + finalized invoices — with identical field names/semantics across REST (`billing` in the `/v1/usage` envelope), GraphQL (`usage.billing { currentCost, invoices }`), MCP (`get_usage`), and the dashboard's distinct "Current Spend" card (an _Invoice_ badge, not the estimate). `billing` is `null`/absent (estimate-only, never a 500) when no bex Stripe Subscription exists, the workspace is structurally excluded, billing is off (`BEX_STRIPE_SECRET_KEY` unset), or the Stripe read degrades. A Mode-B comped Subscription can still expose rated net-zero invoice data. Still a **bex-ahead extension** — Render exposes no billing API, so this is internal cross-surface consistency, not a Render-parity claim. **Credits (w5/m70):** the same `billing` object carries a `credits` block — `{availableUsd, currency, grants[{name, remainingUsd, expiresAt}]}` from Stripe's `credit_balance_summary`/`credit_grants` reads (never derived from the invoice preview, whose total is unreliable for credit under flexible billing mode) — identical on REST/GraphQL/MCP (guarded by `TestBillingCrossSurfaceParity`), absent (not zeroed) at zero balance or on a degraded/permission-denied credit read. Dashboard: a "Credits remaining" card (hidden entirely at zero, mirroring Render's own billing-page presentation of promotional credit), a credit-adjusted "Credits applied −$X → amount due $Y" line under the invoice preview, an earliest-expiry note, and the ADR046 clarification that a payment method is still required. The dashboard page itself was renamed `/usage` → `/billing` in the same milestone (Render's workspace IA; `/usage` redirects, the usage API keeps its ADR023 names).
- **Billing onboarding, dunning, and self-service** — w7/m51–m52 provide one contract — gated on `can_manage_billing` (billing role or admin) since **w1/m60**, so Render's **Billing** role manages billing without full workspace-admin — across REST (`/v1/workspaces/{id}/billing` and hosted-session POSTs), GraphQL (`workspaceBillingReadiness`, `createBilling*Session`), MCP (`get_billing_readiness`, `create_billing_*_session`), and the dashboard. Setup-mode Checkout binds a test payment method to the existing metered contract; Portal is Customer-scoped; Tax reports unconfigured until an operator-confirmed catalog and active same-mode registration pass. Signed failed/action-required/success invoice and Subscription events now converge through the same durable lifecycle as the polling backstop: visible grace, reversible test-mode enforcement, exact-marker recovery, owner notifications, and a 409 billable-mutation gate while enforced/recovering. This is a **bex-ahead extension**, not a Render-parity claim: Render publicly documents billing UI and broad failed-payment suspension rights, but not a grace schedule, ownership/recovery algorithm, or billing-lifecycle API. The **billing-role authorization** now matches Render's role split (w1/m60); bex leaves static sites/data untouched and refuses live enforcement. See the [dated comparison](../render-artifacts/billing-onboarding.md).
- **In-app Audit Log viewer** — dashboard Settings → **Security & Compliance** → Audit Log (`w4/m14`, regrouped `w4/m15`) is a live, paginated, in-app table. Render's dashboard has no in-app audit-log table at all — only a date-range CSV export under Workspace Settings → Compliance (render.com/docs/audit-logs, checked 2026-07-11); bex places its richer table under the analogous Security & Compliance grouping.
- **GitHub repo listing & connection status over the API** — `GET /v1/repos` + MCP `list_repos`/`list_git_connections` return the workspace's connected installations' repositories (private included, each annotated with the owning GitHub account) and the connections' account/install URLs, so "which of my repos can you deploy?" is one agent call. Render lists repos only through its private dashboard API and its MCP has no repo tools (w2/m8, [ADR026-github-integration.md](../ADR026-github-integration.md)). **Workspace targeting (w6/m18, w1/m55):** connect/list-connections/disconnect/repo-list use `ownerId` on REST/GraphQL and per-call `workspaceId` on the MCP `list_repos`/`list_git_connections` tools, so a multi-workspace caller can check or list a **non-default** workspace's GitHub connections explicitly rather than only ever resolving their default one. **Multi-account (w5/m74, [ADR075](../ADR078-github-workspace-connections.md)):** a workspace holds several connections; `GET /v1/git/connections` / `gitConnections` / `list_git_connections` list them all, and `DELETE /v1/git/connections/{installationId}` disconnects one. The singular `get_git_connection` / `GET /v1/git/connection` remain as deprecated single-connection aliases. **Claim flow (w5/m75, [ADR078 §3a](../ADR078-github-workspace-connections.md)):** `POST /v1/git/claim` / `claimGit` return `{claimUrl}` — the OAuth-authorize round trip that binds an installation **already present** on GitHub (where GitHub strips the install URL's signed state); this is the workspace-bound model's answer to Render's "direct github.com install just works" (Render's user-bound OAuth model _reads_ installations, so it never needs a binding ceremony). Deliberately absent from MCP: the claim is a browser OAuth ceremony an agent cannot complete, matching connect's existing MCP absence. **N:N + claim selection (ADR078 §2/§3a, 2026-09-16):** claiming an installation another workspace already holds now succeeds on its own proof instead of reporting `no_claimable_installation`, and an admin who administers several installations gets a dashboard account picker (`GET /v1/git/claim/selections/{id}` + `selectGitClaim`) rather than an unresolvable `ambiguous_installation`. Both selection surfaces are MCP-absent for the same browser-ceremony reason.
- **A user-consented OAuth 2.1 provider for third-party agents** — an MCP client self-registers (DCR), sends its user through bex's own login, and the user grants it on a real **consent screen**; the agent then holds its own revocable, scoped token (w4/m9 + w4/m16, [ADR012-auth.md §7](../ADR012-auth.md#7-oauth-21-provider-for-agents-one-dashboard-login-first-party-sessions--third-party-clients-w4m9)). Render has **no OAuth2 provider or consent surface at all** — agents and CI use dashboard-minted API keys, so there is no Render shape to mirror here (re-checked against api-docs.render.com + render.com/docs 2026-07-12: the only credential is an account-scoped API key). No operator blessing is required: `skip_consent`/`OAUTH_TRUSTED_CLIENTS` only _skips_ the screen for first-party clients. **Cross-surface consistency:** bex-api never distinguishes a consented client from a blessed one — it introspects the bearer and checks the audience, with no trusted-client branch anywhere in `lego/backend`, so both tokens authorize identically at `/mcp`, REST, and GraphQL (evidence: [scripts/auth-oauth21-e2e.sh](../../scripts/auth-oauth21-e2e.sh) legs 8 and 10 assert the same 200 for each). **Granular capabilities (w8/m27):** a third-party human token for the API audience must carry `bex.read` / `bex.write` / `bex.sensitive` (independent, advertised in RFC 9728 `scopes_supported`); missing or near-match scopes fail closed with one coded `insufficient_token_scope` (Render's errorCode; `INSUFFICIENT_SCOPE` until w2/068, 2026-11-03) across REST, GraphQL, and MCP. Dashboard Kratos sessions and machine API keys stay scope-exempt. - **A queued deploy says why it waits** (`w2/m99`, [ADR034](../ADR034-scalable-build-pipeline.md) · [ADR060 D6](../ADR060-build-worker-reliability-and-performance.md)) — while a deploy row is `queued`, the build-log narration states the operator's CURRENT reason (`==> Waiting for a build slot: this workspace has 2/2 builds running`, `==> Waiting for platform build capacity`, `==> Preparing registry credentials`), re-emitted when the reason changes and never repeated per poll, so a capacity wait is distinguishable from a stuck deploy. **Render comparison (checked 2026-09-15):** [render.com/docs/build-pipeline](https://render.com/docs/build-pipeline) documents only "Each Render service can have only one active build at a time" (a cancellation rule, not a queue) and prices the pipeline in minutes per workspace plan; neither it nor [render.com/docs/deploys](https://render.com/docs/deploys) publishes a per-plan build-concurrency cap or any copy for a build waiting on a slot — the only documented queueing is Render **Workflows**' separate per-workflow compute limits. bex is therefore ahead, and the extension is **countless and tenant-neutral by construction**: the workspace cap renders only that workspace's own `<active>/<limit>`, while the cluster-wide cap and the Kubernetes scheduler wait collapse to one fixed neutral line, so no tenant learns another tenant's build activity or the platform's capacity. `failureReason` stays terminal-only — the wait is read from the App's `Ready` condition, never from the field that means "this deploy failed". Produced once in the logs core verb, so REST `GET /v1/logs`, GraphQL `logs`, MCP `list_logs` and the SSE tail carry the identical line.

- **Public price sheet** (2026-11-14, [ADR030](../ADR030-pricing.md) §1) — `GET /pricing` returns bex's customer-facing prices as JSON without a credential, so bex.co checks its pricing page against what bex charges. Render publishes prices only as a web page, with no machine-readable sheet.

The MCP `query_render_postgres` tool itself remains parity, not a superset — it is read-only on both platforms. The dashboard console and its explicitly confirmed write mode are a deliberate bex extension; no write flag was added to the agent tool.
