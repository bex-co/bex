# Environment & config

This is the Environment & config part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), moved out of it on 2026-11-23 (w10/m607) to keep the ledger under the 1 MiB blob limit. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

**Environment-group storage cutover (w8/m114, 2026-10-18).** Non-secret group metadata, names, memberships, links and save coordination move to Postgres; OpenBao retains values and temporary recovery maps ([ADR013](../ADR013-secrets.md)). REST keeps Render's group fields and cursor envelopes; GraphQL and MCP retain their existing projections, and the dashboard consumes the same verbs. [Render's environment-group contract](https://render.com/docs/configure-environment-variables) still applies: reusable variables and secret files linked to services. Deliberate Bex compatibility breaks: the control-plane store is required; abandoned-name reservation errors (`ENV_GROUP_NAME_RESERVED`) disappear while duplicate names still return `ENV_GROUP_NAME_EXISTS`; the old path-migration/name-claim startup modes are removed; group verbs are unavailable during the authorized cutover. These are storage/deployment changes, with no new Render field or API capability claim. Metadata reads make zero OpenBao calls even while a save is busy or requires repair; the existing availability field reports that state and withholds an unusable revision.

| Secret files (mounted at `/etc/secrets`) | ✅ | ✅ | ✅ | ✅ | **A null replace-all clears (w9/109, 2026-11-18):** `PUT /v1/services/{id}/secret-files` with the JSON body `null` answers 200 `[]` and leaves no files, as on Render, for the same Terraform provider request as the env-vars row. **Files over 500 KiB in builds (w4/699, 2026-11-16):** BuildKit refuses any build secret over 500 KiB, and buildctl checks every one when it starts, so a single secret file between 500 KiB and the 1 MiB limit failed every repo build (`secret bex-file-0 too big`). A native build now carries such a file in parts of at most 500 KiB and reassembles it at `/etc/secrets/<name>` on a tmpfs mount for the build command only, so the build reads the exact bytes and the image holds none of them. A Dockerfile build cannot do this, because the tenant's Dockerfile names the secret id. It leaves a file over 500 KiB out of its build secrets, so builds that never mount the file still succeed. The file stays in the build-context root, and the build log names the file and says it cannot be mounted. Render also builds Docker images with BuildKit, which has the same 500 KiB limit. Its behavior with a file this large has not been observed. **In the service root too, for native runtimes (w8/m154, 2026-11-11):** Render: "For non-Docker services, the file is _also_ available in your service's root directory." A Node, Python, Ruby, Go, Rust or Elixir service (web, private, worker, cron, and its pre-deploy command) now reads each secret file at `<service root>/<name>` as well as `/etc/secrets/<name>`, from its next deploy; with `rootDir` the service root is that directory. The root copy is a read-only link, a repository file of the same name gives way to it, and a repository directory of that name is left alone.
