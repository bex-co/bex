| Trigger a deploy | ✅ | ✅ | ✅ | ✅ | Render `POST /services/{id}/deploys` → `internal/deploys/rest.go` `POST /v1/services/{id}/deploys` (201, opens a `dep-…` row + bumps `spec.restartedAt`, w2/m5; 202 for a deploy that waits, w8/378). GraphQL `triggerDeploy(serviceId)` (w2/006) delegates to the same `Trigger` verb. MCP `trigger_deploy` tool added w2/m44. See [ADR017-deploy-from-chat.md](../ADR017-deploy-from-chat.md). UI (Manual Deploy button), `w5/m21`. **w2/m30 deploy body (clearCache semantics corrected w3/m46):** the POST body (and `triggerDeploy` GraphQL args, and — since w3/m46 — the `trigger_deploy` MCP tool) decode three optional fields — `commitId` (string), `clearCache` (Render's `clear`\|`do_not_clear` string enum — **not** a bool; the official CLI always sends it explicitly), `deployMode` (string). **w9/m492:** production runs the build cache in every workspace (`BEX_BUILD_CACHE=s3`), so `clear` is no longer a no-op there: that release purges the App's layer-cache prefix, builds without importing it, and saves a fresh cache, and a Build Source carrier's `POST /v1/build-sources/{id}/builds` with `clearCache` takes the same path ([ADR060 D3 S3 amendment](../ADR060-build-worker-reliability-and-performance.md#d3-amendment-w9m492--the-s3-backend-off-zot); production proof w9/m492 t005). **w7/m88:** with `BEX_BUILD_CACHE=registry`, `clear` stamps `app.bex.co/clear-cache-release-generation` so that release's BuildKit Job skips registry cache restore/import (best-effort purge of `:cache`), still exports a fresh cache, and a later ordinary deploy can reuse it; `do_not_clear`/omission leave import intact. With the gate off both values remain behavioral no-ops for BuildKit builds (ephemeral Jobs start empty). Image-backed triggers accept the enum without inventing a cache effect. A buildpack (kpack) release under `clear` moves its App to a fresh buildpack cache that later releases keep, whatever the gate, so it no longer restores what the user cleared (w5/m134). Validated in shared `validateTrigger` so all three surfaces reject only a value outside the enum (**400**) and accept `clear`/`do_not_clear`/omitted alike. This replaces the earlier bool-typed `clearCache: true → 400` design, which 400'd every deploys-create the CLI sends. `commitId` sets `App.spec.BuildCommit`; the operator uses it as the git ref for this one build (instead of Branch HEAD). A trigger without `commitId` resolves and pins the branch head, so a subsequent plain deploy reverts to the branch — rejected for `cron_job` services (Render: "Not supported for cron jobs"). **Auto-deploy (w1/m148, one write since w4/m431):** Render: "Deploying a specific commit through the Dashboard or a deploy hook disables auto-deploys. The CLI and API don't" ([render.com/docs/deploys](https://render.com/docs/deploys), read 2026-11-16). REST `POST /v1/services/{id}/deploys {commitId}` and MCP `trigger_deploy` keep auto-deploy on. The dashboard's **Manual Deploy → Deploy a specific commit** (repo-backed, non-cron) sends one `triggerDeploy(commitId, disableAutoDeploy: true)`, and a deploy hook called with `ref` does the same: the release write that pins the commit sets `spec.autoDeploy = false` (a deploy waiting under Wait applies it when it opens), so no push can land between the pin and the switch-off, and the events feed records `auto_deploy_disabled {reason: manual_deploy, fromTrigger}` when auto-deploy was on. `disableAutoDeploy` without `commitId` is a 400. `deployMode: "deploy_only"` is **accepted for image-backed services** (re-pull the existing image; no build step) but **rejected with 400 for repo-backed services** because the public trigger deliberately creates a new source-build release and does not expose cached-artifact deployment. **deploy_only mixes (w8/377, 2026-11-21):** Render's create-deploy contract says "`deploy_only` cannot be combined with `commitId`, `imageUrl`, or `clearCache`, as those are build related fields" (pinned `render-public-api-1.json`; [create-deploy](https://api-docs.render.com/reference/create-deploy), read 2026-11-21), so REST, GraphQL `triggerDeploy` and MCP `trigger_deploy` refuse `deploy_only` with `commitId`, `imageUrl` or `clearCache: clear` (MCP `true`) with **400** on any service and open no deploy. `clearCache: do_not_clear` is the field's default and is not a mix. The deploy hook takes no `deployMode`. `deployMode: "build_and_deploy"` (the default) is always accepted. **Queued answer (w8/378, 2026-11-21):** Render answers a trigger that waits behind the deploy in progress `202` "Queued" with no body (pinned `render-public-api-1.json`), and the pinned CLI then finds that deploy with `GET …/deploys?status=queued&limit=1` (`views.WaitForDeployCreate`). REST answers the same way, as the deploy hook does (w4/635), and a trigger that starts at once keeps `201` with the deploy. MCP `trigger_deploy` answers Render's MCP sentence for that case, "The deploy request was accepted, but the deploy has not been created yet. Use list\*deploys to check on the service's deploys." (render-mcp-server `pkg/deploy/tools.go`), and its structuredContent still carries the queued row. GraphQL `triggerDeploy` has no status code and returns the queued deploy. Rollback keeps `201` with its queued deploy, since Render's rollback contract documents no `202`. **w2/m44 imageUrl:** `imageUrl` in the POST body (REST/GraphQL/MCP) lets an image-backed service deploy a specific tag for that deploy only (`spec.releaseConfig`; the saved `spec.image` stays as it was since w8/022); rejected with named 400 for repo-backed services (origin-safety rule; since w8/042 an image-backed override must also keep the saved host/repository/name, per Render's create-deploy contract). **Settings releases keep the deployed image (w6/159, 2026-11-23):** Render applies a deploy's own image to that deploy only: "for future deploys, your service continues to use the tag or digest in its settings" ([render.com/docs/deploying-an-image](https://render.com/docs/deploying-an-image), read 2026-11-23). So `GET /v1/services/{id}` reports the configured tag as `imagePath`, as bex always did, with the running override in the `servingImage` extension (w4/414). A plan change on an image service after an `imageUrl`/`imgURL` deploy, or after a Restart of one, shipped the tag the service was created with, and so did a dashboard Settings save that deploys. Each such settings release now runs the image the release in force selected: the live deploy's digest, or the override still rolling. An environment "Save and deploy" (w4/m418) and a Restart already did this. A release in force that runs the saved image selects nothing, so a saved image held for the next deploy (w8/m135) still ships with the plan change. Render's [compute plans](https://render.com/docs/compute-plans) page does not say which image its plan-change deploy runs, so bex reruns what is live, as for every other configuration-only release. **Dashboard landing (w5/m45):** manual deploy and restart open `/services/{srv-id}/deploys/{returned-dep-id}`; rejection never navigates. **Concurrent triggers (w8/m46):** API, deploy-hook, restart and rollback triggers on one service run one at a time (`deploys.openRelease`: a per-app Postgres advisory lock across bex-api replicas, a fresh App read, an optimistic-lock CR patch, then the deploy row inside the same section). Each row records its own request's image, release generations are strictly ordered, and the CR names the newest, so the newest accepted trigger wins and earlier open rows close `canceled` (superseded). Under Render's default Overlapping Deploy Policy, Wait, an accepted trigger whose deploy cannot start yet waits in one latest-pending `queued` row instead, and the deploy in progress runs to its end whether or not the operator has adopted it yet, whichever writer the newer deploy comes from (w8/387, w8/390; see List / get deploy objects); the row-level ordering here is unchanged, and Render's millisecond tie-break is not published. A trigger whose service was deleted and recreated under its name while it waited for the lock, or between its patch attempts, refuses with 409 `CONFLICT` (the service changed) instead of releasing the namesake (w5/157). **Every deploy runs a native build command (w32/046, 2026-11-19):** Render runs the build command "with each deploy" ([render.com/docs/deploys](https://render.com/docs/deploys)), which is what a deploy hook rebuilding a site for new CMS content relies on. From w9/m492's layer cache until this fix, a native release at an unchanged commit and environment (Manual Deploy → Deploy latest commit with no new push, a deploy hook, REST, GraphQL `triggerDeploy`, MCP `trigger_deploy`, `POST /v1/build-sources/{id}/builds`) was served the step from the cache and went live on the previous build's output. The generated recipe now carries each release's build revision, so every release runs the command and only a retry of one release reuses it ([ADR060 § D3 amendment (w32/046)](../ADR060-build-worker-reliability-and-performance.md#d3-amendment-w32046--every-release-runs-a-native-build-command)). Dockerfile builds keep BuildKit's layer cache. |

A lookup that cannot be made (GitHub unreachable, rate-limited, a private repository with no installation, another host) still opens the deploy. **Hook-vocabulary refusals (w8/141, 2026-10-20):** a refused `ref`/`imgURL` 400 names the hook parameter the caller sent, not the REST body's `commitId`/`imageUrl`; the rule text and status are the shared trigger validation's, and REST/GraphQL/MCP messages are unchanged. a 256-bit token persisted in the App annotation; authenticated REST `GET .../deploy-hook` + `POST .../deploy-hook/regenerate`, GraphQL `deployHook`/`regenerateDeployHook`, MCP `get_deploy_hook`/`regenerate_deploy_hook`, and dashboard Settings reveal/copy/regenerate all return the same `{url}` state. Open `GET`/`POST /v1/deploy-hooks?key={token}` calls the same deploy trigger internals and returns Render's `200 {deploy:{id}}`; per-token limit and its service's share of Render's deploy row, ten a minute each (w8/410; 6/min, burst 2 before), then 429 + `Retry-After`. [Render docs](https://render.com/docs/deploy-hooks) verify secret URL, both methods, rotation, `ref`, response, and Settings placement. **Key statuses (w4/689, 2026-11-16):** Render: `key` is "Required. If it's missing, the response is 401. If it's invalid, the response is 404" ([Render docs](https://render.com/docs/deploy-hooks), read 2026-11-16). bex answers a missing or empty `key` with `401 unauthorized` in the standard error envelope before the per-token limiter and the lookup, and a malformed, unknown or rotated key with `404`. **Deliberate drift:** Render uses `/deploy/{serviceId}?key=…` and dashboard-only management; bex uses `/v1/deploy-hooks?key=…` (the key alone names the service) and adds authenticated API/agent management. **w2/m44:** `?imgURL=` is now forwarded through `TriggerParams.ImageURL` (rejected for repo-backed; for image-backed, accepted only for the saved image's host/repository/name — same rule as the REST body `imageUrl`, w8/042); **Wait overlap answer (w4/635, 2026-11-14):** a call that lands in the latest-pending slot behind a deploy in progress answers Render's `202 Accepted` with no body and no deploy id ("A different deploy is already in progress for this service. Render will start a new deploy after the current one completes", [Render docs](https://render.com/docs/deploy-hooks)); a call that starts a deploy at once keeps `200 {deploy:{id}}`, and later calls coalesce into the one pending deploy. **`ref` turns auto-deploy off (w4/m431, 2026-11-16):** as on Render, a hook call with `ref` pins that commit and turns auto-deploy off in the same write (on the 202 path too), recording `auto_deploy_disabled` with `reason: manual_deploy`; a call without `ref` leaves auto-deploy alone. **Blueprint `initialDeployHook` (w2/m45):** a one-time command that runs exactly once on the service's first successful deploy — parsed from `render.yaml`, stored in `bex.co/initial-deploy-hook` annotation, overrides `App.spec.preDeployCommand` on create; after the operator sets `PreDeploySucceeded`, the API records `bex.co/initial-deploy-hook-ran=true` and stops injecting it; echoed on blueprint reads via `initialDeployHook` field on REST/MCP. |
| List / get deploy objects | ✅ | ✅ | ✅ | ✅ | Render `list_deploys`/`get_deploy`, `GET …/deploys`, and `GET …/deploys/{id}` → `internal/deploys/{rest,graphql,mcp}.go`. **A built deploy leaves `build_in_progress` at its image push (w33/m569, 2026-11-22):** the row moves to `update_in_progress` once the operator dispatches the release, which it now does when the image is pushed rather than when the build Job's `cache-save` ends, and its `build_ended` event carries the push's end (see Build logs). **Lifecycle + timestamps (w2/m38, 2026-07-15; overlap fidelity w2/018, 2026-08-16):** rows persist the observed subset of Render's full eleven-state vocabulary (`created`, `queued`, build/pre-deploy/update progress and failure, `live`, `deactivated`, `canceled`). `updatedAt` advances only on a real status or pre-deploy fact change; `startedAt` marks first execution; `finishedAt` marks the first terminal result. Current-generation App/Job evidence prevents stale projection, an explicit transition table rejects regressions, and a new live deploy atomically deactivates the prior live row while preserving its original `finishedAt`. Overlapping triggers now match Render's documented Wait policy: an executing row remains open through `live`, one latest-pending row is `queued`, and another push cancels only the replaced queued row. **Every runtime (w4/635, 2026-11-14):** until then this held only for repo-backed builds: a prebuilt image's deploy already rolling out was abandoned by the next trigger and its row closed `canceled`, though it never served. Render's Wait is "Allow the in-progress deploy to finish, then proceed directly to the most recently triggered deploy", the default for workspaces created on or after 2025-07-14 ([Render docs](https://render.com/docs/deploys)). The operator now pins a saved-image release once it has adopted it, as it pins a source build, so it serves before the newer release starts. A deploy it has not adopted yet is held by bex-api's deploy verbs instead (w8/387, below). A Restart waits at the row level (w5/m284). Render's workspace Override setting is offered since w4/653 (see Workspace Overlapping Deploy Policy); everything here describes Wait, the default. **Rollback and image overrides (w4/652, 2026-11-14):** Render documents a rollback as "a _new_ deploy using the target deploy's build artifact" ([render.com/docs/rollbacks](https://render.com/docs/rollbacks)) and "Only one deploy can run at a time per service", so those wait too. A release that selects its own runtime (Rollback, Restart, an `imageUrl`/`imgURL` override) would override the release in flight if written at once, so bex-api holds it at the row level, as w5/m284 does a Restart: behind a deploy in flight it answers a `queued` deploy (the hook's bare `202`) that holds the latest-pending slot with no release and no App change, and the deferred-deploy worker runs it, as that same row, once nothing is in flight. A newer trigger replaces it there (`Superseded by dep-…`), a cancel closes it, and one that waits past 3h closes `the deploy this one waited for did not finish within 3h0m0s`. While such a selected release is in flight, a Manual Deploy, API or hook deploy, or a "Save, rebuild, and deploy" waits behind it the same way. **Behind a selected release (w4/661, 2026-11-14):** the operator pins a selected release once it has adopted it, rendering its own image and settings from its adopted view, so a git push, a configuration change that rolls a release, a Blueprint sync and a build-source fan-out, which write the App directly, wait behind a Rollback, Restart or image override in progress and run once it goes live; behind one the operator has not adopted yet they wait as bex-api's own deploy verbs do (w8/387, w8/390, below). **Behind a deploy not adopted yet (w8/387, 2026-11-21):** on Render a triggered deploy is the one in progress from the moment it is created, so the deploy a `201` names always runs. The operator pins a release only once it adopted it, and a newer deploy written to the App before then replaced it: on production two back-to-back triggers left the first, answered `201`, `canceled` ("Superseded by …") about 2 s later, never run (w8/378's live check). bex-api's deploy verbs (REST, GraphQL and MCP trigger, the deploy hook, a build-source carrier's build and "Save, rebuild, and deploy") now hold a deploy behind one whose release generation is ahead of the App's `status.releaseGeneration` at the row level, as w4/652 holds a Rollback: it answers `202` (the hook's bare `202`) with a `queued` deploy that changes no App, and runs once the deploy ahead has ended, so only queued deploys replace each other. Behind a deploy the operator adopted, a plain deploy still writes through and waits behind its pin. Restart, Rollback and image overrides already waited behind any deploy in flight, adopted or not. A waiting "Save, rebuild, and deploy" runs as a rebuild of the latest commit; before, one that waited behind a selected release ran as an environment "Save and deploy" on the build serving. Override keeps its cancel-and-start. **Every writer (w8/390, 2026-11-21):** the writers that change the App directly follow the same rule. A git push and a build-source fan-out behind a deploy the operator has not adopted wait at the row level too: a `queued` `new_commit` deploy that carries the pushed commit or the build, runs once the deploy ahead has ended, and is the only deploy a newer push replaces. A fan-out that completes a linked service's first deploy, which waits for that very build, ships at once. A checksPass commit whose checks passed stays pending, and the recovery poll (every 15 s) dispatches it once the deploy ahead is adopted. A configuration change that rolls a release and a Blueprint sync change saved settings, which the operator would render the deploy ahead from if they landed before adopting it, so they wait for that adoption and then pend behind it. A save held for the next deploy (an Update Service row on REST or MCP, Update Source) waits for that adoption too, under either policy: written first, it held the deploy ahead, which stayed `created` until another deploy canceled it (w6/163, [ADR004](../ADR004-app-deployment.md#settings-saves-wait-for-a-deploy-w8m135-2026-10-29)). That wait lasts at most 15 s, after which the write goes through as before, and it is skipped for a service's first release, which reads the settings saved before it starts. Under Wait two releases never roll at once on one service. A git push is checked by unit tests only, because a live check needs a repository bex controls. **A no-build static site's publish (w8/392, 2026-11-22)** counts as in flight once the operator has adopted it, as a build does: a newer deploy waits in the pending slot until it serves or fails, and its publish Job clones the commit and publishes the directory it was adopted with. Before, the newer deploy replaced it, and it closed `Superseded by dep-…` without serving. **The deploy waiting behind one that serves (w8/396, 2026-11-22)** is the deploy in progress as soon as the deploy ahead ends, as on Render ("proceed directly to the most recently triggered deploy"). bex-api treats it so from the moment its status pass records the deploy ahead, whatever the operator has reported by then. A deploy opened afterwards by any writer (a trigger, a Restart, a git push, a configuration save, a Blueprint sync) answers 202 `queued` and waits behind it, and the waiting deploy is never replaced. Until the operator adopts the waiting deploy, which it does on its next pass, no writer writes its release to the App, where it would replace the waiting deploy: a deploy request waits at the row level, and a saved change waits for the adoption, as behind any deploy the operator has not adopted (w8/387, w8/390). The first fix read the operator's adoption from the App the writer had just written. On production (pin `eaaa61506165`) a trigger 0.59 s after the deploy ahead read `live` wrote the App before the operator's adoption reached it, although the operator had already started the waiting deploy from an earlier read. The trigger answered 201 and closed the waiting deploy `canceled` (`newDeploy`) while its publish ran, then read `Build queued` for that whole publish. **Before the deploy ahead is recorded (w8/397, 2026-11-22):** a deploy can also land once the operator is done with the deploy ahead, but before bex-api's status pass has recorded it as `live`. The waiting deploy cannot leave the waiting slot while the deploy ahead still reads in progress. So when the App reports the deploy ahead served, or a later release adopted, the writer kicks the status pass and waits for it to record the deploy ahead, at most 5 s. It never records that verdict itself. Then it opens its deploy as above. The wait sits where every writer opens its deploy row. An environment "Save and deploy" behind a deploy in flight follows the same rule. A deploy waiting behind a release still in flight is still replaced, and Override keeps its cancel-and-start and does not wait. Canceling a deploy queued behind a selected release the operator adopted ends that deploy alone: bex-api names the release as the one the cancel leaves running, leaves the saved commit alone, and the operator carries it on its view to `live` (w4/666, 2026-11-14). An environment "Save and deploy" on a Git-backed service behind a deploy in flight saves the environment at once and waits at the row level (a queued configuration deploy); once nothing is in flight it runs the saved environment on the build that deploy left serving, not the one serving at save time (w4/667, 2026-11-14). **Through rollout (w8/m119, 2026-10-19):** until then the operator held the newer release only while the executing one built. It adopted the newer release as soon as the build resolved, so the executing release rolled out and served while its row read `canceled` and the previous deploy stayed `live`. The operator now holds the newer release until the executing one serves (recorded in `status.activeRevision`) or settles failed, asleep or canceled. The reconciler closes a row whose release served `live` even when it first looks after that adoption, and keeps a failed rollout or pre-deploy verdict. A `canceled` row's release never served. An App-row lock plus separate active/queued partial unique indexes enforce that invariant; the reconciler retains both rows and projects status/pre-deploy/image evidence only onto the matching release generation. The eleven-value wire vocabulary is unchanged, so REST/GraphQL/MCP filters and the dashboard's queued/live/deactivated/canceled rendering remain aligned. **Filter parity:** REST, GraphQL, and MCP share `FilterOf` for status plus exclusive `createdBefore/After`, `updatedBefore/After`, and `finishedBefore/After`, cursor, and limit. `TestEveryDeployStatusFilterMatchesEverySurface` and `TestDeployLifecycleTimestampFilterSurfaceParity` prove equivalent results; malformed bounds error rather than disappearing. Render's official MCP currently exposes only limit/cursor, so bex's MCP time/status filters are a deliberate three-adapter superset. **UI:** `/services/$serviceId/deploys/$deployId` shows status/trigger/image/pre-deploy outcome/all timestamps and exact-deploy logs; the timeline uses stored `updatedAt`, preserves the earlier live instant for deactivation, polls every open status, and stops on every terminal status. The standalone Deploys tab filters all eleven statuses. **Build-failure attribution (w7/m82, 2026-08-17):** a failed build's `failureReason` now says whether the build failed on the tenant's input or on the platform's infrastructure, instead of the single flat `BuildFailed` that covered both. The App condition reason splits into `BuildFailedUserError` / `BuildFailedInfrastructure` (with `BuildFailed` retained for builds whose class cannot be determined, e.g. kpack), and the shared `IsBuildFailureReason` contract in `lego/types` keeps bex-api's classification aligned — the sweep found that matching the flat literal alone had silently recorded classified build failures as generic `update_failed` deploys. **The eleven-value deploy status vocabulary is deliberately unchanged**: all classes still report `build_failed`, so REST/GraphQL/MCP filters, the dashboard's status rendering, and the notification pathsneed no migration. `failureReason` is a pass-through string on REST (`renderDeploy.failureReason`), GraphQL (`failureReason`), MCP (shares REST's `renderDeploy`), the dashboard (`deploy-header.tsx`), and the failure email — all five verified carrying the classified message end to end, not merely exposing the field. Render reports build failures as a single opaque status with log-derived detail, so the attribution split is a **bex superset** that supersets cleanly (clients reading only `status` are unaffected). **A rollout that misses its health-check window is cancelled and never retried: Render and bex agree (w21/m421, read 2026-11-16).** Render's [health checks](https://render.com/docs/health-checks): "If this condition is not met within 15 minutes, Render cancels the deploy" and keeps routing to the existing instances; its [deploys](https://render.com/docs/deploys) page says "If any command fails or times out, the entire deploy fails" and the service "continues running its most recent successful deploy". Neither page describes an automatic retry of the cancelled deploy; a new deploy is the recovery. bex's operator budget for the first rollout is the same 900 s (`rolloutBudgetSeconds`, the startup probe and the Deployment's `progressDeadlineSeconds`), and the control plane closes a row still open at 18 minutes (`defaultDeployGateTimeout`, 15 plus a 3 minute margin so the operator's own verdict arrives first) as `update_failed` and does not retry it. A Blueprint service whose first rollout waited on a database schema (Gitea, w21/012) read `update_in_progress` for about 17 minutes, then `update_failed`, and stayed failed after the schema existed: that is Render's behavior, not a defect. This covers the rollout window only: Render also stops routing to a running instance after 15 s of failing health checks and restarts it after 60 s, which this paragraph does not check against bex. No divergence is recorded for the missed rollout window.
