# Render operation omissions

This is the Render operation omissions part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), moved out of it on 2026-11-23 (w10/m607) to keep the ledger under the 1 MiB blob limit. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

The route coverage guard (`TestEveryRenderOperationMountedOrDocumented`) walks every operation in the pinned OpenAPI. The following **—** entries are absent Render operations, including native alternatives whose different contracts must not masquerade as aliases. They do not imply that the corresponding bex-native capability is absent. Each operation ID is enumerated in `renderOperationOmissions`; mounting one requires removing its omission entry.

| Render sandbox execution history (`/sandboxes/{id}/execs`) | ✅ | **Long execs and orphaned records (w8/m151, 2026-11-10):** an exec stream lifts w2/m278's long-resume write deadline once the gateway accepts, so a command runs as long as it needs (bounded by the gateway session and the sandbox), where every exec used to die 210 s in. An open record is refreshed every 30 s while its stream runs, and a history read closes a record left unrefreshed past `LongResumeWait` + 2 min (a bex-api restart mid-exec, a minted token never redeemed) at its last heartbeat, with no exit code. **A command that outlived its stream (w32/m381):** in a running sandbox the read first asks the sandbox's command registry, so the record stays open while the command runs and then closes at its own exit with its exit code, not at the disconnect. **w32/m298 (2026-11-09), reopened from the row above by the user's choice of the w32 brainstorm item.** `GET /v1/sandboxes/{id}/execs` (newest first, `cursor`/`limit`, items `{execution, cursor}`) and `GET …/execs/{execId}` serve Render's record: `id`, `sandboxId`, `type` (`runs`/`files`), `operation`, `command` (the command cut to 1024 bytes, or a transfer's path), `userId` (the caller's `usr-` id), `startedAt` (the token mint), and `stoppedAt`/`exitCode` once it ends. A run's exit code comes from its stream; a transfer reports none, which Render's schema allows. Termination stops what is still open. A record is visible to whoever may read its sandbox (another member's answers 404) and is pruned with the sandbox; Render documents no retention. GraphQL `sandboxExecutions`/`sandboxExecution` and MCP `list_sandbox_executions` serve the same records. A store outage loses history but never refuses a command. |

### Sandbox create flags (w2/m263)

How bex answers each sandbox input the pinned Render CLI v2.35 sends, checked against `create-sandbox` and `list-sandboxes` in the pinned OpenAPI. REST, GraphQL `createSandbox`/`sandboxes` and MCP `spawn_sandbox`/`list_sandboxes` share one service path, so they answer alike.

| Input | Status | bex behavior |
| --- | --- | --- |
| `plan` (`--plan`) | ✅ | `1c-2g`, `2c-4g`, `4c-8g` and `8c-16g` size the sandbox container exactly as named. The deprecated `starter`/`standard`/`pro` stay aliases at 0.5 CPU/512 MiB, 1 CPU/2 GiB and 2 CPU/4 GiB. An unknown plan answers `400 invalid_sandbox_plan` listing the accepted names, Render's own code (it read bex's `SANDBOX_PLAN_INVALID` until w8/312). Billing followed the resources through the weighted `sandbox_compute_seconds` meter until 2026-11-18T00:00:00Z; from then a running sandbox bills the CPU it uses and the memory its plan allocates, as on Render (w22/m314, ADR030 §17). Before w2/m263 every plan ran at the template's 0.5 CPU/512 MiB. **Default plan (w8/247, 2026-11-11):** a create that names no plan is Render's default `1c-2g`, in name, size (1 CPU, 2 GiB) and meter weight, on REST, GraphQL and MCP; until then it was the deprecated `starter` at 0.5 CPU/512 MiB, a name the CLI's help no longer lists. Sandboxes created earlier keep their plan, `--plan starter` is still accepted at its own size, and an agent session's sandbox keeps its own size and its `starter` label. **Writable filesystem (w22/008, 2026-11-16):** every plan has Render's 40 GB writable filesystem, now enforced (a 40Gi `ephemeral-storage` limit; the kubelet ends a sandbox that writes past it, verified on production). Render's [Limits page](https://render.com/docs/sandboxes-limits) documents only the figure, not what a write past it does, so the ending (no `ENOSPC`, `df` showing the node's disk) is recorded in [ADR104 D7](../ADR104-sandbox-render-parity.md) as not established against Render. |
| `status` list filter (`--status`, `--all`) | ✅ | Applied, repeated or comma-separated. With no filter, every status except `terminated` is listed. An unknown status answers 400. Since w2/m278 every Render status occurs: `suspending` while an idle sandbox's pause commits, `suspended` once it has, and `resuming` while an exec or file transfer wakes it. |
| `idleTimeoutSeconds` (`--idle-timeout`) | ✅ | Matches Render (user decision w2/m263 D2=A, 2026-11-07; shipped w2/m278). Omitted means 900 s, `0` disables idle suspension, and 300–86400 is honored; anything else answers `400 SANDBOX_IDLE_TIMEOUT_INVALID`. REST, GraphQL and MCP report the value. A sandbox is idle when no exec or file transfer through bex-api is in progress, which is Render's definition ("no command execution or file transfer is in progress"); a command in progress keeps it active, and the window runs from the command's end. **That holds after the command's client leaves too (w32/m381, verified on production 2026-11-14: a CLI killed with SIGTERM or SIGINT 5 s into `sleep 480` left the sandbox `running` until the command ended and `suspended` about 320 s later, and the record read the command's own `stoppedAt` and `exitCode: 0`):** the exec wrapper records each command in the sandbox, and the sweeper asks before it pauses a sandbox with a command whose stream ended without its exit. Background processes do not keep it active, as on Render. A sandbox idle past its timeout is suspended within 30 s and goes `suspending` → `suspended`; `sandbox_compute_seconds` stops at the moment of suspension, as Render stops CPU and memory charges. The next `exec` (run token or legacy `/exec`, MCP `sandbox_exec`) or `copy` resumes it (`resuming` → `running`) and then runs; reading status does not resume it. The REST exec and file routes wait up to 3 min for the resume. MCP `sandbox_exec` waits 20 s, inside bex-api's 30 s write timeout. A slower resume answers `503 SANDBOX_RESUMING` asking for a retry while the resume continues. Sandboxes created before w2/m278 keep reporting `0` and never idle-suspend. Mechanism and what survives: [ADR014 D4](../ADR014-sandboxes.md#d4--idle-hibernate--gateway-observed-autopause), [ADR042 D5](../ADR042-sandbox-cluster-substrate.md#d5--snapshot-semantics-v1-is-rootfs-only-memory-hibernation-is-a-watch-item). **Memory and processes — temporary difference (user decision D1=A, 2026-11-11).** Render resumes an idle sandbox "with its files, memory, and running processes intact" (runtime snapshot, [render.com/sandboxes](https://render.com/sandboxes)). bex keeps the filesystem only: memory, running processes and `/tmp` are lost on suspend. It is not signed off as a lasting difference; w2/m322 closes it with runtime checkpointing. Production walk (w2/m278 t011, 2026-11-11): `sbx-dbq1ddip92ls73cjjjg0` with `--idle-timeout 300` went `suspending` 308 s after its last exec, then `suspended`; the next exec resumed it and read a file written before the suspension. |
| What a suspended sandbox keeps | ⚠️ divergence, **awaiting user sign-off** | Render suspends with a runtime snapshot by default, so "its files, memory, and running processes are intact" after resume (render.com/sandboxes FAQ and launch post, checked 2026-11-07). bex's substrate pauses by committing the root filesystem to an image and recreating the pod (ADR042 D5): files and installed tools under the root filesystem survive, but memory and running processes do not, and `/tmp` (a gVisor-internal tmpfs) is empty after resume. The resumed sandbox has the same id, plan, network policy and timeout. Closing this needs a memory checkpoint (containerd/CRIU under gVisor, `runsc checkpoint`), the ADR042 D5 watch item. Until then, a user who needs a process to survive should run `--idle-timeout 0`. |
| Runtime timeout across suspension | ✅ | Matches Render (w2/m278 t010; render.com/docs/sandboxes-limits, checked 2026-11-07: "If a sandbox is suspended and later resumed, this timeout restarts", and a suspended sandbox is resumable for 30 days). Each resume, from an exec, a file transfer or the resume verb, restarts `timeoutSeconds` from the resume. The inventory reconcile reads the stamped resume time, and the OpenSandbox expiry is renewed to the resume + timeout. While a sandbox is suspended its timeout does not run. It stays resumable for 30 days from its suspension and is then terminated, including a no-timeout sandbox. A no-timeout sandbox that is running is still never terminated. Mechanism: [ADR014 D4](../ADR014-sandboxes.md#d4--idle-hibernate--gateway-observed-autopause). |
| `timeoutSeconds` (`--timeout`, including `--timeout=0`) | ✅ | Matches Render on every plan (w3/m303, 2026-11-10; CLI v2.36 commit `c280b0b6`, which removed Render's Hobby 24 h cap that w2/m263 D3=A had matched). An omitted timeout means 86400 s, `0` means no timeout and is reported as `timeoutSeconds: 0`, and 60 to 2,592,000 s (30 days) are honored. Anything else, 1–59 s included (the pinned description: "Positive values must be at least 60"), answers `400 invalid_timeout_seconds`, Render's own code (it read bex's `SANDBOX_TIMEOUT_INVALID` until w8/312; a name over 64 characters, refused by the REST gate, now carries `invalid_sandbox_name` as GraphQL and MCP did, and the builds list's bad `status` `invalid_status`). | A terminated or errored sandbox | ✅ | **Readable after its end (w3/m318, 2026-11-10).** `sandbox_records` (migration 0224) keeps each sandbox past the OpenSandbox object: written at create, ended by terminate, the lifetime reaper and the idle sweeper (which ends a recorded sandbox OpenSandbox deleted itself at its `expireTime`). **Lifetime expiry (w32/017, 2026-11-12):** the record carries the sandbox's lifetime deadline (`expires_at`, migration 0240: createdAt + `timeoutSeconds`, moved by suspend and resume), so a sandbox OpenSandbox deleted at that deadline reads `terminated` with `terminatedAt` = the deadline on the next 30 s sweep, however young; before, a sandbox under ten minutes old answered 404 for up to ten minutes and then read the sweep time. `GET /v1/sandboxes/{id}` answers an ended sandbox with `status: terminated` and `terminatedAt`; `GET /v1/sandboxes` hides it unless `status=terminated` is named; a repeat terminate answers 204, as Render's "idempotent: returns 204 from any state"; `/execs` keeps its history; both connect-token mints, suspend and resume answer Render's 409 `sandbox_not_running` (bex's own `SANDBOX_ENDED` until w8/314) for a terminated sandbox and the mints for an `errored` one, which CLI v2.36 explains as "sandbox … was terminated at …" / "errored". | Links in a copied directory (CLI `sandboxes copy`, SDK `copy_to`/`copy_from`) | ✅ | Matches Render (w32/m380, verified on production 2026-11-14 with the release CLI on pins `c99e7815ebec` and `2d9bbae6bb8d`): a directory archive keeps its symlinks, with their targets unchanged, in both directions, and skips sockets, FIFOs and devices, as render.com/docs/sandboxes-files states ("Symlinks are preserved, and sockets, FIFOs, and other special files are skipped", read 2026-11-13). ### CLI runtime copy: `ea blueprints` next steps (w2/m263)

✅ **Matches Render's intent (user decision 2026-11-07, w2/m263 D4=A).** Render's CLI tells its users to run `render …`; the bex CLI tells its users to run `bex …`. The pinned CLI's `ea blueprints create|plan|approve|update` build their next step inside upstream (`pkg/blueprint/output.go`) and print it as text and as JSON/YAML `meta.next`. bex now rewrites every run-time `render <command>` reference to `bex <command>`, for the whole class: the blueprint next steps in all three formats, returned errors such as ``Use `render workspace set` `` (`workspace current` with no workspace), `logout` output and cobra deprecation notices. An agent that follows `meta.next` stays on bex. The rewrite wraps the upstream `RunE`, like `brandLoginOutput`, and never edits API data, URLs or `render.yaml`. Rule, seams and inventory: [docs/bex-cli.md](../bex-cli.md#compatibility-and-branding-limits).

Two later extensions follow the same intent, each in upstream's exact phrases only:

- **Product name (user decision D2=A 2026-11-11, w2/073, w2/082).** Render's CLI names Render, so the bex CLI names Bex: "Successfully logged out of Bex.", "Bex will start applying your planned changes.", and `logout`'s two notes that point at the Bex dashboard. The interactive `pg create` wizard's success screen is rewritten too ("Run `bex pg get <name>`"); it is no longer a residual.
- **Variable names (w32/009).** When the launcher filled `RENDER_API_KEY` from `BEX_API_KEY` or `BEX_ACCESS_TOKEN` (w7/m426), or `RENDER_OUTPUT` from `BEX_OUTPUT`, the messages about that variable name the Bex one, which is the one in the user's environment. A `RENDER_*` variable the user set keeps its name.
