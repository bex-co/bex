The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

| Workspace resource-cap visibility | ✅ | ✅ | ✅ | ✅ | `GET /v1/owners/{ownerId}/limits`, GraphQL `workspaceLimits`, and MCP `get_workspace_limits` return one `{used,limit}` pair for services/Postgres/Key Value from the same `ResourceLimits` verb (`0` = unlimited). **w5/m35 UI:** the Usage page shows only configured caps, warns at ≥80%, and polls so independent create/delete flows converge without coupling. | API-key management (create · list · revoke · metadata) | ✅ | ✅ | ✅ | ✅ | `apikeys/rest.go` `/v1/api-keys`; GraphQL `apiKeys`/`createApiKey`/`revokeApiKey`; MCP `create/list/revoke_api_key`; dashboard mint/list/revoke (**w4/m8**). **bex is ahead of Render** — Render has _no_ REST API-key surface (dashboard-only), so the comparison target for the management verbs is bex's own cross-surface consistency, not a Render shape. **The key is a bearer token, as on Render (w7/m426, [ADR012 §8e](../ADR012-auth.md#8e-an-api-key-is-a-bearer-token-w7m426); checked on production on 2026-11-17 at pin `db48cde2bae9`: curl, GraphQL, an MCP `tools/call`, the unmodified Render CLI v2.36.0 and Render's Terraform provider v1.9.1 with one key, and 401 on every surface at the first request after its revocation; at pin `e0a5ba20aac8`, one wrong key repeated from one client behind Cloudflare answered 429 after 127 attempts):** Render mints an opaque key (`rnd_…`) sent directly as `Authorization: Bearer`. A bex key is one string, `bex_<id>_<secret>`, sent the same way on REST, GraphQL and MCP; create returns it once as `key` on all three surfaces and the dashboard shows it with a curl example. bex-api exchanges it at Hydra for the caller and remembers the token, so Render's CLI (`RENDER_API_KEY`), its Terraform provider and a plain curl work with the host and the key changed. Revoking it through bex takes effect at the next request, as Render documents. This replaces the exchange-only model this row recorded until 2026-11-16 as a deliberate divergence, which had no user sign-off: the bare secret pasted as a bearer answered `401`. **The exchange stays** for callers who want a credential that expires: the key's `id` and `secret` are still a Hydra `client_credentials` client (`{issuer}/oauth2/token`, 15-minute access token, no scope; **w4/m105** put the `client_id` in the dialog and keys table). **What a key may do, as on Render (w9/m481, [ADR024](../ADR024-members.md#an-api-key-acts-with-its-creators-role-w9m481)):** a bex key acts with its creator's current member role in the workspace it was minted in, and follows it up and down, as a Render scoped key with "Enable all" does ("Each scoped API key can only access the workspace you create it in", "Your key's access adjusts to match your new member role", [render.com/docs/api-keys](https://render.com/docs/api-keys), read 2026-11-18). So an Admin's key creates webhooks and registry credentials, updates owner notification settings and configures protected environments, and a Developer's key cannot. Until 2026-11-18 every key was a Developer, which this row described as "that workspace's full authority" with no sign-off; that divergence is gone. **Scoped keys, as on Render (w9/m496, [ADR024](../ADR024-members.md#an-api-key-carries-a-chosen-set-of-permissions-w9m496), [ADR118](../ADR118-security-review-scoped-api-keys.md); [render.com/docs/api-keys](https://render.com/docs/api-keys) re-read 2026-11-18):** a key carries a chosen subset of Render's per-area permissions (Render's areas, permission names and levels: Read, Write, Read & write, Run, Execute), never more than its creator's current role, and is refused everything else on REST, GraphQL and MCP with Render's 403 shape (`api_key_permission_denied`, naming the missing permission). Mint takes `permissions` (`POST /v1/api-keys`, `createApiKey`, `create_api_key`; omitted means All, every key minted before included); the gear icon is `PATCH /v1/api-keys/{id}`, `updateApiKeyPermissions` and `update_api_key_permissions`, a person's verb (the key's creator alone since w9/m539; also an Admin until then) that applies on the key's next request; the picker's catalog is `GET /v1/api-keys/permissions`, `apiKeyPermissionCatalog` and `list_api_key_permissions`, each level marked with whether the caller's role may grant it; a level above the creator's role answers `403 api_key_permission_above_role`. The dashboard's API keys page offers Render's picker with All, Read only and Clear all, a gear icon per key and a grant summary per row. Its table has Render's columns (Name, Permissions, Key as the client ID's first characters, Created, Last used, the trash icon) and fits the Account Settings card at 1,280 px; on a phone the name and the revoke stay put while the columns between them scroll (w9/132). Differences: Render's Workflows area is absent (Workflows is off bex's roadmap, DO_NOT_DO), bex adds two areas for products Render lacks (Cloud agents, Git) and places surfaces Render's table does not list in the area Render's docs put them (custom domains and disks under Services; registry credentials and workspace settings under Workspaces), and these REST, GraphQL and MCP verbs are bex extensions, since Render serves keys only in its dashboard. **Every member mints a key, as on Render (w9/m514, [ADR024](../ADR024-members.md#every-member-mints-and-manages-their-own-api-keys-w9m514), [ADR119](../ADR119-security-review-member-api-keys.md); [render.com/docs/api-keys](https://render.com/docs/api-keys) re-read 2026-11-19: "Go to your Account Settings page … and click **Create API key**", with a role gate only on audit log keys):** a Viewer, Contributor or Billing member mints a key on REST, GraphQL, MCP and the dashboard; it acts with exactly their role and grant, and a level above their role answers `403 api_key_permission_above_role` and is shown disabled in the picker with the role it needs. A member below Developer lists, edits and revokes the keys they minted and gets 403 for anyone else's, as on Render's per-person Account Settings (every role since w9/m539, below). Checked on dev-9 for every role, and on production on 2026-11-19 at pin `c624a4f217ff` for an Admin's Read only key (mint, list, revoke, then 401). **Every member lists their own keys, as on Render (w9/m539, [ADR024](../ADR024-members.md#every-member-mints-and-manages-their-own-api-keys-w9m514), [ADR119](../ADR119-security-review-member-api-keys.md#amendment-2026-11-20-w9m539-every-role-lists-its-own-keys); [api-keys](https://render.com/docs/api-keys), [team-members](https://render.com/docs/team-members) and [saml-sso](https://render.com/docs/saml-sso) re-read 2026-11-20, unchanged: keys live on each person's Account Settings, no role sees another member's keys there, and an org admin's only view of them is the enforce-SSO report, which bex has as the login-requirement impact list):** every role's list on REST, GraphQL, MCP and the dashboard is the keys the caller minted in the workspace, and a key's own list is empty. A Developer lists, edits and revokes no one else's key (403); editing a key's grant is its creator's alone, an Admin's edit of another member's key answering `403 api_key_permissions_editor_forbidden`. The divergence this row recorded until 2026-11-20, a Developer and an Admin listing and revoking every key in the workspace, is gone. **Divergence, pending the user's sign-off (not a user decision):** an Admin may opt into every member's keys (`GET /v1/api-keys?allMembers=true`, `apiKeys(allMembers: true)`, `list_api_keys` with `allMembers`, and the dashboard's "All members' keys" switch) and revoke any of them; every other role is refused it 403. Render has no such view. bex keeps it because a demoted member's keys (a demotion ends no membership, so the key follows its creator down and nothing revokes it) and keys with no recorded creator (no one's own) would otherwise be unrevokable from the product; a departed member's keys need none, since every exit revokes them (w2/m163). The user decides whether to keep it, drop it (the stricter variant) or let an Admin also edit another member's grant (the looser variant): [w9/137](../../.pm/w9/blocked/137.md). **No classic keys, as on Render since 2026-11-18 (w9/118):** Render's changelog entry "Fine-grained API keys now generally available" (2026-11-18, [render.com/changelog](https://render.com/changelog)) reads "Newly created Render API keys are now scoped to a single workspace" and "API keys created before this release have access to every workspace you belong to, with permissions matching your member role". Its API keys page ([render.com/docs/api-keys](https://render.com/docs/api-keys), re-read 2026-11-19) calls those older keys classic ("API keys you created before Render rolled out scoped API keys are called classic keys"), says they "continue to work as usual", recommends "replacing your classic keys with scoped API keys", answers "Can scoped API keys access multiple workspaces?" with "No", and its create form always asks to "Select the workspace your key can access". The advice to "continue creating classic API keys" that the 2026-11-18 reading quoted is gone. So Render mints no classic key, and bex mints none: a bex key lists only the workspace it was minted in (`GET /v1/owners`, GraphQL `workspaces`, MCP `list_workspaces`) and is refused its creator's other workspaces on every surface (`requireOneWorkspaceKey` in `TestAPIKeyActsWithItsCreatorsRoleE2E`, real Postgres and OpenFGA). Render's legacy form has no bex counterpart to honor: no bex key was ever minted for more than one workspace, and the keys minted before w9/m496 keep doing exactly what they did, as Render's classic keys do. A script that spans workspaces mints one key per workspace, as it must on Render today. **No verb Render serves to a key refuses an attributed key (w9/117, 2026-11-19):** Render's `POST /v1/postgres/{id}/credentials` reveals nothing and has been an ordinary write since w5/m265, and bex's native Postgres user create (`POST …/users`, `createDatabaseUser`, `create_postgres_user`), which returns the password once, admits a key with a recorded creator, capped by that creator and by "Create and delete database credentials" in its grant ([ADR024](../ADR024-members.md#an-api-key-creates-postgres-logins-as-its-creator-w9117), [ADR121](../ADR121-security-review-key-postgres-logins.md)). **A key manages members as its creator, as on Render (w9/116, [ADR024](../ADR024-members.md#an-api-key-manages-members-as-its-creator-w9116), [ADR120](../ADR120-security-review-key-member-management.md)):** an Admin's key with "Update member roles and remove members" changes a member's role and removes a member (`PATCH`/`DELETE /v1/owners/{ownerId}/members/{userId}`, the bex `/v1/workspaces/{id}/members` routes, GraphQL and MCP); a Developer's key and a key whose grant lacks the permission are refused 403, and a key never acts on its own creator (409 `CANNOT_CHANGE_OWN_ROLE` / `CANNOT_REMOVE_SELF`) or above its creator's current role. **w4/m13** added hygiene metadata — `createdBy` + `lastUsedAt` (last-used recorded off the request path, throttled) — carried identically by all four surfaces, plus a deliberate access-token TTL ([ADR012-auth.md §8](../ADR012-auth.md)). **Workspace targeting (w6/m18, w1/m55):** REST and GraphQL use `ownerId`; MCP uses per-call `workspaceId` plus the dashboard switcher; omitted means the caller's default workspace. Closed two residual gaps m14 (writes-only) left open: `ListAPIKeys` had **no tenant filter at all** (every workspace's keys were visible to any caller who could manage their own) and `RevokeAPIKey` could delete any key by id regardless of which workspace it was bound to — both now scoped, and a caller targeting a workspace they don't belong to (or trying to revoke another workspace's key) gets 403, proven against a live Postgres + OpenFGA (`TestReadSideOwnerIDTargetingE2E`). |
