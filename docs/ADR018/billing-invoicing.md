# Billing & invoicing

This is the Billing & invoicing part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), added on 2026-11-25 (w6/177) as a file of its own, the way w10/m607 split the other sections. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

**Render's surfaces.** Render's billing is a dashboard workflow. Its Billing page lets a member "View and update your plan", "Update your payment method", see the month's accrued usage and "View invoices for past months" ([render.com/docs/render-dashboard](https://render.com/docs/render-dashboard)). Its public API has no billing or invoice endpoint ([billing-invoices.md](../render-artifacts/billing-invoices.md)), and its MCP server has no billing tool. So a ✅ in the REST, GraphQL or MCP column below means the capability is reachable there, a bex-ahead extension ([bex-ahead-of-render.md](bex-ahead-of-render.md)). The UI column is the one compared with Render's behavior.

**Sign-off.** No row in this section carries the user's sign-off. Where Render's public sources do not settle a behavior, bex's choice is marked **not signed off** and names the item that owns it. Each such choice is a recommendation made under [Render parity first](../ADR008-vision.md#render-parity-first), not a user decision (the w6 approved queue of 2026-11-24, [.pm/w6/README.md](../../.pm/w6/README.md)). It stands until the user signs it off in this file, or until Render's behavior is verified and the owning item matches it. The one billing divergence the user has signed off, a card required for every workspace on hosted bex ([ADR075](../ADR075-user-onboarding.md) D7), is its own row in [services-lifecycle.md](services-lifecycle.md).

**Stripe test mode.** w6/m625 to w6/m628 shipped in code and tests. Each is parked on the same Stripe test-mode key from the user for one last check against a real Stripe invoice. Each row names the check still pending.

| Billing page: plan, payment method, accrued charges, included usage | ✅ | ✅ | ✅ | ✅ | **Render:** the Billing page shows the plan, the payment method, the month's accrued usage and past invoices ([render.com/docs/render-dashboard](https://render.com/docs/render-dashboard)). **bex:** the Billing page (`dashboard/src/routes/billing.tsx`; the plan, payment method, charges and included-usage cards in `dashboard/src/features/usage/components/`) reads GraphQL `usage` and `workspaceBillingReadiness`. REST `GET /v1/usage` and `GET /v1/workspaces/{workspaceId}/billing`, and MCP `get_usage` and `get_billing_readiness`, answer the same from one core ([ADR040](../ADR040-billing-metronome.md) §8). Each plan's included usage has a card and a field on every surface: Free instance hours ([ADR030](../ADR030-pricing.md) §10), pipeline minutes (§13), outbound bandwidth (§14) and custom domains (§16). The plan changes through GraphQL `changeWorkspacePlan`, Render's own shape (the Workspace lifecycle row in [identity-workspaces-account.md](identity-workspaces-account.md)). A payment method is added or changed on Stripe's hosted setup-mode Checkout, opened from the page ([billing-onboarding.md](../render-artifacts/billing-onboarding.md)). **Unverified:** how Render's own card form looks; no capture shows it. **Owner:** none open. |
| Invoices for past months: list, PDF, Pay Now | ✅ | ✅ | ✅ | ✅ | **Render:** each past invoice downloads as a PDF from the Billing page, and an unpaid one has Pay Now in its row's menu, which opens Stripe for it ([billing-invoices.md](../render-artifacts/billing-invoices.md); Pay Now rests on forum search summaries). **bex (w6/m625, `c3bd7a9887`):** the invoice list has been on every surface since m48/m50. Each invoice on the Billing page now has Download PDF (Stripe's `invoice_pdf`) and, while it still owes, Pay Now (Stripe's hosted invoice page). REST `GET /v1/usage` (`billing.invoices[]`), GraphQL `BillingInvoice` and MCP `get_usage` carry the same `invoicePdfUrl` and `hostedInvoiceUrl` (`TestInvoiceLinksAgreeAcrossSurfaces`). Statuses are translated, not Stripe's raw words. Until m625, a PDF or a payment meant opening the Stripe Customer Portal. [billing-onboarding.md](../render-artifacts/billing-onboarding.md) called that a deliberate difference on 2026-07-28, with no sign-off; it was a parity gap. **Not signed off:** (1) Pay Now also shows on an `uncollectible` invoice, because bex still collects it (`unpaidInvoiceStatuses`, `lego/backend/internal/billing/settle.go`) and Stripe's page still takes payment for it; whether Render offers it there is unverified. (2) Both links reach every role that views billing (Admin, Developer and Billing). Which roles see Render's Pay Now is unverified, and Render's "Edit payment method" is Admin and Billing only. **Pending:** downloading a PDF and paying an open invoice in Stripe test mode ([m625](../../.pm/w6/blocked/m625/README.md) t004). **Owner:** [w6/m625](../../.pm/w6/blocked/m625/README.md). |
| Unpaid invoice, suspension and recovery | ✅ | ✅ | ✅ | ✅ | **Render:** its terms reserve the right to suspend access "until all outstanding amounts are paid in full" ([render.com/terms](https://render.com/terms)), and an unpaid invoice's Pay Now pays it on Stripe at once. Render publishes no grace period, no list of what it suspends and no recovery timing. **bex:** the dunning lifecycle (`healthy → grace → enforcing → enforced → recovering → healthy`; [ADR040](../ADR040-billing-metronome.md) §7, w7/m52) runs on live Stripe since w4/m81. Since w6/m626, while an invoice is overdue the lifecycle read names it (`overdueInvoice`: `id`, `hostedInvoiceUrl`) on REST, GraphQL and MCP (`TestOverdueInvoiceReadsTheSameOnEverySurface`). The grace and enforced alerts offer Pay now and Update payment method. A card bound in grace or enforcement pays the unpaid invoices at once, so recovery does not wait for Stripe's next retry. **Not signed off** (bex's choices where Render publishes nothing, so neither a match nor a known divergence): (1) grace lasts `BEX_STRIPE_GRACE_PERIOD`, 168h by default. (2) Enforcement suspends web, private, worker and cron services, hibernates Postgres and scales Key Value to zero; it leaves static sites, data and secrets untouched. (3) A newly bound card is charged at once, off-session, oldest invoice first, one attempt per invoice and card. **Pending:** recovery within one reconcile interval in Stripe test mode ([m626](../../.pm/w6/blocked/m626/README.md) t001, t004). A card changed inside the Stripe portal pays at once only after the live endpoint sends `customer.updated` ([w2/070](../../.pm/w2/blocked/070.md)). **Owner:** [w6/m626](../../.pm/w6/blocked/m626/README.md). |
| Billing email | ✅ | ✅ | ✅ | ✅ | **Render:** Pro and higher set a billing email of their own, and Hobby's is the account email and cannot be edited ([billing-email.md](../render-artifacts/billing-email.md)). **bex (w6/m627):** Admin, Developer and Billing read it, and Admin and Billing set it on Pro and higher. It is served on the Billing page, REST `GET`/`PUT /v1/workspaces/{workspaceId}/billing/email`, GraphQL `workspaceBillingEmail`/`setWorkspaceBillingEmail` and MCP `get_billing_email`/`update_billing_email` (`TestBillingEmailOnEverySurfaceE2E`). On Hobby the read is the owner's account email, and a write is refused with `PLAN_FEATURE_REQUIRED` (`feature: billingEmail`, `requiredPlan: pro`). bex's Stripe portal no longer offers an email change, live since 2026-11-25. A Stripe Customer created by Checkout or by usage takes the billing email too ([w6/179](../../.pm/w6/done/179.md), `TestNewCustomersTakeTheBillingEmailE2E`). **Not signed off:** (1) bex's billing notices also go to a Pro or higher workspace's billing email: grace, suspension, recovery and the included-usage notices. Which of Render's emails reach its billing email is unverified. (2) A move to Hobby resets the billing email to the owner's account email; Render's downgrade behavior is unverified. **Pending:** a grace notice reaching a Pro workspace's billing email, and the test-mode portal's configuration, in Stripe test mode ([m627](../../.pm/w6/blocked/m627/README.md) t010). **Owner:** [w6/m627](../../.pm/w6/blocked/m627/README.md). |
| Billing info on invoices: company name, address, VAT or tax ID | ✅ | ✅ | ✅ | ✅ | **Render:** a Billing page button adds company name, address or VAT number to every invoice ([billing-info.md](../render-artifacts/billing-info.md)). **bex (w6/m628):** every Stripe Customer bex creates is named after its workspace, so invoices bill the workspace's name, never its `tea-` id, and a rename follows. Billing info sets a company name, an address and one VAT or tax ID, typed as one of Stripe's customer tax ID types. Admin, Developer and Billing read it, and Admin and Billing set it. It is served on the Billing page, REST `GET`/`PUT /v1/workspaces/{workspaceId}/billing/info`, GraphQL `workspaceBillingInfo`/`setWorkspaceBillingInfo` and MCP `get_billing_info`/`update_billing_info` (`TestBillingInfoOnEverySurfaceE2E`). A tax ID Stripe refuses answers `BILLING_INFO_INVALID` naming its field. **⚠️ Open divergence, not signed off:** bex's tax ID field appears once any country with a Stripe tax ID type is chosen (`dashboard/src/features/usage/lib/tax-id-types.ts`), and the API takes any of those types. Render's VAT field appears only for EU countries, by a staff answer read through a search summary (unverified). **Not signed off:** with no billing info set, the Bill-to is the workspace's display name; what Render prints then is unverified. **Open decision:** the Customers Checkout created before m628 still bill the cardholder's name ([w6/180](../../.pm/w6/180.md)). **Pending:** a finalized invoice per Customer path, a rename and the billing info on the next invoice, in Stripe test mode ([m628](../../.pm/w6/blocked/m628/README.md) t009). **Owner:** [w6/m628](../../.pm/w6/blocked/m628/README.md), [w6/180](../../.pm/w6/180.md). |

| Included usage and approaching-limit emails | ✅ | ✅ | ✅ | ✅ | **Render:** each plan includes Free instance hours, pipeline minutes and outbound bandwidth ([ADR030](../ADR030-pricing.md) §10, §13, §14). Which emails Render sends about them, and when, is not documented. **bex:** `freeInstanceHours`, `buildMinutes` and `includedBandwidth` (`{used, included}`) on REST `GET /v1/usage`, GraphQL `usage` and MCP `get_usage`, with a card each on the Billing page. A workspace's billing owners get one email at 80% and one at exhaustion each month (`lego/backend/internal/notifications/free_hours.go`, `build_minutes.go`, `bandwidth.go`), and a Pro or higher workspace's billing email gets them too (w6/m627). **Not signed off:** the two emails, the 80% threshold and their wording are bex's, since Render's emails are unverified (ADR030 §10, §13, §14). **Owner:** none open. |
| Sales tax and VAT collection | ◐ | ◐ | ◐ | ◐ | **An open gap, not a divergence.** Stripe Tax stays off until an operator supplies a Product tax code, chooses inclusive or exclusive prices, and Stripe reports an active tax registration in the same mode ([ADR040](../ADR040-billing-metronome.md) §6; [the runbook's Stripe Tax gate](../runbooks/stripe-billing-setup.md#optional-stripe-tax-gate)).
