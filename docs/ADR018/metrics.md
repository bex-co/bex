# Metrics

This is the Metrics part of the [Render parity matrix](../ADR018-render-parity.md) (ADR018), moved out of it on 2026-11-23 (w10/m607) to keep the ledger under the 1 MiB blob limit. The matrix's legend, method and evidence sources apply here. Amend these rows in this file, not in ADR018.

**Operational qualification (w4/m144, 2026-10-02):** production Prometheus was OOM-killed during WAL replay, so the implemented ranged-metrics contracts below were unavailable. A production-only recovery budget is prepared; successful existing-data replay, fresh REST/GraphQL/MCP/dashboard samples and restart stability remain unverified. CPU/memory limits still come from pod specs. See [ADR010's recovery gate](../ADR010-observability.md#production-replay-budget-w4m144-2026-10-02). [Render's service metrics](https://render.com/docs/service-metrics) includes CPU and memory; this recovery preserves Bex's existing API meanings and extensions, and does not reconstruct historical samples lost during the outage.

The LogQL pipeline now keeps only entries whose own Loki timestamp lies in `[start, end]` — compared as integer seconds plus a nanosecond remainder, since LogQL's numeric filter is float64 — and drops the two temporary labels before aggregation, so count and host/path latency both see exactly the window, matching the request-log read. Pinned-Loki 3.6.7 execution in the backend suite covers ±1 ns endpoints, same-bucket windows and grouping. REST, GraphQL and MCP share that source; the Prometheus-backed metrics were already evaluated at `end`. **Render's REST contract (w1/m155, w5/m140):** `aggregateBy=statusCode` returns one series per status code (label `statusCode`); before m155 REST dropped `aggregateBy` and answered the single ungrouped series. **w5/m140** served the rest of Render's enum and argument set: `aggregateBy=host` (GraphQL `aggregateBy: ["HOST"]`, MCP `aggregateHttpRequestCountsBy: "host"`, dashboard Group by → Host) returns one request-count series per request host, labelled `host`, from the request-log store — never the host-less Traefik counter, so with no store it is the host filter's 503 `LOG_STORE_UNAVAILABLE`. `aggregationMethod=MAX | MIN`on cpu (MCP`cpuUsageAggregationMethod`, which Render's MCP server passes straight to REST; GraphQL `aggregationMethod`, which GraphQL used to accept and drop) reports each resolution step's highest/lowest per-instance rate (`max*over_time`/`min_over_time`over the existing rate at the 15 s scrape grain), for services and datastores alike; AVG/omitted keeps the plain rate. MCP`get_metrics` accepts Render's metric types (`cpu_usage`, `memory_usage`, `http_request_count`, `bandwidth_usage`, and `active_connections`for a`dpg-`/`red-`resource) alongside bex's ids, labelling each series with the requested name.`api/render_metrics_contract_test.go`walks every Render`/metrics`path and parameter from the pinned spec, so a new one fails until it has a verdict; GraphQL`metrics(…)` + dashboard companions (`monthToDateBandwidth`, `metricsFilters`); MCP `get_metrics`; Metrics tab (w3/m2–m4.5). **Bandwidth availability (w1/m50):** the interactive bandwidth reads are best-effort like Render's own chart — an egress source failing its ADR023 health product inside the window no longer errors the read (that strictness stays billing-only); the series carries a bex-extension `degraded_sources`label (and`monthToDateBandwidth`a`degradedSources`field, both absent when healthy) and the dashboard annotates "Partial data" instead of blanking — Render exposes no health annotation at all, so the extension is additive. **Bandwidth scope fix (w1/m51):** the router resolver now includes Traefik's`websecure-`TLS sibling router (Traefik v3 mints it for every TLS-covered Ingress host — it carries essentially all real HTTPS bytes), so bandwidth/egress across REST/GraphQL/MCP/dashboard/billing stopped counting only 80→443 redirect traffic; the usage rollup simultaneously moved to per-source hour gating (healthy sources record, unhealthy are skipped, transport defers) so prod actually writes`egress_bytes`rows. CPU/mem need metrics-server/Prometheus (503 otherwise). **`host`/`path`filters (w3/m12 → shipped w5/m58):** now supported for`http_requests`/`http_latency`on every surface (REST`?host=&path=`, GraphQL `HOST`/`PATH`filter entries, MCP`get_metrics` `host`/`path`, dashboard Network-card Host dropdown + free-text Path input). Several GraphQL`STATUS_CODE`values are refused with a named 400 instead of silently using the first. MCP`httpHost`/`httpPath`stay scalar, as in Render's MCP. Store-gated: with no`BEX_LOKI_URL`the read returns`ErrLogStoreUnavailable`(503, the honest "needs the log store" state), never a silently-unfiltered result; host/path on`bandwidth`(or any non-request metric) is a named 400 (no per-request axis) on REST and GraphQL. Path filters are bounded at 64 values, 512 bytes per pattern, and 8 `*` wildcards per pattern (400 beyond those bounds). **Request/bandwidth are per-bucket counts (w4/m108, 2026-09-16):**`http_requests`is`sum(increase(...[step]))`(Prometheus) /`count_over_time`(Loki host/path), and the Outbound Bandwidth chart is`egressquery.SumIncreases`over the same step — matching month-to-date / metering`Increase`, so Σ(series) is request count / bytes in the window rather than rate×window. See [metrics-page.md](../render-artifacts/metrics-page.md) § w4/m108. **Shared fate with the request-log stream (w6/m131/t009):** because a host/path-filtered read is served from that store, the w6/m131 attribution outage zeroed it too — and more visibly than the logs symptom, since the unfiltered graph showed real traffic (61 points, 24.33 total on`agentmarketcap-1`) while selecting the service's **own** hostname from the Host dropdown returned 0 series and the card read "No data in range". The`RequestLogMetrics == nil`guard covers "source unwired" (503), not "source wired but the stream is not being produced" — that second state is deliberately not represented, for the reason recorded in row 182 (w6/m131/t002): it is indistinguishable from a genuinely quiet host at this vantage point, so it is caught out-of-band by the scheduled`request-logs-liveness` probe instead of by an error a quiet host would also raise. Host discovery stays App-derived here for the same reason it does in the logs read (row 182, t003). **`ownerId`in GraphQL (w3/m18):** accepted, silently ignored — the verb already scopes to the App's own workspace via`AuthorizeApp`, so `ownerId` adds no filtering power. **`aggregateBy=SERVICE_INSTANCE_ID` (w3/m18):** silently ignored — request PromQL sums at the Traefik service level; per-pod request breakdowns would require per-pod metrics that aren't scraped. **Per-replica percentage correction (w5/m90):** m89's replica aggregation exposed that every percentage divided by one latest aggregate limit — mixed-limit replicas (0.4 of 0.5 vs 0.5 of 1 CPU) misread as 40%/50% instead of 80%/50%. bex-api now normalizes each replica against its own trustworthy limit (kube-state-metrics limit history joined per timestamp; untrustworthy denominators omitted, never faked) before MIN/MAX/AVG (80%/50% → MIN 50%, MAX 80%, AVG 65%), exposed identically on REST (`?percentage=true`), GraphQL (bex-extension `percentage` boolean — documented, no Render equivalent), MCP (`percentage`), and the dashboard (which renders server percentages directly; mixed limits read as "Limits vary" in the header, unavailable percentages get explicit copy distinct from no-data). **Instance-selection preservation (w5/m91):** m89 pruned unavailable selections into all-instances mode and inferred INSTANCE eligibility from returned labels, so an empty supported cpu/memory window misreported a bad request.
