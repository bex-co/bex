| Application logs (query + live tail) | ✅ | ✅ | ✅ | ✅ | **A start of any age reads what is kept (w8/374, 2026-11-21):** Render's List logs documents `startTime` with no range limit (pinned `render-public-api-1.json` `list-logs` and `list-logs-values`: "Defaults to `now() - 1 hour`", no range error), yet `bex logs --start 30d`, `--start 720h` or any older start with no `--end` was a 400 `query range exceeds 720 hours`, because `BEX_MAX_QUERY_HOURS` was checked before the plan floor. Every log read (REST `/v1/logs` and `/v1/logs/values`, GraphQL `logs` and `logLabelValues`, MCP `list_logs` and `list_log_label_values`) now clamps a start past the cap to the cap, measured back from the window's end up to now (`renderWindow`), and the plan's floor narrows it further. The store is still asked for at most 720 hours, the longest plan window, so no kept line is lost; the page cursors name the clamped start; only an inverted window is a 400. The subscribe stream never had the check. Metrics and events keep their 400 ([ADR010](../ADR010-observability.md#durability--retention)). **Render's eight levels, each stored as itself (w3/086, 2026-11-20):** Render's `level` takes eight values, `debug`, `info`, `notice`, `warning`, `error`, `critical`, `alert` and `emergency`, the syslog severities. Its docs list them for the explorer's level mark and the `level` filter ([Logging](https://render.com/docs/logging)), its log streams map a JSON or logfmt `level` field "to an appropriate syslog priority" ([Log streams](https://render.com/docs/log-streams)), and in the reference workspace its dashboard's `logValues(label: LEVEL)` answered exactly those eight for the app and the request logs of two projects, while a JSON `"level":"warn"` line read `warning`. No line there was logged at `notice` or `critical`, so a line at each is not observed directly: the eight values are Render's label vocabulary, not a fold of it. bex's shipper stored four buckets, `notice` as `info` and `critical`, `crit`, `alert` and `emergency` as `error`. It now stores each of the eight under its own name (`crit` → `critical`, `emerg` → `emergency`; `fatal`, `panic` and pino's 50 and 60 stay `error`, Render's handling of them unobserved) in the `app_logs` template and the live tail's copy (`applevel.go`), which `TestAppLineLevelMatchesShipper` runs over the whole vocabulary and `scripts/test_log_shipper.py` runs in the real Alloy image. Lines stored before the change keep `info` or `error` and are found by those. The Postgres and Key Value pipelines keep their four buckets (a Postgres `NOTICE` record is `info`), so on a datastore `notice` still selects `info` and the error-class names `error`. The service Logs tab's Level filter offers the eight in Render's order. **Render's 6,000 lines a minute per instance (w3/m506, 2026-11-19):** Render keeps at most 6,000 application-generated lines a minute for each running instance and drops the rest from the explorer and log streams ([Logging](https://render.com/docs/logging)). bex keeps the same per pod in history (the shipper's `app_logs` token bucket, 100 lines a second with a 6,000-line burst) and in the live tail (`lineCap`, before any filter), so REST, GraphQL, MCP, the CLI and the dashboard read the same capped lines; request, Postgres, Key Value and build lines are not capped. **Recommendation, not a user decision:** Render does not document its window, so a flood's first minute after a quiet spell keeps up to 12,000 lines here (the burst plus a minute's refill). **A tail opened mid-flood (w8/341, 2026-11-19)** shows the 100 lines a second history keeps, not a fresh 6,000-line burst: it warms each instance's bucket over the two minutes before its start bound without showing those lines, and the store-less history read warms the same way. **The same lines, not only as many (w8/m525, 2026-11-20):** the shipper's bucket refilled by Alloy's clock when it read a batch and the tail's by each line's timestamp, so on production a tail opened 100 s into a flood kept as many lines as history but 37.7% other ones (47% before the warm-up). Both now count each line at its own timestamp in whole tokens on one 10 ms grid (the carried `limit-entry-timestamp.patch`, `refill_by_entry_timestamp` on `app_logs`, and `lineCap`), checked against one shared table, so after a flood or a quiet spell they keep the same lines. The production replay on pin `12716d1d7097` measured 0%: none of the tail's 3,590 lines was missing from history, which kept exactly those lines (w8/m525 t005). Whether Render's server fills such a page past 100 lines is not observed, since no Render account was in reach; if it does, this page size is the difference until a follow-up raises the clamp. **A tail begins when it opens (w8/288, 2026-11-12):** Render documents `--tail` as "Stream new logs" and its subscribe as "Logs are streamed in real-time as they are generated". The plugin runs interpreted, and Yaegi hides `Flush` from the compiled proxy behind it, so the instance flushes as the proxy would. Root cause: the shipper reconstructs `{namespace, app}` for a request line by parsing Traefik's `ServiceName`, and its regex was anchored to the literal namespace `default`; under ADR043 tenant Apps live in per-workspace `tea-<xid>` namespaces (and their CR names are tenant-prefixed), so every tenant access line missed the regex and was dropped as `not_a_tenant_app`. The regex now matches `tea-<xid>` as well as `default` (`deploy/gitops/base/log-shipper.yaml`); `TestShipperRegex*` reads the deployed config and asserts a tenant/`default`/non-tenant `ServiceName` attributes to the exact `{namespace, app}` bex-api queries by — the guard w3/m8 lacked. Tenancy is enforced by the query selector (namespace + app both pinned to the caller's resolved values), so the shipper labeling can only hide a line, never leak one. **"Store up, stream not produced" is deliberately NOT a distinct API state (w6/m131/t002).** A `type=request` query against a live store returns `200 {"logs":[]}` whether the service was genuinely quiet or the pipeline had stopped producing, and bex-api cannot tell those apart: Loki's label index is empty in both cases, so there is nothing per-resource to key on. The only honest per-query answer is the empty page — manufacturing an error would lie to every quiet service, and the store-absent 503 path (which keys on store presence and is unchanged) does not extend to it. The distinction is a **platform**-health property, not a per-query one, so it is carried out-of-band: `scripts/request-logs-liveness.sh` runs on a schedule (`.github/workflows/ssh-edge-liveness.yml`, alongside the SSH KEXINIT synthetic) and fails loudly — opening a tracking issue — when no `type=request` stream exists **for any tenant namespace**. That last qualifier is the lesson: `scripts/logs-verify.sh`, the acceptance script w3/m8 left owed, could not have caught this outage even if it HAD been run in production, because it exercises `APP_NS=default` — precisely the one namespace the broken regex still matched.
