## Context

### The product

"Code on the tenant's GitHub repo, in our cloud": the tenant assigns a task (dashboard, IDE, or MCP), bex runs a coding agent in an isolated sandbox with the repo checked out, and the result comes back as a draft PR — the shape of GitHub Copilot cloud agent, OpenAI Codex cloud, Devin, Claude Code on the web, and Cursor cloud agents. This is pillar 5 territory (ADR008): the sandbox substrate exists (ADR042); this ADR is the product layer on top of it.

### What the exemplars verifiably do

An adversarially verified research pass (2026-08-01; 25 sources fetched, 21 claims confirmed, 4 refuted) found the exemplars converge on one architecture. The load-bearing findings, all 3-0 verified against primary docs:

- **Ephemeral sandbox per task, repo preloaded.** Copilot cloud agent runs in "its own ephemeral development environment, powered by GitHub Actions" ([GitHub docs](https://docs.github.com/copilot/concepts/agents/coding-agent/about-coding-agent)); Codex runs each task in an isolated cloud container checked out at the selected branch, where it edits files and runs tests/linters ([OpenAI](https://openai.com/index/introducing-codex/)), with a 12h container-state cache for follow-up turns.
- **Egress default-deny, opt-in internet.** Codex launched with agent-phase internet disabled (setup scripts run _with_ network to install dependencies; the agent phase then runs without), later adding opt-in domain allowlists ([Codex internet-access docs](https://developers.openai.com/codex/cloud/internet-access)). Copilot ships a customizable [agent firewall](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-firewall). Network egress control — not in-sandbox policy — is the primary prompt-injection/exfiltration mitigation.
- **Git-native delivery, in-band steering.** Copilot: exactly one branch and one PR per task, steered by `@copilot` PR comments. Codex: commits inside the sandbox with citations of terminal logs and test outputs as verifiable evidence; the user promotes to a PR. Codex shipped _without_ mid-task steering and had to add it — a steering channel is table stakes.
- **Per-request billing is dead.** GitHub retired premium requests effective 2026-06-01, replacing them with token-passthrough "AI credits" (1 credit = $0.01, metered on input/output/cached tokens at published per-model rates), explicitly because "a quick chat question and a multi-hour autonomous coding session can cost the user the same amount" ([GitHub blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/)). GitHub now dual-meters agentic features: tokens (AI credits) **plus** compute (Actions minutes) ([pricing docs](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)). Devin (ACU quota + overage, [billing docs](https://docs.devin.ai/admin/billing)) and Cursor (plan-included usage pool, arrears overage, [pricing](https://cursor.com/pricing)) fit the same subscription-plus-metered pattern. AWS AgentCore Runtime prices the compute leg per-second on actual CPU ($0.0895/vCPU-hr) + peak memory ($0.00945/GB-hr) with idle CPU-free ([pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)).

Research caveats: no claims about the _internal_ architecture of Devin, Claude Code on the web, or Cursor cloud agents survived verification (only their billing did), so the architectural convergence rests on Copilot + Codex evidence. The ACP adopter ecosystem (below) was fetched but not adversarially verified. Claude Code resale/ToS constraints produced no surviving claims and remain an open question.

### ACP as the interface

The [Agent Client Protocol](https://agentclientprotocol.com/protocol/overview) (Zed-originated) is JSON-RPC 2.0 — request/response methods plus one-way notifications — covering sessions, prompt turns, tool-call streaming, permission requests, file ops, and terminals. Verified transport state ([spec](https://agentclientprotocol.com/protocol/transports)): stdio is the transport agents SHOULD support; a Streamable HTTP transport is a **draft**; custom transports MAY be implemented — so a WebSocket carrying newline-delimited JSON-RPC is architecturally sanctioned but not standardized, and **auth, reconnection, and multi-client attach are left to the implementation**. Session resumption (`session/load`) is an **optional** agent capability: clients MUST check `loadSession` in the `initialize` response and MUST NOT call `session/load` if absent ([session setup](https://agentclientprotocol.com/protocol/session-setup)). Ecosystem signals (Claude Code via ACP in [Zed](https://zed.dev/blog/claude-code-via-acp), Gemini CLI, [OpenHands](https://www.openhands.dev/blog/use-any-coding-agent-in-openhands-with-acp), community bridges like [acp-ws-bridge](https://github.com/ytthuan/acp-ws-bridge)) confirm the bridging pattern is being pursued; verify per-agent maturity before committing to a binary. Notably, an ACP provider for the Vercel AI SDK ([`@mcpc-tech/acp-ai-provider`](https://github.com/mcpc-tech/mcpc/tree/main/packages/acp-ai-provider), listed in the [AI SDK community-provider directory](https://ai-sdk.dev/providers/community-providers/acp)) adapts spawned ACP agents to `LanguageModelV3`/`streamText` — stdio-spawn only, stateful sessions via `persistSession`/`existingSessionId` (→ `session/load`), no token-usage reporting; D3 builds on it.

## Decision

### Session architecture

![Session architecture: the developer uses the dashboard (TanStack, useChat) or an IDE (native ACP client); the dashboard calls POST /v1/agent-sessions on bex-api and both clients stream through the isolated ssh-gateway, the sole session ingress and sole holder of pods/exec; bex-api authorizes can_operate with OpenFGA, writes control-plane Postgres, sends meter events to Stripe, mints GitHub installation tokens and opens draft PRs, and drives the OpenSandbox server, which manages the workspace's gVisor, default-deny sandbox namespace; the gateway claims nonces and tees transcripts into Postgres, proxies both streams to the session driver and proxies token mints to bex-api; the driver talks stdio ACP JSON-RPC to the agent binary, whose Pod-bound Git smart-HTTP client refreshes tokens through the gateway, and the agent clones and pushes bex-agent branches to GitHub](assets/ADR047-cloud-coding-agent-sessions-architecture.svg)

### D1 — Sandbox-per-session on the existing substrate

One OpenSandbox sandbox per agent session in the workspace's `<ws>-sandbox` namespace, from an agent template image (agent binary + ACP shim + git + language toolchains), created through the existing lifecycle client with the same reserved-metadata stamping (`bex.co/owner`, `bex.co/workspace`, `app.bex.co/regime=sandbox`). Setup phase (clone + dependency install, network open per D5) is separated from the agent phase, Codex-style. Idle sessions hibernate via rootfs snapshot; resume restores the rootfs and restarts the agent process (see D3 for conversation state). No new substrate: kubernetes-sigs/agent-sandbox and similar were considered and rejected — they would rebuild w3/m32 for no capability gain.

**Amended 2026-11-18 (w10/017): a session chooses its sandbox size.** `agentConfig.template` names the agent template a session runs on, on every create surface (REST, GraphQL, MCP, an automation's template). bex-api registers two: `agent` (2 CPU, 4 GB), the default, and `agent-4c-8g` (4 CPU, 8 GB), which the sandbox meter bills as the larger shape. Three `bex agent run` sessions on `bex-co/beancount-io` ran out of memory on the default while the automations running the same routine on `agent-4c-8g` finished, and the CLI had no way to ask for the larger one. `bex agent run`, `chat`, `handoff` and `automations create|update` now take `--template`. A create naming any other template is refused at once with `AGENT_SESSION_INPUT_INVALID` on `agentConfig.template` and the list of templates, where before the session failed only when its sandbox was started. A session whose sandbox is killed for memory has a failure reason that names its template and the next larger one. Devin also lets a session pick its machine when it starts and keeps an organization default ([Outposts](https://docs.devin.ai/cloud/outposts/overview), read 2026-11-18). bex has no workspace default template yet, and the dashboard composer does not offer the choice (`w10/023`).

**Amended 2026-11-19 (w10/m519): a workspace default template, and the choice in every client.** The reference is Devin, where a session's machine is picked under Configuration → Virtual environment when it starts and an admin sets the organization default under Settings → Devin → Default platform or through the API, for sessions created afterwards ([Outposts](https://docs.devin.ai/cloud/outposts/overview), read 2026-11-19).

- **The default.** The agent environment (D5's amendment of 2026-10-27) gains `defaultTemplate` (`agent_environments.default_template`, `''` for the platform's). A workspace admin sets it to any registered agent template through REST `PATCH /v1/agent-environment`, GraphQL `updateAgentEnvironment`, MCP `update_agent_environment`, `bex agent env set --default-template` and Settings → Agents; `""` returns to `agent`. Any other name is `400 AGENT_ENVIRONMENT_TEMPLATE_INVALID` with `field: defaultTemplate`, `template` and `templates` (the names), and nothing is written.
- **Where an empty choice resolves.** A create naming no `agentConfig.template` takes the workspace default in the create's workspace-dependent half (`resolveCreateModel`), which also resolves the model, and records it in the session's `agentConfig`. Every read then reports the template the session runs on, its later turns keep it, and a change of the default applies only to sessions created afterwards. A child session takes its parent's recorded template. An automation's template stores only an explicit choice, so a run naming none takes the default in force when it fires. A session created before templates were recorded reads `agent`, which it ran on.
- **A default that stopped being registered.** It is kept in the row but not used: sessions run on `agent`, and the reads report `agent` as the default, never a failed session. Saving the default again refuses the name.
- **The list.** The agent environment read and the capabilities read (REST, GraphQL, MCP) carry `defaultTemplate` (the effective default) and `templates`, each `{name, cpu, memoryGb}` with numbers a client sorts and formats, smallest first: the session-only templates `sandbox.AgentSessionLifecycle.AgentTemplates` lists, never an image or a general sandbox template. The capabilities read was written for the mobile composer (w11/m6) when every sandbox template was internal; the agent templates are now a customer choice, so it lists them. The dashboard and the CLI read the list from there and hard-code no name or size.
- **Errors.** The create's refusal of an unknown template is unchanged (`AGENT_SESSION_INPUT_INVALID` on `agentConfig.template`, listing the templates and their sizes; it gains the `template` param and no longer calls `agent` "the default", since a workspace's may differ). The out-of-memory reason names the session's template and the next larger one and says to pick it as the Sandbox in the dashboard's new-session composer or with `bex agent run --template`.
- **Clients.** The `/agents` composer and the automation form offer the templates with their sizes and preselect the workspace default (the form's empty choice is "the workspace's default at each run"); Settings → Agents sets the default for admins and shows it to members; the session header shows the session's template and size; `bex agent models` lists the templates with the default marked and `bex agent env` shows the default.
- **Mobile (w10/031, 2026-11-20).** The phone composer reads `defaultTemplate` and `templates` from the capabilities read and shows the template the session will run on, with its CPU and memory, in a pill beside the agent and model. With more than one template the pill opens a picker of them all, sized and with the default marked, and the session starts on the pick (`agentConfig.template`, sent only when it is not the default); a workspace with one template shows it without a choice, and a read with none shows no pill. A session keeps its template for every turn, as a Devin session keeps its machine, so no message switches it.

### D2 — Repo access: gateway-held installation token, smart-HTTP branch confinement

- bex-api mints a **per-session** GitHub App installation token from the existing ADR026 integration, scoped to the target repo, `contents:write` added (sessions must push), and `workflows:write` wherever the installation grants it ([amendment w10/014](#workflow-files-amendment-w10014-2026-11-18)).
- The token never enters the sandbox. Git speaks smart HTTP to the isolated gateway; after direct source-Pod verification, the gateway refreshes the token through bex-api and injects it only on its fixed TLS hop to `github.com/<bound-repo>`. The sandbox image contains no credential helper or cache.
- **Branch confinement is server-side and protocol-enforced**: the gateway parses every receive-pack command and rejects the request unless every updated ref is exactly the session's bound `refs/heads/bex-agent/*` branch. Legal leading `shallow <oid>` declarations are validated, bounded, and forwarded without being mistaken for ref commands; declarations after the command list, malformed object ids, deletions, and every other ref still fail closed. Tenant branch protection remains defense in depth, not the primary boundary.
- **Snapshot hygiene**: credentials (and the OpenSandbox tenant key) are scrubbed before any rootfs snapshot; a resumed sandbox re-fetches through the helper. _Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): no credential reaches the sandbox, so the pre-snapshot scrub is removed._

Implementation contract (security amendment): OpenSandbox metadata carries only the session id plus SHA-256 label digests of repository and branch. The non-secret proxy URL encodes those exact values; the gateway resolves the direct source IP to one Pod in the claimed `<ws>-sandbox` namespace and verifies every digest before its HMAC-authenticated bex-api mint. bex-api checks current lifecycle and repository ownership before minting one-repository `contents:write`. The gateway retains the token, fixes upstream host/repo, rejects redirects, and parses receive-pack for the exact branch. GitHub tokens do not encode branch scope, so smart-HTTP enforcement closes the gap left by token narrowing alone.

#### Workflow files (amendment w10/014, 2026-11-18)

GitHub refuses any ref update that changes a file under `.github/workflows/` unless the token holds `workflows:write`, and it compares a new branch with the default branch. So a session that started from an older commit could not push its branch at all once the default branch had changed a workflow. Four production sessions pinned to `35a5a52ec` failed this way, including one that pushed the pinned commit unchanged, and `open_or_update_draft_pr` then answered `branch_not_pushed`. The refusal was reproduced on `bex-co/bex` on 2026-11-18, and the same push with `workflows:write` was accepted.

Devin's GitHub App holds Workflows read and write ("Allow Devin to set up new workflows, e.g. to help configure CI/CD", [docs.devin.ai/integrations/gh](https://docs.devin.ai/integrations/gh)). The bex App already held it, and every installation had granted it. The session token and the takeover fast-forward token therefore request `contents:write` + `workflows:write`.

- An installation that has not granted Workflows (an App created from the older manifest, or an owner who has not yet approved the change) refuses that mint with 422. The mint then retries with `contents:write` alone, so the session still pushes every change that leaves the workflow files as the default branch has them.
- For that case the gateway puts a plain-words explanation in front of GitHub's refusal, as side-band progress that git prints as `remote: bex: …`. It says why the push was refused, that `git fetch origin HEAD && git merge FETCH_HEAD` fixes a branch that started from an older commit, and that a real workflow edit needs an owner of the account to approve the permission. Every byte GitHub sent still reaches the agent.
- The smart-HTTP branch confinement above is unchanged. `workflows:write` therefore reaches only the session's own `bex-agent/*` branch, plus the pull request branch a takeover fast-forwards, where `/devin` pushes too.
- Security note: a workflow added on the session branch can run on its push with the repository's Actions secrets. The agent could already reach those secrets by editing code that an existing `pull_request` workflow runs for its draft PR. Environment protection rules still gate deployment secrets.

#### `gh` reads (amendment w10/m513, 2026-11-19)

A repo session's `gh` reads its repository's GitHub API, and the token still never enters the sandbox. The driver serves gh's `http_unix_socket` and forwards `api.github.com` calls to a fifth-segment route on the same Pod-bound proxy URL, `<proxy URL>/github-api/<REST path or graphql>`. After the same source-Pod and label-digest verification, the gateway admits REST `GET`/`HEAD` under `/repos/<bound repo>` and GraphQL queries whose top-level fields read that repository, a node by id, the rate limit or the schema. It asks bex-api's new internal verb (`/v1/agent-session-github-read-credentials`, the mint's HMAC, lifecycle and owner checks; never for a repository environment build) for a token narrowed to the one repository with read-only `actions`, `checks`, `statuses`, `pull_requests`, `contents` and `metadata`, and injects it on the fixed `api.github.com` hop. It follows GitHub's storage redirects for logs and archives itself, without the token, and refuses every write with a message naming the `bex` MCP tools. The route has its own per-session (1000) and per-workspace (10000) budget. Devin's machine carries a real `gh` token instead ([Security profiles](https://docs.devin.ai/product-guides/security-profiles), read 2026-11-19); bex keeps this section's invariant and matches the reads, which is what an agent needs to reproduce CI. Writes stay with the ADR090 tools; [ADR090 D4](ADR090-agent-owned-delivery.md#d4--agent-facing-tool-the-bex-stdio-mcp-server) has the details.

#### `gh` writes (amendment w10/m522, 2026-11-19)

The same route now admits the writes Devin's `gh` token makes on the session's repository, except opening or changing the pull request and changing code: comments and review-thread replies, reviews whose event is not `APPROVE`, labels, assignees and requested reviewers, issues (create, comment, edit, close, reopen), re-running or cancelling Actions runs and jobs, and (since w10/033, 2026-11-20) dispatching a workflow on the session branch only, as REST paths under `/repos/<bound repo>/` and as the GraphQL mutations the pinned gh sends for them. For each admitted write the gateway asks bex-api's second internal verb (`/v1/agent-session-github-write-credentials`, the read verb's HMAC and checks, audited as `agentsessions.MintGitHubWriteCredential`) for a token narrowed to the one repository with `pull_requests`, `issues` and `actions` write plus the read token's reads, never `contents`, `workflows`, `statuses`, `checks` or `administration` write, and injects it on the same fixed hop; reads keep the read-only token. An installation that has not granted the whole set gets the intersection with what it granted. Everything else stays refused before GitHub, naming `open_or_update_draft_pr`, `reply_on_pull_request` (since w10/m538 also `mark_pull_request_ready` and `merge_pull_request`) and the session branch: pull request create, edit, ready, merge, close and reopen, approvals and dismissals, workflow dispatch on any other ref, commit statuses and checks, contents, refs, releases, settings, and every other repository. This section's invariant holds: the sandbox still holds no token, and code still reaches GitHub only through the branch-confined Git proxy. Writes share the route's budget, and a session's own comment, posted as the App's bot, never steers it (D11). [ADR090 D4](ADR090-agent-owned-delivery.md#d4--agent-facing-tool-the-bex-stdio-mcp-server) lists each admitted and refused write with its reason.

#### A workspace can turn `gh` off (amendment w10/m524, 2026-11-19)

A Devin security profile can "remove the GitHub CLI token" from the machine. Sessions under it "keep working with your repositories through Devin's git integration" but "cannot make direct GitHub API calls", and org admins hold the "Manage security profiles" permission by default ([Security profiles](https://docs.devin.ai/product-guides/security-profiles), read 2026-11-19). The agent environment (D5's amendment of 2026-10-27) gains the same switch.

- **The setting.** `githubCliEnabled` on REST `GET`/`PATCH /v1/agent-environment`, GraphQL `agentEnvironment`/`updateAgentEnvironment` and MCP `get_agent_environment`/`update_agent_environment`, `bex agent env set --github-cli on|off` and the GitHub CLI switch in Settings → Agents. It is `true` by default, including for a workspace that never saved an environment, because Devin's machine carries the token unless a profile removes it. It is stored as the opt-out, `agent_environments.github_cli_disabled boolean NOT NULL DEFAULT false` (migration 0314), so a row's zero value, which is how bex-api reads a workspace with no row, keeps `gh` on. Writes are admin-only and audited like the environment's other fields.
- **Scope.** The whole workspace: every repo session, automation run and child session in it, which is Devin's organization default. Devin's narrower bindings (the automations default, one automation, one session) are a stricter variant, filed as [w10/035](../.pm/w10/035.md).
- **Two enforcement points.** First, bex-api's two `gh` credential verbs read the workspace's row on every call, after the Pod, lifecycle and branch checks, and refuse with a named refusal (`X-Bex-Agent-Credential-Refusal: github-cli-off`, still a plain `403` to an older gateway) before any GitHub token is minted. The denial is audited under the verb's own audit verb. The gateway's `github-api` route answers each such call `403` in GitHub's error shape with the message below, and counts it as `bex_ssh_gateway_authentications_total{result="github_cli_off"}`. A call the route refuses on its own (a write it never admits, another repository) keeps its own message, since it is refused whatever the setting. Second, at dispatch bex-api sets `BEX_AGENT_GITHUB_CLI=0` on a repo session's driver, which then configures no `gh`: no socket, no gh config (it removes one an earlier turn left on a kept disk) and no `GH_*` variables. The overlay says `gh` is off and that pull requests stay with the `bex` tools. An absent variable means on, so an older bex-api never turns `gh` off by omission.
- **When a change applies.** Off: a running session's next `gh` call is refused, because the mint reads the row on every call with no cache, and turns dispatched afterwards have no `gh`. That is sooner than Devin, where "a running session keeps the restrictions it resolved at its last wake", which is the safe direction for turning access off. On: the route serves the next call of a session whose turn has `gh` configured, and a session whose current turn was dispatched while `gh` was off gets it from its next turn, as a Devin session gets a change "the next time they resume".
- **What stays.** Git (the Git mint never reads the setting), pushes to the session branch, `open_or_update_draft_pr`, `reply_on_pull_request`, `mark_pull_request_ready` and `merge_pull_request` (w10/m538), and PR feedback.
- **The refusal** that `gh` prints after `HTTP 403:` reads "bex: gh is turned off for this workspace's agent sessions (the agent environment's GitHub CLI setting, githubCliEnabled). A workspace admin turns it back on in Settings → Agents or with `bex agent env set --github-cli on`. Pushes to your session branch and the bex MCP tools open_or_update_draft_pr, reply_on_pull_request, mark_pull_request_ready and merge_pull_request still work."

#### The session marks its pull request ready and merges it (amendment w10/m538, 2026-11-20)

Devin merges its own pull requests when asked, under the repository's branch protection ([GitHub integration](https://docs.devin.ai/integrations/gh), [SDLC integration](https://docs.devin.ai/essential-guidelines/sdlc-integration), read 2026-11-20), so a repo session's `bex` MCP server now also lists `mark_pull_request_ready` and `merge_pull_request`. Each calls a gateway verb on the same Pod-bound proxy URL (`<proxy URL>/pull-request/ready` and `…/pull-request/merge`) that forwards over the signed hop to bex-api, which acts on the session's recorded pull request only, pins the merge to the recorded head and mints a one-repository token per call (Pull requests and Contents write, plus Workflows write for a merge, falling back without it as the push token does). The token never enters the sandbox, so this section's invariant holds. `gh pr ready` and `gh pr merge` stay refused in the `github-api` route, whose write token holds no `contents` write, and the refusal names the tools. Branch protection decides, an `APPROVE` review stays refused everywhere, and a merge records `prState: merged` at once. [ADR090 D3](ADR090-agent-owned-delivery.md#d3--the-pull-request-verb) has the contract: the merge call, the method rule, the refusal codes, the takeover rule and the overlay's "only when asked".

#### `gh` in the session's terminals (amendment w10/027, 2026-11-20)

Devin's `gh` token is on the machine for every shell ([Security profiles](https://docs.devin.ai/product-guides/security-profiles): the machine "can carry a GitHub CLI (`gh`) token", read 2026-11-20), so `gh` works in a session's web Shell, `ssh` session and Zed as it does for the agent. The driver writes the agent's `GH_*` settings as shell exports to `gh/env.sh` beside its status file once the `gh` socket serves, and the image's `/etc/profile.d/bex-agent-tools.sh` sources it: the web Shell's and SSH's `/bin/sh` (dash) through `ENV`, `ssh … '<command>'` and Zed's `/bin/sh -lc` through `/etc/profile`, and bash as before. A repo-less session, and a turn dispatched with `gh` off, have no such file, so their terminals have no `GH_*`. A terminal's calls take the same socket, route, budget and audit as the agent's. It runs as the agent's uid and could reach the socket already, so the file adds no access, and the token still never enters the sandbox.

The image also bakes `uv`/`uvx` and `gitleaks` and, beside Debian's 3.11, every Python line a session can select (w4/m544, below; Python 3.12 alone before), each pinned and checked at build (`lego/agent-image/README.md`), so sessions with no repository environment can run Python, `uv` and secret-scan checks. Since w10/024 (2026-11-19) it also has what Devin's base image preinstalls ([Template library](https://docs.devin.ai/onboard-devin/environment/templates), read 2026-11-19): JDK 17 (Temurin), Rust and Cargo through rustup, the AWS CLI, nvm and direnv, pinned and checked the same way. uid 10001 owns the Rust and nvm homes, so a session installs the toolchain a `rust-toolchain.toml` or the Node an `.nvmrc` names, and the D5 registry catalog admits what they fetch. Every bash gets nvm, through `BASH_ENV` where no startup file is read, and interactive shells get the direnv hook, as Devin's shell does.

The OpenSandbox tenant API key is platform-side and is never injected into an agent sandbox. `/usr/local/bin/bex-pre-snapshot` still removes its enumerated emergency location along with Git credential files/cache state before a rootfs snapshot and fails closed if any location survives. _Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): `bex-pre-snapshot`, `POST /snapshot/scrub` and the snapshot grant are deleted; the snapshot holds no live secret._ Resume needs no restored secret: the next Git operation invokes the helper and re-mints.

#### A session runs the Python its repository asks for (amendment w4/m544, 2026-11-20)

Before, every session's `python3` was Debian's 3.11 and Python 3.12 the one other line baked, whatever the repository asked for, so an agent ran, tested and debugged on a line its deploy would not use. Now a session picks its Python the way a Render native build does, from the same table:

- **Selection follows Render's rules** ([python-version](https://render.com/docs/python-version), read 2026-11-20): `PYTHON_VERSION` (a workspace- or repo-scoped secret, since agent environments carry no plain variables), else the first line of the repository's root `.python-version` (a line gets its reviewed patch), else Render's dated default for when the session was created (3.14.10 since 2026-11-03). bex-api passes that time as `BEX_AGENT_SESSION_CREATED_AT` (RFC 3339), and a snapshot build's creation time to a build; with none the legacy 3.13 line applies, as for a native build of unknown age. The table and the resolution are `lego/types/toolchains`, which the native build reads too ([ADR060 D7 addendum](ADR060-build-worker-reliability-and-performance.md#d7-addendum--native-runtime-version-lines-w8m51-2026-10-05)), so the two cannot disagree. `PYTHON_VERSION=3.11` (a line, not a patch) runs the line's patch, as a native build does; Render requires a patch there (ADR018).
- **When:** the driver asks `agent-toolchain python <checkout>` (`lego/backend/cmd/agent-toolchain`, baked at `/usr/local/bin/agent-toolchain`) after the checkout and before any setup step: in a session, in a snapshot build, and again in a session booted from a snapshot, whose branch can differ from the one built. The session's first turn shows the choice as its first step, `setup: Python` with `==> Using Python 3.13.18 (from .python-version)` (`(default)` for Render's default), in the transcript every surface reads; a build records it as its first step, `Python`. The overlay names the version and its source. A `PYTHON_VERSION` secret's value would show redacted (ADR098 D6), so the step names the source, not the value.
- **What runs:** the image bakes the reviewed patch of each bookworm line, 3.8 to 3.15, copied from the digests a native build of the line runs on: the official builds, with GNU readline (`readline.backend == "readline"`), which python-build-standalone's libedit is not. The driver points `python`, `python3`, `pip`, `pip3` and the line's `python3.X`/`pip3.X` in `/opt/bex-python/bin` at the choice. That directory is first on the image's `PATH` and on the `PATH` `/etc/profile.d/bex-agent-tools.sh` restores for login shells, so the agent's commands, setup steps, the web Shell, SSH and Zed all run it. The other lines keep their versioned names, and `/usr/bin/python3` stays Debian's 3.11.
- **An exact patch the image lacks** (`PYTHON_VERSION=3.11.9` against the baked 3.11.18) is fetched as a native build swaps in an exact version's image (ADR060 w8/175): the official `python:3.11.9-bookworm` image's top layers, from the one carrying the interpreter on, each checked against its digest, through the D5 registry catalog (Docker Hub) and the session's proxy, into `/opt/bex-python/3.11.9`. When that fails, the session runs the line's reviewed patch and the step says so and why: `==> Could not fetch python:3.11.9-bookworm (<reason>); using the reviewed Python 3.11 build, 3.11.18`.
- **A request no session runs fails setup** `AGENT_SESSION_SETUP_FAILED`, naming it (`PYTHON_VERSION=2.7.18 is not a supported Python version; supported Python lines are …`), never silently picking another line. 3.7 is refused that way too: its official build is bullseye's and needs OpenSSL 1.1, which bookworm lacks, so the image does not bake it (a native build still runs it on its own bullseye image).
- **uv decides for itself.** bex sets no `UV_PYTHON*` variable: uv's default `python-preference = "managed"` finds the selected `python3.X` on `PATH` before downloading, and a repository whose uv configuration says `only-managed` still gets uv's own python-build-standalone download, as in its CI.

Devin, the reference for agent surfaces, does no automatic selection: a blueprint's `initialize` step runs `actions/setup-python` with the version the repository wants, and the `PATH` it sets reaches later steps and the session's shells. bex makes the choice itself, by Render's rules, but in the same place: a visible step before the setup steps, whose `PATH` reaches every setup step and terminal.

### D3 — ACP is the agent interface; a sandbox-internal AI SDK driver fronts it

- The agent runs as an **ACP server over stdio** inside the sandbox (the SHOULD-support transport every candidate binary already speaks). It is spawned and owned by a small Node **session driver** using the official ACP SDK directly; plans, tool calls, diffs, terminals, and messages are mapped into the durable AI SDK UI-message stream without a lossy language-model wrapper. The image pins and build-verifies every public profile executable — `claude-agent-acp`, `codex-acp`, and `gemini --acp` — and the driver starts each in its own process group so cancel/timeout kills adapter descendants as well. The reviewed profile also owns provider bootstrap: Codex is bound through ACP `providers/set` to the exact session model proxy before `session/new`, and its typed session-failure extension converts a terminal provider/transport record into a failed turn even though the adapter wraps that record in `stopReason=end_turn`. The boundary remains **stdio-spawn only** (no remote transport), which is precisely why the driver lives inside the sandbox rather than on any server. Agent pluggability (D7) collapses to a reviewed `command`/`args`/bootstrap-env profile.
- The driver exposes two local listeners, and the sandbox's NetworkPolicy admits ingress **only from the gateway**:
  1. **AI SDK UI-message stream (SSE)** — consumed by the dashboard's `useChat`/AI Elements. The driver maps ACP session updates directly into typed AI SDK parts (including **`data-acp-*`** plans, diffs, and terminals) before publishing them through one sanitized stream (`lego/agent-image/driver/src/session.ts`), and the browser renders those parts with session UI components.
  2. **No raw ACP launcher.** Native clients use the authorized conversation transport; same-Pod code cannot directly spawn the model-key-bearing adapter.
- bex-api exposes `POST /v1/agent-sessions` (+ GraphQL/MCP twins): authorize `can_operate` via OpenFGA, create/resume the sandbox, mint an **HMAC session ticket** on the web-shell pattern (`BEX_SHELL_TICKET_SECRET` design: DB-backed single-use nonce for long-lived streams, short expiry, claims bind subject + sandbox pod + workspace), and hand the client the gateway origin. Shipped in w3/m39: the durable `agent_sessions` row, first-class `agent_session → workspace` OpenFGA tuple, create/resume/list/get/cancel adapters, reserved sandbox metadata, and ticket mint. `BEX_AGENT_SESSION_GATEWAY_URL` supplies the returned origin; the phase-2 gateway consumes the ticket and claims its nonce through the existing shared `shell_ticket_nonces` store.
- The **isolated ssh-gateway** grows a third listener that verifies the ticket, claims the nonce, and **proxies both streams** to the driver — the same reverse-proxy shape as the existing sandbox-exec SSE path, replacing the previously planned bespoke WebSocket⇄JSON-RPC bridge for the dashboard. bex-api never touches the sandbox network path, and the gateway remains the sole session ingress and sole holder of `pods/exec` (lifecycle/debug) — unchanged trust design (ADR035).
- The gateway **tees the session stream into a transcript** in the control-plane DB. Reattach and multi-surface attach (dashboard + IDE on one session) replay the transcript, then resume live. Agent-side conversation resume after hibernation maps to the provider's `existingSessionId` → ACP `session/load`, used **only when the agent advertises `loadSession`** (the agent's own on-disk session state survives in the rootfs snapshot); transcript replay is the universal fallback. _Amended 2026-10-25 ([ADR059](ADR059-agent-sandbox-hibernation.md) superseded): there is no hibernation or rootfs snapshot any more. An idle session's sandbox is terminated after `BEX_AGENT_SANDBOX_IDLE_TTL` (2h), and the next message runs in a fresh sandbox with no on-disk agent state, so it is primed from the durable transcript (the continuity ladder's rung 2 below)._ Reconnection and multi-client-attach semantics are bex-defined (the spec leaves them open).
- Accepted trade-offs of the driver: the browser-facing wire protocol is the AI SDK UI-message stream, not ACP itself; the provider reports **zero token usage** (ACP does not carry it), so token metering cannot come from this path; ACP permission requests surface no client callback — the agent runs auto-approve inside the sandbox; and the provider is young (v0.2.x, AI SDK v6, dynamic `acpTools()` marked experimental), so it remains exactly pinned and vendor-tested. Live `POST /turn` requires a gateway-signed Ed25519 grant bound to session + action + expiry + single-use nonce. Only the public verification key enters the sandbox.

**The UI-message stream is the end-to-end session API (verbatim-forward guarantee).** The reason `acp-ai-provider` + the AI SDK sit inside the sandbox at all is so that the tenant-facing streaming API of an agent session **is** the standard [AI SDK UI-message stream](https://ai-sdk.dev/docs/ai-sdk-ui/stream-protocol) (`v1`) — the format the frontend Vercel AI SDK (`useChat`) consumes natively, with zero client-side adaptation. This is already true at the source: the shipped driver emits `streamText → toUIMessageStream()` plus the `data-acp` mapping, and serves it in-sandbox at `GET /stream` with `content-type: text/event-stream` **and the protocol marker `x-vercel-ai-ui-message-stream: v1`** (`lego/agent-image/driver/src/server.mjs`). The following invariants bind every hop between that endpoint and the browser (i.e. the gateway attach listener, `w3/m43`):

1. **Byte-transparent forwarding.** The gateway reverse-proxies the stream verbatim — it MUST NOT re-encode, filter, reorder, translate, or inject stream parts, and MUST preserve the `x-vercel-ai-ui-message-stream: v1` header end to end (exposing it cross-origin via `Access-Control-Expose-Headers`, with the dashboard origin CORS-allowlisted). "No protocol bridging" is a contract, not a convenience: any transformation would silently fork the wire format away from what `useChat` validates.
2. **Transport-level additions only.** The gateway may add exactly three things, none of which alter stream bytes: (a) **authentication** — the D3 HMAC ticket (90s TTL, DB-backed single-use nonce, claims binding subject + session + exact sandbox pod + workspace namespace), carried in a header, never the URL (web-shell precedent); (b) the **transcript tee** — a read-only copy into the control-plane store; (c) **replay-then-live splicing** — on (re)attach, previously teed parts are replayed first and the live tail spliced after, so the client sees one continuous `v1` stream (`useChat`'s `messages`-seed + `resumeStream` consume this directly).
3. **Single safe path.** The sandbox NetworkPolicy admits ingress only from the gateway; the gateway is the sole session ingress and bex-api never joins the stream path (unchanged ADR035 trust design). TLS terminates at the platform edge onto the gateway exactly as for the web shell. Reattach after ticket expiry mints a fresh ticket via the attach verb (gap #8).
4. **Version lockstep.** The driver is pinned to the AI SDK **v6** line by `acp-ai-provider` (`0.2.9` + `ai@6.0.237` today); the dashboard pins the v6-paired client (`@ai-sdk/react@3.x`). The two ends upgrade together — never independently — because later majors add part types older clients don't know, and the `v1` marker alone does not guarantee part-level compatibility across majors.
5. **Additive source timestamps (w4/m87).** Each newly emitted UI-message chunk carries an optional top-level `at` (ISO-8601 UTC, `Date.toISOString()` shape, e.g. `2026-08-19T23:06:00.000Z`) assigned **once** at the driver publication boundary (`lego/agent-image/driver/src/acp-map.ts` + `session.ts` `publish`). The same instant is mirrored at `providerMetadata.bex.at` so AI SDK assembly of text/reasoning/tool parts retains it; a closed text/reasoning block also carries `endAt`. The gateway, durable transcript store (`text`, not jsonb), live attach, and replay forward the field byte-transparently — no database column and no gateway rewrite. Consumers that do not understand `at` ignore it; legacy and mixed transcripts without a valid `at` keep the duration-less `Worked`/`Thought` fallback rather than inventing time.

Net effect: any AI SDK client — the bex dashboard's `useChat`, or a tenant's own AI SDK app pointed at the attach endpoint with a valid ticket — can consume an agent session as a standard streaming chat API.

#### D3 recovery amendment — one cleanup verdict and bounded terminal convergence (w5/m72, 2026-08-17)

The production incident for `ags-da1prbt040bc73aj5230` exposed four independent seams that could combine into one permanently live-looking session: the deployed gateway role missed the new `agent_session_turns` grant; a legitimate 1.57 GiB repository exceeded the driver's aggregate 1 GiB scan counter; the catch path repeated that same failing scrub and exited the driver; and OpenSandbox left a Failed child Pod represented by a Pending BatchSandbox. The lifecycle contract is amended as follows:

- **The release owns installed grants.** After bex-api migrations, `deploy.yml` applies the release's exact `dbrole.sql` grant surface without rotating the gateway credential, then rolls the gateway. Gateway startup checks every required schema/table privilege before opening listeners. A migration/grant mismatch is therefore a rollout failure, not a user's first broken replay.
- _Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): the driver credential scrub and Git-object scan below are deleted; the next two bullets are history._
- **Persisted cleanup is bounded by work, not repository size.** Writable roots are deduplicated by inode and scanned with file/entry-count, recursion-depth, deadline, abort, fixed-chunk memory, and an optional explicit byte budget. Large ordinary files are streamed. A `.git` directory's metadata is scrubbed as ordinary writable state, while `git cat-file --batch-all-objects --unordered --batch` streams every reachable and unreachable object in decompressed form. A credential in an immutable Git object or oversized file fails delivery closed; unrelated aggregate bytes do not.
- **One turn owns one cleanup verdict.** The ACP child is stopped idempotently before scrub/delivery. A failed scrub is attempted once, recorded as the readable terminal reason, prevents push/delivery, and forgets the in-memory credential in `finally`; the top-level process does not invoke the same failing cleanup again. The minimal status/stream server remains available until control-plane acknowledgement when the process can remain alive.
- **Terminal state has two independent signals.** The carried OpenSandbox controller patch projects Failed/Succeeded/non-zero-terminated Pods into `BatchSandbox.status.phase=Failed`, a `PodFailed` condition, bounded exit/signal detail, and `taskFailed`. Independently, the gateway checks the exact Pod/container before attach and classifies a failed exec against fresh Pod state, then emits the stable internal `sandbox_terminated` code; bex-api maps it to terminal-not-found. The Completer writes the active→terminal transition with a database compare-and-set, immediately reclaims a known-dead sandbox, and caps a continuous ambiguous status-read failure at two minutes. Metrics use only the bounded `outcome`/`reason` labels—never tenant, session, sandbox, repo, or raw error text.

All product adapters continue to read the same durable session row and turn/transcript tables. REST, GraphQL, and MCP therefore expose the same terminal `phase`/`failureReason`/turn completeness, while gateway replay and the dashboard can still render retained user turns and assistant parts after the Pod disappears.

#### D3 continuity amendment — agent context across sandbox generations (w5/m84, 2026-08-30)

Production session `ags-da9mh5vj596c73en5eq0` exposed that this section's continuity promise was never implemented: after a post-hibernation resume, the dashboard replayed the full durable history while the fresh agent process received only the literal steer prompt ("try again") and answered that it had no idea what to retry. Today's "transcript replay is the universal fallback" reaches only the **client**; nothing ever reaches the **agent**. The gap is worst for sessions whose every prior turn died during setup (e.g. the m82/m83 clone failures): they hibernate with an empty snapshot, so even a perfect state-restore design would have nothing to restore, yet resume still delivers a cold prompt.

The contract is now explicit — every fresh agent process spawned for a session that has prior durable turns MUST be primed by exactly one rung of this ladder, tried in order:

1. **Agent-native resume** — ACP `session/load` from the agent's own on-disk session state, used when the adapter advertises `loadSession` **and** the state is present. _Amended 2026-10-25: the ADR059 D3 snapshot that used to restore this state is retired, so the state exists only when the driver restarts inside the same, still-live sandbox. A follow-up after the 2h idle close lands in a fresh sandbox with no state and takes rung 2._
2. **Transcript re-priming** — the driver injects a bounded context preamble derived from the durable transcript (turn prompts + assistant text; tool noise elided; newest-first truncation under an explicit byte budget) ahead of the new user prompt. The preamble is marked so the stream/tee does not re-render it as fresh conversation.
3. **Task re-delivery** — when **no prior turn ever reached the agent** (setup-phase failures), the resume/steer prompt is prefixed with `agent_config.task`: a bare "try again" means "retry the task," never an open question to a blank agent.

The applied rung is surfaced on the turn (a `data-` part / turn annotation) so the dashboard can indicate restored-vs-fresh agent context instead of implying fidelity that was not there. Implementation tracked as `w5/m84`; ADR059 D3/D4 and ADR051 carry the matching snapshot-scope and transcript-purpose amendments. Since 2026-10-25 (w10/m15) every follow-up on a closed session is a fresh dispatch on the same branch, so this ladder — in practice rung 2 or 3 — is the only continuity mechanism; there is no snapshot restore.

### D4 — Delivery: draft PR + evidence

_Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): the agent commits, pushes its branch and opens or updates its draft PR through the gateway `pull-request` verb and the `bex` stdio MCP tool. The platform pins the branch and PR head, appends the footer and records the PR immediately; the driver only checks Git state and nudges the agent once; the Completer finalizes from the recorded PR. The evidence field and column are deleted. The passages below are kept as history._

A session ends (or checkpoints) by pushing its `bex-agent/*` branch with the session token and opening a **draft PR** via the GitHub App from bex-api. The session record attaches Codex-style verifiable evidence — command log, test output tails — sourced from the transcript. Steering channels: new ACP prompt turns on an attached session (phase 2), and a PR-comment loop (webhook → resume session) as a follow-on.

**Revised by w5/m65 (2026-08-09) — the evidence digest is retired as a presentation surface.** Delivery is unchanged: the driver pushes the `bex-agent/*` branch and the Completer opens a draft PR on every pushed successful turn. What changed is the PR body — now session metadata only (session id, branch, head, API link) — and that neither the dashboard nor the mobile app renders the evidence at all. The digest was a phase-1 artifact from when a completed session had no conversation record; [ADR051](ADR051-agent-session-transcript.md)'s durable transcript now carries the real narrative, making the digest a lossy duplicate — and a misleading one, since the driver's extractor classifies any tool output as "test output" (a `grep` reporting "No matches found" rendered under a Test-output heading). The `evidence` **wire field is retained** on REST/GraphQL for API consumers and is still populated; only its renderers were removed. _Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): the wire field and its column are removed._

**Shipped completion mechanism (w3/m41).** _Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): the driver no longer stages, commits or pushes, and the Completer no longer opens the PR._ Delivery is deterministic and enforced outside the agent (the Copilot model): after the headless turn, the **sandbox driver** stages the working tree, commits, pushes the `bex-agent/*` branch through the m38 credential helper, and writes the head SHA + a bounded evidence extract into its machine-readable status file. A **bex-api background Completer** polls each running session's status file through the existing gateway sandbox-exec boundary (a trusted system seam — no per-tick tenant authorization, since it acts only on durable sessions the platform owns; bex-api still never holds `pods/exec`), and on a pushed successful turn opens (or idempotently reuses) the **draft PR** via the GitHub App, records `headSha`/`prUrl`/`prNumber`/`evidence` on the session, and tears the sandbox down. A failed turn, a lost sandbox, or a failed PR-open becomes a `failed` session with a named reason — never a hang. **Phase-1 steering** (D8) re-dispatches a fresh sandbox on the same branch with the new prompt (a new prompt cannot ride the original sandbox until live attach exists); the Completer then updates the same draft PR, and `turns` + `deliveryMode` record the multi-turn history. Live E2E is proven by `scripts/agent-session-verify.sh`.

**Idempotent Git publication amendment (2026-08-18).** _Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): the driver push state machine is deleted with driver-owned delivery._ The `ags-da2daqui706c739sqvtg` production failure exposed that a Git process exit code is not the publication verdict: an already-current session ref or a lost successful HTTP response can make the final `git push` report an RPC error/`Everything up-to-date` even though the exact candidate is already published. After scanning the immutable candidate, the driver now reads the remote session ref immediately before push and applies this state machine: remote equals candidate ⇒ idempotent success; remote equals the setup baseline ⇒ push the exact candidate with the captured force-with-lease; remote equals anything else ⇒ fail as a concurrent update. If the push command itself errors, one fresh remote read may convert it to success **only** when the ref equals the exact scanned candidate; the final equality check remains mandatory. A newly accepted or successfully dispatched retry clears the previous turn's `failureReason`, so an active/successful retry cannot continue displaying the stale terminal error. Tests cover exact-candidate replay, conflicting remote updates, and legal shallow receive-pack metadata.

### D5 — Egress: default-deny with per-session opt-in

The `<ws>-sandbox` default-deny NetworkPolicy stays. Baseline allowlist for the agent phase: GitHub (clone/push via the helper) and the model API endpoint only (ADR090 adds the PR verb on the same gateway `:8082` hop; no new egress); setup phase may open package registries (_amended 2026-10-27: the registries stay open through the agent phase, and the posture is a per-workspace tier — see the amendment below_). Tenants may widen per session with an explicit allowlist (Codex pattern). When a metering LLM proxy exists (D6 phase 2), the model-API allowlist narrows to the proxy — one mechanism then provides token metering **and** the exfiltration choke point.

Wave-1 implementation (w3/m40): `internal/sessionegress` creates one namespaced `CiliumNetworkPolicy` keyed by the immutable `bex.co/agent-session` Pod identity before OpenSandbox creates the Pod. Setup admits the fixed package registry catalog (`BEX_AGENT_SETUP_REGISTRIES` can replace the defaults), GitHub, the HTTPS model endpoint derived from that session's selected agent/provider config, the identity-authenticated gateway credential hop, and validated exact tenant hostnames. The one-way transition updates that same policy to remove package registries; the allowlist hash must remain unchanged (_amended 2026-10-27: the transition keeps the registries and only pins the hash_). The clusterwide `sandbox-egress-default-deny` contains only structural node, API, metadata, and private/rebinding denies, while its former positive rules moved to a legacy policy that explicitly excludes agent-session Pods. Thus policy creation, transition, and deletion never remove the underlying deny. API-server admission confines bex-api's dynamic Cilium authority to canonical `<ws>-sandbox` namespaces and rejects CIDR/entity, wildcard, broad-selector, and non-TLS public rules. Tenant entries are exact public DNS names only; invalid, duplicate, private, wildcard, URL-shaped, or excessive entries return the named `AGENT_SESSION_EGRESS_ALLOWLIST_INVALID` 400.

**Amendment (2026-10-27, w10/m17) — workspace network tiers; package registries stay open through the agent phase.** User direction 2026-10-27: an agent that cannot install dependencies cannot build or test the change it delivers. The `/rt-simplify-logic` session `ags-dbf8nggkbcjs73a5r3u0` could not run `go build`, `go test`, `make lint` or `yarn test`, so its PRs shipped verified only by inspection. The sandbox network posture is now configured once per workspace (the "agent environment": REST `GET/PATCH /v1/agent-environment`, GraphQL `agentEnvironment`/`updateAgentEnvironment`, MCP `get_agent_environment`/`update_agent_environment`; admin-only writes) instead of per session:

- **`registries`** (the default, including for every workspace that never saved an environment): GitHub (`github.com`, `api.github.com`, `codeload.github.com`, `uploads.github.com`, `raw.`/`objects.githubusercontent.com` and, since 2026-11-19 (w10/m513), `release-assets.githubusercontent.com`, where GitHub redirects every release download, so a repository environment's setup step can install a tool or runtime version the image lacks, as a Devin blueprint's `initialize` does), the gateway hops and the built-in package-registry catalog (npm/Yarn, PyPI, Go proxy + sumdb, Maven Central, crates.io, RubyGems, Docker Hub; `BEX_AGENT_SETUP_REGISTRIES` replaces it) **for the whole session**. Since w10/024 (2026-11-19) the catalog also holds what the image's toolchains fetch to build a repository with no setup, as on Devin's base image: `index.crates.io` (cargo's default sparse index, without which the crates.io entries served no current cargo), `static.rust-lang.org` (the toolchain a `rust-toolchain.toml` names), `nodejs.org` (`nvm install` for an `.nvmrc`), and the Gradle wrapper's `services.gradle.org` (which redirects to GitHub release assets) with the plugin portal's `plugins.gradle.org` and `plugins-artifacts.gradle.org`. They serve public downloads only, like the registries. The setup→agent transition no longer removes the registries; it still requires the tenant widening to equal the one setup was prepared with.
- **`custom`**: `registries` plus up to 32 workspace hostnames, validated with the per-session allowlist rules (`AGENT_ENVIRONMENT_HOSTS_INVALID`) and refused if already in the baseline.
- **`full`**: opt-in any-host access over HTTP(S) through the gateway egress proxy (_amended 2026-10-28, w10/m19: originally stored but enforced as `registries`, because the admission policy admits only exact FQDN rules and Cilium deny rules cannot carve the model providers out of a world allow; see the amendment below_).

The explicit per-session `egressAllowlist` still works on every surface. It merges with the tier's hosts, and the merged widening keeps the 32-destination cap. Every dispatch (create, steer, and the next message after the idle close) re-resolves the environment, so a change applies from a session's next turn. A new sandbox generation therefore re-prepares the session policy in the setup phase. That is no longer a widening, because setup and agent admit the same destinations. In every tier the model-provider APIs (`api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com`, `openrouter.ai`) stay reachable only through the gateway model proxy (in `full`, the egress proxy refuses them by name and TLS SNI; see the 2026-10-28 amendment for the accepted limits).

**Trade-off, accepted.** Keeping registries open through the agent phase widens the exfiltration paths beyond setup: an agent steered by hostile repo content could publish a package to a public registry. The user accepts it because the sandbox holds no reusable secret worth exfiltrating. The model key is a session-bound placeholder that only the gateway swaps (ADR062), and Git push is pinned to the session's `bex-agent/*` branch by the gateway proxy. It also matches every compared product's default: Devin, Codex cloud (the "common dependencies" preset), Claude Code on the web ("limited", package registries) and GitHub Copilot's coding agent (a firewall that allows the common registries). Wider access (`full`) stays opt-in per workspace.

**Amendment (2026-10-28, w10/m19) — the `full` tier is enforced through a gateway egress proxy.** A world or CIDR rule cannot express "any host except the model providers", so `full` does not widen the Cilium policy at all; it narrows it. A full-tier session's `CiliumNetworkPolicy` carries the annotation `bex.co/egress-posture: full`, **no** public FQDN rule, DNS filtered to the gateway host only, and exactly three gateway hops: Git `8082`, model `8084` and the egress proxy `8085`. A direct connection to any public address is dropped by the sandbox default-deny. The `bex-api-session-egress` admission policy admits this shape only with the marker (0 FQDN rules, 4 endpoint rules including `8085`); every other policy keeps the allowlist shape and can never open `8085`. The posture is part of the session's immutable identity hash, so a setup→agent transition cannot switch postures. `registries` and `custom` are unchanged.

The egress proxy is a fourth gateway listener (`BEX_AGENT_EGRESS_PROXY_ADDR`, default `:8085`, cluster-internal, no edge route). bex-api sets `HTTPS_PROXY`/`HTTP_PROXY` (both spellings) on full-tier sandboxes to `http://<ns>:<session>@bex-ssh-gateway…:8085`. The userinfo is the base64url session claim, not a credential. `NO_PROXY` names the gateway and loopback, so Git and model traffic keep their dedicated proxies. The driver passes this env to the agent and its tools (Claude Code, curl, npm, pip, Go and git all honour it). `BEX_AGENT_NETWORK_TIER` adds one overlay line telling the agent that HTTP(S) goes through a proxy and that raw TCP and SSH are unavailable. For each request the proxy:

1. **Binds the source Pod** exactly like the Git and model proxies: `KubeSessionPodResolver` on the TCP source IP, then `AuthorizeSessionPod` on the immutable session labels against the claimed namespace and session.
2. **Requires the `full` tier** through a new HMAC verb on bex-api's internal listener, `POST /v1/agent-session-egress-grants`. It applies the same live-lifecycle and current-sandbox check as the mints and reads the workspace's current tier. Allowed grants are cached per Pod for 30s and refusals for 5s, so switching a workspace off `full` stops its live sandboxes within 30s. An unreachable bex-api fails closed.
3. **Accepts only ports 443 and 80** (`BEX_AGENT_EGRESS_PORTS`). CONNECT tunnels must open with a TLS ClientHello. Plain HTTP must use absolute form and is forwarded with the URL's own authority as the Host.
4. **Refuses the model providers** (`api.anthropic.com`, `api.openai.com`, `generativelanguage.googleapis.com`, `openrouter.ai`, from the same `sessionegress` list), so model traffic keeps going through the bex model proxy:
   - by CONNECT or URL host, including subdomains;
   - by TLS SNI: an SNI naming a provider, or differing from the CONNECT host, closes the tunnel. This also blocks a raw-IP CONNECT carrying a provider SNI, and CDN domain fronting.
   - **Not** by resolved IP. Providers such as `openrouter.ai` sit on shared CDN anycast addresses, so an IP denylist would block unrelated sites. The platform key never enters the sandbox, so a direct provider connection could only ever carry a tenant's own key.
5. **Refuses private destinations (SSRF guard).** It rejects private, loopback, link-local (including the metadata service), CGNAT, documentation/benchmark, multicast, ULA, NAT64, 6to4 and Teredo ranges, plus `BEX_AGENT_EGRESS_DENY_CIDRS`. It also rejects single-label, `.local`, `.internal`, `.svc` and `.cluster.local` names. It resolves the name once as an absolute name (no cluster search domains), requires **every** answer to pass, and dials the checked IP, so DNS rebinding cannot pick the address.
6. **Bounds usage.** Concurrent tunnels are capped at 256 global and 32 per Pod. Cumulative budgets: 20,000 connections per session, 100,000 per workspace and 20 GiB per session (process-local, reset on restart). Tunnels close after 5m idle and 1h total. Metrics `egress_proxy_connections_total{result}` and `egress_proxy_bytes_total{direction}` carry no hosts. A content-free `agentsessions.EgressUsage` audit event per session per minute records connection and byte counts only, never hosts or URLs. Each grant decision is audited as `agentsessions.GrantEgress`.

The gateway's own egress is not restricted by any network policy (none selects it in `bex-system`), which is what lets it reach world `:443`/`:80`. If one is ever added, it must keep that allowance.

**Amendment (2026-11-20, w10/032) — Java tools reach the proxy.** The JVM reads no `HTTPS_PROXY`, and Maven's HTTP transport takes a proxy only from its settings, so on `full` the JDK 17 every session has (w10/024) could not download a dependency or a Gradle distribution. bex-api also sets `BEX_AGENT_JAVA_PROXY_OPTIONS` on full-tier sandboxes: the same proxy, claim and direct hosts as JVM system properties (`http.proxyHost`, `https.proxyHost` and their `Port`, `User` and `Password`; `http.nonProxyHosts`, the JDK's loopback default plus `NO_PROXY`'s gateway hosts; and an empty `jdk.http.auth.tunneling.disabledSchemes`, without which the JDK refuses Basic on a CONNECT).

- The image puts them in front of `JAVA_TOOL_OPTIONS` in every shell, and the driver does the same for the agent's own process. A repository's own value stays after them, so its own properties win. Gradle, its wrapper and an older Maven wrapper answer the proxy's Basic challenge from these properties.
- `/etc/mavenrc`, which every `mvn` sources, writes Maven global settings naming the proxy and passes them as `-gs` (`-is` on Maven 4), unless the command names its own. A repository's own user settings (`~/.m2/settings.xml`, or `-s` in `.mvn/maven.config`) merge over them. They keep the HTTP blocker of Maven's stock global settings, which they stand in for.
- Maven 3.9's client (Apache HttpClient 4.5) sends a proxy scheme it re-uses from its auth cache as `Authorization`, not `Proxy-Authorization`, once concurrent downloads outnumber its cached schemes. So the proxy also reads the claim from a CONNECT's `Authorization`, still bound to the source Pod. A CONNECT's `Authorization` belongs to no origin; a plain-HTTP request's does, so it is never read.
- A JVM HTTP client that installs no `java.net.Authenticator` still gets 407: the JDK sends proxy credentials only through one.

**Limits, accepted.** Tools that ignore proxy env or speak raw TCP (SSH remotes, database clients, `git://`, UDP) cannot reach the internet. Node's built-in `fetch` ignores proxy env unless `NODE_USE_ENV_PROXY=1`. TLS is not intercepted, so a CDN-hosted provider could still be reached by an encrypted Host header behind a matching SNI. The proxy then sees only an allowed name, but the workspace spends its own key rather than the platform's, which never enters the sandbox. The same model is used by Codex cloud and Claude Code on the web for configurable internet access. Render has no equivalent, so this is not a parity divergence.

The D6 phase-2 proxy is a required narrowing, not an optional alternative: once it exists, the session agent/provider resolver must return only that proxy endpoint and direct vendor model endpoints must disappear from newly rendered policies. The proxy then owns vendor selection and token metering behind the single egress choke point.

### D6 — Billing: two meters, quota + overage — explicitly no per-request meter

Two new ADR023 meter kinds through the existing sealed-outbox → Stripe pipeline, gated by ADR046's `PaymentGate`:

1. `sandbox_compute_seconds` — per-second sandbox lifecycle compute (vCPU/GB-weighted, AgentCore-style; hibernated sessions do not accrue). Needed regardless: sandboxes are currently unmetered.
2. `agent_token_units` — model-token passthrough at per-model rates (AI-credits-style), phase 2, sourced from agent usage reporting or the metering proxy.

Packaging: plan-included agent quota + metered overage (Devin/Cursor pattern) via Stripe metered Subscriptions with included quantities. **Per-request/premium-request billing is rejected** — the exemplar that invented it retired it because autonomous sessions break the unit economics.

**A retained session sandbox's image is absorbed, not billed (w22/005, 2026-11-14).** `/v1/sandboxes` sandboxes pay snapshot storage for the image a suspension retains (ADR104 D11, `sandbox_snapshot_gb_seconds`); an agent-session sandbox does not: `storageRef` in `lego/backend/internal/sandbox/meter.go` returns no ref for a sandbox that carries `bex.co/agent-session`, so no storage object opens for it. The reference product agrees. Devin's billing documentation states that a sleeping session does not consume ACUs and that an awake but idle session sleeps itself after about 0.1 ACU ([docs.devin.ai billing](https://docs.devin.ai/admin/billing)), and a sleeping session can be resumed for 14 days ([release notes](https://docs.devin.ai/release-notes/2026), 2026-10-09). A settled turn's sandbox is terminated after its idle grace (`BEX_AGENT_SANDBOX_IDLE_TTL`), and the per-workspace storage cap (`BEX_SANDBOX_MAX_STORAGE_GB_PER_WORKSPACE`) counts `/v1/sandboxes` storage objects, imports and repository environment builds (ADR104 D11, ADR111 D9). **Corrected by w22/m413 (2026-11-15):** the one agent-session image that is kept, the disk of a turn a person stopped ([D12](#d12--a-message-to-a-running-session-is-queued-stop-turn-ends-only-the-current-turn-w22m403-2026-11-14)), is absorbed under the same rule and is also counted, bounded and deleted. Its bytes are reserved against that cap, under the lock imports and builds take, before the image is copied, and count until the registry has dropped the image and its row is removed (`agent_session_retained_images.size_bytes` in `sandboxStorageBytesSQL`); a workspace at the cap keeps nothing, and the turn records the loss. It is kept for `BEX_AGENT_INTERRUPT_RETENTION` (default 24 hours, never above 7 days, so always below Devin's 14), and is deleted on expiry, cancel, delete, archive, workspace delete and once the next turn is running from it, with a sweep that retries a failed delete.

### D7 — Agent binary: BYO-API-key first, binary pluggable

v1 is **bring-your-own-API-key**: the tenant supplies their model credential (stored in OpenBao per ADR013, injected at session start, scrubbed per D2 — _superseded by [ADR062](ADR062-sandbox-credential-vault.md) and [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): the key stays in the model proxy and nothing is scrubbed_). This sidesteps the unresolved Claude Code resale/ToS question, matches bex's open-source positioning, and reduces v1 billing to the compute leg. The template image treats the agent as pluggable; selection criteria are verified ACP maturity and `loadSession` support (candidates: Claude Code via its ACP adapter, Gemini CLI, OpenHands, opencode). Bundled-token billing and a default bundled agent are revisited once the metering proxy exists and the ToS question is answered.

**Amended 2026-11-19 (w10/m516): the model is chosen per session, per automation and per message, as on Devin.** On a workspace that runs agents on the platform model (ADR090, no model key of its own), the claude profile's model comes from a platform catalog ([ADR090 § Model pin](ADR090-agent-owned-delivery.md#platform-openrouter-route-for-an-allowlisted-workspace-2026-10-23)), not from one workspace-wide pin. The reference is Devin's agent selector: chosen when a session starts, switched mid-session "with your next message", an organization default, and `devin_mode` at create echoed by the session read ([Your First Session](https://docs.devin.ai/get-started/first-run), [Create Session](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions), [Models](https://docs.devin.ai/cli/models), read 2026-11-19).

- **Create and automations.** `agentConfig.model` on a session create (REST, GraphQL, MCP, `bex agent run --model`) and on an automation's template (create, update, `bex agent automations apply`) names any catalog model. Omitted, the workspace default runs, else the catalog's first model. A model outside the catalog is refused at create or save with `400 AGENT_SESSION_MODEL_NOT_OFFERED`, which lists the offered ids. An automation run whose stored model has since left the catalog runs the workspace's model and records that in its run's `error` note instead of failing every fire.
- **A message switches it.** A follow-up message (REST/GraphQL/MCP `model`, `bex agent send --model`, chat `/model`, the dashboard steering composer) may name a catalog model. The turn it starts runs that model, and the session read reports it from then on. A queued message switches the model when it runs. Without a model a message keeps the session's model. This works because every turn starts a fresh sandbox (D8 phase 1), so no in-place model change is needed.
- **Visible.** The capabilities read gives each offered agent `model` (what a session that names none runs) and `models` (what it may name: the catalog, a fixed profile's one model, or empty where the workspace's own provider takes any id). `bex agent models`, the composers, the automation form and Settings → Agents show them. A workspace on its own key keeps a free-form model.
- **Mobile (w10/029, 2026-11-20).** The phone composer shows the chosen agent's model in a pill beside the agent: a catalog agent's pill opens a picker of its `models` with the default marked, and the session starts on the pick (`agentConfig.model`, sent only when it is not the default). A fixed-model agent's pill shows its model without a choice, and an agent with no `models` (the workspace's own key) shows no pill. The admin allow-list is the amendment below.

**Amended 2026-11-20 (w10/m527): a workspace admin chooses which catalog models its members may pick, as Devin's admins do.** Devin's agent picker "lists only the agents available to you" because "Admins control which agents are available", and its "Allowlisted models" team setting hides a model outside the allowlist from every picker; a pinned default "must be in the allowlist to take effect", else the built-in default runs ([Your First Session](https://docs.devin.ai/get-started/first-run), [Devin Desktop admin controls](https://docs.devin.ai/desktop/controls), [Devin CLI Team Settings](https://docs.devin.ai/cli/enterprise/team-settings), read 2026-11-20).

- **The list.** The workspace agent environment carries `enabledModels`: the platform catalog models members may choose, in catalog order with the catalog default first. REST `GET`/`PATCH /v1/agent-environment`, GraphQL `AgentEnvironment.enabledModels` and `AgentEnvironmentInput.enabledModels`, MCP `get_agent_environment`/`update_agent_environment`, `bex agent env` / `bex agent env set --models ID,ID…` and Settings → Agents ("Models members can choose") read and write it. A write replaces the whole list, as `enabledAgents` does. It is admin-only (`can_manage`) and audited like the other environment fields.
- **Storage and default.** It is stored as the opt-out `agent_environments.disabled_models` (migration 0315), so a workspace with no row, every row before the migration and a model added to the catalog later offer the whole catalog. `models` stays the whole catalog, so Settings can list what an admin may turn on.
- **Refusals.** A write that leaves the catalog default off (an empty list does), names a model outside the catalog, or is sent where there is no catalog (the workspace's own key, or no platform route) is `400 AGENT_ENVIRONMENT_MODELS_INVALID` (`field: enabledModels`, `model`, `models`: the catalog), and nothing is written. A create, a message or an automation create or update naming a turned-off model is `400 AGENT_SESSION_MODEL_NOT_OFFERED`, and `defaultModel` naming one is `AGENT_ENVIRONMENT_MODEL_NOT_OFFERED`; both list only the offered models, and their message says an admin turned the model off.
- **Where it applies.** One helper, `offeredModels` (`lego/backend/internal/agentsessions/environment.go`), is the catalog less the turned-off models, with the catalog default always kept. It drives create, the message check, the turn dispatch, automation save and fire, the capabilities read's `models` (and hence `bex agent models` and every dashboard picker) and the `defaultModel` check.
- **A turned-off workspace default.** Turning off the model `defaultModel` names is allowed. The saved default stays and reads back, but it stops taking effect: sessions and automations that name no model run the catalog default, and the capabilities read's `model` says so. `bex agent env` and Settings → Agents mark it. Refusing the write instead would make an admin change the default first, which Devin does not ask.
- **When a change applies.** New creates, messages and automation saves see it at once. A turn in flight keeps its model, because the mint pins the model the session recorded. The session's next dispatch re-resolves it: a stored model that is turned off runs the workspace default, else the catalog default, and the session read reports the model that ran. A queued message naming a model turned off while it waited runs the same fallback. An automation whose template names one runs the workspace default and records "the template's model … is turned off in this workspace; this run used …" on the run.
- **On the workspace's own key** there is no catalog: any model id is free-form, the reads give `enabledModels: []` as they give `models: []`, a write is refused, and Settings hides the list. A stored list is kept and applies again if the workspace clears its key.
- **Scope.** This is Devin's organization-level allowlist. Its group-level lists and its filter by provider are narrower variants, filed by t007 if users would miss them.

### D9 — Dashboard session surface: one render layer, two swappable data sources

The dashboard surface (formerly held note `.pm/w5/035.md`, materialized as `w1/m64`; deep-research pass 2026-08-02) is the Devin-shaped session UI: a sessions list + new-session composer, a session detail page with an activity timeline, a draft-PR/evidence card (_Superseded by [ADR090](ADR090-agent-owned-delivery.md) (2026-10-22): evidence removed; the PR card remains_), and a steering composer. Its architecture is chosen so the phase-1 (fire-and-forget) and phase-2 (live attach) products share **one rendering layer** and differ only in data source:

![Dashboard session surface: the developer opens the /agents routes, which feed one UIMessage render layer (vendored AI Elements) backed by two data sources; the phase-1 Apollo hooks call bex-api over GraphQL with the Kratos session cookie; the phase-2 useChat transport first mints an attach ticket from bex-api over GraphQL, then opens a cross-origin SSE stream with the HMAC ticket to the isolated ssh-gateway, which proxies to the session driver's GET /stream in the workspace's sandbox namespace; bex-api and the gateway (nonce claim, transcript tee/replay) both use control-plane Postgres](assets/ADR047-cloud-coding-agent-sessions-dashboard.svg)

The **conversation column** runs on `useChat` over the target-shape stream endpoint and nothing else: the stream's replay mode is the single history source for terminal and running sessions alike. _(Superseded 2026-08-02, before build: an earlier plan had the dashboard synthesize a `UIMessage[]` timeline from polled data plus localStorage-persisted prompts as a pre-gateway interim — discarded with the target-API-shape decision so the interim never ships; `w1/m64` builds directly on the `w3/m43` contract, with vendored AI Elements — hook-agnostic, React 19 + Tailwind 4, both already the dashboard's stack — rendering the parts either way.)_
- **Transport.** `useChat` + a transport pointed at the same-origin stream path (`api.bex.co/v1/agent-sessions/{id}/stream` — no CORS, no second origin in dashboard config): ticket rides a header, never a URL; `prepareReconnectToStreamRequest` re-mints via the `attach-ticket` verb per reconnect (the 90s TTL makes per-connect mint mandatory); `dataPartSchemas` validate the driver's `data-acp` parts, rendered as collapsible Reasoning/Task/Tool/Terminal groups (the Devin "Worked/Thought for Xs" shape). Reasoning beside a call joins that call's activity group as a step (2026-11-15), so an agent's think-act rhythm reads as one summary line between two pieces of narration (`Ran 10 commands · Thought 5 times`), as Devin's Activity view folds its rows; only a thought with no call beside it stands alone. Steering routes by state: live session ⇒ chat `POST` (`sendMessage`); idle ⇒ the redispatch verbs. Client disconnect ≠ cancel — Cancel stays an explicit verb. Degraded states are honest per the house 503 pattern: stream endpoint unconfigured/unavailable ⇒ the conversation column says so while the metadata views keep rendering.
- **Version pin.** The in-sandbox driver is held to the AI SDK **v6** line by `@mcpc-tech/acp-ai-provider` (`ai@^6`; no v7 support yet), while `ai@7` is current. The dashboard pins `@ai-sdk/react@3.x` (the v6-paired line) to match the driver's stream, and both sides upgrade together — the UI-message stream protocol (`v1`) is shared, but skew is not tested territory.
- **Backend gaps the frontend exposes** (fold into the phase-2 milestone): a ticket-only **attach verb** for running sessions (today only create/resume/steer mint, so a page reload on a running session cannot reattach); **per-turn history** (`turns` is an integer counter — steering prompts and prior-turn evidence are not stored, so a reloaded phase-1 page loses turn wording); optional +/− diff stats in evidence for the PR card.
- **Exemplar table stakes held to** (verified against Devin/Copilot cloud agent/Codex cloud, 2026-08-02): grouped/collapsible activity rather than a flat log, a diff-first deliverable card with the PR link, a mid-run-capable steering composer (delivered as a queue by [D12](#d12--a-message-to-a-running-session-is-queued-stop-turn-ends-only-the-current-turn-w22m403-2026-11-14); live injection stays unavailable), explicit stop/cancel with preserved-work semantics, and status/duration metadata. Devin's Shell/Browser/Editor workspace tabs are differentiators, not table stakes, and are out of scope.

**Target API shape (decided 2026-08-02) — two planes, one public origin.** The session API converges on a control plane and a conversation plane, split by required authority, not by protocol:

| Plane | Served by | Endpoints |
| --- | --- | --- |
| Control (JSON; REST/GraphQL/MCP parity) | bex-api process | `POST /v1/agent-sessions` (create; fast accept, no ticket — w2/m64) · `GET /v1/agent-sessions[/{id}]` (list/get: phase, PR; evidence removed by ADR090) · `POST /{id}/cancel` · `POST /{id}/resume` (revive idle session; fast accept, no ticket) · `POST /{id}/attach-ticket` (the sole ticket mint — reconnect + first connect once a sandbox exists) |
| Conversation (Vercel AI SDK UI-message contract) | gateway process | `POST /v1/agent-sessions/{id}/stream` (submit a prompt turn on a live session; verbatim-forwarded to the driver) · `GET /v1/agent-sessions/{id}/stream` (reconnect: transcript replay then live tail; **terminal sessions: replay-only then `[DONE]`**) — ticket-authenticated |

- **Public origin.** Both planes publish under the primary API origin (`api.bex.co/...`): the platform edge routes the `/stream` path to the **gateway process** by path rule. External developers see one API product with one origin and no CORS second origin; which process serves which path is an internal implementation detail (the GitHub pattern: log downloads are `api.github.com` API, bytes come from a blob host). Two recorded caveats: this is a deliberate, documented exception to the "everything on the API origin is served by the bex-api process" audit assumption, and the gateway MUST ignore any cookies arriving on that path — the ticket is the only accepted credential. A neutral dedicated origin remains a fallback if edge path-routing proves operationally troublesome.
- **Absorbed into the chat contract**: live steering (the chat `POST` _is_ the prompt turn — the `steer` verb narrows to idle-session redispatch and is slated for deprecation into `resume` + chat `POST` once live attach ships; the MCP `steer_agent_session` tool survives as a one-shot alias for non-streaming clients); transcript reading (the stream endpoint's replay mode serves reattach **and** terminal-session history — an optional JSON transcript read may be added for MCP/REST parity); the dashboard consumes this contract directly — the once-planned client-side prompt-persistence interim was discarded before build and never ships.
- **Explicitly not absorbed**: `create`/`cancel`/`list`/`get`/`resume` stay JSON control verbs. Creation precedes the driver's existence (authz, sandbox provisioning, egress policy, credential wiring happen before there is anything to forward to); client disconnect ≠ cancel (AI SDK semantics — `stop()` only closes the connection); listing and result metadata (phase, PR, billing) are control-plane authority written by the Completer and, since [ADR090](ADR090-agent-owned-delivery.md), by the PR verb; and non-streaming consumers (MCP tools, CLI scripts, CI) need the poll-shaped surface — GitHub's public agent-tasks API is poll-only, validating that shape as a product in itself.
- **Accept fast, provision async (w2/m64, 2026-08-09).** `create`/`steer`/`resume` originally provisioned the sandbox _synchronously_ on the request path (pod schedule + image pull, tens of seconds), so a dashboard submit visibly hung ("每次 chat 都要等半天" — user report). The mutations now do only the cheap, fail-fast work synchronously — authorization, input validation, egress derivation, the BYO model-key read, the durable row, and the OpenFGA parent tuple — return immediately in the `creating`/`redispatching`/`resuming` phase, and run the slow sandbox provisioning in a background goroutine (`context.WithoutCancel` + a hard ceiling). Consequences threaded through all three surfaces identically: (a) the mint verbs **no longer return a ticket** — there is no sandbox to bind claims to yet, so the client mints lazily via `attach-ticket` once a sandbox exists (the dashboard already did this per reconnect); `attach-ticket` on a not-yet-provisioned session returns the named, retryable `AGENT_SESSION_NOT_ATTACHABLE` 409. (b) A provisioning failure surfaces as a `failed` session with a named reason (not a hung request); the dashboard renders it inline with a one-click Retry. (c) A `Cancel` racing an in-flight background dispatch converges without orphaning a sandbox or resurrecting the session — `RecordAgentSessionDispatch` is CAS-guarded (`WHERE phase NOT IN ('canceling','canceled')`) so a dispatch that loses the race tears its just-created sandbox back down, and the failure/resume transitions skip a session a cancel already took terminal. The synchronous conflict guards (`AGENT_SESSION_TURN_IN_FLIGHT`, `AGENT_SESSION_NOT_STEERABLE`) and all input-validation 400s are unchanged.

**Shipped in w3/m43.** The conversation plane is built:

- **Transcript store** (`agent_session_transcripts`, migration 0067): parts stored as **`text`, not `jsonb`** — jsonb canonicalizes (reorders keys, adds whitespace) and would corrupt the verbatim-forward guarantee. `seq` is the driver's emission ordinal (0-based); `PRIMARY KEY (session_id, seq)` + `ON CONFLICT DO NOTHING` makes the tee idempotent across gateway replicas and re-attaches. `ON DELETE CASCADE` with the session; retention prune rides the audit sweep.
- **Gateway attach listener** (`internal/sshgateway/agentattach`, browser-facing `:8083`): verifies the agent-session ticket (reusing `BEX_SHELL_TICKET_SECRET`), single-use-claims its nonce in the shared `shell_ticket_nonces` store, then — on `GET` — replays the durable transcript to the client and splices the live driver stream, teeing new parts; on `POST`, forwards a live prompt turn. The listener resolves the ticket's pod → IP and **dials the in-sandbox driver's stream port directly** (no `pods/exec`; the sandbox NetworkPolicy admits only this one gateway ingress). Byte-transparent: it preserves the `data:` payloads and the `x-vercel-ai-ui-message-stream: v1` header, and ignores cookies. During a live GET/POST it emits a serialized SSE comment heartbeat every 15 seconds; the comment is transport-only (never persisted) and keeps the edge from closing a healthy stream while a tool or credential scrub is silent for minutes, so the eventual `[DONE]` remains observable. A gone pod (terminal session) yields transcript replay + `[DONE]`. **CORS:** although the endpoint lives on the api origin, the dashboard calls it cross-subdomain (`dashboard.bex.co → api.bex.co`), so the handler answers the OPTIONS preflight and echoes the matched Origin + `Access-Control-Expose-Headers: x-vercel-ai-ui-message-stream` (reusing `BEX_API_CORS_ORIGIN`) — without it the browser blocks the stream even though `curl` works. _(This gap was caught by a live prod probe, 2026-08-02, not by the unit tests, and fixed in place.)_
- **Driver live turn** (`POST /turn`, `lego/agent-image/driver`): runs another turn on the persistent session with the UI-message stream kept open, single-flighted (concurrent `POST` → 409), mirroring parts to both the hub (attached `GET` clients) and the `POST` response.
- **Steer decision (recorded):** live steering is the chat `POST` to the stream; the `steer` verb keeps the idle/terminal **redispatch** path and returns a **documented 409** (`AGENT_SESSION_TURN_IN_FLIGHT`) on a running session — no silent absorption. The MCP `steer_agent_session` tool stays a one-shot alias.
- **`attach-ticket` verb** is three-surface (REST `POST /{id}/attach-ticket`, GraphQL `attachAgentSession`, MCP `attach_agent_session`) — the Render-parity twin of the other mint verbs. The **stream endpoint itself is intentionally REST-only**: a raw byte stream is not a GraphQL/MCP shape, so those surfaces expose the ticket (to attach) rather than duplicating the stream.
- **Sandbox ingress:** the gateway→driver dial (bex-system → `<ws>-sandbox` :8787) is granted by the cluster-wide Cilium policy `sandbox-agent-driver-ingress` (deploy/gitops), NOT a per-namespace k8s allow — the ADR045 tenant-namespace admission control confines bex-api to converging default-deny only, so a duplicate k8s policy would be rejected (found live on prod, w3/m43). The k8s layer stays default-deny.
- **Edge routing:** a Traefik `IngressRoute` (`config/ssh/ingressroute-agent-attach.yaml`) path-routes `api.bex.co/v1/agent-sessions/{id}/stream` to the gateway with priority over bex-api's `/` Ingress, reusing the `bex-api-tls` cert.

**w5/m71 persistence amendment (2026-08-17; supersedes the ordinal/live-turn claims above).** An accepted prompt is now a first-class `agent_session_turns` row, inserted before asynchronous dispatch; `turns` counts accepted non-empty user intents, not successful sandbox provisions. The initial task and every Steer therefore survive refresh and provisioning failure. Turn acceptance clears the old durable sandbox binding so an attach cannot mislabel the previous driver's output as the new turn; the prior id travels only in the background teardown input. Legacy migration recovers turn 1 from `agent_config.task` only; previously lost follow-up text is not reconstructed. User intent is capped at 100 KiB per prompt and 8 MiB per session.

Assistant chunks remain text payloads, but their idempotency key is `(session_id, turn, part_index)` because every fresh sandbox restarts its driver ordinal at zero. `seq` is now a store-allocated monotonic session replay cursor, not the driver ordinal. Completion always merges the full current-turn log, so a partial live tee cannot suppress the suffix.

The gateway's durable replay is intentionally a **role adapter**, not wholly byte-transparent: assistant payloads are preserved, while one outer `start`/`finish` and `data-user-prompt` parts derived from durable turns provide the role and turn boundaries the AI SDK response stream does not contain. Completeness/truncation facts accompany each prompt. A raw public live `POST /turn` cannot participate in the transactional turn ledger, so `ActionTurn` ticket mint is disabled with `AGENT_SESSION_LIVE_TURN_UNAVAILABLE`; follow-ups use Steer once the current turn settles. The in-sandbox endpoint may remain as an internal implementation seam but is not public authority.

The live-substrate E2E leg passed with the m41 gate: the 2026-08-18 production verifier covered attach/replay/reattach alongside create → draft PR, steering, refusal, transcript durability, and cleanup. Unit + real-Postgres + driver coverage remains green.

### D11 — PR feedback steers the session (w9/m344, 2026-11-12)

The reference is Devin. Devin answers comments on PRs its sessions are working on, as long as the session is not archived. The commenter needs write or admin permission on the repository and a GitHub account linked to their Devin account. Bot comments are ignored by default, but CI failures are always processed. Comments that arrive while the session is busy are delivered to that session, not to a new one ([GitHub integration](https://docs.devin.ai/integrations/gh), [PR bot comment settings](https://docs.devin.ai/product-guides/bot-comment-settings)). bex does the same:

- **Events.** The GitHub App receives `issue_comment` (created, on a pull request), `pull_request_review` (submitted) and, since w9/m348, `pull_request_review_comment` (created). A review's own event carries its inline comments, so an inline comment's own event matters only as a `/bex` command, the second place Devin accepts `/devin`; the webhook drops every other one before any workspace lookup, with bots' comments and comments on closed PRs. On a PR a session owns, an inline `/bex` comment is queued as its whole review, under the review's key, so it and the review's own delivery queue one item whichever arrives first. An inline comment of an approving review steers nothing, as the approval does not. `check_suite` (completed) is already subscribed (w1/m181). Each event is matched to the session that owns the PR: the same installation's repository and `prNumber`. A closed or merged PR is ignored. A PR no session owns, or one whose session is canceled or archived, takes only a `/bex` command (below).
- **Who may steer.** The commenter must be a GitHub user, not a Bot. Their permission on the repository must be `write` or `admin`, read through the installation's collaborator-permission API. Its legacy field maps `maintain` and custom roles onto those levels; `author_association` alone does not say whether they can push. Their GitHub account must be linked to a member of the session's workspace who may steer the session (`can_create`, the same check a steer makes). The link is the member's Kratos `github` OIDC credential, matched by the numeric GitHub user id (ADR012 §10). Anyone else is ignored and logged without a reply. The turn runs as the linked member, so authorization, audit and billing name that person. This is the same check a steer from the dashboard makes.
- **CI failures.** A `check_suite` that concludes `failure` on the session's current `headSha` steers it once with the failing check names and summaries. That covers Devin's "always processes CI failures"; bex has no bot-comment toggle. A new head that fails again steers again. After 3 turns in a row that delivered only CI failures, with no other turn in between, bex stops. Any other turn restarts the count, including one steered from the dashboard. This bound is bex's own, against a runaway loop; the session's spend ceiling still applies. The CI steer runs as the session's creator (`createdBy`). **A failure the base branch shares (w6/m399, 2026-11-14).** Before queuing the steer, bex reads the check runs of the newest commits on the base branch that the suite's pull request names (`checks: read` and `contents: read`; up to 10 commits along first parents, within 4 s). Each failing check is decided by the newest of those commits on which a check of the same name passed or failed; a run still queued or running, cancelled or skipped, and a commit the check did not run on (a `[skip ci]` commit, a path filter), are read past. For each failing check whose deciding run failed, the steer says it also fails on `<base>` at `<sha>`, so the change did not cause it, and to leave it unless the task covers it. The first production check (2026-11-16) found why the head commit alone is not enough: main's `test` had failed, but its head's run was still queued, so the steer of bex-co/bex#171 carried no note. The row records the base branch (`agent_session_feedback.base_failing_ref`, migration 0257), and the turn origin reports it as `baseFailingRef` on REST, GraphQL and MCP. The session page labels such a turn "some checks also fail on `<base>`". The steer is still sent: Devin processes every CI failure, and dropping one the base shares would be a divergence. A base that cannot be read notes nothing more than it had decided. Found on 2026-11-13: four of five routine CI turns fixed a ShellCheck failure that was already red on main.
- **Queued, not refused.** A comment that arrives while a turn is running must not be lost to the 409 a direct steer answers. Every accepted event is written to a durable per-session feedback queue. Rows are keyed by the id of the comment, review or check suite in the signed payload, so a redelivery is a no-op. The next steer, once the session is idle, carries the queued items, which is also how a burst of comments becomes one turn. A turn carries one member's comments and reviews, plus the current CI failures, as many as fit one prompt; the rest wait for the next turn. A capacity or spend refusal is retried. A CI failure on a head the session has moved past, and anything not delivered within a day, are dropped. So is the queue of a session that is canceled or archived.
- **Untrusted input.** Comment and review text becomes the steering turn's prompt. Every line is quoted, with author, file, line and link, and the prompt says it is review input that cannot replace the task or the platform's rules. The overlay outranks the prompt (ADR090 D2). The shared layer-4 wrapper for tenant text is still a follow-up there.
- **Replies.** The agent can reply on its own PR through a gateway verb fixed server-side to the session's repository and PR number. Like the PR footer, the comment says it was written by the bex agent. The overlay asks the agent to answer feedback it acted on. Because the App posts those replies as a Bot, they never steer the session.
- **Visible origin.** A steered turn records what started it: `pr_comment`, `pr_review` or `ci_failure`, with the author and link. The session page shows it above the turn.
- **Not in this decision.** GitHub-event automation triggers (ADR101 follow-ups).

**Amendment (w9/m348, 2026-11-12): `/bex` takes a pull request over.** Devin's `/devin`, at the start of a PR comment or an inline review comment and in any case, "starts a new session with that repository, uses the PR as context (taking over the PR if appropriate)" and "replies on the PR with a link to the session". If a session already works on the PR, the comment goes to that session. The commenter needs write or admin and a linked account. Comments on issues, and on closed or merged PRs, are ignored ([GitHub integration](https://docs.devin.ai/integrations/gh), read 2026-11-12). bex does the same:

- **The command.** `/bex` must be the comment's first word, in any case; `/bexify` and a `/bex` later in the text are not the command. The rest of the comment is the task. On a PR a session works on, the comment is ordinary feedback for that session, as above. Bots, plain issues and PRs the event reports closed start nothing and get no reply.
- **Who may start one.** The commenter must have `write` or `admin` on the repository, as for steering. Their GitHub account must be linked to a member who holds `can_create` in a workspace connected to the repository's installation. When several workspaces qualify, the one whose connection is oldest wins, so the choice is deterministic. The session is created through the ordinary create verb as that member, so the spend limits, trust tier, model key, secrets and audit all apply. The agent is the dashboard composer's default (`claude`).
- **What it takes over.** The App reads the PR. Only an open, same-repository PR qualifies, and its head must not be the default branch. A fork PR, a PR whose fork was deleted, a PR that has since closed or merged, a head that is the default branch, a protected head (bex would be refused every update, or, as a rule bypass actor, move a guarded branch), and a head that is another session's `bex-agent/` branch each get a reply naming the reason, and no session. The row records `takeover_pr_number` and `takeover_head_ref` (migration 0239), with `prNumber`, `prUrl` and `headSha`, from the start, so the PR's comments, reviews and CI reach it. Two concurrent `/bex` comments start one session: the create takes a per-pull-request advisory lock and is refused as owned while a live session works on the PR, so the second comment becomes that session's feedback. Unarchiving a takeover session takes the same lock and is refused (`AGENT_SESSION_PULL_REQUEST_OWNED`) while another live session works on the PR, and the PR lookup prefers a live session over a newer ended one.
- **The session never pushes the PR's branch.** It works on its own `bex-agent/<ags-id>` branch, so the prefix rule holds at every Git, mint, label and create boundary ([ADR094 D3](ADR094-coding-agent-mcp.md#d3--create_agent_session-input)). The driver starts that branch from the PR's head (`BEX_AGENT_BASE_BRANCH`). The gateway sees only old and new object ids and cannot stop a force-push, so a pushable PR branch would let a rebase or a prompt injection erase reviewers' commits. Instead, the PR verb (`open_or_update_draft_pr`) brings the PR up to date by fast-forwarding its head branch to the session branch's head through the GitHub API (`PATCH …/git/refs/heads/<head>` with `force: false`). The verb compares the two first: behind or diverged answers `pr_branch_diverged` with the merge to run, and only an ahead head is written. GitHub refuses anything that is not a fast-forward too, and a refusal of the write itself is a branch rule, answered `pr_branch_protected` (not retried). Every call re-reads the PR and refuses a head that became the default branch or moved to another repository. It opens no PR and never touches the title, body or draft state, which stay the author's. The overlay explains this; the driver's delivery check nudges a turn that pushed but did not bring the PR up to date.
- **Acknowledgement and reply.** The App reacts 👀 on the comment, then replies on the PR with the session's dashboard link (`<BEX_DASHBOARD_URL>/agents/<ags-id>`, the PR footer's route) or the reason it started none. A definite create refusal (spend, trust tier, model key, …) is answered with a fixed sentence and its code only, since the PR is public; the details stay in the log and on the dashboard. A failure that may clear asks the commenter to comment `/bex` again. Every path after the 👀 replies.
- **Idempotent.** The create's idempotency key is the comment id, under a `github-pr-` prefix that client keys may not use. The starting comment is stored as turn 1's delivered feedback, keyed as its feedback would be (`comment:<id>`, or `review:<id>` for an inline comment's review). A redelivery therefore finds the session, lands on that row and does nothing more. So does the review event an inline `/bex` comment belongs to, whose other comments the first prompt carries instead.
- **The prompt.** The first turn names the PR's number, title and URL and who asked. It quotes the comment, the inline comment's file and line, and the rest of its review as untrusted text, as feedback is quoted.
- **Visible origin.** Turn 1 shows the comment that started the session, read from the same turn origins ("Started from @login's comment").

### D12 — A message to a running session is queued; Stop turn ends only the current turn (w22/m403, 2026-11-14)

The reference is Devin ([release notes](https://docs.devin.ai/release-notes/2026), read 2026-11-14): messages can be sent to a session that is waiting for capacity (2026-06-05); queueing while Devin works is a preference (2026-07-17); a stop shortcut exists while Devin works (2026-08-21); `Cmd/Ctrl+Enter` while editing a queued message sends it immediately (2026-08-26); queued messages survive idle and resume (2026-09-09); interrupting keeps "the part of the reply you already saw" (2026-10-14); queued messages can be "sent, edited, removed or reordered" (2026-10-16); and Side Chats offer "send to interrupt it or queue to run after it finishes" (2026-11-06).

**Today.** Every steer starts a fresh sandbox and driver process (the phase-1 constraint in `Service.Steer`). A steer on a session that is `creating`, `running`, `resuming` or `redispatching` answers `409 AGENT_SESSION_TURN_IN_FLIGHT`, and the composer is disabled while a turn runs. D9's public live-turn path stays unavailable (`AGENT_SESSION_LIVE_TURN_UNAVAILABLE`), so nothing can be injected into a running turn. Cancel is terminal. Under the recommendations below, a person can add to a running agent without waiting and without cancelling it. `#APPROVAL-MODE` forbids approval gating and an agent-to-user question channel; this is the other direction (user to agent), gates nothing and pauses nothing.

The choices below are the recommendations of milestone w22/m403, made under the Devin-reference rule. They are not user decisions. One diverges from Devin's observable behavior and is recorded in [ADR018](ADR018-render-parity.md) as awaiting the user's sign-off; it does not block the milestone.

- **Queue by default.** A steer on an in-flight session is accepted and queued (`202`, with the queued message in the body) instead of refused. This **diverges** from Devin, where queueing is a preference: bex has no live injection, so the only alternative to queueing is to refuse the message. "Send now" (below) covers Devin's immediate send.
- **What is stored.** The validated steer request: the prompt, attachment ids, skills, secret names and output schema. Everything `Steer` validates that does not depend on dispatch state (prompt size, attachments, skills, secrets, schema) is checked at enqueue; `admitDispatch` (payment method, billing mutation, live-sandbox cap), the spend ceiling, the branch rules and the prompt-history quota run when the message becomes a turn. Editing changes the prompt text only.
- **Order and size.** FIFO by a position column, one message per turn, at most 10 pending per session (`409 AGENT_SESSION_QUEUE_FULL`). A steer on an **idle** session with pending messages is queued too, so a direct send cannot jump the queue; the dispatcher delivers within one poll. An idempotency key (optional, unique per session) makes a retried send harmless, whether its first attempt queued or started a turn (see As built, w22/m408). The CLI sends one with every send but does not repeat a send itself (see As built).
- **Lifetime.** Messages are cleared when the session is canceled, archived or deleted. They are **never dropped by age**, unlike D11's 24-hour feedback: a person's message is not stale review text. A message blocked at dispatch (spend ceiling, live-sandbox cap) stays queued and shows its reason.
- **Dispatcher.** A sibling of the D11 worker: `core.Poll`, a `FOR UPDATE SKIP LOCKED` claim over sessions that are `completed` or `failed`, not archived and holding pending messages, a 2-minute lease, and delivery through `Service.Steer` as the member who queued it (identity `Method "session"`, so `can_operate` is checked again at dispatch; a member who lost access has the message dropped with a reason). Outcomes follow D11: delivered, dropped on a final refusal, released on a retryable one. The store table is new (`agent_session_queued_messages`) because D11's table keys on `(session_id, source_key)` and its `kind` check allows only PR kinds; its claim and lease columns are copied. The D11 worker skips a session that has pending user messages, so user messages go first and one worker wins each idle session; the in-flight 409 and its release path remain the race safety.
- **Stop turn (interrupt).** Ends the running turn and nothing else. The session returns to idle: phase `completed` with the turn flagged `interrupted`, so no phase constraint changes. The reply streamed so far stays in the transcript (the Completer harvests it as for a normal turn, ADR051), commits already pushed stay on the `bex-agent/*` branch, and pending messages stay queued, the first dispatching next. The driver already has a per-turn `AbortController` that only SIGTERM triggers; aborting it runs `session/cancel` and kills the ACP child while the driver process survives. All five profiles (claude, codex, gemini, muse, deepseek) run through that ACP layer, so none refuses. There is no bex-api-to-driver push channel, so bex-api writes a sentinel file in the sandbox through the existing gateway exec path (`sandbox.Service.sessionExec`, the way `ReadSessionStatus` reads the status file) and the driver watches it, aborts the turn and writes status `interrupted` instead of `failed`. The Completer finalizes `interrupted` like a completed turn. _Amended 2026-11-15 (w22/m413, see the last As built below): the stopped turn's disk is then saved as a retained image and the next message boots its fresh sandbox from it; without one, the sandbox is reaped by the usual completed-turn teardown and the next message starts a fresh sandbox exactly as every steer does._ `409 AGENT_SESSION_NO_TURN_RUNNING` when no turn runs; the existing codes for canceled, archived and foreign sessions. Cancel is unchanged. This design was derived by reading the driver, the Completer and the gateway exec path; the live check on a running stack is t004's.
- **Send now** is interrupt, then move the message to the front of the queue. It is a composition of the two verbs, with no API of its own.
- **API.** REST `POST /v1/agent-sessions/{id}/interrupt`; `GET /v1/agent-sessions/{id}/queued-messages`; `PATCH` and `DELETE` on `/v1/agent-sessions/{id}/queued-messages/{messageId}`; `POST .../queued-messages/{messageId}/move`. GraphQL: `queuedMessages` on the session type, and the mutations `editQueuedAgentSessionMessage`, `deleteQueuedAgentSessionMessage`, `moveQueuedAgentSessionMessage` and `interruptAgentSession`. MCP: `send_agent_session_message` queues, plus tools to list, edit, delete and move queued messages and `interrupt_agent_session`. A turn carries `interrupted` (and, since w22/m413 t004, what became of its disk: see the last As built). The scope matrix, the MCP allowlist and golden test, and the CLI contract tests classify each.
- **Not verified about Devin.** Whether Devin's Stop keeps the session was not established in this review, so it is not asserted here.

**As built (w22/m403 t002–t004, 2026-11-14).** The design above stands; these are the choices the code made where it was silent, and the one place it differs.

- **Inline secrets are not queued.** A queued message sits in Postgres until it runs, and an inline secret's value must never. A send that carries `secrets` while the session is busy, or has messages waiting, is refused `409 AGENT_SESSION_QUEUE_INLINE_SECRETS`; naming workspace secrets in `secretNames` queues fine. This differs from D12's "what is stored", which lists secret names only.
- **Who may do what.** A send needs `can_create`, as every steer does, and the dispatcher checks it again for the author at dispatch (a member who lost it has the message dropped with a reason). Listing, deleting and moving queued messages and Stop turn need `can_operate`, as Cancel does. Editing needs `can_create` and makes the editor the author, so the turn runs as the person whose text it is; a message that carries attachments is the exception, since they are the sender's uploads and only the sender's turn may attach them (`403 AGENT_QUEUED_MESSAGE_ATTACHMENTS_OWNED` for anyone else).
- **API details.** A steer that queues answers `202` with `queuedMessage` and `pendingMessages` on the session; one that starts a turn answers `200` as before. `Idempotency-Key` (REST header, `idempotencyKey` on GraphQL and MCP) is honored for every keyed send (w22/m408, below): a retry returns what the first attempt did, and the same key with another message is `AGENT_SESSION_IDEMPOTENCY_KEY_REUSED`. Codes: `AGENT_SESSION_QUEUE_FULL`, `AGENT_QUEUED_MESSAGE_NOT_FOUND` (404), `AGENT_QUEUED_MESSAGE_DISPATCHED` (409: delivered, dropped or being dispatched now), `AGENT_SESSION_NO_TURN_RUNNING`, and `AGENT_SESSION_TURN_STARTING` (a turn whose sandbox is not up has no agent to stop yet). `move` takes `{"position": n}`, 1 runs next. `steerable` is unchanged (a message starts a turn now); a session that can queue is any that is not canceled or archived. `queuedMessages` is on single-session reads, `pendingMessages` on lists too, and a message dropped for a reason is logged but not listed.
- **Dispatcher.** It polls every 5 s. The claim leases only the head of a session's queue, and the transaction that starts its turn (`BeginQueuedAgentSessionTurn`) records it as delivered, so a crash between the two cannot run it twice. D11 yields twice: its claim skips a session with pending messages, and its steer is refused while any wait. A final refusal (the author lost `can_create`, an archived or canceled session, a refused prompt, the prompt-history quota) drops the message with its reason. Every other refusal keeps it, releases its lease and shows the error text as `blockedReason`, so it is retried, after the 30 s backoff below: that includes the refusals a person can fix, although they are a 400, 403 or 404 like the final ones (no model key for the agent, an agent the workspace cannot run, the author's missing second factor under `WORKSPACE_2FA_REQUIRED`, a skill or secret the message names that is gone), and the limits that clear on their own (live sandboxes, trust tier, billing). A message a person can still fix is never lost silently, since a dropped message is logged but not listed.
- **Stop turn.** `POST .../interrupt` answers `202` once the request is delivered; the Completer settles the turn on a 2 s tick for that session (`StopSignal`: `Service.Interrupt` tells the Completer in the same process, which then reads that session's status every 2 s for up to 2 minutes), so Stop shows within a few seconds of the driver's own settle (its 3 s drain plus the Git facts); a request served by another replica, or a lost signal, costs only the 15 s tick that watches every running session (w22/m413 t001). The sentinel is `/var/run/bex-agent/interrupt`, beside the status file, holding the number of the turn to end: a sentinel for another turn is ignored, so a stale one never ends a later turn. The driver polls it every 500 ms, aborts that turn with its own reason, waits briefly for the streamed parts to reach the log, reads the checkout's Git facts and writes status `interrupted`. bex-api records the request on the turn before it writes the sentinel, and the Completer believes the status only for such a turn (w22/m408, below). The driver never commits or pushes (ADR090), here either: commits the agent had pushed stay on the branch, and anything it had not is named in the delivery note. _As first built that work was lost when the next turn's sandbox replaced this one; since w22/m413 (below) the disk is kept for a bounded time and the next turn continues from it._ A turn that owed a structured result is not failed for lacking it. The live abort on a real sandbox has not been run.
- **The CLI's send is one attempt.** Until w22/m408 the server recorded an idempotency key only for a message that was queued, so repeating a send whose `200` was lost would queue it again and run it as a second turn. `bex agent send` and the `chat` composer therefore send once, under a key, and report a transient failure (a 429, a gateway 5xx, a dropped connection) instead of repeating it; the person sends again if the message did not arrive. The server now answers a repeated key with the earlier outcome (below), so repeating a send is safe; making the CLI repeat it is a follow-up. `create` keeps its retry, since a created session is always recorded under its key.

**As built (w22/m408, 2026-11-14).** The w22/m403 review found four gaps in the queue by reading the code; each is closed, with a test against real Postgres that fails on the old behavior. Migration `0268_agent_session_turn_key_and_interrupt_request` carries the two turn-table changes.

- **A keyed send is honored whichever way the first attempt went.** A send that starts a turn directly records its `Idempotency-Key` and a digest of its request (`queueRequestHash`, the one a queued message uses) on `agent_session_turns` (`idempotency_key`, `request_hash`, both null for a keyless send and for a turn a queued message started, unique per session where not null), in the transaction that inserts the turn row. `Service.Steer` looks the key up before it decides to queue or start, first in `agent_session_turns`, then in `agent_session_queued_messages` (any state), and returns the earlier outcome:

  - a turn the first attempt started: the session as it stands now, `200` with no `queuedMessage`, the answer a send that starts a turn gives. The answer is the session as it is when the retry arrives, so once a later queued turn has started the retry shows that turn, and a retry after the session was archived or canceled gets that refusal instead of a replay;
  - a message it queued: the message with its place, `202`; once the message was dispatched or dropped, the message in that state (`state: dispatched` with its `turn`), still `202`, and nothing new starts or queues;
  - the same key with another request: `409 AGENT_SESSION_IDEMPOTENCY_KEY_REUSED`, whichever way the first attempt went; a keyless send is never a replay.

  Keys are per session. The check is repeated under the session's row lock, where every write that carries a key is serialized: the keyed begin and the enqueue each look the key up there, so retries that race the first attempt find its turn or message instead of starting or queueing a second. A canceled or archived session still answers its own refusal before a replay. The lookup sits behind the existing refusals, so a replay costs one extra read of the session.

- **`interrupted` is believed only for a turn bex-api was asked to stop.** `Service.Interrupt` stamps `agent_session_turns.interrupt_requested_at` (idempotent: the first request's time stands) for the turn it names, before it writes the sentinel, so the sandbox cannot write the status first. The Completer finalizes a turn as completed and flagged `interrupted` only if that turn carries the stamp. Any other `interrupted` status, which only the untrusted sandbox can have written, is logged and takes the path of a finished turn: `complete()` runs, so a turn that owes a structured result and has none fails with `STRUCTURED_OUTPUT_MISSING` as it would have without the lie. A request belongs to its turn: the stamp for turn N does not cover turn N+1. The stamp is on the turn row, so a replacement sandbox started for the same turn number inherits it.
- **A reorder never trades places with the message being started.** A message whose lease is held (`claimed_until` in the future) is the head the dispatcher is starting. `move` refuses it, and refuses any move that would give it another place (a move ahead of it, "send now" among them), with `409 AGENT_QUEUED_MESSAGE_DISPATCHED` and no position changed; the messages behind it still reorder among themselves, and a lapsed lease holds nothing. The begin that delivers a message refuses, rather than re-reading, a message that changed after the claim: it compares the prompt and author of the claim, and a mismatch is `ErrQueuedMessageChanged` (internal code `AGENT_QUEUED_MESSAGE_CHANGED`, never a client's answer). The dispatcher releases the message with no reason and the next pass claims it again and runs `Steer` on the saved text, as the member who saved it, so every check runs for them. Refusing was chosen over re-reading because the turn also depends on what `Steer` resolved and authorized for the claimed author (the model key, the attachment binding, the can_create check), which a re-read of the prompt alone would not redo.
- **A blocked head is retried about twice a minute.** The claim leaves a head with a non-empty `blocked_reason` alone until its last attempt is `queueBlockedBackoff` (30 s, beside the poll and lease constants) old; a head with no blocked reason (a lost race, a turn that started first) is claimed at once, and an edit clears the reason, so a person's change is tried at the next poll. Up to 20 blocked sessions therefore run about two steers a minute, not one per 5 s pass. The backoff runs from the claim, not from the failure, so a steer that itself takes 30 seconds or more gets no backoff. The message's `blockedReason` text is unchanged.

**As built (w22/m413 t002–t003, 2026-11-15): a stopped turn keeps its disk.** User decision 2026-11-14 (option A, w22/012): the work a turn had not delivered when a person stopped it survives into the next message, with ADR090's Git custody unchanged: the driver still never commits or pushes, and bex-api pushes nothing on a Stop. Devin keeps a sleeping session's machine and can resume it for 14 days ([release notes](https://docs.devin.ai/release-notes/2026), 2026-09-25, 2026-10-05, 2026-10-09). The decision said "suspend the sandbox and resume it"; the mechanism built keeps the disk as an image and starts the next turn's sandbox from it, because `Client.Resume` posts no body, so a resumed pod would keep the stopped turn's create-time environment (prompt, turn number, secrets, model route, egress) and its stale `status.json`, interrupt sentinel and `result.json`. A new sandbox gets a fresh environment, secrets and egress, and the driver's `ensureRepo` leaves a workspace that is already a Git checkout alone: commits, edits and untracked files stay, and a checkout left on another branch comes onto the session branch with them (a driver test pins both, with an unpushed commit, a dirty tree and the repository moving on meanwhile). Migration `0271_agent_session_retained_images`; code in `internal/agentsessions/retention.go`, `completion_retention.go`, `internal/sandbox/agent_build.go` and `internal/store/agent_retained_images.go`.

- **Saving.** One transaction (`FinalizeAgentSessionRetaining`) settles a stopped turn as completed and inserts a `saving` row in `agent_session_retained_images`, at most one live row per session. The session is steerable at the instant the row exists, so a Steer cannot slip in before it, and the row is the claim, so two replicas never pause one sandbox. Stop still shows within seconds: the settle does not wait for the pause. The save runs behind it, off the Completer's loop (four at once per replica, five minutes for the pause and the copy): it reads the transcript, which needs a running pod, and keeps nothing if that fails; then `RetainAgentSessionSandbox`, which shares `commitAgentSandbox` with `CommitAgentBuildSandbox`. That removes `status.json`, the interrupt sentinel and `result.json` and checks each is gone, refuses at the workspace's storage cap before it pauses, pauses (the commit Job commits the root filesystem), reads the newest snapshot, reserves its bytes under the storage lock, copies it to `snapshots/<ws>-sandbox/images/ari-<id>:image`, and ends the paused sandbox and its pause images. The Completer then clears the session's sandbox id, only while it is still that sandbox's, and deletes the session's egress policy unless a newer turn has started, since the policy is the session's and shared by every sandbox of its turns (`CleanupAgentDispatches` leaves a newer turn's the same way). `saving` then becomes `kept`, until `BEX_AGENT_INTERRUPT_RETENTION` (default 24 hours). The save's deadline is the pause and copy (5 minutes), the end of the sandbox (30 seconds) and the Completer's records (30 seconds, a context of their own started when the save ends), which is also how long the next turn waits: the save and its cleanup always finish before any Steer can start fresh, so a save never works on a session that has moved on. The idle reaper leaves a sandbox that has a `saving` row alone.
- **An open editor is not ended.** Stop must not kill a live edit. When an editor SSH session is open on the session (the check `teardown` makes, `AgentSessionSSHActivity`), a stopped turn settles as usual but keeps nothing: its sandbox stays up under the SSH pin and the idle grace as before, and the next message starts fresh, as every steer did before retention. A failed read of that check counts as open.
- **Continuing.** A send, direct or from the queue (both go through `Service.Steer` to `runSteerDispatch`), first waits for a save in progress, up to its deadline, and then claims the kept image: `kept` to `in_use` in one statement that also compares `retained_until` with the clock. It waits before it tears the previous sandbox down and before it reads the transcript for the continuity env, since the save is pausing that sandbox and harvesting that transcript. An image saved on another agent image than the template's now is released and the turn starts fresh, as ADR111 D4 does for builds. The dispatch creates the sandbox with `AgentImage{ID, Digest}`, the ADR111 path (`agentImageRef`, fresh env, `PrepareSetup`, `TransitionToAgent`), with no prebuilt marker, so a repository environment's setup steps run again as for any turn without a snapshot. Once the turn is bound to its sandbox the image is spent: it is released as continued, any other live retained image of the session as superseded, and the purge deletes it. A dispatch that ends before it binds lets go of its claim, so the next message can use the image.
- **Fallbacks, never an error.** No image, an expired one, one saved on an older agent image, or one still being saved at its deadline: the turn starts from a fresh sandbox. A sandbox that cannot start from the image (any create error but the capacity limit) is retried once from a fresh sandbox, the image is released as unusable, and the turn's delivery note starts with "The changes kept from the stopped turn could not be restored, so this turn started from a fresh checkout of the branch." (`agent_session_turns.start_note`, put first by the Completer when the turn settles); if the fresh sandbox does not start either, the image was not at fault and stays kept. A full storage cap, a failed transcript read or a failed pause keeps nothing: the turn stays settled as it was, `agent_session_turns.retention` says `lost`, and the sandbox follows today's lifecycle (the idle grace; one whose pause had begun is ended). The cap bounds the save at two points: the check before the pause, and the reservation after the commit, which counts the image's real size under the lock imports take.
- **Every end deletes the image.** Each transition of the handle is a compare-and-set on its state, and the claim reads the clock in the same statement as the state, so an expiry and a Steer never both win and an image in use is never released from under its dispatch (tests race the two and fire the expiry mid-boot). Cancel and archive release it in the same transaction as the session change; Delete deletes the image before the session row, whose cascade would drop the handle, and fails, retryably, if the registry cannot; the sandbox purger lists a workspace's handles before the tenant cascade; a sweep on every Completer tick expires kept images, lets go of claims whose dispatch died, abandons a save whose replica is gone, and deletes released images with a backoff, keeping the handle until the registry no longer holds the image. Every purge takes at most 5 images and at most 10 seconds, on the Completer's one loop and in Cancel, archive and Delete alike, so a hung registry stalls neither a Stop's settle nor a request: a handle it leaves waits for the next sweep, and Delete fails retryably. A save that ends after its retention was released deletes the image it wrote.
- **What is recorded.** The turn carries `retention` (`kept`, `continued` or `lost`), `retained_until` and, since t004, `retention_reason` (migration `0272_agent_session_turn_retention_reason`), written in the transactions that make each transition, for the surfaces to show (below). A release copies its reason onto the turn with the loss, because the image's row is deleted once the registry no longer holds the image; a stopped turn that kept nothing because an editor was open records `lost` with the reason `editor_open`, since no image was ever begun for it. `bex_agent_session_retentions_total{result}` counts saves.
- **The setting.** `BEX_AGENT_INTERRUPT_RETENTION`, a Go duration, default 24 hours, `0` keeps nothing, and a value over 7 days is cut to 7 days, so it is always below Devin's 14. A shorter bound than Devin's is the one divergence left, with a full cap or a failed pause; both are in [ADR018](ADR018-render-parity.md).
- **What the image holds.** Whatever the agent left on its disk, including a file that carries a secret value the agent wrote, as ADR111 D6 says of a build's snapshot, and the driver baked into it. Environment variables are not part of an image. It lives in the workspace's own registry namespace, boots only that workspace's sandboxes, and only the same session's next turn.
- **What the surfaces say (w22/m413 t004, 2026-11-15).** Each turn of the transcript (REST `GET /v1/agent-sessions/{id}/transcript`, GraphQL `agentSessionTranscript.turns`, MCP `get_agent_session_transcript`), beside `interrupted`, carries the same four fields, built once in `Service.Transcript` (`turnRetention`, `internal/agentsessions/turn_retention.go`):

  - `retention`, always present: `none` (nothing was kept and nothing is owed: the turn was not stopped, retention is off, its sandbox was already gone or its session was archived), `saving` (the turn has settled and its disk is being saved, for as long as a few minutes), `kept` (until `retainedUntil`; the next message continues from it), `continued` (the next turn started from it) or `lost`. `saving` is derived by the API's read of the turns (`Store.AgentSessionTurnsWithRetention`) from the image's saving row and is never stored, since the turn's own record is written when the save ends; the plain `AgentSessionTurns` stays a read of `agent_session_turns` alone, because the SSH gateway's scoped database role calls it and holds no privilege on `agent_session_retained_images` (ADR035; a store test and the dbrole integration test pin it), so it reports the retention as recorded; a `kept` record whose time has passed reads `lost` with the reason `expired`, as the next message treats it, without waiting for the Completer's sweep to say so.
  - `retainedUntil`, RFC 3339 for a `kept` turn and `null` (absent on REST and MCP) otherwise.
  - `retentionLostReason`, for a `lost` turn when the cause is one of: `expired`, `storage_full` (the workspace's storage cap had no room), `save_failed` (the transcript read, the pause, the copy or the record failed, or the save never ended), `editor_open`, `canceled`, `archived` or `not_restored` (the next turn could not start from the image, or it was saved on an older agent image). A superseded image or a deleted session names none. Empty on GraphQL, absent on REST and MCP, otherwise.
  - `startNote`, the sentence a turn that had to start from a fresh checkout although the stopped turn's disk was kept begins its delivery note with: it is set on that next turn, not on the stopped one, whose own `retention` is then `lost` with `not_restored`.

  The dashboard shows a line under the interrupted note of each stopped turn: "Your changes are kept until {time}" for `kept` (the time is the viewer's own clock, so before hydration the line names none), "Saving your changes so the next message can continue from them" for `saving`, "The next message continued from these changes" for `continued`, and for `lost` "Your unpushed changes were lost when the retained sandbox expired", or the briefer cause for a full storage cap, a failed save, an open editor or a disk the next turn could not restore (a canceled or archived session says only that the changes were lost). `none` adds nothing. It reads while the save runs on the active poll cadence, so the line turns to its answer by itself, and the strings are in all eight dashboard locales. `bex agent logs` ends a stopped turn with `■ Turn N was interrupted before it finished.` and the same sentence (with `-o json`, that turn as the API sent it, after the turn's rows), and `bex agent get` adds a `Stopped` row for a settled session whose latest turn was stopped, from one extra read of the transcript that asks for no part; its `-o json|yaml` answers stay the API's own and read nothing extra. `bex agent wait`, `run --wait` and `chat` do not show it.

- **Not built.** The live check on a running stack is t008's.
- **Not done (follow-ups).** Skipping the setup steps over a retained disk. A sub-cap for retained bytes, so a user of `/v1/sandboxes` only is not starved by them, and a 429 text that no longer blames "suspended sandboxes" alone. Gating the purge on `save_deadline <= now`: a purge can remove the handle of a released row while its save is still pushing, and a crash of that save then leaks the image. Pause images leaked by a crash in the middle of a save. `session.jsonl` now carrying across turns of a continued disk, against the driver's 16 MiB log cap. A rolling deploy in which an old replica's dispatch never settles the retained images (it never calls the settle after binding). No skip for a clean tree, so every Stop pays the pause latency (the three later triggers below skip one; w10/m491). With no sandbox registry configured every Stop logs a failed save and counts it as failed: retention should be off when the registry is not configured.

**As built (w10/m491, 2026-11-18): every turn end with undelivered work keeps its disk.** Production sessions lost verified, unpushed fixes in two days (`ags-dbu0pfdikg6s738lam7g`, `ags-dbu0pfmc1l2s739d3n3g`, `ags-dbutgej906ns73ff3kb0`): m413 kept a disk only on a Stop, and every other end discarded it. A follow-up message tore the previous sandbox down and booted a fresh clone (`runSteerDispatch`), the idle grace terminated a completed turn's sandbox, and a failed turn was torn down at its settle. Devin keeps a session's machine across sleeps, wakes the same machine for a preview, a file view, a terminal or SSH, and resumes it for 14 days whatever ended the last exchange ([release notes](https://docs.devin.ai/release-notes/2026), 2026-09-25, 2026-10-05, 2026-10-09, read 2026-11-18). The m413 mechanism (the retained image, its handle, its claim and every release) is reused unchanged; only when it runs is widened. ADR090 is unchanged: neither the driver nor bex-api commits or pushes anything, and a push of the work to a recovery ref, the inbox note's other option, is not taken, because bex-api would then push work the agent did not deliver.

- **The triggers.** `agent_session_turns.retention_cause` records which (migration `0299_agent_session_turn_checkout`): `stopped` (m413, unchanged: always saved), `failed` (the driver's failure, the no-progress watchdog, the turn ceiling, a missing structured result: at the settle, where `teardown` skips the idle grace), `idle_closed` (a completed turn, where the idle reaper would terminate the sandbox) and `replaced` (the next message, direct or queued, in `runSteerDispatch` before it claims an image and tears the previous sandbox down). The first two share one hook, `Completer.retainOnClose`, at the point `teardown` calls `terminate`, after the editor pin; the third is `Completer.retainReplaced`, run inline in the background dispatch (`Service.Completer` is the same Completer). All three begin through `BeginAgentSessionRetention`, the `saving` row that is the claim on pausing the sandbox: it takes only a sandbox the session still holds (a settled session on that turn) or the one its new turn just replaced (`agent_session_dispatches.previous_sandbox_id`), never an archived session's, never a second live row. A close that finds the next turn begun leaves the sandbox to that dispatch; a message that finds a close's save running waits for it through the claim, as for a Stop.
- **The clean-tree skip.** Only a checkout holding undelivered work is saved: uncommitted changes (untracked files included) or local commits no remote-tracking ref has. The decision reads the turn's recorded facts: the driver now writes `git` (`dirty`, `unpushedCommits`) on a failed status too, after the agent is stopped and bounded at 15 s (`checkoutFacts`, `session.ts`), and the Completer records them on the turn (`checkout_dirty`, `unpushed_commits`, NULL for unknown) before it settles the turn, so every later reader has them. When they are unknown (a session with no repository, a setup failure, an older driver) or an editor has connected since the turn ended, the checkout is read in the sandbox through the gateway exec path (`ReadSessionCheckout`, read-only Git with `fsmonitor` off; a workspace that is not a checkout counts any file as uncommitted). A read that fails keeps today's teardown. A clean checkout pays no pause.
- **What degrades, and how it is said.** An editor open on a sandbox a message replaces keeps nothing and records `lost`, `editor_open`, as for a Stop (a close waits for the editor to disconnect). A full cap or a failed save on a close records the loss and ends the sandbox, as the close would have, so the reaper never retries every tick; on a message it starts fresh. A failed turn whose sandbox was already gone (`failLostSandbox`) records `lost` with the new reason `sandbox_lost` and an unknown stake, unless the turn recorded its checkout clean. A save can now follow an earlier loss on the same turn (a Stop with an editor open, then the idle close once it disconnected): the keep clears the loss reason.
- **The wait a message pays.** A message after a turn with undelivered work waits for that save (the pause, the commit Job and the copy, about 40 s on `dev-10` in m413's check, at most `retentionSaveWindow`) while the session reads `redispatching`; the accept stays fast. A clean turn's message waits for nothing new.
- **What the surfaces say.** `retention` is no longer `none` for every turn nobody stopped: it reads each turn's record whatever ended it, and `saving` is derived for any turn with a saving row. Each transcript turn (REST, GraphQL, MCP, one `turnRetention`) also carries `retentionCause` (`stopped`, `failed`, `replaced`, `idle_closed`; a stopped turn recorded before the column reads `stopped`) and the stake, `unpushedCommits` and `uncommittedChanges`, each absent (null on GraphQL) for `none` or when unknown; the field descriptions are shared constants, so GraphQL and MCP say the same. `retentionLostReason` adds `sandbox_lost`. A turn that started fresh after a loss begins its delivery note with the loss, as `startNote`: "The 2 unpushed commits and the uncommitted changes from turn 3 were lost (the workspace's sandbox storage was full), so this turn started from a fresh checkout of the branch."; a disk that could not boot says "The changes kept from turn 3 could not be restored, …". The agent is told the same in its prompt (`BEX_AGENT_CHECKOUT_NOTE`, rendered by the driver as `<checkout-state>` before the prompt on every continuity rung), or, on a restored disk, "This turn's checkout is the one turn 3 left, restored from its sandbox's disk: … are still there". The dashboard draws the retention line, and a second line with the stake ("2 unpushed commits · uncommitted changes", in all eight locales, plural-aware), at the end of every such turn, under the interrupted note for a stopped one; `bex agent logs` ends the turn with `■ Turn N: Your 2 unpushed commits and uncommitted changes are kept until …` and `bex agent get` shows it as a `Changes` row (`Stopped` for a stopped turn).
- **The setting.** `BEX_AGENT_INTERRUPT_RETENTION` keeps its name and now bounds every kept disk; renaming a production setting would buy nothing but a deploy step. `.env.example` is unchanged.
- **Not done (follow-ups).** Running processes are still not kept (a new sandbox boots from the disk), and the 24-hour bound stays below Devin's 14 days, both recorded in [ADR018](ADR018-render-parity.md). The live check on `dev-10` is the milestone's t011.

### w5/m77 — ACP profile manifest and stream hot-path simplification (2026-08-22)

Vercel's experimental `@ai-sdk/harness` / `@ai-sdk/harness-acp` layer (AI SDK v7, sandbox-orchestrating) validates the **declarative runtime profile** idea but duplicates mechanisms bex already owns: direct `@agentclientprotocol/sdk` stdio in the in-pod driver, OpenSandbox lifecycle, gateway credential brokering, transcript authority, and the AI SDK **v6** UI-message stream (`x-vercel-ai-ui-message-stream: v1`). **Adoption boundary (frozen):** do not introduce `@ai-sdk/harness`, a second bridge, a WebSocket hop, a second sandbox provider, or an AI SDK major-version migration to gain ACP compatibility. The useful lesson — one release-locked, non-secret profile manifest — is adopted in `lego/backend/internal/agentsession/agent-profiles.json`, embedded by `lego/backend/internal/agentsession/profiles.go` and loaded by the in-pod driver. Supported profile ids remain the only tenant-selectable agent surface; executables, args, bootstrap env, credential env, and model-proxy routing are operator-owned static facts verified at image build.

The live conversation hot path is optimized without changing wire bytes or dashboard semantics:

- **Gateway attach** (`agentattach.go`): accepted UI-message parts forward to the browser **before** batched `AppendAgentSessionTranscript` calls; one serial writer flushes at 32 parts, 1 MiB, 100 ms, and stream end; its 32-slot queue and 2 MiB total outstanding-byte budget apply bounded backpressure while preserving `(session_id, turn, part_index)` idempotency and ADR051 log-harvest recovery.
- **In-pod driver** (`session.ts`, `stream-hub.ts`): one mode-0600 append sink per turn buffers bounded writes and closes before terminal status; the hub stores each sanitized part with its single encoded SSE frame for byte accounting, replay, eviction, and fan-out.

Fixtures in `lego/agent-image/driver/test/hotpath-baseline.test.ts`, `lego/backend/internal/sshgateway/agentattach/transcript_batcher_test.go`, and `lego/backend/internal/store/agentsessions_batch_pg_test.go` record frame encoding, file operations, and actual PostgreSQL transaction counts. The 2026-09-05 closeout distinguishes the original per-part implementation from the earlier partial optimization: that partial version already batched calls but launched unbounded concurrent writers, permitting sequence allocation out of order. The final writer serializes batches and stops further persistence after its first failure; ADR051 harvest fills the missing suffix. Each append has a five-second deadline independent of request cancellation, and terminal `[DONE]` waits for queued persistence attempts. First-frame tests block the store explicitly, separating gateway forwarding from model latency and completion polling.

### w5/m80 — bounded, fast, clearly-attributed failures (2026-08-27)

A full dev-5 end-to-end run measured the failure path, not just the happy path, and found three defects. **(1) Turn timeout defaulted to 4h.** The driver's fallback (`config.ts`) was `4 * 60 * 60 * 1000` and bex-api injected nothing, so a hung model call or runaway tool loop held a sandbox for up to four hours. bex-api now injects `BEX_AGENT_TURN_TIMEOUT_MS` from `BEX_AGENT_TURN_TIMEOUT` (default 30m) on every dispatch, and the driver fallback is 30m — the bound is never disabled. **(2) A bad/expired BYO key hung ~192s.** The whole "running" duration was one `session/prompt` the agent CLI/SDK retried against an instant vendor 401 before surfacing it; `initialize`/`session/new` were <1s, so it was not agent boot. The gateway model proxy now treats a **post-mint vendor 401/403** as a non-transient auth rejection and reports it over the same gateway→bex-api HMAC channel as the mint (`InternalModelAuthFailurePath`); bex-api CASes the live session to `failed` with an actionable reason, and the Completer reaps the now-terminal sandbox on its next tick — seconds, not minutes. Transient vendor failures (429/5xx) still relay for the CLI's normal retry. **(3) Failed sandboxes lingered ~30m.** `teardown` applied the ADR059 Active-tier idle grace (meant for a _completed_ result a user may reopen in an editor) to failed sessions too, pinning plan quota; a failed session with no open editor SSH now skips the grace and reclaims at the next tick (the open-SSH pin still holds — never kill a live edit). Finally, a background **provisioning** failure now records its reason in `failure_reason` (not just `status`), matching the Completer's driver-failure path, so every terminal-failure class — sandbox-create/capacity, model-auth, turn-timeout — surfaces a non-empty reason across REST/GraphQL/MCP and the dashboard callout (closes `w5/048`).

**Amended 2026-11-11: production runs `BEX_AGENT_TURN_TIMEOUT=4h`** (`lego/operator/config/prod`; the code default stays 30m). The 30m bound killed all eight scheduled `rt-*` routines on their first day while they were still building and testing, and a timed-out turn loses its unpushed work. The wall clock cannot tell a hung turn from a long one, so a hung turn holds its sandbox for up to four hours again until an idle (no agent event) timeout takes over as the hang guard; `maxSpendUSD` bounds the model cost meanwhile.

**Amended 2026-11-18 (w10/016): a command the agent waits on is progress while it uses the CPU.** The idle bound w9/m349 added (`BEX_AGENT_TURN_IDLE_TIMEOUT`, 30m, `driver/src/turn-bound.ts`) counted only ACP updates and prompts, and paused only for a tool call still open. muse sends a long command to the background, ends the tool call with `background_running`, and holds its prompt open with no update until the command ends, so `ags-dbutgej906ns73ff3kb0` failed with "ACP turn made no progress for 1800000ms" 36 minutes into the dashboard's full `yarn test`, with its verified fix not yet pushed. The driver now samples the CPU time of its own descendants (the agent, its MCP servers and every command they started; `driver/src/activity.ts`) from `/proc` every minute, and a minute in which they used at least 5% of one CPU holds the idle clock as an open tool call does, for at most `BEX_AGENT_TOOL_CALL_TIMEOUT` past the agent's last update. A command waiting on the network or a lock uses no CPU, so a hung turn still fails at the idle bound; a runaway command fails at the tool-call cap, not the ceiling. The output of a background command is not read: the agent's pipes are its own, and that run piped the suite into `tail`, so there was none. The idle limit itself is unchanged and is not made per automation: the case that reached it no longer does, and a longer limit would only delay the hang guard. A turn the bound does fail keeps its undelivered work (w10/m491).

### w5/m132 — a failure code clients decide by (2026-10-07)

A failed session carries `failureReasonCode` beside `failureReason` on REST, GraphQL and MCP, so a client acts on the cause without matching the sentence. The one code today is `SANDBOX_CAPACITY_LIMIT` (`sandbox.CodeSandboxCapacityLimit`), recorded when a dispatch is refused at the workspace's sandbox limit; the dashboard's upgrade callout decides by it alone. Only the dispatch abandonment writes a code, in the same statement as its sentence; every other write that clears or replaces the sentence clears it (`agent_sessions.failure_reason_code`, migration 0144, which backfills older capacity failures from `failure_reason` or, before w5/m80, `status`). REST and MCP omit the key when it is empty, and GraphQL answers null.

**Capacity only when it is capacity (w9/074, 2026-11-04).** The OpenSandbox server's pod-ready timeout used to map to `SANDBOX_CAPACITY_LIMIT` unconditionally. On 2026-11-04 a sandbox node joined without gVisor and every agent session failed as "capacity reached (plan limit)", while the workspace was nearly idle. bex-api still cannot see the pod, but it now checks what it can: when the workspace's live sandboxes, times this template's CPU and memory limits, still fit under the plan's limits (`store.SandboxComputeLimits`), the quota cannot have refused the pod. The timeout is then `SANDBOX_START_FAILED` (503, "the cause is on bex's side, not your plan"), recorded as the session's code with "sandbox did not start (platform issue)". A plan lookup or sandbox list that fails keeps the capacity answer. The dashboard's upgrade callout still decides only by `SANDBOX_CAPACITY_LIMIT`, so a platform failure no longer offers an upgrade. The root cause of a stuck pod stays in `w10/008`. _Amended by w10/m497 below: bex-api now reads the pod, so the start failure names its cause, and a full pool waits instead of failing._

### w10/m497 — a full sandbox pool waits for a machine; every other start failure names its cause (2026-11-18)

On 2026-11-17 and 18, seven sessions failed with `SANDBOX_START_FAILED` while the workspace's quota had room. Their pods sat `Unschedulable` (`Insufficient memory`) on the one `cpx42` sandbox node for the OpenSandbox server's 300 s wait, and the server deleted them. Devin never fails a session for its own capacity. A session "waiting for capacity" keeps its messages and starts by itself, and since 2026-09-30 "sessions on an outpost now wait for the outpost's machine to come online instead of failing" ([release notes](https://docs.devin.ai/release-notes/overview), read 2026-11-18). bex now does the same.

**Cause source: bex-api reads the pod, while the create waits.**

- A new ClusterRole, `bex-tenant-sandbox-api`, grants core `pods` `get` and `list` and nothing else: no watch, logs, exec, events or Secrets. The NamespaceReconciler binds it to `bex-system/bex-api` in each `<ws>-sandbox` namespace. The namespace admission policy admits exactly that binding, and `scripts/gitops-validate.sh` pins the role's rules.
- No new trust: a sandbox pod's spec holds only what bex-api itself wrote into it. This is the hosting namespace's `bex-tenant-api` pod read without its Secrets rule, so ADR028's "no cluster-wide Secrets for bex-api" holds unchanged.
- **The read happens during the create.** The server deletes the pod when its wait ends, so a read after the 504 finds nothing. bex-api lists the attempt's pod by its own labels (`bex.co/agent-session` and `bex.co/agent-dispatch-turn`; a Render sandbox by `bex.co/sandbox-id`) every 10 s from the tenth second until the create answers. The last observation names the cause.
- **Rejected sources:**
  - OpenSandbox's own GET reports only `Pending` and "Sandbox is being created".
  - Events are not needed: the pod's conditions and container states carry every cause below, so the least privilege leaves them out.
- The quota check reads the namespace's two ResourceQuotas with the `resourcequotas` `get` the NamespaceReconciler already holds.

**Cause vocabulary.** `failureCause` sits beside `failureReasonCode: SANDBOX_START_FAILED` and nowhere else. The code itself is unchanged.

| Cause | What bex-api saw | Failure reason |
| --- | --- | --- |
| `pool_full` | `PodScheduled=False`, reason `Unschedulable`: no sandbox machine has room (`Insufficient cpu`, `Insufficient memory`, …) or none is ready | "No sandbox machine had room for this session for 60 minutes, so it did not start. Send the message again to retry." |
| `image_pull` | a container or init container waiting `ErrImagePull`, `ImagePullBackOff`, `InvalidImageName` or `ErrImageNeverPull` | "The sandbox image could not be pulled, so the session did not start. Try again, and contact support if it keeps failing." |
| `runtime` | scheduled, but the pod sandbox never started (`PodReadyToStartContainers=False`, which is what `FailedCreatePodSandBox` and a missing `RuntimeClass` handler leave), a container waiting `CreateContainerError`, `CreateContainerConfigError` or `RunContainerError`, or the pod `Failed` | "The sandbox runtime could not start this session's machine. Try again, and contact support if it keeps failing." |
| `quota` | no pod at all, and a namespace ResourceQuota with less room than one sandbox pod charges at most (`store.SandboxPodQuotaMax`) | "The workspace's sandbox quota refused this session's machine. Stop a running sandbox or session, then try again." |
| `unknown` | anything else, or a read that was refused or failed | "sandbox did not start (platform issue)", as before |

`SANDBOX_CAPACITY_LIMIT` keeps its plan-limit meaning (w9/074). A pod that was scheduled, or that waited for scheduling, was admitted by the quota, so `pool_full`, `image_pull` and `runtime` skip the plan-limit check. Only `quota` and `unknown` still run it. A Render sandbox create (`POST /v1/sandboxes`) answers the same 503 `SANDBOX_START_FAILED` with the same words and `params.cause`. Render documents no capacity answer for a sandbox create, so the extra parameter is an extension.

**The wait: only `pool_full`, for up to an hour.**

- **Attempts.** Each attempt is one OpenSandbox create. Its own 300 s wait holds the pod in the scheduler's queue, so the session starts as soon as room frees during it. An attempt that ends `pool_full` is followed by another after 15 s (`sandboxWaitBackoff`). Before each new attempt, bex-api ends any sandbox of this turn that survived (`CleanupAgentDispatches` by the turn's labels), so a wait never leaves two sandboxes for one turn. w1/m405's t002 has not shipped; this is the same guarantee, built on the turn label.
- **Bound.** One hour (`sandboxWaitBound`), and never more than the turn ceiling (`BEX_AGENT_TURN_TIMEOUT`: 4 h in production, 30 min by default). The routines' turns on the interim node ran from 8 to 68 minutes (ADR105 § Until the AX42-1 arrives), so an hour lets a burst of hourly starts drain behind the turns already running. A pool still full after that is undersized: the alert below fires, and the turn fails with cause `pool_full` and words that say how long it waited.
- **Every other cause fails at once** with its own words. A retry would not change an image that does not pull, a runtime that does not start or a quota that refuses.
- **Keep-alive.** Before every attempt, one transaction (`MarkAgentDispatchWaiting`) checks that the session is still unbound on this turn, in `creating` or `redispatching`, and not archived. It stamps `agent_sessions.sandbox_wait_since` once, moves the dispatch's `next_check_at` to 16 minutes ahead (`sandboxWaitLease`) and stores the dispatch's input (`agent_session_dispatches.wait_spec`, below). The dispatch's 15-minute background ceiling (`dispatchTimeout`) restarts with each attempt of a waiting dispatch and is not lifted for any other, so a replica still waiting always ends its own wait a minute before its lease runs out.
- **Recovery: a wait survives a rollout (w10/022, 2026-11-19).** A waiting dispatch is never due while its replica waits, so neither dispatch recovery nor the legacy repair in `ListAgentDispatchesDue` abandons it. A failed previous-sandbox teardown never moves a live dispatch's `next_check_at` earlier either (`DeferPreviousSandboxTeardown`). When the waiting replica itself exits, as every rollout drains every replica within minutes, its dispatch becomes due when its lease runs out, and dispatch recovery on any other replica carries the wait on instead of abandoning it:
  - **The stored input** is the dispatch spec as the accepting verb built it: the template, model endpoint, egress, driver env, delivery mode and the retained disk the dispatch claimed. It holds no secret. Secrets, attachments, skills and the repository environment are read again by the resumed dispatch, as by every dispatch, and the model key is the session's placeholder, made again. Abandoning or binding the dispatch drops it.
  - **One replica resumes it.** One compare-and-set on `next_check_at` (`ResumeAgentDispatchWait`) claims the due dispatch, so of the replicas whose ticks find it, exactly one carries it on, under a new lease.
  - **Never two sandboxes.** The resuming replica first runs the keep-alive's check, then ends whatever the stopped replica's last create left for the turn (`CleanupAgentDispatches` by the turn's labels), then creates again.
  - **Nothing else changes.** The bound still counts from `sandbox_wait_since`. Cancel, Delete and Archive end a resumed wait as they end any other, and one that came while no replica waited ends it at the resume, with nothing created.
  - **What a rollout still costs:** up to 16 minutes, the lease of the last attempt, in which no create runs for the waiting session. A wait held by a replica that predates this change, or whose stored input cannot be read, is still abandoned as interrupted ("Send the prompt again to retry"), as is every dispatch that is not waiting.
- **Cancel, Delete and Archive end the wait at once.**
  - Cancel takes the session out of `creating`. Delete needs a finished session, so Cancel comes first. Archive stamps `archived_at`.
  - A watcher on the session row cancels the attempt in flight within 10 s, and the next attempt's check refuses.
  - A create that already answered binds nothing: `RecordAgentSessionDispatch`'s CAS refuses a canceled session and tears its sandbox down.
  - An archived waiting session fails with "The session was archived while it waited for a sandbox machine, so it did not start."
- **Boundary with w1/m405.** Transient create faults stay in w1/m405: a dropped connection, a 502/503/504, `SANDBOX_RUNTIME_UNAVAILABLE`, and the server's `KUBERNETES::API_ERROR` 500s. w1/m405's definition of done keeps `SANDBOX_START_FAILED` failing at once, and this milestone changes exactly one case of it: `pool_full`, which waits. When w1/m405 retries a transient fault, it wraps the same create this wait repeats.

**Surfaces.**

- The session view (REST, GraphQL, MCP) gains three fields:
  - `waitingFor: "sandbox_capacity"` while the session waits; absent otherwise, and GraphQL null.
  - `waitingSince`, when the wait began.
  - `failureCause`, beside `SANDBOX_START_FAILED` only.
- The phase stays `creating` (or `redispatching`) and `state` stays `working`, so clients keep polling and an automation's overlap rule still counts the session as working.
- The dashboard's session page and list, and `bex agent get`, `logs` and `run`, show "Waiting for a sandbox machine" with the time waited. A failure shows the cause's words, in all eight locales. The upgrade callout still keys only on `SANDBOX_CAPACITY_LIMIT`.
- An automation run's activity (`GET /v1/agent-automations/{id}/runs`, GraphQL `agentAutomationRuns`, MCP `list_agent_automation_runs`) carries its session's `state`, `waitingFor`, `waitingSince`, `failureReasonCode` and `failureCause`. The dashboard's run history then reads "Waiting for a sandbox machine", or "Didn't start" with the cause, apart from `failed_create`. A session that fails to start is a `started` run, so it never counts toward the `repeated_failures` pause (ADR101 D7).

**Signal.** Three series feed the alert, documented beside ADR105's pool-size decision:

- `bex_agent_session_sandbox_waiting{cause}`, a gauge of the sessions waiting now, per replica. Sum it across replicas.
- `bex_agent_session_sandbox_wait_seconds{outcome}`, a histogram of each wait, labelled `started`, `gave_up` or `ended`.
- A new `waiting` outcome on `bex_agent_session_provision_seconds`, for each attempt that ended `pool_full`.

`AgentSandboxPoolFull` fires when sessions have been waiting for 15 minutes. `AgentSessionProvisionFailing`'s denominator leaves the `waiting` attempts out, so a burst of waits neither hides nor raises its failure ratio.

### w5/m81 — lifecycle latency instrumentation (2026-08-27)

The dev-5 numbers above had to be derived from pod timestamps and an out-of-band ACP probe because a session carried no per-phase timing (only row/turn timestamps + two counters). bex-api now exposes, on the same Prometheus registry as the existing agent-session counters:

- `bex_agent_session_turn_duration_seconds{outcome}` — a turn's running-transition→terminalization wall-clock (completed/failed/lost). This is the series that surfaces a hung turn (the ~192s bad-key case) and validates the m80 fixes. It includes ≤1 completer poll interval of detection lag (an upper bound on the true turn time).
- `bex_agent_session_provision_seconds{outcome}` — sandbox provisioning wall-clock (the `CreateAgentSessionSandbox` call, which blocks until the pod is Running or fails), labelled running/failed.

**Observed SLO baseline (dev-5, warm node/image, 2026-08-26/27):** create-accept ~100ms; provisioning 3–10s (cold image pull ~23s per ADR059); agent-ready <1s (`initialize` 132ms + `session/new` 736ms); happy-path turn ≈ model latency; a bad-key turn was ~192s **before** m80 t003 and is seconds after. **Time-to-first-model-call** is approximated by `provision_seconds` — agent boot measured <1s, so the running-transition is within ~1s of the first model call for a turn-1 session; a precise per-turn first-token metric is deferred because it requires correlating the turn-start (bex-api) with the first proxied call (gateway), which the current one-way mint channel does not carry.

### w5/m88 — durable turn timing + full outcome coverage (2026-09-08)

m81 measured turn duration from `agent_sessions.updated_at`, which pin/archive also rewrite mid-turn and would shorten samples. Timing now anchors on durable `agent_session_turns` columns: `created_at` (acceptance), `started_at` (set once at sandbox bind / running transition; NULL when the turn never ran), and `completed_at` (terminal CAS). Series contract:

- `bex_agent_session_turn_outcomes_total{outcome}` — successful terminal CAS count. Closed outcomes: `completed`, `failed`, `lost`, `canceled`, `vendor_auth_rejected`, `dispatch_failed`. Only the winning CAS observes (no double-count on Completer races or replayed auth reports).
- `bex_agent_session_turn_duration_seconds{outcome}` — **running** wall-clock only (`started_at` → terminal). Never-running failures (dispatch abandon before bind, auth reject before running) increment the outcome counter and **do not** emit a fabricated duration sample. Pre-migration turns with NULL `started_at` are treated the same (no guessed historical precision).
- `bex_agent_session_provision_seconds{outcome}` — unchanged; provisioning latency remains separate from turn running duration.
- Prompt-less rehydrate, pin/archive, and idle hibernation do not mint phantom turns or extra terminal observations.

Prometheus scrape/process resets still apply — this is operational telemetry, not a durable exactly-once ledger. Precise first-token tracing remains deferred.

## Alternatives considered

- **Per-request ("premium requests") billing** — rejected; retired by its inventor effective 2026-06-01 (four stale premium-request claims were refuted 0-3/1-2 in verification; any source describing multipliers as current is outdated).
- **Bespoke session protocol instead of ACP** — rejected; ACP buys IDE clients (Zed, JetBrains direction) and agent pluggability for the cost of supplying transport semantics bex must build either way.
- **AI SDK driver outside the sandbox** (dashboard SSR spawning or dialing the agent remotely) — rejected; `@mcpc-tech/acp-ai-provider` is stdio-spawn only with no remote transport, and a remote-transport fork would recreate exactly the bespoke bridge the in-sandbox driver avoids.
- **Bespoke WebSocket⇄JSON-RPC gateway bridge / raw ACP launcher** — rejected; it bypasses the action-bound launch grant and is unnecessary for the dashboard conversation transport.
- **kubernetes-sigs/agent-sandbox or E2B-hosted substrate** — rejected; duplicates w3/m32.
- **Bundled model spend at flat ACU-style rates in v1** — deferred, not rejected; requires the metering proxy and margin/ToS clarity first (D7).
- **Replacing the JSON control verbs with the AI-SDK stream endpoint (SSE-only session API)** — rejected (2026-08-02, D9 target-API-shape decision): only in-conversation actions (prompt turns, stream parts, history replay) fold into the chat contract; create/cancel/list/get/resume require control-plane authority the verbatim-forwarded driver path cannot exercise, and non-streaming consumers (MCP tools, CLI scripts, CI) need the poll-shaped JSON surface — GitHub's public agent-tasks API is poll-only. What **was** absorbed: live steering (chat POST) and transcript reading (stream replay mode).
