# Workspace members & roles (w4/m12)

The one multi-tenant IAM surface [w1/m9](ADR003-control-plane.md) left out: invite a teammate by email, assign one of Render's five roles, list members, change a role, and remove a member — over Core verbs that write `tenant_members` rows and OpenFGA `workspace:<id>` tuples together, with a dashboard **Settings → Team** page. It turns the role matrix OpenFGA has modelled since m4 ([ADR012-auth.md](ADR012-auth.md), `deploy/gitops/authz/model.fga`) from a static model into a populated one: a workspace stops being a single-person silo.

## The shape

One feature package, three thin adapters, Render-consistent — the same rule the rest of bex-api follows ([ADR006-bex-api.md](ADR006-bex-api.md)):

- **`lego/backend/internal/members`** — the Core verbs (`service.go`): `List`, `SeatUsage`, `Invite`, `ChangeRole`, `Remove`, `ListInvites`, `ResendInvite`, `RevokeInvite`, and `AcceptInvite` (`SeatUsage`/`ResendInvite`/`AcceptInvite` are w1/m33 — see § Parity completion). Every workspace-scoped verb targets an **explicit workspace id** and gates on _that_ workspace (`AuthorizeOn(rel, workspace:<id>)` — the mutations acting on one member/invite use `AuthorizeOnTarget`, so their audit rows carry a `member:`/`invite:` target), like the workspace-lifecycle verbs — managing members is an admin acting **on** a workspace it administers, not on its own default workspace. `AcceptInvite` is the exception by design: the token is the capability and the caller is _becoming_ a member, so its gate is only "an authenticated, onboarded caller" (`Authorize(can_view)` on the caller's own workspace).
- **`rest.go` / `graphql.go` / `mcp.go`** — the fragments. REST under `/v1/workspaces/{id}/members` + `/invites` + `/seat-usage`, plus the unscoped `POST /v1/invites/accept` (bex extensions — Render manages members only via its dashboard GraphQL); GraphQL `workspaceMembers` (carrying `workspaceSeatUsage` in the same document) / `workspaceInvites` + the six mutations (the dashboard Team page's client); MCP nine tools (an agent seats teammates the same way a human does).
- **`lego/backend/internal/store/members.go`** — the write side of membership: role update / remove on `tenant_members`, the `tenant_invites` lifecycle (incl. `RefreshInvite`), and the shared redemption core behind `AcceptInvitesForEmail` (login email-match) and `AcceptInviteByToken` (direct link). Reads (`ListTenantMembers`/`CountTenantMembers`) live in `store/workspaces.go`.
- **`lego/backend/internal/mailer`** — a provider-agnostic SMTP sender for the invite email; wired from `BEX_SMTP_ADDR`/`BEX_SMTP_FROM` (the same relay the Kratos courier uses — SendGrid in prod, Mailpit locally).

## Roles

The five Render roles, verified live (`docs/render-artifacts/team-members.graphql`) and already the FGA relations in `model.fga`:

| role | can, per the matrix ([ADR012-auth.md](ADR012-auth.md)) |
| --- | --- |
| `viewer` | read-only resource lists/details/metrics; **not** logs or sensitive fields |
| `contributor` | + logs, restart/suspend/resume, bare redeploy, cron **schedule**; **not** create/delete, sensitive fields, or **choosing the code a workload runs** (w1/m68) |
| `developer` | + create/delete, connection strings, env vars, API keys; **no** org settings |
| `admin` | full resources **and** org settings — members, billing, protected envs |
| `billing` | billing management only (Stripe onboarding/checkout/portal via `can_manage_billing`) + read-only non-sensitive names |

An API key is not a sixth role: it acts with its creator's current role in the workspace it was minted in ([§ An API key acts with its creator's role](#an-api-key-acts-with-its-creators-role-w9m481)), narrowed to the permissions it was granted ([§ An API key carries a chosen set of permissions](#an-api-key-carries-a-chosen-set-of-permissions-w9m496)).

Roles are **UPPERCASE on the wire** (Render's enum: `ADMIN`, `DEVELOPER`, …) and lowercase as the stored role / FGA relation; adapters convert at the view boundary. A change of role is a Revoke of the old relation tuple then a Grant of the new one; the `tenant_members.role` column is the source of truth, the tuple a best-effort follow-up (the resolver re-drives a missing grant on login).

### The contributor boundary: lifecycle, not code (w1/m68)

`contributor` is the "operate what exists" role, so the line bex draws is **whether the request supplies executable content**. Supplying a pre-deploy command, a cron `command`, a one-off job command, or a deploy `imageUrl`/`commitId` is create-like and needs `can_create` (developer and up); a parameter-free redeploy and a schedule-only cron change stay `can_operate`. The reasoning, and the verbs it covers, live in `lego/backend/internal/api/m68_executable_selection_test.go`, which enumerates the class so a new verb of the same shape cannot join it unnoticed — the failure mode that left four verbs behind when the class was first fixed.

**Parity note, honestly stated.** Render's dashboard descriptions for CONTRIBUTOR are not capturable from this workspace's tier (`docs/render-artifacts/team-members.graphql`: Contributor/Viewer/Billing are Scale+-gated and not selectable), so bex's exact boundary for these parameters is **not verified against Render's**. Render's public docs describe Contributor as able to deploy, which bex preserves — a bare trigger still works. What is unverified is whether Render also lets a Contributor swap the image or pin an arbitrary commit. bex deliberately does not, because that is attacker-chosen code running with the service's secrets and network identity. If a Scale-tier capture ever shows Render permitting it, this is a **deliberate divergence to keep**, not a bug to close.

The `billing` role's distinguishing capability became **live and enforced in w1/m60**: the customer-billing verbs (`internal/billing`'s `Status`/`Checkout`/`Portal`) now gate on `can_manage_billing` (`billing or admin`), so a billing-role member manages billing without workspace-admin — exactly Render's BILLING role — while staying denied every resource mutation and sensitive read. Before w1/m60 the relation was modelled in `model.fga` but had **no Go consumer** (billing verbs gated on admin-only `can_manage`), so the role's one distinguishing power was inert; the fix is the last modelled-but-dead relation gaining its consumer ([ADR012-auth.md](ADR012-auth.md), [ADR040-billing-metronome.md](ADR040-billing-metronome.md)).

### Roles are plan-gated (w6/m12)

Not every role is assignable on every plan — Render's live capture (`docs/render-artifacts/team-members.graphql`, `RESEARCH-workspaces.md` finding 5) shows the role picker itself narrows by plan: **Hobby** has no invites at all (single member, always `admin`); **Pro** offers `admin`/`developer` only; **Scale**/**Enterprise** add `contributor`/`viewer`/`billing`. bex encodes this as `PlanLimits.AllowedRoles` (`lego/backend/internal/store/plans.go`'s `LimitsFor`, alongside the member/service caps) plus a `RoleAllowedOnPlan(plan, role) bool` predicate, and enforces it in two places:

- `members.Invite` / `members.ChangeRole` reject a role outside `RoleAllowedOnPlan(tenant.Plan, role)` with a `core.ErrBadRequest` naming the plan and its allowed roles (`guardPlanRole`).
- `workspaces.Service.ChangePlan`'s downgrade guard refuses a plan change while any member holds a role the **target** plan's `AllowedRoles` no longer offers, naming the blocking member(s) — a downgrade must shed the disallowed roles first (`ChangeRole`/`Remove` them) before the plan can flip.

No migration is needed for pre-existing data: roles shipped after plans (w4/m12 came after w6/m1), so no workspace could have assigned an out-of-plan role before this guard existed.

## Invites: pending row → redeem on login

An invite is addressed to an **email**, which has no OpenFGA subject yet — the recipient may not have signed up. So an invite is a `tenant_invites` row (id, email, role, `token_hash`, `expires_at`, `accepted_at`), not a membership. The link token is stored **hashed** (sha256, w1/041 — a DB read yields no redeemable links); the plaintext exists only in flight, minted at create/resend and carried just long enough to email. It is redeemed on the recipient's **first authenticated login**:

1. The auth gate reads the caller's email from their Kratos identity traits (`internal/api/auth.go` `whoami`) and passes it — with its Kratos verified-state (`EmailVerified`) — to onboarding.
2. `tenantService.acceptInvites` (`internal/api/tenancy.go`) calls `AcceptInvitesForEmail`, which — in one transaction — turns every outstanding, unexpired invite for that email into a `tenant_members` row at its role and marks the invite accepted, then writes the matching OpenFGA role tuple.
3. Onboarding's **personal-tenant** resolution is owner-keyed (`CreateTenantWithMember`'s `owner_identity_id` upsert), **not** membership-keyed, so an invited membership never masquerades as the caller's own workspace — the admin grant stays pinned to the workspace the caller actually owns, never the one they were invited to as a viewer.

### An invite never re-roles an existing member (w1/m82)

**Inviting someone who already belongs to the workspace is refused** — `members.Invite` returns a conflict (HTTP 409 on REST, the same coded error on GraphQL/MCP) carrying `MEMBER_ALREADY_EXISTS`, matching Render's "already a member". Changing a member's role has exactly one verb, `ChangeRole`, which is audited (`roleFrom`→`roleTo`) and refuses to strip the last admin. Membership is keyed by subject while the address lives in Kratos, so the guard resolves the workspace's members through the same `Identities` seam `List` uses; without an identity reader (`BEX_KRATOS_ADMIN_URL` unset) no address resolves and the invite proceeds, because the redemption rule below holds the line regardless.

**Redemption creates memberships; it never changes one.** `store.redeemInvite` upserts `ON CONFLICT … DO UPDATE SET role = tenant_members.role` — a deliberate no-op update that keeps the existing role while still returning it — and both acceptance paths report that **effective** role, which is what the caller writes into OpenFGA, so the row and the tuple cannot disagree. The invite is still marked accepted so it stops lingering.

This replaces the original "an invite can UPGRADE an existing membership's role" behavior, which was the same write in the safe direction: `DO UPDATE SET role = EXCLUDED.role` also **silently downgraded**. Found in the 2026-08-19 dashboard QA walk — inviting an established **admin** at the invite dialog's default role demoted them on their next authenticated request (the auth gate redeems by email match, so the change landed later and nowhere the UI showed), reported to the inviter only as "Invitation sent". A role change is now impossible to trigger by accident from the invite path.

Invites expire (Render's 7 days). Delivery is best-effort: a flaky relay is logged, not surfaced — the invite row exists and redeems by email match regardless, and an admin can **resend** (`ResendInvite`, w1/m33: fresh mail, expiry pushed forward, id unchanged; a lapsed-but-unaccepted invite is revived). Since w1/041 a resend **rotates the token**: only the hash is at rest, so the original plaintext cannot be re-emailed — the freshly emailed link supersedes the original, which stops redeeming (before w1/041, the token was stored plaintext and resend kept it, so the original link stayed live). Set `BEX_DASHBOARD_URL` to give the email a sign-up deep link.

### Email verification and login-time redemption (w1/m53)

Login-time redemption (path 1–2 above) matches on the caller's Kratos **trait email**. Kratos issues a session **before** an address is verified (verification is an async flow), so on its own the trait email is not proof of ownership: if an invite is sent to an address whose owner has **not signed up yet**, an attacker could register with that address, get a session, and redeem the invite on first login — email is a unique Kratos identifier, so this window exists only for not-yet-registered invitees, but the invited role can be admin.

`whoami` therefore also reads Kratos's `verifiable_addresses` and reports `Identity.EmailVerified`. Setting **`BEX_REQUIRE_VERIFIED_INVITE_EMAIL=1`** gates login-time redemption on a verified email (`tenantService.RequireVerifiedInviteEmail`), closing the window. The gate shipped **off by default** (w1/m53) while the email-verification UX was incomplete; with the dashboard's `/auth/verification` page (w4/008, Ory Elements `Verification` over Kratos's `use: code` flow) completing the loop, **prod now sets it** (w1/040, `lego/operator/config/api/deployment.yaml`). A gate-skipped invite is not lost — it stays pending and redeems on the invitee's next login after they verify (the redemption runs on every resolver cache-miss). Deployments without a working verification UX must leave the flag unset or every invited teammate is blocked. The token path (below) is unaffected — its capability is the unguessable token, not an email claim.

**The emailed link is directly redeemable (w1/m33, dedicated handoff w11/m8).** Email now points to the exact HTTPS handoff `https://dashboard.bex.co/invite#invite=<token>`, keeping the bearer out of the initial HTTP request; an OS-verified native association or the dashboard fallback may claim it. The dashboard accepts exactly one 32-character lowercase-hex token, stores only that bearer capability in tab-scoped `sessionStorage`, applies a no-referrer policy, and scrubs the complete query/fragment before routing into sign-up or the authenticated dashboard. The token survives the Kratos/OAuth round-trip and redeems via `AcceptInvite` (REST `POST /v1/invites/accept`, GraphQL `acceptWorkspaceInvite`, MCP `accept_workspace_invite`), so an invite works even when the recipient signs up under a **different email** than the one invited — the case the email match above can never redeem. The token path runs the same accept-time plan/seat guards (`AcceptInviteByToken` shares the redemption core with `AcceptInvitesForEmail`) but refuses **loudly** where the login path skips silently. GraphQL exposes stable terminal codes `INVITE_INVALID`, `INVITE_EXPIRED`, `INVITE_ALREADY_ACCEPTED`, and `INVITE_PLAN_LIMIT`; typed store causes, not prose matching, drive them. A redeemed token is single-use. None of this changes verified-email gating for login-time email matching.

## Invitation journey for new and existing accounts (2026-09-06)

**Decision:** the browser `/invite` handoff is also the dedicated invitation review page, outside dashboard chrome. It replaces ADR076 finding 8's fixed confirmation banner while preserving its explicit token-acceptance requirement. The banner and sticky dashboard header occupied the same top edge and stacking level, obscuring the invitation and its actions. Invitation review must not compete with an unrelated workspace's navigation or resource-creation actions.

| Entry state | Journey |
| --- | --- |
| New account | Open emailed link → choose Sign up → registration and required verification → invitation review |
| Existing account, signed out | Open emailed link → choose Sign in → invitation review |
| Existing account, signed in | Open emailed link → invitation review directly |
| Signed in with another email | Show the signed-in email; permit explicit token acceptance with that account, preserving the bearer-capability contract |
| Already a member (including verified-email redemption during login) | Show the effective membership and Open workspace; do not replay acceptance or change the role |

The review page shows the validated workspace name, role, inviter email when available, and the signed-in email. A new authenticated preview verb reads the hashed token without redeeming it; it returns only invitation context and the caller's membership state. Invalid/revoked, expired, and already-used-by-another-account invitations have explicit terminal states. An accepted invitation may open the workspace only if the caller is currently a member; a spent token grants no new access. Preview is authenticated on all adapters, with tokens in request bodies rather than URL query strings, and dashboard reads are not cached.

**Existing security semantics remain:** verified-email matching can redeem outstanding invitations during authentication; token acceptance requires an explicit click and supports a different email. This change does not introduce a universal consent requirement or change the login-time redemption policy. Opening an invitation must not itself call the token acceptance mutation. Multiple links are independent; a newly opened link replaces the pending token in that tab and must never reuse stale invitation context.

**Actions and exits:** Join workspace stays visible as Joining… while pending, prevents duplicate submission, and shows failures inline. After acceptance, refresh the workspace list, confirm effective `canView` permission for the destination, wait until the workspace provider observes the membership, select the destination, and enter its overview. Selecting before the provider observes the new list can trigger its stale-list fallback to the personal workspace. If authorization/list refresh is still pending, offer retrying workspace access without replaying the committed mutation. Open workspace follows the same refresh-and-select path. Not now clears only the pending browser token, leaves membership unchanged, and returns to the previous dashboard page when known, otherwise the default dashboard. It is not a server-side decline. Normal onboarding applies when the user continues into their own workspace.

**Authentication and billing ordering:** retain the exact token in tab-scoped session storage through sign-up/sign-in/verification and account switching; scrub it from the URL before navigation. Pending invitation review takes precedence over the personal-workspace payment wall. Client navigations resolve this intent in the root authentication boundary; initial hydration checks it separately because TanStack trusts the server’s transported `beforeLoad` result. A pending browser-only token redirects to a fresh `/invite` document before hydration mounts billing. Ordinary dashboard visits retain their normal SSR shell and route-shaped loading state. Once the destination is selected, normal server-derived billing readiness and role checks apply to that workspace (ADR075 D7); invitation review does not exempt resource use from payment requirements.

**Presentation and verification:** one centered, responsive card with a named heading, account context, one primary action, and a secondary exit; no dashboard header/sidebar or overlapping fixed banner. Loading must preserve the card's geometry. Verify desktop, narrow mobile, keyboard navigation, and 200% zoom, plus local dev-7 flows for new registration/verification, existing signed-in/signed-out accounts, different-email acceptance, already-member links, cancellation, invalid/expired/revoked/used links, retry, and correct destination selection. Local email delivery uses Mailpit.

### Local verification (2026-09-06)

Verified against dev-7 with the local dashboard, real Kratos, CNPG Postgres, and Mailpit; API verification gating was enabled (`BEX_REQUIRE_VERIFIED_INVITE_EMAIL=1`). The admin's test workspace was assigned Pro directly in the disposable local database so invitations could be exercised without billing setup. Dev-7's default insecure authorization mode was retained; these browser checks establish invitation lifecycle/navigation, not production OpenFGA enforcement or Stripe payment processing.

Passed: Team UI invitation and email delivery; new-user registration and real email verification; existing-user sign-in and sign-up/sign-in switching; signed-in different-email token acceptance; automatic verified-email membership detection; correct workspace selection across reload; local dismissal and previous-page return; expired/revoked/used/malformed links; resend and token rotation; duplicate-member refusal; authentication/account switching with preserved invitation; and pending-invitation precedence before any payment-readiness request. Injected browser network failures verified retained intent, a single mutation on double click, and retrying workspace access without replaying committed acceptance. Desktop and narrow-mobile loading/ready bounds matched in light/dark presentation; keyboard actions and the effective layout at 200% zoom remained usable.

Regression coverage includes authenticated preview/error/member-role semantics, read-only hashed-token lookup and resend rotation against a separate local test database, invitation routing before payment mounting, effective authorization readiness, and the workspace-provider notification race found during the live run.

## Guardrails

- **Seat cap** — accepted members + outstanding invites both consume a seat, so a single-member (Hobby) workspace can't invite a second person until upgraded (`store.CanAddMember`).
- **Plan-gated roles** — invite/change-role reject a role the workspace's plan doesn't offer (`store.RoleAllowedOnPlan`, `guardPlanRole`); see "Roles are plan-gated" above.
- **Last-admin refusal** — the only admin cannot be demoted or removed, so a workspace is never left with no one who can administer it (`CountTenantAdmins`, `guardLastAdmin`).
- **Self refusals; the creator is an ordinary Admin** — nobody acts on their own membership through the manage-members verbs (`guardSelf`). The workspace's creator is an Admin like any other, as on Render (w5/m372): another Admin may demote or remove them and they may leave, subject only to the last-admin rule, and the store ends their onboarding binding with the change. See "The membership-invariant matrix" below for the full actor→target table and the history of the owner rule it replaced.
- **Atomic membership** — the `tenant_members` row is the source of truth; its OpenFGA tuple is kept in step (grant on accept/upgrade, revoke on remove/downgrade). Postgres and OpenFGA aren't one transaction, so tuple writes are best-effort and idempotent (check-before-grant, delete-tolerates-absent).
- **Ending a membership ends its delegated credentials (w2/m163).** Removing a member revokes the **API keys that member created in that workspace** — unbind, then delete the Hydra client, the same fail-closed order and the same `apikeys.AccountTeardown` code path [ADR086](ADR086-account-deletion.md) already uses for account deletion, narrowed by workspace. After the keys and the role tuple, and before the row, the exit stops the **agent sessions that member started in that workspace**, directly or through one of the keys it just revoked (w5/186, ADR107): a running turn would otherwise keep minting git and model credentials until its turn timeout. Every such session is flipped to canceling first, which stops its mints; a database failure there fails the exit, leaving the member in place for the retry. Each is then torn down with its descendants and records `failureReasonCode` `AGENT_SESSION_CREATOR_REMOVED`; a sandbox outage there does not fail the exit (the sandbox inventory reconciler stops a canceling session's sandbox, and a later cancel finishes it). Account deletion's offboarding does the same in each workspace that survives the account, for the sessions the person started (its keys are already gone by then).

  The gap this closes: `store.BindClient` gave every API key **its own** `tenant_members` row at role `developer` (at its creator's role since w9/m481), keyed by the key's Hydra client id. `Remove` deleted only the departing human's row and revoked only their tuple, so the key kept full developer access to the workspace its creator had just been removed from, attributed to nobody on the Team surface. Revocation that does not cover a subject's delegated credentials is not revocation.

  Scope is exactly (created by that subject) ∩ (bound to that workspace): a subject's keys in **other** workspaces are never touched, because leaving one workspace says nothing about the others. Account deletion stays global by subject, which is correct for that path. Ordering inside `Remove` is key disposal → tuple revoke → row delete, so a failure at any step leaves a retryable state with the membership still intact rather than the hole itself (membership gone, key live). A disposal failure **fails the removal** — reporting a clean removal over a credential that still authorizes is the precise lie being fixed — and the success audit row carries `revokedKeyCount` so a destructive side effect is visible afterwards. The dashboard's remove dialog states it before the admin confirms.

  Unbinding a key atomically writes its permanent `(client_id, client_id)` marker in `oauth_revocations` with deleting the binding. Every API replica checks that marker for both cached machine tokens and fresh Hydra introspection results, so the next request returns **401**, including a token used just before removal. Machine client IDs are never recycled; their markers remain terminal. Human OAuth logout keeps its existing timestamp-based cache invalidation semantics.

  **Accepted cost, recorded deliberately:** this introduces member-departure breakage — a departing engineer's key may be what a CI pipeline authenticates with. That is not in tension with [ADR078 §1](ADR078-github-workspace-connections.md)'s praise for bex _avoiding_ that failure in the git-connection model; the distinction is what the resource depends on. A git connection is bound by an admin proving they administer an installation, and no member's continued membership is part of what authorizes it — so nothing breaks when they leave. An API key **is** a delegation of one subject's authority, and `CreatedBy` is that authorizing relationship. bex avoids departure breakage wherever the resource never depended on the member, and accepts it exactly where it did. The remedy for the CI case is a key minted by a remaining admin, not a credential that outlives its authorization. (Render reaches the same end state from the other direction: its keys are user-owned and leave with the user.)

- **Deleting a workspace ends every API key bound in it (w9/120).** A key acts in exactly the workspace it is bound to, so once that workspace is gone the key has no basis left, whoever minted it. `apikeys.WorkspacePurger` runs first among the pre-cascade purgers. Each key bound there loses every role tuple and gets its permanent `oauth_revocations` marker. Then its Hydra client is deleted, and the tenant cascade drops its binding row. The row is how a retried delete finds the key again, so a failure at any step converges on the retry.

  The gap this closes: the delete revoked only the people's tuples (`ListTenantMembers` reads `kind = 'user'`), and the cascade then dropped the keys' bindings. Each key kept its tuple and its Hydra client, appeared in no key list, and `RevokeAPIKey` answered not-found for it. Render's keys belong to the user, so deleting a workspace leaves them working in the user's other workspaces; a bex key acts in one workspace (w9/118 tracks the difference).

### The membership-invariant matrix (w5/m101, 2026-09-16)

Who may act on whom through the manage-members verbs (`members.Service.ChangeRole` / `Remove` — REST `PATCH`/`DELETE /v1/workspaces/{id}/members/{subject}`, the matching GraphQL mutations, the MCP tools). Every refusal is a `core.CodedError` wrapping `ErrConflict`: REST 409, the code in GraphQL's `extensions`, and prefixed onto the MCP message. 409 rather than 403 is deliberate — the caller _is_ an authorized admin; it is the **target's** state that forbids the write.

| Target | Remove | Change role |
| --- | --- | --- |
| The workspace's creator (`tenants.owner_identity_id`) | allowed (w5/m372); the binding ends with the row | allowed (w5/m372); a demotion below admin ends the binding |
| Yourself (the caller's subject, human or machine) | `CANNOT_REMOVE_SELF` | `CANNOT_CHANGE_OWN_ROLE`, in both directions |
| The last admin | refused (`ErrLastAdmin`, 400) | refused when demoting (`ErrLastAdmin`, 400) |
| An ordinary member | allowed | allowed, subject to the plan role gate |
| A machine binding (`tenant_members` row keyed by a Hydra client id) | allowed — a client id is an ordinary subject | allowed |

**The workspace's creator is an ordinary Admin (w5/m372, 2026-11-13), amending w5/m101.** Render has no Owner role: "A workspace's creator is automatically assigned this role" (Admin), Admins change other members' roles including other Admins', and every role may leave ([render.com/docs/team-members](https://render.com/docs/team-members), read 2026-11-12). bex refused the creator's removal, demotion and leave (`OWNER_CANNOT_BE_REMOVED`, `OWNER_ROLE_CANNOT_CHANGE`, `OWNER_CANNOT_LEAVE`), and a Render client's `DELETE /v1/owners/{ownerId}/members/{userId}` on the creator got a 409 where Render answers 204. Those refusals are retired.

- **Why they existed.** `tenantService.EnsureTenant` (`lego/backend/internal/api/tenancy.go`) resolves a caller's personal workspace by `tenants.owner_identity_id` and re-grants workspace admin on every cache miss. With the binding left in place, removing the creator either never stuck (the admin tuple came back) or stranded the account (no new personal workspace, ever), so w5/m101 refused it.
- **Why they are no longer needed.** The store now ends the binding in the same transaction as the membership change, under the membership advisory lock (`store.detachOwnerTx`, shared with ADR086's `RemoveAccountMember`): on `RemoveMember`, on `UpdateMemberRole` below admin, and so on a leave. The removed or demoted creator's next session misses `TenantForOwner`, gets a newly minted personal workspace, and is granted admin there and nowhere else. A session that read the binding just before the change could grant admin just after it, so onboarding re-reads the binding after any grant it writes and revokes the grant if the binding has ended (`tenantService.personalTenant`); a remove or leave revokes the admin tuple once more after its commit, which covers a grant that landed before it (`members.endMembership`). Remove, leave and a demotion from admin evict the subject's cached resolution.
- **What stays.** Nobody removes themselves or changes their own role through the manage-members verbs (`guardSelf`; the user's 2026-09-16 request "we should not allow the workspace owner to remove itself" is kept as written), and the last human Admin can be neither removed, demoted nor leave (`guardLastAdmin` plus the in-transaction count).
- **A side effect, accepted.** A creator demoted but still a member gets a fresh, empty personal workspace on their next session as well, because their old workspace is no longer bound to them. Without that, onboarding would restore their admin role.
- **The workspace's contact email** follows the binding while it exists. Once the creator is detached it is the oldest remaining human Admin, the rule that already applied to workspaces created without a binding (w5/m103's fallback, below).
- **`isOwner`** (GraphQL `WorkspaceMember.isOwner`, the members view) stays as information: it names the bound creator while they remain an Admin. No action depends on it, and the dashboard neither labels nor restricts the row.
- **Decision state.** This follows the w5/m372 proposal's recommendation under ADR008 Render parity first and the root AGENTS.md rule that an earlier design conflicting with parity is amended. The user's explicit confirmation of amending the 2026-09-16 rule is still open; the alternative, keeping the refusals, would need the user's sign-off recorded in ADR018 as a divergence.

**Leaving is the exit (w5/m102).** `members.LeaveWorkspace` is the self-scoped counterpart to the refusals above: it takes **no subject argument at all** — the caller's identity is the subject — so no shape of the call can remove somebody else, which is what separates it from `Remove`. It is authorized as any member (`can_view` on the workspace, the `AcceptInvite` precedent) rather than `can_manage`: leaving is not managing a teammate. Its one refusal is the last admin (the shared `ErrLastAdmin` rule, 400). Until w5/m372 the workspace owner was refused too (`OWNER_CANNOT_LEAVE`); the creator now leaves like any Admin and the binding ends with the row.

It reaches `Remove`'s end state by `Remove`'s fail-closed route: dispose the leaver's API keys in that workspace (the w2/m163 rule — a credential must not outlive the membership that justified it, whichever exit was taken), revoke the role tuple, then delete the row. It is audited as its own verb, `members.Leave`, so the events feed can tell "left" from "was removed by an admin" — the caller and the target are the same subject, which is precisely the shape `Remove` refuses.

Leaving also evicts **two** caches, not one: the caller's workspace resolution (`InvalidateTenant`) and their cached membership positive for the workspace they left (`InvalidateMembership`, added here). The second was a real gap — `IsMember` caches positives for `core.PositiveTTL`, so a request explicitly naming the workspace just left kept resolving into it for up to 30 s. It was never an access bypass (OpenFGA is the gate, and the role tuple is revoked), but it is the m13 blank-switcher symptom, so both are evicted.

| Actor → target | Remove | Change role | Leave |
| --- | --- | --- | --- |
| The workspace's creator | allowed (admin only; the binding ends) | allowed (admin only; a demotion ends the binding) | allowed (self only; the binding ends) |
| Self | `CANNOT_REMOVE_SELF` → use Leave | `CANNOT_CHANGE_OWN_ROLE` | the verb's whole purpose |
| Last admin | refused | refused on demotion | refused |
| Ordinary member | allowed (admin only) | allowed (admin only) | allowed (self only) |

**A member is a person (w5/m103).** `BindClient` gives every API key a `tenant_members` row keyed by its Hydra client id, at role `developer` (at its creator's role since w9/m481) — that row is what makes the key resolve to its workspace and authorize there. Nothing distinguished it from a human's, so a bound key was listed on the Team surface, counted against the plan's seat cap, and — verified live on dev-5, 2026-09-17 — could be **promoted to admin through the member verbs**, which wrote a real `workspace:admin` tuple for the machine subject. Removing one through the same surface returned 204 and left the Hydra client alive but unbound: a key still listed on the API-keys page, silently authorizing nothing.

The discriminator is an explicit `tenant_members.kind` column (`user` | `machine`, migration 0129), written at bind time. It cannot be inferred from the subject: a Kratos identity id and a Hydra client id are both UUIDs, so any shape test would be a guess. Reads split by **intent**, not by table:

| Read | Filters `kind = 'user'`? | Why |
| --- | --- | --- |
| `ListTenantMembers`, `CountTenantMembers`, `CountTenantAdmins`, the in-transaction last-admin rechecks, `SubjectIsWorkspaceAdmin`, ADR086's "another admin remains" preflight | **yes** | each answers "who are the people here" — the Team list, the seat the plan charges for, the human who must remain able to administer or be notified |
| `GetTenantMember`, `IsMember`, `TenantForIdentity`, `TenantForKey` | **no** | each answers "may this subject act here", and a machine binding legitimately may — filtering these would break every API key |

`ChangeRole`, `Remove` and `LeaveWorkspace` refuse a machine target with `MEMBER_IS_MACHINE` (409) naming the API-keys surface. Seat usage and `CanAddMember` now count the same set, so the displayed "X of Y seats" and the invite refusal cannot disagree — the invariant this ADR already claimed.

`identityResolved: false` keeps its w4/070 meaning exactly: **a human whose Kratos identity did not resolve**. Those members stay listed, mutable and removable; they were the only thing a machine row was previously distinguishable from, and conflating the two is the regression to watch for.

Bindings written before the migration default to `user` — Hydra is the only registry of client ids, so SQL cannot classify them. bex-api reconciles them once at startup against the live client list (`store.MarkMachineMemberships`, `backfillMachineMemberships` in `cmd/api/main.go`), logged and never fatal: a failure degrades to the pre-m103 behavior rather than to a broken API.

**The workspace's owner is the owner (w5/m103).** `ownerEmail` resolves `tenants.owner_identity_id` first. It previously returned the **oldest remaining admin**, so removing a founding admin silently reassigned who a workspace appeared to belong to — on a field billing and support read. The oldest-admin answer survives only as an explicit fallback for workspaces with no binding at all (anything created through `CreateWorkspace` rather than first-login onboarding), and a workspace whose bound owner is unresolvable answers `""` rather than naming somebody else as if they owned it.

**Adding a member-mutating verb.** `TestMemberMutatingVerbsRunTheGuards` (`internal/members/owner_self_guards_test.go`) reads `service.go`'s AST and fails if a verb writes `RemoveMember`/`UpdateMemberRole` without the guards its shape calls for: a verb that takes a `subject` parameter must run `guardSelf` + `guardLastAdmin`; a self-only verb (no `subject` parameter, like `LeaveWorkspace`) must run `guardLastAdmin`. The creator needs no guard of its own since w5/m372: the store ends the binding. A self-only verb that later grew a subject parameter falls into the first branch and fails until it is guarded like one — that escalation is the thing being pinned shut. `TestEveryMembershipEndingVerbDisposesKeys` separately enumerates the exits that owe API-key disposal. Extend this matrix along with either.

## An API key acts with its creator's role (w9/m481)

**Decision (2026-11-18).** A bex API key acts with exactly its creator's **current** member role in the workspace it was minted in, following that role up and down and never more. This is Render's rule: "Your member role in the selected workspace determines which permissions you can grant an API key", "Enable all" grants "every permission your member role allows", and the FAQ "What happens to an API key if my member role changes?" answers "Your key's access adjusts to match your new member role" ([render.com/docs/api-keys](https://render.com/docs/api-keys), read 2026-11-18). Until then every key was bound as a Developer, so an Admin's key was refused the Admin-only writes Render's Terraform provider makes: webhooks, registry credentials, owner notification settings and protected environments ([checklist](terraform-compatibility-checklist.md), class 3). Render's per-resource scoped keys were not taken here; w9/m496 added them ([§ An API key carries a chosen set of permissions](#an-api-key-carries-a-chosen-set-of-permissions-w9m496)).

**Mechanism: mirrored tuples plus a request-time ceiling.** Of the two candidates (mirrored tuples alone, or mirrored tuples with a request-time cap), bex takes the second. Evaluating a key's request _as its creator_ was ruled out: the creator's tuples reach every workspace they belong to, which I2 forbids.

1. **Seat at mint.** `tenancy.BindKey` binds through `store.BindClientForCreator`, which reads the creator's own row in the workspace inside the mint's workspace advisory lock (the lock `UpdateMemberRole` takes too, so a mint and a role change never interleave) and writes the key's machine row at that role with `tenant_members.created_by` (migration 0297); the key's OpenFGA tuple gets the same role. A creator who is not a person in the workspace at a role that mints keys (Admin or Developer) is refused, and so is one whose own role intent is still queued (`ErrRoleUnsettled`, 403 "your workspace role change is still being applied").
2. **Follow every change.** `store.enqueueRoleReconciliation`, the one function every path that sets a person's workspace role writes through (`UpdateMemberRole`, invite redemption, an org workspace join), also sets the role of every machine row that person created in that workspace and queues the same intent for each key, in the same transaction. `members.ChangeRole` converges those keys right after the commit and **before** the person's own tuples (`reconcileCreatorKeys`, exact-role, check-before-write), so on a demotion no key keeps the old role longer than its creator; a retried change converges them too, and `RunRoleReconciler` converges whatever a failed write left. An organization role change sets no workspace role (ADR115: an Owner joins a workspace explicitly), so it has nothing to move. Keys bound before the column existed take their creator once at startup (`store.RecordKeyCreators`, from Hydra's `bex.co/created-by` stamp, the w5/m103 backfill's pattern). Revoking a key revokes every role tuple, not only `developer`.
3. **Cap at request time.** `core.Base.checkAuthz` and `checkAuthzFresh`, the two places every decision is made, call `keyCeiling` after an API key's own positive answer: the key's creator must hold the same relation on the same object through the same check (the cached `Check` for a read, the uncached `CheckFresh` for a write), and a workspace object must be the key's own bound workspace. The creator comes from Hydra's immutable stamp through the two-factor gate's cached lookup (`twofactor.Gate.APIKeyCreator`, `Base.KeyCreators`); a key minted by another key (possible only before codex round-7 F3) is capped through the chain, at most three links. The audit-silent projections that asked OpenFGA directly (who reads a webhook's secret, a workspace's billing figures, every sandbox) now ask `Base.HoldsFresh`, which carries the same ceiling.

**The invariants.**

- **I1, never more than the creator, now.** The ceiling is an AND over the creator's own decision at the same freshness, so a tuple that lags or fails to move (a failed revoke strands `admin` after a demotion) cannot lift a key above its creator, and the key's staleness window is exactly its creator's: 30 s of positive cache for a read on another replica, none for a write. Tested: `TestKeyIsRefusedWhatItsDemotedCreatorMayNotDo`, `TestKeyCeilingChecksTheCreatorAsFreshlyAsTheKey`, the e2e `TestAPIKeyActsWithItsCreatorsRoleE2E` (real Postgres and OpenFGA, a stranded `admin` tuple, all four writes refused on REST, GraphQL and MCP) and the property test `TestKeyNeverExceedsItsCreatorOverRandomHistories`.
- **I2, its own workspace only.** A key has a row and tuples only in the workspace it is bound to, naming another workspace is refused by membership, and the ceiling refuses any other workspace object even against a stray hand-written tuple. Its creator's roles elsewhere add nothing, because the ceiling can only refuse.
- **I3, no recorded creator, no expansion.** A key with no `bex.co/created-by` stamp is never re-seated (its `created_by` stays NULL) and the ceiling refuses it every relation a Developer lacks (`can_manage`, `can_manage_billing`, the org joins), whatever tuple it holds.
- **I4, keys still do not mint credentials.** `AuthorizeMintClass` is unchanged: a key still cannot create an API key, enroll an SSH key, invite or re-role a member, or create an organization or workspace. Only webhook create and repoint moved, to `AuthorizeExportClass` (ADR012 § 7, the `mint` operation class).
- **I5, member verbs still refuse key subjects.** `guardMachine` is unchanged: a key's role changes only through its creator's.

**Cost per key request.** One cached creator lookup (a Hydra admin GET per key and per creator once a minute per replica) and one more OpenFGA check: served from the positive cache for a read, uncached for a write, as the key's own check is. A creator lookup that cannot answer fails the request closed (503), as the login-requirements gate already did for workspaces that require 2FA.

**Production keys (read-only, 2026-11-18).** Hydra held 24 bex API keys. 16 carry no creator stamp; all 16 are `m35-*` fixtures `scripts/verify-sandbox-isolation-live.sh` minted directly in Hydra on 2026-11-15 and never cleaned up, 4 of them bound as Admin by hand. One key's creator is an operator-provisioned client (a 2026-08-03 fixture). The other 7 were minted by three people. I3 applies to the 16: none of them can act above a Developer any more, which the isolation script's own Admin principal accounts for by recording its bootstrap client as creator. Their cleanup is w9/119.

**Threats and residual risk.** A demoted creator's key is held by the ceiling at once and by its tuple once the outbox converges; a removed creator's key is revoked with the membership (w2/m163), and if that teardown fails the ceiling refuses it everything, since its creator holds nothing. The residuals are the ones a person's own session has: a read on another replica may use a positive cached up to 30 s, and Hydra's creator stamp is trusted as written by the mint (only Hydra's admin API, which bex alone holds, can change it). The review is recorded in [ADR117](ADR117-security-review-api-key-roles.md).

## An API key carries a chosen set of permissions (w9/m496)

**Decision (2026-11-18).** A bex API key carries a grant: a chosen subset of Render's per-area permissions, never more than its creator's current role, as Render's scoped keys do. Render ([render.com/docs/api-keys](https://render.com/docs/api-keys), re-read 2026-11-18): "API keys limit access to resources within a specific workspace, so you can grant each key only the permissions it needs"; the create form offers "All: Grants every permission your member role allows for every resource", "Read only: Grants Read access to every applicable resource" and "Clear all: Removes all permissions from the key"; "Your member role in the selected workspace determines which permissions you can grant an API key"; and a key's permissions change later through "the gear icon next to the key", then "Save changes". The page now names the first preset "All" where w9/114 quoted "Enable all"; nothing else changed since w9/m481 read it the same day. This section narrows § An API key acts with its creator's role: the role stays the ceiling, the grant is a second, chosen ceiling under it.

**The catalog** (`core.KeyPermissionCatalog`, pinned by `TestKeyPermissionCatalogMatchesRendersTables` against Render's tables transcribed independently). Render's areas in Render's order (Services, Sandboxes, Deploys, Monitoring, Postgres, Key Value, Object storage, Build sources, Workspaces, Projects, Environment groups, Blueprints, Audit logs), each permission with Render's name and the levels it offers (Read, Write, Read & write, Run, Execute), each level granting Render's action rows. A level is offered when it grants at least one action, so Deploys' "Run deployments" offers Run only, and Key Value's "Read Key Value connection details" Read only.

- **Render's Write-without-Read rows hold.** "Environment variables and secret files" at Write grants "Set environment variable and secret file values" and not their view; the same for Postgres credentials, build-source and environment-group values. A Write-only key's REST write echoes only what it sent; an environment group's write response, which shows the whole group, is answered masked.
- **Workflows is left out.** Workflows is off bex's roadmap ([DO_NOT_DO](../.pm/DO_NOT_DO.md)), so there is nothing to grant; recorded in ADR018.
- **Surfaces Render's table does not list take the area Render's docs put them in**, as extra actions marked `Bex`: custom domains, disks, headers, routes and maintenance are a service's configuration (Services); registry credentials and the workspace's own settings, plan and usage are the workspace's (Workspaces, which Render's docs put registry credentials and plan under). Two bex areas cover products Render does not have: **Cloud agents** (sessions, automations, skills, repository environments; agent secrets as a Write-only permission) and **Git** (connections and repositories). All grants both, as it grants everything.
- **What no grant covers** is marked `KeyNoGrant` in the operation map: API keys and SSH keys, the account, organizations, push devices and the caller's own memberships (joining, leaving, accepting an invite). Only a key whose grant is All reaches those, and then only past their own gates (I4, I5).
- **A permission no key may exercise yet is still offered and recorded.** "Update member roles and remove members" (w9/116) and "Create and delete database credentials" for a new Postgres user (w9/117) sit in the same permission rows as actions keys do use, so hiding them would hide the row; I4 and I5 keep refusing them until those items land.

**Storage.** One level per permission, stored as `"permission:level"` entries in `tenant_members.key_permissions` on the key's own machine row (migration 0300, a check keeps it off people's rows). NULL is All; an empty array is Render's Clear all. The row is the one revocation already deletes, so a revoked key's grant goes with it. A mint writes the grant after binding the key and before its secret leaves the server, and takes the key back if that write fails. Considered and not taken: Hydra client metadata (`bex.co/…`, where the creator stamp lives) is immutable in practice and read through the two-factor gate's 60 s cache, which would let a removed permission outlive its edit on another replica (I8); a separate table would need its own lifecycle and cascade beside the row that already has one.

**Enforcement.** Per operation, in the dispatch gate every surface already calls (`api.requireScopeClass`; GraphQL checks every top-level field of every selected operation against one read of the grant, so a batch cannot mix a refused field in, and a nested `envVar` or `secretFile` needs "View environment variables and secret files"). `keyPermissionOps` maps each of the 1,122 classified operations to the actions it needs (all of them), or to `KeyAnyGrant` (the caller's identity and workspace, the platform's catalogs) or `KeyNoGrant`; `TestKeyPermissionsCoverLiveOperations` fails on a live operation with no entry and on an entry with no operation, and `TestKeyPermissionWritesNeedAWriteAction` fails if a Read only key could reach any write. Rules for an entry: Render's action for the endpoint; a secret's own view for anything that reveals a value; both areas for anything that changes two (linking an environment group to a service needs both writes; applying a Blueprint needs the write of every resource kind a Blueprint creates or changes, since Render's own "Update and disconnect Blueprints" applies nothing). The grant is read uncached, one indexed lookup per request, the same cost as the revocation marker every cached token already reads (ADR012 §8d).

- **Field projections ask the grant too** (`core.Base.KeyGrantAllows`): an environment group's values on its REST read, a webhook's signing secret, the workspace's billing figures and a Blueprint's raw manifest are shown to a scoped key only when its grant covers them, beside the relation check that already caps them at the creator.
- **Side entry points.** Log tails (`GET /v1/logs/subscribe`) re-check "View service logs" on every watchdog tick. Shell, exec, file-transfer and agent-attach tickets are minted through the dispatch gate under their own actions; the streams they open are revalidated by the SSH gateway against the key's role and revocation, not its grant (ADR118).
- **Mint and edit.** `permissions` on `POST /v1/api-keys`, GraphQL `createApiKey` and MCP `create_api_key`, omitted meaning All; the gear icon is `PATCH /v1/api-keys/{id}`, `updateApiKeyPermissions` and `update_api_key_permissions`; the picker reads `GET /v1/api-keys/permissions`, `apiKeyPermissionCatalog` and `list_api_key_permissions`, each level marked with whether the caller's role may grant it. A level names the workspace relations its creator must hold (Workspaces Read & write and Audit logs need an Admin's `can_manage`; Projects Read & write a Developer's `can_create`, its protected-environment action left to the creator ceiling); a mint or edit naming a level its creator's current role lacks is `403 api_key_permission_above_role`, checked uncached. Render has no public key API, so these are bex extensions, kept additive.

**Keys minted before this section, and a mint that names no permissions, are All**: exactly what they did yesterday, every permission their creator's role allows, following that role. Render's classic keys "continue to work as usual" the same way. Old scripts and Render's Terraform provider keep working unchanged.

**The invariants** (I1–I5 of the previous section hold unchanged):

- **I6, the grant can only refuse.** A key is allowed an operation only when its grant covers every action the operation needs **and** its own relation checks pass, which `keyCeiling` caps at its creator's decision at the same freshness. No grant lifts a key past its creator, past I4 or past I5. Tested: `TestScopedKeyIsRefusedOutsideItsGrantOnEverySurface`, the e2e `TestScopedAPIKeyE2E` (a demoted Admin's key with the webhooks grant is refused) and the property test `TestKeyDecisionIsItsGrantAndItsCreator`.
- **I7, fail closed.** An operation with no entry is refused to every key whose grant is not All; a grant that cannot be read answers 503, never the creator's role; a stored entry the catalog no longer offers grants nothing. Tested: `TestScopedKeyGrantFailsClosed`, `TestKeyGrantFailsClosed`, `TestKeyGrantStorageRoundTrip`.
- **I8, a narrowing applies on the key's next request.** Changing a grant is a mint-class verb: a person only, the key's creator or a workspace Admin, validated against the creator's current role. Nothing caches the grant, so no replica keeps a removed permission at all. Tested: `TestNarrowedGrantRefusesTheNextRequest`, `TestAKeyCannotEditAGrant` and the e2e edits on REST, GraphQL and MCP.

**Threats and residual risk.** A leaked scoped key is limited to its grant, its creator's role and its workspace. The residuals are an open shell, exec or file stream outliving a narrowing until the SSH gateway's own session cap, and the per-request lookup's cost. The review is [ADR118](ADR118-security-review-scoped-api-keys.md).

## Enforcement (the definition of done)

On a cluster with OpenFGA enforced: an admin invites an email → the recipient gets the mail (Mailpit locally), signs up, and lands in the workspace at the assigned role; the [ADR012-auth.md](ADR012-auth.md) role matrix is observably enforced per role (a viewer reads but 403s on suspend / member management; a developer mutates resources but not org settings; an admin manages members); removing a member revokes their access; the last admin cannot remove or demote themselves.

## Member identity: `userId` + `email` (w6/m10)

`members.MemberView` (`lego/backend/internal/members/service.go`) carries `userId` (the opaque `own-` id) and `email` alongside `subject`/`role`/`createdAt` — the same enrichment `workspaces.ListMembers` performs for the owners read API ([ADR018-render-parity.md](ADR018-render-parity.md)): `OwnerIDForSubject` mints/resolves the `own-` id, an injected `EmailLookup` (adapted from the Kratos-admin `IdentityReader`, `BEX_KRATOS_ADMIN_URL`) resolves the email. REST, GraphQL (`workspaceMembers`), and MCP (`list_workspace_members`) all surface the same two fields off the one `List` verb — no per-surface reimplementation. Degradation is honest, not an error: with the identity reader unwired, or on a per-subject lookup miss, `email` comes back `""` and the request still succeeds; `userId` is always populated (it's minted from the control-plane store, not the identity provider). The dashboard Team page shows `email` as a member's primary identity, falling back to `userId` when email is unavailable, with the raw `subject` demoted to a secondary line.

**Unresolved Kratos identities stay as members (w4/070).** A `tenant_members` row whose Kratos identity no longer resolves is kept — deleting authorization silently is worse than leaving an admin-removable seat — and GraphQL/MCP expose `identityResolved: false` so the Team row can badge the fallback instead of looking like a normal blank email. REST keeps Render's `status: "active"` (no Render enum value for this case).

**Mutations stay subject-keyed.** `ChangeRole`/`Remove` (REST `PATCH`/`DELETE .../members/{subject}`, the GraphQL mutations' `subject:` arg, the MCP tools' `subject` param) are unchanged — a deliberate call, not an oversight: this is a bex-native contract, not a mirror of Render's `userId`-keyed REST surface (see the owners API's note in `docs/render-artifacts/owners-api.md`).

## Parity completion (w1/m33, 2026-07-16)

The gaps a live side-by-side against Render's Team Members section surfaced, closed in one pass:

- **Seat usage** — `SeatUsage` (viewer-visible, like `List`) returns Render's `owner.usage.users {used, limit}`: `used` = accepted members + outstanding invites (the exact `store.CanAddMember` formula, so the display and the refusal can never disagree), `limit` from `PlanLimits.MaxMembers` (0 = unlimited). REST `GET /v1/workspaces/{id}/seat-usage`, GraphQL `workspaceSeatUsage`, MCP `get_workspace_seat_usage`; the Team card title renders "X of Y seats" and disables the invite entry point when full (the w6/m15 blocked-invite CTA stays as the recovery path).
- **`mfaEnabled` on `MemberView`** — Render's per-member `otpEnabled`, spelled the way bex's own owners read API already spells it. The members `IdentityLookup` seam now carries `{Email, MFAEnabled}` from the same Kratos-admin credential inspection (`workspaces.KratosIdentities.Lookup`, incl. the w4/020 webauthn-stub rule); honest-false on a miss, exactly like `email`. The member row shows a 2FA badge.
- **Required 2FA (w22/m402).** A workspace admin can require 2FA ([ADR012 §9a](ADR012-auth.md#9a-workspace-enforced-two-factor-authentication-w22m402)). While it is on, the member row shows "2FA required, not enabled" for a member whose `mfaEnabled` is false, and that member (and any API key or SSH key they own) is refused on the workspace until they enroll. `mfaEnabled` keeps its meaning: an enrolled TOTP or passkey.
- **Audit rows for every member mutation** — invite / resend / change-role / remove / revoke record through the authorize interception with `member:<subject>` / `invite:<inv-id>` targets (`AuthorizeOnTarget`); Invite and ChangeRole defer their allowed row until the mutation lands (`RecordMemberInvited` / `RecordMemberRoleChanged`) so it can carry the invite id + email (`TargetName`) and the typed `roleFrom`→`roleTo` pair (migration 0040); both acceptance paths (login email-match in `tenancy.go`, token verb) record `members.AcceptInvite` with the **accepting** identity as the caller. REST audit metadata exposes `roleFrom`/`roleTo`/`email`.
- **Placement** — the dashboard Team panel lives on `/workspace/settings` (between the details card and the danger zone), where Render puts it; it had been on account `/settings` since w4/m12 (w5/m36 had recorded that as an IA choice — deliberately revisited by user direction, 2026-07-16).

## Known divergence from Render

- **No `name` trait.** bex's Kratos identity schema defines only `email` (no `name`), so nothing above ever surfaces a Render-style `user.name` — there is no field to omit-on-unset here, the trait simply doesn't exist. → future work only if a real consumer needs it. (Avatar likewise — bex has no avatar upload anywhere.)
- **Flatter GraphQL.** Render nests members under `owner.team.members`; bex has no polymorphic `owner` type, so it exposes workspace-scoped `workspaceMembers` / `workspaceInvites` queries. Field names (role, email, expiresAt, userId) match.
- **Active-workspace resolution** stays single-tenant (w1/m9): a caller resolves to one workspace for resource queries. The member verbs sidestep this by taking an explicit workspace id; a full workspace switcher is future work (the `workspaces` query already returns every membership).
- **Unresolved identity is not a Render `status`.** Render's `teamMember.status` is `active | inactive`. A Kratos lookup miss is not deactivation, so owners REST stays `active` while bex-native GraphQL/MCP carry `identityResolved`. Unresolved rows are kept until an admin removes them.

## Deploy-notification preferences are per workspace (w4/m128, 2026-09-21)

A member's deploy-email preferences (`deployStarted` / `deploySucceeded` / `deployFailed`) are **per member per workspace**, not per account. `notification_settings` is `UNIQUE (tenant_id, subject)` and `ListNotifyRecipients` — the mail fan-out — joins on that pair, so whether you are emailed about a deploy in workspace B is decided by workspace B's row.

Four parts of the product had opinions about this and only three agreed. The schema (migration 0013) and the fan-out said per workspace. The API said per account: `GetSettings`/`UpdateSettings` keyed on `Base.Tenant(ctx)` and no adapter offered an argument to name a workspace, so they always resolved the caller's **default** one. MCP said something else again — both notification tools sat in `mcpCallerScopedTools`, the list of "tools that operate on the caller rather than on a workspace".

**The API and MCP change; the schema and the fan-out are right.** Per workspace is Render's model, it is what the storage already committed to in its own header comment, and it is the only option where no data is discarded — collapsing to per account would need a migration and a rule for members holding different values in different workspaces, which is a preference change made on the user's behalf.

So: `ownerId` is an optional argument on REST (`?ownerId=`), GraphQL (`notificationSettings(ownerId:)` / `updateNotificationSettings(ownerId:)`) and, via the shared workspace middleware, MCP; omitting it keeps the previous behavior of the caller's default workspace. For an account in three workspaces, all three rows are now reachable — previously two were unreachable through any surface while all three still decided whether it got mail. A member who turned deploy-failure email off kept receiving it from their other workspaces, and nothing in the product could show them why. A single-workspace account cannot observe any of this, which is why it survived from w3/m9 to here.

**Render's `/notification-settings/owners/{ownerId}` is deliberately not the path for this.** The id in it is the same workspace id, but Render's operation there returns the owner-level object — `{ownerId, slackEnabled, emailEnabled, previewNotificationsEnabled, notificationsToSend}` — a workspace-wide policy rather than one member's own preferences, and its Slack half is a recorded non-goal. Serving a `{deployStarted, deploySucceeded, deployFailed}` body from Render's path would misrepresent two Render operations. Since w3/m271 that path serves the real owner-level object, the workspace policy a service on "default" follows ([ADR052 D2](ADR052-notifications.md)); the member-scoped query parameter still addresses the caller's own preferences.

**Known gap, recorded rather than fixed here:** the native-push half (`pushNotificationSettings` / `UpsertNotificationPushPolicy`) writes the same `(tenant_id, subject)` row and still keys on the default workspace only. It has its own shape and its own milestone; this one is about which workspace a deploy-email preference belongs to.

## Account-deletion offboarding (ADR086)

The last-admin refusal is also the account-deletion preflight: a sole-member workspace is deleted through workspace teardown, a shared workspace is left only when another admin remains, and a workspace with other members but no other admin blocks the request. Intent rechecks this matrix under deterministic membership locks so preview cannot race a role or membership change.
