# ADR: Sandbox cluster substrate — multi-node OpenSandbox, gVisor isolation, and the bex-api gateway

**Status:** accepted and implemented for create/list/get/exec/stop on the Kubernetes/gVisor substrate. m33 exec landed concurrently with the m35 security hardening, which is deployed and adversarially verified on the production gVisor/Cilium substrate (2026-07-30: the full ownership, same/cross-workspace network, DNS/FQDN/SNI egress, identity ingress, lifecycle RBAC, sandbox-Pod runtime admission, NamespaceReconciler admission, and Hubble matrix — 40 checks, clean disposable-fixture audit); the sandbox may now expand further. This ADR refines [ADR014-sandboxes.md](ADR014-sandboxes.md); Render `ea sandbox` shapes displace that ADR's original E2B lifecycle routes.

## Context

Pillar 5 (hosted agent sandboxes) was taken off the roadmap on 2026-07-08 ([`.pm/DO_NOT_DO.md`](../.pm/DO_NOT_DO.md) #18) for three reasons: the Render-alternative core was unfinished, sandboxes are a second product surface competing for worker capacity, and **the mechanism was single-host-only**. This ADR records how pillar 5 is now realized — by removing that third reason: taking OpenSandbox from a host-local Docker-runtime toy to a real **multi-node Kubernetes-runtime cluster substrate**.

Before w3/m32, bex had **no consumer of a multi-node OpenSandbox cluster** (audit captured 2026-07-27):

- The GitOps-installed controller ([`deploy/gitops/charts/opensandbox-controller/`](../deploy/gitops/charts/opensandbox-controller/)) has **zero CR instances** — installed but undriven.
- The lifecycle control-plane server runs only as a host `uvx --from opensandbox-server` process on `:8077`; there is **no container image, Deployment, Service, ConfigMap, or PVC** for it.
- Prod runs `BEX_RUNTIME=kubernetes` with **no `BEX_OPENSANDBOX_URL`** — the operator never calls OpenSandbox; it is a dev/local path only.
- The k8s-runtime path ([`deploy/opensandbox/sandbox-k8s.toml`](../deploy/opensandbox/sandbox-k8s.toml)) hardcodes `/Users/tianpan/...` paths and is blocked on OrbStack (cri-dockerd, not containerd-CRI — [ADR014](ADR014-sandboxes.md) D5).
- No `Pool` CRs, no `RuntimeClass`, no isolation boundary, no ingress/egress components.

Two refinements to ADR014 shape this design:

1. **Surface = Render CLI `ea sandbox`.** The official `render-oss/cli` v2.21.0 already ships `render ea sandbox create/exec/list/stop` → `/v1/sandboxes*`, today returning 404 ([`docs/cli-compatibility-checklist.md`](cli-compatibility-checklist.md):238-241). Making those work unmodified is bex's core parity philosophy — the sandbox becomes a Render-CLI-compatible REST surface, not (only) E2B/MCP.
2. **Isolation = strong runtime isolation now** — originally Kata, **amended to gVisor** (D3): the prod Hetzner Cloud `cpx32` nodes expose no `/dev/kvm`, so Kata (needs KVM) is impossible here; gVisor's non-KVM `systrap` platform was validated live instead. Either way, per [ADR044](ADR044-sandbox-runtime-comparison.md) pause/resume stays **rootfs-only** (runtime isolation, not memory snapshots).

## Decision

Six decisions. Directory layout follows the repo's function-based convention (like `zot`): substrate configs in `deploy/opensandbox/`, Argo-reconciled manifests in `deploy/gitops/`, the gVisor node pool in `infra/`, and the Go gateway in `lego/backend/internal/sandbox/`.

### D1 — Multi-node Kubernetes-runtime substrate (replace the single-host toy)

Deploy `opensandbox-server` (the Python lifecycle API) **in-cluster** as a Deployment + Service + ConfigMap (cluster-portable TOML) + PVC (sqlite store) + ServiceAccount/Role in `opensandbox-system`, talking to the already-installed BatchSandbox controller. A `server.Dockerfile` packages the PyPI package into an image (no official image exists today). The cluster TOML drops the hardcoded `kubeconfig_path` (in-cluster ServiceAccount), bind-mounts the BatchSandbox template as a ConfigMap, and sets `[runtime] type=kubernetes workload_provider=batchsandbox`. `BEX_OPENSANDBOX_URL` becomes `http://<svc>.opensandbox-system.svc:<port>`. The controller (not the server) now receives the snapshot registry + credential flags once the carried patch confines the commit Job to `opensandbox-snapshot` (D5, resolved w3/m42); the server's own 0.2.2 config model still has no `[snapshot]` block, so snapshot wiring lives on the controller values, not the server TOML.

### D2 — bex-api is the synchronous sandbox gateway; surface = Render CLI `ea sandbox`

A new `lego/backend/internal/sandbox/` feature package owns an **in-package OpenSandbox HTTP client** (`core.DoJSON` / `core.OryTransport` — the Hydra/OpenBao pattern; the operator's `lego/operator/internal/runtime/opensandbox.go` client is unimportable from backend by Go's `internal` rule and the `operator → types ← backend` arrow). `Create` is rewritten to be **template-based** (ADR014 D2), dropping the host-local `docker inspect` coupling; a template registry fixes image+entrypoint at registration time. The REST surface serves the **Render CLI `ea sandbox` shapes** at `/v1/sandboxes*` (create/exec/list/stop); MCP tools `spawn_sandbox` / `sandbox_exec` follow the per-feature `mcp.go` fragment. E2B parity stays deferred (ADR014 D2) — both the gRPC data plane and ADR014 D2's E2B REST lifecycle shapes: the Render shapes occupy `/v1/sandboxes*`, so E2B REST compatibility would need distinct routes if ever revived. It wires in at the five canonical insertion points (`cmd/api/main.go` env-read, `api.Deps`, `api.Server`, `NewServer`, `features()`).

**A restarting lifecycle server is a named 503, and a deploy restarts it once (w8/248, 2026-11-11).** `opensandbox-server` is one replica with `strategy: Recreate` (its sqlite store is a ReadWriteOnce volume), so each restart is a window with no server. Two things made that window a customer-facing outage on every deploy:

- **The answer named nothing.** The client returned the transport error or `opensandbox list: status N` as it was, so `bex sandboxes list`, a sandbox read and a stop answered `500 internal error` in every workspace. `sandbox.Client` now answers `503 SANDBOX_RUNTIME_UNAVAILABLE` with `Retry-After: 5` on REST, GraphQL (`extensions.code`) and MCP when the server cannot be reached (the connection is refused, has no route or is not made within 5 s) or answers a status that says it could not serve the request: any 5xx on a read, and 503 alone on a write. A read is also repeated twice, 0.3 s and 0.9 s apart within a 3 s budget, so a gap of about a second is not seen at all. A write is sent once, and after a 502, a 504 or a connection that ended it is not told to retry, because it may have been applied. A 5xx that carries the server's own error code (its pod-ready timeout is a 504) is the server answering and keeps its existing mapping. The list a create makes under the workspace's admission lock is sent once, so an outage does not hold that lock for the length of the repeats.
- **A deploy restarted the server three times.** `scripts/opensandbox-server-secret.sh` restarted it after mirroring the control-plane token, Argo CD rolled it onto the new image digest, and the deploy's "wait for OpenSandbox control plane" step restarted it again. Measured on the 2026-11-11 05:21 UTC deploy, list failed for about two minutes and then failed again a minute later. The Secret mirror now stamps the Secret's `resourceVersion` on the pod template (`bex.co/cp-token-secret-version`), which rolls the server only when the token changed, and the wait step restarts a Deployment only when it has not converged after three minutes. `scripts/opensandbox-server-secret.test.sh` covers both with a stubbed `kubectl`, and `scripts/gitops-validate.sh` fails if either unconditional restart returns.

One restart per deploy remains, because the server image is rebuilt with a new digest on every deploy even when nothing in it changed (w8/254).

### D3 — Strong isolation on a dedicated sandbox node pool — **gVisor, not Kata** (amended 2026-07-28)

Untrusted agent-generated code demands stronger-than-container isolation (ADR014 "Future considerations"; [ADR022-tenant-isolation.md](ADR022-tenant-isolation.md)). This ADR originally chose **Kata**, but Kata needs hardware virtualization (`/dev/kvm`), and **verified on prod 2026-07-28 the cluster's Hetzner Cloud `cpx32` nodes do not expose it** (no nested virt, no `vmx`/`svm`) — Kata is **impossible** on this infra. The substitute is **gVisor (`runsc`)**: a user-space application kernel that reduces the host-kernel syscall attack surface and whose `systrap` platform needs **no KVM**. Validated live on a `cpx32` node — `runsc --platform=systrap do echo` runs and a Pod reached `Running` under `runtimeClassName: gvisor`. gVisor is the non-KVM rung between ordinary `runc` and a Kata/Firecracker microVM; Kata remains the choice if KVM-capable nodes (Hetzner dedicated/bare-metal) ever join.

Ship a `gvisor` `RuntimeClass` ([`deploy/opensandbox/gvisor-runtimeclass.yaml`](../deploy/opensandbox/gvisor-runtimeclass.yaml)) and install `runsc` + the containerd runsc runtime **at node bootstrap** on a dedicated **tainted `bex.co/sandbox` node pool** (CAPH `preKubeadmCommands` in [`infra/clusterapi/overlays/hetzner-caph/`](../infra/clusterapi/overlays/hetzner-caph/)) — **not** by restarting containerd on a live node, which breaks the Cilium datapath (learned 2026-07-28). The pool must be **stable (min ≥ 1)**, not the autoscaled burst pool (an idle burst node is reclaimed, taking any imperative install with it — also learned 2026-07-28). Sandboxes run in per-tenant **`<ws>-sandbox` namespaces** ([ADR043](ADR043-tenant-namespace-isolation.md) D1/D2) on that pool, behind a Cilium egress-deny/metadata-deny boundary mirroring [`deploy/gitops/base/build-boundary.yaml`](../deploy/gitops/base/build-boundary.yaml). The dedicated pool separates sandbox capacity from the tenant pool — the original DO_NOT_DO "competing for capacity" concern.

The namespace is an administrative/workspace boundary, **not a trust boundary between sandboxes**. Every sandbox Pod is a separate hostile principal, including two sandboxes owned by different members of the same workspace. `<ws>-sandbox` therefore gets no same-namespace allow and no raw DNS allow. Sidecars belonging to one sandbox share that Pod's network namespace and need no cross-Pod exception.

The BatchSandbox template is not trusted as the runtime boundary. A fail-closed `bex-sandbox-pods` ValidatingAdmissionPolicy selects namespaces carrying the reconciler-owned sandbox regime label and rejects every Pod—including Pods created indirectly by Jobs—unless it retains `runtimeClassName: gvisor`, `bex.co/pool=sandbox` placement, the sandbox workload label, `automountServiceAccountToken: false`, and no create-time `nodeName` scheduler bypass. This prevents a compromised lifecycle server/controller from using its legitimate namespace-scoped Pod authority to fall back to runc or jump pools.

OpenSandbox's egress sidecar is not used. Its [Kubernetes network-isolation guidance](https://open-sandbox.ai/architecture/network-isolation) confirms that the sidecar depends on an `iptables` NAT redirect that gVisor's netstack does not implement and recommends a CNI-level FQDN policy such as Cilium `toFQDNs` for this combination. Cilium therefore enforces DNS, FQDN, TLS SNI, node, API-server, cluster, and metadata policy outside the guest. A missing Cilium rule fails closed through the namespace's default-deny policy.

Snapshot semantics (D5) are unchanged by gVisor: pause/resume stays rootfs-only.

gVisor is deliberately **not described as a microVM boundary**. It still relies on the host kernel beneath its application kernel and has a different residual escape surface from hardware-virtualized Kata/Firecracker. Dedicated tainted nodes, restricted Pod security, no ServiceAccount token, and Cilium policy are compensating layers; a future high-assurance tier should move to KVM-capable nodes and a microVM runtime rather than claiming gVisor provides hardware isolation.

### D4 — Security: the bex-api ↔ OpenSandbox link is a single trusted hop

The retired host-local path had **no** application-layer security: the server bound `127.0.0.1`, had no `api_key`, ran `OPENSANDBOX_INSECURE_SERVER=YES`, and relied on loopback. That is unsafe for an in-cluster Service because anyone reaching the lifecycle API could drive any sandbox. The GitOps deployment therefore enables upstream OpenSandbox's **multi-tenant mode** (OSEP-0014): an HTTP tenant-lookup provider receives the caller's `OPEN-SANDBOX-API-KEY`, returns `{namespace, ttl}` or 401, and scopes lifecycle operations to that namespace. Defense in depth mirrors the bex-api↔OpenFGA/Hydra/OpenBao pattern:

- **L3/L4** — portable ingress default-deny plus Cilium identity policy on `opensandbox-system`, admitting only the `bex-api` ServiceAccount/workload in `bex-system` on TCP 8077 and denying tenant, sandbox, label-spoofing, and other platform Pods.
- **L7** — enable multi-tenant mode with the HTTP tenant-lookup provider backed by bex IAM: bex-api mints per-workspace keys mapped to `<ws>-sandbox`, so OpenSandbox itself rejects cross-tenant operations even if bex-api bugs; drop `INSECURE_SERVER`. Key custody mirrors `BEX_OPENFGA_TOKEN` (k8s Secret + env, out-of-band).
- **East-west (load-bearing)** — a compromised sandbox must not bypass bex-api and drive the lifecycle API directly. Closed by the `<ws>-sandbox` egress-deny (D3), a portable default-deny on the server, and Cilium ingress that matches bex-api's namespace, ServiceAccount, workload identity, and TCP 8077. A Pod label alone is not treated as authentication.

#### Security principals and fail-closed rules

The protected assets are tenant source/data in each sandbox, the workspace tenant keys, the bex control-plane bearer, the Kubernetes API, node/kubelet credentials, cloud metadata, and every other tenant or platform workload. The attacker is arbitrary code with full control of one sandbox process and network stack, and may also be an authenticated ordinary member trying to operate another member's sandbox. A compromised lifecycle server is a separate trusted-component failure and must be contained to already-provisioned sandbox namespaces.

The NamespaceReconciler that creates those per-tenant RoleBindings has a separate API-server admission boundary ([ADR043 D6](ADR043-tenant-namespace-isolation.md#d6--dynamic-namespace-rbac-is-admission-confined)). Although Kubernetes RBAC must grant its `bex-api` ServiceAccount cluster-scoped namespace and named-role `bind` verbs, fail-closed CEL policies admit them only for canonical bex-managed tenant namespaces with fixed Pod Security labels, the exact sandbox `default-deny`, migration-only deletion of known legacy allows, and exact regime-specific subjects. A bex-api token therefore cannot reuse that plumbing to downgrade sandbox PSS/network isolation or bind a sandbox/Secret role into a platform namespace.

The shared OpenSandbox server, controller, and sandbox-exec SSH gateway remain part of the multi-tenant trusted computing base. Binding the same ServiceAccounts into every provisioned `<ws>-sandbox` contains their Kubernetes authority to the sandbox regime, but those RoleBindings aggregate: compromise of a shared component is **not** contained to one workspace and can affect or inspect all provisioned sandbox namespaces within that component's verbs. The exec gateway is reachable on its internal TCP 8081 listener only from the exact bex-api Cilium identity and requires a short-lived, signed, single-use command ticket; its Kubernetes `pods/exec` grant exists only through sandbox-namespace RoleBindings. Per-tenant component identities or an API-server broker/impersonation design would be required to reduce the remaining blast radius; m35 claims cluster/platform containment, not tenant containment after a trusted-component exploit.

The exact allowed flows are:

| Source identity | Destination | Port / protocol | Authentication and authorization |
| --- | --- | --- | --- |
| Authenticated external caller | bex-api public API | HTTPS → TCP 8090 | OAuth/API key/Kratos authentication, workspace membership, OpenFGA verb check, then per-sandbox owner check |
| `bex-system/bex-api` Pod | `opensandbox-system/opensandbox-server` Pod | TCP 8077 | Cilium namespace + ServiceAccount + workload identity and per-workspace `OPEN-SANDBOX-API-KEY`; no shared server key or insecure mode |
| `bex-system/bex-api` Pod | `bex-system/bex-ssh-gateway` Pod | TCP 8081 | Cilium namespace + ServiceAccount + workload identity and a short-lived HMAC-signed, single-use ticket binding caller, workspace, sandbox, namespace, and command; no other same-namespace/Traefik/monitoring Pod is admitted on this port |
| `bex-system/bex-ssh-gateway` ServiceAccount | Kubernetes API | TCP 443 | projected ServiceAccount token; `pods/exec` only through per-`<ws>-sandbox` RoleBindings after verifying the exact ticket; no Secret read and no cluster-wide binding |
| `opensandbox-system/opensandbox-server` Pod | `bex-system/bex-api` Pod | TCP 8091 | Cilium/Kubernetes pod identity plus `Authorization: Bearer <BEX_CP_TOKEN>` for tenant-key resolution |
| `opensandbox-system/opensandbox-server` Pod | CoreDNS Pod | UDP/TCP 53 | Cilium L7 DNS permits only the fixed `bex-api` tenant-resolver Service name and its deterministic resolver search expansions; arbitrary queries are denied |
| `opensandbox-system/opensandbox-server` ServiceAccount | Kubernetes API | TCP 443 | projected ServiceAccount token; cluster-wide `get/list/watch` only, with mutation granted solely by RoleBindings inside provisioned `<ws>-sandbox` namespaces |
| `opensandbox-system/opensandbox-controller-manager` ServiceAccount | Kubernetes API | TCP 443 | projected ServiceAccount token; cluster-wide informer reads omit Secrets, while pod/job/CR/status/finalizer writes exist only through RoleBindings in provisioned `<ws>-sandbox` namespaces; its system-namespace Role is Lease+event only (no ConfigMap or Pod mutation), it cannot create Pods that mount credentials there, and snapshot credential flags are disabled |
| `opensandbox-system/opensandbox-server` Pod | sandbox Pod `execd` | TCP 44772 | Cilium namespace + ServiceAccount + workload identity; no label-only Kubernetes NetworkPolicy allow, no other source is admitted, and there is no separate upstream L7 credential |
| sandbox Pod | CoreDNS Pod | UDP/TCP 53 | Cilium L7 DNS rules admit only the names the sandbox's network policy allows (any name under `allow-all`, the listed names under `allow-list`, none under `deny-all`, the platform FQDN allowlist for a pre-w32/m283 sandbox); see [Sandbox network policies](#sandbox-network-policies-w32m283) |
| sandbox Pod | platform-approved public FQDN | TLS/TCP 443 | Cilium `toFQDNs` plus exact TLS SNI; no/wrong-SNI, wildcard, non-443, private/rebound targets, and unapproved names are denied. A client may connect to a learned public IP only when it still authenticates the approved destination through SNI—the network layer cannot observe whether the socket API originally received a hostname or an IP literal |

Everything not in the table is denied, including sandbox→sandbox in the same workspace, sandbox→hosting, sandbox→platform/lifecycle API/Kubernetes API/node/metadata, public IP traffic without an approved TLS SNI, private-IP rebinding, and arbitrary DNS. The lifecycle server's own egress is default-denied outside the four dependencies above and its DNS is name-filtered; the controller has no DNS egress at all. These controls close direct internet/DNS bearer exfiltration, while the shared-component cross-tenant TCB limitation above still applies to their deliberately reachable Kubernetes/bex-api/execd destinations.

The public FQDN allowlist is destination confinement, **not DLP**. Any approved writable HTTPS service can still be used to exfiltrate data to an attacker-controlled account on that service; Cilium authenticates the destination name/SNI, not the remote account or request contents. Do not inject platform or tenant credentials into the guest. Per-destination credential brokering and an outbound content-aware proxy remain future hardening rather than claims of this boundary.

On create, bex stamps reserved `bex.co/owner`, `bex.co/workspace`, effective network-policy, plan, region, timeout, and `app.bex.co/regime=sandbox` metadata. Callers cannot supply or override that metadata. List/get/lifecycle/exec first require the exact workspace, sandbox regime, enforced `deny-all` stamp, and owner; an explicit workspace administrator (`can_manage`) may override ownership. Foreign, missing, incompletely hardened, malformed, and legacy ownerless metadata all produce the same `SANDBOX_NOT_FOUND` 404 so another sandbox's existence is not disclosed.

#### Sandbox network policies (w32/m283)

**Amended 2026-11-08 for Render parity** ([ADR008 § Render parity first](ADR008-vision.md#render-parity-first)). A sandbox's outbound posture is Render's `networkPolicy`, and the default is Render's: "a new sandbox allows outbound network traffic to any destination using any protocol" ([render.com/docs/sandboxes-creating](https://render.com/docs/sandboxes-creating)). This replaces the earlier bex-only posture, in which every sandbox was `deny-all` and `deny-all` meant a fixed platform HTTPS allowlist (GitHub, npm, PyPI and the model providers). That divergence carried no user sign-off in ADR018.

| `networkPolicy.type` | Reaches | How it is enforced |
| --- | --- | --- |
| `allow-all` (omitted policy) | any public destination, any protocol, any DNS name | the static `sandbox-egress-allow-all` CiliumClusterwideNetworkPolicy, selecting Pods labeled `bex.co/egress=allow-all`: CoreDNS with any name, and `0.0.0.0/0` / `::/0` minus every private, shared (100.64/10), loopback, link-local, multicast and reserved range |
| `allow-list` + `rules` | the listed hostnames over HTTPS (TCP 443 with a matching TLS SNI) and nothing else | a per-sandbox CiliumNetworkPolicy `sandbox-egress-<hash>` in `<ws>-sandbox`, written by bex-api before the sandbox exists and deleted on terminate: CoreDNS filtered to the listed names, plus `toFQDNs` + `serverNames` on 443 |
| `deny-all` | nothing — no DNS, no public address | no allow at all; only the structural default-deny selects the Pod |

**Rules.** Each rule is `{domain, protocol}` with `protocol` `https` (Render accepts no other). A domain is a lowercase multi-label hostname with no scheme, port or path; matching is exact (`example.com` does not cover `api.example.com`). A wildcard is allowed only as the leftmost label: `*.example.com` covers **one** subdomain level and not the apex — the TLS-certificate reading of Render's "a wildcard is only allowed as the leftmost label", rendered as Cilium's single-label `*.` pattern in both the DNS filter and the SNI match. At most 100 rules, each domain once; IP literals and `.local`/`.localhost`/`.internal`/`.cluster.local` names are refused by name (`SANDBOX_NETWORK_POLICY_INVALID`). Rules are required for `allow-list` and refused for the other two. Reads return them as Render does; they live in the per-sandbox policy's annotation, because sandbox metadata is persisted as labels.

**The floor holds under every policy.** `sandbox-egress-default-deny`'s denies take precedence over every allow: the node and other nodes, the kube-apiserver, link-local/cloud metadata, and private addresses on 443 even when an approved name resolves to one. CIDR rules never select Cilium-managed endpoints, so `allow-all` reaches no Pod, Service or other tenant — the sandbox→sandbox, sandbox→hosting, sandbox→platform and execd/agent-driver ingress rules in the table above are unchanged. Suspend and resume (w2/m278) keep the Pod's labels, so a policy survives them.

**Listed names resolve through libc (w8/m152, 2026-11-11).** Cilium's DNS filter answers every query a policy does not list with `REFUSED`. With the kubelet's default `ndots:5`, a resolver asks `example.com.<ws>-sandbox.svc.cluster.local` and the other two search-list candidates before `example.com` itself. glibc and Go's resolver go on to the name itself after a refused candidate. musl, the libc of the Alpine base image, takes the first refusal as the answer, so from the allow-list's release on 2026-11-08 `wget`, `apk` and `getent` resolved no listed name. The BatchSandbox template (`deploy/opensandbox/batchsandbox-template.yaml`) now sets `dnsConfig.options` `ndots: "1"`: a dotted name is asked as an absolute name first, and the search list applies only to single-label names. The DNS rule, `toFQDNs`, the SNI match and the admission grammar are unchanged, so nothing new can be queried or reached. `scripts/gitops-validate.sh` fails if either template loses the option, and the isolation matrix resolves and fetches the listed name through the base image's own `getent` and `wget`.

Observed on production before the change: the query `example.com.svc.cluster.local.` to the same resolver answered `NXDOMAIN` in an `allow-all` sandbox and `REFUSED` in an allow-list sandbox, so the refusal is the sandbox's policy and not CoreDNS. Writing `ndots:1` into `/etc/resolv.conf` inside that allow-list sandbox made an exact name and a `*.` name resolve and fetch, while the wildcard's apex, an unlisted name and plain HTTP stayed denied.

| Policy shape | Image and libc | Before | With `ndots:1` |
| --- | --- | --- | --- |
| Render `allow-list` (per-sandbox policy) | Alpine base, musl | affected: no listed name resolved | fixed |
| Agent session, setup and agent phases (per-session policy) | `bex-agent-sandbox`, Debian bookworm, glibc | not affected: glibc and Node's `dns.lookup` resolve registry hosts and the credential gateway past the refused candidates | unchanged, the same names resolve |
| `sandbox-egress-legacy-allowlist` (sandboxes created before w32/m283) | Alpine base, musl | affected the same way | not reached: no new sandbox takes this policy, and an existing Pod keeps the template it was created with |

The agent row was measured with the agent image's base (`node:22-bookworm-slim`) against a resolver that refuses every unlisted name, at both `ndots` values; the musl rows with `alpine:3` against the same resolver and in the production sandbox above. A sandbox created before the change keeps `ndots:5` across suspend and resume, because its BatchSandbox holds the template it was created from; it resolves listed names once it is recreated.

Two alternatives were rejected. Listing each name's three search-suffixed forms in the DNS rule would let CoreDNS answer `NXDOMAIN`, but it triples the rule (300 names at the 100-rule limit), loosens the `bex-api-sandbox-egress` grammar and ties the policy to the Pod's search list. Making Cilium answer denied queries with `NXDOMAIN` (`tofqdns-dns-reject-response-code`) is a cluster-wide agent setting applied by the cluster bring-up workflow, and it changes the answer for every FQDN policy on the cluster.

**Why allow-all is a static policy.** bex-api's ServiceAccount may write CiliumNetworkPolicies in every sandbox namespace, so a world or CIDR rule must never be something bex-api can author. allow-all is therefore a GitOps object selected by a label bex stamps through OpenSandbox metadata (which callers cannot set, D4), and the only per-sandbox object — the allow-list — is confined by the `bex-api-sandbox-egress` ValidatingAdmissionPolicy to one canonical sandbox namespace, a selector naming exactly one `sbx-` id, and exactly one filtered-DNS rule plus one FQDN+SNI rule on 443, with no CIDR, entity, service, gateway, deny or ingress section. `bex-api-session-egress` (agent sessions) is unchanged and judges every other bex-api policy write.

**Unchanged.** Agent-session sandboxes (ADR047 D5, ADR062) are never selected by `sandbox-egress-allow-all`; they keep their per-session policy and the gateway model proxy, so no platform or tenant credential is exposed to direct internet egress. A sandbox created before w32/m283 carries no `bex.co/egress` label and keeps `sandbox-egress-legacy-allowlist`, reported as `deny-all`, until it ends; that policy can be removed once no unlabeled sandbox Pod remains. Free-plan SMTP blocking ([ADR022](ADR022-tenant-isolation.md)) is a hosting-service rule on Render and is not applied to sandboxes.

#### Sandbox environment variables (w32/m297)

**Added 2026-11-09 for Render parity.** Render's create body takes `env`, a `{name: value}` map "injected into the sandbox at creation", and no Render read returns it. bex does the same on REST (`env`), GraphQL (`env: [EnvVarInput!]`, refusing `generateValue` and a repeated key) and MCP (`spawn_sandbox` `env`). The pinned CLI's `--env-var`/`--env-file` and the SDKs' `create(env=…)` work unchanged.

- **Limits are Render's:** at most 100 variables, 256 KB across names and values (render.com/docs/sandboxes-limits, checked 2026-11-09). Over either answers `400 SANDBOX_ENV_INVALID`. bex-api caps every request body at 2 MiB (`BEX_MAX_BODY_BYTES`).
- **Names and values follow a service's env rules** (`core.CheckEnvKey`): letters, digits, `-`, `_` and `.`, at most 253 characters; a value holds no NUL, and one `NAME=value` entry stays under execve's 128 KiB. Names starting with `BEX_`, `EXECD_` or `OPENSANDBOX_` (any case) are refused: those prefixes belong to the platform and to OpenSandbox's in-sandbox exec daemon, and a caller value would shadow them. Render documents no name rules, so this is a narrow, recorded divergence. A refusal names the variable, never its value.
- **Storage.** The values travel in the OpenSandbox create request and live in the sandbox's BatchSandbox and Pod spec, like a Render-style inline env. Only platform operators can read those objects; tenants never reach the Kubernetes API. No bex-api response, log line or event carries a value. The reusable BYO model key of an agent session still never enters a Pod spec (ADR047 D7); that path is unchanged.
- **Suspend and resume** recreate the Pod from the same spec (D5), so the variables survive a suspension.

#### Sandbox groups (w22/m311)

**Added 2026-11-10 for Render parity** ([ADR008 § Render parity first](ADR008-vision.md#render-parity-first), [ADR104](ADR104-sandbox-render-parity.md) D7 and gaps 2, 12 and 14). Every Render sandbox belongs to a group, a group carries a concurrency limit, and a create or resume that would pass the limit answers 429. Sources, all read on 2026-11-10: render.com/docs/sandboxes-creating and /docs/sandboxes-limits; the pinned OpenAPI (`lego/backend/internal/api/openapi/render-public-api-1.json`: `create-sandbox-group`, `list-sandbox-groups`, `retrieve-sandbox-group`, `update-sandbox-group` and the `errorCode` vocabulary); and the pinned CLI v2.35 (`pkg/sandboxgroup`, `cmd/sandboxgroups*.go`). All are single-vendor, and the product is in beta, so each figure can change. What the pages do not say is marked as a **guess** below.

**What Render documents.** Every sandbox is created in a group, and "the first sandbox group created in a workspace is the default"; a sandbox created before any group exists gets a default group made for it (the OpenAPI example names it "Default"). A workspace has at most 10 groups. Group names are unique within the workspace. `concurrencyLimit` is at least 1, capped at 1,000 "even if a higher value is sent", defaults to 1,000 and is set only through the API or SDK. "Suspended sandboxes do not count" toward it. At the limit "requests to create or resume a sandbox fail with HTTP 429", and "to resume a suspended sandbox, its group must have available capacity". Lowering the limit does not stop sandboxes that are running. The one region is `oregon`. The list returns 20 groups a page (at most 100), newest first, with a cursor.

**Decisions, one per field of the pinned group schema.**

| Field | Value |
| --- | --- |
| `id` | `sbg-<xid>`, minted only by `id.New(id.SandboxGroup)`. Render's pattern `^sbg-[0-9a-v]{20}$` is exactly xid's shape, so bex's ids need no widening (unlike `sbx-`). A malformed id is a 400 `invalid_sandbox_group_id`, Render's own code. |
| `ownerId` | the workspace's `tea-` id |
| `name` | unique per workspace, compared exactly (case-sensitive; **guess**, Render says only "unique"). 1 to 100 characters, no leading or trailing space, no control characters (**guess**: Render documents no length). A taken name is a 409 `SANDBOX_GROUP_NAME_TAKEN` (Render documents the 409 and no code). |
| `region` | always `oregon`, as Render documents it, stored and not used for placement (D7). Another value is a 400 `SANDBOX_REGION_INVALID`. A sandbox's own `region` still reports the platform region (`BEX_REGION`'s Render alias), so on a deployment outside oregon the two read differently. That mismatch is cosmetic and predates groups; align it deliberately, not here. |
| `isDefault` | true for the workspace's first group. Exactly one per workspace, enforced by a partial unique index. |
| `environmentId` | always `null`. ADR032 environments are out of scope here; Render's Dashboard menu has an optional environment on "+ New > Sandbox Group", which is a recorded gap (w22/m311 t012). |
| `concurrencyLimit` | the **effective** limit: the stored value capped by the ceiling `BEX_SANDBOX_MAX_GROUP_CONCURRENCY` (default 1,000, Render's). A new group starts at the ceiling or 1,000, whichever is lower. `PATCH` clamps a higher value to the ceiling, never refuses it, and answers the capped value; a value below 1, or none, is a 400 `SANDBOX_GROUP_LIMIT_INVALID`. |
| `createdAt`, `updatedAt` | row timestamps; `PATCH` moves `updatedAt` |

**Over the group cap.** The task started from a recommendation of 429 because the docs page gives no code. The pinned OpenAPI does: its `errorCode` vocabulary lists `sandbox_group_limit_reached`, "a sandbox group create, or a sandbox create that needs a new default group, for an owner already at its sandbox group limit", answered as a **400**, and the pinned CLI's own comment says "the API returns 409 when the name is taken and 400 when the workspace is at its group limit". bex answers that. The cap is `BEX_SANDBOX_MAX_GROUPS_PER_WORKSPACE` (default 10, `0` disables). A workspace with no group is below any cap, so the lazy default can never hit it; Render's second case cannot arise until a group delete exists (w3/m303 t003).

**The default group is created lazily.** There is no workspace-creation hook and no backfill. The default is created, named "Default", the first time a sandbox create or a sandbox read needs a group and the workspace has none. A workspace whose first group is created by hand makes that group the default, as Render says. A sandbox with no binding row (one created before this change) belongs to the workspace's default group; a resume or a create binds it explicitly. **w3/m303 t003's `default set` must bind every unbound sandbox to the old default before it moves the default**, or those sandboxes would move with it. This replaces t002's "backfill each workspace's default group and bind existing sandboxes" with the same observable result: after the change a workspace's existing sandboxes list in its default group.

**Where the binding lives: a Postgres table, not an OpenSandbox label.** `sandbox_group_members (workspace_id, sandbox_id, group_id, lease_until)` sits beside `sandbox_names`, keyed by the public `sbx-` id, with a composite foreign key so a sandbox can never be bound to another workspace's group, and cascades with the workspace. A label (`bex.co/sandbox-group`, an `sbg-` id fits a label value) would have kept OpenSandbox the one source of truth, but the race-safe count below needs a durable reservation that outlives a create while OpenSandbox's list lags behind it, and that reservation has to live beside the binding it protects. A second copy of the group in a label would be a drift risk for nothing. The cost is a table that must be pruned against the live list; the idle sweeper does that every pass, as it does for names. **Ended sandboxes (w3/m318):** OpenSandbox remains the truth for a live sandbox, but Render keeps an ended one readable, so `sandbox_records` holds each sandbox's last read shape and end time past the object's deletion (written at create, ended by terminate, the lifetime reaper and the sweeper, deleted 30 days after the end); an ended sandbox's executions are kept with it. The group of an agent-session sandbox is none: those sandboxes are not Render sandboxes, never count, and have their own cap (`BEX_AGENT_MAX_LIVE_SANDBOXES_PER_WORKSPACE`).

**Which statuses count.** Render names only "suspended". bex counts **creating, running, suspending and resuming** and does not count **suspended, errored and terminated**. A suspending sandbox still holds its pod until the commit finishes, so it counts until it is suspended; an errored or terminated one cannot run. This is bex's reading of a silence in the docs, not a Render rule, and `TestHoldsSlotStatus` pins it so a change is visible.

**Worked example (limit 2).**

| Step | Active (counts) | Answer |
| --- | --- | --- |
| create A, create B | A, B (2) | both 201 |
| create C | A, B (2) | **429** `SANDBOX_GROUP_CONCURRENCY_LIMIT`; nothing is started |
| suspend A (it settles to `suspended`) | B (1) |  |
| create C | B, C (2) | 201: a suspended sandbox does not count |
| resume A, or exec in A (which resumes it) | B, C (2) | **429**; A stays suspended |
| terminate B | C (1) |  |
| resume A | C, A (2) | accepted |
| `PATCH` the limit to 1 | C, A (2) | 200 with `concurrencyLimit` 1; **nothing stops** |
| create D | C, A (2) | 429 until the active count is below 1 |

**Race safety.** A create or resume is one critical section per workspace, under a Postgres transaction-scoped advisory lock (`sandbox-admission:<workspace>`): read the stored bindings, list the workspace's sandboxes from OpenSandbox, count, and write the binding, all before the lock is released. The lock is per workspace, not per group, because the workspace-wide cap spans groups. Parallel requests on any bex-api replica therefore queue on the lock, and each counts the effect of the ones before it. The count is the union of two things, because OpenSandbox's status is not instant:

- a sandbox whose **live status** is creating, running, suspending or resuming; and
- a sandbox with an **unexpired lease** that the list shows absent or still suspended: an admission took its slot (a create not yet visible, or a resume OpenSandbox accepted but still lists as suspended), and the list has not caught up. The lease is 7 minutes before a create (it outlasts the 330 s synchronous create), then 2 minutes once the create succeeded or a resume was accepted.

The lease is cleared when the sandbox suspends (explicitly or by the idle sweeper), the binding is deleted when it is terminated or its create fails, and an admission that already holds a slot (a repeated resume while OpenSandbox still lists the sandbox suspended) is admitted without counting itself twice. A create that timed out waiting for its pod keeps its slot until the lease ends, because the pod may still come up and must then count in the group it was created in. Nothing is counted for ever: a lease that runs out releases its slot, and a binding old and unleased and absent from the live list is pruned. The list is read inside the lock with a 10 s bound, so a hung OpenSandbox delays one workspace's creates by at most that and cannot hold the lock longer; a request that waits 15 s for the lock gives up with a retryable 503 `SANDBOX_ADMISSION_BUSY` (`TestSandboxAdmissionWaitIsBoundedPG`), because each waiter holds a pooled connection and a burst for one workspace must not starve the pool. The properties are proved against the real Postgres: `TestSandboxAdmissionNeverExceedsTheLimitPG` (the lock), `TestParallelCreatesNeverExceedTheLimit` and `TestParallelResumesNeverExceedTheLimit` (the service, with the create slowed so the list lags and with resumes the fake lists as still suspended), and `TestSlotLeaseCoversListLagAndExpires`. Removing the lock, or the lease, or the admission from one resume path, fails them.

**Every resume path is held to the limit.** The explicit `POST /v1/sandboxes/{id}/resume` and the three implicit ones (exec, and the run and file connect-token mints, which all resume through `ensureRunning`) call the same `admitResume` before the provider resume (`TestImplicitResumeIsHeldToTheLimit`). A refused resume leaves the sandbox suspended and reaches OpenSandbox not at all. A mint answers 429 itself (it starts the resume and answers at once, w32/m299), so the SDK's mint sees the refusal. Agent-session resumes are not groups' business and are untouched.

**The 429.** The body is bex's usual error envelope (`error`, `message`, `id` `too_many_requests`, `code`, `params`) because Render documents no 429 body text for a concurrency refusal. `code` is `SANDBOX_GROUP_CONCURRENCY_LIMIT` (params `sandboxGroupId`, `concurrencyLimit`, `active`) or, for the workspace-wide cap, `SANDBOX_WORKSPACE_CONCURRENCY_LIMIT`. There is no `Retry-After`: a limit does not clear with time. The error class `core.ErrTooManyRequests` is new in the shared kernel and carries the same code through REST (429), GraphQL (`extensions.code`) and MCP (the text prefix). A refusal counts as `rejected` in `bex_sandbox_create_total`, not `failed`, so a client hitting its own limit cannot raise `SandboxProvisionFailing`; `bex_sandbox_concurrency_refusals_total{limit,op}` counts them.

**The workspace cap (ADR104 D11).** `BEX_SANDBOX_MAX_ACTIVE_PER_WORKSPACE` (default **100**, `0` disables) caps the active Render sandboxes of one workspace across all its groups, counted by the same rule. Render's own ceiling would be 10 groups of 1,000, so 100 is a deliberate bex bound, **a guess** that no Render page states. It differs from Render only above 100 concurrent sandboxes in one workspace; ADR104 D11 requires a per-workspace bound whatever Render does, and the divergence needs ADR018's sign-off row. The workspace's plan quota (`store.SandboxComputeLimits`) already bounds compute, so the cap is the abuse bound before capacity, not capacity.

**Surfaces.** REST serves the four routes the pin documents (`POST` and `GET /v1/sandbox-groups`, `GET` and `PATCH /v1/sandbox-groups/{sandboxGroupId}`) and `sandboxGroupId` on `POST /v1/sandboxes` and `GET /v1/sandboxes`; a sandbox reads `sandboxGroupId`. GraphQL has `sandboxGroups`, `sandboxGroup`, `createSandboxGroup`, `updateSandboxGroup`, the `sandboxGroupId` argument on `createSandbox` and `sandboxes`, and the `sandboxGroupId` field. MCP has `list_sandbox_groups`, `get_sandbox_group`, `create_sandbox_group`, `update_sandbox_group` and `sandboxGroupId` on `spawn_sandbox` and `list_sandboxes`. `TestGroupBehaviorsAgreeAcrossRESTGraphQLAndMCP` runs twenty-two scenarios on each surface (group create, retrieve, list and update, and sandbox create, list and wake) and requires the same code, or the same normalized fields on success. Its REST leg calls the Service's router directly, so the refusals the Render request gate answers first are held to the same codes separately (`TestSandboxCLIv235FlagsReachNamedAnswersThroughTheComposedServer`: a malformed group id and a `concurrencyLimit` below 1 or absent). Without the control-plane store there is no group store: the routes answer 503 `SANDBOX_GROUPS_UNAVAILABLE`, a create naming a group is refused before anything starts, and an unnamed create works with no limit, as before. The remaining `/v1/sandbox-groups/{id}/builds` and `/snapshots` routes still answer their named 404 (ADR104 gaps 3 and 13).

**Authorization and isolation.** Listing and reading a group need `can_view`; creating one and changing its limit need `can_create`, as sandbox create and terminate do (Render documents no role rule). A by-id route resolves the group's own workspace through a routing read and then authorizes there; a group in a workspace the caller does not belong to answers the same `SANDBOX_GROUP_NOT_FOUND` as one that does not exist, as sandboxes do (`ScopeByVisibleID`).

**Compute and egress bounds (ADR104 D11, w22/m311 t006).** The workspace cap above is the compute bound. **Egress is not metered for sandboxes, and no alert is added.** The operator's `egress-meter` lists pods by the label `app.bex.co/app` and attributes bytes by `bex.co/app-id` (`lego/operator/internal/egressmeter/meter.go`, `reconcilePods` and `desiredPodResources`); a `<ws>-sandbox` pod carries neither (its labels are the `bex.co/*` metadata bex stamps, `app.bex.co/regime=sandbox` among them), so the meter never sees a sandbox's egress and `bex_app_direct_egress_bytes_total` has no sandbox series. cAdvisor does not fill the gap either: the `kubernetes-cadvisor` job drops every series with `container=""`, and cAdvisor reports pod-level network counters on such series, so no per-pod transmit series is kept (read from the scrape configuration, not checked against a live scrape). An alert on a series Prometheus never holds would report health it cannot observe (the rule `scripts/gitops-validate.sh` already states for w5/m95), and a promtool test on a synthetic series would pass without proving that. The follow-up is an operator change: let the meter select sandbox pods (label `app.bex.co/regime=sandbox` and `bex.co/sandbox-id`, attributed to the workspace's sandbox namespace), after which the alert, its promtool test and its Grafana panel (ADR088 § 6) are small. Until then D11's egress clause is open.

**Not verified offline.** Live Render's behavior was read from its pages and its OpenAPI, not exercised: whether a `suspending` sandbox counts there, the 429 body text, whether `sandbox_group_suspended` (which the pin documents on create and connect) has a group-suspend operation behind it (the pin has none, so bex never answers it), and the name rules above. The production walk with the unmodified CLI is w22/m311 t007.

### D5 — Snapshot semantics: v1 is rootfs-only; memory hibernation is a watch item

The k8s BatchSandbox pause/resume commits the rootfs to an OCI image and recreates the pod ([ADR044](ADR044-sandbox-runtime-comparison.md)); gVisor does not change this. So v1 "sleep = free" preserves the **filesystem only — memory and processes do not survive pause.** This is weaker than E2B's memory hibernation and weaker than the single-host Docker path ADR014 D5 described. The k8s-native path to memory hibernation is containerd checkpoint/restore (CRIU) — recorded as a watch item, not v1 work.

**Blocked on prod by the per-tenant PSS floor (found w3/m32/t007, 2026-07-29).** Once sandboxes run in the per-tenant `<ws>-sandbox` namespace (ADR043/m31), pause fails: the OpenSandbox controller's snapshot **commit Job mounts the node `containerd.sock` via a `hostPath` volume** to export the rootfs, but `<ws>-sandbox` enforces PodSecurity **`baseline`**, which forbids `hostPath` — so the commit pod is rejected (`FailedCreate … violates PodSecurity "baseline": hostPath volumes`) and the sandbox hangs in `Pausing` indefinitely. Create/list/exec/stop are unaffected (validated). The two ways forward, neither v1: (a) run the privileged commit Job in a dedicated platform namespace (not the tenant's) — an upstream OpenSandbox change, since it currently creates the Job in the sandbox namespace; or (b) relax the sandbox-namespace PSS to admit the commit Job — **rejected**, it would let every untrusted sandbox pod mount `hostPath`, dissolving the isolation floor. This strengthens D5's original "watch item" call with a concrete mechanism.

**Option (a) implemented (w3/m42, 2026-08-01; ADR047 gap 2).** A carried patch (`deploy/opensandbox/patches/controller-snapshot-job-namespace.patch`, intended as an upstream PR) adds a `--snapshot-job-namespace` controller flag: when set, the commit/unpause Jobs run in one dedicated platform namespace — `opensandbox-snapshot`, created by the vendored chart with PodSecurity `privileged` labels and a Job-scoped Role for the controller ServiceAccount — instead of the tenant's. Cross-namespace owner references being invalid, Job→snapshot linkage moves to labels (`sandbox.opensandbox.io/sandbox-snapshot-namespace`) and cleanup keeps the upstream TTL + explicit-delete paths; commit pods stay pinned to the source node by `spec.nodeName` (which also bypasses the sandbox pool's `NoSchedule` taint, and stays outside the `bex-sandbox-pods` admission policy since the platform namespace carries no `app.bex.co/regime=sandbox` label — that policy's `nodeName` denial is a second, independent reason the Jobs could never run in tenant namespaces). In this mode the patch also nests snapshot repositories under the sandbox's source namespace (`<registry>/<ws>-sandbox/<sandbox>-<container>`) so registry pull ACLs can be scoped per tenant. deploy.yml builds `ghcr.io/bex-co/opensandbox-controller` from the pinned upstream commit + patch (signed, scanned, digest-written-back).

**Verified resolved on prod (w3/m42 t002, 2026-08-02).** `scripts/verify-sandbox-pause-resume-live.sh` passed against the production gVisor substrate: create → rootfs marker → pause (pod deleted, commit Job confined to `opensandbox-snapshot`, snapshot `Succeed`, pushed to the per-tenant Zot repo) → resume (pod recreated from the snapshot image via the per-workspace pull credential) → marker intact. The full credential chain is live: `bex-snapshot-push` (out-of-band, `scripts/snapshot-registry-secrets.sh`; bex-builder adminPolicy) for the commit push, and per-workspace resume-pull Secrets minted/revoked automatically by the operator's `SandboxNamespaceRegistryReconciler` (read-only `snap-<ns>` Zot users scoped to `snapshots/<ns>/**`; RoleBindings stamped by the NamespaceReconciler under the bind-allowlist admission policy). Two substrate findings from the live bring-up: (1) **runsc's default memory-backed rootfs overlay silently defeats commit-based snapshots** — tenant writes never reach the host containerd rw layer, so sandbox nodes run `--overlay2=none` (runsc.toml at node bootstrap, `infra/clusterapi/overlays/hetzner-caph/sandbox-pool.yaml`; slower FS I/O, correct hibernation); (2) **gVisor mounts `/tmp` as an internal tmpfs**, so `/tmp` state does not survive pause by design — a documented tenant-visible semantic. The "sleep = free" economics are unblocked.

**Driven by idle suspension (w2/m278, 2026-11-07).** bex-api now pauses a sandbox after Render's `idleTimeoutSeconds` (default 900) with no exec or file transfer, and resumes it on the next one ([ADR014 D4](ADR014-sandboxes.md#d4--idle-hibernate--gateway-observed-autopause)). The lifecycle server's phases map onto Render's statuses: `Pausing` → `suspending`, `Paused` → `suspended`, `Resuming` → `resuming`. Pause and resume answer 202 and 409 for a phase that refuses them, and bex treats a 409 as another replica already moving the sandbox. This D5 semantic is therefore tenant-visible on Render's surface: an idle-suspended sandbox keeps its root filesystem but not its memory, processes or `/tmp`, where Render keeps all three. ADR018 § Sandbox create flags records that as a divergence awaiting sign-off; memory hibernation (CRIU) remains the watch item that would close it. The BatchSandbox controller deletes a sandbox at `spec.expireTime` even while it is paused. So bex-api renews the expiry through the server's `renew-expiration` route: to the pause + 30 days before a pause, and to the resume + timeout after a resume (w2/m278 t010, ADR014 D4).

**Memory and process survival: feasibility (w2/m322 t001, 2026-11-11).** The user funded it (w2/m278 D1=A), because Render resumes an idle sandbox "with its files, memory, and running processes intact". The production substrate is `gvisor`/`runsc` under containerd 2.3.3 (`bex-sandbox-*` nodes).

What exists:

- `runsc checkpoint`/`restore` work from the runsc CLI ([gVisor checkpoint/restore](https://gvisor.dev/docs/user_guide/checkpoint_restore/)). Since [gvisor#15551](https://github.com/google/gvisor/pull/15551) (merged 2026-10-16, in release-20261019.0 and later), they can take a whole pod sandbox with `--no-root-container`.

What does not:

- Kubernetes drives runsc only through `containerd-shim-runsc-v1`, which answers the task Checkpoint RPC with `ErrNotImplemented`. containerd's CRI `CheckpointContainer` is unimplemented for runsc ([containerd#12280](https://github.com/containerd/containerd/issues/12280), open).
- The kubelet's checkpoint API is CRIU-based and cannot take a gVisor sandbox.
- Shim-level checkpoint/restore is [gvisor#14760](https://github.com/google/gvisor/pull/14760), open since 2026-09-15. An earlier attempt ([gvisor#13326](https://github.com/google/gvisor/pull/13326)) was closed unmerged.
- A community patched shim exists ([runsc-task-restore](https://github.com/mayur-tolexo/runsc-task-restore), a POC tested on kind).

Constraints on any route:

- A checkpoint image can be read only by the exact gVisor build that wrote it, so every build that wrote a live checkpoint must stay installed.
- Restore checks the target host's CPU features.
- Open sockets reset on restore.

**Conclusion:** no upstream route exists today. The only carriable route is a bex-maintained patched runsc shim on the sandbox node image. Whether to carry it, or wait for gvisor#14760 to merge, is a user decision recorded on w2/m322.

### D6 — Validate on real containerd-CRI, not the OrbStack mock

The BatchSandbox snapshot path does **not** work on `scripts/mock-cluster.sh` (OrbStack/cri-dockerd), and that local cluster has neither Cilium nor runsc. Security validation therefore needs a real containerd-CRI+Cilium+gVisor node. The DoD loop is create → execute adversarial probes → stop/delete under gVisor; pause/resume is verified separately on the prod gVisor substrate (D5, resolved w3/m42) since the OrbStack mock lacks the containerd-CRI + runsc `--overlay2=none` prerequisites the snapshot commit needs.

## Alternatives considered

- **Keep the single-host Docker runtime** — rejected. No HA, no multi-node, host loss loses all sandboxes and snapshots. This was the mechanism gap that paused pillar 5; D1 removes it.
- **AgentENV / Firecracker substrate** ([ADR044](ADR044-sandbox-runtime-comparison.md)) — rejected for bex: Rust node, prototype in-memory control plane, no client surface; would trade a working integration for a substrate rewrite and a second non-k8s scheduler. Tracked as the reference design for memory snapshots and microVM isolation.
- **Ordinary container isolation (build-boundary) instead of gVisor** — rejected for pillar 5. Sandboxes run **untrusted agent-generated code**; gVisor's user-space kernel adds a syscall boundary that a runc container does not. The build-boundary pattern is still reused for namespace and egress isolation underneath it.
- **E2B-SDK as the primary surface** — deferred. Render-CLI compatibility is bex's parity philosophy and the `render ea sandbox` commands already exist as 404s to close; E2B's gRPC data plane is deferred per ADR014 D2.
- **`Sandbox` CRD reconciled by the operator** — rejected in ADR014 D0. Sandboxes are interactive, ephemeral sessions; async CR reconcile fights synchronous create/exec/connect.

## Consequences

- A new `opensandbox-server` container image must be built/sourced (D1).
- gVisor node-image work (CAPH `KubeadmConfigTemplate` + the stable sandbox pool) is the long pole and the riskiest piece (D3).
- bex-api gains a direct-runtime responsibility (an OpenSandbox client) — a documented, sandbox-scoped exception to the operator-is-the-only-mechanism rule (ADR014).
- v1 "sleep = free" is **rootfs-only**; the memory-hibernation story is honestly weaker than E2B's until CRIU lands (D5).
- `.pm`: a dated (2026-07-27) re-open clause on `DO_NOT_DO.md` #18 + a fresh milestone (not a reuse of the removed `w2/m3`); ADR014 status amended to match.
- Validation is gated on a real containerd-CRI node (D6) — the local mock cannot close the snapshot DoD.
- Three watch items carry forward: containerd/CRIU for k8s memory hibernation (D5); the bex-api↔OpenSandbox link stays single-hop-only as the sandbox tenant boundary hardens; and the warm `Pool` (D1) pre-warms capacity in `opensandbox-system` — under per-tenant `<ws>-sandbox` scoping (D3/D4) a tenant's create cannot draw from a pool in another namespace, so pool-backed create latency needs a per-tenant (or claim-time-move) warm strategy before it helps multi-tenant traffic.
