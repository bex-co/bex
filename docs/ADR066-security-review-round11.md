# ADR066: Security review round 11

**Status:** Accepted (2026-08-17) **Scan:** codex-security `gzqd2O` (2026-08-17), repository snapshot `f8283a3`.

## Context

Eleventh pass in the ADR028 → ADR045 → ADR055 → ADR056 → ADR057 → ADR072 → ADR061 → ADR063 → ADR064 lineage. The scan reported 10 findings (1 high, 5 medium, 4 low). Triage verified each against source; 7 were fixed in place with regression tests, 1 is a partial fix with a structural follow-up, 1 is a deferred repeat of the standing digest-pinning inventory, and 1 is accepted product behavior.

Headline: the round's only high was a real bypass of the codex-F1 protected-secret guard — the validator enumerated the spec's secret-reference fields but not the two pending-projection annotations that `runtimeEnvSecret`/`secretFileMounts` project exactly like them, and the operational Secrets bex-api mints (`<app>-clone`, `<app>-registry-pull`) plus the operator's `reg-pull-<name>` carried no protected label at all. All three close under one contract change: the label moves to the shared `types/` module, every credential materializer stamps it, the validator covers annotations, and the operator's configured out-of-band secret names are denied by name.

## Dispositions

### Fixed in place

**1 — App CR secret-reference validation bypassed via pending annotations / unlabeled operational Secrets (high, medium confidence). CONFIRMED.** The F1 guard (`rejectProtectedSecretRefs`) covered `spec.envFromSecret[s]`, `filesFromSecrets`, and per-variable `secretKeyRef` — but `app.bex.co/pending-env-secret` and `app.bex.co/pending-files-secret` are consumed as kubelet-projected Secret references (`runtimeEnvSecret` → envFrom, `secretFileMounts` → the `/etc/secrets` volume) and were absent from the validated set; a hand-applied App CR could name the labeled backup credential through either annotation. Separately, the clone token (`lego/backend/internal/apps/clonesecret.go`), the external-registry pull credential (`lego/backend/internal/registrycreds/pullsecret.go`), and the operator's per-App Zot credential (`lego/operator/internal/registry/creds.go`) were never labeled, so a plain `spec.envFromSecret` reference mounted them.

Fix: `LabelProtectedFromTenantMount`/`ProtectedFromTenantMount` move into `lego/types/v1alpha1` (the leaf contract both modules import; the operator's `execution` constants become aliases); all three materializers stamp the label at creation (the operator backfills it on pre-existing pull secrets); the validator enumerates both pending annotations; and the operator-configured out-of-band names (`BEX_REGISTRY_PULL_SECRET`, `BEX_REGISTRY_PUSH_SECRET`, `BEX_REGISTRY_BUILD_PULL_SECRET`, tenant signing key) are denied **by name** — no Secret object needs to exist for the refusal to hold. `imagePullSecret` resolution ignores labels, and `spec.cloneSecret` is wired only into build-plane pods, so neither legitimate consumer regresses. Tests: `protected_secret_test.go` gains the two annotation vectors + configured-name vectors; backend clone/registry tests assert the label. Severity note: exploitation requires a principal with App-CR write but no Secret read in the namespace (the delegated-writer boundary the lineage has tracked since ADR055); the fix removes the bypass under that threat model rather than assuming it away.

**2 — SSH pre-auth pool admission starvation (medium, high confidence). CONFIRMED, fixed.** The global `BEX_SSH_MAX_PREAUTH_CONNS` semaphore (an earlier round's own control) had no per-source fairness: one address holding `MaxPreAuthConns` silent connections for the 10s handshake deadline sheds every other tenant's handshakes. Fix: `sshgateway.SourceLimiter` (the SessionLimiter/ChannelLimiter shape) acquired after `proxyproto.Wrap` resolves the real client — so the cap keys on the Traefik-asserted source, not the proxy pod IP — released with the global slot; `BEX_SSH_MAX_PREAUTH_CONNS_PER_SOURCE` (default 32, negative restores global-only), metered `bex_ssh_limit_rejected_total{scope="preauth_source"}`. Mirrors the per-source admission the git/model proxies already had. Residual: a source-IP-rotating flood is an edge/LB concern, same as the SNI proxies' posture.

**4 — Custom maintenance pages exhaust the shared activator (medium, high confidence). CONFIRMED, fixed.** Every public request to a maintenance host built a fresh `http.Transport` and fetched the tenant-configured origin synchronously — unauthenticated traffic converted into unbounded activator sockets/goroutines. Fix (all SSRF/redirect/size validation unchanged): a process-wide `customPageCache` — per-URI `singleflight` + 30s TTL snapshots (bounded at 256 entries), a 16-slot global origin-fetch semaphore, one pooled shared transport, and a 10-minute stale-on-error window. Tests: a 50-request concurrent flood for one URI performs exactly one origin fetch; expired snapshots refresh; origin failure serves the stale snapshot inside the window and surfaces beyond it; 64 distinct slow URIs never exceed the concurrent-fetch cap.

**5 — Stale cached `can_manage` in the sandbox owner override (medium, high confidence). CONFIRMED, fixed.** `isWorkspaceAdmin` — the cross-owner override behind `ownedSandbox`, which gates exec-ticket minting and lifecycle verbs on other members' sandboxes — used the cached `Check`, so a demoted admin could ride a positive cached on another API replica for up to `PositiveTTL` (30s). Fix: the override consults `core.FreshChecker.CheckFresh` when the wired checker supports it (degrading to `Check` for uncached checkers), completing the round-5/8/9 fresh-authz seam at this sink. Test: `staleAdminChecker` (cached yes, fresh no) loses cross-owner get/terminate while the owner path is untouched.

**6 — Unbounded aggregate secret maps (medium, medium confidence). CONFIRMED, fixed.** Per-key `SetEnvVar`/`SetSecretFile` writes merged into whole-map objects with no count or byte bound; beyond the amplification cost, a map past Kubernetes' 1 MiB Secret ceiling wrote to OpenBao first and then failed at the projection (source/projection divergence). Fix: aggregate quotas — 500 keys / 512 KiB per service for env vars and for secret files — enforced inside the CAS mutate (re-checked on every retry), on batch replacement, and on blueprint seeding, before any write; OpenBao response bodies decode through an 8 MiB `io.LimitReader`. Tests: cap-refused writes never reach the store; deleting frees room; oversized values and batches are refused. **Missed alias, closed in w1/m147 (2026-09-15).** The fix above changed `files.go`/`service.go`/`store.go` but not `batch.go`. The batch `PatchEnvironment` behind REST `PATCH /v1/services/{id}/environment`, GraphQL `patchServiceEnvironment`, MCP `patch_service_environment` and the dashboard's Environment editor therefore wrote both maps with no check, and a 614,400-byte secret file was stored and deployed on production. Both of its mutates, and the revision-aware path, now check the resulting map before any write. A map already over quota can shrink but not grow. `secrets/quota_guard_test.go` and `envgroups/quota_guard_test.go` drive every exported map writer with an over-quota input, and fail when a writer-named verb has no case, so the next alias fails CI instead of production. **Secret files take their own bound, w4/m363 (2026-11-14).** Secret files now have a contents-only bound of Render's 1 MB combined, as 1 MiB (1,048,576 bytes); names do not count. The 500-file limit stays. Environment variables keep 500 keys and 512 KiB of names plus values. The earlier rationale ("512 KiB per map keeps the base64 projection inside a 1 MiB Secret") did not hold. Kubernetes stores a Secret's `Data` as raw bytes, and base64 is only its JSON wire form. `k8s.io/api@v0.37.1` `core/v1/types.go:8288` says "The total bytes of the values in the Data field must be less than MaxSecretSize bytes", with `MaxSecretSize = 1 * 1024 * 1024` at `:8326`; keys are not counted. The apiserver refuses only a total past that number. The operator envtest `secret_files_bound_envtest_test.go` pins this against a real kube-apiserver and etcd: values of exactly 1,048,576 bytes under 500 keys of 253 characters are accepted, and 1,048,577 bytes are refused as Invalid. So a files map at the bound still fits the one `<name>-files` (or `<evg-id>-files`) Secret it projects into, and this finding's source/projection divergence cannot recur. That Secret holds nothing but the files: revision stamps are annotations, which the limit does not count. The one place several maps share a Secret is a build's merged secret files. The operator packs them into as many `bld-…-native-files` Secrets as needed, each at most `MaxSecretSize` of values and 500 keys. Production etcd's `--max-request-bytes` was not read. A full Secret plus its managed fields is about 1.3 MiB, under etcd's 1.5 MiB default, which the envtest's etcd runs with.

**9 — Database export history grows without retention (low, high confidence). CONFIRMED, fixed.** `CreateExport` appended to `spec.exports` forever; every reconcile and list traversed the full history. Fix: `pruneTerminalExports` keeps all non-terminal requests plus the newest 10 terminal ones (failed/expired) at each create; the operator's status mirror already drops entries absent from spec. Artifacts of pruned entries are unaffected (expiry is operator-driven from observed entries). Test: 15 expired + 1 available + 1 new ⇒ 12 entries, the available one retained.

**10 — Cached mobile OAuth callback restores a session after logout (low, high confidence). CONFIRMED, fixed.** `ExpoOAuthTransport.completeAuthorization` memoized the resolved token-set promise by exact callback URL indefinitely, and logout never cleared it — replaying the exact prior deep link bypassed pending-state/PKCE/nonce checks and re-persisted the old tokens. Fix: `OAuthTransport.reset?()` drops the memoized completion; `SessionManager.clearLocalSession` invokes it on every terminal boundary (sign-out, invalid-grant, forced clears). The memo itself is retained **within** an authorization: the active AuthSession and the Expo Router deep link both observe one native callback and must converge on a single code exchange, so clearing it eagerly would break sign-in; the reset boundary is what makes the memo authorization-scoped instead of process-scoped. Tests: reset fires on sign-out and on the forced-clear path.

### Partially fixed (structural follow-up recorded)

**3 — Env-group reads scan global OpenBao metadata before tenant filtering (medium, high confidence). CONFIRMED; path migration closed by w2/m80; the scan itself removed by w8/m114, which moved group metadata into the control-plane store — a list is now one indexed query and reads no OpenBao path ([ADR013](ADR013-secrets.md)). The history below describes the KV layout it replaced.** Group metadata lives in one shared index (the pre-w7/m70 layout), so every list/name-resolution/membership read did one OpenBao metadata read per global group before the workspace filter, and creation had no quota — a tenant-driven cross-tenant amplification. Fix shipped now: a per-workspace create quota (`BEX_MAX_ENV_GROUPS_PER_WORKSPACE`, default 100, 0 disables; refusal `ENV_GROUP_LIMIT` across REST/GraphQL/MCP, best-effort like the blueprint cap). **w2/m80** then closed the structural deferral itself: env-groups now write under their own workspace-prefixed OpenBao tenant via the same `withTenant` seam w7/m70 gave services (`secrets.WithTenant`/`TenantFromContext`), with a thin legacy-tenant locator so a bare-gid lookup still resolves, dual-read fallback for a not-yet-migrated group, and prefix-scoped lists (`listGroupIDs`) that union the legacy tenant only for entries whose legacy copy is still full content — never for a locator, which would otherwise force a cross-tenant read to resolve. The one-time `MigratePaths` sweep (env-gated `BEX_ENV_GROUP_PATH_MIGRATION=dry-run|apply`, wired next to the existing name-claim audit in `cmd/api/main.go`) moves any remaining legacy-resident group; see `docs/runbooks/env-group-path-migration.md`. The interim 15s metadata-snapshot cache (`metaCache`) is retired — a scoped list's own walk is now bounded by the target workspace's own group count (the create quota above), so the extra caching layer no longer earns its complexity against the new dual-read semantics. Content hydration (2 reads per matched group, capped at 200 by codex #10) is unchanged.

### Deferred (standing inventory, fourth report)

**7 — Mutable backup helper images touch plaintext KeyValue snapshots (low, high confidence).** `busybox:1.37`, `alpine:3.21` + runtime `apk add age`, and the version-derived Valkey image in the KeyValue backup CronJob are the same digest-pinning inventory item deferred through ADR055 F7 → ADR061 #1/#12 → ADR064 and re-confirmed here: the remediation is a first-party pinned backup image (preinstalled age + gzip + valkey-cli), which belongs to that inventory, not a one-off pin. No new exposure relative to the standing item.

### Accepted

**8 — Opening an invite URL auto-joins the authenticated visitor (low, high confidence).** Bearer-link semantics are the designed invite model (ADR024; the redemption hook's own contract documents joining "even when the caller signed up under a different email", and Slack/Render invite links behave identically). The "attacker" must be a workspace admin who creates an invite for an email they already know and induce a click; the victim's exposure is membership in the attacker's workspace (no cross-workspace credential or data access; joining provisions nothing billable — ADR046 gates paid intent on a payment method). If invite-driven joins ever gain financial or trust consequences, revisit with a workspace/role confirmation step at redemption.

## Amendment 2026-11-14 (ADR110, R25-12)

The residual above, and finding 2's, rest on "edge/LB rate limiting" covering source-rotating connection floods at the SNI-proxy posture. That premise is false: the Hetzner load balancer has no L4 connection limiter, nothing else in the repository provides one, and no alert watches `connections_rejected_total`. The SNI proxies take one global slot at accept, before the PROXY header and SNI are read, so a few sources hold every slot for the 10-second handshake deadline (reproduced on the real `pg-sni-proxy`: a legitimate client served 25 of 25 before and 1 of 74 during the hold). The residual stays accepted, with the control in the pod: per-source counting now keys an IPv6 address on its /64 (w21/m394 t017), and a per-source cap before SNI resolution, a 2-second pre-header deadline and a rejected-connections alert are w21/070.
