# Product adoption at obs.bex.co

[Product adoption](https://obs.bex.co/d/bex-product-adoption/product-adoption) is inventory-first: **customer inventory, growth, and provisioning health**. It answers what exists, how many workspaces own it, what changed, and whether resources reached readiness. It is an ops-only Grafana dashboard, not a tenant analytics API, human-activity counter, uptime report, or replacement for the platform/build dashboards.

## Definitions and scope

The default range is 30 days, UTC, with a five-minute refresh and daily points. **Min interval** can be changed to one hour or five minutes. Longer ranges automatically coarsen: at least hourly beyond three days, daily beyond 40 days, and whole-day multiples beyond 1,000 days. Each main series is bounded to 1,001 points; coarsening still uses bucket-end snapshots, never sums or daily peaks. The main panels respect the selected end, including collection coverage and the seven-day comparison. Each point uses the latest complete source snapshot within 15 minutes of the bucket end; the final partial bucket ends at the selected end. Missing, failed, or stale samples are gaps, never zero or a line carried forward. The legend uses the last value, including null, not the last non-null value.

The main layout is collection coverage → services/datastores → workspace reach/domains → observed changes/resource state → provisioning progress/timing → range-end inventory and seven-day net change. Creator counts, activation, deployment outcomes, historical hosting and creation cohorts remain in a collapsed **Adoption detail** row. Its explicitly labeled current domain panel ignores the historical range. Global collection coverage ignores product filters. Historical domain adoption applies audience/time but not service-type selection.

### Main inventory panels

| Measure | Meaning |
| --- | --- |
| Services over time | Persisted App rows, split into static, web, private, worker and cron. Failed, suspended and not-yet-projected Apps still exist. Kubernetes readiness does not determine inventory membership. |
| Datastores over time | Complete, paginated authoritative Database/KeyValue CR lists, restricted to known workspaces. Migration twins are deduplicated by ID, preferring the workspace namespace. Deleting CRs remain inventory until actually absent. A failed list publishes no partial count. |
| Workspace reach | Distinct owning workspaces at each point, overall and by feature. Feature lines overlap and must not be summed. The overall line is unknown if any selected resource source is missing. These are workspaces, not people. |
| Domains over time | Explicit persisted claims, excluding generated redirects. Configured, ownership-verified and certificate-ready are overlapping subsets; never stacked or summed. Verified claims with stale/missing TLS evidence have a separate unknown count. Resource-type filtering uses the parent App type. |
| Observed creations/deletions | Successful creation facts and App deletion facts; datastore removal is detected by absence from a complete inventory list. Datastore removal time is approximate. Short-lived datastores between snapshots, best-effort attribution, audience reclassification and workspace privacy erasure mean this is not an exact stock/flow accounting ledger. It excludes legacy backfill, and buckets before the collection/retention boundary are unknown. |
| Resource state | Mutually exclusive ready, provisioning, failed, suspended, canceled, deleting and unknown states. Ready requires a current-generation condition and the resource's Ready/Running phase. An idle cron can be ready. Suspended/hibernated resources are intentional, not failed. Missing/stale readiness is unknown, not a deletion. |
| Provisioning progress | Resources created after inventory collection began and first observed by the selected end. Classifies first observed readiness, removal before readiness, or unresolved. Unresolved includes failed, suspended and missing observations; removal is not a canceled deployment. Short-lived resources missed entirely by the sampler are outside this cohort. Deployment outcomes remain separate in Adoption detail. |
| First observed readiness | Creation to first sampled ready: an upper-bound observation, normally up to five minutes late and longer across gaps. Shows completed sample count, p50, p95 only with at least 20 timed completions, and oldest unresolved age. Legacy resources are excluded. Historical queries never borrow a readiness/removal event after the selected end. |
| Seven-day net change | Range-end inventory minus inventory exactly seven days earlier, with a fresh complete snapshot required at each endpoint. Missing either endpoint produces null, not artificial growth. Owning-workspace counts are distinct per type, not additive. |

### Adoption detail

| Measure | Meaning |
| --- | --- |
| Creating surface | Which surface created the resource: `dashboard`, `cli`, `mcp`, `api` (direct REST/GraphQL), `blueprint`, or `unknown`. Mutually exclusive, so the categories sum. Resolved from facts the request already carries, never inferred from workspace, plan or actor type. Precedence, in order: a Blueprint apply wins over whatever transport triggered the sync, because the user declared intent in a manifest and the same engine runs from a manual sync and from the webhook worker, which is not a request at all; then MCP, which is agent traffic by construction; then the CLI, which identifies itself in `User-Agent` on REST; then a browser session on GraphQL, which is the dashboard; then any remaining product request is direct API use. `unknown` is a real population — legacy backfill predates collection, and auth/internal transports are not product traffic. This is a different axis from creator accounts below: actor type records whether a human or a machine credential authenticated, and cannot distinguish a dashboard click from a CLI invocation. `blueprint` means applied from a **registered** Blueprint: a one-shot `render.yaml` deploy is attributed to the transport it arrived on, even where it auto-registers a Blueprint row as a side effect. **Known gap:** a Blueprint apply that creates a managed Postgres or Key Value records no creation event at all — those two paths never reach the recorder — so such datastores are absent from this axis rather than mis-attributed. Do not read the `blueprint` slice as complete for datastores. |
| Agent-driven share | MCP's share of successful creations in range. Null, never 0%, when nothing was created in range. Deliberately narrow: it counts only MCP, because that is the surface agents demonstrably use. An agent driving the CLI is indistinguishable from a person driving it without joining CLI telemetry, which this board does not do, so that usage lands under `cli` and this figure understates rather than guesses. |
| Creator accounts | Distinct authenticated human-account subjects on successful resource creations and explicit domain additions. A machine credential is not a person; an agent using a human OAuth grant remains that account. No account/email inference from workspace membership. |
| Creating workspaces | Distinct workspaces with those creation/addition effects. This is not dashboard DAU, every config change, or all CLI usage. |
| Feature adoption | Static sites, web/private services, workers, cron jobs, Postgres and Key Value. Creation counts, creator accounts, workspace reach and services deployed in the window are separate columns. Deployed resources need not be newly created resources. Inventory is shown separately in the main snapshot panels. |
| Newly activated | First successful service deployment found in retained selected-type history. Not guaranteed to be first-ever. Managed datastores use hosting observations, not App deployment records. |
| Seven-day activation | Workspaces created after collection started, whose full seven-day follow-up has elapsed by the selected end. Workspace created → service created → first successful deploy. Custom domains are optional. Only those mature cohorts enter the denominator. |
| Deployment experience | One terminal result per deploy ID; deactivation of an older successful release does not produce another completion. Cancellations are displayed but excluded from the failure-rate denominator. p50/p95 span known nonnegative start-to-finish intervals, not build-only time. |
| Domains | Explicit domain claims only: generated apex/www redirect siblings are excluded. Ownership verified and TLS certificate observed are different steps. TLS evidence is certificate bytes in the expected Secret, not an external DNS/HTTPS probe or certificate-expiration check. Samples older than 30 minutes are unknown. |
| Hosting workspaces | Distinct workspaces with a live sample on a UTC day touching the selected range, including customers taking no interactive action. A daily bucket remembers whether any sample was live; it is not uptime, traffic, continuous availability or a count of active people. Apps require current-generation Ready=True and Running; intentionally suspended/hibernated services are not live. |
| Repeat creation | First observed creation/adoption calendar-week cohort returning for another creation/adoption in the next week. Only mature next-week windows appear. It is not general product retention; read-only use and redeploy-only visits are not collected as creator activity. |

Known gaps are intentional labels, not synthetic zero data: failed pre-creation attempts, every configuration write, business-level traffic, second-service funnels and general interaction retention are not collected. Creation-surface attribution was a gap in the first version and is now collected (w5/m97); what remains uncollected there is narrower and stated in the surface definition below. Existing operational request/error dashboards remain the view of API failures.

## Data, provenance and privacy

Migration 0114 introduces a closed event schema, explicit audience labels, daily hosting samples, domain certificate observations and a collection-start timestamp. Migration 0115 adds complete source/bucket metadata, aggregate counts by workspace/type/state, one lifecycle checkpoint per resource, and a separate inventory-collection start. Inventory has no synthetic backfill. No event or snapshot stores resource names, hostnames, repository URLs, prompts, credentials, request bodies or raw errors. Stable workspace/resource/account identifiers remain sensitive: only the ops-gated reader has access.

The independent inventory worker polls every five minutes, off the request and reconciliation paths. Each source has a ten-second budget, including at most seven seconds for paginated Kubernetes listing; a 100,000-object safety bound fails closed rather than truncating. Each page is immediately reduced to opaque IDs, closed fields and timestamps; customer specs are not retained across pages. Source publication is transactional. An advisory lock and observation-time guard prevent duplicate replicas or older passes from rolling inventory backward. Services/domains come from Postgres; if App status listing fails, service existence is still known and readiness is unknown. Postgres/KeyValue inventory cannot be refreshed without a complete CR list. Source snapshots are independent, not a globally atomic cross-system snapshot. The status strip reports each source separately; one fresh source cannot certify all sources.

App creates are recorded after materialization succeeds; validation failures, dry runs, duplicate creates and Kubernetes write failures do not record a successful creation. The common create tail also covers new Blueprint resources. Managed Postgres/Key Value creation uses the existing successful-effect hooks. Explicit domain additions enrich their persisted event with the actor; declarations made inside service/Blueprint creation can have unknown creators. Deployment outcomes and domain ownership transitions use transactional database triggers. An API authorization audit row is never treated as a successful resource creation.

Creation attribution is best effort, bounded to one second, and does not turn a completed operation into a user-facing failure if analytics is unavailable. Other successful configuration changes are not silently inferred from authorization logs. Account deletion clears actor identifiers and changes their type to unknown; subject locking plus deletion tombstones prevent the recorder from reintroducing a deleting identity.

Historical backfill uses only surviving Apps, workspaces, deployments and domain rows and is labeled **legacy**. Creators are unknown; previously deleted resources cannot be recovered. Pre-migration domain verification timestamps may be backfilled rather than measured, so legacy timing is not onboarding-performance evidence. Old managed-datastore creation times are not guessed from their first sample.

Events, inventory snapshots and daily hosting rows share the configured audit retention window (90 days by default). The event-retention watermark prevents purged history being shown as known zero in the changes chart. Current lifecycle checkpoints remain while the resource exists; removed checkpoints age out with retention. Ordinary App deletion preserves recent events. Failed-creation rollback explicitly removes provisional events/checkpoints in the same database transaction. Workspace deletion cascades its analytics; deleted account attribution is removed. Historical workspace counts consequently change under privacy erasure. Current reviewed audience classification applies to both historical comparison endpoints; reclassification is not a customer creation/deletion event. These are retained observations, not permanent all-time totals.

The older hosting/TLS sampler remains for Adoption detail: the reconciler samples its own managed Apps after lifecycle write-back with one shared two-second pass budget; each resource is stored at most every five minutes unless state changes. Domain certificate checks reuse the product domain-view helper. Datastore daily hosting is batch-written by the independent inventory worker from each complete source sample, within that source's existing ten-second budget. These daily "ever live" buckets are never reused as point-in-time inventory.

## Audience classification

Customer/unclassified are included by default; known internal, QA and canary workspaces are excluded. Unknown does **not** mean customer. The unclassified-workspace tile makes the remaining classification work visible. Billing exclusion, workspace name, email domain and plan are not reliable substitutes.

An administrator can upsert exact, reviewed workspace IDs into `product_analytics_audiences` with audience `customer`, `internal`, `qa` or `canary`. The Grafana reader cannot edit those labels. No existing workspace is classified automatically.

## Deployment order and credentials

1. Deploy the backend containing migrations 0114/0115/0117 and the success/inventory recorders. Do not enable the updated reader before all three schemas exist: the projection selects `surface` and `surface_started_at`, so applying it against a pre-0117 database fails closed rather than serving a board without the attribution axis. The inventory history starts at rollout, not at the beginning of the selected dashboard range.
2. With an explicit production `KUBECONFIG`, run `DRY_RUN=1 bash scripts/product-analytics-bootstrap.sh`, then the same command without dry-run. Re-run this step whenever `scripts/product-analytics.sql` changes, not only on first install — the views are the reader's whole surface and the script is idempotent. New columns are always appended for the same reason: `CREATE OR REPLACE VIEW` can only add at the end, so an inserted one aborts this step against a cluster that already has the older view. It provisions the restricted `bex_product_analytics` role/views and `monitoring/grafana-product-analytics` Secret (password and CNPG CA). The implementation shares credential handling with the CLI reader through a closed-profile helper.
3. Preserve the Secret with the existing SealedSecret custody workflow. Project only apiVersion/kind/name/namespace/type/data before sealing; never commit a last-applied annotation containing plaintext. Add the encrypted production manifest to the production overlay. No new .env credential is required.
4. Deploy the Grafana values. The new Secret references are optional so missing bootstrap credentials cannot take the existing ops boards offline. Product queries fail closed until the role/schema/CA exist. If Grafana starts before bootstrap, restart it afterward to load the credential environment variable. Coordinate these steps when shipping; this change alone does not create a production credential.
5. Verify datasource health and all panels, classify known internal workspaces, then make one real authenticated creation and verify creator/workspace/type attribution. Never put test fixture rows into production.

Grafana's `product-analytics` datasource uses hostname/CA-verified TLS, at most four pooled connections, and a dedicated read-only role with six connections and ten-second query/idle-transaction limits. Its grants cover only eight explicitly projected analytics views. It cannot read raw Apps, domains, audit events, credentials, or mutate anything. Keep the existing bundled-plugin auto-installer disabled on the read-only Grafana image.

## Verification

- From `lego/backend`, run `go test -p 1 -count=1 ./...` against a fresh disposable database via `BEX_TEST_DB_URI`. The serial package setting matches CI: existing integration suites truncate shared tables, so package-parallel execution can erase another suite's fixtures.
- `python3 -m unittest scripts/test_cli_analytics.py scripts/test_product_analytics.py -v` against disposable PostgreSQL using PGHOST/PGPORT/PGUSER. Each suite creates and removes its own database and reader role. CI uses the pinned PostgreSQL service via BEX_CLI_ANALYTICS_TEST_CONTAINER.
- Backend tests include completed-vs-failed creation hooks, actor classification, cancellation bounds, full-schema PostgreSQL migration, event deduplication, hosting sample throttling, rollback, retention and account cleanup. Inventory tests cover completed/failed pagination, migration-twin deduplication, false/unknown/stale readiness, source atomicity, no phantom deletion, known-zero versus unknown, first-ready preservation and workspace erasure.
- SQL tests execute every main and collapsed-detail panel, including selected-end semantics, unknown comparison endpoints, partial-day boundaries, distinct workspace reach, audience/type filters, three minimum intervals, long-range point limits, reader column allowlists, low-volume p95 suppression, stale TLS and migration down/up.
- `bash scripts/gitops-validate.sh` checks pinned rendering and both restricted datasource contracts.

No tenant REST/GraphQL/MCP response changes are introduced; the shared service methods supply the same success semantics across those transports.
