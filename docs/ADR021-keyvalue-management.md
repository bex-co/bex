# ADR: managed key-value for tenants (Valkey, plans, internal/external URLs)

**Status:** accepted and implemented. The mechanism — the `KeyValue` CRD (`lego/types/v1alpha1/keyvalue_types.go`), the Valkey-projecting controller (`lego/operator/internal/controller/keyvalue_controller.go`), and the `valkey` tier family (`lego/types/tiers/tiers.yaml`) — ships and is live in prod. The Render-compatible **REST/GraphQL/MCP surface** now ships too (`lego/backend/internal/keyvalue/`, w2/m7): `/v1/key-value` CRUD + connection-info + suspend/resume, GraphQL `keyValue*`, and Render's three current MCP tools (`list_key_value`/`get_key_value`/`create_key_value`) — see [ADR006-bex-api.md](ADR006-bex-api.md) § Managed Key Value. It is the direct sibling of managed Postgres ([docs/ADR009-postgresql-management.md](ADR009-postgresql-management.md)) — same shape, one engine down. The **dashboard** surface shipped too (w5/m12): `/keyvalue` list, `/keyvalue/new` create, `/keyvalue/$id` detail with connection-info reveal + suspend/resume.

## Context

Render sells **managed Key Value** (Valkey/Redis-compatible) as a first-class datastore, alongside Postgres. bex wants parity. Key Value is the second-largest datastore gap after Postgres, ranked by the parity audit (m13). The mechanism must exist before any API/dashboard surface can be built — the same CR-first ordering the `Database` followed.

## Decision

### 1. A standalone `KeyValue` resource → a single-instance Valkey StatefulSet

A key-value store is standalone (created independently; multiple services connect to it; it outlives any one app). So model it as a standalone **`KeyValue`** (CR), _not_ `App.spec.kv`. The operator projects it to a single-instance **Valkey `StatefulSet`** in the **tenant's namespace**, mirroring how `Database` projects to a CNPG `Cluster`.

![A KeyValue resource projects a single-replica Valkey StatefulSet in the tenant namespace; the StatefulSet has a PVC for appendonly data, a ClusterIP Service, an immutable auth Secret that projects the immutable connection Secret, and on paid plans a coherent-RDB kvbak CronJob that uploads a nightly gzip to object storage; tenant Apps use the internal URL through the Service, and external clients use the rediss:// URL through the Key Value SNI proxy on :6379](assets/ADR021-keyvalue-management.svg)

### 2. Two URLs = two network paths (the core of the product)

|  | bex |
| --- | --- |
| **Internal URL** | the stable ClusterIP **`<id>` Service**: `redis://<id>:6379`, without credentials, as Render's. A new store's Service routes through its auth proxy from birth, so its URL is credential-free from the first read (w9/m521). An older store's became so at its auth-proxy cutover (w8/204). With internal authentication on it is `redis://<id>:<password>@<id>:6379`, Render's form, and an older store not yet cut over keeps that credentialed form (naming `default` until `status.username` holds, w9/m521). Same-workspace clients can also resolve `<id>.<tenant-ns>.svc`. Every credentialed form keeps working. |
| **External URL** | the **`bex-kv-sni-proxy` TLS/SNI pass-through front door** on shared `:6379`, routing `<id>.kv.bex.co` → that store's TLS Service port. Opt-in per store via `spec.public`. Connection info answers it for a private store too, over the same host, which nothing routes until the store is public (w9/134, below). |

The external hostname becomes routable only when `spec.public: true`, `BEX_KV_DOMAIN` is set, and a `BEX_CLUSTER_ISSUER` can provide its certificate (private by default) — exactly the Postgres pattern with a Valkey-owned TLS endpoint. The controller-owned immutable `<id>-auth` Secret is the only password authority. The immutable `<id>` compatibility Secret projects both URL forms (`uri` internal, `externalUri` external) plus `host`/`port`/`password`; when endpoint metadata changes, the controller replaces that projection rather than mutating it in place.

**Every store answers an external URL (w9/134, 2026-11-20).** Render answers `externalConnectionString` and a `cliCommand` over its external endpoint for every store, including one created with `ipAllowList: []`, whose endpoint exists and admits nothing (three of the nine stores in the Terraform provider's cassettes at pin `06af456`, each read while `creating`; Render's OpenAPI `keyValueConnectionInfo` requires all three strings). Render's dashboard shows neither string for such a store: its Connections section reads "External traffic not allowed. Add IP addresses in the Networking section." in their place ([capture](render-artifacts/key-value.md)). bex matches both:

- **The host.** Wherever `BEX_KV_DOMAIN` is set, the operator records `status.reservedExternalHost` (`<id>.<BEX_KV_DOMAIN>`) for every store, public or not, from its first pass. `status.externalHost`, the field the edge routes by, stays empty for a private store and equals the reserved host for a public one, so a later rule reopens the very host a client copied.
- **The strings.** Connection info (REST, the `/redis` alias and GraphQL) answers a private store's `rediss://<user>:<password>@<reserved host>:6379` and Render's TLS command over it (` REDISCLI_AUTH=… valkey-cli --user … -h … --sni … -p 6379 --tls`), with no `externalCertificate`: a private store has no Certificate. The read stays `can_view_sensitive`, fresh and audited, as for a public store, whose answer already carried the same password.
- **Nothing opens.** The private store's endpoint admits nothing, as Render's does while the list is empty: `bex-kv-sni-proxy` routes only a `spec.public` store whose `externalHost` equals `<id>.<domain>`, so the wildcard host reaches the edge, which refuses the handshake from every source. The store requests no Certificate (no Let's Encrypt budget is spent, w4/m357), opens no TLS listener and has no TLS port on its Service until a rule makes it public. A string copied while private connects once the rule lands and the certificate issues.
- **The dashboard** shows a private store's internal URL, and under the External Key Value URL and Valkey CLI command labels the note that adding an inbound IP rule under Networking enables external access, never the strings themselves.
- A platform with no `BEX_KV_DOMAIN` reserves no host: its stores keep an empty external string and a command over the internal host.

**Internal authentication (w8/204, 2026-10-28).** Render defaults internal connections to unauthenticated access and always authenticates external connections ([Key Value connection documentation](https://render.com/docs/key-value#requiring-auth-for-internal-connections), checked 2026-10-28). bex therefore fronts each store with a separate auth-injecting proxy Deployment. The proxy opens each plain upstream connection through a backend Service selecting only that store's Valkey pod, authenticates as its restricted `default` user, consumes the authentication response, then forwards the client stream unchanged. Existing clients can still send their own correct `AUTH`. Valkey keeps its password and tenant ACL; the proxy never uses the privileged platform user. The external TLS port is forwarded as an opaque encrypted stream to Valkey, retaining end-to-end TLS, external authentication and metering.

**Enable Internal Authentication (w5/m268, 2026-11-05).** Render's Info → Connections button ("Any existing connections that use your unauthenticated URL will break"; afterwards "your instance's internal connection URL now includes a username and password") is `spec.internalAuth`, enable-only by CEL like Render's control (no disable is documented, and Render's audit vocabulary has only `EnableRedisInternalAuthEvent`). The operator writes the credentialed URL into the connection Secret as soon as it sees the flag and clears `status.internalAuthOptional`. The stable `<id>` Service stays on the store's proxy, and the proxy switches to forwarding each client's own `AUTH` instead of supplying it (`BEX_KV_INTERNAL_AUTH=client`, w6/m463, 2026-11-17; § 9). The switch is the proxy Deployment's only change, so it rolls the proxy and nothing of Valkey's: the old proxy pod's termination closes every connection it authenticated — what Render's restart does, without restarting Valkey. Since proxies drain on `SIGTERM` (w6/m512), the operator closes that pod's connections in Valkey once it terminates (§ 10). Until w6/m463 the operator instead pointed `<id>` straight at the Valkey pod and deleted the proxy, which also took the tenant's connection limit away (§ 9). Readiness waits for the proxy's rollout, so the status reads `config_restart` for those seconds, as Render documents a restart for this control (§ 3). During the rollout (`maxSurge: 1`) the old pod still serves until the new one is Ready, and through its 5 s `preStop` pause (w9/135, § 10), so a client without the password can connect for those seconds (2.8 s after the change on the local cluster, w6/m463 t003), and that connection closes with the old pod. Linked services read the credentialed URL from the connection Secret on their next deploy. Connection info answers the credentialed URL as soon as `spec.internalAuth` is set, even before the operator persists the status change. bex-api's `EnableInternalAuth` (can_create) is served on GraphQL `enableKeyValueInternalAuth`, MCP `enable_keyvalue_internal_auth` and the bex REST extension `POST /v1/key-value/{id}/internal-auth` (Render has no REST field; ADR008 forbids a dashboard-only control), audited as `EnableRedisInternalAuthEvent`; views carry `internalAuth`.

**From birth (w9/m521, 2026-11-19).** Render answers a new store's first connection-info read, while it is still `creating`, with `redis://red-…:6379` (the Terraform provider's cassettes at pin `06af456`). A store whose stable Service does not exist yet has no client connected straight to Valkey, so nothing waits for the proxy to strand. The pass that creates that Service (`routeKeyValueFromBirth`, an uncached read that finds none) points it at the proxy and sets `status.internalAuthOptional` before it writes the connection Secret. The first status write and the first Secret therefore carry the credential-free URL. Until the proxy is Ready the Service has no endpoints, as while any store is still creating, and readiness waits for the proxy, so `available` still means the URL connects. A store created with `spec.internalAuth` is routed through the proxy from birth too, in client mode, and keeps its credentialed URL. The security reasoning:

- **Nothing turns authentication off.** Valkey keeps its password and tenant ACL. The proxy supplies the restricted `default` user's `AUTH`, as it does for every cut-over store.
- **Nothing widens reach.** The proxy's NetworkPolicies are written before the proxy and the Service, and they are the ones a cut-over store has: the workspace and environment peers reach the stable Service, and only the store's own proxy reaches its backend. The Service never selects the Valkey pod, not even in the pass that creates it. Both are pinned against a real API server, which records every write to the Service (`A new Key Value's first reconcile (w9/m521)`).
- **The string carries no secret.** The read stays `can_view_sensitive`, fresh, because the same answer carries the external credential.
- An older store keeps the w8/204 cutover below. A manager without `InternalProxyImage` (a legacy embedding) keeps the credentialed form.

**The store's id is a user (w9/m521, 2026-11-19).** Every Render credential string names the store's id as its user: `rediss://red-…:<password>@…`, `--user red-…`, and `redis://red-…:<password>@red-…:6379` with internal authentication ([render.com/docs/key-value](https://render.com/docs/key-value)). The tenant ACL therefore has a second user named `<id>`, with exactly the `default` user's rule (`valkeyTenantUserRule`) and password:

- A new template starts the server with it.
- A running template rendered without it is held as it runs (`applyKeyValueStatefulSet`), so the operator upgrade restarts no store. The operator adds the user to that server as the platform user, with `ACL SETUSER <id> reset on #<sha256> …`, so the password travels only as its hash. It records the credential revision and the server process on the StatefulSet (`app.bex.co/valkey-username`), and adds it again after any restart from the held template. A template the store's own change rolls anyway (a plan, version or persistence change, a credential rotation, a suspension) carries the user from then on.
- `status.username` names the id once every server the store runs knows it. Only then do connection info and the compatibility Secret (`username`, `uri`, `externalUri`) move from `default` to the id. Rewriting that immutable Secret touches no pod, like an access flip. A Blueprint `connectionString` then reads the same URL connection info answers.
- `default` keeps working: the proxy's injected `AUTH`, the readiness probe and every client that copied an earlier string use it. The immutable `<id>-auth` Secret keeps `username: default`.
- `AUTH <id> <password>` reaches Valkey unchanged through the SNI edge (TLS pass-through) and through the proxy in client mode. After a restart from a held template, `AUTH <id>` fails until the operator's pass that sees the restarted pod adds the user again, a window of the pod watch's latency. A template the store's own change rolls closes it for good.
- Verified on both pinned images by `TestValkeyRuntimeUsername` (`BEX_TEST_VALKEY=1`): the runtime add keeps the `run_id` and a Persistence Off key, the id user's ACL equals `default`'s, `CONFIG SET` and `ACL SETUSER` are refused for it, `AUTH` works over the plain and TLS listeners, and a restart from the held template needs the add again. `TestKeyValueTemplateGetsTheUsernameOnlyWhenItRollsAnyway` pins that the user rolls no running template.

A separate Deployment permits migration without changing the Valkey pod template or restarting the store, preserving the live keyspace even when persistence is Off. An existing store's stable Service changes its selector only after the proxy is ready. Once switched, it keeps routing through the proxy during future proxy rollouts; it does not fall back to an authenticated-only backend. `status.internalAuthOptional` records this cutover and gates the credential-free API URL; until then the API retains the credentialed legacy URL. The compatibility connection Secret follows the same cutover, so Blueprint `connectionString` references see the supported URL. Workspace and environment ingress policies cover both endpoints and admit only the exact own proxy to its backend.

The backend connection-info verb retains the fresh sensitive-read authorization and immutable-authority revision check on both forms, because the same response may carry the external credential. REST, GraphQL and dashboard copy read this one verb. This work supplies Render's default internal behavior; the optional internal-auth requirement toggle remains unimplemented. An explicit incorrect `AUTH` continues to be checked by Valkey. Production acceptance still requires deployment and the unauthenticated/credentialed internal, authenticated external, ACL and cross-workspace fixture matrix.

**IP allowlist** (`spec.ipAllowList`, w7/m5) gates the **external** SNI endpoint only: every metered proxy replica watches the KeyValue CR and checks the original source address from the trusted edge PROXY header (or the socket source on a direct connection) before dialing the store — the same mechanism as Database (ADR009 §IP allowlist). The environment-projected allowlist is an additional AND layer. The proxy retains empty-layer-as-unrestricted composition for legacy CRs and absent environment rules. An explicit empty datastore allowlist **update** withdraws public intent, so the external route disappears instead of reaching that unrestricted predicate (see the state matrix below). The internal path is never gated. Entries are `{cidr, description}` pairs (w4/m24): the description is operator-facing metadata that persists on the CR and never affects enforcement. Pre-m24 bare-string CR/store entries were normalized fleet-wide and are rejected by both admission and structured REST decoding; separately named GraphQL/MCP string-list arguments remain supported and are explicitly lifted into entries. Surfaced as Render's `ipAllowList` on the key-value REST/GraphQL/MCP create + REST `GET/PUT /v1/key-value/{id}/ip-allow-list`, the REST `PATCH /v1/key-value/{id}` `ipAllowList` field (w7/m45 — the path the official CLI's `keyvalues update --ip-allow-list`/`--clear-ip-allow-list` uses; a non-nil empty list clears it), GraphQL `keyValueIpAllowList`/`setKeyValueIpAllowList`, MCP `update_key_value(ipAllowList:)` (w7/m45; w1/m71 folded `set_key_value_ip_allow_list` into it), and the dashboard's Networking section. **`maxmemoryPolicy`** is likewise updatable after create (w7/m45): REST `PATCH` (`maxmemoryPolicy` field, the CLI's `update --memory-policy`), GraphQL `setKeyValueMaxmemoryPolicy`, and MCP `update_key_value(maxmemoryPolicy:)` all route through the shared `UpdateKeyValue`, normalizing the underscore/hyphen forms identically to create (REST's Render-schema validator admits the hyphenated spellings of both enums on create and `PATCH`, w8/139). The dashboard's detail page carries a Maxmemory Policy section (w7/007) over `setKeyValueMaxmemoryPolicy`, so post-create editing is no longer create-only. **`persistenceMode` is updatable post-create the same way (w6/m127):** REST `PATCH` (`persistenceMode` — Render's fifth `keyValuePATCHInput` property), GraphQL `setKeyValuePersistenceMode`, and MCP `update_key_value(persistenceMode:)`, all through the shared `UpdateKeyValue`/`validate`. The operator's `valkeyArgs` re-derives the AOF/RDB flags from the changed `spec.persistenceMode`; a restart applies them only after the persistence handoff described below succeeds.

**A refused source reads Render's refusal (w8/m562, 2026-11-22).** Render answers a client from a disallowed address with an error its client prints as `AUTH failed: Client IP address is not in the allowlist.` ([render.com/docs/key-value § Enabling external connections](https://render.com/docs/key-value#enabling-external-connections), read 2026-11-22). Until w8/m562 the proxy closed such a client after its ClientHello, as it closes an unknown name, so the client read a bare TLS EOF. The SNI proxy cannot end TLS itself (the `*.kv.bex.co` wildcard is gated, w4/m357), so the store's own `kv-internal-proxy` answers instead:

- On a public store's name whose allow list refuses the source, the SNI proxy forwards the ClientHello to the store's stable Service on port `6381` (`KeyValueAllowListRefusalPort`) instead of closing. The store's proxy listens there (`BEX_KV_ALLOWLIST_REFUSAL_ADDR`) whenever it forwards the TLS port. It ends TLS with the store's own mounted `<id>-kv-tls` certificate, so the private key never leaves the tenant namespace, and answers every command with `-Client IP address is not in the allowlist.`. `valkey-cli` prints it after `AUTH failed: ` for its opening `AUTH`, and after `(error) ` for the command it then sends on the same connection, so the refusal answers each command, not only the first.
- The listener has no upstream and holds no password (its configuration refuses either), so nothing a refused client sends reaches Valkey or the TLS pass-through, and the refusal never checks a password. It reads commands within Valkey's bounds for an unauthenticated client (10 arguments of at most 16 KiB, or an inline line of 16 KiB), answers at most 64, runs at most 16 refusals at once and closes the rest, and each connection lives at most 5 s.
- An unknown name is still closed after its ClientHello, before any handshake, whatever the source.
- In the SNI proxy, a refused connection keeps its per-source and per-network handshake slots (w21/070) for its whole life, which ends 10 s after accept, and takes none of the store's route capacity. It counts as `bex_kv_proxy_connections_rejected_total{reason="allowlist"}`, which `DatastoreProxyShedding` leaves out because the customer's own rule is not shedding, and none of its bytes is metered as the store's egress.
- **Degraded path.** Valkey never listens on `6381`. A store whose stable Service still selects Valkey, or whose held proxy template predates the listener, refuses the dial, and the client is closed as before. No `kvInternalProxyRollRevision` bump delivered the listener (§ 10): a store created after the deploy has it at once, and a running store gets it at its next own change (a plan change, an internal-auth change, a credential rotation, a resume). The stable Service's port rolls nothing, so every public store carries it at once.
- A private store has no route at all: the proxy routes only public stores, and a private store has no certificate to answer with. A client of its reserved host (w9/134) still reads the dropped connection. This matches Render, not a divergence (w8/409, 2026-11-22). Render documents a store with an empty list as "_not_ reachable at their external URL" and shows no external URL for it until a range is added. It documents the refusal only for "a disallowed IP address", and publishes a URL that refuses every source through the dummy `0.0.0.0/32` range, which makes a bex store public and so reaches the refusal above.

**Free-tier persistence is available, and the default is durable (w6/m127).** bex's free Valkey tier carries a 1 GB disk (`tiers.yaml storageGB: 1`) — a conscious divergence from Render's non-persistent 25 MB free tier — so persistence is offered on every plan. A regression in the create form had copied Render's "free plan → persistence forced Off, both controls locked" behavior from a premise (no persistent disk) that does not hold for bex, silently making dashboard-created free stores pure in-memory caches while the API path defaulted to `journal_snapshot`. The form no longer special-cases the free plan; both creation paths now default to `journal_snapshot`.

**Persistence transitions (w4/m153).** Journal + Snapshot → Snapshot only converts the authoritative journal-backed dataset to RDB. For a running store, Snapshot only → Journal + Snapshot first enables AOF on the serving process and waits for a successful, fully completed rewrite of its current keyspace, including writes not yet snapshotted. The previous pod remains in place on preparation failure. A pod-identity/generation handoff token then identifies that journal as authoritative for the replacement process. For suspended stores already carrying the persistence protocol, an initializer builds the journal from the current RDB on resume, never from an older AOF left on disk. The initializer runs on the same PVC before the target server starts, and a failed conversion must not serve an older dataset as success. Ordinary restarts retain the selected mode's durability limits: Snapshot only can lose writes since its last snapshot, and journal mode uses `appendfsync everysec`. Changes to or from Off intentionally discard all data; an Off restart must not reload historical durable files. The dashboard requires the displayed `sudo clear key value <name>` phrase before either destructive direction, while durable-to-durable changes save directly. Resource identity, credentials and endpoints remain stable. The AOF conversion sequence follows the existing [restore precedent](#5-paid-plan-off-cluster-backups-and-aof-aware-restore) in `scripts/restore-keyvalue.sh`, without invoking that throwaway restore workflow on a managed store.

**Legacy adoption and new storage.** Adding this protocol is lazy: an unchanged legacy workload, including Off, keeps its existing pod template and does not restart merely because the operator was upgraded. On a real workload change, the operator establishes the legacy source from the owned serving process before installing the initializer. Only an absent StatefulSet **and** absent managed PVC authorize `new:<mode>` bootstrap. A pending bootstrap marker distinguishes an interrupted first initialization from a store that has already served. Established durable formats require their source snapshot or journal to exist, and a missing bootstrap marker on a populated volume cannot authorize empty initialization; these cases fail closed instead of silently starting an empty or historical dataset.

**Legacy suspended-store limitation.** An unmarked legacy store with no serving pod has no proven last persisted format. A StatefulSet revision at zero replicas does not establish which format last served. A changed durable rollout or resume therefore fails closed with the `PersistenceSourceUnknown` condition until the platform operator establishes the last persisted format; the controller does not guess from desired flags. An explicit switch to Off remains available as a destructive reset: the initializer records discard intent before removing the managed data files, so this path needs no inferred source format. This restriction applies to legacy storage without established authority. Marked stores and known-new storage handle suspended edits and initialize or convert automatically on resume. Production rollout and the milestone's live data-survival acceptance remain separate verification requirements; these protocol notes do not claim that those probes have run.

The public `persistenceMode` field remains the **requested** setting, not a separate applied-mode field. After acceptance, the existing generation-aware `status` reports `config_restart` for a previously serving store until the current rollout is Ready; first provisioning uses `creating`, an explicitly failed phase uses `unavailable`, and suspension remains `suspended`. REST nests persistence in `options`; GraphQL/MCP return the same underscore-normalized value directly. The dashboard labels `config_restart` as Restarting and its save toast says Updating, so a successful mutation is not a durability-completion claim.

**Open pages see configuration changes (w4/m226).** The dashboard's polled Key Value detail read now selects `persistenceMode` and `maxmemoryPolicy`, which reach the persistence and eviction editors through the normalized cache. A page left open after another client turned persistence Off therefore classifies a change back to a durable mode against Off and asks for the typed deletion confirmation, and the policy editor edits the current policy. A configuration save first lets any detail read already in flight finish, then re-asserts its saved value, so a poll sent before the write cannot put the old mode back; a confirmation opened against a mode that has since changed is discarded. This closes the gap after a successful poll; it is not a compare-and-swap: a change made after the latest delivered read is still classified against that read.

**Render comparison checked 2026-10-02.** Render's [Key Value documentation](https://render.com/docs/key-value#data-persistence) and [persistence changelog](https://render.com/changelog/specify-disk-persistence-behavior-for-paid-key-value-instances) describe a restart for a persistence-mode change and loss of all data for changes to or from Off. The documentation limits persistence to paid instances; bex deliberately provides a durable Free default below. This check used official documentation, not a paid Render mutation; Render's current dashboard confirmation flow and its transition/error status timing were not observed.

**Stores already created on `off` are not force-migrated.** Making `persistenceMode` updatable is the deliberate remedy: an affected owner (or the operator on their behalf) moves the store to `journal_snapshot` with a single PATCH — no recreation or change to id/connection details, but the Off transition discards the existing cache data. The platform does **not** silently flip existing stores, because a persistence change rolls the pod and a store's owner may deliberately want an ephemeral cache (`off` is a legitimate paid-plan choice); a forced fleet-wide durability change without consent is the opposite failure mode. New free stores default durable; existing ones self-serve.

**Render REST create default.** Render documents new Key Value instances as externally disabled until an inbound IP rule is added, and the official CLI has no bex-only `public` field. On `POST /v1/key-value`, omission therefore stays private unless the request carries a nonempty `ipAllowList` (the exact body produced by the CLI's documented `--ip-allow-list` flag), in which case `spec.public=true`. An omitted or explicit empty list never combines with bex's empty-layer-is-open rule to create accidental world access; explicit `public:false` wins, and explicit `public:true` remains available to bex callers. GraphQL, MCP, dashboard/shared-service calls, and direct CR/YAML flows remain private when `public` is omitted. Blueprint creates retain the private default when `ipAllowList` is omitted; explicit rules follow the Blueprint contract below. Existing resources are not migrated. Public intent without a reconciled `status.externalHost` returns a named 503 from connection-info before exposing a URI, with `BEX_KV_DOMAIN` guidance.

### Datastore allowlist update intent (w2/m166)

A present nonempty allowlist enables external access for its CIDRs; a present empty list disables external access. The same rule applies to Key Value and Postgres through REST PATCH, the dedicated REST PUT, GraphQL setters, MCP update tools, dashboard editors, and Blueprint datastore writes. The pinned Render CLI v2.27.0 (`a764810a768202704e7206eb7b87a47211fcd98e`) sends `ipAllowList:[]` for `--clear-ip-allow-list` and describes the result as externally blocked. Render's [Key Value guide](https://render.com/docs/key-value#enabling-external-connections) and [Postgres guide](https://render.com/docs/postgresql-creating-connecting#restricting-external-access), checked 2026-10-02, both define this operation as disabling external connections while preserving internal access.

| Allowlist in update | Explicit `public` in update | Resulting external intent |
| --- | --- | --- |
| Omitted | Omitted | Keep both the saved list and public intent. |
| `[]` | Omitted | Save an empty list and set `public:false`; block new external connections after convergence. |
| Nonempty | Omitted | Replace the list and set `public:true`; matching sources can connect once ready. |
| Any, including omitted | `false` | Keep or replace the list as requested, but withdraw the external route. |
| Omitted | `true` | Publish using the existing resource and environment restrictions. |
| `[]` | `true` | Explicit Bex override: publish with no resource-level source restriction; environment rules still apply. |
| Nonempty | `true` | Publish with the supplied resource list AND any environment restriction. |

`public` wins only when explicitly supplied in the same update. Existing public/empty resources are not migrated; unrelated updates preserve their state. Clearing such a list explicitly now disables the external path, even though the saved entries already equal `[]`.

**Reads report effective access (w4/m315).** Every read reports what the external endpoint admits (`core.EffectiveAllowList`, the rule the Blueprint export already used): a public resource with no saved rules reads `0.0.0.0/0` and `::/0`, a private one reads `[]` whatever inactive rules it keeps, and any other reads its saved rules. This holds on REST (including the `/v1/redis` alias and `GET …/ip-allow-list`), GraphQL, MCP, the dashboard and the export, for both datastores. The list alone therefore says whether the endpoint is reachable, as on Render, and writing back what was read keeps access: the unrestricted pair is a nonempty write, so a public/empty resource stays public and gains the two explicit rules. The dashboard lists the effective rules as ordinary rows and no longer needs a separate unchanged-save path or a "no rules but still open" message. Before w4/m315 reads returned the saved list and the dashboard paired it with public intent instead. Invalid CIDRs and refused writes leave both fields unchanged; dry runs only preview. None of these writes gates internal access, changes HTTP service/static empty-list behavior, or reverses the environment layer's independent AND policy and inherited deny-all.

**Superseded reasoning.** [w4/m116](../.pm/w4/done/m116/README.md) correctly added private-to-public Key Value updates, but deliberately made publication sticky because this ADR incorrectly claimed that Render empty datastore lists meant open access. The 2026-10-02 CLI/network reproduction showed fresh authenticated KV, Postgres primary and PgBouncer connections succeeding after clear, contradicting the pinned client's blocked message. w2/m166 keeps rule-addition publication and supersedes the sticky-clear decision for both datastores. Historical PM evidence remains intact; the shared proxy's empty-layer predicate is not globally reversed.

**Create omission defaults are retained.** Render REST Key Value create remains private for omitted/empty rules, and a nonempty list implies public intent unless an explicit `public:false` overrides it. Render REST Postgres create remains public by omission and records explicit unrestricted IPv4/IPv6 rules when effective public intent is true and the list is omitted (w2/038); explicit `[]` without a `public` override creates a private database. The public Postgres create API rejects `ipAllowList:null` and `public:null` with HTTP 400 before the adapter runs. See [the create-time override matrix](ADR009-postgresql-management.md#postgres-create-access-intent-w2038). For Postgres, GraphQL, MCP and dashboard creates now resolve omission as REST does, and a Blueprint Postgres with an omitted `ipAllowList` is public too (w8/157, w4/553); see ADR009. Key Value creates on every adapter, and direct CR/YAML for both datastores, keep the private default when `public` is omitted, which for Key Value is Render's. Explicit Blueprint rules have the semantics below. Explicit Bex `public:true` with empty rules remains an intentional unrestricted-resource choice, subject to environment restrictions. Existing resources are not silently migrated.

**Blueprint create and sync.** The presence-aware datastore writers (`ApplyBlueprintDatabaseSpec` and `ApplyBlueprintKeyValueSpec` in `lego/backend/internal/apps/blueprint_plan.go`) preserve both saved rules and public intent when `ipAllowList` is omitted on update. An explicit `ipAllowList: []` clears the rules and disables external access; a nonempty list replaces the rules and enables access for matching sources. Explicit lists have the same publication meaning at create. This changes neither omission admission in the pinned Render schema nor the private create default where omission is allowed. Render Blueprint objects have no Bex `public` field, so the same-operation override in the API matrix above is not available in YAML.

**Blueprint export preserves effective datastore access.** `GenerateBlueprint` uses `generateDatabaseEntry` and `generateKeyValueEntry` in `lego/backend/internal/apps/blueprint_generate.go` to emit an explicit `ipAllowList` for each datastore:

| Source resource | Exported `ipAllowList` |
| --- | --- |
| Private, including retained inactive rules | `[]` |
| Public with an empty resource list (legacy or explicit Bex override) | `0.0.0.0/0` and `::/0`, both as `source` entries |
| Public with resource rules | Those rules, including their descriptions |

This representation preserves publication and the resource-level source policy, not dormant configuration: Render's schema cannot encode inactive rules separately from public intent. Applying the exported file to a private resource with retained rules clears those inactive rules; applying it to a legacy public/empty resource records explicit unrestricted IPv4 and IPv6 rules. The first plan must report that representation change even though external access is unchanged, and the next plan is a no-op. Environment restrictions remain an independent AND layer; the export does not flatten them into each datastore's `ipAllowList`. HTTP service/static lists retain their separate contract.

Render's "allow any IP" rule `0.0.0.0/0` also admits IPv6 sources at the datastore SNI front doors (w8/140): `sniproxy.ParseAllowList` treats a rule that masks to `0.0.0.0/0` as `0.0.0.0/0` plus `::/0` in either layer. Render's datastore endpoints are IPv4-only, so there the rule admits everyone; ours also publish AAAA and dual-stack clients try IPv6 first. The equivalence is enforcement-only (the saved rule and every readback stay as authored), and narrower IPv4 rules are not widened ([w9/m164](../.pm/w9/done/m164/README.md)).

### 3. End-to-end public TLS

The public wildcard must be **DNS-only (gray-cloud)** — Cloudflare's proxy is HTTP(S) only and cannot carry raw TCP `:6379`. Public Valkey clients use direct TLS (`rediss://`) end to end: cert-manager issues `<name>.<BEX_KV_DOMAIN>`, Valkey listens with that certificate on private port `6380`, and the shared proxy forwards the bounded ClientHello plus the remaining encrypted stream without terminating TLS. The internal URL remains plaintext `redis://` on port `6379`, with authentication supplied by the per-store front after cutover; public TLS does not force in-cluster Apps through encryption or the meter.

**The TLS listener switches at runtime (w8/m134 t003, user decision D3 2026-10-29).** Every store created since then turns its listener on and off without a restart, so no external-access change restarts it or empties a Persistence Off store:

- **Birth.** The pod mounts the `<id>-kv-tls` Secret with `optional: true`, and the server starts through a short `sh` wrapper (`kvTLSWrapperScript`, run via the image's own entrypoint) that appends the listener flags (`--tls-port 6380` with `/tls/tls.crt`, `/tls/tls.key`, `tls-auth-clients no`) only when both certificate files are present. A private store requests no Certificate, so `bex kv create` spends no ACME latency or per-domain issuance quota on a store that may never be exposed, and its pod starts at once with no TLS listener.
- **Enable.** The Certificate is requested in the same reconcile. Once cert-manager has written the Secret, the operator logs in as the platform user and runs `CONFIG SET tls-cert-file … tls-key-file … tls-ca-cert-file … tls-auth-clients no`, then `CONFIG SET tls-port 6380`. Valkey loads the certificate as the port opens. Until the kubelet has projected the files it refuses and keeps `tls-port 0`, so the operator retries every 5 s. The pod template, StatefulSet and keyspace are untouched, and the process keeps its `run_id`. The Service's TLS port, `status.externalHost` and the proxy route follow `spec.public`.
- **Until the certificate issues, there is no external access (w4/m357).** A public store has no TLS listener while its Certificate is pending, so on 2026-11-13, when Let's Encrypt's `bex.co` budget ran dry, new public stores had none for hours (rounds 254 and 304). The `PublicCertificateReady` condition (`Issued`, `Issuing`, `ListenerStarting`, `RateLimited`, `IssuanceFailed`) says why. The read, GraphQL `KeyValue`, MCP and connection info carry `externalCertificate` (`publiclyTrusted` once the listener is open, else `pending` or `failed`) with `externalCertificateReason`; the dashboard's Details read "Yes (external endpoint opening: certificate pending)" or "Yes (not reachable yet: certificate issuance failed)", and the Connections card says the store is reachable only from services meanwhile. The budget, the alert and the gated `*.kv.bex.co` wildcard fix are in [ADR009 § Publicly trusted server certificates](ADR009-postgresql-management.md#publicly-trusted-server-certificates-w2m245).
- **Disable.** `CONFIG SET tls-port 0` closes the listener in the same process, and the Certificate is withdrawn. Its issued Secret stays (cert-manager keeps it, and the delete-time TLS cleanup still owns it), so a later re-enable opens the listener without a new issuance.
- **Restart.** A pod restarted while public comes back listening from the mounted Secret through the wrapper. One restarted while private with the Secret still present briefly listens in-cluster (behind the same password) until the next reconcile sets `tls-port 0`; the proxy never routes a non-public store.
- The auth proxy and its backend Service always carry the TLS port for such a store, so opening the listener rolls nothing there either.
- Verified on both pinned images (Valkey 7.2 and 8.1) by `TestValkeyRuntimeTLSSwitch` (`BEX_TEST_VALKEY=1`). It runs the pod's own start command and the operator's switch: no listener without the files; an enable before the files exist is refused and leaves `tls-port 0`; the enable keeps the `run_id` and a Persistence Off key; `tls-port 0` closes it; and a restart starts the listener only with the files mounted. `TestKeyValueRuntimeTLSSwitchRestartsNothing` pins that enable, disable and re-enable leave the StatefulSet's resourceVersion unchanged.
- Valkey reads the certificate files when the listener opens or the process starts, not on cert-manager's renewal, which rewrites the mounted files only. The static listener below has the same limit.

**Older stores keep their static listener (w4/m233).** A store created before w8/m134 t003 has the listener in its pod template, or none. The operator upgrade changes neither, so it restarts no running store. Adding or dropping that static listener changes the pod template, so the StatefulSet restarts the store, and a Persistence Off store comes back empty. Once such a store's pod template carries the listener, the operator keeps it and its Certificate even after `spec.public` goes false. Turning external access off removes only the Service's TLS port, `status.externalHost` and the proxy route (the proxy routes only `spec.public` stores). Turning it back on restores them. Neither change rolls the pod. While private, the kept Certificate is left as issued for cert-manager to renew, so a TLS fault cannot stall the store's other reconciles. The static listener is dropped only while the store is suspended, when no process runs to restart. An older store with no listener takes one restart at its first enable, and that roll adopts the runtime switch, so it is its last. The IP gate does not move: the proxy still refuses a non-public store, the listener is reachable in-cluster only (behind the same password as the plaintext port), and keeping it costs one renewing Certificate per store that was ever public.

The status agrees. When `UpdateKeyValue` writes a change it knows restarts nothing (a rename, an edit of the store's own allow-list, or an access flip on a store whose listener already runs or switches at runtime), it records the generation that write lands at in the `app.bex.co/restart-free-generation` annotation. The write is a merge patch locked to the resourceVersion it read, so the mark cannot land on a racing writer's generation. While that is the only generation a Ready store has not observed, the store reads `available`, not `config_restart`. The operator keeps a serving store Ready while it rewrites the immutable connection Secret for an access flip, which touches no pod. Connection info names the routed `externalHost` only while `spec.public` is set; a private store's string names its reserved host, the same name, which the edge stops routing as soon as `spec.public` is false (w9/134). An environment allow-list fan-out is not marked and still reads `config_restart` until observed.

- `status.tlsListener` reports whether the process runs the listener. `status.tlsRuntimeSwitch` reports that the store switches it at runtime.
- Connection info (REST, the `/redis` alias and GraphQL) answers the external `rediss://` URL and its CLI command as soon as the operator records `externalHost`, whether or not the listener has opened (w9/m521, 2026-11-19; it replaced w8/237's withholding). Render answers them while a store is still `creating`. `externalCertificate` (`pending`, `failed`, `publiclyTrusted`; w4/m357) says whether the TLS listener accepts connections yet. The dashboard's Connect panel shows the URL with a note under it while it is pending or failed.
- **A store created public reads `creating` until its listener opens** (w9/m521). Render's `available` means every string it handed out connects, so readiness also waits for the listener (`keyValueFirstListenerWait`), only while the store has never been available, its certificate has not failed, and the create is less than 5 minutes old. A later first enable on a store that has been available keeps it `available` with `externalCertificate: pending`. A failed certificate, or one still not issued after 5 minutes, reads `available` with `externalCertificate` `failed` or `pending`, so a stalled issuance never holds the store's internal clients. The listener usually opens about a minute after the create.
- The API's `externalAccessRestarts` (GraphQL; a bex REST/MCP extra) is true only for a running older store whose next enable would add the static listener. Where `BEX_KV_DOMAIN` is unset no listener is ever added, so the flag over-reports there.
- **History.** w8/181 (db739b089) started every new store with the static listener so that the first enable restarted nothing. A private store's Certificate is requested only once it is public, so its pod required a Secret that never appeared and stayed `creating` (w8/m134, hotfixed 2026-10-23 by starting private stores without the listener, which brought back the first-enable restart). t003 removed that restart with the runtime switch rather than a birth listener.
- For an older running store with persistence Off, REST PATCH/PUT, GraphQL `setKeyValueIpAllowList`/`setKeyValuePublic` and MCP `update_key_value` refuse that first enable with 400 `KEY_VALUE_RESTART_CONFIRMATION_REQUIRED` unless `confirm` carries `sudo clear key value <name>`. That is the phrase the dashboard's persistence change uses for the same data loss. The dashboard asks for the phrase the refusal names and retries once, as it does for protected environments.
- A Blueprint has no `confirm` channel, and the auto-sync worker runs unattended, so a plan or sync whose `ipAllowList` would make that same first enable on a running Persistence Off store is refused with a named bad-request error pointing at the Networking settings or the confirmed PATCH (`keyvalue.RefuseBlueprintExternalAccessRestart`, w4/358). Stores with persistence on, already public, or suspended are unaffected. An explicit apply flag is a possible looser variant, not shipped.
- Render documents no restart for allowlist changes (render.com/docs/key-value, checked 2026-10-19). Stores created since w8/m134 t003 match it; the one first-enable restart of an older private store is the remaining recorded divergence.
- Blueprint `ipAllowList` writes bypass the update path and are tracked separately (w4/358).

Connection-info's ready-to-run command takes Render's shape (w9/m521, 2026-11-19), with that routing requirement made explicit: ` REDISCLI_AUTH=<password> valkey-cli --user <user> -h <externalHost> --sni <externalHost> -p 6379 --tls`.

- The leading space keeps it out of shell history under `HISTCONTROL=ignorespace`. The password travels in the environment, where `ps` does not show it.
- `--sni` stays, before Render's ` -p <port> --tls` tail. valkey-cli 8.1.1 sends a TLS server name only with `--sni` (`src/cli_common.c`), and the shared edge deliberately requires SNI to select one store. Render's regional endpoint (`oregon-keyvalue.…:6377`) routes by username instead, so Render's command has none.
- The Render CLI's `kv-cli` (`pkg/tui/views/rediscli.go`) runs the command as written. It splits it on spaces, makes the words before `valkey-cli` the process's whole environment and the words after it its arguments, and falls back to `redis-cli` when `valkey-cli` is not installed. `redis-cli` takes the same flags.
- A private store's command takes the same external form over its reserved host, as Render's does (w9/134, above). Only a store with no external host (no `BEX_KV_DOMAIN`) connects to the internal host, as its internal URL does: ` valkey-cli -h <id> -p 6379` while that URL is credential-free, ` REDISCLI_AUTH=<password> valkey-cli --user <user> -h <id> -p 6379` with internal authentication. From w9/m521 to w9/134 every private store had that internal form.
- Until w9/m521 the commands were `redis-cli --sni <externalHost> -u <rediss-uri>` and `redis-cli -u <redis-uri>`.

[`scripts/datastore-dns-cloudflare.sh`](../scripts/datastore-dns-cloudflare.sh) is the production guard for that distinction. Given `BEX_DB_DOMAIN`, `BEX_KV_DOMAIN`, `HCLOUD_TOKEN`, and an ephemeral zone-scoped `CLOUDFLARE_API_TOKEN`, it reconciles the two datastore wildcard names to the Terraform-owned edge load balancer's IPv4 address with `proxied:false` and removes any AAAA (A only, as Render's datastore hosts publish — [ADR009](ADR009-postgresql-management.md), w9/m164); `--check` performs the same comparison without mutation. It does not target the proxied App/API/custom-domain zone paths. This gate was added after the 2026-07-18 official-CLI acceptance run found `*.kv.bex.co` incorrectly orange-clouded: bex-api returned a valid public `rediss://` endpoint and Hetzner reported healthy 6379 targets, but ordinary Cloudflare proxy addresses could not accept raw Valkey TCP.

In production, `bex-kv-sni-proxy-public` is a fixed `NodePort` (`31892`) with `externalTrafficPolicy: Local`; Terraform owns the shared Hetzner edge LB's `6379 → 31892` listener and TCP health check. `Local` admits only workers with a local proxy endpoint. Because a TCP load balancer otherwise replaces the application-visible client address, the datastore listener also enables PROXY protocol. The proxy consumes a bounded v1/v2 header before the TLS ClientHello only from the load balancer's fixed `10.10.0.7/32` private address and applies the asserted public source to both allowlist layers; untrusted headers fail closed and headerless direct/dev connections keep their socket source. ADR009's compatibility-first CI handoff applies to this listener too: Terraform cannot enable headers until the same commit's deploy proves every Valkey/PostgreSQL proxy pod runs the header-capable digest. The production `allow-production-edge-proxies` NetworkPolicy opens only the PostgreSQL/Valkey proxy pods' public ports through the `bex-system` default deny.

Only bytes copied from the TLS backend to the public client increment `bex_kv_proxy_egress_bytes_total{resource_id,resource_kind="key_value"}`. Requests, denied/unrouted handshakes, and internal clients contribute zero. The operator deletes pre-m15 Traefik `IngressRouteTCP`/`MiddlewareTCP` objects during reconcile so no unmetered bypass remains.

**A plan change restarts the store (w4/m263).** `setPlan` puts the plan into the Valkey container's resources, a StatefulSet pod-template change, so the only pod is replaced and the store is unavailable for a minute or two. Render documents the same: upgrading requires a restart, and data loss depends on the persistence mode. With Persistence Off nothing is on disk to reload, so every key is lost; Journal + Snapshot and Snapshot only keep what they persisted. The dashboard says so on the Instance type card and, for an Off store, requires the typed `sudo clear key value <name>` phrase. REST `PATCH`, GraphQL `updateKeyValuePlan`, MCP `update_key_value` and Blueprints accept the change without a confirmation, as Render's API does, and describe the consequence in their descriptions; a `confirm`-gated refusal would break the pinned CLI's `keyvalues update --plan` and is a separate follow-up. Blueprint sync therefore also just restarts the store, matching Render's Blueprint behavior for a plan change.

**A plan change only goes up (w8/249, 2026-11-11).** Render: "It is not currently possible to downgrade a Key Value instance" ([render.com/docs/key-value § Changing compute plans](https://render.com/docs/key-value), read 2026-11-11). bex accepted any plan change, so `bex kv update --plan free` restarted a paid store into less memory than its data might need. A change to a plan with less memory than the current one is now refused with `400 KEY_VALUE_PLAN_DOWNGRADE_UNSUPPORTED` before anything is written (`keyvalue.ErrPlanDowngrade`). The rule is the same on REST `PATCH /v1/key-value/{id}`, GraphQL `updateKeyValuePlan`, MCP `update_key_value`, and their dry runs. A Blueprint that declares a smaller `plan` than the store has is refused in the plan and in the sync, since a sync has no confirm channel; a Blueprint that declares no `plan` leaves the plan alone. Re-sending the current plan, under its id or a size alias, is no change. The dashboard's plan picker disables every plan smaller than the current one and says why. To use a smaller plan, create a new instance and move the data. Render documents no refusal body for a downgrade request and does not say what a Blueprint with a lower `plan` does, so the code and the Blueprint refusal are bex's own.

**A maxmemory-policy change restarts nothing (w4/m330, 2026-11-11; replaces w4/m316's restart).** Render documents restarts for a persistence change, a plan upgrade and Enable Internal Authentication, and none for the eviction policy ([render.com/docs/key-value](https://render.com/docs/key-value), read 2026-11-11). The operator now matches that. The pod template keeps the policy its server started with when the policy is the only change, so the StatefulSet does not roll; every reconcile then brings the running process to `spec.maxmemoryPolicy` with one `CONFIG SET maxmemory <budget> maxmemory-policy <p>` as the platform user (the tenant's `default` user cannot run `@admin`, w4/191). An unset policy is Valkey's default (no budget, `noeviction`). The runtime step waits until the pod runs the StatefulSet's current revision, so a pod about to be replaced never takes a new plan's budget, and applies as soon as the server process runs (Valkey takes `CONFIG` while it loads the dataset). A pod restarted for another reason, from a template that still holds an older policy, is brought to the current one that way, so it can run the older policy only for the moments before the operator's next pass; a suspended store's template takes the current policy outright, and a template change that rolls the pod anyway (plan, version, persistence) starts the new server with it. Once the template and the process both run the store's policy, the operator dials nothing. `status.maxmemoryPolicy` records the policy the running process was last confirmed to run. A refused `CONFIG SET` keeps the store serving and is retried within 5 seconds. So the dashboard's Maxmemory Policy card saves without a dialog, GraphQL `setKeyValueMaxmemoryPolicy` and MCP `update_key_value` say the change applies without a restart, and bex-api marks a policy-only write restart-free, so the status stays `available` instead of reading `config_restart`. A policy-only change records the generic `keyvalue.UpdateKeyValue` audit row, not `key_value_config_restart`, because nothing restarts; a persistence change still records it. REST, Blueprints and the pinned CLI's `keyvalues update --maxmemory-policy` are unchanged.

### 4. Plans — Render's Key Value vocabulary

The `valkey` tier family uses Render's **Key Value** plan vocabulary (`free` / `starter` / `standard` / `pro` / `pro_plus` / …) — the same names Render's Key Value product shares with its web-service ladder, _not_ the Postgres `basic-*` names. MVP shipped the first three; **since w5/m266 (2026-11-05) the ladder is Render's**: `free`, `starter` (`256mb`), `standard` (`1g`), `3g`, `pro` (`5g`), `pro_plus` (`10g`), `pro_max` (`20g`), `pro_ultra` (`40g`) and `50g`. Each tier's memory is the plan's RAM, and its volume is twice that. `pro_plus` and `pro_max` run on the `xl` serving pool, while `pro_ultra` and `50g` need the `xxl` pool and share Pro Ultra's temporary pause (refused `INSTANCE_TYPE_UNAVAILABLE`, shown unavailable). Render's size ids alias the legacy-named rungs. The original three were:

| plan | compute (requests==limits) | storage | instances | Render KV equivalent |
| --- | --- | --- | --- | --- |
| `free` | 100m / 128Mi | 1Gi | 1 | Free (25 MB; bex more generous) |
| `starter` | 100m / 256Mi | 1Gi | 1 | Starter (256 MB) |
| `standard` | 500m / 1Gi | 5Gi | 1 | Standard (1 GB) |

**An omitted plan, per create surface (w33/m436, 2026-11-16).** Only a Blueprint defines a default that is not Free. Render's blueprint-spec § `plan` says "Render uses `256mb` for a new Key Value instance" and keeps an existing instance's plan, so a Blueprint entry without `plan` creates on `starter`. That store is priced as Starter, counts as paid intent for the payment-method gate, and never takes the workspace's free slot. A sync that omits `plan` leaves the store's plan alone. Every other surface keeps the CRD default (`free`). None of them conflicts with a pinned Render contract:

| Surface | Omitted `plan` | Render basis |
| --- | --- | --- |
| Blueprint create (`type: keyvalue` and the legacy `redis`) | `starter` (Render's `256mb`) | blueprint-spec § `plan`, read 2026-11-16 |
| Blueprint sync or adopt of an existing store | the store's plan, unchanged | the same section: "Render retains the current compute plan for an existing service" |
| REST `POST /v1/key-value` | `free` | Render's pinned `keyValuePOSTInput` requires `plan`, so there is no Render default to match. bex relaxes the requiredness (`renderRequiredCompatibility`) and keeps the CRD default |
| MCP `create_key_value` | `free` | Render's MCP server makes `plan` optional with `mcp.DefaultString(KeyValuePlanFree)` and sends `free` when it is absent (`render-oss/render-mcp-server` `pkg/keyvalue/tools.go`, `main` at `a18ef3e`, read 2026-11-16). The pin in `render-mcp-tools.json` records `plan` as optional and does not record defaults |
| GraphQL `createKeyValue` | `free` | bex-only surface, no Render counterpart |
| Dashboard New Key Value | never omitted: the form sends the card the user picked, with Free, the first card, preselected | a form's preselection is not an API default, and Render documents none for its form |

Generate Blueprint always writes the store's plan, `plan: free` included, so applying an exported file again never moves a free store to Starter.

`spec.storageGB` may grow past the plan floor, never below (storage is expand-only). The operator persists the accepted request in `status.allocatedStorageGB`, the corresponding explicit intent in `status.observedStorageGB`, and the last PVC capacity in `status.storageCapacityGB`; the effective request is the maximum of the recorded allocation, the selected plan floor, explicit intent, the StatefulSet claim template, and the live PVC **request**. A plan change therefore never shrinks the disk. The observed PVC **capacity** is physical and never feeds the logical allocation (w4/m193): a provider floor such as Hetzner's 10 GiB minimum volume can exceed any request, and promoting it turned a default Free store's 1 GB allocation into a reported 10 GiB. Capacity only gates readiness (`StorageReady` stays false while it trails the request) and is kept in `status.storageCapacityGB` for operations. Stores reconciled before that fix may carry a floor-inflated `allocatedStorageGB`/PVC request; bookkeeping cannot separate that from genuine growth, so those high-waters are retained rather than silently decreased.

Growth targets the real StatefulSet PVC, `data-<red-id>-0`, rather than trying to mutate the immutable `volumeClaimTemplates`. The PVC must be Bound and its named StorageClass must have `allowVolumeExpansion: true`; then the operator patches only a larger storage request and waits for capacity convergence. The `StorageReady` condition distinguishes PVC creation/binding, missing or non-expandable StorageClass, controller resize, filesystem resize, and provisioned capacity. `Ready` remains false during a non-suspended resize, and the controller backs off five minutes for an unsupported class instead of hot-looping. Kubernetes documents the underlying [PVC expansion and filesystem-resize lifecycle](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#expanding-persistent-volumes-claims).

Shrink intent is rejected as `StorageShrinkRejected` without changing the PVC. Rollout health is evaluated independently: the StatefulSet must have observed its current generation, `currentRevision` must equal `updateRevision`, and the desired current-revision Pod must be Ready. Thus old available replicas cannot hide either a failed plan rollout or pending expansion. The API keeps the same honesty at the status word (w4/m137). A store that has served (its `status.credentialRevision` is written only on Ready) reports Render's `config_restart` while it restarts after a maxmemory, persistence, or plan change, and `creating` is reserved for a first provision. A `Ready` phase whose Ready condition trails the current generation, or is still the suspended placeholder after a resume, also reads `config_restart` rather than `available`. The dashboard labels it **Restarting**, and a config save switches the detail page to its fast poll so the restart is visible. When a spelling-divergent tier is added (`pro_plus`), the family gains a `renderPlan` field like `compute`.

### 5. Paid-plan off-cluster backups and AOF-aware restore

> This CronJob's encryption and credential scoping (Tier A of [ADR050-encrypted-platform-backups.md](ADR050-encrypted-platform-backups.md)) are specified there, not here.

The operator gives every non-Free plan a deterministic `kvbak-<id>` CronJob when all three `BEX_KV_BACKUP_DESTINATION`, `BEX_KV_BACKUP_ENDPOINT`, and `BEX_KV_BACKUP_S3_SECRET` settings are present. Any missing setting disables the feature: a new reconcile adds no backup CronJob or backup finalizer. Production uses `s3://bex-tfstate/keyvalue`, the Wasabi endpoint, and the out-of-band `default/bex-kv-backup-s3` Secret (`AWS_ACCESS_KEY_ID` plus `AWS_SECRET_ACCESS_KEY`). Free plans remain PVC-only and receive no CronJob.

Each instance hashes its immutable `red-` id into a stable slot from 03:20–03:39 UTC, avoiding a fleet-wide snapshot spike. The job authenticates through `REDISCLI_AUTH` from the immutable `<id>-auth` Secret and runs `valkey-cli --rdb` over the private Service. That replication-protocol request produces a coherent RDB without copying a live `dump.rdb` or granting `pods/exec`. A second stage gzips it; the credentialed uploader writes `keyvalue/<id>/<RFC3339-UTC>.rdb.gz` and retains the lexicographically newest seven. Suspended stores keep their CronJob but set `spec.suspend: true`, so intentional hibernation neither runs nor pages.

This is snapshot recovery, **not PITR**. The paid-plan RPO is the nightly cadence (at most roughly one day plus job delay); writes after the latest successful RDB can be lost. Free-plan durability is only the live PVC and may be lost with that volume or cluster. `BackupCronJobStale` pages when an active CronJob has no success for more than 26 hours, including a CronJob that never succeeded.

Deletion is fail-closed while backups are configured. The backup finalizer first removes the CronJob and every labeled backup Job, then a durable terminal Job recursively deletes `keyvalue/<id>/`; only a proven successful purge releases the resource. If backups are disabled, the backup finalizer never gets added to new resources and any historical backup finalizer releases without waiting for an unavailable purge. The independent TLS cleanup obligation below remains.

**Job labels (w6/139, 2026-11-17).** The backup and purge Jobs and their pods carry `app.bex.co/keyvalue-job: <id>`, never `app.bex.co/keyvalue`. That label is the whole selector of `<id>` (before its proxy is ready) and of `<id>-backend`, and a backup pod is Ready while it uploads, so until w6/139 it became an endpoint of both on ports where nothing listens: during every paid store's nightly backup about half of its new connections were reset, and so was the proxy's readiness check. The operator selects the Job pods by the parent-UID label `app.bex.co/keyvalue-uid` (their NetworkPolicy peers and the delete-time wait), which Jobs from before the change carry too, so a backup running across that operator upgrade keeps its network path. The change restarts no store: it rewrites only the CronJob template and the Job selector in up to three NetworkPolicies.

RDB restore must account for AOF precedence: when Valkey starts with an existing append-only directory, it loads AOF instead of `dump.rdb`. `scripts/restore-keyvalue.sh` is the executable path: it accepts only a new `restore-*` namespace/PVC, gzip- and checksum-validates the selected object, proves the data directory has no RDB/AOF, seeds `/data/dump.rdb`, starts once with `appendonly no`, verifies a known key without printing it, enables and rewrites AOF, rolls, and verifies again. It has no in-place mode. The mechanism drill is recorded in [the 2026-07-31 KeyValue restore drill](drills/2026-07-31-keyvalue-restore.md); the scripted production rerun and transfer portability finding are in [the w7/m69 all-store drill](drills/2026-07-31-scripted-restore-e2e.md).

### 6. Lifecycle (create → connect → delete)

1. **Create** `KeyValue{name, plan, storage}`. No create surface takes a version: a new store leaves `spec.version` empty and runs the operator default, Valkey 8, as a new Render Key Value does (w4/743). The CRD still admits `"7"` so a store created on Valkey 7 before keeps running it.
2. **Provision** → the operator creates the StatefulSet (Valkey `--requirepass <generated> --appendonly yes`, PVC for AOF data), the ClusterIP Service, the immutable `<id>-auth` authority, and the immutable `<id>` connection projection. The password is generated once on first reconcile and is not a user-rotatable setting. A legacy connection Secret seeds the authority during migration, preserving the running password.
3. **Prove rollout consistency** → the Pod template carries the one-way SHA-256 credential revision. `status.credentialRevision` advances only when the current StatefulSet revision and Pod are Ready; no credential value enters status, Events, or logs.
4. **Surface connection info** → REST/GraphQL reads the authority only while its hash matches `status.credentialRevision`; otherwise it returns conflict. **Amended by w8/305 (2026-11-13):** the read no longer also requires phase Ready. The revision advances only once the pods serve it and the password never changes, so a restart (a persistence change, a resume) keeps a matching revision; the Ready condition had answered 409 "credentials are still converging" through every restart. **Amended by w9/108 (2026-11-18):** a store with no recorded revision yet (first provisioning) is served too. Render answers connection info for a store that is still `creating`, and its Terraform provider reads it straight after the create. Until the pods serve, no other password exists for clients to split against, so only a recorded revision that differs from the authority is refused. A read that arrives before the operator's first pass, which writes the authority and records the host a few tens of milliseconds after the create, waits up to 5 s for it instead of answering 404 (no Secret yet) or 503 (no external host yet). After `status.internalAuthOptional` confirms stable-Service cutover, the internal string omits credentials; the external string always keeps them. The dashboard therefore cannot reveal credentials from a split rollout or advertise an unauthenticated URL before it works. MCP exposes KeyValue metadata but no credential-read tool.
5. **Delete** → the independent TLS finalizer quiesces the owned Certificate and observes it absent, then deletes the proven per-instance TLS Secret and observes it absent. For a previously backed-up store, the backup finalizer also stops backup work and purges `keyvalue/<id>/`. Deleting the `KeyValue` then garbage-collects the StatefulSet, auth-proxy Deployment, both Services, PVC and both immutable credential Secrets. The proxy removes the route from its watched table. While either cleanup finalizer holds the CR (`DeletionTimestamp` set), tenant **by-id reads** return the same `not found` as an absent id (`core.NotFoundIfDeleting`, w8/m35) — REST get/connection-info and siblings, GraphQL, MCP — and List omits the row; workspace-limits still counts it under `terminating` (w6/m129). A finalization that overruns its 15-minute bound stamps `DeletionStalled` on the KeyValue (w8/012) and backs the requeue off while retaining the finalizer.

**TLS cleanup (w4/m149).** Every canonical KeyValue lifetime receives `app.bex.co/kv-tls-cleanup` before Certificate creation, independently of its plan and backup configuration. The obligation survives public-to-private changes; never-public stores complete it once both exact artifacts are absent. It does not create an RDB purge job. The existing backup finalizer also fences TLS cleanup for a legacy paid instance already terminating before enrollment. cert-manager retains issued Secrets by default, so Certificate ownership alone cannot provide this cleanup guarantee.

New Certificate templates propagate the KeyValue UID to the issued Secret. Cleanup verifies the canonical namespace, current lifetime, Certificate owner and exact reserved `<id>-kv-tls` name. Legacy ownerless Secrets require matching cert-manager issuance metadata and a creation time within the current KeyValue lifetime. Conflicting or unproven ownership fails closed; it is not adopted or bulk-purged. Secret access uses the existing uncached tenant client, and deletion preconditions protect replacement objects. Read/delete errors and pending child deletion retain the finalizer across manager restarts. Namespace termination can take over namespace-local cleanup without releasing a backup obligation.

The delete audit checks the exact Certificate and TLS Secret as well as existing workload/backup artifacts. A Kubernetes access failure is not absence. Optional S3 prerequisites still produce an explicit skip. Operator tests and an isolated audit harness verify the protocol; real cert-manager garbage collection and public/private dashboard deletion remain a post-release QA requirement.

### 7. Identity and rename (stable `red-` id + mutable name, w9/m6)

Identity and display name are separate, exactly as managed Postgres shipped in w9/m3 (ADR009 §Rename and legacy migration):

- **New stores mint `KeyValue.metadata.name = red-<xid>`** through `internal/id` (`id.KeyValue`, Render's Key Value prefix). This immutable value is the REST/GraphQL/MCP id and the root of every physical object name — the StatefulSet, Service, PVC, credentials Secret, and the external SNI hostname (`<red-id>.<BEX_KV_DOMAIN>`). Because the id (not the name) lives in the hostname and Secret, a **rename never breaks a connection string**.
- **`KeyValue.spec.name` is the mutable, user-facing DNS-label name** (`ValidResourceName`: ≤30 chars, DNS-1123 label). It is workspace-scoped unique — two workspaces may reuse a name; a duplicate inside one workspace is rejected (`core.ErrConflict`).
- **Canonical identity is required.** Production and the maintained local cluster were verified to contain no missing `spec.name` or non-`red-` ids before the old name-as-id fallback was removed; the CRD now requires `spec.name` (w1/m56 t009).

`PATCH /v1/key-value/{id}` changes only `spec.name` (and/or `plan`); the KeyValue metadata name/UID, StatefulSet, PVC, credentials Secret, Service, external route, project/environment membership, and connection strings all remain attached to the immutable id. The same core mutation (`UpdateKeyValue`) backs REST, GraphQL `renameKeyValue`, MCP `update_key_value(name:)`, and the dashboard; `dryRun=true` runs identical validation without writing. The GET-by-id item route resolves by the opaque id only — the official Render CLI resolves a typed name to a `red-` id via the list filter, then routes every item call by that id, so the split is what makes the unmodified CLI's `keyvalues update <name> --name <new>` land on the right store.

**Migration closeout.** The original rollout backfilled missing display names without re-keying CRs, then enabled rename traffic after identity-preservation checks. The 2026-07-28 fleet audit found zero remaining legacy shapes, so the one-time script and metadata-name reader were retired and `spec.name` became required. Rollback restores the preceding code/CRD commit without reversing canonical object data.

### 8. Tenant command surface (w4/191, w5/m110)

Tenants connect as Valkey's `default` user, which the operator defines explicitly instead of a bare `--requirepass` that left it `+@all` (w4/191).

**The tenant user loses `@admin` as a category** (w5/m110): `default on >$(VALKEY_PASSWORD) ~* &* +@all -@admin +config|get +client|list +slowlog|get +slowlog|len`.

- Every data, keyspace, scripting and pub/sub command stays, including `FLUSHALL`.
- So does read-only introspection: `INFO`, `CONFIG GET`, `CLIENT LIST`, `SLOWLOG GET`/`LEN`.
- Everything in `@admin` answers `NOPERM`, so a new admin verb is denied by default. That covers:
  - `CONFIG SET|REWRITE|RESETSTAT` (the memory budget and eviction policy the dashboard shows);
  - `ACL SETUSER|LIST|…` (the revealed password; it also hides the platform user);
  - `SAVE`/`BGSAVE`/`BGREWRITEAOF` and `SYNC`/`PSYNC` (persistence and backups are platform-managed);
  - `REPLICAOF`/`FAILOVER`;
  - `SHUTDOWN`, `DEBUG`, `MODULE`;
  - `MONITOR`, and `CLIENT KILL|PAUSE` over other connections.
- w4/191's thirteen-verb deny-list had left `SYNC`, `MONITOR` and `CLIENT KILL` open.

**The control plane logs in as its own ACL user, `bex`** (`+@all`). Its password is in the immutable `<id>-platform` Secret, which nothing names in status and no API reveals.

- That user runs the live persistence handoff (`CONFIG SET appendonly`), the metrics exporter's `INFO` scrape and the backup's `--rdb` replication.
- So a tenant restriction can never lock them out. w4/191 had: the handoff ran as `default` and every Snapshot → Journal + Snapshot switch wedged in `PersistenceTransitionFailed`.
- A store whose serving process predates the user is first rolled once in its current Snapshot mode to add it, then journaled from the new process. This is the same ordinary restart any template change makes.
- The readiness probe stays on `default`, because `PING` is not `@admin`.

Verified with `ACL DRYRUN` on both pinned images (Valkey 7 and 8) booted with the StatefulSet's own args (`keyvalue_persistence_engine_test.go`).

**Divergence from Render.** Render documents no command list today. Its forum shows `CONFIG` (including `CONFIG GET`) refused, `SAVE`/`BGSAVE` disabled, and `CLIENT` allowed. bex matches that except that `CONFIG GET` stays readable: tenants have relied on it since w4/191, and it exposes nothing they don't own. Change these settings through the API, which reconciles them durably.

The persistence-transition helper instance is exempt from all of this: it listens only on a private unix socket and is driven by the operator itself.

### 9. Connection limits (w6/m456, 2026-11-17)

Every store accepts exactly the client connections its plan allows on Render ([compute plans § Render Key Value plans](https://render.com/docs/compute-plans#render-key-value-plans), read 2026-11-17: "Specify a compute plan to determine the instance's available RAM and connection limit", [Key Value](https://render.com/docs/key-value)). The figure is each plan's in `connlimit.Valkey` (`lego/types/tiers/connlimit`), which `tiers` copies into each `valkey` tier's `ConnectionLimit` (§ 10, w6/154), pinned per plan id and Render size alias by `TestValkeyConnectionLimitsMatchRender`:

| plan (Render id) | `free` | `starter` (`256mb`) | `standard` (`1g`) | `3g` | `pro` (`5g`) | `pro_plus` (`10g`) | `pro_max` (`20g`) | `pro_ultra` (`40g`) | `50g` |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| connections | 50 | 250 | 1,000 | 3,000 | 5,000 | 10,000 | 20,000 | 40,000 | 50,000 |

**Enforcement.** Before m456 `valkey-server` ran Valkey's default 10,000 clients, and `kv-internal-proxy` capped each of its two listeners at 1,024 and closed the excess. A free store took 2,048 connections and a `pro` store stopped at 1,024.

- `kv-internal-proxy`, in front of every tenant connection, with or without internal authentication (w6/m463), holds the plan's limit as **one budget across its plain and TLS listeners** (`BEX_KV_MAX_CONNECTIONS`). The next client reads `-ERR max number of clients reached`, byte for byte Valkey's own refusal, and no upstream is dialed for it.
- `valkey-server` starts with `--maxclients` set to the limit plus a **platform reserve of 10**: the readiness probe, the exporter's scrape, the proxy's readiness check (two during its rollout), the operator's runtime passes and a backup snapshot never queue behind a tenant at its limit. A plain client that the server itself refuses (one that reached it some other way) gets the server's refusal through the proxy instead of a closed connection.
- The backup snapshot dials the `<id>-backend` Service, not the proxy, so it uses the reserve and never one of the tenant's connections.
- The proxy's memory limit scales with the plan: 32 Mi plus 48 KiB per connection, never below the 128 Mi every proxy had. At 5,000 idle connections the proxy's cgroup held 195.7 MB (measured on Valkey 8, linux/arm64), about 39 KB per connection, so a fixed 128 Mi would OOM at about 3,300.

**The refusal on TLS.** Valkey writes nothing to a TLS client past its `maxclients`: it refuses before the handshake and drops the connection (`acceptCommonHandler`; reproduced on the pinned Valkey 8 image as an `SSLEOFError`). So a TLS client past the budget is answered by the proxy itself. It completes the handshake with the store's own certificate (the `<id>-kv-tls` Secret, mounted optional into the proxy as into the server) and writes the same refusal. The certificate is read at each refusal, so a renewal applies at once. At most 16 refusals are answered at a time per listener, and past that the client is closed. The proxy pod gains no new authority: it already holds the tenant password, and the certificate is the store's own.

**Existing stores restart for nothing.** A StatefulSet template written before m456 keeps its flagless server args whenever the limit is the only difference and the running server can be lowered to the plan's figure. Each pass then sets the running process with `CONFIG SET maxclients` as the platform user and records the value on the StatefulSet (`app.bex.co/valkey-maxclients: <limit>/<its process>`), so a settled store is not dialed again until its container restarts. The record cannot go on the pod: the `bex-operator-pod-labels` admission policy lets the operator change no Valkey pod annotation, and production refused the first rollout's pod record on every pass. The held limit goes through the same template write as the held priority class (`holdDatastorePriority`) and environment labels (`holdIsolationLabel`), so changes that roll nothing hold together. In the first rollout they did not: each hold read the other's pending change as a reason to roll, so two production stores that were still waiting to adopt the priority class or the environment label restarted once at 12:10Z on 2026-11-17 (w6/m456 t006, `TestKeyValueClientLimitHoldsBesideTheOtherDeferredChanges`). The fixed operator held on production (w6/m456 t011, 2026-11-17): it recorded the third store's 260 with its server still the process started on 2026-11-12, and a free probe whose template was edited back to no `--maxclients` and no priority class rolled once for the edit, then ran 60 by `CONFIG SET` with no second roll across 7 minutes of reconciles. A server started without the flag can only be lowered at runtime. Valkey sets its own open-files limit to `maxclients` + 32 at start (all three production stores ran at 10,032), so `CONFIG SET` cannot take it past 10,000. A pre-m456 `pro_plus`, `pro_max`, `pro_ultra` or `50g` store therefore rolls once to start with its flag. Lowering below the clients already connected keeps every one of them and refuses new ones until the count drops (`TestValkeyRuntimeMaxclients`, both pinned images).

**A plan change** rewrites the pod's CPU and memory, so the StatefulSet rolls as it always has, and as Render's does ("Upgrading requires a restart", [Key Value](https://render.com/docs/key-value), read 2026-11-17). The new server starts with the new plan's `--maxclients`, and the proxy's budget follows in its own rollout. The limit adds no restart of its own.

**External connections (w6/m457).** `kv-sni-proxy` admits each public store's route up to twice its plan's limit (`sniproxy.RouteCapacity`, of the plan's `connlimit.Valkey` figure on every watch event), under the same process caps as `pg-sni-proxy` ([ADR009 § External connection admission](ADR009-postgresql-management.md#external-connection-admission-w6m457-2026-11-17)): no per-workspace cap, no per-source cap by default, 128 handshakes per network and 4,096 connections per replica. Before, the 65th external client of any store was closed after its ClientHello. Now the client past the plan's limit reaches `kv-internal-proxy`, which completes TLS with the store's certificate and writes Valkey's refusal. `TestAStoreAtItsLimitAnswersTheNextExternalClientWithValkeysRefusal` drives a `starter` store through both proxies: 250 external TLS clients are relayed, and the 251st reads `-ERR max number of clients reached`. Verified on production on 2026-11-17: from a host on the store's allowlist, a `starter` probe held 250 external TLS clients (each `AUTH` and `PING` answered), the 251st read `-ERR max number of clients reached`, and no `kv-sni-proxy` replica counted a rejection. Like `pg-sni-proxy`, it sets no idle or lifetime bound on a routed stream (w6/149), as Valkey sets none: its `timeout` is `0` by default and "does not apply to Pub/Sub clients" ([valkey.io/topics/clients](https://valkey.io/topics/clients/)). `BEX_KV_PROXY_IDLE_TIMEOUT` and `BEX_KV_PROXY_MAX_LIFETIME` are unset incident levers. The edge load balancer still closes a stream that has carried no data for an hour, so a `SUBSCRIBE` client that gets no message for that long is closed there (ADR009, same section; ADR018).

**Stores with internal authentication (w6/m463, 2026-11-17).** Until w6/m463, `spec.internalAuth` (w5/m268) retired the proxy and pointed `<id>` at `valkey-server`, so those tenants met only the server's bound, the plan's limit plus the reserve of 10, and could hold the reserve, locking out the probe, the exporter and the operator. No production store had internal authentication then. Now the proxy stays in front of those stores too, and `<id>` routes through it on both ports:

- Its plain listener runs in **plain passthrough** (`BEX_KV_INTERNAL_AUTH=client`, `kvinternalauth.PlainPassthrough`): it forwards the client's bytes unchanged and writes nothing of its own upstream, so the client's own `AUTH` decides its access, and a client without the password reads Valkey's `-NOAUTH`. It draws on the same budget as the TLS listener. The client past it reads `-ERR max number of clients reached` in plain text, and a refusal from the server itself passes through unchanged.
- **The readiness check still authenticates**, so the proxy pod keeps the default user's password for `--check` only. Valkey answers an unauthenticated `PING` with `-NOAUTH` before it looks at loading, so a check without the password could not tell a loading server from a ready one, and w1/m166's readiness would regress. The pod held the password before this change, so it gains no authority.
- The backup snapshot dials `<id>-backend` for every store, so it uses the reserve.
- Enabling internal authentication rolls only the proxy (§ 2).
- A store that enabled it before w6/m463 adopts the proxy like any other store at the w8/204 cutover: `<id>` keeps selecting Valkey until its proxy is ready, so it never loses its endpoint.

Verified on production on 2026-11-18 (pin `359aee37d`), on free probes in `bex-canary`:

- Enabling internal authentication closed a held unauthenticated client 4 s later, and new unauthenticated clients read `-NOAUTH`. Valkey's `run_id`, restart counts and StatefulSet revision did not change.
- 50 authenticated clients were admitted on the internal URL and on the external TLS URL (from an allowlisted host). The 51st read `-ERR max number of clients reached` on both, inside TLS on the external one.
- While a tenant held the 50, the store stayed Ready, Prometheus kept scraping `redis_up` 1, a snapshot over `<id>-backend` transferred the RDB, and a maxmemory-policy change applied within seconds.

**Where the limit is shown (w6/m459).** As on Render's dashboard ([render-artifacts/key-value.md](render-artifacts/key-value.md#where-render-shows-the-connection-limit-w6m459-t001-2026-11-17), read 2026-11-17), every plan card on the create page and in the detail page's plan picker states its limit on a line under the RAM ("50 connections"), the Details card has a Connection limit row beside Instance type (Render's Key Value Instance card), and the Metrics tab's Active Connections chart reads "Limit N" beside its title, the title Render gives it. Each reads `connectionLimit` from GraphQL `keyValueInstanceTypes`, never a frontend table. The catalog stays a GraphQL-only bex extension: Render has no plan-catalog endpoint, so REST and MCP carry none. Render's Postgres plan cards show no connection limit, so bex's do not either ([render-artifacts/postgres-connection-limit.md](render-artifacts/postgres-connection-limit.md)). Verified on production 2026-11-17 (pin `e36296ae8`): the create page's cards read Free "50 connections" through 50 GB "50,000 connections", and a Starter store's Details card, plan picker and chart read 250.

### 10. A platform deploy rolls no store's proxy (w6/m469, w6/m470, 2026-11-18)

`kv-internal-proxy` runs out of the operator's own image, and until w6/m512 a proxy pod that stopped closed every connection it relayed (`kvinternalauth.Serve` on `SIGTERM`). Until w6/m469 every operator deploy wrote the new operator digest into every store's proxy template, so each of the 11 production deploys on 2026-11-17 closed every tenant connection to every store. Render breaks a store's connections when the customer changes the store (a plan change, enabling internal authentication: "Render restarts your Key Value instance", [Key Value](https://render.com/docs/key-value)), not when Render ships its own platform.

**The rule (w6/m469, superseded by w6/m517).** From w6/m469 a store's proxy rolled when its binary, env, pod annotations or resources changed, never because the operator's image changed. w6/m517 made the rule stricter: a proxy's whole pod template now waits for the store's own roll (below). Once production had adopted every proxy into that hold (2026-11-19 21:15Z), w6/m517 t006 removed the image hold's code. While it ran:

- At startup the manager hashed the `/kv-internal-proxy` in its own image (sha256).
- Each proxy Deployment recorded the hash of the binary its pod template's image carried, in its own `metadata.annotations["app.bex.co/kv-internal-proxy-sha256"]`, never on the pod template, because adding it there would have rolled every proxy once. Deployments written before w6/m517 t006 still carry the record, and nothing reads it.
- While the record equaled the manager's hash, the proxy kept the image it ran. Otherwise it took the manager's image, and the record followed.
- Every other template field was rendered as always, so enabling internal authentication, a credential rotation, a plan change or a suspension rolled the proxy on the held image, which ran a byte-identical binary.
- A manager that could not read its binary (`make run`), or whose image was overridden by `BEX_BACKUP_HELPER_IMAGE`, held nothing: the proxy followed the operator's image as before.

**Why a hash is enough.** The build is reproducible. `/kv-internal-proxy` links only the standard library and `kvinternalauth`, and the `lego/` build context carries no VCS stamp, so its bytes change exactly when its code or the Go toolchain does. Hashed out of six production images from 2026-11-17, the binary changed exactly at w6/m456 and w6/m463: at most 2 of that day's 11 deploys would have rolled a proxy. The held digest can be weeks old. GHCR keeps every `bex-operator` version, and no workflow deletes one.

**Adopting a proxy with no record (until w6/m517 t006).** A Deployment written before w6/m469 recorded no hash. For it the operator read `/kv-internal-proxy` out of the Deployment's current image in its registry with `registry.ImageFileSHA256`, which `cmd/proxy-pin` still uses for the SNI pins below. That function reads the image index, this architecture's manifest and its config through the same bounded, digest-verified reader as an image's ports (`ReadImageConfig`), with an anonymous pull token. Then it downloads the one layer added by the binary's `COPY` history entry, at most 64 MiB within 30 s, and checks it against its digest too. Only a digest reference whose binary was byte-identical kept its image, and the hash was then recorded. Any doubt rolled the proxy as before: a tag, a missing build step, a registry error or a different binary. Recording a hash bumps the Deployment's generation, because the API server copies a Deployment's annotations to its ReplicaSet, but it creates no new ReplicaSet and replaces no pod.

**The SNI proxies (w6/m470, 2026-11-18).** `bex-kv-sni-proxy` and `bex-pg-sni-proxy` front every store's and database's external TLS connections, and close them all when a pod stops. Until w6/m470 they took their image from the `controller=` pin, so every operator deploy rolled both and closed every external Key Value and Postgres connection ([w6/141](../.pm/w6/done/141.md)). Kustomize, not the operator, gives them their image, so the hold lives in `deploy.yml`:

- Each DaemonSet carries its own placeholder (`kv-sni-proxy:latest`, `pg-sni-proxy:latest`), pinned separately beside `controller=` in `deploy/gitops/base/bex.yaml`. `config/default` never maps them: its build runs first, so an entry there would rename them before Argo's outer `kustomize edit set image` could match them.
- The write-back moves `controller=` to the new digest as before. For each SNI pin it runs `lego/operator/cmd/proxy-pin`, which reads `/kv-sni-proxy` (or `/pg-sni-proxy`) out of the pinned image and the new one through `registry.ImageFileSHA256`, for `linux/amd64`, production's platform, whatever the runner's architecture. The pin stays while the two are byte-identical and moves to the new digest otherwise (`scripts/operator-pins.sh`).
- Any doubt moves the pin, which every deploy did before: a registry error, a missing build step, a command that did not build. None of them fails the deploy.
- The pin holds the image, not the template. An env, probe or resource change in a DaemonSet manifest still rolls it, on the held image.
- The PROXY-protocol wait expects, per DaemonSet, the digest pinned for it. A held image runs byte-identical bytes, so it is exactly as header-capable as the new one.
- `scripts/deploy-superseded.sh` and the write-back's own check treat the three pins in `bex.yaml` as generated fields, each matched exactly once. `scripts/gitops-validate.sh` renders `config/prod` under three distinct digests and checks that each lands on its own workloads.
- A new placeholder needs two commits. The first adds its pin to `bex.yaml`, and the second, after the root app `bex-platform-prod` has synced the first, makes a manifest use the placeholder. `bex-operator` reads `main`'s manifests on its own refresh, but its image list comes from the Application spec, which only the root app updates. When w6/m470 shipped both changes in one commit, `bex-operator` synced the manifests about 2 minutes before the root app updated the spec. It rendered the bare `kv-sni-proxy:latest` and `pg-sni-proxy:latest`, and one node's two SNI pods sat in `ImagePullBackOff` for about 3 minutes (2026-11-18 06:53–06:56Z, [w6/m470 t006](../.pm/w6/done/m470/done/t006.md)).

**What moves an SNI binary (w6/150, 2026-11-20).** Both binaries link `k8s.io` and controller-runtime, so they change more often than `/kv-internal-proxy`. A Go binary changes with any source edit in a package it links, comments and code it never calls included, because the build ID it embeds hashes every source file of every linked package. Test files leave it alone. Until w6/150 both proxies linked `lego/types/v1alpha1` for the `KeyValue` and `Database` types, so every CRD edit moved both pins. Of the 128 production pins from 2026-11-01 to 2026-11-20, 50 followed a commit touching a package either proxy linked, and 27 of those touched no such package but `lego/types/v1alpha1`.

- **Routing views.** Since w6/150 the proxies watch both kinds through views in `internal/sniproxy/crd.go`. They decode only the fields the routes read: the plan, `public`, the three allowlist layers' CIDRs, the pooler flag and each read replica's name for a `Database`, and the published `status.externalHost` for a `KeyValue`. They register under the CRDs' group and kinds, and the decoder drops the rest of the API server's JSON. `pg-sni-proxy` names a replica's labels with its own copy of the operator's `ReadReplicaServiceName` and `ReadReplicaPoolerName`. Neither binary links `lego/types/v1alpha1`, so a CRD edit leaves both byte-identical and the deploy keeps both pins.
- **The proof.** `TestACRDFieldEditLeavesBothProxiesByteIdentical` lists both binaries' dependencies and fails on any bex package outside `internal/sniproxy`, `types/env`, `types/netutil`, `types/proxyproto` and, since w6/154, `types/tiers/connlimit`. It then builds both before and after a field added to `KeyValueSpec` and `DatabaseSpec` through a build overlay, and compares their sha256. Built as the image builds them (`linux/amd64`, no workspace), the same edit changed both binaries on the tree before w6/150 and neither after it.
- **The contract.** `TestTheViewsReadTheCRDContract` checks every view field against the CRD's at the same JSON path and of the same kind, and `TestTheReplicaLabelsAreTheOperators` checks the replica labels against the operator's names. A routed field renamed or retyped in `v1alpha1` fails them until the view follows, and that edit then rolls both proxies, as it must. A change to either view rolls both, because one package holds them.
- **What still moves a pin.** Of the other 23 pins: the proxies' own code (8), the `tiers` catalog (8, most of them for compute plans and serving pools no proxy reads; since w6/154 only a connection limit, below), `lego/Dockerfile` (5, which changes the binaries only when it changes the Go toolchain or the build flags), and `operator/go.mod` (2).
- **Connection limits (w6/154, 2026-11-20).** Both proxies size each route from its plan's connection limit. Until w6/154 they read it from `lego/types/tiers`, which embeds the whole `tiers.yaml` and every compute tier, so a compute plan or serving pool edit moved both pins ([w6/154](../.pm/w6/done/154.md)). The limits now live in a package of their own, `lego/types/tiers/connlimit`: Render's limit for each Key Value plan (`connlimit.Valkey`), each Postgres plan's `max_connections` (`connlimit.Postgres`) and PgBouncer's `max_client_conn` (`connlimit.PostgresPoolerMaxClientConn`). The proxies link it and nothing else of the catalog.
  - **`tiers` builds on it.** It fills each datastore tier's `ConnectionLimit` or `MaxConnections` from `connlimit`, and refuses to load a datastore plan `connlimit` gives no limit, or a Postgres or Key Value default other than `connlimit`'s. `tiers.yaml` carries no limit, and its strict decoding refuses `maxConnections` and `connectionLimit`. The proxies resolve a plan with `connlimit.Valkey.Resolve` and `connlimit.Postgres.Resolve`, the rule of `tiers`' `Resolve`: the plan's own limit, or the default plan's for an empty or unknown one.
  - **The two stay in step.** `TestConnectionLimitsAreTheCatalogs` checks that each ladder names exactly the catalog's plans, and that every plan, an empty one and an unknown one resolve to the same limit on both sides. `TestRouterCarriesEachStoresCapacityFromThePlan` and `TestRouterCarriesEachRoutesCapacityFromThePlan` check that the routes of every plan the catalog or `connlimit` names admit twice the figure the operator gives the server.
  - **What still rolls them.** An edit to `connlimit` rolls both, as a figure the routes read must, so a datastore plan added to the catalog rolls them with its limit. `TestACatalogEditLeavesBothProxiesByteIdentical` builds both proxies before and after an overlay that changes the free compute tier's CPU, `pro-plus`'s serving pool and `tiers.go`, and expects both byte-identical. Then it builds them after a `connlimit` edit and expects both changed. Built as the image builds them (`linux/amd64`, no workspace), the same `tiers` edit changed both binaries at `d9c5bfed1` and neither after w6/154. Of the commits behind the 8 `tiers` pins above, only `0eed45bcb` (the Key Value limits) and `22287e974` (four new Key Value plans) changed a figure `connlimit` now holds.
  - **A limit published on the CR was rejected.** A `status` field the operator writes would reach the routes without a roll. But it needs a CRD field, it lags a plan change, and the proxies would still need a size for a route whose status the operator has not written yet: a new store, or every store while a deploy rolls the proxies before the operator. A limit edit is rare, so it keeps its roll.

A content-addressed image per proxy was rejected: it needs two more GHCR packages with signing, SBOM and the CVE gate and a reproducible image config, and would still roll on every distroless base bump.

**A roll that changes the proxy drains (w6/m512, 2026-11-19).** Until w6/m517 a deploy that changed `/kv-internal-proxy` rolled every store's proxy, and until w6/m512 that roll closed every stream at once, so each command in flight failed ([w6/142](../.pm/w6/done/142.md)). Since w6/m517 only the store's own change or an override bump rolls a proxy, and that roll drains.

- **A pause first (w9/135, 2026-11-21).** The deleted pod sleeps 5 s in `preStop` while it still accepts, because its endpoint takes a moment to leave every node's service rules, as the SNI proxies' does (w6/m515, below). Without it, a client in a same-workspace pod that dialed `<id>:6379` every 200 ms while enabling internal authentication rolled the proxy read 3 `Connection refused` within 0.6 s after 29 `PONG`s, on the local cluster with Valkey untouched (w9/m521 t001). The pause is part of the pod template, so it reaches each store at its own next roll, like any rendering change, and no override bump brought it: a store's first roll after w9/135 can still refuse a dial for that moment, because its old pod was written without the pause.
- **The drain.** On its first `SIGTERM` the old pod closes both listeners, so it accepts nothing new while the Service sends new clients to the Ready new pod (`maxSurge: 1`, `maxUnavailable: 0`). Every open stream keeps relaying until its client or Valkey closes it. Whatever is still open after `BEX_KV_DRAIN_SECONDS` closes, and the process exits as soon as its last stream ends. A second signal closes everything at once. Unset, the proxy closes at once as before, so `make run` and older templates behave as they did.
- **The bound is 30 s**, with `terminationGracePeriodSeconds: 40` (35 before w9/135): the kubelet counts the pause against it, and the last 5 s let the process close what is left itself before `SIGKILL`. 30 s is Render's default shutdown delay for its own instances ("If your app's process doesn't exit within its specified shutdown delay (default 30 seconds)", [deploys](https://render.com/docs/deploys), read 2026-11-19). Render documents no figure for Key Value. A command in flight finishes in milliseconds, and the pod leaves as soon as it is idle, so the bound only decides when a held client is closed. It also caps how long a node drain waits for a proxy. The env and the grace period rode in the same template write as the image the changed binary brought, so w6/m512's own deploy rolled each proxy once. That roll still closed at once, because the old pods ran the old code.
- **The reserve.** A draining pod's streams still count in Valkey, and the new pod admits up to the plan's limit on a budget of its own. Measured on both pinned images (`TestADrainingProxyLeavesTheReserveToThePlatform`): when a free store's tenants held 50 clients through the old pod and reconnected 50 through the new one, they took all 60 of Valkey's slots, and a platform-user dial was refused. So, while it drains, the old pod reads `INFO clients` every 100 ms as the default user (`kvinternalauth.KeepReserve`; the pod held that password already, for `--check`). Whenever the store has more clients than the plan's limit besides that connection, it closes as many of its own draining streams. The new pod's tenants then always connect, and the readiness probes, the exporter and the operator keep the reserve. Platform clients count toward the limit here, so a tenant at its limit can lose a draining stream a few seconds before the deadline. Three other fixes were rejected. Letting `--check` treat a full server as ready still leaves Valkey's own probe, the exporter and the operator refused. No shorter bound helps, because a tenant can open 10 connections within any window. Raising `--maxclients` restarts every store, since Valkey lowers its own open-files hard limit to the start value (§ 9).
- **Rolls that must cut at once.** Enabling internal authentication must still close every connection the old pod authenticated ("Any existing connections that use your unauthenticated URL will break", § 2). The old pod cannot learn why it stops, because its env and grace period are fixed when it is created. So the operator closes those connections in Valkey. On each pass while a terminating proxy pod's `BEX_KV_INTERNAL_AUTH` differs from the store's mode, it lists Valkey's clients as the platform user and kills every client from that pod's IP (`CLIENT LIST`, `CLIENT KILL ID`). It repeats every second until the pod is gone, and proxy pod events enqueue the store. The old pod still serves until the new one is Ready, as in w6/m463, so the store keeps an endpoint, and through its pause, so a client it accepts then is cut within a second too. No RBAC is added (the operator already lists and watches pods), and the proxy gains no authority.
- **No other roll needs the cut.** A credential rotation, a plan change and a suspension change Valkey's template too, so its restart closes every upstream connection, which ends the old pod's drain. Making a store private changes no proxy template, because the proxy forwards its TLS port while the store's server can listen (§ 3). The `kv-sni-proxy` route decides who reaches that port, and dropping a route has never closed its open streams (`cmd/kv-sni-proxy`); this milestone changes neither.

**A proxy's template waits for the store's own roll (w6/m517, 2026-11-19).** The drain lets a command in flight finish, but a held client (a pool, a pub/sub subscriber, a blocking command longer than 30 s) was still closed at its end, without notice, on each deploy that changed `/kv-internal-proxy` or the proxy's rendering: 2 of the 11 production deploys on 2026-11-17, and the proxy changed in each of w6/m456, w6/m463 and w6/m512 within three days ([w6/145](../.pm/w6/done/145.md)). Render breaks a store's connections when the customer changes it, and for its own infrastructure only in service-affecting maintenance that "usually occur[s] no more than once every three months", announced by email and reschedulable for a paid service ([platform maintenance](https://render.com/docs/platform-maintenance), read 2026-11-19). Each of those three changes also changed the rendering in the same commit, so an image-only deferral would have deferred none of them: the hold covers the whole template.

- **The rule.** A proxy Deployment's pod template stays exactly as it runs, whatever the manager's image, binary or rendering (`keyValueInternalProxyRoll`). It moves only when the Deployment is new, when it runs no pod before or after the pass (a suspension or a resume, which starts from no pod), when the store's roll inputs changed since the template was written, or when the override asks for it. It then takes the manager's image and the full current rendering in one write, so the store's change brings every pending platform change with it in a single roll. Replicas, strategy and selector are rendered on every pass, so suspension and resume work as before.
- **The roll inputs** are what the customer's change writes into the template: the plan and its connection limit (`BEX_KV_MAX_CONNECTIONS`, the memory limit; Valkey's `maxclients` follows the plan at runtime, § 9, so the proxy's budget does too), `spec.internalAuth` (`BEX_KV_INTERNAL_AUTH`), the credential revision and its Secret, and whether the TLS port is forwarded and from which Secret (making an older store with a static listener public; a runtime-switch store always forwards it, § 3). Their sha256, over one `name=value` line each, is recorded in the Deployment's own `metadata.annotations["app.bex.co/kv-internal-proxy-inputs"]`, never on the pod template, which would roll every proxy once. A plan change, a credential rotation and a suspension also restart Valkey, which closes every upstream connection anyway. Enabling internal authentication rolls only the proxy, and the cut above still closes the old pod's clients.
- **Adoption.** A Deployment that records no inputs (written before w6/m517) takes the current rendering on the manager's image. One whose template already equals it is recorded without a template change: its generation moves, but no ReplicaSet is created and no pod is replaced. Any other rolls once and is held from then on. A template written before w6/m512, without the drain env, is one of those. w6/m517 shipped only after w6/m512's production roll was recorded, and its comparison still kept a proxy's image while it carried the manager's binary (w6/m469). So the deploy that shipped it (pin `def3eb4883de`, 2026-11-19 21:15Z) recorded all three stores' proxies, which ran an older image with the same binary, without a roll ([t005](../.pm/w6/done/m517/done/t005.md)). w6/m517 t006 then removed the image hold, so a Deployment that records no inputs and runs another image now rolls once onto the manager's.
- **The override.** `kvInternalProxyRollRevision` is a constant, recorded in `app.bex.co/kv-internal-proxy-roll-revision`. A Deployment that records a lower revision takes the rendering on the next pass and records the constant, so a bump rolls every store's proxy once, after the drain, and never again until the next bump. A missing or unreadable record takes the rendering too, and a higher record (left by a newer operator before a rollback) stays. Bump it in a reviewed commit, only for a security fix in the proxy or its template, or for a held template that can no longer work. There is no env var or flag: that would be an unreviewed production lever, and the manager restarts on every deploy anyway. `TestKeyValueInternalProxyRenderingIsPinned` pins the rendered template of four fixture stores (plain and TLS-forwarding, each with and without internal authentication) and their inputs digest. A rendering change fails it with the decision to make: the change reaches each store only at its next own change, bump the revision if that is not acceptable, and update the pin either way. An inputs change fails it too, because it rolls every proxy at once, as a bump does.
- **Held templates must keep working.** While any proxy may run an older template and binary, the operator must not rename or remove what one relies on: the `<id>-backend` Service and its ports, the auth and TLS Secrets it mounts, the pod labels its NetworkPolicy and the internal-auth cut select (`reconcileKeyValueInternalProxyPolicy`), and the `--check` readiness command. A change that breaks one of them bumps the override in the same commit.
- **No time ceiling.** A ceiling would bring back an unannounced close, rarer but the same divergence: Render does not break a paid store's connections without notice, and bex has no maintenance-notice surface (`.pm/DO_NOT_DO.md` lists maintenance runs as a non-goal). Render "might perform maintenance on a free service at any time, without advance notice" (same page), so rolling free stores at once would be Render-consistent, but one rule holds for every plan.
- **What still closes a held client:** the store's own change (a plan change, enabling internal authentication, a credential rotation, a suspension), an override bump, a node drain or an eviction. Each roll drains for 30 s, except the internal-auth cut, which closes the old pod's clients within seconds.

**An SNI-proxy roll drains too (w6/m515, 2026-11-19).** `bex-kv-sni-proxy` and `bex-pg-sni-proxy` roll on every deploy that changes their binary, which any `lego/types/v1alpha1` edit did until w6/150 and any `lego/types/tiers` edit until w6/154 (above). Until w6/m515 each such roll closed every external Key Value and Postgres stream at once. And while the old pod held the node's `hostPort`, the new pod could not start there, so the node admitted no new external client either ([w6/144](../.pm/w6/done/144.md)).

- **Surge, with no host port.** Both DaemonSets roll with `maxSurge: 1` and `maxUnavailable: 0`, and ask for no `hostPort`. The edge LB reaches them through the `externalTrafficPolicy: Local` NodePorts 31056 and 31892 (`config/prod`), so each node's new pod becomes its local endpoint and is Ready before the old pod is told to stop. The `hostPort` served only ADR009's dev edge. It also kept a second pod off the node, and PodSecurity `baseline` refused it on the local cluster, where neither proxy could run.
- **A pause, then the drain.** The deleted pod first sleeps 5 s in `preStop` while it still accepts, because its endpoint takes a moment to leave every node's service rules. On the local cluster, a pod that stopped accepting at once refused a new client in that moment. Then `SIGTERM` closes the listener, and every open stream relays until its client or the backend ends it. Whatever is still open after `BEX_KV_PROXY_DRAIN_SECONDS` or `BEX_PROXY_DRAIN_SECONDS` closes, and the process exits as soon as its last stream ends. A second signal closes everything at once. Unset, a proxy closes at once as before. `terminationGracePeriodSeconds` covers the pause, the bound, the wait for a final scrape below and a margin (3,645 s since w6/151, 3,610 s from w6/m518, 40 s before). The manager stops with the signal, so a draining pod's routing table is frozen, and open streams never consult it again.
- **The bound is 3,600 s (w6/m518, 2026-11-20),** which was then the proxies' 1 h idle timeout. w6/m515 shipped 30 s, Render's default shutdown delay as for `/kv-internal-proxy` above, because two gates read each node's oldest pod, so they waited for every draining pod (on the local cluster, 91 s for a 90 s drain). [w6/m518](../.pm/w6/done/m518/README.md) made both read each node's new pod, then raised the bound:
  - **The deploy's wait.** `scripts/operator-pins.sh wait` no longer runs `kubectl rollout status`. After the image wait it passes once the DaemonSet has observed its generation and every node it should run on runs a Ready, non-terminating pod of the current template (`pod-template-generation`). A new pod that never becomes Ready still fails it after 300 s.
  - **The health signal.** Argo's built-in DaemonSet check is `rollout status`'s rule, so `bex-operator` read Progressing for every second of a drain, and `PlatformGitOpsUnhealthy` fires after 15 m. The operator keeps `app.bex.co/new-pods-ready: "<generation>/<nodes>"` on both SNI DaemonSets while every node runs such a pod (`SNIProxyRolloutReconciler`). `deploy.yml` installs `deploy/argocd/daemonset-health.lua` as `argocd-cm`'s DaemonSet check: the built-in rule, plus Healthy where the annotation matches the generation and the node count. Every other DaemonSet reads as before, and a new pod that never becomes Ready still reads Progressing and still fires the alert, whose rule and window are unchanged. Releasing the old pod from the DaemonSet was rejected: it would also leave the Services' endpoints and the scrape, and become an unmanaged pod to every drainer.
  - **Why an hour.** With a surge, the drain no longer holds the edge, and Kubernetes evicts no DaemonSet pod in a node drain, so no gate waits for the bound. An external stream that carries no data for an hour is closed anyway, by the proxies' idle timeout until w6/149 and by the edge load balancer's since (ADR009 § External connection admission), and a stream that never ends is closed once whatever the bound, so a longer bound would only keep old pods on their nodes. `TestTheDaemonSetGivesTheDrainItsBound` keeps the bound at most an hour, and at most the proxies' idle timeout when one is set as an incident lever. A draining pod accepts nothing, requests 32 Mi and keeps its metrics listener, so a deploy within the hour schedules a third pod per node, and Prometheus scrapes it until it exits.
- **Every byte reaches a scrape (w6/151, 2026-11-20).** Until w6/151 a stream's backend→client bytes were added to `bex_kv_proxy_egress_bytes_total` or `bex_pg_proxy_egress_bytes_total` only when it closed, and the process exits with a drain's last stream. So the bytes of that stream, and of every stream the bound closed, never reached a scrape (production, below).
  - **Counted as delivered.** `sniproxy.CopyBidirectional` adds each write to the counter as it reaches the client, so a scrape taken while a stream runs reads what it has delivered. A long stream is billed in the hours it ran, not in the hour it closed, and a crash or a lost node loses at most what a pod copied since its last scrape. The copy is a read-write loop with a 32 KiB buffer, as it was for every stream until w6/149 removed the default bounds: `io.Copy` splices on Linux and reports nothing until the stream ends.
  - **The exit follows a scrape.** Once a drain's last stream has ended, the process keeps its metrics listener until a Prometheus scrape that began after that moment has been served, for at most `sniproxy.FinalScrapeWait`: 35 s, two of the jobs' 15 s scrapes and 5 s for the second to finish. That scrape reads every byte the pod counted. A scrape is a request with Prometheus's `X-Prometheus-Scrape-Timeout-Seconds` header, so the kubelet's readiness probe on the same path never stands in for one. A hard stop exits without waiting. The grace period grew to 3,645 s (5 + 3,600 + 35 + 5), so the wait also runs after a drain that reached its bound, and `TestTheDaemonSetGivesTheDrainItsBound` and `scripts/gitops-validate.sh` hold it there.
  - **Why even a pod with nothing new waits.** An exit just after a scrape leaves Prometheus a whole interval to drop the target. Before w6/151 an exit could fall just before a scrape, which then read `up` 0 from the dead pod and failed the hour for every store: on production the old pod `bex-kv-sni-proxy-5wkfv` exited with the streams its bound closed, and its target read `up` 0 at 09:51:11Z on 2026-11-20, 15 s after its last good scrape. So the hour ending 10:00Z billed no external Key Value egress. Postgres passed that hour: its old pod's target was gone before the next scrape. A pod with no stream now exits at the first scrape after `SIGTERM`, not at `SIGTERM`.
  - **What reaches the bill.** What w6/151 adds to the bill is the healthy hours a long stream ran through before its close. Until w6/155 a roll's own hours billed no external datastore egress: the health gate judged each proxy fleet at once, so an hour in which an SNI pod started failed its process-start term, and one in which a pod exited before 80% of the hour had passed failed its sample term, for every store of that kind.
  - **The drained scrape (w6/155, 2026-11-20).** The gate now judges each pod on its own ([ADR023 § The SNI sources are judged per pod](ADR023-usage-metering.md#the-sni-sources-are-judged-per-pod-w6155-2026-11-20)). A new pod passes because its counters started at zero inside the hour. An exiting pod passes only when its last successful scrape read `bex_kv_proxy_drained` or `bex_pg_proxy_drained` at 1: `AwaitFinalScrape` sets the gauge before it waits, so the scrape that releases the exit reads it, and a crash, a lost node or a forced deletion never does. Both jobs keep the gauge (`deploy/gitops/base/prometheus.yaml`). The pods a roll replaces run the binary of the roll before, so the first roll whose exits bill is the one after the pin that carries w6/155.

  - Neither session's bytes, nor those of the clients the bound closed, reached the scrape, because each pod counted a stream only when it closed and exited with its last one. [w6/151](../.pm/w6/done/151.md) fixed both (above).

**The gap that remains.** The internal proxy's unannounced close is gone: no platform deploy rolls a store's proxy since w6/m517. The SNI proxies keep a smaller gap, and the per-store deferral above cannot close it: one SNI pod serves every store and database on its node. Since w6/m518 an external session that ends within the hour (an interactive `psql` session, a migration, a long query, a batch job's subscriber) is never cut by an SNI roll. A client that keeps its connection busy for longer (a pool, a permanent subscriber) is still closed once, 1 h after the old pod's `SIGTERM`, without notice, on each deploy that changes an SNI binary. Render breaks such connections only in announced maintenance (above). Since w6/150 they roll less often: an edit to `lego/types/v1alpha1` leaves both binaries byte-identical, so the deploy keeps both pins, and at most 23 of the 128 pins from 2026-11-01 to 2026-11-20 would have moved them instead of 50 (above). Their own code, the Go toolchain, a dependency bump and the datastore limits in `lego/types/tiers/connlimit` (the rest of `tiers` since w6/154) still roll them. On production the deploy of pin `cce6c749f6ff` (2026-11-21), whose range edits `lego/types/v1alpha1` in five commits (two of them `DatabaseSpec`) and `tiers.go` but nothing either proxy links, kept both SNI pins and rolled neither ([w6/150](../.pm/w6/done/150.md)). Apart from rolls, the proxies close no stream since w6/149 (until then a stream silent both ways for an hour, and every stream at 24 h). The edge load balancer still closes one that carries no data for an hour, the gap [ADR018](ADR018-render-parity.md#other-datastores--storage) records.

## MVP scope

Ship only what fits the current single node — single-instance plans differing by compute + storage (above). The metered TLS/SNI front door is opt-in per store via `spec.public` + `BEX_KV_DOMAIN`; `BEX_CLUSTER_ISSUER` is also required so the operator can issue the backend certificate.

## Consequences

- Deferred to post-MVP: HA/replication (a Valkey replica/sentinel needs a ≥3-node worker pool), eviction/scale-to-zero for free-tier stores, and overage billing. Public TLS, outbound response metering, and paid-plan nightly off-cluster RDB backups are implemented. Free remains explicitly PVC-only.
- The REST/GraphQL/MCP surface (`list_key_value` / `get_key_value` / `create_key_value` + `/v1/key-value` CRUD/connection-info/suspend/resume + GraphQL `keyValue*`) shipped in w2/m7 on top of this mechanism; the dashboard shipped in w5/m12. The retired bex-only `list_key_value_instances` alias is no longer registered.
- **Version-change parity assessment (2026-07-16, w8/m16): no upgrade verb.** Render's official `keyValuePATCHInput` and legacy `redisPATCHInput` schemas list only `name`, `plan`, `maxmemoryPolicy`, `persistenceMode`, and `ipAllowList`; neither accepts `version`. Render's Key Value documentation likewise documents plan upgrades and states that new instances run Valkey 8 while legacy instances remain on Redis 6 without version updates. Therefore bex's create-time-only `spec.version` matches the absence of a Render version-change contract; no mirror milestone is warranted. Reassess only if Render adds a version field or explicit upgrade flow. **Amended by w4/743 (2026-11-27):** Render's create takes no version either (its form, `keyValuePOSTInput` and MCP `create_key_value` have none), so bex's create no longer does: every new store runs Valkey 8, and `spec.version` is read-only history that keeps a pre-w4/743 Valkey 7 store on its major.
