# ADR097 — Render Build Sources on bex: a build-only carrier App and per-service image copies

**Status:** Accepted, 2026-11-03 (w2/m254 t001). Implementation tracked in `w2/m254`. Render parity: no divergence intended; any found during implementation is recorded in [ADR018](ADR018-render-parity.md).

## Context

Render's public API gained **Build Sources** (round-5 drift, w2/m251): a workspace object that builds once (git-backed) or names an external image (image-backed), owns its own build-time environment (env vars, secret files, linked env groups), keeps a build history, and is linked to any number of services. A linked service carries `buildSourceId`; it takes all source and build configuration from the build source (create omits `repo`, `branch`, `image`, `buildFilter`, `runtime` and build-time env), and a git source must be in the service's region (`build_source_region_mismatch`). Triggering a build (`POST /build-sources/{id}/builds`) builds the branch head even when an up-to-date build exists, and "services linked to the build source with autodeploy enabled are deployed with the result". Deploys gain `buildId`, and `POST /services/{id}/deploys` accepts a `buildId` to deploy a specific build (`build_not_found`, `build_not_succeeded`). The dashboard edits a service's source under Settings → Build → Source → "Update source".

bex's build pipeline is App-shaped end to end (`lego/operator/internal/controller`, ~4,800 lines of build code): the build Job, its namespace, per-App registry credentials (one Zot htpasswd user and one ACL entry per App repository, ADR022/ADR074), build-time datastore reach, cancellation, failure classification and metrics are all keyed on an `App`. Zot used to re-read credential/ACL changes only on a pod restart, so per-link ACL grants would have bounced the registry on every link change. Since w4/m347 it hot-reloads them (`registry/verify.go`, ADR022 § Credential activation), so that cost is gone, but every grant is still a write to two cluster-global Secrets.

## Decision

1. **A build source is a carrier App.** `POST /v1/build-sources` creates an App CR of the new type `build_source` in the workspace namespace (public id prefix `bds-`, minted by `id.New`; `bsr` was already the Blueprint sync run prefix), carrying the git or image configuration and the build-time environment exactly as a service's App does. The operator runs the unchanged build pipeline for it and records the result (`status.image` digest, `status.buildRun`), but never creates a runtime for it: no Deployment, Service, Ingress, certificate, autoscaler or sleep. bex-api's service surfaces (lists, counts, plan quotas, metering, events of service kinds) exclude the type; `/v1/build-sources` is its only REST face.
2. **Build history.** Each carrier build is one of the carrier's deploy rows, published under the `bld` prefix (`id.Rekind` of the deploy id, same xid), with its build run id, status, timing, commit and the resulting digest, or the image identity for image-backed sources. There is no separate builds table. `POST …/builds` bumps the carrier's build trigger (the same field a manual deploy bumps) and opens a row.
3. **Linking.** A service with `buildSourceId` is an App whose `spec.buildSource` names the carrier. Its own build is skipped; its desired image is the carrier's selected build. Linking, unlinking and creating with `buildSourceId` go through the normal service write paths with Render's refusals.
4. **Image delivery without ACL changes.** On deploy the operator copies the carrier's built manifest into the linked service's own repository with the builder's admin credential — a cross-repository blob mount for the config and each layer, then a manifest PUT (a new `registry.CopyManifest` next to `TagManifest`) — and deploys the service from its own repository with its own pull credential. No per-link Zot ACL entry, no registry restart; a service can never read another repository. The digest is unchanged, so a deploy's image provenance stays exact.
5. **Fan-out.** When a carrier build succeeds, bex-api opens a deploy row (with `buildId`) for every linked service whose auto-deploy is on and sets that service's desired build; a deploy request with `buildId` selects an older succeeded build. Services with auto-deploy off keep their current release until deployed by hand.
6. **Surfaces.** REST serves the 20 Render operations (replacing w2/m251's named 404s); GraphQL and MCP expose the same verbs as bex extensions named after the REST verbs; the dashboard adds the Settings → Build → Source dialog. `buildSourceId` replaces the named refusal on service create/PATCH/GET.
7. **Regions.** bex has one region per installation (`BEX_REGION`, ADR049 D7): any Render region on a build source normalizes to it, so `build_source_region_mismatch` never fires on a single-region installation; a multi-region installation would compare normalized regions.

## Implementation notes (2026-11-03)

- **Ids.** `bsr` is already the Blueprint sync run prefix, so a build source is `bds-…` (minted by `id.New`); Render's contract publishes no pattern or example for either id. A build is the carrier's deploy row, and its public id is that row's id under the `bld` prefix (`id.Rekind`, same xid), so build history needs no separate table (§2 is satisfied by the carrier's deploys) and `GET …/builds/{buildId}` is one indexed lookup. `buildRun.id` is the deploy id; the list cursor is too.
- **Storage.** A carrier is an `apps` row of type `build_source` whose Kubernetes name is its `bds-` id, so it can never collide with a service name. A linked service carries `build_source_id` and the selected `build_source_image`, projected into `spec.buildSource`. Every service listing excludes carriers.
- **Render semantics to keep** (api-docs.render.com, `update-service`, `trigger-build-source-build`): a PATCH that links cannot be combined with build-configuration changes (only `startCommand`); linking to a native-runtime source requires a start command, and a Docker/image source rejects one; a link does not deploy until the deploy API is called; only git sources can be built.

- **Quota (t003).** ADR043 D3 makes the namespace's App count ResourceQuota the race-free service cap. A carrier is an App object, so the quota is widened by exactly the workspace's carrier rows (`roomForBuildSources`), re-converged when a carrier row is written (before its App) and after one is deleted; services stay capped at the plan's ceiling by the API server. Carriers have their own ceiling (`QuotaCaps.BuildSources`, 25 — Render publishes none), checked at create. Residual closed (w9/m180 t005): every service and build source create holds its workspace's create lease (`store.PGStore.WithWorkspaceCreateLease`, a `workspace_create_leases` row) from its row write through its App write. A carrier therefore widens the quota and writes its App with no service create in between, so a service can no longer take its slot. The lease is a row taken and released by short statements, not a Postgres advisory lock: a lock would pin a pooled connection per holder and per waiter while the create opens more, and concurrent creates could exhaust the pool. A crashed holder's lease expires after two minutes, a long create renews it, and a waiter gives up after 30 seconds with a retryable 503 `WORKSPACE_CREATE_BUSY`. Postgres and Key Value creates do not take it.
- **Create and edit (t003).** A carrier goes through the service create path (validation, clone secret, registry credential, release stamping) shaped as a build-only App; no plan is billed and no start command is required (each linked service supplies its own). Edits reuse the service setters, resolved under `core.WithBuildSources` after the id is checked to name a carrier; like Render, an edit is saved without building.

- **Names, links and fan-out (w9/m180).**
  - A build source's name is unique in its workspace on create and rename. A taken name is a 409 `BUILD_SOURCE_NAME_TAKEN`, as an env group's taken name is a 409 `ENV_GROUP_NAME_EXISTS`; Render's create and update document only 400/401/403/404/429 and no code for this case.
  - A create's `serviceIds` and `envGroupIds` are checked before the carrier is written. If the first service link then fails transiently, the carrier is deleted again, so a retry starts clean. A later failure keeps the carrier, because an earlier link already rewrote that service's own source, and answers 409 `BUILD_SOURCE_PARTIALLY_LINKED` naming the linked and failed services.
  - The fan-out writes a linked service's build conditionally under its trigger lock (`SelectAppBuildSourceImage`), so two runs of one build, a resync overlapping a slow first run, deploy each service once.
  - A refusal a retry would meet again completes the fan-out without that service: billing enforcement, a missing or re-linked service. The workspace owner deploys by hand once settled. Only transient failures keep the build open for the resync.

## Blueprints (w3/m270)

Render's Blueprint schema declares build sources in `buildSources` (at the root, under `ungrouped`, and under `projects[]`) and links a service with `services[].buildSource: <name>`. bex maps them onto the carriers above, so a Blueprint and the API manage the same object.

1. **Identity.** A build source's `name` is unique in the workspace, as Render's schema says, and is its carrier's display name. A sync finds the existing carrier by that name; two carriers sharing a name are refused rather than picked by list order.
2. **Scope.** A root or `ungrouped` entry is unscoped. A `projects[].buildSources` entry is scoped to that project (the carrier's `projectId`), resolved from the project's environments as the apply groups them. A build source's project cannot change: a sync declaring a different project is refused. A project that declares build sources and no environments is created for them (w3/m275, Render's 2026-10 schema).
3. **Fields.** `git.*` carries the service field names (`repo`, `branch`, `runtime`, `buildCommand`, `buildFilter`, `rootDir`, `dockerContext`, `dockerfilePath`, `registryCredential`, `envVars`), so a build source compiles into the build-only service declaration its carrier is and goes through the same presence-aware plan and sync. Omission semantics are a service's: an omitted `buildFilter` clears, every other omitted field is kept. `git.region` normalizes to the installation's region (§7). `image` is `{url, creds}`, as on a service.
4. **Build-time env vars.** A build source's `envVars` take a service's forms (w3/m275): literals re-apply on every sync, `generateValue` and `sync: false` seed the carrier's env store once, `fromGroup` links the env group to the build source, and `fromDatabase` / a Key Value `fromService` become secret-ref build env, which the build Job mounts. A `fromService` reference to a service is refused by name: build sources apply before services, so the build would run before what it names exists.
5. **Sync.** Build sources are applied after datastores and before services. A new one is created as `POST /v1/build-sources` creates it, and builds. A changed one is patched and rebuilt, the way a changed service redeploys; its linked services with auto-deploy on then deploy the result (§5). An unchanged one writes nothing.
6. **Links.** `buildSource` names a build source this file declares or one the workspace already has; any other name is refused before any write. The schema forbids source fields beside it (as Render's does), and Render's start-command rule applies (a native source needs the service's `startCommand`, a Docker or image one takes none). Linking an existing service, or unlinking it by declaring its own source again, is a sync change: it rolls out like any other. **Cron jobs (w3/m367):** Render's 2026-11-13 schema lets a `type: cron` service take `buildSource` with no runtime of its own. bex already linked cron jobs on REST (`buildSourceLinkTypes`), and a Blueprint cron's Render-named `startCommand` satisfies the link's start-command rule as its `command` does.
7. **Ownership and plan.** A build source is claimed (`build_source` claim kind) and labeled like the other managed resources, appears in the Blueprint's `resources[]` as `type: build_source` (Render's enum), and detaches when a file stops declaring it. Plan actions use kind `build_source`, with changed fields named `git.<field>` or `image`.
8. **Export.** Generate Blueprint writes a linked service as `buildSource: <name>` and exports each build source the selected services link under `buildSources`; the export re-plans as a no-op.

## Consequences

- One build feeds many services with no registry restart and no cross-repository read grant.
- Every place that enumerates Apps must exclude `build_source` carriers. `TestEveryAppEnumerationDeclaresBuildSources` guards Kubernetes `AppList` reads, and `TestEverySQLAppsReadDeclaresBuildSources` guards SQL that reads `FROM`/`JOIN apps` (w9/m180), so a new enumeration cannot silently include them.
- A carrier's builds are its deploy rows, but it is not a service: deploy webhook events exclude carriers, and a project or environment's service list never moves one, even when a caller names it (w9/m180).
- Storage cost: each linked service holds a reference to the same blobs (blob mounts share storage), so copies are cheap.
