# ADR118: Security review — a scoped API key's grant

- **Status**: Accepted (2026-11-18, w9/m496)
- **Trigger**: w9/m496 changes what a credential may do. A bex API key now carries a grant, a chosen subset of Render's per-area permissions, refused everything outside it on every surface ([ADR024 § An API key carries a chosen set of permissions](ADR024-members.md#an-api-key-carries-a-chosen-set-of-permissions-w9m496)).
- **Lineage**: a focused pass after [ADR117](ADR117-security-review-api-key-roles.md), like [ADR103](ADR103-security-review-static-rewrite-proxy.md). It keeps ADR117's invariants I1–I5 and reviews the three the grant adds: I6 (the grant can only refuse), I7 (fail closed) and I8 (a narrowing applies on the key's next request).
- **Amended**: 2026-11-19 (w9/125). The open-gateway-stream residual is closed: a stream a key opened is held to its grant on every revalidation tick (verdict 20).

## Scope

`lego/backend/internal/core/keygrant.go` (the catalog, `KeyGrant`, `Base.KeyGrant`, `KeyGrantAllows`, `RequireGrantableKeyGrant`, `KeyGrantCap`); the dispatch gate in `internal/api/scope_matrix.go` (`requireScopeClass`, `requireKeyGrant`, `requireGraphQLScopeFrom`, `withScopeClassREST`) and its operation map `internal/api/key_permission_ops.go`; storage (`store.SetAPIKeyGrant`, `store.APIKeyGrant`, migration 0300, `tenancy.Service`); mint and edit (`apikeys.CreateAPIKey`, `UpdateAPIKeyPermissions`, `PermissionCatalog` and their REST, GraphQL and MCP adapters); the projections that now ask the grant (`envgroups` values, `webhooks` signing secret, `usage` billing figures, `apps` Blueprint manifest) and the log tail's watchdog (`logs.withKeyGrant`). The w9/125 amendment adds the gateway's hold on a key's stream: the tickets' `KeyAction` and `core.KeyStreamAction`, the mint sites (`apps.CreateShellSession`, `sandbox` exec and connect tokens, `agentsessions.AttachTicket`), the internal verb `agentsession.KeyGrantHandler` (`POST /v1/api-key-grant` on :8091, `store.BoundAPIKeyGrant`) and the gateway's `sshgateway.KeyGrantGate` in all five transports.

## Verdicts

| # | Attack | Verdict | Evidence |
| --- | --- | --- | --- |
| 1 | A grant names a permission its creator's role lacks, so the key acts above its creator | Blocked twice | the mint and every edit check each named level against the **creator's** current relations, uncached (`RequireGrantableKeyGrant`, 403 `api_key_permission_above_role`); and a granted operation still passes the key's own relation checks, which `keyCeiling` caps at the creator at the same freshness, so a grant whose creator was later demoted only refuses. `TestMintRefusesAGrantAboveTheCreatorsRole`, `TestRequireGrantableKeyGrant`, and the e2e `TestScopedAPIKeyE2E`: a demoted Admin's key that still names the webhooks write is refused it, and the demoted creator cannot widen another key past their new role |
| 2 | An Admin edits a Developer's key up to Admin permissions | Blocked | an edit is validated against the key's creator, not its editor (`TestEditNarrowsAndWidensWithinTheCreatorsRole`) |
| 3 | A key widens its own grant, or another key's | Blocked | the edit verb is mint-class: `AuthorizeMintClass` refuses every machine caller before anything else; REST, GraphQL and MCP classify it `mint`. `TestAKeyCannotEditAGrant`, the e2e PATCH as a key |
| 4 | A member who is neither the key's creator nor an Admin rewrites someone's key | Blocked | `api_key_permissions_editor_forbidden` unless the caller is the creator or holds `can_manage` uncached (`TestEditNarrowsAndWidensWithinTheCreatorsRole`) |
| 5 | A newly added operation has no entry, so a scoped key reaches it unchecked | Blocked twice | at runtime an operation missing from `keyPermissionOps` needs `KeyNoGrant`, which no scoped grant holds (`TestScopedKeyGrantFailsClosed`); in CI `TestKeyPermissionsCoverLiveOperations` fails on any live REST, GraphQL or MCP operation without an entry, and `TestKeyPermissionDriftReportsAnUnmappedOperation` proves the comparison catches one |
| 6 | An entry maps a write to a read action, so a Read only key writes | Blocked | `TestKeyPermissionWritesNeedAWriteAction` fails on any write- or mint-class operation a Read-level action is enough for, outside a named list of writes that change nothing (validating or previewing a render.yaml, running SQL through the connection the credentials view reveals, a recovery-window lookup) |
| 7 | A sensitive read maps to a resource's plain view | Blocked | `TestKeyPermissionSensitiveReadsNeedASecretView`: every sensitive-class read needs a secret's own view (env-var values, environment-group values, build-source values, connection strings and credentials, exports, object bytes) |
| 8 | The grant cannot be read (Postgres down), and the gate falls back to the creator's role | Blocked, fails closed | `Base.KeyGrant` answers `ErrAuthzUnavailable` (503) and every projection hides its value. `TestScopedKeyGrantFailsClosed`, `TestKeyGrantFailsClosed` |
| 9 | A stored entry names a permission the catalog later drops or renames | Blocked | it grants nothing and is logged (`KeyGrantFromEntries`, `TestKeyGrantStorageRoundTrip`) |
| 10 | A GraphQL batch mixes a permitted field with a refused one, in one operation or as a second operation selected by no name | Blocked | every top-level field of every selected operation is checked against one read of the grant before anything resolves; one refusal refuses the document. `TestScopedKeyIsRefusedOutsideItsGrantOnEverySurface` (`query A {…} mutation B {…}`, and two roots in one query) |
| 11 | A secret through a nested GraphQL field of a permitted root (`service { envVar(…) { value } }`) | Blocked | the nested-secret walk the OAuth gate already does now also needs "View environment variables and secret files" from a key; environment-group, datastore and build-source values are root fields with their own entries, and the `EnvGroup` and replica connection types nest key names and hosts only |
| 12 | A secret on a plain read's projection: an environment group's values on `GET /v1/env-groups/{id}` or a write's response, a webhook's signing secret, billing figures, a Blueprint's raw manifest | Fixed in the change | each projection asked only the relation (which a Developer's key holds); it now also asks `KeyGrantAllows` for the secret's own action and answers masked when the grant lacks it |
| 13 | A cached grant outlives a narrowing on another replica | Blocked | nothing caches it: the gate reads the key's row on every request, as the revocation marker already is. `TestNarrowedGrantRefusesTheNextRequest` counts one read per request; the e2e narrows over REST, GraphQL and MCP and is refused on the next request |
| 14 | A live log tail outlives a narrowing | Fixed in the change | the tail's watchdog asks for "View service logs" on every tick (`logs.withKeyGrant`). `TestKeyTailEndsWhenItsGrantNoLongerCoversLogs`: a key's open tail ends, and frees its slot, once its grant stops covering logs, and fails if the watchdog stops reading the grant |
| 15 | A side entry point skips the dispatch gate | Not a gap | a key reaches bex-api only through the REST mux and the Cloudflare-shaped mux (`withScopeClassREST`), `/graphql` and both MCP mounts (`requireMCPScope`). The routes mounted outside them take no API key: deploy hooks and sandbox connect tokens authenticate with their own HMAC or URL token, minted through a gated operation; the GitHub callback with its signed state; webhooks, the OIDC issuer and RFC 9728 metadata are public. Shell, exec, file-transfer and attach tickets are minted only through gated operations (`services.jobs`, `sandboxes.exec`, `sandboxes.files`, `agents.manage`) |
| 16 | A scoped mint whose grant write fails leaves a key that acts with All | Blocked | the grant is written before the secret leaves the server, and a failed write unbinds the key and deletes its client (`TestMintRollsBackWhenTheGrantCannotBeRecorded`); a process that dies in between leaves a client whose secret nobody ever received |
| 17 | A key with no machine row (unbound or revoked) reads as All | Not a gap | the row is the key's binding: without it the key holds no tuple, so every decision is refused before the grant matters; a revoked key is refused by the revocation marker first (ADR012 §8d) |
| 18 | A key with no recorded creator is scoped and then widened past I3 | Blocked | its grant can only be set to All (`UpdateAPIKeyPermissions` refuses a scoped grant for it); I3 still caps it at a Developer |
| 19 | Over random grants, creator roles and operations, a key is allowed something its grant or its creator refuses | Blocked | `TestKeyDecisionIsItsGrantAndItsCreator` (500 random cases through the real gate and `keyCeiling`) |
| 20 | A shell, exec, file transfer or agent attach a key opened outlives a narrowing of its grant (this review's first residual) | Fixed (w9/125) | bex-api signs into each ticket the action its mint needed (`KeyAction`, set by `core.KeyStreamAction` only for an API key; a person's ticket, background work running as a key's creator and bex-api's own commands name none, so § Accepted still holds for work a key started). The gateway's Postgres role cannot read a grant, so `sshgateway.KeyGrantGate` asks bex-api's HMAC verb `POST /v1/api-key-grant`, which answers from the grant read uncached as the dispatch gate reads it, at redemption and on every revalidation tick, and ends the stream at the first tick after a narrowing. An answer it cannot get ends a key's stream (I7) and never touches a person's, which never asks. A native SSH key a key enrolled before ADR072 F3 is told from a person's once per connection and held the same way: one-off jobs (Services Read & write) on a service, Sandbox execution in an agent session's sandbox. Per transport, `TestWebSocketKeyShellEndsAtTheFirstTickAfterItsGrantNarrows`, `TestSandboxExecKeyStreamEndsAtTheFirstTickAfterItsGrantNarrows`, `TestSandboxFileKeyTransferEndsAtTheFirstTickAfterItsGrantNarrows`, `TestAgentAttachKeyStreamEndsAtTheFirstTickAfterItsGrantNarrows` and `TestNativeSSHKeyOwnedSessionEndsAtTheFirstTickAfterItsGrantNarrows` see the stream end after one grant read past the narrowing; their `…SurvivesAWideningAndAnUnrelatedChange` and `…NeverAsksForAGrant` siblings keep it for a widening, an unrelated change, a grant that still covers it and every person; `TestAKeysExecEndsWhenItsGrantNarrows` runs bex-api's own mint through the real gateway; `TestStreamTicketMintsNeedTheActionTheGatewayHoldsThemTo` keeps each ticket's action equal to what its operations need |

Every new guard was reverted once and a test above failed: the gate's grant check (16 assertions failed), the nested-secret check, the GraphQL batch walk, the role cap at mint and at edit, the mint-class gate on the edit verb, and the environment-group projection. So were w9/125's: each transport's tick and redemption check, the file revalidator's action, the connect tokens' carried action, and native SSH's per-connection and per-tick checks.

## Accepted, by design

- **Writes that run code imply the environment they run in.** A key that may change a service's start command or image, run a one-off job or open a shell (Services Read & write) can make the service print its own environment, without "View environment variables and secret files"; a key that may start a cloud-agent session can have the agent use the workspace's agent secrets. This is Render's model: its Services Read & write bundles "Manage preview environments and one-off jobs" with service updates. bex adds no stricter rule, so a grant means on bex what it means on Render.
- **A Write-only credential grant yields a credential.** Postgres credentials at Write ("Create and delete database credentials") answers the new credential, as Render's does; "View connection strings and credentials" is about existing ones.
- **Work a key started keeps running after a narrowing.** An automation or agent session it created, or a deploy it triggered, is not stopped by a later edit, as it is not by a role change; pausing or deleting it is a person's call.

## Residual risk

- **Open gateway streams (closed 2026-11-19, w9/125, verdict 20).** A stream a key opened ends within one `BEX_SSH_REVALIDATE_INTERVAL` (1 minute) of a narrowing, as it does of a revocation or a role change. What is left: a key-owned native SSH connection, like every native SSH session, rides out up to three unanswered checks in a row (w6/147), so a bex-api outage keeps it at most three minutes; and during the first rollout of this change, a gateway question that reaches a bex-api replica without the verb is unanswered, which refuses a key's stream and a native SSH login, as a bex-api outage already refuses a login through the owner's email check.
- **Cost.** One indexed Postgres lookup per API-key request, the same as the revocation marker every cached token already reads; a grant lookup that cannot answer turns that key's requests into 503s until Postgres answers. Each stream a key holds open adds one internal verb call, one grant lookup and one nonce row per revalidation tick; a person's stream adds none, and a native SSH connection one at authentication.
