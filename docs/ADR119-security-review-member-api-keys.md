# ADR119: Security review — every member mints and manages their own API keys

- **Status**: Accepted (2026-11-19, w9/m514)
- **Trigger**: w9/m514 widens who may hold a credential. Every member role now mints an API key in its workspace, as on Render, and a member below Developer lists, edits and revokes the keys they minted ([ADR024 § Every member mints and manages their own API keys](ADR024-members.md#every-member-mints-and-manages-their-own-api-keys-w9m514)).
- **Lineage**: a focused pass after [ADR117](ADR117-security-review-api-key-roles.md) and [ADR118](ADR118-security-review-scoped-api-keys.md), whose invariants I1–I8 it keeps, reviewing the two this change adds: I9 (minting widens who holds a key, never what a key may do) and I10 (a member below Developer reaches only the keys they minted).

## Scope

`lego/backend/internal/apikeys/service.go` (`relOwnKeys`, `CreateAPIKey`, `PermissionCatalog`, `ListAPIKeys`, `keyRelation`, `mintedByCaller`, `RevokeAPIKey`, `UpdateAPIKeyPermissions`); `store.BindClientForCreator` and `tenancy.BindKey` (seating a key at any member role); the unchanged paths the wider set of key holders now reaches: `core.keyCeiling`, `core.RequireGrantableKeyGrant`, `store.enqueueRoleReconciliation`, `apikeys.AccountTeardown.CleanupSubjectInWorkspace` and the dispatch gate's `keyPermissionOps`. Reviewed as an attacker holding a Viewer, Contributor or Billing membership, and a key they minted.

## Verdicts

| # | Attack | Verdict | Evidence |
| --- | --- | --- | --- |
| 1 | A Viewer's key reads service logs, a sensitive field (environment variables, connection strings) or restarts, creates or deletes a service | Blocked | the key holds a `viewer` tuple and `keyCeiling` asks its creator the same relation at the same freshness. The e2e `TestBelowDeveloperAPIKeysE2E` asserts each key's answer equals its creator's on six REST calls (list, logs, restart, create, environment variables, deploy) and the named refusals on GraphQL and MCP; `TestKeyNeverExceedsItsCreatorOverRandomHistories` now starts creators at all five roles over 500 histories (reverting the ceiling fails it at the second history) |
| 2 | A Viewer's or Contributor's key opens a shell, an exec stream, a file transfer or a live agent turn | Blocked | each ticket is minted by a verb that decides `can_view_sensitive` (web shell, native SSH resolution, sandbox exec and files) or `can_create` (an agent turn), pinned by `representativeVerbRelations`; neither role holds them, and the ceiling refuses them to the key whatever its tuple says. A Contributor's key may read an agent transcript (`can_operate`), as the Contributor may. With no stream opened there is nothing for the SSH gateway's revalidation to keep alive |
| 3 | A Billing member's key reaches billing figures, the Stripe portal or the Build Pipeline spend | Allowed, as for its creator | these verbs decide `can_manage_billing`, which a Billing member holds, Render's "full access to the workspace's billing settings, including updating payment method"; the key's grant must be All, because no scoped level grants the billing writes (ADR024 § Billing's grant cap). The e2e reads `pipelineSettings` with the Billing key and is refused it with the Viewer's. An Admin's key reached the same verbs before this change |
| 4 | A member names a level above their role in a mint or an edit | Blocked | `RequireGrantableKeyGrant` against the creator's current role, uncached: `TestEveryMemberRoleMintsAKeyCappedAtTheirRole` and the e2e (a Viewer's Read & write, Run and Write mints answer `403 api_key_permission_above_role`; a Viewer's widening edit of their own key is refused) |
| 5 | A Viewer lists, edits or revokes another member's key in their workspace | Blocked | `keyRelation` decides any key the caller did not mint with `can_manage_keys`, the gate every key verb had before, so the answer is the 403 a Viewer always got, audited once as a denial against `can_manage_keys` (`TestABelowDeveloperMemberEditsAndRevokesOnlyTheirOwnKeys`; on REST, GraphQL and MCP in the e2e). `ListAPIKeys` filters to the caller's own keys unless `can_manage_keys` holds, failing closed to that view (`TestABelowDeveloperMemberListsOnlyTheirOwnKeys`); reverting the filter, the own-key path or the machine-caller exclusion each fails a test |
| 6 | A creator reaches their own key through a workspace they are not in, or names their workspace for a key bound elsewhere | Blocked | the verb's `Authorize` still checks membership of the acting workspace, and `requireKeyIn` still holds the key to it (`TestOwnKeysStayInTheirWorkspace`) |
| 7 | A key with no recorded creator, or one minted by a key, becomes someone's own | Blocked | `mintedByCaller` needs a person caller and a non-empty `bex.co/created-by` equal to their subject; such keys stay `can_manage_keys` (`TestABelowDeveloperMemberListsOnlyTheirOwnKeys`) |
| 8 | A member forges a key's creator to make another member's key their own | Not a gap | the stamp is written by bex's mint from the caller's identity into Hydra client metadata that only bex's admin API can change (ADR117 residual 2) |
| 9 | A Viewer's key lists, revokes or mints keys through its own client id | Blocked | a machine caller owns no key (`TestAKeyOwnsNoKey`: a Viewer's All key lists nothing and revokes neither its own nor a key it is stamped as the creator of); minting stays human-only (`AuthorizeMintClass`, I4) |
| 10 | A Viewer's key enrolls an SSH key, mints a key or re-roles a member | Blocked | I4 and I5 are unchanged; the e2e asserts all three answer 403 for a Viewer's key |
| 11 | A promoted member's key keeps the higher role after a demotion, or survives removal | Blocked | `enqueueRoleReconciliation` moves every key the person minted in the same transaction as their own role, for any role, and the ceiling holds it at once (I1); removal revokes the member's keys (w2/m163). The e2e promotes a Viewer to Developer (their key creates a service), demotes them (refused) and removes them (the key is deleted and loses its tuple) |
| 12 | The relation choice leaks whether a key id exists | Not a gap | `keyRelation` reads the key before the one `Authorize`, but the only thing it decides is whether the caller minted it, which the caller already knows; an unknown key and another member's key are both decided with `can_manage_keys`, so every answer is the one a caller of that role got before |
| 13 | Reading the key before authorization fails open when Hydra cannot answer | Not a gap | a registry error is returned (no `Authorize`, no key change); only a not-found falls back to `can_manage_keys` |

Every new guard was reverted once and a test above failed: the list filter, the own-key relation, the machine-caller exclusion, the mint gate's relation, and the seat at any role in `BindClientForCreator` (the e2e's Contributor mint answers 403 without it).

## Accepted, by design

- **A key is as strong as its creator, now including the roles below Developer.** A Contributor's key restarts services and reads logs, and a Billing member's key opens the Stripe portal, because their creators can. That is the rule of ADR117 and Render's ("Your key's access adjusts to match your new member role").
- **A member's own-key verbs are audited under `can_manage_ssh_keys`**, the relation over a member's own credentials, and another member's under `can_manage_keys`. Each row's verb (`apikeys.CreateAPIKey`, `apikeys.RevokeAPIKey`, `apikeys.UpdateAPIKeyPermissions`) and target are unchanged.

## Residual risk

- **Shared workspace quotas.** The active-key quota (20 keys) and the mint rate (a burst of 5, then 20 a minute) are per workspace, so a member below Developer can now spend them, which only a Developer or an Admin could before. The cost is a refused mint (`409 API_KEY_ACTIVE_LIMIT`, `API_KEY_CREATION_RATE_LIMIT`), never access. Owner: the workspace Admin, who sees and revokes every key and whose removal of a member revokes theirs; each mint is in the audit log. Revisit with a per-member share if a workspace reports it.
- **ADR117's and ADR118's residuals stand** for these keys: a read on another replica may use a 30 s cached positive, and an open gateway stream outlives a grant narrowing until its session cap ([w9/125](../.pm/w9/125.md)); a below-Developer key can open no such stream (verdict 2).
