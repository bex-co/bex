# ADR121: Security review — an API key creates Postgres logins

- **Status**: Accepted (2026-11-19, w9/117)
- **Trigger**: w9/117 relaxes a credential-class gate. bex's native Postgres user create (`POST /v1/postgres/{id}/users`, GraphQL `createDatabaseUser`, MCP `create_postgres_user`) returns the new login's password once, so `postgres.Service.CreateUser` took `AuthorizeMintClass`, which refuses every machine caller (ADR024 I4). Render's key with "Create and delete database credentials" creates a PostgreSQL user, so bex refused what Render allows. A bex API key with a recorded creator now creates one, acting for its creator ([ADR024 § An API key creates Postgres logins as its creator](ADR024-members.md#an-api-key-creates-postgres-logins-as-its-creator-w9117)). Render parity comes first, and AGENTS.md says to amend the older decision rather than keep the divergence; this review is what makes the amendment safe.
- **Lineage**: a focused pass after [ADR117](ADR117-security-review-api-key-roles.md), [ADR118](ADR118-security-review-scoped-api-keys.md), [ADR119](ADR119-security-review-member-api-keys.md) and [ADR120](ADR120-security-review-key-member-management.md), whose invariants I1–I12 it keeps, except that I4 no longer covers creating a Postgres login. It adds I13 (a key creates a Postgres login only as its creator could, now). It follows ADR120's shape: the same gate, the same reasoning, a different verb.

## Scope

`lego/backend/internal/postgres/access.go` (`CreateUser`, `createUser`); `core.Base.AuthorizeExportClass`, `AttributedAPIKey` and `KeyCreator` (`internal/core/keyrole.go`); the unchanged paths a key's create now reaches: `core.keyCeiling` in both checks, `createUser`'s cached `can_create` fetch and its uncached re-check (`AuthorizeDatabaseFresh`, codex round-8 #8), the Database's own-workspace resolution (w6/m17), `ValidateRoleIdentifier` and the reserved names (w4/m170), the dispatch gate's `keyPermissionOps` (all three native operations and Render's `POST /v1/postgres/{id}/credentials` need `postgres.credentials.manage`) and the audit row. Reviewed as an attacker holding a leaked API key of each member role, with All and with a scoped grant, and as a delegated third-party token.

## Verdicts

| # | Attack | Verdict | Evidence |
| --- | --- | --- | --- |
| 1 | A Contributor's, Viewer's or Billing member's key creates a login | Blocked | none of them holds `can_create`, and the ceiling asks the creator the same relation at the same freshness, so a stray developer tuple on the key lifts nothing. `TestAKeyCreatesNoPostgresUserItsCreatorMayNot`; the e2e's Contributor key gets 403 on REST, GraphQL, MCP and Render's route |
| 2 | A Developer is demoted or removed; their key keeps creating logins | Blocked (I1) | `createUser` re-checks `can_create` uncached and the ceiling asks the creator uncached too, so the key is refused on its next request; a removal also revokes the key (w2/m163). The unit test demotes and removes the creator under a key whose own tuple still says developer; the e2e demotes the creator through the member verb (refused on every surface, allowed again once promoted back) and removes them (refused) |
| 3 | A key whose grant lacks "Create and delete database credentials" creates a login | Blocked (I6) | the dispatch gate maps `REST POST /v1/postgres/{id}/users`, `createDatabaseUser`, `create_postgres_user` and `REST POST /v1/postgres/{id}/credentials` to `postgres.credentials.manage`, which only Postgres credentials Write or Read & write grants. The e2e's Postgres instances Read & write key (with credentials Read) gets `403 api_key_permission_denied` on all four; its credentials Write key creates logins |
| 4 | A key with no recorded creator creates a login | Blocked | I3 leaves such a key `can_create` (a Developer's relations), so the class gate is what refuses it: `AuthorizeExportClass` admits a machine caller only when Hydra names it a bex API key with a creator. `TestCreateUserStillRefusesAnUnattributedCaller` and the e2e on the three native surfaces |
| 5 | A delegated third-party OAuth token creates a login | Blocked (w4/079, codex round-7 F3) | `AuthorizeExportClass` falls through to `AuthorizeMintClass` for every caller that is not an attributed key, and a human token from a client bex did not provision fails it, `bex.write` or not. Same tests |
| 6 | A `client_credentials` client that is not a bex API key (operator-provisioned) creates a login | Blocked | it is no key in Hydra's registry, so `AttributedAPIKey` is false. `TestCreateUserStillRefusesAnUnattributedCaller` gives it a developer tuple and it is still refused |
| 7 | A key creates a login on a database in another workspace where its creator is a Developer | Blocked (I2) | the Database is authorized against its own workspace (w6/m17), a key holds tuples only in its own, and the ceiling refuses any other workspace object |
| 8 | The creator lookup cannot answer (Hydra down) | Blocked, fails closed | `KeyCreator` returns `ErrAuthzUnavailable` (503) before anything is written. `TestCreateUserFailsClosedWhenTheKeyRegistryCannotAnswer` |
| 9 | A key reads the password of a login it did not create, or of the default | Not changed | the create returns only the login it makes; every other password is behind the connection info, which stays `sensitive` (`can_view_sensitive`) and needs "View connection strings and credentials" in the grant |
| 10 | A key makes an owner-privileged login, or takes the owner's or a reserved name | Not a gap | the native create always makes a login with `OwnerPrivileges: false`; the owner's name, an existing login and the reserved names are refused (400) as for a person (`TestUsersCRUD`, `reserved_identifiers_test.go`). Render's route, which makes the new default with owner privileges, was already open to keys and is unchanged |
| 11 | A key's login is not attributable | Not a gap | the audit row the create records (`RecordDatabaseEffect` with `DatabaseCredentialsCreated`) is built from the request identity, so it names the key's client id as the caller, as every key write does (ADR012 §8e) |

Each relaxation was reverted once and a test failed. With `AuthorizeMintClass` back in place, the unit tests and the e2e's Developer key failed (403). With no class gate at all, the key with no recorded creator, the operator client and the delegated third-party token each created a login, in the unit test and on every native surface of the e2e.

## Accepted, by design

- **A login a key creates outlives the key.** A login made by a key stays after the key is revoked, as one its creator makes stays after their session ends. That is the point w4/079 kept for a delegated token, whose consent is not the member's own authority. A bex API key is the member's own credential, revoked with their membership (w2/m163). Render's keys work this way.
- **A Write-only grant yields a credential.** A key granted only "Create and delete database credentials" gets the new login's password without "View connection strings and credentials", as [ADR118](ADR118-security-review-scoped-api-keys.md) accepted for Render's Write-without-Read rows: the view permission is about existing credentials.

## Residual risk

- **A leaked Developer or Admin key with the permission can add a login to every database in its workspace.** Owner: the workspace Admin. The audit log names the key, the login is listed with the database's credentials, deleting it retires it (NOLOGIN, NULL password), and revoking the key stops further creates. A key for automation that does not manage database users can be minted without the permission (w9/m496).
- **A create racing its creator's demotion.** The fresh `can_create` check runs before the write, so a demotion that commits between them lets one create land: the same window a request from the creator's own session has.
- **ADR117's, ADR118's, ADR119's and ADR120's residuals stand** for these keys.
