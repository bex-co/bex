# Render CLI compatibility checklist

Render's own CLI ([render.com/docs/cli](https://render.com/docs/cli), open-source [`render-oss/cli`](https://github.com/render-oss/cli)) is bex's fifth verified surface, the same way `render-oss/render-mcp-server` anchors the MCP surface ([ADR018-render-parity.md](ADR018-render-parity.md)). bex never forks or patches the CLI (`.pm/DO_NOT_DO.md`); this page tracks how much of it works against bex-api **unmodified**, with every claim backed by a captured, reproducible run. Gaps are bex-api's to fix, never the CLI's.

**Method.** One command per row (or one row per family where every subcommand shares a single root cause), each run for real against a live bex-api instance with real data (a deployed `web_service`, a `Database`, a `KeyValue`), evidence linked to [`.pm/w9/done/m2/evidence/log.md`](../.pm/w9/done/m2/evidence/log.md). Legend mirrors ADR018: ✅ works · ◐ works with a named divergence · ✖ fails (gap — owner in the backlog below) · — deliberate non-goal (`.pm/DO_NOT_DO.md`).

## Systemic root causes

Fifteen recurring/discovered bugs explain most of the ✖ rows below; each is cited by name in the table instead of repeating the diagnosis per row. RC1–RC6 came from the initial audit; RC7–RC9 surfaced during the same fix pass (same commit, `dfff3034`) but weren't broken out as their own root causes in the first draft of this table; RC10 only became visible once RC1's error-envelope fix stopped masking it, in a follow-up pass (`b4e3f64f`). RC11–RC12 surfaced in a third, more skeptical pass that pushed past `postgres update --plan` into its other flags and `postgres create --ip-allow-list` — both fixed in that same pass. RC13 is a still-open, deliberately-deferred display gap (owner/region/dashboardUrl/updatedAt, across Postgres/Service/KeyValue) found along the way. RC14 — found and fixed independently, same day, by a parallel pass over `keyvalues` — is KeyValue's own version of RC11/RC12's class of bug (flat `owner`/`options`/`ipAllowList` instead of Render's nested shape); its fix also resolves KeyValue's slice of RC13's `owner` gap specifically, but not `region`/`dashboardUrl`/`updatedAt` for any of the three resource types, nor Postgres/Service's `owner` gap — RC13 stays open for that remaining scope (`.pm/w6/016.md`). RC15 surfaced when w4/m22 seeded the previously unverified Environments success path and exposed its cursor-envelope drift.

| **RC1** | **Error envelope shape.** bex-api's error writer (`lego/backend/internal/core/http.go:63,66`, `WriteJSON(w, code, map[string]string{"error": err.Error()})`) emitted `{"error": "<message>"}`. Render's real contract (the CLI's generated `Error` type, `cli/pkg/client/types_gen.go:2120`) is a flat `{"id": "...", "message": "..."}` body. Because `{"error": "..."}` was still valid JSON, `encoding/json` silently unmarshaled it into a zero-value `Error{}` (no error to fall back on) — the CLI's `firstNonNilErrorField` (`cli/pkg/client/client.go:115-149`) then reported the unhelpful generic `"unknown error"` for **every** bex-api 4xx/5xx the CLI hit, discarding the real (often perfectly good) message bex-api sent. **Fixed 2026-07-15** (`dfff3034`: error bodies now also carry Render's `{id,message}` shape, `lego/backend/internal/core/http.go`), re-verified live — `postgres get <unknown-id>` now shows a real, specific message. ## Reproducing the ✅ rows

`scripts/cli-compat.sh verify` re-runs the rows marked ✅/◐ above that make a real bex-api call and exits non-zero the moment one regresses (see [`.pm/w9/done/m2/verify.sh`](../.pm/w9/done/m2/verify.sh) for exactly what it checks and how). As of 2026-07-15 this includes the full `keyvalues` lifecycle (create/list/get/suspend/resume/delete) the RC3/RC4/RC14 fixes shipped — it creates a uniquely-named real KeyValue instance (with a real `--ip-allow-list` entry) and cleans it up in a trap so a failed run never leaves one behind. Strengthened after RC14 slipped past the original version: a new `checkFields` helper asserts a whole set of fields (`id`, `name`, `ownerId`, `maxmemoryPolicy`, `persistenceMode`, `cidrBlock`) together against one response, specifically because RC14 exited 0 and echoed the right id/name while silently dropping every other field — a single-field spot check is exactly the kind of check that missed it the first time. **Not yet covered by this script** (verified manually, live, against dev-4/dev-9 this pass, but no automated regression guard exists yet): `postgres` full lifecycle (including the RC11/RC12 update flags and `--ip-allow-list`), `services` create/update/delete/instances, `deploys` list/create/cancel, `logs`, `environments`, and `logout`'s OAuth-revoke path — a gap worth closing so RC2/RC7–RC12 can't silently regress either.
