# Task: 用中文讨论「我能怎样帮 worker 解阻」

`/unblock <wN>`（Codex：`$unblock wN`）。这是面向用户的解阻对话：让用户尽快明白 **worker 为什么停住、自己能帮什么、作出哪个决定或完成哪一步后 worker 就能继续**。流程是：**必要核查 → 中文解释与建议 → 讨论用户能采取的行动 → 决定写回 board → 实现交接 loopx**。

成功标准是用户得到清晰可行的介入办法，需要用户回答的问题得到讨论，已确认结论落到 board。检查了多少文件、扫出了多少过时项，都不能代替这段沟通。默认不在本对话里自动启动 loopx、做实现或以 `$ship` 收尾。

接受 `w4`、`.pm/w4/` 或该 workstream 的 `blocked/` 路径，归一化为仓库内 `.pm/wN/`。没有目标时询问，不默认选 w4；路径不明确或 workstream 不存在时说明问题，不新建队列。

## 1. 做足以支持讨论的核查

- 读 `.pm/AGENTS.md`、`.pm/DO_NOT_DO.md` 和 [pm](../pm/SKILL.md)。所有 board 写入均通过 pm；记录解阻结论使用其 `unblock` 子命令。
- **对照最新代码，避免讨论过时的问题。** `git fetch origin main`；在 main 上可安全快进时 `git pull --ff-only origin main`。保留本地和其他会话的改动，不为核查而 reset、clean、stash 或提交。不能快进或不在 main 时，读取 `origin/main` 的 board、相关代码并对照本地 diff；fetch 失败就说明依据哪个可用版本继续。记录核查的 commit SHA。
- 枚举目标 `blocked/` 中的 milestone 和 inbox note，跳过嵌套 `done/`，对照 workstream README。先看条目说明及相关未完成任务，了解原卡点与已有决定；再按需要补充关键证据。
- **核查服务于讨论，不成为一轮完整审计。** 关键事实足以支持建议后，就向用户讲解并提问；不要先做全量镜像审计、重建、测试或部署，迟迟没有用户能采取的下一步。复杂条目逐组深入，不必等全部条目查完才开始交流。
- 过时项仍要清理：已满足原 DoD 的附证据通过 pm 关闭；重复或失效项按 pm 清理并保留有价值的历史；只是卡点消失、仍有工作则恢复待办。不要把代码合入当作线上验收通过。清理结果简短交代，然后回到仍需要帮助的卡点。
- 合并共同卡点，映射到全部受影响的 ID，避免重复问同一个决定。跨 workstream 依赖可读，board 写入只限目标 workstream。
- 现有规则或用户已作的决定直接沿用，普通技术判断交给 worker。Render parity 的充分实现不受可选增强或旧 ADR 阻挡，不把它们重新包装成用户决策。

- **对标产品决定推荐方向（用户偏好 2026-10-30）。** 托管（hosting）面向客户的行为对标 render.com（[ADR008 § Render parity first](../../../docs/ADR008-vision.md#render-parity-first)）。云端编码 agent（agent sessions、`/agents`、沙箱、PR 交付）对标 Devin（[ADR047](../../../docs/ADR047-cloud-coding-agent-sessions.md)）。
  - 推荐项必须是与对标产品一致的那一项。推荐前先核实对标产品的实际行为，不凭记忆；说明“Render / Devin 怎么做”，并作为推荐理由写出来。
  - 与对标产品不一致的选项可以列出，但不能作为推荐项，并要讲明它造成的偏离。偏离只有经用户签字、记录进 [ADR018](../../../docs/ADR018-render-parity.md)（Render）或相应 agent ADR（Devin）后才成立。
  - 可选增强不能挡住对齐所需的实现：先按对齐方案恢复，更严或更松的变体另开条目。已有规则或对标产品的行为能决定的做法，直接记为复核结论，不再要求用户拍板。确需产品取舍、外部资源或用户专属操作的才交给用户。

## 2. 核心交付：告诉用户能怎样帮忙，并讨论到可行动

用简体中文、从用户视角解释，保留必要的任务 ID 和代码名。先讲最值得处理的一组，不以文件清单或扫描统计开场。每组说明：

1. **想做到什么、现在卡在哪里：** 用具体场景说清影响，以及 worker 为什么自己过不去。
2. **你能怎样帮：** 一个明确的决定、授权、信息、资源或外部动作。说清谁在什么地方做什么；不要只说“需要确认”“缺权限”或“等上游”。
3. **我的建议与取舍：** 推荐可行路径，解释用户需要承担的成本、风险或维护责任，必要时比较其他路径。
4. **答复或行动之后：** 哪些工作会恢复、worker 第一件做什么、怎样确认条件已经满足。

**从客户角度讲场景和选项。** 解释卡点和每个选项时，尽量描述 bex 的客户（在 bex 上托管服务或使用编码 agent 的开发者）实际会经历什么：在哪个页面、CLI 命令或 API 调用里做了什么，看到什么、等多久、出错时得到什么提示，之后能不能继续。例如写“客户在 dashboard 点 Deploy 后，状态一直停在 Building，十分钟后才报错，日志里看不到原因”，而不是“reconcile 超时未上报 condition”。对比选项时，写清每个选项下客户的体验有什么不同，以及 render.com 或 Devin 的客户在同一场景下看到什么；技术细节放在后面，作为补充说明。确实没有客户可见影响的（纯内部机制、CI、运维）要直说，并改从运营者或 worker 的角度描述后果。

每轮落到一个可回答的问题或可执行的行动卡，不让用户读完后还得追问“所以我能做什么”。事实与推断分开，证据链接用于支撑判断，长日志和 digest 留在 board。

**“外部依赖”也要解释用户的介入空间。** 在现有约束内考虑用户能否补资源、授权替代路径、协调依赖、调整可交付范围，或明确接受等待的代价。不要未经讨论就把真实取舍归结为“只能等”。已有决定不重问；没有现实可行的用户动作时，坦白说明原因、依赖方和解除信号，不编造选择题。

按理解成本选择沟通方式，同一轮可混用：

| 情况 | 方式 |
| --- | --- |
| 多个独立、背景短、后果明确的决定 | 小批量 wizard，通常一轮 2–3 题，方便快速回答 |
| 一个简单决定 | 解释背景与建议，直接问一个短问题 |
| 背景复杂或取舍相互依赖 | 专门讨论一个主题，先让用户理解，再逐步收敛 |
| 缺用户专属权限、账号、信息或资源 | 行动卡：谁、在哪里做什么、完成信号是什么 |
| 外部依赖或上游迟迟不交付 | 解释等待的影响，讨论用户能授权或推动的可行替代路径 |
| worker 已能自行解决或卡点已消失 | 简短说明用户无需做什么，经 pm 恢复并准备交接 |

### 简单项：批量 wizard

- 使用当前模式可用的提问工具；没有时用简短编号选项。每题给足独立理解所需的背景，通常 2–3 个互斥选项，推荐项放前面，用客户会经历的具体体验说明每个选项的结果或代价。推荐项按上文对标规则选：托管选与 render.com 一致的，编码 agent 选与 Devin 一致的，并在选项说明里写明对标依据。不要用无意义的选项凑数。
- 决定用稳定编号（如 D1），映射到相关 board ID，允许 `D1=A，D2=B`。按答案调整后续题，不一次抛长问卷；依赖前一个决定的问题随后再问。
- 相互依赖的决定依次问，尚未澄清的复杂问题不能混入“全部同意推荐项”。“这批都按推荐”只适用于已展示且后果讲清的这一批。预选值、沉默、超时不是决定；等待答案时可做独立核查，不能替用户写下答案。

### 复杂项：专门对话

先用客户或运营者的具体经历解释现状与取舍，再比较少数可行路径；推荐服从上文对标规则，并说明已经核实的 render.com 或 Devin 依据。每次只问最能推进讨论的一件事；用户追问就先解释清楚，不急着逼成选择题，也不把普通实现细节甩给用户。需要用户决定的是目标、范围、资源或可接受的代价，worker 负责技术设计与验证。

例如，上游旧版镜像暂未提供修复时，可以讨论“是否允许 worker 维护平台统一修补的基础镜像，以承担一项持续维护成本来摆脱等待”，并说明它与每次租户构建临时安装补丁的区别；另一条路径是继续等待并明确风险和复查条件。这是帮助用户理解并决定可接受的路径，具体镜像构建与验证交给 worker。

复杂讨论不拖住独立决定：及时保存已确认结论。适合另开对话时给简短上下文（ID、背景、证据、核心问题），不假装已创建新会话。用户可先交接已决定的部分，其余保留待讨论。

### 外部动作：行动卡

写清最小步骤和完成信号。例如“管理员在现有 QA 环境配置登录凭据；worker 用 `scripts/qa-login.sh` 验证登录”，不让用户把密码贴进对话。worker 按已有授权能完成的动作留给 worker。用户同意一个计划不等于外部动作已经完成：在 board 中分别记录决定和仍待验证的条件。

## 3. 每个决定及时写回 board

收到明确答案后，调用 **`/pm unblock <wN/item> <结论与依据>`**。已有规则或过时项的证据也可据实记录为复核结论，不能冒充用户决定。不等复杂项全部聊完才保存；未答问题保持待定。

让 worker 只读 board 就能接手，用中文在原条目记录：

- 日期、涉及 ID、来源（用户决定 / 现有规则 / 复核证据）。
- 采用的路径、范围、理由及用户接受的取舍；写明已核实的对标依据（render.com 或 Devin），或不适用的原因。
- 用户要完成的动作、剩余条件、责任人和完成信号。
- worker 下一步、依赖、验收标准与必要证据入口；明确仍待决定的问题。

需要时同步原步骤和 DoD，但不删掉未完成的验收来伪造解阻。条件已具备才恢复待办；还缺外部动作则保持 blocked 并写明下一步。恢复不等于 done；已满足原 DoD 的按 pm 关闭。重跑复用已有决定，只处理新事实和未解决部分。

## 4. 交接实现，结束解阻对话

核对实际路径、状态和链接，简短说明：**你的决定已记在哪里；你还需做什么；哪些项可继续；worker 下一步做什么**。对未解决的主题留下明确问题，不能只交付“检测完成”和 blocked 数量。

实现与深入验证归 [loopx](../loopx/SKILL.md)。默认将可执行指令写进 board，并给出 **`/loopx <wN>`**（Codex：`$loopx wN`）作为交接，结束本次解阻对话；**只有用户明确要求现在开始实现或运行 loopx，才在当前会话启动它**。loopx 处理该 workstream 的全部开放队列，启动前说明范围。

`/unblock` 本身不授权源代码实现、镜像构建、部署、重建、commit 或 push。不要先自动做完工程，再把 `$ship` 权限问题当成用户唯一能帮助 worker 的事。用户明确追加的执行或发布请求按对应 skill 和仓库规则处理。
