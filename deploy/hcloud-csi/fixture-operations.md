# m144 owned-fixture operations

These fixed operations extend the existing main-only `hcloud-csi-rollout.yml` production-cluster job. They provision no infrastructure and accept no target, command, manifest, device, selector, image or query input. Inventory and CSI rollout retain their existing behavior. No real fixture authority is checked into this change: `fixture-proof.example.json` is deliberately invalid.

After the CSI rollout, operator adoption and bounded-class activation are verified, root creates one guarded Starter fixture through the prepared REST driver. The service's dated name uses the actual **UTC** create date. Root archives the actual HTTP201/request hash and disk binding, then commits a sanitized `deploy/hcloud-csi/fixture-proof.json` using the example's schema. Populate both pre-create baseline lists from the real driver; never replace them with empty lists for convenience. Copy `created_at` from the real create intent and preserve the driver's expiry, with the same one-service/one-disk/5Gi/two-hour/$0.03 budget. Do not include credentials, request environment values, fixture tokens or response URLs in this proof.

The existing read-only inventory supplies the actual App and PVC names/UIDs. The public `srv-…` ID is a label, not the App name; long child names are truncated. The proof must bind actual lifetimes, never predicted names alone. The proof must be tracked, unchanged from HEAD, non-symlinked and unexpired before active fixture operations. A later same-name App, PVC, PV or CronJob never inherits authority.

1. Dispatch `operation=fixture-bind`, `fixture_phase=initial-1g`. This reads selected metadata only. It verifies the exact service/workspace/disk App, App-owned PVC, PV claimRef, bounded encrypted StorageClass, Secret **metadata only**, service Deployment/ReplicaSet/pod chain, own node/attachment and reviewed CSI pod. It emits `candidateBinding`: exact PV/class/Secret/CronJob lifetimes, volume handle, reviewed CSI image/runtime image ID, and hashes of the controller-owned backup template and pod spec. Review its image ID against the published artifact review, then add the exact `candidateBinding` object as `binding` in the same proof and commit it. No exec or mutation is possible without this second committed binding.
2. Dispatch `operation=fixture-inspect` at `initial-1g`, `full-1g`, `grown-5g`, `restart-5g`, `redeploy-5g`, or `restored-5g`. Expected admitted size and raw ext4 geometry are 1Gi for the first two phases and 5Gi thereafter. Fixed read-only exec runs only `cryptsetup status`, `blkid -p -o value -s TYPE`, and `dumpe2fs -h` in the reviewed, bound-node CSI driver container. The device derives exclusively from the exact PV/attachment provider handle. CSI pod UID/container ID/image ID are rechecked around every exec. Only LUKS/device/sector and ext4 block geometry fields are emitted; filesystem labels, UUIDs and tenant files are not retained.
3. The same inspect operation reads that exact live node's fixed kubelet `/proxy/metrics` endpoint, filtering in memory to `kubelet_volume_stats_{used,capacity,available}_bytes` for the own namespace/PVC. Only those selected samples and collection time/node attribution are emitted. This avoids historical Prometheus series on an old node. Kubelet's own volume-stat cache still applies; sample collection alone does not prove that a post-fill/grow sample has refreshed. Compare successive receipts with the fixture's real usage probes and wait/reinspect until the observed full/grow behavior agrees. No synthetic requested-size metric substitutes for physical stats.
4. After the REST fixture driver has compacted files and recorded hashes, add its actual `snapshot_not_before` UTC timestamp to the proof and commit. Dispatch `operation=fixture-backup`, `fixture_phase=grown-5g`. It refuses existing deterministic Job names and in-flight own backup/restore Jobs. It posts exactly one Job copied from the verified own CronJob, with its exact CronJob UID owner, unchanged pod policy and run/ownership-digest provenance. An ambiguous transport failure never causes a replay. The first selected receipt preserves the actual created Job UID before policy validation. This step does not wait for or claim snapshot success.
5. Dispatch `fixture-backup-status` to read only that deterministic provenance-checked Job, even when a lost POST response left its UID unknown. It reports absent, or verifies the original committed CronJob/proof annotation/pod-spec provenance and emits the selected actual UID/status for root review. A post-create policy mismatch emits identity only with `podPolicyVerified=false` and fails; it never adopts the changed policy. Read-only reconciliation remains available after expiry/parent teardown. Commit the reviewed actual UID as `backup_job_uid` before cleanup. Verify the fresh own-instance snapshot separately through REST before requesting the REST restore. The existing operator and REST lifecycle perform growth, restart, redeploy, restore and final service/disk deletion. These CI operations never patch App/PVC/Secret/volume state or restart tenant pods.
6. Dispatch `fixture-backup-cleanup` to delete only the recorded Job, using `DeleteOptions.preconditions.uid` and foreground propagation. This cleanup remains allowed after expiry and after the old parents disappear; it refuses any replacement App/PVC/CronJob UID, wrong Job UID or changed creation provenance. It can cancel an active own backup to avoid stranding it past the budget window. A recorded exact own UID with changed pod policy can also be cancelled: the receipt stays explicitly unverified, and cancellation grants no exec or new-work authority. An accepted delete remains pending until the exact Job is observed absent. Use the REST/operator path for service, PVC/PV, Secret, snapshot purge and provider-volume cleanup; do not delete those resources directly.

Fixed active phases require the admitted PVC size, unchanged immutable binding, one Ready own service pod, exactly one attached node, and the reviewed Ready CSI image. Rebinding a per-mount pod or VolumeAttachment is allowed only through the same immutable App/PVC/PV chain; each receipt records the new identities for the prepared driver to compare with its preceding phase. Metadata, a Job completion or a successful source build alone cannot satisfy m144's original real hard-full, online growth, persistence, remount/restore, metrics, requested billing, every API/UI surface and cleanup definition of done.

## Continuous cleanup observation

After committing the exact binding, start `fixture-cleanup-observe` before acceptance mutations or DELETE. This fixed observer runs for at most100 minutes, with its own concurrency group so the backup workflow can run alongside it. The original fixture's two-hour deadline remains unchanged. It establishes exact App/purge-Job watches and a positive matching provider-volume HTTP200 baseline, samples the existing own geometry/metrics operations, then observes deletion through exact resource lifetimes and provider404. No provider write or Secret data read is added.

Download `m144-fixture-observer-ready` from that exact workflow run while its observer remains active. Its `ready.json` must contain the actual matching `observerReady` envelope, App UID, namespace, provider handle, expiry and server-established watch versions before dependent actions begin. Active job logs can return404, so stdout alone is insufficient for this handoff. The artifact is published before the bounded completion wait. Verify that the observer job remains active during acceptance; a failed observer leaves cleanup unproved and must not delay the deadline DELETE.

After the child is stopped/reaped, `m144-fixture-observer-evidence` preserves `observer.jsonl` and `status.json`. Cleanup requires the observed successful own-prefix purge, exact Kubernetes-resource absence and provider404. A changed helper image retains only `UNAPPROVED` evidence for independent strict signature/source review. Artifacts contain selected metadata, never credentials, kubeconfig or tenant files.

The separate `observer-channel-smoke` operation runs on `bex-ci` with no production environment or resource access. It uploads `m144-observer-channel-smoke` before a sixty-second hold so the artifact API can be checked while the job is active. Its deliberately invalid IDs and `protocolSmokeReady` state cannot authorize a real fixture.
